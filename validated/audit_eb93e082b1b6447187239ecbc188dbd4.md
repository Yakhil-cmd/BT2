### Title
Missing reentrancy guard in `register-for-bond` lets an attacker-controlled `signer-manager` trait implementation manipulate sBTC custody state before `roll-sbtc` executes, desynchronizing recorded custody from actual sBTC moved - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond` reads the staker's currently-custodied sBTC (`old-sbtc`) and computes the amount that should be transferred (`new-sbtc`) at the top of the function, then, before ever moving those tokens, invokes an attacker-supplied contract through the `<signer-manager-trait>` parameter via `signer-manager-validate-stake`. Only after that external call returns does the function call `roll-sbtc tx-sender old-sbtc new-sbtc` and commit the new `protocol-bond-memberships` / `protocol-bonds-total-staked` / `total-sbtc-staked` state. This is structurally identical to the Ammplify pattern: amounts are computed from state read at the start, an external/untrusted callback is allowed to run in between, and the state-changing settlement step at the end still uses the stale pre-callback amounts.

### Finding Description
`register-for-bond` computes `sats-total`, `old-sbtc` (via `get-staker-custodied-sbtc tx-sender`), and `new-sbtc` before doing any of its external interaction: [1](#0-0) 

It then calls into the caller-chosen `signer-manager` trait implementation: [2](#0-1) 

Only afterwards does it perform the actual custody movement and commit accounting state, using the `old-sbtc`/`new-sbtc` values computed *before* the trait call: [3](#0-2) 

`signer-manager` is a trait parameter (`<signer-manager-trait>`), so the caller can pass any contract implementing that trait, including one that re-enters `pox-5` inside `signer-manager-validate-stake` (e.g. calling `unstake-sbtc` or another bond operation on behalf of `tx-sender` or a delegated principal) to change `total-sbtc-staked`, `protocol-bond-memberships`, or the staker's custodied-sbtc accounting before the outer call resumes. When execution returns, `register-for-bond` still uses the `old-sbtc`/`new-sbtc` values captured before the reentrant mutation, so `roll-sbtc` moves a token amount that no longer matches the staker's true custodied balance, and the subsequent `map-set`/`var-set` calls overwrite the (already reentrantly-mutated) bond/staking state with values computed from stale inputs.

Crucially, the developers of this exact contract already recognized this class of risk in the sibling function `unstake-sbtc`, which explicitly guards against it: [4](#0-3) 

`register-for-bond`'s trait-calling code path (lines 753-756) has no equivalent `validate-no-reentrancy` call before it computes and later consumes `old-sbtc`/`new-sbtc`, breaking the invariant that "sBTC actually moved by `roll-sbtc` equals sBTC accounted for in `protocol-bond-memberships`/`total-sbtc-staked`" whenever the untrusted trait implementation reenters.

### Impact Explanation
If the reentrant call inside `signer-manager-validate-stake` can alter `get-staker-custodied-sbtc tx-sender`, `total-sbtc-staked`, or the staker's existing bond membership (e.g. by unstaking/rolling that staker's sBTC through a different code path mid-call), the final `roll-sbtc`/`map-set`/`var-set` sequence in `register-for-bond` will double-count or under-count sBTC custody relative to what was actually transferred. This can result in the protocol's recorded `total-sbtc-staked` diverging from the sBTC the contract actually holds — i.e., staking positions (and their associated signer weight / reward eligibility) backed by sBTC that was never actually locked, or sBTC being permanently stuck/unaccounted for. This matches the "double-counting a commitment" / "unlocking value never locked" / "signing weight exceeding locked value" impact classes.

### Likelihood Explanation
Exploitability requires the attacker to supply a malicious `signer-manager` (or in the "no bond admin/no other user's key" constraint, be the staker themselves calling with their own controlled signer-manager for their own bond registration) and requires that `signer-manager-validate-stake` actually invoke the caller-controlled trait method with enough control flow to reenter `pox-5` before `roll-sbtc` runs. I was not able to fully verify the internal implementation of `signer-manager-validate-stake` or `roll-sbtc` within the available iterations, so whether a full reentrant call chain (e.g. into `unstake-sbtc`, which itself is guarded) is actually reachable from within that trait callback is not fully confirmed from the code retrieved. The presence of the `validate-no-reentrancy` guard specifically added to `unstake-sbtc` for "reentrancy through signer-manager trait calls" is strong circumstantial evidence that this attack surface is real and was only partially mitigated across the affected entry points.

### Recommendation
Add the same `(try! (validate-no-reentrancy))` guard used in `unstake-sbtc` to `register-for-bond` before any state is read that will later be consumed by `roll-sbtc`, or re-read `old-sbtc`/`new-sbtc` (and re-validate bond/staker state) immediately after the `signer-manager-validate-stake` callback returns, so that the values passed to `roll-sbtc` and the committed accounting always reflect post-callback state.

### Proof of Concept
1. Staker calls `register-for-bond` with a malicious `signer-manager` contract implementing `<signer-manager-trait>`.
2. `register-for-bond` computes `old-sbtc`/`new-sbtc` from the staker's current custodied sBTC.
3. `register-for-bond` calls `signer-manager-validate-stake`, which invokes the malicious contract; inside that call, the malicious contract re-enters `pox-5` (e.g. via `unstake-sbtc`, using the staker's already-authorized position) and mutates `total-sbtc-staked` / the staker's custody-related state.
4. Execution returns to `register-for-bond`, which proceeds to call `roll-sbtc tx-sender old-sbtc new-sbtc` and commit `protocol-bond-memberships` / `protocol-bonds-total-staked` / `total-sbtc-staked` using the stale `old-sbtc`/`new-sbtc`, producing a mismatch between actual sBTC held by the contract and the amount recorded as staked.
