Based on my research, I found the key mechanism in ocore that mirrors the `block.number`/`block.timestamp` invalidation-hash bug class: the oscript `timestamp` value exposed to AA formulas is not the actual submission time of the triggering unit, but is derived from `objMcUnit.timestamp` — i.e., the timestamp of the **last stable MC unit at the time the trigger executes** — not a per-trigger unique value.

### Title
AA `timestamp` oscript value is derived from the last stable MC unit rather than the trigger unit, enabling identical values across multiple distinct triggers - (File: aa_composer.js)

### Summary
In `handleTrigger()`, `objValidationState.last_ball_timestamp` is set to `objMcUnit.timestamp` [1](#0-0) , and the oscript `timestamp` keyword simply returns this value [2](#0-1) . `objMcUnit` is the last **stable** MC unit read via `readLastStableMcUnit()`/`readLastUnit()` [3](#0-2) , not the actual trigger unit that invoked the AA. Because MC stabilization/advancement can lag behind incoming triggers (multiple triggers can be processed while the "last stable MC unit" stays the same), many distinct trigger units processed in sequence receive the exact same `timestamp` value from oscript — directly analogous to `block.number`/`block.timestamp` staying constant across multiple transactions on L2s such as Arbitrum/Optimism described in the report.

### Finding Description
AA authors are documented/expected to use `timestamp` as a source of per-response uniqueness/anti-collision entropy — this is explicitly demonstrated in the official test suite, where AA state-var keys are built as `trigger.address || timestamp` specifically to disambiguate calls [4](#0-3) . Because this `timestamp` is quantized to "the timestamp of the last stable MC unit" rather than a value unique per trigger unit, two or more different triggers arriving before the MC advances again will see an identical `timestamp`. Any AA logic that treats `trigger.address || timestamp`-style keys (or similar dedup/nonce constructions combining `timestamp` with `trigger.data`/`trigger.address`) as a unique identifier for state-var slots, generated addresses (`chash160`), issued asset identifiers, or "already processed" markers can experience collisions between logically distinct triggers, exactly mirroring the SphereX bug class where a coarse block-level value was mistakenly treated as a per-transaction unique invalidation component.

### Impact Explanation
If an AA's state machine uses `timestamp` combined with `trigger.address` (or similar) as a per-call idempotency/uniqueness key — a pattern explicitly used and tested in ocore's own test suite [5](#0-4)  — then a second, unrelated trigger from a different unit that happens to execute while the last stable MC unit (and hence `timestamp`) hasn't changed can silently overwrite/collide with state written by the first trigger. Depending on the AA's design, this can cause loss of funds, incorrect balance/state updates, or one legitimate trigger effectively voiding another's effect (a false-positive "duplicate" outcome) at the AA level. This is an AA-fund-loss/state-corruption class of impact reachable by any unpermissioned AA-trigger sender.

### Likelihood Explanation
`timestamp` staleness during trigger processing is a normal, frequent occurrence rather than an edge case: whenever a batch of AA triggers becomes stable together, or when triggers cascade through secondary AA calls, `objMcUnit`/`last_ball_timestamp` is fixed once at the start of `handleTrigger` for the whole primary+secondary chain [6](#0-5) , and `handleAATriggers()` iterates and processes many trigger rows from the `aa_triggers` queue for the same stabilized MCI in one pass [7](#0-6) . Any two primary triggers landing in that same batch (a routine event, not requiring any special conditions) get an identical `timestamp` value.

### Recommendation
For any AA-facing "uniqueness" guarantee, do not rely on `timestamp` alone or in combination with `trigger.address`/`trigger.data` as an anti-collision key; if oscript is meant to support unique-per-trigger identifiers, expose `trigger.unit` (already available) as the canonical uniqueness value instead of encouraging patterns keyed on `timestamp`. Documentation and any built-in helpers/test patterns that suggest `trigger.address || timestamp` as a good uniqueness idiom should be corrected to use `trigger.unit`, which is genuinely unique per unit [8](#0-7) .

### Proof of Concept
1. Deploy an AA whose `state` formula does: `var[trigger.address || timestamp]['processed'] = 1;` guarded by `if (!var[trigger.address || timestamp]['processed'])` to prevent "duplicate" trigger handling (this is the exact idiom shown in ocore's own test file) [4](#0-3) .
2. Have two different addresses each send a trigger unit to this AA. If both triggers get processed by `handleAATriggers()` while the last stable MC unit (and thus `timestamp`) has not advanced between them — e.g., both are queued in the same `aa_triggers` batch for one stabilized MCI [9](#0-8)  — and, due to a formula bug/design that omits `trigger.address` uniqueness or combines it in a colliding way, the second trigger's write to the state var can be treated as already "processed", causing it to be bounced/ignored or to silently overwrite the first trigger's state, corrupting the AA's stored state and potentially causing funds mismanagement.
