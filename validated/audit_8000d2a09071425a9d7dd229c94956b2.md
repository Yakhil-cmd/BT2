## Finding

### Title
Webhook signature verification is bound to `repository.owner.login`, but handlers act on unrelated commits/repositories, enabling cross-organization forged CI status and unauthorized deploy triggers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which organization's* `webhook_secret` is used to authenticate an inbound webhook based on `repository.owner.login` (or `organization.login`), but the handlers that actually execute side effects for that webhook operate on a different field (`repository.full_name`) or, in the case of `StatusHandler`, on no repository-scoping at all. This breaks the intended binding: *"the organization whose secret authenticated the payload" == "the repository/stack that gets written to."*

### Finding Description
`WebhooksController#verify_signature` resolves the signing organization purely from the JSON body itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` maintains fully independent `GitHubApp` instances — each with its own `webhook_secret` — keyed by organization name, as documented for "Using Multiple GitHub Applications" and exercised in `test/dummy/config/secrets_double_github_app.yml`: [3](#0-2) 

Once the signature is verified against *whatever organization the attacker names in `repository.owner.login`/`organization.login`*, `WebhooksController#create` dispatches the entire raw payload to handlers: [4](#0-3) 

Handlers resolve the target repository/stack from a *different* payload field, `repository.full_name`, via the shared `Handler` base class: [5](#0-4) 

Nothing enforces that `repository.full_name`'s owner segment matches `repository.owner.login` used for signature selection — they are simply two independent keys read from the same untrusted JSON body. Worse, `StatusHandler` does not scope by repository/organization at all — it matches purely on commit SHA across the entire installation: [6](#0-5) 

Creating a `Status` with `state: "success"` on an existing commit triggers `ContinuousDeliveryJob` for that commit's actual stack when continuous deployment is enabled, independent of which organization's secret was used to authenticate the webhook (confirmed by test behavior): [7](#0-6) 

### Impact Explanation
In a multi-organization Shipit deployment (the documented, supported configuration), an actor who legitimately controls only their own organization's GitHub App/webhook secret (Org A) — with no Shipit account, no `ApiClient` token, and no access to Org B's secrets — can:
1. Sign an arbitrary JSON payload with Org A's `webhook_secret` (which they legitimately hold, e.g. as an Org A GitHub App admin).
2. Set `repository.owner.login` (or `organization.login`) to `"OrgA"` so `verify_signature` selects and validates against Org A's secret.
3. Set unrelated fields consumed by handlers — e.g. an arbitrary commit `sha` belonging to Org B's stack for `status` events, or `repository.full_name = "OrgB/repo"` for `push`/`pull_request` events.

Because the signature check and the handler's write target are decoupled, the forged webhook is accepted and acted upon against Org B's stack. For `status` events this can force `ContinuousDeliveryJob` to run and trigger an **unauthorized deploy** of Org B's application by injecting a fabricated `success` status on an otherwise-undeployed commit — meeting the "unauthorized deploy" Critical-impact criterion, achieved purely by an attacker who never had access to Org B's secrets or Shipit credentials.

### Likelihood Explanation
Any Shipit installation configured with multiple GitHub organizations (a documented, first-class configuration) is affected. The attack requires only knowledge of a commit SHA in the target stack (visible on public GitHub repos or leaked via Shipit's own UI/API) and control of any one configured organization's webhook secret — a low bar since webhook secrets are commonly known to org/repo admins who set them up, not to Shipit administrators exclusively.

### Recommendation
Bind webhook processing to a single, consistently-verified organization identity:
- Derive `repository_owner` and select `Shipit.github(organization:)` from the same field the handlers use (`repository.full_name`'s owner segment), and reject the request (422) if `repository.owner.login`/`organization.login` disagree with the owner segment of `repository.full_name`.
- In `Shipit::Webhooks::Handlers::Handler` and `StatusHandler`, scope resolution (`Commit.where(sha:)`, `Repository.from_github_repo_name`) to only stacks/repositories whose configured GitHub organization matches the organization whose `webhook_secret` verified the request, rejecting/ignoring any mismatch.

### Proof of Concept
Given a Shipit instance configured with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret`:
1. Attacker (who only knows `OrgA`'s `webhook_secret`) computes `sha1=HMAC(OrgA_secret, body)` over:
```json
{
  "sha": "<sha-of-an-org-b-undeployed-commit>",
  "state": "success",
  "context": "ci/attacker",
  "repository": { "owner": { "login": "OrgA" } }
}
```
2. POSTs to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`.
3. `WebhooksController#verify_signature` resolves `repository_owner = "OrgA"`, verifies against `OrgA`'s secret, succeeds (`app/controllers/shipit/webhooks_controller.rb:24-30`).
4. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) looks up `Commit.where(sha: params.sha)` — matching the Org B commit regardless of the authenticated organization — and creates a `success` `Status`.
5. If Org B's stack has `continuous_deployment: true`, this triggers `ContinuousDeliveryJob` and an unauthorized deploy of Org B's stack (`test/models/commits_test.rb:233-243` demonstrates this exact `create!(state: 'success')` → `ContinuousDeliveryJob` behavior).

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
