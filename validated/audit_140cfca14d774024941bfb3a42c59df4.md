Based on my investigation, I found a plausible admission-boundary weakness in the **encrypted transactions** feature (a newer, non-standard Aptos capability layered on top of transaction admission), but I want to be explicit about the confidence level before presenting it.

### Title
Encrypted-transaction decryption path never verifies the sender/signer-key binding (`PayloadAssociatedData`), allowing ciphertext replay under a different sender - (File: `consensus/src/pipeline/decryption_pipeline_builder.rs`)

### Summary
Aptos' encrypted-transaction feature encrypts the transaction executable and binds the ciphertext to a specific `(sender, signer_auth_keys)` pair via `PayloadAssociatedData`, which is supposed to be checked with `EncryptedPayload::verify()` / `Ciphertext::verify(&associated_data)`. [1](#0-0)  However, the actual on-chain decryption/admission path that transitions a payload from `Encrypted` to `Decrypted` — `try_into_decrypted()` — only checks the `payload_hash` and optional `claimed_entry_fun`, never the associated-data binding. [2](#0-1)  The consensus decryption pipeline that drives this call also never invokes the associated-data verification; it calls `do_final_decryption(&decryption_key.key, prepared_ciphertext_or_error)` with only the raw decryption key and prepared ciphertext, then feeds the result straight into `try_into_decrypted`. [3](#0-2) 

### Finding Description
`EncryptedPayload::verify(sender, signer_auth_keys)` exists specifically to bind a ciphertext to the account that encrypted it, and is used by the SDK when building an encrypted transaction. [4](#0-3)  Grepping the codebase for callers of this verification shows it is exercised only from the SDK builder and from unit tests (e.g. `test_encrypted_payload_verification_binds_sender_and_auth_key` in `sdk/src/transaction_builder.rs`) — it is not called from the consensus decryption pipeline (`consensus/src/pipeline/decryption_pipeline_builder.rs`) or from the VM's transaction validation / prologue logic (`aptos-move/aptos-vm/src/transaction_validation.rs`, `aptos-move/aptos-vm/src/aptos_vm.rs`) that actually admits/executes decrypted transactions.

Since `RawTransaction.sender` and `sequence_number` are not encrypted (only the payload executable is), and since the ciphertext bytes are opaque and independently decryptable by the committee once the decryption key for the corresponding `encryption_epoch` is available, an attacker who can observe someone else's `EncryptedInner.ciphertext` (visible before decryption, as it must be included in blocks so the committee can decrypt it) can copy those exact ciphertext bytes into a new `RawTransaction` where `sender`/`sequence_number`/`gas_unit_price`/`expiration_timestamp_secs`/`chain_id` are the attacker's own values, sign it validly with their own key, and submit it. `TransactionAuthenticator::verify()` will pass because it only checks that the signature covers the (attacker-controlled) outer fields plus the copied ciphertext bytes — it does not know or care whose ciphertext this originally was. [5](#0-4)  During consensus decryption, `try_into_decrypted` will succeed because the `payload_hash` matches the plaintext hash regardless of who submitted the outer envelope — it never checks that the decrypted content was intended for this sender. [6](#0-5)  The result is that the copied plaintext executable is admitted and executed under the copying attacker's account/signer, not the original ciphertext creator's — a cross-account admission mismatch that the `PayloadAssociatedData` mechanism exists to prevent but is never enforced at the execution/admission boundary.

### Impact Explanation
This breaks the confidentiality/anti-front-running guarantee that the encrypted-transaction feature is designed to provide: an unprivileged network observer can copy any not-yet-decrypted ciphertext they see in a proposed block and resubmit it as their own transaction, causing the exact same decrypted executable/arguments to be admitted and executed under their own sender context before or instead of the original submitter's transaction. This is a genuine admission-boundary defect — a validation step (`PayloadAssociatedData`/ciphertext binding) that should gate admission is silently skipped, letting a transaction execute under the wrong submitter binding.

### Likelihood Explanation
Likelihood depends on timing: the attacker needs visibility into another party's ciphertext before/while it is being decrypted by the committee (e.g., by observing the proposed block or batch before the decryption key for that round is revealed) and needs to be fast enough to have their copy included and decrypted around the same epoch. This is plausible in a threshold-encrypted mempool/consensus design where ciphertexts must be broadcast to the committee before the decryption key is derived.

### Recommendation
Call `EncryptedPayload::verify()` (i.e., `Ciphertext::verify(&PayloadAssociatedData::new(raw_txn.sender(), signer_auth_keys))`) as part of `try_into_decrypted()` (or immediately before it in the decryption pipeline), using the associated data derived from the *actual signer(s) of the outer envelope* that is being decrypted, and reject with a new `DecryptionFailureReason` (e.g. `AssociatedDataMismatch`) if it fails — mirroring how `payload_hash`/`claimed_entry_fun` are already checked.

### Proof of Concept
Conceptual PoC (not executed, since this requires standing up the full batch-encryption + consensus decryption pipeline):
1. User A builds and submits an encrypted transaction; its `EncryptedInner.ciphertext` becomes visible in a proposed block prior to decryption.
2. Attacker C observes the ciphertext bytes and `payload_hash`/`extra_config`/`encryption_epoch`, and constructs a new `RawTransaction` with `sender = C`, a fresh valid `sequence_number`, and the same `TransactionPayload::EncryptedPayload(EncryptedPayload::Encrypted(original))` (same `ciphertext`, `payload_hash`, `encryption_epoch`, `extra_config`/`claimed_entry_fun`).
3. C signs this `RawTransaction` normally; `TransactionAuthenticator::verify()` succeeds since it only checks C's own signature over the (C-controlled) envelope plus the copied ciphertext bytes.
4. Once the committee reveals the decryption key for that `encryption_epoch`, the decryption pipeline decrypts the copied ciphertext to the same plaintext `DecryptedPlaintext` and calls `try_into_decrypted`, which only checks `payload_hash` — matches — and admits/executes the transaction under `sender = C`.

**Confidence caveat:** I was not able to inspect the full signature of `FPTXWeighted::decrypt`/`do_final_decryption` (only the call site) within the available tool budget, so I cannot 100% rule out that associated-data is threaded through some other layer of the batch-encryption crate (`aptos-batch-encryption`) that I didn't fully trace. The `verify()` API's existence and its exclusive use in SDK/tests, combined with `try_into_decrypted`'s explicit, narrowly-scoped checks (hash + claimed entry function only, no sender/associated-data check), is strong but not fully exhaustive evidence. If you need certainty, a Devin session should trace `FPTXWeighted::prepare_ct`/`decrypt` in `crates/aptos-batch-encryption/src/schemes/fptx_weighted.rs` to confirm whether associated data is ever bound at the cryptographic layer versus only at the optional `verify()` call.

    pub fn try_into_decrypted(
        &mut self,
        eval_proof: EvalProof,
        plaintext: DecryptedPlaintext,
    ) -> Result<(), DecryptionFailureReason> {
        let Self::Encrypted(original) = self else {
            panic!("try_into_decrypted called on non-Encrypted state");
        };

        if original.payload_hash != CryptoHash::hash(&plaintext) {
            return Err(DecryptionFailureReason::PayloadHashMismatch);
        }

        if let Some(claim) = &original.claimed_entry_fun {
            let TransactionExecutable::EntryFunction(entry_fun) = plaintext.executable() else {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            };
            if *entry_fun.module() != claim.module {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
            if let Some(claimed_function_id) = &claim.function
                && entry_fun.function() != claimed_function_id.as_ident_str()
            {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
        }

        *self = Self::Decrypted {
            original: original.clone(),
            eval_proof,
            decrypted: plaintext,
        };
        Ok(())
    }

    /// Encrypts a transaction payload using the provided encryption key.
    /// This is a helper method used internally by `with_encrypted_payload` and `payload`.
    fn encrypt_payload(
        payload: TransactionPayload,
        sender: AccountAddress,
        signer_auth_keys: Vec<(AccountAddress, AuthenticationKey)>,
        encryption_key: &EncryptionKey,
        encryption_epoch: u64,
    ) -> Result<EncryptedPayload> {
        // Convert payload to executable
        let executable = payload.executable()?;
        let extra_config = payload.extra_config();

        // Generate decryption nonce
        let decryption_nonce: DecryptionNonce = rand::random();

        // Create DecryptedPayload for encryption
        let decrypted_payload = DecryptedPlaintext::new(executable, decryption_nonce);

        let associated_data = PayloadAssociatedData::new(sender, signer_auth_keys);

        // Encrypt the payload
        // Note: FPTXWeighted::encrypt requires CryptoRng from ark_std::rand, so we use StdRng
        let mut rng = StdRng::from_entropy();
        let ciphertext = FPTXWeighted::encrypt(
            encryption_key,
            &mut rng,
            &decrypted_payload,
            &associated_data,
        )?;

        // Compute payload hash from the executable
        // We need to compute hash before encryption, so we use the executable directly
        let payload_hash = CryptoHash::hash(&decrypted_payload);

        // Create encrypted payload
        Ok(EncryptedPayload::Encrypted(EncryptedInner {
            ciphertext,
            extra_config,
            payload_hash,
            encryption_epoch,
            claimed_entry_fun: None,
        }))
    }
