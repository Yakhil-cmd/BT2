### Title
Webhook signature only authenticates *which secret matched*, not the organization/repository the payload claims to act on - cross-tenant forgery of statuses, pushes and team memberships - (`app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` picks a GitHub App/secret to validate the HMAC using a field read out of the *same* attacker-controlled JSON body (`repository.owner.login`, falling back to `organization.login`), then verifies the raw body against that org's `webhook_secret`. [1](#0-0) [2](#0-1)  Nothing ties that authenticated organization to the repository/commit the payload actually targets. Handlers instead resolve their target from other fields of the same body — `repository.full_name` for push/pull_request handlers [3](#0-2)  and, most severely, `sha` with **no repository scoping at all** for status updates [4](#0-3) , or `organization.login`/`team` free text for membership handling [5](#0-4) . Since Shipit explicitly supports multiple independent GitHub App configurations, each with its own `webhook_secret`, per organization [6](#0-5) [7](#0-6) , a party who legitimately controls the webhook secret for *one* configured organization can forge a validly-signed payload that authenticates as that organization while acting on data belonging to a completely different organization/repository configured in the same Shipit instance.

### Finding Description
The equality the code should enforce is:
`organization that authenticated the request == organization that owns the repository/commit/team being mutated`

What actually happens:
1. `verify_signature` derives `repository_owner` from `params.dig('repository','owner','login')` or `params.dig('organization','login')` [2](#0-1) , uses it solely to pick which `GitHubApp`/`webhook_secret` to HMAC-verify against [1](#0-0) , and only checks that the signature is a valid HMAC of `request.raw_post` under *that* secret [8](#0-7) .
2. Because the attacker constructs the entire JSON body themselves, `repository.owner.login` (used to pick the verifying secret) and every other field in the same payload (`repository.full_name`, `sha`, `organization.login`, `team`) are all attacker-controlled and mutually independent. There is no code path anywhere that checks these fields against each other.
3. Handlers then act on whichever field they use for targeting, oblivious to which secret validated the request:
   - `Handler#stacks` looks up `Repository.from_github_repo_name(payload.dig('repository','full_name'))` globally in the DB, not scoped to the authenticating org [3](#0-2) , and `Repository.from_github_repo_name` performs an unscoped `find_by(owner:, name:)` across the whole table [9](#0-8) .
   - `StatusHandler#process` is worse: it doesn't consult `repository` at all — it matches `Commit.where(sha: params.sha)` instance-wide and calls `commit.create_status_from_github!(params)` [4](#0-3) , so any commit sha in the entire Shipit instance can receive a forged status regardless of which org's secret signed the request.
   - `MembershipHandler#process` builds/updates a `Team` keyed by attacker-supplied `params.team.id`/`params.organization.login`, and adds an attacker-chosen `member.login` to it [10](#0-9) . `User#authorized?` grants access whenever the requesting user belongs to any team listed in `Shipit.github_teams` [11](#0-10) , so a forged `membership` event can synthesize a matching `Team` (same `organization`/`slug` as a configured `oauth.teams` entry) and add an arbitrary GitHub login to it.

Before the attack (baseline expectation): a webhook secret for org "A" should only ever authorize mutations to org "A"'s repositories/commits/teams.
After the attack: knowledge of org "A"'s `webhook_secret` (a value legitimately possessed by whoever administers org A's GitHub App in this Shipit instance) is sufficient to sign a payload whose `repository.full_name`/`sha`/`organization.login` fields reference org "B" (or any other org/repo/commit tracked by the same Shipit deployment), and Shipit will act on it.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out in scope. Concrete consequences:
- **Cross-repository writes / unauthorized status manipulation**: `StatusHandler` lets a signer of any configured org forge CI statuses on any commit tracked anywhere in the instance, which can unlock/allow automatic deploy checks that gate merges/deploys in unrelated stacks.
- **Cross-repository writes / unauthorized sync**: `PushHandler`/PR handlers let a signer of org A trigger `stack.sync_github`, archive/unarchive review stacks, or manipulate PR-driven review stacks for a repository actually owned by org B, since `Repository.from_github_repo_name` is not scoped to the authenticating organization.
- **Escalation into `Shipit.github_teams` authorization**: `MembershipHandler` allows fabricating `Team`/`Membership` records that match an org/team name Shipit uses for access control (`Shipit.github_teams`), letting an attacker add themselves (or anyone) to a required team and pass `User#authorized?`.

These map directly to the report's Critical/High categories ("cross-repository writes", "escalation into `Shipit.github_teams` authorization", "unauthorized deploy/rollback/merge").

### Likelihood Explanation
Requires the deployment to run Shipit with more than one configured GitHub organization sharing the same `/webhooks` endpoint (a documented, supported configuration - `docs/setup.md` "Using Multiple GitHub Applications"), and requires the attacker to know a legitimately-issued `webhook_secret` for at least one of those organizations (e.g., a tenant/customer org onboarded onto a shared Shipit instance, who is fully entitled to sign webhooks for *their own* org but not others). Given that this multi-tenant configuration is explicitly documented as a first-class feature, and the vulnerable code path (`verify_signature`, `Handler#stacks`, `StatusHandler#process`, `MembershipHandler#process`) is unconditionally reachable for any webhook event, likelihood is moderate-to-high in any deployment using multiple GitHub App configurations.

### Recommendation
Bind the authenticated organization to every subsequent lookup:
- After `verify_signature` succeeds, propagate the resolved `repository_owner`/organization identity into the handler dispatch, and require every handler to check that the resource it is about to mutate (`repository.full_name`'s owner segment, `commit.stack.repository.owner`, `team.organization`) equals the organization whose secret validated the signature, rejecting the event otherwise.
- In particular, scope `StatusHandler#process`'s `Commit.where(sha:)` lookup by the repository/stack belonging to the authenticated organization, and scope `Repository.from_github_repo_name` lookups (via `Handler#stacks`) similarly.
- For `MembershipHandler`, validate that `params.organization.login` matches the authenticated organization before creating/updating `Team`/`Membership` records.

### Proof of Concept
Given a Shipit instance configured with two organizations, `orgA` (attacker-administered, webhook secret known to attacker) and `orgB` (victim, with a tracked repository `orgB/critical-repo` and commit `deadbeef`):

1. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "deadbeef",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/decoy" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` — a value they can legitimately compute since they know `orgA`'s secret.
3. POST to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"orgA"` from the body, fetches `orgA`'s `GitHubApp`, and the signature validates successfully [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeef")` — matching the commit that actually belongs to `orgB/critical-repo` — and creates a forged successful CI status on it [4](#0-3) , even though the signature was for `orgA` and `repository.full_name` never referenced `orgB`.

This demonstrates the break: the org that authenticated (`orgA`) is not the org whose data was written (`orgB`'s commit/status). The same technique applies to `PushHandler` (setting `repository.full_name` to a victim org's repo to trigger `sync_github`) and `MembershipHandler` (setting `organization.login`/`team` to match a `Shipit.github_teams` entry to gain authorization).

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
