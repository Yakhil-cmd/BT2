This is the exact structure needed for the cross-organization signature/binding mismatch analog.### Title
Webhook signature verification is bound to the payload's `repository.owner.login`, not to the `repository.full_name` the event actually writes to - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App configuration (and therefore which `webhook_secret`) to verify a signature against using one field of the untrusted JSON body (`repository.owner.login`, i.e. the organization), while every downstream event handler resolves the `Stack`/`Repository` to mutate using a *different* field of that same body (`repository.full_name`). Because nothing ties these two fields together, and because `GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatically verified, an attacker can pick an organization slug that has no `webhook_secret` configured to short-circuit verification, then set `repository.full_name` to point at any other tenant's repository to have that repository's handlers process the forged event.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [2](#0-1) 
picks the `GitHubApp` used for verification via `Shipit.github(organization: repository_owner)`, where [3](#0-2) 
`repository_owner` is read straight out of the attacker-controlled JSON body (`repository.owner.login`, falling back to `organization.login`).

In `lib/shipit/github_app.rb`: [4](#0-3) 
`verify_webhook_signature` returns `true` unconditionally whenever the selected organization has no `webhook_secret` configured. Shipit explicitly supports multiple, independently configured GitHub organizations, each with its own optional `webhook_secret`: [1](#0-0) 
and the setup docs/example secrets show `webhook_secret` as an optional (`nil`-able) per-organization key: [5](#0-4) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the *entire unvalidated body* to handlers: [6](#0-5) 
Every handler resolves the target repository/stack from a completely different JSON field — `repository.full_name` — with no cross-check against the `repository.owner.login`/organization that was used to select the verification secret: [7](#0-6) 
For example `PushHandler` uses this to find stacks and immediately triggers a GitHub sync for them: [8](#0-7) 
and `Repository.from_github_repo_name` resolves purely by the `owner/name` parsed out of `full_name`, independent of whichever organization the signature check used: [9](#0-8) 

**The broken binding, as an equality that should hold but doesn't:**
`organization used to select/verify the webhook secret (repository.owner.login)` == `organization that owns the repository/stack the handler mutates (owner portion of repository.full_name)`

Before the attack: for a legitimately-configured multi-org Shipit instance, every inbound webhook for `org/repo` is signed with `org`'s secret and only ever affects `org/repo`'s data.

After the attack: an attacker crafts a body where `repository.owner.login` (or `organization.login`) is set to any organization slug configured in Shipit **without** a `webhook_secret` (verification auto-passes per `lib/shipit/github_app.rb:76-83`), while `repository.full_name` is set to `victim-org/victim-repo` (a fully different, secret-protected organization's repository). `verify_signature` succeeds because it only ever checked the secret-less organization; the handler then mutates `victim-org/victim-repo`'s `Stack`/`Commit`/`ReviewStack` records because it never looked at `repository.owner.login` at all.

### Impact Explanation
This breaks the trust boundary between organizations hosted on the same Shipit instance: an attacker who controls no credentials for `victim-org` can inject fully-processed GitHub events attributed to `victim-org/victim-repo`. Concrete reachable consequences with the surveyed handlers:
- `push`: forces `Stack#sync_github` for an arbitrary victim stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), which can trigger continuous-deployment pipelines out of band.
- `status`: creates/overwrites `CommitStatus` records for arbitrary victim commits (independent of GitHub's real CI state), which Shipit's deploy-gating logic (required statuses) consults before allowing a deploy — a forged "success" status can make an unsafe commit appear deployable, directly feeding into "an unauthorized deploy" outcome.
- `pull_request` events (`opened`/`labeled`/`closed`) can provision, archive, or unarchive review stacks belonging to `victim-org/victim-repo`.

This qualifies as High/Critical under the stated impact list (spoofed status enabling an unauthorized deploy path; cross-tenant writes to a repository/stack the attacker never authenticated against).

### Likelihood Explanation
Exploitability depends only on the Shipit operator having configured at least one organization without a `webhook_secret` (explicitly supported and shown as the default/optional case in the shipped example config), which is a realistic multi-tenant configuration mistake rather than a theoretical one, since `webhook_secret` is documented as optional per org. No GitHub credentials, Shipit session, or API token of any kind are required — only knowledge of the target `repository.full_name` and the name of any secret-less configured organization, both of which are discoverable/guessable (e.g., via the docs, the CHANGELOG, or trial requests that return `422` vs a processed response).

### Recommendation
- Bind the verified signature to the exact resource being mutated: after computing `repository_owner`, re-derive the organization from `repository.full_name`'s owner segment (or from `Repository#owner`) and require it to match `repository_owner` before dispatching to handlers.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for a *configured* multi-organization deployment; either require a secret for every organization or refuse to process events whose claimed organization differs from the resolved repository's actual organization.
- As defense in depth, resolve the target `Repository`/`Stack` first, look up the webhook secret from the resolved repository's stored owner/organization (not from the untrusted payload), and verify against that.

### Proof of Concept
Preconditions: Shipit instance configured with `github: { open-org: { <no webhook_secret> }, victim-org: { webhook_secret: "s3cr3t" } }`, and `victim-org/victim-repo` already tracked as a Stack.

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   # ignored, no secret configured for "open-org"

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
`repository_owner` resolves to `open-org`, `Shipit.github(organization: 'open-org').verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`), so `verify_signature` passes with `head 422` never called. `PushHandler` then resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and enqueues a sync for the victim's stack — despite the request never having been signed with `victim-org`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)

  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
