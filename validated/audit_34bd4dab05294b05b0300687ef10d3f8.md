### Title
`/events` SSE endpoint has no authentication because `Pubsubstub::StreamAction` bypasses the `Shipit::Authentication` concern and the middleware referenced in code comments does not exist - (File: `config/routes.rb`, `app/controllers/shipit/github_authentication_controller.rb`, `app/controllers/concerns/shipit/authentication.rb`)

### Summary
The comment in `GithubAuthenticationController#callback` claims `/events` and `/sidekiq` rely on a `UserRequiredMiddleware` to enforce `session[:authenticated]`, but no such class exists anywhere in the engine. Because `/events` is mounted directly as a raw Rack endpoint (`mount Pubsubstub::StreamAction.new, at: "/events"`), it never passes through `ApplicationController`/`ShipitController`, so the `force_github_authentication` `before_action` defined in `Shipit::Authentication` never runs against it either.

### Finding Description
The claimed binding is: `session[:authenticated] == true` (or equivalently a logged-in, authorized `current_user`) `⇒` request reaches `Pubsubstub::StreamAction` and receives SSE data. Tracing the code shows this binding does not hold.

- `session[:authenticated] = true` is set only in `GithubAuthenticationController#callback` [1](#0-0) , with a comment claiming `/events` and `/sidekiq` "leverage `UserRequiredMiddleware`" to check it.
- Grepping the entire repository for `UserRequiredMiddleware` returns exactly one match: the comment itself. No class definition, no `app.middleware.use`/`insert_*` registration exists anywhere, including `lib/shipit/engine.rb`, which only registers `OmniAuth::Builder` and, conditionally, `Shipit::SameSiteCookieMiddleware` [2](#0-1) .
- `/events` is registered with `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` at the top level of `config/routes.rb` [3](#0-2) . A `mount` of a Rack endpoint dispatches directly to that Rack app; it does not instantiate any `ActionController` and therefore never runs `before_action` callbacks such as `force_github_authentication`.
- `force_github_authentication` is defined as a controller `before_action` inside `Shipit::Authentication`, included only by controllers such as `ShipitController` [4](#0-3) [5](#0-4) . It has no mechanism to apply to a mounted Rack app.

Consequently `session[:authenticated]`/`current_user.authorized?` has zero effect on who can reach `Pubsubstub::StreamAction`; any unauthenticated HTTP client can `GET /events?channels[]=stack.<id>` (or `repository.<id>`) and receive the SSE stream, since the gem itself performs no authorization check on channel names (channel names are simply derived from `@stack.id`/`@repository.id` embedded in views, e.g. `events_path(channels: ["stack.#{@stack.id}"])` [6](#0-5) , and stack/repository ids are visible in ordinary page URLs, so no secret is required to guess a channel name).

Existing guards do not prevent this: `force_github_authentication`, `User#authorized?`, and the `github_teams` restriction all operate at the `ActionController` layer and are structurally incapable of covering a `mount`-ed Rack app; no other filter, `verify_signature`, or `ExplicitParameters` schema applies to `/events` at all.

### Impact Explanation
An unauthenticated attacker can subscribe to any stack's or repository's SSE channel and receive live "update" notifications published via `Pubsubstub.publish` from `Shipit::Stack` [7](#0-6) , i.e. unauthenticated read of stack/task state-change events, for any repository/stack hosted on the Shipit instance, repeatable indefinitely and across all tenants (any stack id can be enumerated/guessed since ids appear in normal page URLs). This matches the listed **High** severity category: "unauthenticated read of stack state, task streams or deploy output." It does not rise to Critical because the published payloads observed are update/refresh signals rather than direct exfiltration of `GITHUB_TOKEN`/`github_access_token`/`api_clients_secret`, and no write/command-execution path is reachable through this endpoint.

### Likelihood Explanation
No preconditions beyond network access to the Shipit host are required; the attacker needs no session, token, team membership, or repository role. This is trivially and repeatably exploitable with a single unauthenticated HTTP GET per target stack/repository channel, for as long as the Shipit instance runs with the routes as shipped (the `mount` at `/events` is unconditional in `config/routes.rb`, not feature-flagged).

### Recommendation
Enforce authentication at the Rack layer for the `/events` mount (and any `/sidekiq` mount the host adds), e.g. by wrapping `Pubsubstub::StreamAction.new` with an actual middleware/rack app that checks `session[:authenticated]`/`current_user.authorized?` before dispatching to `Pubsubstub::StreamAction`, or by moving the SSE endpoint behind a real controller action that includes `Shipit::Authentication`. Additionally, validate that the requested channel corresponds to a stack/repository the authenticated user is authorized to view, rather than trusting client-supplied channel names.

### Proof of Concept
```ruby
# test/integration/events_authentication_test.rb (proposed, not present in repo)
require 'test_helper'

module Shipit
  class EventsAuthenticationTest < ActionDispatch::IntegrationTest
    test "UserRequiredMiddleware is not defined anywhere in the engine" do
      assert_not defined?(Shipit::UserRequiredMiddleware),
        "UserRequiredMiddleware referenced in github_authentication_controller.rb comment does not exist"
    end

    test "/events is served without session[:authenticated] being set" do
      stack = shipit_stacks(:shipit)
      # no session set at all -- session[:authenticated] is nil/false
      get "/events", params: { channels: ["stack.#{stack.id}"] },
          headers: { "Accept" => "text/event-stream" }

      # Binding under test: session[:authenticated] == true  <=>  response served
      # Actual: request succeeds despite session[:authenticated] being falsy
      assert_response :success
    end
  end
end
```
Both assertions demonstrate the broken binding: the middleware the comment relies on does not exist, and the `/events` mount serves requests regardless of `session[:authenticated]`.

      before_action :force_github_authentication
      helper_method :current_user
    end

    module ClassMethods
      def skip_authentication(*args)
        skip_before_action(:force_github_authentication, *args)
      end
    end

    private

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
