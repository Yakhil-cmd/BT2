### Title
Cross-repository CI status forgery via `Shipit::Webhooks::Handlers::StatusHandler#process` lacking repository binding check - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up `Commit` rows purely `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, without ever checking that the webhook's `repository.full_name` equals the matched commit's `stack.repository.full_name`. Because GitHub SHA-1 identifiers are content-derived and not scoped to a specific repository, an attacker who controls any repository wired to Shipit (their own fork/org) can replicate an existing commit object (same tree, parents, author/committer timestamps and message) to reproduce an identical SHA, then fire a legitimately-signed `status` webhook from their own repo naming that SHA — causing Shipit to write a `success` status onto the *victim* stack's commit.

### Finding Description
The binding that should hold is:
`payload.dig('repository','full_name') == commit.stack.repository.full_name`

but it is never evaluated. `StatusHandler#process` is: [1](#0-0) 
which iterates *every* `Commit` row across *every* stack that shares the pushed `sha`, with no repository/stack filter at all, unlike other handlers in the same directory that scope lookups by `repository_name` (e.g. push/pull_request handlers). `create_status_from_github!` then unconditionally persists the forged status: [2](#0-1) 
Status creation flips `Commit#status`/`#success?`, which feeds directly into: [3](#0-2) 
and `deployable?` being true (combined with `stack.continuous_deployment?`) schedules deployment: [4](#0-3) 

Webhook signature verification only proves the request came from a GitHub App/webhook secret that is valid for *some* registered repository — it does not, and cannot by itself, prove the `sha` in the payload actually belongs to that repository's history. Since git commit SHAs are computed purely from commit content (tree, parents, author, committer, message, timestamps) and not from the repository name, an attacker fully controlling a repo they own can construct a commit object byte-for-byte identical to one that exists in a victim's tracked repository, giving it the same SHA, and then legitimately trigger GitHub to fire a signed `status` event for that SHA from their own repo. `drop_unhandled_event`, `verify_signature`, and the `ExplicitParameters` schema all pass because the request is a validly-formed, validly-signed status event — none of them check repository ownership of the SHA.

### Impact Explanation
A record (a CI `Status`) is written for a repository/stack that never authenticated it, directly enabling `Commit#deployable?` to become true and `schedule_continuous_delivery` to enqueue a deploy of a commit the target repository's own CI never actually approved. This is a cross-tenant mutation: a payload for one repository (attacker's) mutates another repository's stack/commit state and can trigger an unauthorized deploy — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy."

### Likelihood Explanation
Preconditions: the attacker needs (a) any repository connected to the same Shipit instance/webhook configuration (trivially satisfiable — attacker only needs to be able to add a webhook to a repo they own, and Shipit installations are typically GitHub-App-wide, not secret-per-repo), and (b) the ability to reproduce the exact byte content of the target commit (tree, message, author/committer identities and timestamps, parent SHA) in their own repository so the SHA matches. This is feasible whenever the target commit's full content is knowable/public (e.g. via the target's own public GitHub repo, PR diff, or leaked patch) — no cryptographic SHA-1 collision is required, only content replication, since SHA-1 of a git commit object is deterministic over that content. The target commit must not already be deployed/most-recent and the stack must not be locked and have `ignore_ci?` false, all attacker-observable/likely conditions. The attack is repeatable against any stack/repository sharing the webhook signing configuration.

### Recommendation
In `StatusHandler#process` (and analogously in `check_suite_handler.rb` if it has the same gap), scope the `Commit` lookup by the stack's repository derived from `payload.dig('repository','full_name')` before calling `create_status_from_github!`, e.g. join through `Commit -> Stack -> Repository` and reject/skip commits whose `stack.repository.full_name` does not equal the payload's `repository.full_name`.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_repository_binding_test.rb
test "status webhook for repository A must not affect commit belonging to repository B" do
  repo_a = shipit_repositories(:shipit)
  repo_b = create_repository(owner: 'attacker-org', name: 'evil-fork')
  stack_a = create_stack(repository: repo_a)
  stack_b = create_stack(repository: repo_b)

  colliding_sha = 'a' * 40
  commit_a = create_commit(stack: stack_a, sha: colliding_sha)

  payload = {
    'sha' => colliding_sha,
    'state' => 'success',
    'repository' => { 'full_name' => repo_b.full_name }
  }

  assert_not_equal payload.dig('repository', 'full_name'), commit_a.stack.repository.full_name

  Shipit::Webhooks::Handlers::StatusHandler.new(delivery: stub_delivery(payload)).process

  commit_a.reload
  assert_not commit_a.deployable?, "commit belonging to a different repository must not become deployable from an unrelated repo's status webhook"
end
```
Assertions: before the call, `payload.dig('repository','full_name')` (`repo_b.full_name`) differs from `commit_a.stack.repository.full_name` (`repo_a.full_name`); after processing the current code, `commit_a.deployable?` incorrectly flips to `true`, proving the missing binding check.
