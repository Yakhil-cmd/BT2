### Title
Webhook signature is verified against a secret keyed by the attacker-controlled `repository.owner.login`/`organization.login` field, while the actual event target is resolved from the equally attacker-controlled `repository.full_name` — allowing forged cross-repository events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the unauthenticated JSON body, before the signature has been checked. The rest of the pipeline (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) then dispatches on the same raw `params`, and the individual handlers locate the target `Stack`/repository using `repository.full_name`, a different field from the one used to pick the signing secret. Because both fields live in the same attacker-forged JSON body, an attacker who legitimately owns one GitHub organization/repository configured in Shipit (and thus knows that organization's `webhook_secret`) can sign a payload whose `owner.login` matches their own org (so signature verification passes) while `full_name` points at a victim organization/repository tracked by a different Shipit stack.

### Finding Description
`verify_signature` computes the expected HMAC using the secret for `repository_owner`, which is taken directly from the request body: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` itself only checks the HMAC of the raw body against the secret for the organization resolved above — it has no knowledge of, or binding to, which repository inside that body the payload claims to target: [3](#0-2) 

After signature verification, `create` re-parses and dispatches the *same* raw JSON to event handlers: [4](#0-3) 

Downstream handlers (e.g. the `pull_request` handler family) resolve the affected repository/stack using `repository.full_name` inside that payload rather than `repository.owner.login`, as shown by the multiple `full_name` references in those handlers (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `reopened_handler.rb`, `label_capturing_handler.rb`). The value used to select the verifying secret (`owner.login`/`organization.login`) is therefore never cryptographically bound to the value used to select the acted-upon repository (`full_name`). Since GitHub signs the entire raw body with the secret configured for the *sending* repository's org, and this app also lets an attacker choose which secret is "credited" by controlling `owner.login`, an attacker holding a legitimate `webhook_secret` for **any** org configured in Shipit can forge a full JSON body where:
- `repository.owner.login` = attacker's own org (secret known to attacker) — used only to pick the signature key.
- `repository.full_name` = `victim-org/victim-repo` — a completely unrelated repository/stack tracked by Shipit.

The attacker signs this crafted body with their own known secret and POSTs it to the shared `/webhooks` endpoint. `verify_signature` passes because the signature is valid for the secret it looked up (attacker's own org). The event is then processed as if it legitimately originated from `victim-org/victim-repo`.

Binding broken (equality that should hold but doesn't):
`organization whose webhook_secret authenticated the request` == `repository/stack the event handler subsequently writes to`.

### Impact Explanation
This breaks a core trust boundary of the engine: the webhook endpoint is public and multi-tenant across every GitHub organization configured in Shipit, and the signature is meant to prove "this request really came from GitHub for repository X." Because the secret-selection field and the target-repository field are independent and both attacker-supplied, an attacker with write access to only their own, unrelated GitHub repo/org can inject `push`, `status`, `check_suite`, `pull_request`, or `membership` events against a victim's stack that they have no access to. Depending on which handler is targeted, consequences include:
- Forging a `status` event as "success" for an arbitrary commit SHA on the victim stack, which can trigger `deployable_status` transitions and, on stacks with continuous deployment enabled, cause an **unauthorized deploy**.
- Forging `pull_request` events to open/close/label PRs on review stacks belonging to a different repository, mutating stack state that belongs to a repo the attacker does not control.
- Cross-repository state corruption/writes against stacks the attacker has no legitimate relationship with.

This matches the report's "Critical" bucket ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
The only precondition is that the attacker legitimately administers at least one GitHub organization/repository that is configured in this Shipit instance (i.e., has a `webhook_secret` assigned, which is the normal state for any onboarded org — not a privileged or Shipit-specific credential). No Shipit session, API token, or GitHub App private key is required; the attacker crafts the HTTP request themselves and computes the HMAC locally with a secret they already know. This is a realistic, unprivileged-attacker scenario matching the rules' credential/repository boundary criteria.

### Recommendation
Bind the secret-selection field and the event-target field to the same verified value. Concretely: after selecting the org via `repository_owner`, verify that every repository/stack referenced elsewhere in the payload (`repository.full_name`, PR `base.repo.full_name`, etc.) belongs to that same, already-authenticated organization before any handler is allowed to act on it — reject the webhook if these do not match.

### Proof of Concept
1. Attacker owns `attacker-org/attacker-repo`, which is configured in Shipit with `webhook_secret: S`.
2. Attacker crafts a raw JSON body for a `status` (or `pull_request`) event where:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"` (a stack actually tracked by Shipit)
   - `sha`, `state: "success"`, etc., set to target a real commit in the victim stack.
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `"attacker-org"` [2](#0-1) , fetches `Shipit.github(organization: "attacker-org")`, and `verify_webhook_signature` succeeds because the HMAC is valid for secret `S` [3](#0-2) .
5. `create` dispatches the full, forged `params` (including `repository.full_name = "victim-org/victim-repo"`) to the registered `status`/`pull_request` handlers [4](#0-3) , which resolve and mutate the victim stack using `full_name`, producing an unauthorized status/PR state change on a repository the attacker never controlled.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
