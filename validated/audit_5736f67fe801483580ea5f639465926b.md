This confirms the multi-tenant GitHub App configuration: `Shipit.github(organization:)` looks up per-organization credentials/webhook secrets via `github_app_config`, keyed by the organization name in `secrets.github`, and `WebhooksController#verify_signature` derives that organization purely from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` inside the untrusted, attacker-supplied JSON body, then verifies the HMAC signature against that org's secret only — but the object that actually gets written to (a `Repository`/`Stack`) is resolved independently by each `Handler` via `payload.dig('repository', 'full_name')`. ### Title
Cross-tenant webhook forgery via mismatched signature-verification organization and processed repository full_name - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, taken from the same untrusted JSON body it is validating (`repository.owner.login` or `organization.login`). Every event `Handler` (e.g. `Shipit::Webhooks::Handlers::PushHandler`, `PullRequest::*Handler`) instead resolves the target `Repository`/`Stack` using a *different* field of the same body, `repository.full_name`. Because the controller never checks that `repository.full_name` belongs to the organization used for signature verification, a tenant who legitimately knows one organization's webhook secret (any customer/org onboarded on this multi-tenant Shipit instance) can forge a payload whose `repository.owner.login` matches their own org (so the signature check passes) while `repository.full_name` points at an unrelated repository belonging to a different organization on the same instance.

### Finding Description
- `Shipit.github_app_config`/`Shipit.github` supports per-organization GitHub App configs (`TOP_LEVEL_GH_KEYS`, `github_app_config`), each with its own `webhook_secret` [1](#0-0) .
- `WebhooksController#verify_signature` picks the app/secret to validate against solely from `repository_owner`, itself read from the raw POST body before the signature has been validated against *that specific repository* [2](#0-1) , [3](#0-2) .
- Once `verified` is true, `WebhooksController#create` dispatches the whole payload to `Shipit::Webhooks.for_event(event)` handlers unconditionally [4](#0-3) .
- Every handler's `repository_name` (and thus the `Repository`/`Stack` acted upon) is derived from `payload.dig('repository', 'full_name')` — a field never compared to `repository_owner` [5](#0-4) . This is used, for example, by `PushHandler#process` to sync/deploy commits on stacks belonging to the resolved repository [6](#0-5) , and by pull-request handlers to update or archive stacks tied to a different repository entirely [7](#0-6) .

The broken equality is: **organization that authenticated the signature (`repository.owner.login`) ≠ repository that is actually written (`repository.full_name`)**.

### Impact Explanation
On a multi-tenant Shipit deployment (multiple GitHub orgs configured with distinct `webhook_secret`s under `secrets.github`), any org that is a legitimate, low-privilege customer of the instance can compute a valid signature using its own known secret, but substitute a `repository.full_name` belonging to a different tenant's repository/stack. This can trigger unauthorized cross-repository writes: forced `GithubSyncJob`/deploy-related state changes via `PushHandler`, spurious PR/stack archiving via `PullRequest::ClosedHandler`/`ReopenedHandler`, or membership/status mutations for a repository the attacker does not own. This matches the "Critical: cross-repository writes / unauthorized deploy" impact category, since it lets one tenant's credentials influence another tenant's deployment pipeline state.

### Likelihood Explanation
Exploitation requires only knowledge of a single organization's `webhook_secret` configured on the shared Shipit instance (something any onboarded tenant would legitimately possess to register their own repo's webhook) plus the ability to POST directly to `/webhooks` with a crafted, correctly-signed JSON body — no Shipit session, API token, or GitHub App private key is needed. This only applies to deployments that actually configure multiple organizations under `secrets.github` (per-org GitHub Apps); a single-organization instance (`github_default_organization` nil, using the top-level `secrets.github`) is not affected since there is only one webhook secret and one implicit "organization" for all repositories, so verification and dispatch are effectively bound together.

### Recommendation
After computing `verified`, additionally assert that the resolved `repository_owner` matches the owner segment of every `repository.full_name`/`base_repository.full_name`/`organization.login` field that will subsequently be used by handlers to select the `Repository`/`Stack`, rejecting the payload (`head(422)`) on mismatch. Alternatively, have handlers resolve the target repository/stack and confirm its `Repository#owner` equals the `repository_owner` used to select the verifying GitHub App before performing any write.

### Proof of Concept
1. Assume the Shipit instance is multi-tenant with `secrets.github` configured as `{ tenant_a: { webhook_secret: "secretA", ... }, tenant_b: { webhook_secret: "secretB", ... } }`, and `tenant_b/private-repo` is onboarded as a `Repository`/`Stack` belonging to `tenant_b`.
2. Attacker controls `tenant_a` and legitimately knows `secretA` (e.g. they configured their own GitHub App's webhook).
3. Attacker crafts a JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker chosen sha>",
     "repository": { "owner": { "login": "tenant_a" }, "full_name": "tenant_b/private-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, raw_body)>` and sends `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"tenant_a"`, looks up `tenant_a`'s app, verifies successfully against `secretA` [2](#0-1) .
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("tenant_b/private-repo")` and triggers `stack.sync_github(expected_head_sha: params.after)` on `tenant_b`'s stack [6](#0-5)  — a cross-tenant write the attacker had no authorization to perform.

    return nil unless secrets&.github

  end
