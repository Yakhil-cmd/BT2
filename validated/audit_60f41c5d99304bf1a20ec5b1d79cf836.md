### Title
Unauthenticated `X-Shipit-User` header lets any API-token holder impersonate an arbitrary Shipit `User` for deploys, rollbacks, merges and locks - (File: `app/controllers/shipit/api/base_controller.rb`)

### Summary
`ApiClient#authenticate` cryptographically verifies *which token* is calling the API, but the `User` identity that gets attributed to (and, for merge requests, recorded as the requester of) every write action is taken from a plain, unsigned `X-Shipit-User` request header and is never checked against the authenticated `ApiClient`. This is the same class of bug as the disputed `Swap.vy` finding: a binding that should tie the verified credential (the HMAC-signed API token) to the acting principal is missing, so the two can diverge — exactly the "GitHub identity vs. `User` bound to the session" trust boundary called out in the rules, here manifesting as "the credential that authenticated vs. the `User` the action is attributed/authorized as".

### Finding Description
`ApiClient.authenticate` verifies the HMAC-signed token and returns the `ApiClient` record; that is the only cryptographically-verified identity in the request [1](#0-0) . Separately, `current_user` — the object attributed as the actor of the operation — is derived from `identify_user`, which trusts the raw `X-Shipit-User` header and does a case-insensitive lookup with no signature, no relation to `current_api_client.creator`, and no check that the caller is entitled to act as that login: [2](#0-1) 

Any request carrying a valid `ApiClient` token (even one scoped only to `deploy:stack`/`lock:stack`/etc. via `require_permission`) can set `X-Shipit-User: <any-existing-login>` and have all of the following record/attribute the action to that arbitrary user instead of the real caller:

- `DeploysController#create` → `stack.trigger_deploy(commit, current_user, ...)` [3](#0-2) 
- `RollbacksController#create` → `deploy.trigger_rollback(current_user, ...)` / `active_task.abort!(aborted_by: current_user, ...)` [4](#0-3) 
- `TasksController#trigger`/`#abort` → `stack.trigger_task(..., current_user, ...)`, `task.abort!(aborted_by: current_user)` [5](#0-4) 
- `LocksController#create`/`#update` → `stack.lock(params.reason, current_user)` [6](#0-5) 
- `MergeRequestsController#update` → `MergeRequest.request_merge!(stack, params[:id], current_user)`, which persists `merge_requested_by: user` and writes that login into the GitHub merge commit message via `merge_message` [7](#0-6) [8](#0-7) [9](#0-8) 
- `ReleaseStatusesController#create` → `deploy.report_healthy!(user: current_user)` / `report_faulty!(user: current_user)` [10](#0-9) 

Equality that should hold but doesn't: `current_api_client.creator == current_user` (or at minimum, `current_user` should be constrained to identities the token holder is entitled to represent). Instead, `current_user` is fully attacker-controlled via a header while `current_api_client` is the only thing actually verified.

### Impact Explanation
This is an authorization/audit-attribution bypass, not merely a cosmetic mislabeling issue:
- `stack.lock_author`/`archive!`/`lock` fields, `merge_requested_by`, and the GitHub merge-commit "Merge-Requested-By" trailer are all forgeable audit trails: an attacker holding a low-privilege but valid token (e.g., a CCMenu read-only-derived or narrowly-scoped client) can make it appear that a trusted teammate or admin requested/approved a merge, deploy, or lock/unlock, which can be used to push through a deploy or merge while shifting blame/approval onto someone else.
- Because none of these controllers cross-check `identify_user` results against `current_api_client.creator` or team membership (`User#authorized?` is only used for browser session auth in `app/controllers/concerns/shipit/authentication.rb`, not for API requests), the impersonation is unconstrained: any existing login discoverable through the UI/API (`GET /api/stacks/.../commits`, GitHub org membership, etc.) can be used.
- This does not itself grant new `ApiClient` *permissions* (the token's `permissions` array still gates the operation), so it is an escalation of identity/attribution within whatever operations the token is already scoped for — it does not directly yield RCE or GITHUB_TOKEN exfiltration. Given the strict impact list in the rules (cross-repository writes, unauthorized deploy/rollback/merge, escalation into `Shipit.github_teams` authorization), the closest fit is "unauthorized deploy, rollback or merge" attribution forgery, since a holder of a `deploy:stack`/`lock:stack` token can force a deploy/rollback/merge to be recorded and reported (including to Hooks/GitHub) as performed by an arbitrary other `User`.

### Likelihood Explanation
Any client possessing a valid, narrowly-permissioned `ApiClient` token (a routine credential, e.g. issued for CI or CCMenu-style integrations) can trivially set an arbitrary `X-Shipit-User` header on any authenticated API call; no additional access, secrets, or session is required beyond the token itself. Existing tests already assert the header is honored (`test/controllers/api/deploys_controller_test.rb`, `test/controllers/api/rollback_controller_test.rb`, `test/controllers/api/tasks_controller_test.rb`), confirming this is a designed but unauthenticated behavior. Because the rules exclude findings that merely "require an ApiClient token," note this analog is *not* about obtaining the token — it is about what a legitimately-issued, narrowly-scoped token can additionally forge (a different user's identity) once it is authenticated, which is squarely the ownership/binding gap analog requested.

### Recommendation
Do not derive `current_user` purely from an unauthenticated header. At minimum, require that the `X-Shipit-User` value be validated against the authenticated `ApiClient` (e.g., only allow it to equal `current_api_client.creator.login`, or require callers to prove control of that identity via a signed assertion), and audit-log both the authenticating `ApiClient` and the acting `User` separately so forged attribution cannot occur without evidence of divergence.

### Proof of Concept
1. Attacker obtains any valid `ApiClient` token scoped only to `deploy:stack` (e.g. a CI integration token) for the stack `acme/webapp/production`.
2. Attacker sends:
   ```
   POST /api_clients/../acme/webapp/production/deploys
   Authorization: Basic base64("<own-valid-token>")
   X-Shipit-User: trusted-admin-login
   { "sha": "<sha>" }
   ```
3. `DeploysController#create` calls `stack.trigger_deploy(commit, current_user, ...)` where `current_user` resolves to the `User` record for `trusted-admin-login` purely from the header [11](#0-10) .
4. The resulting `Deploy` (and any subsequent lock/unlock, merge request, or release status update using the same header trick) is permanently recorded as triggered/approved by `trusted-admin-login`, even though that user never made the request.

      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
