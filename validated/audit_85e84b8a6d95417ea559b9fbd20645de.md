### Title
Unbounded attestor list in the `attested` address/asset condition allows unbounded-cost SQL evaluation - (File: ocore--007/definition.js)

### Summary
The `attested` operator in address/asset definitions accepts an array of attestor addresses (`arrAttestors`) with no upper bound on its size, and — unlike sibling operators `in data feed` / `in merkle` — does not scale the `complexity` counter with the size of that array. As a result, `MAX_COMPLEXITY`/`MAX_OPS` limits do not constrain how large the attestor list can be, and every evaluation of the condition runs a SQL query whose `IN(...)` clause is proportional to the attacker-chosen array length.

### Finding Description
In `validateDefinition`'s `evaluate()` for `case 'attested'`, the code only validates that `arrAttestors` is a non-empty array and iterates it once to check each element is a valid address, but adds a fixed cost (`complexity++`, `count_ops++`) regardless of the array's length: [1](#0-0) 

Compare this to `in data feed` and `in merkle`, which explicitly account for the size of their address array in the complexity budget (`complexity += arrAddresses.length-1`), which naturally caps the array length once `MAX_COMPLEXITY` is reached: [2](#0-1) [3](#0-2) 

Because `attested` has no equivalent scaling, an attacker can define an address (or an asset's `issue_condition`/`transfer_condition`, or a signed-message authentifier condition) containing `['attested', ['this address', [huge_array_of_addresses]]]` while keeping `complexity` at 1, bypassing the intended complexity/DoS-limiting mechanism entirely.

At evaluation time (`validateAuthentifiers`'s `case 'attested'`), this huge array is passed straight into a SQL query via `storage.filterAttestedAddresses`, which builds an `attestor_address IN(?)` clause and a correlated subquery over `address_definition_changes`, executed once per unit that needs to be validated against this condition: [4](#0-3) [5](#0-4) 

This is directly analogous to the reported issue class ("unbounded computation reachable via attacker-controlled parameter causing expensive verification"): the `checkBalances`-style unbounded loop in the external report maps to an unbounded, attacker-controlled `IN(...)` list evaluated on every validation of a definition/condition that references it.

### Impact Explanation
If this `attested` condition is used as an asset's `transfer_condition` or `issue_condition`, *every* spender of that asset — not just the attacker — triggers the oversized query on every payment validation, since `transfer_condition`/`issue_condition` evaluation happens for each transfer/issue in `validatePaymentInputsAndOutputs`: [6](#0-5) 

Similarly, if used as (part of) an address definition or in a signed-message authentifier, every unit spent from that address, or every signed message verified against it, re-evaluates the oversized condition (definitions are re-validated on every use, per the comment in `validateAuthentifiers`): [7](#0-6) 

Because every full node must independently validate incoming units/messages the same way, a maliciously large attestor list can inflate per-unit validation time/CPU/DB load on all validating nodes, degrading their ability to validate and confirm other units in a timely manner — a network-wide processing slowdown triggered by a single posted unit/definition.

### Likelihood Explanation
Likelihood is moderate: constructing such a definition/condition requires only posting a normal unit with an address definition, asset definition, or signed message containing the crafted `attested` array — no special privileges are needed, and nothing in the current validation path rejects a large attestor array or charges it against `MAX_COMPLEXITY`/`MAX_OPS`. The main constraint is unit/payload size limits, but attestor addresses are 32 bytes each, so a large number of them (thousands) still fits well within typical payload limits, especially relative to the resulting SQL work.

### Recommendation
Charge the `attested` operator's complexity/ops proportional to `arrAttestors.length`, mirroring `in data feed`/`in merkle` (e.g., `complexity += arrAttestors.length - 1`), so the existing `MAX_COMPLEXITY`/`MAX_OPS` limits actually bound the size of the attestor list. Additionally, consider adding an explicit maximum length cap for `arrAttestors` (similar to caps used elsewhere, e.g., `MAX_DATA_FEED_NAME_LENGTH`) independent of complexity accounting, to make the bound explicit and robust against future complexity-formula changes.

### Proof of Concept
1. Attacker composes an asset definition (or address definition, or signed-message authentifier condition) whose `transfer_condition` (or definition) is:
   `['attested', ['this address', [<addr_1>, <addr_2>, ..., <addr_N>]]]` with `N` in the thousands, all syntactically valid base32 addresses.
2. `validateDefinition`'s `case 'attested'` (definition.js:370-388) only loops once over the array to validate each address is well-formed and adds a constant `complexity++`/`count_ops++`, so the definition passes `MAX_COMPLEXITY`/`MAX_OPS` checks regardless of `N`.
3. The asset is confirmed on the DAG.
4. Any user (attacker or victim) who subsequently issues/transfers this asset triggers `Definition.evaluateAssetCondition` → `validateAuthentifiers`'s `case 'attested'` (definition.js:904-915), which calls `storage.filterAttestedAddresses` (storage.js:1959-1974) building a query with `attestor_address IN(<N addresses>)` plus a correlated subquery — cost scales with `N` and is repeated for every future transfer/issue of the asset, on every validating node.
