### Title
Single Non-Attested/Restricted Output Address Blocks an Entire Multi-Recipient AA Payment, Freezing Rewards for All Other Recipients - (File: validation.js, aa_composer.js)

### Summary
Ocore assets can be defined with `spender_attested`, `transfer_condition`, or `is_transferrable` restrictions that gate who may receive an asset. When an Autonomous Agent (AA) distributes rewards to multiple recipients by batching several outputs into one `payment` message (which is atomically validated as a whole), a single recipient address that fails the attestation/condition check causes the entire message — and thus the entire response unit — to fail validation and bounce. This is directly analogous to the USDC blacklist issue: one non-compliant address in a batch of payees blocks funds from reaching every other legitimate recipient bundled in the same unit.

### Finding Description
Payment outputs for a restricted asset are validated as a single atomic set in `validatePaymentInputsAndOutputs`. If the asset is `spender_attested`, every address in `arrOutputAddresses` must be attested, or the whole payment fails: [1](#0-0) 

Similarly, `transfer_condition`/`issue_condition` are evaluated once for the aggregate set of addresses/inputs, and any failure rejects the entire payment message: [2](#0-1) 

And a non-transferrable asset (`is_transferrable: false`) constrains the whole set of input/output addresses together, not per-output: [3](#0-2) 

On the AA side, when `sendUnit` in `aa_composer.js` builds a payment message with multiple outputs (e.g., a reward-distribution AA looping over many recipients into one `payment` message with an `asset`), the whole unit is composed and validated together via `validateAndSaveUnit`. Any failure — including "some output addresses are not attested" or "transfer or issue condition not satisfied" — is caught and the entire trigger bounces, discarding all outputs in that unit, not just the offending one: [4](#0-3) [5](#0-4) 

The asset-level restrictions themselves (`spender_attested`, `transfer_condition`, `issue_condition`, `is_transferrable`) are defined and validated per `validateAssetDefinition`, and are legitimate, definer-controlled features — any asset issuer (including an AA issuing its own reward asset) can configure them: [6](#0-5) 

Because ocore requires all outputs of a single `payment` message (and, by extension, the entire authored unit) to validate atomically, there is no way to "skip" a single non-compliant recipient the way per-transfer ERC20 calls could revert individually while others succeed. A single unattested/blacklisted-analog address in the recipient set is sufficient to void the whole distribution unit.

### Impact Explanation
An AA that distributes an asset-based reward (e.g., a custom reward token, or an asset with `spender_attested`/`transfer_condition` set by its definer) to many recipients in one payment message is vulnerable to a denial-of-service: if any single recipient in that batch is not attested (or otherwise fails the transfer condition), none of the recipients in that unit receive their funds — the entire trigger response bounces. This freezes AA funds/rewards for all legitimate users bundled with the non-compliant one, satisfying the "AA fund loss or freezing" impact class. If the AA logic deterministically re-attempts to pay the same recipient set on subsequent triggers, the AA can become permanently stuck distributing to that group.

### Likelihood Explanation
This requires an asset used by the AA (issued either by the AA itself or by a third party) to have `spender_attested`, `transfer_condition`, or `is_transferrable` restrictions, and an AA design that batches multiple recipients into one payment message (a common gas/size-optimization pattern, e.g. loop-based reward distribution). Since asset attestor lists and transfer conditions can change over time (attestors revoke attestation, oracle-driven conditions evaluate false), it is plausible in production reward-distribution AAs, particularly once they interact with externally-defined, permissioned assets.

### Recommendation
- When an AA pays out a restricted asset to multiple recipients, avoid bundling arbitrary user-supplied/external recipients into a single atomic `payment` message; instead issue one `payment` message per recipient (or per small, independently-retriable batch) so that a failure for one recipient does not block others.
- For assets with `spender_attested`/`transfer_condition`, pre-filter/validate recipient eligibility in AA formula logic (e.g., via `attested`/`in data feed` checks) before including them in outputs, and skip/queue non-eligible recipients rather than letting them cause a hard bounce of the whole unit.
- Document for AA authors that atomic validation of `payment.outputs` in `validatePaymentInputsAndOutputs` (validation.js) means restricted-asset payouts should not be batched with untrusted third-party addresses.

### Proof of Concept
1. Define an asset `A` (via `app: 'asset'`) with `spender_attested: true` and an attestor `X`, as validated by `validateAssetDefinition` (validation.js:2725-2750).
2. Deploy a reward-distribution AA that, on trigger, builds a single `payment` message for asset `A` with outputs to recipients `[R1, R2, ..., Rn]`, following the pattern used in `sendUnit`/`completePaymentPayload` (aa_composer.js).
3. Attestor `X` attests `R1..Rn-1` but never attests `Rn` (or revokes attestation for `Rn`).
4. Trigger the AA. During validation, `storage.filterAttestedAddresses` finds `arrAttestedOutputAddresses.length !== arrOutputAddresses.length` because `Rn` is missing (validation.js:2630-2641), causing `validatePaymentInputsAndOutputs` to return `"some output addresses are not attested"`.
5. `validateAndSaveUnit` fails, `aa_composer.js` calls `bounce(err)` (aa_composer.js:1405-1411), and the whole response unit — including the payouts intended for `R1..Rn-1` — is discarded/bounced, denying rewards to every recipient bundled in that unit because of the single non-compliant address `Rn`.
