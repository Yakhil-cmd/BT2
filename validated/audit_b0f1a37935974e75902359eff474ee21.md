### Title
Tokens received by the controller during `flash_position` that are not declared in `collaterals`/`refund_assets` are permanently locked with no recovery path - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`flash_position` measures and settles callback-delivered tokens exactly once, at callback return, and only for token addresses the caller pre-declared in `collaterals` or `refund_assets`. Any other token the receiver transfers to the controller during `execute_flash_position` — or any token that cannot be declared because it is not a listed asset in the debt hub and account spoke — sits on the controller's balance forever. No sweep, rescue, or later-attribution entrypoint exists, mirroring the "one-time generation hook that can never be re-run" bug class.

### Finding Description
The flow is:

1. `process_flash_position` snapshots balances only for the declared `collaterals` assets and `refund_assets` before invoking the receiver (`flash_position.rs:120-130`).
2. After the callback, `collect_collateral_deposits` computes `balance_delta_since` only over `collaterals` and deposits those deltas as supply (`flash_position.rs:145-146`, `325-352`).
3. `refund_listed_assets` computes deltas only over `refund_assets` and transfers them back to `caller` (`flash_position.rs:148`, `372-384`).

There is no third pass over arbitrary assets and no controller-side sweep entrypoint; `docs/reference/endpoints.md` states this explicitly: "Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint."

Worse, `validate_refund_assets` requires every refund asset to be a listed, active asset in `(debt.hub_id, account.spoke_id)` and disjoint from `collaterals` (`flash_position.rs:240-255`), and `validate_collaterals` requires `require_can_supply` for each collateral (`flash_position.rs:202`). A callback that produces a token not listed in that spoke/hub — e.g., an arbitrary SAC or a token listed only under a different hub — cannot be declared at all, so its recovery is impossible even in principle.

This is directly reachable by any address: `flash_position` requires only caller auth plus owner/delegate auth on `account_id` (or `account_id = 0` for a fresh account), a flashloanable debt market, and a Wasm receiver — the caller's own receiver is allowed (`flash_position.rs:69-101`).

### Impact Explanation
Permanent freezing of funds. Tokens stranded on the controller are not credited to any account, not counted in pool accounting, and cannot be withdrawn by anyone. While the naive reading is "caller shoots own foot," receiver contracts are routinely shared infrastructure: a leverage/vault/router contract that calls `flash_position` on behalf of users and forwards third-party tokens (router outputs in an intermediate asset, LP redemptions, rewards) can lock depositors' funds permanently with a single omitted or non-declarable asset.

### Likelihood Explanation
Medium. The receiver must send a token that is neither declared nor declarable. This happens naturally whenever a callback route produces an unexpected intermediate asset, a token listed under a different hub than the debt hub (same token address can't be declared as `refund_assets` since `validate_refund_assets` checks the debt `hub_id` and the account's `spoke_id` listing), or an unlisted reward token. Because the unlisted-token case cannot be declared even proactively, any receiver touching such assets guarantees the loss.

### Recommendation
Add a recovery path analogous to the report's recommendation: either (a) a permissionless `sweep`/`rescue` entrypoint that returns positive controller balance deltas for tokens with no accounting claim back to a designated address (e.g., the receiver or account owner), or (b) track the set of tokens touched during the callback and refund any positive residual delta to `caller` after `refund_listed_assets`, so undeclared receipts are not stranded.

### Proof of Concept
1. Deploy a Wasm receiver `R` whose `execute_flash_position` sends an unlisted token `X` (or a token listed only in another hub) to the controller in addition to delivering the declared collateral.
2. Call `Controller::flash_position(caller, 0, spoke_id, PositionMode::Multiply, debt=(hub, USDC), amount, receiver=R, data, collaterals=[(hub,XLM, min)], refund_assets=[])`.
3. The call succeeds: `X` is not in `collaterals` (fails `require_can_supply`) nor declarable in `refund_assets` (fails `require_listed_active_config`), so `collect_collateral_deposits`/`refund_listed_assets` never inspect it.
4. The controller's `X` balance increased and there is no entrypoint (`supply`/`withdraw`/`claim_revenue`/`recapitalize`/any admin path) that reads controller token balances to release it — the tokens remain locked indefinitely.
