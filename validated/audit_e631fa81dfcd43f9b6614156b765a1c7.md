### Title
Cross-tenant status/commit forgery via webhook signature not bound to the repository it targets - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) is used to validate an inbound webhook's HMAC signature based on `repository_owner`, a value read straight out of the *unauthenticated* JSON body (`repository.owner.login` or `organization.login`). Once the signature check passes, the payload is handed to the event handler, which resolves the actual target of the write using a *different, uncorrelated* field of the same body: `repository.full_name` (or, in `StatusHandler`, no repository scoping at all — only a global `sha` lookup). Nothing ties "the organization whose secret produced a valid signature" to "the repository/commit that is actually mutated." This is the same class of bug as the report: a field acted on is never covered by the verification that is supposed to authenticate it.

### Finding Description
- `verify_signature` computes `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature`, where `repository_owner` comes from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`: [1](#0-0) [2](#0-1) 
- Signature verification itself is a plain HMAC compare against the `webhook_secret` configured for whichever organization key was extracted: [3](#0-2) 
- In a multi-organization Shipit deployment, each GitHub organization onboarded gets its own `webhook_secret`, configured under its own top-level key in `github:`: [4](#0-3) 
This secret is set by whoever creates and installs that org's GitHub App — i.e., by the organization owner themselves, not by the Shipit operator. An org owner onboarding their own tenant is not a "privileged Shipit user"; they only ever gain legitimate knowledge of their *own* org's `webhook_secret`.

- Once `verify_signature` passes, `WebhooksController#create` dispatches the raw payload to handlers with no further binding of "the org that signed this" to "the repository/commit being written": [5](#0-4) 
- The base `Handler` resolves the *target* stack/repository from a completely independent field, `repository.full_name`, which is never compared to the `repository_owner` used above for signature selection: [6](#0-5) 
- Worse, `StatusHandler` doesn't even use that field: it matches commits **globally by `sha`** across the entire Shipit instance, with no repository/stack scoping whatsoever: [7](#0-6) 

The broken equality is: `organization_that_signed(payload) == organization_that_owns(target_repository_or_commit)`. The signature only proves the first side; the handlers act on the second side using unrelated, attacker-controlled fields, so the two are never actually checked to match.

### Impact Explanation
An attacker who legitimately controls one onboarded, low-trust GitHub organization (and thus legitimately knows that organization's own `webhook_secret`, exactly as any org admin following `docs/setup.md` would) can:
1. Produce a validly HMAC-signed webhook whose `repository.owner.login`/`organization.login` is their own org (so `verify_signature` passes using their own secret), while setting `repository.full_name`, `sha`, `state`, and `context` to arbitrary values belonging to a *different* organization/stack tracked by the same Shipit instance.
2. Because `StatusHandler` looks up commits purely by `sha` with no repository check, this forged, validly-signed `status` event can mark any commit in the entire instance (belonging to any other tenant) as `state: "success"` via `Commit#create_status_from_github!`.
3. Commit/CI statuses are exactly what Shipit's deploy-safety gating (`commit_status`/`deployable_status` checks) relies on to decide whether a commit is safe to deploy, so this can be used to force an unrelated organization's unreviewed/malicious commit to appear "green" and eligible for deploy — an unauthorized-deploy-enabling cross-repository write, satisfying the Critical bar ("cross-repository writes" / "an unauthorized deploy").
4. Even without the `StatusHandler` global lookup, the more general issue (`Handler#repository_name` using `repository.full_name` uncorrelated with the org used for signing) lets a signer for org A drive `PushHandler`/`CheckSuiteHandler` actions (e.g., `stack.sync_github`) against org B's stacks.

### Likelihood Explanation
This requires no privileged Shipit credential, GitHub App private key, or `ApiClients` token — only the ordinary, self-service ability to register/administer one GitHub organization's own GitHub App on a multi-org Shipit instance, which is the documented onboarding path. Any such tenant can craft an arbitrary JSON body and a matching HMAC using its own known secret; there is no additional control preventing the mismatch between the signing organization and the acted-upon repository/commit.

### Recommendation
Bind signature verification to the same value used for authorization of the write:
- After verifying the signature, re-derive the organization owning the *target* repository (`repository.full_name`) from Shipit's own `Repository`/`Stack` records (not from the payload) and reject the webhook if it does not match the organization whose secret validated the signature.
- In `StatusHandler` (and any other handler), scope commit/status lookups to the repository declared in the payload's `repository.full_name`, cross-checked against the verified organization, instead of a global `Commit.where(sha:)` lookup.
- Consider verifying webhook signatures per-installation using the GitHub App's installation ID present in modern webhook deliveries rather than trusting an org name pulled from the JSON body pre-verification.

### Proof of Concept
1. Configure Shipit with two organizations, `tenant-a` and `tenant-b`, each with its own GitHub App/`webhook_secret`, per the documented multi-org format in `docs/setup.md` (lines 184-209).
2. As the owner of `tenant-a` (attacker-controlled, low-trust org), craft a `status` event body:
```json
{
  "sha": "<sha of a commit belonging to a tenant-b stack>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "tenant-a" }, "full_name": "tenant-a/attacker-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(tenant-a's webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `tenant-a`, validates the signature against `tenant-a`'s own `webhook_secret` — passes, since attacker legitimately knows this secret. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` globally and calls `create_status_from_github!`, marking tenant-b's commit as `success` regardless of the `repository` field in the payload. [7](#0-6) 
6. Tenant-b's stack now reflects a forged green CI status on a commit the attacker never had access to, potentially unlocking an unauthorized deploy on tenant-b's stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
