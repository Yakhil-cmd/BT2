### Title
Cross-org signature verification split lets a no-secret-org webhook mutate another org's review stack - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to validate against using `params.dig('repository', 'owner', 'login')`, while `LabeledHandler` resolves the actual `Shipit::Repository`/stack independently from `params.repository.full_name`. Because `GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as "always verified", an attacker can name a multi-tenant-configured Shipit instance's no-secret organization in `repository.owner.login` (bypassing signature checks entirely) while pointing `repository.full_name` at a different, secret-protected org's repository, causing the handler to archive/unarchive that org's review stack.

### Finding Description
The broken binding: the equality that must hold is `org_used_for_signature_verification (params.repository.owner.login) == org_that_owns_the_mutated_repository (params.repository.full_name.split('/').first)`. Nothing in the code enforces this.

- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-30` computes `repository_owner` from `params.dig('repository','owner','login')` (or `organization.login` as fallback) at line 61, and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) has `return true unless webhook_secret` — if the selected org has no `webhook_secret` configured, **any** signature (even absent/garbage) passes verification unconditionally.
- After verification, `WebhooksController#create` dispatches the raw, attacker-controlled `params` to `Shipit::Webhooks.for_event(event)` handlers, independent of which org "verified" the request.
- `LabeledHandler#repository` (`app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb:65-68`) resolves the target repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — a completely separate field from `repository.owner.login`, with no cross-check.
- `LabeledHandler#handle` then calls `stack.archive!` / `stack.unarchive!` on the resolved `ReviewStackAdapter` for that repository (lines 49-57), based on the label vs. `repository.provisioning_behavior_*`.

Exploit: In a Shipit deployment configured with multiple GitHub orgs (`Shipit.github_organizations`), if one org (`evil-org`, attacker-controlled or simply misconfigured/unconfigured) has no `webhook_secret` set, an attacker POSTs to `/webhooks` with header `X-Github-Event: pull_request` and a JSON body where `repository.owner.login = "evil-org"` (so `verify_signature` picks the org with no secret and always passes) but `repository.full_name = "victim-org/protected-repo"` (so `LabeledHandler` looks up and mutates the real, secret-protected `victim-org` repository's review stack). No valid `X-Hub-Signature` for `victim-org`'s secret is required.

Existing guards that fail to prevent this: `drop_unhandled_event` only checks the event type is registered, not payload consistency; `ExplicitParameters` schema in `LabeledHandler.params` only validates presence/type of fields, not that `repository.full_name`'s org matches `repository.owner.login`; `verify_signature`'s `rescue GithubOrganizationUnknown` only guards against totally unknown orgs, not against orgs with no secret configured.

### Impact Explanation
An unauthenticated attacker can force `stack.archive!`/`stack.unarchive!` (which trigger provisioning/deprovisioning side effects for review-stack environments) on a review stack belonging to an organization/repository the attacker does not control and for which they never satisfied the HMAC signature check. This is a payload for one repository (nominally `evil-org`) mutating another repository's/org's stack state — matching the Critical "payload for one repository mutating another's stack" category. Repeatable against any repository with `review_stacks_enabled`, as long as some org in the deployment's `secrets.github` config lacks a `webhook_secret`.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured for the multi-org github secrets schema (`Shipit.github_organizations` returning multiple orgs, i.e. `secrets.github` keyed by org rather than the legacy single-app schema), and (2) at least one configured org lacking `webhook_secret`. Under the legacy single-app config (`github_default_organization` nil), `Shipit.github(organization: repository_owner)` ignores the passed-in org and always uses the single top-level secret, so this specific bypass would not apply. Given multi-org configuration is an explicitly supported and documented feature (`docs/setup.md`, `TOP_LEVEL_GH_KEYS`), and operators may reasonably leave `webhook_secret` unset for a low-risk/staging org, this is a realistic misconfiguration rather than a purely theoretical one. Attacker cost is a single crafted HTTP POST, fully repeatable.

### Recommendation
Enforce that the organization used to verify the webhook signature matches the organization actually owning the resource(s) mutated by the handler: derive `repository_owner` and validate that `params.repository.full_name.split('/').first.casecmp(repository_owner) == 0` before verification, and reject if they don't. Additionally, treat a missing `webhook_secret` for a *configured* multi-org entry as a hard configuration error (fail closed) rather than "always verified" in `GitHubApp#verify_webhook_signature`, at least for the multi-org schema.

### Proof of Concept

1. Configure test secrets with two orgs: `secrets.github = { "evil-org" => { app_id:..., installation_id:..., private_key:... } (no webhook_secret), "victim-org" => { ..., webhook_secret: "victims-secret" } }`.
2. Create `Shipit::Repository.create!(owner: "victim-org", name: "protected-repo", review_stacks_enabled: true, provisioning_behavior: "allow_with_label")` and an associated `Shipit::ReviewStack` for a PR branch, initially unarchived.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and JSON body: `{"action":"labeled","number":1,"pull_request":{...,"state":"open","head":{"ref":"pr-branch","sha":"..."},"labels":[]},"repository":{"owner":{"login":"evil-org"},"full_name":"victim-org/protected-repo"},"sender":{"login":"attacker"}}`.
4. Assert response is `200 OK` (not `422`), confirming `verify_signature` passed via `evil-org`'s missing secret — i.e. assert `repository_owner (from payload) == "evil-org"` while `full_name.split('/').first == "victim-org"` (the two sides of the equality diverge).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
