### Title
Session fixation on GitHub OAuth callback due to missing `reset_session` - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`GithubAuthenticationController#callback` binds a successfully-authenticated GitHub identity to `session[:user_id]` without first calling `reset_session`, unlike `#logout` which explicitly resets the session. This breaks the equality that should hold between "the session ID a user's browser is currently carrying" and "the session ID that becomes authenticated as a specific `User`."

### Finding Description
The callback action performs the OAuth exchange and then writes the resulting `User` id directly into the existing session store, without rotating the session identifier: [1](#0-0) 

Contrast this with `#logout`, which does call `reset_session`: [2](#0-1) 

`Shipit::Authentication#force_github_authentication` and `#current_user` subsequently trust `session[:user_id]` as the sole binding between the browser session and the `User` record for all authorization decisions (e.g. `current_user.authorized?` against `Shipit.github_teams`): [3](#0-2) 

Because the session ID is never rotated at authentication time, if an attacker can get a victim's browser to carry a session ID known to the attacker (a classic session-fixation precondition, e.g. via a subdomain cookie-setting mechanism or any mechanism that lets an ID be pre-established before login — not requiring any Shipit credential, token, or privileged account), then once the victim completes the real GitHub OAuth login, that same session ID becomes bound to the victim's authenticated `User`. The attacker, already holding that session ID, then inherits the victim's authenticated session and its full `Shipit.github_teams` authorization, without ever needing the victim's GitHub credentials.

### Impact Explanation
This breaks the "GitHub identity vs. `User` bound to the session" trust binding described in scope: the equality "session ID == identity that completed OAuth" fails because the session ID is not rotated post-authentication. Successful exploitation grants unauthenticated escalation into the authenticated user's `Shipit.github_teams` authorization (matching the listed High-impact class), potentially allowing an attacker to reach any Shipit functionality the victim can (deploys, rollbacks, merges), which can cascade to Critical impact (unauthorized deploy/rollback/merge).

### Likelihood Explanation
Likelihood depends entirely on the attacker's ability to fix a session ID in the victim's browser before the OAuth completes — this is a standard external precondition for session-fixation attacks and does not require any Shipit-specific secret, token, or privileged account. The application-side root cause (missing `reset_session` in `callback`, contrasted with its presence in `logout`) is concretely present in the code with no mitigating control (no session ID rotation, no CSRF `state`/nonce binding shown in this controller).

### Recommendation
Call `reset_session` (or otherwise rotate the session identifier) in `GithubAuthenticationController#callback` before setting `session[:user_id]`, mirroring the pattern already used in `#logout`.

### Proof of Concept
1. Attacker establishes/knows a session ID that will be used by the victim's browser (external precondition, e.g. cross-subdomain cookie write).
2. Victim visits Shipit and completes GitHub OAuth login via `GithubAuthenticationController#callback`.
3. Because `callback` never calls `reset_session`, the pre-existing (attacker-known) session ID is the one that gets `session[:user_id] = sign_in_github(auth)` written into it.
4. Attacker replays the same session ID/cookie and is now treated as the fully authenticated victim by `Shipit::Authentication#current_user`, inheriting the victim's `Shipit.github_teams` authorization.

**Note on scope limitations:** I was unable to fully verify within the in-scope engine code whether any CSRF/OAuth `state` parameter validation exists elsewhere in the omniauth middleware configuration (typically outside `app/**`), which could partially mitigate this. I could not find such validation in the reviewed controller code. Other candidate analogs I investigated (webhook organization-vs-repository binding in `WebhooksController#verify_signature` vs `Handlers::Handler#repository_name`, and `ApiClient` stack-scoping) were excluded because exploiting them required possessing a `webhook_secret` or `ApiClient` token, both explicitly out of scope per the rules.

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
