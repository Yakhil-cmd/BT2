### Title
Webhook signature verified against `repository.owner.login`, but event handlers dispatch on the unauthenticated `repository.full_name` — allows cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret used to validate the `X-Hub-Signature` HMAC based on `repository.owner.login` (falling back to `organization.login`) taken from the JSON payload. However, once the signature is accepted, every event handler (`PushHandler`, `StatusHandler`, PR handlers, etc.) resolves the actual `Stack`/`Repository`/`Commit` to act on using a *different* payload field — `repository.full_name` (or bare `sha` in `StatusHandler`) — which is never covered by the signature check binding. In a multi-organization Shipit deployment, an attacker who legitimately controls one configured GitHub organization (and thus knows its `webhook_secret`) can sign a payload whose `repository.owner.login` matches their own org (so it passes `verify_signature`) while setting `repository.full_name` to point at a repository belonging to a *different* configured organization/stack.

**Binding broken (as an equality):** the engine assumes
`organization authenticated by signature (repository.owner.login / organization.login) == organization/repository actually written (repository.full_name)`.
The verification step establishes the left side; every handler acts on the right side; nothing enforces they are equal.

**Before attacker's request:** In a single-org deployment this is harmless because there's only one `webhook_secret` and one possible `repository_owner`. **In a multi-org deployment** (the officially documented configuration in `docs/setup.md`), each organization has its own distinct `webhook_secret`. Org A's secret authenticates only messages claiming `repository.owner.login == "OrgA"`, but says nothing about `full_name`.

**After attacker's request:** An attacker who is an authorized member/admin of their own onboarded GitHub org "OrgA" (and thus can trigger or replay a correctly-signed webhook from OrgA, or simply knows OrgA's `webhook_secret` because they administer that org's GitHub App) can POST a forged JSON body to `/webhooks` with:
- `X-Hub-Signature` computed with OrgA's `webhook_secret` over the exact raw body sent,
- `repository.owner.login = "OrgA"` (so `verify_signature` passes against OrgA's secret),
- `repository.full_name = "OrgB/victim-repo"` (a repository tracked under a completely different, unrelated organization/stack).

This satisfies `verify_signature` while causing handlers to act on OrgB's stack: e.g. a forged `push` event queues `GithubSyncJob` for OrgB's stack with an attacker-chosen `expected_head_sha`, or a forged `status` event injects a fabricated commit status (`state: 'success'`) onto any commit sha the attacker guesses/knows in OrgB's repo, which can influence CI-gated deploy/merge decisions (`MergeRequest#all_status_checks_passed?`, `Stack#deployment_checks_passed?`), all without ever possessing OrgB's actual `webhook_secret`.

### Impact Explanation
This crosses an authentication boundary the engine intends to keep per-organization: possession of Org A's webhook secret should only allow injecting events for Org A's repositories, not for repositories belonging to other onboarded organizations. Exploiting it lets an attacker forge/influence commit statuses and push-triggered syncs for a victim organization's stack, which can be used to manipulate merge-queue gating (`ci_missing`/`ci_failing` checks) and trigger unwanted syncs — a cross-repository write influence achieved purely by signing with a different, attacker-controlled organization's secret. This matches the High-severity class "escalation into `Shipit.github_teams` authorization" adjacent territory and can contribute to an unauthorized deploy/merge outcome when combined with fabricated success statuses satisfying merge-queue CI requirements.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (explicitly documented and supported), and (2) the attacker to control/administer one of the onboarded GitHub organizations (and thus its webhook secret) — a scenario the engine's own trust model assumes should be isolated per-org. No compromise of the victim org's credentials, no Shipit session, and no `ApiClient` token are required — only the ability to send an HTTP POST to the public `/webhooks` endpoint with a validly-signed-for-OrgA body. This is realistic in shared/consolidated Shipit instances serving multiple orgs/teams, which is the exact use case the multi-org config exists for.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after determining which organization's secret verified the signature, enforce that every repository/organization field referenced by the dispatched handler (`repository.full_name`, `repository.owner.login`, `organization.login`) actually belongs to that same verified organization before invoking handlers — e.g., reject the webhook if `repository.full_name.split('/').first.downcase != repository_owner.downcase`. Alternatively, pass the verified organization into `Handler#stacks`/`Repository.from_github_repo_name` lookups and require an exact match, and scope `StatusHandler`'s `Commit.where(sha:)` lookup to commits belonging to stacks under the verified organization.

### Proof of Concept
1. Configure Shipit with two GitHub orgs per `docs/setup.md` multi-org schema: `OrgA` (attacker-administered) and `OrgB` (victim), each with distinct `webhook_secret`s, both with stacks/repositories tracked in Shipit.
2. As an administrator of OrgA's GitHub App, craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, raw_body)>`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully against OrgA's secret (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `push_handler.rb:12-17`) and enqueues `GithubSyncJob` for OrgB's stack — despite the request never being signed by OrgB's secret.

**Uncertainty:** I could not find any additional cross-check code (e.g., in `Handler` base class or a before-dispatch callback) that ties the verified organization to the handler's repository resolution; based on the code read, no such check exists, but I was not able to inspect every handler file (only a subset were retrieved) to confirm none of them independently re-validate the organization.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
