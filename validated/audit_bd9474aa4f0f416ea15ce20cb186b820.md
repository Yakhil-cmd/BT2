### Title
Cross-organization webhook forgery: webhook signature is verified against the organization in `repository.owner.login`, but stack/repository lookup trusts the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit can be configured (per `docs/setup.md` and `config/secrets.development.example.yml`) to serve **multiple independent GitHub organizations** from a single instance, each with its own `app_id`, `installation_id` and, crucially, its own `webhook_secret`. `WebhooksController#verify_signature` selects which organization's secret to validate the inbound webhook against using `repository.owner.login` (or `organization.login`) taken from the JSON body, but every event `Handler` (`PushHandler`, the `PullRequest::*Handler`s, etc.) resolves the actual `Stack`/`Repository` to mutate using a completely different field of the same body: `repository.full_name`. Nothing ties these two fields together, so a payload that is legitimately signed by Organization B's own webhook secret can still carry `repository.full_name` pointing at Organization A's repository/stack, and the handler will happily act on Organization A's data.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to check the HMAC against based on `repository_owner`: [1](#0-0) [2](#0-1) 

This only proves the raw body was signed by the secret belonging to the organization named in `repository.owner.login`/`organization.login`. It does **not** constrain which repository the payload is allowed to reference.

Every webhook `Handler` base class instead resolves the target `Stack` purely from `repository.full_name`, with no relation at all to the organization that was used for signature verification: [3](#0-2) 

`PushHandler`, which drives `stack.sync_github`, consumes exactly that `stacks` scope: [4](#0-3) 

The pull-request handlers do the same, independently re-deriving the repository from `full_name`: [5](#0-4) 

Because Shipit's own documentation shows this instance-wide, multi-organization configuration as a supported deployment model (separate `app_id`/`installation_id`/`webhook_secret`/`oauth` per org key under `github:`), an operator who legitimately administers *their own* GitHub App/organization on that shared Shipit instance can sign an arbitrary JSON body with their own, genuinely-possessed `webhook_secret`, while forging the `repository.owner.login` to match their own org (so verification passes) and forging `repository.full_name` to name a *different* tenant's repository. The signature check (`repository.owner.login` → secret lookup) and the object actually written (`repository.full_name` → `Stack`) are never required to be equal, breaking the intended binding:

`organization whose secret authenticated the request == repository/stack that gets written`

### Impact Explanation
An attacker who is a legitimate administrator of one configured GitHub organization/App on a shared, multi-tenant Shipit deployment can:
- Force `PushHandler` to call `stack.sync_github(expected_head_sha: ...)` on a foreign organization's `Stack`, driving unauthorized synchronization/build state changes for a repository they do not own.
- Trigger the pull-request handlers (`OpenedHandler`, `ReopenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) against a foreign `Stack`'s `review_stacks`, causing creation/close/unarchive/label mutation of review stacks belonging to another organization's repository.

This is a cross-repository/cross-tenant write performed by an entity that only legitimately controls its own organization's webhook secret — matching the Critical severity bucket ("cross-repository writes").

### Likelihood Explanation
This requires only that (a) the Shipit instance is configured for more than one GitHub organization (a documented, supported setup) and (b) the attacker administers one of those organizations' own GitHub Apps, which lets them freely craft and correctly HMAC-sign arbitrary webhook bodies with their own secret. No compromise of another party's secret, session, or API token is required, so likelihood is high in any genuinely multi-org deployment.

### Recommendation
After signature verification succeeds for organization `O`, require that `repository.owner.login`/`organization.login` in the payload matches the actual owner of the `Repository`/`Stack` resolved via `repository.full_name` before dispatching to any handler (or, more simply, only resolve stacks/repositories whose stored `owner` equals the verified `repository_owner`). This restores the binding between "who signed the request" and "what gets written."

### Proof of Concept
1. Deploy Shipit configured for two organizations, e.g.:
```yaml
github:
  org-a:
    webhook_secret: secretA
    ...
  org-b:
    webhook_secret: secretB
    ...
```
2. Org B's administrator (attacker) knows `secretB` legitimately.
3. Attacker builds a `push` webhook payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-b" },
    "full_name": "org-a/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(secretB, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "org-b")`, whose `verify_webhook_signature` succeeds because the body was indeed signed with `secretB`.
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("org-a/victim-repo")`, finds Org A's stack, and calls `stack.sync_github(expected_head_sha: ...)` — mutating Org A's data using a signature authorized only for Org B.

Unable to fully trace `Shipit.github(organization:)`/`Shipit.github_teams` implementation details in `lib/shipit.rb` due to remaining tool-call limits; this does not affect the core finding, which rests entirely on `webhooks_controller.rb` and `webhooks/handlers/handler.rb`.
