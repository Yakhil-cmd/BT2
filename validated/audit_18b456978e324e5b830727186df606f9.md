### Title
Webhook signature verified against attacker-chosen organization while payload's `repository.full_name` (untrusted) is used to select the target repository/stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub organization's `webhook_secret` to validate the HMAC signature against by reading an untrusted field straight out of the still-unverified JSON body (`repository.owner.login` / `organization.login`). Once the signature check passes, every webhook handler resolves the actual target repository/stack from a *different*, equally untrusted field of the same body (`repository.full_name`). These two fields are never checked for consistency, so a signature that is valid for organization A's secret authorizes a payload whose `repository.full_name` names a completely different repository/organization B.

### Finding Description
`WebhooksController` extracts the org used for signature verification directly from the raw, unauthenticated request body: [1](#0-0) 

`repository_owner` is derived purely from the payload: [2](#0-1) 

`verify_webhook_signature` then simply HMAC-verifies the *entire raw body* against the secret configured for whichever organization that field named: [3](#0-2) 

Because the secret is picked from data inside the very body being verified, anyone who legitimately possesses (or can obtain) the `webhook_secret` for *any one* GitHub organization configured on the Shipit instance can construct an arbitrary JSON body, set `repository.owner.login`/`organization.login` to that known organization, sign the whole body with that organization's secret, and the signature check will pass for that payload.

However, once `create` dispatches to the event handlers, the repository/stack that is actually acted upon is resolved from a separate field of the same attacker-authored payload: [4](#0-3) 

`repository.full_name` is never required to match `repository.owner.login`/`organization.login`. So a webhook signed with Organization A's secret can freely set `repository.full_name` to `"OrgB/some-other-repo"`, and `PushHandler`/`StatusHandler`/etc. will operate on Organization B's stacks: [5](#0-4) [6](#0-5) 

The equality that is supposed to hold — "organization whose secret authenticated the request" = "organization/repository the handlers act on" — is broken: verification binds to `payload.repository.owner.login`, while every mutation binds to `payload.repository.full_name`, and nothing forces these two independently-attacker-controlled strings to agree.

### Impact Explanation
An attacker who knows the `webhook_secret` for one organization hosted on a shared Shipit instance (a realistic, unprivileged-relative-to-other-orgs scenario for multi-tenant Shipit deployments configured via the multi-org `github:` block in `config/secrets.yml`) can forge `push`, `status`, `check_suite`, `pull_request`, and `membership` events for *any other organization's repositories/stacks* known to that Shipit instance. Depending on the handler this enables: forcing `GithubSyncJob`/`stack.sync_github` on an arbitrary stack (which can trigger continuous-deployment style syncs and downstream deploy triggering), injecting fabricated commit statuses, or manipulating team/membership records — all cross-organization, cross-repository actions performed using the app's own GitHub credentials and without any legitimate relationship to the targeted org. This matches the "cross-repository writes / unauthorized deploy" class of impact.

### Likelihood Explanation
Requires only knowledge of one organization's `webhook_secret` — a value that is explicitly optional (`webhook_secret: nil` is a supported no-signature configuration) and is scoped per-organization rather than per-installation-relationship, so it is not bound to the specific repository being targeted. Any party trusted with (or that leaks/obtains) a single org's webhook secret in a Shipit instance serving multiple GitHub organizations can exploit this without any additional privilege, session, or API token — matching the medium/likely scenario described in the analog report.

### Recommendation
Bind the signature verification target to the same field the handlers use to resolve the repository (`repository.full_name`), or, better, require that `repository.full_name`'s owner segment match the organization/secret used to verify the signature before dispatching to handlers. Alternatively, verify the signature against the actual `Repository`/`Stack` resolved by `repository.full_name` rather than a raw, independently-controlled `owner.login`/`organization.login` field.

### Proof of Concept
1. Shipit is configured with two GitHub organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per the multi-org config block documented in `config/secrets.development.example.yml`).
2. Attacker knows (or has legitimate access to) `org-a`'s `webhook_secret` only.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/target-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, body)>` and sends the request to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature against `org-a`'s secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/target-repo")`, and calls `stack.sync_github(expected_head_sha: ...)` on `org-b`'s stack — a stack the attacker has no legitimate relationship to — despite the request only ever being authenticated as belonging to `org-a`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
