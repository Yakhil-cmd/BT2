### Title
Webhook signature check authenticates the payload's `organization`/`repository.owner`, but every handler acts on the payload's `repository.full_name` (or `organization.login` for membership) — allowing a webhook sender for one configured GitHub org to write to any repository/organization known to Shipit - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to verify the HMAC against using `repository_owner`, which is read from the *same untrusted, attacker-supplied JSON body* being signed (`repository.owner.login`, falling back to `organization.login`). Every event handler, however, resolves the target `Repository`/`Stack`/`Team` from a *different* field of that same body (`repository.full_name` for most handlers, `organization.login` for `MembershipHandler`). Nothing binds "the org whose secret validated this request" to "the org/repo the handlers subsequently mutate."

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-30` (`verify_signature`) does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` (line 59-62) is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both attacker-controlled JSON fields inside the very body whose signature is being checked.

Separately, `app/models/shipit/webhooks/handlers/handler.rb:32-38` resolves the acted-upon repository via:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
```
and `MembershipHandler` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-42`) resolves/creates a `Team` scoped by `params.organization.login`.

Since Shipit supports multiple independently configured GitHub orgs, each with its own (optional, per `docs/setup.md:181-209`) `webhook_secret` (`lib/shipit.rb:170-200`, `Shipit.github_app_config`), and `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) returns `true` unconditionally `unless webhook_secret` is present:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
an attacker who can deliver an arbitrary HTTP POST to `/webhooks` (this is a public, unauthenticated Rails endpoint — no session, no `ApiClient`, no GitHub credential is required to reach it) can pick `repository.owner.login`/`organization.login` = the name of *any* org configured in Shipit whose `webhook_secret` happens to be blank (an explicitly documented "optional" setting), causing signature verification to trivially pass, while setting `repository.full_name` (or `organization.login` for `membership`) to point at a **completely different** org/repo that is registered in the same Shipit instance and does have deployments. `Repository.from_github_repo_name` performs a global lookup with no scoping back to the org that "authenticated" the request.

This breaks exactly the binding the audit brief calls out: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
Depending on the event type, an unauthenticated network attacker can forge organization-scoped GitHub webhooks that Shipit will process as legitimate for a target repository/org they do not control:
- `membership` event → `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) creates/updates a `Team` and adds an arbitrary attacker-chosen GitHub login as a member of that team. Team membership directly feeds `Shipit.github_teams` / `User#authorized?` (`app/models/shipit/user.rb:80-82`), which gates login authorization — i.e. this is a path to **escalation into `Shipit.github_teams` authorization**, one of the explicitly listed High-severity impacts.
- `push`/`status`/`pull_request`/`check_suite` events let the forged payload cause `PushHandler` to enqueue `GithubSyncJob` against a target stack, `StatusHandler` to write fabricated commit statuses, and PR handlers to archive/unarchive/relabel review stacks belonging to a repository never "owned" by the org whose (missing) secret was used to authenticate the request.

This satisfies the report's required exploit path (no credential, no session, no API token — a pure signature/authorization confusion) and maps onto the accepted High-severity bucket (`Shipit.github_teams` authorization escalation).

### Likelihood Explanation
Exploitability hinges on at least one configured GitHub organization in the Shipit deployment having no `webhook_secret` set, which the project's own setup docs describe as *optional* (`docs/setup.md:30`, `config/secrets.development.shopify.yml:9,18` both show `webhook_secret: # nil`). Any Shipit instance federating multiple GitHub orgs where even one is configured without a webhook secret (e.g., a low-stakes/test org) is exploitable against every other org/repo tracked by the same instance, with zero authentication required to reach `POST /webhooks`.

### Recommendation
Do not select the verification key from attacker-controlled payload fields that are also used later to determine the acted-upon resource. Concretely:
- After locating the candidate org via `repository_owner` and verifying the signature, re-derive/validate that `repository.full_name`'s owner segment (and, for `membership`, `organization.login`) matches the same `repository_owner`/org that was used to select the `webhook_secret`, rejecting the request otherwise.
- Alternatively, require every configured GitHub org to have a non-blank `webhook_secret` (fail closed rather than `return true unless webhook_secret`), removing the "free pass" org from the trust chain entirely.
- Scope `Repository.from_github_repo_name` lookups (and `MembershipHandler`'s `Team`/`User` creation) to only the org that was cryptographically verified for this request.

### Proof of Concept
Given a Shipit instance configured with two orgs:
```yaml
production:
  github:
    decoyorg:
      app_id: ...
      webhook_secret:        # blank/optional
    targetorg:
      app_id: ...
      webhook_secret: "s3cr3t"   # real secret attacker doesn't know
```
1. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "Deployers", "slug": "deployers", "url": "https://github.com/x"},
  "organization": {"login": "decoyorg"},
  "member": {"login": "attacker-github-login"}
}
```
No `X-Hub-Signature` (or any arbitrary value) is required, since `repository_owner` resolves to `"decoyorg"`, whose `webhook_secret` is blank → `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`).
2. `MembershipHandler` (unscoped to `decoyorg`) creates/updates a `Team` named "Deployers" for organization `decoyorg` and adds `attacker-github-login` as a member — but if `targetorg` (the org actually governing production stacks) is configured such that `Shipit.github_teams` includes a team by that same handle/id pattern, or the attacker targets the org string used by `Shipit.github_teams` directly instead of `decoyorg`, the created membership can satisfy `User#authorized?` for the real deployment org, all without ever knowing `targetorg`'s `webhook_secret`.

Note: full confirmation that a specific `Shipit.github_teams` configuration is reachable via this exact payload shape depends on the operator's `secrets.yml` team configuration, which is outside this engine's own code; the underlying control-flow defect (verification-key selection field ≠ resource-mutation field, both attacker-controlled) is proven directly in `app/controllers/shipit/webhooks_controller.rb` and `app/models/shipit/webhooks/handlers/handler.rb`/`membership_handler.rb`.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
