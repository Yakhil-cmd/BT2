### Title
Webhook signature is validated against `repository.owner.login`, but the repository whose `review_stacks` gets provisioned is resolved from the independently-controlled `repository.full_name`, letting any org with a valid webhook secret provision review stacks on another tenant's repository - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to check based on `params.dig('repository','owner','login')`, while `PullRequest::OpenedHandler#repository` resolves the target `Shipit::Repository` (and thus `review_stacks` scope) from `params.repository.full_name`. Since the raw JSON body is fully attacker-controlled (this is a raw HTTP POST, not something GitHub is guaranteed to produce faithfully once an attacker owns a legitimately-onboarded org's webhook secret), these two fields can be made inconsistent, letting a payload signed with org A's secret name a repository belonging to org B in `full_name`.

### Finding Description
The binding the code implicitly assumes is: `repository_owner (used to pick the HMAC secret) == owner(repository.full_name) (used to resolve the Repository record that gets provisioned)`.

- `WebhooksController#verify_signature` derives the signing organization purely from `params.dig('repository','owner','login')` and fetches that org's `GitHubApp` to verify `X-Hub-Signature`: [1](#0-0) [2](#0-1) 

- `OpenedHandler#repository` resolves the actual `Shipit::Repository` record (whose `review_stacks` scope is used for provisioning) purely from `params.repository.full_name`, split on `/`: [3](#0-2) [4](#0-3) 

- `provision?` then reads that resolved (victim) repository's `provisioning_behavior_prevent_with_label?` and the attacker-controlled PR labels to decide whether to provision: [5](#0-4) 

The `full_name` string and the `owner.login` sub-field are two independent JSON fields in the raw POST body; nothing in the `ExplicitParameters` schema (`opened_handler.rb` only requires `repository.full_name`) or in `verify_signature` cross-checks that `full_name`'s owner segment matches `repository.owner.login`. On a genuine GitHub-originated webhook these two would always agree, but the attacker here is defined by the rules as anyone able to `POST /webhooks` directly with an arbitrary raw body. If the attacker legitimately controls a tenant org ("attacker-org") already onboarded into Shipit's multi-org GitHub App config (so they know `attacker-org`'s `webhook_secret`), they can:

1. Set `repository.owner.login = "attacker-org"` so `verify_signature` selects attacker-org's `GitHubApp` and its known `webhook_secret`, computing a valid `X-Hub-Signature` for the crafted raw body.
2. Set `repository.full_name = "victim-org/victim-repo"` — a real repository in Shipit belonging to a different tenant, configured with `provisioning_behavior_prevent_with_label`.
3. Include no `labels` on the PR (or omit the provisioning label), and open the PR (`action: "opened"`) with an empty `assignees`/`labels` array satisfying the params schema.
4. `respond_to_pull_request_opened? -> provision?` evaluates `repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?` against the victim's repository config -> `true`.
5. `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` creates a review stack scoped to the **victim's** `Repository#review_stacks`.

Existing guards do not stop this: `verify_signature` only proves the raw body was signed by *some* known org's secret, not that the signing org matches the `repository.full_name` owner used later. `drop_unhandled_event` and the `ExplicitParameters` schema (`opened_handler.rb` params block) never validate `repository.owner.login` at all, so it isn't cross-checked anywhere in the pull-request handler pipeline.

### Impact Explanation
A payload signed by one tenant's webhook secret can create and eventually provision a `ReviewStack` for another tenant's repository, which subsequently runs deploy/provisioning `Command`/`PTY.spawn` logic (via `ReviewStackProvisioningQueue#provision` -> `stack.provision`) using the victim repository's own `GITHUB_TOKEN`/deploy configuration. This is a payload for one repository (or rather, one signing organization) mutating and driving execution on another organization's stack — matching the Critical category ("a payload for one repository mutating another's stack ... or an unauthorized deploy"). It is repeatable against any victim repository configured with `provisioning_behavior_prevent_with_label` (the default-safe posture, ironically the one meant to *restrict* provisioning) as long as the attacker can guess/know its `full_name`, which is often public information (public GitHub repo names).

### Likelihood Explanation
The attacker must possess a valid `webhook_secret` for at least one org already configured in Shipit's multi-org GitHub App setup (`Shipit.github(organization:)`), which is a realistic precondition in any multi-tenant Shipit deployment where multiple orgs are onboarded and the "attacker" is a legitimate admin/integrator of one of them but hostile toward another tenant. No GitHub session, API token, or Shipit credentials for the victim org are needed — only the attacker's own org webhook secret, and knowledge of the victim's `owner/repo` name. This is a single crafted HTTP POST, fully repeatable and requires no privilege escalation beyond already holding one tenant's webhook secret.

### Recommendation
In `WebhooksController#verify_signature` (or in each handler before resolving/using `repository.full_name`), assert that `params.dig('repository','owner','login')` matches the owner segment of `params.dig('repository','full_name')` before proceeding, rejecting the webhook (HTTP 422) on mismatch. Alternatively, derive the target `Repository` exclusively from the same `repository.owner.login`/`repository.name` fields that were used to select the verifying `GitHubApp`, rather than from a separately-controlled `full_name` string.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure two orgs in `Shipit.github_config` (or use the existing `secrets_double_github_app.yml` fixture) — `"attacker-org"` with a known `webhook_secret_a`, and `"victim-org"` with a different secret.
2. Create `victim_repository = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo", provisioning_behavior: "prevent_with_label", review_stacks_enabled: true)`.
3. Build a raw JSON body for a `pull_request` `opened` event where:
   - `payload["repository"]["full_name"] = "victim-org/victim-repo"`
   - `payload["repository"]["owner"]["login"] = "attacker-org"`
   - `payload["pull_request"]["labels"] = []` (no provisioning label)
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", webhook_secret_a, raw_body)`.
5. `post shipit.webhooks_path, params: raw_body, headers: { "X-Github-Event" => "pull_request", "X-Hub-Signature" => signature, "Content-Type" => "application/json" }`.
6. Assert response is `200`/`204` (accepted), and assert `victim_repository.review_stacks.exists?` (or a `Shipit::ReviewStack` scoped to `victim_repository`) is `true` — proving a review stack was created for `victim-org/victim-repo` from a payload signed only by `attacker-org`'s secret, satisfying the broken binding `repository_owner(signing) == owner(full_name)`.
