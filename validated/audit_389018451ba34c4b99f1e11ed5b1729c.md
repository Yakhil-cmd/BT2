`derived_string_struct_to_bytes_and_length` in [1](#0-0)  operates on a `Struct` whose field order is fixed by the Move type definition `struct DerivedStringSnapshot has store, drop { value: String, padding: vector<u8> }` [2](#0-1) . Move's runtime `Value`/`Struct` objects always conform to their declared type layout — the VM constructs these values via typed natives such as `bytes_and_width_to_derived_string_struct`, which packs `[value, padding]` in that fixed order [3](#0-2) , or via `create_derived_string`/`derive_string_concat` natives that go through the same packing helpers [4](#0-3) . There is no code path by which an unprivileged caller can inject a `Struct` with swapped field order at this layer — the layout is dictated by the compiled Move type, not by attacker-supplied bytes at this stage; even `is_derived_string_struct_layout` only validates the *type layout* shape (order of `String` then `vector<u8>`), consistent with the declared struct [5](#0-4) .

pub fn derived_string_struct_to_bytes_and_length(value: Struct) -> PartialVMResult<(Vec<u8>, u32)> {
    let mut fields = value.unpack()?.collect::<Vec<Value>>();
    if fields.len() != 2 {
        return Err(code_invariant_error(format!(
            "DerivedStringSnapshot has wrong number of fields: {:?}",
            fields.len()
        )));
    }
    let padding = fields.pop().unwrap().value_as::<Vec<u8>>()?;
    let value = fields.pop().unwrap();
    let string_bytes = string_to_bytes(value.value_as::<Struct>()?)?;
    let string_len = string_bytes.len();
    Ok((
        string_bytes,
        u32::try_from(bcs_size_of_byte_array(string_len) + bcs_size_of_byte_array(padding.len()))
            .map_err(|_| {
            code_invariant_error(format!(
                "DerivedStringSnapshot size exceeds u32: string_len: {string_len}, padding_len: {}",
                padding.len()
            ))
        })?,
    ))
}
