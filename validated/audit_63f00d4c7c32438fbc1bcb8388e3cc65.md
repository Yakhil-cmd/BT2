This confirms the vulnerability. `Api::CCMenuController#stack` at [1](#0-0)  uses `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!` method defined in the base controller at [2](#0-1) , which restricts lookups to `current_api_client.stack_id` when the client is stack-scoped. ### Title
Stack-scoped API token can read the state of any stack via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the base `#stack` helper to bypass the API-client stack scoping that every other API controller relies on, letting any token minted with `read:stack` permission and a single-stack scope fetch the CI/deploy status of every stack in the installation, not just the one it was authorized for.

### Finding Description
The intended trust boundary is: an `ApiClient` record optionally carries a `stack_id`; when set, `Api::BaseController#stacks` restricts all stack lookups to that one stack: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [5](#0-4) , and `#stack` builds on that scoped relation: `@stack ||= stacks.from_param!(params[:stack_id])` [6](#0-5) . This is exactly how stack-scoped tokens (e.g. the one auto-created by `CCMenuUrlController#client` with `permissions: %w[read:stack]`, see [7](#0-6) ) are meant to be confined to a single stack.

`Api::CCMenuController`, however, redefines `#stack` to bypass this scoping entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`require_permission :read, :stack` only asserts that `"read:stack"` is present in the token's `permissions` array; it never checks `stack_id` equality: `check_permissions!` simply does `permissions.include?(required_permission)` [4](#0-3) . Since `stack_id` scoping is a separate, disjoint concept implemented only in `#stacks`/`#stack` on the base controller — and `CCMenuController` overrides `#stack` without re-adding that check — a token minted for Stack A satisfies the `read:stack` permission check and can then be pointed at any other stack's `stack_id` param to retrieve that stack's CCMenu status.

Concretely, `CCMenuUrlController#fetch` mints (or reuses) a per-user, per-stack `ApiClient` scoped to one stack and hands its token to any authenticated Shipit UI user via `ccmenu_url_url` [8](#0-7) . That token — which the fixture `here_come_the_walrus` models (`stack: shipit`, `permissions: [read:stack]`), see [9](#0-8)  — is meant to only ever read the one stack it was generated for. Because `Api::CCMenuController#stack` ignores `current_api_client.stack_id`, that same token can be replayed against `/api/stacks/:any_other_stack/ccmenu` to read that other stack's build/lock/deploy status, breaking the "stack a token authorizes" ↔ "stack it touches" binding.

### Impact Explanation
This is an unauthenticated-relative-to-scope read of stack state: `lastBuildStatus` (derived from `merge_status`, including whether the stack is locked), `activity` (whether a deploy is currently running), and `lastBuildLabel`/`lastBuildTime` (the latest deploy id and timestamps) as rendered in [10](#0-9) . Per the engine's own severity rubric, "unauthenticated read of stack state, task streams or deploy output" via escalation past a token's authorized scope is High severity — a token issued for one stack discloses operational/deploy state for every other stack in the installation.

### Likelihood Explanation
Exploitation only requires possession of a valid CCMenu token — something every Shipit user can self-provision for any stack they can view via `CCMenuUrlController#fetch`, and which is embedded in a bare query-string URL meant for polling by third-party CI-status tools. No special privilege beyond ordinary Shipit login is needed to mint the token; the only extra step is substituting a different `stack_id` in the request path.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from the base controller (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so stack-scoped tokens are constrained the same way they are everywhere else in the API.

### Proof of Concept
1. As any logged-in Shipit user, visit a stack's settings page and click "Fetch URL" for CCMenu, or hit `GET /ccmenu/:owner/:repo/:env` directly — this creates/returns an `ApiClient` scoped to that one stack with `read:stack` permission (`app/controllers/shipit/ccmenu_url_controller.rb`).
2. Take the returned `token` query parameter.
3. Send `GET /api/stacks/:other_owner/:other_repo/:other_env/ccmenu?token=<token>` for a *different* stack than the one the token was scoped to.
4. Observe a `200 OK` with XML disclosing that other stack's lock/build/deploy status, even though the token's `ApiClient#stack_id` does not match — because `Api::CCMenuController#stack` at [1](#0-0)  never consults `stack_id` scoping.
