### Title
Unbounded `console.log` of full AA-generated units/messages and oscript `log` statements causes unbounded per-unit log growth - ([File: aa_composer.js])

### Summary
The Mattermost CVE truncates search-query error text before writing it to the postgres log; ocore has analogous unbounded logging paths reachable by an ordinary, unprivileged unit poster who triggers an Autonomous Agent (AA). Several `console.log` calls in `aa_composer.js` dump the entire AA-composed unit (including all messages/state) via `util.inspect(..., { depth: 6 })` with no size cap, and the oscript `log` statement in `formula/evaluation.js` writes evaluated entries to `console.log` capped only by *count* (100), not by total size.

### Finding Description
Any address holder can post a unit that triggers an AA (this is the standard, permissionless way to invoke deployed AAs). Every node that processes the trigger runs `aa_composer.handleTrigger`, which unconditionally logs the fully composed unit object to the process console at multiple points, with no truncation: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

`util.inspect(objUnit, { depth: 6 })` serializes messages, outputs, and (for `data`/`data_feed` messages) arbitrary state-var/payload content the AA writes into its response unit, all without any length limit — unlike `joint_storage.js`'s `truncate()` helper, which was added specifically to cap error text before persisting it (`truncate(str, maxLength = 200)`): [5](#0-4) 

Separately, the `log` oscript statement (usable inside any AA definition) evaluates an array of expressions and writes them to the console every time the AA executes: [6](#0-5) 
The only guard is on the *number* of log entries (`arr[1].length > 100`), not on the size of each evaluated value, so a single log entry can carry a large string/object built from trigger data, state vars, or oscript string operations, and this is re-logged on every trigger that reaches this statement.

Because both paths execute on **every full node** that processes the trigger unit (not just the poster's node), and because AA triggering is cheap and repeatable (bounded only by normal unit/AA fees), an attacker can cause sustained, oversized log writes across the network's full nodes by repeatedly triggering an AA that emits large messages/state or by triggering any AA containing a `log` statement with attacker-influenced data.

### Impact Explanation
This is a resource-exhaustion (disk-space/log-volume) issue analogous to CVE-2023-2785: repeated triggering causes unbounded log growth on every processing full node, which can fill disks, degrade I/O performance, and potentially crash or destabilize nodes (denial of service), impacting network availability to confirm new units — without requiring any privileged position, malicious peer, or protocol violation.

### Likelihood Explanation
High reachability: any address can post a payment/trigger unit to an existing AA (no special privileges needed), and any AA (including ones the attacker deploys themselves) can be constructed to maximize logged payload size (e.g., long `data` message payloads or `log` statements over large strings/objects). The only friction is normal unit/trigger fees, which is far cheaper than the disk-filling logging cost being incurred per unit by every full node in the network, making this a low-cost, repeatable network-wide DoS vector.

### Recommendation
- Truncate or omit `util.inspect` output of `objUnit`/`messages` in `aa_composer.js` (e.g., cap serialized length similar to `joint_storage.js`'s `truncate()`), or move these to a debug-only log level disabled by default in production.
- In `formula/evaluation.js`'s `log` handling, enforce a maximum serialized size per log entry (and/or total), not just an entry count, consistent with existing `MAX_STRING_LENGTH`/`MAX_AA_STRING_LENGTH` constraints used elsewhere in oscript evaluation.
- Audit other unconditional `console.log` calls that serialize attacker-influenced unit/message content (e.g., `composer.js:592`, `validation.js:126`/`454`) for unbounded size and apply the same truncation pattern.

### Proof of Concept
1. Deploy an AA whose response includes a `log` statement or a `data` message that echoes a large string built from `trigger.data` (e.g., string concatenation up to the oscript string-length limit) back through the response.
2. Repeatedly post trigger units (from any address, no special privileges) invoking this AA.
3. Observe that every full node processing each trigger writes a large, untruncated `console.log` entry (`'unit', util.inspect(objUnit, { depth: 6 })` and/or `'log', entries`) to its log output on each trigger, scaling log volume linearly with the number of triggers sent, independent of any actual state change needed.
