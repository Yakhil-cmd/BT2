### Title
Bridge Operators Can Call `handleERC20Transfer` / `handleERC721Transfer` with Arbitrary Unregistered Token Addresses — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

`handleERC20Transfer` and `handleERC721Transfer` in the Kaia service-chain bridge accept a caller-controlled `_tokenAddress` parameter with no check against the `registeredTokens` whitelist. Any bridge operator can supply an arbitrary token address, causing the bridge to call `mint()` or `transfer()` on a contract that was never approved for cross-chain settlement. This is the direct Kaia analog of the Convex `VoterProxy.vote()` bug: a privileged role (`operator` ↔ `voteDelegate`) can direct the asset-holding contract (bridge ↔ `VoterProxy`) to interact with an arbitrary external contract without a whitelist.

---

### Finding Description

`_requestERC20Transfer` — the **outbound** path — is correctly guarded:

```solidity
function _requestERC20Transfer(address _tokenAddress, ...)
    internal
    onlyRegisteredToken(_tokenAddress)   // ← whitelist enforced
    onlyUnlockedToken(_tokenAddress)
``` [1](#0-0) 

But `handleERC20Transfer` — the **inbound** path that actually moves assets — carries no such guard:

```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,   // ← attacker-controlled, never checked
    uint256 _value,
    ...
)
    public
    onlyOperators            // ← only role check, no token whitelist
{
    ...
    if (modeMintBurn) {
        require(ERC20Mintable(_tokenAddress).mint(_to, _value), ...);
    } else {
        IERC20(_tokenAddress).safeTransfer(_to, _value);
    }
}
``` [2](#0-1) 

The identical gap exists in `handleERC721Transfer`:

```solidity
function handleERC721Transfer(..., address _tokenAddress, ...)
    public
    onlyOperators   // ← no onlyRegisteredToken check
{
    ...
    if (modeMintBurn) {
        require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(...));
    } else {
        IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
    }
}
``` [3](#0-2) 

The `BridgeTokens` contract defines the whitelist and its modifiers but they are simply never applied to the handle functions: [4](#0-3) 

---

### Impact Explanation

**Lock mode (`modeMintBurn = false`):** The bridge holds ERC20/ERC721 tokens in custody. An operator can call `handleERC20Transfer` with any token address the bridge happens to hold (registered or not), with a fresh valid nonce, and transfer those tokens to an arbitrary `_to` address. This drains bridged assets from the contract without a corresponding cross-chain request.

**MintBurn mode (`modeMintBurn = true`):** An operator can call `handleERC20Transfer` with any contract address that exposes a `mint(address, uint256)` selector. If the bridge has been granted the minter role on any token (which is required for normal operation), the operator can mint unbounded token supply to any address — an unauthorized mint of bridged assets.

The corrupted value is the token balance of `_to` (inflated) and the bridge's token reserve or the token's total supply (drained/inflated).

---

### Likelihood Explanation

The default `operatorThreshold` for `ValueTransfer` votes is **1** (set in the `BridgeOperator` constructor): [5](#0-4) 

A single compromised or malicious operator is sufficient to execute the attack with no additional co-signers. Operators are registered by the bridge owner, but the owner and operators are distinct roles; a compromised operator key is a realistic threat model for a live bridge.

---

### Recommendation

Add `onlyRegisteredToken(_tokenAddress)` (and optionally `onlyUnlockedToken(_tokenAddress)`) to both `handleERC20Transfer` and `handleERC721Transfer`, mirroring the protection already present on the outbound path:

```solidity
function handleERC20Transfer(
    ...
    address _tokenAddress,
    ...
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // add this
    onlyUnlockedToken(_tokenAddress)     // add this
{
```

```solidity
function handleERC721Transfer(
    ...
    address _tokenAddress,
    ...
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // add this
    onlyUnlockedToken(_tokenAddress)     // add this
{
```

### Proof of Concept

**Setup (lock mode):**
1. Deploy `Bridge` with `modeMintBurn = false`.
2. Register `tokenA` and fund the bridge with 1000 `tokenA`.
3. Register `operator1` as an operator (threshold = 1, default).

**Attack:**
```solidity
// operator1 calls handleERC20Transfer with tokenA (registered) but
// a fresh nonce that was never requested from the counterpart chain.
bridge.handleERC20Transfer(
    bytes32(0xdeadbeef...),  // fake requestTxHash
    attacker,                // _from (irrelevant)
    attacker,                // _to  ← receives drained tokens
    address(tokenA),         // _tokenAddress ← registered token, no extra check needed
    1000e18,                 // _value ← full bridge reserve
    999,                     // _requestedNonce ← fresh, not yet closed
    block.number,
    ""
);
// Result: attacker receives 1000 tokenA; bridge reserve is zero.
```

**Attack (mintBurn mode):**
```solidity
// operator1 calls handleERC20Transfer with an UNREGISTERED token address
// on which the bridge has minter role.
bridge.handleERC20Transfer(
    bytes32(0xdeadbeef...),
    attacker,
    attacker,
    address(unregisteredMintableToken),  // ← not in registeredTokens, no revert
    1_000_000e18,
    999,
    block.number,
    ""
);
// Result: 1,000,000 unregisteredMintableToken minted to attacker.
```

The nonce check (`_lowerHandleNonceCheck` + `_voteValueTransfer`) only prevents **replay** of already-closed nonces; it does not prevent an operator from fabricating a new nonce with an arbitrary token address, since there is no on-chain proof that the nonce corresponds to a real cross-chain request.
