### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` matches commits solely by `sha` with no scoping to the repository/stack that authenticated the webhook, so a GitHub `status` event verified only against org-A's `webhook_secret` can update the `Status` of any `Commit` row across all stacks that happens to share that sha, including stacks owned by unrelated org-B. Because git shas are content-addressed (e.g. identical cherry-picks or the universally-known empty-tree sha `4b825dc642cb6eb9a060e54bf8d69288fbee4904`), an attacker who controls a repository under org-A can trigger status writes on org-B's commit records without ever authenticating against org-B's secret.

### Finding Description
The broken binding is: verified organization (org-A, established in `verify_signature` via `Shipit.github(organization: repository_owner)` at [1](#0-0)  ) == organization owning every `Commit` row mutated by `process`. This does not hold, because `process` never joins/filters by repository:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

The controller's `verify_signature` only proves the request came from a source holding org-A's `webhook_secret`/App key, derived from `repository_owner` in the payload (`params.dig('repository','owner','login')`) [3](#0-2) . It never constrains which `Commit` rows the subsequent handler is allowed to touch — `create` simply dispatches the full parsed JSON to every registered handler for the event type [4](#0-3) . The `StatusHandler`'s `ExplicitParameters` schema only requires `sha`/`state`/etc.; it never requires or validates `repository.full_name` against the commits being updated [5](#0-4) .

Attacker flow: attacker owns repo `org-A/evil`, adds `Shipit` as a GitHub App/webhook there (a normal, unprivileged action for any repo owner). They create a commit with a sha colliding with a commit that already exists on org-B's Shipit stack (trivially achievable via the well-known empty-tree sha, or by cherry-picking a public upstream commit that both org-A and org-B track). They send (or GitHub sends) a `status` webhook event for that sha with `state: success` (or `failure`) and `context`. `verify_signature` succeeds because it only checks org-A's secret against `repository_owner = org-A`. `StatusHandler#process` then loads `Commit.where(sha: same_sha)`, which returns rows in both stacks, and calls `create_status_from_github!` on all of them, mutating org-B's commit status.

None of the existing guards catch this: `verify_signature` authenticates the sender's organization, not the target record's organization; `drop_unhandled_event`/`check_if_ping` are unrelated; the `ExplicitParameters` schema validates types, not scope; there is no `stacks`/repository scope applied inside `process`.

### Impact Explanation
This is a cross-repository/cross-tenant write: a payload authenticated for org-A mutates a `Commit`/`Status` record belonging to org-B's stack, matching the "payload for one repository mutating another's stack/commit" Critical category. An attacker can flip CI status (`success`/`failure`/`pending`) on arbitrary victim stacks' commits, which can influence merge/deploy gating logic that consults commit statuses (e.g., `CommitChecks`, deploy readiness) — enabling unauthorized/forced deploys or blocking legitimate ones on a repository the attacker never authenticated against. This is repeatable for any sha collision the attacker can engineer or opportunistically exploit (well-known empty-tree sha, shared upstream commits, submodule commits, or shared vendored history), against any number of Shipit-tracked repositories.

### Likelihood Explanation
Preconditions: the attacker needs a Shipit App/webhook installed on a repo under their control (self-service, e.g., any public GitHub App install flow for the Shipit app) and needs the target sha to also exist as a `Commit` row on the victim's Shipit stack — trivially true for the constant empty-tree sha, or for shared open-source commits across mirrored/forked/vendored repos, or via crafted cherry-picks. No secrets of org-B are required; the attacker only needs their own valid `webhook_secret`/signature for org-A. Cost is a single crafted `status` webhook POST, fully repeatable and scriptable.

### Recommendation
Scope the lookup to only commits belonging to stacks whose repository matches the authenticated `repository_owner`/`repository.full_name` from the payload, e.g. `Commit.joins(:stack).merge(Stack.where(repository: repository_for(params))).where(sha: params.sha)`, or pass the verified repository from the controller into the handler and require it in the `ExplicitParameters` schema, then filter commits by that repository before applying the status update.

### Proof of Concept
Minitest plan (models test, no live GitHub):
```ruby
test "StatusHandler does not update commits belonging to a different repository" do
  stack_a = shipit_stacks(:cyclonoid) # repository under org-A
  stack_b = create_stack(repository: create(:repository, owner: "org-B", name: "repo-b"))

  sha = "4b825dc642cb6eb9a060e54bf8d69288fbee4904"
  commit_a = stack_a.commits.create!(sha: sha, message: "empty tree", author: shipit_authors(:sample))
  commit_b = stack_b.commits.create!(sha: sha, message: "empty tree", author: shipit_authors(:sample))

  payload = {
    'sha' => sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => stack_a.repository.full_name, 'owner' => { 'login' => 'org-A' } },
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_equal 'success', commit_a.reload.state
  # Assert the binding: verified org-A payload must NOT mutate org-B's unrelated commit
  refute_equal 'success', commit_b.reload.state
end
```
Currently this assertion fails (`commit_b.state` becomes `success`), proving the equality "verified organization == organization of every mutated Commit" is broken.
