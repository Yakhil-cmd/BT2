### Title
ERC721 Bridge Uses `transferFrom` Instead of `safeTransferFrom` When Delivering Tokens to Recipients — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.handleERC721Transfer` uses `IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId)` to deliver a bridged ERC721 token to the recipient. This is the direct analog of the external H-08 bug class: using the wrong transfer method when a contract already owns the asset. Unlike ERC20's `safeTransfer`, ERC721's `transferFrom` does **not** invoke `onERC721Received` on the recipient. If `_to` is a smart contract that does not implement `IERC721Receiver`, the token is silently transferred into a contract that cannot handle it, permanently locking the NFT.

---

### Finding Description

In `BridgeTransferERC721.sol`, the non-mintBurn path of `handleERC721Transfer` is:

```solidity
// line 69
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
```

The bridge contract holds the ERC721 token in custody (deposited via `requestERC721Transfer` or `onERC721Received`). When operators vote to release it to `_to`, the bridge calls `transferFrom(address(this), _to, _tokenId)`.

The OpenZeppelin v2 ERC721 `transferFrom` only checks `_isApprovedOrOwner(msg.sender, tokenId)`. Because `msg.sender == address(this) == owner`, the check passes and the transfer succeeds — but it **never calls `onERC721Received`** on `_to`. If `_to` is a contract without `IERC721Receiver`, the NFT is irrecoverably locked there.

By contrast, the ERC20 bridge (`BridgeTransferERC20.sol` line 71) correctly uses `IERC20(_tokenAddress).safeTransfer(_to, _value)` — the ERC20 equivalent that sends from the contract's own balance without requiring allowance. The ERC721 bridge should analogously use `safeTransferFrom(address(this), _to, _tokenId)`, which performs the same ownership check but additionally verifies the recipient can accept ERC721 tokens.

---

### Impact Explanation

Any ERC721 token bridged in lock/unlock mode (non-mintBurn) to a contract address that does not implement `IERC721Receiver` is permanently lost. The token leaves the bridge's custody and enters a contract that cannot transfer it out. This is an irreversible loss of a bridged asset.

---

### Likelihood Explanation

The `_to` address originates from the user's original cross-chain transfer request. Users routinely send NFTs to contract wallets, multisigs, DAOs, or other smart contracts. Many such contracts do not implement `IERC721Receiver`. The operators faithfully relay whatever `_to` was specified; they have no mechanism to validate whether `_to` can receive ERC721 tokens. This scenario is reachable in normal operation without any malicious actor.

---

### Recommendation

Replace `transferFrom` with `safeTransferFrom` in `handleERC721Transfer`:

```solidity
// Before (line 69):
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// After:
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

This mirrors the ERC20 bridge's use of `safeTransfer` and ensures that if `_to` cannot accept ERC721 tokens, the transaction reverts and the token remains safely in the bridge rather than being permanently locked in an incompatible contract.

---

### Proof of Concept

1. User on source chain calls `requestERC721Transfer(tokenAddr, contractWithoutReceiver, tokenId, "")`.
2. Operators relay the request; two operators call `handleERC721Transfer(txHash, user, contractWithoutReceiver, tokenAddr, tokenId, nonce, blockNum, uri, "")`.
3. On the second operator vote, `_voteValueTransfer` returns `true` and execution reaches line 69.
4. `IERC721(tokenAddr).transferFrom(address(this), contractWithoutReceiver, tokenId)` succeeds — the bridge is the owner, so `_isApprovedOrOwner` passes.
5. The NFT is now owned by `contractWithoutReceiver`, which has no `onERC721Received` and no way to call `transferFrom` or `safeTransferFrom` to move it out.
6. The NFT is permanently locked. The `HandleValueTransfer` event is emitted, so the bridge considers the transfer complete and will never retry. [1](#0-0) [2](#0-1) [3](#0-2)
