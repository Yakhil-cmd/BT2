### Title
Cross-tenant status webhook fan-out via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no filter on the repository/stack that the verified webhook belongs to, then calls `create_status_from_github!` on every matching `Commit` row. Because `sha` is not globally unique to one repository (e.g., an empty-tree or otherwise content-identical commit can exist as separate `Commit` rows across many stacks), a single signed status webhook for one tenant's repository can mutate and fire hooks/merge scheduling for every other tenant that happens to share that sha.

### Finding Description
The broken binding: the code assumes `{stack_ids mutated by one status webhook} == {stack_id of the repository that signed/authenticated the webhook}`. In fact the actual set is `{stack_id : Commit.sha == params.sha}`, which is a superset whenever multiple stacks contain a `Commit` row with the same `sha` value.

Code path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-38`) verifies the HMAC signature against `Shipit.github(organization: repository_owner)`, i.e., it authenticates that the *sender* owns `repository_owner`. It never restricts which `Commit`/`Stack` rows the payload's `sha` may affect. [1](#0-0) 
- `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 
This query is global across all stacks/tenants — there is no `stacks.where(...)` or `repository`-scoped filter, unlike sibling handlers such as `CheckSuiteHandler`, which explicitly scopes via `stacks.where(branch: ...)` derived from `Repository.from_github_repo_name(repository_name)` in the base `Handler` class. [3](#0-2) [4](#0-3) 
- `Commit#create_status_from_github!` calls `add_status` which replicates the status using the *commit's own* `stack_id` (not the webhook's originating repository) and fires stack-level hooks/side-effects. This is confirmed by the test suite, which asserts that `add_status`/`create_status_from_github!` emits `Hook.emit(:deployable_status, ...)` and enqueues `ProcessMergeRequestsJob` scoped to `commit.stack` for each transition. [5](#0-4) [6](#0-5) 

Attacker's exact request: attacker owns/controls a GitHub repository registered as a Shipit stack (e.g., stack A). They push/create a commit whose sha is content-identical to a commit that other unrelated stacks (B, C, ...) also recorded (classic case: the empty-tree sha `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any repo forked/rebased to reproduce an identical tree+parents+timestamps). They then trigger (or directly POST, since GitHub will sign it correctly for their own repo) a `status` webhook with `state: success`, `sha` = shared sha. The webhook signature check passes because it's legitimately signed for the attacker's own org/repo. `StatusHandler` then iterates *all* `Commit` rows with that sha across all stacks and independently invokes `add_status` on each, firing `deployable_status` hooks and scheduling merge/CD jobs for stacks the attacker does not own and never authenticated against.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) only validate that the request is a legitimately-signed webhook from *some* org — none of them constrain the `Commit.where(sha:)` scope to that org's repository/stack. The root cause is the missing stack/repository filter in `StatusHandler#process`.

### Impact Explanation
A forged/legitimate-for-attacker webhook for one repository causes `Commit#add_status` to run on `Commit` rows belonging to unrelated stacks/tenants, emitting `Hook.emit(:deployable_status, ...)` (external webhook fan-out to those tenants' configured hook URLs with attacker-influenced status content) and enqueuing `ProcessMergeRequestsJob`/continuous-delivery scheduling for those stacks. This is "a payload for one repository mutating another's stack/commit" — matching the Critical category. Repeatable against any set of stacks sharing a sha (most realistically via well-known content-identical objects like the empty tree, but also achievable deliberately by crafting identical commit metadata across forks). Blast radius scales with the number of tenants ("N stacks") sharing that sha on a single Shipit instance.

### Likelihood Explanation
Preconditions: a multi-tenant Shipit instance where `Commit.where(sha: X)` legitimately returns rows for more than one `stack_id` — this requires either (a) common shared low-entropy commits (empty-tree sha, or shas of trivial/boilerplate initial commits across many templated repos) or (b) an attacker deliberately reproducing another repo's known commit sha in their own repo history (feasible for shared/forked history, harder for arbitrary target shas but not required — colliding on a known shared sha like the empty tree requires no special access). The attacker needs no Shipit credentials, only ownership of one registered repository/stack and the ability to have GitHub deliver (or replay) a `status` event for it — a normal, unprivileged GitHub action. Cost is low and the attack is repeatable at will.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the stack(s) belonging to the repository the verified webhook covers, mirroring `CheckSuiteHandler`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the `stacks` helper already defined in `Webhooks::Handlers::Handler` (`Repository.from_github_repo_name(repository_name)&.stacks`), so only commits belonging to the authenticated repository's own stacks are updated.

### Proof of Concept
Add a test to `test/models/commits_test.rb` (or a new handler test file) that:
1. Creates three `Stack` fixtures (`stack_a`, `stack_b`, `stack_c`) each with a `Commit` row sharing the same `sha` value (e.g., the empty-tree sha), each associated with hooks subscribed to `deployable_status`.
2. Builds a `status` webhook payload with `repository.full_name` pointing only at `stack_a`'s repo, `sha` = the shared sha, `state: 'success'`.
3. Stub/allow the signature check for `stack_a`'s org only (`GithubHook.any_instance.stubs(:verify_signature).returns(true)` as in existing `WebhooksControllerTest`).
4. Post the webhook via `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (or through the controller).
5. Assert:
   - Expected (secure) binding: `Hook` emissions for `:deployable_status` and enqueued `ProcessMergeRequestsJob`/`ContinuousDeliveryJob` occur only for `stack_a`.
   - Actual (current) behavior: assert (as the PoC) that `expect_hook_emit`/`assert_enqueued_with` fire for `stack_b` and `stack_c` as well — demonstrating the cross-tenant mutation. This can build on the existing pattern in `test/models/commits_test.rb:763-777` (`assert_enqueued_with(job: ProcessMergeRequestsJob, args: [stack.commit])`) but for all three stacks after a single webhook targeted at `stack_a`.
