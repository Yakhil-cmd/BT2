### Title
Cross-repository Status forgery via unscoped SHA lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `params.sha` with `Commit.where(sha: params.sha)`, never checking that the SHA belongs to the repository named in the incoming webhook payload. Because commit SHAs are content-addressed and identical across forks/clones of a repository, a webhook whose `repository` field points at an attacker-owned repo (R2) but whose `sha` matches a commit already present in a victim stack (R1) will have its attacker-controlled `description`/`target_url`/`context` written verbatim onto R1's `Status` row via `Status.replicate_from_github!`.

### Finding Description
The binding the question asks about is: "strings displayed as S1's CI metadata == strings genuinely emitted by R1's own CI integration." Tracing the code:

- `Shipit::WebhooksController#verify_signature` validates the HMAC signature of the raw body against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-supplied JSON body (`params.dig('repository','owner','login')`) [1](#0-0) [2](#0-1) . This only proves the webhook was legitimately signed for *some* org/app installation that the attacker controls (R2) — it says nothing about which commit the `sha` in the payload actually belongs to.
- `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
This lookup is **global across all stacks/repositories** — it never restricts to commits belonging to the repository named in the payload. Contrast this with the base `Handler` class, which defines a `stacks` helper that *does* scope by `Repository.from_github_repo_name(repository_name)` [4](#0-3) , but `StatusHandler` never uses it.
- `Commit#create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` [5](#0-4) , and `Status.replicate_from_github!` writes `description`, `target_url`, `context`, `state`, and `created_at` verbatim from the webhook params onto the found commit's `Status` row, scoped to the *found commit's* `stack_id` (i.e., R1's stack) [6](#0-5) .

Since git commit SHAs are content-addressed hashes of tree+parents+author/committer+timestamps+message, any fork of R1 (which an unprivileged attacker can create) will contain commits with byte-identical SHAs to commits in R1. An attacker who forks R1 into R2, or otherwise crafts/replays a commit whose SHA equals a commit already in R1's Shipit stack, and then triggers (or replays) a `status` webhook naming R2 as the repository, will have their chosen `description`/`target_url`/`context` written onto R1's existing `Status` row. This status is then read by the stack/commit UI as if it came from R1's own CI, since nothing in `Status`, `Commit`, or the views distinguishes "which repository's webhook produced this Status" beyond the `stack_id` — and the `stack_id` used is the *victim's* stack because the lookup found the victim's `Commit`.

None of the listed guards intercept this: `verify_signature` validates only that the request came from a legitimately-signed installation for R2, not that R2 authored the referenced commit; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema only validates types/shape of `sha`, `state`, `description`, `target_url`, `context`; there is no `Repository`/`Stack` validation involved in this write path since `stack_id` is taken from the found `Commit`, not from the payload.

### Impact Explanation
This is a payload for one repository (R2) mutating another repository's stack/commit data (R1) — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attacker can inject an arbitrary `target_url` (e.g., pointing operators to an attacker-controlled URL surfaced in the deploy UI) and an arbitrary `description`/`context` label, spoofing CI provenance on a commit that may be under active deploy review in R1. This is repeatable against any commit whose SHA the attacker can reproduce (trivially, any commit reachable by forking R1, which is public/attacker-forkable by definition of a GitHub repo an unprivileged user can interact with), and against any stack tracking that repository.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository (R2) where they can trigger a `status` webhook delivery that is validly signed for whatever GitHub App/organization installation Shipit trusts for R2, and (b) knowledge of a commit SHA present in a victim R1 stack that they can also produce/reference in R2 (trivial via forking R1, since fork commit SHAs are identical to the upstream). Both are achievable by an unprivileged GitHub user with no Shipit credentials, consistent with the stated threat model. The attack is repeatable per request and does not require any race condition or timing.

### Recommendation
In `StatusHandler#process` (and analogously any other SHA-keyed handler), scope the `Commit` lookup to the repository named in the webhook payload, e.g. via the existing `stacks` helper: `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently restrict via `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a status can only be applied to commits belonging to the repository that the (signature-verified) payload actually names.

### Proof of Concept
Minitest plan (no live GitHub, using existing fixtures/factories):
1. Create `stack_r1` for repository `owner/r1` with `commit = shipit_commits(:...)` whose `sha = "deadbeef..."`.
2. Create `stack_r2` for a distinct repository `owner/r2` (or none at all — R2 need not have a Shipit stack).
3. Build a `status` webhook payload with `repository.full_name = "owner/r2"`, `sha = commit.sha` (the R1 commit's SHA), and attacker-chosen `description: "FAKE CI PASSED"`, `target_url: "https://evil.example/phish"`, `context: "ci/attacker"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, as `verify_signature` is not part of the handler and is out of scope for this unit test).
5. Reload `commit` and assert:
   - `commit.statuses.last.target_url == "https://evil.example/phish"`
   - `commit.statuses.last.description == "FAKE CI PASSED"`
   - `commit.statuses.last.stack_id == stack_r1.id`
   demonstrating that a payload declaring repository `owner/r2` wrote a status onto `owner/r1`'s stack/commit, violating the binding that displayed CI metadata originates from the commit's own repository's CI integration.
