### Title
Independently-Bounded TPS Fee Voting Parameters Lack Cross-Validation, Enabling Fee Formula to Exceed Total Supply and Freeze Network Confirmation - (File: `validation.js`, function `validateInlinePayload` / `system_vote` case)

### Summary
Ocore lets any unit poster vote on three independent, coin-weighted system parameters — `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` — that are combined multiplicatively/exponentially to compute the mandatory TPS fee every unit must pay. Each parameter is validated only against its own fixed numeric bound; there is no check on the *combination* of the three values, mirroring the JOJO finding where `borrowFeeRate`, `initialMortgageRate` and `liquidationMortgageRate` are each individually bounded but never cross-validated, letting an internally-consistent-looking but jointly unsafe parameter set become active.

### Finding Description
The `system_vote` message handler validates each subject independently: [1](#0-0) 

- `base_tps_fee` ≤ 1e8
- `tps_interval` ≥ 0.1 (no upper bound)
- `tps_fee_multiplier` between 1 and 1000

Each subject is voted on and counted independently, with the final value being a coin-weighted median of votes cast for that single subject: [2](#0-1) 

None of the three checks reference the values of the other two subjects. Once accepted, `storage.systemVars` stores each subject's timeline separately and `getSystemVar` simply picks the latest value per-subject: [3](#0-2) 

These three independently-set values are then combined exponentially to compute the fee every ordinary unit poster must pay: [4](#0-3) 

```
tps_fee   = base_tps_fee * (exp(tps / tps_interval) - 1)
fee_to_pay = tps_fee_multiplier * tps_fee
```

Because `tps_interval` has no practical cap on how small it can be (min 0.1), and `base_tps_fee` and `tps_fee_multiplier` can each independently reach their maxima (1e8 and 1000 respectively), the combination `base_tps_fee=1e8, tps_interval=0.1, tps_fee_multiplier=1000` produces a required fee that grows explosively even at modest observed `tps` (transactions-per-second), e.g. at `tps=1`: `exp(1/0.1)=e^10≈22026`, giving `fee_to_pay ≈ 1e8 * 22026 * 1000 ≈ 2.2×10^15` — already exceeding the total coin supply (`constants.TOTAL_WHITEBYTES`), before accounting for even higher, entirely plausible, real-world `tps` spikes.

Each of the three values individually satisfies its own hard-coded bound, exactly as in the JOJO bug where `initialMortgageRate`, `liquidationMortgageRate`, and `borrowFeeRate` each individually passed their own checks but the *combination* was unsafe because no code validated the relationship between them.

### Impact Explanation
`validateTpsFee` rejects any unit whose paid `tps_fee` (scaled by `tps_fee_multiplier`) is below the currently required minimum: [5](#0-4) 

If the combined parameter set drives the required fee above what is economically payable (or above the total money supply), ordinary participants — and even non-OP nodes — cannot construct units that satisfy the fee requirement once network activity (`tps`) rises even slightly. This directly matches the accepted impact category "a network unable to confirm new units": the DAG would stall for regular unprivileged unit posters whenever transaction throughput increases, because the fee formula's exponential blow-up was never bounded by a joint sanity check across `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier`.

### Likelihood Explanation
Reaching this state requires only that a coin-weighted majority of voters (each an ordinary, unprivileged unit poster casting a `system_vote` message — a message type reachable by any address, not an admin-only operation) push each of the three subjects toward its individually-permitted extreme over time via the standard vote-median mechanism. No single vote is invalid; each subject's value independently satisfies the range checks in `validateInlinePayload`. This is a legitimate, permissionless path (unlike a hub/peer/node compromise), matching the class of reachable actors required by the rules (unprivileged unit poster). The likelihood of accidental (non-malicious) drift into an unsafe combination is non-trivial given there is no code path anywhere that rejects a combination even though the interaction between the three parameters is well-defined and exponential.

### Recommendation
When counting votes for `base_tps_fee`, `tps_interval`, or `tps_fee_multiplier` in `countVotes` (and/or when validating an individual `system_vote` in `validateInlinePayload`), compute the worst-case fee implied by the *proposed* value together with the currently active values of the other two subjects (and vice versa), and reject/clamp updates that would allow `base_tps_fee * tps_fee_multiplier * (exp(tps/tps_interval) - 1)` to exceed a safe ceiling (e.g., a fraction of `constants.TOTAL_WHITEBYTES`) at some bounded/plausible `tps`. Alternatively, tighten the individual bounds so that even the worst-case combination of all three maxima cannot make the fee formula exceed the total money supply at reasonably foreseeable `tps` values, analogous to enforcing `liquidationMortgageRate` sufficiently above `initialMortgageRate` accounting for the worst-case `borrowFeeRate` in the JOJO recommendation.

### Proof of Concept
1. Over the course of a year, a coin-weighted majority of addresses submit `system_vote` messages independently: `{subject: "base_tps_fee", value: 1e8}`, `{subject: "tps_interval", value: 0.1}`, `{subject: "tps_fee_multiplier", value: 1000}`. Each vote passes the per-subject checks in `validateInlinePayload` (lines 1893-1907).
2. `countVotes` (main_chain.js 1878-1903) computes the coin-weighted median independently per subject and each of the three system vars converges to these extreme (but individually valid) values, stored via `storage.systemVars[subject].unshift(...)`.
3. Real network throughput rises to even `tps = 1` (a modest, realistic load).
4. `storage.getCurrentTpsFee`/`getCurrentTpsFeeToPay` (storage.js 1397-1408) compute `fee_to_pay ≈ base_tps_fee * tps_fee_multiplier * (exp(tps/tps_interval)-1) ≈ 2.2×10^15`, exceeding `constants.TOTAL_WHITEBYTES`.
5. `validateTpsFee` (validation.js 1050-1097) now requires every unit (from non-OP posters) to pay a `tps_fee` no ordinary user can afford, and OPs alone cannot process all traffic — the network effectively cannot confirm new units from ordinary users once tps ticks up, since no code path ever validated the joint safety of `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` together.
