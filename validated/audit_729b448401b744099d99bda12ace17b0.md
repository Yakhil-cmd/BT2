### Title
Unvalidated Staking-Info Response in `SyncStakingInfo` Allows Any Connected Peer to Corrupt Validator-Set and Reward-Distribution Records — (`datasync/downloader/downloader.go`, `datasync/downloader/queue.go`)

---

### Summary

The `SyncStakingInfo` recovery flow, exposed as `admin_syncStakingInfo`, fetches historical staking records from a caller-specified peer and writes them directly to the local database. The delivery handler `DeliverStakingInfos` contains an explicit stub validator that unconditionally returns `nil`, and the recovery loop checks only the `BlockNum` field of each response item. A malicious peer can therefore serve arbitrarily crafted `P2PStakingInfo` payloads — with fake `NodeIds`, `RewardAddrs`, and `StakingAmounts` — that are persisted verbatim, permanently corrupting the validator-set and reward-distribution records used by the node.

---

### Finding Description

**Stub validator in `DeliverStakingInfos`**

`DeliverReceipts` validates every receipt against the header's `ReceiptHash` before accepting it: [1](#0-0) 

`DeliverStakingInfos`, by contrast, ships a `validate` closure that is a permanent no-op: [2](#0-1) 

**Unchecked write in the recovery loop**

`SyncStakingInfo` requests staking records from a single caller-specified peer. On receipt, it checks only that `stakingInfo.BlockNum` matches the expected block number, then calls `PutStakingInfoToDB` with the raw peer-supplied content: [3](#0-2) 

No field in the `P2PStakingInfo` struct — `NodeIds`, `StakingContracts`, `RewardAddrs`, `StakingAmounts` — is verified against on-chain state (staking contract storage, AddressBook, or the canonical block's state root).

**Admin-API exposure**

`SyncStakingInfo` is registered as `admin_syncStakingInfo` and is callable by any process with admin-IPC or admin-HTTP access: [4](#0-3) [5](#0-4) 

---

### Impact Explanation

Staking info stored by `PutStakingInfoToDB` is the authoritative source for:

- **Weighted-random proposer selection** — `NodeIds` and `StakingAmounts` determine which validators are eligible to propose blocks and with what probability.
- **Block reward distribution** — `RewardAddrs` are the addresses to which KAIA block rewards are sent each epoch.

A malicious peer that serves a response with:
- `RewardAddrs` replaced by attacker-controlled addresses → all KAIA block rewards for the affected epoch(s) are redirected.
- `StakingAmounts` zeroed for honest validators → those validators are excluded from proposer selection, enabling a minority to dominate block production.
- `NodeIds` replaced → the validator committee is silently replaced.

Because the corrupted records are persisted to the misc DB, the effect survives node restarts and propagates to all logic that reads staking info for those block numbers.

---

### Likelihood Explanation

The trigger requires an operator to call `admin_syncStakingInfo` and supply the malicious peer's node ID. This is a semi-privileged action, but it is a documented recovery procedure that operators are expected to use when staking records are missing (e.g., after a database migration or partial sync). A malicious peer that is already connected to the node and that knows the operator is running a recovery can serve crafted data with no further interaction. The operator has no way to detect the corruption at call time because no validation output is surfaced.

---

### Recommendation

1. **Validate content against on-chain state.** After receiving a `P2PStakingInfo` batch, re-derive the expected staking info by reading the staking contract storage at the canonical state root for each block number and compare it field-by-field before calling `PutStakingInfoToDB`.

2. **Remove the stub validator.** Replace the `// TODO-Kaia-Snapsync update validation logic` no-op in `DeliverStakingInfos` with a real check — at minimum, verify that the `BlockNum` in each item matches the corresponding header in the request set and that the data hash matches a commitment in the block header or a trusted source.

3. **Restrict peer selection.** In `SyncStakingInfo`, consider requiring the target peer to be a known, trusted peer (e.g., a CN peer with a verified node ID) rather than any registered peer.

---

### Proof of Concept

1. Start a Kaia node (pre-Kaia-fork chain) with some staking-interval blocks missing from the misc DB.
2. Connect a malicious peer that implements the `kaia/65` protocol and responds to `StakingInfoRequestMsg` with a crafted `[]*staking.P2PStakingInfo` where `RewardAddrs` are attacker-controlled addresses and `StakingAmounts` are inflated for attacker-controlled validators.
3. From the victim node's admin console:
   ```js
   admin.syncStakingInfo("<malicious-peer-enode-id>", 0, 10000)
   ```
4. After the call returns, query the misc DB for the staking records at the affected block numbers. The `RewardAddrs` and `StakingAmounts` will reflect the attacker-supplied values.
5. Observe that subsequent block reward distributions for those epochs use the corrupted addresses, and that proposer selection weights are skewed toward attacker-controlled validators.

The root cause is the unconditional `return nil` in the `validate` closure of `DeliverStakingInfos` ( [2](#0-1) ) and the absence of any content check in the recovery loop ( [3](#0-2) ).
