### Title
Webhook signature verification keys off the attacker-controlled `repository`/`organization` login instead of the org that actually authenticates the signature - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App / `webhook_secret` to validate a delivery against by reading `repository.owner.login` (or `organization.login`) straight out of the **unverified** JSON body, then uses that org's secret to HMAC-check the whole raw body. Any handler downstream, however, resolves the actual repository/organization it acts on independently, from the very same unverified body. In a multi-organization Shipit deployment (each org configured with its own `webhook_secret`, as shown in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`), this creates two different reads of "which org is this event for" over the same payload, bound only by the attacker's own choice of field values — not by the signature itself.

### Finding Description
`verify_signature` derives the verification key from payload data before the signature is validated: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns the `GithubApp` configured for whatever organization name appears in the body, and `verify_webhook_signature` only confirms the raw body was HMAC-signed by *that* org's `webhook_secret`: [3](#0-2) 

Once verification passes, `Handler#repository_name` re-reads the repository target straight from the same unverified body to locate the `Stack`/`Repository` to act on: [4](#0-3) 

and `MembershipHandler` similarly trusts `params.organization.login` from the body to create/attach a `Team` and add a member to it: [5](#0-4) 

The equality that should hold is: **org whose secret validated the signature == org whose repository/team the handler mutates**. Nothing in the code enforces this. An administrator of one org configured in the same multi-tenant Shipit install (who legitimately knows their own org's `webhook_secret`, since they configured it) can craft a payload where `repository.owner.login`/`organization.login` is set to their own org (so `verify_signature` selects and validates against their own known secret) while `repository.full_name` or the `team`/`member` fields target a different org's repository, stack, or team. The signature check passes because it is only checking "was this body signed by org X's secret", not "does org X own the repository/team referenced inside this body".

### Impact Explanation
Via `PushHandler`, this lets the forging org trigger `stack.sync_github(expected_head_sha:)` against a `Stack` belonging to a different organization's repository, using an attacker-chosen `after` SHA — feeding an unauthorized, arbitrary state transition into another org's stack sync. Via `MembershipHandler`, the forging org can create/mutate a `Team` row for another organization and call `team.add_member(user)`, i.e. grant arbitrary users membership in a `Shipit::Team`, which is used for `Shipit.github_teams`-style authorization gating access to stacks. This is exactly the "escalation into `Shipit.github_teams` authorization" class of High-severity impact: an org that authenticated (via its own known secret) is not the org whose repository/team is written.

### Likelihood Explanation
This requires the Shipit deployment to host multiple organizations with independent `webhook_secret`s (an explicitly supported and documented configuration) and requires the attacker to be an administrator/owner of one of those organizations' GitHub Apps — i.e., someone who legitimately knows their own org's `webhook_secret` but has no authorization over the target org's repositories/teams. No GitHub write access, Shipit session, or API token is needed; only knowledge of a secret the attacker is entitled to know for their own org. This is a realistic, low-effort attack in any multi-org Shipit instance.

### Recommendation
Bind the field used to select the verification key to the field(s) used by handlers to determine the acted-upon resource, and cross-check they match after signature verification — e.g., re-derive `repository_owner`/`organization` from the handler's own resolved `Repository`/`Team` record and reject the event if it doesn't match the org whose secret validated the signature. Alternatively, only trust a single canonical field (verified early) and have all handlers consistently key off that same field rather than independently re-parsing `repository.full_name` / `organization.login` from the raw body.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgAttacker` (secret `S_A`, known to the attacker who administers that GitHub App) and `OrgVictim` (secret `S_V`, unknown to attacker), per the multi-org config format in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker crafts a `membership` (or `push`) webhook JSON body:
   - `organization.login` = `"OrgAttacker"` (so `repository_owner`/`Shipit.github(organization:)` resolves to `OrgAttacker`'s app and `S_A`)
   - `team` object pointing at a team associated with `OrgVictim`'s stacks (or, for `push`, `repository.full_name` = `"OrgVictim/target-repo"`)
   - `member.login` = attacker's own GitHub login
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, raw_body)` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "OrgAttacker")` and validates successfully against `S_A`.
5. `MembershipHandler#process` runs and calls `team.add_member(member)`, adding the attacker to a `Team` tied to `OrgVictim`, all without ever possessing `OrgVictim`'s `webhook_secret`. [6](#0-5)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
