### Title
`StatusHandler#process` resolves commits by SHA only, without validating that the webhook's `repository.full_name` owns the commit's stack, allowing cross-repository `Status` forgery - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Every other webhook handler (`PullRequest::OpenedHandler`, etc.) resolves target stacks via `Handler#stacks`, which binds `payload['repository']['full_name']` to `Repository.from_github_repo_name(repository_name).stacks` before touching any record. `StatusHandler#process` instead runs `Commit.where(sha: params.sha)` with no repository/stack filter, so a `status` webhook whose payload names the attacker's own repository but whose `sha` matches a commit that also exists (by content-identical git object hash) in an unrelated victim stack will mutate that victim's commit.

### Finding Description
The binding that should hold and holds for every other handler is: `payload['repository']['full_name'] == repository owning the stack whose records get mutated`. In `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) this is enforced explicitly:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
```
`StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) never calls `stacks` or `repository_name`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
`Commit#sha` is a global git object hash, not scoped to a repository/stack. Because git object hashes are computed from tree/parent/author content, an identical commit (e.g. from a fork, or a repository that previously shared history with a Shipit-tracked repo) can exist with the same SHA in two different repositories that Shipit treats as two different `Repository`/`Stack` rows.

Attack flow:
1. Attacker owns/controls a GitHub repository (e.g. a fork of, or a repo sharing commit history with, a Shipit-tracked "victim" repository), and that repository has the Shipit GitHub App installed (a normal, unprivileged action any GitHub user can take on a public repo).
2. The victim's Shipit stack already has a `Commit` row for SHA `X` (fetched via normal push/PR sync).
3. Attacker triggers (via GitHub's real status API, using their own token, on their own repo) a `status` event for a commit with the identical SHA `X` (present in their fork because it's the same git object).
4. GitHub signs and delivers the webhook with `repository.full_name` = attacker's repo. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) verifies the signature using `Shipit.github(organization: repository_owner)` for the attacker's own org — this succeeds because it is a legitimately signed request for the attacker's own repository. `drop_unhandled_event` passes because `status` is a handled event.
5. `StatusHandler.call(params)` runs and matches `Commit.where(sha: X)`, which returns the **victim's** commit row (belonging to a different `Repository`/`Stack`), and calls `commit.create_status_from_github!(params)`, writing a forged `Status` onto the victim's stack.

None of the existing guards catch this: `verify_signature` only authenticates that the *sender* legitimately controls the named repository/org — it says nothing about which `Commit` rows the handler is allowed to touch. `drop_unhandled_event` only filters by event type. The `ExplicitParameters` schema for `StatusHandler` only validates presence/types of `sha`, `state`, etc., not repository ownership. `stacks`/`repository_name` are simply never invoked in this handler.

### Impact Explanation
A forged `Status` (e.g., `state: "success"`) is written onto a commit belonging to a repository/stack the attacker does not control. Since `Commit#deployable?` and CI-gating logic (`Commit#status`, `Commit#blocked?`, `Stack#continuous_deployment?`) consult `statuses`, this can make an otherwise CI-failing or CI-pending commit in the victim's stack appear deployable, or interfere with `ContinuousDeliveryJob`/merge scheduling (`stack.schedule_merges`). This is a payload from one repository mutating another repository's stack/commit records — matching the Critical category "a payload for one repository mutating another's stack, commit, task." It is repeatable against any commit SHA the attacker can reproduce/share with a victim stack (e.g., via fork history, cherry-picks, or any commit whose tree+parents+metadata the attacker can replicate) and is not limited to a single request.

### Likelihood Explanation
Preconditions: Shipit must be tracking the victim commit already (normal operation for any active stack), and the attacker needs a repository with the Shipit GitHub App installed and the ability to produce/reference a commit with an identical SHA to one already ingested by Shipit (trivially achievable via forking a public repo, which is the common case for OSS projects using Shipit, or reusing a shared merge-base commit). No Shipit session, API token, or secret is required — only ordinary GitHub repository ownership and the ability to trigger a `status` webhook for their own repo (e.g., via the GitHub Statuses API with their own token, or CI on their fork). This is low-cost and fully repeatable.

### Recommendation
Scope `StatusHandler#process` by repository the same way every other handler does: resolve `stacks` from `payload['repository']['full_name']` and restrict the commit lookup to `Commit.where(sha: params.sha, stack: stacks)` (or `stacks.flat_map(&:commits)...`), discarding matches on commits belonging to stacks not owned by the reporting repository.

### Proof of Concept
Minitest plan (no live GitHub):
```ruby
test "StatusHandler does not create a status for a commit belonging to an unrelated repository/stack" do
  victim_repository = shipit_repositories(:shipit) # or create Repository(owner: 'victim', name: 'repo')
  victim_stack = create_stack(repository: victim_repository)
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  end
end
```
Both sides of the equality before the fix: `payload['repository']['full_name']` = `"attacker/unrelated-repo"`, while the mutated commit's owning repository (`victim_commit.stack.repository.github_repo_name`) = `"victim/repo"` — they diverge, yet `victim_commit.statuses.count` still increases, proving the binding is broken. After applying the recommended `stacks`-scoped fix, the assertion `assert_no_difference` passes because the lookup is restricted to commits under `Repository.from_github_repo_name('attacker/unrelated-repo').stacks`, which does not include `victim_commit`.
