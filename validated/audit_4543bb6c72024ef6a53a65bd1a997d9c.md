Webhook signature verification is bound to the payload's `repository.owner.login`, not the repository whose stack is actually written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the `X-Hub-Signature` against using an **unverified** field taken directly from the still-unauthenticated request body (`repository.owner.login`), while the handlers that actually mutate state (e.g. `PushHandler`) resolve the target `Stack` using a **different** field from that same unverified body (`repository.full_name`). In Shipit's multi-organization mode, these two fields are never checked for consistency, so a signature valid for organization A's webhook secret is accepted as authorization to act on a stack belonging to organization B.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up a per-organization config (`app_id`, `webhook_secret`, `private_key`, ...) as documented for multi-org deployments: [2](#0-1) [3](#0-2) 

Signature verification only proves that the raw POST body was signed with *some organization's* configured `webhook_secret` — it does not bind that organization to the repository that the request will actually mutate. The `create` action then dispatches the raw, already-"verified" `params` (the entire unmodified body) to handlers: [4](#0-3) 

`PushHandler` resolves the target stacks using `repository.full_name`, a completely separate field from the one used in `verify_signature`: [5](#0-4) [6](#0-5) [7](#0-6) 

This is the same class of bug as the reported LST issue: a value that gates a security decision (`scalingFactor`/here, signature-org selection) is disconnected from the value that the protected action actually acts on (`priceReturn` target discount/here, the stack that gets synced). The check "verifies organization X's signature" is silently substituted for "authorizes writes to repository under organization X", when the payload's `full_name` can name an entirely different organization's repository.

### Impact Explanation
An attacker who legitimately administers Organization A's GitHub App integration in a multi-tenant Shipit deployment (and therefore knows Organization A's `webhook_secret`, since they configured that App) can forge an HTTP POST directly to the public `/webhooks` endpoint with:
- `repository.owner.login = "org-a"` (selects Org A's secret for signature verification)
- `repository.full_name = "org-b/victim-repo"` (used by the handler to find the actual `Stack`)
- a valid `X-Hub-Signature` computed with Org A's known `webhook_secret` over that exact crafted body

Because `verify_signature` never cross-checks that `repository_owner` (used to pick the secret) matches `repository.full_name`'s owner (used to pick the mutated `Stack`), the forged request passes verification and is processed as if it were a genuine GitHub-originated event for Organization B's repository — e.g. triggering `GithubSyncJob` for Org B's stack via `PushHandler#process` with attacker-chosen `ref`/`after` sha: [8](#0-7) 

This crosses a repository/organization trust boundary the signature is meant to enforce, letting an attacker who only controls Organization A's app credentials inject synthetic push/status/pull-request/membership events that mutate state for stacks belonging to Organization B, which they have no authorization over — a cross-repository write against the deployment-trust binding.

### Likelihood Explanation
This requires the Shipit deployment to be configured for multiple GitHub organizations (a supported, documented configuration) and requires the attacker to know one organization's `webhook_secret` — a credential that organization's own administrators legitimately possess, but which grants no explicit authorization over other organizations' stacks. No GitHub App private key, session, or `ApiClient` token is required; the `/webhooks` endpoint is unauthenticated by design and only gated by this signature check.

### Recommendation
In `WebhooksController#verify_signature`, after computing `repository_owner`, also derive the owner implied by `repository.full_name` (or whichever field each handler will key off), and reject the request (422) unless they match. Alternatively, resolve the target `Stack`/`Repository` strictly through the same organization used for signature verification (e.g., require `Repository.from_github_repo_name(...)`'s owner to equal `repository_owner` before dispatching to handlers), so the value that authorizes the request is the same value the request acts upon.

### Proof of Concept
1. Deploy Shipit in multi-org mode with orgs `org-a` and `org-b`, each with distinct `webhook_secret`s, per `docs/setup.md`.
2. As an administrator of `org-a` (who legitimately knows `org-a`'s `webhook_secret`), craft a JSON push payload:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, raw_body)>`.
4. `POST` this body with header `X-Github-Event: push` to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature using Org A's secret.
6. `PushHandler#process` resolves `Repository.from_github_repo_name("org-b/victim-repo")` and enqueues `GithubSyncJob` for Org B's stack with the attacker-supplied `after` sha, even though the attacker has no authorization over `org-b`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
