### Title
Missing balance-overflow check in `updateFinalAABalances` allows AA balance corruption and chain-halting `checkBalances()` panic - (File: aa_composer.js)

### Summary
`aa_composer.js` guards against AA balance overflow only at the point where a trigger's incoming payment is first credited (`updateInitialAABalances`), but the equivalent bookkeeping in `updateFinalAABalances` — which applies the deltas from an AA's own outgoing/consumed payment messages — performs the same unbounded `+=` arithmetic with **no overflow check at all**.

### Finding Description
`updateInitialAABalances` explicitly tracks a `bOverflow` flag and bounces the trigger if the resulting balance exceeds `MAX_BALANCE`, but only for MCIs `>= constants.pemCurvesFixMci`: [1](#0-0) 

The equivalent balance-update code for the AA's own consumed/produced payment outputs, `updateFinalAABalances`, applies deltas to `objValidationState.assocBalances[address][asset]` and to `byte_balance` with plain JS `+=`, and has **no** `MAX_BALANCE`/overflow check anywhere in the function: [2](#0-1) 

Because JS numbers are IEEE-754 doubles, once a stored `balance` (persisted as `BIGINT` in the `aa_balances` table, but manipulated in JS as a `Number`) grows past `Number.MAX_SAFE_INTEGER` (2^53-1), successive `balance=balance+?` SQL updates and the JS-side mirror in `objValidationState.assocBalances` silently lose precision and can diverge from each other (SQLite/MySQL `BIGINT` keeps exact integer arithmetic, JS `Number` does not beyond 2^53). This class of bug is directly analogous to the reported Cosmos SDK issue: unchecked additive arithmetic on a reward/balance accumulator that a normal (unprivileged) actor can grow arbitrarily by repeatedly sending payments/triggers to an AA, eventually overflowing/losing precision and corrupting consensus-critical state.

The downstream consequence is severe: `checkBalances()`, which runs periodically to reconcile `aa_balances` against actual UTXO outputs, `throw`s a hard `Error` on any mismatch that is not explainable by float precision within a `1e-5` relative tolerance: [3](#0-2) 

An uncaught balance mismatch beyond that tolerance is a synchronous `throw Error(...)` inside a `conn.query` callback, which is fatal for a Node.js process (uncaught exception ⇒ process crash) if not specifically wrapped by a domain/try-catch at a higher level. Since every full node runs this same deterministic logic against the same consensus data, any AA whose balance path exercises the uncovered `updateFinalAABalances` addition into the >2^53 range would deterministically crash every full node that processes that AA's activity — a network-wide chain halt, matching the CWE-190 bug class in the report.

### Impact Explanation
An attacker (any ordinary unit poster / AA trigger sender) can:
1. Deploy or use an existing AA that forwards/accumulates payments through `updateFinalAABalances`'s delta path (i.e., balances updated via consumed inputs/produced outputs rather than the initial trigger credit).
2. Repeatedly send triggers/payments driving that AA's per-asset balance up past `Number.MAX_SAFE_INTEGER` through many "good" transactions, none of which pass through the checked `updateInitialAABalances` overflow gate for that particular delta.
3. Once precision is lost, `checkBalances()` will detect the mismatch between DB `BIGINT` and cached in-memory/`aa_balances` double and `throw`, crashing full nodes running the periodic reconciliation job — a network unable to confirm new units (chain halt), and/or non-deterministic behavior since some nodes may hit floating-point rounding differently depending on operation order (`Math.round`, accumulated float error), causing consensus disagreement on AA balances/state.

This satisfies the "Validate" criteria: node disagreement on validity/stability, or a network unable to confirm new units.

### Likelihood Explanation
Reaching `MAX_BALANCE`/`Number.MAX_SAFE_INTEGER` (2^53 ≈ 9×10^15) requires a very large accumulated sum, which is economically expensive for the base asset (since `MAX_CAP`/`TOTAL_WHITEBYTES` for bytes is bounded well below this in practice), but is much easier for custom AA-issued assets with large or uncapped issuance amounts under attacker control (asset `cap` up to `constants.MAX_CAP`, and repeated AA-controlled issuance/transfer cycles). An attacker who controls both the AA definition (or interacts with an existing vulnerable AA) and the asset issuance can engineer the delta path in `updateFinalAABalances` to reach overflow more cheaply than through the guarded initial-trigger path. Likelihood is Medium: it requires deliberate construction (asset with large cap, or many trigger cycles) but no privileged network position — fully reachable by a standard AA trigger sender.

### Recommendation
Add the same `MAX_BALANCE` overflow check used in `updateInitialAABalances` to `updateFinalAABalances`, checking `objValidationState.assocBalances[address][asset]` and `byte_balance` after each `+=`, and bounce the trigger (or reject prior to committing) when any resulting balance exceeds `MAX_BALANCE`, gated consistently with `mci >= constants.pemCurvesFixMci` (or unconditionally going forward). Additionally, consider migrating `aa_balances` bookkeeping in JS to a big-integer/arbitrary-precision representation (or `BigInt`) to avoid silent precision loss before reaching `Number.MAX_SAFE_INTEGER`, rather than relying solely on a hard cap check.

### Proof of Concept
Conceptual PoC (cannot be executed without a live node, but derivable from code):
1. Define/deploy an AA that issues a very large capped asset (`cap` close to `constants.MAX_CAP`) to itself, or accepts repeated large transfers of an attacker-controlled asset.
2. Send a sequence of triggers/payments to the AA such that its outgoing/consumed payment messages processed in `sendUnit` → `updateFinalAABalances` repeatedly add large `assocDeltas[asset]` values to `objValidationState.assocBalances[address][asset]`, without ever routing through the checked `updateInitialAABalances` path for that specific delta.
3. Drive the cumulative balance for that asset past `Number.MAX_SAFE_INTEGER` (2^53-1).
4. Because `updateFinalAABalances` has no overflow guard [4](#0-3) , the trigger is accepted and `aa_balances.balance` (exact `BIGINT` in SQL) diverges from the JS-side double-precision mirror.
5. On the next periodic `checkBalances()` run, the SQL-vs-calculated comparison in `sql_balances_to_outputs`/`sql_outputs_to_balances` detects a discrepancy exceeding the `1e-5` relative-precision tolerance and executes `throw Error("checkBalances failed...")` [5](#0-4) , crashing every full node that runs this check — a chain-wide halt.

			if (!assocDeltas[output.asset])

			assocDeltas[output.asset] -= output.amount;
			// this might happen if there is another pending invocation of our AA that created the outputs we are spending now
			if (!objValidationState.assocBalances[address][output.asset])
				arrNewAssets.push(output.asset);
		});

			if (message.app !== 'payment')
				return;

			var asset = payload.asset || 'base';

				if (output.address !== address)
