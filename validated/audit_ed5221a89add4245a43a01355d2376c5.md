### Title
Webhook signature verification is bound to `repository.owner.login`, but event handlers act on the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` derives which GitHub organization's webhook secret to use for HMAC verification from `params.dig('repository','owner','login')` [1](#0-0) , but every event handler resolves the actual repository/stack to mutate from a *different* JSON path, `payload.dig('repository','full_name')` [2](#0-1) . Nothing enforces that these two attacker-supplied fields refer to the same repository. Combined with the fact that `verify_webhook_signature` unconditionally accepts the request whenever the resolved organization has no `webhook_secret` configured (`return true unless webhook_secret`) [3](#0-2) , this breaks the intended binding: "the organization that authenticated the request" == "the repository that is written."

### Finding Description
The `WebhooksController` is a public, unauthenticated Rails controller (`skip_before_action :verify_authenticity_token`, no session/API-client requirement) [4](#0-3) . Its only gate is `verify_signature`:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

`repository_owner` is read straight out of the attacker-controlled JSON body. It selects which per-organization `GitHubApp` (and therefore which `webhook_secret`) is used to validate the HMAC:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [3](#0-2) 

`webhook_secret` is populated from `@config[:webhook_secret].presence` [6](#0-5)  - i.e. it is an optional per-organization setting, and multi-organization configurations are an explicitly supported deployment shape (see the "double github app" fixture referenced by the config loader). If any organization configured in a Shipit instance omits `webhook_secret`, `verify_webhook_signature` returns `true` for *any* payload whose `repository.owner.login`/`organization.login` resolves to that organization, regardless of the actual HMAC header supplied.

Once past `verify_signature`, `create` dispatches the raw, unverified body to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [7](#0-6) 

Every handler (base `Handler#stacks`/`#repository_name`, `PushHandler#process`, and all `PullRequest::*Handler#repository`) resolves the target using `payload.dig('repository','full_name')` [2](#0-1) [8](#0-7)  - a field the attacker can set independently of `repository.owner.login`. `Repository.from_github_repo_name` looks up whatever `full_name` claims, and `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` acts on it directly, with no check that `full_name`'s owner segment equals `repository_owner`.

**Equality that should hold but doesn't:** organization whose `webhook_secret` authenticated the request == owner of the repository the handler subsequently mutates. Instead the code checks `repository.owner.login` for authentication and `repository.full_name` for the write target - two independently attacker-controlled fields in the same unauthenticated JSON body.

### Impact Explanation
An unauthenticated network attacker who knows (or targets) an organization in the Shipit configuration that has no `webhook_secret` set can send a forged `push` (or `pull_request`/`status`/`check_suite`) webhook with:
- `repository.owner.login` = the secret-less organization (so `verify_webhook_signature` short-circuits to `true`),
- `repository.full_name` = any other tracked repository/stack, including ones belonging to fully-secured organizations.

This lets the attacker drive `PushHandler` to call `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` on an arbitrary tracked stack, or drive `PullRequest` handlers to archive/unarchive review stacks, or forge `status`/`check_suite` events that mark an arbitrary commit as passing required CI checks. On stacks with `continuous_deployment` enabled and CI-based gating, forging a passing status for a specific commit can cause Shipit to autonomously trigger a deploy of that commit - i.e., an unauthorized deploy driven entirely by an unauthenticated request, which satisfies the "Critical - unauthorized deploy" bar. At minimum, it is a full authentication bypass of the webhook signature check for any repository, satisfying "High - unauthenticated write of stack state."

### Likelihood Explanation
Exploitability depends on the deployment having at least one configured GitHub organization without a `webhook_secret` (an optional, supported configuration state in `GitHubApp#initialize`) while other organizations/repos being targeted are otherwise fully protected. This is plausible in real multi-organization Shipit deployments (the codebase ships fixtures for multi-app/multi-org GitHub configuration), but I could not fully confirm from the indexed content whether any current production `secrets.yml` example leaves `webhook_secret` blank for a live org - this is a caveat on likelihood, not on the presence of the code-level flaw. Even without a secret-less org, the fundamental field-mismatch (auth on `repository.owner.login`, action on `repository.full_name`) remains a latent authorization-binding bug that a background agent should fix by validating the two fields match before dispatching.

### Recommendation
- In `WebhooksController#verify_signature`, after successful signature verification, explicitly re-derive and enforce that `params.dig('repository','owner','login')` matches the owner segment of `params.dig('repository','full_name')` before dispatching to handlers, rejecting mismatches with `422`.
- Require `webhook_secret` to be present for every configured GitHub organization (fail fast at boot/config-load time rather than silently allowing `return true unless webhook_secret`), removing the unauthenticated bypass path entirely.
- Consider deriving the authenticating organization solely from `repository.full_name` (the same field used by handlers) rather than a separate `repository.owner.login`/`organization.login` field, eliminating the two-field trust split.

### Proof of Concept
Given a Shipit instance with organizations `secure-org` (has `webhook_secret`) and `open-org` (no `webhook_secret` configured), and a tracked stack for `secure-org/victim-repo`:

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted

{
  "ref": "refs/heads/master",
  "after": "<sha attacker wants synced/deployed>",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secure-org/victim-repo"
  }
}
```

- `repository_owner` resolves to `"open-org"` [9](#0-8) .
- `Shipit.github(organization: "open-org").verify_webhook_signature(...)` returns `true` unconditionally because `open-org` has no `webhook_secret` [10](#0-9) .
- `PushHandler#process` resolves stacks via `payload.dig('repository','full_name')` = `"secure-org/victim-repo"` [2](#0-1)  and calls `stack.sync_github(expected_head_sha: "<attacker sha>")` [8](#0-7) , acting on `secure-org`'s protected stack despite the request only having "authenticated" as `open-org`.
