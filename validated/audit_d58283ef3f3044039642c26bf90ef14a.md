## Title
Membership webhook signature is verified against an attacker-chosen organization, letting an unprivileged actor join a privileged `Shipit.github_teams` team - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/secret to validate the webhook against using an organization login taken straight from the unauthenticated JSON body, not from any value that has already been cryptographically verified. Because the webhook secret is documented as optional per organization, any organization configured without a `webhook_secret` makes signature verification a no-op for requests that claim to originate from that organization. The `membership` event handler then uses another, independently-attacker-controlled field of the same body (`team.id`, `organization.login`) to add the attacker's GitHub login to an arbitrary existing `Team` row, bypassing the intended binding between "the organization whose signature was checked" and "the team/organization actually mutated."

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the raw, unverified payload and uses it to pick the `GithubApp` instance whose secret will validate the request: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

The setup documentation explicitly marks the webhook secret as optional, so an organization with no secret is an anticipated, documented configuration, not a misuse of the engine: [4](#0-3) 

Once `verify_signature` passes (trivially, for any body, as long as `organization.login`/`repository.owner.login` names an org with no secret), `WebhooksController#create` dispatches the full, still-unverified body to the registered handler for the event: [5](#0-4) 

For the `membership` event, `MembershipHandler#process` looks up (or creates) a `Team` purely by the attacker-supplied `team.id` (GitHub's numeric team id) — with no check that this team belongs to the organization that was actually signature-checked — and adds the attacker-controlled `member.login` to it: [6](#0-5) 

Team membership is exactly what gates access to the Shipit UI/API: `Authentication#force_github_authentication` requires `current_user.authorized?`, which is backed by membership in `Shipit.github_teams`: [7](#0-6) 

**Broken binding**: the organization whose webhook signature is checked (`repository_owner`, resolved from `organization.login` in the payload and matched against a possibly-secret-less `GithubApp`) is not equal to the `Team`/organization actually written by `MembershipHandler` (identified by attacker-supplied `team.id`). Because the two fields are independent parts of the same unauthenticated JSON body, an attacker can satisfy the first ("authenticate" as an org with no secret) while targeting the second (a real, privileged team belonging to a different, secured organization).

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization (explicitly listed High-impact category): an unprivileged external actor who can reach `/webhooks` can add their own GitHub login as a member of any `Team` row already known to Shipit (team IDs are GitHub-side integers, discoverable via the GitHub API for public teams/orgs the attacker can query, or already present in Shipit's DB from prior legitimate events), gaining `current_user.authorized?` on the real Shipit instance and thus full access to trigger deploys/rollbacks.

### Likelihood Explanation
Requires: (1) at least one organization configured in `Shipit.github` without a `webhook_secret` (explicitly supported/documented as optional), and (2) the attacker knowing/guessing the target `Team`'s GitHub `id`. Both conditions are plausible in real deployments that manage multiple organizations with mixed secret configuration, or in single-org setups where the operator omitted the optional secret. No session, API token, or repository write access is required — only network access to the public `/webhooks` endpoint.

### Recommendation
Bind the value used to select the verifying `GithubApp`/secret to the same value used by the handler to decide what gets mutated (e.g., require `MembershipHandler` to verify that the `Team`'s stored `organization` equals the `organization.login` that was actually signature-checked, and reject if they diverge, or refuse verification entirely for organizations lacking a configured secret instead of treating it as "always valid").

### Proof of Concept
1. Configure/observe that some organization `orgNoSecret` in `Shipit.github` has no `webhook_secret` (allowed by setup docs).
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": { "login": "orgNoSecret" },
  "team": { "id": <github_id of a real privileged Team>, "name": "Developers", "slug": "developers", "url": "https://example.com" },
  "member": { "login": "attacker-github-login" }
}
```
No valid `X-Hub-Signature` is required because `verify_webhook_signature` short-circuits to `true` for `orgNoSecret`.
3. `WebhooksController#verify_signature` passes; `MembershipHandler#process` finds the existing privileged `Team` by `team.id` and calls `team.add_member(User.find_or_create_by_login!('attacker-github-login'))`.
4. The attacker's user now passes `current_user.authorized?` and gains full Shipit access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
