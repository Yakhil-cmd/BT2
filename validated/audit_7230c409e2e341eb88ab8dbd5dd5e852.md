### Title
Webhook signature verification is keyed on attacker-controlled `repository.owner.login` while event routing trusts an independent `repository.full_name` field, letting a payload for one org's (unauthenticated) app bypass verification for a different org's tracked repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to check the `X-Hub-Signature` against based on `repository_owner`, a value read straight out of the untrusted JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). The actual routing of the event to a `Stack`/`Repository` in `Shipit::Webhooks::Handlers::Handler#repository_name` uses a *different* field from the same body: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so the organization whose signature is checked is not guaranteed to be the organization/repository the event is ultimately applied to. ### Finding Description
This is the analog of the Sherlock finding: the code checks one identity (`stake` in the original bug; here, the *organization* used to fetch the verifying `GitHubApp`) but acts on a different, independently-controlled identity (`asset`; here, the *repository* resolved via `full_name` for job dispatch). The binding that should hold is:

`organization authenticated by verify_webhook_signature == organization owning the repository that Webhooks::Handlers actually mutate`

but this equality is never enforced.

`Shipit.github(organization:)` looks up per-organization config from `secrets.github`, and each organization can independently be configured with an *optional* `webhook_secret` (documented as "Webhook secret (optional)" in `docs/setup.md`, and shown as blank in `config/secrets.development.example.yml`). Crucially, `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever no secret is configured for the org resolved from the payload: [4](#0-3) 

Because `repository_owner` is taken from the same JSON body the attacker fully controls, and it only selects the app used to compute/verify the HMAC (not the one whose secret was actually used to sign the real GitHub-originated request), an attacker can submit a forged webhook body where:
- `repository.owner.login` = an organization configured in this multi-org Shipit instance with a blank/absent `webhook_secret` (a documented, valid configuration per `docs/setup.md` "Using Multiple Github Applications"), causing `verify_webhook_signature` to trivially return `true`, while
- `repository.full_name` = the full name of a *different*, protected/tracked repository (belonging to an organization that does have a `webhook_secret` configured).

`Shipit.github(organization: repository_owner)` resolves per the case-insensitive lookup in `github_app_config`, which is driven entirely by attacker input: [5](#0-4) 

The downstream handler (`PushHandler`, or any other registered handler) never re-checks `repository.owner.login` against the org whose secret validated the request — it resolves the target purely via `repository_name`/`full_name`: [6](#0-5) [3](#0-2) 

The result: signature verification is bound to a field the handler does not act on, and the handler acts on a field the signature never covers.

### Impact Explanation
Once verification is bypassed this way, an unauthenticated attacker can inject arbitrary forged `push`, `status`, `check_suite`, `pull_request`, or `membership` events targeting *any* repository/stack tracked by the Shipit instance, not just repositories under the weakly-configured org. Notably:
- Forged `push` events trigger `GithubSyncJob`, which fetches and appends commits from GitHub for the targeted stack using the app's own GitHub credentials, and can trigger `CacheDeploySpecJob` — an unauthorized/attacker-influenced sync of a stack that the attacker does not control.
- Forged `status`/`check_suite` events can flip commit deployability signals used to gate deploys, potentially enabling an unauthorized deploy to proceed on a stack the attacker has no legitimate access to.
- Forged `membership` events can create/delete `Team`/`Membership` records tied to `Shipit.github_teams` authorization, which is explicitly called out as a High-severity impact category (escalation into `Shipit.github_teams` authorization).

This satisfies the required impact bar: unauthorized deploy/rollback triggering and escalation into `Shipit.github_teams` authorization, achieved purely as an unauthenticated network attacker with no session, no `ApiClient` token, and no repository write access — only knowledge that the target Shipit instance is a multi-org deployment with at least one configured organization lacking a `webhook_secret`.

### Likelihood Explanation
The vulnerability requires the operator to have configured multi-organization GitHub Apps (`config/secrets.github` keyed by organization, per `docs/setup.md` "Using Multiple Github Applications") with at least one organization's `webhook_secret` left blank — an option explicitly presented as valid ("Webhook secret (optional)") rather than a misconfiguration. Any organization onboarded to a shared Shipit instance without configuring a webhook secret becomes a skeleton key for spoofing events against every other organization's repositories tracked by that same instance, because the single `/webhooks` endpoint routes all organizations' events through one shared `WebhooksController`. No credentials, tokens, or elevated GitHub permissions are needed — only that the attacker knows the (public) `full_name` of the target repository and the (also public, since it's the attacker's own or any known) `login` of an org with no configured secret.

### Recommendation
Do not let `repository.owner.login`/`organization.login` (used to select the verifying app) diverge from the identity actually acted upon:
- After signature verification succeeds, re-derive the organization owning `payload.dig('repository', 'full_name')` (e.g., via the `Repository` record already resolved by the handler) and require it to equal `repository_owner`/the org whose secret validated the signature, rejecting the event otherwise.
- Treat a missing `webhook_secret` for one organization as authorizing only events whose `repository.full_name` belongs to that same organization — never allow an app with no configured secret to implicitly vouch for events referencing repositories under a different, secret-protected organization.
- Consider making `webhook_secret` mandatory in multi-org configurations, since its absence undermines the security boundary the multi-tenant design (`docs/setup.md`, `TOP_LEVEL_GH_KEYS`) otherwise relies on.

### Proof of Concept
1. Operate (or find) a Shipit instance configured with multiple GitHub organizations in `secrets.github`, where organization `weak-org` has `webhook_secret` unset/blank, and organization `victim-org` (with repo `victim-org/protected-repo`, tracked by an existing `Stack`) has a real `webhook_secret` configured.
2. Craft a forged `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha that exists on GitHub>",
  "repository": {
    "full_name": "victim-org/protected-repo",
    "owner": { "login": "weak-org" }
  }
}
```
3. Send it to `POST /webhooks` with header `X-Github-Event: push` and any (or no) `X-Hub-Signature`.
4. `verify_signature` calls `Shipit.github(organization: "weak-org")`, resolves `weak-org`'s config (no `webhook_secret`), and `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb:76-77`.
5. `create` proceeds, `Shipit::Webhooks.for_event('push')` dispatches to `Handlers::PushHandler`, which resolves the target via `payload.dig('repository', 'full_name')` = `"victim-org/protected-repo"`, matching the real, secret-protected stack, and enqueues `GithubSyncJob` for it — despite the request never being authenticated against `victim-org`'s secret at all.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
