### Title
Missing enforcement that `cap` matches the sum of `denominations` in AA-defined assets, allowing declared asset cap to be bypassed — ([File: aa_validation.js])

### Summary
When a normal (non-AA) unit defines an asset, `validateAssetDefinition` in `validation.js` enforces that a capped, fixed-denomination asset's `cap` field must equal the sum of `count_coins * denomination` across all declared `denominations`, and rejects mismatches between capped/uncapped denominations and the `cap` field. When an Autonomous Agent (AA) template defines an `asset` message (the `case 'asset':` branch of `validateAADefinition` in `aa_validation.js`), this exact same cross-field invariant is never checked, even though the AA path independently validates the individual fields (`cap` format, `denominations` format) that the invariant depends on.

### Finding Description
In `validation.js`, `validateAssetDefinition` (used for regular, human-authored `asset` messages) computes `total_cap_from_denominations` from the `denominations` array and enforces: [1](#0-0) 
- uncapped and capped denominations cannot be mixed with a `cap`,
- `cap` must be present if any denomination is capped,
- and critically: `total_cap_from_denominations && payload.cap !== total_cap_from_denominations` is rejected — i.e., `cap` must exactly equal the sum of all `count_coins * denomination`.

In `aa_validation.js`, the analogous `case 'asset':` branch of `validateAADefinition` — which validates asset-definition messages emitted from AA templates (bytecode executed deterministically by every AA when triggered) — validates: [2](#0-1) 
that `cap` is a valid positive integer or formula, and separately validates the *format* of each `denominations` entry via `validateDenominations`: [3](#0-2) 
(checking `denomination` and `count_coins` are individually well-formed), but **at no point cross-checks that the sum of `count_coins * denomination` equals `payload.cap`**, nor that uncapped denominations are disallowed when `cap` is present. The rest of the AA `asset` case (lines 289–336) only checks `issue_condition`/`transfer_condition` shape, `cosigned_by_definer`, `issued_by_definer_only` combinations, and boolean/formula typing of other flags — none of it restores the missing cap/denominations consistency check.

Because AA-defined asset messages are written verbatim (after formula evaluation) into the `assets` and `asset_denominations` tables by `writer.js`: [4](#0-3) 
the actual mintable supply of a fixed-denomination asset is governed by the `asset_denominations.count_coins` rows (consumed by `indivisible_asset.js`'s coin-issuance logic keyed on `count_coins`/`max_issued_serial_number`), not by the `cap` field itself. The `cap` field is only used elsewhere as a signal that the asset is "capped" (e.g., to restrict `serial_number` to 1 in `validation.js`'s issue-input validation) and as a value that downstream consumers — wallets, oscript/definition conditions referencing `cap`, block explorers, and third-party tooling — trust as the authoritative maximum supply of the asset.

Since an AA author fully controls the AA template (an oscript program), they can define an asset with, e.g., `cap: 100` and `denominations: [{denomination: 1, count_coins: 1000000}]`. This message passes `validateAADefinition` unmodified (the same gap exists whether the values are literals or formulas whose evaluated values are checked nowhere against each other), and gets accepted into the ledger with a `cap` of 100 while the real issuable supply is 1,000,000 units — a 10,000x inflation relative to the value everyone is expected to trust as the cap.

### Impact Explanation
This breaks the security invariant that `cap` bounds an asset's total supply for AA-issued fixed-denomination (indivisible) assets — an invariant enforced for non-AA-authored assets but silently unenforced for AA-authored ones. Any AA, address definition (`'has'`, `'sum'`, `'seen'` filters), or external system that treats the recorded `cap` as an upper bound on total supply (e.g., logic assuming `total_supply <= cap` when reasoning about asset scarcity, collateral, or fair-launch guarantees) can be deceived, and the actual circulating supply of the asset can exceed its advertised cap — a concrete supply-inflation outcome for the affected asset. This mirrors the analog bug class: a required cross-field constraint (`maxFee`/`ttl` == 0 in the original report) is checked in one code path but silently dropped in the parallel path that handles the same message type from an automated/agent-driven origin, letting invalid parameter combinations reach the point where they produce financial consequences.

### Likelihood Explanation
Any AA author can trivially craft an `asset` message inside an AA template with a `cap` that does not match `denominations`; no special privileges or race conditions are required, and the deterministic AA execution model means every node accepts the identical (invalid) definition without disagreement. The barrier is only that the attacker/AA author must want to define such an asset — a low bar, since deceiving downstream consumers of `cap` is directly incentivized (e.g., to imply scarcity while retaining large mint capacity).

### Recommendation
Add the same cross-field validation used in `validation.js`'s `validateAssetDefinition` to `aa_validation.js`'s `case 'asset':` branch: reject the definition if `fixed_denominations` denominations are a mix of capped/uncapped entries inconsistent with `cap`, and require `sum(count_coins * denomination) === cap` whenever `cap` is a literal number and denominations are literal (non-formula) values. Where `cap` or `denominations` are formulas (evaluated only at trigger time), perform the equivalent check post-evaluation, before the resulting `asset` message is accepted into `assets`/`asset_denominations` (e.g., in `aa_composer.js`'s message-completion pipeline, alongside the existing `sortDenominations` handling), mirroring the guard that already exists for non-AA-authored assets.

### Proof of Concept
1. Deploy an AA whose template includes (conceptually, mirroring `test/samples/create_an_asset.oscript`):
```
{
  app: 'asset',
  payload: {
    cap: 100,
    is_private: false,
    is_transferrable: true,
    auto_destroy: false,
    fixed_denominations: true,
    issued_by_definer_only: true,
    cosigned_by_definer: false,
    spender_attested: false,
    denominations: [{ denomination: 1, count_coins: 1000000 }]
  }
}
```
2. Trigger the AA to emit this `asset` message. `validateAADefinition`'s `case 'asset':` accepts it (no check that `100 !== 1 * 1000000`). [5](#0-4) 
3. The asset is written with `cap = 100` in `assets` and `count_coins = 1000000` at denomination 1 in `asset_denominations`. [4](#0-3) 
4. Subsequent issuance of this asset (via `indivisible_asset.js`) can mint up to 1,000,000 units even though the recorded `cap` is 100, defeating any downstream logic that treats `cap` as the true maximum supply.

Note: I was not able to fully trace every downstream consumer that treats `cap` as an authoritative supply bound (this would require deeper review of wallet/UI and third-party integrations, which are outside the indexed core validation/consensus code), so the precise financial blast radius depends on which components rely on `cap` equalling total issuable supply. The core validation gap itself — the absent cross-check present in the non-AA path but missing in the AA path — is confirmed directly in `aa_validation.js` and `validation.js`.
