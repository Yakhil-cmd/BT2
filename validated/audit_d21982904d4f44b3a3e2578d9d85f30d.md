## Analysis

The escrow feature in this codebase is the arbiter-contract shared address created by `deriveSharedAddress()` in `arbiter_contract.js`. Its definition is fully deterministic and, once created, is a permanent on-chain address — an escrow "instance" is not disposable after settlement.

For the dispute-resolution branches of the definition (both the public-asset "arbiter decides" branch and the private-asset "counterparty confirms" branch), the release condition is a bare `["in data feed", ...]` check with no accompanying `has output` restriction and no `min_mci` upper bound tied to the specific payment:

```
["and", [
    ["address", offeror_address],
    ["in data feed", [[contract.arbiter_address], "CONTRACT_" + contract.hash, "=", offeror_address]]
]],
``` [1](#0-0) 

and for private assets:
```
arrDefinition[1][1] = ["and", [
    ["address", offeror_address],
    ["in data feed", [[acceptor_address], "CONTRACT_DONE_" + contract.hash, "=", offeror_address]]
]];
``` [2](#0-1) 

By contrast, the non-disputed "has output" branches were explicitly hardened by the developers against a reuse/combination attack, adding a `not has input from other address` guard so that combining several contracts in one transaction cannot let an attacker redirect the change:
```
// protect against combining several contracts in a single transaction (if their parties, amounts, and assets are identical, the 'has what' above would satisfy both contracts, allowing the attacker to send the change to themselves)
arrDefinition[1][1][1].push(["not", ["has", {what: "input", asset: contract.asset || "base", address: "other address"}]]);
``` [3](#0-2) 

No equivalent protection or amount/one-time binding exists for the `in data feed` branches. Once the arbiter (or, for private assets, the counterparty) posts the `CONTRACT_<hash>` / `CONTRACT_DONE_<hash>` data feed value, that fact is permanently recorded and stable on the DAG (`readDataFeedValueByParams`/`dataFeedExists` simply look for any stable unit matching the feed name/value with no upper MCI bound tied to a single settlement event) [4](#0-3) [5](#0-4) . This means the shared address's authorization to the named winner is not "spent" or otherwise invalidated once the original escrow amount is withdrawn — it remains valid forever for that address, unrestricted in the amount it can move, because the condition does not require any matching `has output` clause the way the ordinary "has output" completion branches do.

### Title
Arbiter/prosaic-contract escrow shared addresses remain permanently spendable by the dispute winner after settlement, allowing reuse/drain of later deposits - (File: arbiter_contract.js)

### Summary
`deriveSharedAddress()` builds the dispute-resolution branches of an escrow's shared-address definition using only `["address", X], ["in data feed", ...]`, with no `has output` binding and no expiry tied to the original escrow amount, unlike the "has output" branches which the code explicitly protects against multi-contract reuse.

### Finding Description
Each arbiter escrow is a smart address whose spending conditions are computed once in `deriveSharedAddress()` and never change on-chain [6](#0-5) . Two of its five OR-branches (public-asset arbiter verdict, and private-asset "CONTRACT_DONE" branch) authorize the winning party to spend from the address purely based on the presence of a stable data-feed value, without any accompanying constraint that ties the authorized spend to the specific escrowed `contract.amount`, and without any upper bound (`min_mci`) that would confine the authorization to the original round of funding [7](#0-6) . Because a data feed's truth is permanent once stable, this authorization never expires. In contrast, the "has output" completion branches were specifically patched to prevent an attacker from reusing/combining escrow logic across transactions [3](#0-2) , showing the maintainers recognized this exact bug class for one branch but left the data-feed branches unprotected. The shared address itself is a normal DAG address that anyone can send funds to at any time, independent of the wallet software's own state machine (`pay()`/`complete()` only guard the local DB `status` column, not the on-chain address) [8](#0-7) .

### Impact Explanation
After a dispute is resolved (or a private-asset contract is marked done) and the arbiter/counterparty posts the winner's data feed value, the already-declared winner permanently retains the ability to unilaterally sweep any balance subsequently present at that same shared address, with no further arbiter, cosigner, or counterparty action required and no relation to the original contract amount. If the same address is reused for any reason (accidental re-payment, front-run donation, secondary business use, or a wallet-UI reuse mistake), those additional funds can be stolen by the previously declared winner outright. This is unauthorized spending / fund loss for one of the escrow counterparties.

### Likelihood Explanation
Exploitation requires no privileged access — it only requires that funds land again at an already-resolved escrow shared address, which is entirely plausible in normal usage patterns (repeat business with the same counterparty/arbiter pairing generating identical addresses would not happen since `contract.hash` is embedded, but any accidental or naive resend by the losing/paying party to the historical address is sufficient). Since ordinary users interact with these addresses via copy-pasted addresses/QR codes long after settlement, likelihood of accidental fund loss is realistic, and an attacker (the previously declared winner) needs to do nothing but wait and then spend.

### Recommendation
Bind the dispute-resolution branches to the same "has output" pattern already used for the non-disputed completion branches (i.e., require the current unit to include an output of exactly `contract.amount` to the winner, and add the `not has input from other address` guard), or add a `min_mci`/one-shot mechanism (e.g., requiring the spend to also consume a specific marker output only present in the original funding unit) so that the data-feed authorization cannot be re-used to sweep unrelated, later deposits to the same address.

### Proof of Concept
1. Alice and Bob create an arbiter contract; shared address `S` is derived via `deriveSharedAddress` with dispute-resolution branches keyed to `CONTRACT_<hash>` [9](#0-8) .
2. Alice pays escrow amount to `S`; a dispute occurs; arbiter posts data feed `CONTRACT_<hash> = Bob`. Bob calls `complete()` and withdraws the escrowed amount [10](#0-9) .
3. Months later, Alice (or anyone) sends additional bytes to address `S` (e.g., mistakenly reusing a saved address, or intentionally donating).
4. Bob composes a new unit spending from `S` using the still-valid `["in data feed", [[arbiter], "CONTRACT_<hash>", "=", Bob]]` branch; validation succeeds because the data feed value is permanently stable, with no requirement that this spend match the original `contract.amount` or occur only once.
5. Bob drains the newly deposited funds without any new dispute, arbiter action, or Alice's consent.

function pay(hash, walletInstance, arrSigningDeviceAddresses, cb) {
	getByHash(hash, function(objContract) {
		if (!objContract.shared_address || objContract.status !== "signed" || !objContract.me_is_payer)
			return cb("contract can't be paid");
		var opts = {
			asset: objContract.asset,
			to_address: objContract.shared_address,
			amount: objContract.amount,
			spend_unconfirmed: walletInstance.spendUnconfirmed ? 'all' : 'own'
		};
		if (arrSigningDeviceAddresses.length)
			opts.arrSigningDeviceAddresses = arrSigningDeviceAddresses;
		walletInstance.sendMultiPayment(opts, function(err, unit){								
			if (err)
				return cb(err);
			setField(objContract.hash, "status", "paid", function(objContract){
				cb(null, objContract, unit);
			});
			// listen for peer announce to withdraw funds
			storage.readAssetInfo(db, objContract.asset, function(assetInfo) {
				if (assetInfo && assetInfo.is_private)
					db.query("INSERT "+db.getIgnore()+" INTO my_watched_addresses (address) VALUES (?)", [objContract.peer_address]);
			});
		});
	});
}
