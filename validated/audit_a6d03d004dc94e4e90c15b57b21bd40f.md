### Title
Webhook signature verification selects the GitHub App/secret from an unauthenticated `repository.owner.login` (or `organization.login`) field that is never cross-checked against the `repository.full_name` the handlers act on, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to validate a payload's HMAC signature against by reading `repository.owner.login` / `organization.login` straight out of the *unverified* JSON body, before any signature has been checked [1](#0-0) . The same request body's `repository.full_name`/`repository.owner`/`organization` values are subsequently used by event handlers (e.g. push/status/membership) to decide which `Stack`/`Repository`/`Team` record to mutate. Nothing in the controller enforces that the organization used to select the verifying secret is the same organization whose repository actually gets written to.

### Finding Description
The binding that should hold is: *the organization whose secret authenticated the request* == *the organization/repository the handler subsequently writes to*. This is broken because:

1. `repository_owner` is computed purely from attacker-suppliable JSON, prior to signature verification: [2](#0-1) 

2. That value is used to fetch a per-organization `GitHubApp` instance and check the signature only against that organization's `webhook_secret`: [1](#0-0) 

3. `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank/not configured — a documented, supported configuration (see `docs/setup.md` and the multi-org fixture `test/dummy/config/secrets_double_github_app.yml`, which sets `webhook_secret: # nil` for both `OrgOne` and `OrgTwo`): [3](#0-2) 

4. Once `verify_signature` passes, `WebhooksController#create` parses the raw body again and dispatches it to the registered handler for the event type, keyed only on the `X-Github-Event` header — not on the organization used for verification: [4](#0-3) 

5. Handlers (e.g. the push handler) locate the target `Stack`/`Repository` using the `repository` object's own `full_name`/owner+name fields in the body — independent JSON keys from the ones used in step 1. The test suite confirms unknown/mismatched `repository.full_name` values are simply looked up against existing stacks (`test/controllers/webhooks_controller_test.rb`, "create github repository which is not yet present in the datastore" and ":push with the target branch queues a GithubSyncJob") [5](#0-4) .

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used by the handler to pick the target stack) are two independently-controlled fields in the same unauthenticated POST body, an attacker can set them to different organizations. If the Shipit instance hosts multiple GitHub Apps/organizations (a supported topology per `docs/setup.md`'s "Using Multiple Github Applications" section) and any one of them has no `webhook_secret` configured — or the attacker otherwise knows one org's secret — the attacker can craft a request that "authenticates" as that low-value/unsecured organization while `repository.full_name` (and thus the record actually mutated) points at a completely different, victim organization's stack.

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written," directly matching the analog category called out in scope. A successful forgery lets an unprivileged, unauthenticated network attacker inject arbitrary webhook events (`push`, `status`, `check_suite`, `membership`, etc.) that get processed as if they came from GitHub for a repository/organization the attacker has no relationship with — causing cross-repository writes (fake commits appended to a victim `Stack`'s history via `GithubSyncJob`, spurious CI `Status`/`CheckRun` records, or bogus `Team`/`User` membership records) without ever needing a Shipit session, `ApiClient` token, or the victim organization's real `webhook_secret`.

### Likelihood Explanation
The `/webhooks` endpoint is intentionally public and unauthenticated apart from this signature check, so no prior access is required to reach it. The only precondition is that the Shipit deployment hosts (or has ever hosted) more than one GitHub organization/app, with at least one org lacking a configured `webhook_secret` (an explicitly documented and tested configuration) or with an org whose secret the attacker can otherwise obtain (e.g. their own GitHub App installation added to the same Shipit instance). This is a realistic and intended-supported multi-tenant setup, not a hypothetical misconfiguration.

### Recommendation
After successfully verifying the signature for `repository_owner`, re-derive and assert that the organization embedded in `repository.full_name` (or the `organization` object used by the actual handler) matches the organization that authenticated the request; reject the request otherwise. Additionally, treat a missing `webhook_secret` as "reject all webhooks for this organization" rather than "accept unconditionally," or require an explicit opt-in flag to allow unsigned webhooks for a given organization.

### Proof of Concept
Note: the following describes the request-crafting logic derivable from the code inspected; full end-to-end execution against a running instance (to confirm the exact field names consumed by `push_handler.rb`) could not be completed within the available tool budget and should be verified interactively.

1. Configure/observe a Shipit instance hosting two GitHub orgs, `OrgUnsecured` (no `webhook_secret` set, as in `test/dummy/config/secrets_double_github_app.yml`) and `VictimOrg` (has a real `webhook_secret`, holding a `Stack` the attacker wants to tamper with).
2. POST to `/webhooks` with header `X-Github-Event: push` and no/garbage `X-Hub-Signature`, and a JSON body:
```json
{
  "repository": {
    "owner": { "login": "OrgUnsecured" },
    "full_name": "VictimOrg/victim-repo"
  },
  "after": "<attacker-chosen sha>"
}
```
3. `repository_owner` resolves to `"OrgUnsecured"`; `Shipit.github(organization: "OrgUnsecured").verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank, per `lib/shipit/github_app.rb`.
4. The request reaches `create`, and the push handler is invoked with a body whose `repository.full_name` names `VictimOrg/victim-repo`, causing it to operate on `VictimOrg`'s stack despite the signature never being checked against `VictimOrg`'s secret.

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
