## Title
CCMenu token issued for one stack authorizes reading build state of every stack - (File: `app/controllers/shipit/ccmenu_url_controller.rb`)

### Summary
The CCMenu URL feature mints an `ApiClient` token intended to expose the CI status of a single stack to third-party build-radiator tools. The token it hands out is never bound to the stack the caller requested it for, so once the token leaks (which is expected for this feature — CCMenu/CCTray URLs are routinely embedded in public build dashboards) it can be replayed against `Api::CCMenuController#show` with any other stack's `stack_id`, exposing build name/status/label/URL for stacks the token was never meant to touch. This is the same class of bug as the Hop report: a credential that is supposed to be scoped to one target is honoured for any target.

### Finding Description
`CCMenuUrlController#fetch` generates the token used in the public CCMenu URL: [1](#0-0) 

The client is looked up/created keyed only by `creator` and a fixed `name: 'CCMenu Client'` — it never records which `stack` the request was for:

```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```

Because `find_or_create_by!` doesn't set the `stack` attribute, `ApiClient#stack_id` stays `nil` for every user's single shared "CCMenu Client" record, regardless of how many stacks that user requests CCMenu URLs for.

The API-side authorization binds "what the client is authorized to read" to `current_api_client.stack_id`: [2](#0-1) 

`current_api_client.stack_id?` returns `false` when `stack_id` is `nil`, so `stacks` degrades to `Stack.all` — the token is treated as globally scoped rather than restricted to the one stack the URL was generated for. `Api::CCMenuController` also authenticates via the raw `token` query param and resolves the stack straight from `params[:stack_id]`: [3](#0-2) 

So the binding that should hold — "stack the token was issued/authorized for" == "stack the token can be used to read" — is broken: the token authorizes exactly one stack's CCMenu URL at issuance time, but touches (and reads status for) every stack in the installation for the lifetime of the token.

### Impact Explanation
CCMenu/CCTray URLs are explicitly designed to be embedded in third-party or semi-public build-status dashboards (that's the entire purpose of the feature — see `app/controllers/shipit/ccmenu_url_controller.rb` and the XML CCMenu format rendered in `app/views/shipit/ccmenu/project`). Anyone who obtains one such leaked URL/token — e.g., from a build radiator screen, a shared dashboard config, or a forwarded link — can swap the `stack_id` segment of the path and use the same token to pull build name, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` for any other stack tracked by the Shipit instance, including stacks/environments the token holder was never granted visibility into. This is an unauthorized read of stack state across repository/environment boundaries, matching the High-impact category "unauthenticated [i.e., scope-violating] read of stack state."

### Likelihood Explanation
Likelihood is high: no privileged Shipit session or GitHub credentials are required, only possession of any single previously-issued CCMenu token (a routine, intentionally-shared artifact for this feature). The attacker only needs to know or guess another stack's `owner/repo/environment` path (visible in the Shipit UI/URLs generally, or enumerable) and substitute it into the existing token's request.

### Recommendation
Scope the CCMenu `ApiClient` to the specific stack it was generated for, and enforce that scope server-side:

```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client', stack: stack)
end
```

Additionally, `Api::CCMenuController#stack` (and the general `stacks`-scoping bypass pattern in `Api::CCMenuController`/`ccmenu_url_controller.rb` that resolve `Stack.from_param!` unscoped) should route through the same `current_api_client.stack_id`-aware `stacks` scope used in `Api::BaseController`, so a stack-bound token can never resolve a different stack even if a client record predates the fix.

### Proof of Concept
1. User A visits Shipit and generates a CCMenu URL for `stack_a` via `GET /ccmenu/owner/repo-a/production` → `CCMenuUrlController#fetch` returns `https://shipit.example.com/api/stacks/owner/repo-a/production/ccmenu?token=<T>`.
2. This URL is embedded in a shared/public build-radiator dashboard, as intended by the feature.
3. An attacker who can see that URL (a viewer of the dashboard, or someone who found it in a config) copies the token `T` and requests: `GET /api/stacks/owner/OTHER-REPO/staging/ccmenu?token=<T>`.
4. `Api::CCMenuController#authenticate_api_client` accepts `T` (still valid, still has `read:stack` permission, `stack_id` is `nil` so no restriction applies), `stack` resolves `owner/OTHER-REPO/staging` unscoped, and the response reveals that stack's build name, status, and last-build metadata — a stack User A's token was never intended to expose.
