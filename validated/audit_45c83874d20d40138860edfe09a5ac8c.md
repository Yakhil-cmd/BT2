## Title
Sensitive `wallet_arbiter_contracts` row (pairing secrets, cosigner list) broadcast unfiltered to cosigner devices - ([File: arbiter_contract.js])

### Summary
`arbiter_contract.js` fetches the *entire* `wallet_arbiter_contracts` DB row via `getByHash()`/`SELECT *` and forwards it verbatim to other devices in two code paths (`shareContractToCosigners` and `shareUpdateToCosigners`), unlike the sibling `createAndSend()` function, which explicitly deletes the sensitive `cosigners` field before sending the same kind of object to the contract peer. Because the "sanitize-before-send" step is missing from the cosigner-sharing paths, private/bearer-credential fields (`my_pairing_code`, `peer_pairing_code`, `peer_contact_info`, `cosigners`, `arbstore_address`, `arbstore_device_address`) leak to parties that were never meant to receive them — mirroring the CVE pattern where a single object mixing public and server-only data was reused in a code path that lacked the filtering applied elsewhere.

### Finding Description
`createAndSend()` demonstrates that the developers are aware `cosigners` (and by extension other internal-only fields) must not be sent to external devices: [1](#0-0) 

However, `shareContractToCosigners()` reads the full row with `getByHash()` (`SELECT * FROM wallet_arbiter_contracts WHERE hash=?`, decoded by `decodeRow`) and sends the **unfiltered** object to every cosigner device address: [2](#0-1) 

`getByHash`/`getBySharedAddress` return the raw row, including `my_pairing_code`, `peer_pairing_code`, `peer_contact_info`, `arbstore_address`, `arbstore_device_address`, and `cosigners`: [3](#0-2) 

`my_pairing_code`/`peer_pairing_code` are permanent pairing codes of the form `device_pubkey@hub#pairing_secret`, generated in `respond()`/`createAndSend()` via `device.getOrGeneratePermanentPairingInfo`: [4](#0-3) 

A pairing secret is a bearer credential: any device that knows it can pair as a correspondent without further authorization, as implemented in `device.js`’s `handlePairingMessage`, which accepts any device presenting a matching `pairing_secret`: [5](#0-4) 

The single-field sharing helper has the same problem: `setField()` explicitly whitelists `peer_pairing_code` and `cosigners` as shareable fields and calls `shareUpdateToCosigners`, which sends `{hash, field, value: objContract[field]}` straight to every cosigner device address with no filtering of what that value represents: [6](#0-5) [7](#0-6) 

`shareContractToCosigners` is invoked as soon as the counterparty accepts the contract (`respond("accepted", …)`) and again after the shared address is created, i.e. it is triggered by the remote contract counterparty’s own action: [8](#0-7) [9](#0-8) 

### Impact Explanation
When a contract counterparty (an unprivileged, potentially malicious paired device) accepts/responds to an arbiter contract, the local node broadcasts the full contract row — including the counterparty's own `peer_pairing_code`/`peer_contact_info` and its own `my_pairing_code` and the internal `cosigners` device-address list — to every cosigner of its own multisig wallet address. Any cosigner who receives this leaked permanent pairing secret can subsequently pair with the counterparty's device (or the user's own device) without consent, exposing correspondent relationships and enabling further social-engineering/impersonation against the wallet's users. This is a confidentiality breach of device-pairing credentials and wallet topology data — an unauthorized-disclosure impact analogous to the CVE's leaked `workerConfig` credentials, though it does not directly enable fund theft on its own.

### Likelihood Explanation
The leak is triggered automatically as part of the normal arbiter-contract acceptance/response flow, with no special conditions required beyond a legitimate multisig wallet cosigner relationship and a counterparty who accepts or updates the contract. No malicious network position or privileged access is needed — only a standard paired-device interaction that is part of the arbiter-contract feature's expected usage.

### Recommendation
Sanitize the contract object before broadcasting it to cosigners the same way `createAndSend()` sanitizes it before sending to the peer: strip `my_pairing_code`, `peer_pairing_code`, `peer_contact_info`, `arbstore_address`, `arbstore_device_address`, and `cosigners` (or any field not strictly required by cosigners to render the contract UI) from the object passed to `device.sendMessageToDevice(..., "arbiter_contract_shared", objContract)` in `shareContractToCosigners()`. Additionally, restrict the whitelist in `setField`/`shareUpdateToCosigners` so that credential-like fields (`peer_pairing_code`, `cosigners`) are never relayed to cosigners verbatim.

### Proof of Concept
1. Device A (attacker) and Device B (victim) exchange an arbiter contract; B has a multisig wallet address with cosigner Device C.
2. A calls `respond(hash, "accepted", signedMessage, signer, cb)` on its own side or otherwise triggers the offer/accept flow, causing B to run `respond()` → `setField(..., "status", "accepted", ...)` → `shareContractToCosigners(hash)`.
3. B's `shareContractToCosigners` sends the *entire* `wallet_arbiter_contracts` row for this contract — including `my_pairing_code` (B's permanent pairing secret) and `peer_pairing_code`/`peer_contact_info` (A's pairing secret/contact info, if already exchanged) — to cosigner C via `device.sendMessageToDevice(C, "arbiter_contract_shared", objContract)`.
4. C now possesses A's and/or B's permanent pairing secrets and can use them via `handlePairingMessage` to pair as a correspondent device with A or B without their knowledge, confirming the confidentiality breach.
