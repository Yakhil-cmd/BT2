### Title
Webhook signature verification is scoped by `repository.owner.login` while `OpenedHandler` mutates state scoped by the independent `repository.full_name` field, allowing a no-secret org's payload to write to another org's repository - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to check against using `params.dig('repository','owner','login')`, and `GitHubApp#verify_webhook_signature` trivially returns `true` when that org has no configured secret. Because `repository.owner.login` and `repository.full_name` are independent, attacker-controlled JSON fields in the same payload, an attacker can pass verification under a no-secret org while `OpenedHandler` resolves and mutates a totally different (victim) organization's repository via `params.repository.full_name`.

### Finding Description
The binding that should hold is: `organization_that_verified_signature == organization_that_owns_repository_mutated_by_handler`, i.e. `params.dig('repository','owner','login') == owner_prefix_of(params.repository.full_name)`.

In `verify_signature`, the controller derives the org used for verification purely from `repository.owner.login` (with an `organization.login` fallback): [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally trusts the request when that org has no configured `webhook_secret`: [3](#0-2) 

Meanwhile, `OpenedHandler#repository` resolves the record to mutate using a *different* field of the same body, `params.repository.full_name`, with no cross-check against `repository.owner.login`: [4](#0-3) [5](#0-4) 

Since both `repository.owner.login` (used for auth) and `repository.full_name` (used for the actual write target) are attacker-supplied JSON fields, they need not agree. An attacker who knows (or discovers) that some org `A` configured in `Shipit.secrets.github` has no `webhook_secret`, can craft:
```
X-Github-Event: pull_request
X-Hub-Signature: sha1=anything   (or omitted)
{
  "action": "opened",
  "number": 1,
  "pull_request": { ...head.ref/sha, user, assignees, labels... },
  "repository": { "owner": { "login": "org-A-no-secret" }, "full_name": "victim-org/victim-repo" },
  "sender": { "login": "attacker" }
}
```
`verify_signature` calls `Shipit.github(organization: "org-A-no-secret")`, which has no `webhook_secret`, so `verify_webhook_signature` returns `true` regardless of the header value. `drop_unhandled_event` does not filter `pull_request`, and `check_if_ping` is a no-op. The request reaches `OpenedHandler#process`, which resolves `repository` from `victim-org/victim-repo` and, if that repository has `review_stacks_enabled` and a matching `provisioning_behavior`, calls `ReviewStackAdapter#find_or_create!`, creating/mutating a `ReviewStack` under the victim org's repository — despite the request never having authenticated against victim-org's secret at all.

No existing guard closes this gap: `drop_unhandled_event` only filters by event type, `verify_signature`'s only real check is HMAC-vs-secret for the org named in `owner.login` (not `full_name`), and `Repository.from_github_repo_name`/model validations only validate the string format of `full_name`, not that it matches the verifying org. The `ExplicitParameters` schema on `OpenedHandler` requires the same top-level `repository.full_name` field but does not require it to match `repository.owner.login`, since the raw params hash retains both independently-controlled fields before/after the schema is applied.

### Impact Explanation
An attacker with no Shipit credentials, no `webhook_secret`, and no relationship to the victim repository can cause `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler` to create a `ReviewStack` entry for an arbitrary victim repository they don't own, provided (a) at least one org in the multi-org GitHub config lacks a `webhook_secret`, and (b) the victim repository has `review_stacks_enabled` with a provisioning behavior that doesn't require special conditions (`allow_all`, or one satisfiable purely from attacker-supplied `labels`/PR fields). This is a cross-tenant/cross-repository state manipulation matching the "Critical" category (payload for one repository mutating another's stack/records). The attack is fully repeatable against any repository as long as the "no secret" org precondition holds, and the same pattern applies to sibling handlers (`ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, etc.) that resolve `repository` the same way via `from_github_repo_name(params.repository.full_name)`.

### Likelihood Explanation
The exploit requires a specific Shipit deployment precondition: multi-org GitHub configuration (`Shipit.github_organizations` with more than one org) where at least one configured org has no `webhook_secret` set. This is a real, supported configuration path (`GitHubApp#verify_webhook_signature` explicitly early-returns `true` for a blank secret), but it is a deployment/configuration choice rather than a universal default — a single-org Shipit instance with a secret configured for its only org would not directly expose this specific cross-org divergence (though the "any signature accepted when secret is blank" issue could still bite a single org with no secret configured). Attacker cost is a single unauthenticated HTTP POST; no GitHub-side privileges, tokens, or knowledge of any secret are needed, only knowledge/guessing of an org name lacking a secret and the target repository's `full_name`.

### Recommendation
Bind the verified organization to the mutated resource: require that `repository.owner.login` (or `organization.login`) used to select the `webhook_secret` matches the owner segment of `repository.full_name` before dispatching to handlers, and reject the request if they differ. Additionally, treat a missing `webhook_secret` as "signature verification is impossible" rather than "signature is trivially valid" — either require a secret for every configured org or apply an explicit, opt-in "no verification" flag scoped strictly to that org's own repositories, never letting an unverified/no-secret org's identity be used to authorize writes to a different org's records.

### Proof of Concept
Minitest plan (integration test, no live GitHub):
1. Configure two orgs in `Shipit.secrets.github`-equivalent test config: `org-a` with `webhook_secret: nil`, and `org-b` with a secret and an existing `Repository` (`org-b/target-repo`) that has `review_stacks_enabled: true`, `provisioning_behavior: "allow_all"`.
2. POST to `/webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or an arbitrary `sha1=...` value), and body:
   ```json
   {
     "action": "opened",
     "number": 1,
     "pull_request": { "id":1, "number":1, "url":"u", "title":"t", "state":"open", "additions":1, "deletions":0,
       "head": {"sha":"abc123", "ref":"feature-branch"},
       "user": {"login":"attacker"}, "assignees": [], "labels": [] },
     "repository": { "owner": {"login": "org-a"}, "full_name": "org-b/target-repo" },
     "sender": {"login":"attacker"}
   }
   ```
3. Assert response is `200 OK` (not `422`), proving `verify_signature` passed based on `org-a`'s absent secret.
4. Assert `Shipit::Repository.find_by(owner: "org-b", name: "target-repo").review_stacks` gained a new `ReviewStack` for `feature-branch`, i.e. `assert_difference -> { Shipit::Repository.find_by(owner: 'org-b', name: 'target-repo').review_stacks.count }, 1`.
5. Explicitly assert the pre/post equality check: before the request, `verifying_org = "org-a"` and `mutated_repo_owner = "org-b"` (unequal); after the request, the `ReviewStack` created belongs to `org-b`, confirming the binding `verifying_org == mutated_repo_owner` was violated.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
