### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by SHA, with no scoping to the GitHub organization/repository that the webhook signature actually authenticated. This breaks the trust binding "an organization that authenticated versus the repository that is written": the `X-Hub-Signature` proves only that the payload came from *some* org configured in `Shipit.github`, keyed by `repository.owner.login` in the payload [1](#0-0) , but the handler applies the effect (writing a `Status` row) to any `Commit` record in the entire Shipit instance whose `sha` matches, regardless of which repository/stack it belongs to [2](#0-1) .

### Finding Description
The webhook flow is:
1. `WebhooksController#verify_signature` picks the `github_app` (and its `webhook_secret`) using `repository_owner`, taken from the **unverified** JSON body (`params.dig('repository', 'owner', 'login')`), then verifies the raw body against that org's HMAC secret [3](#0-2) .
2. On success, the full parsed payload is dispatched to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
3. Most handlers scope their effect to the repository named in the payload via `Handler#stacks`, which calls `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository', 'full_name')` [5](#0-4) .
4. `StatusHandler`, however, does **not** use `stacks`/`repository_name` at all. It only requires `sha` and `state` and does a global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [6](#0-5) .

Since `verify_signature` only proves the payload was signed by *an* organization configured in the Shipit instance (selected using the attacker-controlled `repository.owner.login` field), and `StatusHandler` never re-checks that the `Commit` it mutates belongs to that same organization/repository, an entity that is legitimately able to trigger a signed `status` webhook for **its own** repository (e.g., an org admin who installs/configures the GitHub App for org A, or any GitHub user who can produce a real `status` event on a repo under org A where the app is installed) can write a fabricated CI status onto a `Commit` that actually belongs to a completely different, unrelated stack — as long as the `sha` values collide. Git commit SHAs are content-addressed, not secret, and identical SHAs commonly occur across repositories through forks/mirrors of public commits (the SHA is a hash of tree + message + author/committer + timestamps + parent SHAs, not of the repository identity). This is a genuine confusable binding: **the organization whose secret signed the request vs. the repository/stack whose `Commit` gets written**.

The consequence, `create_status_from_github!` → `add_status`, drives blocking/deployable logic and Hook emission (`commit_status`, `deployable_status`) and can flip `stack.schedule_merges` [7](#0-6) [8](#0-7) . Forging a passing/failing status on a commit belonging to another stack can therefore unblock (or block) deploys/merges for a repository the attacker has no access to — a cross-repository write of state that gates automated shipping decisions.

### Impact Explanation
This qualifies as a cross-repository write under the listed Critical impact category: an attacker who is only authorized against org/repo A can forge deploy-blocking/allowing CI status on a `Commit` belonging to org/repo B, without ever holding B's webhook secret, GitHub credentials, or repository access. Because commit status directly feeds `deployable?`/`blocked?` and `schedule_merges`, this can influence whether an unrelated stack ships a deploy or merge.

### Likelihood Explanation
Requires: (1) multiple GitHub organizations/repositories configured behind the same Shipit instance (a documented, supported multi-tenant configuration — see `secrets_double_github_app.yml`) [9](#0-8) , and (2) a SHA collision between a commit the attacker can trigger a status event for and a commit tracked by the victim stack. SHA collisions are not attacker-forgeable at will (SHA-1 preimage), but identical commits (same content/parents/timestamps) legitimately recur across forks/mirrors of the same upstream history — a realistic, not purely theoretical, occurrence for shared open-source dependencies tracked by multiple Shipit-managed stacks. Likelihood is moderate: it does not require any credential compromise, only a legitimate, differently-scoped signed webhook.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, matching the pattern used by every other handler (`Handler#stacks`/`repository_name`), e.g. filter `Commit.joins(:stack).merge(stacks).where(sha: params.sha)` instead of a global `Commit.where(sha:)`. This restores the invariant that a webhook signed by org A's secret can only mutate state belonging to repositories under org A.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/organizations, `OrgA` and `OrgB`, each tracked with its own stacks (as supported by `secrets_double_github_app.yml`).
2. Stack `OrgB/repo` has tracked `Commit` with `sha = X` (e.g., a vendored/forked open-source commit also present verbatim in `OrgA/repo`, so the SHA is identical).
3. Attacker, who legitimately controls/administers `OrgA/repo` (and thus can produce genuinely signed `status` webhook deliveries for it, e.g. by pushing a commit status via GitHub's API on a repo they own that shares that SHA), triggers a `status` event with `sha: X`, `state: "success"`.
4. `WebhooksController#verify_signature` verifies the signature using `OrgA`'s `webhook_secret` and succeeds because the request genuinely came from GitHub for `OrgA/repo` [1](#0-0) .
5. `StatusHandler#process` executes `Commit.where(sha: X)`, which matches the `Commit` row belonging to `OrgB/repo`'s stack, and calls `create_status_from_github!` on it [2](#0-1) .
6. A forged "success" status is now attached to `OrgB`'s commit, potentially unblocking it for deploy/merge, even though the attacker never had access to `OrgB`'s repository, webhook secret, or GitHub credentials.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state

        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
