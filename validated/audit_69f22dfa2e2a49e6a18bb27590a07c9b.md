### Title
Path traversal in `DeploySpec::FileSystem#build_config` via `inherit_from` allows arbitrary file read outside the checked-out repository - ([File: app/models/shipit/deploy_spec/file_system.rb])

### Summary
`DeploySpec::FileSystem#build_config` resolves the `inherit_from` key with `path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))` and never verifies the resolved path stays inside `@app_dir` before calling `.exist?`/`read_config`. Because `Pathname#join` honors `../` segments and discards the receiver entirely when the argument is absolute, an attacker-controlled `shipit.yml` can force `read_config` to read and YAML-parse an arbitrary file reachable by the Shipit deploy-host process, outside the checked-out working tree.

### Finding Description
The binding the question describes should hold: `inherits_from_path == a path inside @app_dir for every value taken from the attacker's shipit.yml`. That binding is broken.

- `config_file_path` resolves the primary spec file strictly under `@app_dir`/`directory` via `file(filename, root: true)` [1](#0-0)  — this part is fine, filenames come from a fixed allow-list, not attacker input.
- However once that file is parsed, `build_config` computes the inherited path from attacker-supplied YAML content with no containment check: [2](#0-1) 
`path.dirname.join(user_value)` will:
  - Traverse arbitrarily far with `../../../etc/foo.yml`.
  - Jump to an absolute path entirely (e.g. `/etc/foo.yml`), since `Pathname#join` discards the left-hand side when the right-hand argument is absolute.
- `inherits_from_path.exist?` and `read_config` (`SafeYAML.load(path.read)`) then operate directly on that resolved path with no boundary check [3](#0-2) .
- This is invoked from `load_config`, which is the entry point used every time a `DeploySpec::FileSystem` is built off a checked-out commit directory, e.g. `EphemeralCommitChecks#run` (runs on arbitrary commits, including PR/fork commits, driven by webhook-triggered checks) [4](#0-3)  and `StackCommands#build_cacheable_deploy_spec`/`#fetch_deployed_revision` [5](#0-4) .

No existing guard (`verify_signature`, `require_permission!`, model validators, `EnvironmentVariables#permit`) is relevant here because the attacker never needs authentication — they only need to control the contents of a `shipit.yml` in a commit that gets checked out (their own branch/PR), which is already part of the intended attack surface for `EphemeralCommitChecks`.

### Impact Explanation
The primitive granted is: read an arbitrary file on the deploy host (subject to OS file permissions of the Shipit process) whose parsed YAML content will be `deep_merge`d into the resulting deploy spec. Practical caveats:
- If the target file isn't valid YAML producing a Hash, `inherits_config_obj.deep_merge(config_obj)` raises `NoMethodError`, causing spec loading to fail rather than leak data — this limits reliable disclosure to files that happen to parse as YAML mappings (e.g. other config/credentials files, adjacent stacks' `shipit.yml`, Capistrano `shared/config/*.yml` on hosts using that layout).
- For content to be observable by the attacker, the merged values need to surface somewhere visible to them (e.g. echoed via `dependencies_steps`/`review_checks` executed by `EphemeralCommitChecks`, whose output is generally visible only to users with access to the stack/PR check status, not necessarily the anonymous internet attacker).
- Since the attacker already fully controls the primary `shipit.yml` for their own commit (and can already define `dependencies`/`review` steps directly, without needing `inherit_from`), this traversal does not by itself grant new command-execution capability beyond what an attacker already has for their own PR's ephemeral checks. Its net new capability is a file-existence oracle and potential disclosure of adjacent host files' content when they parse as usable YAML and get reflected into task/step output.

Given the uncertain reflection path, this is best characterized as a **file-existence oracle plus conditional information disclosure**, not a demonstrated RCE or credential-exfiltration primitive on its own.

### Likelihood Explanation
Low attacker cost: opening a PR / pushing a branch with a crafted `shipit.yml` containing `inherit_from: ../../../../etc/passwd` (or an absolute path) is enough to trigger the traversal whenever the engine loads a `DeploySpec::FileSystem` for that commit (e.g. via `EphemeralCommitChecks`, which runs automatically on webhook-driven commit status checks). No special Shipit privileges, secrets, or team membership required — only the ability to author a commit that gets checked out.

### Recommendation
In `build_config`, resolve and canonicalize `inherits_from_path` (e.g. `File.expand_path`) and explicitly verify it is a descendant of `@app_dir` (or of the same repository root) before calling `.exist?`/`read_config`; reject or ignore `inherit_from` values that escape that boundary.

### Proof of Concept
```ruby
# test/models/shipit/deploy_spec/file_system_test.rb (new test)
test "#build_config refuses inherit_from paths outside app_dir" do
  Dir.mktmpdir do |outside_dir|
    outside_file = File.join(outside_dir, 'secret.yml')
    File.write(outside_file, { 'deploy' => { 'override' => ['cat /etc/shadow'] } }.to_yaml)

    Dir.mktmpdir do |app_dir|
      shipit_yml = File.join(app_dir, 'shipit.yml')
      relative_traversal = Pathname.new(outside_file).relative_path_from(Pathname.new(app_dir))
      File.write(shipit_yml, { 'inherit_from' => relative_traversal.to_s }.to_yaml)

      spec = Shipit::DeploySpec::FileSystem.new(app_dir, stacks(:shipit))

      # Binding under test: inherits_from_path (derived from attacker's `inherit_from`)
      # should equal a path inside app_dir, never `outside_file`.
      assert_raises(Shipit::DeploySpec::FileSystem::PathTraversalError) do
        spec.send(:load_config)
      end
      # Currently (pre-fix) this instead succeeds and merges `outside_file`'s
      # content into the spec, proving the containment check is missing.
    end
  end
end
```
This demonstrates that `build_config` will follow a relative/absolute path outside `@app_dir` supplied entirely through attacker-controlled YAML, with no containment check present in the current implementation.

      SHIPIT_CONFIG_INHERIT_FROM_KEY = "inherit_from"
      def build_config(path, config_obj)
        return config_obj if config_obj.blank? || !config_obj.key?(SHIPIT_CONFIG_INHERIT_FROM_KEY)

        inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))
        if inherits_from_path.exist?
          inherits_config_obj = read_config(inherits_from_path)
          config_obj = inherits_config_obj.deep_merge(config_obj)
          path = inherits_from_path
        end

        build_config(path, config_obj)
      end

      def read_config(path)
        SafeYAML.load(path.read) if path.exist?
      end
