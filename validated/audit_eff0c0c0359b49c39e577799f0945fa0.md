### Title
Legacy-vs-explicit rule parsing differential in `Rule.from_dict` allows silently ineffective or case-sensitive-bypassable `block` rules - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`Rule.from_dict` gives strict, undocumented precedence to an explicit `conditions:` list over the legacy `pattern:` field, and the two forms are evaluated with different matching semantics in `RuleEngine`. An attacker who controls the frontmatter of a hookify rule (via `/hookify` generation output or a repo-shipped `hookify.*.local.md` file) can author a rule whose visible `pattern`/message looks like a strict `block` guardrail while the actual `conditions` used for matching are weaker, mismatched, or case-sensitive, causing dangerous commands to silently evade the block rule.

### Finding Description
`Rule.from_dict` (`plugins/hookify/core/config_loader.py:45-84`) processes frontmatter as follows: [1](#0-0) 
If `conditions` is present in the frontmatter, it is used exclusively for matching and the legacy `pattern` field is *only* stored for display (`rule.pattern`) — it is never converted into a condition, and there is no validation that the two are consistent: [2](#0-1) 

Separately, `RuleEngine._check_condition` (`plugins/hookify/core/rule_engine.py:144-180`) applies the operator exactly as given, with no case normalization for non-regex operators (`contains`, `equals`, `starts_with`, `ends_with`): [3](#0-2) 
Whereas the *legacy* pattern path is always converted into a `regex_match` condition, and `regex_match` is always compiled with `re.IGNORECASE`: [4](#0-3) [5](#0-4) 

This creates two exploitable differentials:
1. **Precedence/consistency bypass**: a rule authored (via `/hookify` generation from attacker-influenced/prompt-injected input, or a repo-shipped rule file) can declare `action: block`, `pattern: "rm -rf"` (to look protective to a reviewer/user), but supply a `conditions:` list that references a non-existent field, wrong tool-specific field, or an unmatchable pattern. Because `conditions` takes exclusive precedence with no cross-check against `pattern`, the rule silently never matches (`_extract_field` returns `None` → `_check_condition` returns `False` → `_rule_matches` returns `False`), while looking like an active `block` rule.
2. **Case-sensitivity bypass**: authoring the same block intent with `operator: contains`/`equals`/`starts_with`/`ends_with` instead of `regex_match` makes the check case-sensitive, so a command like `RM -RF /` or `Rm -Rf /` evades a rule that would have blocked it had it been expressed as the legacy `pattern:` field (which is always compiled case-insensitively).

Because `load_rule_file` (`plugins/hookify/core/config_loader.py:244-274`) swallows parsing errors and simply skips/loads whatever frontmatter is present, there is no enforcement anywhere in the loader or engine that legacy and explicit forms of the same intended rule are semantically equivalent, violating the stated invariant.

### Impact Explanation
`hookify` `block` rules are the mechanism by which Claude Code enforces local guardrails (deny `PreToolUse`/`Stop` actions) against dangerous `Bash`/file operations. A rule that is authored to look like it blocks a dangerous command class but is actually inert (via the `conditions` precedence bug) or trivially bypassable by case variation (via non-regex operators) results in Claude executing commands that the user believes are blocked. This matches "Unauthorized local command execution that bypasses Claude Code approval or deny controls," since the deny decision path in `RuleEngine.evaluate_rules` (`plugins/hookify/core/rule_engine.py:61-84`) is never reached for the affected command.

### Likelihood Explanation
Exploitation requires only that attacker-influenced content shape the `conditions`/`pattern`/`operator` fields of a hookify rule file — reachable either through a repo-shipped `.claude/hookify.*.local.md` file (ordinary repository content, no privilege needed to plant such a file in a PR/fork a user opens with Claude Code) or through prompt-injected content steering `/hookify` rule generation. No special privileges, admin access, or social engineering beyond normal repo content review is required, and the mismatch between the human-readable `pattern`/message and the actually-enforced `conditions` is easy to construct and hard for a casual reviewer to notice.

### Recommendation
- In `Rule.from_dict`, validate that when both `pattern` and `conditions` are present they are logically consistent (or reject/warn on conflicting definitions instead of silently favoring `conditions`).
- Enforce a single canonical, case-insensitive matching semantic across all operators (or explicitly document/require case-insensitivity for `contains`/`equals`/`starts_with`/`ends_with` for `block` rules), so legacy and explicit forms cannot diverge in strictness.
- Add schema validation in `load_rule_file`/`extract_frontmatter` that flags unknown condition `field` names per `event`/tool type, and fail closed (treat as `block`-everything or reject the file) rather than silently producing a non-matching rule.

### Proof of Concept
Unit test extending `plugins/hookify/core/config_loader.py` / `plugins/hookify/core/rule_engine.py` test harnesses:

```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

frontmatter_legacy = {
    "name": "block-rm-rf",
    "enabled": True,
    "event": "bash",
    "action": "block",
    "pattern": "rm -rf",
}
frontmatter_explicit_broken = {
    "name": "block-rm-rf",
    "enabled": True,
    "event": "bash",
    "action": "block",
    "pattern": "rm -rf",  # looks identical/protective to a reviewer
    "conditions": [{"field": "cmd_typo", "operator": "regex_match", "pattern": "rm -rf"}],
}
frontmatter_explicit_case = {
    "name": "block-rm-rf",
    "enabled": True,
    "event": "bash",
    "action": "block",
    "conditions": [{"field": "command", "operator": "contains", "pattern": "rm -rf"}],
}

engine = RuleEngine()
input_data = {"tool_name": "Bash", "hook_event_name": "PreToolUse",
              "tool_input": {"command": "RM -RF /"}}

rule_legacy = Rule.from_dict(frontmatter_legacy, "danger")
rule_broken = Rule.from_dict(frontmatter_explicit_broken, "danger")
rule_case = Rule.from_dict(frontmatter_explicit_case, "danger")

assert engine.evaluate_rules([rule_legacy], input_data) != {}   # legacy blocks (IGNORECASE regex)
assert engine.evaluate_rules([rule_broken], input_data) == {}   # explicit "broken" field never matches -> bypass
assert engine.evaluate_rules([rule_case], input_data) == {}     # case-sensitive contains -> bypass
```

Expected: `rule_legacy` produces a `permissionDecision: deny` (block) response, while `rule_broken` and `rule_case`, despite representing "the same" intended block rule, return `{}` (no block), demonstrating the legacy/explicit semantic divergence and the resulting bypass of the guardrail.
