### Title
Cross-tenant status injection via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook with `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, with no `Repository`, `Stack`, or organization scoping. Because git commit SHAs are content-addressed and not namespaced per repository, an attacker who controls any repository whose GitHub App installation delivers webhooks to the Shipit instance can reproduce an existing victim commit's exact git object (same tree/parents/author/committer/timestamps — trivially done by copying a public commit's raw object bytes) and then create a status on it via the GitHub API for their own repo, causing Shipit to write that status onto the victim's `Commit` row in a completely unrelated `Stack`.

### Finding Description
The intended binding is: `Commit#stack_id` reached by a `status` webhook must equal the `Stack`/`Repository` whose GitHub App installation actually delivered that webhook (i.e., `commit.stack.repository.full_name == payload.repository.full_name`). This binding is not enforced.

- `Commit.by_sha`/`by_sha!` (used elsewhere, e.g. `app/controllers/shipit/api/deploys_controller.rb`, `app/controllers/shipit/deploys_controller.rb`) is always called in a stack-scoped context (`stack.commits.by_sha(...)`), and additionally raises `Commit::AmbiguousRevision` on short-SHA collisions [4](#0-3) .
- `StatusHandler#process`, by contrast, uses a global, full-SHA, exact-match query with zero stack/repository scoping [1](#0-0) . Sibling handlers correctly scope by stack/branch before touching commits: `PushHandler#process` scopes via `stacks.not_archived.where(branch:)` [3](#0-2) , and `CheckSuiteHandler#process` scopes via `stacks.where(branch:)` then `stack.commits.where(sha:)` [2](#0-1) . `StatusHandler` has no equivalent guard.

Exploit flow:
1. Attacker identifies a target `Commit` in a victim's stack (public repo commit, sha40 known/observable via GitHub).
2. Attacker reproduces the identical git commit object (same tree hash, parent hash, author/committer name/email/timestamp, message) inside a repository they control — this is not a SHA-1 preimage/collision attack, it is the normal git property that identical content hashes identically regardless of which repository stores it; copying the raw object via `git cat-file`/`git hash-object` and pushing it reproduces the exact same 40-character sha.
3. Attacker triggers (or waits for) a GitHub `status` event on that commit in their own repo (e.g., via their own CI or a direct API call using their own token) — GitHub delivers a legitimately signed webhook to Shipit for the attacker's own installation.
4. `WebhooksController#verify_signature` succeeds because the signature genuinely matches the org-specific `webhook_secret` for the attacker's own installation [5](#0-4)  — this guard authenticates *that the webhook truly came from GitHub for that installation*, but does nothing to confirm the sha belongs to that installation's repository.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matching the victim's `Commit` row in a different `Stack`/`Repository`, and calls `commit.create_status_from_github!(params)`, writing an attacker-controlled `state`/`description`/`target_url`/`context` status onto it [6](#0-5) .

Existing guards do not catch this: `verify_signature` only proves webhook authenticity for the sending organization, not sha ownership; there is no `ExplicitParameters` repository/stack binding in `StatusHandler`'s `params do...end` block [7](#0-6) ; and `Commit::AmbiguousRevision` is irrelevant here since the query is a full, exact match, not a prefix match.

### Impact Explanation
A forged/injected commit status lands on the victim's `Commit` row in an unrelated `Stack` that the attacker never authenticated against. Since `create_status_from_github!` feeds directly into `Commit#status` / `Status::Group` [8](#0-7) , and `deployable?`/blocking logic depends on that status [9](#0-8) , this can flip a commit to "success" and unblock/trigger continuous deployment (`schedule_continuous_delivery`) on the victim's stack [10](#0-9) . This matches the "payload for one repository mutating another's stack/commit" Critical category — a cross-tenant write that can lead to an unauthorized deploy.

### Likelihood Explanation
The main precondition is that the attacker's own repository must have a webhook-emitting GitHub App installation known to this Shipit instance (i.e., `repository_owner` resolves to a configured `github` entry) — for public/self-serviceable GitHub Apps this is attacker-achievable without any operator interaction. Reproducing an identical sha40 requires no cryptographic break, only copying an existing public commit object into the attacker's own repo, which is a normal git operation. Both preconditions are realistically attacker-achievable, making this repeatable against any victim commit whose sha is known and whose repository is publicly observable.

### Recommendation
Scope `StatusHandler#process` to the reporting repository, e.g. resolve the `Stack`/`Repository` from `params.repository`/payload the same way other handlers do, and restrict the commit lookup to `stack.commits.where(sha: params.sha)` (or `Commit.joins(:stack).merge(Repository scoped by payload full_name)`), matching the pattern already used in `CheckSuiteHandler`.

  stack_b = Shipit::Stack.create!(repository: Shipit::Repository.create!(owner: 'attacker', name: 'repo'), environment: 'production', branch: 'master')

  commit_attacker = stack_b.commits.create!(sha: shared_sha, message: 'attacker commit')

  params = Shipit::Webhooks::Handlers::StatusHandler.new.tap { }.params_class.new(

  ) rescue nil

  assert_difference -> { commit_victim.statuses.count }, 0 do

  end
end
