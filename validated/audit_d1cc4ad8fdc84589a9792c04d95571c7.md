## Title
Cross-tenant commit-status forgery via unscoped `Commit.where(sha:)` lookup enabling unauthorized `ContinuousDeliveryJob` triggers - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

## Summary
`StatusHandler#process` looks up commits by `sha` alone with no repository/stack scoping, even though the base `Handler` class already provides a `stacks` helper built exactly for binding a webhook payload to the repository that authenticated it. A properly signed status webhook from an attacker's own (legitimately registered) repository can therefore create a `Status` on a commit belonging to a completely different organization's stack, and if that stack has `continuous_deployment?` enabled, `ContinuousDeliveryJob` gets enqueued for it.

## Finding Description
The binding that should hold is: `organization_that_signed_webhook(repository_owner) == organization_owning(stack_of_matched_commit)`. This binding is never enforced.

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) validates the HMAC signature against the `webhook_secret` of `repository_owner` — the org named in the payload's `repository.owner.login`. This proves the request came from a repo belonging to that org, and nothing more.
- `Shipit::Webhooks::Handlers::Handler` (app/models/shipit/webhooks/handlers/handler.rb:32-38) provides a `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) that is meant to scope a handler's DB writes/reads to stacks belonging to the repository that emitted the event.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) ignores this helper entirely: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. This is a global, cross-tenant query with no `repository`/`stack` filter.
- `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` (app/models/shipit/commit.rb:165-169) uses the **matched commit's own** `stack_id` — i.e., whatever stack that SHA happens to belong to, not the stack of the repo that sent the webhook.
- `Status#schedule_continuous_delivery` (app/models/shipit/status.rb:19,42-44) runs `after_commit ... on: :create`, calling `commit.schedule_continuous_delivery`, which (per `Commit#deployable?` = `!locked? && (stack.ignore_ci? || (success? && !blocked?))`) can enqueue `ContinuousDeliveryJob` for that commit's actual stack when `stack.continuous_deployment? && stack.deployable?`.

Exploit flow: GitHub's Status API does not require the `sha` parameter to correspond to a commit that physically exists in the calling repository — it accepts any 40-hex string as a key. An attacker who legitimately controls a repository already registered as a Shipit tenant (their own org, with its own valid `webhook_secret`) sets a commit status with `state: success` and `sha` equal to a victim commit's SHA (commit SHAs are public/discoverable via the victim's Shipit UI or GitHub page) on their own repo. GitHub delivers a webhook signed with the attacker's own org's real secret, which passes `verify_signature` for `repository_owner = attacker_org`. `StatusHandler#process` then matches the victim's `Commit` row purely by SHA equality, creates a `Status` on the **victim's** stack, and — if the commit is otherwise pending/no-CI-blocked and the victim stack has `continuous_deployment` enabled — enqueues `ContinuousDeliveryJob` for the victim's stack.

Existing guards do not stop this: `verify_signature` only checks that the payload came from *some* org's registered repo, not that the matched commit belongs to that org; `drop_unhandled_event` and the `ExplicitParameters` schema only validate the shape of `sha`/`state`, not scope; and unlike other handlers (e.g., `PushHandler`, `PullRequest::*Handler`) which use `stacks` from the base `Handler`, `StatusHandler` never calls it.

## Impact Explanation
A payload authenticated for one repository/organization mutates another organization's `Commit`/`Status` records and can trigger an unauthorized deploy job (`ContinuousDeliveryJob`) against a victim stack the attacker has no access to. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy". Blast radius is any stack in the entire Shipit installation whose tracked commits share a SHA the attacker can predict/replay (trivial, since SHAs are public and GitHub's Status API doesn't require SHA existence in the calling repo). It is repeatable against arbitrary victim stacks/commits as long as the attacker knows the target SHA and the target stack has `continuous_deployment` enabled and the commit is otherwise not blocked/locked.

## Likelihood Explanation
Preconditions: attacker needs write access to any single repository that is already a legitimate Shipit tenant (their own repo/org, a normal, low-privilege situation for a multi-tenant Shipit deployment), knowledge of a target commit SHA (public), and a victim stack with `continuous_deployment: true` and a pending/deployable commit sharing that SHA. No secrets, sessions, or elevated GitHub roles are needed beyond normal write access to one's own repository. This is cheap and repeatable — a single `POST /repos/:owner/:repo/statuses/:sha` GitHub API call per attempt.

## Recommendation
Scope `StatusHandler#process` to the repository that emitted the webhook, e.g. use the base class's `stacks` helper and restrict the commit lookup to `stacks.joins(:commits).where(shipit_commits: { sha: params.sha })` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), so a status can only be applied to commits belonging to stacks whose repository matches the authenticated webhook's `repository.full_name`.

## Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook from one repo cannot trigger CD on another org's stack sharing the same SHA" do
  attacker_stack = shipit_stacks(:shipit) # belongs to org "attacker-org/attacker-repo"
  victim_stack = shipit_stacks(:cyclimse) # belongs to a different org, continuous_deployment: true
  victim_stack.update!(continuous_deployment: true)

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...) # pending, unlocked, not blocked

  payload = {
    'repository' => { 'full_name' => attacker_stack.repository.github_repo_name,
                       'owner' => { 'login' => attacker_stack.repository.owner } },
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker'
  }

  assert_no_enqueued_jobs(only: ContinuousDeliveryJob) do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
  # currently FAILS: ContinuousDeliveryJob is enqueued with args [victim_stack]
  # even though the webhook was authenticated for attacker_stack's organization.
end
```
