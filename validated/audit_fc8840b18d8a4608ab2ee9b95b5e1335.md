### Title
CCMenuController#stack bypasses `current_api_client.stack_id` scoping, allowing any read:stack token to fetch any stack's CI status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` scopes accessible stacks to `current_api_client.stack_id` via `stacks.from_param!`, but `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, bypassing that scoping entirely. Any `ApiClient` token with the generic `read:stack` permission (created for one stack) can be used to fetch ccmenu XML for any other stack, including private/review stacks, by simply changing the `stack_id` in the URL.

### Finding Description
The intended invariant is: `stacks == Stack.where(id: current_api_client.stack_id)` when `current_api_client.stack_id?` is true, and `stack = stacks.from_param!(params[:stack_id])` [1](#0-0) .

`CCMenuController` breaks this by redefining `stack` to bypass the `stacks` scope entirely and query the global `Stack` model: [2](#0-1) 

The only authorization check applied is `require_permission :read, :stack`, which calls `current_api_client.check_permissions!(:read, :stack)`. That method only checks whether the string `"read:stack"` is present in the client's `permissions` array — it has no knowledge of, or binding to, the specific `stack_id` in the request: [3](#0-2) 

So the equality the system is supposed to enforce — `resolved_stack ∈ Stack.where(id: current_api_client.stack_id)` — never gets evaluated on this path; instead `resolved_stack = Stack.from_param!(params[:stack_id])`, unconstrained by the token's `stack_id`.

Exploit flow:
1. Attacker obtains (or is issued) a stack-scoped `ApiClient` with `stack_id = A` and permission `read:stack` (e.g. via the `ccmenu_url#fetch` flow, which creates exactly such a client: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)` [4](#0-3) ), giving them a `?token=` URL for stack A's ccmenu feed.
2. `CCMenuController#authenticate_api_client` accepts the token straight from `params[:token]` [5](#0-4) .
3. Attacker sends `GET /api/stacks/<review-stack-owner>/<review-stack-repo>/<review-stack-branch>/ccmenu?token=<their-stack-A-token>`.
4. `require_permission!(:read, :stack)` passes because the token has `read:stack` permission (unrelated to which stack).
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` to the targeted review stack, not stack A.
6. `show` renders the review stack's latest deploy/rollback state as ccmenu XML, disclosing task/deploy state for a stack outside the token's intended scope.

This differs from every other API endpoint in the same routes scope (`tasks`, `deploys`, `hooks`, `lock`, etc.), which all inherit `BaseController#stack` and are correctly scoped through `stacks.from_param!`.

### Impact Explanation
An attacker holding any single stack-scoped `read:stack` token (which can legitimately be self-issued for a stack they have access to via `ccmenu_url#fetch`, or leaked/shared) can enumerate and read the CI/CD status (last deploy id, success/failure, running state) of **any** stack on the Shipit instance, including private or review stacks they have no authorization for. This is repeatable against arbitrary stacks by simply varying the `stack_id` path segment, with no additional privilege required. This matches the "High — unauthenticated read of stack state, task streams or deploy output" category, since the effective read is unauthenticated with respect to the specific target stack.

### Likelihood Explanation
Preconditions: attacker needs any valid `ApiClient` token with `read:stack` permission scoped to *some* stack — trivially obtainable for any stack the attacker can access via the UI's "CCMenu URL" feature (`ccmenu_url#fetch`), or via any other legitimately issued stack-scoped token. No GitHub secrets, session, or elevated role is required. The attack is a single unauthenticated GET request with a known/guessable `stack_id` (owner/repo/branch), fully repeatable and scriptable.

### Recommendation
Remove the `stack` and `authenticate_api_client` overrides in `Shipit::Api::CCMenuController` and rely on the inherited `BaseController#stack` (which uses the scoped `stacks.from_param!`) and `BaseController#authenticate_api_client` (Basic Auth via `ApiClient.authenticate`), or explicitly re-apply the `current_api_client.stack_id` scoping when resolving `params[:stack_id]` if `params[:token]` support must be preserved for embeddable CCMenu URLs.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
require 'test_helper'

module Shipit
  module Api
    class CCMenuControllerTest < ActionController::TestCase
      test "a token scoped to stack A cannot fetch ccmenu for review stack B" do
        stack_a = shipit_stacks(:shipit)
        stack_b = shipit_stacks(:cyclimse) # a distinct/review stack

        client = ApiClient.create!(
          creator: shipit_users(:walrus),
          name: 'scoped client',
          stack: stack_a,
          permissions: %w[read:stack],
        )

        # Binding under test: resolved stack must be in Stack.where(id: client.stack_id)
        assert_equal [stack_a.id], Stack.where(id: client.stack_id).pluck(:id)

        get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }

        # Expect scoping to reject cross-stack access
        assert_response :not_found # or :forbidden — currently fails: returns 200 with stack_b's ccmenu XML
      end
    end
  end
end
```
Run against current code: the request returns `200 OK` with stack B's ccmenu XML instead of `404`/`403`, confirming the scoping bypass.
