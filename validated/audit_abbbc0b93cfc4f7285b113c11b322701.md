### Title
Unauthenticated read of live stack/task event streams via `mount Pubsubstub::StreamAction.new, at: '/events'` - ([File: config/routes.rb])

### Summary
`config/routes.rb` mounts `Pubsubstub::StreamAction.new` at `/events` as a raw Rack application, bypassing the `ShipitController`/`Shipit::Authentication` concern entirely. Because `before_action :force_github_authentication` only runs for requests dispatched through Rails controllers that include the concern, an unauthenticated internet client can connect directly to `/events?channels[]=stack.<id>` and receive every `Pubsubstub.publish` broadcast for that channel.

### Finding Description
The broken binding: every stack/task update rendered to a browser is gated by `current_user.authorized?` inside `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:8,20-34`), i.e. `response_data == f(current_user.authorized?)`. But for `/events`, `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` (`config/routes.rb:9`) hands the request directly to the `Pubsubstub` Rack app, which is not an `ActionController` and therefore never runs `ShipitController`'s `before_action :ensure_required_settings` or the included `Shipit::Authentication#force_github_authentication` filter (`app/controllers/shipit/shipit_controller.rb:16,18`). No middleware in `lib/shipit/engine.rb` (only `OmniAuth::Builder` and, conditionally, `Shipit::SameSiteCookieMiddleware`) enforces authentication ahead of the mount either. So for this endpoint the equality becomes `response_data == f(true)` regardless of `current_user.authorized?`, breaking the intended binding.

Channel names are predictable/enumerable: `Stack#broadcast_update` publishes to `"stack.#{id}"` using the stack's sequential primary key (`app/models/shipit/stack.rb:561-567`), and the same pattern is used for commit/status/task broadcasts (see `test/models/status_test.rb:58-63`, `test/models/deploys_test.rb:1121-1126`, `test/models/commits_test.rb:946-951`, and the view usage `subscribe events_path(channels: ["stack.#{@stack.id}"])` in `app/views/shipit/stacks/show.html.erb:1` and `app/views/shipit/stacks/all_tasks.html.erb:1`).

Attacker request: an unauthenticated `GET /events?channels[]=stack.1` (or any guessed/enumerated stack id) opens an SSE connection and receives every subsequent `update` event for that stack — including deploy/task status changes — with no session, token, or team membership.

Existing guards (`force_github_authentication`, `User#authorized?`, `verify_signature`, `ExplicitParameters`, model validations) are all controller-level or webhook-level and never execute on this Rack-mounted path, so none of them prevent the divergence.

### Impact Explanation
An unauthenticated attacker can read live stack/task state and deploy/task status streams for any stack whose id they guess (ids are small sequential integers, trivially enumerable) — this matches "unauthenticated read of stack state, task streams" (High). It does not expose secrets, task output content (only lightweight `update` pings triggering client-side refetches — the actual protected content still requires an authenticated page load to render), but it does leak the existence/activity cadence of stacks and task/deploy lifecycle events across the entire instance, repeatably, for every tenant/stack.

### Likelihood Explanation
No Shipit or GitHub secrets, sessions, or privileged roles are needed — only network access to the mounted `/events` route, which is on by default per `config/routes.rb`. Stack ids are sequential and easily enumerated by an attacker who has created even one stack or observed one id. Cost to the attacker is a single unauthenticated HTTP request; the attack is trivially repeatable against every stack id on the instance.

### Recommendation
Do not mount `Pubsubstub::StreamAction` unauthenticated. Wrap it behind an authenticating Rack app/middleware (e.g., a small wrapper controller that runs `force_github_authentication`/`current_user.authorized?` and validates that the requested `channels[]` correspond to stacks/tasks the current user is permitted to view) before delegating to `Pubsubstub::StreamAction`, or move the stream action into a real controller action subclassing `ShipitController` so the existing authentication concern applies, validating channel ownership against `current_user`.

### Proof of Concept
```ruby
# test/integration/events_stream_authentication_test.rb
require 'test_helper'

module Shipit
  class EventsStreamAuthenticationTest < ActionDispatch::IntegrationTest
    test "unauthenticated request to /events for a guessed stack channel is not gated by force_github_authentication" do
      stack = shipit_stacks(:shipit)

      # No session[:user_id] set, no ApiClient token.
      get "/events", params: { channels: ["stack.#{stack.id}"] }

      # Binding under test: response should equal the same redirect/forbidden
      # response force_github_authentication produces for every other endpoint.
      refute_equal 302, response.status
      refute_includes response.headers['Location'].to_s, github_authentication_path
      # Demonstrates the connection is accepted rather than challenged.
      assert_includes [200, 101], response.status
    end
  end
end
```
This demonstrates that unlike every controller-backed route (which redirects to `github_authentication_path` per `force_github_authentication`, `app/controllers/concerns/shipit/authentication.rb:20-34`), `/events` accepts the connection without any authentication check.
