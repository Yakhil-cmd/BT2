### Title
Cross-organization commit-status forgery via `StatusHandler` — the organization whose webhook secret authenticates a request is never bound to the commit/repository the handler writes to - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook purely against the organization named in the payload's `repository.owner.login` (or `organization.login`), using that organization's configured `webhook_secret`. Once the HMAC check passes, `Shipit::Webhooks::Handlers::StatusHandler#process` is invoked and mutates state (`Commit#create_status_from_github!`) using only `params.sha` — a value that is completely disconnected from the organization/repository binding that was verified.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb#verify_signature` derives the "authenticated organization" from the request body itself: [1](#0-0) [2](#0-1) 

The signature is verified with the `webhook_secret` scoped to that organization's `GitHubApp` config: [3](#0-2) 

All this proves is "the sender knows OrgA's webhook secret." It does **not** prove that the event's other payload fields (in particular the `sha`) actually belong to a repository owned by OrgA.

The `status` event is then dispatched to `StatusHandler`, which never consults `repository_name`/`stacks` (the org-scoping helper defined in the base `Handler` class) at all — it queries `Commit` globally by SHA: [4](#0-3) [5](#0-4) 

Because `Commit.where(sha: params.sha)` is not filtered by stack/repository/organization, any commit SHA that happens to exist in *any* stack tracked by this Shipit instance — regardless of which GitHub organization/repository it belongs to — will have a fabricated status recorded against it, as long as the *attacker's own* organization's webhook secret produces a valid signature for the raw POST body.

This is the exact analog of the reported bug class: a value is *acted on* (`params.sha`, and the commit/stack it resolves to) that is never covered by — nor bound to — the thing the security check actually verified (the payload's `repository.owner.login` / that organization's secret). The equality that should hold but doesn't is:

`organization whose secret authenticated the request == organization that owns the repository/commit being written to`

Before the attacker's request: Commit X (belonging to Org B's stack) has no forged/incorrect status.
After the attacker's request (signed with Org A's own legitimate webhook secret, with `sha` set to Org B's commit and `state: "success"`): Commit X now has an attacker-controlled status record, even though the request was only ever authenticated as coming from Org A.

### Impact Explanation
Commit CI status directly gates automated protocol/business logic in Shipit: `DeploySpec#required_statuses`/`blocking_statuses` (`app/models/shipit/deploy_spec.rb`) determine whether a commit is considered "deployable" and whether continuous delivery / merge-queue processing proceeds. By forging a `success` status on an arbitrary SHA belonging to a stack outside the attacker's own organization, an attacker who legitimately administers or has been issued a webhook secret for *one* Shipit-tracked GitHub organization can manipulate CI-gating status for commits in a *completely different* organization's stack, which can unblock or trigger an unauthorized deploy for that unrelated stack. This matches the Critical-tier impact of "an unauthorized deploy, rollback or merge" via a broken authentication/authorization binding, since possession of Org A's webhook secret grants effectively unbounded write access to Commit status for every repository configured on the same Shipit instance.

### Likelihood Explanation
Requires the attacker to possess a valid `webhook_secret` for at least one organization configured on the shared Shipit instance (a routine, low-privilege credential in any multi-tenant/multi-org Shipit deployment — e.g., any team onboarded with its own GitHub App). No cross-org credentials, GitHub App private key, or Shipit session are required. The only additional requirement is knowledge of a target commit SHA in another org's stack, which is often public (GitHub commit pages, PR links) or guessable from Shipit's own UI (stack/commit history pages are visible to any authenticated Shipit user). This makes the attack realistically reachable in any deployment hosting more than one organization's webhook secret.

### Recommendation
`StatusHandler#process` (and the base `Handler#stacks`/`repository_name` helper more generally) must scope the operation to the organization that was actually verified in `WebhooksController#verify_signature`, e.g., by passing the authenticated `repository_owner` down into the handler dispatch and requiring `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: authenticated_owner })` rather than an unscoped `Commit.where(sha: ...)`. More generally, every handler should verify that `payload.dig('repository','full_name')` belongs to the same organization that `verify_signature` authenticated, rejecting the event otherwise.

### Proof of Concept
1. Shipit instance is configured with two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` (see `config/secrets.development.shopify.yml` layout, `lib/shipit/github_app.rb#initialize`).
2. Attacker legitimately controls (or has been issued) `org-a`'s `webhook_secret` (e.g., they are the app owner for `org-a`, an org unrelated to `org-b`).
3. Attacker identifies a commit SHA `deadbeef...` belonging to a stack under `org-b` (visible via Shipit's own commit/deploy history UI, or GitHub).
4. Attacker crafts a JSON body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-a" } }
}
```
5. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(org_a_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
6. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `Shipit.github(organization: "org-a")`, and the signature validates successfully because it was signed with `org-a`'s own secret.
7. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` — matching the commit under `org-b`'s stack — and calls `commit.create_status_from_github!(params)`, recording a forged `success` status on a commit the attacker has no relationship to, potentially satisfying `required_statuses`/`blocking_statuses` gating and enabling an unauthorized deploy of `org-b`'s stack.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
