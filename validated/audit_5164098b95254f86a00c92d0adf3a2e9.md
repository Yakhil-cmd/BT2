### Title
Cross-organization `Team` identity confusion via unscoped `Team.find_or_create_by!(github_id:)` allows any registered org to inject members into another org's team - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` looks up/creates a `Team` keyed solely by the attacker-controllable, GitHub-numeric `params.team.id`, with no check that the `params.organization.login` making the request actually owns that team. `verify_signature` in `WebhooksController` only proves the payload was signed by *some* org's genuine `webhook_secret`; it never validates that the `team.id` inside the payload belongs to the signing org. Any org with a legitimate Shipit-registered `webhook_secret` can therefore add arbitrary `member.login`s to a `Team` that belongs to a completely different, victim organization.

### Finding Description
The intended binding is: **`Team#organization` that authenticated the request == `Team#organization` that owns `github_id`**. Tracing the code shows this binding is never enforced:

- `WebhooksController#verify_signature` derives `repository_owner` from `params.dig('organization','login')` [1](#0-0)  and verifies the HMAC signature using `Shipit.github(organization: repository_owner)`'s `webhook_secret` [2](#0-1) . This only proves the request was signed by the org named in the payload's own `organization.login` field — it says nothing about which `team.id` the payload may reference.
- `MembershipHandler#find_or_create_team!` finds-or-creates a `Team` scoped only by `github_id: params.team.id`, a value fully controlled by whoever composes the payload [3](#0-2) . If a `Team` with that `github_id` already exists (created earlier by the legitimate owning org), the block is skipped entirely and the existing row is returned unmodified — `organization` is not re-validated against `params.organization.login`.
- `MembershipHandler#process` then unconditionally calls `team.add_member(member)` for `action == 'added'` [4](#0-3) , and `Team#add_member` inserts a `Membership` row with no ownership check [5](#0-4) .
- `MembershipHandler`'s `params` schema only requires `team.id/name/slug/url`, `organization.login`, and `member.login` as plain strings/integers — no cross-validation exists in the `ExplicitParameters` schema [6](#0-5) .

Attack: Attacker A registers/controls org `attacker-org-a`, which has a real Shipit `webhook_secret` (any org onboarded to the Shipit instance qualifies — this is not restricted to a privileged org). Attacker A sends a `membership` webhook, correctly signed with `attacker-org-a`'s own secret, but with `team.id` set to the numeric GitHub ID of a *victim* org's team (team IDs are discoverable via GitHub's public API or by observing prior legitimate webhooks) and `member.login` set to their own attacker-controlled GitHub login. Because `find_or_create_by!` matches on `github_id` alone, it returns the victim's existing `Team` record, and the attacker's login is added as a `Membership` on that team. A second unrelated org (`attacker-org-b`), with its own genuine secret, can do the same concurrently for a different `member.login` against the same `team.id` — both succeed independently once `find_or_create_by!`'s internal rescue-and-retry resolves the race, since the check is a global unique key on `github_id`, not a composite key with the owning organization.

None of the existing guards prevent this: `verify_signature`/`GitHubApp#verify_webhook_signature` authenticate *the sending org*, not *the team-organization relationship claimed inside the JSON body*; `drop_unhandled_event` only filters unsupported event types; the `ExplicitParameters` schema only validates types/presence, not cross-field ownership.

### Impact Explanation
If the victim `Team`'s `github_id` corresponds to a team listed in `Shipit.github_teams`, this is a direct authorization escalation: `User#authorized?` grants access when `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) , so an attacker-controlled GitHub login added to that `Team` via a forged webhook from an unrelated, low-privilege org becomes an authorized Shipit user — able to log in, view stack/task state, and depending on further authorization checks, trigger deploys/rollbacks. This is repeatable against any team whose `github_id` is known, from any org possessing a genuine webhook_secret, multiplying the blast radius across all tenants sharing the Shipit instance. This matches the High/Critical category: "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Preconditions: attacker must control (or register) at least one org that already has a Shipit `webhook_secret` configured (a normal onboarding step for any org using this Shipit instance, not requiring compromise of another tenant's secret) and must know/guess a victim team's numeric `github_id` (obtainable via GitHub's public teams API for public orgs, or observed from prior webhook deliveries). No GitHub App private key, session, or `api_clients_secret` is needed. This is feasible with moderate effort and fully repeatable.

### Recommendation
Scope the `Team` lookup/creation by both `github_id` **and** `organization` (matching `params.organization.login` against the org whose webhook_secret verified the request), i.e. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and reject/raise if an existing `Team` with that `github_id` has a different `organization` than the authenticated org.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb (conceptual, no live GitHub)
test "membership webhook from unrelated org can add member to a foreign team" do
  victim_team = shipit_teams(:some_team) # organization: "victim-org", github_id: 555

  payload = {
    'action' => 'added',
    'team' => { 'id' => victim_team.github_id, 'name' => victim_team.name, 'slug' => victim_team.slug, 'url' => victim_team.api_url },
    'organization' => { 'login' => 'attacker-org' }, # different org, but has its own genuine webhook_secret
    'member' => { 'login' => 'attacker-login' }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)

  attacker_user = Shipit::User.find_by(login: 'attacker-login')
  assert victim_team.reload.members.include?(attacker_user),
    "expected binding organization-that-signed == organization-that-owns-team to hold, but attacker-org added a member to victim-org's team"
end
```
Both sides of the claimed binding (`signing org` vs `owning org` of `github_id`) diverge: the test shows a `Membership` created for `victim_team` by a payload signed by `attacker-org`, confirming the vulnerability.
