## Title
Webhook signature verified against `repository.owner.login`, but repository resolution trusts unverified `repository.full_name` — cross-repository/cross-organization stack sync - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to HMAC-verify the payload against using `repository.owner.login` (or `organization.login`) from the JSON body. All webhook handlers, however, resolve the target `Repository`/`Stack` using a *different* field of the same unverified body: `payload.dig('repository', 'full_name')`. Because the signature only proves "this payload was signed with organization X's secret", and never binds that organization to the `full_name` field the handlers actually act on, a valid signature from organization X's secret does not guarantee the acted-upon repository belongs to organization X.

### Finding Description
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` (or `organization.login`) and asks `Shipit.github(organization: repository_owner)` to verify the signature: [1](#0-0) [2](#0-1) 

- After verification, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` is invoked using the raw parsed JSON, and each `Handler` resolves the affected stacks via a **separate** field: [3](#0-2) [4](#0-3) 

The verified binding is:
`HMAC-valid(payload, secret_for(repository.owner.login))`

The binding actually relied on downstream is:
`Repository.from_github_repo_name(repository.full_name)`

These are two independent JSON fields in the same attacker-controlled request body. Nothing ties `repository.owner.login` to `repository.full_name` — an attacker who legitimately owns/administers an organization (and therefore genuinely knows that organization's `webhook_secret`, e.g. because they set it up themselves, or because it's a shared/default secret across installs) can produce a JSON payload where `repository.owner.login` is their own org (so the HMAC check passes) while `repository.full_name` names an entirely different, victim repository/stack. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and the `pull_request/*` handlers all just use `repository_name`/`from_github_repo_name` blindly: [5](#0-4) [6](#0-5) 

### Impact Explanation
This breaks the binding between "the organization whose secret authenticated the payload" and "the repository/stack whose state is mutated". Concretely:
- `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` on a victim's stack, forcing a re-sync to an attacker-chosen SHA/branch state (potential stack state corruption or triggering unwanted deploy eligibility).
- `StatusHandler` writes forged CI statuses (`Commit#create_status_from_github!`) onto a victim's commits, which can flip commits from "not deployable" to "deployable" if the victim's `shipit.yml` `ci.require` context matches, and then interacts with Shipit's continuous-deployment/merge-queue logic — this is a path toward an **unauthorized deploy** of attacker-chosen content that was never actually reviewed/approved for the victim repository.
- `CheckSuiteHandler`/pull-request handlers similarly operate on `Repository.from_github_repo_name`-resolved victim data using forged payload fields.

This matches the analog of "an organization that authenticated versus the repository that is written": the org bound by the verified signature is not the org that owns the repository actually mutated.

### Likelihood Explanation
Exploitability depends on the attacker being able to produce a *validly signed* payload for **some** organization configured in this Shipit install, while the `repository.full_name` field targets a **different** organization/repository also hosted by the same Shipit install (multi-tenant deployments configuring multiple GitHub orgs/apps, each with its own `webhook_secret`, are an explicit supported configuration per `Shipit.github(organization:)` / `GithubOrganizationUnknown`). If the attacker has legitimate write/webhook-admin access to one org configured on the instance (a plausible and common scenario for shared internal deploy tools), they can forge cross-organization webhook events without any credential belonging to the victim org. No `ApiClient` token, `github_access_token`, or session is required — only the ability to reach the public webhook endpoint and know one org's `webhook_secret` (which the attacker legitimately possesses for their own org).

### Recommendation
Verify the signature using the same field that is subsequently trusted for repository resolution, and cross-check that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatching to handlers. Concretely, in `WebhooksController#verify_signature`/`create`, derive both the signing organization and the acted-upon repository owner from `full_name`, reject if they differ, and pass this validated repository identity down into `Handler` rather than letting each handler independently re-parse `payload.dig('repository', 'full_name')`.

### Proof of Concept
1. Shipit instance is configured with two GitHub orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (a supported multi-org configuration via `Shipit.github(organization:)`).
2. Attacker is a legitimate admin of `attacker-org` and therefore knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` webhook JSON body:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>"
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to `/github/webhooks`.
5. `verify_signature` computes `repository_owner = "attacker-org"`, looks up `Shipit.github(organization: "attacker-org")`, and the signature verifies successfully (`app/controllers/shipit/webhooks_controller.rb:59-62`, `:24-30`).
6. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: <attacker sha>)` on the victim's stack — despite the signature only proving control of `attacker-org`.
