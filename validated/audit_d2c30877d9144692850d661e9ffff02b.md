### Title
Missing zero-address check on `creator` account in `initialize_with_permission` permanently freezes accrued creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` accepts a `creator` account that is only declared as `UncheckedAccount<'info>` with no `constraint`, `address`, or non-default check, then stores its raw key into `PoolState.pool_creator` via `pool_state.initialize(...)`. This is the exact bug class described in the report: an address argument accepted and persisted without validating it is non-zero.

### Finding Description
In `InitializeWithPermission`, the `creator` field is declared as: [1](#0-0) 
with no ownership, signer, or non-default constraint anywhere in the account struct. The `payer` (who funds/creates the pool and controls all account inputs, including `creator`) is free to pass `Pubkey::default()` (the zero address) as `creator`.

That unchecked key is then written straight into the persistent `PoolState` account: [2](#0-1) 
via `PoolState::initialize`, which stores it as `self.pool_creator = pool_creator.key();` with no validation inside the setter either: [3](#0-2) 

Both fee-collection paths for creator fees gate the collector against this stored `pool_creator` value:
- `collect_creator_fee` requires the `creator` signer's address to equal `pool_state.pool_creator`: [4](#0-3) 
- `collect_creator_fee_permissionless` requires the passed `creator` account to equal `pool_state.pool_creator` (its ATA becomes the fee destination): [5](#0-4) 

`Pubkey::default()` (all-zero, `11111111111111111111111111111111`) has no known private key, so `collect_creator_fee` can never be signed for such a pool. `collect_creator_fee_permissionless` would technically execute, but its associated token account is created with `associated_token::authority = creator` where `creator == Pubkey::default()`; the fees would be sent to an ATA owned by the zero-address, an account nobody controls, effectively vaporizing the funds even though the transfer itself does not revert.

Meanwhile, creator fees continue to accumulate normally in `PoolState.creator_fees_token_0/1` on every swap when `enable_creator_fee` is true (this pool is created with `enable_creator_fee = true`, see the last argument of `initialize()` above), so real user/LP-derived fee funds pile up in the vaults with no reachable, useful recipient.

### Impact Explanation
This is a permanent freezing-of-funds bug affecting real economic value: creator fees split out of every swap on a pool created this way accumulate indefinitely in `token_0_vault`/`token_1_vault` (tracked in `PoolState.creator_fees_token_0/1`) but can never be collected by any party who can prove ownership, because the only "owner" recorded is the zero address. This satisfies the report's harm bar of concrete permanent freezing of funds tied to a pool's fee-ledger accounting.

### Likelihood Explanation
The `payer` calling `initialize_with_permission` fully controls every account passed in the instruction, including `creator`, and nothing in the Anchor account validation of `InitializeWithPermission` prevents `creator = Pubkey::default()`. This can happen either by an operator/UI mistake (matching the exact scenario flagged in the referenced report, i.e., "passing a 0 address is a mistake") or deliberately by a permissioned pool creator who wants to guarantee creator fees are burned. Note that reaching this instruction requires holding a valid `Permission` PDA for the `payer` (granted via `create_permission_pda`, an admin-only instruction), so this is not a fully unprivileged, anyone-can-call path — it requires the caller to already be an approved pool creator. That reduces likelihood relative to a fully open surface, but any approved creator (a normal, non-privileged-w.r.t.-protocol-admin business role) can trigger it.

### Recommendation
Add an explicit non-default check on `creator` in `InitializeWithPermission`, e.g. `require_keys_neq!(creator.key(), Pubkey::default())` before calling `pool_state.initialize(...)`, or add an Anchor `constraint = creator.key() != Pubkey::default()` to the account definition. Consider also validating this in `PoolState::initialize` itself so any other current or future call site is protected.

### Proof of Concept
1. Obtain (or be granted) a `Permission` PDA for `payer` via the existing `create_permission_pda` admin flow.
2. Call `initialize_with_permission` with `payer` as a normal signer, `creator = Pubkey::default()`, valid `token_0_mint`/`token_1_mint`, and `creator_fee_on` set so creator fees accrue.
3. Pool initializes successfully; `pool_state.pool_creator == Pubkey::default()`.
4. Execute normal swaps (`swap_base_input`/`swap_base_output`) against the pool; creator fees accrue in `pool_state.creator_fees_token_0/1`.
5. Attempt `collect_creator_fee`: fails permanently, since no signer can ever match `address(0)`.
6. Attempt `collect_creator_fee_permissionless`: succeeds mechanically, but funds land in an ATA owned by `Pubkey::default()`, which is unreachable/unspendable by any real party — funds are effectively lost.
