### Title
Webhook signature is verified against a secret chosen from an unauthenticated field, letting an attacker forge events for a repository they don't control - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` picks *which* GitHub App/organization's HMAC secret to verify a webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unverified JSON body, then checks the signature with that org's secret. Separately, the event handlers that actually locate the `Stack` to act on use a *different* field from the same unverified body, `repository.full_name`. Nothing forces these two fields to refer to the same repository/organization. This mirrors the report's root cause: a binding is enforced on one identity field (the operator/organization that "authenticates") while a *different* field (the investor address/target repository) is the one actually acted upon.

### Finding Description
`verify_signature` selects the app config by an attacker-supplied field and verifies against that specific org's secret: [1](#0-0) [2](#0-1) 

The signature check itself is a straightforward HMAC compare using the secret bound to that chosen organization: [3](#0-2) 

Once the signature is accepted, `create` dispatches the *entire raw body* to handlers: [4](#0-3) 

Handlers resolve the target `Stack`/`Repository` using `repository.full_name` from that same body — a field never compared against the `repository.owner.login`/`organization.login` value used for secret selection: [5](#0-4) 

Shipit explicitly supports (and documents) multiple GitHub Apps/organizations, each with its own `webhook_secret`, keyed by organization name in config: [6](#0-5) [7](#0-6) 

**Equality that should hold, but doesn't:** `organization used to select/verify the webhook secret == organization owning the repository the handlers act on`. Before the attacker's request: for legitimate GitHub-originated webhooks these two fields naturally agree. After the attacker's request: an attacker who knows (or controls) the `webhook_secret` for *one* configured organization (e.g., their own org in a multi-tenant Shipit deployment, or a leaked secret for org A) can POST directly to `/webhooks` with `repository.owner.login = "orgA"` (so the correct/known secret is selected and the HMAC passes) while setting `repository.full_name = "orgB/critical-repo"` (an entirely different, victim organization/repository) inside the same JSON body that the handler uses to look up the `Stack`.

### Impact Explanation
This breaks the trust boundary between "the organization whose webhook secret authenticated this request" and "the repository/stack the request is allowed to mutate." Depending on event type, this lets the attacker:
- Inject arbitrary `push` events for a stack they don't own, driving `GithubSyncJob` to sync attacker-chosen SHAs into the victim stack's commit history.
- Forge `status`/`check_run`/`check_suite` events, marking arbitrary commits on a victim stack as passing CI.
- Manipulate `pull_request` events against a victim's review-stack provisioning.

If the victim stack has continuous deployment or merge-queue automation gated on CI status, spoofed green statuses can lead to an unauthorized deploy or merge — matching the Critical-tier impact criteria ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires the attacker to know a valid `webhook_secret` for at least one organization configured in the multi-org Shipit deployment (a realistic scenario for a self-service/multi-tenant Shipit instance where each org's admins configure — and thus know — their own secret), and requires that a `Stack` for the targeted victim `repository.full_name` already exists. No GitHub session, `ApiClient` token, or repository write access to the *victim* repo is needed — only knowledge of a currently-valid webhook secret for any onboarded organization, since the `/webhooks` endpoint is unauthenticated aside from that HMAC check.

### Recommendation
After selecting the GitHub App/secret for `repository_owner`, verify that `repository.owner.login` (or `organization.login`) actually matches `repository.full_name`'s owner segment before dispatching to handlers, or better, resolve the target `Stack`/`Repository` and re-derive/re-check its expected organization against the one used for signature verification, rejecting the event if they diverge.

### Proof of Concept
1. Attacker's own organization, `orgA`, is a legitimately configured multi-org Shipit tenant with a known `webhook_secret` (`SECRET_A`).
2. Victim `orgB/critical-repo` is tracked by the same Shipit instance as a `Stack`.
3. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/critical-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, body)>` and sets `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "orgA")` (from `repository.owner.login`), and the HMAC matches `SECRET_A`, so the request passes.
6. `PushHandler`/relevant handler then resolves the target using `payload.dig('repository','full_name')` = `"orgB/critical-repo"`, acting on the victim's `Stack` even though the request was only ever authenticated for `orgA`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml

  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
