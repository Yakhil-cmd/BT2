This is a strong match to the bug class: a payload-derived field is used to select the trust boundary (webhook secret/organization), while a *different* field within the same payload—not itself covered by that selection logic—determines which stack's data actually gets written.

### Title
Webhook signature verification selects the signing organization from `repository.owner.login`, but handlers act on the unrelated `repository.full_name`/`sha` fields, letting a valid webhook secret from one org forge state changes for stacks belonging to any other org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives the HMAC-verifying GitHub App/secret from `repository.owner.login` (or `organization.login`) taken out of the untrusted JSON body itself, then hands the same body to handlers that key their side effects off different payload fields (`repository.full_name` for `PushHandler`, or bare `sha` for `StatusHandler`) with no re-check that these fields belong to the organization whose secret was used. The equality the deployment trust model relies on — `organization whose secret verified this webhook == organization that owns the repository being acted upon` — is never enforced, because both values are attacker-controlled fields inside a single payload that is only self-consistent by GitHub's convention, not by any code-level check in this engine.

### Finding Description
`verify_signature` picks the app/secret to validate against purely from the payload: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Shipit natively supports configuring one GitHub App (and one distinct `webhook_secret`) per organization — this is a documented, in-scope feature: [3](#0-2)  and [4](#0-3) .

Once the signature check passes (using whichever org's secret matched `repository.owner.login`), the raw body is dispatched to handlers that read *other* fields to decide which `Stack`/`Commit` records to mutate:
- `PushHandler` looks up stacks by `payload.dig('repository','full_name')`, unrelated to `repository.owner.login`: [5](#0-4) [6](#0-5) 
- `StatusHandler` matches purely on `sha` across ALL stacks/orgs, with no repository/org check at all: [7](#0-6) 

Because an org owner/admin can freely create their own GitHub App on their own org and knows that org's `webhook_secret` (it's a secret *they* set when registering the app, not a secret controlled by the victim), they can compute a valid `X-Hub-Signature` for any payload body they like, entirely outside of GitHub's delivery pipeline, and POST it directly to `/webhooks`. `verify_signature` will select their own org's app (because `repository.owner.login` in the crafted payload says so) and validate successfully, even though the `repository.full_name` / `sha` fields embedded in that same body point at a stack belonging to a completely different, victim organization.

### Impact Explanation
Via `StatusHandler`, the attacker can inject arbitrary CI `state`/`context`/`description` values for **any known commit `sha`** belonging to a victim stack, without needing that org's webhook secret at all: [8](#0-7) . A forged `success` status on the relevant CI context is exactly what `Commit#add_status` uses to schedule merges: [9](#0-8) , which triggers `ProcessMergeRequestsJob`, and if `all_status_checks_passed?` now evaluates true because of the forged status, `MergeRequest#merge!` calls `stack.github_api.merge_pull_request` using Shipit's own GitHub App credentials for the *victim* stack: [10](#0-9) , [11](#0-10) . This is an **unauthorized merge** driven entirely by an attacker who only controls their own, unrelated organization's webhook secret — squarely inside the "Critical/High: unauthorized deploy, rollback or merge" impact bucket defined in scope.

### Likelihood Explanation
Requires the Shipit deployment to be configured for multiple GitHub organizations (the documented multi-org secrets schema), and the attacker to control (own) at least one such organization's GitHub App/webhook secret while targeting a victim stack hosted under a different organization on the same Shipit instance — a realistic scenario for any multi-tenant Shipit deployment, which is the express purpose of the "Using Multiple Github Applications" feature. No privileged Shipit session, `ApiClient` token, or GitHub write access to the victim repo is needed; only knowledge of one's own webhook secret and the target commit `sha`, which is often visible via the public GitHub commit page.

### Recommendation
In `WebhooksController`, after verifying the signature, re-derive and cross-check that every stack/repository/commit the handler is about to act on actually belongs to the same organization/repository the signature was verified against (i.e., bind `repository.full_name`'s owner to `repository_owner`, and constrain `StatusHandler`'s `Commit.where(sha:)` lookup to stacks under that verified organization). Do not trust `repository.full_name` or bare `sha` independently of the field used to select the signing secret.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s multi-org schema).
2. Attacker, an admin of `attacker-org`, knows `attacker-org`'s `webhook_secret` (they set it themselves).
3. Attacker crafts a JSON body:
```json
{
  "sha": "<victim-org-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/irrelevant" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>` and POSTs it to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, verifies against `attacker-org`'s secret — succeeds.
6. `StatusHandler` matches `Commit.where(sha: "<victim-org-commit-sha>")` regardless of organization and creates a forged success status on the victim's commit, potentially unblocking `MergeRequest#merge!` for the victim stack via Shipit's own GitHub credentials.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  class ProcessMergeRequestsJob < BackgroundJob
    include BackgroundJob::Unique
    on_duplicate :drop

    queue_as :default

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
  end
end
