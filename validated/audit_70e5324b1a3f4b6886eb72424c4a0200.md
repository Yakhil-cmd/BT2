### Title
Unbounded in-memory buffering of git command stdout/stderr allows memory-exhaustion DoS from attacker-controlled remote repo content - ([File: pkg/cmd/cmd.go])

### Summary
`git-sync`'s command runner captures the entire stdout and stderr of every git subprocess into unbounded `bytes.Buffer` instances before returning them as strings, with no byte-size cap or count limit. Since `git-sync` invokes `git` against a remote repository/ref that is fully attacker-controlled (the whole point of the tool is to sync from a possibly untrusted or compromised remote), a malicious remote can cause git commands (e.g. `git fetch`, `git log`, `git ls-remote`, `git worktree add`, `git submodule`, etc.) to emit multi-hundred-MB or multi-GB of output (huge commit messages, huge ref lists, verbose fetch progress with huge object counts, or crafted blobs echoed by some command), all of which is buffered fully in memory before any size check occurs. This directly mirrors the reported bug class: buffering untrusted, attacker-influenced data with no byte-size bound (here, not even a count bound), enabling heap exhaustion and denial of the sync process — analogous to the FutureMessageBuffer issue in besu, just at the transport/command layer instead of the consensus-message layer.

`outbuf`/`errbuf` are plain `bytes.NewBuffer(nil)` sinks attached directly to `cmd.Stdout`/`cmd.Stderr`. There is no `io.LimitReader`, no max-size truncation, and no incremental discard — the buffers grow without bound for as long as the child `git` process writes data, and the full contents are then materialized as Go strings (`stdout`, `stderr`) which are further copied by callers (e.g. into log fields, into `strings.Split` result slices) in `main.go`, e.g.: [3](#0-2) 

`git-sync` runs dozens of git subcommands via this same `Runner.Run` path (27 call sites in `main.go`) as part of the fetch/worktree/checkout cycle, all against the attacker-controlled `--repo`/`--ref`. Any of these commands whose output size scales with attacker-supplied repository content (commit messages, ref names/counts, verbose fetch/clone progress, submodule enumeration, `git config list` output which can be influenced by submodule `.gitmodules`/config entries fetched from the remote) can be inflated by a malicious server to force unbounded memory growth in the `git-sync` process, exactly as the FutureMessageBuffer advisory describes unbounded buffering of untrusted, size-uncontrolled payloads.

### Impact Explanation
Because the buffers are uncapped, a malicious or compromised remote git endpoint (the same "attacker-pushed commit/ref" trust boundary named in scope) can force `git-sync` to allocate memory proportional to attacker-chosen output size on every sync cycle. Given `git-sync` runs on a fixed `--period` and repeats fetch/log/config calls indefinitely, an attacker can repeatedly trigger allocation of oversized buffers, exhausting the sidecar container's memory limit and causing the process to be OOM-killed — a persistent sync denial of the kind explicitly listed as in-scope impact ("persistent sync denial"). This does not require any privileged git-sync flag; only that git-sync is configured to sync from the attacker-influenced repository/ref, which is the tool's normal operating mode.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where `--repo`/`--ref` point at a repository not fully trusted/controlled by the operator (e.g. syncing configs from a third-party or less-trusted upstream, or a compromised upstream account), since no attacker privilege beyond pushing content/refs to that repository is required. The condition is purely structural (any git subcommand output size), not dependent on a specific git feature flag.

### Recommendation
Wrap `cmd.Stdout`/`cmd.Stderr` in `runWithStdin` with a bounded writer (e.g. `io.LimitWriter`-equivalent or a custom capped buffer that truncates/errors past a configurable byte budget, similar to how `vendor/github.com/prometheus/procfs/net_ip_socket.go` uses `io.LimitReader` with an explicit `readLimit`), and fail the command (or truncate with a clear marker) once the limit is exceeded rather than allowing unbounded growth. Apply the cap uniformly to every call site in `pkg/cmd/cmd.go` so all git invocations, including fetch, log, worktree, and config listing, are protected.

### Proof of Concept
1. Configure `git-sync --repo=<attacker-controlled-repo> --ref=<branch>` pointing at a git server the attacker controls.
2. Attacker creates a commit whose commit message (or an object referenced by verbose fetch progress / `git log`/`git config list -z` output) is many hundreds of megabytes, or creates a very large number of refs/branches so that verbose git output balloons.
3. On each `--period` sync cycle, `git-sync` calls into `runWithStdin` (`pkg/cmd/cmd.go:63-93`) which unconditionally buffers all of that output into `outbuf`/`errbuf` with no size limit.
4. Repeated cycles (or a single sufficiently large payload) drive the `git-sync` sidecar's memory usage past its container limit, causing an OOM kill and persistent denial of the sync loop — without the attacker needing any credentials beyond the ability to push content to the synced repository/ref.

Note: I could not fully verify from the indexed content whether any of the 27 `Run` call sites in `main.go` pass `--verbose`/progress flags that would maximize attacker-controlled output size (e.g., exact `git fetch` flags) — a Devin session with full repository access would be needed to enumerate every call site and its argument list precisely.

func runWithStdin(ctx context.Context, log logintf, cwd string, env []string, stdin, command string, args ...string) (string, string, error) {
	cmdStr := cmdForLog(command, args...)
	log.V(5).Info("running command", "cwd", cwd, "cmd", cmdStr)

	cmd := exec.CommandContext(ctx, command, args...)
	if cwd != "" {
		cmd.Dir = cwd
	}
	if len(env) != 0 {
		cmd.Env = env
	}
	outbuf := bytes.NewBuffer(nil)
	errbuf := bytes.NewBuffer(nil)
	cmd.Stdout = outbuf
	cmd.Stderr = errbuf
	cmd.Stdin = bytes.NewBufferString(stdin)

	start := time.Now()
	err := cmd.Run()
	wallTime := time.Since(start)
	stdout := strings.TrimSpace(outbuf.String())
	stderr := strings.TrimSpace(errbuf.String())
	if ctx.Err() == context.DeadlineExceeded {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, ctx.Err(), stdout, stderr)
	}
	if err != nil {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, err, stdout, stderr)
	}
	log.V(6).Info("command result", "stdout", stdout, "stderr", stderr, "time", wallTime)

	return stdout, stderr, nil
