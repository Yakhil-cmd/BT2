### Title
Missing Registered-Token Validation in `handleERC20Transfer` Allows Operators to Mint or Transfer Arbitrary Tokens — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`handleERC20Transfer` in `BridgeTransferERC20` accepts a caller-supplied `_tokenAddress` and, in `modeMintBurn` mode, calls `ERC20Mintable(_tokenAddress).mint(...)` on it without ever verifying that `_tokenAddress` is in the `registeredTokens` whitelist. The outbound path (`_requestERC20Transfer`) correctly enforces `onlyRegisteredToken`, but the inbound handle path has no equivalent guard. With the default operator threshold of 1, a single operator can exploit this to mint arbitrary amounts of any token for which the bridge holds the minter role, or to drain any ERC-20 balance held by the bridge.

---

### Finding Description

`_requestERC20Transfer` (the outbound/request path) is decorated with both `onlyRegisteredToken(_tokenAddress)` and `onlyUnlockedToken(_tokenAddress)`: [1](#0-0) 

`handleERC20Transfer` (the inbound/handle path) has **no such modifiers**. After passing `onlyOperators` and the voting check, it directly casts `_tokenAddress` to `ERC20Mintable` and calls `mint`: [2](#0-1) 

The `registeredTokens` mapping in `BridgeTokens` is the authoritative whitelist of legitimate cross-chain token pairs: [3](#0-2) 

The voting mechanism uses `keccak256(msg.data)` as the vote key, so all parameters — including `_tokenAddress` — are part of the vote commitment: [4](#0-3) 

Critically, the **default operator threshold is 1**, meaning a single operator can unilaterally execute a value-transfer handle: [5](#0-4) 

The identical gap exists in `handleERC721Transfer`, which also lacks `onlyRegisteredToken` and calls `mintWithTokenURI` on the caller-supplied `_tokenAddress`: [6](#0-5) 

---

### Impact Explanation

**In `modeMintBurn = true` mode:** A single operator submits `handleERC20Transfer` with `_tokenAddress` set to any ERC-20 contract for which the bridge contract holds the `MinterRole`. The bridge calls `ERC20Mintable(_tokenAddress).mint(_to, _value)`, creating tokens out of thin air for an attacker-controlled `_to` address. This is an unauthorized mint of bridged assets.

**In `modeMintBurn = false` mode:** The bridge calls `IERC20(_tokenAddress).safeTransfer(_to, _value)`. Any ERC-20 token balance held by the bridge (including legitimately locked user deposits) can be drained to an attacker-controlled address. This is an unauthorized transfer of bridge-custodied assets.

Both outcomes directly satisfy the allowed impact gate: *unauthorized mint or transfer affecting bridged assets or system-managed funds*.

---

### Likelihood Explanation

- The default `operatorThresholds[ValueTransfer]` is **1**, so no collusion is required.
- Operators are semi-trusted relayers; a single compromised or malicious operator key is sufficient.
- The bridge is deployed in production service-chain configurations; the attack surface is reachable from any registered operator address.
- No privileged owner action is needed after the operator is registered.

---

### Recommendation

Add `onlyRegisteredToken(_tokenAddress)` (and optionally `onlyUnlockedToken(_tokenAddress)`) to `handleERC20Transfer` and `handleERC721Transfer`, mirroring the guards already present on the outbound paths:

```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,
    uint256 _value,
    uint64 _requestedNonce,
    uint64 _requestedBlockNumber,
    bytes memory _extraData
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // ADD THIS
    onlyUnlockedToken(_tokenAddress)     // ADD THIS
{
```

Apply the same fix to `handleERC721Transfer` in `BridgeTransferERC721.sol`.

---

### Proof of Concept

1. Bridge is deployed in `modeMintBurn = true` mode. Attacker controls one registered operator key (threshold = 1).
2. Attacker deploys `FakeToken` (or identifies any token where the bridge is a minter).
3. Attacker calls:
   ```solidity
   bridge.handleERC20Transfer(
       bytes32(0),          // _requestTxHash (arbitrary, not yet seen)
       attacker,            // _from
       attacker,            // _to
       fakeTokenAddress,    // _tokenAddress — NOT in registeredTokens
       1_000_000e18,        // _value
       nextNonce,           // _requestedNonce
       blockNumber,
       ""
   );
   ```
4. `onlyOperators` passes. `_voteValueTransfer` passes (threshold = 1, single vote). No `onlyRegisteredToken` check exists.
5. Bridge executes `ERC20Mintable(fakeTokenAddress).mint(attacker, 1_000_000e18)`.
6. Attacker receives 1,000,000 tokens minted from an unregistered contract, with no corresponding lock on the counterpart chain.
