## Confirmed analog: `Api::CCMenuController` ignores the ApiClient's `stack_id` scope

### Title
Unauthorized cross-stack read via CCMenu API token not scoped to its minted stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The external report's root cause is a check-vs-use mismatch: the code verifies one variable (`baseBalance`) but mints/acts on a different, unverified variable (`amount`). The Shipit engine analog is `Api::CCMenuController`, which authenticates an `ApiClient` token and checks a generic `read:stack` permission, but then resolves the *stack to render* from the raw `params[:stack_id]` instead of the stack the token was actually scoped/minted for.

### Finding Description
`Shipit::Api::BaseController` implements scoping for stack-bound tokens: [1](#0-0) 
`stacks` restricts the accessible set to `current_api_client.stack_id` when the client is scoped, and `stack` resolves `params[:stack_id]` **within that scope** via `stacks.from_param!`.

However, `Api::CCMenuController` overrides `stack` and bypasses this scoping entirely: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` relation, ignoring `current_api_client.stack_id`.

The CCMenu token is minted per-stack specifically to bind it to one stack: [3](#0-2) 
`CCMenuUrlController#fetch` creates (or reuses) an `ApiClient` with `permissions: %w[read:stack]` for `current_user`, embeds its `authentication_token` in a URL scoped to `stack.to_param`, and hands that URL out (e.g. published in CI dashboards, README badges, CCTray monitoring tools). The permission model only enforces the coarse `read:stack` scope at the class level (`require_permission :read, :stack` in `app/controllers/shipit/api/base_controller.rb:19-21` and `app/controllers/shipit/api/ccmenu_controller.rb:6`), never the per-`ApiClient.stack_id` binding — that binding is supposed to be enforced by `BaseController#stack`/`#stacks`, but `CCMenuController` doesn't use it.

Binding broken (equality that should hold but doesn't):
`ApiClient(token).stack_id == params[:stack_id] resolved by controller#stack`
In every other API controller inheriting `BaseController#stack` (deploys, tasks, locks, etc.) this equality is enforced. In `CCMenuController` it is not: the token only needs `read:stack` in its `permissions` array; the actual stack argument is taken unchecked from the request.

### Impact Explanation
Any holder of a valid CCMenu token (which is routinely embedded in plaintext query strings, shared with CI dashboards, IRC bots, or external CCTray/JetBrains/TeamCity monitors — i.e., exposed to systems/users below the trust level of the Shipit web session) can substitute an arbitrary `stack_id` and read deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state, etc.) for **any stack on the instance**, not just the one the token was minted for. This is an unauthenticated-scope escalation matching the rubric's "High: unauthenticated read of stack state, task streams or deploy output" — the attacker only needs *some* valid `read:stack`-scoped token (their own, legitimately minted for a stack they do have access to) to read every other stack's state.

### Likelihood Explanation
High. No privileged Shipit session, GitHub App key, or `api_clients_secret` is required beyond possessing one's own legitimately-issued CCMenu token (any user with access to any single stack can mint one via `CCMenuUrlController#fetch`). The exploit is a single parameter substitution on a documented, unauthenticated-by-header API route (`api_stack_ccmenu_url`), requiring no code execution, no write access, and no interaction with GitHub credentials.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` collection (inherited from `BaseController`) instead of `Stack.from_param!` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so a stack-scoped `ApiClient.stack_id` is enforced consistently with every other API controller.

### Proof of Concept
1. As User A (member of Stack A only), visit Stack A's settings page and trigger the CCMenu URL fetch (`CCMenuUrlController#fetch`, route backing "CCMenu URL" in `app/views/shipit/stacks/settings.html.erb`). This creates/returns an `ApiClient` named "CCMenu Client" scoped to `stack_id = Stack A.id` with `permissions = ["read:stack"]`, and returns a URL of the form:
   `GET /api/stacks/stack-a-owner/stack-a-repo/stack-a-env/ccmenu.xml?token=<TOKEN_A>`
2. Take `TOKEN_A` and replace the `stack_id` path segments with Stack B's identifiers (a stack User A has no access to):
   `GET /api/stacks/stack-b-owner/stack-b-repo/stack-b-env/ccmenu.xml?token=<TOKEN_A>`
3. `authenticate_api_client` in `app/controllers/shipit/api/ccmenu_controller.rb:33-36` accepts `TOKEN_A` via `ApiClient.authenticate(params[:token])`, `require_permission :read, :stack` passes because the client has `read:stack`, and `stack` resolves Stack B unchecked (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`), returning Stack B's build/deploy status in the response — despite `TOKEN_A` never being authorized for Stack B.

```ruby
# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
```
