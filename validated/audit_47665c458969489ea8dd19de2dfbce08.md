### Title
Cross-organization team membership injection via `github_id`-only lookup in `MembershipHandler` bypasses `authorized?`'s team gate - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` record solely by the attacker-controlled `team.id` field from the webhook payload, without verifying that `params.organization.login` matches the `organization` already stored on that `Team` row. Because `User#authorized?` and `force_github_authentication` only check Team primary-key membership (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`), an attacker who can produce a validly-signed `membership` webhook for ANY org configured in a multi-tenant Shipit install can add themselves as a member of a victim org's team, as long as the numeric `team.id` collides with a team already tracked by `Shipit.github_teams`.

### Finding Description
The broken binding: the code implicitly assumes `Team.find_by(github_id: X).organization == params.organization.login`, but nothing enforces this.

Path:
1. `WebhooksController#verify_signature` derives `repository_owner` from `organization.login` for membership events and verifies the signature using `Shipit.github(organization: repository_owner)`'s `webhook_secret` — this only proves the webhook came from *that* org, not that the team referenced belongs to it. [1](#0-0) [2](#0-1) 
2. `MembershipHandler#find_or_create_team!` performs `Team.find_or_create_by!(github_id: params.team.id)`. The lookup key is only `github_id`; `organization` is only assigned inside the creation block, so if a `Team` with that `github_id` already exists (e.g., a victim org's team already tracked because it's in `Shipit.github_teams`), the existing row is returned unchanged and the attacker-supplied `organization.login` is silently discarded. [3](#0-2) 
3. `process` then calls `team.add_member(member)` where `member` is built from the attacker-controlled `params.member.login`. [4](#0-3) 
4. `authorized?` grants access purely by DB-level Team id intersection: `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, with no organization check at all. [5](#0-4) 
5. `force_github_authentication` trusts `current_user.authorized?` as the final gate. [6](#0-5) 

Attacker request: a `POST /webhooks` with header `X-Github-Event: membership`, signed with the attacker's own org's `webhook_secret`, body:
```json
{"action":"added","team":{"id":<victim_team_github_id>,"name":"x","slug":"x","url":"https://example.com"},"organization":{"login":"<attacker-org>"},"member":{"login":"<attacker-login>"}}
```
Since the `Team` row for `victim_team_github_id` already exists (it is one of `Shipit.github_teams`), `find_or_create_by!` returns that exact row and adds the attacker as a member. No signature/permission check re-validates that the org in the payload actually owns that team id.

This fails specifically because the existing guards (`verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema) validate signature and shape, not team/organization ownership, and `authorized?`'s Team-id equality is the exact binding being subverted.

### Impact Explanation
A successful forgery lets an attacker who controls (or is trusted for) any org configured on a shared/multi-tenant Shipit instance grant themselves membership in another organization's authorized team, satisfying `authorized?` and passing `force_github_authentication`. This is a full authentication/authorization bypass into `Shipit.github_teams`, granting the attacker the same UI/API access as a legitimate victim-org team member (viewing stacks, triggering deploys/rollbacks, etc., subject to further per-stack checks). It is repeatable against any team whose `github_id` the attacker can learn, and the blast radius spans every tenant/org sharing the same Shipit deployment.

### Likelihood Explanation
Preconditions: (a) Shipit is configured for multiple organizations, each with its own webhook and the attacker legitimately controls at least one of them; (b) the victim's team is already present in the `teams` table (true once it's listed in `Shipit.github_teams` and has received at least one prior membership event, per `find_or_create_team!`'s create-on-first-webhook behavior — or an admin pre-created it); (c) attacker can determine the victim team's numeric GitHub `github_id` (given as a precondition in the question — plausible via brute force since team ids are small sequential integers, or leaked in other GitHub API responses). Given these, the exploit costs a single crafted, validly-signed HTTP POST and is fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` AND `organization` (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/raise if a `Team` with that `github_id` already exists under a *different* `organization` rather than silently reusing it.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/membership_handler_test.rb`, illustrative):
```ruby
victim_team = Shipit::Team.create!(github_id: 999, organization: 'victim-org', slug: 'devs', name: 'Devs')
Shipit.stubs(:github_teams).returns([victim_team])

attacker_login = 'attacker'
User.any_instance... # or stub find_or_create_by_login! to avoid live GitHub

handler = Shipit::Webhooks::Handlers::MembershipHandler.new(
  action: 'added',
  team: { id: 999, name: 'Devs', slug: 'devs', url: 'https://example.com' },
  organization: { login: 'attacker-org' },
  member: { login: attacker_login }
)
handler.process

attacker_user = Shipit::User.find_by(login: attacker_login)
assert_equal victim_team.id, attacker_user.teams.first.id
assert_includes Shipit.github_teams.map(&:id), attacker_user.teams.first.id
assert attacker_user.authorized?, "attacker incorrectly authorized via cross-org team id collision"
```
Assertions on both sides of the binding: `victim_team.organization` remains `'victim-org'` (unchanged, proving `organization.login` from the forged payload was ignored) while `attacker_user.teams.map(&:id)` still intersects `Shipit.github_teams.map(&:id)`, demonstrating `authorized?` returns `true` despite the team belonging to a different, non-attacker-controlled organization.
