## Finding: Confirmed — Missing Length-Parity Validation in `FeePayerSignature`/`MultiAgentSignature` REST Parsing

### Summary

The REST API's `VerifyInput for FeePayerSignature` implementation and the `TryFrom<&FeePayerSignature> for TransactionAuthenticator` conversion never check that `secondary_signer_addresses.len() == secondary_signers.len()`. The two vectors are converted independently and collected as-is, so a client-supplied JSON body with mismatched vector lengths is accepted and turned into a `TransactionAuthenticator::FeePayer` (or `::MultiAgent`) value whose address list and signer list are no longer positionally aligned.

### Finding Description

`FeePayerSignature::verify` only calls `.verify()` on each individual signer entry — it never compares vector lengths: [1](#0-0) 

The conversion into the canonical `TransactionAuthenticator` similarly maps `secondary_signer_addresses` and `secondary_signers` with two independent `.iter().map(...).collect()` calls — there is no `zip`, no length assertion, nothing that ties an address at index `i` to a signer at index `i`: [2](#0-1) 

The same pattern (no length check) exists for the non-fee-payer multi-agent case: [3](#0-2) 

Notably, elsewhere in the codebase, a different consumer (`all_signer_auth_keys`, used for encrypted-transaction key derivation) explicitly guards against exactly this scenario by returning `None` when `secondary_addresses.len() != secondary_auths.len()`: [4](#0-3) 

This shows the codebase is aware that mismatched vector lengths are a hazard for at least one downstream consumer, but the equivalent defensive check is absent from the REST-facing `FeePayerSignature`/`MultiAgentSignature` parsing path, so a malformed submission is not rejected at the API boundary itself.

### Impact Explanation

At minimum, this is a missing input-validation control at the REST admission boundary: the API accepts and silently constructs a structurally malformed `TransactionAuthenticator` (unequal address/signer vector lengths) instead of returning a validation error, contrary to the expectation that REST parsing should reject inconsistent input rather than passing it downstream. I was not able to confirm within the available exploration budget whether the core `TransactionAuthenticator::verify()` match arms for `MultiAgent`/`FeePayer` (in `types/src/transaction/authenticator.rs`) subsequently perform a strict length-equality check (vs. a lossy `zip`) before allowing a transaction to reach mempool/VM admission — that code was not fully retrievable in this session. If that downstream `verify()` also lacks a strict length check and instead zips the two vectors, an attacker could smuggle an extra unauthenticated address into `secondary_signer_addresses` (used later to derive the executed signer set) that never had a corresponding signature validated, which would be a genuine sender/signer-binding break. Absent confirmation of that downstream code path, the confirmed, provable issue is the missing validation at the API layer.

### Likelihood Explanation

Any unprivileged caller can submit an arbitrary JSON transaction body to the REST submission endpoint; no privileged key or pre-existing approval is required to trigger the missing-validation code path itself.

### Recommendation

Add explicit length-parity checks in `VerifyInput for FeePayerSignature` and the equivalent `MultiAgentSignature` verification (and/or in the `TryFrom` conversions) in `api/types/src/transaction.rs`, mirroring the guard already used in `all_signer_auth_keys`, so REST submissions with mismatched `secondary_signer_addresses`/`secondary_signers` lengths are rejected with a validation error rather than silently producing a malformed authenticator. Additionally, confirm/harden `TransactionAuthenticator::verify()` in `types/src/transaction/authenticator.rs` to use a strict length-equality bail before zipping addresses and signers, so this invariant is enforced defense-in-depth at the core-type level regardless of which entrypoint constructs the authenticator.

### Proof of Concept

Submit a REST transaction-submission JSON payload where `signature.type = "fee_payer_signature"` with `secondary_signer_addresses` containing 2 entries but `secondary_signers` containing only 1 entry. Based on the confirmed code above, `FeePayerSignature::verify()` performs no length check [1](#0-0) , and `TryFrom<&FeePayerSignature>` builds the `TransactionAuthenticator::FeePayer` from the two vectors independently without validation [5](#0-4) , so the malformed payload is not rejected at this layer with a clear "length mismatch" error, contrary to the expected behavior in the proof idea.
