### Title
Webhook signature verification is bound to `repository.owner.login`, while all event handlers act on the unverified `repository.full_name` - forging cross-repository webhook events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App / webhook secret to use for HMAC verification based on an **unauthenticated** field of the incoming payload (`repository.owner.login`), but every webhook handler subsequently acts on a **different** unauthenticated field of the same payload (`repository.full_name`) to resolve the target `Repository`/`Stack`. Because the HMAC signature only proves "this body was signed with organization X's secret," and does not bind the signature to the specific repository/org named in the body, an attacker who legitimately controls any single organization onboarded to Shipit (and therefore knows that organization's own GitHub App webhook secret) can forge an arbitrary payload whose `repository.owner.login` is their own org (to pass verification) while `repository.full_name` points at a completely different, victim organization's repository tracked by the same Shipit instance.

### Finding Description
`verify_signature` computes the signing key using data taken straight from the unverified body: [1](#0-0) [2](#0-1) 

`repository_owner` is read directly from `params.dig('repository', 'owner', 'login')` (or `organization.login`), i.e. attacker-controlled JSON, *before* the signature has been checked. `Shipit.github(organization: repository_owner)` then looks up that organization's dedicated webhook secret from `secrets.github` and uses it to verify `X-Hub-Signature`: [3](#0-2) 

Once the signature "verifies" (against whichever organization the attacker named), `create` dispatches the same raw JSON to every registered handler: [4](#0-3) 

Every handler resolves its target repository/stack from a *different* field of the same body, `repository.full_name`, with no re-check that this repository belongs to the organization whose secret was used to verify the signature: [5](#0-4) [6](#0-5) [7](#0-6) 

The equality that should hold is:

`organization authenticated by HMAC == organization that owns the repository the handlers mutate`

Instead, the code lets an attacker set:
- `repository.owner.login = "attacker-org"` (chosen so `Shipit.github(organization: "attacker-org")`'s secret — known to the attacker because they administer that org's GitHub App installation on the same Shipit instance — is used for verification), while
- `repository.full_name = "victim-org/victim-repo"` (used by every downstream handler to find the real, unrelated stack).

Because these two fields are never cross-checked, a valid signature computed with the attacker's own org secret authorizes a payload that fully controls another organization's `Stack` state.

### Impact Explanation
This breaks the deployment-trust boundary between organizations multiplexed on a single Shipit instance. Depending on which webhook event/handler is invoked, an attacker who only administers their own (unrelated, low-value) GitHub organization can, without ever touching the victim organization or the Shipit UI/API:
- Archive/unarchive victim review stacks (`ReviewStackAdapter#archive!`/`#unarchive!`), forcing deprovisioning or unwanted re-provisioning of the victim's environment: [8](#0-7) 
- Inject fabricated commit statuses, push events, or labels that Shipit uses to gate merges/deploys for the victim's stack, since the `push`/`status`/`pull_request` handlers all key off the same unauthenticated `repository.full_name`.

This is a cross-tenant/cross-repository write achieved purely by forging a webhook body, satisfying the "cross-repository writes" / "unauthorized deploy" Critical impact bar, since the org-vs-repository binding that the whole multi-tenant webhook trust model depends on is not enforced anywhere in the flow.

### Likelihood Explanation
Requires only that the attacker administers (or has installed the GitHub App for) at least one organization tracked by the same Shipit instance — an "unprivileged" foothold relative to the victim organization, with no Shipit session, API token, or victim credentials needed. Crafting the payload is trivial (plain JSON + HMAC-SHA1 using a secret the attacker legitimately possesses for their own org).

### Recommendation
In `verify_signature`, after resolving `github_app` and verifying the signature, additionally assert that `repository_owner` matches the owner portion of `params.dig('repository', 'full_name')` (and/or that the resolved `Repository`'s org matches the org whose secret authenticated the request) before allowing handlers to run; reject with `422` on mismatch.

### Proof of Concept
1. Attacker is an admin of `attacker-org`, which has the Shipit GitHub App installed, giving them `attacker-org`'s webhook secret (`secrets.github[:attacker-org][:webhook_secret]`).
2. Attacker crafts a JSON body, e.g. for `X-Github-Event: pull_request`:
```json
{
  "action": "closed",
  "number": 1,
  "pull_request": { "...": "..." },
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sender": { "login": "attacker-org" }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known webhook secret over this exact raw body.
4. POST to `/github/webhooks` (routed to `WebhooksController#create`). `verify_signature` resolves `repository_owner` = `"attacker-org"`, verifies successfully against `attacker-org`'s secret.
5. `ClosedHandler`/`ReviewStackAdapter` resolves the stack via `payload.dig('repository','full_name')` = `"victim-org/victim-repo"` and archives the victim's review stack — all triggered with credentials the attacker legitimately owns for an unrelated organization.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
          def archive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no Stack exists. Ignoring."
              )
              return true
            end
            return if stack.archived?

            stack.remove_from_provisioning_queue
            stack.deprovision
            stack.archive!(user, *args, &block)
          end

          def unarchive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no ReviewStack exists. Creating."
              )
              return create!
            end
            return unless stack.archived?

            stack.transaction do
              Shipit::ReviewStackProvisioningQueue.add(stack)
              stack.unarchive!(*args, &block)
            end
          end
```
