### Title
Unchecked `git add --intent-to-add` exit status in `_temp_index` lets a raced file deletion silently drop all untracked files (including still-present malicious ones) from the review diff - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`_temp_index` filters `untracked_paths` down to files that still `os.path.lexists` right before invoking `git add --intent-to-add -- <surviving>`, specifically to avoid the documented all-or-nothing failure of `git add -N`. However, the `subprocess.run` call for this `add` never checks `result.returncode`, so a TOCTOU race between the `lexists` filter and the actual `git add` execution (or the broader window between `compute_v2_review_set`'s `git status --porcelain` snapshot and this call) can still make the whole `add` command fail non-zero, and the failure is swallowed silently.

### Finding Description
`_temp_index` computes `surviving = [p for p in untracked_paths if os.path.lexists(os.path.join(cwd, p))]` and then runs `git add --intent-to-add -- <surviving>` [1](#0-0) . The code comment explicitly documents that `git add -N -- a b nonexistent` is atomic and exits 128 adding nothing if even one path is missing [2](#0-1) . The `surviving` filter is meant to close that gap by pre-checking existence, but:

1. The `lexists` check and the actual `subprocess.run` invocation are not atomic — a concurrent process (e.g. a build script, another Claude Code tool call, or any unprivileged local process/tool with file access to the same working tree) can delete, rename, or otherwise invalidate one of the `surviving` paths in the window between the Python-side filter and the `git add` process actually opening those paths.
2. Even in the non-race case, the call site never inspects the `subprocess.run` return code: `subprocess.run([...], cwd=cwd, capture_output=True, text=True, timeout=10, env=env)` result is discarded entirely [3](#0-2) . If `git add` fails for any reason (deleted path, permission error, corrupted worktree entry, symlink loop, etc.), execution proceeds straight to `yield env` as if the add had succeeded.
3. Because the temp index is a scratch copy that is discarded after the `with` block, a failed `add --intent-to-add` means none of the untracked paths (not just the raced one) receive intent-to-add markers in the temp index, so `git diff` run against that index in `get_git_diff` (line 419) shows none of them — including sibling files that are entirely unrelated to the race and still present and malicious on disk.
4. The window is not limited to the single `_temp_index` call; `compute_v2_review_set` first snapshots `untracked` via `_git_status_porcelain` [4](#0-3) , returns `untracked_in_review` [5](#0-4) , and only later is that list passed by a separate caller into `get_git_diff(..., untracked_paths=...)` which opens `_temp_index` [6](#0-5) . That gap (status call → diff call) is on the order of the hook's processing time (LLM turn, review pipeline), giving a realistic multi-hundred-millisecond-to-second window for an attacker-controlled concurrent process to manipulate files, not just the microsecond TOCTOU inside `_temp_index` itself.

### Impact Explanation
This is a review-evasion / detection-bypass bug: a malicious untracked file that should be included in the security review diff can be silently excluded because of an unrelated raced sibling causing the atomic `git add` to fail with its return code ignored. That undermines the core invariant of the security-guidance plugin — that the diff handed to the LLM reviewer reflects the true untracked-file set at review time — allowing attacker-authored code sitting as an untracked file to bypass Claude Code's automated security review entirely. This is a scoped detection-bypass/trust-boundary-bypass in the review/export logic, not remote code execution or credential theft, but it defeats the very security control the plugin exists to provide.

### Likelihood Explanation
Exploitation requires an unprivileged concurrent process or tool call in the same working tree (e.g., a build/watch process, another automation script, or a second Claude Code tool invocation) capable of touching one of the untracked files during the window between `_git_status_porcelain`'s snapshot and `_temp_index`'s `git add` call. That is plausible in many real dev environments (file watchers, linters, CI scripts, parallel Claude Code sessions) without requiring elevated privileges, though it does require reasonably precise timing to land in the vulnerable window and is inherently racy/non-deterministic (not reliably reproducible on demand, but repeatable with a fuzzing harness that mutates the untracked set on a timer/thread during the call).

### Recommendation
Check `result.returncode` from the `git add --intent-to-add` call in `_temp_index`. On non-zero exit, retry by re-filtering `surviving` against a fresh `lexists` check (loop with a bound, e.g. 2-3 attempts) before falling back to per-file `git add --intent-to-add -- <single path>` calls so one racily-missing file cannot silently exclude siblings that are still present. Also emit a `debug_log` warning on failure so silent exclusion is at least observable/telemetered.

### Proof of Concept
Integration/fuzz test in the plugin's git-diff test suite:
1. Create a repo with two untracked files, `benign.txt` and `malicious.py` (containing an obviously flagged pattern, e.g. `eval(input())`).
2. Call `compute_v2_review_set`-equivalent to obtain `untracked_paths = ["benign.txt", "malicious.py"]`.
3. Spawn a background thread/process that deletes `benign.txt` timed to race with (or monkeypatch `os.path.lexists` to return True then immediately delete the file before the `subprocess.run` call inside) `_temp_index`'s `git add` invocation.
4. Call `get_git_diff(cwd, baseline_sha, untracked_paths=untracked_paths)`.
5. Assert: if `git add` in this scenario returns non-zero (simulate by deleting `malicious.py` too, or forcing exit 128 via a monkeypatched `subprocess.run` for the add call), the resulting diff must still contain `malicious.py`'s content (i.e., the fix retries/falls back per-file) — the test should FAIL against current code because current code silently proceeds with an empty temp index and `malicious.py` is absent from `get_git_diff`'s output despite being present, untracked, and unrelated to the raced file.

def get_git_diff(cwd, baseline_sha, full_context=False, paths=None, untracked_paths=None):
    """
    Get the git diff between the baseline SHA and the current working tree,
    including untracked (new) files.

    Uses a temporary copy of the git index (GIT_INDEX_FILE) so the user's
    real index is never modified. The temp index gets intent-to-add entries
    for untracked files, making them visible in the diff output. Cleanup
    is just deleting the temp file in a finally block.

    If `paths` is given, the diff is restricted to those paths (relative to
    cwd; absolute paths are converted, paths outside cwd are dropped).
    `untracked_paths` (repo-root-relative) is forwarded to _temp_index so it
    can add only those files instead of scanning the whole worktree.
    """
    pathspec = _diff_pathspec(cwd, paths)
    if paths and not pathspec:
        # Caller restricted to specific paths but none are inside this repo
        # (e.g. only ~/.claude/... edits). Returning "" flows to skip(6); an
        # empty pathspec would mean an UNRESTRICTED diff — the bug this whole
        # change exists to fix.
        return ""

    cmd = [*GIT_CMD, "diff", "--no-color", "--no-ext-diff", baseline_sha] + (["--unified=99999"] if full_context else []) + pathspec
    try:
        with _temp_index(cwd, untracked_paths) as env:
            # env is None when no index could be found (bare repo / not a
            # repo) — diff still runs, just without untracked-file support.
            result = subprocess.run(cmd, cwd=cwd, capture_output=True, timeout=30, env=env)
