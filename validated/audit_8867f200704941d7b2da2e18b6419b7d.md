### Title
Cross-organization commit-status forgery via unscoped `Commit` lookup in `StatusHandler` breaks the org-authenticated-vs-repository-written binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` is used to validate an inbound webhook's HMAC based on an attacker-controlled field of the *same* payload (`repository.owner.login`), while `Webhooks::Handlers::StatusHandler` (invoked after that check passes) applies the payload's `sha`/`state` to **any** `Commit` record in the database that matches the SHA, with no scoping to the repository/organization that was actually authenticated. This is the same class of bug as the analog report: a value that is validated (the pivot price / here, the organization used to pick the verifying secret) is not the same value that is actually acted upon (the price computation / here, the commit that gets its CI status mutated), so an attacker who controls one tenant's credentials can affect a different tenant's data.

### Finding Description
`Shipit::WebhooksController#verify_signature` picks a `Shipit::GitHubApp` (and hence a `webhook_secret`) using an organization name taken straight from the JSON body: [1](#0-0) [2](#0-1) 

Shipit explicitly supports hosting multiple, independent GitHub organizations/apps behind the same webhook endpoint, each with its own `webhook_secret`: [3](#0-2) [4](#0-3) 

Once the signature check passes for whichever organization the payload claims to be from, the raw JSON body is dispatched to the registered handler for the event type: [5](#0-4) 

For the `status` event, the handler is `StatusHandler`, which looks up commits **purely by SHA**, with no filtering by `repository.full_name`/owner at all (unlike `PushHandler`, which at least scopes to `Repository.from_github_repo_name`): [6](#0-5) 

Compare this with the base `Handler` class, which *does* have a repository-scoping helper (`stacks`/`repository_name`) that `StatusHandler` does not use: [7](#0-6) 

The security-relevant equality that should hold is:
```
organization whose webhook_secret authenticated the request == organization owning the repository/commit being written
```
Instead, the code enforces only:
```
organization whose webhook_secret authenticated the request == organization named in payload["repository"]["owner"]["login"]
```
and the commit that actually gets mutated is chosen independently, by `sha` alone, with no cross-check against the authenticated organization. An attacker who legitimately controls one org's GitHub App installation on the same Shipit instance (a supported, documented multi-tenant configuration) knows that org's real `webhook_secret` and can therefore produce a **valid** HMAC signature for `X-Hub-Signature` over a payload of their own choosing. They can set `repository.owner.login` to their own org (so the signature check passes) while setting `sha` to the SHA of a commit that belongs to a completely different stack/organization hosted on the same instance, and set `state`/`context`/`description`/`target_url` to arbitrary values.

### Impact Explanation
Commit statuses are the mechanism `ci.require` in `shipit.yml` uses to gate whether a deploy is allowed to proceed (continuous delivery / deploy-blocking checks are driven by `Commit#statuses`, populated exactly through `create_status_from_github!` in `StatusHandler#process`). Because the lookup is unscoped, a low-privilege attacker who is a legitimate owner/admin of one org's GitHub App on a shared Shipit instance can forge a "success" status for a required CI context on a commit belonging to an unrelated, higher-privileged organization's stack, potentially satisfying the `ci.require` gate and causing an unauthorized deploy to be triggered for a repository/organization they do not otherwise have write access to. This matches the required "unauthorized deploy" Critical-impact criterion. It could equally be used to forge a failing status to block deploys on a victim stack.

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate, unprivileged tenant of a multi-org Shipit deployment (i.e., they administer their own GitHub App/organization with its own known `webhook_secret`) — no GitHub credentials or access to the victim organization are needed, and no Shipit session/API token is required, satisfying the "unprivileged attacker" scope of this review. This is a straightforward, deterministic bug in `StatusHandler`, not a probabilistic or resource-exhaustion issue, and directly parallels the reported bug class of "parameter used for validation differs from parameter used for the actual effect."

### Recommendation
Scope `StatusHandler#process` (and any other handler that doesn't already scope by repository) to only touch commits belonging to stacks whose `Repository` matches `payload.dig('repository', 'full_name')`, and additionally verify that this repository's owner matches the organization whose `webhook_secret` was used to authenticate the request, e.g. by rejecting the webhook if `repository.owner.login` (used for signature selection) does not match the repository actually referenced for the mutation.

### Proof of Concept
1. Set up (or be a legitimate low-privileged tenant of) `Org-Attacker`, which has its own configured GitHub App entry (`github.Org-Attacker.webhook_secret = S`) on a shared Shipit instance that also hosts `Org-Victim/private-repo` (per `docs/setup.md`'s multi-org configuration).
2. Note (or already know) the SHA of a commit belonging to a stack on `Org-Victim/private-repo` that Shipit has already ingested (e.g. via any public commit list, PR, or CI log leak).
3. Craft a JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "required-ci-check",
  "target_url": "https://example.com",
  "repository": { "owner": { "login": "Org-Attacker" }, "full_name": "Org-Attacker/some-repo" }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(S, body)>` using the known `Org-Attacker` webhook secret `S`.
5. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` resolves the org via `repository.owner.login` = `Org-Attacker`, uses `S`, and the signature verifies successfully.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (no repository/org scoping applied), and calls `create_status_from_github!`, injecting a forged "success" status for `required-ci-check` on `Org-Victim`'s commit — potentially unblocking a deploy gated by `ci.require` on that stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
