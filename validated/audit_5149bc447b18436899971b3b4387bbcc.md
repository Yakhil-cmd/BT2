### Title
API client tokens scoped to one stack can read CCMenu build status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via `stack_id`, enforced by `Api::BaseController#stacks`/`#stack` (`app/controllers/shipit/api/base_controller.rb:74-80`), which restricts the queryable `Stack` relation to `Stack.where(id: current_api_client.stack_id)` when the client is scoped. `Api::CCMenuController` overrides this `stack` accessor and instead calls `Stack.from_param!(params[:stack_id])` directly (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`), which queries the unscoped `Stack` relation for any repository/environment path, breaking the binding `token.stack_id == stack_accessed`.

### Finding Description
`ApiClient` permissions are checked purely by name (`read:stack`, etc.) in `ApiClient#check_permissions!` (`app/models/shipit/api_client.rb:38-45`) and never consult `stack_id`. The per-stack restriction relies entirely on controllers using the scoped `stacks`/`stack` helpers in `BaseController`. `Api::StacksController`, `Api::TasksController`, `Api::DeploysController`, and `Api::HooksController` all rely on (or explicitly reuse) `stacks.from_param!`, so a client scoped to stack A cannot address stack B through them. `Api::CCMenuController` instead defines its own `stack` method calling `Stack.from_param!` directly on the model class, ignoring `current_api_client.stack_id` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`). Before the attacker's request, the equality `token.stack_id == accessible_stack.id` holds for every other read endpoint; after issuing a request against `/ccmenu/*stack_id`, that equality is broken — any valid token carrying `read:stack` permission, no matter which single stack it was scoped to, can retrieve `show` output (build status, last build label/time, activity, web URL) for every stack in the installation.

### Impact Explanation
This is an unauthenticated-scope read of stack state comparable to the "High" tier described in scope: an attacker holding a narrowly-scoped `ApiClient` token (e.g., a low-privilege CCMenu client auto-created by `CCMenuUrlController` for any logged-in user, `app/controllers/shipit/ccmenu_url_controller.rb:15-18`) can enumerate build/deploy status of stacks outside the scope they were granted, defeating the per-stack authorization boundary that the rest of the API enforces.

### Likelihood Explanation
Any authenticated Shipit user can trivially obtain a stack-scoped `read:stack` token for one stack via the existing `/ccmenu/:stack_id` flow (`CCMenuUrlController#fetch`), then reuse that same token's HTTP Basic credentials against `/api/stacks/:other_stack_id/ccmenu` for a different stack path — no admin action or extra permission is required, only knowledge/guessing of another stack's `owner/name/environment` identifier, which is not treated as secret in Shipit.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped accessor, e.g. `stacks.from_param!(params[:stack_id])` (as `BaseController` and `Api::StacksController` already do), so a stack-scoped token cannot resolve stacks outside `current_api_client.stack_id`.

### Proof of Concept
1. As an authenticated user, call `GET /ccmenu/<owner>/<repo>/<env>` to have `CCMenuUrlController#fetch` mint a fresh `ApiClient` scoped to that one stack with `permissions: ['read:stack']`, returning its `authentication_token`.
2. Using that token as HTTP Basic auth, call `GET /api/stacks/<other_owner>/<other_repo>/<other_env>/ccmenu` — a stack the token was never scoped to.
3. `Api::CCMenuController#authenticate_api_client` (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`) accepts the token, `require_permission :read, :stack` passes because the token has `read:stack`, and `#stack` resolves via unscoped `Stack.from_param!`, returning the other stack's build status in the XML response — despite the token being minted for a different stack only.
