## Title
Webhook signature verification is keyed to an attacker-controlled `repository.owner.login` field, allowing cross-organization forged events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate an inbound webhook against by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted, attacker-supplied JSON body, rather than from any value that is itself authenticated independently of the signature it's used to select.

### Finding Description
The engine supports multiple GitHub Apps/organizations sharing a single `/webhooks` endpoint (`docs/setup.md` "Using Multiple Github Applications", `secrets_double_github_app.yml`). Each organization has its own `webhook_secret`. When a webhook arrives, the controller does: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of `params.dig('repository', 'owner', 'login')`, i.e., attacker-controlled JSON, and used to look up `Shipit.github(organization: repository_owner)` — the org whose `webhook_secret` will be used for HMAC verification. Verification success only proves "this body was signed with Org X's secret", it does **not** prove that the events/data contained in that body actually pertain to a repository owned by Org X.

Once verification passes, the raw params are dispatched to handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`), and each handler resolves the target `Stack`/`Repository` from a *different* field of the same payload — `repository.full_name` — via `Handler#stacks`/`Handler#repository_name`: [3](#0-2) 

and `Repository.from_github_repo_name`: [4](#0-3) 

Nothing ties `repository.owner.login` (the value used to pick the verifying secret) to `repository.full_name` (the value used to select which stack/repository is actually written to). Anyone who legitimately controls a GitHub App installation onboarded to this Shipit instance — even for a low-privilege organization they administer themselves — knows that organization's `webhook_secret` (it's configured by the org admin per `docs/setup.md`). Since HMAC verification only checks that *some* body was signed with *some* known org's secret, that org admin can construct an arbitrary JSON payload (not something GitHub generated) where `repository.owner.login` = "MyOwnOrg" (so the correct secret is selected and the signature computed over that exact custom body validates) but `repository.full_name` = "victim-org/victim-repo" (so handlers act on a completely different tenant's stack). This breaks the intended binding: *the organization whose secret authenticated the request* ≠ *the repository the handlers actually write to*.

### Impact Explanation
Handlers dispatched off this payload (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, `PullRequest` handlers) perform state-changing operations — e.g. `PushHandler#process` calls `stack.sync_github(expected_head_sha: ...)` on any matching stack for the forged `repository.full_name`/branch: [5](#0-4) 

An attacker who administers their own onboarded organization (with a valid, self-configured `webhook_secret`) can forge push/status/check_suite/membership events against **any other tenant's stacks** hosted on the same Shipit instance, triggering syncs, fake commit statuses, and team/membership mutation — a cross-repository/cross-tenant write that the victim organization never authorized. This satisfies the "cross-repository writes" Critical impact bucket, since the write is not scoped to the organization/repository that actually authenticated the request.

### Likelihood Explanation
Requires the attacker to control (i.e., be an admin of) at least one legitimate, low-privilege GitHub App/organization already onboarded onto the shared Shipit instance — a realistic scenario for any multi-tenant Shipit deployment as explicitly documented and supported (`secrets_double_github_app.yml`). No access to the victim's GitHub App, webhook secret, or `ApiClient` token is required, and no reliance on GitHub actually emitting a mismatched payload — the attacker crafts and POSTs the payload directly to `/webhooks`, computing the HMAC themselves with their own known secret.

### Recommendation
Bind the value used to select the verifying secret to the value used for dispatch: after verifying the signature with the secret associated with `repository_owner`, additionally assert that `repository.full_name`'s owner segment matches `repository_owner` (or, more robustly, resolve `Repository` via `full_name` first, then verify the signature strictly with that specific repository's associated organization secret, rejecting the request if the two disagree).

### Proof of Concept
1. Onboard organization `attacker-org` to the shared Shipit instance with a self-chosen `webhook_secret` (a legitimate deployment scenario per `docs/setup.md`).
2. Craft a `push` payload JSON with `repository.owner.login = "attacker-org"` (to select the correct secret for verification) but `repository.full_name = "victim-org/victim-repo"` and a target `ref`/`after` matching a real stack under `victim-org/victim-repo`.
3. Compute `X-Hub-Signature = sha1=HMAC(attacker-org's webhook_secret, raw_body)`.
4. POST to `/webhooks` with `X-Github-Event: push` and the forged signature header.
5. `WebhooksController#verify_signature` succeeds (secret matches `attacker-org`'s), then `PushHandler#process` resolves stacks via `repository.full_name = "victim-org/victim-repo"` and triggers `stack.sync_github` on the victim's stack — a write the attacker never had permission to perform.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
