### Title
`Api::CCMenuController#stack` bypasses `current_api_client.stack_id` scoping by calling `Stack.from_param!` instead of `stacks.from_param!` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` scopes stack lookups to the authenticated `ApiClient`'s authorized stack via `stacks` (which filters by `current_api_client.stack_id` when set) and `stack` (`stacks.from_param!`). `Shipit::Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, so any authenticated `ApiClient` token — even one restricted to a single stack — can read the CCMenu build status of any stack in the system.

### Finding Description
The binding that should hold is: `stack ∈ current_api_client.stack_id-authorized stacks`, i.e. for any authenticated request, `resolved_stack ∈ {s : s.id == current_api_client.stack_id}` when `current_api_client.stack_id?` is true.

In `Api::BaseController`:
```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`Api::CCMenuController` overrides `#stack` and drops the `stacks` scoping entirely:
```
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

The only authorization check performed before rendering is `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`:
```
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [3](#0-2) 

This only checks the string permission (`"read:stack"`) — it never compares `current_api_client.stack_id` to the target stack. The `stack_id` scoping is *only* enforced by `BaseController#stacks`/`#stack`, which `CCMenuController` bypasses by calling `Stack.from_param!` directly instead of `stacks.from_param!`. Because `Stack.from_param!` resolves against the entire `Stack` table with no client-scoping, any token with `read:stack` permission — regardless of its `stack_id` restriction — can fetch CCMenu XML (build status, activity, last build label/time, web URL) for any stack on the Shipit instance by simply changing `params[:stack_id]` in the request.

`Api::CCMenuController#authenticate_api_client` also confirms tokens are accepted via the `token` query param (as used by `CCMenuUrlController`, which mints exactly such scoped tokens: `ApiClient.create_with(permissions: %w[read:stack])`) [4](#0-3) , so this scoped-token flow is the intended, reachable usage pattern that gets bypassed.

### Impact Explanation
An attacker holding (or obtaining, e.g. via a leaked/shared CCMenu URL for one stack) a valid `ApiClient` token scoped to a single stack (`stack_id` set) can read the CCMenu status — build activity, last build status/label/time, web URL — of **any other stack** in the Shipit instance by substituting `stack_id` in the request URL. This is a cross-tenant, unauthenticated-relative-to-scope read of stack state, matching the High-severity category "escalation into ... unauthenticated read of stack state." It is fully repeatable against arbitrary stacks with a single HTTP GET per stack, with no rate limiting or further authorization checks involved.

### Likelihood Explanation
Preconditions: the attacker needs *some* valid `ApiClient` token with `read:stack` permission (typically obtained legitimately as a CCMenu URL for a stack they do have access to, e.g. via `CCMenuUrlController#fetch`, or any other means of legitimately possessing a scoped API client token). No GitHub secrets, session, or elevated role is required — only possession of a single scoped, already-created API token. Given that CCMenu URLs are designed to be embedded in third-party dashboards/tools (a normal, low-privilege use case), tokens of this kind are commonly distributed outside of Shipit's trust boundary, making exploitation low-cost and highly feasible once one such token is known.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from `BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
i.e., remove the override entirely (or make it call `stacks.from_param!`) so CCMenu respects `current_api_client.stack_id` scoping identically to every other API controller.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a client scoped to stack_a cannot fetch ccmenu status for stack_b" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: "main")

  scoped_client = ApiClient.create!(
    creator: @user,
    name: "Scoped CCMenu Client",
    permissions: %w[read:stack],
    stack_id: stack_a.id,
  )

  # Binding under test: stack ∈ { s : s.id == current_api_client.stack_id } == { stack_a }
  request.headers['Authorization'] = 'bleh'
  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

  # Expected per binding: stack_b ∉ {stack_a} => 404/403
  assert_response :not_found # or :forbidden

  # Actual (bug): controller resolves stack_b via Stack.from_param! and returns 200 with stack_b's data
  # assert_response :ok
  # assert_payload 'name', stack_b.to_param
end
```
This demonstrates that `stacks.from_param!` (as used elsewhere) would correctly 404 for `stack_b`, while `Api::CCMenuController#stack`'s `Stack.from_param!` override incorrectly resolves and serves it.
