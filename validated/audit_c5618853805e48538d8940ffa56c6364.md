## Title
`data_feed[[...]]` in AA formulas lets a caller-chosen `min_mci` window be manipulated the same way a too-short TWAP period can be gamed - ([File: formula/evaluation.js], [File: data_feeds.js])

### Summary
The external report is about `getUsdPrice(_period)` in a Solidity oracle where the caller/backend picks the averaging `_period`, and a short period lets an attacker move the price within that window before the read. The analogous pattern in `ocore` is the `data_feed[[oracles=..., feed_name=..., min_mci=...]]` (and `in_data_feed[[...]]`) oscript primitives, where the **AA author freely chooses `min_mci`** (the "period", expressed in MCI units instead of seconds) that bounds how far back the read is allowed to look. When an AA sets a `min_mci` that is very close to (or equal to) the current MCI, the read is serviced not only from stable, already-final data but, for AA evaluation, also from **unstable data-feed messages still sitting in the current DAG round** (`storage.assocUnstableMessages`), which can include data feeds posted in the very same or a still-unconfirmed batch of units as the AA trigger.

### Finding Description
`data_feed`/`in_data_feed` evaluation in oscript resolves to `dataFeeds.readDataFeedValue` / `dataFeeds.dataFeedExists`, passing `bAA` (true when evaluated inside an AA) and the `min_mci` value taken directly, unvalidated for "freshness", from the formula parameters supplied by the AA definition author: [1](#0-0) 

When `bAA` is true, `readDataFeedValue` first scans `storage.assocUnstableMessages` for **still-unstable** units authored by the oracle address(es) whose `latest_included_mc_index` falls within `[min_mci, max_mci]`, and only falls back to the stable KV-store lookup if no unstable candidate is found: [2](#0-1) 

The equivalent `dataFeedExists` used by `in_data_feed`/`in data feed` address-definition conditions does the same unstable-message scan when `bAA` is set: [3](#0-2) 

Because `min_mci` is just an integer supplied by the AA author (validated only for being a non-negative integer, not for representing any minimum look-back distance), an AA can be written (or, more importantly, a generic/reusable "price-reading" AA can be parameterized by `trigger.data`) to accept an oracle value with `min_mci` set arbitrarily close to `mci`/`last_ball_mci`. This is structurally identical to the reported bug: the oracle-price "period" is a free parameter, and a short period allows the value to be read essentially at "spot" resolution, including values that are still part of an unstable, reorganizable portion of the DAG: [4](#0-3) 

The whitepaper/test fixtures also show this exact "spot vs TWAP/MA" tension: `futures_contract.oscript` and `option_contract.oscript` intentionally read a moving-average feed (`GBYTE_USD_MA`) specifically to avoid short-window manipulation, confirming that AA authors are relied upon to pick a safe averaging feed/period themselves, with the platform (`ocore`) enforcing no minimum: [5](#0-4) [6](#0-5) 

### Impact Explanation
An AA that reads a price/data-feed value with an author-chosen, unbounded-minimum `min_mci` (or `min_mci` close to the trigger's MCI) can have that value read from a still-unstable unit posted by the oracle in the same DAG round as the trigger. If the oracle address is compromised, colludes, or is itself economically incentivized (e.g., an asset issuer acting as its own price oracle for a lending/futures/option AA), a value can be posted and consumed atomically before the DAG round stabilizes, allowing manipulation of AA fund flows (over/under payment, unfair liquidation, wrong futures settlement) analogous to a manipulated too-short TWAP. This can cause direct AA fund loss.

### Likelihood Explanation
Exploitability depends entirely on how a given AA is authored: the vulnerability is only reachable if an AA (or an `in data feed` address-definition authentifier) is written with a `min_mci` too close to current MCI or 0, and the value is used to move base/asset funds. `ocore` itself does not enforce a minimum look-back window, unlike the recommendation in the report. This mirrors the "Acknowledged"/by-design status of the original finding: the underlying primitive is intentionally flexible, and safety is delegated to the AA author, so likelihood is tied to AA-authoring practices rather than a platform-level guarantee.

### Recommendation
Consider adding an optional or default minimum look-back distance for `data_feed`/`in_data_feed`/`in data feed` when used in AA/authentifier contexts (e.g., a documented minimum `min_mci` distance, or excluding not-yet-stable oracle-authored units from the unstable-message fast path unless the AA explicitly opts into low-latency unstable reads). At minimum, clearly document in the oscript reference that `min_mci` acts like a TWAP "period" and that AA authors relying on price feeds should choose values far enough behind `last_ball_mci`/`mci` to avoid consuming still-unstable oracle posts, and should prefer averaged feeds (as done in the `_MA` sample contracts) over instantaneous ones.

### Proof of Concept
1. Deploy an AA whose response formula includes `data_feed[[oracles='<ORACLE>', feed_name='PRICE', min_mci=0]]` (or a very small explicit `min_mci`), used to size a payment (e.g., futures/option settlement as in `test/samples/futures_contract.oscript`).
2. As the oracle (or a colluding actor controlling the oracle address), post a `data_feed` unit with a favorable price value, and in the same DAG round send the AA-triggering unit referencing/using this still-unstable value.
3. Because `bAA=true` causes `readDataFeedValue`/`dataFeedExists` to scan `storage.assocUnstableMessages` for oracle-authored units whose `latest_included_mc_index` falls within `[min_mci, mci]` (`data_feeds.js:204-273`, `data_feeds.js:13-97`), the AA consumes the manipulated, not-yet-stabilized price and pays out based on it.
4. If the DAG later reorganizes such that the manipulated data-feed unit's position/stability changes, the AA's already-executed response (fund transfer) cannot be reversed, resulting in fund loss/inflation relative to the "true" stabilized price - the same class of loss described for a too-short TWAP window.

function readDataFeedValue(arrAddresses, feed_name, value, min_mci, max_mci, unstable_opts, ifseveral, timestamp, handleResult){
	var bLimitedPrecision = (max_mci < constants.aa2UpgradeMci);
	var start_time = Date.now();
	var objResult = { bAbortedBecauseOfSeveral: false, value: undefined, unit: undefined, mci: undefined };
	var bIncludeUnstableAAs = !!unstable_opts;
	var bIncludeAllUnstable = (unstable_opts === 'all_unstable');
	if (bIncludeUnstableAAs) {
		var arrCandidates = [];
		for (var unit in storage.assocUnstableMessages) {
			var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
			if (!objUnit)
				throw Error("unstable unit " + unit + " not in assoc");
			if (!objUnit.bAA && !bIncludeAllUnstable)
				continue;
			if (objUnit.sequence !== 'good')
				continue;
			if (objUnit.latest_included_mc_index < min_mci || objUnit.latest_included_mc_index > max_mci)
				continue;
			if (_.intersection(arrAddresses, objUnit.author_addresses).length === 0)
				continue;
			storage.assocUnstableMessages[unit].forEach(function (message) {
				if (message.app !== 'data_feed')
					return;
				var payload = message.payload;
				if (!ValidationUtils.hasOwnProperty(payload, feed_name))
					return;
				var feed_value = payload[feed_name];
				if (value === null || value === feed_value || value.toString() === feed_value.toString())
					arrCandidates.push({
						value: string_utils.getFeedValue(feed_value, bLimitedPrecision),
						latest_included_mc_index: objUnit.latest_included_mc_index,
						level: objUnit.level,
						unit: objUnit.unit,
						mci: max_mci // it doesn't matter
					});
			});
		}
		if (arrCandidates.length === 1) {
			var feed = arrCandidates[0];
			objResult.value = feed.value;
			objResult.unit = feed.unit;
			objResult.mci = feed.mci;
			if (ifseveral === 'last')
				return handleResult(objResult);
		}
		else if (arrCandidates.length > 1) {
			if (ifseveral === 'abort') {
				objResult.bAbortedBecauseOfSeveral = true;
				return handleResult(objResult);
			}
			arrCandidates.sort(function (a, b) {
				if (a.latest_included_mc_index < b.latest_included_mc_index)
					return -1;
				if (a.latest_included_mc_index > b.latest_included_mc_index)
					return 1;
				if (a.level < b.level)
					return -1;
				if (a.level > b.level)
					return 1;
				if (bIncludeAllUnstable) // still ambiguous, sort randomly (it's OK outside AAs)
					return 1;
				throw Error("can't sort candidates "+a+" and "+b);
			});
			var feed = arrCandidates[arrCandidates.length - 1];
			objResult.value = feed.value;
			objResult.unit = feed.unit;
			objResult.mci = feed.mci;
			return handleResult(objResult);
		}
