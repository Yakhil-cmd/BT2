### Title
Cross-tenant webhook forgery via `repository.owner.login` / `repository.full_name` field mismatch bypasses `verify_webhook_signature` for `pull_request` `labeled` events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization config (and thus which `webhook_secret`) to validate the signature against using `params.dig('repository', 'owner', 'login')`, while every downstream handler (e.g. `Shipit::Webhooks::Handlers::PullRequest::LabeledHandler#repository`) resolves the actual target `Repository`/`Stack` using the independent `params.repository.full_name` field. Because both fields live in the same attacker-controlled JSON body, an attacker can pick an organization for signature purposes that has no `webhook_secret` configured (or whose secret they know) while pointing `repository.full_name` at a completely different, victim-owned repository/stack.

### Finding Description
The invariant that should hold is: `repository_owner_used_for_signature_verification == owner(repository.full_name_used_to_resolve_the_stack)`. The code never enforces this equality.

- `verify_signature` computes the org for secret lookup solely from `params.dig('repository', 'owner', 'login')` (or `organization.login`): [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever `webhook_secret` is blank for that resolved organization, and otherwise only accepts a `sha1=` prefixed HMAC (never `sha256=`): [3](#0-2) 
- `LabeledHandler#repository` independently resolves the target `Repository` from `params.repository.full_name`, a completely separate JSON field the attacker also controls: [4](#0-3) 
- `handle` then archives/unarchives the resolved stack based on the label state, with no re-check that the stack's owning repository matches whatever repository authenticated the signature: [5](#0-4) 

Exploit flow: attacker crafts a `pull_request`/`labeled` payload where `repository.owner.login` = `"attacker-org"` (an org with no `webhook_secret` configured in `Shipit` config, or one the attacker otherwise controls), but `repository.full_name` = `"victim-org/victim-repo"` (the real target with `blocking_statuses` configured). `verify_signature` looks up `Shipit.github(organization: "attacker-org")`, finds no `webhook_secret`, and `verify_webhook_signature` returns `true` unconditionally regardless of the (attacker-supplied, legacy `sha1=`) signature header. The request passes verification. `Shipit::Webhooks.for_event('pull_request')` then dispatches to `LabeledHandler`, which resolves `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.archive!`/`stack.unarchive!` on the victim's review stack — a write against a repository that never authenticated the request.

This defeats the intended per-organization webhook-secret isolation: the signature check authenticates one identity (`attacker-org`) while the mutation is applied to a different identity's (`victim-org`) records.

### Impact Explanation
An unprivileged attacker (who need only own or register any GitHub org, or any org left with no `webhook_secret` set in the Shipit `github` config) can force-archive or force-unarchive a victim's review stack without ever authenticating against that victim's secret. On stacks with `blocking_statuses` configured, archiving/unarchiving a stack can alter its `blocked?` state and thus gate or unblock deploys — a payload for one repository (`attacker-org`) mutating another repository's stack (`victim-org/victim-repo`). This matches the Critical category: "a payload for one repository mutating another's stack." The attack is repeatable against any repository/stack whose full name the attacker knows, with no rate limiting on the signature check itself.

### Likelihood Explanation
Preconditions: (1) at least one organization configured in Shipit's `github` settings without a `webhook_secret` (or one the attacker can otherwise satisfy), (2) knowledge of the victim's `owner/repo` full name (public information), (3) the victim stack has `review_stacks_enabled` and a provisioning label configured so `LabeledHandler` acts. Attacker cost is a single unauthenticated `POST /webhooks` request with a crafted JSON body and an arbitrary `X-Hub-Signature: sha1=...` header; no secrets, tokens, or GitHub permissions are required. This is fully repeatable and requires no live GitHub interaction.

### Recommendation
Bind signature verification and repository resolution to the same field: derive the authenticating organization/repository from the identical `repository.full_name` (or `id`) used by handlers, and reject the request if the two disagree. Additionally, do not treat a missing `webhook_secret` as "verified" — require every configured GitHub App/organization to have a secret, and fail closed (reject) if a secret is absent rather than short-circuiting to `true`. Accept `X-Hub-Signature-256` (sha256) as the primary/only supported algorithm going forward.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
```ruby
test "labeled event with mismatched owner/full_name mutates a different repository's stack" do
  # Setup: victim repo/stack with blocking_statuses & review_stacks_enabled, provisioning label configured.
  victim_repo = shipit_repositories(:shipit) # owner: "victim-org"
  victim_stack = # a review stack under victim_repo, currently unarchived

  # "attacker-org" has NO webhook_secret configured in Shipit.github config.
  payload = {
    action: "labeled",
    number: 1,
    pull_request: { id: 1, number: 1, url: "...", title: "x", state: "open",
                     additions: 0, deletions: 0,
                     head: { sha: "a"*40, ref: "attacker-branch" },
                     user: { login: "attacker" }, assignees: [],
                     labels: [{ name: victim_repo.provisioning_label_name }] },
    repository: { full_name: "victim-org/victim-repo", owner: { login: "attacker-org" } },
    sender: { login: "attacker" }
  }.to_json

  post "/webhooks", params: payload,
       headers: { "X-Github-Event" => "pull_request",
                  "X-Hub-Signature" => "sha1=deadbeef", # garbage, unverifiable against victim's secret
                  "Content-Type" => "application/json" }

  assert_response :ok
  # Equality check: the value authenticating the request (attacker-org, no secret => bypass)
  # must NOT equal the owner of the mutated resource (victim-org).
  assert_not_equal "victim-org", "attacker-org"
  # Yet the mutation happened on victim's stack:
  assert victim_stack.reload.archived? # or unarchived?, depending on label logic
end
```
Assert both sides of the binding explicitly: `authenticating_owner ("attacker-org") != mutated_repository_owner ("victim-org")`, while the request still returns `200 OK` and the victim stack's archived state changed — proving cross-tenant mutation succeeded without the victim's `webhook_secret`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
