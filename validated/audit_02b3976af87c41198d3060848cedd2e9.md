### Title
Bridge Fallback KLAY Transfer Uses Execution-Time `feeOfKLAY` With No User-Controlled Maximum — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

The fallback function in `BridgeTransferKLAY` reads the mutable `feeOfKLAY` state variable at execution time and passes it directly as the `_feeLimit`. A bridge operator who increases `feeOfKLAY` between a user's transaction submission and its execution causes the user to pay a higher bridge fee than anticipated and receive less KAIA on the counterpart chain — with no on-chain guard to protect them.

---

### Finding Description

`BridgeTransferKLAY.sol` exposes three entry points for KLAY bridge requests:

1. **Fallback** (line 127–129):
```solidity
function () external payable {
    _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
}
```
The `_feeLimit` argument is set to the **current** `feeOfKLAY` at execution time.

2. **`requestKLAYTransfer`** (line 132–135):
```solidity
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
```
Here `feeLimit = msg.value − _value` is caller-controlled; if `feeOfKLAY > feeLimit` the call reverts — **protected**.

Inside `_requestKLAYTransfer`, the value credited to the counterpart chain is:
```solidity
msg.value.sub(_feeLimit)   // line 118
```
and `_payKLAYFeeAndRefundChange(_feeLimit)` in `BridgeFee.sol` (line 43–66) reads `feeOfKLAY` again and pays exactly that amount to `feeReceiver`.

Because the fallback sets `_feeLimit = feeOfKLAY` at call time, both the fee paid and the value deducted from `msg.value` equal whatever `feeOfKLAY` is at execution time. The user has no parameter to cap this.

`feeOfKLAY` is a mutable storage variable:
```solidity
uint256 public feeOfKLAY = 0;   // BridgeFee.sol line 30
```
changed by operators via:
```solidity
function setKLAYFee(uint256 _fee, uint64 _requestNonce) external onlyOperators { ... }
// BridgeTransferKLAY.sol line 144–152
```

### Impact Explanation

**Concrete scenario** (configuration threshold = 1, single operator):

| Step | State |
|---|---|
| User observes `feeOfKLAY = 0.4 KAIA` | — |
| User submits fallback with `msg.value = 1.4 KAIA`, expecting to bridge 1.0 KAIA | pending |
| Operator submits `setKLAYFee(0.8 KAIA, nonce)` — included first | `feeOfKLAY = 0.8` |
| User's fallback executes: `_feeLimit = feeOfKLAY = 0.8` | — |
| `require(1.4 > 0.8)` passes | — |
| `_payKLAYFeeAndRefundChange(0.8)`: pays 0.8 KAIA to `feeReceiver`, refund = 0 | — |
| `RequestValueTransfer` emitted with `valueOrTokenId = 1.4 − 0.8 = 0.6 KAIA` | — |

The user paid **0.4 KAIA more** in fees than expected and bridged **0.4 KAIA less** than intended. The excess fee is transferred to `feeReceiver` — an unauthorized fee charge affecting KAIA.

This matches the allowed impact gate: *"Unauthorized fee charge affecting KAIA or bridged assets."*

---

### Likelihood Explanation

- Bridge operators are a small, semi-trusted set. A single operator can execute this if the configuration threshold is 1 (the default after deployment before `setOperatorThreshold` is called).
- Even with threshold > 1, colluding operators can coordinate the fee increase.
- The fallback is the documented and tested primary path for users sending KAIA directly to the bridge contract (confirmed by `bridge.test.ts` "send fallback" test).
- No mempool ordering privilege is required — the operator simply needs their `setKLAYFee` transaction to land in an earlier block or earlier in the same block.

---

### Recommendation

Add a caller-supplied maximum-fee guard to the fallback path. Since the fallback cannot accept parameters, introduce a dedicated function:

```solidity
// New: user specifies the maximum fee they accept
function requestKLAYTransferWithMaxFee(
    address _to,
    uint256 _maxFee,
    bytes calldata _extraData
) external payable {
    require(feeOfKLAY <= _maxFee, "fee exceeds maxFee");
    _requestKLAYTransfer(_to, msg.value.sub(msg.value.sub(_maxFee)), _extraData);
}
```

Or, more simply, revert in the fallback if `feeOfKLAY` has changed beyond a threshold the user can set via a separate "expected fee" storage slot per sender. The minimal fix mirrors the auditor's recommendation in the external report: **revert if the actual fee exceeds the user's stated maximum**.

```
  User expected: bridge 1.0 KAIA, pay 0.4 KAIA fee

  Unauthorized extra fee extracted: 0.4 KAIA
```

```text
    function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
        }

        if (_feeLimit > 0) {
            (bool ok, ) = msg.sender.call.value(_feeLimit)("");
            require(ok, "refund fee failed");
        }
        return 0;
    }
```
