### Title
Webhook signature is verified against the organization in `repository.owner.login`, but the acted-upon repository is selected from the independent `repository.full_name` field, allowing cross-organization forgery of GitHub events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification from `params.dig('repository', 'owner', 'login')` [1](#0-0) , while `Shipit::Webhooks::Handlers::Handler#stacks` selects the actual `Repository`/`Stack` to mutate from the independent `payload.dig('repository', 'full_name')` field of the same attacker-supplied JSON body [2](#0-1) . Nothing binds these two fields together, so a caller who legitimately controls one organization's webhook secret (e.g. an org onboarded in a multi-org Shipit config) can sign a payload whose `owner.login` matches their own org (passing signature verification) while `full_name` points at a stack belonging to a different, unrelated organization/repository.

### Finding Description
`verify_signature` computes the signing organization purely from attacker-controlled JSON:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

Once the signature check passes, the handler dispatch never re-derives or cross-checks the organization; it independently re-reads `repository.full_name` to look up the real target:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler#process` and `StatusHandler`/`CheckSuiteHandler` (same base `Handler#stacks`) then operate on whatever stack this `full_name` resolves to, e.g. enqueuing a `GithubSyncJob` or creating a `Status`/`CheckRun` record for that stack's commit [4](#0-3) .

Because `owner.login` and `full_name` are two independent JSON fields inside the same raw HTTP body that the signature covers byte-for-byte, the HMAC only proves "this exact byte string was signed by organization X's secret" — it says nothing about internal field consistency. An attacker who knows the webhook secret for their own onboarded organization can therefore craft a body where `owner.login = "attacker-org"` (so `Shipit.github(organization: "attacker-org")`'s secret validates the signature) but `repository.full_name = "victim-org/victim-repo"` (so the handler acts on the victim's `Stack`). This breaks the binding "organization that authenticated == repository that is written."

### Impact Explanation
The most consequential handler affected by this decoupling is `StatusHandler`, which creates a `Status` record for a commit on the resolved stack based on attacker-supplied `sha`/`state`/`context` fields (confirmed by `webhooks_controller_test.rb`'s `":state create a Status for the specific commit"` test) [5](#0-4) . Shipit's `ci.require` deploy-safety gate blocks deploys unless required status contexts report success on the commit being deployed (per README's CI section) [6](#0-5) . An attacker who controls the webhook secret for any organization onboarded to a shared/multi-tenant Shipit instance can forge a `status` event whose signature validates against their own org but whose `repository.full_name`/`sha` target a victim stack, injecting a forged "success" status that was never actually produced by CI on the victim's repository. This can satisfy `ci.require` and enable an otherwise-blocked, unauthorized deploy to proceed — matching the Critical-impact category "an unauthorized deploy."

### Likelihood Explanation
Exploitability requires only that the attacker be an unprivileged tenant with their own organization/GitHub App configured in Shipit's multi-org `github:` secrets structure (a supported, documented configuration) [7](#0-6) , and that they know their own `webhook_secret` (which they configure themselves when setting up their GitHub App). No access to the victim's repository, no Shipit session, and no `ApiClient` token is needed — they only need to POST a hand-crafted JSON body with a correctly computed HMAC to the shared `/github/webhooks` endpoint. This is a realistic misuse path in any deployment where more than one organization/tenant shares a single Shipit instance.

### Recommendation
Do not trust the `repository.owner.login` (or `organization.login`) field alone to pick the verification secret while separately trusting `repository.full_name` to pick the mutation target. After verifying the signature, re-derive the acting organization from the same trusted source used for signature selection (or from the `Repository` record already stored in Shipit, matched by both owner and name) and reject the event if `repository.owner.login` does not match the owner embedded in `repository.full_name`. Alternatively, since Shipit already resolves `Repository.from_github_repo_name`, verify that the resolved `Repository#owner` equals `repository_owner` used for signature selection before dispatching to any handler.

### Proof of Concept
1. Shipit instance is configured with two organizations, `attacker-org` (attacker's own, webhook secret `S_A` known to the attacker) and `victim-org` (unrelated tenant with an existing `Stack` for `victim-org/victim-repo`), per the multi-org `github:` secrets format [7](#0-6) .
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim commit sha awaiting a required CI context>",
  "state": "success",
  "context": "<required ci context name>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_A, body)` using their own known secret `S_A`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature against `S_A` [8](#0-7) .
5. The `status` handler resolves the target stack via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` [2](#0-1)  and creates/updates a `Status` record on the victim's commit with the attacker-chosen `state`/`context`, even though the attacker has no access to `victim-org`.
6. If the forged context matches a `ci.require` entry on `victim-org/victim-repo`'s `shipit.yml`, the victim stack's deploy safety check now sees a fabricated "success," enabling an unauthorized deploy.
