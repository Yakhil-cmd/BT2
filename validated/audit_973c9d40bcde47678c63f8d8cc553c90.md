### Title
Complete liquidity withdrawal permanently zeroes `pool_state.lp_supply` and drains vault reserves, causing permanent denial-of-service of `deposit` (and effectively of `swap`) - (File: `programs/cp-swap/src/instructions/withdraw.rs`, `programs/cp-swap/src/instructions/deposit.rs`)

### Summary
A liquidity provider who holds the entire *circulating* LP supply of a pool can call `withdraw` with `lp_token_amount == pool_state.lp_supply`, which drains 100% of the vault reserves and sets `pool_state.lp_supply` to `0`. Any subsequent call to `deposit` divides by `pool_state.lp_supply` inside `CurveCalculator::lp_tokens_to_trading_tokens`, which fails/returns `None` when the denominator is `0`, permanently reverting with `ErrorCode::ZeroTradingTokens`. Because the pool PDA and `lp_mint` were created with Anchor `init` (one-time initialization), the pool can never be "reset" the way HydraDX suggested (i.e., "re-add the token as if it were new") — the pool is permanently bricked for deposits, and since the vault reserves are also fully drained, `swap_base_input`/`swap_base_output` on this pool are effectively dead as well (zero reserves).

### Finding Description
`withdraw` computes the amount to return to the LP using `pool_state.lp_supply` as the denominator of the pro-rata share, not the LP mint's true total supply: [1](#0-0) 

`pool_state.lp_supply` is explicitly documented as the "True circulating supply without burns and lock ups" — i.e., it deliberately excludes the 100 LP tokens permanently locked at pool creation: [2](#0-1) 

At `initialize`/`initialize_with_permission`, a `lock_lp_amount = 100` is subtracted from the minted amount given to the creator, and the initial `lp_supply` field is set to the circulating (non-locked) value: [3](#0-2) 

Because `withdraw`'s payout formula uses `lp_token_amount / pool_state.lp_supply * total_token_x_amount`, a single LP who holds all of the circulating supply can pass `lp_token_amount = pool_state.lp_supply`, which yields a ratio of `1`, entitling them to the **entire** vault balance (`total_token_0_amount`, `total_token_1_amount`) — even though the locked 100 LP tokens still notionally exist and are supposed to represent a permanent, unspendable claim on the pool. After this withdrawal: [4](#0-3) 
`pool_state.lp_supply` becomes `0` and the vaults are drained to (near) zero.

Any subsequent `deposit` call recomputes shares via the same curve function, now with `pool_state.lp_supply == 0` as the denominator: [5](#0-4) 
`CurveCalculator::lp_tokens_to_trading_tokens` performs a division by `lp_token_supply`; with `lp_token_supply = 0` this cannot succeed and the function returns `None`, which is converted to `ErrorCode::ZeroTradingTokens` and the whole instruction reverts.

Unlike the HydraDX case (where the team argued the affected asset can simply be re-added to the Omnipool "as if new"), this Solana program cannot recover: the pool's PDA (`pool_state`) and `lp_mint` account were created via Anchor's `init` constraint during `initialize`, which can only succeed once per (`amm_config`, `token_0_mint`, `token_1_mint`) triple: [6](#0-5) 
There is no instruction to reset `lp_supply` or re-run `initialize` on an already-initialized pool, so the DoS on `deposit` is permanent for that specific pool.

### Impact Explanation
Once `pool_state.lp_supply` reaches `0`:
- `deposit` permanently reverts for that pool (division/`None` on zero supply), so no new liquidity can ever be added again.
- The vault reserves are drained to (near) zero by the final withdrawer, so `swap_base_input`/`swap_base_output`, which rely on nonzero reserves for the constant-product math, are also effectively unusable.
- This is a full, permanent freeze of the pool's core functionality (deposit and swap), matching the "Medium" impact class recognized in the HydraDX report ("function of the protocol or its availability could be impacted"), and can be triggered by ordinary LP behavior (all LPs exiting) or deliberately by a single dominant LP.

### Likelihood Explanation
This requires no privileged role and no special build flags — any account that holds (or accumulates, e.g. via being the sole/dominant LP) the full circulating `lp_supply` can call the permissionless `withdraw` instruction with `lp_token_amount = pool_state.lp_supply` in a single transaction with attacker-chosen accounts and data. This is especially plausible for newly created or low-liquidity pools where one LP (e.g., the pool creator) holds the entire circulating supply.

### Recommendation
- Use the LP mint's actual total supply (including the locked `lock_lp_amount`) as the denominator in the pro-rata withdraw calculation, so the locked shares always retain a backing reserve and the vault can never be fully drained by a single withdrawer.
- Alternatively, cap `withdraw` so it cannot reduce `pool_state.lp_supply` to `0`, or add explicit handling in `deposit` for the `lp_supply == 0` edge case (e.g., re-seed pricing using the raw vault balances, mirroring the "re-add the token as if new" logic proposed in the referenced report) so the pool doesn't become permanently unusable.

### Proof of Concept
1. Call `initialize` to create a pool; creator receives `liquidity - 100` LP tokens; `pool_state.lp_supply = liquidity - 100`. [3](#0-2) 
2. The creator (or any single LP holding the entire circulating supply) calls `withdraw` with `lp_token_amount = pool_state.lp_supply`. The payout ratio is `1`, so `results.token_0_amount == total_token_0_amount` and `results.token_1_amount == total_token_1_amount` — the entire vault is transferred out. [1](#0-0) 
3. `pool_state.lp_supply` is set to `0`. [7](#0-6) 
4. Any later `deposit` call on this pool computes `CurveCalculator::lp_tokens_to_trading_tokens(..., u128::from(pool_state.lp_supply), ...)` with `lp_supply = 0`, which fails and the call reverts with `ErrorCode::ZeroTradingTokens`. [8](#0-7) 
5. Because `initialize`/`initialize_with_permission` use Anchor `init` on the pool PDA and `lp_mint`, the pool cannot be recreated, making the DoS on `deposit` permanent for that pool.
