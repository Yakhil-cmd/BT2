### Title
Asset attestor-list update permanently freezes previously attested holders' coins - (File: validation.js, storage.js)

### Summary
Obyte's `spender_attested` asset type requires every spender (and every recipient) to be attested by the asset's current attestor list at spend time. The asset definer can post a new `asset_attestors` message at any point to replace that list. Because the protocol only ever consults the *latest* attestor list when validating a payment, an address that received/held asset coins while attested under the old list becomes permanently unable to spend them once the definer republishes a new attestor list that does not include (or re-attest) that address. There is no mechanism analogous to a "withdraw by old reference" — the coins are simply stuck in that address forever, exactly mirroring the reported bug class where funds tied to an old configuration become unrecoverable once the admin points the contract at a new configuration.

### Finding Description
When an asset is defined with `spender_attested: true`, both issuing and spending require the author addresses to appear in the asset's *attestor-approved* list: [1](#0-0) 

The attestor list itself is mutable: the definer (single author) can publish a new `asset_attestors` message at any later mci, and validation only enforces "one update per asset per unit", not any continuity with the previous list: [2](#0-1) 

When resolving the currently valid attestor list for balance/spend checks, `storage.readAsset` always picks the single latest `asset_attestors` unit and only reads that list — never any historical or intermediate list: [3](#0-2) 

`filterAttestedAddresses` then intersects the requested spender/owner addresses against only the current attestor list, gated further by any subsequent address definition change, but with no fallback to a prior attestor list: [4](#0-3) 

Finally, both transfer input ownership and output recipients are checked against this single latest attested-address set: [5](#0-4) [6](#0-5) 

Consequence: suppose Alice legitimately received/holds coins of a `spender_attested` asset while she was on attestor list V1. The definer (or an attestor acting per the asset's own rules) later posts `asset_attestors` with list V2 that omits Alice (intentionally, by mistake, or due to key rotation of the attestor). From that point on, `arrAttestedAddresses` for any last_ball_mci ≥ the V2 unit's mci no longer contains Alice, so:
- Alice can never again spend her existing unspent outputs of that asset (`"owner address is not attested"`), and
- Nobody can send that asset back to Alice either (`"some output addresses are not attested"`).

Her balance is frozen indefinitely with no protocol-level "old reference" recovery path — structurally identical to the `TokenSaleDistributor.setTokenAddress` bug, where overwriting a single mutable reference (the current token address / the current attestor list) strands value tied to the old reference, and the recovery function (`withdraw` / payment validation) only operates against the new/current reference.

### Impact Explanation
This causes concrete, protocol-visible fund freezing: any holder of a `spender_attested` asset can have their balance permanently locked as an unintended (or intentional, griefing) side effect of a routine attestor-list rotation performed by the asset's definer/attestor, which is a normal, expected operation the protocol explicitly supports (`asset_attestors` app exists specifically to let attestors update). Because the freeze is enforced by consensus validation itself, no node can be convinced to accept a spend from the "stale" attested address — it's not a bug for one node, it's uniform network-wide fund loss for the affected holder. This matches "AA/asset fund freezing" impact category.

### Likelihood Explanation
The `asset_attestors` message is a standard feature reachable by any asset issuer who defines a `spender_attested` asset; posting an attestor list update is a single, unprivileged (from the network's perspective) message any definer can send at will, with no constraint requiring continuity of previously-attested addresses. Given normal attestor rotation (e.g., compliance/KYC providers changing address, or an attestor being dropped for any reason), this is very plausible to occur unintentionally, and trivially exploitable intentionally by a malicious/rogue definer to freeze specific holders' funds at any time after issuance.

### Recommendation
Consider one or more of:
1. When validating a spend, allow the owner's attestation to be checked against the attestor list that was in effect at the time the output was created (or at the time the address was last positively attested), not only the single latest list — i.e., preserve a "grandfather" clause for outputs received under a still-historically-valid attestation.
2. Require attestor list updates to be strictly additive (never able to silently drop previously attested addresses) or require an explicit, validated migration path (e.g., a bounded transition window during which both old and new lists are honored) before old attestations are invalidated.
3. At minimum, document/require that asset definers must not publish an `asset_attestors` update that drops addresses with existing unspent balances without providing them an unlock window, and add tooling/warnings for definers to check current holder attestation status before rotating the list.

### Proof of Concept
1. Definer issues asset `A` with `spender_attested: true` and initial attestor `Att1`.
2. `Att1` (or the definer) attests address `Alice` via the `attestation` app: `unit_authors`, `attestations` (`storage.js`).
3. Definer sends payment of asset `A` to `Alice`; validation succeeds because `Alice` is in `arrAttestedAddresses` (`validation.js:2115-2122`, `2630-2642`).
4. Definer posts a new `asset_attestors` message naming `Att2` as the sole attestor, omitting any re-attestation of `Alice` (`validation.js:2033-2041`).
5. `storage.readAsset` now resolves the attestor list to the `Att2` unit only (`storage.js:1917-1946`), and `filterAttestedAddresses` no longer returns `Alice` (`storage.js:1959-1974`) since her old `attestations` record predates/references a different (now superseded) attestor set logic used by the query's continuity condition.
6. Any subsequent attempt by `Alice` to spend her previously received output of asset `A` fails validation with `"owner address is not attested"` (`validation.js:2506-2507`), and no unit sending the asset back to her can be constructed either (`validation.js:2637-2638`). Her balance is permanently frozen.

Note: I could not fully inspect `validateAttestorListUpdate` (validation.js line ~2829 onward) within the available tool budget to confirm every precondition it enforces (e.g., whether it requires the new list's author to match the current attestor(s) or only the asset definer); this detail should be verified in a full code review, but it does not change the core finding that the *latest-list-only* lookup in `storage.readAsset`/`filterAttestedAddresses` has no continuity mechanism for previously attested holders.
