### Title
Webhook signature is verified against the organization derived from the payload, but handlers act on a different, unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Finding Description
The binding this analog breaks is: **the GitHub organization whose secret authenticated the webhook == the repository that the handler subsequently writes to**.

In `WebhooksController#verify_signature`, the organization used to pick the HMAC secret is taken directly from the untrusted JSON payload, before the signature has been checked: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` selects a `GithubApp`/webhook secret keyed on `repository.owner.login` (or `organization.login`), and `verify_webhook_signature` only proves the request body was HMAC-signed with *that organization's* secret: [3](#0-2) 

Once the signature check passes, the raw payload is dispatched unchanged to the event handlers: [4](#0-3) 

But the handlers never re-derive or re-check the organization used above. Instead, `Handler#repository_name` reads a completely separate field, `repository.full_name`, to look up which `Repository`/`Stack` records to act on: [5](#0-4) 

`PushHandler` then triggers `stack.sync_github` for every matching, non-archived stack on that repository/branch: [6](#0-5) 

Nothing ties `repository.full_name`'s owner back to `repository.owner.login`/`organization.login` that was used for signature verification. In a multi-organization Shipit deployment (`Shipit.github(organization: ...)` implies more than one configured GitHub App/organization, each with its own `webhook_secret`), an attacker who legitimately controls the webhook secret for **their own** configured organization ("org-A") can craft a payload where:
- `repository.owner.login` / `organization.login` = `"org-A"` (so the signature computed with org-A's own secret verifies successfully), while
- `repository.full_name` = `"org-B/victim-repo"` (a repository belonging to a completely different, unrelated organization/stack).

The request passes `verify_signature` (correctly signed by org-A's real secret) and is then processed as if it legitimately concerned `org-B/victim-repo`, because the handler layer trusts `repository.full_name` unconditionally.

### Impact Explanation
This breaks the equality "authenticated organization == repository written," letting an attacker who only has legitimate control of one configured GitHub App/organization forge events for stacks belonging to a different organization:
- `push` events can force `sync_github`/deploy-relevant state updates on unrelated stacks.
- `membership` events create/modify `User`/`Team`/`Membership` records outside the attacker's own organization scope.
- `status`/`check_suite` events, if forged this way, can inject spoofed CI state for another organization's commits, which Shipit trusts when computing `required_statuses`/`deployable?`, potentially enabling an unauthorized deploy on a stack the attacker never had access to.

This matches the Critical/High categories: unauthorized deploy and cross-repository writes performed by someone without any credential for the victim repository, purely by abusing correctly-signed traffic from an unrelated organization.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub organization/App (a documented, supported multi-tenant setup), and that the attacker administers (or has webhook-delivery access to) any one of those configured organizations - no access to the victim's repository, token, or session is needed. The vulnerable code path (`repository_owner` derived from payload, `repository_name` derived independently from `repository.full_name`) is unconditional in `app/controllers/shipit/webhooks_controller.rb` and `app/models/shipit/webhooks/handlers/handler.rb`.

### Recommendation
After signature verification succeeds, re-validate that the organization used to select the secret matches the owner embedded in `repository.full_name` (or better: pass the verified organization explicitly into `Handler.call`/`repository_name` and reject/ignore any payload whose `repository.full_name` owner does not match the organization whose secret verified the signature).

### Proof of Concept
1. Configure Shipit with two organizations, `org-A` and `org-B`, each with its own `webhook_secret` (a standard multi-org Shipit deployment).
2. As an attacker who administers `org-A`'s GitHub App/webhook (their own organization, no access to `org-B`), craft a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "org-B/victim-repo",
    "owner": { "login": "org-A" }
  }
}
```
3. Sign the raw body with `org-A`'s real `webhook_secret` (`X-Hub-Signature: sha1=...`), set `X-Github-Event: push`, and POST to `/github/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-A")` and verifies successfully, since the body was genuinely signed with org-A's secret.
5. `PushHandler#process` calls `Repository.from_github_repo_name("org-B/victim-repo")` and triggers `sync_github` on `org-B`'s stacks - despite the request never having been authenticated by anything belonging to `org-B`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
