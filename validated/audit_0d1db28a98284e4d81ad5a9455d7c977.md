### Title
Webhook signature verification is bypassed when the payload-selected organization has no `webhook_secret`, allowing forged `membership` events to grant unauthorized team membership - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
The reported smart-contract bug is about a delegatecall trusting the target contract's response without checking that the target actually exists, letting an attacker get a "success" result for an operation that never really happened. The structural analog here is that `WebhooksController#verify_signature` selects *which* organization's secret to check the signature against using a field taken from the very payload it is supposed to authenticate, and the underlying verification (`GithubApp#verify_webhook_signature`) treats "no secret configured for that organization" as automatic success — an unsigned/forged payload is treated as verified as long as it names an organization that Shipit knows about but has not been given a `webhook_secret`.

### Finding Description
`WebhooksController#verify_signature` picks the organization used for verification straight from the untrusted request body: [1](#0-0) [2](#0-1) 

That organization is then used to fetch a `GithubApp` instance and call `verify_webhook_signature`: [3](#0-2) 

Line 77, `return true unless webhook_secret`, means that if the organization named in the attacker-controlled `repository.owner.login` / `organization.login` field is one Shipit knows about (it exists in `Shipit.github` config) but that entry has a blank/unset `webhook_secret`, signature verification is skipped entirely and the request is treated as authentic — regardless of the actual `X-Hub-Signature` header. The sample configuration explicitly shows `webhook_secret` as an optional, nullable field: [4](#0-3) 

Once "verified" this way, the controller dispatches the entire (forged) payload to registered handlers with no further authentication: [5](#0-4) 

The `membership` event handler (exercised by tests) creates `Team`, `User`, and `Membership` records purely from payload fields — `organization.login`, `team.{id,slug,name,url}`, `member.login`, and `action` — with no additional cross-check against the organization that was actually verified: [6](#0-5) 

This breaks the intended binding **"organization that authenticated == organization whose membership is written."** The signature check authenticates (trivially, via the blank-secret bypass) an organization name taken from the payload, but the membership-mutation code trusts every other field in that same payload — including `team` and `member` — to create real authorization records. `Shipit.github_teams` (configured under `oauth.teams`) is the mechanism used to gate access to Shipit via GitHub team membership, so forging a `Membership` row is a direct path to `Shipit.github_teams` authorization escalation.

### Impact Explanation
An unauthenticated attacker who knows (or can enumerate) that a configured GitHub organization in the target Shipit instance has no `webhook_secret` set can send a forged `membership` webhook naming that organization, a privileged team (one referenced in `Shipit.github_teams`), and their own GitHub login as the added `member`. This creates a `Membership` record granting them Shipit-side team authorization without ever being a real member of that GitHub team or organization — an authorization bypass reaching the "escalation into `Shipit.github_teams` authorization" High-impact category. Other event types processed via the same bypass (`push`, `status`, `pull_request`, `check_suite`) similarly let the attacker inject fabricated commit/status/CI data into any stack's history once the "authenticated" organization check is defeated.

### Likelihood Explanation
The attack requires no credentials, no session, and no GitHub App key — only that at least one organization is configured in `Shipit.github` without a `webhook_secret`, a state the codebase and sample config explicitly treat as valid/supported (`config/secrets.development.shopify.yml`), not merely a documentation-violation edge case. Multi-tenant Shipit deployments (multiple GitHub orgs configured) are the primary scenario this endpoint is built for, making the misbound trust between "verified organization" and "acted-upon data" directly reachable through the public webhook endpoint.

### Recommendation
- Do not allow "no secret configured" to silently short-circuit `verify_webhook_signature` to `true`; require a `webhook_secret` for every configured organization, or reject unsigned requests by default.
- After signature verification, cross-check that every organization/repository-identifying field used later by handlers (e.g., `team`, `member`, `repository.full_name`) is consistent with — and scoped to — the organization that was actually verified, not simply re-trusted from the same unauthenticated payload.
- Add an explicit configuration validation at boot that fails if any configured GitHub organization is missing a `webhook_secret`.

### Proof of Concept
1. Target Shipit instance configures two organizations in `Shipit.github`, e.g. `trusted-org` (has `webhook_secret`) and `staging-org` (no `webhook_secret`, e.g. left as `nil` per `config/secrets.development.shopify.yml`).
2. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: membership` and no valid `X-Hub-Signature`, body:
```json
{
  "action": "added",
  "organization": { "login": "staging-org" },
  "team": { "id": 1, "slug": "privileged-team", "name": "Privileged Team", "url": "https://example.com" },
  "member": { "login": "attacker-github-login" }
}
```
3. `verify_signature` resolves `repository_owner` to `"staging-org"` [2](#0-1) , fetches `Shipit.github(organization: "staging-org")`, and `verify_webhook_signature` returns `true` immediately because `webhook_secret` is blank for that org [7](#0-6) .
4. The `create` action dispatches the payload to the membership handler, which creates a `Membership` linking `attacker-github-login` to `privileged-team`, as demonstrated by the equivalent test flow [8](#0-7) .
5. The attacker now has Shipit-side authorization tied to `privileged-team`, without ever being a real member of that team on GitHub.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
