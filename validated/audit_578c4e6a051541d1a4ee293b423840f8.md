This is a strong analog. The `WebhooksController` verifies the HMAC signature using a GitHub App config keyed by `repository_owner`, but the handlers that actually write data resolve the target `Repository`/`Stack` from a completely different, signature-uncovered field: `payload.dig('repository', 'full_name')`.

### Title
Webhook signature is validated against `repository.owner.login`'s organization secret while handlers act on the unauthenticated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) [1](#0-0) [2](#0-1) . Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full raw JSON payload to handlers [3](#0-2) . Those handlers resolve which `Stack`/`Repository` to mutate using a separate field, `payload.dig('repository', 'full_name')`, via `Handler#repository_name` and `Handler#stacks` [4](#0-3) .

### Finding Description
The equality the engine implicitly relies on is:

`organization authorized by HMAC (repository.owner.login)` == `repository actually written to (repository.full_name)`

Nothing in `verify_signature` or `Handler` enforces this equality. The HMAC signature only proves the raw byte string was signed with *some* per-organization `webhook_secret` (looked up via `Shipit.github(organization: repository_owner)` [5](#0-4) ); it says nothing about whether the org that owns that secret is the same org whose repository the payload claims to describe elsewhere in the JSON (`repository.full_name`). Since `repository.owner.login` and `repository.full_name`'s owner-prefix are independent JSON keys with no cross-validation, an org that legitimately controls one repository's webhook secret can produce a validly-signed payload whose `repository.full_name` names an entirely different repository/stack tracked by this Shipit install. `Handler#stacks` then resolves and mutates that unrelated stack: `Repository.from_github_repo_name(repository_name)&.stacks` [6](#0-5) .

Additionally, `github_app.rb`'s `verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for the resolved organization (`return true unless webhook_secret`) [7](#0-6) , which widens the bypass: any organization onboarded to this Shipit instance without a configured secret makes the "authenticated organization" side of the binding worthless, while the "repository written" side (`full_name`) is fully attacker-controlled in the JSON body.

Concretely, handlers such as `PullRequest::ClosedHandler`, `OpenedHandler`, `LabeledHandler`, etc., act on `payload.dig('repository', 'full_name')` to find stacks and mutate merge-queue/review-stack state [8](#0-7) , and push/status handlers similarly key off `repository.full_name` through the shared `Handler` base class.

### Impact Explanation
If an attacker can produce (or replay) a payload validly signed for org A but naming a stack belonging to org B in `repository.full_name`, they can inject fabricated `push`, `status`, `pull_request`, or `merge_status`-related events for repository B's stacks — e.g., faking commit statuses that gate deploy safety checks, or driving merge-queue/review-stack state transitions for a repository they don't own. This is a cross-repository write achieved purely through a payload field ("repository.full_name") that is never covered by the signature verification decision, breaking repository isolation between tenants of a single Shipit instance.

### Likelihood Explanation
Exploitability depends on the attacker being able to obtain (or forge) *a* validly-signed webhook for *any* organization onboarded to the Shipit instance — either because that org has no `webhook_secret` configured (`return true unless webhook_secret`), or because the attacker controls one legitimate GitHub org/webhook delivery mechanism on the instance and can freely edit the JSON body's `repository.full_name` before it's HMAC-signed by their own org's secret (since GitHub itself signs whatever body the sending org's webhook delivers, and nothing stops a malicious org-owner from customizing outbound webhook payloads if they control the sending side, e.g. via a custom webhook proxy). This requires at least control of one org's webhook configuration on the instance, which is a lower bar than requiring a Shipit session, API token, or GitHub App private key — no such credential is needed here, only the ability to have the JSON body's `repository.full_name` diverge from `repository.owner.login`.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, cross-check that `payload.dig('repository', 'full_name')`'s owner segment matches `repository_owner` (the same field used to select the signing org's secret) before dispatching to handlers, rejecting the webhook if they diverge. Additionally, treat "no `webhook_secret` configured" as a hard failure (or explicit opt-in) rather than an implicit signature bypass in `GithubApp#verify_webhook_signature`.

### Proof of Concept
1. Org `attacker-org` is configured in this Shipit instance (or has no `webhook_secret` set at all, satisfying `return true unless webhook_secret`) [9](#0-8) .
2. Attacker crafts a JSON body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, ...event fields...}`, signs it (or sends unsigned if `webhook_secret` is blank for `attacker-org`), and sets `X-Github-Event`/`X-Hub-Signature` headers.
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature check passes (either genuinely signed with attacker-org's secret, or trivially bypassed if that secret is blank) [10](#0-9) .
4. `create` dispatches `params` to the relevant handler (e.g. `PullRequest::ClosedHandler`) which calls `Handler#stacks`, resolving `Repository.from_github_repo_name("victim-org/victim-repo")` and mutating that stack's state — a repository the attacker never controlled and whose owner never authorized this payload [4](#0-3) .
