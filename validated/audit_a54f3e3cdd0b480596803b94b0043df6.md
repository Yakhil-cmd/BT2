### Title
Scaled debt valuation overflow permanently freezes a saturated market - ([File: common/src/rates/index.rs])

### Summary
A borrower can leave a market with enough scaled debt that ordinary interest accrual makes `borrowed * borrow_index / RAY` exceed `i128::MAX`. Because every pool mutation synchronizes interest before applying the requested operation, the resulting `MathOverflow` permanently blocks repayment, withdrawal, liquidation, bad-debt cleanup, revenue claims, and further index updates for that market. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The controller exposes permissionless `borrow` and `update_indexes`; the latter forwards the caller-selected market list to the pool after authenticating the caller. [4](#0-3) [5](#0-4) [6](#0-5) 

During accrual, `calculate_supplier_rewards` separately computes the old and new RAY-denominated debt values as `borrowed.mul(old_index)` and `borrowed.mul(new_index)`. [7](#0-6)  `Ray::mul` calls `mul_div_half_up`; although the multiplication is widened to `I256` when necessary, the final quotient must still fit in `i128` and otherwise panics with `MathOverflow`. [8](#0-7) [9](#0-8) 

Market accrual runs through `global_sync`, which invokes `accrue_step` before committing the new indexes. [10](#0-9) [11](#0-10)  All pool mutation legs first call `synced_market`, which loads the market and runs `global_sync`; therefore no later repayment or withdrawal logic can execute once accrual overflows. [12](#0-11) 

The overflow threshold is below the configured borrow-index ceiling: valid asset caps can admit approximately 170 billion whole tokens, while accrued RAY market totals must independently fit `i128`, and the protocol documentation explicitly notes that value overflow can precede the index ceiling and block exits. [13](#0-12) [14](#0-13) 

### Impact Explanation
This permanently freezes all user funds and debt positions in the affected `(hub_id, asset)` market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize collateral, and protocol revenue cannot be claimed because each path performs the same overflowing accrual before state mutation. [15](#0-14) [12](#0-11) 

The regression test demonstrates the concrete cliff: a 98%-utilized 18-decimal market eventually returns `MATH_OVERFLOW` from `update_indexes`, after which both a raw withdrawal and a repayment revert with the same error. [16](#0-15) 

### Likelihood Explanation
Triggering the condition requires an extremely large position and sustained high utilization, but it does not require privileged execution at attack time. One address can supply collateral through `supply`, create the debt through `borrow`, and later invoke the permissionless `update_indexes` once the accrued debt value crosses the `i128` boundary. [17](#0-16) [5](#0-4) 

Spoke caps constrain but do not eliminate the scenario because their maximum permitted value is still the full token-to-RAY representable amount; accrued values can subsequently exceed that domain even though the admitted cap itself fit. [18](#0-17) [19](#0-18) 

### Recommendation
Make market accrual tolerate unrepresentable RAY totals instead of aborting before any operation can reduce them. For example, use widened debt values through interest calculation, clamp the borrow index to the largest value for which current market debt remains representable before evaluating supplier rewards, or add a pre-accrual bound that rejects borrows/supplies which could later push `borrowed * borrow_index / RAY` or `supplied * supply_index / RAY` past `i128::MAX`. [1](#0-0) [11](#0-10) 

### Proof of Concept
1. Assume a listed 18-decimal debt market `D` and a collateral market `C`, each configured within its protocol-valid cap domain and with enough existing liquidity in `D`. [20](#0-19) 
2. The attacker calls `supply(caller, 0, spoke_id, [(C, collateral_amount)])` to create an account, using enough collateral to support the desired borrow. [21](#0-20) 
3. The attacker calls `borrow(caller, account_id, [(D, debt_amount)], None)`, where `debt_amount` is near the admitted cap; the test fixture uses approximately `980_000_000 * 10^18` base units of an 18-decimal asset. [4](#0-3) [22](#0-21) 
4. Under sustained high utilization, interest compounds until the next `borrowed.mul(new_borrow_index)` result no longer fits `i128`. [23](#0-22) [24](#0-23) 
5. Any caller can then trigger the condition with `update_indexes(caller, [D])`; the call reverts with `MathOverflow`, leaving the pre-overflow state intact. [6](#0-5) [25](#0-24) 
6. Subsequent `repay(caller, account_id, [(D, 1)])` and `withdraw(caller, supplier_account, [(D, amount)], None)` both revert with `MathOverflow` because their pool legs call `global_sync` before mutating balances. [12](#0-11) [3](#0-2)

pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);
    let supplier_rewards = accrued_interest.checked_sub(env, protocol_fee);

    (supplier_rewards, protocol_fee)

pub(crate) fn synced_market(env: &Env, hub_asset: &HubAssetKey) -> Cache {

pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
```

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );
```

| Bound | Consequence |
|---|---|
| Asset decimals 0..=18 | Exact token-to-RAY upscaling. Below 3: collateral only, no flash loans, no liquidation fee, its account's only supply position, at least 2 whole units while in debt |
| Both indexes initially RAY; ceiling 10^36 | 10^9 times initial index; protocol constants |
| Supply-index floor 10^24 | At most 1,000 times the shares minted at index one for the same deposit |
| Borrow APR maximum 2 RAY | 200% annual rate; not a bound on balance growth alone |
| Token-to-RAY input maximum `i128::MAX / 10^(27-d)` | About 170.14 billion whole tokens, before other limits |
| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.
