### Title
Global oracle monotonicity guard lets any user grief another user's price-dependent operation - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`write-feeds`/`price-resolve` in `v0-4-market.clar` accept a Pyth/DIA price blob from **any caller** via the `price-feeds` parameter present on `collateral-add`, `collateral-remove`, `borrow`, `supply-collateral-add`, and `liquidate`. Each call updates a single global map `last-update` keyed only by `{type, ident}` (the price feed identity), and `oracle-timestamp-fresh` rejects any subsequently-submitted price whose `timestamp` is older than that global value, even if that price is independently fresh relative to `max-staleness`. Because the guard is shared across all users of a feed rather than scoped per-transaction/per-user, one user's legitimately-fresh price submission can permanently (until a newer off-chain price is published) block any other user whose fetched price update happens to carry an older (but still valid) publish-time for that feed.

### Finding Description
`last-update` is defined once per `{type, ident}` pair, globally shared by every position that references that feed: [1](#0-0) 

`price-resolve` enforces `(>= ts prev)` against this shared value and, on success, advances it to the caller-supplied timestamp: [2](#0-1) 

`write-feeds`/`write-feed` let **any caller** push a fresh signed Pyth update through this same path as an ordinary part of their own transaction (no permission check, no per-user scoping): [3](#0-2) 

`liquidate` and the other hot-path functions all take an optional `price-feeds` argument that is fed straight into `write-feeds` before health/oracle evaluation of the target position: [4](#0-3) 

Since Pyth publishes new prices continuously (sub-second cadence) and different off-chain relayers/clients fetch price blobs at slightly different times, it is normal for two independent users to be carrying differently-timestamped but both-still-fresh blobs for the same feed at the same moment. Whichever transaction lands first raises the shared `last-update`; anyone else whose blob carries an earlier `publish-time` for that identical feed then fails `oracle-timestamp-fresh` and their whole transaction (`ERR-ORACLE-INVARIANT`) reverts — even though their own price data independently satisfies `max-staleness`.

### Impact Explanation
Attacker and victim are two unrelated, unprivileged users of the same market who both interact with the same price feed (e.g., STX/USD, used by essentially every position). The victim is a liquidator (or any user) submitting an otherwise-valid, fresh price blob to evaluate/act on a third party's (or their own) position. The shared state is the single global `last-update` map entry for that feed. The attacker needs no special capability: any transaction that includes `price-feeds` for that feed (a `collateral-add` of a trivial amount, a `borrow`, etc.) with a timestamp equal to or ahead of what the victim is about to submit permanently raises the bar the victim must clear. If the attacker deliberately (or even incidentally) submits the freshest-available blob for a feed just before a liquidator's liquidation transaction lands (same block or a following block, since the value persists until overwritten by an even-newer timestamp), the liquidator's blob — fetched moments earlier and thus carrying an older `publish-time` — fails `(>= ts prev)` and the entire `liquidate` call reverts with `ERR-ORACLE-INVARIANT`. This is "a position made unevaluable by a third party": the borrower's unhealthy position cannot be liquidated by that transaction, temporarily protecting an under-collateralized position and exposing suppliers to additional bad-debt risk before the liquidator can re-fetch and resubmit an even-newer price. This lands in the "temporary freezing of funds" impact class (the liquidator's action, and the position's evaluability, are blocked pending a fresher upstream price).

### Likelihood Explanation
This does not require any privileged role, DAO action, or flashloan — it only requires calling any of the already-public hot-path functions (`collateral-add`, `borrow`, etc.) with a `price-feeds` payload that includes a valid, recent Pyth update for a shared feed, which any address can obtain and submit trivially and cheaply (e.g., adding a dust amount of collateral). Because Pyth prices update multiple times per second and market activity is continuous, races between differently-fetched-but-both-valid timestamps for the same feed are a routine occurrence, not a contrived edge case — an attacker only needs to time one cheap transaction to precede a target liquidation.

### Recommendation
Do not use a single global "latest seen timestamp" as a hard floor that fails unrelated transactions. Either (a) scope freshness purely to `oracle-timestamp-fresh`'s own staleness window relative to `stacks-block-time` without the monotonic `>= prev` gate, since `max-staleness` already bounds acceptable age, or (b) if monotonicity must be kept to prevent replay of intentionally-stale data, only reject a submitted price if it is older than `stacks-block-time - max-staleness`, not older than the last price anyone else happened to submit; alternatively, allow price-resolve to simply skip re-validating/overwriting `last-update` when the caller's own data is merely not-the-newest-but-still-fresh instead of hard-erroring the whole transaction.

### Proof of Concept
1. STX/USD Pyth feed publishes update `P1` at `t=100`, then `P2` at `t=101` (sub-second real cadence, values are the routine off-chain feed cadence).
2. User B (liquidator) fetches `P1` at real time `~100.2` intending to call `liquidate(borrower, ..., price-feeds=(some (list P1-blob)))`.
3. Before B's transaction is included, User A (any address, unrelated to B or the borrower) submits any hot-path call (e.g., `collateral-add(..., price-feeds=(some (list P2-blob)))`) which succeeds and sets `last-update[{TYPE-PYTH, STX_IDENT}] = 101` via `price-resolve` at `mainnet/contracts/market/v0-4-market.clar:390-393`.
4. B's `liquidate` transaction then executes `write-feeds` → `price-resolve` with `P1` (`timestamp=100`); `oracle-timestamp-fresh(100, 101, max-staleness)` evaluates `(>= 100 101)` as false, so the `asserts!` at `mainnet/contracts/market/v0-4-market.clar:387-388` fails with `ERR-ORACLE-INVARIANT`, reverting B's entire liquidation call.
5. The borrower's unhealthy position survives that block unliquidated purely because of A's unrelated, earlier-landing transaction on the shared feed state — despite B's own price data being independently fresh under `max-staleness`.
