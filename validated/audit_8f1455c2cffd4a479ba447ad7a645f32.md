### Title
Cross-repository forged commit status accepted by `StatusHandler` bypasses `Commit#deployable?` even when `Stack#ignore_ci?` is `false` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Webhooks::Handlers::StatusHandler#process` looks up commits to update purely `Commit.where(sha: params.sha)`, with no check that the webhook's source repository matches the repository owning the `Stack` the matched `Commit` belongs to. Any GitHub org/repo that shares a commit SHA with a victim's tracked repository (trivial to arrange via a fork, since SHAs are content-addressed and forks/PRs commonly retain upstream commit SHAs) can emit a `status` webhook that is applied to the victim's `Commit`, flipping `success?` to `true` and making `Commit#deployable?` return `true` even though the victim's real CI provider never reported success on that stack.

### Finding Description
The broken binding: the question's binding is `success?` (delegated from `Commit` to `status`, `app/models/shipit/commit.rb:219`) `== outcome of CI runs the victim's own CI provider executed for the victim's own repository`. In practice this reduces to: `Commit#status` == `Status` records created via `Status.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/status.rb:24-33`), and those records are created for *any* `Commit` row that matches `params.sha`, independent of which repository/organization actually sent the webhook (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`): [1](#0-0) 

`create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)`, which uses the commit's own (victim) `stack_id` for the newly created `Status` [2](#0-1) . Because the `stack_id` on the new `Status` is taken from the matched `Commit` (not from the webhook payload's repository), the forged status is fully "legitimate-looking" from the victim Stack's point of view: `Commit#status`, `#success?`, `#state` all aggregate over `statuses` scoped by `stack_id` (`app/models/shipit/commit.rb:12,219`), with no cross-check against which GitHub repository actually emitted the webhook.

`Commit#deployable?` is: [3](#0-2) 
For a victim Stack with `ignore_ci? == false`, the right-hand disjunct `success? && !blocked?` is exactly what an attacker forges. `blocked?` only depends on other undeployed commits' `blocking?` state on the same stack (`app/models/shipit/commit.rb:231-237`) and is unaffected by this attack, so it does not block the exploit when there are no other blocking commits (the common case). `locked?` is a Stack-owner controlled flag unrelated to CI and is typically `false`.

Exploit flow: (1) Attacker forks or otherwise obtains a repository containing a commit with the same SHA as a commit already tracked in the victim's Stack (achievable because SHAs are content-addressed and preserved across forks/cherry-picks/rebases with identical trees+parents+metadata, or because the attacker mirrors the victim repo). (2) Attacker configures their own GitHub webhook (of a repo they own) to POST a `status` event to the shared Shipit host's `POST /webhooks` endpoint, with `sha` equal to the victim commit's SHA and `state: 'success'`. (3) `StatusHandler.process` finds the victim's `Commit` row purely by SHA match and calls `commit.create_status_from_github!(params)`, creating a new `success` `Status` scoped to the victim `stack_id`. (4) `commit.success?` now returns `true`, `commit.deployable?` returns `true`, and `Stack#next_expected_commit_to_deploy`/`UndeployedCommit#deploy_state` will treat the commit as `allowed`, enabling a real deploy trigger despite the victim's actual CI having reported `pending` or `failure`.

Existing guards do not stop this: webhook signature verification (`verify_signature`/`GitHubApp#verify_webhook_signature`) only proves the payload came from *some* registered GitHub App installation delivering *a* webhook — it does not bind the payload's `sha`/`state` to the repository that the target `Stack`/`Commit` belongs to. `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler` only validate presence/type of `sha`, `state`, etc.; they do not validate repository ownership.

### Impact Explanation
A successful forgery lets an attacker cause an **unauthorized deploy of code that has not passed the victim's real CI**, directly matching the "unauthorized deploy" Critical category: a payload originating from one repository (the attacker's) mutates state (a `Status` record, and downstream, deploy eligibility) belonging to another repository's `Stack`/`Commit`. This is repeatable against any Stack whose tracked commit history intersects (by SHA) with a repository the attacker controls, and does not require `ignore_ci` to be enabled — it works against the "safer" `ignore_ci: false` configuration, contrary to the assumption that disabling `ignore_ci` protects against forged deploys.

### Likelihood Explanation
Preconditions: the victim Stack has `ignore_ci? == false` (default/typical), the target commit is `pending` or `failure` in reality, and no other undeployed commit is currently `blocking?` on that stack. The attacker needs zero Shipit privileges — only the ability to control a GitHub repository (their own fork or any repo) that shares a commit SHA with the victim's tracked history, and to configure that repo's webhook (or otherwise POST) to the shared `/webhooks` endpoint. Sharing a SHA across repos is a routine, low-cost occurrence (forks, mirrors, cherry-picks, PR branches) rather than requiring any secret. Attacker cost is low and the attack is repeatable for every future commit that meets the SHA-overlap condition.

### Recommendation
`StatusHandler#process` (and analogous handlers matching purely by `sha`) must scope the `Commit` lookup to commits belonging to a `Stack` whose `Repository` matches the webhook's authenticated source repository (e.g., `repository_owner`/`repository.full_name` from the verified payload), not merely `Commit.where(sha: ...)`. Concretely, resolve the source `Repository` from the verified webhook context, then constrain: `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { ... matches payload repo ... })` before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (model-level, no live GitHub, matching the question's proof idea):
```ruby
test "#deployable? is falsely true via forged cross-repo status even when ignore_ci is false" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(ignore_ci: false)

  commit = shipit_commits(:first) # belongs to victim_stack
  commit.stack.update!(ignore_ci: false)
  commit.statuses.create!(stack_id: commit.stack_id, state: 'failure', context: 'ci/real')
  assert_predicate commit, :failure?
  refute_predicate commit, :deployable?

  # Simulate a forged status webhook whose sha matches `commit.sha`
  # but originates from an unrelated/attacker-controlled repository,
  # as processed by StatusHandler#process which does not check repo ownership.
  forged_payload = OpenStruct.new(sha: commit.sha, state: 'success', context: 'ci/attacker', created_at: Time.now.to_s)
  Shipit::Commit.where(sha: forged_payload.sha).each { |c| c.create_status_from_github!(forged_payload) }

  commit.reload
  assert_predicate commit, :success?          # forged status accepted
  refute_predicate commit.stack, :ignore_ci?  # confirms conservative config
  assert_predicate commit, :deployable?       # exploit: deployable despite real CI failure
end
```
This asserts the two sides of the equality (`commit.success?` post-forgery vs. the victim's real CI outcome `failure?`) diverge, proving the bypass.
