### Title
Missing domain/context binding in `is_valid_signed_package()` / `validateSignedMessage()` enables authorization-message replay across AAs (confused-deputy / authorization-artifact injection) - ([File: signed_message.js])

### Summary
The oscript primitive `is_valid_signed_package()`, backed by `signed_message.validateSignedMessage()`, verifies only that a `signed_message` object is cryptographically authored by a claimed address (plus optional freshness via `last_ball_unit`). It performs no binding of the signed artifact to the AA (`this_address`) that is asking to validate it, to the asset/purpose it is used for, or to any single-use nonce. This mirrors the root cause of CVE-2024-12369 (WildFly Elytron OIDC): the library validates that an authorization artifact is authentic, but does not verify that it was issued *for this specific relying party/context*, allowing a token/message obtained in one context to be injected and accepted in another.

### Finding Description
`is_valid_signed_package` is evaluated in `formula/evaluation.js`: [1](#0-0) 

It delegates the actual cryptographic/definition check to `signed_message.validateSignedMessage()`: [2](#0-1) 

The function checks:
1. That the object shape is well-formed (`signed_message`, `authors`, `last_ball_unit`, `version`).
2. That the author whose address matches the caller-supplied `evaluated_address` actually signed the payload (`unit_hash_to_sign` derived from `objectHash.getSignedPackageHashToSign`).
3. Optionally, that `last_ball_unit` exists and is stable/on the main chain. [3](#0-2) 

Nowhere does the primitive bind the signed content to:
- the verifying AA's own address (`this_address`),
- the specific contract/session/period/nonce it is meant for,
- or the asset/amount context it authorizes.

Binding is entirely left to the AA author, who must manually embed distinguishing fields (e.g. `channel`, `period`) inside `signed_message` and manually compare them against `this_address`/state variables, as shown in the bundled payment-channel sample: [4](#0-3) 

If an AA author omits this manual binding (a very easy omission, exactly analogous to an OIDC relying party that fails to check `redirect_uri`/`state`/PKCE), any legitimately-signed package produced by a counterparty for one purpose, one AA instance, or one point in time can be replayed/injected wherever `is_valid_signed_package()` is called against the same signer address — including into a different instance of the same parameterized/base AA template, into a stale round of the same contract, or into any other AA that expects a similarly shaped `signed_message` from that user. Because `is_valid_signed_package` returns `true` purely from proof of authorship, the confused-deputy AA will treat the replayed message as fresh, valid authorization.

### Impact Explanation
Any AA (payment channel, order-book exchange, or custom escrow logic) that relies on `is_valid_signed_package()` to authorize a fund-moving branch is exposed to unauthorized spending or fund loss if it does not itself add contextual binding: a counterparty-signed message intended to authorize movement of funds in one round/instance can be replayed to trigger the same or a different AA into releasing/moving funds again, or a stale (older, more favorable-to-the-attacker) signed state can be substituted for the current one when the AA fails to explicitly reject it. This is a fund-loss/fund-freezing primitive within the AA framework, reachable purely by an AA trigger sender who is a legitimate off-chain counterparty replaying a previously obtained signature — no privileged network position is required.

### Likelihood Explanation
Exploitability is conditional on the calling AA's own oscript logic: AAs that (like the bundled sample) manually verify `channel`/`period`/`this_address` fields inside `signed_message` are not vulnerable. However, the ocore core library provides no default protection, no documented required fields, and no complexity/registration mechanism to prevent replay across contexts — the responsibility is fully offloaded to AA authors, and the necessity of this workaround is only visible by inspecting sample code and comments in the library itself. Given how easy the omission is (a single missing equality check) and how commonly `is_valid_signed_package` is expected to be used for off-chain payment/escrow authorization, likelihood of an insecure AA using this primitive is moderate to high in the ecosystem.

### Recommendation
Provide replay-safe primitives at the library/oscript level rather than relying entirely on AA authors:
- Extend `signed_message.validateSignedMessage()` / `is_valid_signed_package()` to optionally require and check a caller-supplied "domain" or "audience" field (e.g., binding to `this_address` of the invoking AA) so a package signed for AA X cannot validate as `true` when checked from AA Y.
- Document and/or enforce that `signed_message` payloads used for fund authorization must include an application-specific nonce or state counter, and give AA authors a built-in helper to check nonce monotonicity, rather than requiring bespoke `channel`/`period` comparisons.
- Consider adding a per-AA-instance domain separator (similar to EIP-712 domain separation) automatically mixed into `getSignedPackageHashToSign` when the package is validated inside an AA context, so cross-AA replay is structurally impossible even if the AA logic forgets to check it explicitly.

### Proof of Concept
1. Deploy (or reuse) a parameterized/base AA template similar to `test/samples/payment_channels.oscript`, but omit the `channel`/`period` binding checks that the bundled sample includes:
```
// vulnerable variant
if (!is_valid_signed_package(trigger.data.sentByPeer, $bInitiatedByA ? $addressA : $addressB))
    bounce('invalid signature by peer');
$transferredFromPeer = trigger.data.sentByPeer.signed_message.amount_spent;
```
(no check that `signed_message.channel == this_address` or `signed_message.period == var['period']`).
2. Party A signs an off-chain message `{signed_message: {amount_spent: 100}, authors: [...] }` intended for channel instance #1 to authorize a settlement.
3. Because the base AA is parameterized (same template, many deployed instances share validation logic), the same signed package validates as `true` via `is_valid_signed_package()` when submitted as a trigger to a *different* instance (channel #2) or a *stale* round of the same channel, since `validateSignedMessage()` in `signed_message.js` only re-derives `unit_hash_to_sign` and checks the ECDSA signature over the whole package — it never inspects which AA address is asking or which round is current.
4. The confused AA processes the replayed authorization and releases/moves funds a second time (double payout) or accepts an outdated, more favorable balance state, resulting in fund loss for the counterparty who signed the original message.
