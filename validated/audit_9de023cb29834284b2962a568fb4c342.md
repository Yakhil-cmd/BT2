### Title
Unbounded recursive purge of chained pending joints causes prolonged single-connection stall - (File: joint_storage.js)

### Summary
When a joint with unresolved dependencies (missing `parent_units`) is finally found to be bad, `purgeJointAndDependencies` walks the entire tree of joints that (transitively) depend on it via `collectQueriesToPurgeDependentJoints`, one DB round-trip per level, all inside a single open transaction on a single pooled connection. An attacker can pre-seed the `dependencies`/`unhandled_joints` tables with a long/wide chain of otherwise-valid-looking joints that all transitively depend on one root unit, then cause that root to be marked bad, forcing the node to serially walk and mutate the whole chain while holding one DB connection and never releasing it until the walk completes.

### Finding Description
Unresolved units (units that reference parents the node hasn't received yet) are stored as "unhandled joints" together with `dependencies` rows pointing at the missing parents: [1](#0-0) 

When a peer sends a joint whose parents are unknown, `handleOnlineJoint`/`network.js` persists it via `saveUnhandledJointAndDependencies` and requests the missing parents: [2](#0-1) 

This is the direct structural analog of Bitcoin's "orphan transaction" pool (a tx whose inputs are not yet known), which is exactly the bug class named in the CVE.

Crucially, when a joint is eventually judged bad (validation failure, e.g. `ifUnitError`), the node purges it and recursively purges every joint that (directly or indirectly) depends on it: [3](#0-2) [4](#0-3) 

`collectQueriesToPurgeDependentJoints` is recursive: for every dependent unit found at the current level it issues one more `SELECT`, then recurses again for each of *those* dependents (`async.eachSeries(rows, ..., collectQueriesToPurgeDependentJoints(...))`), one DB round-trip per node in the tree, entirely serialized. All of this happens inside a single `BEGIN ... COMMIT` transaction held on one connection taken from the pool (`db.takeConnectionFromPool`): [5](#0-4) 

Because `unhandled_joints`/`dependencies` are unbounded in aggregate size (individual joints are only purged after they sit for 1 hour, and there's no cap on the number of joints or the depth/width of the dependency graph a peer can build up), an attacker can:
1. Craft a chain (or wide tree) of N joints, each syntactically valid enough to pass early checks and only fail on "unresolved dependency" (missing parent), so each is accepted into `unhandled_joints`/`dependencies` (`ifNeedParentUnits`) rather than immediately rejected.
2. Make the root of the chain eventually fail hard validation (`ifUnitError`/`ifJointError`), which triggers `purgeJointAndDependenciesAndNotifyPeers` → `joint_storage.purgeJointAndDependencies` → `collectQueriesToPurgeDependentJoints`.
3. The node then serially walks and mutates all N dependent rows, one query per node, on a single connection, inside one open transaction, for the entire duration of the walk.

This mirrors the underlying flaw class in CVE-2024-52914: a single crafted unconfirmed transaction/graph of pending transactions causes disproportionate, serialized processing work when its dependency chain is finally resolved/invalidated, tying up node resources.

### Impact Explanation
While each individual unit is bounded (`MAX_PARENTS_PER_UNIT` anti-spam check exists per-unit), there is no limit on:
- the total number of pending `unhandled_joints`/`dependencies` rows the node will accumulate from various peers/postings before the 1-hour purge sweep runs, or
- the depth/width of the dependency tree that can be built by chaining many such units together.

An attacker can therefore force `collectQueriesToPurgeDependentJoints` to serially process a very large number of nodes, one DB round trip at a time, while holding a single pooled connection and an open transaction. Because connection pools are finite, this can starve other operations (new joint validation, catch-up, other purges) that need a free connection, degrading or stalling the node's ability to process/confirm new units — directly matching the "node unable to confirm new units" impact criterion.

### Likelihood Explanation
Exploitability depends on the attacker's ability to get many "unresolved-dependency" joints accepted and stored (each individually looks legitimate at receipt time, since they only fail at the "missing parent" stage, not on the earlier cheap syntactic checks), and then to trigger invalidation of the common ancestor. This is achievable by any unprivileged unit poster/relaying party over the normal joint-relay path (`handleOnlineJoint`) without needing a malicious hub, elevated privileges, or protocol violations — it uses the standard "missing parent → save unhandled joint → request parent" flow that DAG nodes must support. The main uncertainty is the practical scale needed (how many chained joints before the effect is significant), which requires load-testing to quantify precisely.

### Recommendation
- Bound `collectQueriesToPurgeDependentJoints` recursion width/depth (or overall total rows) per invocation, and/or convert the algorithm to an iterative batched purge (single/bounded number of `SELECT`s using recursive CTE or breadth batching) instead of one query per graph node.
- Impose a global cap on the number of outstanding `unhandled_joints`/`dependencies` rows (and/or a cap on chain depth of pending dependents) so a single purge operation cannot cascade unboundedly.
- Release/rotate the DB connection periodically during a long purge instead of holding one connection and one open transaction for the whole walk, so pool exhaustion cannot occur.
- Reduce the 1-hour TTL for pending unresolved joints, or scale it down under load, to shrink the size of dependency graphs that can accumulate before being purged anyway.

### Proof of Concept
1. As an unprivileged peer/unit poster, submit a sequence of well-formed joints U1 → U2 → ... → Un where each Ui references a parent unit that does not yet exist on the target node (so each triggers `ifNeedParentUnits` and gets stored via `saveUnhandledJointAndDependencies`, chaining Un's dependency on U(n-1), etc.), building a long dependency chain rooted at a still-missing unit U0.
2. Trigger (or wait for) validation of U0 to fail permanently (e.g., ensure U0 ultimately arrives in a form that fails `validation.validate`, causing `ifUnitError`/`ifJointError`).
3. Observe that `purgeJointAndDependenciesAndNotifyPeers` → `collectQueriesToPurgeDependentJoints` serially walks all N chained dependents, one query per node, on a single held connection/transaction — measure the wall-clock time and connection-pool occupancy versus N to demonstrate the near-linear (and pool-blocking) cost that scales with attacker-controlled chain length.

function saveUnhandledJointAndDependencies(objJoint, arrMissingParentUnits, peer, onDone){
	var unit = objJoint.unit.unit;
	assocUnhandledUnits[unit] = true;
	db.takeConnectionFromPool(function(conn){
		var sql = "INSERT "+conn.getIgnore()+" INTO dependencies (unit, depends_on_unit) VALUES " + arrMissingParentUnits.map(function(missing_unit){
			return "("+conn.escape(unit)+", "+conn.escape(missing_unit)+")";
		}).join(", ");
		var arrQueries = [];
		conn.addQuery(arrQueries, "BEGIN");
		conn.addQuery(arrQueries, "INSERT "+conn.getIgnore()+" INTO unhandled_joints (unit, json, peer) VALUES (?, ?, ?)", [unit, JSON.stringify(objJoint), peer]);
		conn.addQuery(arrQueries, sql);
		conn.addQuery(arrQueries, "COMMIT");
		async.series(arrQueries, function(){
			conn.release();
			if (onDone)
				onDone();
		});
	});
}

function purgeJointAndDependencies(objJoint, error, onPurgedDependentJoint, onDone){
	var unit = objJoint.unit.unit;
	const truncatedError = truncate(error);
	assocKnownBadUnits[unit] = truncatedError;
	db.takeConnectionFromPool(function(conn){
		var arrQueries = [];
		conn.addQuery(arrQueries, "BEGIN");
		conn.addQuery(arrQueries, "INSERT "+conn.getIgnore()+" INTO known_bad_joints (unit, json, error) VALUES (?,?,?)", [unit, JSON.stringify(objJoint), truncatedError]);
		conn.addQuery(arrQueries, "DELETE FROM unhandled_joints WHERE unit=?", [unit]); // if any
		conn.addQuery(arrQueries, "DELETE FROM dependencies WHERE unit=?", [unit]);
		collectQueriesToPurgeDependentJoints(conn, arrQueries, unit, truncatedError, onPurgedDependentJoint, function(){
			conn.addQuery(arrQueries, "COMMIT");

				delete assocUnhandledUnits[unit];

				if (onDone)
					onDone();

// onPurgedDependentJoint called for each purged dependent unit
function collectQueriesToPurgeDependentJoints(conn, arrQueries, unit, error, onPurgedDependentJoint, onDone){
	conn.query("SELECT unit, peer FROM dependencies JOIN unhandled_joints USING(unit) WHERE depends_on_unit=?", [unit], function(rows){
		if (rows.length === 0)
			return onDone();
		const truncatedError = truncate(error);
		//conn.addQuery(arrQueries, "DELETE FROM dependencies WHERE depends_on_unit=?", [unit]);
		var arrUnits = rows.map(function(row) { return row.unit; });
		arrUnits.forEach(function(dep_unit){
			assocKnownBadUnits[dep_unit] = truncatedError;
			delete assocUnhandledUnits[dep_unit];
		});
		conn.addQuery(arrQueries, "INSERT "+conn.getIgnore()+" INTO known_bad_joints (unit, json, error) \n\
			SELECT unit, json, ? FROM unhandled_joints WHERE unit IN(?)", [truncatedError, arrUnits]);
		conn.addQuery(arrQueries, "DELETE FROM unhandled_joints WHERE unit IN(?)", [arrUnits]);
		conn.addQuery(arrQueries, "DELETE FROM dependencies WHERE unit IN(?)", [arrUnits]);
		async.eachSeries(
			rows,
			function(row, cb){
				if (onPurgedDependentJoint)
					onPurgedDependentJoint(row.unit, row.peer);
				collectQueriesToPurgeDependentJoints(conn, arrQueries, row.unit, error, onPurgedDependentJoint, cb);
			},
			onDone
		);
	});
}
