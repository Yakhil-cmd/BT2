### Title
Cross-organization webhook forgery via attacker-selectable signing key - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment, the webhook signature is verified using a GitHub App configuration selected from **attacker-controlled payload fields**, while the actual repository/stack that gets mutated is looked up from a **different, also attacker-controlled** field in the same payload. This breaks the binding between "the organization whose secret authenticated the request" and "the repository that is actually written to," letting a party who only controls (or knows the secret of) one configured organization forge webhook events against any other organization's stacks tracked by the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks which `GitHubApp`/secret to verify the HMAC signature against by reading the organization name straight out of the unauthenticated request body:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up per-organization config by that same attacker-supplied name:
```ruby
def github(organization: github_default_organization)
  if github_default_organization.nil?
    config = secrets.github
  else
    config = github_app_config(organization)
    raise GithubOrganizationUnknown, organization if config.nil?
  end
  @github[organization] ||= GitHubApp.new(organization, config)
end
``` [2](#0-1) 

Once the signature check passes, `WebhooksController#create` dispatches the *entire* raw JSON body to the registered handlers, which independently resolve the target repository from a separate field, `repository.full_name`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

Handlers such as `PushHandler` (triggers `stack.sync_github`) and `StatusHandler` (creates commit statuses, which feed CI-gated auto-merge/deploy logic via `stack.schedule_merges`) act purely on `repository.full_name`: [4](#0-3) [5](#0-4) 

Because `repository.owner.login` (used to select the verifying secret) and `repository.full_name` (used to select the mutated stack) are two independent, attacker-writable JSON fields inside the same request, an attacker who is able to produce a validly-signed webhook for **any one** configured organization (e.g. because they administer that org's own GitHub App webhook, or because that org's `webhook_secret` was left unset — explicitly documented as "optional" in `docs/setup.md`) can set `repository.owner.login` to that organization while setting `repository.full_name` to a completely different, victim organization's repository. `verify_signature` authenticates the payload as belonging to the attacker's own organization, but the handlers then act on the victim's stack. This is the same class of flaw as the report: the code proves "a caller of type X made this request" (dtfs program / org A) but never confirms that the *object being acted upon* (trade / repository) actually belongs to X.

### Impact Explanation
This allows an unauthorized cross-organization write: forging a `status` event lets an attacker mark an arbitrary commit `success` for any tracked repository's required CI context, which is consumed by `Commit#add_status` to flip `deployable_status` and invoke `stack.schedule_merges`, i.e., it can push an otherwise CI-blocked commit into Shipit's auto-merge/deploy pipeline for a stack the attacker does not control — an unauthorized deploy/merge path. Forging a `push` event similarly forces `stack.sync_github` for a stack belonging to another organization. This satisfies the "unauthorized deploy, rollback, or merge" / "cross-repository writes" impact bar, achieved with no Shipit session, no `ApiClient` token, and no knowledge of the victim organization's `webhook_secret` or GitHub App private key.

### Likelihood Explanation
Exploitability requires only that the Shipit instance tracks repositories across more than one GitHub organization (a documented, supported configuration — `config/secrets.development.example.yml` shows the multi-org schema) and that the attacker controls a validly-signed webhook for at least one of those organizations (including the trivial case where that organization's `webhook_secret` was left blank, which `GithubApp#verify_webhook_signature` explicitly treats as "always verified": `return true unless webhook_secret`). No interaction with the victim organization's credentials is needed at any point.

### Recommendation
- Short term: after signature verification succeeds for organization `repository_owner`, cross-check that the resolved `Repository`/`Stack` for `repository.full_name` actually belongs to that same verified organization before invoking any handler; reject the webhook otherwise.
- Long term: bind the verified organization identity to the object being mutated for every webhook-driven state change, analogous to requiring the `dtf_program_signer` account on every trade instruction — never let a downstream handler resolve its target from a payload field that was not the one used for authentication.

### Proof of Concept
1. Shipit is configured with two organizations: `org-a` (attacker controls/administers its GitHub App webhook, or `webhook_secret` is unset for `org-a`) and `org-b` (victim, properly secured, tracks stack `org-b/victim-repo`).
2. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Attacker signs the request with `org-a`'s (known/blank) `webhook_secret` and sends it to `POST /webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature against `org-a`'s secret.
5. `StatusHandler#process` then looks up commits by `sha` regardless of organization and calls `commit.create_status_from_github!`, marking the victim's commit as passing CI and triggering `stack.schedule_merges`, without ever validating that `org-a` (the authenticated org) owns `org-b/victim-repo`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

module Shipit
  module Webhooks
    module Handlers

        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String

          accepts :created_at, String

          end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
