### Title
Cross-organization webhook authorization bypass via `repository_owner`/`repository.full_name` mismatch in `WebhooksController` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's GitHub App/webhook secret to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), but the handlers that actually mutate state (e.g. `PushHandler`, `CheckSuiteHandler`, `PullRequest::OpenedHandler`) look up the target `Repository`/`Stack` using a completely separate field, `payload.dig('repository', 'full_name')`. Nothing ties the two together, so the organization whose secret authenticated the request is not necessarily the repository being written to.

### Finding Description
`verify_signature` in [1](#0-0)  computes `repository_owner` from the JSON body itself: [2](#0-1) 
and uses it to pick the `Shipit.github(organization: repository_owner)` instance whose `webhook_secret` verifies the HMAC signature via `verify_webhook_signature` in [3](#0-2) .

Once verified, `create` hands the *entire raw payload* to the registered handler for the event, e.g. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in [4](#0-3) . Handlers derive the target repository from a *different* JSON field — `repository.full_name` — via the base `Handler#repository_name`/`#stacks` helpers: [5](#0-4) 
and `Repository.from_github_repo_name` simply splits `full_name` on `/` and looks the row up with no cross-check against the org that authenticated the request: [6](#0-5) 

Because Shipit supports multiple independently configured GitHub Apps/organizations (each with its own `webhook_secret`, as configured in [7](#0-6)  and [8](#0-7) ), a party who legitimately administers/knows the `webhook_secret` for one onboarded organization ("OrgA") can craft (or replay with edits) a webhook body where `repository.owner.login` (or `organization.login`) is `"OrgA"` — so it authenticates against `OrgA`'s secret — while `repository.full_name` is set to `"OrgB/some-repo"`, a repository belonging to a completely different, unrelated tenant organization onboarded on the same Shipit instance.

The equality that should hold but doesn't:
`organization authenticated by HMAC (repository.owner.login / organization.login)` == `organization implied by repository.full_name used to resolve the Repository/Stack that gets written to`.

Before the attacker's crafted request: `repository_owner("OrgA") == full_name_owner("OrgA")` for legitimate GitHub-originated webhooks (GitHub always sends consistent payloads). After the attacker's request: `repository_owner("OrgA") != full_name_owner("OrgB")`, yet the request still passes `verify_signature` and is dispatched to handlers operating on `OrgB`'s data.

### Impact Explanation
Handlers reachable through this path can mutate cross-tenant state:
- `PushHandler` calls `stack.sync_github(expected_head_sha:)` on stacks resolved from the attacker-chosen `full_name`, affecting deploy-tracking state for a repository the attacker does not own — [9](#0-8) .
- `CheckSuiteHandler` schedules `RefreshCheckRunsJob` against another org's commits — [10](#0-9) .
- `PullRequest::OpenedHandler`/`ReviewStackAdapter` can create, archive, or unarchive `ReviewStack` records (which trigger provisioning/deprovisioning, i.e. actual deploy/rollback-like actions) for a repository resolved purely from the attacker-controlled `full_name` field, with no verification that `full_name`'s owner matches the authenticating organization — [11](#0-10) [12](#0-11) .

This crosses the "cross-repository writes" / "unauthorized deploy or rollback" impact bar for multi-tenant Shipit installations, since an attacker who is only trusted for their own onboarded org's webhook stream can trigger writes/provisioning actions against a different org's repositories and stacks.

### Likelihood Explanation
This requires the attacker to control (or know) the `webhook_secret` for at least one organization already configured in a multi-tenant Shipit deployment — i.e., they must be a legitimate but unprivileged tenant on the same instance, not an anonymous internet attacker, and not someone who needs a Shipit session/API token/GitHub App private key. Given Shipit explicitly supports configuring multiple organizations (`config/secrets*.yml`), this is a realistic deployment shape, and the crafted payload is a straightforward unsigned-boundary edit of a field (`repository.full_name`) that is never covered by any consistency check against the field used for signature routing (`repository.owner.login`/`organization.login`).

### Recommendation
In `WebhooksController#verify_signature` (or in the base `Handler`), enforce that the organization used to select/verify the webhook secret matches the owner segment of `repository.full_name` (and any other org-identifying field used later, e.g. `organization.login` in `MembershipHandler`) before dispatching to handlers. Concretely, after successfully verifying the signature, re-derive `repository_owner` from the same field(s) the handlers will use, and reject the request (422) if they diverge, e.g.:
```ruby
def verify_signature
  ...
  full_name_owner = params.dig('repository', 'full_name')&.split('/', 2)&.first
  if full_name_owner && full_name_owner.casecmp(repository_owner.to_s).nonzero?
    return head(422)
  end
  ...
end
```

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. As an administrator of `OrgA` (attacker), obtain `OrgA`'s `webhook_secret` (legitimately known, since it was configured for their own org's GitHub App).
3. Build a `push` event JSON payload with:
   - `repository.owner.login = "OrgA"` (so `WebhooksController#repository_owner` resolves to `OrgA`, and the HMAC is computed/verified using `OrgA`'s secret).
   - `repository.full_name = "OrgB/victim-repo"`, `ref = "refs/heads/master"`, `after = "<attacker chosen sha>"`.
4. Sign the raw JSON body with `OrgA`'s `webhook_secret` using `Hook::DeliverySigner`-equivalent HMAC-SHA1 and set `X-Hub-Signature`.
5. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` passes because it only checks the `OrgA` secret against `repository_owner == "OrgA"`.
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on `OrgB`'s stack, even though the request was never authenticated by `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

          def archive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no Stack exists. Ignoring."
              )
              return true
            end
            return if stack.archived?

            stack.remove_from_provisioning_queue
            stack.deprovision
            stack.archive!(user, *args, &block)
          end

          def unarchive!(*args, &block)
            if stack.blank?
              Rails.logger.info(

              )
              return create!
            end
            return unless stack.archived?

              Shipit::ReviewStackProvisioningQueue.add(stack)
              stack.unarchive!(*args, &block)
            end
          end
