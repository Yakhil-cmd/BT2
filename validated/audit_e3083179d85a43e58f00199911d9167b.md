I found a genuine cross-tenant authorization break. The `StatusHandler` webhook handler is the outlier among GitHub webhook handlers: unlike `PushHandler` and `CheckSuiteHandler`, it never scopes its lookup to the repository the payload claims to be about.

### Title
Cross-organization commit status injection via unscoped `StatusHandler` webhook lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization to verify the HMAC signature against using the `repository.owner.login` (or `organization.login`) found in the *payload itself*. Verification only proves the request was signed with **that organization's** webhook secret — it does not restrict *which* commit/stack the handler is allowed to touch. `StatusHandler#process` ignores this binding entirely and updates **any** commit in the database whose `sha` matches, across all stacks and all organizations.

### Finding Description
`WebhooksController#verify_signature` selects the org-scoped secret from attacker-supplied payload fields: [1](#0-0) [2](#0-1) 

This only proves "the request was signed by the organization named in the payload" — it says nothing about which repository/stack the event is allowed to affect. The other real handlers enforce that binding by scoping to the repository named in the payload via the shared `Handler#stacks` helper: [3](#0-2) [4](#0-3) [5](#0-4) 

`StatusHandler`, however, never calls `stacks`/`repository_name` and instead queries `Commit` globally by SHA, with no repository/organization filter at all: [6](#0-5) 

The write itself lands on whatever stack the matched `Commit` belongs to, regardless of which organization's secret verified the request: [7](#0-6) [8](#0-7) 

This is exactly the class of bug in the report: a loop/lookup that should be bounded by a specific value (here, "the repository/organization that authenticated") but instead runs over the unbounded default (here, "every commit in the database").

### Impact Explanation
Shipit-engine is explicitly multi-tenant: a single instance can host multiple GitHub organizations, each with its own App/webhook secret, as shown in the sample config: [9](#0-8) 

Any organization onboarded to a shared Shipit instance can trivially compute a valid `X-Hub-Signature` for its own webhook secret and POST an arbitrary `status` event body. Because `StatusHandler` matches by `sha` alone across all stacks, that organization can inject a fabricated `success` (or `failure`) CI status onto a commit belonging to a completely different organization's stack, as long as the SHA is known/guessable (e.g., commits on public repos, or SHAs leaked via Shipit's own UI/API).

That injected status directly affects: `enable_ci_on_stack`, `schedule_continuous_delivery` (potentially triggering an unauthorized automated deploy for continuous-deployment stacks), and `MergeRequest#all_status_checks_passed?` used by the merge queue to gate merges (`app/models/shipit/merge_request.rb` `all_status_checks_passed?`/`any_status_checks_failed?`). Forging a "success" status for another org's protected commit can therefore unblock or trigger an **unauthorized deploy or merge** on infrastructure the attacker's organization has no legitimate access to — this satisfies the Critical bar ("unauthorized deploy, rollback or merge", "cross-repository writes").

### Likelihood Explanation
Any organization already integrated with the shared Shipit instance (a low-privilege actor relative to other tenants — no Shipit session, no `ApiClient` token, no GitHub write access to the victim repo is required) can perform this by simply signing a hand-crafted JSON body with its own known webhook secret and POSTing it to the shared `/github/webhooks` endpoint with `X-Github-Event: status`. No race condition, no guessing of secrets, and no interaction with the victim organization is needed beyond knowing/guessing a target commit SHA.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do — restrict the `Commit` lookup to `stacks` derived from `payload.dig('repository', 'full_name')` (or otherwise verify that `repository_owner` used for signature verification matches the owning stack's repository) before updating status.

### Proof of Concept
1. Organization "OrgA" is a legitimate tenant on the shared Shipit instance with its own `webhook_secret` for its GitHub App.
2. OrgA computes `sha1=HMAC(webhook_secret_A, body)` for an arbitrary JSON body: `{"sha": "<victim_orgB_commit_sha>", "state": "success", "context": "ci/required-check", "repository": {"owner": {"login": "OrgA"}}}`.
3. POST this body with header `X-Github-Event: status` and the computed `X-Hub-Signature` to the shared webhooks endpoint.
4. `verify_signature` looks up `Shipit.github(organization: "OrgA")` (from the payload's own `repository.owner.login`), verifies successfully since it's OrgA's own secret.
5. `StatusHandler#process` runs `Commit.where(sha: "<victim_orgB_commit_sha>")`, finds the commit belonging to OrgB's stack (no repository filter), and creates a `success` status on it — potentially unblocking OrgB's merge queue or triggering OrgB's continuous deployment.
