### Title
Automated Commit-Security-Review Silently Skips Commits Delayed Past a Fixed Freshness Window, With No Fallback or Warning - (File: plugins/security-guidance/hooks/gitutil.py)

### Summary
The `security-guidance` plugin's commit-review hook decides whether a git commit is eligible for automated vulnerability scanning based on a fixed 120-second "freshness" window measured against `now`, with no mechanism to detect or compensate for delayed hook execution (system load, async scheduling delay, or any form of "downtime" for the review pipeline). Commits whose reflog timestamp falls outside this window are classified as `stale` and dropped from review, exactly analogous to the reported oracle bug where `reserves()`/`sample()` had "no awareness of how much time has passed since the most recent observation was made" and no fallback flag for unreliable data.

### Finding Description
`_git_reflog_recent_commits` in `gitutil.py` scans the last `max_n` HEAD reflog entries and computes `age = now - int(ct)` for each commit-action entry [1](#0-0) . Only entries with `age <= max_age_s` (default 120s) are returned as `fresh`; everything else is counted only as `stale` and is excluded from the returned SHA list [2](#0-1) .

This mirrors the oracle bug pattern precisely: the function measures only a duration relative to `time.time()` at call time, with a single fixed threshold, and has no logic to distinguish "the commit really is old and irrelevant" from "the review hook itself was delayed" (e.g., by CPU contention, the async `PostToolUse`/`Stop` hook queue backing up, host being under load, or any other execution delay). The docstring for this function even hints at this by noting real-world causes of delay: `"HEAD@{0} is by definition the most recent reflog entry"` is treated specially precisely because the age gate is otherwise unreliable when a chained command runs slowly enough that `%ct` is `>120s` old "by the time the async PostToolUse hook fires" [2](#0-1) . In other words, the code authors already know the hook can be arbitrarily delayed, but the mitigation only special-cases `idx == 0`; any older `HEAD@{1..max_n-1}` entry silently falls out of scope for review the moment execution is delayed past the window — the same class of resilience gap the external report criticizes ("no provision for this issue... no awareness of how much time has passed").

Unlike the report's suggested mitigation ("track average duration... refuse to return a sample, or return a warning flag"), this code path returns a bare `stale` counter with no propagation of a "review may be incomplete" signal to the user, and no refusal behavior — the commit is simply treated as if it never needed review.

### Impact Explanation
This function feeds `compute_v2_review_set`-style logic used by the plugin's automated security code-review hook, which is the actual security control meant to catch vulnerable/malicious code introduced via `git commit`. If the hook's own execution is delayed for any reason (host under load, resource contention, queued async hooks, or any of the "downtime"-style conditions cited in the report), a genuinely recent commit falls outside the 120-second freshness window and is classified `stale`, meaning it is dropped from the fresh SHA list and never gets automated security review. This is a concrete instance of "unauthorized action bypasses a security/tool-authorization boundary due to lack of staleness detection" — an attacker (or an unprivileged, buggy automation) could exploit predictable review-pipeline latency by pushing/queuing commits so their reflog timestamp lands outside the window by the time the async hook executes, causing malicious code changes to slip past the commit-review security control silently, with no warning surfaced anywhere.

### Likelihood Explanation
The comment block explicitly documents that this scenario already happens in normal operation ("chained-command and noop-guard cases" push `%ct` more than 120s stale by the time the hook fires), meaning the failure mode is not a hypothetical edge case but an acknowledged, reachable condition under ordinary load or command chaining — no adversarial network condition is required, only the same class of "large delay before the security check runs" scenario the report is about. This raises likelihood relative to the pure-DoS-attacker-timing scenario in the original report.

### Recommendation
Apply the report's own recommended mitigation pattern here: track typical hook-firing latency, and when a stale count is non-zero, do not silently drop those commits from review — either (a) still review them but flag the result as "delayed review, verify manually," or (b) expand the freshness window dynamically based on observed hook-dispatch latency, or (c) surface a report to the user/session that N commits were skipped from automated review due to staleness so a human can decide whether to run a manual review pass.

### Proof of Concept
Not independently executable from static analysis alone (would require reproducing hook scheduling delay in a live Claude Code session), but the code path is directly traceable:
1. `gitutil._git_reflog_recent_commits(repo_root, max_age_s=120, max_n=5)` computes `age = now - int(ct)` per reflog entry.
2. Any entry with `idx > 0` and `age > max_age_s` is appended to `stale` count only, and is never returned in `fresh` [3](#0-2) .
3. Simulating hook dispatch delay (e.g., a slow/queued async `PostToolUse` invocation, or several commits made in quick succession followed by a slow chained command) causes commits beyond `HEAD@{0}` to age out of the window before the hook reads the reflog, and the caller receives no indication that reviewable commits were dropped — confirmed by the function's own docstring describing this exact real-world trigger [4](#0-3) .

If it is surfaced only in debug logs/metrics and never blocks or warns the interactive user, the impact described above holds at full severity; if it triggers a user-facing warning, severity should be downgraded accordingly.
