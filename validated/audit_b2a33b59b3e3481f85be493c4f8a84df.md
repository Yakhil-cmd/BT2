### Title
Operator Can Handle Transfers for Unregistered Token Addresses, Enabling Unauthorized Asset Drain or Mint — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The `handleERC20Transfer` and `handleERC721Transfer` functions in the Kaia service-chain bridge accept a caller-supplied `_tokenAddress` parameter without verifying it against the bridge's registered token registry. Any registered operator can supply an arbitrary token address, bypassing the namespace/scope restriction that limits the bridge to only handling registered tokens. This is the direct analog of the RocketStorage ACL bug: a registered entity (operator) can affect assets outside its permitted scope.

---

### Finding Description

The bridge contract hierarchy separates outbound requests from inbound handles:

- **Outbound** (`_requestERC20Transfer`): enforces `onlyRegisteredToken(_tokenAddress)` — only registered tokens can be bridged out.
- **Inbound** (`handleERC20Transfer`): enforces only `onlyOperators` — **no check** that `_tokenAddress` is registered. [1](#0-0) 

The `_requestERC20Transfer` path applies the `onlyRegisteredToken` guard: [2](#0-1) 

But `handleERC20Transfer` has no equivalent guard — it proceeds directly to mint or transfer using the operator-supplied `_tokenAddress`: [3](#0-2) 

The same asymmetry exists in `handleERC721Transfer`: [4](#0-3) 

The `BridgeOperator` constructor sets the default `operatorThresholds` for both `ValueTransfer` and `Configuration` vote types to **1**, meaning a single operator vote immediately executes: [5](#0-4) 

---

### Impact Explanation

**Non-mintBurn mode (parent-chain bridge):** The bridge holds ERC20 tokens in escrow. A registered operator can call `handleERC20Transfer` with any ERC20 token address held by the bridge (registered or not) and any `_to` address. With threshold = 1, a single operator immediately drains the specified token balance from the bridge to an arbitrary recipient. This constitutes unauthorized transfer of bridged assets.

**MintBurn mode (child-chain bridge):** If the bridge contract has been granted minter role on any ERC20Mintable token (registered or not), a registered operator can call `handleERC20Transfer` with that token address and mint an arbitrary `_value` to any `_to` address. This constitutes unauthorized minting of bridged assets.

The corrupted state: `IERC20(_tokenAddress).balanceOf(bridge)` decreases (or token supply increases) for a token that was never registered for bridging, with no corresponding legitimate cross-chain request.

---

### Likelihood Explanation

- The default `operatorThresholds[ValueTransfer]` is 1, so a single operator can execute without any co-signer.
- Operators are registered by the bridge owner and are semi-trusted. A compromised or malicious operator can exploit this without any additional privilege.
- The attack requires no special on-chain state beyond being a registered operator — a condition that is explicitly granted by the owner.

---

### Recommendation

Add an `onlyRegisteredToken(_tokenAddress)` check to `handleERC20Transfer` and `handleERC721Transfer`, mirroring the guard already present on the outbound path:

```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,
    ...
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // ADD THIS
{
```

This ensures operators can only settle transfers for tokens that the bridge owner has explicitly registered, matching the namespace-scoped access control pattern recommended in the RocketStorage report.

---

### Proof of Concept

1. Deploy `Bridge` with `modeMintBurn = false`. Fund it with 1000 units of an unregistered ERC20 token `T` (e.g., sent directly via `transfer`).
2. Owner registers operator `A`. Default threshold = 1.
3. Operator `A` calls:
   ```solidity
   bridge.handleERC20Transfer(
       bytes32(0),          // arbitrary requestTxHash
       address(0),          // from (ignored)
       attacker,            // to
       address(T),          // unregistered token
       1000,                // value
       0,                   // requestedNonce
       1,                   // requestedBlockNumber
       ""
   );
   ```
4. `_voteValueTransfer(0)` returns `true` immediately (threshold = 1).
5. `IERC20(T).safeTransfer(attacker, 1000)` executes.
6. Attacker receives 1000 units of `T` from the bridge with no legitimate cross-chain request on the counterpart chain. [6](#0-5) [7](#0-6)
