### Title
`StatusHandler#process` matches commits globally by SHA, letting one org's verified `status` webhook mutate another org's `Commit` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Every other webhook handler (`PushHandler`, `CheckSuiteHandler`, `MembershipHandler`, all `pull_request` handlers) scopes its side effects through `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.repository.full_name)` before touching any `Stack`. `StatusHandler#process` instead runs `Commit.where(sha: params.sha)` with no repository filter at all, so a correctly-signed `status` payload for repository X updates every `Commit` row in the entire database that happens to share that SHA, including commits owned by stacks under a completely different GitHub App/org.

### Finding Description
The binding that should hold is: `GitHubApp(organization: repository_owner_of(payload)).webhook_secret verified payload` == `GitHubApp/org that owns the Stack whose Commit gets mutated`.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) [2](#0-1) . This only proves the payload's *repository field* is authentic for org X's App1 secret.
- `WebhooksController#create` then dispatches to `Shipit::Webhooks.for_event(event)` handlers with the raw JSON `params`, which for a `status` event resolves to `StatusHandler` [3](#0-2) .
- `StatusHandler#process` ignores `payload['repository']` entirely and queries `Commit.where(sha: params.sha)` across all stacks, then calls `commit.create_status_from_github!(params)` on every match [4](#0-3) .
- Contrast with the base class's `stacks` helper, which every sibling handler uses to scope to `Repository.from_github_repo_name(repository_name)` [5](#0-4) [6](#0-5) . `StatusHandler` is the one handler that never calls `stacks`.
- The unique index on `Commit` is `(sha, stack_id)`, not `sha` alone [7](#0-6) , confirming the same SHA is expected to legitimately exist under multiple independent stacks (forks, mirrored/renamed repos, shared history before divergence, etc.), and `Commit.where(sha:)` (without `stack_id`) will return all of them.

Because git commit SHAs are content-addressed and repositories frequently share commit history (forks, upstream/downstream mirrors, or two orgs' repos that happen to include the same historical commits), a `status` event that is fully legitimate and correctly signed for org X's repository can carry a SHA that also exists as a `Commit` row belonging to a `Stack` tracked under org Y's completely separate GitHub App/webhook_secret. `create_status_from_github!` writes the new status (state, description, target_url, context, created_at) onto that unrelated commit and can trigger continuous-deployment side effects (per `Commit#add_status`/CD logic exercised in `test/models/commits_test.rb`).

`verify_signature`, `drop_unhandled_event`, and the `ExplicitParameters` schema for `StatusHandler` (`sha`, `state`, `branches`, etc.) do nothing to prevent this — they only validate payload shape and origin for the *declared* repository, never restrict which `Commit`/`Stack` rows are ultimately mutated.

### Impact Explanation
An attacker who can cause GitHub to emit a real, correctly-signed `status` event for a repository they control (any push/PR/CI status update on their own fork) can mutate `Commit` state — and potentially trigger deploys via continuous deployment — for a `Stack` belonging to a different, unrelated GitHub App/organization tenant of the same Shipit instance, purely because both repositories' histories contain a commit with the same SHA. This is a payload-for-one-repository-mutates-another's-stack/commit scenario, matching the Critical category, and is repeatable against any shared-history repository pair on the instance.

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment configured with more than one GitHub App/org (`github_app_config` keyed by org, as in `lib/shipit.rb#github_app_config`), and (2) two tracked repositories across those orgs that share at least one commit SHA (trivially true for forks of the same upstream, or repos importing/cherry-picking the same commits). No secrets, sessions, or privileged roles are needed by the attacker — only the ability to push to their own repository/fork and let GitHub deliver the resulting `status` webhook, which is standard unprivileged GitHub activity.

### Recommendation
Scope `StatusHandler#process` the same way as every other handler: resolve commits only within `stacks` (i.e., `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks&.commits&.where(sha: params.sha)`) instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status from org X's verified webhook mutates a Commit belonging to org Y's stack" do
  # Two independent tenants/GitHub Apps
  # org_x owns stack_x/repo "org-x/app"; org_y owns stack_y/repo "org-y/app-fork"
  stack_x = shipit_stacks(:shipit)         # tracked under App1 (org "shopify")
  stack_y = shipit_stacks(:cyclimse)       # tracked under a different repo/org, App2

  shared_sha = "deadbeefcafefeed0000000000000000000cafe"
  commit_x = stack_x.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
                                      committer: shipit_users(:walrus),
                                      authored_at: Time.now, committed_at: Time.now)
  commit_y = stack_y.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
                                      committer: shipit_users(:walrus),
                                      authored_at: Time.now, committed_at: Time.now)

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature for org X verified only
  request.headers['X-Github-Event'] = 'status'

  body = {
    sha: shared_sha, state: 'success', context: 'ci/attacker',
    repository: { full_name: stack_x.github_repo_name, owner: { login: 'org-x' } }
  }.to_json

  assert_difference -> { commit_y.reload.statuses.count }, 1 do
    post :create, body:, as: :json
  end
  # BUG: org Y's commit/stack, never authenticated by this request, was mutated
end
```
Expected (buggy) result: `commit_y.statuses.count` increases even though the payload was only ever verified against org X's `webhook_secret` and referenced org X's `repository.full_name`. After the fix (scoping through `stacks`), this assertion should fail — only `commit_x` should receive the status.
