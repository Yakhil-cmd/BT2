### Title
`Api::CCMenuController#stack` bypasses stack-scoping by calling `Stack.from_param!` instead of `stacks.from_param!` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::BaseController#stacks` restricts resolvable stacks to `Stack.where(id: current_api_client.stack_id)` when the API client is scoped to a single stack, and `BaseController#stack` correctly calls `stacks.from_param!`. `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!` directly on the unscoped `Stack` relation, completely bypassing the `stacks` scope for this action, so any authenticated CCMenu token can read the CCTray/CI status of any stack, not just the one it was issued for.

### Finding Description
Binding under audit: for a stack-scoped `ApiClient`, `resolved_stack ∈ Stack.where(id: current_api_client.stack_id)` must hold for every `#stack` resolution in stack-scoped API controllers.

In `app/controllers/shipit/api/base_controller.rb`:
```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`Api::CCMenuController` overrides `#stack`:
```
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

This resolves against the unscoped `Stack` relation, so `resolved_stack` is not constrained to `current_api_client.stack_id` — the equality is broken.

Authorization for this action is `require_permission :read, :stack`, which only calls `ApiClient#check_permissions!(operation, scope)`:
```
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [3](#0-2) 

This check only verifies the client has the generic `read:stack` permission string in its `permissions` array; it never checks `current_api_client.stack_id` against the resolved stack. So it provides no protection against cross-stack access.

Exploit: an attacker who holds any valid CCMenu API token scoped to stack A (`api_clients.stack_id = A`, `permissions` includes `read:stack`) sends `GET /api/stacks/:any_other_stack_id/cc.xml?token=<token>` (or via Basic Auth) with `params[:stack_id]` set to a different repository's stack B. `CCMenuController#authenticate_api_client` authenticates the token normally (`ApiClient.authenticate(params[:token])`), then `#show` calls `stack` (the overridden method), which resolves stack B via `Stack.from_param!` with no scoping, then renders stack B's CCTray XML (`lastBuildStatus`, `lastBuildLabel`, activity, lock status, etc.) via the `shipit/ccmenu/project` template.

Existing guards do not prevent this: `verify_signature`/webhook checks are irrelevant here (this is a token-authenticated read endpoint, not a webhook). `stacks` scoping exists in `BaseController` but is never invoked by the overridden method. `require_permission!`/`check_permissions!` verifies operation type only, not stack identity.

### Impact Explanation
A CCMenu token scoped to one repository's stack can read build/deploy status, lock state, and last-deploy metadata for any other stack in the Shipit instance, across tenants/repositories. This is a cross-tenant unauthorized read of stack state, matching the "High - unauthenticated read of stack state" category (here it's a token confined to one stack reading another's state, i.e., an authorization/scoping bypass with the same effect). It is fully repeatable against arbitrary `stack_id` values by any holder of any single valid CCMenu token, and requires no additional privilege.

### Likelihood Explanation
Preconditions: attacker must possess any one valid, stack-scoped CCMenu `ApiClient` token with `read:stack` permission (these tokens are widely distributed, e.g., embedded in CI badge URLs, README build-status links, or CCTray configuration for a single project) and know or guess another stack's `stack_id`/param (`owner/repo/branch` or the stack's numeric id — stack params are typically not secret, being derivable from GitHub repo names visible to the public). No GitHub secrets, session, or Shipit operator access is needed. This is trivially and repeatably exploitable with a single crafted request.

### Recommendation
Change `Api::CCMenuController#stack` to use the inherited scoping:
```
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
(i.e., remove the override entirely so it falls back to `BaseController#stack`, or explicitly call `stacks.from_param!`).

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (or a new test file), add a test asserting:
1. `Api::CCMenuController#stack` calls `#stacks` (Mocha expectation) rather than `Stack` directly:
```ruby
test "#stack is resolved through the stacks scope" do
  controller = Api::CCMenuController.new
  controller.expects(:stacks).returns(Stack.where(id: @stack.id)).at_least_once
  controller.params = ActionController::Parameters.new(stack_id: @stack.to_param)
  controller.send(:stack)
end
```
2. End-to-end proof that a token scoped to stack A can read stack B:
```ruby
test "a token scoped to one stack cannot read another stack's status" do
  scoped_client = ApiClient.create!(name: 'x', creator: @user, stack: @stack, permissions: ['read:stack'])
  other_stack = Stack.create!(repository: Repository.new(owner: 'other', name: 'repo'), branch: 'main')

  get :show, params: { stack_id: other_stack.to_param, token: scoped_client.authentication_token }

  assert_response :not_found # expected after fix; currently returns 200 with other_stack's data
end
```
Before the fix, the second test returns `200 OK` with `other_stack`'s CCTray XML, demonstrating the scope bypass; after routing through `stacks.from_param!`, it raises `Stack::NotFound`/renders 404 because `other_stack` is outside `current_api_client.stack_id`.
