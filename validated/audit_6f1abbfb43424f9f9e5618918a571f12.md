### Title
Pool creator fees can be permanently frozen if the creator's fixed ATA is frozen/blacklisted, with no way to redirect or recover funds - (File: programs/cp-swap/src/instructions/collect_creator_fee.rs, programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs)

### Summary
`collect_creator_fee` and `collect_creator_fee_permissionless` always send accumulated creator fees to a token account whose address is deterministically derived from the immutable `pool_creator` field stored in `pool_state`, with no alternate-destination or admin-override path, analogous to the referenced `setManager` DoS where a forced transfer to a fixed, potentially-blacklisted/frozen address blocks the only mechanism for recovering value.

### Finding Description
Both collection instructions constrain the destination account to be the creator's own ATA and derive/create it with `associated_token::authority = creator`: [1](#0-0) [2](#0-1) 

The `creator` address itself is immutably pinned to `pool_state.load()?.pool_creator` in both accounts structs: [3](#0-2) [4](#0-3) 

The actual fee transfer goes through `transfer_from_pool_vault_to_user`, which performs a `transfer_checked` CPI that will fail if the destination token account is frozen by the mint's freeze authority: [5](#0-4) 

Critically, `is_supported_mint` only restricts a narrow allow-list of Token-2022 *extensions* (`TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, `ScaledUiAmount`) for pool token mints, and does nothing to prevent or account for a mint's freeze authority — which is a base SPL Token field present even on plain legacy `Token` mints (e.g., USDC-style tokens) and is entirely outside this allow-list check: [6](#0-5) 

Because the ATA address for `(creator, mint)` is deterministic, if the creator's freeze authority (e.g., a centralized stablecoin issuer) freezes that specific account, every future call to `collect_creator_fee` / `collect_creator_fee_permissionless` reverts on the `transfer_checked` CPI. There is no admin function to change `pool_creator`, no alternate recipient parameter, and no way to sweep/redirect the accrued `creator_fees_token_0` / `creator_fees_token_1` elsewhere — the same "forced transfer to a hard-coded, potentially frozen address, with no recovery mechanism" pattern as the referenced `setManager` DoS.

### Impact Explanation
Once the creator's ATA is frozen, `creator_fees_token_0`/`creator_fees_token_1` continue to accrue on every swap (via `update_fees`) but can never be withdrawn — the funds are permanently locked inside the pool's token vaults with no code path to release them. This is a permanent freezing of the pool creator's earned funds, matching the "permanent freezing of user or LP funds" acceptance criterion.

### Likelihood Explanation
Exploitation requires an external actor (the mint's freeze authority, e.g., a stablecoin issuer like Circle for USDC) to freeze the specific creator ATA — this mirrors the exact precondition in the source report (USDC blacklist). Given that `is_supported_mint` does not vet or reject mints with an active/settable freeze authority, any pool created with such a token as `token_0`/`token_1` is exposed. This is a plausible, not purely theoretical, occurrence given the prevalence of freeze-authority-capable tokens (including USDC/USDT) among typical AMM trading pairs.

### Recommendation
Do not hard-bind the fee recipient's token account to a derived ATA of an immutable `pool_creator`. Options: allow the pool creator (or an authorized party) to specify an alternate destination token account per-call (similar to how `collect_protocol_fee`/`collect_fund_fee` accept arbitrary `recipient_token_*_account`s), or add an admin/creator-controlled path to update the fee-recipient address so a frozen destination can be swapped out, preventing permanent loss of accrued fees.

### Proof of Concept
1. Create a pool where `token_0` (or `token_1`) is a token with a freeze authority (e.g., a legacy SPL token acting like USDC).
2. Perform swaps so that `creator_fees_token_0` accrues in `pool_state` via `update_fees`.
3. The mint's freeze authority freezes the pool creator's ATA for that mint (the deterministic ATA derived from `pool_creator` + mint).
4. Any subsequent call to `collect_creator_fee` (by the creator) or `collect_creator_fee_permissionless` (by anyone) reverts inside `transfer_from_pool_vault_to_user`'s `transfer_checked` CPI because the destination account is frozen.
5. Since `creator` in the accounts struct is permanently constrained to `pool_state.pool_creator` and there is no instruction to change it or the recipient account, the accrued creator fees remain stuck in the vault indefinitely.

```rust
pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
```

```rust
pub fn is_supported_mint(
    mint_account: &InterfaceAccount<Mint>,
    mint_associated_is_initialized: bool,
) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;
    let extensions = mint.get_extension_types()?;
    for e in extensions {
        if e != ExtensionType::TransferFeeConfig
            && e != ExtensionType::MetadataPointer
            && e != ExtensionType::TokenMetadata
            && e != ExtensionType::InterestBearingConfig
            && e != ExtensionType::ScaledUiAmount
        {
            return Ok(false);
        }
    }
    Ok(true)
}
```
