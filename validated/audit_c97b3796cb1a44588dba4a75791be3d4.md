### Title
`shipit.yml`'s `machine.environment` on an untrusted PR branch can override `GITHUB_TOKEN` in `TaskCommands#env` - ([File: lib/shipit/task_commands.rb])

### Summary
`TaskCommands#env` merges `deploy_spec.machine_env` (raw, unfiltered content read from the `machine: environment:` key of the `shipit.yml` checked out from the task's working directory) *after* `Commands#base_env` has already set the real `GITHUB_TOKEN`, with no allowlist restricting the keys `machine_env` may contain. For a `ReviewStack`, that `shipit.yml` is checked out from the fork PR's head commit, so an attacker who can push a branch/PR fully controls this hash and can set `GITHUB_TOKEN` to an arbitrary string, replacing the real deploy token for every command spawned for that task.

### Finding Description
The broken binding: `(keys defined in a PR-branch shipit.yml's machine.environment) ∩ (reserved keys set by Commands#base_env, e.g. GITHUB_TOKEN) = ∅` is **not enforced**.

Path:
- `Commands#base_env` sets `'GITHUB_TOKEN' => github.token` [1](#0-0) .
- `TaskCommands#env` builds the final env by chaining merges: `super` (→ `base_env`) `.merge(@stack.env)` `.merge({fixed keys})` `.merge(deploy_spec.machine_env)` `.merge(@task.env)` — `deploy_spec.machine_env` is merged after `GITHUB_TOKEN` is set and is not filtered [2](#0-1) .
- `DeploySpec#machine_env` simply returns `config('machine', 'environment') || {}` [3](#0-2) , and `DeploySpec::FileSystem` loads that `config` straight from the `shipit.yml`/`.shipit/shipit.yml` file found under `@task.working_directory` (the checked-out commit) [4](#0-3) [5](#0-4) .
- Unlike `deploy_variables`/`task_definitions.variables`, which are explicitly passed through `EnvironmentVariables#permit` via `filter_deploy_envs`/`filter_envs` before user-supplied overrides are accepted [6](#0-5) [7](#0-6) , `machine_env` has no equivalent allowlist check anywhere before being merged into the spawned command's environment.
- For a `ReviewStack`, the branch is the PR author's fork branch (`params.pull_request.head.ref`) as set by `ReviewStackAdapter#stack_attributes` [8](#0-7) , so the `shipit.yml` content read by `DeploySpec::FileSystem` for review-stack tasks is attacker-authored.

Note: I could not confirm in the retrieved code that `ReviewStackAdapter#stack_attributes` seeds `Stack#environment_variables` directly (it only sets `branch`, `environment`, `ignore_ci`, `continuous_deployment`), so the specific `@stack.env`/`StackCommands#env` override path described in the question is not substantiated by the code I could inspect. The actually demonstrable and equally severe path is through `deploy_spec.machine_env` in `TaskCommands#env`, which is unambiguously attacker-controlled for review stacks and unfiltered.

### Impact Explanation
Any command run for a review-stack task (deploy, rollback, custom task) receives an attacker-chosen `GITHUB_TOKEN` value instead of the real deploy token. Downstream steps that read `$GITHUB_TOKEN` (e.g., `git push`, API calls invoked from deploy/rollback/task scripts) will use the attacker's value, and — worse — if the task output prints `env` or the script echoes credentials, this could also mask/replace legitimate credential usage. This matches "GITHUB_TOKEN override / potential credential leak" for the affected stack's repository, repeatable on every task run for any review stack whose PR shipit.yml sets `machine.environment.GITHUB_TOKEN`.

### Likelihood Explanation
Low cost, no privileges required beyond opening/pushing a PR from a fork that is provisioned as a review stack (feature must be enabled by the maintainer via `Shipit.review_stacks_enabled?`-style config, which is a deployment configuration, not a Shipit secret). The attacker only needs to add a `machine: environment: GITHUB_TOKEN: ...` block to `shipit.yml` on their own branch.

### Recommendation
Filter `deploy_spec.machine_env` (and `@stack.env`) through a reserved-keys denylist/allowlist before merging into `TaskCommands#env`/`StackCommands#env`, rejecting or stripping any key already defined by `Commands#base_env` (`GITHUB_TOKEN`, `GITHUB_DOMAIN`, `GIT_ASKPASS`), analogous to how `EnvironmentVariables#permit` is already applied to `deploy_variables`/task variables.

### Proof of Concept
minitest plan (extends existing `test/unit/deploy_commands_test.rb` patterns):
```ruby
test "machine_env cannot override GITHUB_TOKEN" do
  Shipit.github(organization: 'shopify').stubs(:token).returns('real-token')
  @deploy_spec.stubs(:machine_env).returns('GITHUB_TOKEN' => 'attacker')
  command = @commands.perform.first
  assert_equal 'real-token', command.env['GITHUB_TOKEN']  # binding under test: base_env['GITHUB_TOKEN'] == command.env['GITHUB_TOKEN']
end
```
Currently this assertion fails because `command.env['GITHUB_TOKEN']` equals `'attacker'`, since `deploy_spec.machine_env` is merged unfiltered after `base_env` in `TaskCommands#env` (`lib/shipit/task_commands.rb:46`).
