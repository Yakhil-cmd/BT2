### Title
Payer can set an arbitrary, unverified `pool_creator` in `initialize_with_permission`, permanently freezing accrued creator fees - (File: programs/cp-swap/src/instructions/initialize_with_permission.rs)

### Summary
`initialize_with_permission` accepts `creator` as an `UncheckedAccount` that is never required to sign and is never checked against `payer` or the `permission` PDA [5](#0-4) [6](#0-5) . This arbitrary address is written directly into `PoolState.pool_creator` [2](#0-1) , permanently binding future creator-fee accrual and collection rights to an address the caller never proved control over.

### Finding Description
The `Initialize` instruction (non-permissioned) sets `pool_creator` to the transaction's own `creator: Signer<'info>`, guaranteeing that whoever creates the pool controls the creator identity [7](#0-6) [8](#0-7) . By contrast, `InitializeWithPermission` decouples the paying/permissioned signer (`payer`, gated by the `Permission` PDA seeded on `payer.key()`) from the `creator` field, which is merely an `UncheckedAccount` supplied as instruction data with no signature or ownership check [6](#0-5) . `pool_state.initialize(...)` then stores this attacker-chosen `creator.key()` as `pool_creator` with `enable_creator_fee = true` [2](#0-1) .

Once the pool is live, every swap accrues a `creator_fee` slice of the trade fee (carved directly out of the swap's total fee, i.e. real value taken from traders/LPs) into `creator_fees_token_0/1` [3](#0-2) [4](#0-3) . Withdrawal of these fees is exclusively gated on `pool_creator`: `collect_creator_fee` requires `creator: Signer` whose address must equal `pool_state.pool_creator` [9](#0-8) , and even the "permissionless" variant only relaxes the *caller* requirement but still routes all proceeds to the fixed `pool_creator` address via an ATA, using `creator` only as an `UncheckedAccount` matched by `address` constraint, not as a signer [10](#0-9) .

Because `payer` never has to prove control of `creator` (no signature, no seed derivation from `payer`, no relationship to the `permission` PDA which is keyed on `payer` alone), a caller can:
- Set `creator` to a keypair whose private key nobody holds (a "burn"/unownable pubkey), so `collect_creator_fee` can never be signed and `collect_creator_fee_permissionless` deposits fees into an ATA that no one can ever move — permanently freezing the accrued `creator_fees_token_0/1` value that was skimmed out of every swap.
- Impersonate a real, known address (e.g., a reputable protocol/market maker) as "pool creator" without their consent, misrepresenting endorsement of the pool while diverting a portion of every swap's fee to that address's control, exactly analogous to the OpenQ bug class of binding privileged identity/state to an unverified, attacker-supplied ID.

### Impact Explanation
This is a permanent freezing-of-funds vector: value that is unconditionally deducted from every swap as `creator_fee` [11](#0-10)  becomes irrecoverable once `pool_creator` is set to an address nobody controls, since both collection paths ultimately require either a signature matching `pool_creator` or send funds to an ATA owned by that unowned address [12](#0-11) [13](#0-12) . There is no mechanism (e.g., admin fallback, protocol reclaim) to recover these frozen fees, and the value is siphoned out of the pool's fee economics affecting swappers/LPs on every trade for the pool's lifetime.

### Likelihood Explanation
Any account satisfying the `permission` PDA check for its own `payer` key can call `InitializeWithPermission` and supply any pubkey as `creator`; no cross-check, signature, or relationship to `payer`/`permission` is enforced on that field [5](#0-4) . This requires a single transaction with attacker-chosen accounts and no special privileges beyond whatever permission-gating already applies to pool creation, making it straightforward to trigger.

### Recommendation
Require `creator` to either be the same as `payer`, or require `creator` to be a `Signer` (proving control) in `InitializeWithPermission`, mirroring the non-permissioned `Initialize` flow where `pool_creator` is always the transaction's own signer [7](#0-6) . Alternatively, tie the `permission` PDA check to the `creator` field itself, or add an explicit constraint binding `creator` to a value the caller has proven ownership of, so `pool_creator` can never be set to an address unrelated to the actual pool creator.

### Proof of Concept
1. Attacker (or any account holding a valid `Permission` PDA for its own `payer` key) calls `initialize_with_permission` supplying:
   - `payer` = attacker's own signer (satisfies `permission` seed check).
   - `creator` = an arbitrary pubkey with no known private key (e.g., a deterministically-derived non-signable address), or alternatively a real third party's address without their consent.
2. `create_pool` and `pool_state.initialize(...)` execute normally; `pool_state.pool_creator` is set to the attacker-chosen `creator` key with `enable_creator_fee = true` [2](#0-1) .
3. Users swap against the pool via `swap_base_input`/`swap_base_output`; each swap accrues `creator_fee` into `pool_state.creator_fees_token_0/1` [14](#0-13) .
4. `collect_creator_fee` cannot be called because no one can produce a signature for the chosen `creator` pubkey [9](#0-8) ; `collect_creator_fee_permissionless` can be called by anyone but only deposits the accrued fees into an ATA owned by the unowned `creator` address [15](#0-14) , from which the tokens can never subsequently be moved since no signer exists for that authority.
5. Result: the creator-fee portion of every trade against this pool is permanently and irrecoverably locked.
