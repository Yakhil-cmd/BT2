### Title
Cross-tenant repository/stack mutation via unbound `repository.full_name` vs. HMAC-verified organization - (File: `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`Handler#stacks`/`#repository_name` resolve the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')`, while `WebhooksController#verify_signature` selects which organization's webhook secret to validate the HMAC against using the *different* field `payload.dig('repository', 'owner', 'login')` (or `organization.login`). Nothing in the request pipeline enforces that these two fields agree, so a payload that is "verified" for one tenant org can carry a `full_name` naming a stack belonging to a completely different tenant.

### Finding Description
The broken binding, stated as an equality that is assumed but never enforced:
`payload.dig('repository','owner','login')` (used in `WebhooksController#verify_signature`, [1](#0-0) , org-selection at [2](#0-1) ) **must equal** the owner segment of `payload.dig('repository','full_name')` (used in `Handler#repository_name`/`#stacks`, [3](#0-2) ).

`verify_signature` picks the `GitHubApp` (and thus the `webhook_secret`) to validate against solely from `repository_owner`, via `Shipit.github(organization: repository_owner)` [4](#0-3) . `GitHubApp#verify_webhook_signature` compares the `X-Hub-Signature` against `OpenSSL::HMAC.hexdigest` of the *whole raw body* using that org's secret, but critically, if no `webhook_secret` is configured for that organization it **short-circuits and returns `true` unconditionally**: [5](#0-4) . `webhook_secret` is explicitly documented as optional (`docs/setup.md` "Webhook secret (optional)") and multiple shipped/test configs leave it `nil` (e.g. `test/dummy/config/secrets.yml`, `config/secrets.development.shopify.yml`).

Once signature verification passes, `WebhooksController#create` forwards the *entire raw JSON payload* unchanged to the handler: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) . The handler never re-derives or checks `repository.owner.login`; it only reads `repository.full_name` to find the `Repository`/`Stack`: `Repository.from_github_repo_name(repository_name)&.stacks` [3](#0-2) , and `Repository.from_github_repo_name` simply splits the string on `/` and does a DB lookup with no cross-org check [7](#0-6) .

Exploit flow (assuming an org configured without a `webhook_secret`, which is a documented, non-default-secured configuration state): an internet attacker, with no session, no API token and no secret of any kind, POSTs directly to `/webhooks` with:
- `X-Github-Event: push` (or `check_suite`, `pull_request`)
- body: `{"repository": {"owner": {"login": "<org-without-secret>"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/<victim-branch>", "after": "<attacker-chosen-sha>"}`

`verify_signature` resolves `repository_owner = "<org-without-secret>"`, calls `Shipit.github(organization: "<org-without-secret>")`, and `verify_webhook_signature` returns `true` immediately because `webhook_secret` is blank — no signature is even checked. `PushHandler#process` then runs `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }` [8](#0-7)  against the victim's stack resolved via `full_name = "victim-org/victim-repo"`, enqueuing `GithubSyncJob` for the victim's stack. Similarly `CheckSuiteHandler#process` schedules check-run refresh on victim commits [9](#0-8) , and PullRequest handlers (`ClosedHandler`, `LabeledHandler`, `OpenedHandler`, etc.) can archive/unarchive or provision victim review stacks purely off the spoofed `full_name`, e.g. [10](#0-9) .

Existing guards fail to prevent this: `drop_unhandled_event` only checks the event name is registered; `check_if_ping` only special-cases `ping`; `ExplicitParameters` schemas only validate types/presence of fields, never cross-field consistency between `repository.owner.login` and `repository.full_name`; and `Repository`/`Stack` model validations only constrain owner/name character sets, not which webhook context created the record.

Note: `StatusHandler` is not affected by this specific primitive since it looks up by `Commit.sha` directly rather than via `Handler#stacks`/`repository_name` [11](#0-10) .

### Impact Explanation
An attacker can cause writes/state changes against a victim tenant's `Stack`, `Commit`, and review-stack records (branch sync jobs, check-run refresh scheduling, PR-driven archive/unarchive/provisioning) despite the request never being authenticated for that tenant's organization. This is a payload for one repository mutating another tenant's stack/commit/task records — matching the Critical impact bucket. The primitive is generic across every subclass of `Handler` that resolves state via `#stacks`/`#repository_name` (`PushHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler`s), so it is repeatable against any tracked stack in the instance from a single crafted POST per target, as long as at least one configured GitHub organization on the instance has no `webhook_secret` set (or its secret is otherwise known/leaked).

### Likelihood Explanation
Exploitability is conditioned entirely on at least one configured GitHub App/organization in the multi-tenant instance having no `webhook_secret` set — this is documented as optional and is the default in shipped example/test configs (`test/dummy/config/secrets.yml`, `config/secrets.development.shopify.yml`, `config/secrets.development.example.yml` all show `webhook_secret: # nil`). If that precondition holds, exploitation requires zero secrets, zero sessions, and a single crafted HTTP POST with attacker-chosen JSON — trivially cheap and fully repeatable against any repository/stack in the instance. If every configured org has a real, unguessed `webhook_secret`, this specific unauthenticated path is not exploitable (the attacker would need to already know a secret, which is out of scope per the threat model), but the underlying missing cross-check in `Handler#stacks` remains latent and would immediately become exploitable the moment any org's secret is unset, leaked, or a genuinely malicious tenant with a valid secret misuses it.

### Recommendation
Bind the verified organization to the repository resolution:
1. In `WebhooksController#verify_signature`, after establishing `repository_owner`, pass it through to handler invocation (`handler.call(params, verified_owner: repository_owner)`).
2. In `Handler#repository_name`/`#stacks`, require and check that the owner segment of `payload.dig('repository','full_name')` matches the org that was actually verified (case-insensitively), rejecting (e.g., returning `Stack.none`/raising) on mismatch.
3. Treat a blank/absent `webhook_secret` as a configuration error rather than an implicit bypass — require an explicit opt-in (e.g., `insecure_webhooks: true`) to skip signature verification, and log/alert when it happens.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/handler_test.rb`, or via `PushHandlerTest`):
```ruby
test "PushHandler resolves stack purely from full_name, without checking verifying org" do
  victim_stack = shipit_stacks(:shipit) # tracked stack for e.g. "shopify/shipit-engine"
  payload = {
    "ref" => "refs/heads/#{victim_stack.branch}",
    "after" => "deadbeef",
    "repository" => {
      "owner" => { "login" => "attacker-org" }, # org used for HMAC verification
      "full_name" => victim_stack.repository.github_repo_name # "shopify/shipit-engine", NOT "attacker-org/..."
    }
  }

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: "deadbeef"]) do
    Shipit::Webhooks::Handlers::PushHandler.call(payload)
  end
end
```
Assert both sides of the binding explicitly:
```ruby
handler = Shipit::Webhooks::Handlers::PushHandler.new(payload)
assert_equal "shopify", handler.send(:repository_name).split("/").first  # owner used for DB lookup
# vs. verifying org used by controller for HMAC:
assert_equal "attacker-org", payload.dig("repository", "owner", "login")
refute_equal payload.dig("repository", "owner", "login"), handler.send(:repository_name).split("/").first
```
This demonstrates `Handler` never receives nor checks the verifying org, and successfully mutates (enqueues a sync job for) a stack belonging to a different org than the one whose signature was checked.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
