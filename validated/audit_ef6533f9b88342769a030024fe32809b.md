### Title
Unscoped `Commit.where(sha:)` in `StatusHandler#process` lets a `status` webhook for one repository flip CI state and trigger auto-deploy on any other stack sharing the same SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table with no repository filter, unlike the base `Handler#stacks` helper (scoped via `Repository.from_github_repo_name`) that other handlers use. `verify_signature` in `Shipit::WebhooksController` only proves the payload came from *some* GitHub org/repo whose signing secret matches — it never restricts which `Stack`/`Commit` rows the handler is allowed to touch. Because a `success` status write can flip `Commit#deployable?` and (`stack.schedule_merges`/`ContinuousDeliveryJob`) trigger an auto-deploy running as the stack's configured bot identity, an attacker who owns any repository can forge a `ci/integration` success status for a SHA that also exists in a victim stack and force a ship or unblock.

### Finding Description
The invariant that should hold is: `status.repository.full_name == commit.stack.repository.full_name` for every `Commit` row mutated by a `status` webhook. That equality is never checked.

Path:
1. Attacker signs up as any GitHub user, owns/controls a repo `attacker/evil`, and knows (or crafts) a commit SHA that also exists as a `Shipit::Commit` in a victim stack (e.g. by cherry-picking/rebasing a public commit from the victim's open-source repo into their own repo, or by colliding on a SHA the victim stack already recorded from a shared fork/upstream).
2. Attacker's repo has Shipit's GitHub App/webhook installed for their own repository, so `X-Hub-Signature` validates against `Shipit.github(organization: repository_owner)` for **their own org** — `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-49) only checks the signature matches the app registered for the org in the payload, not that the org is the victim's.
3. `WebhooksController#create` (lines 10-15) parses the body and calls `Shipit::Webhooks.for_event('status').each { |handler| handler.call(params) }` with the full attacker-controlled JSON, including `sha`, `context: "ci/integration"`, `state: "success"`.
4. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb, lines 20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This ignores `payload.dig('repository', 'full_name')` entirely — it does not use the `stacks`/`repository_name` scoping helper defined in the base `Handler` class (`app/models/shipit/webhooks/handlers/handler.rb`, lines 32-38), which every repository-scoped handler (push, pull_request, check_suite, membership) relies on. Any `Commit` row across any stack/repository whose `sha` matches the attacker-supplied string is mutated.
5. `Commit#create_status_from_github!` (app/models/shipit/commit.rb, lines 165-169) writes the status, and `add_status` (lines 366-386) recomputes `status`, and if the simple state changed, calls `stack.schedule_merges` and — via `Commit#schedule_continuous_delivery` (lines 281-287) — enqueues `ContinuousDeliveryJob` when `deployable? && stack.continuous_deployment? && stack.deployable?`. On a victim stack configured with `bot_login` (`Shipit.user`), the resulting deploy/merge runs under that bot's identity/credentials, not the attacker's.
6. `Commit#deployable?` (line 227-229) and `Commit#blocked?` (lines 231-237) both depend on the injected status, so the same bug can also be used to *block* a victim stack by injecting a failing/error status for a required context, or to *unblock* by injecting a fabricated `success`.

None of the existing guards catch this: `verify_signature` authenticates the sender's own org, not the target stack; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema in `StatusHandler.params` validates types/presence of `sha`/`state`/`context`, not repository ownership; there is no `require_permission!`/`stacks` scoping call inside `StatusHandler#process` the way there should be.

### Impact Explanation
A single unauthenticated (from Shipit's perspective) webhook to `POST /webhooks`, signed only with the attacker's own repository's webhook secret, can write a `Status` row to any `Commit` in the database that happens to share the submitted SHA, regardless of which stack/repository actually owns that commit. On a victim stack with `bot_login` configured, this can force an auto-triggered deploy or rollback that executes under the bot's credentials, or block a legitimate deploy by injecting a bogus failing status for a required context — this is a cross-repository record write with real ship/block consequences, matching the "payload for one repository mutating another's stack/commit" and "unauthorized deploy/rollback" Critical category. The attack is repeatable against any stack that shares a SHA with an attacker-reachable commit (forks, cherry-picks, shared upstream history are common in practice), and the blast radius spans all stacks/tenants on the same Shipit instance, not just the attacker's own repository.

### Likelihood Explanation
Preconditions: the attacker needs only their own GitHub repository with Shipit's webhook/app installed (something any GitHub user can set up for a repo they own) and a SHA value that also appears as a `Commit` on a victim stack — trivially achievable by forking/cherry-picking a commit from the victim's (often public) history, or by targeting stacks tracking widely-shared upstream commits. No Shipit session, API token, or `Shipit.github_teams` membership is required. Cost is a single crafted HTTP POST to `/webhooks` with a valid signature for the attacker's own org. This is fully repeatable and requires no timing/race window.

### Recommendation
Scope `StatusHandler#process` by the reporting repository, mirroring the base `Handler#stacks` helper:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
(or filter `Commit.where(sha: params.sha)` further by `commit.stack.repository.full_name == repository_name`), so a status can only mutate commits belonging to the repository that authenticated the webhook.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, hypothetical addition):
```ruby
test "a success status from repo A does not affect a commit with the same SHA on repo B's stack" do
  repo_a = shipit_repositories(:shipit)              # attacker-controlled repo
  repo_b = create_repository(full_name: 'victim/app') # victim repo
  stack_b = create_stack(repository: repo_b)
  stack_b.update!(continuous_deployment: true)
  shared_sha = 'a' * 40
  commit_b = stack_b.commits.create!(sha: shared_sha, message: 'shared commit')

  before = commit_b.reload.deployable? # binding LHS: victim commit deployability before attacker's webhook

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/integration',
    'repository' => { 'full_name' => repo_a.full_name } # attacker's own repo
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  after = commit_b.reload.deployable? # RHS: victim commit deployability after attacker's webhook

  assert_equal before, after, "status webhook for repo A must not change deployability of repo B's commit"
  assert_empty commit_b.reload.statuses, "no Status row should be created on a commit not owned by the reporting repository"
end
```
Both sides of the equality (`before == after`) diverge with the current `Commit.where(sha:)` implementation because the status write and `deployable?`/`schedule_continuous_delivery` recomputation happen regardless of `repository['full_name']`; the test fails on current code and would pass once `StatusHandler#process` is scoped to the reporting repository's stacks.     def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
