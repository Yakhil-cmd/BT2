This confirms the pattern: every other event handler (`PushHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler`s) scopes its queries through `stacks`, which is derived from `Repository.from_github_repo_name(repository_name)&.stacks` — i.e., restricted to the repository named in the authenticated webhook payload [1](#0-0) . `StatusHandler#process`, by contrast, queries `Commit.where(sha: params.sha)` globally with no repository/stack scoping at all before writing a `Status` [2](#0-1) , and its `params` schema doesn't even require or reference `:repository` [3](#0-2) .

### Title
Unscoped `Commit.where(sha:)` lookup lets a signed status webhook for one repository write `Status` rows on unrelated stacks - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by `sha` across the entire `commits` table with no repository/stack scoping, unlike every other webhook handler in the engine which restricts to `stacks` derived from the authenticated payload's `repository.full_name`. Any validly-signed `status` webhook (i.e., a legitimate GitHub status event for a repository already onboarded to the Shipit instance) whose commit `sha` happens to collide with a `Commit` row belonging to a different, unrelated stack will cause `Status.replicate_from_github!` to write a status against that unrelated stack too.

### Finding Description
The broken binding is: `commit.stack.repository.full_name` (the stack a `Status` gets written to) should equal `payload.dig('repository', 'full_name')` (the repository that produced and signed the webhook). Instead, `StatusHandler#process` does:

```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This iterates every `Commit` row in the database matching the sha, regardless of which stack/repository owns it, and calls `commit.create_status_from_github!(params)`, which internally uses `stack_id` sourced from the (victim) commit, not from the webhook's authenticated repository:

```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [4](#0-3) 

`Status.replicate_from_github!` then does a `find_or_create_by!` keyed on `stack_id`, `state`, `context`, `created_at`, etc., silently creating a `Status` per matching stack with no cross-check against the requesting repository [5](#0-4) .

For comparison, every other handler restricts its query using the `stacks` helper, which resolves `Repository.from_github_repo_name(repository_name)&.stacks` before touching any records — e.g. `PushHandler#process` (`stacks.not_archived.where(branch:)...`) and `CheckSuiteHandler#process` (`stacks.where(branch: ...)`) [6](#0-5) [7](#0-6) . `StatusHandler`'s params schema doesn't even declare a `:repository` field [3](#0-2) , so nothing in the handler ties the operation to the sending repository.

`verify_signature` in `WebhooksController` only ensures the webhook was legitimately signed by *some* configured GitHub organization matching `repository.owner.login` (or `organization.login`) in the payload [8](#0-7) ; it does not, and cannot, constrain which `Commit`/`Stack` rows the event is allowed to touch — that check must happen (and doesn't) inside the handler. So an attacker only needs a genuinely signed `status` event from a repository they legitimately control (which is already onboarded/uses the same Shipit instance, plausible in shared/multi-tenant or shared-app-secret setups) whose commit `sha` collides with a `Commit` row belonging to a different stack — a documented real-world scenario for scaffold/template-generated repos sharing an identical initial commit (same author, message, and timestamp yields the same SHA-1).

### Impact Explanation
A single legitimately-signed webhook from the attacker's own onboarded repository causes `Status` records to be created against every other stack that happens to have a `Commit` row with the same `sha`, regardless of tenant/organization. Since `Status` state (`success`/`failure`/`pending`/`error`) drives `Commit#state`, CI gating, and (per `Status#enable_ci_on_stack`, `#schedule_continuous_delivery`) downstream continuous-deployment triggers [9](#0-8) , an attacker can inject fabricated "success" statuses onto unrelated stacks' commits, potentially unblocking or misdirecting an unauthorized deploy on a repository/organization they never authenticated to. This is a cross-tenant, unauthorized write — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Exploitation requires: (1) the attacker controls a repository already onboarded to the target Shipit instance and can trigger genuinely GitHub-signed `status` events for it (achievable via CI systems or the repo's own commit-status API, no Shipit secrets needed), and (2) a `sha` collision between the attacker's commit and a `Commit` row already tracked for a victim stack. True SHA-1 preimage collision is infeasible, but identical-content-derived collisions are realistic for shared scaffold/template initial commits (same author/committer identity, message, and timestamp), which is exactly the precondition the question stipulates. Given that precondition, exploitation is trivial and repeatable per victim stack sharing the sha.

### Recommendation
Scope `StatusHandler#process` to the authenticated repository, mirroring other handlers: require `repository.full_name` in `params`, resolve `stacks` via `Repository.from_github_repo_name`, and restrict the commit lookup to `stacks.joins(:commits).where(shipit_commits: { sha: params.sha })` (or equivalent) instead of a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby

test "process only creates statuses for commits belonging to the webhook's own repository" do
  colliding_sha = "a" * 40

  stack_a = shipit_stacks(:shipit) # repository: "shopify/shipit-engine" (attacker's own, onboarded)
  stack_b = create_stack_with_repository("victim-org/other-repo")
  stack_c = create_stack_with_repository("another-victim/unrelated-repo")

  commit_a = stack_a.commits.create!(sha: colliding_sha, ...)
  commit_b = stack_b.commits.create!(sha: colliding_sha, ...)
  commit_c = stack_c.commits.create!(sha: colliding_sha, ...)

  payload = {
    'sha' => colliding_sha, 'state' => 'success', 'context' => 'ci',
    'created_at' => Time.now.iso8601,
    'repository' => { 'full_name' => 'shopify/shipit-engine', 'owner' => { 'login' => 'shopify' } },
    'branches' => [{ 'name' => stack_a.branch }]
  }

  assert_difference -> { Status.where(stack_id: stack_b.id).count }, 0 do
    assert_difference -> { Status.where(stack_id: stack_a.id).count }, 1 do
      Shipit::Webhooks::Handlers::StatusHandler.call(payload)
    end
  end
  # Current (buggy) behavior: Status.where(stack_id: stack_b.id).count and
  # Status.where(stack_id: stack_c.id).count both increase by 1 as well,
  # proving cross-tenant writes.
end
