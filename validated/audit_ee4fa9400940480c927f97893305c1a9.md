### Title
Cross-organization webhook signature confusion enables forged ReviewStack provisioning for arbitrary repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC using `params.dig('repository','owner','login')`, but the pull-request handlers (e.g. `OpenedHandler`) resolve the actual `Repository` to act on using a completely separate field, `params.dig('repository','full_name')`. Because these two fields are never cross-checked, an attacker who controls (or who can exploit an org with no configured `webhook_secret` for) one onboarded GitHub organization can forge a payload whose `owner.login` matches the organization used for signature verification while `full_name` points at a different, victim organization's repository.

### Finding Description
The claimed binding is: `organization_verifying_signature == organization_owning_target_repository`, i.e. `params.dig('repository','owner','login') == params.dig('repository','full_name').split('/').first`. This binding is never enforced.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`) and selects `Shipit.github(organization: repository_owner)` to verify `X-Hub-Signature` against the raw body: [1](#0-0)  and [2](#0-1) .
2. `Shipit.github` looks up the per-org config from `secrets.github`; Shipit explicitly supports multi-organization deployments where each org has its own `webhook_secret` (see `config/secrets.development.shopify.yml` example and `Shipit#github_app_config`): [3](#0-2) .
3. `GitHubApp#verify_webhook_signature` HMACs the raw body against that org's own secret — and if the org has no `webhook_secret` configured, it returns `true` unconditionally: [4](#0-3) .
4. Once verification succeeds, `WebhooksController#create` parses the same raw JSON body and dispatches it, unmodified, to registered handlers: [5](#0-4) .
5. `OpenedHandler#repository` resolves the target `Repository` from a *different* field of the same payload, `params.repository.full_name`, with no reference back to `repository_owner`/the verifying org: [6](#0-5) . The base `Handler` class exhibits the identical pattern via `repository_name`: [7](#0-6) .
6. `Repository.from_github_repo_name` performs a direct `owner/name` lookup with no ownership/org-of-signer check: [8](#0-7) .
7. `OpenedHandler#process` then unconditionally calls `ReviewStackAdapter#find_or_create!` for that resolved repository if the repo's own provisioning settings (`review_stacks_enabled` + `provisioning_behavior_*`) allow it: [9](#0-8) , and `create!` writes a new `ReviewStack`/`PullRequest` row scoped to `repository.review_stacks`: [10](#0-9) .

Exploit flow: an attacker who is onboarded as one tenant org ("attacker-org", with its own real `webhook_secret` configured in this Shipit instance's multi-org `secrets.github` map — the exact scenario the engine documents and supports) crafts a JSON body where `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/victim-repo"`, computes the HMAC-SHA1 using attacker-org's own known secret, and POSTs it to `/webhooks` with `X-Github-Event: pull_request`. `verify_signature` looks up and validates against attacker-org's app/secret and passes. The handler then acts on `victim-org/victim-repo`, provisioning a `ReviewStack` for a repository the attacker never authenticated for. The same primitive works even without a legitimate second org, against any onboarded org whose `webhook_secret` is left blank (`verify_webhook_signature` short-circuits to `true`).

None of the existing guards close this: `verify_signature` only checks that *some* valid signer produced the byte stream — it never re-derives or compares the owner against `full_name`; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema in `OpenedHandler.params` only enforces types/presence of `repository.full_name`, not its relation to `repository.owner.login` (which isn't even part of the required schema for this handler); model validations on `Repository` just constrain characters in `owner`/`name`, not who submitted the webhook.

### Impact Explanation
Impact: Critical — a payload authenticated for one tenant/organization ("attacker-org") mutates state (creates a `ReviewStack`, a `PullRequest` record, and enqueues `ReviewStackProvisioningQueue`) for a different repository/organization ("victim-org/victim-repo") that never authenticated the request. This is a cross-tenant write triggered purely by a signature the attacker legitimately controls for their own org. The same confusion applies to every handler built on the base `Handler#repository_name` (`Handler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`), so archiving/unarchiving/provisioning behavior for arbitrary repositories can be forced by any onboarded tenant, or by exploiting a misconfigured org lacking `webhook_secret`. Repeatable per request against any repository name the attacker chooses, as long as that repository has review-stack provisioning enabled by its own maintainers (a victim-side configuration precondition, not an attacker-controlled one).

### Likelihood Explanation
Requires this Shipit instance to be configured for multiple GitHub organizations (the multi-org `secrets.github` schema the engine explicitly documents and ships example configs for), with the attacker controlling one of those onboarded orgs' webhook secret, OR simply finding any onboarded org with no `webhook_secret` set (which bypasses signature verification for that org entirely, requiring zero secret knowledge). Given multi-tenant Shipit installations are a documented, supported configuration, and per-org `webhook_secret` is explicitly optional in the config template, this precondition is realistic and low-cost for an attacker who is a legitimate member of just one tenant org or who discovers a blank-secret org.

### Recommendation
In `WebhooksController#verify_signature` (or in the base `Handler`), after successfully verifying the signature for `repository_owner`, additionally assert that `repository_owner` matches the owner segment of `params.dig('repository','full_name')` (and of `params.dig('organization','login')` if present) before dispatching to handlers; reject with `422` on mismatch. Alternatively, resolve the repository/org strictly from the same field used for signature verification throughout the handler chain, never from a second, independently-controlled JSON field.

### Proof of Concept
Minitest plan (controller test, e.g. extending `test/controllers/webhooks_controller_test.rb`):
1. Stub `Shipit.github_app_config`/`secrets.github` (or `Shipit.stubs(:github)`) so two orgs exist: `attacker-org` with a known `webhook_secret` = `"attackersecret"`, and `victim-org` with its own distinct secret.
2. Create `victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo", review_stacks_enabled: true, provisioning_behavior: :allow_all)`.
3. Build a `pull_request` `opened` payload: `repository.owner.login = "attacker-org"`, `repository.full_name = "victim-org/victim-repo"`, valid `pull_request` fields.
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "attackersecret", body_json)`.
5. Set `X-Github-Event: pull_request` and `X-Hub-Signature: signature`, POST to `:create`.
6. Assert both sides of the binding: `params.dig('repository','owner','login') == "attacker-org"` (the org whose secret verified the request) while `params.dig('repository','full_name').split('/').first == "victim-org"` (the org actually mutated) — they differ.
7. Assert `response.status == 200`, and `assert_difference -> { victim_repo.review_stacks.count }, 1 do ... end`, confirming a `ReviewStack` was created under `victim_repo` despite the signature only proving knowledge of `attacker-org`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
