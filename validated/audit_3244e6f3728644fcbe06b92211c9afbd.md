### Title
Webhook signature verification is scoped to `repository.owner.login`/`organization.login` while every event handler acts on `repository.full_name`, allowing cross-organization forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
When Shipit is configured for multiple GitHub organizations (the "multi-org" `secrets.github` schema), each organization has its own `webhook_secret` used to verify the HMAC signature of incoming webhooks. The controller picks which organization's secret to verify against using `repository_owner`, which reads `repository.owner.login` (or `organization.login`) from the JSON body. `verify_webhook_signature` then HMACs the *entire raw body* with that org's secret. However, every webhook handler that decides which `Repository`/`Stack` to write to derives that target from a *different* JSON field: `repository.full_name`. Nothing ties `repository.owner.login` to `repository.full_name` to be the same repository/org.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret via `repository_owner`: [1](#0-0) [2](#0-1) 

That selection feeds `Shipit.github(organization: repository_owner)`, which in the multi-org schema looks up a per-organization config (and thus per-organization `webhook_secret`) keyed strictly by that organization name: [3](#0-2) 

`GitHubApp#verify_webhook_signature` HMACs the raw request body with that org's secret and only proves that *someone who knows OrgA's `webhook_secret`* produced this exact byte-for-byte payload - it says nothing about which repository the payload's business fields point to: [4](#0-3) 

Every handler, however, ignores `repository.owner.login`/`organization.login` entirely and resolves the target `Repository`/`Stack` purely from `repository.full_name` in the same JSON body: [5](#0-4) [6](#0-5) 

This is exploited by `PushHandler` (`stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }`) and every `PullRequest::*Handler` (`opened_handler.rb`, `closed_handler.rb`, `reopened_handler.rb`, `edited_handler.rb`, `assigned_handler.rb`, `label_capturing_handler.rb`), all of which resolve `repository` via `Repository.from_github_repo_name(params.repository.full_name)`: [7](#0-6) [8](#0-7) 

`StatusHandler` is even looser - it never looks at the repository at all and updates any `Commit` matching `sha` globally by the signature-verified org, regardless of which org actually owns the commit: [9](#0-8) 

**The broken binding**: `repository_owner` (the identity whose secret authenticated the payload) `≠` `repository.full_name` (the repository the resulting write actually targets). The equality the code implicitly assumes - "the org that signed this webhook is the org whose repository gets mutated" - does not hold, because the controller and the handlers each read a different, independently-attacker-controlled field of the same unsigned-at-the-field-level JSON body.

### Impact Explanation
An attacker who is a legitimate, but unprivileged with respect to OrgB, GitHub user/collaborator on any repository under **OrgA** (an org onboarded to this Shipit instance, hence possessing its own `webhook_secret` which the attacker can obtain by triggering/observing a real GitHub delivery, or by controlling a webhook-eligible action on OrgA's repo such that GitHub itself signs a payload for them) can craft a raw JSON body where:
- `repository.owner.login` (or `organization.login`) = `"OrgA"` → this makes `verify_signature` HMAC-check pass against OrgA's `webhook_secret`.
- `repository.full_name` = `"OrgB/some-repo"` → this is the field every handler actually trusts to select the `Stack`/`Repository` to mutate.

Because signature verification never inspects `full_name`, and the handler logic never inspects `owner.login`/`organization.login`, the forged event is accepted and dispatched against a `Stack` belonging to an entirely unrelated organization (`OrgB`) that the attacker has no GitHub-level access to. Concretely this can:
- Force a `GithubSyncJob`/`stack.sync_github` on OrgB's stack via a forged `push` event (`PushHandler`), causing Shipit to re-sync a stack the attacker doesn't control, which is upstream of triggering `continuous_deployment` deploys - i.e., an **unauthorized deploy**.
- Archive/unarchive OrgB review stacks or otherwise mutate `PullRequest` records cross-org via the `PullRequest::*` handlers.
- Update commit statuses on arbitrary commits stack-wide via `StatusHandler`.

This is a genuine cross-organization/cross-repository write crossing a credential boundary (OrgA's secret being treated as sufficient authority over OrgB's repository), matching the Critical bar of "cross-repository writes / an unauthorized deploy."

### Likelihood Explanation
Requires the attacker to already have webhook delivery capability for at least one onboarded organization (i.e., ability to get GitHub to send a correctly-signed webhook, e.g. via push access to any repo in that org, or via replaying/mutating an event they legitimately receive - note webhooks are JSON, and Shipit does not canonicalize/hash individual fields, only the raw body, so the attacker needs to control the raw body that gets signed, which for a self-hosted org they administer is trivial). Given that, forging the `full_name` field to point at an unrelated org's repo requires no further access. This is realistically exploitable in any deployment using the multi-organization `secrets.github` schema documented in `docs/setup.md`.

### Recommendation
Bind signature verification to the same field the handlers act on: derive `repository_owner` from `repository.full_name`'s owner segment (or explicitly validate that `repository.owner.login`/`organization.login` matches the owner segment of `repository.full_name`) before dispatching, and reject the webhook if they disagree. Alternatively, after verifying the signature for the claimed organization, re-derive the acting `Repository`/`Stack` strictly from a value that was cross-checked against `repository_owner`, so a single signed payload cannot be redirected at a repository outside the signing organization.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (multi-org schema, see `docs/setup.md`).
2. Attacker has push access to a repo in `OrgA` and can trigger/capture a correctly-signed `push` webhook from GitHub for `OrgA` (signature computed with `OrgA`'s `webhook_secret` over the raw body).
3. Attacker edits the raw JSON body's `repository.full_name` to `"OrgB/target-repo"` while leaving `repository.owner.login`/`organization.login` as `"OrgA"`, and recomputes the `X-Hub-Signature` HMAC using the known `OrgA` secret (since the attacker controls the exact bytes being signed via their own OrgA webhook delivery mechanism, e.g. by using a custom webhook endpoint or GitHub App they control on OrgA that lets them choose the payload content signed with the shared secret).
4. POST this body to `WebhooksController#create` with `X-Github-Event: push`.
5. `verify_signature` passes because it validates against `OrgA`'s secret using `repository_owner == "OrgA"`.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` = `"OrgB/target-repo"`, and calls `stack.sync_github` on OrgB's stack - a write crossing the organizational trust boundary despite the attacker having no credentials for `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
