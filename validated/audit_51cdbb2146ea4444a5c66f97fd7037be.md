### Title
Stack-scoped API client tokens bypass their `stack_id` restriction in `CCMenuController#show` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that a stack-restricted `ApiClient` (one created with a `stack_id`) may only ever resolve `stack` from the set of stacks it is authorized for via the `stacks` helper. `Shipit::Api::CCMenuController`, however, overrides `stack` and resolves it directly from `Stack.from_param!(params[:stack_id])`, completely ignoring the token's `stack_id` scope, so any holder of a stack-scoped `read:stack` token can read CI/build status for arbitrary stacks.

### Finding Description
`ApiClient` records can be scoped to a single stack (`belongs_to :stack, optional: true`) [1](#0-0) . `Api::BaseController` is designed to enforce this scope for every request: it computes the authorized set of stacks as `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `stack` is derived from that scoped relation via `stacks.from_param!(params[:stack_id])` [2](#0-1) . This is the binding: *the set of stacks a token authorizes* should equal *the stack the request actually touches*.

`Api::CCMenuController` breaks this binding. It inherits from `BaseController` and declares `require_permission :read, :stack`, which only checks that the token has the `read:stack` permission string — it does not check which stack the token is scoped to (`ApiClient#check_permissions!` just checks `permissions.include?("read:stack")`, with no stack comparison) [3](#0-2) . Crucially, `CCMenuController` overrides the `stack` accessor to bypass the scoped `stacks` relation entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

`#show` then renders using this unscoped `stack`:
```ruby
def show
  latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
  render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
end
``` [5](#0-4) 

Compare this to `Api::StacksController`, which correctly resolves `stack` through the scoped `stacks` relation (`stacks.from_param!(params[:id])`) [6](#0-5) , and to `ApiClient` fixtures such as `here_come_the_walrus`, which is explicitly tested to be limited to a single stack via `stack_id` in other API controllers (e.g. `test/controllers/api/stacks_controller_test.rb` "an api client scoped to a stack will only see that one stack" [7](#0-6) ).

**Before vs after the equality:**
- Before request: `current_api_client.stack_id` = the single stack this token was created for (say Stack A). The security invariant is "the token authorizes Stack A only."
- After request to `CCMenuController#show` with `stack_id` = Stack B (any other stack): the controller happily returns Stack B's build status/CI info because `stack` is computed independent of `current_api_client.stack_id`. The invariant "token authorizes = stack touched" is broken; a token scoped to Stack A now reads Stack B.

This is directly analogous to the reported bug class: a "terminal"/authoritative scoping check (the `stacks` restriction, meant to be enforced consistently everywhere, like the intended terminal `ShuttingDown` state) is silently overridden/bypassed in one code path (`CCMenuController`), letting an operation proceed against a resource it was never supposed to touch — just as the gateway's re-connect thread could revert/bypass the shutdown state and let payments race past the intended barrier.

### Impact Explanation
This lets a holder of any `read:stack`-permitted, stack-scoped `ApiClient` token enumerate/read CI build status, last-deploy status, and revision info of every stack in the Shipit instance, not just the one it was issued for. This matches the High-impact category "unauthenticated read of stack state ... for a token that should only authorize one stack" (escalation into a scope the credential doesn't cover, cross-stack information disclosure).

### Likelihood Explanation
Any deployment that issues scoped `ApiClient` tokens with `read:stack` (a normal, low-privilege permission meant for read-only integrations such as CCMenu widgets — see `CCMenuUrlController`, which auto-provisions such a client with only `read:stack` [8](#0-7) ) is affected. Exploitation only requires sending an HTTP GET with the token and an arbitrary `stack_id` to `/api/:stack_id/ccmenu.xml`; no elevated privileges, secrets, or race conditions are needed.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so the `current_api_client.stack_id` restriction is enforced consistently for this controller as it is for the others.

### Proof of Concept
1. Create (or obtain) a stack-scoped `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A (e.g. via `CCMenuUrlController#fetch`, which mints such a client automatically for any authenticated user).
2. Compute its `authentication_token`.
3. Send: `GET /api/<StackB-owner>/<StackB-name>/<StackB-env>/ccmenu.xml` using Basic auth with the token, where Stack B ≠ Stack A.
4. Observe the response returns Stack B's build name/status/last build info, even though the token was only ever authorized for Stack A — confirmed by `Api::CCMenuController#stack` at [4](#0-3)  never consulting `current_api_client.stack_id`.
