### Title
Unhandled exception in `definition template` authentifier evaluation crashes validating nodes - (File: definition.js)

### Summary
`validateAuthentifiers()` in `definition.js`, used to verify signatures/authentifiers of an address definition when a unit is validated, implements a `'definition template'` operator that looks up a `definition_template` message in the DAG by unit id. If the referenced unit/template is not found (or somehow returns more than one row), the code executes `throw Error("not 1 template")` directly inside an asynchronous `conn.query` callback instead of returning a normal validation error through `cb2`.

### Finding Description
`definition.js` exposes two implementations of the `'definition template'` operator:
- In `validateDefinition()` (used for evaluating address/asset conditions during general definition validation), the analogous code safely returns `cb("template not found or too many")` when the query does not return exactly one row. [1](#0-0) 
- In `validateAuthentifiers()` (used to verify an author's actual signatures/authentifiers against the address definition during unit validation, `validateAuthor` → `validateAuthentifiers`), the equivalent branch instead does: [2](#0-1) 

```js
case 'definition template':
    var unit = args[0];
    var params = args[1];
    conn.query(
        "SELECT payload FROM messages JOIN units USING(unit) \n\
        WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1",
        [unit, objValidationState.last_ball_mci],
        function(rows){
            if (rows.length !== 1)
                throw Error("not 1 template");
            ...
        }
    );
    break;
```

Because `unit` is fully attacker-controlled (an author can define an address whose definition contains `['definition template', ['<any_unit_id>', {...}]]`, since address definitions are self-chosen when an address is first used), an attacker can trivially reference a unit id that does not carry a stable `definition_template` message. This makes `rows.length === 0`, hitting the `throw Error("not 1 template")` line. This `throw` happens inside a database driver callback (asynchronous context), not inside a `try/catch`, and is not caught anywhere up the call chain from `validateAuthor` → `validateAuthentifiers` → `conn.query` callback. In Node.js, an exception thrown from an async callback like this propagates as an uncaught exception, which crashes the entire node process by default (unless a global uncaught-exception handler restarts it, which does not safely resume mid-validation/mid-transaction state).

This is the same bug class as the GPAC CVE: a data structure (`rows` from a descriptor-like lookup) that is not validated for the expected shape/cardinality before being dereferenced, causing an invalid operation (dereferencing `rows[0]` "should" hold, but the code instead crashes hard via an unguarded `throw`) when a crafted/malformed input is supplied.

### Impact Explanation
Any full node (relay, hub, wallet backend) that validates a unit signed by an address whose definition uses `['definition template', [<nonexistent_or_ambiguous_unit>, {...}]]` will crash with an uncaught exception while evaluating that unit's authentifiers. Since unit validation of newly received units is mandatory for every full node to reach consensus, a single crafted unit broadcast to the network can crash every full node that attempts to validate it — a network-wide denial of service that prevents new units from being confirmed until node operators patch/restart, satisfying the "network unable to confirm new units" impact criterion.

### Likelihood Explanation
Likelihood is high: constructing the attack requires only defining (or reusing) an address whose definition contains a `'definition template'` clause pointing to a non-template (or nonexistent) unit id, then posting/broadcasting one unit signed with that address. No special privileges, hub/peer compromise, or race conditions are required — a normal unprivileged unit poster can trigger it deterministically.

### Recommendation
In `validateAuthentifiers()`'s `'definition template'` case (`definition.js` line ~811), replace the `throw Error("not 1 template")` with a graceful failure path consistent with `validateDefinition()`'s handling, e.g. `return cb2(false)` or invoke `fatal_error`/`cb2(false)` so that the authentifier path simply fails to validate (as with other malformed-definition branches) rather than crashing the process. Additionally, wrap the JSON parsing (`JSON.parse(template)`) and `replaceInTemplate` calls in a `try/catch` (mirroring the equivalent protection already present in `validateDefinition()`), since a corrupted/incompatible stored template or parameter set can also throw here.

### Proof of Concept
1. Attacker creates/uses an address whose on-chain definition (posted as `author.definition` when the address is first used) is:
   `['r of set', {required: 1, set: [['definition template', ['<UNIT_HASH_OF_NONEXISTENT_OR_NON_TEMPLATE_UNIT>', {p:'v'}]]]}]`
   (any composite condition can wrap the `definition template` op; a bare `['definition template', [...]]` at top level fails the "each branch must have a signature" check in `validateDefinition`, so wrap it under an `or`/`r of set` alongside a normal `sig` branch to pass initial definition validation while still causing the vulnerable evaluation path to run during signature checking.)
2. Attacker posts a unit signed by this address; `objAuthor.authentifiers` supplies a signature for the `sig` sub-branch (or a bogus authentifier for the `definition template` path—either way, `validateAuthentifiers` evaluates the `definition template` branch as part of walking the full definition tree).
3. `unit` in `args[0]` is chosen to be any 44-byte-formatted base64 string that is not a stable `definition_template` unit (e.g., a random hash, or a real payment unit's hash).
4. During validation of the newly broadcast unit, `validateAuthor` invokes `validateAuthentifiers`, which runs the `'definition template'` case, the DB query returns 0 rows, and `throw Error("not 1 template")` fires inside the `conn.query` callback, crashing the validating node process.

**Confidence note:** I was not able to execute this against a live node in this environment to directly observe the crash; the finding is based on static analysis of the code paths (`validation.js` → `validateAuthor` → `definition.js:validateAuthentifiers`) and the asymmetry between the safe handling in `validateDefinition()` and the unsafe `throw` in `validateAuthentifiers()`. Verifying the exact conditions under which the top-level definition-validation checks (e.g., "each branch must have a signature", complexity limits) still permit reaching this code path in practice should be confirmed with a live/test-network reproduction.
