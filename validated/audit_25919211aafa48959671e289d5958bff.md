### Title
Session Fixation in OAuth Callback Allows Account Takeover via Pre-Set Session Cookie - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
`GithubAuthenticationController#callback` establishes the authenticated identity by writing `session[:user_id]` directly into the existing session hash, without first rotating the session identifier via `reset_session`. This breaks the equality that should hold between "the session identifier a client presents" and "the identity that session is allowed to represent" once authentication state changes, the exact class of trust-binding failure highlighted in the reference report (an uninitialized/unrotated state object being claimed by an unintended party).

### Finding Description
The engine's own authentication concern demonstrates that it knows how to rotate sessions when identity trust changes: `Shipit::Authentication#force_github_authentication` explicitly calls `reset_session` when a stale login is detected before redirecting to re-authenticate. [1](#0-0) 

However, the actual point where a GitHub identity is bound to a session — the OmniAuth callback — does not do this: [2](#0-1) 

`sign_in_github` resolves/creates the `User` from the OmniAuth `raw_info` and merely returns an id, which is then assigned into the *existing* session hash: [3](#0-2) 

Because Rails' `CookieStore`/session middleware does not rotate the session id on a simple `session[:key] = value` write, any session identifier that existed prior to authentication (e.g., one set on the victim's browser for the Shipit host before they ever log in) continues to be valid after `session[:user_id]` is populated. This is the textbook session-fixation binding failure: "session id issued to the client" should equal "session id valid only for the identity that authenticated it," but here a pre-existing (attacker-known) session id becomes valid for whichever GitHub identity next completes the OmniAuth flow using that same browser/session.

`app/controllers/concerns/shipit/authentication.rb` also shows the downstream consumer of `session[:user_id]`: `find_current_user` trusts it unconditionally to look up the bound `User`. [4](#0-3) 

### Impact Explanation
If an attacker can cause a known/fixed session identifier to be set in a victim's browser prior to the victim completing GitHub OAuth login (a classic pre-condition for session fixation, e.g. via any mechanism that lets an attacker set a cookie scoped to the Shipit host before authentication), the attacker's browser — holding the same session id — becomes authenticated as the victim once the victim logs in. This is an authentication bypass / unauthorized account takeover of the victim's Shipit session, matching the explicitly in-scope High-severity category "session fixation / forced OAuth completion." Once fixated, the attacker inherits the victim's `current_user`, including whatever `Shipit.github_teams` authorization and deploy/rollback/merge privileges the victim holds inside Shipit — i.e. escalation into privileged actions without ever presenting valid GitHub credentials themselves.

### Likelihood Explanation
The missing `reset_session` at the login boundary is unconditional and reachable by any unauthenticated user who exercises the standard `/github/auth/github/callback` route; no privileged credential, GitHub App key, webhook secret, or API token is needed to trigger the vulnerable code path itself. The engine's own code proves the team is aware `reset_session` is the correct mitigation (it's used elsewhere for stale-login handling) but it is simply absent from the primary login-completion path, making this a concrete, low-complexity gap rather than a theoretical one.

### Recommendation
Call `reset_session` (or otherwise rotate the session id, e.g. `request.session_options[:renew] = true`) in `GithubAuthenticationController#callback` immediately before or after assigning `session[:user_id]`, so that any pre-existing session identifier cannot be reused post-authentication. Re-assign `session[:authenticated] = true` after the rotation so downstream middleware relying on it (`UserRequiredMiddleware`) continues to work correctly.

### Proof of Concept
1. Attacker requests any page on the Shipit host without a session cookie and captures the `Set-Cookie: _session_id=SID` value issued by the app (or otherwise fixes a known `SID` on the victim's browser for the Shipit domain, e.g. by getting the victim to visit any Shipit URL while sharing/observing that cookie value, or via any host-scoped cookie-setting primitive).
2. Attacker lures the victim (already or subsequently) into visiting `https://shipit.example.com/github/auth/github` while their browser sends the fixed `SID` cookie, and the victim completes GitHub OAuth normally.
3. `GithubAuthenticationController#callback` executes `session[:user_id] = sign_in_github(auth)` against the *same* session record identified by `SID` — no `reset_session` occurs. [5](#0-4) 
4. Attacker now sends requests with the same fixed `SID` cookie; `current_user`/`find_current_user` resolves to the victim's `User` record via `session[:user_id]`. [4](#0-3) 
5. Attacker is now fully authenticated as the victim, including any `Shipit.github_teams` authorization the victim has, enabling unauthorized deploys/rollbacks/merges as that user.
