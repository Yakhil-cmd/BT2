### Title
Cross-tenant Team hijack via unscoped `github_id` lookup in `MembershipHandler#find_or_create_team!` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` looks up teams by `github_id` alone, with no organization filter, while `WebhooksController#verify_signature` only checks that the signature matches the organization named in the payload — not that the `team.id` in the payload actually belongs to that organization. An attacker who controls their own GitHub org and its Shipit webhook secret can therefore forge a `membership` event that mutates a `Team` row belonging to a completely different, privileged organization, adding themselves as a member and gaining `Shipit.github_teams` authorization.

### Finding Description
The broken binding: the organization that signs the webhook (`repository_owner` == `attacker-org`, verified against `Shipit.github(organization: 'attacker-org')`'s `webhook_secret`) is asserted to equal the organization owning the `Team` record referenced by `params.team.id` (`shopify`). These are not the same value, and nothing in the code enforces that they must be.

Code path:
- `WebhooksController#verify_signature` selects the GitHub app config purely from `repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`) and verifies the signature against that org's own `webhook_secret`: [1](#0-0) [2](#0-1) . This only proves the request came from *some* org the attacker legitimately controls (`attacker-org`); it says nothing about the `team` object inside the payload.
- `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` — matching solely on `github_id`, with no `organization:` scoping in the query: [3](#0-2) . If a `Team` row with that `github_id` already exists (e.g. the `shopify` team referenced in `Shipit.github_teams`), `find_or_create_by!` returns that existing record unchanged (the `organization`/`github_team=` block only runs on creation), and `team.add_member(member)` inserts a `Membership` into it: [4](#0-3) .
- `User#authorized?` checks membership against `Shipit.github_teams.map(&:id)` without any organization check either: [5](#0-4) , and `Shipit.github_teams` is populated once from `github.oauth_teams`: [6](#0-5) .

Exploit flow: attacker owns `attacker-org` and has a valid `webhook_secret` for it in `secrets.github`. They discover (or guess/enumerate) the numeric `github_id` of a `Team` row that is part of `Shipit.github_teams` (owned by e.g. `shopify`). They POST `/webhooks` with `X-Github-Event: membership`, `action: 'added'`, `team: {id: X, ...}`, `organization: {login: 'attacker-org'}`, `member: {login: 'attacker'}`, `repository: {owner: {login: 'attacker-org'}}`, signed with `attacker-org`'s own secret. Signature verification passes (correctly, for `attacker-org`). `find_or_create_team!` resolves to the existing privileged `shopify` team by `github_id` match, and `attacker` is added as a member, making `User#authorized?` true for the attacker across the whole Shipit instance.

None of the existing guards catch this: `verify_signature` verifies authenticity of the sender org, not ownership of the referenced team; `drop_unhandled_event` only checks the event is registered; the `ExplicitParameters` schema on `MembershipHandler` only validates types/presence of `team.id`, `team.name`, etc., not org consistency; there is no `require_permission!`/authorization check on inbound webhooks (they're inherently privileged system events, trusted by signature alone); `Team` has no DB uniqueness constraint or model validation scoping `github_id` to `organization`.

### Impact Explanation
A fully unprivileged operator of any GitHub org onboarded to the same Shipit instance can, with a single crafted webhook POST, add arbitrary GitHub logins as members of any `Team` whose numeric `github_id` they know, including teams enumerated in `Shipit.github_teams`. This directly grants `User#authorized?` == true, i.e., full Shipit authorization (deploys, rollbacks, task execution, etc.) instance-wide, without ever authenticating as that team's real organization. This is a cross-tenant privilege escalation and matches the "High - escalation into `Shipit.github_teams` authorization" category (and arguably drifts into deploy/rollback authorization since `authorized?` gates those actions). The action is repeatable for any known `github_id` and any attacker-chosen GitHub login, and reversible/removable membership updates (`action:'removed'`) let the attacker also disrupt legitimate teams by ejecting real members using the same lookup flaw.

### Likelihood Explanation
Preconditions: Shipit configured with multiple GitHub orgs in `secrets.github` (multi-tenant setup, which the question states is a supported/documented configuration), the attacker controlling one such org (a normal, unprivileged onboarding scenario for many self-service Shipit deployments), and a pre-existing `Team` row for the target privileged org (created lazily via `Shipit.github_teams` or prior `membership`/OAuth activity). The `github_id` of a target team is not inherently secret — it can be discovered via public GitHub API team lookups if the target org's team page/API is accessible, or via prior legitimate webhook traffic — and is a small enumerable integer in the worst case. No Shipit secrets are needed beyond the attacker's own legitimately-provisioned webhook secret. This makes the attack low-cost and reliably repeatable.

### Recommendation
Scope the team lookup by both `github_id` and `organization` (derived from the verified `repository_owner`/`organization.login` of the request), e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: repository_owner)`, and additionally validate that `params.organization.login` matches the signature-verified `repository_owner` before trusting it. Consider adding a uniqueness validation/index on `(github_id, organization)` on `Team` to prevent silent cross-org collisions at the model layer as well.

### Proof of Concept
In `test/controllers/webhooks_controller_test.rb` (existing file, out-of-scope to modify per rules, but describing the plan for reference):
1. Configure `secrets.github` fixture-style with two orgs: `shopify` and `attacker-org`, each with distinct `webhook_secret`.
2. Create a `shipit_teams(:shopify_team)` fixture with `organization: 'shopify'`, `github_id: 4242`, included in `Shipit.github_teams`.
3. Build a `membership` payload: `{action: 'added', team: {id: 4242, name: 'shopify_team', slug: 'shopify-team', url: '...'}, organization: {login: 'attacker-org'}, member: {login: 'attacker'}, repository: {owner: {login: 'attacker-org'}}}`.
4. Sign the raw JSON body with `attacker-org`'s `webhook_secret` and set `X-Hub-Signature`/`X-Github-Event: membership` headers; POST to `/webhooks`.
5. Assert response is `200`/`204` (accepted), assert a `Shipit::Membership` row now links `User.find_by(login: 'attacker')` to `shipit_teams(:shopify_team)` (`team.organization == 'shopify'` unchanged), and assert `User.find_by(login: 'attacker').authorized?` is `true`.
6. Both sides of the binding are asserted explicitly: `repository_owner` used for signature verification (`'attacker-org'`) vs. `team.reload.organization` (`'shopify'`) — showing they diverge while the mutation still succeeds.
