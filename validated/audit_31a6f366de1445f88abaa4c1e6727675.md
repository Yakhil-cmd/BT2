## Finding

Shipit's webhook signature check binds only to the **organization named in the payload** (`repository.owner.login`), not to any particular repository, while at least one downstream handler (`StatusHandler`) writes data keyed **only on commit SHA, with no repository/organization scoping at all**. In a multi-GitHub-App deployment where any single org is configured without a `webhook_secret` (an explicitly supported/documented configuration), this breaks the binding "organization that authenticated == repository that is written," letting an outsider spoof commit statuses (and other events) against completely unrelated, victim repositories/orgs — including forging a passing CI status that the merge queue will act on.

### Title
Webhook Authentication Is Scoped to a Payload-Chosen Organization While Event Handling Is Not Scoped to Any Repository, Enabling Cross-Tenant Status Forgery and Unauthorized Merges - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) authenticates an inbound webhook using `repository_owner`, a value read straight out of the untrusted JSON body via `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . If that particular organization's `webhook_secret` is unset (a first-class, documented configuration — see the `webhook_secret: # nil` examples), `GitHubApp#verify_webhook_signature` unconditionally returns `true`, skipping HMAC validation entirely [3](#0-2) .

Once "authenticated" this way, `WebhooksController#create` hands the **entire unauthenticated `params` body** to every registered handler for the event type [4](#0-3) . `Webhooks::Handlers::StatusHandler#process`, unlike other handlers, never scopes to a repository at all — it looks up commits purely by SHA across every stack Shipit manages: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) .

### Finding Description
The equality that should hold is:
`organization whose secret authenticated the request == organization owning the repository/commit that gets mutated`

Before the fix, the code allows:
- `repository_owner` (used to pick the verifying `GitHubApp`/secret) is taken from `repository.owner.login` or `organization.login` in the same JSON body the attacker controls [2](#0-1) .
- If that org has no `webhook_secret` configured, `verify_webhook_signature` short-circuits to `true` without checking anything, since `return true unless webhook_secret` [6](#0-5) .
- `StatusHandler` then applies the payload's `state`/`context`/`target_url` to **every** `Commit` row in the entire Shipit installation whose `sha` matches the attacker-chosen value, with zero repository ownership check [7](#0-6) . (Contrast this with the base `Handler` class, which defines a `stacks`/`repository_name` scoping helper that other handlers such as `PushHandler`, `OpenedHandler`, `ClosedHandler`, etc. all use [8](#0-7)  — `StatusHandler` opts out of this scoping.)

A commit SHA is not secret — it is visible on GitHub, and commit objects are commonly shared across forks (a public fork shares the ancestor history/SHAs of the upstream repository). An attacker who controls (or creates) a GitHub org/repo that Shipit has onboarded with no `webhook_secret` can:
1. Fork or otherwise legitimately trigger a `status` event from GitHub for their own repo, using a SHA that also exists in a victim stack's tracked history (e.g., a shared ancestor commit, or simply crafting the raw webhook POST directly since no signature is enforced for that org).
2. Set `state: "success"` and `context` matching the victim stack's required CI check name (discoverable from the victim's public `shipit.yml`).
3. Because `verify_signature` accepts the request (attacker's unsecured org) and `StatusHandler` never checks which repository the SHA belongs to, Shipit records a spoofed passing status on the victim's commit.

### Impact Explanation
`MergeRequest#all_status_checks_passed?` consumes exactly the status rows written by `StatusHandler` [9](#0-8) , and `ProcessMergeRequestsJob` calls `merge_request.merge!` once all required checks pass [10](#0-9) , which invokes `stack.github_api.merge_pull_request` [11](#0-10) . A forged status can therefore cause Shipit to merge a pull request in a repository the attacker has no access to — an unauthorized merge using the app's own GitHub credentials, matching the Critical-tier impact ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
This requires only that one org in a multi-org Shipit deployment omit `webhook_secret` — a configuration explicitly shown as valid in the shipped example/config files (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`) and in `docs/setup.md`'s "Using Multiple Github Applications" section [12](#0-11) . No Shipit session, `ApiClient` token, or the victim org's own `webhook_secret` is ever needed.

### Recommendation
- Scope every webhook handler (especially `StatusHandler`) to the repository named in the payload the same way `Handler#stacks`/`repository_name` already does for other handlers, and additionally verify that `repository.full_name`'s owner matches the `repository_owner` used for signature verification.
- Do not silently treat a missing `webhook_secret` as "always verified"; either require a secret for every configured organization or reject/flag such configurations at boot.

### Proof of Concept
1. Deploy Shipit with two orgs configured: `victim-org` (has `webhook_secret`, hosts a stack with required CI context `ci/tests`) and `attacker-org` (no `webhook_secret` set, as permitted by the documented config schema).
2. Identify a commit SHA tracked by the victim stack's pending merge request (visible via the public PR on GitHub).
3. POST directly to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim PR head sha>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
   No valid `X-Hub-Signature` is required because `attacker-org` has no `webhook_secret`, so `verify_webhook_signature` returns `true` [6](#0-5) .
4. `StatusHandler#process` matches the commit by SHA alone and records a "success" status against it [5](#0-4) , regardless of `victim-org` being a completely different, secured organization.
5. `ProcessMergeRequestsJob` sees `all_status_checks_passed?` return true and merges the victim's pull request.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
