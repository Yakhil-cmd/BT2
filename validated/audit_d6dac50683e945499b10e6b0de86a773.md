### Title
Unchecked `governance.removevalidator` in `none` governance mode allows any council member to drain the validator set below BFT threshold — (File: `kaiax/gov/headergov/impl/header.go`)

---

### Summary

In `none` governance mode, `checkConsistency` performs zero validation on `governance.removevalidator` votes. Any council member can cast a single vote that removes all other council members (except the governing node) in one block, with no minimum-size guard and no mechanism for targeted validators to respond or prevent removal. The default value for `governance.governancemode` is `"none"`, and since the parameter is now deprecated (cannot be changed via vote), any chain deployed without explicitly setting `"single"` is permanently exposed.

---

### Finding Description

`checkConsistency` in `kaiax/gov/headergov/impl/header.go` handles `AddValidator`/`RemoveValidator` with an unconditional early return in non-`single` mode:

```go
case gov.AddValidator, gov.RemoveValidator:
    params := h.GetParamSet(blockNum)
    // compare with governing node only in single mode.
    if params.GovernanceMode != "single" {
        return nil   // ← zero validation in none mode
    }
``` [1](#0-0) 

In `none` mode this returns `nil` immediately, skipping every safety check:
- No minimum post-removal council size (BFT requires ≥ 4 for fault tolerance)
- No check that the voter is not removing themselves
- No check that the vote would leave a viable committee

The `applyVote` function in `getter_council.go` then applies the removal at the very next block, protecting only the `governingNode`:

```go
for _, address := range addresses {
    if address == governingNode {
        continue
    }
    switch voteKey {
    case gov.RemoveValidator:
        if council.Contains(address) {
            council.Remove(address)
        }
    }
}
``` [2](#0-1) 

Batch removal is supported — a single `removevalidator` vote may list multiple addresses: [3](#0-2) 

The council update formula is incremental and immediate:

```
Council(N) = Council(N-1) + AddValidatorVotes(N-1) - RemoveValidatorVotes(N-1)
``` [4](#0-3) 

The default value for `governance.governancemode` is `"none"`: [5](#0-4) 

Because `GovernanceGovernanceMode` is now deprecated (voting to change it returns `ErrDeprecatedVote`), any chain deployed with the default `"none"` mode cannot migrate to `"single"` mode via governance and is permanently in the vulnerable state: [6](#0-5) 

---

### Impact Explanation

A single council member in `none` mode can issue one `governance.removevalidator` vote listing all peer council members (except the governing node). At the next block, the council is reduced to one address. Istanbul BFT requires `ceil(2N/3)` committed seals; with N=1 the chain halts or a single node produces all blocks unilaterally. This is an invalid validator-set state transition causing consensus divergence on all honest nodes. [7](#0-6) 

---

### Likelihood Explanation

Mainnet and Kairos explicitly configure `"single"` mode, so they are not directly affected. However:
- The default value is `"none"`, so any chain deployed without explicit governance configuration is vulnerable.
- `GovernanceGovernanceMode` is deprecated and cannot be changed via vote, permanently locking such chains in `"none"` mode.
- The attacker needs only to be a council member — a semi-trusted role, not a majority.
- The attack requires a single transaction (one block proposal with a batch `removevalidator` vote).

---

### Recommendation

Add a post-removal council-size check inside `checkConsistency` for `RemoveValidator` in `none` mode. Specifically, verify that `len(council) - len(removedAddresses) >= minCouncilSize` (where `minCouncilSize` is at least 4 for BFT fault tolerance) before accepting the vote. The same guard should be applied in `applyVote` as a defense-in-depth measure. [1](#0-0) 

---

### Proof of Concept

1. Deploy a chain with `governance.governancemode = "none"` (the default, or any non-mainnet deployment).
2. Initial council: `[A, B, C, D, E]` where `A` is the `governingNode`.
3. Council member `B` (or `A`) proposes a block at block `N` containing:
   ```
   header.Vote = removevalidator([C, D, E])   // batch removal
   ```
4. `VerifyVote` calls `checkConsistency` → returns `nil` immediately (no check in `none` mode).
5. `PostInsertBlock` → `applyBlock` → `applyVote` removes `C`, `D`, `E` from the council.
6. At block `N+1`, `Council = [A, B]` — below the BFT threshold of 4.
7. `B` repeats with `removevalidator([A])` — blocked only because `A` is `governingNode`.
8. Final council: `[A]`. Chain halts or `A` produces all blocks unilaterally.

`C`, `D`, and `E` have no mechanism to respond: there is no counter-vote window, no challenge-response process, and no minimum-size guard that would reject the vote at verification time. [1](#0-0) [2](#0-1)

func applyVote(header *types.Header, council *valset.AddressSet, governingNode common.Address) bool {
	voteKey, addresses, ok := parseValidatorVote(header)
	if !ok {
		return false
	}

	originalSize := council.Len()
	for _, address := range addresses {
		if address == governingNode {
			continue
		}
		switch voteKey {
		case gov.AddValidator:
			if !council.Contains(address) {
				council.Add(address)
			}
		case gov.RemoveValidator:
			if council.Contains(address) {
				council.Remove(address)
			}
		}
	}
	return originalSize != council.Len()
```
