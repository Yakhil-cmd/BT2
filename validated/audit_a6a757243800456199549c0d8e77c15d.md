### Title
Cross-Organization Webhook Spoofing via Unverified `repository.owner.login` used to Select the Signature Secret - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate the `X-Hub-Signature` against using a field read straight out of the *unauthenticated* request body (`repository.owner.login` / `organization.login`), while the event handlers that actually mutate state key off a different field in that same unauthenticated body (`repository.full_name`). Because the secret-selection field and the state-mutation field are never bound to each other by the signature check, an attacker can pick an organization whose webhook secret is unset (or otherwise weaker) to trivially satisfy signature verification, then point `repository.full_name` at a stack that belongs to a completely different, properly-secured organization.

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is parsed from `request.raw_post` before any signature has been verified — it is fully attacker-controlled. It is used to pick which `GitHubApp` instance (and thus which `webhook_secret`) validates the signature:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

Note the `return true unless webhook_secret` short-circuit: if the organization named in the payload has no `webhook_secret` configured (documented as optional in `docs/setup.md`), verification is bypassed entirely regardless of payload content.

Meanwhile, every event handler resolves the target `Stack`/`Repository` using a *different* field from the same unauthenticated payload:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

Since `repository.owner.login` (used to choose the trust anchor) and `repository.full_name` (used to choose the object acted upon) are independent, attacker-supplied JSON keys in the same POST body, they are not bound by any shared verified value. An attacker can set `repository.owner.login`/`organization.login` to any organization configured in `secrets.github` that has `webhook_secret` unset (or any org they can otherwise satisfy), while setting `repository.full_name` to the full name of a real, tracked repository belonging to a *different* organization that does have a properly configured secret. The signature check passes (`true` returned unconditionally for the secret-less org), and the handler for `push`/`status`/`check_suite`/etc. then acts on the spoofed repository, e.g. enqueuing `GithubSyncJob` for that stack's `stack_id`, or otherwise mutating commit/status state, task tracking, etc. for a stack the attacker was never authorized to influence.

This is the "organization authenticated versus repository that is written" trust binding called out in scope: `repository_owner` (authenticated side) ≠ the repository/stack actually processed (written side), and nothing enforces `repository_owner == repository.full_name`'s owner post-verification.

### Impact Explanation
An unprivileged, unauthenticated network attacker (no session, no `ApiClient` token, no GitHub credentials) can forge GitHub webhook deliveries that affect stacks belonging to organizations other than the one whose (missing) secret satisfied the check. This can trigger `GithubSyncJob` (re-sync of git refs/HEAD tracked by the stack) [4](#0-3) , forge commit `status`/`check_suite` state used for merge/deploy decisioning [5](#0-4) , or manipulate `membership`/`Team` records used for `Shipit.github_teams` authorization [6](#0-5) . Forged commit-status/check_suite state is particularly significant because Shipit gates deploys on commit statuses/checks, so this can influence whether a revision is considered deployable — an escalation path toward an unauthorized deploy decision, matching the High severity bar ("escalation into `Shipit.github_teams` authorization" / effects on stack state).

### Likelihood Explanation
Exploitability depends on at least one configured GitHub organization in a multi-org Shipit deployment having `webhook_secret` unset — which the setup docs explicitly describe as optional (`docs/setup.md`, "Webhook secret (optional)") — or otherwise being guessable/weak, while another organization's repository is the actual attack target. In single-organization deployments with a properly set `webhook_secret`, this specific path collapses to needing that one secret, which is out of scope. The likelihood is therefore contingent on deployment configuration (multi-org setups mixing secured and unsecured entries), which is a supported and documented configuration schema (`config/secrets.development.shopify.yml`), not a misuse of the engine.

### Recommendation
Bind the field used to select the verification secret to the field used to identify the state to mutate: e.g., after selecting `github_app` by `repository_owner`, re-validate that the resolved `Repository`/`Stack` for `repository.full_name` actually belongs to that same `repository_owner`, and reject the webhook if they diverge. Additionally, consider treating a missing `webhook_secret` as "reject all webhooks for this organization" rather than "accept all", or require `webhook_secret` to be mandatory for any but the default single-org config.

### Proof of Concept
1. Deploy Shipit configured with two organizations in `secrets.github`: `secure-org` (webhook secret set, e.g. tracks `secure-org/prod-repo`) and `insecure-org` (webhook secret left blank per the documented optional setting).
2. POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or any arbitrary value), and JSON body:
```json
{
  "organization": { "login": "insecure-org" },
  "repository": { "owner": { "login": "insecure-org" }, "full_name": "secure-org/prod-repo" },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/main"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "insecure-org")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally [7](#0-6) .
4. `Shipit::Webhooks.for_event('push')` handler resolves the target via `payload.dig('repository', 'full_name')` = `"secure-org/prod-repo"` [8](#0-7) , enqueuing `GithubSyncJob` for the `secure-org/prod-repo` stack despite the request never being authenticated with `secure-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
