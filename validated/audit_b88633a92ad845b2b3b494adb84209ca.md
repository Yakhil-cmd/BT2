### Title
Webhook signature verification is bound to the payload's `repository.owner.login`/`organization.login` while downstream handlers act on `repository.full_name` — cross-organization webhook spoofing - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify the HMAC signature against using a field taken from the *same, attacker-controlled* JSON body (`repository.owner.login`, falling back to `organization.login`), rather than from any transport-level or otherwise trusted identifier. The verified organization identity is never re-checked against the repository that the event handlers actually act on (`repository.full_name`), which is the field used downstream (`GithubSyncJob`, `Status` creation, `RefreshCheckRunsJob`, etc.) to resolve the target `Stack`/`Repository`.

### Finding Description
`verify_signature` computes `repository_owner` purely from the untrusted payload: [1](#0-0) 

and uses it only to pick which per-organization `GithubApp`/webhook secret to verify against: [2](#0-1) 

Shipit supports one `GithubApp` (and one `webhook_secret`) per organization, keyed by an `organization` string passed into `Shipit.github(organization:)`: [3](#0-2) 

Once the signature check passes, the raw parsed payload — not just the field used for verification — is handed unchanged to the event handlers: [4](#0-3) 

The handlers (e.g. `push`, `status`) resolve the target `Stack`/`Repository`/`Commit` from `repository.full_name` (and commit `sha`), a different field of the same body than the one used for signature routing. The test suite demonstrates the controller performs no cross-check between the two: a payload's `repository.full_name` can be mutated independently of `repository.owner.login` and the request is still accepted/processed (only the downstream lookup fails to find a matching stack, not because of a mismatch check): [5](#0-4) 

and the `status` handler creates a `Status` purely from `sha`/`state`/`context`/`repository` fields of the body, unconditional on any relationship to the org used for verification: [6](#0-5) 

**Binding broken:** "organization authenticated" (`repository_owner` → the `GithubApp`/secret whose HMAC passed) ≠ "repository written" (`repository.full_name` → the `Stack`/`Repository`/`Commit` actually mutated). In a Shipit deployment that hosts multiple organizations (each with its own configured `GithubApp`/`webhook_secret`, which is the documented multi-org configuration shape), an attacker who controls (or is a legitimate member of) organization A can sign a webhook payload with A's webhook secret while setting `repository.full_name` (and other fields) to reference a repository/stack belonging to organization B. `verify_signature` passes because it only checks the signature against A's secret using A's own org name from the payload; the handler then acts on B's repository/stack because that's the field it actually reads.

This is directly analogous to the reported Solidity bug: there, a `blsKey → address` binding used by `recordL1Block` could be silently rewritten by an unrelated actor because the write path (`_registerAndStake`) never checked whether the key already belonged to someone else, decoupling "who is authorized" from "what gets recorded as authoritative". Here, "who signed" (org A) is decoupled from "what gets written" (org B's repo/commit/stack), because the field selecting the trust anchor and the field driving the mutation are independent, attacker-controlled parts of the same unsigned-at-selection-time JSON body.

### Impact Explanation
The most severe reachable consequence is spoofing a `status` webhook to inject a forged `success` `Status` for a commit belonging to a victim stack in another organization. Shipit's deploy-safety checks gate deploys on required CI statuses; a forged passing status can make an otherwise-unreviewed/unvetted commit appear deployable, and can also feed `GithubSyncJob`/`RefreshCheckRunsJob` triggers against the victim's stack. This lines up with the in-scope "unauthorized deploy" and "unauthenticated read/write of stack state" impact tiers, since the attacker never needed any credential belonging to the victim organization — only their own (or any) organization's independently configured webhook secret.

### Likelihood Explanation
Exploitability requires only the ability to send an HTTP POST to the public `/github/webhooks` endpoint with a validly-signed body for *any* organization configured in the Shipit instance (no privileged Shipit session, `ApiClient` token, or victim credentials are needed). Any user who is a collaborator/admin on a repository under an org with its own configured GitHub App (a normal multi-tenant Shipit setup) can trigger their own org's webhook, then replay/craft a modified payload with a divergent `repository.full_name`. This is a low-cost, no-privilege attack path, matching the "High" likelihood profile of the original report's analog (only requires unprivileged, attacker-controlled inputs).

### Recommendation
In `WebhooksController`, cross-validate that every repository/organization reference used by downstream handlers (`repository.full_name`'s owner segment, `organization.login`, and any embedded `sender`/`installation` org context) is consistent with the `repository_owner` value that selected the verifying `GithubApp`/secret, and reject the request (422) on mismatch before dispatching to `Shipit::Webhooks.for_event`. Prefer deriving the trust anchor from a value GitHub itself sends out-of-band per app/installation (e.g., `X-GitHub-Hook-Installation-Target-ID` or the installation ID embedded in the app's own registered config) rather than solely from attacker-controlled JSON fields, and additionally verify that the resolved `Stack`'s `Repository#owner` matches the authenticated organization before any handler mutates state.

### Proof of Concept
1. Attacker is a member of GitHub organization `attacker-org`, which has its own `GithubApp` configured in the Shipit instance with webhook secret `S_A` (multi-org Shipit deployment).
2. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "<victim-commit-sha-in-org-B>",
     "state": "success",
     "description": "forced pass",
     "context": "ci/required-check",
     "target_url": "https://example.com",
     "created_at": "...",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "branches": [{ "name": "master" }]
   }
   ```
3. Attacker signs the raw body with `S_A` and sends `POST /github/webhooks` with `X-Github-Event: status` and `X-Hub-Signature: sha1=<hmac-with-S_A>`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (derived from `repository.owner.login`) and successfully verifies the signature against `S_A`. [2](#0-1) 
5. The `status` handler processes the same body's `sha`/`repository.full_name`, resolving `victim-org/victim-repo`'s commit and creating a fraudulent passing `Status` for it, as shown by the equivalent legitimate flow in the test suite (same code path, different — spoofed — organization/repo pairing): [6](#0-5) 

**Note on verification limits:** I was unable to retrieve the exact source of `app/models/shipit/webhooks/handlers/push_handler.rb` and `status_handler.rb` in this session (a tool-call error prevented reading them on the final turn), so the precise line-level logic that resolves `Stack`/`Commit` from `repository.full_name` is inferred from the controller code, `github_app.rb`, and the corroborating test behavior rather than read directly from the handler files. Confirming the exact handler implementation would strengthen (or could disprove, if an owner cross-check already exists there) this finding.
