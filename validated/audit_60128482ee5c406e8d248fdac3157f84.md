### Title
Webhook signature verification keys off `repository.owner.login`, but every event handler dispatches on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multi-tenant GitHub App configuration, where each GitHub organization can have its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects *which* organization's secret to verify the HMAC signature against by reading `repository.owner.login` (or `organization.login`) out of the **same unauthenticated request body** it is about to validate [2](#0-1) . However, once the signature check passes, every downstream handler (`Handler#stacks`/`#repository_name`, `PushHandler`, all `PullRequest::*Handler`s) resolves the actual `Repository`/`Stack` to act on using `repository.full_name` from that same payload [3](#0-2) [4](#0-3) [5](#0-4) . `repository.owner.login` (used to pick the secret) and `repository.full_name` (used to pick the target repository) are two independent JSON fields never cross-checked against each other.

### Finding Description
This is the same class of bug as the report's `Controller.sol` case: a value used to select the "authorization context" (`fs`/`ifs`) diverges from the value actually acted on (the lock's real state), because the two are computed from different, not-mutually-verified sources. Here:

- Authentication binding used: `secret_for(repository.owner.login) == valid_signature(raw_body)` [6](#0-5) [7](#0-6) .
- Effect binding actually exercised: `stack = Repository.from_github_repo_name(repository.full_name).stacks` [3](#0-2) .

Because the signature only proves "this body was HMAC-signed with organization A's webhook secret," and never proves "the repository named in `repository.full_name` belongs to organization A," a party that legitimately controls a GitHub organization "A" configured in Shipit (and therefore its GitHub App and, in a self-registered/self-service multi-tenant deployment, its `webhook_secret`) can craft a raw POST body whose `repository.owner.login` is `"A"` (satisfying `verify_signature`) while `repository.full_name` is `"victim-org/victim-repo"` (satisfying the handler's repository lookup). All handlers keyed on `repository.full_name` — `PushHandler` (triggers `GithubSyncJob`), `StatusHandler` (records commit CI status), and the `PullRequest::*Handler`s (archive/unarchive review stacks, capture labels) — will then execute against a stack that belongs to a completely different, unrelated tenant, despite the signature never covering that binding.

### Impact Explanation
This breaks exactly the binding the rules call out: "an organization that authenticated versus the repository that is written." Concretely reachable effects include:
- Forged `push` events causing `GithubSyncJob` to sync/deploy commits for another tenant's stack it has no access to [8](#0-7) .
- Forged `status` events letting an attacker mark commits on a victim's stack as CI-passing, which the deploy UI relies on to gate an unauthorized deploy.
- Forged `pull_request` events archiving/unarchiving/deprovisioning a victim's review stacks.

This falls under "unauthorized deploy, rollback or merge" / cross-repository writes territory, since a repository belonging to organization A can trigger state changes and deploy pipelines for a repository/stack belonging to organization B, without B's authorization ever being checked.

### Likelihood Explanation
Exploitability strictly depends on the operator running Shipit as a genuinely multi-tenant deployment where `secrets.github` holds multiple per-organization entries (`github_app_config(organization)`) and where an unprivileged-relative-to-victim party controls one of those organizations/apps (and can obtain or set that organization's own `webhook_secret`, e.g. in a self-service onboarding flow) [9](#0-8) . In the common single-tenant deployment (one `github:` block, `github_default_organization` nil) there is only one secret and this specific cross-tenant forgery collapses back to a normal, single-secret webhook — it only manifests as a genuine trust-boundary break in the multi-org configuration. I could not fully verify from the indexed files whether the webhook secret is ever attacker-influenced/self-registered in this codebase (no self-service GitHub App registration flow was found in-scope), which limits confidence that an *unprivileged* attacker (as opposed to a privileged operator) can actually reach this path.

### Recommendation
`WebhooksController#verify_signature` should not use payload data to select the verification secret while the payload is still unauthenticated. Where multiple GitHub Apps/secrets are supported, either look up the app by a signed/opaque routing key (e.g., URL path segment tied to organization, or App ID from a header) instead of `repository.owner.login`/`organization.login`, or — after signature verification succeeds for a given org — additionally assert that `repository.full_name`'s owner segment matches the organization whose secret validated the signature before any handler resolves a `Stack`/`Repository` from `repository.full_name`.

### Proof of Concept
1. Shipit is deployed multi-tenant with `secrets.github[:orgA]` and `secrets.github[:orgB]`, each with distinct `webhook_secret`s [10](#0-9) .
2. Attacker controls org `orgA`'s GitHub App/webhook secret (e.g. as the admin who registered it) and knows `orgB` hosts a victim stack for `orgB/victim-repo`.
3. Attacker crafts a raw JSON body: `{"repository": {"owner": {"login": "orgA"}, "full_name": "orgB/victim-repo"}, "after": "<sha>", "ref": "refs/heads/main"}` and computes `X-Hub-Signature` using `orgA`'s known `webhook_secret`.
4. POSTs to `/github/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` → `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and the signature validates [6](#0-5) .
6. `PushHandler#process` resolves stacks via `repository_name` → `"orgB/victim-repo"` and enqueues `GithubSyncJob` for `orgB`'s stack [8](#0-7) [3](#0-2) , causing Shipit to act on `orgB`'s repository despite the request being authenticated only for `orgA`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
