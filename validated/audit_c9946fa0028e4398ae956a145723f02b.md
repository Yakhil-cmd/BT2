### Title
Webhook organization used for signature selection is not bound to the repository actually acted upon, enabling cross-organization stack sync/pull-request state writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a webhook against using `repository_owner`, derived from the untrusted, not-yet-verified JSON body (`repository.owner.login`, falling back to `organization.login`). Once that per-organization secret validates the raw HMAC, the `create` action re-parses the same body and dispatches it to handlers that instead key all their side effects off `repository.full_name` — a separate field never checked against `repository_owner`. In a multi-organization Shipit deployment (`Shipit.github_organizations`, `github_app_config`), a webhook correctly signed with Organization A's secret can carry a payload whose `repository.full_name` points at a repository owned by Organization B, and the engine will still execute the corresponding handler against Organization B's `Stack`/`Repository`/`PullRequest` records.

### Finding Description
`verify_signature` computes `repository_owner` before any cryptographic check has occurred, purely from the JSON body, and uses it to pick the `GitHubApp` (and therefore the `webhook_secret`) that must validate `X-Hub-Signature`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (`github_app_config`) in a multi-org secrets file (see `test/dummy/config/secrets_double_github_app.yml`), each with its own independent `webhook_secret`: [4](#0-3) 

After the signature check passes, `create` re-parses `request.raw_post` and calls every registered handler for the event with the full JSON body: [5](#0-4) 

Every handler resolves the target repository/stack from `payload.dig('repository', 'full_name')`, e.g. the base `Handler#repository_name`/`#stacks`, `PushHandler#process`, and the pull-request handlers that call `Shipit::Repository.from_github_repo_name(params.repository.full_name)`: [3](#0-2) [6](#0-5) [7](#0-6) 

The binding the code implicitly assumes is:
`organization used to verify signature (repository.owner.login / organization.login) == organization of repository.full_name acted upon by the handler`

Nothing enforces this equality. An attacker who is a legitimate GitHub webhook sender for Organization A (i.e., knows/controls Org A's configured `webhook_secret`, which any repo admin in Org A can view/rotate in the GitHub App settings) can sign a JSON body whose top-level `repository.owner.login` (or `organization.login`) is `"OrgA"` but whose `repository.full_name` is `"OrgB/some-repo"` (or a `pull_request`/`push` payload entirely about an OrgB-owned repository). `verify_signature` selects OrgA's `GitHubApp`, the HMAC validates against OrgA's secret, and the request is accepted. `create` then dispatches the same payload to, e.g., `PushHandler`, which resolves `Repository.from_github_repo_name("OrgB/some-repo")` and calls `stack.sync_github(expected_head_sha: ...)`, or to a pull-request handler which mutates a `PullRequest`/review-stack under Org B — none of which is gated by any check that Org B's own secret produced the signature.

### Impact Explanation
This breaks the trust boundary between organizations in a single Shipit deployment configured with `Shipit.github_organizations` for multiple GitHub orgs: possession of one organization's webhook secret is sufficient to inject fabricated push/status/pull_request/check_suite events that are processed as if they legitimately originated from a different organization's repository, causing unauthorized `GithubSyncJob` enqueues, review-stack creation, and pull-request state writes against that other organization's stacks — a cross-repository/cross-organization write triggered without ever compromising Org B's own credentials.

### Likelihood Explanation
Requires (a) a multi-organization Shipit deployment and (b) knowledge of one configured organization's `webhook_secret` (obtainable by anyone with access to that org's GitHub App settings, which is a lower privilege bar than access to the target org). No `ApiClient` token, `github_access_token`, or session is needed — only the ability to send an HTTP POST to `/webhooks` with a body signed for the org the attacker controls, targeting a `repository.full_name` in a different org.

### Recommendation
After selecting `github_app` by `repository_owner` and verifying the signature, re-derive the organization from `repository.full_name` (or `organization.login` for org-scoped events) and require it to match `repository_owner` exactly before dispatching to handlers; reject the request (422) on mismatch instead of only checking for an unknown organization.

### Proof of Concept
1. Deploy Shipit with `secrets.github` configured for two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who knows only `OrgA`'s `webhook_secret`, build a `push` event JSON body with `repository.owner.login = "OrgA"` (so `verify_signature` selects OrgA's `GitHubApp`) but `repository.full_name = "OrgB/target-repo"` and a crafted `after` SHA.
3. Compute `X-Hub-Signature` as `sha1=` + HMAC-SHA1(OrgA's `webhook_secret`, raw body) and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` passes (OrgA's secret matches), `create` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("OrgB/target-repo")` and calls `sync_github` on OrgB's stacks — despite the request never being signed with OrgB's secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
