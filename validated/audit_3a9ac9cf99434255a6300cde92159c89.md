## Analysis

The external DSTContract report is about code complexity, but the requested analog — "an organization that authenticated versus the repository that is written" — maps to a real, concrete asymmetry in Shipit's webhook processing pipeline.

### Root cause

`WebhooksController#verify_signature` authenticates a webhook delivery only at the **organization** level, resolving which GitHub App/secret to check via `repository_owner` (`repository.owner.login` or `organization.login`): [1](#0-0) 

Every other default handler then re-derives the concrete repository from the payload and scopes its side effects to that repository's stacks, e.g. `PushHandler` and the base `Handler#stacks`/`repository_name`: [2](#0-1) [3](#0-2) 

`StatusHandler`, however, never calls `stacks`/`repository_name` at all — it looks up **any** `Commit` row across the entire installation whose `sha` matches the payload and writes a GitHub-originated status onto it: [4](#0-3) 

`Commit#create_status_from_github!` then feeds that into `add_status`, which can flip `deployable?`/`status` and trigger `schedule_continuous_delivery` for whichever stack happens to own that commit row: [5](#0-4) [6](#0-5) [7](#0-6) 

Crucially, `sha` is indexed only per-`stack_id` (`index_commits_on_stack_id_and_sha`), not globally unique — the schema allows the identical commit `sha` to exist in multiple `Stack`s (e.g. two environments/stacks tracking the same repository, or an organization running several Shipit-connected repos under one GitHub App/webhook secret as documented in `config/secrets.development.shopify.yml`'s multi-org layout).

### The broken binding

`verify_signature` proves "this payload came from an installation authorized for organization O," but `StatusHandler#process` never re-checks that the `sha` it acts on belongs to a stack under organization O. Any tenant/organization whose own webhook secret legitimately validates against `Shipit.github(organization: ...)` can submit a `status` event naming a `sha` that collides with a `Commit` belonging to a *different* stack/repository, and Shipit will apply the forged CI status to that unrelated commit — potentially flipping it to `success` and unblocking `deployable?`/`schedule_continuous_delivery` for that other stack's continuous-deployment pipeline.

This is a genuine equality break: `organization verified by signature ≠ repository/stack whose commit status is written`, unlike every other handler that re-derives and scopes to the payload's own `repository.full_name`.

### Limitation

I could not fully verify from the indexed code whether Shipit deployments in practice host multiple distinct, mutually-untrusting GitHub orgs behind the same webhook endpoint with independently-issued secrets versus a single-tenant install — this affects how directly "unprivileged" the attacker is in a given deployment. The `config/secrets.development.shopify.yml` sample and the per-organization `Shipit.github(organization:)` lookup strongly suggest multi-org hosting is a supported, intended configuration, but confirming exploitability against a specific real deployment would require running the app. [8](#0-7) 

Given the scoping constraints (must not require possession of *another* org's secret or write access to another org's repo), the finding stands as: **the missing repository-scope check in `StatusHandler`, contrasted with every sibling handler's correct scoping**, is the concrete, file-and-method-verifiable analog of the reported "code doesn't match developer intent" bug class.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
