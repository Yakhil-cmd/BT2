### Title
Webhook signature is verified against the organization derived from the payload's `repository.owner.login`, while every event handler acts on state keyed only by `repository.full_name` / raw commit SHA — allowing a low-privilege GitHub org (that has installed the Shipit app) to forge webhooks that mutate a *different*, victim-owned repository's state - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
This mirrors the H-33 pattern (state acted upon does not match the state that was actually validated/synced). In `RedeemProcess`, rewards were updated using stale state because the sync happened *after* the mutating action instead of *before*, so the entity that was mutated and the entity whose state was used for validation diverged. In Shipit, the binding that is supposed to hold is: **the GitHub organization whose webhook secret validated the request signature == the repository/commit that the resulting handler mutates**. That binding is never enforced.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from the untrusted JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository','owner','login')` (with fallback to `organization.login`) and is used only to select which `Shipit.github(organization:)` app/secret verifies the HMAC signature (`lib/shipit.rb`, `github`/`github_app_config`). Once the signature matches *that* organization's configured secret, `create` dispatches the same raw payload to every registered handler without re-checking that `repository.owner.login` matches the repository the handler is about to touch: [3](#0-2) 

Handlers key off `repository.full_name` (independent of `repository.owner.login`) to find the `Repository`/`Stack`, e.g.: [4](#0-3) 

or, worst case, off a bare commit SHA with **no repository scoping at all**: [5](#0-4) 

Because `repository.owner.login` and `repository.full_name`'s owner segment are independent JSON fields, a payload can set:
```json
{ "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" } }
```
The signature check uses `attacker-org`'s legitimately-installed webhook secret (an org that installed the Shipit GitHub App on their own account, an unprivileged action any GitHub user can do for a multi-tenant Shipit deployment configured with per-organization secrets — see `github_app_config`/`TOP_LEVEL_GH_KEYS` in `lib/shipit.rb`), and it passes. The handler, however, operates on `victim-org/victim-repo`'s `Stack`/`Commit` records.

### Impact Explanation
`StatusHandler#process` calls `commit.create_status_from_github!(params)` for any `Commit` row whose `sha` matches the attacker-supplied SHA, with zero repository/stack filter. A commit SHA collision/guess (commits are frequently public, e.g., from a public victim repo) lets the attacker inject a fabricated CI "success" status on a victim commit, satisfying "safe to deploy" checks and driving an **unauthorized deploy** of a stack that the attacker never had legitimate access to — this crosses the Critical bar ("unauthorized deploy") explicitly listed in scope. `PushHandler` and `CheckSuiteHandler` similarly resolve stacks purely via `repository.full_name`, so an attacker who owns any org onboarded to a shared Shipit instance can trigger `stack.sync_github` or `schedule_refresh_check_runs!` on stacks belonging to a completely different, victim-owned GitHub organization/repository — a cross-repository state write performed under someone else's authorization boundary.

### Likelihood Explanation
Requires the attacker to control a GitHub organization/app installation that a shared Shipit deployment already trusts (i.e., has a `webhook_secret`/App installation configured) — a scenario the engine explicitly supports via its multi-organization `secrets.github` schema (`github_app_config`, `github_organizations` in `lib/shipit.rb`). No repository write access, `ApiClient` token, or session is needed; the attacker only needs to be able to deliver an HTTP POST with a valid HMAC for their own org, which is exactly the credential they legitimately hold once their org is onboarded. This is a plausible configuration for any Shipit instance serving more than one GitHub organization.

### Recommendation
Enforce the binding that H-33 teaches: validate against the same entity you are about to mutate, computed from the same trusted source. After signature verification succeeds for organization `O`, require `repository.full_name`'s owner segment to equal `O` before dispatching to handlers, and have `StatusHandler` scope `Commit.where(sha:)` to commits whose stack's repository owner matches the verified organization instead of a bare, global SHA lookup.

### Proof of Concept
1. Attacker's GitHub organization `attacker-org` installs the Shipit GitHub App on a shared/multi-tenant Shipit instance, receiving webhook secret `S_attacker`.
2. Attacker crafts a `status` (or `push`/`check_suite`) webhook payload:
   ```json
   {
     "sha": "<victim-commit-sha>",
     "state": "success",
     "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature` using `S_attacker` over the raw body; `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature matches — request passes.
4. `create` dispatches to `Shipit::Webhooks.for_event('status')` → `StatusHandler#process`, which runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no ownership check, writing a forged "success" status onto the victim's commit and potentially unblocking an unauthorized deploy of `victim-org/victim-repo`.
