### Title
Malicious swap route can steal unrelated caller tokens inside the caller’s authorization tree - (contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept caller-supplied route bytes and pass them to the configured router. The controller authorizes only its own exact input transfer, but the router invokes route-selected pool contracts beneath the caller’s `require_auth`; a malicious pool can therefore add an unrelated `token.transfer(caller, attacker, amount)` to the recorded authorization tree and steal that token if the caller signs it. [1](#0-0) [2](#0-1) 

### Finding Description
For `swap_collateral(caller, account_id, current, amount, new, swap)`, the controller authenticates `caller`, authorizes only `transfer(controller -> router, amount)` for the strategy input, and calls `router.execute_strategy(controller, amount, swap)`. [3](#0-2) [4](#0-3) 

The route payload chooses the pool address and token addresses for each hop, and venue dispatch invokes that pool before measuring the resulting balances. [5](#0-4)  Soroban records a token transfer made by that pool from the original caller as a child invocation under the caller’s authorization; signing the simulated tree authorizes it even though the requested lending operation never named that token or amount. [6](#0-5) 

The malicious pool can still satisfy every protocol check: it receives the router’s exact hop input, returns a positive output, and lets the final account solvency check pass. Those checks bound the routed controller funds, not unrelated transfers from the caller’s wallet. [7](#0-6) [8](#0-7) 

### Impact Explanation
This is theft of user funds beyond the funds supplied to, borrowed through, or withdrawn by the lending operation. An attacker can drain any unrelated token balance that the victim can transfer, while still returning a valid swap output so the strategy completes. [9](#0-8) 

### Likelihood Explanation
Exploitation requires the victim to submit and sign a transaction containing the malicious route and the extra recorded authorization. A normal client that inspects the authorization tree would reject it, but a quoting service, malicious frontend, copied calldata, or wallet that presents insufficient detail can cause the victim to sign it. An attacker does not need a privileged role, leaked key, protocol upgrade, or control of a listed token. [6](#0-5) 

### Recommendation
Do not allow route bytes to name arbitrary executable pool contracts for privileged user calls. Store a governance-managed venue/pool registry and reject route addresses outside it, or otherwise isolate user authorization from route-selected code. Independently, wallets and official clients must simulate the exact route and reject any authorization child other than the single expected input transfer. [1](#0-0) [10](#0-9) 

### Proof of Concept
1. Victim owns a healthy account with listed USDC collateral and also holds `WALLET_TOKEN`, which need not be a protocol asset.
2. Attacker deploys a Soroswap-compatible `pool` contract configured with `(victim, WALLET_TOKEN, attacker, victim_balance)`.
3. Attacker supplies a `swap_collateral` route whose `Swap(Soroswap)` hop names that pool, listed USDC as input, and listed ETH as output.
4. The victim calls:
   `swap_collateral(victim, victim_account, usdc_hub_asset, amount, eth_hub_asset, malicious_route)`.
5. The router transfers the hop input to the malicious pool and invokes its `swap`; during that call, the pool executes `WALLET_TOKEN.transfer(victim, attacker, victim_balance)` and returns enough ETH for the measured-output check. [11](#0-10) 
6. Simulation records the unrelated wallet transfer as a child of the victim’s `swap_collateral` authorization. If the victim signs that recorded tree, the unrelated token is transferred and the lending swap still completes. [6](#0-5)

```rust
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
```

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
