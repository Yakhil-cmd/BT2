### Title
`Commit.where(sha: params.sha)` in `StatusHandler#process` is not scoped to the webhook's repository, allowing one webhook to mutate commits/statuses belonging to any stack sharing the same SHA - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` queries `Commit` globally by `sha` and calls `create_status_from_github!` on every match, instead of scoping the lookup to the stacks that belong to the webhook's authenticated repository. Since git SHAs are content-addressed and not globally unique across unrelated repositories (e.g. the empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any commit with byte-identical author/committer/message/timestamps/tree), a single signed webhook for repository A can create/update `Status` rows on `Commit` records that belong to repository B's stack.

### Finding Description
The broken binding: `params.sha` (verified only to belong to the repository named in `payload['repository']['full_name']`) should equal `commit.sha AND commit.stack ∈ Repository.from_github_repo_name(payload_repo).stacks`, but the code only checks `commit.sha == params.sha` with no stack/repository constraint: [1](#0-0) 

Every other handler in this file scopes to the base class's `stacks` helper, which is derived from the verified payload's `repository.full_name`, e.g. `PushHandler#process` uses `stacks.not_archived.where(branch:)`: [2](#0-1) [3](#0-2) 

`StatusHandler` skips this scoping entirely and hits the `Commit` table directly, unscoped by stack/repository.

`WebhooksController#verify_signature` only verifies that the payload signature matches the GitHub App key for the *organization* named by `repository_owner` — it never validates that the `sha` in the payload actually belongs to the repository named in the payload, nor does it constrain which `Commit` rows the handler may touch: [4](#0-3) 

Attack flow: attacker owns a GitHub repository/organization onboarded into Shipit (so they can generate a validly-signed `status` webhook for their own repo). They create a commit whose SHA is guaranteed or likely to also exist in a victim stack's `Commit` table — the canonical example is the empty-tree/empty-commit SHA, or any commit whose full content (tree, parents, author, committer, message, timestamps) is byte-identical to a commit already synced into a victim's monorepo/vendored history. They send a signed `status` event naming only their own repository with that `sha`. `Commit.where(sha: params.sha)` returns commit rows from *all* stacks with that SHA, and `commit.create_status_from_github!(params)` (which calls `statuses.replicate_from_github!(stack_id, github_status)`) writes a `Status` row for every matching commit, including ones belonging to the victim's stack, potentially flipping `Commit#state`, triggering `deployable?` transitions, and — since `continuous_deployment` stacks trigger deploys based on commit status per `commits_test.rb`'s CD-related tests — this can indirectly trigger a deploy on a repository the attacker never authenticated against.

None of the existing guards prevent this: `verify_signature` only authenticates the sender for their own org/repo, not the `sha`'s ownership; `drop_unhandled_event` only checks event type; `ExplicitParameters` schema only validates types/presence of `sha`/`state`, not scope; and the `stacks` helper that would provide correct scoping is defined but unused by `StatusHandler`.

### Impact Explanation
A single validly-signed webhook from an attacker's own repository writes `Status` records (and can flip `Commit#state`/`deployable?`) for commits belonging to an unrelated victim stack, without any authentication tying the SHA to that victim repository. This directly matches "a payload for one repository mutating another's stack, commit, task or team," and given continuous-deployment stacks derive deploy triggers from commit status, this can produce an unauthorized deploy — Critical severity. The blast radius scales with however many stacks/repos happen to contain a `Commit` row with the colliding SHA (multi-tenant monorepo/vendored-history setups are the realistic trigger, and empty-tree/empty-commit collisions are trivially constructable by an attacker without any special access).

### Likelihood Explanation
Preconditions: attacker must control (or be able to push to) a GitHub repository already onboarded as a Shipit stack (any unprivileged GitHub user with a repo can do this, e.g. via a fork with a webhook configured, or their own repo added to Shipit by a maintainer), and a victim `Commit` row must exist with an identical `sha` (achievable deterministically via well-known empty-tree/empty-commit SHAs, or via shared vendored/monorepo history — no secrets required). Attacker cost is a single signed `status` webhook, which they can legitimately produce for their own repository. This is fully repeatable against any stack containing a colliding SHA.

### Recommendation
Scope the lookup to the verified payload's repository, mirroring the pattern used by `PushHandler`/`Handler#stacks`:
```ruby
def process
  stacks.commits.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
(`Stack has_many :commits`, so `stacks.commits` scopes the query correctly.)

### Proof of Concept
Minitest plan (e.g. in `test/models/shipit/webhooks/handlers/status_handler_test.rb`, currently absent for this specific scoping case — but demonstrable via `test/controllers/webhooks_controller_test.rb`):

```ruby
test ":status webhook must not mutate commits belonging to a different stack" do
  sha = "4b825dc642cb6eb9a060e54bf8d69288fbee4904" # git empty tree sha

  stack_a = shipit_stacks(:shipit) # repository named in the webhook payload
  stack_b = Shipit::Stack.create!(repository: Shipit::Repository.create!(owner: "other", name: "repo"), environment: "production")

  commit_a = stack_a.commits.create!(sha:, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  commit_b = stack_b.commits.create!(sha:, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  request.headers['X-Github-Event'] = 'status'
  body = { 'sha' => sha, 'state' => 'success' }.merge(repository_params).to_json # repository_params names stack_a's repo only

  assert_difference -> { commit_a.statuses.count }, 1 do
    assert_no_difference -> { commit_b.statuses.count } do
      post :create, body:, as: :json
    end
  end
end
```

With the current code, `commit_b.statuses.count` will incorrectly change (proving the vulnerability); after applying the fix (`stacks.commits.where(sha:)`), only `commit_a`'s statuses change.
