### Title
Webhook signature verified against the payload's `repository.owner.login`, but every event handler acts on the unauthenticated `repository.full_name` — cross-organization forgery in multi-app deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the HMAC `webhook_secret`) used to authenticate an inbound webhook based on `repository_owner`, a value read straight out of the untrusted JSON body. Every webhook handler, however, resolves the actual `Repository`/`Stack` to mutate using a *different*, also attacker-supplied field: `repository.full_name`. Nothing ties these two fields together, so in a multi-organization Shipit deployment, a party who legitimately administers **one** configured GitHub App/org can forge a signature that is valid for their own org while pointing the payload at a repository belonging to a **different** org served by the same Shipit instance.

### Finding Description
`verify_signature` picks the app config purely from the payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a completely independent secret per organization key when Shipit is configured for multiple GitHub Apps (a documented, supported configuration): [3](#0-2) 

The signature is only checked against `HMAC(webhook_secret_for(repository_owner), raw_body)`: [4](#0-3) 

Once the signature passes, `create` dispatches to handlers using the raw parsed JSON, and every handler resolves the target repository from `repository.full_name` — a field never checked for consistency with `repository_owner`: [5](#0-4) 

Concretely, `StatusHandler` writes CI/deploy-blocking commit statuses directly from attacker-supplied fields onto any commit whose SHA happens to match, with no ownership check at all: [6](#0-5) 

`PushHandler` similarly triggers `stack.sync_github` for any stack found via `repository.full_name`, independent of `repository_owner`: [7](#0-6) 

**The broken equality**: `organization authenticated by verify_signature (repository_owner)` should equal `organization/repository that the dispatched handler mutates (repository.full_name)`. The code enforces neither an equality check nor a canonicalization step between these two independently-controlled JSON fields.

### Impact Explanation
In a multi-GitHub-App Shipit deployment (explicitly documented as "Using Multiple Github Applications"), an attacker who legitimately controls one configured org (and therefore knows/can compute a valid signature with that org's `webhook_secret`) can forge webhook deliveries that are processed as if they came from GitHub for a **different** organization's repository hosted on the same Shipit instance. This allows:
- Forging arbitrary commit CI statuses (`StatusHandler`) on another org's commits, which Shipit uses to gate whether a commit is deployable/mergeable — an unauthorized bypass of deploy/merge safety gates.
- Forcing sync/refresh jobs (`PushHandler`, `CheckSuiteHandler`) against another org's stacks.
- Manipulating another org's review-stack lifecycle via the `pull_request` handlers, all keyed only off `repository.full_name`.

This is a cross-organization/cross-repository write achieved without any credential belonging to the victim organization, satisfying the Critical "cross-repository writes" / "unauthorized deploy" bar.

### Likelihood Explanation
This requires a multi-GitHub-App Shipit configuration (a supported, documented setup) and requires the attacker to be a legitimate administrator of at least one of the configured orgs — not of the victim org, and not a Shipit user/session/API token holder. Given that this is exactly the trust boundary the webhook signature is supposed to enforce (organization isolation), and the check never re-validates the acted-upon repository against the authenticated organization, exploitation is straightforward once the multi-app precondition holds.

### Recommendation
After signature verification succeeds, cross-check that the resolved `Repository` (via `repository.full_name`) actually belongs to the same GitHub organization/app used to verify the signature (`repository_owner`), rejecting the webhook (422) if they diverge. Do this centrally in `WebhooksController#verify_signature` or in the shared `Handler` base class before any handler is allowed to run.

### Proof of Concept
1. Shipit is configured with two GitHub Apps: `orgA` (attacker-administered) and `orgB` (victim), per `docs/setup.md`'s multi-org example.
2. Attacker computes `sig = HMAC-SHA1(webhook_secret_orgA, body)` for a JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "orgB/victim-repo", "owner": { "login": "orgA" } }
}
```
3. POST this to `/github/webhooks` with `X-Github-Event: status` and `X-Hub-Signature: sha1=<sig>`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` (from `repository.owner.login`), validates the signature successfully against `webhook_secret_orgA`.
5. `StatusHandler.process` runs `Commit.where(sha: params.sha)` — matching against `orgB/victim-repo`'s real commit — and calls `create_status_from_github!`, forging a passing CI status the attacker was never authorized to set on `orgB`'s repository.

**Uncertainty**: I could not fully trace `Commit#create_status_from_github!` or confirm exactly how a forged status affects deploy gating in every configuration (e.g., `ignore_ci`), due to index/context limits; a Devin session with full repo access would be needed to verify the exact downstream deploy-gating consequences and to confirm no additional owner check exists elsewhere in the dispatch path (e.g., in `Shipit::Webhooks.for_event`).

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
