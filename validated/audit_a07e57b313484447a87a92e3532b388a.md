### Title
Webhook signature verification binds only the claimed organization, not the repository/commit acted upon, allowing cross-tenant status/event forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to validate a webhook against using the organization name embedded in the very same untrusted payload it is trying to authenticate, while the event handlers that subsequently act on the payload key off a *different*, independently-controlled field (`repository.full_name`, or in the case of commit statuses, a bare `sha` with no repository scoping at all). In a multi-tenant Shipit deployment (the "Using Multiple Github Applications" configuration), this breaks the intended binding: `organization authenticated == repository/commit written`.

### Finding Description
`WebhooksController#verify_signature` picks the app/secret to validate against solely from the payload's own `repository.owner.login` / `organization.login` field: [1](#0-0) [2](#0-1) 

In multi-org mode, each organization has its own independent `webhook_secret` in `secrets.github`: [3](#0-2) [4](#0-3) 

The signature is verified with HMAC-SHA1 using that org's secret over the raw body: [5](#0-4) 

Once `verify_signature` succeeds (because the attacker correctly supplied the secret for *their own* onboarded organization), `WebhooksController#create` dispatches the entire raw payload to the registered handlers with no further check that the payload's other repository-identifying fields actually belong to the organization whose secret was used: [6](#0-5) 

Handlers resolve the target repository/stack from a separate field, `repository.full_name`, which is not covered by the org-selection logic and can point to any repository tracked by the shared Shipit instance: [7](#0-6) [8](#0-7) 

Worse, the `status` event handler doesn't even scope by repository at all — it looks up commits purely by SHA across the entire instance: [9](#0-8) 

So the value that gates signature verification (`repository.owner.login`, mapped to an organization's `webhook_secret`) is never cryptographically or logically bound to the value the handlers use to select which repository/commit is mutated (`repository.full_name` or bare `sha`). Any tenant organization admin who legitimately knows their own org's `webhook_secret` (a value they configure themselves per `docs/setup.md`'s "Using Multiple Github Applications" section) can produce a validly-signed webhook body for their own org while filling in a different org's `repository.full_name`/`sha` in the JSON.

### Impact Explanation
This crosses a genuine trust boundary in a multi-organization Shipit deployment: an unprivileged-with-respect-to-victim, but legitimate, tenant of org A can forge webhook events that are accepted as authentic for org B's repositories/commits that they have no access to. Concretely:
- Forging a `status` event lets the attacker inject arbitrary fake CI/commit statuses (`Commit#create_status_from_github!`) for any commit SHA already known to the instance (e.g. via public GitHub activity of the victim repo), which can flip deploy/merge-queue readiness checks to "green," enabling an unauthorized deploy or merge of unreviewed/malicious code in the victim's stack.
- Forging a `push` event lets the attacker trigger `stack.sync_github` for a victim's stack.
This matches the Critical-tier impact category "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Exploitation requires the attacker to be a legitimate participant in a multi-org Shipit installation (i.e., they know their own organization's configured `webhook_secret`, which they set up themselves per the documented multi-org configuration) and knowledge of a target commit SHA / repository full name tracked by another tenant on the same instance — both readily obtainable from public GitHub activity. No access to the victim org's secret, `ApiClient` token, or GitHub credentials is required. This is realistic for any shared/hosted multi-tenant Shipit deployment, which the project explicitly documents and supports (`docs/setup.md`, "Using Multiple Github Applications").

### Recommendation
After signature verification succeeds against the secret for `repository_owner`, re-validate that every repository-identifying field consumed by the handlers (`repository.full_name`, and any `sha`/status lookups) actually belongs to that same verified organization before acting on it — e.g., assert `params.dig('repository','full_name').split('/').first == repository_owner`, and scope the `status` handler's `Commit` lookup by repository, not by bare SHA.

### Proof of Concept
1. Deploy Shipit in multi-org mode with `OrgA` and `OrgB` each configured with distinct `webhook_secret`s (per `test/dummy/config/secrets_double_github_app.yml`), both tracking stacks on the same Shipit instance.
2. As the legitimate owner of `OrgA`'s GitHub App/webhook (attacker), compute `sha1=HMAC(OrgA_webhook_secret, body)` for a crafted JSON body:
```json
{
  "sha": "<victim-commit-sha-on-OrgB-repo>",
  "state": "success",
  "context": "ci/tests",
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/whatever"}
}
```
3. POST to `/webhooks` with `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s app, and the signature validates successfully (attacker knows this secret).
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) runs `Commit.where(sha: params.sha)` — matching the OrgB victim commit regardless of the `repository` field used in verification — and creates a forged successful status on it, which can be leveraged to satisfy deploy/merge gating for OrgB's stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
