## Title
Cross-Organization Webhook Forgery via Unbound `repository.full_name` — Signed Org Never Matched to Written Repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook against using an **attacker-controlled** field inside the very payload being verified (`repository.owner.login`, falling back to `organization.login`), and then hands the *entire* parsed payload to the event handlers. [1](#0-0)  Those handlers determine which `Repository`/`Stack` to act on using a *different* field, `repository.full_name`, which is never cross-checked against the organization that produced a valid signature. [2](#0-1)  In a multi-organization Shipit deployment (`config/secrets.yml` keyed by org, each with its own `webhook_secret`), any organization owner who legitimately knows their own GitHub App's webhook secret can forge a payload that authenticates as their own org while acting on a repository belonging to a completely different, unrelated organization.

### Finding Description
The verification flow is:
1. `repository_owner` is read directly out of the untrusted, not-yet-verified request body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [3](#0-2) 
2. That value picks the `GithubApp` instance/secret used to verify the HMAC signature: `Shipit.github(organization: repository_owner)` → `verify_webhook_signature`. [4](#0-3) [5](#0-4) 
3. On success, the raw JSON is dispatched unmodified to the matching event handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [6](#0-5) 
4. Handlers resolve the target repository using a *separate* field, `payload.dig('repository', 'full_name')`, via `Repository.from_github_repo_name`, e.g. in `PushHandler`/`Handler#stacks`. [2](#0-1) [7](#0-6) 
5. `Repository.from_github_repo_name` performs a plain `owner/name` lookup with no relation whatsoever to which organization's secret validated the request: `find_by(owner: repo_owner, name: repo_name)`. [8](#0-7) 

Because the HMAC only covers the raw request body as a whole (not a specific sub-field), and the field used to *choose the verification key* (`repository.owner.login` / `organization.login`) is not the same field used to *decide what gets modified* (`repository.full_name`), a party who legitimately possesses one org's `webhook_secret` can freely set `repository.full_name` to any other tracked repository and sign the whole (self-consistent, valid-for-their-org) payload with their own secret. The signature will pass — it is being checked against the correct secret for the org named in the payload — but the code that actually performs the mutation trusts a different, unguarded field from that same attacker-crafted body.

This is the binding break: **organization that authenticated (`repository.owner.login` used to select `webhook_secret`) ≠ repository that is written (`repository.full_name` used to find `Stack`/`Repository`)**.

### Impact Explanation
`PushHandler.process` calls `stack.sync_github(expected_head_sha: params.after)` for every not-archived stack on the branch matched, which can trigger repository sync and downstream deploy/merge automation for a *victim* repository the attacker never controls or was never granted access to. [9](#0-8)  Other handlers keyed the same way (status, check_suite, pull_request family) similarly resolve their target `Repository`/`Stack` from the unguarded `repository.full_name`, so an attacker in control of one org's webhook secret can inject fabricated commit statuses, check-suite results, or pull-request state transitions (archive/unarchive review stacks, capture labels) against a different organization's stacks — i.e., cross-repository writes into deployment state driven by GitHub-originated automation, satisfying the "cross-repository writes" / "unauthorized deploy" criteria.

### Likelihood Explanation
Exploitability requires only that the attacker be the legitimate administrator of any one organization configured in the same multi-tenant Shipit instance (they inherently know their own App's `webhook_secret`, since they configure it when creating their GitHub App per `docs/setup.md`). [10](#0-9)  No access to the victim org, no GitHub App installation on the victim repository, and no Shipit session/API token is needed — only a raw HTTP POST to the shared `/webhooks` endpoint with a self-crafted, self-signed JSON body.

### Recommendation
After signature verification succeeds, derive the organization actually authorized to act from the *same* field that was cryptographically bound to the verified secret (i.e., re-derive `repository.owner.login`/`organization.login` post-verification) and require that every handler's `repository.full_name` owner component match that verified organization before any lookup/mutation is performed. Reject the webhook (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (as in `config/secrets.development.shopify.yml`), both tracking repositories in Shipit. [11](#0-10) 
2. As the administrator of `attacker-org`'s GitHub App, craft a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Compute `X-Hub-Signature` with `attacker-org`'s known `webhook_secret` over the raw body.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `attacker-org`, verifies successfully against `attacker-org`'s secret. [4](#0-3) 
5. `PushHandler` resolves the target via `repository.full_name = "victim-org/victim-repo"` and calls `stack.sync_github` on `victim-org`'s stacks — despite the request never being authenticated by `victim-org`'s secret. [9](#0-8)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",

      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
