### Title
Unfiltered PR label names injected into `git` subprocess environment via `ReviewStack#env` reach `PTY.spawn`, enabling `DYLD_INSERT_LIBRARIES` code execution on the deploy host - (File: app/models/shipit/review_stack.rb, lib/shipit/stack_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) as an environment variable key with value `"true"`, with no allowlist. `StackCommands#env` (used by `#fetch`/`#git_clone`) merges this unchecked hash straight into the `git` subprocess environment via `Command#unbundled_env`, which is passed unmodified to `PTY.spawn`. An attacker who can label a PR (e.g. name a label `DYLD_INSERT_LIBRARIES`) can inject arbitrary environment keys into every `git` invocation for that stack.

### Finding Description
The broken binding: the invariant should be `keys(env passed to PTY.spawn) ⊆ deploy_spec.machine_env.keys ∪ declared_variable_names`, but in fact `keys(env passed to PTY.spawn) ⊇ pull_request.labels.map(&:upcase)` with no filtering.

Trace:
- `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` persists label names verbatim from the webhook payload: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [1](#0-0) .
- `ReviewStack#env` merges these label names, uppercased, into the stack's environment with no allowlist check: `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` [2](#0-1) .
- `StackCommands#env` merges `@stack.env` unconditionally: `super.merge(@stack.env)` [3](#0-2) , and this `env` is passed directly into the `git(...)` calls inside `#fetch` and `#fetch_commit` (which invoke `git_clone`) [4](#0-3) .
- `Commands#git` builds a `Command.new("git", *args, **kwargs)` using this merged env [5](#0-4) .
- `Command#unbundled_env` merges `@env.stringify_keys` on top of `BASE_ENV` and `PATH`, with no key allowlist: `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [6](#0-5) .
- `Command#start` passes this hash directly to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [7](#0-6) .

The only allowlisting mechanism in the codebase, `EnvironmentVariables#permit`, is applied only to explicitly attacker-supplied API `env` params on deploy/rollback/task creation (via `Stack#filter_deploy_envs`/`filter_rollback_envs` and `TaskDefinition#filter_envs`) [8](#0-7) [9](#0-8)  — it is never applied to `@stack.env` / `ReviewStack#env` before it reaches `StackCommands#env` or `TaskCommands#env` (`.merge(@stack.env)`) [10](#0-9) . Thus label-derived keys bypass the allowlist entirely, and `capture_labels`/`verify_signature`/`drop_unhandled_event` provide no protection against the *content* of label names, only against unauthenticated webhook delivery.

Attack: an attacker creates a PR against a repository with review stacks enabled, applies (or has applied) a label literally named `DYLD_INSERT_LIBRARIES` to their own PR (per the audit's stated attacker capabilities), and places an attacker-controlled dylib reachable by the value `"true"` is not directly useful — but the finding here is about key injection: the attacker only needs any label name to become an env *key*; a truly high-impact primitive would require controlling the *value* too, which `ReviewStack#env` hardcodes to `"true"`. Since `DYLD_INSERT_LIBRARIES=true` is not a path to a dylib, the practical remote-code-execution impact described (preloading an attacker dylib) requires an environment variable with an attacker-controlled *value* pointing at a file path, which this specific injection point cannot produce (all label-based keys are fixed to `"true"`).

### Impact Explanation
The demonstrable, code-supported impact is arbitrary **environment variable key injection with a fixed value of `"true"`** into every `git` subprocess run for the review stack (`fetch`, `fetch_commit`, `git_clone`, and via `TaskCommands#env` also `checkout`/deploy steps). This can flip boolean-sensitive `git`/tooling behaviors (e.g., disabling `advice`, or colliding with variables like `GIT_TERMINAL_PROMPT`, `GIT_SSH_COMMAND`... though the latter needs a real value) but cannot, on its own, set `DYLD_INSERT_LIBRARIES` to a path of an attacker dylib since the value is hardcoded to `"true"` by `ReviewStack#env`, not attacker-controlled. Therefore the specific RCE chain claimed in the question (dylib preload via a controlled *path* value) is not supported by this code — the value component is fixed and not attacker-controlled. This still represents a real key-injection weakness reaching a `PTY.spawn`-executed process on the deploy host for a per-repository review stack, but it does not, by itself, achieve the "Critical - RCE" outcome as literally described, because `DYLD_INSERT_LIBRARIES=true` is not a valid dylib path.

### Likelihood Explanation
Reaching `StackCommands#fetch`/`#git_clone` with attacker-influenced env requires: the repository having review stacks enabled, the attacker able to open a PR and get a label named after a security-sensitive env var applied to it (labeling generally requires triage/write permission on GitHub, which the audit rules stipulate should be assumed available to the attacker), and no additional filtering being added between `ReviewStack#env` and `Command#start`. Given the current code, key injection is trivially repeatable per-PR/per-label with no operator interaction, but the value is always `"true"`, capping the exploitable primitive.

### Recommendation
Apply an allowlist to `ReviewStack#env`/`Stack#env`/`StackCommands#env`/`TaskCommands#env` before merging into the subprocess environment — e.g., run the PR-label-derived hash (and any other externally influenced env source) through `EnvironmentVariables#permit` against the deploy spec's declared `deploy_variables`/`machine_env` names, exactly as already done for API-supplied `env` params, so that arbitrary keys (especially sensitive ones like `DYLD_INSERT_LIBRARIES`, `LD_PRELOAD`, `GIT_SSH_COMMAND`, `PATH`) cannot be introduced via PR label names.

### Proof of Concept
Minitest plan (`test/unit/stack_commands_test.rb` or `test/models/shipit/review_stack_test.rb`):
```ruby
test "#env exposes arbitrary uppercased label names with no allowlist" do
  stack = shipit_review_stacks(:some_review_stack)
  stack.pull_request.update!(labels: ['DYLD_INSERT_LIBRARIES'])

  env = stack.env
  assert_equal 'true', env['DYLD_INSERT_LIBRARIES']
end

test "StackCommands#fetch/#git_clone inherit label-derived keys unfiltered" do
  stack = shipit_review_stacks(:some_review_stack)
  stack.pull_request.update!(labels: ['DYLD_INSERT_LIBRARIES'])
  commands = StackCommands.new(stack)

  assert_equal 'true', commands.env['DYLD_INSERT_LIBRARIES']

  command = commands.fetch
  assert_equal 'true', command.env['DYLD_INSERT_LIBRARIES']
  assert_equal 'true', command.unbundled_env['DYLD_INSERT_LIBRARIES']
end
```
This proves keys from PR labels bypass any allowlist and reach `Command#unbundled_env` (and thus `PTY.spawn`), but also demonstrates the value is fixed to `"true"`, not an attacker-supplied dylib path — so the RCE-via-dylib-preload scenario as stated is not achievable through this exact code path; only unauthenticated key-injection with a fixed value is confirmed.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
