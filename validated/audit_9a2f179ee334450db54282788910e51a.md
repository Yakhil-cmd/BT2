### Title
Stake-Denominator Manipulation During Partitioned Reward Recalculation Allows Reward Misattribution - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
The Wheel bug is a class of "mutate your weighted share after the probability/allocation was supposed to be locked in, but before final settlement." The closest reachable analog in agave is in the SIMD-0123 block-reward / partitioned epoch-reward recalculation path: the **denominator** (`total_active_stake`, taken from `RewardEpochDelegatedStakes`) is deliberately pinned to the value computed at the epoch boundary, but the **numerator** (an individual delegation's `stake`) is recomputed from the *live* `StakesCache` every time `recalculate_stake_rewards` runs during the multi-block partitioned distribution window.

### Finding Description
`calculate_block_reward` computes each stake's share of a vote account's `pending_delegator_rewards` as:

```
stake / total_active_stake * pending_delegator_rewards
``` [1](#0-0) 

`total_active_stake` comes from the pinned `RewardEpochDelegatedStakes` snapshot taken once at the epoch boundary [2](#0-1) , computed via `calculate_activated_stake` in `compute_new_epoch_caches_and_rewards` [3](#0-2) .

However, `stake` (the numerator) for each stake account is *not* pinned the same way when rewards are recalculated after the epoch boundary. `recalculate_stake_rewards` re-derives `stake_delegations` from the *current, live* `StakesCache` at the moment recalculation runs:

```rust
let stakes = self.stakes_cache.stakes();
let EpochRewardCalculateParamInfo { stake_history, stake_delegations, cached_vote_accounts } =
    self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
``` [4](#0-3) 

`get_epoch_params_for_recalculation` explicitly pulls `stake_history` and `stake_delegations` straight from the live `stakes` cache with no reference back to the state at the original epoch-boundary calculation: [5](#0-4) 

Recalculation is triggered on `recalculate_partitioned_rewards_if_active`, which runs whenever `EpochRewards` sysvar is still `active` — i.e., on every subsequent bank across the multi-block partitioned distribution window (rewards are split across `num_partitions`, paid out block by block) [6](#0-5) .

Because the `StakeInstruction::Merge` instruction is a normal, unprivileged, permissionless instruction (any staker can merge one already-fully-active stake account into another under the same authority/lockup/voter), and merging two fully-activated stakes to the same vote account is instant (no warmup delay) — a staker with an *unpaid* stake reward for a given vote account can, within the distribution window (before their partition is paid), merge in additional already-active stake delegated to that same voter. On the next block's recalculation, their numerator (`delegation_effective_stake`) jumps up while the fixed denominator (`total_active_stake`) stays the same, letting them claim a disproportionately large slice of that voter's fixed `pending_delegator_rewards` pool relative to other, still-unpaid delegators of the same vote account — exactly the "grow your weighted share during the open/cooldown window before the outcome/allocation is finalized" pattern from the Wheel report.

There is an existing regression test (`test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator`) confirming the **denominator** is correctly pinned across recalculation [7](#0-6) , but this test does not exercise or protect the **numerator** side — i.e. it doesn't cover a staker increasing their own delegation via `Merge` between partition payouts.

### Impact Explanation
If exploitable, this allows a staker to capture inflation/block rewards attributable to *other* delegators of the same validator, by shifting weight into an unpaid stake account mid-distribution. This is a misattribution of rewards between delegators of the same vote account (not new lamports minted, but lamports taken from the still-fixed pool that should have gone proportionally to other stakers), matching the "misattributed or duplicated rewards" acceptance criterion.

### Likelihood Explanation
Requires: (1) SIMD-0123 / Alpenglow block-reward path enabled (`block_revenue_sharing` feature), (2) attacker controls at least two stake accounts delegated to the same vote account, one already fully activated and unpaid in the current distribution, (3) the distribution window (`num_partitions`) spans enough blocks for the attacker's `Merge` transaction to land and a subsequent recalculation to occur before that partition's payout. This is plausible on mainnet given `num_partitions` is typically sized so that partitioned reward distribution spans multiple blocks. Likelihood is moderate — feature-gated and requires specific timing, but the underlying accounting asymmetry (pinned denominator vs. live numerator) is confirmed in code.

### Recommendation
Pin the numerator's `stake_delegations`/`stake_history` snapshot used during recalculation to the same epoch-boundary point used for `RewardEpochDelegatedStakes`, rather than re-reading the live `StakesCache`, or explicitly cap/reject stake merges into accounts with an outstanding unpaid partitioned reward for the current distribution epoch until distribution completes.

### Proof of Concept
Conceptual (not run):
1. Stake account A delegated to vote V, fully active, has an unpaid `PartitionedStakeReward` for `rewarded_epoch` still pending in a later partition.
2. Stake account B, also fully active and delegated to V, held by same authority.
3. Epoch boundary occurs; `RewardEpochDelegatedStakes` for V is pinned; A's reward share is computed and stored as pending (unpaid) in `all_stake_rewards`.
4. Before A's partition pays out, submit `StakeInstruction::Merge(B into A)` — permissionless, same-authority operation, allowed since both are fully active [8](#0-7) .
5. On the next bank/slot, `recalculate_partitioned_rewards_if_active` → `recalculate_stake_rewards` re-reads A's now-larger `delegation.stake` from the live `StakesCache`, while `total_active_stake` (denominator) remains the value pinned at the epoch boundary [4](#0-3) .
6. A's recalculated `block_reward`/inflation share increases beyond its epoch-boundary-computed proportion, at other unpaid delegators' expense.

Note: I could not fully trace the exact `num_partitions` sizing logic or confirm end-to-end that no additional epoch-boundary guard (e.g., re-snapshotting individual stake amounts, not just the total) exists elsewhere in the payout path; this would need to be validated by writing an integration test analogous to `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` but injecting a `Merge` between partial distributions instead of merely adding stake before the epoch boundary.

    /// Retrieves stake history and delegations for stake reward recalculation
    /// after snapshot restore.
    fn get_epoch_params_for_recalculation<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        stakes: &'a Stakes<StakeAccount<Delegation>>,
    ) -> EpochRewardCalculateParamInfo<'a> {
        // Use `stakes` for stake-related info
        let stake_history = stakes.history().clone();
        let stake_delegations = stakes.stake_delegations_vec();

        // Use the VAT-filtered vote-account snapshot from epoch_stakes.
        // Recalculation should match the vote-account admission policy used for
        // distribution.
        let leader_schedule_epoch = self.epoch_schedule().get_leader_schedule_epoch(self.slot());
        let distribution_epoch_vote_accounts = self
            .epoch_stakes(leader_schedule_epoch)
            .expect("calculation should always run after Bank::update_epoch_stakes()")
            .stakes()
            .vote_accounts();
        let cached_vote_accounts =
            self.get_cached_vote_accounts(rewarded_epoch, distribution_epoch_vote_accounts);

        EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        }
    }

    /// If rewards are still active, recalculates partitioned stake rewards and
    /// updates Bank::epoch_reward_status. This method assumes that reward
    /// commissions have already been calculated and delivered, and *only*
    /// recalculates stake rewards
    pub(in crate::bank) fn recalculate_partitioned_rewards_if_active<F, TP>(
        &mut self,
        thread_pool_builder: F,
    ) where
        F: FnOnce() -> TP,
        TP: std::borrow::Borrow<ThreadPool>,
    {
        let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
        if epoch_rewards_sysvar.active {
            let thread_pool = thread_pool_builder();
            let (stake_rewards, partition_indices) =
                self.recalculate_stake_rewards(&epoch_rewards_sysvar, thread_pool.borrow());
            self.set_epoch_reward_status_distribution(
                epoch_rewards_sysvar.distribution_starting_block_height,
                stake_rewards,
                partition_indices,
            );
        }
    }
