## Analysis

I found a concrete analog. The bug-class hint is "a field/scope that is nominally enforced elsewhere is bypassed in one code path, allowing an authorization boundary to be crossed" — exactly the pattern called out in the rules as "a stack a token authorises versus a stack it touches."

### Title
Stack-scoped API token can read any stack's CCMenu status, bypassing its stack authorization scope - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` records can be created scoped to a single stack (`stack_id`), and `Api::BaseController#stacks`/`#stack` enforce that scope for every other API endpoint. `Api::Ccmenu Controller`, however, overrides `stack` with its own implementation that ignores the client's `stack_id` scope entirely, letting any authenticated `read:stack` token read the CI/deploy status of every stack in the installation.

### Finding Description
`ApiClient` supports an optional `stack_id` used to scope tokens to a single stack: [1](#0-0) . `Api::BaseController` enforces this scope centrally: [2](#0-1) 
Every controller that relies on `stack`/`stacks` from `BaseController` (e.g. `Api::StacksController`, `Api::DeploysController`, `Api::TasksController`) is therefore limited to the stack(s) the token is bound to.

`Api::CCMenuController`, however, redefines `stack` to bypass the scoping helper completely: [3](#0-2) 
It only runs `require_permission :read, :stack`, which just checks that the token has the `read:stack` *permission string* — it does not check whether the requested `stack_id` matches the token's bound `stack_id`: [4](#0-3) 

The equality the engine is supposed to maintain is:
`stack the token authorizes (client.stack_id) == stack the token is allowed to act on (params[:stack_id] resolved via Api::BaseController#stack)`

`Api::CCMenuController#stack` breaks this equality by resolving `params[:stack_id]` directly against the global `Stack` relation (`Stack.from_param!`), independent of `current_api_client.stack_id`.

### Impact Explanation
Any valid, low-privilege API token that is scoped to a single stack (created e.g. for the CCMenu integration, see `CCMenuUrlController`) and has the `read:stack` permission can be replayed against `api/:stack_id/ccmenu.xml` for an arbitrary other stack id/slug, disclosing that stack's deploy/build status, last build label, last build time, and web URL — data the token was never authorized to see. This is a cross-tenant/cross-stack read of stack state (deploy status/output metadata) that maps to the "High – unauthorized read of stack state / deploy output" category: a token authorized for stack A is able to touch stack B.

### Likelihood Explanation
The precondition is only possession of any valid API token with `read:stack` permission (the credential can be scoped narrowly to a single stack, as intended by the product's own CCMenu-token workflow, `CCMenuUrlController`). No repository write access, GitHub App key, or privileged account is needed — only a routine, narrowly-scoped API credential that the application itself is designed to hand out for this exact endpoint. The bypass is a one-line override that is trivially reachable on every request to this controller, so likelihood is high once any stack-scoped token exists.

### Recommendation
Remove the private `stack` override in `Api::CCMenuController` and use the inherited, scope-respecting `Api::BaseController#stack`/`#stacks` (i.e. `stacks.from_param!(params[:stack_id])`) so the CCMenu endpoint enforces the same `stack_id` binding as every other API controller.

### Proof of Concept
1. Create (or have the application create, as `CCMenuUrlController` already does) an `ApiClient` scoped to `stack_id: A` with permission `read:stack`, and obtain its `authentication_token`.
2. Send `GET /api/<stack_B_owner>/<stack_B_repo>/<stack_B_env>/ccmenu.xml?token=<token>` for a *different* stack `B` that the token is not scoped to.
3. Observe that `Api::CCMenuController#stack` resolves `params[:stack_id]` via `Stack.from_param!` directly (bypassing `current_api_client.stack_id` scoping used everywhere else), and the response renders stack `B`'s deploy/build status (200 OK with `lastBuildStatus`, `lastBuildLabel`, etc.), even though the token is only supposed to authorize reads for stack `A`.
