### Title
Status webhook mutates commits across all repositories/stacks because `Commit` lookup is scoped only by `sha`, never by the authenticated repository - (`app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) queries `Commit.where(sha: params.sha)` and mutates every matching row, without ever consulting `payload['repository']['full_name']` or scoping to the organization/repository whose secret authenticated the request. `Handler#repository_name` and `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) exist precisely for this purpose but `StatusHandler` never calls them. The equality the question wants checked - `repository_owner` used in `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:59-62`) vs. `repository.full_name` used to scope the mutation - never holds any protective role here because `full_name` is **not used at all** in the write path, verified or spoofed.

### Finding Description
Broken binding: `authenticated_org (repository_owner) == repository scope of the Commit write`. In `WebhooksController#verify_signature`, the signing organization is derived from `params.dig('repository','owner','login') || params.dig('organization','login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`) and checked against `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` (`lines 24-30`). Each organization can have its own `webhook_secret` (`lib/shipit/github_app.rb:50,76-83`, `lib/shipit.rb:170-200`), so this only proves the request was signed by *some* org's own secret - it says nothing about which repository's data may be mutated.

Once signature verification passes, `WebhooksController#create` dispatches the parsed JSON straight to `StatusHandler.call(params)` (`app/controllers/shipit/webhooks_controller.rb:10-15`). `StatusHandler#process` runs:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
(`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`). This ActiveRecord query is **global** across the `commits` table - it has no `stack_id`, no join to `Repository`, and never calls `repository_name`/`stacks` from the parent `Handler` class (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), even though those helpers exist and are presumably used by other handlers for exactly this scoping purpose.

Attack: an attacker who legitimately owns/administers *their own* GitHub org registered in Shipit (i.e., they possess a valid `webhook_secret` for `attacker_org`) can send `POST /webhooks` with `X-Github-Event: status`, a `repository.owner.login` of `attacker_org` (so `verify_signature` passes with their own secret), and a `sha` value copied from any commit that exists in a victim stack's `commits` table (git SHAs of public commits are trivially obtainable from GitHub). The `repository.full_name` field can be anything - spoofed to the victim's name or left as the attacker's own; it is never read by `StatusHandler`. `Commit.where(sha: ...)` will still return the victim's `Commit` row (and any other row across the whole install sharing that sha), and `create_status_from_github!` will write a status (`state`, `context`, `description`, `target_url`) onto it via `Status.replicate_from_github!` (`app/models/shipit/commit.rb:165-169`).

This write has real consequences downstream: `Commit#deployable?` depends on `success?` and `blocked?` (`app/models/shipit/commit.rb:227-237`), and `create_status_from_github!`/`add_status` triggers `deployable_status` hooks and can enqueue `ProcessMergeRequestsJob` (seen in `test/models/commits_test.rb:763-777`), i.e. it can flip a victim commit's CI status from failing/pending to `success`, unblocking deploys or the merge queue on a stack the attacker never authenticated against.

Why existing guards fail: `verify_signature` only authenticates "a legitimate org's webhook", not "the org that owns this specific commit/stack." `ExplicitParameters` (`params do ... end` in `status_handler.rb`) validates types/shapes of `sha`, `state`, etc., but not which repository the sha belongs to. No code anywhere cross-checks `repository_owner`/`repository.full_name` against the `Stack`/`Repository` that actually owns the matched `Commit` row.

### Impact Explanation
Any organization configured in Shipit (i.e., any repository owner using Shipit, however unrelated to the victim) can, using only their own valid webhook secret, forge a commit-status update for a `sha` belonging to a completely different repository/stack. This is "a payload for one repository mutating another's stack/commit" - explicitly listed as Critical impact. It can flip `Commit#deployable?`/`blocked?` state and trigger downstream automation (merge-queue processing, deploy readiness) for a stack the attacker has no authorization over. The blast radius spans every stack/repository hosted by the same Shipit instance, and the attack is repeatable for any known commit SHA (which is public GitHub data) as long as the attacker can authenticate as *any* configured org.

### Likelihood Explanation
Preconditions: the attacker must be a legitimate owner of some org/repo already registered in Shipit with its own `webhook_secret` (i.e., not a fully anonymous internet user with zero standing - they need at least one valid, if unrelated, GithubApp secret). Given that, the attack cost is trivial: one `curl` POST with a valid HMAC over an attacker-controlled JSON body, using a `sha` copied from the victim's public commit history. No GitHub cooperation, no privileged Shipit role, and no knowledge of the victim's secret is required. This is fully repeatable against any repository/stack sharing the Shipit deployment.

### Recommendation
Scope `StatusHandler#process` (and any other handler using `Commit.where(sha: ...)` globally) to the repository authenticated by the webhook: use `Handler#stacks`/`repository_name` to resolve the `Stack`(s) that belong to `payload['repository']['full_name']`, and further verify that `repository_name`'s owner matches the authenticated `repository_owner` used in `verify_signature`. Concretely, replace the query with something like `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), so a webhook can only mutate commits belonging to the stack(s) tied to the exact repository that was cryptographically authenticated.

### Proof of Concept
Add a minitest to `test/controllers/webhooks_controller_test.rb` (or `test/models/webhooks/handlers/status_handler_test.rb`):

```ruby
test "status webhook from an unrelated org mutates a victim commit purely by sha" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, author: shipit_users(:walrus),
                                                committer: shipit_users(:walrus),
                                                authored_at: Time.now, committed_at: Time.now,
                                                message: 'victim commit')

  payload = {
    'repository' => { 'full_name' => 'attacker-org/some-other-repo',
                       'owner' => { 'login' => 'attacker-org' } },
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/spoofed'
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', ATTACKER_ORG_WEBHOOK_SECRET, payload)

  assert_difference -> { victim_commit.statuses.count }, 1 do
    post shipit.github_webhooks_path,
         params: payload,
         headers: { 'X-Github-Event' => 'status', 'X-Hub-Signature' => signature,
                    'Content-Type' => 'application/json' }
  end

  assert_equal 'success', victim_commit.reload.state
end
```

Assertions to make on both sides of the claimed binding:
- Before: `repository_owner` (`attacker-org`) != owner of `victim_stack`'s repository, yet `verify_signature` returns 200 (not 422) because the signature matches `attacker-org`'s own secret.
- After: `victim_commit.statuses.count` increased and `victim_commit.state == 'success'`, proving the write occurred with zero dependency on `repository.full_name`/`repository.owner.login` matching the victim - confirming the repository-scope binding is completely absent in `StatusHandler#process`.
