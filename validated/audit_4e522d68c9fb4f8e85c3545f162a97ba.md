### Title
Cross-organization Team stamping via divergent `repository.owner.login`/`organization.login` fields - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization used for HMAC verification from `params.dig('repository','owner','login') || params.dig('organization','login')`, while `MembershipHandler#find_or_create_team!` stamps the newly created `Team#organization` from `params.organization.login`. Because a single `membership` payload can legally contain both a `repository.owner.login` and a top-level `organization.login` with different values, an attacker who can produce a validly-signed payload for one organization can cause a `Team` row to be created and tagged with a different, arbitrary organization string.

### Finding Description
The broken binding: `organization_used_for_signature_verification (repository_owner)` == `organization_persisted_on_new_Team_row (params.organization.login)` is assumed but not enforced.

Trace:
- `app/controllers/shipit/webhooks_controller.rb:59-62` — `repository_owner` reads `params.dig('repository','owner','login') || params.dig('organization','login')`. If `repository.owner.login` is present it takes precedence and `organization.login` is completely ignored for this decision. [1](#0-0) 
- `app/controllers/shipit/webhooks_controller.rb:24-30` — `verify_signature` calls `Shipit.github(organization: repository_owner)` and verifies the HMAC signature against that organization's `webhook_secret`. [2](#0-1) 
- `app/models/shipit/webhooks/handlers/membership_handler.rb:38-43` — once the request is admitted, `find_or_create_team!` creates the `Team` (when `github_id` doesn't already exist) and sets `team.organization = params.organization.login`, a field that was never consulted during signature verification when `repository.owner.login` was present. [3](#0-2) 

Exploit: an attacker who administers a GitHub organization ("attacker-org") that is legitimately registered as one tenant in this Shipit instance's multi-org GitHub App configuration (and therefore knows that org's `webhook_secret`, since they configured the webhook themselves) sends `POST /webhooks` with header `X-Github-Event: membership` and a body:
```json
{ "action": "added", "team": { "id": 999999, "name": "x", "slug": "x", "url": "https://x" },
  "repository": { "owner": { "login": "attacker-org" } },
  "organization": { "login": "shopify" },
  "member": { "login": "attacker" } }
```
signed with `attacker-org`'s `webhook_secret`. `repository_owner` resolves to `attacker-org`, `verify_signature` succeeds using `Shipit.github(organization: 'attacker-org')`, and the request is admitted. `MembershipHandler#find_or_create_team!` then creates a brand-new `Team` with `github_id: 999999` and `organization: 'shopify'` — a value the attacker never had cryptographic authority over.

Existing guards do not catch this: `verify_signature` only checks the HMAC against one organization's secret and never cross-checks `organization.login`; the `ExplicitParameters` schema in `MembershipHandler` only requires the `organization.login` field to be a `String`, it does not compare it to `repository_owner`; there is no model validation on `Team#organization` tying it back to the verified webhook organization.

### Impact Explanation
This lets a payload authenticated for one organization mutate/create state (`Team.organization`) attributed to a different organization the attacker does not control — matching the "payload for one repository mutating another's ... team" Critical category. `Team#organization` is used as the join key for `has_many :github_hooks` (foreign_key/primary_key `:organization`) and (via `Team.find_or_create_by_handle`) feeds into `Shipit.github_teams`, which is consulted by `User#authorized?` (`app/models/shipit/user.rb:80-82`) to gate Shipit login/authorization. A forged `Team` row bound to a victim org's namespace (e.g., `shopify`) with an attacker-chosen `github_id`/slug creates a spoofed team object that does not correspond to any real GitHub team in that org, which can pollute team-based authorization bookkeeping and is repeatable for any `team.id` not yet present in the `teams` table (unique index is on `organization+slug`, not on `github_id`, so repeated attempts with new ids are unconstrained).

### Likelihood Explanation
The primary precondition is unusual but explicitly stated as in-scope by the question: the attacker's own organization ("attacker-org") must already be a configured tenant in this Shipit instance's GitHub Apps configuration with a `webhook_secret` known to the attacker (which is realistic in a multi-tenant Shipit deployment where each org's admin configures their own app/secret). Given that, the only other requirement is that no `Team` row exists yet for the chosen `team.id`, which the attacker fully controls by picking an unused id. No other secrets, sessions, or privileged roles are required, and the attack is trivially repeatable against arbitrary target `organization.login` values.

### Recommendation
In `MembershipHandler#find_or_create_team!`, use the already-authenticated `repository_owner`/organization value used for signature verification (not `params.organization.login`) when stamping `team.organization`, or explicitly validate `params.organization.login == repository_owner` (as derived by the controller) and reject the event otherwise. More generally, `WebhooksController#verify_signature` should ensure every organization-identifying field used later in the pipeline is validated against the same organization that produced a valid signature, rather than allowing handlers to pick a different field.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (minitest, no live GitHub)
test "membership payload with mismatched repository.owner.login and organization.login stamps Team with unverified org" do
  @request.headers['X-Github-Event'] = 'membership'

  # Attacker only proves control of 'attacker-org' via HMAC
  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  body = {
    action: 'added',
    team: { id: 999_999, name: 'x', slug: 'x', url: 'https://x' },
    repository: { owner: { login: 'attacker-org' } },
    organization: { login: 'shopify' }, # attacker never authenticated as shopify
    member: { login: 'attacker' }
  }.to_json

  assert_difference -> { Shipit::Team.count }, 1 do
    post :create, body: body, as: :json
    assert_response :ok
  end

  team = Shipit::Team.find_by(github_id: 999_999)
  # Left side: organization used to verify the signature (attacker-org)
  # Right side: organization persisted on the new Team row (shopify)
  refute_equal 'attacker-org', team.organization
  assert_equal 'shopify', team.organization
end
```
This demonstrates the signature was validated for `attacker-org` while the created `Team#organization` was set to `shopify`, confirming the binding is broken.
