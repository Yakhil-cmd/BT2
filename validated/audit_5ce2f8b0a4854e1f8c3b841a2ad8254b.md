### Title
Cross-organization webhook signature verification bound to `repository_owner`, not to `sha`/repository, allows attacker-owned-org signature to forge Status on victim commits - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` binds the HMAC signature check only to the organization derived from `repository.owner.login`/`organization.login` in the payload, via `Shipit.github(organization: repository_owner)`. Once that check passes, `StatusHandler#process` mutates data using only `params.sha`, with no re-validation that the `sha` (or any repo identifier) actually belongs to the organization/repository that was cryptographically verified.

### Finding Description
The claimed binding, made explicit: `verify(signature, secret_for(repository_owner)) == true` should imply `mutation_scope == repository_owner`'s repositories. In this codebase that equality does not hold, because the mutation scope is actually `Commit.where(sha: params.sha)` — a global lookup across all stacks/repositories, keyed only by string equality on `sha`.

Code path:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and fetches `Shipit.github(organization: repository_owner)`, then calls `github_app.verify_webhook_signature(signature, request.raw_post)` [1](#0-0) [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` performs an HMAC-SHA1 compare of the raw body against the `webhook_secret` configured for that specific organization only [3](#0-2) . This proves the request was signed by whoever holds `attacker-owned-org`'s secret — it says nothing about the truthfulness of any `sha` field embedded in the body.
3. On success, `WebhooksController#create` dispatches the entire raw JSON body to `StatusHandler.call(params)` for a `status` event, with no re-check that `params['repository']` matches the organization that was verified [4](#0-3) .
4. `StatusHandler#process` only requires `sha` and `state` as schema fields (no repository/org constraint) and executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . This is a *global* lookup by `sha` across the `commits` table, not scoped to any stack/organization derived from the verified signer.

Because commit shas from public GitHub repositories are public information, an attacker who owns any org configured in Shipit (with a legitimate, self-controlled `webhook_secret`) can sign a `status` payload naming their own repository/org (so `verify_signature` succeeds) but set `sha` to a sha they observed on a victim's public repository that happens to already exist as a `Commit` row in Shipit (i.e., a commit already synced from the victim's tracked stack). `StatusHandler` will match that `Commit` record purely by `sha` string equality and create a new `Status` against it via `create_status_from_github!`, regardless of which org/repo was actually authenticated.

None of the listed guards intercept this: `drop_unhandled_event` only checks that a handler exists for the event type; the `ExplicitParameters` schema in `StatusHandler` only requires `sha`/`state` types and does not constrain them to the verified repo; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` in this unauthenticated webhook path (webhooks are inherently no-session); and `Commit` has no organization-derived scoping in this query — it is scoped by `sha` value alone.

### Impact Explanation
An attacker with a legitimate GitHub App/webhook secret for their *own* organization can forge a `Status` on a `Commit` belonging to a *different* organization's stack, as long as that commit's sha is already known to Shipit (synced from the victim's public repo). This is a cross-tenant data-integrity violation: a signature valid for org A is treated as sufficient authorization to write into org B's commit history/status table. Since `Status` creation can trigger `enable_ci_on_stack`, `schedule_continuous_delivery`, and hook broadcasts (`after_create`/`after_commit` callbacks) [6](#0-5) , a forged "success" status on the right commit can influence continuous-delivery decisions (e.g., trigger `ProcessMergeRequestsJob`, as shown in test evidence of CD side effects tied to status transitions) [7](#0-6) . This matches the "payload for one repository mutating another's stack/commit" Critical category.

### Likelihood Explanation
Preconditions: (1) attacker must operate/own at least one GitHub organization already configured in Shipit's `github` secrets section (multi-org support is explicitly documented) [8](#0-7) , giving them a legitimate `webhook_secret` for their own org; (2) the victim's commit sha must already exist in Shipit's `commits` table (i.e., previously synced from a tracked stack), which is likely for any actively deployed stack; (3) the sha itself is public info via GitHub's API for public repos. Given a Shipit instance with multiple onboarded orgs, this is a realistic, low-cost, repeatable attack — a single crafted POST per target commit, fully scriptable.

### Recommendation
Scope the mutation to the verified identity: `StatusHandler` (and other handlers keyed by `sha`) should filter `Commit.where(sha: params.sha)` by the stack(s) whose `repository.full_name`/owner matches the payload's `repository` field, and additionally cross-check that the verified `repository_owner` used for signature verification matches `commit.stack.repository.owner`. Alternatively, restructure `verify_signature` to also validate `params['repository']['full_name']` against the specific stack's repository before invoking handlers, rejecting mismatches between the signed organization and the target commit's owning stack.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "status webhook from unrelated org can forge a status on a victim's commit by sha" do
  victim_commit = shipit_commits(:first) # belongs to org "shopify" stack in fixtures

  # Attacker's org is "attacker-owned-org"; stub signature verification to only
  # succeed for attacker's org, proving the signature never binds to `victim_commit`'s org.
  Shipit.stubs(:github).with(organization: 'attacker-owned-org').returns(
    stub(verify_webhook_signature: true)
  )

  request.headers['X-Github-Event'] = 'status'
  forged_payload = {
    'sha' => victim_commit.sha,          # learned via public GitHub API
    'state' => 'success',
    'repository' => { 'owner' => { 'login' => 'attacker-owned-org' } } # attacker's own repo
  }.to_json

  assert_difference -> { victim_commit.statuses.count }, 1 do
    post :create, body: forged_payload, as: :json
  end
  assert_response :ok

  # Binding check: the org verified by the signature ("attacker-owned-org")
  # does NOT equal the org owning the mutated commit (victim_commit.stack.repository.owner).
  refute_equal 'attacker-owned-org', victim_commit.stack.repository.owner
end
```
This demonstrates that `verify_signature`'s success for `attacker-owned-org` and the actual mutation target (`victim_commit`, owned by a different org) diverge — the equality `signed_org == mutated_repo_owner` is false, yet the write succeeds.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
