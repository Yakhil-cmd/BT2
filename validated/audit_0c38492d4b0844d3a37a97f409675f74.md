### Title
Unvalidated commit SHA from git host response permits path traversal in extension pin file path - ([File: pkg/cmd/extension/http.go, pkg/cmd/extension/manager.go])

### Summary
`fetchCommitSHA` in `pkg/cmd/extension/http.go` returns the raw HTTP response body from a `commits/{targetRef}` request as the "commit SHA" without validating that it is a well-formed hex commit hash. This value is later spliced directly into a file name (`.pin-%s`) that is joined with `targetDir` in `manager.go`'s pin-path construction, so a response body containing `../` sequences could cause the resulting path to escape `targetDir`.

### Finding Description
`fetchCommitSHA(httpClient, baseRepo, targetRef)` issues a GET to `repos/{owner}/{repo}/commits/{targetRef}` with the `application/vnd.github.v3.sha` Accept header and returns `string(body)` verbatim with no format check (no regex/length validation for a 40- or 64-character hex SHA, no `strings.TrimSpace`): [1](#0-0) 

That return value is used by `installGit` as `commitSHA`, which is embedded into `fmt.Sprintf(".pin-%s", commitSHA)` and then combined with `targetDir` via `filepath.Join` to compute `pinPath`. Because `filepath.Join`/`filepath.Clean` interpret `..` segments lexically, if `commitSHA` contains path-traversal sequences (e.g. `../../../../tmp/evil`), the resulting `pinPath` can resolve outside `targetDir`.

Under normal operation against genuine github.com/GHES, this endpoint always returns a valid hex SHA, so the practical trigger requires the attacker to control the *content* of the HTTP response for this specific API call — i.e., the victim's `gh` client is pointed at an attacker-influenced/compromised host (an explicitly in-scope attacker capability per this audit's threat model: "controls responses from a host the victim points gh at"). No client-side validation exists between the HTTP response and the path construction to reject malformed/traversal-containing SHA strings.

I was not able to retrieve the exact surrounding lines of `installGit`/`pinPath` in `manager.go` within the available tool budget (grep confirmed the tokens `pinPath`, `commitSHA`, `targetDir` exist there, but I could not view the precise code block), so the exact sanitization state at that call site (e.g., whether any hex-format check exists there) could not be fully confirmed from source inspection.

### Impact Explanation
If exploitable, this allows a file to be created/overwritten at an attacker-chosen path outside the extension's install directory (`targetDir`), matching the "file write outside intended path" impact class. The severity is bounded by: (a) file content is limited to whatever the pin-marker mechanism writes (not fully attacker-controlled arbitrary content), and (b) it requires the victim's `gh` to be pointed at a host whose API responses are attacker-influenced, rather than github.com itself.

### Likelihood Explanation
Low-to-moderate likelihood. Exploitation requires the victim to run `gh extension install` against a repo host where the attacker (or a compromised host) controls the raw body returned for `GET /repos/{owner}/{repo}/commits/{ref}` with the SHA Accept header — this is not achievable against real github.com (which always returns a valid SHA), so it is realistically confined to malicious/compromised GitHub Enterprise Server instances the victim has configured `gh` to trust. Given that constraint, the precondition is significant, but it is explicitly within the stated threat model ("controls responses from a host the victim points gh at").

### Recommendation
Validate the value returned by `fetchCommitSHA` against a strict hex-SHA pattern (e.g., `^[0-9a-f]{40}$` or `{64}` for SHA-256) before using it anywhere, and reject/error out on mismatch. Additionally, when constructing `pinPath`, verify (e.g., via `filepath.Rel` or a prefix check after `filepath.Clean`) that the resulting path remains within `targetDir` before performing any file write.

```go
// pkg/cmd/extension/http_test.go (illustrative)
func TestFetchCommitSHA_RejectsNonHexResponse(t *testing.T) {
    reg := httpmock.Registry{}
    reg.Register(
        httpmock.REST("GET", "repos/owner/ext/commits/evil-ref"),
        httpmock.StringResponse("../../../../tmp/evil"),
    )
    client := &http.Client{Transport: &reg}
    sha, err := fetchCommitSHA(client, ghrepo.New("owner", "ext"), "evil-ref")
    // Expected (fix): err != nil because response is not a valid hex SHA
    require.Error(t, err)
    _ = sha
}

// pkg/cmd/extension/manager_test.go (illustrative)
func TestInstallGit_PinPathConfinement(t *testing.T) {
    targetDir := t.TempDir()
    maliciousSHA := "../../../../tmp/evil"
    pinPath := filepath.Join(targetDir, fmt.Sprintf(".pin-%s", maliciousSHA))
    // Expected (fix): pinPath must remain within targetDir
    rel, err := filepath.Rel(targetDir, pinPath)
    require.NoError(t, err)
    require.False(t, strings.HasPrefix(rel, ".."))
}
```
Both assertions should hold after adding hex-format validation to `fetchCommitSHA` and/or a containment check before writing `pinPath`; currently neither check exists in `fetchCommitSHA` per [1](#0-0) .
