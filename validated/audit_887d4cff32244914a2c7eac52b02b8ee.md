### Title
Cross-repository commit status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by `sha`, with no check that the commit's owning `Stack`/`Repository` matches the repository that actually emitted and signed the webhook. Because GitHub commit SHAs are shared across forks/mirrors of the same history, an attacker who owns any repository configured as a Shipit stack can send a legitimately-signed status webhook from their own repo and mutate the `Status` of a `Commit` row belonging to a completely different tenant's stack, including one that is the target of an in-flight `Task`.

### Finding Description
The binding that should hold is: `payload['repository']['full_name'] == commit.stack.github_repo_name` for every `Commit` mutated by a status event. This binding is never checked.

- `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only verifies that the HMAC signature is valid for the GitHub App/organization identified by `params.dig('repository','owner','login')` — i.e., it authenticates "this event genuinely came from GitHub for org X," not "this event is about repository Y that owns the affected record." [1](#0-0) 

- `StatusHandler`'s params schema never even captures `repository.full_name` — it only requires `sha`, `state`, and optional description/context/target_url/branches. [2](#0-1) 

- `StatusHandler#process` then does a *global*, cross-tenant lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. `Commit` rows are per-`stack` (`belongs_to :stack`), and nothing here filters by `stack.repository`. [3](#0-2) 

- `create_status_from_github!` unconditionally writes a new `Status` for that commit and recomputes `status`, feeding `deployable?`, `blocked?`, `active?`, and triggers `schedule_continuous_delivery`/`Hook.emit(:deployable_status, ...)`. [4](#0-3) [5](#0-4) 

**Exploit flow**: SHA1 commit identifiers are identical across a repository and any fork/mirror of it that shares history up to a common point (this is normal git behavior, not a hash collision). If a victim organization has registered `victim/repo` as a Shipit stack, and an attacker forks it as `attacker/repo` and also registers that fork as a Shipit stack (self-service repo/stack registration is available to any authenticated GitHub user per Shipit's normal flow), then:
1. Attacker picks a SHA that is shared history between the fork and `victim/repo` and that is currently inside `victim`'s active `Task`'s commit range (`since_commit`..`until_commit`).
2. Attacker sets a commit status on that SHA in their own fork via the GitHub API (or by pushing a build to their own CI hooked to their fork) — GitHub genuinely and correctly signs and delivers this `status` webhook to Shipit for `attacker/repo`.
3. `verify_signature` passes because the signature is valid for the attacker's own org/repo.
4. `StatusHandler#process` matches on `sha` alone and finds **both** the attacker's own `Commit` row and `victim`'s `Commit` row for that SHA, and calls `create_status_from_github!` on both — mutating `victim`'s commit's `status`/`state`, which feeds `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) and interacts with `Commit#active?`/`Stack#active_task` used throughout deploy/CD decision logic (`app/models/shipit/stack.rb:221-225,337-341,459-467`). [6](#0-5) [7](#0-6) 

None of the listed guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, model validations) prevent this, because they operate at the level of "is this a valid GitHub webhook for org X," never at the level of "does this Commit's owning repository match the webhook's repository."

### Impact Explanation
An attacker who controls only their own (forked) repository can force writes of `Status`/`deployable?` state on `Commit` records belonging to another tenant's `Stack`, without ever authenticating against that tenant's repository. This can flip a victim's in-flight or queued commit between "deployable"/"blocked"/"success"/"failure", which is consumed by `Stack#next_commit_to_deploy`, `Commit#schedule_continuous_delivery`, and merge/deploy hooks — i.e., a payload validly attributed to one repository mutates another repository's stack/commit state, and can influence an unauthorized deploy, rollback-avoidance, or merge decision. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." Repeatable at will and against any victim stack that shares commit history (fork/mirror/monorepo-split) with any repository the attacker controls.

### Likelihood Explanation
Preconditions: victim's repo must be a Shipit stack; attacker must own/control a repository that shares at least one commit SHA with the victim's history (trivial via forking a public repo) and that repository must also be configured as a Shipit stack (or otherwise wired to emit correctly-signed status webhooks to the same Shipit instance) — a self-service action available to ordinary GitHub users in typical Shipit deployments. No secrets, sessions, or elevated GitHub permissions are required; only the ability to set a commit status on the attacker's own fork. This is a realistic, low-cost, repeatable attack for any shared-repository/monorepo/fork topology.

### Recommendation
In `StatusHandler#process` (and analogously `CheckSuiteHandler`/other SHA-keyed handlers), scope the `Commit` lookup to the stack(s) whose `repository` matches the webhook payload's `repository.full_name`/`owner`/`name`, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: ..., name: ... })`, and capture `repository` in the `StatusHandler` params schema so it can be validated before mutating any `Commit`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "status webhook from an unrelated repository must not mutate another stack's active-task commit" do
  victim_repo = shipit_repositories(:shipit)
  victim_stack = shipit_stacks(:shipit)
  shared_sha = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared base commit")
  attacker_repo = Shipit::Repository.create!(owner: "attacker", name: "fork")
  attacker_stack = Shipit::Stack.create!(repository: attacker_repo, environment: "production")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "shared base commit")

  task = victim_stack.tasks.create!(
    since_commit: victim_commit, until_commit: victim_commit,
    definition: victim_stack.find_task_definition("deploy"), user: shipit_users(:walrus)
  )
  task.update!(status: "running")

  before = victim_commit.reload.status.state

  # Equality claimed by the binding, BEFORE:
  assert_not_equal "attacker/fork", victim_stack.github_repo_name

  Shipit::Webhooks::Handlers::StatusHandler.new.process(
    OpenStruct.new(sha: shared_sha, state: "failure", description: nil, target_url: nil, context: "ci")
  )

  # AFTER: victim's commit status/deployable? changed despite the webhook
  # having authenticated only attacker/fork, not victim/repo.
  assert_not_equal before, victim_commit.reload.status.state
  refute victim_commit.deployable?
end
```
This demonstrates that a status event never scoped to `victim`'s repository still mutates `victim_commit.status`/`deployable?` while a `Task` on `victim_stack` is active, confirming the broken repository-binding.
