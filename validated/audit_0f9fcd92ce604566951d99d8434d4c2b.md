### Title
Governance/OP-list takeover via balance acquired just before `system_vote_count` stabilizes, with no minimum holding period - ([File: main_chain.js])

### Summary
The `ocore` on-chain governance mechanism for changing the order-provider (`op_list`) and other consensus/economic parameters (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) weighs `system_vote` messages by whatever base-currency balance the voting address holds **at the moment the vote is counted** (i.e., when the paired `system_vote_count` unit stabilizes), not by a balance that was held for any minimum period before the vote was cast. This mirrors the root cause of the Token of Power incident: an attacker who transiently acquires a large share of the voting weight can single-handedly dictate a governance outcome in one shot, because there is no timelock/holding-period requirement decoupling "acquire tokens" from "vote counts with full weight."

### Finding Description
Any non-AA unit author can post a `system_vote` message choosing a full `op_list` slate or a numeric system parameter, and any non-AA author can post the paired `system_vote_count` message that schedules a recount: [1](#0-0) [2](#0-1) 

When the unit carrying `system_vote_count` stabilizes, `countVotes()` is invoked and recomputes voting weight from scratch using each voter's **current** stable base-currency balance: [3](#0-2) 

This balance is not the balance the voter had when they cast their `system_vote`, nor is it required to have been held for any prior duration — it is simply "SUM of currently unspent stable-good base outputs owned by that address" at the time counting happens: [4](#0-3) 

For `op_list`, the winning slate is simply the `COUNT_WITNESSES` addresses with the highest summed voter balance among those who voted for them within the lookback window — there is no requirement that the winning choice represent an absolute majority of all bytes in existence, only that the total participating balance across the (possibly multi-year) lookback window exceeds `SYSTEM_VOTE_MIN_SHARE * TOTAL_WHITEBYTES`: [5](#0-4) [6](#0-5) 

Because the balance snapshot is taken only at count time and not pinned to the moment the vote was cast (nor to a sustained holding period), an attacker can:
1. Acquire a large amount of bytes (e.g., via exchange purchase, flash-style transfer, or temporary custody) shortly before triggering a recount.
2. Post `system_vote` for a malicious `op_list` (installing addresses they control as order providers) or for extreme numeric parameters (e.g., `base_tps_fee`, `tps_fee_multiplier`) that could be economically damaging.
3. Post `system_vote_count` for the same subject.
4. Once those units become stable, `countVotes()` tallies the attacker's currently-held balance at full weight, letting the attacker's vote dominate if their momentarily-held balance exceeds the combined balance of all other participants who voted differently in the active window.

There is a partially analogous defense for **emergency** OP changes (`EMERGENCY_COUNT_MIN_VOTE_AGE`, `EMERGENCY_OP_LIST_CHANGE_TIMEOUT`) that requires unstable votes to "age" before being counted in the emergency path: [7](#0-6) 
but this safeguard applies only to the emergency-recovery code path (used when the network is stuck) and does **not** apply to normal `system_vote`/`system_vote_count` processing, nor does it impose any minimum holding period on the balance itself — it only delays counting of very recent votes in the emergency case, not the ordinary vote-count flow used to update `op_list` or numeric parameters in day-to-day operation.

### Impact Explanation
A successful attack lets an unprivileged unit poster overwrite `storage.systemVars.op_list` (the order providers that determine main-chain stability/witnessing) or manipulate TPS-fee-related economic parameters (`base_tps_fee`, `tps_interval`, `tps_fee_multiplier`, `threshold_size`) network-wide: [8](#0-7) [9](#0-8) 
Controlling the OP list is equivalent to controlling who is trusted to attest main-chain stability, which can be leveraged toward double-spend/finality-disagreement style outcomes network-wide, and manipulating TPS-fee parameters can freeze or distort the network's fee market. This is a High-severity, network-wide governance takeover analogous to TOP's DAO takeover, not merely a resource-only issue.

### Likelihood Explanation
Exploitation requires temporarily holding a voting balance larger than the combined weight of dissenting active voters in the lookback window, and requires that other participants not counter-vote before the attacker's `system_vote_count` stabilizes. In a young network or a period of low voter turnout (the lookback window keeps expanding backward until `SYSTEM_VOTE_MIN_SHARE` of the total supply has participated, which could span multiple years), the balance needed to dominate the tally could be far smaller than a true majority of the whole token supply — directly mirroring the TOP situation where the attacker exploited a very small effective quorum (16,384 total TOP tokens) to cheaply acquire >50% voting power. Because balance is measured at count time with no holding-duration requirement, the attack window is short and does not require the attacker to keep the funds locked, lowering the capital-efficiency cost of the attack (funds can be moved/returned immediately after the vote stabilizes).

### Recommendation
Require system-vote weight to be based on a balance that was held continuously for a minimum period prior to casting the vote (e.g., balance as of `last_ball_mci` at vote time, verified again to have existed since some minimum age), rather than the balance held at count time. Alternatively/additionally, require a true majority-of-supply quorum for `op_list` changes (not just a relative plurality among active voters) and extend the `EMERGENCY_COUNT_MIN_VOTE_AGE`-style anti-flash-vote protection to the normal (non-emergency) `system_vote`/`system_vote_count` path.

### Proof of Concept
1. Attacker acquires (via purchase/transfer) a base-currency balance exceeding the combined active voting balance for `op_list` in the current lookback window (this can be much smaller than 51% of total supply if participation/quorum in that window is low).
2. Attacker posts a `system_vote` unit with `{ subject: 'op_list', value: [<attacker-controlled addresses>] }` — validated per [10](#0-9) .
3. Attacker posts a `system_vote_count` unit with payload `'op_list'` — validated per [2](#0-1) .
4. Once the unit carrying `system_vote_count` stabilizes, `main_chain.js` calls `countVotes(conn, mci, 'op_list')`, which computes `voter_balances` from the attacker's currently-held stable balance [11](#0-10)  and, because the attacker's slate collects the highest summed balance, installs the attacker-controlled addresses as the new `op_list` [12](#0-11) .
5. Attacker may now move the acquired funds elsewhere; the governance change already took effect with no timelock or holding-period check having been enforced.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}


async function applyEmergencyOpListChange(conn, emergency_count_command_timestamp, cb) {
	// last stable unit
	const [{ timestamp, main_chain_index }] = await conn.query("SELECT timestamp, main_chain_index FROM units WHERE is_stable=1 AND is_on_main_chain=1 ORDER BY main_chain_index DESC LIMIT 1");
	if (emergency_count_command_timestamp < timestamp + constants.EMERGENCY_OP_LIST_CHANGE_TIMEOUT) {
		console.log(`too early to apply emergency OP list change yet`);
		return cb();
	}
	console.log(`applying emergency vote count after being stuck at mci ${main_chain_index}`);
	await countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp);
	cb();
}
