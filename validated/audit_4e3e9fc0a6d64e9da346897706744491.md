### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` but handlers act on `repository.full_name`, allowing cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the per-organization webhook secret using `repository_owner`, derived from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), and validates the HMAC over the *entire* raw request body with that secret. [1](#0-0) [2](#0-1)  However, none of the event handlers use `repository.owner.login` to resolve which stack/repository to act on — they all resolve the target repository from `repository.full_name` instead, via `Shipit::Webhooks::Handlers::Handler#repository_name`. [3](#0-2) 

Because the HMAC covers the raw body, this is not exploitable as a pure signature bypass by itself in the common single-secret deployment. But in the documented multi-organization configuration (`Shipit.github(organization:)`, `github_app_config`), each org has its own independent `webhook_secret`. [4](#0-3)  A GitHub App/webhook admin for Organization A (who legitimately knows Org A's `webhook_secret` because they administer that org's installation) can craft and correctly sign an arbitrary JSON body where `repository.owner.login` (or `organization.login`) is set to `"OrgA"` — satisfying `verify_signature`'s org lookup and HMAC check — while `repository.full_name` is set to `"OrgB/some-other-repo"`. `verify_signature` never checks that `repository.owner.login` matches `repository.full_name`'s owner segment, and downstream handlers never re-check the authenticating org against the repo they operate on.

### Finding Description
- `verify_signature` picks the HMAC secret purely from `repository_owner` (or `organization.login`), then validates the raw POST body against that secret: [5](#0-4) 
- `repository_owner` is attacker-controlled JSON, independent of `repository.full_name`: [2](#0-1) 
- All webhook handlers (push, pull_request opened/closed/reopened/edited/labeled/unlabeled, label-capturing, membership, check_suite) resolve the acted-upon repository/stack from `repository.full_name`, never cross-checking it against the org whose secret validated the payload: [3](#0-2) [6](#0-5) [7](#0-6) 
- The `membership` handler is even more permissive: it trusts `organization.login` from the payload directly to create/attribute a `Team`, with no relation at all to a repository, and no re-validation against the org that authenticated the request: [8](#0-7) 
- The multi-org secret configuration is the officially supported mechanism (`github_app_config`, `TOP_LEVEL_GH_KEYS`), confirming the engine intends per-organization trust boundaries that this code does not enforce end-to-end: [9](#0-8) 

This is precisely the pattern called out in scope rule 3: "an organization that authenticated versus the repository that is written." The equality that should hold is: `organization_that_signed(payload) == owner(repository.full_name acted upon)`. In a multi-org deployment this equality is never checked; only `organization_that_signed(payload) == repository.owner.login` (a field the same request body also controls, unconstrained by `full_name`) is checked.

### Impact Explanation
An attacker who legitimately controls a GitHub App installation/webhook secret for one organization onboarded to a shared Shipit instance can forge and correctly sign webhook events that cause writes against a *different* organization's repositories/stacks tracked by the same Shipit instance: triggering `GithubSyncJob`s, archiving/unarchiving stacks, creating/deleting `Team` memberships, capturing pull-request labels, and updating commit statuses for repositories they do not own. This is a cross-repository write across organization trust boundaries, which is explicitly listed as a Critical impact in the rules.

### Likelihood Explanation
Requires the attacker to already be an authorized administrator of at least one organization's GitHub App installation configured on the shared Shipit instance (i.e., knows that org's `webhook_secret`), and requires the shared instance to be configured for multiple organizations (`Shipit.github(organization:)` mode) with more than one tenant. This is a realistic configuration per `docs/setup.md`'s multi-org example, but it is a somewhat narrower blast radius than a fully unauthenticated attacker, since it depends on cross-tenant isolation being expected within one Shipit deployment.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after signature verification, assert that the organization derived from `repository.full_name`'s owner segment (and/or `organization.login` for org-level events) matches the `repository_owner`/organization that was used to select the verifying secret, rejecting the webhook (422) on mismatch. Centralize this check in the base `Handler` class so all current and future handlers get it for free rather than trusting `full_name` unconditionally.

### Proof of Concept
1. Configure Shipit with multi-org GitHub App secrets for `OrgA` and `OrgB`, each tracking their own repositories/stacks.
2. As the legitimate holder of `OrgA`'s `webhook_secret`, construct a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POST to `/github/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, loads `Shipit.github(organization: "OrgA")`, and validates the HMAC successfully. [1](#0-0) 
5. `PushHandler#stacks` resolves the repository via `Repository.from_github_repo_name("OrgB/victim-repo")`, enqueuing `GithubSyncJob` for `OrgB`'s stack, even though the request was never signed with `OrgB`'s secret. [3](#0-2) [6](#0-5) 

**Note on verification limits:** I was not able to execute this end-to-end in a live multi-org deployment; the analysis is based on static code review of the controller, `Handler` base class, and individual handlers. I could not find any additional check elsewhere in `app/**` or `lib/shipit/**` that cross-validates the authenticating organization against `repository.full_name` before handler dispatch — if such a check exists outside the indexed portions of the codebase, it would mitigate this finding.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
