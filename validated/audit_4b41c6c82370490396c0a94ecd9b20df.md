## Title
`collect_creator_fee` / `collect_creator_fee_permissionless` are not gated by the pool's status/pause bitmask, unlike every other fund-moving instruction - (File: `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
`PoolState` exposes an admin-controlled `status` bitmask (`PoolStatusBitIndex::{Deposit, Withdraw, Swap}`) that lets the admin pause deposits, withdrawals and swaps via `update_pool_status` as a circuit breaker [1](#0-0) . `deposit`, `withdraw`, `swap_base_input`, and `swap_base_output` all check `pool_state.get_status_by_bit(...)` before moving funds and revert with `ErrorCode::NotApproved` if the relevant bit is disabled [2](#0-1) . However, `collect_creator_fee` and `collect_creator_fee_permissionless`, which also transfer tokens out of the pool vaults, contain no such status check at all [3](#0-2) [4](#0-3) .

### Finding Description
The `status` bitmask exists specifically so the admin can halt fund movement out of a pool (e.g., during an active exploit, oracle manipulation, or fee-rate abuse) via `update_pool_status` [5](#0-4) . Every other outbound-transfer path in scope — `deposit.rs`, `withdraw.rs`, `swap_base_input.rs`, `swap_base_output.rs` — is gated by `get_status_by_bit`, confirmed by the single match each in those files [6](#0-5) . `collect_creator_fee`/`collect_creator_fee_permissionless` are unconditionally callable regardless of `status`: they only check that `creator_fees_token_0`/`creator_fees_token_1` are non-zero before transferring the accrued creator fees out of `token_0_vault`/`token_1_vault` to the creator's ATA [7](#0-6) . `collect_creator_fee_permissionless` in particular can be invoked by any unprivileged signer as `payer`, with funds always routed to `pool_creator` [8](#0-7) , so pausing the pool does nothing to stop this outflow.

This is the direct analog of the reported bug class: a fund-affecting instruction that is inconsistent with sibling instructions which are protected by the same guard, allowing state changes/fund movement to continue exactly when the protocol's pause mechanism is meant to prevent it.

### Impact Explanation
When an admin disables a pool via `update_pool_status` (e.g., in response to a malicious pool creator wash-trading to inflate `creator_fee_rate` accrual, or any incident requiring an emergency freeze), the creator-fee ledger (`creator_fees_token_0/1`) can still be drained from the vaults through `collect_creator_fee_permissionless` by anyone, with proceeds going to the (potentially malicious) `pool_creator`. This defeats the purpose of the pause as an incident-response control and lets a malicious actor complete extraction of accrued fees even after the protocol has flagged the pool as unsafe and attempted to halt outflows.

### Likelihood Explanation
The path is reachable by any unprivileged account in a single transaction: no special account or elevated permission is required to call `collect_creator_fee_permissionless`, and `collect_creator_fee` requires only the pool's own `pool_creator` signer — which is attacker-controlled if the attacker created the pool. Triggering it simply requires the admin having paused the pool while fees remain outstanding, a realistic and expected operational scenario for the `status` mechanism.

### Recommendation
Add a status check to both instructions consistent with the rest of the codebase, e.g. introduce a dedicated bit (or reuse `Withdraw`) and check it before transferring:
```rust
if !pool_state.get_status_by_bit(PoolStatusBitIndex::Withdraw) {
    return err!(ErrorCode::NotApproved);
}
```
placed at the top of `collect_creator_fee` and `collect_creator_fee_permissionless`, mirroring the guard already present in `deposit.rs`, `withdraw.rs`, `swap_base_input.rs`, and `swap_base_output.rs`.

### Proof of Concept
1. A pool creator sets up a pool and, through self-swaps or wash trading, accrues a large `creator_fees_token_0`/`creator_fees_token_1` balance [9](#0-8) .
2. The admin detects abuse and calls `update_pool_status` to disable all pool operations (`status = 7`) as an emergency stop [10](#0-9) .
3. Any account (including the malicious creator) calls `collect_creator_fee_permissionless`; since the instruction never checks `pool_state.status`, the transfer succeeds and the fees are moved out to the creator's token accounts despite the pause [4](#0-3) .

```rust
pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;
```

```rust
pub fn update_pool_status(ctx: Context<UpdatePoolStatus>, status: u8) -> Result<()> {
    require_gte!(255, status);
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    pool_state.set_status(status);
    pool_state.recent_epoch = Clock::get()?.epoch;
    Ok(())
}
```
