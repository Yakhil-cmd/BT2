## Verdict: Valid finding (High severity, not Critical)

The underlying mechanism described is accurate: `PreStxOp::parse_from_tx` derives `output` solely from the **first output's address bytes** of the PreStx Bitcoin transaction — a value fully controlled by whoever crafts the transaction script, requiring no possession of the named address's Stacks or Bitcoin private key. [1](#0-0) 

`StackStxOp::get_sender_txid` only requires that the StackStxOp's `input[0]` spend `vout==1` of the referenced PreStxOp — a purely structural/UTXO-chain check, not a signature-based identity check. [2](#0-1) 

The burnchain indexer then looks up the PreStxOp via that txid and passes `pre_stack_stx.output` directly as `sender` into `StackStxOp::from_tx`, which sets `sender: sender.clone()` with zero additional validation. [3](#0-2) [4](#0-3) 

`process_stacking_ops` then invokes pox-4's `stack-stx` as a Clarity contract-call with `tx-sender` forcibly set to this attacker-chosen `sender` address (i.e., `V`), bypassing the normal Stacks-transaction signature requirement entirely. [5](#0-4) 

Critically, `collect_pox_4_stacking_args` always passes `Value::none()` as `signer-sig` for burnchain-originated ops. [6](#0-5) 

In `pox-4.clar`'s `stack-stx`, the only checks tied to the victim's identity are balance-sufficiency and "not already stacked/delegating" — there is **no check that `tx-sender` (i.e., V) authorized this call**. The `consume-signer-key-authorization` / `verify-signer-key-sig` logic only authenticates the **signer key** (used for the reward-address/signing-set registration), not the **stacker** (`tx-sender`) whose balance gets locked. [7](#0-6) [8](#0-7) 

### Why this is real but not Critical
No STX is stolen or permanently frozen — the locked STX unlocks back to V automatically after `lock-period` cycles, matching normal PoX unlock behavior. The exploit does not create "value locked/unlocked without backing," nor double-counts a reward, nor mints anything unbacked. What it does allow is:
- An **unsigned stacking action**: V's STX gets locked for up to `POX_MAX_NUM_CYCLES` cycles without V's Stacks or Bitcoin key ever being used.
- **Temporary freezing of staked funds** belonging to V.
- The attacker sets `reward_addr` (via the StackStxOp's own first Bitcoin output) to their own address, so any PoX BTC rewards for the reward slot backed by V's coerced STX are paid to the attacker, not V.

This matches the rules' **High** category ("temporary freezing of staked funds ... an unsigned stacking action"), not **Critical** (no permanent freeze, no theft of the locked STX principal itself, and no sBTC/locked-STX minting or double count).

### Title
Unsigned/impersonated `stack-stx` locking of a victim's STX via attacker-crafted `PreStxOp`+`StackStxOp` pair - (File: stackslib/src/chainstate/burn/operations/stack_stx.rs)

### Summary
`PreStxOp::parse_from_tx` sets `output` from the first Bitcoin output's raw address bytes with no signature/ownership check, and `StackStxOp::from_tx` propagates that address as `sender` based only on a UTXO-spend linkage (`vout==1`), not proof of key ownership. `process_stacking_ops` then calls pox-4 `stack-stx` with `tx-sender` forced to this attacker-chosen address, and pox-4's `stack-stx` never authenticates `tx-sender`, only the unrelated `signer-key`.

### Finding Description
Equality claimed broken: **STX locked by the applied StackStxOp == STX actually authorised by the named sender (V)**. This is false whenever V never used a private key in either Bitcoin transaction.

Attack flow:
1. Attacker crafts a `PreStxOp` Bitcoin tx with two outputs: output[0] = V's Stacks-address-equivalent hash160 (chosen freely, no key needed), output[1] = attacker-controlled change funding the follow-up. `PreStxOp::parse_from_tx` accepts this and records `output = V` [9](#0-8) .
2. Attacker crafts a `StackStxOp` whose `input[0]` spends `PreStxOp`'s `vout=1` (satisfying `get_sender_txid`'s vout==1 check, using only the attacker's own key controlling that UTXO) [2](#0-1) .
3. `burnchain.rs` resolves `sender = &pre_stack_stx.output` (= V) and calls `StackStxOp::from_tx(..., sender=V, ...)`, producing `StackStxOp{ sender: V, reward_addr: <attacker's own address>, stacked_ustx, ... }` [3](#0-2) .
4. `process_stacking_ops` executes pox-4's `stack-stx` with `tx-sender = V` [5](#0-4) .
5. `stack-stx` in pox-4 checks only `V`'s balance and stacking/delegation state — it never asserts V consented; `signer-sig` is passed as `none` and the `signer-key` authorization path only validates the (unrelated) signer key, not V [7](#0-6) .

No existing guard (`check-caller-allowed`, `consume-signer-key-authorization`, balance check) verifies that V authorized the stacking action itself.

### Impact Explanation
V's unlocked STX (up to their full balance) is forcibly locked for `num_cycles` reward cycles without consent — a High-severity "unsigned stacking action" / "temporary freezing of staked funds." The attacker additionally redirects PoX BTC reward payouts for the slot backed by V's coerced STX to an address of the attacker's choosing. This is repeatable against any address with sufficient unlocked balance, for the cost of two Bitcoin transactions (a `PreStxOp` and a `StackStxOp`) with negligible attacker-owned UTXO value required beyond fees.

### Likelihood Explanation
Preconditions: V holds `>= stacked_ustx` unlocked STX and is not currently stacked/delegating; V's Stacks address's hash160 is public knowledge (trivial to obtain). No PoX-4 membership state, prepare-phase timing, or reward-cycle-start condition blocks this — it is a straightforward two-transaction burnchain construction available to any Bitcoin/Stacks user, fully repeatable per victim per cycle.

### Recommendation
Require an on-chain, cryptographically verifiable authorization from the named `sender`/stacker address before honoring burnchain-originated `StackStxOp`s — e.g., require a `stacker-sig` analogous to `signer-sig`, verified against V's Stacks public key, before `process_stacking_ops` is allowed to call `stack-stx` with `tx-sender = sender`. Alternatively, restrict burnchain-native stacking (`PreStxOp`/`StackStxOp`) so that `sender` must be provably derivable from the same key(s) that signed the Bitcoin inputs (e.g., match the PreStxOp `output` hash160 against a Bitcoin pubkey supplied/verified in the same transaction), instead of trusting an arbitrary output field.

### Proof of Concept
Rust integration test plan (mirroring existing tests such as `stackslib/src/burnchains/tests/db.rs` and `stacks-node/src/tests/neon_integrations.rs`):
1. Initialize chain with two Stacks keys: `attacker_sk` (funds attacker-controlled Bitcoin UTXOs) and victim address `V` with balance `B >= stacked_ustx`, but never derive/use a private key for `V` in any Bitcoin signing operation.
2. Submit a `PreStxOp` Bitcoin transaction, signed only with `attacker_sk`'s Bitcoin key, whose first output's scriptPubKey encodes `V`'s hash160 (not attacker's), and second output funds the attacker's own change address.
3. Submit a `StackStxOp` Bitcoin transaction whose `input[0]` spends `vout=1` of the PreStxOp tx (signed only by attacker's Bitcoin key), with `reward_addr` pointing to an attacker-controlled address, `stacked_ustx <= B`.
4. Mine both, allow `process_stacking_ops` to run.
5. Assert: `stacking-state` map in pox-4 for principal `V` is populated (`get-stacker-info V` returns `Some`), and `stx-account V`'s locked amount == `stacked_ustx`, **despite `V`'s private key never being used to sign anything** — breaking the equality "STX locked for V == STX V authorized," which should be `0` but is `stacked_ustx`.
6. Additionally assert PoX reward-set entry's `pox-addr`/payout target equals the attacker's chosen `reward_addr`, not any address associated with `V`.
