### Title
Floating-point precision loss in fixed-denomination asset cap validation allows sum mismatch with declared cap - (File: `validation.js`, `validation_utils.js`)

### Summary
`validateAssetDefinition` in `validation.js` computes the total capacity of a fixed-denomination asset by summing `count_coins * denomination` for every denomination entry using native JavaScript number arithmetic, then compares the sum to the declared `cap` with strict equality. `count_coins` is validated only with `isPositiveInteger`, which has no upper bound, while `denomination` is separately capped at `constants.MAX_CAP`. Multiplying an unbounded `count_coins` by a `denomination` that can itself already be as large as `MAX_CAP` easily exceeds `Number.MAX_SAFE_INTEGER` (2^53), causing the product—and the accumulated `total_cap_from_denominations`—to silently lose precision, exactly the same class of "insufficient intermediate value precision" defect described in the StableSwap report (there, `Uint256` intermediates overflowed/rounded incorrectly for large legitimate values; here, native JS doubles do the same).

### Finding Description
In `validateAssetDefinition`: [1](#0-0) 
each denomination's `count_coins` is checked only with `isPositiveInteger(denomInfo.count_coins)`: [2](#0-1) 
`isInteger` merely checks `Math.floor(value) === value`, which is trivially true for any large double (even values far beyond `Number.MAX_SAFE_INTEGER`, since such doubles are always "integral" in floating-point representation even though they no longer represent every integer exactly). Meanwhile `denomInfo.denomination` is bounded only by `constants.MAX_CAP`: [3](#0-2) 
The multiplication `denomInfo.count_coins * denomInfo.denomination` and the running sum `total_cap_from_denominations` are then compared against the asset's declared `payload.cap` with strict equality: [4](#0-3) 
Because IEEE-754 doubles only guarantee exact integer representation up to 2^53 (~9.007e15), and `denomination` alone can already approach `MAX_CAP`, an issuer can choose a `count_coins`/`denomination` pair whose true product is far larger than any legitimate declared cap, yet whose double-precision-rounded value happens to equal `payload.cap` (a value that is itself bounded and therefore exactly representable). The check `payload.cap !== total_cap_from_denominations` then passes even though the true mathematical sum of `count_coins * denomination` across all declared denominations is not equal to `cap`.

The identical unbounded `count_coins`/`denomination` validation pattern (with formula alternatives) also appears in the AA-definition path for nested asset definitions, i.e. an AA author can define an asset with the same flaw: [5](#0-4) 

### Impact Explanation
The declared `cap` combined with the per-denomination `count_coins` limits is the mechanism that bounds the total possible supply of a fixed-denomination (indivisible) asset — actual issuance is enforced by validating individual issue inputs against these declared denominations/serial numbers. If the consensus-critical cap-consistency check can be satisfied via floating-point rounding despite the true denomination sum exceeding the declared `cap`, an asset issuer can create a fixed-denomination asset that is accepted network-wide as capped at `cap`, while the enforced per-denomination `count_coins` limits actually permit issuing strictly more total value than `cap`. This is a concrete supply-inflation vector reachable by any unprivileged asset issuer through a standard asset-definition message (or via an AA's nested asset definition), not a peer/node-trust issue.

### Likelihood Explanation
Triggering the mismatch requires no special privileges — any address can post an `asset` message (or any AA author can embed a nested asset definition) with a `denominations` array. The attacker only needs to pick `count_coins` and `denomination` values whose product, once rounded to a double, coincidentally equals a chosen legal `cap` value (both bounded and exactly representable), which is a straightforward search/construction problem, not a probabilistic one. This makes the likelihood high once the arithmetic weakness is understood.

### Recommendation
Perform the `count_coins * denomination` multiplication and the running total using arbitrary-precision integer arithmetic (e.g. `BigInt`) instead of native JS numbers, and compare the exact sum to `payload.cap` using that arbitrary-precision result. Additionally bound `count_coins` similarly to `denomination` (e.g., relative to `MAX_CAP`) so that intermediate products cannot exceed safe magnitudes in the first place. Apply the same fix to the analogous nested-asset-definition validation path in `aa_validation.js`.

### Proof of Concept
Conceptually (values illustrative, subject to the exact value of `constants.MAX_CAP`):
1. Choose `denomination_1 = D` close to `MAX_CAP` and `count_coins_1 = N` such that `D * N` computed as a double rounds to some representable integer `cap`, while the true integer product `D * N` (computed exactly) is materially larger than `cap`.
2. Submit an asset definition with `fixed_denominations: true`, a single denomination `{denomination: D, count_coins: N}`, and `cap = <the rounded value>`.
3. `validateAssetDefinition` accepts the definition because `payload.cap !== total_cap_from_denominations` evaluates to `false` (floating point equality by coincidence), even though `count_coins * denomination` truly is not equal to `cap`.
4. The asset issuer can then issue indivisible-denomination units up to the true (uncapped-by-rounding) `count_coins` limit for that denomination, exceeding the nominal `cap` that other nodes/wallets believe bounds the asset's total supply.
