### Title
Missing cosigner-authorization check in "sign" message handler allows any paired device to trigger a spending signature-request for a local multisig address - ([File: wallet.js])

### Summary
The CVE-2018-19569 bug class is "a credential/session that should be limited in scope instead grants broader, unauthorized access." In `ocore`, the analogous authorization gap is in the `"sign"` message handler in `handleMessageFromHub()`: when the target address is local (`ifLocal`), the code that should verify the sending device is an actual cosigner of the wallet is explicitly commented out, so any correspondent device can invoke this path for any address/signing_path pair it knows about.

### Finding Description
`handleMessageFromHub` processes the `"sign"` subject sent by *any* paired device (from_address is derived only from the device's pubkey/signature, not from wallet membership) [1](#0-0) . After validating the unit's structure, it calls `findAddress(body.address, body.signing_path, ...)` and, in the `ifLocal` branch, immediately proceeds to fire `signing_request` (or push the joint into online-joint validation) — the actual cosigner check has been commented out: [2](#0-1) 

The comment states: *"the commented check would make multilateral signing impossible"* — i.e., the check `SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?` that would confirm `from_address` is a legitimate cosigner of the wallet owning `body.address` was intentionally removed to support the "multilateral signing" use case (different addresses/parties signing the same message, e.g., contracts). However, this means **any known correspondent device**, not just genuine multisig cosigners, can submit a `sign` request referencing one of the user's own local addresses and signing paths, causing the wallet to build/validate an attacker-supplied unsigned unit and raise a `signing_request` event with arbitrary payment outputs embedded inside `objUnit`.

By contrast, the `ifRemote` branch (forwarding a signing offer to another device) *does* still enforce `other_device_addresses.includes(from_address)` [3](#0-2) , showing the authors know such membership checks are needed — the `ifLocal` branch is the outlier where the check was stripped.

### Impact Explanation
For interactive (GUI) wallets, the missing check reduces to a UX/social-engineering risk: an untrusted correspondent can push crafted "please sign this payment" dialogs to a victim referencing the victim's own address, with attacker-chosen outputs (subject to the payment/output validations already present), potentially tricking the user into signing away funds via a plausible-looking confirmation prompt they did not initiate.

For headless/automated signers (`getSigner()` in `wallet.js`, used by `headless_wallet.js`-style deployments) the same `findAddress`/`ifLocal` path is used to actually produce signatures without a human confirmation dialog [4](#0-3) . If a headless wallet operator has any correspondent device paired at all (e.g., for chat/notification purposes) that is not a genuine cosigner of a given multisig address, that correspondent can still cause a `"sign"` request to reach `findAddress`/`ifLocal`, potentially producing a valid signature or a confirmation-eliciting event for a unit it did not legitimately construct — the root authorization boundary (`from_address` must be a listed cosigner) that would normally gate this is not enforced by the network-facing handler itself, only implicitly by whichever UI layer chooses to display a warning.

This maps to unauthorized-spending/fund-loss impact class described in the "Validate" instructions (concrete unauthorized spending or AA/wallet fund loss), since the check that would enforce "only real cosigners of this address may request a signature" is missing at the protocol/handler level.

### Likelihood Explanation
Requires only that an attacker be a paired correspondent device of the victim (a normal, low-friction interaction achievable via pairing links, textcoin chat, etc. — not a privileged or hub-level position), and that the victim have at least one multisig/shared address. No hub or peer compromise is needed; this is reachable exactly by "a paired device" per the analog scope in the rules.

### Recommendation
Restore (or replace with an equivalent) the cosigner-membership check in the `ifLocal` branch of the `"sign"` case before emitting `signing_request` or validating/joining the unit — verify `from_address` is listed as a cosigner/signer for `body.address`'s wallet (or the relevant shared-address signing path) in a way compatible with legitimate multilateral-signing use cases (e.g., check `wallet_signing_paths`/`shared_address_signing_paths`/`extended_pubkeys` membership, or an explicit multilateral-signing allow-list) rather than removing the authorization boundary entirely.

### Proof of Concept
1. Attacker device pairs with victim's wallet (normal, unprivileged pairing flow) so it becomes a `correspondent_devices` entry.
2. Attacker sends a hub message to the victim with `subject: "sign"`, `body: {address: <victim's local multisig address>, signing_path: "r", unsigned_unit: {...attacker-crafted payment outputs...}}`.
3. `handleMessageFromHub` validates structural fields, calls `findAddress`, hits `ifLocal`, and — because the cosigner check is commented out — proceeds directly to emit `signing_request`/validate the joint, regardless of whether the attacker device is an actual cosigner of that address [5](#0-4) .
4. Depending on the wallet's UI/automation, this can result in a misleading confirmation prompt or (for automated signers) a signature being produced for a unit the attacker controls the content of.
