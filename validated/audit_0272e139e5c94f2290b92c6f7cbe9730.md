### Title
`ERC20Transactor` treats a non-`bool`/no-return `transfer()` result as XCM failure while the underlying ERC-20 balance mutation has already succeeded on-chain - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
The Halborn report flags a Solidity `claim()` using raw `IERC20.transfer()` that reverts for tokens (USDT-style) whose `transfer` doesn't return a `bool`. The Polkadot SDK analog is `ERC20Transactor::withdraw_asset_with_surplus` / `deposit_asset_with_surplus`, which call an arbitrary ERC-20-style `pallet-revive` contract's `transfer()` via `bare_call` and then require the ABI-encoded return data to decode as `bool` with `IERC20::transferCall::abi_decode_returns_validate`. If the token contract mutates balances but returns no data (or non-bool data), decoding fails and the whole instruction is treated as `XcmError::FailedToTransactAsset`, even though the contract's internal transfer already executed. [1](#0-0) 

### Finding Description
`IsLocalAccountKey20` matches **any** local `Location(0, [AccountKey20{..}])`, so any address can be used as an XCM "asset id" routed to `ERC20Transactor`, with no allow-list restricting which contracts are treated as ERC-20s: [2](#0-1) 

In `withdraw_asset_with_surplus`, the transactor calls the target contract's `transfer(checking_account, amount)` via `pallet_revive::Pallet::<T>::bare_call`. This is a real, state-mutating call — if the target contract implements `_update`/`_transfer` semantics that move balances unconditionally (as in the repo's own `MyTokenFake.sol` test fixture, which mutates balances but returns a `uint256` instead of `bool`), the on-chain balance transfer succeeds regardless of what is returned: [3](#0-2) 

But the transactor only accounts for success by decoding the return data as a `bool`: [4](#0-3) 

If decoding fails (empty/short returndata, as with real-world non-standard ERC-20s like USDT/BNB, or a wrong-typed return), the function returns `Err(XcmError::FailedToTransactAsset(...))` without crediting `AssetsInHolding`. The repo's own tests confirm this exact scenario is reachable and currently just errors the whole XCM program, without asserting that the already-mutated on-chain ERC-20 balance is restored: [5](#0-4) [6](#0-5) 

The XCM executor does have a `TransactionalProcessor`/`with_storage_layer` mechanism that rolls back the `WithdrawAsset` instruction and the holding register on error: [7](#0-6) [8](#0-7) 

This rollback relies on `frame_support::storage::with_transaction`, which correctly reverts *pallet storage* changes made through the runtime's transactional storage layers — including the storage written by `pallet_revive::bare_call` (contract storage writes go through the same overlay), **provided** `bare_call` doesn't commit outside of that transactional context (e.g. via `frame_support::storage::transactional::with_storage_layer` misuse, or an inner call that force-commits). I could not fully verify from static inspection alone whether `pallet_revive::Pallet::<T>::bare_call`'s internal storage meter / contract execution always stays nested inside the outer `with_transaction` layer for every code path (e.g., events already deposited via `env.deposit_event` are typically not rolled back by storage transactions since they use `frame_system::Pallet::deposit_event`, which is deliberately excluded from transactional rollback in FRAME) — meaning a spurious `Transfer` event could still be emitted for a transfer that is later rolled back, creating an observable inconsistency for off-chain indexers relying on events, distinct from a direct balance-loss bug.

### Impact Explanation
Assuming the storage-layer rollback is fully effective (most likely, since `WithdrawAsset`/`DepositAsset` are wrapped in `Config::TransactionalProcessor::process`), the primary externally-visible impact is a **denial-of-service on legitimate transfers of any real-world ERC-20 contract that doesn't strictly return `bool`** (e.g., real USDT bytecode registered as an `AccountKey20` asset on Asset Hub). Any user attempting to move such a token via XCM (`pallet_xcm::execute`/`limited_reserve_transfer_assets`, etc.) would have their otherwise-valid XCM program fail deterministically, even though no privileged actor or malicious input was involved — a self-DoS baked into the transactor design, not an attacker exploiting another party. This is a Medium-severity correctness/compatibility issue analogous to the original report (frozen functionality vs. loss of funds), assuming rollback holds. If, contrary to my expectation, `bare_call`'s internal balance mutation and/or events are **not** fully covered by the outer transactional rollback for some execution path, the impact escalates to real fund loss (tokens moved to the checking account with no compensating holding credit and no restoration) — this specific scenario I was not able to conclusively confirm or rule out with the available read-only tools.

### Likelihood Explanation
Reachability requires no privilege: any signed account can register/use an `AccountKey20` contract as an XCM asset id (`IsLocalAccountKey20` matches unconditionally) and call `pallet_xcm::execute` with a `withdraw_asset`/`deposit_asset` targeting that contract. Deploying a "fake ERC20" via `pallet-revive` is a standard permitted operation. The repository's own test suite (`smart_contract_does_not_return_bool_fails`, `smart_contract_not_erc20_will_error`) demonstrates the exact reachable failure path already exists and is exercised in CI, confirming high likelihood of triggering the error condition; what remains uncertain is only the depth/completeness of the storage rollback guarantee across all `bare_call` side effects.

### Recommendation
Align `ERC20Transactor`'s return-handling with the OpenZeppelin `SafeERC20`-style pattern referenced in the original report: treat a call that reverts as failure, but treat a call that succeeds with **empty** return data as success (per EIP-20 compatibility conventions), only requiring exact `bool` decoding when return data is non-empty. Additionally, add an explicit test asserting that the on-chain ERC-20 balance (and any emitted events) are fully restored to their pre-instruction state when `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` return an error, closing the uncertainty around whether `bare_call`'s internal effects are fully covered by `Config::TransactionalProcessor`'s rollback.

### Proof of Concept
Not independently executed; relying on existing repository test evidence. The repo already contains failing-path tests (`smart_contract_does_not_return_bool_fails`, `smart_contract_not_erc20_will_error`) at [5](#0-4)  and [6](#0-5)  that assert `PolkadotXcm::execute(...).is_err()` for a non-bool-returning contract, confirming the guard triggers as described; these tests do **not** assert on-chain balance state post-failure, so full fund-safety could not be verified via static reading alone. A complete PoC would extend these tests with balance assertions on the ERC-20 contract's internal storage before/after the failed XCM to confirm whether the transfer is truly rolled back or silently persists.

	/// Execute `f` inside a transactional context that backs up and restores `holding` and
	/// `fees` on failure.
	fn transactional_process(
		&mut self,
		f: impl FnOnce(&mut Self) -> Result<(), XcmError>,
	) -> Result<(), XcmError> {
		self.transactional_process_with_custom_rollback(f, |_| {})
	}

	/// Like [`Self::transactional_process`], but also calls `on_rollback` when the
	/// transaction is rolled back.
	///
	/// NOTE: holding and fees registers are already automatically rolled back. Custom handler
	/// is for _extra_ rollback logic.
	fn transactional_process_with_custom_rollback(
		&mut self,
		f: impl FnOnce(&mut Self) -> Result<(), XcmError>,
		on_rollback: impl FnOnce(&mut Self),
	) -> Result<(), XcmError> {
		let mut backup_holding = BackupAssetsInHolding::safe_backup(&self.holding);
		let mut backup_fees = BackupAssetsInHolding::safe_backup(&self.fees);
		let result = Config::TransactionalProcessor::process(|| f(self));
		if Config::TransactionalProcessor::IS_TRANSACTIONAL && result.is_err() {
			backup_holding.restore_into(&mut self.holding);
			backup_fees.restore_into(&mut self.fees);
			on_rollback(self);
		}
		result
	}

	/// Process a single XCM instruction, mutating the state of the XCM virtual machine.
	fn process_instruction(
		&mut self,
		instr: Instruction<Config::RuntimeCall>,
	) -> Result<(), XcmError> {
		tracing::trace!(
			target: "xcm::process_instruction",
			instruction = ?instr,
			"Processing instruction",
		);

		match instr {
			WithdrawAsset(assets) => {
				self.ensure_can_subsume_assets(assets.len())?;
				Config::TransactionalProcessor::process(|| {
					let origin = self.origin_ref().ok_or(XcmError::BadOrigin)?;
					let mut total_surplus = Weight::zero();
					let mut withdrawn = AssetsInHolding::new();
					// Take `assets` from the origin account (on-chain)...
					for asset in assets.inner() {
						let (credit, surplus) = Config::AssetTransactor::withdraw_asset_with_surplus(
							asset,
							origin,
							Some(&self.context),
						)?;
						withdrawn.subsume_assets(credit);
						// If we have some surplus, aggregate it.
						total_surplus.saturating_accrue(surplus);
					}
					// ...and place into holding.
					self.holding.subsume_assets(withdrawn);
					// Credit the total surplus.
					self.total_surplus.saturating_accrue(total_surplus);
					Ok(())

use frame_support::storage::{with_transaction, TransactionOutcome};
use sp_runtime::DispatchError;
use xcm::latest::prelude::*;
use xcm_executor::traits::ProcessTransaction;

/// Transactional processor implementation using frame transactional layers.
pub struct FrameTransactionalProcessor;
impl ProcessTransaction for FrameTransactionalProcessor {
	const IS_TRANSACTIONAL: bool = true;

	fn process<F>(f: F) -> Result<(), XcmError>
	where
		F: FnOnce() -> Result<(), XcmError>,
	{
		with_transaction(|| -> TransactionOutcome<Result<_, DispatchError>> {
			let output = f();
			match &output {
				Ok(()) => TransactionOutcome::Commit(Ok(output)),
				_ => TransactionOutcome::Rollback(Ok(output)),
			}
		})
		.map_err(|error| {
			tracing::debug!(target: "xcm::transactional", ?error, "Failed to process XCM transaction");
			XcmError::ExceedsStackLimit
		})?
	}
}
