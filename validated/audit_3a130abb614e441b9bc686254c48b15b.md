### Title
Denial of Service via unbounded `chains` array in `private_payments` device message - ([File: wallet.js])

### Summary
`handlePrivatePaymentChains` in `wallet.js` accepts an attacker/counterparty-controlled `body.chains` array from a paired device (`private_payments` message) and processes every chain and every element of every chain sequentially, without any limit on the number of chains or the length of each chain, causing unbounded, expensive per-element DB work (BEGIN/COMMIT transactions, mutex locks, multiple queries per element) on the receiving node/wallet.

### Finding Description
The device-message handler in `wallet.js` dispatches `private_payments` bodies directly to `handlePrivatePaymentChains`: [1](#0-0) 

`handlePrivatePaymentChains` validates only that `chains` is a non-empty array and that each chain element has the expected shape — there is no bound on `arrChains.length`, nor on the length of each individual chain (`c.length`): [2](#0-1) 

It then iterates every chain with `async.eachSeries`, calling `network.handleOnlinePrivatePayment` for each one: [3](#0-2) 

Each chain, once accepted, is validated element-by-element via `privatePayment.validateAndSavePrivatePaymentChain`, which performs a DB connection checkout, `BEGIN`/`COMMIT`, and a duplicate-check query per call: [4](#0-3) 

For indivisible (fixed-denomination) private assets, the actual chain elements are validated one at a time with `async.forEachOfSeries`, each doing multiple queries (`spend_proofs` lookup, `graph.determineIfIncluded` DAG-inclusion walk, and a full `validation.validatePayment` call) with no cap on `arrPrivateElements.length`: [5](#0-4) [6](#0-5) 

This is structurally analogous to the Discourse bug class: a party first "creates many replies" — here, crafts a message with an arbitrarily large `chains` array and/or arbitrarily long chains — and then the victim is forced to "fetch/process them all at once" in one message, with no restriction on the reply/element count.

### Impact Explanation
A paired device (a counterparty who is allowed to send private payments, e.g. any correspondent who has previously exchanged pairing info) can send a single `private_payments` message containing a very large number of chains and/or very long chains. The receiving wallet will serially open DB transactions, take the `handleJoint` mutex, and run `graph.determineIfIncluded` and full payment validation for every element, all within the same message-handling flow. This ties up the receiver's single-threaded DB/mutex-bound processing, delaying or blocking legitimate unit/payment processing and effectively degrading or denying service to the victim's wallet/node — reachable from an already-established private-payment counterparty without needing to gain any special privilege.

### Likelihood Explanation
High likelihood: the sender only needs to be a paired device/correspondent that is permitted to exchange private payments (a normal, low-privilege capability in the private-payment attack surface named in scope). No cryptographic validity of the innermost payment content is required to inflict the cost, because processing (query lookups, mutex acquisition, transaction start/rollback) happens before/independent of final success — the attacker can supply malformed-but-structurally-valid chain elements to keep exercising the workflow.

### Recommendation
Add explicit upper bounds, enforced before any processing begins:
- Limit the number of chains accepted per `private_payments` message (`arrChains.length`).
- Limit the length of each individual chain (`c.length`) in `handlePrivatePaymentChains`.
- Consider adding an overall size/complexity cap check (similar to `string_utils.isTooBigObj`) on the whole `body.chains` payload before invoking `network.handleOnlinePrivatePayment`, and rate-limit/queue processing per sending device.

### Proof of Concept
1. Attacker device pairs/correspondents with victim wallet (normal private-payment capability).
2. Attacker sends a `private_payments` device message where `body.chains` is an array of, e.g., tens of thousands of syntactically-valid-looking chains (or a few chains with tens of thousands of elements each), each satisfying the minimal shape checks in `handlePrivatePaymentChains` (non-empty objects/arrays for `unit`, `payload.asset`, `payload.inputs`, `payload.outputs`).
3. Victim's `handleMessageFromHub` → `handlePrivatePaymentChains` iterates all chains serially, invoking `network.handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain` → (`indivisible_asset.js`/`divisible_asset.js`) `validateAndSavePrivatePaymentChain`, each doing DB transactions, mutex locks, and multi-query validation per element, with no maximum count anywhere in the path — degrading the victim's node responsiveness.

**Note on verification limits:** I was not able to inspect `divisible_asset.js`'s equivalent `validateAndSavePrivatePaymentChain` implementation in this session (only the indivisible-asset path was retrieved), so the exact per-element cost for divisible private assets is not fully confirmed here; however the `private_payment.js` dispatcher shows the same unbounded array is routed to it identically, and the absence of any max-length check applies to both paths equally.

function parsePrivatePaymentChain(conn, arrPrivateElements, callbacks){
	var bAllStable = true;
	var issuePrivateElement = arrPrivateElements[arrPrivateElements.length-1];
	if (!issuePrivateElement.payload || !issuePrivateElement.payload.inputs || !issuePrivateElement.payload.inputs[0])
		return callbacks.ifError("invalid issue private element");
	var asset = issuePrivateElement.payload.asset;
	if (!asset)
		return callbacks.ifError("no asset in issue private element");
	var denomination = issuePrivateElement.payload.denomination;
	if (!denomination)
		return callbacks.ifError("no denomination in issue private element");
	async.forEachOfSeries(
		arrPrivateElements,
		function(objPrivateElement, i, cb){
			if (!objPrivateElement.payload || !objPrivateElement.payload.inputs || !objPrivateElement.payload.inputs[0])
				return cb("invalid payload");
			if (!objPrivateElement.output)
				return cb("no output in private element");
			if (objPrivateElement.payload.asset !== asset)
				return cb("private element has a different asset");
			if (objPrivateElement.payload.denomination !== denomination)
				return cb("private element has a different denomination");
			var prevElement = null; 
			if (i+1 < arrPrivateElements.length){ // excluding issue transaction
				var prevElement = arrPrivateElements[i+1];
				if (prevElement.unit !== objPrivateElement.payload.inputs[0].unit)
					return cb("not referencing previous element unit");
				if (prevElement.message_index !== objPrivateElement.payload.inputs[0].message_index)
					return cb("not referencing previous element message index");
				if (prevElement.output_index !== objPrivateElement.payload.inputs[0].output_index)
					return cb("not referencing previous element output index");
			}
			validatePrivatePayment(conn, objPrivateElement, prevElement, {
				ifError: cb,
				ifOk: function(bStable, input_address){
					objPrivateElement.bStable = bStable;
					objPrivateElement.input_address = input_address;
					if (!bStable)
						bAllStable = false;
					cb();
				}
			});
		},
		function(err){
			if (err)
				return callbacks.ifError(err);
			callbacks.ifOk(bAllStable);
		}
	);
}
