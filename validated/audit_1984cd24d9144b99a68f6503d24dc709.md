### Title
Webhook signature is verified against the organization named in an untrusted field, while handlers act on a different untrusted field naming the target repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to HMAC-verify the raw webhook body against by reading `repository.owner.login` (or `organization.login`) straight out of the unauthenticated JSON payload, then all event handlers separately pull `repository.full_name` out of that same unauthenticated payload to decide which `Repository`/`Stack` to mutate. Nothing ties these two fields together, so the "organization whose secret authenticated the request" and "repository that gets written to" are never checked for equality.

### Finding Description
`verify_signature` computes `repository_owner` from the payload and fetches that organization's `GithubApp`/secret to validate `X-Hub-Signature`: [1](#0-0) [2](#0-1) 

Once the signature check passes (i.e., HMAC-SHA1 of the *entire raw body* matches using organization `repository_owner`'s webhook secret), `create` dispatches the full payload, unmodified, to every registered handler for the event: [3](#0-2) 

Handlers never look at `repository_owner`. Instead, the base `Handler` class (and every subclass) resolves the target `Repository` from a *different* payload field, `repository.full_name`: [4](#0-3) 

This is used by `PushHandler` to sync stacks: [5](#0-4) 

and by every pull-request handler (open/close/reopen/label/etc.) to locate the repository whose review stacks get archived, unarchived or created: [6](#0-5) [7](#0-6) 

Because `Shipit.github(organization:)` raises `Shipit::GithubOrganizationUnknown` for unrecognized organizations, the engine's whole security model assumes multiple distinct GitHub Apps/orgs can be configured, each with its own `webhook_secret` (documented per-organization in `docs/setup.md`). A user/administrator who legitimately controls a Shipit-connected organization ("Org A") knows Org A's `webhook_secret` (it's visible in their own GitHub App settings). Using that secret they can HMAC-sign an arbitrary raw JSON body where `repository.owner.login = "OrgA"` (so `verify_signature` passes using Org A's key) but `repository.full_name = "OrgB/private-repo"` (so the handler acts on Org B's repository/stacks, which the attacker has no access to). The two identifiers are never required to agree anywhere in the request path.

### Impact Explanation
This breaks the binding: `repository_owner` (the identity that authenticated the webhook via a valid HMAC) must equal the owner of `repository.full_name` (the identity whose data is mutated). By forging a body signed with one organization's secret but naming another organization's repository, an attacker who is a legitimate admin/webhook-secret-holder of Org A can trigger `stack.sync_github`, archive/unarchive/create review stacks, and otherwise mutate Repository/Stack/PullRequest state that belongs to Org B, a repository they have zero authorization over. This is an unauthorized cross-repository write across GitHub-organization trust boundaries in a self-hosted, multi-organization Shipit deployment.

### Likelihood Explanation
Requires only that the attacker administers (or otherwise knows the webhook secret of) any single GitHub App/organization already configured in the Shipit instance — no repository write access, ApiClient token, or session on the target organization is needed. In any Shipit deployment serving more than one organization (explicitly supported per `Shipit.github(organization:)` and documented per-org secrets), this is directly reachable by an unprivileged outsider to the victim org.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), enforce that the organization derived for signature verification (`repository_owner`) matches the owner segment of `repository.full_name` used by handlers, rejecting the request (422) on mismatch. More robustly, resolve the target repository/organization once (from a single trusted field) and use that same value both to select the verification secret and to scope all handler lookups, rather than trusting two independently-read fields from the same unauthenticated body.

### Proof of Concept
1. Attacker is a legitimate admin of "OrgA", which has its own GitHub App installed on this Shipit instance with webhook secret `S_A` (visible to them in GitHub App settings).
2. Attacker crafts a `push` payload: `{"ref": "refs/heads/main", "after": "<sha>", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/private-repo"}}`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_A, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` derives `repository_owner = "OrgA"` [2](#0-1) , fetches OrgA's `GithubApp`, and the signature validates successfully since it was computed with `S_A`.
5. `create` dispatches to `PushHandler`, which resolves stacks via `repository_name = payload.dig('repository', 'full_name')` = `"OrgB/private-repo"` [4](#0-3)  and triggers `stack.sync_github(expected_head_sha: ...)` for OrgB's stack [5](#0-4) , an organization the attacker has no legitimate access to.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified
