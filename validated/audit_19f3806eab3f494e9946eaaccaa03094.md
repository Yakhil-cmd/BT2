### Title
`consolidatedNode.Split` Division-by-Zero Panic Corrupts Proposer Reward Distribution on Prague Blocks — (`kaiax/staking/staking_info.go`)

---

### Summary

`consolidatedNode.Split` in `kaiax/staking/staking_info.go` computes a proportional split of the proposer's block reward between a validator's CNStaking address and its Consensus-Liquidity (CL) pool. It divides by `totalAmount = c.StakingAmount + c.CLStakingInfo.CLStakingAmount` with no guard against zero. Both fields are `uint64` values expressed in whole-KAIA units (integer-divided by `params.KAIA`), so any validator whose CNStaking balance **and** CL-pool balance are each below 1 KAIA produces `totalAmount = 0`. Go's `(*big.Int).Div` panics on a zero divisor. The panic fires inside `specWithProposerAndFunds` / `specWithProposerAndFundsFlex`, which are called unconditionally from `getDeferredRewardFullKore` / `getDeferredRewardFullFlex` → `FinalizeState` for every block after the Prague hardfork. Every node that attempts to execute or validate such a block crashes.

---

### Finding Description

**Vulnerable function** — `kaiax/staking/staking_info.go`, `consolidatedNode.Split`:

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }
    var (
        cnAmountBig = big.NewInt(int64(c.StakingAmount))
        clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
        totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
    )
    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount = clAmount.Div(clAmount, totalAmount)   // ← panics when totalAmount == 0
    cnAmount := big.NewInt(0).Sub(amount, clAmount)
    return cnAmount, clAmount
}
``` [1](#0-0) 

The only guard is `c.CLStakingInfo == nil`. There is **no** check that `totalAmount > 0` before the division.

Any validator whose CNStaking contract holds **< 1 KAIA** yields `StakingAmount = 0`. Any CL pool with **< 1 KAIA** yields `CLStakingAmount = 0`. Both can be zero simultaneously. `consolidateNodes` attaches a non-nil `CLStakingInfo` to the CN regardless of the CL amount: [6](#0-5) 

There is no filter on `CLStakingAmount > 0` before attaching the struct.

---

### Impact Explanation

When the block proposer is a validator registered in both AddressBook and CLRegistry with sub-1-KAIA balances in both contracts, every node executing `FinalizeState` for that block hits the `big.Int.Div` panic. Because `FinalizeState` is executed by all validators during block processing (not only by the proposer), the panic is network-wide for that block. The result is:

- **Consensus divergence / network halt**: all honest nodes crash or fail to finalize the block; the chain cannot advance past that block number.
- **Incorrect reward accounting**: even if the panic were replaced by a silent zero-division return, the CL pool would receive 0 KAIA and the CN address would absorb the entire proposer reward, silently misrouting KAIA.

Both outcomes match the allowed impact gate: *invalid state transition* and *consensus divergence on honest nodes*, and *incorrect reward distribution affecting KAIA*.

---

### Likelihood Explanation

- Prague hardfork must be active (already planned/deployed on Kaia mainnet).
- A validator must be registered in AddressBook **and** in CLRegistry.
- Both the CNStaking contract balance and the CL pool balance must be below 1 KAIA at the staking-info source block.
- The validator must be selected as block proposer (round-robin or weighted-random with non-zero weight from the validator set, independent of staking amount).

In the permissioned validator set, a validator can be in AddressBook with a CNStaking contract that has been drained or never funded above 1 KAIA. Registering in CLRegistry with a freshly-deployed pool (0 balance) is straightforward. The combination is realistic and requires no majority collusion.

---

### Recommendation

Add a zero-guard in `consolidatedNode.Split` before dividing:

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }
    cnAmountBig := big.NewInt(int64(c.StakingAmount))
    clAmountBig := big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
    totalAmount := new(big.Int).Add(cnAmountBig, clAmountBig)

    // Guard: if total staking is zero, all reward goes to CN (no CL split).
    if totalAmount.Sign() == 0 {
        return amount, big.NewInt(0)
    }

    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount.Div(clAmount, totalAmount)
    cnAmount := new(big.Int).Sub(amount, clAmount)
    return cnAmount, clAmount
}
```

Additionally, consider filtering out CLStakingInfo entries with `CLStakingAmount == 0` in `consolidateNodes`, or enforcing a minimum CL registration amount in the CLRegistry contract, to prevent the degenerate state from arising in the first place.

---

### Proof of Concept

1. Deploy a Kaia node with Prague hardfork active.
2. Register validator `V` in AddressBook with a CNStaking contract holding 0.5 KAIA (< 1 KAIA → `StakingAmount = 0` after integer division).
3. Register `V`'s node ID in CLRegistry pointing to a CL pool with 0.3 KAIA (< 1 KAIA → `CLStakingAmount = 0`).
4. Wait for `V` to be selected as block proposer (round-robin policy guarantees this).
5. When block `N` is proposed by `V`, every node calls `FinalizeState` → `getDeferredRewardFullKore` → `specWithProposerAndFunds`:
   - `cn.RewardAddr == config.Rewardbase` ✓ (proposer match)
   - `cn.CLStakingInfo != nil` ✓ (CL registered)
   - `cn.StakingAmount = 0`, `cn.CLStakingInfo.CLStakingAmount = 0`
   - `totalAmount = 0`
   - `clAmount.Div(clAmount, totalAmount)` → **panic: division by zero**
6. All nodes crash; the chain halts at block `N`.

		spec             = reward.NewRewardSpec()

		distributableFee = new(big.Int).Sub(execFee, burntFee)

	// because fees are exclusively allocated to proposer. By the way, remainder goes to KIF.

	proposer, stakers := config.Kip82Ratio.Split(validators)
	ratioRemainder := calcRemainder(minted, proposer, stakers, kif, kef)
	kif.Add(kif, ratioRemainder)

	// Further distribute using Kip82Ratio. By the way, remainder goes to proposer.
	// After Prague, if the CLStaking is not nil, the proposer and staking rewards are proportionally distributed to both CN and CL.
	// For proposer rewards, see `specWithProposerAndFunds`.
	stakersAlloc, kip82Remainder := assignStakingRewards(config, stakers, si)
	proposer.Add(proposer, kip82Remainder)

	spec.BurntFee = new(big.Int).Add(burntFee, blobFee)
	spec.Stakers = stakers
	for addr, amount := range stakersAlloc {
		spec.IncRecipient(addr, amount)
	}
	spec = specWithProposerAndFunds(spec, config, proposer, kif, kef, si)
	return spec, nil
