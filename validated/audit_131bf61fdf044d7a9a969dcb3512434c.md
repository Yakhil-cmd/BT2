Based on my review of `pallet-asset-conversion`'s multi-hop swap implementation, the reported EVM bug class does not have an analog here.

The `BerabotRouter._executeV2Swap` bug stemmed from reusing the *original* `amountIn` for every hop of a multi-hop path instead of threading the output of each hop into the next hop's input calculation.

In `pallet-asset-conversion`, the equivalent multi-hop logic in `balance_path_from_amount_in` and `balance_path_from_amount_out` explicitly threads the running amount through each iteration of the loop, rather than reusing the initial value:

- `balance_path_from_amount_in` mutates a local `amount_out` variable each iteration and feeds it into `Self::get_amount_out(fee, &amount_out, &reserve_in, &reserve_out)` for the *next* hop, correctly compounding the calculation hop-by-hop. [1](#0-0) 
- `balance_path_from_amount_out` does the symmetric thing in reverse, updating `amount_in` per hop via `Self::get_amount_in`. [2](#0-1) 
- The resulting `BalancePath` (a `Vec<(AssetKind, Balance)>` with one precomputed amount per hop) is what actually drives fund movement in `credit_swap`, which reads `amount_out` per adjacent pair directly from this precomputed path rather than recomputing it from the original input — eliminating the class of bug where a stale/initial `amountIn` leaks into later hops. [3](#0-2) 

Both `do_swap_exact_tokens_for_tokens` and `do_swap_tokens_for_exact_tokens` build this per-hop path once via `balance_path_from_amount_in`/`balance_path_from_amount_out` and then pass the fully resolved path to `Self::swap`/`credit_swap`, so there is no point in the flow where a hop's calculation incorrectly reuses the very first `amount_in` value the way the EVM `_executeV2Swap` did. [4](#0-3) [5](#0-4) 

Existing multi-hop tests (`swap_exact_tokens_for_tokens_in_multi_hops`, `swap_tokens_for_exact_tokens_in_multi_hops`) exercise exactly this 3-asset path scenario and assert the correct compounded amounts at each pool, confirming the per-hop threading works as intended. [6](#0-5) [7](#0-6) 

No vulnerability found for this question.

		pub(crate) fn balance_path_from_amount_out(
			amount_out: T::Balance,
			path: Vec<T::AssetKind>,
		) -> Result<BalancePath<T>, DispatchError> {
			let mut balance_path: BalancePath<T> = Vec::with_capacity(path.len());
			let mut amount_in: T::Balance = amount_out;

			let mut iter = path.into_iter().rev().peekable();
			while let Some(asset2) = iter.next() {
				let asset1 = match iter.peek() {
					Some(a) => a,
					None => {
						balance_path.push((asset2, amount_in));
						break;
					},
				};
				let fee = Self::pool_fee_for(asset1, &asset2)?;
				let (reserve_in, reserve_out) = Self::get_reserves(asset1.clone(), asset2.clone())?;
				balance_path.push((asset2, amount_in));
				amount_in = Self::get_amount_in(fee, &amount_in, &reserve_in, &reserve_out)?;
			}
			balance_path.reverse();

			Ok(balance_path)
		}
