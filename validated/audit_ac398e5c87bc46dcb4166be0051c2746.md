### Title
`StatusHandler#process` mutates `Commit` rows without repository scoping, allowing cross-repo status injection - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` only authenticates that the requester controls the `repository.owner.login` org named in the payload; it never re-checks that org against the repository actually owning the `Commit` rows a handler mutates. `StatusHandler#process` queries `Commit.where(sha: params.sha)` across the entire `commits` table with no repository/stack scoping, so any org that can produce a valid signature for its own webhook secret can inject a `commit_status` onto any `Commit` in any other tenant's stack, provided the (attacker-chosen) `sha` string collides with a real commit tracked elsewhere.

### Finding Description
The claimed binding is: `repository_owner` (used by `verify_signature`, equal to `params.dig('repository','owner','login')`) must equal `Repository.from_github_repo_name(payload.dig('repository','full_name')).owner` for every `Commit` row mutated by the invoked handler.

Tracing the code:
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) computes `repository_owner` from the payload and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. This proves only that the HMAC matches the secret configured for that org — it authenticates the envelope's claimed owner, not the specific commit/stack that will be touched.
- `WebhooksController#create` then dispatches `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (`app/controllers/shipit/webhooks_controller.rb:10-15`), passing the full JSON payload straight through.
- The `Handler` base class supplies a `stacks` helper that correctly scopes lookups to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`). `CheckSuiteHandler#process` uses this correctly: `stacks.where(branch: params.check_suite.head_branch).each { |stack| stack.commits.where(sha: ...) }` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`).
- `StatusHandler#process`, however, does **not** use `stacks` at all:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
(`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`). This is a bare, global, unscoped `Commit` lookup by `sha` — it never consults `payload.dig('repository','full_name')` or the `repository_owner` that `verify_signature` just authenticated. Any `Commit` row anywhere in the database whose `sha` matches the attacker-supplied string gets a new status created via `create_status_from_github!`.

Exploit flow: an attacker who administers/owns some GitHub org/repo `attacker/repo` (able to produce a validly signed `status` webhook for that repo) sends `POST /webhooks` with `X-Github-Event: status`, a body whose `repository.owner.login` is `attacker`, and `sha` set to a commit SHA known to exist in a victim org's tracked stack (e.g., copied from a public commit, or brute-guessed/observed via the victim's public GitHub history, CI badges, PR pages, etc.). `verify_signature` passes because the signature matches `attacker`'s webhook secret. `StatusHandler.call(params)` then finds the victim's `Commit` row purely by `sha` equality and writes a new `CommitStatus`/triggers `create_status_from_github!`, which can flip the commit's aggregate `state` (e.g., to `success`), potentially unblocking `deployable?` checks, triggering `ProcessMergeRequestsJob`, or firing `deployable_status`/`commit_status` webhooks/hooks for the victim's stack — none of which the attacker's org has any relationship to.

No other guard intervenes: `check_if_ping` and `drop_unhandled_event` only gate on the event type; `ExplicitParameters` (`params do requires :sha, String ... end`) validates types, not ownership; there is no `Stack`/`Repository` membership check anywhere in `StatusHandler`.

### Impact Explanation
A payload correctly signed for repository/org A can mutate `Commit` and derived `CommitStatus` state belonging to a completely unrelated repository/org B — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Since `Commit.state` participates in deployability checks (`deployable?`, blocking logic) and can enqueue `ProcessMergeRequestsJob` or fire hooks, this can influence downstream deploy/merge decisions for victim stacks the attacker never authenticated against. The attack is repeatable against any `sha` value the attacker can guess or copy, for as many `Commit` rows share that sha across the whole install (single Shipit instance can host many unrelated orgs' repos), so blast radius spans every tenant on that Shipit deployment.

### Likelihood Explanation
Preconditions are attacker-controlled and cheap: register/own any GitHub org/repo, configure a Shipit webhook (or simply know that org's webhook secret since it's the attacker's own), and know or predict a target `sha`. SHA collision across unrelated repos is naturally rare for random guessing, but the SHA is not secret — it is visible in the victim's public GitHub commit history, PR URLs, CI logs, or Shipit's own public stack views, so the attacker can simply copy it. No Shipit session, API token, or team membership is needed at any point — only the ability to make the *webhook body* say `sha: <copied-value>`. This is fully repeatable and low-cost per request.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring `CheckSuiteHandler`: replace the global `Commit.where(sha: params.sha)` with a lookup restricted to `stacks` (i.e. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` or iterate `stacks.each { |stack| stack.commits.where(sha: params.sha).each(&...) }`), so a `Commit` is only mutated if it belongs to a stack whose `Repository` matches `payload.dig('repository','full_name')` — and by extension the same owner/org that `verify_signature` authenticated.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or similar, not present today for this specific case):

```ruby
test "status webhook for org A does not mutate a Commit belonging to org B" do
  # Arrange: two stacks/repos with distinct owners but a colliding sha
  org_a_repo = shipit_repositories(:example) # owner: "example-org" (some fixture with owner A)
  org_b_stack = shipit_stacks(:shipit)       # belongs to a Repository whose owner is B, distinct from A
  colliding_sha = "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"

  victim_commit = org_b_stack.commits.create!(
    sha: colliding_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus),
    authored_at: Time.now, committed_at: Time.now, message: "victim commit"
  )

  # Binding under test, stated explicitly BEFORE tracing:
  #   repository_owner (payload for org A) == Repository.from_github_repo_name(payload['repository']['full_name']).owner
  # should hold for every Commit mutated. Here it does NOT: owner_a != org_b_stack.repository.owner.
  payload = {
    "sha" => colliding_sha,
    "state" => "success",
    "repository" => { "full_name" => org_a_repo.github_repo_name, "owner" => { "login" => org_a_repo.owner } }
  }

  assert_no_difference -> { victim_commit.reload.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
  # Current code FAILS this assertion: victim_commit gains a status even though
  # org_a_repo.owner != org_b_stack.repository.owner.
end
```

This demonstrates the equality `repository_owner == Repository.from_github_repo_name(payload).owner` is required by the security model but is never checked by `StatusHandler#process`, allowing the cross-tenant mutation.
