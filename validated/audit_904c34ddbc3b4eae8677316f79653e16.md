### Title
`EnvironmentVariables#interpolate` exposes the real `GITHUB_TOKEN` (and any other unbounded env value) to any shipit.yml-defined step without whitelist checks - ([File: lib/shipit/environment_variables.rb])

### Summary
`Shipit::EnvironmentVariables#interpolate` substitutes any `$WORD` occurrence in a task step string with the corresponding value from the full merged environment hash, with no reference to the task's declared `variables:` whitelist. Because `Commands#base_env` unconditionally injects the app's real `GITHUB_TOKEN` into every task/deploy/rollback environment, any shipit.yml step that references `$GITHUB_TOKEN` will have it substituted verbatim and streamed to the task's captured output.

### Finding Description
Broken binding: the bytes handed to `PTY.spawn` should equal the step string in `shipit.yml` with only variables declared in that task's `variables:` list substituted. Actual behavior: `interpolate` performs `@env.fetch(variable) { ENV[variable] }` for every `$WORD` in the string with no whitelist consultation at all: [1](#0-0) 

The whitelist mechanism (`EnvironmentVariables#permit`/`sanitize_env_vars`) exists in the same class but is a separate method never called from the `Command#start` → `interpolate_environment_variables` → `interpolate` path: [2](#0-1) [3](#0-2) 

Crucially, `@env` reaching this call already contains the real secret. `Commands#base_env`, inherited by every `*Commands` subclass (including `TaskCommands`), sets `GITHUB_TOKEN` to the live `github.token` value: [4](#0-3) 

`TaskCommands#env` merges `super` (i.e. `base_env`, containing `GITHUB_TOKEN`) with stack/task env and passes the result into every step's `Command`: [5](#0-4) 

So `@env.fetch('GITHUB_TOKEN')` succeeds directly — it never needs to fall back to process `ENV`. Any step string authored in shipit.yml (custom task, deploy, or rollback step) that contains `$GITHUB_TOKEN` gets that literal secret substituted in and executed via `PTY.spawn`, with output captured to the task log by `TaskExecutionStrategy::Default#capture!`. No code on this path checks the step string's variable references against the task's declared `variables:` schema — `permit` is a distinct, unused-here mechanism (used to filter user-supplied deploy-time input, not to gate which names may appear in step strings).

### Impact Explanation
Once a commit containing such a step is executed by any task/deploy/rollback (via continuous deployment or an authorized operator triggering it), the Shipit host's real `GITHUB_TOKEN` — a credential with GitHub API/write access on behalf of the app — is printed into the task output visible to anyone who can view that stack's task/deploy page. This matches the Critical category "exfiltration of ... deploy-time secrets." The blast radius is scoped to the stack whose shipit.yml carries the malicious step, but it is fully repeatable (every run of that step leaks the token again) and the leaked token can then be reused outside Shipit against GitHub.

### Likelihood Explanation
The attacker only needs write access to a `shipit.yml` file that will eventually be checked out and executed by a task/deploy/rollback — e.g. via a merged PR, a repo the attacker controls with continuous deployment enabled, or by convincing/waiting for an operator to run a custom task against their commit. No Shipit session, API token, or GitHub team membership is required to *author* the payload; only someone (possibly automated via CD) needs to *execute* it, which is the normal, expected operation of running a task against that commit. This is a config-controlled trigger, not a privileged-secret-bypass, but the exposure itself is a genuine, unmitigated engine bug, since the `variables:` whitelist that shipit.yml documents as the safety boundary for step-referenced variables is never enforced by `interpolate`.

### Recommendation
Make `Command#interpolate_environment_variables` / `EnvironmentVariables#interpolate` whitelist-aware: only allow interpolation of variable names explicitly declared by the task's `variables:` definitions (reusing `permit`/`sanitize_env_vars`), and exclude internal/secret keys such as `GITHUB_TOKEN`, `GIT_ASKPASS`, etc. from ever being interpolatable from step strings, keeping them usable only as literal process env for tools like `git`/`git-askpass` rather than shell-string substitution targets.

### Proof of Concept
Add to `test/unit/environment_variables_test.rb` (or `command_test.rb`):
```ruby
test "interpolate exposes GITHUB_TOKEN from full env without whitelist" do
  env = { 'GITHUB_TOKEN' => 'super-secret-token' }
  interpolated = EnvironmentVariables.with(env).interpolate('echo $GITHUB_TOKEN')
  assert_equal 'echo super-secret-token', interpolated
end
```
And end-to-end via `Command`:
```ruby
test "Command leaks GITHUB_TOKEN-like env into shell output" do
  command = Command.new('echo $GITHUB_TOKEN', env: { 'GITHUB_TOKEN' => 'super-secret-token' }, chdir: '.')
  assert_includes command.run, 'super-secret-token'
end
```
Both assert the equality that should NOT hold under a correct whitelist (`interpolated step == declared-variables-only substitution`) but does hold today, confirming the unrestricted interpolation.

```ruby
    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
```
