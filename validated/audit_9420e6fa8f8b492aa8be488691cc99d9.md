### Title
Webhook signature verification key is selected using an unverified field from the same payload it is meant to authenticate, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted, not-yet-verified request body, then verifies the signature against that org's secret. [1](#0-0) [2](#0-1)  This breaks the intended binding "organization that authenticated == repository that is written": the org whose secret validates the request is chosen from attacker-controlled payload content, not derived from a trusted, out-of-band source.

### Finding Description
`Shipit::WebhooksController#create` parses the raw JSON body and dispatches it to registered handlers for the declared event, gated by `verify_signature`. [3](#0-2) 

`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — a value taken from the same unauthenticated body being verified. [1](#0-0) [2](#0-1) 

Each GitHub App/organization in `Shipit` is configured with its own `webhook_secret`, and `verify_webhook_signature` HMAC-compares the signature against that specific secret. [4](#0-3)  Consequently, the equality that should hold is:

`organization whose secret validated the signature == organization owning the repository/stack that the dispatched handler will act on`

Because both fields (`repository.owner.login` used for key-selection, and the rest of `repository`/`organization`/`sha`/etc. used by the actual handler to look up and mutate a `Stack`/`Repository`/`Commit`) live in the same untrusted JSON body, an attacker who controls (or has legitimately configured) any single organization's `webhook_secret` in the Shipit instance can sign a payload with that organization's secret while filling in the `repository` object with data belonging to a *different, victim* stack/repository. Since `verify_signature` only checks "does this signature match the secret for the org named in this payload," and that org name is exactly the field the attacker gets to choose, the check passes even though the actual content being processed (and eventually written to the database / used to trigger `GithubSyncJob`, create commits, statuses, memberships, etc.) targets a repository/org the attacker does not own.

### Impact Explanation
This allows cross-repository/cross-organization forged writes: an attacker who controls one legitimate GitHub App/org integration on the Shipit instance can forge webhook events (`push`, `status`, `check_suite`, `membership`, etc.) that are processed as if delivered for a *different* org's repository, since the field used to choose the verification secret is not bound to the field(s) the downstream handler trusts to select the target repository/stack. This matches the "cross-repository writes" high/critical impact category, since it lets an attacker inject synthetic commits, statuses, or check-suite state, or manipulate memberships/teams for stacks outside their authorization scope, without any Shipit session or `ApiClient` token.

### Likelihood Explanation
Exploitation requires the attacker to control at least one organization/app integration configured in the Shipit instance (i.e., know one org's `webhook_secret`) — a realistic bar in any multi-tenant or self-service onboarding deployment of Shipit, since organizations legitimately register their own GitHub App webhook secrets. No repository write access, TLS interception, or privileged Shipit account is required — only the ability to send a crafted HTTP POST to the public `/webhooks` endpoint with a valid signature for the attacker's own org.

### Recommendation
Do not select the verification secret from a field embedded in the same untrusted payload being verified. Instead:
- Bind the webhook endpoint to a specific organization/app (e.g., via a per-org URL path or a static installation ID established at GitHub App registration time), rather than trusting `params.dig('repository', 'owner', 'login')`.
- After successful signature verification, independently re-derive/validate the organization and target repository from GitHub App installation metadata (not from body fields) before dispatching to handlers.
- Reject events whose declared `repository`/`organization` owner does not match the app installation associated with the delivery (available via GitHub's installation webhook headers/IDs).

### Proof of Concept
1. Attacker registers/controls a GitHub App integration for org `attacker-org` on the target Shipit instance and knows its `webhook_secret`.
2. Attacker crafts a `push` (or `status`/`membership`) webhook JSON body where `repository.owner.login` (or `organization.login`) is set to `attacker-org`, but `repository.full_name`/`sha`/`branches` reference a `victim-org/victim-repo` stack tracked by the same Shipit instance.
3. Attacker computes `X-Hub-Signature` using the known `attacker-org` `webhook_secret` over the crafted raw body, per `Hook::DeliverySigner`/`verify_webhook_signature` semantics. [4](#0-3) 
4. POST to `/webhooks` with the crafted body and signature.
5. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (per the spoofed `repository_owner`), verifies successfully with the attacker's own secret, and the request proceeds to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, where handlers act on the `victim-org/victim-repo` data embedded in the payload. [5](#0-4)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
