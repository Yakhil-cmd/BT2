### Title
Webhook signature verification selects a signing organization independent of the repository the event handlers act on, allowing cross-organization forgery of commit statuses - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which `GithubApp` (and therefore which `webhook_secret`) is used to validate the inbound HMAC signature based on an attacker-supplied field of the *same unverified JSON body* (`repository.owner.login`, falling back to `organization.login`). The event handlers that actually mutate state (`StatusHandler`, `PushHandler`, `MembershipHandler`) do not necessarily use that same field to scope what they write to: `StatusHandler` locates the target `Commit` purely by `sha` with no verification that the sha belongs to the organization/repository whose secret produced the signature. This breaks the equality "organization whose secret authenticated the payload" == "repository/commit the payload is allowed to mutate."

### Finding Description
`verify_signature` derives `repository_owner` from the raw JSON payload before establishing any trust in its contents: [1](#0-0) [2](#0-1) 

This value selects the `Shipit.github(organization:)` app instance whose `webhook_secret` is used in `verify_webhook_signature`, i.e. whichever organization's secret the attacker actually possesses (e.g., their own onboarded org) can be named here to make the check pass, as long as they sign the *exact bytes* of their crafted body with that org's own secret: [3](#0-2) 

Once the signature check passes, `create` dispatches the parsed body to the matching handlers without re-checking that the organization used for signing matches the repository/commit being mutated: [4](#0-3) 

The `Handler` base class only scopes lookups by `repository.full_name` when a handler chooses to call `stacks`; nothing enforces that this value must equal `repository_owner`/`organization.login`, the field that was actually used for authentication: [5](#0-4) 

Critically, the `status` event handler locates the target commit purely by `sha`, independent of any organization/repository field, as shown by its own test, which supplies only `repository.owner.login = "shopify"` (no `full_name`) yet successfully writes a `Status` onto an arbitrary pre-existing commit: [6](#0-5) 

Because `sha` is a global identifier with no organizational namespace enforced in this lookup path, an attacker who legitimately controls a `webhook_secret` for *any* organization configured on the shared Shipit instance can:
1. Sign a "status" event payload with their own valid secret so `verify_signature` passes.
2. Set `sha`, `state`, `description`, `context`, and `target_url` to arbitrary attacker-chosen values pointing at a commit sha belonging to a completely different, unrelated organization/stack hosted on the same Shipit instance.
3. Have Shipit persist that forged `Status` as if it came from the real CI/organization that owns that commit.

### Impact Explanation
Commit statuses are the basis for Shipit's merge-queue and deploy gating logic (blocking/required statuses referenced by `DeploySpec`/`MergeRequest`/`Status::Group`). By injecting a fabricated "success" status for a commit belonging to another organization's repository, an attacker who only has legitimate access to their own low-trust org's webhook secret can defeat required-status checks and enable an unauthorized deploy or merge of a commit that never passed real CI — a cross-organization write and unauthorized-deploy primitive within the meaning of the accepted impact categories.

### Likelihood Explanation
Exploitability requires only that the attacker control (or configure) the `webhook_secret` of some organization already onboarded to the same multi-tenant Shipit deployment (a normal, documented, non-privileged action for an org admin setting up their own GitHub App integration — not the target org's secret, a Shipit session, or any Shipit-internal credential). Given Shipit's documented support for multiple `github:` organizations sharing one instance, this is a realistic configuration.

### Recommendation
In `WebhooksController#verify_signature` and each `Handler`, require that the resolved signing organization equals the organization implied by the payload's target repository/commit before performing any mutation (e.g., resolve the target `Stack`/`Repository` first, derive its owning organization from Shipit's own records, and only then select/verify against that organization's secret; reject the request if the two disagree). For `StatusHandler` specifically, scope the `Commit` lookup by the stack/repository resolved from a trusted source rather than by `sha` alone.

### Proof of Concept
1. Configure Shipit with two organizations in `github:` config, `org-a` (attacker-controlled, secret known to attacker) and `org-b` (victim, tracks a `Stack` with commit `sha=X`).
2. POST to `/webhooks` with header `X-Github-Event: status`, body: `{"sha":"X","state":"success","description":"forged","context":"ci/required","target_url":"...","repository":{"owner":{"login":"org-a"}}}`.
3. Compute `X-Hub-Signature` using `org-a`'s `webhook_secret` over the exact raw body — `verify_signature` succeeds because it selects `org-a`'s app based on `repository.owner.login`.
4. `StatusHandler` (dispatched via `Webhooks.for_event('status')`) creates/updates a `Status` on commit `X`, which belongs to `org-b`'s stack, as demonstrated by the existing test at `test/controllers/webhooks_controller_test.rb:42-59` (no `repository.full_name` is required for the write to succeed).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
