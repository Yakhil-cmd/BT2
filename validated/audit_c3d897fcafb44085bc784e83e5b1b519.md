### Title
Signer-key authorizations issued as raw signatures in `pox-4.clar` cannot be revoked before use — ([File: stackslib/src/chainstate/stacks/boot/pox-4.clar])

### Summary
`pox-4.clar` supports two ways to authorize use of a signer key for `stack-stx`, `stack-extend`, `stack-increase` and `stack-aggregation-commit`: (1) an off-chain SIP-018 signature (`signer-sig`) recovered against `signer-key`, or (2) an on-chain, revocable authorization stored in the `signer-key-authorizations` map via `set-signer-key-authorization`. Only the second path can be disabled by the signer. Once a signer produces a raw `signer-sig` and hands it to a stacker/pool operator, there is no function that lets the signer invalidate that specific signature before it is consumed. This is the exact bug class described in the eBTC report: a previously issued authorization (permit/signature) cannot be revoked, only "used up" or allowed to expire naturally.

### Finding Description
`verify-signer-key-sig` in `pox-4.clar` branches on whether `signer-sig-opt` is `some` or `none`: [1](#0-0) 

When a signature is supplied, the function only checks that the `used-signer-key-authorizations` map does not already contain the tuple `{signer-key, reward-cycle, topic, period, pox-addr, auth-id, max-amount}` and that the signature recovers to `signer-key`. It never consults `signer-key-authorizations`, which is the only map the signer can toggle via `set-signer-key-authorization` (`allowed: false`): [2](#0-1) 

`consume-signer-key-authorization` marks the tuple as used only *after* a successful call — it provides replay protection, not revocation: [3](#0-2) 

The `used-signer-key-authorizations` map is exactly a "has this signature been spent" flag, never a "has this signature been cancelled" flag: [4](#0-3) 

Because `auth-id` is chosen by the signer at signing time and baked immutably into the signed message hash (see `get-signer-key-message-hash`), a signer who has handed a valid, not-yet-submitted `signer-sig` to a stacker/pool has no on-chain call that can invalidate that specific `(signer-key, reward-cycle, period, topic, pox-addr, auth-id, max-amount)` tuple. `set-signer-key-authorization` only affects the code path that is used when `signer-sig-opt` is `none`; it has zero effect on a pre-issued, still-valid signature.

This mirrors the eBTC finding precisely: as in EBTCToken/BorrowerOperations, an issued credential (there: an EIP-2612 permit / position-manager approval; here: a SIP-018 `signer-sig`) remains fully redeemable regardless of any subsequent "revoke" action the grantor takes, because the revocation mechanism (there: `revokePositionManagerApproval`; here: `set-signer-key-authorization allowed:false`) does not intersect with the signature-verification code path at all.

Notably, the successor contract `pox-5.clar` implements an explicit grant-revocation flow (`RevokeSignerGrant`, and corresponding `...ErrGrantRevoked` error paths surfaced in the test-suite for `register-for-bond`, `stake`, and `update-bond-registration`), indicating that the project itself recognized and fixed this exact bug class for `pox-5`, while `pox-4` — which remains an in-scope, currently-relied-upon contract — still lacks it.

### Impact Explanation
A signer who has provided a valid, unexpired `signer-sig` to a stacker or stacking pool (a routine real-world workflow — signer keys are frequently controlled separately from the stacker's principal and signatures are distributed off-chain ahead of time) cannot stop that signature from being redeemed even after deciding to withdraw authorization (e.g., because the relationship with the pool ended, the key is believed compromised, or terms changed). The stacker/pool can still call `stack-stx`, `stack-extend`, `stack-increase`, or `stack-aggregation-commit` with the old signature at any point before the `reward-cycle`/`period` values embedded in the signed message become stale, causing the signer's key to be used, and the stacker's STX to be locked, in a manner the signer no longer consents to. This is a stacking action the signer never authorized at execution time — the category the analysis explicitly calls out as in-scope ("a stacking action the staker/signer never authorised").

### Likelihood Explanation
This requires no privileged access: any party who already holds a validly-signed `signer-sig` (a normal artifact of the intended off-chain signing workflow) can submit it at will, and the signer has no on-chain call available to stop them. The precondition (signer previously provided a signature, then wants to revoke) is a realistic and common operational scenario for stacking pools.

### Recommendation
Add an explicit revocation mechanism analogous to `pox-5`'s grant-revocation pattern, or route the raw-signature branch of `verify-signer-key-sig` through a per-key/per-tuple "revoked" map that a signer can set directly (independent of, but checked in both code paths, similar to `used-signer-key-authorizations`). Alternatively, allow signers to increment a per-signer-key nonce that is embedded in the signed message hash, so that a signer can invalidate all previously issued but unused signatures with a single low-cost on-chain call, mirroring the `increaseNonce()` remediation adopted for the eBTC permit issue.

### Proof of Concept
1. Signer `S` produces an off-chain SIP-018 signature for `topic = "stack-stx"`, a chosen `auth-id`, `reward-cycle = R`, `period = P`, `pox-addr = A`, `max-amount = M`, following `get-signer-key-message-hash` [5](#0-4) , and gives the `signer-sig` bytes to stacker `T` (e.g. as part of a pooling agreement).
2. Before `T` submits `stack-stx`, `S` decides to withdraw consent (e.g., ends the arrangement) and calls `set-signer-key-authorization` with `allowed:false` for the matching tuple, believing this revokes `T`'s ability to use the key.
3. `T` still calls `stack-stx` passing the original `signer-sig` (not `none`), reaching `consume-signer-key-authorization` → `verify-signer-key-sig`, whose `signer-sig`-present branch [6](#0-5)  never reads the `signer-key-authorizations` map that `S` just modified.
4. The transaction succeeds, `S`'s signer key is used and `T`'s STX gets locked for `P` cycles at `R`, despite `S`'s explicit revocation attempt — demonstrating the equality break: "consent recorded on-chain" ≠ "consent actually enforced at signature-verification time."

;; This function does two things:
;;
;; - Verify that a signer key is authorized to be used
;; - Updates the `used-signer-key-authorizations` map to prevent reuse
;;
;; This "wrapper" method around `verify-signer-key-sig` allows that function to remain
;; read-only, so that it can be used by clients as a sanity check before submitting a transaction.
(define-private (consume-signer-key-authorization (pox-addr { version: (buff 1), hashbytes: (buff 32) })
                                                  (reward-cycle uint)
                                                  (topic (string-ascii 14))
                                                  (period uint)
                                                  (signer-sig-opt (optional (buff 65)))
                                                  (signer-key (buff 33))
                                                  (amount uint)
                                                  (max-amount uint)
                                                  (auth-id uint))
  (begin
    ;; verify the authorization
    (try! (verify-signer-key-sig pox-addr reward-cycle topic period signer-sig-opt signer-key amount max-amount auth-id))
    ;; update the `used-signer-key-authorizations` map
    (asserts! (map-insert used-signer-key-authorizations
      { signer-key: signer-key, reward-cycle: reward-cycle, topic: topic, period: period, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount } true)
      (err ERR_SIGNER_AUTH_USED))
    (ok true)))
