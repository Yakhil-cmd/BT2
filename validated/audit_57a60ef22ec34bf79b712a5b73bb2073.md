### Title
StatusHandler writes GitHub commit statuses by SHA alone with no repository/stack scoping, allowing cross-repository status forgery - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` never calls the `stacks` scoping helper that `PushHandler`, `CheckSuiteHandler`, and the `PullRequest::*` handlers use to constrain writes to the payload's own repository. Instead it resolves target `Commit` rows purely by `Commit.where(sha: params.sha)`, so any validly-signed `status` webhook whose SHA happens to match a commit already stored for a *different* repository/stack will write a forged `Status` onto that unrelated stack.

### Finding Description
The binding that should hold is:
`commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` row updated by a `status` webhook.

`StatusHandler#process` breaks this:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

It queries `Commit` globally by `sha`, with no `stacks`/`repository_name` filter, unlike `PushHandler#process`, which explicitly does `stacks.not_archived.where(branch:).find_each { ... }` before touching any record: [2](#0-1) 

The base `Handler#stacks` method exists precisely to scope writes to `Repository.from_github_repo_name(repository_name)&.stacks`: [3](#0-2) 

`StatusHandler` never references `stacks` or `repository_name`, so this method is dead code for this handler — confirming the question's premise.

`Commit#sha` is a raw git SHA-1 with no dependency on the repository name; identical commit objects (same tree/parents/author/committer/timestamps/message) produce identical SHAs across repositories that share history (forks, repo copies, `git push` of the same commit object into a new repository). `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` using the commit's own `stack_id`, not anything derived from the payload's repository: [4](#0-3) 

**Exploit path:** `WebhooksController#verify_signature` validates the HMAC signature using the webhook secret configured for `repository_owner` (the payload's org), and this scoping is by *organization*, not by *repository*: [5](#0-4) [6](#0-5) 

So once an attacker controls (or pushes to / has API write access to) **any** repository whose GitHub App/webhook installation shares that org's registered secret, they can:
1. Obtain/copy a commit object with an identical SHA to a commit already tracked by a victim `Stack` in that org (e.g., fork the target repo, or `git push` the same commit object into a new repo they own inside the org).
2. Call GitHub's Status API on their own repo for that SHA with an arbitrary `state` (`success`), `description`, and `target_url`.
3. GitHub delivers a `status` webhook, correctly signed with the org's real secret, but with `payload.repository.full_name` pointing to the attacker's own repo.
4. `WebhooksController#verify_signature` passes (correct org secret). `StatusHandler#process` matches by SHA only and writes a forged `Status` onto the victim stack's commit, since it never checks that the commit's `stack.repository.full_name` matches `payload.repository.full_name`.

No existing guard prevents this: `verify_signature` authenticates the org, not the specific repository named in the payload; `ExplicitParameters` only validates field shapes, not the repository/stack relationship; and `Handler#stacks` — the mechanism meant to enforce this binding — is simply never invoked by `StatusHandler`.

### Impact Explanation
An attacker can inject an arbitrary, fully attacker-controlled CI `Status` (`success`/`failure`/`pending`, description, target_url) onto a commit belonging to a stack they do not control, as long as they can produce a validly-signed webhook (via a repo under the same trusted org/app installation) and can get a commit with a matching SHA into their own repository. If the victim stack is `continuous_deployment?`-enabled and that status is what makes the commit `deployable?` (`success? && !blocked?`), this can trigger an **unauthorized deploy** via `schedule_continuous_delivery`/`ContinuousDeliveryJob`, matching the Critical impact category ("a payload for one repository mutating another's stack... or an unauthorized deploy"). This is repeatable against any stack/repository sharing a commit SHA reachable by the attacker and is not limited to a single tenant boundary within the affected organization.

### Likelihood Explanation
Preconditions: (1) the attacker needs write/API access to at least one repository whose webhook deliveries are signed with the same org secret Shipit trusts (e.g., a repo they create/own inside an org where the GitHub App is installed broadly, or a fork covered by that installation); (2) the attacker needs a commit object with a SHA identical to one already ingested for the victim stack, which is trivial to obtain by cloning/forking the target repository (SHA-1 git commit identity is independent of the hosting repository). Both preconditions are realistic and low-cost for an attacker who is a member of, or has any repository access within, the trusted GitHub organization/app installation — no Shipit credentials, session, or secrets are required.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the payload's own repository, mirroring the other handlers, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).where(sha: params.sha)... # or
  Commit.joins(:stack).merge(stacks).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
i.e., use `Handler#stacks` (derived from `Repository.from_github_repo_name(repository_name)`) to constrain the `Commit` query so a status can only be written to commits whose stack's repository matches the payload's `repository.full_name`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — actual file is out-of-scope per rules but describes the reproducible check):
1. Create `stack_a` for `repository_owner/repo-a` with a `Commit` `sha: "deadbeef..."`.
2. Create `stack_b` for `repository_owner/repo-b` (different repository, no such commit).
3. Build a `status` payload where `payload['repository']['full_name'] == 'repository_owner/repo-b'` but `sha == "deadbeef..."` (the sha belonging to `repo-a`'s commit).
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert:
   - `commit_a.reload.statuses.count` increased (i.e., the forged status landed on `stack_a`'s commit) — proving `equality(payload.repository.full_name, commit.stack.repository.full_name)` does **not** hold.
   - Additionally, stub `Shipit::Webhooks::Handlers::Handler#stacks` with `StatusHandler.any_instance.expects(:stacks).never` and confirm `StatusHandler.call(payload)` still succeeds and writes the status — proving `stacks` is dead code for this handler and no repository-scoping guard is exercised.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
