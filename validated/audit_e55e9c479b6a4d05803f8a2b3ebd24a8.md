### Title
Unauthenticated `my_xpubkey`/`wallet_fully_approved` device messages allow a non-paired peer to inject itself into a pending multisig-wallet setup, permanently freezing wallet finalization - ([File: device.js], [File: wallet.js], [File: wallet_defined_by_keys.js])

### Summary
The Mattermost CVE describes an unauthenticated lifecycle callback (`/ac/installed`) that is trusted during a *pending install* window, letting an attacker inject a rogue value that corrupts the integration's shared state. In `ocore`, the hub-message dispatcher whitelists two subjects — `my_xpubkey` and `wallet_fully_approved` — to be processed **from devices that are not yet paired/known correspondents** at all, during the *pending* multi-device (BIP44/multisig) wallet-creation window.

### Finding Description
`handleJustsaying` in `device.js` only enforces cryptographic signature/hash checks on the outer, hub-relayed envelope; it does not require the sender to be a known correspondent for two subjects: [1](#0-0) 

These two subjects are routed to `wallet.js`'s `handleMessageFromHub`, which dispatches them to `wallet_defined_by_keys.js`: [2](#0-1) 

`addDeviceXPubKey` (triggered by `my_xpubkey`) blindly inserts/updates a row in `extended_pubkeys` keyed by `wallet` + the sender's own `from_address`, with **no check that `from_address` is one of the addresses agreed upon in the wallet's `wallet_definition_template`** (that check exists only in `handleOfferToCreateNewWallet`, which is the *offer* path, not the `my_xpubkey`/`wallet_fully_approved` path): [3](#0-2) 

`handleNotificationThatWalletFullyApproved` (triggered by `wallet_fully_approved`) similarly inserts an unvalidated row and calls `checkAndFinalizeWallet`: [4](#0-3) 

`checkAndFinalizeWallet` only checks that *every existing row* in `extended_pubkeys` for the wallet has `member_ready_date` set before marking the wallet ready: [5](#0-4) 

Because any unpaired attacker who learns/guesses a pending `wallet` identifier can insert an extra `extended_pubkeys` row for that wallet (analogous to injecting a rogue value during the "pending install" window before the legitimate lifecycle completes), the attacker permanently adds a phantom member to the join set. Legitimate cosigners will never send that phantom device a `wallet_fully_approved` notification (since it's not part of `wallet_signing_paths`/the real `arrDeviceAddresses` set), so `member_ready_date` for the injected row never gets populated, and `checkAndFinalizeWallet`'s `rows.some(...!row.member_ready_date)` guard permanently blocks finalization — the multisig wallet setup is stuck in an incomplete state indefinitely for all legitimate participants.

### Impact Explanation
This is a freezing/denial-of-finalization bug on a legitimate multi-device (multisig) wallet-creation flow: unauthenticated attackers reachable only via the hub message-relay path (no pairing required, matching the CVE's unauthenticated-callback pattern) can corrupt a pending, multi-party cryptographic wallet setup so that it never completes, denying the intended cosigners the ability to use the shared wallet. This satisfies the "AA/wallet fund loss or freezing" bar in the validation criteria for the wallet/contract message-handling surface.

### Likelihood Explanation
Exploitation requires the attacker to know the specific `wallet` identifier of a wallet currently being set up between other parties — this value is not derived from any publicly-observable data in the reviewed code paths, so the attacker needs some means of learning it (e.g., social engineering, or observing it leak elsewhere), matching the CVSS `AC:H`/`UI:R`-like conditions of the underlying CVE (a bounded, non-trivial precondition rather than fully open access). Given that, likelihood is moderate — the code path itself performs no authentication or membership validation once the identifier is known, so the attack is otherwise reliable and repeatable.

### Recommendation
In `handleMessageFromHub`'s `my_xpubkey` and `wallet_fully_approved` cases (`wallet.js:162-178`) and in `addDeviceXPubKey`/`handleNotificationThatWalletFullyApproved` (`wallet_defined_by_keys.js:361-393`), verify that `from_address` is actually one of the device addresses recorded in `wallet_signing_paths` (or the wallet's definition template) for the given `wallet` before inserting/updating `extended_pubkeys`. Reject messages from addresses that are not expected members of that specific pending wallet, closing the "unauthenticated injection into a pending lifecycle" gap analogous to the Mattermost `/ac/installed` issue.

### Proof of Concept
1. Device A and Device B begin creating a 2-of-2 (or N-of-N) wallet via `create_new_wallet`; A generates a `wallet` id and shares it with B out-of-band as part of the legitimate flow.
2. Attacker device C, not paired with A or B, learns the `wallet` id (e.g., via a leak/side channel) and sends a `hub/message` with `subject: "my_xpubkey"`, `body: {wallet: <id>, my_xpubkey: <C's own xpubkey>}`, addressed to A. Because `my_xpubkey` is in `arrSubjectsAllowedFromNoncorrespondents`, A's node processes it without requiring C to be paired (`device.js:213-220`).
3. `addDeviceXPubKey` inserts a row for `(wallet, C's device_address)` with `approval_date` set (`wallet_defined_by_keys.js:361-376`), with no verification that C is part of the original `wallet_definition_template`.
4. A and B legitimately complete their approvals, but `checkAndFinalizeWallet` (`wallet_defined_by_keys.js:122-138`) never sees `member_ready_date` populated for C's phantom row, since neither A nor B ever notifies C — the wallet never reaches the `ready_date` state on A's node, permanently blocking use of the shared wallet.

function checkAndFinalizeWallet(wallet, onDone){
	db.query("SELECT member_ready_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0){ // wallet not created yet or already deleted
		//	throw Error("no wallet in checkAndFinalizeWallet");
			console.log("no wallet in checkAndFinalizeWallet");
			return onDone ? onDone() : null;
		}
		if (rows.some(function(row){ return !row.member_ready_date; }))
			return onDone ? onDone() : null;
		db.query("UPDATE wallets SET ready_date="+db.getNow()+" WHERE wallet=? AND ready_date IS NULL", [wallet], function(){
			if (onDone)
				onDone();
			eventBus.emit('wallet_completed', wallet);
		});
	});
}
