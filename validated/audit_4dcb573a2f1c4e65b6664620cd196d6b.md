### Title
AA payment bounce mechanism can permanently freeze funds when the received asset cannot be sent back due to `transfer_condition`, `is_transferrable`, or `spender_attested` restrictions - ([File: aa_composer.js])

### Summary
Autonomous Agents (AAs) rely on an automatic "bounce" mechanism to refund the trigger's payment when the AA's application logic fails or produces no valid response. This bounce mechanism naively re-sends the exact asset that was received back to `trigger.address` using a standard payment message. If that asset's protocol-level transfer restrictions (`transfer_condition`, `is_transferrable`, or `spender_attested`) prevent a payment to `trigger.address` at the time the bounce is attempted, the bounce payment itself fails validation, and the code path recurses into `bounce()` while already bouncing, causing the whole response to be dropped with `finish(null)` — leaving the received funds permanently stuck in the AA's address. This mirrors the reported bug class: a restricted/blacklist-like payment-token condition silently breaks the refund path, and the depositor has no way to recover funds.

### Finding Description
When a primary AA trigger fails (bad `if` condition, thrown error, insufficient balance, etc.), `handleTrigger` calls `bounce(error)`: [1](#0-0) 

`bounce()` builds a payment message for **every asset present in `trigger.outputs`** (not just base bytes) and sends it back to `trigger.address` via `sendUnit(messages)`:
```
for (var asset in trigger.outputs){
    var amount = trigger.outputs[asset];
    var fee = bounce_fees[asset] || 0;
    ...
    messages.push({app: 'payment', payload: {asset: asset, outputs: [{address: trigger.address, amount: bounced_amount}]}});
}
sendUnit(messages);
```

`sendUnit()` then builds and validates a real unit through `validateAndSaveUnit`, which runs the full payment validation logic in `validation.js`. For non-base assets this enforces:
- `is_transferrable` restrictions (a transfer must go to/from the asset definer unless conditions are met): [2](#0-1) 
- `spender_attested` (output address must be attested): [3](#0-2) 
- Arbitrary `transfer_condition`/`issue_condition` evaluated via `Definition.evaluateAssetCondition`: [4](#0-3) 

If any of these checks fail (e.g., the asset is `is_transferrable: false` and neither the AA nor `trigger.address` is the definer, or `spender_attested` is required and `trigger.address` lost its attestation between trigger time and bounce time, or a custom `transfer_condition` evaluates to false for the recipient), `validateAndSaveUnit` fails and `sendUnit` calls `bounce(err)` again: [5](#0-4) 

Because `bBouncing` is already `true` from the first call, this second invocation short-circuits:
```
if (bBouncing)
    return finish(null);
``` [6](#0-5) 

This means **no response unit is produced at all** — not even a partial refund of the base-byte portion that would otherwise be refundable. The trigger unit that deposited the funds into the AA is already final on the DAG (it is a separate, valid, previously-saved unit), so the deposited asset balance remains at the AA address with no automatic recovery path. Unless the AA's own oscript explicitly handles that specific asset (most simple/template AAs, e.g. `just_a_bouncer.oscript`, only reference `base` and rely on the default bounce for everything else), the funds are permanently unreachable through the standard bounce flow.

### Impact Explanation
This causes irrecoverable freezing of AA funds: any unprivileged AA trigger sender can deposit a payment-restricted asset (one with `transfer_condition`, `spender_attested`, or `is_transferrable: false`) into an AA whose logic does not explicitly forward/handle that asset. If the trigger later needs to be bounced for any reason (a common, easily reachable condition — the `if` clause failing, a thrown formula error, insufficient balance, exceeding `MAX_RESPONSES_PER_PRIMARY_TRIGGER`, etc.), the automatic refund silently fails and the entire trigger's outputs (including the base bytes that would otherwise have been refundable) become permanently stuck in the AA's balance. This matches the "AA fund loss or freezing" impact class.

### Likelihood Explanation
Likelihood is moderate to high: many production assets legitimately use `spender_attested`, `transfer_condition`, or `is_transferrable: false` (e.g., KYC-gated or non-transferable tokens), and AA authors commonly do not anticipate that generic AAs must explicitly forward every possible asset type they might receive. Attestor status or condition state can change between the time a trigger unit is created and the time the AA processes it (attestation is checked at validation/bounce time, not at trigger-composition time), making the failure condition realistically reachable by an ordinary user or by the asset issuer's own attestor revoking status.

### Recommendation
- In `bounce()`/`sendUnit()`, when constructing the automatic refund messages, validate in advance (or catch failures per-asset) whether each asset in `trigger.outputs` can legally be sent back to `trigger.address` given its `transfer_condition`/`is_transferrable`/`spender_attested` settings.
- If a given asset cannot be safely bounced, do not let its failure block bouncing of the other assets (in particular, base bytes) — process refund messages independently instead of aborting the whole unit on a single asset's validation failure.
- Consider recording/exposing (e.g., via a getter or state var) any asset balance that could not be bounced, so AA authors or affected users are aware funds are stuck and can potentially resolve it (e.g., an attestor re-attesting the address, or an explicit recovery message).

### Proof of Concept
1. Asset issuer defines asset `A` with `spender_attested: true` (or `transfer_condition` requiring attestation of the recipient), and attests `UserAddr`.
2. `UserAddr` sends a trigger unit to AA `X` carrying: enough base bytes to cover `bounce_fees`, plus some amount of asset `A`.
3. AA `X`'s oscript logic does not reference asset `A` at all (only handles `base`), so under normal circumstances any leftover `A` balance sits unused at the AA, or the AA's `if` condition legitimately fails for this trigger, forcing a bounce.
4. Before the AA processes the trigger (or by the time attestor state matters again for a later trigger causing a bounce), the attestor revokes `UserAddr`'s attestation for asset `A` (a normal, permitted, single attestor action, independent of the AA).
5. The AA bounces: `bounce()` in `aa_composer.js` attempts to refund asset `A` to `trigger.address` (`UserAddr`), but `validatePaymentInputsAndOutputs` rejects it with `"some output addresses are not attested"` (`validation.js` line 2637-2638).
6. `sendUnit` calls `bounce(err)` again; since `bBouncing` is already true, `finish(null)` is returned — no response unit is created, and neither the base bytes nor asset `A` are refunded. The deposited funds remain permanently stuck at AA address `X` with no path to recovery through the standard bounce mechanism.
