### Title
Webhook signature verification and target-repository resolution use different, attacker-controllable payload fields, allowing cross-organization/cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization webhook secret to validate the HMAC signature against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')`. Once the signature check passes, the actual event handlers (e.g. `PushHandler`, `Handler#stacks`) resolve the target `Repository`/`Stack` using a *different* payload field, `payload.dig('repository', 'full_name')`. Both fields live inside the same HMAC-signed request body, but nothing ties the verified organization to the repository that is ultimately acted upon.

### Finding Description
`verify_signature` picks the app config to verify against based on payload content, not a trusted, externally-authenticated source: [1](#0-0) [2](#0-1) 

The Shipit engine supports multiple GitHub Apps/organizations, each with its own `webhook_secret`, resolved via `Shipit.github(organization:)` / `github_app_config`: [3](#0-2) 

After the signature is accepted, the actual event dispatch and target resolution use a separate field, `repository.full_name`, completely decoupled from the field used to pick the signing secret: [4](#0-3) [5](#0-4) 

Because `verify_webhook_signature` computes the HMAC over `request.raw_post` as a whole using whichever org's secret is picked from `repository.owner.login`, an attacker who legitimately controls a valid signed webhook for *their own* org (e.g., they installed/administer the Shipit GitHub App on a repository/org they own, which is common in a multi-tenant Shipit setup covering several organizations) can freely construct the JSON body themselves. They can set `repository.owner.login` to their own org (so the correct, known-to-them webhook secret is used and the HMAC validates), while independently setting `repository.full_name` to any other tracked repository (e.g. a victim organization's repo also configured in the same Shipit instance). The equality that should hold — `organization that authenticated == organization owning the repository written` — is broken: verification proves "this request was signed by org A's secret", but the handlers act on "org/repo B", which was never authenticated.

Additional confirmation that the secret-selection field is attacker-visible/controllable in the request body and not derived from a trusted per-app routing key: `verify_webhook_signature` even short-circuits to `true` when no `webhook_secret` is configured for the selected org: [6](#0-5) 

### Impact Explanation
An attacker who is a legitimate GitHub App installer/administrator for one organization/repo tracked by a shared Shipit instance can forge webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) that are processed as if they originated from a *different* organization/repository also tracked by the same instance. This enables cross-repository/cross-organization state manipulation: triggering `GithubSyncJob`/deploy-relevant syncs, creating fabricated commit statuses, archiving/unarchiving review stacks, or adding/removing team memberships on a repository the attacker does not control — an unauthorized cross-repository write, matching the High/Critical impact bar for "cross-repository writes" via a broken authentication binding.

### Likelihood Explanation
Requires the attacker to be a legitimate, valid recipient of a webhook secret for *some* org tracked by the instance (i.e., they administer their own GitHub App installation/org that Shipit also tracks) — a realistic scenario for any multi-tenant Shipit deployment tracking multiple organizations/customers, since `Shipit.github_organizations`/`github_app_config` explicitly supports multiple orgs with independent secrets. No Shipit session, ApiClient token, or GitHub write access to the victim repository is required; only crafting a raw HTTP POST with a self-computed valid signature.

### Recommendation
Bind webhook processing to the same field used for signature verification: derive the acting repository/stack strictly from `repository.owner.login` (or an equivalent trusted key) rather than the independently-parsed `repository.full_name`, or verify that `repository.full_name`'s owner segment matches `repository.owner.login` before dispatching to handlers. Alternatively, route/verify per organization using a value that is not embedded in attacker-controlled JSON (e.g. a URL path segment identifying the configured organization, checked against the payload for consistency).

### Proof of Concept
1. Attacker administers GitHub org/repo `attacker-org/attacker-repo`, which has Shipit's GitHub App installed with webhook secret `S_attacker` (a legitimate, separate tenant in the same Shipit instance that also tracks `victim-org/victim-repo`).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_attacker, raw_body)` themselves and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and validates successfully since the attacker used their own valid secret.
5. `Handler#stacks` resolves via `Repository.from_github_repo_name("victim-org/victim-repo")` (from `repository.full_name`), and `PushHandler#process` triggers `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` against the victim's stack — a write triggered under a false organizational authentication binding.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
