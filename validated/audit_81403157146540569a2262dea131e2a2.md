### Title
Membership webhook accepted for any GitHub organization whose config omits a `webhook_secret`, allowing forged team-membership escalation into `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to verify against purely from an attacker-controlled JSON field (`organization.login`/`repository.owner.login`), and `GitHubApp#verify_webhook_signature` treats a blank/absent `webhook_secret` as automatically verified. This breaks the equality "GitHub organization that authenticated the webhook" == "organization the payload is trusted to write to," analogous to the Origami finding where `vestedReserves` (the trusted balance) is checked/used stale relative to the `redemption` request that is actually honored.

### Finding Description
`verify_signature` derives the org used for verification directly from the untrusted payload: [1](#0-0) [2](#0-1) 

The signature check itself trivially passes when no secret is configured for that organization: [3](#0-2) 

Once verification is bypassed/passed, `params` (fully attacker-controlled) is dispatched unchanged to handlers, e.g. `MembershipHandler`, which creates/updates a `Team` and adds arbitrary members to it based solely on the payload: [4](#0-3) 

`Shipit.github_teams` — the set of teams gating access via `User#authorized?` — is derived from the GitHub App's configured `oauth_teams`, matched by `Team.find_or_create_by_handle`: [5](#0-4) [6](#0-5) 

If a deployed instance configures multiple GitHub organizations (as the multi-tenant config format supports, per `app_id/installation_id/webhook_secret` per org) and any one of them is left with `webhook_secret` unset — which the code explicitly tolerates as "return true unless webhook_secret" — an unauthenticated network attacker can `POST /webhooks` with `X-Github-Event: membership`, set `organization.login` to that unsecured org, and add themselves (or any GitHub login) as a member of the team matching `Shipit.github_teams`. This directly defeats the authorization binding enforced in `force_github_authentication`/`authorized?`.

### Impact Explanation
This maps to the explicitly listed High-severity impact "escalation into `Shipit.github_teams` authorization." An attacker who already has (or creates) a GitHub account with the target login can be granted membership in the gating team purely by forging an HTTP POST, with no GitHub App private key, no webhook secret, and no prior repository access — provided the deployment includes at least one configured organization lacking a `webhook_secret` (which the codebase explicitly supports as a valid, non-erroring configuration state, see `docs/setup.md`'s `webhook_secret: some-secret-value` shown only as "optional").

### Likelihood Explanation
Likelihood is conditional: it requires an operator to have configured at least one GitHub organization without a `webhook_secret` (explicitly documented as optional in `docs/setup.md`, and modeled as `nil` in `test/dummy/config/secrets_double_github_app.yml`). Given the engine ships this as a supported, undocumented-as-dangerous configuration and defaults to treating it as "always verified," this is a real and not merely theoretical misconfiguration risk baked into the trust model rather than a hypothetical host-application deviation.

### Recommendation
Do not derive the verification org from the unauthenticated payload before verification; instead require every configured GitHub organization to have a non-blank `webhook_secret`, and fail closed (reject, not auto-accept) when one is absent, rather than `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Deploy Shipit with two orgs configured, `OrgOne` (with `webhook_secret`) and `OrgTwo` (`webhook_secret: nil`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. As an unauthenticated network attacker, `POST /webhooks` with header `X-Github-Event: membership` and JSON body: `{"action":"added","team":{"id":1,"name":"Team","slug":"team","url":"https://github.com/x"},"organization":{"login":"OrgTwo"},"member":{"login":"attacker-login"}}`.
3. `verify_signature` resolves `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. `MembershipHandler#process` runs, creating the team (or matching an existing `Shipit.github_teams` team by id) and adding `attacker-login` as a member, per `app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`.
5. If `attacker-login`'s GitHub account subsequently authenticates via OAuth, `User#authorized?` now returns true, granting access previously gated by team membership.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
