### Title
Hookify plugin's `block` rule enforcement is bound to a hardcoded tool whitelist and is trivially bypassed by any other file/command tool - (File: `plugins/hookify/hooks/pretooluse.py`, `plugins/hookify/core/rule_engine.py`, `plugins/hookify/core/config_loader.py`)

### Summary
The hookify plugin lets a user define `event: bash` / `event: file` rules with `action: block` to prevent dangerous operations (e.g. `rm -rf`, edits to `.env`/credential files). The enforcement, however, is entirely implemented inside the plugin's own `PreToolUse` hook script and depends on a hardcoded tool-name whitelist (`Bash` for "bash" events; `Edit`, `Write`, `MultiEdit` for "file" events). Any tool call that is not one of these four literal names is invisible to the rule engine, so the "block" protection can be bypassed by using any other tool capable of running commands or writing files — most notably `NotebookEdit`, MCP-provided filesystem/shell tools, or a subagent (`Task`) invocation whose internal tool name differs — exactly mirroring the reported bug class of a lock/guard implemented in the wrong layer that the actual operation path ignores.

### Finding Description
The `PreToolUse` hook entrypoint decides which rule set to load purely from `tool_name`: [4](#0-3) 

If `tool_name` is anything other than `Bash`/`Edit`/`Write`/`MultiEdit` (for example an MCP filesystem-write tool, `NotebookEdit`, or a custom tool), `event` stays `None`. `load_rules(event=None)` then skips the event filter entirely: [5](#0-4) 

So every enabled rule is handed to the engine regardless of the tool involved. The rule still must match via `_rule_matches`, but that check falls back to `_extract_field`, which — like the hook entrypoint — only knows how to pull `command`/`file_path`/`new_text`/`content` out of the tool_input for the same four literal tool names (`Bash`, `Write`, `Edit`, `MultiEdit`): [6](#0-5) 

For any other tool name, `_extract_field` returns `None`, `_check_condition` returns `False`, and the rule silently never matches — even though `action: block` was configured and intended to unconditionally stop the operation. The "lock" is real (and documented to users as a hard `block`), but it is enforced only inside this narrow tool-name whitelist rather than at the point where the dangerous effect (arbitrary file write / command execution) actually happens — analogous to the reported issue where the pause flag lived in `SpiritFactory` but the unguarded `swap()` execution path lived in `PancakePair`.

### Impact Explanation
A user or org relying on a hookify `block` rule to enforce a security boundary (e.g. "never write to `.env`", "never run `rm -rf`") gets a false sense of protection: the guard only fires for the literal `Bash`/`Edit`/`Write`/`MultiEdit` tool names. Any other reachable tool that can write files or run shell-equivalent operations — an installed MCP server's file-write/exec tool, `NotebookEdit` (which can embed and execute code in notebook cells), or any tool invoked from within a subagent — bypasses the block outright, since the enforcement never runs at all rather than degrading to a warning. This can let an unprivileged/compromised prompt path perform the exact operation the user configured hookify to block.

### Likelihood Explanation
Likelihood is moderate-to-high in any environment that (a) uses the hookify plugin's `block` action as a real safety control and (b) has any additional tool surface beyond the four hardcoded names — which is common, since MCP servers and `NotebookEdit` are standard, first-class Claude Code capabilities. No special privileges are needed to trigger the bypass; it only requires directing the agent (via a normal prompt, or content encountered while browsing/reading files) to perform the blocked action through a different tool.

### Recommendation
Move rule matching off the hardcoded tool-name whitelist: derive the `event`/field-extraction logic generically (e.g. from the tool's declared input schema, or by checking common field names like `file_path`/`command`/`content` across all tools rather than special-casing four names), or fail closed by treating unmatched tools as event `"all"` so conditions are still evaluated. At minimum, document prominently that hookify's `block` action only covers `Bash`, `Edit`, `Write`, and `MultiEdit`, and that any other tool (MCP tools, `NotebookEdit`, subagent tool calls with different names) is unguarded by design.

### Proof of Concept
1. Create `.claude/hookify.block-env.local.md`:
```markdown
---
name: block-env-writes
enabled: true
event: file
action: block
conditions:
  - field: file_path
    operator: regex_match
    pattern: \.env$
---
Blocked: writes to .env files are not allowed.
```
2. Ask Claude to write secrets to `.env` using the `Write` tool → hookify's `PreToolUse` hook correctly returns `permissionDecision: deny` (per `rule_engine.py` lines 72-79), and the write is blocked.
3. Ask Claude to perform the equivalent write via any tool not in `{Bash, Edit, Write, MultiEdit}` — e.g. an installed MCP filesystem-write tool, or via `NotebookEdit` targeting an `.ipynb` that indirectly writes the secret out through a cell's code execution — and observe that `pretooluse.py` computes `event = None`, `load_rules(None)` returns the rule anyway, but `_extract_field` returns `None` for `file_path` on that tool name, so `_rule_matches` returns `False` and the operation proceeds unblocked, defeating the configured `block` rule entirely.
