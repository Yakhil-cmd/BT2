This Traefik bug is a network-listener-layer resource exhaustion (unauthenticated TCP/TLS handshake stall in a reverse-proxy's ACME TLS-ALPN fast path). It is not reachable through a signed extrinsic, enabled contract deploy/call, or permitted XCM execute/send/transfer as required by the analog scan's entry-point criteria, and it falls squarely into the explicitly excluded bug class of "oversized-input/flooding/generic resource-exhaustion claims" at the networking/transport layer rather than a FRAME/XCM/runtime state-transition invariant violation.

I searched the relevant polkadot-sdk networking code for an equivalent unauthenticated-handshake-without-timeout pattern. The codebase's actual analogs in `substrate/client/network` consistently apply explicit timeouts to remote-controlled handshakes/negotiations rather than omitting them:

- Notifications substream opening uses an explicit `OPEN_TIMEOUT` around handshake negotiation: [1](#0-0) , applied via `.with_timeout(OPEN_TIMEOUT)` when constructing outbound substream requests: [2](#0-1) .
- The libp2p WebSocket/TCP telemetry transport wraps connection attempts (including WS HTTP upgrade) in a `CONNECT_TIMEOUT`: [3](#0-2) [4](#0-3) .
- PVF worker socket handshake acceptance is bounded by a `spawn_timeout` race via `futures::select!`, so a stalled handshake can't hang the accepting task indefinitely: [5](#0-4) .
- Litep2p's negotiation layer surfaces explicit `NegotiationError::Timeout`/dial timeout classifications, indicating timeout enforcement is built into the transport/negotiation path rather than absent: [6](#0-5) .

None of these represent a runtime-level (FRAME/XCM/contracts) attacker entry point with attacker-controlled state mutation, issuance, or unauthorized dispatch, so they don't qualify as a demonstrable analog under this scan's required scope even setting aside the explicit exclusion of generic resource-exhaustion/DoS findings.
