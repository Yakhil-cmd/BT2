### Title
Crafted swap route can add wallet-draining token transfers to a user’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The controller accepts caller-provided `swap` bytes and forwards them unchanged to the configured router after authorizing only the controller’s bounded input transfer. [1](#0-0)  The route format indexes arbitrary pool addresses and dispatches those addresses to venue adapters without an allowlist. [2](#0-1) [3](#0-2)  A malicious pool can therefore execute below the victim’s `require_auth` scope and request an unrelated `token.transfer(victim, attacker, amount)`, which simulation records as a child authorization. [4](#0-3)  If the victim signs the simulated tree without detecting that extra child, the unauthorized-looking wallet transfer executes. [5](#0-4) 

### Finding Description
Strategy entrypoints expose route bytes directly to users: `swap_collateral(caller, account_id, current, amount, new, swap)` passes `swap` into `process_swap_collateral`. [6](#0-5)  That function authorizes the account owner or delegate, withdraws the selected collateral, and calls the shared strategy swap path with the attacker-controlled route. [7](#0-6)  `multiply`, `swap_debt`, and `repay_debt_with_collateral` expose the same pattern. [8](#0-7) [9](#0-8) 

The controller’s own authorization is narrow and correct: it authorizes exactly `token_in.transfer(controller, router, amount_in)` with no nested invocations. [10](#0-9)  The missing boundary is the user’s root authorization: the opaque `swap` payload may identify a deployed contract as a pool, and venue adapters invoke that contract. [11](#0-10) [12](#0-11)  Structural decoding checks index bounds and program shape, but it does not establish that `idx_a` names an honest or known pool. [13](#0-12) 

A malicious venue can use the caller authorization context to invoke `victim_token.transfer(victim, attacker, amount)` while still returning enough output for the swap’s balance-delta and risk checks to pass. The repository’s regression test demonstrates that simulation nests the theft under the victim’s `swap_collateral` authorization and that enforcement accepts it when the returned tree includes that child. [14](#0-13) [5](#0-4) 

### Impact Explanation
This is theft of arbitrary user-held token balances that are unrelated to the amount routed through the lending operation. The victim may receive a nominally valid swap result and a solvent position while a separate token transfer empties another wallet asset. [15](#0-14)  The controller’s post-call checks only bound controller-held `token_in` spending and require positive `token_out` receipt; they do not inspect unrelated child transfers in the signed auth tree. [16](#0-15) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious pool contract and construct the route bytes because pool addresses come from the route’s `assets` registry. [17](#0-16)  Exploitation requires victim interaction: a wallet, SDK, or user must sign the authorization tree containing the malicious child transfer. Honest clients can reject it because an honest controller strategy requires no child under the user authorization, while the malicious path introduces one. [18](#0-17)  The risk is nevertheless material because the route is opaque bytes and transaction simulation naturally produces the poisoned tree for signature. [19](#0-18) 

### Recommendation
Constrain route pools to a governance-approved venue/pool registry, or replace opaque user-supplied pool addresses with venue identifiers resolved against that registry. At minimum, make the protocol/SDK decode every submitted `StrategyPayload`, enumerate all nested authorization invocations produced by simulation, and reject any tree containing a child transfer other than the explicitly documented router input pull. Add a regression assertion for all strategy entrypoints equivalent to the existing `swap_collateral` test.

### Proof of Concept
1. Deploy a pool contract whose `swap` implementation calls `token::Client::new(wallet_token).transfer(victim, attacker, wallet_balance)` and also returns/transfers enough route output to satisfy `min_out`.
2. Build `StrategyPayload` with the malicious pool in `assets`, a valid swap opcode, and token indices producing a positive output.
3. Ask the victim to call `Controller::swap_collateral(caller=victim, account_id, current, amount, new, swap)` using the payload.
4. During simulation, the malicious pool’s transfer is recorded as a child of the victim’s `swap_collateral` invocation. [20](#0-19) 
5. If the victim signs that simulated authorization tree, enforcement executes the transfer and the attacker receives `wallet_balance`, while the victim’s requested collateral swap still succeeds. [5](#0-4)

```rust
/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
```

**File:** docs/explanation/threat-model.md (L154-164)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
