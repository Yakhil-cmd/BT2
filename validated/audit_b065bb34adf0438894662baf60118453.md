### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` but every event handler routes and writes based on the unchecked `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. Every webhook `Handler` (push, status, pull_request, check_suite), however, determines which `Stack`/`Repository` to act on using a completely different, unverified field: `payload.dig('repository','full_name')`. The signature never binds these two values together, so nothing prevents a payload whose `repository.owner.login` matches one organization's secret while `repository.full_name` points at a stack belonging to a different organization.

### Finding Description
Signature verification: [1](#0-0) 
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```
and the org-selection field: [2](#0-1) 

Every handler's target repository, by contrast, is computed from `full_name`, not `owner.login`: [3](#0-2) 

`Shipit.github(organization:)` looks up per-organization app configs and their independent `webhook_secret`s: [4](#0-3) 

The `verify_webhook_signature` HMAC check only proves that the raw body was signed with *that organization's* secret - it does not constrain any field inside the JSON body, including `repository.full_name`: [5](#0-4) 

The binding that should hold is: `organization authenticated by signature == organization whose repository is written to`. Because `repository_owner` (used to pick the secret) and `repository_name`/`full_name` (used to pick the target `Stack`) are independently attacker-controlled fields inside the same signed JSON body, an attacker who controls the webhook secret for *any one* configured organization (e.g. an org admin who legitimately set up a Shipit organization webhook for their own org, per `test/fixtures/shipit/github_hooks.yml`'s `Organization`/`Repo` hook types) can forge a payload with `repository.owner.login` set to their own org (so it passes signature verification against their known secret) but `repository.full_name` set to a *different* organization's repository that has a stack configured in the same Shipit instance.

This lets the attacker drive `StatusHandler` to create arbitrary CI `Status` records for commits belonging to a repository/stack they do not control: [6](#0-5) , or drive `PushHandler` to trigger `stack.sync_github` for another org's stack: [7](#0-6) .

### Impact Explanation
Forging a "success" status for an arbitrary commit in a stack the attacker does not own is significant: `Commit#deployable?` and merge-queue eligibility depend on `success?`/`blocked?`, which are derived from ingested statuses: [8](#0-7) . Forged successful CI statuses can make an otherwise-failing or unreviewed commit appear deployable/mergeable in a stack belonging to a different, victim organization, i.e. cross-repository/cross-organization forgery of deploy-gating state - a High-severity escalation matching "unauthorized deploy" and "cross-repository writes" categories, achieved purely by an attacker who legitimately controls one organization's webhook secret but never obtained credentials for the victim organization/repository.

### Likelihood Explanation
Requires only that an attacker administers (or can register) a GitHub organization/repository webhook against the shared Shipit instance and knows that organization's own configured `webhook_secret` (which they choose or are told when they set it up) — no access to the victim org's secret, `ApiClient` token, or GitHub credentials for the victim repo is needed. This is realistic in any deployment where Shipit serves multiple GitHub organizations/repositories with distinct per-org `webhook_secret`s (the `github_app_config`/`TOP_LEVEL_GH_KEYS` multi-org config path in `lib/shipit.rb` exists specifically to support this), which is a documented, supported configuration rather than a misconfiguration.

### Recommendation
Bind the field used to select the verification secret to the field used for routing: verify the HMAC using the organization/app config resolved from `repository.full_name`'s owner (or verify that `repository.owner.login`/`organization.login` equals the owner segment of `repository.full_name`) before dispatching to handlers, rejecting the webhook if they diverge.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `attacker-org` and `victim-org`, each with a distinct `webhook_secret` (multi-org config per `github_app_config`).
2. Attacker, an admin of `attacker-org`, creates a GitHub organization webhook pointed at Shipit's `/webhooks` endpoint using a secret of their choosing (which they know), matching `attacker-org`'s configured `webhook_secret`.
3. Attacker crafts a `status` (or `push`) event JSON body with `repository.owner.login = "attacker-org"` (or `organization.login = "attacker-org"`) but `repository.full_name = "victim-org/victim-repo"`, computes the HMAC over this raw body using the `attacker-org` secret, and sends it with header `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature since it matches `attacker-org`'s secret.
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which resolves the target via `Handler#repository_name` = `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, and calls `commit.create_status_from_github!(params)` for commits in `victim-org`'s stack, injecting a forged CI status the attacker was never authorized to set.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
