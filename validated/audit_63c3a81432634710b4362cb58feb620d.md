### Title
Account authorization trusts cached `account.owner` instead of the position-NFT's current owner, letting a prior owner keep spending authority after the NFT is transferred - ([File: contracts/controller/src/account.rs])

### Summary
`require_owner_or_delegate` / `is_owner_or_delegate` authenticate spending authority (borrow, withdraw, multiply, swap_debt, swap_collateral, repay_debt_with_collateral, migrate_from_blend, and the liquidation `Credit` receiver check) against the `owner` field stored on the `Account` struct, not against the position-NFT's current `owner_of`. This mirrors the CoreDNS bug class: the check consults a secondary, possibly stale status signal (the cached owner) instead of performing verification against the authoritative source (the NFT, since `account_id == token_id`). The codebase itself maintains two different notions of ownership: `require_account_owner` resolves the owner via `storage::account_owner(env, account_id)` (the NFT-backed lookup), while `is_owner_or_delegate` compares `caller == *owner` where `owner` is passed in as `account.owner` [1](#0-0) .

### Finding Description
Every spending path loads `Account` from storage and calls `require_owner_or_delegate(env, account_id, caller, &account.owner)` — see `AccountGuard::Migrate` and `AccountGuard::Multiply` in `load_or_create_account` and the debt/collateral position flows [2](#0-1) . If the position NFT is transferred (position-nft `transfer`/`approve` are reachable unprivileged paths per the engagement scope), the `Account` struct's `owner` field is only updated if a transfer hook resyncs it. The delegate set is also keyed by the stored owner (`storage::get_delegates(env, account_id, owner)`), compounding the staleness: delegates authorized under the old owner retain authority even after sale.

The counterpart `require_account_owner` explicitly re-reads `storage::account_owner` rather than trusting the cached field [3](#0-2) , showing the codebase knows the two can diverge — the same distinction the CoreDNS tsig plugin missed between the transport's `TsigStatus()` and real signature verification.

### Impact Explanation
After an account NFT changes hands, the previous owner (or their delegates) retains full spending authority over the account's collateral and debt capacity: they can `withdraw` all collateral to themselves and `borrow` up to the account's LTV into an arbitrary `to` address, draining the account the buyer paid for — theft of user funds. Conversely, if `account.owner` is synced on transfer but stored positions/delegates are keyed to the old owner, the new owner may be unable to withdraw (permanent freezing of funds).

### Likelihood Explanation
High if the cached field is not resynced on transfer: NFT transfers are a normal, unprivileged operation and the attacker is simply the seller retaining authority. Uncertainty: I could not verify within available iterations whether `position-nft::transfer` calls back into the controller to rewrite `account.owner`. If such a hook exists and is complete, the cached and canonical owners cannot diverge and the finding collapses; the two-source design and the separate `require_account_owner` path suggest it is at least not uniformly enforced.

### Recommendation
Make `is_owner_or_delegate`/`require_owner_or_delegate` resolve the owner through `storage::account_owner(env, account_id)` (the NFT's `owner_of`) at check time, as `require_account_owner` already does, instead of reading `account.owner`. Key delegate storage by `account_id` alone so grants survive transfers only via the new owner's explicit `add_delegate`. Verify in `position-nft` whether `transfer` resyncs controller state; if it does, remove the duplicate cached `owner` field to eliminate the divergence permanently.

### Proof of Concept
1. Alice supplies XLM/USDC collateral to `account_id` A via `controller::supply`, then transfers position-NFT token A to Bob (or Bob buys it).
2. `storage::get_account(A).owner` still holds Alice; `require_owner_or_delegate` short-circuits on `caller == owner` before ever consulting the NFT [4](#0-3) .
3. Alice calls `controller::withdraw(alice, A, withdrawals, to=alice)` and `controller::borrow(alice, A, borrows, to=alice)`; both pass the owner check against the stale field and move Bob's collateral and newly minted debt proceeds to Alice.
4. Bob, the NFT owner, is rejected by `require_owner_or_delegate` on the same paths even though `require_account_owner` (used by `add_delegate`/`renew_account`) would accept him — confirming the two owner sources diverge.

pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}

/// Requires the owner or a registered, active manager delegated by that owner.
pub(crate) fn require_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) {
    if is_owner_or_delegate(env, account_id, caller, owner) {
        return;
    }
    panic_with_error!(env, GenericError::NotAuthorized);
}

/// Returns metadata after verifying that `caller` currently owns the account NFT.
pub(crate) fn require_account_owner(env: &Env, account_id: u64, caller: &Address) -> AccountMeta {
    let meta = storage::get_account_meta(env, account_id);
    let owner = storage::account_owner(env, account_id);
    assert_with_error!(env, owner == *caller, GenericError::AccountNotInMarket);
    meta
}
