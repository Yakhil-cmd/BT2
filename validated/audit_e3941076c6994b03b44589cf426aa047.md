Confirmed: there's no uniqueness check anywhere in `validateDefinition`'s `'r of set'` handler (or `'weighted and'`, `'in data feed'`, `'in merkle'`, `'attested'`) that would prevent the same sub-branch/address/pubkey from being listed multiple times within the `set` array.

### Title
`'r of set'` / `'weighted and'` definitions allow duplicate signer branches, defeating multisig thresholds - (File: definition.js)

### Summary
`validateDefinition()` in `definition.js` validates the `'r of set'` and `'weighted and'` operators by checking `args.set` is an array with a minimum length and that `required`/`weight` values are sane, but it never checks that the elements of `args.set` are distinct. [1](#0-0)  The same applies to `'weighted and'`. [2](#0-1)  A definition author can therefore list the same `["address", X]` or `["sig", {pubkey: P}]` leaf multiple times inside one `set`.

### Finding Description
When a unit author (or shared-address definition author) crafts a definition such as:
```
["r of set", { required: 2, set: [
  ["sig", {pubkey: P_A}],
  ["sig", {pubkey: P_A}],   // duplicate of the first branch
  ["sig", {pubkey: P_B}]
]}]
```
`validateDefinition` accepts it because it only checks `args.set.length >= 2` and `required <= args.set.length`, with no uniqueness constraint on the set members. [3](#0-2) 

During spending, `validateAuthentifiers()` evaluates each `'sig'` branch independently by looking up `assocAuthentifiers[path]` for that specific path and validating the signature with `ecdsaSig.verify(objValidationState.unit_hash_to_sign, signature, args.pubkey)`. [4](#0-3)  Because ECDSA verification only depends on the message hash, signature, and public key (not on the JSON path), the holder of key `P_A` can supply the exact same signature value at both `path.0` and `path.1`, satisfying both branches with a single real signature. The `'r of set'` counting logic then reaches `count >= args.required` (2) using only one actual private key. [5](#0-4) 

This is analogous to the reported `topHolders` issue: an array (`args.set`) that is supposed to represent a set of distinct signers/oracles/weights is never validated to be a unique set, so a single value can be silently duplicated to manipulate a threshold count.

### Impact Explanation
This breaks the security assumption underlying every `M-of-N` shared address, wallet, or asset-spending condition built with `'r of set'` (and the weight-manipulation analog with `'weighted and'`). Co-signers who agree to fund an address believing it requires cooperation of `N` distinct parties (e.g., a "2-of-3" corporate/escrow wallet) can be defrauded if the definition author embeds one address/pubkey twice: that single party can then unilaterally satisfy the "2 of 3" (or higher) requirement and spend funds without the consent of the other nominal co-signers. This is a direct unauthorized-spending / fund-loss vulnerability for any shared address or AA-controlled definition relying on `'r of set'`/`'weighted and'` thresholds.

### Likelihood Explanation
Exploitation requires the malicious party to control (or influence) the crafting of the address definition before other parties commit funds — realistic in shared-address setups (e.g. `wallet_defined_by_addresses.js`) where one participant proposes the JSON definition and others may not manually audit it for duplicated leaves, since the definition is normally reviewed as a rendered "M of N" policy rather than raw JSON. Since `validateDefinition` performs no dedup check at any point (unit validation, AA address definitions, asset conditions), this is reachable purely from a standard address-definition/unit-posting path with no privileged access needed.

### Recommendation
In the `'r of set'` and `'weighted and'` cases of `validateDefinition`, reject definitions where `args.set` contains duplicate/equivalent sub-definitions (e.g., by comparing `JSON.stringify` of each normalized branch, or specifically disallowing repeated `['address', X]` / `['sig', {pubkey}]` / `['hash', {hash}]` leaves within the same set), mirroring the post-audit fix described for the `topHolders` array (rejecting duplicates and zero/invalid addresses).

### Proof of Concept
1. Two parties, A and B, agree to create a shared address requiring "2 of 3" signatures, expecting participants A, B, and C.
2. Party A actually submits the definition:
```json
["r of set", { "required": 2, "set": [
  ["sig", {"pubkey": "<A's pubkey>"}],
  ["sig", {"pubkey": "<A's pubkey>"}],
  ["sig", {"pubkey": "<B's pubkey>"}]
]}]
```
3. `validateDefinition` accepts this as a valid 2-of-3 definition since it only checks array length and `required <= set.length`. [3](#0-2) 
4. B and C fund the resulting address, believing 2 independent signers are required.
5. When spending, A supplies the same ECDSA signature for both `r.0` and `r.1` authentifier paths; `validateAuthentifiers` verifies both independently and successfully, reaching `count (2) >= required (2)`, letting A spend alone. [4](#0-3) [5](#0-4)
