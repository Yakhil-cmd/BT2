### Title
Webhook signature verified against the organization derived from `repository.owner.login`, but events are applied to the repository named in the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC signature against using `repository_owner`, which is read from the attacker-controlled JSON body (`repository.owner.login`, falling back to `organization.login`). Once the signature matches, the raw, still-unvalidated payload is dispatched to handlers that resolve the actual repository/stack to act on from a **different** field, `repository.full_name` (`Shipit::Webhooks::Handlers::Handler#repository_name`). Nothing ties `full_name` to `owner.login`/`organization.login`, so the organization whose secret authenticated the request is not the same as the repository the handlers subsequently write to.

### Finding Description
`verify_signature` computes the signing organization purely from the payload: [1](#0-0) [2](#0-1) 

The `Shipit.github(organization: repository_owner)` app is picked purely from `repository.owner.login`/`organization.login`, and `github_app.verify_webhook_signature` only proves the request was signed with that organization's `webhook_secret`: [3](#0-2) 

Once verification passes, the raw JSON body is handed unchanged to every registered handler for the event: [4](#0-3) 

Handlers (e.g. `PushHandler`, pull-request handlers) determine the repository/stack to mutate from `payload.dig('repository', 'full_name')` - a completely separate JSON field never covered by the signature-selection logic: [5](#0-4) [6](#0-5) [7](#0-6) 

Shipit explicitly supports configuring multiple GitHub organizations, each with its own `webhook_secret`, exactly the scenario where this mismatch is exploitable: [8](#0-7) 

**Binding broken:** `organization authenticated (repository.owner.login / organization.login, checked against that org's webhook_secret)` ≠ `repository written (repository.full_name, used unchecked by handlers to select the Stack/Repository to mutate)`.

An attacker who legitimately controls (or has installed the Shipit GitHub App for) *any one* configured organization knows that organization's `webhook_secret` (it is configurable per-organization by design, e.g. because they administer their own org's app settings) can:
1. Sign a forged webhook body with their own organization's secret so `owner.login`/`organization.login` = their org (passes `verify_signature`).
2. Set `repository.full_name` inside the same payload to `"victim-org/victim-repo"` — a repository/stack they have no access to.
3. The signature check passes (their org's secret matched), but the handler that actually executes (`PushHandler`, PR handlers, etc.) resolves and mutates the stack belonging to `victim-org/victim-repo`.

### Impact Explanation
Because `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on stacks matched purely by the forged `repository.full_name`, an attacker who is only authorized to sign webhooks for their own configured organization can force a sync/build cycle on a stack belonging to a different, unrelated repository, and — if continuous deployment is enabled on that stack — trigger an unauthorized deploy. Pull-request handlers similarly allow archiving/unarchiving review stacks or mutating `PullRequest` records for repositories the attacker does not own. This satisfies the "unauthorized deploy" / cross-repository write impact bucket without any GitHub credentials, Shipit session, or API token — only knowledge of a webhook secret for a completely different, unrelated organization the attacker legitimately administers.

### Likelihood Explanation
Requires Shipit to be configured with more than one GitHub organization/app (each with a distinct `webhook_secret`), which is an explicitly documented and supported configuration. Any principal who administers one of those organizations' GitHub App settings (and therefore knows/controls that org's `webhook_secret`) can exploit this without needing access to the victim organization or repository at all — a purely payload-crafting attack against a public HTTP endpoint (`/webhooks`).

### Recommendation
After signature verification, validate that the organization/owner used to select the verifying secret is the same as the owner embedded in `repository.full_name` (and any other repository-identifying fields consumed by handlers) before dispatching to handlers. Alternatively, resolve the repository/stack strictly from the same field used for signature-secret selection, or bind webhook secrets per-repository (not per-organization) so a forged `full_name` cannot cross organizational boundaries.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret `S1`) and `victim-org` (secret `S2`), per the multi-org config format in `config/secrets.development.example.yml`.
2. Attacker, who administers `attacker-org`'s GitHub App and thus knows `S1`, crafts a `push` webhook body:
```json
{
  "ref": "refs/heads/master",
  "after": "<victim commit sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S1, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and verifies successfully against `S1`.
5. `PushHandler` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github`/enqueues `GithubSyncJob` on `victim-org`'s stack, which the attacker has no authorization over.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
