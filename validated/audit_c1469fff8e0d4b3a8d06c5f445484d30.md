### Title
Untracked-file review bypass via mtime-preserving content rewrite - (File: plugins/security-guidance/hooks/diffstate.py)

### Summary
`compute_v2_review_set` excludes a pre-existing untracked file from `review_set` whenever `_unchanged_since_baseline` finds its current `st_mtime_ns` equal to the value captured at UPS time, with no content/hash comparison. An attacker who can trigger any write to that file during the turn (e.g., a malicious build/test script invoked via Bash) can rewrite its content and then reset its mtime to the pre-turn value with `os.utime`, causing the modified file to be silently excluded from review.

### Finding Description
`_list_untracked` (plugins/security-guidance/hooks/diffstate.py:319-351) snapshots `{repo-relative path: st_mtime_ns}` for every untracked, non-ignored file at UPS time, saved as `untracked_at_baseline`. At Stop time, `compute_v2_review_set` (plugins/security-guidance/hooks/diffstate.py:353-438) computes: [1](#0-0) 

`_unchanged_since_baseline(p)` only compares `os.stat(p).st_mtime_ns` to the previously recorded value; it never inspects file content or a hash. Because `git status --porcelain` marks untracked files as `??` regardless of content changes, git-side signals cannot detect the modification either — mtime equality is the *sole* discriminator used to decide `preexisting_unchanged`, which is then subtracted from `untracked` to form `dirty_now`/`review_set`.

Exploit flow: the file must already exist as untracked before the turn begins (so it is captured in `untracked_at_baseline`). During the turn, a Bash tool invocation runs repo-controlled tooling (e.g., a `Makefile` target, npm script, or test-runner plugin the attacker planted as ordinary repo content) that: (1) `stat`s the file to read its current mtime, (2) overwrites its content with malicious payload, (3) calls `os.utime(path, ns=(atime_ns, mtime_ns))` to restore the exact original mtime. Since the mtime value is directly observable from the filesystem before the write (no secret needed), this restoration is trivial and deterministic. At Stop, `_unchanged_since_baseline` returns `True`, the file is placed in `preexisting_unchanged`, subtracted from `new_untracked`, and never enters `dirty_now` or `review_set` — even though `changed_since_count`/git-diff logic never runs against it either, since it's untracked and outside `changed_since`'s tracked-diff scope.

No existing guard mitigates this: there is no content hash, no size check, and no `git diff` equivalent for untracked files feeding into the exclusion decision.

### Impact Explanation
A malicious/altered untracked file (e.g., a script, config, or code file later read/executed by the workflow) silently escapes the type-design-analyzer/code-review pass that consumes `review_set`, breaking the documented invariant "reviewed set == changed set." This allows planted or backdoored content to persist across a Claude Code turn without triggering the security-guidance review, undermining the plugin's core detection guarantee for untracked files specifically.

### Likelihood Explanation
Requires: (1) a pre-existing untracked file present in the working tree before the current turn's UPS baseline capture, and (2) some process running during the turn (build script, test runner, git hook, editor plugin) that the attacker can influence to perform the stat/rewrite/utime sequence. Both preconditions are realistic in supply-chain-style scenarios where repo content (Makefiles, package.json scripts, pre-commit hooks) is attacker-influenced and executed via normal Bash tool usage. No elevated privileges, secrets, or race-condition timing beyond ordinary filesystem read/write access are needed — mtime restoration is deterministic, not probabilistic, making this fully repeatable once the preconditions hold.

### Recommendation
Bind the "unchanged since baseline" decision to content, not mtime alone: store a content hash (e.g., SHA-256) or file size+hash pair alongside mtime_ns in `untracked_at_baseline`, and only exclude a file when both mtime and content hash match. Alternatively, drop the mtime-only fast path entirely and always hash-compare untracked files at Stop against their UPS-captured digest.

### Proof of Concept
Unit test in `plugins/security-guidance/hooks/diffstate.py` test suite:
1. Initialize a git repo with one commit; create an untracked file `evil.txt` with content `"benign"`.
2. Call `_list_untracked(cwd)` to obtain `untracked_at_baseline = {"evil.txt": mtime_ns_0}`.
3. Simulate attacker rewrite: read `mtime_ns_0` via `os.stat`, overwrite `evil.txt` with `"malicious payload"`, then call `os.utime("evil.txt", ns=(atime_ns_0, mtime_ns_0))` to restore the original mtime exactly.
4. Call `compute_v2_review_set(cwd, baseline_sha, head_at_capture, untracked_at_baseline)`.
5. Assert `evil.txt` (as an absolute path) IS present in the returned `review_paths` / `review_set`. Current implementation fails this assertion — the file is excluded via `preexisting_unchanged`, demonstrating the invariant violation.
