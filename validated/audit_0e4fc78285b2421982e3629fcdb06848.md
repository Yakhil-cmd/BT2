### Title
Api::CCMenuController bypasses ApiClient stack-scoping, letting a stack-scoped token read CI status for any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` scoped to a single stack (`stack_id` set) can only resolve stacks it is authorized for, via the `stacks`/`stack` helper methods. `Shipit::Api::CCMenuController` overrides `#stack` to bypass this scoping entirely, resolving the stack directly from the unscoped `Stack` relation using the `stack_id` URL parameter. Any valid `ApiClient` token carrying the `read:stack` permission — including one deliberately scoped to only one stack — can therefore be used to fetch CCMenu/CI status (deploy success/failure, lock reason, stack name) for *any* stack in the Shipit instance, not just the one it was authorized for.

### Finding Description
`Api::BaseController` defines the authorization binding between an `ApiClient` and the stacks it may touch: [1](#0-0) 

This binding is: `stack requested ∈ (current_api_client.stack_id? ? {current_api_client.stack_id} : Stack.all)`.

`Api::CCMenuController` however defines its own `#stack` method that ignores `current_api_client` entirely and resolves any stack from the raw parameter: [2](#0-1) 

It only declares `require_permission :read, :stack`, which merely checks that the string `"read:stack"` exists in `ApiClient#permissions` — it never checks which specific stack the client is scoped to: [3](#0-2) 

So the equality that should hold — *the stack a token authorizes == the stack the request touches* — is broken here: `Api::CCMenuController#stack` touches `Stack.from_param!(params[:stack_id])` unconditionally, regardless of `current_api_client.stack_id`.

The engine explicitly supports creating stack-scoped tokens (an `ApiClient` with `stack_id` set, and its own `belongs_to :stack, optional: true` association), and the intended behavior of such scoping is validated elsewhere, e.g. in the stacks API test suite: [4](#0-3) 

`Api::CCMenuController` is the one endpoint that does not honor this contract.

### Impact Explanation
An `ApiClient` token that was deliberately minted to be scoped to a single stack (e.g. handed to an external CI dashboard, embedded in a CCMenu client URL, or given to a third-party integrator who is only supposed to see one project's deploy status) can be replayed with a different `stack_id` query parameter against `/api/1/stacks/:stack_id/ccmenu` to read another stack's deploy/lock state, name, and last build status/label — data belonging to a different stack the token holder was never authorized to see. This is an authorization-scope escalation across stacks: a credential that authenticates read access to `Stack A` ends up touching arbitrary stacks, matching the "High — unauthorized read of stack state" impact class.

### Likelihood Explanation
Any holder of a valid `read:stack`-permission API client token (including intentionally stack-scoped ones, which are a first-class supported feature) can trigger this by simply changing the `stack_id` in the request URL — no additional secret, session, or elevated privilege is required beyond the token they already legitimately hold for their own stack.

### Recommendation
Make `Api::CCMenuController#stack` honor the same scoping used by the rest of the API by delegating to the inherited `stacks`/`stack` helpers (i.e. resolve via `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`), so that a stack-scoped `ApiClient` cannot resolve a stack outside of `current_api_client.stack_id`.

### Proof of Concept
1. Create (or obtain) an `ApiClient` with `permissions: ["read:stack"]` and `stack_id` set to Stack A (e.g. via the CCMenu URL flow or directly assigning `stack_id`).
2. Using that client's `authentication_token`, issue: `GET /api/1/stacks/<STACK_B_ID_OR_NAME>/ccmenu?token=<token>` where Stack B is a stack the token was never scoped to.
3. Observe the response renders Stack B's CI project XML (name, lastBuildStatus, lastBuildLabel, etc.) despite the token being scoped only to Stack A — confirmed by `Api::CCMenuController#stack` resolving via unscoped `Stack.from_param!` rather than the client-scoped `stacks` relation used elsewhere in the API (`app/controllers/shipit/api/base_controller.rb:74-80` vs `app/controllers/shipit/api/ccmenu_controller.rb:27-36`).
