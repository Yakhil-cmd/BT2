### Title
Webhook signature is verified against an attacker-chosen organization while the write target (commit/repository) is taken from unrelated payload fields — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC against using `repository_owner`, a value taken from the *same untrusted payload* the attacker controls [1](#0-0) . `repository_owner` is derived from `params.dig('repository', 'owner', 'login')` (or the top-level `organization.login`) [2](#0-1) . If any organization configured on the Shipit instance has no `webhook_secret` set (a supported, sample configuration, see `config/secrets.development.shopify.yml`), `verify_webhook_signature` returns `true` unconditionally [3](#0-2) , regardless of the actual `X-Hub-Signature` header or payload contents. However, none of the downstream event handlers re-derive the acted-upon resource from that same `repository.owner.login`/organization field that was authenticated: `StatusHandler` looks up `Commit` rows purely `Commit.where(sha: params.sha)` with **no repository/stack scoping at all** [4](#0-3) , and `PushHandler`/`Handler#stacks` instead resolve the target repository from `payload.dig('repository', 'full_name')` [5](#0-4)  — a field independent of the `repository.owner.login`/`organization.login` value used to pick the verification secret.

### Finding Description
This is the same bug class as the report: a value that is checked/authenticated (`repository_owner`, used only to select which org's secret validates the signature) does not map cleanly to the operation/resource that is actually written (the `Commit`/`Repository`/`Stack` touched by the handler). The intended invariant is:

`organization whose secret authenticated the request == organization owning the repository/commit being mutated`

Because `repository_owner` and `repository.full_name`/`Commit.sha` are independent, attacker-controlled fields inside the same unsigned-until-verified JSON body, an attacker can pick any organization configured on the instance that lacks a `webhook_secret` (trivially satisfying `verify_webhook_signature`) and then supply a `repository.full_name` or a bare commit `sha` belonging to an entirely different, properly-secured organization's stack. `verify_signature` only checks that the chosen organization's secret matches (or is absent) [1](#0-0) ; it never confirms the organization actually owns the resource the handler subsequently acts on.

`StatusHandler` is the most severe instance: it performs no repository scoping whatsoever, matching commits globally by `sha` [4](#0-3) , then calls `commit.create_status_from_github!(params)`, letting an attacker set an arbitrary CI status (`state`, `context`, `description`) on any commit in any stack on the instance, as long as they can satisfy signature verification for *any one* configured (and misconfigured) organization.

### Impact Explanation
Forged commit statuses are used by Shipit to gate deploys and the merge queue via `ci.require`/`ci.blocking`/`merge.require` checks defined in `shipit.yml` (documented in `README.md` around the CI/Merge Queue sections) [6](#0-5) . By forging a `status` webhook event that is only signature-checked against an unrelated, weakly-configured organization but writes a `success` status against a target commit belonging to a different, security-sensitive stack, an unprivileged external attacker can satisfy required-status gates and cause Shipit to consider a commit deployable/mergeable that never actually passed CI — leading to an unauthorized deploy or merge. This maps to the in-scope Critical impact "unauthorized deploy, rollback or merge."

### Likelihood Explanation
Exploitability depends on at least one organization configured on the Shipit instance lacking a `webhook_secret` — a configuration explicitly present in the shipped sample secrets file (`config/secrets.development.shopify.yml`, `webhook_secret: # nil`) and permitted by `verify_webhook_signature`'s early return [7](#0-6) . Multi-organization Shipit deployments are an explicitly supported topology (see `test/controllers/webhooks_controller_test.rb`, which handles multiple orgs via `repository_owner`) [8](#0-7) . No GitHub App private key, session, or API token is required — only an HTTP POST to the public `/webhooks` endpoint with a crafted JSON body.

### Recommendation
- Do not let the endpoint pick a verification secret from a field independently controllable from the resource being written. Require the organization that authenticates a webhook to be the same organization that owns the `repository`/`commit` being mutated; reject the request otherwise.
- Scope `StatusHandler` (and any other handler) to the repository identified in the payload rather than performing a global `Commit.where(sha:)` lookup — join through `Repository`/`Stack` the same way `Handler#stacks` does.
- Treat organizations with a missing/blank `webhook_secret` as unverifiable and reject their webhooks by default, or require an explicit opt-in flag, rather than silently returning `verified = true`.
- Apply a single, consistent authorization check across all handlers, comparing the same authenticated identity used at the controller layer to the resource acted upon at the handler layer.

### Proof of Concept
1. Configure (or find) a Shipit instance with two organizations, e.g. `weak-org` (no `webhook_secret` configured) and `victim-org` (properly secured), both defined in `secrets.yml`.
2. As an unprivileged external attacker with no credentials, POST to `/webhooks` with:
   - `X-Github-Event: status`
   - `X-Hub-Signature: sha1=anything` (irrelevant — ignored because `weak-org` has no secret)
   - Body:
     ```json
     {
       "repository": { "owner": { "login": "weak-org" } },
       "sha": "<victim commit sha under victim-org's stack>",
       "state": "success",
       "context": "ci/required-check",
       "branches": [{"name": "master"}]
     }
     ```
3. `verify_signature` resolves `repository_owner` = `weak-org`, calls `Shipit.github(organization: "weak-org").verify_webhook_signature(...)`, which returns `true` unconditionally because `weak-org` has no `webhook_secret` [3](#0-2) .
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim commit belonging to `victim-org`'s stack regardless of which organization authenticated the request — and creates a forged `success` status on it [4](#0-3) .
5. If `victim-org`'s stack requires that status context for deploy or merge-queue gating, the forged status satisfies the requirement, enabling an unauthorized deploy/merge on a repository the attacker never had credentials for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
