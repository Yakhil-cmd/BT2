### Title
Stale in-memory unit-props cache causes permanent missing-parent stall / node disagreement on unit validity - (File: network.js, storage.js)

### Summary
The Chrome CVE is a use-after-free on a stale object that the browser continues to treat as valid. The closest reachable analog in ocore is a **stale-cache-treated-as-valid** bug: `storage.readStaticUnitProps()`/`isKnownUnit()` permanently cache partial unit props in `assocCachedUnits` the first time a unit reference is seen (e.g., as a parent), and this cache is only invalidated by `forgetUnit()` on explicit archiving [1](#0-0) . `checkIfNewUnit()` treats any unit present in this cache (`isKnownUnit`) as "known", even when its full content/dependencies were never actually retrieved [2](#0-1) [3](#0-2) .

### Finding Description
When a posted/received unit references as a parent a unit whose full content is locally pruned (a final-bad pruned unit), `validation.js` returns `error_code === "unresolved_dependency"` with `bRequestPrunedContent = true`, and `handleJoint`'s `ifNeedParentUnits` callback in `network.js` stores the joint itself in the KV store and registers it in `assocUnitsWaitingForPrunedContent`, then calls `requestJoints()`/`requestNewMissingJoints()` to fetch the missing parent content [4](#0-3) .

`requestNewMissingJoints()` filters units through `joint_storage.checkIfNewUnit()`, which short-circuits to `ifKnown()` whenever `storage.isKnownUnit(unit)` is true — and `isKnownUnit` returns true merely because `assocCachedUnits[unit]` (populated earlier by any unrelated lookup, e.g. `readStaticUnitProps` during best-parent/witness-list computations) already holds *partial* props for that unit, even though its full joint content was never fetched [2](#0-1) [3](#0-2) [5](#0-4) . This exact hazard is called out in an inline code comment at the callsite: *"requestNewMissingJoints relies on checkIfNewUnit, which can say ifKnown() for a unit that only has stale props cached in assocCachedUnits, even though its full content is exactly what we are missing"* [6](#0-5) .

The result: the re-request for the missing pruned content is silently skipped (`ifKnown` just logs and returns), while the dependent unit sits parked in `assocUnitsWaitingForPrunedContent`/`kvstore` waiting for content that will never be delivered because no peer is ever actually asked for it again [7](#0-6) . Any unposted unit an attacker crafts that references such a pruned/uncached-then-cached parent can trigger this state deterministically, since a single unprivileged unit poster fully controls which units are named as parents.

### Impact Explanation
A unit (and anything transitively depending on it, including AA triggers that spend from or reference outputs on that branch) can become permanently unconfirmable on the affected node: it stays queued as "waiting for pruned content" forever because the re-request path is skipped. Different nodes will have different values in `assocCachedUnits` depending on their own query history, so this is not deterministically reproducible network-wide but can desynchronize individual nodes' views of the DAG — nodes stuck like this will disagree with peers on which units/branches are resolvable, and in the worst case a witness node stuck in this state stops confirming units on that branch, matching the "network unable to confirm new units" / "node disagreement on validity or stability" impact classes.

### Likelihood Explanation
Reachable by any unprivileged unit poster: crafting a unit whose declared parent is a unit that is locally final-bad/pruned on the target node is sufficient to enter the `bRequestPrunedContent` branch (this is explicitly designed to be handled — see the comment "e.g. spending a locally pruned final-bad output" at the callsite) [8](#0-7) . Hitting the *specific* stale-cache race requires that `assocCachedUnits[unit]` for the missing parent was already populated by an earlier, unrelated code path (e.g., MC/witness-list traversal via `readStaticUnitProps`/`buildListOfMcUnitsWithPotentiallyDifferentWitnesslists`) before the re-request fires [9](#0-8) . This makes exploitation timing-dependent rather than always guaranteed on first attempt, but the developers' own comment confirms the condition is real and known to occur.

### Recommendation
Do not rely on `isKnownUnit`/`assocCachedUnits` presence alone to decide whether a unit's full joint content has been retrieved. Track full-content retrieval state separately (e.g., a distinct `assocUnitsWithFullContent` set populated only when `readJoint`/`saveJoint` actually persists the joint), and have `checkIfNewUnit` (or a dedicated check used by `requestNewMissingJoints`) consult that state instead of the partial-props cache when deciding whether to re-request missing pruned content. Additionally, add a periodic sweep (similar to `purgeExpiredCachedPrunedJoints`) that re-checks entries in `assocUnitsWaitingForPrunedContent` past their `expiry_ts` and forces a fresh re-request rather than silently expiring.

### Proof of Concept
1. On a target full node, cause `assocCachedUnits[X]` to be populated for some unit `X` via an unrelated MC/witness-list traversal (`readStaticUnitProps`) — this occurs naturally as part of normal DAG processing for many units.
2. As an unprivileged peer, post/broadcast a new unit `U` that names `X` as a parent, where `X`'s full joint content is not actually stored (e.g., previously archived as `final-bad`/pruned via `purgeUncoveredNonserialJoints`) on the target node.
3. `validation.validateParentsExistAndOrdered`/parent lookup fails to find full content for `X`, causing `ifNeedParentUnits(['X'], true)` with `bRequestPrunedContent = true`.
4. `network.js`'s `ifNeedParentUnits` handler stores `U` in `assocUnitsWaitingForPrunedContent['X']` and calls `requestJoints`/`requestNewMissingJoints(ws, ['X'])`.
5. Because `assocCachedUnits['X']` is already populated from step 1, `storage.isKnownUnit('X')` returns `true`, so `joint_storage.checkIfNewUnit` calls `ifKnown()`, and `requestNewMissingJoints` never issues a `get_joint` request for `X`.
6. `U` (and any units depending on it) never becomes confirmable on this node, demonstrating the node-level denial of confirmation caused by trusting the stale cache as proof of "known" content — directly analogous to the CVE's core defect of continuing to operate on an object whose validity/lifetime assumption no longer holds.

Note: I was unable to fully trace whether any other codepath (e.g. `rerequestLostJoints`) eventually recovers from this specific stuck state, since `assocUnitsWaitingForPrunedContent` entries are keyed only by the missing unit and I could not locate, within the indexed content, the consumer code that resolves this map when a pruned unit's content later arrives via a different route. A Devin session with full repository access would be needed to confirm whether `findLostJoints`/`rerequestLostJoints` (which also gates on `assocUnitsInWork`, not on the stale-cache condition) provides an independent recovery path that would reduce this to a transient rather than permanent stall.

function readStaticUnitProps(conn, unit, handleProps, bReturnNullIfNotFound){
	if (!unit)
		throw Error("no unit");
	var props = assocCachedUnits[unit];
	if (props)
		return handleProps(props);
	conn.query("SELECT level, witnessed_level, best_parent_unit, witness_list_unit FROM units WHERE unit=?", [unit], function(rows){
		if (rows.length !== 1){
			if (bReturnNullIfNotFound)
				return handleProps(null);
			throw Error("not 1 unit "+unit);
		}
		props = rows[0];
		assocCachedUnits[unit] = props;
		handleProps(props);
	});
