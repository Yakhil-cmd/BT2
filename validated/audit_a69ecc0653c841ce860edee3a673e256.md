### No vulnerability found for this question.

Verified via code trace: in `verify_cell_kzg_proof_batch` (src/eip7594/eip7594.c), every element of the caller-supplied `cell_indices` array is validated against `CELLS_PER_EXT_BLOB` in the sanity-check loop [1](#0-0) before any other array is allocated or any challenge/proof computation begins. The exact same `cell_indices` pointer (unmutated — only `unique_commitments`/`commitment_indices` are derived and computed separately by `deduplicate_commitments`) is later passed straight through to `computed_weighted_sum_of_proofs`, which internally calls `get_coset_shift_pow_for_cell(&h_k_pow, cell_indices[i], s)` for `i` in `0..num_cells` [2](#0-1) . Since `num_cells` and the array contents are identical to what was checked in the sanity loop, every `cell_index` reaching `get_coset_shift_pow_for_cell` in the current, single call path is already `< CELLS_PER_EXT_BLOB`, so `h_k_pow_idx = cell_idx_rbl * FIELD_ELEMENTS_PER_CELL` stays within `s->roots_of_unity`'s bounds and the internal `assert` never fires.

The question itself only speculates about "a future refactor or a direct call to the static helper from a different entry point" — `get_coset_shift_pow_for_cell` and `get_inv_coset_shift_for_cell` are `static` functions in `eip7594.c` [3](#0-2) , not exported, and are called only from within this file's own already-bounds-checked call paths (`compute_commitment_to_aggregated_interpolation_poly` and `computed_weighted_sum_of_proofs`, both reachable only from `verify_cell_kzg_proof_batch` after the guard at lines 861–864). There is no current public API, binding, or code path that lets an unprivileged attacker supply a `cell_index` to these helpers that bypasses that check. This is a hypothetical concern about future code changes, not a demonstrable, currently reachable vulnerability, which is explicitly out of scope ("theoretical findings").
