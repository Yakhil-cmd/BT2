### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while every webhook handler acts on the unrelated `repository.full_name` / `organization.login` fields inside the same unauthenticated payload, allowing cross-repository/cross-team writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` governs a request purely from `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), but the value that is actually written to by the dispatched handler — `repository.full_name` (used by `Repository.from_github_repo_name`) or `organization.login`/`team.id` (used by `MembershipHandler`) — is never checked against `repository_owner`. Whenever the resolved organization's `webhook_secret` is unset (an explicitly supported, documented configuration state), verification is a no-op, and an unauthenticated attacker can submit a forged payload that "authenticates" as one configured organization while mutating state belonging to a completely different repository/organization/team tracked by the same Shipit instance.

### Finding Description
`verify_signature` computes the GitHub App/secret to check against solely from the attacker-controlled JSON body: [1](#0-0) [2](#0-1) 

The actual verification is delegated to `GitHubApp#verify_webhook_signature`, which is a **no-op when no `webhook_secret` is configured for that organization** — a state explicitly produced by the documented, optional `webhook_secret` key (shown as blank/nil in `test/dummy/config/secrets.yml` and `docs/setup.md`'s multi-org example): [3](#0-2) 

Once the request passes this check (either because the secret matches or because it was never configured), the raw JSON `params` are handed unmodified to every registered handler for that event: [4](#0-3) 

None of the handlers re-derive or cross-check the organization used for authentication. Instead, they resolve the target `Repository`/`Stack`/`Team` from a *different* field of the same payload:
- `Handler#stacks` / `#repository_name` resolves the acted-upon repository from `payload.dig('repository','full_name')`, unrelated to `repository_owner`: [5](#0-4) 
- `PushHandler#process` triggers a GitHub sync on any stack whose repository matches that `full_name`: [6](#0-5) 
- PR handlers (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabeledHandler`) archive/unarchive review stacks resolved the same way: [7](#0-6) 
- `MembershipHandler#process`/`#find_or_create_team!` creates or updates a `Team` keyed by attacker-supplied `team.id`, and sets `team.organization = params.organization.login` — a field that is never required to equal `repository_owner`/the organization whose secret validated the request — then adds an attacker-chosen `member.login` to that team: [8](#0-7) 

`Team#organization`/`#handle` (`"#{organization}/#{slug}"`) is the same construct compared against `Shipit.github_teams` entries used to gate application-wide authorization: [9](#0-8) [10](#0-9) 

The broken equality is: `organization_used_to_select_webhook_secret == organization/repository/team actually mutated by the handler`. Before the attack, this must hold for every accepted webhook (GitHub always sends matching values). After a forged request, an attacker can make the left side equal any configured organization with a blank secret while making the right side equal any repository, stack, or team known to the Shipit instance — including ones in organizations the attacker does not control at all.

### Impact Explanation
- Cross-repository/cross-organization writes: forging `push` or `pull_request` events lets an unauthenticated party trigger `sync_github`, archive, or unarchive on any stack/review-stack tracked by the instance, regardless of which organization actually owns that repo.
- Authorization escalation into `Shipit.github_teams`: by forging a `membership` event with `organization.login` set to a team handle checked in `force_github_authentication`, and `member.login` set to the attacker's own Shipit login, the attacker can insert themselves into a `Team` record whose `handle` grants application access, without ever being a real member of that GitHub team. This matches the explicitly listed High-impact criterion "escalation into `Shipit.github_teams` authorization."
- No credential, session, `ApiClient` token, or `webhook_secret` knowledge is required when the resolved organization's `webhook_secret` is left blank (a supported configuration), satisfying the unprivileged-attacker requirement.

### Likelihood Explanation
`webhook_secret` is an optional field (`@config[:webhook_secret].presence`), and multiple shipped configuration examples in this repository leave it blank. Any deployment following that documented pattern for at least one onboarded organization exposes every handler's cross-entity trust gap to unauthenticated forged requests; no interaction with GitHub itself is required since the controller only reads request headers/body.

### Recommendation
Bind the value verified by `verify_signature` to the value the handler actually mutates: require `repository.owner.login`/`organization.login` (whichever was used to select the `GitHubApp`) to equal the organization portion of `repository.full_name` (and, for `MembershipHandler`, equal `organization.login` used to persist the `Team`) before dispatch. Additionally, make `webhook_secret` mandatory (fail closed rather than "return true unless webhook_secret") so that no organization can be onboarded without HMAC verification.

### Proof of Concept
1. Deploy Shipit with an organization `attacker-org` configured in `github:` but with `webhook_secret` left blank (as shown in `test/dummy/config/secrets.yml`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "deadbeef"
}
```
No `X-Hub-Signature` header is required to pass validation because `attacker-org` has no configured secret; `PushHandler` will resolve `victim-org/victim-repo`'s stacks via `full_name` and enqueue a sync job for them.
3. Repeat with `X-Github-Event: membership` and a `team`/`organization` object matching a `Shipit.github_teams` entry to add the attacker's own `member.login` to that authorization team.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
```
