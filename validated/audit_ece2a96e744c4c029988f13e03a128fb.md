### Title
Webhook signature verification keyed on `repository.owner.login` while sync/write logic acts on `repository.full_name` allows cross-organization signature bypass - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret` used to verify `X-Hub-Signature`) using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Every downstream handler that decides *which stack/repository the event is applied to* instead uses `payload.dig('repository', 'full_name')` (`Shipit::Webhooks::Handlers::Handler#repository_name`). These are two independently attacker-controlled fields inside the same unauthenticated JSON body: the field used to pick the verification key is not the field used to determine what gets written. ### Finding Description
`Shipit.github(organization:)` looks up per-organization config via `github_app_config`, and `GitHubApp#verify_webhook_signature` explicitly **bypasses verification** (`return true unless webhook_secret`) when that organization's config has no `webhook_secret` set: [4](#0-3) [5](#0-4) 

In a multi-organization deployment (the engine explicitly supports this, see the `github:` map keyed by org name, e.g. `test/dummy/config/secrets_double_github_app.yml`), it is plausible/common for some organizations to be configured without a `webhook_secret` (e.g. GitHub Apps that don't set one, or a misconfigured/legacy org), while other organizations tracked in the same Shipit instance do have one.

The binding that should hold is:
`organization used to select/verify the signing key == organization owning the repository whose stacks are mutated`

The controller breaks this equality: it authenticates the request against the app/config for `repository.owner.login`, but every `Handler` subclass (`PushHandler`, `StatusHandler`, pull-request handlers, etc.) resolves the target `Stack`/`Repository` via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, a completely separate field of the same payload. [6](#0-5) [7](#0-6) 

An attacker who knows (or guesses) the login of *any* organization onboarded to the Shipit instance that has no `webhook_secret` configured can craft a POST to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) = that unsecured org's login (selects a `GitHubApp` whose `verify_webhook_signature` always returns `true`)
- `repository.full_name` = `"targeted-org/targeted-repo"` (any other tracked repository, including ones belonging to organizations that *do* have a real webhook secret)

The request passes `verify_signature` unconditionally (no valid `X-Hub-Signature` needed at all), and the handler then acts on the targeted repository's stacks — e.g. `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` for the attacker-chosen branch/SHA, or pull-request handlers create/archive `ReviewStack`s, capture labels, etc. — for a repository that is not the one whose credentials authorized the request.

### Impact Explanation
This is an authentication bypass on the webhook ingestion boundary: the signature check can be neutralized by choosing an unrelated, unsecured organization identifier while the actual mutation targets a repository/stack belonging to a different, properly-secured organization. Consequences include forged `push` events that trigger `GithubSyncJob`/deploy pipeline state changes, forged `status`/`check_suite` events that manipulate commit statuses used for merge/deploy gating, and forged pull-request events that create or archive review stacks — all without possessing the real GitHub webhook secret for the targeted repository's organization. This matches the "unauthorized deploy/rollback" and "authentication bypass" impact classes.

### Likelihood Explanation
Requires only knowledge of two organization/repository names already onboarded onto the same Shipit instance (both discoverable via the public UI/API, since Shipit stacks and repo owners are visible in `Stack`/`Repository` listings) and requires that at least one onboarded organization lacks a `webhook_secret`. This is a realistic, not purely theoretical, configuration state for multi-tenant Shipit deployments, and no attacker credentials (API tokens, GitHub write access, etc.) are needed — only an unauthenticated HTTP POST.

### Recommendation
Verify the webhook signature using the same organization/repository identity that will actually be acted upon. Concretely, derive both `repository_owner`/verification key and the repository resolved by handlers from the single canonical field `repository.full_name` (or explicitly cross-check that `repository.owner.login` matches the owner segment of `repository.full_name` before proceeding). Additionally, consider making `webhook_secret` mandatory for every configured GitHub organization (reject/log instead of silently returning `true` when absent), removing the fail-open behavior in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Onboard/observe that organization `unsecured-org` is configured in Shipit's `github:` secrets map without a `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), while `victim-org` (which owns a real tracked stack, e.g. `victim-org/victim-repo`) has a `webhook_secret` configured.
2. Send:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef   (arbitrary/invalid)

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "unsecured-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the bogus `X-Hub-Signature`.
4. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack — despite the request never having been signed by `victim-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
