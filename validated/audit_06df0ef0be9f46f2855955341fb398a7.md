### Title
Validator ECDSA Nodekey Written as Unencrypted Plaintext with World-Readable Permissions, Enabling Validator Privilege Escalation — (`cmd/kgen/main.go`, `cmd/homi/setup/cmd.go`)

---

### Summary

Multiple key-generation tools in the repository write the validator ECDSA nodekey to disk as raw hex plaintext with `os.ModePerm` (0o777 — world-readable and world-writable). The nodekey is the private key that both signs Istanbul BFT consensus messages and authorizes `onlyNodeId` system-contract calls (validator lifecycle: `ready-candidate`, `ready-validator`, `pause`, `resume`, `exit`, `offboard`). Any local user on the machine where keys were generated can read the file and impersonate the validator on-chain.

---

### Finding Description

**`cmd/kcn/genkeys.go` — `generateKeysAction`**

Even the newer `generate-keys` command, which uses the correct `0o600` permission for the keystore JSON files, still writes `nodekey` and `bls-nodekey` as raw unencrypted hex:

```go

writeFile(blsNodekeyHexPath, hex.EncodeToString(blsKey.Marshal()), 0o600)
``` [6](#0-5) 

The README explicitly documents this design: "`nodekey`/`bls-nodekey` are also kept as raw hex because the node loads them directly." [7](#0-6) 

---

### Impact Explanation

The nodekey is the validator's root ECDSA private key. Per the documentation:

> `nodekey` — node identity (p2p) + createNode `nodeId`; **signs state transitions (onlyNodeId)** [8](#0-7) 

> These commands require `msg.sender == node-id` (the private key **is** the node key). [9](#0-8) 

An attacker who reads the nodekey file can:

1. **Validator privilege escalation via system contracts**: Send transactions signed as the validator's node-id to call `onlyNodeId`-gated functions — `pause`, `resume`, `exit`, `offboard` — changing the validator's on-chain state without authorization. This directly alters the active validator set, affecting consensus participation and reward distribution.

2. **Consensus impersonation**: Sign Istanbul BFT `PREPREPARE`, `PREPARE`, and `COMMIT` messages as the legitimate validator, enabling equivocation or consensus disruption.

The `ValidatorInfo` struct stores the raw hex nodekey in its `Nodekey` field:

```go
type ValidatorInfo struct {
    Address  common.Address
    Nodekey  string   // raw hex private key
    NodeInfo string
}
``` [10](#0-9) 

This struct is also serialized to JSON (`validator` / `node_info.json`) with `os.ModePerm`, leaking the private key in a second location.

---

### Likelihood Explanation

- `cmd/kgen` is the documented tool for generating Kaia node keys. Any operator who runs `kgen --file` on a shared or multi-user system (CI server, jump host, shared build machine) exposes the nodekey to all local users.
- `cmd/homi` is used for network genesis setup and is routinely run in DevOps pipelines where multiple users may have filesystem access.
- `os.ModePerm` (0o777) is the most permissive Unix mode — no configuration or exploit is needed; a simple `cat keys/nodekey1` suffices.
- The files are never deleted after use; they persist on disk indefinitely.

---

### Recommendation

**Short term:**
- Replace all `os.ModePerm` with `0o600` for any file containing private key material in `cmd/kgen/main.go`, `cmd/homi/setup/cmd.go`, and their `WriteFile`/`MkdirAll` helpers.
- Replace `os.ModePerm` directory creation with `0o700` for directories holding key files.

**Long term:**
- Do not store the nodekey as raw hex at all. The node should load it exclusively from the encrypted keystore (`.json` + `.pass`), eliminating the plaintext `nodekey` file. If the node daemon requires a plaintext file for startup, document that it must be on a `tmpfs` or equivalent in-memory filesystem and deleted after first use.
- Consider deriving the runtime nodekey from the encrypted keystore at startup rather than persisting a plaintext copy.

### Proof of Concept

```bash
# 1. Operator generates keys on a shared machine
kgen --file --ip 1.2.3.4 --port 32323

# 2. Attacker (any local user) reads the world-readable nodekey
cat keys/nodekey
# Output: a4f3c1...  (raw hex ECDSA private key, 64 chars)

# 3. Attacker uses the stolen key to call onlyNodeId system contract
kcn valops pause --private-key 0xa4f3c1... --endpoint http://validator-rpc:8551
# Result: validator is paused on-chain without the legitimate operator's knowledge

# For homi-generated keys:
homi setup --cn-num 4 --type local
cat keys/cn1/nodekey1   # world-readable, raw hex
```

func writeNodeKeyInfoToFile(validator *validatorInfo, parentDir string, nodekey string) error {
