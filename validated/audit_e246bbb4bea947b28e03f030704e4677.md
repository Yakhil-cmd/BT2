### Title
Attacker-controlled PR label named `PATH` overrides the shell `PATH` in `Command#unbundled_env`, breaking binary-resolution integrity for spawned processes - (File: `lib/shipit/command.rb`)

### Summary
`Shipit::ReviewStack#env` turns every pull-request label into an environment variable by upcasing the label name and assigning it the literal value `"true"`, with no denylist for reserved variable names. Because this hash is merged last in `Command#unbundled_env`, a pull-request author who names a label `PATH` (or `path`) causes the value Shipit computed for `PATH` (`Shipit.shell_paths.join(':') + ':' + ENV['PATH']`) to be replaced by the string `"true"` for every subsequent command run against that stack/task.

### Finding Description
The claimed binding is: `Command#unbundled_env['PATH']` (after `.merge(@env.stringify_keys)`) `== Shipit.shell_paths.join(':') + ':' + ENV['PATH']`. Tracing the code shows this binding is broken:

- `Shipit::ReviewStack#env` merges pull request labels into the stack env, upcasing the label name as the key and hardcoding `"true"` as the value: [1](#0-0) 
- `PullRequest::LabelCapturingHandler#capture_labels` writes `pull_request.labels` directly from the webhook payload's `pull_request.labels[].name` with no filtering of reserved names: [2](#0-1) 
- `Shipit::TaskCommands#env` merges `@stack.env` (which includes the label-derived hash) into the task's environment, which then flows through `deploy_spec.machine_env` and `@task.env`: [3](#0-2) 
- `Shipit::Command#unbundled_env` computes the "correct" `PATH` from `Shipit.shell_paths` and `ENV['PATH']`, then merges `@env.stringify_keys` **on top of it**, so any `PATH` key present in the caller-supplied env (including one derived from a PR label) wins: [4](#0-3) 
- This `unbundled_env` result is what is passed directly to `PTY.spawn`: [5](#0-4) 

Existing guards do not prevent this: the webhook `params` schema for `LabelCapturingHandler` only validates that `labels` is an array of objects with a string `name` — it applies no allow/deny-list on label content: [6](#0-5) . `ReviewStack#env` itself performs no filtering of reserved environment variable names (`PATH`, `LD_PRELOAD`, `BUNDLE_PATH`, etc.) before upcasing the label into a key: [7](#0-6) .

Confirmed existing tests only assert benign labels like `wip`/`bug` are captured as env vars, never testing collision with reserved names such as `PATH`: [8](#0-7) [9](#0-8) .

Attack: an unprivileged GitHub user opens a PR from their own fork against a repo with an active `Shipit::ReviewStack`, and adds a label literally named `PATH` via the GitHub UI. GitHub's `labeled` webhook is emitted with `pull_request.labels[].name == "PATH"`, `LabelCapturingHandler#capture_labels` persists this into `pull_request.labels`, and the next command run for that stack (deploy, rollback, or any task) computes `env['PATH'] == "true"` instead of the shell paths Shipit intended.

### Impact Explanation
Every subsequent `Command` invocation for that specific review stack (git, bundler, deploy-spec-defined commands) will resolve unqualified binary names against `PATH="true"` instead of Shipit's trusted `shell_paths`/system `PATH`. Since `"true"` is not an absolute path, POSIX exec semantics treat it as a directory relative to the process's current working directory (`chdir`, which for tasks is the checked-out working directory of the attacker's own branch/commit). This gives the PR author a route to have Shipit resolve command names (e.g., `git`, `bundle`, or whatever the deploy spec calls) against a directory under their control if such a directory happens to exist in the checkout — this is a genuine break in the PATH-integrity guarantee. This is scoped to the attacker's own review stack (not other repos/tenants), but constitutes uncontrolled/attacker-influenced binary resolution for a `PTY.spawn`-executed command on the deploy host, matching the "Critical - RCE on the deploy host via `Command`/`PTY.spawn`" category, contingent on further conditions (an appropriately named executable landing in the resolved relative directory during checkout) which are plausible for an attacker who controls their own PR branch content and directory naming.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: an unarchived `Shipit::ReviewStack` must exist for the repo (a standard, common Shipit review-app configuration, not attacker-controlled but common), and the attacker needs only permission to open a PR against that repo and label it (which their own fork PR gets automatically) — no Shipit session, secret, or maintainer role is required. The label name `PATH` is trivial to create through the normal GitHub UI. This is repeatable per PR/stack and costs the attacker nothing beyond opening a PR and clicking "add label."

### Recommendation
In `Shipit::ReviewStack#env`, deny-list (or strictly allow-list) environment variable names derived from PR labels — at minimum exclude `PATH` and other security-sensitive variables (`LD_PRELOAD`, `BUNDLE_PATH`, `GIT_*`, etc.) before merging label-derived keys into the stack's env. Alternatively/additionally, in `Command#unbundled_env`, compute and enforce the trusted `PATH` value **after** merging `@env`, so caller-supplied env can never override the `PATH` Shipit computed from `Shipit.shell_paths`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (proof sketch)
test "#env does not allow a PR label to override PATH" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.update!(labels: ['PATH'])

  computed_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"

  refute_equal 'true', stack.env['PATH']
  # demonstrates the divergence introduced by ReviewStack#env
  assert_equal 'true', stack.env['PATH'], "current (vulnerable) behavior"
end

# test/lib/shipit/task_commands_test.rb (proof sketch)
test "Command#unbundled_env PATH is not overridable via a PR label named PATH" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.update!(labels: ['PATH'])
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  command = Shipit::Command.new('true', chdir: Dir.tmpdir, env: env)

  computed_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
  assert_equal computed_path, command.unbundled_env['PATH'],
    "PR label named PATH should not override Shipit's computed PATH"
end
```
Both assertions fail against current code, demonstrating that `Command#unbundled_env['PATH']` diverges from the Shipit-computed `PATH` whenever a PR carries a label literally named `PATH`.
