### Title
CCMenuController bypasses ApiClient stack scoping, allowing a stack-scoped token to read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup used by every other API controller and resolves the target stack directly from the URL parameter instead of going through the stack set the authenticated `ApiClient` is authorized for. This breaks the binding between the stack a token authorizes (`ApiClient#stack_id`) and the stack the request actually touches (`params[:stack_id]`), letting a token that was minted for one stack read CCMenu/build-status data for any other stack in the installation.

### Finding Description
`Shipit::Api::BaseController` enforces stack scoping through the `stacks` helper, which restricts the queryable set of stacks to the one the current `ApiClient` was bound to at creation time: [1](#0-0) 

`require_permission :read, :stack` only checks that the client's `permissions` array contains `"read:stack"`; it never checks *which* stack is being accessed: [2](#0-1) 

The actual per-stack restriction is entirely delegated to the `stacks`/`stack` helper in `BaseController`. However, `CCMenuController` defines its own `stack` method that ignores this scoping and loads the stack straight from the global `Stack` relation using only the URL parameter, plus its own `authenticate_api_client` that skips the base's stack-aware authentication path: [3](#0-2) 

Concretely, the binding that should hold is:
`token.stack_id (authorized stack) == params[:stack_id] (touched stack)`

For every other API endpoint this equality is enforced via `stacks.from_param!(params[:stack_id])` (raising/filtering out stacks not owned by the token). In `CCMenuController#stack`, the right-hand side is looked up against `Stack.from_param!(params[:stack_id])` directly, with no reference to `current_api_client.stack_id` at all — so the equality is never checked.

`ApiClient` tokens are commonly minted scoped to a single stack (e.g. the `here_come_the_walrus` fixture has `stack: shipit`, and `CCMenuUrlController` generates a per-stack CCMenu URL/token pairing a stack id in the URL with a client token), and are meant to be embedded in third-party CI-status tools: [4](#0-3) 

Any holder of such a token (leaked to a CI-dashboard tool, browser history, logs, etc.) can simply change `stack_id` in the CCMenu URL to query any other stack the installation manages.

### Impact Explanation
This is an authorization-escalation issue: a token deliberately scoped to a single stack can be used to read deploy/build state (`stack.deploys_and_rollbacks.last`, running status, timestamps) of every stack in the Shipit instance, not just the one it was issued for. This matches the "High" category of escalation beyond the authorization a credential was granted and unauthenticated (from the perspective of the other stacks) read of stack/deploy state.

### Likelihood Explanation
Exploitation only requires possession of any valid API token with `read:stack` permission (which is granted automatically to the auto-created CCMenu client) and knowledge/guessing of another stack's slug/id — both are low-friction, requiring no privileged access, GitHub credentials, or session. This aligns with the rule set's requirement of an unprivileged-attacker analog breaking a deployment-trust binding without needing an admin/session/webhook secret.

### Recommendation
Have `CCMenuController#stack` (and its `authenticate_api_client` override) route through the same `stacks`-scoped lookup used in `BaseController`, i.e. `stacks.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot resolve stacks outside `current_api_client.stack_id`.

### Proof of Concept
1. Create/observe an `ApiClient` scoped to stack A (`stack_id = A`) with permission `read:stack` (this is exactly what `CCMenuUrlController#client` auto-provisions per user, and what the `here_come_the_walrus` fixture represents).
2. Obtain its authentication token (e.g., via the `/ccmenu_url` endpoint tied to stack A, or a leaked CCMenu URL).
3. Issue `GET /api/stacks/:B/ccmenu.xml?token=<token>` for an arbitrary stack `B` that the token was never scoped to.
4. `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` directly (bypassing `stacks`), so the request succeeds and returns stack B's deploy/build status, even though the token is only supposed to authorize reads of stack A.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end

# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
