### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup flips required-context state for a victim stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming `status` webhook using a bare, application-wide `Commit.where(sha: params.sha)` lookup with no repository/stack scoping. Because Git commit SHAs are shared across forks and mirrors of the same history, an attacker who owns a fork of the victim's repository can legitimately trigger their own signed webhook for a commit SHA that also exists in the victim's `Stack`, and have their `context: ci/jenkins`/`state: failure` (or `success`) status attached to the victim's commit record.

### Finding Description
The broken binding: the invariant the code should enforce is
`commit.stack.github_repo_name == payload.repository.full_name` for every `Status` created from a webhook, i.e. a status delivered by GitHub for repository R must only be attached to commits belonging to stacks tracking repository R.

Instead, `StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`Commit.where(sha:)` is a global, unscoped query across every stack/repository in the installation — there is no `.where(stack_id: ...)` or repository filter. `Commit#create_status_from_github!` then unconditionally records the status and re-evaluates the commit's aggregate status: [2](#0-1) 
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
```
and `add_status` re-derives `deployable?`/`blocked?` state and calls `stack.schedule_merges` when the new status is `pending` or `success`: [3](#0-2) 

The only upstream gate is `WebhooksController#verify_signature`, which authenticates the webhook against `Shipit.github(organization: repository_owner)` — i.e., it only proves the payload was really sent by the repository named in the payload, not that the `sha` referenced belongs exclusively to that repository: [4](#0-3) 

Exploit flow:
1. Attacker forks the victim's GitHub repository (or otherwise controls a repository that shares commit history/ancestor commits with the victim repository — a routine consequence of the fork+PR workflow, since forked repos initially contain byte-identical, same-SHA commit objects as the upstream).
2. Victim's Shipit `Stack` has already ingested that shared commit (e.g., as a common ancestor of a merged PR) and has `merge_queue_enabled: true`, requiring the `ci/jenkins` context.
3. Attacker triggers a real, correctly-signed `status` webhook from their own (attacker-owned) repository/org for that shared SHA, with `context: ci/jenkins`, `state: failure` (or `success`).
4. `verify_signature` passes, because the signature is validated against the attacker's own GitHub App/org, which legitimately sent this payload.
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — matching not only the attacker's own repo's commit record (if any) but also the victim stack's `Commit` row with the same SHA, and writes a `Status` onto it.
6. This flips the victim commit's aggregate `status`/`deployable?`, and can trigger `stack.schedule_merges`, or block deploys/merges depending on whether `state` is `failure` or `success`, for a stack the attacker never authenticated for and does not control.

No existing guard checks that the resolved `Commit#stack.github_repo_name` matches the webhook's own `repository.full_name`/owner — `verify_signature` authenticates the sender but the handler never re-validates the sha-to-repository binding before mutating state.

### Impact Explanation
An unprivileged GitHub user (owner of any fork/derivative repo sharing history with a victim repo) can inject arbitrary CI status (`failure` to block merges/deploys, or `success` to force a merge-queue advance and downstream `merge!`) onto commits belonging to a victim stack they do not own or administer. This is a cross-tenant write: a payload correctly authenticated for repository A mutates state (`Status`, `deployable?`, merge queue progression) for stack/commit belonging to repository B. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Preconditions: victim stack must have `merge_queue_enabled: true` and require the `ci/jenkins` context, and the targeted SHA must exist as a `Commit` row in both the attacker's own accessible repo (to send a legitimately-signed webhook) and the victim's stack (shared ancestor/fork history — a very common real-world condition, not requiring a hash collision). Attacker cost is minimal: fork a repo, configure a webhook/GitHub App status update for their own fork, and post a `status` event for a shared SHA. This is repeatable against any stack sharing history with an attacker-accessible repository.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any similar handlers) by the repository identified in the webhook payload, e.g. filter through `commit.stack.repository` matching `params.repository.full_name`/owner before calling `create_status_from_github!`, rejecting or ignoring statuses whose payload repository does not match the commit's own stack repository.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`, conceptually — no live GitHub required):
1. Create two stacks: `victim_stack` (repo `victim/repo`, `merge_queue_enabled: true`, requiring `ci/jenkins`) and `attacker_stack` (repo `attacker/repo`).
2. Create a `Commit` with an identical `sha` (e.g., `"deadbeef" * 5`) under both `victim_stack` and `attacker_stack` (simulating shared fork history).
3. Assert baseline binding: `victim_commit.status.success? == false` (or whatever pending state) and `victim_stack.commits.find_by(sha:).stack_id == victim_stack.id` — i.e. the victim commit's state is independent of the attacker's repo state.
4. Build `StatusHandler` params: `sha: shared_sha, context: 'ci/jenkins', state: 'failure'` (as would arrive from `attacker/repo`'s legitimately-signed webhook).
5. Invoke `StatusHandler.new(params).process` (bypassing controller-level signature check, since that check only validates sender authenticity, not sha scoping).
6. Assert the equality is now broken: `victim_stack.commits.find_by(sha: shared_sha).status.failure? == true`, and/or `victim_commit.deployable?` changed from its baseline — demonstrating the attacker-authenticated payload mutated the victim stack's commit despite never authenticating for `victim/repo`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
```
