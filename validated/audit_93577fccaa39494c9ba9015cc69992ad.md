### Title
Ralph Wiggum state file path is unanchored to project root, causing cross-directory state confusion - ([File: plugins/ralph-wiggum/hooks/stop-hook.sh])

### Summary
`stop-hook.sh` and `commands/cancel-ralph.md` both hardcode the relative path `.claude/ralph-loop.local.md` instead of anchoring it to `$CLAUDE_PROJECT_DIR`. Because the hook's working directory tracks the agent's live shell cwd (which can drift into any nested directory, e.g. a vendored dependency or submodule, via ordinary `cd` usage during the session), a nested `.claude/ralph-loop.local.md` planted by an attacker in repo content can be read/deleted/mutated instead of the top-level session's real state file.

### Finding Description
`stop-hook.sh` sets `RALPH_STATE_FILE=".claude/ralph-loop.local.md"` and immediately does relative file operations (`-f`, `sed`, `rm`, `mv`) against it: [1](#0-0) . This resolves relative to the hook process's current working directory. Claude Code explicitly exposes `$CLAUDE_PROJECT_DIR` to hook commands precisely to avoid this kind of drift, as documented in the plugin's own hook-development guidance: [2](#0-1) . `stop-hook.sh` never references `$CLAUDE_PROJECT_DIR`, nor does it read the `cwd` field that is present in every hook input payload: [3](#0-2) .

Similarly, `commands/cancel-ralph.md` grants Bash/Read tool permissions and instructions against the same bare relative path with no project-root anchoring: [4](#0-3) . `setup-ralph-loop.sh`, which creates the state file at `/ralph-loop` time, has the identical relative-path pattern (`mkdir -p .claude` / `.claude/ralph-loop.local.md`) with no root anchoring either: [5](#0-4) .

If a repository contains a nested directory (submodule, vendored dependency, or any subproject) with its own pre-planted `.claude/ralph-loop.local.md`, and the agent's shell working directory moves into that subdirectory during the session (a completely ordinary occurrence — e.g., running build/test commands inside a vendored package), any subsequent Stop-hook invocation or `/cancel-ralph` execution that happens while cwd is inside that subdirectory will operate on the nested file rather than the top-level session's real Ralph state file. There is no session-id binding, no `$CLAUDE_PROJECT_DIR` anchoring, and no canonicalization/allowlist check that would catch this — the existing validation in the script (iteration/max_iterations numeric checks) validates the *content* of whatever file is found at the relative path, but does nothing to validate that the path itself points at the correct file.

### Impact Explanation
Scoped impact is session/state cross-talk, not privilege escalation or arbitrary code execution: an attacker-planted nested state file can cause (a) the real top-level Ralph loop to be silently "stopped" or its iteration counter tampered with, or (b) `/cancel-ralph` to report success/cancel the wrong loop while the genuine top-level loop keeps running or vice versa. This matches a "unauthorized file action / trust-boundary bypass causing session state corruption" class of impact — the plugin acts on attacker-supplied file content and location rather than the session's actual bound state.

### Likelihood Explanation
Requires: (1) attacker-controlled repo content containing a nested `.claude/ralph-loop.local.md` (trivial — any contributor/PR can add this in a submodule or vendored folder), and (2) the agent's persistent shell cwd moving into that subdirectory at some point in the session (common during normal build/test workflows, or easily nudged via prompt injection in README/build instructions telling the agent to `cd` into that folder). No admin privilege, key leakage, or social engineering beyond ordinary repository content is required, making this realistically reachable in normal agentic workflows.

### Recommendation
Anchor `RALPH_STATE_FILE` (and the equivalent paths in `cancel-ralph.md` and `setup-ralph-loop.sh`) to `${CLAUDE_PROJECT_DIR}/.claude/ralph-loop.local.md` instead of a bare relative path, and/or use the `cwd`/project-root field from the hook input JSON to construct an absolute, canonicalized path before any file operation. Additionally, consider binding the state file to `session_id` to prevent any cross-directory or cross-session ambiguity.

### Proof of Concept
Integration test:
1. Create a repo with `.claude/ralph-loop.local.md` at root (`iteration: 1`, `max_iterations: 0`, `active: true`).
2. Create `vendor/nested/.claude/ralph-loop.local.md` with `iteration: 5`, `max_iterations: 5` (i.e., already at max).
3. Invoke `stop-hook.sh` with cwd set to `vendor/nested` and stdin JSON containing a valid `transcript_path`.
4. Assert the hook reports "Max iterations reached" and removes `vendor/nested/.claude/ralph-loop.local.md`, while the root `.claude/ralph-loop.local.md` (the real session state, iteration 1) is left untouched and never inspected.
5. Repeat with `/cancel-ralph`'s Bash/Read invocations run from `vendor/nested` cwd; assert it reports cancelling "iteration 5" and deletes the nested file, while the real top-level loop's `.claude/ralph-loop.local.md` remains present and active — demonstrating the cwd-dependent single-source-of-truth violation.

```markdown
# Cancel Ralph

To cancel the Ralph loop:

1. Check if `.claude/ralph-loop.local.md` exists using Bash: `test -f .claude/ralph-loop.local.md && echo "EXISTS" || echo "NOT_FOUND"`

2. **If NOT_FOUND**: Say "No active Ralph loop found."

   - Read `.claude/ralph-loop.local.md` to get the current iteration number from the `iteration:` field
   - Remove the file using Bash: `rm .claude/ralph-loop.local.md`
```

```shellscript
# Create state file for stop hook (markdown with YAML frontmatter)
mkdir -p .claude

# Quote completion promise for YAML if it contains special chars or is not null
if [[ -n "$COMPLETION_PROMISE" ]] && [[ "$COMPLETION_PROMISE" != "null" ]]; then
  COMPLETION_PROMISE_YAML="\"$COMPLETION_PROMISE\""
else
  COMPLETION_PROMISE_YAML="null"
fi

cat > .claude/ralph-loop.local.md <<EOF
---
active: true
iteration: 1
max_iterations: $MAX_ITERATIONS
completion_promise: $COMPLETION_PROMISE_YAML
started_at: "$(date -u +%Y-%m-%dT%H:%M:%SZ)"
---

$PROMPT
EOF
```
