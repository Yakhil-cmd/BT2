### Title
DoS: Dust-flooding a custom-asset AA address can make it permanently unable to send that asset - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `sendUnit()` → `completePaymentPayload()` selects unspent outputs for an AA response payment by querying `outputs` for the AA's address and looping over every returned row in `iterateUnspentOutputs()`. For the base asset, the query filters out dust (`amount>=FULL_TRANSFER_INPUT_SIZE`), explicitly to defend against "spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond" (comment at line 1144). However, for any non-base (custom) asset, this dust filter is not applied, and the SQL query in `readStableOutputs`/`readUnstableOutputsSentByAAs` has no `LIMIT`, no minimum-amount threshold, and the JS-side loop (`iterateUnspentOutputs`) has no cap on the number of inputs it accumulates before checking `MAX_MESSAGES_PER_UNIT`/`MAX_INPUTS_PER_PAYMENT_MESSAGE`. This is the same bug class as the reported `claimForAllWindows()` DoS: an attacker-controlled, monotonically growing collection (here, the AA's unspent custom-asset UTXO set) is iterated in full whenever the affected function is invoked, and an attacker can keep enlarging that collection at negligible cost until the function becomes unusable.

### Finding Description
In `aa_composer.js` (`sendUnit` → `completePaymentPayload`):
- `readStableOutputs()` builds:
  `"...WHERE address=? AND asset"+(asset ? "="+conn.escape(asset) : " IS NULL AND amount>=" + FULL_TRANSFER_INPUT_SIZE)+" AND is_spent=0 ..."`
  For a custom `asset`, only `asset=?` is required — there is no `amount>=` dust threshold, unlike the base-asset branch.
- `iterateUnspentOutputs(rows)` then does `for (var i = 0; i < rows.length; i++)`, pushing every row into `payload.inputs` and `arrUsedOutputIds` until the target amount is reached or `rows` is exhausted. There is no early bail-out based on a maximum number of inputs; the loop only stops when it has accumulated enough amount or run out of rows.
- Any address (unprivileged) can send a custom, previously-issued asset in arbitrarily many tiny/dust outputs to the AA address (each such transfer is a normal, valid unit any unprivileged sender can post — this is exactly the reachable, unprivileged-attacker path required: "asset issuance and transfer conditions" / "payment inputs/outputs").
- Because unspent outputs of that asset accumulate at the AA address forever (each new dust payment simply adds one more `is_spent=0` row), the query result set that `iterateUnspentOutputs` must process grows without bound as the attacker keeps sending more dust. There is no per-call cap comparable to `pickDivisibleCoinsForAmount`'s `LIMIT constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2` used elsewhere in wallet-composed payments — the AA's own internal coin-selection path in `aa_composer.js` does not apply that limit before iterating.
- The consequence mirrors `claimForAllWindows()`: every time the AA needs to pay out that asset (in response to any legitimate trigger, from any user), it must process the ever-growing set of dust UTXOs, which increases the CPU/DB time of `handleTrigger`/`sendUnit` on every node validating/executing the response, and risks exceeding `MAX_MESSAGES_PER_UNIT` (making the response payload invalid, causing bounce) or otherwise making the AA's normal, legitimate response processing prohibitively expensive or outright non-functional.

### Impact Explanation
An attacker can, at low and bounded cost to themselves (paying dust output fees only), permanently degrade or eventually disable an AA's ability to pay out a custom asset it holds/manages, by flooding its address with a large number of tiny custom-asset outputs. Because the loop and query lack a cap, this:
- Increases per-trigger processing time and DB load on every full node that executes/validates the AA's response, for every future trigger involving that asset.
- Can push the number of required inputs above `MAX_MESSAGES_PER_UNIT`/`MAX_INPUTS_PER_PAYMENT_MESSAGE`, causing the AA to be permanently unable to compose a valid response payment in that asset (funds effectively frozen / AA malfunction), which is a concrete "AA fund loss or freezing" impact as called out in the validation rules.
- Is irreversible by normal users of the AA — the dust outputs remain unspent (and hence part of the coin-selection candidate set) until an AA-controlled transaction actually consumes them, and the AA can't consume them faster than they're accumulated if the attacker persists.

### Likelihood Explanation
Any unprivileged user who can issue or hold a custom asset (transferable, low-cost) can post many small transfer units to an AA address. This requires no special privileges, no compromised keys, no operator/witness role — only ordinary transaction posting, which matches the "unprivileged unit poster / asset issuer" threat model in scope. The attack cost is proportional to the number of dust outputs created (network fees for many tiny units), which is asymmetric relative to the growing cost imposed on every node handling the AA's future responses — the classic DoS asymmetry that made the original `claimForAllWindows()` finding High severity.

### Recommendation
- Apply the same dust-amount floor used for the base asset to custom assets in `readStableOutputs`/`readUnstableOutputsSentByAAs` (e.g., only consider outputs whose amount is not "net negative" once the additional per-input transfer overhead is accounted for), or otherwise cap the number of unspent-output rows considered per payment (e.g., add `LIMIT constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` to the SQL, consistent with `inputs.js`'s `pickDivisibleCoinsForAmount`).
- Track and bail out early once `payload.inputs.length` (plus already-used other-message inputs) would exceed `MAX_MESSAGES_PER_UNIT`/`MAX_INPUTS_PER_PAYMENT_MESSAGE`, returning a graceful bounce rather than silently accumulating an unbounded input list.
- Consider periodic/administrative consolidation ("sweeping") of dust UTXOs into a single output so an AA's spendable set doesn't grow unbounded from attacker-supplied noise.

### Proof of Concept
1. Attacker issues (or otherwise obtains) a small amount of a transferable custom asset `A`.
2. Attacker repeatedly sends outputs of asset `A` to AA address `X` in denominations of 1 unit each (each such transfer is a normal valid payment any user can post), building up N (e.g., tens of thousands) unspent outputs of asset `A` at address `X`. No dust-amount floor exists for non-base assets in `aa_composer.js`'s `readStableOutputs` query (`" AND asset="+conn.escape(asset)` with no `amount>=` condition), so all of these persist as `is_spent=0` rows. [1](#0-0) 
3. Any legitimate user sends a trigger to AA `X` that causes it to pay out asset `A` (e.g., as part of normal AA logic). `completePaymentPayload()` calls `readStableOutputs()` then `iterateUnspentOutputs(rows)`, which iterates the full, attacker-inflated row set. [2](#0-1) [3](#0-2) 
4. As N grows, this processing (run by every node validating/executing the AA response) grows correspondingly, and once N is large enough, the composed payload will exceed `MAX_MESSAGES_PER_UNIT`/`MAX_INPUTS_PER_PAYMENT_MESSAGE` constraints, making it impossible for the AA to ever complete a valid response involving asset `A`, effectively freezing that asset in the AA — the same "grows forever, eventually unusable" pattern as `claimForAllWindows()`.

*Note: I was unable to fully verify whether a global cap (e.g., `MAX_MESSAGES_PER_UNIT` check) is applied elsewhere before or after `iterateUnspentOutputs` is called in every code path (e.g., in `validation.js`), so it is possible partial mitigations exist downstream that reduce (but do not eliminate) the severity; a Devin session with full repository access would be needed to trace every call site and confirm whether any such cap intercepts this scenario before resource exhaustion occurs.*
