### Title
Session Fixation on GitHub OAuth Callback via Missing `reset_session` - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`Shipit::GithubAuthenticationController#callback` binds the authenticated user to the existing session (via `session[:user_id]` and `session[:authenticated] = true`) without ever calling `reset_session`. This preserves the pre-authentication session identifier across the trust boundary, enabling classic session fixation (CWE-384): an attacker who plants/knows a session cookie before authentication can hijack the victim's post-authentication session.

### Finding Description
The broken binding is: `session_id(before GET /auth/github/callback) == session_id(after GET /auth/github/callback)`.

`callback` is defined as: [1](#0-0) . It reads `request.env['omniauth.auth']`, then does `session[:user_id] = sign_in_github(auth)` and `session[:authenticated] = true`, then redirects — with no call to `reset_session` anywhere in this method.

By contrast, `logout` explicitly calls `reset_session`: [2](#0-1) , and `force_github_authentication` also calls `reset_session` when forcing a fresh login: [3](#0-2) . This shows the codebase's own convention is to rotate the session on privilege-boundary crossings, but `callback` — the actual login completion point — omits it.

`current_user` is resolved purely from `session[:user_id]`: [4](#0-3) , so whoever controls the session record referenced by the session cookie controls the identity Shipit believes is logged in.

Exploit flow: the attacker visits any unauthenticated Shipit page to obtain a valid session cookie/record for a session store entry they know (Rails' cookie-store session is fixed by the cookie itself; even with a server-side store, the pre-auth session ID persists). The attacker gets the victim to use that same cookie (shared browser profile, kiosk, CI runner sharing a persisted cookie jar, or any mechanism that transports the cookie to the victim's browser before they complete `GET /auth/github/callback`). When the victim finishes GitHub OAuth, `callback` writes the victim's `user_id` into the *same* session record instead of rotating to a fresh one. The attacker, still holding that cookie, now has a session where `session[:user_id]` == the victim's ID, and `current_user` resolves to the victim on all subsequent requests, including deploy/rollback actions on `stacks`.

No existing guard prevents this: `force_github_authentication` only resets the session for a *different* case (`requires_fresh_login?`), not on normal successful login; there is no CSRF/state check being bypassed here (that's omniauth's job and orthogonal); model validations and webhook signature checks are irrelevant to this session-management code path.

### Impact Explanation
An attacker who can pre-plant or share a session cookie with a victim can, upon the victim's legitimate GitHub login completing, acquire full authenticated access as that victim — including deploy, rollback, and stack management actions gated behind `current_user`/`force_github_authentication`. This is a session fixation / forced OAuth completion bypass, matching the "High" impact category (session fixation / forced OAuth completion) explicitly listed in scope. It is repeatable against any victim who can be induced to reuse the attacker-influenced session (shared machines, kiosks, CI runners, or cookie-jar reuse scenarios), and the blast radius is per-victim-session rather than cross-tenant, but grants full account takeover for that session's duration.

### Likelihood Explanation
Requires the attacker to get their session cookie into the victim's browser before the victim completes OAuth — feasible in shared-browser/kiosk/CI-runner environments, or via response-splitting/cookie-injection style delivery if any exists, but does not require any Shipit or GitHub secret, admin privilege, or GitHub App key. This depends entirely on Shipit engine's own controller code (no `reset_session` call), independent of host-level session ID rotation configuration, so it is a genuine engine-level bug reachable by an unprivileged actor as described.

### Recommendation
Call `reset_session` in `Shipit::GithubAuthenticationController#callback` immediately before (or in place of) setting `session[:user_id]`/`session[:authenticated]`, so a new session identifier is issued at the moment of privilege escalation (unauthenticated → authenticated), consistent with the pattern already used in `logout` and in the fresh-login-required branch of `force_github_authentication`.

### Proof of Concept
Minitest plan (`test/controllers/github_authentication_controller_test.rb`, adapting existing callback test setup):
```ruby
test "callback rotates the session id to prevent fixation" do
  request.session[:some_pre_auth_marker] = "attacker-controlled"
  pre_auth_session_id = request.session.id

  stub_request_env_for_omniauth_success # existing helper used by other callback tests

  get :callback

  post_auth_session_id = request.session.id

  refute_equal pre_auth_session_id, post_auth_session_id,
    "session id must be rotated on login to prevent session fixation"
  assert_nil request.session[:some_pre_auth_marker],
    "pre-auth session data must not survive into the authenticated session"
end
```
This asserts both sides of the equality `session_id(before) == session_id(after)`: currently they are equal (bug present); after adding `reset_session` in `callback`, they diverge and the fixture data set before authentication no longer survives.

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

    end
