### Title
Unbounded disk growth from permanently stored invalid joints in `known_bad_joints` - ([File: joint_storage.js])

### Summary
An unprivileged peer or unit poster can repeatedly submit syntactically/structurally invalid joints (up to `MAX_UNIT_LENGTH`, ~5 MB each) that fail joint-level validation. Every such rejection is permanently persisted to the `known_bad_joints` table with no expiration, size cap, or purge routine, allowing an attacker to fill the victim node's disk with garbage data — directly analogous to CVE-2025-54605 ("disk filling from invalid blocks") in Bitcoin Core.

### Finding Description
When a joint fails validation at the joint level (as opposed to unit-content level), `network.js`'s `handleJoint` calls `joint_storage.saveKnownBadJoint(objJoint, error, ...)`: [1](#0-0) 

`saveKnownBadJoint` stringifies and inserts the **entire raw joint JSON** into the `known_bad_joints` table permanently, keyed by `objectHash.getJointHash(objJoint)`: [2](#0-1) 

Unlike `unhandled_joints`, which has an explicit TTL-based cleanup (`purgeOldUnhandledJoints` deletes rows older than 1 hour) invoked periodically via `purgeJunkUnhandledJoints`: [3](#0-2) [4](#0-3) 

there is no equivalent purge for `known_bad_joints` anywhere in the codebase — rows accumulate forever. The in-memory dedup map `assocKnownBadJoints` only prevents re-processing an *identical* joint hash a second time, but does nothing to stop an attacker from crafting a unique joint (e.g. varying an authentifier byte, timestamp, or any field) on every submission, each of which is a fresh joint hash and thus a fresh row. Since these are joint-level errors (malformed structure, bad signature format, size, etc.), they are cheap for the attacker to generate — no valid parents, no proof-of-work-equivalent cost, and no rate limiting is applied before the row is written. Each joint can be up to `MAX_UNIT_LENGTH` (5 MB by default): [5](#0-4) 

This is reachable both from a posted (light-client) joint via `handlePostedJoint` and from an online joint received from a peer via `handleOnlineJoint`, both of which route through `handleJoint`: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker (an unprivileged unit poster or a regular peer connection) can continuously submit unique, cheaply-crafted invalid joints, each up to 5 MB, causing the node's local database (`known_bad_joints` table) to grow without bound. Because there is no purge, size limit, or per-peer rate-limit on this specific write path, a sustained attack can exhaust the victim's disk space, potentially crashing the node's database engine or halting all further unit processing/writes — a denial of service against a single-node's ability to validate and store new units, consistent with the "network unable to confirm new units" impact class.

### Likelihood Explanation
High. Triggering `ifJointError` only requires a structurally malformed joint (not passing hash/authors/parents/messages structural checks in `validation.js`), which is trivial to generate programmatically and does not require any spendable funds, valid signatures over real inputs, or interaction with consensus state. An attacker can send an essentially unlimited stream of large, unique joints from a single connection or many connections without needing to pass any of the deeper (expensive) validation stages.

### Recommendation
Add a bound to `known_bad_joints`: cap total stored rows/bytes (e.g. LRU eviction or a maximum row count), add a time-based purge similar to `purgeOldUnhandledJoints`, and avoid storing the full raw joint JSON — store only the hash/error reason needed for dedup, or truncate/omit the joint body. Additionally, consider rate-limiting joint-level validation failures per peer/connection before they reach the persistence layer.

### Proof of Concept
1. Open a connection to the victim node (or post via the light-client `post_joint`/`handlePostedJoint` API).
2. Repeatedly submit joints that are large (up to `MAX_UNIT_LENGTH`) and intentionally malformed so they fail at the joint-level checks in `validation.js` (e.g., wrong authors/messages structure), varying a byte each time so each generates a distinct joint hash.
3. Observe each submission triggers `ifJointError` → `joint_storage.saveKnownBadJoint`, inserting a new row into `known_bad_joints` with the full JSON payload.
4. Repeat at high volume; since no purge or cap exists for this table, the database file grows unbounded until disk space is exhausted.

function saveKnownBadJoint(objJoint, error, onDone){
	var joint_hash = objectHash.getJointHash(objJoint);
	const truncatedError = truncate(error);
	assocKnownBadJoints[joint_hash] = truncatedError;
	db.query(
		"INSERT "+db.getIgnore()+" INTO known_bad_joints (joint, json, error) VALUES (?,?,?)",
		[joint_hash, JSON.stringify(objJoint), truncatedError],
		function(){
			onDone();
		}
	);
}
