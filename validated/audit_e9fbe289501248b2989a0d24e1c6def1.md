### Title
Webhook signature verification is bound to `repository.owner.login` while every event handler acts on the independent, unbound `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook using the `repository.owner.login` (or `organization.login`) field of the *unverified* JSON body, then checks the request's `X-Hub-Signature` against that secret. All downstream `Shipit::Webhooks::Handlers` (e.g. `PushHandler`, `PullRequest::ClosedHandler`) resolve which `Stack`/`Repository` to act on using a *different* field of the same body, `repository.full_name`. Because nothing cryptographically binds these two fields together, a signature that is valid for organization A's webhook secret can be replayed with `repository.full_name` pointed at organization B's repository, in any deployment configured with multiple GitHub Apps/organizations.

### Finding Description
`verify_signature` computes the app/secret to check against purely from attacker-supplied JSON, before the signature has been validated: [1](#0-0) 

`repository_owner`, the value used to pick the GitHub App (and thus the `webhook_secret`), is read straight from the request body: [2](#0-1) 

`verify_webhook_signature` only checks the HMAC of the *whole raw body* against the secret chosen this way; it performs no check that `repository.full_name` (or any other field) is consistent with `repository.owner.login`: [3](#0-2) 

Once the signature check passes, event handlers derive the target repository from a *different* JSON field, `repository.full_name`, with no re-check against `repository.owner.login`: [4](#0-3) 

`PushHandler` uses this to trigger a sync against any stack matching that repo/branch: [5](#0-4) 

`PullRequest::ClosedHandler` independently re-reads `params.repository.full_name` (a separately declared, unchecked string) to resolve the repository whose review stack gets archived: [6](#0-5) 

Shipit explicitly supports multiple GitHub Apps/organizations sharing one instance, each with its own `webhook_secret`, selected purely by organization name from the payload: [7](#0-6) 

**Binding broken:** `organization authenticated by webhook_secret (repository.owner.login)` ≠ `repository acted upon by the handler (repository.full_name)`.

Before the attack: signature verification is expected to authenticate that "GitHub, on behalf of the exact repository the payload describes, sent this event."
After the attack: an entity holding a valid `webhook_secret` for *any one* organization configured on the Shipit instance can produce a validly-signed body while setting `repository.full_name` to reference a repository belonging to a *different* organization also configured on that instance, since only `repository.owner.login`/`organization.login` is checked against the secret, and `repository.full_name` is never cross-validated.

### Impact Explanation
An attacker who is an owner of one GitHub organization/App configured in a multi-org Shipit deployment (a routine, unprivileged scenario for anyone who can create their own GitHub App and ask to be onboarded, or who compromises one tenant's low-value webhook secret) can forge webhook deliveries that are treated as authentic for a *different* organization's repositories. Concretely this allows:
- Forcing `Stack#sync_github` to run for arbitrary victim stacks (`PushHandler`), affecting deploy-eligibility/commit tracking.
- Archiving another organization's review stacks (`PullRequest::ClosedHandler`) or injecting fabricated commit statuses (`StatusHandler`) that influence merge/deploy gating decisions for repositories the attacker does not own.

This is a cross-repository/cross-organization write achieved purely by webhook forgery, without ever compromising the victim organization's own `webhook_secret`, `GITHUB_TOKEN`, or session — matching the "unauthorized deploy/merge" and "cross-repository writes" impact classes.

### Likelihood Explanation
Requires: (1) the Shipit instance configured with multiple GitHub Apps/organizations (a documented, supported configuration), and (2) the attacker controlling (or having compromised) the `webhook_secret` of *any one* of those organizations. Given that condition, exploitation is a single crafted HTTP POST with a computed HMAC — no other privilege (no Shipit session, no `ApiClient` token, no repository write access on the victim's org) is needed. Likelihood is therefore moderate: it is not exploitable on single-org deployments, but is straightforward once the multi-org feature is in use.

### Recommendation
Bind the field used to select the verification secret to the field(s) actually consumed by handlers. At minimum, in `WebhooksController#verify_signature`, after determining `repository_owner` and verifying the signature, re-derive the repository referenced in the payload and confirm its owner matches the organization whose secret validated the signature (reject if `repository.full_name.split('/').first.casecmp?(repository_owner)` fails). More robustly, resolve the target `Repository`/`Stack` inside each handler and assert `stack.repository.owner == verified_organization` before performing any mutation.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`, "Using Multiple Github Applications") with two orgs: `orgA` (attacker-controlled GitHub App, secret known to attacker) and `orgB` (victim).
2. Attacker crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "deadbeef...",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(orgA_webhook_secret, body)` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` (from `repository.owner.login`), validates the HMAC successfully against `orgA`'s secret.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("orgB/victim-repo")` and triggers `sync_github` on the victim's stacks — despite the request never being signed by, nor originating from, `orgB`'s GitHub App.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
