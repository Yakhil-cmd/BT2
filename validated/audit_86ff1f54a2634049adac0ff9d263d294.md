### Title
NULL/undefined pointer dereference in `handleOnlinePrivatePayment` when a private-payment counterparty sends a private element without a `payload` object - (File: network.js)

### Summary
`network.js`'s `handleOnlinePrivatePayment()` validates only that `arrPrivateElements` is a non-empty array before immediately dereferencing `arrPrivateElements[0].payload.denomination`. Like the muhammara bug, where `QueryDictionaryObject()` can return `NULL` and the caller dereferences it without a presence check, here `arrPrivateElements[0].payload` is attacker-controlled and can be omitted or set to `null`, causing an unhandled `TypeError` (dereferencing `undefined`/`null`) before any deeper structural validation occurs.

### Finding Description
`handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks)` performs this check first: [1](#0-0) 

```js
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
```

The only guard is `isNonemptyArray(arrPrivateElements)`, which validates that the array has elements but performs no check on the *shape* of each element. `arrPrivateElements[0].payload` is read directly and its `.denomination` property is accessed unconditionally. If a counterparty sends a private element object that lacks a `payload` key (or sets it to `null`), `arrPrivateElements[0].payload.denomination` throws `Cannot read properties of undefined (reading 'denomination')`, exactly analogous to the muhammara case where `QueryDictionaryObject()` returning NULL is dereferenced without a check.

This function is reachable from `handleOnlinePrivatePayment`'s callers processing `private_payment` messages received directly from another party (peer-to-peer private payment delivery, not the hub-relayed/validated path that performs the stricter shape check in `wallet.js`'s `handlePrivatePaymentChains`, which validates `isNonemptyObject(e.payload)` before calling the network layer). Any path that calls `network.handleOnlinePrivatePayment` with attacker-supplied `arrPrivateElements` that skip that upstream shape validation reaches the unguarded field access.

### Impact Explanation
An unhandled `TypeError` thrown synchronously inside a WebSocket message handler is not caught by any surrounding try/catch in the call path shown, and in Node.js an uncaught exception thrown outside of a promise/async boundary crashes the process (or is caught by a top-level `uncaughtException` handler, if present, which typically still causes the node to become unresponsive/restart). This constitutes a remotely triggerable Denial-of-Service: a single malformed `private_payment` message from a counterparty who is legitimately permitted to send private-payment chains to the victim's wallet/hub can crash the receiving node, matching the impact category "network unable to confirm new units" if directed at hub/relay processes, or at minimum a wallet DoS.

### Likelihood Explanation
Likelihood is high for the specific reachable surface: any device (private-payment counterparty) that is authorized to exchange private payment chains with a wallet can trivially omit the `payload` field or send `payload: null` in the head element of `arrPrivateElements`. No cryptographic material or special privilege is needed — this is simply a malformed JSON object sent over an already-established device-messaging channel used for private payment delivery.

### Recommendation
Add an explicit presence/shape check for `arrPrivateElements[0].payload` (and its expected sub-fields) before dereferencing, mirroring the stricter validation already performed in `wallet.js handlePrivatePaymentChains` (e.g., `isNonemptyObject(e.payload)`), and return `callbacks.ifError(...)` instead of allowing the property access to throw:

```js
if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
    return callbacks.ifError("private_payment content must be non-empty array");
if (!ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload))
    return callbacks.ifError("no payload in head private element");
```

### Proof of Concept
Send (as a private-payment counterparty/device) a `private_payment` message whose content is:
```json
[
  { "unit": "SOME_VALID_LOOKING_UNIT_BASE64", "message_index": 0 }
]
```
i.e., omit the `payload` field entirely (or set `"payload": null`). When the receiving node calls `network.handleOnlinePrivatePayment(ws, arrPrivateElements, ...)`, the line `arrPrivateElements[0].payload.denomination` throws a `TypeError`, which is not guarded, leading to a process crash/DoS on the receiving node.

**Note on confidence/uncertainty:** I was not able to fully trace, within the available tool budget, every single call site that feeds untrusted network/device input into `handleOnlinePrivatePayment` (e.g., confirming whether every code path performs the stricter `wallet.js`-style shape validation before reaching this function, or whether some direct-peer/device-message path bypasses it). The `wallet.js handlePrivatePaymentChains` path does perform a stricter check before forwarding to the network layer, but it wasn't fully confirmed whether *all* invocation paths of `network.handleOnlinePrivatePayment` (e.g. from direct peer connections without going through `wallet.js`) apply the same guard first. This should be verified in a live session against the full call graph before treating this as conclusively exploitable end-to-end.
