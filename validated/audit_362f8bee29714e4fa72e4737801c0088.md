### Title
`StatusHandler#process` writes CI status to `Commit` rows across all stacks without scoping to the webhook's authenticated repository, enabling a cross-tenant `deployable?` flip - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, a global, unscoped query, then calls `commit.create_status_from_github!(params)` on every match regardless of which stack/repository owns that `Commit`. Because the `commits` table's uniqueness constraint is `(sha, stack_id)` rather than `sha` alone, the same SHA can legitimately exist as separate `Commit` rows under different stacks (e.g. forks/mirrors sharing git history), letting an attacker who controls a signed webhook from their own org write a `success` status onto another org's `Commit`, flipping `Commit#deployable?`.

### Finding Description
The binding that should hold is: `webhook_signing_org(payload.repository.owner.login) == commit.stack.repository.owner` for every `Commit` row mutated by the webhook. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only proves the payload was signed by whichever org is named in `repository_owner` — it never restricts which `Commit`/`stack` rows the resulting handler is allowed to touch.

`StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This is a global, unscoped lookup by `sha` across the entire `commits` table — no join/filter on `stack`, `repository`, or the authenticated `repository_owner`. Contrast this with `CheckSuiteHandler#process` (app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17), which correctly scopes via `stacks.where(branch: ...)` before touching `stack.commits`, i.e. constrained to stacks belonging to the authenticated repository. `StatusHandler` has no equivalent scoping. `create_status_from_github!` then writes the status using the *found commit's own* `stack_id` (app/models/shipit/commit.rb:165-169), and `Status.replicate_from_github!` persists it (app/models/shipit/status.rb:24-33), triggering `schedule_continuous_delivery` on that commit's stack — not the stack that authenticated the webhook. [4](#0-3) [5](#0-4) 

The schema explicitly permits the same SHA to exist under multiple stacks: the unique index on `commits` is `(sha, stack_id)`, not `sha` alone. [6](#0-5) 

Exploit flow: attacker owns/controls a GitHub org "attacker-org" that already has a legitimately configured Shipit stack (so their `status`/`check_suite` webhooks are correctly signed and pass `verify_signature`). Attacker forks or otherwise causes a repository under their control to share a git commit (identical SHA) with a `Commit` row already present under a victim stack (this happens whenever two Shipit stacks/forks share history, which is common for mirrored/forked repos tracked by Shipit). Attacker's CI (or the attacker directly, since they control their own repo's status posting) sends a `status` webhook for that shared SHA with `state=success`. `verify_signature` passes because it is genuinely signed by attacker-org's webhook secret. `StatusHandler#process` then finds *all* `Commit` rows with that SHA — including the victim's — and calls `create_status_from_github!` on each, writing a `success` `Status` under the victim stack. If the victim commit is unlocked and not otherwise blocked, `Commit#deployable?` (app/models/shipit/commit.rb:227-229) flips to `true`, enabling `ContinuousDeliveryJob`/`schedule_merges` to deploy on the victim's stack. [7](#0-6) 

Existing guards do not prevent this: `verify_signature` only authenticates the org name embedded in the payload, it does not constrain which `Commit`/`stack` records the handler may mutate; `ExplicitParameters` (`params do ... end` in `StatusHandler`) only validates payload shape, not repository ownership; there is no `stacks`/repository scoping call in `StatusHandler` analogous to `CheckSuiteHandler`.

### Impact Explanation
An attacker with a legitimately-configured but unrelated Shipit stack can write forged CI status records to another tenant's `Commit`, flipping `Commit#deployable?` and triggering `ContinuousDeliveryJob`/merge scheduling for a stack/repository they do not own — an unauthorized deploy trigger for another org's stack. This is a cross-tenant write ("a payload for one repository mutating another's ... commit ... task ... an unauthorized deploy"), matching the Critical severity bar. The blast radius extends to any Shipit deployment hosting multiple stacks/tenants where SHA collisions/shared history across stacks are possible (forks, mirrors, monorepo splits).

### Likelihood Explanation
Preconditions: (1) attacker must already have a Shipit-registered stack of their own with a valid webhook integration (a legitimate but low-privilege configuration, not a Shipit operator role); (2) a `Commit` row must exist in a victim stack with the same SHA as one the attacker's repo can post a status for — realistic when repos are forked/mirrored and Shipit tracks both, or when a shared upstream commit is synced into multiple stacks. Attacker cost is low (send one webhook), and the attack is repeatable against any commit shared this way. Likelihood is moderate-to-high in multi-tenant Shipit deployments where forks/mirrors of tracked repositories are common, but requires this SHA-sharing precondition, so it's not universally exploitable against arbitrary unrelated repositories without shared history.

### Recommendation
Scope `StatusHandler#process` (and any similar unscoped lookups) to only the stacks/commits belonging to the repository that authenticated the webhook, mirroring `CheckSuiteHandler`'s pattern, e.g. resolve `stacks` from the payload's `repository.full_name`/`repository_owner` first, then `stack.commits.where(sha: params.sha)`, instead of a global `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two stacks under different repositories/orgs: `stack_a` (attacker-owned, repository `attacker-org/repo`) and `stack_b` (victim, repository `victim-org/repo`).
2. Create `Commit` rows with the *same* `sha` under each stack (`stack_a.commits.create!(sha: "deadbeef...", ...)`, `stack_b.commits.create!(sha: "deadbeef...", ...)`), reflecting the unique `(sha, stack_id)` index that permits this.
3. Assert BEFORE: `commit_b.deployable?` is `false` (no success status yet) — left side of binding: `signing_org = "attacker-org"`, right side: `commit_b.stack.repository.owner = "victim-org"` — these differ.
4. Stub `Shipit.github(organization: 'attacker-org').verify_webhook_signature` to return `true` (simulating a genuinely signed webhook from attacker-org).
5. POST to `/webhooks` with `X-Github-Event: status`, body `{"sha" => "deadbeef...", "state" => "success", "repository" => {"owner" => {"login" => "attacker-org"}}}`.
6. Assert AFTER: `commit_b.reload.deployable?` becomes `true` even though the webhook was only authenticated for `attacker-org`/`stack_a` — proving the binding is violated: a webhook authenticated for one org mutated another org's commit/stack state.
7. Additionally assert `commit_a.reload.deployable?` also became `true` (expected, in-scope write) to contrast the correct vs. incorrect write.
