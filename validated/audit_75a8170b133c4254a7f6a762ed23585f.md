### Title
Unbounded blob size and no total-size cap before disk write - ([File: internal/skills/installer/installer.go])

### Summary
`installSkill` in [1](#0-0)  fetches each skill file via `discovery.FetchBlob` and writes the fully-buffered content to disk with `os.WriteFile`, with no check against the file's declared size or any global byte budget. Because a skill's file list (and their sizes) is entirely attacker-controlled via the repository's git tree, an attacker publishing a skill with many/large blobs can force the victim's `gh skill install` to buffer and write an arbitrarily large amount of data.

### Finding Description
`DiscoverSkillFiles` parses the tree API response into `SkillFile{Path, SHA, Size}`, where `Size` is already known from GitHub's tree entry metadata and is fully attacker-controlled (attacker owns the tree/blobs) — see [2](#0-1) . `installSkill` iterates these files but never inspects `file.Size` before calling `discovery.FetchBlob`: [3](#0-2) .

`FetchBlob` decodes the entire base64 blob payload into memory via `io.ReadAll` with no size ceiling, then returns it as `iostreams.Untrusted`: [4](#0-3) . The decoded bytes are then written verbatim to disk with `os.WriteFile(destPath, []byte(content), 0o644)`: [5](#0-4) .

There is no size validation anywhere in this chain (no comparison to `file.Size`, no cap on cumulative bytes across files/skills). The worker pool in `Install` runs up to `maxConcurrency = 5` goroutines concurrently, each independently invoking `installSkill`/`FetchBlob`/`os.WriteFile` per skill: [6](#0-5) [7](#0-6) . This means up to 5 large blobs can be buffered and written in parallel, multiplying peak memory and disk write throughput, but it does not change the fundamental fact that the total data written is bounded only by however many/large files the attacker's tree lists — concurrency amplifies rate, not an additional class of bypass.

Existing protections in this codebase (`safepaths`, `safeurl`) only address path-traversal and URL-construction safety; they do not implement or enforce any byte-size limit on blob fetch or write.

### Impact Explanation
This maps to a resource-exhaustion / disk-exhaustion denial-of-service against the local machine running `gh skill install`. Concretely: a malicious repository can advertise a `skills/` directory whose SKILL.md-adjacent files are (or reference) blobs of maximal allowed size, and/or reference many files, causing the victim's `gh` process to buffer each blob fully in memory and then write it to disk, potentially consuming large amounts of disk space and memory per invocation. Actual per-blob size is ultimately bounded by whatever ceiling the GitHub Git Data "get a blob" API enforces server-side (historically ~100MB for blob content retrieval), but nothing in the `gh` client itself prevents accepting and writing blobs up to that limit, nor caps the aggregate size across many files/skills in a single install run. This is a local availability impact only (disk/memory exhaustion), not code execution, credential exfiltration, or a path/authorization bypass.

### Likelihood Explanation
Exploitability requires only that the victim run `gh skill install` (or equivalent bulk-install flow) against a repository the attacker controls, publishing a `skills/` tree with large or numerous blob entries matching the skill convention. No token, no MITM, no social engineering beyond convincing/tricking the victim into installing from that repo is needed. This is realistic given `gh skill install` is explicitly designed to consume third-party published skills. Repeatability is high — the same crafted repo can be reused across systems.

### Recommendation
- Enforce a reasonable maximum size (e.g., check `SkillFile.Size` from the tree entry before fetching) and reject/skip files exceeding a sane per-file threshold (e.g., a few MB, consistent with typical SKILL.md/asset sizes).
- Enforce an aggregate size budget across all files in a skill (and across all skills in a single `Install` invocation) to bound total disk/memory usage.
- Consider streaming the blob fetch/decode/write path instead of fully buffering with `io.ReadAll` in `FetchBlob`, using an `io.LimitReader` to hard-cap bytes read regardless of what the tree metadata claims.

### Proof of Concept
Go test sketch using `httpmock`:
1. Mock `GET /repos/o/r/git/trees/{treeSHA}?recursive=true` to return a tree with one `blob` entry under `skills/evil/` with `size` field set very large (e.g., 500_000_000) matching `SKILL.md`.
2. Mock `GET /repos/o/r/git/blobs/{sha}` to return `{"sha":"...","encoding":"base64","content":"<very large base64 payload>"}` (e.g., construct a large but test-feasible payload, such as tens of MB, to demonstrate the absence of a cap without requiring an actual multi-hundred-MB test fixture).
3. Call `installer.Install` with a single skill pointing at this tree/blob.
4. Assert that `installSkill` proceeds to call `os.WriteFile` with the full, unbounded content and does not return an error or truncate — i.e., there is no size-limit check that would otherwise cause `installSkill` to fail with something like "blob exceeds maximum allowed size".
5. Compare against the expected fix behavior: after adding a size cap, the same test should assert an error is returned before any bytes are written to disk.

// DiscoverSkillFiles returns all file paths belonging to a skill directory
// by fetching the skill's subtree directly using its tree SHA.
func DiscoverSkillFiles(client *api.Client, host, owner, repo, treeSHA, skillPath string) ([]SkillFile, error) {
	apiPath, err := safeurl.JoinPath("repos", owner, repo, "git", "trees", treeSHA)
	if err != nil {
		return nil, err
	}
	apiPath.SetQuery("recursive", "true")
	var tree treeResponse
	if err := client.REST(host, "GET", apiPath.String(), nil, &tree); err != nil {
		return nil, fmt.Errorf("could not fetch skill tree: %w", err)
	}

	if tree.Truncated {
		// Recursive fetch was truncated. Fall back to walking subtrees individually.
		return walkTree(client, host, owner, repo, treeSHA, skillPath, 0)
	}

	var files []SkillFile
	for _, entry := range tree.Tree {
		if entry.Type == "blob" {
			files = append(files, SkillFile{
				Path: skillPath + "/" + entry.Path,
				SHA:  entry.SHA,
				Size: entry.Size,
			})
		}
	}

	return files, nil
}

// FetchBlob retrieves the content of a blob by SHA. The blob is base64-encoded
// inside the JSON response and decoded here, so it is returned as
// iostreams.Untrusted and callers must choose sanitized display or raw
// round-tripping.
func FetchBlob(client *api.Client, host, owner, repo, sha string) (iostreams.Untrusted, error) {
	apiPath, err := safeurl.JoinPath("repos", owner, repo, "git", "blobs", sha)
	if err != nil {
		return iostreams.Untrusted{}, err
	}
	var resp struct {
		SHA      string `json:"sha"`
		Content  string `json:"content"`
		Encoding string `json:"encoding"`
	}
	if err := client.REST(host, "GET", apiPath.String(), nil, &resp); err != nil {
		return iostreams.Untrusted{}, fmt.Errorf("could not fetch blob: %w", err)
	}

	if resp.Encoding != "base64" {
		return iostreams.Untrusted{}, fmt.Errorf("unexpected blob encoding: %s", resp.Encoding)
	}

	// GitHub API returns base64 with embedded newlines; use the StdEncoding
	// decoder via a reader to handle them transparently.
	decoded, err := io.ReadAll(base64.NewDecoder(base64.StdEncoding, strings.NewReader(resp.Content)))
	if err != nil {
		return iostreams.Untrusted{}, fmt.Errorf("could not decode blob content: %w", err)
	}

	return iostreams.NewUntrustedBytes(decoded), nil
}
