### Title
Stale-worktree cleanup timer is refreshed by ref oscillation, allowing an attacker who controls the synced ref/repo to indefinitely bypass `--stale-worktree-timeout` and exhaust disk space under `--root` - (File: main.go)

### Summary
`git-sync`'s stale-worktree garbage collection (`removeStaleWorktrees`) decides what to delete purely from filesystem `ModTime()`, and that `ModTime` is reset via `touch()` every single time a worktree transitions from "current" to "stale," not from when it was actually abandoned. An attacker who can push/alter the remote ref (the "attacker-pushed commit/ref" threat model this scan targets) can cycle the ref among a small set of distinct commits faster than `--stale-worktree-timeout`, causing each of those worktrees to be re-touched on every eviction from "current" status. This is structurally identical to the reported Union Finance issue: a counter meant to measure sustained "badness"/inactivity (`vouch.lastUpdated` / worktree `ModTime`) is reset by an unprivileged, repeatable, low-cost action (a trivial repeat borrow / a trivial ref flip), defeating the intended aging/penalty logic.

### Finding Description
`repoSync.SyncRepo` touches the outgoing worktree directory every time the ref changes: [1](#0-0) 

That touch resets the directory's `ModTime`, which is the sole input to the staleness check in `removeStaleWorktrees`: [2](#0-1) 

The intent (confirmed by the flag docs) is that a worktree is retained for `--stale-worktree-timeout` after it *stops* being the link target, then reclaimed: [3](#0-2) 

However, `ModTime` is reset every time the directory *re-enters* the stale state, not once when it was first abandoned. If an attacker controlling the upstream repository (or a compromised push credential/ref) pushes alternating commits — e.g. `A, B, A, B, ...` — faster than the configured `--stale-worktree-timeout` and `--period`, each flip makes the previous "current" worktree stale and immediately re-touches it (main.go:1964-1970), restarting its staleness clock before `removeStaleWorktrees` (invoked from the outer sync loop) ever observes it as old enough to delete. By using more than two distinct large commits in the rotation, the attacker can keep an arbitrary number of multi-hash worktrees alive simultaneously under `git.worktreeFor("")` (the `.worktrees` directory under `--root`), since none of them individually accumulates enough idle time to cross the timeout.

### Impact Explanation
This produces unbounded growth of worktree directories under `--root` (bounded only by the number of distinct commits/content sizes the attacker cycles through and available disk), because the cleanup mechanism can be perpetually defeated by cheap, legitimate-looking ref churn. Once disk under `--root` fills, subsequent `git fetch`/`worktree add`/checkout operations that `git-sync` depends on for every future sync will fail, resulting in persistent sync denial for the sidecar and any consumer relying on the published symlink. This falls within the accepted impact category of "persistent sync denial" caused by resource exhaustion driven entirely by attacker-controlled ref/commit content, without requiring any additional flags beyond a configured `--stale-worktree-timeout` (or even the default of `0`, though the effect is most pronounced with a non-trivial configured timeout, which is the documented/expected usage).

### Likelihood Explanation
Likelihood is moderate-to-high in environments where `git-sync`'s upstream `--repo` is attacker-influenceable (e.g., synced from a branch that untrusted contributors can push to, or a compromised upstream). No special git-sync flags beyond a normal `--stale-worktree-timeout` deployment are required; the attacker only needs push access to the source ref and the ability to alternate commits faster than the configured timeout/period, which are ordinary git operations, not privileged git-sync features.

### Recommendation
Base staleness on the time since the worktree was first observed as non-current (i.e., persist a first-went-stale timestamp, analogous to the report's recommendation to use `lastRepay`/creation time rather than a value refreshed by routine, repeatable actions) rather than resetting `ModTime` on every transition into the stale state. Alternatively, only `touch()` a worktree directory the first time it becomes stale (skip the touch if it is already stale and its `ModTime` predates "now"), and/or enforce a hard cap on total worktree count/disk usage under `--root` independent of the timeout-based cleanup.

### Proof of Concept
1. Deploy `git-sync` with `--stale-worktree-timeout=5s` and `--period=100ms` against a repo the attacker can push to (mirrors the existing `e2e::stale_worktree_timeout` test scaffolding: [4](#0-3) ).
2. Attacker pushes commit `A`, waits for sync, then pushes commit `B` (different content), waits for sync — this causes the `A` worktree to become stale and be `touch()`-ed (main.go:1964-1970).
3. Before 5s elapses, attacker pushes commit `A` again (revert), then `B` again, repeating this flip faster than `--stale-worktree-timeout`.
4. Observe via `assert_file_exists "$ROOT/.worktrees/$wtA"` and `$wtB` that neither worktree is ever removed by `removeStaleWorktrees` (main.go:1420-1441), regardless of how long the campaign runs, because each is re-touched before crossing the timeout.
5. Scale the rotation to N distinct large commits to grow `$ROOT/.worktrees` without bound until disk exhaustion breaks subsequent syncs.

func (git *repoSync) removeStaleWorktrees() (int, error) {
	currentWorktree, err := git.currentWorktree()
	if err != nil {
		return 0, err
	}

	git.log.V(3).Info("cleaning up stale worktrees", "currentHash", currentWorktree.Hash())

	count := 0
	err = removeDirContentsIf(git.worktreeFor("").Path(), git.log, func(fi os.FileInfo) (bool, error) {
		// delete files that are over the stale time out, and make sure to never delete the current worktree
		if fi.Name() != currentWorktree.Hash() && time.Since(fi.ModTime()) > git.staleTimeout {
			count++
			return true, nil
		}
		return false, nil
	})
	if err != nil {
		return 0, err
	}
	return count, nil
}

            The length of time to retain stale (not the current link target)
            worktrees before being removed. Once this duration has elapsed,

            (as determined by --sync-timeout). If not specified, this defaults
            to 0, meaning that stale worktrees will be removed immediately.
