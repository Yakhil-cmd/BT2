### Title
Cross-Organization Webhook Forgery via Owner/Full-Name Mismatch in Signature Verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) is used to validate an inbound webhook's HMAC signature based on `repository_owner`, a field taken directly from the **unverified** JSON body. Every webhook handler, however, resolves the target `Stack`/`Repository` using a *different* field from the same unverified body: `repository.full_name`. Because the signature check authenticates the organization named in `owner.login` while the actual write target is whatever repository is named in `full_name`, an attacker who controls (or can register) a repository under any organization configured on the same Shipit instance can forge a validly-signed webhook whose `owner.login` matches their own org but whose `full_name` names a victim repository in a different organization.

### Finding Description
- `verify_signature` fetches the app config via `Shipit.github(organization: repository_owner)`, where `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 
- The signature itself is verified with `OpenSSL::HMAC.hexdigest` against that org's `webhook_secret`; if that org's `webhook_secret` is unset (a documented, valid configuration — see the example secrets files), verification is skipped entirely and `true` is returned unconditionally. [3](#0-2) [4](#0-3) 
- Once the signature "passes" (bound only to `owner.login`), `WebhooksController#create` dispatches the full, attacker-controlled payload to every registered handler for the event. [5](#0-4) 
- Every handler resolves its target stack independently, using `repository.full_name` — not `owner.login` — via the shared `Handler#stacks`/`Handler#repository_name`: [6](#0-5) 
- Concretely, `PushHandler` uses this shared resolver to find and act on stacks matching `full_name` and the pushed branch, calling `stack.sync_github(expected_head_sha: params.after)`: [7](#0-6) 

The engine explicitly supports multiple, independently-configured GitHub Apps/organizations on one Shipit instance (each with its own `webhook_secret`), as shown in the multi-org secrets fixture: [8](#0-7) 

Nothing in `verify_signature` or in `Handler` cross-checks that `owner.login` (the identity that authenticated the request) is actually the owner segment of `full_name` (the repository the handler will act on). The equality that should hold — `organization authenticated == organization owning the repository being written to` — is never enforced.

### Impact Explanation
An attacker who has legitimate access to *any* organization/app configured on the shared Shipit instance (e.g., their own low-trust org, or any org whose `webhook_secret` is left blank per the documented default) can compute or bypass a valid signature and then set `repository.full_name` to target a completely unrelated, higher-trust repository/stack. This lets an unprivileged external actor drive `Stack#sync_github` and any other webhook-triggered side effects (branch tracking, commit ingestion, CI/status processing feeding the merge queue, PR-driven review-stack creation) against a repository they have no access to — a cross-repository/cross-organization boundary violation reachable with no Shipit session, API token, or GitHub write access to the victim repo.

### Likelihood Explanation
Exploitability requires only: (1) the target Shipit instance hosting more than one GitHub App/organization (an explicitly supported, documented configuration), and (2) the attacker controlling a repository in one of those configured organizations (their own, or any one left with no `webhook_secret`, which is the default/example configuration). No secrets belonging to the victim organization are needed. This is a straightforward payload-crafting attack against a public webhook endpoint.

### Recommendation
In `WebhooksController#verify_signature` (or centrally in `Handler`), verify that `payload.dig('repository', 'owner', 'login')` (or `organization.login`) matches the owner segment actually used to resolve the target `Repository`/`Stack` (i.e., derived consistently from `repository.full_name`) before any handler runs. Alternatively, resolve the target `Repository` first using an owner+name pair verified against the same organization used to select the `webhook_secret`, rejecting the request if they diverge.

### Proof of Concept
1. Attacker controls `attacker-org/attacker-repo`, connected to the shared Shipit instance's GitHub App configured with `webhook_secret: nil` (or a secret the attacker knows because it's their own org).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates (or skips validation for) the signature using `attacker-org`'s config — succeeding. [1](#0-0) 
4. `PushHandler#process` resolves `stacks` via `full_name = "victim-org/victim-repo"` and invokes `sync_github`/downstream processing on the victim's stack, despite the signature only proving authorship by `attacker-org`. [6](#0-5) [7](#0-6)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
