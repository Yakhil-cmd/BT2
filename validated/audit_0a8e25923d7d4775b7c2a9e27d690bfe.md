## Answer

The scenario in the question is real: `PreStxOp::parse_from_tx` places no cryptographic requirement that the address in `output` (taken from tx output #0) be controlled by whoever signs the transaction's inputs — it only requires the output be `try_into_stacks_address()`-representable.

**The broken equality:**
`STX principal whose balance is locked/queried by `.pox-N stack-stx`` (`tx-sender` == `PreStxOp.output`) **should equal** `STX principal that actually authorized this burnchain-stacking action (i.e., controlled the Bitcoin key that "proves" the op)`. As shown below, these two values can diverge.

### Code path

1. `PreStxOp::parse_from_tx` takes output #0 of the PreStx transaction, requires only that it is representable as a legacy Bitcoin/Stacks address — no relation to `tx.get_signers()`/input keys is checked: [1](#0-0) 

2. The follow-on `StackStxOp` is bound to the `PreStxOp` only by requiring its first input to reference `(pre_stx_txid, vout=1)` — i.e., it must spend the *change* output of the PreStx tx, which belongs to whoever funded/signed the PreStx tx (the attacker), not to whoever's address sits at vout=0: [2](#0-1) 

3. `classify_transaction` propagates `pre_stx.output` directly as `sender` for the `StackStxOp` (and identically for `TransferStxOp`/`DelegateStxOp`), with no additional check that this address is related to the actual signer of either transaction: [3](#0-2) 

4. When the operation is applied, the node invokes the PoX contract's `stack-stx` **directly as a Clarity contract-call with `tx-sender` forcibly set to `sender`** (i.e., the attacker-chosen `PreStxOp.output`), bypassing normal signed-transaction authorization entirely: [4](#0-3) 

5. Inside `stack-stx` (pox-4), the only authorization-like check is `consume-signer-key-authorization`, which validates a *signer-key* (for the DKG/reward-slot signing role) — it does **not** verify that `tx-sender` (the STX owner) consented to have `amount-ustx` locked: [5](#0-4) 

### Exploit flow

- Attacker builds a `PreStxOp` Bitcoin tx: input = attacker's own UTXO (attacker signs it), output vout#0 = the reserve/exchange's legacy Bitcoin address (attacker only needs to know this public address, not its key), output vout#1 = change back to attacker.
- `PreStxOp.output` becomes `StacksAddress::from_legacy_bitcoin_address(reserve_addr)` — the reserve's Stacks address — entirely without reserve's participation.
- Attacker then submits a `StackStxOp` tx whose input spends vout#1 of the prior tx (signed with the attacker's own key, since it's the attacker's change). `StackStxOp.sender` is set from the `PreStxOp.output` = reserve's address; `reward_addr` (PoX payout address) is taken from the new tx's own vout#0 and can be set to the attacker's own address.
- The node executes `stack-stx` with `tx-sender = reserve address`. If the reserve has sufficient unlocked STX, its balance is locked for `num_cycles`, and PoX BTC rewards for those cycles are paid to the attacker's `reward_addr` — all without the reserve ever signing a Stacks transaction or a Bitcoin transaction from its own key.

### Why existing guards don't stop it

- `verify-signer-key-sig`/`consume-signer-key-authorization` authenticate a signer-key for the DKG/reward-slot role only, not the STX-owner's consent to lock their balance — it's orthogonal to `tx-sender`.
- `check-pox-lock-period`, `can-stack-stx` and the balance check (`stx-get-balance tx-sender`) only validate cycle/amount bounds, not authorization of `tx-sender` itself.
- There is no code anywhere in `PreStxOp`/`StackStxOp` parsing that compares the Bitcoin address at `PreStxOp` output vout#0 to the public key(s) that signed either the PreStx or StackStx Bitcoin transaction's inputs.

### Impact

This is a **temporary freezing of a third party's STX balance plus theft of the associated PoX/BTC reward**, matching the rules' High-severity categories ("temporary freezing of staked funds," "an unsigned stacking action"). It is repeatable against any address with a spendable unlocked STX balance, at the cost of only a couple of cheap Bitcoin transactions (attacker's own UTXOs/fees), and requires no privileged role — fully consistent with the described PRECONDITIONS.

### Title
Unauthorized locking of an arbitrary Stacks address's STX via `PreStxOp`/`StackStxOp` output spoofing - (File: stackslib/src/chainstate/burn/operations/stack_stx.rs)

### Summary
`PreStxOp::parse_from_tx` binds the future "stacking sender" identity to an arbitrary Bitcoin output address (vout#0) with no proof that the transaction's signer controls that address; the companion `StackStxOp` is authorized merely by spending vout#1 (the payer's own change), letting anyone lock STX out of any address whose legacy Bitcoin-mapped address they merely know, while diverting PoX rewards to themselves.

### Finding Description
The equality that should hold — "the STX-owning principal that authorized a stack-stx lock == the principal whose Bitcoin key signed the operation" — is broken because `PreStxOp.output` (the future `StackStxOp.sender`, hence Clarity `tx-sender` for the `stack-stx` contract-call) is read from an *output* of the PreStx transaction, which requires no signature, while the *authorization* check (`StackStxOp::get_sender_txid`) only verifies that the StackStx transaction spends vout#1 of the same PreStx transaction — a UTXO that belongs to whoever funded the PreStx transaction, not to whoever owns vout#0. See `PreStxOp::parse_from_tx` (`stackslib/src/chainstate/burn/operations/stack_stx.rs:106-126`), `StackStxOp::get_sender_txid` (`stack_stx.rs:232-247`), `classify_transaction` propagation (`stackslib/src/burnchains/burnchain.rs:929-963`), and the direct `tx-sender`-forced contract call in `process_stacking_ops` (`stackslib/src/chainstate/stacks/db/blocks.rs:4120-4130`). The pox-4 `stack-stx` function's only signature check (`consume-signer-key-authorization`/`verify-signer-key-sig`) authenticates the *signer key* for reward-slot purposes, not the STX owner's consent to lock their tokens.

### Impact Explanation
An attacker can lock any address's unlocked STX balance for up to the maximum PoX lock period without any interaction or signature from that address's owner, freezing their funds, while redirecting the corresponding PoX BTC reward payout to an address the attacker controls. This is repeatable every reward cycle against any sufficiently-funded target and matches "High — temporary freezing of staked funds" / "an unsigned stacking action."

### Likelihood Explanation
Feasible for any unprivileged actor: they only need (a) their own Bitcoin UTXOs to fund and sign both burnchain transactions, and (b) knowledge of the target's Bitcoin-derived legacy address (public information for any exchange/reserve). No pause admin, signer, or miner privilege is required, and the attack works in any epoch with active PoX/pox-4 stacking.

### Recommendation
Require that `PreStxOp.output` be provably controlled by the signer of the PreStx transaction's inputs (e.g., derive `sender`/`output` from the input's own public key/script rather than an arbitrary output), or require the `StackStxOp`'s (and `DelegateStxOp`'s) resulting Clarity call to additionally validate stacker consent independent of the signer-key authorization (e.g., a SIP-018 signature from the STX principal itself, analogous to `signer-sig`, before locking funds not owned by the transaction's actual key).

### Proof of Concept
Rust test on a booted `TestPeer`/regtest chainstate:
1. Fund attacker's Bitcoin wallet; construct and submit a `PreStxOp` with `output` set to a `StacksAddress` derived from a legacy Bitcoin address belonging to a "reserve" test account that never signs anything.
2. Fund the reserve's Stacks account with STX via normal means (simulate pre-existing balance).
3. Submit a `StackStxOp` whose only input spends vout#1 of the PreStx transaction (signed solely by the attacker), with `reward_addr` set to an attacker-controlled PoX address and `stacked_ustx` set to the reserve's full balance.
4. Mine forward and assert: (a) `stack-stx` succeeded with `tx-sender == reserve_stx_address`; (b) `get-stacker-info reserve_stx_address` shows a lock; (c) reserve's `STXBalance` shows `locked > 0` even though `reserve`'s private key never signed any Bitcoin or Stacks transaction; (d) reward for the cycle accrues to the attacker's `reward_addr`. This demonstrates the LOCK/AUTHORITY equality is violated.
