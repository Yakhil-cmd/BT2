### Title
Cross-organization `membership` webhook allows attacker to join arbitrary `Shipit::Team` by `github_id`, escalating into `Shipit.github_teams` authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
The `WebhooksController#verify_signature` only proves that the request was signed by *some* GitHub organization configured in `Shipit.github`, using `repository_owner` (taken straight from the attacker-controlled `organization.login` field for `membership` events) to pick which `webhook_secret` to check against. `MembershipHandler#find_or_create_team!` then looks up `Shipit::Team` purely by `github_id`, with no check that the found team's `organization` matches the organization that actually signed the request. An attacker who controls any org configured in `Shipit.github` can therefore forge a `membership` event whose `team.id` collides with a pre-existing `Team` belonging to a completely different organization and insert themselves as a member of it.

### Finding Description
The claimed binding is: `organization_that_signed_payload == organization_owning_matched_team`. Tracing the code shows this binding is never enforced, so it does **not** hold.

1. `WebhooksController#verify_signature` derives `repository_owner` via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . A `membership` payload has no `repository` key, so `repository_owner` is simply `params['organization']['login']` — a value fully controlled by whoever sends the webhook.
2. It then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . If the attacker names their own configured organization in `organization.login` and signs the body with that org's real `webhook_secret` (which they legitimately possess as the org owner), verification succeeds.
3. `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id)` [3](#0-2) . This lookup is scoped only by `github_id`, a plain integer with no relation to `params.organization.login` or to which org's secret verified the request. If the attacker sets `team.id` to the `github_id` of a pre-existing `Team` row belonging to a different, victim organization (e.g., `shopify`), `find_or_create_by!` finds and returns that existing record; the `do |team| ... end` initializer block (which sets `team.organization = params.organization.login`) only runs on creation, so the victim team's `organization` column is left untouched.
4. `MembershipHandler#process` then calls `team.add_member(member)` for `action: 'added'`, creating a `Shipit::Membership` linking the attacker's `User` (created via `User.find_or_create_by_login!(params.member.login)`, whose login is also attacker-controlled) to the victim's `Team` [4](#0-3)  and [5](#0-4) .
5. `User#authorized?` grants global Shipit access if the user's `teams` intersects `Shipit.github_teams` [6](#0-5) . If the victim team is one of the configured `Shipit.github_teams`, the attacker now satisfies this check.

No existing guard closes this gap: `verify_signature` validates a signature against an org name taken from the same untrusted payload used later to select the team; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence of fields, not cross-org identity; nothing in `Team`, `Membership`, or `MembershipHandler` re-derives or re-checks the organization against the signing org for existing records.

### Impact Explanation
A successful exploit lets an attacker who owns any GitHub organization configured in Shipit's `github` secrets forge membership into a `Shipit::Team` belonging to an entirely different, victim organization, without ever needing that victim organization's `webhook_secret`. If the victim team is listed in `Shipit.github_teams`, this directly grants the attacker `User#authorized?` == true, i.e. full authenticated access to the Shipit instance (deploy/rollback/merge capabilities across all stacks), which is an authentication/authorization bypass matching the "Critical: authentication bypass" / "High: escalation into `Shipit.github_teams`" categories. It is repeatable for any `github_id` the attacker can obtain and against any tenant/team configured on the same Shipit instance, so the blast radius spans all organizations sharing that deployment.

### Likelihood Explanation
Preconditions: (1) the attacker must control at least one GitHub organization that is configured in Shipit's `github` secrets (i.e., they must be an "onboarded" org with its own valid `webhook_secret` — the question's own attacker model grants this); (2) they need to know or guess the numeric `github_id` of a pre-existing `Team` row for the victim org (GitHub team IDs are not treated as secrets — they appear in team API responses/URLs, and could plausibly be discovered by anyone with visibility into the victim org's teams, or brute-forced since they are small sequential integers). Given those, the attack cost is a single crafted, self-signed HTTP POST to `/webhooks` with `X-Github-Event: membership`, fully repeatable at will.

### Recommendation
`MembershipHandler#find_or_create_team!` must scope the `Team` lookup by both `github_id` and `organization`, and the found/created team's `organization` must always be verified to equal the organization whose `webhook_secret` authenticated the request (i.e., compare against `repository_owner`/`params.organization.login` as validated in `verify_signature`, and reject or no-op if they diverge, e.g. via `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)` and raising/dropping the event if an existing team by that `github_id` belongs to a different `organization`).

### Proof of Concept
Add a minitest under `test/controllers/webhooks_controller_test.rb` (or an integration test):

```ruby
test ":membership from attacker org can hijack a team belonging to a different org" do
  victim_team = Team.create!(github_id: 999, organization: 'shopify', name: 'Victim', slug: 'victim', api_url: 'https://api.github.com/teams/999')

  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    team: { id: victim_team.github_id, name: 'Victim', slug: 'victim', url: victim_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker' }
  }.to_json

  assert_difference -> { Membership.count }, 1 do
    post :create, body: body, as: :json
  end

  attacker = User.find_by!(login: 'attacker')
  assert_includes victim_team.reload.members, attacker
  # Binding check: the org that signed (attacker-org) does NOT equal victim_team.organization ('shopify')
  refute_equal 'attacker-org', victim_team.organization
end
```
This demonstrates a `Membership` created for `victim_team` (owned by `shopify`) purely from a request signed with `attacker-org`'s credentials, proving the equality `organization_that_signed == organization_owning_team` is false yet the write still succeeds.
