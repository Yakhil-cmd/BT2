### Title
Webhook signature is verified against `repository.owner.login`, but the record written is selected by `repository.full_name` - cross-organization webhook forgery (Authentication Bypass) - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App / `webhook_secret` used for HMAC verification based on `repository.owner.login` (or `organization.login`), while the actual `Stack`/`Repository` that gets written by the event handlers is looked up using the *different* JSON field `repository.full_name`. These two fields are never cross-checked, so a payload can be signed as belonging to organization A while acting on a repository that belongs to organization B.

### Finding Description
`verify_signature` selects the per-organization webhook secret with: [1](#0-0) 
and derives that organization from: [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves the app config (and thus the `webhook_secret`) keyed strictly by `repository.owner.login`, as documented for multi-org setups in `docs/setup.md` ("Using Multiple Github Applications") — each organization has its own `app_id`/`webhook_secret`.

However, once the signature passes, every event `Handler` resolves the target repository/stack using a completely different field: [3](#0-2) 

`repository_name` reads `payload.dig('repository', 'full_name')` (i.e. `owner/repo`), not `repository.owner.login`. `PushHandler` and `StatusHandler` then act on whatever stacks that lookup returns: [4](#0-3) 

Because `repository.owner.login` (used to select the secret for signature verification) and `repository.full_name` (used to select the repository/stack that is mutated) are independent, attacker-controlled fields inside the same JSON body, there is no guarantee they refer to the same repository. This breaks the intended binding: `organization that authenticated == repository that is written`.

### Impact Explanation
An attacker who can obtain a validly-signed webhook payload for *any* organization configured in Shipit (e.g. by having push/webhook-configuration rights on a low-value repo in Organization A, or otherwise causing Organization A's app to sign a payload) can craft a payload where `repository.owner.login = "orgA"` (so `verify_webhook_signature` succeeds against Org A's secret) but `repository.full_name = "orgB/high-value-repo"`. This request is treated as authentic and dispatched to `PushHandler`/`StatusHandler`, which will locate and mutate stacks belonging to Org B's repository — an org the attacker has no credentials for. `PushHandler` triggers `stack.sync_github(expected_head_sha:)` and `StatusHandler` writes forged CI statuses via `commit.create_status_from_github!`, both of which influence deployability/state of a stack the attacker does not otherwise control. This is a cross-organization/cross-repository authentication-boundary violation reachable without any Shipit session, `ApiClient` token, or GitHub write access to the target repository, satisfying the "authentication bypass" / "cross-repository writes" impact bar.

### Likelihood Explanation
Exploitation only requires the ability to produce one validly HMAC-signed webhook body for some organization configured on the Shipit instance (the multi-org configuration is a documented, in-scope setup). The two fields (`repository.owner.login` vs `repository.full_name`) are ordinary attacker-controlled JSON fields with no server-side cross-validation, so once a valid signature for any org is obtained the `full_name` field can be freely set to target a different org's repository.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), require that the organization used to select the webhook secret matches the owner segment of `repository.full_name` (and, for organization-scoped events, that `organization.login` matches `repository.owner.login`). Reject the request (422) if they diverge, ensuring the signature-verified identity is the same identity the handlers act upon.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/organizations as documented, `orgA` (secret `SA`) and `orgB` (secret `SB`), each with stacks tracking their own repos.
2. Attacker (has webhook-secret `SA` for `orgA`, e.g. via a repo they administer under `orgA`) builds a payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/high-value-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(SA, body)>` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` and validates successfully against `SA`. [1](#0-0) 
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("orgB/high-value-repo")` [3](#0-2) 
and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on a stack the attacker never authenticated for, updating its head commit purely on the strength of `orgA`'s secret.
