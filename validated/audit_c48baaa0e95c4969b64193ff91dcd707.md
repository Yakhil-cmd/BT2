### Title
Webhook signature validated against `repository.owner.login` while handlers act on the independent `repository.full_name` field, allowing cross-organization stack writes - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
This is a structural analog of the `lastRPS` bug class: a cached/validated value (`lastRPS`, set by one code path) is later trusted by a different code path (`registerRewardDeposit`) without re-validating that the two are still consistent. In Shipit, the webhook pipeline has the same shape: the field used to select *which organization's secret* verifies the HMAC signature is not the same field later trusted to decide *which repository/stack* the verified payload is allowed to mutate.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/organization config — and therefore the `webhook_secret` used for HMAC verification — using: [1](#0-0) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Verification itself is per-organization keyed HMAC: [2](#0-1) 

Multiple organizations, each with their own GitHub App/`webhook_secret`, are expected to be configured simultaneously (see `config/secrets.development.shopify.yml` listing `somegithuborg` / `someothergithuborg`, and `docs/setup.md`). [3](#0-2) 

Once the signature check passes, the entire raw JSON body is handed unmodified to the event handlers: [4](#0-3) 

Every handler, however, resolves *which Stack/Repository to act on* using a different key in the same payload — `repository.full_name` — via `Shipit::Webhooks::Handlers::Handler#repository_name`: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler` (and `PullRequest::ClosedHandler`, which independently re-derives `Repository.from_github_repo_name(params.repository.full_name)`) act on whatever repository `full_name` says, regardless of which organization's secret validated the request: [6](#0-5) [7](#0-6) 

`repository.owner.login` and `repository.full_name` are two independent fields inside the same JSON body — nothing in the engine cross-checks that `full_name` starts with `owner.login`. The HMAC only proves the whole body was signed with *some* organization's secret; it does not prove the semantic consistency between the field used to pick the secret and the field used to pick the target repository.

**The broken equality:** `organization whose secret authenticated the request == repository/stack that gets written`. Before a malicious request: this equality always holds because GitHub itself always sends consistent `repository.owner.login`/`repository.full_name` pairs. After an attacker crafts a raw POST: the attacker controls both fields independently, so `repository.owner.login` can be set to an org they know the secret for (e.g., their own GitHub App installation configured on this same Shipit instance) while `repository.full_name` names a completely different, unrelated repository/stack tracked by the instance under a different organization.

### Impact Explanation
Any organization admin/owner who is legitimately allowed to install a GitHub App and receive webhooks on a shared, multi-org Shipit instance (a supported, documented configuration) can forge a POST to `/webhooks` signed with their own known `webhook_secret`, but with `repository.full_name` pointing at another organization's repository/stack tracked by the same instance. This triggers cross-repository writes: `PushHandler` will enqueue `GithubSyncJob`/`stack.sync_github` against another org's stacks, and `PullRequest::ClosedHandler` will archive/mutate another org's review stacks — actions that should require that org's own verified webhook. This matches the "Critical: cross-repository writes / unauthorized deploy" impact class, since sync/merge/deploy-adjacent state of an unrelated repository can be manipulated by a party who was never authorized for that repository.

### Likelihood Explanation
Requires only the ability to send an arbitrary HTTP POST to the public `/webhooks` endpoint with a valid signature computed from a webhook secret the attacker legitimately possesses (their own org's App secret in a shared/multi-tenant Shipit deployment). No repository write access, session, or `ApiClient` token to the *target* stack is needed — only the attacker's own, unrelated organization's webhook secret, which they configure themselves. This is realistic wherever Shipit hosts stacks for more than one GitHub organization/App, a configuration explicitly documented and supported by the engine.

### Recommendation
In `Shipit::Webhooks::Handlers::Handler#stacks`/`repository_name` (and in `PullRequest::ClosedHandler#repository`), verify that the resolved `Repository`'s `owner` matches the organization (`repository.owner.login`/`organization.login`) that was actually used to validate the webhook signature, and reject the event otherwise. Alternatively, pass the verified `repository_owner` down from `WebhooksController` into the handler dispatch and assert it equals the owner portion of `repository.full_name` before any handler is invoked.

### Proof of Concept
1. Configure Shipit (as documented) with two organizations, `orgA` and `orgB`, each with its own GitHub App and `webhook_secret`; both have stacks tracked in the same Shipit instance.
2. As the legitimate owner of `orgA`'s GitHub App, compute a valid `X-Hub-Signature` for a crafted push payload using `orgA`'s known `webhook_secret`, but set inside the JSON body:
   - `repository.owner.login = "orgA"` (satisfies `repository_owner` used for signature lookup)
   - `repository.full_name = "orgB/target-repo"` (a repository/stack belonging to `orgB`)
3. POST this body with header `X-Github-Event: push` to `/webhooks`. `verify_signature` succeeds because it only checks `repository.owner.login == "orgA"` against `orgA`'s secret.
4. `PushHandler#process` calls `Repository.from_github_repo_name("orgB/target-repo")`, resolving `orgB`'s stacks, and enqueues `stack.sync_github` for them — a write triggered against `orgB`'s stack using only `orgA`'s webhook credential.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
