The key finding centers on `number_from_seed` in `formula/evaluation.js`, which is oscript's general-purpose "randomness" primitive exposed to AA authors, and whose seed input has no protections against attacker precomputation—directly mirroring the "VDF inputs may be precomputable" bug class.

### Title
Attacker-controlled/grindable seeds in `number_from_seed` allow AA trigger senders to precompute favorable "random" outcomes - (File: formula/evaluation.js)

### Summary
Obyte's oscript language exposes `number_from_seed(seed[, min, max])` as a general-purpose pseudo-random-number primitive that AA (Autonomous Agent) authors commonly use to implement lotteries, games, and other outcome-randomizing logic. Like the reported `VDFVerifier` issue, this primitive is designed for reuse across many application scenarios, but the engine enforces no constraint ensuring the `seed` value is unpredictable or immune to precomputation at the time an AA trigger is composed. A trigger sender fully controls the unit they post (`trigger.data`, `trigger.unit`, output amounts, timestamp, parent selection, etc.), so any AA logic that derives "randomness" from trigger-controlled values can be freely searched/ground off-chain — trying arbitrarily many candidate triggers locally and only broadcasting the one unit whose derived outcome benefits the attacker — with no proof-of-work, staking, or time-lock cost analogous to the VDF/blockhash mitigations the report describes for `Inflation`.

### Finding Description
`number_from_seed` is implemented in `formula/evaluation.js` (case `'number_from_seed'`): it evaluates the caller-supplied `seed` expression, computes `sha256(seed)`, and maps the leading 16 hex characters onto a `[min,max]` range using simple division/scaling. [1](#0-0) 

The corresponding validation logic in `formula/validation.js` only checks argument count/types (non-string min/max, 1-3 args) — it performs no check on the *source* or entropy of `seed` itself. [2](#0-1) 

The oscript grammar allows `seed` to be any expression, including `trigger.data.*`, `trigger.unit`, `trigger.address`, `timestamp`, or any combination thereof. [3](#0-2) 

Because `trigger.unit` is the hash of the unit the trigger sender composes and signs locally before ever broadcasting it, and `trigger.data` is entirely attacker-supplied payload, the AA author's naive choice `number_from_seed(trigger.unit)` (or any other trigger-derived seed) is fully known to the sender before the corresponding unit is announced to the network. The attacker can construct many candidate trigger units offline (varying non-consensus-critical fields such as `trigger.data`, message ordering, parent selection, or timestamp), compute `number_from_seed` locally for each candidate exactly as the AA would, and only publish the one unit that yields a favorable outcome. This costs no proof-of-work and is unlimited in attempts, unlike the Ethereum block-hash entropy source discussed in the original report, which at least requires waiting for a future block to be mined by others.

The library does provide a genuinely more secure alternative — `vrf_verify`, which validates an RSA-based verifiable proof tied to an oracle's private key [4](#0-3) 
— but nothing in the engine prevents or warns against using the insecure `number_from_seed` primitive for the same "randomness" purpose, and it remains the far simpler, commonly-reached-for API.

### Impact Explanation
AAs are executed deterministically by all full nodes and their responses (including payment outputs) are consensus-critical. [5](#0-4) 
If an AA (e.g. a lottery, game-of-chance, or randomized-fee/discount contract) derives its payout logic from `number_from_seed` seeded by trigger-controlled data, an attacker/trigger-sender can grind offline for a trigger whose derived "random" outcome maximizes their payout, causing the AA to disburse funds unfairly. This is a direct path to AA fund loss (the same impact category called out as acceptable in the rules) reachable by any ordinary trigger sender with no special privilege — it doesn't require a malicious node, hub, or network-level attack, only local computation before broadcasting a single unit.

### Likelihood Explanation
Likelihood is high for any AA that follows the common (and until now undocumented-as-unsafe) pattern of seeding "randomness" from trigger-controlled data, because: (1) grinding is essentially free — computing SHA-256 and comparing against a `[min,max]` bound is cheap and can be repeated arbitrarily many times locally with no on-chain cost or delay; (2) the vulnerable primitive (`number_from_seed`) is the most obvious/ergonomic randomness function in oscript, more so than the significantly more complex `vrf_verify`; (3) the engine does not itself impose any check preventing trigger-derived data from being used as the sole seed, unlike other AA primitives that are hardened over time (e.g., `is_valid_signed_package` disabling itself in certain contexts to prevent recursive abuse, per `formula/validation.js` line 816). [6](#0-5) 

### Recommendation
- Document explicitly (and ideally enforce via linting/AA-validation warnings) that `number_from_seed` must never be seeded solely from trigger-controlled inputs (`trigger.data`, `trigger.unit`, `trigger.address`, freely chosen timestamps) when unpredictability matters; require mixing in a value unknown to the sender at trigger-composition time (e.g., a hash of a future, not-yet-existent MC unit, or a committed value from a trusted oracle via `data_feed`/`vrf_verify`).
- Consider extending `formula/validation.js`'s `number_from_seed` handling to statically flag/reject formulas where the seed expression is provably derived only from `trigger.*` fields with no independent oracle/VRF-backed entropy.
- Promote `vrf_verify` (or an equivalent oracle-backed commit-reveal / VDF-style construction) as the only sanctioned building block for AA "randomness," analogous to how the VDF report recommends restricting inputs to values immune to precomputation (e.g., minimum bit-length, hashing, primality testing).

### Proof of Concept
1. Deploy an AA whose `state` formula computes a payout multiplier via `number_from_seed(trigger.unit, 1, 100)` (or `number_from_seed(trigger.data.nonce, 1, 100)`), paying out more bytes/asset when the resulting number exceeds some threshold, as in `formula/evaluation.js` lines 1872-1917 above.
2. As the attacker, before broadcasting anything, construct the trigger unit exactly as the wallet would (same author, address, definition, parents, payment inputs/outputs), but vary a harmless field the AA does not otherwise constrain, e.g. `trigger.data.nonce` (or accept many different valid parent-unit combinations, changing `trigger.unit`'s hash each time).
3. For each candidate trigger, locally recompute `sha256(seed)` and the resulting `number_from_seed` output exactly as the AA formula engine would (same algorithm as `formula/evaluation.js` lines 1893-1917), off-chain, with zero cost, and repeat until a candidate produces the maximal favorable payout.
4. Sign and broadcast only that winning trigger unit; the AA validates and executes deterministically per `aa_composer.js`'s `handleTrigger`/`evaluateAA` flow, paying out the attacker-chosen favorable amount as if it were fairly randomized. [7](#0-6)
