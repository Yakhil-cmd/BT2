### Title
`ERC20Transactor` credits/debits the fixed requested `amount` into the XCM holding register instead of the ERC20 balance actually moved, breaking accounting for fee-on-transfer ERC20s - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor`, wired into Asset Hub Westend's `AssetTransactors` tuple, is used by any signed account executing XCM (via `pallet_xcm::transfer_assets`, `execute`, etc.) that references an ERC20 asset ID of the form `AccountKey20`. Its `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` implementations call the ERC20 contract's `transfer()` and, on a `true` return value, unconditionally treat the requested `amount` as fully moved — they never compare the checking account's/beneficiary's balance before and after the call. Any ERC20 contract that charges a fee-on-transfer (or otherwise moves less than the requested `value` while still returning `true`) causes the XCM holding register / checking-account accounting to diverge from the real on-chain ERC20 balances.

### Finding Description
`withdraw_asset_with_surplus` ( [1](#0-0) ) calls `IERC20::transferCall { to: checking_address, value: amount }` from the user's account to the `TransfersCheckingAccount`. If the call succeeds and decodes to `true`, it constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` using the **originally requested** `amount`, not the actual balance delta observed on `TransfersCheckingAccount`.

`deposit_asset_with_surplus` ( [2](#0-1) ) does the mirror operation: it calls `transfer(beneficiary, amount)` from `TransfersCheckingAccount`, and on `Ok(true)` simply returns `Ok(surplus)` — again with no verification that the beneficiary actually received `amount`.

Neither function performs a pre/post balance check on the source or destination account (an ERC20 equivalent of the fee-on-transfer PoC's recommended fix: "compute the balance before and after the transfer and use the delta"). The trait doc for `TransactAsset::withdraw_asset` even states the return value "should always be equal to `_what`" — this implementation blindly assumes that invariant holds for arbitrary ERC20 contracts matched by `ERC20Matcher`, rather than verifying it.

### Impact Explanation
If the referenced ERC20 contract implements a fee-on-transfer (or any transfer that moves less than `value` while returning `true`, e.g. rebasing/deflationary tokens):
- On withdraw: the `TransfersCheckingAccount` actually receives `amount - fee`, but the XCM holding register is credited with the full `amount`. This over-credits the executor's internal accounting relative to the real backing held by the checking account.
- On deposit: the beneficiary receives `amount - fee`, while the holding register is debited by the full `amount` and the operation is reported as fully successful (`Ok(surplus)`), silently under-delivering value to users with no error/refund/trap.

Repeated use of such assets breaks the 1:1 backing between what the XCM executor "believes" it holds in the checking account and what is really available, which can (a) cause future legitimate deposits to fail once the checking account balance is exhausted below what outstanding holding-register credits imply, and (b) silently lose value for users on deposit, both of which are integrity breaks of the transactor's accounting for the affected asset class. This does not affect assets that behave as standard ERC20 (fee-free, return actual amount transferred), and it does require a specific ERC20 contract with non-standard transfer semantics to be matched by `ERC20Matcher` and referenced in an XCM message — this is analogous to, and same class as, the referenced PoolTogether Medium finding.

### Likelihood Explanation
Reachability requires only that a signed account submit an XCM (through `pallet_xcm`'s public entry points such as `transfer_assets`/`execute`, no privileged origin needed) that references an `AccountKey20`-identified ERC20 contract handled by `ERC20Transactor`, which is part of the production `AssetTransactors` tuple on Asset Hub Westend ( [3](#0-2) ). Any user (not just governance) can deploy or reference an ERC20 contract with fee-on-transfer semantics via `pallet-revive`, since contract deployment is a normal, unprivileged extrinsic. The bug class matches Medium severity as in the reference report (accounting mismatch dependent on non-standard, but permissionless, token behavior), not an immediately catastrophic unbacked-issuance bug across all assets.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the relevant account's ERC20 balance immediately before and after the `transfer` call (e.g., via a `balanceOf` call) and use the observed delta — not the requested `amount` — when constructing `Erc20Credit`/reporting success. If the delta is less than the requested `amount`, either fail the operation (`FailedToTransactAsset`) or credit/report only the actually-moved amount, consistent with how `fungible`/`fungibles::transfer` in FRAME return the *actual* amount transferred (see [4](#0-3) ) rather than assuming success implies the exact requested amount moved.

### Proof of Concept
Not executed. Reasoning is based on static code inspection only:
- Confirmed `ERC20Transactor` is wired into the live `AssetTransactors` tuple used by `XcmConfig::AssetTransactor` on Asset Hub Westend ( [5](#0-4) ), confirming production reachability via `pallet-xcm`'s public extrinsics.
- Confirmed via `prdoc/stable2506/pr_7762.prdoc` that this transactor is intentionally added to Asset Hub Westend to let arbitrary user-referenced ERC20 contracts be used in XCM ( [6](#0-5) ).
- No automated Rust/XCM integration test reproducing an actual fee-on-transfer ERC20 contract was run; this would require deploying a custom `pallet-revive` contract with non-standard `transfer` semantics and asserting the holding-register/beneficiary-balance divergence, which was not executed in this session. I could not verify at runtime whether any downstream consumer (e.g., `Trader`, `AssetTrap`) happens to cross-check the ERC20 balance elsewhere in the pipeline — this would need to be confirmed via a live reproduction before treating this as fully proven.

	fn transfer(
		asset: Self::AssetId,
		source: &AccountId,
		dest: &AccountId,
		amount: Self::Balance,
		preservation: Preservation,
	) -> Result<Self::Balance, DispatchError> {
		let _extra = Self::can_withdraw(asset.clone(), source, amount)
			.into_result(preservation != Expendable)?;
		Self::can_deposit(asset.clone(), dest, amount, Extant).into_result()?;
		if source == dest {
			return Ok(amount);
		}

		Self::decrease_balance(asset.clone(), source, amount, BestEffort, preservation, Polite)?;
		// This should never fail as we checked `can_deposit` earlier. But we do a best-effort
		// anyway.
		let _ = Self::increase_balance(asset.clone(), dest, amount, BestEffort);
		Self::done_transfer(asset, source, dest, amount);
		Ok(amount)
	}
