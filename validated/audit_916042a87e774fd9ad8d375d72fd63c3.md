### Title
Third-party supply restamps a victim's cached risk parameters without the health-factor floor that gates `update_account_threshold` - (File: contracts/controller/src/positions/supply.rs)

### Summary
`supply` is permissionless for topping up hub assets an account already holds (`INV-AUTH-03`). Every supply leg calls `merge_supply_leg`, which unconditionally invokes `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple`, overwriting the position's cached LTV/liquidation-threshold tuple with the currently listed values. The dedicated restamping path, `update_account_threshold`, is deliberately gated: when `has_risks` is set it reverts unless the account clears an update health-factor floor, precisely so a third party cannot push an account into liquidation. The supply path applies the same restamp with no such floor.

### Finding Description
- `process_supply` authenticates only the caller and restricts non-owners to assets already present via `require_third_party_existing_supply` [1](#0-0) .
- `process_deposit` credits the measured receipt and calls `merge_supply_leg` per leg [2](#0-1) .
- `merge_supply_leg` runs `refresh_supply_risk_params(..., RiskRefreshScope::FullTuple)` on the victim's position before updating it [3](#0-2) .
- By contrast, the permissionless `update_account_threshold` "reverts unless the account clears the update health-factor floor, so it cannot be used to push an account into liquidation" [4](#0-3)  — confirming that restamping cached risk parameters is recognized as a risk-affecting action that needs an HF guard, which the supply leg lacks.

### Impact Explanation
Health factor is computed from Context-cached per-position thresholds. If governance lowers a listed asset's liquidation threshold (a legitimate config change), every account holding that asset keeps its stale, higher cached threshold until something restamps it. The intended refresh path (`update_account_threshold`) refuses to restamp an account that would fall below the update HF floor. An attacker can instead call `supply(victim_account_id, spoke, [(asset, dust)])` — allowed because the victim already holds the asset — which restamps the tuple via `FullTuple` with no HF check, dropping the victim's HF below 1 and immediately liquidating them at the new (harsher) parameters. The attacker then calls `liquidate` and seizes collateral at the HF-scaled bonus, extracting value the protocol's own threshold-update gate was designed to defer.

### Likelihood Explanation
Requires a governance risk-parameter tightening that leaves some accounts healthy under stale thresholds but unhealthy under new ones — a routine occurrence whenever thresholds are reduced. The attacker needs only dust of an asset the victim already supplies and a signed `supply` call; no privileged role, no oracle manipulation. Impact is forced liquidation and seizure bonus extraction (theft of user funds / loss better characterized as Medium given the config-change precondition).

### Recommendation
Apply the same health-factor floor used by `update_account_threshold` when a non-owner supply triggers `refresh_supply_risk_params` on another account's position, or skip the `FullTuple` restamp (or restamp LTV only) for third-party top-ups so strangers cannot force restamping of a victim's liquidation threshold.

### Proof of Concept
1. Governance reduces the liquidation threshold of asset `X`.
2. Victim account holds `X` supply and debt; HF ≥ 1 under the stale cached threshold, < 1 under the new one.
3. Attacker calls `controller.supply(attacker, victim_id, spoke_id, [(X_key, 1)])` — permitted since the victim already supplies `X` (`require_third_party_existing_supply` passes).
4. `merge_supply_leg` restamps the position's threshold via `RiskRefreshScope::FullTuple`; the victim's HF drops below 1.
5. Attacker calls `controller.liquidate(...)` and seizes collateral at the bonus — a transition `update_account_threshold` would have reverted.

/// Restricts third parties to existing supply positions. New accounts are
/// exempt because the caller becomes their owner.
fn require_third_party_existing_supply(
    env: &Env,
    account_id: u64,
    resolved_account_id: u64,
    caller: &Address,
    account: &Account,
    aggregated: &AggregatedPayments,
) {
    if account_id != 0
        && !account::is_owner_or_delegate(env, resolved_account_id, caller, &account.owner)
    {
        for (hub_asset, _) in aggregated.iter() {
            assert_with_error!(
                env,
                account.supply_positions.contains_key(hub_asset.clone()),
                GenericError::NotAuthorized
            );
        }
    }
}
