### Title
Webhook signature verified against attacker-selected organization while the acted-upon repository/stack is taken from the same unverified-binding payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App (and therefore the HMAC secret) used to check `X-Hub-Signature` based on `repository_owner`, which is read directly from the JSON body (`params.dig('repository','owner','login')`) rather than from any independently-authenticated source. In a multi-organization Shipit deployment (a documented, supported configuration in `docs/setup.md`, "Using Multiple Github Applications"), this creates a binding mismatch: "organization whose secret authenticated the request" is not provably equal to "repository/stack that the downstream handler mutates," because both values are read from the same attacker-influenced payload.

### Finding Description [1](#0-0) 
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [2](#0-1) 
where `repository_owner` is:
```ruby
params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
```
This is exactly the same JSON body whose `repository.full_name` field the downstream `Shipit::Webhooks` handlers (e.g. `push_handler.rb`, `status_handler.rb`) will later use to resolve which `Stack`/`Repository` record to act on. The signature check only proves the request was signed by *some* configured organization's `webhook_secret`; it never proves that the organization owning that secret matches the organization of the repository the handler will subsequently mutate.

`GithubApp#verify_webhook_signature` itself only verifies the raw body against a secret, with no cross-check against the resolved repository: [3](#0-2) 

The Shipit engine explicitly supports installing multiple independent GitHub Apps for multiple GitHub organizations against a single Shipit instance: [4](#0-3) 
and each organization gets its own `webhook_secret` (e.g. `secrets_double_github_app.yml`, `OrgOne`/`OrgTwo` keys) — this is a legitimate deployment pattern, not a misuse of the engine.

Because `Shipit.github(organization: repository_owner)` merely looks up which secret to check, but the same field is not cryptographically bound to the rest of the payload as "the org this signature is scoped to," a party who legitimately administers **one** of the configured GitHub Apps (and thus legitimately knows/controls that org's webhook secret through normal GitHub App configuration) can craft and directly POST a payload to `/github/webhooks` with `repository.owner.login` set to their own org (so the signature check passes with their own secret) while setting `repository.full_name` to a *different* org's tracked repository. The downstream handler resolves the target `Stack`/`Repository`/`Commit` purely from `repository.full_name`, `sha`, `state`, etc., with no re-check that this repository belongs to the same organization whose secret validated the request.

### Impact Explanation
This breaks the intended trust binding "organization authenticated == repository being written," letting an operator of one legitimately-configured GitHub App organization inject forged webhook events (`status`, `push`, `check_suite`, `pull_request`, etc.) that are attributed to and acted on for a **different** organization's stacks/repositories tracked by the same shipit instance. Depending on the handler, this can: mark arbitrary commits as having passing CI status (`status_handler.rb`) enabling unauthorized deploys once combined with the deploy trigger logic, trigger `GithubSyncJob` for another org's repo/branch, or manipulate pull-request-based review stacks belonging to another org — an authorization/trust escalation across repository boundaries, consistent with the "cross-repository writes / unauthorized deploy" impact tier.

### Likelihood Explanation
This requires the attacker to already legitimately control one configured GitHub App/org in a multi-org Shipit deployment (i.e., they possess a legitimate webhook secret for their own org, which is an ordinary, documented configuration — not "requiring webhook_secret" theft of someone else's secret). Given that, no further privilege is needed: the endpoint is publicly reachable and the mismatch between "verifying org" and "target repository" is a direct, unconditional code path with no exploit precondition beyond normal multi-org operation.

### Recommendation
After resolving `repository_owner` and verifying the signature, additionally verify that the `Repository`/`Stack` resolved for the event actually belongs to the same GitHub organization/app whose secret validated the signature (e.g., compare `repository.full_name`'s owner segment against `repository_owner`, and/or scope handler lookups by the verified organization) before dispatching to `Shipit::Webhooks.for_event(event)`.

### Proof of Concept
1. Deploy Shipit with two GitHub Apps configured, `OrgA` and `OrgB`, each tracking their own stacks (per `docs/setup.md` multi-org instructions).
2. As the legitimate administrator/owner of `OrgA`'s GitHub App (who knows `OrgA`'s `webhook_secret` from GitHub App settings), craft a `status` (or `push`) event JSON body with:
   - `repository.owner.login = "OrgA"` (so `repository_owner` resolves to `OrgA` and the HMAC computed with `OrgA`'s secret validates)
   - `repository.full_name = "OrgB/some-tracked-repo"`, `sha`, `state`, `target_url` pointing at a real commit tracked under an `OrgB` stack.
3. Sign the body with `OrgA`'s webhook secret using `sha1=HMAC-SHA1(OrgA_secret, body)` and POST it to `/github/webhooks` with `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `verify_signature` passes (using `OrgA`'s secret), and `Shipit::Webhooks.for_event('status')` handlers run against `OrgB`'s repository/commit using only `repository.full_name` from the body, creating/altering a `Status` for a commit that belongs to a different organization than the one that authenticated the request.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
