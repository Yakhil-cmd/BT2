### Title
Malicious swap route can drain arbitrary wallet tokens under the caller’s authorization - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
`swap_collateral` and the other controller strategy paths accept attacker-controlled `swap` bytes and invoke the configured router without restricting route-internal contract calls or enforcing that the caller’s authorization contains only the expected token movement. [1](#0-0)  A malicious route can therefore place contract code beneath the caller’s `require_auth` tree and execute an otherwise unrelated `token.transfer(victim, attacker, amount)` if the victim submits the simulated authorization tree. [2](#0-1) 

### Finding Description
The controller snapshots balances, authorizes only the router’s exact input transfer, and calls `SwapAggregatorClient::execute_strategy` with the user-supplied `swap` payload. [3](#0-2)  Those measures bound the controller’s own input grant, but they do not prevent route-selected contracts from adding another invocation that requires the same user as its authorizer. [4](#0-3) 

The repository’s regression test models this exact flow: a router transfers the expected input, invokes the payload-selected hop pool, and pays a fair output. [5](#0-4)  The attacker-controlled hop then calls `token.transfer(victim, attacker, amount)` on a token completely unrelated to the lending position. [6](#0-5)  Simulation records that theft as a child of the victim’s `swap_collateral` authorization, and the recorded transaction both steals the victim’s wallet balance and deposits the expected swap output. [7](#0-6) 

This is authorization-scope confusion rather than a bad price or route-quality issue: the router can return a valid or even generous output while arbitrary unrelated wallet assets are transferred inside the signed invocation tree. [8](#0-7) 

### Impact Explanation
A malicious route can steal any token held by the victim, including assets not listed by or deposited into the protocol, up to the amount encoded in the malicious child transfer. [9](#0-8)  The demonstrated loss drains the victim’s entire `WALLET_BALANCE` while the protocol-level swap still succeeds normally. [10](#0-9)  Because successful execution depends only on the victim submitting the authorization tree produced for the malicious transaction, the route payload can be delivered through a malicious frontend, quote service, transaction builder, or phishing flow. [2](#0-1) 

### Likelihood Explanation
Any ordinary user can call `swap_collateral` for their own account and provide arbitrary `swap` bytes; the controller does not decode, simulate, or constrain the route’s downstream contract graph before invoking it. [1](#0-0)  The router likewise uses pool and token addresses selected by its payload rather than enforcing a venue allowlist. [11](#0-10)  The exploit does require the victim to submit a signed authorization tree containing the malicious child transfer, so wallet visibility and client validation materially affect practical exploitability. [12](#0-11) 

### Recommendation
Treat the swap payload as untrusted executable routing data and prevent route code from becoming a child of the user’s lending authorization where possible. [13](#0-12)  At minimum, constrain execution to governance-approved venue implementations rather than payload-selected contract addresses, and have clients simulate and reject authorization trees containing any invocation other than the expected controller input transfer. [2](#0-1)  Prefer a venue allowlist or immutable venue registry in the router over opaque bytes because payload-level address selection is the mechanism that lets attacker code request the victim’s token authorization. [14](#0-13) 

### Proof of Concept
1. Deploy an attacker-controlled contract whose route entrypoint calls `token.transfer(victim, attacker, victim_wallet_balance)` on an arbitrary unrelated token. [15](#0-14) 
2. Craft `swap` bytes that direct the configured router through that contract while still paying a fair `token_out` amount to the controller. [9](#0-8) 
3. Have the victim invoke `swap_collateral(victim, account_id, current_asset, amount, new_asset, swap)`. [1](#0-0) 
4. During simulation, Soroban records the rogue token transfer as a child of the victim’s root `swap_collateral` authorization rather than as a separate top-level transfer. [16](#0-15) 
5. If the victim signs that recorded tree, the unrelated wallet token is fully transferred to the attacker while the protocol swap succeeds. [8](#0-7)

    pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        sender.require_auth();
        let route = RoutedSwap::from_xdr(&env, &swap_xdr).expect("route must decode");
        let router = env.current_contract_address();
        token::Client::new(&env, &route.token_in).transfer(&sender, &router, &total_in);
        let _: Val = env.invoke_contract(&route.hop_pool, &symbol_short!("swap"), vec![&env]);
        token::Client::new(&env, &route.token_out).transfer(&router, &sender, &route.min_out);
        route.min_out
    }

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
