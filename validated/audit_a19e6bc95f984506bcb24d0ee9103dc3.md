### Title
Attacker-controlled route venue injects arbitrary token-transfer authorizations into the caller's signed auth tree, draining the caller's wallet - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The CVE is a command-injection class: a user-influenced parameter (`ssh_scp_new`'s path argument) is concatenated into a command executed on a remote host. The analog here is the `swap` route bytes accepted by the controller's strategy verbs. The controller forwards them verbatim to the configured router, which calls whatever `pool`/`token` addresses the route names (`invoke_contract` per hop, no venue allowlist). Code in that attacker-named contract runs below the caller's `require_auth` frame, and any `token.transfer(caller, …)` it performs is recorded by simulation as a child of the caller's authorization entry. If the caller signs the simulated tree — which wallets routinely do — the injected transfer executes. This is arbitrary command (auth invocation) injection through a user-influenced argument, proven by an in-repo test.

### Finding Description
`swap_tokens` forwards the caller-supplied `StrategySwap` bytes to `router.execute_strategy(controller, amount_in, swap)` after granting the router one exact input transfer (`swap.rs:34-38`). The route payload names the per-hop `pool` contract; `dispatch_hop` invokes it (`contracts/swap-aggregator/src/venues/mod.rs:34-40`) and the router keeps no allowlist of hop addresses. The caller (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, or direct `execute_strategy`) authorizes the top-level call; Soroban simulation runs in recording mode, so any `require_auth` issued by route-selected code — e.g. `token::Client::transfer(victim, attacker, full_wallet_balance)` inside a rogue hop pool — is attached as a sub-invocation of the caller's auth entry. The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates exactly this: a `RogueHopPool.swap` steals `WALLET_BALANCE` of an unlisted token from Alice, simulation records the theft under Alice's `swap_collateral` entry, and after she signs the recorded tree her balance is 0 and the attacker holds the funds — while the swap itself still returns a fair output and passes `NoSwapOutput`/risk gates. The threat model acknowledges the same: "a route can put third-party code on the call stack below the caller's authorization… the loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" (`docs/explanation/threat-model.md:154-165`).

### Impact Explanation
Theft of user funds. The injected transfer is not limited to the routed `amount_in`; it can move any token balance the signing caller holds, in any token contract, for any amount, to an arbitrary recipient. A malicious route served by a compromised or hostile quote/route provider (the analog of the attacker influencing `ssh_scp_new`'s third parameter) converts a routine `swap_collateral` into a full wallet drain.

### Likelihood Explanation
Reachable by any unprivileged address that can get a victim to submit its route bytes through `swap_collateral`/`swap_debt`/`multiply`/`repay_debt_with_collateral` or `execute_strategy`. The only attacker requirements are deploying one contract that performs a `transfer` inside its venue entrypoint and convincing the victim to use the poisoned route — the victim's own signature authorizes the injected child. Simulation does not flag it: recording mode deliberately records the rogue transfer under the caller's entry, so the signed envelope looks like one ordinary swap with extra auth children that clients that don't decode the tree will sign. Likelihood is bounded by social/UI delivery of the route, not by any on-chain check, which is why severity is Medium-to-High rather than critical.

### Recommendation
Constrain the authorization surface at the contract layer rather than relying on clients decoding auth trees: in the controller's strategy paths, have the router enumerate venue/pool addresses or restrict invocations to venues/pools registered in an allowlist, or have the controller itself invoke hops so route-selected code never runs beneath the caller's `require_auth` frame. Short of that, the router should reject routes whose hop pool addresses are not drawn from a configured registry, so third-party code cannot appear below the caller's authorization at all.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` (in-repo): `UnlistedPoolRouter` mimics the router's hop invocation; `RogueHopPool` is an attacker-deployed "pool" whose `swap` calls `token.transfer(alice → attacker, WALLET_BALANCE)` on an unrelated wallet token. Calling `ctrl.swap_collateral(alice, account_id, usdc, SWAP_IN_USDC, eth, route)` in recording mode produces a recorded auth tree where the stolen transfer is a sub-invocation of Alice's `swap_collateral` entry (`recorded == [(alice, poisoned_root)]` asserted at lines 206-222), Alice's wallet balance becomes 0, the attacker holds `WALLET_BALANCE`, and the swap still delivers its declared `min_out` — showing the injected command executes inside a fully valid, risk-passing call.
