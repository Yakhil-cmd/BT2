The closest structural analog in this codebase is `pallet-insecure-randomness-collective-flip`, which derives randomness from the last 81 parent block hashes [1](#0-0) , and is consumed by `pallet-lottery`'s `generate_random_number`/`choose_ticket` to pick a payout winner [2](#0-1) . This mirrors the EOS incident's root cause (predictable, previous-block-derived RNG used to determine a monetary payout), but it does not qualify as a reportable finding here for two independent reasons:

1. **Explicitly disclosed, not a hidden defect.** The pallet's own docs and README state in the title "DO NOT USE IN PRODUCTION" and explicitly warn that "Hashing the result of this function will remove any low-influence properties... entirely manipulatable by the author of the parent block" [3](#0-2) [4](#0-3) . `pallet-lottery` itself carries a `TODO: deal with randomness freshness` note referencing the exact concern (`substrate/frame/lottery/src/lib.rs:515-516`) linking to a tracked upstream issue [5](#0-4) . A known, clearly-labeled limitation is not an unreported vulnerability.

2. **No live production wiring.** The only place in the codebase where `pallet-lottery` and `pallet-insecure-randomness-collective-flip` are wired together is `substrate/bin/node/runtime/src/lib.rs`, which is the generic Substrate reference/example node runtime, not a deployed Parity/Snowbridge chain with an active bounty program [6](#0-5) . This is exactly the "reference-runtime reproduction alone is not bounty eligibility" and "config-only/dependency-only" exclusion called out in the scan instructions.

No other real, permitted entry point (signed extrinsic, XCM, contracts, bridges) reachable on a live in-scope chain reproduces the EOS-style predictable-randomness theft pattern.

	/// Randomly choose a winning ticket from among the total number of tickets.
	/// Returns `None` if there are no tickets.
	fn choose_ticket(total: u32) -> Option<u32> {
		if total == 0 {
			return None;
		}
		let mut random_number = Self::generate_random_number(0);

		// Best effort attempt to remove bias from modulus operator.
		for i in 1..T::MaxGenerateRandom::get() {
			if random_number < u32::MAX - u32::MAX % total {
				break;
			}

			random_number = Self::generate_random_number(i);
		}

		Some(random_number % total)
	}

	/// Generate a random number from a given seed.
	/// Note that there is potential bias introduced by using modulus operator.
	/// You should call this function with different seed values until the random
	/// number lies within `u32::MAX - u32::MAX % n`.
	/// TODO: deal with randomness freshness
	/// https://github.com/paritytech/substrate/issues/8311
	fn generate_random_number(seed: u32) -> u32 {
		let (random_seed, _) = T::Randomness::random(&(T::PalletId::get(), seed).encode());
		let random_number = <u32>::decode(&mut random_seed.as_ref())
			.expect("secure hashes should always be bigger than u32; qed");
		random_number
