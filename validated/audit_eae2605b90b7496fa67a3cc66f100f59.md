### Title
Private assets sent to an Autonomous Agent address are permanently unspendable and irrecoverable - (File: [aa_composer.js](), [storage.js]())

### Summary
The report's bug class — a payable/receiving code path with no corresponding withdraw mechanism, permanently locking funds — has a concrete analog in ocore's Autonomous Agent (AA) subsystem. A private (non-base) asset payment sent to an AA address can never be recognized as AA balance, never triggers the AA, and can never be spent by anyone, resulting in permanently locked funds.

### Finding Description
AAs execute in response to payment `trigger`s built by `getTrigger()`, which only reads outputs from `message.payload` when `message.app === 'payment'`: [1](#0-0) 

For private payments, however, the public unit never carries the plaintext `payload` — only `payload_hash` with `payload_location: "none"`; the actual amounts/addresses are revealed only to the parties on the private chain via device messaging (see `private_payment.js`'s `validateAndSavePrivatePaymentChain`, `network.js`'s `handleOnlinePrivatePayment`). Since an AA is a program with no private key and no device address, it can never be a party to that off-DAG private delivery, so `getTrigger()` will never see these outputs and the AA will never fire in response to them.

Separately, even if the private payload were somehow known, the AA balance accounting explicitly excludes private outputs. When an AA's initial balance is computed from confirmed outputs, the query filters `AND (is_private=0 OR is_private IS NULL)`: [2](#0-1) 

This means a private output landing at an AA address can never be counted in `aa_balances`, so the AA's oscript logic (`balance[asset]`) will never reflect it and can never construct a spending message for it.

Nothing in unit/payment validation prevents a normal user from sending such a payment. `validatePayment()`/`validatePaymentInputsAndOutputs()` validate private payments generically for any recipient address (no `checkNotAAs`-style restriction is applied to the payment destination for private assets): [3](#0-2) [4](#0-3) 

Asset-definition validation confirms indivisible, transferable private assets are a legitimate configuration (only divisible private assets must be non-transferable/auto-destroy): [5](#0-4) 

Because the AA address has no private key, it can never generate the correct spend proof required to move the private output out again (`validatePrivatePayment`'s spend-proof check keyed to the owning address) — so once such a payment is confirmed, nobody, including the sender, can ever spend it further: the AA cannot (it never learns of or credits the funds), and the original sender cannot (ownership has legitimately transferred to the AA address).

### Impact Explanation
Funds (any indivisible, transferable private asset — e.g. a private token) sent to an AA address are permanently and irrecoverably locked: they are excluded from `aa_balances` by design, never appear in any AA trigger, and can never be spent since the AA holds no private key and no device channel to receive the private payload needed to construct a spend. This is a direct, unmitigated fund-freezing condition analogous to the reported "payable function with no withdraw" issue, except here the loss is total and permanent rather than merely inconvenient.

### Likelihood Explanation
Likelihood is user-error driven rather than requiring a malicious actor: any unprivileged wallet user or dApp UI that lets someone pay an AA with a private (indivisible, transferable) asset — a completely valid protocol configuration — will trigger this. There is no client-side or protocol-side validation rejecting private payments to AA addresses (`checkAAOutputs` in `aa_addresses.js` only checks bounce-fee sufficiency generically, not asset privacy), so the condition is straightforward to hit unintentionally, and cannot be recovered from after the fact.

### Recommendation
- Add explicit validation (mirroring `checkNotAAs`) that rejects private-asset payment outputs whose destination is a known AA address, at the point private payments are validated/saved (`validation.js` `validatePayment`, `private_payment.js`) and in wallet-side pre-flight checks (`aa_addresses.checkAAOutputs`).
- Alternatively/additionally, expose a recovery path: if a private output is ever confirmed at an AA address, allow a governance/definer-level mechanism or protocol-level rule to reclaim/refund it, consistent with the judge's suggestion in the referenced report ("adding a way to retrieve locked funds would mitigate the issue").

### Proof of Concept
1. Create a private, indivisible, transferable asset (`is_private: true`, `fixed_denominations: true`, `is_transferrable: true`) as allowed by `validateAssetDefinition` (`validation.js:2794-2799`).
2. From a normal wallet, compose and send a private payment of this asset with an output address equal to a deployed AA's address (this passes `validatePayment`/`validatePaymentInputsAndOutputs`, which impose no AA-destination restriction for private payments).
3. Observe that:
   - `aa_composer.getTrigger()` never includes this output because the unit's `payment` message has no inline `payload` for a private payment (`aa_composer.js:379-393`).
   - `storage.js`'s AA-balance query explicitly excludes `is_private` outputs (`storage.js:954-962`), so `aa_balances` for the AA address never reflects the received amount.
4. Confirm no oscript logic, getter, or wallet operation can ever surface or spend this output — it remains permanently stuck at the AA address.
