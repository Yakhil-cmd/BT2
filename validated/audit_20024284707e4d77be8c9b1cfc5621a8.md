This confirms the vulnerability: `CCMenuController` overrides the `stack` method to bypass the base class's stack-scoping logic entirely.

In `app/controllers/shipit/api/base_controller.rb:74-80`, the base `stack` method is properly scoped: `stacks` restricts to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `stack` calls `stacks.from_param!(params[:stack_id])` — meaning a stack-scoped `ApiClient` can only ever resolve to its own stack.

But `app/controllers/shipit/api/ccmenu_controller.rb:29-31` overrides this with `Stack.from_param!(params[:stack_id])` directly — completely ignoring `current_api_client.stack_id`. The `require_permission :read, :stack` before_action only checks that the permission string `read:stack` is in the client's `permissions` list via `ApiClient#check_permissions!` (`app/models/shipit/api_client.rb:38-45`), it never checks which stack the token is scoped to.

### Title
Stack-scoped ApiClient token bypasses its stack binding in CCMenuController - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
An `ApiClient` token created with a `stack_id` (e.g. via the CCMenu "create read-only client" flow) is intended to only ever read the one stack it was scoped to. `CCMenuController` overrides the inherited `stack` resolution method and drops that scoping check, so the token can be used to read deploy status for *any* stack in the installation, not just the one it was issued for.

### Finding Description
`Shipit::Api::BaseController#stack` (`app/controllers/shipit/api/base_controller.rb:74-80`) enforces the binding "stack a token authorizes == stack a token touches" by restricting the queryable relation to `Stack.where(id: current_api_client.stack_id)` whenever the authenticating `ApiClient` has a non-null `stack_id`.

`Shipit::Api::CCMenuController` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) redefines `stack` as:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
This resolves `params[:stack_id]` against the full `Stack` table with no reference to `current_api_client.stack_id`, breaking the binding entirely. `require_permission :read, :stack` (line 6) only calls `ApiClient#check_permissions!` (`app/models/shipit/api_client.rb:38-45`), which checks the string `"read:stack"` is present in `permissions` — it has no awareness of which stack the token belongs to.

`CCMenuUrlController#client` (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`) creates exactly this kind of scoped client: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` combined with the stack context of that request — and the CCMenu URL feature is explicitly designed to hand out a long-lived token+URL pair scoped to a single stack for use in external CI dashboard tools (which is why the token appears in a URL query string, a comparatively exposed channel).

### Impact Explanation
A leaked CCMenu URL/token — scoped by design to only report on one stack — can be replayed against `GET /api/:owner/:repo/:stack/ccmenu.xml?token=...` with any other `stack_id` substituted in the path, and the attacker will get back deploy status, last build result, and commit information for a stack the token was never authorized for. This is an unauthorized read of stack state across the authorization boundary the token was scoped to, matching the "unauthenticated read of stack state" class of impact (the token is valid, but the read is unauthorized for that particular stack).

### Likelihood Explanation
Any holder of a stack-scoped CCMenu token (which is explicitly designed to be embedded in URLs and shared with external CI status tools) can trivially edit the `stack_id` segment of the URL to target a different stack in the same Shipit install. No other credentials or privileges are required beyond possessing one valid, narrowly-scoped token.

### Recommendation
Have `CCMenuController#stack` reuse the inherited, properly scoped `stacks`/`stack` logic from `BaseController` (or explicitly check `current_api_client.stack_id.nil? || current_api_client.stack_id == resolved_stack.id`) instead of querying `Stack.from_param!` directly against the full `Stack` table.

### Proof of Concept
1. As user Alice, request a CCMenu URL for `stack-A` via `CCMenuUrlController#fetch`; this creates an `ApiClient` with `permissions: ['read:stack']` and `stack_id = stack-A.id`, and returns a URL like `.../api/owner/repoA/stack-A/ccmenu.xml?token=<TOKEN>`.
2. Take `<TOKEN>` and request `.../api/owner/repoB/stack-B/ccmenu.xml?token=<TOKEN>` (any other stack in the same installation).
3. `CCMenuController#authenticate_api_client` successfully authenticates the token; `require_permission :read, :stack` passes because `permissions` contains `read:stack`; `CCMenuController#stack` resolves `stack-B` directly via `Stack.from_param!`, ignoring that the token's `stack_id` is `stack-A.id`.
4. The response renders `stack-B`'s latest deploy status/build info via `shipit/ccmenu/project`, even though the token was only ever authorized (and intended) to read `stack-A`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
