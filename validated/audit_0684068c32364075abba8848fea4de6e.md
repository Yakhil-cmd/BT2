### Title
Cross-organization `Team` hijack via unverified `organization` in `MembershipHandler` grants `Shipit.github_teams` membership - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` solely by the attacker-controlled `params.team.id` (GitHub team ID), and only checks/sets `organization` when the `Team` row is newly created. Once a privileged `Team` (one whose `id` is in `Shipit.github_teams`) already exists in the database, a `membership` webhook whose signature was verified against a *different, attacker-owned* organization's `webhook_secret` can still add an arbitrary (attacker's real, session-bound) `User` to that privileged `Team`, flipping `Shipit::User#authorized?` to `true`.

### Finding Description
The claimed binding is: `organization that signed the webhook (verified via Shipit.github(organization: repository_owner).verify_webhook_signature)` == `organization that owns the Team referenced by params.team.id`. This binding is never checked.

- `WebhooksController#verify_signature` picks the GitHub App config to check the HMAC signature against using `repository_owner`, itself read straight from the attacker-controlled payload (`params.dig('repository','owner','login') || params.dig('organization','login')`): `app/controllers/shipit/webhooks_controller.rb:24-49,59-62`. This only proves the payload was signed by *some* configured org's `webhook_secret` — the one the attacker owns/controls if Shipit is configured for multiple GitHub orgs (`lib/shipit.rb:170-181,190-194`, documented in `docs/setup.md` "Using Multiple Github Applications").
- `MembershipHandler#process` and `#find_or_create_team!` then look up/create the `Team` purely by `params.team.id` (a GitHub-side numeric ID that is fully attacker-supplied JSON, not re-validated against GitHub): `app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`. The `organization:` field from the payload is only assigned inside the `find_or_create_by!` block, i.e. **only when the `Team` doesn't already exist**. If a `Team` with that `github_id` already exists (e.g., a legitimate privileged team belonging to org "victim-org" was already synced from a real webhook or `Team.find_or_create_by_handle`), the block never runs, so the payload's `organization.login` is silently ignored and never compared to `team.organization`.
- `team.add_member(member)` (`app/models/shipit/team.rb:41-43`) then unconditionally creates a `Membership` for `member = User.find_or_create_by_login!(params.member.login)` — the attacker names their own real GitHub login, which resolves to their own, correctly OAuth-bound `User` row.
- `Shipit::User#authorized?` (`app/models/shipit/user.rb:80-82`) checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` against exactly these `Membership`/`Team` rows, with no re-validation that the membership was ever confirmed by the real owning organization.

Attack flow: attacker's own repository/org ("attacker-org") is a legitimately configured Shipit tenant with its own real `webhook_secret`. Attacker POSTs to `POST /webhooks` with header `X-Github-Event: membership`, a body `{"action":"added","team":{"id":<github_id of privileged Team>,...},"organization":{"login":"attacker-org"},"member":{"login":"<attacker's real login>"},"repository":{"owner":{"login":"attacker-org"}}}`, signed with attacker-org's real `webhook_secret` (which the attacker legitimately possesses as that org's admin). `verify_signature` passes because it only checks against "attacker-org"'s config. `MembershipHandler` finds the existing privileged `Team` by `github_id` and adds the attacker's `User` as a member, with no check that "attacker-org" is the organization that owns that `Team`.

None of the existing guards catch this: `verify_signature` validates *a* valid signature exists, not that the signing org matches the referenced team's org; the `ExplicitParameters` schema in `MembershipHandler` only enforces types/presence, not cross-field integrity; `drop_unhandled_event` is irrelevant (membership is a handled event); `User#authorized?` trusts `Membership` rows unconditionally.

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization (High/Critical per the given severity table): the attacker's own, genuinely-authenticated session (bound via `session[:user_id]` to their real GitHub identity) becomes `authorized?` for stacks gated by a privileged team, enabling deploys/merges/rollbacks they should not be able to trigger. The attack is repeatable against any privileged `Team` whose `github_id` the attacker can guess or observe (GitHub team IDs are visible via public API/UI), and works cross-tenant — one onboarded org's webhook credentials can corrupt another onboarded org's authorization data. Blast radius is bounded to Shipit installations configured with multiple GitHub organizations (the multi-org `secrets.github` schema) where at least one onboarded org is less trusted than another whose teams gate authorization.

### Likelihood Explanation
Requires: (1) Shipit configured in multi-org mode (`github_default_organization` non-nil, i.e., more than one org's config under `secrets.github`), (2) attacker legitimately controls one of those onboarded orgs' webhook delivery (owns/administers that GitHub org/app installation, giving them its real `webhook_secret`), and (3) knowledge of the target privileged `Team`'s GitHub `id` (easily discoverable) and that the `Team` row already exists in Shipit's DB (true for any team already used for authorization). No Shipit secrets, session, or API token are needed beyond what the attacker already legitimately has for their own org, and the attacker's own `User` row is created through the normal OAuth flow. This is straightforward to execute with a single crafted HTTP POST and is fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, always validate that `params.organization.login.downcase == team.organization` for existing teams (reject/raise otherwise), not only when creating a new record. Additionally, cross-check that `repository_owner`/the organization used for signature verification in `WebhooksController#verify_signature` matches `params.organization.login` for membership events, and that it matches the `Team#organization` before calling `add_member`/`members.delete`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":membership from one org cannot add a member to another org's existing team" do
  victim_team = shipit_teams(:shopify_developers) # organization: "shopify", github_id: X
  attacker_org_config # ensure Shipit multi-org secrets include "attacker-org" with its own webhook_secret

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker_real_login' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, payload)
  @request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { Membership.where(team: victim_team).count } do
    post :create, body: payload, as: :json
    assert_response :ok # or :unprocessable_entity after fix
  end

  refute victim_team.members.exists?(login: 'attacker_real_login')
end
```
Before the fix, the assertion `assert_no_difference` fails: a `Membership` row is created binding the attacker's real `User` to `victim_team`, and `victim_team.members.exists?(login: 'attacker_real_login')` becomes true, causing `Shipit::User#authorized?` to return `true` for that user's genuine session.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end
