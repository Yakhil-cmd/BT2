### Title
CCMenu API endpoint ignores `ApiClient` stack scoping, letting a stack-scoped token read another stack's build/deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` tokens can be scoped to a single `stack_id`, and `Shipit::Api::BaseController` is supposed to enforce that scoping on every request. `Api::CCMenuController` overrides the `stack` lookup and bypasses that enforcement, so a token that is only authorized (and was only ever handed out) for one stack can be replayed with a different `stack_id` in the URL to read another stack's CCMenu status. This is the same class of bug as the CometBFT `ProcessProposal` issue: a verification step exists (`stacks`/`stack` scoping in the base controller) but the concrete code path that actually reads data (`CCMenuController#stack`) doesn't go through it, so the "stack a token authorizes" and "stack it touches" diverge.

### Finding Description
`Shipit::Api::BaseController` defines the scoping contract that every API controller is expected to use: [1](#0-0) 

`current_api_client.stack_id?` restricts `stacks` (and therefore `stack`) to the single stack the client was scoped to when created. This is exactly how a stack-scoped `ApiClient` is meant to work, as shown by the `here_come_the_walrus` fixture, which is scoped to the `shipit` stack with only `read:stack` permission: [2](#0-1) 

and is exercised in the stacks API test verifying that a stack-scoped client "will only see that one stack": [3](#0-2) 

`Api::CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely and resolves any `stack_id` param directly against all stacks: [4](#0-3) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string; it never checks *which* stack the token is bound to (`ApiClient#check_permissions!` is scope-name only): [5](#0-4) 

So the equality that should hold — `stack authorized by token` == `stack read by the request` — is broken specifically in this controller, because it recomputes `stack` from the raw `stack_id` param instead of delegating to `BaseController#stack` (which is scoped via `stacks`).

### Impact Explanation
Any holder of a valid `read:stack`-permission `ApiClient` token — even one deliberately scoped to a single, non-sensitive stack (e.g., handed out via the “CCMenu URL” feature, which is meant to expose only that one stack's build badge/status) — can supply a different `stack_id` in the `GET /api/stacks/:stack_id/ccmenu` request and receive that other stack's build status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, `webUrl`, etc.), including for stacks the client was never authorized to see. This is a cross-stack authorization bypass: it discloses task/deploy state of stacks outside the token's intended scope without further authentication, breaking the "stack a token authorizes vs. stack it touches" binding.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (the primary supported use case for the CCMenu feature, via `CCMenuUrlController#client`, which creates read-only tokens intended for a specific stack's CCMenu badge). Exploitation requires no privileged access beyond possessing one such token/URL (which are commonly embedded in CI dashboards, README badges, or CCMenu-compatible tools) and a single unauthenticated-relative-to-target GET request with a different `stack_id`.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. Create (or obtain) a stack-scoped, read-only `ApiClient` for stack A, e.g. via the "CCMenu URL" feature (`GET /ccmenu/*stack_id` → `CCMenuUrlController#fetch`), which mints a token scoped for that use case.
2. Using that token's `authentication_token` value, issue:
   `GET /api/stacks/<other-org>/<other-repo>/<other-env>/ccmenu?token=<token>`
   substituting `stack_id` for a *different* stack B that the token was never scoped/authorized for.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `current_api_client.stack_id` scoping enforced by `BaseController#stacks`), the request succeeds and returns stack B's CCMenu XML (build status, lock state, last build time), confirming cross-stack information disclosure with a token that should only have access to stack A.
