### Title
Unbounded ancestor-walk in TPS-fee calculation can stall stabilization processing - (File: `storage.js`, function `getFinalTps`)

### Summary
`storage.js`'s `getFinalTps(objUnitProps)` computes a unit's final TPS fee by walking backward through the DAG from the unit's main-chain position down to its `last_ball_mci`, using an unbounded `while (true)` traversal that accumulates a `visited` map and re-expands parent sets on every iteration. This is structurally the same pattern flagged in the referenced report: a loop whose cost grows with the "distance" between two points that are supposed to be close but can, under certain conditions, be far apart, and that runs on a path reachable by ordinary unit-posting activity (payments/commission accounting), executed once per unit at every MC stabilization event.

### Finding Description
`getFinalTps` starts from a stabilizing unit's properties and walks up through `parent_units`/`best_parent_unit` chains recorded in `assocStableUnits`, counting the unit itself plus every ancestor unit (and their `count_aa_responses`) whose `main_chain_index` is greater than `last_ball_mci`: [1](#0-0) 

The traversal has no hard cap on the number of iterations or number of ancestor units visited — it continues via `while (true)` until no new parent props remain: [2](#0-1) 

This function is invoked from the stabilization path (`updateTpsFees`, called from `writer.js`/`main_chain.js`) each time an MCI becomes stable, i.e., every unit posted to the DAG eventually triggers this computation once it is included and stabilized. The cost of the walk scales with `mci - last_ball_mci`, i.e., with the number of DAG units between a unit and the last stable ball it references. This is directly analogous to the `rewardRateLog` loop in the external report: a backward-walking accumulator loop whose size is a function of "how much history has accumulated since the last checkpoint," triggered by ordinary, unprivileged use of the protocol (posting units/payments), and executed on the hot path of confirming new state.

### Impact Explanation
If the number of DAG units between a unit's MCI and its `last_ball_mci` grows large (e.g., due to network congestion, a burst of low-priority units, or unit authors referencing an older-than-necessary stable last ball while remaining protocol-valid), `getFinalTps` must walk and re-count a correspondingly large ancestor set for every affected unit at stabilization time. Because this runs synchronously inside the stabilization/`markMcIndexStable` pipeline for every newly stabilized MCI, a sufficiently large backlog could make per-MCI stabilization processing (and therefore TPS-fee/commission accounting, which gates further unit validation) substantially more expensive, degrading the node's ability to keep confirming new units in a timely manner.

### Likelihood Explanation
Reaching this code path only requires ordinary, unprivileged activity: posting units/payments that get included in the DAG and eventually stabilize; no special privileges are needed. However, I could not fully verify (within the available static analysis) that the protocol enforces a tight upper bound on how far a valid unit's `last_ball_unit` may lag behind its own `main_chain_index` at the moment of composition — parent/last-ball selection logic (`parent_composer.js`) generally keeps last-ball close to the tip, and I was not able to confirm within this session whether an attacker can deliberately and repeatedly force a large sustained gap purely through legitimate unit composition, or whether existing consistency/parent-selection rules already bound this gap tightly enough to make the loop cost negligible in practice. This uncertainty lowers confidence in exploitability versus a purely theoretical concern.

### Recommendation
- Cap the number of ancestor units/iterations `getFinalTps` will traverse, and/or maintain an incrementally-updated running count/cache instead of recomputing the full backward walk on each call, similar to the report's suggested fix of removing the log-replay pattern in favor of an O(1) running accumulator.
- Add explicit protocol-level bounds (if not already present) on how far `last_ball_unit`'s MCI may lag behind a unit's expected MCI at validation time, to prevent large ancestor sets from accumulating between a unit and its referenced last ball.
- Add instrumentation/metrics around this traversal's iteration count in production to detect if real-world MCI/last-ball gaps ever approach sizes that would make this a practical bottleneck.

### Proof of Concept
Not independently verified end-to-end in this session (would require constructing a live DAG scenario with a deliberately large `mci - last_ball_mci` gap and measuring stabilization latency). The structural analog to the reported unbounded-loop pattern is demonstrated by the code itself: [2](#0-1) 
which shows the loop growing proportionally to the number of ancestor units between a unit and its last stable ball, mirroring the `rewardRateLog` accumulator loop in the original finding.
