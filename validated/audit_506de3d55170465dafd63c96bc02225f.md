### Title
Large high-utilization market can permanently freeze through accrual overflow - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary

A market whose scaled debt value approaches the `i128` ceiling can be driven into a state where every subsequent accrual panics before the borrow-index cap is reached. Because all market-mutating operations synchronize interest before applying the requested action, the affected market can no longer process withdrawals, repayments, liquidations, or index updates.

### Finding Description

`accrue_step` unconditionally converts scaled debt and supply into RAY-denominated values by calling `scaled_to_original` before calculating utilization and index growth [1](#0-0) . `scaled_to_original` multiplies the scaled balance by the current index and panics on `MathOverflow` when the resulting value does not fit `i128` [2](#0-1) . The borrow-index ceiling is applied only after this unscale succeeds, so it does not prevent the value overflow [3](#0-2) .

Every pool mutation loads the market and runs `global_sync` before the operation-specific mutation, meaning the overflow is encountered even by actions that would reduce the position [4](#0-3) . The integration test demonstrates the reachable state with a one-billion-token, 18-decimal market at 98% utilization: `update_indexes` eventually fails with `MathOverflow`, after which withdrawal and repayment attempts fail with the same error [5](#0-4) .

### Impact Explanation

Once the overflow condition is reached, the market is permanently frozen. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot reduce the debt, and governance cannot make the market operational through ordinary `update_indexes`, liquidation, or `recapitalize` calls because each path accrues first. This creates permanent freezing of user funds and can leave the protocol with unmanagable bad debt.

### Likelihood Explanation

The attack requires a very large borrow position and sustained high utilization. A single unprivileged attacker can create the condition by supplying the target asset, supplying sufficient collateral in another market, calling `borrow` for most of the target liquidity, and later invoking the public controller `update_indexes` path. The required amount is within the protocol's admitted 18-decimal cap domain, but the capital requirement and long accrual period make exploitation difficult.

### Recommendation

Accrual should saturate or bound the unscaled balance before calling `scaled_to_original`, or cap accrual using a checked simulation that never panics. In particular, `accrue_step` should clamp `borrowed_original` and `supplied_original` to a safe value for utilization/rate calculations, or `scaled_to_original` should provide a saturating accrual-specific variant. Recovery paths should also allow repayment, liquidation, bad-debt cleanup, and recapitalization without depending on the overflowing unscale.

### Proof of Concept

The existing deterministic test constructs the full attack path:

1. Create an 18-decimal market using the XLM interest-rate curve and permit sufficiently large supply/borrow caps.
2. Supply `1_000_000_000 * 10^18` native units.
3. Supply enough collateral and borrow 98% of the market through `borrow`.
4. Advance ledger time in yearly intervals while calling `update_indexes`.
5. `update_indexes` panics with `MathOverflow` before `borrow_index` reaches `MAX_BORROW_INDEX_RAY`; subsequent `withdraw` and `repay` calls panic identically [5](#0-4) .

    supply_index: Ray,

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
