### Title
Cross-organization forged `status` webhooks bypass repository-ownership binding, enabling unauthorized deploys of arbitrary commits - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound webhook only against the organization named in the attacker-controlled JSON body (`repository.owner.login` or `organization.login`), then hands the *entire unrestricted* payload to the matching `Shipit::Webhooks::Handlers::Handler`. For the `status` event, `Shipit::Webhooks::Handlers::StatusHandler#process` never re-checks that the commit whose status it is mutating actually belongs to the organization/repository that was authenticated — it looks the commit up globally by SHA across the whole instance. This breaks the same trust binding described in the Frankencoin report: a value that is used to select which credential to trust (`repository_owner` chosen for signature verification) diverges from the value that ultimately determines what gets mutated (an arbitrary commit `sha`, resolved with no repository scoping at all).

### Finding Description
The controller resolves which GitHub App/secret to check the signature against purely from the payload itself, before the payload has been validated in any way: [1](#0-0) [2](#0-1) 

Once the HMAC check against that organization's `webhook_secret` passes, the raw JSON is dispatched to all handlers for the event: [3](#0-2) 

Most handlers (push, pull_request) additionally scope by `repository.full_name` via `Handler#stacks`: [4](#0-3) 

However `StatusHandler` performs no such scoping whatsoever — it looks up commits by SHA across the *entire* database, independent of which repository/organization the payload claims to be from: [5](#0-4) 

The binding that should hold is:
`organization authenticated by verify_signature == repository (and therefore the commit set) that the handler is permitted to mutate`

Instead, `verify_signature` only proves "this HMAC matches organization X's `webhook_secret`" — it says nothing about which commit/stack the payload subsequently touches. Because a `status` payload's `sha` field is a completely independent value from `repository.owner.login`/`organization.login`, an operator (or anyone in control of one Shipit-registered organization's webhook, e.g. an org admin who legitimately possesses that org's `webhook_secret`) can sign an arbitrary payload with their own organization's secret while setting `sha` to any commit SHA that happens to exist for a *different, unrelated stack/repository* in the same Shipit instance (Shipit routinely hosts multiple organizations, as shown by the multi-org config in `test/dummy/config/secrets_double_github_app.yml`).

`create_status_from_github!` then writes a forged CI status onto that victim commit: [6](#0-5) 

which directly feeds `deployable?`: [7](#0-6) 

and `schedule_continuous_delivery`: [8](#0-7) 

### Impact Explanation
An attacker who controls a legitimate GitHub organization/webhook already onboarded to a shared, multi-tenant Shipit instance can forge a `status` event, sign it with their own organization's `webhook_secret`, and target any commit SHA belonging to a completely different organization's stack. Turning a failing/pending commit into `success` makes it `deployable?` and, combined with `continuous_deployment`, can trigger an **unauthorized deploy** of that commit in a victim stack the attacker has no legitimate access to — this is a cross-organization/cross-repository-write class impact matching the "unauthorized deploy" and "escalation" categories.

### Likelihood Explanation
Requires (a) a multi-organization Shipit deployment where the attacker legitimately owns/administers one of the configured organizations (and thus its `webhook_secret`), and (b) knowledge of a target commit SHA in another stack (SHAs are often visible in the Shipit UI/API, PR links, etc., which are not secret). No repository-write access, no `ApiClient` token, no privileged Shipit account, and no compromise of the target organization's own GitHub credentials is required — only crafting a raw HTTP POST directly to the shared `/webhooks` endpoint with a self-computed HMAC. This is a real, unprivileged-relative-to-the-victim-repository attack path, not a theoretical one.

### Recommendation
`StatusHandler` (and any other handler that does not already scope to `stacks`) must verify that the resolved `Commit`'s `stack.repository` matches `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, and `WebhooksController#verify_signature` should additionally assert that `repository.owner.login`/`organization.login` is consistent with the actual repository being targeted by the handler, rather than trusting it purely for secret selection.

### Proof of Concept
1. Stand up (or use) a Shipit instance configured with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as modeled in `test/dummy/config/secrets_double_github_app.yml`).
2. As the legitimate owner of `OrgA`, obtain `OrgA`'s `webhook_secret` (you configured it on your own GitHub App/webhook).
3. Find a commit SHA belonging to a stack under `OrgB` (e.g. from the public web UI).
4. Craft a JSON body: `{"sha": "<OrgB's commit sha>", "state": "success", "context": "ci", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/some-repo"}}`.
5. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)`.
6. POST directly to `/webhooks` with header `X-Github-Event: status`.
7. `verify_signature` succeeds (verified against `OrgA`), and `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) writes a forged `success` status onto the `OrgB` commit, with no code path ever comparing the payload's `repository` field to the commit's actual stack/repository.
