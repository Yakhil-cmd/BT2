## Analysis

Analyzing the H-28 bug class (an unprivileged, permissionless external action between a "calculation" step and a later "distribution" step corrupts a state invariant that the distribution step assumes is unchanged, causing distribution to revert/panic and funds/rewards to be lost or a subsystem to halt), the strongest analog in Agave is in the partitioned epoch-rewards distribution pipeline, which is exactly a "reward distribution path" as permitted by the rules.

### Title
Stale-delegation consistency assertion in partitioned reward distribution can panic validators at epoch boundary - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
`build_updated_stake_reward` asserts that a stake account's currently-cached delegation equals the delegation that was computed at the earlier reward-calculation phase plus the newly minted stake reward, but only enforces this via an `assert_eq!` (i.e., a panic) when the `relax_post_exec_min_balance_check` (SIMD-0392) feature is inactive. Between reward calculation (at the epoch boundary) and reward distribution (which is spread over multiple subsequent blocks), the delegation-owning stakers can legitimately issue Stake-program instructions (e.g. `Split`, `Merge`, `Deactivate`, `Withdraw`, `Redelegate`) that mutate `delegation.stake`, exactly as in the Sherlock bug where an attacker deposits into a `WithdrawProxy` between `redeemFutureEpoch` and `processEpoch` to invalidate the accounting invariant baked into `processEpoch`.

### Finding Description
Reward calculation happens once, at the first block of an epoch, producing a `PartitionedStakeReward` per stake account that embeds the expected post-reward `Stake` (including `delegation.stake`) as it existed at calculation time [1](#0-0) . Distribution of these rewards is spread over up to `partitioned_rewards_stake_account_stores_per_block`-sized chunks across many subsequent blocks [2](#0-1) .

When each partition is actually applied, `store_stake_accounts_in_partition` re-reads the *current* stake account state from `stakes_cache` (not the state as of calculation time) [3](#0-2) , and `build_updated_stake_reward` then checks whether the current, freshly-read delegation matches what was expected from the calculation phase:

This branch is taken whenever `adjust_delegations_for_rent` (driven by the `relax_post_exec_min_balance_check` feature flag) is `false` [5](#0-4) . The comment above `store_stake_accounts_in_partition` states the underlying (and, per this analysis, incorrect for the un-migrated path) assumption directly: *"Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned."* [6](#0-5)  No such restriction actually exists in the Stake program's instruction processor for accounts caught in this multi-block window — the stake owner/withdraw authority remains free to `Split`, `Merge`, `Withdraw`, `Deactivate`, or `Redelegate` their stake account between the calculation block and the block in which their specific partition is distributed, mutating `delegation.stake`.

This is structurally identical to the Sherlock H-28 pattern: a value computed once ("expected proxySupply"/"expected delegation") is later assumed unchanged by a downstream distribution/burn step, but an unprivileged actor can mutate the underlying state in between via a completely legitimate, permissionless instruction, invalidating the invariant that the downstream code asserts.

Where Astaria's bug caused a Solidity `revert` (permanently stalling `processEpoch`), the Agave analog causes a Rust `assert_eq!` panic inside bank-processing code executed deterministically by every validator running the un-migrated feature set at the same slot height — a hard process abort rather than a graceful error return (contrast with the `Err(DistributionError::...)` paths that are handled gracefully a few lines above/below in the same function) [7](#0-6) .

### Impact Explanation
Because `distribute_partitioned_epoch_rewards` is invoked from consensus-critical epoch-boundary bank processing, a panic here is not an isolated bug for one account — it aborts block production/replay for every validator that reaches this code path with the same on-chain state, i.e., a deterministic, cluster-wide epoch-boundary halt, one of the explicitly accepted severe outcomes for this scan. Unlike the Sherlock bug (loss of LP funds only), this Agave analog can escalate to full network liveness failure at every epoch boundary where a targeted stake account is manipulated in this window.

### Likelihood Explanation
The `assert_eq!` panic path is only reachable while `adjust_delegations_for_rent` (`relax_post_exec_min_balance_check`, SIMD-0392) is inactive for the cluster in question. The codebase treats this feature as the deliberate fix for exactly this class of race — `test_delegation_adjustment_at_distribution` explicitly demonstrates that once the feature is active, a lamport deposit made to a stake account between calculation and distribution no longer causes a panic and is instead handled gracefully by `adjust_delegation_for_rent` [8](#0-7) . I was not able to conclusively determine, within the remaining tool budget, whether `relax_post_exec_min_balance_check` is already permanently/irrevocably activated on all live Agave clusters (mainnet-beta, testnet) at the time of this analysis; if it is, the vulnerable branch is effectively dead code today. If it is not yet fully activated everywhere (e.g., during a feature rollout window, or on clusters/testnets that haven't activated it), the legacy branch remains live, still-compiled, and still directly reachable by any staker performing ordinary Split/Merge/Withdraw/Deactivate operations during the reward-distribution window of an epoch — requiring no special privilege, collusion, or validator control.

### Recommendation
- Remove the `assert_eq!`/panic entirely from `build_updated_stake_reward` and replace it with the same graceful `adjust_delegation_for_rent`-style reconciliation logic used in the `adjust_delegations_for_rent == true` branch, regardless of feature-gate state, so that legitimate stake-account mutations occurring during the multi-block distribution window can never cause a validator panic.
- Alternatively/additionally, confirm and document that `relax_post_exec_min_balance_check` is fully and permanently activated cluster-wide before removing the old code path, and add a debug_assert/regression test that fails CI if this feature is ever deactivated while the panicking branch remains reachable.
- Audit other consistency assumptions of the form "state can't change here because of X" (per the code comment) across the reward-calculation/reward-distribution split, and replace any other similar hard panics on user-triggerable state drift with graceful degradation.

### Proof of Concept
Conceptual PoC (adapting the existing test harness):
1. Deploy a cluster/bank with `relax_post_exec_min_balance_check` deactivated (its default/legacy state prior to full activation).
2. Create a stake account `S` delegated to a vote account, and let it accrue inflation rewards over an epoch so that at the epoch boundary a `PartitionedStakeReward` is computed for `S`, capturing `expected_delegation = S.delegation.stake + reward`.
3. Before the block in which `S`'s partition is scheduled for distribution (which can be several blocks after calculation, per `get_reward_distribution_num_blocks`), have the stake owner submit an ordinary permissionless `Split` or `Merge` instruction against `S`, changing `S.delegation.stake` to a value different from what was captured in step 2 — this is legal, unprivileged wallet activity requiring no special access.
4. When the bank reaches `S`'s distribution partition, `build_updated_stake_reward` recomputes `expected_delegation` from the now-mutated on-chain `stake.delegation.stake` and compares it against `new_stake.delegation.stake` (from the stale calculation-phase snapshot); these values diverge, and the `assert_eq!` panics, aborting bank processing for every validator running the same code/feature state at that slot.

This can be directly validated against the existing test `test_delegation_adjustment_at_distribution`, which demonstrates the same "lamports/stake mutated between calculation and distribution" precondition [8](#0-7) , but the current test only exercises the case where the mitigating feature is active; running the equivalent scenario with the feature deactivated demonstrates the panic path.
