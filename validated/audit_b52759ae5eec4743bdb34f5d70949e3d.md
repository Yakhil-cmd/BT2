## Title
Webhook Organisation-vs-Repository Confusion Allows Cross-Organization Forged Events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate a webhook against based on `repository.owner.login` read from the *unverified* JSON body, while every event `Handler` (used after the signature check passes) resolves the actual `Stack`/`Repository` to mutate using a *different* field of the same unverified body: `repository.full_name`. Because these two fields are never checked for consistency, an attacker who legitimately controls one organization's webhook secret can forge a signature that is valid for that organization while pointing the actual event payload at a completely different, unrelated repository/stack tracked by the same Shipit instance.

### Finding Description
`verify_signature` derives the signing identity purely from body content, not from anything cryptographically bound to it beforehand: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` config (and thus the `webhook_secret`) keyed only by `repository.owner.login`, and `verify_webhook_signature` just checks the HMAC of the whole raw body against that org's secret: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the same raw params to the event handlers: [4](#0-3) 

Every handler (`push`, `status`, `check_suite`, etc.) inherits `Handler#stacks`, which resolves the target `Stack` using a **different** JSON field, `repository.full_name`, completely independent of `repository.owner.login`: [5](#0-4) 

The engine explicitly supports multiple GitHub Apps/organizations with independent `webhook_secret` values in the same Shipit deployment, as shown by the multi-org test fixture: [6](#0-5) 

**Binding broken:** the organization whose secret authenticated the request (`repository.owner.login`) ≠ the repository/stack that the handler actually writes to (`repository.full_name`). Nothing ties these two fields together, and neither is covered by any mechanism stronger than "appears somewhere in the HMAC-signed raw body," so an attacker who legitimately knows *one* org's `webhook_secret` (e.g., because they administer their own GitHub App installation "OrgA" pointed at the shared Shipit endpoint) can freely choose the `full_name` field to target any other tracked stack.

### Impact Explanation
An attacker who is a legitimate GitHub App administrator for OrgA (and thus knows OrgA's `webhook_secret`, a normal, non-privileged position for someone managing their own org's GitHub App) can:
1. Build a `push`/`status` payload with `repository.owner.login = "OrgA"` (to pass signature verification against OrgA's known secret) but `repository.full_name = "OrgB/high-value-repo"` (a stack belonging to a different, unrelated organization tracked by the same Shipit instance).
2. Sign the raw body with OrgA's real `webhook_secret` and send it to `/webhooks`.
3. `verify_signature` succeeds because it only checks the body against OrgA's secret.
4. `PushHandler`/`StatusHandler` (via `Handler#stacks`/`#repository_name`) resolve and mutate `OrgB`'s stack — e.g. queuing a `GithubSyncJob` that calls `stack.commits.create_from_github!` for arbitrary attacker-chosen `expected_head_sha`, or flipping commit CI status used to gate deploys.

This is a cross-repository / cross-organization write inside Shipit driven entirely by a payload the attacker fully controls, satisfying the "cross-repository writes" / "unauthorized deploy" impact bar, since injected commits or manipulated commit statuses on a foreign stack can influence what gets deployed later by legitimate operators of that stack.

### Likelihood Explanation
Requires only that the attacker legitimately controls (or has been granted) a GitHub App installation for some organization also pointed at this Shipit instance's shared `/webhooks` endpoint — a normal, unprivileged position relative to any *other* organization's stacks — and that Shipit hosts multiple organizations/apps (an explicitly supported configuration per `test/dummy/config/secrets_double_github_app.yml`). No access to `GITHUB_TOKEN`, `api_clients_secret`, or the target org's own webhook secret is needed.

### Recommendation
Bind the two fields together before trusting either: `verify_signature` (or the handlers) should reject any event where `repository.owner.login` does not match the owner implied by `repository.full_name`, or better, key secret lookup and stack resolution off the same, single verified identifier so an attacker cannot supply divergent values for "who signed" versus "what gets written."

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>
Content-Type: application/json

{
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/high-value-repo"
  },
  "after": "<attacker_chosen_sha>",
  "ref": "refs/heads/master"
}
```
`repository_owner` resolves to `"OrgA"` → signature verified with OrgA's real secret → passes. `PushHandler` resolves the target via `payload.dig('repository','full_name')` = `"OrgB/high-value-repo"` → enqueues `GithubSyncJob` for OrgB's stack, using an attacker-controlled `expected_head_sha`, even though the request never carried anything signed by OrgB.     def verify_signature
```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end

    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class Handler
        class << self
          attr_reader :param_parser

          def params(&block)
            @param_parser = ExplicitParameters::Parameters.define(&block)
          end
        end

        def self.call(params)
          new(params).process
        end

        attr_reader :params, :payload

        def initialize(payload)
          @payload = payload
          @params = self.class.param_parser.parse!(payload)
        end

        def process
          raise NotImplementedError
        end

        private

        def stacks
          @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
        end

        def repository_name
          payload.dig('repository', 'full_name')
        end
      end
    end
  end
```
