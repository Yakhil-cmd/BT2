### Title
Webhook `status` events are authenticated by organization but applied to a commit `sha` with no repository binding, allowing cross-organization commit-status forgery - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification from `repository.owner.login` (falling back to `organization.login`) in the JSON body, but this is only used to pick the *signing key*, not to constrain which repository the event is allowed to affect. `StatusHandler`, which processes the `status` webhook event, never checks the payload's `repository` field at all — it looks up commits purely `by sha`. This breaks the same class of binding described in the external report: a field that is used to authenticate the request (organization owning the payload's `repository`) is disjoint from the field the code actually acts on (`sha`, unscoped by repository/organization).

### Finding Description
`verify_signature` derives the organization used to fetch the correct `github_app`/`webhook_secret` from the payload itself: [1](#0-0) [2](#0-1) 

Every other handler in the engine derives the target repository from `payload.dig('repository', 'full_name')` via the shared base class and scopes queries to that repository's stacks: [3](#0-2) 

`StatusHandler`, however, does not call `stacks`/`repository_name` at all. It resolves the affected object purely from `sha`, which is attacker-controlled data inside the same payload whose *outer* `repository.owner.login` was used only to select the verifying secret: [4](#0-3) 

Because `Commit.where(sha: params.sha)` is global (not scoped by `stack`/`repository`), the equality that should hold — "organization whose secret authenticated the request" == "repository/commit that the event is allowed to mutate" — is not enforced anywhere in this handler. Any organization onboarded into a multi-tenant Shipit instance (each org configured with its own `webhook_secret`, as reflected by `Repository#github_app` calling `Shipit.github(organization: owner)`) can produce a validly-signed `status` payload for its *own* repository while setting an arbitrary `sha` value that actually belongs to a commit tracked under a completely different organization's repository: [5](#0-4) 

### Impact Explanation
An attacker who legitimately administers one GitHub organization already onboarded to a multi-tenant Shipit deployment (and therefore can produce a signature GitHub itself would send, or otherwise control that org's configured webhook secret/delivery) can forge `status` webhook payloads that pass `verify_signature` for their own org, yet target the `sha` of a commit belonging to a different, unrelated organization/repository tracked by the same Shipit instance. `StatusHandler#process` will happily call `commit.create_status_from_github!(params)` for that foreign commit, letting the attacker inject arbitrary CI/commit status entries (`state`, `context`, `target_url`, `description`) onto a repository they have no real GitHub permissions on. Since commit/CI status is one of the standard signals Shipit uses to determine whether a commit is deployable, this allows an unprivileged-with-respect-to-victim-repo attacker to make an unreviewed/unvetted commit in another organization appear "green"/deployable, enabling an unauthorized deploy of that commit by a legitimate operator relying on the forged status — satisfying the Critical "unauthorized deploy" impact category.

### Likelihood Explanation
Requires the attacker to control or administer at least one organization already configured in this Shipit installation (a normal, unprivileged tenant relationship, not a privileged Shipit account) and to be able to produce a request that passes `verify_signature` for that organization (e.g., a real webhook delivery from their own GitHub org/repo, replayed or crafted with modified body fields while keeping a route to a validly-signed request for their org). No access to the victim's repository, GitHub App private key, or Shipit session is needed. This is a straightforward, code-verifiable logic gap (missing repository scoping in `StatusHandler`), not a theoretical or best-practice concern.

### Recommendation
In `StatusHandler#process`, restrict the `Commit` lookup to commits belonging to the same repository referenced in the payload (i.e., join through `stacks`/`repository` using `repository_name`, mirroring how the base `Handler#stacks` method scopes other handlers), rather than matching on `sha` alone across the entire installation.

### Proof of Concept
1. Attacker onboards/administers `attacker-org` in the multi-tenant Shipit instance, giving them a webhook whose deliveries are signed with `attacker-org`'s configured `webhook_secret`.
2. Attacker crafts (or replays with a modified body while preserving a valid signature path) a `status` event:
```json
{
  "sha": "<victim-org/victim-repo commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `github_app`, and successfully verifies the (attacker-known) signature. [1](#0-0) 
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (owned by an unrelated org), and calls `create_status_from_github!`, writing the forged status onto that commit regardless of which organization actually authenticated the request. [4](#0-3)
