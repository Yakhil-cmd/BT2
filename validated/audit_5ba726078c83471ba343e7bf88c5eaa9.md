### Title
Webhook signature verified against `repository.owner.login`, but handlers act on unrelated `repository.full_name` - cross-tenant repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (or `organization.login` as a fallback). Every webhook handler, however, resolves the target `Stack`/`Repository` to act on using a completely different payload field: `payload.dig('repository', 'full_name')`, read in `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing ties `repository.owner.login` to `repository.full_name` being consistent.

### Finding Description
The relevant code paths: [1](#0-0) 

`verify_signature` fetches `github_app = Shipit.github(organization: repository_owner)` and verifies `X-Hub-Signature` against that organization's `webhook_secret`: [2](#0-1) 

`repository_owner` is derived purely from attacker-controlled JSON body fields (`repository.owner.login`, falling back to `organization.login`), not from any authenticated/URL-bound tenant identifier.

Once the signature check passes, `create` dispatches the same raw JSON body to the registered handlers: [3](#0-2) 

Every handler that needs to find the affected `Stack` uses `Handler#stacks`/`#repository_name`, which reads an entirely different field of the same payload — `repository.full_name` — and never cross-checks it against `repository.owner.login`: [4](#0-3) 

`PushHandler` (and `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) inherit this `stacks`/`repository_name` resolution and use it to sync commits, update CI statuses, and trigger `GithubSyncJob`, `RefreshCheckRunsJob`, or commit-status writes for whatever `full_name` is supplied — with no verification that this repository actually belongs to the organization whose secret validated the signature.

**Binding broken:** the organization that authenticated the request (`repository.owner.login`, checked via HMAC against that org's `webhook_secret`) ≠ the repository the engine actually writes to (`repository.full_name`, used by every handler to locate the `Stack`/`Repository`). In a multi-tenant Shipit deployment (`Shipit.github(organization:)` supports per-organization app configs, as seen in `lib/shipit/github_app.rb`), any organization admin who has legitimately configured their own GitHub App/webhook integration with Shipit knows their own valid `webhook_secret` for HMAC signing. That admin can send `X-Hub-Signature` computed correctly for their own org, while forging `repository.full_name` in the JSON body to point at an unrelated victim organization's repository/stack. The signature check only inspects `repository.owner.login` (which the attacker sets to their own org so verification succeeds), never `full_name`.

### Impact Explanation
This crosses the "cross-repository writes" bar: an attacker with a legitimate, unprivileged tenant integration (their own org's webhook, not a stolen secret) can inject fabricated `push`, `status`, or `check_suite` events against a victim stack/repository they do not control. This can create bogus commits/records via `GithubSyncJob`, forge commit CI statuses (`StatusHandler` writes `Status` records used to gate deployability/merge-queue decisions per `app/models/shipit/deploy_spec.rb` CI config), and manipulate check-run state (`RefreshCheckRunsJob`) for a repository outside the attacker's own trust boundary — all without needing the victim's `webhook_secret`, an `ApiClient` token, or any session credential.

### Likelihood Explanation
Requires the Shipit instance to host multiple organizations/tenants (i.e., `Shipit.github(organization:)` resolves per-organization app/secret configs) and for the attacker to control at least one legitimate GitHub org integrated with that same instance — a realistic scenario for shared/SaaS-style Shipit deployments. No knowledge of the victim's secret, no repository write access to the victim repo on GitHub, and no privileged Shipit account are needed; the attacker only crafts the outbound webhook body themselves.

### Recommendation
After signature verification, re-derive the organization from the *same* field used for routing (`repository.full_name`'s owner segment, or `repository.owner.login`) and assert it matches; or better, verify the webhook secret using an organization identity resolved consistently from `repository.full_name` before ever calling `Handler#stacks`. Reject events where `repository.owner.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
1. Attacker legitimately configures Organization `attacker-org` in the multi-tenant Shipit instance, obtaining its real `webhook_secret`.
2. Attacker POSTs to `/webhooks` with:
   - Header `X-Github-Event: push`
   - Header `X-Hub-Signature: sha1=<HMAC of body using attacker-org's real webhook_secret>`
   - Body:
     ```json
     {
       "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
       "after": "<attacker-chosen sha>",
       "ref": "refs/heads/master"
     }
     ```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates the HMAC — passes, since attacker used their own valid secret.
4. `PushHandler#process` (via `Handler#stacks`/`#repository_name`) resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and syncs/enqueues jobs against the victim's stack, even though the victim never authorized or signed this event. [5](#0-4) [4](#0-3)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
