### Title
Webhook signature verification is silently bypassed when `webhook_secret` is unset, allowing unauthenticated `membership` events to grant `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatic success instead of failing closed, exactly mirroring the reported bug class where a disabled security control (`redis_enabled`/nonce check) silently degrades authentication instead of raising an error. Because `webhook_secret` is documented as "optional" and defaults to `nil`, any Shipit deployment created without setting it accepts **unsigned, attacker-forged** webhook payloads at `/webhooks`. This allows an unprivileged network attacker to forge a `membership` event that adds an arbitrary GitHub login to a `Team` used for `Shipit.github_teams` authorization, escalating that login's access once it completes normal GitHub OAuth login.

### Finding Description
`verify_webhook_signature` returns `true` — i.e. "signature is valid" — whenever no `webhook_secret` is configured, with no warning or error raised: [1](#0-0) 

This is invoked unconditionally by the webhook controller, which only rejects the request when `verified` is `false`: [2](#0-1) 

`webhook_secret` is explicitly documented as optional and has no default value, with no indication that omitting it makes the endpoint unauthenticated: [3](#0-2) [4](#0-3) 

With the signature check neutralized, an attacker can POST a `membership` webhook event, which is processed without any further authorization check and directly mutates team membership: [5](#0-4) 

Team membership is the sole basis for application authorization once a user is logged in via GitHub OAuth: [6](#0-5) [7](#0-6) 

The binding that should hold is: **GitHub webhook signature verified == webhook payload is authoritative for team membership**. When `webhook_secret` is unset, the right-hand side is satisfied unconditionally (any payload is treated as authoritative), breaking the binding without any operator-visible error, exactly as in the reported analog where `redis_enabled: False` silently made any signed "None" nonce authoritative.

### Impact Explanation
An attacker who knows (or brute-forces) an existing `Team#github_id` belonging to one of the organization's `Shipit.github_teams` can forge a `membership` "added" event naming any GitHub login as `member`. `MembershipHandler#process` will call `Team#add_member`, inserting that login into the authorized team without any GitHub-side action. If that GitHub login later (or already) completes the normal OAuth login flow, `User#authorized?` will now return `true` for them, granting them access to stacks, deploys, rollbacks, and merge queue actions — an escalation into `Shipit.github_teams` authorization, which is explicitly listed as a High-impact category for this engine.

### Likelihood Explanation
This requires only a misconfiguration that the codebase itself allows and documents as optional — no code change, TLS interception, or credential theft is needed, only that an operator (accidentally or by following the "optional" documentation) deploys without `webhook_secret` set. This is analogous in likelihood/mechanism to the original report, where the vulnerable state is a legitimate, documented configuration path rather than a hypothetical host-application misuse.

### Recommendation
- Short term: `verify_webhook_signature` should fail closed (return `false`) when `webhook_secret` is blank in non-development environments, and `Shipit.all_settings_present?` / startup checks should require `webhook_secret` to be present before serving `/webhooks` in production.
- Long term: Make `webhook_secret` mandatory outside of `Rails.env.development?`/`test?`, and add explicit "insecure" wording to the config/docs analogous to the report's recommendation for `redis_enabled`.

### Proof of Concept
1. Deploy Shipit with `github.webhook_secret` left blank (a supported, documented configuration per `docs/setup.md`).
2. As an unauthenticated attacker, send:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": <id of an existing required team>, "name": "Developers", "slug": "developers", "url": "http://example.com"},
  "organization": {"login": "<org>"},
  "member": {"login": "<attacker-controlled-or-target-github-login>"}
}
```
No `X-Hub-Signature` header, or any arbitrary value, is required — `verify_webhook_signature` returns `true` because `webhook_secret` is `nil`.
3. `Team#add_member` persists the new membership.
4. The named GitHub login, upon completing standard OAuth login, is now recognized as `authorized?` via `Shipit.github_teams` membership, gaining full application access.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end
```
