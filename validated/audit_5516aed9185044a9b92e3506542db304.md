### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in webhook status handling - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the **organization** derived from the payload (`repository.owner.login` / `organization.login`), using that organization's configured `webhook_secret`. Once the signature is accepted, the full, unscoped payload is handed to `StatusHandler`, which looks up the target `Commit` purely by `sha` with **no check that the commit belongs to a stack/repository owned by the authenticated organization**. This breaks the binding "organization that authenticated == repository that is written": a tenant that legitimately owns *one* organization/app configuration in Shipit can forge a signed `status` event naming any commit SHA from a *different* organization's stack and inject an arbitrary state (e.g. `success`) for it, which can trigger that stack's auto-merge logic.

### Finding Description
`verify_signature` resolves the GitHub App/secret to check against solely from payload fields: [1](#0-0) [2](#0-1) 

The signature is an HMAC over the *entire* raw body computed with the secret of whatever organization `repository_owner` names, per `verify_webhook_signature`: [3](#0-2) 

Once this check passes, `WebhooksController#create` dispatches the *entire, attacker-controlled* JSON body to the handler for the event type, with no re-validation that other fields inside the payload (e.g. `sha`) actually belong to that same organization: [4](#0-3) 

`StatusHandler#process` then resolves the target commit purely by SHA, globally across the entire database, with no repository/stack scoping at all: [5](#0-4) 

This differs from other handlers such as `PushHandler`, which at least scope to `stacks` derived from `payload.dig('repository', 'full_name')`: [6](#0-5) [7](#0-6) 

`StatusHandler` has no equivalent scoping — it never touches `repository`/`organization` at all, so the signature-authenticated organization has zero relationship to the commit whose status gets mutated.

Applying a forged status ultimately calls `Commit#add_status`, which — on state transitions to `pending`/`success` — schedules merges for the affected stack: [8](#0-7) 

**Binding broken:** organization authenticated by webhook HMAC (`repository_owner` in `WebhooksController#verify_signature`) ≠ repository/stack actually written to (any stack owning the attacker-chosen `sha` in `StatusHandler#process`).

### Impact Explanation
Any tenant that Shipit operators have configured as a distinct GitHub organization/app (each with its own `webhook_secret` in `config/secrets*.yml` under `github:`) can, using only their own known secret, forge a `status` webhook event referencing a commit SHA that belongs to a *different* organization's tracked stack. Because `StatusHandler` performs a global `Commit.where(sha:)` lookup with no ownership check, the forged status is applied to that foreign commit, which can flip `stack.schedule_merges` into motion for a repository the attacker has no legitimate relationship with — an unauthorized merge trigger on someone else's stack. This satisfies the Critical criterion of "an unauthorized deploy, rollback, or merge" without requiring the attacker to hold any Shipit session, `ApiClient` token, or write access to the victim repository — only knowledge of a target commit SHA (which is public information for any repository visible on GitHub) and control of one legitimately-configured, unrelated organization/app in the same Shipit deployment.

### Likelihood Explanation
Requires a multi-tenant Shipit deployment where the attacker legitimately controls (or was issued webhook credentials for) one configured organization, plus knowledge of a target commit SHA in another organization's stack (trivially obtainable for public repos, or leaked through Shipit's own UI/API for stacks the attacker can view). No privileged Shipit account, `webhook_secret` theft, or GitHub App key compromise of the *victim* organization is needed — only the attacker's own, legitimately-issued organization credentials. This is a realistic risk in any installation serving more than one GitHub organization.

### Recommendation
Scope every webhook handler's data lookups to the organization/repository that was actually verified during signature verification, not just to attacker-supplied identifiers embedded in the payload. Concretely, in `StatusHandler#process`, restrict the `Commit` lookup to stacks belonging to the repository/organization resolved from the same trust anchor used in `verify_signature` (e.g., join through `stack.repository.owner` matching `repository_owner`), mirroring the scoping already done by `Handler#stacks` for other handlers. More generally, bind the entire per-event payload to the specific organization whose secret validated it, rejecting or ignoring any payload whose declared repository/organization does not match.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` (attacker-controlled, secret known to attacker) and `org-b` (victim, has a stack tracking commit `abc123...` on a protected branch pending merge).
2. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "abc123...",           // commit belonging to org-b's stack
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/attacker-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature` using `org-a`'s known `webhook_secret` over the raw body and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "org-a")` and validates the HMAC successfully (signature matches `org-a`'s secret). [9](#0-8) 
5. `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, finds the commit belonging to `org-b`'s stack (no ownership check), and applies the forged `success` status. [5](#0-4) 
6. The status transition triggers `stack.schedule_merges` on `org-b`'s stack. [10](#0-9)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
