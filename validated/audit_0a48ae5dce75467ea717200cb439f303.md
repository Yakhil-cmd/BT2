### Title
Unbounded HTTP response body reads in credential/webhook flows can cause memory-exhaustion DoS - (File: main.go, pkg/hook/webhook.go)

### Summary
The external report describes a lack of a size cap on data ingested from an external source (a WASM file), letting an attacker force the process to buffer/process arbitrarily large content and exhaust resources. The closest reachable analog in `git-sync` is that every HTTP response body consumed by the process is read fully into memory with `io.ReadAll`, with no `io.LimitReader`/max-size cap, in `CallAskPassURL`, `RefreshGitHubAppToken`, and the webhook `Do` method.

### Finding Description
`git-sync` makes outbound HTTP calls to endpoints supplied via flags (`--askpass-url`, `--webhook-url`, GitHub App token endpoint) and unconditionally reads the entire response body without any length limit:

- `CallAskPassURL` reads the auth URL's response body twice with `io.ReadAll(resp.Body)`, once for the error path and once for the success path, with no cap on size. [1](#0-0) 
- `RefreshGitHubAppToken` reads the GitHub App token endpoint's error body the same way. [2](#0-1) 
- The webhook `Do` implementation reads the webhook response body fully into memory before logging/returning it. [3](#0-2) 

Separately, all `git` subprocess output (stdout/stderr) is captured into unbounded `bytes.Buffer`s in `pkg/cmd/cmd.go`'s `runWithStdin`, so any git operation that returns very large stdout/stderr (e.g., verbose output against a repo with huge trees/blobs) is also buffered without limit. [4](#0-3) 

None of these paths impose a byte cap analogous to the "max file size" fix recommended in the WASM report.

### Impact Explanation
If the endpoint behind `--askpass-url` or `--webhook-url` returns an extremely large or unbounded (e.g. streaming/never-closing) body, `git-sync` will attempt to buffer it entirely in memory, which can exhaust process memory and crash or hang the sidecar, causing persistent sync denial for the pod it serves. This matches the "D:H" (denial-of-service/high) impact class in the original BVSS vector.

### Likelihood Explanation
Exploitation requires the operator-configured askpass/webhook endpoint (or its DNS/backend) to be compromised or to misbehave, or requires a `--askpass-url`/webhook target that is reachable by an untrusted third party (e.g., a shared or attacker-influenced HTTP endpoint). This is a narrower reachable surface than the WASM report's direct attacker-uploaded file, so likelihood is lower and depends on operator configuration flags (`--askpass-url`, `--webhook-url`) being pointed at a non-trusted or compromised service.

### Recommendation
Wrap all `resp.Body` reads with `io.LimitReader(resp.Body, maxBytes)` (and treat truncation/overflow as an error) in `CallAskPassURL`, `RefreshGitHubAppToken`, and `Webhook.Do`. Consider also bounding the `bytes.Buffer` used for subprocess stdout/stderr capture in `pkg/cmd/cmd.go`, or streaming/truncating output for logging purposes.

### Proof of Concept
Not independently verified end-to-end (would require standing up a malicious/misbehaving `--askpass-url` or `--webhook-url` HTTP server that sends a very large or infinite body and observing `git-sync` OOM); the code paths cited above show the unbounded read is the exact root cause and require no privileged access beyond configuring git-sync to point at an attacker-influenced endpoint.
