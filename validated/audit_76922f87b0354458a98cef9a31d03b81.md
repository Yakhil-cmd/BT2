### Title
Interpretation confusion in `has_only()` oscript builtin's dynamically built character-class regex - (File: `formula/evaluation.js`)

### Summary
The oscript builtin `has_only(str, chars)` builds a JavaScript `RegExp` character class directly from an AA-supplied `chars` string, escaping only the `]` character and rejecting a trailing unescaped backslash. It does not neutralize other characters that carry special meaning inside a regex character class — most notably a leading `^` (negation) and `-` (range operator). This mirrors the CWE-436 "interpretation conflict" class in the reported phpseclib advisory, where characters in a supposedly literal matching context (SAN strings) retained unintended regex semantics (e.g. `+` as wildcard), causing verification to accept something the author did not intend.

### Finding Description
`has_only` is implemented in `formula/evaluation.js`: [1](#0-0) 

The sanitization performed is:
1. Reject if `chars` contains an escaped `]` (`\]`) or ends in a lone backslash.
2. Replace any literal `]` with `\]`.
3. Build `new RegExp("^[" + chars + "]*$")` and test the target string against it.

No handling is applied for:
- A leading `^` in `chars`, which negates the character class instead of being treated as a literal caret.
- `-` between two characters in `chars`, which JavaScript regex interprets as a range (e.g. `"0-9"` intended as literal `0`, `-`, `9` becomes the full digit range instead).
- Other characters that behave specially only inside a class (e.g. `\` combinations forming escape sequences like `\w`, `\d`, `\s` when `chars` contains a backslash followed by a letter).

This is directly analogous to the reported bug class: a string that a caller intends to be interpreted as a literal set of allowed characters is instead partially interpreted with regex semantics, silently expanding (or restricting) what actually matches — the same "name confusion" mechanism as the SAN wildcard issue, just applied to AA-side string validation instead of TLS hostname validation.

`has_only` is a public oscript keyword available to any Autonomous Agent author, and the string being tested (`str`) as well as, in some AA designs, the allowed-character set (`chars`) can originate from `trigger.data` supplied by an unprivileged trigger sender: [2](#0-1) 

The parsing/keyword list confirms `has_only` is a first-class exposed formula operation, not an internal-only helper. [3](#0-2) 

Test cases in the repo confirm the exact escaping gaps that are handled (`]` and trailing `\`) but do not cover `^`/`-` range confusion: [4](#0-3) 

### Impact Explanation
If an AA author uses `has_only(field, allowed_chars)` as a security-relevant validation gate (e.g., to whitelist characters in an identifier, ticker, or code path selector before authorizing a payout, minting an asset, or branching into a privileged code path), a trigger sender can exploit the regex-range/negation confusion to make `has_only` return `true` for a string the author intended to reject (validation bypass), or to make legitimate strings unexpectedly fail. A validation bypass on a security-critical field can lead to unauthorized fund release from the AA, incorrect state transitions, or AA fund loss — matching the "unauthorized spending / AA fund loss" impact class requested. Because this is a deterministic function evaluated identically by all full nodes, it does not cause node disagreement, but it can be leveraged purely as an authorization-bypass primitive within a single AA's logic.

### Likelihood Explanation
Exploitability depends on how an individual AA uses `has_only` for validation — this is not a universal, unconditional vulnerability of ocore itself, but a footgun exposed by the base language's `has_only` implementation that any deployed AA relying on it for input sanitization inherits. Any AA author who writes a character-set string containing `-` (e.g., `"a-zA-Z0-9-_"` intending a literal hyphen) or where user-influenced data ends up composing part of the `chars` argument is silently exposed to this misinterpretation. Given `has_only` is documented/intended for character-set validation, this is a plausible and realistic pattern in AA code.

### Recommendation
Harden the `has_only` implementation in `formula/evaluation.js` to escape all regex metacharacters that carry special meaning inside a character class, not just `]`: specifically escape `^` when it is the first character (or escape it unconditionally), escape `-` when not at the very start/end of the class, and escape `\`. Alternatively, avoid building a class-based `RegExp` altogether and implement `has_only` as a direct per-character membership check against the literal character set derived from `chars` (e.g., split `chars` into individual code points and test each character of `str` for membership), which eliminates regex-interpretation ambiguity entirely.

### Proof of Concept
Within an AA (or via `formula/evaluation.js` `has_only` test harness), assume the intended allowed set is the literal characters `0`, `-`, `9` (i.e., digits `0`/`9` and a literal hyphen), authored as:
```
has_only(trigger.data.code, "0-9")
```
Under the current implementation this evaluates as `new RegExp("^[0-9]*$")`, so `code = "12345678"` — which was never meant to be considered "only 0, -, 9" — passes validation, even though it contains characters (`1`-`8`) outside the author's intended literal set. A trigger sender fully controls `trigger.data.code` and can supply any digit string to pass a check the AA author believed restricted to the three literal characters `0`, `-`, `9`, bypassing the intended input-sanitization gate. Depending on how the AA subsequently branches on this validated value (e.g., to authorize a payout path), this can be leveraged to reach unauthorized code paths and unintended fund movement.
