### Title
Predictable PID-based temp file name in stop-hook.sh allows symlink-following file overwrite - ([File: plugins/ralph-wiggum/hooks/stop-hook.sh])

### Finding Description
The atomic state-update logic builds a temp file path using the shell's own PID: `TEMP_FILE="${RALPH_STATE_FILE}.tmp.$$"`, then writes to it with `sed ... > "$TEMP_FILE"` and finally does `mv "$TEMP_FILE" "$RALPH_STATE_FILE"` [1](#0-0) . Shell output redirection (`>`) opens the target path with `O_CREAT|O_TRUNC` and follows symlinks rather than using `O_EXCL`/`O_NOFOLLOW`. There is no existence check, no `mktemp`, and no symlink check before the write.

Because the working directory (`.claude/`) is populated from repository content that an attacker controls (e.g. a malicious repo the victim clones/opens with Claude Code), the attacker can pre-create a path `.claude/ralph-loop.local.md.tmp.<N>` as a symlink pointing at a sensitive file inside the workspace or accessible filesystem location. If the hook process's PID (`$$`) happens to match `N`, the `sed ... > "$TEMP_FILE"` write will follow the symlink and truncate/overwrite the symlink's target with the (mostly harmless, but attacker-partially-influenced) sed output, and the subsequent `mv` will then replace `.claude/ralph-loop.local.md` itself with the attacker's symlink, redirecting all future reads/writes of the ralph-loop state file to the attacker-chosen target.

The practical blocker is that `$$` is not attacker-controlled or predictable at repo-authoring time; the attacker would need to plant a very large number of symlinks (bounded by the OS's PID range, e.g. up to `/proc/sys/kernel/pid_max`, commonly 32768–4194304) to have a realistic chance of matching the actual runtime PID. No existing code path narrows or validates this — there is no allowlist, no symlink guard (`[[ -L ]]` check), and no use of `mktemp`/`O_NOFOLLOW`.

### Impact Explanation
If a PID collision occurs, the attacker can cause an unauthorized overwrite of an arbitrary file reachable via a symlink planted in repository content, and subsequently hijack the ralph-loop state file itself, corrupting the stop-hook's control flow or overwriting content outside the intended `.claude/` sandbox. This matches an "unauthorized file action" / local file corruption impact category, but is constrained to files the hook process already has write permission to.

### Likelihood Explanation
Exploitation requires the attacker to pre-plant a symlink whose numeric suffix matches the exact PID of the bash process that will execute `stop-hook.sh` at hook-invocation time — a value not knowable or influenceable by the attacker in advance. A brute-force approach (committing thousands to millions of symlinks covering the plausible PID space) is technically possible in git but conspicuous, bloats the repository dramatically, and is far from guaranteed to hit the live PID given ASLR-like PID allocation and system-specific `pid_max`. This significantly limits real-world feasibility/reliability compared to a normal predictable-temp-file race in a long-lived multi-user shared-tmp scenario.

### Recommendation
Replace the PID-based temp filename with a securely created temp file, e.g. `mktemp` in the same directory (`TEMP_FILE=$(mktemp "${RALPH_STATE_FILE}.XXXXXX")`), and verify the resulting path is not a symlink (`[[ ! -L "$TEMP_FILE" ]]`) before writing, or write with `set -o noclobber` / an explicit `O_NOFOLLOW`-respecting mechanism. Additionally, check `[[ -L "$RALPH_STATE_FILE" ]]` before trusting/reading it, and reject symlinked state files outright.

### Proof of Concept
Integration test plan:
1. In a scratch git repo, create `.claude/ralph-loop.local.md` with valid frontmatter (`iteration:`, `max_iterations:`, `completion_promise:`) followed by a prompt body.
2. Before invoking the hook, spawn a wrapper script that first reads the hook's own `$$`-to-be (or brute-force by pre-creating symlinks `.claude/ralph-loop.local.md.tmp.<N>` for a bounded test range, e.g. the actual expected PID captured via a stub) pointing to a sentinel file `/tmp/victim.txt` containing known content.
3. Run `stop-hook.sh` with a crafted `transcript_path` JSON on stdin so it reaches the update-state branch.
4. Assert that when `$$` matches the pre-created symlink's suffix, `/tmp/victim.txt` is overwritten with sed output, and `.claude/ralph-loop.local.md` becomes a symlink to `/tmp/victim.txt` (verified via `[[ -L ]]` and `readlink`), demonstrating the symlink-following overwrite and state-file hijack.
5. Assert that after the fix (using `mktemp` + symlink check), the same setup either fails safely (aborts) or writes only within `.claude/`, and `/tmp/victim.txt` remains untouched.
