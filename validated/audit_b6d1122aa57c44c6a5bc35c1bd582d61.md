This confirms the vulnerability chain: `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [1](#0-0)  to resolve which `Stack`/`Repository` receives the event, while `WebhooksController#verify_signature` selects which GitHub App/HMAC secret to check the signature against using `repository_owner`, which independently reads `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) [2](#0-1) . These two fields — `repository.owner.login` (authenticates the org) and `repository.full_name` (selects the repo that is written to) — are both attacker-supplied JSON fields inside the same signed raw body, but the signature only proves the body came from *an* org whose secret matches; it does not bind `owner.login` to `full_name`'s owner. In a multi-org deployment (`Shipit.github(organization:)` supports per-organization `webhook_secret`, as documented and exercised in `config/secrets.development.shopify.yml` / `test/dummy/config/secrets_double_github_app.yml`) [3](#0-2) , an attacker who legitimately controls Org A's GitHub App/webhook (and thus knows Org A's `webhook_secret`) can craft a payload with `repository.owner.login = "org-a"` (so `verify_signature` picks Org A's secret and it validates) but `repository.full_name = "org-b/victim-repo"`. `PushHandler`/`StatusHandler`/`CheckSuiteHandler` then act on whatever stacks match `full_name`, i.e. Org B's stacks, using `Repository.from_github_repo_name` [4](#0-3) .

### Title
Webhook organization used for signature verification is not bound to `repository.full_name` acted upon by handlers, allowing cross-organization webhook forgery in multi-app deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against based on `repository.owner.login` (or `organization.login`) extracted from the unauthenticated JSON body, while all event handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc., via `Handler#repository_name`) instead resolve the target `Repository`/`Stack` using `repository.full_name` from the same body. Nothing checks that these two fields refer to the same organization.

### Finding Description
`verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it to select which configured GitHub App (and therefore which `webhook_secret`) to verify the HMAC against: `Shipit.github(organization: repository_owner)` [5](#0-4) . In a "multiple GitHub applications" deployment, each organization has its own distinct `webhook_secret` [6](#0-5) , and `Shipit.github` looks up the config by that organization key [3](#0-2) .

Once the signature check passes, `WebhooksController#create` dispatches the full, attacker-controlled `params` to the appropriate handler [7](#0-6) . Handlers determine which `Repository`/`Stack` to act on via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` independently of `repository_owner` [8](#0-7) .

Binding broken (equality that should hold but doesn't):
`organization authenticated via repository.owner.login (used to pick webhook_secret)` ≠ `organization implied by repository.full_name (used to select the Repository/Stack acted upon)`.

Before the attack: for a legitimately-forwarded GitHub webhook, `repository.owner.login` and the owner segment of `repository.full_name` are always identical, so the two code paths coincidentally agree. After the attack: an attacker who controls (or has been granted) a GitHub App installation/webhook for one organization ("org-a") in a multi-org Shipit instance knows org-a's `webhook_secret`. They can POST a forged payload with `repository.owner.login = "org-a"` (satisfies `verify_signature`, since it will look up and correctly HMAC-validate against org-a's secret) but `repository.full_name = "org-b/victim-repo"` (used by `PushHandler`/`StatusHandler`/etc. to resolve stacks belonging to org-b). This causes Shipit to act on org-b's stacks — e.g. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on any non-archived stack matching the forged branch/sha for org-b's repository [9](#0-8) , and `StatusHandler#process` creates forged commit statuses on org-b's commits [10](#0-9) , which can satisfy `ci.require` checks and enable continuous-deployment/merge-queue actions on a repository the attacker does not control.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Forged commit statuses combined with continuous deployment or the merge queue can lead to an unauthorized deploy on another organization's stack — meeting the Critical bar ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires the deployment to use the multi-organization GitHub App configuration (documented and supported feature) and requires the attacker to already have legitimate control over the webhook/secret of at least one onboarded organization in that shared Shipit instance. This is a realistic scenario for shared/hosted Shipit instances serving multiple GitHub orgs, but not exploitable against single-organization deployments (the common case), since there `repository_owner` doesn't select among distinct secrets.

### Recommendation
In `WebhooksController#verify_signature` and/or `Handler#repository_name`, enforce that the organization used to select the verifying `webhook_secret` matches the owner segment of `repository.full_name` (and `organization.login` where present) before processing, rejecting the request (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with a distinct `webhook_secret` (as in `config/secrets.development.shopify.yml`) [11](#0-10) , both onboarded with stacks in the same Shipit instance.
2. As an attacker who knows org-a's `webhook_secret` (e.g., because they administer org-a's GitHub App), craft a `push` payload: `{"ref": "refs/heads/main", "after": "<victim sha>", "repository": {"owner": {"login": "org-a"}, "full_name": "org-b/victim-repo"}}`.
3. Compute `X-Hub-Signature` using org-a's `webhook_secret` over the raw body.
4. POST to `/github/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner = "org-a"`, fetches org-a's app, and the signature validates [12](#0-11) .
5. `PushHandler#process` resolves stacks via `repository.full_name = "org-b/victim-repo"` [8](#0-7)  and triggers `sync_github` on org-b's stack using attacker-supplied `after` sha, despite the request never being authenticated by org-b's secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
