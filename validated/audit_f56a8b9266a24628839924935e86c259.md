### Title
Interest accrual can permanently freeze a saturated market before the borrow-index cap is reached - ([File: contracts/pool/src/cache/scale.rs])

### Summary
A market can enter a state where every subsequent interest-accrual operation overflows `i128` while unscaling indexed balances. Because `update_indexes`, repayments, withdrawals, liquidations, and other market operations accrue or unscale balances first, the same overflow makes the market permanently unusable.

### Finding Description
The pool stores user balances as RAY-scaled supply and debt shares and converts them back into token amounts using market indexes. `Cache::calculate_utilization` calls `scaled_to_original` on both `borrowed` and `supplied`, using `borrow_index` and `supply_index` respectively. [1](#0-0)  Other core operations also unscale the indexed balances during withdrawals and repayments. [2](#0-1) 

Interest synchronization is invoked for each requested market by `accrue`, which loads the market cache and calls `interest::global_sync`. [3](#0-2)  At sufficiently high utilization and a large enough scaled balance, index growth can make `scaled_to_original` produce a value above `i128::MAX`. The arithmetic then reverts with `MathOverflow` instead of allowing the configured borrow-index ceiling to engage.

The repository includes a regression-style test demonstrating this state transition. It constructs an 18-decimal market with `1e9` whole tokens supplied and 98% utilization, advances time until `update_indexes` fails with `MathOverflow`, and then confirms that both withdrawal and repayment fail with the same error. [4](#0-3) 

### Impact Explanation
Once the market crosses the representable-value boundary, the failure is persistent rather than a single-call rejection. Any operation that needs to accrue the market or unscale its indexed balances reverts, so suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate affected debt, and routine index updates cannot restore operation. This causes permanent freezing of user funds in the affected market and can leave protocol debt unmanageable.

### Likelihood Explanation
The attack requires a very large 18-decimal market and sustained near-full utilization long enough for the borrow index to multiply the scaled debt beyond the `i128` value ceiling. That is an extreme capitalization and time requirement, but it is reachable through ordinary unprivileged `supply`, `borrow`, and `update_indexes` behavior rather than privileged configuration, malformed storage, leaked keys, or token misbehavior. An attacker who can supply the required liquidity and establish high utilization can deliberately place the market on this trajectory.

### Recommendation
Bound index accrual before unscaling balances, and make the index ceiling engage before value reconstruction can overflow. In particular:

- cap `borrow_index` and `supply_index` before computing scaled-to-original values that can exceed `i128`;
- add checked guards based on `scaled_balance * index / RAY <= i128::MAX`;
- clamp utilization or accrual growth so the configured index ceiling is always reached before the value ceiling;
- ensure repayments and withdrawals retain a recovery path when index accrual reaches the cap;
- add a production regression test based on the existing `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` scenario.

### Proof of Concept
The existing test demonstrates the vulnerable state transition:

1. Create an 18-decimal market using the XLM interest-rate curve.
2. Supply `1_000_000_000 * 10^18` base units.
3. Supply collateral and borrow 98% of the market.
4. Advance time and call `update_indexes` repeatedly.
5. `update_indexes` eventually fails with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`.
6. Subsequent `withdraw` and `repay` calls fail with the same `MathOverflow`. [5](#0-4)

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
