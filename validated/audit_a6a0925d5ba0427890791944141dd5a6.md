### Title
Webhook `status` event writes CI status to commits in **any** stack, not just the repository whose signature was verified - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` records with a **global**, repository-unscoped query (`Commit.where(sha: params.sha)`), while every sibling handler (`PushHandler`, `CheckSuiteHandler`) resolves its targets through the `stacks` helper, which filters by `Repository.from_github_repo_name(repository_name)`. The webhook signature is verified per-organization/repository, but the actual mutation performed by `StatusHandler` is not bound to that same organization/repository — it is bound only to a bare SHA string taken from the payload. This is the same class of bug as the audited `_onDecreaseLever` flaw: the entity that is authorized/verified (`leverParams.position` / the webhook's `repository_owner`) is not the entity that is actually acted upon (`address(this)` / *any* stack whose commit happens to share that SHA).

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` verifies the HMAC signature using the organization/app derived from `params.dig('repository', 'owner', 'login')` [1](#0-0)  and only then dispatches `params` to the registered handlers for the event [2](#0-1) .

The base `Handler` class exposes a `stacks` helper that correctly scopes lookups to the repository named in the (verified) payload: [3](#0-2) 

`PushHandler` and `CheckSuiteHandler` both use this `stacks` scope to restrict their writes to the repository that was actually authenticated: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, ignores `repository_name`/`stacks` entirely and updates every `Commit` row in the whole Shipit installation whose `sha` matches the payload, regardless of which repository/stack that commit row belongs to: [6](#0-5) 

Because `Commit` records are stored per `stack_id` (a stack tracks one repository/branch) but the same 40-character git SHA can legitimately exist in multiple stacks — forks, mirrors, repositories sharing history, cherry-picked/rebased commits with identical tree+parent+metadata, or simply a coincidence engineered by an attacker who controls the source repository and can craft a commit whose SHA1 collides with (or is deliberately reproduced in) a target stack's commit — a `status` webhook that is correctly signed for organization/repository A can be used to plant a status (e.g., `success`/`failure` for context `ci/circleci`) onto a `Commit` object belonging to stack B, in organization C, that the attacker has no access to and that never sent this webhook.

The binding that should hold and is broken:
`organization/repository authenticated by verify_signature` == `repository whose Commit rows are mutated by the handler`.
For `StatusHandler` this becomes `organization/repository authenticated` != `every stack whose Commit.sha happens to match`.

### Impact Explanation
CI statuses drive deploy/merge safety gates: `Commit#deployable?`/`Stack#trigger_deploy`, and `MergeRequest#reject_unless_mergeable!`/`StatusChecker` all consult a commit's recorded statuses to decide whether required CI checks passed [7](#0-6) [8](#0-7) . By forging a `success` status for a commit belonging to a repository/organization it doesn't own, an attacker who legitimately controls (or has push/webhook access to) any other repository configured in the same Shipit instance can cause a victim stack to consider a required status context satisfied, unblocking an otherwise CI-gated automatic merge or continuous deploy. This matches the "unauthorized deploy, rollback or merge" impact bucket.

### Likelihood Explanation
Exploitability requires the attacker to be able to trigger a genuinely signed `status` webhook (i.e., control some GitHub repository that is a valid, configured source for the Shipit installation's GitHub App/organization) and to produce or discover a commit SHA that also exists as a `Commit` row for the target stack. This is realistic in multi-repo/multi-tenant Shipit deployments (forked repositories, mirrored/rebased history, shared submodules, or repositories that share commit graphs), and is strictly a same-instance cross-repository confusion — no secret, token, or session is required beyond the ability to make GitHub emit a `status` event for a repo already wired to Shipit.

### Recommendation
Scope `StatusHandler#process` by the payload's repository the same way `PushHandler`/`CheckSuiteHandler` do, e.g. restrict the lookup to `stacks.map(&:commits)` (commits belonging to stacks resolved from `repository_name`) instead of a bare, repository-unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Attacker registers/owns Repository R2 in Shipit, tracked by Stack S2 (any organization the GitHub App is installed for is sufficient — no special privilege on the victim stack S1/Repository R1 is needed).
2. Attacker crafts a commit in R2 whose SHA matches (or is engineered to match through identical tree/parent/author/committer/timestamp/message) a `Commit` row that already exists for the victim Stack S1 (Repository R1), e.g., a cherry-picked/rebased identical patch, or a shared submodule/mirrored commit.
3. Attacker pushes/triggers a `status` event for R2 (e.g., via their own CI reporting a `success` status, or by using their write access to R2 to call GitHub's Statuses API on that SHA). GitHub signs and sends the webhook with R2's/organization's legitimate `webhook_secret`.
4. `WebhooksController#verify_signature` validates the signature against R2's organization — this succeeds, because it is a real webhook for R2 [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` globally and updates every matching `Commit` row across the whole installation, including the one belonging to victim Stack S1/Repository R1 [6](#0-5) .
6. The forged `success` status on S1's commit satisfies a required CI context, allowing an automatic merge/deploy on S1 that the attacker never had access to trigger legitimately.
