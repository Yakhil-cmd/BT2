### Title
Duplicate-private-payment shortcut in `validateAndSavePrivatePaymentChain()` matches only revealed output fields, skipping validation of the input/provenance chain - ([File: private_payment.js])

### Summary
`private_payment.js`'s `validateAndSavePrivatePaymentChain()` short-circuits full validation whenever an incoming private-payment element's *output* fields (`address`, `amount`, `blinding`, `denomination`) already match a previously stored, revealed output row for the same `unit`/`asset`/`message_index` (and `output_index` for fixed-denomination assets). This mirrors the CVE-2025-68243 bug class: an identity/duplicate-matching routine that compares only a subset of the fields that define the object's true identity/provenance (here, the *outputs*), while ignoring another field set that also defines it (here, the *inputs*, i.e., the spend/provenance chain). Because the match is treated as sufficient proof of "it's the same payment," the code returns `ifOk()` without ever calling into `indivisibleAsset`/`divisibleAsset`'s `validateAndSavePrivatePaymentChain`, which is where spend-proof checks, source-output inclusion checks, and asset-consistency checks actually happen.

### Finding Description
In `private_payment.js`: [1](#0-0) 
the code queries the `outputs` table for an existing row keyed by `unit`, `asset`, `message_index` (and `output_index` when `fixed_denominations`), and if a row is found whose address is already revealed, it computes `bDuplicate` by comparing:
- for indivisible assets: `stored.denomination`, `stored.amount` (vs. `claimed_output.amount`), `stored.address`, `stored.blinding` — all taken purely from the *outputs* side of the payload,
- for divisible assets: the same four output fields, matched against *any* output in the payload (`.some(...)`), explicitly because "divisible outputs are never hidden individually … so match against any of them" [2](#0-1) .

Nowhere in this duplicate check are the payload's `inputs` (the field(s) declaring which prior output/asset issuance this element spends, i.e., `input.unit`, `input.message_index`, `input.output_index`, or `input.type === 'issue'` with `serial_number`) compared against anything already recorded. Yet it is precisely the `inputs` section that establishes the *provenance* of the funds — this is the part validated deeply by `indivisibleAsset.validatePrivatePayment` (spend-proof hash check, `validateSourceOutput`/`graph.determineIfIncluded`) and by `divisibleAsset.validateDivisiblePrivatePayment` (via `validation.validatePayment`), both of which are the actual functions being bypassed by the early `return transaction_callbacks.ifOk()`.

This is structurally identical to the NFS bug: `nfs_match_client()` treated two client records as the "same identity" by comparing only some fields (`export_path` etc.) while omitting fields (`cert_serial`, `privkey_serial`) that also define the client's cryptographic identity under `RPC_XPRTSEC_TLS_X509`. Here, `validateAndSavePrivatePaymentChain()` treats two private-payment elements as the "same payment" by comparing only the *output* fields while omitting the `inputs`/provenance fields that also define what payment this actually is.

### Impact Explanation
Because `bDuplicate` is computed from output fields alone, a counterparty in a private payment (or private-asset issuer/relayer) could resend a private-payment element for the *same* `unit`/`message_index`/`output_index` and the *same* revealed `address`/`amount`/`blinding`/`denomination`, but with a **different, unvalidated `inputs` section** (pointing to a different, possibly fabricated or already-consumed, source output or a bogus `serial_number`/issuance claim). The node will treat this as a harmless duplicate and immediately return `ifOk()` — skipping `checkInputDoubleSpend`, spend-proof verification, and source-output-inclusion checks that would normally catch a forged provenance claim. Any logic elsewhere (wallet UI, forwarding to other cosigners/wallet members, or subsequent chain-building via `buildPrivateElementsChain`/`restorePrivateChains`) that trusts "validation succeeded" for this element without re-deriving the input chain from the DB could be led to treat a bogus input claim as validated, risking acceptance of an unfounded provenance link for a private asset (an availability/integrity issue for private-asset accounting rather than a directly spendable double-spend, since no new DB rows are written on the "duplicate" path).

### Likelihood Explanation
The pathway is reachable by any private-payment counterparty simply by resending a crafted private-payment element to a peer that already possesses the corresponding output (a normal occurrence in ocore's private-payment relay/retry model, e.g., after `ifWaitingForChain`/`findUnfinishedPastUnitsOfPrivateChains` retries). No special privileges are needed beyond being a party to (or intercepting/relaying within) a private payment exchange, and the output fields required to trigger the "duplicate" branch (`address`, `blinding`, `amount`, `denomination`) are already known to the counterparty from the legitimate first exchange.

### Recommendation
Extend the duplicate-detection comparison in `private_payment.js` to also validate that the `inputs` of the resubmitted element are identical to (or consistent with) what was used/expected for the already-stored output — e.g., by hashing/comparing the full `payload.inputs` (unit/message_index/output_index or issue serial_number) against a stored provenance record, not just the output's revealed fields. Alternatively, drop the short-circuit entirely and always route through `indivisibleAsset`/`divisibleAsset` validation (which is idempotent w.r.t. already-applied DB writes) so that spend-proof and source-inclusion checks are never skipped for a resubmitted element.
