Confirmed: `Handler#stacks` and `Handler#repository_name` (used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolve the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')` [1](#0-0) , while `WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC against using a *different* field, `repository_owner` (`repository.owner.login` or falls back to `organization.login`), extracted from the same unverified JSON body [2](#0-1) . Nothing in the code checks that `repository.owner.login` (the field used to pick the signing secret) is consistent with `repository.full_name` (the field used to pick the stack/repository to mutate).

### Title
Webhook signature verification key is selected from an unverified field that is decoupled from the repository actually acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App config (and thus the HMAC secret) to validate a webhook using `repository_owner`, computed by digging into the *raw, unauthenticated* JSON body itself. `Handler#stacks`/`repository_name`, used by every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers) to decide which `Repository`/`Stack` to write to, reads a *different* field of the same untrusted body: `repository.full_name`. The equality the engine implicitly relies on — "the org whose secret validated this signature" == "the owner of the repository the handler is about to mutate" — is never enforced.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [3](#0-2) .

Once `verified` is true, `create` dispatches the full raw body to the registered handler: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .

Every handler resolves the target stack from `payload.dig('repository', 'full_name')` [1](#0-0) , and `Repository.from_github_repo_name` splits that string on `/` to look up `owner`/`name` independently of `repository.owner.login` [5](#0-4) .

Because Shipit supports multiple configured GitHub organizations/App installations (as shown in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`, each with its own `webhook_secret`) [6](#0-5) , an entity that legitimately controls one configured organization's webhook secret (e.g. it installed the same Shipit GitHub App on its own, attacker-controlled org, or that org was configured with `webhook_secret: nil`, which `verify_webhook_signature` treats as "trust anything": `return true unless webhook_secret` [7](#0-6) ) can freely construct the rest of the JSON body. The `repository.owner.login`/`organization.login` field only steers which secret is checked; the `repository.full_name` field that actually determines the mutated `Stack`/`Commit` is not required to match, and is never cross-checked against the value used for signature-key selection.

### Impact Explanation
Using a signature that is only proven to come from *organization A's* installation, an attacker can forge a webhook body whose `repository.full_name` names a completely different, unrelated Shipit-tracked stack (e.g. `victim-org/victim-repo`):
- Forged `push` events invoke `stack.sync_github(expected_head_sha:)` on arbitrary stacks [8](#0-7) , forcing unauthenticated GitHub syncs / potential state churn on repositories the attacker has no access to.
- Forged `status` events call `commit.create_status_from_github!(params)` for any `sha` present in Shipit's DB, letting the attacker inject fabricated CI status (e.g. mark a required check "success") on commits belonging to a victim repository [9](#0-8) , since `Commit.where(sha:)` is not scoped by repository/stack at all.

This can escalate into unauthorized deploys/merges of unreviewed code (a forged passing status can satisfy `required_statuses` used by the merge queue), which maps to the "unauthorized deploy, rollback or merge" Critical-impact category.

### Likelihood Explanation
Exploitability requires the attacker to hold a valid webhook secret for *some* organization configured in the Shipit installation. This is realistic in multi-tenant/multi-org Shipit deployments (explicitly supported, as shown by the double-github-app test fixture) where the attacker's own org, which they administer and can install the shared GitHub App on, is one of the configured organizations — or where an operator leaves `webhook_secret` unset for convenience/dev as the shipped sample config demonstrates. No repository write access, API token, or session is required; the webhook endpoint is unauthenticated by design and reachable by anyone who can send an HTTP request with a correctly-signed body for any one configured org.

### Recommendation
After signature verification succeeds, re-derive `repository_owner`/`organization.login` from the verified payload and assert it matches the owner encoded in `repository.full_name` (and in `Handler#repository_name`) before dispatching to handlers; reject the request (422) on mismatch. Do not treat a `nil` `webhook_secret` as "always verified" for organizations that also own trackable repositories — require a secret in any configuration where the org can act as an event source for `Handler`-consumed repositories.

### Proof of Concept
1. Configure/attacker controls organization `attacker-org` with its own valid GitHub App installation and webhook secret on the shared Shipit instance (or picks an org configured with `webhook_secret: nil`).
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(body, attacker-org secret)>` (or sends no valid signature at all if the target org has no secret) over a crafted body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha tracked by Shipit>",
  "state": "success",
  "branches": [{"name": "master"}]
}
```
3. `X-Github-Event: status` header is set; POST to `/github/webhooks`.
4. `verify_signature` looks up `Shipit.github(organization: 'attacker-org')` and validates the HMAC against `attacker-org`'s (attacker-known) secret — verification passes.
5. `StatusHandler#process` runs unmodified against `victim-org/victim-repo`'s commit, creating a forged "success" status for that commit even though the signature only ever proved knowledge of `attacker-org`'s secret [9](#0-8) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
