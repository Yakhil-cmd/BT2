### Title
Cross-organization webhook forgery via decoupled signature-selection and repository-resolution fields — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to validate against using `params.dig('repository','owner','login')` [2](#0-1) [3](#0-2) , while `ClosedHandler`/`LabelCapturingHandler` resolve the target `Repository`/`Stack` using the unrelated field `params.repository.full_name` [4](#0-3) [5](#0-4) . Nothing in the codebase enforces that these two fields agree, so an attacker holding only their own org's `webhook_secret` can sign a payload under their own org while pointing `full_name` at a victim org's repository, causing `review_stack.archive!` to execute against the victim's stack.

### Finding Description
The broken binding, stated as an explicit equality that the code implicitly relies on but never checks:
`repository_owner (params.dig('repository','owner','login'), used to pick the HMAC secret) == full_name.split('/').first (params.repository.full_name, used to resolve the Repository/Stack acted upon)`.

Trace:
1. `WebhooksController#create` parses raw JSON and dispatches to handlers with no further validation beyond `verify_signature` [6](#0-5) .
2. `verify_signature` calls `Shipit.github(organization: repository_owner)`, which looks up per-org config keyed by `repository_owner` [7](#0-6) , then HMAC-validates the raw body against that org's `webhook_secret` [8](#0-7) .
3. `repository_owner` is read from `params.dig('repository','owner','login')`, a JSON field fully controlled by whoever constructs the payload [3](#0-2) .
4. `ClosedHandler#repository` and `LabelCapturingHandler#repository` independently derive the acted-upon repository from `params.repository.full_name`, a sibling field within the same `repository` sub-object, via `Repository.from_github_repo_name`, which is a bare DB lookup with no correlation to `owner.login` [1](#0-0) .
5. Since `owner.login` and `full_name`'s owner segment are two separate keys, an attacker can set them inconsistently: `repository.owner.login = "attacker-org"` (used only for step 2/3) and `repository.full_name = "victim-org/victim-repo"` (used only for step 4).

Attacker's exact request: two sequential `POST /webhooks`, both signed with `attacker-org`'s own known `webhook_secret`:
- Request 1: `X-Github-Event: pull_request`, `action: "closed"`, `repository.owner.login: "attacker-org"`, `repository.full_name: "victim-org/victim-repo"`. Passes `verify_signature` (secret matches attacker-org's config), reaches `ClosedHandler#process` → `respond_to_pull_request_closed?` true → `review_stack.archive!` on the resolved victim `ReviewStack` [9](#0-8) [10](#0-9) .
- Request 2: same forged binding, `action: "labeled"`. `LabelCapturingHandler#labeled_active_stack?` requires `!stack.archived?` [11](#0-10) ; since request 1 already set `archived_since`, this guard correctly evaluates to `false` and `capture_labels` is skipped — this part of defense-in-depth holds.

Existing guards checked and found insufficient: `verify_signature` only proves possession of *some* org's secret, not the org named in `full_name`; `drop_unhandled_event` and `ExplicitParameters` schema only validate structural shape/types, not cross-field consistency; `Repository.from_github_repo_name` performs no ownership correlation.

### Impact Explanation
Request 1 lets any attacker who owns/registers a GitHub org (or otherwise obtains a webhook secret for one org) attributably archive (and via `ReviewStackAdapter#archive!`, deprovision) another org's/repository's `ReviewStack`, executing `stack.archive!`, `stack.deprovision`, and `stack.remove_from_provisioning_queue` for a repository they never authenticated for [10](#0-9) . This is repeatable against any victim repository/stack whose `owner/name` the attacker can guess or discover, and is directly the "payload for one repository mutating another's stack" Critical category. The follow-up `labeled` request is correctly blocked by the `archived?` check, so no additional label-capture impact is confirmed beyond the archive itself.

### Likelihood Explanation
Requires only that Shipit be configured with the documented multi-org GitHub App schema (`github: { orgA: {...}, orgB: {...} }`) as shown in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml` [12](#0-11) ; single-org installations are not affected by this specific org-confusion path since there is only one secret. The attacker needs no privileges beyond running/controlling a GitHub org that is one of the configured orgs (or any org if `github_default_organization` allows arbitrary matching) and knowing/guessing a victim `owner/repo` name. No GitHub App installation on the victim org is required. Cost is a single crafted HTTP POST with a valid HMAC computed from a secret the attacker legitimately possesses.

### Recommendation
In `WebhooksController` (or in each handler's `repository` resolution), assert that `params.dig('repository','owner','login')` equals the owner segment parsed from `params.repository.full_name` before processing; reject the webhook (422) on mismatch. Alternatively, resolve the target repository directly from `repository.owner.login` instead of trusting `full_name`, and derive `full_name` only for display/logging purposes.

require "test_helper"

module Shipit
  class CrossOrgWebhookForgeryTest < ActionController::TestCase
    tests WebhooksController

    setup do
      # Two orgs configured with distinct webhook secrets, as in
      # test/dummy/config/secrets_double_github_app.yml
      Shipit.stubs(:github_app_config).with("attacker-org").returns(webhook_secret: "attacker-secret")
      Shipit.stubs(:github_app_config).with("victim-org").returns(webhook_secret: "victim-secret")

      @stack = create_victim_review_stack(owner: "victim-org", name: "victim-repo")
    end

    test "closed event signed by attacker-org archives victim-org's stack" do
      body = closed_payload(owner_login: "attacker-org", full_name: "victim-org/victim-repo").to_json
      signature = sign(body, "attacker-secret")

      @request.headers["X-Github-Event"] = "pull_request"
      @request.headers["X-Hub-Signature"] = signature

      assert_changes -> { @stack.reload.archived? }, from: false, to: true do
        post :create, body: body, as: :json
      end
      # Binding check: repository_owner ("attacker-org") != full_name owner ("victim-org"),
      # yet the archive succeeded against victim-org's stack -> Critical cross-tenant mutation.
    end

    test "subsequent labeled event on the now-archived victim stack is blocked" do
      @stack.archive!(shipit_users(:codertocat))

      body = labeled_payload(owner_login: "attacker-org", full_name: "victim-org/victim-repo").to_json
      signature = sign(body, "attacker-secret")

      @request.headers["X-Github-Event"] = "pull_request"
      @request.headers["X-Hub-Signature"] = signature

      assert_no_changes -> { @stack.reload.pull_request.labels } do
        post :create, body: body, as: :json
      end
      assert @stack.reload.archived?, "archived? guard must remain true and block capture_labels"
    end

    private

    def sign(body, secret)
      "sha1=" + OpenSSL::HMAC.hexdigest("sha1", secret, body)
    end
  end
end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
