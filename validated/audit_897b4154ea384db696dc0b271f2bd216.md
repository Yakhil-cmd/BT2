### Title
Webhook signature is verified against `repository.owner.login`/`organization.login`, but handlers act on an unrelated `repository.full_name` / commit `sha` from the same unverified JSON body - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization whose `webhook_secret` is used to validate the HMAC signature based on `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Every webhook `Handler` (a sibling class reading the same JSON body) instead resolves the target `Repository`/`Stack`/`Commit` from a *different, unvalidated* field of the same payload: `payload.dig('repository', 'full_name')` in `Handler#stacks`, or `params.sha` in `StatusHandler` with no repository scoping at all. Nothing enforces that `repository.full_name` belongs to the organization named in `repository.owner.login`/`organization.login`.

### Finding Description
The binding that should hold is: `organization used to select webhook_secret (repository_owner) == organization that owns the repository/commit being written to`. This binding is broken:

- `WebhooksController#verify_signature` picks the app config with `Shipit.github(organization: repository_owner)` and validates `X-Hub-Signature` against that org's secret only. [1](#0-0) [2](#0-1) 

- Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` hands the entire raw, attacker-controlled JSON to the handler. [3](#0-2) 

- `Handler#stacks` resolves the target repository from `payload.dig('repository', 'full_name')`, completely independent of `repository_owner`/`organization.login` used above. [4](#0-3) 

- `PushHandler#process` uses that mismatched repository lookup to trigger `stack.sync_github(expected_head_sha: params.after)` on any matching stack. [5](#0-4) 

- `StatusHandler#process` is worse: it doesn't even consult `repository.full_name` — it updates **any** `Commit` in the whole install whose `sha` matches `params.sha`, regardless of which repository/org that commit belongs to. [6](#0-5) 

Because the HMAC secret is chosen per-organization (`@webhook_secret = @config[:webhook_secret]` in `GithubApp#initialize`, checked in `verify_webhook_signature`), an attacker who legitimately controls the webhook secret for *their own* onboarded organization (`org-A`) can craft a payload where:
- `repository.owner.login` = `"org-A"` (so the signature check passes with org-A's secret), and
- `repository.full_name` = `"org-B/victim-repo"` (or any known commit `sha` belonging to `org-B`) [7](#0-6) [8](#0-7) 

This lets the attacker forge `push`/`status` events that are cryptographically "valid" (per org-A's secret) but are processed as if they came from org-B, driving org-B's `Stack`/`Commit` state.

### Impact Explanation
The most damaging concrete path is `StatusHandler`: an attacker forges a `status` webhook, signs it with their own organization's `webhook_secret`, and sets an arbitrary commit `sha` (a public value obtainable from any repo on GitHub) with `state: "success"`. `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` updates matching commit rows for *any* stack in the Shipit instance, not just the attacker's own org. Because deploy eligibility (`ci.require`, blocking/required statuses used by `Stack`/`Commit#deployable?` gating) is derived from these `Status` rows, an attacker can inject a fabricated passing CI status for a victim repository's commit, bypassing the CI gate that governs whether that commit can be deployed — an unauthorized-deploy-enabling primitive achieved purely by forging a webhook signed with a credential the attacker legitimately possesses for an unrelated organization. `PushHandler` similarly lets an attacker trigger `sync_github` against a victim stack it doesn't control. This crosses the "unauthorized deploy" / "cross-repository writes" impact bar from a credential (webhook secret for org-A) that grants no privilege over org-B.

### Likelihood Explanation
This requires the Shipit deployment to be multi-tenant (multiple GitHub organizations/apps configured, each with its own `webhook_secret`), which is an explicitly supported configuration (`Shipit.github(organization:)`, per-org config in `lib/shipit/github_app.rb`). Any user/bot who legitimately owns a webhook secret for one onboarded organization — a low, "unprivileged" bar relative to other organizations on the same instance — can exploit this without any GitHub App private key, Shipit session, or API token. Likelihood is therefore Medium-High in any instance serving more than one organization.

### Recommendation
After signature verification, re-validate that the repository/commit being mutated by the handler actually belongs to the organization (`repository_owner`) whose secret validated the request. Concretely:
- In `Handler#stacks`, verify `repository_name.split('/').first == repository_owner` (or pass the verified organization down from the controller and assert equality) before resolving stacks.
- In `StatusHandler`, scope the `Commit` lookup by the commit's stack/repository owner, not just by `sha` alone.
- Alternatively, pass the already-verified `repository_owner`/organization from `WebhooksController` into each `Handler` and have `Handler#stacks` cross-check it against `payload.dig('repository', 'full_name')` / `payload.dig('repository', 'owner', 'login')`, rejecting mismatches.

### Proof of Concept
1. Shipit instance is configured with two GitHub Apps/orgs: `org-A` (attacker-controlled, webhook secret known to attacker) and `org-B` (victim, has stack `org-B/victim-repo`, commit `abcdef123...` currently pending/failing CI).
2. Attacker crafts a `status` webhook body:
```json
{
  "sha": "abcdef123...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-A" }, "full_name": "org-A/attacker-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using org-A's `webhook_secret` (`OpenSSL::HMAC.hexdigest('sha1', webhook_secret, body)`), matching `GithubApp#verify_webhook_signature` at `lib/shipit/github_app.rb:76-83`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-A"`, fetches org-A's `GithubApp`, and the signature check passes.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this matches the victim's real commit in `org-B/victim-repo` (found purely by `sha`, no org/repo filter) and marks its `ci/required-check` status as `success`, even though the request was authenticated only for `org-A`.
6. If `org-B`'s stack requires that check before allowing deploys, it is now unblocked, enabling an unauthorized deploy driven entirely by a forged status the attacker was never authorized to submit for `org-B`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
