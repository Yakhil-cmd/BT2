### Title
Webhook signature verification is scoped to an organization derived from the payload, but `StatusHandler` writes commit statuses without checking that scope, enabling cross-repository status forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using an organization name pulled out of the very payload it is about to trust, but nothing later re-checks that the organization which "authenticated" the request is the same organization/repository whose data actually gets mutated. `StatusHandler` in particular updates commit statuses purely by SHA, with zero repository/organization scoping, so a webhook that is validly signed for one tenant organization can be used to write GitHub status data onto commits belonging to a completely different organization's stack.

### Finding Description
`verify_signature` picks the verifying secret based on `repository_owner`, which is read straight out of the untrusted JSON payload before the signature has been confirmed to belong to that data: [1](#0-0) [1](#0-0) [2](#0-1) 

The actual cryptographic check is a straightforward per-organization HMAC compare: [3](#0-2) 

Shipit explicitly supports one distinct GitHub App (and therefore one distinct `webhook_secret`) per organization in a shared deployment, as documented for multi-tenant setups: [4](#0-3) 

Once the signature check passes for whichever organization `repository_owner` names, the raw payload is dispatched unchanged to every handler for the event: [5](#0-4) 

Most handlers additionally scope themselves to the repository named in `repository.full_name` via `Handler#stacks`/`#repository_name`: [6](#0-5) 

But `StatusHandler`, used for the `status` event, does not use this repository scoping at all — it looks up commits solely by `sha` across the entire `Commit` table and writes attacker-supplied status fields (`state`, `description`, `target_url`, `context`) onto whatever commit(s) match, in any stack, in any organization: [7](#0-6) 

This breaks the intended trust binding: `verified_organization (repository_owner used to select the HMAC secret) == organization that owns the resource being written`. Concretely, an organization "A" that is legitimately configured in `secrets.yml` (and therefore knows/controls its own `webhook_secret`, exactly as intended by the multi-org feature) can send a `status` event whose `repository.owner.login`/`organization.login` is `"A"` (so `verify_webhook_signature` succeeds using A's own secret) while the `sha` field names a commit belonging to organization "B"'s repository. `StatusHandler` will happily attach a forged CI status to B's commit.

### Impact Explanation
Commit statuses in Shipit gate deployability/merge decisions (`deployable_status`, `merge_status` hooks and related UI/CI gating logic depend on `CommitStatus` records created via `create_status_from_github!`). By forging a "success" status on an arbitrary victim commit, a tenant that is only supposed to be trusted for its own organization's webhooks can manipulate another organization's deploy-readiness signal, which can lead to an unauthorized deploy being triggered against a stack it has no legitimate access to. This matches the High-impact criteria of "escalation into authorization" / unauthorized ship, achieved purely by exploiting the mismatch between the signature-verification scope (`repository_owner`) and the actual write scope (global `sha` lookup with no organization check).

### Likelihood Explanation
This requires the attacker to be a legitimate, already-configured tenant organization in a multi-org Shipit deployment (i.e., they know their own `webhook_secret`, which the documented multi-org feature intentionally hands to each onboarded organization). No GitHub App private key, `GITHUB_TOKEN`, or Shipit session/API token is needed — only the ability to have GitHub deliver (or replay) a validly-signed `status` webhook for their own org while supplying an arbitrary victim `sha`. Given multi-tenant Shipit installations are an explicitly documented and supported configuration, this is a realistic, unprivileged-relative-to-other-tenants attack path.

### Recommendation
After signature verification succeeds for a given organization, re-validate that every resource referenced by handler logic (commit SHA, repository, stack) actually belongs to that same verified organization before performing any write. Concretely, `StatusHandler#process` should scope its `Commit` lookup through the commit's stack/repository and assert that repository's owning organization matches `repository_owner`/the organization whose secret validated the request, rejecting or ignoring the event otherwise. The same organization-vs-resource check should be applied to `CheckSuiteHandler` and any other handler that trusts payload-provided identifiers without tying them back to the verified organization.

### Proof of Concept
1. Shipit is deployed serving two tenant organizations, `org-a` and `org-b`, each with its own `webhook_secret` in `config/secrets.yml` per the documented multi-org setup.
2. `org-a` (attacker-controlled) knows its own `webhook_secret` and can produce validly HMAC-signed `status` event payloads.
3. Attacker sends:
```
POST /shipit/webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<valid HMAC using org-a's webhook_secret>
{
  "organization": { "login": "org-a" },
  "sha": "<sha of a real commit belonging to org-b's repository>",
  "state": "success",
  "context": "ci/tests",
  "description": "forged",
  "created_at": "2026-09-02T00:00:00Z"
}
```
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and the signature validates successfully using `org-a`'s secret. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the matching commit in `org-b`'s stack (no organization/repository check), creating a forged `success` status on it. [8](#0-7)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
