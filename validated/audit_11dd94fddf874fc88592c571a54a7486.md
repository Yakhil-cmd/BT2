## Title
Webhook signature is verified against an attacker-chosen organization (`repository.owner.login`) while event handlers act on an unrelated repository (`repository.full_name`), enabling cross-repository writes with a signature that never covered the acted-upon repo - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to validate the incoming webhook against using `repository.owner.login` read straight out of the *unauthenticated* JSON body. All the actual event handlers, however, locate the `Stack`/`Commit` to mutate using a completely different field from that same body: `repository.full_name`. Nothing ties these two fields together, so a request that "authenticates" as belonging to one GitHub organization can act on a repository belonging to a totally different, unrelated organization.

### Finding Description
`verify_signature` computes the organization used for HMAC validation solely from the payload itself: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` unconditionally returns `true` when the resolved organization has no `webhook_secret` configured — a fully supported, documented configuration since GitHub Apps do not require a webhook secret at creation time (Shopify's own sample dev config ships with `webhook_secret: # nil`): [3](#0-2) [4](#0-3) 

After signature verification "passes" (or is bypassed for an unsecured org), the controller dispatches the *entire raw, attacker-supplied payload* to all registered handlers without any further scoping to the org that was used for auth: [5](#0-4) 

Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers, etc.) resolves its target `Stack`/`Commit` using `repository.full_name` — a field completely independent of `repository.owner.login`: [6](#0-5) [7](#0-6) 

Concrete handler examples that write state based on this attacker-controlled, un-cross-checked field: [8](#0-7) [9](#0-8) 

**Equality that is broken:** `organization authenticated (repository.owner.login → webhook_secret used to validate X-Hub-Signature)` ≠ `repository written (repository.full_name → Repository.from_github_repo_name → Stack/Commit mutated)`. The engine never asserts that the owner of `full_name` matches `repository.owner.login`.

### Impact Explanation
If any organization configured under `Shipit.github` has no `webhook_secret` set (an explicitly documented, supported state — not a misconfiguration outside the documented setup), an unprivileged external attacker can:
1. Set `repository.owner.login` to that unsecured organization's login, so `verify_signature` passes regardless of the `X-Hub-Signature` header value (`return true unless webhook_secret`).
2. Set `repository.full_name` to any other, fully secured, tracked repository (belonging to an entirely different organization).
3. Have the request fully processed: `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for that victim stack, or `StatusHandler` injects arbitrary commit statuses (`state`, `target_url`, `description`) for that victim's commits via `commit.create_status_from_github!`.

This is a cross-repository write achieved through a signature check that never actually covered the repository being mutated, matching the "Critical — cross-repository writes" bucket: the attacker's forged/unsigned request is accepted as authentic for one org's namespace but mutates state belonging to a different, unrelated repository/stack it was never authorized to touch.

### Likelihood Explanation
Requires only that a single configured GitHub App entry in `Shipit.github` lacks a `webhook_secret` — an officially supported zero-secret configuration for GitHub Apps, not a deviation from documented deployment. No token, session, or repository write access is needed; the attacker only needs network access to the `/webhooks` endpoint.

### Recommendation
Bind the organization used for signature verification to the same value used by handlers to resolve the target repository (i.e., derive both from `repository.full_name`, or explicitly assert `repository.owner.login == full_name.split('/').first` before signature verification and before dispatching to handlers). Additionally, `GithubApp#verify_webhook_signature` should not silently return `true` for every request when `webhook_secret` is unset; if a secret is genuinely optional for an org, that org's webhooks should be scoped or rejected rather than treated as universally trusted.

### Proof of Concept
1. Configure Shipit with two orgs in `Shipit.github`: `open-org` (no `webhook_secret`) and `secure-org` (has a `webhook_secret`, hosts a tracked `secure-org/critical-repo` stack).
2. POST to `/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature` (or garbage value), and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secure-org/critical-repo"
  }
}
```
3. `repository_owner` resolves to `open-org`; `Shipit.github(organization: 'open-org').verify_webhook_signature` returns `true` unconditionally since `open-org` has no `webhook_secret` — see `lib/shipit/github_app.rb:76-83`.
4. `PushHandler#stacks` resolves via `Repository.from_github_repo_name('secure-org/critical-repo')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56`), and `stack.sync_github(expected_head_sha: '<attacker-chosen-sha>')` is invoked for `secure-org`'s stack — despite the request never being signed by `secure-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
