### Title
Cross-tenant forged CI status via unscoped sha lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no filter on the repository/organization that `verify_signature` actually authenticated. `WebhooksController#verify_signature` only proves the payload's `repository.owner.login` corresponds to the organization whose secret signed the request; it never proves that the `sha` inside the body belongs to that same organization's repository. Any org owner (or org with a webhook configured) can therefore forge a `status` event naming a sha they don't own and have it applied to a commit belonging to a completely different tenant's stack.

### Finding Description
Binding claimed and broken: `payload.dig('repository','owner','login')` (the org whose secret verified the request in `WebhooksController#verify_signature`, app/controllers/shipit/webhooks_controller.rb:24-49) should equal the organization that owns the `Repository`/`Stack`/`Commit` being mutated by the handler. `StatusHandler` never enforces this.

Code path:
- `WebhooksController#create` parses the body and dispatches to `Shipit::Webhooks.for_event(event)` handlers (app/controllers/shipit/webhooks_controller.rb:10-15), after `verify_signature` validates the HMAC using `Shipit.github(organization: repository_owner)` (line 25), where `repository_owner` is read straight from the *attacker-controlled* payload (`params.dig('repository','owner','login')`, line 59-62). This only proves the signer knows the webhook secret for that org — it says nothing about the `sha` field in the body.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a **global**, unscoped `Commit` lookup — no join/filter on `stack`, `repository`, or the verified `repository_owner`. Contrast with `CheckSuiteHandler#process` (app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17), which correctly scopes through `stacks` (derived from `Repository.from_github_repo_name(repository_name)` in `Handler#stacks`, app/models/shipit/webhooks/handlers/handler.rb:32-34) before touching commits. `StatusHandler` skips this scoping entirely and doesn't even call `stacks`.

Exploit flow: attacker owns org `attacker-org` with a Shipit-configured webhook secret for their own repo. They learn (e.g. from a public GitHub commit page, PR, or task output) a commit sha `S` that Shipit tracks under victim stack `victim-org/victim-repo`. They POST to `/webhooks` with `X-Github-Event: status`, `repository.owner.login = attacker-org` (so `verify_signature` passes using their own secret), but `sha = S`, `state = "success"`, and forged `description`/`target_url`. `StatusHandler` matches `Commit.where(sha: S)` regardless of which org signed the request, and calls `commit.create_status_from_github!(params)` on the victim's commit, which internally calls `add_status` (app/models/shipit/commit.rb:366-386) — potentially flipping `deployable_status` and firing `stack.schedule_merges` for the victim's stack.

Existing guards fail here because: `verify_signature` validates org-vs-secret but not org-vs-sha; `ExplicitParameters` schema in `StatusHandler` only validates types/presence of `sha`/`state`/etc., not ownership; there is no `require_permission!`/`stacks` scoping check in this handler at all.

### Impact Explanation
An attacker who owns any Shipit-integrated GitHub organization (even a throwaway/free one, as long as its webhook secret is configured in the Shipit host, or in a shared/default GithubApp config) can set arbitrary CI status (`state`, `description`, `target_url`, `context`) on any known commit sha belonging to any other tenant's stack, with no relationship to that tenant. This can flip a victim commit's `deployable_status` and trigger `stack.schedule_merges` (per `Commit#add_status`, app/models/shipit/commit.rb:379-384), i.e., write/mutate state and potentially trigger downstream deploy/merge automation for a stack that never authenticated the request. This is a cross-repository/cross-tenant write, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Preconditions: attacker needs (a) an org with a Shipit webhook configured (attacker's own, fully legitimate and self-controlled), and (b) knowledge of a target commit sha, which is often public (GitHub commit URLs, PR pages, status badges, CI logs). No Shipit session, API token, or victim secrets are required. The attack is a single unauthenticated HTTP POST and is fully repeatable against any sha the attacker can learn, across arbitrary victim stacks/orgs configured in the same Shipit instance.

### Recommendation
Scope `StatusHandler#process` to the verified repository, mirroring `CheckSuiteHandler`. E.g., resolve `stacks` (or the `Repository` from `repository_name`/`repository_owner`) and constrain the commit lookup: `stacks.flat_map(&:commits).where(sha: params.sha)` or join through `Repository` → `Stack` → `Commit` so a commit is only updated if it belongs to a stack owned by the repository that was actually authenticated by `verify_signature`.

### Proof of Concept
Minitest plan (webhooks_controller_test.rb style):
1. Create two fixture stacks under different repositories/orgs, e.g. `stack_a` (owner `attacker-org`) and `stack_b` (owner `victim-org`), each with a tracked `Commit` sharing/using the same known `sha` value `S` (`shipit_commits` fixture or `stack_b.commits.create!(sha: 'deadbeef...')`).
2. Stub `Shipit.github(organization: 'attacker-org').verify_webhook_signature` to return `true` (attacker legitimately controls this secret), while asserting no call/verification occurs for `victim-org`.
3. POST `:create` with `X-Github-Event: status`, body `{ "sha" => S, "state" => "success", "repository" => { "owner" => { "login" => "attacker-org" } } }`.
4. Assert: before request, `stack_b.commits.find_by(sha: S).state != 'success'`; after request, `stack_b.commits.find_by(sha: S).reload.state == 'success'` — i.e., a commit under `victim-org`'s stack was mutated by a request that only authenticated as `attacker-org`, proving `repository_owner (verified) == attacker-org` while `commit.stack.repository.owner == victim-org`, violating the claimed binding.
