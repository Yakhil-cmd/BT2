### Title
Cross-repository Status write via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `sha` across the entire `commits` table and calls `create_status_from_github!` on every match, without ever using the inherited `stacks` scope (which resolves `Repository.from_github_repo_name(repository_name)`). Because signature verification (`WebhooksController#verify_signature`) only proves the sender knows the `webhook_secret` configured for the *organization* named in the payload (`Shipit.github(organization: repository_owner)`), and not that this organization/repository actually owns the target `Commit` row, an attacker who controls any Shipit-onboarded GitHub organization can forge a `status` webhook that mutates a `Commit` belonging to a completely different stack/repository, as long as the SHA collides.

### Finding Description
The broken binding: **repository named in the verified payload (repo-A, owner org-A)** must equal **repository owning the `Commit` row mutated (repo-B / Stack B)** — but this equality is never checked.

- `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` and `verify_webhook_signature`, which only confirms the request HMAC matches the secret configured for `repository_owner` (an organization-level secret) [1](#0-0) . It never checks that the named `repository.full_name` in the payload maps to any real `Repository`/`Stack` in the DB, nor that it matches the commit that will be touched.
- `Handler` provides a `stacks` helper explicitly meant to scope handler logic to the repository named in the verified payload: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none` [2](#0-1) . Other handlers such as `PushHandler` and `CheckSuiteHandler` use this scope, but `StatusHandler` does not.
- `StatusHandler#process` instead does a global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . This ignores `repository_name`/`stacks` entirely — any `Commit` row anywhere in the database with a matching `sha` is mutated.
- `Commit#create_status_from_github!` writes the status using the **found commit's own** `stack_id`, not any value derived from the payload: `statuses.replicate_from_github!(stack_id, github_status)` [4](#0-3) , and `Status.replicate_from_github!` persists a new `Status` row scoped to that `stack_id` [5](#0-4) .

Exploit flow: Attacker A controls org-A (and thus knows/owns the GitHub App webhook secret configured for org-A in Shipit) and owns repo-A within it. A crafts a commit in repo-A whose tree/SHA equals a SHA already present as a `Commit` row belonging to victim Stack B (any repo, any org) — e.g., an empty-tree/cherry-picked commit reproducing the same SHA. A computes a valid `X-Hub-Signature` using org-A's known secret and POSTs to `/webhooks` with `X-Github-Event: status`, `repository.full_name = "org-A/repo-A"`, `sha = <colliding-sha>`, and arbitrary `state`/`description`/`context`. `verify_signature` passes (org-A's own secret, known to A). `StatusHandler#process` finds Stack B's `Commit` row by `sha` alone and calls `create_status_from_github!`, writing an attacker-controlled `Status` (state/description/context/target_url) onto Stack B's commit — a stack A does not own and has no legitimate access to.

No existing guard prevents this: `drop_unhandled_event`/`check_if_ping` are unrelated; `verify_signature` authenticates the org, not the specific repo-to-commit binding; `ExplicitParameters` only validates payload shape, not repository ownership; the `stacks` scope exists precisely to bind repo-to-record but is bypassed here.

### Impact Explanation
A verified webhook for repo-A/org-A directly mutates a `Commit`/`Status` belonging to an unrelated Stack B/repo-B, matching the "Critical: a payload for one repository mutating another's stack, commit" category. Consequences include: injecting fake CI success/failure statuses that can flip `Commit#state`, trigger `enable_ci_on_stack`, `schedule_continuous_delivery`, and enqueue `ProcessMergeRequestsJob` for Stack B — i.e., an attacker owning an arbitrary onboarded org can fabricate green/red CI signals on any other tenant's commit whose SHA they can reproduce, potentially manipulating merge/deploy automation on Stack B. This is repeatable against any stack/commit sharing a discoverable SHA and scales across every tenant hosted on the same Shipit instance.

### Likelihood Explanation
Preconditions: (1) attacker must own/administer a GitHub organization that is itself onboarded in Shipit (so a `webhook_secret` exists and is known to them — trivial if it's their own org's GitHub App config), and (2) attacker must produce a commit whose SHA collides with a specific target commit in a victim's stack. SHA collision via git tree/blob reuse (cherry-pick, copying identical file/commit metadata) is feasible when the attacker can predict or observe the victim's commit content (e.g., open-source, mirrored, or previously public commits), though blindly targeting an arbitrary unknown commit SHA is impractical. The attack cost is a single crafted HTTP POST with a correctly computed HMAC using a secret the attacker legitimately possesses for their own org — no theft of victim secrets required. Given the specific but realistic precondition (attacker being a legitimate a tenant on a shared Shipit instance, or otherwise possessing a valid webhook secret), the finding is credible and repeatable.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository verified by the webhook signature, e.g. use `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or equivalently filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the pattern used by `PushHandler`/`CheckSuiteHandler` so a status can only be applied to commits belonging to a stack whose repository matches `repository_name` from the verified payload.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status webhook for repo-A must not update a commit belonging to Stack B" do
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature verified for repo-A/org-A

  stack_b = shipit_stacks(:shipit) # victim stack, different repository
  colliding_commit = stack_b.commits.create!(sha: 'deadbeef' * 5, ...) # simulate SHA collision

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => colliding_commit.sha,
    'state' => 'success',
    'context' => 'attacker-context',
    'repository' => { 'full_name' => 'org-A/repo-A', 'owner' => { 'login' => 'org-A' } },
    'branches' => []
  }.to_json

  assert_no_difference 'colliding_commit.statuses.count' do
    post :create, body:, as: :json
  end
  # Currently FAILS: colliding_commit.statuses.count increases by 1,
  # proving repo-A's verified payload mutated Stack B's commit.
end
```
Both sides of the binding: `repository_name` resolved from the verified payload (`org-A/repo-A`) vs. `colliding_commit.stack.repository.full_name` (Stack B's actual repo) — they differ, yet the write occurs, confirming the vulnerability.
