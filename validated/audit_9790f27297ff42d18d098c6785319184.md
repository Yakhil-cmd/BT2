I found a clear architecture bug matching the requested binding class: **organization authenticated (webhook signature) vs. repository actually written to (commit status update)**.

## Analysis

`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based solely on `repository_owner`, extracted from the payload itself: [1](#0-0) [2](#0-1) 

Shipit explicitly supports multi-tenant configuration where each GitHub organization has its own `app_id`/`webhook_secret` (documented at `docs/setup.md` "Using Multiple Github Applications"), meaning different customer orgs legitimately hold different secrets: [3](#0-2) 

Once the signature passes, `Shipit::Webhooks::Handlers::StatusHandler#process` (registered for the `status` event) resolves which `Commit` to mutate purely by `sha`, with **no repository or organization scoping at all** — unlike other handlers (`Handler#stacks`/`Handler#repository_name`) that scope by `repository.full_name`: [4](#0-3) [5](#0-4) 

That forged status feeds `Commit#create_status_from_github!` → `#add_status`, which can flip `deployable?` and trigger `stack.schedule_merges`: [6](#0-5) [7](#0-6) [8](#0-7) 

### Title
Cross-tenant forged commit status via organization-agnostic `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature is verified against the webhook secret of the organization named in the payload's `repository.owner.login`/`organization.login` field, but the `status` event handler never re-checks that the target commit belongs to a stack owned by that same organization — it looks the commit up by `sha` across the entire installation. In a multi-tenant Shipit deployment (multiple GitHub orgs configured under `github:` in `config/secrets.yml`), a customer who legitimately controls their own org's webhook secret can forge a signed `status` webhook whose `repository.owner.login` matches their own org (so signature verification succeeds) while the `sha` field targets a commit belonging to a different tenant's repository/stack.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` instance — and thus the HMAC secret — solely from `repository_owner`, itself read out of the untrusted, attacker-supplied JSON body (`app/controllers/shipit/webhooks_controller.rb:59-62`). This binds "the organization whose secret authenticated the request" to a value inside the same payload the attacker controls. `StatusHandler#process` then executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) with no join/filter against `repository.full_name` or the stack that belongs to the authenticating organization, unlike `Handler#stacks`/`#repository_name` used by other handlers (`app/models/shipit/webhooks/handlers/handler.rb:32-38`). The equality that should hold — *organization that authenticated the webhook == organization owning the commit being mutated* — is never enforced.

### Impact Explanation
An attacker who is a legitimate tenant of a multi-org Shipit instance (owns/administers their own GitHub org with its own App/webhook secret configured under `Shipit.githubs`) can post a crafted `status` event: `repository.owner.login` set to their own org (to pass signature verification with their own secret) and `sha` set to a commit hash belonging to a victim tenant's stack, with `state: "success"`. This flips `deployable?` for the victim's commit and can invoke `stack.schedule_merges` (`app/models/shipit/commit.rb:227-229,383`), enabling an unauthorized deploy or an unauthorized merge via the merge queue on a repository the attacker has no access to — a cross-tenant write achieved purely by knowing a target commit sha, which maps to "unauthorized deploy, rollback or merge" impact.

### Likelihood Explanation
Requires only that the host application is configured with multiple GitHub organizations (a documented, supported configuration) and that the attacker is a normal customer/administrator of one of those orgs — no repository write access, `ApiClient` token, or private key needed for the victim's org. The attacker only needs to know a target commit's sha, which is generally available for any repository whose commit history/PRs are visible.

### Recommendation
In `StatusHandler` (and any other handler resolving records without going through `Handler#stacks`), scope the `Commit` lookup to stacks whose repository matches `payload.dig('repository', 'full_name')`, and additionally verify that `repository_owner` used for signature selection matches the `repository.owner.login` actually used to locate the target `Stack`/`Repository`, so the organization that authenticated the webhook is provably the same one whose data is mutated.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `orgA` (attacker-controlled) and `orgB` (victim), each with distinct `webhook_secret` values as shown in `docs/setup.md`'s multi-org example.
2. Attacker computes `sha256`/`sha1` HMAC of a JSON body using `orgA`'s `webhook_secret`:
```json
{
  "sha": "<victim_commit_sha_in_orgB_repo>",
  "state": "success",
  "repository": { "owner": { "login": "orgA" } }
}
```
3. POST to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed_hmac>`.
4. `verify_signature` resolves `Shipit.github(organization: "orgA")` and the signature matches, so the request passes (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit in `orgB`'s stack (no ownership check), and calls `create_status_from_github!`, setting it to `success` and potentially triggering `schedule_merges` for `orgB`'s stack.
