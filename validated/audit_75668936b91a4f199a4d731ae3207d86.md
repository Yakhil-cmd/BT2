### Title
Cross-repository status forgery clears `continuous_delivery_delayed_since` and triggers an unauthorized deploy - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/stack.rb`)

### Summary
`StatusHandler#process` resolves target commits solely by `sha`, with no binding to the repository that authenticated the webhook, so a status crafted by an attacker's own (legitimately webhook-registered) repository can be applied to any `Commit` row across any stack that happens to share that SHA. When that write flips a delayed commit to `deployable?`, the periodic `ContinuousDeliveryJob` deploys it via `Stack#trigger_deploy`, which unconditionally calls `continuous_delivery_resumed!`, clearing `continuous_delivery_delayed_since` on the victim stack and running an unauthorized deploy.

### Finding Description
The broken binding is: `Shipit::Webhooks::Handlers::StatusHandler#process` should enforce `commit.stack.repository == webhook_repository`, but instead does: [1](#0-0) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }` matches every `Commit` row across every stack/repository with that SHA, not only commits belonging to the repository whose webhook secret validated the request. Signature verification (`verify_signature` / `GitHubApp#verify_webhook_signature`) only proves the payload came from *some* repository legitimately registered in Shipit — it does not scope the *effect* of the handler to that repository's own stacks.

Because Git SHAs are content-addressed, an attacker who forks a public repository that a victim also has configured in Shipit shares identical commit SHAs up to the fork point. The attacker can onboard their own fork as a Shipit stack (a self-service, unprivileged action), then fire a genuine, correctly-signed `status` webhook from their own repository for a shared-history SHA with `state: success` and a `context` matching one of the victim stack's required statuses.

`StatusHandler` writes this forged status onto the victim's `Commit` row too, since it only filters by `sha`. This flips `Commit#deployable?`: [2](#0-1) 

Once the commit is `deployable?` for the victim stack, the next `ContinuousDeliveryJob` run (already scheduled and unrelated to who forged the status) calls `Stack#trigger_continuous_delivery`: [3](#0-2) 

which invokes `trigger_deploy`, and `trigger_deploy` unconditionally calls `continuous_delivery_resumed!` after every deploy attempt, with no check of whether the delay was legitimately due to expire: [4](#0-3) 

This both (a) executes a real, unauthorized `Deploy` on the victim's stack, and (b) resets `continuous_delivery_delayed_since` to `nil`, defeating the operator's configured delay/backoff (`continuous_delivery_delayed!` at line 206-208) on a stack the attacker has no permission on.

None of the existing guards prevent this: `verify_signature` authenticates the sender as *a* registered repository, not the *specific* repository owning the target commit; `drop_unhandled_event` only filters event types; `ExplicitParameters` (`requires :sha, :state`) validates payload shape, not repository ownership; and there is no `Repository`/`Stack` scoping applied in `StatusHandler#process` itself.

### Impact Explanation
A payload authenticated for one repository (the attacker's own fork) mutates another repository's stack state (the victim's `Commit`, and transitively its `Deploy` and `continuous_delivery_delayed_since`), matching the Critical category "a payload for one repository mutating another's stack ... or an unauthorized deploy." The attacker triggers a real `Deploy` job on the victim's infrastructure and can repeatedly reset the CD delay/backoff, defeating deployment throttling cross-tenant. This is repeatable against any victim stack whose repository shares commit history with a repository the attacker controls (forks of public repos being the common case).

### Likelihood Explanation
Preconditions: the victim stack must have `continuous_deployment?` enabled with `checks?`/`deployment_checks?` configured (so `continuous_delivery_delayed_since` is meaningful), and the victim's repository must be public/forkable so an attacker can create a repo sharing commit SHAs. The attacker needs only: (1) a fork of the victim's repo, (2) self-service onboarding of that fork as a Shipit stack (standard, unprivileged Shipit usage), and (3) the ability to push a commit and let GitHub emit (or directly POST) a `status` webhook — all actions available to any GitHub user with no Shipit session, API token, or secrets. This is low-cost and fully repeatable.

### Recommendation
Scope `StatusHandler#process` (and any other sha-keyed handler) to commits belonging to the repository that authenticated the webhook, e.g. `Commit.joins(:stack).where(sha: params.sha, stacks: { repository_id: current_repository.id })`, or by comparing `stack.github_repo_name` against the webhook's repository full name before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (new/extended test)
test "status webhook for shared sha does not mutate unrelated stack's commit or resume CD" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(continuous_delivery_delayed_since: 1.hour.ago)
  attacker_repo = Shipit::Repository.create!(owner: 'attacker', name: 'fork-of-victim')
  attacker_stack = Shipit::Stack.create!(repository: attacker_repo, environment: 'production', branch: 'master')

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared history commit')
  # attacker's own commit row with the SAME sha, in their own stack
  attacker_stack.commits.create!(sha: shared_sha, message: 'shared history commit')

  before = victim_stack.continuous_delivery_delayed_since

  handler = Shipit::Webhooks::Handlers::StatusHandler.new
  handler.process_test_payload(sha: shared_sha, state: 'success', context: 'ci/required')

  victim_stack.reload
  assert_equal before, victim_stack.continuous_delivery_delayed_since, "victim stack's CD delay must not be reset by attacker's status"
  assert_nil Shipit::Deploy.where(stack: victim_stack).order(:id).last&.id, "no unauthorized deploy should have been created on victim stack"
end
```

      deploy = with_lock do

        deploy.save!

      end
