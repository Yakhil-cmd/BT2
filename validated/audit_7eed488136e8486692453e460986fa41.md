### Title
`Api::CCMenuController#stack` bypasses `current_api_client` stack scoping, letting a client scoped to stack A read CCMenu status for any stack B - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController` scopes API clients to a single stack via the `stacks` method (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`), but `Api::CCMenuController#stack` overrides this and resolves `params[:stack_id]` against the unscoped `Stack.from_param!`, ignoring `current_api_client.stack_id` entirely. Combined with `#authenticate_api_client`'s fallback to Basic-Auth (`super unless @current_api_client`) when `params[:token]` is invalid or absent, any authenticated `ApiClient` with `read:stack` permission - even one explicitly scoped to a different stack - can fetch the CCMenu XML (build/deploy status) of an arbitrary stack it was never granted access to.

### Finding Description
Binding claimed: `current_api_client.stack_id == params[:stack_id]`'s resolved `Stack#id`, when `current_api_client.stack_id?` is true.

Code path:
- `app/controllers/shipit/api/ccmenu_controller.rb:33-36` - `authenticate_api_client` first tries `ApiClient.authenticate(params[:token])`; if that fails (invalid/missing token), it calls `super`, which is `Api::BaseController#authenticate_api_client` (lines 48-61), performing standard HTTP Basic-Auth verification via `ApiClient.authenticate`. Any valid, non-expired Basic-Auth credential for *any* `ApiClient` (regardless of that client's `stack_id`) sets `@current_api_client`.
- `require_permission :read, :stack` (line 6) only checks `current_api_client.check_permissions!(:read, :stack)` (`app/models/shipit/api_client.rb:38-45`), which validates the *operation:scope* string against the client's `permissions` array - it never compares `stack_id`.
- `#stack` (lines 29-31) resolves the target stack via `Stack.from_param!(params[:stack_id])`, the **unscoped** class method, instead of the base controller's `stacks.from_param!` (`app/controllers/shipit/api/base_controller.rb:74-80`), which is the only place `current_api_client.stack_id` is enforced.

Because `CCMenuController#stack` never calls the scoped `stacks` helper, the equality `current_api_client.stack_id == stack.id` is never checked here, regardless of which authentication branch (token param or Basic-Auth fallback) produced `@current_api_client`. An attacker holding valid Basic-Auth credentials for `ApiClient` X (scoped to stack A, `read:stack` permission) can send `GET /api/1/stacks/:owner/:repo/:branch/cc.xml` (or equivalent CCMenu route) with `params[:token]` invalid/omitted and the Basic-Auth header for client X, targeting `stack_id` for stack B. Authentication succeeds via the Basic-Auth fallback, permission check passes (client X has `read:stack`), and `stack` resolves stack B unconstrained — CCMenu XML for stack B is rendered and returned to a party never granted access to stack B.

Existing guards (`require_permission!`, `check_permissions!`, `ExplicitParameters`) only validate operation/scope strings, not stack identity, and none of them intersect with the `stack` resolution logic that was overridden in this subclass.

### Impact Explanation
An attacker who legitimately possesses (or obtains) Basic-Auth credentials for any `ApiClient` with `read:stack` permission scoped to one stack can read build/deploy status (CCMenu XML — commit sha of last deploy/rollback, running state, timestamps) for **any other stack** in the Shipit instance, including stacks belonging to different repositories/teams. This is a cross-tenant unauthorized read of stack state, matching the High-severity category "unauthenticated/unauthorized read of stack state." It is fully repeatable for any `stack_id` value and does not require the attacker to control the target stack in any way.

### Likelihood Explanation
The attacker still needs valid credentials for *some* `ApiClient` (Basic-Auth username/token pair) with `read:stack` permission — this is not accessible to a fully anonymous internet user per the threat model (no `ApiClient` token is assumed available). This weakens the practical likelihood: exploitation requires possessing at least one legitimate, stack-scoped API credential (e.g., an intentionally narrowly-scoped client issued to a low-trust integration), after which cross-stack disclosure is trivial and repeatable at zero additional cost.

### Recommendation
Change `Api::CCMenuController#stack` to use the base controller's scoped `stacks.from_param!(params[:stack_id])` instead of the unscoped `Stack.from_param!`, so `current_api_client.stack_id` scoping is enforced identically to the rest of `Api::BaseController` subclasses, regardless of whether authentication used the token param or the Basic-Auth fallback.

### Proof of Concept
Under `test/controllers/api/ccmenu_controller_test.rb` (not modifying files outside scope, purely descriptive plan for a minitest):
1. Create `stack_a` and `stack_b`.
2. Create `api_client_a = ApiClient.create!(stack: stack_a, permissions: ['read:stack'], creator: user)`.
3. Send `get :show, params: { stack_id: stack_b.to_param, token: 'invalid-token' }`, with request headers set via `ActionController::HttpAuthentication::Basic.encode_credentials(api_client_a.id.to_s, api_client_a.authentication_token)` (or equivalent valid Basic-Auth pair for `api_client_a`).
4. Assert binding both sides:
   - `assert_equal stack_a.id, ApiClient.authenticate(request.authorization...).stack_id` (the authenticated client's scope is stack A).
   - `assert_equal stack_b.id, assigns(:stack).id` — showing the rendered stack is B, not A.
5. `assert_response :success` and assert response body contains `stack_b`'s CCMenu project data — proving stack B's state was disclosed to a client scoped only to stack A, violating the claimed binding.
