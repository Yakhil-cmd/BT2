### Title
`ENV` injection via pull request label name reaches deploy step's process environment unfiltered - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) directly into the stack's environment hash with no allowlist, and this hash flows unfiltered into `deploy.override` command execution via `Command#unbundled_env` and `PTY.spawn`. An unprivileged fork PR author can label their own PR (e.g., with a label whose upcased form is `ENV`) to inject an arbitrary environment variable name into the deploy process's environment.

### Finding Description
The broken binding is: **the set of environment variable names available to a `deploy.override` shell process should equal `{keys from Shipit-controlled defaults} ∪ {keys explicitly allowlisted via deploy_variables}`**, but in practice it also includes **`{fork PR label names, uppercased}`** with no allowlist filtering.

Trace:
- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does: `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` — every label name becomes an env key verbatim (uppercased), unconditionally.
- Label names are attacker-controlled and captured straight from the webhook payload by `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`): `pull_request.update!(labels: params.pull_request.labels.map(&:name))`. The `LabeledHandler`/`OpenedHandler` schemas only require `labels[].name` be a `String` — no character/content allowlist (confirmed emoji labels are explicitly accepted per `test/models/shipit/webhooks/handlers/pull_request/label_capturing_handler_test.rb:122-130`).
- This `stack.env` is merged into the deploy environment via `TaskCommands#env` / `DeployCommands#env`/`StackCommands#env` (`lib/shipit/task_commands.rb:33-48`, `lib/shipit/stack_commands.rb:13-15`), which is confirmed by `test/lib/shipit/deploy_commands_test.rb` and `test/lib/shipit/task_commands_test.rb` showing `env["WIP"]`/`env["BUG"]` populated straight from labels.
- Crucially, this merge path is **separate** from the allowlisted path: `EnvironmentVariables#permit` (`lib/shipit/environment_variables.rb:13-18`) is only invoked via `DeploySpec#filter_deploy_envs`/`filter_task_envs`, which sanitizes only the caller-supplied `env` parameter (e.g., from `DeploysController#create` params) against `deploy_variables`/`task variables`. It is never applied to `stack.env` / the pull-request-label-derived keys.
- `Command.new(..., env:)` stores `@env` and `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) does `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — i.e., whatever key names arrive in `@env` survive intact into the final environment hash, including a key literally named `ENV`.
- `Command#start` (`lib/shipit/command.rb:85-101`) calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`. Since each deploy step is constructed as a single command-line string (`Command.new(command_line, env:, chdir:)`, `parse_arguments` yields a one-element `@args` array), `interpolated_arguments` is a single string, causing Ruby's `Process.spawn`/`PTY.spawn` semantics to execute it through the system shell (`/bin/sh -c "<command_line>"`) rather than as an argv array. In this invocation mode, environment variables such as `ENV` (honored by dash/ash-family shells to source a startup file) or similar shell-startup-file variables become attacker-controllable and can be abused by any label whose uppercased form matches such a variable name.
- Why existing guards fail: `verify_signature`/`GitHubApp#verify_webhook_signature` only validate that the payload came from GitHub for that repo — they do not restrict what the payload's `pull_request.labels[].name` can be. `ExplicitParameters` (`params do ... requires :labels, Array do requires :name, String end end`) only enforces type `String`, not content or an allowlist. There is no `EnvironmentVariables.permit` call anywhere in the `ReviewStack#env` → `TaskCommands#env`/`DeployCommands#env` → `Command#unbundled_env` chain.

Exploit flow: An attacker forks a repository with `provisioning_behavior: allow_all` and review stacks enabled, opens a PR (auto-provisions a `ReviewStack`), adds a label whose name uppercases to `ENV` (or another shell-meaningful variable), and the label is captured by `LabelCapturingHandler`. On the next deploy/CD run of that review stack, `ReviewStack#env` injects `ENV=true` (or attacker sets other keys) into the process environment used by `deploy.override` commands, which are executed via a shell.

### Impact Explanation
If the target shell used to execute deploy steps honors an attacker-controlled `ENV`-class variable to source an arbitrary file at shell startup, and the attacker can also control or predict the referenced path's contents (e.g., through other fork-controlled state, cached workdir files, or a race), this results in **arbitrary command execution on the Shipit deploy host** in the context of the process running deploy commands — a Critical RCE. Even absent the specific `ENV`-sourcing gadget, the underlying primitive — **unfiltered, attacker-controlled environment-variable-name injection into `PTY.spawn`'d deploy processes** — is a serious violation of the intended env allowlist boundary (`EnvironmentVariables#permit`) that exists precisely to prevent this class of injection for other input vectors (task/deploy API `env` params). It affects only stacks under `provisioning_behavior: allow_all` (or `allow_with_label`/`prevent_with_label` depending on label state) for repositories with review stacks enabled, and is repeatable per PR/label by the fork's own author against their own review stack (not directly against other tenants' stacks, since it only affects the attacker's own PR's stack).

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with `provisioning_behavior` of `allow_all` (or a label-provisioning mode where the attacker's label makes the stack active), and the review stack must run a deploy (continuous deployment or manual). No privileged credentials are required — opening a PR and adding a label on one's own fork is achievable by any GitHub user with read access sufficient to open a PR against the repo. Whether this yields full RCE depends on the target OS/shell's behavior for the specific injected variable and on being able to control/predict the sourced file's content — this final step could not be fully verified in this codebase-only review (it depends on the deploy host's `/bin/sh` implementation, which is outside this engine's code). The finding itself — the unfiltered environment key injection — is concretely demonstrable and reproducible via existing test patterns (`test/models/shipit/review_stack_test.rb:59-65`, `test/lib/shipit/deploy_commands_test.rb`).

### Recommendation
Apply an allowlist to pull-request-label-derived environment variables before merging into `Stack#env`/`ReviewStack#env`, e.g., reject or drop label-derived keys that collide with reserved/dangerous names (`ENV`, `BASH_ENV`, `PATH`, `IFS`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `RUBYOPT`, `BUNDLE_GEMFILE`, etc.) and any key already present in `BASE_ENV`/`Command::BASE_ENV`. More robustly, route `ReviewStack#env`'s label-derived hash through `EnvironmentVariables#permit` against an explicit, repo-configured allowlist of permitted "label env" names, mirroring how `deploy_variables`/`task variables` are enforced for user-triggered deploys. Additionally, ensure deploy/task commands are invoked with an explicit argv array (avoiding the single-string shell-invocation form of `PTY.spawn`) wherever the command line itself is not attacker-controlled shell syntax, to reduce reliance on shell-startup-file variables.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (extend existing suite)
test "#env allows arbitrary reserved-looking keys from pull request labels (ENV injection)" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["env"]  # attacker-controlled fork PR label

  # Binding under test: stack.env should NOT contain a key equal to a
  # dangerous/reserved env var name derived purely from an unprivileged label.
  assert_not_includes stack.env.keys, "ENV",
    "PR label was allowed to inject a reserved env var name into the deploy environment"
end
```

```ruby
# test/lib/shipit/deploy_commands_test.rb (extend existing suite)
test "[allow_all] deploy.override commands inherit ENV injected via a pull request label" do
  stack = shipit_stacks(:review_stack)
  deploy = stack.trigger_continuous_delivery
  stack.pull_request.labels = ["env"]  # uppercased -> "ENV"

  env = Shipit::DeployCommands.new(deploy).env
  assert_equal "true", env["ENV"]  # demonstrates the unfiltered injection

  command = Shipit::Command.new("./script/deploy", env: env, chdir: ".")
  assert_equal "true", command.unbundled_env["ENV"],
    "the spawned deploy process environment inherits an unprivileged, label-controlled ENV key"
end
```

These tests demonstrate the exact equality violation: `stack.env["ENV"]` and `Command#unbundled_env["ENV"]` should be empty/unset (only Shipit-controlled or allowlisted keys should reach the spawned process), but they instead equal the attacker's label-controlled value, confirming the unfiltered path from pull request labels to the `deploy.override` process environment. Full exploitation to RCE via shell-`ENV`-sourcing behavior depends on the specific `/bin/sh` implementation on the deploy host, which is outside the scope of this engine's code and was not independently verified here.
