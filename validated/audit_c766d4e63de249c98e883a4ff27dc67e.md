### Title
Nil-pointer dereference on `gist.Owner` when attacker-controlled host returns 200 with missing `owner` field - (File: pkg/cmd/gist/edit/edit.go)

### Summary
`editRun` only guards against a `404` response by mapping it to `shared.NotFoundErr`; any other successful (`200`) response is trusted verbatim, including one whose JSON body omits or nulls the `owner` field. Because `Gist.Owner` is a `*GistOwner` pointer with `omitempty` ( [1](#0-0) ), a crafted response causes `gist.Owner` to remain `nil`, and the very next line in `editRun` dereferences it unconditionally, panicking the CLI.

### Finding Description
`shared.GetGist` only special-cases HTTP `404` into `shared.NotFoundErr`; any other status/body that decodes without an `encoding/json` error is passed straight through as a successful `*Gist` with no further validation: [2](#0-1) 

In `editRun`, the only check performed before touching `gist.Owner` is the `errors.Is(err, shared.NotFoundErr)` 404 guard; when the attacker's host answers with HTTP 200 and a JSON body that simply omits (or sets to `null`) the `"owner"` key, `err` is `nil`, so execution proceeds past the "gist not found" guard directly into: [3](#0-2) 

`gist.Owner` is `*GistOwner` and defaults to `nil` when absent from JSON (`omitempty` on an unset pointer). The comparison `username != gist.Owner.Login` dereferences the nil pointer, causing an unrecovered panic that crashes the `gh gist edit` invocation. The identical pattern exists in `pkg/cmd/gist/rename/rename.go`: [4](#0-3) 

This matches the exact call sequence described in the question — `shared.GetGist` → `apiClient.REST` → no error returned → `editRun`'s `if username != gist.Owner.Login` — except the root cause is not a misclassification of `api.HandleHTTPError`, but the complete absence of a nil-check/ownership-presence validation on a *successful* (200) response body from an attacker-controlled host.

### Impact Explanation
This is a client-side denial-of-service: an attacker who controls the responses of a host the victim has pointed `gh` at (e.g., a custom/enterprise `GH_HOST`, or any environment where the API endpoint is attacker-influenced) can crash `gh gist edit`/`gh gist rename` for that user by omitting the `owner` field from the gist JSON payload. No code execution, credential leak, or ownership bypass occurs — the process panics before any update request is sent, so it does not qualify as an authorization bypass, just a crash/DoS.

### Likelihood Explanation
Requires the victim to run `gh gist edit <id>` (or `gh gist rename`) against a host under attacker control for API responses — consistent with the stated threat model ("controls responses from a host the victim points gh at"). No authentication bypass or MITM is needed beyond that precondition; the crafted response is trivial to construct (a valid JSON object simply missing the `owner` key), making this fully repeatable.

### Recommendation
In `editRun` (and `renameRun`), explicitly validate that `gist.Owner` is non-nil before dereferencing it, returning an explicit error (e.g., "gist has no owner information") instead of allowing a panic. Consider centralizing this check inside `shared.GetGist` so all callers benefit uniformly.

### Proof of Concept

```go
func TestEditRun_NilOwnerCausesPanic(t *testing.T) {
    reg := &httpmock.Registry{}
    defer reg.Verify(t)

    reg.Register(
        httpmock.REST("GET", "gists/1234"),
        httpmock.StringResponse(`{"id":"1234","description":"","files":{"a.txt":{"content":"hi"}}}`), // no "owner" field, 200 OK
    )
    reg.Register(
        httpmock.GraphQL(`query UserCurrent\b`),
        httpmock.StringResponse(`{"data":{"viewer":{"login":"monalisa"}}}`),
    )

    ios, _, _, _ := iostreams.Test()
    opts := &EditOptions{
        IO:         ios,
        HttpClient: func() (*http.Client, error) { return &http.Client{Transport: reg}, nil },
        Config:     func() (gh.Config, error) { return config.NewBlankConfig(), nil },
        Selector:   "1234",
    }

    // Expect: this call panics with a nil pointer dereference on gist.Owner.Login
    // instead of returning a graceful error.
    require.Panics(t, func() { _ = editRun(opts) })
}
```
Expected assertion: without a fix, `editRun` panics inside the `username != gist.Owner.Login` comparison; after adding a nil check, it should instead return a handled error such as `"gist has no owner information"`.

```go
func GetGist(client *http.Client, hostname, gistID string) (*Gist, error) {
	gist := Gist{}
	path, err := safeurl.JoinPath("gists", gistID)
	if err != nil {
		return nil, err
	}

	apiClient := api.NewClientFromHTTP(client)
	err = apiClient.REST(hostname, "GET", path.String(), nil, &gist)
	if err != nil {
		var httpErr api.HTTPError
		if errors.As(err, &httpErr) && httpErr.StatusCode == 404 {
			return nil, NotFoundErr
		}
		return nil, err
	}

	return &gist, nil
}
```
