### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` only authenticates that the webhook's claimed `repository.owner.login` matches a configured GitHub organization's secret; it never confirms that the `sha`/`context` payload actually pertains to that organization's repositories. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, which is a global, unscoped query across every stack/repository tracked by the Shipit instance. Any onboarded, unprivileged tenant can therefore forge a `status` webhook (signed with their own org's webhook secret) naming any known commit sha from an unrelated repository, and Shipit will attach a spoofed `Status` (with attacker-chosen `context`/`state`/`target_url`) to that victim commit.

### Finding Description
The broken binding is: `authenticated_repository_owner` (the org whose secret validated the HMAC in `verify_signature`) must equal `commit.stack.repository.owner` for every `Commit` that gets mutated by the webhook — but the code never enforces this equality.

- `WebhooksController#verify_signature` derives `repository_owner` from the payload and validates the signature against `Shipit.github(organization: repository_owner)`'s secret [2](#0-1) . This proves the request was signed by *some* organization onboarded to Shipit, not that the `sha` inside the payload belongs to that organization.
- `StatusHandler#process` fetches commits purely by `sha`, with no scoping by repository, stack, or organization at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) .
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, using the *victim* commit's own `stack_id` — so the forged `Status` becomes fully attributed to the victim's stack and merges into that commit's `Status::Group` [4](#0-3) .
- `Status.replicate_from_github!` copies `state`, `description`, `target_url`, and `context` verbatim from the payload with no cross-check against the repository that produced them [5](#0-4) , and the model's only validation is `validates :state, inclusion: { in: STATES, allow_blank: true }, presence: true` [6](#0-5) .
- `Status::Group#select_significant_status` picks the most relevant status purely by `context`/state precedence, with no repository check, so a spoofed `context: 'ci/travis', state: 'success'` can outrank or mask real, legitimate failing statuses for that exact context [7](#0-6) .

Attack flow: attacker owns/administers a repository/organization that is legitimately onboarded into the target Shipit instance (attacker knows their own webhook secret, as is normal for GitHub webhook setup). Attacker looks up a victim commit's public sha (e.g., from the victim's public GitHub repo or the victim's Shipit UI) and POSTs to `/webhooks` with `X-Github-Event: status`, a valid signature computed with the attacker's own org secret, and a body: `{"sha": "<victim-sha>", "state": "success", "context": "ci/travis", "repository": {"owner": {"login": "<attacker-org>"}}}`. `verify_signature` passes because the signature matches the attacker's own org. `StatusHandler` then finds the victim's `Commit` (owned by a completely different stack/repository) purely by sha match and attaches the forged status to it.

Existing guards do not stop this: `verify_signature` authenticates the *sender org*, not the *target commit's owning repository*; `drop_unhandled_event` only checks the event type exists; the `ExplicitParameters` schema in `StatusHandler` only validates types/presence, not repository binding; and `Status` model validations only constrain `state` to an enum.

### Impact Explanation
This lets a payload from one onboarded repository/organization mutate another repository's `Commit`/`Status` records — directly matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." A forged success status on a fabricated `ci/travis` context can make `Commit#state`/`Commit#status` (used for `deployable?`, continuous deployment gating, and merge-request auto-merge via `ProcessMergeRequestsJob`) falsely report the commit as green, potentially triggering an unauthorized deploy or auto-merge of a commit whose real CI never passed. It is repeatable against any commit sha in the entire instance, across arbitrary tenants, as long as the attacker has one legitimately onboarded (even brand-new, throwaway) repository/org in the same Shipit deployment.

### Likelihood Explanation
Preconditions: the attacker needs at least one repository/organization onboarded into the shared Shipit instance (a very low bar for a multi-tenant Shipit deployment — creating a throwaway org and connecting it is the normal onboarding flow) and knowledge of the victim's commit sha (public on GitHub). No secrets, sessions, or elevated roles belonging to the victim are needed. This is trivially repeatable and scriptable against any tracked commit.

### Recommendation
In `StatusHandler#process` (and analogous handlers), scope the `Commit` lookup by the repository asserted in the payload (matched to the actual `Stack`/`Repository` record), e.g. join through `stack.repository` and only apply the status to commits whose stack's repository matches `params.repository.full_name`/owner — mirroring the pattern already used in `PullRequest::ClosedHandler` (`Shipit::Repository.from_github_repo_name(params.repository.full_name)`). Reject webhooks where the commit's owning repository does not match the authenticated `repository_owner`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook from unrelated repository cannot forge status on a victim commit" do
  victim_commit = shipit_commits(:cyclimse_first) # belongs to `cyclimse` stack/repo
  attacker_repository_owner = "attacker-org"       # a different, unrelated onboarded org

  payload = OpenStruct.new(
    sha: victim_commit.sha,
    state: "success",
    context: "ci/travis",
    target_url: "https://attacker.example.com/fake-ci",
    created_at: Time.now.to_s
  )

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(
      repository_owner: attacker_repository_owner
    ).call(payload.to_h)
  end

  refute_equal "ci/travis", victim_commit.reload.status.context
end
```
This test should fail on current code (the forged status IS created and `commit.status.context == 'ci/travis'` / `commit.status.success?` becomes true), demonstrating that `Commit.where(sha: params.sha)` in `StatusHandler#process` is not scoped to the authenticated repository, confirming the binding is broken.
