### Title
Blinding factor and full output data of private-asset payments logged in plaintext via `console.log` - (File: indivisible_asset.js)

### Summary
The CVE-2021-3447 analog is a class of "sensitive parameter written to plaintext log" bugs. In `ocore`, when a node validates an incoming private-asset payment element (data supplied by a private-payment counterparty, e.g. through a textcoin/private payment chain sent over `device.js` messaging), the code logs the full un-hidden spend-proof input, including the address, amount and — critically — the `blinding` factor of the output, to the process console/log with `console.log`.

### Finding Description
In `validatePrivatePayment` (`indivisible_asset.js`), when processing a "transfer" type private input, the code computes a `spend_proof` from the previous private element's revealed output (address, amount, `blinding`) and then immediately logs the same object in full: [1](#0-0) 

The logged fields (`address`, `amount`, `blinding`) are exactly the data that make the private/hidden-asset scheme confidential: outputs in private/indivisible-asset payments are stored hidden as `{amount, output_hash}` and are only unblinded/revealed when explicitly shared with the intended recipient through the encrypted device-messaging channel, see the output-hash check just above this call: [2](#0-1) 

This validation path is reached whenever any counterparty in a private-asset chain (e.g., a textcoin claimant, a payment recipient, or a cosigner receiving a forwarded private chain) sends a private element to be validated — i.e., it is directly triggerable by an unprivileged party who is simply a private-payment counterparty, matching the "private payment chains" reachable surface named in scope. The same value is also used to compute a `spend_proof` hash that is stored on-chain (via `spend_proofs` table), and disclosure of the `blinding` value, `amount` and `address` in a log defeats the confidentiality purpose of blinding: any process that captures logs (log aggregation, verbose/debug mode, crash reporters, third-party log shipping) will have plaintext access to the previously-hidden amount and blinding factor of every private output that passes through this validation function on that node — this is analogous to CVE-2021-3447's core issue of confidential parameters not being protected from logging.

Similarly, `device.js`'s `decryptPackage` unconditionally logs the full decrypted contents of every peer-to-peer device message (`console.log("decrypted: "+decrypted_message)`), which can include private-payment payloads, wallet/xpubkey material, and pairing data forwarded between correspondent devices: [3](#0-2) 

### Impact Explanation
Disclosure of the `blinding` factor together with `address` and `amount` for a private/hidden output breaks the confidentiality guarantee of Obyte's private (hidden) assets: anyone with read access to the node's logs (a very common attack surface — shared hosting, log aggregation services, crash/telemetry pipelines, or simply verbose/debug output enabled) can reconstruct the amount and beneficiary of transactions that were specifically designed to remain hidden from third parties, including from the hub and from other nodes. While this does not by itself enable double-spending or fund theft, it is a confidentiality breach of private-asset data equivalent in class to the CVE-2021-3447 issue (sensitive parameter logged in plaintext, not protected against disclosure), and it is squarely within the private-payment-chain surface reachable by any private-payment counterparty.

### Likelihood Explanation
The `validatePrivatePayment` function is executed automatically, without additional authorization, any time a node receives a private-asset transfer/chain element from any correspondent (recipient, sender forwarding to cosigners, or textcoin claim flow) — no special privileges are required beyond being a normal correspondent in a private payment. `console.log` output is enabled by default in Node.js deployments unless explicitly redirected/suppressed, so the sensitive data is logged on every validation of every private transfer input, not just in a debug/verbose mode.

### Recommendation
Remove or gate the `console.log` statement that prints the full spend-proof object (`address`, `amount`, `blinding`) in `validatePrivatePayment` (indivisible_asset.js, lines ~125-133), and similarly remove/gate the unconditional logging of decrypted device-message contents in `decryptPackage` (device.js, line 466). If logging is needed for debugging, redact or hash the sensitive fields (e.g., log only the resulting `spend_proof` hash, never the raw `blinding`/`amount`/decrypted payload), and ensure such logging is opt-in (e.g., behind a debug flag) rather than always-on.

### Proof of Concept
1. Node A and Node B are correspondents; Node A sends Node B a private-asset (indivisible) payment, or B is the intended chain in a forwarded textcoin claim.
2. On Node B, `wallet.js`/`indivisible_asset.js` calls `validatePrivatePayment` to validate the incoming `objPrivateElement`/`objPrevPrivateElement` for a `transfer` input.
3. Inside `validatePrivatePayment`, the code executes:
   ```js
   console.log("validation spend proof: "+JSON.stringify({
       asset: payload.asset,
       unit: input.unit,
       message_index: input.message_index,
       output_index: input.output_index,
       address: src_output.address,
       amount: prev_hidden_output.amount,
       blinding: src_output.blinding
   }));
   ```
   (`indivisible_asset.js:125-133`)
4. This line prints the plaintext `address`, `amount`, and `blinding` of what is supposed to be a hidden/private output to standard output/log files on Node B, even though these values are never persisted unblinded anywhere else outside the intended encrypted channel.
5. Anyone with access to Node B's logs (log shipping, crash reporting, hosting provider, etc.) can now read the confidential amount and blinding of the private payment, defeating the purpose of the private/hidden asset feature — an impact analogous to CVE-2021-3447's plaintext logging of sensitive parameters.
