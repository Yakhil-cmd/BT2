### Title
Webhook signature verification keys off `repository.owner.login`, but event handlers dispatch based on the unverified `repository.full_name` field, allowing a hosted organization to trigger writes on another organization's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the inbound signature using the organization derived from the payload itself (`repository.owner.login`, falling back to `organization.login`), while every event `Handler` resolves the target `Repository`/`Stack` from a *different* payload field, `repository.full_name`. Nothing ties these two fields together, so a payload that is validly signed for organization X can carry a `repository.full_name` pointing at a repository owned by organization Y.

### Finding Description
`Shipit.github(organization: repository_owner)` in `app/controllers/shipit/webhooks_controller.rb:25` picks per-organization webhook config (and thus the HMAC secret used to verify `X-Hub-Signature`) based on: [1](#0-0) 

Once the signature is accepted, `WebhooksController#create` dispatches the raw parsed body to registered handlers: [2](#0-1) 

Every handler (`PushHandler`, the `PullRequest::*` handlers, etc.) resolves the affected `Repository`/`Stack` from `payload.dig('repository', 'full_name')` via the shared base class, completely independent of the field used for signature routing: [3](#0-2) 

`PushHandler#process` then calls `stack.sync_github` for every matching, non-archived stack on the resolved repository: [4](#0-3) 

`Repository.from_github_repo_name` performs a case-insensitive lookup purely on `owner/name` parsed out of `full_name`, with no cross-check against the organization that was actually used to verify the signature: [5](#0-4) 

The equality that should hold — `organization_whose_secret_signed_the_request == owner_of_the_repository_that_gets_acted_on` — is never enforced. `repository_owner` (verification key) and `repository.full_name` (mutation target) are two independent, attacker-influenceable fields inside the same JSON body that GitHub — or anyone able to configure a webhook delivery using organization X's legitimately-provisioned secret — controls. On a multi-tenant Shipit deployment where `Shipit.github(organization: ...)` maps several distinct organizations to distinct webhook secrets (as implied by `GithubOrganizationUnknown` handling in the controller), an actor who legitimately controls organization X's webhook configuration can emit a signed body whose `repository.owner.login` is `"X"` (so it verifies against X's secret) but whose `repository.full_name` is `"Y/some-repo"`, causing Shipit to act on organization Y's stack.

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written," which the review's rules explicitly recognize as a valid deployment-trust boundary. The concrete consequence via `PushHandler` is an unauthorized sync/deploy trigger (`stack.sync_github`) on a stack belonging to an organization the attacker does not control — a cross-repository/cross-tenant action that meets the "unauthorized deploy" bar, since `sync_github` updates the stack's tracked head and can drive subsequent automatic deployment. Other handlers (`PullRequest::*`) similarly resolve their target `Repository`/`Stack` from `full_name` and could archive/unarchive review stacks belonging to a different organization than the one whose signature validated the request.

### Likelihood Explanation
This requires the attacker to control (or configure a custom delivery for) a webhook endpoint that is signed with an organization's secret already provisioned within this multi-org Shipit deployment — i.e., they must be the legitimate owner/admin of one organization hosted by the instance. No theft of another organization's `webhook_secret`, `GITHUB_TOKEN`, or GitHub App private key is required; the attacker uses their own, validly-issued credential to cross into another tenant's data, which is exactly the class of "unprivileged-attacker analog breaking a deployment-trust binding" the rules call out.

### Recommendation
After parsing the payload, re-derive the organization from `repository.full_name` (the field actually used to resolve the target `Repository`/`Stack`) and confirm it matches the organization whose secret was used in `verify_signature`, rejecting the request (422) on mismatch. Alternatively, scope signature verification to the specific `Repository` record resolved from `full_name` rather than to a free-floating `repository_owner` value taken from the same untrusted payload.

### Proof of Concept
1. Shipit is configured with two organizations, `X` and `Y`, each with its own GitHub App/webhook secret via `Shipit.github(organization: ...)`.
2. Attacker controls organization `X`'s webhook configuration and can produce a validly HMAC-signed delivery using `X`'s secret.
3. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "Y/production-repo",
    "owner": { "login": "X" }
  }
}
```
4. `verify_signature` computes `repository_owner` = `"X"`, fetches `Shipit.github(organization: "X")`, and the HMAC validates successfully since it was actually signed with X's secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("Y/production-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on organization Y's stack, even though the request was authenticated only for organization X. [6](#0-5)

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
