This confirms the exploit chain: the `StatusHandler` at [1](#0-0)  creates a `Status` for any commit matching `params.sha` with no repository-ownership check at all — it only filters by `sha`, not by `repository.full_name`. Combined with the signature-bypass gap in `WebhooksController#verify_signature` and `GitHubApp#verify_webhook_signature` (which trivially returns `true` when `webhook_secret` is blank, a documented "optional" setting), an attacker who knows any configured GitHub organization lacking a `webhook_secret` can forge a `status` webhook for a commit belonging to an entirely different, unrelated stack/organization, flipping it to `success` and triggering `schedule_continuous_delivery` → `ContinuousDeliveryJob` → an unauthorized deploy, as shown in `Commit#schedule_continuous_delivery` and `Status#schedule_continuous_delivery` at [2](#0-1)  and [3](#0-2) .

### Title
Webhook signature verification is keyed to attacker-controlled `repository.owner.login`/`organization.login` while the acted-upon repository is a different attacker-controlled field, enabling forged CI status / push events across organizations - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the request against using `repository_owner`, a value read straight out of the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) at [4](#0-3) . Meanwhile, every event handler (`PushHandler`, `StatusHandler`, PR handlers, etc.) resolves the target `Stack`/`Commit` using a *different* field of the same attacker-controlled body — `repository.full_name` (via `Handler#stacks`/`#repository_name`, [5](#0-4) ) or, for `StatusHandler`, only `params.sha` with no repository binding at all ( [1](#0-0) ).

`GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever `webhook_secret` is blank for the selected organization: [6](#0-5) . The setup docs explicitly document `webhook_secret` as **optional** ( [7](#0-6) ) and the multi-org example configs ship with `webhook_secret: # nil` for every organization ( [8](#0-7) , [9](#0-8) ). In a multi-organization deployment (`Shipit.github(organization:)`, [10](#0-9) ), any organization whose app config omits `webhook_secret` becomes a universal signature bypass for the whole engine, because the check only cares about the `organization`/`repository.owner.login` value the *attacker* supplied, not about which repository is subsequently acted upon.

### Finding Description
The trust binding that should hold is: **the GitHub organization whose secret authenticated the webhook == the organization/repository that the handler subsequently writes to.** This binding is broken because:
1. Signature verification org selection: `Shipit.github(organization: repository_owner)` uses `repository_owner`, itself taken from the unverified JSON body (before any signature check occurs).
2. If that organization's `webhook_secret` is not configured (an explicitly supported, "optional" configuration in `docs/setup.md`), `verify_webhook_signature` returns `true` for *any* signature header value, including none.
3. Handlers such as `StatusHandler` never re-validate that the acted-upon commit/repository belongs to the organization that was used to pick the (bypassed) secret — `StatusHandler#process` matches purely on `Commit.where(sha: params.sha)` [1](#0-0) , and other handlers key on `repository.full_name`, a value fully independent from `repository_owner`/`organization.login` used for step 1.

Before the attack: only a legitimately signed GitHub webhook for organization X can create a `Status`/trigger a sync for stacks tied to organization X's repositories.
After the attack: an unprivileged network attacker who knows (a) any org configured without `webhook_secret` exists in the installation and (b) the target commit `sha`/`repository.full_name` for a *different* organization's stack, can POST a forged, unsigned `status` (or `push`) event that is processed as authentic for that unrelated stack.

### Impact Explanation
For `status` events, forging a `success` state for an undeployed commit on a stack with `continuous_deployment: true` invokes `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob.perform_later(stack)` [2](#0-1) , which can result in `Stack#trigger_continuous_delivery` actually deploying that commit [11](#0-10)  — an unauthorized deploy triggered purely from a forged, unauthenticated HTTP request. This matches the High-impact category "escalation ... unauthenticated read of stack state" / Critical "unauthorized deploy" per the scope rules, since no Shipit session, `ApiClient` token, or repository write access is required — only knowledge of a public commit sha and a misconfigured (but explicitly documented-as-optional) org.

### Likelihood Explanation
The likelihood is directly tied to operator configuration, but the vulnerable configuration is the one the project's own docs and example secrets files present as normal/valid (`webhook_secret` marked "(optional)", shipped example YAMLs setting it to `nil` for every org). Any Shipit installation serving multiple GitHub organizations where at least one has not set a `webhook_secret` is fully exposed, and the attacker requires no credentials, only the public `/webhooks` endpoint and knowledge of a target commit sha/repo name — both routinely observable from GitHub itself.

### Recommendation
Do not let the value used to select the verification secret be independent of, or trusted more than, the value that determines what is acted upon. Concretely: after selecting `github_app` from `repository_owner`, re-verify that the resolved `Repository`/`Stack` for the event (via `repository.full_name`) actually belongs to that same `repository_owner`/organization before dispatching to handlers, and reject the request otherwise. Additionally, treat an org configured without `webhook_secret` as "verification not attempted" only for organizations intentionally operated without any repository binding, or better, require `webhook_secret` to be present for every configured organization and fail closed (return 422) instead of returning `true` when it's blank.

### Proof of Concept
1. Attacker knows a Shipit instance is configured for two organizations, `looselyconfigured-org` (no `webhook_secret` set, per the documented-optional setting) and `victim-org` (target, has a stack with `continuous_deployment: true`).
2. Attacker finds a public, undeployed commit `sha` on `victim-org/some-repo` that is tracked as a Shipit stack.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature` (or an arbitrary one), and JSON body:
```json
{
  "sha": "<target commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "looselyconfigured-org" }, "full_name": "victim-org/some-repo" }
}
```
4. `verify_signature` calls `Shipit.github(organization: "looselyconfigured-org")`; because that org's `webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of the (invalid) signature header.
5. `StatusHandler#process` runs unmodified, calling `Commit.where(sha: ...).create_status_from_github!`, setting the commit to `success`, which — if the stack has continuous deployment enabled — schedules and can execute an unauthorized deploy.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
