### Title
`Api::DeploysController#create`'s `require_ci` check trusts `commit.deployable?` without re-verifying that the underlying `Status` rows were sourced from a webhook naming the commit's own repository - ([File: app/controllers/shipit/api/deploys_controller.rb])

### Summary
`Status::StatusHandler#process` resolves target commits purely by `Commit.where(sha: params.sha)` with no check against the payload's own `repository`/`name` field, so a `status` webhook that is validly signed for *some* org can attach a `success` `Status` to a `Commit` row belonging to a *different* stack/repository that happens to share the same sha (e.g., via a fork sharing git history). `commit.deployable?` and every deploy-time safety check (including the explicit `require_ci` API guard) treat that persisted boolean as already-trusted, with zero re-derivation of provenance at `trigger_deploy` time.

### Finding Description
Binding claimed: `commit.deployable? == true` implies `Status` rows contributing to `success?` were authored via a payload whose `repository.full_name`/`name` equals `commit.stack.repository.full_name`.

Trace:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only checks that the HMAC matches the GitHub App secret for the **organization** derived from `params.dig('repository','owner','login')`. It never checks that the *specific repository* named in the payload is the one that owns the target `Commit`/`Stack`.
2. `Webhooks::Handlers::StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This performs a global lookup by `sha` across **all stacks/repositories** tracked by this Shipit instance. The payload's `name`/`repository.full_name` field (present in real GitHub payloads, see `test/fixtures/payloads/status_master.json:4,103`) is never compared against `commit.stack.repository.full_name`.
3. `commit.create_status_from_github!` → `add_status { statuses.replicate_from_github!(stack_id, github_status) }` writes the `Status` using `commit.stack_id` (correct FK-wise), but the *matching of which commit(s) get the status in the first place* was never scoped to the originating repository.
4. `Commit#deployable?` (app/models/shipit/commit.rb:227-229): `!locked? && (stack.ignore_ci? || (success? && !blocked?))`. `success?` is delegated to `:status`, computed purely from the already-persisted `statuses` association — no re-derivation of which webhook/repository produced them.
5. `Api::DeploysController#create` (app/controllers/shipit/api/deploys_controller.rb:22): `param_error!(:require_ci, "Commit is not deployable") if params.require_ci && !commit.deployable?` — calls only the boolean, no provenance check.
6. `Stack#build_deploy`/`#trigger_deploy` (app/models/shipit/stack.rb:161-196) likewise only reads `until_commit.deployable?` to set `ignored_safeties`.

Because two different `Commit` rows in two different stacks/repositories can legitimately share the same `sha` (e.g., a fork of a public repo retains identical commit objects with identical SHA-1 values), a status event that GitHub validly signs for the attacker's own org/repo can be routed by `StatusHandler` onto the victim stack's `Commit` row for that same sha, flipping `deployable?` to `true` there. Every downstream consumer — including the explicit `require_ci: true` safety switch — accepts this already-persisted boolean without re-checking that its origin matches `commit.stack.repository`.

### Impact Explanation
An attacker who can get a legitimately-signed `status` webhook fired from a repository they control (e.g., a public fork of the target repo sharing commit history, with the same GitHub App/org installation) can cause a `success` `Status` to be recorded against the victim's `Commit` row. This defeats the `require_ci: true` API safety switch in `Api::DeploysController#create`, letting an unauthorized deploy proceed for a commit that never actually passed CI in the victim's own repository. This is a cross-repository payload mutating another stack's commit state and enabling an unauthorized deploy — Critical impact, repeatable against any stack/repository whose tracked commits share a sha with an attacker-reachable repository.

### Likelihood Explanation
Requires: (a) the attacker's repository to be under an org/installation for which Shipit's GitHub App is configured (so `verify_signature` passes), and (b) a commit sha collision between the attacker's repo and the victim's tracked commit — realistically achieved by forking the victim's (public) repository so the shared commit history carries identical SHA-1 objects, then triggering (or emitting) a status event for that sha from the fork. No Shipit session, API token, or secret is needed beyond what GitHub itself provides when the attacker's own repository emits the webhook. This mirrors the "previous scenario" cross-repo status forgery already assumed reachable in this audit series; this question additionally confirms no later stage (deploy trigger, `require_ci`) re-validates provenance, so the forged write is sufficient on its own to defeat the safety switch.

### Recommendation
Scope `StatusHandler#process` (and `CommitChecks`/other webhook handlers that resolve commits by sha) to the repository named in the payload, e.g. resolve the target `Stack`(s) via `Repository.from_github_repo_name(params.name || params.repository&.full_name)` and restrict `Commit.where(sha:, stack: matching_stacks)` before calling `create_status_from_github!`, analogous to how `PullRequest::AssignedHandler#pull_request` scopes lookups by `repository.id` (app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb:53-65). As defense in depth, `Commit#deployable?`/`Api::DeploysController#create` could also re-validate that contributing `Status#context`/origin metadata is consistent with the commit's own stack, but the root fix belongs in the webhook handler's commit resolution.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` or a dedicated cross-repo test:
```ruby
test ":status writes success onto a commit belonging to a different stack/repository than the payload names" do
  victim_stack = shipit_stacks(:shipit) # repository.full_name == 'shopify/shipit-engine' (or similar)
  victim_commit = shipit_commits(:fifth) # currently not deployable
  refute_predicate victim_commit, :deployable?

  request.headers['X-Github-Event'] = 'status'
  # payload signed/accepted for an *attacker-controlled* org/repo, but sha collides with victim_commit.sha
  forged_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'name' => 'attacker/forked-repo',
    'branches' => [{ 'name' => victim_stack.branch }]
  }.merge(repository_params_for('attacker/forked-repo')).to_json

  post :create, body: forged_payload, as: :json
  assert_response :ok

  assert_predicate victim_commit.reload, :deployable?

  # Now show require_ci is defeated:
  post :create, params: { stack_id: victim_stack.to_param, sha: victim_commit.sha, require_ci: true }, as: :json # via Api::DeploysController
  assert_response :accepted # should have been :unprocessable_entity
end
```
Both sides of the binding: LHS `victim_commit.deployable? == true` (achieved without any status ever being authored via a payload naming `victim_stack.repository.full_name`); RHS `Status` rows' authoring payload named `attacker/forked-repo`, not `victim_stack.repository.full_name` — the equality is broken, confirming the vulnerability.     def trigger_deploy(*args, **kwargs)
      if changed?
        # If this is the first deploy since the spec changed it's possible the record will be dirty here, meaning we
        # cant lock. In this one case persist the changes, otherwise log a warning and let the lock raise, so we
        # can debug what's going on here. We don't expect anything other than the deploy spec to dirty the model
        # instance, because of how that field is serialised.
        if changes.keys == ['cached_deploy_spec']
          save!
        else
          Rails.logger.warning("#{changes.keys} field(s) were unexpectedly modified on stack #{id} while deploying")
        end
      end

      run_now = kwargs.delete(:run_now)
      deploy = with_lock do
        deploy = build_deploy(*args, **kwargs)
        deploy.save!
        deploy
      end
      run_now ? deploy.run_now! : deploy.enqueue
      continuous_delivery_resumed!
      deploy
    end
