### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login`, but the handler dispatch is bound to a different field `repository.full_name` — allowing cross-organization forged webhook events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) is used to validate the `X-Hub-Signature` HMAC based on `repository.owner.login` (falling back to `organization.login`) from the JSON body. [1](#0-0) [2](#0-1)  Once the signature is accepted, every handler resolves the target `Repository`/`Stack` to act on using a completely different field of the *same* payload: `repository.full_name`. [3](#0-2)  These two fields are never cross-checked, so the field that authenticates the request (`repository.owner.login`) and the field that determines what gets written (`repository.full_name`) can point to two different organizations/repositories in a single crafted payload.

### Finding Description
`verify_signature` computes `repository_owner` and uses it to fetch the corresponding `Shipit.github(organization: repository_owner)` app config, and verifies the HMAC using that org's `webhook_secret`: [1](#0-0) 

The `create` action then re-parses the identical raw body and dispatches to handlers keyed only on `X-Github-Event`: [4](#0-3) 

Handlers such as `PushHandler` never look at `repository.owner.login` again. Instead they resolve the affected stacks purely from `repository.full_name`: [3](#0-2) [5](#0-4) 

This is analogous to the reported bug class: instead of a non-deterministic map lookup being substituted for explicit case handling, here two independent, attacker-controlled JSON keys within the same payload are treated as if they describe the same entity, when nothing enforces that binding. The binding that should hold is:

`organization that authenticates the signature (repository.owner.login) == organization/repository that handlers act on (repository.full_name)`

Before the attack: in the legitimate flow, GitHub always sets `repository.owner.login` and `repository.full_name` consistently for the org/repo that owns the installation and computed the signature, so the two fields always agree.

After the attack: an entity that controls a GitHub App installation on Shipit for `attacker-org` (and therefore knows/controls `attacker-org`'s `webhook_secret`, e.g. in a multi-org Shipit deployment as documented) can send a POST to `/webhooks` with `repository.owner.login = "attacker-org"` (so `verify_signature` picks `attacker-org`'s webhook secret and the HMAC validates) while setting `repository.full_name = "victim-org/victim-repo"`. `PushHandler` (or any other handler keyed on `repository.full_name`) will then act on `victim-org/victim-repo`'s stacks, e.g. triggering `stack.sync_github(expected_head_sha: params.after)` for a repository the attacker does not control. [5](#0-4) 

### Impact Explanation
This breaks the binding "organization that authenticated versus the repository that is written," letting an attacker who legitimately controls one configured GitHub organization's app forge deploy-triggering webhook events (sync, status, check_suite, pull_request handling, etc.) against another organization's stacks hosted on the same Shipit instance, without having any credentials for the victim organization. Depending on which handler is targeted, this can trigger unauthorized `GithubSyncJob`s, fabricate commit statuses, or manipulate merge/PR state for repositories the attacker has no legitimate access to — a cross-repository/cross-organization write that maps to the "cross-repository writes" / "unauthorized deploy" Critical/High impact bar.

### Likelihood Explanation
Exploitability requires the attacker to already have valid signing capability for at least one GitHub App/org configured on the target Shipit instance (i.e., they must be an org admin for some org onboarded to the shared Shipit deployment, as described in the documented multi-organization setup). Given that requirement, forging the cross-organization payload itself is trivial (a single crafted JSON body), so likelihood is meaningfully bounded by how many independent organizations share one Shipit deployment — this is an explicitly supported and documented configuration. [6](#0-5) 

### Recommendation
After `verify_signature` succeeds, handlers should re-derive/validate the target repository using the same `repository.owner.login`/`organization.login` value that was used to select the signing organization, and reject (or the controller should reject) any payload where `repository.full_name`'s owner segment does not match `repository_owner`. Concretely, `Handler#repository_name` in `app/models/shipit/webhooks/handlers/handler.rb` should be constrained to the verified organization, and `WebhooksController#verify_signature` should pass the verified organization into the handler dispatch so handlers can assert consistency before mutating any `Stack`.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per the documented multi-org setup). [6](#0-5) 
2. As an admin of `attacker-org`'s GitHub App, craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over this exact body.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` to `"attacker-org"`, fetches `attacker-org`'s app, and the signature validates. [1](#0-0) 
6. `PushHandler` resolves stacks via `repository.full_name` = `"victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack, even though the request was never signed by `victim-org`'s app. [5](#0-4) [3](#0-2)

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
