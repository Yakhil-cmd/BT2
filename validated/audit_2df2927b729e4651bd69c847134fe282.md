### Title
AA payment messages for fixed-denomination assets are silently dropped while accompanying state changes still execute, permanently locking funds - (File: aa_composer.js)

### Summary
In `aa_composer.js`, when an Autonomous Agent (AA) sends a `payment` message for an asset with `fixed_denominations` (an indivisible asset), the composer silently drops the payment message from the response unit instead of bouncing the whole trigger. Any accompanying `state` message in the same response (typically used to decrement an internal accounting variable that tracks the user's withdrawable balance) is not filtered out and still executes. The result is the same class of bug as the reported `CollateralEscrowV1` issue: an outbound transfer that does not actually happen, while the code that records the transfer as "done" (decrementing the balance) proceeds unconditionally.

### Finding Description
In `sendUnit()` inside `handleTrigger()`, each `payment` message is processed with `storage.loadAssetWithListOfAttestedAuthors`. If the asset has `fixed_denominations`, the payload is left incomplete and the callback returns immediately with a comment acknowledging it will be dropped later: [1](#0-0) 

Later, the composer performs a second filtering pass that removes any `payment` message whose asset is `fixed_denominations` — without bouncing or raising any error for this specific case: [2](#0-1) 

Notably, this behavior is asymmetric with how private assets are handled just a few lines earlier: attempting to send a private asset from an AA does raise an error and triggers a bounce (`cb("sending private asset from AA")`), which reverts all state changes performed by the trigger via the existing `bounce()`/`revert()` machinery: [3](#0-2) 

Fixed-denomination assets get no such protection — the payment message vanishes from `messages` quietly, but any other message in the same array (e.g., an `app: 'state'` message that decrements a balance variable such as `var[$key] -= trigger.data.amount`, exactly the withdrawal accounting pattern used throughout the AA sample templates) is unaffected by this filter and still runs via `executeStateUpdateFormula`: [4](#0-3) 

This is the same root cause as the reported Solidity bug: the code that performs the "effect" (decrementing the recorded balance/state) executes without verifying that the corresponding transfer message actually succeeded or was even included in the final unit.

### Impact Explanation
Any AA that tracks user balances internally (the canonical withdraw pattern seen repeatedly in the codebase's own sample scripts, e.g. `test/samples/a_bank_without_percent.oscript` and `test/samples/order_book_exchange.oscript`, which pair a `payment` message with a `state` message that decrements `var[$key]`) is at risk if it is (or is later reconfigured/parameterized to be) used with an indivisible/fixed-denomination asset: [5](#0-4) 

When such a withdrawal is triggered for a fixed-denomination asset, the AA's response unit will contain the `state` message that decrements the user's accounted balance, but the `payment` message that was supposed to actually send the asset to the user is silently removed. The user's internal balance is destroyed with no corresponding on-chain transfer occurring — the asset units held by the AA become permanently unreachable through that AA's accounting logic, since the only record of entitlement (the state variable) has already been erased.

### Likelihood Explanation
This requires an AA definition (posted by any unprivileged unit poster) that pays out a fixed-denomination asset in response to a trigger. This is a legitimate, common pattern (asset-holding/exchange/vault-style AAs), and nothing in AA validation (`aa_validation.js`) rejects payment messages targeting fixed-denomination assets at definition time — the failure only manifests silently at execution time in `aa_composer.js`. Any trigger sender (including the intended withdrawer) can reach this path by simply calling the withdraw functionality with an indivisible asset as the target asset.

### Recommendation
Treat an attempted payment of a `fixed_denominations` asset the same way sending a private asset is treated: return an error from `sendUnit`'s per-message processing (rather than filtering it out silently) so the whole trigger bounces and all state changes — including the balance decrement — are reverted via the existing `bounce()`/`revert()` mechanism. Alternatively, if dropping such payment messages must remain silent, ensure the removal happens *before* the AA's oscript logic is evaluated (or reject invalid `payment` messages targeting fixed-denomination assets during static AA validation) so that state formulas can never assume the withdrawal succeeded.

### Proof of Concept
1. Define an AA with a withdraw case identical in structure to `test/samples/order_book_exchange.oscript`, but targeting an asset that is defined with `fixed_denominations: true` (an indivisible asset), e.g.:
```
messages: [
  { app: 'payment', payload: { asset: "{trigger.data.asset}", outputs: [{address: "{trigger.address}", amount: "{trigger.data.amount}"}] } },
  { app: 'state', state: `{ var[$key] = var[$key] - trigger.data.amount; }` }
]
```
2. A user deposits the indivisible asset and accrues `var[$key]` balance via the AA's deposit handling.
3. The user posts a trigger to withdraw: `trigger.data = { withdraw: true, asset: <fixed_denom_asset>, amount: N }`.
4. In `handleTrigger` → `sendUnit`, the payment message for `<fixed_denom_asset>` is dropped at aa_composer.js:1356 (no bounce), but the `state` message decrementing `var[$key]` remains and executes via `executeStateUpdateFormula`.
5. The resulting response unit has no payment output to the user for the indivisible asset, yet `var[$key]` has been permanently reduced — the user's claim on the AA's held indivisible-asset balance is now lost with no way to withdraw it.
