### Title
Cross-tenant Status forgery via `Shipit::Webhooks::Handlers::StatusHandler#process` toggles arbitrary victim commit/stack deployability - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the signature against using `repository_owner`, a value read directly out of the attacker-controlled JSON payload (`params.dig('repository','owner','login')`), not from any lookup tied to the `sha` being reported. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no re-check that the resolved commit's `stack`/org matches the org that authenticated the request. An attacker who owns any GitHub org/repo registered in Shipit can sign a `status` webhook with their own valid `webhook_secret`, but put a victim's commit `sha` and any `state`/`context`/`description`/`target_url` in the body, and it will be written as a `Status` on the victim's commit.

### Finding Description
Binding that should hold: `org_that_authenticated_signature == org_owning_stack(Commit.find_by(sha: params.sha))`.

Trace:
- `app/controllers/shipit/webhooks_controller.rb:24-30` (`verify_signature`) computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` (line 59-62) is `params.dig('repository','owner','login') || params.dig('organization','login')` — fields fully controlled by the requester's JSON body, not derived from the `sha` or any existing `Repository`/`Stack` record.
- `verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) only checks the HMAC against the secret for that *self-declared* org. If the attacker owns a Shipit-registered org/app installation, they know that org's `webhook_secret` context and can produce a valid signature for a payload whose `repository.owner.login` is their own org while the `sha` field references an unrelated victim commit.
- `Handlers::StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this looks up the commit purely by `sha` across the entire installation, with zero scoping to the repository/org that signed the request. [1](#0-0) 
- `Commit#create_status_from_github!` → `statuses.replicate_from_github!` persists a `Status` row with the attacker-supplied `state`, `context`, `description`, `target_url` for that commit's `stack_id`. [2](#0-1) 
- Commit statuses feed `Status::Group`, whose `required_statuses` (delegated from `commit`) and `blocking?`/significant-status logic determine deployability; forging a `success` state for a context matching the victim stack's required status directly clears a blocking condition used by `Stack#deployable?`/`Commit#deployable?`. [3](#0-2) 

None of the listed guards prevent this: `verify_signature` validates a signature, but against an org chosen from the same untrusted payload, not against the commit's true owner; `drop_unhandled_event` and the `ExplicitParameters` schema (`requires :sha`, `accepts :state/:description/:target_url/:context`) only validate types/presence, not tenancy; there is no `stacks`/`current_api_client` scoping in this webhook path at all (webhooks are unauthenticated except for the HMAC check, which is exactly the part being bypassed via org confusion).

The existing test `test/controllers/webhooks_controller_test.rb:42-59` (":state create a Status for the specific commit") demonstrates the mechanism (lookup purely by `sha`) but always uses the same org for signature and commit, so it doesn't exercise the cross-tenant case; the sibling test "verifies webhook signature" (lines 94-107) shows the per-org secret selection logic but likewise doesn't test payload/commit-owner mismatch.

### Impact Explanation
An attacker who has *any* Shipit-registered GitHub org (or who can trigger real webhooks from a repo they own, if Shipit is multi-org configured per `docs/setup.md` "Using Multiple Github Applications") can write arbitrary `Status` rows (state/description/target_url/context) onto commits belonging to other tenants' stacks, without needing the victim org's `webhook_secret`. This can: (a) flip a required/blocking CI context to `success`, directly satisfying `deployable?`/`Status::Group` logic used to gate deploys and (implicitly) rollback eligibility, and (b) inject attacker-controlled `description`/`target_url` strings that render in the victim stack's commit/task UI. This is a payload for one repository mutating another repository's commit/stack state — matching the "Critical: a payload for one repository mutating another's stack, commit, task, or team, or an unauthorized deploy" category.

### Likelihood Explanation
Preconditions: Shipit must be configured to authenticate more than one org (or the attacker otherwise has a valid `webhook_secret` for some org registered in the instance — a very plausible operational reality for shared Shipit deployments per `docs/setup.md`'s "Using Multiple Github Applications" section). The attacker needs to know the victim's commit `sha` and the victim stack's required status context name, both of which are public information (commit SHAs and CI context names are visible on GitHub/PRs). No Shipit session, API token, or the victim's `webhook_secret` is required. Cost is a single crafted HTTP POST to `/webhooks` with a valid signature for the attacker's *own* org — trivially repeatable against any commit whose SHA is known.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the authenticated org/repository instead of a bare `Commit.where(sha:)`: pass the verified `repository_owner`/`repository.full_name` through from the controller to each handler, and filter commits by `stack.repository` (or equivalent) matching that verified identity before calling `create_status_from_github!`. More generally, `WebhooksController#verify_signature` should not use attacker-supplied `repository.owner.login` alone to select the verification secret without also constraining downstream handlers to only mutate records belonging to that same, verified repository/org.

### Proof of Concept
Minitest plan (in `test/controllers/webhooks_controller_test.rb`, mirroring the existing ":state create a Status" test):
1. Set up two fixtures: `victim_stack` (org `"victim-org"`) with a commit `victim_commit` (known `sha`), and rely on the existing `shipit_stacks(:shipit)` fixture as `attacker-controlled` org (`"shopify"`, per `repository_params` helper).
2. Assert precondition (LHS/RHS of the binding before): `victim_commit.stack.repository.owner` (`"victim-org"`) != authenticated org in the request (`"shopify"`).
3. Stub `Shipit.github(organization: 'shopify')#verify_webhook_signature` to return `true` (as in existing tests, simulating attacker knowing only their own org's secret).
4. POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: victim_commit.sha, state: 'success', context: <victim's required status context>, target_url: 'http://evil.example', description: 'pwned' }.merge(repository: { owner: { login: 'shopify' } })`.
5. Assert: `victim_commit.statuses.reload.last.state == 'success'`, `target_url == 'http://evil.example'` — i.e., the RHS (org owning the mutated commit/stack) now diverges from LHS (org that authenticated), proving the binding is broken.
6. Additionally assert `victim_commit.stack.reload.deployable?` (or the relevant blocking-status check) flips to `true`/unblocked as a result, demonstrating the deploy/rollback-eligibility impact. [4](#0-3) [5](#0-4) [6](#0-5) [2](#0-1) [3](#0-2)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
