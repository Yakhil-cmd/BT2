### Title
Webhook signature verification authenticates against a different organization than the repository the payload writes to, allowing cross-org / cross-repository forged Push and Status events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate `X-Hub-Signature` against using `repository.owner.login` (falling back to `organization.login`) read straight out of the untrusted JSON body. Every downstream `Handler` (e.g. `PushHandler`, `StatusHandler`) instead resolves the actual `Repository`/`Stack` to mutate using a *different* field of the same untrusted body, `repository.full_name`. Because these two fields are never checked for consistency, an attacker who is a legitimate GitHub org admin for **any** organization configured in Shipit (and therefore knows that org's `webhook_secret`) can craft a payload that authenticates as their own org but names a victim org's repository, causing Shipit to sync commits or forge commit statuses for a repository/stack they have no authorization over.

### Finding Description
`verify_signature` computes the authenticating organization purely from the payload: [1](#0-0) [2](#0-1) 

It then fetches `Shipit.github(organization: repository_owner)` and checks the HMAC using that org's `webhook_secret` [3](#0-2) .

Once the signature check passes, `Handler#process` (invoked from `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `WebhooksController#create`) resolves the target repository from a **separate** field: [4](#0-3) 

`PushHandler` uses this to find stacks and call `stack.sync_github(expected_head_sha: params.after)`: [5](#0-4) 

`StatusHandler` uses `params.sha`, unrelated to `stacks`/`repository_name`, to attach a forged CI status to any commit matching that sha across the whole install: [6](#0-5) 

Shipit explicitly supports hosting multiple, independently-trusted GitHub organizations in one instance, each with its own `webhook_secret`, exactly the configuration documented in "Using Multiple Github Applications": [7](#0-6) 

The binding that should hold is: **organization that authenticated the request == organization owning the repository the handler writes to**. Before the attack, both fields are populated consistently by real GitHub webhooks. After the attacker's crafted POST, `repository.owner.login` (used for signature selection) is set to the attacker's own org (whose secret they legitimately know), while `repository.full_name` (used by `Handler#repository_name`) is set to a victim org/repo tracked by the same Shipit instance. The signature check passes because it's validated against the attacker's own org's secret, but the mutation happens against the victim's `Stack`.

### Impact Explanation
This crosses a repository trust boundary the app is supposed to enforce: an org that only controls its own GitHub App integration can act on stacks belonging to a completely different, unrelated organization/repository hosted on the same Shipit instance. Concretely:
- Via `PushHandler`, the attacker can trigger `Stack#sync_github` with an attacker-chosen `expected_head_sha` against a victim's branch/stack, causing Shipit to record/sync an arbitrary commit as the head of the victim's tracked branch.
- Via `StatusHandler`, the attacker can forge a green/`success` CI status (`commit.create_status_from_github!`) for any commit sha in the system, independent of which repo it belongs to, which can be used to make an otherwise-blocked victim commit appear "deployable" and get shipped through the normal deploy flow.

This satisfies the Critical bar of "cross-repository writes" / "unauthorized deploy" since it lets an attacker's org credentials manipulate state belonging to an unrelated repository.

### Likelihood Explanation
Requires that the Shipit instance is configured with more than one GitHub organization (a documented, common setup) and that the attacker controls (or is an admin of) at least one of those onboarded orgs, thus legitimately knowing that org's `webhook_secret` (which they themselves configured when installing their GitHub App). No access to the victim org, no Shipit session, and no API token are needed — only a raw HTTP POST to the public `/webhooks` endpoint with a forged JSON body and a correctly computed HMAC using their own org's secret. This is a moderate-likelihood but concrete exploit path limited to multi-org deployments.

### Recommendation
Do not trust `repository.owner.login`/`organization.login` from the payload in isolation to select the verifying secret while independently trusting a different payload field (`repository.full_name`) to select the mutated resource. After signature verification, re-derive and pin the "authenticated organization" and cross-check it against the owner of the repository resolved by `Handler#repository_name` (and `stacks`) before performing any write; reject the webhook if they don't match. Alternatively, resolve the repository/organization once from a single canonical, already-verified field and reuse that value throughout handler dispatch, rather than re-parsing the raw payload twice with different key paths.

### Proof of Concept
1. Shipit is configured with two orgs in `config/secrets.yml`: `org-attacker` (secret known to the attacker, who legitimately installed the GitHub App there) and `org-victim` (tracked stack `org-victim/app`), per the multi-org config documented in `docs/setup.md`.
2. Attacker computes `sha256`/`sha1` HMAC of a crafted JSON body using `org-attacker`'s `webhook_secret`:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already present in org-victim/app>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/app"
  }
}
```
3. Attacker POSTs this to `Shipit`'s public `/webhooks` endpoint with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed with org-attacker secret>`.
4. `verify_signature` looks up `Shipit.github(organization: 'org-attacker')` (from `repository.owner.login`) and the signature validates successfully.
5. `PushHandler#process` resolves `repository_name` as `org-victim/app` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack, an org the attacker has no legitimate access to.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
