### Title
Webhook handler repository resolution uses unauthenticated `repository.full_name`, allowing cross-org/cross-repository stack, commit, and check-run mutation - (File: app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the organization named in `repository.owner.login` (or `organization.login`), but `Handler#repository_name`/`#stacks` independently resolve the target `Repository` from `payload.dig('repository', 'full_name')` with no check that this value belongs to the verified organization. An attacker who controls (or can sign for) one configured GitHub org can therefore forge a webhook whose `repository.full_name` names a completely different, real repository, and every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) will mutate that victim repository's `Stack`/`Commit` records.

### Finding Description
The claimed binding is: `verified_organization == owning_organization_of(repository_name)`, where `verified_organization` is `repository_owner` used to pick the `GitHubApp` in `WebhooksController#verify_signature`, and `owning_organization_of(repository_name)` is the org portion of the `full_name` used by `Handler#repository_name`/`#stacks`.

Tracing the code:
- `WebhooksController#verify_signature` selects the app to authenticate with using `repository_owner`, defined as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and then verifies the HMAC signature with that app's secret [2](#0-1) .
- The full raw JSON body (unmodified) is then dispatched to every registered handler for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .
- Inside every `Handler`, `stacks` and `repository_name` derive the target repository purely from `payload.dig('repository', 'full_name')`, a field completely separate from `repository.owner.login`: [4](#0-3) .
- Nothing in `ExplicitParameters` schemas (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`) requires or checks that `repository.full_name`'s owner segment equals `repository.owner.login`/`organization.login`. [5](#0-4) [6](#0-5) [7](#0-6) 
- Additionally, `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the configured org has no `webhook_secret`: `return true unless webhook_secret` [8](#0-7) , so if any org in `Shipit.github_apps` lacks a secret, signing is not even required for that org.

Exploit request: attacker sends `POST /webhooks` with header `X-Github-Event: push` (or `status`/`check_suite`), body containing:
```json
{
  "repository": { "owner": {"login": "AttackerOrg"}, "full_name": "VictimOrg/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
signed (or, if `AttackerOrg` has a blank `webhook_secret`, unsigned/arbitrarily signed) so that `verify_signature` succeeds against `AttackerOrg`'s app. `Handler#repository_name` then reads `"VictimOrg/victim-repo"`, `Repository.from_github_repo_name` resolves the real victim `Repository`, and `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stacks [9](#0-8) , or `StatusHandler` writes a forged commit status via `commit.create_status_from_github!(params)` on any commit matching the attacker-supplied `sha` regardless of repository [10](#0-9) , or `CheckSuiteHandler` schedules check-run refreshes for a victim stack's commit [11](#0-10) .

None of the existing guards (`drop_unhandled_event`, `verify_signature`, `ExplicitParameters` schemas) cross-check `repository_owner` against `repository.full_name`'s owner segment, so the divergence is never detected.

### Impact Explanation
An attacker who controls or can sign for any single organization registered in `Shipit.github_apps` (or exploits one with a blank `webhook_secret`) can trigger state-changing webhook processing against any other repository/stack tracked by the same Shipit instance: forcing `sync_github` on an arbitrary stack/branch, injecting fabricated commit statuses via `StatusHandler`, or forcing check-run refresh scheduling via `CheckSuiteHandler`. This is exactly the "payload for one repository mutating another's stack, commit, task or team" scenario, matching Critical severity. It is repeatable per request against any repository whose `full_name` the attacker knows, and the blast radius spans every tenant/org configured on the shared Shipit instance since verification is organization-scoped but resolution is not.

### Likelihood Explanation
Requires only that at least two organizations be configured in `Shipit.github_apps` (a typical multi-tenant Shipit deployment) — either one lacking `webhook_secret` (silently bypasses signature check per `GitHubApp#verify_webhook_signature`), or the attacker legitimately administering one org's webhook secret (which they set/see when wiring up their own org's webhook). No Shipit session, API token, or GitHub push access to the victim repo is needed — only the ability to POST an HTTP request to `/webhooks`. This is low-cost and fully repeatable.

### Recommendation
In `Handler#repository_name`/`#stacks`, cross-check the resolved repository's owner against the organization that was actually used to verify the signature (pass `repository_owner`/verified org context down from the controller into `Handler.call`), and reject the event if they don't match. Additionally, require `webhook_secret` to be present for every configured `GitHubApp` (fail closed rather than `return true unless webhook_secret`).

### Proof of Concept
Parameterized minitest under `test/models/shipit/webhooks/handlers/` (per handler class):
1. Configure `Shipit.github_apps` with two orgs: `attacker-org` (real or blank `webhook_secret`) and `victim-org` (owns a real `Repository`/`Stack` fixture, e.g. `victim-org/victim-repo`).
2. Build a payload where `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/victim-repo"`, plus event-specific required fields (`ref`/`after` for push, `sha`/`state` for status, `check_suite.head_sha`/`head_branch` for check_suite).
3. Sign the raw JSON with `attacker-org`'s secret (or leave unsigned if blank) and `POST` to `/webhooks` with `X-Github-Event` set accordingly.
4. Assert `response.status == 200` (verification passed for `attacker-org`).
5. Assert the victim `Stack`/`Commit` was mutated: e.g., `stack.sync_github` was invoked (mock/spy), or a `Status` row was created on the victim commit, or `schedule_refresh_check_runs!` was called — proving `verified_organization` (`attacker-org`) != `owning_organization_of(repository_name)` (`victim-org`) yet the mutation still executed against `victim-org/victim-repo`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
