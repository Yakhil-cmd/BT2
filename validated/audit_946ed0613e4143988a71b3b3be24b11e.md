### Title
Webhook signature is verified against an attacker-controlled organization field while status/push handlers act on unrelated repositories and commits - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to validate an incoming webhook against using a field taken directly from the unauthenticated request body, while the event handlers that subsequently mutate state key off different payload fields that are never cross-checked against the field used for authentication. This breaks the binding "the organization whose secret authenticated the request" == "the repository/commit that gets written."

### Finding Description
`verify_signature` computes the signing organization purely from the incoming JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both attacker-controlled fields inside the unauthenticated HTTP body. This value is used only to pick the `webhook_secret` used to compute the HMAC (`Shipit.github(organization: repository_owner)`), not to constrain what the handlers subsequently act on.

Once the HMAC check passes, handlers derive the actual write target from entirely different, unverified fields:
- `Handler#repository_name` reads `payload.dig('repository', 'full_name')` to resolve the `Repository`/`Stack` [3](#0-2) 
- `StatusHandler#process` looks up commits *globally by `sha`* with no scoping to organization/repository at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) 
- `PushHandler#process` resolves stacks via `repository_name`/branch, independent of `repository_owner` [5](#0-4) 

Because Shipit's multi-tenant config allows separate GitHub Apps (and therefore separate `webhook_secret`s) per organization (`config/secrets.development.shopify.yml` shows two independent org entries, each with its own `webhook_secret`) [6](#0-5) , an actor who legitimately controls Organization A's GitHub App (and therefore knows Organization A's `webhook_secret`, which org owners/admins can read from their own GitHub App settings) can compute a valid signature for a payload whose `repository.owner.login` is `"OrgA"` (so it authenticates), but whose `repository.full_name` / commit `sha` point at a stack or commit belonging to an entirely unrelated Organization B tracked by the same Shipit instance. Nothing in `verify_signature` or the handlers re-checks that the authenticated organization actually owns the repository being written to.

### Impact Explanation
This crosses the "unauthorized deploy/rollback" bar identified in scope: `StatusHandler` writes arbitrary CI/status state (`create_status_from_github!`) onto any commit matched purely by `sha`, regardless of which org authenticated the webhook. Since Shipit gates deploys on required CI statuses (`ci.require` in `shipit.yml`, enforced through `Commit`/`CommitChecks`), an attacker who legitimately controls one organization's GitHub App can forge a "success" status for a commit belonging to a completely different, unrelated organization's stack hosted on the same Shipit instance, defeating that org's CI-gating and enabling an unauthorized deploy. Similarly `PushHandler` can trigger `sync_github` against another organization's stack, and other repository-scoped handlers (pull_request handlers, `check_suite_handler`) can be induced to act on repositories that were never associated with the authenticating organization. This is effectively a cross-repository/cross-organization write achieved without the actual owning organization's secret, matching the "cross-repository writes / unauthorized deploy" Critical impact bar.

### Likelihood Explanation
Requires the attacker to legitimately control (or compromise) at least one organization's GitHub App configured in the same multi-tenant Shipit deployment — a credential/repository boundary that is explicitly a normal, unprivileged tenant in a shared Shipit instance, not a Shipit session or `ApiClient` token. Given Shipit's documented multi-org support (`config/secrets.*.yml` supporting multiple independent orgs), this is a realistic deployment shape, and the only requirement is crafting a JSON body with mismatched `repository.owner.login` vs `repository.full_name`/`sha` — no other privilege is needed.

### Recommendation
After computing the authenticating organization from the payload and verifying the HMAC, re-validate that every field the handler subsequently writes to (repository full_name in `Handler#repository_name`, and especially the unscoped commit lookup in `StatusHandler`) actually belongs to that same authenticated organization/installation before performing any writes. Concretely, `StatusHandler` should scope its `Commit` lookup through the repository/stack associated with the authenticated organization rather than a bare `Commit.where(sha: ...)`, and `Handler#stacks`/`#repository_name` should reject payloads where `repository.full_name`'s owner does not match `repository_owner` used for signature verification.

### Proof of Concept
1. Attacker legitimately administers Organization A's GitHub App on a shared Shipit instance that also hosts Organization B's stacks, and thus knows Org A's `webhook_secret`.
2. Attacker crafts a `status` event body:
```json
{
  "sha": "<sha-of-a-commit-in-orgB/private-repo-currently-pending-ci>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" } }
}
```
3. Attacker computes `X-Hub-Signature` using Org A's known `webhook_secret` and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and the signature validates successfully [1](#0-0) .
5. `StatusHandler#process` matches the commit purely by `sha` (belonging to Org B) and records a fabricated "success" status on it [4](#0-3) , satisfying Org B's `ci.require` gate and enabling an unauthorized deploy of Org B's stack that Org A never had legitimate access to.
