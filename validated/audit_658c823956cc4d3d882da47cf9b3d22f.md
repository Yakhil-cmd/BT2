### Title
NonTransfer proxy is not a true superset of Auction proxy, allowing proxy-granted escalation to `Registrar::swap` - ([File: polkadot/runtime/rococo/src/lib.rs])

### Summary
`ProxyType::is_superset` in the Polkadot/Rococo/Westend/staking-async relay-chain runtimes unconditionally declares `NonTransfer` a superset of every other `ProxyType`, including `Auction`. However, `ProxyType::filter` for `NonTransfer` explicitly excludes `Registrar::swap` ("Specifically omitting Registrar `swap`") while `ProxyType::Auction::filter` admits the entire `Registrar(..)` call family, including `swap`. This is the exact "declared-superset admits less than the subset it claims to dominate" class of bug that was already found and fixed for `NonTransfer`/`Governance` in `asset-hub-westend` (regression tests `non_transfer_proxy_is_not_a_superset_of_governance` and `proxy_type_superset_relation_matches_call_filters`), but the same lattice violation still exists for `NonTransfer` vs `Auction` on the relay-chain runtimes.

### Finding Description
`pallet_proxy::do_proxy` only blocks a proxy from calling `add_proxy`/`remove_proxy` with a *stronger* proxy type when `!def.proxy_type.is_superset(proxy_type)`: [1](#0-0) 

For the relay-chain runtimes (`polkadot/runtime/rococo`, `polkadot/runtime/westend`, `substrate/frame/staking-async/runtimes/rc`), `is_superset` treats `NonTransfer` as dominating every other proxy type via a wildcard arm: [2](#0-1) 

But `NonTransfer`'s `filter` explicitly documents and enforces that `Registrar::swap` is *not* admitted: [3](#0-2) 

while `Auction`'s `filter` admits the unrestricted `Registrar { .. }` call family (which includes `swap`): [4](#0-3) 

The same pattern (wildcard `is_superset` for `NonTransfer`, `Registrar::swap` excluded from `NonTransfer::filter`, full `Registrar(..)` admitted by `Auction::filter`) is repeated in `polkadot/runtime/westend/src/lib.rs` (lines ~975-978, 1004-1010, 1022-1029) and `substrate/frame/staking-async/runtimes/rc/src/lib.rs` (lines ~1356-1362, 1392-1398, 1410-1418).

Because `do_proxy`'s guard only checks `is_superset` before allowing `add_proxy`/`remove_proxy`, and separately gates the `add_proxy`/`remove_proxy` call itself only through `def.proxy_type.filter(c)` (and `Proxy(..)` is fully admitted by `NonTransfer`), an account holding a `NonTransfer` proxy for a real account can add itself an `Auction` sub-proxy for that same real account — bypassing the explicit `NonTransfer` restriction against `Registrar::swap` and then dispatching `Registrar::swap` via the newly self-granted `Auction` proxy.

### Impact Explanation
This lets a delegate who was only granted the intentionally weaker `NonTransfer` proxy escalate to the `Auction` proxy type and invoke `Registrar::swap` on behalf of the real account — a capability the real account's grant explicitly excluded ("Specifically omitting Registrar `swap`" is a deliberate carve-out, mirroring the documented intent behind the already-fixed `Governance`/`NonTransfer` case). `Registrar::swap` affects para-id/lease assignment for the real account's parachain(s); an unintended holder gaining this ability is an authorization-consistency violation of the proxy lattice, matching CWE-863 (Incorrect Authorization) — the same class as the reported OpenClaw issue, where a weaker/adjacent authorization bucket (`DM pairing`) was silently treated as satisfying a stricter bucket (`group allowlist`). Here, `NonTransfer`'s claim of dominating `Auction` (via `is_superset`) is not backed by its actual `filter`, letting the "declared superset" self-grant the narrower type and use it to reach a call its own filter denies.

I was not able to fully confirm within this session the exact origin requirements of `Registrar::swap` itself (whether it requires `ensure_signed` plus a para-manager check, or `ensure_root`) — the file `polkadot/runtime/common/src/paras_registrar/mod.rs` uses both `ensure_signed` and `ensure_root` in different calls and I could not pin down `swap`'s specific check before the session ended. If `swap` requires `ensure_root`, this proxy-filter mismatch would be unreachable via a signed proxy path and the impact would be void; the explicit `// Specifically omitting Registrar swap` comment in the `NonTransfer` filter strongly implies `swap` is reachable by a signed (para-manager) origin — otherwise excluding it from a proxy filter would be meaningless — but this needs direct confirmation.

### Likelihood Explanation
Likelihood is Medium-Low: it requires an account to have already been granted a `NonTransfer` proxy by a real account that owns/manages a parachain registration, and requires `Registrar::swap` to actually be reachable via a non-root signed origin (unconfirmed above). No privileged role, governance action, or stolen keys are needed beyond the normal, intended `add_proxy` grant flow that real users perform routinely.

### Recommendation
Either (a) make `ProxyType::is_superset` for `NonTransfer` an explicit enumeration of dominated types the way it should conservatively deny `Auction` (or any type whose `filter` admits calls `NonTransfer::filter` denies), or (b) add the same lattice-consistency regression test already present for `asset-hub-westend` (`proxy_type_superset_relation_matches_call_filters`) to `polkadot/runtime/rococo`, `polkadot/runtime/westend`, and `substrate/frame/staking-async/runtimes/rc`, and fix any violations it surfaces (in particular `NonTransfer` vs `Auction` around `Registrar::swap`).

### Proof of Concept
Not executed. The structural mismatch is demonstrated purely by source inspection:
- `is_superset(NonTransfer, Auction) == true`: [2](#0-1) 
- `NonTransfer::filter` denies `Registrar::swap`: [3](#0-2) 
- `Auction::filter` admits full `Registrar(..)` (incl. `swap`): [4](#0-3) 
- `do_proxy` gate that permits the self-escalating `add_proxy`: [5](#0-4) 

A minimal FRAME integration reproduction (not run in this session) would: (1) have a real account grant a `NonTransfer` proxy to an attacker account; (2) attacker calls `Proxy::proxy(real, Some(NonTransfer), Proxy::add_proxy{delegate: attacker, proxy_type: Auction, delay: 0})` — expected to succeed under current `is_superset` logic; (3) attacker calls `Proxy::proxy(real, Some(Auction), Registrar::swap{...})` — expected to succeed since `Auction::filter` admits it. Execution against the actual `Registrar::swap` origin check was not performed, so the final reachability of step (3) through `Registrar::swap`'s own origin gate remains unverified in this session — this is the key remaining unknown that would need to be confirmed (via `polkadot/runtime/common/src/paras_registrar/mod.rs`) before treating this as a confirmed, exploitable escalation rather than a proven filter/superset lattice inconsistency (which is itself already established and documented by the codebase's own regression-test precedent for the sibling `NonTransfer`/`Governance` case).
