### Title
Unbounded-size oscript/AA formula strings cause disproportionate nearley-parser CPU consumption before any complexity limits apply - (File: formula/validation.js, formula/evaluation.js)

### Summary
CVE-2019-6785 is a Markdown-field DoS: GitLab fed an overly long, attacker-controlled string into a generic parser without a pre-parse size/complexity gate, causing disproportionate CPU consumption. `ocore` has the same structural pattern in its oscript/AA formula pipeline: any unprivileged unit poster (AA author, AA trigger sender, address-definition author) can embed a formula string inside a unit (AA definition `data`/`data_feed`/`payment`/output `if`/`init` fields, `definition_template`, `in data feed` address-definition clauses, etc.), and that raw string is fed straight into the nearley Earley parser with no formula-specific length or structural-complexity cap — the only limit is the generic whole-unit size cap (`MAX_UNIT_LENGTH`, up to 5MB).

### Finding Description
Formula strings extracted via `getFormula()` are parsed by `nearley.Parser` in two independent code paths, `formula/validation.js:exports.validate` and `formula/evaluation.js:exports.evaluate`, both of which call `parser.feed(formula)` unconditionally before any of the AA cost-control mechanisms (`MAX_COMPLEXITY`, `MAX_OPS`, `depth > 100` check) are applied: [1](#0-0) [2](#0-1) 

The complexity/op-count and recursion-depth guards (`MAX_COMPLEXITY`, `count_ops`, `depth > 100`) are enforced only while walking the already-parsed AST, i.e. strictly after the nearley parse has finished: [3](#0-2) [4](#0-3) 

Formula-bearing fields are widely reachable from a single posted unit without any privileged role: AA `data`, `data_feed`, `payment`, `poll`, `attestation`, output `if`/`init`, and message `init` fields all accept plain strings that are checked only with `getFormula()` (a lightweight `{...}` wrapper detector), not with any length limit on the wrapped formula text itself: [5](#0-4) [6](#0-5) 

The only outer bound on the size of such a string is the overall serialized unit size limit: [7](#0-6) 

Earley parsing (which nearley implements) has worst-case cubic time complexity (`O(n^3)`) for ambiguous or highly recursive grammars, and the oscript grammar (`formula/grammars/oscript.ne` / compiled `oscript.js`) contains many recursive/ambiguous productions (nested parentheses, chained `?:`/`otherwise`, arithmetic operator chains, `with_selectors`, nested arrays/dictionaries): [8](#0-7) 

Crafting a formula string close to the unit-size ceiling (megabytes) that maximizes parser ambiguity/backtracking (e.g., deeply nested parenthesized arithmetic expressions or ternary/otherwise chains) can force `nearley.Parser.feed()` to consume CPU time far out of proportion to normal formula sizes, before the formula's semantic complexity is even checked. Existing tests already show the codebase is aware that deeply nested constructs are problematic (they null out the result but still must parse/evaluate first), and none of them stress-test near-maximum-size adversarial ambiguous input: [9](#0-8) 

### Impact Explanation
Formula parsing happens synchronously as part of standard unit/AA-definition validation, which every full node must perform to accept and relay a unit and to execute an AA trigger. A single crafted unit (an AA definition, or a trigger to an AA containing string fields checked via `getFormula`, or an address definition using `in data feed`) can force every validating node to spend disproportionate CPU time in the nearley parser before rejecting or accepting the unit. This can stall a node's validation queue, delaying confirmation of other legitimate units on that node and, if propagated network-wide, degrade the network's ability to confirm new units in a timely manner — matching the "network unable to confirm new units" impact class in the validation rules.

### Likelihood Explanation
Any unprivileged actor who can post a unit (AA definition author, AA trigger sender, or address-definition author using formula-bearing conditions) can trigger this path with no special privileges, keys, or node compromise — only a specially crafted string within existing size limits (up to `MAX_UNIT_LENGTH`, several megabytes). No cooperation from other parties, oracles, or witnesses is required.

### Recommendation
- Impose an explicit maximum length on formula strings independent of the overall unit size limit, checked before invoking `nearley.Parser`/`parser.feed()` in both `formula/validation.js` and `formula/evaluation.js`.
- Consider bounding grammar recursion/nesting depth at the lexer/pre-parse stage (e.g., counting bracket/paren nesting) to avoid worst-case Earley parsing behavior on adversarially ambiguous input.
- Add a wall-clock or CPU-time budget around the parse step itself (not just AST evaluation) so a single formula cannot dominate validation time regardless of size.

### Proof of Concept
Construct an AA definition unit whose `data`/`data_feed` payload value (or an output `if`/`init` field) is a formula string of near-maximum allowed size composed of deeply nested, same-precedence, ambiguity-inducing constructs, e.g.:
```
"{" + "(".repeat(N) + "1" + ")".repeat(N) + "}"
```
or long chains of `otherwise`/ternary/arithmetic operators, where `N` is chosen so the whole unit stays under `MAX_UNIT_LENGTH` but the formula substring is large (hundreds of KB to a few MB). Post this as an AA-definition-bearing unit (`aa_validation.js` `validateAADefinition` → `getFormula` → `formulaValidator.validate` → `nearley.Parser.feed`). Measure validation CPU time versus formula length to confirm super-linear growth prior to any `MAX_COMPLEXITY`/`MAX_OPS` rejection.

Note: I was not able to fully verify the exact worst-case asymptotic behavior of the specific compiled `oscript.js` grammar (this would require running/profiling the nearley table, which is outside static analysis) — the finding is based on the well-documented worst-case behavior of Earley parsers on ambiguous/recursive grammars combined with the confirmed absence of a pre-parse formula-length gate in the reviewed code paths.
