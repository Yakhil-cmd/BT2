### Title
Cross-stack disclosure via ccmenu API token: token minted for one stack reads any stack's deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The `ApiClient` created by `CCMenuUrlController#fetch` for a stack's CCTray URL is never bound to that stack, and `Api::CCMenuController#stack` overrides the base controller's stack-scoping to query `Stack.from_param!` directly instead of the client-scoped `stacks` relation. As a result, any valid ccmenu query-string token — regardless of which stack it was generated for — can be replayed against `/api/stacks/:other_stack_id/ccmenu.xml?token=...` to read another stack's deploy/task status.

### Finding Description
Claimed binding: `stack accessed == current_api_client.stack_id` (i.e. a ccmenu token should only unlock the stack it was minted for).

Actual code:
- `CCMenuUrlController#client` creates the `ApiClient` with only `permissions: %w[read:stack]` and never sets `stack:`, so `current_api_client.stack_id` is `nil` for every ccmenu client: [1](#0-0) .
- `Api::BaseController#stacks` would scope by `current_api_client.stack_id` only if it were present: [2](#0-1) . Since `stack_id` is nil, `stack_id?` is false and the fallback is `Stack.all` — no scoping occurs at all for this client type.
- On top of that, `Api::CCMenuController` overrides `stack` entirely, bypassing even the (already non-functional) scoped `stacks` helper and resolving any `stack_id` param against the full `Stack` table: [3](#0-2) .
- `authenticate_api_client` in this controller accepts the token straight from `params[:token]` with no header requirement, confirming it is designed for unauthenticated CCMenu/CCTray clients: [4](#0-3) .
- `require_permission :read, :stack` only checks the coarse `read:stack` permission string via `ApiClient#check_permissions!`, which has no notion of *which* stack — it just checks `permissions.include?("read:stack")`: [5](#0-4) .

Exploit flow: an operator with access to a Shipit stack A calls `CCMenuUrlController#fetch` (e.g. clicking "CCMenu URL" in stack settings) and receives a URL containing `client.authentication_token`. Because this token is not stack-bound, an attacker who obtains that URL/token (via a shared or forwarded ccmenu link, e.g. added to a monitoring dashboard) can send `GET /api/stacks/<stack_B>/ccmenu.xml?token=<token>` for any other stack `B` on the same Shipit instance and receive stack B's `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc., none of which the token holder was ever granted access to.

Existing guards fail because: `require_permission!` only checks the flat `read:stack` string, not a specific stack; `stacks`/`stack_id?` scoping in the base controller is dead code for this client type since `stack_id` is never populated; and `Api::CCMenuController#stack` doesn't even use the scoped `stacks` helper.

### Impact Explanation
An attacker who obtains a single ccmenu token (which is unauthenticated/unsigned beyond `ApiClient.authenticate`, i.e. requires no session, no GitHub credentials, no `api_clients_secret`) can read task/deploy state — build status, last build label, activity, web URL — for **any stack on the Shipit instance**, not just the one the token was issued for. This is repeatable indefinitely against arbitrary `stack_id` values and matches the High severity category "unauthenticated read of stack state, task streams or deploy output." It is not restricted to a single tenant/repository; it spans every stack hosted by the instance.

### Likelihood Explanation
Preconditions: the attacker needs to obtain one valid ccmenu token, which is routinely embedded in plaintext URLs meant to be pasted into external CCTray-compatible monitoring tools, shared over chat, or added to dashboards — a realistic disclosure vector already anticipated by the question ("shared/forwarded ccmenu link"). No Shipit secrets, sessions, or GitHub credentials are needed once a token leaks. The cost to enumerate other `stack_id`s is trivial since stack params are typically `owner/repo/branch`-style human-readable slugs. This is a low-cost, highly repeatable attack once any single token is exposed.

### Recommendation
- Bind the `ApiClient` created in `CCMenuUrlController#client` to the specific stack (`stack: stack`) at creation.
- Restore stack scoping in `Api::CCMenuController#stack` to use the base controller's `stacks` relation (scoped by `current_api_client.stack_id`) instead of unscoped `Stack.from_param!`.
- Consider making `check_permissions!`/`require_permission!` aware of the target stack for stack-bound clients, rejecting access when `current_api_client.stack_id.present? && current_api_client.stack_id != stack.id`.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a ccmenu token minted for stack A cannot read stack B" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.create!(owner: 'other', name: 'repo'), branch: 'main')

  # Simulate CCMenuUrlController#client: a token-holding ApiClient with read:stack,
  # not associated to any particular stack (mirrors current implementation).
  client = ApiClient.create!(creator: users(:walrus), name: 'CCMenu Client', permissions: %w[read:stack])
  token = client.authentication_token

  get :show, params: { stack_id: stack_b.to_param, token: token }

  assert_response :ok
  project = Hash.from_xml(response.body)['Projects']['Project']
  assert_equal stack_b.to_param, project['name'] # leaks stack B despite token never being scoped to B
end
```
This demonstrates that possessing a valid ccmenu token (as generated by `CCMenuUrlController#fetch`) is sufficient to read any stack's status, violating the intended per-stack scoping.
