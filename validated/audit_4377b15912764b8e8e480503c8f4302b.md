### Title
API-scoped `read:stack` token can read the CC-Menu build status of any stack, not just the one it is authorized for - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`ApiClient` records can be scoped to a single stack via their `stack_id` column, and `Shipit::Api::BaseController` enforces this scope by resolving stacks through the `stacks`/`stack` helpers, which filter by `current_api_client.stack_id` when present. `Shipit::Api::CCMenuController` overrides `stack` to bypass this scoping, resolving the stack directly from the request param instead of the token-restricted collection, breaking the binding `token.authorized_stack == stack_acted_on`.

### Finding Description
`Shipit::Api::BaseController` centralizes stack scoping for API tokens: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the authenticated `ApiClient` is scoped to a specific stack, and `stack` resolves `params[:stack_id]` only within that restricted set. This is the mechanism that guarantees a token scoped to Stack A cannot act on Stack B.

`CCMenuController`, however, overrides both `authenticate_api_client` (to also accept a `token` query parameter, used for the public/unauthenticated CI status badge use case) and, critically, overrides `stack` to bypass the scoped `stacks` helper entirely: [2](#0-1) 

Because `stack` here calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(params[:stack_id])`, the `current_api_client.stack_id` scope enforced elsewhere in the same controller hierarchy is never applied. `require_permission :read, :stack` only checks that the token's `permissions` array contains `read:stack` (a capability check via `ApiClient#check_permissions!`); it performs no ownership/scope check on which stack is being accessed: [3](#0-2) 

So the equality that should hold — "the stack a token authorizes" == "the stack the request actually touches" — is broken specifically in this controller. Any valid token with the `read:stack` permission (regardless of its `stack_id` binding) can supply an arbitrary `stack_id` param and retrieve that other stack's CI/build status XML.

### Impact Explanation
This matches the "High" bucket: unauthenticated/under-scoped read of stack state. A token deliberately scoped to a single stack (e.g., generated for a public CCMenu badge on Stack A, as done in `CCMenuUrlController#client`) can be replayed with a different `stack_id` to disclose another stack's last build/deploy status, lock state, and existence — information the token issuer never intended to expose for other stacks. Because `CCMenuUrlController` embeds the raw `authentication_token` in a URL meant to be handed out to third parties/dashboards (e.g., CI status widgets), this token is more likely to leak or be shared outside the trust boundary than an interactive-session token, making the scope bypass more consequential in practice. [4](#0-3) 

### Likelihood Explanation
Exploitation only requires possession of any `read:stack`-permissioned `ApiClient` token (including the low-privilege ones self-service-created via the CCMenu badge flow) and knowledge/guessing of another stack's `to_param` (owner/name/environment), which is not secret. No additional credentials, GitHub access, or session are needed beyond the token itself.

### Recommendation
Make `CCMenuController#stack` resolve through the same scoped `stacks` collection as `BaseController`, e.g. `stacks.from_param!(params[:stack_id])`, so that a stack-scoped token cannot resolve a stack outside its `stack_id` binding, consistent with how `require_permission` is expected to compose with scope enforcement elsewhere in the API.

### Proof of Concept
1. As a Shipit user, visit a stack's page and trigger the CCMenu URL flow (`GET /stacks/:stack_id/ccmenu.xml` fetch), which creates/reuses an `ApiClient` with `permissions: ['read:stack']` (see `CCMenuUrlController#client`) and returns a URL like `.../ccmenu.xml?token=<TOKEN>` scoped conceptually to Stack A.
2. Take that `<TOKEN>` and issue: `GET /api/stacks/<STACK_B_ID>/ccmenu.xml?token=<TOKEN>` where `STACK_B_ID` is a different, unrelated stack.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unscoped, the request succeeds and returns Stack B's CI project XML (build status, last build label, activity), even though the token was never authorized for Stack B.

    def fetch

    end

    def client
