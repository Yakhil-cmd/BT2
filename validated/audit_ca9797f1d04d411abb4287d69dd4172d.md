### Title
Membership webhook does not bind `team.id` to the verifying organization, allowing cross-org `Membership` injection into any pre-existing `Shipit.github_teams` team - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up `Team` solely by the global, attacker-supplied `params.team.id`, with no check that the team belongs to the organization whose `webhook_secret` verified the request. An attacker who controls their own GitHub org (and its Shipit `webhook_secret`) can submit a `membership` webhook naming any existing victim team's `github_id`, causing `team.add_member(member)` to attach an attacker-controlled user to that victim `Team`.

### Finding Description
The claimed binding is: `Membership(team_id=T, user_id=U)` exists in Shipit ⟺ GitHub actually reports `U` as a member of team `T`, where `T ∈ Shipit.github_teams`.

Trace:
- `Shipit::WebhooksController#verify_signature` picks the HMAC secret via `Shipit.github(organization: repository_owner)`, where `repository_owner` is `params.dig('organization', 'login')` for membership events [1](#0-0) [2](#0-1) . This means signature verification only proves the request was signed with the secret belonging to the org named in `organization.login` — which an attacker fully controls, since it is their own org.
- `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id)`, keyed only on the global numeric `github_id`, with no check that `params.organization.login` matches the found/created `Team#organization` [3](#0-2) . If a `Team` row with that `github_id` already exists (e.g., the victim org's team, previously created via a legitimate webhook), `find_or_create_by!` returns the existing record and the initialization block (which sets `organization`) never runs.
- `team.add_member(member)` then appends `member` — a `User` created purely from the attacker-supplied `params.member.login` via `User.find_or_create_by_login!` [4](#0-3)  — to `Team#members` [5](#0-4) .
- If that victim `Team`'s id is listed in `Shipit.github_teams`, `User#authorized?` becomes true for the attacker's user without them ever being a real member of the victim org [6](#0-5) [7](#0-6) .

None of the existing guards prevent this: `verify_webhook_signature` only checks HMAC against the secret for the org named in the payload, not that the payload's `team.id` is owned by that org [8](#0-7) ; `drop_unhandled_event`/`ExplicitParameters` only validate shape/presence, not cross-org ownership [9](#0-8) .

### Impact Explanation
An attacker gains an unauthorized `Membership` row linking their own `User` to a victim `Team` that may be one of the teams gating access via `Shipit.github_teams`, which is used by `force_github_authentication`/`User#authorized?` to grant application access [10](#0-9) . This is repeatable for any `team.id` the attacker knows/guesses and matches the High-severity category "escalation into `Shipit.github_teams` authorization." It does not by itself grant `Command`/`PTY.spawn` execution, but it is a durable authorization bypass affecting a separate tenant/org's access control.

### Likelihood Explanation
Preconditions: attacker must operate a GitHub org configured in Shipit with its own `webhook_secret` (satisfiable by any org owner who installs the Shipit webhook for `membership` events on their own org — no privileged Shipit credentials needed), and must know/guess the victim `Team`'s numeric `github_id` (GitHub team ids are visible via the public Teams API for visible teams, or leak through prior legitimate webhook deliveries, making them not secret). Given that, the attack is a single crafted, correctly-signed HTTP POST to `/webhooks`, fully repeatable against any `Team` row already present in Shipit's database.

### Recommendation
In `MembershipHandler#find_or_create_team!`, when a `Team` is found (not created) by `github_id`, verify `team.organization == params.organization.login` (case-insensitively) before proceeding, and raise/reject (or treat as a mismatch to be logged and dropped) rather than silently reusing the existing record. Additionally, harden `verify_signature`/`Team.find_or_create_by!` so team lookups are scoped by `(github_id, organization)` rather than `github_id` alone.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/membership_handler_test.rb`, hypothetical):
1. Seed `victim_team = Team.create!(github_id: 424242, organization: 'shopify', slug: 'developers', name: 'Developers')`, matching `shipit_teams(:shopify_developers).github_id` from fixtures.
2. Add `victim_team.id` (or its `github_id`) to a stubbed `Shipit.github_teams` list so it participates in authorization.
3. Build a `membership` webhook payload signed with an **attacker org's** webhook secret (`Shipit.github(organization: 'attacker-org')`), with:
   - `organization.login = 'attacker-org'`
   - `team = { id: 424242, name: 'Developers', slug: 'developers', url: '...' }` (same `github_id` as `victim_team`)
   - `member.login = 'attacker-user'`
   - `action = 'added'`
4. Assert before: `Membership.where(team: victim_team, user: User.find_by(login: 'attacker-user')).exists?` is `false`, and `victim_team.organization == 'shopify'`.
5. Invoke `Shipit::Webhooks::Handlers::MembershipHandler.call(payload)` (or POST to `/webhooks` with the attacker-org signature header).
6. Assert after: `Membership.where(team: victim_team, user: User.find_by(login: 'attacker-user')).exists?` is `true`, and `victim_team.reload.organization` is still `'shopify'` (proving the attacker's payload attached to the victim's org team despite `organization.login` being `'attacker-org'`) — demonstrating the equality "Membership reflects real GitHub-reported membership for `Shipit.github_teams` team" is broken.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
