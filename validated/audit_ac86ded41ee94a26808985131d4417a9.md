### Title
Webhook signature verification keys off an attacker-controlled `repository.owner.login` field that is decoupled from the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GithubApp` instance (and therefore the `webhook_secret` used to validate `X-Hub-Signature`) using a value read straight out of the untrusted JSON body — `repository.owner.login` — while the handlers invoked immediately afterwards act on a different field of that same body (the repository's `full_name`) to decide which `Stack`/`Repository` to mutate. The signature is verified against the *organization named in the payload*, not against the *repository that will actually be written to*.

### Finding Description
`verify_signature` computes the verification key from a value the attacker fully controls: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` — an unauthenticated, self-reported field inside the very payload whose signature is being checked. `Shipit.github(organization: repository_owner)` looks up a `GithubApp` per configured organization, and each organization can independently have no `webhook_secret` configured, which is an explicitly supported configuration: [3](#0-2) 

`verify_webhook_signature` returns `true` unconditionally — regardless of the signature header — whenever the selected organization's `webhook_secret` is blank. Multiple organizations can be configured on one Shipit install, and secrets are per-organization (`config/secrets.development.shopify.yml` shows two independent org blocks, each with its own optional `webhook_secret`).

Once `verify_signature` passes, `create` dispatches the *entire* untrusted payload to event handlers: [4](#0-3) 

Those handlers determine the target `Stack`/commit from other fields of the same payload (e.g. `repository.full_name`, `sha`, `state`) rather than from `repository_owner`. The test suite confirms the repository actually processed is taken from `repository.full_name`, independent of the field used above for signature-org selection: [5](#0-4) 

This breaks the binding: `organization authenticated by verify_signature` ≠ `repository whose Stack/commit state gets written by the event handler`. An attacker can set `repository.owner.login` (or `organization.login`) to any organization configured on the Shipit instance that happens to have no `webhook_secret` set, while pointing `repository.full_name` / `sha` / `state` at a *different*, protected organization's stack. `verify_webhook_signature` short-circuits to `true` for the spoofed organization, and the forged payload is then processed as if it had been legitimately signed by GitHub for the real target repository.

### Impact Explanation
The `status` webhook handler creates a `Shipit::Status` record straight from attacker-controlled `sha`/`state`/`context` fields once signature verification is bypassed this way. Stacks that gate deploys behind `ci.require` status contexts (`README.md` "ci.require") can have their CI gate satisfied by a forged "success" status for an arbitrary commit on a protected repository, enabling an unauthorized deploy through Shipit's normal continuous-deployment path — without possessing any `webhook_secret`, `ApiClient` token, or GitHub credentials for the targeted repository/organization. This matches the "unauthorized deploy" high-impact criterion.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured with at least two GitHub organizations where one has no `webhook_secret` set — an explicitly documented, supported configuration (`docs/setup.md`, `config/secrets.development.shopify.yml`). Given that condition, the attack is a single unauthenticated HTTP POST to `/webhooks` with a crafted JSON body; no signature, session, or token is required.

### Recommendation
Verify the webhook signature using the secret belonging to the organization that actually owns the repository being mutated by the handler (i.e., derive the verification key from the same repository identity the handler will act on), or require every configured organization to have a non-blank `webhook_secret` and refuse verification when one is absent instead of returning `true`.

### Proof of Concept
1. Configure a Shipit instance with two organizations: `victim-org` (has `webhook_secret` set, hosts the real protected stack) and `attacker-org` (no `webhook_secret`, or any org not requiring one).
2. POST to `/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature` for `victim-org`, and body:
```json
{
  "sha": "<victim-org commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "full_name": "victim-org/protected-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: 'attacker-org')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. The `status` handler creates a `Status` for the commit in `victim-org/protected-repo` using the forged `state`/`context`, satisfying any `ci.require` gate for that stack without ever presenting a valid signature for `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
