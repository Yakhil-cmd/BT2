Based on my investigation, the strongest analog to the ERC165Checker bug class (a function contractually expected to always return a boolean but able to revert/throw instead) in this codebase is `signature.verifyMessageWithPemPubKey` in `signature.js`, called from the `is_valid_sig` oscript operator in `formula/evaluation.js`.

### Title
`verifyMessageWithPemPubKey` can throw an uncaught exception instead of returning `false`, crashing formula evaluation for `is_valid_sig` - ([File: signature.js])

### Summary
`verifyMessageWithPemPubKey` is invoked from the `is_valid_sig` oscript function, whose contract (like `ERC165Checker.supportsInterface`) is to always resolve to a boolean via `cb(result)`, never to throw. The function contains unguarded buffer parsing logic before its `try/catch` block, unlike its sibling helper `verifyMessageWithSecp256k1PemPubKey`, which wraps all parsing in `try/catch`.

### Finding Description
In [1](#0-0) , `verifyMessageWithPemPubKey` strips PEM headers and decodes to a DER buffer, then computes `algIdStart` by indexing into `der[1]` and slicing/comparing bytes — all *outside* any `try/catch`: [2](#0-1) 
Only the final `verify.verify(...)` call at the bottom is wrapped in `try/catch` (lines 42-47). Compare this with `verifyMessageWithSecp256k1PemPubKey`, where the entire body, including buffer indexing/slicing, is wrapped in `try/catch` and defensively returns `false` on any exception [3](#0-2) .

This function is called from the `is_valid_sig` case in the oscript formula evaluator: [4](#0-3) 
Crucially, the call site does **not** wrap `signature.verifyMessageWithPemPubKey(...)` in a `try/catch` either — it assumes the function can never throw, exactly mirroring the incorrect assumption in the ERC165Checker advisory (`abi.decode` "always successfully decodes").

While the PEM key passed here has already gone through `validateAndFormatPemPubKey`, which performs its own independent structural checks (sequence tag `0x30`, second sequence marker, identifier length whitelist) in [5](#0-4) , this is a separate, duplicated parsing implementation from the one in `verifyMessageWithPemPubKey`. Any divergence between the two implementations, or a corner case not covered by `validateAndFormatPemPubKey`'s checks (e.g., a `contentAloneB64` value whose length is not a multiple that survives `Buffer.from(..., 'base64')` decoding to the same byte layout assumed downstream, or a valid identifier-length combination for which `algIdStart`/`der.slice` indexing hits an unexpected edge), can result in `verifyMessageWithPemPubKey` throwing synchronously and propagating an uncaught exception out of the oscript evaluator.

### Impact Explanation
Because `evaluate()` in `formula/evaluation.js` calls this synchronously inside a callback chain without a `try/catch`, an uncaught exception here would propagate up through the AA formula evaluator. Since `is_valid_sig` is reachable from any AA definition/trigger and from address-definition `formula` clauses (per `formula/validation.js` and `definition.js` allowing `is_valid_sig`), a malicious AA author or unit poster could craft a PEM key value that reaches this unguarded code path and crashes/throws during unit or AA-response validation. If the exception is not caught by a top-level handler, this could crash the node process or, if caught inconsistently across versions, cause different nodes to disagree on whether a given unit/AA trigger is valid — a node-disagreement / DoS scenario analogous to the "revert instead of returning false" class from the advisory.

### Likelihood Explanation
This is a reachable, attacker-controlled path: `is_valid_sig(message, pem_key, sig)` takes fully attacker-supplied strings (e.g., from `trigger.data`), as demonstrated extensively in `test/pem_sig.test.js`. However, likelihood is tempered by the fact that `validateAndFormatPemPubKey` already performs several structural checks before `verifyMessageWithPemPubKey` is called, so triggering an actual throw would require finding a PEM/DER byte layout that passes the first validator's checks but still breaks an assumption in the second parser's unguarded indexing/slicing logic. I could not construct or confirm a concrete byte sequence that achieves this within the scope of static analysis — this is the main uncertainty in this finding.

### Recommendation
Wrap the header-stripping/DER-parsing logic in `verifyMessageWithPemPubKey` (lines 27-36) in the same defensive `try/catch` pattern used in `verifyMessageWithSecp256k1PemPubKey`, returning `false` on any exception, and/or wrap the call site in `formula/evaluation.js` (line 1728) in a `try/catch` that resolves to `false` on error — consistent with how `is_valid_merkle_proof` and other formula operators already guard external verification calls with `try { ... } catch (e) { res = false; }` (see `formula/evaluation.js` lines 1798-1803).

### Proof of Concept
Not conclusively demonstrated: I identified the structural gap (unguarded parsing code before the `try` block, and an unguarded call site) but was unable to construct or verify, within available tools, a specific `pem_key` payload that (a) passes `validateAndFormatPemPubKey`'s independent checks and (b) still triggers a thrown exception in `verifyMessageWithPemPubKey`'s `der[1]`/`der.slice(...).equals(...)` logic. Confirming exploitability would require constructing/testing a boundary-case DER buffer (e.g., at the edges of the `identifiersLength` whitelist values 13/16/19/20) against both parsers side by side.

	var contentB64 = pem_key

		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");

function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;

		var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
		var sigBytes = Buffer.from(signature, encoding);
		var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
		var compactSig = Buffer.from(ecdsa.signatureNormalize(rawCompact));

		var msgBuf = Buffer.isBuffer(message) ? message : Buffer.from(message);
		var hash = crypto.createHash('sha256').update(msgBuf).digest();
		return ecdsa.ecdsaVerify(compactSig, hash, pubkey);
	} catch(e) {
		console.log('secp256k1 pem verify exception: ' + e);
		return false;
	}
}

function validateAndFormatPemPubKey(pem_key, algo, handle, bPostPemCurvesFix) {

	if (!ValidationUtils.isNonemptyString(pem_key))
		return handle("pem key should be a non empty string");

	//we remove header and footer if present
	var contentAloneB64 = pem_key.replace("-----BEGIN PUBLIC KEY-----", "").replace("-----END PUBLIC KEY-----", ""); 
	
	//we remove space, tab space or carriage returns
	contentAloneB64 = contentAloneB64.replace(/\s/g, "");

	if (contentAloneB64.length > 736) // largest is RSA 4096 bits
		return handle("pem content is too large");

	if (!ValidationUtils.isValidBase64(contentAloneB64))
		return handle("not valid base64 encoding" + contentAloneB64);

	var contentAloneBuffer = Buffer.from(contentAloneB64, 'base64');

	if (contentAloneBuffer[0] != 0x30)
		return handle("pem key doesn't start with a sequence");

//we determine start and length of algo/curve identifiers
	if (contentAloneBuffer[1] <= 0x7F){
		if (contentAloneBuffer[2] != 0x30)
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 4;
		var identifiersLength = contentAloneBuffer[3];
	} else if (contentAloneBuffer[1] == 0x81){
		if (contentAloneBuffer[3] != 0x30) 
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 5;
		var identifiersLength = contentAloneBuffer[4];
	} else if (contentAloneBuffer[1] == 0x82){
		if (contentAloneBuffer[4] != 0x30) 
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 6;
		var identifiersLength = contentAloneBuffer[5];
	} else {
		return handle("wrong length tag");
	}

	//we decode the length of identifiers
	if (identifiersLength != 13 && identifiersLength != 16 && identifiersLength != 19 && identifiersLength != 20)
		return handle("wrong identifiers length" + identifiersLength);

	//we isolate the identifiers
	var contentAloneHex = contentAloneBuffer.toString('hex')
	var typeIdentifiersHex = contentAloneHex.slice(identifiersStart * 2, identifiersStart *2 + identifiersLength *2);

	if (!objSupportedPemTypes[typeIdentifiersHex])
		return handle("unsupported algo or curve in pem key");

	if (bPostPemCurvesFix && !objSafePemTypes.has(typeIdentifiersHex))
		return handle("unsupported curve after pem curves fix MCI");

	if (algo != "any"){
		if (algo == "ECDSA" && objSupportedPemTypes[typeIdentifiersHex].algo != "ECDSA")
			return handle("PEM key is not ECDSA type");
		if (algo == "RSA" && objSupportedPemTypes[typeIdentifiersHex].algo != "RSA")
			return handle("PEM key is not RSA type");
	}

	if (objSupportedPemTypes[typeIdentifiersHex].algo == "ECDSA" && objSupportedPemTypes[typeIdentifiersHex].hex_pub_key_length != (contentAloneHex.length - identifiersStart * 2 - identifiersLength *2 - 8))
		return handle("wrong key length");

	//we add back header and footer
	pem_key =	"-----BEGIN PUBLIC KEY-----" + "\n";
	pem_key += contentAloneB64+"\n";
	pem_key += "-----END PUBLIC KEY-----";
	return handle(null,pem_key);
