### Title
Cross-organization commit-status forgery via unscoped `StatusHandler` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate an inbound webhook against using `repository_owner`, a value read directly out of the (still-unverified) JSON body: `params.dig('repository', 'owner', 'login')`. [1](#0-0) [2](#0-1)  Once the HMAC check passes for *that* organization, the raw payload is dispatched to per-event handlers with no further scoping by the engine. [3](#0-2) 

Most handlers correctly re-derive the acted-on `Stack`/`Repository` from the *same* `repository.full_name` field that is part of the signed body, via `Handler#stacks`: [4](#0-3) 

`StatusHandler`, however, does not use that scoping at all. It looks up commits **globally by SHA** across every stack/repository in the installation:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

In a multi-organization Shipit deployment (the documented setup explicitly supports several GitHub organizations, each with its own `webhook_secret`) [6](#0-5)  an actor who legitimately owns/administers **one** configured organization (and therefore knows/controls that organization's real `webhook_secret`, set when they create their own GitHub App per the setup docs) can craft and correctly sign a `status` event whose `repository.owner.login` matches their own org (making `verify_signature` pass), while the `sha` field names a commit that actually belongs to a **different** organization's stack. Because `StatusHandler` never checks that the commit's stack corresponds to the repository/organization that was authenticated, the forged status is written onto that unrelated commit.

### Finding Description
This mirrors the reported bug class: a verified/authenticated identity (the organization whose signature was checked) is silently divorced from the entity actually mutated (the commit/stack the status is written to). The signature only proves "this request's `webhook_secret` belongs to org X"; it says nothing about which commit the payload's `sha` may reference, and `StatusHandler` performs no additional binding check between "org X" and "the commit's owning repository/stack." Every other default handler (`PushHandler`, `CheckSuiteHandler`, pull request handlers) resolves its target scope through `Repository.from_github_repo_name(repository_name)` using the same `repository.full_name` field that is inside the signed body, so the org-authenticated-vs-target relationship stays consistent for them. `StatusHandler` breaks that invariant by keying purely off the globally-unique-but-unscoped `sha` string.

Commit SHAs are not secrets — they are visible in Shipit's own UI/API (task/deploy pages, commit lists) and, for any repository hosted on github.com, in the public/private repo itself to anyone with read access, including members of unrelated organizations hosted on the same Shipit instance.

### Impact Explanation
This is a cross-repository/cross-organization write: an actor authenticated only for organization X can inject arbitrary CI status data (`state`, `description`, `target_url`, `context`) onto commits belonging to organization Y's stacks, via `Commit#create_status_from_github!`. [7](#0-6)  Commit statuses feed into Shipit's release/status tracking (`last_release_status`, `create_release_status!`) which stacks use to gate operator-visible CI state and, in typical Shipit configurations, deploy eligibility. [8](#0-7)  Forging a passing status on a commit in an org the attacker has no legitimate access to can therefore falsify the CI signal an operator relies on before shipping that commit — an unauthorized-deploy-adjacent write that falls squarely in the "cross-repository writes" Critical category, independent of whether the attacker can trigger the deploy themselves.

### Likelihood Explanation
Requires the attacker to already be a legitimate holder of a valid `webhook_secret` for *some* organization configured on the shared Shipit instance (a realistic scenario for any multi-tenant deployment, since org onboarding, not admin trust of a single privileged operator, is what the `secrets.yml` structure documents). No `ApiClient` token, session, or GitHub App private key for the *victim* organization is needed — only the attacker's own, legitimately-issued organization credentials plus a known/guessable commit SHA belonging to the victim stack.

### Recommendation
Scope `StatusHandler#process` (and any other handler relying on global identifiers such as commit SHA) to the repository named in the same signed payload, mirroring `Handler#stacks`/`Repository.from_github_repo_name(repository_name)`, before updating any `Commit` record — i.e., restrict the `Commit.where(sha: params.sha)` lookup to commits whose `stack.repository` matches `payload.dig('repository', 'full_name')`.

### Proof of Concept
1. Attacker legitimately administers GitHub org `EvilOrg`, which is configured in Shipit's `secrets.yml` with `webhook_secret = S`.
2. Attacker learns (via Shipit UI, public repo browsing, etc.) a commit SHA `deadbeef...` belonging to `VictimOrg/victim-repo`, tracked by a `VictimOrg` stack.
3. Attacker computes `HMAC-SHA1(S, body)` for a payload:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "repository": {"owner": {"login": "EvilOrg"}}
}
```
4. `POST /webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`. `verify_signature` resolves `Shipit.github(organization: "EvilOrg")` and validates successfully. [1](#0-0) 
5. `StatusHandler.process` finds `Commit.where(sha: "deadbeef...")` — the `VictimOrg` commit — and records the forged `"success"` status against it. [9](#0-8)
