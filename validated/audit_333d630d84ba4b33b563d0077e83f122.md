### Title
Autonomous Agent price/data-feed reads default to unstable, not-yet-finalized AA-posted values, enabling within-cascade price manipulation - ([File: data_feeds.js])

### Summary
`readDataFeedValue()` is invoked from oscript's `data_feed[[...]]` operator with `unstable_opts = bAA` [1](#0-0) , so any AA reading a data feed automatically considers data-feed messages from units authored by AAs that are still **unstable** (not yet included in a stabilized main-chain index), in addition to permanently committed values [3](#0-2) . This is the oscript analog of Sturdy's read-only-reentrancy exploit: a price/value can be read and acted upon before the underlying state that produced it has become final/immutable.

### Finding Description
`readDataFeedValue` scans `storage.assocUnstableMessages` for any unit whose author is an AA (`objUnit.bAA`), whose `sequence === 'good'`, and whose `latest_included_mc_index` falls in `[min_mci, max_mci]`, collecting `data_feed` payload values into `arrCandidates` before ever touching the durable, stabilized `kvstore` index (`readDataFeedByAddress`) [4](#0-3) . Because AA triggers cascade — a primary trigger can spawn secondary AA triggers that are all processed and appended as new units within the same stabilization pass (`handleSecondaryTriggers` in `aa_composer.js`) before any of them are on a stabilized MC index — an "oracle" AA that posts a `data_feed` message reflecting some internal, momentarily perturbable value (e.g., its own `balance[asset]`, as literally demonstrated by the `balance[$asset]`/`balance[base]` pricing pattern in `uniswap_like_market_maker.oscript` [5](#0-4) ) can have that skewed value picked up immediately by a second, victim AA in the same cascade via `data_feed[[oracles=...]]`, because the victim's read explicitly includes not-yet-stable AA messages (`bIncludeUnstableAAs` is always true for AA callers) rather than only durable, previously-finalized feed postings.

This mirrors the Sturdy root cause precisely: a price is derived from a pool/AA balance that can be transiently skewed in the same atomic sequence of operations (there, one Ethereum transaction with a flash loan and read-only reentrancy into Balancer; here, one primary-trigger cascade of AA secondary triggers all committed together before stabilization), and a downstream contract/AA consumes that transient, not-yet-final value for a financial decision.

### Impact Explanation
An attacker able to trigger a chain of AA responses within a single primary-trigger cascade can cause a consumer AA to read a data-feed value derived from a balance/state that the attacker skewed moments earlier in the same cascade (e.g., via a large swap into a balance-based pricing AA), and use that manipulated value to under-collateralize a loan, mis-price a swap, or otherwise extract funds from a victim AA — a concrete unauthorized-spending / AA fund-loss scenario, matching the "Medium/High" impact bar (unauthorized fund movement based on manipulated financial data).

### Likelihood Explanation
Likelihood depends entirely on third-party AA authors building oracle-style AAs whose posted `data_feed` values are derived from balances/state that can be moved within one trigger cascade (a common and demonstrated oscript pattern, per the `uniswap_like_market_maker.oscript` sample bundled with the codebase). The underlying `readDataFeedValue` behavior of unconditionally including unstable AA-authored feeds for any AA reader is a core, always-on protocol mechanism, so the attack surface exists for any deployed AA using `data_feed[[...]]` against another AA-controlled oracle in the same DAG region — not requiring any privileged actor, matching an unprivileged AA-trigger-sender threat model.

### Recommendation
Reconsider defaulting `unstable_opts` to `bAA` for every AA `data_feed[[...]]` read in `formula/evaluation.js`; instead require an explicit opt-in (e.g., a dedicated `unstable=true` df_param) so AA authors consciously choose to trust in-cascade, not-yet-stable oracle postings, and document the reentrancy-like risk of oracle AAs whose feed values derive from mutable balances. Consider adding same-cascade "settlement" ordering guarantees or a minimum-age/stability requirement for data-feed values used in high-value financial computations.

### Proof of Concept
Conceptually: (1) Attacker sends a large payment/swap into an AMM/oracle-style AA (as in `uniswap_like_market_maker.oscript`) that computes and posts a price via a `data_feed` message keyed off `balance[$asset]`/`balance[base]` in the same response. (2) In the same primary-trigger cascade, a secondary trigger fires a victim lending/pricing AA that reads `data_feed[[oracles='<oracle_AA>', feed_name='price']]`; because `readDataFeedValue` includes unstable AA-authored messages by default [6](#0-5) , it picks up the just-posted, skewed price from the still-unstable oracle response unit rather than the last finalized value, causing the victim AA to compute an incorrect payout/borrow amount favorable to the attacker. Full exploitation requires locating a real deployed oracle AA of this balance-derived design; this could not be further verified against a live AA definition within the indexed codebase and would need confirmation via a Devin session with full repository/AA-registry access.

function readDataFeedValue(arrAddresses, feed_name, value, min_mci, max_mci, unstable_opts, ifseveral, timestamp, handleResult){
	var bLimitedPrecision = (max_mci < constants.aa2UpgradeMci);
	var start_time = Date.now();
	var objResult = { bAbortedBecauseOfSeveral: false, value: undefined, unit: undefined, mci: undefined };
	var bIncludeUnstableAAs = !!unstable_opts;
	var bIncludeAllUnstable = (unstable_opts === 'all_unstable');
	if (bIncludeUnstableAAs) {
		var arrCandidates = [];
		for (var unit in storage.assocUnstableMessages) {
			var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
			if (!objUnit)
				throw Error("unstable unit " + unit + " not in assoc");
			if (!objUnit.bAA && !bIncludeAllUnstable)
				continue;
			if (objUnit.sequence !== 'good')
				continue;
			if (objUnit.latest_included_mc_index < min_mci || objUnit.latest_included_mc_index > max_mci)
				continue;
			if (_.intersection(arrAddresses, objUnit.author_addresses).length === 0)
				continue;
			storage.assocUnstableMessages[unit].forEach(function (message) {
				if (message.app !== 'data_feed')
					return;
				var payload = message.payload;
				if (!ValidationUtils.hasOwnProperty(payload, feed_name))
					return;
				var feed_value = payload[feed_name];
				if (value === null || value === feed_value || value.toString() === feed_value.toString())
					arrCandidates.push({
						value: string_utils.getFeedValue(feed_value, bLimitedPrecision),
						latest_included_mc_index: objUnit.latest_included_mc_index,
						level: objUnit.level,
						unit: objUnit.unit,
						mci: max_mci // it doesn't matter
					});
			});
		}
		if (arrCandidates.length === 1) {
			var feed = arrCandidates[0];
			objResult.value = feed.value;
			objResult.unit = feed.unit;
			objResult.mci = feed.mci;
			if (ifseveral === 'last')
				return handleResult(objResult);
		}
		else if (arrCandidates.length > 1) {
			if (ifseveral === 'abort') {
				objResult.bAbortedBecauseOfSeveral = true;
				return handleResult(objResult);
			}
			arrCandidates.sort(function (a, b) {
				if (a.latest_included_mc_index < b.latest_included_mc_index)
					return -1;
				if (a.latest_included_mc_index > b.latest_included_mc_index)
					return 1;
				if (a.level < b.level)
					return -1;
				if (a.level > b.level)
					return 1;
				if (bIncludeAllUnstable) // still ambiguous, sort randomly (it's OK outside AAs)
					return 1;
				throw Error("can't sort candidates "+a+" and "+b);
			});
			var feed = arrCandidates[arrCandidates.length - 1];
			objResult.value = feed.value;
			objResult.unit = feed.unit;
			objResult.mci = feed.mci;
			return handleResult(objResult);
		}
