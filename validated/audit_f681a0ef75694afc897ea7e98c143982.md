### Title
Remote assertion crash (DoS) via `throw Error("no src_coin")` in payment validation of a private fixed-denomination asset transfer input - (File: validation.js)

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` contains an unconditional `throw Error(...)` for the `transfer` input case of a private, fixed-denomination (indivisible) asset, asserting that `objValidationState.src_coin` (and its nested fields) have already been populated. This precondition is only satisfied when the payment is reached through the dedicated private-payment-chain path (`indivisible_asset.js` → `validatePrivatePayment`), which explicitly sets `objValidationState.src_coin` before calling `validation.validatePayment`. Any other caller of the normal unit-validation pipeline (`validation.validate` → `validateMessages` → `validatePaymentInputsAndOutputs`) for a `payment` message referencing a private indivisible asset with a `transfer`-type input never sets `src_coin`, so the code path hits the `throw Error("no src_coin")` (or the following `throw Error("no src_output")` / `"no denomination in src coin"` / `"no src coin amount"`) assertions.

The comment itself acknowledges that `src_coin` is only ever populated by the private-payment-chain caller. That caller is `validatePrivatePayment` in `indivisible_asset.js`, which sets `objValidationState.src_coin` right before invoking `validation.validatePayment`: [3](#0-2) 

However, `validatePaymentInputsAndOutputs` (and the containing `validatePayment`) is also reachable through the standard unit validation flow used for every unit broadcast on the network — `validation.validate()` → `validateMessages()` → `validatePayment()` — without ever touching `indivisible_asset.js` or setting `src_coin`. `validation.validate()` is invoked directly on any joint/unit received from an unprivileged peer via `handleJoint()` in `network.js`. [4](#0-3)  and the core dispatch: [5](#0-4) 

Because a payment message's `app`/`payload_location` (e.g. `inline`) and payload structure are attacker-controlled fields of the posted unit, an unprivileged unit author can construct a `payment` message that:
- references an existing private, `fixed_denominations` asset (`objAsset.is_private && objAsset.fixed_denominations` true, checked via `storage.readAsset`), and
- includes an input with `type` omitted (defaulting to `"transfer"`), pointing at some (even non-existent, since no DB lookup occurs before the throw) source output.

When such a unit passes through the regular validation pipeline (not the private-payment-chain code), `objValidationState.src_coin` is `undefined`, and the assertion `throw Error("no src_coin")` fires synchronously inside a callback invoked from `async.forEachOfSeries`/`async.series`. This throw is not wrapped in a `try/catch` anywhere in the call chain from `validate()`, so it propagates as an uncaught exception. `network.js` explicitly re-throws inside its `uncaughtException` handler to crash the process rather than continue in a possibly inconsistent state: [6](#0-5) 

This is analogous to CVE-2023-37018: a remotely-reachable message missing an implicitly-required internal field triggers a hard assertion (`throw Error`) that crashes the process, and the attacker (any peer/unit poster) can repeat this indefinitely to produce a persistent denial of service.

### Impact Explanation
Any node that validates the malicious unit (every full node on the network that receives/relays the unit, plus any node re-validating it from storage) will hit the uncaught `throw Error("no src_coin")` and crash the process, per the explicit `uncaughtException` handler design in `network.js`. Since unit validation of newly received/broadcast units is unavoidable for keeping the DAG updated, this is a network-wide repeatable denial-of-service vector: the network becomes unable to confirm new units because validating nodes keep crashing on the same (or similarly crafted) unit.

### Likelihood Explanation
The trigger requires:
1. An existing private, `fixed_denominations` (indivisible) asset on the network (a common existing asset type — private indivisible/"blackbytes"-like assets are a normal deployed feature),
2. Any unprivileged unit author crafts and posts a `payment` message using that asset with a `transfer`-type input.

No privileged position, hub/peer trust, or timing race is required — only knowledge of one existing private fixed-denomination asset hash, which is public information (assets are registered on-chain). This makes the likelihood high and the attack trivially repeatable.

### Recommendation
Do not use a hard `throw Error(...)` assertion for a condition that can be reached from untrusted, attacker-controlled unit content. Convert the `src_coin`/`src_output`/`denomination`/`amount` checks in `validatePaymentInputsAndOutputs` (validation.js:2415-2424) into a normal validation failure path (`return cb("...")` / `callback("...")`), or explicitly detect and reject (with a normal `ifUnitError`) transfer inputs for private fixed-denomination assets when reached outside the private-payment-chain flow (i.e., when `objValidationState.bPrivate` is not set and `src_coin` is absent), rather than crashing the process. More generally, audit all `throw Error(...)` calls inside functions reachable from `validation.validate()` for other similar "should never happen" assumptions that are, in practice, attacker-influenceable.

### Proof of Concept
1. Identify (or as the attacker, become the definer of) an on-chain asset `A` with `is_private = true`, `fixed_denominations = true`.
2. Craft and sign a new unit `U` from an arbitrary address with a `payment` message:
   - `app: "payment"`, `payload_location: "inline"`
   - `payload.asset = A`
   - `payload.denomination = <valid denomination of A>`
   - `payload.inputs = [ { unit: "<any 44-char base64 string>", message_index: 0, output_index: 0 } ]` (no `type` field ⇒ defaults to `"transfer"`)
   - `payload.outputs` crafted to satisfy the earlier private-output field checks (`output_hash` present, exactly one "open" output with `address`/`blinding`, etc., per lines 2163-2200) so control reaches the input-processing loop.
3. Broadcast `U` to the network / submit via `network.js` `handleJoint` (as an unprivileged unit poster).
4. On every node that validates `U`, `validation.validate()` → `validateMessages()` → `validatePaymentInputsAndOutputs()` reaches the `transfer` case for asset `A` with `objValidationState.src_coin` unset (this code path was never populated because it did not go through `indivisible_asset.js`'s private-chain validator), causing `throw Error("no src_coin")`.
5. The exception propagates uncaught; `network.js`'s `process.on('uncaughtException', ...)` handler re-throws it, crashing the node process. Repeating step 3 with new units causes repeated crashes across the network.
