### Title
Cross-organization commit-status forgery via mismatched signature-scope vs. repository-scope fields in webhook processing - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret used to authenticate an inbound webhook using the payload's `repository.owner.login` (or `organization.login`) field, while the code paths that act on the webhook — `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` and `StatusHandler#process` — resolve the target `Repository`/`Stack`/`Commit` using the entirely separate `repository.full_name` field. Nothing binds these two fields together cryptographically; the HMAC only proves the raw body was signed with the secret selected for whichever organization the attacker chose to put in `repository.owner.login`.

### Finding Description
`Shipit.github(organization:)` supports a multi-tenant secrets layout keyed by GitHub organization, each with its own `webhook_secret`: [1](#0-0) 

`WebhooksController#verify_signature` picks which organization's `GitHubApp` (and therefore which `webhook_secret`) to verify the signature against solely from the JSON body's `repository.owner.login`/`organization.login`: [2](#0-1) 

The HMAC check itself only proves that the raw body matches the secret for whatever organization was named in that field: [3](#0-2) 

However, none of the event handlers use `repository.owner.login`/`organization.login` to decide which `Stack`/`Repository`/`Commit` to mutate. They instead resolve the target purely from `repository.full_name`: [4](#0-3) 

For example, `StatusHandler` looks up commits globally by `sha` across all stacks and writes a new commit status, with no organization/owner check at all: [5](#0-4) 

`PushHandler` similarly resolves stacks via `repository_name` (i.e. `repository.full_name`) and triggers a sync: [6](#0-5) 

Because GitHub always generates these two fields (`repository.owner.login` and `repository.full_name`) consistently from the same repository, this mismatch is invisible under normal operation — both fields always agree. But nothing in the code enforces that agreement. An entity that legitimately knows a valid `webhook_secret` for **one** onboarded organization (e.g., an org admin who configured their own GitHub App/webhook integration with this shared Shipit instance) can construct an arbitrary JSON body, sign it themselves with their own known secret, and set:
- `repository.owner.login` = their own organization (so `verify_signature` picks their own, known-good secret and the HMAC check passes), while
- `repository.full_name` = `"victim-org/victim-repo"` (so the handler layer acts on a stack belonging to a completely different, unrelated organization).

This breaks the trust binding: *the organization whose secret authenticated the request* ≠ *the repository the handler code actually writes to*.

### Impact Explanation
This allows a party trusted only for their own organization's webhook channel to inject forged GitHub events against another tenant's stack in the same Shipit instance:
- Forged `status` events write fabricated commit statuses onto a victim's commits via `Commit#create_status_from_github!`, which can be exploited to falsify CI/deployability signals used by `deployable?`/continuous-deployment gating (`Stack#continuous_delivery_delayed?`, `#trigger_continuous_delivery`), potentially causing deploys to be triggered/blocked against the victim's operator's intent.
- Forged `push` events can trigger `Stack#sync_github` against a victim stack.
- Forged `membership`/`pull_request`/`check_suite` events can create teams/users, alter review-stack lifecycle, or refresh check-runs for a victim's stack.

This is a cross-tenant write capability crossing an authentication boundary that the code believes is enforced (repository-owner-scoped webhook secrets), qualifying as unauthorized cross-repository writes affecting deploy-gating signals in a multi-tenant deployment.

### Likelihood Explanation
Exploitability requires the instance to be configured in the multi-organization mode (`secrets.github` keyed by multiple orgs, each with distinct `webhook_secret`), which is an explicitly supported configuration in `lib/shipit.rb`. Any party who legitimately administers a GitHub App/webhook for one onboarded organization already knows that organization's `webhook_secret` by design (they configure it when wiring up GitHub → Shipit). No GitHub-side spoofing, `ApiClient` token, or session is required — only the ability to send an arbitrary HTTP POST with a valid signature computed from a secret the attacker legitimately possesses for their own org.

### Recommendation
Cryptographically or programmatically bind the field used for signature-key selection to the field used for repository resolution: after selecting `repository_owner` to pick the verifying `GitHubApp`, re-derive/validate that `repository.full_name.split('/').first` (case-insensitively) matches `repository_owner` before dispatching to handlers, and reject (422) on mismatch. More robustly, resolve the target `Stack`/`Repository` via a lookup scoped to the verified organization rather than trusting the payload's `full_name` in isolation.

### Proof of Concept
Given a Shipit instance configured with two organizations, `attacker-org` (secret `S_attacker`, known to the attacker) and `victim-org` (secret `S_victim`, unknown to the attacker):

1. Attacker builds a `status` webhook payload:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_attacker, raw_body)`.
3. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, calls `Shipit.github(organization: "attacker-org")`, and verifies the signature using `S_attacker` — which succeeds because the attacker signed it with that exact secret. [7](#0-6) 
4. `StatusHandler#process` then runs against `Commit.where(sha: params.sha)`, writing a forged status onto the victim's commit, entirely independent of the `attacker-org` scoping used for authentication. [5](#0-4)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      head(422) unless verified

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
