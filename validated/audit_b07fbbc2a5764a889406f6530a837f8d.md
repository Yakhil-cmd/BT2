### Title
Unescaped delimiter in arbiter contract hash source allows contract-field collision / injection - (File: arbiter_contract.js)

### Summary
`getHashSrc()` builds the canonical string used to compute an arbiter contract's identifying `hash` by joining free-text, peer-controlled fields (`title`, `text`, `creation_date`, `payer_address`, `payer_name`, `arbiter_address`, `payee_address`, `payee_name`, `amount`, `asset`) with a fixed, non-escaped delimiter `exports.DELIMITER = "[|#|]"`. Because none of the joined field values are checked for containing the delimiter itself, an attacker who controls `title`/`text`/party-name fields (any peer negotiating an arbiter contract) can embed the literal delimiter sequence plus forged trailing values inside a field, producing a source string — and therefore a SHA-256 hash — identical to that of a semantically different contract (different amount, asset, arbiter, or counterparty). This mirrors the KirbyData bug class (CWE-140): a separator that is trusted to delimit fields during canonicalization/hashing but is not neutralized in the field content, letting an attacker "inject" bogus fields that collide with, or are indistinguishable from, another record's canonical representation.

### Finding Description
`getHashSrc` (used by `getHash`, which becomes `contract.hash`, the primary key of `wallet_arbiter_contracts` and the value embedded into the shared-address oscript definition as `"CONTRACT_" + contract.hash`) concatenates variable-length, attacker-controlled strings with a static delimiter and no per-field escaping or length-prefixing: [1](#0-0) 

`title` and `text` (arbitrary free text) and `my_party_name`/`peer_party_name` are supplied by either party via `createAndSend()` and transmitted to the peer as an untrusted `arbiter_contract_offer` device message: [2](#0-1) 

Because these strings can contain the literal `DELIMITER` bytes, two different tuples of (title, text, creation_date, payer_address, payer_name, arbiter_address, payee_address, payee_name, amount, asset) can be crafted to produce the exact same joined string and hence the exact same SHA-256 hash. This is precisely the delimiter-injection class described in the KirbyData advisory: a fixed separator trusted to delineate record fields, but not neutralized inside field values, allowing forged/overlapping field boundaries.

The resulting `contract.hash` is not just a display value — it is used as:
- the DB primary key for `wallet_arbiter_contracts` and `arbiter_disputes.contract_hash` (`getByHash`, `getDisputeByContractHash`),
- the oscript data-feed key embedded directly into the shared multisig address definition that releases escrowed funds: [3](#0-2) 

The arbiter posts the dispute winner under the data-feed key `"CONTRACT_" + contract.hash`, and the shared address's spending condition checks `["in data feed", [[contract.arbiter_address], "CONTRACT_" + contract.hash, "=", offeror_address]]`. If two different contracts (with different amount/asset/party terms but colliding hashes because of the delimiter-injection above) share the same `contract.hash`, an arbiter resolution genuinely intended for contract A can satisfy the spending condition of a maliciously-crafted contract B that shares the identifier, since the on-chain condition only checks the hash string, not the full contract content.

### Impact Explanation
An attacker who is a counterparty to a private arbiter contract can craft `title`/`text`/party-name fields containing the delimiter sequence to force a hash collision between the contract they actually intend to sign and a second, more favorable (to them) contract (different amount, asset, or arbiter cut). Because the shared-address spending definition and the arbiter's dispute-resolution data feed key are keyed solely by this colliding hash string, this can be leveraged to misdirect an arbiter's resolution or dispute records to release escrowed funds to the wrong address/amount — an AA/shared-address fund-loss scenario reachable purely from a posted device message chain by an unprivileged private-contract counterparty.

### Likelihood Explanation
Exploitation requires only that the attacker be one of the two contracting parties (or, more narrowly, that they be able to submit contract terms — the standard, permitted role for this feature) and be able to embed a fixed 5-character delimiter string plus crafted trailing field content inside a free-text `title`/`text` field, which are otherwise completely unrestricted. No cryptographic break is needed — only construction of a string collision by direct concatenation, which is straightforward given full attacker control of the joined field values (SHA-256 preimage over an attacker-chosen delimiter-manipulated string is not itself broken, but the delimiter ambiguity means many different logical contracts map to the same canonical string/hash by construction, not by preimage attack).

### Recommendation
Do not build the hash source by naive delimiter-joining of variable-length untrusted strings. Instead:
- Reject/validate that `title`, `text`, and party-name fields cannot contain the `DELIMITER` sequence (analogous to the `\n` checks already enforced for data-feed names/values elsewhere in the codebase), or
- Use an unambiguous, self-delimiting encoding for the hash source (e.g., length-prefixed fields, or `getSourceString`/`getJsonSourceString` from `string_utils.js`, which already reject values containing their join character), eliminating any possibility that one field's content can be interpreted as spilling into an adjacent field.

### Proof of Concept
1. Party A crafts a contract offer with `arbiter_address = ARB1`, `amount = 100`, `asset = base`, and a `title` field engineered to contain the literal bytes `"[|#|]"+text2+"[|#|]"+creation_date+"[|#|]"+payer_address+"[|#|]"+payer_name+"[|#|]"+"ARB2"+"[|#|]"+payee_address+"[|#|]"+payee_name+"[|#|]"+"999999"+"[|#|]"+"asset2"` such that the resulting `getHashSrc()` output is byte-identical to the honest source string of a second, more lucrative contract B (`arbiter = ARB2`, `amount = 999999`, `asset = asset2`).
2. Both contracts produce the same `contract.hash` from `getHash()`.
3. The shared address definitions for both contracts reference the data-feed key `"CONTRACT_" + hash`; the arbiter's resolution (or the dispute record keyed by `contract_hash` in `arbiter_disputes`) intended for contract A can now be looked up/matched against contract B's spending condition, since consumers of `contract.hash` (DB lookups, oscript `in data feed` condition) treat the identifier as authoritative without re-verifying the full field tuple against the hash.

**Uncertainty note:** I was not able to execute this scenario end-to-end (no code execution available), so the exact byte-for-byte collision string and full confirmation that no other layer (e.g., additional server-side/arbstore validation of the plaintext contract fields against the hash) blocks this were not verified against runtime behavior; this is based on static analysis of `arbiter_contract.js` only.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
