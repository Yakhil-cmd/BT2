## Title
CCMenu API token authorizes read access to *all* stacks while being distributed as a single-stack CI badge URL — ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` token that is bound to `creator + name` only — never to the `stack_id` in the URL that requested it — yet grants the global `read:stack` permission with no `stack` scope. The `Api::CCMenuController`, which is designed to be polled unauthenticated by third-party CI dashboards using that query-string token, resolves the target stack directly from `params[:stack_id]` without checking that the token is scoped to that stack. This breaks the equality that should hold: *stack the CCMenu URL/token was minted for == stack the token can read*.

### Finding Description
When a user requests the CCMenu badge URL for Stack A: [1](#0-0) 

`client` is looked up/created via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — note there is no `stack:` attribute set, so the resulting `ApiClient` record has `stack_id = nil`.

The generated `authentication_token` is then embedded as a `token` query parameter in a URL that is nominally "for Stack A" (`api_stack_ccmenu_url(stack_id: stack.to_param)`), but the token itself carries no stack binding at all.

On the consuming side, `Api::BaseController#stacks` normally enforces the binding between an `ApiClient`'s `stack_id` and the stacks it may touch: [2](#0-1) 

But `Api::CCMenuController` bypasses this entirely — it authenticates via the raw `params[:token]` and resolves `stack` directly from `Stack.from_param!(params[:stack_id])`, never going through the `stacks` scoping helper: [3](#0-2) 

Since `ApiClient#stack_id?` is `false` for this "CCMenu Client" token (no `stack` was ever assigned), the token is a *global* `read:stack` credential. Combined with `CCMenuController#stack` not consulting `current_api_client.stack_id` at all, any holder of a single CCMenu URL — which is designed to be embedded in unauthenticated third-party CI-status tooling, not treated as a sensitive session credential — can substitute any other `stack_id` in the URL and read that stack's deploy status too.

This is the same class of bug as the reported issue: a verification/authorization step (`ApiClient` permission check, analogous to the `baseGas`/`callWithMinGas` gas check) is satisfied, but the entity it is actually applied against (`stack` resolved from `params[:stack_id]`) is never checked against the entity the token was actually authorized/minted for (Stack A). The check "passes" while the binding it was meant to enforce is silently broken.

### Impact Explanation
This is an unauthenticated read of stack state: anyone in possession of one stack's CCMenu URL (which is routinely shared with unauthenticated external tooling, dashboards, or CI aggregators, and can leak via logs/referrers) can read the deploy status of every stack managed by the Shipit instance, not just the one they were given access to. This matches the "High — unauthenticated read of stack state" impact category.

### Likelihood Explanation
Likelihood is high and requires no privileged access beyond having legitimately been given (or having leaked to them) any single CCMenu URL — a URL that is explicitly designed to be handed to unauthenticated, non-logged-in consumers (CI status badge tools). No additional social engineering, session, or API client secret is required beyond what's already exposed by design in that URL.

### Recommendation
Bind the `ApiClient` created in `CCMenuUrlController#client` to the specific `stack`, and have `Api::CCMenuController#stack` resolve through the scoped `stacks` collection (as `Api::BaseController` does for every other endpoint), so a CCMenu token can only ever read the stack it was minted for.

### Proof of Concept
1. As a legitimate user with access to Stack A, visit the CCMenu URL page to obtain the generated `ccmenu_url` (containing `?token=<TOKEN>`), per `app/controllers/shipit/ccmenu_url_controller.rb`.
2. Note the `ApiClient` backing `<TOKEN>` has `stack_id = nil` and permission `read:stack` (global), since it's created via `find_or_create_by!(creator:, name: 'CCMenu Client')` without a `stack:` argument.
3. Send `GET /api/stacks/<any-other-stack>/ccmenu?token=<TOKEN>` for a Stack B the requester should not have visibility into.
4. `Api::CCMenuController#authenticate_api_client` accepts the token unconditionally; `#stack` resolves `Stack.from_param!(params[:stack_id])` = Stack B with no cross-check against the token's original stack; the response renders Stack B's CI/deploy status.

# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
