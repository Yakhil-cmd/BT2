## Analysis

This confirms the exploit chain: `User#authorized?` (`app/models/shipit/user.rb:80-82`) gates access to the whole app based on `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, and team membership is populated exclusively from the `membership` webhook via `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`), which trusts `params.team`, `params.organization.login`, and `params.member.login` straight out of the request body with no cross-check against the org that was used to select the verification secret.

### Title
Webhook signature check silently no-ops when `webhook_secret` is unset, letting an unauthenticated caller forge `membership` events and grant themselves `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as "signature valid" instead of "cannot verify, reject": [1](#0-0) 
Because `webhook_secret` is documented and defaulted as **optional** (`docs/setup.md` line 30/119, `template.rb` line 106, `config/secrets.development.shopify.yml` line 9), a standard/documented Shipit install that leaves it blank accepts **any** POST to `/webhooks` as if it were a genuinely signed GitHub delivery, for the organization resolved from the attacker-controlled body itself.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to check against using data taken from the very payload being verified: [2](#0-1) [3](#0-2) 

`verify_webhook_signature` then does:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [1](#0-0) 

If no `webhook_secret` is configured (the documented default/optional state), this method returns `true` unconditionally, regardless of the `X-Hub-Signature` header or body content. The controller then dispatches to handlers with the raw, unauthenticated, attacker-supplied JSON: [4](#0-3) 

`MembershipHandler` uses that unauthenticated payload directly to create/modify `Team` and `Membership` records: [5](#0-4) 

Those `Membership` records are the sole basis for `User#authorized?`, which gates every controller behind `Shipit::Authentication#force_github_authentication`: [6](#0-5) [7](#0-6) 

**The binding that is broken:** the identity/organization that "authenticated" the webhook request (i.e., whichever GitHub org config the controller happened to select via `repository_owner`/`organization.login`, which for an unset-secret org accepts unsigned traffic) is treated as equivalent to "a real GitHub-originated event for that org's real team membership," when in fact no credential was checked at all. This mirrors the reported bug class: a value used to drive a privileged state change (`amm_coin_mint`/`amm_pc_mint` in the Raydium report; here, `team`/`organization`/`member` in the membership payload) is never validated against anything actually protected by a trust boundary — here the "boundary" (HMAC signature) is bypassed entirely when the optional secret is absent, exactly as documented setup permits.

### Impact Explanation
An unauthenticated network attacker who knows (or guesses) a Shipit instance's `/webhooks` URL (documented publicly as `<homepage>/webhooks`) and the name of any GitHub organization/team already configured in `Shipit.github_teams` can:
1. POST a forged `membership` event (`action: "added"`, arbitrary `member.login`, matching `team` id/slug) with header `X-Github-Event: membership`.
2. Because `webhook_secret` is optional and commonly left unset (per this engine's own default templates), `verify_signature` passes unconditionally.
3. `MembershipHandler` creates/attaches a `Membership` for an attacker-chosen GitHub login to that team.
4. If the attacker also completes GitHub OAuth login as that same login (a normal, unprivileged action any GitHub user can do), `User#authorized?` returns `true`, granting them full authenticated access to the Shipit UI/API — i.e., escalation into `Shipit.github_teams` authorization, one of the explicitly listed High-severity impacts, and from there access to deploy/rollback/merge functionality reserved for authorized team members.

### Likelihood Explanation
High under the engine's own documented defaults: `webhook_secret` is explicitly called out as "optional" in `docs/setup.md`, ships blank in `template.rb` and `config/secrets.development.shopify.yml`, and the `/webhooks` endpoint is unauthenticated and publicly documented by design (it must be, to receive real GitHub events). No credential, session, or prior access of any kind is required to exploit this — only knowledge of a valid team id/slug and a GitHub login, both of which are typically public (team pages, GitHub profiles).

### Recommendation
- Change `verify_webhook_signature` so a missing/blank `webhook_secret` is a hard failure (reject the request / log a misconfiguration error) rather than an implicit pass, or require `webhook_secret` to be present at boot for every configured organization.
- Do not let webhook-driven `Team`/`Membership` mutations be the sole source of truth for authorization; periodically reconcile against live GitHub team membership (the existing `bin/rake teams:fetch` task) rather than trusting webhook payloads exclusively.
- Add a startup check/validation in `Shipit.github_app_config` that refuses to boot (or disables the `membership` handler) for any organization lacking a configured `webhook_secret`.

### Proof of Concept
Given a Shipit deployment where the org `"OrgOne"` (per `test/dummy/config/secrets_double_github_app.yml`-style config) has `webhook_secret:` blank, and `Shipit.github_teams` includes `OrgOne/developers` (github_id `48`):

```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": 48, "name": "developers", "slug": "developers", "url": "https://github.com/orgs/OrgOne/teams/developers" },
  "organization": { "login": "OrgOne" },
  "member": { "login": "attacker-github-login" }
}
```
No `X-Hub-Signature` header is required — `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgOne")`, whose `verify_webhook_signature` short-circuits to `true` because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`). `MembershipHandler#process` then creates a `Membership` row for `attacker-github-login` in team `48`. The attacker then logs into Shipit via normal GitHub OAuth as `attacker-github-login`; `User#authorized?` finds the forged `Membership` and grants access.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

    end
