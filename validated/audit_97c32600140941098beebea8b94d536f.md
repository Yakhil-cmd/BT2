### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)`, with no filter on the repository/organization that authenticated the webhook, and then calls `commit.create_status_from_github!(params)` for every match. Because git commit SHAs are content-derived and identical across forks/mirrors, an attacker who owns a fork of a victim's public repository can trigger a correctly-signed webhook from their own repo that still creates a `Status` row (with attacker-controlled `state`/`description`/`context`/`target_url`) on the victim's stack, because `Status.stack_id` is taken from the matched `Commit`'s own `stack_id`, not from the repository that signed the request.

### Finding Description
The claimed binding is: `Status#stack_id` written by a webhook == `stack_id` of the repository whose signature was verified in `WebhooksController#verify_signature`. In fact the code enforces only: `Status#stack_id == matched_Commit#stack_id`, where the `Commit` is selected solely by `sha` equality, with no join or check against `repository_owner`/`repository.full_name` from the payload.

Path:
- `WebhooksController#verify_signature` validates the HMAC signature using `Shipit.github(organization: repository_owner)` [1](#0-0) . This only proves the request was signed for the org named in the payload (i.e., GitHub actually sent it for that repo's event) — it says nothing about which `Commit`/`Stack` rows may be touched.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This query is global across every `Stack`/repository configured in the Shipit instance — it is not scoped by `params.dig('repository', 'full_name')` or by the organization that was authenticated.
- `Status.replicate_from_github!` then persists the attacker-supplied `state`/`description`/`target_url`/`context`/`created_at` verbatim under `stack_id:` taken from the matched commit's own association:
```ruby
def replicate_from_github!(stack_id, github_status)
  find_or_create_by!(
    stack_id:,
    state: github_status.state,
    description: github_status.description,
    target_url: github_status.target_url,
    context: github_status.context,
    created_at: github_status.created_at
  )
end
``` [3](#0-2) 

Exploit flow: an attacker forks (or otherwise obtains) a public repository tracked as a Shipit stack, so that at least one commit SHA is identical between the attacker's repo and the victim's tracked stack (trivial — unmodified upstream commits keep their SHA in any fork/mirror, and this is also true if the attacker simply mirrors/replays the victim's public commits into their own repo). The attacker then sets an arbitrary commit status on that SHA in their own repository (via the GitHub UI/API on a repo they own) or otherwise triggers a `status` webhook event for that SHA. GitHub signs and delivers this webhook correctly for the attacker's org/repo, so `verify_signature` passes. `StatusHandler` then matches the shared SHA against the victim's `Commit` row (in a completely different `Stack`/org) and writes a `Status` there with the attacker-controlled fields, under the victim stack's `stack_id`.

None of the listed guards prevent this: `verify_signature` only authenticates the signer, not the target rows; `drop_unhandled_event` and `ExplicitParameters` (`params do ... end` in `StatusHandler`) validate shape, not ownership; there is no `require_permission!`/`stacks` scope check in this handler at all.

### Impact Explanation
This lets an unprivileged GitHub user (owner of any repository whose commit history overlaps a victim's tracked stack) write forged CI/status data into the victim's stack: `Status.state` can be forced to `success`, unblocking `deployable?`/`blocked?` checks (`Commit#deployable?` at `app/models/shipit/commit.rb` lines 227-229) and `schedule_merges`/`schedule_continuous_delivery` triggers on `add_status` [4](#0-3) , potentially causing an unauthorized/incorrect deploy decision on the victim's stack purely from an attacker-controlled payload sent for their own repository. This is a payload from one repository mutating another repository's stack/commit data, matching the Critical category in scope.

### Likelihood Explanation
Preconditions: the victim repository/stack must have a `Commit` row whose SHA the attacker can reproduce or observe (straightforward for any public repository — forking preserves SHAs for unmodified commits, and even a single un-rebased upstream commit shared between attacker fork and victim stack is enough). The attacker needs no Shipit credentials, no knowledge of `webhook_secret`/`api_clients_secret`, and no `Shipit.github_teams` membership — only the ability to set a commit status on a repo they control and have GitHub deliver the resulting webhook. This is cheap, repeatable against any stack sharing history with a public/forkable repo, and requires no privileged Shipit configuration beyond the engine's default webhook wiring.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` by the authenticated repository, not by SHA alone — e.g., resolve the target `Stack`(s) via `params.dig('repository','full_name')`/`repository_owner` (as already used for signature verification) and restrict `Commit.where(sha: ..., stack_id: matched_stack_ids)` before calling `create_status_from_github!`, so a `Status` can only ever be created under the stack whose repository actually authenticated the webhook.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (illustrative)
test "status webhook from one repository cannot write a Status onto another repository's stack via shared sha" do
  victim_stack = shipit_stacks(:shipit)              # tracks github repo "shopify/shipit-engine"
  attacker_stack = shipit_stacks(:cyclimse)          # tracks github repo "attacker/shipit-engine-fork"

  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared upstream commit")
  # attacker's stack has no Commit row for this sha at all -- irrelevant, handler doesn't check it

  params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: shared_sha,
    state: "success",
    description: "forged by attacker",
    context: "attacker-ci",
    target_url: "https://attacker.example.com"
  )

  assert_difference "victim_commit.statuses.count", 1 do
    Shipit::Webhooks::Handlers::StatusHandler.new.process(params) # simulating attacker-authenticated delivery
  end

  status = victim_commit.statuses.last
  assert_equal victim_stack.id, status.stack_id   # BROKEN BINDING: victim stack_id used
  assert_equal "success", status.state            # attacker-controlled state persisted on victim stack
  assert_equal "forged by attacker", status.description
end
```
This demonstrates that a `Status` row is created with `stack_id == victim_stack.id` purely from `sha` equality, even though the simulated webhook body/authentication context corresponds only to the attacker's repository, proving `stack_id` on the written row is not bound to the repository that authenticated the request.
