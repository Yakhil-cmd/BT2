### Title
Unscoped commit status writes cross repository boundaries in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Shipit's webhook signature verification is bound to the *organization* extracted from the payload (`repository.owner.login`), which selects which GitHub App configuration (and thus which `webhook_secret`) is used to validate the HMAC signature. Every other handler that mutates state (e.g. `PushHandler`) additionally scopes the resulting database write to the *specific repository* named in the payload via `Handler#stacks`/`Handler#repository_name`. `StatusHandler`, however, breaks this invariant: it verifies the signature for the sending org/repo, but then writes the resulting `Status` to **any** `Commit` row in the entire Shipit instance that happens to share the same `sha`, with no repository/stack scoping at all. This mirrors the Illuminate/Yield bug class: the field that is authenticated (the sending repository's org) is not the field that is actually acted upon (the commit/stack that receives the write).

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration used to validate `X-Hub-Signature` based on the organization derived from the payload: [1](#0-0) [2](#0-1) 

This binds authentication to "which org sent this and does its secret match", nothing more. `Shipit.github(organization:)` resolves independent per-organization secrets: [3](#0-2) 

Once the signature check passes, the raw params are dispatched to handlers with no further repository check performed by the controller itself: [4](#0-3) 

The base `Handler` class provides a helper that correctly scopes any lookup to the repository named in the payload: [5](#0-4) 

`PushHandler` uses this scoping correctly — it only updates stacks belonging to the repository that was actually the subject of the (verified) webhook: [6](#0-5) 

`StatusHandler` does not use this scoping mechanism at all. It looks up commits purely by SHA, globally, across every stack/repository tracked by the Shipit instance, and writes a GitHub status onto whatever `Commit` rows match: [7](#0-6) 

Because git commit SHAs are a hash of tree/parents/author/committer/message/timestamps and not tied to a specific repository, it is trivial for anyone with push/webhook-triggering access to *any* repository monitored by this Shipit instance (org A) to reproduce the exact SHA of a commit that exists in a *different, unrelated* repository/stack (org B) — e.g., by fetching a public commit and pushing/cherry-picking it verbatim into their own repo, or by forking the target repository. A `status` event genuinely signed by org A's webhook secret will then cause Shipit to write/overwrite the `Status` for the corresponding `Commit` row belonging to org B's stack, because the write path performs no comparison between the authenticated repository and the repository actually mutated.

This is the exact class of bug in the report: the field that was verified (`repository_owner` selecting the signing org/secret) is not the field the code acts on when performing the write (`Commit.where(sha:)`, unscoped by repository).

### Impact Explanation
Shipit's deploy pipeline can be configured (`ci.require`) to gate deploys on commit statuses being green (`README.md` §CI). An attacker who has legitimate webhook-triggering ability for any one repository monitored by the instance (e.g., a collaborator on a low-trust/sandbox repo with the Shipit GitHub App installed) can forge a "success" status for a commit SHA that coincidentally/deliberately also exists in a higher-trust stack's repository, satisfying CI requirements there and enabling an **unauthorized deploy** in that unrelated stack — without ever having credentials, GitHub team membership, or write access to the victim repository. This matches the in-scope "unauthorized deploy" impact category.

### Likelihood Explanation
Exploitation requires: (1) the target Shipit instance tracks more than one repository/stack (very common), and (2) the attacker can trigger a genuinely signed `status` webhook whose payload references a commit SHA that also exists in the victim stack's `commits` table. Reproducing an identical SHA across repositories is straightforward for public commits (git objects are portable), and CI systems posting statuses for arbitrary SHAs pushed to a repo are common. This does not require compromising `webhook_secret`, `api_clients_secret`, or a GitHub App private key — it only requires legitimate push/webhook access to one monitored repository, which is a much lower bar than the privileges normally needed to affect another stack.

### Recommendation
Scope `StatusHandler#process` to only update commits that belong to the repository named in the verified payload, mirroring what `PushHandler`/`Handler#stacks` already do:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
More generally, every handler that performs a database write from webhook payload data should route through `Handler#stacks`/`repository_name` so the authenticated repository and the mutated repository can never diverge.

### Proof of Concept
1. Shipit instance tracks Stack A (`org/victim-repo`) and Stack B (`org2/attacker-repo`), both with the Shipit GitHub App installed and their own webhook secrets configured in `secrets.github`.
2. Attacker has push access to `org2/attacker-repo` and knows (or can fetch) a commit `C` with SHA `deadbeef...` that is currently tracked in Stack A's history (e.g. a shared open-source dependency commit, or by forking `victim-repo`).
3. Attacker pushes/cherry-picks commit `C` into `attacker-repo`, preserving byte-for-byte content so the SHA is identical, then triggers (via CI, or the GitHub Statuses API on their own repo) a `status` event with `state: success` for SHA `deadbeef...`.
4. GitHub signs this payload with `org2`'s webhook secret; `WebhooksController#verify_signature` correctly validates it against `org2`'s app config using `repository_owner = "org2"`.
5. `StatusHandler#process` executes `Commit.where(sha: "deadbeef...")`, which matches the row belonging to Stack A (`victim-repo`), and calls `create_status_from_github!` on it — marking the victim's commit as CI-green despite the webhook never having come from `org/victim-repo`.
6. If Stack A's `ci.require` includes that status context, this can unblock a deploy the attacker had no authorization to influence.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
