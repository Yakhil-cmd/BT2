### Title
Cross-organization webhook forgery: `repository_owner` used for signature verification diverges from `repository.full_name` used by `AssignedHandler` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to verify a webhook against using `repository_owner`, which reads `params.dig('repository','owner','login')` and falls back to `params.dig('organization','login')`. `AssignedHandler` (and all `pull_request` handlers) instead resolve the affected `Repository`/`Stack`/`PullRequest` from the independent `params.repository.full_name` field. Because these two fields are never cross-checked, a payload can be *signed and verified* against one organization's secret while acting on a completely different organization's stack.

### Finding Description
The broken binding is the implicit assumption:
`repository_owner == owner(repository.full_name)`

which the code never enforces.

- `verify_signature` computes the verifying org as: [1](#0-0) 
and uses it to select the `GitHubApp` instance/secret: `Shipit.github(organization: repository_owner)`. [2](#0-1) 

- `AssignedHandler#repository` resolves the target repository purely from `params.repository.full_name`, with no relation to whatever value was used for `repository_owner`: [3](#0-2) 
and `pull_request` looks up the persisted `Shipit::PullRequest` for that repository/stack and `process` writes to it: [4](#0-3) 

- The `params` schema for `AssignedHandler` only requires `repository.full_name`, not `repository.owner.login`: [5](#0-4) 
so a payload with `repository: { full_name: "victim-org/victim-repo" }` (no `owner` key) and a separate top-level `organization: { login: "attacker-org" }` is schema-valid for the handler while causing `repository_owner` to fall back to `organization.login`.

Exploit flow: an attacker who legitimately controls "attacker-org" in a Shipit multi-tenant configuration (they installed the GitHub App / configured the webhook and thus know `attacker-org`'s `webhook_secret`) crafts a `pull_request` / `action=assigned` payload with:
- `organization.login = "attacker-org"` (or simply `repository.owner.login = "attacker-org"` — the fallback isn't even required for the general bug, since `repository.owner.login` and `repository.full_name` are also two independent attacker-set fields)
- `repository.full_name = "victim-org/victim-repo"` (an unrelated org's onboarded stack)
- signs the request body with `attacker-org`'s known `webhook_secret`

`Shipit.github(organization: "attacker-org")` resolves to the attacker's own valid `GitHubApp`/secret, `verify_webhook_signature` succeeds, and the request passes `verify_signature`. `Shipit::Webhooks.for_event('pull_request')` then dispatches to `AssignedHandler`, which resolves `repository` from `repository.full_name = "victim-org/victim-repo"`, finds the victim's persisted `Shipit::PullRequest`, and overwrites its `github_pull_request` attribute with attacker-controlled JSON — a write to victim-org's stack that was never authenticated by victim-org's secret.

None of the existing guards prevent this: `verify_signature`/`GitHubApp#verify_webhook_signature` only prove that whoever supplied `organization.login`/`repository.owner.login`'s secret signed the body — they never re-check that the *same* organization owns `repository.full_name`. `drop_unhandled_event`, the `ExplicitParameters` schema, and model validations (`Repository`/`Stack`) only validate individual field shapes, not cross-field ownership.

### Impact Explanation
An attacker who administers any org onboarded into a multi-tenant Shipit instance can forge webhook events that mutate persisted `PullRequest` records belonging to a different, unrelated org/stack that they do not control and whose secret they never possessed — matching the Immunefi Critical category "a payload for one repository mutating another's stack, commit, task or team." The write is limited to what `AssignedHandler#process` does (`pull_request.update(github_pull_request: params.pull_request)`), i.e., overwriting cached PR metadata (assignees, labels, title, state, head sha/ref) for an existing stack's `PullRequest` record. I did not find, in the code paths traced, evidence that this specific update directly triggers an autodeploy/rollback/merge as the bot identity — that portion of the question's exploit narrative is not substantiated by `AssignedHandler` itself, only the cross-tenant unauthorized write is directly demonstrable from this code.

### Likelihood Explanation
This requires a Shipit instance configured for multiple GitHub organizations (`secrets.github` keyed by org) with at least two onboarded orgs/stacks, one of which the attacker legitimately administers (so they know that org's `webhook_secret`). Given that precondition, the attack is a single unauthenticated `POST /webhooks` request, fully repeatable against any other onboarded org/stack/PR number pair, at negligible attacker cost.

### Recommendation
Cross-check that the organization used to select the verification secret matches the owner of `repository.full_name` before dispatching to handlers — e.g., derive `repository_owner` strictly from `repository.full_name.split('/').first` (or require `repository.owner.login` to equal that prefix) rather than falling back to an independent `organization.login` field, and reject the request if they diverge.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` (conceptual, not to be placed in `test/**` per scope note but demonstrating the assertion needed):
1. Configure `secrets.github` with two orgs, `attacker-org` (secret `S_A`) and `victim-org` (secret `S_V`), each with an onboarded `Stack`/`Repository`/`PullRequest` fixture.
2. Build a `pull_request` `action: 'assigned'` payload with `repository: { full_name: 'victim-org/victim-repo' }` (no `owner`) and `organization: { login: 'attacker-org' }`.
3. Sign the raw body with `S_A` (attacker-org's secret) and set `X-Hub-Signature`.
4. POST to `/webhooks`; assert `response.status == 200` (verification passes) and assert that `victim-org`'s `Shipit::PullRequest#github_pull_request` was updated with attacker-supplied JSON — proving the equality `repository_owner ("attacker-org") == owner(repository.full_name) ("victim-org")` is false yet the write still occurred.
