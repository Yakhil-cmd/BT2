### Title
Private textcoin payload written to disk with default OS file permissions exposes spendable mnemonic to any local user - ([File: wallet.js])

### Summary
When a private (non-public) asset is sent to a textcoin address, `sendMultiPayment`'s `preCommitCb` writes the recipient's private-payment payload — including the plaintext spending `mnemonic` and the private-element chains — to a file on disk via `storePrivateAssetPayload`, using a caller-supplied path and Node's default `fs.writeFile`, which does not restrict file permissions.

### Finding Description
In the private-asset payment flow, `preCommitCb` retrieves a save path from `opts.getPrivateAssetPayloadSavePath` and calls `storePrivateAssetPayload(fullPath, cordovaPathObj, mnemonic, arrChainsOfRecipientPrivateElements, cb)`. [1](#0-0) 

`storePrivateAssetPayload` builds a zip containing the plaintext `mnemonic` (from which the private key of the freshly generated textcoin address is deterministically derivable, see `expandMnemonic`) plus the private payment chains, and writes it to `fullPath` with plain `fs.writeFile(fullPath, zipFile, cb)` — no explicit file mode is passed, so the file is created with the process's default umask-derived permissions (typically world/group readable on POSIX systems). [2](#0-1) 

`expandMnemonic` shows the mnemonic alone is sufficient to derive the signing key and address for the textcoin: [3](#0-2) 

This is directly analogous to the CVE-2023-49345 bug class: an application writes sensitive temporary/intermediate data to a file that is left readable by any local user on the system, allowing that data to be viewed or manipulated before it reaches its intended destination.

### Impact Explanation
The written file contains a spendable mnemonic for a live on-chain output (the textcoin address funded by the payment). Any other local user/process on the same machine that can read this file before it is deleted, transmitted, or overwritten can derive the private key via `expandMnemonic` and claim/spend the funds themselves — a direct unauthorized-spending / fund-theft primitive, not merely an information leak. On a shared or multi-tenant host (e.g., shared hosting for a headless wallet, or a device where multiple local accounts/apps exist), this results in concrete loss of funds for the legitimate recipient.

### Likelihood Explanation
Exploitation requires local access to the same filesystem the wallet process runs on, and a window during which the file exists at `fullPath` before it is consumed/removed. This satisfies the "unprivileged... local access" model expected of this analog class (no privileged/malicious-peer or malicious-node capability is required — only local coexistence). Likelihood depends on deployment (e.g., desktop single-user machines have lower risk; shared/multi-user or CI/headless environments raise it), but the underlying primitive — plaintext spending secret + default file permissions — is unconditionally present in the code path.

### Recommendation
When calling `fs.writeFile` in `storePrivateAssetPayload`, explicitly pass restrictive permissions (e.g., `{ mode: 0o600 }`), matching the `0o700`-style directory hardening already used elsewhere in the codebase (e.g., `kvstore.js`, `sqlite_pool.js`). Additionally, consider encrypting the mnemonic/payload at rest or minimizing its residency time on disk, and documenting that consumers of `getPrivateAssetPayloadSavePath` must supply paths in directories not readable by other local users.

### Proof of Concept
1. A user sends a private asset as a textcoin (`sendMultiPayment` with a text-address output and a private asset), triggering `preCommitCb` → `storePrivateAssetPayload`. [4](#0-3) 
2. The resulting zip file at `fullPath` is created with default `fs.writeFile` permissions (world/group readable per umask). [5](#0-4) 
3. A second local user or process on the same host reads the file, unzips it, extracts `mnemonic`, and calls `expandMnemonic(mnemonic)` to derive the private key/address. [3](#0-2) 
4. The attacker uses this key to sign a spend from the textcoin address before the legitimate recipient claims it, resulting in fund theft.

function expandMnemonic(mnemonic) {
	var addrInfo = {};
	mnemonic = mnemonic.toLowerCase().split('-').join(' ');
	if ((mnemonic.split(' ').length % 3 !== 0) || !Mnemonic.isValid(mnemonic)) {
		throw new Error("invalid mnemonic: "+mnemonic);
	}
	mnemonic = new Mnemonic(mnemonic);
	addrInfo.xPrivKey = mnemonic.toHDPrivateKey().derive("m/44'/0'/0'/0/0");
	addrInfo.pubkey = addrInfo.xPrivKey.publicKey.toBuffer().toString("base64");
	addrInfo.definition = ["sig", {"pubkey": addrInfo.pubkey}];
	addrInfo.address = objectHash.getChash160(addrInfo.definition);
	return addrInfo;
}

function storePrivateAssetPayload(fullPath, cordovaPathObj, mnemonic, chains, cb) {
	var storedObj = {
		mnemonic: mnemonic,
		chains: chains
	};
	var bCordova = (typeof window === 'object' && window.cordova);
	var JSZip = require("jszip");
	var zip = new JSZip();
	zip.file('private_textcoin', JSON.stringify(storedObj));
	var zipParams = {type: "nodebuffer", compression: 'DEFLATE', compressionOptions: {level: 9}};
	zip.generateAsync(zipParams).then(function(zipFile) {
		if (!bCordova) {
			var fs = require('fs');
			fs.writeFile(fullPath, zipFile, cb);
		} else {
			window.requestFileSystem(LocalFileSystem.TEMPORARY, 0, function(fs) {
				window.resolveLocalFileSystemURL(cordovaPathObj.root, function(dirEntry) {
					dirEntry.getDirectory(cordovaPathObj.path, {create: true, exclusive: false}, function(dirEntry1) {
						dirEntry1.getFile(cordovaPathObj.fileName, {create: true, exclusive: false}, function(file) {
							file.createWriter(function(writer) {
								writer.onwriteend = function() {
									cb(null); 
								};
								writer.write(zipFile.buffer);
							}, cb);
						}, cb);
					}, cb);
				}, cb);
			}, cb);
		}
	}, cb);
}
