### Title
Webhook Organization Used for Signature Verification Is Not Bound to the Repository the Payload Writes To - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to validate a webhook against using an attacker-controlled field from the *unverified* JSON body, while the actual repository/stack the handlers mutate is resolved independently from other fields in that same body. Because `webhook_secret` is documented and coded as optional per organization, an organization configured without a secret lets any payload claiming to belong to that organization bypass signature verification entirely, yet the handlers still act on whatever `repository.full_name` is embedded in the (otherwise unauthenticated) body.

### Finding Description
`verify_signature` derives the organization used to fetch the signing key purely from the raw JSON, before any authentication occurs: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization config and builds a `GitHubApp` keyed only by that org name: [3](#0-2) 

Signature verification then trivially returns `true` whenever that organization's `webhook_secret` is unset: [4](#0-3) 

`webhook_secret` is explicitly documented as **optional** per app/organization in a multi-org install: [5](#0-4) 

This reproduces the report's root cause pattern exactly: a value used to gate a security-critical decision (`LAST_HARVEST_PERFORMANCE_FEE_TIME` reusing the `NAV` key) is derived from the wrong/uncommitted source, so the check silently validates against the wrong thing. Here, the *authenticated identity* (organization picked from `repository.owner.login` or `organization.login` in the raw body) is not cryptographically bound to the *repository actually acted upon* by the downstream handler, which independently reads `repository.full_name` (or equivalent) from the same untrusted payload to locate the `Stack`/`Repository` record and enqueue jobs (e.g. `GithubSyncJob`, membership/team mutations).

Binding broken (equality that should hold but doesn't):
`organization authenticated by verify_signature == organization owning the repository the handler subsequently writes to`

Before the attacker's request: the binding is assumed to hold implicitly since normally `repository.owner.login` and `repository.full_name`'s owner segment are the same GitHub-controlled value.
After a crafted request: the attacker sets `repository.owner.login` (used only for secret selection) to an organization with no `webhook_secret` configured, while embedding a different target repository's `full_name` for the handler logic — decoupling the two uses of the payload.

### Impact Explanation
If any tenant/org entry in a multi-org `secrets.yml` omits `webhook_secret` (allowed by design/docs), an attacker who knows only that org's name (public information) can submit a completely unsigned/forged webhook body. Because handlers like the push handler resolve the target `Stack`/`Repository` from other fields of the same body rather than from the organization used for verification, this allows unauthenticated writes into Shipit's data model (queuing `GithubSyncJob`s, creating/deleting `Team`/`Membership` records, closing/labeling PRs via handlers) for repositories that were never protected by that request's (nonexistent) signature — a cross-repository write / authorization bypass via webhook forgery.

### Likelihood Explanation
Requires an operator to have configured at least one organization in `secrets.yml` without `webhook_secret` — an explicitly supported and documented configuration, not a misconfiguration outside the engine's design. No GitHub credentials, API tokens, or session are needed; the attacker only needs the public `/webhooks` endpoint and knowledge of the unsecured org's name/slug.

### Recommendation
- Do not allow `verify_webhook_signature` to unconditionally return `true` when `webhook_secret` is blank; require an explicit "unauthenticated organization" opt-in flag instead of silently trusting any payload.
- Bind the organization used for verification to the organization actually referenced by `repository.full_name`/`organization.login` acted upon by the handler, rejecting mismatches.
- Consider making `webhook_secret` mandatory for all configured organizations.

### Proof of Concept
1. Configure two organizations in `secrets.yml` per the documented multi-org format, where `orgWithoutSecret` has no `webhook_secret` set (a supported configuration per `docs/setup.md`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
   ```json
   {
     "repository": { "owner": { "login": "orgWithoutSecret" }, "full_name": "orgWithoutSecret/some-other-real-repo" },
     "after": "<attacker-chosen-sha>"
   }
   ```
   with any/no `X-Hub-Signature` value.
3. `verify_signature` calls `Shipit.github(organization: "orgWithoutSecret")` → `verify_webhook_signature` returns `true` (no secret configured) → request proceeds to `create`, and `Shipit::Webhooks.for_event('push')` handlers process the forged payload against the real `orgWithoutSecret/some-other-real-repo` stack, enqueueing `GithubSyncJob` with attacker-supplied `expected_head_sha` — all without any valid signature.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
