### Title
Borrowers in one hub can drain the shared token balance backing other hubs' markets, freezing withdrawals (`File: contracts/pool/src/cache/cash.rs`)

### Summary
The upstream bug class is a shared bounded resource (the read-tx semaphore) that is sized for one consumer group while other long-lived holders draw from the same pool, letting a transient consumer take the last slot a permanent holder needs. In XOXNO Lending the analog is the physical token balance of the pool contract: every market keyed by `(hub_id, asset)` keeps its own `cash` book, but all markets on the same token share one token balance. Every outbound guard checks only the market's own booked `cash`, never the real `token.balance(pool)` net of sibling markets' claims, so one market's borrowers can spend tokens that another market's suppliers' withdrawals depend on.

### Finding Description
Per ADR-0002, markets for one token in different hubs keep distinct books but share the pool's token balance. The liquidity checks are all per-market bookkeeping:

- `Cache::require_reserves` asserts only `self.cash >= amount` — the market's own tracked cash, not the actual balance [1](#0-0) 
- `require_liquidation_buffer` reserves `LIQUIDATION_BUFFER_BPS` of *that market's* floored supplied amount from *that market's* `cash`; it does not read `token.balance` or sibling markets at all [2](#0-1) 
- `transfer_out` then calls `token.transfer(pool, recipient, amount)`, which reverts when the shared physical balance is insufficient [3](#0-2) 

The protocol's own fuzz target encodes the missing invariant — `cash_A + cash_B <= token.balance(pool)` — as an assertion to check rather than an enforced guard: "Markets on one asset share the token balance, so a per-market `cash <= balance` check cannot detect an overdraw." [4](#0-3) 

Concretely: hub A and hub B both list USDC, each booking 1,000 USDC cash, pool balance 2,000. A borrower in hub A borrows up to `cash_A - buffer_A` (≈980 with `max_utilization = RAY` uncapped, which `require_utilization_below_max` explicitly permits) [5](#0-4) . Repeating, or combined with hub-A flash loans/withdrawals, hub A's market can drive the physical balance below hub B's booked 1,000. Any hub-B `withdraw`/`claim_revenue`/`flash_loan` then passes `require_reserves` (its book says cash is there) but reverts inside `token.transfer`, freezing hub-B suppliers' funds until hub-A debt is repaid. The attacker reaches this via unprivileged `controller::borrow` (or `multiply`/`flash_position` which mint debt through the same `mint_debt` path) on a healthy account in hub A.

The same gap makes `claim_revenue` and the 2% liquidation buffer unreliable: the buffer is computed against hub-A's book only, so sibling-market drawdown can leave the seizure reserve physically empty even while every per-market guard passes. Documentation acknowledges shared custody ("share its pool balance and token risks") but no mechanism bounds the cross-market drawdown; the fuzz harness treats `Σ cash ≤ balance` as a property that should hold.

### Impact Explanation
Temporary freezing of funds: suppliers, revenue claimants, and flash borrowers of a healthy, fully backed market in hub B cannot withdraw because a different market's borrowers physically spent the shared tokens. The freeze persists until hub-A borrowers repay; at a stressed borrow rate, repayment may be economically discouraged, extending the freeze. It also silently degrades the liquidation buffer's purpose — seizures needing cash can fail when sibling markets have drained the balance.

### Likelihood Explanation
Requires the same token listed in two hubs (a supported, documented configuration per ADR-0002) and an attacker with enough collateral to borrow hub A's market down to its buffer — ordinary borrowing cost, no privileged access. Likelihood is moderate: it needs a multi-hub listing of one asset and sufficient attacker capital, and the freeze self-corrects on repayment, so it is a Medium rather than a High.

### Recommendation
Like the upstream fix (floor the semaphore at the census of all long-lived holders), floor the drawable amount at the shared physical reality: in `transfer_out`/`require_reserves`, check `token.balance(pool) - draw >= Σ sibling cash` (or maintain a per-asset total-cash counter alongside per-market cash) so no market's outflow can spend tokens booked to another market. Alternatively, enforce a global per-asset reserve `Σ cash + reserved ≤ balance` at every debit.

### Proof of Concept
1. Governance lists USDC in hub 1 and hub 2 (same SAC, separate `PoolKey::State` books, one pool balance).
2. Victim supplies 1,000 USDC via `controller::supply` into a spoke on hub-2 market; hub-2 book: cash = 1,000.
3. Attacker supplies collateral and calls `controller::borrow` on the hub-1 USDC market for `cash_1 - buffer_1` repeatedly (or via `multiply`), until `token.balance(pool) < 1,000`.
4. Victim calls `controller::withdraw` on hub 2: `require_reserves` passes (hub-2 `cash` = 1,000), `token.transfer` in `transfer_out` reverts on insufficient balance — funds frozen until attacker repays.

Validation status: confirmed `require_reserves`/`require_liquidation_buffer` are per-market only and `transfer_out` performs the raw token transfer; the cross-market `Σ cash ≤ balance` check exists only as a fuzz assertion, not in production code. I did not exhaustively trace every caller of `transfer_out`, but `borrow`, `withdraw`, `flash_loan`, and `claim_revenue` all route through the same per-market `cash` guard per the pool README's guard table.

pub(crate) fn require_liquidation_buffer(env: &Env, cache: &Cache, draw: i128) {
    let supplied = cache.unscale_supply_floor(cache.supplied());
    let reserved = mul_div_ceil(env, supplied, LIQUIDATION_BUFFER_BPS, BPS);
    assert_with_error!(
        env,
        cache.cash().saturating_sub(draw) >= reserved,
        CollateralError::InsufficientLiquidity
    );
}

fn assert_cash_matches_balance(
    env: &Env,
    pool: &LiquidityPoolClient<'_>,
    pool_addr: &Address,
    asset: &Address,
    state: &PoolStateRaw,
) {
    let sibling = pool_state(pool, &hub_asset_in(asset, SIBLING_HUB_ID)).cash;
    let tracked = state.cash + sibling;
    let balance = pool_balance(env, asset, pool_addr);
    assert!(
        tracked <= balance,
        "tracked cash across markets on this asset exceeds token balance: \
         driven={} sibling={} balance={}",
        state.cash,
        sibling,
        balance,
    );
}
