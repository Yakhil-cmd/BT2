### Title
Deploy environment variables are whitelisted against the stack's cached (HEAD) `shipit.yml`, not the `shipit.yml` of the commit actually being deployed - ([File: app/models/shipit/stack.rb])

### Summary
The vulnerability class in the external report is a deployment-trust binding break: a value that is *validated* against one authority is later *acted on* under a different authority (a signature covers one payload field while another unverified field drives execution). The closest analog reachable in this engine's own code — without any special privilege beyond a normal deploy request — is the mismatch between the `shipit.yml` used to authorize (whitelist) deploy environment variables at deploy-creation time and the `shipit.yml` that is actually loaded and executed for the specific commit (`until_commit`) that gets deployed.

### Finding Description
`Stack#build_deploy` filters user-supplied `env` through `filter_deploy_envs`, which is delegated to `cached_deploy_spec`: [1](#0-0) [2](#0-1) 

`cached_deploy_spec` is a serialized snapshot of the `shipit.yml` computed asynchronously by `CacheDeploySpecJob`, checked out from `stack.commits.reachable.last` — i.e., essentially the branch HEAD — not the commit the current deploy targets: [3](#0-2) 

However, when the deploy actually runs, the executed steps/commands and their environment are derived from `TaskCommands#deploy_spec`, which is loaded from the commit checked out into `@task.working_directory` — i.e., the specific `until_commit` for that task, which can differ from the HEAD commit used to populate `cached_deploy_spec` (e.g., deploying/rolling back to an older SHA, or a race between a push and a deploy request): [4](#0-3) 

Crucially, `TaskCommands#env` merges the already-filtered `@task.env` (permitted at creation time against `cached_deploy_spec`) unconditionally into the process environment, without re-filtering it against the `deploy_spec` of the commit that is actually checked out and executed: [5](#0-4) 

This is the same trust-binding gap as the report's core theme: the entity that authorizes a field (here, the whitelist of permitted deploy variable names, taken from the stack's cached/HEAD `shipit.yml`) is not the same entity whose logic ultimately consumes/executes that field (the `shipit.yml` of the specific commit being deployed, read fresh from disk at run time). Equality that should hold — "the `shipit.yml` that authorized these variable names == the `shipit.yml` whose deploy steps execute with those variables" — does not hold whenever the two commits diverge.

### Impact Explanation
If a repository's `shipit.yml` at HEAD declares a deploy variable (e.g., a variable that gets interpolated into a shell command in `deploy.override`) that is *not* declared, or is declared with different semantics/defaults, in the `shipit.yml` of an older commit still selectable for deploy, an authenticated deploy-triggering user can pass that variable through `filter_deploy_envs` (validated against HEAD) and have it merged into the task's environment when the actual deploy steps run against the older commit's script — a script that never opted into receiving that variable and may not sanitize/expect it. Because deploy step templates are shell commands sourced from `shipit.yml` (see `deploy.override` /`deploy.pre`/`deploy.post` and variable interpolation in README), smuggling an unexpected/unvalidated environment variable into those commands can result in command/argument injection on the deploy host, i.e. escalate to RCE on the deploy host — matching the Critical impact bar in this engine's context.

### Likelihood Explanation
Exploitation requires: (1) the ability to trigger a deploy to a specific older, still-deployable commit (a normal, unprivileged capability for any user permitted to deploy the stack), and (2) a repository maintainer having, at some point, changed the variable whitelist between commits (adding or renaming a deploy variable, or changing how a variable is consumed in the script) — which is a routine occurrence in active repositories, not a contrived edge case, especially given `CacheDeploySpecJob`'s explicit reliance on `reachable.last` and asynchronous, potentially-stale caching. The engine's own comments acknowledge the cache can be stale relative to the actual HEAD (`CacheDeploySpecJob`'s re-enqueue logic when "the head moved under us"). This makes the divergence between cached and actual spec a realistic, recurring condition rather than a rare corner case.

### Recommendation
- Re-validate/re-filter `Task#env` (and `Deploy#env`) against the `DeploySpec` of the commit actually checked out for execution (`TaskCommands#deploy_spec`) immediately before merging into the process environment in `TaskCommands#env`, rather than trusting the whitelist decision made at creation time against `cached_deploy_spec`.
- Alternatively, compute `filter_deploy_envs`/`filter_rollback_envs` from a `DeploySpec::FileSystem` built from `until_commit` (the actual commit being deployed) rather than from the stack's asynchronously cached, HEAD-derived spec.
- Ensure `CacheDeploySpecJob`'s cache is never treated as authoritative for enforcement decisions tied to a specific commit's contents; use it only for UI/discovery purposes.

### Proof of Concept
1. Repository's `shipit.yml` at commit `A` (older, still deployable) has no `deploy.variables` entries (or a narrow set).
2. A maintainer later pushes commit `B` (new HEAD) that adds a deploy variable, e.g. `EXTRA_FLAG`, used unsafely in `deploy.override` (e.g. `./script/deploy $EXTRA_FLAG`).
3. `CacheDeploySpecJob` runs and updates `stack.cached_deploy_spec` to reflect commit `B`'s `shipit.yml`, including the new `EXTRA_FLAG` variable definition — see `app/jobs/shipit/cache_deploy_spec_job.rb:16-29`.
4. An authenticated user with deploy rights issues `POST /stacks/:id/deploys` with `until_commit_id` pointing at commit `A` and `env: { EXTRA_FLAG: "; malicious-command #" }`.
5. `DeploysController#create` → `Stack#build_deploy` → `filter_deploy_envs` (delegated to `cached_deploy_spec`, i.e., commit `B`'s spec) permits `EXTRA_FLAG` because it is declared in the cached (HEAD) spec — see `app/models/shipit/stack.rb:161-172` and `:527-531`.
6. The deploy task checks out commit `A` and `TaskCommands#deploy_spec` loads commit `A`'s `shipit.yml` (which never declared `EXTRA_FLAG`) — see `lib/shipit/task_commands.rb:13-15`.
7. `TaskCommands#env` merges `@task.env` (containing the attacker-controlled `EXTRA_FLAG`) unconditionally, without re-checking it against commit `A`'s variable whitelist — see `lib/shipit/task_commands.rb:33-48` — and the deploy step(s) from commit `A`'s script execute with `EXTRA_FLAG` set in the shell environment, potentially enabling injection depending on how the deploy script or shell interpolation consumes it.

```ruby
    def perform(stack)
      return if stack.inaccessible?

      commit = stack.commits.reachable.last
      commands = Commands.for(stack)
      commands.with_temporary_working_directory(commit:, recursive: false) do |path|
        stack.update!(cached_deploy_spec: DeploySpec::FileSystem.new(path, stack))
      end

      # A duplicate enqueued while this job held the dedupe lock was dropped;
      # if the head moved under us, that dropped job's work is still
      # outstanding, so hand it off rather than leaving the spec stale.
      CacheDeploySpecJob.perform_later(stack) if stack.commits.reachable.last&.id != commit&.id
    end
```
