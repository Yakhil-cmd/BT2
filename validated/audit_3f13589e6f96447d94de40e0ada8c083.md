### Title
Webhook signature verification keys off an unauthenticated `repository.owner.login`/`organization.login` field while handlers act on the separate, equally unauthenticated `repository.full_name` field, letting a webhook sender that holds one organization's `webhook_secret` forge events against any other tracked repository/stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to validate the HMAC signature against using a value pulled straight out of the *unverified* JSON body (`repository_owner`), before the signature has been checked [1](#0-0) . That same request body is then dispatched unchanged to the event handlers, which independently resolve the target `Repository`/`Stack` from a *different* field of the same body: `repository.full_name` [2](#0-1) . Nothing ties the field used to pick the verifying secret (`repository.owner.login`/`organization.login`) to the field used to select what gets written (`repository.full_name`), and the `StatusHandler` doesn't scope by repository at all — it matches on bare commit `sha` across the whole installation [3](#0-2) .

### Finding Description
This is a direct analog of the reported bug class: a value is trusted/acted upon that was never actually covered by the cryptographic check meant to authorize it. In the Seaport report, the recipient identity used to decide the payment mechanism (ETH vs WETH) diverges from the recipient that ends up controlling the funds. Here, the **organization whose secret authenticated the request** diverges from the **repository that the handlers actually write to**.

Concretely:
- `repository_owner` (used only to select which app/secret validates `X-Hub-Signature`) is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) of the raw, not-yet-verified body [4](#0-3) .
- The base `Handler` class resolves `stacks`/`repository_name` from `payload.dig('repository', 'full_name')` [2](#0-1) , an independent JSON field.
- Shipit explicitly documents and supports running with multiple GitHub Apps, one per organization, each with its own `webhook_secret` in `config/secrets.yml` [5](#0-4) [6](#0-5) .
- In that supported multi-org configuration, a party who legitimately knows/controls one org's `webhook_secret` (e.g., the admin/owner of org A, onboarded as a tenant of the shared Shipit instance) can compute a valid HMAC over an arbitrary JSON body. `verify_webhook_signature` performs no further binding: it just checks the HMAC against whatever `webhook_secret` was selected by `repository_owner` [7](#0-6) .
- The attacker sets `repository.owner.login`/`organization.login` = "org-A" (their own, to make `Shipit.github(organization: repository_owner)` pick org A's known secret) while setting `repository.full_name` = "org-B/victim-repo" (or, for `status` events, simply an arbitrary `sha` belonging to a commit tracked under any stack in the instance — `StatusHandler` never checks the requesting org against the commit's owning repository at all) [8](#0-7) .
- Because the signature check never re-derives or compares the org against `full_name`/`sha`, the forged, correctly-signed request is accepted (`head(:ok)` after `verify_signature` passes) and dispatched to handlers that write to org B's stacks/commits [9](#0-8) .

### Impact Explanation
This breaks the trust binding "organization that authenticated == repository that is written." Concrete consequences within the handler set:
- `PushHandler` triggers `stack.sync_github(expected_head_sha: params.after)` on any stack matching the attacker-chosen branch, letting an org-A-signed request drive synchronization of org B's stacks with an attacker-controlled `after` SHA [10](#0-9) .
- `StatusHandler` writes commit statuses (`commit.create_status_from_github!`) for any `Commit` row in the entire installation matching a given `sha`, without any check that the requester's authenticated org owns that repository [3](#0-2) . Since CI status is what gates the merge queue (`MergeRequest::StatusChecker`, `any_status_checks_failed?`, `reject_unless_mergeable!`) and ultimately `merge!` calling GitHub's merge API [11](#0-10) , forging a passing status on a victim commit can unblock/trigger an unauthorized merge, and can also unblock deploy gating (`ci.require`/`ci.blocking`) documented in the deploy spec [12](#0-11) .

This maps to the required "High" bar (escalation causing an unauthorized merge/deploy) via a cross-tenant write that was never authorized for that repository, satisfying the rule's required impact category (unauthorized deploy/merge, cross-repository writes).

### Likelihood Explanation
Requires only that the Shipit instance is configured for multiple GitHub organizations (a documented, supported deployment mode) and that the attacker is a legitimate tenant/admin of one onboarded org who therefore knows that org's own `webhook_secret`. No repository write access to the victim's repo, no `ApiClient` token, and no compromise of the victim's secrets are needed — only crafting a JSON body with mismatched `owner.login`/`organization.login` vs. `full_name`/`sha` and a correctly computed HMAC using the attacker's own known secret.

### Recommendation
Bind the verified secret to the same repository identity the handlers act on: derive the app/secret selection and repository resolution from the identical trusted field (e.g., always use `repository.full_name`'s owner segment for both signature selection and handler dispatch, or re-validate that `repository.owner.login`/`organization.login` matches the owner encoded in `repository.full_name` before processing). Additionally, scope `StatusHandler`'s `Commit.where(sha:)` lookup to commits belonging to stacks under the authenticated organization rather than a bare global `sha` match.

### Proof of Concept
1. Deploy Shipit with the documented multi-org GitHub App configuration (`secrets.yml` containing `github.org-A` and `github.org-B`, each with distinct `webhook_secret`), with a stack tracking `org-B/victim-repo`.
2. As the admin/owner of `org-A` (who legitimately knows `org-A`'s `webhook_secret`), craft a `status` (or `push`) webhook JSON body:
   - `repository.owner.login` = `"org-A"` (so `verify_signature` selects and validates against org-A's known secret).
   - `sha` = the known SHA of a commit on `org-B/victim-repo`'s tracked stack (obtainable via GitHub's public commit history) and `state` = `"success"`.
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(org-A-webhook-secret, body)` and POST to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` passes (`Shipit.github(organization: "org-A").verify_webhook_signature` succeeds) [1](#0-0) ; `StatusHandler.process` then writes a forged `success` status onto the victim commit regardless of which org authenticated it [3](#0-2) , potentially clearing `ci_missing`/`ci_failing` rejection and enabling an unauthorized merge of `org-B`'s pull request.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity

      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
```
