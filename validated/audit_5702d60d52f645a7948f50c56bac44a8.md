### Title
Webhook organization used to select the signing secret is not bound to the repository whose state is written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to check the `X-Hub-Signature` against based on an **unverified field of the same JSON body it is trying to authenticate**. If any organization configured in `Shipit.github` has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` unconditionally returns `true` for that organization, regardless of the actual signature header. An attacker can therefore forge a webhook whose `repository.owner.login`/`organization.login` field points at that unsecured org (satisfying `verify_signature`) while other fields in the same payload (e.g. `repository.full_name`, `after`, `ref`) drive the downstream write against stacks/state that are not actually related to that org's real webhook trust boundary.

### Finding Description
`repository_owner` is read straight from the unauthenticated request body before any signature check occurs: [1](#0-0) 

That value selects the `GitHubApp` instance used to verify the signature: [2](#0-1) 

And `verify_webhook_signature` trusts the request unconditionally whenever the selected app's `webhook_secret` is blank: [3](#0-2) 

The binding that should hold is:

`organization authenticated by verify_signature == organization/repository whose Stack state is mutated by the event handler`

Because `repository_owner` is attacker-controlled JSON (not itself covered by any signature at the time it is read), and because at least one configured organization can legitimately have `webhook_secret: nil` (this is literally the documented default in the shipped example config), an attacker who knows of such an org can craft a payload where the "authenticating" identity (`repository.owner.login`) is the unsecured org while the payload's other fields (`ref`, `after`, `repository.full_name`, etc.) are consumed by the event handler (e.g. `PushHandler#process`) to drive real writes: [4](#0-3) 

Nothing in `verify_signature` re-checks that the org used to select the (absent) secret is the same org that the handler will act on. This is analogous to the M-9 pattern: a value (the "organization" field used purely to pick a trust anchor) is taken at 100% face value without being cryptographically bound to the value that is actually acted upon (the repository/stack the handler mutates), letting an attacker exploit the mismatch for effect they should not be entitled to.

### Impact Explanation
If exploited, this allows an unauthenticated network attacker to inject arbitrary forged GitHub webhook events (push, status, check_suite, membership, etc.) into Shipit as if they came from GitHub, as long as one org in the multi-org configuration has no `webhook_secret`. Depending on the handler reached, this can trigger unauthorized `GithubSyncJob` runs, fabricate commit statuses, or manipulate team/membership records tied to `Shipit.github_teams` authorization — i.e., escalation into the authorization model the engine relies on for deploy access. This matches the High-impact category "escalation into `Shipit.github_teams` authorization" defined in scope.

### Likelihood Explanation
Likelihood depends entirely on operational configuration: the flaw is only exploitable if a deployer configures multiple GitHub organizations in `Shipit.github` and leaves `webhook_secret` blank for at least one of them (a state the shipped example config explicitly shows as the default `# nil`). In a single-org deployment with a secret always configured, this analog does not manifest. This conditional dependency is why likelihood is limited to configurations matching the documented example, rather than being universally exploitable.

### Recommendation
Do not select the verification secret from an unauthenticated field of the payload without also validating that the resolved organization matches the repository ultimately acted upon by the handler. Additionally, treat a missing `webhook_secret` as a hard failure (reject the webhook) rather than as an implicit "always verified" bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Operator configures two GitHub orgs in `Shipit.github`, e.g. `OrgA` (has `webhook_secret` set) and `OrgB` (misconfigured, `webhook_secret: nil`), per the documented layout in `config/secrets.development.shopify.yml`.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and a body such as:
```json
{
  "organization": { "login": "OrgB" },
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/some-tracked-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. `repository_owner` resolves to `OrgB`; `Shipit.github(organization: "OrgB")` returns the `GitHubApp` with a blank `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally regardless of the `X-Hub-Signature` header supplied (or absent).
4. `create` proceeds to `Shipit::Webhooks.for_event('push')`, and `PushHandler#process` looks up stacks matching `full_name`/branch from the payload and calls `stack.sync_github(expected_head_sha: params.after)`, causing Shipit to sync to an attacker-chosen commit SHA for a stack that is nominally governed by `OrgA`'s trust boundary, without ever presenting a valid signature for either org.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
