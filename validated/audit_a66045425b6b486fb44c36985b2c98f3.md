### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit for an incoming GitHub `status` webhook purely by SHA, with no check that the SHA belongs to the repository that actually sent the webhook. Because git commit SHAs are content-addressed and repository-agnostic, an attacker who controls any repository that delivers validly-signed webhooks to the Shipit host can attach a forged status to a commit that has an identical SHA in a completely different, victim stack, directly manipulating `StatusChecker` results consumed by `MergeRequest#reject_unless_mergeable!`/`merge!`.

### Finding Description
The broken binding: the code assumes
`Status.stack_id == the stack of the repository named in the webhook payload that produced it`
but in fact
`Status.stack_id == commit.stack_id, where commit is found solely by Commit.where(sha: params.sha)` — a query with no repository/stack filter at all.

Code path:
- `app/models/shipit/webhooks/handlers/status_handler.rb`:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
The `params` schema only validates `sha`, `state`, and optional `description`/`target_url`/`context`/`created_at`/`branches` — it never checks or requires a `repository` field matching the target commit's stack.
- `app/models/shipit/commit.rb#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, using the found commit's own `stack_id` — whatever stack that commit row belongs to, regardless of which repository's webhook triggered the call.
- `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb` confirms uniqueness is scoped to `(stack_id, sha)`, not `sha` alone — the schema explicitly anticipates the *same sha existing in multiple stacks* (forks, shared upstream history, cherry-picks, subtree merges), so `Commit.where(sha:)` can and does legitimately return rows across unrelated stacks.
- `app/controllers/shipit/webhooks_controller.rb#verify_signature` only authenticates that the payload was signed by GitHub for the organization named in the payload's `repository.owner` — it authenticates *who sent the webhook*, not *whether the sha inside it belongs to that sender's repo*. `drop_unhandled_event` and `verify_signature` never inspect `params.sha` against `repository.full_name`. Consumer side: `MergeRequest#all_status_checks_passed?`, `#any_status_checks_failed?`, `#any_status_checks_missing?` build `StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)` purely from `head.statuses_and_check_runs` (`statuses + check_runs` on the commit), with no re-validation of where each `Status` row originated. [4](#0-3) [5](#0-4) 

Exploit flow:
1. Attacker identifies a victim open-source PR whose head commit is public (necessary anyway for Shipit's GitHub-based merge queue). They reproduce a byte-identical git commit object (same tree, parents, author/committer identities and timestamps, message) in a repository they control — git's content-addressing guarantees the same SHA.
2. Attacker's repository is onboarded to receive/deliver real, GitHub-signed webhooks to the Shipit host (e.g., it's their own fork registered as a Shipit stack, or any repo under an org where Shipit's GitHub App/webhook is installed).
3. Attacker calls GitHub's Statuses API on their own repo/commit (an action fully within their rights on their own repository) with `context` equal to a value present in the victim stack's `merge_request_required_statuses` (configured via the victim's own `shipit.yml`) and `state: failure` (or `success` to force premature merge).
4. GitHub delivers a validly-signed `status` webhook to `POST /webhooks`. `verify_signature` passes because the payload really was signed for the attacker's own organization/repo.
5. `StatusHandler#process` matches `Commit.where(sha: params.sha)`, finds the victim's identical-sha commit row, and calls `create_status_from_github!`, writing a `Status` with `stack_id` = victim stack.
6. `MergeRequest#reject_unless_mergeable!` (via `any_status_checks_failed?`) now sees the forged failing status among `head.statuses_and_check_runs` and calls `reject!('ci_failing')`, or with a forged `success` status it satisfies `all_status_checks_passed?`/`any_status_checks_missing?` to let `merge!` proceed.

None of `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema on `StatusHandler` check that the commit resolved by SHA actually belongs to the repository named in the webhook payload, so the divergence is not caught anywhere in the path.

### Impact Explanation
A payload legitimately originating from repository A (attacker-controlled) mutates stack/commit/merge-request state belonging to repository B (victim), matching the "payload for one repository mutating another's stack, commit… " Critical category, and can directly cause an unauthorized merge (`merge!` firing from a forged `success` status) or a denial-of-service rejection (`reject!('ci_failing')`) of a legitimate PR. It is repeatable against any victim stack/commit whose SHA the attacker can reproduce, and is not limited to a single tenant — any two stacks sharing history (forks, shared upstream, monorepo migrations) are exposed.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository capable of delivering a validly GitHub-signed webhook to the Shipit host (own fork onboarded as a stack, or membership in an org where Shipit's GitHub App/webhook already exists), and (b) the ability to reproduce a byte-identical commit SHA to the victim's head commit, which is straightforward for any commit that is public (a normal precondition for Shipit-based PR merge queues, since the victim's git history is inherently visible). No secrets, tokens, or elevated Shipit roles are required — the attacker only uses their own repository's legitimate GitHub credentials/CI to set statuses on commits they own. This is realistic and repeatable at low cost.

### Recommendation
In `StatusHandler#process` (and `create_status_from_github!`/`replicate_from_github!`), scope the commit lookup to the stack(s) whose registered repository matches the payload's `repository.full_name`/`repository_owner`, e.g. `Commit.joins(:stack).where(sha: params.sha, stack: { repository: expected_repo }).each { ... }`, rejecting or ignoring status events whose declared repository does not match the stack that owns the candidate commit row.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_forgery_test.rb
require 'test_helper'

module Shipit
  class StatusHandlerForgeryTest < ActiveSupport::TestCase
    test "a status webhook for repo A's commit is applied to repo B's stack if the sha collides" do
      victim_stack = shipit_stacks(:shipit) # tracks 'shopify/shipit-engine'
      attacker_stack = shipit_stacks(:cyclimse) # tracks a different repo owned by attacker

      shared_sha = 'deadbeef' * 5
      victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
      # Simulate identical-content commit existing in attacker's own repo/stack
      attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

      merge_request = shipit_merge_requests(:shipit_pending)
      merge_request.stack.update!(cached_deploy_spec: DeploySpec.new(
        'merge' => { 'required_statuses' => ['ci/required'] }
      ))
      merge_request.update!(head: victim_commit)

      forged_params = Webhooks::Handlers::StatusHandler.new_test_params(
        sha: shared_sha, state: 'failure', context: 'ci/required'
      )
      # Binding under test:
      #   LHS: Status row's stack_id after handling
      #   RHS: stack_id of the repository that actually authenticated the webhook (attacker_stack.id)
      Webhooks::Handlers::StatusHandler.call(forged_params) # simulates attacker's validly-signed webhook

      forged_status = victim_commit.reload.statuses.last
      assert_equal victim_stack.id, forged_status.stack_id      # LHS: actually written
      refute_equal attacker_stack.id, forged_status.stack_id    # RHS: binding claims it should be attacker's

      assert merge_request.reload.any_status_checks_failed?
      assert_equal 'ci_failing', merge_request.reject_unless_mergeable! && merge_request.merge_status
    end
  end
end
```
This demonstrates the two sides of the binding diverge: the forged status is attributed to the victim's stack purely because of the SHA match, with no verification that the webhook's authenticated repository owns that commit, and `reject_unless_mergeable!` fires off the forged row alone.
