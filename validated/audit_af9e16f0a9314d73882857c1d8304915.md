## Finding

`StatusHandler` mutates commit CI status for **any** repository tracked by the Shipit instance based solely on a commit SHA, while webhook signature verification only proves that *some* configured GitHub organization sent the request — not that it owns the commit/repository being mutated. [1](#0-0) [2](#0-1) 

### Title
Forged commit-status webhook from any configured GitHub organization bypasses CI-gated deploys for repositories belonging to a different organization/stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
Shipit supports hosting multiple independent GitHub organizations on the same instance, each with its own `webhook_secret` [3](#0-2) . `WebhooksController#verify_signature` resolves *which* organization's secret to validate the HMAC against purely from an attacker-controlled field in the (as-yet-unverified) JSON body, `repository.owner.login`/`organization.login`: [1](#0-0) [4](#0-3) . Once that single check passes, `StatusHandler#process` writes the forged CI status to **every** `Commit` row in the whole database matching the `sha` field of the payload, with no scoping to the organization/repository that produced the valid signature: [5](#0-4) . This is in stark contrast to the base `Handler` class's `stacks`/`repository_name` scoping pattern used by other handlers (e.g. `PushHandler`), which resolves the target `Repository` from `payload.dig('repository','full_name')` before acting [6](#0-5) [7](#0-6)  — `StatusHandler` never calls `stacks` at all.

### Finding Description
The binding that should hold is:
`organization that authenticated the webhook request (via HMAC/webhook_secret)` == `repository/stack whose Commit rows are written by the handler`

Before the pull request/attack sequence: a webhook signed with organization A's `webhook_secret` is only supposed to be able to affect data belonging to organization A's repositories, because `Shipit.github(organization: repository_owner)` is meant to look up the correct app config for that specific org's traffic [8](#0-7) .

After the attack: since `StatusHandler#process` performs `Commit.where(sha: params.sha)` with no repository/stack filter at all [2](#0-1) , a status event that is correctly HMAC-signed with organization A's secret can update the CI status of a `Commit` belonging to organization B's stack, as long as the attacker supplies a `sha` that matches a commit already tracked by Shipit for org B (git SHAs are content hashes — an attacker who can construct/replicate the same tree+parent+author+message can obtain the same SHA in their own repo under org A, then have GitHub legitimately deliver — or self-forge, since they hold org A's secret — a status webhook for that SHA).

That forged status feeds directly into deploy gating: [9](#0-8) 
`deployable?` becomes true (`success? && !blocked?`) once `create_status_from_github!` records a `success` state for the targeted commit, even though the organization that actually owns that stack never approved or produced that CI result.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out as in-scope: an attacker who only controls one organization's webhook secret (a credential scoped to that organization's own GitHub App, not a privileged Shipit account, `ApiClient` token, or the global `webhook_secret`/`api_clients_secret`) can write cross-repository/cross-organization state — forged CI status on commits belonging to a stack they do not control. Because `Commit#deployable?` and `blocked?` gate whether a deploy/rollback is permitted (`require_ci`, `ignore_ci`, blocking statuses), this can be used to force a victim stack's commit into a "deployable" state it should not be in, enabling an unauthorized deploy of that commit, or conversely to poison a victim's commit with a bogus `failure`/blocking status to stall their pipeline. This matches the Critical category "cross-repository writes" / "an unauthorized deploy" defined in scope.

### Likelihood Explanation
Likelihood is moderate-to-high in the realistic deployment shape this engine explicitly documents (multi-org config in `config/secrets.yml`, one `webhook_secret` per organization). No Shipit session, `ApiClient` token, `api_clients_secret`, GitHub App private key, or repository write access is required — only knowledge of one organization's own `webhook_secret`, which by design that organization's own admins possess for their own legitimate integration, and the ability to reproduce/guess a target commit SHA (trivial if the attacker can create an identical commit, e.g. by forking or reproducing content in their own repo, since SHA1 content hashes are deterministic and not organization-scoped).

### Recommendation
`StatusHandler` (and any other handler that writes state keyed only by an identifier extracted from the payload, such as `sha`) must scope its query through the same `repository`/`stack` resolution used for signature verification, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { id: repository.id })`, mirroring the pattern already used in `Handler#stacks`/`PushHandler`. More generally, `WebhooksController#verify_signature` should ensure that the organization resolved for HMAC verification is the same organization whose data every downstream handler is permitted to mutate, rather than trusting an unrelated field of the same unverified-until-that-point payload to pick the verification key.

### Proof of Concept
1. Attacker legitimately owns/administers organization `attacker-org` in the Shipit multi-org config and therefore knows `attacker-org`'s `webhook_secret`.
2. Attacker creates a commit in a repo of `attacker-org` that is content-identical to (or otherwise reproduces the SHA of) a commit already tracked in Shipit for `victim-org/victim-repo`'s stack — or simply already knows the SHA from public commit history if the victim repo is public/forked.
3. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')`, validates the signature successfully [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the victim's commit (no org/repo filter), marking it `success` [2](#0-1) .
7. `victim commit.deployable?` now returns true, allowing the victim stack to be deployed/merged as if CI passed, despite the attacker having no relationship to `victim-org`.

*Note: full confirmation that `Shipit.github(organization:)` supports independently-secreted multi-org configs in production (beyond the documented example) is based on `config/secrets.development.example.yml` and `lib/shipit/github_app.rb`; if the target deployment is single-organization only, the practical severity is reduced to same-organization cross-repository forgery (still a violation, since `StatusHandler` still ignores repository scoping entirely, but the "organization" boundary itself would not be crossed).*

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
```
