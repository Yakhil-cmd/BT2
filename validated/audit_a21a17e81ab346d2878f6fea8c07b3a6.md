## Analog Found

### Title
Webhook signature verification is bound to the payload's claimed organization while handlers act on the payload's `repository.full_name`, allowing signature bypass to forge cross-repository status writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The Sherlock finding describes a broken safety binding: one gate (repayment enable/disable) doesn't cover a related, security-critical operation (liquidation), letting an attacker exploit the gap. The same *class* of bug exists in `WebhooksController`: the cryptographic signature check is bound to the organization named in `repository.owner.login` (or `organization.login`), but the handlers that actually mutate state key off a *different* field, `repository.full_name`, which is never covered by that verification. Combined with the fact that `GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatically verified, an attacker can select an organization with no configured secret to satisfy the "authentication" check while directing the actual write at a repository belonging to a different, fully-secured organization.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/secret to verify against using only the organization identifier in the payload: [1](#0-0) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` resolves the app/secret for whichever org string is supplied, and if that org has no `webhook_secret` configured (the docs and shipped example configs explicitly show `webhook_secret: # nil` as a valid, supported state for multi-org installs), `verify_webhook_signature` unconditionally returns `true`: [3](#0-2) [4](#0-3) [5](#0-4) 

Once the request passes this check, `WebhooksController#create` dispatches the raw JSON to the registered handler for the event, without any further comparison between the organization used for authentication and the repository the handler will act on: [6](#0-5) 

Handlers derive their target repository/stack from `repository.full_name`, a completely independent JSON field from `repository.owner.login`: [7](#0-6) 

`StatusHandler` is even worse: it doesn't scope by repository at all — it looks up `Commit` globally by SHA and writes attacker-supplied `state`/`description`/`target_url`/`context` to a `Status` record for any matching commit anywhere in the Shipit instance: [8](#0-7) 

**Binding broken (equality that should hold but doesn't):**
`organization used to select/verify the webhook signature` == `organization/repository the dispatched handler is permitted to mutate`.

Before the attacker's crafted request: this equality trivially holds because every legitimate webhook from GitHub has `repository.owner.login` and `repository.full_name` referring to the same repository, and every configured org is expected to carry a real `webhook_secret`.

After the attacker's crafted request: an attacker sets `repository.owner.login` (or `organization.login`) to an organization configured in `secrets.yml` **without** a `webhook_secret` (a documented, supported configuration), while setting `repository.full_name`/`sha` to reference a *different*, fully-secured tracked repository/commit. `verify_signature` passes (secret blank ⇒ always verified), but the handler writes state for the unrelated, secured repository.

### Impact Explanation
This is a genuine authentication-bypass leading to a cross-repository, attacker-controlled write, which matches the Critical bucket ("cross-repository writes"). Concretely:
- `StatusHandler` lets an unauthenticated attacker write arbitrary commit statuses (`state`, `description`, `target_url`, `context`) for any commit tracked by any stack in the installation, without ever possessing that repository's/organization's webhook secret. Since `ci.require` statuses gate deploys (per `README.md`), this can be used to force a commit into a "success" CI state to unlock an otherwise-blocked deploy, or spam a "failure" status to block legitimate deploys.
- `PushHandler`/`CheckSuiteHandler` similarly resolve their target purely from `repository.full_name` and can trigger `GithubSyncJob`/`schedule_refresh_check_runs!` against arbitrary tracked stacks, again authenticated only against an unrelated, secret-less organization.

### Likelihood Explanation
Exploitation requires only that the Shipit instance is configured with the multi-organization GitHub App schema and that at least one configured organization has no `webhook_secret` set — a state explicitly documented and shown as valid in `docs/setup.md` and the shipped example/test secrets files (`webhook_secret: # nil`). No credentials, GitHub App keys, session, or `ApiClient` token are needed; the attacker only needs to know (or guess) the name of one org with a blank secret and the `repository.full_name`/commit SHA of the target they want to affect. This is a realistic operational configuration, not a purely theoretical one, since GitHub Apps do not require a webhook secret to function.

### Recommendation
Bind the organization used for signature verification to the organization that owns the repository the handler will actually mutate — reject any webhook where `repository.owner.login`/`organization.login` does not match the owner implied by `repository.full_name`. Additionally, treat a blank `webhook_secret` as a misconfiguration to warn about rather than an implicit "always verified" bypass, and have handlers (especially `StatusHandler`) scope commit/status lookups by the verified repository rather than a global SHA lookup.

### Proof of Concept
1. Configure Shipit with two GitHub orgs: `SecureOrg` (has `webhook_secret` set) tracking `SecureOrg/app`, and `OpenOrg` (no `webhook_secret`, per the documented supported config).
2. POST to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<sha of a commit in SecureOrg/app>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "SecureOrg/app", "owner": { "login": "OpenOrg" } }
}
```
No `X-Hub-Signature` header (or any garbage value) is required.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OpenOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — request passes.
4. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` globally (no repository scoping) and calls `create_status_from_github!`, writing a forged "success" status for the targeted commit in `SecureOrg/app`, potentially unblocking a deploy gated by `ci.require`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
