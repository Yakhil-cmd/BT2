### Title
Webhook signature verification selects the GitHub organization from an unauthenticated payload field, decoupling "which org authenticated" from "which repository is written" - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` config (and thus the webhook secret) to validate a webhook against using `repository_owner`, a value read straight out of the still-unauthenticated request body. Every webhook handler, however, resolves the `Repository`/`Stack` to act on using a *different* field of that same body, `repository.full_name`. Because Shipit supports multiple independently-configured GitHub organizations, and per-organization `webhook_secret` is documented as optional, an unprivileged attacker can pick any organization slot in the installation whose secret is unset to make `verify_webhook_signature` short-circuit to `true`, while pointing the payload's `repository.full_name` at a completely unrelated stack/repository that is actually protected by a secret. No secret, session, or token of any kind is required.

### Finding Description
`WebhooksController#verify_signature` derives the organization used for verification purely from the incoming JSON, before any authentication has taken place: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a `GitHubApp` instance whose `verify_webhook_signature` unconditionally returns `true` when that specific organization has no `webhook_secret` configured: [3](#0-2) 

Multiple, independently-secreted organizations are an explicitly supported deployment shape (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), and leaving `webhook_secret` blank is documented as an optional setting, not a misconfiguration: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (using the org derived from `repository.owner.login`/`organization.login`), `WebhooksController#create` dispatches the *entire raw payload* to the registered handler for the event type: [6](#0-5) 

Every handler, however, resolves the target `Repository`/`Stack` using `repository.full_name`, a field that has no relationship to the field used for signature routing: [7](#0-6) [8](#0-7) [9](#0-8) 

This is the exact class of bug in H-22: one field (`yIntercept`/`slope`, analogous here to the org used for signature selection) is treated as authoritative for a security decision, while a *different* field (`totalAssets` computed from raw balance, analogous here to `repository.full_name` used for the actual state-changing action) is what the effect actually operates on, and the two are never forced to agree.

The equality that should hold but doesn't:
`organization used to select/verify the webhook signature` == `repository/stack that the handler mutates`

Before the attacker's request: only webhooks whose HMAC matches the secret of the *target repository's own organization* are processed for that repository.
After the attacker's request: an attacker who knows nothing about any secret sends one POST to `/webhooks` with `repository.owner.login` (or `organization.login`) set to any organization in the multi-org config that has no `webhook_secret`, and `repository.full_name` set to the name of the actually-targeted repository (belonging to a different, secured organization). `verify_signature` passes unconditionally (blank secret ⇒ `true`), and the handler acts on the targeted repository's stacks exactly as if a legitimate, signed GitHub webhook had arrived for it.

### Impact Explanation
Depending on the event type sent, this allows an unauthenticated attacker to:
- Force `GithubSyncJob` runs and `Commit` status writes on stacks belonging to organizations they have no relationship to (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`), forging CI/commit-status state (`Commit#create_status_from_github!`).
- On stacks with `continuous_deployment` enabled, forging a passing status can make a commit `deployable?`, which is consumed by the continuous-delivery machinery (`Stack.schedule_continuous_delivery`, `Stack#trigger_continuous_delivery`) to trigger a real, unauthorized deploy without any credential.
- Manipulate `pull_request` / merge-queue and review-stack lifecycle handlers for arbitrary repositories (archive/unarchive review stacks, capture labels, etc.).

This crosses the "cross-repository writes" / "unauthorized deploy" bar defined as Critical impact, and requires no session, API token, or knowledge of any secret — only the presence of at least one organization slot in the deployment's multi-org GitHub config without a configured `webhook_secret`, which is an explicitly supported, documented configuration.

### Likelihood Explanation
Likelihood depends entirely on whether the deployment uses multiple GitHub organizations and at least one of them has no `webhook_secret` set (e.g., a staging/internal org, or one where the operator followed the documented "optional" guidance literally). Given the shipped example configs default `webhook_secret` to `nil`/blank, and multi-org support is a first-class documented feature, this is a realistic deployment shape, not a contrived edge case.

### Recommendation
- Verify the webhook signature using the secret belonging to the organization that owns the repository the handler will actually act on (`repository.full_name`'s owner), not a separately-derived `repository_owner` field.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank for *any* configured organization if other organizations in the same installation require a secret; either require a secret to be configured for every organization in a multi-org setup, or fail closed (reject) rather than "pass" when a secret is absent for the org resolved from attacker-controlled input.
- Cross-check that the organization used to authenticate the webhook matches the owner encoded in `repository.full_name` before dispatching to handlers.

### Proof of Concept
Given a Shipit installation configured with two organizations, e.g. `OrgWithoutSecret` (no `webhook_secret`) and `OrgWithSecret/target-repo` (has a `webhook_secret`), an unauthenticated attacker sends:

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything     # irrelevant, will be ignored

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known to exist>",
  "repository": {
    "full_name": "OrgWithSecret/target-repo",
    "owner": { "login": "OrgWithoutSecret" }
  }
}
```

`repository_owner` resolves to `"OrgWithoutSecret"` [2](#0-1) , `Shipit.github(organization: "OrgWithoutSecret")` returns a `GitHubApp` with `webhook_secret` blank, so `verify_webhook_signature` returns `true` regardless of the (bogus) `X-Hub-Signature` [3](#0-2) . The request proceeds to `PushHandler`, which resolves stacks via `repository.full_name == "OrgWithSecret/target-repo"` [7](#0-6)  and enqueues a sync for that stack — despite the attacker never knowing `OrgWithSecret`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
