### Title
Missing Timestamp/Freshness Validation for Signed Packages Enables Replay Attacks - (File: signed_message.js)

### Summary
`signed_message.js`'s `validateSignedMessage()` accepts an optional `timestamp` field in a signed package/message (`objSignedMessage`) as part of its allowed schema, but never validates that this timestamp is fresh, bounded, or otherwise tied to a non-replayable value. This mirrors the lakeFS S3-gateway bug class: a value that is part of the signed payload (and therefore looks like it should provide freshness/anti-replay guarantees) is never actually checked, so a captured, validly-signed package can be replayed indefinitely as long as the underlying signature and (when present) `last_ball_unit` stability checks still pass.

### Finding Description
`validateSignedMessage()` explicitly whitelists `timestamp` as an allowed top-level field of a signed message: [1](#0-0) 

However, nowhere in the function body is `objSignedMessage.timestamp` read, compared against `Date.now()`, or checked against `last_ball_timestamp`/`last_ball_mci` for expiry. The only real anti-replay-adjacent check is the optional `last_ball_unit` freshness for the *definition* lookup, but this only fixes the *definition version* used at validation time — it does not expire the *authorization* itself; the same signed package with the same `last_ball_unit` remains valid to submit at any point in the future (the referenced ball only needs to still be stable and known): [2](#0-1) [3](#0-2) 

This `validateSignedMessage()` function is the sole security boundary reused by:
1. `is_valid_signed_package()` in oscript/AA formula evaluation — reachable by any unprivileged AA trigger sender who embeds a `signed_package` object (e.g. `trigger.data.signed_package`) in a triggering unit: [4](#0-3) 
2. Wallet/device off-chain contract flows (`arbiter_contract_response`, `prosaic_contract_response`), which accept `signed_message` from a paired device/peer to authorize contract-state transitions: [5](#0-4) [6](#0-5) 

Because `timestamp` is defined in the schema but not enforced, any oscript/AA author or wallet flow that relies on the presence of a `timestamp` field for freshness (as its presence in the schema implies it is meant to be used for that purpose) gets no actual protection from ocore itself — replay protection must be independently and correctly re-implemented by every AA author using ad-hoc counters (e.g. the `period` field pattern seen in the payment-channel sample): [7](#0-6) 

If an AA (or off-chain contract flow) does not implement its own strictly-increasing nonce/period and instead relies on `timestamp` (a field ocore explicitly allows for this purpose) to reject stale packages, an attacker who captures a previously valid `signed_package`/`signed_message` (via logs, an intermediary device, an untrusted hub relay, or a previous on-chain trigger) can resubmit it to `is_valid_signed_package` in a new trigger, or resend it to a wallet peer, and it will validate successfully indefinitely.

### Impact Explanation
For AAs that use `is_valid_signed_package` to authorize state changes (fund releases, channel settlements, order execution) keyed off application data rather than a purpose-built nonce, replaying an old — but still cryptographically valid — signed package can cause repeated unauthorized execution of the authorized action (e.g., double-spending an off-chain-authorized transfer, re-triggering settlement with stale balances), i.e. AA fund loss. In the wallet/off-chain contract path, replay of a captured `arbiter_contract_response`/`prosaic_contract_response` signed acceptance can cause a peer to be bound to an already-superseded contract state.

### Likelihood Explanation
Exploitability depends on the specific AA/oscript's use of `is_valid_signed_package` (whether it implements its own nonce, as the shipped sample does) — so this is not universally exploitable, but ocore itself provides no baseline protection and explicitly reserves a `timestamp` field that looks like it should provide one. Any AA author who reasonably assumes ocore validates the `timestamp` field for freshness (since it's part of the accepted schema) is silently unprotected. This is a design/documentation-security gap in the shared library function used by all such applications.

### Recommendation
- In `signed_message.js`, when `timestamp` is present in `objSignedMessage`, enforce a maximum allowed skew against `last_ball_timestamp` (or wall-clock time for non-network-aware calls) so that packages older than a defined TTL are rejected.
- Alternatively/additionally, expose a documented, first-class anti-replay primitive (e.g., a `oscript` built-in `is_valid_signed_package(pkg, address, {max_age: N})`) so AA authors don't have to reinvent nonce/period logic, and update `formula/evaluation.js`'s `is_valid_signed_package` handling to surface and enforce this.
- Update documentation to clarify that `timestamp` in a signed message is currently unenforced and that AA/wallet developers must implement their own strictly increasing nonce (as done in the payment-channel sample) — or better, enforce it in the core so all consumers benefit automatically.

### Proof of Concept
1. Party B signs a package for AA X: `signMessage({ ..., timestamp: T0 }, addressB, ...)`, producing `signed_package_v1`, and sends it to Party A off-chain (e.g., over a device pairing channel or embedded in an earlier trigger's `data`).
2. Party A (or anyone who observes `signed_package_v1`, e.g. via a hub relay, prior unit, or log) posts a unit whose trigger contains `trigger.data.sentByPeer = signed_package_v1` to an AA that checks `is_valid_signed_package(trigger.data.sentByPeer, addressB)` and does not itself enforce a monotonically increasing nonce tied to `timestamp` (only checking the value against, e.g., `trigger.data.amount_spent` business logic).
3. `formula/evaluation.js` → `signed_message.validateSignedMessage()` validates the signature/authentifiers successfully; `timestamp` is never checked, so validation succeeds even though `T0` is long expired.
4. The AA executes the authorized action again using the stale package, since ocore performed no freshness check: [8](#0-7) [1](#0-0)
