### Title
Cross-tenant membership forgery via `MembershipHandler#find_or_create_team!` ignoring organization binding - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#process` looks up the target `Team` solely by the attacker-supplied `team.id` and never checks that the webhook's `organization.login` (used to select which webhook secret verifies the signature) actually matches that team's `organization`. Because `WebhooksController#verify_signature` picks the verifying `GitHubApp` config from the attacker-controlled `organization.login`/`repository.owner.login` field, an attacker who owns their own tenant (their own org with its own `Shipit::GithubHook::Organization` row/secret) can sign a `membership` `added` event that names a `team.id` belonging to a *different*, privileged team (one listed in `Shipit.github_teams`) and add themselves to it.

### Finding Description
Broken binding, stated explicitly:
`Membership(team_id: T, user_id: U) exists in Shipit's DB` should imply `GitHub reported, for the organization owning team T, that member U was added to team T`. This is violated whenever `T` is a team belonging to organization `O_real` but the webhook that created the row was verified using organization `O_attacker`'s secret.

Code path:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` (app/controllers/shipit/webhooks_controller.rb:59-62). For a `membership` payload there is no `repository` key, so this resolves to the attacker-supplied `organization.login`.
2. `Shipit.github(organization: repository_owner)` (lib/shipit.rb) fetches the `GitHubApp` config keyed by that attacker-controlled organization name, i.e. the attacker's own configured tenant, whose `webhook_secret` the attacker knows because they set it up themselves. The HMAC signature therefore validates.
3. The verified payload is dispatched to `Handlers::MembershipHandler.call(params)` → `#process` (app/models/shipit/webhooks/handlers/membership_handler.rb:22-34), which calls `find_or_create_team!`:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [1](#0-0) 
This performs a lookup keyed **only** on `github_id`. Since the target Team already exists (it's one of `Shipit.github_teams`), the block (which would set `organization`) never runs — the existing record is returned as-is, with no comparison between `params.organization.login` (the org whose secret verified the signature) and `team.organization` (the org the team actually belongs to).
4. `process` then calls `team.add_member(member)` (`Team#add_member`, app/models/shipit/team.rb:41-43), inserting a `Membership` row for the attacker's own `User` (created via `User.find_or_create_by_login!(params.member.login)`) against the *real* privileged team.
5. `User#authorized?` (app/models/shipit/user.rb:80-82) checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, which is now true for the attacker.

Existing guards do not stop this: `verify_signature` only proves the payload was signed by *some* org the attacker controls, not that it was signed by the org owning the referenced `team.id`; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence of fields, not cross-organization consistency; there is no check anywhere binding `params.organization.login` to `team.organization` in `MembershipHandler`.

### Impact Explanation
The attacker gains membership in an arbitrary team already trusted by `Shipit.github_teams`, which flips `User#authorized?` to `true` and grants them access to the entire Shipit application — stacks, deploys, rollbacks, API client management — as if they were a legitimate member of the real organization's team. This is a full authentication/authorization bypass of Shipit's own access control, exploitable repeatedly and requiring no privileges in the target organization; only knowledge of the target team's numeric `github_id` (typically discoverable via GitHub's team API/URLs) and control of any tenant configured in Shipit is needed. Blast radius spans all stacks/repositories gated behind `Shipit.github_teams`, i.e. the entire Shipit deployment, since authorization is global per user, not per-repository.

### Likelihood Explanation
Preconditions: the attacker must control at least one GitHub organization that has been configured as a valid tenant in Shipit (`Shipit::GithubHook::Organization` row with a known `webhook_secret`) — which the rules state is an available attacker capability ("attacker owns a GitHub org/repo with a configured Shipit github_hooks Organization row"). The target `team.id` (GitHub's numeric team ID) must be known or guessed; this is a modest but realistic bar. No other privileged secrets are needed. The attack is a single POST to `/webhooks` and is fully repeatable against any team ID.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that `params.organization.login` matches the `organization` column of any existing `Team` found by `github_id` before proceeding (reject/raise if they differ), and/or bind the webhook signature verification more strictly by cross-checking the verifying organization against the `Team#organization` before calling `add_member`/`members.delete`. At minimum, scope the `find_or_create_by!` lookup with `organization: params.organization.login` in addition to `github_id`, ensuring a `Team` record can never be mutated by a webhook signed for a different organization.

### Proof of Concept
minitest plan (controller-level, no live GitHub):
```ruby
test "membership webhook signed by attacker org cannot grant membership to a team owned by another org" do
  target_team = shipit_teams(:shopify_developers) # organization: "shopify", already in Shipit.github_teams
  Shipit.stubs(:github_teams).returns([target_team])

  # Attacker's own tenant config, verified via GithubHook.any_instance.stubs(:verify_signature) style used elsewhere,
  # or by stubbing Shipit.github(organization: 'attacker-org').verify_webhook_signature to return true.
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # or equivalent signature stub for 'attacker-org'

  request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: target_team.github_id, name: target_team.name, slug: target_team.slug, url: target_team.api_url },
    organization: { login: 'attacker-org' }, # attacker's own org, NOT "shopify"
    member: { login: 'attacker' }
  }.to_json

  post :create, body: payload, as: :json
  assert_response :ok

  attacker = Shipit::User.find_by!(login: 'attacker')

  # Broken binding assertion:
  # LHS: Membership(team_id: target_team.id, user_id: attacker.id) now exists in Shipit's DB
  assert target_team.members.reload.include?(attacker)
  # RHS: GitHub never reported this for org "shopify" (the org that actually owns target_team) — only "attacker-org" signed it.
  # Yet authorization is granted:
  assert attacker.authorized?
end
```
This demonstrates that `User#authorized?` becomes `true` for a `User` created purely from a webhook signed by an organization the attacker controls, despite `team.organization` ("shopify") never matching the signing organization ("attacker-org").
