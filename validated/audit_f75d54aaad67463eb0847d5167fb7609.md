### Title
Permanent Pairing Secret Remains Valid After Device Unpairing, Allowing Revoked Correspondents to Re-Pair - (File: device.js)

### Summary
`device.js`'s permanent pairing mechanism (`getOrGeneratePermanentPairingInfo`) creates a `pairing_secret` with `is_permanent=1` and an expiry date of `'2038-01-01'` [1](#0-0) . Unlike a one-time pairing secret, this permanent secret is never deleted, rotated, or otherwise invalidated when the correspondent it was used to pair is later removed. This is analogous to the Jupyter Server bug: a long-lived secret used for authorization (`pairing_secret` for cookie secret) is not revoked when the corresponding trust relationship is terminated (unpairing for password reset).

### Finding Description
When a device pairs using a permanent pairing secret, `handlePairingMessage` explicitly skips deletion of the secret because it is permanent: only non-permanent secrets are deleted after use, `if (pairing_rows[0].is_permanent === 0){ ... DELETE FROM pairing_secrets ... }` [2](#0-1) . The permanent secret is handed out to counterparties, e.g. it is embedded in a `my_pairing_code` sent to the peer device address as part of the `arbiter_contract.js` `respond()` flow when a contract is accepted [3](#0-2) , and it can also be shared through `byteball:`/`obyte:` pairing URIs parsed by `uri.js` [4](#0-3) .

When a user later decides to revoke a correspondent (e.g., because a device/key was compromised, or the counterparty misbehaved), the only mechanism available is `removeCorrespondentDevice`, which deletes rows from `outbox` and `correspondent_devices`, but never touches the `pairing_secrets` table [5](#0-4) . This function is invoked, for example, when a peer requests unpairing via the `removed_paired_device` message handler in `wallet.js` [6](#0-5) .

Because the permanent pairing secret is untouched by this "revocation" operation, and it does not expire until 2038, anyone who previously obtained it (including the exact correspondent that was just removed) can immediately resend a `pairing` message with the same still-valid `pairing_secret` and be silently re-inserted into `correspondent_devices` as a confirmed, non-blackholed correspondent via `handlePairingMessage` [7](#0-6) .

### Impact Explanation
Correspondent status is not merely a chat contact list — it gates which paired devices are allowed to participate in signing-related protocol flows: `wallet.js`'s `readNonRemovableDevices` cross-references `correspondent_devices`-derived device addresses with `shared_address_signing_paths`, `wallet_signing_paths`, `pending_shared_address_signing_paths`, `prosaic_contracts`, and `wallet_arbiter_contracts` to decide whether a device is safe to remove [8](#0-7) . A revoked device that silently re-pairs using the still-valid permanent secret regains the ability to send/receive device messages tied to these flows (multi-sig signature requests, arbiter contract negotiation/dispute messages, private payment chains) as a trusted correspondent, undermining the user's revocation decision without any further warning. Since correspondent identity underlies which counterparties are trusted for cosigning and private-payment chain exchange, this creates a path toward continued unauthorized participation in fund-related flows after the user believed access was cut off.

### Likelihood Explanation
The permanent pairing secret is by design shared out-of-band with counterparties (arbiter contract peers, other cosigners) and is explicitly intended for reuse, `db.query("SELECT pairing_secret FROM pairing_secrets WHERE is_permanent=1 ...")` [9](#0-8) , so a legitimate former counterparty already possesses it. No additional exploitation is required — simply replaying the same pairing message after being removed. Likelihood is therefore high for the removed-counterparty scenario, though realizing fund-loss impact requires an additional protocol step (participation in signing/arbiter flows).

### Recommendation
- When a correspondent is removed via `removeCorrespondentDevice`, also invalidate/rotate any permanent pairing secret that was used to establish that specific pairing, or at minimum require the local user to re-approve any subsequent re-pairing attempt from a device address that was previously removed.
- Consider tracking which pairing_secret established each correspondent relationship and revoking/regenerating that secret (or blacklisting the device address) on unpairing, rather than only deleting `correspondent_devices`/`outbox` rows.
- Alternatively, emit a UI-level warning/require explicit re-confirmation whenever a `pairing` message auto-restores a correspondent that had previously been removed.

### Proof of Concept
1. Device A generates a permanent pairing code via `getOrGeneratePermanentPairingInfo` and shares it with Device B, e.g., through the arbiter-contract acceptance flow (`arbiter_contract.js respond()`), which pairs B as a confirmed correspondent through `handlePairingMessage`.
2. The user later removes B as an untrusted correspondent, e.g., by processing a `removed_paired_device` message or otherwise calling `device.removeCorrespondentDevice(B, ...)`.
3. `pairing_secrets` still contains B's usable permanent secret because `is_permanent=1` rows are never deleted or expired (expiry `'2038-01-01'`).
4. Device B (or a colluding third party who obtained the code) resends the original `pairing` message with the same `pairing_secret` to Device A's hub.
5. `handlePairingMessage` finds the still-valid `is_permanent=1` row and silently re-inserts B into `correspondent_devices` with `is_confirmed=1`, restoring B's trusted correspondent status without any fresh authorization from the user.

			pairing_secret = crypto.randomBytes(9).toString("base64");

function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
				[from_address, device_pubkey, json.device_hub, safe_device_name],
				function(){
					db.query( // don't update name if already confirmed
						"UPDATE correspondent_devices SET is_confirmed=1, name=? WHERE device_address=? AND is_confirmed=0", 
						[safe_device_name, from_address],
						function(){
							db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
								eventBus.emit("paired", from_address, body.pairing_secret);
								if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
									db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
									eventBus.emit('paired_by_secret-'+body.pairing_secret, from_address);
								}
								if (body.reverse_pairing_secret)
									sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null);
								callbacks.ifOk();
							});
						}
					);
				}
			);
		}
	);
}

function readNonRemovableDevices(onDone){

	var sql = "SELECT DISTINCT device_address FROM shared_address_signing_paths ";
	sql += "UNION SELECT DISTINCT device_address FROM wallet_signing_paths ";
	sql += "UNION SELECT DISTINCT device_address FROM pending_shared_address_signing_paths ";
	sql += "UNION SELECT DISTINCT peer_device_address AS device_address FROM prosaic_contracts ";
	sql += "UNION SELECT DISTINCT peer_device_address AS device_address FROM wallet_arbiter_contracts ";
	sql += "UNION SELECT DISTINCT arbstore_device_address AS device_address FROM arbiter_disputes ";
	if (conf.ArbStoreWebURI)
		sql += "UNION SELECT DISTINCT device_address AS device_address FROM arbiters";
	
	db.query(
		sql, 
		function(rows){
			
			var arrDeviceAddress = rows.map(function(r) { return r.device_address; });

			onDone(arrDeviceAddress);
		}
	);
}

function determineIfDeviceCanBeRemoved(device_address, handleResult) {
	device.readCorrespondent(device_address, function(correspondent){
		if (!correspondent)
			return handleResult(false);
		readNonRemovableDevices(function(arrDeviceAddresses){
			handleResult(arrDeviceAddresses.indexOf(device_address) === -1);
		});
	});
};
