### Title
Asset attestor list can be changed by the definer at any time, freezing/redirecting `spender_attested` asset transfers - ([File: validation.js])

### Summary
For assets created with `spender_attested: true`, transfers are permitted only to addresses that are "attested" by one of the addresses in the asset's current attestor list. This attestor list is not fixed at asset issuance; the asset definer can post an `asset_attestors` message at any time, with no timelock, quorum, or decentralization requirement, instantly changing which attestor addresses are trusted for that asset. This is directly analogous to the reported issue of `yieldTracker` addresses being changeable by governance at any time, creating unreviewed risk (including denial-of-service) for downstream users who rely on those addresses continuing to behave as originally agreed.

### Finding Description
When an asset is defined with `spender_attested: true`, every payment output must be sent to an address attested by one of the asset's attestors, enforced in `validatePaymentInputsAndOutputs`: [1](#0-0) 

The attestor list used for this check is always the *latest* one posted for the asset, chosen purely by DAG level/rowid, with no cap on how often it can change: [2](#0-1) 

The only party who is allowed to update this list is the original `definer_address`, and the update is accepted unconditionally as long as the asset requires attestation — there is no cooldown, no multi-party approval, no notice period, and no restriction preventing the definer from swapping in a completely different attestor set (including addresses they fully control) or removing attestors that previously vouched for existing holders: [3](#0-2) [4](#0-3) 

The write path simply appends a fresh row set for the asset without invalidating or checking against the previous list's intent: [5](#0-4) 

Because holders/AAs/wallets build their trust and payment logic around "this asset lets me pay to addresses attested by X, Y, Z", but X, Y, Z can be swapped out unilaterally and instantly by the definer, any code (wallet, AA, or exchange contract) that assumes attestor addresses are stable for a `spender_attested` asset can be broken without warning.

### Impact Explanation
- **Denial of Service on transfers**: if the definer removes/rotates the attestor addresses (maliciously, by mistake, or because a key was compromised), all previously-attested holders instantly lose the ability to receive/transfer the asset until they re-obtain attestation from the new attestor set — freezing funds for legitimate holders who did nothing wrong.
- **Unauthorized redirection of trust**: the definer (or an attacker who compromises the definer's key) can replace attestors with addresses under their own control and then self-attest arbitrary addresses, bypassing the KYC/whitelist guarantee the `spender_attested` flag was supposed to provide to third parties (exchanges, AAs, counterparties) who integrated with the asset expecting the original attestor set.
- Any AA or contract that hard-codes trust in specific attestor addresses for a `spender_attested` asset (a normal integration pattern) can have its logic silently invalidated, matching the reported class of bug: "undiscovered or unknown bugs such as Denial of Service" stemming from an address that can be changed at any time by a privileged party with no checks.

### Likelihood Explanation
Any asset definer can trigger this unilaterally at any point after asset creation by posting a single `asset_attestors` message — no cooperation from holders, no delay, no multisig requirement beyond controlling the definer address. This is a normal, always-available action in the protocol, not requiring a hard fork or edge case, making the likelihood of accidental or malicious misuse realistic wherever third parties build durable trust assumptions on top of a `spender_attested` asset's attestor list.

### Recommendation
- Add safeguards analogous to what the original report recommends for `yieldTrackers`: e.g., a timelock/delay before an `asset_attestors` update takes effect, requiring events/notice so integrators can react; or an option to make the attestor list immutable at issuance for assets that opt in.
- Consider requiring some minimal decentralization for attestor list changes (e.g., multi-attestor consensus) rather than sole control by `definer_address`, or clearly document the trust assumption so downstream contracts do not treat the attestor list as immutable when it is not.

### Proof of Concept
1. Definer issues asset `A` with `spender_attested: true`, `attestors: [X]`. Users obtain attestation from `X` and are able to send/receive `A`.
2. An AA or third-party wallet is built assuming attestor `X` remains authoritative for asset `A`.
3. Definer posts a single-authored `asset_attestors` message for asset `A` with `attestors: [Y]` (a brand-new address), which is accepted per `validateAttestorListUpdate` (`validation.js:2829-2848`) with no additional checks.
4. `storage.readAsset` (`storage.js:1917-1946`) now returns `Y` as the sole valid attestor going forward; every future payment of asset `A` is checked with `storage.filterAttestedAddresses` (`validation.js:2632-2641`) against `Y` only.
5. All holders/output addresses previously attested only by `X` fail the `"some output addresses are not attested"` check and can no longer transfer asset `A` until re-attested by `Y` — a definer-triggered denial of service — or, if `Y` is controlled by the definer, the definer can self-attest arbitrary new addresses, undermining the original attestation guarantee relied upon by holders and integrators.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
