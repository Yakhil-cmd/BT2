### Title
Webhook signature is authenticated against `repository.owner.login`, but the repository actually written to is selected by the unrelated `repository.full_name` field, enabling cross-organization webhook forgery in multi-tenant Shipit deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to authenticate an inbound webhook based on `repository.owner.login` (falling back to `organization.login`), a field taken from the attacker-suppliable JSON body itself. The event is then dispatched to handlers that determine the *actual target repository/stack* using an entirely different field of the same body, `repository.full_name` (via `Handler#repository_name`). Nothing ties these two fields together, so the organization whose secret is used to authenticate the request is not required to equal the organization whose repository is actually mutated.

### Finding Description
`verify_signature` picks the signing key like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the untrusted JSON payload before the HMAC check is even performed. The signature validation itself (`GitHubApp#verify_webhook_signature`) validates the whole raw body against the secret configured for that `organization` key — it does not, and cannot, verify that other fields inside that same body (like `repository.full_name`) actually belong to that organization: [3](#0-2) 

Once the signature is accepted, the actual write target is resolved independently, by every `Handler` subclass, from `repository.full_name` — a completely different field of the same payload: [4](#0-3) 

For example `PushHandler` uses `stacks` (built from `repository_name`) to trigger a GitHub sync on whatever stack it resolves to: [5](#0-4) 

`Shipit.github(organization:)` looks up per-organization app credentials from `secrets.github`, confirming Shipit explicitly supports multi-tenant setups where multiple GitHub organizations, each with its own `webhook_secret`, are configured on a single Shipit instance: [6](#0-5) 

This breaks the intended equality: `organization authenticated by the signature check == organization whose repository is mutated by the handler`. Concretely, the code proves "the sender knows organization A's `webhook_secret`" but then acts on whatever `repository.full_name` says, with no assertion that `repository.full_name`'s owner equals `repository.owner.login`/`organization.login` used for authentication.

### Impact Explanation
In a multi-organization Shipit deployment (the officially supported per-organization `github:` credentials schema shown in `lib/shipit.rb#github_app_config` and `config/secrets.development.shopify.yml`), anyone who possesses the webhook secret for one low-value/less-trusted organization configured on the instance can forge a webhook payload whose `repository.owner.login`/`organization.login` names that low-value org (so it authenticates and picks the correct signing key) while `repository.full_name` names a repository/stack that actually belongs to a different, more sensitive organization also hosted on the same instance. Because handlers key exclusively off `repository.full_name`, the forged event is applied to the unrelated organization's stack. Depending on the webhook event type this allows unauthorized cross-repository writes — e.g. forced GitHub syncs, injected/forged commit statuses (which can be used to satisfy CI-gating and enable an unauthorized deploy through the merge queue / continuous deployment path), or spoofed `check_suite` refreshes — against repositories the attacker's known secret was never meant to authorize.

### Likelihood Explanation
Exploitation requires only knowledge of any one organization's `webhook_secret` configured on a shared/multi-tenant Shipit instance (which is a normal, documented deployment topology for this engine, not a privileged Shipit session or `ApiClient` token), plus the ability to build a crafted JSON payload — no GitHub repository access or Shipit account is required. The mismatch between the field used for authentication and the field used to resolve the mutation target is a straightforward, always-reachable code path (`before_action :verify_signature` then unconditional handler dispatch in `create`), making this a structural rather than probabilistic issue for any instance hosting more than one organization.

### Recommendation
After successfully verifying the signature for `repository_owner`, require that the owner portion of `repository.full_name` (or `organization.login`, for org-scoped events) matches the authenticated `repository_owner`/organization before dispatching to handlers. Reject the webhook (422) on mismatch, mirroring the fix pattern from the referenced report: use a single, consistently-verified identifier for both the authentication decision and the mutation target instead of trusting two independently-controlled fields from the same unauthenticated-until-verified payload.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `orgA` (attacker knows/controls `webhook_secret: secretA`) and `orgB` (hosts a sensitive stack tracked by Shipit), per the `github:` multi-org schema in `lib/shipit.rb#github_app_config`.
2. Attacker builds a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/sensitive-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(secretA, raw_body)` and sends it with `X-Github-Event: push` to `POST /github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")`, whose `webhook_secret` matches, so `verify_webhook_signature` returns `true`. [1](#0-0) 
5. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, which resolves `stacks` from `repository.full_name == "orgB/sensitive-repo"` and triggers `stack.sync_github(expected_head_sha: ...)` against `orgB`'s stack, even though the request was authenticated only via `orgA`'s secret. [4](#0-3) [5](#0-4)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
