### Title
Cross-repository commit-status forgery via unscoped webhook `status`/`check_suite` handlers - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App secret to verify a webhook's HMAC based on `repository.owner.login` (or `organization.login`) taken from the JSON body, and only checks that this organization's `webhook_secret` matches. It never verifies that the rest of the payload actually belongs to that organization/repository. `Webhooks::Handlers::StatusHandler` then acts on `params.sha` alone, with no repository/organization scoping at all, while `CheckSuiteHandler`/push/pull_request handlers scope only by `repository.full_name`, a field that is likewise never cross-checked against the signing organization. Any organization onboarded on a shared Shipit instance can therefore forge a signed webhook (signed with its own legitimate `webhook_secret`) that writes commit statuses, or triggers check-run refreshes, against commits/stacks belonging to a completely different organization/repository.

### Finding Description
The binding that should hold is:

`organization that authenticated the webhook == repository/commit that is written by the handler`

but this equality is never enforced.

- `WebhooksController#verify_signature` computes `repository_owner` from the payload and fetches `Shipit.github(organization: repository_owner)` to verify the HMAC signature: [1](#0-0) [2](#0-1) 
- Once verified, the controller dispatches the *entire* parsed payload to every registered handler for the event, with no additional cross-check: [3](#0-2) 
- `StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` — no repository or stack scoping whatsoever — and writes a GitHub status onto them: [4](#0-3) 
- `CheckSuiteHandler#process` scopes only through `stacks`, which is derived from `payload.dig('repository', 'full_name')` in the shared `Handler` base class — a field distinct from the `repository.owner.login`/`organization.login` field used for signature verification: [5](#0-4) [6](#0-5) 

Because Shipit supports multiple independently configured GitHub organizations/apps on one instance (each with its own `webhook_secret`), a signature that is valid for organization A says nothing about whether the payload's `repository.full_name`/commit `sha` legitimately belongs to organization A. An org admin who legitimately controls one onboarded organization's GitHub App/webhook configuration can forge the HMAC (since they know their own `webhook_secret`) while setting `repository.full_name` or `sha` to point at a stack/commit owned by a different, unrelated organization on the same Shipit instance.

### Impact Explanation
This breaks the "authenticated organization" vs "repository/commit actually written" trust boundary and results in a cross-repository/cross-organization write: an attacker who is a legitimate GitHub App/webhook administrator for Organization A can, without ever touching Organization B's secrets or an `ApiClient` token, create/update GitHub commit statuses on Organization B's commits (`StatusHandler`) or trigger check-run refreshes on Organization B's stacks (`CheckSuiteHandler`). Commit statuses are read by `Commit#deployable?`/deploy gating logic used to decide whether a commit is safe to deploy or eligible for continuous delivery; forging a passing status on a victim commit can push it toward being treated as deployable, i.e. an unauthorized influence over another repository's deploy pipeline — a cross-repository write that the engine's own webhook trust model is supposed to prevent.

### Likelihood Explanation
Likelihood is limited to Shipit deployments that onboard more than one GitHub organization (multiple `github:` entries in secrets, as shown by `test/dummy/config/secrets_double_github_app.yml`), where organizations do not fully trust each other. In that configuration, no additional privilege beyond "administer one of the onboarded orgs' GitHub App/webhook settings" is required — no `ApiClient` token, no `github_access_token`, and no access to the victim organization's secrets. Commit SHAs and repository full names are public GitHub metadata, so constructing a colliding, targeted payload is straightforward.

### Recommendation
Bind the payload's `repository.full_name` (and, transitively, the commits/stacks it resolves to) to the organization whose `webhook_secret` verified the signature. Concretely:
- In `WebhooksController#verify_signature`, retain the verifying organization and pass it (or enforce it) through to handler dispatch.
- In `Webhooks::Handlers::Handler#stacks`/`#repository_name`, and specifically in `StatusHandler`, require that the resolved `Repository`'s owner matches the organization that authenticated the request before performing any writes; reject (422) otherwise.

### Proof of Concept
1. Shipit is configured with two onboarded GitHub organizations, `orgA` and `orgB`, each with its own `webhook_secret` (as in `secrets_double_github_app.yml`).
2. Attacker administers `orgA`'s GitHub App/webhook and therefore knows `orgA`'s `webhook_secret`.
3. Attacker crafts a `status` event body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/attacker-repo" },
  "sha": "<sha of a commit belonging to orgB's stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. Attacker computes `X-Hub-Signature: sha1=...` using `orgA`'s `webhook_secret` and POSTs to `/webhooks`.
5. `verify_signature` resolves `Shipit.github(organization: "orgA")`, verifies successfully. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching orgB's commit — and writes a forged passing status onto it, with no verification that this commit belongs to `orgA`. [4](#0-3)
