### Title
Independent Per-Recipient Rounding in Headers Commission Distribution Can Inflate Total Distributed Commission Beyond the Fee Actually Paid - (File: `headers_commission.js`)

### Summary
`AntiSnipAttack.calcFeeProportions` computes a claimable share of a total via `(numerator)/C.FEE_UNITS` and then subtracts it from the total, letting rounding/order-of-operations errors make the claimed component exceed the whole. `ocore`'s headers-commission distribution logic has the analogous root cause: when a unit's headers commission is split among several `earned_headers_commission_recipients`, each recipient's payout is computed independently with `Math.round(full_amount * share / 100.0)`, and the individual rounded results are inserted into `headers_commission_contributions`/`headers_commission_outputs` without ever being reconciled against `full_amount` (the actual commission amount debited from the payer unit). [1](#0-0) 

### Finding Description
When a multi-authored unit wins a parent's headers commission, `calcHeadersCommissions` distributes `full_amount` (the exact `headers_commission` field of the payer unit) among the addresses listed in `earned_headers_commission_recipients`, using each recipient's `earned_headers_commission_share` (validated only to sum to exactly 100 across recipients): [2](#0-1) 

Each recipient's individual payout is calculated as `Math.round(full_amount * share / 100.0)`: [3](#0-2) 
and again when the same child unit wins headers commission from multiple parents, this is aggregated with another independent rounding step: [4](#0-3) 

Because each rounding operation is performed independently per recipient (rather than computing all-but-last recipients and giving the remainder to the last one), the sum of the individually rounded amounts is not guaranteed to equal `full_amount`. An attacker who controls the `earned_headers_commission_recipients` list of a multi-authored unit (e.g., using several addresses they control as co-authors) can choose shares specifically engineered so that each recipient's `full_amount * share / 100.0` value lands just above a `.5` boundary, causing every individual rounding to round up. With enough recipients, the total credited to `headers_commission_outputs` can systematically exceed the `headers_commission` amount actually paid/deducted by the payer unit(s). The same pattern (`Math.round(payload_commission / count_paid_witnesses)`) exists for payload/witnessing commissions as well, showing this is a systemic pattern rather than an isolated typo: [5](#0-4) 

This is the identical bug class described in the external report: a proportional/claimable amount is computed via independent arithmetic operations against a fixed total, and the code never checks or clamps the sum of the parts against the whole before crediting it as spendable balance.

### Impact Explanation
`headers_commission_outputs` amounts become spendable balance for the named recipients via `headers_commission`-type inputs, validated and consumed as real byte balance: [6](#0-5) 
If the sum of independently rounded recipient shares can exceed the amount actually paid by the payer unit, this represents new spendable value created without a corresponding debit — i.e., inflation of the effectively spendable byte supply, which is one of the explicitly in-scope impacts (asset/byte supply inflation via unauthorized value creation).

### Likelihood Explanation
This is reachable by any ordinary unit author: composing a multi-authored unit with a crafted `earned_headers_commission_recipients` array (integer percentages summing to 100, address-sorted) is a normal, unprivileged unit-posting operation, no special privileges are required. The only requirement is winning headers commission at all (any unit can be the "best child" for at least one parent), and the attacker fully controls the share percentages. However, per-round gains from rounding are bounded (at most roughly `0.5 * (number_of_recipients - 1)` bytes per distribution event), so accumulating meaningful inflation requires repeated execution across many mci/parent units, which is why this is rated Medium rather than High.

### Recommendation
Do not round each recipient's share independently. Compute all-but-the-last recipient's amount via rounding, and derive the last recipient's amount as `full_amount - sum(previous rounded amounts)` so the total always reconciles exactly to `full_amount`. Apply the same fix at the aggregation step in `headers_commission.js` (lines 199-206) and to the analogous `Math.round(payload_commission / count_paid_witnesses)` logic in `paid_witnessing.js` (lines 157-173), ensuring `SUM(amount)` per commission event can never exceed the actual commission/payload_commission being distributed.

### Proof of Concept
Conceptual PoC (concrete DB/mci setup would be needed to fully execute, but the arithmetic is deterministic):
1. Author a multi-authored unit `U` with N co-author addresses controlled by the attacker.
2. Set `earned_headers_commission_recipients` with N entries whose `earned_headers_commission_share` values are chosen (summing to 100) such that for the eventual `full_amount` (the winning parent's `headers_commission`), each `full_amount * share/100.0` value falls just above `k + 0.5` for some integer `k` (e.g., share fractions like `100/N` adjusted by ±1 to hit rounding-favorable fractions).
3. Get `U` selected as the "best child" (`getWinnerInfo`) for one or more parent units so it wins `full_amount`.
4. After `calcHeadersCommissions` runs, sum `headers_commission_contributions.amount` for `U`'s payer unit across all recipient addresses; due to independent `Math.round` per recipient (`headers_commission.js:183`), this sum can be strictly greater than `full_amount`, crediting more spendable balance in `headers_commission_outputs` than was actually paid by the payer unit.
