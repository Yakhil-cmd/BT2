### Title
Cross-Repository CI Status Forgery via Unscoped `sha` Lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` updates commit CI status by looking up commits **only by `sha`**, with no check that the commit belongs to the repository/organization whose webhook credentials were used to authenticate the request. Because Shipit's webhook signature verification selects the `GitHubApp`/secret to validate against based on an attacker-controlled field in the very same payload (`repository.owner.login` / `organization.login`), an attacker who legitimately controls webhooks for **any** org/repo tracked by a shared, multi-tenant Shipit instance can forge a `status` event carrying an arbitrary, publicly-known commit `sha` belonging to a **different** repository/stack, and have Shipit record a fabricated (e.g. `success`) status against that unrelated commit.

### Finding Description
Webhook signature verification is org-scoped: [1](#0-0) 
`repository_owner` is derived entirely from the untrusted JSON body: [2](#0-1) 

In a multi-organization deployment (a documented, supported configuration, `config/secrets.yml` `github.<org>.webhook_secret`), `Shipit.github(organization:)` resolves a **different** `GitHubApp`/secret per organization key: [3](#0-2) 

Once the HMAC is validated against the secret belonging to whatever organization the attacker declared in the payload (an organization the attacker legitimately controls, with their own legitimate `webhook_secret`), the actual event handler ignores repository scoping entirely: [4](#0-3) 

`Commit.where(sha: params.sha)` is queried globally, across all stacks/repositories tracked by the Shipit instance — there is no filter tying the looked-up commit back to `repository_owner`/`repository.full_name` from the same payload. This breaks the trust binding: **organization authenticated (whose webhook_secret validated the signature) ≠ repository actually written (whichever repository happens to contain a commit with the attacker-chosen `sha`)**.

This is structurally analogous to the `RewardsMath` bug: a check performed on one piece of state (`_rewardsAmount` / the signing organization) fails to constrain a side effect applied to unrelated state (`TPSS`/linked list / an arbitrary commit's status), because no invariant ties the two together.

### Impact Explanation
Commit statuses recorded via this path feed directly into deploy/merge gating logic used across the engine, e.g. `MergeRequest#all_status_checks_passed?`/`any_status_checks_failed?`, which read `head.statuses_and_check_runs` populated from the `Commit#statuses` records created by `StatusHandler`: [5](#0-4) 
Forging a passing status on a target commit in another team's stack can cause `ci.require`/`blocking` status checks to be satisfied fraudulently, enabling an **unauthorized deploy or unauthorized merge** in `ProcessMergeRequestsJob`/deploy flows that gate on commit status — matching the required Critical impact ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
The attacker only needs: (1) legitimate control of a GitHub App/webhook configured for their own organization within the same shared Shipit instance (a supported, documented multi-org setup — no stolen secrets, sessions, or API tokens required), and (2) the target commit's `sha`, which is public information for any repository they can view. No `ApiClient` token, GitHub App private key, or Shipit session is required, satisfying the "unprivileged attacker" bar. The primary uncertainty is deployment topology: the exploit requires Shipit to be configured for multiple GitHub organizations sharing one instance (as `docs/setup.md`/README document as a supported feature), and requires a real sha collision opportunity across repos being tracked by the same instance — I could not verify from the indexed code whether `Commit#create_status_from_github!` performs any additional stack/repo cross-check (its implementation was not present in the retrieved index), which is the main remaining uncertainty.

### Recommendation
In `StatusHandler#process` (and similarly review `CheckSuiteHandler`), scope the `Commit` lookup to the repository identified by the same payload fields used for signature verification, e.g. `stacks.merge(Commit.where(sha: params.sha))` where `stacks` is restricted to `Repository.where(owner: repository_owner, ...)`, rather than an unscoped `Commit.where(sha: ...)`.

### Proof of Concept
1. Shipit is configured with two organizations in `secrets.yml`: `OrgA` (attacker-controlled, `webhook_secret: attackerSecret`) and `OrgB` (victim, tracked stacks with real deploy gating on CI status).
2. Attacker learns the `sha` of a commit on an `OrgB`-owned stack (public GitHub data).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a body `{"sha": "<OrgB commit sha>", "state": "success", ...}` merged with `{"repository": {"owner": {"login": "OrgA"}}}`, signed with `attackerSecret`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully (attacker owns this secret).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the `OrgB` commit (no repository check), creating a forged `success` status on it via `commit.create_status_from_github!`.
6. This forged status can satisfy CI requirements gating `OrgB`'s deploys or merge queue.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
```
