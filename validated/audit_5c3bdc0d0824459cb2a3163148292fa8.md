### Title
Unbounded in-memory `handledChainsCache` growth from paired-device private payment chains enables memory-exhaustion DoS - (File: wallet.js)

### Summary
`handlePrivatePaymentChains()` in `wallet.js` caches a hash of every distinct set of `private_payment_chain` message bodies received from a paired device/hub in the module-level object `handledChainsCache`, purely to deduplicate re-sent chains. The cache is only pruned by a 1-hour time-based sweep, not by size, and the key space is fully controlled by the sender (a hash of attacker-supplied `body.chains`). A counterparty that is allowed to send private payment chains to a wallet (any paired device, or any hub-relayed peer) can generate unlimited distinct chain payloads and flood this cache, consuming server memory analogous to the Liferay `SessionClicks` issue where attacker-controlled request parameters were retained without limit.

### Finding Description
`handlePrivatePaymentChains(ws, body, from_address, callbacks)` is reached from `handleMessageFromHub()` for the `private_payment_chain`-related device-message subjects [1](#0-0) , i.e. by anyone able to pair with, or relay through the hub to, the wallet device — an unprivileged counterparty exactly like the "private-payment counterparty" category in scope.

The handler validates only structural shape of `body.chains` (non-empty arrays/objects/strings), not how many distinct payloads a peer may submit over time: [2](#0-1) 

It then computes `cache_key = objectHash.getBase64Hash(arrChains)` and, after processing, unconditionally stores it: [3](#0-2) 

The cache itself is a plain object with no maximum-size bound, only time-based expiry every hour: [4](#0-3) 

Because `cache_key` is derived from attacker-controlled content (`arrChains`), a peer can trivially generate an unbounded number of unique keys (e.g., by varying a payload field slightly on each submission) and force `handledChainsCache` to retain one entry per submission for up to an hour, with no upper bound on the number of concurrent entries. This is the same bug class as CVE-2025-3526: attacker-controlled request data is cached in server memory without a size/count restriction, only a time-based cleanup, allowing memory exhaustion.

### Impact Explanation
Sustained flooding of `handledChainsCache` by a paired device or hub-relayed peer grows unbounded memory usage on the receiving wallet/hub process. Because `handlePrivatePaymentChains` is invoked serially under a mutex per message from the hub [5](#0-4) , and each distinct payload also triggers real work (DB queries, validation, forwarding to other wallet members) before being cached, both memory and CPU/DB load scale with attacker-chosen distinct submissions, degrading or crashing the victim node — a denial-of-service condition consistent with the "network unable to confirm new units" / node availability impact class.

### Likelihood Explanation
Any device paired with the target wallet, or any hub able to relay `private_payment_chain` messages, can trigger this path with no special privilege beyond an established pairing (which is a standard, low-barrier prerequisite for wallet-to-wallet interaction). Generating unique `arrChains` hashes is trivial (varying trivial payload fields), and there is no rate limiting, size cap, or per-sender quota on `handledChainsCache` entries.

### Recommendation
Bound `handledChainsCache` by size (e.g., LRU eviction with a maximum entry count) in addition to time-based expiry, and/or scope/rate-limit the number of distinct chain submissions accepted per `from_address`/device within a time window before they are cached and processed.

### Proof of Concept
1. Pair an attacker-controlled device with the victim wallet (standard pairing flow).
2. Repeatedly send `private_payment_chain`-style hub messages with `body.chains` containing minimally-valid but distinct private payment chain payloads (vary a nested field such as `payload.outputs[0].amount` each time to produce a new `objectHash.getBase64Hash(arrChains)` per submission).
3. Each submission passes the structural checks in `handlePrivatePaymentChains` [2](#0-1)  and, once processed, is added to `handledChainsCache` [6](#0-5) .
4. Repeat submissions faster than the 1-hour cleanup interval [7](#0-6)  to accumulate unbounded cache entries and observe increasing process memory on the victim.
