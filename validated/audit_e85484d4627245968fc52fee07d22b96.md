### Title
Tokens sent directly to the pool contract are permanently locked — the cash book ignores them and no recovery entrypoint exists - ([File: contracts/pool/src/lib.rs](contracts/pool/src/lib.rs))

### Summary
The liquidity pool tracks reserves in a `cash` bookkeeping field that only moves through owner-gated, measured-receipt operations (`supply`, `repay`, `recapitalize`). Any user who transfers tokens directly to the pool's SAC address creates an excess `token.balance(pool) - cash` surplus that no entrypoint — for the sender, other users, or even the owner — can ever claim. Unlike the swap-aggregator, which has `sweep_balance`, the pool exposes no rescue/skim function.

### Finding Description
Every pool mutator is `#[only_owner]` (the controller), and every outbound leg is bounded by the tracked `cash` book, not the real token balance:

- `claim_revenue` pays `min(cash, floor(revenue_value))` — it cannot touch the donated surplus (contracts/pool/src/lib.rs:243-252; `docs/reference/formulas.md` payout formula).
- `withdraw`/`borrow` debit `cash` and transfer only book-backed amounts.
- `recapitalize` credits cash only up to the backing shortfall and refunds the excess *of the declared amount* back to the payer — it never pays out pre-existing balance.
- `supply`/`repay` credit the *measured balance delta* of the controller's own transfer (INV-ACCT-03), so a prior donation sitting in the balance is not captured by the depositor either.

The design is explicit: INV-ACCT-02 states "Reserve checks use tracked market cash; token donations alone do not increase it" (docs/reference/invariants.md:104-109), and the integration test `pool_all_money_paths_preserve_books_and_shared_token_custody` confirms a 7-token donation sits outside every market's `cash` (tests/test-harness/tests/pool_money_flow_audit.rs:86-103). The pool's endpoint list (contracts/pool/README.md:67-84) contains no sweep/rescue — a `grep` for `sweep|rescue|recover|skim` finds only the swap-aggregator's `sweep_balance`, which is a different contract.

So `balance(pool) > Σ cash` is a state with no exit path for the surplus. This is the direct analog of the Nouns `Stream.cancel` finding: stray tokens are visible in the contract but unreachable by anyone.

### Impact Explanation
Permanent freezing of funds. Tokens mistakenly sent to the pool (e.g., a user calling the SAC `transfer` to the pool address expecting it to count as a deposit, or a wrong-recipient send) are locked forever. They are not credited to the sender's supply, cannot be withdrawn, cannot be claimed as revenue, and cannot be swept by governance — the owner can only move book-backed `cash`. This satisfies the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Low likelihood per incident (requires a user mistake — a direct token transfer outside the controller's supply flow), but the pool is a long-lived public address holding many assets, so mistaken transfers are a realistic occurrence over the contract lifetime, matching the original report's Medium assessment. No privileged action is needed to trigger the freeze; any unprivileged holder of the token can send it.

### Recommendation
Add an owner-only `sweep(hub_asset, recipient)` to the pool that transfers `token.balance(pool) − Σ cash(asset)` (the surplus above all markets' cash books sharing that token) to a governance-controlled recipient, mirroring `sweep_balance` in `contracts/swap-aggregator/src/lib.rs:189-203`. Alternatively, route donations through `recapitalize` semantics so the surplus at least fills backing shortfalls before becoming claimable.

### Proof of Concept
1. Deploy pool + controller, create a USDC market; ALICE supplies 1,000 USDC through `controller.supply` — `cash == balance == 1,000`.
2. BOB mistakenly calls `token.transfer(BOB, pool, 500)` directly on the SAC.
3. State: `token.balance(pool) == 1,500`, `cash == 1,000` (verified by `get_reserves`; the donation does not increase the book — INV-ACCT-02, and pinned by tests/test-harness/tests/pool_money_flow_audit.rs:86-96).
4. BOB attempts `controller.supply` of a normal amount — the pool credits only the measured delta of his new transfer, not the 500 already sitting there.
5. Owner calls `claim_revenue` — payout is capped at `cash`; the 500 surplus cannot be moved.
6. No entrypoint in `contracts/pool` transfers the excess balance; the 500 USDC is permanently locked. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    /// Transfers each token's balance above its reserved fee total to `recipient`. Owner only.
    #[only_owner]
    fn sweep_balance(env: Env, recipient: Address, tokens: Vec<Address>) {
        renew_instance(&env);
        let router = env.current_contract_address();
        let n = tokens.len();
        for i in 0..n {
            // `i < n == tokens.len()`, so the index is in range by construction.
            let token = tokens.get_unchecked(i);
            let client = token::Client::new(&env, &token);
            let balance = client.balance(&router);
            let reserved = storage::reserved_fee_balance(&env, &token);
            if balance > reserved {
                client.transfer(&router, &recipient, &(balance - reserved));
            }
        }
    }
