# Analysis: Analog for CVE-2017-5841 in ocore

## Bug-class mapping

CVE-2017-5841 is a case where a demuxer trusts an embedded length/tag field to slice a buffer without validating it against the actual decoded data size, causing an out-of-bounds read that crashes the parser. The closest reachable analog in `ocore--011` is in the c-hash (chash) decoding logic used to validate every address that appears in a posted unit (author addresses, address-definition `address` conditions, asset definer/issuer addresses, etc.).

## Title
Unhandled exception on malformed base32-decoded c-hash crashes address validation — (File: `chash.js`)

## Summary
`isChashValid()` in `chash.js` decodes an attacker-supplied 32/48-character address string and assumes the decoded buffer is always exactly 160 or 288 bits long. That length assumption is only enforced deep inside `separateIntoCleanDataAndChecksum()`, which `throw`s if it isn't met — but that call is **not** inside the `try/catch` that guards the decode step. Any crafted address string that decodes to a buffer of unexpected bit-length raises an uncaught exception that propagates out of `isValidAddress()`/`isChashValid()` into unit/definition validation.

## Finding Description [1](#0-0) 

`isChashValid(encoded)` only wraps the `base32.decode(encoded)` / `Buffer.from(encoded, 'base64')` call in `try/catch`: [2](#0-1) 

Everything after the `catch` block — `buffer2bin(chash)` and `separateIntoCleanDataAndChecksum(binChash)` — runs unguarded: [3](#0-2) 

`separateIntoCleanDataAndChecksum()` explicitly asserts the bit-length must be exactly 160 or 288, and `throw`s an `Error` otherwise: [4](#0-3) 

The code assumes that any string passing the character-count check (`encoded_len === 32 || encoded_len === 48`) will always decode to exactly 20 or 36 bytes. This mirrors the AVI-demuxer root cause: a length/tag value from untrusted input is trusted for downstream slicing/parsing without the actual decoded size being re-validated before that data is consumed — the check exists, but is only reached on a code path outside the protective `try/catch`, so instead of a graceful `return false`, the process throws.

`isChashValid` (via `isValidAddress`/`isValidDeviceAddress` in `validation_utils.js`) is exercised on every author address, `address`, `seen address`, `has definition change`, `attested` operand, and asset definer address encountered while validating a freshly posted unit — i.e., it is fully reachable from an unprivileged unit poster without needing the unit to otherwise be valid.

## Impact Explanation
If `base32.decode()`/`Buffer.from(..., 'base64')` for a given crafted 32/48-character string does not error out itself but yields a buffer whose byte length differs from the expected 20/36 bytes (e.g., due to embedded padding characters, alternate casing, or other quirks accepted by the `thirty-two` decoder / Node's lenient base64 decoder), `isChashValid()` throws an uncaught `Error`. Since this call sits deep in the address/definition validation call graph, an uncaught exception here can crash the validating process (Node's default behavior for uncaught synchronous exceptions is to terminate the process) while processing an incoming unit. That directly satisfies the "network unable to confirm new units" / "node disagreement on validity" criteria: a node that crashes while validating a unit stops confirming new units, and if the exception is instead caught at a different level on different node versions, nodes could diverge on whether the unit is valid.

## Likelihood Explanation
The address-validation path is invoked unconditionally for every author, `address`-condition operand, and related fields on every unit received, making it trivially reachable by any unit poster. The only uncertainty is whether a base32/base64 string of the exact required character count can be crafted to decode to a buffer of the wrong byte length using the specific `thirty-two` library version bundled with this repo; this could not be fully confirmed without inspecting the `thirty-two` package's decode implementation in `node_modules`, which was not available in the indexed context. The structural defect (throwing code not covered by the `try/catch`) is confirmed directly in `chash.js`.

## Recommendation
Wrap the entire body of `isChashValid()` — not just the initial decode call — in `try/catch`, and additionally explicitly verify `chash.length === encoded_len===32 ? 20 : 36` immediately after decoding, returning `false` on mismatch instead of relying on the later `throw` in `separateIntoCleanDataAndChecksum`.

## Proof of Concept
Conceptual (pending confirmation of a concrete decoder quirk):
1. Craft a 32-character string that satisfies `thirty-two`'s base32 decode without throwing, but whose decoded buffer is not exactly 20 bytes (e.g., a string containing a padding/invalid-but-tolerated character sequence recognized by the library as an early terminator).
2. Post a unit whose author address (or an `address`/`seen address`/`attested` operand in an address definition) equals this string.
3. When the node validates the unit and calls `isValidAddress()` → `chash.isChashValid()`, `separateIntoCleanDataAndChecksum()` throws `Error("bad length=...")`, which is not caught anywhere in this call chain, crashing/aborting unit validation for that node.

**Caveat:** I could not verify from the available index whether the `thirty-two` npm package (or Node's base64 decoder) can actually be coerced into producing a wrongly-sized buffer from a fixed-length input string, since the library's source is not included in the indexed codebase. This should be independently verified against the exact `thirty-two` version in `package.json` before treating this as a confirmed exploitable bug; a Devin session with full filesystem access could inspect `node_modules/thirty-two` to confirm or refute the decode-length edge case.
