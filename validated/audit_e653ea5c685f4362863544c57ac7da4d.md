### Title
Webhook organization used for signature verification is decoupled from the repository the event payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and its `webhook_secret`) to validate the inbound HMAC signature using `repository_owner`, a value read directly out of the unauthenticated JSON payload. The rest of the payload (in particular the `repository.full_name` field used later by the event handlers) is not required to match that same owner, and is never itself covered by an owner-scoped check. This breaks the equality `organization authenticated == repository written`.

### Finding Description
`verify_signature` picks which app config (and therefore which `webhook_secret`) is used to verify the HMAC over the raw body: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` returns the `GitHubApp` instance configured for that organization name, and `verify_webhook_signature` is called on that instance: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

If Shipit is configured for multiple GitHub organizations (the documented multi-org config in `config/secrets.development.example.yml`), and *any one* of those organizations is configured without a `webhook_secret` (an explicitly optional setting per `docs/setup.md`), then a request whose `repository.owner.login` is set to that unsecured organization's name will pass `verify_signature` unconditionally — no HMAC is even computed. Nothing at that point ties the verified `repository_owner` to the rest of the JSON body: the same request can set `repository.full_name` to any other, secured organization/repository (e.g. `"secured-org/production-app"`), which is what the event handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) use to locate the target `Repository`/`Stack` to act on. The value used to select the trust boundary (`repository_owner` → app/secret) and the value used to select the object actually mutated (`repository.full_name` inside the same untrusted `params`) are independent fields in an attacker-supplied body, so authenticating one organization does not guarantee the repository written belongs to that organization.

This is the direct analog to the C4 finding: `pay()` used `msg.sender`-controlled state for the callback before all effects were finalized, letting the caller manipulate later state; here, the controller resolves *which* secret authenticates the request from an attacker-supplied field, then permits the same attacker-supplied body to name a completely different resource to update, with no re-check tying the two together.

### Impact Explanation
An unauthenticated attacker who knows (or can guess) the name of one configured GitHub organization that lacks a `webhook_secret` can forge `push`/`status`/`check_suite`/`membership` etc. events for a *different* organization's stacks with a completely fabricated payload (fake commit SHA, fake CI `state`, fake `membership` additions creating users/teams, etc.). This can drive `GithubSyncJob`/status updates for stacks that belong to organizations that *did* configure a secret, effectively achieving an unauthorized/forged deploy trigger or CI-status spoofing without ever holding that organization's `webhook_secret`. This matches the "unauthorized deploy" / cross-repository write impact tier.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where at least one configured organization omits `webhook_secret` (explicitly documented as optional, and the default/example config ships with it unset). This is a realistic misconfiguration rather than a contrived one, and no credentials, session, or API token are needed to exploit it — only knowledge of an organization name that has no secret configured.

### Recommendation
Bind the two identities together explicitly: after selecting the `GitHubApp` via `repository_owner` and verifying the signature (or confirming a secret is actually configured — do not silently trust when `webhook_secret` is blank), re-verify that every repository/organization reference inside the payload used by downstream handlers (`repository.full_name`, `organization.login`, etc.) matches the same `repository_owner` that was authenticated. Reject requests where these diverge, and consider making `webhook_secret` mandatory (or per-organization enforced) rather than optional when multiple organizations are configured.

### Proof of Concept
1. Configure Shipit with two organizations: `unsecured-org` (no `webhook_secret`) and `secured-org` (deploys a real, sensitive stack).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "secured-org/production-app" },
  "after": "<some-existing-sha-in-secured-org/production-app>",
  "ref": "refs/heads/master"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "unsecured-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` without checking any HMAC.
4. The push handler processes the event using `repository.full_name = "secured-org/production-app"`, enqueuing sync/deploy-relevant work for a stack the attacker never authenticated against.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
