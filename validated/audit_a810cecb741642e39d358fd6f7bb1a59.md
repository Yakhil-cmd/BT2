### Title
`MultiKeyAuthenticator` threshold check can be satisfied by one signer reusing a single signature across duplicate public-key slots - (File: `types/src/transaction/authenticator.rs`)

### Summary
`MultiKeyAuthenticator::verify` enforces an M-of-N approval threshold purely by counting *bitmap slot indices* that have a signature, not by requiring N distinct underlying signing keys/identities. If the `MultiKey` public-key list contains a duplicate public key (nothing in `MultiKey::new`/`MultiKeyAuthenticator::new` rejects duplicates), the holder of that single duplicated key can supply one signature and place a copy of it at each of the duplicate-key bitmap positions, satisfying a 2-of-N (or M-of-N) threshold alone.

### Finding Description
`MultiKeyAuthenticator::new` only checks that a bitmap index is in range and not already set — it does not check that the underlying public keys referenced by different signature slots are distinct: [1](#0-0) 

`to_single_key_authenticators` reconstructs one `SingleKeyAuthenticator` per bitmap slot and only validates counts against `signatures_required()`, again without checking key uniqueness: [2](#0-1) 

`verify` then simply iterates the reconstructed per-slot authenticators and requires each to validate: [3](#0-2) 

The repo's own test proves the bypass: a `MultiKey` is built with `keys = [sender0_pub, sender1_pub, sender1_pub]` (the last two entries are the *same* key) and `signatures_required = 2`: [4](#0-3) 

A single signature from `sender1` is placed at both duplicate-key indices (1 and 2), and the transaction authenticator verification succeeds — meaning the "2 signatures required" threshold is satisfied using only one real signer's key: [5](#0-4) 

This is the local admission analog of the external report's "shared signer" replay theme: the approval-validation logic (multisig/threshold binding) accepts an approval set that does not correspond to the intended set of distinct signers, because binding is done by bitmap index/count rather than by distinct signing identity.

### Impact Explanation
An Aptos account authenticated via `Scheme::MultiKey`/`AuthenticationKey::multi_key` that is set up (or later reconfigured, e.g. via key rotation flows building a `MultiKey`) with even one duplicated public key silently degrades its effective approval threshold. For a "2-of-3" custody/multisig account where the intent is that at least 2 *distinct* parties must co-sign, a party whose key was duplicated in the list (accidentally, or maliciously inserted during collaborative account setup) can authorize and get committed any transaction — including sending funds or invoking privileged module functions — entirely alone. This is unauthorized transaction execution under the wrong (incomplete) signer/approval set, which directly matches the admission-boundary impact criteria (authenticator/multisig approval-set validation accepting the wrong approval set).

### Likelihood Explanation
Exploitation requires that the target `MultiKey` account's public-key list contain a duplicate entry. This can arise from: (a) a malicious co-participant during collaborative multisig setup deliberately inserting their own key twice (the constructors do not reject this), or (b) tooling/user error that silently produces a security-degraded account that "looks" like an N-of-M multisig but isn't. Because the authentication key is derived from the full key-list bytes, victims verifying only the count of keys/threshold (and not key uniqueness) could be misled into treating such an account as safely multi-party. The core validation path itself provides no defense-in-depth against this, so likelihood is driven entirely by whether duplicate-key `MultiKey` lists are ever produced/accepted at account-creation/rotation time — this repo snippet does not show any framework-level rejection of duplicate keys either.

### Recommendation
Enforce uniqueness of public keys within `MultiKey` at construction time (`MultiKey::new`) and/or require `MultiKeyAuthenticator::to_single_key_authenticators`/`verify` to reject bitmaps where two or more signed slots reference the same underlying public key, so the on-chain approval count reflects distinct signing identities, not just distinct bitmap positions.

### Proof of Concept
The existing unit test in the repo is itself a working PoC of the bypass (using duplicate key at positions 1 and 2, reusing `signature1` for both, and `signed_txn.verify_signature().unwrap()` succeeding): [6](#0-5) 

Note: I could not locate the `MultiKey` struct's own field-level constructor code (`MultiKey::new`) in the indexed content to confirm definitively whether it validates key uniqueness elsewhere (e.g., in `types/src/transaction/authenticator.rs` outside the shown ranges); the behavior demonstrated by the existing test strongly implies no such check exists, but if a full-repo review is needed to rule out an uniqueness check added elsewhere, a Devin session with full file access should verify `MultiKey::new`'s implementation directly.

impl MultiKeyAuthenticator {
    pub fn new(public_keys: MultiKey, signatures: Vec<(u8, AnySignature)>) -> Result<Self> {
        ensure!(
            public_keys.len() < (u8::MAX as usize),
            "Too many public keys, {}, in MultiKeyAuthenticator.",
            public_keys.len(),
        );

        let mut signatures_bitmap = aptos_bitvec::BitVec::with_num_bits(public_keys.len() as u16);
        let mut any_signatures = vec![];

        for (idx, signature) in signatures {
            ensure!(
                (idx as usize) < public_keys.len(),
                "Signature index is out of public key range, {} < {}.",
                idx,
                public_keys.len(),
            );
            ensure!(
                !signatures_bitmap.is_set(idx as u16),
                "Duplicate signature index, {}.",
                idx
            );
            signatures_bitmap.set(idx as u16);
            any_signatures.push(signature);
        }

        Ok(MultiKeyAuthenticator {
            public_keys,
            signatures: any_signatures,
            signatures_bitmap,
        })
    }

    pub fn to_single_key_authenticators(&self) -> Result<Vec<SingleKeyAuthenticator>> {
        ensure!(
            self.signatures_bitmap.last_set_bit().is_some(),
            "There were no signatures set in the bitmap."
        );

        ensure!(
            (self.signatures_bitmap.last_set_bit().unwrap() as usize) < self.public_keys.len(),
            "Mismatch in the position of the last signature and the number of PKs, {} >= {}.",
            self.signatures_bitmap.last_set_bit().unwrap(),
            self.public_keys.len(),
        );
        ensure!(
            self.signatures_bitmap.count_ones() as usize == self.signatures.len(),
            "Mismatch in number of signatures and the number of bits set in the signatures_bitmap, {} != {}.",
            self.signatures_bitmap.count_ones(),
            self.signatures.len(),
        );
        ensure!(
            self.signatures.len() >= self.public_keys.signatures_required() as usize,
            "Not enough signatures for verification, {} < {}.",
            self.signatures.len(),
            self.public_keys.signatures_required(),
        );
        let authenticators: Vec<SingleKeyAuthenticator> =
            std::iter::zip(self.signatures_bitmap.iter_ones(), self.signatures.iter())
                .map(|(idx, sig)| SingleKeyAuthenticator {
                    public_key: self.public_keys.public_keys[idx].clone(),
                    signature: sig.clone(),
                })
                .collect();
        Ok(authenticators)
    }

    pub fn verify<T: Serialize + CryptoHash>(&self, message: &T) -> Result<()> {
        let authenticators = self.to_single_key_authenticators()?;
        authenticators
            .iter()
            .try_for_each(|authenticator| authenticator.verify(message))?;
        Ok(())
    }
