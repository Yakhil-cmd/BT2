### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook purely by SHA, with no filter on repository or stack, so a validly-signed status event from an attacker-controlled repository can write a `Status` row onto any other stack's `Commit` that happens to share the same SHA (e.g. via a shared git history / fork). This lets one authenticated repository's webhook mutate another repository's commit state, flipping `deployable?`/merge eligibility on the victim stack. The `review_stacks_enabled` flag and the `OpenedHandler#provision?` precedence bug are unrelated to this path and do not gate it.

### Finding Description
The broken binding: `commit.stack_id == repository_owner_of(params)` is assumed but never enforced. In practice `StatusHandler#process` does: [1](#0-0) 

`Commit.where(sha: params.sha)` queries the entire `commits` table across all stacks/repositories, then calls `commit.create_status_from_github!(params)` on every match. The only authentication performed before this runs is `WebhooksController#verify_signature`, which validates the HMAC using `Shipit.github(organization: repository_owner)` — i.e., it proves the webhook came from *some* GitHub org the attacker controls, not that the `sha` in the payload belongs to that org's repository: [2](#0-1) 

`Commit#create_status_from_github!` then writes the `Status` using the matched commit's own `stack_id` (not the requesting repository's), via `Status#replicate_from_github!`: [3](#0-2) [4](#0-3) 

`Commit#add_status` then evaluates the new status against the previous one and, if the state transition matters, emits `deployable_status` and schedules merges/continuous delivery for the victim stack — exactly the flip needed to force ship/block: [5](#0-4) [6](#0-5) 

**Root cause**: no repository/stack scoping is applied to the `sha` lookup, so any authenticated (i.e., real, signature-valid) webhook for *any* repository onboarded to the Shipit instance can affect a commit belonging to a *different* stack, provided the two repositories ever shared a commit object with an identical SHA (the common case for forks, or repos with shared history/merge commits).

**On `review_stacks_enabled` / the provisioning precedence bug**: This is a real, separate bug in `OpenedHandler#provision?`, `ReopenedHandler#unarchive?`, etc. — the boolean expression `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (allow_with_label && has_label) || (prevent_with_label && !has_label)` has Ruby's standard `&&`/`||` precedence, meaning the last two clauses are **not** gated by `review_stacks_enabled` at all: [7](#0-6) 
However, this logic lives entirely in the *pull_request* handlers (provisioning a `ReviewStack`) and is never consulted by `StatusHandler` or `Commit#create_status_from_github!`. The `review_stacks_enabled` flag therefore has no bearing on whether a status webhook can write to a stack's commit — the unscoped-SHA write works identically whether the victim stack is a regular `Stack` or a `ReviewStack`, and whether `review_stacks_enabled` is true or false. The question's exploit narrative conflates two independent bugs; only the `StatusHandler` scoping issue is actually reachable in the way described.

### Impact Explanation
An attacker who controls (or authenticates against) any repository onboarded into the same Shipit instance can forge a `success`/`failure` status for a `context` (e.g. `sonarqube`) that a victim stack's deploy spec marks as `required`/`blocking`, as long as the SHA in their webhook matches a SHA that also exists as a `Commit` row on the victim's stack (trivially achievable with forks or shared history). This can force a commit's `deployable?` to become true (unblocking an otherwise-blocked deploy) or false (denial of an otherwise-good deploy), and triggers `stack.schedule_merges` / `deployable_status` hooks on a stack the attacker never authenticated for. This is a payload for one repository mutating another's commit/stack state — matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Preconditions: (1) attacker must operate a repository that is itself onboarded to the target Shipit instance (so a genuinely GitHub-signed `status` webhook reaches it), and (2) the victim stack must contain a `Commit` row with a SHA identical to one the attacker can produce/control in their own repo (satisfied by forks of the victim repo, shared submodule/merge history, or repos migrated/rebased from the same source). `review_stacks_enabled` is not a precondition. Attacker cost is low: no Shipit credentials, secrets, or team membership are needed — only the ability to author a real GitHub status event on a repo they control. This is repeatable against any stack sharing a SHA with an attacker-controlled repo.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogously in `Commit.by_sha`/other SHA-based handlers) to the repository that authenticated the webhook, e.g. resolve `Repository.from_github_repo_name(params.repository.full_name)` and restrict `Commit.where(sha: params.sha)` to `commit.stack.repository == repository` (or join through `stacks` belonging to that repository) before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "a status for a SHA shared with another repository's stack must not affect the other stack" do
  attacker_stack = shipit_stacks(:shipit)              # attacker's onboarded repo/stack
  victim_stack   = shipit_stacks(:cyclimse)            # unrelated victim stack, review_stacks_enabled: false

  shared_sha = "a" * 40
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), committer: shipit_users(:shipit))
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), committer: shipit_users(:shipit))

  victim_stack.repository.update!(review_stacks_enabled: false)
  before = victim_commit.reload.deployable?

  params = ActiveSupport::HashWithIndifferentAccess.new(
    sha: shared_sha, state: "success", context: "sonarqube"
  )
  Shipit::Webhooks::Handlers::StatusHandler.new(params.merge(repository: { full_name: "attacker/repo" })).process

  after = victim_commit.reload.deployable?

  # Assert the binding: victim_commit.stack_id == attacker_stack_authenticated_for should hold,
  # i.e. victim stack's status set must be untouched by attacker repo's webhook.
  assert_equal before, after, "attacker's status webhook must not change deployability of an unrelated stack's commit"
  assert_empty victim_commit.statuses.where(context: "sonarqube")
end
```
This currently fails (the victim commit does receive the `sonarqube` status and `deployable?` changes), demonstrating the cross-stack write.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
