### Title
Stack-Scoped API Token Read Restriction Bypassed via `CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` can be bound to a single stack via its `stack_id` column, and `Shipit::Api::BaseController` is supposed to enforce that binding for every API request. `Shipit::Api::CCMenuController` overrides the scoping helper with an unscoped lookup, so a token that is only authorized for stack A can read the deploy/build state of any other stack.

### Finding Description
`Shipit::ApiClient` has `belongs_to :stack, optional: true` [1](#0-0)  and the intended invariant is enforced in `Shipit::Api::BaseController`:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

This is the binding: *"the stack a token authorizes"* (`current_api_client.stack_id`) must equal *"the stack the request actually touches"* (`stack`, derived from `params[:stack_id]` but filtered through `stacks`). This scoping is confirmed to be an enforced security boundary in `test/controllers/api/stacks_controller_test.rb`, which explicitly tests that "an api client scoped to a stack will only see that one stack" [3](#0-2) , and fixture `here_come_the_walrus` demonstrates a real, stack-scoped `ApiClient` record used throughout the API test suite.

`Shipit::Api::CCMenuController`, however, overrides `stack` with an **unscoped** lookup that ignores `current_api_client.stack_id` entirely:

```ruby
class CCMenuController < BaseController
  require_permission :read, :stack

  def show
    latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
    render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
  end

  private

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end

  def authenticate_api_client
    @current_api_client = ApiClient.authenticate(params[:token])
    super unless @current_api_client
  end
end
``` [4](#0-3) 

`require_permission :read, :stack` only checks that the `read:stack` string is present in `current_api_client.permissions` via `ApiClient#check_permissions!` [5](#0-4) ; it performs no per-stack authorization check. The per-stack restriction is supposed to come entirely from `BaseController#stacks`/`#stack`, which `CCMenuController` bypasses by redefining `stack` to call `Stack.from_param!` directly instead of `stacks.from_param!`.

**Equality broken:**
- Before: `token.stack_id == requested_stack.id` is required to read any stack's state through the API.
- After (attacker's request): `token.stack_id == A`, but `requested_stack.id == B` (attacker-supplied `params[:stack_id]`), and the request still succeeds because `CCMenuController#stack` never consults `token.stack_id`.

### Impact Explanation
Any holder of a legitimately-issued, single-stack-scoped `ApiClient` token with the `read:stack` permission can query `GET /api/stacks/:stack_id/ccmenu.xml` for **any** stack in the Shipit instance, not just the one it was authorized for. This discloses that stack's existence, its lock state, and its latest deploy/rollback status (`lastBuildStatus`, `activity`, `lastBuildLabel`, `webUrl`, etc.), as rendered by `app/views/shipit/ccmenu/project*`. This is an unauthorized read of stack state that crosses the authorization boundary the `stack_id` scoping was designed to enforce, matching the "High - escalation into ... unauthenticated read of stack state, task streams or deploy output" class of impact (here, escalation past a token's intended read scope to another stack's state).

### Likelihood Explanation
Likelihood is credible but bounded: it requires the attacker to already hold a valid, stack-scoped `ApiClient` token with `read:stack` permission (issued by an admin for a specific, narrower purpose, e.g., a CI status badge integration limited to one stack). Given such a token — which is the entire justification for `stack_id` scoping existing — the bypass is a single unauthenticated URL parameter change (`stack_id`) with no further requirement (no secrets, no privilege escalation, no session). The test suite (`test/controllers/api/ccmenu_controller_test.rb`) never exercises a stack-scoped client, so this gap is untested and not caught by CI.

### Recommendation
Make `CCMenuController#stack` respect the same scoping as the rest of the API by using the inherited `stacks` relation instead of an unscoped `Stack.from_param!`:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This restores the invariant that a token's `stack_id` binding must equal the stack actually being read, consistent with `Shipit::Api::BaseController#stack`.

### Proof of Concept
1. As an admin, issue a stack-scoped `ApiClient` (`stack_id = A.id`, `permissions = ['read:stack']`) — this is the same kind of client the CCMenu URL generator (`Shipit::CCMenuUrlController`) is designed to hand out for a specific stack [6](#0-5) .
2. Using that client's `authentication_token`, issue:
   `GET /api/stacks/B/ccmenu.xml?token=<token-scoped-to-A>`
   where `B` is a different stack than `A`.
3. Expected (per the scoping invariant enforced elsewhere, e.g. `Shipit::Api::StacksController#index`): request should fail to resolve stack `B` (404/`stacks.from_param!` would raise `RecordNotFound` since `stacks` is limited to `Stack.where(id: A.id)`).
4. Actual: the request succeeds with `200 OK` and returns stack `B`'s deploy/build status XML, because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unscoped, ignoring the token's `stack_id` binding. This can be confirmed by comparing against `test/controllers/api/stacks_controller_test.rb`'s "scoped to a stack" behavior [3](#0-2) , which shows the intended (but here bypassed) scoping semantics.
