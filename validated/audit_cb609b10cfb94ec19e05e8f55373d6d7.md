### Title
Cross-repository CI status forgery via unscoped `Commit.where(sha:)` in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` writes GitHub `status` webhook data to **every** `Commit` row that shares the given SHA, with no scoping to the repository/stack that authenticated the webhook. Because git SHAs are content-addressed, an attacker can produce a commit with an identical SHA to one that already exists on a victim's (production) stack and then push a `status` webhook for an unrelated context such as `sonarqube`, silently flipping that commit's aggregated CI state on the victim stack.

### Finding Description
The broken binding is:
`authenticated_repository (from GitHub App signature check) == repository whose commit rows are mutated`

which the code never enforces. Trace:

- `Shipit::WebhooksController#verify_signature` only validates the payload against the GitHub App configured for the **organization** in the payload (`Shipit.github(organization: repository_owner)` and `github_app.verify_webhook_signature`), never against the specific repository/stack: [1](#0-0) [2](#0-1) 
- `StatusHandler#process` then looks up commits by bare SHA across the *entire* `commits` table, with no `stack_id`/repository filter at all: [3](#0-2) 
- For every matching `Commit`, `create_status_from_github!` is invoked, which appends a `Status` and recomputes the aggregate `status` via `add_status`. If the state transition changes `simple_state`, it emits `deployable_status` and calls `stack.schedule_merges` when the new status is pending/success: [4](#0-3) [5](#0-4) 
- Whether a commit is deployable, and whether newer commits are blocked, is derived purely from this stored status data (`deployable?`, `blocked?`), independent of which repository actually reported it: [6](#0-5) 

Exploit flow: an attacker who owns/controls a repository under the same GitHub organization/App installation as a victim's production stack (or any organization for which they can produce a validly signed status event, e.g. by having push/status-setting rights on their own repo in that org) creates a commit whose SHA collides with a commit already present in the victim's `commits` table (trivial via forking the victim's public repo history, cherry-picking, or importing the same upstream commit — git SHAs are identical for identical commit content regardless of remote). The attacker then sets a commit status (`context: sonarqube`, `state: success` or `failure`) on that SHA from their own repo. GitHub sends the resulting `status` webhook, which is legitimately signed for the attacker's organization/repo, passes `verify_signature`, and is processed by `StatusHandler`. Because `Commit.where(sha: params.sha)` is unscoped, it also updates the identically-shaed commit belonging to the victim's stack, flipping its aggregate CI status and potentially unblocking `schedule_merges`/marking the commit `deployable?` on the victim's production environment stack.

Existing guards do not prevent this: `verify_signature` authenticates the webhook's origin organization, not the specific repository being mutated; there is no `ExplicitParameters` repository field checked against the found commit's `stack.repository`; no `require_permission!`/`stacks` scope applies to webhook processing at all (webhooks are unauthenticated by user identity, only HMAC-signed per org).

### Impact Explanation
A payload legitimately signed for one repository can mutate CI-status data (and therefore deploy/merge eligibility) belonging to an entirely different repository's stack — this is exactly the "payload for one repository mutating another's stack/commit" category, rated Critical. If the affected stack is a production environment with continuous deployment or merge automation gated on CI status, this can force an unauthorized deploy or unblock a merge for attacker-influenced code. The blast radius extends to any stack whose commits happen to share a SHA with a commit reachable by the attacker (all repos sharing history/forks within the same signed organization).

### Likelihood Explanation
Preconditions: attacker needs to be able to produce a validly-signed `status` webhook for *some* repository under an organization Shipit trusts (achievable with any repo they control that has the Shipit GitHub App installed on the org, or has status-setting API access on their own repo), and needs a SHA collision with a victim commit, which is trivial to engineer by forking/importing the exact same commit content. No Shipit credentials, sessions, or maintainer status are required — only ordinary GitHub repository permissions on the attacker's own repo. This is repeatable per SHA/commit and is not rate-limited beyond normal GitHub API/webhook delivery.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run/other handlers) to commits belonging to the repository that authenticated the webhook, e.g. filter by `stack.repository_id`/`github_repo_name` derived from `params.dig('repository', 'full_name')`, not solely by SHA. Reject or ignore statuses whose payload repository does not match the commit's owning stack repository.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, conceptually):
```ruby
test "status webhook does not affect commits from a different repository sharing the same SHA" do
  victim_stack = shipit_stacks(:shipit) # production environment, requires 'sonarqube'
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')

  other_stack = Shipit::Stack.create!(repository: shipit_repositories(:other), environment: 'staging', branch: 'master')
  attacker_commit = other_stack.commits.create!(sha: 'a' * 40, message: 'attacker commit, same sha')

  before_state = victim_commit.reload.status.state

  Shipit::Webhooks::Handlers::StatusHandler.new(
    'sha' => 'a' * 40, 'state' => 'success', 'context' => 'sonarqube',
    'repository' => { 'full_name' => other_stack.repository.full_name }
  ).call

  after_state = victim_commit.reload.status.state

  assert_equal before_state, after_state, "status from unrelated repository must not change victim stack's commit CI state"
end
```
Expected today: the assertion fails because `Commit.where(sha:)` matches both `victim_commit` and `attacker_commit`, flipping `victim_commit`'s status and, if this were a production stack with `continuous_deployment?`, triggering `stack.schedule_merges`/`deployable?` changes.

      already_deployed = deployed?

      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
