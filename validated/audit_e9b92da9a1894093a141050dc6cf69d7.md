### Title
Cross-repository CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's webhook secret to use for signature verification based on an attacker-controlled JSON field (`repository.owner.login`), but the payload fields that are actually acted upon by event handlers — in particular the commit `sha` consumed by `StatusHandler` — are never checked against the organization/repository that was used to validate the signature. This breaks the intended binding: `organization whose secret validated the signature == repository/commit the handler writes to`.

### Finding Description
`WebhooksController#verify_signature` derives the app/secret to check the signature against purely from the payload itself: [1](#0-0) [2](#0-1) 

Any organization onboarded into the Shipit instance (i.e., any org for which the operator has configured a `github.webhook_secret`, per `docs/setup.md`) can compute a valid `X-Hub-Signature` over an arbitrary JSON body as long as `repository.owner.login`/`organization.login` in that body names their own organization — the signature check has no relationship to which repository/commit the rest of the payload references.

Once the signature passes, `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event)` handlers with the raw, attacker-controlled `params`: [3](#0-2) 

For the `status` event, `StatusHandler#process` looks up commits **globally by SHA only**, with no scoping to the repository/organization that authenticated the request: [4](#0-3) 

`Commit.where(sha: params.sha)` searches every commit tracked by every stack in the entire Shipit installation. Since `sha` is a free-form attacker-supplied string and there is no join/filter on `repository`/`stack`, an attacker who legitimately administers Org A (and therefore knows Org A's `webhook_secret`) can forge a `status` webhook, sign it with Org A's secret (satisfying `verify_signature`, which only checked that the org named in the payload — Org A — matches the secret used), while setting `sha` to a commit SHA that actually belongs to a completely different stack/repository (Org B) that the attacker does not control. `create_status_from_github!` then records a fabricated status (e.g., `state: "success"`, arbitrary `context`) directly from attacker-controlled fields onto that unrelated commit.

This is the direct analog of the report's root cause: the report shows a liquidator manipulating one field (`maxBorrowPart`) to steer execution into a code path that bypasses a protection that was designed around a different, unenforced binding (bad-debt-aware liquidation). Here, `verify_signature`'s scope (organization → secret) is silently detached from the object the handler actually mutates (`sha` → arbitrary commit in any stack), letting an attacker "aim" a payload field that was never covered by the check that authorized the request.

### Impact Explanation
A forged `success` status on `ci.require`-listed contexts (see `README.md` `ci.require` documentation) can make `Commit#deployable?` (via `Status::Group`) report a commit as deployable even though its real CI never passed. If the affected stack has `continuous_deployment` enabled, `Stack#update_deployable` / `next_commit_to_deploy` logic will pick up this falsely-"green" commit and automatically call `trigger_deploy`, executing that commit's `shipit.yml` deploy steps on the deploy host and rolling it out to production — an unauthorized deploy of a commit that was never legitimately validated, triggered by an attacker who has no access to (and no relationship with) the victim organization or its `webhook_secret`. This matches the required Critical impact category ("an unauthorized deploy").

### Likelihood Explanation
Requires only: (1) the attacker legitimately administers/owns any single organization already configured with a `github.webhook_secret` in the Shipit instance (a normal, unprivileged tenant in a multi-org deployment, as shown supported by `test/dummy/config/secrets_double_github_app.yml`), and (2) knowledge of a target commit SHA in another tracked repository (trivially obtainable from GitHub's public API/UI for public repos, or leaked via Shipit's own UI/API for private ones). No access to the victim org's secret, no `ApiClient` token, and no privileged Shipit session is required — only the ability to send an HTTP POST with a validly-signed-for-their-own-org payload to the shared `/webhooks` endpoint.

### Recommendation
Scope `StatusHandler` (and any other handler that looks up records by payload-supplied identifiers) to the repository/organization that was actually authenticated in `verify_signature`, e.g., join through `stack.repository` and require `payload.dig('repository','full_name')` (or the verified organization) to match the owner of the commit's stack before applying the status update. More generally, `WebhooksController` should pass the verified organization down to handlers and have every handler filter its target records by that verified scope rather than trusting repository/commit identifiers taken from the unauthenticated portion of the payload's semantic meaning.

### Proof of Concept
1. Attacker administers `OrgA`, which is configured in Shipit with `github.webhook_secret = SECRET_A` (a normal, non-privileged tenant setup).
2. Attacker identifies a commit SHA `deadbeef...` belonging to a Shipit-tracked stack under `OrgB`, e.g., a required CI context `ci/tests` that is currently failing/pending for that commit.
3. Attacker builds a JSON body:
   ```json
   {
     "sha": "deadbeef...",
     "state": "success",
     "context": "ci/tests",
     "repository": { "owner": { "login": "OrgA" } }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(SECRET_A, body)` (valid, since `verify_signature` looks up the secret for `OrgA` from the payload's own `repository.owner.login`).
5. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`. `verify_signature` passes because the signature matches `OrgA`'s secret and the org name embedded in the payload.
6. `StatusHandler#process` executes `Commit.where(sha: 'deadbeef...')` — matching the `OrgB` commit — and calls `create_status_from_github!`, recording a fabricated `success` status for `ci/tests` on that commit, even though the attacker has no relationship with `OrgB`.
7. If `OrgB`'s stack has `continuous_deployment: true` and `ci/tests` was the only missing required status, Shipit's continuous delivery logic now considers the commit deployable and automatically deploys it.

(Unable to fully re-verify the exact `Commit#deployable?`/`Status::Group` aggregation logic within the available iterations — this is inferred from the `README.md` documentation of `ci.require` and continuous-deployment behavior referenced in `app/models/shipit/stack.rb`; a Devin session with full repo access would be needed to trace `Commit#deployable?` end-to-end and confirm the exact conditions under which a single forged status flips deployability.)

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
```
