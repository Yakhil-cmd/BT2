### Title
Fixed 8,000-character truncation of `diff_text` in `build_refute_prompt` lets attacker-controlled diff padding push malicious lines out of the self-refute evidence window, causing false REFUTE of real findings - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_refute_prompt` truncates the diff shown to the adversarial self-refute stage to the first 8,000 characters (`diff_text[:8000]`), while the earlier investigate stage sees a much larger capped diff (up to `DIFF_PER_FILE_BYTES`=80,000/`DIFF_TOTAL_BYTES`=400,000). An attacker who controls the diff content (e.g. via padding it with large/early filler files or hunks) can push the truly dangerous `+` lines past byte 8000, and the refute prompt explicitly instructs the model to REFUTE candidates whose `vulnerableCode` "does NOT appear on any + line in the DIFF block above" — causing the model to drop a real, correctly-identified vulnerability as a false positive.

### Finding Description
`build_refute_prompt` is defined at [1](#0-0) , which slices `diff_text[:8000]` unconditionally before handing it to the adversarial refute model. The prompt then tells the model to refute a candidate if "the cited vulnerableCode does NOT appear on any + line in the DIFF block above — it is unchanged context in a touched file. The diff did not introduce it," at [2](#0-1) .

The `diff_text` fed into this function is built from the much larger, per-file/total capped diff used at the investigate stage (`DIFF_PER_FILE_BYTES=80000`, `DIFF_TOTAL_BYTES=400000`, see [3](#0-2) , and the equivalent path in `llm.py` at [4](#0-3)  then re-sliced at 8000 chars for the refute prompt, e.g. [5](#0-4) ). There is no guarantee that the region actually cited by a candidate's `vulnerableCode` remains inside the retained first-8000-character window — an attacker who controls the diff (ordinary developer changes, a large auto-generated file listed first, many touched files, or verbose comments/whitespace padding placed before the vulnerable hunk) can reliably arrange for the real `+` line to fall beyond byte 8000.

Because the refute-stage instructions treat "not found in the DIFF block above" as legitimate refuting evidence for the PRE-EXISTING rule, and because "Default = SURVIVES" only applies when no refuting rule matches, an attacker can engineer this exact false match to get a genuinely new vulnerability refuted and dropped from the final findings list — even though it was correctly identified in the investigate stage which saw the full (larger) diff.

This is not blocked by any existing control: the model does have Read/Grep tool access and *could* verify against the real file, but the prompt itself supplies a plausible, textually-grounded excuse ("not on any + line in the DIFF block above") that a model can and reasonably would use without doing the extra Read/Grep step, especially under the adversarial "try to disprove" framing that biases toward finding refuting evidence.

### Impact Explanation
This breaks the intended security invariant that the self-refute/adjudication stage should not systematically drop genuinely new, in-diff vulnerabilities. If the review model incorrectly refutes a real finding because of this truncation artifact, the vulnerable change is silently reviewed as safe: `agentic_review`/`review_api` returns no guidance for that finding (see the `survived` filtering path at [6](#0-5) ), and the developer/agent proceeds to commit/push code containing the security vulnerability. The scoped impact matches "Sensitive code, prompt, token, diff, or local file disclosure to an unintended local or remote sink" in the sense that the actual vulnerable sink (e.g., a hardcoded secret, SSRF, command injection line) ships unreviewed because the review's own truncation logic was gameable by diff shape/ordering.

### Likelihood Explanation
Exploitability only requires the ability to shape the diff being reviewed — something any contributor authoring the diff already has by construction (ordinary PR/commit content, file ordering, or padding). No privilege escalation, key leakage, or social engineering is required. The 8000-character cutoff is a small, fixed, and predictable budget relative to the 80,000/400,000-byte caps used earlier in the pipeline, making it straightforward to construct a diff (e.g., one or more filler files/hunks preceding the real change) that reliably pushes the real vulnerability outside the refute window. This is a deterministic constant, not a probabilistic race, so the effect is repeatable.

### Recommendation
Do not use a flat prefix slice of the full concatenated diff for the refute stage. Instead:
- Build the refute-stage diff excerpt per-candidate (e.g., include only the file(s)/hunks referenced by each candidate's `filePath`), or
- Increase/parameterize the refute budget to match the investigate-stage cap (or make it proportional to the number of candidates × a fixed per-candidate slice), and always ensure each candidate's cited file/hunk region is present, and
- Remove or soften the "not on any + line in the DIFF block above" refutation rule so it is not solely based on presence in a truncated string; require the model to actually Read the cited file/line when making the PRE-EXISTING determination rather than pattern-matching against a possibly-truncated inline block.

### Proof of Concept
Unit test plan for `build_refute_prompt` (and the equivalent inline logic in `llm.py`):
1. Construct `diff_files` with two files: `filler.py` containing an 8000+ character block of benign added (`+`) lines, and `vuln.py` containing a single clearly dangerous added line (e.g. `+os.system(user_input)`).
2. Run investigate-equivalent capping (`cap_diff_for_prompt`) to build `diff_text` as done in production, then call `build_refute_prompt(candidates, diff_text)` with a candidate whose `vulnerableCode` is the `os.system(user_input)` line from `vuln.py`.
3. Assert that `diff_text[:8000]` (the actual text embedded in the returned prompt) does **not** contain the vulnerable line — demonstrating the candidate's evidence is absent from the model-visible excerpt despite being present in the full diff.
4. Assert (documenting the flaw) that the refute prompt's PRE-EXISTING instruction text is present verbatim while the vulnerable `+` line is excluded — showing the model is instructed to check for evidence that has been truncated away, i.e. the invariant "truncation must not consistently drop the high-risk lines the user expects to be reviewed" is violated for any diff exceeding ~8000 characters before the vulnerable hunk.
