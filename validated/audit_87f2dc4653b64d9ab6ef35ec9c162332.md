## Title
Protocol and fund fee rounds to 0 on small trades, allowing the protocol/fund fee split to be silently zeroed out - (File: `programs/cp-swap/src/curve/fees.rs`)

### Summary
`Fees::protocol_fee` and `Fees::fund_fee` compute their share of the already-collected `trade_fee` using `floor_div` (truncating integer division). Because `trade_fee` itself is only guaranteed to be `>= 1` (via `ceil_div` in `Fees::trading_fee`), any swap whose `trade_fee` is small relative to `FEE_RATE_DENOMINATOR_VALUE` (1,000,000) will cause `protocol_fee` and/or `fund_fee` to round down to 0, even though `protocol_fee_rate`/`fund_fee_rate` are non-zero.

### Finding Description
`ceil_div`/`floor_div` and the fee split live in [1](#0-0) . `Fees::trading_fee` rounds the trade fee **up** so it is never 0 as long as `trade_fee_rate > 0` and `amount > 0`, but `Fees::protocol_fee` and `Fees::fund_fee` round **down** the protocol/fund cut *of that trade fee*.

In `CurveCalculator::swap_base_input`/`swap_base_output`, `protocol_fee` and `fund_fee` are computed directly from `trade_fee` (not from the original input/output amount): [2](#0-1) [3](#0-2) 

Because `trade_fee` can legitimately be as small as `1` (e.g., dust-sized swaps, or pools configured with a low `trade_fee_rate`), the subsequent `floor_div(trade_fee, protocol_fee_rate, 1_000_000)` and `floor_div(trade_fee, fund_fee_rate, 1_000_000)` will evaluate to `0` unless `protocol_fee_rate`/`fund_fee_rate` are extremely large (close to `1_000_000`, i.e., ~100%). `create_amm_config` only validates that rates don't overflow the denominator, not that they are large enough to avoid this rounding: [4](#0-3) .

`pool_state.update_fees` then records `protocol_fee = 0` and `fund_fee = 0` into `protocol_fees_token_x`/`fund_fees_token_x` [5](#0-4) . Since `vault_amount_without_fee` subtracts only `protocol_fees_token_x + fund_fees_token_x + creator_fees_token_x` from the raw vault balance to determine the LP-backed reserves [6](#0-5) , the entire `trade_fee` for that swap silently accrues to LPs instead of being split with the protocol/fund owner as configured.

This is directly analogous to the referenced `flatFeeForOrder` bug: an integer-division fee calculation rounds to 0 for small enough inputs relative to the configured rate, defeating the intended fee split.

### Impact Explanation
This is reachable by any unprivileged user calling `swap_base_input` or `swap_base_output` with attacker-chosen (small) `amount_in`/`amount_out`. Repeatedly performing many small/dust swaps lets an attacker (or any regular trader) systematically ensure `protocol_fee == 0` and `fund_fee == 0` on every trade, permanently diverting the protocol's and fund owner's configured revenue share into the LP-backed pool reserves. This is a fee-ledger accounting flaw: `protocol_fees_token_0/1` and `fund_fees_token_0/1` under-accrue relative to the fee split the `AmmConfig` (`protocol_fee_rate`/`fund_fee_rate`) is supposed to enforce, and this diverted value is not recoverable via `collect_protocol_fee`/`collect_fund_fee` since the ledger never recorded it.

### Likelihood Explanation
High likelihood for pools with typical/low `trade_fee_rate`, `protocol_fee_rate`, or `fund_fee_rate` settings, or for low-decimal/low-liquidity token pairs where a "dust" swap size naturally occurs. No special privileges are required — a single transaction with a small `amount_in` is sufficient, and it can be repeated indefinitely and cheaply.

### Recommendation
After computing `protocol_fee`/`fund_fee` via `Fees::protocol_fee`/`Fees::fund_fee`, treat these as fee reallocations from `trade_fee` rather than allowing them to silently round to 0 — e.g., use `ceil_div` (consistent with `trading_fee`/`creator_fee`) so the split never fully rounds away, or explicitly reject/adjust swaps where a non-zero configured `protocol_fee_rate`/`fund_fee_rate` produces a zero fee despite `trade_fee > 0`.

### Proof of Concept
1. Create an `AmmConfig` with `trade_fee_rate = 100` (0.01%), `protocol_fee_rate = 120000` (12%), `fund_fee_rate = 0`, `creator_fee_rate = 0`, `FEE_RATE_DENOMINATOR_VALUE = 1_000_000` (per `programs/cp-swap/src/curve/fees.rs`).
2. Call `swap_base_input` with a small `amount_in` such that `trading_fee(amount_in, 100)` (ceil_div) evaluates to a small number, e.g. `trade_fee = 8`.
3. `protocol_fee = floor_div(8, 120000, 1_000_000) = 0` (since `8*120000 = 960000 < 1_000_000`), while `trade_fee = 8` is still deducted from the swapper's input and remains in the vault.
4. `pool_state.update_fees` records `protocol_fee = 0`, so `protocol_fees_token_x` is unchanged, and the full `trade_fee` of 8 units silently becomes part of the LP-backed reserve via `vault_amount_without_fee` instead of 12% (≈1 unit, rounding aside) being reserved for the protocol.
5. Repeating this swap many times accumulates a systematic loss of protocol/fund fee revenue with zero cost beyond normal trade fees.

    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }
