### Title
Webhook organization used to select the HMAC secret is not bound to the repository the payload writes to - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification based on an unauthenticated field of the payload itself (`repository.owner.login` / `organization.login`), rather than binding that verified organization to the repository that the subsequent event handlers actually act upon (`repository.full_name`). This breaks the equality "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` is a `before_action` that runs prior to `create`: [1](#0-0) 

It calls `Shipit.github(organization: repository_owner)` to fetch the `GithubApp`/secret to verify against, where: [2](#0-1) 

`repository_owner` is read directly out of the attacker-supplied JSON body (`params.dig('repository', 'owner', 'login')`), before any signature has been validated. The HMAC check itself only proves that the raw body was signed with *that org's* secret: [3](#0-2) 

However, once the request passes this check, `create` parses the same raw body again and dispatches it to event handlers (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`), which locate the target `Stack`/`Repository` using `repository.full_name` — a separate field in the same JSON body that is never cross-checked against the verified `repository.owner.login`: [4](#0-3) 

Because nothing ties `repository.owner.login` (the field used to pick the verification secret) to `repository.full_name` (the field used to determine which repository/stack record is written to), an attacker who possesses (or is legitimately entitled to configure) the webhook secret for organization A can craft a JSON payload where `repository.owner.login = "org-A"` (so the correct secret is selected and the HMAC validates) but `repository.full_name = "org-B/some-repo"`. The signature check passes, yet the event is processed against a repository/stack belonging to an entirely different organization.

This is structurally the same class of defect as the audit finding: the report describes a value (`amount`) that is acted upon by a `delegatecall` but whose refund side effect is not durably bound/committed independent of the call's own control flow, so a value consumed downstream diverges from the value that was actually validated/protected. Here, the value used for the *authorization decision* (`repository.owner.login`) diverges from the value used for the *effectful action* (`repository.full_name`), with no binding enforced between them.

### Impact Explanation
This allows an unprivileged webhook sender who controls (or has been given) any one organization's webhook secret to force Shipit to process fabricated push/status/check_suite/pull_request events against a *different* organization's repository, since the handler layer trusts `repository.full_name` unconditionally after the (mis-scoped) signature check. Depending on the handler reached, this can trigger `GithubSyncJob`, commit status writes, or check-run refreshes for a repository/stack that does not belong to the organization whose secret authenticated the request — a cross-repository/cross-organization write driven entirely by payload content, matching the "cross-repository writes" High/Critical impact bucket in scope.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP POST to `/webhooks` with a validly-signed body for *some* organization Shipit is configured to serve (a routine capability for anyone able to configure a webhook against their own org/repo in a multi-tenant Shipit deployment), and to set an arbitrary `repository.full_name` in the JSON body — no elevated Shipit session, API token, or GitHub App private key is needed. The mismatch is unconditional and does not depend on any race condition or edge case.

### Recommendation
After extracting `repository_owner` and verifying the signature against that organization's secret, re-derive (or assert) that every other repository-identifying field consumed by downstream handlers (`repository.full_name`, `repository.owner.login` used in `PushHandler`, `StatusHandler`, etc.) belongs to the same organization that was used to select/verify the secret. Reject the webhook (422) if `repository.full_name`'s owner segment does not match the verified `repository_owner`.

### Proof of Concept
1. Configure Shipit with two organizations, `org-A` (attacker-controlled, webhook secret known to attacker) and `org-B` (victim, has a tracked stack/repo `org-B/victim-repo`).
2. Craft a `push` event JSON body:
   ```json
   {
     "repository": { "owner": { "login": "org-A" }, "full_name": "org-B/victim-repo" },
     "after": "<attacker-chosen sha>"
   }
   ```
3. Compute `X-Hub-Signature` using `org-A`'s known `webhook_secret` over this exact raw body, per `Hook::DeliverySigner`/`verify_webhook_signature` logic: [5](#0-4) 
4. `POST /webhooks` with header `X-Github-Event: push` and the computed signature.
5. `verify_signature` resolves `Shipit.github(organization: "org-A")` and validates successfully against `org-A`'s secret. `create` then dispatches the push payload to `Shipit::Webhooks.for_event('push')` handlers, which look up the stack/repository using `repository.full_name = "org-B/victim-repo"`, causing Shipit to enqueue a sync/deploy-relevant job against `org-B`'s stack despite the request only having been authenticated for `org-A`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
