### Title
Predictable AA randomness from attacker-known `trigger.unit` allows costless outcome-grinding in gambling AAs (roll-back-style RNG bias) - ([File: formula/evaluation.js])

### Summary
The oscript function `number_from_seed()` lets an Autonomous Agent (AA) author derive "randomness" by hashing any expression the author supplies. If a gambling/dice AA seeds this function with `trigger.unit` (or any other value the trigger author fully controls and can compute *before* broadcasting), the trigger poster can locally pre-compute the exact outcome and simply refuse to broadcast a losing unit, retrying with a new `trigger.unit` (by changing parents/timestamp) until a winning hash is found — at zero cost, since an unsigned/unbroadcast unit never touches the DAG. This mirrors the EosDice "roll-back" incident, where the attacker exploited a resource-rollback mechanism to retry a dice bet until it produced a favorable, low-cost outcome.

### Finding Description
`number_from_seed` computes a deterministic PRNG value from a SHA-256 hash of whatever seed expression is passed to it: [1](#0-0) . There is no restriction preventing the seed from being `trigger.unit`, `trigger.address`, or other data that is 100% knowable to the unit's author prior to posting.

`trigger.unit` is populated from `objUnit.unit`, the hash of the trigger unit itself, which the composer/wallet computes and controls at composition time, long before the unit is ever broadcast to peers: [2](#0-1) . A wallet/attacker can freely vary unit-hash-affecting fields (parent selection, timestamp) to iterate over many candidate `trigger.unit` values, feed each candidate into the exact same `number_from_seed` algorithm client-side (identical SHA-256 based logic is trivially reproducible off-chain), and only actually sign+broadcast the specific unit whose resulting seed yields a winning game outcome. Losing candidate units are simply discarded — there is no cost or on-chain trace for a unit that is never broadcast, just like EOS's rollback let `binaryfunxxx` discard resource-costly failing rolls and only "commit" bets that later profited.

This is conceptually the same "outcome pre-check + selective commit" pattern as the EosDice incident: both let an attacker preview a pseudo-random game result before it becomes economically binding, and only proceed with favorable draws.

### Impact Explanation
Any AA built as a game of chance (dice, lottery, coin-flip) that seeds `number_from_seed` (or `sha256`, similarly reachable at [3](#0-2) ) with attacker-controlled/predictable data such as `trigger.unit`, `trigger.address`, or `trigger.data` loses all unpredictability. The attacker can guarantee wins on demand, draining the AA's balance — a concrete AA fund loss, matching the "Medium" severity of the source incident (funds extracted from a betting contract via biased/predictable outcome selection).

### Likelihood Explanation
This requires no privileged access — merely a normal wallet composing candidate trigger units, which is the standard "unprivileged unit poster" capability in scope. The `number_from_seed`/`trigger.unit` combination is a natural, commonly-seen mistake for developers writing dice/lottery AAs in oscript, since `trigger.unit` looks unit-unique and superficially "random" but is actually attacker-known pre-broadcast data.

### Recommendation
- In documentation/linting for AA authors, explicitly warn against using `trigger.unit`, `trigger.address`, `trigger.data`, or any other value known to the trigger author prior to broadcast as a randomness seed.
- Encourage/enforce use of `response_unit` (only determined after the response is composed, depending on `last_ball_unit`/parent selection at response time) or an external oracle-provided random feed as the seed source instead.
- Consider adding a formula-validation warning (in `formula/validation.js`) when `number_from_seed`/`sha256` seeds are built purely from `trigger.*` fields without any AA-controlled or oracle-sourced entropy mixed in.

### Proof of Concept
1. Deploy an AA with logic such as:
   ```
   {
     $roll = number_from_seed(trigger.unit, 1, 100);
     if ($roll <= 49)
       bounce("you lose");
     ...
     send double the wager to trigger.address ...
   }
   ```
2. Off-chain, an attacker's wallet composes a payment-triggering unit to this AA but does not sign/broadcast it yet.
3. Using the same algorithm as `formula/evaluation.js` (SHA-256 of the seed, taking the first 16 hex chars as a fraction, per [1](#0-0) ), the attacker computes what `number_from_seed(trigger.unit, 1, 100)` would evaluate to for this exact candidate `objUnit.unit`.
4. If the result is a loss, the attacker changes parent units/timestamp (any field influencing the unit hash), producing a new `trigger.unit`, and repeats step 3.
5. Once a winning hash is found, the attacker signs and broadcasts that specific unit, guaranteeing a win with no cost incurred for the discarded losing attempts — directly analogous to the EosDice roll-back exploit's free-retry-until-win pattern.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };

		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
