### Title
Cross-repository commit-sha lookup in `StatusHandler#process` lets any authenticated-webhook sender forge a `state=error` status that blocks a *different* stack's continuous deployment - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `Commit.where(sha: params.sha)`, with no scoping to the `repository.full_name`/organization that produced and signed the webhook. Because webhook-signature verification (`WebhooksController#verify_signature`) is only checked against the GitHub App config for the *sending* organization, an attacker who owns any repository wired into Shipit (their own fork/org) can send a validly-signed `status` webhook whose `sha` field is copied from a public commit belonging to Victim's stack, causing Shipit to write a forged `error` status onto Victim's commit and block Victim's `ContinuousDeliveryJob`.

### Finding Description
The binding the code is supposed to enforce is:
`Status.state written to commit C == state reported by GitHub CI for the (repository, sha) pair that C actually belongs to`, gated by the assumption that `Commit.where(sha:)` only ever resolves to commits owned by the repository that authenticated the webhook.

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) picks the `GitHubApp` via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled JSON body (`params.dig('repository','owner','login')`). This only proves the payload was signed by *some* configured GitHub App/organization known to this Shipit instance - not that it corresponds to Victim's repository.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This performs a **global, unscoped** lookup by `sha` across the entire `commits` table, matching any stack whose `sha` happens to equal `params.sha` - it never checks `params['repository']['full_name']` against `commit.stack.repository`.
- `Commit#create_status_from_github!` → `Status.replicate_from_github!` writes the forged `state` (e.g. `"error"`) as a real `Status` row on the matched commit (`app/models/shipit/status.rb:24-33`, `app/models/shipit/commit.rb:165-169`).
- `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) becomes `false` once `status.state != 'success'`, so `Commit#schedule_continuous_delivery`/`ContinuousDeliveryJob` will not enqueue a deploy for that commit even though Victim's real CI reported success.

Attacker request: attacker registers/owns a repository whose organization is configured in Shipit (or any org for which `webhook_secret` is blank, since `GitHubApp#verify_webhook_signature` returns `true` unless a secret is configured - `lib/shipit/github_app.rb:76-83`), computes or copies Victim's public commit SHA, and POSTs to `/webhooks` with header `X-Github-Event: status` and body `{"sha": "<victim_sha>", "state": "error", "repository": {"owner": {"login": "<attacker_org>"}}, ...}`. The signature check passes because it is validated against the attacker's own organization's secret, not Victim's. `drop_unhandled_event` and the `ExplicitParameters` schema (`requires :sha`, `requires :state`) do not reject this - they only validate types/presence, not repository ownership.

Existing guards that fail to prevent this: `verify_signature` only authenticates *an* organization, not the one owning the target commit; `Commit.where(sha:)` has no `stack_id`/repository filter; no validator ties a `Status`'s `stack_id` (taken from the matched `commit.stack_id`) back to the repository asserted in the payload.

### Impact Explanation
An attacker with no privileges on Victim's repository/stack can write a fabricated `Status` (state `error`/`failure`) onto Victim's commit, which flips `Commit#deployable?` to `false` and prevents `ContinuousDeliveryJob` from being scheduled - effectively vetoing Victim's continuous-delivery pipeline on demand, while the record appears indistinguishable from Victim's own CI output (same `Status` model, `context`, `description` fields attacker fully controls). This is a payload for one repository (attacker's) mutating another repository's stack/commit records, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any commit sha the attacker knows (commit shas of public repos are trivially visible on GitHub), and can target multiple Victim stacks/tenants sharing the same Shipit instance as long as the sha values are known or guessable (git sha collisions across identical commit content are also possible via forking, though not required - only the sha string in the JSON body needs to match, not real git data).

### Likelihood Explanation
Preconditions: Victim stack has `continuous_deployment?` true and `ignore_ci?` false (default configuration for most stacks). Attacker cost is minimal: they need an org registered with Shipit (or an org whose `webhook_secret` is unset, which trivially bypasses verification per `return true unless webhook_secret`) and knowledge of Victim's target commit SHA - both are commonly public. No secrets of Shipit or Victim's GitHub org are required. This is directly exploitable by any internet requester who can produce a validly-signed webhook for *any* organization known to the instance, and is fully repeatable.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers, e.g. `CheckSuiteHandler`) to the repository/stack actually authenticated by the webhook: resolve the `Stack`/`Repository` from `params['repository']['full_name']` (or the `GithubHook` record that was signature-verified) and constrain `Commit.where(sha: params.sha, stack_id: stack.id)` instead of a bare global `sha` lookup. Additionally, `verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank; require a configured secret per organization/repository.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub):
```ruby
test "a status payload citing another stack's repository cannot poison a foreign commit's deployability" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment true, ignore_ci false
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, author: shipit_users(:shipit))
  victim_commit.statuses.create!(stack: victim_stack, state: 'success', context: 'ci/real')
  assert victim_commit.deployable?

  attacker_payload = ActionController::Parameters.new(
    sha: victim_commit.sha,
    state: 'error',
    context: 'ci/forged',
    description: 'forged by attacker',
    branches: []
  )

  assert_no_enqueued_jobs(only: ContinuousDeliveryJob) do
    Shipit::Webhooks::Handlers::StatusHandler.new.process # simulate attacker-signed request for a different org/repo
  end

  # Broken binding demonstrated:
  # LHS (should hold): victim_commit.status.state == 'success' (Victim's real CI result)
  # RHS (actual after attack): victim_commit.reload.status.state == 'error' (attacker-forged)
  assert_equal 'error', victim_commit.reload.status.state
  refute victim_commit.deployable?
end
```
This confirms `ContinuousDeliveryJob` is not scheduled for Victim's genuinely green commit after an attacker-forged `status` webhook naming Victim's sha but originating from an unrelated, attacker-controlled repository/organization. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
