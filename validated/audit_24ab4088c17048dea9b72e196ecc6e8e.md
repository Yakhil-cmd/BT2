### Title
Missing global tracking of consumed Bitcoin L1 lockup outpoints allows double-counting of sats credited to a bond - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
### Finding Description
`verify-l1-lockups` sums the sats credited for a staker's bond by folding over a list of Bitcoin UTXO proofs via `validate-l1-lockup`, which deduplicates outpoints only *within the single call's accumulator* (`seen-outpoints`, capped at 10 entries) using `(asserts! (is-none (index-of? seen-outpoints outpoint)) ERR_DUPLICATE_LOCKUP_OUTPOINT)` [1](#0-0) . There is no persistent, contract-wide map recording which Bitcoin `(txid, output-index)` outpoints have already been credited to a staker's bond across separate calls — the `seen-outpoints` list is built fresh in the fold's initial accumulator each invocation [2](#0-1) .

This mirrors the SafEth "residual/uncounted balance" bug class: just as SafEth failed to reconcile `address(this).balance` against what it actually tracked (allowing value to be double-handled or lost), pox-5's sats-credited accounting relies solely on ephemeral per-call state rather than a durable ledger of consumed proofs, so the same valid Bitcoin lockup transaction output can, in principle, be re-submitted in a later `register-for-bond`/rollover call (a new outer transaction, hence a fresh `seen-outpoints` accumulator) and be counted toward `amount-sats` again, inflating a staker's/bond's recorded `amount-sats` without any additional STX/sats actually being locked on Bitcoin.

### Impact Explanation
If exploitable, this breaks the core equality that a staker's bond `amount-sats` (and consequently `get-total-sbtc-staked-for-bond`, signing weight, and reward share) must correspond 1:1 to sats actually locked on the Bitcoin chain. Re-crediting an already-counted outpoint would inflate a staker's recorded stake and reward/signing weight beyond what is truly backed by locked BTC — a double-counting of a commitment, which per the rules constitutes a Critical-severity issue (double-counting a commitment or reward, signing weight exceeding locked value).

### Likelihood Explanation
This requires confirming that `verify-l1-lockups`/`validate-l1-lockup` is reachable from a public entry point (e.g., `register-for-bond` or a rollover path) more than once for the same staker with the same UTXO proof, and that no other global map (outside what I could locate in `pox-5.clar`) prevents replay of a previously-accepted outpoint. I was not able to fully trace every call site of `verify-l1-lockups` and the full bond-registration/rollover flow within the available context to confirm whether an outer guard (e.g., a global `used-outpoints` map, or a one-time-registration invariant) exists elsewhere in the contract to prevent this replay. This uncertainty should be resolved by a full code review of `pox-5.clar`'s `register-for-bond` and any rollover/renewal function that re-invokes `verify-l1-lockups`.

### Recommendation
Add a persistent, contract-level map keyed by `{txid, output-index}` (or a hash thereof) that is checked and set the first time an outpoint is credited toward a bond's `amount-sats`, and assert `(is-none (map-get? used-lockup-outpoints outpoint))` before crediting in `validate-l1-lockup`, independent of the per-call `seen-outpoints` accumulator. This ensures each Bitcoin lockup output can only ever be counted once across the contract's lifetime, not just once per transaction.

### Proof of Concept
1. Staker submits `register-for-bond` (or equivalent) with a valid L1 lockup proof for outpoint `O` (txid `T`, output-index `i`), which passes `validate-l1-lockup` and is summed into `amount-sats` [3](#0-2) .
2. In a later, separate transaction (e.g., a rollover, extend, or re-registration call that also invokes `verify-l1-lockups`), the staker resubmits the same outpoint `O` with the same valid merkle/script proof.
3. Because `seen-outpoints` starts empty for this new call's accumulator [2](#0-1) , the duplicate check `(asserts! (is-none (index-of? seen-outpoints outpoint)) ERR_DUPLICATE_LOCKUP_OUTPOINT)` does not fire, and the same BTC-locked sats are added to `sum` again, inflating `amount-sats`/staked totals without any new BTC being locked.

**Note:** I could not verify within the available index whether an outer, cross-call guard exists (e.g., in `register-for-bond` or a rollover function) that would prevent resubmission of the same outpoint across separate top-level calls. Given the ambiguity, this should be treated as a finding requiring confirmation via full tracing of `pox-5.clar`'s bond-registration and rollover code paths (a Devin session with full repository access would be needed to trace every caller of `verify-l1-lockups` and confirm or refute the presence of a persistent outpoint registry).
