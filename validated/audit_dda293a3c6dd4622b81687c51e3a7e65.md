### Title
Unfiltered `machine.environment` in attacker-controlled `shipit.yml` allows loader-variable injection (`DYLD_INSERT_LIBRARIES`) into dependency-step commands - (File: `app/models/shipit/deploy_spec.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/command.rb`)

### Summary
`DeploySpec#machine_env` returns `config('machine', 'environment')` from the checked-out repository's `shipit.yml` with no allowlist, unlike every other env-injection surface in the engine (`filter_deploy_envs`, `TaskDefinition#filter_envs`) which route through `EnvironmentVariables#permit`. `TaskCommands#env` merges this unfiltered hash directly into the env used for both `install_dependencies` (`bundle install`/`ruby`) and `perform` steps, and `Command#unbundled_env`/`Command#start` pass it straight to `PTY.spawn` with no key restriction. For a review stack under `allow_all`, the working directory is the attacker's own PR branch, so the attacker fully controls this `shipit.yml` and can set `DYLD_INSERT_LIBRARIES` (or `LD_PRELOAD`) pointing at a dylib/so they also commit to the same repo.

### Finding Description
The broken binding: `deploy_spec.machine_env` is asserted to be a **safe, pre-vetted** environment contribution (as commands assume `TaskCommands#env` only contains keys that passed through a name-based allowlist, mirroring `Stack#build_deploy`/`Stack#trigger_task`), but in fact `machine_env` (`app/models/shipit/deploy_spec.rb:69-71`) is `config('machine', 'environment') || {}` — a raw, unfiltered read straight out of `shipit.yml`, with **no** call to `EnvironmentVariables#permit` anywhere in its path.

Path:
1. Attacker opens/pushes to a PR on a repo with `provisioning_behavior_allow_all?` (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:65-70`), creating a `ReviewStack` whose `branch`/checkout content is the attacker's fork.
2. `TaskExecutionStrategy::Default#run` → `checkout_repository` checks out the attacker's commit into `@task.working_directory`, so `DeploySpec::FileSystem.new(@task.working_directory, @stack)` parses the attacker's own `shipit.yml`, including an arbitrary `machine: { environment: { DYLD_INSERT_LIBRARIES: './evil.dylib' } }` block.
3. `perform_task` → `capture_all!(@commands.install_dependencies)`, where `TaskCommands#install_dependencies` builds `Command.new(command_line, env:, chdir: steps_directory)` (`lib/shipit/task_commands.rb:17-21`) using `TaskCommands#env`, which does `.merge(deploy_spec.machine_env)` unfiltered (`lib/shipit/task_commands.rb:33-48`).
4. `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` (`lib/shipit/command.rb:92`), where `unbundled_env` is `BASE_ENV.merge(...).merge(@env.stringify_keys)` (`lib/shipit/command.rb:103-105`) — `@env` (containing `DYLD_INSERT_LIBRARIES`) is merged last, with no key allowlist anywhere in `Command`.
5. The dependency step (`bundle install`, discovered by `BundlerDiscovery#bundle_install`) is a ruby/bundler process that, on a macOS deploy host, honours `DYLD_INSERT_LIBRARIES` and preloads the attacker's dylib — which the attacker also committed into their own repo (checked out into `@task.working_directory`, i.e. on disk at spawn time).

Existing guards do not apply here: `filter_deploy_envs`/`filter_rollback_envs` (`app/models/shipit/deploy_spec.rb:174-180`) and `TaskDefinition#filter_envs` (`app/models/shipit/task_definition.rb:63-65`) only sanitize the **user/API-submitted** `env:` param (`Stack#build_deploy`, `Stack#trigger_task`) against `deploy_variables`/`task variables`. `machine_env` is a completely separate code path that bypasses `EnvironmentVariables#permit` entirely — it is never passed through `filter_deploy_envs` or any variable-definition whitelist.

### Impact Explanation
If the deploy host is macOS and the spawned ruby/bundler binary is not hardened-runtime signed (typical for rbenv/rvm-managed rubies), `DYLD_INSERT_LIBRARIES` causes the attacker's dylib to execute with the privileges of the Shipit deploy process — arbitrary code execution on the deploy host, matching the Critical RCE class defined in scope (`Command`/`PTY.spawn`). The attacker only needs `allow_all` provisioning enabled on the target repository (or `allow_with_label`/`prevent_with_label` satisfied via label control on their own PR) and a Gemfile/dependency step to trigger `install_dependencies`. This is repeatable per PR/commit against any repository configured with review stacks, and is not limited to one tenant only insofar as the deploy host itself is shared infrastructure — a compromised deploy host can affect any stack/repository/credentials materialized on that host (e.g. `GITHUB_TOKEN` set in `Commands#base_env`, other stacks' checkouts).

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with `allow_all` (or the attacker must satisfy the label condition), review-stack dependency steps must invoke a ruby/bundler binary, and the deploy host must be macOS with a non-hardened ruby toolchain. Attacker cost is low — pushing a `shipit.yml` with a `machine.environment` block and a dylib file to their own fork is trivial and requires no privileges beyond opening a PR. This is fully repeatable (one PR per attempt) and does not require any Shipit secret, session, or GitHub App credential.

### Recommendation
Route `DeploySpec#machine_env` through the same `EnvironmentVariables#permit`/allowlist mechanism used for `filter_deploy_envs`/`filter_envs`, or hard-deny any key matching known loader/interpreter variables (`DYLD_INSERT_LIBRARIES`, `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`, etc.) in `Command#unbundled_env` regardless of source, so `@env` cannot override security-sensitive process-loader variables inherited from `BASE_ENV`.

### Proof of Concept
minitest plan (`test/unit/deploy_commands_test.rb` or a new `test/lib/task_commands_test.rb`):
```ruby
test "#install_dependencies does not allow machine.environment to override loader variables" do
  @deploy_spec.stubs(:machine_env).returns('DYLD_INSERT_LIBRARIES' => './evil.dylib')
  command = @commands.install_dependencies.first
  # Binding under test: command.env['DYLD_INSERT_LIBRARIES'] should NOT equal the attacker value,
  # i.e. assert_nil command.env['DYLD_INSERT_LIBRARIES'] (currently FAILS because it equals './evil.dylib')
  assert_nil command.env['DYLD_INSERT_LIBRARIES']
end
```
Second assertion, showing it reaches `PTY.spawn`'s env:
```ruby
test "Command#unbundled_env passes through machine_env-injected loader variables" do
  command = Shipit::Command.new('true', env: { 'DYLD_INSERT_LIBRARIES' => './evil.dylib' }, chdir: '.')
  assert_equal './evil.dylib', command.unbundled_env['DYLD_INSERT_LIBRARIES']
end
