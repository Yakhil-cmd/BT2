### Title
AA balance overflow cap (`MAX_BALANCE`) enforced on trigger receipt but not on secondary transfers/settlement in `updateFinalAABalances` - ([File: aa_composer.js])

### Summary
This mirrors the Megapot "LP pool cap enforced on entry, not on settlement" bug class: ocore defines a hard safety cap `MAX_BALANCE` for AA per-asset balances, computed to stay safely below `2**63-1` and clear of `Number.MAX_SAFE_INTEGER` given `MAX_MESSAGES_PER_UNIT * MAX_CAP` headroom [1](#0-0) . This cap is explicitly checked when an AA first receives a trigger's payment (`updateInitialAABalances`), which sets `bOverflow` and rejects the trigger with `"balance overflow"` if the resulting balance exceeds `MAX_BALANCE` [2](#0-1) [3](#0-2) . However, the settlement path that applies balance deltas after an AA sends its own response unit — `updateFinalAABalances`, which processes consumed outputs and secondary payments in bulk — updates `objValidationState.assocBalances[address][asset]` and the DB `aa_balances.balance` column with no equivalent `> MAX_BALANCE` check at all [4](#0-3) .

### Finding Description
`MAX_BALANCE` exists specifically to keep AA balances from overflowing 64-bit/safe-integer arithmetic used throughout the formula evaluator and consensus-critical balance bookkeeping. The invariant is enforced only at the "deposit" entry point (`updateInitialAABalances`), analogous to Megapot enforcing the LP pool cap only at LP-deposit time via `_calculateLpPoolCap`. But `updateFinalAABalances` — which runs whenever an AA response consumes outputs and/or receives payments from secondary AA-to-AA triggers/messages as part of settling the response unit — increments `objValidationState.assocBalances[address][asset]` by arbitrary deltas (`assocDeltas[asset]`) and persists it to `aa_balances` without ever comparing the new balance to `MAX_BALANCE`. Multiple secondary triggers, chained AA calls, or accumulation of asset issuance/payments across a chain of responses can therefore drive an AA's balance for a given asset above `MAX_BALANCE` through this code path, exactly as LP pool value in Megapot could exceed its cap through the settlement/drawing accumulation path that bypassed `_calculateLpPoolCap`.

### Impact Explanation
If `assocBalances[address][asset]` (and the persisted `aa_balances.balance`) exceeds `MAX_BALANCE`, later arithmetic on that balance (e.g. `getTypeAndValue`/`getValueSize` conversions via `Decimal.toNumber()`, formula evaluations reading `balance[asset]`, or subsequent `updateInitialAABalances` additions on top of an already-near-limit value) risks precision loss or crossing `Number.MAX_SAFE_INTEGER`/`2**63-1` bounds. Because ocore is a full-replication, deterministic DAG ledger, any divergence in how different node implementations round or truncate an over-cap balance can produce node disagreement on AA-response validity/state, or effectively freeze/corrupt AA funds if the recorded balance can no longer be safely spent (funds become inaccessible or double-counted). This satisfies the "AA fund loss or freezing" / "node disagreement on validity" bar.

### Likelihood Explanation
Reaching `updateFinalAABalances` with large deltas requires either a single AA response unit with very large payment outputs, or (more practically) chained/secondary AA triggers that repeatedly add to the same AA's balance across a call chain before the aggregate is checked. Since `updateInitialAABalances`'s check only bounds the *initial* trigger deposit, and per-unit amounts are already bounded by `MAX_CAP`/`MAX_MESSAGES_PER_UNIT`, an attacker/AA author would need to orchestrate a sequence of secondary triggers each within normal limits but cumulatively pushing one AA's tracked balance over `MAX_BALANCE`. This is achievable by a normal AA-trigger sender or AA author crafting a multi-hop AA definition (a legitimately reachable path per the analog scope), but requires an unusual, deliberately engineered scenario (near-limit balances plus many chained calls), so likelihood is moderate rather than trivial.

### Recommendation
Apply the same `> MAX_BALANCE` overflow check inside `updateFinalAABalances` after computing each asset's new `objValidationState.assocBalances[address][asset]` (mirroring the check already done in `updateInitialAABalances`), and bounce/reject the response (or fail unit composition) if any asset balance would exceed `MAX_BALANCE`, rather than only guarding the initial trigger-balance update.

### Proof of Concept
Not independently reproduced in this analysis; a concrete PoC would require constructing an AA definition with a chain of secondary triggers (AA-to-AA payments) whose cumulative `assocDeltas` pushed through `updateFinalAABalances` drive `objValidationState.assocBalances[address][asset]` above `MAX_BALANCE` without ever tripping the `bOverflow` check that only exists in `updateInitialAABalances`. This would need to be validated by instrumenting/testing `aa_composer.js`'s `handleTrigger`/`updateFinalAABalances` flow directly, which was not verified end-to-end here — flagged as an area for further confirmation before treating this as fully proven.

	function updateFinalAABalances(arrConsumedOutputs, objUnit, cb) {
		if (trigger_opts.bAir)
			throw Error("updateFinalAABalances shouldn't be called with bAir");
		var assocDeltas = {};
		var arrNewAssets = [];
		arrConsumedOutputs.forEach(function (output) {
			if (!assocDeltas[output.asset])
				assocDeltas[output.asset] = 0;
			assocDeltas[output.asset] -= output.amount;
			// this might happen if there is another pending invocation of our AA that created the outputs we are spending now
			if (!objValidationState.assocBalances[address][output.asset])
				arrNewAssets.push(output.asset);
		});
		objUnit.messages.forEach(function (message) {
			if (message.app !== 'payment')
				return;
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address !== address)
					return;
				if (!assocDeltas[asset]) { // it can happen if the asset was issued by AA
					assocDeltas[asset] = 0;
					arrNewAssets.push(asset);
				}
				assocDeltas[asset] += output.amount;
			});
		});
		var arrQueries = [];
		if (arrNewAssets.length > 0) {
			var arrValues = arrNewAssets.map(function (asset) { return "(" + conn.escape(address) + ", " + conn.escape(asset) + ", 0)"; });
			conn.addQuery(arrQueries, "INSERT "+conn.getIgnore()+" INTO aa_balances (address, asset, balance) VALUES "+arrValues.join(', '));
		}
		for (var asset in assocDeltas) {
			if (assocDeltas[asset]) {
				conn.addQuery(arrQueries, "UPDATE aa_balances SET balance=balance+? WHERE address=? AND asset=?", [assocDeltas[asset], address, asset]);
				if (!objValidationState.assocBalances[address][asset])
					objValidationState.assocBalances[address][asset] = 0;
				objValidationState.assocBalances[address][asset] += assocDeltas[asset];
			}
		}
		if (assocDeltas.base)
			byte_balance += assocDeltas.base;
		async.series(arrQueries, cb);
	}
