### Title
Malicious secondary AA can force revert of an unrelated primary AA trigger, blocking permissionless protocol actions such as liquidation/settlement - (File: `aa_composer.js`)

### Summary
When an autonomous agent (AA) sends a payment to another address as part of its response, and that address is itself an AA, the recipient AA is automatically invoked as a "secondary trigger." If the attacker deploys a malicious AA at that address whose logic unconditionally bounces, the resulting failure propagates all the way back up and forces the *entire* primary trigger — including all of its other state changes and unrelated payments — to be rolled back and bounced. This lets any user who controls (or is entitled to receive funds at) an AA address deny a protocol's permissionless action (e.g. liquidation, forced settlement) simply by making their receiving AA always bounce.

### Finding Description
Autonomous agents in ocore are executed via `handleTrigger()` in `aa_composer.js`. When a primary AA's response includes a payment whose output address is itself an AA, `handleSecondaryTriggers()` is invoked to run that recipient AA's logic synchronously as part of the same top-level transaction: [1](#0-0) 

If the secondary (child) AA "bounces" (fails/reverts, e.g. via `bounce()` in its own oscript logic), its `onDone` callback returns a `bounce_message`, which is treated as an error in the `async.eachSeries` loop: [2](#0-1) 

Because the top-level call is not itself a secondary trigger (`bSecondary === false`), the failure calls `revert()`, which explicitly rolls the *entire* primary trigger's execution back to the initial savepoint — undoing all of the primary AA's already-computed state changes and payments to any other, unrelated addresses in the same transaction — and then invokes `bounce()` on the primary trigger itself: [3](#0-2) 

This atomic "all messages in a trigger succeed or none do" behavior is exercised and expected in the test suite (e.g. `chain of AAs`, `issue recently defined asset`, `calling a remote function that fails`), confirming it is deliberate, universal AA-call semantics rather than a narrow edge case: [4](#0-3) [5](#0-4) 

This mirrors the reported bug class: a party who controls the destination of a payment triggered by a permissionless protocol action can unilaterally cause the entire action to fail, by making the receiving logic always reject/bounce — exactly as a smart-contract account that reverts on `receive()` blocks a Solidity `.transfer()`-based settlement.

### Impact Explanation
Any AA-based protocol (lending, vaults, insurance, marketplaces, DEXes) that must permissionlessly pay funds to a user-controlled or user-specified address risks denial of service if that address is an AA that always bounces:
- A borrower/user can deploy or control an AA at the payout address used by a protocol's liquidation, settlement, or forced-close logic and make it always bounce, blocking that specific liquidation/settlement action even though it is supposed to be callable/executable by anyone.
- Because the revert is not scoped to just the payment message but to the *entire* trigger, other unrelated state updates and payouts to third parties bundled in the same trigger are also rolled back, amplifying the griefing impact beyond the single victim.
- This can freeze protocol funds/state in the affected AA (funds stay locked in the position that cannot be liquidated/settled) and prevent legitimate protocol actions from ever confirming for that account, similar in effect to the original Notional "reject vault settlement" impact (blocked liquidation, blocked forced settlement).

### Likelihood Explanation
Exploitation only requires the ability to deploy an AA (any user can permissionlessly define/post an AA definition and have funds/payouts routed to it, e.g. by using it as a collateral/borrower/liquidity-provider address in a protocol) and to write a trivial "always bounce" message handler. No special privileges, timing races, or network-level assumptions are needed — it is purely a function of the recipient's own oscript logic, matching the "unprivileged AA author" and "AA trigger sender" threat model.

### Recommendation
- Protocol AAs that make permissionless payouts to addresses they do not control (e.g. liquidation proceeds, forced settlement refunds) should avoid letting a single failing secondary AA revert the entire trigger. Options include:
  - Splitting the payout into its own trailing message/trigger executed after the protocol AA's own critical state changes are finalized, so a bounce by the recipient cannot undo the protocol's own settlement/liquidation bookkeeping.
  - Detecting/whitelisting whether a destination address is an AA and, if so, avoiding synchronous chaining for critical/forced flows, or documenting this risk so protocol authors design around it (e.g. crediting an internal balance the recipient can pull later, rather than pushing funds through a potentially hostile AA in the same atomic trigger).
- At the ocore engine level, consider offering a payment mode/flag that sends funds to an AA address without invoking it as a secondary trigger (pure balance credit, no code execution), so protocols have a "safe push" option analogous to wrapping ETH into WETH instead of relying on a raw `.transfer()`.

### Proof of Concept
1. Deploy `MaliciousAA`, an AA whose only message logic is `bounce("reject");` unconditionally.
2. Deploy `ProtocolAA`, representing e.g. a lending/vault protocol, whose primary trigger logic:
   - Updates internal state (e.g. marks a position/vault as settled/liquidated, credits other users).
   - Sends a payment message to the address on record for the user being settled/liquidated (which is `MaliciousAA`'s address).
3. Anyone (attacker or an unrelated third party) posts a trigger unit that invokes `ProtocolAA`'s settlement/liquidation function for the position owned by `MaliciousAA`.
4. `handleSecondaryTriggers()` invokes `MaliciousAA` as a secondary trigger; it bounces immediately.
5. Per `revert()`/`handleSecondaryTriggers()` logic (`aa_composer.js` lines 1743–1783), the entire `ProtocolAA` primary trigger — including the position-settlement state update and any payouts to other unrelated users bundled in the same response — is rolled back, and the primary trigger itself is bounced back to the caller.
6. Result: the settlement/liquidation can never succeed as long as `MaliciousAA` keeps bouncing, demonstrating the permissionless action is fully blockable by the fund recipient, analogous to the original Vault-settlement rejection bug.
