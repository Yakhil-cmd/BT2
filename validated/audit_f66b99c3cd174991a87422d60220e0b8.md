### Title
Cross-organization webhook forgery: authenticated `repository.owner.login` is unbound from the acted-upon `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound GitHub webhook by reading `repository.owner.login` from the *unverified* JSON body, while the handlers that actually act on the payload (create stacks, sync commits, trigger deploy pipelines) key off the independent `repository.full_name` field from the same body. These two fields are never checked for consistency, so any tenant who legitimately controls one GitHub App/organization configured in Shipit can forge a webhook that authenticates as their own organization but is routed to and acted upon as if it came from a completely different (victim) repository/stack.

### Finding Description
`verify_signature` picks the verifying app config via:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where `repository_owner` is read straight from the JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` resolves to a **per-organization** `GitHubApp`/`webhook_secret` when Shipit is configured for multiple GitHub organizations (the documented "Using Multiple Github Applications" setup) [3](#0-2) [4](#0-3) . Verification only checks that the raw body was HMAC-signed with *that organization's* secret [5](#0-4)  - it never checks that the org whose secret was used actually owns the repository referenced elsewhere in the same body.

The handler dispatch (`create`) simply hands the raw parsed JSON to all registered handlers for the event [6](#0-5) . Handlers resolve the target `Stack`/`Repository` from a *different* field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) 

`PushHandler` uses this to look up stacks and immediately kick off a sync:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [8](#0-7) 

Because `repository.owner.login` (used for signature-key selection) and `repository.full_name` (used for stack routing) are both attacker-supplied fields inside the same request body that the attacker fully controls and signs, an attacker who legitimately administers **their own** Shipit-registered GitHub organization (and therefore knows/controls their own App's `webhook_secret`) can:
1. Set `repository.owner.login` to their own org so `verify_signature` selects their own known secret and the HMAC check passes.
2. Set `repository.full_name` to an entirely different, victim organization's repository already onboarded as a Shipit `Stack`.

The signature check has no way to reject this: it only verifies "this body was signed with Org-A's secret," not "the repository this body claims to modify belongs to Org-A."

### Impact Explanation
This breaks the binding "organization whose secret authenticated the webhook" == "repository the webhook payload is used to write to." An attacker who is not authorized on the victim repository at all (no Shipit account, no `ApiClient` token, no GitHub write access to the victim repo — only administrative control of their own, separate, legitimately-onboarded GitHub organization/App) can:
- Force `GithubSyncJob` to run against an arbitrary victim `Stack` with an attacker-chosen `expected_head_sha` [9](#0-8) , causing Shipit to fetch and ingest commits for that stack out of band and re-cache its deploy spec, and, if `continuous_deployment` is enabled on that stack, potentially triggering pipeline actions the victim organization did not initiate.
- More generally, drive any registered webhook handler (`membership`, `pull_request`, `check_suite`, `status`, etc.) against a repository/stack/organization the attacker does not own, since every handler trusts `payload.dig('repository', 'full_name')` (or `organization.login` for membership events) without re-validating it against the authenticated org.

This is a cross-organization/cross-repository write capability reachable by an unprivileged-relative-to-the-victim attacker, matching the "Critical - cross-repository writes / unauthorized deploy" bar.

### Likelihood Explanation
This is directly exploitable in any Shipit deployment configured with the documented multi-organization GitHub App setup (a supported, first-class configuration, not a misconfiguration) — any tenant onboarded with their own GitHub App automatically has the credentials needed to forge cross-tenant webhooks. It requires no compromise of the victim, no session, no `ApiClient` token, and no GitHub write access to the victim repository — only being one of potentially many legitimate/self-service organizations wired into a shared Shipit instance.

### Recommendation
After verifying the HMAC signature, re-derive the organization/repository the signature was issued for and require that `repository.full_name`'s owner match `repository_owner` (or, better, always look up the target `Stack`/`Repository` by an identifier bound to the authenticated organization, e.g. only accept events for repositories that belong to the same `Repository.owner` as the app config used for verification) before dispatching to handlers.

### Proof of Concept
1. Deploy Shipit with the multi-org GitHub App configuration (`github.AttackerOrg` and `github.VictimOrg`, each with distinct `webhook_secret`s), as documented in `docs/setup.md`. Ensure a `Stack` already exists for `VictimOrg/victim-repo` (`branch: main`).
2. As the administrator of `AttackerOrg` (a legitimate, unrelated tenant), craft a JSON payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<any-sha-attacker-wants-synced>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac_sha1(AttackerOrg_webhook_secret, body)>` using the webhook secret the attacker legitimately knows for their own org's GitHub App.
4. POST this body with header `X-Github-Event: push` to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "AttackerOrg")`, whose `webhook_secret` matches the attacker's signature ⇒ verification passes.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("VictimOrg/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, enqueuing `GithubSyncJob` against the victim's stack — despite the attacker having no access to `VictimOrg` at all.

**Uncertainty**: I could not fully trace `Stack#sync_github` or confirm exactly which GitHub credentials `GithubSyncJob#fetch_missing_commits`/`stack.github_api` uses at runtime for the ensuing GitHub API calls (it resolves via `stack.github_app` → `Shipit.github(organization: repository.owner)`, using the victim's own real App per `app/models/shipit/stack.rb:434-440`), nor whether `continuous_deployment` auto-deploy paths would trigger further from this without additional CI/status gating. A Devin session with full repo/test access would be needed to run the existing `test/controllers/webhooks_controller_test.rb` and `test/jobs/github_sync_job_test.rb` suites and confirm the exact downstream effects end-to-end.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
