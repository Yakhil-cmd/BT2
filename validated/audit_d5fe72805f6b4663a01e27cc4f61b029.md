### Title
Unauthenticated `sender` binding in `StackStxOp`/`PreStxOp` allows locking any victim's STX without their signature - (File: `stackslib/src/chainstate/burn/operations/stack_stx.rs`)

### Summary
`PreStxOp::parse_from_tx` sets the future `sender` of a stacking operation to whatever Bitcoin address appears in output[0] of the PreStx transaction, with no proof that the creator of that transaction controls the corresponding private key. `StackStxOp::get_sender_txid` only requires that vout=1 of that same PreStx txid be spent, which the attacker fully controls, so the attacker can bind any victim's Stacks address as `sender` while authorizing the operation with their own unrelated key.

### Finding Description
The claimed equality: `STX locked by an applied StackStxOp == STX owned by the party that cryptographically authorized the operation`. This is broken.

- `PreStxOp::parse_from_tx` derives `output` purely from output[0]'s address of the PreStx Bitcoin transaction, converted directly via `try_into_stacks_address()`: [1](#0-0) . Nothing ties this address to the key(s) that signed the transaction's *inputs* - any Bitcoin transaction can pay an output to an arbitrary address without the payer controlling that address's key.
- `StackStxOp::get_sender_txid` only enforces that the StackStx transaction's input spends `vout == 1` of the referenced PreStx txid: [2](#0-1) . It performs no check relating the signer of this input to the address recorded in output[0] of the PreStx tx.
- `Burnchain::classify_transaction` then takes `sender = &pre_stack_stx.output` (attacker-chosen victim address) and constructs the `StackStxOp` with it: [3](#0-2) .
- `process_stacking_ops` executes `stack-stx` directly as a contract-call with `tx-sender` forced to `sender.clone().into()` - i.e., the victim's principal - with no Stacks-layer signature check at all: [4](#0-3) .

Attacker's exact call sequence:
1. Craft a Bitcoin transaction (`PreStxOp`) with output[0] = victim's legacy Bitcoin address (i.e., the hash160 embedded in the victim's real Stacks address) and output[1] = an address the attacker controls. The attacker only needs to sign the transaction's own funding input, not anything belonging to the victim.
2. Spend output[1] with a `StackStxOp` transaction, self-signed, encoding `stacked_ustx`, `num_cycles`, `reward_addr` = attacker's own PoX payout address.
3. `get_sender_txid`/`classify_transaction` accept the pair since only the vout=1 spend condition is checked; `sender` is copied from the unverified output[0] address (the victim).
4. `process_stacking_ops` invokes pox-4/pox-5 `stack-stx` with `tx-sender` = victim, locking the victim's real STX balance and routing PoX BTC rewards to the attacker's `reward_addr`.

This is repeatable for any number of distinct victim addresses using the same attacker Bitcoin key on vout=1 across many separate PreStx/StackStx transaction pairs; only the outputs of the PreStx tx and target address change, no interaction with victims is required, and the guard checks in the rules (`verify-not-prepare-phase`, `check-pox-lock-period`, `verify-signer-key-grant`, etc.) operate on the already-computed `sender`/args and never verify that `sender` was cryptographically authorized by whoever signed the burnchain transaction.

### Impact Explanation
The attacker can (a) lock any victim account's unlocked STX balance for up to the maximum cycle count without the victim's consent (temporary freezing of staked funds), and (b) redirect the resulting PoX/BTC stacking rewards that should accrue to the victim to an address the attacker fully controls (theft of stacking rewards). Because the sender-binding flaw applies independently to every PreStx/StackStx pair, the attack is fully repeatable across arbitrarily many victim principals using a single attacker-controlled Bitcoin key for vout=1, matching the Critical category ("theft ... of locked STX or sBTC rewards", "temporary freezing of staked STX").

### Likelihood Explanation
No privileged role is required: the attacker only needs their own Bitcoin UTXOs to fund the PreStx/StackStx transaction pair, ordinary knowledge of the target Stacks address's underlying hash160 (public information embedded in every c32 address), and no interaction with or signature from the victim. This works against any standard single-sig Stacks account whose address is the canonical hash160-derived c32 address (the overwhelming majority of accounts) with a nonzero unlocked balance, and can be repeated per victim with negligible marginal cost (one more Bitcoin OP_RETURN transaction pair per victim).

### Recommendation
Cryptographically bind the `sender`/`output` field of `PreStxOp` to the signer of the transaction's own inputs (e.g., require output[0]'s address to match the signer of input 0, or require an additional signature proving control of the claimed sender address) before it is trusted as the stacking principal in `StackStxOp`, `TransferStxOp`, and `DelegateStxOp`. Alternatively, require the StackStx/DelegateStx/TransferStx spending key itself to match the `sender` address, rather than an independently-chosen output[1].

### Proof of Concept
Rust integration test plan (extending `stackslib/src/burnchains/tests/db.rs` style tests or a `neon_integrations.rs`-style test):
1. Create victim principal `V` (real key `sk_v`) with a nonzero initial balance in `conf.initial_balances`.
2. Craft a `PreStxOp` with `output = V`'s address but sign/fund the underlying Bitcoin transaction with an unrelated attacker key `sk_a1` (never using `sk_v`).
3. Craft a `StackStxOp` transaction spending vout=1 of the PreStx tx, signed only by the attacker's key controlling that output, with `reward_addr` = attacker's own address.
4. Mine the blocks and assert:
   - Before: `V`'s STX balance is fully unlocked (`get_balance`/account query shows `locked = 0`).
   - After: `V`'s STX balance shows `locked > 0` (`stacked_ustx` amount) even though `sk_v` never signed any Stacks or Bitcoin transaction.
   - The PoX reward set / `reward_addr` entry created for the cycle is the attacker's address, not `V`'s.
5. Repeat steps 2-4 for several distinct victim principals `V1..Vn` using the same attacker key on vout=1 each time, asserting all victims' balances become locked in the same or successive blocks despite none of them signing anything.

    pub fn get_sender_txid(tx: &BurnchainTransaction) -> Result<&Txid, op_error> {
        match tx.get_input_tx_ref(0) {
            Some((ref txid, vout)) => {
                if *vout != 1 {
                    warn!("Invalid tx: StackStxOp must spend the second output of the PreStxOp");
                    Err(op_error::InvalidInput)
                } else {
                    Ok(txid)
                }
            }
            None => {
                warn!("Invalid tx: StackStxOp must have at least one input");
                Err(op_error::InvalidInput)
            }
        }
    }
