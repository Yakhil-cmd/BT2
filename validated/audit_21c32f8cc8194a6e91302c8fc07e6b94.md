### Title
Missing `Halted` operating-mode check in `snowbridge_pallet_system_frontend::add_tip` allows bypassing bridge halt - ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

### Summary
`pallet-system-frontend` on AssetHub exposes `register_token` and `add_tip`, both of which burn/swap user assets and forward a `Transact` XCM to the BridgeHub `EthereumSystemV2` pallet. `register_token` checks `ExportOperatingMode` (`Halted`) before doing any work, but `add_tip` performs the swap/burn and dispatches the XCM to BridgeHub without any such check.

### Finding Description
`register_token` explicitly guards against the halted state: [1](#0-0) 

`add_tip`, dispatched by any signed account with no privileged origin, performs the same category of state-changing operations (asset swap, ether burn, XCM dispatch to BridgeHub) but omits the `ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted)` check entirely: [2](#0-1) 

The `ExportOperatingMode` storage and the `Halted` error exist specifically to allow governance to stop Ethereum-bound export operations during an incident: [3](#0-2) [4](#0-3) 

This is structurally the same class of bug as the Connext report: a set of sibling entry points that are all supposed to be blocked by the same guard, but the guard was applied inconsistently — one function checks it, a similar function does not. The `ExportPausedQuery` implementation for this pallet is likewise only driven by `ExportOperatingMode`, and is used by `PausableExporter` to gate `SendXcm` at the router level, but that router-level gate is a separate mechanism (used for the raw XCM `SendXcm` implementation) and does not block the pallet's own `add_tip` extrinsic, which builds its own `Transact` call and sends it directly via `Self::send_xcm` / `T::XcmSender::deliver`, bypassing that pausable exporter check: [5](#0-4) [6](#0-5) 

I could not confirm from the code inspected whether the `SendXcm` type configured for `T::XcmSender` in the actual AssetHub runtime is wrapped with `PausableExporter`; if it is, the halt might still be enforced at the router layer for the underlying message delivery, which would reduce/negate the practical impact of this gap. I was unable to fully verify this wiring within the available context.

Additionally, on the BridgeHub side, `snowbridge_pallet_system_v2::add_tip` performs no operating-mode check of its own either — it only checks `T::FrontendOrigin`: [7](#0-6) 

So if the AssetHub-side `add_tip` check is bypassed and the runtime's `XcmSender` is not itself halt-aware, there is no downstream check on BridgeHub that would reject the tip while the system is supposed to be halted.

### Impact Explanation
If confirmed that `T::XcmSender` for `pallet-system-frontend` is not wrapped in a halt-aware router, a user could continue to submit `add_tip` calls (swapping/burning their own assets and sending `Transact` messages to BridgeHub) even after governance sets `ExportOperatingMode::Halted` to stop bridge activity during an incident. This would undermine the purpose of the halt mechanism, though the affected calls only involve the caller's own assets (swap + burn of the caller's tip asset) and update relayer reward bookkeping (`Tips`/`LostTips`) on BridgeHub — it is not a direct fund-theft vector, and it doesn't touch the actual outbound message queue processing/backing/commitments guarded elsewhere. This bounds it to a Medium-severity, "missing pause enforcement" class finding rather than a Critical/High loss-of-funds finding.

### Likelihood Explanation
Any signed AssetHub account can trigger `add_tip` at will with no special privileges — the only prerequisite is that governance has previously set `ExportOperatingMode::Halted` for an operational reason. Given the pallet code as written, the omission is deterministic and always reproducible whenever the pallet is halted, contingent on the unresolved question of whether the configured `T::XcmSender` independently enforces the halt.

### Recommendation
Add the same `ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted)` check at the start of `add_tip` in `bridges/snowbridge/pallets/system-frontend/src/lib.rs`, mirroring the check already present in `register_token`, so that both dispatchables that trigger swap/burn + BridgeHub `Transact` calls are consistently blocked while the export operating mode is halted.

### Proof of Concept
- Failed/missing guard identified by direct code comparison: `register_token` (lines 225–252) contains the `Halted` check; `add_tip` (lines 254–273) does not, in `bridges/snowbridge/pallets/system-frontend/src/lib.rs`.
- Existing unit test `test_switch_operating_mode` in `bridges/snowbridge/pallets/system-frontend/src/tests.rs` (lines 113–147) confirms `register_token` is rejected with `Error::<Test>::Halted` after `set_operating_mode(Halted)`, but no analogous test exists (or was found) asserting that `add_tip` is likewise blocked when halted — the existing `add_tip_*` tests (lines 149–267) do not set `Halted` mode at all.
- I did not execute a new local reproduction; this analysis is based on static code inspection of the available files only. A concrete integration reproduction would need to: (1) call `EthereumSystemFrontend::set_operating_mode(Root, Halted)`, then (2) call `EthereumSystemFrontend::add_tip(signed_user, message_id, asset)` and observe it still succeeds (no `Halted` error), confirming the missing guard — this was not run in this session.
- Unresolved: whether the runtime-level `T::XcmSender` (outside the pallet's own mock) wraps calls in `PausableExporter`, which — if present — would provide an independent halt enforcement path for the underlying XCM delivery and reduce the practical severity of this gap. This could not be confirmed from the files reviewed.

		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
