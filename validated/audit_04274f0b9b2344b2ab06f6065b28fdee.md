## Analog Vulnerability Found

### Title
Webhook signature verification is keyed by the payload's claimed organization, not the repository the event actually writes to, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This is a structural analog of the DYAD "bounded Kerosene" bug: the report shows a mismatch between what is *authorized* (a supposedly higher-value, restricted asset) and what is *actually acted upon* by the seizing logic. In Shipit, the analogous trust binding is: `organization that authenticated the webhook == repository whose Stack is looked up and mutated by the handler`. The webhooks controller breaks this equality because the HMAC signature is verified against a secret selected using one attacker-controlled field (`repository.owner.login` / `organization.login`), while downstream event handlers act on a separate, independently-controlled field of the very same JSON body (the repository identity used to resolve a `Stack`).

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify against purely from fields inside the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` returns `params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')`. Shipit supports hosting multiple GitHub organizations from a single instance, each with its own independently configured `webhook_secret`: [3](#0-2) 

Because the request body is raw, attacker-supplied JSON (not something GitHub itself vouches for beyond the HMAC), an actor who legitimately knows the `webhook_secret` for **one** trusted organization (e.g., their own org, onboarded onto the same multi-tenant Shipit instance) can craft a payload where:
- `repository.owner.login` / `organization.login` == their own, legitimate org (so `verify_signature` picks the correct secret and the HMAC they compute over the full raw body validates), while
- the `repository.full_name` (or other repo-identifying field) used later by the event handler (e.g., `Shipit::Webhooks::Handlers::PushHandler`, dispatched via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) is set to a **different, victim organization's repository** also hosted on that Shipit instance. [4](#0-3) 

Nothing in `verify_signature` or in the handler dispatch cross-checks that the organization whose secret validated the signature is the same organization that owns the repository the handler subsequently loads and mutates (Stack lookup, `GithubSyncJob` enqueue, commit status writes, etc., per the handler directory).



This is the same class of bug as the DYAD report: the entity that is authenticated/valued (the organization whose secret matched) is not the entity that is ultimately acted upon (the repository/Stack that gets written to).

### Impact Explanation
An attacker who legitimately controls one organization onboarded to a shared/multi-tenant Shipit instance can forge webhook events attributed to a different organization's repository. Depending on which handler fires, this can trigger unauthorized `GithubSyncJob` runs, spurious/forged commit statuses, membership/team mutations, or merge-queue state changes against a repository/Stack the attacker does not own — a cross-repository write achieved purely by crafting a JSON body, which meets the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Requires only that Shipit be configured for multiple GitHub organizations (a documented, supported configuration - see "Using Multiple Github Applications") and that the attacker be a legitimate keyholder for one of those organizations' webhook secrets. No GitHub App private key, `ApiClient` token, Shipit session, or org membership on the victim side is required — the attacker only needs their own org's `webhook_secret`, which is by design known outside of Shipit (it's configured when the org's admin sets up their GitHub App). This satisfies the "unprivileged relative to the victim" requirement.

### Recommendation
`verify_signature` (or the handlers downstream) should cross-check that the organization whose secret validated the payload is the same organization referenced by `repository.owner.login`/`repository.full_name` actually used to resolve the `Stack`/`Repository` record, rejecting the event if they diverge, rather than trusting two independently-settable JSON fields to agree.

### Proof of Concept
1. Shipit instance is configured with two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `config/secrets.yml`, as documented for multi-org setups).
2. Attacker, who legitimately knows `attacker-org`'s `webhook_secret`, crafts a `push` event JSON body:
   - `organization.login` = `attacker-org`
   - `repository.owner.login` = `attacker-org`
   - `repository.full_name` = `victim-org/victim-repo`
3. Attacker computes `X-Hub-Signature` as `sha1=HMAC(attacker-org's webhook_secret, raw_body)`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature.
5. `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` runs the push handler using `repository.full_name = "victim-org/victim-repo"`, causing Shipit to act on the victim's Stack (e.g., enqueue `GithubSyncJob`) despite the request never having been authorized by `victim-org`.

*(Note: I was not able to retrieve the full source of `app/models/shipit/webhooks/handlers/push_handler.rb` within the available tool budget to cite the exact line where the repository/Stack lookup occurs; this should be verified directly when reviewing the fix, but the controller-level signature/repository binding gap described above is confirmed from `webhooks_controller.rb`.)*
