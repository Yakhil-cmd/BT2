### Title
Missing Zero-Address Guard on `CLPoolAddr` Causes Permanent Loss of CL Staking Rewards — (`kaiax/reward/impl/getter.go`)

---

### Summary

The Kaia reward module distributes staking rewards to consensus-liquidity (CL) pool addresses read directly from the CLRegistry contract. Unlike the KIF/KEF/KPF fund addresses — which have explicit zero-address guards that redirect funds to the proposer — the `CLPoolAddr` field of `CLStakingInfo` is used without any zero-address check. If `CLPoolAddr` is `address(0)` (due to a misconfigured or malicious CLRegistry entry), the CL portion of every block's staking reward is permanently sent to `address(0)` and burned.

---

### Finding Description

In `kaiax/reward/impl/getter.go`, four functions distribute rewards to `cn.CLStakingInfo.CLPoolAddr` without validating it is non-zero:

**`assignStakingRewards`** (Kore/Prague staker path): [1](#0-0) 

**`assignStakingRewardsFlex`** (Flex/Osaka staker path): [2](#0-1) 

**`specWithProposerAndFunds`** (proposer reward path, Prague): [3](#0-2) 

**`specWithProposerAndFundsFlex`** (proposer reward path, Flex): [4](#0-3) 

By contrast, the KIF, KEF, and KPF fund addresses all have explicit zero-address guards that redirect their portion to the proposer when empty: [5](#0-4) 

The `CLPoolAddr` is populated directly from the CLRegistry contract's `clPools` array with no zero-address validation: [6](#0-5) 

The `Validate()` function on `RewardSpec` only checks for negative amounts, not for zero-address recipients: [7](#0-6) 

`FinalizeState` then calls `state.AddBalance(addr, amount)` for every entry in `spec.Rewards` — including any entry keyed to `address(0)`: [8](#0-7) 

`state.AddBalance` accepts `address(0)` without error: [9](#0-8) 

---

### Impact Explanation

Every block in which a validator has `CLPoolAddr == address(0)` in the CLRegistry, the CL-proportional share of that validator's staking reward (computed by `cn.Split(reward)`) is credited to `address(0)` and permanently burned. The CN reward address receives only the CN-proportional share. The burned amount is proportional to `CLStakingAmount / (StakingAmount + CLStakingAmount)` of the validator's total staking reward. This is an unauthorized burn of KAIA block rewards every block for the lifetime of the misconfigured entry.

---

### Likelihood Explanation

The `CLPoolAddr` is read from the CLRegistry system contract without any zero-address guard in the staking getter: [10](#0-9) 

The comment explicitly notes `kpfAddr (spareAddr) can be empty even after the AddressBook is activated`, acknowledging that on-chain addresses can be zero. The CLRegistry mock used in tests does not validate against `address(0)`: [11](#0-10) 

If the production CLRegistry contract does not enforce `CLPoolAddr != address(0)` at registration time, any validator that registers with a zero pool address (deliberately or by misconfiguration) triggers the loss every block.

---

### Recommendation

Add a zero-address guard for `CLPoolAddr` in all four reward-distribution functions, mirroring the existing pattern for KIF/KEF/KPF. When `CLPoolAddr` is empty, the CL portion should fall back to the validator's `RewardAddr` (analogous to how fund portions fall back to the proposer):

```go
// In assignStakingRewards / assignStakingRewardsFlex
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount
    if !common.EmptyAddress(cn.CLStakingInfo.CLPoolAddr) {
        alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
    } else {
        alloc[cn.RewardAddr].Add(alloc[cn.RewardAddr], clAmount)
    }
}
```

Apply the same pattern in `specWithProposerAndFunds` and `specWithProposerAndFundsFlex`. Additionally, add a zero-address check in `parseCallResult` to reject or skip CLStakingInfo entries with a zero `CLPoolAddr`.

---

### Proof of Concept

1. A validator registers in the CLRegistry with `CLPoolAddr = address(0)` and `CLStakingAmount = X`.
2. `parseCallResult` stores this as a `CLStakingInfo` with `CLPoolAddr = address(0)`.
3. `consolidateNodes()` attaches this `CLStakingInfo` to the validator's `consolidatedNode`.
4. At block finalization, `assignStakingRewards` (Prague path) computes `cn.Split(reward)` → `(cnAmount, clAmount)`.
5. `alloc[address(0)] = clAmount` is written into the reward map.
6. `FinalizeState` calls `state.AddBalance(address(0), clAmount)`, permanently burning `clAmount` KAIA every block.
7. The `Validate()` call does not catch this because it only checks for negative amounts.

The `clAmount` burned per block equals `CLStakingAmount / (StakingAmount + CLStakingAmount) × validatorStakingReward`. At mainnet scale with a validator staking 5M KAIA and a CL amount of 5M KAIA, this is 50% of that validator's staking reward burned every block indefinitely.
