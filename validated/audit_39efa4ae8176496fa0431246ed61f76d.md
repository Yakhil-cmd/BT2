### Title
Asset definer can revoke/replace attestor list of a `spender_attested` asset at any time, freezing holders who already qualified - (File: [validation.js](https://github.com/Jortegata/ocore--020/blob/main/validation.js))

### Summary
The reported bug is about `SAM::setGoldenEggFee()` letting a privileged party (edition owner) change a reward-affecting parameter at any time, even after users have already earned/relied on it, stripping a winner post-hoc. The analogous root cause in `ocore` is that `validateAttestorListUpdate()` lets an asset's definer replace the `spender_attested` attestor list for an already-issued, already-circulating asset at any time, with no restriction tied to the asset's lifecycle or to addresses that have already been attested and are holding/transacting the asset.

### Finding Description
`validateAttestorListUpdate()` allows the asset definer to submit an `asset_attestors` message that overwrites the list of attestor addresses for a `spender_attested` asset, with the only checks being that the message is single-authored, well-formed, that the asset requires attestors, and that the sender is the definer: [1](#0-0) 

There is no timing/lifecycle gate analogous to `onlyBeforeSAMPhase` — the definer can call this repeatedly, at any main-chain-index, long after the asset has been issued and transferred to holders who relied on being (or becoming) attested.

The attestor list is consumed at spend/transfer-validation time via `filterAttestedAddresses`, which is checked against outputs using the attestor-list unit that is stable and confirmed as of `last_ball_mci` at validation time — i.e., the *current* list, not the list that applied when the recipient originally became attested: [2](#0-1) [3](#0-2) 

Asset attestor state is also resolved to "the latest list of attestors" relative to `last_ball_mci` when loading the asset: [4](#0-3) 

Because the definer's `asset_attestors` update is unrestricted in time and unconditioned on any prior attestation commitments, the definer can:
1. Attest an address (directly or via an attestor they control) to induce a user to accept/hold the `spender_attested` asset, and
2. Later submit a new `asset_attestors` message that drops that address (or all addresses) from the list, making previously-valid holders permanently unable to satisfy `filterAttestedAddresses` on transfer/output validation, freezing their asset balance.

This mirrors the Golden-Egg-Fee root cause exactly: a privileged, unrestricted setter can retroactively strip value/eligibility that a legitimate, unprivileged holder had already relied upon, with the review-recommended fix pattern being to lock the setter once the relevant "phase" (asset lifecycle here) has concluded or once the affected party has already benefited.

### Impact Explanation
An asset definer griefing or rug-pulling holders of a `spender_attested` asset by revoking attestor status after issuance/transfer constitutes fund freezing (holder cannot spend/transfer their genuine, already-received asset balance because their address can no longer be attested per the current attestor list) — this is a concrete, protocol-level "AA/asset fund freezing" impact class, reachable by any unprivileged holder who legitimately received such an asset.

### Likelihood Explanation
The `asset_attestors` message is a normal, unauthenticated-beyond-definer-signature message type that any asset definer (an ordinary account, not requiring special network privileges) can post at any time after asset creation, with no cooldown, no restriction to "before mint/issue concluded," and no protection for addresses/holders who already benefited from a prior attestor list. This makes the scenario trivially reachable by a malicious or careless asset issuer.

### Recommendation
Apply the same fix pattern used for `setGoldenEggFee`: restrict `asset_attestors` updates to a well-defined phase of the asset's lifecycle (e.g., disallow changes after the asset has had any transfers to non-definer addresses, or require that removed attestors/addresses retain a grace period during which previously-attested outputs remain spendable), so that a definer cannot retroactively invalidate attestation status that other addresses already relied on to hold/receive the asset.

### Proof of Concept
1. Definer creates asset A with `spender_attested: true` and posts an initial `asset_attestors` list containing attestor `X`.
2. Attestor `X` attests address `H` (holder). Definer issues/sends asset `A` to `H`, whose output passes `filterAttestedAddresses` because `H` is attested.
3. After `H` accumulates a balance of asset `A`, definer posts a new `asset_attestors` message (still passes `validateAttestorListUpdate`, no lifecycle restriction) that removes attestor `X` or lists a different set of attestors that does not attest `H`.
4. `H` attempts to transfer/spend its previously valid balance of asset `A`; `validatePaymentInputsAndOutputs` → `filterAttestedAddresses` now fails for `H`'s output address because the "latest" attestor list (per current `last_ball_mci`) no longer attests `H`, per [2](#0-1) , freezing `H`'s funds despite having done nothing wrong.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
