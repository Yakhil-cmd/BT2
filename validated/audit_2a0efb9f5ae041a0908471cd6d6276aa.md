### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but repository writes are keyed off the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization used to compute the HMAC secret from `repository.owner.login` (or `organization.login`) in the raw, not-yet-verified JSON body, and calls `verify_webhook_signature` for that organization. Separately, every event handler resolves the `Repository`/`Stack` that will actually be mutated using `repository.full_name`, a distinct field in the same attacker-controlled payload. These two fields are never cross-checked against each other. Combined with the fact that `verify_webhook_signature` trivially returns `true` when the resolved organization has no `webhook_secret` configured, an attacker can pick an org with no secret to satisfy verification while targeting a completely different, "protected" organization's repository for the actual write.

### Finding Description
- `WebhooksController#verify_signature` picks the organization purely from payload content: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 

- `GithubApp#verify_webhook_signature` short-circuits to `true` whenever the resolved app has no `webhook_secret` configured - i.e. any payload is accepted unauthenticated for that organization. [3](#0-2) 

- Once the controller passes verification, `WebhooksController#create` dispatches the *entire raw payload* (not scoped to the "verified" organization) to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [4](#0-3) 

- Every handler (`PushHandler`, `OpenedHandler`, `ClosedHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the repository to mutate via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` - a field completely independent from `repository.owner.login` used for signature selection. [5](#0-4) [6](#0-5) 

This is structurally the same defect class as the C4 finding: the binding used for the trust decision (`organization` used to authenticate = `repository.owner.login`) is not the same binding used for the effectful operation (`repository` actually written = `repository.full_name`). Because both fields live in the same attacker-supplied raw JSON body (the webhook request), an attacker forging a raw POST can decouple them: set `repository.owner.login` to an organization Shipit knows about but has *not* configured a `webhook_secret` for (making `verify_webhook_signature` return `true` unconditionally), while setting `repository.full_name` to `protected-org/target-repo` - a repository belonging to an organization that *does* have HMAC protection configured.

### Impact Explanation
If a Shipit instance is configured with multiple GitHub organizations/Apps (a supported configuration, since `Shipit.github(organization:)` is looked up per-organization) and at least one configured organization lacks a `webhook_secret`, an unprivileged external attacker can forge webhook requests that satisfy signature verification for the secret-less org while writing state (triggering deploys via `sync_github`, creating/archiving review stacks, posting commit statuses, refreshing check runs) against a different organization's protected repository/stack, without ever knowing that organization's `webhook_secret`. This is effectively an authentication bypass leading to unauthorized state changes (e.g., forcing `GithubSyncJob`/`sync_github` on an arbitrary tracked stack, or archiving/unarchiving review stacks) on a repository the attacker was never authorized to act on.

### Likelihood Explanation
Requires the deployment to have at least one configured GitHub organization/App with `webhook_secret` blank/nil (which the shipped test/dummy config demonstrates is a normal, unremarkable configuration state - `webhook_secret: null`), and the target instance to also track a second, differently-secured organization's repository. No credentials, GitHub App keys, or session access are required - only the ability to send an HTTP POST to the public `/webhooks` endpoint with a crafted JSON body, which is exactly the class of unprivileged attacker this analysis targets.

### Recommendation
Bind signature verification to the same repository identity used for the write: derive the organization used to select the webhook secret from `repository.full_name`'s owner segment (or equivalently validate that `repository.owner.login` and the owner segment of `repository.full_name` match) before dispatching to handlers, and reject payloads where they diverge. Additionally, treat a missing `webhook_secret` as "verification not configured -> reject" rather than "verification always passes," or require every organization that can be targeted by handlers to have a non-blank `webhook_secret`.

### Proof of Concept
1. Shipit is configured with two organizations: `org-a` (no `webhook_secret` set) and `org-b` (has `webhook_secret` configured and tracks a repository `org-b/prod-stack`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/prod-stack"
  }
}
```
3. `WebhooksController#verify_signature` computes `repository_owner` = `"org-a"`, calls `Shipit.github(organization: "org-a").verify_webhook_signature(...)`, which returns `true` immediately since `org-a` has no `webhook_secret` (`app/lib/shipit/github_app.rb:76-77`), regardless of the (possibly absent/garbage) `X-Hub-Signature` header.
4. Request passes verification and reaches `create`, which dispatches to `PushHandler`. `PushHandler#stacks` resolves via `Handler#repository_name` = `payload.dig('repository','full_name')` = `"org-b/prod-stack"`, locating the real `org-b` repository/stack and triggering `stack.sync_github(expected_head_sha: "deadbeef")` on it - all without ever satisfying `org-b`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
