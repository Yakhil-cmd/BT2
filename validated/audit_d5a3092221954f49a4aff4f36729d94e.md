### Title
Unchecked division in `token_price_x32` causes a divide-by-zero panic that can permanently DoS pool swaps - (File: `programs/cp-swap/src/states/pool.rs`)

### Summary
`PoolState::token_price_x32` performs raw (non-checked) `u128` division on token vault amounts derived from `vault_amount_without_fee`, with no guard against a zero denominator. This is analogous to CVE-2017-8842, where `bufRead::get()` in `libzpaq.h` performed an unguarded division that could be driven to zero by crafted/attacker-influenced input, crashing the program. Here, an attacker-influenced vault state (reachable through ordinary `swap_base_input`/`swap_base_output` calls) can drive one of the two vault-minus-fees terms to zero, causing the same class of divide-by-zero panic in Rust, aborting the enclosing instruction.

### Finding Description
`vault_amount_without_fee` computes the "real" (fee-excluded) balances of each vault by subtracting accumulated protocol/fund/creator fees from the raw SPL token account balance: [1](#0-0) 

`token_price_x32` then divides these two fee-excluded balances by each other without any zero check, unlike every other arithmetic helper in the curve/fee modules (`Fees::trading_fee`, `ceil_div`, `floor_div`, `checked_ceil_div`, `ConstantProductCurve::swap_base_input_without_fees`, etc.), which either guard against a zero denominator or return `Option`/`Result`: [2](#0-1) 

Compare this to the safe patterns used everywhere else in the codebase, e.g. `Fees::floor_div`/`ceil_div` explicitly check `fee_denominator == 0`: [3](#0-2) 
and `ConstantProductCurve::swap_base_input_without_fees` uses `checked_div`/`.unwrap()` on results derived from arithmetic that is bounds-checked earlier in the swap flow: [4](#0-3) 

`token_price_x32` is invoked from the oracle-update path in both `swap_base_input.rs` and `swap_base_output.rs`, which are reachable by any unprivileged swapper submitting a single transaction with attacker-chosen swap amounts. If a swap (or a sequence of swaps by any unprivileged trader) drives one vault's raw token balance down to exactly equal the sum of that token's accrued `protocol_fees`, `fund_fees`, and `creator_fees` (i.e., `vault_amount_without_fee` returns `0` for that side), then the subsequent division `token_1_amount * Q32 / token_0_amount` (or the symmetric case) divides by zero. In Rust, integer division by zero always panics at runtime regardless of build profile, aborting the instruction.

### Impact Explanation
Because the fee-excluded vault amount is recomputed from on-chain state (raw vault balance minus persisted fee ledger) on every call rather than being clamped away from zero, an attacker can attempt to force this exact-equality edge case through crafted swap amounts. Once the vault balance for one token exactly equals its accrued fees, every subsequent swap (any caller) that reaches the oracle-update call will panic and revert, effectively denial-of-servicing that pool's swap instruction until the condition changes (e.g., fees are drained or new deposits shift the balance) — a low-liquidity or thinly-traded pool could become effectively unusable, which is a form of impaired/frozen access to pool functionality for all its users and LPs.

### Likelihood Explanation
Reaching exact equality between a vault's raw balance and its accrued-fee total requires precise value engineering, which is harder than a simple "empty pool" DoS, since it depends on rounding behavior across `Fees::trading_fee`/`protocol_fee`/`fund_fee`/`creator_fee` (all integer ceil/floor divisions) accumulating deterministically. This makes the likelihood moderate rather than trivial — feasible for a determined attacker on a low-liquidity, low-decimal-precision pool who can perform many small swaps to nudge fee accumulation and vault balance into exact alignment, but not a one-shot trivial trigger.

### Recommendation
Guard `token_price_x32` (and any other unchecked division added to `PoolState`) with an explicit zero check on the denominator, returning a domain error (e.g., `ErrorCode::InsufficientVault` or a new `ErrorCode::ZeroTradingTokens`-style error) instead of allowing a raw division, consistent with the `checked_div`/`Option`-returning patterns already used throughout `curve/fees.rs` and `curve/constant_product.rs`.

### Proof of Concept
Conceptual PoC (exact numeric path not verified due to indexing limits on the full `swap_base_input.rs`/`swap_base_output.rs` call sites, which reference `token_price_x32` once each but were not fully read in this pass):
1. Attacker repeatedly calls `swap_base_input`/`swap_base_output` on a newly created, low-liquidity pool, choosing input amounts such that accumulated `protocol_fees_token_0`/`fund_fees_token_0`/`creator_fees_token_0` sum equals the raw `token_0_vault.amount` exactly after a swap.
2. The swap instruction's post-swap oracle update calls `pool_state.token_price_x32(vault_0.amount, vault_1.amount)`.
3. `vault_amount_without_fee` returns `token_0_amount == 0`.
4. `token_1_amount as u128 * Q32 as u128 / token_0_amount as u128` panics with a divide-by-zero, aborting the transaction and any following swap that hits the same state until the balance/fee relationship changes. [2](#0-1)

fn ceil_div(token_amount: u128, fee_numerator: u128, fee_denominator: u128) -> Option<u128> {
    if fee_denominator == 0 {
        return None;
    }
    token_amount
        .checked_mul(u128::from(fee_numerator))?
        .checked_add(fee_denominator)?
        .checked_sub(1)?
        .checked_div(fee_denominator)
}

/// Helper function for calculating swap fee
pub fn floor_div(token_amount: u128, fee_numerator: u128, fee_denominator: u128) -> Option<u128> {
    if fee_denominator == 0 {
        return None;
    }
    token_amount
        .checked_mul(fee_numerator)?
        .checked_div(fee_denominator)
}
