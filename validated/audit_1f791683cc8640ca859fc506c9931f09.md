### Title
Opaque swap routes can attach unrelated user token transfers to the caller’s authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy entrypoints accept opaque `swap` bytes and execute route-selected contracts through the configured router. A malicious route hop can invoke `token.transfer(victim, attacker, amount)` for an unrelated wallet token while still returning a valid swap output; Soroban records that transfer as a child of the victim’s `swap_collateral` authorization and executes it if the victim signs the generated authorization tree. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`StrategySwap` is an opaque `Bytes` value supplied by the caller rather than a structured, controller-validated route. [4](#0-3) 

`swap_collateral` authenticates `caller`, checks that the caller owns or controls the account, withdraws the selected collateral into controller custody, and forwards the opaque route to `swap_tokens`. [5](#0-4) [6](#0-5) 

`swap_tokens` authorizes only the exact controller-to-router input-token transfer, but then invokes `router.execute_strategy(&controller, &amount_in, swap)` inside the caller’s authorized controller invocation. [7](#0-6) 

After the router call, the controller checks only that the declared input was not overspent and that the declared output-token balance increased; it has no mechanism to reject unrelated nested calls performed by route-selected contracts. [8](#0-7) 

The test harness demonstrates a route containing an attacker-controlled `hop_pool`; the router invokes that route-selected contract, whose `swap` function transfers an unrelated token from the victim to the attacker. [9](#0-8) [2](#0-1) 

### Impact Explanation
The attacker can steal unrelated tokens held in the victim’s wallet while the requested collateral swap remains economically valid. [10](#0-9) 

The demonstrated scenario transfers the victim’s entire `77_770_000_000` unit balance of a token that the lending protocol never listed, while the controller still receives the expected ETH output and credits the victim’s collateral position. [11](#0-10) [12](#0-11) 

This is direct theft of user funds rather than route-quality loss: the stolen asset is outside the declared `token_in` and `token_out`, and neither the input spend check nor the positive output check bounds it. [8](#0-7) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious hop contract, construct the route payload, and cause a wallet or integration to request the victim’s authorization for `swap_collateral`. [13](#0-12) [14](#0-13) 

The exploit requires the victim to sign an authorization tree containing the unrelated token transfer; without that child authorization, the transfer fails and the transaction rolls back. [15](#0-14) 

If simulation records the malicious transfer and the victim signs the resulting tree, execution succeeds and moves the unrelated token to the attacker. [16](#0-15) 

The same exposure applies to the other controller strategies that pass opaque `swap` or `convert_swap` payloads into `swap_tokens`, including `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [17](#0-16) [18](#0-17) [19](#0-18) 

### Recommendation
Do not pass arbitrary route-selected contract execution under the account owner’s authorization. Replace opaque route bytes with a structured route format whose venues are constrained to governance-approved, immutable venue adapters, and reject arbitrary hop addresses or function names.

Keep the exact controller-input authorization, but additionally require client and wallet integrations to display every authorization child and reject a strategy authorization containing any token transfer other than the expected controller-input transfer. Authorization-tree inspection is necessary defense-in-depth because the controller’s balance checks cannot observe unrelated transfers authorized by the caller.

### Proof of Concept
The repository’s harness demonstrates the complete pattern: [20](#0-19) 

```rust
// Attacker-controlled hop invoked by the route.
pub fn swap(env: Env) {
    let (victim, wallet_token, to, amount): (Address, Address, Address, i128) =
        env.storage().instance().get(&symbol_short!("PLAN")).unwrap();

    token::Client::new(&env, &wallet_token)
        .transfer(&victim, &to, &amount);
}
```

1. The victim supplies USDC and owns a lending account. [21](#0-20) 
2. The attacker deploys `RogueHopPool` configured with `(victim, wallet_token, attacker, amount)`. [22](#0-21) 
3. The attacker encodes a route naming that hop while still declaring a fair USDC-to-ETH output. [13](#0-12) 
4. The victim is induced to invoke:

```text
Controller::swap_collateral(
    caller = victim,
    account_id = victim_account,
    current = USDC HubAssetKey,
    amount = 50_000_000_000,
    new = ETH HubAssetKey,
    swap = malicious_route_xdr,
)
```

5. Simulation records `token.transfer(victim, attacker, WALLET_BALANCE)` beneath the victim’s `swap_collateral` authorization. [23](#0-22) 
6. Signing the generated tree transfers the full unrelated wallet-token balance to the attacker while the requested collateral swap completes. [16](#0-15)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
