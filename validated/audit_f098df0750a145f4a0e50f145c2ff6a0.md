### Title
Webhook signature verification is keyed to an attacker-controlled `repository.owner.login` field that is decoupled from the `repository.full_name` actually used to route the event, allowing forged pushes against any tracked stack whenever any configured GitHub organization has a blank `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GithubApp` (and therefore which `webhook_secret`) to verify an inbound webhook against using `repository_owner`, a value read directly out of the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). The corresponding handlers (e.g. the push handler that later enqueues `GithubSyncJob`) locate the target `Stack`/`Repository` using the full repository name from the same payload. Nothing forces the organization used for signature selection to match the owner encoded in the repository actually processed. Combined with `GithubApp#verify_webhook_signature` unconditionally returning `true` when an organization's `webhook_secret` is blank (a state the project's own setup docs treat as optional/valid), an attacker can pick any configured-but-secretless organization to satisfy signature verification while still causing the handler to act on a *different*, fully-secured organization's repository/stack.

### Finding Description
`verify_signature` picks the app config purely from the payload: [1](#0-0) [2](#0-1) 

The signature check itself, in `GithubApp#verify_webhook_signature`, is a no-op when no secret is configured for that organization: [3](#0-2) 

The project's own setup documentation and sample secrets file treat `webhook_secret` as an optional per-organization setting, i.e. leaving it blank/nil is a documented, supported configuration state rather than a misconfiguration outside the engine's control: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes, the raw JSON `params` (fully attacker-controlled since nothing else validated it) is dispatched to the registered handlers for the event, and the push handling path resolves and acts on a stack keyed off the repository's full name embedded in that same payload, as demonstrated by the existing push test that asserts a `GithubSyncJob` is enqueued for the stack matching the payload's repository: [6](#0-5) 

Because `repository_owner` (used to pick the signing organization) and the repository the handler ultimately targets are read from independently-controllable JSON fields in the same attacker-supplied body, an attacker can set `repository.owner.login` (or `organization.login`) to any organization configured on the instance that happens to have a blank `webhook_secret`, causing signature verification to trivially pass, while setting `repository.full_name`/other repository identifying fields to point at a completely different, "properly secured" organization's tracked repository. The handler will process the forged event as if it legitimately originated from GitHub for that other repository.

This is the direct analog of the reported bug class: a value used to satisfy an authorization/verification check (`repository_owner` → selected `webhook_secret`) is not the same value bound by that check to the value later acted upon (`repository.full_name` → actual `Stack`/`Repository` synced), breaking the equality that should hold between "organization authenticated" and "repository written."

### Impact Explanation
A successful forged push webhook lets an unauthenticated attacker cause `GithubSyncJob` to run for an arbitrary tracked stack with an attacker-chosen `expected_head_sha`, which is the trigger mechanism continuous delivery relies on. This can result in an unauthorized deploy being triggered for a stack the attacker has no legitimate access to, and can also spoof other events (status, check_suite, pull_request, membership) against arbitrary organizations/stacks tracked by the same Shipit instance, once any single configured organization has no `webhook_secret`. This satisfies the Critical criterion of "an unauthorized deploy" via cross-repository/cross-organization event forgery.

### Likelihood Explanation
Exploitability depends entirely on the deployment having at least one configured GitHub organization without a `webhook_secret` set — a state the project's own documentation and sample config explicitly allow/describe as optional rather than disallowed. Any multi-organization Shipit deployment where even one lower-priority/test organization is configured without a webhook secret exposes every other organization's repositories to forged webhooks, since the webhook endpoint is public and unauthenticated by design prior to signature verification.

### Recommendation
Bind the repository/stack the handler acts on to the same organization value that was cryptographically verified, or refuse verification entirely (rather than defaulting to `true`) when a `webhook_secret` is not configured, and independently confirm that `repository.full_name`'s owner segment matches `repository_owner`/the organization used for signature selection before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `secure-org` (has `webhook_secret` set) and `blank-org` (no `webhook_secret`, per the documented optional setting).
2. Ensure a `Stack` tracking `secure-org/critical-repo` exists.
3. POST to `/webhooks` with header `X-Github-Event: push` and a JSON body where:
   - `repository.owner.login` = `"blank-org"` (or `organization.login` = `"blank-org"`)
   - `repository.full_name` = `"secure-org/critical-repo"`
   - `after` = attacker-chosen SHA
4. `verify_signature` resolves `Shipit.github(organization: 'blank-org')`, whose `verify_webhook_signature` returns `true` unconditionally because `blank-org` has no `webhook_secret` (`lib/shipit/github_app.rb:76-83`), regardless of the `X-Hub-Signature` header supplied (or omitted).
5. The push handler processes the payload against `secure-org/critical-repo`'s `Stack`, enqueuing `GithubSyncJob` with the attacker-supplied SHA, as in `test/controllers/webhooks_controller_test.rb:23-32`, without ever needing `secure-org`'s real webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
