### Title
Silent absorption of unmatched/under-threshold trigger payments into AA balance skews on-chain reserve accounting (donation attack) - (File: aa_composer.js, exploitable via AAs like test/samples/uniswap_like_market_maker.oscript)

### Summary
Ocore's AA engine tracks each AA's asset/byte balances in `aa_balances`, updated unconditionally in `updateInitialAABalances()` before any `if`-case of the AA is evaluated [1](#0-0) . When a trigger's outputs do not satisfy the `if` condition of any case (or the resulting `messages` list is empty), the AA does not bounce the funds back — it silently keeps them and posts an "empty response", explicitly documented in the code as "eat the received coins and send no response, state changes are still performed" [2](#0-1) .

This is functionally identical to the reported Solidity bug: an attacker can send a small amount of an asset/bytes to a contract/AA to inflate a balance figure that downstream logic assumes represents only "legitimate" tracked funds, corrupting a ratio/accounting calculation, without the AA's own internal state variables being updated to reflect the deposit.

### Finding Description
Many AAs (e.g. the shipped sample `test/samples/uniswap_like_market_maker.oscript`) compute pool ratios directly from the AA's on-chain balance rather than from an internally maintained reserve variable:

```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
$current_ratio = $asset_balance / $bytes_balance;
``` [3](#0-2) 

`balance[...]` is populated from the `aa_balances` table, which is updated as soon as the trigger's outputs are received (`updateInitialAABalances`), independent of whether any `if` case for that trigger actually matches [4](#0-3) . Every case in the market-maker AA guards on thresholds such as `trigger.output[[asset=base]] > 1e5` or `trigger.output[[asset=$asset]] > 0` [5](#0-4) , [6](#0-5) , [7](#0-6) .

If an attacker sends bytes (or the pool asset) in an amount/format that fails to satisfy any case's `if` condition (e.g., under the `1e5` threshold, or combined with data that matches nothing), `aa_composer.js` finds no active messages, logs `'no messages after filtering'`, and calls `handleSuccessfulEmptyResponseUnit(null)` — the funds are absorbed into the AA's balance and no bounce, no state update, and no ratio-changing case is executed [2](#0-1) . The `aa_balances` entry for the AA permanently reflects the extra donated amount, but the pool's internal accounting variable (`var['mm_asset_outstanding']`) is untouched.

Every subsequent legitimate `balance[$asset]` / `balance[base]` read (invest, divest, or swap cases) will now compute a permanently skewed `$current_ratio` / `$p` (the constant product), exactly mirroring the "increasing or decreasing seniorVaultWethRewards" issue in the external report where a raw balance read used for accounting could be manipulated by an unsolicited transfer.

### Impact Explanation
Because AA logic frequently reads `balance[asset]` (a directly attacker-influenceable, unconditionally-updated ledger value) instead of an isolated internally tracked reserve variable, an unprivileged trigger sender can:
- Distort a market-maker/AMM-style AA's price ratio, causing later investors to receive an incorrect number of pool shares, or later swappers to receive incorrect output amounts — a direct funds-loss/fund-freezing vector for legitimate users of any AA following this common on-chain-balance-based accounting pattern.
- Repeat the donation indefinitely at low cost (any bounce-fee-insufficient amount is absorbed rather than bounced), since the check that prevents a normal bounce (`(trigger.outputs.base||0) < bounce_fees.base`) only stops the explicit bounce-refund path but does not prevent balance inflation; funds are simply kept without any state update.
This is a Medium-severity issue: it does not break DAG consensus/stability, but it can cause an AA (fund-holding logic) to lose accounting integrity and cause real fund loss/incorrect distribution for third parties interacting with the AA, matching the accepted "AA fund loss or freezing" impact category.

### Likelihood Explanation
Any address can post a unit whose payment output goes to a target AA with an amount/data combination that fails every `if` case (e.g., sending less than a documented minimum threshold, or sending an asset the AA doesn't expect in that trigger). No special privileges, keys, or timing windows are required — a single low-value unit triggers the absorption. This pattern is present by design in the ocore AA sample library and is a common construction encouraged by the engine's documentation/examples, making it highly likely developers replicate the vulnerable `balance[...]`-based accounting pattern in production AAs.

### Recommendation
- AAs that need "net of my own deposit" reserve accounting should maintain reserves in explicit state variables (`var['reserve_base']`, `var['reserve_asset']`) updated only inside matching cases, instead of relying on `balance[asset]`, which reflects all funds ever unconditionally absorbed into the AA (including uninvited/unmatched deposits).
- Alternatively, `aa_composer.js` could bounce trigger outputs that don't match any case whenever the value exceeds `bounce_fees` (rather than silently keeping them when `messages.length === 0`), removing the free "donation" primitive for well-funded triggers, though this would be an ocore-engine-level behavior change requiring careful backward-compatibility review since `'no messages after filtering'` is explicitly treated as a valid/deliberate "silently accept coins" pattern in other samples (e.g. `test/samples/a_bank_without_percent.oscript` catches all triggers via `if: "{!trigger.data.withdraw}"` to intentionally record deposits) [8](#0-7) .
- Document prominently (AA developer guide / oscript reference) that `balance[asset]` includes any and all funds sent to the AA address, matched or unmatched by any case, and that pool/ratio-based AAs must not use it directly for share/price computation without excluding donation-style deposits via internal reserve tracking.

### Proof of Concept
1. Deploy an AA identical to `test/samples/uniswap_like_market_maker.oscript` (or any AA using the same `balance[asset]`-based ratio pattern).
2. Attacker sends a plain payment of, say, 50,000 bytes (below the `1e5` threshold required by the "invest" and "exchange bytes to asset" cases) to the AA address, with no `$asset` output and no matching `trigger.data`.
3. In `aa_composer.js`, `updateInitialAABalances` adds the 50,000 bytes to `aa_balances` for the AA address before any case is evaluated [9](#0-8) .
4. `evaluateAA` finds no case whose `if` is true (all guard conditions require `>1e5` or an asset output), so `messages` filters to empty and the engine calls `handleSuccessfulEmptyResponseUnit(null)`, logging `'no messages after filtering'` [2](#0-1) ; the 50,000 bytes remain in the AA's `balance[base]` permanently.
5. A subsequent legitimate investor's `$bytes_balance = balance[base] - trigger.output[[asset=base]]` is now 50,000 bytes higher than the AA's true tracked reserves (`var['mm_asset_outstanding']` implied reserve), skewing `$current_ratio` and `$issue_amount` for that and all future investors/divestors — extractable value/loss for legitimate LPs.

Note: I was unable to execute this scenario against a live ocore test harness in this session; the analysis is based on static code reading of `aa_composer.js` and the bundled sample AA `uniswap_like_market_maker.oscript`. Confirming the exact numeric skew and any offsetting mitigations elsewhere in the codebase would require running the existing AA test suite (`test/aa.test.js`, `test/aa_composer.test.js`) with a crafted low-value trigger, which a Devin session with terminal access could perform.
