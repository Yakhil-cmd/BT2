### Title
Cross-organization webhook signature confusion enables spoofed commit statuses and forged deploy triggers - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to use for HMAC verification based on `repository_owner`, a value read directly from the **unverified** JSON body, before the signature has been checked [1](#0-0) [2](#0-1) . In a multi-organization deployment (`Shipit.github(organization:)`, documented in `docs/setup.md`), every organization configures and knows its own `webhook_secret` [3](#0-2) . Nothing ties that `webhook_secret`/`repository_owner` pair to the `repository.full_name` (or `sha`) the downstream handlers actually act on.

### Finding Description
The equality that should hold is:
`organization whose webhook_secret authenticated the request == organization owning the repository/commit the handler mutates`

Because `repository_owner` is taken from `params.dig('repository','owner','login')` of the still-unverified body, an attacker who administers their own GitHub App/org on the same Shipit instance (and therefore legitimately knows their own `webhook_secret`) can freely choose every other field of the JSON body — including `repository.full_name` used by `Handler#repository_name` [4](#0-3) , or `sha` used by `StatusHandler#process`.

`StatusHandler#process` is the most direct instance of the break: it resolves the target purely by `Commit.where(sha: params.sha)` with **no repository/organization scoping whatsoever** [5](#0-4) . So as long as the attacker's own `webhook_secret` verifies the HMAC over the crafted body, they can set `state: 'success'` on any commit SHA that happens to exist in *any* stack tracked by the Shipit instance, regardless of which org/app the signature was generated for.

Given that a commit's status affects `deployable?`/`next_commit_to_deploy` and that stacks with `continuous_deployment: true` automatically deploy once a commit becomes deployable (`Stack#trigger_continuous_delivery`, `ContinuousDeliveryJob`) [6](#0-5) [7](#0-6) , an attacker who controls only their own (unrelated) GitHub App installation can forge a passing CI status for a commit belonging to a completely different organization's stack and trigger an unauthorized deploy on it.

The same confusion applies to `PushHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, and `OpenedHandler`, all of which resolve the acted-upon `Repository`/`Stack` solely via `params.repository.full_name`, a field never bound to the organization whose secret produced the signature [8](#0-7) [9](#0-8) .

### Impact Explanation
This meets the "Critical - unauthorized deploy" bar: an attacker with a legitimate GitHub App installation on their own organization (no privileged Shipit access, no `ApiClient` token, no access to the victim org's `webhook_secret`) can:
1. Sign an arbitrary crafted webhook payload with their own known `webhook_secret`.
2. Set `repository.owner.login` to their own org (so `verify_signature` picks and successfully matches their own secret).
3. Set the target `sha`/`repository.full_name` to values belonging to a victim organization's stack tracked by the same Shipit instance.
4. Cause `StatusHandler` to record a fabricated "success" CI status on a victim commit, or `PushHandler`/PR handlers to trigger sync/archive/provisioning actions on a victim's `Stack`.
5. If the victim stack has `continuous_deployment: true`, this results in an unauthorized deploy of code the attacker never had permission to touch.

### Likelihood Explanation
Requires only that the attacker (or anyone who has installed their own GitHub App on the shared Shipit instance's `secrets.yml` multi-org config) knows their own `webhook_secret` — something the org admin sets themselves per `docs/setup.md`. No access to the victim org's secret, GitHub repo, or Shipit session is required, satisfying the "unprivileged attacker" constraint.

### Recommendation
Bind the field used to select the verifying `webhook_secret` to the same field(s) used by every handler to select the target repository/commit, and re-validate after signature verification that `repository.owner.login` (or organization) matches the organization actually associated with `repository.full_name`/`sha`. `StatusHandler` in particular must scope `Commit.where(sha:)` to commits belonging to stacks whose repository belongs to the verified `repository_owner`/organization, not to the entire instance.

### Proof of Concept
1. Attacker has installed their own GitHub App (`org-attacker`) on the shared Shipit instance and knows its `webhook_secret` (`s_attacker`).
2. Attacker crafts:
```json
{
  "sha": "<sha of a commit belonging to victim-org/victim-repo tracked by the same Shipit instance>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-attacker" }, "full_name": "victim-org/victim-repo" }
}
```
3. Computes `X-Hub-Signature: sha1=HMAC-SHA1(s_attacker, raw_body)`.
4. `WebhooksController#verify_signature` extracts `repository_owner = "org-attacker"`, loads `Shipit.github(organization: "org-attacker")`, verifies successfully (attacker's own valid secret) [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit (no org scoping), and calls `create_status_from_github!` marking it as passing CI [5](#0-4) .
6. If `victim-org/victim-repo`'s stack has `continuous_deployment: true` and this newly "passing" commit becomes the next deployable commit, `ContinuousDeliveryJob`/`trigger_continuous_delivery` deploys it — an unauthorized deploy triggered entirely from an unrelated organization's credentials.
