### Title
Webhook signature verification is scoped to an attacker-controlled `repository.owner.login` while stack/commit resolution uses an independent `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App / webhook secret to validate a request against using a field read straight out of the unauthenticated JSON body, before the HMAC signature has been checked. The handlers that actually act on the payload (updating stacks, commit statuses, etc.) key off a *different* field of that same body. Nothing ties the two together, so in a multi-organization deployment an attacker who only knows of one organization configured with a blank `webhook_secret` can forge events that are accepted "verified" and then made to target an entirely different, properly-secured organization's repository/stack.

### Finding Description
`verify_signature` derives the organization used for verification purely from the untrusted body: [1](#0-0) [2](#0-1) 

`repository_owner` is computed via `params.dig('repository', 'owner', 'login')` — a value that lives inside the raw JSON body itself and is not yet cryptographically verified at the point it is used to select the verifying `GitHubApp`.

`Shipit.github(organization:)` looks up per-organization config, and `GitHubApp#verify_webhook_signature` trivially passes when that organization has no `webhook_secret` configured: [3](#0-2) 

This "optional" webhook secret is a documented, supported configuration — every example in the docs/setup materials shows `webhook_secret:` as blank/optional per organization in a multi-org setup: [4](#0-3) 

Meanwhile, once `create` runs, handlers resolve the *actual* repository/stack to mutate using a completely independent field of the same JSON body, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) [6](#0-5) 

Concretely, `PushHandler` triggers a GitHub sync for any stack matching the branch of the resolved repository, and `StatusHandler` writes commit statuses for any commit matching the given SHA, both scoped only by `full_name`, not by the organization that “authenticated” the request: [7](#0-6) [8](#0-7) 

**Broken binding:** the organization whose (absent) secret "authenticated" the request ≠ the repository/stack whose state is actually written.

### Impact Explanation
In a documented multi-org Shipit configuration where at least one configured organization has no `webhook_secret` set (an explicitly supported, commonly-seen default in every secrets example in this repo), an unauthenticated attacker can:
1. Send a POST to `/webhooks` with `X-Github-Event: status` (or `push`/`check_suite`), setting `repository.owner.login` to the org with no secret (so `verify_webhook_signature` returns `true` unconditionally) and `repository.full_name` to `victim-org/victim-repo`, a real repository/stack belonging to a different, properly-secured organization.
2. `StatusHandler` will write forged commit statuses (`success`/`failure`) for arbitrary commit SHAs on the victim stack, which Shipit's deployability logic uses to gate deploys — enabling an **unauthorized deploy** by forging green CI status, or blocking legitimate deploys via forged failures.
3. `PushHandler`/`GithubSyncJob` can likewise be triggered with an attacker-chosen `expected_head_sha` against the victim stack.

This crosses a real authentication/repository-write boundary without any credential for the victim organization, matching the Critical tier ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires: (a) the host app run in the documented multi-organization `github:` config mode, and (b) at least one configured organization with a blank `webhook_secret`. Both are explicitly presented as valid/optional in this engine's own documentation and example secrets files, so this is a realistic deployment state, not a hypothetical misconfiguration outside the documented setup.

### Recommendation
Bind the two fields together before trusting either: after selecting the verifying `GitHubApp` from `repository.owner.login`, require that the same organization matches the owner segment of `repository.full_name` (or any other repository identifier the payload will subsequently be used to resolve) before dispatching to handlers. Alternatively, do not allow organizations with a blank `webhook_secret` to short-circuit verification when acting as if fully trusted equally to configured ones, and/or perform a single verification pass keyed by the resolved `Repository`'s configured organization rather than by the raw, pre-verification payload field.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`: `victim-org` (with a `webhook_secret` set) and `attacker-org` (with `webhook_secret` left blank, matching every documented example).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success"
}
```
No valid `X-Hub-Signature` is required since `attacker-org` has no `webhook_secret`, so `verify_webhook_signature` returns `true` (`lib/shipit/github_app.rb:77`).
3. `WebhooksController#create` dispatches to `StatusHandler`, which resolves the repository via `payload.dig('repository', 'full_name')` = `victim-org/victim-repo` and writes the forged status onto the victim's commit, independent of which org "verified" the request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
