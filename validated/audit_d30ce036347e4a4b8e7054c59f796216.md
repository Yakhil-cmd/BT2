Found it: `Api::CCMenuController#stack` bypasses the tenant-scoping method used by every other API controller.

### Title
CCMenu API endpoint uses unscoped `Stack.from_param!` instead of token-scoped `stacks`, breaking the stack-scope binding a `read:stack` token authorises - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` scopes every stack lookup by the authenticated `ApiClient`'s `stack_id`, so a stack-scoped token can only ever resolve the one `Stack` it was minted for [1](#0-0) . `Api::CCMenuController`, however, overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, never going through that scoped collection [2](#0-1) , so any valid token — including one deliberately scoped to a single stack — can read `deploys_and_rollbacks` for **any** stack in the installation by simply changing `stack_id` in the URL/params.

### Finding Description
The intended trust binding is: `token.stack_id == stack read`. `BaseController#stacks` enforces this equality for every other API controller: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) . `CCMenuController` instead defines its own private `stack` method that resolves the stack from `params[:stack_id]` via `Stack.from_param!`, completely independent of `current_api_client` [3](#0-2) . The only authorization check performed is `require_permission :read, :stack`, which merely verifies the token's `permissions` array contains `"read:stack"` — it never checks which stack the permission applies to [4](#0-3) . Additionally, `CCMenuController` overrides `authenticate_api_client` to accept the token from a query-string `token` param instead of a `Basic` header [5](#0-4) , which is exactly the flow `CCMenuUrlController#fetch` uses to mint a `read:stack`-only token scoped to one stack for embedding in third-party CI dashboard tools [6](#0-5) . That deliberately narrow, stack-scoped token is exactly the credential that leaks into low-trust contexts (CI dashboards, third-party tools), yet because the controller's `stack` method bypasses the scoping logic, the token's authorization ("this stack") never matches what is actually returned ("any stack"). This is the analog of the SafeMath/unchecked-calculation class of bug from the report: a value (the token's `stack_id` scope) is computed/asserted in one place but never actually checked/enforced at the point where it's consumed, so the binding silently diverges.

### Impact Explanation
This is an unauthenticated read of stack state (deploy status, last deploy time, running state) for any stack in the Shipit installation via a token that was intentionally minted with `stack_id` scoping to restrict it to one project. This satisfies the High-severity bucket: "unauthenticated read of stack state, task streams or deploy output" via a credential (the CCMenu token) that was never supposed to carry that scope in the first place — this is a scope-escalation bug in the engine's own authorization code, not a missing-credential scenario, since possessing *a* valid (even minimally scoped, publicly embedded) token is the intended threat model for this endpoint.

### Likelihood Explanation
Any holder of a CCMenu URL/token (these are designed to be embedded in external CCTray-compatible dashboard clients, i.e., low-trust distribution) can trivially change the `stack_id` parameter in the request to enumerate other stacks' build/deploy status. No other credential or privilege is required beyond the one CCMenu token they already legitimately hold for a single stack.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the token-scoped `stacks` collection (as every other API controller does) rather than calling `Stack.from_param!` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so `require_permission :read, :stack` is enforced against the same stack set the token was scoped to.

### Proof of Concept
1. Call `GET /ccmenu_url?stack_id=my-project` while authenticated as a normal user; this creates (or reuses) a `read:stack`-only `ApiClient` scoped to `stack_id = my-project` and returns a URL containing `?token=<signed-token>` [7](#0-6) .
2. That URL/token is embedded into a CI dashboard tool (its intended use).
3. An attacker (or the third-party tool operator) who obtains this token requests `GET /api/stacks/other-project/cc_menu.xml?token=<signed-token>`.
4. `authenticate_api_client` accepts the token from the query string and sets `@current_api_client` to the scoped client [5](#0-4) .
5. `require_permission :read, :stack` passes because the token has `"read:stack"` in `permissions`, regardless of stack [4](#0-3) .
6. `stack` resolves `other-project` via `Stack.from_param!`, bypassing the `stack_id`-scoped `stacks` collection, and returns build/deploy status for `other-project` — a stack the token was never intended to expose [8](#0-7) .
