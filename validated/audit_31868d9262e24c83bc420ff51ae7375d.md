### Title
Unverified `recapitalize` credits the cash book and pays a refund for tokens never delivered, draining custody and leaving the book insolvent - ([File: contracts/pool/src/ops/recapitalize.rs](contracts/pool/src/ops/recapitalize.rs))

### Summary
This is the direct analog of the TRSRY finding: bookkeeping reports reserves that were never actually received, so downstream transfers that pass the liquidity guard still fail — or worse, are paid out to someone who never funded them. `recapitalize::accounting` credits `min(amount, backing_shortfall)` to the tracked `cash` book purely from the controller-supplied `amount` argument, then `transfer_out` refunds `amount - applied` to `payer`. The pool never measures its real token-balance delta, unlike the `flash_loan` path which reconciles `token.balance()` with strict equality. The controller entrypoint `recapitalize` is reachable by an unprivileged caller.

### Finding Description
In `contracts/pool/src/ops/recapitalize.rs:44-67`, `accounting` computes `applied = amount.min(guards::backing_shortfall(&cache))`, calls `cache.credit_cash(applied)`, commits, and sets `refund = amount - applied`. `apply` then calls `outcome.cache.transfer_out(&payer, outcome.refund)` at line 34. Nothing in this path reads `token.balance(pool)` before or after; the pool trusts the controller's `amount` as proof of an inbound transfer (the README states the pool "credits cash" on "the controller's word, without verifying the transfer" for `in` legs — but `recapitalize` is `in/out`, and the `out` leg is sized from the unverified `in`).

Two failure modes result:

1. **Refund theft**: if `backing_shortfall < amount` (including shortfall = 0 in a healthy market), the pool transfers `amount - applied` of *real* tokens to `payer` while only `applied` was notionally "received". With shortfall = 0, the entire `amount` is refunded — an outright payout of pool custody to an arbitrary `payer` argument.
2. **Book overstatement** (the exact TRSRY analog): `credit_cash(applied)` inflates `cash` without custody. `require_reserves` in `contracts/pool/src/cache/cash.rs:15-21` checks `self.cash >= amount` against the book, so subsequent `withdraw`, `borrow`, `flash_loan`, and `claim_revenue` pass the `InsufficientLiquidity` guard and then revert inside the SAC `transfer` at `cash.rs:51-52`, freezing user withdrawals. The existing test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` in `contracts/pool/tests/flows.rs:3408-3483` already demonstrates this: an unfunded recapitalize drains custody to zero while `state.cash` still claims the full deposit, and the supplier's `withdraw` fails with the SAC `BalanceError = 10`, not a pool guard.

### Impact Explanation
Theft of user funds (unbacked refund to `payer`) and temporary freezing of funds / contract unable to operate from lack of token funds: suppliers' withdrawals and liquidations revert at the token transfer despite `get_reserves` and the liquidity guard reporting sufficient cash — identical in shape to TRSRY's `getReserveBalance` reporting tokens it no longer held after the loan.

### Likelihood Explanation
Medium. Exploitation requires only that the controller forwards a caller-chosen `amount` without pre-transferring or measuring the full amount into the pool. The money-flow invariant `tracked cash <= token.balance()` (`tests/fuzz/fuzz_targets/pool_native.rs:115-122`) and INV-ACCT-03's "measured receipt" claim (`docs/reference/invariants.md:114-124`) are both violated by this path — every other token-funded credit (supply, repay) measures the balance delta, but recapitalize does not. The pool-side test fixture proves the unwind happens with a single call.

### Recommendation
Make `recapitalize` use measured receipt like the other `in` flows: snapshot `token.balance(pool)` at entry, compute `received = balance_after - balance_before` (or require the controller to transfer before the call and measure the delta inside `accounting`), set `applied = received.min(backing_shortfall)`, and refund `received - applied` — never more than was actually received. Alternatively, reconcile the refund against the real balance before `transfer_out`.

### Proof of Concept
The repository's own test demonstrates the unfunded-custody divergence, `contracts/pool/tests/flows.rs:3408-3483`:

```rust
// fund pool with a real deposit of 10_000_000_000, state.cash == balance
let custody = token.balance(&t.pool);
// recapitalize with NO inbound transfer; payer is a fresh address
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
assert_eq!(token.balance(&t.pool), 0, "custody is gone");
assert!(t.state_snapshot().cash >= deposit, "book still claims the funds");
// supplier's withdraw passes require_reserves, then reverts in the SAC transfer
let outcome = t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
// outcome is SAC BalanceError = 10, not InsufficientLiquidity / PoolInsolvent
```

An unprivileged caller reaches this via the controller `recapitalize` entrypoint, passing their own address as `payer` and an `amount` exceeding any inbound transfer actually performed; the pool pays `amount - applied` out of real custody and overstates `cash` by any `applied` that was never received.
