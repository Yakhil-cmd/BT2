### Title
Unbounded output-selection loop in AA `sendUnit()`/`completePaymentPayload()` allows dust-flooding an AA address to block outgoing AA payments - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `completePaymentPayload()` selects UTXOs for an AA-generated payment by running `readStableOutputs()`/`readUnstableOutputsSentByAAs()` (SQL queries with **no `LIMIT`**) and then feeding every returned row into `iterateUnspentOutputs()`, a synchronous `for` loop with no cap on the number of inputs it will accumulate. [1](#0-0) [2](#0-1)  Any unprivileged party can send many tiny payments (just above the `FULL_TRANSFER_INPUT_SIZE` dust threshold) to an AA address to inflate this candidate-output set without bound, exactly analogous to the reported unbounded `activeProtectionIndexes` loop that reverts the caller due to out-of-gas/out-of-resources.

### Finding Description
When an AA sends a payment (base or asset) to satisfy a trigger response, `sendUnit()` calls `completePaymentPayload()`, which builds the payload by pulling unspent outputs belonging to the AA address:

```
function readStableOutputs(handleRows) {
    ...
    conn.query(
        "SELECT unit, message_index, output_index, amount, output_id \n\
        FROM outputs ... WHERE address=? AND asset=... AND is_spent=0 \n\
            AND sequence='good' AND main_chain_index<=? \n\
            AND output_id NOT IN(...) \n\
        ORDER BY main_chain_index, unit, output_index",
        [address, mci], handleRows
    );
}
``` [1](#0-0) 

There is no `LIMIT` clause, so the query can return an arbitrarily large row set. `iterateUnspentOutputs()` then walks the entire returned array synchronously:

```
function iterateUnspentOutputs(rows) {
    for (var i = 0; i < rows.length; i++){
        var row = rows[i];
        ...
        payload.inputs.push(input);
        total_amount += row.amount;
        ...
        if (total_amount < target_amount)
            continue;
        ...
    }
}
``` [2](#0-1) 

The comment at `readStableOutputs()` only mitigates *sub-`FULL_TRANSFER_INPUT_SIZE`* dust by excluding outputs smaller than `FULL_TRANSFER_INPUT_SIZE`; it does nothing to bound the *count* of outputs at or slightly above that threshold. [3](#0-2)  An unprivileged unit poster can therefore send an arbitrary number of separate units, each containing one payment output of exactly `FULL_TRANSFER_INPUT_SIZE` (or a bit more) bytes to a target AA address. Every one of these becomes an unspent, un-consolidated output row matched by the `WHERE` clause. There is no cap elsewhere in `inputs.js`/`aa_composer.js` on how many of these rows `iterateUnspentOutputs()` will pull in a single call — unlike the address-wallet-side `pickMultipleCoinsAndContinue()` in `inputs.js`, which explicitly limits to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2` rows via SQL `LIMIT`. [4](#0-3)  No equivalent `LIMIT` or `MAX_INPUTS_PER_PAYMENT_MESSAGE` bound exists in the AA output-selection path.

As a result, once the AA needs to spend to an address (e.g., forwarding funds in a trigger response), it must iterate through the full dust-inflated set to accumulate `target_amount`, growing `payload.inputs` without an enforced ceiling, before even reaching the unit-size/oversize-fee checks that would otherwise reject an oversized unit.

### Impact Explanation
This blocks the AA's ability to construct a valid outgoing payment: the resulting unit either becomes too large (rejected during commit/broadcast because `objUnit.headers_commission + objUnit.payload_commission > constants.MAX_UNIT_LENGTH`, triggering the AA's `bounce()` fallback) or the composition step itself becomes prohibitively expensive to compute for every trigger execution touching that balance, on every node that re-executes the AA (during validation and catchup). Because AA execution must be deterministically reproduced by every full node, this is not merely a performance nuisance on one node — it forces all nodes validating triggers against this AA/address to redo the same expensive/failing computation, and it can permanently prevent the AA from ever successfully sending funds out of that balance, effectively freezing AA funds for the affected asset, matching the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Likelihood is high: no privileged access is required. Any wallet can post ordinary payment units, each containing one output of `FULL_TRANSFER_INPUT_SIZE` bytes, to any known AA address, at a cost roughly proportional to that dust amount plus normal unit fees, to grow the AA's spendable-output set arbitrarily.

### Recommendation
Bound the number of inputs selected per AA payment message analogous to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` used elsewhere (`inputs.js`) — add a `LIMIT` to the `readStableOutputs()`/`readUnstableOutputsSentByAAs()` queries and cap iterations in `iterateUnspentOutputs()`, falling back to multiple payment messages/units or partial fulfillment strategies rather than attempting to consume an unbounded output set in one pass. Additionally raise the dust-exclusion threshold and/or track a per-address "candidate output count" to detect and reject/merge pathological dust flooding before it reaches the AA composer.

### Proof of Concept
1. Deploy or locate an AA that at some point sends a base-asset payment to an address using AA-controlled balance (any AA forwarding funds).
2. From an unprivileged wallet, post N ordinary units, each with a single payment output of exactly `FULL_TRANSFER_INPUT_SIZE` (or slightly more) bytes to the AA's address, for large N (e.g., tens of thousands), spread across many units to avoid `MAX_MESSAGES_PER_UNIT`/`MAX_OUTPUTS_PER_MESSAGE` limits.
3. Trigger the AA to send a base-asset payment from that address.
4. Observe `completePaymentPayload()` → `readStableOutputs()` returning all N dust rows (no `LIMIT`), and `iterateUnspentOutputs()` looping over all of them, producing an oversized `payload.inputs`, causing the constructed unit to exceed `constants.MAX_UNIT_LENGTH` and the AA response to `bounce()`, or causing excessive computation time repeated by every validating node.
