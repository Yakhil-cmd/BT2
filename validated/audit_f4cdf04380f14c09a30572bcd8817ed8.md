### Title
Uncaught exception in `chash.isChashValid` when a checksum-length mismatch occurs during address validation - (File: `chash.js`)

### Summary
CVE-2016-2797 is a bounds/length-mismatch bug in a table-driven lookup function (`CmapSubtable12Lookup`) that trusted a crafted, attacker-supplied binary structure to have a length/index relationship it did not actually have, causing an out-of-bounds access. The closest reachable analog in ocore is `chash.js`'s length-mapping logic (`calcOffsets` / `separateIntoCleanDataAndChecksum`), which assumes that a decoded c-hash buffer always has exactly 160 or 288 bits and throws an **uncaught** `Error` otherwise — reachable from any externally supplied address string (e.g., in a unit's outputs, definitions, `is_valid_address`, etc.) via `isValidAddress`/`isValidChash`.

### Finding Description
`chash.isChashValid(encoded)` only validates the *string* length of `encoded` (32 or 48 chars) before decoding: [1](#0-0) 

The decode step (`base32.decode` or `Buffer.from(encoded,'base64')`) is wrapped in try/catch, but the very next step is not: [2](#0-1) 

`separateIntoCleanDataAndChecksum(binChash)` requires `bin.length` to be *exactly* 160 or 288 bits, otherwise it throws unconditionally, with no try/catch around this call in `isChashValid`: [3](#0-2) 

A 32-character base32 string is expected to decode into exactly 20 bytes (160 bits), and a 48-character base64 string into exactly 36 bytes (288 bits). But this relationship is guaranteed only if the decoder faithfully rejects any malformed input to the expected byte width. If the `thirty-two` base32 decoder (or `Buffer.from(str,'base64')` for malformed/ non-canonical base64 padding, e.g. strings containing extra `=`, whitespace-adjacent characters, or non-canonical padding accepted leniently by Node's base64 decoder) ever returns a buffer whose length isn't exactly 20 or 36 bytes for a same-length input string, `binChash.length` will not be 160/288, and `separateIntoCleanDataAndChecksum` throws an `Error` that propagates straight out of `isChashValid`, out of `isValidChash`/`isValidAddress`, and into whatever validation code path called it.

This mirrors the CVE-2016-2797 bug class conceptually: a length/offset table is entered based on an assumption about the decoded structure's size that a malicious/crafted input can violate, and the code doesn't defensively re-check that assumption before doing table-indexed processing — it only wraps the decode call, not the size-dependent processing that follows.

### Impact Explanation
`isValidAddress`/`isValidChash` is called pervasively throughout unit and AA validation (`validation.js`, `definition.js`, `aa_validation.js`, `formula/validation.js`, `formula/evaluation.js`, `light.js`, `witness_proof.js`, `wallet.js`, etc.) — i.e., on attacker-controlled address strings supplied in ordinary posted units (output addresses, address-definition fields, `is_valid_address` in oscript/AA formulas), reachable by any unprivileged unit poster or AA trigger sender: [4](#0-3) 

If a crafted 32- or 48-character string can make the decoded buffer length not equal exactly 20/36 bytes, calling `isChashValid` throws an uncaught exception during unit validation. Depending on where this exception surfaces in the call stack (e.g., inside a `db.query` callback or async validation flow without an enclosing try/catch), this can crash the node process handling the unit, or otherwise abort validation non-deterministically, leading to inconsistent acceptance/rejection of the same unit across nodes — i.e., node disagreement on validity, or a unit-processing path that halts confirmation of subsequent units on the affected node.

### Likelihood Explanation
Exploitability hinges on whether the actual base32/base64 decoding libraries used (`thirty-two` npm module for base32, Node's built-in `Buffer.from(str,'base64')`) can be coerced into producing a decoded buffer of unexpected byte length for a string of exactly 32/48 characters (e.g., via embedded padding characters, mixed case, or non-alphabet characters that the decoder silently skips rather than rejects). I could not fully verify the `thirty-two` library's internal behavior in this repo (the module's source is not indexed here), so this is asserted as a **plausible, but unconfirmed**, root cause; the guard gap in `chash.js` (missing try/catch around `separateIntoCleanDataAndChecksum` in `isChashValid`) is confirmed and concrete regardless of whether the decoder can be tricked into a mismatched length.

### Recommendation
Wrap the entire body of `isChashValid` (decode through comparison) in try/catch and return `false` on any exception, rather than only wrapping the decode call, so that any length assumption violation degrades safely to "invalid c-hash" instead of throwing an uncaught exception during unit/AA validation.

### Proof of Concept
Not fully constructible without confirming a `thirty-two`/base64 decoding edge case that yields a mismatched buffer length for a 32/48-character input; this would need to be validated against the actual `thirty-two` library behavior (e.g., fuzzing `base32.decode()` with strings containing padding/invalid characters while keeping length 32) to find a value where `chash.isChashValid("<crafted-address-string>")` throws instead of returning `false`. If confirmed, the PoC unit would simply place that crafted address string in an output/definition field and post it as an ordinary unit.
