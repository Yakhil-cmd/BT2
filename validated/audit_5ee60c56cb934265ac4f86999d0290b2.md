### Title
`Commit.where(sha: params.sha)` in `StatusHandler#process` is unscoped, allowing cross-tenant status forgery via shared SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` queries `Commit.where(sha: params.sha)` with no `stack_id`/repository scoping, unlike sibling handlers such as `CheckSuiteHandler` which explicitly scope through `stacks.where(...)` and `stack.commits.where(...)`. Since a validly-signed `status` webhook only proves the request came from *some* repository the attacker owns, but the query then matches *every* `Commit` row across *all* stacks/tenants sharing that SHA, an attacker who owns any GitHub repo can forge a status for any commit whose SHA happens to collide with a commit in another tenant's stack (e.g. the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any SHA an attacker can arrange to duplicate, such as by pushing an identical commit/tree to their own repo).

### Finding Description
**Binding claimed broken:** `{Commit rows touched by StatusHandler#process} == {commits belonging to payload.repository.full_name}`. Trace shows this is false.

- `WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses the JSON body and dispatches to handlers registered for the event type, after `verify_signature` (line 24-49) checks the HMAC signature against `Shipit.github(organization: repository_owner)`'s webhook secret. This proves the payload was sent by the owner of `payload['repository']['owner']['login']` — it does **not** restrict which `Commit` records the handler may touch.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
  ```
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
  ```
  This is a global, unscoped `ActiveRecord` query across the entire `commits` table — no `stack_id`, no `repository`, no use of the `stacks`/`repository_name` helpers that `Handler` provides (app/models/shipit/webhooks/handlers/handler.rb:32-38).
- Compare with `CheckSuiteHandler#process` (app/models/shipit/webhooks/handlers/check_suite_handler.rb:14-16), which correctly scopes: `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }`.
- `Commit#create_status_from_github!` (app/models/shipit/commit.rb:165-169) calls `statuses.replicate_from_github!(stack_id, github_status)`, writing a `Status` row tied to that commit's own `stack_id` — meaning the forged status is persisted against whatever tenant/stack that `Commit` row actually belongs to, not the attacker's.

**Attack:** Attacker owns repo `attacker/evil`, configures it as a Shipit stack (or simply has a webhook configured pointing at the Shipit host — webhook secret is per-organization via `Shipit.github(organization:)`, so attacker needs a repo whose org is registered with Shipit, or can trigger a status event on any repo Shipit accepts). They push a commit whose SHA matches a targeted victim commit's SHA (trivially achievable for the empty-tree SHA, or any content-identical commit, since git SHA1 is content-addressed and identical across repositories), then have GitHub emit a `status` event for that SHA (e.g., via a CI integration or GitHub Status API call on their own repo). The signature check passes because it's genuinely signed by attacker's own org's webhook secret. `StatusHandler#process` then matches **all** `Commit` rows in the DB with that SHA — across every stack/tenant — and writes a forged `Status` (arbitrary `state`, `description`, `target_url`, `context`) onto each of them.

**Why existing guards fail:** `verify_signature` authenticates *who sent the payload*, not *which records the payload may affect*. `drop_unhandled_event` and `ExplicitParameters` schema only validate event registration and payload shape, not scope. No `Repository`/`Stack` scoping like `CheckSuiteHandler` is applied here.

### Impact Explanation
An attacker with no privileges beyond ownership of any repository whose org is configured with Shipit (or any repo capable of emitting a signed `status` webhook accepted by the instance) can inject forged CI/status state (`success`, `failure`, `pending`, arbitrary `description`/`target_url`) onto commits belonging to unrelated stacks/tenants, purely by SHA collision. Since Shipit uses commit status (`required_statuses`, `blocking_statuses`) to gate deploy eligibility, a forged "success" status can help unblock/enable a deploy for a victim stack's commit that never actually passed CI on that repository — this is a cross-tenant record write ("a payload for one repository mutating another's stack/commit"), matching the **Critical** impact category (payload for one repo mutating another's commit/stack state, contributing to unauthorized deploy conditions). It is repeatable against any targeted SHA the attacker can reproduce/collide, and is not limited to a single victim — every stack across the instance sharing that SHA is affected in one request.

### Likelihood Explanation
Preconditions: attacker needs a Shipit-registered organization/repo with a valid webhook (a normal, low-privilege setup step available to anyone who can create/own a GitHub repo and add it to Shipit, or simply the ability to send a signed `status` webhook payload for their own registered repo). No Shipit session, API token, or secret is required beyond what GitHub itself provides when the attacker's own repo emits its own signed webhook. SHA collision across repos is trivial for well-known objects (empty tree/blob SHAs common to virtually all repositories) and achievable for arbitrary content by pushing byte-identical commits. This makes the attack low-cost and fully repeatable.

### Recommendation
Scope `StatusHandler#process` to the payload's own repository, mirroring `CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the `stacks` helper (`Repository.from_github_repo_name(repository_name).stacks`) already provided by `Handler`, so only commits belonging to the authenticated payload's repository are ever touched.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `stack1` (repo `attacker/evil`), `stack2` (repo `victim/one`), `stack3` (repo `victim/two`), each with a `Commit` having `sha: '4b825dc642cb6eb9a060e54bf8d69288fbee4904'`.
2. Build a valid `status` webhook payload for `attacker/evil` with that sha and `state: 'success'`.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing HTTP layer, since signature validity is not in question — assume it already passed `verify_signature`).
4. Assert: `stack2.commits.find_by(sha: ...).status.state == 'success'` and `stack3.commits.find_by(sha: ...).status.state == 'success'` — i.e., commits in `victim/one` and `victim/two` received the forged status despite the webhook only being signed for `attacker/evil`.
