### Title
Same-block oracle self-dealing via AA reading unstable data-feed values from chained AA responses - (File: `data_feeds.js`, `aa_composer.js`, `formula/evaluation.js`)

### Summary
The external report describes a flashloan-enabled oracle attack: an attacker manipulates a fallback price oracle and, in the same atomic operation, uses the manipulated price to trigger favorable liquidations/exchanges before the false price can be contested or reverted. The analogous condition in `Ellentat/ocore--017` is the `data_feed[[...]]` oscript primitive's ability to read **not-yet-stable** ("unstable") data-feed values posted by other AAs, combined with the AA composer's ability to chain multiple AA triggers atomically (as "secondary" triggers) within the processing of a single primary trigger unit.

### Finding Description
`data_feed[[...]]`/`in_data_feed[[...]]` evaluation in an AA context calls `dataFeeds.readDataFeedValue()` / `dataFeeds.dataFeedExists()` with `unstable_opts = bAA` (true whenever the formula is being evaluated inside an AA trigger). [1](#0-0) [2](#0-1) 

When `bIncludeUnstableAAs` is set, both functions scan `storage.assocUnstableMessages` — i.e. `data_feed` messages posted by units that have **not yet stabilized** — and accept any candidate whose author matches the requested oracle address and whose `objUnit.bAA` flag is set (meaning the poster is itself an AA address). [3](#0-2) [4](#0-3) 

This is intentionally designed to let an AA read a fresh, still-unstable price/output just posted by *another AA* earlier in the same causal chain, so that oracle-relayer AAs and consumer AAs (e.g. a price-oracle AA feeding a lending/exchange AA) can be composed and executed atomically. The AA composer supports exactly this kind of atomic chaining: a single primary trigger unit can cause a cascade of secondary AA triggers (`bSecondary`) that are all executed synchronously within `handlePrimaryAATrigger`/`handleTrigger`, up to `MAX_RESPONSES_PER_PRIMARY_TRIGGER`, before the whole batch is written and any outside party can react. [5](#0-4) [6](#0-5) 

The combination reproduces the report's exploit shape: if a price-dependent AA (analogous to `StabilityPool`/`PriceFeed` consumers, e.g. the sample `futures_contract.oscript`/`option_contract.oscript` AAs that gate large payouts on `data_feed[[oracles='<single oracle address>', ...]]`) trusts a single upstream oracle AA, an attacker who can influence that oracle AA's output (or who controls/compromises it) can, in one causal chain of unit(s):
1. Cause the oracle AA to post a manipulated `data_feed` value as part of its response;
2. In the same trigger cascade (still unstable), have the downstream consumer AA read that unstable value via `data_feed[[...]]` and immediately pay out/liquidate/exchange based on it;
3. All of this resolves atomically as soon as the primary trigger's cascade completes and the batch is committed — with no window for a third party to intervene, exactly as the flashloan+oracle-manipulation report describes for Chainlink/Tellor + StabilityPool. [7](#0-6) [8](#0-7) 

The sample AAs (`futures_contract.oscript`, `option_contract.oscript`) themselves illustrate the single-oracle trust pattern that any real DeFi-style AA (lending, stablecoin, prediction market) on ocore would replicate: they resolve high-value payouts strictly from one hardcoded oracle address with a plain `<`/`>` comparison and no delay/median/multi-oracle safeguard. [7](#0-6) 

### Impact Explanation
Any AA whose economic logic (collateral valuation, liquidation threshold, redemption rate) depends on `data_feed`/`in_data_feed` values sourced from another AA is exposed to atomic self-dealing: the value can be produced and consumed in the same unresolved causal chain before the network/other participants have any chance to see or contest it, unlike values read from already-stabilized state. This can cause direct AA fund loss (over-payout, wrongful liquidation, mispriced exchange) analogous to the drained stability pool in the original report. This is a Medium/High severity design risk depending on how much value the ecosystem's DeFi AAs place in single-oracle-AA data feeds.

### Likelihood Explanation
Exploitability requires: (1) a consumer AA that trusts a data feed sourced from an oracle that is itself an AA (not a plain human-authored feed, since `objUnit.bAA` gating excludes ordinary user-posted feeds from the unstable-read path), and (2) that oracle AA's value being influenceable by the same party triggering the consumer AA within one atomic chain. This is a real, reachable pattern for composable oracle/lending AA ecosystems (a core design feature of oscript's AA-to-AA composability), but it depends on application-level AA design choices (whether the app author picks a single, triggerable oracle AA versus an externally-fed, human/multi-sig oracle address) rather than being a universal protocol flaw — hence Medium likelihood.

### Recommendation
- For any price/oracle-role AA that other AAs may compose with atomically, require that data-feed values consumed for high-value decisions come from **stable** (already-finalized) data, not `unstable_opts`-included fresh AA outputs, or add explicit `min_mci`/staleness and multi-source (median-of-N) requirements in application-level AA templates.
- Consider documenting/warning (or optionally gating) the atomic unstable-data-feed read path so it cannot be silently relied upon for critical financial payouts without an explicit developer opt-in, since it collapses the normal "wait for stabilization" trust assumption that DAG consensus otherwise provides.
- Encourage/require AA authors building lending/stablecoin/derivative AAs to use multiple independent oracle addresses and time-weighted or delay-based checks, mirroring the original report's own recommendation to avoid a single manipulable price source triggering irreversible fund movement in one atomic step.

### Proof of Concept
Conceptual chain (cannot be fully executed without a live testnet, but demonstrates the reachable path):
1. Deploy an oracle-relay AA `O` whose response posts a `data_feed` message with a price computable/influenceable by its trigger's `trigger.data` (a common oscript pattern for bridging user-submitted prices into AA-consumable feeds).
2. Deploy/target a consumer AA `C` (a lending/derivative AA) whose payout logic uses `data_feed[[oracles=O_address, feed_name='price']]` to determine a liquidation/redemption amount, per the pattern shown in `test/samples/option_contract.oscript` lines 59-73. [7](#0-6) 
3. Post a single unit that triggers `O` with attacker-favorable data, whose response chains (secondary trigger) into `C` before `O`'s data-feed unit stabilizes.
4. Because `readDataFeedValue`/`dataFeedExists` include `objUnit.bAA`-flagged unstable units authored by `O` when evaluating inside `C`'s AA execution, `C` reads the manipulated, not-yet-stable price and pays out accordingly, atomically, within the same `handlePrimaryAATrigger` cascade. [3](#0-2) [5](#0-4) 

Note: I was unable to fully trace every step of the secondary-trigger dispatch code (`sendUnit`/`bSecondary` chaining logic in `aa_composer.js`) within the available search budget to confirm the exact synchronous ordering guarantees end-to-end; a full audit/PoC on a testnet with two cooperating malicious AAs would be needed to conclusively demonstrate fund extraction.
