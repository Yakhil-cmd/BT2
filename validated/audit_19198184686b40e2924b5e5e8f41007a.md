### Title
Unhandled exception / node crash via malformed c-hash length in `chash.isChashValid` reachable through `isValidAddressAnyCase` - (File: chash.js)

### Summary
The CVE hints at a crash caused by insufficient bounds/length validation of attacker-supplied data before it reaches a low-level buffer routine. In `ocore`, the c-hash decoding pipeline (`chash.js`) has an analogous flaw: `isChashValid()` only wraps the base32/base64 *decode* step in `try/catch`, but the subsequent bit-length validation performed deeper in `separateIntoCleanDataAndChecksum()` throws an uncaught `Error` for any decoded length other than 160 or 288 bits. This function is reachable from unit/address validation through `validation_utils.isValidAddressAnyCase()`, which — unlike `isValidAddress()` — does **not** first restrict the input to the base32 alphabet `[A-Z2-7]`, so an attacker can supply a 32-character string engineered to decode to an unexpected bit length and trigger the uncaught throw during validation of a posted unit.

### Finding Description
`chash.isChashValid()` decodes the given string and only guards the decode call itself: [1](#0-0) 

The decoded buffer is fed to `buffer2bin()` and then to `separateIntoCleanDataAndChecksum()`, which throws a plain `Error` (not caught anywhere in this call chain) if the resulting bit length is not exactly 160 or 288: [2](#0-1) 

`isValidAddress()` prevents reaching this code path with malformed input because it first enforces the strict base32 charset via a regex before calling `isChashValid`: [3](#0-2) 

However, `isValidAddressAnyCase()` skips that charset check and only enforces the string length (32), before calling straight into `isChashValid`: [4](#0-3) 

If the base32 decoder (`thirty-two` package) decodes a 32-character string containing characters outside the strict `[A-Z2-7]` alphabet (e.g., lowercase letters, digits `0/1/8/9`, or punctuation) into a byte buffer whose bit length is not 160, the uncaught `Error` from `separateIntoCleanDataAndChecksum` propagates out of `isChashValid` → `isValidAddressAnyCase`, crashing the calling code path if not caught by an outer handler at the point of use — mirroring the CVE's pattern of an under-validated length field flowing into low-level data processing and causing a crash.

### Impact Explanation
If a node's unit/message validation logic calls `isValidAddressAnyCase()` on an attacker-controlled address field, a single crafted unit can trigger an unhandled exception. Depending on where in the validation call stack this exception surfaces, this can crash the validating process (denial-of-service) or, at minimum, cause inconsistent validation behavior between nodes that catch generic errors at different call layers versus nodes that don't — risking node disagreement on unit validity.

### Likelihood Explanation
Exploitability depends on whether the `thirty-two` base32 decoder actually maps some family of 32-character non-strict-alphabet inputs to buffers whose bit length differs from 160 (this needs decoder-specific confirmation, which was not directly observable from the indexed files). The reachability of `isValidAddressAnyCase` from attacker-controlled unit content also could not be conclusively pinpointed within the available index — the grep found a single usage in `validation.js`, but its surrounding code/context was not returned before the tool budget was exhausted.

### Recommendation
Wrap the entire body of `isChashValid()` (not just the decode step) in a single `try/catch` so any internal throw (from `separateIntoCleanDataAndChecksum`, `mixChecksumIntoCleanData`, `checkLength`, etc.) safely returns `false` instead of propagating. Additionally, align `isValidAddressAnyCase()` with `isValidAddress()` by validating the character set (or at least the decoded byte length) before invoking the deeper c-hash bit-manipulation logic.

### Proof of Concept
Conceptual PoC (pending confirmation of the exact `thirty-two` decode behavior for non-canonical inputs):
1. Construct a 32-character string using characters outside `[A-Z2-7]` (e.g., digits `0`, `1`, `8`, `9`, or lowercase letters) that the `thirty-two` base32 decoder accepts and decodes to a buffer whose length in bits is not 160.
2. Pass this string as an address value to any code path that calls `validation_utils.isValidAddressAnyCase()` on unit-supplied data.
3. Observe the uncaught `Error` thrown from `chash.js`'s `separateIntoCleanDataAndChecksum` propagate out of `isChashValid`.

**Caveat**: Due to the limits of the code index used for this analysis, I could not verify (a) the exact decode behavior of the `thirty-two` library for non-canonical 32-character inputs, or (b) the full call-site context of the single `isValidAddressAnyCase` usage in `validation.js` to confirm it is reached directly from unauthenticated unit content without an enclosing `try/catch`. A Devin session with full repository/dependency access would be needed to confirm both points and produce a concrete crafted-unit PoC.

function separateIntoCleanDataAndChecksum(bin){
	var len = bin.length;
	var arrOffsets;
	if (len === 160)
		arrOffsets = arrOffsets160;
	else if (len === 288)
		arrOffsets = arrOffsets288;
	else
		throw Error("bad length="+len+", bin = "+bin);
	var arrFrags = [];
	var arrChecksumBits = [];
	var start = 0;
	for (var i=0; i<arrOffsets.length; i++){
		arrFrags.push(bin.substring(start, arrOffsets[i]));
		arrChecksumBits.push(bin.substr(arrOffsets[i], 1));
		start = arrOffsets[i]+1;
	}
	// add last frag
	if (start < bin.length)
		arrFrags.push(bin.substring(start));
	var binCleanData = arrFrags.join("");
	var binChecksum = arrChecksumBits.join("");
	return {clean_data: binCleanData, checksum: binChecksum};
}
