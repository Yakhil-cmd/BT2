### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but stack-mutating handlers act on the independent `repository.full_name` field, allowing cross-organization forged deploy triggers - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature against using `repository_owner`, a value read straight out of the *unverified* JSON body (`repository.owner.login`, falling back to `organization.login`). Once the signature check passes, `create` dispatches the same raw, attacker-controlled payload to handlers such as `PushHandler`, which resolve the target `Stack` using a *different* field of the same payload: `repository.full_name` (via `Handler#repository_name` / `Repository.from_github_repo_name`). Nothing ties `repository.owner.login` to `repository.full_name`'s owner segment. In a multi-organization Shipit deployment (`config/secrets.yml` keyed by org, as documented in `docs/setup.md`), a party who legitimately possesses one organization's `webhook_secret` can forge a payload whose `repository.owner.login` matches their own org (so their own valid secret authenticates the request) while `repository.full_name` points at a stack belonging to a *different* organization hosted on the same Shipit instance, triggering an unauthorized `stack.sync_github` on a repository/org they do not control.

### Finding Description
- `verify_signature` computes the signing key from an unverified payload field: [1](#0-0) 
- `repository_owner` is read directly from the JSON body before any signature check occurs: [2](#0-1) 
- `Shipit.github(organization:)` looks up a per-organization `webhook_secret` from `secrets.github` and instantiates the matching `GitHubApp`: [3](#0-2) 
- `verify_webhook_signature` only proves that the raw body was HMAC-signed with *that particular org's* `webhook_secret`; it says nothing about which repository/org the body's other fields describe: [4](#0-3) 
- After the signature check, `create` unconditionally hands the same raw, attacker-supplied JSON to the handler chain: [5](#0-4) 
- `PushHandler#process` (and the base `Handler`) resolve target stacks using `repository.full_name`, a field completely independent of `repository.owner.login`/`organization.login` used for signature-org selection: [6](#0-5) [7](#0-6) 
- `Repository.from_github_repo_name` performs a plain lookup by `owner`/`name` parsed out of `full_name`, with no cross-check against the org whose secret verified the request: [8](#0-7) 

The broken binding is: **"organization that authenticated" == "organization whose repository is written"**. The signature proves the message was signed by holder of Org A's `webhook_secret`; the handler then acts on whatever `repository.full_name` says, which the same signed body can freely set to `"OrgB/victim-repo"`. Because the signature covers the raw bytes (so `repository.full_name` cannot be tampered with by a third party), the actual attacker here is anyone who legitimately controls a `webhook_secret` for at least one organization configured on the shared multi-org Shipit instance (e.g., an org admin who installed their own GitHub App per `docs/setup.md`'s "Using Multiple Github Applications" section) — they can craft and self-sign a payload naming their own org as `repository.owner.login`/`organization.login` while setting `repository.full_name` to another tenant's repository.

### Impact Explanation
This crosses the trust boundary between separately-configured GitHub organizations sharing one Shipit instance. An attacker who is only an authenticated webhook sender for Org A can trigger `stack.sync_github` (and by extension deploy pipelines that key off a repo's HEAD sync) for stacks belonging to Org B, without ever possessing Org B's `webhook_secret`, GitHub App credentials, or repository write access. This matches the "unauthorized deploy" / cross-repository-write class of Critical impact defined for this engine, since Shipit's core webhook contract (a repo's own signed events control that repo's stacks) is broken.

### Likelihood Explanation
Requires the multi-organization GitHub App configuration described in `docs/setup.md` ("Using Multiple Github Applications") to be in use, and requires the attacker to be a legitimate holder of a `webhook_secret` for at least one tenant org on the shared instance (e.g., any org admin who can configure their own GitHub App webhook against the same Shipit endpoint). Given that is an intended supported deployment topology, and no additional privilege beyond "controls one org's webhook secret" is needed, likelihood is credible for any Shipit deployment serving multiple independently-administered GitHub organizations.

### Recommendation
After resolving the target repository/stack from `repository.full_name`, verify that its registered `owner` matches the organization (`repository_owner`) whose `webhook_secret` validated the signature, rejecting the request (e.g., `head(422)`) on mismatch. Alternatively, bind the signature verification key to the org actually owning the repository resolved by the handler, rather than to a value taken from the same unverified payload used to select the key.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `orga` and `orgb`, each with distinct `webhook_secret`s, per the multi-org config in `docs/setup.md`.
2. `orga`'s admin (attacker) knows `orga`'s `webhook_secret` (they configured their own App).
3. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "full_name": "orgb/victim-repo",
       "owner": { "login": "orga" }
     }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orga_webhook_secret, body)>` and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "orga")` (from `repository.owner.login`) and successfully verifies the signature using `orga`'s secret — see `app/controllers/shipit/webhooks_controller.rb:24-30` and `lib/shipit/github_app.rb:76-83`.
6. `create` dispatches the body to `PushHandler`, which resolves stacks via `repository.full_name = "orgb/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on `orgb`'s stack — despite the attacker never possessing any `orgb` credential.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
