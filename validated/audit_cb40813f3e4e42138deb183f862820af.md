### Title
Tokens transferred directly to the pool or controller are permanently locked — no sweep or rescue path exists - (File: contracts/pool/src/ops/recapitalize.rs, contracts/controller/src/markets.rs)

### Summary
The XOXNO Lending pool accepts arbitrary inbound SAC token transfers (any address can hold a token balance; there is no opt-in), but every outbound token leg is tied to a debited bookkeeping amount (`cash`, revenue payout, or a measured-receipt refund). No entrypoint — public or owner — moves the unbooked surplus between `token.balance(pool)` and tracked `cash`, and the controller likewise has no token-swept path: its refund logic only returns positive callback deltas and explicitly never sweeps prior balances. The result mirrors the Entropy/Executor finding: assets can be pushed into the contracts but can never leave, so directly transferred funds are permanently locked barring a Wasm upgrade.

### Finding Description
- The pool's only reconciliation of real balance against the `cash` book is inside `flash_loan` ("The only reconciliation against a real `token.balance()` is in `flash_loan`, which checks it three times with strict equality" — `contracts/pool/README.md`). `supply`, `repay`, and `recapitalize` credit `cash` purely on the controller's measured receipt, and every outbound transfer (`withdraw`, `borrow`, `claim_revenue`, refund legs in `repay`/`recapitalize`) is sized by bookkeeping, not by surplus.
- `ops::recapitalize::accounting` applies only `min(amount, backing_shortfall)` and refunds the declared remainder (`contracts/pool/src/ops/recapitalize.rs:52-55`); nothing ever pays out the difference between balance and `cash`.
- The threat model confirms the gap is systemic: "Direct donations do not rewrite those books" (`docs/explanation/threat-model.md`) and, for the controller, "Refunds cover only positive callback deltas of refund-listed tokens; ... Neither category sweeps prior balances."
- There is no `rescue`/`sweep`/`skim` entrypoint in `contracts/pool/src/lib.rs`, `contracts/controller/src/lib.rs`, or the governance operation set. All pool mutators are `only_owner` (the controller), and the controller exposes no way to move tokens it holds.

An unprivileged user (or a third-party integration, vault, or keeper that misroutes a payment — e.g., repaying debt by `token.transfer` to the pool instead of calling `controller::repay`, which the liquidation skill explicitly warns is "a donation") permanently loses the full amount. The same applies to tokens left in the controller outside a measured callback window.

### Impact Explanation
Permanent freezing of funds. Any token balance sent directly to the pool above the `cash` book, or held by the controller outside a measured delta, has no exit path; recovery requires a contract upgrade, identical to the Entropy/Executor report. The frozen amount is unbounded.

### Likelihood Explanation
Low-to-moderate: loss requires an erroneous direct transfer rather than a protocol entrypoint, but the footgun is realistic — the codebase itself documents that liquidators must not transfer repayment directly to the pool, and there is no way for any actor (including governance) to rescue the funds once sent. Additionally, unsolicited surplus desynchronizes `balance` from `cash`, which also trips `flash_loan`'s strict-equality check; the freezing component stands independently.

### Recommendation
Short term, add an owner/governance-gated sweep on the pool (and controller) that transfers `token.balance(self) - total_cash` for each listed asset to a treasury address, or route surplus into `cash`/revenue accounting. Long term, document the donation trap in the SDK so integrators never call `token.transfer(..., pool, ...)` outside a measured-receipt entrypoint.

### Proof of Concept
```rust
// pool context: market (hub, USDC) with cash == balance == 1_000e7
let donor = Address::generate(&env);
token_admin.mint(&donor, &500_0000000);
// Unprivileged direct transfer — no controller call involved
token::Client::new(&env, &usdc).transfer(&donor, &pool_addr, &500_0000000);

assert_eq!(token.balance(&pool_addr), 1_500_0000000);
assert_eq!(pool.get_reserves(&hub_asset), 1_000_0000000); // cash unchanged

// No public or owner entrypoint can move the 500 surplus:
// withdraw/repay/recapitalize refunds are capped by book amounts,
// claim_revenue is capped by tracked revenue and cash,
// and governance has no sweep operation. The 500 USDC is locked
// until a Wasm upgrade.
```
Controller variant: `token.transfer(user -> controller, X)`; subsequent `repay`/`supply` measured deltas and refund legs only cover callback-window deltas, so the prior balance `X` is never swept — confirmed by the threat-model statement that refund logic does not touch prior balances.
