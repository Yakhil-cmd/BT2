### Title
Webhook signature is verified against an org derived from the payload, but handlers act on repository/commit data never bound to that org — cross-repository forged commit statuses and sync triggers ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC signature against using `repository_owner`, a value read out of the untrusted JSON payload itself (`repository.owner.login`, falling back to `organization.login`). [1](#0-0) [2](#0-1)  Nothing then verifies that the resource the handlers actually operate on (a repository named by `repository.full_name`, or in the `status` event's case, a commit looked up **globally by sha with no repository scoping at all**) belongs to that same organization. This is exactly the class of bug described in the referenced report: a field that is acted upon is never covered by the binding that was actually verified (there, votes vs. delegation references; here, the org whose secret validated the signature vs. the repository/commit the handler mutates).

### Finding Description
`verify_signature` calls `Shipit.github(organization: repository_owner)` and then checks the raw POST body's HMAC against that organization's configured `webhook_secret`. [1](#0-0)  `repository_owner` is derived purely from attacker-controlled JSON fields inside the very payload being verified. [2](#0-1) 

Once the signature validates (i.e., the payload was signed with *some* organization's secret that Shipit is configured to trust), the individual event handlers use *other, independent* fields of the same payload to decide what to write to:

- `Handler#repository_name` reads `payload.dig('repository', 'full_name')`, a separate JSON field from `repository.owner.login` used for signature selection — nothing enforces that `full_name`'s owner segment matches `repository_owner`. [3](#0-2) 
- `StatusHandler#process` is worse: it does not use `repository`/`stacks` scoping at all. It looks up `Commit.where(sha: params.sha)` **across the entire database** and calls `commit.create_status_from_github!(params)` on whatever commit matches that sha, regardless of which repository/org it belongs to. [4](#0-3) 
- `PushHandler#process` similarly trusts `repository_name` (i.e., `full_name`) from the payload to select stacks to sync, independent of the org used to validate the signature. [5](#0-4) 
- `CheckSuiteHandler#process` likewise resolves `stacks` via `repository_name` (inherited from `Handler`) and schedules check-run refreshes for any matching commit. [6](#0-5) 

So the binding actually enforced is: **"signature was produced with secret(X) where X = payload.repository.owner.login"**, while the binding the code needs (and never checks) is: **"the repository/commit being written belongs to organization X."** These are only equal by convention (a legitimate GitHub webhook naturally has `repository.owner.login` matching `repository.full_name`'s owner segment, and `sha` naturally belonging to that repo) — nothing in the code enforces that equality for a forged request.

### Impact Explanation
In a Shipit deployment configured with more than one GitHub organization (each with its own `webhook_secret` in `Shipit.github(organization:)` config), anyone who legitimately possesses the `webhook_secret` for their own, lower-privileged organization (e.g., an org admin who configured their own org's GitHub webhook integration into this shared Shipit instance) can craft an arbitrary JSON payload, sign it with their own org's secret, and set `repository_owner`-related fields to their own org while setting `repository.full_name` (or, for `status` events, simply guessing/observing another repo's commit `sha`) to point at a **different organization's repository/commit**. This breaks the "organization authenticated versus the repository that is written" trust boundary and enables:
- Forging a `status` webhook that injects a fabricated `success` CI status onto a specific commit sha of a repository they don't own, potentially satisfying deploy-safety checks and enabling an **unauthorized deploy** of that commit on another org's stack.
- Forging `push`/`check_suite` events to trigger sync/check-run refresh jobs against stacks belonging to a different organization (cross-repository writes to Shipit's own data model, e.g. `Commit`/`Status` records, syncing arbitrary shas).

This matches the required impact bar: cross-repository writes and an unauthorized deploy.

### Likelihood Explanation
This requires the deployment to configure more than one GitHub organization in Shipit (a documented, supported multi-tenant configuration), and requires the attacker to legitimately hold one such organization's `webhook_secret` (something an org admin configuring their own GitHub App/webhook integration would naturally have) — i.e., an "unprivileged" attacker relative to the *other* organizations' repositories, not relative to Shipit's admin or GitHub credentials. No GITHUB_TOKEN, `api_clients_secret`, or Shipit session is required. For the `status` handler specifically, the attacker doesn't even need a matching `repository.full_name` — the global, unscoped `Commit.where(sha:)` lookup makes exploitation trivial for any commit sha they can observe (commit shas of tracked stacks are typically visible on Shipit's public-ish stack pages).

### Recommendation
- In `WebhooksController`, after verifying the signature, re-derive the organization/repository binding and enforce it explicitly: confirm that `repository.full_name`'s owner segment equals the `repository_owner` (or `organization.login`) used to select the verifying secret, and reject the request otherwise.
- In `Shipit::Webhooks::Handlers::Handler#stacks`/`repository_name`, and specifically in `StatusHandler#process`, scope lookups to the repository/organization that was cryptographically verified rather than trusting `payload.dig('repository', 'full_name')` or an unscoped `Commit.where(sha:)` query. Pass the verified organization/repository context from the controller into each handler and filter commits/stacks by it.
- Add regression tests asserting that a validly-signed webhook for organization A cannot mutate commits/stacks belonging to organization B.

### Proof of Concept
1. Shipit is configured with two GitHub orgs, `org-a` and `org-b`, each with its own `webhook_secret`.
2. Attacker administers `org-a`'s GitHub App/webhook config and thus knows `org-a`'s `webhook_secret`.
3. Attacker observes (e.g., via Shipit's public stack/commit pages) a commit `sha` belonging to a stack under `org-b/some-repo` that is pending/blocked by a failing CI status.
4. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<org-b commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/some-repo" }
}
```
   signed (`X-Hub-Signature`) with `org-a`'s `webhook_secret`.
5. `verify_signature` resolves `Shipit.github(organization: "org-a")` and validates successfully. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `org-b` commit (no ownership check), and calls `create_status_from_github!`, injecting a fabricated `success` status onto `org-b`'s commit. [4](#0-3) 
7. If this status is one `org-b`'s stack relies on for deploy safety, the forged status can enable an unauthorized deploy of that commit.
