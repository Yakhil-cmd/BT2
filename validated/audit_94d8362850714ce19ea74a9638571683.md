### Title
Uncaught exception in AA trigger execution can permanently halt AA processing after MCI stabilization, crash-looping the node on restart - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `handleTrigger()` — the function that executes an AA's oscript in response to a trigger unit posted by any unprivileged user/AA — contains multiple bare `throw Error(...)` statements that are not wrapped in any try/catch along the call path from `main_chain.js`/`writer.js` up through `network.js`. Because AA trigger execution is invoked *after* the triggering unit's MCI has already been marked stable and committed to the DB, an uncaught exception here reproduces the Sherlock M‑8 bug class: a single crafted, attacker-reachable trigger can put the node into a state that crashes the whole process and, because the un-processed `aa_triggers` row is never deleted, **re-crashes on every restart** until the DB is manually patched.

### Finding Description
AA triggers are processed by `handleAATriggers()`, invoked synchronously right after an MCI is marked stable, both during normal operation and on node startup: [1](#0-0) [2](#0-1) 

The AA-triggers table row for a given `(mci, unit, address)` is deleted only *after* `handleTrigger()` calls back into `handlePrimaryAATrigger`'s success continuation: [3](#0-2) 

`handleTrigger()` itself contains several unconditional `throw Error(...)` statements that are reachable while evaluating attacker-supplied AA definitions/oscript and trigger content, e.g.: [4](#0-3) [5](#0-4) [6](#0-5) 

None of these `throw` sites is caught anywhere in the `handlePrimaryAATrigger` → `handleTrigger` → `handleSecondaryTriggers`/`sendUnit` chain, nor in `handleAATriggers()`'s `async.eachSeries` wrapper: [7](#0-6) 

An uncaught exception thrown asynchronously here is not caught by any `try/catch`; it becomes a Node.js `uncaughtException`, which `network.js`'s global handler explicitly re-throws to intentionally kill the process: [8](#0-7) 

The crucial parallel to the Sherlock report: because the triggering unit's MCI was already committed as stable *before* `handleAATriggers()` runs (`stabilizeMci` commits the transaction, then calls the trigger handler), the `aa_triggers` row for the poisoned trigger persists in the database. On the next boot, `startRelay()` calls `await aa_composer.handleAATriggers();` "in case anything's left from the previous run" — which immediately re-reads and re-executes the exact same trigger, hitting the same unguarded throw and crashing again. This is a self-perpetuating restart-crash loop identical in mechanism to the reported Solana inbound-tracker panic: an unvalidated/edge-case condition inside a "trusted-invariant" code path halts an entire class of protocol processing (here, all AA-trigger execution network-wide) indefinitely, with no automatic recovery, because the very state that triggers the crash cannot be un-committed.

### Impact Explanation
If an attacker (any user who can post a unit addressed to an AA, or any AA author) can construct an AA definition/trigger combination that reaches one of these unguarded `throw` sites, they can crash every full node processing that MCI. Because the offending `aa_triggers` row remains un-deleted, restarting simply reproduces the crash — halting stabilization of all subsequent units and all AA execution network-wide (not just for that one AA), i.e. "a network unable to confirm new units," which is explicitly an accepted impact class for this analysis. This is a Critical/High class of denial of service against the whole DAG, not just a single AA, since MC advancement is blocked while trigger execution is stuck in a crash loop.

### Likelihood Explanation
Likelihood depends on whether an unprivileged AA author can actually construct inputs (e.g., a base AA with recursive/self-referencing secondary triggers, or a base_aa configuration combined with bouncing state) that reach the internal-invariant `throw` statements (`"secondary triggers while bouncing"`, `"response_unit with bouncing a secondary AA"`, `"bad AA definition"`, `"assocBalances and bAir do not match"`). These are guarded as "should never happen" invariants, suggesting the developers already assume normal AA validation (`validateAA`) prevents reaching them — similar to how the Solana codebase assumed tx hashes would always be 64 bytes before the fix. I was not able to fully confirm within the available exploration budget whether `validateAA`/`validateAATrigger` in `validation.js` closes every path to these throws, or whether some combination of nested `base_aa` redirection, secondary-trigger fan-out, and bounce state can still reach them at runtime (as opposed to at validation time). This is the main open uncertainty in this analysis.

### Recommendation
1. Wrap the `handlePrimaryAATrigger` / `handleTrigger` / `handleSecondaryTriggers` execution chain in `aa_composer.js` in a try/catch (or convert internal invariant violations into a graceful `bounce()`/error response) so that any unexpected exception during AA execution does not propagate to an `uncaughtException` and kill the process.
2. Ensure that if an AA response fails unexpectedly, the corresponding `aa_triggers` row is still safely handled (e.g., marked bad or retried with backoff) rather than being left to re-trigger the same crash indefinitely on restart.
3. Audit all `throw Error(...)` statements inside `aa_composer.js` and `formula/evaluation.js` that assume invariants about AA definitions/state and confirm each one is actually unreachable given `validateAA`'s pre-checks; add explicit runtime validation checks (returning bounce/errors) for any that are runtime-reachable from attacker-controlled AA definitions or trigger data.

### Proof of Concept
Not independently reproduced — this would require constructing a concrete AA definition (e.g., nested `base_aa` + secondary-trigger recursion combined with a bounce) that passes `validateAA` static validation in `validation.js` but reaches one of the unguarded `throw Error(...)` statements identified in `aa_composer.js` (lines 424, 1674, 1719) during actual trigger execution, then observing that the node process crashes via the `network.js` `uncaughtException` handler and re-crashes identically on restart because the `aa_triggers` row is never deleted. Confirming exact reachability requires deeper testing of the AA validator (`validateAA`/`validateAATrigger`) than was possible within this investigation's scope.
