### Title
Webhook signature verification is bound to an attacker-controlled organization field while events act on an independently attacker-controlled repository field, enabling cross-tenant webhook forgery (unauthorized status/merge/deploy state injection) — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which organization's secret* to validate a webhook against using one payload field (`repository.owner.login`, falling back to `organization.login`), while every `Webhooks::Handlers::Handler` subclass resolves *which repository/stack the event actually mutates* using a completely different, independently-controlled payload field (`repository.full_name`). Because the HMAC only proves the request was signed by whatever organization's secret matches the first field, it proves nothing about the second field. Combined with the fact that `GithubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization, an unauthenticated attacker can post a forged event that "authenticates" as any org lacking a configured secret while acting on the stack/repository of a completely different, unrelated organization.

### Finding Description
`WebhooksController#verify_signature` computes the org used for signature verification from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — attacker-controlled JSON in the raw POST body. `Shipit.github(organization: repository_owner)` then looks up that organization's `GithubApp` config and its `webhook_secret`: [3](#0-2) 

Critically, `verify_webhook_signature` short-circuits to `true` if that organization has no `webhook_secret` configured at all (`return true unless webhook_secret`). This means for any organization onboarded to a multi-tenant Shipit instance without a configured secret (a supported, non-error configuration), signature verification is a no-op.

Once verification passes (via a real signature *or* via a secret-less org), `WebhooksController#create` dispatches the raw parsed body to handlers unmodified: [4](#0-3) 

Every handler resolves its target stack(s) using a *different* field from the same payload — `repository.full_name` — with no cross-check against the field used for signature verification: [5](#0-4) 

For example, `PushHandler` uses that resolved scope to call `stack.sync_github`: [6](#0-5) 

and the `status` handler (exercised in `test ":state create a Status for the specific commit"`) creates a `Status` record directly from attacker-supplied `state`/`context`/`description` fields for whatever commit/repo `repository.full_name` resolves to: [7](#0-6) 

**The broken binding, stated as an equality that should hold but doesn't:**
`organization whose secret authenticated the request` (derived from `repository.owner.login` / `organization.login`) `== organization/repository that the dispatched handler actually mutates` (derived independently from `repository.full_name`).

Before the attack: these two fields are always populated consistently by real GitHub webhook deliveries, so the invariant silently holds and is never enforced in code. After the attack: an unauthenticated party crafts a payload where `repository.owner.login` = an organization with no `webhook_secret` configured on this Shipit instance (satisfies the bypassed signature check) while `repository.full_name` = `<victim-org>/<victim-repo>` — an entirely different, unrelated organization/stack that is also hosted on the same Shipit instance. The forged event is processed as if it were a legitimate GitHub delivery for the victim stack.

### Impact Explanation
This breaks the deployment-trust binding between "the organization whose webhook credential was checked" and "the repository the engine actually acts on," letting an outsider inject fabricated GitHub state (commit statuses, pull_request/review-stack transitions, push-triggered `GithubSyncJob`s) into a victim organization's stack without ever needing that victim org's secret, an `ApiClient` token, or a Shipit session/login. Concretely:
- Forged `status` events can inject a fake passing/failing CI status for a required check (`required_statuses`/`blocking_statuses` used in merge/deploy gating) on an arbitrary commit of a victim stack, potentially unblocking an unauthorized merge or deploy.
- Forged `pull_request` events (`labeled`/`unlabeled`/`reopened`) can archive/unarchive review stacks or otherwise change PR/review-stack state for a victim repository.
- Forged `push` events can trigger `GithubSyncJob` for a victim stack, which, combined with `continuous_deployment`, can influence when the next deploy is dispatched.

This matches the "unauthorized deploy, rollback or merge" / cross-repository-writes category of impact defined in scope.

### Likelihood Explanation
Exploitability depends on at least one organization registered with this Shipit instance having no `webhook_secret` configured — a normal, documented, non-error state (`@webhook_secret = @config[:webhook_secret].presence`, no validation that it must be present) — which is plausible in any real multi-tenant deployment during onboarding or for internal/low-risk orgs. No credentials, tokens, sessions, or GitHub App keys are required by the attacker; only network access to the public `/webhooks` endpoint and knowledge of another onboarded organization's login/repository full name (both are public GitHub information).

### Recommendation
Enforce that the organization used to select and verify the webhook signature is the *same* organization the event claims to act upon: derive `repository_owner` and the handler's `repository_name`/stack-resolution from the same trusted, verified value, and reject payloads where `repository.full_name`'s owner segment does not match the verified `repository_owner`. Additionally, require `webhook_secret` to be present for every configured organization (fail closed rather than `return true unless webhook_secret`), so an org without a secret cannot be used to bypass verification for itself or, by extension, for any other org's repository.

### Proof of Concept
1. Assume Shipit is configured for at least two organizations: `victim-org` (has stacks, has a configured `webhook_secret`) and `no-secret-org` (onboarded but with no `webhook_secret` set — a supported configuration per `lib/shipit/github_app.rb`).
2. Attacker (no session, no token, no secret) sends:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "<required-check-context>",
  "description": "forged",
  "target_url": "https://attacker.example",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "no-secret-org" }
  }
}
```
3. `WebhooksController#verify_signature` computes `repository_owner = "no-secret-org"`, loads that org's `GithubApp`, and `verify_webhook_signature` returns `true` unconditionally because `no-secret-org` has no `webhook_secret` (per `lib/shipit/github_app.rb:76-77`).
4. The `status` handler resolves the target using `repository.full_name = "victim-org/victim-repo"` (per `app/models/shipit/webhooks/handlers/handler.rb:36-38`) and creates/updates a `Status` for the specified commit in `victim-org`'s stack, exactly as demonstrated by the existing test `":state create a Status for the specific commit"` — except here the attacker supplied fabricated `state`/`context`/`description` values for a repository unrelated to the organization that "authenticated" the request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
