### Title
Cross-organization Team hijack via `github_id`-only lookup in `MembershipHandler` grants `Shipit.github_teams` authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Shipit::Team` solely by `github_id`, never validating that `params.organization.login` matches the `organization` already stored on that row. In a multi-organization Shipit deployment (`secrets.github` keyed by multiple orgs, each with its own `webhook_secret`), a webhook that is correctly signed by organization B's secret can still mutate a `Team` row that legitimately belongs to organization A, adding an attacker-controlled user to it via `team.add_member(member)`.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`organization_that_signed_the_webhook (params.organization.login, verified via Shipit.github(organization: repository_owner).verify_webhook_signature)` == `team.organization (the org that actually owns the Team row matched by github_id)`.

Code path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from `params.dig('organization', 'login')` for membership events (no `repository` key present), then calls `Shipit.github(organization: repository_owner)` and verifies the HMAC signature against **that organization's own `webhook_secret`** (`lib/shipit/github_app.rb:76-83`). This only proves the payload was sent by *some* legitimate org configured in `secrets.github` — the attacker's own org — not that it concerns that org's own data.
- `MembershipHandler#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`) does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }`. The `organization:` assignment inside the block only runs **on creation**; if a `Team` row already exists with that `github_id` (created at boot for a *different* org via `Shipit.github_teams` / `Team.find_or_create_by_handle`, `app/models/shipit/team.rb:18-27`), `find_or_create_by!` returns the existing record untouched, and `params.organization.login` is silently ignored.
- `process` then calls `team.add_member(member)` (`app/models/shipit/webhooks/handlers/membership_handler.rb:23-28`, `app/models/shipit/team.rb:41-43`), inserting the attacker-controlled `User` into that pre-existing, cross-org team's membership.
- `Shipit.github_teams` (`lib/shipit.rb:256-258`) is computed from `github.oauth_teams` of the **default/primary** organization only, so a `Team` row for the primary org is exactly what governs `User#authorized?` (`app/models/shipit/user.rb:80-82`). GitHub team IDs are globally unique integers assigned by GitHub across all orgs, so an attacker who is a member/admin of a secondary org onboarded onto the same Shipit instance can craft a `membership` webhook naming any known/guessable primary-org team `github_id`.

None of the existing guards stop this: `verify_signature` only checks that *an* onboarded org's secret matches (it succeeds for the attacker's own org, by design); `drop_unhandled_event` doesn't apply since `membership` is a handled event; the `ExplicitParameters` schema only validates types/presence, not cross-field consistency between `organization.login` and the `team` being mutated; there is no `require_permission!`/`force_github_authentication` on the webhooks endpoint since webhooks are meant to be unauthenticated aside from signature verification.

### Impact Explanation
A user with `added` membership in a completely unrelated, attacker-controlled GitHub organization (that is nonetheless configured as one of the multiple organizations in this Shipit instance's `secrets.github`) can silently join a `Shipit::Team` belonging to the primary organization. If that team's `github_id` is one of `Shipit.github_teams`, the attacker's `Shipit::User#authorized?` flips to `true`, granting full UI/API access to the Shipit instance — stacks, deploys, rollbacks, task logs — for repositories under the primary organization, i.e. cross-tenant privilege escalation. This matches the "High: escalation into `Shipit.github_teams` authorization" (and arguably edges toward Critical given the resulting unauthorized deploy/rollback capability) category explicitly listed in scope. The attack is repeatable for any known/guessable team `github_id` and is not limited to a single request.

### Likelihood Explanation
This requires a genuine multi-organization Shipit deployment where more than one GitHub organization is configured under `secrets.github`, each with a distinct `webhook_secret` — i.e., the attacker must control (or be a member with webhook-configuring rights of) one of those onboarded secondary organizations, and know or guess the `github_id` of a `Team` already persisted for the primary org (obtainable e.g. via GitHub's team API if teams aren't strictly private, or via prior reconnaissance). This is a non-trivial but realistic precondition for shared/managed Shipit instances serving multiple organizations, which the engine explicitly supports via its multi-org `secrets.github` schema. Given that precondition, the exploit itself costs a single crafted HTTP POST with a signature the attacker legitimately possesses for their own org.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify on every request (not just at creation) that an existing matching `github_id` record's `organization` equals `params.organization.login`, rejecting/logging a mismatch instead of silently reusing the row.

### Proof of Concept

# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "membership webhook from org B cannot add a member to a team owned by org A" do
  # Precondition: multi-org secrets.github with org 'shopify' (primary, in Shipit.github_teams)
  # and org 'attacker-org' (secondary, independently configured with its own webhook_secret).
  target_team = shipit_teams(:shopify_developers) # organization == 'shopify'
  attacker_org_secret = Shipit.github(organization: 'attacker-org').send(:webhook_secret)

  payload = {
    action: 'added',
    team: { id: target_team.github_id, name: target_team.name, slug: target_team.slug, url: target_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'evil-attacker' }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', attacker_org_secret, payload)

  post '/webhooks', params: payload,
       headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => signature,
                  'Content-Type' => 'application/json' }

  assert_response :ok

  attacker = Shipit::User.find_by(login: 'evil-attacker')
  # Binding check (should be false, is currently true — the bug):
  assert_equal 'attacker-org', 'attacker-org' # org that signed the request
  assert_equal target_team.organization, 'shopify' # org that owns the mutated team
  assert_includes target_team.reload.members, attacker # attacker was added to org-A's team
  assert attacker.authorized? # attacker escalated into Shipit.github_teams authorization
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
    end

    def handle
      "#{organization}/#{slug}"
    end

    def add_member(member)
      members.append(member) unless members.include?(member)
