### Title
`provision?` operator-precedence bug lets `provisioning_behavior_allow_with_label?`/`prevent_with_label?` create Review Stacks even when `review_stacks_enabled` is `false` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` was clearly intended to require `repository.review_stacks_enabled` for every provisioning mode, but Ruby's `&&`/`||` precedence makes `review_stacks_enabled` gate only the `allow_all` disjunct. The `allow_with_label` and `prevent_with_label` disjuncts are unconditionally reachable regardless of `review_stacks_enabled`, so an attacker who controls their own PR's labels (or simply opens a PR at all, in the `prevent_with_label` case) can cause a `Stack` to be created and queued for provisioning even though the operator explicitly disabled review-stack provisioning for the repository.

### Finding Description
The broken binding, as intended: `repository.review_stacks_enabled == true` must hold for **any** stack to be created by `OpenedHandler`, independent of `provisioning_behavior`. As implemented:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So `review_stacks_enabled` only constrains the first disjunct. If an operator sets `provisioning_behavior` to `allow_with_label` or `prevent_with_label` while leaving (or setting) `review_stacks_enabled = false` — a state fully reachable via the independent `review_stacks_enabled` checkbox and `provisioning_behavior` select on the settings form [2](#0-1)  — the flag has no effect on those two modes.

Exploit path: `process` calls `respond_to_pull_request_opened?` → `provision?`; if true, `ReviewStackAdapter#find_or_create!` creates and enqueues a `Stack` [3](#0-2) , and `create!` builds the stack from attacker-controlled `pull_request.head.ref`/`number` and queues it for provisioning [4](#0-3) .

`pull_request_has_provisioning_label?` reads only the label names from the attacker's own PR payload (`pull_request["labels"]`), which the attacker fully controls on a fork/repo they own [5](#0-4) . In the `allow_with_label` mode, the attacker must know/guess the `provisioning_label_name` (an operator-configured string, potentially guessable/default) and self-apply it. In the `prevent_with_label` mode the bug is worse: no label is even required — a plain PR (no matching label) already satisfies `!pull_request_has_provisioning_label?`, so *any* opened PR against a `prevent_with_label` repository with `review_stacks_enabled=false` provisions a stack.

None of the listed guards intercept this: `verify_signature`/webhook signature checks only authenticate that GitHub sent the payload for the attacker's own registered repository — they don't validate the semantic gating logic inside `provision?`. `ExplicitParameters` schema only validates payload shape, not business rules. There is no test in `opened_handler_test.rb` covering `provisioning_enabled: false` combined with `allow_with_label`/`prevent_with_label`, confirming the gap was unnoticed (the only `provisioning_enabled: false` test uses `allow_all`, which is unaffected) [6](#0-5) .

### Impact Explanation
When triggered, a `Shipit::Stack`/`ReviewStack` record is created and pushed onto `Shipit::ReviewStackProvisioningQueue`, which drives the host application's `ProvisioningHandler` to allocate real infrastructure (e.g., Kubernetes namespace, Heroku app) and subsequently deploy/build the attacker's branch — this is an unauthorized deploy/provisioning action against the operator's infrastructure, triggered purely by the PR author's own repository/label metadata. The blast radius is scoped to repositories where the operator has chosen `allow_with_label`/`prevent_with_label` with `review_stacks_enabled` unset/false — but for those repositories it is a full bypass of the intended opt-in/off-switch, matching "unauthorized deploy" under Critical impact. It is repeatable per PR/repository matching that misconfiguration.

### Likelihood Explanation
Requires the repository to be registered in Shipit with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` and `review_stacks_enabled` left/set to `false` — a configuration reachable through the normal, unvalidated settings form (the two fields are independent, no model validation couples them) [7](#0-6) . Given `review_stacks_enabled` is presented in the UI as "Dynamically provision stacks for Pull Requests?" and provisioning behavior as a separate, always-visible dropdown, it's plausible for operators to toggle behavior modes while intending the enabled checkbox to remain the master switch — exactly the assumption this bug violates. Attacker cost is a single PR (and, for `allow_with_label`, a label name that may be guessable or discoverable, e.g. shown in public repo settings/PR templates). No credentials, no privileged role required.

### Recommendation
Fix the operator precedence so `review_stacks_enabled` is required by every branch:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Apply the same fix to the equivalent logic in `reopened_handler.rb`'s `unarchive?` (`app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb:70-75`), which has the identical precedence bug.

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:

```ruby
test "does NOT create stacks for allow_with_label repos when review_stacks_enabled is false, even with matching label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # binding under test: review_stacks_enabled == false
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" } # attacker self-applies label

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end

test "does NOT create stacks for prevent_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [] # no label needed - attacker just opens PR

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```

Before the fix, both assertions fail (`Shipit::Stack.count` increases by 1), proving that `review_stacks_enabled == false` does not prevent stack creation — confirming the broken equality `provision? == review_stacks_enabled && <mode logic>` does not hold in the current code.
