### Title
Stack-scoped API token authorization bypass in `Api::CCMenuController#stack` allows cross-stack CCMenu status disclosure - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces per-token stack scoping by having `stacks` fall back to `Stack.where(id: current_api_client.stack_id)` when an `ApiClient` is bound to a specific stack, and by resolving the requested stack through that scoped relation (`stacks.from_param!`). `Api::CCMenuController` overrides the private `stack` helper and resolves the requested stack directly from the global `Stack.from_param!(params[:stack_id])`, bypassing the scoping relation entirely. This breaks the binding "stack a token authorizes == stack it touches": a stack-scoped `read:stack` token can be used to fetch CCMenu status/build info for any stack in the installation, not just the one it was issued for.

### Finding Description
`ApiClient` supports being scoped to a single stack (`belongs_to :stack, optional: true`), and `BaseController` implements the enforcement of that scope: [1](#0-0) 

`require_permission :read, :stack` (used by `CCMenuController`) only checks that the token's `permissions` array contains `read:stack`; it never checks the stack-id scope itself: [2](#0-1) 

The actual enforcement of "this token may only see its own stack" happens exclusively through the `stacks`/`stack` helper chain in `BaseController`. `CCMenuController` redefines `stack` to bypass that chain and resolve the stack globally: [3](#0-2) 

Every other consumer of `stack` in this hierarchy (e.g. `Api::StacksController`) goes through the scoped `stacks` relation, so `CCMenuController` is the outlier that silently drops the per-token stack restriction while still declaring (and passing) the generic `read:stack` permission check.

### Impact Explanation
Holding a `read:stack` token that was minted/scoped for one stack (`ApiClient#stack_id` set) is sufficient to read `#show` (CCMenu XML status, `lastBuildStatus`, `lastBuildLabel`, `webUrl`, activity, lock status) for **any** stack on the Shipit instance by supplying a different `stack_id` in the request, since `CCMenuController#stack` never consults `current_api_client.stack_id`. This crosses the "stack a token authorizes vs. stack it touches" trust boundary and constitutes unauthorized disclosure of stack/build state for repositories the token holder was never granted visibility into — matching the "unauthenticated/unauthorized read of stack state" High-impact class, since the scoping mechanism (the only authorization gate distinguishing "my stack" from "any stack") is entirely inert for this endpoint.

### Likelihood Explanation
Any holder of a stack-scoped API token (a legitimate, lower-privilege credential intentionally restricted to one stack) can trigger this by simply changing the `stack_id`/`id` path parameter on the CCMenu endpoint — no additional exploitation primitives, timing, or race conditions are required. The only precondition is possession of a stack-scoped token with `read:stack`, which is precisely the class of credential this scoping feature exists to constrain.

### Recommendation
Remove `CCMenuController`'s private `stack` override, or reimplement it using the scoped `stacks.from_param!` (as `BaseController#stack` already does), so CCMenu lookups honor `current_api_client.stack_id` the same way every other API controller does:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. Create (e.g. via console/fixture) an `ApiClient` scoped to `stack_a` (`stack_id: stack_a.id`, `permissions: ['read:stack']`), and obtain its `authentication_token`.
2. Issue a request against a different stack (`stack_b`) using that token:
   `GET /api/stacks/stack_b_owner/stack_b_name/staging/ccmenu.xml?token=<stack_a-scoped-token>`
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!`, the request succeeds (`200 OK`) and returns `stack_b`'s CCMenu XML (build status, last build label, lock state), even though the token is bound only to `stack_a`.
