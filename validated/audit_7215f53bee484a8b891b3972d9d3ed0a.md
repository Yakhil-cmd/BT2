Based on my investigation, I found a genuine analog: the Agave vote program's `pending_delegator_rewards` accumulator (SIMD-0123) is incremented via `add_pending_delegator_rewards` on every `DepositDelegatorRewards` instruction, but I could not locate any code path that subtracts/clears this field when the block-reward portion is actually paid out to delegators during epoch reward distribution.

### Title
`pending_delegator_rewards` is never decremented when block rewards are distributed, permanently over-reserving vote account withdrawals - (File: `programs/vote/src/vote_state/handler.rs`)

### Summary
The vote program tracks a `pending_delegator_rewards` field on `VoteStateV4` that any unprivileged account can increase by calling the permissionless `DepositDelegatorRewards` instruction. This field is consumed as a reservation that blocks withdrawals via `Withdrawable`-analogous logic in `withdraw()`, but no code path subtracts from it after the reward is actually distributed to stake accounts.

### Finding Description
`add_pending_delegator_rewards` in `programs/vote/src/vote_state/handler.rs` only ever adds to the field: [1](#0-0) 

It is called from `deposit_delegator_rewards`, which is reachable by any signer (the "source" account) via the permissionless `DepositDelegatorRewards` instruction — no privileged withdrawer signature is required, only the depositing source account must sign: [2](#0-1) 

During epoch reward calculation/distribution, `calculate_block_reward` reads `pending_delegator_rewards` from the vote state view to compute how much of it should be paid out to each delegating stake account for the epoch, and the value is used again on every subsequent epoch boundary recalculation: [3](#0-2) 

Rewards are then paid to stake accounts and capitalization/sysvar bookkeeping is updated in `distribute_epoch_rewards_in_partition` and `store_stake_accounts_in_partition`: [4](#0-3) [5](#0-4) 

However, none of these distribution paths call back into the vote account to reduce `VoteStateV4::pending_delegator_rewards`. Meanwhile, `withdraw()` in `programs/vote/src/vote_state/mod.rs` treats `pending_delegator_rewards` as an un-withdrawable reserve on top of rent-exempt minimum, and blocks full account closure entirely while it is nonzero: [6](#0-5) 

This directly mirrors the reported bug class: a "pending" counter is incremented on deposit but is not decremented on the corresponding "consumption" event (withdrawal/distribution), so it monotonically grows and permanently misrepresents the true reserved/available balance.

### Impact Explanation
Because `pending_delegator_rewards` never decreases after the block-reward-eligible amount is distributed to stakers each epoch, the value keeps growing with every `DepositDelegatorRewards` call, while the actual lamports have already left the vote account (transferred to stake accounts as part of `stake_reward.block_reward`). This causes:
- The withdrawer's legitimately withdrawable balance is permanently reduced by amounts that have already been paid out, effectively locking increasing amounts of the withdrawer's own lamports in the vote account forever (funds become stuck / unspendable, an unsigned/unintended fund-lockup which is a lasting on-chain state corruption).
- `withdraw()`'s full-account-close path (`InstructionError::InsufficientFunds` guard at `pending_delegator_rewards > 0`) can never succeed again once any deposit has occurred and been fully distributed, permanently disabling vote-account closure — a denial-of-service on a previously-available operation.
- Since the value is also fed into `calculate_block_reward`'s numerator every epoch (clamped by `.min(pending_delegator_rewards)`), if distribution logic elsewhere assumes the stale, ever-growing counter reflects real undistributed rewards, this skews reward-share math relative to the block-revenue-sharing design intent (SIMD-0123), representing a form of stake/reward accounting corruption reachable purely by submitting `DepositDelegatorRewards` transactions.

### Likelihood Explanation
`DepositDelegatorRewards` is a permissionless instruction — any account holding lamports and able to sign can invoke it against any V4 vote account without needing the vote account's authorization, as shown by `deposit_delegator_rewards` requiring only the source signer: [7](#0-6) 
Every such call increments `pending_delegator_rewards` unconditionally (as long as it doesn't overflow), and reward distribution runs automatically every epoch for validators with `block_revenue_sharing` enabled. No special privileges, timing, or malicious-leader behavior are needed — a single ordinary transaction sender can trigger the accumulation, and normal cluster epoch processing triggers the (missing) decrement path. This makes the bug trivially and repeatedly reachable.

### Recommendation
When `store_stake_accounts_in_partition`/`build_updated_stake_reward` distributes `partitioned_stake_reward.block_reward` amounts sourced from a vote account's `pending_delegator_rewards`, the corresponding vote account's `pending_delegator_rewards` field must be reduced (e.g., via a `sub_pending_delegator_rewards` counterpart to `add_pending_delegator_rewards`) by the total block reward amount actually distributed for that vote account in that epoch, keeping it consistent with the real reserved/undistributed lamports still held by the vote account. This should be applied transactionally with the same store operation that mutates stake accounts, to avoid consensus-divergence between validators that might otherwise compute inconsistent decrements.

### Proof of Concept
1. Create a V4 vote account with `block_revenue_sharing` active.
2. Any account calls `VoteInstruction::DepositDelegatorRewards { deposit: N }` (permissionless, per `deposit_delegator_rewards` at `programs/vote/src/vote_state/mod.rs:935-988`), setting `pending_delegator_rewards = N`.
3. Let an epoch boundary pass with `block_revenue_sharing` enabled; `calculate_block_reward` computes and `store_stake_accounts_in_partition` distributes `block_reward` lamports (up to `N`) to delegators — lamports leave the vote account into stake accounts, confirmed by `test_store_stake_accounts_in_partition` behavior in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`.
4. Inspect the vote account's `pending_delegator_rewards` post-distribution — it remains `N` (unchanged), even though the lamports have been paid out and are no longer present in the vote account for that purpose.
5. Attempt `Withdraw` of the vote account's full balance (`programs/vote/src/vote_state/mod.rs:1084-1121`) — it is rejected with `InstructionError::InsufficientFunds` due to the stale nonzero `pending_delegator_rewards`, even though the actual reward amount that field was meant to reserve has already left the account.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }

                block_reward_lamports_burned,

        // increase total capitalization by the distributed rewards
        self.capitalization
            .fetch_add(stake_reward_lamports_minted, Relaxed);

        // decrease total capitalization by burned block rewards
        self.capitalization
            .fetch_sub(block_reward_lamports_burned, Relaxed);

        // decrease distributed capital from epoch rewards sysvar
        self.update_epoch_rewards_sysvar(
            stake_reward_lamports_minted + stake_reward_lamports_burned,
            block_reward_lamports_distributed + block_reward_lamports_burned,
        );

        // update reward history for this partitioned distribution
        self.update_reward_history_in_partition(&updated_stake_rewards);

        let metrics = RewardsStoreMetrics {
            pre_capitalization,
            post_capitalization: self.capitalization(),
            total_stake_accounts_count: partition_rewards.all_stake_rewards.num_rewards(),
            total_num_partitions: partition_rewards.partition_indices.len(),
            partition_index,
            store_stake_accounts_us,

    fn store_stake_accounts_in_partition(
        &self,
        partition_rewards: &StartBlockHeightAndPartitionedRewards,
        partition_index: u64,
    ) -> DistributionResults {
        let feature_snapshot = self.feature_set.snapshot();
        // Name intentionally doesn't match -- "adjust delegations for rent" is
        // part of relaxing post-exec min balance checks.
        let adjust_delegations_for_rent = feature_snapshot.relax_post_exec_min_balance_check;
        let use_fixed_point_stake_math = feature_snapshot.upgrade_bpf_stake_program_to_v5_1;

        let mut stake_reward_lamports_minted = 0;
        let mut stake_reward_lamports_burned = 0;
        let mut block_reward_lamports_distributed = 0;
        let mut block_reward_lamports_burned = 0;
        let indices = partition_rewards
            .partition_indices
            .get(partition_index as usize)
            .unwrap_or_else(|| {
                panic!(
                    "partition index out of bound: {partition_index} >= {}",
                    partition_rewards.partition_indices.len()
                )
            });
        let mut updated_stake_rewards = Vec::with_capacity(indices.len());
        let stakes_cache = self.stakes_cache.stakes();
        let stakes_cache_accounts = stakes_cache.stake_delegations();
        let stake_history = stakes_cache.history();
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        let rent = &self.rent_collector.rent;
        for index in indices {
            let partitioned_stake_reward = partition_rewards
                .all_stake_rewards
                .get(*index)
                .unwrap_or_else(|| {
                    panic!(
                        "partition reward out of bound: {index} >= {}",
                        partition_rewards.all_stake_rewards.total_len()
                    )
                })
                .as_ref()
                .unwrap_or_else(|| {
                    panic!("partition reward {index} is empty");
                });
            let stake_pubkey = partitioned_stake_reward.stake_pubkey;
            let stake_reward_amount = partitioned_stake_reward.inflation.stake_reward;
            let block_reward_amount = partitioned_stake_reward.block_reward;

            match Self::build_updated_stake_reward(
                self.epoch,
                stake_history,
                new_warmup_cooldown_rate_epoch,
                stakes_cache_accounts,
                partitioned_stake_reward,
                rent,
                adjust_delegations_for_rent,
                use_fixed_point_stake_math,
            ) {
                Ok(stake_reward) => {
                    stake_reward_lamports_minted += stake_reward_amount;
                    block_reward_lamports_distributed += block_reward_amount;
                    updated_stake_rewards.push(stake_reward);
                }
                Err(err) => {
                    error!(
                        "bank::distribution::store_stake_accounts_in_partition() failed for \
                         {stake_pubkey}, {stake_reward_amount} lamports burned: {err:?}"
                    );
                    stake_reward_lamports_burned += stake_reward_amount;
                    block_reward_lamports_burned += block_reward_amount;
                }
            }
        }
        drop(stakes_cache);
        self.store_accounts(
            (self.slot(), &updated_stake_rewards[..]),
            // Reuse the rewards calculation thread pool to parallelize
            // loading the previous versions of the stake accounts.
            Some(crate::bank::rewards_calculation_thread_pool()),
        );
        DistributionResults {
            stake_reward_lamports_minted,
            stake_reward_lamports_burned,
            block_reward_lamports_distributed,
            block_reward_lamports_burned,
            updated_stake_rewards,
        }
    }
