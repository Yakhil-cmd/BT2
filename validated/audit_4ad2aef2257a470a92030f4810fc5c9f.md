## Title
Arbiter contract sharing leaks permanent device pairing secrets (`my_pairing_code`/`peer_pairing_code`) to unrelated wallet cosigners - (File: `arbiter_contract.js`)

## Summary
`shareContractToCosigners()` in `arbiter_contract.js` broadcasts the full, unsanitized arbiter-contract row — including both parties' permanent device-pairing secrets — to every cosigner of the local multisig wallet, even though those cosigners have no legitimate need to know the counterparty's pairing secret. This mirrors the Mattermost issue where a PATCH response returned unsanitized remote-cluster authentication tokens to a caller who should not have received them.

## Finding Description
Each arbiter contract stores `my_pairing_code` and `peer_pairing_code`, which encode a device's *permanent* pairing secret:
`objContract.my_pairing_code = pairingInfo.device_pubkey + "@" + pairingInfo.hub + "#" + pairingInfo.pairing_secret;` [1](#0-0) 

This permanent pairing secret is stored with a near-infinite expiry and, critically, `handlePairingMessage()` auto-adds any sender who presents a matching pairing secret as a confirmed correspondent device — with no additional user confirmation: [2](#0-1) 

When a contract is accepted, `respond()` sets `my_pairing_code` on the contract and then `shareContractToCosigners()` is invoked, which fetches the *entire* contract row via `getByHash` (containing both `my_pairing_code` and `peer_pairing_code`) and sends it unfiltered to every wallet cosigner: [3](#0-2) 

`getAllMyCosigners()` resolves cosigners purely from the shared wallet's signing paths — these devices are co-owners of `my_address`'s wallet, but they have no relationship whatsoever with the contract's counterparty (`peer_address`/`peer_device_address`): [4](#0-3) 

`createSharedAddressAndPostUnit()` similarly calls `shareContractToCosigners(contract.hash)` after the shared address is derived, again propagating the full contract object (with both pairing secrets) to cosigners: [5](#0-4) 

Nowhere is the contract object sanitized before being sent to cosigners — unlike `createAndSend`, which explicitly strips the `cosigners` field before sending to the peer (`delete objContractForPeer.cosigners;`), there is no equivalent stripping of `peer_pairing_code`/`my_pairing_code` before the cosigner broadcast: [6](#0-5) 

## Impact Explanation
Any wallet cosigner (a paired device that merely co-owns the multisig wallet used as `my_address`) receives the counterparty's permanent pairing secret without ever having interacted with that counterparty. Because permanent pairing secrets are accepted with no owner confirmation in `handlePairingMessage`, the cosigner can immediately pair with the counterparty's device and become an auto-confirmed correspondent. From that trusted correspondent position the cosigner can send fully-trusted device protocol messages recognized by `wallet.js`'s `handleMessageFromHub` dispatcher — e.g. spoofed `create_new_wallet`, `create_new_shared_address`, or `arbiter_contract_offer` messages — to the victim who now believes the sender is a legitimate, newly-paired contact. This creates a foothold for subsequent social-engineering-driven, unauthorized fund-moving actions (e.g., tricking the victim into approving a malicious shared address or signing a payment), all stemming from the unintended token disclosure. This is a Medium-severity confidentiality issue analogous to the Mattermost CWE-201 finding, with the ocore-specific difference that the leaked secret is directly consumable to gain unauthorized device trust.

## Likelihood Explanation
Reachable by any legitimate cosigner of a multisig wallet used in an arbiter contract — no special privilege beyond being a normal wallet cosigner is required, and the leak occurs automatically on contract acceptance (`respond`) or shared-address derivation (`createSharedAddressAndPostUnit`), which are routine, expected flows.

## Recommendation
Before calling `shareContractToCosigners`, strip `my_pairing_code` and `peer_pairing_code` (and any other counterpart-specific secrets) from the object sent to cosigners, mirroring the existing `delete objContractForPeer.cosigners` pattern used for the peer-facing message. Cosigners should only receive fields necessary to build/verify the shared address and track contract status (`hash`, `status`, `shared_address`, `unit`, amounts, addresses), not pairing credentials.

## Proof of Concept
1. Alice and Bob co-own a 2-of-2 multisig wallet; Bob is a cosigner device with no relationship to Carol.
2. Alice creates an arbiter contract with Carol (`createAndSend`), and Carol accepts it, causing `respond()` to set/share `my_pairing_code` for Carol and eventually `createSharedAddressAndPostUnit` to run on Alice's side.
3. `shareContractToCosigners(hash)` sends the full contract object — including `peer_pairing_code` (Carol's permanent pairing secret) — to Bob via `device.sendMessageToDevice(device_address, "arbiter_contract_shared", objContract)`.
4. Bob extracts `peer_pairing_code` from the received message and sends a `pairing` device message directly to Carol's hub/pubkey using that secret.
5. Per `handlePairingMessage`, Carol's device automatically adds Bob as a confirmed correspondent with no user interaction, because the permanent pairing secret matches.
6. Bob is now a trusted correspondent of Carol and can send spoofed wallet/contract protocol messages that Carol's client will process as coming from a known device.

function respond(hash, status, signedMessageBase64, signer, cb) {
	cb = cb || function(){};
	getByHash(hash, function(objContract){
		if (objContract.status !== "pending" && objContract.status !== "accepted")
			return cb("contract is in non-applicable status");
		var send = function(authors, pairing_code) {
			var response = {hash: objContract.hash, status: status, signed_message: signedMessageBase64, my_contact_info: objContract.my_contact_info};
			if (authors) {
				response.authors = authors;
			}
			if (pairing_code) {
				response.my_pairing_code = pairing_code;
			}
			device.sendMessageToDevice(objContract.peer_device_address, "arbiter_contract_response", response);

			setField(objContract.hash, "status", status, function(objContract) {
				if (status === "accepted") {
					shareContractToCosigners(objContract.hash);
				};
				cb(null, objContract);
			});
		};
		if (status === "accepted") {
			device.getOrGeneratePermanentPairingInfo(function(pairingInfo){
				var pairing_code = pairingInfo.device_pubkey + "@" + pairingInfo.hub + "#" + pairingInfo.pairing_secret;
				setField(objContract.hash, "my_pairing_code", pairing_code);
				composer.composeAuthorsAndMciForAddresses(db, [objContract.my_address], signer, function(err, authors) {
					if (err) {
						return cb(err);
					}
					send(authors, pairing_code);
				});
			});
		} else {
			send();
		}
	});

function revoke(hash, cb) {
	getByHash(hash, function(objContract){
		if (objContract.status !== "pending")
			return cb("contract is in non-applicable status");
		setField(objContract.hash, "status", "revoked", function(objContract) {
			shareUpdateToPeer(objContract.hash, "status");
			cb(null, objContract);
		});
	});
}

function shareContractToCosigners(hash) {
	getByHash(hash, function(objContract){
		getAllMyCosigners(hash, function(cosigners) {
			cosigners.forEach(function(device_address) {
				device.sendMessageToDevice(device_address, "arbiter_contract_shared", objContract);
			});
		});
	});
}

function getAllMyCosigners(hash, cb) {
	db.query("SELECT device_address FROM wallet_signing_paths \n\
		JOIN my_addresses AS ma USING(wallet)\n\
		JOIN wallet_arbiter_contracts AS wac ON wac.my_address=ma.address\n\
		WHERE wac.hash=?", [hash], function(rows) {
			var cosigners = [];
			rows.forEach(function(row) {
				if (row.device_address !== device.getMyDeviceAddress())
					cosigners.push(row.device_address);
			});
			cb(cosigners);
		});
}
