This confirms the vulnerability by contrast: `CheckSuiteHandler#process` scopes via `stacks.where(branch: ...)` before touching commits [1](#0-0) , and `PushHandler#process` scopes via `stacks.not_archived.where(branch:)` [2](#0-1) , both using the `Handler#stacks` helper which filters by `Repository.from_github_repo_name(repository_name)` [3](#0-2) . `StatusHandler#process`, by contrast, never calls `stacks` or filters by repository at all — it queries `Commit.where(sha: params.sha)` globally [4](#0-3) .

### Title
`StatusHandler#process` writes GitHub statuses onto every `Commit` sharing a `sha` across all repositories/orgs, bypassing repository binding - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a `status` webhook only against the `webhook_secret` of the organization named in the payload's `repository.owner.login` [5](#0-4) , but `StatusHandler#process` never uses that repository information to scope its write — it looks up `Commit.where(sha: params.sha)` engine-wide and mutates every matching row [4](#0-3) . Any organization that can send a validly-signed status webhook for its own repo can therefore write CI status onto a `Commit` belonging to a different organization's `Stack`, as long as the two repos happen to share a commit `sha` (e.g., an identical initial/empty-tree commit, a cherry-picked/rebased commit, or a submodule/fork with shared history).

### Finding Description
The claimed binding is: `organization whose webhook_secret verified the payload (Org A) == organization owning the Commit row mutated (Org B)`. Tracing the code shows this binding is never enforced, so it is broken.

- `WebhooksController#verify_signature` derives `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, confirming only that the payload was HMAC-signed by *some* organization's `webhook_secret` [6](#0-5)  and [7](#0-6) .
- After signature verification, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw JSON payload to `StatusHandler.call` [8](#0-7) .
- `StatusHandler`'s `ExplicitParameters` schema does not even require a `repository` field — only `sha`, `state`, and optional fields [9](#0-8) .
- `process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, an unscoped query across the entire `commits` table, spanning all `Stack`s and organizations [4](#0-3) .
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, which creates a `Status` row scoped to whatever `stack_id` the matched `Commit` happens to belong to [10](#0-9) , and `Status.replicate_from_github!` persists it via `find_or_create_by!(stack_id:, state:, ...)` [11](#0-10) . This status then feeds `Commit#deployable?`/`#blocked?` and CI gating for that stack, and triggers `enable_ci_on_stack`, `schedule_continuous_delivery`, and merge-request processing hooks [12](#0-11) .

By contrast, sibling handlers correctly scope to the requesting repository before touching any `Commit`: `CheckSuiteHandler#process` restricts to `stacks.where(branch: ...)` (where `stacks` is derived from `Repository.from_github_repo_name(repository_name)` in the base `Handler` class) before iterating `stack.commits.where(sha: ...)` [1](#0-0) , and `PushHandler#process` similarly filters `stacks.not_archived.where(branch:)` [2](#0-1) . `Handler#stacks` explicitly exists for this purpose: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none` [3](#0-2) . `StatusHandler` is the outlier that omits this scoping entirely.

**Attacker's exact request**: An attacker who owns/controls Org A's GitHub repository (unprivileged relative to Org B) triggers (or crafts, if their own repo can emit signed status webhooks — e.g. by pushing a commit and having their own CI/GitHub post a `status` event, which GitHub signs with Org A's `webhook_secret`) a `status` webhook payload where `sha` equals a commit hash that also exists in Org B's `Stack#commits` (trivially achievable with the empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any commit cherry-picked/shared across repos). `verify_signature` succeeds because it only checks Org A's secret against Org A's own repo name in the payload. `StatusHandler#process` then finds and mutates the `Commit` row belonging to Org B's stack too.

**Why guards fail**: `verify_signature` binds authentication to "payload's declared repository owner has a valid signature," not to "the mutated row belongs to that repository." `drop_unhandled_event`, `ExplicitParameters` schema validation, and `Repository`/`Stack` model validators never come into play here because the flaw is purely in the unscoped ActiveRecord query — no model-level constraint ties `Commit.sha` uniqueness to a repository.

### Impact Explanation
A single crafted/legitimately-signed status webhook from an attacker-controlled repository can write forged CI status (`success`/`failure`/`pending`/`error`, plus arbitrary `description`, `target_url`, `context`) onto a completely unrelated tenant's `Commit`, provided a matching `sha` exists in that tenant's stack. This can flip `Commit#deployable?` to `true` (enabling an unauthorized deploy of an attacker-influenced status) or force it to `false`/blocked (denial of legitimate deploys), and triggers downstream side effects like `enable_ci_on_stack`, `schedule_continuous_delivery`, and `ProcessMergeRequestsJob` for the victim's stack [12](#0-11) . This is a cross-repository/cross-tenant mutation of another organization's `Commit`/CI state without that organization's authentication, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
The attacker needs: (1) control of a GitHub repository/org with a Shipit-configured `webhook_secret` (i.e., they must be a legitimate but unrelated tenant of the same Shipit instance — not a Shipit operator or victim's maintainer), and (2) a `sha` collision between their repo and the victim's stack's commits. Exploitability is highest against the well-known empty-tree SHA (shared by virtually all git repositories) or through repos with shared/forked history, cherry-picks, or vendored subtree commits — not purely theoretical. The attack is repeatable per matching SHA and costs only a single HTTP POST once signed (or the ability to trigger their own repo's real status events, which GitHub will sign automatically). No live GitHub access is required to demonstrate this — it is fully reproducible in a controller test using two fixture `Stack`s in different simulated orgs sharing a `Commit#sha`.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to the repository that was authenticated, mirroring `CheckSuiteHandler`/`PushHandler`: require `repository.full_name` in the params schema, resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, and restrict the query to `stacks.flat_map(&:commits)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative addition)
test ":status webhook signed for org A must not mutate org B's commit with the same sha" do
  org_a_repo = shipit_repositories(:org_a_repo) # owner login "org-a", webhook_secret "secretA"
  org_b_stack = shipit_stacks(:org_b_stack)     # belongs to repository owned by "org-b"
  shared_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee4904'

  commit_a = org_a_repo.stacks.first.commits.create!(sha: shared_sha, ...)
  commit_b = org_b_stack.commits.create!(sha: shared_sha, ...)

  payload = {
    'sha' => shared_sha, 'state' => 'success', 'context' => 'ci/forged',
    'repository' => { 'full_name' => org_a_repo.full_name, 'owner' => { 'login' => 'org-a' } }
  }.to_json

  request.headers['X-Github-Event'] = 'status'
  # signature valid for org-a's webhook_secret only
  request.headers['X-Hub-Signature'] = sign_with('secretA', payload)

  assert_no_difference -> { commit_b.statuses.count } do  # EXPECTED after fix; currently FAILS (count increases)
    post :create, body: payload, as: :json
  end
end
```
Binding assertion: before the fix, `commit_b.reload.statuses.count` changes from the request signed only for `org-a`'s `webhook_secret`, proving `organization verifying signature (org-a) != organization owning mutated Commit (org-b)`.
