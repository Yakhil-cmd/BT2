### Title
`Handler#stacks` target selection is bound only to `payload['repository']['full_name']`, independent of the `repository_owner` field used for signature verification - ([File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`Shipit::Webhooks::Handlers::Handler#stacks` resolves its target exclusively via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, never consulting `repository_owner` or any value tied to which `GitHubApp`/secret verified the request. Because `WebhooksController#verify_signature` selects the verifying `GitHubApp` using a *different* JSON field (`payload.dig('repository','owner','login')` or `payload.dig('organization','login')`), an attacker who controls the raw JSON body can make these two fields diverge, causing a request that "verifies" for org A to act on org B's stacks.

### Finding Description
The binding that should hold is:
`org_that_passed_verification == org_that_stacks_targets`, i.e. `repository_owner (used in Shipit.github(organization: repository_owner))` `== owner segment of payload.dig('repository','full_name') (used in Handler#stacks)`.

Tracing the code:
- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , then does `github_app = Shipit.github(organization: repository_owner)` and verifies the HMAC signature using that org's configured `webhook_secret` [2](#0-1) .
- Separately, `Handler#stacks` computes `repository_name = payload.dig('repository','full_name')` and resolves `Repository.from_github_repo_name(repository_name)` [3](#0-2) .
- Both `repository_owner` and `repository.full_name` are read from the *same attacker-supplied JSON body* (`params = JSON.parse(request.raw_post)` at [4](#0-3) ), but they are two independent object paths (`repository.owner.login` vs `repository.full_name`) with no code anywhere cross-checking that `full_name` starts with `owner.login` matching the org used to select the signing app.
- `Repository.from_github_repo_name` simply splits the attacker string on `/` and looks up by `owner`/`name` [5](#0-4) , with no relation to which `GitHubApp`/organization key was used to verify.
- `Shipit.github(organization:)` in multi-org mode picks a distinct `GitHubApp` (and therefore a distinct `webhook_secret`) per organization key from `secrets.github` [6](#0-5) , and `verify_webhook_signature` returns `true` unconditionally when that specific org's `webhook_secret` is blank/unset [7](#0-6) .

Exploit flow (multi-org Shipit deployment): if any organization key in `secrets.github` has no `webhook_secret` configured (or the attacker otherwise knows/controls that org's secret, e.g. their own onboarded org), the attacker POSTs to `/webhooks` with:
```json
{
  "repository": {
    "owner": { "login": "attacker-org-with-no-secret" },
    "full_name": "victim-org/victim-repo"
  },
  ...
}
```
`verify_signature` looks up `Shipit.github(organization: "attacker-org-with-no-secret")`, finds no `webhook_secret`, and returns `true` — verification "passes" for `attacker-org-with-no-secret`. The request proceeds to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [8](#0-7) . Every handler's `stacks` method then resolves via `full_name = "victim-org/victim-repo"`, entirely ignoring that verification only ever proved control of `attacker-org-with-no-secret`. This is structural: `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `OpenedHandler`, `LabeledHandler`, and all `Shipit::Webhooks::Handlers::*` subclasses inherit `stacks` from the shared `Handler` base class unchanged.

No existing guard closes this gap: `drop_unhandled_event` only checks the event type is registered; `ExplicitParameters` schemas validate shape/types of fields, not cross-field consistency between `repository.owner.login` and `repository.full_name`; `Repository` model validations only constrain format of stored `owner`/`name`, not the incoming webhook JSON's internal consistency.

### Impact Explanation
An attacker with no Shipit credentials and no knowledge of the victim org's `webhook_secret` can inject fabricated push/status/check-suite/pull-request webhook events that are attributed to and act upon an arbitrary victim repository's `Stack`(s) (e.g. faking a `push` to trigger `PushHandler` behavior, or a `check_suite`/`status` update affecting `StatusHandler`/`CheckSuiteHandler` state, or fabricated PR label/open events for `LabeledHandler`/`OpenedHandler`), as long as they can pass verification for *some* org (their own, or any org lacking a configured `webhook_secret`). This is a payload for one repository mutating another repository's stack/commit/state — matching the Critical impact category. Blast radius: every tenant/organization configured in `secrets.github` is a potential victim as long as at least one organization entry (attacker's own or misconfigured) allows verification to pass without knowledge of that specific victim's secret.

### Likelihood Explanation
Requires a multi-org Shipit deployment (`secrets.github` keyed by multiple organizations) where at least one configured organization has no `webhook_secret` set, or the attacker legitimately owns/controls an onboarded organization with a known secret. Cost to attacker is a single crafted HTTP POST to `/webhooks` with mismatched `owner.login`/`full_name` fields — no GitHub-side action or session/token is needed, and it is fully repeatable against any repository whose `owner/name` is known.

### Recommendation
Enforce that the organization used for signature verification is the same organization used for target resolution: derive `repository_owner` and the target repository from the same trusted field, and reject the request if `payload.dig('repository','owner','login')` does not match the owner segment of `payload.dig('repository','full_name')`. Additionally, `Handler#stacks`/`repository_name` should validate consistency with the verified `repository_owner`, and `GitHubApp#verify_webhook_signature` should not silently return `true` for organizations without a `webhook_secret` — it should fail closed instead.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/handler_test.rb (conceptual, added to test/)
class HandlerBindingTest < ActiveSupport::TestCase
  test "stacks resolves purely from repository.full_name regardless of verified org" do
    org_a_repo = shipit_repositories(:shipit) # owner/name for org A
    payload = {
      'repository' => {
        'owner' => { 'login' => 'org-b-attacker' }, # org that "passed" verification
        'full_name' => org_a_repo.full_name          # unrelated victim org/repo
      }
    }

    handler = Class.new(Shipit::Webhooks::Handlers::Handler) do
      params { }
      def process; end
    end.new(payload)

    resolved_stacks = handler.send(:stacks)

    assert_equal org_a_repo.stacks.to_a, resolved_stacks.to_a,
      "stacks target is driven solely by payload['repository']['full_name'], " \
      "not by the org ('org-b-attacker') that verify_signature actually verified"
  end
end
```
This demonstrates that `stacks` binds only to `payload.dig('repository','full_name')` and never checks the org that `verify_signature` validated, confirming the break is structural across the `Handler` base class inherited by all webhook handler subclasses.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
