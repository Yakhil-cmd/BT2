### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while every handler acts on a different, unsigned-binding field (`repository.full_name`, commit `sha`, `team.id`) — allows cross-tenant forgery in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a payload's HMAC against using `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), then delegates the full raw payload to handlers that key their actual write actions off completely different fields (`repository.full_name`, `sha`, `team.id`, `check_suite.head_sha`). In a multi-tenant Shipit deployment (the officially supported "Using Multiple GitHub Applications" mode) this creates exactly the index/binding mismatch described in the analog report: the field validated by the signature check is not the field the write operation is scoped to.

### Finding Description
Shipit explicitly supports hosting multiple, independently-trusted GitHub organizations from one instance, each with its own `webhook_secret`, `app_id`, and `private_key`: [1](#0-0) [2](#0-1) [3](#0-2) 

`verify_signature` looks up the App/secret for the request purely from `repository_owner`: [4](#0-3) [5](#0-4) 

Once signature verification passes for *that org's* secret, the entire raw JSON body is handed unmodified to every registered handler for the event: [6](#0-5) 

But handlers determine the actual target repository/stack/record from other fields inside the same payload, never re-checking that they match the organization that was authenticated:
- `Handler#repository_name` (base class used by push, pull_request handlers, etc.) resolves the repository purely from `payload.dig('repository', 'full_name')`: [7](#0-6) 
- `PushHandler#process` triggers a resync for any stack matching that repository/branch: [8](#0-7) 
- `StatusHandler#process` writes a CI status onto **any** `Commit` whose `sha` matches the payload, with no repository/organization scoping at all: [9](#0-8) 
- `CheckSuiteHandler#process` schedules check-run refreshes for any stack/commit matching `check_suite.head_sha`/`head_branch`, again unscoped to the authenticated org: [10](#0-9) 

Because `Shipit.github(organization: ...)` treats each configured organization as an independent tenant with its own secret (verified in `test/unit/shipit_test.rb`), a party that legitimately owns/administers one configured organization (and therefore knows that organization's `webhook_secret`, since they provisioned the GitHub App and configured the secret with the Shipit operator) can compute a valid HMAC for a payload of their own choosing and POST it directly to the shared `/github_hooks` endpoint. There is nothing in `verify_signature` or the handlers that ties the signed `repository.owner.login`/`organization.login` to the repository/commit/stack actually mutated.

### Impact Explanation
This breaks the binding "the organization whose secret authenticated the request == the repository being written," which the report generalizes as `self.startIdx` (the value used for the bounds check) not matching `self.length` (the value actually operated on). Concretely, an attacker who controls Org A's GitHub App configuration in a multi-tenant Shipit instance can:
- Forge a `status` webhook with `state: "success"`/`context` for a commit `sha` belonging to a stack owned by a completely different organization (Org B), because `StatusHandler` matches on bare `sha` with no repository check — this can flip CI state used by continuous deployment/merge-queue gating, leading to an **unauthorized deploy** of a commit whose real CI never passed.
- Forge a `push`/`check_suite` webhook naming `repository.full_name` of Org B's repository to force out-of-band resyncs (`GithubSyncJob`) or check-run refresh scheduling against a stack it doesn't own, while the signature was validated only against its own org's secret.

This qualifies as cross-repository/cross-tenant action and an unauthorized deploy trigger, matching the High/Critical impact classes in scope (unauthorized deploy, cross-repository writes).

### Likelihood Explanation
Requires the attacker to be an administrator of at least one organization configured on a shared, multi-tenant Shipit instance (a documented, supported configuration) — not requiring any Shipit session, `ApiClient` token, or GitHub write access to the victim's repository. Given this is a documented multi-org feature, likelihood is realistic wherever an operator hosts multiple, mutually-untrusting organizations on one Shipit instance, which is precisely the scenario `docs/setup.md`'s "Using Multiple Github Applications" section targets.

### Recommendation
After signature verification succeeds, re-derive and enforce that every write path (`Handler#repository_name`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, etc.) matches records whose `Repository#owner` (or organization) equals the same `repository_owner`/`organization.login` that authenticated the signature — i.e., bind the verified organization value into a scoped lookup instead of trusting the unscoped `full_name`/`sha`/`team.id` fields from the payload independently.

### Proof of Concept
1. Configure Shipit with two tenants as in `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`), each with its own `webhook_secret`.
2. As the administrator of `OrgOne` (who knows `OrgOne`'s `webhook_secret` because they configured it), craft a `status` event JSON body:
   ```json
   { "sha": "<sha-of-a-commit-belonging-to-OrgTwo's-stack>", "state": "success", "context": "ci/tests",
     "repository": {"full_name": "OrgOne/some-repo", "owner": {"login": "OrgOne"}} }
   ```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgOne_webhook_secret, body)` and POST to the shared webhook endpoint with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = "OrgOne", looks up `Shipit.github(organization: "OrgOne")`, and the signature validates successfully.
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) matches `Commit.where(sha: params.sha)` — which finds and updates the commit belonging to OrgTwo's stack, regardless of the fact that the signature was only proven for OrgOne.
