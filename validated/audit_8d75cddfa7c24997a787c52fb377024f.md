### Title
Terminal escape-sequence injection via crafted binary-magic-byte prefix bypasses `CopyGuardedContent`/`BinaryContentType` guard - ([File: pkg/iostreams/content.go])

### Summary
`CopyGuardedContent` (used by `gh release download -O -`) and `readFileRun` (used by `gh repo read-file`) classify content as "binary" or "text" using only the leading bytes via `http.DetectContentType`, and once classified binary they stream the entire remaining content **without ever scanning it for ANSI escape bytes**. An attacker who publishes a release asset or repository file that begins with a recognizable binary magic number (e.g. the PNG signature) but whose trailing bytes contain `0x1B` escape sequences can have that payload written verbatim to the victim's non-TTY stdout, defeating the escape-sequence guard entirely.

### Finding Description
`BinaryContentType` classifies content solely from `http.DetectContentType`, which itself only inspects the first 512 bytes of the buffer (`contentSniffLen`). [1](#0-0)  In `CopyGuardedContent`, only the first `contentSniffLen` bytes (`head`) are used for this classification; if `BinaryContentType(head)` reports binary and the destination is not a TTY, the head is written and the remainder of the reader is copied through `io.Copy` with **no `ContainsEscapeSequence` check at all** — the function's own comment states "Binary content streams without buffering." [2](#0-1)  This is confirmed as intentional/tested behavior by the unit test case `"binary when piped is written raw"`, which asserts the full PNG-prefixed payload is written unchanged. [3](#0-2) 

The same pattern exists in `pkg/cmd/repo/read-file/read_file.go`: `BinaryContentType(file.Content)` classifies the whole file by its magic bytes, and if classified binary and stdout is not a TTY, `file.Content` (including any embedded escape sequences in the tail) is written directly to `opts.IO.ContentOut` with no `ContainsEscapeSequence` call anywhere on that path. [4](#0-3)  The escape-sequence scan (`ContainsEscapeSequence`) is only reached on the non-binary branch. [5](#0-4) 

Both `gh release download` and `gh repo read-file` call `opts.IO.SetContentSanitization(false)` before writing this content, explicitly disabling any secondary sanitization pass and relying solely on this guard. [6](#0-5) [7](#0-6) 

An attacker crafts a release asset or repository file: `b"\x89PNG\r\n\x1a\n" + junk + ANSI_escape_payload`. `http.DetectContentType` reports `image/png` from the leading signature, so the file is classified as binary. The victim runs `gh release download <tag> -O -` (or `gh repo read-file <path> -R attacker/repo`) with stdout piped to another program that ultimately renders to a terminal (e.g. `| cat`, `| less`, a log viewer, or a script that later echoes the captured output) — a common workflow for inspecting downloaded content. Because gh's own `IsStdoutTTY()` is false in a pipe, the guard's TTY refusal never triggers, and the escape bytes are streamed through untouched to whatever ultimately displays them.

### Impact Explanation
This allows terminal escape-sequence injection (e.g., title-bar spoofing, cursor/screen manipulation, OSC 8 hyperlink deception used for phishing, or in vulnerable terminal emulators more severe control-sequence abuse) against a victim who downloads/reads attacker-published content and pipes it through a terminal-rendering intermediary — exactly the `OUTPUT_SAFETY` invariant the guard was built to enforce, and exactly the scenario the code's own comments and tests already anticipate as an accepted binary-streaming behavior rather than a text-escape leak.

### Likelihood Explanation
Highly feasible and repeatable: any unprivileged GitHub user can attach an arbitrary release asset or commit a file with a crafted magic-byte prefix. Exploitation requires only that the victim run `gh release download ... -O -` or `gh repo read-file ...` with stdout piped (not directly attached to a TTY), which is a normal, encouraged usage pattern per the commands' own `--output -` documentation.

### Recommendation
Do not skip the escape-sequence scan purely because content sniffs as binary. Either (a) always scan the full content (buffered, as already done for text) for `0x1B` bytes regardless of classification before writing to a non-TTY destination that could still ultimately reach a terminal, or (b) restrict the "stream binary verbatim" fast path to writes explicitly known to go to a file (`--output <path>`) rather than to `stdout`/pipes, since the whole risk is specific to stdout being consumed by a terminal-adjacent process downstream.

### Proof of Concept
Extend `TestCopyGuardedContent` in `pkg/iostreams/content_test.go` with a case whose binary-sniffed head is a valid PNG signature but whose tail contains an escape sequence, and assert it is currently written raw (demonstrating the bypass) rather than refused:
```go
{
    name: "binary-prefixed payload with hidden escape in tail streams raw when piped",
    content: append(append([]byte("\x89PNG\r\n\x1a\n"), make([]byte, 16)...),
        []byte("\x1b]0;pwned\x07")...), // OSC escape sequence in the tail
    isTTY: false,
    // current behavior: wantOut equals full content (escape sequence not caught)
    wantOut: append(append([]byte("\x89PNG\r\n\x1a\n"), make([]byte, 16)...),
        []byte("\x1b]0;pwned\x07")...),
},
```
Running this against `CopyGuardedContent` shows the escape bytes are written to the buffer unmodified, confirming no `ErrEscapeSequence` is raised despite `ContainsEscapeSequence` on the full content returning `true`. An equivalent integration test can be built for `readFileRun` using an `httpmock` GitHub Contents API response whose base64-decoded content starts with `\x89PNG\r\n\x1a\n` followed by an ANSI escape sequence, run with stdout redirected to a non-TTY buffer, and assert the escape bytes appear in the captured output.

// BinaryContentType reports whether content appears to be binary and, if so,
// returns its detected MIME type. Textual content returns ("", false).
func BinaryContentType(content []byte) (string, bool) {
	if len(content) == 0 {
		return "", false
	}
	ct := http.DetectContentType(content)
	if i := strings.IndexByte(ct, ';'); i >= 0 {
		ct = strings.TrimSpace(ct[:i])
	}
	if strings.HasPrefix(ct, "text/") {
		return "", false
	}
	return ct, true
}
```

func CopyGuardedContent(w io.Writer, r io.Reader, isTTY bool) error {
	head := make([]byte, contentSniffLen)
	n, err := io.ReadFull(r, head)
	if err != nil && !errors.Is(err, io.EOF) && !errors.Is(err, io.ErrUnexpectedEOF) {
		return err
	}
	head = head[:n]

	if mime, ok := BinaryContentType(head); ok {
		if isTTY {
			return BinaryTerminalError{MIME: mime}
		}
		if _, err := w.Write(head); err != nil {
			return err
		}
		_, err := io.Copy(w, r)
		return err
	}
```
