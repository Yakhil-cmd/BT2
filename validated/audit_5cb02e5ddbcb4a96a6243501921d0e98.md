### Title
API client stack-scope bypass in CCMenu endpoint allows cross-stack read of build/deploy state - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method used by `BaseController`, replacing the scoped lookup (`stacks.from_param!`) with an unscoped `Stack.from_param!(params[:stack_id])`. This breaks the binding: **stack a token authorizes == stack a token can read**. A stack-scoped `ApiClient` token, created specifically to expose CI/build status for one stack, can be replayed against `stack_id` values for any other stack in the installation and will successfully return that stack's build/deploy status.

### Finding Description
`Shipit::Api::BaseController` defines the scoping mechanism that all API endpoints are supposed to rely on: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

When an `ApiClient` is created with a `stack_id` (e.g. the `CCMenu Client` created by `CCMenuUrlController`), `stacks` restricts lookups to that single stack, and any controller using `require_permission` + the inherited `stack` method is scoped accordingly.

`CCMenuUrlController` explicitly creates such a scoped, minimally-privileged token: [2](#0-1) 

```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```

However, `Shipit::Api::CCMenuController` overrides `stack` and bypasses the scoping entirely: [3](#0-2) 

```ruby
class CCMenuController < BaseController
  require_permission :read, :stack
  ...
  def show
    latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
    render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
  end

  private

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end
```

`require_permission :read, :stack` only checks that `ApiClient#permissions` contains `read:stack` via `ApiClient#check_permissions!`: [4](#0-3) 

```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
  end
  true
end
```

This check is a global capability check (`does this token have read:stack anywhere`), not a per-resource authorization check. The per-resource restriction is supposed to come from `stacks`/`stack` in `BaseController`, but `CCMenuController#stack` never calls that scoped helper — it calls `Stack.from_param!` directly against the whole `Stack` table.

**Binding broken**: `current_api_client.stack_id (authorized stack)` == `params[:stack_id] (stack actually read)`. Before the fix this equality is enforced by `stacks.from_param!`; in `CCMenuController` it is never enforced.

The `ccmenu` route accepts the token via query string as an explicit alternate authentication path: [5](#0-4) 

```ruby
def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

confirmed by the test suite exercising the query-string flow: [6](#0-5) 

### Impact Explanation
Any holder of a stack-scoped `read:stack` token (the exact kind Shipit itself mints for embedding in CCMenu/CI-status-widget URLs, see `CCMenuUrlController`) can use that token to read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state, etc.) for *every* stack configured on the Shipit instance, not just the one it was scoped and intended for. This is an unauthorized cross-stack read of stack/deploy state, matching the in-scope "High" impact category ("escalation into ... authorization ... unauthenticated read of stack state ... deploy output"). It leaks stack existence, naming, environment, lock reasons, and deploy status across repositories/environments the token holder should have no visibility into.

### Likelihood Explanation
High. No special privileges are required beyond possessing any single scoped `read:stack` API token — which is routinely generated and distributed by Shipit itself (e.g., embedded in CCMenu URLs shown in the stack settings page) for exactly one stack. The attacker only needs to change the `stack_id` route/query parameter to any other stack's slug; no additional secret, session, or write access is needed.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (or reimplement it using the inherited, scoped `stacks` helper), e.g.:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

so that scoped tokens are restricted to the stack(s) they were actually authorized for, consistent with every other API controller.

### Proof of Concept
1. As an authenticated Shipit user, visit a stack's settings page; Shipit generates (via `CCMenuUrlController#fetch`) a `read:stack`-scoped `ApiClient` token bound to `stack_id = <stack A>`.
2. Using that token as Basic Auth or as the `token` query parameter, call:
   `GET /api/<stack_A>/cc.xml?token=<token>` → succeeds (expected).
3. Replay the same token against a different stack:
   `GET /api/<stack_B>/cc.xml?token=<token>` where stack B is *not* the stack the token was scoped to.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!`, the request succeeds and returns stack B's build/deploy status, even though `current_api_client.stack_id` is set to stack A only, demonstrated by the existing scoping mechanism in `BaseController#stacks` being silently bypassed.
