### Title
Authentication bypass into `Shipit.github_teams` via unsigned webhooks for organizations configured without a `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/secret to validate a webhook against using an attacker-supplied field of the very payload it is about to trust, and `GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as "always valid." Combined with `MembershipHandler`, which trusts the `organization.login`, `team`, and `member.login` fields of that same unsigned payload to create `Team`/`Membership` rows, an unauthenticated attacker can add an arbitrary GitHub login to a `Team` that matches one of the `Shipit.github_teams` handles, bypassing `Authentication#force_github_authentication`'s team-membership gate entirely.

### Finding Description
`verify_signature` derives the organization used to select the signing secret straight from the untrusted request body, then defers to that organization's app to check the signature: [1](#0-0) [2](#0-1) 

The actual HMAC check is: [3](#0-2) 

`return true unless webhook_secret` means that for any configured GitHub organization/app entry whose `webhook_secret` is left blank, signature verification is skipped completely — any POST with the right `X-Github-Event` header is accepted regardless of the `X-Hub-Signature` header content. Leaving `webhook_secret` blank is an explicitly supported, documented configuration, not an attacker-controlled secret: [4](#0-3) [5](#0-4) 

Once past `verify_signature`, `WebhooksController#create` dispatches the fully attacker-controlled JSON body to the matching handler: [6](#0-5) 

For the `membership` event, `MembershipHandler` creates/fetches a `Team` keyed only by an attacker-chosen `team.id`, and adds an attacker-chosen `member.login` to it: [7](#0-6) 

Authorization into the whole application is gated purely by whether the logged-in user belongs to any `Team` whose id is in `Shipit.github_teams`: [8](#0-7) [9](#0-8) 

`Shipit.github_teams` entries are themselves resolved/created by `organization`/`slug` handle: [10](#0-9) 

The binding that should hold is: *the organization whose secret authenticated the webhook == the organization/team the webhook payload is permitted to mutate*. Instead, the organization value used to pick (or entirely skip) signature verification (`repository.owner.login` / `organization.login`) and the organization/team value the handler writes to (`params.team`, `params.organization.login`, `params.member.login`) are read from the same untrusted JSON independently, with no cryptographic tie between "this org's secret validated the request" and "this is the org this request is allowed to modify." When any configured org has no secret, that binding collapses entirely — there is no verification step at all.

### Impact Explanation
An unauthenticated network attacker who knows (or discovers, e.g. via `docs/setup.md`-style deployments, GitHub App marketplace listings, or simply an org name for which the operator never set a webhook secret in `config/secrets.yml`) an organization entry lacking `webhook_secret` can:
1. POST a forged `membership` event with `organization.login` set to that unsecured org, `member.login` equal to their own GitHub username, and a `team` payload whose `id`/`slug`/`organization` matches (or is used to create) a `Team` corresponding to one of `Shipit.github_teams`.
2. `MembershipHandler` creates the `Team`/`User`/`Membership` rows unconditionally (`verify_signature` passed trivially).
3. On next OAuth login, `User#authorized?` finds the attacker's `User` record now belongs to a team in `Shipit.github_teams` and grants full access to the Shipit UI: viewing all stacks, task output, and triggering deploys/rollbacks/merges.

This is an escalation into `Shipit.github_teams` authorization — explicitly listed as a High-severity impact category.

### Likelihood Explanation
Requires no credentials, no session, no repository access — only that the deployment has at least one GitHub organization/app configured in `Shipit.github` whose `webhook_secret` was left blank (a state the shipped sample configs and setup docs treat as normal/optional). Given `webhook_secret` is documented as optional and not all operators configure it for every org (especially secondary/legacy org entries in multi-org deployments), this is a realistic misconfiguration rather than a theoretical one, and the exploit path itself (crafting arbitrary JSON to `/github/webhooks`) requires no special access.

### Recommendation
- Do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank; treat a missing secret as "reject all webhooks for this organization" (or require configuration validation at boot to refuse starting without a secret per configured org).
- Cryptographically or structurally bind the organization that authenticates the request to the organization/team the handler is permitted to mutate — e.g., verify that `params.organization.login`/`params.team.organization` matches the same `repository_owner`/org used for signature selection, and reject mismatches even when a signature is present.
- For `MembershipHandler`, do not trust client-supplied `team.id` as sufficient identity; corroborate team membership changes against `Shipit.github_teams` configuration boundaries explicitly, rejecting organizations not in that configured set.

### Proof of Concept
Assuming a Shipit deployment configured with two GitHub orgs, `secure-org` (has `Shipit.github_teams` restricting access to `secure-org/employees`) and `legacy-org` (configured in `Shipit.github` but with `webhook_secret` left blank, as shown valid in `config/secrets.development.shopify.yml`):

```
POST /github/webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "organization": { "login": "legacy-org" },
  "team": { "id": 999999, "name": "employees", "slug": "employees", "url": "https://example.com" },
  "member": { "login": "attacker-github-login" }
}
```

- `verify_signature` calls `Shipit.github(organization: "legacy-org")`, finds a configured app whose `webhook_secret` is blank, and `verify_webhook_signature` returns `true` unconditionally — no `X-Hub-Signature` needed.
- `MembershipHandler#process` creates `Team(github_id: 999999)` and adds `User(login: "attacker-github-login")` to it via `add_member`.
- If `secure-org/employees`'s `Shipit.github_teams` handle also resolves to a `Team` with `organization: "secure-org", slug: "employees"`, an attacker who instead targets that exact organization/slug pair (`team.organization` set accordingly, or by controlling `find_or_create_by_handle` matching) becomes a member of a team inside `Shipit.github_teams`, so `User#authorized?` now returns true for the attacker after they complete an ordinary OAuth login with their own real GitHub account of that login name.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
