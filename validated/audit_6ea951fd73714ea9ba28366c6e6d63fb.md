### Title
Unbounded recursion in `validateAuthentifiers`'s inner `evaluate()` for nested `address` definitions can crash a validating node - (File: definition.js)

### Summary
`validateAuthentifiers()` in `definition.js` recursively evaluates an address's spending-condition tree to check signatures/authentifiers supplied on a posted unit. Unlike the sibling `evaluate()` used in `validateDefinition()` (which increments a `complexity`/`count_ops` counter on every recursive call and enforces `constants.MAX_COMPLEXITY`/`MAX_OPS`), the `evaluate()` function inside `validateAuthentifiers` has **no complexity, op-count, or depth limit at all**.

### Finding Description
For the `'address'` opcode, `evaluate()` re-enters itself with the *same* `path` string after resolving the nested address's definition: [1](#0-0) 

The only guard before recursing is `pathIncludesOneOfAuthentifiers(path, arrAuthentifierPaths, bAssetCondition)`, which just checks that `path` is a prefix of one of the paths for which the unit supplies an authentifier: [2](#0-1) 

Because the `path` argument is never lengthened for the `'address'` op (compare with `'or'`/`'and'`/`'r of set'`, which append `.index` to `path` on each recursive step), this prefix check keeps succeeding indefinitely as the recursion walks through a chain of nested address definitions. Each individual address definition is validated independently (via `validateDefinition`, which does bound *its own* complexity to `MAX_COMPLEXITY`), but that per-definition bound says nothing about how many *other* addresses may be chained together through `['address', X]` opcodes at authentication time, since `validateAuthentifiers`'s `evaluate` never tracks cumulative complexity across the whole chain.

An attacker who controls two (or more) addresses can craft:
- address `A`'s definition containing `['address', 'B']`
- address `B`'s definition containing `['address', 'A']`

Both `A` and `B` individually pass `validateDefinition` (trivial 1-level complexity, well under `MAX_COMPLEXITY`). When a unit is later signed by (or otherwise references) `A` with an authentifier path that resolves into this branch, `validateAuthentifiers`'s `evaluate()` will call `storage.readDefinitionByAddress` for `B`, recurse into `B`'s definition, hit `['address', 'A']`, call `readDefinitionByAddress` for `A` again, and so on — with no depth or complexity counter to stop it. This mirrors the CVE-2017-17497 bug class: a loop/recursive traversal that keeps re-entering child structures based on a variable (`path`) that is never validated/advanced enough to terminate the process, ultimately exhausting the call stack or looping effectively forever, crashing the Node.js validation process (uncaught `RangeError: Maximum call stack size exceeded` or an unresponsive event loop from unbounded async recursion).

### Impact Explanation
Any single unprivileged unit poster who has previously registered two (or more) mutually-referencing addresses (a cheap, permissionless operation — address definitions just need distinct chash160 values and can freely embed `['address', ...]` references to other addresses) can trigger unbounded recursion during signature validation of a subsequently posted unit. This crashes (or hangs) the validating node process for **every node that validates the unit**, not just a single malicious peer — i.e., it is reachable purely through unit content, not a network/peer-level attack. A node crash during validation halts the network's ability to confirm new units until recovered, matching the "network unable to confirm new units" impact bar.

### Likelihood Explanation
Likelihood is high for an attacker: creating two cross-referencing address definitions requires no special privilege (any user can define an address with an `['address', other_address]` condition), and the recursion is triggered by ordinary unit posting/signing — no cooperation from other users, hubs, or witnesses is needed.

### Recommendation
Add an explicit recursion-depth (or complexity/op-count) guard inside `validateAuthentifiers`'s `evaluate()`, mirroring the `complexity`/`count_ops` tracking already present in `validateDefinition`'s `evaluate()` [3](#0-2) , and/or increment `path` (or a separate depth counter) on the `'address'` case so that `pathIncludesOneOfAuthentifiers` cannot keep matching indefinitely across a chain of nested address definitions. Reject definitions whose resolved authentication chain exceeds a fixed depth/complexity bound.

### Proof of Concept
1. Attacker creates address `B` with definition `['sig', {pubkey: pubB}]` combined via `or` with `['address','A']` (or a minimal `['address','A']`-only branch reachable under an authentifier path) and posts it (validated fine — depth 1).
2. Attacker creates address `A` with definition containing `['address','B']` similarly and posts it (validated fine — depth 1).
3. Attacker posts a unit authored by `A`, supplying an authentifier at a path that resolves through the `'address'` branch (e.g., placeholder/any accepted authentifier for that path, since `pathIncludesOneOfAuthentifiers` only checks prefix matching, not that the target op is `'sig'`).
4. During validation, `validateAuthentifiers`'s `evaluate()` resolves `A → B → A → B → …` indefinitely (`definition.js:774-800`), exhausting the call stack (or looping via nested async callbacks) and crashing/hanging the validating node.

Because index/search limits may exclude some file contents from this analysis, the exact call sites in `validation.js` that populate `arrAuthentifierPaths` and invoke `validateAuthentifiers`, as well as any cycle-detection that might exist in `storage.readDefinitionByAddress`, could not be fully confirmed here — a full Devin session with complete file access would be needed to verify these call paths end-to-end before treating this as fully proven.
