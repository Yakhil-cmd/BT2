### Title
Pool creator address is stored without a zero-address check, permanently freezing creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` lets any unprivileged payer create a pool and freely choose the `creator` account, which is stored as `pool_creator` in `PoolState` without any validation that it is non-zero or otherwise meaningful, mirroring the reported `OwnableImpl::__initOwnable()` bug class where a critical address field is set without a zero-address check.

### Finding Description
In `InitializeWithPermission`, `creator` is declared as an unchecked, unconstrained account: [1](#0-0) 

The caller-supplied `creator.key()` is stored directly into the newly created pool state with no validation: [2](#0-1) 

Unlike `update_amm_config`'s owner-setters, which explicitly guard against the zero pubkey via `require_keys_neq!(new_owner, Pubkey::default())`: [3](#0-2) 

there is no equivalent check when `pool_creator` is initialized. Any unprivileged caller invoking `initialize_with_permission` (reachable via `lib.rs`'s program entrypoint) can pass the System Program ID / default `Pubkey` (`11111111111111111111111111111111`) as `creator`, permanently baking that value into `pool_state.pool_creator`.

### Impact Explanation
Once `pool_creator` is set to the zero/default address, all creator fees accrued by the pool (`creator_fees_token_0` / `creator_fees_token_1`) become permanently unrecoverable:
- `collect_creator_fee` requires a `Signer` whose key equals `pool_creator`: [4](#0-3) 
No private key exists for the default/System Program pubkey, so this path can never be signed.
- `collect_creator_fee_permissionless` sends the fees to an ATA owned by `creator` (still constrained to equal `pool_creator`): [5](#0-4) [6](#0-5) 
Any tokens delivered here land in an ATA owned by the System Program address, which nobody controls, so the funds are effectively burned/frozen forever inside the pool's vaults ledger.

This is a permanent freezing of pool creator fee funds, matching the report's impact category (a critical role address becomes unusable/inaccessible once set to the zero address).

### Likelihood Explanation
The attack requires zero privilege: any account can call `initialize_with_permission` as `payer`, is the one funding the new pool, and can freely pass any `creator` account (including the well-known default `Pubkey`) since the accounts struct places no constraint (e.g., `constraint = creator.key() != Pubkey::default()`) on it. This makes the likelihood high for any pool created this way where the creator address is chosen incorrectly or maliciously, since there is no way to correct `pool_creator` after pool initialization (no `set_new_creator`/`transfer_creator` instruction exists in the program).

### Recommendation
Add an explicit zero-address (and possibly non-executable) check on `creator` in `InitializeWithPermission`, e.g.:
```rust
require_keys_neq!(creator.key(), Pubkey::default());
```
before storing it into `pool_state.pool_creator`, mirroring the `require_keys_neq!` checks already present in `update_config.rs`'s `set_new_protocol_owner` / `set_new_fund_owner`.

### Proof of Concept
1. Attacker (or any unprivileged user) calls `initialize_with_permission` supplying `creator = 11111111111111111111111111111111` (the default/System Program `Pubkey`), along with valid mints, vaults, and a valid `permission` PDA for their own `payer` key.
2. `pool_state.initialize(...)` stores `pool_creator = Pubkey::default()`: [2](#0-1) 
3. Swaps occur against the pool, accruing `creator_fees_token_0`/`creator_fees_token_1` in `PoolState`.
4. Any attempt to collect these fees via `collect_creator_fee` fails permanently (no keypair for the zero address can sign as `creator`), and `collect_creator_fee_permissionless` routes the funds to an ATA owned by the unspendable default address, permanently freezing the creator fee funds inside the pool's fee ledger.
