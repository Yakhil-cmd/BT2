### Title
Cross-Organization Webhook Forgery via Signature/Target Binding Mismatch in Multi-Tenant Webhook Verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit explicitly supports hosting multiple GitHub organizations from a single instance, each with its own GitHub App and its own `webhook_secret` [1](#0-0) , exposed via `Shipit.github_organizations` / `Shipit.github_app_config` [2](#0-1) . `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the incoming HMAC against based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), a field taken from the **attacker-suppliable JSON body itself** [3](#0-2) . The HMAC is only checked to be *valid for that self-selected organization's secret* — it never proves the event actually came from GitHub for the org/repo that the corresponding event handler subsequently acts on, because the handlers resolve the target `Stack`/`Repository` using an entirely different field, `payload.dig('repository', 'full_name')` [4](#0-3) .

### Finding Description
In a multi-organization deployment, an actor who legitimately administers *one* onboarded GitHub organization (Org A) knows Org A's `webhook_secret` (they configured/received it when installing their own Shipit GitHub App). Because `verify_signature` computes `Shipit.github(organization: repository_owner)` using `repository.owner.login` taken straight out of the untrusted JSON body [5](#0-4) , this actor can:

1. Craft an arbitrary webhook JSON body with `repository.owner.login = "OrgA"` (so `verify_signature` selects Org A's `GitHubApp` and secret) but `repository.full_name = "OrgB/victim-repo"` (a repository they have no access to at all).
2. Sign the entire raw body with Org A's `webhook_secret` (which they legitimately possess) and send it directly to `/webhooks`.
3. `verify_webhook_signature` succeeds because the HMAC is computed over the full request body using Org A's secret, and the request body is entirely attacker-controlled — nothing ties the *selected verification secret* to the *repository the handler will act on* [6](#0-5) .
4. `WebhooksController#create` then dispatches the forged event to the registered handlers with the raw, attacker-controlled params [7](#0-6) , and handlers such as `PushHandler`, `Handler#stacks`/`Handler#repository_name` resolve the target stack purely from `repository.full_name`, independent of which org's secret validated the signature [4](#0-3) [8](#0-7) .

This breaks the binding: `organization authenticated (repository.owner.login used to pick the webhook secret) == organization/repository actually written (repository.full_name used by the handler)`. The two fields live in the same attacker-controlled JSON body and are never cross-checked.

### Impact Explanation
An operator of one onboarded organization in a multi-tenant Shipit instance can forge webhook events (`push`, `status`, `check_suite`, `pull_request`, etc.) that are processed as if they originated from a completely different organization's repository they have no access to. Concretely:
- `PushHandler` will enqueue `GithubSyncJob`/`sync_github` for any `Stack` matching the forged `repository.full_name`, forcing Shipit to treat an attacker-chosen `after` SHA as the new head for a victim stack [9](#0-8) .
- A forged `status` event can mark an arbitrary commit on a victim's stack as CI-`success`, which, combined with `continuous_deployment`, can trigger an unauthorized automatic deploy of attacker-chosen code on infrastructure the attacker does not own.
- Pull-request based handlers (`opened`, `labeled`, etc.) resolve `Repository.from_github_repo_name(params.repository.full_name)` the same way, allowing cross-repository provisioning/archival actions on review stacks belonging to other organizations.

This satisfies the "unauthorized deploy" / cross-repository write impact tier: the attacker crosses an organizational trust boundary they are not authorized to act within, using only credentials legitimately issued to them for a different organization.

### Likelihood Explanation
This requires the deployment to use Shipit's documented multi-organization configuration (multiple entries under `github:` in `secrets.yml`, each with its own app/secret) [1](#0-0) , and requires the attacker to be a legitimate admin/operator of at least one of the onboarded organizations (so they know that org's `webhook_secret`). This is a realistic scenario for shared/central Shipit instances serving several teams or business units, where each team's admins are trusted only for their own org but not for others'. No compromise of the target organization's secret, GitHub token, or API access is required.

### Recommendation
- After the HMAC signature is verified for the organization selected from the payload, re-derive the "owning organization" independently from `repository.full_name` (or `organization.login` for org-scoped events) and require it to exactly match the organization whose secret validated the signature; reject on mismatch.
- Alternatively, verify the signature against every configured organization's secret and only accept the request if the same organization both (a) validates the signature and (b) owns the repository named in `repository.full_name`.
- Ensure `head(422)` in `verify_signature` is followed by an explicit halt of the callback chain (e.g. `return` or `throw(:abort)`) so no ambiguity remains about downstream processing.

### Proof of Concept
Assume a Shipit instance configured with two organizations, `OrgA` (attacker is a legitimate admin, knows `webhook_secret_A`) and `OrgB` (attacker has no access), per the documented multi-org config [1](#0-0) .

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, body)>

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-that-exists-in-OrgB/victim-repo>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```

`repository_owner` resolves to `"OrgA"` [5](#0-4) , so `Shipit.github(organization: "OrgA")` is used to verify the signature, which succeeds because the attacker signed the body with `webhook_secret_A`. The `create` action then dispatches to `PushHandler`, which resolves the target stacks using `payload.dig('repository','full_name')` = `"OrgB/victim-repo"` [4](#0-3) , causing Shipit to sync/deploy a repository the attacker does not own, using only credentials for `OrgA`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
