### Title
`pull_request` webhook signature verification key (`repository.owner.login`) is decoupled from the target-lookup key (`repository.full_name`), letting a no-secret organization's identity authorize writes to a different repository's `PullRequest`/`ReviewStack` state - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` used for HMAC verification using `params.dig('repository','owner','login')`, but `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler` (and the `ReviewStackAdapter`/`Shipit::Repository.from_github_repo_name` it delegates to) resolves the *target* repository/stack using the independent field `params.repository.full_name`. Because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected org's config has no `webhook_secret` [1](#0-0) , and because nothing cross-checks that `repository.full_name` actually belongs to the org named in `repository.owner.login`, an attacker can pass verification using a no-secret org while pointing the payload's `full_name` at an arbitrary, fully-secured victim repository.

### Finding Description
The broken binding is: verification identity `params.repository.owner.login` should equal the effective target identity implied by `params.repository.full_name` for every accepted webhook. In this codebase they are two independently attacker-controlled JSON fields that are never compared.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and fetches `Shipit.github(organization: repository_owner)` [2](#0-1) .
2. If that org's config has a blank `webhook_secret`, `verify_webhook_signature` short-circuits to `true` regardless of the actual signature header [1](#0-0) . The dummy test config itself ships with `"webhook_secret": null` [3](#0-2) , showing this "no-secret organization" state is a realistic configuration, not a theoretical edge case.
3. Once past `verify_signature`, `create` dispatches the raw parsed body to `Shipit::Webhooks.for_event(event)` handlers unchanged [4](#0-3) .
4. `LabelCapturingHandler` only requires `repository.full_name` as a `String` in its `ExplicitParameters` schema — there is no constraint tying it to `repository.owner.login` [5](#0-4) . It resolves the actual target via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5) , then locates the review stack and, on `action == "unlabeled"` (or opened/labeled/reopened) with a present, non-archived stack, overwrites `stack.pull_request.update!(labels: params.pull_request.labels.map(&:name))` [7](#0-6) .
5. Those persisted labels are later surfaced as uppercased boolean environment variables merged into the deploy/task environment via `ReviewStack#env` [8](#0-7) , confirmed by `test/lib/shipit/deploy_commands_test.rb` and `test/lib/shipit/task_commands_test.rb` showing labels become `command.env['WIP']`/`env['BUG']`-style entries that reach deploy/task command execution.

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or an arbitrary one), and a JSON body such as:
```json
{
  "action": "unlabeled",
  "number": 1,
  "pull_request": { "...": "...", "labels": [{"name": "malicious_flag"}] },
  "repository": { "owner": { "login": "no-secret-org" }, "full_name": "victim-org/victim-repo" },
  "sender": { "login": "attacker" }
}
```
`repository.owner.login` names an org Shipit has configured but with no `webhook_secret` (verification auto-passes), while `repository.full_name` names the victim stack that belongs to a *different*, secret-protected org/repository. `verify_signature` never reads or validates `full_name`, so the forged payload is accepted, and `LabelCapturingHandler` mutates the victim repo's `PullRequest#labels`.

Existing guards do not stop this: `drop_unhandled_event` only checks whether a handler exists for the event type; the `ExplicitParameters` schema on `LabelCapturingHandler` only validates types/presence, not cross-field consistency; `verify_signature`'s `rescue Shipit::GithubOrganizationUnknown` only fires if the org name in `repository.owner.login` isn't configured at all — it does not fire when that org *is* configured but merely lacks a secret, nor does it inspect `full_name`.

The claim in the question about `blocking_statuses` and `blocked?` being toggled by this specific handler is not supported by the code: `Commit#blocked?` is driven purely by `stack.blocking_statuses` matched against commit `Status#blocking?`, which comes from the `status`/`check_suite` webhook handlers, not from `LabelCapturingHandler` [9](#0-8) . Labels only affect the injected environment variables via `ReviewStack#env`, not `blocked?`. That part of the exploit narrative does not hold for this handler; the genuine, demonstrable impact is environment-variable injection into a victim stack's deploy/task commands via forged `PullRequest#labels`.

### Impact Explanation
An unprivileged internet attacker who knows (or guesses) the name of any Shipit-configured GitHub organization lacking a `webhook_secret` can forge `pull_request` events that mutate `PullRequest#labels` for **any** review stack, including stacks belonging to a completely different, properly-secured organization, by simply setting `repository.full_name` to the victim's `owner/repo`. This corrupts persisted `PullRequest` state and injects attacker-chosen boolean environment variables (`LABEL_NAME=true`) into subsequent deploy and task command environments for the victim stack, per `ReviewStack#env`. This matches "a payload for one repository mutating another's stack" in the Critical impact category. It is fully repeatable against any repository whose stack has an active, non-archived `PullRequest` record, for as long as any one org in the Shipit config is missing a `webhook_secret`.

### Likelihood Explanation
Preconditions: at least one GitHub organization configured in Shipit with a blank/missing `webhook_secret` (shown to be a realistic default in this codebase's own test fixtures), and a victim stack with an associated `PullRequest`. Attacker cost is a single unauthenticated HTTP POST with no GitHub or Shipit credentials, no valid signature, and no knowledge of the victim org's secret — only the name of the no-secret org and the victim's `owner/repo` string, both of which are typically public/discoverable. This is trivially repeatable and requires no privileged role.

### Recommendation
Validate that `repository.owner.login` (or `organization.login`) used to select the verifying `GitHubApp`/secret is consistent with the organization portion of `repository.full_name` before processing any handler, and reject the request if they diverge. Additionally, treat a configured organization with a blank `webhook_secret` as a hard failure (422) rather than an automatic pass in `GitHubApp#verify_webhook_signature`, since that behavior effectively disables authentication for that org's webhooks entirely.

### Proof of Concept
Minitest plan (add to `test/controllers/webhooks_controller_test.rb`):
```ruby
test "forged pull_request unlabeled event from a no-secret org mutates a different org's stack" do
  # Precondition: configured org "shopify" (from secrets.test.json) has webhook_secret: null
  victim_stack = shipit_stacks(:review_stack) # belongs to a different repo/org in fixtures
  victim_stack.pull_request.update!(labels: ["safe"])

  request.headers['X-Github-Event'] = 'pull_request'
  # No X-Hub-Signature header provided at all / arbitrary value
  body = {
    action: 'unlabeled',
    number: victim_stack.pull_request.number,
    pull_request: pull_request_payload_for(victim_stack).merge(labels: []),
    repository: {
      owner: { login: 'shopify' }, # no-secret org: auto-verified
      full_name: victim_stack.repository.full_name # a DIFFERENT, unrelated repo
    },
    sender: { login: 'attacker' }
  }.to_json

  post :create, body:, as: :json

  assert_response :ok
  assert_equal [], victim_stack.pull_request.reload.labels # binding broken: attacker mutated a repo it never authenticated for
end
```
Assert on both sides of the equality: before the request, `repository_owner ("shopify") != victim_stack.repository.full_name.split('/').first` (organization used for signature verification differs from the organization actually mutated); after the request, `victim_stack.pull_request.labels` has changed despite the attacker never possessing the victim org's `webhook_secret` — proving the divergence is exploitable.

    end
