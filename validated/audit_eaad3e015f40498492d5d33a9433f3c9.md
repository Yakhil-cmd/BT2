### Title
Cross-organization webhook forgery via unbound `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to check the HMAC against using `repository.owner.login` (falling back to `organization.login`), but the handlers that actually act on the payload resolve the target `Stack`/`Repository` using a completely different, unchecked field: `repository.full_name`. Because these two fields are never cross-validated, a party who controls the webhook secret for **any** GitHub organization onboarded to a multi-tenant Shipit instance can forge a validly-signed webhook whose `repository.owner.login` names their own org (so the signature check passes) while `repository.full_name` names a repository belonging to a **different** onboarded organization, causing Shipit to act on that other org's stack.

### Finding Description
`verify_signature` computes the app/secret to validate against like this: [1](#0-0) [2](#0-1) 

`repository_owner` (used only to pick the `webhook_secret`) is read from `repository.owner.login` (or `organization.login`). The HMAC (`X-Hub-Signature`) is computed over the *entire* raw body, so the signature does prove the sender knows the correct secret — but the secret used is chosen by the very same attacker-controlled JSON that is being verified. Nothing ties `repository.owner.login` to `repository.full_name`, which is the field every downstream `Handler` actually uses to resolve the target stack: [3](#0-2) 

`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and every `PullRequest::*Handler` all use `repository_name`/`params.repository.full_name` (never `repository.owner.login`) to look up `Repository.from_github_repo_name(...)` and thus the `Stack`: [4](#0-3) 

In Shipit's documented multi-org configuration (`docs/setup.md`, "Using Multiple Github Applications"), each onboarded GitHub organization has its own `webhook_secret`, configured by whoever administers that org's GitHub App: [5](#0-4) 

The binding that Shipit relies on but never enforces is:
`organization authenticated by verify_signature (repository.owner.login/organization.login)` == `repository actually written by the Handler (repository.full_name)`

Before the attack: org B's admin can only produce validly-signed webhooks for org B's own repos (`repository.owner.login == "OrgB"` and `repository.full_name` starting with `"OrgB/..."`, as GitHub itself would normally send).
After the attack: org B's admin sends a payload with `repository.owner.login = "OrgB"` (so `Shipit.github(organization: "OrgB")` is used, and the HMAC is computed with the secret they legitimately know) but `repository.full_name = "OrgA/some-repo"`. `verify_signature` passes; `Handler#stacks`/`#repository` then resolves and mutates `OrgA`'s `Stack`.

### Impact Explanation
This breaks Shipit's organizational trust isolation in multi-tenant deployments: an entity that only has legitimate control over one onboarded organization's GitHub App (its own `webhook_secret`) can forge events that are attributed to, and acted upon, an entirely different organization's repository/stack, without ever having credentials, membership, or write access to that target repository. Concretely, via `PushHandler`, the attacker can force `GithubSyncJob` to run for the victim stack with an attacker-chosen `expected_head_sha`, and via the `PullRequest` handlers they can create/archive/unarchive review stacks belonging to the victim organization. This is a cross-repository write achieved purely by exploiting the unbound `repository.full_name` vs. `repository.owner.login` fields — the same class of "field acted on but not covered by verification" bug flagged in the source report (amount transferred vs. amount trusted).

### Likelihood Explanation
Requires the target Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration) and requires the attacker to control the webhook secret of any one of the onboarded orgs — a normal admin capability for that org's own GitHub App, not the victim org. No access to the victim repository, its GitHub org, or a Shipit session/API token is needed. This is straightforward to exploit once the multi-org condition is met: craft one JSON body, compute one HMAC, and POST it to `/webhooks`.

### Recommendation
Cross-validate that the field used to select the verifying secret matches the field used to resolve the target repository/stack. Concretely, derive the resolved repository's owner from `repository.full_name` (or `organization.login` for org-scoped events) and require it to equal `repository.owner.login`/`organization.login` used in `verify_signature`, rejecting the webhook (422) on mismatch. Alternatively, have `Handler#repository_name` verify that the owner segment of `full_name` matches the organization whose secret validated the request.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`), and a `Stack` for `OrgA/victim-repo`.
2. As the admin of `OrgB`'s GitHub App (who legitimately knows `OrgB`'s `webhook_secret`), build a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgB_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#repository_owner` returns `"OrgB"`, so `Shipit.github(organization: "OrgB").verify_webhook_signature` succeeds. `PushHandler` then resolves `Repository.from_github_repo_name("OrgA/victim-repo")` and enqueues `GithubSyncJob` for `OrgA`'s stack with the attacker-supplied `expected_head_sha`, despite the attacker having no relationship with `OrgA`.
