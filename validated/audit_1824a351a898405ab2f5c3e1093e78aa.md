### Title
Webhook signature verification is scoped to `repository.owner.login`, but write path is keyed on the unrelated `repository.full_name` field, allowing cross-organization webhook forgery in multi-org Shipit deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate the HMAC signature against using `repository_owner`, which is read directly from the untrusted, unverified JSON body (`params.dig('repository', 'owner', 'login')`). Once the signature matches, the actual event handlers (`PushHandler`, `StatusHandler`, etc.) resolve the `Repository`/`Stack` to mutate using a *different* field from that same payload: `repository.full_name`. Nothing cross-checks that the organization whose secret validated the signature is the same organization whose repository is written to.

### Finding Description
```ruby
# app/controllers/shipit/webhooks_controller.rb
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The signature check binds `HMAC-SHA1(secret_for(repository.owner.login), raw_body)`. But the payload writer (base `Handler` class) does not use `repository.owner.login` at all — it independently parses `repository.full_name`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`Repository.from_github_repo_name` splits this string on `/` to look up owner and name independently of any authentication context: [3](#0-2) 

`PushHandler#process` and `StatusHandler#process` both act on `stacks`/`Commit` records resolved this way, e.g. triggering a `sync_github` or writing a commit status: [4](#0-3) [5](#0-4) 

Shipit explicitly supports multiple, independently configured GitHub Apps/organizations, each with its own `webhook_secret`, as shown by the test fixture with `OrgOne`/`OrgTwo` sections: [6](#0-5) 

**The broken binding (equality that should hold but doesn't):**
`organization_that_authenticated(repository.owner.login)` should equal `organization_of_repository_written(repository.full_name)`. Because both fields come from the same attacker-controlled JSON body and are never cross-checked, an attacker who legitimately controls one configured organization (and thus knows/can produce a valid signature with that organization's `webhook_secret`) can set `repository.owner.login` to their own org (so the signature check passes using their own secret) while setting `repository.full_name` to `"other-org/other-repo"` (a repository belonging to a different tenant configured on the same Shipit instance). The event is then processed as if it legitimately originated from `other-org`.

### Impact Explanation
This allows an attacker who owns a legitimately-configured (but different) GitHub organization on a shared, multi-tenant Shipit instance to inject forged `push`, `status`, `check_suite`, `pull_request`, or `membership` events that are attributed to and written against a stack/repository they do not control. Depending on handler, this can:
- Trigger unauthorized `GithubSyncJob`/`sync_github` calls against another org's stack (`push`).
- Falsify a commit's CI/deploy status (`status`), which several Shipit deploy-gating features rely on to decide if a commit is deployable.
- Alter team memberships (`membership` handler creates/removes `Membership` records for teams unrelated to the attacker's org).

This is a cross-tenant write into repository/stack state that the attacker was never authorized to touch, matching the "cross-repository writes" High-severity criterion.

### Likelihood Explanation
Requires: (1) the target Shipit deployment configured for multiple GitHub organizations (a documented, supported configuration), and (2) the attacker controls one of those organizations' GitHub App/webhook secret (i.e., is a legitimate customer/tenant of that Shipit instance, but not of the target org). No Shipit session, API token, or repository write access is required — only the ability to send a correctly-signed webhook body with attacker-chosen JSON fields, which any owner of a configured GitHub App can do by triggering (or directly crafting/replaying) a webhook delivery.

### Recommendation
In `WebhooksController#verify_signature`, after successful signature verification, re-derive the repository owner strictly from the same field used by `repository_owner` and require it to match the owner segment parsed by `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before dispatching to handlers. Reject (422) any event where these two owners diverge, closing the gap between "organization that authenticated" and "repository that is written."

### Proof of Concept
1. Shipit instance is configured with two organizations in `secrets.yml`: `OrgA` (attacker-controlled, webhook secret known to attacker) and `OrgB` (victim, has a repository/stack registered in Shipit).
2. Attacker crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker chosen sha>",
     "repository": {
       "owner": {"login": "OrgA"},
       "full_name": "OrgB/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` — valid, since they know `OrgA`'s secret.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and successfully verifies the signature. [7](#0-6) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")`, unrelated to `OrgA`, and enqueues `sync_github` for `OrgB`'s stack — a write the attacker was never authorized to trigger. [4](#0-3)
