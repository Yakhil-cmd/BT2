### Title
Nonce is advanced on a rejected `DelegateAction` when a function-call access key attaches a deposit and the protocol fix is not enabled - ([File: runtime/runtime/src/actions.rs])

### Summary
`validate_delegate_action_key` detects that a function-call-permission access key was used to sign a `DelegateAction` with a non-zero deposit — an explicitly disallowed combination — but the missing/conditional early return lets execution fall through to the nonce-persisting code at the end of the function instead of aborting immediately, mirroring the report's "detect an error but continue execution" pattern.

### Finding Description
In `validate_delegate_action_key`, once the sender's access key is resolved and nonce/expiry checks pass, the function checks function-call permission restrictions on the delegated action [1](#0-0) . When the single `Action::FunctionCall` in the delegate action carries a non-zero `deposit`, the code sets `result.result = Err(... DepositWithFunctionCall)` but only returns early `if ProtocolFeature::FixDelegateActionDepositWithFunctionCallError.enabled(...)`: [2](#0-1) 

The comment directly above the conditional return explicitly documents the bug class: *"Before this fix, the missing early return allowed execution to fall through to the receiver_id and method_name checks, which could overwrite this error with a different one."* When the feature is not enabled for the active protocol version, execution continues past the deposit-violation detection into the `receiver_id`/`method_name` checks [3](#0-2)  and, if those checks also pass, all the way to the nonce-commit block at the end of the function: [4](#0-3) 

Every other error branch in this function (`AccessKeyNotFound`, `DelegateActionRequiresNonGasKey`, `DelegateActionInvalidNonceIndex`, `DelegateActionInvalidNonce`, `DelegateActionNonceTooLarge`, `RequiresFullAccess`, `ReceiverMismatch`, `MethodNameMismatch`) returns immediately with `return Ok(())` before the nonce update, so a rejected delegate action normally does not advance the signer's nonce. The deposit-with-function-call path is the one exception when the fix feature is disabled: the error is recorded, but execution proceeds to bump and persist the access key / gas key nonce as if a legitimate action had been processed.

### Impact Explanation
Advancing the account's access-key nonce (or gas-key nonce) as a side effect of a rejected delegate action is a state change that should not occur for an invalid, unauthorized-by-permission transaction. This diverges from the invariant enforced on every other rejection path in the same function (no state mutation on failure) and constitutes an unauthorized state change driven purely by attacker-controlled input (a function-call-permission key signing a `DelegateAction` with a deposit). Depending on which protocol version is active, this can also let the final recorded error be silently overwritten by a different error (`ReceiverMismatch`/`MethodNameMismatch`) rather than the true `DepositWithFunctionCall` cause, degrading error-reporting fidelity for callers/relayers.

### Likelihood Explanation
This is reachable directly from a submitted `DelegateAction`/meta-transaction signed by any account holding a function-call-permission access key — no privileged or validator role is required. The condition is fully attacker-controlled: crafting a delegate action with a non-zero deposit on the sole `FunctionCall` action. Whether the vulnerable path is live on a given chain depends on whether `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError` is enabled for the current protocol version; on any deployment where it is not yet enabled, the bug is live for every meta-transaction with a function-call-permission signer.

### Recommendation
Make the early `return Ok(())` after setting `result.result = Err(... DepositWithFunctionCall)` unconditional (i.e., remove the `if ProtocolFeature::...enabled(...)` gate), so the function always aborts before reaching the receiver/method checks and before the nonce-persisting block, consistent with every other error branch in `validate_delegate_action_key`. If backward protocol compatibility is required, ensure the nonce-commit block itself is also gated so that under the old protocol version the nonce is not silently advanced on this rejection path.

### Proof of Concept
1. Create an account with a function-call-permission access key restricted to some `receiver_id`/`method_names`.
2. Sign a `DelegateAction`/`DelegateActionV2` containing exactly one `Action::FunctionCall` whose `deposit` is non-zero, targeting the permitted `receiver_id` and an allowed `method_name`.
3. Submit it while the active protocol version has `FixDelegateActionDepositWithFunctionCallError` disabled (pre-fix protocol version).
4. Observe: the action is rejected with `DepositWithFunctionCall` (or, if instead the receiver/method mismatched, that error masks the true cause), yet `validate_delegate_action_key` still executes the nonce-persist block [5](#0-4) , advancing the signer's access-key/gas-key nonce despite the action having been rejected — unlike every other rejection path in the same function, which returns before any state mutation.
