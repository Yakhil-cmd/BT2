### Title
Null-pointer-style dereference on `storage.assocStableUnits[trigger.unit]` allows a crafted primary AA trigger to crash node processing - ([File: aa_composer.js])

### Summary
`handleTrigger()` guards against a unit triggering more than one primary AA response by reading `storage.assocStableUnits[trigger.unit].count_aa_responses` directly, without checking whether `trigger.unit` actually has a cache entry in `assocStableUnits`.

### Finding Description
In the primary-trigger path of `handleTrigger`, the double-trigger check is: [1](#0-0) 
```js
// skip this check for dry-run which uses genesis unit as trigger unit
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && storage.assocStableUnits[trigger.unit].count_aa_responses && mci >= constants.pemCurvesFixMci)
    return bounce('a second primary trigger from the same unit is not allowed');
```
`storage.assocStableUnits` is an in-memory cache populated by `initStableUnits`/`initCaches` at startup and mutated by `resetStableUnits`/`shrinkCache`/`forgetUnit` at runtime [2](#0-1) . Entries are pruned from `assocStableUnits` once a unit becomes old enough (`shrinkCache`, called every 5 minutes) [3](#0-2) , and the cache is fully reset in some flows (`resetStableUnits` clears then re-populates it) [4](#0-3) . If `trigger.unit` (the unit that is being used as a primary AA trigger) is not present as a key in `assocStableUnits` at the moment this check runs — e.g. because the cache was reset/shrunk concurrently with a delayed or re-processed AA trigger, or because of any code path that invokes `handleTrigger` for a unit whose stable-unit cache entry hasn't been (re-)populated yet — `storage.assocStableUnits[trigger.unit]` evaluates to `undefined`, and `.count_aa_responses` throws a `TypeError: Cannot read properties of undefined`. This mirrors the CVE's root cause: a piece of state that is supposed to always be initialized before being dereferenced is read unconditionally, without the caller checking for the absence/failure case first (in the kernel case, `udp_prod_queue` being null because `udp_lib_init_sock()` failed; here, the cache entry being absent because the object was never inserted or was already evicted).

### Impact Explanation
An unhandled synchronous exception thrown deep inside AA-trigger processing (inside `updateInitialAABalances`'s callback, which is itself invoked from the unit-processing/writer pipeline) is not routed through the existing `bounce()`/`revert()` error-handling machinery used elsewhere in this same function for expected errors. A thrown `TypeError` here would propagate up out of normal control flow, and depending on the surrounding caller's exception handling, this can crash the node process or leave AA processing for a stable unit half-completed, causing the node to disagree with the rest of the network on the trigger's response/state, i.e. a denial-of-service/liveness/consensus-divergence class issue reachable simply by posting a payment (trigger) unit to a live AA.

### Likelihood Explanation
Triggering this specific window requires `trigger.unit` to already be stable (since AA responses are only computed for stable trigger units) yet somehow absent from `assocStableUnits`, which is not the normal case — under ordinary conditions `initStableUnits`/`markMcIndexStable` insert an entry for every stable unit before AA processing runs. I could not fully verify from static reading alone whether there is a genuinely reachable timing window (e.g., interaction between `shrinkCache`'s periodic eviction and delayed/retried AA processing, or `resetMemory`/`resetStableUnits` racing with in-flight secondary/primary trigger processing) that lets an attacker force this state deterministically from an unprivileged unit-posting client. This uncertainty limits confidence that this is reliably attacker-triggerable versus only occurring under internal race conditions.

### Recommendation
Guard the dereference the same way other cache lookups in this file already do (e.g. checking for `undefined` before use), for example:
```js
const objTriggerUnitProps = storage.assocStableUnits[trigger.unit];
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && objTriggerUnitProps && objTriggerUnitProps.count_aa_responses && mci >= constants.pemCurvesFixMci)
    return bounce('a second primary trigger from the same unit is not allowed');
```
and treat a missing cache entry as an internal error via `throw Error(...)` (to fail loudly/consistently rather than crash unexpectedly), or fetch/refresh unit props via `storage.readUnitProps` if the invariant that the unit must be cached cannot be guaranteed at this call site.

### Proof of Concept
I could not construct a concrete, self-contained reproduction demonstrating that an external, unprivileged unit-poster can force `trigger.unit` to be absent from `storage.assocStableUnits` at the exact moment `handleTrigger` runs this check — the cache is normally kept in sync with unit stabilization, and doing so would require winning a race against `shrinkCache`'s periodic (5-minute) eviction or an in-progress `resetMemory`/`resetStableUnits` call. This is a real, static null/undefined-dereference bug pattern (matching the CVE's bug class of dereferencing state without checking it was actually initialized/present), but I cannot confirm from code inspection alone that it is reliably reachable by a remote unprivileged trigger sender under normal node operation, as opposed to only occurring during rare internal race windows.
