### Title
Unauthorized locking of a victim's STX via `PreStxOp`/`StackStxOp` pairing that never verifies stacker ownership - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`PreStxOp::parse_from_tx` sets the future PoX "sender"/stacker identity purely from the *first* Bitcoin output (`vout=0`) of the PreStx transaction, while `StackStxOp::get_sender_txid` only requires the follow-up `StackStxOp` transaction's first input to spend the *second* output (`vout=1`) of that same PreStx transaction. Because Bitcoin lets anyone pay to any output address without proving control of it, and because control over `vout=1` (needed to satisfy the pairing check) is cryptographically unrelated to `vout=0`'s address, an attacker can name an arbitrary victim Stacks address as the `sender` for a `StackStxOp` and have the victim's real STX balance run through the `stack-stx` PoX contract call with `tx-sender` set to the victim, with rewards routed to an attacker-chosen `reward_addr`.

### Finding Description
The claimed equality that should hold is: *the Stacks principal whose STX gets locked by a processed `StackStxOp` == the principal who cryptographically authorized (signed for) that lock*. This equality is broken.

- `PreStxOp::parse_from_tx` derives `output` (the future stacker identity) solely from `outputs.get(0)` of the Bitcoin PreStx transaction, with zero requirement that the transaction's *inputs* (the actual Bitcoin funds/keys being spent) have any relationship to that output address: [1](#0-0) 
- `StackStxOp::get_sender_txid` only enforces that the `StackStxOp` transaction's first input spends `vout=1` of the referenced PreStx transaction — a completely different output than the one used to compute `sender`: [2](#0-1) 
- The burnchain classifier wires `pre_stack_stx.output` directly in as the `StackStxOp`'s `sender`, with no additional ownership check: [3](#0-2) 
- When the op is later applied, `sender` (i.e., `PreStxOp.output`, chosen freely by whoever built `vout=0`) is used verbatim as `tx-sender` for the Clarity `stack-stx` call: [4](#0-3) 
- Inside `stack-stx` (pox-4), the only checks are on the victim's *balance* and *stacking state* — never on whether `tx-sender` actually authorized this call, since there is no Stacks-level signature involved at all in this burnchain-op code path: [5](#0-4) 
- The `signer-sig`/`signer-key` check (`consume-signer-key-authorization`) only authorizes the *signer* (a pool/PoX-reward-address key that the attacker themselves controls), never the stacker (`tx-sender`/victim) — so it does nothing to close this gap.

Exploit flow:
1. Attacker picks victim Stacks address `V` (public information) that holds unlocked STX ≥ some `amount-ustx`.
2. Attacker crafts a Bitcoin `PreStxOp` transaction whose `vout=0` pays to the p2pkh address matching `V`'s hash160, and whose `vout=1` pays to an address the attacker controls (dust amounts only).
3. Attacker crafts a Bitcoin `StackStxOp` transaction whose first input spends `(pre_stx_txid, 1)` (which the attacker legitimately controls) and whose payload encodes `stacked_ustx`, `num_cycles`, and an attacker-generated `signer_key`/`signer-sig`/`max_amount`/`auth_id`.
4. On processing, `classify_transaction` resolves `sender = V` from the PreStxOp, and `process_stacking_ops` invokes `pox-4.stack-stx` with `tx-sender = V`.
5. If `V` has sufficient unlocked balance and is not already stacking/delegating, the call succeeds and `V`'s STX is locked for `num_cycles` reward cycles into a PoX address chosen entirely by the attacker.

No existing guard (`check()` on `StackStxOp`, `PreStxOp` having no `check()` at all, or the pox-4 Clarity assertions) verifies that the party who funded/authorized the Bitcoin spend of `vout=1` is the same party who controls `V`. The mechanism was seemingly intended so that a single Bitcoin keyholder pays for both outputs of the PreStx tx to "prove" they own the corresponding Stacks address, but nothing in the code enforces that `vout=0` and `vout=1` belong to the same key.

### Impact Explanation
The attacker can force-lock an arbitrary victim's unlocked STX into PoX stacking without any authorization from the victim, and redirect the PoX reward address (BTC/sBTC payouts earned on that locked STX) to an address the attacker controls. This is theft of PoX rewards that should have accrued to the victim's own locked stake, plus temporary freezing of the victim's STX for the chosen lock period (up to `POX_MAX_NUM_CYCLES`), matching the Critical category ("theft ... of sBTC rewards", "permanent/temporary freezing of staked STX ... never locked [by consent]"). This is repeatable against any address with a qualifying unlocked balance, at the negligible cost of a few dust-value Bitcoin transactions per victim.

### Likelihood Explanation
Preconditions are minimal: the attacker needs no privileged role, only the ability to broadcast ordinary Bitcoin transactions (explicitly permitted attacker capability — "craft burnchain stacking ops from their own Bitcoin inputs"). The victim must simply hold enough unlocked STX and not already be stacking/delegating in the target cycle — an extremely common state for most STX holders. The attack works in any epoch where `StackStxOp`/`PreStxOp` burnchain ops are accepted (2.05 through current pox-4 in Nakamoto), so it is broadly and repeatedly exploitable against many victims simultaneously.

### Recommendation
Tie the `sender`/stacker identity to the same Bitcoin key that must sign the follow-up `StackStxOp` spend, e.g., require `PreStxOp.output` to be derived from the *same* output (`vout=1`, the one the `StackStxOp` must spend) rather than `vout=0`, or otherwise cryptographically bind `vout=0`'s address to the input signer of the PreStx transaction. Alternatively, deprecate/disable the legacy burnchain-op stacking path for current PoX versions in favor of Stacks-native, tx-sender-signed `stack-stx` calls only.

### Proof of Concept
Rust integration test plan (using the harness already present in `stackslib/src/burnchains/tests/db.rs`):
1. Set up a victim Stacks address `V` funded with STX via genesis balances (as in existing stacking integration tests, e.g. `stacks-node/src/tests/neon_integrations.rs`).
2. Construct a `PreStxOp`/`BitcoinTransaction` with `outputs[0].address` = `V`'s legacy Bitcoin-equivalent address (hash160 of `V`) and `outputs[1].address` = an attacker-controlled address; process via `Burnchain::classify_transaction` and confirm `op.output == V` (mirrors `stackslib/src/burnchains/tests/db.rs:495-515`).
3. Construct a follow-up `StackStxOp`/`BitcoinTransaction` whose only input's `tx_ref == (pre_stx_txid, 1)`, encoding `stacked_ustx`, `num_cycles`, and an attacker-chosen `signer_key`/`signer-sig`. Process via `classify_transaction` and assert `op.sender == V`.
4. Run `StacksChainState::process_stacking_ops` (as in `stackslib/src/chainstate/stacks/db/blocks.rs`) with this op and assert:
   - Before: `stx-account V` reports `locked = 0`.
   - After: `stx-account V` reports `locked == stacked_ustx` and `unlock-height` matching the attacker-chosen `num_cycles`, with the PoX reward address equal to the attacker's chosen `reward_addr` — all without any Stacks transaction signed by `V`.
5. This demonstrates the equality "locked-STX owner == authorizing signer" is violated: `V`'s STX became locked and its future rewards routed to the attacker, with `V` never signing or approving anything.

        match tx.get_input_tx_ref(0) {
            Some((ref txid, vout)) => {
                if *vout != 1 {
                    warn!("Invalid tx: StackStxOp must spend the second output of the PreStxOp");
                    Err(op_error::InvalidInput)
                } else {
                    Ok(txid)
                }
            }
            None => {
                warn!("Invalid tx: StackStxOp must have at least one input");
                Err(op_error::InvalidInput)
            }
        }
    }
