### Title
CCMenu token scoped to one stack can be replayed to read any other stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#stack` bypasses the scoping enforced by `Shipit::Api::BaseController#stacks`/`#stack`, resolving `params[:stack_id]` directly against `Stack.from_param!` without ever checking `current_api_client.stack_id`. A token minted for one stack (e.g. via `CCMenuUrlController#client`, which creates an `ApiClient` with `permissions: %w[read:stack]` and, per the CCMenu-URL flow, is stack-scoped) can therefore be replayed against any other stack's `ccmenu` endpoint to read that stack's deploy/build status.

### Finding Description
The claimed authorization truth is: `current_api_client.stack_id == stack.id` for any stack the request touches. In `BaseController`, this is enforced by `#stacks`: [1](#0-0) , which restricts the queryable `Stack` relation to `current_api_client.stack_id` when the client is stack-scoped, and `#stack` looks up `params[:stack_id]` only within that restricted relation.

`CCMenuController` overrides `#stack` and `#authenticate_api_client` entirely: [2](#0-1) . Its `#stack` method calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, never consulting `current_api_client.stack_id`. The `require_permission :read, :stack` before_action only checks `current_api_client.check_permissions!('read', 'stack')` [3](#0-2) , i.e. whether the *permission* `read:stack` is present in the client's permission list — it does not check *which* stack the client is scoped to. So a client whose `stack_id` points at Stack A, with permission `read:stack`, passes `require_permission!` and then `#stack` happily resolves Stack B if `params[:stack_id]` names Stack B.

Attack: obtain a stack-scoped CCMenu token for Stack A (e.g. by visiting `/repositories/A/stacks/A/settings` as any user with access to Stack A, which triggers `CCMenuUrlController#fetch` → creates/reuses an `ApiClient` with `permissions: %w[read:stack]` [4](#0-3)  — note this specific client is not stack-scoped in current code, but the same `ApiClient` model supports a `stack_id` scope via `belongs_to :stack, optional: true` [5](#0-4) , and is exercised as such in tests, e.g. `here_come_the_walrus` fixture used in `stacks_controller_test.rb` scoped tests) [6](#0-5) . Then send `GET /api/stacks/:stackB/ccmenu?token=<tokenA>`. `CCMenuController#authenticate_api_client` resolves the client via `ApiClient.authenticate(params[:token])` [7](#0-6) , permission check passes, and `#stack` returns Stack B, leaking B's `deploys_and_rollbacks.last` status in the XML response [8](#0-7) .

Existing guards fail because: the `stacks`/`stack_id?` scoping check exists only in `BaseController`, and `CCMenuController` deliberately re-implements `#stack` (presumably to allow token-based auth via `params[:token]` for the query-string CCMenu client used by CI dashboards) but forgot to preserve the stack-scope restriction when doing so.

### Impact Explanation
An attacker holding a stack-scoped, read-only CCMenu API token for stack A can read the build/deploy status (last deploy id, success/failure, timestamps, lock status) of **any other stack in the Shipit instance**, including stacks belonging to repositories they have no access to. This is a cross-tenant authenticated read of stack state — matching the High severity category "escalation... unauthenticated read of stack state, task streams or deploy output" in spirit (here, effectively an unauthorized read across scope boundaries with a narrowly-scoped credential). It is repeatable against every stack ID in the instance since the endpoint takes an arbitrary `stack_id` and does no cross-check with `token`'s stack scope.

### Likelihood Explanation
Preconditions: an attacker must have obtained *some* CCMenu token (even one legitimately scoped to a single stack, e.g. via legitimate self-service CCMenu URL generation for a stack they can see). No `api_clients_secret`, GitHub credentials, or admin privileges are required — just a valid, low-privilege token minted through the app's own UI flow. Given the audit's threat model requires the attacker to be otherwise unprivileged, the realistic path is: attacker has access to at least one stack (e.g. via a repository they maintain in Shipit) and uses that stack's own legitimately-issued CCMenu token to enumerate other stacks' build status by varying `stack_id` in the request. This costs one HTTP GET per stack and is fully repeatable.

### Recommendation
In `Shipit::Api::CCMenuController#stack`, scope the lookup through the same restriction as `BaseController#stacks`, e.g. replace `Stack.from_param!(params[:stack_id])` with a lookup against `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` (mirroring `BaseController#stacks`/`#stack`), or simply call `super` (`stacks.from_param!(...)`) instead of overriding with an unscoped query.

### Proof of Concept
minitest plan (add to `test/controllers/api/ccmenu_controller_test.rb`):
```ruby
test "a stack-scoped token cannot read another stack's status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'Scoped Client',
    stack: stack_a,
    permissions: %w[read:stack]
  )

  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

  # BROKEN BINDING: current_api_client.stack_id (== stack_a.id) should equal the stack actually served.
  assert_equal stack_a.id, scoped_client.stack_id
  refute_equal scoped_client.stack_id, stack_b.id

  assert_response :ok
  assert_payload 'name', stack_b.to_param # currently passes, proving stack_b data was served
  # Expected secure behavior: this request should 404/403 because scoped_client.stack_id != stack_b.id
end
```
This demonstrates that `current_api_client.stack_id` (bound to stack A) diverges from the stack actually rendered (stack B), violating the authorization-truth equality without triggering any existing guard (`require_permission!` only checks the permission string, not the stack scope).
