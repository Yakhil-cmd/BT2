### Title
Attacker-controlled PR labels overwrite `PATH` in deploy environment, leading to RCE on the deploy host - (File: app/models/shipit/review_stack.rb)

### Summary
`Shipit::ReviewStack#env` merges every PR label (transformed to `LABEL_NAME.upcase => "true"`) directly into the environment hash used to build deploy commands, with no allow-list check against `deploy_spec.machine_env`/`VariableDefinition`. An attacker who can label their own PR (a label literally named `path`) can therefore inject `'PATH' => 'true'` into the process environment passed to `PTY.spawn`, corrupting binary resolution for every step of the next deploy on that review stack's working directory.

### Finding Description
The broken binding: the set of keys accepted into `Command#unbundled_env` (and ultimately `PTY.spawn`) should equal only `Shipit.shell_paths`-derived `PATH` plus keys explicitly permitted by `deploy_spec.machine_env`/`VariableDefinition::permit`, but in practice it equals `BASE_ENV keys ∪ {'PATH'} ∪ arbitrary-uppercased-PR-label-keys`.

Path traced:
- `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` verbatim from the webhook payload onto `PullRequest#labels`, with no filtering of label names [1](#0-0) .
- `ReviewStack#env` merges `super` (Stack's base env) with a hash built by upcasing every stored label name and mapping it to `"true"` [2](#0-1) . A label literally named `path` becomes `{"PATH" => "true"}`, unconditionally merged — no comparison against `deploy_spec.machine_env` or any `VariableDefinition` allow-list occurs anywhere in this method.
- `TaskCommands#env` merges `@stack.env` early in its chain, before the fixed keys, `deploy_spec.machine_env`, and `@task.env`, none of which reset `PATH` [3](#0-2) .
- `Command#unbundled_env` computes `BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)` — since `@env` (from the merged chain above) already contains `'PATH' => 'true'`, the final `.merge` overwrites the constructed safe `PATH` [4](#0-3) .
- `Command#start` then calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, executing every deploy-step binary through a `PATH` of `"true"` [5](#0-4) .

`filter_deploy_envs`/`filter_rollback_envs` (which call `EnvironmentVariables#permit(deploy_variables)`) exist in `DeploySpec` [6](#0-5) , but these are applied only to the deploy-time submitted variables (`@task.env`), not to `@stack.env`/`ReviewStack#env`. There is no guard filtering PR-label-derived env keys against any allow-list before they reach `Command`.

Attacker action: open a PR on a repository with `review_stacks_enabled: true` and `provisioning_behavior: allow_all`, wait for/trigger review-stack provisioning, then add a label named `path` (case-insensitive, since `.upcase` normalizes it) to that PR via the GitHub UI/API on their own repository, which GitHub relays to `POST /webhooks` as a `pull_request` `labeled` event. On the next deploy of that review stack, the corrupted `PATH` is used for every step.

### Impact Explanation
This is Critical: RCE on the deploy host. With `PATH=true`, subsequent binary lookups fail to resolve normally; combined with a writable stack working directory (the review stack's own checked-out repository, which the same attacker controls via their PR), the attacker can place executables (e.g., named `bundle`, `git`, `cap`) that get resolved via relative/`bundle exec`-style invocation or via any component of the deploy pipeline that still searches cwd-adjacent paths, executing attacker code as the Shipit deploy user. This affects only the attacker's own repository/review stack (the PR's stack), so the blast radius is scoped to tenants using `review_stacks_enabled` + `allow_all` provisioning — but it is fully repeatable per repository and per PR, and it is a real deploy-time execution corruption without any secrets or privileged role required.

### Likelihood Explanation
Preconditions are all attacker-triggerable without privilege: `review_stacks_enabled=true` and `provisioning_behavior=:allow_all` are repository configuration choices already documented as supporting unauthenticated review-stack creation for forks; labeling one's own PR requires no repository write access beyond opening the PR (label creation/assignment on a PR you opened, or via an already-existing label matching `path`, is within any contributor's/fork owner's capability depending on repo settings, and the exploit works with any label whose name upcases to `PATH`). No Shipit secrets, tokens, or session are needed — the webhook is legitimate, and `capture_labels` unconditionally trusts the payload's label list once signature verification passes (which is a separate, already-enforced control, not what's broken here). Attacker cost is a single PR + label + waiting for the next deploy trigger, fully repeatable.

### Recommendation
In `Shipit::ReviewStack#env`, filter the label-derived hash through the same allow-list mechanism used for deploy variables (e.g., `deploy_spec.filter_deploy_envs` / `VariableDefinition`), or explicitly reject/blacklist keys that collide with reserved environment variables such as `PATH`, `BUNDLE_PATH`, `HOME`, etc., before merging. At minimum, never allow arbitrary user-controlled data to set `PATH`; `Command#unbundled_env` should compute `PATH` last/authoritatively rather than allowing `@env` to override it, e.g. merge order should be `BASE_ENV.merge(@env.stringify_keys).merge('PATH' => ...)` so the constructed safe path always wins, or explicitly strip `'PATH'` from `@env` before merging.

### Proof of Concept
In `test/models/shipit/review_stack_test.rb` (not modifying, just describing intended assertions):
```ruby
test "#env allows PR label named 'path' to override PATH" do
  stack = shipit_stacks(:shipit)  # or a review stack fixture
  pull_request = stack.pull_request
  pull_request.update!(labels: ['path'])

  env = stack.env
  assert_equal 'true', env['PATH']
  refute_includes env['PATH'], Shipit.shell_paths.first
end

test "TaskCommands#env propagates malicious PATH label to Command" do
  task = shipit_deploys(:review_stack_deploy) # deploy on a stack whose pull_request.labels == ['path']
  commands = Shipit::TaskCommands.new(task)
  assert_equal 'true', commands.env['PATH']
end
```
Binding under test: `stack.env['PATH'] == "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` (expected, safe) vs. observed `stack.env['PATH'] == 'true'` after the label is set — the two diverge, confirming the break.
