### Title
Cross-repository `blocking_statuses` bypass via unscoped sha lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` updates every `Commit` row in the entire database that shares the reported sha, with no check that the commit's stack belongs to the repository whose webhook produced the event. An attacker who owns any repository (and can therefore send a genuinely-signed webhook for it) can push a commit object identical to one already present on an unrelated victim stack (same sha, since git shas are content-addressed and reproducible from public commit data), then fire a `success` status for it, which is written onto the victim's `Commit` record and defeats that stack's `blocking_statuses` gate.

### Finding Description
The broken binding is: `webhook.repository.full_name == commit.stack.repository.full_name` is required by the security model of `blocking_statuses`, but is never checked.

`StatusHandler#process` is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Unlike every other webhook handler, it does not use the base class's `stacks` helper, which scopes lookups to `Repository.from_github_repo_name(repository_name)&.stacks` [2](#0-1) . Instead it queries `Commit` globally by `sha` across all stacks/repositories/tenants in the installation, and calls `create_status_from_github!` on every match, regardless of which repository the webhook came from.

`WebhooksController#verify_signature` only proves the payload is a genuinely signed webhook for the organization named in the payload's own `repository.owner.login` — it does not constrain which `Commit` rows the handler is permitted to mutate [3](#0-2) . Signature verification is repository/organization-scoped for authentication purposes only; it says nothing about authorization to mutate a different tenant's commit records.

Downstream, `Commit#blocked?` walks undeployed commits and checks `blocking?` on each, and `Status::Common#blocking?` is `!success? && commit.blocking_statuses.include?(context)` [4](#0-3) . Once the forged `success` status lands on the shared-sha `Commit` row (via `create_status_from_github!` → `add_status` → `statuses.replicate_from_github!`), that commit's `blocking?` becomes false, so `Commit#blocked?` [5](#0-4)  and `Commit#deployable?` [6](#0-5)  unblock the victim stack's newer undeployed commits, feeding into `UndeployedCommit#deploy_state`/`deploy_disallowed?` [7](#0-6)  and continuous delivery/redeploy decisions.

Exploit flow:
1. Attacker owns/controls a repository with the Shipit GitHub App installed (or any repository whose org is registered in `Shipit.github(organization:)`), giving them the ability to send a validly signed `status` webhook for that repository.
2. Attacker obtains a commit object that already exists in a victim stack's history — either by forking a public victim repo, or by reproducing a byte-identical commit (same tree, parents, author/committer, timestamps, message) so its SHA matches, and pushes it into their own repo.
3. Attacker fires (or GitHub fires on their behalf) a `status` event with `state: success` for that sha on their own repository.
4. `WebhooksController#verify_signature` validates it correctly — it is a real webhook for the attacker's own repo.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the victim's `Commit` row (same sha, different `stack_id`), and calls `create_status_from_github!` on it, writing a `success` status attributed to the attacker's payload onto the victim's commit.
6. `blocking?` flips to false for that commit; `Commit#blocked?` on all newer undeployed commits in the victim stack now returns `false`.

No existing guard prevents this: `verify_signature` checks only the requesting organization's key, not the target commit's owning stack; `ExplicitParameters` (`ClassName.params` block in `StatusHandler`) validates shape/types of the payload fields but not repository ownership of the affected records; there is no `require_permission!`/`stacks` scoping call in `StatusHandler#process` as there is in other handlers.

### Impact Explanation
A record (a `Status`) is written for a repository ("victim's stack") that never authenticated the write — the write was authenticated only for the attacker's own repository. This directly satisfies "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy" (Critical). Concretely, it clears a `blocking_statuses` safety gate the victim relies on for compliance/security sign-off (e.g., `soc/compliance` type contexts, per existing test fixtures `shipit_commits(:soc_second)`/`soc_third` [8](#0-7) ), enabling continuous deployment or the redeploy button to proceed on a stack the attacker does not control. The attacker never needs credentials for the victim's org/repo/stack. Blast radius: any tenant stack sharing a commit sha with any repository the attacker can trigger a webhook from (including their own throwaway repo) is affected — this is not limited to one target, since the lookup is entirely global (`Commit.where(sha: ...)` unscoped by stack/repository).

### Likelihood Explanation
Preconditions: victim stack must have `blocking_statuses` configured, an undeployed commit chain, and a shared commit sha with a repo the attacker controls. The attacker cost is low: they need only a repository they own with the Shipit GitHub App/webhook configured (a normal, unprivileged setup step available to "any GitHub user"), and the ability to reproduce a git commit object with identical sha — trivial when forking a public repo (fork retains identical shas) or when a commit is otherwise reachable/known (e.g., a shared open-source dependency commit, a common initial commit, or a commit an attacker learns via the victim's public commit history/PR). No secrets, sessions, or team membership are required. The attack is repeatable against any stack sharing a discoverable sha.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to the repository that sent the webhook, mirroring the base `Handler#stacks` helper, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures the sha lookup is restricted to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`'s own stacks, closing the cross-tenant write.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, new):
```ruby
test "status webhook from an unrelated repository does not clear another repo's blocking status" do
  victim_blocking_commit = shipit_commits(:soc_second) # belongs to victim stack, currently pending/blocking
  victim_descendant = shipit_commits(:soc_third)

  # Precondition: block is active
  assert_predicate victim_blocking_commit, :pending?
  assert_predicate victim_blocking_commit, :blocking?
  refute_predicate victim_descendant, :deployable?

  # Attacker's payload references an unrelated repository, but with the SAME sha
  # as the victim's blocking commit (simulating the same-sha technique)
  attacker_payload = {
    'sha' => victim_blocking_commit.sha,
    'state' => 'success',
    'context' => victim_blocking_commit.stack.blocking_statuses.first,
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } },
    'branches' => [{ 'name' => 'main' }]
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  victim_blocking_commit.reload
  victim_descendant.reload

  # ASSERTION: binding must still hold -- an unrelated repo's webhook must NOT
  # be able to flip the victim's blocking commit state.
  refute_predicate victim_blocking_commit, :blocking?   # currently FAILS (flips to false) -- vulnerable
  refute_predicate victim_descendant, :deployable?       # currently would incorrectly become deployable
end
```
This test demonstrates `blocked?`/`deployable?` flipping purely because `Commit.where(sha:)` in `StatusHandler#process` ignores `payload['repository']['full_name']`, with no live GitHub calls (fixture-only, single-process minitest).
