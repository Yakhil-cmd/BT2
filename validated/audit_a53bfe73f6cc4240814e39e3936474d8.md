### Title
Interest-accrual `i128` overflow permanently freezes a large market before `MAX_BORROW_INDEX_RAY` can cap the index - (File: common/src/rates/index.rs)

### Summary
Every pool verb runs `interest::global_sync` before mutating state, and accrual computes `borrowed * borrow_index` in `i128` RAY space. On a sufficiently large market at sustained high utilization, that product overflows `i128` and panics with `MathOverflow` *before* the `MAX_BORROW_INDEX_RAY` ceiling in `update_borrow_index` can ever engage. From that point every call that touches the market — `supply`, `borrow`, `withdraw`, `repay`, `seize_positions` (liquidation), `update_indexes`, `net_settle`, `recapitalize`, `claim_revenue` — reverts forever. This is the on-chain analog of CVE-2014-9808: a crafted input (a whale-scale, high-utilization market left to accrue) drives the code into a crashing path that permanently denies service.

### Finding Description
`update_borrow_index` is the sole writer of `borrow_index` and clamps it to `MAX_BORROW_INDEX_RAY` = 1e36, i.e. the index itself can never exceed ~1e9× [1](#0-0) [2](#0-1) . But the accrual path multiplies the scaled debt by the index in `i128`: `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` and `borrowed.mul(env, old_borrow_index)`, and `Cache::calculate_utilization` calls `scaled_to_original(borrowed, borrow_index)` / `scaled_to_original(supplied, supply_index)` on every load [3](#0-2) [4](#0-3) [5](#0-4) . RAY values carry 27 decimals, so `scaled * index` overflows `i128` (~1.7e38) when `scaled_raw * index_raw / 1e27 > i128::MAX` — roughly when scaled shares exceed ~1.7e38 RAY-units divided by the index. A market holding ~1e27 base units of an 18-decimal asset reaches this at an index of ~170×, which the configured rate curve (up to `MAX_BORROW_RATE_RAY` = 2 RAY/year equivalent slope) can produce long before `borrow_index` approaches 1e36.

The dedicated test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates this end-to-end: `try_update_indexes_for` reverts `MathOverflow`, and because every verb accrues first, `try_withdraw_raw` and `try_repay` revert with the same error; the assertion confirms `borrow_index < MAX_BORROW_INDEX_RAY`, i.e. the safety cap never engaged [6](#0-5) . There is no governance escape path that skips accrual — `update_params`, `claim_revenue`, `seize_positions`, and `recapitalize` all run `Cache::load` → `global_sync`, which panics in the same multiply.

### Impact Explanation
Permanent freezing of funds for the entire affected market. Once the overflow line is crossed, suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize, and the accrued bad debt cannot be socialized through that market's own state — every path reverts in `global_sync`. All supplied principal and earned yield in that market is locked indefinitely; the pool contract is unable to operate the market. Note the upstream fix path (contract upgrade) is out of scope; in-scope, no entrypoint recovers it.

### Likelihood Explanation
A single unprivileged address can create the precondition with no privileged action: `supply` a very large amount of a listed low-priced, high-decimals asset and `borrow` it to high utilization (the test uses 98% on the XLM-style curve). Caps can bind, but the cap domain admits up to `i128::MAX / 10^(27-d)` units and `lift_caps` shows configs at that scale are reachable through normal governance-listed markets; the attacking capital is denominated in an asset the attacker may hold cheaply. After setup, only time/accrual is needed — the test reaches the cliff within the asserted bound at 98% utilization. No price manipulation, oracle dishonesty, or privileged parameter is required; the curve's high-utilization rates are a legitimate, configured regime. Uncertainty: the number of accrual periods depends on the configured rate curve, and a market with caps or rates too low to reach ~170× index before utilization drops would not hit it; but the test proves at least one legitimately configurable curve crosses it, and `MAX_BORROW_INDEX_RAY` provides no protection at any rate.

### Recommendation
Make accrual overflow-safe or bound it before the index is applied:
- In `common/src/rates/index.rs::update_borrow_index`, clamp `new_index` not only at `MAX_BORROW_INDEX_RAY` but at the largest index for which `borrowed * index` still fits `i128` (`min(MAX_BORROW_INDEX_RAY, i128::MAX * RAY / borrowed)`), and clamp `supply_index` analogously against `supplied` in `update_supply_index`.
- Alternatively, compute `calculate_supplier_rewards` and `calculate_utilization` through `I256` intermediates (the machinery already exists in `fp_core::to_i256_operands` [7](#0-6) ) so accrual can complete and cap the index instead of panicking.
- Document the corrected market-size/time-to-freeze bound in `docs/reference/formulas.md`, which the test notes is currently wrong.

### Proof of Concept
The repository already contains a reproducer:

`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356` — `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`:
1. List an 18-decimal market (`BIG18`) with the XLM curve and lifted caps.
2. `supply_raw(BOB, "BIG18", 1e9 * 1e18)`; `borrow_raw(ALICE, "BIG18", 0.98 * principal)` — both ordinary unprivileged entrypoints.
3. Advance time in one-year steps; `try_update_indexes_for(&["BIG18"])` eventually returns `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`.
4. `try_withdraw_raw(BOB, "BIG18", 1)` and `try_repay(ALICE, "BIG18", 1.0)` both revert `MathOverflow` — the market is permanently frozen, since every entrypoint accrues before acting.

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
