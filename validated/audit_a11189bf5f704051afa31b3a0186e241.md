## Analysis

The external report's core issue is a mismatch between **who is authorized to act** (the signer/session authority) and **which account actually supplies the funds** (the true source account) — the `transfer` instruction trusted "is this a valid signer" without checking that the *same* account was the one being debited.

The closest reachable analog in `ocore` is in the Autonomous Agent (AA) trigger-composition logic. When an AA is triggered, `getTrigger()` derives the AA-visible "sender identity" (`trigger.address`) purely from `objUnit.authors[0].address`, while the actual bytes/asset credited to that identity (`trigger.outputs`) are summed from **all** payment outputs addressed to the AA in the unit, regardless of which author's inputs actually funded them: [1](#0-0) 

Because a unit can legitimately have multiple independent authors (each with their own inputs) up to `constants.MAX_AUTHORS_PER_UNIT`, and `validatePaymentInputsAndOutputs` only requires that an input's `address` be *one of* the authors of the unit — not that it correspond to a particular output or to `authors[0]` specifically: [2](#0-1) 

...the AA identity used for crediting/withdrawing funds (`trigger.address`) is never tied to which author's inputs actually paid. AA templates widely used in this codebase's own samples key balances and withdrawal authorization purely off `trigger.address`: [3](#0-2) [4](#0-3) 

### Title
Trigger identity (`trigger.address`) is decoupled from the actual funding source in multi-authored AA triggers — (File: `aa_composer.js`)

### Summary
`getTrigger()` sets `trigger.address` to `objUnit.authors[0].address` and separately sums *all* payment outputs sent to the AA in the unit into `trigger.outputs`, without verifying that the funds attributed to `trigger.address` actually originated from that author's own payment inputs.

### Finding Description
`getTrigger(objUnit, receiving_address)` builds the trigger object as:
```js
var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
...
payload.outputs.forEach(function (output) {
    if (output.address === receiving_address) {
        trigger.outputs[asset] += output.amount;
    }
});
``` [1](#0-0) 

`trigger.address` is used pervasively by AA oscript authors as the "identity" of the depositor/withdrawer (e.g. `var[$key] = var[$key] + trigger.output[[asset=base]]` and later `trigger.address == $key` gating withdrawals). However, `trigger.address` is derived solely from the *first sorted author* of the unit, while the actual byte/asset amount credited (`trigger.outputs`) is aggregated from **every** output addressed to the AA in that unit — regardless of which author's inputs financed those outputs.

`validateAuthors`/`validatePaymentInputsAndOutputs` permit multi-authored units where each author supplies distinct inputs, requiring only that an input's `address` be *some* author of the unit: [5](#0-4) [2](#0-1) 

There is no constraint tying a specific author's inputs to a specific output, nor any restriction preventing a trigger unit itself from having multiple authors (the `arrAuthors.length !== 1` restriction only applies to AA-generated response units, not to user-submitted trigger units): [6](#0-5) 

This is the same authorization class as the reported bug: the code validates "is this account party to a transaction that was properly authorized" (an author signed the unit) but never validates "is this the account whose balance is actually being moved," letting the identity used for crediting/authorizing withdrawal differ from the true source of the funds.

### Impact Explanation
Any AA template that keys balances/permissions off `trigger.address` (a documented and widely used pattern, as shown in the shipped sample AAs `a_bank_without_percent.oscript`, `order_book_exchange.oscript`, `sell_asset_for_bytes.oscript`, `ico_with_milestones.oscript`) can misattribute deposits: if a unit combining inputs from two different addresses (two authors) sends funds to such an AA, only `authors[0]`'s address is recorded as the depositor for the *entire* combined amount. Since `authors[0]` also satisfies the AA's withdrawal condition (`trigger.address == $key`), that author can subsequently withdraw funds that were actually paid for by the co-author's inputs — an AA fund loss / unauthorized-spending outcome for the second author.

### Likelihood Explanation
Exploitation requires a multi-authored unit combining a victim's inputs with an attacker's inputs into a single payment to a vulnerable AA — a scenario that can arise from joint/consolidated-payment features (e.g. shared/multi-signature spending flows, batch payments proposed by wallets, or crowdfunding-style joint contributions) where a user is asked to co-sign a transaction without realizing that the AA will attribute the whole deposit to the other co-author. The attacker fully controls which of their own addresses is used as `authors[0]` (they can generate many candidate addresses to guarantee alphabetical precedence), making this deterministically exploitable once a victim can be induced to co-sign such a unit.

### Recommendation
Track, per AA output, which author's inputs actually financed it (or restrict primary AA-triggering units to a single author, consistent with how AA response units are already restricted to `arrAuthors.length === 1`), so that `trigger.address`/crediting logic cannot be decoupled from the genuine source of funds. At minimum, document and enforce that multi-authored units must not be treated as valid AA triggers, closing the gap between signer identity and fund source in the same way `arbiter_contract.js` already had to patch an analogous "combining transactions" issue with an explicit `["not", ["has", {what:"input", address:"other address"}]]` guard.

### Proof of Concept
1. Attacker generates address `A` (choosing one that sorts before the intended victim address `V`, easily done by generating several candidate addresses).
2. Attacker convinces `V` to co-sign a single unit with two authors `[A, V]`, containing one `payment` message whose combined inputs come from both `A` and `V`, with a single output of `amount = inputs_A + inputs_V` sent to AA address `D` implementing a deposit/withdraw pattern like `test/samples/a_bank_without_percent.oscript`.
3. When the unit stabilizes, `getTrigger()` sets `trigger.address = A` (authors[0]) and `trigger.outputs.base = inputs_A + inputs_V` [1](#0-0) .
4. The AA credits `var['balance_A_base'] += inputs_A + inputs_V`, attributing V's contribution to A.
5. Attacker later sends `trigger.data.withdraw` from address `A`; since `trigger.address == A` satisfies the AA's stored balance key, attacker withdraws the full combined amount, including V's funds, as shown by the withdrawal case logic in [7](#0-6) .

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
