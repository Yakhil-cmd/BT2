### Title
Liquidation full-close path interprets duplicate offered legs inconsistently — merged total drives the refund plan while the token pull uses only the first matching leg - (File: contracts/controller/src/positions/liquidation/apply.rs)

### Summary
The bug class in the external report is *ambiguous parsing of a single input stream between two consumers* (a bare-LF chunk boundary read differently by front- and back-end), which enables smuggling. The XOXNO Lending analog is a genuine dual-interpretation of the liquidator's `debt_payments` list: the repayment planner aggregates duplicate `(hub_asset, amount)` legs into one total, while the settlement pull `offered_amount` resolves only the *first* matching leg. The two consumers therefore disagree on how much the liquidator offered, by the sum of all duplicate legs.

### Finding Description
`calculate_repayment_amounts` in `contracts/controller/src/positions/liquidation/math.rs:120` calls `payments::aggregate_positive_payments` (`contracts/controller/src/payments.rs:65-101`), which merges all duplicate legs for a hub asset into a single total in first-seen order. On that merged total it caps `payment_amount` at `actual_debt` and pushes any remainder into the `refunds` vector (`math.rs:139-147`).

In `apply_liquidation_repayments` (`contracts/controller/src/positions/liquidation/apply.rs:54-56`), when a full-close plan supplies `offered`, the per-leg pull is computed by `offered_amount` (`apply.rs:90-93`), which is `offers.iter().find(|(key, _)| key == hub_asset)` — it returns the amount of the **first** matching raw leg, not the merged total. `transfer_amount_measured` then pulls only that first amount (`apply.rs:58-65`), and the pool repays `received`, refunding to `payer` only what exceeds the debt (`contracts/pool/src/ops/repay.rs:44-57`).

So for `debt_payments = [(asset, D), (asset, D)]` against a debt of `D`: the plan records a refund of `D` (merged `2D` minus debt `D`), yet only `D` is ever pulled from the liquidator and the pool's own overpayment refund is `0`. The planned refund of `D` is unfunded by the pull — the controller-side refund ledger and the actual token flows disagree by exactly the duplicate amount. This is precisely the smuggling shape: one parser (aggregation) counts the full stream, the other parser (`find`, first-match) silently truncates it at the first boundary.

### Impact Explanation
If the planned `refunds` entries are paid out from protocol-held balances (controller custody or the pool refund path) after the pull, the liquidator is paid `D` that was never received — direct theft of user funds while also seizing collateral for a debt the victim's repayment never actually funded beyond `D`. If the refund is not separately payable, the discrepancy at minimum makes the full-close refund accounting internally inconsistent (`InternalError` paths / stranded-funds DoS on a permissionless, always-open `liquidate` entrypoint). I was not able to fully trace where `refunds` produced by `calculate_repayment_amounts` are settled in `liquidation/mod.rs` before the iteration limit, so the precise fund source is unverified — but the dual-interpretation defect itself is confirmed in code.

### Likelihood Explanation
`liquidate` is permissionless and open even during pause, and `debt_payments` is an attacker-controlled `Vec<HubPayment>` that accepts duplicates by design (per `docs/reference/endpoints.md:51`). Triggering requires only submitting duplicate legs in a full-close liquidation, reachable by any unprivileged address.

### Recommendation
Aggregate `offered` with `aggregate_positive_payments` before the pull (or look the leg up in the merged map the planner produced), so the pull amount, the repayment leg, and the refund computation all consume the same interpretation of the input. Alternatively reject duplicate legs outright in liquidation payment lists.

### Proof of Concept
Call `liquidate(liquidator, victim_id, debt_payments = [(hub_asset, D), (hub_asset, D)], SeizeMode::Transfer)` on an account whose `hub_asset` debt is `D`. `aggregate_positive_payments` merges the legs to `2D`, so the plan queues a `D` refund (`math.rs:139-147`); `offered_amount` pulls only the first `D` (`apply.rs:90-93`), so the pool's own overpayment refund is `0` (`repay.rs:44-57`), leaving the planned `D` refund unfunded/divergent from actual token flows.
