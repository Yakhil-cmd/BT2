### Title
Cross-Organization Commit-Status Forgery via Webhook Signature/Target Mismatch in `StatusHandler` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate a webhook against using the payload's `repository.owner.login` field, but `StatusHandler#process` — the handler that actually mutates state — never checks that field, or any repository identifier, at all. It matches purely on commit `sha` across the entire database. This breaks the binding "organization authenticated == repository/commit actually written," letting an attacker who controls (or targets) any organization configured with **no** `webhook_secret` forge a `status` event that updates commit statuses belonging to a completely different, fully-secured organization/stack, as long as the SHA happens to match.

### Finding Description
`WebhooksController#verify_signature` derives the organization used for signature verification exclusively from the untrusted payload: [1](#0-0) [2](#0-1) 

The resulting `GitHubApp` performs the actual signature comparison: [3](#0-2) 

Note the early `return true unless webhook_secret` — Shipit explicitly supports (and documents) configuring an organization's GitHub App **without** a `webhook_secret`, and supports multiple GitHub Apps for multiple organizations simultaneously: [4](#0-3) [5](#0-4) 

So for any organization whose app has no secret configured, `verify_signature` passes unconditionally regardless of the request body.

Once past `verify_signature`, the dispatched handler is what actually authorizes *which repository/stack* gets written. Most handlers (e.g. `PushHandler`, `CheckSuiteHandler`) correctly scope to the repository named in the payload via the base `Handler#stacks`/`#repository_name` helpers, which key off `repository.full_name`: [6](#0-5) [7](#0-6) [8](#0-7) 

`StatusHandler`, however, does **not** call `stacks`/`repository_name` at all — it looks up commits solely by SHA, globally: [9](#0-8) 

Thus the equality that should hold — *organization authenticated by the signature check* == *repository/commit actually written by the handler* — does not hold for `status` events. The signature check is scoped to `repository.owner.login`; the actual write is scoped to nothing but a raw `sha` string that can collide with a commit belonging to any stack/organization tracked by this single Shipit instance.

### Impact Explanation
An attacker with no Shipit credentials, no `ApiClient` token, and no access to the victim organization's GitHub App secret can forge a `status` webhook (`state: success`, arbitrary `context`) for any commit SHA that exists in the Shipit database, as long as they route the request through an organization configuration that has no `webhook_secret` set (a documented, supported configuration for any org onboarded onto a multi-org Shipit instance) or one whose HMAC they can otherwise trivially satisfy. Because commit statuses are used to satisfy `ci.require` gates and other deploy/merge readiness checks, this can flip a targeted commit belonging to an unrelated, secured organization/stack from "not deployable" to "deployable," enabling an unauthorized deploy, or feeding a false-green status into the continuous-delivery/merge-queue logic. This matches the accepted "unauthorized deploy, rollback or merge" impact category.

### Likelihood Explanation
Likelihood is elevated relative to the analog report because, unlike `ScrollChain.commitBatch` (restricted to an `OnlySequencer` allowlist), `POST /webhooks` is an unauthenticated, internet-reachable endpoint by design — the security boundary is entirely the per-organization HMAC check. Any Shipit deployment onboarding more than one GitHub organization, where at least one organization's app is left without a `webhook_secret` (explicitly presented as an optional field in `docs/setup.md` and the example secrets files), is exposed. Even where all configured `webhook_secret`s are set, the underlying design flaw (no correlation between the field used to select the signing org and the field/identifier used by `StatusHandler` to select the record to mutate) remains latent and is a real deviation from the pattern used by every other handler in the same directory.

### Recommendation
- In `StatusHandler#process`, scope the `Commit` lookup to the stacks resolved from the payload's `repository.full_name` (as `PushHandler`/`CheckSuiteHandler` already do), rather than searching all commits by SHA alone.
- In `WebhooksController#verify_signature`, after successfully verifying the signature for `repository_owner`, additionally assert that `repository_owner` matches the owner segment parsed out of `repository.full_name` (or `repository.owner.login`) before dispatching to handlers, so the authenticated organization and the organization whose data will be written are provably the same value.
- Consider disallowing/warning when a multi-organization Shipit deployment configures any organization with a blank `webhook_secret`, since it silently disables authentication for that organization's inbound webhooks.

### Proof of Concept
1. Configure Shipit with two GitHub App organizations, e.g. `TrustedOrg` (has `webhook_secret` set) and `UnsecuredOrg` (per the documented optional schema, `webhook_secret` left blank).
2. Identify (or guess) a commit SHA belonging to a stack under `TrustedOrg`, e.g. one required to pass `ci/required-check` per that stack's `shipit.yml` `ci.require`.
3. Send, with no valid credentials and any/garbage `X-Hub-Signature`:
```
POST /webhooks
X-Github-Event: status
{
  "repository": { "owner": { "login": "UnsecuredOrg" }, "full_name": "UnsecuredOrg/anything" },
  "sha": "<TrustedOrg commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. `verify_signature` resolves `Shipit.github(organization: "UnsecuredOrg")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally — the request is accepted.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the `TrustedOrg` commit (unrelated to `UnsecuredOrg`), and calls `create_status_from_github!`, marking the required CI check as passing on a repository/organization the attacker never authenticated against.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
