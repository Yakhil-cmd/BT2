This confirms the multi-org design: each configured GitHub organization has its own independent `webhook_secret` in `Shipit.github_app_config` [1](#0-0) , and `WebhooksController#verify_signature` selects which secret to validate against solely from the payload's `repository.owner.login` (or `organization.login`) field [2](#0-1) . However, none of the event handlers use that same field to resolve the target repository/stack — they instead resolve it from `payload.dig('repository', 'full_name')` [3](#0-2) , a completely independent, unauthenticated field of the same JSON body.

### Title
Webhook signature is bound to `repository.owner.login`, but event handlers act on the unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks a per-organization `webhook_secret` using `repository_owner` (`params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')`) and HMAC-validates the raw body against it [4](#0-3) [5](#0-4) . Once the signature is accepted, the whole raw payload is dispatched unmodified to the event handlers [6](#0-5) . Every handler, however, resolves the affected `Repository`/`Stack` from `repository.full_name`, a distinct field of the same payload that was never part of the signature-selection logic and is not cross-checked against `repository.owner.login` [3](#0-2) , [7](#0-6) , [8](#0-7) .

### Finding Description
Shipit supports multi-tenant GitHub App configuration, one entry per organization, each carrying an independent `webhook_secret` (`Shipit::TOP_LEVEL_GH_KEYS`, `github_app_config`) [9](#0-8) [1](#0-0) , as demonstrated by the two-tenant fixture `secrets_double_github_app.yml`. The binding the system implicitly relies on is:

`organization whose secret validated the signature == organization that owns the repository the handler mutates`

The controller only checks `owner.login`'s secret [5](#0-4) , while every downstream handler (push, pull_request opened/labeled/edited/closed, check_suite, status, membership) keys off `repository.full_name` to look up the target `Repository`/`Stack` [3](#0-2) . Nothing enforces that `full_name`'s org prefix matches `owner.login`. A caller who knows (or controls) the `webhook_secret` configured for *any one* tenant organization onboarded to a shared/multi-tenant Shipit instance can sign an otherwise-arbitrary JSON body with that tenant's secret, set `repository.owner.login` to that tenant (satisfying `verify_signature`), and set `repository.full_name` to `victim-org/victim-repo` belonging to a *different* tenant configured on the same Shipit instance. The push handler would then invoke `stack.sync_github` [10](#0-9)  and pull-request handlers would archive/unarchive review stacks or capture PR metadata [11](#0-10)  for a repository the attacker's org has no relationship to — a cross-tenant/cross-repository write triggered purely by controlling one tenant's own webhook credential rather than the victim's.

### Impact Explanation
This crosses the "cross-repository writes" bar explicitly called out as Critical impact: an attacker who only holds credentials scoped to their own onboarded organization's webhook can force Shipit actions (sync, archive/unarchive review stacks, label capture, PR state mutation) against a stack belonging to a different organization's repository on the same multi-tenant Shipit deployment.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (supported and tested via `github_app_config`/`secrets_double_github_app.yml`) and requires the attacker to already be a legitimate low-privilege tenant with access to their own org's `webhook_secret` (e.g. as configured by their own GitHub App/organization webhook). No access to the victim org's secret, GITHUB_TOKEN, or Shipit user session is needed — only their own tenant's credential and knowledge of the victim's `full_name`.

### Recommendation
In `Handler#repository_name`/`stacks`, cross-validate that the resolved `Repository`'s owner matches the organization whose `webhook_secret` was used to verify the signature (thread the verified organization through from `WebhooksController#verify_signature` into the handler `payload`, and reject/ignore events where `repository.full_name`'s owner segment does not match `repository.owner.login`/the verified organization).

### Proof of Concept
1. Shipit is deployed with two tenants configured, `OrgOne` and `OrgTwo`, each with its own GitHub App and `webhook_secret` [12](#0-11) .
2. Attacker controls `OrgOne`'s webhook secret (legitimately, as `OrgOne`'s own tenant admin).
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using `OrgOne`'s `webhook_secret` and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "OrgOne")` and accepts the signature [4](#0-3) .
6. `PushHandler` resolves stacks via `Repository.from_github_repo_name("OrgTwo/victim-repo")` [3](#0-2)  and triggers `sync_github` on `OrgTwo`'s stack, entirely outside `OrgOne`'s authorization scope.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
