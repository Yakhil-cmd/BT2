### Title
Webhook signature verification keys off `repository.owner.login` while every handler resolves the target stack from `repository.full_name`, letting one authenticated GitHub organization forge events for another organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC against using `repository.owner.login` (or `organization.login`), but every webhook `Handler` subsequently resolves the actual `Stack`/`Repository` to act on using the completely independent `repository.full_name` field of the *same, already-signed* payload. Because the two fields are never cross-checked, a value that legitimately authenticates as "this request came from GitHub App configured for org A" does not guarantee that the repository being acted upon actually belongs to org A. This is the same class of bug as the reported issue: a modifier/authorization check binds to one identity (`masterPenPie` vs. the actual caller) while the executed logic acts on a different, unverified party.

### Finding Description
In a multi-organization Shipit deployment (explicitly supported and documented in `docs/setup.md`, `config/secrets.development.shopify.yml`), each GitHub organization has its own `app_id`, `installation_id`, and `webhook_secret`: [1](#0-0) 

The controller picks the verification secret purely from `repository_owner`, derived from the payload: [2](#0-1) [3](#0-2) 

Once `verify_webhook_signature` passes (HMAC-SHA1 over the full raw body using org A's `webhook_secret`), the raw JSON is handed unmodified to every registered handler: [4](#0-3) 

Every handler, however, resolves *which repository/stack* to operate on using a different field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

Nothing in the pipeline enforces that `repository.owner.login` (the field used to select and validate the signing secret) matches the owner encoded in `repository.full_name` (the field used to pick the actual target `Stack`). Since the entire raw body is under attacker control before it is HMAC-signed, an entity holding org A's `webhook_secret` can freely set `repository.owner.login = "orgA"` (to pass signature verification against org A's secret) while setting `repository.full_name = "orgB/some-target-repo"` (to redirect the handler's side effects onto a stack that actually belongs to org B, a completely different tenant/organization configured in the same Shipit instance).

This breaks the binding: *the organization whose credential authenticated the request* ≠ *the repository/stack the request is allowed to mutate*.

The most severe reachable handler is `StatusHandler`, which creates a `CommitStatus` directly from unauthenticated-content payload fields with no re-fetch/validation against GitHub's actual API state: [6](#0-5) 

Commit statuses gate CI requirements (`ci.require`) and the merge queue (`merge` behavior described in `README.md`), meaning forged statuses for a commit belonging to a stack in a different, unrelated GitHub organization can flip CI-required checks to `success`, enabling that other organization's protected stack to merge or deploy despite failing/absent real CI. `PushHandler` similarly triggers `stack.sync_github` for any stack matching the forged `full_name`, regardless of which org's secret validated the request: [7](#0-6) 

### Impact Explanation
This qualifies as an unauthorized deploy/merge under the accepted High-impact category: an entity with legitimate authority over one configured GitHub organization's webhook (a boundary explicitly established by Shipit's own multi-org configuration model) can forge commit-status/push events that are accepted as authentic for a *different* organization's stacks, allowing CI-required merge/deploy gates to be bypassed for repositories it has no legitimate authority over. It does not require a Shipit session, `ApiClient` token, or the target org's own `webhook_secret` - only possession of any *one* configured organization's webhook secret in a multi-tenant install, which the engine documents as a supported, common configuration.

### Likelihood Explanation
This requires a multi-organization Shipit configuration (documented as a first-class supported setup) and possession of one organization's `webhook_secret` - which is a materially lower privilege bar than compromising the target organization's own secret, GitHub App private key, or a Shipit user session/API token. Any GitHub org owner who can view their own app's webhook secret (a routine administrative action within their own org, not the target org) can mount this without any interaction from the target organization or its Shipit maintainers.

### Recommendation
After signature verification, re-derive the expected owning organization strictly from the *verified* secret's associated organization (not from a payload field), and reject or ignore the event if `repository.full_name`'s owner does not match the organization whose `webhook_secret` was used to verify the signature. Concretely, `WebhooksController` should pass the authenticated organization identity down to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization:) }`, and `Handler#stacks`/`#repository_name` should assert that the resolved `Repository`'s owner equals `verified_organization` before acting.

### Proof of Concept
1. Configure Shipit for two organizations, `orgA` and `orgB`, each with distinct `webhook_secret`s (per `docs/setup.md`).
2. As an attacker with legitimate access to `orgA`'s GitHub App settings (its own webhook secret - not orgB's), craft a `status` webhook payload:
```json
{
  "sha": "<sha-of-commit-in-orgB-stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "full_name": "orgB/target-repo",
    "owner": { "login": "orgA" }
  }
}
```
3. Sign the raw body with `orgA`'s `webhook_secret` and send it as `X-Hub-Signature` to `POST /github/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and the HMAC validates successfully.
5. `StatusHandler#process` executes, and via `Handler#repository_name`/`#stacks` resolves `orgB/target-repo`'s commit and creates a `Status`/`CommitStatus` marking the required CI context as `success`, even though the attacker has no relationship with `orgB` and did not know or use `orgB`'s `webhook_secret`.
6. If `orgB`'s stack has continuous delivery/merge-queue enabled gated on that CI context, this forged status can unblock an otherwise CI-failing commit for deploy or merge.
