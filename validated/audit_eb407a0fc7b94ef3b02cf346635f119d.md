### Title
Cross-organization webhook forgery lets an attacker with only their own org's webhook secret create GitHub commit statuses (and check-suite refreshes) on stacks belonging to an unrelated GitHub organization, enabling an unauthorized deploy - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects **which** GitHub App/webhook secret to validate a webhook against based on an attacker-controlled field of the very payload it is about to trust (`repository.owner.login`), while several webhook handlers — most notably `StatusHandler` — act on data (`sha`) that is **not scoped to that organization or repository at all**. This breaks the binding "organization that authenticated == repository/stack that is written", which is exactly the class of bug flagged in the referenced report (a value used to authorize an action diverges from the value the action actually operates on).

### Finding Description
In a multi-tenant Shipit deployment, `secrets.github` can hold one config (including its own `webhook_secret`) per GitHub organization [1](#0-0) . Each organization's admin picks/knows their own `webhook_secret` when installing their GitHub App [2](#0-1) .

`WebhooksController#verify_signature` picks the secret to validate against solely from `repository_owner`, itself taken directly from the untrusted request body: [3](#0-2) [4](#0-3) 

Because the whole endpoint is shared across all configured organizations, an attacker who legitimately administers **their own** org's GitHub App (and therefore knows that org's `webhook_secret`, per the setup docs) can craft an arbitrary JSON body, set `repository.owner.login` to their own org so the HMAC check passes with a secret they know, and set every other field to target a **different** organization's data.

`StatusHandler#process` demonstrates the impact: it does not scope by repository/organization at all — it looks up commits by `sha` across the **entire database**: [5](#0-4) 

`Status#after_create` (`enable_ci_on_stack`) and `after_commit` (`schedule_continuous_delivery`) then run against whatever stack owns that commit — a stack that can belong to a completely different, unrelated organization than the one whose secret authenticated the request: [6](#0-5) [7](#0-6) 

Other handlers reduce, but do not eliminate, the same class of gap: `CheckSuiteHandler`, `PushHandler`, etc. use `Handler#stacks`, which resolves the target repository from `repository.full_name` — a different payload field than the `repository.owner.login` used for signature selection, so these two fields can likewise be set inconsistently within the same attacker-crafted, but validly-signed (with the attacker's own org secret), body: [8](#0-7) 

### Impact Explanation
An attacker who controls a GitHub App/webhook secret for *any one* organization configured on a shared Shipit instance can forge a `status` webhook that is authenticated with their own org's secret but whose `sha` matches a commit belonging to a victim organization's stack. Because `Commit.where(sha: params.sha)` is unscoped, a forged `success` status matching a stack's required CI context (`ci.require`) can satisfy CI gating and trigger `schedule_continuous_delivery`, resulting in an **unauthorized deploy** on the victim organization's stack — meeting the Critical-tier impact defined for this analysis ("an unauthorized deploy, rollback or merge"). This requires no privileged Shipit credentials (no `ApiClient` token, no `webhook_secret` of the victim org, no GitHub App private key of the victim org) — only knowledge of a webhook secret for any one org hosted on the same multi-tenant instance.

### Likelihood Explanation
Exploitability depends on the deployment running Shipit in the documented multi-organization mode with more than one GitHub org sharing the same `/webhooks` endpoint (a supported, documented configuration) [1](#0-0) . Any legitimate customer/organization admin on such a shared instance — who is fully "unprivileged" with respect to any other tenant's stacks — already possesses everything needed (their own org's webhook secret) to carry out the attack; no social engineering, secret theft, or additional access is required beyond what such an admin is issued as part of normal onboarding.

### Recommendation
Bind webhook signature verification to the same field(s) the handlers subsequently trust to select the target repository/stack, and reject the request if they diverge. Concretely:
- Have `verify_signature` derive the organization strictly from `repository.full_name`'s owner segment (the same field `Handler#repository_name`/`stacks` use), not from a separately-trusted `repository.owner.login`/`organization.login` field.
- Additionally, scope `StatusHandler#process` (and any other handler that queries globally) by the resolved `Repository`/`Stack` derived from the payload's `repository.full_name`, instead of querying `Commit.where(sha: ...)` across all stacks.
- Consider validating that `repository.owner.login` (or `organization.login`) is consistent with `repository.full_name`'s owner before processing, rejecting the webhook otherwise.

### Proof of Concept
1. Configure (or be an existing legitimate admin of) `OrgA`'s GitHub App on a shared Shipit instance, with a known `webhook_secret_A`.
2. Identify a commit `sha` belonging to a stack in `OrgB` (also hosted on the same instance) that is pending a CI-required context, e.g. `ci/travis`.
3. Craft a JSON body:
```json
{
  "repository": { "owner": { "login": "OrgA" } },
  "sha": "<OrgB commit sha>",
  "state": "success",
  "context": "ci/travis"
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, body)>` and POST to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'OrgA')` and the signature validates successfully against `webhook_secret_A` [3](#0-2) .
6. `StatusHandler#process` finds `OrgB`'s commit by `sha` (no org/repo scoping) and creates a `success` `Status` for it [5](#0-4) , which can satisfy CI gating and trigger continuous delivery on `OrgB`'s stack.
