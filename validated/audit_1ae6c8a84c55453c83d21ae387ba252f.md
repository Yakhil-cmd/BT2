### Title
Uncaught `throw` on missing/ambiguous `definition template` reference crashes node during authentifier validation - ([File: definition.js])

### Summary
`FRRouting`'s CVE-2024-34088 is a classic "lookup can return nothing, caller doesn't handle it" DoS: `get_edge()` can return NULL and the caller dereferences it, crashing the daemon. `ocore` has an analogous pattern in `definition.js`'s `validateAuthentifiers`, where the `'definition template'` opcode handler queries the DB for a referenced `definition_template` message and, unlike the sibling function `validateDefinition`, throws an uncaught `Error` instead of returning a graceful validation error when the row count is not exactly 1.

### Finding Description
When validating the spending condition (authentifiers) of an address that uses a `['definition template', [unit, params]]` node, `validateAuthentifiers`'s inner `evaluate()` runs: [1](#0-0) 
This queries `messages`/`units` for `app='definition_template'` at the given `unit`, and if `rows.length !== 1` it executes `throw Error("not 1 template")` inside an asynchronous DB callback — there is no `try/catch` around this call path, so the exception is unhandled and terminates the Node.js process, exactly analogous to a NULL-deref crash from an unchecked lookup.

Contrast this with the structural definition validator `validateDefinition`, which performs the same lookup but handles the "not found or too many" case safely via a callback: [2](#0-1) 
Here, `if (rows.length !== 1) return cb("template not found or too many");` gracefully rejects the unit instead of crashing.

Because an address's `definition_chash` is simply `chash160(arrDefinition)` and is never checked against the DB at "address creation" time, any unprivileged user can construct an address whose definition is (or contains) a `'definition template'` node pointing at:
- a unit that has never been posted (garbage/attacker-chosen base64 string), or
- a unit whose `definition_template` message later becomes non-serial/voided (sequence changes from `'good'`), or
- a unit that (in edge/reorg scenarios) yields zero or more-than-one matching rows.

The attacker funds this address with a trivial payment to themselves, then posts a spending unit authored by this address with `author.definition` set to the `'definition template'` node. Every full node that validates this unit's authentifiers reaches the vulnerable code path and crashes.

### Impact Explanation
An uncaught exception thrown from inside a DB query callback during unit validation is not caught by the surrounding validation logic and will terminate the Node.js process for any full/hub node that attempts to validate the malicious unit. Since unit validation is mandatory before a unit can be added to the DAG, this can be weaponized to repeatedly crash nodes that receive/relay the unit, preventing the network from confirming new units from the affected nodes — a network availability/DoS impact analogous to the FRR OSPF daemon crash in the CVE.

### Likelihood Explanation
Likelihood is high for any node that validates the crafted unit: the attacker only needs the ability to post a single ordinary unit (self-funded address, standard `definition template` conditional address definition) — no special privileges, hub/witness role, or victim cooperation are required. The condition is fully attacker-controlled (choice of `unit` reference in the template node), so a `rows.length !== 1` result can be reliably engineered (e.g., by referencing a unit that was never posted, or one whose `definition_template` message is later voided/non-serial due to a conflicting double-spend of the templating unit).

### Recommendation
In `definition.js`'s `validateAuthentifiers`, change the `'definition template'` case to mirror `validateDefinition`'s safe handling: instead of `throw Error("not 1 template")` when `rows.length !== 1`, invoke `cb2(false)` (or an equivalent graceful failure signal consistent with `validateAuthentifiers`'s callback contract) so that the unit is rejected as invalid rather than crashing the process. Audit other `throw Error(...)` calls inside async DB callbacks reachable from unit/AA/authentifier validation for the same unchecked-lookup pattern.

### Proof of Concept
1. Craft `arrDefinition = ['definition template', ['<44-byte base64 string that is not a real unit, or a unit id that will never carry a definition_template message>', { key: 'value' }]]`.
2. Compute `address = chash160(arrDefinition)`.
3. Send a small payment from an attacker-controlled address to `address` (self-funding, no special privilege needed).
4. Compose and broadcast a unit spending that output, with `authors: [{ address, definition: arrDefinition, authentifiers: {...} }]`.
5. Any node validating this unit executes `validateAuthentifiers` → hits the `'definition template'` case in [1](#0-0)  → the query returns 0 rows → `throw Error("not 1 template")` is raised uncaught inside the async callback → the node process crashes.
