### Title
Webhook signature verification is keyed to attacker-controlled `repository.owner.login`/`organization.login`, decoupled from the `repository.full_name` used to dispatch events - allowing cross-organization webhook forgery in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which HMAC secret) to verify a webhook against based on a field taken directly from the unverified JSON body, while the actual event-processing code (`Handler#repository_name`) selects which `Repository`/`Stack` to act on using a *different* field from that same unverified body. In a multi-organization Shipit installation these two fields are never cross-checked, so a valid signature for one configured organization can be used to authorize actions against a completely different organization's repositories.

### Finding Description
`WebhooksController` runs `verify_signature` as a `before_action`, before any part of the payload has been authenticated: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`repository_owner` is read straight from the request body (`params` is populated from the raw JSON payload before any signature check occurs). This value picks *which* `GitHubApp` (and thus which `webhook_secret`) is used to validate the HMAC, via `Shipit.github(organization:)`: [3](#0-2) 

Meanwhile, once the request passes that check, `create` dispatches the *same untouched payload* to handlers: [4](#0-3) 

Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the target `Stack`/`Repository` using a *different* payload field, `repository.full_name`: [5](#0-4) 

Nothing enforces that `repository.owner.login` (used to pick the verifying secret) and `repository.full_name`'s owner (used to pick the acted-upon repository) refer to the same organization. Shipit explicitly supports configuring several independent GitHub Apps/organizations, each with its own `webhook_secret`, in `secrets.yml`: [6](#0-5) 

This breaks the binding "organization that authenticated == organization whose repository is written." An attacker who can produce a valid signature for *any one* configured organization (e.g. because that organization's `webhook_secret` is blank/unset - explicitly a supported, documented "nil" default in `config/secrets.development.example.yml`/`config/secrets.development.shopify.yml` - or because the attacker legitimately controls that low-trust org and can trigger real deliveries there) can set `repository.owner.login`/`organization.login` to that org while setting `repository.full_name` to `HighTrustOrg/victim-repo`. `verify_signature` will validate successfully against the low-trust org's secret (or trivially pass if that secret is blank, per `verify_webhook_signature`'s `return true unless webhook_secret`), yet the handler will act on the high-trust org's `Repository`/`Stack`. [7](#0-6) 

### Impact Explanation
This allows an unauthenticated-for-the-target-org attacker to inject forged GitHub events for repositories they do not own, as long as they can produce (or trivially satisfy, via a blank secret) a valid signature for *some* other organization configured on the same Shipit instance. Concretely:
- `status` events let the attacker fabricate arbitrary `CommitStatus` records (state, description, target_url) for any commit SHA on the victim stack, as shown by the existing test asserting these fields are taken verbatim from the payload. [8](#0-7) 
- `push`/`check_suite` events enqueue `GithubSyncJob`/`RefreshCheckRunsJob` for the victim stack based on attacker-supplied `after`/branch data. [9](#0-8) 

Forged commit statuses and check-suite refreshes feed directly into Shipit's deploy-gating logic (release status / merge status), so this can be used to spoof green CI status and influence which commits are considered deployable/mergeable - an authorization-boundary violation between organizations hosted on the same instance. This matches the High-impact category "escalation into authorization boundary" / unauthenticated manipulation of stack/task state across a trust boundary that the app is supposed to enforce per-organization.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (explicitly documented and supported) where at least one configured organization either has no `webhook_secret` set (a documented default state, `# nil`, in the example secrets files) or where the attacker is able to obtain a valid signature for any one configured org (e.g., by being a legitimate low-privilege GitHub App/webhook owner for that org). No `Shipit` session, `ApiClient` token, or repository write access on the *victim* org is needed — only the ability to send an HTTP POST to the public `/webhooks` endpoint with a crafted body and a signature valid for a different, weaker-trust org on the same instance.

### Recommendation
Verify the webhook signature using the organization actually derived from `repository.full_name` (the same value used for dispatch), not a separately-extracted `repository.owner.login`/`organization.login`. Alternatively, after selecting the signing organization, cross-check that its name matches the owner segment of `repository.full_name` before processing, and reject the request if they differ. Additionally, do not treat a blank/missing `webhook_secret` as an implicit “always verified” pass in `GitHubApp#verify_webhook_signature` for organizations that host trusted stacks.

### Proof of Concept
Assume a Shipit instance configured with two orgs in `secrets.yml`: `trusted-org` (real `webhook_secret`) and `low-trust-org` (no `webhook_secret` configured, or one known to the attacker).

1. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "organization": { "login": "low-trust-org" },
  "repository": { "full_name": "trusted-org/victim-repo", "owner": { "login": "low-trust-org" } },
  "sha": "<any commit sha on trusted-org/victim-repo>",
  "state": "success",
  "description": "forged",
  "target_url": "https://evil.example.com"
}
```
2. `verify_signature` calls `Shipit.github(organization: "low-trust-org")` and `verify_webhook_signature` returns `true` (blank secret, or attacker-known secret for `low-trust-org`).
3. `create` dispatches the raw payload to `Handlers::StatusHandler`, which resolves the target via `payload.dig('repository','full_name')` = `"trusted-org/victim-repo"` and creates a forged `CommitStatus` on that repository's stack — with no valid signature ever having been checked against `trusted-org`'s actual `webhook_secret`.

# frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
