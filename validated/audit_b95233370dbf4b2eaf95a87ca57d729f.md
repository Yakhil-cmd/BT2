### Title
Webhook signature verification is scoped to the wrong organization, letting an attacker impersonate any tracked repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate an inbound webhook against using `repository_owner`, a value taken straight from the unauthenticated request body (`params.dig('repository','owner','login')` / `params.dig('organization','login')`). Once the signature check passes, every event `Handler` (e.g. `PushHandler`) looks up the target `Stack`/`Repository` using a *different* field from the same untrusted payload: `payload.dig('repository', 'full_name')`. The engine never re-checks that the organization whose secret validated the request actually owns the repository that is subsequently acted upon. This is the same class of bug as the BendDAO report: a field used for the authorization/verification decision (`repository.owner.login` → org secret) is disjoint from the field the business logic actually consumes and trusts (`repository.full_name` → stack/repo lookup).

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes `repository_owner` from the JSON body and fetches `Shipit.github(organization: repository_owner)`, then calls `github_app.verify_webhook_signature(header_signature, raw_post)`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` in `lib/shipit/github_app.rb:76-83` short-circuits with `return true unless webhook_secret`, i.e. if the organization selected via the attacker-controlled `repository_owner` field has no `webhook_secret` configured, **any** payload (even unsigned) passes verification. [3](#0-2) 
- Leaving `webhook_secret` unset is explicitly presented as a valid, documented configuration in `docs/setup.md` (`**github.webhook_secret** If you've set a webhook secret during the App creating, you should copy it here.`) and in the shipped example secrets files (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), both of which ship with `webhook_secret: # nil`. [4](#0-3) [5](#0-4) 
- After verification, `Handler#stacks` (used by every handler, e.g. `PushHandler`) resolves the target repository from a completely different field, `payload.dig('repository', 'full_name')`, with no re-validation that this repository belongs to the organization that satisfied `verify_signature`. [6](#0-5) [7](#0-6) 
- `Shipit.github` resolves the org config purely by dictionary lookup on the name supplied at call time (`github_app_config`), with no cross-check against the repository being targeted. [8](#0-7) 

**Equality that should hold, but doesn't:** `organization-that-authenticated(repository.owner.login)` == `organization-that-owns(repository.full_name)`. The controller enforces neither this equality nor a hard-fail when a configured organization has no `webhook_secret`.

### Impact Explanation
An unauthenticated network attacker who knows (or guesses) that any *one* configured GitHub organization in a Shipit deployment has an unset `webhook_secret` — a state the project's own docs and shipped example configs treat as normal — can send a forged `X-Github-Event: push` POST to the public `/github/webhooks` endpoint with:
- `repository.owner.login` = the organization with no `webhook_secret` (verification trivially returns `true`), and
- `repository.full_name` = any other tracked stack's repository (owned by a different, properly-secured organization).

`PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) will then locate the victim stack via `Repository.from_github_repo_name` and enqueue `GithubSyncJob`, which calls `Stack#sync_github`/`trigger_continuous_delivery`. For stacks with `continuous_deployment: true`, this can force premature/unauthorized deploy scheduling of a stack the attacker has no legitimate relationship with, without ever presenting an `ApiClient` token, session, or GitHub credential — crossing the "unauthorized deploy" and "unauthenticated write to another repository's stack state" boundaries called out in scope.

### Likelihood Explanation
Likelihood is moderate-to-high in any multi-organization Shipit deployment where at least one configured org omits `webhook_secret` — a configuration explicitly modeled as acceptable in the shipped docs/examples. No credentials, session, or prior access are required; the attacker only needs the public webhook endpoint URL and knowledge of one org name lacking a secret, both discoverable via error responses (`GithubOrganizationUnknown` logging includes `repository_owner`) or simple guessing of common org slugs.

### Recommendation
1. In `WebhooksController#verify_signature`, fail closed (`head(422)`/reject) when the resolved organization has no `webhook_secret` configured, rather than treating a blank secret as "always verified."
2. Bind webhook processing to the same organization used for verification: after determining `repository_owner`, require that every handler's `repository_name`/`full_name` resolves to a repository whose owner matches `repository_owner`, rejecting mismatches.
3. Update `docs/setup.md` and example secret files to make clear that an unset `webhook_secret` disables authenticity checks entirely, and stop shipping example configs that leave it blank by default.

### Proof of Concept
Given a Shipit instance configured with two GitHub App orgs, `orgNoSecret` (no `webhook_secret`) and `victimOrg` (properly configured, `webhook_secret` set), with a stack tracking `victimOrg/app` and `continuous_deployment: true`:

```
POST /github/webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json
(no X-Hub-Signature header, or any arbitrary value)

{
  "ref": "refs/heads/main",
  "after": "<any sha>",
  "repository": {
    "owner": { "login": "orgNoSecret" },
    "full_name": "victimOrg/app"
  }
}
```

`verify_signature` calls `Shipit.github(organization: "orgNoSecret")` → `webhook_secret` blank → `verify_webhook_signature` returns `true` unconditionally. `PushHandler` then resolves `repository_name` from `full_name` = `"victimOrg/app"`, finds the real `victimOrg/app` stack, and enqueues `GithubSyncJob`, triggering sync/continuous-delivery logic for a stack completely unrelated to `orgNoSecret`, despite no valid signature having ever been presented for `victimOrg`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
