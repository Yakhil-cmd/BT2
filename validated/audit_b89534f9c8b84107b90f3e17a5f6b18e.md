### Title
`inherit_from` path-traversal in `DeploySpec::FileSystem#build_config` lets an attacker-controlled `shipit.yml` pull arbitrary host files into the deploy config - ([File: app/models/shipit/deploy_spec/file_system.rb])

### Summary
`build_config` resolves `inherit_from` with `path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))` and passes the result straight to `read_config`/`SafeYAML.load` with no check that the resolved path stays inside `@app_dir`. A `shipit.yml` on any branch/PR whose content an attacker controls (they own the branch that gets checked out into the stack's working directory) can set `inherit_from: '../../../../etc/passwd'`-style values to make Shipit read and YAML-parse files outside the checkout root.

### Finding Description
Binding that should hold: `inherits_from_path == path within @app_dir` (i.e. `inherits_from_path.to_s.start_with?(@app_dir.to_s)`), evaluated at `app/models/shipit/deploy_spec/file_system.rb#L152`. In the actual code: [1](#0-0) 
`inherits_from_path` is built by simply joining the dirname of the current config file with the attacker-supplied `inherit_from` string, with no `Pathname#expand_path` + prefix check, no `File.realpath` containment test, and no rejection of `..` segments. If `inherits_from_path.exist?`, its contents are read via `read_config`, which calls `SafeYAML.load(path.read)` (`file_system.rb#L162-164`), and the result is `deep_merge`d into the stack's effective deploy spec, and `build_config` recurses so an attacker can chain multiple `inherit_from` hops.

`config_file_path` itself is safely constrained to a fixed filename list under `@app_dir` (`file_system.rb#L135-142`), but that constraint is not carried through to the `inherit_from` resolution.

Attack path: `@app_dir`/checkout root is `Task#working_directory` — a real git checkout of the branch/commit being deployed (`lib/shipit/task_commands.rb#L14, #L61-74`), which for a stack/review-stack is populated by cloning `@stack.git_path`/checking out the attacker's commit (`lib/shipit/stack_commands.rb`, `lib/shipit/task_commands.rb#L50-74`). Any GitHub user who can push a branch/PR that Shipit will build/deploy (e.g. a review-stack owner, or someone who can get a `shipit.yml` merged into an evaluated ref) fully controls the content of `shipit.yml`, including `inherit_from`. Because `@app_dir` sits many directories under `Rails.root` (`Rails.root/data/stacks/<owner>/<repo>/<environment>/deploys/<id>`, see `Stack#base_path`/`#deploys_path`), a sufficiently long `../` chain in `inherit_from` can reach arbitrary files readable by the Shipit process — including files elsewhere in the Shipit application tree or on the host filesystem.

None of the existing guards (`verify_signature`, `ExplicitParameters`, `Repository`/`Stack` validators, `EnvironmentVariables#permit`) apply here because this is a pure filesystem read inside `DeploySpec::FileSystem`, entirely downstream of webhook/auth checks — it operates on already-checked-out repository content.

### Impact Explanation
The primary confirmed impact is **arbitrary file read on the deploy host, gated by YAML parseability**: any file the Shipit process user can read and that reaches inherits `.exist?` gets `SafeYAML.load`'d and `deep_merge`'d into the deploy spec. Whether this rises to secret exfiltration depends on the target file happening to parse as YAML with keys `DeploySpec` recognizes (e.g. `deploy.override`, `machine.environment`) so its values are echoed into task command lines/output that the attacker (who owns the stack/review-stack and can view its task logs) can see. Arbitrary unstructured files (e.g. `/etc/passwd`) will typically not surface useful data through this path even though the read itself occurs, and files with attacker-unknown structure are unlikely to line up with recognized keys. This still constitutes uncontrolled path traversal / information-disclosure primitive scoped to the `inherit_from` resolution and is a real defect, but end-to-end demonstrated exfiltration of a specific named secret (`GITHUB_TOKEN`, `secret_key_base`, etc.) was not confirmed given available context — the questioned code path lacks any containment check, which is the core bug regardless of the strength of the downstream data-exposure chain.

### Likelihood Explanation
Preconditions: the attacker needs their own commit content (a `shipit.yml` with `inherit_from`) checked out into a stack's/review-stack's working directory — achievable by anyone who can push a branch that Shipit provisions/builds/deploys as their own review stack, with no privileged Shipit role required. Cost is a single crafted `shipit.yml` per attempt, fully repeatable, and does not require any secret or session. The main uncertainty is which specific host files are both reachable via relative traversal and coincidentally structured as usable YAML with recognized config keys, which affects how damaging a given traversal is but not whether the missing containment check exists.

### Recommendation
In `build_config`, resolve `inherits_from_path` with `File.expand_path` (or `Pathname#realpath` on an existing file) and assert the result is still a descendant of `@app_dir` (e.g. `inherits_from_path.to_s.start_with?("#{@app_dir.realpath}/")`) before calling `read_config`; reject/ignore the `inherit_from` value otherwise instead of silently walking outside the checkout.

### Proof of Concept
```ruby
test '#build_config refuses to read outside @app_dir via inherit_from traversal' do
  Dir.mktmpdir do |app_dir|
    stack = shipit_stacks(:shipit)
    outside_dir = Dir.mktmpdir
    secret_path = File.join(outside_dir, 'secrets.yml')
    File.write(secret_path, "deploy:\n  override:\n    - leaked_secret_command\n")

    shipit_yml = File.join(app_dir, 'shipit.yml')
    File.write(shipit_yml, "inherit_from: '#{Pathname.new(secret_path).relative_path_from(Pathname.new(app_dir))}'\n")

    deploy_spec = Shipit::DeploySpec::FileSystem.new(app_dir, stack)
    config = deploy_spec.send(:load_config)

    # Binding under test: inherits_from_path must stay within app_dir.
    refute config['deploy']['override'].include?('leaked_secret_command'),
      "inherit_from traversal escaped @app_dir (#{app_dir}) and pulled in #{secret_path}"
  end
end
```
This test currently fails against the shown implementation because `build_config` has no containment check, confirming the traversal.

      SHIPIT_CONFIG_INHERIT_FROM_KEY = "inherit_from"
      def build_config(path, config_obj)
        return config_obj if config_obj.blank? || !config_obj.key?(SHIPIT_CONFIG_INHERIT_FROM_KEY)

        inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))
        if inherits_from_path.exist?
          inherits_config_obj = read_config(inherits_from_path)
          config_obj = inherits_config_obj.deep_merge(config_obj)
          path = inherits_from_path
        end

        build_config(path, config_obj)
      end

      def read_config(path)
        SafeYAML.load(path.read) if path.exist?
      end
