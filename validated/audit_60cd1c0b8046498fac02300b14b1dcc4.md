### Title
Sensitive Device-Message Content (Private Payment Chains, Mnemonics, Signing Payloads) Insertion into Log File - (File: device.js)

### Summary
`device.js`'s `decryptPackage()` unconditionally logs the full plaintext of every decrypted device message to the console/log with `console.log("decrypted: "+decrypted_message)`, before the message is even parsed or type-checked. [1](#0-0) . Because any paired correspondent (or the hub relaying `hub/deliver` traffic to the node) can cause an arbitrary encrypted body to be decrypted and logged, this reproduces the CWE-532 pattern from CVE-2021-20191 (ansible): sensitive payloads that should stay protected end up unconditionally written to a log sink that may be read by lower-privileged users, log-shipping agents, or crash-report collectors.

### Finding Description
`decryptPackage()` is the single entry point that decrypts all inbound device messages, whether they arrive directly from a peer or via `hub/deliver`/`hub/message` from the hub. [2](#0-1)  After successful AES-GCM decryption it does:
```
var decrypted_message = decrypted_message_buf.toString("utf8");
console.log("decrypted: "+decrypted_message);
``` [1](#0-0) 
This happens for every message type the wallet handles, including:
- `private_payments` bodies, i.e. full chains of private-asset elements containing `blinding` factors and `address` fields used to spend divisible/indivisible private assets, as forwarded by `sendPrivatePayments`/`forwardPrivateChainsToDevices`. [3](#0-2) 
- `sign` requests, which can carry `assocPrivatePayloads` — the private payment payloads that must otherwise be revealed only to specific counterparties. [4](#0-3) 
- textcoin mnemonics sent as part of private-asset textcoin transfers (`storePrivateAssetPayload`, `assocMnemonics`). [5](#0-4) 
- pairing secrets exchanged in `pairing` messages (`pairing_secret`, `reverse_pairing_secret`). [6](#0-5) 

None of this is gated by a debug flag or `no_log`-style redaction — the full JSON body is dumped as soon as it is decrypted, regardless of message subject. This exactly mirrors the ansible bug class: secrets that are supposed to be protected end up unconditionally written to a log artifact that a broader audience (log aggregators, other local users, crash reporters, cloud logging backends) may read even without access to the process's TLS/DB credentials or private keys.

### Impact Explanation
Anything a paired device (or a malicious/compromised hub relaying `hub/deliver`) sends to the victim node is fully echoed into that node's logs in plaintext:
- Leaked private payment chain elements (`address` + `blinding`) let a log reader reconstruct the private outputs and their spend proofs, enabling them to independently claim/forward the same private funds or double-spend a private output whose secrecy the design otherwise relies on. [7](#0-6) 
- Leaked textcoin mnemonics (which derive the address/private key that can claim the textcoin) grant a log reader direct unauthorized-spending capability over sent textcoin funds. [8](#0-7) 
- Leaked pairing secrets allow an unauthorized third party to pair as a correspondent device with the victim.

This satisfies the required "concrete unauthorized spending" bar, since the leaked material (blinding factors, mnemonics) is directly redeemable/spendable, not merely metadata.

### Likelihood Explanation
Any existing correspondent device can trigger this simply by sending a normal message (a payment notification, a signing request, or forwarded private chain) — this is routine wallet traffic, not an attack requiring special access. Every such message passes through `decryptPackage()` and is unconditionally logged before any validation occurs. [9](#0-8)  The likelihood of exposure depends on operational log handling (whether stdout/logs are shipped elsewhere or readable by other principals), which is common in production deployments (log aggregation, hosting providers, crash reporting).

### Recommendation
Remove or redact the `console.log("decrypted: "+decrypted_message)` statement in `decryptPackage()` (and similar full-payload logs such as `"saving private chain "+JSON.stringify(arrPrivateElements)` in `indivisible_asset.js` and `"forwardPrivateChainsToOtherMembersOfOutputAddresses", arrChains` in `wallet.js`). At minimum, log only message type/subject and length, never the raw decrypted body, private payload fields (`blinding`, `mnemonic`, `pairing_secret`), or full private-element chains.

### Proof of Concept
1. Node B is paired with node A (routine wallet correspondent relationship).
2. B sends A any device message containing sensitive material, e.g. a `private_payments` message with a chain of private elements (blinding factors) via `sendPrivatePayments`, or a textcoin claim/transfer carrying a mnemonic. [3](#0-2) 
3. On A's side, `network.js` `hub/deliver`/`message_from_hub` handling passes the encrypted package to `device.js`'s message handler, which calls `decryptPackage()`. [10](#0-9) 
4. `decryptPackage()` decrypts and immediately logs the full plaintext JSON body, including `blinding`, `mnemonic`, or `pairing_secret` fields, via `console.log("decrypted: "+decrypted_message)`. [1](#0-0) 
5. Any party with read access to A's console output/log files (log aggregation service, shared host, crash reporting tool) can extract the sensitive fields and use them to spend the referenced private funds or claim the textcoin, independent of any access to A's actual private keys or database.
