### Title
Signature check authenticates the reporting GitHub organization while the write target repository is taken from an unbound payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC against using `repository_owner`, a value read directly out of the untrusted JSON body (`params.dig('repository','owner','login')`). Every downstream `Webhooks::Handlers::Handler` subclass, however, decides which `Stack`/`Repository`/`Commit` to write to using a *different* field of the same body: `payload.dig('repository','full_name')`. Because the HMAC only proves "this body was signed with organization X's secret," and X is picked from a field that is never cross-checked against `full_name`, anyone who knows (or is validly issued) one organization's webhook secret can craft a signed payload whose `repository.full_name` points at a completely unrelated repository/stack tracked by the same Shipit instance, and have Shipit act on it.

### Finding Description
The guard binding that should hold is:
`organization whose secret validated the HMAC == organization owning the repository/stack that gets mutated`

`verify_signature` computes this binding only on one side: [1](#0-0) [1](#0-0) [2](#0-1) 

`repository_owner` (`repository.owner.login`, or `organization.login`) is used solely to pick a `Shipit.github(organization: ...)` config and validate `X-Hub-Signature`/`webhook_secret` against it (falling back to `true` if that org has no `webhook_secret` configured).

Every event handler, however, resolves the actual `Stack`/`Repository`/`Commit` to mutate from a separate JSON field, `repository.full_name`, with no re-validation that this repository is owned by the organization that authenticated the request: [3](#0-2) 

Concrete write paths that trust this unguarded field:
- `PushHandler#process` triggers a GitHub sync for any matching stack: [4](#0-3) 
- `StatusHandler#process` writes a CI status onto a commit matched purely by `sha`: [5](#0-4) 

Since `Stack` deployability and continuous-delivery triggering are driven by these stored `Status`/`CheckRun` records (via `Stack#deployable?`/`Commit#deployable?`, seen throughout `app/models/shipit/stack.rb` and `app/models/shipit/commit.rb`), forging a `status` event lets an attacker inject a fabricated "success" status onto an arbitrary commit belonging to a stack/org the attacker does not control, as long as they can produce (or are issued) a validly-signed body under *any* configured organization. Multi-organization deployments are an explicitly supported configuration, each with its own `webhook_secret`: [6](#0-5) 

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding. An attacker who legitimately controls (or is issued app credentials for) organization B's Shipit-registered GitHub App can:
1. Produce a validly HMAC-signed `status` webhook body where `repository.owner.login = "org-b"` (satisfies `verify_signature`) but `repository.full_name = "org-a/protected-repo"`.
2. Have `StatusHandler` write a forged `success` status onto any existing commit SHA of `org-a/protected-repo` that Shipit already knows about.
3. If that stack has `continuous_deployment` enabled or CI-gated deploy checks (`ci.require`), the forged status can satisfy `deployable?`/`Stack#next_commit_to_deploy` and cause Shipit to automatically execute an unauthorized deploy of `org-a`'s repository, or make a human operator manually deploy code they believe passed CI.

This crosses into the Critical category of "unauthorized deploy" without ever needing organization A's own webhook secret, GitHub App credentials, or repository write access on GitHub itself — purely a Shipit-engine-side confusion between the field used for authentication and the field used to select the write target.

### Likelihood Explanation
Medium-to-High: the webhooks endpoint is intentionally public/unauthenticated aside from the HMAC check (`skip_before_action :verify_authenticity_token`), so no session or GitHub write access is required. The only prerequisite is possession of one valid organization's webhook secret (or use of an org configured with `webhook_secret: nil`, which is explicitly allowed by `verify_webhook_signature` returning `true` when blank, per the template/example configs). Cross-repo targeting requires only knowledge of an existing commit SHA in the victim stack, which is often publicly visible on GitHub.

### Recommendation
Bind the two fields together instead of trusting them independently: after computing `repository_owner` and validating the signature, re-derive the acted-upon repository's owner from `repository.full_name` (or `organization.login`) and reject the event (422) unless it matches `repository_owner`. Alternatively, resolve the GitHub App/secret to use for verification from the same field (`full_name`'s owner segment) that handlers use to select the target repository, so a single authenticated identity governs both signature verification and the write target.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `org-a` (protected, real secret) and `org-b` (attacker-controlled/known secret, or blank `webhook_secret`), per `config/secrets.development.shopify.yml`.
2. Locate an existing commit SHA already tracked in a stack belonging to `org-a/protected-repo` (e.g., visible via public GitHub commit history).
3. Craft a `status` event JSON body:
```json
{
  "sha": "<org-a commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-b" }, "full_name": "org-a/protected-repo" }
}
```
4. Sign the raw body with `org-b`'s known/blank webhook secret and POST to `/webhooks` with header `X-Github-Event: status` and the resulting `X-Hub-Signature`.
5. `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) resolves `Shipit.github(organization: "org-b")` and validates successfully.
6. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) finds the commit by `sha` alone (no owner check) and creates a forged `success` status for `org-a`'s commit, potentially triggering an unauthorized continuous deployment.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      )
