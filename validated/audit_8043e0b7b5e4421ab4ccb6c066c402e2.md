### Title
CCMenu `show` bypasses `stack_id`-scoped ApiClient authorization, allowing cross-stack deploy-status disclosure - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#show` renders deploy/rollback status for any stack that `Stack.from_param!(params[:stack_id])` resolves to, because the controller overrides the base `stack` helper with an unscoped lookup instead of the base controller's `stacks.from_param!` which filters by `current_api_client.stack_id`. The permission check `require_permission!(:read, :stack)` only verifies the client has the `read:stack` permission string; it never verifies the target stack matches the client's assigned `stack_id`. As a result, a token created and scoped to one stack can read deploy status for every other stack in the installation.

### Finding Description
The intended binding is: information returned by `show` about a stack ∈ information the presenting token's `stack_id` authorizes, i.e. `stack.id == current_api_client.stack_id` (when `current_api_client.stack_id?` is true).

In the base controller, this binding is enforced by the `stacks` helper: [1](#0-0) 
`stacks` restricts the query to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `stack` resolves `params[:stack_id]` only within that scoped relation.

`CCMenuController` overrides `stack` and drops this scoping entirely: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, so any syntactically valid stack id/slug resolves regardless of the authenticated client's `stack_id`.

The only authorization gate before `show` runs is: [3](#0-2) 
which triggers `require_permission!`: [4](#0-3) 
and `ApiClient#check_permissions!`: [5](#0-4) 
This only checks whether `"read:stack"` is present in the client's `permissions` array — it never compares `operation`/`scope` against `stack_id`. So a client scoped to stack A with `read:stack` permission passes this check for *any* requested `stack_id`.

`show` then renders the resolved stack's latest deploy/rollback: [6](#0-5) 
exposing stack name, `lastBuildStatus`, `lastBuildLabel` (deploy label/commit-derived identifier), `lastBuildTime`, and `webUrl` for arbitrary stacks, per the CCMenu XML view fields exercised in the existing test suite: [7](#0-6) 

Attacker flow: obtain (or hold) a legitimate CCMenu/API token for stack A (`ApiClient#authentication_token`, passed via `params[:token]` or Basic Auth per `authenticate_api_client` override at ccmenu_controller.rb:33-36), then issue `GET /stacks/:owner/:repo/:env/ccmenu.xml?token=<A's token>` (or the API-namespaced route) with `stack_id` parameters pointing at other repositories/environments. Since the id/slug space is small and sequential/predictable, the attacker can enumerate stacks and receive 200 XML for every stack that exists (vs. a `ActiveRecord::RecordNotFound`/404 for stacks that don't), confirming existence and leaking latest build status/label for stacks they were never granted access to.

Existing guards do not stop this: `verify_signature`/webhook guards are irrelevant (this is a token-authenticated read endpoint, not a webhook); `ExplicitParameters` is not used here; `require_permission!` checks only the permission string, not stack identity; and the base controller's `stacks` scoping — the one mechanism that would enforce the binding — is explicitly bypassed by the local `stack` override.

### Impact Explanation
Any holder of a stack-scoped ApiClient token with `read:stack` permission can read deploy/build status, last build label, and web URL for every other stack in the Shipit instance, including stacks belonging to other teams/repositories that they have no authorization for. This is a cross-tenant, unauthenticated (relative to the target stack) read of stack state, matching the "High - unauthenticated read of stack state ... or deploy output" impact category. It is fully repeatable: each request is independent and stateless, and the attacker can iterate over arbitrary `stack_id` values to build a full inventory of stacks and their current deploy status across the installation.

### Likelihood Explanation
Preconditions: attacker must possess at least one valid ApiClient token scoped to any stack with `read:stack` permission (a normal, low-privilege token that any team using CCMenu integration would be issued, e.g. embedded in a CI dashboard URL as `params[:token]`). No GitHub secrets, webhook secrets, or Shipit session are required — only an existing legitimate token for stack A, which per the threat model can be assumed available to "an attacker holding a token for stack A's CCMenu client." Given that, the attack cost is a single HTTP GET per candidate `stack_id`, trivially scriptable, with no rate limiting mentioned in the code.

### Recommendation
In `Api::CCMenuController`, remove the local `stack` override (or reimplement it using the scoped `stacks` relation from the base controller, i.e. `stacks.from_param!(params[:stack_id])`) so that `current_api_client.stack_id` scoping is enforced identically to the rest of the API controllers.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token scoped to stack A cannot read stack B's status via #show" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "other", name: "repo"), branch: 'main', environment: 'production')

  client_scoped_to_a = ApiClient.create!(
    creator: @user, name: 'ccmenu-a', stack: stack_a, permissions: ['read:stack']
  )

  get :show, params: { stack_id: stack_b.to_param, token: client_scoped_to_a.authentication_token }

  # Binding under test: stack.id == current_api_client.stack_id
  assert_not_equal stack_b.id, client_scoped_to_a.stack_id
  assert_response :forbidden # or :not_found — currently fails, actual response is :ok with stack_b's data
end
```
Currently this request returns `200 OK` with `stack_b`'s XML (name/lastBuildStatus/lastBuildLabel), demonstrating the broken binding; after applying the recommended fix (`stacks.from_param!`), it returns a 403/404 as expected.
