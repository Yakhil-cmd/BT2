### Title
Cross-organization team membership forgery via unscoped `Team.find_or_create_by!(github_id:)` in `MembershipHandler` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the organization named in the payload itself (`repository_owner`, which falls back to `params.organization.login` for `membership` events since these events carry no `repository` key). `MembershipHandler#find_or_create_team!` then looks up the target `Team` solely by `github_id`, with no organization filter, so an attacker who controls a legitimately-configured GitHub App/webhook for one organization (org A) can forge a `membership` payload naming org A (to pass signature verification) but pointing `team.id` at a `Team` row that already belongs to a different organization (org B), causing `team.add_member(member)` to write a `Membership` for org B using only org A's secret.

### Finding Description
The binding that must hold is: **the organization whose `webhook_secret` authenticated the request (`repository_owner` in `WebhooksController#verify_signature`, `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`) must equal `team.organization` for every `Membership` created as a result of processing that request.**

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, using that organization's own `webhook_secret` [2](#0-1) . A `membership` GitHub event has no `repository` key at all, so `repository_owner` is taken entirely from the attacker-supplied `organization.login` field inside the JSON body — a field with no independent authentication.
2. `MembershipHandler#find_or_create_team!` resolves the target team purely by numeric id: `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [3](#0-2) . The `organization=` assignment inside the block only runs when a **new** record is created; if a `Team` row with that `github_id` already exists (e.g., previously created from a legitimate org B membership event), `find_or_create_by!` returns the existing row untouched, and its `organization` column keeps its original value ("orgB").
3. `MembershipHandler#process` then unconditionally calls `team.add_member(User.find_or_create_by_login!(params.member.login))` [4](#0-3) , which appends the membership via `Team#add_member` [5](#0-4) . `Membership` only validates `user_id` uniqueness scoped to `team_id`; it does not re-check that the requesting organization matches `team.organization` [6](#0-5) .

Exploit flow: attacker legitimately controls org A's GitHub App/webhook configuration (this is a normal, unprivileged org-admin capability, not a Shipit secret). Attacker sends a signed `membership` POST where `organization.login = "orgA"` (so `verify_webhook_signature` succeeds using orgA's own secret) but `team.id` is set to the `github_id` of an existing `Team` row belonging to org B (team ids are visible via GitHub's public/authenticated team APIs or simply guessable/enumerable integers). `action: "added"`, `member.login: "attacker"`. The request passes signature verification (org A is legitimately configured), `find_or_create_team!` matches the pre-existing org B `Team`, and `team.add_member` inserts a `Membership` linking the attacker's auto-vivified `User` to org B's team — a `Team` never authenticated by org B's webhook secret for this request.

Existing guards do not prevent this: `verify_signature` only checks that *some* configured org's secret matches the signature, not that the signed org matches the team being mutated; `ExplicitParameters` schema only validates types/presence of `team.id`, `organization.login`, `member.login`, not their mutual consistency; there is no `Shipit.github_teams` restriction limiting which orgs may report membership for a given `github_id` (per the stated precondition, confirmed by `lib/shipit.rb:256-258` where `github_teams` is built independently from `oauth_teams` handles, with no cross-check against inbound membership events).

### Impact Explanation
An attacker who legitimately administers org A's GitHub App/webhook (unprivileged w.r.t. Shipit, no Shipit secrets needed) can append arbitrary attacker-controlled GitHub logins as members of any pre-existing `Team` in Shipit's database belonging to a completely different organization, without org B's webhook ever being invoked. Since `Shipit.github_teams` and team-based authorization (`oauth_teams`) are derived from `Team`/`Membership` records, this is a direct escalation into org B's `Shipit.github_teams` authorization boundary — matching the "High: escalation into `Shipit.github_teams` authorization" impact category. This is repeatable against any `Team` row whose `github_id` the attacker can discover, across arbitrary target organizations, as long as the attacker controls webhook signing for at least one configured org.

### Likelihood Explanation
Preconditions: Shipit must be configured with the multi-org GitHub App secrets schema (`secrets.github` keyed per organization) so `repository_owner`/`Shipit.github(organization:)` resolves per-org; the attacker must legitimately administer at least one such configured organization's webhook (a realistic scenario for any multi-tenant Shipit deployment onboarding customer orgs); a target `Team` row for org B must already exist in Shipit (created by any prior legitimate membership event) and its `github_id` must be known/guessable (GitHub team IDs are sequential integers, often discoverable via GitHub's team API). Given these are not exotic requirements for a multi-org Shipit install, the attack is straightforward and requires only crafting one HTTP POST with a valid HMAC for the attacker's own org.

### Recommendation
Scope the team lookup by organization, not just `github_id`: e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally verify inside `MembershipHandler#process` that `params.organization.login` (the org used for signature verification) equals the resolved `team.organization` before calling `team.add_member`/`team.members.delete`, raising/dropping the event otherwise. Consider adding a DB-level check/unique index enforcing `(github_id, organization)` consistency for `Team`.

### Proof of Concept
```ruby
test ":membership cannot append a member to a team belonging to another organization" do
  team_b = shipit_teams(:shopify_developers) # existing team, organization: "shopify"
  team_b.update!(organization: 'org-b')

  @request.headers['X-Github-Event'] = 'membership'
  # Signed/verified as org A ("shopify"), but targets team_b's github_id which belongs to org-b
  payload = {
    action: 'added',
    team: { id: team_b.github_id, name: team_b.name, slug: team_b.slug, url: team_b.api_url },
    organization: { login: 'shopify' }, # signature verified against shopify's secret
    member: { login: 'attacker' }
  }.merge(repository_params) # repository_params sets owner.login to 'shopify' too, matching org A

  assert_no_difference -> { Team.where(organization: 'org-b').count } do
    post :create, body: payload.to_json, as: :json
    assert_response :ok
  end

  attacker = Shipit::User.find_by(login: 'attacker')
  # Binding under test: repository_owner ('shopify') must equal team_b.organization ('org-b') for this write to be legitimate.
  assert_not_equal 'shopify', team_b.organization
  assert Shipit::Membership.exists?(team: team_b, user: attacker), 
    "attacker membership was written to org-b's team using only org A's (shopify) verified signature"
end
```
