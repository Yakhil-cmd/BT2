The reported issue is a **pure front-running/economic attack** on `CREATE2`-based pool deployment (address predictability enabling gas-griefing), which is explicitly out of scope per the analysis rules (front-running/economic attacks are to be rejected, not reported as findings).

Beyond that exclusion, there is no valid analog here even setting policy aside: Polkadot SDK's contract address derivation already binds the deployer to the address, which is precisely the mitigation the Kyber report recommends. In `pallet-revive`, `create2` takes the `deployer: &H160` and folds it into the hash together with salt and init code hash [1](#0-0) , and the `Instantiate` frame arm computes the address from `deployer`, `executable.code()`, `input_data`, and `salt` together [2](#0-1) . Similarly, `pallet-contracts`'s `DefaultAddressGenerator::contract_address` hashes `deploying_address`, `code_hash`, `input_data`, and `salt` together [3](#0-2) . Since the deployer/sender is already an inseparable input to the address formula (unlike the vulnerable `BaseSplitCodeFactory._create` which omitted `msg.sender`), an attacker observing a pending instantiate extrinsic in the mempool cannot cause their own front-run deployment to collide with the victim's target address — a different sender always yields a different address. There is also an explicit guard against re-entrant/duplicate-salt collisions for the same account (`DuplicateContract`), further hardening this path [4](#0-3) .

/// Determine the address of a contract using the CREATE2 semantics.
pub fn create2(deployer: &H160, code: &[u8], input_data: &[u8], salt: &[u8; 32]) -> H160 {
	let init_code_hash = {
		let init_code: Vec<u8> = code.into_iter().chain(input_data).cloned().collect();
		keccak_256(init_code.as_ref())
	};
	let mut bytes = [0; 85];
	bytes[0] = 0xff;
	bytes[1..21].copy_from_slice(deployer.as_bytes());
	bytes[21..53].copy_from_slice(salt);
	bytes[53..85].copy_from_slice(&init_code_hash);
	let hash = keccak_256(&bytes);
	H160::from_slice(&hash[12..])
}

impl<T: Config> AddressGenerator<T> for DefaultAddressGenerator {
	/// Formula: `hash("contract_addr_v1" ++ deploying_address ++ code_hash ++ input_data ++ salt)`
	fn contract_address(
		deploying_address: &T::AccountId,
		code_hash: &CodeHash<T>,
		input_data: &[u8],
		salt: &[u8],
	) -> T::AccountId {
		let entropy = (b"contract_addr_v1", deploying_address, code_hash, input_data, salt)
			.using_encoded(T::Hashing::hash);
		Decode::decode(&mut TrailingZeroInput::new(entropy.as_ref()))
			.expect("infinite length input; no invalid inputs for type; qed")
	}

- audience: Runtime Dev
  description: |-
    Fixes https://github.com/paritytech/polkadot-sdk/issues/12639

    A contract's `ContractInfo` is not written to `AccountInfoOf` until its constructor
    frame pops, so the `is_contract` collision guard in `ContractInfo::new` could not see an
    address that was still being constructed. A re-entrant `CREATE2` with the same salt and
    code (which is nonce independent) therefore resolved to the same address and ran a second
    constructor frame for one account, permanently leaking its consumer reference and code
    refcount and orphaning the second child trie's storage deposit.

    `push_frame` now rejects a nested instantiate whose target address already appears as a
    `Constructor` frame on the call stack, returning `DuplicateContract` (matching EIP-684).
