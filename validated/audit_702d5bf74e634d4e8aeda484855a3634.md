### Title
`spender_attested` asset transfers permanently freeze after an address definition change unless attestor proactively re-attests - (File: `storage.js`, `validation.js`)

### Summary
Ocore's `spender_attested` asset feature requires that, at the last-ball MCI of a spending unit, the owner's address must have an attestation from an asset attestor that is *more recent* than the address's latest `definition change`. This mirrors the BondNFT `epoch` pattern: validity of a legitimate transfer silently depends on an unrelated party (the attestor) performing a maintenance action (issuing a fresh `attestation`) after every routine, user-controlled event (an address definition change). If that maintenance action doesn't happen, the transfer permanently and deterministically reverts, even though nothing wrong occurred on the spender's side — funds of a `spender_attested` asset become stuck.

### Finding Description
`storage.filterAttestedAddresses` computes the set of addresses currently considered "attested" for a `spender_attested` asset: [1](#0-0) 

The query only counts an `attestations` row as valid if its `main_chain_index` is **greater than** the MCI of the most recent `address_definition_changes` row for that same address. This is invoked from `loadAssetWithListOfAttestedAuthors`, which is called for every payment of a `spender_attested` asset: [2](#0-1) 

`validatePaymentInputsAndOutputs` then hard-fails the spend if the owner address is not in `arrAttestedAddresses`: [3](#0-2) [4](#0-3) 

Just like BondNFT's `_transfer` requiring `epoch[bond.asset] == block.timestamp/DAY` (a value only refreshed by unrelated `distribute()` calls), here a spend of a `spender_attested` asset requires the *attestor* to have posted a fresh `asset_attestors`/`attestation` unit **after** the *owner's* most recent address-definition change. Posting a new address definition (key rotation, recovery, adding co-signers, etc.) is a completely ordinary, unprivileged action any address holder can take at any time and has nothing to do with the asset or the attestor. Once it happens, every prior attestation for that address is treated as stale by `filterAttestedAddresses`, and the address is excluded from `arrAttestedAddresses` until the attestor notices and republishes an attestation — an action the protocol cannot force and the spender cannot trigger themselves.

### Impact Explanation
Exactly as in the BondNFT report, the check blocking the transfer/spend is unrelated to any actual wrongdoing by the spender — it is an implementation artifact of freshness-tracking (attestation-after-definition-change) rather than a real compliance failure. If the attestor is inactive, unaware of the definition change, or the asset has been effectively abandoned (attestor no longer publishing updates), the affected address's holdings of that asset become **permanently frozen**: `validatePaymentInputsAndOutputs` will reject every payment input from that address with `"owner address is not attested"` indefinitely, with no way for the asset holder to unlock the funds themselves. This is a legitimate freezing-of-funds condition reachable by any normal address holder (including an AA holding a `spender_attested` asset, since AAs can also have their definitions effectively updated via template addresses) via a routine, unprivileged operation (posting an address-definition-change unit).

### Likelihood Explanation
Address definition changes are a normal, commonly-used feature (key rotation/recovery, adding a vault definition, etc.), and nothing warns the user that doing so will strand any `spender_attested` asset balances they hold. The attestor has no on-chain trigger telling it that a specific holder rotated their definition and needs re-attestation, so in practice the re-attestation may lag arbitrarily or never happen, especially for less-actively-maintained assets. Unlike BondNFT's daily `distribute()` calls (frequent, incidental), here the "refresh" event (an attestor scanning for definition changes and re-attesting) is not part of any automatic workflow at all, making the freeze likely to persist far longer, and even indefinitely.

### Recommendation
Decouple attestation freshness from address-definition-change MCI comparisons, or make address-definition changes automatically preserve attestation validity (e.g., only invalidate attestations when there is on-chain evidence the *keys* actually changed for the identity being attested, not merely a definition update the attestor might not care about). At minimum, provide holders a way to re-request/self-refresh attestation validity, or require attestors to include a supersedable/renewable attestation obligation instead of a strict `>` MCI ordering that any unrelated definition change can invalidate.

### Proof of Concept
1. Asset issuer creates a `spender_attested` asset and attests address `A` (`asset_attestors`/`attestation` message referencing `A`) at MCI `100`.
2. `A` legitimately spends the asset — succeeds, since the attestation (MCI 100) is the latest and no definition change exists yet.
3. Later, `A`'s owner rotates keys by posting a normal `definition` message / address-definition-change at MCI `200` (unrelated to the asset).
4. `A` attempts to spend more of the asset. `filterAttestedAddresses` runs:
   `main_chain_index (attestation=100) > IFNULL(latest definition_change mci=200, 0)` → false, so `A` is excluded from `arrAttestedAddresses`.
5. `validatePaymentInputsAndOutputs` rejects the payment with `"owner address is not attested"` at [5](#0-4) , and will continue to do so for every future spend attempt from `A`, until the attestor (an unrelated third party) notices and republishes an attestation for `A` after MCI 200 — which nothing in the protocol requires or automates.

// filter only those addresses that are attested (doesn't work for light clients)
function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}

// note that light clients cannot check attestations
function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
}
