### Title
Webhook signature verification is scoped to the wrong organization, allowing cross-organization webhook forgery when any configured GitHub App lacks a `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the request's HMAC signature against based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), but the actual repository/stack that ends up being mutated by the handler is resolved from a *different* payload field, `payload.dig('repository', 'full_name')`, with no check that this value is consistent with the owner used for signature verification.

### Finding Description
`verify_signature` picks the GitHub App config to verify against using an attacker-controlled field: [1](#0-0) [2](#0-1) 

That per-organization app config determines whether HMAC verification is enforced at all: [3](#0-2) 

Note `return true unless webhook_secret` — if the organization resolved by `repository_owner` has no `webhook_secret` configured (a supported, documented configuration for multi-org setups, see `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`), the signature check is bypassed unconditionally regardless of the actual signature header sent.

Meanwhile, the handler that decides *which tracked repository/stack to act on* uses a completely separate field of the same JSON body, never cross-checked against the "authenticated" owner: [4](#0-3) [5](#0-4) 

The `PushHandler`, which triggers a `GithubSyncJob` for a matched stack, only requires `ref` and `after` beyond what the base `Handler` requires, and reuses `stacks` from `repository_name` (i.e. `repository.full_name`): [6](#0-5) 

**The broken equality binding:** the code assumes `params['organization']['login']` (used to select the webhook secret / "authenticated organization") always equals the organization embedded in `params['repository']['full_name']` (the "repository written"). Nothing enforces that equality. An attacker who controls (or can freely target) an organization entry in `config/secrets.yml` that has `webhook_secret: nil` can send an arbitrary, unsigned JSON body where:
- `repository.owner.login` = the unprotected organization (satisfies/bypasses `verify_signature`)
- `repository.full_name` = `"<other-org>/<tracked-repo>"` (a completely different, tracked repository under a different, properly configured organization)

Because `verify_webhook_signature` short-circuits to `true` for the unprotected org, the request passes `before_action :verify_signature` with zero cryptographic proof of anything, and the handler then acts on the stack matched by the forged `repository.full_name`.

### Impact Explanation
This is a cross-organization/cross-repository write vector: an unprivileged, unauthenticated HTTP client can force `PushHandler` to enqueue `GithubSyncJob` for any stack tracked by Shipit, as if it were a legitimate signed webhook from GitHub for that repository, by simply routing the request through an organization entry that has no `webhook_secret` configured. This directly breaks the trust boundary the signature check exists to enforce ("only GitHub, authenticated via a shared per-organization secret, may trigger stack state changes"), and lets an attacker author webhook payloads for repositories/organizations they have no relationship with at all — matching the "cross-repository writes" and "unauthorized deploy" impact class. The same `repository.full_name`-vs-`repository.owner.login` mismatch equally affects every other handler under `app/models/shipit/webhooks/handlers/**` (pull request handlers, check-run handlers, etc.), all of which resolve their target repository purely from `repository.full_name`.

### Likelihood Explanation
Exploitability depends entirely on deployment configuration: it requires at least one configured GitHub organization in `config/secrets.yml` with `webhook_secret` unset/blank while other organizations' repositories are tracked by the same Shipit instance — a configuration explicitly documented and shown as valid in `docs/setup.md` (multi-org section) and shipped as a test fixture (`test/dummy/config/secrets_double_github_app.yml`, where `OrgTwo` has `webhook_secret: # nil`). In such deployments (any multi-tenant Shipit install where not every org’s GitHub App has a webhook secret set), the attack requires no credentials, no GitHub App private key, and no prior session — only a single unauthenticated `POST` to `/webhooks`.

### Recommendation
- In `WebhooksController#verify_signature`, require every configured GitHub App to have a non-blank `webhook_secret`; treat a missing secret as a hard misconfiguration (raise/refuse to boot) rather than as "verification passes."
- Cross-validate that `payload.dig('repository', 'owner', 'login')` (or `organization.login`) used to select the webhook secret is the *same* organization implied by `payload.dig('repository', 'full_name')` before dispatching to any handler.
- Consider deriving the acting repository from the same trusted field used for signature selection, rather than trusting a second, independently-controlled payload field.

### Proof of Concept
Given a `config/secrets.yml` with two orgs, `SecureOrg` (has `webhook_secret` set) and `OpenOrg` (no `webhook_secret`), and Shipit tracking a stack for `SecureOrg/critical-repo`:

```bash
curl -X POST http://shipit.example.com/webhooks \
  -H 'X-Github-Event: push' \
  -H 'Content-Type: application/json' \
  -d '{
        "ref": "refs/heads/master",
        "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
        "repository": {
          "owner": { "login": "OpenOrg" },
          "full_name": "SecureOrg/critical-repo"
        }
      }'
```

`repository_owner` resolves to `OpenOrg`; `Shipit.github(organization: 'OpenOrg').verify_webhook_signature` returns `true` unconditionally (no secret configured), so no `X-Hub-Signature` header is even required. `WebhooksController#create` then dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name('SecureOrg/critical-repo')` and enqueues `GithubSyncJob` for that stack — a stack belonging to an organization the attacker never authenticated against.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
