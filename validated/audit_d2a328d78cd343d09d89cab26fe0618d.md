### Title
`Shipit::Api::CCMenuController#show` uses `Stack.from_param!` instead of the `current_api_client`-scoped `stacks` lookup, disclosing any organization's stack via a leaked CCMenu token - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` scopes stack lookups to the token's `stack_id` via `stacks`/`stack` (line 74-80), but `Shipit::Api::CCMenuController` redefines `stack` to call `Stack.from_param!(params[:stack_id])` directly, bypassing that scoping entirely. Combined with the fact that `CCMenuUrlController#client` mints tokens without ever setting `stack_id` (making them global reads on `read:stack` regardless), any holder of a CCMenu URL/token can substitute an arbitrary `stack_id` in the path and read another organization's build status, lock reason, and last deploy sha.

### Finding Description
The binding that should hold is: `current_api_client.stack_id == rendered_stack.id` (or `current_api_client.stack_id.nil?` only for genuinely unscoped clients). In `BaseController` this is enforced by: [1](#0-0) 
`stacks` filters to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and the generic `stack` method looks up the requested `stack_id` param only within that scope.

`CCMenuController` overrides this protection: [2](#0-1) 
`stack` here calls `Stack.from_param!(params[:stack_id])` against the entire `Stack` relation, never consulting `current_api_client.stack_id`. `require_permission :read, :stack` (line 6) only checks that the token carries the `read:stack` permission bit - it performs no ownership/scope check, that is `require_permission!` merely calls `current_api_client.check_permissions!(operation, scope)`, which validates capability, not target identity.

Separately, `CCMenuUrlController#client` mints the token with no `stack_id` at all: [3](#0-2) 
so even without the `#show` override, a "per-stack" CCMenu token is in fact a global `read:stack` credential from the moment it's created (`find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, keyed only on user + name, not stack).

Attack: a user pastes their CCMenu URL for `org-a/repo` (`.../api/{org-a}/{repo}/ccmenu.xml?token=T`) into a public dashboard. An unprivileged attacker with no Shipit session or credentials copies `T` and issues `GET /api/{org-b}/{other-repo}/ccmenu.xml?token=T`. `authenticate_api_client` (overridden in `CCMenuController` at line 33-36) accepts `T` via query string. `stack` then resolves `org-b/other-repo` unconditionally, and `#show` renders build status, activity, lock reason and last deploy sha for that unrelated stack. No existing guard (`verify_signature`, `require_permission!`, `ExplicitParameters`, model validations) checks that the resolved stack matches the token's intended stack, because none of them inspect `stack_id` scoping for this controller.

### Impact Explanation
Any party in possession of one legitimately-issued, non-secret-looking CCMenu URL (routinely shared publicly, e.g. pasted into build-radar dashboards, wikis, or CI badges) can enumerate and read build status, lock/lock-reason, and last deploy SHA for **any** stack in the Shipit instance, across organizational boundaries, by only changing the URL path segment. This is repeatable indefinitely and against every stack hosted by the instance - it is an unauthenticated (from the target org's perspective) cross-tenant information disclosure, matching the "High - unauthenticated read of stack state" category.

### Likelihood Explanation
Preconditions are low-cost and realistic: the attacker only needs to obtain one CCMenu URL, which is designed to be embedded in public CI dashboards/badges (its whole purpose), and knowledge/guessing of a target `owner/repo` stack path (often public GitHub repo names). No Shipit session, API secret, or GitHub credential is required. The exploit is a single unauthenticated HTTP GET with a modified path segment.

### Recommendation
In `Shipit::Api::CCMenuController`, remove the private `stack` override and rely on `BaseController#stack`/`stacks`, which honors `current_api_client.stack_id`. Additionally, fix `CCMenuUrlController#client` to mint a stack-scoped `ApiClient` (set `stack_id: stack.id` and key `find_or_create_by!` on `[creator, stack, name]` rather than just `[creator, name]`), so each CCMenu token is bound to exactly one stack.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (conceptual addition)
test "a ccmenu token minted for one org cannot read another org's stack" do
  org_a_repo = Repository.create!(owner: 'org-a', name: 'repo-a')
  org_a_stack = Stack.create!(repository: org_a_repo, branch: 'main')
  org_b_repo = Repository.create!(owner: 'org-b', name: 'repo-b')
  org_b_stack = Stack.create!(repository: org_b_repo, branch: 'main')

  # Mint via CCMenuUrlController flow equivalent: token scoped (intended) to org_a_stack
  client = ApiClient.create!(permissions: %w[read:stack], stack_id: org_a_stack.id)

  get :show, params: { stack_id: org_a_stack.to_param, token: client.authentication_token }
  assert_response :ok # expected: token works for its own stack

  get :show, params: { stack_id: org_b_stack.to_param, token: client.authentication_token }
  # Binding under test: current_api_client.stack_id (org_a_stack.id) == rendered stack.id
  # BROKEN: CCMenuController#stack ignores stack_id scoping entirely
  assert_response :forbidden # currently fails: request returns 200 and leaks org_b's build data
end
```
