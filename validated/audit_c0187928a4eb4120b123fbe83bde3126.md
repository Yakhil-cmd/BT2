## Title
Missing Authorization Check on `creator` Field in `initialize_with_permission` Allows Arbitrary Pool-Creator Impersonation - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` accepts a `creator` account that is declared as a plain `UncheckedAccount` with no signature requirement, no PDA derivation, and no relationship constraint to the transaction signer (`payer`). Any permissioned `payer` can pass an arbitrary pubkey as `creator`, and that pubkey is permanently recorded on-chain as `pool_state.pool_creator`, the identity entitled to collect creator fees for the life of the pool.

### Finding Description
In the `InitializeWithPermission` accounts struct, `creator` is declared only as `/// CHECK: creator of pool` with no constraint: [1](#0-0) 

Unlike `payer_token_0`/`payer_token_1`/`payer_lp_token`, which are all constrained to `token::authority = payer`, the `creator` account has no `has_one`, `address`, `Signer`, or seed constraint tying it to the transaction signer or to any authorization record such as the `permission` PDA (which only verifies `payer`, not `creator`): [2](#0-1) 

The handler then writes this attacker-chosen, unvalidated key directly into permanent pool state as the authoritative `pool_creator`: [3](#0-2) [4](#0-3) 

This is the same bug class as CVE-2025-65031: the program trusts a client-supplied identity field (`creator`, analogous to Rallly's `authorName`) instead of deriving/verifying it from the actual signer, letting the caller attribute a privileged identity to an arbitrary, non-consenting or unrelated account. Contrast this with the permissionless `Initialize` path, where `creator` is a `Signer<'info>` and must match the account that funds and signs the pool creation: [5](#0-4) 

This `pool_creator` field is not a cosmetic label — it is later used as the sole authorization gate for collecting all accumulated creator fees: [6](#0-5) [7](#0-6) 

Because `pool.initialize()` is only ever called once at pool creation and there is no instruction that updates `pool_creator` afterward (confirmed by the sole occurrences of `pool_creator` being in `pool.rs` and the two `collect_creator_fee*` files), the misattribution is permanent for the pool's lifetime.

### Impact Explanation
An attacker who holds a valid `permission` PDA (a permissioned but still economically-untrusted actor, not a program admin) can create a pool while naming any arbitrary pubkey as `pool_creator`. This permanently and irrevocably assigns the exclusive right to collect all future creator-fee revenue generated by that pool's trading volume to an account that never consented to, requested, or signed for that role. This can be used to:
- Falsely present a victim (e.g., a well-known project or influencer address) as the "creator" of a pool for phishing/social-engineering purposes, mirroring the Rallly impersonation vector.
- Permanently misdirect creator-fee accounting to an unrelated or unreachable address (e.g., a burn address or an address the attacker controls but is not the actual liquidity/token deployer), corrupting the fee-ledger's intended ownership semantics with no remediation path since the field cannot be updated later.

This satisfies the "insolvent/incorrect fee-ledger accounting" and "unauthorized privileged effect" bar: an unprivileged/uncontracted identity is granted an on-chain privileged entitlement without consent or verification.

### Likelihood Explanation
Any account holding a `Permission` PDA (via `create_permission_pda`) can trigger this in a single transaction with attacker-chosen accounts and instruction data — there is no additional signature, oracle, or off-chain dependency required. The only precondition is possessing permissioned access to call `initialize_with_permission` at all, which is the intended caller of this exact instruction, making the misuse straightforward and reachable in the normal flow.

### Recommendation
Require `creator` to either be a `Signer` (mirroring the permissionless `Initialize` path) or add an explicit constraint proving consent/authorization from the named creator (e.g., a dedicated creator-authorization PDA signed by `creator`, or require `creator == payer` unless a verifiable delegation record exists). At minimum, do not allow an arbitrary unchecked account supplied solely by `payer` to be permanently recorded as the fee-collection authority.

### Proof of Concept
1. Attacker obtains a valid `Permission` PDA for their `payer` key (the normal precondition for calling `initialize_with_permission`).
2. Attacker submits `initialize_with_permission` with `payer` = attacker's key, but `creator` = an arbitrary pubkey of their choosing (a victim's known public address, or any unrelated/unreachable key) — no signature or additional proof is required for `creator`.
3. The instruction succeeds; `pool_state.pool_creator` is permanently set to the attacker-chosen key via `pool_state.initialize(...)`.
4. All subsequent `collect_creator_fee` calls now gate on `address = pool_state.load()?.pool_creator` matching the attacker-chosen key — a role the named account never agreed to and may not even control, with no instruction available to correct it.
