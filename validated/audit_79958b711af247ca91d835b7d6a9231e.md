### Title
`StatusHandler#process` writes CI status to commits by SHA only, with no check that the webhook's `repository` matches `commit.stack.repository`, enabling cross-repository forced-deploy - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits solely via `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, with no comparison against the webhook payload's `repository.full_name`. This breaks the binding the question identifies: the status written by `add_status` must originate from a payload whose repository equals `stack.repository`, but the code never enforces that equality, so any commit sharing a SHA across stacks/repositories receives the forged status and can become `deployable?`.

### Finding Description
The broken binding, stated explicitly: `commit.stack.repository.full_name == payload['repository']['full_name']` is assumed by the design but never checked, i.e. the actual code enforces only `commit.sha == params.sha` [1](#0-0) .

Path: `WebhooksController#create` parses the JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers, gated by `verify_signature`, which selects the GitHub App/webhook secret using `repository_owner` extracted from the *same attacker-controlled payload* (`params.dig('repository','owner','login')`) [2](#0-1) [3](#0-2) . Signature verification is delegated to `GitHubApp#verify_webhook_signature`, which returns `true` unconditionally `unless webhook_secret` is configured for that organization [4](#0-3) .

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
`sha` is a plain string column on `Commit` with no requirement that it be scoped to a particular repository at the query level here — the lookup only filters by `sha`, not by `stack_id` or `repository`. `create_status_from_github!` calls `add_status`, which creates a `Status` row, emits `deployable_status`, and calls `stack.schedule_merges` [5](#0-4) [6](#0-5) . `Status#schedule_continuous_delivery` then calls `commit.schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob.perform_later(stack)` if `commit.deployable? && stack.continuous_deployment? && stack.deployable?` [7](#0-6) , and `deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [8](#0-7) .

Because the lookup is SHA-keyed across the entire `commits` table, a commit belonging to a victim's stack whose SHA happens to also be tracked by an attacker-influenced repository (any repository with overlapping git history, e.g. a public fork the attacker controls, or shared vendor/base commits) receives the forged status. Its `deployable?` state flips to `true` purely from an inbound webhook whose declared `repository` was never compared to `commit.stack.repository`.

Existing guards do not close this gap: `verify_signature` authenticates the *sender's own organization* (derived from the very payload the attacker crafted) against that organization's configured secret — it says nothing about which `stack`/`repository` the SHA belongs to [9](#0-8) . `ExplicitParameters` on `StatusHandler` only validates `sha`/`state`/`branches` types, not repository identity [10](#0-9) . No model validation ties `Status`/`Commit` to the requesting repository at write time.

### Impact Explanation
An attacker who controls (or can send signed/accepted webhooks for) any repository whose commit history overlaps a victim's tracked SHA can write a `success` `Status` onto the victim's `Commit`, flip `Commit#deployable?` to `true`, and trigger `ContinuousDeliveryJob.perform_later(stack)` for the victim's stack — an unauthorized deploy on infrastructure the attacker does not own or administer. This is a payload for one repository mutating another's commit/stack state and triggering an unauthorized deploy, matching the "Critical" category (payload for one repository mutating another's stack/commit and an unauthorized deploy). The blast radius extends to any Shipit deployment tracking multiple stacks/repos that can share commit SHAs (forks, shared base history, cherry-picked/rebased commits, or repository renames), and is repeatable per matching SHA.

### Likelihood Explanation
This requires: (1) a target stack with `continuous_deployment?` true, unlocked commit, `stack.ignore_ci?` false as stated in the preconditions; (2) a commit SHA collision between the victim's tracked history and a repository the attacker can send an accepted status webhook for; (3) the attacker's declared organization in the payload having a configured/guessable webhook flow that passes `verify_signature` (either a genuinely owned repo/org with the app installed, or — separately — an org for which no `webhook_secret` is configured, which trivially bypasses verification per `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret`). Full exploitation depends on the SHA-collision precondition, which is realistic for forked/mirrored repositories but not universal; likelihood is moderate-to-high specifically in fork-based or multi-stack-per-repository setups, and it is fully repeatable once a colliding SHA is identified.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to commits whose `stack.repository` matches the webhook payload's `repository.full_name` (and/or restrict to `stack_id`s associated with that repository), e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { full_name: params.repository.full_name })`, before calling `create_status_from_github!`. Apply the same repository-binding check to other SHA-keyed webhook handlers (e.g. `CheckSuiteHandler`) if they share this pattern.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook for repo A must not write status onto a commit belonging to stack B" do
  victim_stack = shipit_stacks(:shipit) # repository == 'shopify/shipit-engine'
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, ...)

  # Attacker-controlled payload declares a DIFFERENT repository but the SAME sha
  forged_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  }

  # Binding under test, stated explicitly BEFORE tracing:
  # commit.stack.repository.full_name (shopify/shipit-engine) == payload['repository']['full_name'] (attacker/unrelated-repo)
  # => false, yet the handler still writes the status.

  assert_no_enqueued_jobs only: ContinuousDeliveryJob do
    Shipit::Webhooks::Handlers::StatusHandler.new(forged_payload).process
  end

  victim_commit.reload
  refute_predicate victim_commit, :success? # currently FAILS: status is written despite repository mismatch
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
