### Title
Missing cosigner-authorization check in `wallet.js` `"sign"` handler lets any paired device request signatures for shared/multisig addresses it is not a party to - (File: wallet.js)

### Summary
CVE-2020-9300 is an access-control class bug: authenticated, low-privileged principals can trigger actions on resources they are not authorized for (viewing restricted incidents, adding themselves as participants) because ownership/role checks are missing on the relevant handlers. The closest reachable analog in ocore is in the paired-device message handler for the `"sign"` subject: the `ifLocal` branch that processes a signing request for a locally-hosted (shared/multisig) address does not verify that the requesting device is actually a listed cosigner of that address/signing path before acting on the request.

### Finding Description
In the hub/device message handler `handleMessageFromHub`, the `case "sign":` branch validates the unit structure, payload hashes, and that `body.address` is among the unit's authors, then calls `findAddress(body.address, body.signing_path, {...})`. [1](#0-0) 

For a locally-hosted address (multisig hosted on several devices, or a multilateral/shared address with a device belonging to this wallet), the `ifLocal` callback fires. The authorization check that would confirm the sender (`from_address`, an arbitrary paired correspondent) is actually one of the address's registered cosigners/device members is explicitly commented out: [2](#0-1) 

The comment itself acknowledges the check exists and was intentionally disabled ("the commented check would make multilateral signing impossible"), meaning any correspondent device that is paired with the wallet — not just the actual cosigners of `body.address` — can send a `"sign"` request for that address/signing_path. The handler proceeds to validate the embedded unit via `network.handleOnlineJoint` and unconditionally raises the `"signing_request"` event (which normally surfaces a confirmation UI to the wallet's owner) using attacker-supplied `objUnit`, `assocPrivatePayloads`, and `signing_path`. [3](#0-2) 

By contrast, in the `ifRemote` branch (proxying a request to another device holding the actual key), the code *does* enforce that the sender is a listed cosigner before forwarding: `other_device_addresses.includes(from_address)`. [4](#0-3) 

This asymmetry confirms that the `ifLocal` path is missing the equivalent authorization check against the wallet/shared-address's actual cosigner list (e.g., `extended_pubkeys` table keyed by `wallet` and `device_address`, as referenced in the disabled code), which is exactly the class of access-control gap described in CVE-2020-9300: an entity that should not be treated as a participant/cosigner of a restricted resource (a shared address) can nonetheless act on messages scoped to that resource.

### Impact Explanation
Any paired device correspondent of a wallet can craft arbitrary `"sign"` requests naming any locally-hosted multisig/shared address they know about (addresses are often shared with counterparties in normal usage, e.g., for shared wallets or bilateral contracts) and any `signing_path`, together with an attacker-chosen `unsigned_unit` (payment outputs, private payloads, `signing_path`). Because the cosigner-membership check is disabled, the request is accepted and processed as if it came from a legitimate co-owner of that address, triggering unit validation and a `"signing_request"` UI event with attacker-controlled unit content that the wallet owner is prompted to sign. This is a concrete instance of missing authorization on a spending-adjacent, security-sensitive operation (requesting a cosigner's signature for a transaction), and it directly enables the "unauthorized participant added to a restricted transaction/resource" bug class from the CVE: an unauthorized party can insert itself into a multisig signing flow it has no right to interact with, and can flood/target the flow with crafted payment content designed to get funds signed away.

### Likelihood Explanation
Requires only that the attacker be a paired device of the victim (a low bar — pairing is done liberally in Obyte wallets, e.g., via chat, textcoin, bot interactions, or any prior correspondence) and that the attacker know the target shared/multisig address (routinely learned from a prior joint transaction, a shared address definition exchange, or simply asking the victim to pair). No compromise of keys or the hub is needed. The disabled check is a deliberate but incomplete workaround (removed to "not break multilateral signing"), indicating the authors were aware trust boundaries needed enforcement here but did not replace it with a correct per-address/per-path authorization check.

### Recommendation
Restore and correctly scope the authorization check in the `ifLocal` branch of the `"sign"` case: verify that `from_address` is a registered device/cosigner for the specific `body.address` (and ideally the specific `signing_path`) before invoking `network.handleOnlineJoint` and emitting `"signing_request"`. This can reuse the existing (but disabled) query pattern joining `extended_pubkeys`/wallet membership or the shared-address definition's device-address mapping, generalized to also cover multilateral (non-wallet) shared addresses, rather than removing the check outright.

### Proof of Concept
1. Device A pairs with Device B (normal correspondent pairing, e.g. via chat link) — no special privilege required.
2. Device A learns of a multisig/shared address `ADDR` hosted locally by Device B (e.g., from a previous joint transaction or a shared address exchange), for which A is not a listed cosigner/device member.
3. Device A sends a hub message to Device B: `{subject: "sign", body: {address: ADDR, signing_path: "r", unsigned_unit: <attacker-crafted payment unit>}}`.
4. Device B's `handleMessageFromHub` reaches `case "sign"`, structural checks pass (attacker fully controls the unit content), `findAddress` resolves `ifLocal` since `ADDR` is local to B.
5. Because the cosigner-membership check is commented out, B proceeds to validate the crafted unit and emits `"signing_request"` to the local UI/wallet owner as if A were a legitimate cosigner of `ADDR`, despite A never having been authorized on that address. [2](#0-1)
