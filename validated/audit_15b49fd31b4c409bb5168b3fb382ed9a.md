### Title
`StatusHandler#process` matches commits by bare SHA across all repositories, ignoring `branches` and `repository` scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` declares a `branches` field in its `params` schema, implying branch/repo-aware scoping, but `#process` never reads `params.branches` or `params.repository` at all. It queries `Commit.where(sha: params.sha)` globally and calls `create_status_from_github!` on every matching commit regardless of which repository or stack it belongs to.

### Finding Description
The binding that should hold is: for every `Commit` mutated by this handler, `commit.stack.repository.full_name == params.repository.full_name`, and additionally every branch name in `params.branches` should belong to that same repository. Neither is checked.

The code is: [1](#0-0) 

```
params do
  requires :sha, String
  requires :state, String
  ...
  accepts :branches, Array do
    requires :name, String
  end
end

def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

`params.branches` and `params.repository` are parsed by `ExplicitParameters` but never referenced inside `#process`. The lookup `Commit.where(sha: params.sha)` is not scoped to a stack or repository at all - any `Commit` row in the entire Shipit database sharing that SHA string will be mutated. Since Git commit SHAs are content-addressed and preserved across forks, an attacker who forks a victim's public repository will have commits with identical SHAs to the upstream repository. If the attacker's own repository/fork is also tracked as a Shipit stack (self-registered, or via an org-wide GitHub App installation covering many repos under one webhook secret verified only by `repository_owner`, not by exact repository), the attacker can trigger a real, correctly-signed `status` event carrying a victim SHA plus a `branches` array naming only their own throwaway branch. `WebhooksController#verify_signature` only checks the HMAC signature against the app/org-level webhook secret via `Shipit.github(organization: repository_owner)`; it never confirms that `params.repository.full_name` matches the repository the commit belongs to. `drop_unhandled_event` and `ExplicitParameters` schema validation only check that required fields exist and pass type checks - they do not enforce any repository/branch ownership binding. As a result, the presence of `branches` in the schema is decorative; it does nothing to prevent a payload naming an unrelated repo/branch from writing a `Status` onto a `Commit` belonging to `victim/prod`.

### Impact Explanation
An attacker can write a `Status` record on any `Commit` that shares a SHA with a commit in their own controlled repository, provided that SHA is also present in `victim/prod`'s Shipit-tracked stack. `Status` creation feeds `enable_ci_on_stack`, `schedule_continuous_delivery`, and `broadcast_update`, all called on the victim's commit/stack via `Commit#create_status_from_github!`. This can inject a fabricated "success"/"failure" CI status which downstream continuous-delivery/CI-gating logic on the victim stack may rely on to trigger deploys or unblock merges - meeting the "payload for one repository mutating another's stack/commit" Critical criterion. The blast radius spans any stack in the same Shipit instance whose GitHub App/org webhook secret verification does not bind to an exact repository.

### Likelihood Explanation
Preconditions: (1) the attacker's own repository must be reachable by a webhook whose signature verifies against `Shipit.github(organization: repository_owner)` for some `repository_owner` also covering the victim (e.g., same GitHub org/App installation, or attacker being able to register their own repo as a Shipit stack under an org Shipit trusts); (2) the attacker's repo must share a commit SHA with `victim/prod`, achievable simply by forking the victim's public repository. No Shipit session, API token, or secret is required - the attacker only needs push/webhook-trigger capability on a repo whose events are already accepted by the deployed GitHub App/webhook secret. This is a low-cost, repeatable attack against any Shipit instance whose webhook signature check is organization-scoped rather than exact-repository-scoped, combined with this handler's complete lack of repository/branch scoping.

### Recommendation
In `StatusHandler#process`, filter commits to only those whose `stack.repository.full_name` (or equivalent repository association) equals `params.repository.full_name`, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { full_name: params.repository.full_name })`. Additionally validate that any provided `params.branches` entries correspond to branches actually tracked by that repository's stacks before considering the status relevant, and reject/ignore statuses for SHAs that don't belong to the repository named in the payload.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Create two stacks/repos: `victim_stack` (repository `victim/prod`) with `commit = shipit_commits(:victim_release)` at `sha = "deadbeef..."`, and an unrelated `attacker_stack` (repository `attacker/fork`).
2. Post a `status` webhook payload: `{ sha: commit.sha, state: 'success', repository: { full_name: 'attacker/fork' }, branches: [{ name: 'attacker-throwaway' }] }`, signed with a secret that only verifies for `attacker/fork`'s configured hook/organization.
3. Assert binding before: `commit.stack.repository.full_name != payload['repository']['full_name']` (i.e., `'victim/prod' != 'attacker/fork'`).
4. Assert that after posting, `commit.statuses.count` is unchanged (`assert_no_difference('commit.statuses.count')`) - this fails today because `StatusHandler#process` creates the status regardless of the repository mismatch, since it never reads `params.repository` or `params.branches`.
