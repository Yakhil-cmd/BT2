## Analysis

Zest's vault contracts implement an ERC4626-style share conversion for deposits, using floor-division (`mul-div-down`) when total assets exceed total shares (price-per-share > 1) [1](#0-0) . Unlike `redeem`, which explicitly guards against a zero output with `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` [2](#0-1) , the `deposit` function has no equivalent check on `inkind` (the computed shares) before minting [3](#0-2) . This is the exact bug class from the H-3 report (rounding-to-zero share/strategy-token mint on deposit), reachable in all six mainnet vaults (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-ststxbtc`, `v0-vault-usdc`, `v0-vault-usdh`), since they share the identical `deposit`/`convert-to-shares-preview` pattern [4](#0-3) .

### Title
Zero-share deposits silently mint no zTokens while socializing the depositor's assets to existing suppliers - (File: mainnet/contracts/vault/v0-vault-stx.clar and sibling vaults)

### Summary
`deposit()` computes shares to mint via `convert-to-shares-preview`, which floors `(amount * total-supply) / total-assets` once the share price exceeds 1:1 (i.e., after interest has accrued) [1](#0-0) . If a depositor's `amount` is small enough that `amount * total-supply < total-assets`, `inkind` rounds to `u0`. `deposit()` only checks `(>= inkind min-out)` for slippage and never asserts `inkind > u0` [5](#0-4) , so with the common default `min-out = u0`, the transaction proceeds: the underlying asset is transferred in and `assets` is increased, but `ft-mint? zft u0 recipient` mints zero zTokens to the depositor [6](#0-5) .

### Finding Description
The `assets` variable (shared vault state) is incremented by the depositor's full `amount` regardless of whether any shares were minted [7](#0-6) , and share value is `total-assets / total-supply` (used in `convert-to-assets-preview` for all other suppliers' redemptions) [8](#0-7) . When a depositor's transaction rounds to zero shares:
- **Victim**: the depositing principal loses their deposited underlying asset (transferred into the vault) and receives 0 zTokens in return - permanently losing their principal to the pool.
- **Beneficiaries**: every *other* existing zToken holder, because `total-assets` increases while `total-supply` stays constant, raising `convert-to-assets-preview` for their existing shares.

This is not attacker-caused, but it is a genuine cross-principal harm through the shared `assets`/`zft` supply state: one unprivileged depositor's funds are involuntarily donated to all other suppliers.

### Impact Explanation
This is a **permanent freezing/loss of funds** for the affected depositor equal to their deposited amount (the underlying transfer succeeds, the mint silently produces zero shares, and there is no revert or refund path), which falls under the in-scope "permanent freezing of funds" / "direct theft of user funds at rest" impact classes.

### Likelihood Explanation
Occurs naturally, without any adversarial action, whenever `total-assets > total-supply` (i.e., anytime after interest has accrued, since `total-assets` grows continuously via `total-assets-preview`'s interest term [9](#0-8) ) and a user deposits a sufficiently small `amount` relative to the current share price. Any vault that has been live long enough to accrue meaningful interest, or any low-decimal/low-value asset (e.g., small STX deposits, or assets with fewer decimals), increases the probability that ordinary small deposits round to zero.

### Recommendation
Add `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` in `deposit()` for every vault, mirroring the existing check already present in `redeem()` [2](#0-1) , so the transaction reverts instead of silently consuming the depositor's funds for zero shares.

### Proof of Concept
1. Vault has accrued interest such that `total-assets = 2,000,000` and `total-supply = 1,000,000` (price-per-share = 2.0).
2. User calls `deposit(amount: u1, min-out: u0, recipient: user)`.
3. `convert-to-shares-preview(1)` computes `mul-div-down(1, 1000000, 2000000)` = `0` (floor rounding) [10](#0-9) .
4. `(>= inkind min-out)` → `(>= u0 u0)` passes; `(> amount u0)` passes since `amount = u1`.
5. `receive-underlying` pulls `1` unit of the underlying from the user; `ft-mint? zft u0 recipient` mints zero shares; `assets` is incremented by `1` [6](#0-5) .
6. The user has lost `1` unit of underlying permanently with zero zTokens received, while every other zToken holder's redeemable value increases proportionally.

```text
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

```text
(define-private (total-assets-preview)
  (let ((current-assets (var-get assets))
        (debt (debt-preview))
        (borrowed (var-get total-borrowed))
        (interest (if (> debt borrowed) (- debt borrowed) u0)))
    (+ current-assets interest)))
```

```text
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      (states (var-get pause-states))
      (u (try! (accrue)))
      (account contract-caller)
      (CAP-SUPPLY (var-get cap-supply))
      (current-assets (var-get assets))
      (inkind (convert-to-shares-preview amount)))

    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))
    
    (print {
      action: "deposit",
      caller: contract-caller,
      data: {
        depositor: account,
        recipient: recipient,
        amount: amount,
        shares-minted: inkind,
        assets: (+ current-assets amount)
      }
    })

    (ok inkind)))
```
