The reported CVE concerns a stack-corruption bug in musl libc's C `qsort` implementation (incorrect double-word primitives in its Leonardo-number-based smoothsort/pdqsort variant), which only manifests in C programs linked against musl and calling arrays exceeding ~7 million elements [1](#0-0) . This is a dependency at the OS/toolchain level (used only for musl-target cross-compilation tooling in this repo) and is not something the polkadot-sdk Rust codebase's own sorting code paths — like `Vec::sort`, `sort_unstable`, `sort_by_key`, or `sort_unstable_by` used across FRAME pallets (e.g. `substrate/frame/sassafras/src/lib.rs:852-919`, `cumulus/pallets/collator-selection/src/migration.rs:134`, `substrate/primitives/arithmetic/src/lib.rs:234-235`) — ever invoke, since Rust's standard library implements its own sorting algorithms and does not call into libc's `qsort` [2](#0-1) [3](#0-2) .

There is no reachable user entry point (extrinsic, XCM message, or contract call) in this codebase that would exercise musl's `qsort` C function with an attacker-controlled array of over seven million elements, and no such invariant violation exists in the Rust runtime code — this is purely a dependency-only issue outside the scope of the described attacker model.
