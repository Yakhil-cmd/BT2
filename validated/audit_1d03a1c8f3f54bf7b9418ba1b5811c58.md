### Title
Stack-scoped API token can read another stack's CCMenu status via `Api::CCMenuController#stack` bypassing stack-scope binding - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's stack-lookup method with an unscoped one, breaking the binding "stack a token authorises == stack it touches," the same class of bug as the oTAP report: a caller-controlled identifier (here, `params[:stack_id]`) is used to fetch a resource without being checked against the credential's authorized scope.

### Finding Description
`Api::BaseController` establishes the binding that a stack-restricted `ApiClient` may only touch the stack it was scoped to: [1](#0-0) 
`stacks` filters by `current_api_client.stack_id` when present, and `stack` is derived from that filtered scope via `stacks.from_param!(...)`. Permission checks (`require_permission`) only validate the permission string (`read:stack`, etc.) via `ApiClient#check_permissions!`: [2](#0-1) 
They never validate that the requested `stack_id` matches `current_api_client.stack_id`. That check is entirely delegated to the `stacks`/`stack` helper methods.

`Api::CCMenuController` bypasses that helper and defines its own `stack`: [3](#0-2) 
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
This queries `Stack.from_param!` against **all** stacks, not `current_api_client`'s scoped `stacks`. The controller only enforces `require_permission :read, :stack`, which is satisfied by any client holding the `read:stack` permission — including one that was deliberately scoped (via `stack_id` on the `ApiClient` record) to a single stack.

This is exactly analogous to the H-42 pattern: the code path that *should* bind an authorization credential to a single resource (the oTAP `user`/owner check in Magnetar; the `ApiClient.stack_id` scope check here) is skipped in one particular execution path (`_exitPositionAndRemoveCollateral`'s second call; `CCMenuController#stack`), while a different, correctly-scoped path (`base_controller#stack`) exists elsewhere in the same class hierarchy and creates a false expectation that scoping is enforced everywhere.

### Impact Explanation
An attacker who holds (or is given, e.g. via `CCMenuUrlController`, a browser extension flow, or any legitimately-issued single-stack API token) an `ApiClient` token scoped to one stack (`stack_id` set, permission `read:stack` only) can supply an arbitrary `stack_id` param to `Api::CCMenuController#show` and read the CCMenu XML status (`lastBuildStatus`, `lastBuildLabel`, `activity`, etc.) of any other stack in the Shipit instance, including private/internal stacks the token was never meant to access. This matches the in-scope High-impact class: "unauthenticated read of stack state, task streams or deploy output" performed by a credential that authorizes only one stack but is used to touch another.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped API clients for CCMenu integration (this is the documented purpose of `CCMenuUrlController`, which mints exactly such a token). Any holder of one such legitimately-issued, narrowly-scoped token — which is explicitly designed to be shared with lower-trust consumers (e.g. embedded in CI dashboards) — can immediately pivot to read other stacks' state by changing the `stack_id` in the URL; no additional secret, session, or privilege escalation is required beyond possessing one intentionally narrow-scope token.

### Recommendation
In `Api::CCMenuController#stack`, reuse the base controller's scoped lookup (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so the `current_api_client.stack_id` binding is enforced identically to every other API controller.

### Proof of Concept
1. As an admin, create a stack-scoped CCMenu client for `stack-a` (e.g. via `CCMenuUrlController#fetch`), yielding a token `T` whose `ApiClient` record has `stack_id = stack-a.id` and `permissions = ["read:stack"]`.
2. Using `T`, issue: `GET /api/stacks/stack-a/ccmenu.xml?token=T` → succeeds (expected).
3. Using the same `T`, issue: `GET /api/stacks/stack-b/ccmenu.xml?token=T` (any other stack in the instance).
4. `Api::CCMenuController#authenticate_api_client` authenticates `T` successfully; `require_permission :read, :stack` passes because `T` has `read:stack`; `stack` resolves via unscoped `Stack.from_param!("stack-b")`, returning `stack-b`'s CCMenu XML (build status, label, activity) even though `T` was only ever authorized for `stack-a`.
