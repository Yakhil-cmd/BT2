### Title
Webhook signature verification keys on `repository.owner.login` while event handlers act on the untied `repository.full_name` / `organization.login` fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to HMAC-verify the raw payload against using `repository_owner`, which is read from the payload's `repository.owner.login` (or `organization.login`) field [1](#0-0) [2](#0-1) . Once the HMAC check passes, every `Webhooks::Handlers::Handler` subclass instead resolves the target `Repository`/`Stack` (or `Team`/`organization`) from a *different* field of the same JSON body — `repository.full_name` in `Handler#repository_name` [3](#0-2)  — or from `organization.login` directly in `MembershipHandler` [4](#0-3) . Nothing verifies that these two fields refer to the same organization. In a multi-tenant Shipit deployment (multiple orgs configured, as shown in `docs/setup.md` and `config/secrets.development.shopify.yml`), an admin of one onboarded GitHub organization can forge a payload whose `repository.owner.login`/`organization.login` names their own org (so the signature check passes with their own legitimate `webhook_secret`) while `repository.full_name` names a repository belonging to a completely different, victim organization.

### Finding Description
The broken binding is: **`organization authenticated by verify_signature` == `organization/repository actually acted upon by the handler`**.

- Signature verification path: `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` → `Shipit.github(organization: repository_owner)` → `verify_webhook_signature` [1](#0-0) [2](#0-1) . This only proves the *raw body as a whole* was HMAC-signed with organization X's `webhook_secret` — it proves the sender knows org X's secret, nothing about which repository the body's other fields describe.
- Action path: every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) looks up the target `Repository` via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — an independent string field that an attacker fully controls in the JSON body they construct, as long as the overall body is HMAC-valid for the org they legitimately administer [3](#0-2) . `Repository.from_github_repo_name` splits this string on `/` with no cross-check against `repository.owner.login` [5](#0-4) .
- `MembershipHandler` is worse: it trusts `organization.login` directly to create/attach a `Team` and add/remove a `member`, again without tying it back to the org whose secret validated the request [6](#0-5) .

Because `verify_signature` treats the whole raw JSON as opaque bytes and only checks "was this HMAC'd by org X's secret," it never asserts "and org X is the same org referenced by `repository.full_name`/`organization.login` inside the body," exactly the class of bug described in the report: a signature covering a message whose *content fields consumed downstream* are not what the verifier actually checked semantically.

### Impact Explanation
An org admin who legitimately owns a GitHub App installation configured in this multi-tenant Shipit instance (and therefore its `webhook_secret`) can forge webhook deliveries that are validated as "signed by my org" but whose `repository.full_name`/`organization.login` point at any other tenant's repository/org known to the same Shipit install. This allows:
- `PushHandler`: trigger `stack.sync_github(expected_head_sha: ...)` on a victim stack for an arbitrary branch/SHA of the attacker's choosing [7](#0-6) .
- `StatusHandler`: inject fabricated CI status (`state`, `context`, `description`) onto any commit `sha` in the system, potentially satisfying deploy/merge gating checks for a victim stack [8](#0-7) .
- `CheckSuiteHandler`: force a refresh of check runs against a victim stack's commits [9](#0-8) .
- `MembershipHandler`: create/modify `Team` membership records tied to an arbitrary `organization.login`, which feeds directly into `Shipit.github_teams` authorization checks (`User#authorized?`) [10](#0-9) [11](#0-10) .

The status/push manipulation path is a cross-repository-write / unauthorized-deploy vector (a listed Critical/High impact); the membership path is an escalation into `Shipit.github_teams` authorization (listed High impact).

### Likelihood Explanation
Requires the attacker to be an admin of at least one GitHub organization that is legitimately onboarded into the same multi-tenant Shipit instance as the victim organization (a documented, supported configuration — multiple orgs share one Shipit deployment per `docs/setup.md` and `config/secrets.development.shopify.yml`). The attacker uses only their *own* org's webhook secret, which they already legitimately possess; no secret theft, session, or ApiClient token is needed for the victim org. This is exactly the "unprivileged relative to the victim, but a legitimate participant" trust level used in the source report (a malicious IDkg receiver signing with its own valid key over falsified content).

### Recommendation
In `WebhooksController#verify_signature`, after HMAC validation succeeds, cross-validate that every organization-identifying field in the payload (`repository.owner.login`, `organization.login`, and — critically — the owner segment of `repository.full_name`) is consistent with the `repository_owner` used to select the signing key, and reject the request (422) if they diverge. Equivalently, have each `Handler` re-derive `repository_owner`/`organization` from the same trusted field the controller used for key selection, rather than trusting `repository.full_name`/`organization.login` independently downstream.

### Proof of Concept
1. Attacker administers `attacker-org`, a GitHub organization configured in the same Shipit instance as victim organization `victim-org/victim-repo`, and knows `attacker-org`'s `webhook_secret`.
2. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: push` and a raw JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org webhook_secret, raw_body)` and sends it.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` matches → signature accepted [1](#0-0) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, taken from `payload.dig('repository', 'full_name')`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack [7](#0-6) [3](#0-2) , despite the signature only having been checked against `attacker-org`'s secret.
