### Title
Broken stack-scope binding in CCMenuController allows a stack-scoped ApiClient token to read the CI status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with `stack_id` set) may only see the stack it was scoped to, by filtering through `stacks` before resolving `stack`. `CCMenuController` overrides `#stack` and resolves it directly from `Stack.from_param!(params[:stack_id])`, completely bypassing the `current_api_client.stack_id` scoping check. This breaks the intended equality `token.authorized_stack_id == stack_id_being_read`, letting a token scoped to stack A read build/deploy status for any other stack B.

### Finding Description
`BaseController#stacks` is the authorization boundary for stack-scoped tokens: [1](#0-0) 
`stack` is normally resolved through this scoped relation (`stacks.from_param!`), so a token created with a `stack_id` (via `ApiClient#stack`) can only resolve stacks that match `current_api_client.stack_id`.

`CCMenuController`, however, redefines `stack` to load directly from the global `Stack` model, never going through `stacks`/`current_api_client.stack_id`: [2](#0-1) 

The only gate on the action is `require_permission :read, :stack`, which checks the `read:stack` *permission bit*, not which specific stack the token is bound to: [3](#0-2) 

This is directly analogous to the external report's root cause: a value that should be used consistently in a security-relevant computation (the scaling factor / share amount) is instead substituted with a different, unrelated value (the raw decimal count), silently producing a result far outside the intended bound. Here, the security-relevant binding "stack the token is authorized for" is silently substituted with "any stack_id supplied in the request", because `CCMenuController#stack` reimplements resolution outside of the authorization-scoped path that every other API controller uses (e.g. `StacksController`, `TasksController`, `HooksController` all inherit `BaseController#stack`, which passes through `stacks`).

The test suite confirms the intended scoping semantics exist elsewhere in the API (an `ApiClient` scoped to one stack only sees that stack via `index`): [4](#0-3) 
But `CCMenuControllerTest` never exercises a scoped token against a *different* `stack_id`, so this gap is untested.

### Impact Explanation
Any holder of a valid `ApiClient` token that was deliberately scoped to a single stack (an intentionally weaker/limited credential, e.g. issued to a specific team or CI integration for stack A) can read the CI/deploy status (`show` action renders `deploys_and_rollbacks.last`, build status, last build label, etc.) of **any other stack** in the Shipit instance by simply supplying a different `stack_id` in the CCMenu URL/query token param. This is an unauthorized cross-stack read of stack state — matching the "High" impact bucket ("unauthenticated read of stack state, task streams or deploy output" via escalation beyond the token's intended authorization scope).

### Likelihood Explanation
- No special privilege is required beyond possessing any valid, even minimally-scoped, API token with the `read:stack` permission (a normal, expected credential in this system).
- The endpoint additionally accepts the token via query string (`authenticate_api_client` override reading `params[:token]`), making it trivial to hit directly in a browser/CI widget URL, and the only input needed to pivot to another stack is the target `stack_id`, which is a predictable/enumerable value (`owner/repo/branch` style, per `stack_id_format` route constraint).
- The bug requires no interaction with GitHub, no privileged account, and no bypass of HMAC/signature checks — it's a straightforward missing-scope-check in the controller.

### Recommendation
- **Short term:** Make `CCMenuController#stack` resolve through the scoped `stacks` relation (i.e., reuse `BaseController#stack`/`stacks`) instead of `Stack.from_param!` directly, so a stack-scoped token can never resolve a stack outside `current_api_client.stack_id`.
- **Long term:** Add regression tests asserting that a stack-scoped `ApiClient` receives a 404/403 (not the CI payload) when the `stack_id` in the CCMenu request does not match its authorized stack, and audit all controllers that override `stack`/`stacks` for the same pattern.

### Proof of Concept
1. Create/obtain an `ApiClient` with `stack_id` set to Stack A (e.g., via `test/fixtures/shipit/api_clients.yml` pattern like `here_come_the_walrus`, which is scoped and has `read:stack` permission).
2. Using that token's `authentication_token`, issue: `GET /api/stacks/:stack_id_for_stack_B/ccmenu?token=<stack-A-scoped-token>`.
3. `authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` passes (client has the `read:stack` permission bit), and `stack` resolves Stack B directly via `Stack.from_param!(params[:stack_id])`, bypassing the `current_api_client.stack_id` restriction that `BaseController#stacks` would have enforced.
4. The response renders Stack B's build status/last deploy — data the token was never authorized to access.
