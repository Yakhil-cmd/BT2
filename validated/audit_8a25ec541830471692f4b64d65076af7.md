### Title
Mandatory secondary-AA trigger can permanently revert a primary AA's legitimate payment/withdrawal response - (File: `aa_composer.js`)

### Summary
When a primary AA response contains a payment output directed at another AA address, `ocore` automatically and unconditionally fires a secondary trigger on that AA as part of processing the primary trigger. If the secondary AA bounces for any reason (its own bounce-fee threshold, a hard-coded amount constraint, a paused/frozen state variable, etc.), the whole primary response — including any legitimate payment that was meant to reach the actual withdrawing user — is rolled back via `revert()`. This mirrors the Tokemak issue: a mandatory, externally-controlled sub-operation with its own pass/fail constraints is force-executed inside a withdrawal-adjacent flow, and its failure bricks the outer, otherwise-valid operation.

### Finding Description
`handleTrigger` in `aa_composer.js` collects the set of output addresses touched by a primary AA's response and, if any of them are themselves AA addresses, calls `handleSecondaryTriggers`: [1](#0-0) 

For every AA found among the output addresses, a *child trigger* is composed from the payment the primary AA is sending and `handleTrigger` is invoked recursively as a secondary trigger: [2](#0-1) 

Crucially, if any of these secondary triggers bounces, the error is propagated up and, for the primary invocation, causes a full `revert`, not merely a filtering-out of that one message: [3](#0-2) 

`revert()` rolls back to the initial savepoint, discards **all** accumulated responses (including any of the primary AA's other, perfectly valid messages such as a payment output to the real user requesting a withdrawal), and then calls `bounce()`: [4](#0-3) 

This is analogous to the Tokemak bug: in Tokemak, `_beforeTokenTransfer` unconditionally invokes `_rewarder.withdraw(from, amount, true)`, which unconditionally triggers `gptoke.stake(...)`, and if that mandatory sub-call reverts (due to `GPToke`'s own min/max/paused constraints), the entire withdrawal reverts even though the withdrawal itself was otherwise valid. Here, an AA composing a normal, valid withdrawal payment can be forced through a mandatory secondary-AA invocation whenever any output happens to be an AA address; that secondary AA's own bounce conditions (bounce-fee minimums enforced via `checkAAOutputs`/`MissingBounceFeesErrorMessage` in `aa_addresses.js`, or arbitrary logic written into the secondary AA's own `bounce()` calls) become a hard dependency for the primary AA's unrelated withdrawal to succeed.

### Impact Explanation
If a primary AA's payout logic routes funds through, or coincidentally targets, another AA address (e.g., a proxy/vault AA, a DEX AA, a pool AA) and that secondary AA is later paused, drained of its bounce-fee reserve, or otherwise made to always bounce (by design or by an attacker forcing it into a bounce state, e.g. by manipulating its state vars via unrelated triggers), then every future primary trigger whose response happens to send a payment to that AA will be reverted — including the requesting party's legitimate withdrawal/payment. Funds intended for withdrawal never leave the primary AA and the calling unit's response is bounced, effectively freezing the withdrawal path for as long as the downstream secondary AA condition holds. This matches "AA fund loss or freezing" and "node disagreement/inability to confirm new units performing withdrawal" impact classes.

### Likelihood Explanation
Likelihood is moderate-to-high in any composed system of interacting AAs (a common pattern in Obyte, e.g. proxy/vault AAs forwarding payments to other AAs as documented in the sample scripts such as `fundraising_proxy.oscript` and `things_registry_and_marketplace.oscript`). Any AA author who builds a withdrawal/payout flow that can, under some branch, direct an output to another AA address is exposed: that downstream AA does not need to be malicious — it only needs to enter a bounce condition (insufficient balance for its own bounce fees, a paused state var, expired feed) at the same moment the primary AA tries to pay out.

### Recommendation
- Do not force a synchronous, all-or-nothing secondary trigger for AA-directed outputs that are incidental to an otherwise self-contained primary response; consider making secondary-trigger failures non-fatal to the primary response (e.g., let the primary response still finalize with its own state changes and payments, and merely note that the secondary trigger bounced), similar to how Tokemak's fix suggestion decouples the mandatory sub-call (`claim`) from the core withdrawal logic.
- Alternatively, allow AA authors to explicitly opt out of automatic secondary triggering for specific outputs, or require an explicit acknowledgment/flag so that a downstream AA's bounce cannot silently roll back the primary AA's independent legitimate response.

### Proof of Concept
1. Deploy AA `A` with a withdrawal case that, on `trigger.data.withdraw`, sends a `payment` message to `trigger.address` and, in some other branch, forwards a fee/rebate `payment` to AA `B` (an external AA integration).
2. Configure/observe AA `B` such that it currently has a state where it will bounce for the amount/asset sent by `A` (e.g. `B`'s balance is insufficient to cover its own `bounce_fees`, matching how `checkAAOutputs`/`MissingBounceFeesErrorMessage` in `aa_addresses.js` flags this condition, or `B` contains a `bounce(...)` call for a currently-true condition).
3. Trigger `A`'s withdrawal case with a valid request. `handleTrigger` in `aa_composer.js` (lines 1702-1757) detects `B` among `arrOutputAddresses`, composes a secondary trigger, and invokes it recursively.
4. `B` bounces its secondary trigger; the error is bubbled to `handleSecondaryTriggers`'s `async.eachSeries` callback and `revert()` (lines 1759-1783) is invoked for the primary trigger.
5. Result: the entire response of `A`, including the intended withdrawal payment to the original requester, is rolled back and bounced — the withdrawal never completes even though `A`'s own withdrawal-branch logic and balances were valid.
