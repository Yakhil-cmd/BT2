### Title
Webhook signature validated against an organization derived from the same untrusted payload, allowing cross-organization forgery of GitHub events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization whose `webhook_secret` is used to verify the incoming HMAC signature by reading `repository.owner.login` (or `organization.login`) directly out of the **untrusted, attacker-controlled JSON body**, rather than from any authenticated, out-of-band source (e.g. a route parameter tied to a specific installation, or a per-repository/per-org routing key established outside the payload). Once the signature check passes, the actual work performed by the registered `Webhooks::Handlers::Handler` subclasses (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, PR handlers) resolves the target `Repository`/`Stack` from a *different* payload field, `repository.full_name` (`Handler#repository_name`), which is never cross-checked against the organization that was used to select the verifying secret.

### Finding Description
Shipit engine supports multiple GitHub organizations configured in `secrets.github`, each with its own `webhook_secret`, selected via `Shipit.github(organization:)`: [1](#0-0) 

The webhook entry point picks which organization's secret authenticates the request based purely on payload content: [2](#0-1) 

The binding that should hold is:
`organization whose secret validated the HMAC signature == organization that owns the repository the handlers subsequently act on`

But both sides of this equality are derived from the same single attacker-supplied JSON document, using two independent fields:
- Left side (`repository_owner`): `params.dig('repository','owner','login') || params.dig('organization','login')`, used only to pick the verifying secret.
- Right side (`repository_name`): `payload.dig('repository','full_name')`, used by every handler to look up the `Repository`/`Stack` to act on: [3](#0-2) 

Because HMAC verification only proves "this body was signed with organization X's secret", and organization X is *itself read from the body*, an attacker who legitimately controls (or has ever obtained) the `webhook_secret` for **any one** configured organization (e.g. by being a maintainer on a repo under Org A, where they can view/rotate that org's GitHub App webhook secret, or because it was configured on a repo they administer) can:
1. Set `repository.owner.login = "OrgA"` (so `Shipit.github(organization: "OrgA")` is looked up, and the signature is checked against Org A's secret — which the attacker knows).
2. Set `repository.full_name = "OrgB/critical-repo"` — any repository/stack tracked by the Shipit instance under a completely different organization.
3. Sign the full raw body with Org A's `webhook_secret` and submit it.

`verify_signature` succeeds (Org A's secret matches Org A's own signature), and the payload is dispatched to handlers, e.g.: [4](#0-3) 

`PushHandler#process` uses `stacks`, which resolves via `Repository.from_github_repo_name(repository_name)` where `repository_name` comes from the forged `repository.full_name`, and invokes `stack.sync_github(expected_head_sha: params.after)` on Org B's stack — an org the attacker never authenticated against. This enqueues `GithubSyncJob`, which uses the app's own privileged GitHub credentials (`stack.github_api`) to fetch commits and can advance the stack's known commit history / feed continuous delivery: [5](#0-4) 

The same pattern applies to `StatusHandler` (forging CI status for another org's commits, potentially unblocking deploy gating) and `MembershipHandler` (creating/altering `Team` membership using `organization.login` taken from the payload, independent of the signature-selected org), since none of these handlers verify that the org used to authenticate matches the org/repo they operate on.

### Impact Explanation
This breaks the deployment-trust binding explicitly called out as in-scope: "an organization that authenticated versus the repository that is written." The consequence is a **cross-repository/cross-organization write**: an attacker who is only entitled to send webhooks for Org A can, in a multi-org Shipit deployment, forge webhook events that mutate state (commit history, deployability, CI status, or team membership) for stacks/repositories belonging to Org B, using the target app's own GitHub credentials to fetch and persist that state. Depending on which handler is exercised, this can influence what Shipit considers deployable/mergeable (via forged `status` events on `Commit#create_status_from_github!`) or advance the git history Shipit trusts for a foreign stack (via `PushHandler`/`GithubSyncJob`), i.e. an unauthorized manipulation of deploy-gating state for a repository outside the attacker's authorized organization — matching the High-impact category "escalation into `Shipit.github_teams` authorization" (via forged `membership` events) and materially undermines per-organization isolation.

### Likelihood Explanation
This requires the Shipit instance to be configured with more than one GitHub organization (`github_default_organization` non-nil path in `lib/shipit.rb`), and requires the attacker to know one configured organization's `webhook_secret` — which is a normal, expected credential for anyone who administers a repo/organization onboarded to that Shipit instance, not a privileged Shipit account. Given that per-org secrets are inherently distributed to each onboarded organization, and nothing in the code prevents a signer for Org A from asserting facts about Org B's repositories, likelihood is realistic wherever multi-tenant Shipit deployments exist.

### Recommendation
Do not select the verifying secret from a field inside the same payload whose integrity that secret is meant to protect. Either:
- Bind the webhook endpoint to a specific organization/installation via the URL/route (out-of-band, e.g. `/webhooks/:organization`) and use that trusted parameter — not payload contents — to select `webhook_secret`; or
- After choosing a candidate secret and verifying the signature, additionally verify that `repository.owner.login`/`organization.login` used for secret selection matches the `repository.full_name`'s owner segment before invoking handlers, rejecting mismatches; or
- Use GitHub App installation IDs (rather than organization login strings pulled from the body) to disambiguate which secret to use, since installation ID assignment is not attacker-controlled payload content in the same trust sense.

### Proof of Concept
1. Configure Shipit with two organizations, `orga` and `orgb`, each with distinct `webhook_secret`s, and a tracked `Stack`/`Repository` for `orgb/critical-repo`.
2. As an attacker who administers a repo under `orga` (and thus knows `orga`'s `webhook_secret`), craft a `push` event payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orga" },
    "full_name": "orgb/critical-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orga_webhook_secret, raw_body)>` and `X-Github-Event: push`.
4. POST to `/webhooks`. `verify_signature` calls `Shipit.github(organization: "orga")` and validates successfully against the attacker-known secret.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("orgb/critical-repo")` and calls `stack.sync_github(expected_head_sha: ...)` for Org B's stack — an org the attacker's signature never proved authorization for.

Note: full verification of `Repository.from_github_repo_name` and `Stack#sync_github` internals was not completed within the available investigation budget; the analysis is based on `Handler#repository_name`/`#stacks` and `GithubSyncJob#perform`, which are sufficient to establish the binding break and its write-capable consequence, but a Devin session with full repo access could confirm the exact downstream side effects (e.g. whether continuous deployment is auto-triggered) for a complete severity determination.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
