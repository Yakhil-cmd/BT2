### Title
`membership` webhook: signature verified against `repository.owner.login`, but team mutation uses attacker-controlled `organization.login` — ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/org whose `webhook_secret` verifies a webhook using `repository.owner.login` (falling back to `organization.login` only if `repository` is absent), while `MembershipHandler` never reads `repository` at all — it creates/updates a `Team` using the independent `organization.login` field and mutates `Membership` rows via `member.login`. An attacker who forges the full JSON body can put a no-secret org in `repository.owner.login` (to pass `verify_signature`) and a different, real org in `organization.login` (to control which `Team`/org the handler actually mutates).

### Finding Description
The broken binding: **the org whose `webhook_secret` verified the request (`repository.owner.login` / fallback `organization.login`) must equal the org the handler mutates (`organization.login` used by `MembershipHandler`)**. This equality does not hold.

Code path:
- `Shipit::WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and uses it to fetch `Shipit.github(organization: repository_owner)` before calling `verify_webhook_signature` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved org has no configured `webhook_secret`: `return true unless webhook_secret` [3](#0-2) .
- `MembershipHandler` requires its own `organization.login` and `team.id`/`member.login` fields, completely independent from `repository` [4](#0-3) , and uses `params.organization.login` to build/find the `Team`, then adds/removes the `member` from it [5](#0-4) .

Because `repository` is only used by the controller for signature routing and is otherwise irrelevant to `MembershipHandler`, an attacker-controlled payload can set:
```json
{
  "action": "added",
  "repository": { "owner": { "login": "attacker-no-secret-org" } },
  "organization": { "login": "victim-org" },
  "team": { "id": 48, "name": "x", "slug": "x", "url": "http://x" },
  "member": { "login": "attacker-github-login" }
}
```
with `X-Github-Event: membership`. If `attacker-no-secret-org` is any org configured in `Shipit.github_organizations` without a `webhook_secret` (or falls back to no secret through `github_app_config`), `verify_signature` passes regardless of the `X-Hub-Signature` header content, while the mutated `Team`/`Membership` records belong to `victim-org`.

None of the existing guards catch this: `verify_signature` never cross-checks that the org it used for verification is the same one the eventual handler will act upon; `drop_unhandled_event` only checks the event name is registered; the `ExplicitParameters` schema in `MembershipHandler` validates types/presence but not that `organization.login` matches `repository.owner.login`; there is no `require_permission!`/`User#authorized?` check inside the webhook path (that model method only governs later authorization reads, which are now poisoned by the forged membership row).

### Impact Explanation
A successful request creates or deletes `Team`/`Membership` rows for an org the attacker never authenticated against, using only a webhook secret (or lack thereof) belonging to an unrelated org. Since `User#authorized?`/`Shipit.github_teams`-derived checks elsewhere in the app rely on `Membership` rows, this can be used to add an attacker-controlled GitHub login to a privileged team of `victim-org`, escalating into stack/task/deploy authorization for that org — matching "Authentication/authorization bypass" / "payload for one repository mutating another's stack/team" (Critical) since the request is fully unauthenticated with respect to `victim-org`. It is repeatable against any org pairing where one configured org lacks a `webhook_secret`.

### Likelihood Explanation
The exploit requires: (1) the target host to have multiple GitHub orgs configured (`Shipit.github_organizations`) as is standard in multi-tenant Shipit deployments, and (2) at least one of those orgs to have a blank/unset `webhook_secret` — a realistic misconfiguration since nothing in `GitHubApp` or the setup docs enforces a non-empty secret, and `verify_webhook_signature` silently no-ops in that case [3](#0-2) . Given that precondition, the attack costs a single unauthenticated HTTP POST with a crafted body and requires no valid signature at all, and is trivially repeatable.

### Recommendation
In `Shipit::WebhooksController#verify_signature`, do not let `repository.owner.login` silently diverge from the organization the specific handler will act on: either (a) always require `organization.login` (or the field each handler actually mutates) to match `repository.owner.login` when both are present, rejecting mismatches, or (b) have each handler declare which org field determines authorization and route signature verification through that same field. Additionally, `GitHubApp#verify_webhook_signature` should fail closed (return `false`, not `true`) when no `webhook_secret` is configured for an org, rather than treating an absent secret as "always valid."

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test ":membership forged repository.owner.login (no-secret org) mutates a different org's team" do
  # Setup: configure two orgs, "no-secret-org" (no webhook_secret) and "shopify" (has a secret)
  # e.g. via secrets fixture override or stub Shipit.github_app_config
  Shipit.stubs(:github_app_config).with('no-secret-org').returns({}) # no webhook_secret key
  Shipit.stubs(:github_app_config).with('shopify').returns({ webhook_secret: 'realsecret' })

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = 'sha1=deadbeef' # attacker has no secret, arbitrary/invalid signature

  body = {
    action: 'added',
    team: { id: shipit_teams(:shopify_developers).id, name: 'Developers', slug: 'developers', url: 'http://x' },
    organization: { login: 'shopify' },              # org actually mutated
    member: { login: 'attacker-login' },
    repository: { owner: { login: 'no-secret-org' } } # org used for signature verification
  }.to_json

  assert_difference -> { Membership.count }, 1 do
    post :create, body: body, as: :json
    assert_response :ok
  end

  # Equality that should hold but doesn't:
  # org verifying signature ("no-secret-org") != org whose Team/Membership was mutated ("shopify")
  membership_org = Team.find(shipit_teams(:shopify_developers).id).organization
  assert_equal 'shopify', membership_org
  refute_equal 'no-secret-org', membership_org
end
```
This demonstrates that the signature-verifying org (`no-secret-org`) and the mutated org (`shopify`) diverge, confirming the forged-webhook authorization bypass.
