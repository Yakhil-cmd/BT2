### Title
Frontrunnable fraud-proof / signed-order claims in `is_valid_signed_package`-based AA templates allow reward theft - (File: test/samples/payment_channels.oscript)

### Summary
The official payment-channel AA template shipped in the ocore repository uses `is_valid_signed_package()` to verify a peer-signed message and then pays out funds to `trigger.address` rather than to the address that is cryptographically tied to the signed message. Because the signed package (`trigger.data.sentByPeer`) is public information the moment it appears in a broadcast unit or in the mempool/DAG, any unprivileged party can copy it into their own trigger and redirect the payout to themselves, exactly mirroring the MessageProcessor "frontrun for profit" pattern where anyone can rebroadcast a valid `oracleMessage`/`oracleSignature` pair to capture `maybePaySender`'s reward.

### Finding Description
`is_valid_signed_package()` (`formula/evaluation.js` case `'is_valid_signed_package'`, backed by `signed_message.validateSignedMessage()`) only checks that the supplied signed package is validly authored by a *specific address argument* — it does not bind the payout recipient to that address. [1](#0-0) 

In the `payment_channels.oscript` sample AA that ships with ocore (and is validated/parsed by the test suite as a canonical AA example), the "fraud proof" case:
1. Accepts `trigger.data.sentByPeer`, a signed package that was presumably created and privately held by the honest channel closer's counterparty.
2. Validates it with `is_valid_signed_package(trigger.data.sentByPeer, ...)`, confirming only that *some* correctly-known address signed the embedded message.
3. Pays out the entire channel balance to `trigger.address` — i.e., whoever calls the AA function — instead of to the honest claimant who possesses/reveals the proof: [2](#0-1) 

Once the honest party broadcasts a unit invoking this fraud-proof case (or shares/leaks the signed package to prepare their claim), the `sentByPeer` signed package becomes visible to anyone monitoring the DAG/mempool before the honest unit becomes final. An attacker can extract that signed package and immediately submit their own trigger unit containing the identical `sentByPeer` object, but with `trigger.address` set to their own address, and (using a slightly higher fee/faster propagation) beat the honest sender's unit into the DAG. `is_valid_signed_package` validation still succeeds, the state checks still pass, and the AA sends the entire "send all" balance to the frontrunner's `trigger.address` instead of the honest party's.

This is the direct structural analog of the reported MessageProcessor issue: the payout recipient is derived from the caller-controlled parameter (`msg.sender` / `trigger.address`) instead of from the cryptographically-authenticated party embedded in the signed message, so possession of a valid signed message (which becomes public once submitted or shared) is sufficient to steal the associated reward via frontrunning.

The same anti-pattern is echoed in the accompanying `order_book_exchange.oscript` sample, where `is_valid_signed_package()` is used to validate signed limit orders, though there the balances are credited to the order's own signed `address`, so that specific case is not exploitable the same way — it demonstrates that the vulnerable pattern is isolated to templates that route payouts through `trigger.address`. [3](#0-2) 

### Impact Explanation
Any user who deploys this reference AA template as-is (it is provided as the canonical example of `is_valid_signed_package` usage in the codebase's test/sample corpus, likely to be copied by AA authors) is exposed to a guaranteed fund-theft primitive: the honest counterparty who legitimately holds proof of the peer's fraud loses their entire channel payout to a frontrunner, and the frontrunner recovers the channel's whole balance for the cost of a race-condition transaction. This is a concrete, unauthorized-spending / AA fund-loss scenario for the honest trigger sender.

### Likelihood Explanation
Likelihood is high whenever this fraud-proof case is actually needed (i.e., whenever a channel closer under-reports the amount transferred and the honest counterparty must submit the peer's genuinely signed record to correct it). Because the reward for submitting the signed package is unconditionally paid to `trigger.address`, and because the signed package must become visible (either broadcast in the honest party's own pending unit, or shared in preparation for submission) before it is included in a stable unit, it is trivially observable and copyable by bots that watch for any unit/trigger referencing `fraud_proof` and `sentByPeer`.

### Recommendation
The AA logic should not pay out to `trigger.address`. Instead, the payout address should be derived from the signed message itself (e.g., `signed_message.address`, i.e., the counterparty's own address encoded and authenticated inside the signed package, exactly as `order_book_exchange.oscript` does for its balances), so that only the party who is cryptographically entitled to the funds — not whoever races to submit the trigger — receives them. More generally, any AA (or JS wallet contract logic) that uses `is_valid_signed_package`/`is_valid_sig` to authorize a payment must bind the recipient to the signer identity contained in the validated package, not to the unauthenticated `trigger.address` of the calling unit.

### Proof of Concept
1. Channel `close_initiated_by` = 'A'; A under-reports `transferredFromMe`, i.e., lies about the amount spent.
2. B, holding a validly signed message from A (`{channel, period, amount_spent}`) proving the true higher amount, prepares a trigger unit to the AA with `trigger.data = {fraud_proof: true, sentByPeer: <A's signed package>}` in order to claim the "send all" balance.
3. Before B's unit is included/stabilized, an attacker C observes `sentByPeer` in B's broadcast unit (or in the mempool) and immediately posts their own trigger unit to the same AA with identical `trigger.data.sentByPeer` but `trigger.address = C`, using a slightly better fee/propagation to get processed first.
4. The AA's `is_valid_signed_package(trigger.data.sentByPeer, $addressA)` check succeeds (identical signed package), the `spentByA`/`spentByB` state checks pass, and the AA sends the entire channel balance (`payload.outputs: [{ address: '{trigger.address}' }]`) to C instead of B. [2](#0-1)
