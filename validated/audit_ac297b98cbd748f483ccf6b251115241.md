### Title
Cross-organization webhook signature confusion allows write to any repository's Stack using a different organization's webhook secret - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-GitHub-App deployment (`Shipit.github_organizations` configured with multiple orgs, each with its own `webhook_secret`), `WebhooksController#verify_signature` selects which organization's HMAC secret to verify the request against using `repository_owner`, which is read straight from the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). The event handlers that actually mutate state (`PushHandler`, `MembershipHandler`, the `PullRequest::*Handler`s) resolve the target `Repository`/`Stack`/`Team` from a *different* field of the same untrusted body: `params.dig('repository','full_name')` (or `params.organization.login` for membership events). Nothing enforces that the organization used to select/verify the signature is the same organization that owns the repository being acted upon.

### Finding Description
`verify_signature` in [1](#0-0)  computes:

```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```

where `repository_owner` is derived from the attacker-controlled payload: [2](#0-1) . `Shipit.github(organization:)` looks up per-organization config (secret, keys) via `github_app_config` in [3](#0-2) , so the org name embedded in the JSON body itself picks whose `webhook_secret` is used to validate the HMAC.

Once verification passes, `create` dispatches the raw, already-parsed JSON body to the event handler: [4](#0-3) . The handler base class resolves the acted-upon repository from `payload.dig('repository', 'full_name')`, a field independent of `repository_owner`: [5](#0-4) . Concrete handlers such as `PushHandler` ( [6](#0-5) ), and the `PullRequest::OpenedHandler`/`ClosedHandler`/etc. (`Shipit::Repository.from_github_repo_name(params.repository.full_name)`, e.g. [7](#0-6) ) all key off `repository.full_name`, and `MembershipHandler` keys team/org membership writes off `params.organization.login` ( [8](#0-7) ).

Because an attacker fully controls the raw JSON payload (only the HMAC signature is checked, and only against whichever org's secret `repository_owner` names), nothing requires `repository.owner.login`/`organization.login` (used for signature selection) to equal the owner encoded in `repository.full_name` (used for the actual write). If the deployment hosts multiple GitHub Apps/orgs (as `github_organizations`/`github_app_config` explicitly support, see [9](#0-8) ), an attacker who is a legitimate installer/webhook sender for **their own** organization (`org-A`, whose secret they legitimately know because GitHub delivers it to them for their own app installation) can craft a payload whose `repository.owner.login`/`organization.login` = `org-A` (so the signature check passes using `org-A`'s secret) but whose `repository.full_name` = `org-B/victim-repo` (a completely different, victim organization's repository). The request is HMAC-valid for `org-A`, yet the handler will look up and mutate `org-B`'s `Repository`/`Stack`/`PullRequest`/`Team` records — triggering `sync_github`, archiving/unarchiving review stacks, or creating team memberships for a repository/org the attacker never authenticated against.

This is the same class of bug as the M-14 report: the entity that is cryptographically authenticated (`org-A`, via its webhook secret) is not equal to the entity actually written to (`org-B`'s repository/stack/team) — i.e. `authenticated_organization == written_repository_owner` is never enforced.

### Impact Explanation
An attacker who legitimately controls one configured GitHub organization/app in a multi-org Shipit deployment can forge webhook events that pass signature verification (using their own known secret) but that target and mutate a different organization's `Stack`/`Repository`/`PullRequest`/`Team` records — e.g., forcing a `GithubSyncJob`/deploy-relevant `sync_github` on another org's stack, archiving/unarchiving another org's review stacks, or injecting arbitrary team membership (`MembershipHandler#process` calls `team.add_member(member)`) for a `Team` scoped to a different organization. This is a cross-repository/cross-organization write achieved purely by crafting a webhook payload, without needing write access to the victim's actual GitHub repository — matching the "cross-repository writes" / unauthorized-mutation impact bar.

### Likelihood Explanation
Requires: (1) the Shipit deployment to run in multi-organization/multi-app mode (`github_organizations` with more than one entry — an explicitly supported, documented configuration), and (2) the attacker to be a legitimate operator/owner of at least one of the configured organizations (so they know that org's `webhook_secret`, which GitHub would supply to them for their own installed app) or otherwise be able to trigger a webhook delivery signed with a known/weak secret for one org. Given multi-org support exists specifically for larger deployments serving several orgs/customers, this is a realistic configuration, and no additional privilege beyond "control one tenant org's webhook" is needed to write into another tenant's repository state.

### Recommendation
In `WebhooksController#verify_signature`, after successfully verifying the signature against `repository_owner`, cross-check that the organization owning the payload's `repository.full_name` (or `organization.login` for org-level events) matches `repository_owner` exactly before dispatching to handlers; reject (422) on mismatch. Alternatively, resolve the target `Repository`/`Team` using the *verified* `repository_owner` rather than re-deriving the owner from `full_name`/`organization.login` inside each handler, so the authenticated identity and the mutated identity are structurally the same value.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs/apps, `org-A` and `org-B`, each with distinct `webhook_secret`s (per `secrets.github` schema consumed by `github_app_config` in `lib/shipit.rb`).
2. Attacker controls `org-A`'s GitHub App installation and therefore knows `org-A`'s `webhook_secret` (standard, since GitHub gives it to whoever configures the webhook for their own org/app).
3. Attacker crafts a `push` webhook JSON body where:
   - `repository.owner.login` = `"org-A"` (used by `WebhooksController#repository_owner` to select the verification secret)
   - `repository.full_name` = `"org-B/victim-repo"` (used by `PushHandler`/`Handler#stacks` to select the target `Repository`)
4. Attacker computes `X-Hub-Signature` using `org-A`'s known secret and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "org-A").verify_webhook_signature(...)`, which succeeds because the signature was computed with `org-A`'s real secret.
6. `create` proceeds to `PushHandler.call(params)`, which resolves `stacks` via `Repository.from_github_repo_name("org-B/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on `org-B`'s stack — a write triggered by a payload the attacker forged for a repository they never authenticated against.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
