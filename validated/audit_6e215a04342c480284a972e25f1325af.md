### Title
Divisible private-payment duplicate check matches on a single output, causing remaining outputs of a multi-output private payment to be silently dropped — ([File: private_payment.js])

### Summary
In `validateAndSavePrivatePaymentChain()` the anti-duplicate check for divisible private assets queries **all** stored output rows for a `(unit, asset, message_index)` tuple and only compares a **single already-known** row against **any one** of the outputs declared in the incoming `payload.outputs` array. If a match is found for just one output, the whole chain is treated as an already-processed duplicate and the function returns `ifOk()` immediately — without ever inserting the other, still-missing outputs of that same message. This mirrors the `LiquidationRow` bug class: a partial/declared value (a single matched output) is used to short-circuit processing of the whole set (multiple outputs / the full `totalBalanceToLiquidate`), permanently losing the untouched remainder.

### Finding Description
`validateAndSavePrivatePaymentChain()` fetches candidate stored rows with: [1](#0-0) 

For divisible assets (no `output_index` filter), if the query returns exactly one row that already has an `address` (i.e., was previously revealed/saved), the code checks whether that single stored row matches **any** entry in `payload.outputs` via `.some()`: [2](#0-1) 

A `payment` payload for a divisible private asset can legitimately contain two outputs sharing the same `message_index` — e.g. a payee output and a change output. If only one of them (say the change output sent back to the sender) has already been persisted to `outputs` from an earlier, partial delivery of the private chain (a scenario reachable when the same private-payment chain is retransmitted/resent by the counterparty via `handleOnlinePrivatePayment` in `network.js`, or replayed through `handleSavedPrivatePayments`), the `.some()` match against that single row is enough to mark the **entire** payload as a duplicate: [3](#0-2) 

Once `bDuplicate` is true, the function calls `transaction_callbacks.ifOk()` and returns without ever calling `assetModule.validateAndSavePrivatePaymentChain(conn, arrPrivateElements, transaction_callbacks)`: [4](#0-3) 

This means the second (non-matching) output of the same payment — e.g. the actual recipient's payment output — is never inserted into `outputs`, and its corresponding spend of the source coin (`inputs` row marking the parent output as spent) is likewise never recorded via `divisible_asset.js`'s `validateAndSaveDivisiblePrivatePayment()`: [5](#0-4) 

The recipient never receives a usable, chain-verifiable private output (their wallet cannot spend funds whose predecessor chain was never fully saved), while the source coin from the parent chain link may already be marked `is_spent` from the partially-processed prior attempt, leaving the coins effectively stranded — unspendable by sender or recipient.

### Impact Explanation
This is fund freezing/loss reachable by an ordinary private-payment counterparty (no special privilege needed) — matching the "private-payment counterparty" reachability criterion. Once a divisible private-asset chain is (even partially) resent and a coincidental or crafted match occurs on one output, the remaining output can never be completed/saved, permanently stranding those private coins. Because private payments are validated and saved in isolation per-wallet (not globally consensus-checked in real time the way public payments are), this discrepancy is not caught by any cross-node consensus mechanism — it silently corrupts one party's private-payment state.

### Likelihood Explanation
Requires that exactly one of the two outputs of a divisible private payment message has already been persisted (address revealed) while the other has not — a state reachable through legitimate retry/retransmission flows in `network.js` (`savePrivatePayment` / `handleSavedPrivatePayments`) when private-chain delivery to hub/peer is interrupted or replayed, or through a malicious/careless private-payment counterparty deliberately resending a modified chain where one output intentionally reuses previously-seen `(address, amount, blinding)` values to trigger the false-duplicate short-circuit. This does not require any node/peer/hub compromise — it can be triggered by a normal payment counterparty crafting or replaying a private-payment message.

### Recommendation
For divisible assets, the duplicate check must verify that **all** declared outputs for the `message_index` are already fully and correctly stored (matching the complete set, not just one entry), not merely that one output out of possibly several coincides with one stored row. Consider comparing the full ordered/hashed set of `payload.outputs` against the full set of already-stored rows for that `(unit, asset, message_index)`, and only short-circuit as duplicate when every output is already present and matches exactly.

### Proof of Concept
1. Alice sends Bob a divisible private payment with two outputs in one `payment` message: `outputs[0]` = payee output to Bob, `outputs[1]` = change output back to Alice.
2. Due to a network hiccup / retry, only the change output (`outputs[1]`, address = Alice, some amount/blinding) gets persisted to `outputs` for that `(unit, asset, message_index)` on Bob's node (e.g., from a partial prior processing attempt or an earlier chain link handled independently).
3. Alice (or an attacker replaying the same private-payment envelope) resends the full `arrPrivateElements` chain for this payment via `handleOnlinePrivatePayment` → `private_payment.validateAndSavePrivatePaymentChain`.
4. `private_payment.js:70-107` fetches the one stored row (the change output), and since `payload.outputs.some(...)` finds a match against `outputs[1]`, the entire payload is flagged `bDuplicate = true`.
5. `transaction_callbacks.ifOk()` is invoked immediately; `outputs[0]` (Bob's payee output) and its spend-proof/inputs linkage are never inserted.
6. Bob's node believes the chain was already saved successfully (`ifOk`), but Bob's wallet never receives a spendable private output — the funds are stranded.

Note: I was not able to execute this in a live environment; the analysis is based on static code review of `private_payment.js`, `divisible_asset.js`, and `network.js`, and the exact upstream conditions needed to produce the "one output already stored, one missing" precondition (partial retries, hub caching) are inferred from the retry/resend code paths in `network.js` rather than directly observed.
