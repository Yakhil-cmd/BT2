### Title
Signature-verification org divergence allows cross-org `pull_request:reopened` forgery to unarchive/mutate a victim's production `ReviewStack` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a webhook using `repository_owner`, which is read from `params.dig('repository','owner','login')`. Every handler (including `ReopenedHandler`) instead resolves the actual repository/stack to mutate from `params.repository.full_name`, a completely separate, attacker-controlled field. Because these two values are never checked for equality, an attacker can pick an org with no `webhook_secret` configured (or one whose secret they don't need, since `verify_webhook_signature` returns `true` unconditionally when no secret is configured) for `repository.owner.login`, while pointing `repository.full_name` at a victim org/repo, causing `ReopenedHandler` to unarchive/recreate a `ReviewStack` for a repository that never authenticated the request.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:

`repository_owner_used_for_auth (params.repository.owner.login) == repository_used_for_mutation (Repository.from_github_repo_name(params.repository.full_name).owner)`

Trace:
1. `before_action :check_if_ping, :drop_unhandled_event, :verify_signature` runs before `create`. [1](#0-0) 
2. `verify_signature` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(...)`, where `repository_owner` is derived solely from `params.dig('repository', 'owner', 'login')`. [2](#0-1) [3](#0-2) 
3. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that organization's config: `return true unless webhook_secret`. [4](#0-3) 
4. Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full, unmodified `params` (not scoped to the "authenticating" org) to every registered handler. [5](#0-4) 
5. `ReopenedHandler#repository` resolves the actual `Repository` (and thus the review stack to mutate) independently, from `params.repository.full_name`, not from `repository_owner`: `Shipit::Repository.from_github_repo_name(params.repository.full_name)`. [6](#0-5) 
6. `Repository.from_github_repo_name` simply splits `"owner/name"` and does a DB lookup, with no relation back to whichever org authenticated the webhook. [7](#0-6) 
7. If `unarchive?` is true for that resolved repository's provisioning settings, `process` calls `stack.unarchive!` on the `ReviewStack` built by `ReviewStackAdapter.new(params, scope: repository.review_stacks)`, i.e., a stack that belongs to the victim org's repository, not the org whose config was used to check the signature. [8](#0-7) 

Exploit flow: attacker sends `POST /webhooks` with `X-Github-Event: pull_request`, body `action: "reopened"`, `repository.owner.login` set to an org configured in Shipit with no `webhook_secret` (or any org they can trivially forge because no secret gate exists for it), while `repository.full_name` is set to `"victim-org/victim-repo"` that maps to a real `Repository` with review stacks enabled and a production-environment `Stack`/`ReviewStack`. The controller resolves and validates the signature using the harmless/no-secret org (trivially passing), then hands the raw JSON to `ReopenedHandler`, which acts on `victim-org/victim-repo` and unarchives (or recreates) its review stack, regardless of the environment. Existing guards do not prevent this: `verify_signature` never compares `repository_owner` against `params.repository.full_name`'s owner; `drop_unhandled_event` and `ExplicitParameters` schema only check required fields' types/presence, not cross-consistency of the two owner fields; `Repository` model validations only validate character format, not authentication provenance.

### Impact Explanation
An unprivileged attacker with no Shipit session, no `api_clients_secret`, and no knowledge of the victim org's `webhook_secret` can trigger a webhook-authenticated side effect (`stack.unarchive!`, creation of a `ReviewStack`) against an arbitrary victim repository/stack that they don't own and never authenticated as. This is exactly "a payload for one repository mutating another's stack" — a Critical-severity outcome per the scope. Since `unarchive!` can bring back (or spin up) a review stack tied to a pull request the attacker controls (their own fork/PR), and the affected stack can be the production-environment stack, this could feed into subsequent deploy/merge automation associated with that stack, amplifying the blast radius. This is repeatable against any victim repository whose owner org is registered in Shipit, as long as the attacker can find/guess/configure any org identifier accepted by `Shipit.github(organization: ...)` with a blank or attacker-known secret.

### Likelihood Explanation
Preconditions: (a) Shipit must have at least one configured GitHub organization with no `webhook_secret` set (or one whose secret the attacker can otherwise satisfy) for `verify_webhook_signature` to short-circuit to `true`; (b) the victim repository must exist in Shipit with `review_stacks_enabled` and a provisioning behavior (`allow_all`, or `allow_with_label`/`prevent_with_label` satisfiable via PR labels the attacker controls on their own PR) that makes `unarchive?` true. Both are plausible operator configurations (e.g., an internal/test org with signature verification intentionally disabled, or multiple orgs onboarded with inconsistent secret configuration). No GitHub or Shipit secrets are required from the attacker; a raw HTTP POST with attacker-controlled JSON is sufficient, and the action is repeatable at will.

### Recommendation
Enforce that the organization used to select/verify the webhook secret matches the owner embedded in `repository.full_name` (and any other repository identifiers used later by handlers) before dispatching to handlers — e.g., derive a single canonical repository owner in `WebhooksController`, verify the signature against it, and reject the request if `repository.full_name`'s owner segment differs from `repository.owner.login`. Additionally, treat "no configured webhook_secret" as a hard failure (reject the webhook) rather than treating it as an implicit bypass, unless that behavior is explicitly desired for local/dev environments.

### Proof of Concept
Under `test/controllers/webhooks_controller_test.rb` (or a new test file), add a minitest:
1. Configure two orgs in the test Shipit config: `"noauth-org"` with `webhook_secret: nil` (or stub `Shipit.github(organization: "noauth-org").verify_webhook_signature` to return `true` unconditionally, matching production code path at `lib/shipit/github_app.rb:77`), and the real `"shopify"`/victim org used by `shipit_stacks(:shipit)` fixture with review stacks enabled and a production `Stack`.
2. Build a `pull_request` payload: `action: "reopened"`, `repository: { owner: { login: "noauth-org" }, full_name: "shopify/<victim-repo>" }`, with a valid `pull_request` sub-object matching an existing/associated PR/branch for the victim's `ReviewStack`.
3. Set `request.headers['X-Github-Event'] = 'pull_request'`, and post the payload without any valid `X-Hub-Signature` for the victim org (only satisfying "noauth-org"'s lack of a secret).
4. Assert response is `:ok` (200) — i.e., `verify_signature` passed using `"noauth-org"`.
5. Assert the victim's `ReviewStack` for `shopify/<victim-repo>` transitioned from archived to unarchived (`assert stack.reload.active?` or equivalent), proving the handler mutated a repository that never authenticated the request — violating the equality `repository_owner_used_for_auth == repository_used_for_mutation.owner`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
