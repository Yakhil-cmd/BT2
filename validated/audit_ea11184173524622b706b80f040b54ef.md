### Title
PR labels can overwrite reserved `ENVIRONMENT`/`BRANCH`/`GITHUB_REPO_*` keys in `ReviewStack#env`, letting `Command#interpolate_environment_variables` substitute attacker-controlled values into deploy-step arguments - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges pull-request label names (upcased, valued `"true"`) *on top of* the base `Stack#env` hash, and Ruby's `Hash#merge` lets the argument hash win on key collisions. A PR label literally named `environment` (or `branch`, `last_deployed_sha`, `github_repo_name`, `github_repo_owner`, `deploy_url`) therefore overwrites the corresponding reserved key with the string `"true"`, and that corrupted value is exactly what `Command#interpolate_environment_variables` substitutes for `$ENVIRONMENT` in deploy-step argument strings.

### Finding Description
The binding the question asks to validate is: *"the value substituted for `$ENVIRONMENT` in `interpolate_environment_variables` == `@stack.environment`, not a value derivable from `pull_request.labels`."* Tracing the code shows this binding is **false**.

- `Stack#env` builds the base hash including `'ENVIRONMENT' => environment` [1](#0-0) .
- `ReviewStack#env` overrides this method: `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` [2](#0-1) . In `Hash#merge(other)`, keys present in `other` win, so a label named `environment` (case-insensitive, since it's upcased) produces `labels["ENVIRONMENT"] = "true"`, which overwrites the `"ENVIRONMENT" => environment` entry from `super`.
- `TaskCommands#env` merges `@stack.env` into the task's env and then only adds `SHIPIT_USER`, `EMAIL`, `BUNDLE_PATH`, `SHIPIT_LINK`, `TASK_ID`, `IGNORED_SAFETIES`, `GIT_COMMITTER_NAME/EMAIL`, `deploy_spec.machine_env`, and `@task.env` — none of these restore `ENVIRONMENT` [3](#0-2) . The corrupted `ENVIRONMENT` value from the review stack's label-tainted `env` therefore survives into the final env hash used by deploy/rollback commands.
- `Command#interpolate_environment_variables` and `EnvironmentVariables#interpolate` then substitute `$ENVIRONMENT` tokens in argument strings (e.g. `cap $ENVIRONMENT deploy`) using this same env hash, with no distinction between "reserved system" keys and "label-derived" keys [4](#0-3) [5](#0-4) .

Existing tests confirm the label-merging behavior generally (`WIP`, `BUG` labels appear as env vars) but do not test for collisions with the reserved keys `ENVIRONMENT`, `BRANCH`, `LAST_DEPLOYED_SHA`, `GITHUB_REPO_NAME`, `GITHUB_REPO_OWNER`, `DEPLOY_URL` [6](#0-5) [7](#0-6) . No sanitization, key-collision guard, or reserved-word denylist exists in `ReviewStack#env` to prevent a label from shadowing a system-reserved environment variable name.

The attacker's action is opening/labeling a pull request on a repository that has ReviewStacks enabled, with a label literally named `environment` (or any of the other reserved names). Per the stated attacker model this is within scope ("label their own PR"). Once that PR is synced into a `ReviewStack`, any deploy/rollback/task step in that stack's `shipit.yml` that references `$ENVIRONMENT`, `$BRANCH`, `$GITHUB_REPO_NAME/OWNER`, or `$DEPLOY_URL` in its command string will have the attacker's label value (`"true"`) substituted instead of the intended stack/repo value.

### Impact Explanation
This lets a pull-request author corrupt the effective value of environment variables that are documented as trusted, system-derived deploy parameters (`ENVIRONMENT`, `BRANCH`, `GITHUB_REPO_NAME`, `GITHUB_REPO_OWNER`, `DEPLOY_URL`, `LAST_DEPLOYED_SHA`) for any deploy step that interpolates them via `$VARNAME` syntax, within that specific review stack. If a deploy script uses a pattern like `cap $ENVIRONMENT deploy`, the command executed by `PTY.spawn` will target an unintended value (`"true"`) instead of the operator-configured stack environment — an unauthorized/incorrect deploy target driven purely by PR label text, matching the "unauthorized deploy" Critical category. The blast radius is scoped to the specific `ReviewStack` tied to the attacker's own PR/repository (not cross-tenant), since `pull_request.labels` only affects that PR's associated stack.

### Likelihood Explanation
Preconditions: the target repository must use Shipit `ReviewStack`s (PR-based ephemeral stacks) and its `shipit.yml` deploy/task steps must reference one of the reserved variable names (`$ENVIRONMENT`, `$BRANCH`, etc.) via `$VARNAME` interpolation — this is a documented, encouraged pattern per the README's script parameters section. The attacker only needs to add a label with a reserved name to their own PR, which the audit's attacker model explicitly grants. No secrets, tokens, or privileged roles are required. This is repeatable for every PR/deploy cycle on any repository using this pattern.

### Recommendation
In `ReviewStack#env`, prevent PR labels from shadowing reserved/system keys — e.g., reverse the merge precedence so `super` wins on collision (`pull_request_labels_env.merge(super)`), or explicitly reject/filter label names that collide with `Stack#env`'s reserved keys (`ENVIRONMENT`, `BRANCH`, `LAST_DEPLOYED_SHA`, `GITHUB_REPO_NAME`, `GITHUB_REPO_OWNER`, `DEPLOY_URL`) before merging.

### Proof of Concept
Minitest plan (extends existing `test/models/shipit/review_stack_test.rb` pattern, no live GitHub required):
```ruby
test "#env does not let pull request labels override reserved ENVIRONMENT key" do
  stack = shipit_stacks(:review_stack)
  true_environment = stack.environment
  stack.pull_request.labels = ["environment"]

  assert_equal true_environment, stack.env["ENVIRONMENT"]
end

test "Command#interpolated_arguments resolves $ENVIRONMENT to stack.environment even with a colliding label" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["environment"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  command = Shipit::Command.new('cap $ENVIRONMENT deploy', env: env, chdir: '.')

  assert_equal [%(cap #{stack.environment} deploy)], command.interpolated_arguments
end
```
Both sides of the binding equality (`env["ENVIRONMENT"]` vs. `stack.environment`) diverge with current code — `env["ENVIRONMENT"]` becomes `"true"` instead of `stack.environment` — demonstrating the binding is broken.
