### Title
Uncontrolled resource consumption via ZIP-bomb in private-payment file import - ([File: wallet.js])

### Summary
`wallet.js`'s `handlePrivatePaymentFile()` accepts a ZIP file (a "private payment" / textcoin asset payload sent by a private-payment counterparty) and unpacks it with `jszip` before parsing the enclosed JSON chain data. Its only defense against a ZIP-bomb style attack is a check on the ZIP's self-declared, attacker-controlled `uncompressedSize` header field, not on the actual bytes produced by decompression, mirroring the CVE-2023-46104/CVE-2024-23952 Apache Superset ZIP-bomb bug class (uncontrolled resource consumption on unpacking an untrusted archive).

### Finding Description
`storePrivateAssetPayload()` builds a ZIP containing a `private_textcoin` entry with the payment chain JSON, used when sending a private-asset textcoin payload to a counterparty: [1](#0-0) 

The counterparty later imports it via `handlePrivatePaymentFile()`, which loads the archive with `JSZip.loadAsync()` and then attempts a size guard before decompressing the entry contents: [2](#0-1) 

The guard `entry._data.uncompressedSize > 100 * 1024 * 1024` reads the *declared* uncompressed-size field stored in the ZIP local/central-directory header — a value fully controlled by whoever crafted the archive. It is not validated against the size actually produced by the DEFLATE decoder. A malicious counterparty can forge a ZIP whose header claims a small `uncompressedSize` (e.g., a few KB) while the underlying compressed stream inflates to gigabytes of data (a classic ZIP bomb), bypassing the size check entirely. When `entry.async("string")` is subsequently called, JSZip performs the actual inflate and will hold the resulting oversized string/buffer in memory, exhausting the wallet process's memory/CPU. [3](#0-2) 

This function is directly reachable by any private-payment counterparty who can convince/cause a wallet to open a crafted "private payment"/textcoin ZIP file — the intended use case for this code path per `storePrivateAssetPayload`/`handlePrivatePaymentFile` pairing.

### Impact Explanation
Successful exploitation crashes or hangs the victim's wallet process (denial of service) via memory/CPU exhaustion when importing an attacker-supplied private-payment ZIP. This does not lead to double-spend, fund loss, or consensus disagreement, but it can render a wallet unable to process legitimate private payments during/after the attack, satisfying the "network unable to confirm new units" class only in a very narrow, single-node sense (local resource exhaustion, not network-wide). Given the rules require concrete unauthorized spending/double-spend/inflation/fund loss/consensus impact, this bug's practical impact is limited to a single victim wallet DoS.

### Likelihood Explanation
Any counterparty in a private-payment/textcoin flow can craft and deliver a malicious ZIP (the delivery mechanism for these files is out-of-band, e.g., file share/email/link, but the parsing logic itself is what's vulnerable and is exactly the flow this code implements). No special privileges are needed to craft the payload beyond producing a valid-looking ZIP with a forged size header, which is a well-known and easy technique (e.g., nested/highly-compressible DEFLATE streams).

### Recommendation
- Enforce a hard limit on bytes actually produced during decompression (e.g., use a streaming inflate with a byte-count cutoff, or `jszip`'s streaming API `entry.internalStream("text")` combined with counting emitted bytes and aborting once a threshold is exceeded) instead of trusting the declared `uncompressedSize` header.
- Additionally bound `compressedSize`/total archive size and reject entries whose compression ratio is implausibly high (e.g., > 100:1) before attempting to inflate.

### Proof of Concept
1. Craft a ZIP file containing one entry named `private_textcoin` where the local file header declares `uncompressed_size` as a small value (e.g. 1024 bytes) but whose actual DEFLATE stream, when inflated, expands to several GB (standard zip-bomb construction, e.g. highly repetitive data with maximum compression).
2. Deliver this file to a victim wallet as if it were a legitimate private-payment/textcoin file (the same channel normally used for files produced by `storePrivateAssetPayload`).
3. Victim wallet calls `handlePrivatePaymentFile(fullPath, content, cb)`; the size check at wallet.js:2895 passes because it only inspects the forged header value.
4. `entry.async("string")` (wallet.js:2897) fully inflates the bomb into memory, exhausting the process's memory/CPU and causing a crash or unresponsive wallet. [4](#0-3)
