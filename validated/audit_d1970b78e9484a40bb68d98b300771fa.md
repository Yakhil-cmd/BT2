### Title
Address Lookup Table resolution performed before cheap validity checks, enabling unauthenticated-cost DoS via attacker-controlled lookup keys - (File: `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs`)

### Summary
`translate_to_runtime_view` resolves every `MessageAddressTableLookup` in an incoming packet by calling into `Accounts::load_lookup_table_addresses_into`, which performs an `accounts_db` account load (`load_with_fixed_root`) for each referenced ALT account key [1](#0-0) , [2](#0-1) . This resolution step runs **before** the cheaper, fast-fail checks — blockhash/nonce age validation (`check_transaction_without_status_cache`) and fee-payer funding validation (`check_fee_payer_unlocked`) — that would otherwise let the banking stage cheaply discard a bogus or unfunded transaction [3](#0-2) . Because a transaction only needs a syntactically valid (self-generated, free) signature to reach this code path, an attacker can flood the cluster with packets whose message references many distinct (including non-existent/cold) ALT account keys to force expensive, uncosted `accounts_db` lookups on every validator node, before any fee is charged or the transaction is otherwise rejected.

### Finding Description
The bug class in the Keycloak advisory is: an unvalidated, attacker-controlled identifier (a proxy header value) is used to trigger an expensive resource-bound operation (DNS resolution) *before* proper validation/trust checks are applied, tying up shared worker/IO threads.

The analogous pattern here is the ordering of operations inside `try_handle_packet` / `translate_to_runtime_view`:
1. Packet is parsed and sanitized (`SanitizedTransactionView::try_new_sanitized`, cheap, in-memory) [4](#0-3) .
2. Account-lock-limit is checked (cheap, count-only) [5](#0-4) .
3. `load_addresses_for_view` is called unconditionally for any V0 transaction, which walks every `address_table_lookup` entry in the message and calls `Bank::load_addresses_from_ref` → `Accounts::load_lookup_table_addresses_into` → `load_with_fixed_root` → `AccountsDb::load` for **each** ALT account key referenced [6](#0-5) , [7](#0-6) , [2](#0-1) .
4. Only *after* this potentially disk-touching lookup work does the code perform the inexpensive blockhash/nonce-age check and fee-payer funding check, both of which are cheap, in-memory/short-circuiting validations that could reject most spam transactions immediately [3](#0-2) .

Because signature generation is free (an attacker just signs with a locally-generated keypair; no funded account or valid blockhash is required to construct a syntactically valid packet), and because a single V0 message can reference multiple ALT lookups up to the account-lock limit, an attacker can craft a stream of packets that are cheap to produce but each force multiple `accounts_db` reads on every receiving validator before any fee-based cost accounting or the compute-budget/cost-model machinery (`CostModel::calculate_cost`) is even invoked [8](#0-7) . The expensive resolution is not itself capped by anything computed from the (unresolved) transaction's declared compute budget, mirroring the Keycloak flaw where a costly resolution is performed against unauthenticated/unvalidated attacker input ahead of the checks that would otherwise gate it.

### Impact Explanation
Repeated, cheap-to-produce packets carrying multiple ALT lookups can force disproportionate `accounts_db` load work (potentially disk I/O for cold/nonexistent lookup-table accounts) on the packet-receive/buffering hot path of every validator that ingests the packet, ahead of the fee-payer and blockhash checks that would otherwise reject it for free. Sustained at scale, this can degrade banking-stage/receive-and-buffer throughput cluster-wide, which is a transaction-triggered availability/DoS concern rather than a fund-movement or consensus-divergence bug. It does not by itself allow unsigned fund movement, minting, CPI privilege escalation, or replay.

### Likelihood Explanation
Reachable by any unprivileged sender: the packet only needs to parse as a valid V0 sanitized transaction with a self-consistent (but not necessarily funded) signature and one or more ALT lookups; no on-chain state, existing balance, or special privilege is required to reach the resolution step. The attacker fully controls the referenced ALT account keys and can maximize the number of lookups per message up to the account-lock limit.

### Recommendation
Reorder the checks in `try_handle_packet`/`translate_to_runtime_view` so that cheap, fast-reject validations (blockhash/nonce age via `check_transaction_without_status_cache`, and fee-payer funding via `check_fee_payer_unlocked`) run before the potentially disk-touching ALT resolution (`load_addresses_for_view`). Additionally consider bounding/costing ALT resolution (e.g., charging or rate-limiting per distinct ALT account referenced) independent of whether the transaction is ultimately accepted, so that the expensive lookup work cannot be forced for free ahead of validation.

### Proof of Concept
Conceptual (no working exploit executed — this is a code-path/ordering analysis):
1. Generate an arbitrary, locally-created keypair (no funding needed) and sign a V0 message referencing the maximum allowed number of distinct, non-existent Address Lookup Table account keys in `address_table_lookups`.
2. Submit a high-rate stream of such packets to a validator's banking stage.
3. Each packet enters `try_handle_packet` → `translate_to_runtime_view` → `load_addresses_for_view`, forcing an `AccountsDb::load` per referenced (bogus) ALT key before the blockhash-age or fee-payer checks run, consuming banking-stage CPU/IO capacity for transactions that are guaranteed to be rejected and never pay a fee.

Note: I could not fully confirm within the available tool budget whether cryptographic signature verification (`SigVerifyStage`) is guaranteed to occur strictly before this code path for all packet ingestion routes in this codebase snapshot; this should be verified directly in a full checkout before treating the PoC as conclusive.

pub(crate) fn translate_to_runtime_view<D: TransactionData>(
    data: D,
    bank: &Bank,
    transaction_account_lock_limit: usize,
    sanitize_config: &SanitizeConfig,
) -> Result<(RuntimeTransaction<ResolvedTransactionView<D>>, u64), PacketHandlingError> {
    // Parsing and basic sanitization checks
    let Ok(view) = SanitizedTransactionView::try_new_sanitized(data, sanitize_config) else {
        return Err(PacketHandlingError::Sanitization);
    };

    let Ok(view) = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    ) else {
        return Err(PacketHandlingError::Sanitization);
    };

    // Discard non-vote packets if in vote-only mode.
    if bank.vote_only_bank() && !view.is_simple_vote_transaction() {
        return Err(PacketHandlingError::Sanitization);
    }

    if usize::from(view.total_num_accounts()) > transaction_account_lock_limit {
        return Err(PacketHandlingError::LockValidation);
    }

    let (loaded_addresses, deactivation_slot) = load_addresses_for_view(&view, bank)?;

    let Ok(view) = RuntimeTransaction::<ResolvedTransactionView<_>>::try_new(
        view,
        loaded_addresses,
        bank.get_reserved_account_keys(),
    ) else {
        return Err(PacketHandlingError::Sanitization);
    };

    // Validate no duplicate accounts (must be after resolution to catch ALT duplicates)
    if validate_account_locks(view.account_keys(), transaction_account_lock_limit).is_err() {
        return Err(PacketHandlingError::LockValidation);
    }

    Ok((view, deactivation_slot))

/// Load addresses from ALTs (if necessary) and return the
/// [`LoadedAddresses`] with the minimum deactivation slot.
pub(crate) fn load_addresses_for_view<D: TransactionData>(
    view: &SanitizedTransactionView<D>,
    bank: &Bank,
) -> Result<(Option<LoadedAddresses>, Slot), PacketHandlingError> {
    match view.version() {
        TransactionVersion::Legacy | TransactionVersion::V1 => Ok((None, u64::MAX)),
        TransactionVersion::V0 => bank
            .load_addresses_from_ref(view.address_table_lookup_iter())
            .map(|(loaded_addresses, deactivation_slot)| {
                (Some(loaded_addresses), deactivation_slot)
            })
            .map_err(|_| PacketHandlingError::ALTResolution),
    }
}

    pub fn load_addresses_from_ref<'a>(
        &self,
        address_table_lookups: impl Iterator<Item = SVMMessageAddressTableLookup<'a>>,
    ) -> Result<(LoadedAddresses, Slot), AddressLoaderError> {
        let slot_hashes = self
            .transaction_processor
            .sysvar_cache()
            .get_slot_hashes()
            .map_err(|_| AddressLoaderError::SlotHashesSysvarNotFound)?;

        let mut deactivation_slot = u64::MAX;
        let mut loaded_addresses = LoadedAddresses::default();
        for address_table_lookup in address_table_lookups {
            deactivation_slot = deactivation_slot.min(
                self.rc
                    .accounts
                    .load_lookup_table_addresses_into(
                        &self.ancestors,
                        address_table_lookup,
                        &slot_hashes,
                        &mut loaded_addresses,
                    )
                    .map_err(into_address_loader_error)?,
            );
        }

        Ok((loaded_addresses, deactivation_slot))
    }
