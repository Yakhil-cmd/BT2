### Title
Unfiltered `machine.environment` from an attacker's fork `shipit.yml` reaches `PTY.spawn` env for shell-interpreted steps - (File: lib/shipit/task_commands.rb, app/models/shipit/deploy_spec.rb, lib/shipit/command.rb)

### Summary
`TaskCommands#env` merges `deploy_spec.machine_env` — which is read verbatim from the checked-out `shipit.yml`'s `machine.environment` key — directly into the environment passed to every task step's `Command`, with no allowlist filtering. Because the review stack under `allow_all` checks out the attacker's own fork/PR branch, the attacker fully controls this `shipit.yml`, and thus controls arbitrary environment variable keys (including `GIT_ASKPASS`) that reach `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` for every shell-interpreted deploy/dependency step.

### Finding Description
The broken binding: `deploy_spec.machine_env` (attacker-authored) should equal `filtered_env` (an allowlisted subset), but in `TaskCommands#env` it is merged unfiltered: [1](#0-0) 

Contrast this with `DeploySpec#filter_deploy_envs`/`filter_rollback_envs`, which do enforce an explicit allowlist via `EnvironmentVariables#permit(deploy_variables)`: [2](#0-1) [3](#0-2) 

`machine_env` has no equivalent guard — it is read straight from the repo's `shipit.yml`: [4](#0-3) 

`DeploySpec::FileSystem` is instantiated against `@task.working_directory`, i.e., the actual checked-out working tree of the task's commit: [5](#0-4) 

For a `ReviewStack` provisioned under `allow_all`, that working tree is checked out from the PR/fork branch that the unprivileged attacker controls (`@stack.branch`, `@stack.repo_git_url`), so the `shipit.yml` read by `DeploySpec::FileSystem` is the attacker's own file. `ReviewStack#env` separately merges PR labels as env keys with a fixed `"true"` value, but that is not required — the attacker doesn't need labels at all; `machine.environment` in their own `shipit.yml` is a direct, value-controlled injection point: [6](#0-5) 

The merged env then flows into `Command#env` for every `install_dependencies`/`perform` step: [7](#0-6) 

`Command#unbundled_env` performs no key allowlisting when merging `@env`: [8](#0-7) 

and `Command#start` passes this env straight into `PTY.spawn`, with `parse_arguments` leaving a single-string step as one argument (so `PTY.spawn` shell-interprets it): [9](#0-8) [10](#0-9) 

Attack flow: attacker opens a PR from their fork with `shipit.yml` containing `machine: { environment: { GIT_ASKPASS: '/path/in/checkout/malicious.sh' } }`. Under `allow_all` provisioning, Shipit auto-provisions a `ReviewStack` for this PR without requiring a maintainer label/approval. When the task's shell-interpreted `deploy`/`dependencies` steps run (any step that shells out to `git`, e.g. a step invoking `git submodule update`, a private git-based dependency fetch, or any other git subcommand triggered from within the step), `GIT_ASKPASS` (or any other injected variable such as `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`, `PATH`) is present in that spawned process's environment and can redirect execution to attacker-controlled code checked into the same PR.

Existing guards do not stop this: `EnvironmentVariables#permit` only guards `deploy_variables`/`rollback_variables`, not `machine.environment`; there is no model validation on `machine.environment` keys in `DeploySpec`/`Stack`; and webhook signature verification only authenticates that the PR event genuinely originates from the linked repository — it does not restrict what an authenticated-but-unprivileged fork author can put inside their own `shipit.yml`.

### Impact Explanation
An unprivileged fork/PR author can inject arbitrary environment variable keys and values into every shell-interpreted step run for their own review-stack deploy on the Shipit host, without any maintainer approval, purely by setting `provision_behavior: allow_all` on the repository. This can be leveraged into RCE on the deploy host (matching the "Critical - RCE on the deploy host via Command/PTY.spawn" category) whenever any deploy/dependency step shells out to a tool influenced by environment (git, Ruby, bundler, etc.). It is repeatable: any PR against a repository configured with `allow_all` review stacks is affected, and the attacker can retry with any new PR/commit.

### Likelihood Explanation
Requires the target repository's Shipit configuration to enable `provision_behavior: allow_all` review stacks (a documented, non-default but supported feature) so unprivileged fork PRs are auto-provisioned. Given that precondition, the attacker cost is minimal: open a PR from a fork with a crafted `shipit.yml`. No secrets, sessions, or maintainer privileges are needed. The remaining variable is whether the repo's deploy/dependency steps invoke a tool sensitive to the injected variable (e.g., git) — this is common in real-world `shipit.yml` deploy pipelines but not guaranteed for every repository.

### Recommendation
Apply the same allowlist mechanism used for `deploy_variables`/`rollback_variables` to `machine.environment`: require operators to declare permitted machine-environment variable names (or hardcode a deny-list of dangerous variables like `GIT_ASKPASS`, `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`, `IFS`, `PATH`), and reject/strip disallowed keys in `DeploySpec#machine_env` before merging into `TaskCommands#env`. Additionally, consider not honoring `machine.environment` at all for review stacks provisioned under `allow_all` from forked/untrusted branches.

### Proof of Concept
minitest plan (no live GitHub):
1. Build a `Shipit::ReviewStack` with `provision_behavior` `allow_all` and a `pull_request` fixture.
2. Stub `DeploySpec::FileSystem#config('machine','environment')` (or write a fixture `shipit.yml`) to return `{'GIT_ASKPASS' => '/tmp/malicious.sh'}`.
3. Instantiate `Shipit::TaskCommands.new(task)` and call `#env`; assert:
   - `env['GIT_ASKPASS'] == '/tmp/malicious.sh'` (left side: attacker-supplied value; right side: value present in the env hash actually merged) — this equality should be false if a whitelist were applied, but currently holds true.
4. Build a `Shipit::Command.new('git fetch', env: task_commands.env, chdir: some_dir)` and assert `command.unbundled_env['GIT_ASKPASS'] == '/tmp/malicious.sh'`, proving the value reaches the hash passed to `PTY.spawn`.
5. Optionally stub `PTY.spawn` to capture the first positional arg (the env hash) and assert it contains the injected key, closing the loop from `shipit.yml` to the spawned process env.
