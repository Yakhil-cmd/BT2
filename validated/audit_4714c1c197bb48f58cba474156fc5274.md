### Title
Unauthenticated subscription to `stack.#{id}` push channels via `/events` mount bypasses engine's own authentication - ([File: config/routes.rb, app/models/shipit/stack.rb])

### Summary
The engine mounts `Pubsubstub::StreamAction.new` directly at `/events` as a Rack endpoint rather than as a controller action, so it never passes through `Shipit::Authentication#force_github_authentication` or any other before_action defined in this engine. Any caller who can reach `/events` can pass `channels[]=stack.<id>` and receive every event this engine publishes on that channel, with zero code in the engine checking that the caller is authorized for that stack.

### Finding Description
The broken binding: for every other read path in this engine, `current_user.authorized?` (checked in `app/controllers/concerns/shipit/authentication.rb:20-34`, included via `Shipit::ShipitController`) must be true before stack data is served. The equality that should hold is `stack_event_delivered_to(caller) == true only if authorized?(caller, stack) == true`. This is violated for `/events`.

`config/routes.rb:9` mounts `Pubsubstub::StreamAction.new` as a plain Rack app:
```
mount Pubsubstub::StreamAction.new, at: "/events", as: :events
```
This is not a subclass of `Shipit::ShipitController`, so it never receives `before_action :force_github_authentication` from `app/controllers/concerns/shipit/authentication.rb:8`, which is the sole authorization gate defined by this engine. There is no other controller, middleware, or concern in this engine's own code (`app/controllers/**`, `lib/shipit/engine.rb`) that wraps or inspects the `/events` path or the `channels[]` request parameter. `Pubsubstub::StreamAction` itself is a third-party gem with no knowledge of Shipit's `User#authorized?` / stack ownership model.

Meanwhile `app/models/shipit/stack.rb:561-567` publishes live stack-state events on a purely numeric, guessable/enumerable channel name:
```
def broadcast_update
  Pubsubstub.publish("stack.#{id}", { id:, updated_at: }.to_json, name: 'update')
end
```
This channel is the same one the engine's own views subscribe to for live status refresh, e.g. `app/views/shipit/stacks/show.html.erb:1`, `app/views/shipit/stacks/all_tasks.html.erb:1`, `app/views/shipit/merge_requests/merge_requests/index.html.erb:1` all call `subscribe events_path(channels: ["stack.#{@stack.id}"])`. Anyone who can guess or enumerate a numeric stack id can subscribe to that same channel directly against `/events` without ever hitting a Shipit controller, and therefore without ever hitting `force_github_authentication` or `User#authorized?`.

Existing guards do not apply: `verify_signature`/`GitHubApp#verify_webhook_signature` only guard `POST /webhooks`; `force_github_authentication` only runs on controllers that `include Shipit::Authentication`, and `Pubsubstub::StreamAction` is not one of them; there is no `stacks` scope or per-channel ACL check anywhere in this engine's code.

### Impact Explanation
An attacker with no Shipit session and no API token can open a long-lived SSE connection to `GET /events?channels[]=stack.<id>` for arbitrary/enumerated stack ids and receive `update` events fired whenever `Stack#broadcast_update` runs (deploy/task/lock state changes trigger stack timestamp updates broadcast on this channel). This is repeatable against every stack in the installation simply by iterating numeric ids, giving unauthenticated read of live deploy/task state across all tenants of a multi-team Shipit install. This matches the "High - unauthenticated read of stack state, task streams or deploy output" category.

### Likelihood Explanation
No special Shipit or GitHub configuration is required beyond the default engine mount, which is unconditional (`config/routes.rb:9` always mounts `/events`). The attacker only needs network access to the Shipit host and a stack id (trivially enumerable as a small integer, or observable from any public page/HTML source that already embeds `events_path(channels: [...])`). Cost is a single unauthenticated HTTP request; the exploit is fully repeatable and requires no secrets, sessions, or tokens.

### Recommendation
Do not mount `Pubsubstub::StreamAction` as a bare Rack app. Wrap it in a controller action (or a Rack middleware defined by this engine) that: (1) runs `force_github_authentication`/`current_user.authorized?` before establishing the SSE stream, and (2) validates that each requested channel name corresponds to a stack/repository the current user is authorized to view (e.g., parse `stack.<id>` and check `current_user.authorized?` plus stack visibility) before subscribing the client to it.

### Proof of Concept
```ruby
# test/controllers/events_authorization_test.rb
require "test_helper"

module Shipit
  class EventsAuthorizationTest < ActionDispatch::IntegrationTest
    test "subscribing to a stack channel via /events requires authorization" do
      stack = shipit_stacks(:shipit)

      # No session, no api client, no cookies set.
      get "/events", params: { channels: ["stack.#{stack.id}"] }, as: :json

      # Binding under test: an unauthenticated caller must NOT be able to
      # establish a subscription to a stack's push channel.
      assert_not_equal 200, response.status,
        "expected /events to reject unauthenticated channel subscription, " \
        "but Pubsubstub::StreamAction served it directly (no engine-level " \
        "force_github_authentication or per-channel authorization applied)"
    end

    test "no controller class backs the /events mount, so Shipit::Authentication cannot apply" do
      route = Shipit::Engine.routes.routes.find { |r| r.name == "events" }
      assert route.present?
      # Mounted Rack apps have no #controller/#action; Shipit::Authentication's
      # before_action can only ever run on ActionController subclasses.
      assert_nil route.defaults[:controller],
        "confirms /events is a raw Rack mount, bypassing Shipit::ShipitController's " \
        "before_action :force_github_authentication entirely"
    end
  end
end
```
Both assertions currently fail against the exploited behavior (the first request succeeds and streams events; the mount has no `:controller` default), confirming the engine performs no authentication or per-channel authorization of its own for `/events`.
