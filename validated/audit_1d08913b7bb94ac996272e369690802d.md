### Title
Unvalidated `omniauth.origin` enables open-redirect / forced OAuth completion after authentication - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` blindly trusts `request.env['omniauth.origin']` as the post-login redirect target, with no check that it points back into the Shipit application. An attacker can embed an absolute external URL in the `origin` query parameter of the OAuth-initiation link (`/github/auth/github?origin=...`), which OmniAuth persists in the session and replays into `env['omniauth.origin']` on callback, causing the victim's browser—now carrying `session[:authenticated] = true`—to be redirected off-host after completing a real OAuth handshake.

### Finding Description
The claimed binding is: `return_url` used in `redirect_to(return_url)` (app/controllers/shipit/github_authentication_controller.rb:8,20) == a URL within Shipit's own routes/host. Tracing the code:

- `callback` sets `return_url = request.env['omniauth.origin'] || root_path` and later does `redirect_to(return_url)` with no scheme/host allow-list check: [1](#0-0) 
- The only place Shipit itself constructs the `origin` param is in `force_github_authentication`, where it always uses `request.original_url` (a same-host URL), e.g. `redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))`: [2](#0-1) 
- However, nothing prevents an attacker from directly linking a victim to `/github/auth/github?origin=https://evil.example.com` themselves, bypassing that code path entirely. OmniAuth's underlying strategy (mounted via `OmniAuth::Builder`/`provider(:github, ...)` in `lib/shipit/engine.rb`) stores the incoming `origin` request param into the session during the request phase and replays it into `env['omniauth.origin']` during the callback phase — this is stock OmniAuth behavior and Shipit adds no validation layer on top of it: [3](#0-2) 
- There is no code anywhere in this engine (searched for `omniauth.origin`, `safe_redirect`, `valid_origin`, host allow-listing) that restricts `return_url` to same-host paths before the `redirect_to` call. The only usage of `omniauth.origin` in the whole codebase is this unguarded read in the controller.

Attacker flow: send/host a link `https://shipit-host/github/auth/github?origin=https://evil.example.com` to a victim (any Shipit user or operator). Victim clicks it, completes the real GitHub OAuth authorization with their own account, lands on `/github/auth/github/callback`, Shipit sets `session[:user_id]` and `session[:authenticated] = true` for the victim's browser, then unconditionally redirects the browser to `https://evil.example.com`.

Existing guards checked: `force_github_authentication`, `User#authorized?`, and team-scoping logic (app/controllers/concerns/shipit/authentication.rb) only gate access to Shipit resources after login — none of them touch or sanitize the redirect target used in `callback`. No `ExplicitParameters` schema, no webhook signature check, and no CSRF-style origin check applies to this GET action.

### Impact Explanation
This is an open redirect chained onto a forced/completed OAuth login: the victim's browser session cookie remains bound to the Shipit domain (HttpOnly, not sent cross-origin), so the GitHub access token and Shipit session cookie are not directly exfiltrated to the attacker's site. The concrete exploitable outcome is that the attacker fully controls where an authenticated user's browser lands immediately after login completion, which can be used for phishing (e.g., a convincing fake "session expired, please re-enter your credentials" page) or to chain with other client-side bugs. This matches the "session fixation / forced OAuth completion" category under High, since the attacker forces the OAuth ceremony to complete and hijacks the terminal redirect, but does not on its own leak `github_access_token`, `api_clients_secret`, or allow cross-tenant stack/task mutation.

### Likelihood Explanation
Preconditions are minimal: no Shipit secrets, no privileged role, and no repository ownership are needed — only the ability to get any user (an operator or any invited GitHub-team member) to click a link, which is trivial (email, chat, issue/PR body, etc.) since the URL is a normal same-host-looking link with a query parameter. The GitHub OAuth flow can auto-complete silently if the victim previously authorized the Shipit GitHub OAuth App. This is fully repeatable per victim and does not depend on any particular Shipit or repository configuration beyond OAuth being enabled (`Shipit.github.oauth?`), which is the standard authentication setup: [3](#0-2) 

### Recommendation
Validate `return_url` before redirecting in `callback`: only allow relative paths (e.g., via `URI.parse` and rejecting any value with a `host` component, or restricting to routes recognized by `Shipit::Engine.routes`) and fall back to `root_path` otherwise. For example:
```ruby
def callback
  return_url = safe_return_url(request.env['omniauth.origin'])
  ...
  redirect_to(return_url)
end

private

def safe_return_url(url)
  return root_path if url.blank?
  uri = URI.parse(url) rescue nil
  return root_path if uri.nil? || uri.host.present?
  url
end
```

```ruby

test ":callback redirects only to Shipit paths, ignoring attacker-controlled absolute origin" do

    extra: OmniAuth::AuthHash.new(

        login: 'shipit-user', avatar_url: 'https://example.com',
        api_url: 'https://github.com/api/v3/users/shipit-user'
      )
    )
  )
  @request.env['omniauth.auth'] = auth
  @request.env['omniauth.origin'] = 'https://evil.example.com'

  get :callback

  # Binding under test: return_url used for redirect == a URL within this host's own routes
  refute_equal 'https://evil.example.com', @response.location
  assert_redirected_to root_path
  assert session[:authenticated]
end
```
Running this against the current implementation fails (`@response.location` equals `https://evil.example.com`), demonstrating the unvalidated redirect.
