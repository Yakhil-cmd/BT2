### Title
Cross-org membership webhook allows adding arbitrary users to another organization's privileged `Team` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#repository_owner` falls back to `params.dig('organization', 'login')` to select which `Shipit.github_teams`-configured `GitHubApp` verifies the webhook signature [1](#0-0) , but `MembershipHandler#find_or_create_team!` looks up the team purely by `params.team.id` (the GitHub team's `github_id`), never checking that this team belongs to the organization whose signature was actually verified [2](#0-1) . This lets an attacker who controls an unsecured (no `webhook_secret`) GitHub organization forge a `membership` event that mutates a `Team` belonging to a different, secured organization, provided that team already exists in Shipit's database (e.g. because it is one of `Shipit.github_teams`).

### Finding Description
The binding that should hold is: `verified_organization (repository_owner used in verify_signature) == organization owning params.team.id`. This binding is never checked.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner` via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and looks up the corresponding `GitHubApp` with `Shipit.github(organization: repository_owner)` to verify `X-Hub-Signature` [3](#0-2) .
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization has no `webhook_secret` configured [4](#0-3) .
3. `MembershipHandler` requires `organization.login`, `team.id`, `team.name`, `team.slug`, `team.url`, and `member.login`, matching real GitHub payload shape (no `repository` key needed) [5](#0-4) .
4. `find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id)`; if a `Team` row with that `github_id` already exists (its `organization` column set from a previous, legitimate sync — e.g. a `Shipit.github_teams` entry created via `Team.find_or_create_by_handle` in `lib/shipit.rb:257`), the block is skipped entirely and the existing row is simply returned — `params.organization.login` is never compared to `team.organization` [2](#0-1) .
5. `process` then does `team.add_member(member)`, adding an attacker-chosen (or attacker-created) `User` to that team's `memberships` [6](#0-5) .

Exploit flow: attacker owns/controls org A (configured in `secrets.github` with no `webhook_secret`). They POST to `/webhooks` with `X-Github-Event: membership`, body `{"action":"added","team":{"id":<org B's known team github_id>,"name":...,"slug":...,"url":...},"organization":{"login":"org-a"},"member":{"login":"attacker-or-victim-login"}}`, no `repository` key. `repository_owner` resolves to `"org-a"`, whose `verify_webhook_signature` trivially returns `true` (no secret). The handler then finds org B's pre-existing `Team` by `github_id` and appends the specified member.

This bypasses the intended guard because `verify_signature` establishes provenance only for the *organization named in the payload*, not for the *team being mutated*; nothing downstream re-validates that the verified organization actually owns the target team.

### Impact Explanation
If the mutated team is one of `Shipit.github_teams` (used by `User#authorized?` via `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) ), this becomes an authorization escalation: an attacker can grant an arbitrary GitHub-registered login membership in a Shipit-privileged team, without ever needing that org's `webhook_secret` or any GitHub permission on org B. This satisfies "escalation into `Shipit.github_teams` authorization" (High), and if that authorization gates deploy/rollback/merge actions in the host app, this becomes a path to unauthorized deploys (Critical territory). The attack is repeatable against any pre-existing `Team` row whose `github_id` the attacker can guess or observe (GitHub team IDs are enumerable/visible via the GitHub API for public teams or teams the attacker can otherwise observe), and is not limited to a single team — any team already present in Shipit's DB is vulnerable as long as at least one org in `secrets.github` lacks a `webhook_secret`.

### Likelihood Explanation
Preconditions: (1) at least two orgs configured under `secrets.github`, one without `webhook_secret` (or with a secret the attacker controls, since they own that org and can produce a valid signature themselves); (2) the target `Team` row already exists in Shipit's DB with a known `github_id` (typical for `Shipit.github_teams`, which are eagerly created via `Team.find_or_create_by_handle`). The attacker only needs to control/own the unsecured org (fully within the stated attacker capabilities — "any internet user who can send HTTP requests ... including POST /webhooks") and know/guess the target team's `github_id`. No Shipit credentials, session, or GitHub secret for org B is needed. This is a low-cost, repeatable, single-HTTP-request attack.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that `params.organization.login` matches the existing team's `organization` column when the team already exists (raise/reject on mismatch rather than silently accepting), and/or have `WebhooksController#verify_signature` reject membership payloads whose `organization.login` doesn't correspond to the team's actual organization before dispatching to handlers.

### Proof of Concept
```ruby
test ":membership from an unsecured org cannot mutate another org's team" do
  # org "org-a" has no webhook_secret; org "org-b" is secured and owns team github_id 999
  secured_team = Team.create!(organization: "org-b", slug: "secured", name: "Secured", github_id: 999, api_url: "https://x")

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate org-a's trivial verification
  @request.headers['X-Github-Event'] = 'membership'

  payload = {
    action: 'added',
    team: { id: 999, name: secured_team.name, slug: secured_team.slug, url: secured_team.api_url },
    organization: { login: 'org-a' },
    member: { login: 'mallory' }
  }.to_json

  assert_no_difference -> { Team.count } do
    assert_difference -> { secured_team.reload.members.count }, 1 do
      post :create, body: payload, as: :json
      assert_response :ok
    end
  end

  # BROKEN BINDING: verified org ("org-a") != team.organization ("org-b"), yet mutation succeeded
  assert_not_equal 'org-a', secured_team.reload.organization
end
```
This demonstrates that a membership row is created under org B's team despite the request only being authenticated for org A, confirming `find_or_create_team!` never checks `params.organization.login` against the existing team's `organization` column.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
