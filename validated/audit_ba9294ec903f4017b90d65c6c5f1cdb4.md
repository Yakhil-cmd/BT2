### Title
Extension `--pin` verification silently bypassed by empty-body response from attacker-controlled host - (File: pkg/cmd/extension/http.go, pkg/cmd/extension/manager.go)

### Summary
`gh extension install <url> --pin <ref>` is designed to install and lock an extension to a specific commit. The commit is resolved via `fetchCommitSHA`, which trusts any HTTP 200 response body verbatim as the resolved SHA, including an **empty** body. `installGit` then treats an empty `commitSHA` exactly the same as "no pin requested" and skips the checkout step entirely, silently leaving the extension at whatever `git clone` put on disk (the mutable default branch HEAD) instead of the user-specified pinned commit. This mirrors the reported Uniswap V3 class of bug: a zero/empty value that was only ever expected in one benign state (no liquidity / no pin requested) is indistinguishable from an attacker-influenced degenerate response, and the code silently takes the "no-op" path instead of failing safe.

### Finding Description
`gh extension install` supports installing from an arbitrary host, not just github.com:
```
$ gh extension install https://my.ghes.com/owner/gh-extension
``` [1](#0-0) 

When a user supplies `--pin <ref>`, `Manager.installGit` resolves the ref to a full commit SHA via `fetchCommitSHA`, using the target host's REST API: [2](#0-1) 

`fetchCommitSHA` treats any status code ≤ 299 as success and returns the raw response body as the SHA, with **no validation that the body is non-empty or looks like a SHA**:
```go
resp, err := httpClient.Do(req)
...
if resp.StatusCode == 422 {
    return "", commitNotFoundErr
}
if resp.StatusCode > 299 {
    return "", api.HandleHTTPError(resp)
}
body, err := io.ReadAll(resp.Body)
...
return string(body), nil
``` [3](#0-2) 

`installGit` then uses this untyped result as a control-flow sentinel identical to the "user did not request a pin" case:
```go
var commitSHA string
if target != "" {
    commitSHA, err = fetchCommitSHA(m.client, repo, target)
    if err != nil {
        return err
    }
}
...
_, err := m.gitClient.Clone(cloneURL, []string{targetDir})
if err != nil {
    return err
}
if commitSHA == "" {
    return nil
}
scopedClient := m.gitClient.ForRepo(targetDir)
err = scopedClient.CheckoutBranch(commitSHA)
``` [4](#0-3) 

Because `commitSHA == ""` is the same sentinel used for "no pin was requested" (`target == ""`), a host that returns HTTP 200 with an empty body for the `GET /repos/{owner}/{repo}/commits/{ref}` request (Accept: `application/vnd.github.v3.sha`) causes `installGit` to silently skip `CheckoutBranch` and the creation of the `.pin-<sha>` marker file, leaving the extension checked out at whatever commit `git clone` (the target's default branch HEAD) resolved to — not the commit the user pinned to.

The command layer does not detect this and unconditionally reports success:
```go
if io.IsStdoutTTY() {
    fmt.Fprintf(io.Out, "%s Installed extension %s\n", cs.SuccessIcon(), args[0])
    if pinFlag != "" {
        fmt.Fprintf(io.Out, "%s Pinned extension at %s\n", cs.Cyan(pinFlag))
    }
}
``` [5](#0-4) 

### Impact Explanation
An attacker who controls the target GHES/self-hosted host referenced in `gh extension install <url> --pin <ref>` (an explicitly supported, attacker-published/attacker-controlled endpoint per the documented feature) can make the "commit resolution" endpoint return `200 OK` with an empty body. The CLI then:
- Skips checking out the pinned commit,
- Skips writing the `.pin-<sha>` marker used to signal a pinned install,
- Reports success and even prints "Pinned extension at `<ref>`" to the user,

while the extension executable that ends up on disk and gets executed on every future `gh <ext>` invocation is whatever the attacker put on the mutable default branch — which can differ arbitrarily (and maliciously) from the commit the user believed they pinned to. This is a verification bypass leading to arbitrary local code execution under a false assurance of pinning/reproducibility, which is exactly the kind of supply-chain protection the `--pin` flag exists to prevent.

### Likelihood Explanation
The install path (`gh extension install <arbitrary-url> --pin <ref>`) is a documented, ordinary CLI usage pattern, and the vulnerable branch is reached automatically any time the ref-resolution response happens to be empty — no unusual client configuration or race condition is required. The only precondition is that the attacker controls (or can MITM as an actual endpoint owner, e.g. their own GHES instance) the HTTP response for the commit-lookup call, which is inherent to installing extensions from third-party/self-hosted hosts, a scenario the tool explicitly advertises support for.

### Recommendation
In `fetchCommitSHA` (pkg/cmd/extension/http.go), validate that the returned body is non-empty and matches a plausible SHA format (e.g., hex string of expected length) before returning it as success; treat an empty or malformed body as an error, not a silent success. In `installGit` (pkg/cmd/extension/manager.go), do not conflate "commitSHA == \"\" because no pin was requested" with "commitSHA == \"\" because a lookup response was invalid" — use a separate boolean (e.g., `pinRequested bool`) to gate the checkout/pin-file logic instead of relying on the string's zero value.

### Proof of Concept
1. Stand up a mock GHES-like server implementing the extension API endpoints used by `gh extension install`.
2. For `GET /api/v3/repos/owner/gh-evil-ext/commits/v1.0.0` with header `Accept: application/vnd.github.v3.sha`, respond with `200 OK` and an empty body (instead of a 40/64-hex-char SHA).
3. Push a benign-looking script to the default branch of `owner/gh-evil-ext` at pin time, but ensure a malicious payload is what will land there after users install.
4. Run:
   ```
   gh extension install https://my.ghes.com/owner/gh-evil-ext --pin v1.0.0
   ```
5. Observe: the command succeeds, prints "Installed extension ..." and "Pinned extension at v1.0.0", but no `.pin-<sha>` file is created in the extension directory and `CheckoutBranch` is never invoked — the extension is left at the repository's default branch HEAD rather than the `v1.0.0` commit, matching `installGit`'s `if commitSHA == "" { return nil }` early-return at [6](#0-5) .
6. Subsequently updating the default branch on the attacker's host changes the code executed by `gh evil-ext ...` on the victim's machine despite the victim believing the install was pinned.

**Note:** I was not able to run this scenario end-to-end (no execution environment available), so this PoC is derived purely from static code review of `fetchCommitSHA` and `installGit`; I recommend validating it with a live test against a controlled mock server before relying on it as confirmed-exploitable.

// fetchCommitSHA finds full commit SHA from a target ref in a repo
func fetchCommitSHA(httpClient *http.Client, baseRepo ghrepo.Interface, targetRef string) (string, error) {
	url, err := safeurl.JoinPathWithHostPrefix(ghinstance.RESTPrefix(baseRepo.RepoHost()), "repos", baseRepo.RepoOwner(), baseRepo.RepoName(), "commits", targetRef)
	if err != nil {
		return "", err
	}
	req, err := http.NewRequest("GET", url.String(), nil)
	if err != nil {
		return "", err
	}

	req.Header.Set("Accept", "application/vnd.github.v3.sha")
	// TODO(api-client-rollout)
	// This has been deferred from moving to api.Client due to its custom Accept header and bare SHA response body.
	resp, err := httpClient.Do(req)
	if err != nil {
		return "", err
	}

	defer resp.Body.Close()
	if resp.StatusCode == 422 {
		return "", commitNotFoundErr
	}
	if resp.StatusCode > 299 {
		return "", api.HandleHTTPError(resp)
	}

	body, err := io.ReadAll(resp.Body)
	if err != nil {
		return "", err
	}

	return string(body), nil
}
