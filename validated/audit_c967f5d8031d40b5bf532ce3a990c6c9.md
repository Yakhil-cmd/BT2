### Title
Webhook signature verification keys on `repository.owner.login` while handlers act on `repository.full_name`, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports hosting multiple GitHub organizations on a single instance, each with its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which organization's secret to verify the HMAC signature against using a field pulled straight out of the untrusted JSON body — `repository.owner.login` (or `organization.login`) — rather than any value tied to which secret produced the signature [2](#0-1) . Once that check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs handlers over the *same* raw params, which resolve the affected repository/stack using a different field of the same payload (`repository.full_name`).

### Finding Description
`Shipit.github(organization:)` looks up per-organization config (including `webhook_secret`) from `secrets.github`, keyed by organization name [3](#0-2) . `WebhooksController#verify_signature` derives that organization key from the request body itself:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

and verifies:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [5](#0-4) 

`verify_webhook_signature` is a plain HMAC-SHA1 comparison over the raw body using that org's `webhook_secret` [6](#0-5) . This proves only that *whoever* crafted the request knew the secret belonging to the organization named in `repository.owner.login` — it says nothing about which repository the rest of the payload claims to be operating on. A JSON body is not required to be internally consistent (GitHub would never emit such a payload, but Shipit's endpoint does not check that), so an attacker who legitimately controls an org onboarded to the same Shipit instance (and therefore knows/owns that org's `webhook_secret`, e.g. an org admin) can build:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  ...
}
```
sign it with `attacker-org`'s `webhook_secret`, and send it. `verify_signature` computes `repository_owner == "attacker-org"`, fetches `attacker-org`'s secret, and the HMAC matches — verification passes. The event handlers, however, dispatch based on `repository.full_name`/repository identity fields elsewhere in the same payload to find or create the `Stack`/`Repository` object to act on (consistent with `Repository.from_github_repo_name` usage elsewhere, e.g. [7](#0-6) , and the `full_name` references found in `app/models/shipit/webhooks/handlers/handler.rb` and the `pull_request/*` handlers).

The binding that should hold is: **organization that authenticated (via `webhook_secret`) == repository that is written (target of the handler's side effects)**. It is broken because these are two independently attacker-controlled fields of the same unsigned-structure JSON body, and only one of them is checked against the key used for verification.

### Impact Explanation
Depending on which webhook event/handler is exploited, this allows an attacker who only controls their own onboarded organization to inject forged, "verified" events against a victim organization's stacks hosted on the same Shipit instance:
- Forged `status` events can mark arbitrary commits on a victim's stack as CI-`success`, feeding directly into `Commit#deployable?`/`required_statuses` gating used by both the deploy API (`require_ci` check in `app/controllers/shipit/api/deploys_controller.rb:22`) and the merge queue (`MergeRequest::StatusChecker`, `deploy_spec.rb:194-196`), enabling an **unauthorized deploy or merge** on a repository the attacker does not own.
- Forged `push` events can trigger `GithubSyncJob` against a victim stack.
- Forged `pull_request`/`check_suite`/`membership` events can manipulate merge-queue state or team/user membership tied to a victim's repository.

This satisfies the Critical/High bar of "unauthorized deploy, rollback or merge" via a credential/organization boundary that should isolate tenants from one another.

### Likelihood Explanation
Exploitation requires the attacker to control (or be an admin of) at least one GitHub organization already configured on the shared Shipit instance — a routine, low-privilege condition for any multi-tenant Shipit deployment (the documented setup explicitly supports several orgs, each with independent `webhook_secret`, see `config/secrets.development.shopify.yml`). No access to the victim org, no GitHub App private key, and no Shipit session/API token are required — only the ability to send an HTTP POST to the public `/webhooks` endpoint with a payload signed by a secret the attacker legitimately possesses for their own org.

### Recommendation
In `WebhooksController#verify_signature`/`#repository_owner`, do not let handler-visible identity fields (`repository.full_name`, repository/stack resolution) diverge from the field used to select the verification key. Concretely: after selecting `repository_owner` for signature verification, re-validate that any repository referenced later in the payload (`repository.full_name`, `organization.login`, etc.) is actually owned by that same, verified organization before dispatching to handlers, or key the lookup exclusively off a value that cannot be forged independently of the signing secret (e.g. resolve the App installation from `X-GitHub-Hook-Installation-Target-ID`/GitHub App metadata rather than a client-supplied JSON field).

### Proof of Concept
1. Shipit instance is configured with two organizations, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (as documented in `config/secrets.development.shopify.yml`).
2. Attacker is a legitimate admin of `attacker-org`'s GitHub App/webhook config and therefore knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `status` (or `push`) webhook JSON body where `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/victim-repo"` and `sha`/`state` point at a commit in `victim-org`'s Shipit stack.
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` computes `repository_owner == "attacker-org"`, fetches `attacker-org`'s secret, HMAC matches, request is accepted.
6. The `status` handler processes the event using `repository.full_name` (`victim-org/victim-repo`) to locate and update the commit status on `victim-org`'s stack, letting the attacker mark arbitrary commits there as CI-passing without ever authenticating to `victim-org`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
