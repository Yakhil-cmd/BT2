### Title
Cross-repository forged commit status enables unauthorized continuous-delivery deploy trigger on `Shipit::ReviewStack` via unscoped `Commit.where(sha:)` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook with a global, cross-tenant `Commit.where(sha: params.sha)` query that is never scoped to the repository that authenticated the webhook. Because `Shipit::ReviewStack` commits live in the same `commits` table and are gated for deploy purposes only by `Commit#deployable?` (which checks `success?`/`blocked?`/`locked?`, not repository identity), an attacker who owns an unrelated, legitimately-webhook-registered repository can create a real GitHub commit with the same SHA as a commit tracked by someone else's `ReviewStack` (trivial via forking, since git SHAs are content-addressed) and post a genuine, correctly-signed status event for it, forging a `success` status onto the victim `ReviewStack`'s commit and enabling an unauthorized continuous-delivery deploy of that review environment.

### Finding Description
Binding claimed and broken: `commit.stack.repository.full_name == webhook.repository_owner/full_name` (the repository whose commit is mutated must equal the repository that authenticated the webhook). This is violated because the lookup ignores the authenticated repository entirely.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only verifies the HMAC using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the attacker-controlled JSON body (`params.dig('repository','owner','login')`, line 61). This proves the request came from *some* org whose webhook secret matches the payload's own `repository.owner.login` (i.e., the attacker's own org/repo) — it proves nothing about the `sha` field's origin or about which `Stack`/`Commit` the event is allowed to touch.
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — an unscoped query across **all** stacks/repositories in the install, including `Shipit::ReviewStack` records (which are just `Stack` subtypes sharing the same `commits` table).
3. Because git SHAs are content hashes, an attacker can fork (or otherwise obtain) the exact same commit object that exists in the target repository/PR branch tracked by a `ReviewStack`, then set a real commit status on that identical SHA within their own, attacker-owned repository. GitHub computes and signs this webhook legitimately for the attacker's own org — `verify_signature` passes.
4. `create_status_from_github!` creates a `Shipit::Status` row against the victim commit; `Status`'s `after_commit :schedule_continuous_delivery` (`app/models/shipit/status.rb:19,42-44`) calls `commit.schedule_continuous_delivery`, which (per `Commit`'s own `after_commit :schedule_continuous_delivery, on: :create` wiring, `app/models/shipit/commit.rb:24-25`) enqueues `Shipit::ContinuousDeliveryJob`.
5. `ContinuousDeliveryJob#perform` (`app/jobs/shipit/continuous_delivery_job.rb:10-21`) checks `stack.continuous_deployment?`, schedule windows, and `stack.occupied?`, then calls `stack.trigger_continuous_delivery` — which ultimately relies on `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`: `!locked? && (stack.ignore_ci? || (success? && !blocked?))`) being satisfied. The forged `success` status directly flips this predicate true with zero regard for which repository actually authenticated the event.

Existing guards fail to stop this: `verify_signature` authenticates only the requester's own org, not the target of the `sha`; `drop_unhandled_event` only filters unhandled event types; `ExplicitParameters` (`StatusHandler.params`) only validates types/presence of `sha`/`state`, not ownership; there is no `require_permission!`/`stacks` scope check anywhere in the webhook path since webhooks are inherently cross-account by design — but the missing piece is scoping the `Commit` lookup to the stack(s) belonging to the authenticated repository.

Caveat on provisioning vs. deploying: `Shipit::ReviewStack` provisioning (the `provision`/`provision_success` state machine transitions, `app/models/shipit/review_stack.rb:45-82`) is only enqueued from PR lifecycle webhook handlers (opened/labeled/synchronize/reopened via `ReviewStackAdapter`, `app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb`), not from `Commit#deployable?` or status events. So this bug does **not** let an attacker provision a brand-new environment for a PR that was never opened. It **does** let an attacker trigger an unauthorized `Deploy`/continuous-delivery run against an **already-provisioned** `ReviewStack` (i.e., "update a review environment"), because `ContinuousDeliveryJob` only checks `continuous_deployment?`, schedule, `occupied?`, and `Commit#deployable?` — none of which verify the status's authenticating repository matches the review stack's repository.

### Impact Explanation
An attacker who controls any repository with a legitimately configured Shipit webhook can, for any `ReviewStack` (or ordinary `Stack`) elsewhere in the same Shipit install whose tracked commit SHA the attacker can reproduce (via fork/clone, since SHAs are content-derived), forge a passing CI status and cause `Shipit::ContinuousDeliveryJob` to fire an unauthorized deploy/rollback-equivalent task against that stack/review-environment — a cross-tenant "payload for one repository mutating another's stack/commit/task" and triggering an unauthorized deploy, which matches the Critical severity bucket. This is repeatable against any commit SHA the attacker can reproduce and works identically whether the target is a normal `Stack` or a `ReviewStack`.

### Likelihood Explanation
Preconditions: (1) attacker owns/controls a repository already integrated with the Shipit instance (so a webhook signature will validate for their own org — a normal, unprivileged onboarding action, not a secret leak); (2) target `ReviewStack` has `continuous_deployment` enabled and is not currently occupied/locked; (3) attacker can obtain a commit object with the exact same SHA as one tracked in the victim stack (straightforward via forking a public upstream repo, since the PR branch commit is by definition public). No Shipit secrets, sessions, or team membership are required. Cost is low and the technique is repeatable across any number of target stacks sharing SHAs the attacker can reproduce.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run/other webhook handlers relying on bare `sha` lookups) to only the `Commit`s belonging to `Stack`s whose `repository.full_name` matches the authenticated `params.dig('repository','full_name')` from the verified webhook payload, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { full_name: params.repository.full_name })`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_review_stack_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerReviewStackTest < ActiveSupport::TestCase
        test "cross-repo status forges success on an unrelated ReviewStack's commit" do
          victim_stack = shipit_stacks(:review_stack) # belongs to repo "shopify/shipit-engine" (fixture)
          victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, message: "pr head")

          attacker_repo_full_name = "attacker/unrelated-fork"
          refute_equal victim_stack.repository.full_name, attacker_repo_full_name

          payload = {
            sha: victim_commit.sha,
            state: "success",
            context: "ci",
            repository: { full_name: attacker_repo_full_name, owner: { login: "attacker" } }
          }

          assert_difference -> { victim_commit.statuses.count }, 1 do
            StatusHandler.new(ExplicitParameters::Params.new(payload)).process
          end

          assert_predicate victim_commit.reload, :deployable?
          assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack]) do
            victim_commit.schedule_continuous_delivery
          end
        end
      end
    end
  end
end
```
Both sides of the binding diverge: `victim_stack.repository.full_name` ("shopify/shipit-engine") != the webhook's authenticated `attacker_repo_full_name` ("attacker/unrelated-fork"), yet the status is written and continuous delivery is scheduled for `victim_stack`.
