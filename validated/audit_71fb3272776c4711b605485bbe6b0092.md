### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while event handlers act on the unverified `repository.full_name` field, allowing cross-repository/cross-organization forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using the payload field `repository.owner.login` (or `organization.login`), but every event handler (`Handler#repository_name`, used by `PushHandler`, the `PullRequest::*` handlers, etc.) resolves the *target* stack/repository using a completely different, unverified payload field: `repository.full_name`. Because HMAC verification never binds these two fields together, a valid signature computed with one organization's `webhook_secret` can carry a JSON body whose `repository.full_name` points at a totally different, unrelated repository/stack.

### Finding Description
`verify_signature` computes the org to validate against purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the configured `GitHubApp` (and its `webhook_secret`) purely from `repository.owner.login`/`organization.login` in the untrusted body, and the resulting `verify_webhook_signature` call only checks that the raw body's HMAC matches that org's secret: [3](#0-2) 

Meanwhile, the actual work performed by handlers is scoped by a *different* field, `repository.full_name`, read from the same unauthenticated JSON body: [4](#0-3) 

`PushHandler` uses `stacks` (derived from `repository_name`, i.e. `repository.full_name`) to select which stacks to sync: [5](#0-4) 

The PR handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`) likewise resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` independently of the organization used for signature verification: [6](#0-5) 

Since Shipit explicitly supports multiple GitHub Apps/organizations sharing one Shipit instance (each with its own `webhook_secret`), as documented: [7](#0-6) 

the equality the code relies on is: **organization that authenticated the signature == organization that owns the repository the handler acts on**. This equality is never enforced. An attacker who is an authorized member/owner of *any* organization configured in this Shipit instance's `github:` section (attacker-org) knows or can derive attacker-org's `webhook_secret` (they configured/administer that GitHub App installation) and can freely craft the JSON payload delivered to `WebhooksController#create`. They set `repository.owner.login` (or `organization.login`) to `attacker-org` — so `verify_signature` fetches attacker-org's `GitHubApp` and successfully validates the HMAC (computed by the attacker with their own known secret) — while setting `repository.full_name` to `victim-org/victim-repo`, an entirely different repository/stack tracked by the same Shipit instance but belonging to another organization.

### Impact Explanation
Because handler routing trusts `repository.full_name` independently of the verified organization, this breaks the "organization that authenticated versus the repository that is written" binding explicitly called out as in-scope. Concretely:
- Via `PushHandler`, the attacker can trigger `stack.sync_github(expected_head_sha:)` for any tracked stack whose `full_name` they can guess/know, forcing an out-of-band GitHub sync of a repository/branch they do not own.
- Via the PR handlers (`OpenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ClosedHandler`), the attacker can create, archive/unarchive, or otherwise manipulate review stacks for a victim repository's pull requests by forging `pull_request`/`repository` fields, since none of these depend on the authenticating organization matching the acted-upon repository.

This is a cross-repository/cross-organization write performed by an attacker who has no legitimate relationship to the victim organization, satisfying the "cross-repository writes" Critical impact criterion, since it lets an unprivileged-relative-to-the-victim actor (privileged only within their own, separately configured org) drive state changes (stack sync, review-stack archive/create) on a repository/organization they don't control.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured with more than one GitHub organization/App (a documented, supported configuration), and the attacker must control (or have been granted webhook-secret knowledge for) one of those configured organizations — not the victim's. This is a realistic scenario for shared, multi-tenant Shipit deployments serving several orgs, and requires no access to the victim's secrets, tokens, or GitHub App at all — only knowledge of the victim's `repository.full_name`, which is typically public information (e.g., `github.com/victim-org/victim-repo`).

### Recommendation
Bind signature verification to the same repository/organization the handler will act upon: compute a single canonical organization/repository identity once, verify the signature against that organization's secret, and reject the payload if `repository.full_name`'s organization does not match the organization used to select the `webhook_secret` (i.e., cross-check `repository.owner.login` == owner segment of `repository.full_name` == the org whose secret validated the signature) before dispatching to any handler.

### Proof of Concept
1. Shipit instance is configured with two organizations in `config/secrets.yml`: `attacker-org` (attacker is an org owner/admin, knows `webhook_secret_A`) and `victim-org` (tracks stack `victim-org/victim-repo`), per the multi-org setup in `docs/setup.md`.
2. Attacker crafts a `push` payload body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, body)>` using their own known `webhook_secret_A`.
4. `POST /github/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: 'attacker-org')`, which succeeds and validates the signature against `webhook_secret_A` — passes (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `repository_name` from `repository.full_name` = `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's real stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), even though the signature only proved knowledge of `attacker-org`'s secret, not any relationship to `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
