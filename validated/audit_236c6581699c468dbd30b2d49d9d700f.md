### Title
Attacker-triggered `system_vote_count` for a numerical subject with no in-window votes crashes `countVotes` and halts MC stabilization - (File: main_chain.js)

### Summary
Any unprivileged unit poster can post a `system_vote_count` message for a numerical subject (`threshold_size`, `base_tps_fee`, `tps_interval`, or `tps_fee_multiplier`) as validated in [1](#0-0) . When that unit stabilizes, `countVotes()` is invoked unconditionally for the requested subject during `markMcIndexStable` processing [2](#0-1) . If the subject has never received any `system_vote`, or all its existing votes fall outside the computed `since_timestamp` window, the numerical branch computes `total_voted_balance` from an empty result set and reaches an unrecoverable `throw Error` deep inside stabilization logic, an uncaught exception that is not attacker-input-checked before being reachable.

### Finding Description
`countVotes(conn, mci, subject)` is triggered every time a stable unit carries a `system_vote_count` message; the subject is only checked to be one of the five known constants and is otherwise fully attacker-controlled [1](#0-0) . The counting itself runs as part of finishing the stabilization pass for the mci in `markMcIndexStable`: [2](#0-1) 

Inside `countVotes`, for the numerical subjects, the function queries `numerical_votes` joined with `voter_balances` restricted to `timestamp>=since_timestamp`: [3](#0-2) 

`since_timestamp` is derived by walking backward year by year until the accumulated voted balance clears a minimum share, or until it reaches `activation_timestamp` [4](#0-3) . If the subject in question has zero votes cast (a brand-new subject that nobody voted on, or one whose entire history is younger than one look-back cycle so that the balance requirement is never met and the loop exits at `activation_timestamp` with still nothing counted), `rows` from the numerical query is empty. `total_voted_balance` then evaluates to `0`, the accumulation loop over `rows` never executes, and `value` remains `undefined`. The code then executes:
```js
if (value === undefined)
    throw Error(`no median value for ` + subject);
```
This `throw` happens synchronously inside an `async` function invoked from the stabilization pipeline (`updateMainChain` → `advanceMcStability`/`markMcIndexStable` → `handleAATriggers`/`calcCommissions` → `countVotes`), with no surrounding try/catch that turns it into a soft validation failure. It is a process-level fatal error triggered purely by the presence of a single, otherwise perfectly valid `system_vote_count` unit that references a subject with an empty/insufficient vote history — directly analogous to the reported bug class where a "round" (here, a subject's voting window) can be forced into a state with zero effective entries, and the subsequent aggregation step (`% currentEntryIndex` in the original report, `median` computation here) cannot produce a result and blows up instead of degrading gracefully.

Note: an initial guard exists — `if (values.length === 0) return console.log(...)` — but that guard only checks whether *any* address has ever voted for the subject at all (`SELECT DISTINCT address FROM system_votes WHERE subject=?`), independent of the `since_timestamp` window used in the numerical branch. It is therefore possible to have `values.length > 0` (someone voted for the subject at some point) while the numerical `rows` result (restricted to `timestamp>=since_timestamp`) is empty, so the guard does not prevent reaching the `throw`.

### Impact Explanation
This is an unprivileged, single-unit-triggerable crash inside the core MC-stabilization code path. Because `countVotes` runs synchronously as part of stabilizing every node that processes the chain, an uncaught exception here brings down (or corrupts the state of) every full node that processes this mci — a network-wide inability to advance main-chain stability/confirm new units, matching the "network unable to confirm new units" acceptance criterion. Unlike the original YoloV2 report where the attacker needed to fill an entire round with fake participants, here a single crafted unit with a `system_vote_count` message for a fresh/rarely-voted numerical subject is sufficient, at minimal cost (a single unit fee), to reach the same class of unhandled "empty aggregate" fault.

### Likelihood Explanation
Reaching this requires only posting a normal unit containing a `system_vote_count` app-message referencing one of the whitelisted numerical subjects (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) after the `v4UpgradeMci`/devnet activation, and waiting for it to stabilize. No privileged role, special witness position, or large capital outlay is needed — any address able to post units can do this. The only precondition is that the chosen subject currently has no votes within the dynamically computed `since_timestamp` window, which is trivially satisfiable for a subject nobody has voted on recently (or immediately after the subject's voting is first activated, before enough balance-weighted votes accumulate).

### Recommendation
In the numerical branch of `countVotes`, treat an empty `rows` result (or `total_voted_balance === 0`) as "no votes to count yet" and skip updating `system_vars` for that subject instead of throwing, mirroring the existing `values.length === 0` early-return behavior:
```js
if (rows.length === 0 || total_voted_balance === 0) {
    console.log(`no votes within window for ${subject}, skipping vote count`);
    await conn.query(conn.dropTemporaryTable('voter_balances'));
    return;
}
```
This prevents an attacker-chosen `system_vote_count` unit for an under-voted subject from crashing the stabilization pipeline, while preserving the intended "apply the vote once enough weight is present" semantics.

### Proof of Concept
1. Attacker posts a valid unit with message `{app: "system_vote_count", payload: "tps_interval"}` (or any other numerical subject that currently has no votes, or only votes older than the computed lookback window) — this passes validation per [1](#0-0)  since only membership in the subject whitelist is checked.
2. The unit stabilizes; during `markMcIndexStable`, `voteCountSubjects` includes `"tps_interval"`, so `countVotes(conn, mci, "tps_interval")` is invoked [2](#0-1) .
3. Because no addresses voted for `tps_interval` within `[since_timestamp, mc_timestamp]`, the numerical-subject query returns `rows = []`, making `total_voted_balance = 0` and the median-selection loop never sets `value` [5](#0-4) .
4. `throw Error("no median value for tps_interval")` fires inside the stabilization call chain, crashing/aborting the node's processing of this mci for every full node that reaches this stabilization step — halting further main-chain confirmation until the code is patched or the unit is otherwise excluded.
