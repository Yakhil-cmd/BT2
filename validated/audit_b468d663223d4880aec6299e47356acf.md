### Title
Same-Transaction Spot-Balance Oracle Manipulation via unbuffered `balance[]` selector in atomic AA trigger cascades - (File: formula/evaluation.js, aa_composer.js)

### Summary
The Makina exploit is a textbook "unchecked synchronous deposit" oracle manipulation: a permissionless function reads a DEX pool's *current, unfinalized* balance state and immediately uses it as the pricing basis within the same atomic execution, with no TWAP or delay. Obyte's Autonomous Agent (AA) engine has the equivalent primitive: the `balance[address][asset]` oscript selector returns the *live, unbuffered* balance of any address — including another AA — and AA trigger cascades (a primary trigger plus all its chained secondary triggers) execute and commit as a single atomic unit, exactly like a single EVM transaction. AA authors are explicitly encouraged by ocore's own bundled sample templates to use this raw balance as an AMM/threshold pricing input, reproducing the exact anti-pattern that drained Makina.

### Finding Description
The `balance` case in the formula evaluator resolves to `readBalance()`, which returns whatever is currently in `objValidationState.assocBalances[param_address][bal_asset]` — a live, in-memory balance snapshot maintained for the whole trigger cascade — falling back to the DB `aa_balances` table only if absent from memory. There is no time-weighting, no minimum block/MCI delay, and no restriction that `param_address` be `this_address`; any AA can query any other AA's balance at the current point of the atomic response chain. [1](#0-0) 

This selector is validated as legal specifically for AA context (`if (!bAA) return cb(op + ' in non-AA')`), confirming it is a first-class, sanctioned AA primitive rather than an edge case. [2](#0-1) 

Crucially, ocore's own bundled example AAs instruct developers to use this exact primitive as a pricing/threshold oracle with zero delay: a constant-product market maker computes exchange rates directly from `balance[$asset]`/`balance[base]`, [3](#0-2) 
and a fundraising proxy AA gauges a *different* AA's ("the game") progress toward a threshold by reading `balance[$destination_aa][base]` directly, with no time buffer. [4](#0-3) 

The atomicity guarantee that makes this dangerous comes from `aa_composer.js`: a primary trigger's chain of secondary AA-to-AA triggers is processed synchronously in one call graph (`handleSecondaryTriggers`), and if *any* AA anywhere in that chain bounces, the **entire cascade is rolled back** to the savepoint taken before any balance changes were applied — i.e., all-or-nothing execution across every AA touched, not just the bouncing one. [5](#0-4) [6](#0-5) 

Finally, the whole set of responses generated by the primary trigger (all balance changes, all state updates) is written and committed in a single `batch.write({ sync: true }, ...)` inside one DB transaction — the same "single atomic transaction, no pause, no delay" property that let Makina's attacker manipulate a Curve pool and read the manipulated state in the same breath. [7](#0-6) 

### Impact Explanation
Any AA design that uses `balance[other_AA][asset]` (or even `balance[this_address][asset]` combined with multiple chained payment messages) as a pricing/valuation input for issuing assets, computing exchange rates, or gating payouts is exposed to intra-cascade manipulation: an attacker structures a single trigger unit that chains through a "pool"/"proxy" AA (skewing its balance via a large payment), then, within the same atomic secondary-trigger tree, another AA reads that already-skewed `balance[...]` to price a trade or authorize a withdrawal before the cascade completes and commits. Because the whole tree commits together (or reverts together on any bounce), this is functionally equivalent to a flash-loan-in-one-transaction attack: unauthorized extraction of AA-held funds (bytes or issued assets) at a manipulated exchange rate, i.e. concrete AA fund loss reachable by any unprivileged unit poster who can afford the trigger's bounce fees.

### Likelihood Explanation
Reachability is high: triggering an AA chain requires nothing beyond posting an ordinary payment-carrying unit to a public AA address, something any wallet holder can do. The vulnerable pattern (raw, undelayed `balance[]` used as price input across AAs) is not hypothetical — it is the literal pattern demonstrated in ocore's own shipped sample AAs (`uniswap_like_market_maker.oscript`, `fundraising_proxy.oscript`), meaning developers following the documented, "reference" way of building AMM/threshold logic on top of AAs inherit this exact class of oracle-manipulation risk, with no core-level guardrail (no TWAP helper, no mandatory settlement delay, no warning in `formula/validation.js`) preventing it.

### Recommendation
- Add a core-level time-weighted/settled-balance primitive (e.g., a `balance_at(mci)` or a delay-enforced snapshot) that AA authors can use instead of raw `balance[]` for cross-AA pricing, and document `balance[]` as unsafe for use as a price oracle across AA boundaries within the same trigger cascade.
- Update the bundled reference templates (`uniswap_like_market_maker.oscript`, `fundraising_proxy.oscript`) to demonstrate manipulation-resistant pricing (e.g., requiring the balance to be read as of a previously stabilized MCI, or requiring a cooling-off unit between deposit and price-dependent withdrawal) since these samples are widely copied as starting points by DeFi-style AA developers.
- Consider warning-level lint/validation in `formula/validation.js` when `balance[address][...]` is used with `address` other than `this_address`, to flag potential cross-AA spot-price dependencies during AA definition validation.

### Proof of Concept
Conceptual reachable path (no code changes needed to demonstrate the primitive; only an AA that follows the shipped anti-pattern is needed):
1. Deploy `PoolAA` following the `uniswap_like_market_maker.oscript` pattern, pricing swaps via `balance[$asset]`/`balance[base]`.
2. Deploy `ConsumerAA` that, as a secondary trigger triggered by a payment forwarded from `PoolAA`, reads `balance[PoolAA_address][$asset]` to value/authorize a payout (mirroring `fundraising_proxy.oscript`'s `balance[$destination_aa][base]` pattern).
3. Attacker posts a single unit sending a large payment to `PoolAA` structured so that `PoolAA`'s response message forwards part of the funds on to `ConsumerAA` as a secondary trigger within the same cascade (`aa_composer.js` `handleSecondaryTriggers`, `aa_composer.js:1702-1757`).
4. `ConsumerAA` reads `balance[PoolAA][$asset]` (`formula/evaluation.js:1510-1528`) reflecting the just-skewed, uncommitted balance from step 3, and computes a payout at the distorted rate.
5. The whole chain (PoolAA response + ConsumerAA response) commits together in one `batch.write` (`aa_composer.js:91-151`); if `ConsumerAA` had instead bounced, the entire chain — including `PoolAA`'s already-computed balance changes — would roll back atomically (`aa_composer.js:1759-1783`), confirming the transaction-equivalent atomicity that makes the manipulate-then-read sequence riskless for the attacker to attempt.

	function handleSecondaryTriggers(objUnit, arrOutputAddresses) {
		conn.query("SELECT address, definition, mci, main_chain_index FROM aa_addresses LEFT JOIN units USING(unit) WHERE address IN(?) AND mci<=? ORDER BY address", [arrOutputAddresses, mci], function (rows) {
			if (rows.length > 0 && constants.bTestnet && mci < testnetAAsDefinedByAAsAreActiveImmediatelyUpgradeMci)
				rows = rows.filter(function (row) {
					if (row.main_chain_index && row.main_chain_index < mci) // previous definition is already stable
						return true;
					var len = storage.getUnconfirmedAADefinitionsPostedByAAs([row.address]).length;
					if (len > 0)
						console.log("not calling secondary trigger from unit " + objUnit.unit + " to AA " + row.address);
					return (len === 0);
				});
			if (rows.length === 0) {
				saveStateVars();
				addUpdatedStateVarsIntoPrimaryResponse();
				return onDone(objUnit, bBouncing ? error_message : false);
			}
			if (bBouncing)
				throw Error("secondary triggers while bouncing");
			async.eachSeries(
				rows,
				function (row, cb) {
					var child_trigger = getTrigger(objUnit, row.address);
					child_trigger.initial_address = trigger.initial_address;
					child_trigger.initial_unit = trigger.initial_unit;
					if ("max_aa_responses" in trigger && mci >= constants.pemCurvesFixMci) // propagate the cap set on the primary trigger to secondary triggers
						child_trigger.max_aa_responses = trigger.max_aa_responses;
					var arrChildDefinition = JSON.parse(row.definition);

					var child_trigger_opts = { ...trigger_opts };
					child_trigger_opts.trigger = child_trigger;
					child_trigger_opts.params = {};
					child_trigger_opts.arrDefinition = arrChildDefinition;
					child_trigger_opts.address = row.address;
					child_trigger_opts.bSecondary = true;
					child_trigger_opts.onDone = function (objSecondaryUnit, bounce_message) {
						if (bounce_message)
							return cb(bounce_message);
						cb();
					};
					handleTrigger(child_trigger_opts);
				},
				function (err) {
					if (err) {
						// revert
						if (bSecondary)
							return bounce(err);

						return revert({message: "one of secondary AAs bounced with error: ", callChain: {address, next: err}});
					}
					saveStateVars();
					addUpdatedStateVarsIntoPrimaryResponse();
					onDone(objUnit, bBouncing ? error_message : false);
