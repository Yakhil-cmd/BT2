### Title
Orphaned `is_spent` flag on outputs whose spending unit later became `final-bad` permanently freezes stable-good funds - ([File: writer.js])

### Summary
When a new unit spends an output, `writer.js` unconditionally sets `outputs.is_spent=1` for the source output as soon as *any* transfer input references it, including the case where that same input is later determined to be a non-unique double-spend loser whose unit gets permanently voided as `final-bad`. Nothing in the codebase resets `is_spent` back to `0` when the spending unit's sequence resolves to `final-bad`. This "orphaned" spend flag survives forever, causing wallet/AA software that filters on `is_spent=0` to treat a perfectly good, stable, unspent output as already spent, freezing the funds from ever being used again.

### Finding Description
`writer.js` marks the source output as spent for every author of a `"transfer"` input at write time, independent of whether the input will ultimately be judged the winner of a double-spend: [1](#0-0) 

The `is_unique` column (which actually tracks whether this particular input "wins" the double-spend, or is set to `NULL`/left unresolved for double-spend competitors) is computed separately: [2](#0-1) 

Double-spend resolution logic in `validation.js` only clears `inputs.is_unique` for the losing claims, and only for still-unstable units — it never touches `outputs.is_spent`: [3](#0-2) 

`final-bad` units are explicitly documented as being permanently and irrevocably voided competitors: [4](#0-3) 

Once such a losing spending unit is finalized as `final-bad`, its `INSERT INTO inputs` row and the `UPDATE outputs SET is_spent=1` performed at write time are never revisited or rolled back anywhere in `writer.js`, `main_chain.js`, or `joint_storage.js` finalization code. The source output keeps `is_spent=1` forever even though no `good`-sequence unit actually spends it.

This exact defect — an output flagged as spent while no good spender exists — is independently confirmed and reproduced by an internal diagnostic tool that compares the two computation methods and explicitly calls these "zombie-spent outputs": [5](#0-4) [6](#0-5) 

Every consumer that selects spendable coins for building new payments, AA responses, or balance totals filters strictly on `is_spent=0` (e.g. `balances.js`, `composer.js`, `aa_composer.js`, `wallet.js`, `indivisible_asset.js`, `mc_outputs.js`, `inputs.js`, `wallet_defined_by_addresses.js`), so a zombie-spent output becomes permanently unusable by its rightful owner even though it is unambiguously good, stable, unspent balance on the DAG.

This is directly analogous to the GitLab bug class: an authorization/state-tracking record (`is_spent`) is never cleaned up after the entity that created it (the losing double-spend input, tied to a `final-bad`/orphaned unit) is invalidated, and downstream logic keeps enforcing the stale record's effect.

### Impact Explanation
The affected output's coins become permanently frozen from the perspective of every wallet/AA/composer code path that respects the `is_spent` flag, since nothing in the codebase ever clears it once set. This is a concrete fund-freezing bug reachable purely through the normal course of DAG operation — it requires no malicious peer, node, hub, or network attack, only that an address (an unprivileged unit poster) ends up on the losing side of a double-spend resolution for one of its own stable outputs (a routine, expected occurrence in an asynchronous DAG such as resubmitting a payment after a stalled/forked broadcast, or a co-signer of a shared/multisig address acting adversarially to fork one of their own joint outputs). The victim can never recover or re-spend that balance through normal wallet operation, meeting the "AA fund loss or freezing" impact bar.

### Likelihood Explanation
Double-spends on one's own outputs (accidental via resubmission after connectivity issues, or intentional by a co-signer on a shared/multisig address) are a normal, expected event in this DAG design and are explicitly handled (and thus anticipated) by `checkForDoublespends`/`acceptDoublespends`. Any such event that resolves with the losing unit becoming `final-bad` triggers this bug deterministically — there is no additional precondition, timing race, or privileged capability required, making the likelihood high given that double-spend races are a routine part of normal DAG operation.

### Recommendation
When a unit's `sequence` is set to `final-bad` (in `main_chain.js`/`writer.js`/wherever finality propagation determines the final-bad status), issue a corresponding reconciliation query to reset `outputs.is_spent=0` for any output uniquely spent by that `final-bad` unit's inputs, provided no other `good`-sequence unit also claims it (mirroring the `NOT EXISTS` logic already implemented as the corrected balance query in `tools/compare_vote_balances.js`). Alternatively, replace all `is_spent=0` filters used for spendability/balance computation with the `NOT EXISTS (... good, stable spender ...)` pattern shown as the "NEW" method in that same tool, eliminating reliance on the stale, unmaintained `is_spent` column entirely.

### Proof of Concept
1. Address A has a stable, good output O.
2. Attacker (or A itself, via a stalled resend, or a malicious co-signer of a shared address) posts unit U1 spending O, followed shortly by unit U2 also spending O (a double-spend), both signed validly by A/the shared definition.
3. `writer.js` sets `outputs.is_spent=1` for O when either U1 or U2 is written (whichever is processed/committed), per `writer.js:378-383`.
4. Network/DAG resolution eventually finalizes one of U1/U2 as `sequence='good'` and the other as `sequence='final-bad'` per the standard double-spend finality rules in `validation.js`.
5. If the unit that triggered `is_spent=1` for O turns out to be the one that becomes `final-bad` (e.g., due to it also being non-unique/losing in the specific finality resolution), `outputs.is_spent` for O remains permanently `1`, though no `good` unit ever actually consumed O.
6. Address A can never spend O again through `composer.js`/`wallet.js`/`balances.js`, all of which query `is_spent=0` to select spendable funds — the balance is durably frozen.
7. Run `tools/compare_vote_balances.js` against a DB exhibiting this state: it reports a nonzero `delta`, empirically demonstrating the divergence between the (buggy) `is_spent`-based balance and the correct NOT-EXISTS-based balance, confirming the existence of such "zombie-spent" outputs in the wild.
