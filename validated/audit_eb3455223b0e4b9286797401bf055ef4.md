### Title
Permanent freezing of staker's locked sBTC if the external `sbtc-token` transfer in `unstake-sbtc` cannot succeed - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`unstake-sbtc` in `pox-5.clar` is the only path by which a bond participant recovers custodied sBTC. It first mutates all of pox-5's internal accounting (per-cycle shares, `protocol-bonds-total-staked`, `total-sbtc-staked`, and the membership's `amount-sats`) and then, in the same atomic transaction, performs a `contract-call?` to the external `sbtc-token` contract's `transfer` function to actually move the sBTC back to the staker. There is no alternate, accounting-only or queued withdrawal path. If that single external call cannot ever succeed for the staker's principal (e.g., the token contract enters a state — pause, blacklist, insufficient physical balance versus pox-5's internal ledger, or any other externally-controlled condition — that always causes the `transfer` to error), `unstake-sbtc` will always revert for that staker, and their sBTC will be frozen in the contract with no way to recover it, forever.

### Finding Description [1](#0-0) 

The function performs, in order:
1. Load `membership` and compute `new-amount-sats` for the staker `(map-get? protocol-bond-memberships staker)`.
2. Mutate per-cycle bond-share bookkeeping via `unstake-sats-from-bond-cycles`.
3. `map-set protocol-bond-memberships`, `map-set protocol-bonds-total-staked`, and `var-set total-sbtc-staked` to reflect the withdrawal.
4. Only at the very end, attempt the actual token movement:
```
(try! (as-contract?
    ((with-ft 'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token
        "sbtc-token" amount-to-withdrawal-sats
    ))
    (try! (contract-call? 'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token
        transfer amount-to-withdrawal-sats tx-sender staker none
    ))
))
``` [2](#0-1) 

Because Clarity transactions are atomic, a failing `transfer` call rolls back the accounting mutations too — so this is not an accounting-inconsistency bug in the narrow sense. The structural problem is the same class as the reported oracle-liquidation-freeze bug: **the contract has exactly one code path to release value, and that path is unconditionally gated on a successful call into an external, out-of-pox-5's-control contract**. Just as `BlueBerryBank.liquidate()` is permanently blocked whenever the Chainlink oracle call reverts, `unstake-sbtc` is permanently blocked whenever the `sbtc-token.transfer` call reverts for a given staker/amount — and pox-5 has no safeguard, retry mechanism, or accounting-only fallback to release the staker's claim in that scenario. Since `pox-5.clar` treats `sbtc-token` as a hard external dependency at the sole exit point for locked collateral, any externally-triggered failure mode of that single call (temporary or permanent) directly translates into a freeze of the staker's sBTC inside pox-5, with the staker's on-chain `protocol-bond-memberships`/`amount-sats` record continuing to show their claim as outstanding but permanently unreachable.

I was not able to find any alternate recovery function, pause-bypass, or admin/staker escape hatch elsewhere in `pox-5.clar` for this scenario — a search for `ERR_SBTC`, `recover`, or a secondary unstake path returned no matches, suggesting `unstake-sbtc` is indeed the sole exit for bond-custodied sBTC.

### Impact Explanation
If the sole external call in `unstake-sbtc` cannot succeed for a period (or permanently), all sBTC held in bond custody for the affected staker(s) becomes permanently unrecoverable through pox-5, even though pox-5's internal ledger (`total-sbtc-staked`, `protocol-bond-memberships`) still reflects the staker as entitled to it. This is a "permanent freezing of staked ... sBTC" outcome, which the scope rules classify as Critical impact.

### Likelihood Explanation
Likelihood depends entirely on external, non-pox-5 conditions of the `sbtc-token` contract (its own pause/blacklist mechanisms or any accounting drift between its ledger and pox-5's internal ledger causing insufficient contract-held balance for a legitimate withdrawal). Per the scope rules, the `sbtc-token` contract's internals are out of scope except where pox-5's own usage is the flaw — and the flaw here is architectural: pox-5 offers no fallback when its single external dependency for releasing collateral fails, mirroring exactly the "oracle down → liquidation frozen" bug class from the reference report.

### Recommendation
Decouple the internal accounting update from the external token transfer so that a failed/unavailable `sbtc-token.transfer` does not permanently strand a staker's claim: e.g., allow the internal ledger update to succeed independent of the transfer's success and expose a separate, retryable "claim/withdraw" entrypoint that can be re-attempted once the external dependency recovers, or maintain a per-staker pending-withdrawal credit that can be redeemed once `sbtc-token` calls succeed again.

### Proof of Concept
Not independently reproducible from the indexed contract alone, since it requires the external `sbtc-token` contract to enter a state where `transfer` unconditionally errors for the affected principal/amount (its implementation is out of scope here). Conceptually:
1. Staker registers for a bond and locks sBTC via `register-for-bond`, custodied by pox-5.
2. The external `sbtc-token` contract enters a state (pause, blacklist of the pox-5 contract principal, or balance shortfall) such that `(contract-call? sbtc-token transfer ...)` always returns an error.
3. Staker calls `unstake-sbtc`; the call to `transfer` errors, the entire transaction (including the intended accounting release) reverts via `try!`.
4. Every subsequent call to `unstake-sbtc` by this staker reverts identically — their custodied sBTC is now permanently unreachable through pox-5, with no other function offering release of that value.

(define-public (unstake-sbtc
        (signer-manager <signer-manager-trait>)
        (amount-to-withdrawal-sats uint)
    )
    (let (
            (staker tx-sender)
            (membership (unwrap! (map-get? protocol-bond-memberships staker)
                ERR_NOT_BOND_PARTICIPANT
            ))
            (bond-index (get bond-index membership))
            (signer (get signer membership))
            (current-cycle (current-pox-reward-cycle))
            (bond-start-cycle (bond-period-to-reward-cycle bond-index))
            (bond-end-cycle (bond-period-to-reward-cycle (+ bond-index u6)))
            (first-changed-reward-cycle (clamp current-cycle bond-start-cycle bond-end-cycle))
            (num-cycles (- bond-end-cycle first-changed-reward-cycle))
            (current-amount-sats (get amount-sats membership))
            (current-total-sbtc-staked (get-total-sbtc-staked))
            ;; Cannot withdrawal more than they've staked
            (new-amount-sats (try! (if (<= amount-to-withdrawal-sats current-amount-sats)
                (ok (- current-amount-sats amount-to-withdrawal-sats))
                ERR_INVALID_UNSTAKE_SBTC_AMOUNT
            )))
        )
        ;; Reject during the prepare phase since next-cycle data is mutated
        (try! (verify-not-prepare-phase))

        ;; `signer-manager` must match the current signer
        (asserts! (is-eq (contract-of signer-manager) signer)
            ERR_INVALID_OLD_SIGNER_MANAGER
        )

        ;; Must be an sBTC lock
        (asserts! (not (get is-l1-lock membership)) ERR_CANNOT_UNSTAKE_SBTC)

        ;; ensure no reentrancy through signer-manager trait calls
        (try! (validate-no-reentrancy))

        ;; Unstake this staker's sBTC from the current and future cycles.
        ;; N.B. Because the staker might use a different signer for the current
        ;; cycle vs future cycles (through `update-bond-registration`), we must
        ;; derive the signer from each cycle individually (instead of using
        ;; `remove-staker-from-bond-cycles`).
        (try! (unstake-sats-from-bond-cycles staker bond-index
            first-changed-reward-cycle num-cycles amount-to-withdrawal-sats
            new-amount-sats
        ))

        (map-set protocol-bond-memberships staker
            (merge membership { amount-sats: new-amount-sats })
        )
        (map-set protocol-bonds-total-staked bond-index
            (- (get-total-sbtc-staked-for-bond bond-index)
                amount-to-withdrawal-sats
            ))

        ;; Mutate the total sBTC staked
        (var-set total-sbtc-staked
            (- current-total-sbtc-staked amount-to-withdrawal-sats)
        )

        (try! (as-contract?
            ((with-ft 'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token
                "sbtc-token" amount-to-withdrawal-sats
            ))
            (try! (contract-call? 'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token
                transfer amount-to-withdrawal-sats tx-sender staker none
            ))
        ))

        (let ((result {
                staker: staker,
                signer: signer,
                bond-index: bond-index,
                amount-withdrawn-sats: amount-to-withdrawal-sats,
                new-amount-sats: new-amount-sats,
            }))
            (print (merge { topic: "unstake-sbtc" } result))
            (ok result)
        )
    )
