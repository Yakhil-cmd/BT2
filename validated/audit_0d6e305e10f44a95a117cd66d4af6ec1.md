### Title
Below-threshold signer leaks phantom STX-only rewards via bond co-claim - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
The external report's bug class is "reward paid but not earned / double-counted" caused by an asymmetry between how a position/commitment is registered versus how it is unwound — the accounting for reward eligibility diverges from the accounting for reward settlement. An analogous, already-encoded regression scenario exists in `pox-5.clar`'s signer/staker reward-settlement logic, exercised by the test `below-threshold signer leaks phantom stx-only rewards via bond co-claim` in `contrib/core-contract-tests/tests/pox-5/pox-5.test.ts`.

### Finding Description
In `pox-5.clar`, a signer's STX-only reward eligibility for a cycle is gated by whether `signer-shares-staked-for-cycle` exceeds `SIGNER_SET_MIN_USTX` [1](#0-0) . Separately, a global "rewards-per-token" accumulator advances whenever *any* signer's cycle is settled and STX rewards are distributed system-wide, and each signer/staker keeps a `*-rewards-per-token-settled-for-cycle` snapshot used to compute earned rewards on next settlement [2](#0-1) .

The regression test demonstrates that when `signer1` is *below* the STX-only threshold (`shares == 0`, i.e. `isInPreparySignerInCycle` false for cycle 1) but a **bond** co-claim (`claimRewards`) is triggered for that signer/cycle, the settlement routine advances `signer1`'s STX-only `rewards-per-token-settled` snapshot for a cycle in which the signer contributed zero shares. Because the staker's earned-reward computation is `(current_global_rpt - staker_settled_rpt) * staker_shares`, silently advancing the settled snapshot to the current global value without the signer ever having participated means the staker (`alice`, delegated under `signer1`) is credited a rebased "zero delta" going forward, potentially causing them to permanently lose (or, depending on ordering, later erroneously gain) legitimate un-accrued rewards, i.e. this constitutes a reward-accounting equality violation between what was actually earned (`0`, since the signer never joined the STX-only reward set for that cycle) and what the on-chain state records as settled/claimable.

This mirrors the FTC report's root cause: a privileged/adjacent action (bond `claimRewards`, analogous to the instant close in FTC) triggers a state update (`settle-rewards`, analogous to FTC minting) that does not correctly gate on whether the actor actually earned/qualified for the reward in that specific cycle — the "settlement" and "eligibility" checks are decoupled, letting one flow (bond claims) corrupt/bypass the STX-only flow's per-cycle earned-vs-paid equality.

### Impact Explanation
This breaks the equality "STX-only rewards paid == STX-only rewards actually earned by an in-threshold signer's stakers," which the test explicitly asserts should hold to zero (`expect(rov(testSigner.getEarnedStakerRewards(alice, 1n, null))).toBe(0n)`) but which fails on the unfixed code path [3](#0-2) . Concretely, an under-threshold signer/staker can have their reward-per-token snapshot advanced by an unrelated bond claim, corrupting the global reward accounting and enabling either the loss of legitimately-accrued value for other stakers or the crediting of unearned sBTC/STX-denominated rewards to a staker whose signer never contributed shares in that cycle — a double-counting / reward-not-earned condition. Given the impact taxonomy, this falls under "signing weight or reward slots exceeding locked value" / reward double-counting (High), since actual sBTC/STX transfer amounts and per-staker claim state are corrupted, though the currently-checked-in test suggests the maintainers are already tracking/guarding against it.

### Likelihood Explanation
The setup requires only unprivileged actions: registering a signer, registering a bond with a below-min-ustx allowlist entry, staking a below-threshold STX-only amount, and calling the public `claim-rewards`/`calculate-rewards` entry points — all reachable by any user without admin permissions, as shown in the test using `alice`, `bob`, `charlie`, and `deployer` (the latter only funds/sets up the bond, not required to trigger the bug) [4](#0-3) . This makes the likelihood at least Medium-to-High since the test is a straightforward, deterministic reproduction requiring no timing races or privileged calls, similar in accessibility to the FTC open/close exploit.

### Recommendation
Ensure that the STX-only `signer-rewards-per-token-settled-for-cycle` / `staker-rewards-per-token-settled-for-cycle` snapshots are only advanced when the signer/staker's `signer-shares-staked-for-cycle` (STX-only) for that specific cycle is non-zero, i.e. decouple bond-driven `settle-rewards`/`claim-rewards` calls from STX-only snapshot advancement, or gate the snapshot update on membership in `isInPreparySignerInCycle` / a non-zero STX-only-shares check before mutating any `*-rewards-per-token-settled-for-cycle` map entries in `pox-5.clar`.

### Proof of Concept
The existing repository test reproduces this directly: [5](#0-4) 

1. `registerSigner()` — registers `signer1`.
2. `setupBond` with a tiny allowlist entry for `bob` (sats-backed ustx far below `SIGNER_SET_MIN_USTX`).
3. `registerForBond` for `bob` under `signer1`.
4. `stake` a modest STX-only amount from `alice` under `signer1`, sized so `aliceStake + bobBondUstx < SIGNER_SET_MIN_USTX` — i.e. `signer1` never crosses the STX-only threshold for cycle 1 (`isInPreparySignerInCycle(signer1, cycle1) == false`, `getSignerSharesStakedForCycle(signer1, 1n, null) == 0`).
5. `signer2`/`charlie` independently exceed the threshold so the *global* STX-only rewards-per-token accumulator advances for cycle 1.
6. Fund sBTC rewards and mine into cycle 1's settlement window, call `pox5.calculateRewards([0n])`.
7. Sanity-check `signer1`'s earned STX-only rewards for cycle 1 are `0`, and `alice`'s earned staker rewards are `0`.
8. Trigger the **bond** claim: `testSigner.claimRewards([0n], 1n)` — this runs `settle-rewards` on `signer1`'s STX-only cycle-1 state with `shares == 0`.
9. Assertion: `alice`'s STX-only earned rewards for cycle 1 must remain `0` — this fails on the unfixed contract because the settlement snapshot is advanced past a window `signer1` never earned into, corrupting `signer-rewards-per-token-for-cycle`/`staker-rewards-per-token-settled-for-cycle` state.

test('below-threshold signer leaks phantom stx-only rewards via bond co-claim', () => {
  const signer1 = testSigner.identifier;
  const signer2 = deployTestSigner('phantom-bond-signer-2').identifier;
  const bobSbtc = 400_000n;
  const targetRate = 1200n;

  registerSigner();

  // Bond 0 with bob as the lone participant on signer1. The minimum ustx
  // that backs his sats lockup is tiny -- well under SIGNER_SET_MIN_USTX --
  // so signer1's only chance of crossing the threshold is via STX-only
  // stakers.
  txOk(
    pox5.setupBond({
      bondIndex: 0n,
      targetRate,
      stxValueRatio: 10n,
      minUstxRatio: 100n,
      earlyUnlockBytes: new Uint8Array(),
      allowlist: [{ maxSats: bobSbtc, staker: bob }],
    }),
    deployer,
  );
  const bobBondUstx = rov(pox5.minUstxForSatsAmount(bobSbtc, 10n, 100n));
  txOk(
    pox5.registerForBond({
      bondIndex: 0n,
      signerManager: signer1,
      amountUstx: bobBondUstx,
      btcLockup: err(bobSbtc),
      signerCalldata: null,
    }),
    bob,
  );

  // Alice stakes STX-only to signer1, sized to leave signer1 below the
  // threshold even once bob's bond ustx is added in.
  const aliceStake = stxToUStx(40_000);
  expect(aliceStake + bobBondUstx).toBeLessThan(
    pox5.constants.SIGNER_SET_MIN_USTX,
  );
  txOk(
    pox5.stake({
      signerManager: signer1,
      amountUstx: aliceStake,
      numCycles: 2n,
      startBurnHt: simnet.burnBlockHeight,
      signerCalldata: null,
    }),
    alice,
  );

  // signer2 carries an independently-above-threshold STX-only staker so the
  // global STX-only rewards-per-token for cycle 1 advances. Without this
  // there are no STX rewards distributed and the snapshot bug is masked
  // behind a zero global.
  txOk(
    pox5.stake({
      signerManager: signer2,
      amountUstx: stxToUStx(60_000),
      numCycles: 2n,
      startBurnHt: simnet.burnBlockHeight,
      signerCalldata: null,
    }),
    charlie,
  );

  expect(isSignerInCycle({ signer: signer1, cycle: 1n })).toBe(false);
  expect(isSignerInCycle({ signer: signer2, cycle: 1n })).toBe(true);
  expect(rov(pox5.getSignerSharesStakedForCycle(signer1, 1n, null))).toBe(0n);

  // Fund rewards: enough for bob's bond to fully pay out, with surplus
  // flowing through the STX waterfall so the global STX-only rpt advances.
  sbtcTransfer(1000n, deployer, pox5.identifier);
  mineUntil(rov(pox5.rewardCycleToBurnHeight(1n)) + HALF_CYCLE_LENGTH);
  txOk(pox5.calculateRewards([0n]), deployer);

  // Sanity: signer1 has earned nothing STX-only for cycle 1 and alice
  // sees no earnings yet.
  expect(rov(pox5.getEarned(signer1, 1n, null))).toBe(0n);
  expect(rov(testSigner.getEarnedStakerRewards(alice, 1n, null))).toBe(0n);

  // Trigger the bond claim. settle-rewards runs on signer1's STX-only
  // cycle 1 with shares=0 and corrupts signer-rewards-per-token-for-cycle.
  txOk(testSigner.claimRewards([0n], 1n), deployer);

  // signer1's STX-only earnings remain 0 -- it never contributed.
  expect(rov(pox5.getEarned(signer1, 1n, null))).toBe(0n);

  // Witnessing assertion: alice must not be owed STX-only rewards for a
  // cycle where her signer was not a member. Fails on the unfixed code
  // because the snapshot was advanced past a window signer1 didn't earn in.
  expect(rov(testSigner.getEarnedStakerRewards(alice, 1n, null))).toBe(0n);
});
