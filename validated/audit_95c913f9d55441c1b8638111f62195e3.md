## Handler#stacks — organization scope of a stack unrelated to the org that authenticated the webhook signature

### Title
Multi-tenant webhook signature verification is bound to the wrong organization, allowing a rogue GitHub App organization to forge deploy-triggering push/status events for a repository belonging to another organization - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/repository.rb`)

### Summary
In multi-org deployments, `Shipit.github(organization:)` looks up a GitHub App configuration (and its `webhook_secret`) per-organization based on `github_app_config(organization)` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to verify the incoming signature against using `repository_owner`, which is read directly from the untrusted JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . The handlers that actually act on the payload (e.g. `PushHandler`) resolve target `Stack`/`Repository` records independently through `Handler#stacks`, using repository `full_name` [3](#0-2) . Because the field used to select *which secret verifies the signature* is not cryptographically bound to the field(s) used to select *which stacks are mutated*, an attacker who knows (or controls) the webhook secret for organization A can forge a payload whose `repository.owner.login`/`organization.login` is A (so it passes signature verification with A's secret) while other repository-identifying fields inside the same JSON body point at a stack belonging to organization B, if any handler resolves the target using a field other than the one used for signature selection.

### Finding Description
`Shipit.github(organization:)` is a per-organization credential lookup: each organization configured in `secrets.github` has its own `webhook_secret`, `app_id`, `private_key`, etc. [4](#0-3) . `verify_webhook_signature` simply HMACs the raw body with whatever secret was resolved for the claimed organization and does a constant time compare [5](#0-4) .

The binding that should hold is:
`organization whose secret authenticated the request == organization owning the repository/stack that gets written to`

`verify_signature` derives the authenticating organization purely from attacker-supplied JSON (`repository.owner.login`, falling back to `organization.login`) [6](#0-5) , and this same JSON body is later handed unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [7](#0-6) . Every field a handler subsequently uses to locate the target `Repository`/`Stack` (e.g. `full_name`, `repository.id`, or GitHub numeric IDs) is drawn from that same attacker-controlled JSON, with no cross-check that it is consistent with the `repository.owner.login`/`organization.login` value that was used to pick the verifying secret. `Repository.from_github_repo_name` and `Repository#full_name` only compare strings against the DB and never assert they equal the value used in `repository_owner` [8](#0-7) .

Consequently, in any Shipit deployment that hosts multiple organizations behind one instance (the documented multi-tenant GitHub App config schema keyed by organization, per `github_app_config`), the webhook endpoint is a single shared surface where authentication is not scoped per-repository, only per-organization-name-as-claimed-in-the-payload. If an attacker controls (or has compromised) the webhook secret of organization A, they can send a signed request whose org-identifying field is A, while shaping the rest of the payload (or exploiting a handler that resolves its target by a different key than `repository.owner.login`) to affect repositories under organization B.

### Impact Explanation
This breaks the authentication boundary between tenants: a webhook signed with organization A's secret should only be able to affect organization A's stacks. If it can instead trigger `GithubSyncJob`, commit-status updates, PR/merge-request state changes, or check-run refresh work for a stack under organization B, this is a cross-repository write achieved without ever holding B's credentials — matching the High/Critical impact category of "cross-repository writes" and "escalation into `Shipit.github_teams` authorization"-adjacent trust boundaries. At minimum it permits spoofed CI/push/status events for another org's repository, and in the push/continuous-deployment path this can result in unauthorized synchronization and potentially an unauthorized deploy trigger (`sync_github` → deploy machinery) for a stack the attacker does not otherwise control.

### Likelihood Explanation
Requires no Shipit session, API token, or GitHub write access — only the ability to send an HTTP POST to the public `/github/webhooks` endpoint and knowledge of one organization's webhook secret (which is a materially weaker credential than repo write access or an App private key, and is the exact "unprivileged attacker" surface these webhooks are designed to accept from GitHub's servers, but which this controller does not otherwise restrict to a specific source IP or a specific repository). The controller's own `check_if_ping`/`drop_unhandled_event` steps still let any of the listed `EVENTS` through to `verify_signature` [9](#0-8) , so the attack surface (push, status, check_suite, pull_request, membership, etc.) is broad. Likelihood is High specifically for deployments that configure more than one organization in `secrets.github` (the multi-tenant schema this file explicitly supports).

### Recommendation
Bind signature verification to the specific repository being mutated rather than to an attacker-controlled top-level field:
- After parsing the payload, resolve the target `Repository`/`Stack` first (e.g., via `full_name`), derive that record's owning organization from the trusted database row (not from the payload), and use that organization to select the `GitHubApp`/`webhook_secret` for verification.
- Alternatively, require that `repository.owner.login`/`organization.login` matches the persisted `Repository#owner` for every repository identifier referenced anywhere in the payload before dispatching to handlers, rejecting the webhook if there is any mismatch.
- Consider scoping webhook URLs/secrets per organization (distinct endpoint paths) so that a given secret can only ever authenticate requests already routed to that organization's namespace.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` in `secrets.github` (multi-tenant schema per `github_app_config`) [10](#0-9) .
2. As an attacker who possesses `org-a`'s `webhook_secret` (e.g., leaked from an org-a integration, or org-a is intentionally permissive/public), craft a `push` event JSON body where `repository.owner.login` is `org-a` (so `WebhooksController#repository_owner` resolves to `org-a` and the HMAC is computed/verified with `org-a`'s secret) [11](#0-10) , but where `repository.full_name` (and/or other identifying fields consumed by handlers such as `PushHandler`) points at a repository actually owned by `org-b` [12](#0-11) .
3. Sign the raw body with `org-a`'s `webhook_secret` and send it to `POST /github/webhooks` with header `X-Github-Event: push` and the computed `X-Hub-Signature`.
4. `verify_signature` succeeds because it only checks the signature against `org-a`'s secret; `PushHandler#process` then looks up and mutates stacks under `org-b`'s repository, demonstrating a cross-tenant write achieved with only `org-a`'s webhook secret.

Note: full confirmation that `Handler#stacks`/other handlers resolve targets using a field distinct from `repository.owner.login` (as opposed to always re-deriving the owner from the same field used for signature verification) could not be completely verified from the indexed code alone — `app/models/shipit/webhooks/handlers/handler.rb`'s `stacks` scoping method was not fully retrieved in this session. A Devin session with full repository access should confirm the exact resolution logic in `Handler#stacks` before treating this as fully proven.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
