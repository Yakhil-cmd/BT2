### Title
Missing cosigner-ACL check on local "sign" requests allows any paired device to trigger signing prompts for a victim's addresses - (File: wallet.js)

### Summary
The MISP CVE is a class of "authorization check omitted before performing a state-changing/exposure action." In `ocore`, the analogous gap is in the device-message handler for `"sign"` requests in `wallet.js`: for `ifRemote` (proxying) the code correctly verifies the requester is a listed cosigner, but for `ifLocal` (the address's keys live on this device) the equivalent cosigner check is present in the code only as a **commented-out block**, so it is never executed.

### Finding Description
`handleMessageFromHub` processes the `"sign"` device-message subject sent by any correspondent ("paired device"): [1](#0-0) . After basic structural validation it calls `findAddress(body.address, body.signing_path, callbacks)` and dispatches to `ifLocal` or `ifRemote` depending on whether the address's private key lives on the current device or on a peer device [2](#0-1) .

For `ifRemote` (this device is only a proxy toward the real signer), the code explicitly checks that the requesting `from_address` is actually listed among the address's cosigners before doing anything: [3](#0-2) 

For `ifLocal` (this device holds the actual signing key for `body.address`), the equivalent check is present in the source but disabled via comments: [4](#0-3) 

Because that check is commented out, `callbacks.ifOk()` is called unconditionally, and the handler proceeds to fire a `"signing_request"` event for essentially any `body.address` that `findAddress` resolves locally — regardless of whether `from_address` (the sender's paired device) is actually a cosigner/member of that address's definition. `findAddress` itself performs no cosigner check for the `ifLocal` branch either; it merely confirms the address/signing_path pair exists in `my_addresses`/`shared_addresses` and that the local device owns the corresponding key material [5](#0-4) .

This means:
- For a genuinely *shared/multisig* address, any correspondent device that knows (or guesses/observes) the address and a valid `signing_path` can submit a signing request and get it routed to the "signing_request" UI event, even if that device/cosigner has no legitimate right to request a signature on that particular sub-path.
- Worse, for a plain **single-signature address belonging solely to the victim**, `findAddress` still resolves it via `my_addresses` and calls `ifLocal`, so an unrelated paired device with no cosigning relationship whatsoever to that address can submit a `"sign"` request that reaches the user's wallet UI as a legitimate-looking signing prompt for the victim's *own* private address, tied to an attacker-supplied unsigned unit/payment structure or `signed_message`. This subverts the intended trust boundary that only enumerated cosigners of an address should be able to originate signing requests for it, which is exactly the class of bug represented by the CVE (an action is allowed to proceed without the ACL check that should gate it).

### Impact Explanation
While actual fund movement still requires local user approval via the `"signing_request"`/`confirm_*` UI events, the missing ACL check breaks the intended cosigner authorization model: any paired correspondent (not necessarily a genuine cosigner) can inject arbitrary unsigned-unit or signed-message signing prompts targeting the victim's own addresses. This enables social-engineering-driven unauthorized spending (the user is shown a plausible-looking signing request they never legitimately requested, for a payment/contract state they did not initiate) and can also be abused to spam/mislead the signing UI for shared addresses from parties who are not real cosigners. This aligns with concrete unauthorized-spending risk gated only by UI confirmation rather than protocol-level authorization, which the cosigner check is specifically meant to prevent (as demonstrated by its enforcement in the `ifRemote` branch).

### Likelihood Explanation
Reachable directly from any paired device — no special privileges, hub compromise, or node/peer trust needed, matching the "paired device can reach" scope. Any existing correspondent (including one added for unrelated purposes, e.g. a low-trust contact) can send a crafted `"sign"` device message; the structural validation earlier in the handler is easily satisfied by any actor who knows one of the wallet's addresses and a plausible signing path (both are often observable from prior payment interactions or from being a cosigner on other addresses).

### Recommendation
Restore/enable the cosigner authorization check in the `ifLocal` branch analogous to the one already implemented in `ifRemote`: before calling `callbacks.ifOk()` and emitting `"signing_request"`, verify that `from_address` is actually a listed cosigner/device for `body.address` (e.g., query `wallet_signing_paths`/`shared_address_signing_paths` for `from_address`), and reject with `callbacks.ifError("sender is not cosigner of this address")` otherwise. For addresses with no cosigning relationship to `from_address` at all (e.g., pure single-sig wallet addresses), the request should be rejected outright.

### Proof of Concept
1. Attacker device A is a correspondent of victim device V (any paired device relationship — does not need to be a cosigner of any of V's addresses).
2. A learns one of V's single-sig addresses `ADDR` (e.g., from a previous invoice/payment).
3. A sends V a device message: `{"subject":"sign","body":{"address":"ADDR","signing_path":"r","unsigned_unit": <attacker-crafted payment unit>}}`.
4. `handleMessageFromHub` → `findAddress("ADDR","r", ...)` resolves `ifLocal` because `ADDR` is one of V's own `my_addresses`.
5. Because the cosigner check is commented out, `callbacks.ifOk()` fires immediately and `"signing_request"` is emitted with the attacker's unit, presenting V with a signing prompt that appears to originate from a legitimate request flow, despite A having no authorization to request signing on `ADDR`.
