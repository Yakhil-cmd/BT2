### Title
Hand-rolled YAML frontmatter parser silently drops indented top-level keys, downgrading `action: block` rules to no-op/warn - (File: plugins/hookify/core/config_loader.py)

### Summary
`extract_frontmatter` implements a minimal, hand-rolled YAML subset parser that only recognizes a top-level key when it has exactly zero leading whitespace (`indent == 0`). Any top-level key such as `action: block` or `enabled: true` that is indented by even a single space or tab (e.g. via copy-paste, editor auto-indent, or an attacker deliberately hiding it in a PR diff) is silently discarded with no error, causing `Rule.from_dict` to fall back to its insecure defaults (`action='warn'`, i.e., non-blocking).

### Finding Description
`extract_frontmatter` (plugins/hookify/core/config_loader.py:87-195) manually tokenizes the frontmatter block line by line. The only branch that records a top-level `key: value` pair requires `indent == 0` [3](#0-2) . If a line carrying `action: block` (or `enabled: true`) has any leading whitespace, none of the branches match it:
- The `indent == 0` branch is skipped.
- The list-item branch requires `stripped.startswith('-')`, which a `key: value` line does not satisfy.
- The dict-continuation branch requires `in_dict_item` to be `True`, which is only set when a `- key: value` list item was previously started.

As a result the line is silently ignored — not merged into any list, not recorded as a key — and the key vanishes from the returned `frontmatter` dict [4](#0-3) . `Rule.from_dict` then falls back to `frontmatter.get('action', 'warn')` [5](#0-4) , producing a `Rule` whose `action` is `'warn'` even though the file visually states `action: block`. `RuleEngine.evaluate_rules` treats non-`'block'` actions as `warning_rules`, which only attach a `systemMessage` and allow the tool call to proceed, instead of `blocking_rules`, which deny the tool call via `permissionDecision: deny` [6](#0-5) . `load_rule_file`/`load_rules` perform no schema validation against a real YAML parser and print no warning for this specific silent-drop case (the only warning is for entirely missing frontmatter) [7](#0-6) .

This breaks the reviewer/enforcement trust boundary: a `.claude/hookify.*.local.md` rule file merged via PR can visually read as a strict blocking rule (`action: block`), and pass human review, while the actual runtime-loaded `Rule` silently behaves as warn-only — with no error, exception, or log line indicating the discrepancy.

### Impact Explanation
Rules in `.claude/hookify.*.local.md` are the mechanism by which this plugin blocks dangerous `Bash`/`Write`/`Edit` operations (e.g. `rm -rf`, credential exfiltration commands, etc.). If such a rule is silently downgraded from block to warn due to a single stray leading whitespace character on the `action:` line, a dangerous tool call that was believed to be hard-blocked instead executes with only a cosmetic warning message shown to the user. This is a policy-enforcement/trust-boundary bypass: the deny-means-deny invariant of the hookify enforcement layer is violated without any observable error.

### Likelihood Explanation
The precondition is limited to being able to add or modify a `.claude/hookify.*.local.md` file (via PR merge or a pre-seeded rule file in a repo checkout), which the audit scope explicitly allows. The triggering condition — a single leading space or tab before a top-level frontmatter key — is trivial to introduce accidentally (editor auto-indent, copy-paste from an indented YAML example) or deliberately, and is easy to overlook in a code review since indentation differences of one character are subtle, especially inside a frontmatter block that legitimately contains indented list/dict content (e.g. `conditions:` items). No validation step in `load_rule_file`/`load_rules` would catch or warn about this specific case.

### Recommendation
Replace the hand-rolled parser with a real YAML parser (e.g. `yaml.safe_load`) for the frontmatter block, or at minimum add strict validation after parsing: assert that the required keys (`action`, `enabled`) are present in the resulting dict and that `action` is one of the expected literal values (`warn`/`block`); if a required key is unexpectedly absent while the raw frontmatter text contains a differently-indented occurrence of that key (detectable via a simple regex sanity check `re.search(r'^\s*action\s*:', frontmatter_text, re.M)`), fail loudly (raise/log and skip loading the rule) rather than silently defaulting to `warn`.

### Proof of Concept

name: block-rm
