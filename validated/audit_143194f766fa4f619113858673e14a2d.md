Based on my investigation, I found a concrete analog: when `objAsset.issued_by_definer_only === true` (line 2370), the double-spend query's `doubleSpendWhere` (line 2360-2373) omits the `AND address=?` clause entirely — the query only filters on `type='issue' AND denomination=? [AND serial_number=?]`, with no address constraint. This means `checkForDoublespends` (validation.js:1661) can return a conflicting row whose `address` differs from the current unit's authors, which directly hits the unconditional assertion-style `throw Error("conflicting "+type+" spent from another address?")` at validation.js:1673 — an uncaught exception inside async DB callback code that is not routed through any `callback(err)` path.

### Title
Reachable assertion/crash in `checkForDoublespends` via issue-input double-spend on `issued_by_definer_only` assets - (File: validation.js)

### Summary
An attacker who posts two conflicting units carrying `issue` inputs for the same `issued_by_definer_only` asset, denomination and serial number, but signed by different authors, triggers an unconditional `throw Error(...)` inside `checkForDoublespends`, crashing the node process.

### Finding Description
`validatePaymentInputsAndOutputs` builds the double-spend detection query for `issue` inputs at [1](#0-0) . When the asset is `issued_by_definer_only`, the code intentionally skips adding `AND address=?` to `doubleSpendWhere` (the `if (objAsset && !objAsset.issued_by_definer_only)` guard at line 2370 is false), because for such assets only the definer address can issue, so the code assumes the address is always consistent.

However, `checkForDoublespends` at [2](#0-1)  unconditionally computes `arrAuthorAddresses` from the *currently validated* unit and asserts that every conflicting row returned by the query has an `address` present in that list; if not, it throws `Error("conflicting "+type+" spent from another address?")`. This throw is not wrapped in a `try/catch` reachable by the validation callback chain — it propagates up through the `conn.query` callback and `async.eachSeries` iterator, becoming an uncaught exception.

Because the SQL for `issue` double-spends on `issued_by_definer_only` assets has no `address` filter, a second, differently-authored unit that issues with the same `denomination`/`serial_number` for the same asset will be returned as a "conflicting" row whose `address` is the *other* author's address — not present in the current unit's `arrAuthorAddresses` — hitting the throw directly (bypassing even the `conf.bLight`/graph-based logic below it).

### Impact Explanation
An uncaught exception thrown during unit validation is not caught by the validation `try/catch` scaffolding in `validate()` (validation.js), and propagates to Node's `process.on('uncaughtException', ...)` handler in [3](#0-2) , which explicitly re-throws to crash the process ("throw err; // crash the process to avoid ending up in an inconsistent state"). Any full node (hub/witness) processing a posted unit or catching up on the DAG that reaches this code path is taken down — a network-wide denial of service: nodes are "unable to confirm new units" once this unit propagates, satisfying the "network unable to confirm new units" impact criterion.

### Likelihood Explanation
Reaching this code requires only posting two ordinary units (not requiring any privileged role) that both issue the same `issued_by_definer_only` asset with identical `denomination`/`serial_number` but from different signing authors — something any unprivileged unit poster can construct once such an asset is defined (asset definitions with `issued_by_definer_only: true` are a standard, commonly used oscript feature). This makes the trigger low-effort and fully attacker-controlled.

### Recommendation
Always include the `address` (or definer address) constraint in the `doubleSpendWhere` clause for `issue` inputs regardless of `issued_by_definer_only`, or replace the unconditional `throw` in `checkForDoublespends` (validation.js:1673) with a graceful `cb2(error)`/`callback(err)` path so unexpected address mismatches result in unit rejection rather than a process crash.

### Proof of Concept
1. Define (or use) an asset `A` with `issued_by_definer_only: true`, `fixed_denominations: false`, no `cap` (or `cap` such that serial_number checks pass), authored by definer address `D`.
2. From address `D` (definer), post unit `U1` that issues asset `A`, `denomination` `X`, `serial_number` `1`.
3. From a second, different address `E` that is also permitted to post (e.g., as `issued_by_definer_only` is only checked for the *issuer*, but validation of address-per-author at line 2338 still requires `E` to be an author of its own unit) — craft `U2` also issuing asset `A` with the same `denomination` `X` and `serial_number` `1`, authored solely by `E`. `objAsset.issued_by_definer_only` will fail this unit for the wrong issuer at line 2110 ("only definer can issue this asset") **unless** validated before reaching `checkInputDoubleSpend`. (Note: full confirmation that `E`'s issuance actually reaches `checkInputDoubleSpend` before the "only definer can issue" check requires re-reading `validatePayment`'s ordering at validation.js:2109-2111, which occurs before `validatePaymentInputsAndOutputs`, so `E`'s own issuance would likely be rejected earlier — this weakens confidence in a two-different-author PoC and needs verification with a full Devin session.)

**Confidence note:** I was not able to fully trace whether `validatePayment`'s earlier `issued_by_definer_only` / `issuer_address` check (validation.js:2109-2111) prevents a non-definer address from ever reaching the vulnerable `checkInputDoubleSpend` path for `issue` inputs, which is necessary to conclusively prove the address-mismatch trigger. A background Devin session with the full codebase and ability to run the validation logic against constructed test units would be needed to confirm reachability precisely (e.g. via re-issuance under multi-authoring where `input.address` differs from `objAsset.definer_address` isn't blocked earlier, or via a race/second-issuance scenario for a definer address itself that changed via `address_definition_change` between the two conflicting units). Given the index-size limitations of this tool, I recommend starting a full Devin session to execute `validation.validate` against two crafted joints to empirically confirm or refute this exact crash path before treating it as fully proven.
