The claim in the audit prompt about `StackStxOp::check` is technically accurate but incomplete on root cause — the real gap is broader than a missing "key ownership" check inside `check()`. I traced the full path and confirmed a genuine, reproducible issue.

### Title
Spoofed `sender` in burnchain `StackStxOp` + stacker-agnostic pox-4 `signer-key-authorizations` lets an attacker lock a victim's STX under a signer key the victim never approved - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`StackStxOp::check` (stack_stx.rs:412-416) only validates that `signer_key` deserializes to a valid secp256k1 key; the `sender` field of a `StackStxOp` is populated purely from the Bitcoin output address embedded in the preceding `PreStxOp` [1](#0-0) , with no Stacks-key signature ever required. Combined with pox-4's `signer-key-authorizations` map, which is keyed only by `(pox-addr, period, reward-cycle, topic, signer-key, auth-id, max-amount)` and is never bound to the stacking principal [2](#0-1) , an attacker can register an authorization for a key they own and then submit a burnchain `StackStxOp` claiming `sender = victim`, causing the victim's real STX balance to be locked under the attacker's signer key.

### Finding Description
Broken equality: `signer-key associated with a stacker's locked STX` == `signer-key that stacker (or their delegate) actually selected/consented to`.

Path:
1. `PreStxOp::parse_from_tx` sets `output` to whatever Bitcoin address appears in the first output of the attacker's own Bitcoin transaction, converted to a `StacksAddress` [3](#0-2) . This requires no signature from the corresponding Stacks/Bitcoin private key — the attacker only needs to pay BTC *to* that hash160, not control it.
2. `StackStxOp::parse_from_tx` inherits that spoofable `sender` unchanged [1](#0-0) , and `StackStxOp::check` only validates `signer_key` format, never that it was chosen by `sender` [4](#0-3) .
3. `process_stacking_ops` executes `stack-stx` in pox-4 using `sender` as `tx-sender`, and always passes `signer-sig = none` for burn ops (the wire format has no room for a 65-byte signature) [5](#0-4) .
4. Because `signer-sig` is `none`, `verify-signer-key-sig`/`consume-signer-key-authorization` falls back to checking `signer-key-authorizations`, a map the attacker can pre-populate for their *own* key via `set-signer-key-authorization` (which only checks that the caller's principal matches `hash160(signer-key)`, not that they match the future stacker) [6](#0-5) [7](#0-6) .
5. `stack-stx` then only checks `(>= (stx-get-balance tx-sender) amount-ustx)` — i.e., the *victim's* real balance — and locks it under the attacker's signer key [8](#0-7) .

Exploit flow: attacker calls `set-signer-key-authorization` for their own key/pox-addr/period/cycle/auth-id/max-amount; crafts a `PreStxOp` whose Bitcoin output hash160 equals the victim's Stacks address hash160; crafts the matching `StackStxOp` with `stacked_ustx <= victim_balance`, `signer_key = attacker_key`, `num_cycles/max_amount/auth_id` matching the pre-registered authorization, `reward_addr` matching the authorized pox-addr. No victim signature, private key, or consent is ever required.

Existing guards don't stop this: `check()` never checks sender/key correlation; `verify-signer-key-sig`/`consume-signer-key-authorization` verify only that the *authorization creator* owns the key, not that the *stacker* consented to it; `stack-stx`'s balance/state asserts operate on the spoofed `tx-sender` and pass as long as the victim isn't already stacking/delegating with sufficient balance.

### Impact Explanation
The victim's STX get locked (and later automatically unlock back to the victim — no principal is permanently lost), so this is not unbacked minting/permanent freezing. What is stolen/misappropriated is **signing weight**: the attacker's signer key is credited with a reward-set slot backed entirely by the victim's locked STX, at zero locked-capital cost to the attacker. This matches the "High" category ("temporary freezing of staked funds," "signing weight or reward slots exceeding locked value," "an unsigned stacking action") rather than "Critical," since no STX/sBTC is stolen or permanently frozen. It is repeatable against any address with a spendable STX balance that is not already stacking or delegating, for as many reward cycles/pox-addrs as the attacker sets up authorizations for.

### Likelihood Explanation
Preconditions: victim must not currently be in `stacking-state` or delegating, and must hold `>= stacked_ustx` unlocked STX. Attacker cost is minimal — a self-issued `set-signer-key-authorization` call plus a normal Bitcoin transaction spending only the attacker's own UTXOs (PreStxOp + StackStxOp). No cycle-phase-specific guard (e.g., `verify-not-prepare-phase`) exists in pox-4 to block this (that check only exists in pox-5.clar for `signer-manager`-related bonding functions, not `stack-stx`). This is fully feasible for an unprivileged attacker and repeatable per victim/cycle.

### Recommendation
Bind `signer-key-authorizations` (and the signature message in `get-signer-key-message-hash`) to the specific stacking principal (`stacker`/`tx-sender`), not just to `(pox-addr, period, reward-cycle, topic, signer-key, auth-id, max-amount)`. Additionally, require that burnchain-hosted `StackStxOp`/`PreStxOp` `sender` be provably tied to the corresponding Stacks private key (e.g., require a companion signed Stacks transaction, or deprecate the trustless Bitcoin-derived `sender` path for pox-4+) so that `sender` cannot be set to an arbitrary victim address without their cooperation.

### Proof of Concept
Rust test plan (in `stackslib/src/chainstate/stacks/boot/pox_4_tests.rs` style, using `prepare_pox4_test`):
1. Fund `victim` account with unlocked STX above the stacking minimum; do not have `victim` sign any transaction.
2. As `attacker`, submit `set-signer-key-authorization` with `signer-key = attacker_pubkey`, chosen `pox_addr`, `period`, `reward_cycle = current`, `topic = "stack-stx"`, `max_amount`, `auth_id`.
3. Construct a `PreStxOp` with `output = victim_stacks_address` (do not sign anything with victim's key) and a matching `StackStxOp` with `sender` inherited as `victim_stacks_address`, `signer_key = attacker_pubkey`, `stacked_ustx <= victim_balance`, `num_cycles/max_amount/auth_id` matching step 2, `reward_addr` matching the authorized `pox_addr`. Mine both ops via `test_burn_block`.
4. Assert equality before: `get-stacker-info(victim) == none` and `reward-set entry.signer == none` for victim's slot.
5. Assert equality after processing: `get-stacker-info(victim)` shows `victim`'s STX locked, but the reward-cycle's PoX reward-set entry's `signer` field equals `attacker_pubkey` (not any key `victim` chose), confirming the signer-key credited with reward-slot weight diverges from the STX owner's consent, while `victim` never signed a `stack-stx`/`set-signer-key-authorization`/`verify-signer-key-sig` transaction.

impl StackStxOp {
    pub fn check(&self) -> Result<(), op_error> {
        if self.stacked_ustx == 0 {
            warn!("Invalid StackStxOp, must have positive ustx");
            return Err(op_error::StackStxMustBePositive);
        }

        if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
            warn!(
                "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
                self.num_cycles, POX_MAX_NUM_CYCLES
            );
        }

        // Check to see if the signer key is valid if available
        if let Some(signer_key) = &self.signer_key {
            Secp256k1PublicKey::from_slice(signer_key.as_bytes())
                .map_err(|_| op_error::StackStxInvalidKey)?;
        }

        Ok(())
    }

;; This function does two things:
;;
;; - Verify that a signer key is authorized to be used
;; - Updates the `used-signer-key-authorizations` map to prevent reuse
;;
;; This "wrapper" method around `verify-signer-key-sig` allows that function to remain
;; read-only, so that it can be used by clients as a sanity check before submitting a transaction.
(define-private (consume-signer-key-authorization (pox-addr { version: (buff 1), hashbytes: (buff 32) })
                                                  (reward-cycle uint)
                                                  (topic (string-ascii 14))
                                                  (period uint)
                                                  (signer-sig-opt (optional (buff 65)))
                                                  (signer-key (buff 33))
                                                  (amount uint)
                                                  (max-amount uint)
                                                  (auth-id uint))
  (begin
    ;; verify the authorization
    (try! (verify-signer-key-sig pox-addr reward-cycle topic period signer-sig-opt signer-key amount max-amount auth-id))
    ;; update the `used-signer-key-authorizations` map
    (asserts! (map-insert used-signer-key-authorizations
      { signer-key: signer-key, reward-cycle: reward-cycle, topic: topic, period: period, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount } true)
      (err ERR_SIGNER_AUTH_USED))
    (ok true)))
