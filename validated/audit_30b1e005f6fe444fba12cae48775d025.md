## Title
Duplicate-operator weight double-counting bypasses multisig threshold in Axelar bridge `validate_proof` - (File: `crates/sui-axelar-cgp/move/sources/validators.move`)

### Summary
`transfer_operatorship` accepts a new operator set without verifying that operator addresses are sorted/unique — the `_isSortedAscAndContainsNoDuplicate` check is explicitly left as a TODO. This is the same root-cause class as the `AFiManager.updateProportion` bug: an aggregate accounting value (total proportion / total weight) is trusted to be well-formed without validating the per-element inputs that compose it, allowing the invariant "each unit of weight maps to one distinct operator" to be silently broken.

### Finding Description
In `transfer_operatorship`, the module computes `total_weight` by summing `new_weights` and only checks `total_weight >= new_threshold` and `new_threshold != 0`: [1](#0-0) 

The comment on line 134 explicitly acknowledges the missing duplicate/sort check: [2](#0-1) 

Because this check is missing, an operator set containing the same public-key address multiple times (with arbitrary weights assigned to each duplicate slot) can be registered as the active operator set for an epoch.

Later, `validate_proof` walks the `signatures` vector and, for each signature, recovers the signer and scans forward through `operators` to find a match, adding that slot's weight to the running total: [3](#0-2) 

Because `operator_index` only moves forward (it is never reset, and a matched index is skipped over on the next iteration), a single real private key that appears at two or more positions in `operators` can produce two or more *distinct signatures over the same `approval_hash`* (ECDSA signatures are non-deterministic unless RFC6979 is enforced, and even with deterministic signing, `normalize_signature` doesn't prevent supplying the same signature bytes twice — the loop only requires `signed_by` to match the next occurrence of that address in `operators`, and the same signature bytes recovered twice will simply match the next duplicate slot). This lets an attacker with **one key** consume multiple weight slots belonging to the same duplicated operator, inflating `weight` far past what the honest key count/stake actually represents, and reach `threshold` without the true 2/3 (or configured) quorum of distinct operators.

### Impact Explanation
`validate_proof` gates `add_approval`/`take_approved_call`, which are used to authorize arbitrary cross-chain message execution through the Axelar bridge integration on Sui (channel-based call approval). If the operator/threshold quorum check can be satisfied by fewer real signers than intended (down to a single colluding or compromised operator holding a duplicated slot), an attacker can forge approval for arbitrary payloads/messages that the bridge will treat as validly quorum-approved. This is a verifier/threshold bypass chained directly to fraudulent message approval, which is analogous to "bridge message forgery... that enables illegitimate mint or unlock" in the allowed Critical impact list, since approved calls can trigger token mint/unlock style actions in downstream Axelar-integrated contracts.

### Likelihood Explanation
Triggering requires: (1) the `transfer_operatorship` payload to have been accepted with a duplicate operator — this itself requires whoever authorizes operatorship transfer (documented as validated externally / via governance in the Axelar model, not attacker-controlled `ctx.sender()` gating within this module) to submit a malformed operator set, and (2) collection of two-plus valid signatures from the one duplicated key over the same hash. Item (1) is the actual root cause exploited here and is a missing-input-validation bug reachable through the normal operatorship-transfer flow (the function itself performs no caller-privilege check in the shown code — only the payload is validated), so it is reachable without additional "malicious governance quorum" assumptions if the same duplicate-set weakness is exploitable by whoever can submit an operatorship-transfer payload (e.g., if this function is itself gated by a `validate_proof` from a previous state, this becomes self-reinforcing/compounding rather than a one-off admin action). I could not fully verify, within the available indexed code, the exact caller/permission wiring for `transfer_operatorship` (i.e., whether it is called only from a channel that itself required a previously-validated proof) — this repository slice does not show the full calling module. This limits confidence that this is reachable purely by an "ordinary unprivileged caller" versus only by whoever already controls a previous quorum, so likelihood should be treated as **uncertain/Medium-to-High** pending that confirmation.

### Recommendation
Implement the missing `_isSortedAscAndContainsNoDuplicate` check in `transfer_operatorship` to reject operator vectors containing duplicate addresses (and enforce strict ascending order as in the original Solidity `AxelarAuthWeighted` reference implementation), matching the intent of the `EDuplicateOperators` error code that already exists but is never asserted: [4](#0-3) 

Additionally, in `validate_proof`, uncomment/enforce the currently disabled malformed-signer check to abort when a signature does not match any remaining operator, and consider tracking consumed indices explicitly rather than relying on monotonic scanning, to avoid any residual double-counting even with valid unique operator sets.

### Proof of Concept
1. Craft a `transfer_operatorship` payload with `new_operators = [A, A]`, `new_weights = [w, w]`, `new_threshold = w + 1` (assume real single-signer weight is `w`, and true policy intends 2 independent signers each weighted `w`, needing `2w` combined, i.e., threshold `w+1` would normally require both distinct operators).
2. Since `total_weight = 2w >= threshold`, and no duplicate/order check exists, the payload passes `transfer_operatorship` validation and becomes the active operator set for the new epoch.
3. To later call `validate_proof`, the holder of key `A` produces two signatures over the same `approval_hash` (e.g., using non-deterministic ECDSA, generating two different valid `(r,s)` pairs, or simply supplying the identical signature bytes twice — both recover to address `A`).
4. In the `validate_proof` loop, the first signature matches `operators[0] == A`, adding weight `w`; `operator_index` advances to 1. The second (identical or alternate) signature is compared against `operators[1] == A`, matches, adds another `w`. Total `weight = 2w >= threshold`, and the function returns `true` — despite only one real operator key having signed.
5. This forged "quorum" approval is then used to `add_approval`/`take_approved_call` an arbitrary payload, which downstream Axelar-integrated Sui modules will treat as validly authorized by the multisig committee.

Note: full exploitability depends on confirming (a) that `validate_proof`/`transfer_operatorship` can be invoked with operator sets not independently verified by an off-chain quorum before submission, and (b) that duplicate signature bytes or non-deterministic ECDSA signing are actually accepted by `secp256k1_ecrecover`/`normalize_signature` without additional replay protection — these could not be fully confirmed from the indexed code alone, so this should be validated with a live Move test before treating as fully confirmed Critical.
