### Title
Asset metadata `name`/`suffix` fields accept RIGHT-TO-LEFT OVERRIDE and other unicode control characters, enabling ticker/asset-name spoofing - (File: wallet.js)

### Summary
`fetchAssetMetadata`/`readAssetMetadata` in `wallet.js` store and display an asset's display `name` (and `suffix`) that is taken verbatim from a `data` message payload posted by any address acting as a "registry" for that asset. No Unicode sanitization is performed, so a malicious registry (or any user acting as author of the metadata unit) can embed a RIGHT-TO-LEFT OVERRIDE (U+202E) or other bidirectional-control characters inside the `name`, causing wallets that render this string to display a visually different/reversed asset name (e.g., masking a scam-token's real identifier so it displays as a trusted ticker), directly mirroring the Minio RTLO advisory's masking-of-original-name issue.

### Finding Description
`fetchAssetMetadata()` reads a `data` message posted by `registry_address` and copies `payload.name` (and `suffix`) directly into `asset_metadata.name`/`suffix` with only a truthiness check: [1](#0-0) 
No length/character-set validation is applied to `payload.name` (unlike `feed_name`/data-feed values elsewhere in the codebase, which explicitly reject characters such as `\n`, see `validation.js` data-feed handling), and there is no check against directionality-override or zero-width Unicode code points. [2](#0-1) 
The resulting name is later composed for user-facing display (e.g., ticker rendering combining `name` + `.` + `suffix`) without sanitization: [3](#0-2) 
Because `registry_address` is only checked to equal the metadata unit's author address (any address can self-register as a "registry" for an asset it does not otherwise control the semantics of), an attacker can create an asset and immediately post metadata that uses RTLO/Unicode tricks in the `name` field so that wallets/exchanges display it as if it were a different, trusted asset's ticker (e.g., an attacker's asset appears with a reversed or visually-confusable name matching "GBYTE" or another well-known token).

### Impact Explanation
A user paying, verifying, or trusting a displayed asset name may be tricked into sending funds to, or accepting, the wrong asset because the rendered ticker/name is spoofed via bidirectional-override characters — the same "masking the original name to trick a user" impact class as the reported Minio advisory. This can lead to concrete unauthorized spending/loss of funds when a user selects or approves a payment based on the spoofed displayed name, satisfying the "concrete unauthorized spending" bar for a Medium-severity issue. Reachable entirely by an unprivileged asset issuer posting a normal `asset` + `data` (registry) message pair — no privileged, network, or peer-trust bypass is required.

### Likelihood Explanation
Any address can issue an `asset` unit and immediately post a `data` message where it is its own `registry_address` for that asset (the only check is `objJoint.unit.authors[0].address === registry_address`), making the attack trivially and repeatably reachable by any wallet user without special privileges.

### Recommendation
Sanitize `name`/`suffix` fields at ingestion time in `fetchAssetMetadata()` (and in any validation path that accepts `data`-app payloads used as asset metadata): reject/strip Unicode bidirectional control characters (U+202A–U+202E, U+2066–U+2069), zero-width characters, and non-printable characters; enforce a restricted charset (e.g., alphanumerics, `.`, `-`, `_`) similar to the character-class restrictions already used for merkle elements in `definition.js` (`element.match(/^[\w ~,.\/\\;:!@#$%^&*\(\)=+\[\]\{\}<>\?|-]{1,100}$/)`).

### Proof of Concept
1. Attacker issues a new `asset` unit (any address can do this).
2. Attacker's own address posts a `data` message on a metadata unit with `registry_address` = itself and payload `{ asset: <attacker_asset>, name: "GBYTE\u202E...", decimals: 9 }`.
3. Any wallet calling `readAssetMetadata`/`fetchAssetMetadata` stores this unsanitized `name` and later renders it in balance/payment UIs, producing a visually spoofed ticker that can mislead a user into trusting or transacting with the wrong asset. [4](#0-3)
