### Title
Uncaught exception in c-hash length validation causes remote node crash / DoS - (File: chash.js)

### Summary
`chash.isChashValid()` decodes an attacker-supplied base32/base64 "c-hash" string and then calls `separateIntoCleanDataAndChecksum()`, which `throw`s a raw `Error` if the decoded bit-length is not exactly 160 or 288. Only the *decode* step is wrapped in try/catch; the subsequent length-validation throw is not, so a crafted address/asset chash of the correct *string* length but malformed encoding can trigger an unhandled exception deep inside address/asset validation that is invoked on every incoming, unauthenticated unit. [1](#0-0) 

### Finding Description
`isChashValid(encoded)` first checks the string length is 32 or 48 characters, then decodes it: [2](#0-1) 

For 48-character inputs it uses `Buffer.from(encoded, 'base64')`. Node's base64 decoder is permissive — invalid characters are silently dropped rather than raising an error — so a 48-character string containing invalid base64 characters can decode to a buffer whose bit-length, after `buffer2bin()`, is neither 160 nor 288 bits. [3](#0-2) 

That mismatched length is then passed to `separateIntoCleanDataAndChecksum()`: [4](#0-3) 

which throws `Error("bad length=...")` outside of the `try { ... } catch(e) { return false; }` block that only wraps the decode call: [5](#0-4) 

This is the JS analogue of the CVE-2017-11608 bug class: a lexing/decoding routine that fails to validate the effective length of attacker-controlled data before it is consumed by a downstream routine that assumes a fixed length, resulting in an out-of-contract state (buffer over-read in C/C++; unhandled `throw` in JS) reachable purely by supplying crafted network input.

`isChashValid` is reached from `isValidChash` / `isValidAddress` / `isValidAddressAnyCase` in `validation_utils.js`, which are used pervasively during unit/message validation (author addresses, definition-referenced addresses, asset issuer/definer addresses, payment output addresses, AA addresses) — all of which are populated straight from a posted unit's JSON payload before any other sanitization occurs. [6](#0-5) 

Because `isValidAddress`/`isValidChash` is called synchronously in many places without a wrapping try/catch (validation.js's various address checks call these predicates directly as boolean conditions, not inside try blocks), an exception thrown from `isChashValid` propagates up the call stack as an uncaught synchronous exception inside a network message handler.

### Impact Explanation
If this exception is not caught by a top-level `try/catch` around the unit/joint validation dispatcher, it becomes an uncaught exception in the Node.js event loop, crashing the hub/full node process. Since it is triggered merely by receiving a unit or message containing a crafted 48-character asset/definition-chash string with invalid base64 characters, a single unprivileged peer can remotely crash any node that validates the unit — a network-wide denial of service preventing confirmation of new units, matching the required impact bar ("a network unable to confirm new units").

### Likelihood Explanation
Likelihood is Medium: the string-length gate (`isStringOfLength(str, len)`) restricts inputs to exactly 32 or 48 characters, so the attacker must specifically choose the 48-character (`isValidBase64`, HASH_LENGTH) codepath used for asset/definition chashes (not the 32-character `base32` address codepath, whose decoder is typically stricter about alphabet). Constructing a 48-character base64-ish string that (a) passes any `isValidBase64` pre-check used at the call site (if present) and (b) decodes via `Buffer.from(x,'base64')` to a byte length other than 36 bytes requires some experimentation with Node's lenient base64 decoding rules, but is fully within reach of a scripting attacker with no special privileges — they only need to post a unit or AA/asset definition referencing the crafted chash.

### Recommendation
- Wrap the entire body of `isChashValid()` (including the calls to `buffer2bin`, `separateIntoCleanDataAndChecksum`, and `getChecksum`) in the existing try/catch, returning `false` on any thrown error instead of only covering the decode step.
- Alternatively/additionally, explicitly verify `chash.length` (in bytes, post-decode) equals the expected 20 or 36 bytes before calling `separateIntoCleanDataAndChecksum`, returning `false` early rather than relying on that function's internal `throw`.
- Add defense-in-depth by ensuring all unit/message validation entry points (`validation.js`) wrap per-field validators in try/catch so that any single malformed field cannot crash the whole node process — this generalizes protection against similar unchecked-length parsing bugs elsewhere in the codebase.

### Proof of Concept
1. Craft a 48-character string `S` consisting mostly of valid base64 alphabet characters but containing a small number of characters that Node's `Buffer.from(x, 'base64')` decoder treats as invalid/ignorable (e.g. certain non-base64 symbols), such that the resulting decoded buffer length in bits is not 288 (and not 160, since it went through the 48-char/base64 branch which never produces the 160-bit path). Node.js historically drops such characters, shifting the padding calculation and yielding a truncated byte buffer.
2. Use `S` as the `asset` field of a `payment` message, or as a `definition_chash`/address-in-definition field, in a unit posted to a node (e.g., via `hub`/`network.js` `handleJoint`, or via AA/asset validation paths in `aa_validation.js` / `definition.js` that call `isValidBase64(asset, constants.HASH_LENGTH)` and eventually `isValidChash`/`isChashValid`).
3. Observe that `separateIntoCleanDataAndChecksum` throws `Error("bad length=...")`, which is not caught by `isChashValid`'s try/catch (only the decode line is wrapped), propagating to the caller.
4. If no enclosing try/catch exists further up the validation call chain for that specific field, the process crashes with an uncaught exception, demonstrating the remote DoS.
