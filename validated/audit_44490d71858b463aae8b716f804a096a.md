### Title
Webhook signature is verified against the organization in `repository.owner.login`, but the stack that is actually mutated is looked up by the unrelated `repository.full_name` field, allowing cross-organization forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
The bug class in the external report is a binding mismatch: the value used to gate/authorize an action differs from the value the action actually operates on. In `Shrine`, the LTV that gates liquidation is derived from a global metric an attacker can inflate, decoupling "what protects a trove" from "what actually happens to that trove." The same class of flaw exists in Shipit's webhook trust boundary: the field used to select the HMAC secret for signature verification (`repository.owner.login`) is not the same field used to resolve which `Stack`/`Repository` the webhook payload acts on (`repository.full_name`). Because the HMAC covers the raw JSON body but Shipit never cross-checks that the two fields agree, a party who legitimately controls the webhook secret for *one* GitHub organization onboarded into a shared Shipit instance can forge a signed payload whose `repository.full_name` points at a *different* organization's repository/stack.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/secret to verify against using only the repository owner login: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Once the signature is accepted, the actual event `params` (the *entire* attacker-controlled JSON, since only `repository.owner.login` was used to pick the verification key) are dispatched to handlers, all of which resolve the target `Stack` from a **different** field, `repository.full_name`: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`Repository.from_github_repo_name` splits `owner/name` straight out of that field with no relation back to `repository.owner.login`: [4](#0-3) 

Handlers such as `PushHandler`, `StatusHandler`, and `CheckSuiteHandler` then perform real, mutating actions on whatever stack `repository.full_name` resolves to: [5](#0-4) [6](#0-5) 

Nothing in the pipeline asserts `repository.full_name.split('/').first == repository.owner.login`. So: the equality the system implicitly relies on is
`organization authenticated (repository.owner.login) == organization written (repository.full_name.split('/').first)`,
and this equality is never enforced.

Shipit natively supports multiple GitHub Apps/orgs configured with independent webhook secrets in one deployment (`Shipit.github(organization:)`, demonstrated by `test/dummy/config/secrets_double_github_app.yml`). In that documented multi-tenant configuration, a legitimate integrator of Org A (who knows Org A's own webhook secret because they configured Org A's GitHub App) can:
1. Sign a webhook body with Org A's secret (valid, legitimate credential for Org A).
2. Set `repository.owner.login` = `"OrgA"` (so `verify_signature` looks up and validates against Org A's real secret — passes).
3. Set `repository.full_name` = `"OrgB/target-repo"` (a stack belonging to a different tenant).

The signature check passes because it only validates the raw bytes against Org A's secret; nothing about the payload's `repository.full_name` is constrained by that check. The handler layer then acts on Org B's stack using purely the forged `full_name`.

### Impact Explanation
This breaks the cross-repository isolation between tenants of a shared Shipit engine instance and enables **cross-repository writes** without any access to Org B:
- `push` events can force `GithubSyncJob` to run for Org B's stack with an attacker-chosen `expected_head_sha`, influencing commit ingestion/detachment logic.
- `status` events let an attacker inject a forged commit status (`create_status_from_github!`) for any commit sha known to exist on Org B's stack, which can flip `deployable?` gating used elsewhere to allow/deny deploys.
- `check_suite` events can trigger `schedule_refresh_check_runs!` against Org B's commits.

Because deploy/merge gating logic in Shipit is influenced by commit status/check state, this can be leveraged to make an otherwise-blocked commit appear deployable/mergeable for a repository the attacker has no access to — matching the "unauthorized deploy" / "cross-repository writes" impact category.

### Likelihood Explanation
Exploitability depends entirely on Shipit being configured for **multiple organizations behind one instance**, each with its own independent webhook secret (explicitly supported and documented, e.g. `test/dummy/config/secrets_double_github_app.yml`). Within that supported topology, the only credential required is knowledge of *your own* org's legitimately-issued webhook secret — no `ApiClient` token, no `webhook_secret` belonging to the victim org, no GitHub App private key of the victim, and no privileged account on the victim's side are required. This exactly fits the specified unprivileged-attacker analog ("an organization that authenticated versus the repository that is written").

### Recommendation
After verifying the HMAC signature, additionally assert that the organization used to select the verification key (`repository.owner.login` / `organization.login`) matches the owner encoded in `repository.full_name` before dispatching to handlers. Reject the webhook (422) on mismatch. Equivalently, have `Handler#repository_name`/`Repository.from_github_repo_name` scope lookups by the verified organization rather than trusting the raw `full_name` field independently.

### Proof of Concept
Given a Shipit instance configured with two GitHub Apps (`OrgA`, secret `SA`; `OrgB`, secret `SB`), where the attacker is a legitimate integrator for `OrgA` only:

```
POST /github/webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(body, SA)>

body = {
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "OrgA" },      # used only for signature-app selection
    "full_name": "OrgB/target-repo"    # used to resolve the Stack that is mutated
  }
}
```

`WebhooksController#verify_signature` computes `Shipit.github(organization: "OrgA").verify_webhook_signature(sig, body)`, which succeeds because the attacker signed with `SA`. `Shipit::Webhooks.for_event('push')` then runs `PushHandler`, whose `stacks` resolves `Repository.from_github_repo_name("orgb/target-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef")` on Org B's stack — despite the attacker never having presented any credential associated with Org B.
