### Title
Unprivileged third-party supply top-up keeps an insolvent account above the $5 dust gate, permanently blocking permissionless `clean_bad_debt` while bad debt accrues interest - (File: contracts/controller/src/positions/supply.rs)

### Summary
The Mantle oracle bug is a count that should be derived from a privileged, monotonic signal (`withdrawableEpoch`) but was instead derived from a balance anyone can push up by depositing. XOXNO Lending has the same shape: permissionless bad-debt cleanup is gated on the account's *collateral value* being at or below a $5 dust threshold, and any unprivileged address may add collateral to an existing supply position on somebody else's account. A griefer can therefore dust-top-up an insolvent account's collateral above $5, causing `clean_bad_debt` to revert with `CannotCleanBadDebt` forever while the debt keeps accruing borrow-index interest.

### Finding Description
`process_clean_bad_debt` is the permissionless cleanup path; it admits an account only when `BadDebtGate::DustCapped` holds, i.e. `is_socializable_bad_debt(totals.total_debt, totals.total_collateral)` requires insolvency **and** collateral at or below the fixed $5 threshold, reverting with `CollateralError::CannotCleanBadDebt` otherwise (`contracts/controller/src/positions/liquidation/mod.rs:196-235`).

On the supply side, `process_supply` intentionally allows third parties to add to an existing supply position on an account they do not own: `require_third_party_existing_supply` only asserts that each paid `hub_asset` already exists in `account.supply_positions` when the caller is not owner/delegate (`contracts/controller/src/positions/supply.rs:61-97`). The supplied tokens are measured and credited to the victim's position via `process_deposit`, raising `totals.total_collateral` on the next risk computation.

So for any insolvent account whose residual collateral sits at or below $5 — exactly the state `clean_bad_debt` exists to resolve — an attacker calls:

```
supply(caller=ATTACKER, account_id=VICTIM, spoke_id, assets=[(hub_asset_of_existing_collateral, amount)])
```

with `amount` just large enough to push the half-up USD collateral above $5. Every subsequent `clean_bad_debt` call reverts. If a price move or liquidation drags collateral back under $5, the attacker repeats the top-up. The attacker loses the donated tokens, so the cost is roughly `$5 - current_collateral + ε` per blocking cycle.

### Impact Explanation
Bad debt is time-sensitive: the unwritten debt keeps accruing at the borrow index, so the eventual write-down onto the market's suppliers (`remaining_ray = total_supply_ray - bad_debt_ray` in the socialization formula) grows strictly larger the longer cleanup is delayed. The attack turns a cheap, immediate keeper cleanup into either (a) a growing supplier loss while it persists, or (b) a forced escalation to the timelocked governance operation `force_socialize_bad_debt`, which the runbook itself describes as the fallback when the account sits above the permissionless threshold. This is a temporary freezing of the loss-resolution path and protocol-insolvency deepening reachable by a single unprivileged address at bounded cost — the same "attacker-controlled input corrupts a cumulative/risk gate" class as the oracle finding.

### Likelihood Explanation
- Entrypoint is fully permissionless: `supply` requires only `require_authorized_caller` (caller auth of the *payer*, not the account owner), and the third-party restriction only requires the position to already exist.
- Insolvent dust-collateral accounts are the normal terminal state of underwater positions (partial liquidations leave residual collateral; price crashes create them directly, as in the $9-collateral fixture).
- Cost is ~$5 per blocking cycle in any already-held collateral asset of the victim — cheap relative to the griefing window it buys.
- Ordinary liquidation does not fully mitigate: liquidating the dust collateral repays at most ~`collateral/(1+bonus)` of debt and does not remove the account; the attacker can re-top-up after each seizure since the position persists until cleanup deletes it.

### Recommendation
Make the dust gate depend on a signal the attacker cannot inflate, not on live collateral value. Options:
- Gate permissionless cleanup on the *debt-side* condition plus collateral **shares owned at liquidation time**, or snapshot/mark the account when it first becomes socializable and let cleanup proceed once marked.
- Alternatively, net same-market supply against debt, or let cleanup accept accounts where `total_collateral` above the threshold is entirely attributable to third-party top-ups — simplest robust fix is to disallow third-party supply to accounts that already have borrow positions (extend `require_third_party_existing_supply` to also reject when `!account.borrow_positions.is_empty()`), since topping up an insolvent borrower's collateral has no legitimate use.

### Proof of Concept
1. BOB supplies 100 ETH. ALICE supplies 8 USDC and borrows 0.002 ETH. Price crash sets USDC to $0.05 → collateral ≈ $0.40 (≤ $5), debt > collateral. `clean_bad_debt(account_id)` is now permissionlessly callable (fixture shape: `tests/test-harness/tests/controller/bad_debt_index.rs:196-220`).
2. Attacker EVE calls `supply(caller=EVE, account_id=ALICE_ACCT, spoke_id, assets=[(hub_asset(USDC), 6 USDC)])`. The position exists, so `require_third_party_existing_supply` passes (`supply.rs:86-96`); EVE's tokens are credited to ALICE's supply position.
3. Collateral is now ≈ $6.40 > $5. Any caller's `clean_bad_debt` reverts with `CannotCleanBadDebt` (`mod.rs:229-235`, matching the `#114` revert observed at `tests/integration/flows/liquidation.sh:360` for the above-threshold case).
4. Interest accrues on the 0.002 ETH debt at the borrow index. If a liquidation or price change brings collateral back under $5, EVE repeats step 2. Only governance's timelocked `force_socialize_bad_debt` can resolve the account, so each griefer cycle extends the window in which supplier losses grow.
