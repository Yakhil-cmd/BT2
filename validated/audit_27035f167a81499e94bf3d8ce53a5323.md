### Title
CCMenu API endpoint lets a stack-scoped ApiClient token read the status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the shared `stack` lookup helper from `Shipit::Api::BaseController` with an unscoped `Stack.from_param!` lookup, breaking the binding between "the stack an `ApiClient` token is authorized for" and "the stack the request actually touches."

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scoped accessors used by all API controllers: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped to a single stack, and `stack` resolves `params[:stack_id]` only within that restricted set. This is the mechanism that enforces "a stack scoped `ApiClient` token can only see that one stack," as verified in `test/controllers/api/stacks_controller_test.rb`.

`CCMenuController`, however, defines its own `stack` method that bypasses `stacks` entirely: [2](#0-1) 

It authenticates the token via `ApiClient.authenticate(params[:token])` (or Basic auth via `super`), enforces only the generic `read:stack` permission string via `require_permission :read, :stack` (checked in `ApiClient#check_permissions!`), and then resolves `stack` with the unscoped `Stack.from_param!(params[:stack_id])` instead of the inherited `stacks.from_param!(params[:stack_id])`.

`ApiClient#check_permissions!` only checks whether the permission string (e.g. `read:stack`) is present in the client's `permissions` list — it performs no check that the resolved `stack_id` matches `current_api_client.stack_id`: [3](#0-2) 

Binding that should hold: `stack_id(current_api_client) == stack_id(resource returned)`. Before the request, an `ApiClient` such as the `here_come_the_walrus` fixture is scoped to a single stack (`stack: shipit`, `permissions: [read:stack]`) as shown in the fixtures: [4](#0-3) 

After the request, `CCMenuController#show` renders `stack.deploys_and_rollbacks.last` for whatever `stack_id` param the caller supplies, regardless of `current_api_client.stack_id`, breaking the equality.

### Impact Explanation
This is an unauthenticated-scope read: the token is valid and has the `read:stack` permission, but it was only meant to authorize access to a single stack. By supplying a different `stack_id` in the URL, the same token can read the deploy/rollback status, last build label, last build time, and web URL of **any** stack in the Shipit instance — an unauthorized cross-stack read of stack state/deploy output, matching the "High - unauthenticated read of stack state, task streams or deploy output" impact category.

### Likelihood Explanation
Likelihood is high for any deployment where scoped `ApiClient` tokens are issued (e.g. via `CCMenuUrlController`, which creates a `read:stack`-scoped client for the CCMenu feature — see `app/controllers/shipit/ccmenu_url_controller.rb`). No privileged access beyond possessing one legitimately-issued, narrowly-scoped token is required; the attacker simply changes the `stack_id` route parameter.

### Recommendation
Remove the `stack` override in `CCMenuController` (or make it delegate to the inherited scoped `stacks.from_param!`) so that CCMenu lookups are constrained the same way as every other API controller:
```diff
- def stack
-   @stack ||= Stack.from_param!(params[:stack_id])
- end
+ # remove override; rely on Api::BaseController#stack which uses `stacks.from_param!`
```

### Proof of Concept
1. Obtain (or be issued) a legitimate `ApiClient` token scoped to `stack_id: A` with `permissions: [read:stack]` (e.g. the CCMenu URL feature issues exactly this kind of token via `CCMenuUrlController#client`).
2. Request `GET /api/stacks/<owner>/<other-repo>/<other-env>/cc_menu.xml?token=<the token>` where `<other-repo>/<other-env>` corresponds to stack `B`, which the token is not scoped to.
3. `authenticate_api_client` in `CCMenuController` accepts the token (valid signature), `require_permission :read, :stack` passes because the token has `read:stack` in its permissions list, and `stack` resolves to stack `B` via the unscoped `Stack.from_param!`, returning stack `B`'s deploy status XML instead of a 403/404.

Note: I could not find any test asserting cross-stack denial specifically for `CCMenuController` (only `stacks_controller_test.rb` verifies scoping for the JSON API), which is consistent with this control being missing specifically in `CCMenuController`.
