### Title
Webhook signature verification is keyed by an attacker-controlled organization field that is independent of the repository/stack the event actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the incoming payload against using `repository_owner`, a value read straight out of the untrusted JSON body. The handler that actually performs the write (creating stacks syncs, teams, memberships, etc.) resolves its target from a *different* field of the same body, `repository.full_name`, with no check that this field belongs to the organization that was used to authenticate the request. Because Shipit explicitly supports multi-organization installations where each organization's `webhook_secret` is optional, an attacker who can trigger (or simply POST) an event for an organization configured with no secret can supply a `repository`/`organization`/`team`/`member` payload that targets a *different* organization's stacks or teams, since nothing binds the two.

### Finding Description
The controller verifies the signature like this: [1](#0-0) 

`repository_owner` is derived purely from the request body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a `GithubApp`/`GithubOrganization` config for that org and calls `verify_webhook_signature`. If that particular organization has no `webhook_secret` configured, verification is a no-op: [3](#0-2) 

Shipit's own setup docs describe `webhook_secret` as **optional per organization**, and explicitly document running multiple GitHub App configs side by side, each with its own (optionally empty) secret: [4](#0-3) [5](#0-4) 

Once the request passes `verify_signature` (because the org keyed off `repository.owner.login` has no secret), every event handler resolves the actual object to mutate from a *separate* field of the same payload, with no cross-check against `repository_owner`: [6](#0-5) [7](#0-6) 

This is the binding break: `verified_organization` (org whose optional secret gated the request) is treated as equal to `target_repository.owner` (org whose `Stack`/`Team`/`Membership` the handler mutates), but nothing in the code enforces that equality — they are two independently attacker-controlled strings inside one JSON body. The `membership` event handler is the most damaging instance, since it creates `Team`/`User`/`Membership` records straight from payload fields (as exercised in the controller test suite), and team membership is exactly the mechanism `Shipit.github_teams` authorization relies on: [8](#0-7) 

### Impact Explanation
If any organization configured on the Shipit instance has no `webhook_secret` (a documented, supported configuration), an unauthenticated attacker can send a forged `membership` webhook whose `repository.owner.login`/`organization.login` matches the unsecured org (passing `verify_signature`), while the `team`/`member` fields reference a team belonging to a *different*, otherwise-protected organization. This lets the attacker add an arbitrary GitHub login to a `Team` that Shipit trusts for `Shipit.github_teams` authorization, escalating an unprivileged GitHub identity into an authorized Shipit user — a High-severity escalation as defined by the scope's impact list. The same organization/repository mismatch also lets an attacker trigger `sync_github` on push events for stacks that belong to unrelated, secured repositories.

### Likelihood Explanation
Likelihood depends entirely on whether the Shipit operator has left `webhook_secret` unset for at least one configured organization — which the project's own documentation presents as an explicit, optional, supported setting rather than a misconfiguration, so it is reasonable to expect it occurs in real multi-org deployments. No GitHub App private key, `api_clients_secret`, or session is required by the attacker; a bare HTTP POST to `/webhooks` with a crafted `X-Github-Event: membership` body directed at the unsecured organization is sufficient.

### Recommendation
Bind signature verification to the same organization that the handler subsequently acts on: after resolving `stacks`/`Team`/`Repository` from the payload, assert that its owning organization equals `repository_owner` (the value used to select the `webhook_secret`), and reject the request otherwise. Additionally, consider requiring `webhook_secret` to be present for every configured organization (removing the "optional" no-op path in `GithubApp#verify_webhook_signature`), so a single unsecured org cannot be used as a signature-verification bypass for the entire multi-org installation.

### Proof of Concept
1. Shipit is configured with two GitHub App orgs: `org-a` (no `webhook_secret` set) and `org-b` (secret set, has a Shipit `Team` used for `Shipit.github_teams` authorization).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": { "login": "org-a" },
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/whatever" },
  "team": { "id": <org-b's authorized team id>, "slug": "org-b-admins", "name": "Org B Admins", "url": "https://example.com" },
  "member": { "login": "attacker-controlled-login" }
}
```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`), regardless of the actual `X-Hub-Signature` header value.
4. `MembershipHandler` processes the event and creates/updates a `Membership` linking `attacker-controlled-login` to `org-b`'s authorized team, exactly as shown by the equivalent legitimate flow in `test/controllers/webhooks_controller_test.rb:129-165`.
5. `attacker-controlled-login` now authenticates into Shipit as a member of an authorized `Shipit.github_teams` team, despite never having been added to that team on GitHub itself.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
