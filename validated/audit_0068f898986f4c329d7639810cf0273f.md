### Title
Ralph-loop completion signal can be hijacked by attacker-controlled content reflected in assistant text, causing premature loop termination or masking of genuine completion - (File: plugins/ralph-wiggum/hooks/stop-hook.sh)

### Summary
`stop-hook.sh` extracts the completion signal by concatenating *all* text blocks of the last assistant message and then taking the **first** `<promise>...</promise>` pair found anywhere in that text via a non-greedy Perl regex. Because the extraction has no notion of "this tag must be the model's deliberate, final statement," any earlier `<promise>` tag reflected from quoted file/tool/MCP content — including the plugin's own example phrases shown to the model in `setup-ralph-loop.sh`/`help.md` — is picked up instead of (or in place of) a genuine completion signal.

### Finding Description
`LAST_OUTPUT` is built by joining every `text`-type content block of the last assistant message: [1](#0-0) 
This means any content the model quotes verbatim — file contents, tool output, MCP responses, or even the plugin's own printed instructions/examples containing `<promise>...</promise>` — is concatenated into the same string that is scanned for the completion tag.

The extraction itself is: [2](#0-1) 
`s/.*?<promise>(.*?)<\/promise>.*/$1/s` is non-greedy up to the *first* `<promise>` and non-greedy up to its *first* matching `</promise>`; the trailing `.*` greedily consumes everything after, discarding any subsequent (possibly genuine) tag. There is no check that exactly one well-formed tag exists, no anchoring to "last" or "only" occurrence, and no distinction between text the model authored intentionally versus text it echoed from an external source.

The setup script itself trains the model to reproduce the literal `<promise>` markup in its responses/prompts (e.g. `Output <promise>FIXED</promise> when all tests pass` in the recommended pattern), and prints example tags directly to the transcript: [3](#0-2) 
If the model quotes/restates this instruction, or quotes a file/tool output containing a crafted `<promise>...</promise>` (e.g., a malicious code comment, README snippet, or MCP tool response embedded in the repo an attacker controls), that tag — not the model's genuine determination — is what gets extracted and compared: [4](#0-3) 

This produces two concrete failure modes:
1. **Forced early termination**: if the attacker can predict or match the user-chosen `COMPLETION_PROMISE` string (often a short, guessable phrase like `DONE`, `FIXED`, `TASK COMPLETE` as shown in the plugin's own docs, and frequently embedded verbatim in the initial prompt/state file which the model may echo), planting `<promise>THAT_EXACT_TEXT</promise>` in repository content that the model quotes causes the loop to be stopped by attacker-controlled content rather than genuine task completion.
2. **Prevented legitimate termination**: any earlier, non-matching `<promise>...</promise>` occurrence anywhere in the reflected text (e.g., an example in a file, a quoted instruction, or an attacker-planted decoy tag) is extracted instead of the model's real, later completion tag, so `PROMISE_TEXT` never equals `COMPLETION_PROMISE` even when the model genuinely finished — forcing the loop to keep running against user intent (up to `max_iterations`, or indefinitely if unset).

No allowlist, provenance check, "last occurrence" logic, or single-tag validation exists to prevent either case.

### Impact Explanation
This breaks the consent/state-correctness invariant that the Ralph loop's exit condition must come from genuine model determination, not from attacker-influenced transcript text. Impact is scoped to denial-of-intended-control over the loop: an attacker who can influence repository/tool/MCP content that a running agent quotes can (a) force early exit of an intentionally long-running automated task, short-circuiting review/testing steps the user relied on the loop to perform, or (b) prevent an already-completed loop from stopping, causing wasted iterations/resources or masking task completion, both against the operator's explicit configuration and intent.

### Likelihood Explanation
Precondition (b) — masking legitimate termination — requires only that some `<promise>...</promise>`-shaped text (not necessarily matching `COMPLETION_PROMISE`) appear earlier in the concatenated assistant text than the genuine tag; this is plausible any time the model quotes files/instructions/tool output containing that markup, which the plugin's own workflow encourages. Precondition (a) — forced early stop — additionally requires the attacker to know/guess the exact `COMPLETION_PROMISE` string, which is weaker but realistic given short, conventional phrases and the common pattern of embedding the exact promise text directly in the prompt (which can leak into files, commit messages, or logs the attacker can seed/observe beforehand).

### Recommendation
- Require the completion tag to be the sole content of the final message (or last line), not just the first occurrence anywhere in concatenated text blocks.
- Only scan the last `text` block (or last paragraph) of the assistant message rather than joining and scanning all blocks, reducing accidental inclusion of quoted/echoed content.
- Reject messages containing more than one `<promise>` tag, or explicitly select the last tag instead of the first, and log a warning when multiple tags are detected.
- Consider requiring the promise tag to appear on its own line with nothing else, to reduce accidental matches from quoted content.

### Proof of Concept
Add a fuzz/unit test around `stop-hook.sh`'s promise extraction:
1. Set `COMPLETION_PROMISE="TASK COMPLETE"` in a test state file.
2. Craft a synthetic transcript line with `role:"assistant"` whose `content` text blocks are: `["Quoting file contents: 'Example: <promise>TASK COMPLETE</promise>' (this is just documentation, not a real completion)", "Actual work still in progress, not done yet."]`.
3. Run `stop-hook.sh` against this transcript and assert it incorrectly outputs the "✅ Detected" success path and removes the state file, even though the model never asserted genuine completion — demonstrating forced early termination via reflected content.
4. Separately, craft a transcript where the model outputs a genuine final `<promise>TASK COMPLETE</promise>` preceded by an unrelated quoted `<promise>SOME OTHER TEXT</promise>` earlier in the same message (e.g., from quoted file content); assert the hook fails to detect completion and continues the loop (`decision: block`), demonstrating masking of legitimate termination.
5. Fuzz with nested tags (`<promise><promise>X</promise></promise>`) and Unicode lookalike tag names/angle brackets to confirm inconsistent/incorrect extraction beyond the two above cases.
