### Title
Compromised Arbiter Can Unilaterally Redirect Shared-Contract Funds via a Single Data-Feed Message - ([File: arbiter_contract.js])

### Summary
`deriveSharedAddress()` in `arbiter_contract.js` builds the address definition that locks the funds of both parties to an arbiter contract. Two of the five `"or"` branches of that definition let either the offeror or the acceptor unilaterally sweep the shared funds as soon as a single `data_feed` message from the (single) `arbiter_address` states that they are the winner, with no requirement that the losing counterparty co-sign or otherwise consent to the resolution. [1](#0-0) 

### Finding Description
The shared address is defined as an `"or"` of five branches: mutual signing, timeout/private-asset "done" branches, and two dispute-resolution branches that are triggered purely by a `data_feed` message from `contract.arbiter_address`: [2](#0-1) 

Each of these two branches only requires:
1. The claiming party's own signature (`["address", offeror_address]` / `["address", acceptor_address]`), and
2. A `data_feed` posted by the single `arbiter_address` with key `"CONTRACT_"+hash` equal to that party's address.

The arbiter's decision is produced and consumed as a single trusted data point — `parseWinnerFromUnit()` simply reads the `data_feed` payload from whatever unit is authored by `objContract.arbiter_address` and treats it as final: [3](#0-2) 

There is no requirement that the *other* (losing) party countersign or otherwise validate the resolution before the winning branch of the definition becomes satisfiable — the counterparty's consent is baked into the *original* contract acceptance (`arbiter_contract_response`), not into the *resolution* itself. This means a single compromised arbiter key is sufficient to post a `CONTRACT_<hash>=<address>` data-feed value declaring an arbitrary party (including one colluding with the attacker, or the attacker themself if they also control an involved party's device) the winner of the dispute, at which point that party can spend the entire shared-address balance using only their own signature — exactly the "malicious/compromised single signer authorizes arbitrary spend of already-locked funds" pattern described in the source report (there, a compromised order-signer could redirect a maker's pre-approved funds; here a compromised arbiter can redirect a shared-address counterparty's locked funds).

The only mitigation present is a post-hoc appeal flow (`in_appeal` → `appeal_approved`/`appeal_declined`) gated by the arbstore device, but this is itself resolved by a *second* single centralized party (the arbstore), not a genuine second maker/taker signature check, and does not prevent the initial malicious `data_feed` from immediately becoming spendable by the colluding/attacker-controlled counterparty. [4](#0-3) 

### Impact Explanation
If the `arbiter_address`'s private key/device is compromised (or the arbiter colludes with one party), the attacker can post a single `data_feed` unit declaring themselves (or their accomplice) the winner of any pending arbiter contract they are a counterparty to, regardless of the actual real-world outcome of the underlying trade/agreement. This directly authorizes the theft of the honest counterparty's locked funds from the shared address — a concrete unauthorized-spending / fund-loss outcome, matching the report's "signer obtains assets for free" scenario.

### Likelihood Explanation
Exploitation requires either (a) compromising the arbiter's signing key/device, or (b) a dishonest arbiter colluding with one of the two contract parties. Since arbiters are chosen per-contract and can be any address (including addresses controlled by an attacker posing as a neutral third party), a malicious actor can simply propose themselves as arbiter for a contract they also participate in (or collude with), making this readily reachable by an ordinary contract-creating user rather than requiring a low-probability key compromise of a well-known third party.

### Recommendation
Require resolution of a dispute to depend on more than a single centralized arbiter attestation — e.g., require the arbiter's data-feed message to be combined with a timeout/deadline and/or an additional independent confirmation (such as the arbstore's separate signature) *before* the winning branch becomes spendable, rather than allowing the arbstore-mediated appeal to be the only check applied after funds are already spendable. This mirrors the client-accepted mitigation in the source report: multiple independent, time-bound signature checks rather than a single trusted party's attestation being immediately actionable.

### Proof of Concept
1. Alice and Bob create an arbiter contract naming arbiter Carol (`arbiter_contract.js`'s `deriveSharedAddress`) locking funds at a shared address whose definition includes the two dispute branches shown above.
2. Carol's device/key is compromised by Mallory (or Carol is dishonest and colludes with Bob).
3. Mallory, controlling Carol's address, posts a unit with a `data_feed` message `{"CONTRACT_<hash>": "<Bob's address>"}` from `arbiter_address` (`arbiter_contract.js:475-479`).
4. Bob composes a payment from the shared address using the `"or"` branch `["address", acceptor_address] AND ["in data feed", ...]`, which is now satisfied solely by Bob's own signature plus Carol's (compromised) data feed — Alice's signature/consent is never required.
5. Bob sweeps the shared funds regardless of the real contract outcome, at Alice's expense.

```javascript
function parseWinnerFromUnit(contract, objUnit) {
	if (objUnit.authors[0].address !== contract.arbiter_address) {
		return;
	}
	var key = "CONTRACT_" + contract.hash;
	var winner;
	objUnit.messages.forEach(function(message){
		if (message.app !== "data_feed" || !message.payload || !message.payload[key]) {
			return;
		}
		winner = message.payload[key];
	});
	if (!winner || (winner !== contract.my_address && winner !== contract.peer_address)) {
		return;
	}
	return winner;
}
```
