### Title
Delimiter-Injection in `in data feed` Spending Condition via Unvalidated `feed_name` - (File: definition.js)

### Summary
Node.js's CVE-2021-44533 is a **field-boundary ambiguity** bug class: a certificate subject with a crafted single-value RDN gets re-interpreted by consumers as a multi-value RDN, letting an attacker smuggle an extra field (a bogus CN) past verification logic that relies on delimiter-based parsing of an untrusted string. ocore has the same bug class in how the `in data feed` address-definition condition builds its KV-store lookup key: the `feed_name` supplied inside an address definition is never checked for embedded `\n` (the field separator used everywhere else in the data-feed key schema), so a malicious co-signer of a shared/multi-sig address can smuggle extra `\n`-delimited fields into the oracle lookup key.

### Finding Description
The `in data feed` oscript operator is validated in `validateDefinition()`: [1](#0-0) 

Unlike every other place in the codebase that accepts a `feed_name` from untrusted input, this validator checks only `isNonemptyString(feed_name)` and length — it never rejects `\n`. Compare this to the two other feed_name entry points, which explicitly guard against `\n` injection because the codebase's KV-store data-feed key format is `\n`-delimited: [2](#0-1) [3](#0-2) 

At spend/evaluation time, the condition is checked against the KV store using the exact same `\n`-joined key scheme: [4](#0-3) 

and the general data-feed key layout (`df\naddress\nfeed_name\ntype\nvalue\nreversed_mci`) is parsed positionally by splitting on `\n`: [5](#0-4) 

Because `feed_name` is embedded raw into this `\n`-joined key without escaping and without a check that it is free of `\n`, an address definition can be created (hashed into the address via `objectHash.getChash160`) whose `feed_name` argument to `in data feed` contains extra `\n`-separated tokens. This shifts the field boundaries of the range keys built in `dataFeedByAddressExists`/`readDataFeedByAddress`, so the prefix/`gte`/`lte`/`lt` bounds computed from `feed_name` no longer correspond to the single logical oracle feed the counterparty believes was pinned into the definition — exactly the "single value gets read as multiple values" ambiguity described in the CVE, but here it corrupts a byte-range key rather than an X.509 RDN.

### Impact Explanation
`in data feed` is commonly used to build oracle/escrow style spending conditions on shared or multi-sig addresses (e.g., "either party can spend once oracle X publishes feed Y"). If the field-boundary ambiguity lets the resulting KV range match a different / broader / narrower set of feed entries than the counterparty who reviewed the human-readable oscript intended, one signer could get the "already witnessed" branch of the condition satisfied prematurely (or the intended branch blocked), leading to unauthorized spending from a jointly controlled address or the freezing of funds under conditions that never actually resolve as expected. This lands in the "concrete unauthorized spending / AA-address fund loss" impact tier the validation rules require, reached purely through a self-crafted address definition and a subsequent unit — no privileged/network role needed.

### Likelihood Explanation
An unprivileged unit poster/AA author can freely craft any string for `feed_name` in an `in data feed` clause; this is only checked for length and non-emptiness in `validateDefinition()`. Getting a counterparty to accept a shared address with a manipulated definition requires social engineering (persuading a wallet or human reviewer that the feed name is benign or intending it to look like a normal name), which is a realistic scenario for a shared payment address, exchange escrow, or DAO-style contract construction workflow already supported by ocore.

### Recommendation
Add the same `feed_name.indexOf('\n') >= 0` (and, if applicable, value/`\n`) rejection to the `in data feed` case in `definition.js`'s `validateDefinition()` that is already enforced in `aa_validation.js` and `validation.js`, so address-definition-level feed names cannot smuggle extra key-delimiter fields into the KV-store lookup key.

### Proof of Concept
1. Attacker (co-signer of a to-be-shared address) crafts a definition:
   `["and", [["sig", {...}], ["in data feed", [["ORACLE_ADDR"], "price\nn\n" + <attacker_chosen_encoded_double>, "=", "1"]]]]`
   — passing `validateDefinition()` in `definition.js` because no `\n` check exists on `feed_name`.
2. The resulting address (`objectHash.getChash160(definition)`) is proposed to a counterparty as "spendable once oracle posts feed `price` = 1", who only inspects the readable prefix `price`.
3. When the unit is posted and validated, `Definition.validateAuthentifiers` evaluates the `in data feed` node, which calls `dataFeeds.dataFeedExists` → `dataFeedByAddressExists`, building the range key as `'df\n'+address+'\n'+feed_name+'\n'+prefixed_value` in `data_feeds.js:139`.
4. Because `feed_name` already contains embedded `\n` fields, the constructed `gte/lte` bounds no longer bound just the `price` feed as the counterparty assumed — they can be made to match (or fail to match) different stored KV entries than the ones the human-readable "price" name implied, letting the attacker's `sig`+`in data feed` branch resolve when it should not (or vice versa). function getMciFromDataFeedKey(key){
	var arrParts = key.split('\n');
	var strReversedMci = arrParts[arrParts.length-1];
	var reversed_mci = parseInt(strReversedMci, 16);
	var mci = 0xFFFFFFFF - reversed_mci;
	return mci;
}

// df:address:feed_name:type:value:strReversedMci
function getValueFromDataFeedKey(key){
	var m = key.split('\n');
	if (m.length !== 6)
		throw Error("wrong number of elements in data feed "+key);
	var type = m[3];
	var value = m[4];
	return (type === 's') ? value : decodeLexicographicToDouble(value);
}
