### Title
Cross-tenant forged commit status via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits globally by `sha` with no repository/stack scoping, and the webhook signature check in `WebhooksController#verify_signature` only authenticates that the request came from *some* organization named in the payload's `repository.owner.login`/`organization.login` field — it never verifies that organization owns the commit being updated. Combined with `GitHubApp#verify_webhook_signature` returning `true` automatically when that organization has no `webhook_secret` configured, an attacker who controls (or names) such an organization can forge a `status` webhook whose `sha` collides with a real commit belonging to a completely different, victim organization's stack, writing an attacker-controlled `state`/`description`/`target_url`/`context` onto the victim's `Commit`.

### Finding Description
The broken binding: `organization that authenticated the payload` (the org identified by `repository_owner` in `WebhooksController#repository_owner`, whose `webhook_secret` was checked) MUST equal `organization owning the Commit` (i.e., the org owning the repository behind `commit.stack.repository`) whenever a webhook payload is used to mutate that commit's state. These are never compared.

Path:
1. `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` purely from the payload's own `repository.owner.login`/`organization.login` field [3](#0-2) , then calls `verify_webhook_signature`, which — per `GitHubApp#verify_webhook_signature` — `return true unless webhook_secret` [4](#0-3) . Multi-org Shipit deployments are explicitly documented and configured per-organization (`config/secrets.*.yml`, `docs/setup.md` "Using Multiple Github Applications"), and each org's `webhook_secret` is independently optional/nilable [5](#0-4) . If any org known to Shipit (e.g., a lower-value org onboarded without a webhook secret) has no secret set, any payload claiming that org as `repository.owner.login` passes signature verification unconditionally — no attacker knowledge of any secret is required.
2. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler#process`, which executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) . This is a table-wide SQL lookup with zero scoping to the authenticated repository/organization — it is not `commit.stack.repository`-filtered in any way.
3. `Commit#create_status_from_github!` calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }`, unconditionally persisting a new `Status` with attacker-supplied `state`, `description`, `target_url`, `context` [2](#0-1) , and can further trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` if the forged state is `success`/`pending` [6](#0-5) .

Attacker request: `POST /webhooks` with header `X-Github-Event: status` and body `{"sha": "<victim commit sha>", "state": "success", "context": "ci/attacker", "repository": {"owner": {"login": "<org-with-no-webhook-secret>"}}}`. Since that org's `webhook_secret` is unset, any `X-Hub-Signature` value (or none at all) is accepted.

Existing guards do not prevent this: `verify_signature` authenticates only "a payload was sent by an org GitHub knows about (or nothing, if no secret configured)"; it never checks that the org matches the commit's actual repository. `drop_unhandled_event` and the `ExplicitParameters` schema only validate the shape of `status` events, not repository binding. No `Repository`/`Stack` scoping exists anywhere in `StatusHandler#process`.

### Impact Explanation
An attacker who can get an org with no `webhook_secret` recognized by the Shipit instance (or exploits a legitimately configured org that has no secret set) can forge arbitrary CI status — including `state: "success"` — onto any victim commit across any other tenant/stack sharing the same Shipit instance, as long as they know or can guess/collide the target `sha`. Since `deployable?`/`blocked?` and continuous delivery gating in `Commit` (`schedule_continuous_delivery`, `stack.schedule_merges`) key off these `Status` rows, this can gate an unauthorized deploy or merge for a repository the attacker never authenticated for. This is a payload for one repository mutating another's commit/stack state, and can lead to an unauthorized deploy — matching the Critical severity category.

### Likelihood Explanation
Preconditions: the Shipit instance must be configured for multiple GitHub organizations (a documented, supported configuration) with at least one organization lacking a `webhook_secret`, and the attacker must know a valid commit `sha` for the target stack (commit shas are often public via PRs/commits pages, git history, or CI logs). No Shipit session, API token, or GitHub secret is required — this exactly matches the assumed unprivileged attacker capabilities. The attack is trivially repeatable against any commit sha, in any stack, at will.

### Recommendation
In `StatusHandler#process` (and analogous handlers), scope the `Commit` lookup to the authenticated repository: join through `Stack`/`Repository` and filter by `repository_owner`/`repository.full_name` derived from the same payload used for signature verification, rejecting or ignoring commits whose stack's repository does not match. Additionally, treat a missing `webhook_secret` for a configured organization as a misconfiguration to warn/reject rather than silently trusting all payloads for that org, or require an explicit opt-in.
