The Polkadot SDK's decompression handling already implements the exact protection that was missing in the CVE. The `sp_maybe_compressed_blob::decompress` function caps the decoder read at `bomb_limit + 1` bytes via `decoder.take(...)` and rejects the blob with `Error::PossibleBomb` if the output exceeds the limit, rather than allocating/decompressing an unbounded amount of data. [1](#0-0) 

Every reachable call site that decompresses attacker/network-supplied data passes an explicit `bomb_limit`:
- PVF preparation of validation code uses `pvf.validation_code_bomb_limit()` [2](#0-1) 
- PoV block data decompression uses `POV_BOMB_LIMIT` [3](#0-2) 
- Runtime blob decompression during Wasm execution uses `CODE_BLOB_BOMB_LIMIT` [4](#0-3) 

There are existing tests confirming oversized compressed payloads are rejected during PVF prechecking and PoV validation rather than causing unbounded memory consumption. [5](#0-4) 

This is the opposite of the CVE-2017-7609 root cause (elfutils' `elf_compress.c` did not validate the compression factor before decompressing). Since the codebase already validates and bounds decompression output size at every reachable entry point, and the prompt's own exclusion criteria explicitly reject "memory/storage-growth scenarios" and "oversized-input/flooding/generic resource-exhaustion claims," there is no demonstrable analog vulnerability here.

fn read_from_decoder(
	decoder: impl Read,
	blob_len: usize,
	bomb_limit: usize,
) -> Result<Vec<u8>, Error> {
	let mut decoder = decoder.take((bomb_limit + 1) as u64);

	let mut buf = Vec::with_capacity(blob_len);
	decoder.read_to_end(&mut buf).map_err(|_| Error::Invalid)?;

	if buf.len() <= bomb_limit {
		Ok(buf)
	} else {
		Err(Error::PossibleBomb)
	}
}

fn decompress_zstd(blob: &[u8], bomb_limit: usize) -> Result<Vec<u8>, Error> {
	let decoder = zstd::Decoder::new(blob).map_err(|_| Error::Invalid)?;

	read_from_decoder(decoder, blob.len(), bomb_limit)
}
