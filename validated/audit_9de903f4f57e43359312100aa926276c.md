### Title
Unauthenticated `X-Shipit-User` header is trusted as deploy/rollback/lock/merge attribution identity - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
The `Shipit::Api::BaseController` authenticates *requests* via an `ApiClient` bearer token (`authenticate_api_client`), but attributes *actions* (who triggered a deploy, aborted a task, locked a stack, merged a PR) to a separate `current_user` derived from the unsigned `X-Shipit-User` request header. This breaks the binding: `identity authenticated by the API token` == `identity credited for the action performed with that token`.

### Finding Description
`authenticate_api_client` verifies the `ApiClient` via `ApiClient.authenticate(token)`, a signed/verified token lookup: [1](#0-0) 

But `current_user`, used throughout the API controllers for authorship, is derived from a plain HTTP header with no signature or cross-check against the authenticated `ApiClient`: [2](#0-1) 

This is exactly the reported bug class: a value (`current_user`) that is *acted upon* by privileged operations (deploy, rollback, abort, lock, merge) is never covered by the *verification* boundary (the `ApiClient` token authentication only proves the token is valid — it says nothing about `X-Shipit-User`). Any caller holding a valid `ApiClient` token — for example a CI/CD service or an integration deliberately scoped with a limited-purpose token — can set `X-Shipit-User` to any existing Shipit login (looked up case-insensitively via `User.where('lower(login) = ?', ...)`) and have arbitrary deploys, rollbacks, task aborts, locks, or merges attributed to that user:
- `stack.trigger_deploy(commit, current_user, ...)` [3](#0-2) 
- `task.abort!(aborted_by: current_user)` [4](#0-3) 
- `stack.lock(params.reason, current_user)` [5](#0-4) 
- `MergeRequest.request_merge!(stack, params[:id], current_user)` [6](#0-5) 
- `deploy.trigger_rollback(current_user, ...)` [7](#0-6) 

This mirrors the `RewardThrottle`/`LinearDistributor` pattern: the field that gates authorization (`ApiClient` permissions/token) is checked, but a second, unverified field (`current_user`/`X-Shipit-User`) that downstream logic actually *acts on* (audit trail, authorization of who performed a privileged action) is never validated against the authenticated principal.

### Impact Explanation
This does not, by itself, bypass `ApiClient.check_permissions!` (a valid token with `deploy:stack`/`lock:stack`/etc. is still required) — so it is not a full authentication bypass. Its impact is spoofing of user attribution/audit-trail on high-value actions (who deployed, who locked, who merged, who aborted), which can undermine any downstream authorization or audit logic that relies on `current_user` identity (e.g., "was this rollback authorized by an on-call engineer") without any signature tying the header to the presenter's actual GitHub identity. It stays within an "escalation into authorization semantics" territory but the trust crossed (holder of an `ApiClient` token impersonating an arbitrary `User` record) is a real, unprivileged-attacker-reachable binding break, matching the required class ("GitHub identity versus the `User` bound to the session").

### Likelihood Explanation
High for any caller already possessing a valid `ApiClient` token (a routine, documented usage pattern for CI/webhooks integrating with Shipit) — no other credential or GitHub identity check gates the header value, and the user lookup is case-insensitive with no confirmation the presenter *is* that user.

### Recommendation
Do not trust a client-supplied header for attribution. Bind `current_user` to the authenticated `ApiClient.creator` (or a signed assertion of identity, e.g., mirroring `SimpleMessageVerifier`), and if delegated attribution via `X-Shipit-User` is a required feature, restrict it to callers with an explicit dedicated permission and validate the supplied login against organization membership before use, rather than a bare `User.where(...).first` lookup.

### Proof of Concept
1. Obtain any valid `ApiClient` token that has been granted `deploy:stack` (e.g., a CI integration token scoped only to a specific stack).
2. Send `POST /api/stacks/:id/deploys` with `Authorization: Basic <token>` and header `X-Shipit-User: <victim-login>` (any existing Shipit user's login, not the token creator).
3. Observe the resulting `Deploy` record is attributed to the victim's `User` via `current_user`, as validated by `identify_user`'s unauthenticated header lookup: [8](#0-7)
