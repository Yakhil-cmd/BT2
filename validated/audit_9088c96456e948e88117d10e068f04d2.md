### Title
Precedence bug in `provision?` lets `allow_with_label`/`prevent_with_label` create ReviewStacks even when `review_stacks_enabled` is false - ([File: app/models/shipit/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?` combines `repository.review_stacks_enabled` with the `provisioning_behavior` checks using `&&`/`||` without parentheses, so Ruby operator precedence only gates the `allow_all` branch on `review_stacks_enabled`. The `allow_with_label` and `prevent_with_label` branches are evaluated independently of `review_stacks_enabled`, letting any fork PR with the configured provisioning label create a `ReviewStack` on a repository whose operator never enabled review stacks.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == true` should gate **all** provisioning outcomes of `provision?`, since it is the single UI toggle ("Dynamically provision stacks for Pull Requests?") an authorized Shipit operator controls (see `docs/review_stacks.md`).

The actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to Ruby's `&&` binding tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. Only the `allow_all` term is conditioned on `review_stacks_enabled`; the label-based branches are entirely independent of it.

Call path: `OpenedHandler#process` → `respond_to_pull_request_opened?` → `provision?` [2](#0-1)  → `ReviewStackAdapter#find_or_create!` → `create!`, which builds the `ReviewStack` with `branch: params.pull_request.head.ref` taken directly from the incoming webhook payload (attacker's fork branch name) and no repository-authorization re-check [3](#0-2) .

Attacker request: an unprivileged GitHub user opens a pull request from a fork against a repository configured with `provisioning_behavior: allow_with_label` and `review_stacks_enabled: false`, adding the repository's configured `provisioning_label_name` to the PR. GitHub emits a `pull_request`/`opened` webhook, which is processed normally (this analysis assumes signature/authenticity checks upstream of `OpenedHandler#process` are functioning as designed and are not themselves in scope here — the bug is purely in the authorization logic inside `provision?`). No existing guard (`respond_to_pull_request_opened?`, `ExplicitParameters` schema, or model validations) checks `review_stacks_enabled` for the label branches, so the divergence reaches `ReviewStackAdapter#create!` unblocked.

### Impact Explanation
A `Shipit::ReviewStack` (a `Shipit::Stack` subtype) is created for a repository whose operator explicitly left `review_stacks_enabled` off, using attacker-controlled `branch` and PR metadata. The stack is queued via `Shipit::ReviewStackProvisioningQueue.add(stack)` for provisioning [4](#0-3) , and once provisioned, later deploy/task flows execute steps sourced from the repository's `shipit.yml` (as configured on that branch) via `Command`/`PTY.spawn` in the deploy pipeline (e.g. `TaskCommands#perform`) [5](#0-4) . Because the branch is attacker-supplied (the fork's PR head ref), an attacker who controls a `shipit.yml` on that branch can influence what commands are eventually run on the deploy host once provisioned — an unauthorized/record write and potential path to command execution on infrastructure an operator did not opt into. This is repeatable against every repository configured with `allow_with_label` or `prevent_with_label` regardless of the `review_stacks_enabled` flag, matching "unauthorized deploy/record creation for a repository that did not authenticate it."

### Likelihood Explanation
Preconditions: repository must have `provisioning_behavior` set to `allow_with_label` (or `prevent_with_label`), and `review_stacks_enabled` may be `false` — this is a fairly plausible operator configuration (e.g., an operator sets a provisioning behavior in anticipation of enabling review stacks later, or toggles the checkbox off temporarily while behavior remains configured). Attacker cost is trivial: open a PR from a fork and add a known/discoverable label name. No secrets or elevated privileges are required. This is fully repeatable per PR/per repository matching the configuration.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every branch:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Apply the same fix to the analogous `provision?` methods in `labeled_handler.rb`, `unlabeled_handler.rb`, and `reopened_handler.rb`, which share this pattern.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb
test "does not provision a review stack via label when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "deploy-me"
  )

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [{ "name" => "deploy-me" }]

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix, this assertion fails (`Shipit::Stack.count` increases by 1) because `provision?` returns `true` despite `review_stacks_enabled == false`; after applying the parenthesization fix, `provision?` returns `false` and no stack is created.
