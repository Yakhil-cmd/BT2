## Analysis

The bug class in the Sherlock report — a refund being sent to the transaction *signer/payer of record* rather than the actual entity that funded the payment — has a direct, concrete analog in `nearcore`'s meta-transaction (NEP-366 `DelegateAction`) implementation.

### Title
Delegate-action deposit refunds are sent to the sender, not the relayer who actually paid the deposit - ([File: runtime/runtime/src/actions.rs])

### Summary
When a relayer submits a meta transaction (`Action::Delegate`/`Action::DelegateV2`), the relayer pays for all gas and any attached token deposits of the inner actions on behalf of the `sender_id`. If the inner action later fails execution on the receiver's shard, the attached deposit is refunded — but the refund goes to the `predecessor_id` of the failed receipt, which is the `sender_id` from the `DelegateAction`, not the relayer who actually supplied the funds. This is the direct nearcore analog of the Babylon/Cosmos SDK "fee granter" refund bug: the party that paid is not the party that receives the refund.

### Finding Description
`apply_delegate_action` builds the forwarded receipt using the plain (non-refund-aware) `ActionReceipt` variant, with `predecessor_id` set to `sender_id` (the delegate-action sender, e.g. "Alice"), even though the relayer funded the deposit and gas: [1](#0-0) 

The comment in the code explicitly documents this behavior as a known consequence:
"Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas... If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction. Gas is refunded to the signer, this is Relayer."

Crucially, the receipt created here does **not** use `ActionReceiptV2`, which has an explicit `refund_to` field designed to redirect balance refunds to a different account than `predecessor_id`: [2](#0-1) 

The fallback logic for balance refunds is: [3](#0-2) 

Since `apply_delegate_action` never sets `refund_to` to the relayer, any deposit refund resulting from a failed inner action defaults to `predecessor_id` (the sender), not the relayer that actually paid. This same gap is acknowledged in the architecture docs: [4](#0-3) 

### Impact Explanation
A malicious `sender_id` ("Alice") can craft a `DelegateAction` containing an inner action with a large attached deposit (e.g. a `Transfer` or `FunctionCall` with deposit) targeting a receiver/method that is guaranteed to fail (non-existent method, insufficient gas, a contract that panics, etc.). The relayer, trusting the delegate action enough to wrap and pay for it, funds the deposit. When the inner action fails, the deposit is refunded to Alice's account (the `predecessor_id` of the forwarded receipt) instead of being returned to the relayer who paid for it — resulting in a direct, unauthorized transfer of value from the relayer to the sender. This is a concrete "theft"/unauthorized balance-change primitive reachable purely by submitting a transaction containing an `Action::Delegate`/`Action::DelegateV2`.

### Likelihood Explanation
This requires only a malicious/dishonest `sender_id` cooperating with (or exploiting the trust of) a relayer — a fully reachable, unprivileged-account path through normal transaction submission. The docs themselves flag this as a real financial incentive for the sender to abuse relayers ("financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard"), and the code confirms no mitigation (`refund_to`) is applied on the delegate-action-generated receipt.

### Recommendation
When constructing the forwarded receipt in `apply_delegate_action`, use `ActionReceiptV2` and set `refund_to` to the relayer's account id (the outer transaction's signer/`predecessor_id` at the time the `DelegateAction` was unwrapped), so that failed-inner-action deposit refunds route back to whoever actually funded the deposit, analogous to how gas refunds already correctly go to the relayer.

### Proof of Concept
1. Relayer submits a transaction with `Action::Delegate(SignedDelegateAction)` where `sender_id = Alice`, `receiver_id = Bob`, inner action = `FunctionCall` with a large `deposit` and a method name that does not exist on `Bob`'s contract (or insufficient gas to succeed).
2. `apply_delegate_action` forwards the actions to Alice's shard, creating a new `ActionReceipt` with `predecessor_id = Alice`, funded by relayer-paid deposit/gas: [5](#0-4) 
3. The receipt is forwarded to Bob; execution fails (unknown method/insufficient gas).
4. Runtime generates a deposit refund receipt to `receipt.balance_refund_receiver()`, which resolves to `predecessor_id` = Alice (since no `refund_to` was set), per: [6](#0-5) 
5. Alice receives the deposit that the relayer paid for; the relayer's funds are lost.

    pub fn refund_to(&self) -> &Option<AccountId> {
        match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseResume(_)
            | ReceiptEnum::GlobalContractDistribution(_) => &None,
            ReceiptEnum::ActionV2(action_receipt_v2)
            | ReceiptEnum::PromiseYieldV2(action_receipt_v2) => &action_receipt_v2.refund_to,
        }
    }

    pub fn balance_refund_receiver(&self) -> &AccountId {
        self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
    }

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
