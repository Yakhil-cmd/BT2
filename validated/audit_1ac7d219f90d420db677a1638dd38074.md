### Title
`--max-iterations` overflow bypasses stop-hook.sh gating, causing infinite Ralph loop execution - (File: plugins/ralph-wiggum/hooks/stop-hook.sh)

### Summary
`setup-ralph-loop.sh` only validates that `--max-iterations` matches the shape `^[0-9]+$`, with no upper bound check, so it accepts arbitrarily large integers such as `99999999999999999999`. `stop-hook.sh` re-validates the value against the same shape-only regex and then performs a native bash numeric comparison `[[ $MAX_ITERATIONS -gt 0 ]]`, which overflows bash's 64-bit signed integer arithmetic and errors out, causing the max-iterations gate to be silently skipped and the loop to run unbounded.

### Finding Description
In `setup-ralph-loop.sh`, the `--max-iterations` value is validated only by `[[ "$2" =~ ^[0-9]+$ ]]` [1](#0-0)  and then written verbatim into the YAML frontmatter of `.claude/ralph-loop.local.md` as `max_iterations: $MAX_ITERATIONS` [2](#0-1) . No maximum magnitude (e.g., bounding against `INT64_MAX`) is enforced, only digit shape.

In `stop-hook.sh`, the state file is parsed and `MAX_ITERATIONS` is re-checked with the same shape-only regex `^[0-9]+$` [3](#0-2) , which passes for any all-digit string regardless of size. The gating check then does:
```
if [[ $MAX_ITERATIONS -gt 0 ]] && [[ $ITERATION -ge $MAX_ITERATIONS ]]; then
``` [4](#0-3) 

Bash's arithmetic/comparison evaluator uses native (typically 64-bit signed) integers. A value like `99999999999999999999` (20 digits, exceeding `9223372036854775807`) causes bash to raise `value too great for base` when evaluating `-gt`/`-ge`. Because this `[[ ]]` expression is the *condition* of an `if`/`&&` chain, its non-zero/error exit status is not subject to `set -e` (conditions of `if`/`while`/`&&` chains are exempt from `errexit`). The script does not `exit`; it simply treats the failed evaluation as "false" and falls through, skipping the `rm "$RALPH_STATE_FILE"; exit 0` termination path. The loop therefore never stops via the max-iterations mechanism, regardless of how many iterations actually occur, because every subsequent invocation of the hook hits the same overflow and false-negative gate.

This defeats the stated invariant ("Only by reaching --max-iterations or detecting --completion-promise" — see the help text at `setup-ralph-loop.sh` lines 48-50) and the explicit user-facing guarantee that a nonzero `--max-iterations` bounds the loop.

### Impact Explanation
The stop hook is designed to be the sole automated brake on the Ralph loop feeding Claude's own output back into itself as input across sessions. If the numeric gate silently fails open due to overflow, a user (or any automation/config path that supplies the `--max-iterations` value, e.g., derived from issue/PR text or CI parameters) intending to bound the loop instead gets unlimited iterations — matching the exact "never terminate the loop... unbounded automated re-submission of repo content/diffs to the model" behavior described. This is a resource-exhaustion / uncontrolled automation impact (excessive model calls, cost, and prolonged unattended agentic execution against repository content) rather than a sandbox escape, consistent with a logic/DoS-class finding.

### Likelihood Explanation
Exploitability only requires supplying a sufficiently large digit string to `--max-iterations` — no special privileges, no bypass of any allowlist, and the regex check does not restrict magnitude. Since the value flows unmodified from CLI argument to state file to the hook's arithmetic, this is deterministic and repeatable on any bash version with native 64-bit (or narrower) integer arithmetic. The precondition is that some caller (script, automation config, or slash-command wrapper) passes an untrusted numeric string into this argument without independent bounding, which is plausible given the loose validation in `setup-ralph-loop.sh`.

### Recommendation
Bound `--max-iterations` against a sane maximum (e.g., reject values greater than `2147483647` or `9223372036854775807`, or a much smaller practical cap like `100000`) at write time in `setup-ralph-loop.sh`, and re-validate the same bound in `stop-hook.sh` before performing arithmetic. Additionally, wrap the numeric comparisons in `stop-hook.sh` with explicit overflow-safe handling (e.g., string-length pre-check before `[[ -gt ]]`, or use `bc`/`awk` for arbitrary-precision comparison) so an out-of-range value causes the loop to fail-closed (stop and report corruption) rather than fail-open (silently continue).

### Proof of Concept
Integration/fuzz test plan:
1. Run `setup-ralph-loop.sh "test prompt" --max-iterations 99999999999999999999` and confirm it succeeds and writes `max_iterations: 99999999999999999999` into `.claude/ralph-loop.local.md`.
2. Set `iteration: 1` in the same file (simulating loop progress) and invoke `stop-hook.sh` with a valid transcript containing no `<promise>` tag.
3. Assert expected behavior: hook should either (a) detect the out-of-range value and stop the loop with a "state file corrupted"-style message, or (b) correctly recognize `iteration >= max_iterations` is not yet true but never falsely disable the eventual max-iterations stop.
4. Observed buggy behavior: `stop-hook.sh` stderr shows `value too great for base` from the `[[ $MAX_ITERATIONS -gt 0 ]]` check, the script does not `exit` on the error, and it proceeds to emit `{"decision":"block", ...}`, incrementing `iteration` indefinitely across repeated invocations with no bound — confirming the max-iterations cap is never enforced for oversized values.
5. Fuzz boundary values: `9223372036854775807` (max int64, should still work), `9223372036854775808` (first overflow value) and confirm the gate breaks exactly at/after the int64 boundary, demonstrating the shape-only regex is insufficient.
