### Title
Webhook signature verification is keyed to an attacker-chosen organization field while the handled payload's repository field is unconstrained, allowing signature bypass and cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which organization's* `GithubApp`/secret to verify a webhook against by reading `repository_owner` straight out of the unauthenticated, unverified JSON body, then calls that org's `verify_webhook_signature`. That method treats a blank `webhook_secret` as an implicit "always valid" sentinel (`return true unless webhook_secret`). Because the field used to pick the verifying organization (`repository.owner.login` / `organization.login`) is independent of the field the downstream handler uses to decide which `Stack`/repository to mutate (`repository.full_name`), an attacker can make the request "authenticate" against any configured organization that happens to have no webhook secret, while pointing the actual payload at a completely different, properly-configured victim repository.

### Finding Description
`verify_signature` computes the organization used for verification purely from request body content, before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` in `GithubApp` degrades to an unconditional pass when `webhook_secret` is not configured for the selected organization: [3](#0-2) 

Multi-organization deployments of Shipit are documented/expected to have per-org secrets, and a blank/`nil` `webhook_secret` per org is shown as a normal templated value: [4](#0-3) 

Once `verify_signature` passes (because the chosen org has a blank secret), the raw, attacker-controlled payload is dispatched to event handlers, e.g. `PushHandler`, which resolves target stacks from the payload's `repository` data (a field never covered by the org-selection check) and triggers a GitHub sync/deploy pipeline using an attacker-supplied `after` SHA: [5](#0-4) 

The equality that should hold is: `organization whose secret authenticated this request == organization that owns the repository/stack the handler subsequently writes to`. Because `repository_owner` (used only to pick the verifying `GithubApp`) and the deeper `repository.full_name`/branch fields (used by `PushHandler#process` to select and mutate the real `Stack`) are both attacker-supplied and never cross-checked against each other or against the signature, this equality can be broken: verification succeeds against org A (misconfigured with no secret) while the mutation lands on a repository belonging to org B.

### Impact Explanation
This allows an unauthenticated network attacker (no Shipit session, no `ApiClient` token, no GitHub credentials) to inject forged GitHub webhook events for any tracked stack, as long as at least one configured GitHub organization in the deployment has a blank `webhook_secret` (a state the codebase's own config templates treat as normal/expected). Forged `push` events can trigger `stack.sync_github(expected_head_sha: params.after)` for a victim repository/stack, and depending on `continuous_deployment` configuration, this can cascade into unauthorized deploys. This matches the "unauthorized deploy" / "cross-repository writes" impact bar.

### Likelihood Explanation
Requires only that one organization in a multi-org Shipit deployment be configured without a `webhook_secret` — a state the shipped config templates present as a normal/valid default rather than an error condition, and which the code does not warn about or forbid. No credentials, session, or prior access are required from the attacker; a single crafted HTTP POST to `/webhooks` suffices.

### Recommendation
Do not select the verifying organization from unauthenticated request content. Instead: (1) reject requests whose claimed `repository_owner`/`organization` used for secret lookup does not match the organization that actually owns the `repository.full_name` referenced later in the payload, and/or (2) stop treating a blank `webhook_secret` as automatic verification success — require an explicit, non-bypassable configuration flag to permit unsigned webhooks, and warn loudly when it is enabled, so a single misconfigured/legacy organization cannot be leveraged to forge events for any other repository in the same installation.

### Proof of Concept
1. Deploy Shipit configured with two GitHub organizations, e.g. `attacker-org` (no `webhook_secret` set, as shown valid in `config/secrets.development.shopify.yml`) and `victim-org` (properly configured with a real secret, hosting a tracked `Stack` for `victim-org/protected-repo`).
2. Attacker sends:
   ```
   POST /webhooks
   X-Github-Event: push
   (no valid X-Hub-Signature)

   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "full_name": "victim-org/protected-repo",
       "owner": { "login": "attacker-org" }
     }
   }
   ```
3. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `attacker-org`'s `GithubApp`, and `verify_webhook_signature` returns `true` unconditionally because `attacker-org` has no `webhook_secret`.
4. `create` proceeds, `PushHandler#process` finds `Stack`s for `victim-org/protected-repo` and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")`, causing Shipit to act on a forged event for a repository the attacker never had credentials for.

Note: I was unable to directly inspect `app/models/shipit/webhooks/handlers/handler.rb` (the `stacks`/`params.repository` resolution helper) or the exact multi-org lookup logic in `Shipit.github`/`GithubApp` initialization within the available index, so the precise mechanics of how `repository.full_name` maps to `Stack` records in `Handler` could not be fully confirmed from source; this is inferred from `PushHandler`'s use of `stacks.where(branch:)` and the documented multi-org config shape. A Devin session with full repository access would be needed to confirm the exact `stacks` scoping method and whether any additional per-request repository/organization cross-check already exists elsewhere in the request pipeline.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
