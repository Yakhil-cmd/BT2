### Title
CCMenuController#stack bypasses ApiClient stack scoping, allowing cross-stack data exposure - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` scopes stack access to `current_api_client.stack_id` when the client is stack-restricted, but `Shipit::Api::CCMenuController` overrides `#stack` with an unscoped `Stack.from_param!` lookup, so a stack-restricted `ApiClient` token can read CI status for any stack, not just the one it was issued for. This is worse than a mere existence oracle: it is full unauthorized data disclosure of another stack's build state.

### Finding Description
The broken binding: `CCMenuController#show`'s visible stack set should equal `BaseController#stacks` (i.e. `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`), but it does not.

`BaseController` defines the scoping primitive: [1](#0-0) 

`CCMenuController` requires only the generic `read:stack` permission (not tied to a specific stack instance) and then defines its own `#stack` that ignores the scoped `stacks` relation entirely: [2](#0-1) 

`ApiClient#check_permissions!` only checks whether the client's `permissions` array contains `"read:stack"` — it never checks which stack is being accessed: [3](#0-2) 

So the only place stack-level authorization is enforced is the `stacks`/`stack` scoping in `BaseController`, and `CCMenuController` deliberately (or accidentally) reimplements `stack` without going through that scope:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
compared to the base:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

Test fixtures confirm stack-scoped clients exist in this codebase (`here_come_the_walrus` is scoped to the `shipit` stack via `stack: shipit`): [4](#0-3) 

**Exploit flow**: An attacker holding a valid `ApiClient` token that is scoped to stack A (via `ApiClient#stack_id`, e.g. issued through `CCMenuUrlController#fetch`, which itself creates an unscoped read-only client, or through any admin-issued stack-scoped client) can call `GET /api/stacks/*stack_id/ccmenu?token=<token>` (or via Basic Auth) with `stack_id` set to stack B — an existing stack the client is not authorized for. `authenticate_api_client` succeeds (valid token), `require_permission :read, :stack` succeeds (client has `read:stack` in its permission list, unrelated to stack B), and `stack` resolves stack B directly via `Stack.from_param!`, bypassing the `stacks` scoping that would otherwise raise `ActiveRecord::RecordNotFound`. The response renders stack B's real CI status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock status, etc.), not merely a distinguishable status code.

Existing guards that fail to prevent this: `require_permission`/`check_permissions!` (permission-name check only, no stack binding); the `stacks`/`stack` scoping pattern used correctly by `StacksController`, `TasksController`, `OutputsController`, `HooksController` (all use `stacks.from_param!`) is simply not used by `CCMenuController`.

### Impact Explanation
A stack-scoped API token (intended to expose only one stack's CCTray/CI status, e.g. tokens generated by `CCMenuUrlController#fetch` for a specific stack) can be replayed against `/api/stacks/*stack_id/ccmenu` with any other stack identifier to read that stack's build status, lock state, and last-deploy metadata. This is an unauthenticated-relative-to-scope read of stack state across tenants/repositories, matching the High severity category ("unauthenticated read of stack state"). It is fully repeatable against any existing stack_id and requires no privileged access beyond possession of any valid API token that has `read:stack` permission, even one deliberately scoped to a single stack.

### Likelihood Explanation
Preconditions: attacker must possess *some* valid `ApiClient` token with `read:stack` permission (this could be a narrowly-scoped token, e.g. a CCMenu URL token shared for one stack's dashboard widget, or a legitimately-obtained but stack-restricted API client). No Shipit secrets, GitHub credentials, or elevated roles are required beyond the token itself. Guessing/enumerating `stack_id` values (`owner/repo/environment`) is straightforward since these are human-readable identifiers often visible in URLs, repo names, or environment naming conventions. The attack is a single GET request per target stack and fully repeatable.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped lookup from `BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the private override entirely (or deleting it so the inherited scoped method is used), ensuring stack-restricted `ApiClient` tokens cannot resolve stacks outside their `stack_id`.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a stack-scoped token cannot read ccmenu status for a different stack" do
  scoped_client = shipit_api_clients(:here_come_the_walrus) # scoped to shipit_stacks(:shipit)
  other_stack = shipit_stacks(:cyclimse) # a different, existing stack
  request.headers['Authorization'] = "Basic #{Base64.encode64(scoped_client.authentication_token)}"

  get :show, params: { stack_id: other_stack.to_param }

  # Binding under test: response for existing-but-unauthorized stack_id must be
  # indistinguishable from a nonexistent stack_id (both should be 403/404),
  # matching the behavior guaranteed by BaseController#stacks scoping used by
  # TasksController/StacksController/OutputsController.
  assert_response :not_found # currently fails: observed :ok (200) with real stack data
end
```
Running this against the current code shows `assert_response :not_found` fails with `response.status == 200`, and the response body contains `other_stack`'s real CI status (`lastBuildStatus`, `webUrl`, etc.), confirming the scope bypass.
