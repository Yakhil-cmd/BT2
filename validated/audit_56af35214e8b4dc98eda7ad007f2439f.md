### Title
Webhook signature verification binds only to `repository.owner.login`, not to the repository actually acted upon, enabling cross-organization webhook forgery in multi-GitHub-App deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate a webhook against using an attacker-controlled field taken straight from the *unverified* raw request body (`repository.owner.login`). The `create` action then hands the *entire* raw, unverified payload — including `repository.full_name` — to the registered webhook handlers, which use that separate field to look up the `Stack`/`Repository` to act on. Because the field used to select the verification key and the field used to select the target repository are two different, independently attacker-controlled values in the same unsigned JSON body, an attacker who legitimately owns a GitHub App/webhook secret for one organization (OrgX) can forge a payload that verifies successfully under OrgX's secret while claiming to be about a repository belonging to a completely different organization (OrgY) also configured on the same Shipit instance.

### Finding Description
`verify_signature` computes the organization to authenticate against purely from the JSON body, not from any cryptographically-bound source: [1](#0-0) 

It then looks up the appropriate `GithubApp`/secret for that claimed organization and checks `X-Hub-Signature` against the raw body: [2](#0-1) 

This design is required to support the documented multi-org configuration, where each organization has its own `webhook_secret`: [3](#0-2) 

Once the signature check succeeds, `create` dispatches the full raw `params` (unmodified) to every registered handler for the event: [4](#0-3) 

Handlers such as the push/status/check_suite handlers are documented to receive this same `params` object and act on whatever repository identifier the payload contains (e.g. `repository.full_name`), independent of the `repository.owner.login` value that was used purely for signature selection: [5](#0-4) 

The binding that should hold is:
`organization_used_for_signature_verification(payload) == organization_of_repository_acted_on(payload)`

Nothing in `verify_signature` or `create` enforces this equality — the two lookups (`repository.owner.login` for the secret, `repository.full_name`/nested repository object for the actual `Stack`/`Repository` record) are computed independently from the same untrusted JSON body. An attacker who controls a legitimate GitHub App installed against OrgX (and therefore knows OrgX's `webhook_secret`) can set `repository.owner.login: "OrgX"` (so verification succeeds against OrgX's secret) while setting the nested `repository.full_name` / `repository` object to point at `OrgY/some-stack`, a completely different organization's repository hosted on the same Shipit instance. The forged, correctly-HMAC-signed request is accepted, and the handler layer processes it as a genuine event for OrgY's stack.

### Impact Explanation
This breaks the authentication-to-authorization boundary between organizations sharing one Shipit instance (the exact "Using Multiple GitHub Applications" configuration Shipit documents). Depending on which event type is forged:
- A forged `status` event can inject fake commit statuses on OrgY's commits, which can satisfy `ci.require` gates and, combined with `continuous_deployment: true`, cause an **unauthorized deploy** of OrgY's stack.
- A forged `push` event can enqueue sync jobs causing Shipit to treat attacker-chosen refs/SHAs as legitimate incoming commits for OrgY's stack.
- A forged `membership`/`check_suite` event can pollute team/commit-check state used for authorization or CI decisions on a repository the attacker does not control.

This is a cross-organization write achieved purely by possessing credentials (a webhook secret) for an unrelated, lower-privilege organization — squarely in the "cross-repository writes" / "unauthorized deploy" impact category, requiring no `ApiClient` token, no GitHub App private key, and no privileged Shipit account.

### Likelihood Explanation
Requires the operator to run Shipit in the documented multi-organization mode (multiple GitHub Apps configured under `github:`), and the attacker must control (or have compromised) a GitHub App/webhook secret for at least one of the configured organizations — a realistic scenario for shared internal Shipit instances serving multiple teams/orgs with different trust levels. No other credential, session, or privileged access is needed; the attacker only needs to send a raw HTTP POST with a body they fully control and a correctly computed HMAC using their own org's secret.

### Recommendation
Do not derive the signing-key lookup and the repository-lookup from independent, equally-unverified fields of the same payload. After verifying the signature, re-derive `repository_owner` from the *same* repository object subsequently used by handlers (i.e., ensure `repository.owner.login` and `repository.full_name`'s owner segment are the same value), or better, verify that the resolved `Stack`/`Repository` record's known owner/organization matches the organization whose secret validated the signature before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two GitHub Apps, `OrgX` and `OrgY`, per `docs/setup.md`'s multi-org format, each with its own `webhook_secret`.
2. As an attacker who legitimately controls OrgX's GitHub App and therefore knows `OrgX`'s `webhook_secret`, craft a `status` (or `push`) event payload:
```json
{
  "repository": {
    "owner": { "login": "OrgX" },
    "full_name": "OrgY/production-app"
  },
  "sha": "<any-sha-in-OrgY-production-app>",
  "state": "success",
  ...
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgX_webhook_secret, raw_body)>`.
4. POST to the webhooks endpoint with `X-Github-Event: status`.
5. `verify_signature` computes `repository_owner == "OrgX"`, fetches `Shipit.github(organization: "OrgX")`, and the signature validates successfully against the attacker-known `OrgX` secret. [6](#0-5) 
6. `create` then dispatches the full `params` — including `repository.full_name: "OrgY/production-app"` — to the status handler, which updates commit status for OrgY's stack despite the request having been authenticated solely against OrgX's credentials. [4](#0-3)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
