### Title
`StatusHandler` resolves commits by SHA with no repository/stack scoping, allowing a webhook authenticated for one GitHub org to write a `Status` (and trigger continuous‑deployment/merge logic) on a different org's `Stack` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` across the entire commits table, not scoped to the repository that authenticated the webhook. Because `Commit` SHAs are only unique per `(sha, stack_id)` and not globally unique, a `status` webhook that is validly signed for org A's repository can update the status of - and trigger continuous delivery/merge pipelines for - a commit belonging to a completely different org's `Stack` whenever the two repos share a commit SHA (e.g. a public fork of the victim's repository).

### Finding Description
The broken binding, stated as an equality that the code is supposed to preserve but does not:

`verify_signature`'s validated org (`Shipit.github(organization: repository_owner)`, `repository_owner` taken from the attacker's own webhook payload) **should equal** the org that owns the `Stack`/`Commit` whose deploy/merge pipeline is mutated as a result of processing that webhook. [1](#0-0) 

`StatusHandler#process` never re-checks this: it resolves affected commits purely by SHA, globally: [2](#0-1) 

`Commit` SHA uniqueness is enforced only per stack, not globally: [3](#0-2) 

This means two different `Stack`s (belonging to two different GitHub organizations/repositories) can legitimately contain `Commit` rows with the identical `sha` — most naturally when a repository is publicly forked, since forks share git history/commit hashes with the upstream repository. An attacker who owns a fork of the victim's repository (or any repository sharing history with it) can register/receive a GitHub webhook for their **own** fork, which GitHub signs with the secret for the attacker's own org. `WebhooksController#verify_signature` only checks that the signature matches the org named in the payload's `repository_owner` — i.e., it validates that the attacker's own org sent the payload, not that the org "owns" every commit SHA referenced in it. [4](#0-3) 

Once through `verify_signature`, `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` against the whole table, hitting any commit row — from any stack, from any org — whose SHA matches, including the victim's `Commit` row for the same underlying commit in their private/independent `Stack`. `create_status_from_github!` calls `add_status`/`Status.replicate_from_github!`, creating a real `Status` record tied to the victim's `stack_id`. [5](#0-4) 

That `Status` creation fires downstream logic unconditionally for the victim's stack:
- `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob`, which (if the victim stack has `continuous_deployment?` enabled and is not occupied) calls `stack.trigger_continuous_delivery`, eventually producing a `Deploy` task that shells out via `Command`. [6](#0-5) [7](#0-6) 
- `add_status` also enqueues `ProcessMergeRequestsJob` when a commit transitions to `pending`/`success`, which drives merge-request auto-merge logic for the victim's stack. [8](#0-7) 

By contrast, `CheckSuiteHandler` first scopes to `stacks.where(branch: params.check_suite.head_branch)` before matching the SHA [9](#0-8) , which (depending on how the base `Handler#stacks` helper restricts to the authenticated repository) likely narrows blast radius there; `StatusHandler` has no equivalent scoping at all, making it the clearly broken handler. I was not able to load the `Handler` base class source in this session to fully confirm the exact scoping semantics of `stacks`, so the `CheckSuiteHandler` mitigation is inferred from its explicit query and not independently verified against the base class implementation.

None of the documented guards prevent this: `verify_signature` only authenticates *which org sent the request*, not *which commits/stacks that org is allowed to affect*; `ExplicitParameters` only validates the shape of `sha`/`state`, not ownership; there is no `Repository`/`Stack` ownership check inside `StatusHandler#process` at all.

### Impact Explanation
An attacker with write access to any repository that shares commit history with a victim's Shipit-tracked repository (trivially achievable via a public GitHub fork) can create arbitrary CI `Status` records for the victim's `Commit`, causing:
- Unauthorized writes to a victim `Stack`'s data (a payload authenticated for repo A mutating repo B's commit/stack state).
- If the victim stack has `continuous_deployment` enabled, unauthorized enqueuing of `ContinuousDeliveryJob`/`Deploy`, which executes real deployment commands via `Command`/`PTY.spawn` on the deploy host.
- Unauthorized triggering of `ProcessMergeRequestsJob`, potentially auto-merging PRs in the victim's repository.

This is repeatable against any stack whose repository shares a commit SHA with an attacker-controlled fork, is not limited to a single request, and crosses the tenant/org boundary the webhook signature is meant to enforce. This matches the "Critical" impact category: "a payload for one repository mutating another's stack, commit, task, or team" and "unauthorized deploy...of attacker-controlled code."

### Likelihood Explanation
Preconditions: the victim repository must be public (or otherwise forkable) so the attacker can obtain a fork sharing at least one commit SHA with the tracked branch history, and the attacker needs any mechanism to cause a `status` event to fire on their own fork with that shared SHA (e.g., pushing a CI integration to their fork, or directly sending a signed webhook using their own repo's legitimate webhook secret, which GitHub provides to any repo owner/admin). Both are within reach of an unprivileged internet user who owns a fork. No Shipit secrets, sessions, or API tokens are required — only the attacker's own valid GitHub webhook credentials for their own repository. This is fully repeatable at will.

### Recommendation
Scope `StatusHandler#process` (and any other handler that resolves records by content-derived identifiers like SHA) to the `Stack`(s)/`Repository` actually identified by the incoming webhook's `repository.full_name`, matching the same repository used to select the `GithubApp`/secret in `verify_signature`. For example, resolve `stacks` for the payload's repository first (as `CheckSuiteHandler` does for branch) and only search `Commit.where(sha: params.sha, stack: matching_stacks)`, rather than querying `Commit` unscoped.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, hypothetical):
```ruby
test "status webhook for org A does not mutate a commit belonging to org B's stack with the same sha" do
  victim_stack = shipit_stacks(:shipit)            # e.g. repo "Shopify/shipit-engine"
  attacker_stack = shipit_stacks(:cyclimse)        # different org/repo, e.g. "attacker/shipit-engine" (a fork)
  shared_sha = "deadbeef" * 5

  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  # Equality under test (should hold, but doesn't):
  # webhook-authenticated org (attacker_stack.repository.owner) == org whose Stack is mutated
  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(
      "sha" => shared_sha, "state" => "success", "context" => "ci",
      "repository" => { "full_name" => attacker_stack.repository.full_name,
                         "owner" => { "login" => attacker_stack.repository.owner } }
    ).call
  end
  # Currently FAILS: victim_commit.statuses.count increases even though
  # the webhook only authenticated the attacker's own org/repo.
end
```
Assert on both sides: `attacker_stack.repository.owner` (the org verified by `verify_signature`) vs. `victim_commit.stack.repository.owner` (the org actually mutated) — the test should show these differ while the write still succeeds, proving the cross-tenant violation. Extend with `assert_no_enqueued_jobs(only: ContinuousDeliveryJob)` for `victim_stack` to demonstrate the deploy-trigger chain does not fire once fixed, and currently does.
