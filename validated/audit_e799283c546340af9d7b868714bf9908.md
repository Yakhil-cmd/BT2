`CCMenuController#stack` bypasses `stack_id`-scoping, allowing a `read:stack` token issued for stack A to read stack B's CC-menu deploy data - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` enforces `require_permission :read, :stack`, which only checks the string permission `"read:stack"` against `current_api_client.permissions`, with no reference to which stack the client is bound to. The actual stack-scoping (restricting a token to `current_api_client.stack_id`) is implemented only in `BaseController#stacks`/`#stack`, but `CCMenuController` overrides `#stack` to call `Stack.from_param!` on the unscoped `Stack` model, bypassing that restriction entirely.

### Finding Description
The broken binding: `scope checked by require_permission!(:read, :stack)` (i.e., `current_api_client.permissions.include?("read:stack")`) is claimed to equal `the concrete stack instance the action reads` (`stack` resolved in `#show`). These are not the same value.

- `require_permission :read, :stack` (`app/controllers/shipit/api/ccmenu_controller.rb:6`) triggers a `before_action` calling `require_permission!(:read, :stack)` → `current_api_client.check_permissions!(:read, :stack)` (`app/controllers/shipit/api/base_controller.rb:82-84`).
- `ApiClient#check_permissions!` (`app/models/shipit/api_client.rb:38-45`) only does: `required_permission = "read:stack"; permissions.include?(required_permission)`. It never inspects `stack_id` or `params[:stack_id]`.
- The actual per-token stack restriction is implemented separately in `BaseController#stacks` (`app/controllers/shipit/api/base_controller.rb:74-76`): `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, consumed by `BaseController#stack` (`:78-80`) via `stacks.from_param!(params[:stack_id])`.
- `CCMenuController` overrides `#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`): `@stack ||= Stack.from_param!(params[:stack_id])` — resolving directly against the unscoped `Stack` class, never calling the `stacks` helper, so `current_api_client.stack_id` is never consulted.
- `#show` (`:22-25`) then renders `shipit/ccmenu/project` (`app/views/shipit/ccmenu/project.xml.builder`) with the unscoped `stack` and its `deploys_and_rollbacks.last`.

Attacker flow: attacker holds a legitimately-issued API token for stack A with permission `read:stack` (`ApiClient#authentication_token`, generated for stack A). They send `GET /stacks_id_or_path/cc_menu.xml?stack_id=B&token=<A's token>` (route param name is `stack_id` per the controller). `authenticate_api_client` (overridden in CCMenuController, `:33-36`) authenticates the client from the token alone. `require_permission!(:read, :stack)` passes because the client's `permissions` array contains `"read:stack"` — this check is scope-string only. `#stack` then resolves `Stack.from_param!("B")` against all stacks, unscoped, returning stack B regardless of the token's `stack_id`. The response renders stack B's latest deploy/rollback status (branch, activity, success/failure) in the CC-menu XML.

Existing guards do not prevent this: `require_permission!` performs no stack binding check; the `stacks` scoping helper that would perform that check is simply not used by this controller's `#stack` override.

### Impact Explanation
An attacker holding any valid `read:stack`-scoped token (even one issued for an unrelated repository/stack) can read cross-tenant deploy status information (latest deploy/rollback outcome, timestamps, running state) for any other stack in the Shipit instance by supplying a different `stack_id` param with their own token. This is an unauthenticated-for-target-stack read of stack state — matching "High: unauthenticated read of stack state" (the caller is authenticated but never authorized for the target stack, so it is effectively an authorization bypass allowing cross-tenant read). It is repeatable against arbitrary stacks by enumerating `stack_id`/path values, with no additional privilege needed beyond possessing any `read:stack` token.

### Likelihood Explanation
Preconditions: attacker must possess at least one valid API token with `read:stack` permission for any stack (a common permission granted to CI/CD integration tools, e.g., for a repository the attacker legitimately controls). No GitHub secrets, session, or elevated Shipit role required. The endpoint is a standard public route (`cc_menu.xml`), used for CI status badges/monitors, so it's easily reachable. Cost is a single HTTP GET request with a different `stack_id`; fully repeatable and scriptable for enumeration across all stacks.

### Recommendation
Change `CCMenuController#stack` to reuse the inherited stack-scoping helper instead of hitting `Stack` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the override entirely (falling back to `BaseController#stack`), so `current_api_client.stack_id` scoping is honored consistently with the rest of the API controllers.
