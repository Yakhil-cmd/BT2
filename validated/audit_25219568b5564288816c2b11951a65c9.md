### Title
Cross-organization team-membership forgery via unscoped `github_id` lookup in `MembershipHandler` breaks the organization-authenticated-vs-team-written binding - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit.github(organization:)` supports a **multi-organization** configuration in which each configured GitHub organization has its own independent `webhook_secret` [1](#0-0) . The `WebhooksController#verify_signature` action selects *which* organization's secret to verify the payload against by reading the untrusted, not-yet-verified `repository_owner`/`organization.login` field straight out of the JSON body [2](#0-1) . This is by design — the signature is still checked against the whole raw body using that organization's own secret — but it means the *only* guarantee provided by the check is "this payload was signed by organization X's webhook secret", not "this payload targets organization X's resources."

`Team::MembershipHandler#find_or_create_team!` and `Team#add_member` then act on `params.team.id` (a GitHub team id) with **no scoping to the authenticated organization**: `Team.find_or_create_by!(github_id: params.team.id)` looks the team up purely by its numeric GitHub id [3](#0-2) . Because `Shipit.github_teams` (the set of teams that grant application authorization via `User#authorized?`) is also just a set of `Team` rows keyed by id [4](#0-3) [5](#0-4) , any organization configured in `secrets.github` (each with its own independent, weaker/less-trusted webhook secret) can forge a `membership` webhook whose signature is valid for *its own* secret while writing membership into a `Team` record that belongs to (has the same numeric `github_id` as) a completely different, more privileged organization's authorization team.

### Finding Description
The break is: **binding = "organization whose webhook_secret authenticated the request" ≠ "organization/team whose membership record is actually written."**

1. `WebhooksController#verify_signature` derives `repository_owner` from the still-unverified JSON payload (`params.dig('repository','owner','login') || params.dig('organization','login')`) and uses it purely to *pick* which `GitHubApp`/secret to validate the signature against [6](#0-5) , then hands the same payload to the handler.
2. For the `membership` event, `MembershipHandler` extracts `params.team.id` and `params.organization.login` from that same attacker-supplied JSON, and looks up or creates the `Team` **solely by `github_id`**, storing `organization: params.organization.login` only on creation (an already-existing `Team` row keeps whatever `organization` value it has) [7](#0-6) .
3. `Team.find_or_create_by_handle` on the other hand computes `github_id` for the authorized team by fetching it live from GitHub for a given `organization/slug` [8](#0-7) , meaning an authorized team such as `Shopify/developers` has some fixed `github_id`.
4. If Shipit is configured for multiple organizations (each with an independent, separately provisioned `webhook_secret`), an operator/attacker of one lower-trust organization can send a `membership` webhook, correctly signed with *their own* org's secret, whose `team.id` equals the `github_id` of the *authorized* team belonging to a different, higher-trust organization, and `member.login` set to any GitHub username. `MembershipHandler#process` will add that arbitrary user to the existing `Team` row (matched purely by id) [9](#0-8) .
5. Once added, that user (once they also authenticate via OAuth as themselves, which is unprivileged/self-service) passes `User#authorized?`, because that method checks membership by team **id** against `Shipit.github_teams`, with no re-verification that the underlying GitHub organization was the one that granted the membership [4](#0-3) .

### Impact Explanation
This escalates an attacker (who only controls a *secondary*, lower-trust GitHub organization configured on the same Shipit instance — no Shipit session, API token, or private key is required) directly into `Shipit.github_teams` authorization for the *primary* organization, which the rules classify as **High** impact ("escalation into `Shipit.github_teams` authorization"). Once authorized, the attacker gains full authenticated access to the Shipit UI/session for every stack, enabling triggering of deploys/rollbacks and reading of all task output/build state.

### Likelihood Explanation
Requires the instance to be configured with the multi-organization `secrets.github` schema (a supported code path in `Shipit.github`/`github_app_config`) where a lower-trust org's webhook secret differs from the primary org's, and requires GitHub team ids to collide/be guessable or discoverable (team ids returned by the GitHub API are not secret and are visible to any member of that team, or via the `membership` webhook payload itself when it originally added a member to that team). This is a real, code-level flaw in this engine's own trust boundary (unscoped `find_or_create_by!(github_id:)`), independent of any GitHub-side control, so likelihood is moderate — it requires multi-org setup but no privileged credentials.

### Recommendation
Scope the `Team` lookup in `MembershipHandler#find_or_create_team!` by both `github_id` **and** `organization` (derived from the authenticated `repository_owner` used in `verify_signature`, not merely `params.organization.login`), and reject/ignore membership webhooks whose `organization.login` does not match the organization that was used to verify the webhook signature. Additionally, `Team.find_or_create_by!` should never silently reuse an existing team row across organizations solely by numeric id.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `primary` (whose team `Shopify/developers`, `github_id: 555`, is listed in `Shipit.github_teams`) and `secondary` (an org the attacker administers, with its own distinct `webhook_secret`).
2. The `Team` row for `Shopify/developers` already exists locally with `github_id: 555` (created earlier via `Team.find_or_create_by_handle` when `Shipit.github_teams` was first resolved).
3. Attacker crafts a `membership` webhook payload:
   ```json
   {
     "action": "added",
     "team": { "id": 555, "name": "developers", "slug": "developers", "url": "..." },
     "organization": { "login": "secondary" },
     "member": { "login": "attacker-login" }
   }
   ```
4. Attacker signs it with `secondary`'s webhook secret and posts it to `/webhooks`. `WebhooksController#verify_signature` resolves `repository_owner` → `"secondary"`, uses `secondary`'s `webhook_secret`, and the signature verifies successfully [6](#0-5) .
5. `MembershipHandler#process` finds the existing `Team` with `github_id: 555` (the `Shopify/developers` team) and adds `attacker-login` as a member [9](#0-8) .
6. `attacker-login` subsequently logs in via GitHub OAuth as themselves (no special privilege needed), and `User#authorized?` returns `true` because they are now a member of a `Team` present in `Shipit.github_teams` [4](#0-3) , granting full access to the Shipit instance.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    end
