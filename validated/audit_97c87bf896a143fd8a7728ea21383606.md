### Title
Hookify's `action: block` rule for `UserPromptSubmit` (and any event other than `Stop`/`PreToolUse`/`PostToolUse`) never actually blocks — only shows a message - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine.evaluate_rules` only emits an enforceable deny signal (`decision: "block"` for `Stop`, or `hookSpecificOutput.permissionDecision: "deny"` for `PreToolUse`/`PostToolUse`) for three hard-coded event names. For every other `hook_event_name` — notably `UserPromptSubmit`, which hookify explicitly supports — a matched blocking rule falls through to the generic `else` branch that returns only `{"systemMessage": combined_message}`, with no field Claude Code interprets as a deny/halt instruction.

### Finding Description
In `evaluate_rules`, once any rule with `action == 'block'` matches, the code branches purely on `hook_event`: [1](#0-0) 

- `hook_event == 'Stop'` → returns `decision: "block"`.
- `hook_event in ['PreToolUse', 'PostToolUse']` → returns `hookSpecificOutput.permissionDecision: "deny"`.
- anything else (including `UserPromptSubmit`, `SessionStart`, `SessionEnd`, `PreCompact`, `Notification`, `SubagentStop`) → returns only `systemMessage`, with **no decision/deny field at all**.

The `UserPromptSubmit` hook executor calls this same function and blindly forwards whatever dict comes back to stdout, always exiting `0`: [2](#0-1) 

Claude Code's documented hook protocol treats a hook's output as advisory unless it contains a recognized field such as `decision`/`permissionDecision` (or a non-zero/blocking exit code) — plain `systemMessage` is just informational text shown to Claude/the transcript. Because hookify always exits `0` and the `UserPromptSubmit` branch never sets `decision`, an `action: block` rule targeting the `prompt`/`UserPromptSubmit` event (or `SubagentStop`, `SessionStart`, etc.) degrades silently into a warning: the message is displayed, but the prompt/session event is not actually halted.

This directly violates the stated invariant that "block action must actually deny, not just warn." Any hookify rule authored against `event: prompt` (the config loader's designation for `UserPromptSubmit`, see `load_rules(event='prompt')` in `userpromptsubmit.py`) with `action: block` is non-functional as a hard block — it only warns — even though the rule author and any downstream consumer of hookify's `action: block` semantic reasonably expect the operation to be stopped.

### Impact Explanation
A user/maintainer who configures a hookify `.local.md` rule with `action: block` for prompt-level or session-level content policy (e.g., "block prompts containing X") gets a false sense of enforcement: the dangerous/forbidden prompt or session event proceeds to be processed by Claude normally, with only a cosmetic warning message attached. This is a policy/deny-bypass in the plugin's own security control surface — the exact "deny means deny" guarantee hookify advertises for `action: block` is broken for `UserPromptSubmit` and all non-`Stop`/`PreToolUse`/`PostToolUse` events, silently weakening any prompt-submission gating built on hookify.

### Likelihood Explanation
Fully deterministic and always reachable: any `.local.md` rule with `event: prompt` (or any other event besides `bash`/`file`/`stop` which map to `PreToolUse`/`PostToolUse`/`Stop`) and `action: block` that matches incoming input will trigger this code path on every single matching `UserPromptSubmit` invocation. No special privileges or timing are required — it is a straightforward logic gap in `evaluate_rules`.

### Recommendation
Add an explicit `UserPromptSubmit` branch that returns a real deny signal recognized by Claude Code's hook protocol for that event (e.g., `{"decision": "block", "reason": combined_message, "systemMessage": combined_message}`), and extend similar explicit handling for any other events hookify intends to support with blocking semantics (`SubagentStop`, etc.), rather than falling through to a message-only `else`. Alternatively, fail closed by treating unrecognized events under `action: block` as an error/hard stop rather than best-effort warning.

### Proof of Concept
```python
# test_rule_engine_userpromptsubmit_block.py
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

def test_block_rule_on_userpromptsubmit_actually_blocks():
    rule = Rule(
        name="block-bad-prompt",
        enabled=True,
        event="prompt",
        action="block",
        conditions=[Condition(field="user_prompt", operator="contains", pattern="forbidden")],
        message="This prompt is forbidden.",
    )
    engine = RuleEngine()
    input_data = {
        "hook_event_name": "UserPromptSubmit",
        "user_prompt": "please run forbidden action",
    }
    result = engine.evaluate_rules([rule], input_data)

    # Expect a recognized deny signal, not just a message
    assert result.get("decision") == "block" or (
        "hookSpecificOutput" in result
        and result["hookSpecificOutput"].get("permissionDecision") == "deny"
    ), f"Blocking rule did not produce a deny signal, got: {result}"
```
Running this against the current implementation fails: `result` is `{"systemMessage": "**[block-bad-prompt]**\nThis prompt is forbidden."}` with no `decision` or `permissionDecision` key, demonstrating the block-that-doesn't-block defect.

def main():
    """Main entry point for UserPromptSubmit hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Load user prompt rules
        rules = load_rules(event='prompt')

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0
        sys.exit(0)
