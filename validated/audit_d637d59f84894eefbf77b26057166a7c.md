### Title
Missing `return` after exception in `handleSavedPrivatePayments` causes double-invocation of `cb`, unlocking `saved_private` mutex prematurely and enabling concurrent processing of private payment records - (File: network.js)

### Summary
In `network.js`, the private-payment reprocessing routine `handleSavedPrivatePayments` iterates unhandled private-payment rows with `async.each`, guarding shared state with the `["saved_private"]` mutex. [1](#0-0)  For each row, `validateAndSave()` computes a hash of the head element's payload inside a `try/catch`; on failure it calls `deleteHandledPrivateChain(..., cb)` (which itself invokes `cb`) but the `catch` block has no `return` statement, so execution falls through to the rest of the function and unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, whose `ifOk`/`ifError`/`ifWaitingForChain` handlers each call `cb` again. [2](#0-1)  This is the closest reachable analog of a "use object after it should have been retired" scheduling bug: the per-item async completion token (`cb`) is invoked twice for the same unit of work.

### Finding Description
An attacker who can get a private-payment element accepted into `unhandled_private_payments` (any private-payment counterparty, since `receivePrivatePayment`'s `savePrivatePayment` only validates `unit`/`message_index`/`output_index`, not the payload shape) can craft a payload that causes `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` to throw (e.g., a payload value type unsupported by the hashing routine). [3](#0-2) [4](#0-3) 

When the hash call throws:
1. The `catch` block sends an error result and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)`, which deletes the DB row and then calls `cb()`. [5](#0-4) [6](#0-5) 
2. Because there is no `return` after the `catch`, control continues to `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, which independently validates/saves the chain and, in any of its three outcome branches, calls `cb` a second time (directly, or via a second `deleteHandledPrivateChain` call). [7](#0-6) 

`async.each`'s completion bookkeeping is not protected against a double-completion of a single iteratee; a second `cb` invocation for the same item is counted again toward completion, so the top-level `function(){ unlock(); ... }` final callback of `async.each` can fire while other rows from the same batch are still mid-flight (still awaiting `graph.determineIfIncludedOrEqual`, DB queries, etc. inside `validateAndSavePrivatePaymentChain`). [8](#0-7)  Calling `unlock()` early releases the `["saved_private"]` mutex key while genuinely-still-running validations for other unhandled private payments in the same batch are in flight. [9](#0-8) 

Because `handleSavedPrivatePayments` is invoked opportunistically from many code paths (`findAndHandleJointsThatAreReady`, after saving new units, on `comeOnline`, etc.), an early unlock lets a second, fully concurrent `handleSavedPrivatePayments` run select and process the *same still-in-flight* rows again (the first pass has not deleted them yet, since its `validateAndSavePrivatePaymentChain` call is still pending), because a normal `lock(["saved_private"], ...)` call from elsewhere is now free to acquire the lock. [10](#0-9) [11](#0-10)  Each `validateAndSavePrivatePaymentChain` call opens its own DB connection with `BEGIN`/`COMMIT`, and the duplicate check queries `outputs` for an existing row before the first transaction has committed, so two overlapping transactions on separate connections can both pass the "not yet present" check for the same private output and both proceed to insert/credit it. [12](#0-11) 

### Impact Explanation
This can lead to the same private output/payment chain being validated and written twice concurrently (a private double-credit), or corrupting/duplicating state tracked in `assocNewUnits` and the `"new_my_transactions"`/`key` events, which drive wallet balance and UI updates. In the worst case this results in a wallet or private-asset holder crediting the same private payment twice (effectively counterfeiting/duplicating a private balance entry), which maps to the "unauthorized spending / duplicate crediting of a stable output" impact category. It requires no privileged access — any private-payment counterparty can supply the malformed payload that triggers the missing `return`.

### Likelihood Explanation
Triggering the malformed-payload exception is straightforward for a private-payment counterparty (crafting a payload value that fails inside `objectHash.getBase64Hash`). However, actually winning the race to get two concurrent `handleSavedPrivatePayments` invocations to double-process the *same* record depends on timing (batch composition and DB latency), so likelihood is moderate rather than trivial-and-guaranteed, but it is deterministically reachable by a chatty counterparty sending several private-payment chains in quick succession while also triggering other events that call `handleSavedPrivatePayments`/`findAndHandleJointsThatAreReady`.

### Recommendation
Add a `return` statement after the `catch` block in `validateAndSave` inside `handleSavedPrivatePayments` so that `cb` is invoked exactly once per row:
```js
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```
Additionally, consider guarding `cb` with a one-shot wrapper (call-once) at the top of the `async.each` iteratee as defense in depth against any other latent double-invocation, and make `validateAndSavePrivatePaymentChain`'s duplicate-output check race-safe (e.g., unique constraint on the relevant columns, or serializing per-output processing) so concurrent transactions cannot both pass the "not yet present" check for the same private output.

### Proof of Concept
1. As a private-payment counterparty, send (or get saved into `unhandled_private_payments` via `receivePrivatePayment`) a private-payment chain whose head element's `payload` is malformed such that `objectHash.getBase64Hash(payload, true)` throws (e.g., an unsupported field type accepted by the loose checks in `receivePrivatePayment`/`handlePrivatePaymentChains` but rejected inside the hashing routine). [3](#0-2) 
2. Trigger `handleSavedPrivatePayments` (e.g., by causing `findAndHandleJointsThatAreReady` to run, or waiting for one of its periodic callers). [10](#0-9) 
3. Observe that `cb` is called twice for this row (once from the `catch`'s `deleteHandledPrivateChain`, once from `validateAndSavePrivatePaymentChain`'s outcome handlers), causing `async.each`'s final callback (`unlock()`) to run before other rows in the same batch finish. [13](#0-12) 
4. While the lock is prematurely free, trigger a second concurrent `handleSavedPrivatePayments` call (e.g., via another unit becoming ready) that selects and reprocesses one of the still-in-flight rows, resulting in `privatePayment.validateAndSavePrivatePaymentChain` being invoked twice concurrently for the same private output before either transaction commits, so both pass the pre-insert duplicate check in `private_payment.js`. [14](#0-13)
