### Title
Webhook signature check keyed on `repository.owner.login` while handlers act on independent `organization.login`/`repository.full_name` fields — signature bypass via unconfigured org secret grants forged team membership / cross-repo events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using `repository_owner`, a field parsed out of the attacker-supplied JSON body itself. The handlers that actually perform writes (`MembershipHandler`, `PushHandler`, etc.) key their side effects on *different* attacker-controlled fields in that same body (`organization.login`, `repository.full_name`). In a multi-organization Shipit deployment (a configuration this engine explicitly supports and ships test fixtures for), if any configured organization has no `webhook_secret` set, signature verification for that organization trivially returns `true`, letting an attacker forge a fully valid "verified" webhook whose payload content targets a *different*, secured organization/repository.

### Finding Description
`verify_signature` picks the signing secret using a field read straight out of the unauthenticated request body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` bypasses verification entirely when no secret is configured for the selected org: [3](#0-2) 

`Shipit#github` resolves a distinct config per organization when the engine is running in the (supported) multi-org schema: [4](#0-3) 

The repo's own dummy test fixtures demonstrate multi-org configs where `webhook_secret` is left `nil` for organizations: [5](#0-4) 

Once `verify_signature` passes (because it checked the secret of the org named in `repository.owner.login`, which has no secret configured), the request body is dispatched to handlers unchanged. Those handlers use *different* fields to decide what to write:
- `MembershipHandler` uses `params.organization.login` (not `repository_owner`) to find/create the `Team` and add/remove the specified `member.login`: [6](#0-5) 
- The generic `Handler` base class (used by `PushHandler`, `StatusHandler`, etc.) resolves the target `Stack`/`Repository` via `repository.full_name`, independent of `repository.owner.login`: [7](#0-6) 

So the binding the security check is supposed to enforce — "the organization whose secret validated this payload" == "the organization/repository the payload's content is applied to" — does not hold. An attacker can set `repository.owner.login` (or the `organization.login` fallback used only for signature selection) to an org with no configured `webhook_secret`, while setting the semantically-consequential fields (`organization.login` for membership, or `repository.full_name` for push/status) to a different, secured org/repo.

### Impact Explanation
For the `membership` event this directly escalates into `Shipit.github_teams` authorization (explicitly listed as a valid High-impact target): an attacker with no credentials can add an arbitrary GitHub login (including their own, if that login is otherwise known to have registered a Shipit `User`) to any `Team` referenced by `Shipit.github_teams`, which gates access to the entire Shipit UI/API per `User#authorized?`: [8](#0-7) 
This is an authorization bypass reachable with zero valid credentials, contingent only on one configured organization in a multi-org Shipit deployment lacking `webhook_secret` — a state the repository's own fixtures show is a realistic/supported configuration, not a contrived edge case.

For `push`/`status` events the same field-mismatch lets an attacker forge sync/status events for stacks belonging to a different, secured organization, without ever presenting a valid signature for that organization.

### Likelihood Explanation
Requires network access to the mounted `/webhooks` endpoint (unauthenticated by design) and a Shipit deployment using the multi-organization secrets schema where at least one configured organization has no `webhook_secret`. No GitHub credentials, Shipit session, or API token are needed. Single-organization deployments are not affected, since `Shipit#github` ignores the `organization:` argument entirely in that mode (`lib/shipit.rb` lines 170-181), which limits exploitability to multi-org setups specifically.

### Recommendation
Bind the field used to select the verification secret and the field used to perform the write to the same value, and refuse to treat verification as satisfied when the resolved GitHub App has no `webhook_secret` configured (fail closed rather than `return true unless webhook_secret`). Additionally, handlers should cross-check that `organization.login` (or the effective org for the event) matches the organization whose secret validated the request before acting on team membership or repository state.

### Proof of Concept
Given a Shipit deployment configured with two organizations, `unsecured-org` (no `webhook_secret`) and `shopify` (`webhook_secret` configured, and referenced by `Shipit.github_teams`):

```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   (arbitrary/invalid)
Content-Type: application/json

{
  "action": "added",
  "team": { "id": 48, "name": "Developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "shopify" },
  "member": { "login": "attacker-controlled-login" },
  "repository": { "owner": { "login": "unsecured-org" } }
}
```

`verify_signature` resolves `Shipit.github(organization: "unsecured-org")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of the (invalid) `X-Hub-Signature` header. `MembershipHandler` then processes the payload against `organization.login = "shopify"`, adding `attacker-controlled-login` to the `Developers` team, which is part of `Shipit.github_teams` — granting that account authorized access to Shipit without ever presenting a valid `shopify` webhook signature.

**Note on limitations:** I was unable to fully trace how `Shipit.github_teams` is populated/configured (only partial matches were found in `lib/shipit.rb` and `app/controllers/concerns/shipit/authentication.rb`) within the available indexed context, so I could not confirm the exact team-selection semantics end-to-end from the index alone; a Devin session with full repository access would be needed to verify this last link precisely.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
