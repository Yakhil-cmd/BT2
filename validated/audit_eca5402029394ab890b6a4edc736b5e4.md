### Title
Open redirect via unvalidated `omniauth.origin` in `GithubAuthenticationController#callback` - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`GithubAuthenticationController#callback` redirects the browser to `request.env['omniauth.origin']` with no validation that the value is a same-host path [1](#0-0) . OmniAuth's default request-phase behavior populates `session['omniauth.origin']` (later exposed as `env['omniauth.origin']` on callback) directly from the unauthenticated `params['origin']` query parameter, and Shipit's OmniAuth setup does not override this with an allow-list [2](#0-1) . As a result, an attacker-controlled `origin` value survives the entire GitHub OAuth round trip and is used verbatim in `redirect_to`.

### Finding Description
The claimed binding is: `return_url` used in `redirect_to(return_url)` (line 20) `==` a same-origin path under the Shipit host. In the actual code, `return_url = request.env['omniauth.origin'] || root_path` (line 8) with no host/scheme check before the redirect on line 20 [3](#0-2) .

`request.env['omniauth.origin']` is populated by the OmniAuth middleware during the `request` action (`GET /github/auth/github`), which is mounted unmodified via `app.middleware.use(OmniAuth::Builder) { provider(:github, *Shipit.github.oauth_config) }` — Shipit passes no `origin_param` override or validation callback [2](#0-1) . OmniAuth's stock `Strategy#request_call`/`callback_phase` logic takes `request.params['origin']` verbatim (falling back to `HTTP_REFERER`) and stores it in the session, later exposing it as `env['omniauth.origin']` on the callback step — this is standard, well-documented OmniAuth behavior when the host app does not restrict it. Shipit's own login redirect at `force_github_authentication` also feeds `origin: request.original_url`, confirming the app intends `origin` to be a same-host value but never enforces it anywhere [4](#0-3) .

Attacker flow: victim clicks `GET /github/auth/github?origin=https://evil.example`. OmniAuth stores `https://evil.example` as `omniauth.origin`. Victim authenticates with GitHub (legitimately, using their own credentials — no secret of Shipit's is exposed). On callback, `GithubAuthenticationController#callback` sets `session[:user_id]`/`session[:authenticated]` for the *victim's own Shipit session* (this part is not attacker-controlled and not itself compromised), then unconditionally executes `redirect_to('https://evil.example')`, sending the victim's browser to the attacker's site immediately after completing a real OAuth login on the legitimate Shipit host.

No existing guard intercepts this: `force_github_authentication` only fires for unauthenticated requests to *other* Shipit pages and itself doesn't sanitize `origin` before generating the login link; `verify_signature`/webhook checks are unrelated (this is a browser-facing OAuth flow, not a webhook); there is no `Repository`/`Stack` model validation involved since no persisted record is written from `origin`. The only existing test asserts sign-in works but never asserts anything about the redirect destination, so the open redirect is unexercised by tests [5](#0-4) .

### Impact Explanation
This is a browser-redirect vulnerability, not a credential- or record-mutation vulnerability: no `github_access_token`, `api_clients_secret`, or session token is exposed to the attacker, and the victim's Shipit session is created normally on the legitimate host. The concrete effect is that, immediately after a real OAuth login, the victim's browser is sent to an attacker-chosen URL — a "forced OAuth completion" / open-redirect primitive useful for phishing continuation (e.g., presenting a fake follow-up page, or chaining into a separate credential-harvesting site) as called out in the severity table under "session fixation / forced OAuth completion" (High). It does not by itself yield an unauthorized deploy, rollback, merge, or secret exfiltration, and is repeatable against any victim who clicks a crafted link, for any Shipit deployment that enables GitHub OAuth (`Shipit.github.oauth?`).

### Likelihood Explanation
Preconditions are minimal and match the unprivileged-attacker model: Shipit must have OAuth enabled (`Shipit.github.oauth?` true, the documented/standard configuration) [2](#0-1) ; no Shipit session, API token, or GitHub secret is required. The attacker only needs to get a victim to click a link of the form `/github/auth/github?origin=https://evil.example` and let the victim complete their own real GitHub login — a low-cost, repeatable social-engineering-adjacent action (link click only, not credential theft). This is fully consistent with OmniAuth's documented default `origin` handling, which is why applications are commonly advised to validate/allow-list the origin before use.

### Recommendation
In `Shipit::GithubAuthenticationController#callback`, validate `request.env['omniauth.origin']` before using it in `redirect_to`: only accept it if it is a relative path (no scheme/host) or matches `Shipit.host`, otherwise fall back to `root_path`. For example, parse with `URI.parse` and reject any value where `.host` is present and doesn't equal the configured `Shipit.host`, or restrict to `request.env['omniauth.origin']` matching `%r{\A/(?!/)}` (a same-app relative path only). Apply the same validation to the `origin:` param accepted by the `request` phase / `force_github_authentication` redirect so an attacker-supplied `origin` can never be round-tripped through OmniAuth in the first place.

```ruby
test ":callback redirects to attacker-controlled external origin (open redirect)" do
  auth = OmniAuth::AuthHash.new(
    credentials: OmniAuth::AuthHash.new(token: 's3cr3t'),
    extra: OmniAuth::AuthHash.new(
      raw_info: OmniAuth::AuthHash.new(
        id: 44, name: 'Shipit User', email: 'shipit-user@example.com',
        login: 'shipit-user', avatar_url: 'https://example.com',
        api_url: 'https://github.com/api/v3/users/shipit-user'
      )
    )
  )
  @request.env['omniauth.auth'] = auth
  @request.env['omniauth.origin'] = 'https://evil.example'

  get :callback

  # Binding under test: return_url (redirect target) should equal a same-host path,
  # not the attacker-controlled absolute external URL.
  assert_not_equal 'https://evil.example', response.location
  assert_redirected_to root_path # expected safe behavior; currently FAILS because:
  # assert_equal 'https://evil.example', response.location  <- actual current behavior
end
```
This demonstrates that the redirect target equals the attacker-supplied `omniauth.origin` value unmodified, violating the intended same-host binding, with no live GitHub interaction required (OmniAuth env vars are stubbed directly, matching the pattern of the existing test).

```ruby
    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint

      # is authenticated.
      session[:authenticated] = true
```

```ruby
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
```
