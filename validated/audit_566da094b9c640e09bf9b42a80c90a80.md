### Title
Webhook signature verification is bound to the payload's `repository.owner.login`/`organization.login`, but `StatusHandler` writes `Status` records by raw commit SHA with no repository check — cross-organization forged CI statuses can trigger deploys ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to HMAC-verify a webhook against using an attacker-supplied field of the JSON body itself (`repository.owner.login` or `organization.login`). Once that check passes, `Shipit::Webhooks::Handlers::StatusHandler#process` does not re-validate that the commit it is about to write a status for belongs to the same organization/repository that was used to authenticate the request — it simply does `Commit.where(sha: params.sha)` across the entire installation. This is the same class of bug as the reported Bancor `transferOrchestratorToken()` issue: a value that is *acted upon* (the target commit/stack to write) is never covered by the check that is supposed to authorize the action (the org whose secret validated the signature).

### Finding Description
- `WebhooksController#verify_signature` picks the signing organization purely from the incoming JSON, before any cryptographic check has taken place: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` only performs an HMAC check over the raw body; it does not, and cannot, verify that the `repository`/`organization` fields embedded in that body are truthful about which repository is actually referenced elsewhere in the same payload — the signature merely proves the payload came from whichever secret matched `repository_owner`: [3](#0-2) 

- Downstream, `Handler#stacks` scopes work to a specific repository via `payload.dig('repository', 'full_name')`: [4](#0-3) 

  But `StatusHandler`, unlike `PushHandler`, never calls `stacks`/`repository_name` at all — it resolves the target purely by commit SHA, globally, across every stack tracked by the Shipit instance: [5](#0-4) 

- The binding that should hold is: `organization that authenticated (repository_owner used to pick webhook_secret)` == `organization/repository that is written (commit.stack.repository)`. `StatusHandler` never enforces this equality — it writes a `Status` for any `Commit` row whose `sha` matches the attacker-chosen value, regardless of which stack/repository/organization that commit actually belongs to.

- `Status` creation is not inert: it enables CI on the stack and schedules continuous delivery: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who administers (or otherwise legitimately knows the GitHub App webhook secret of) *any one* organization tracked by the Shipit instance can forge a `status` webhook event: they set `repository.owner.login`/`organization.login` in the JSON body to their own organization (so `verify_signature` uses their own known secret and passes), while setting `sha` to the commit SHA of a target stack belonging to a *different* organization/repository they do not control. Because `StatusHandler` matches only on `sha` with no scoping to the authenticated repository, the forged `success`/`failure` status is written against the victim stack's commit. Since `Status#enable_ci_on_stack` and `Status#schedule_continuous_delivery` fire on creation, this can flip CI gating and trigger an unauthorized continuous-delivery/deploy cycle on a stack the attacker was never authorized to interact with — satisfying the "unauthorized deploy" / cross-repository-write impact class.

### Likelihood Explanation
Exploitation requires only that the attacker control (or know the webhook secret of) one organization already registered with the Shipit instance — a realistic scenario for any multi-tenant Shipit deployment (the engine explicitly supports "Using Multiple GitHub Applications" with per-organization secrets, per `docs/setup.md`), or in installs where `webhook_secret` is left unset for convenience (`verify_webhook_signature` returns `true` unconditionally when blank, per `lib/shipit/github_app.rb:76-77`). No access to the target repository, its GitHub App, or the Shipit UI is required — only the ability to send a signed POST to the shared `/webhooks` endpoint and knowledge of the target commit's SHA, which is public information for any public repo and often knowable in private ones via other statuses/PRs.

### Recommendation
`StatusHandler` (and any other handler that does not currently do so) must scope its lookup to the repository/organization that was actually authenticated, e.g. restrict `Commit.where(sha: params.sha)` to `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { owner: repository_owner })`, or otherwise cross-check that `commit.stack.repository.owner` matches the `repository_owner` value used by `verify_signature` before creating a `Status`. More generally, `WebhooksController` should pass the already-authenticated `repository_owner`/`github_app` down to handlers so every handler can assert consistency between the authenticated identity and the entity it mutates, rather than re-deriving repository context ad hoc (or not at all) per handler.

### Proof of Concept
1. Attacker administers (or is a member with app-settings access to) `org-attacker`, which is registered in Shipit's `config/secrets.yml` with its own `webhook_secret_attacker`, and knows that secret.
2. Victim stack `org-victim/private-repo` is tracked by the same Shipit instance and has a commit with SHA `abc123...` awaiting a required CI status before it can be deployed/merged.
3. Attacker crafts payload:
```json
{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-attacker/decoy" },
  "organization": { "login": "org-attacker" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_attacker, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-attacker"`, looks up `Shipit.github(organization: "org-attacker")`, and the HMAC check passes using the attacker's own known secret.
6. `Shipit::Webhooks.for_event('status')` invokes `StatusHandler`, which runs `Commit.where(sha: 'abc123...')` — matching the victim's commit in `org-victim/private-repo` — and calls `commit.create_status_from_github!(params)`, creating a forged `success` `Status` on the victim stack, which triggers `enable_ci_on_stack` and `schedule_continuous_delivery`, potentially causing an unauthorized deploy of `org-victim/private-repo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
