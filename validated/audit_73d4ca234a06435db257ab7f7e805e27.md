### Title
API deploy/rollback/lock/task/merge actions attribute the acting `User` from the unauthenticated `X-Shipit-User` header instead of the cryptographically verified `ApiClient` identity - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The reported bug (using `msg.sender` instead of `msgSender()`) is a class of vulnerability where an action is authorized/attributed based on an unverified field instead of the value actually covered by the cryptographic verification. In shipit-engine's API, the equivalent binding is broken between `ApiClient#authenticate` (the cryptographically verified caller) and `current_user` (the identity recorded as having performed the action), which is taken from the client-supplied, unsigned `X-Shipit-User` header.

### Finding Description
`Shipit::Api::BaseController` authenticates the caller via a signed `ApiClient` token (`ApiClient.authenticate`, backed by `SimpleMessageVerifier`) [1](#0-0) . This authentication only proves which `ApiClient` (and its associated `creator`/`permissions`/`stack_id`) is calling — it says nothing about which human user is actually behind the request.

However, `current_user` — the value used for authorization side-effects and for attributing the resulting `Deploy`/`Rollback`/`Task`/lock/merge action to a specific `User` — is derived purely from the client-supplied `X-Shipit-User` request header, with no verification against the ApiClient's identity or credentials at all: [2](#0-1) 

Any caller holding one valid `ApiClient` token (scoped e.g. to `deploy:stack`) can set `X-Shipit-User` to the login of any existing `Shipit::User` (case-insensitively looked up) and every downstream action will be recorded/attributed as performed by that arbitrary user:

- `DeploysController#create` → `stack.trigger_deploy(commit, current_user, ...)` [3](#0-2) 
- `RollbacksController#create` → `deploy.trigger_rollback(current_user, ...)` / `active_task.abort!(aborted_by: current_user, ...)` [4](#0-3) 
- `TasksController#trigger`/`#abort` → `stack.trigger_task(..., current_user, ...)` / `task.abort!(aborted_by: current_user)` [5](#0-4) 
- `LocksController#create`/`#update` → `stack.lock(params.reason, current_user)` [6](#0-5) 
- `MergeRequestsController#update` → `MergeRequest.request_merge!(stack, params[:id], current_user)` [7](#0-6) 
- `ReleaseStatusesController#create` → `deploy.report_healthy!/report_faulty!(user: current_user)` [8](#0-7) 

This is confirmed by the project's own test showing the header value becomes the recorded `deploy.user` verbatim: [9](#0-8) 

The binding that should hold is:
`identity verified by ApiClient.authenticate(token)` == `identity attributed to the resulting Task/Deploy/lock/merge action`

Instead, the engine enforces only:
`identity verified by ApiClient.authenticate(token)` == `identity used for permission scope checks (current_api_client)`
while
`identity attributed to the action` == `attacker-controlled X-Shipit-User header`

These two are never required to match, exactly analogous to the reported Solidity bug where the value emitted in an event (`msg.sender`) diverged from the value actually verified by the meta-transaction signature (`msgSender()`).

### Impact Explanation
Any actor in possession of a single valid `ApiClient` token with `deploy:stack` (or `lock:stack`) permission — regardless of who that token's `creator` is — can trigger deploys, rollbacks, task aborts, stack locks, or forced merges while making the audit trail (`lock_author`, `Deploy#user`, `Task#aborted_by`, merge request requester) show an arbitrary different, real `Shipit::User` as responsible. This is an unauthorized deploy/rollback/merge attribution and identity-spoofing issue: it lets a party that legitimately holds only limited/scoped API-client credentials falsify who authorized a production deploy or an emergency stack lock, undermining any downstream authorization or accountability decisions built on `Task#user`/`lock_author` (e.g., hook payloads sent to third parties, UI display of "locked by", incident review). This matches the "unauthorized deploy, rollback, or merge" and "escalation into authorization" impact categories.

### Likelihood Explanation
High. No special access is required beyond a single valid `ApiClient` token (which itself may be scoped to `deploy:stack` for CI-style automation); the attacker only needs to add one unauthenticated HTTP header (`X-Shipit-User`) with any existing user's login. The engine's own test suite documents this exact behavior as intended ("use the claimed user as author"), confirming it is not verified anywhere in the request path.

### Recommendation
Do not trust the client-supplied `X-Shipit-User` header as an unauthenticated identity claim for security-relevant attribution. At minimum:
- Restrict the header-based `identify_user` override to `ApiClient`s that are explicitly trusted/flagged for impersonation (e.g., only the CI-bridge client), and validate that the claimed user is permitted to be impersonated by that specific `ApiClient`.
- Alternatively, bind `current_user` to the `ApiClient#creator` by default, and require a separate, cryptographically-verifiable mechanism (e.g., a scoped JWT signed by Shipit itself, or an explicit per-client allow-list of impersonatable logins) before letting `X-Shipit-User` override it.
- Audit `lock_author`, `Deploy#user`, `Task#aborted_by`, and `MergeRequest` requester fields to ensure they always reflect a verified identity, not an unauthenticated header value.

### Proof of Concept
1. Obtain (or be granted) any valid `ApiClient` token scoped only to `deploy:stack` for a given `Stack` (e.g., a CI service's automation token) — see `authenticate!` in `test/helpers/api_helper.rb` for how the Basic-auth token is derived from `ApiClient#authentication_token`.
2. Issue: `POST /api_clients_stack_id/deploys` with `Authorization: Basic <base64(api_client_token)>` and header `X-Shipit-User: victim-admin-login` (any existing `Shipit::User#login`), plus a valid `sha`.
3. Observe (per `app/controllers/shipit/api/deploys_controller.rb` line 25 and the existing test at `test/controllers/api/deploys_controller_test.rb:49-54`) that the resulting `Deploy#user` is set to `victim-admin-login`'s `User` record, even though that user never made this API call and the ApiClient's real `creator` may be an unrelated automation account.
4. Repeat against `LocksController#create`/`#update` to lock a stack while `lock_author` is falsely attributed to an arbitrary user, or against `MergeRequestsController#update` to force-merge a PR under a spoofed identity.

      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
