### Title
Webhook signature verification fails open when a configured GitHub organization has no `webhook_secret`, allowing unauthenticated forgery of `membership` events that grant `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` treats an absent `webhook_secret` as "nothing to verify" and returns `true` unconditionally, rather than rejecting the request. Combined with the fact that the organization used to *select* which app/secret to verify against is taken from attacker-controlled JSON fields in the unauthenticated request body, this breaks the trust binding "the organization that authenticated" versus "the team/organization data that is written" by `MembershipHandler`. An attacker can forge a `membership` webhook event and get a chosen GitHub login added to any `Team`, including one listed in `Shipit.github_teams`, which is the sole gate used by `User#authorized?`.

### Finding Description
`WebhooksController#verify_signature` resolves which GitHub App configuration (and therefore which `webhook_secret`) to verify against using data from the *unverified* request body itself: [1](#0-0) [2](#0-1) 

`repository_owner` falls back to `params.dig('organization', 'login')` — a field entirely controlled by the attacker in the raw POST body, evaluated *before* any signature is checked.

The verification itself fails open when the resolved organization has no `webhook_secret` configured: [3](#0-2) 

`webhook_secret` is documented as optional in a single-org setup and is commonly left blank when onboarding additional organizations in a multi-org configuration: [4](#0-3) [5](#0-4) 

Once verification passes (because the chosen org has no secret), the event handler is invoked with the entire attacker-supplied JSON, with no further authenticity check: [6](#0-5) 

`MembershipHandler` unconditionally trusts the payload's `team`, `organization`, and `member` fields to create/update a `Team` and add a `User` to it: [7](#0-6) 

Team membership is the sole authorization gate in the engine: [8](#0-7) [9](#0-8) 

**Binding broken:** the organization whose credential (`webhook_secret`) is used to authenticate the request ≠ the organization/team data that `MembershipHandler` actually writes to the database. Because the org-selection field and the fail-open `webhook_secret` check are independent of the payload's actual authenticity, an attacker can pick an org configuration with no secret to authenticate an event whose *content* (team id, member login) is arbitrary.

### Impact Explanation
This escalates into `Shipit.github_teams` authorization without any credential, matching the explicit High-impact criterion "escalation into `Shipit.github_teams` authorization." An attacker who can identify (or cause to exist, via optional per-org config) any configured GitHub organization lacking a `webhook_secret` can send an unauthenticated `membership` webhook forging `action: 'added'`, an arbitrary `team.id` matching one of `Shipit.github_teams`, and any `member.login`, causing `Team#add_member` to record that GitHub login as an authorized member — bypassing GitHub App webhook authentication entirely for a security-critical event type.

### Likelihood Explanation
Requires only that one configured GitHub organization in `Shipit.github` have a blank/unset `webhook_secret` — an explicitly documented "optional" setting — and that the attacker know (or guess) that organization's login. No GitHub credentials, Shipit session, or `ApiClient` token are needed; the request is a plain unauthenticated POST to `/webhooks`.

### Recommendation
- In `GitHubApp#verify_webhook_signature`, do not fail open: require `webhook_secret` to be present for every configured organization at boot/initialization, and reject (422) any webhook whose resolved app config lacks a secret rather than treating it as automatically verified.
- Do not use attacker-controlled `organization.login` / `repository.owner.login` from the raw payload to select the verification key before the signature has been checked; instead validate the signature against all configured secrets, or bind organization resolution to a value that cannot be forged prior to verification.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, where org `victim-org` has `webhook_secret` unset (per `config/secrets.development.shopify.yml`-style multi-org config).
2. Send, without any authentication, credential, or valid GitHub signature:
```
POST /webhooks
X-Github-Event: membership

{
  "action": "added",
  "team": { "id": 4242, "name": "Shopify Developers", "slug": "shopify-developers", "url": "https://example.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-login" }
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "victim-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` (`lib/shipit/github_app.rb:76-77`) returns `true` unconditionally regardless of the (missing/invalid) `X-Hub-Signature` header.
4. `MembershipHandler#process` runs, finds/creates `Team` with `github_id: 4242` and adds a `User` for `attacker-github-login` to it via `team.add_member(member)`.
5. If team `4242` is listed in `Shipit.github_teams`, any `User` record matching that GitHub login now satisfies `User#authorized?`, granting access to trigger deploys/rollbacks/tasks in Shipit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
