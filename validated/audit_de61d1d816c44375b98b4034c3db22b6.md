## Finding

### Title
Missing duplicate-member check in `r of set` / `weighted and` definitions allows multisig-threshold bypass - (File: `definition.js`)

### Summary
`validateDefinition()` in `definition.js` validates the structure of `r of set` and `weighted and` spending-condition operators (used in address definitions, asset `issue_condition`/`transfer_condition`, and AA definitions) but never checks that the elements of `args.set` are distinct. An address (or asset condition) can therefore be constructed where the same underlying authorization leaf (e.g. the same `["sig", {pubkey: P}]` or the same nested `["address", A]`) is repeated multiple times inside the `set`, letting a single keyholder satisfy more than one "slot" of the declared `required` threshold.

### Finding Description
When a definition containing `r of set` or `weighted and` is validated, `validateDefinition` only checks the shape of the object (`required` is a positive integer, `set` is an array with length ≥ 2, `required <= set.length`), but performs no uniqueness check on the entries of `set`: [1](#0-0) 

The same absence of a uniqueness check exists for `weighted and`, whose set members carry individually assigned weights.

At authentication time, `validateAuthentifiers()` independently evaluates every member of `args.set` by its own path and simply counts how many succeeded (`count >= args.required` for `r of set`, `weight >= args.required` for `weighted and`): [2](#0-1) [3](#0-2) 

Because each set member is authenticated at its own independent path (e.g. `r.0`, `r.1`, `r.2`), a definer can put the identical authorization leaf (same public key or same referenced address) at two or more of those paths. The real signer for that one leaf can supply a valid signature/authorization for each of the duplicate paths (since it is the same private key signing the same `unit_hash_to_sign`), satisfying `count`/`weight` for multiple "slots" alone. This defeats the security guarantee that an `r of set`/`weighted and` definition with `required > 1` needs cooperation from that many *distinct* parties.

This is directly analogous to the reported Solidity issue: an array (`locations_` in `addAsset`, here `set` in `r of set`/`weighted and`) that is supposed to contain distinct elements to preserve a security invariant (distinct storage locations vs. distinct independent authorizers) is stored/used without a duplicate check, silently breaking the invariant the surrounding code relies on.

Elsewhere in the same codebase, similar arrays that matter for correctness/security are explicitly deduplicated via a strict sort-order check (e.g. `checkAttestorList` and `validateHeadersCommissionRecipients` both enforce `prev < current`, which additionally rejects duplicates): [4](#0-3) [5](#0-4) 

showing that the project is aware duplicate-prevention matters for arrays like this, yet it is missing for `r of set`/`weighted and` members.

### Impact Explanation
Address definitions, AA definitions, and asset `issue_condition`/`transfer_condition` all funnel through `validateDefinition`. A malicious or naive party constructing (or being tricked into approving) a shared/multisig address or asset condition with a nominal "N of M" threshold can insert a duplicate member so that fewer than N distinct signers actually control it. This can lead to unauthorized spending of shared funds by a party who was intended to control only a fraction of the required threshold, i.e., loss of funds for other cosigners who believed the true security level was "N of M distinct parties."

### Likelihood Explanation
Any address/asset definition author (including one dishonest party in a proposed shared address, e.g. via `wallet_defined_by_addresses.js`'s `handleNewSharedAddress`/`createNewSharedAddress` flow) can craft such a definition; the flaw is entirely in unit-level definition validation (`definition.js`), so it is reachable by any unprivileged actor able to post a unit or propose a shared address/AA with a custom definition — no special network position needed.

### Recommendation
In `validateDefinition`, when validating `r of set` and `weighted and`, compute a canonical, deterministic serialization (e.g. `JSON.stringify`) of each `set` member (or of `member.value` for `weighted and`) and reject the definition if any two members are identical, similar to the sorted/duplicate checks already used for `earned_headers_commission_recipients` and `attestors`.

### Proof of Concept
1. Construct an address/asset definition:
   `["r of set", {required: 2, set: [["sig", {pubkey: P}], ["sig", {pubkey: P}], ["sig", {pubkey: Q}]]}]`
   This is presented/perceived as "2 of 3 distinct signers" but two slots are bound to the same key `P`.
2. `validateDefinition` accepts it because it only checks `required <= set.length` and structural validity of each member — no duplicate check (`definition.js` lines 147-185).
3. When spending, the holder of `P` supplies the same valid signature for both `r.0` and `r.1` paths in `assocAuthentifiers`; `validateAuthentifiers`'s `r of set` handler (`definition.js` lines 692-711) counts both as successful, so `count (2) >= required (2)` is satisfied without any input from `Q`.
4. Funds controlled by this "multisig" address can now be spent unilaterally by the holder of `P` alone, contrary to the intended 2-distinct-party requirement.
