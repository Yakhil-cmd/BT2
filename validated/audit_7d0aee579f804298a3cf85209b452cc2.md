### Title
Nested/shared-address signature validation can transiently fail (self-DoS) when an inner address's `address_definition_change` is not yet stable before `last_ball` - (File: definition.js)

### Summary
The Fenix report describes a class of bug where a routine, unprivileged action (`dettachFromManagedNFT`) re-validates a previously-accepted state (the pool/gauge list) against the *current* live state, and a legitimate but stale reference (a killed gauge) causes the whole transaction to revert, temporarily locking the user out of their own asset. `ocore` has a structurally analogous pattern in address-definition evaluation: every unit spent from a shared/multi-signature address that contains a nested `['address', other_address]` clause is **re-evaluated against the current state of `other_address`'s definition** at validation time [1](#0-0) . If `other_address` recently changed its definition (via `address_definition_change`) and that change is not yet stable as of the spending unit's `last_ball`, the authentifier check for the `'address'` branch can fail even though the signer is legitimately authorized, causing the outer unit to be rejected until stability catches up.

### Finding Description
`validateAuthentifiers` re-validates the full address definition tree (not just cached results) on every unit that spends from an address, specifically because inner addresses can be redefined between spends [1](#0-0) . The code comment explicitly documents this exact class of issue: *"if an inner address was redefined by keychange but the definition for the new keyset not supplied before last ball, the address becomes temporarily unusable"* [2](#0-1) .

The concrete mechanism is in the `'address'` case of the authentifier evaluator: [3](#0-2) 

- `storage.readDefinitionByAddress` looks up the currently-stable definition of the nested address as of `objValidationState.last_ball_mci`.
- If the definition is not yet stable (`ifDefinitionNotFound`), the code only succeeds if the *current spending unit itself* re-declares the inner address's definition among its own `authors` with a `definition` matching the previously-committed chash: `arrDefiningAuthors.length === 0` immediately returns `cb2(false)` [4](#0-3) .
- Unlike the parallel logic in `validateDefinition` (used for a plain, non-authentifier existence check), which explicitly sets `bAllowUnresolvedInnerDefinitions = true` and lets the check pass optimistically [5](#0-4) , the authentifier path (used when an actual signature/spend is being checked) has no such fallback and hard-fails.

Consequence: a shared/multisig address `S` whose definition includes `['address', 'INNER']` depends on `INNER`'s *current stable* definition at spend time, exactly analogous to `_vote`/`_poke` re-checking the *current* `isAlive` state of a gauge that was fine when the vote was cast. If `INNER` is mid-keychange (its `address_definition_change` unit for a *new* keyset has been broadcast but not yet stabilized before `S`'s spending unit's `last_ball`), any owner of `S` who tries to spend and does not also include `INNER`'s (old or new) definition inline in the very same unit gets `cb2(false)` for that authentifier path, and the whole signature check for `S` fails, rejecting the transaction [3](#0-2) .

### Impact Explanation
This is a Denial-of-Service on the user's own funds, structurally identical to the referenced report's impact class: a legitimate spend/detach cannot be completed even though the underlying signer authority is valid, purely because unrelated third-party state (the nested address's keychange stabilization) has not yet caught up. For a shared/multisig address this can block payments from that address for the duration of the stabilization window, and if the participant who needs to co-sign is unaware they must also attach the inner definition inline, the unit will be rejected repeatedly. This does not cause fund loss or double-spend, but it is a genuine temporary fund-freezing condition triggered by ordinary use (a keychange), reachable by any user who structures an address definition with nested `['address', ...]` references — a fully supported, unprivileged feature.

### Likelihood Explanation
Nested address definitions (`['address', other_address]`) and `address_definition_change` are both standard, documented features usable by any wallet/user; no privileged or malicious actor is required — the condition can occur purely from normal, well-intentioned key rotation timing. The developers already anticipated it in a comment, indicating it is a known, reachable edge case rather than a purely theoretical one. It requires a window during which the new definition of the inner address is not yet stable before the last ball of the spending unit, which is a normal, non-adversarial occurrence during any keychange under network conditions with delayed stabilization.

### Recommendation
Provide the same graceful-degradation behavior in the authentifier path (`validateAuthentifiers`'s `'address'` case) as already exists in the non-authentifier `validateDefinition` path: when the inner address's definition is not yet stable, allow the client to explicitly supply/attach the still-valid, previously-used definition (not only requiring it to appear as an "author" in the exact same unit), or provide a clear, actionable error/documentation path directing users to include the inner definition inline until the keychange stabilizes, rather than silently failing signature verification. At minimum, ensure wallets are made aware they must attach the relevant inner definition until the corresponding `address_definition_change` is stable, to avoid unexpected transient DoS.

### Proof of Concept
1. Address `INNER` is a signer inside a nested definition used by shared address `S` (e.g., `S`'s definition contains `['address', 'INNER']`).
2. `INNER` publishes an `address_definition_change` unit switching to a new keyset; this unit is broadcast but not yet stable.
3. A cosigner of `S` attempts to spend from `S`, signing with the still-valid (or newly valid) key for `INNER`, but does not include `INNER`'s definition inline as an author of this same spending unit.
4. During validation, `evaluate` hits the `'address'` case for path referencing `INNER`; `storage.readDefinitionByAddress` returns `ifDefinitionNotFound` because the new definition is not yet stable as of `last_ball_mci` [6](#0-5) .
5. Because `arrDefiningAuthors.length === 0` (the spending unit does not itself declare `INNER`'s definition), the authentifier check returns `cb2(false)` [7](#0-6) , causing the outer signature check for `S` to fail and the unit to be rejected as invalid, even though the signer holds a legitimate key for `INNER`.
6. The spend from `S` remains blocked until `INNER`'s `address_definition_change` becomes stable (or the user manually attaches the definition inline), reproducing the "temporarily undetachable/unusable" DoS pattern described in the original report.
