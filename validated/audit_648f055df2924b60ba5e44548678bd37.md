### Title
Unscoped SHA lookup in `StatusHandler#process` allows one repository's status webhook to flip `blocked?`/`deployable?` on an unrelated stack sharing the same commit SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with a bare, repository-agnostic query (`Commit.where(sha: params.sha)`), then calls `create_status_from_github!` on every matching row regardless of which stack/repository owns it. Because `verify_signature` only authenticates the webhook against the GitHub App/organization installation named in the payload's `repository.owner.login`—not against the specific repository or stack the SHA belongs to—an attacker who owns or controls any repository behind the same Shipit-configured GitHub App/organization can emit a genuinely-signed `status` webhook whose SHA coincides with a commit tracked by a completely different stack, and thereby mutate that victim stack's `Status`/`blocked?`/`deployable?` state.

### Finding Description
The intended invariant is: `status_for(repository_A, sha) == status_for(repository_A's_stack, sha)`, i.e., a status event authenticated for repository A must only ever be written against commits belonging to stacks tracking repository A. `StatusHandler#process` breaks this: [1](#0-0) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

There is no `stack_id`, `repository`, or `github_repo_name` filter — any `Commit` row anywhere in the database whose `sha` column matches the attacker-supplied `sha` parameter is updated, irrespective of which repository/organization the webhook was signed for.

Upstream, `WebhooksController#verify_signature` only checks the signature against the GitHub App keyed by `repository_owner` (`params.dig('repository','owner','login')`): [2](#0-1) 

This proves the request came from *some* repository under that GitHub App/org installation — it does not prove the request came from the specific repository that owns the commit being mutated. Nothing downstream (`drop_unhandled_event`, `ExplicitParameters` schema in `StatusHandler.params`, or the `StatusHandler#process` body itself) re-checks that the commit's `stack.github_repo_name` matches the webhook's `repository.full_name`.

`Commit#create_status_from_github!` then writes a `Status` and re-evaluates deployability/blocking through `add_status`, which can fire `Hook.emit(:deployable_status, ...)`, call `stack.schedule_merges`, and change `Commit#blocked?`/`Commit#deployable?`: [3](#0-2) [4](#0-3) 

`blocked?` is stack-scoped (`stack.blocking_statuses`), so a `failure` status with `context: ci/coverage` injected onto a victim stack's commit — where that stack's `deploy.yml`/`Stack#blocking_statuses` requires `ci/coverage` — flips `blocked?` to `true` (or, on a later `success`, back to `false`), directly gating or unblocking deploys/merges on a stack the attacker never authenticated for.

Exploit flow: attacker controls a repository whose GitHub organization/owner is the same one configured in `Shipit.github(organization: ...)` (i.e., the attacker's own repo, or any repo under an org where Shipit's GitHub App is installed) — this is exactly the class of "unprivileged attacker who can push to a repository they own and emit webhooks from it." They arrange (or simply await/observe) a commit SHA collision with a victim stack's tracked commit — most plausibly via forks/mirrors that share git history, cherry-picked/mirrored commits, or repos split from a common upstream, which is a normal Shipit deployment topology (many stacks, one org). The attacker's own repository emits (or the attacker crafts and sends, since no per-stack secret exists beyond the org-level webhook secret) a `status` event with that shared `sha`, `context: ci/coverage`, `state: failure`. `verify_signature` passes because it is a legitimately signed webhook from the attacker's own repo under the same GitHub App. `StatusHandler#process` then writes the failing status onto every `Commit` row across the entire installation sharing that SHA, including the victim's, flipping `blocked?`/`deployable?` on a stack the attacker has no relationship to.

### Impact Explanation
A `status` payload authenticated for one repository mutates `Status`/`Commit`/`Stack` state belonging to an unrelated repository/stack, directly gating or forcing deploy/merge decisions (`blocked?`, `deployable?`, `stack.schedule_merges`, `Hook.emit(:deployable_status, ...)`) without that stack's owning repository ever authorizing the write. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable against any commit SHA the attacker can predict or produce a collision for, and the blast radius spans every stack sharing the GitHub App/organization webhook secret with the attacker's repository, not just the attacker's own stack.

### Likelihood Explanation
Preconditions: (1) the victim stack must have `blocking_statuses` (or any required/monitored context) configured such that flipping a status changes observable behavior; (2) the attacker's own repository must share the GitHub App/organization-level webhook signing key with the victim's stack (a realistic multi-repo Shipit deployment, since `verify_signature` is keyed by `repository_owner`, i.e., org-wide, not per-repo); (3) a commit SHA collision between the attacker-controlled repo and the victim stack's tracked history must exist — feasible in mirrored/forked-repo topologies, monorepo-split setups, or cherry-pick workflows common to organizations running many Shipit stacks off one upstream. No Shipit session, API token, or GitHub secret is required beyond what GitHub itself provides when the attacker's own repo emits webhooks. The attack costs one HTTP-triggered GitHub status event and is fully repeatable.

### Recommendation
Scope `StatusHandler#process` (and `Commit`/`Status` lookups more generally, e.g., `CheckSuiteHandler`, `refresh_statuses!`) to only the stacks/commits belonging to the `repository.full_name` (or `repository.owner.login` + `repository.name`) present in the verified webhook payload — e.g., `Commit.joins(:stack).where(sha: params.sha, stack: { repository_full_name: params.repository.full_name })` — instead of a bare `Commit.where(sha: params.sha)`. Alternatively/additionally, verify the webhook signature per-repository (not merely per-organization) if the underlying GitHub App configuration supports it.

### Proof of Concept
Minitest plan (add to `test/models/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):

```ruby
test "a status webhook for repository A must not affect a commit belonging to repository B's stack" do
  victim_stack = shipit_stacks(:shipit) # configured with blocking_statuses including 'ci/coverage'
  victim_commit = shipit_commits(:first)
  shared_sha = victim_commit.sha

  # Simulate an attacker-owned repository whose commit accidentally/deliberately shares the same SHA
  # (e.g. a mirrored/forked repo under the same GitHub App/org installation).
  attacker_repository_full_name = "attacker-org/attacker-repo"

  before_blocked  = victim_commit.reload.blocked?
  before_deployable = victim_commit.deployable?

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'ci/coverage',
    'repository' => { 'full_name' => attacker_repository_full_name, 'owner' => { 'login' => 'attacker-org' } }
  }.to_json

  GithubApp.any_instance.stubs(:verify_webhook_signature).returns(true) # attacker's own genuinely-signed webhook

  post :create, body:, as: :json

  victim_commit.reload
  # BINDING UNDER TEST: a status authenticated for attacker-org/attacker-repo
  # must equal no change to victim_stack's commit state.
  assert_equal before_blocked, victim_commit.blocked?,
    "cross-repository status webhook must not flip blocked? on an unrelated stack"
  assert_equal before_deployable, victim_commit.deployable?,
    "cross-repository status webhook must not flip deployable? on an unrelated stack"
end
```

This test demonstrates that `StatusHandler#process`'s `Commit.where(sha: params.sha)` (app/models/shipit/webhooks/handlers/status_handler.rb:21) writes a `Status` onto `victim_commit` even though the webhook's `repository.full_name` does not match `victim_stack`'s tracked repository, changing `blocked?`/`deployable?` — proving the invariant "a `ci/coverage` status affects only the repository that authenticated it" is violated. Note: I was unable to fully verify from the index whether `Shipit.github(organization:)` secrets are strictly per-organization-wide (shared across all repos in that org) versus per-repository in every deployment configuration (`lib/shipit/github_app.rb` details were not fully retrievable in this session) — this affects exactly how broad the attacker's "same GitHub App installation" precondition is in a given deployment, though the core unscoped-SHA-lookup bug in `StatusHandler#process` is confirmed directly from the code.
