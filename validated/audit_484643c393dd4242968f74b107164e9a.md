### Title
Attacker-controlled unbounded submodule graph in synced repo causes persistent sync denial via `--sync-timeout` exhaustion - (File: main.go)

### Summary
The reported Teller Protocol bug is a class of "unbounded attacker-supplied collection causes a resource-limit revert in the withdrawal/commit path," where a borrower controls the size of `_collateralInfo[]` and this later causes `CollateralManager#_withdraw()`'s for-loop to exceed the block gas limit, permanently blocking a state-transition (withdrawal/liquidation) that other actors need. The closest reachable analog in `git-sync` is the `configureWorktree()` submodule step, which iterates/recurses over whatever the upstream (attacker-pushed) commit declares in `.gitmodules`, bounded only by the fixed `--sync-timeout` budget rather than a size limit enforced by git-sync itself.

### Finding Description
`git-sync` pulls an untrusted, remote-controlled git repository and, on every sync iteration, wraps the whole operation in a fixed-duration context: [1](#0-0) 

That single `ctx` is threaded through `fetch`, `rev-parse`, `createWorktree`, and `configureWorktree`, all the way down to `Runner.Run`, which executes the underlying `git` binary via `exec.CommandContext(ctx, ...)`: [2](#0-1) 

Inside `configureWorktree`, after `reset --hard`, git-sync unconditionally attempts to initialize/update submodules if `--submodules` is not `off` (the default is `recursive`): [3](#0-2) 

The number, nesting depth, and recursion of submodules is entirely determined by the content of the commit being synced (`.gitmodules` + nested repos), i.e., by whoever controls the pushed content of the upstream repository — analogous to the borrower freely sizing `_collateralInfo[]` in the Teller bug. There is no limit in `git-sync` on submodule count/depth before invoking `git submodule update --init --recursive`. If a malicious/compromised upstream repository publishes a commit with an extremely large or deeply/recursively nested submodule graph, `git submodule update --init --recursive` (optionally with `--depth`) can take arbitrarily long to clone all nested repositories, exceeding the fixed `--sync-timeout` context deadline (default 120s, from `flSyncTimeout`) exactly the same way an oversized collateral array pushed the `_withdraw()` loop past the block gas limit.

When the context deadline is hit mid-`submodule update`, `runWithStdin` detects `ctx.Err() == context.DeadlineExceeded` and returns an error: [4](#0-3) 

This error propagates up through `configureWorktree` → `SyncRepo` → the outer loop, which increments `failCount` and retries on the same timeout again next period: [5](#0-4) 

Because the new worktree/commit is never checked out successfully, `git.publishSymlink` is never reached and cleanup (`git.cleanup(ctx)`, which prunes stale worktrees / runs GC) is skipped for that iteration since it only runs in the success branch: [6](#0-5) 

The result is that git-sync can never advance past that specific commit — every retry re-executes the same expensive `git submodule update --init --recursive` and hits the same timeout, producing a **persistent, indefinite sync failure** for that ref until `--max-failures` is exceeded (aborting the process with `os.Exit(1)`) or the operator manually raises `--sync-timeout` / removes the offending commit: [7](#0-6) 

### Impact Explanation
This matches the accepted "persistent sync denial" category. The already-published symlink target (last good commit) is not corrupted, but any legitimate update pushed after the poisoned commit can never be synced because `SyncRepo` always attempts to reach `FETCH_HEAD`/the target ref in order — a repo owner who wants to move forward is durably blocked until they intervene operationally (raise the timeout, drop `--submodules`, or fix the upstream repo). If `--max-failures` is set (or defaults to a bound), the process will eventually call `os.Exit(1)` and stop syncing entirely, taking down the sidecar. This is a genuine denial-of-service of the sync function itself, reachable purely by pushing a commit to the tracked ref of an already-configured `--repo` — no credential leakage, no path escape, but a durable service-denial analogous in mechanism (unbounded attacker-sized collection exhausting a fixed resource budget) to the Teller M-13 report.

### Likelihood Explanation
Likelihood is low-to-medium, similar to the original Sherlock judgment ("cost of the attack is high, impacts only a single loan/repo, not all"): it requires (a) write access (or history of push access before being revoked) to the tracked upstream repository, or a supply-chain compromise of it, and (b) crafting/committing a submodule graph large enough that clone+checkout time reliably exceeds `--sync-timeout` (default 120s) — feasible with thousands of small submodules or deeply nested recursive submodules referencing slow/large remotes. This is a self-inflicted or single-tenant DoS: it only affects consumers who are still pointed at the compromised/malicious repo/ref, not other git-sync deployments.

### Recommendation
- Bound submodule processing independent of the outer `--sync-timeout`: enforce a configurable maximum submodule count/depth (or a `--submodules-timeout`) before invoking `git submodule update --init --recursive`, and fail fast with a clear error rather than repeatedly retrying the same doomed operation.
- Consider decoupling "fetch/checkout of primary content" from "submodule materialization" so that a slow/oversized submodule graph does not block publishing an otherwise-valid primary worktree (mirroring the real-world fix applied to the Teller bug: "separating withdraw and repay logic").
- Surface a distinct metric/log signal when a sync repeatedly fails at the submodule step so operators can detect this DoS quickly instead of it looking like a generic timeout.

### Proof of Concept
1. Configure `git-sync --repo=<attacker-writable-repo> --root=/tmp/root --link=link --submodules=recursive --sync-timeout=120s`.
2. Attacker pushes a commit to the tracked ref whose `.gitmodules` references, e.g., thousands of submodule entries or a submodule chain nested many levels deep (each nested submodule itself containing further submodules), such that a full `git submodule update --init --recursive` takes reliably longer than 120s in the sidecar's environment (network-bound clones amplify this cheaply for the attacker).
3. git-sync's `SyncRepo` reaches `configureWorktree` → `git submodule update --init --recursive` at [8](#0-7)  under the shared `ctx` created per-iteration at [1](#0-0) .
4. The command is killed by `exec.CommandContext` when `ctx` expires; `runWithStdin` returns a `context.DeadlineExceeded` error at [9](#0-8) .
5. Every subsequent sync period repeats steps 3–4 identically (same commit, same submodule graph, same timeout), so the symlink is never advanced past the last good commit — a durable sync denial for that ref until an operator intervenes or `--max-failures` triggers process exit at [7](#0-6) .
