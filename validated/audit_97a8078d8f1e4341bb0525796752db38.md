### Title
Webhook signature is verified against the GitHub organization declared in `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, allowing a valid multi-org tenant to forge sync/deploy-triggering events for another org's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is the closest structural analog to the M-13 pattern: two code paths derive a supposedly-equivalent value from the same input using different logic, and the value used for the trust decision (signature/org selection) is not the value that is actually acted upon (the repository operated on). In Rubicon, the fee denominator used in `Position` differs from the one enforced in `RubiconMarket.buy`, so the "trusted"/verified amount and the "acted upon" amount diverge. In shipit-engine, the field used to select which HMAC secret verifies the request (`repository.owner.login`) is not the field the event handlers actually use to decide which `Repository`/`Stack` to mutate (`repository.full_name`), and nothing binds them together.

### Finding Description
`Shipit::WebhooksController#verify_signature` resolves the signing secret using the organization taken directly from the untrusted JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')`, and `Shipit.github(organization: repository_owner)` looks up the per-organization app config (webhook_secret, etc.) from `Shipit.secrets.github`, keyed by that same organization name: [3](#0-2) 

Shipit explicitly supports hosting multiple, independently-configured GitHub organizations/apps on one instance, each with its own `webhook_secret`: [4](#0-3) 

Once the signature check passes, `create` dispatches the *entire, still-untrusted* payload to the registered handlers: [5](#0-4) 

`Handler#stacks` and concrete handlers (e.g. `PushHandler`) resolve the target repository from a **different** payload field, `repository.full_name`, with no comparison back to `repository.owner.login`: [6](#0-5) [7](#0-6) 

Because the signature verifier and the handler consult two different, independently attacker-controllable fields of the same JSON body, the binding: `organization whose secret authenticated the request == repository the handler acts on` is never enforced. A tenant who legitimately owns an installation for `OrgA` (and therefore knows/controls `OrgA`'s configured `webhook_secret`) can send a webhook whose `repository.owner.login` is `"OrgA"` (so the signature is computed and verified with `OrgA`'s known secret) while `repository.full_name` is set to `"OrgB/some-repo"` — a repository/stack belonging to a completely different tenant `OrgB` on the same shipit-engine instance.

### Impact Explanation
For the `push` event, `PushHandler#process` calls `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }`, which is resolved via `repository_name = full_name`, not the verified org. This enqueues `GithubSyncJob` for `OrgB`'s stack with an attacker-chosen `expected_head_sha`, causing the engine to fetch commits/state for `OrgB`'s repository and update `OrgB`'s `Stack`/`Commit` records out of band from `OrgB`'s real webhook traffic. Depending on `OrgB`'s continuous-deployment configuration, syncing new commits can cascade into `CacheDeploySpecJob`/deploy-triggering flows, i.e. an attacker with only `OrgA`-level credentials can inject repository state and influence deploy triggers for `OrgB`'s stack that they otherwise have no authorization over. This crosses the "GitHub identity/organization authenticated vs. repository being written" trust boundary described in scope, satisfying the "cross-repository writes / unauthorized deploy" impact bar.

### Likelihood Explanation
This requires the deployment to use the documented multi-organization configuration (`Shipit.github(organization: ...)`, distinct `webhook_secret` per org) and requires the attacker to be a legitimate, authenticated tenant/admin of at least one configured organization (`OrgA`) on a shared shipit-engine instance also hosting `OrgB`. That is a realistic scenario for shared/hosted shipit-engine deployments serving multiple orgs, and it needs no privileged Shipit session, `ApiClient` token, or knowledge of `OrgB`'s secret — only knowledge of the attacker's own org's webhook secret, which they legitimately possess. This is a lower-likelihood but concrete cross-tenant issue specific to the multi-org configuration path.

### Recommendation
After selecting the GitHub app/secret used for signature verification based on `repository.owner.login` (or `organization.login`), re-validate that every organization-scoped field the handlers consume (`repository.full_name`'s owner segment, or the resolved `Repository`'s owner) matches that same verified organization before processing the event; reject the payload otherwise.

### Proof of Concept
1. Configure shipit-engine with the multi-org schema, e.g. `github: { OrgA: {webhook_secret: "secretA", ...}, OrgB: {webhook_secret: "secretB", ...} }` (as in `test/dummy/config/secrets_double_github_app.yml`), each org owning separate repositories/stacks.
2. As the legitimate admin of `OrgA` (who knows `secretA`), craft a `push` webhook body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, raw_body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and verifies the signature successfully using `secretA`.
5. `PushHandler#process` resolves the target via `repository.full_name = "OrgB/victim-repo"`, enqueuing `GithubSyncJob` for `OrgB`'s stack with the attacker-supplied `expected_head_sha`, even though the request was never authenticated for `OrgB`.

Note: I was unable to execute this end-to-end in a running environment (no test harness access here), so the exploit chain is derived from static analysis of `WebhooksController`, `Shipit.github`, `Handler#repository_name`, and `PushHandler#process`; the downstream continuous-deployment cascade (`CacheDeploySpecJob` → deploy trigger) is asserted from `GithubSyncJob#perform` calling `CacheDeploySpecJob.perform_later(stack)` but the exact conditions under which that leads to an automatic deploy were not fully traced within the available tool budget.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
