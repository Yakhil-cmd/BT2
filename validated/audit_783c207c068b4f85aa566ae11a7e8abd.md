### Title
Asset attestor list can be revoked by the definer at any time to retroactively deny spending of already-held attested asset balances - ([File: validation.js])

### Summary
An asset can be issued with `spender_attested: true`, requiring that any address holding or spending the asset be attested by one of a set of `attestors` chosen by the asset's `definer_address`. The definer can update this attestor list at will, at any time, via an `asset_attestors` message, with no lock, cooldown, or expiration period protecting holders who already received or are in the process of spending the asset. This mirrors the OpenQ bug class: a privileged party ("issuer"/definer) can change the condition that gates payout of already-committed value, with no grace period, allowing them to strip a holder's ability to move funds they already legitimately hold or are actively spending.

### Finding Description
When an asset is defined with `spender_attested`, `validateAssetDefinition` requires an initial `attestors` list (`checkAttestorList`) at creation time. [1](#0-0) 

Afterwards, the definer can freely replace the attestor list via the `asset_attestors` message type. `validateAttestorListUpdate` only checks that the sender is the asset's definer and that the new list is well-formed — there is no restriction on how often or when this can happen, and no expiration/lock window that protects addresses that were attested under the old list: [2](#0-1) 

This attestor list directly gates the ability to spend the asset. `storage.readAsset` always resolves `arrAttestorAddresses` to the *latest* stable attestor-list unit for the asset, with no historical grace period for previously-attested holders: [3](#0-2) 

`filterAttestedAddresses` then checks membership against this latest list when validating a payment's output/input addresses: [4](#0-3) 

This is enforced both when issuing (`objAsset.arrAttestedAddresses.indexOf(issuer_address) === -1`) and when spending existing outputs (`owner_address is not attested`) in the payment/input validation path: [5](#0-4) [6](#0-5) [7](#0-6) 

Because the attestor list can be swapped out unconditionally by the definer, and the spend-time check always uses the newest stable list (not the list that was in effect when the recipient received/held the coins), a definer can:
1. Publish an asset with `spender_attested: true` and an attestor that attests a victim, inducing them to accept/hold the asset.
2. Wait until the victim has accumulated a balance (analogous to the claimant having done real off-chain/on-chain work to earn the asset).
3. Post an `asset_attestors` update removing the victim's attestor (or replacing the attestor set entirely) before the victim's spend transaction becomes stable/final.
4. Once the new attestor list stabilizes ahead of the victim's spend, the victim's previously valid, expected-to-be-spendable balance becomes permanently unspendable — `"owner address is not attested"` — with no time-locked grace period that guaranteed the victim a window to move funds.

There is no analog to a `_expiration` field for attestor lists — the change takes effect for all subsequent validation as soon as it stabilizes, exactly the missing "validity period" called out in the original report's recommendation.

### Impact Explanation
This directly causes freezing of funds: an address that legitimately holds units of an attested asset can have its holdings rendered permanently unspendable because the definer unilaterally revokes attestation, with no defined grace/expiration window. This is analogous to "theft of unclaimed yield/frozen funds" in the original report — the victim performed real economic actions (accepted/held the asset) trusting the attestation state, only to have the issuer retroactively invalidate their ability to move funds. This satisfies the "AA fund loss or freezing" / "unauthorized... freezing" impact bar.

### Likelihood Explanation
Any asset definer who sets `spender_attested: true` has unilateral, unrestricted, repeatable control over the attestor list via a single-authored `asset_attestors` message — no cosigning, no delay, and no on-chain enforcement of a minimum notice period. This makes the attack fully reachable by any unprivileged asset issuer against any counterparty who is holding or attempting to spend that issuer's asset, requiring only ordinary unit posting.

### Recommendation
Introduce an enforceable delay/expiration for attestor-list changes: require that a new `asset_attestors` update only take effect for spends whose `last_ball_mci` is beyond some minimum number of MCIs (or a wall-clock delay) after the update's stabilization, and validate spends against the attestor list that was current at the time the spent output was created (or at least guarantee a minimum notice window), rather than always the very latest list at spend-validation time.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true`, `attestors: [X]`.
2. Address `V` is attested by `X`, receives outputs of asset `A` from `D` or another party, relying on the fact that it is currently attested.
3. `V` posts a payment spending its `A` balance.
4. Before `V`'s payment stabilizes, `D` posts an `asset_attestors` message removing `X` (or replacing it with an attestor that will not attest `V`), validated only via `validateAttestorListUpdate` (validation.js:2829-2848) with no timing restriction.
5. Once `D`'s update stabilizes ahead of `V`'s spend in main-chain order, `storage.readAsset`/`filterAttestedAddresses` resolve to the new attestor list, and `V`'s pending payment fails validation with `"owner address is not attested"` (validation.js:2504-2507 / 2630-2641), permanently freezing `V`'s balance in asset `A`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
