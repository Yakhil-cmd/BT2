### Title
Stack-scoped ApiClient tokens can read CCMenu status of any stack, bypassing their intended stack authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
An `ApiClient` token created with a `stack_id` (i.e. authorized only for one specific stack) can be replayed against `Shipit::Api::CCMenuController#show` with an arbitrary `stack_id` parameter to read build/deploy status information for any other stack in the installation, because that controller's `stack` resolution method does not honor the client's stack scope.

### Finding Description
Shipit's stack-scoped API tokens are meant to bind a credential to exactly one stack: the token authorizes reads only for the stack referenced by `ApiClient#stack_id` [5](#0-4) . This binding is enforced centrally in `BaseController#stacks`/`#stack`, which filters the resolvable set of stacks down to `current_api_client.stack_id` when the client is scoped [2](#0-1) .

`CCMenuController` re-defines `stack` to call `Stack.from_param!(params[:stack_id])` directly, skipping the `stacks` scoping helper entirely [6](#0-5) . The `require_permission :read, :stack` macro only calls `check_permissions!`, which is a flat check of the `permissions` array (`"read:stack"` present or not) and carries no notion of which stack the permission applies to [7](#0-6) . Consequently, any request bearing a valid, unexpired `read:stack` token — even one explicitly created scoped to Stack A (as in the `here_come_the_walrus` fixture, `stack: shipit`) — is authorized by `check_permissions!` and then served data for whatever `stack_id` param the requester supplies, including stacks the token was never scoped to.

This is the analog of the reported bug class: the "check" (permission verification) is decoupled from the "binding" that should gate access (the token's specific authorized stack), exactly as the expired-lock deposit kept earning the high multiplier because the reward calculation never re-verified the lock-to-multiplier binding. Here, the token's stack authorization is verified for existence of a permission string, but the value actually acted upon (`params[:stack_id]`) is never checked against the value the token was actually authorized for (`current_api_client.stack_id`).

### Impact Explanation
This is an unauthenticated-relative-to-scope read of stack state: possession of any single stack-scoped, read-only API token (which may be distributed to lower-trust integrations, e.g., CI dashboards, on the assumption it only exposes one project's status) is sufficient to enumerate build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock state) for every stack managed by the Shipit instance, including private/internal projects the token holder has no legitimate visibility into. This matches the "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state" class of High severity impact.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped read tokens (the documented, supported use case per the `stack_id` column and the `here_come_the_walrus` fixture) and exposes the CCMenu endpoint, since exploitation requires only a valid token and knowledge/guessing of another stack's `to_param` (owner/repo/branch identifier), which is not secret. `CCMenuUrlController` additionally shows tokens minted for CCMenu usage are handed out via a queryable URL containing the raw token [8](#0-7) , increasing the chance such tokens circulate outside fully trusted contexts.

### Recommendation
Make `CCMenuController#stack` go through the same `stacks` scoping helper as `BaseController#stack` (i.e., `stacks.from_param!(params[:stack_id])`) so that a stack-scoped `ApiClient` cannot resolve any stack outside its `stack_id`, restoring the token-to-stack binding for this endpoint.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to Stack A with `permissions: ['read:stack']` and `stack_id` set to Stack A's id (as in `here_come_the_walrus`).
2. Using that token, call `GET /api/stacks/:stack_id_for_stack_B/ccmenu.xml?token=<token>` (or via Basic auth) with `stack_id` set to a different Stack B.
3. `CCMenuController#stack` resolves Stack B via `Stack.from_param!(params[:stack_id])` without any scoping check, and `require_permission :read, :stack` passes because the token has `"read:stack"` in its flat permissions list.
4. Response renders Stack B's CCMenu XML (build status/label/time/lock state), even though the token was only ever authorized for Stack A. [9](#0-8)
