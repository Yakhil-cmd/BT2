## Title
Race Condition (TOCTOU) in Private Asset Payment Validation Allows Double-Spend of Unstable Private Outputs - (File: `private_payment.js`)

### Summary
`private_payment.js`'s `validateAndSavePrivatePaymentChain` (and the underlying per-asset-type validators in `divisible_asset.js` / `indivisible_asset.js`) implement a classic check-then-act pattern: a duplicate check is performed with a `SELECT`, and if no matching prior row is found, the payment is validated and its input/output rows are `INSERT`ed — all inside a single connection's `BEGIN`/`COMMIT` transaction, but with no cross-request mutex serializing concurrent invocations that reference the same source output. This mirrors the structural flaw in CVE‑2026‑50631/GHSA‑83r6‑96m8‑r52p, where a refresh token's "already used" check and its "mark used" action are not atomic against concurrent requests, allowing the single-use guarantee to be bypassed.

### Finding Description
Public (on-DAG) unit validation in `validation.js` is protected by `mutex.lock(arrAuthorAddresses, ...)` [1](#0-0)  which serializes validation per author address before double-spend checks (`checkInputDoubleSpend` → `checkForDoublespends`) run [2](#0-1) . This mutex protection is also present when a node composes and *saves its own* private/divisible or indivisible-asset payment, via `mutex.lock('handleJoint')` in `getSavingCallbacks` [3](#0-2)  and the analogous code in `indivisible_asset.js` [4](#0-3) .

However, the path for *receiving* private payment chains from a counterparty — `private_payment.js`'s `validateAndSavePrivatePaymentChain`, reached from `network.js`'s `handleOnlinePrivatePayment` and `wallet.js`'s `handlePrivatePaymentChains` — never acquires any mutex. It only wraps the duplicate check and the write in a per-connection DB transaction: [5](#0-4) 

The "duplicate" check queries the `outputs` table for an existing row matching the head element's `(unit, asset, message_index[, output_index])` [6](#0-5) . If nothing is found, it proceeds to the real validation/save routine (`validateDivisiblePrivatePayment` / `validatePrivatePayment`), which itself calls `validation.validatePayment` → `validatePaymentInputsAndOutputs` → `checkInputDoubleSpend` → `checkForDoublespends`, which is also just a `SELECT` against the `inputs` table for a conflicting `src_unit/src_message_index/src_output_index` row [7](#0-6) , [8](#0-7) .

Crucially, for unstable (not-yet-stable) private outputs, `is_unique` is deliberately set to `NULL` rather than `1` [9](#0-8) , [10](#0-9) , which means the DB-level `UNIQUE KEY bySrcOutput(src_unit, src_message_index, src_output_index, is_unique)` constraint [11](#0-10)  does **not** fire for two competing `NULL` rows (NULL never equals NULL in SQL uniqueness semantics). The only remaining protection is the application-level `SELECT`-then-`INSERT` check described above, executed without any mutex.

Because private-asset payment data (outputs/inputs of a hidden payment) exists **only in each participant's local DB** — it is never broadcast on the public DAG (payload_location is `"none"`) — there is no independent, consensus-level backstop analogous to `graph.determineIfIncludedOrEqual` for on-chain double-spends. The recipient's local ledger is the sole arbiter.

### Impact Explanation
If two conflicting private-payment chains — both spending the same not-yet-stable private output — are delivered to the same recipient node/wallet concurrently (e.g., via two nearly-simultaneous device messages, one direct and one relayed through a hub, or a sender deliberately sending two different spend chains for the same coin to two different cosigner connections), both requests can:
1. run their `SELECT ... FROM outputs WHERE unit=... AND asset=... AND message_index=...` duplicate check and find nothing (since neither transaction has committed yet),
2. run `checkForDoublespends` and find no conflicting `inputs` row (same reason),
3. both `COMMIT`, each inserting a new "spent" chain referencing the same source coin.

This produces a genuine double-spend of a private asset from the recipient's perspective — the same coin ends up backing two independent, "validated" outputs recorded in the recipient's ledger, with no mechanism to later reconcile them since private payment content is off-chain. This is fund/asset-supply inflation local to the affected wallet/asset issuer counterpart, directly matching the impact bar (double-spend / unauthorized spending) requested.

### Likelihood Explanation
Exploitation requires an attacker (a private-payment counterparty in full control of message timing) to send two conflicting private-payment chains for the same not-yet-stable coin at effectively the same time, e.g. via two separate device/hub messages hitting `handlePrivatePaymentChains` (wallet.js) or `handleOnlinePrivatePayment` (network.js) on two different connections. Because Node.js processing of two nearly-simultaneous socket messages naturally interleaves at the I/O boundaries (`db.takeConnectionFromPool`, `conn.query("BEGIN", ...)`), and because no `mutex.lock` guards this path (unlike every other write path in the codebase that touches shared spend state), the race window is easily reachable by an attacker who controls both message delivery timings — no privileged access, no malicious peer/hub cooperation is required beyond what a private-payment counterparty already has.

### Recommendation
Serialize `private_payment.js`'s `validateAndSavePrivatePaymentChain` (and its callers in `network.js`/`wallet.js`) with a `mutex.lock` keyed on the source output identity (or globally, similar to `'handleJoint'`/`'private_write'` already used elsewhere, e.g. `validation.js`'s `mutex.lock(["private_write"], ...)` at [12](#0-11) ), so that the duplicate check and the corresponding insert of spend/output rows are atomic with respect to concurrent private-payment processing for the same address/source coin.

### Proof of Concept
1. Attacker holds a private, unstable divisible-asset output `O` (not yet on stable MC).
2. Attacker crafts two different private-payment chains `A` and `B`, both consuming `O` as their sole input, sending to two different (or same) addresses.
3. Attacker sends chain `A` to victim wallet via the hub (`handlePrivatePaymentChains`) and chain `B` via a direct P2P `private_payment` network message (`handleOnlinePrivatePayment`) at nearly the same moment.
4. Both requests open separate DB connections/transactions, each executing the duplicate-check `SELECT` in `private_payment.js` (lines 62–76) and the `checkForDoublespends` `SELECT` in `validation.js` (lines 1661–1705) before either has committed its `INSERT`.
5. Both transactions commit successfully; the victim's local `outputs`/`inputs` tables now contain two independent "valid" spends of `O`, each crediting a different output — a private-asset double-spend / duplication of value with no later reconciliation possible.
