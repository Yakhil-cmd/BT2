### Title
Membership webhook trusts unverified `organization.login` field for `Team#organization`, allowing org impersonation - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook using the organization derived from `repository.owner.login` (falling back to `organization.login` only when `repository` is absent), but `MembershipHandler#find_or_create_team!` independently reads `params.organization.login` to stamp the `Team#organization` column when creating a new team. Because these two payload paths are never cross-checked, an attacker who controls one organization's `webhook_secret` can supply a `repository` object naming their own org (satisfying signature verification) while supplying a different, privileged `organization.login` in the same JSON body, causing a `Team` to be created and attributed to an organization the attacker never authenticated for.

### Finding Description
The broken binding is:
`repository_owner` (the org whose `webhook_secret` verified the request in `WebhooksController#verify_signature`, `app/controllers/shipit/webhooks_controller.rb:59-62`) **must equal** `params.organization.login` (the org value used to set `Team#organization` in `MembershipHandler#find_or_create_team!`, `app/models/shipit/webhooks/handlers/membership_handler.rb:38-42`).

Nothing enforces this equality: [1](#0-0) [2](#0-1) 

`repository_owner` prefers `repository.owner.login` and only falls back to `organization.login` when `repository` is missing from the payload. The `membership` event's real GitHub payload contains only `organization`/`team`/`member` (no `repository`), but the `ExplicitParameters` schema on `MembershipHandler` does not forbid extra top-level keys, and the controller forwards the entire parsed JSON body unmodified to the handler: [3](#0-2) 

So an attacker can craft a body containing both a `repository.owner.login` set to their own (attacker-controlled) organization — which is what `verify_signature` uses to pick the HMAC secret via `Shipit.github(organization: repository_owner)` — and a separate `organization.login` naming a victim/privileged organization, which is what the handler actually uses: [4](#0-3) 

`find_or_create_team!` calls `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login; ... }`. Since `find_or_create_by!` only runs the block when a new row is inserted, this attack is fully effective only for a `team.id` not already present in Shipit's `teams` table (e.g., a team not yet synced from the victim org, or an attacker-fabricated id chosen to also match `Shipit.github_teams` configuration). In that case, a brand-new `Team` row is created with `organization` equal to the impersonated org string, and the attacker's own `member.login` (also fully attacker-controlled and unauthenticated against GitHub — `User.find_or_create_by_login!` in `app/models/shipit/user.rb:22-28` merely fetches profile data) is added via `team.add_member(member)`.

None of the existing guards close this gap: `verify_signature` only checks that *some* organization's secret matches the raw body — it never re-derives the "true" org from the verified secret and compares it against `params.organization.login`; the `ExplicitParameters` schema only validates presence/type, not cross-field consistency; and `Team.find_or_create_by!` provides no protection against the `organization` field being forged on first-creation.

### Impact Explanation
Impact category: High — escalation into `Shipit.github_teams` authorization. `User#authorized?` (`app/models/shipit/user.rb:80-82`) grants access when a user belongs to a `Team` whose `id` is in `Shipit.github_teams`. If a privileged team has not yet been lazily created in Shipit's database, an attacker who owns any configured GitHub organization can forge the `Team#organization`/`github_id` binding at creation time and self-enroll as a member, potentially satisfying `authorized?` and gaining access to a privileged organization's stacks, deploys, and task streams — without ever authenticating against the victim organization's webhook secret.

### Likelihood Explanation
Exploitation requires: (1) the attacker owns at least one GitHub organization already configured in Shipit (has a legitimate `webhook_secret` for it, per `docs/setup.md` multi-org setup), and (2) the target team's `github_id` has not already been created as a `Team` row in Shipit (so `find_or_create_by!`'s block executes). The attacker must also know or guess a real `team.id` corresponding to the org they wish to impersonate (team IDs are often discoverable via GitHub's public/team APIs for organizations with public teams, or by observing prior webhook deliveries). This is a moderate-cost, config-dependent precondition, not requiring any Shipit secret beyond one the attacker legitimately possesses.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and generally in `WebhooksController#verify_signature`), require that the organization used to select the webhook secret equals the organization referenced in the event body. Concretely, compare `params.organization.login` against the `repository_owner` value that was used to verify the signature (or pass the verified organization down to the handler and use it — never `params.organization.login` — for `team.organization`), rejecting the webhook if they differ.

### Proof of Concept
```ruby
test "membership webhook cannot attribute a new team to an unverified organization" do
  # Attacker owns "attacker-org" and knows its webhook_secret.
  attacker_secret = shipit_github_hooks(:attacker_org_membership).secret

  payload = {
    action: 'added',
    team: { id: 999_999, name: 'Fake Team', slug: 'fake-team', url: 'http://example.com' },
    organization: { login: 'shopify' },        # victim/privileged org, unverified
    repository: { owner: { login: 'attacker-org' } }, # used only for signature check
    member: { login: 'attacker' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_secret, payload)}"

  request.headers['X-Github-Event'] = 'membership'
  request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { Shipit::Team.where(organization: 'shopify').count } do
    post :create, body: payload, as: :json
  end
  # EXPECTED (broken today): a Team with organization == 'shopify' IS created,
  # and User.find_by(login: 'attacker').authorized? may become true if the
  # forged team.id matches a Shipit.github_teams entry.
end
```
This asserts the equality `repository_owner (attacker-org, verified) == params.organization.login (shopify, unverified)` must hold before any `Team` row is written for `organization: 'shopify'`; currently it does not.

      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
