### Title
CCMenu tokens are not scoped to the requesting stack, granting cross-stack read access - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` mints an `ApiClient` with `read:stack` permission but never binds it to the stack the CCMenu URL was generated for. Because `ApiClient#stack_id` is left `nil`, the token is treated by the API authorization layer as unrestricted to *all* stacks, not just the one shown in the generated CCMenu URL. This breaks the equality "stack a token authorizes == stack the URL/token is meant to touch."

### Finding Description
`CCMenuUrlController#fetch` builds a URL scoped to a specific stack (`stack_id: stack.to_param`) and attaches an authentication token: [1](#0-0) 

The token is produced by `client`, which creates (or reuses) an `ApiClient` keyed only by `creator` and `name`, granting `read:stack` permission — critically, it never sets the `stack:` association: [2](#0-1) 

`ApiClient` supports a `stack` association intended to scope the client's visibility: [3](#0-2) 

Downstream, `Api::BaseController#stacks` uses this association to decide the visibility scope of any authenticated API client: [4](#0-3) 

Since the CCMenu client's `stack_id` is never set, `current_api_client.stack_id?` is `false`, so `stacks` resolves to `Stack.all` — every stack in the Shipit instance — rather than being restricted to the one stack the URL/token was generated for. Additionally, because the client is found/created by `creator + name` only (not per-stack), the same single `ApiClient` record — and therefore the same reusable token — is shared across every stack for which that user requests a CCMenu URL, compounding the scope mismatch: a token minted while viewing Stack A's settings page is equally valid to read Stack B, Stack C, etc., simply by editing the `stack_id` query parameter of the resulting API URL.

This is the same class of trust-binding failure as the referenced report: a value that is supposed to gate/scope access (the market/stack identity) is not actually enforced consistently everywhere it needs to be, so accounting/authorization intended for one specific entity silently applies more broadly than intended.

### Impact Explanation
An authenticated Shipit user who has permission to view only one stack's settings page (and therefore is only meant to be able to read that stack's CI status via CCMenu) can obtain a `read:stack` token that is valid for every stack in the instance, including stacks they have no legitimate access to (e.g., stacks restricted via `Shipit.github_teams` authorization to another team). This is an unauthorized read of stack state across repositories/teams, matching the "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state" High-impact category, since the token effectively bypasses per-stack read restrictions once issued.

### Likelihood Explanation
Any user capable of reaching the stack settings page for a single stack (a normal, low-privilege capability) can trigger `fetch` and obtain a broadly-scoped token without any additional privilege. No repository write access, webhook secret, or GitHub App credentials are needed — only ordinary application session access to one stack's settings page.

### Recommendation
Bind the CCMenu `ApiClient` to the specific stack being viewed, e.g. `ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(creator: current_user, name: 'CCMenu Client', stack:)`, and ensure client lookup/creation is scoped per stack instead of solely by `creator + name`, so the resulting token is restricted to `Stack.where(id: stack.id)` in `Api::BaseController#stacks`.

### Proof of Concept
1. As User X, who only has read access to Stack A, visit Stack A's settings page and trigger the CCMenu URL fetch (`GET .../ccmenu_url`). This creates/returns an `ApiClient` named "CCMenu Client" for User X with `permissions: ['read:stack']` and `stack_id: nil`, and returns a URL like `.../api/stacks/A/ccmenu.xml?token=<token>`.
2. Take the same `<token>` and issue a request to `.../api/stacks/B/ccmenu.xml?token=<token>` for Stack B, which User X does not have access to.
3. Because `ApiClient#stack_id?` is false, `Api::BaseController#stacks` resolves to `Stack.all`, so `stack.from_param!(params[:stack_id])` succeeds for Stack B and returns its CI/build status — data User X should not be able to read.

Note: I was unable to further verify within this session whether stack-level access in the main (session-based) UI is itself restricted by `Shipit.github_teams` for some stacks (which would confirm the exact severity of the cross-team escalation); this would require checking stack authorization/team-restriction logic (e.g., in `app/models/shipit/stack.rb` or team-based `require_permission` filters) that was not reached in this investigation.

```ruby
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    def client

    end
```

```ruby
# frozen_string_literal: true

module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }
```
