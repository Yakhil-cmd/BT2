This confirms the mechanism, and it is a well-known, intentional design in the burnchain-ops layer (not a bug specific to `DelegateStxOp`). The design relies on Bitcoin transaction chaining, not on address-matching between `PreStxOp.output` and the signer of the `PreStxOp`'s own inputs.

Key facts established:
- `PreStxOp::parse_from_tx` in `stackslib/src/chainstate/burn/operations/stack_stx.rs` only requires the tx to have ≥1 input and ≥1 output; it does not check that `output[0]` corresponds to the address that signed the `PreStxOp`'s own inputs. [1](#0-0) 
- `DelegateStxOp::get_sender_txid` requires the `DelegateStxOp` transaction's **first input** to spend `vout == 1` of a specific prior txid — i.e., it must spend `PreStxOp`'s **second output**. [2](#0-1) 
- `Burnchain::classify_transaction` looks up that referenced `PreStxOp` and sets `sender = &pre_stx.output` (the `PreStxOp`'s **first** output, an arbitrary address chosen by whoever authored the `PreStxOp` tx), passing it into `DelegateStxOp::from_tx`. [3](#0-2) 
- `process_delegate_ops` in `stackslib/src/chainstate/stacks/db/blocks.rs` then runs the `.pox` contract's `delegate-stx` as `tx-sender = sender` (i.e., `pre_stx.output`), with `amount-ustx = delegated_ustx` and `delegate-to = delegate_to`, both fully attacker-supplied in the wire payload. [4](#0-3) 

However, spending `vout == 1` of the `PreStxOp` transaction is a **Bitcoin UTXO spend** — it requires a valid signature that satisfies that output's `scriptPubKey`. The attacker who crafts the `PreStxOp` chooses **both** outputs (`output[0]`, the fake "sender" address, and `output[1]`, the value they will actually spend in the follow-up `DelegateStxOp` tx). Since the attacker controls the private key behind `output[1]` (they set it to their own key when creating the `PreStxOp`), they can freely spend it into the `DelegateStxOp` tx without ever touching the victim's Bitcoin or Stacks keys. `output[0]` (which becomes `op.sender`) is never checked against any signature at all — it's just bytes in the transaction. This is exactly the flaw the question describes, and it's real: the "sender" field of `DelegateStxOp` (and identically `StackStxOp`, `TransferStxOp`, `VoteForAggregateKeyOp`) is **not bound by any signature to a Bitcoin/Stacks private key** — it is simply whatever address the attacker chose to write as `PreStxOp`'s first output, including a victim's real address.

Downstream, `delegate-stx` (per `pox-4.clar`/pox-5 equivalent, `stackslib/src/chainstate/stacks/boot/pox-4.clar:642-685`) only checks `check-caller-allowed` and that `tx-sender` (i.e., the spoofed victim) isn't already delegating — it does **not** require any signature from the delegator. It writes `delegation-state { stacker: tx-sender } => { delegated-to: attacker, amount-ustx: X }`. [5](#0-4) 

Note, however, that `delegate-stx` itself **does not lock or move any STX** — per its own doc comment, it "does not lock the funds, rather, it allows the delegate to issue the stacking lock." The actual fund lock only occurs if the attacker (now recorded as `delegate-to`) subsequently calls `delegate-stack-stx(stacker=victim, ...)`, which checks `get-check-delegation stacker` and, if it matches, locks the **victim's real STX balance** and redirects the resulting reward address to one the attacker controls. [6](#0-5) 

This matches the exact scoped impact in the question: the `DelegateStxOp` step alone authorizes a stacking delegation the victim never signed, and a follow-on (unprivileged, self-authored) `delegate-stack-stx` call by the attacker converts that forged authorization into an actual unsigned lock of the victim's STX with attacker-controlled reward payout — satisfying "authorises a stacking delegation the victim never signed."

I did not find any code path that ties `PreStxOp.output` to the signer of the `PreStxOp`'s own inputs — this absence of binding is the root cause and applies uniformly to `StackStxOp`, `TransferStxOp`, `DelegateStxOp`, and `VoteForAggregateKeyOp`.

### Title
`DelegateStxOp.sender` is derived from an unauthenticated `PreStxOp.output` field, letting anyone forge stacking delegations on behalf of any Stacks address - (`stackslib/src/chainstate/burn/operations/delegate_stx.rs`)

### Summary
`DelegateStxOp::parse_from_tx` (and `Burnchain::classify_transaction`) sets `op.sender` to `PreStxOp.output`, an address field that is never cryptographically bound to the signer of the `PreStxOp` transaction's own Bitcoin inputs. An attacker who fully controls a self-funded `PreStxOp`→`DelegateStxOp` Bitcoin transaction chain can set `output[0]` to any victim address and `delegate_to`/`delegated_ustx` to attacker-chosen values, causing the `.pox` contract's `delegate-stx` to execute as if the victim had authorized it.

### Finding Description
The broken equality: the protocol should guarantee `DelegateStxOp.sender == the StacksAddress corresponding to the private key that authorized/funded this operation chain`. In reality, `DelegateStxOp.sender` is set to `pre_stx.output` — the first output of a previously-mined `PreStxOp` transaction (`stackslib/src/burnchains/burnchain.rs:964-992`) — and `PreStxOp::parse_from_tx` places no constraint on that output address relative to the inputs that funded/signed the `PreStxOp` transaction (`stackslib/src/chainstate/burn/operations/stack_stx.rs:80-126`). The only chain-linking check is that the `DelegateStxOp`'s first input spends `vout==1` of that same `PreStxOp` (`DelegateStxOp::get_sender_txid`, `delegate_stx.rs:105-120`), i.e., the *second* output — never the first ("sender") output.

Exploit flow: the attacker crafts and broadcasts, using only their own BTC UTXOs and keys:
1. A `PreStxOp` tx with `output[0] = victim's StacksAddress` (arbitrary bytes, no signature needed) and `output[1] = an address the attacker controls`.
2. A `DelegateStxOp` tx whose first input spends `output[1]` of tx (1) (signed entirely by the attacker), with payload `delegated_ustx = victim's full stacked/lockable balance`, and `delegate_to = attacker`.

`classify_transaction` resolves `sender = pre_stx.output = victim`, producing `DelegateStxOp { sender: victim, delegate_to: attacker, delegated_ustx: X, ... }` with zero involvement of the victim's keys. `process_delegate_ops` (`stackslib/src/chainstate/stacks/db/blocks.rs:4326-4341`) then calls `.pox` `delegate-stx` with `tx-sender = victim`, which only checks `check-caller-allowed` and that the victim isn't already delegating (`pox-4.clar:642-685`) — no signature check exists. This writes a forged `delegation-state` entry granting the attacker delegate rights over the victim's principal. The attacker can then call `delegate-stack-stx(stacker=victim, ...)` themselves (an ordinary, unprivileged contract call), which locks the victim's real STX and points the reward payout at the attacker's own PoX address.

Existing guards do not prevent this: `verify-not-prepare-phase`, `check-pox-lock-period`, and the `<=` amount guards in `delegate-stack-stx` operate on the (already-forged) `delegation-state` entry and the victim's real balance — they don't verify the *origin* of the delegation record itself.

### Impact Explanation
The attacker obtains delegate rights over the victim's principal without any victim signature, then can lock the victim's real STX for stacking and redirect the reward payout address to one they control — an "unsigned stacking action" and a mechanism for diverting the victim's stacking rewards to the attacker. This is repeatable against any victim address for the cost of two low-value Bitcoin transactions (a `PreStxOp` and a chained `DelegateStxOp`), and the same root cause (unauthenticated `PreStxOp.output`) affects `StackStxOp`, `TransferStxOp`, and `VoteForAggregateKeyOp` identically.

### Likelihood Explanation
No privileged role is required — only the ability to broadcast two ordinary, self-funded Bitcoin transactions (cost: Bitcoin tx fees plus dust) and, to realize fund-locking impact, one ordinary Stacks contract call (`delegate-stack-stx`) from the attacker's own account. No specific cycle phase, membership state, or victim cooperation is needed. This is fully repeatable and requires no race conditions.

### Recommendation
Bind `PreStxOp.output` (and by extension the derived `sender` field for `StackStxOp`/`TransferStxOp`/`DelegateStxOp`/`VoteForAggregateKeyOp`) to the actual signer of the `PreStxOp`'s own inputs — e.g., require `output[0]`'s hash160 to match the hash160 recovered from the first input's scriptSig/witness public key, rejecting the `PreStxOp` (and therefore any chained op) otherwise. Alternatively, require the follow-on op (e.g. `DelegateStxOp`) to independently recover and verify a signer public key (as is already done for `VoteForAggregateKeyOp::get_sender_pubkey`) and reject if it doesn't match `pre_stx.output`.

### Proof of Concept
Rust test in `stackslib/src/chainstate/coordinator/tests.rs` style, extending `test_delegate_stx_btc_ops`:
1. Construct a `BitcoinTransaction` for `PreStxOp` with `outputs[0].address = victim_hash160` (victim never signs) and `outputs[1].address = attacker_hash160`, inputs signed only by attacker's key.
2. Construct a `BitcoinTransaction` for `DelegateStxOp` whose `inputs[0].tx_ref = (prestx_txid, 1)`, signed only by the attacker's key, with `outputs[0].address = attacker_hash160` (→ `delegate_to`) and payload `delegated_ustx = victim_full_balance`.
3. Run both through `Burnchain::classify_transaction` and assert `op.sender == victim_address` while `victim_address` never appears as a signer/input key anywhere in either transaction — i.e., assert `op.sender != recovered_pubkey_address(tx.inputs)`.
4. Feed the resulting `DelegateStxOp` through `StacksChainState::process_delegate_ops` against a chainstate where `victim` holds real STX, and assert the `.pox` `delegation-state` map now shows `{ stacker: victim, delegated-to: attacker, amount-ustx: victim_full_balance }` despite `victim` never signing any Stacks or Bitcoin transaction in the test.
