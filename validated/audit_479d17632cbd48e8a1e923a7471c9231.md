### Title
Forged CI status for a foreign repository's commit via cross-organization webhook signature scoping mismatch - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `status` webhook is authenticated by resolving the signing GitHub App from the payload's `repository.owner.login` [1](#0-0) [2](#0-1) , but `StatusHandler#process` never re-checks that the commit it mutates actually belongs to that same organization/repository — it looks up commits globally by `sha` alone [3](#0-2) . Because `Commit` rows are only unique per `(stack_id, sha)` and not globally unique [4](#0-3) , an attacker who legitimately administers one onboarded GitHub organization/repository (and therefore knows that org's `webhook_secret`) can send a correctly-signed webhook whose `sha` field names a commit belonging to a completely unrelated stack/repository, forging a `success` CI status for it.

### Finding Description
The binding that should hold is: `organization authenticated by signature == organization owning the commit/stack that gets written`. This is broken because:

1. `WebhooksController#verify_signature` selects the GitHub App/secret to verify against solely from the payload's `repository.owner.login` (or `organization.login`) field [1](#0-0) . The HMAC only proves the payload was signed with *that* organization's configured secret — it says nothing about which commit/stack the payload is allowed to reference.
2. `StatusHandler` declares only `sha`, `state`, and optional fields as required parameters — it does not require or validate any repository/owner field at all [5](#0-4) .
3. `StatusHandler#process` resolves affected records with `Commit.where(sha: params.sha)`, iterating over every commit matching that sha across the entire installation, and calls `commit.create_status_from_github!(params)` on each [3](#0-2) . There is no join/filter against the `repository_owner` used for signature verification.
4. `Commit` records are only guaranteed unique per `(stack_id, sha)`, not globally, per the dedicated index migration [4](#0-3) . Since git commit SHAs of victim commits are public information (visible on GitHub), an attacker doesn't need a hash collision — they simply put the known victim SHA in their own, self-signed status payload.
5. Creating a new `Status` on the (foreign) commit is not a no-op: `Commit#add_status` reacts to status transitions and, when the new status becomes `pending` or `success`, calls `stack.schedule_merges` on that commit's real stack [6](#0-5) , and per existing tests a `success` status on a stack with continuous deployment enabled directly triggers a new `Deploy` via `ContinuousDeliveryJob` [7](#0-6) .

### Impact Explanation
An attacker who controls (or is an admin of) their own onboarded, low-privilege GitHub organization/repository in a multi-tenant Shipit install can forge a webhook, correctly signed with their own org's `webhook_secret`, that references a commit SHA belonging to a victim organization's stack. This can inject a fabricated `success`/`pending` status onto that victim commit, which — for stacks with continuous deployment enabled — can trigger an unauthorized deploy, or unblock a merge queue (`schedule_merges`) gated on CI status, without ever having write access to, or a valid webhook secret for, the victim's repository/organization. This matches the "unauthorized deploy" impact category (Critical) because it lets a low-privileged, unrelated tenant influence deploy/merge decisions for a repository they do not control.

### Likelihood Explanation
This requires the attacker to operate at least one legitimately onboarded organization/repository in the same multi-org Shipit deployment (so `Shipit.github(organization: their_org)` resolves and their self-configured `webhook_secret` verifies), plus knowledge of the target commit's SHA (which is public on GitHub). No compromise of the victim org's secret, GITHUB_TOKEN, or Shipit session is required — only crafting an arbitrary JSON body and computing its own HMAC. This is realistic in any Shipit instance that hosts more than one organization/tenant, which the config format (`secrets.github` keyed by organization) explicitly supports [8](#0-7) .

### Recommendation
Scope `StatusHandler` (and any other webhook handler that mutates commit/stack state by SHA alone) so that it only affects commits belonging to stacks/repositories owned by the same GitHub organization/login that was used to verify the signature. Concretely, require and validate `repository.full_name` in `StatusHandler`'s params (as other handlers already do, e.g. `PushHandler`/`Handler#stacks`) and constrain the `Commit` lookup to `Repository.from_github_repo_name(params.repository.full_name)`'s stacks, rejecting or ignoring statuses for commits outside that repository.

### Proof of Concept
1. Attacker configures a legitimate Shipit-tracked repository under organization `attacker-org`, which has a real `webhook_secret` configured for `attacker-org` in `secrets.yml`.
2. Attacker looks up (publicly, via GitHub) the SHA of a commit belonging to victim stack `victim-org/victim-repo`, e.g. `abcd1234...`.
3. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "abcd1234...",
  "state": "success",
  "context": "ci/attacker",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
4. Attacker computes `sha1=HMAC-SHA1(attacker_org_webhook_secret, raw_body)` and sends it as `X-Hub-Signature` with `X-Github-Event: status` to `/github/webhooks`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and verifies successfully (it is their own valid secret) [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: 'abcd1234...')`, which matches the commit belonging to `victim-org/victim-repo`'s stack, and calls `create_status_from_github!`, creating a `success` status on that victim commit [3](#0-2) .
7. If `victim-org/victim-repo`'s stack has `continuous_deployment` enabled, `Commit#add_status` triggers `stack.schedule_merges` / a new deploy on the victim's stack [6](#0-5) .

Note: I was unable to view `Commit#create_status_from_github!`'s exact source (only found via grep, not fully read due to iteration limits), so the exact status-creation code path from parameters to `Status` record is inferred from `StatusHandler` and `Commit#add_status`/tests rather than directly cited line-by-line for that specific method.
