The critical asymmetry: `WebhooksController#verify_signature` computes the app/webhook-secret to use from `repository_owner` (`params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')`), while the actual write target used by every handler (`Handler#repository_name` / `Handler#stacks`) is `payload.dig('repository', 'full_name')`, parsed via `Repository.from_github_repo_name`. These two fields are never cross-checked against each other.

### Title
Webhook signature is validated against `repository.owner.login`, while the write target is resolved from an unverified `repository.full_name` field, allowing cross-organization stack writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
### Finding Description
In a multi-organization Shipit deployment (`Shipit.github(organization:)` supports per-org GitHub Apps/webhook secrets), `WebhooksController#verify_signature` selects which webhook secret to validate the HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

Once the signature is accepted, `create` dispatches the raw, parsed JSON `params` to every registered handler for the event unmodified. [3](#0-2) 

All handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*` family) derive the actual repository/stack to mutate from `payload.dig('repository', 'full_name')` via the shared base class `Handler#repository_name`/`#stacks`, which is passed to `Repository.from_github_repo_name` and used to look up `stacks` that get synced, archived, or unarchived. [4](#0-3) [5](#0-4) [6](#0-5) 

Nothing in `WebhooksController` or `Handler` enforces that `repository.owner.login` (the field used to select the signing secret) equals the owner segment of `repository.full_name` (the field used to select the stacks that get mutated). GitHub's actual webhook payloads always keep these consistent, but this engine trusts the *unverified structure* of the attacker-controlled JSON body for this cross-check — there is none. This is the same bug class as the [EIGEN2-5] report: a state-mutating function (`_kickOperator`/here, `stacks`/`sync_github`) is invoked using a field of the payload (`operatorKickParams`/here, `repository.full_name`) that is disjoint from the field actually covered by the enforced guarantee (max operator count/here, HMAC signature over `repository.owner.login`'s secret).

The equality that should hold and is broken:
`organization whose webhook_secret authenticated the request == owner(repository.full_name) whose stack is written`

### Impact Explanation
An attacker who controls (or has compromised) a GitHub App installed for **any** organization configured in Shipit's multi-org `github:` secrets section (see `docs/setup.md` "Using Multiple Github Applications") can compute a valid HMAC using their own org's `webhook_secret`, but set `repository.full_name` in the JSON body to point at a **different** organization/repo's stack. Since `verify_signature` only checks the org named in `repository.owner.login` (which the attacker fully controls and sets to their own org to pass verification), while `Handler#repository_name` resolves stacks from `repository.full_name` (which the attacker also fully controls, and can set to any victim org/repo), the attacker can trigger `PushHandler#process` (`stack.sync_github`), `CheckSuiteHandler`, or PR handlers (`archive!`/`unarchive!`) against stacks belonging to a completely different, victim organization they have no access to. This crosses a repository-write boundary using credentials scoped to a different repository/org — matching the "cross-repository writes" Critical impact criterion.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (documented, supported configuration), and (2) attacker possession of a valid webhook secret for at least one configured organization (e.g., because they administer their own org's GitHub App installed on the shared Shipit instance — an "unprivileged" attacker with respect to the victim org). No GitHub session, `ApiClient` token, or `api_clients_secret` is needed; only crafting a raw HTTP POST with a computed HMAC over their own secret and an arbitrary `repository.full_name`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), validate that the resolved signing organization matches the owner segment of `repository.full_name` used for dispatch — i.e., derive both the signing key and the mutated repository from the same, single trusted field, or explicitly assert `repository.full_name.split('/').first.casecmp(repository_owner).zero?` before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `docs/setup.md` multi-org config).
2. Attacker knows `attacker-org`'s `webhook_secret` (they administer that org's GitHub App).
3. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org-webhook_secret, raw_body)`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and the signature validates successfully. [1](#0-0) 
6. `create` dispatches to `PushHandler`, which resolves stacks via `repository.full_name` = `"victim-org/victim-repo"`, calling `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on a stack the attacker does not own. [5](#0-4) 

**Uncertainty note:** I was unable to trace exactly what `sync_github` does downstream (e.g., whether it can force a fetch/checkout of attacker-controlled refs into `victim-org/victim-repo`'s deploy pipeline) because that method's implementation in `app/models/shipit/stack.rb` was not fully retrieved in this session. A full Devin session with complete file access would be needed to confirm the precise downstream effect (e.g., whether it merely re-syncs known GitHub state or can be leveraged toward RCE/exfiltration on the deploy host).
