### Title
Cross-tenant CommitStatus forgery via `StatusHandler#process` looking up commits by SHA with no repository scoping - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` solely via `Commit.where(sha: params.sha)`, without ever calling `Handler#stacks`/`#repository_name` to confirm the commit belongs to the repository named in the verified webhook payload. Any org whose webhook secret is valid (even org-attacker's own) can send a `status` event naming a SHA belonging to a completely unrelated org-victim's commit and have a `CommitStatus`/`Status` written against it.

### Finding Description
The binding that must hold is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` (the org/repo that authenticated the webhook via `verify_signature`) — i.e., a `Status` written from a payload must belong to the same repository the payload's HMAC signature was verified against.

Trace:
- `WebhooksController#verify_signature` [1](#0-0)  only proves the payload was signed with `Shipit.github(organization: repository_owner)`'s `webhook_secret` — i.e., that the request genuinely originates from `repository_owner`'s GitHub org. It performs no association with which `Commit`/`Stack` rows may be mutated.
- Every other handler at least attempts repo scoping via `Handler#stacks`, which derives `Repository.from_github_repo_name(repository_name)` from `payload.dig('repository','full_name')` [2](#0-1) .
- `StatusHandler#process` does not call `stacks` or `repository_name` at all; it performs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) , a global, cross-tenant lookup keyed only by the git-content-addressed SHA.
- `Commit#create_status_from_github!` calls `add_status`/`statuses.replicate_from_github!(stack_id, github_status)` [4](#0-3) , writing a `Status` row tied to `commit.stack_id` (org-victim's stack), using `stack_id` derived from the commit found, not from the authenticating org.
- `Status.replicate_from_github!` persists the row unconditionally based on that `stack_id` [5](#0-4) , and `after_create` hooks (`enable_ci_on_stack`, `schedule_continuous_delivery`) then act on org-victim's stack.

Attacker flow: org-attacker owns a real GitHub org/repo registered with Shipit and knows its own `webhook_secret`-signed traffic will pass `verify_signature` (this holds by design — the attacker is a legitimate, verified sender for their own org). The attacker crafts a `status` event JSON body with `repository.full_name` set to their own repo (so `verify_signature` succeeds against their own org's secret) but with `sha` set to a publicly known commit SHA belonging to org-victim's stack (learned via GitHub's public commit API, no secret needed). Because `StatusHandler` never checks `repository_name`/`stacks`, `Commit.where(sha: ...)` matches org-victim's `Commit` row regardless of which repository field was in the payload, and a forged `Status` is written under org-victim's `stack_id`.

None of the existing guards catch this: `verify_signature` only authenticates the sender's org, not the target row; `drop_unhandled_event` only filters by event type; `ExplicitParameters` only validates field shapes (`sha`, `state`, etc.), not ownership; there is no `Repository`/`Stack` association check in `StatusHandler` at all — unlike the (still weak) `full_name`-based checks in other handlers.

### Impact Explanation
A verified webhook from any single registered GitHub org lets the sender write arbitrary `Status` records against any commit/stack in the entire Shipit installation, by guessing/enumerating public commit SHAs. This directly affects `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [6](#0-5)  and CI-gating logic, and can trigger `schedule_continuous_delivery`/`enable_ci_on_stack` on victim stacks, potentially forcing or blocking continuous deployments for repositories the attacker has no relationship with. This is a payload for one repository mutating another's stack/commit state — matching the Critical impact category.

### Likelihood Explanation
Preconditions are trivial: the attacker only needs one legitimate, registered GitHub org/repo in Shipit (which any external org can be, since Shipit onboards arbitrary orgs) and knowledge of a target commit SHA, obtainable from GitHub's public API without any victim secret. The attack is fully repeatable across arbitrary victim stacks/orgs by iterating known SHAs, and requires no elevated privileges beyond being a verified webhook sender for one's own org.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository named in the verified payload, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently constrain via `Repository.from_github_repo_name(repository_name)`'s commits, mirroring (and fixing) the scoping pattern in other handlers so a `Status` can only be attached to commits belonging to stacks under the authenticated repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test "does not write a status for a commit belonging to a different repository" do
          victim_stack = shipit_stacks(:shipit) # belongs to org-victim/repo
          victim_commit = shipit_commits(:first)
          victim_commit.update!(stack: victim_stack, sha: "deadbeef" * 5)

          attacker_repo_full_name = "org-attacker/some-repo"

          payload = {
            "repository" => { "full_name" => attacker_repo_full_name, "owner" => { "login" => "org-attacker" } },
            "sha" => victim_commit.sha,
            "state" => "success",
            "context" => "forged",
          }

          assert_no_difference -> { Status.count } do
            StatusHandler.call(payload)
          end
        end
      end
    end
  end
end
```
Expected current (buggy) behavior: the assertion fails because `Status.count` increases by 1 — `StatusHandler` writes a `Status` against `victim_commit`/`victim_stack` despite the payload naming `org-attacker`'s repository, proving cross-tenant forgery is possible before a fix (the fixed handler should make this test pass with `assert_no_difference`).
