### Title
Missing Receipt Status Check in `writeServiceChainTxReceipts` Allows Malicious Parent Peer to Corrupt Anchored Block Number — (`node/sc/sub_bridge_handler.go`)

### Summary
`SubBridgeHandler.writeServiceChainTxReceipts` processes P2P-delivered receipts without checking `receipt.Status`. A malicious node connected as a parent bridge peer can send a crafted `ServiceChainReceiptResponseMsg` for any tx hash it learned from the child chain's receipt broadcast, causing the child chain to permanently record a false anchoring confirmation and discard the anchoring tx from its retry pool.

### Finding Description
`writeServiceChainTxReceipts` iterates over receipts received via P2P and, for each receipt whose `TxHash` matches a pending `BridgeTxPool` entry, unconditionally:
1. Writes the anchored block number to the DB (`WriteAnchoredBlockNumber`)
2. Stores the receipt (`WriteReceiptFromParentChain`)
3. Removes the tx from `BridgeTxPool` (`RemoveTx`)

No check on `receipt.Status` is performed at any point. The anchoring data (block hash, block number) is extracted from the locally-generated tx, so the written block number is internally consistent — but it is written as "confirmed" even though the anchoring tx was never actually executed on the parent chain.

The tx hashes needed to craft the attack are freely available: the child chain broadcasts them to all connected peers via `broadcastServiceChainReceiptRequest`. The bridge P2P handshake only checks `networkId` and `chainID`, both of which are public knowledge for any given service chain deployment.

### Impact Explanation
- **Persistent DB corruption**: `WriteAnchoredBlockNumber` advances the anchored block number in the bridge service DB, permanently recording a false anchoring confirmation.
- **Loss of retry**: The anchoring tx is removed from `BridgeTxPool` and will not be resubmitted. The child chain's data for that period is never actually anchored to the parent chain.
- **Security guarantee broken**: The anchoring mechanism's purpose is to provide a cryptographic commitment of child chain state on the parent chain. This attack silently voids that guarantee for targeted anchoring periods without any on-chain evidence.

### Likelihood Explanation
Any node that can connect to the child chain's bridge P2P port and pass the chain ID handshake can execute this attack. The required tx hashes are actively broadcast by the victim. No key compromise or majority collusion is needed.

### Recommendation
Add a status check in `writeServiceChainTxReceipts` before processing a receipt:

```go
if receipt.Status != types.ReceiptStatusSuccessful {
    logger.Warn("skipping failed service chain tx receipt", "txHash", txHash.String(), "status", receipt.Status)
    continue
}
```

Additionally, consider verifying the receipt against the parent chain's canonical state (e.g., via a local RPC call to a trusted parent node) rather than trusting P2P-delivered receipt data directly.

### Proof of Concept
1. Connect a malicious node to the child chain's bridge P2P port with the correct `networkId` and `chainID`.
2. Wait for the child chain to broadcast `ServiceChainReceiptRequestMsg` containing pending anchoring tx hashes.
3. Send a crafted `ServiceChainReceiptResponseMsg` containing a `ReceiptForStorage` with `TxHash` = one of those hashes and `Status` = 1 (or any value).
4. Observe that `writeServiceChainTxReceipts` calls `WriteAnchoredBlockNumber` and `RemoveTx` without the anchoring tx ever being executed on the parent chain.
5. Confirm via `ReadAnchoredBlockNumber` that the DB now records the block as anchored, and that the tx is gone from `BridgeTxPool`.

// handleServiceChainReceiptRequestMsg handles receipt request message from child chain.
// It will find and send corresponding receipts with given transaction hashes.
func (mbh *MainBridgeHandler) handleServiceChainReceiptRequestMsg(p BridgePeer, msg p2p.Msg) error {
	// Decode the retrieval message
	msgStream := rlp.NewStream(msg.Payload, uint64(msg.Size))
	if _, err := msgStream.List(); err != nil {
		return err
	}
	// Gather state data until the fetch or network limits is reached
	var (
		hash               common.Hash
		receiptsForStorage []*types.ReceiptForStorage
	)
	for len(receiptsForStorage) < downloader.MaxReceiptFetch {
		// Retrieve the hash of the next block
		if err := msgStream.Decode(&hash); err == rlp.EOL {
			break
		} else if err != nil {
			return errResp(ErrDecode, "msg %v: %v", msg, err)
		}
		// Retrieve the receipt of requested service chain tx, skip if unknown.
		receipt := mbh.mainbridge.blockchain.GetReceiptByTxHash(hash)
		if receipt == nil {
			continue
		}

		receiptsForStorage = append(receiptsForStorage, (*types.ReceiptForStorage)(receipt))
	}
	if len(receiptsForStorage) == 0 {
		return nil
	}
	return p.SendServiceChainReceiptResponse(receiptsForStorage)
}

// Handshake executes the Kaia protocol handshake, negotiating version number,
// network IDs, difficulties, head and genesis blocks.
func (p *baseBridgePeer) Handshake(network uint64, chainID, td *big.Int, head common.Hash) error {
	// Send out own handshake in a new thread
	errc := make(chan error, 2)
	var status statusData // safe to read after two values have been received from errc

	go func() {
		errc <- p2p.Send(p.rw, StatusMsg, &statusData{
			ProtocolVersion: uint32(p.version),
			NetworkId:       network,
			TD:              td,
			CurrentBlock:    head,
			ChainID:         chainID,
		})
	}()
	go func() {
		e := p.readStatus(network, &status)
		if e != nil {
			errc <- e
			return
		}
		errc <- e
	}()
	timeout := time.NewTimer(handshakeTimeout)
	defer timeout.Stop()
	for range 2 {
		select {
		case err := <-errc:
			if err != nil {
				return err
			}
		case <-timeout.C:
			return p2p.DiscReadTimeout
		}
	}
	p.td, p.head, p.chainID = status.TD, status.CurrentBlock, status.ChainID
	return nil
