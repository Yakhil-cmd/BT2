### Title
Webhook signature verification is keyed on an attacker-controlled organization field that is never bound to the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify the request against using `repository_owner`, a value read straight out of the unsigned JSON body (`params.dig('repository', 'owner', 'login')`). Every downstream handler, however, resolves the actual repository/stack to mutate using a *different* field from the same body: `payload.dig('repository', 'full_name')`. Because `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the selected organization has no `webhook_secret` configured (an explicitly supported, documented configuration), an unauthenticated caller can pick an org with no secret for the "authenticating" field while pointing `repository.full_name` at a completely different, secret-protected org/repo that handlers will actually act on. This is the same class of bug as the reported issue: a value trusted for accounting/authorization (`amount` transferred / `repository_owner` authenticated) is never reconciled with the value actually acted upon (`amount` received / `repository.full_name` mutated).

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is taken from the raw, unsigned JSON body itself, before any signature is validated. `Shipit.github(organization: ...)` looks up the `GitHubApp` config for that org name, and `verify_webhook_signature` in `lib/shipit/github_app.rb:76-83` short-circuits to `true` when that org's `webhook_secret` is blank:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

`webhook_secret` is explicitly documented as optional/nilable per-organization (`webhook_secret: # nil`) in the multi-org configuration example. [3](#0-2) 

Meanwhile, every handler resolves the repository to act on via a *different* field: `payload.dig('repository', 'full_name')`, used both in the base `Handler#repository_name` (feeding `stacks`) and directly by name in the pull-request handlers:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

Because `repository.owner.login` (used to select the secret) and `repository.full_name` (used to select the target repository/stack) are independent, attacker-controlled fields in the same unsigned payload, an attacker can set them inconsistently: `owner.login` = an org configured with no `webhook_secret`, and `full_name` = `"<victim-org>/<victim-repo>"` where the victim org *does* have a secret. Verification passes trivially (secret-less org), yet the handler acts on the victim's protected repository. This breaks the equality that should hold: `organization whose signature was verified == organization whose repository state is mutated`.

### Impact Explanation
A push event exploiting this reaches `PushHandler#process`, which calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack of the victim repository:
```ruby
def sync_github(expected_head_sha: nil)
  GithubSyncJob.perform_later(stack_id: id, expected_head_sha:)
end
``` [6](#0-5) 

`GithubSyncJob` fetches real commits for the victim stack from GitHub and appends them, potentially triggering downstream continuous-delivery/deploy behavior for the actual protected repository/branch. [7](#0-6) 

Pull-request handlers reachable the same way can archive/unarchive review stacks or capture labels for the victim repository without any legitimate GitHub delivery from that org, e.g. `PullRequest::ClosedHandler#process` archives a review stack, and `OpenedHandler` provisions one, both resolved via `params.repository.full_name`. [8](#0-7) [9](#0-8) 

This qualifies as unauthorized state mutation of a protected repository/stack driven by a forged webhook that bypassed signature checking - an unauthorized deploy-pipeline trigger against a repository the attacker never authenticated for.

### Likelihood Explanation
Exploitation requires only that the Shipit instance is configured for more than one GitHub organization and that at least one configured organization has no `webhook_secret` set - a state the shipped example configuration explicitly presents as a valid, supported option (`webhook_secret: # nil`). No credentials, tokens, or prior access are required; the attacker only needs the public webhook endpoint URL and knowledge of one org name that lacks a secret, then can freely choose the `repository.full_name` of any other configured org/repo.

### Recommendation
Bind signature verification to the exact repository the payload will be used to mutate, not to a separately-chosen field:
- Verify the signature using the secret associated with the same `repository.full_name` (or its derived owner) that handlers subsequently use to resolve the target `Repository`/`Stack`, rather than a `repository_owner` computed independently.
- Reject payloads where `repository.owner.login` and the owner segment of `repository.full_name` disagree.
- Do not allow signature verification to unconditionally pass (`return true unless webhook_secret`) for any organization that also owns a repository actually configured in Shipit; require a secret whenever the resolved repository exists in Shipit, or fail closed instead of open.

### Proof of Concept
Preconditions: Shipit configured for at least two organizations, e.g. `open-org` (no `webhook_secret`) and `victim-org` (has `webhook_secret`), with a Shipit stack for `victim-org/victim-repo` on branch `master`.

```
POST /github/webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   (arbitrary/invalid)
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
`verify_signature` resolves `github_app = Shipit.github(organization: "open-org")`; since `open-org` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the header value. `PushHandler` then resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob` for the victim stack, causing Shipit to fetch/append commits and potentially trigger deploy logic for a repository the request was never authenticated against.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
