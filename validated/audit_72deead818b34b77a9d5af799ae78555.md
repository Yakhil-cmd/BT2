### Title
Cross-repository status injection via unscoped `Commit.where(sha:)` amplified by `continuous_deployment` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by bare SHA with `Commit.where(sha: params.sha)`, with no join or filter on the repository that authenticated the webhook. Every other handler scopes writes to `stacks` derived from `Repository.from_github_repo_name(repository_name)` in the base `Handler` class, but `StatusHandler` bypasses that scoping entirely, so a legitimately-signed status webhook from repo A can create a `Status` row on a `Commit` belonging to an unrelated stack B whenever the SHA values coincide.

### Finding Description
The broken invariant, stated as an equality that should hold but doesn't:

`commit.stack.repository.full_name == payload.dig('repository', 'full_name')` should be true for every `Commit` mutated by a status webhook, but `StatusHandler#process` never checks it.

Code path:
- `Handler#stacks` (app/models/shipit/webhooks/handlers/handler.rb:32-38) computes `Repository.from_github_repo_name(repository_name)&.stacks`, which is how every other handler (push, pull_request, membership, check_suite) scopes its writes to the repository that authenticated the webhook.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) does not use `stacks` at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. This matches **any** `Commit` row in the database with that SHA, across all stacks/repositories/tenants.
- `Commit#create_status_from_github!` → `Status.replicate_from_github!` (app/models/shipit/commit.rb:165-169, app/models/shipit/status.rb:24-33) creates a `Status` scoped to `commit.stack_id`, i.e. whatever stack that commit row belongs to — not the repo that sent the webhook.
- `Status#after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` (app/models/shipit/status.rb:18-19) then trigger `Commit#schedule_continuous_delivery` (app/models/shipit/commit.rb:281-287), which, if `deployable? && stack.continuous_deployment? && stack.deployable?`, enqueues `ContinuousDeliveryJob` for the victim stack.

`verify_signature` in `Shipit::WebhooksController` (app/controllers/shipit/webhooks_controller.rb:24-49) only checks that the payload is signed with the secret belonging to the GitHub App installation on `repository_owner` (the org in the payload). It proves the webhook really came from that org/repo — it does **not** prove that the `sha` in the payload is unique to that repo. Git SHAs are content-addressed and identical across forks/mirrors that share commit history, so an attacker who owns/controls a repository (fork) that shares history with a victim's tracked repository can:
1. Push/tag a commit in their own repo whose SHA matches a commit already tracked in the victim's Shipit stack (shared upstream history).
2. Have GitHub deliver (or otherwise cause) a `status` event for `context: ci/test` with `state: success` for that SHA from their own, legitimately-signed installation.
3. `StatusHandler` writes that status onto the victim's `Commit` row (matched purely by SHA) belonging to the victim's stack, satisfying `required_statuses`/`ignore_ci?` logic.
4. If the victim stack has `continuous_deployment` enabled, `Commit#schedule_continuous_delivery` fires `ContinuousDeliveryJob`, deploying the now-"green" commit — code the attacker does not control the review of, but can time — or conversely, sending a `failure`/`error` status can flip `blocked?` to true and halt/rollback the victim's pipeline.

No existing guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, model validations) checks repo/stack scoping for `status` events; scoping only exists via the `stacks` helper that `StatusHandler` doesn't use.

### Impact Explanation
A payload authenticated for repository A can create a `Status` record for, and trigger CI-state-driven automation (`ContinuousDeliveryJob`) on, a `Commit`/`Stack` belonging to repository B, provided the SHA is shared. This matches the "payload for one repository mutating another's stack/commit" Critical category: it can force an unauthorized deploy (ship) or an unauthorized block/rollback signal on a victim's `continuous_deployment`-enabled stack. The attack is repeatable against any stack that (a) tracks a commit whose SHA also exists in a repo the attacker controls, and (b) has `continuous_deployment` enabled.

### Likelihood Explanation
Preconditions: attacker must control a repository capable of emitting a validly-signed `status` webhook (own repo/fork with GitHub App installed, or any repo under an org they administer), and the target victim stack must track a commit that shares a SHA with a commit in the attacker's repo (typical for public open-source forks/mirrors, submodule mirrors, or monorepo cross-mounts) and have `continuous_deployment` enabled. This does not require any Shipit secret, session, or API token — only ordinary GitHub repository ownership, matching the stated "unprivileged attacker" model. Given how common shared/forked git history is, this is a realistic, low-cost, and repeatable attack.

### Recommendation
Scope `StatusHandler#process` the same way other handlers are scoped: resolve the commit(s) via the `stacks` (or the specific `Repository` derived from `payload.dig('repository','full_name')`) rather than a bare `Commit.where(sha:)`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)`, and reject the event if `stacks` is empty/`Repository.from_github_repo_name` doesn't resolve.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` style):
```ruby
victim_stack = shipit_stacks(:shipit) # continuous_deployment: true, required_statuses: ['ci/test']
attacker_stack = create(:stack, repository: create(:repository, owner: 'attacker', name: 'evil'))

shared_sha = 'a' * 40
victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared history commit')
attacker_stack.commits.create!(sha: shared_sha, message: 'same content, attacker repo')

payload = {
  'sha' => shared_sha,
  'state' => 'success',
  'context' => 'ci/test',
  'repository' => { 'full_name' => 'attacker/evil', 'owner' => { 'login' => 'attacker' } }
}

# Assert broken binding: status written to victim_commit even though payload's repository is attacker/evil
assert_difference -> { victim_commit.statuses.count }, 1 do
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)
end
assert victim_commit.reload.success?
assert_equal 'attacker/evil', payload['repository']['full_name']
assert_not_equal payload['repository']['full_name'], victim_commit.stack.repository.full_name # binding violated

# And show it triggers ContinuousDeliveryJob for the victim stack
assert_enqueued_with(job: Shipit::ContinuousDeliveryJob, args: [victim_stack])
```
