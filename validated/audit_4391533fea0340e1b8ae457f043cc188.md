### Title
Operator-precedence bug in `OpenedHandler#provision?` lets `review_stacks_enabled=false` be bypassed via `allow_with_label`/`prevent_with_label` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `review_stacks_enabled` with the three `provisioning_behavior` checks using `&&`/`||` without parentheses grouping the first clause, so `review_stacks_enabled` only gates the `allow_all` branch, not the `allow_with_label` or `prevent_with_label` branches. This allows a `ReviewStack` to be created and enqueued for provisioning for a repository that has `review_stacks_enabled=false`.

### Finding Description
The claimed binding is: `review_stacks_enabled_as_configured (repository.review_stacks_enabled) == review_stacks_enabled_as_enforced (whether ReviewStackAdapter#create! is actually invoked)`.

The code is: [1](#0-0) 

Due to Ruby operator precedence, `&&` binds tighter than `||`, so this evaluates as:
```
(review_stacks_enabled && allow_all?) ||
(allow_with_label? && has_label) ||
(prevent_with_label? && !has_label)
```
`review_stacks_enabled` is only ANDed into the first disjunct. If `provisioning_behavior = allow_with_label` and the PR carries the configured label, the second disjunct is `true` independent of `review_stacks_enabled`. The same applies to `prevent_with_label` when the label is absent. This breaks the binding: `review_stacks_enabled=false` no longer implies "review stacks disabled" for two of the three behaviors.

`process` calls `respond_to_pull_request_opened?` → `provision?`, and if true calls `ReviewStackAdapter#find_or_create!`: [2](#0-1) 

`ReviewStackAdapter#create!` unconditionally persists a `ReviewStack` scoped only to `repository.review_stacks` (an unfiltered `has_many`, with no `review_stacks_enabled` check), and immediately enqueues it for provisioning: [3](#0-2) [4](#0-3) 

Once queued, the `ReviewStack` state machine transitions `deprovisioned → provisioning` and calls `stack.provisioner.up`: [5](#0-4) 

No other guard intervenes: `respond_to_pull_request_opened?` only checks `params.action == "opened"` before calling `provision?`; there is no separate re-check of `review_stacks_enabled` anywhere else in the opened-PR path. [6](#0-5) 

The existing test suite covers `allow_with_label`/`prevent_with_label` only with `review_stacks_enabled` left at its default `true` value, and never exercises the `review_stacks_enabled=false` + `allow_with_label`/`prevent_with_label` combination, so this divergence is untested: [7](#0-6) 

### Impact Explanation
For any Shipit-tracked repository configured with `review_stacks_enabled=false` but `provisioning_behavior=allow_with_label` (or `prevent_with_label`), a pull request that carries (or omits) the configured label causes a `ReviewStack` record to be created, a `PullRequest` row to be persisted, and the stack to be enqueued and transitioned into `provisioning`, invoking the repository's `provisioner.up`. Since review stacks provision using the repository's own `shipit.yml`/deploy spec, this results in unauthorized ReviewStack provisioning that the operator explicitly disabled (`review_stacks_enabled=false`), and downstream execution of attacker-influenced provisioning steps on the deploy host for that repository. This is repeatable for every PR opened against that repository as long as the misconfiguration persists, but it is scoped to that single repository/tenant — it does not let an attacker affect another repository's stacks.

### Likelihood Explanation
Exploitation requires the repository operator to have configured `provisioning_behavior` to `allow_with_label` or `prevent_with_label` while also setting `review_stacks_enabled=false` — an internally inconsistent but plausible configuration state (e.g., disabling review stacks generally while leaving a stale label-based behavior configured, or toggling `review_stacks_enabled` off without also resetting `provisioning_behavior` to `allow_all`). Given that configuration, any GitHub user able to open a PR and apply the configured label (or, for `prevent_with_label`, simply open a PR without the label) triggers the bug with a normal, correctly-signed GitHub webhook — no secrets or elevated Shipit privileges needed.

### Recommendation
Parenthesize the boolean expression so `review_stacks_enabled` gates all three behaviors:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Apply the same fix to `LabeledHandler`, `UnlabeledHandler`, and `ReopenedHandler` if they share this pattern (per the grep results, `provisioning_label_name`/`provisioning_behavior` logic also appears in `labeled_handler.rb`, `unlabeled_handler.rb`, and `reopened_handler.rb`, which should be checked for the same precedence bug).

### Proof of Concept
minitest plan (extends `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
1. `repository = shipit_repositories(:shipit)`; call `configure_provisioning_behavior(repository:, provisioning_enabled: false, behavior: :allow_with_label, label: "pull-requests-label")`.
2. Assert side #1 of the binding: `repository.reload.review_stacks_enabled == false`.
3. Build `payload = payload_parsed(:pull_request_opened)` and append `{ "name" => "pull-requests-label" }` to `payload["pull_request"]["labels"]`.
4. Call `OpenedHandler.new(payload).process`.
5. Assert side #2 of the binding: expect `Shipit::Stack.count` to be unchanged (`assert_no_difference`) since `review_stacks_enabled` is `false`; observe instead that a `ReviewStack` is persisted, demonstrating the divergence.
6. Additionally assert `repository.review_stacks.last.awaiting_provision?` is `true`, proving the stack was enqueued for provisioning despite `review_stacks_enabled=false`.
