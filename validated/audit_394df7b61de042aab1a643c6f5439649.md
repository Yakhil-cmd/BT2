The vulnerability is confirmed by the code itself, exactly as claimed.

### Title
Webhook signature verification bypass when organization has no `webhook_secret` configured, allowing unauthenticated forged webhook events - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` unconditionally returns `true` when the organization's `webhook_secret` config is blank, regardless of the `X-Hub-Signature` header or payload contents. Since `WebhooksController#verify_signature` treats this `true` as proof the request bytes were authenticated by GitHub, any internet user can POST arbitrary, unsigned webhook payloads that are then parsed and dispatched to real handlers for any organization lacking a configured secret.

### Finding Description
The broken binding: `verify_webhook_signature(signature, message) == true` is supposed to mean "these exact `message` bytes were HMAC-signed by GitHub using this organization's shared secret." Instead, for an organization with no secret configured, the binding degenerates to `true == true` unconditionally, independent of `signature` or `message`.

Code path:
1. `WebhooksController#create` runs `before_action :verify_signature` [1](#0-0) .
2. `verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` from the attacker-controlled `repository.owner.login` (or `organization.login`) field in the raw JSON body, then calls `github_app.verify_webhook_signature(...)`, only halting with `head(422)` if `verified` is falsy [2](#0-1) .
3. `GitHubApp#verify_webhook_signature` starts with `return true unless webhook_secret`, where `@webhook_secret = @config[:webhook_secret].presence` — if the org's Shipit config omits `webhook_secret`, this is `nil`, so the method returns `true` before ever inspecting `signature` or `message` [3](#0-2) , [4](#0-3) .
4. `create` then parses `request.raw_post` and dispatches to `Shipit::Webhooks.for_event(event)` handlers with no further authentication [5](#0-4) .

No other guard intervenes: `drop_unhandled_event` only filters by event name, not authenticity; `check_if_ping` short-circuits only `ping` events; there is no `ExplicitParameters` schema or session/API-token check in this controller at all — `WebhooksController` inherits from `ActionController::Base`, not the authenticated base controller.

The attacker's request: any unauthenticated HTTP client sends `POST /webhooks` with header `X-Github-Event: push` (or `status`, `check_suite`, `pull_request`, `membership`), any/no `X-Hub-Signature`, and a JSON body naming `repository.owner.login` as an organization whose Shipit config has no `webhook_secret` set. The handler for that event then executes exactly as if GitHub had sent it.

### Impact Explanation
Any organization onboarded into Shipit without a `webhook_secret` (a valid, supported configuration state per `GitHubApp#initialize`, not an error condition) is fully open to forged webhook events. An attacker can: enqueue `GithubSyncJob` for arbitrary commits, forge commit `status` updates that influence deploy/merge gating, forge `check_suite` events to trigger `RefreshCheckRunsJob`, create/delete team `Membership` records via forged `membership` events, or drive any other registered `Shipit::Webhooks` handler — including cross-organization targeting since `repository_owner` is fully attacker-controlled per request. This is a full authentication bypass on the webhook ingestion path, matching the Critical category (forged webhook events accepted; unauthorized state mutation for a repository/organization that never authenticated the request).

### Likelihood Explanation
The only precondition is that at least one organization configured in `Shipit.github(organization:)` lacks a `webhook_secret` value — this is a supported, non-default-enforced configuration (the code explicitly handles the "no secret" case as a legitimate branch, not a misconfiguration error). No credentials, sessions, or GitHub App keys are required by the attacker; the request is a single unauthenticated `POST /webhooks` with attacker-chosen headers and JSON body, fully repeatable against any such organization.

### Recommendation
Do not treat a missing `webhook_secret` as automatically verified. Either require `webhook_secret` to be present for every configured organization (fail closed at boot/config-load time if absent), or make `verify_webhook_signature` return `false` (reject) when no secret is configured, forcing operators to explicitly configure signature verification before webhooks are accepted.

### Proof of Concept
Minitest plan in `test/controllers/webhooks_controller_test.rb`:
```ruby
test "org with no webhook_secret accepts unsigned forged push event" do
  Shipit.github(organization: 'shopify').stubs(:webhook_secret).returns(nil) # or configure the org fixture with webhook_secret: nil

  request.headers['X-Github-Event'] = 'push'
  payload = JSON.parse(payload(:push_master))
  payload["repository"]["owner"]["login"] = "shopify" # victim org, no secret configured
  # no X-Hub-Signature header set at all

  assert_enqueued_with(job: GithubSyncJob) do
    post :create, body: payload.to_json, as: :json
  end
  assert_response :ok
end
```
Assertion on both sides of the binding: left side — `verify_webhook_signature(nil_or_arbitrary_signature, raw_post)` returns `true`; right side — the request bytes were actually signed by `shopify`'s secret — is `false` (no secret exists, no signing occurred). The test demonstrates the handler (`GithubSyncJob` enqueue) executes despite the two sides diverging, proving `head(422)` is never hit and `create` proceeds unauthenticated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
