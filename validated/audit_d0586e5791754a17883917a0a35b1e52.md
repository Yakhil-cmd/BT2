### Title
Cross-repository CI status forgery via unscoped commit lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `WebhooksController` verifies a webhook's HMAC signature against the GitHub App/org selected from an attacker-controlled JSON field (`repository.owner.login`), while `StatusHandler#process` writes a `Status` to whatever `Commit` rows match a `sha` value taken from that same untrusted payload — **without scoping the lookup to the repository/organization that was actually authenticated**. This breaks the trust binding "organization authenticated == repository written," the exact bug class described in the report (a check performed on one identity/parameter while the state-changing action is keyed on a different, colliding value).

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate the signature against using a value pulled straight out of the JSON body: [1](#0-0) [2](#0-1) 

In a multi-organization deployment (explicitly documented and supported, `docs/setup.md` "Using Multiple Github Applications"), each org has its own `webhook_secret`. Any org owner who controls their own installation of the Shipit GitHub App legitimately possesses their own org's `webhook_secret` and can compute a valid `X-Hub-Signature` for a payload of their choosing — as long as `repository.owner.login` (or `organization.login`) in the body names *their own* org, so `Shipit.github(organization: repository_owner)` picks the secret they know.

Once the signature check passes, the generic `Handler` base class independently derives the acted-upon repository from a *different* field of the same forged body: [3](#0-2) 

Most handlers (`PushHandler`, `CheckSuiteHandler`) correctly use this `stacks` helper, which scopes all lookups to `Repository.from_github_repo_name(repository_name)`: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, does **not** use `stacks` at all. It queries `Commit` globally by `sha`, with no repository/stack scoping whatsoever: [6](#0-5) 

This means the binding that is actually authenticated (payload's `repository.owner.login` → the org whose `webhook_secret` was used to accept the request) is never checked against the binding that is actually mutated (`Commit.where(sha: params.sha)` → any commit row in the entire database, belonging to any stack/repository, whose `sha` matches the attacker-supplied value). A `sha` collision across repositories is not exotic here: shared root commits, forked repositories, vendored/cherry-picked commits, or monorepo splits routinely produce identical SHAs across unrelated `Repository`/`Stack` records tracked by the same Shipit instance.

Writing a forged `Status` triggers real side effects: it marks the stack's CI as enabled and can flip a commit's `deployable?`/`simple_state`, and it schedules continuous delivery: [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker who is only an authenticated webhook sender for their **own** GitHub organization (a plausible, unprivileged "customer" of a shared/multi-org Shipit instance, requiring none of the excluded privileges — no `ApiClient` token, no `webhook_secret` of the victim, no repository write access, no session) can forge `state=success` statuses for a victim stack's commit if that commit's SHA is also present in the attacker's own tracked stack (e.g., via a shared history/fork/vendor commit). Because `Status` creation calls `enable_ci_on_stack` and `schedule_continuous_delivery`, this can cause a victim stack configured with `continuous_deployment: true` and a `require_ci`/CI gate to treat an untested or malicious commit as CI-green, resulting in an **unauthorized deploy** of that commit — squarely in the "Critical" impact bucket (unauthorized deploy). At minimum, it is a cross-repository, cross-tenant write of CI state with no scoping check, which independently qualifies as unauthorized cross-repository writes.

### Likelihood Explanation
The likelihood is moderate. It requires: (1) a multi-organization Shipit deployment (a documented, first-class supported configuration), (2) the attacker legitimately controlling/being able to configure a webhook for at least one organization onboarded to that instance, and (3) a SHA collision between a commit tracked under the attacker's stack and a commit tracked under the victim's stack — realistic for forks, shared vendor/template history, or monorepo splits, and, at minimum, easy to construct in a demonstration or CTF-style proof by intentionally forking/mirroring the victim's public repository history into the attacker's own tracked stack to guarantee shared SHAs. No brute-forcing of hashes is required (unlike the original SHA-256 hash-collision report), since the collision surface here is ordinary Git SHA reuse across related repositories, not a cryptographic collision.

### Recommendation
Short term: make `StatusHandler#process` scope its `Commit` lookup through the same `stacks` (repository-derived) helper used by `PushHandler` and `CheckSuiteHandler`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, instead of an unscoped `Commit.where(sha: params.sha)`. Long term: audit every `Webhooks::Handlers::*` subclass to guarantee that the repository/organization used to authenticate the webhook signature is the same repository/organization on which state-changing writes are performed, and add a regression test asserting that a `status` webhook cannot mutate commits belonging to a different `Repository` than the one identified by the authenticated `repository.owner.login`.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `github.webhook_secret` (per `docs/setup.md`'s multi-org config).
2. Attacker creates/tracks a stack in `attacker-org` whose commit history intentionally shares a commit `SHA` with a commit already tracked in a `victim-org` stack (e.g., by forking/mirroring the victim's public repo into their own tracked stack, or exploiting a naturally shared vendor/template commit).
3. Attacker crafts a `status` webhook JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" },
  "sha": "<shared-sha>",
  "state": "success",
  "context": "ci/travis"
}
```
4. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` (`X-Hub-Signature: sha1=<hmac>`), which `Shipit.github(organization: 'attacker-org').verify_webhook_signature` accepts.
5. `StatusHandler#process` runs `Commit.where(sha: '<shared-sha>')`, which returns the commit row belonging to `victim-org`'s stack, and calls `create_status_from_github!`, creating a `success` `Status` on the victim's commit — enabling CI-gated/continuous deployment of that commit in `victim-org` despite the attacker never having authenticated to or having write access on `victim-org`.
