This confirms the binding mismatch. The `verify_signature` before_action in `app/controllers/shipit/webhooks_controller.rb` selects which GitHub App's secret to check against using `repository_owner`, which is read straight from the untrusted JSON payload:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

But the handlers that actually act on the request resolve the target `Stack`/`Repository`/`Commit` using a *different* field of that same untrusted payload — `repository.full_name` in `Handler#repository_name` (used by `PushHandler`) [2](#0-1) , or globally by `sha` with no repository scoping at all in `StatusHandler#process` [3](#0-2) .

In a multi-organization Shipit deployment (as documented in `docs/setup.md`, `config/secrets.development.example.yml`), each GitHub org has its own `webhook_secret` [4](#0-3) . Since `repository_owner` (used to pick the secret) and `repository_name`/`sha` (used to pick the acted-upon record) are independent, unrelated keys in the same attacker-supplied JSON body, nothing forces them to refer to the same repository:

- Equality that should hold: `organization-that-signed(payload) == organization-that-owns(repository/commit acted upon)`.
- What the code actually checks: only that *some* valid signature exists for whatever `repository.owner.login` says, then trusts `repository.full_name` / `sha` unconditionally for the actual side effect.

**Exploit path**: An attacker who controls (or has installed) *any* GitHub App configured in this Shipit instance — even for their own throwaway organization, which requires no privileged access to the victim's org — can craft a POST to `/webhooks` with:
- `X-Github-Event: push`
- `X-Hub-Signature` computed with their own org's `webhook_secret`
- JSON body: `repository.owner.login = "attacker-org"` (so `verify_signature` selects and successfully verifies against their own secret) but `repository.full_name = "victim-org/victim-repo"` (so `PushHandler` looks up and syncs/deploys-triggers the victim's real `Stack` via `stack.sync_github`) [5](#0-4) .

For `status` events it's worse: `StatusHandler` doesn't even scope by repository, only by commit `sha` [3](#0-2) , so an attacker signing with their own org's secret can inject arbitrary CI/commit statuses (`create_status_from_github!`) for any commit sha across any stack in the whole installation, which can flip deployability/merge checks that gate unattended deploys.

This is only exploitable when the deployment is configured with multiple GitHub organizations (each with a distinct `webhook_secret`) sharing one Shipit instance — a documented, supported configuration [4](#0-3) ; with a single global `webhook_secret` the binding collapses back to one org and the analog doesn't apply.

### Title
Webhook signature verification binds to attacker-chosen `repository.owner.login`, not the repository/commit actually acted upon — cross-organization webhook spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify the `X-Hub-Signature` against using `params.dig('repository','owner','login')`, but the webhook handlers (`PushHandler`, `StatusHandler`) act on unrelated fields of the same untrusted payload (`repository.full_name`, `sha`) without re-checking that they belong to the organization whose secret actually verified.

### Finding Description
`verify_signature` computes `repository_owner` from the payload and fetches `Shipit.github(organization: repository_owner)` to verify the HMAC signature [6](#0-5) . Once verification passes, `create` dispatches the full payload to `Shipit::Webhooks.for_event(event)` handlers unmodified [7](#0-6) . `Handler#repository_name` derives the acted-upon repository from `payload.dig('repository','full_name')` — a field never covered by the org selection used for signature verification [8](#0-7) . `StatusHandler` doesn't even use the repository field, matching purely by global commit `sha` [3](#0-2) . In multi-org configurations, an attacker with any valid app/webhook secret for an org they control can forge a signature that passes verification while pointing the handler logic at a victim organization's repository or commit.

### Impact Explanation
This lets an attacker with no access to the victim organization or repository trigger `stack.sync_github` (re-sync from GitHub, which can advance branch state tracked by Shipit) via `PushHandler` [5](#0-4) , and inject/overwrite commit statuses on arbitrary commits across the whole installation via `StatusHandler`, which can be used to satisfy deployability checks that gate unattended deploys/merges. This crosses the "organization that authenticated versus the repository that is written" trust boundary and can lead to unauthorized deploy triggering.

### Likelihood Explanation
Requires only that the Shipit instance is configured for multiple GitHub organizations (a documented, supported setup) and that the attacker controls a GitHub App/webhook secret for any one of them — not privileged access to any other org. No Shipit session, `ApiClient` token, or repository write access to the victim repo is needed.

### Recommendation
After `verify_signature` succeeds, re-derive and enforce that `repository_owner` (or `organization.login`) matches the owner/organization of `repository.full_name` (and, for `status`, the org owning the commit's stack) before dispatching to handlers; reject the webhook otherwise.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` per `docs/setup.md`'s multi-app example.
2. Attacker computes `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over a JSON body: `{"ref":"refs/heads/master","after":"<sha>","repository":{"full_name":"victim-org/victim-repo","owner":{"login":"attacker-org"}}}`.
3. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` fetches `Shipit.github(organization: "attacker-org")` and verifies successfully against the attacker's own secret [6](#0-5) .
4. `PushHandler` looks up `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github` on its stacks, despite the request never being signed by `victim-org`'s app [2](#0-1) .
