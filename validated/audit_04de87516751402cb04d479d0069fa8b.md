### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` but the actual write target is chosen from the independently-controlled `repository.full_name` field, enabling cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/secret to validate the `X-Hub-Signature` against using `repository_owner`, computed as `params.dig('repository','owner','login')` (or `organization.login`) from the unauthenticated JSON body. [1](#0-0) [2](#0-1)  Once the signature check passes, `Shipit::Webhooks.for_event(event)` dispatches the same raw, attacker-supplied JSON body to handlers. [3](#0-2)  Those handlers resolve the `Repository`/`Stack` to act on using a *different* field, `payload.dig('repository', 'full_name')`, via `Handler#stacks`/`Handler#repository_name`. [4](#0-3)  Nothing in the engine enforces that `repository.owner.login` (used to select the verifying secret) and `repository.full_name` (used to select the repository being mutated) refer to the same organization.

### Finding Description
Shipit explicitly supports hosting multiple independent GitHub Apps/organizations from a single instance, each with its own `webhook_secret`: [5](#0-4) . In that configuration, whichever organization is named in the payload determines which App's secret is used to verify the signature: `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`. [1](#0-0) 

The HMAC check itself only proves that the request body was signed with *some* configured organization's secret — it does not bind the content of that body to that organization. `Shipit::Webhooks::Handlers::Handler#repository_name` reads `payload.dig('repository', 'full_name')` — a field entirely independent from `repository.owner.login` — to find the `Repository` and its `stacks`: [4](#0-3) . Handlers such as `PushHandler` then act directly on whatever stacks that lookup returns, e.g. triggering `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching the branch: [6](#0-5) . Similarly, `StatusHandler`/`CheckSuiteHandler` write commit statuses and check-suite state, and PR handlers mutate merge/review state for whichever repository `full_name` names — none of them re-validate that this repository belongs to the organization whose secret produced a valid signature.

Equality that should hold but doesn't:
`organization authenticated by verify_signature (repository_owner)` == `organization of the repository actually written to by the handler (repository.full_name)`

Before the attacker's request: for legitimate GitHub-originated deliveries, `repository.owner.login` and the owner segment of `repository.full_name` always match, because GitHub itself populates both fields consistently and signs the whole body.

After the attacker's request: an attacker who legitimately possesses the `webhook_secret` for organization A (e.g., a customer/tenant who administers their own GitHub App integration in a multi-org Shipit deployment) can freely construct any JSON body, set `repository.owner.login` (or `organization.login`) to `"org-a"` so the signature validates against org A's known secret, while setting `repository.full_name` to `"org-b/some-repo"` — a completely different organization/repository also hosted on the same Shipit instance. The signature check passes (it only cares that org A's secret matches the raw body), but the handler acts on org B's stack.

### Impact Explanation
This breaks the credential boundary between tenants/organizations hosted on one Shipit instance: possession of one organization's webhook secret should only authorize actions on that organization's repositories, but it can be used to forge webhook events (push syncs, commit statuses, check-suite results, pull-request/merge state changes) against any other organization's repositories configured in the same instance. This is a cross-repository write, matching the Critical impact bucket ("cross-repository writes"/"an unauthorized deploy" pathway, since forged `push`/`status`/`check_suite` events can influence `stack.schedule_merges`, deployable status, and continuous-deployment gating for a completely unrelated org's stack).

### Likelihood Explanation
Requires the attacker to already hold a legitimate webhook secret for at least one organization configured on the shared Shipit instance (a realistic condition for multi-tenant deployments where each org manages its own GitHub App/webhook config), and requires that a second, differently-owned organization/repository also be configured on that same instance. No GITHUB_TOKEN, session, or `ApiClient` token is needed — the webhook endpoint is unauthenticated aside from this per-organization HMAC.

### Recommendation
After signature verification, re-derive the organization from `repository.full_name` (or `organization.login` used in `Handler#repository_name`) and require it to match `repository_owner` used for `verify_signature`, rejecting the request (422) on mismatch. Alternatively, look up the `Repository`/`Stack` first, verify the signature using the specific GitHub App tied to that repository's owner, and reject if the two owners disagree, rather than trusting an unauthenticated field to select the verifying key independently from the field used to select the target of the action.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per the multi-org config format in `config/secrets.development.example.yml`).
2. As an administrator of `org-a`'s GitHub App/webhook integration, obtain `org-a`'s `webhook_secret`.
3. Craft a JSON payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
4. Compute `X-Hub-Signature: sha1=HMAC_SHA1(org-a_webhook_secret, body)` and send it as `X-Github-Event: push` to `POST /webhooks`.
5. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s app, and the signature validates successfully. [1](#0-0) 
6. `PushHandler#stacks` resolves via `Repository.from_github_repo_name("org-b/victim-repo")`, and triggers `sync_github` on `org-b`'s stack — an org the attacker has no legitimate access to. [4](#0-3) [6](#0-5)
