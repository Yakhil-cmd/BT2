### Title
Cross-organization webhook forgery via unbound `repository.owner.login` / `repository.full_name` fields - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to authenticate a webhook solely from `params.dig('repository','owner','login')`, while `PullRequest::OpenedHandler#repository` (and the base `Handler#stacks`) independently resolve the target `Shipit::Repository` from `params.repository.full_name`. Nothing in the request pipeline enforces that these two attacker-supplied JSON fields describe the same owner, so a payload can be signed with one organization's secret while acting on a repository belonging to a different organization.

### Finding Description
Binding claimed: `org(repository_owner) == org(full_name.split('/').first)`.

- `verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login')` and validates `request.raw_post` against `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- `OpenedHandler#repository` resolves the target `Shipit::Repository` purely from `params.repository.full_name`, independent of `repository.owner.login`: [3](#0-2) 
- `Repository.from_github_repo_name` simply splits the string on `/` and does a DB lookup with no cross-check against the verified owner: [4](#0-3) 
- The base `Handler#stacks`/`repository_name` helper has the same disconnect: it reads `payload.dig('repository', 'full_name')` with no relation to the field used for signature verification. [5](#0-4) 

Root cause: `repository.owner.login` and `repository.full_name` are two independent keys in the same untrusted JSON body (`params = JSON.parse(request.raw_post)`, `app/controllers/shipit/webhooks_controller.rb:11`). GitHub's real payloads always keep them consistent, but nothing in this engine enforces that invariant on the server side. An attacker who can produce a validly-signed webhook for **one** organization configured in Shipit (i.e., an org they legitimately administer/integrate) can put an arbitrary `full_name` (belonging to a **different** organization's `Shipit::Repository`) in the same payload. `verify_signature` will authenticate the payload using the correct org's secret (the org in `owner.login`), then `OpenedHandler` will act on whatever repository `full_name` names — potentially owned by an unrelated, unverified organization also hosted on the same Shipit instance.

None of the listed guards close this gap: `verify_signature` only checks the HMAC against the org named in `owner.login`, not the org implied by `full_name`; `drop_unhandled_event` only filters unknown event types; `ExplicitParameters` (`opened_handler.rb:8-39`) validates types/presence but not cross-field consistency; `Repository` model validations only constrain the format of `owner`/`name` columns already stored, not the relationship between the two payload fields.

### Impact Explanation
On a Shipit deployment configured for multiple GitHub organizations (each with its own `webhook_secret`, as the `GitHubApp`/`Shipit.github(organization:)` design and the multi-org secrets fixture imply [6](#0-5) ), a party that legitimately controls the webhook secret for Organization A can forge a `pull_request` `opened` event whose `repository.full_name` points at a repository owned by Organization B. This reaches `PullRequest::ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [7](#0-6) , creating/mutating a `ReviewStack` under Organization B's repository using fully attacker-controlled `pull_request.head.sha`/`ref`/`number`/labels — none of which were ever verified against Organization B's actual GitHub state. This is a payload for one (verified) tenant mutating another (unverified) tenant's stack, matching the Critical category in the impact rubric.

### Likelihood Explanation
Exploitation requires the attacker to already control (or know the secret for) at least one organization configured in the shared Shipit instance's `Shipit.github` configuration — i.e., a legitimate but unprivileged tenant of a multi-org Shipit deployment. Given that precondition, forging the cross-owner payload is trivial: a single crafted JSON POST to `/webhooks` with a correct `X-Hub-Signature` for their own org and an arbitrary `repository.full_name` for another tracked repository. The attack is fully repeatable against any repository record present in the shared instance's `shipit_repositories` table.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#initialize`/`Repository.from_github_repo_name`), assert that the owner segment of `repository.full_name` equals `repository.owner.login` (or `organization.login`) before verification succeeds, and reject (422) any payload where they diverge. Alternatively, derive the repository lookup exclusively from the same verified owner value rather than trusting `full_name` independently.

### Proof of Concept
Add a minitest to `test/controllers/webhooks_controller_test.rb`:
1. Configure two orgs in test secrets (already available via `test/dummy/config/secrets_double_github_app.yml`), e.g. `org-a` with secret `secret-a`, and create a `Shipit::Repository` owned by `org-b` with an existing `review_stacks_enabled` repo record.
2. Build a `pull_request` `opened` payload with `repository.owner.login = "org-a"` and `repository.full_name = "org-b/some-repo"`.
3. Sign the raw JSON body with `org-a`'s secret and POST to `/webhooks` with `X-Hub-Signature`.
4. Assert the response is `200 OK` (signature accepted for `org-a`).
5. Assert (expected-to-fail today) that no `Shipit::ReviewStack` was created under `org-b`'s repository — currently a stack IS created, proving the divergence is exploitable; the fix should make this assertion pass by rejecting the request instead.
