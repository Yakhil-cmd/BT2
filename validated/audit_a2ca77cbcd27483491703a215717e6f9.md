## Finding

### Title
Multisig transaction payload-approval binding check is feature-gated, allowing execution of a payload different from the one approved by owners - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`validate_multisig_transaction` (the on-chain multisig prologue invoked by the VM during mempool admission and transaction execution) only enforces that the payload actually executed matches the payload that owners voted to approve when the feature flag `abort_if_multisig_payload_mismatch_enabled` is turned on. When only a payload *hash* was stored at creation time, the hash check is unconditional and safe. But when the *full payload* was stored on-chain at creation time (the common case for `create_transaction`), the equality check between the submitted executable and the stored, voted-on payload is entirely skipped unless that feature is enabled. This is structurally the same defect class as the external report: a security-relevant binding (there: fuses/expiry on non-default domains; here: payload-to-approval binding on the non-default/legacy code path) is applied only in the "special-cased" path and silently omitted otherwise.

### Finding Description
The prologue that the VM runs before executing a multisig transaction is `validate_multisig_transaction`: [1](#0-0) 

- If `transaction.payload_hash` is `Some` (i.e., only the hash was stored on submission), the code unconditionally checks `sha3_256(payload) == *payload_hash` — this path is safe.
- If instead `transaction.payload` (the full payload) was stored on-chain, the corresponding equality check only runs when `features::abort_if_multisig_payload_mismatch_enabled()` is true, and only when the submitted `payload` is non-empty:
```
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    let stored_payload = transaction.payload.borrow();
    assert!(payload == *stored_payload, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
}
```
If this feature is disabled, there is **no check whatsoever** that the payload being executed matches the payload that owners voted to approve when the full payload (not a hash) was stored.

On the Rust/VM side, `run_multisig_prologue` derives `provided_payload` directly from whatever `TransactionExecutableRef` the *executing* account supplies in the outer transaction — this is attacker-controlled input, not something fetched from the approved on-chain record: [2](#0-1) 

Approval/quorum ("can_execute"/"can_be_executed", `num_approvals >= num_signatures_required`) is tracked purely by `sequence_number`, decoupled from payload content unless the payload/hash equality assertion above actually executes. Consequently, quorum for "sequence N" does not by itself guarantee that the payload run at execution time is the payload the owners approved — that guarantee depends entirely on the feature-gated check.

### Impact Explanation
If `abort_if_multisig_payload_mismatch_enabled` is disabled (or not yet activated on a given network/testnet/private deployment using this framework version), any owner permitted to execute a multisig transaction (i.e., who can author the wrapping transaction) can submit a completely different entry-function payload than the one that reached quorum approval, while the on-chain `MultisigAccount` record shows sufficient approvals for that sequence number. This is an admission-boundary authorization bypass: the wrong signer-approval set effectively authorizes an unrelated state transition, matching the "Authenticator/multisig approval validation accepting the wrong approval set" and "Pre-validation mismatch that causes a transaction which should fail admission to execute and commit" impact classes. Given multisig accounts commonly hold pooled funds or administrative capabilities, impact severity is High.

### Likelihood Explanation
Likelihood is contingent on the feature flag's activation state, which I could not conclusively determine to be default-on or default-off from the code alone (the search located the flag's definition and many references in `features.move`/`aptos_features.rs`, but not an authoritative "enabled at genesis" determination within the iteration budget). If the flag is active on the target network, this path is not exploitable. If it is inactive (e.g., a fresh devnet/testnet genesis, a fork of this codebase, or any deployment that has not enabled it), the bypass is directly reachable by any multisig owner with execute rights — no privileged access or leaked keys required. Because the safety of a security-critical binding check should not depend on an opt-in feature flag, this is a genuine design weakness independent of current activation status.

### Recommendation
Make the full-payload equality check unconditional (remove the `abort_if_multisig_payload_mismatch_enabled` gate) whenever `transaction.payload.is_some()`, mirroring the unconditional treatment already given to the `payload_hash` case. If backward compatibility requires staged rollout, treat the check as security-critical and audit whether it is enabled on all live networks before relying on it.

### Proof of Concept
1. Deploy/target a network (or codebase state) where `features::abort_if_multisig_payload_mismatch_enabled()` returns `false`.
2. Owner A creates a multisig transaction via `create_transaction` (or equivalent) with full entry-function payload `P1` (e.g., a benign transfer), storing `transaction.payload = Some(P1)` and `payload_hash = None`.
3. Owners vote and reach quorum (`num_signatures_required`) for that `sequence_number`, believing `P1` is what will run.
4. Owner A (or any owner with execute rights) submits the actual execute transaction using `TransactionExecutableRef::EntryFunction(P2)` where `P2 != P1` (e.g., draining funds to an attacker-controlled address).
5. `run_multisig_prologue` computes `provided_payload = bcs::to_bytes(MultisigTransactionPayload::EntryFunction(P2))`.
6. `validate_multisig_transaction` checks `payload_hash.is_some()` → false (skipped), then checks the feature flag → false → the `payload == stored_payload` assertion block is skipped entirely.
7. The VM proceeds to execute `P2` under the multisig account's authority, even though owners only approved `P1`.

**Caveat:** I was unable to conclusively confirm within this session whether `abort_if_multisig_payload_mismatch_enabled` is active by default on Aptos mainnet; verifying this (e.g., via `aptos-move/aptos-release-builder/src/components/feature_flags.rs` and genesis feature initialization) is needed to confirm real-world exploitability versus a latent design weakness that is currently mitigated by an already-enabled flag.

```rust
pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };
```
