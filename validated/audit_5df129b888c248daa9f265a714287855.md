## Title
Uncaught exception in `readDataFeedValue` sort comparator causes node crash/DoS on AA data-feed evaluation - ([File: data_feeds.js])

### Summary
`data_feeds.js`'s `readDataFeedValue()` builds a list of candidate unstable data-feed messages and, when more than one candidate matches the same `feed_name` from the referenced oracle address(es), sorts them by `latest_included_mc_index` and `level` to pick the winner. If two candidates tie on both fields and the caller did not request `all_unstable`, the comparator executes `throw Error("can't sort candidates ...")` instead of returning a validation error. This is directly analogous to the privacyIDEA CVE-2018-1000809 pattern: an edge-case/malformed input (here, two competing unstable units producing tied sort keys) is not defensively validated, and the resulting improperly handled condition causes an uncontrolled exception during normal request processing (DoS), rather than clean input rejection.

### Finding Description
`readDataFeedValue` is invoked from AA formula evaluation whenever an AA reads a `data_feed[[...]]` value from unstable data (`bIncludeUnstableAAs` path), which is the normal way AAs consume oracle price/data feeds before they are stable: [1](#0-0) 

Inside `readDataFeedValue`, all unstable messages matching the oracle address(es)/feed name are collected into `arrCandidates`: [2](#0-1) 

When more than one candidate is found and `ifseveral !== 'abort'`, the code sorts candidates by `latest_included_mc_index` then `level`, and only when `bIncludeAllUnstable` is true does it tolerate a tie (returning `1` arbitrarily); otherwise it throws synchronously inside the `Array.prototype.sort` comparator: [3](#0-2) 

This `throw` is not wrapped in a `try/catch` anywhere in the call chain from AA trigger execution (`formula/evaluation.js`'s `data_feed` case → `dataFeeds.readDataFeedValue` → `Array.prototype.sort`), so a synchronous exception propagates up through the AA trigger-processing logic (`aa_composer.js` / `handleTrigger`) instead of being converted into a formula "false"/fatal-error result the way other formula errors are (e.g. via `setFatalError`, which is used pervasively elsewhere in `formula/evaluation.js`). No top-level `uncaughtException`/domain handler catches this in the unit-processing path (only `network.js` has any such construct, unrelated to trigger execution), so depending on where in the async chain this fires it either crashes the whole node process or leaves it in an inconsistent state mid-trigger-processing.

An attacker who controls (or is) an "oracle" address referenced by a target AA's `data_feed[[oracles=...]]` formula can post two units from that same address, each containing a `data_feed` message with the same `feed_name`, arranged so both units become part of the unstable DAG with the same `latest_included_mc_index` and the same `level` (parallel/sibling units at the same DAG depth, later joined by later units at the same main-chain index, are a normal occurrence in the DAG, not requiring any special privilege). As soon as any node evaluates a trigger that reads that data feed via `data_feed[[...]]` without `unstable_opts === 'all_unstable'` and without `ifseveral: 'abort'`, the sort comparator throws.

### Impact Explanation
This is reachable by an ordinary unit poster (anyone can define/act as an "oracle" address referenced by any AA's formula — no special privilege is required to post `data_feed` messages) and by an AA author who merely reads unstable oracle data feeds, which is a common and encouraged AA pattern. The resulting uncaught exception can crash a node process while it is mid-way through processing an AA trigger/joint (a core code path exercised for every incoming unit and AA response), i.e., a network-wide denial of service is possible if many/all full nodes evaluate the same AA trigger against the same manipulated oracle data. This matches the "node unable to confirm new units" / "network unable to confirm new units" bar for High severity, since it is not merely a rejected malformed unit but an unhandled runtime exception in the hot processing path.

### Likelihood Explanation
Likelihood is High: no signature/permission is needed to become the "oracle" referenced in an AA's formula (any address can post `data_feed` messages), and producing two sibling/parallel units at the same latest-included-MC-index and DAG level from the same author is a normal-DAG-topology event that does not require exotic conditions — it simply requires posting two units around the same point in the DAG. The vulnerable condition is triggered automatically the next time any node evaluates the AA's `data_feed[[...]]` read against that oracle without `ifseveral: 'abort'`.

### Recommendation
Replace the `throw Error("can't sort candidates ...")` in the sort comparator in `data_feeds.js` (readDataFeedValue) with a defined, deterministic tie-break (e.g., by unit hash) instead of throwing, mirroring how the `bIncludeAllUnstable` branch already resolves ties without throwing. At minimum, wrap the call to `.sort()` (or the whole `readDataFeedValue`/formula evaluation call) in a `try/catch` that converts the exception into `setFatalError`/formula-false, consistent with the rest of `formula/evaluation.js`'s defensive error handling, so a crafted data feed ambiguity degrades to a formula error rather than crashing the process.

### Proof of Concept
1. Deploy (or use) an AA whose formula reads oracle data via `data_feed[[oracles="<ORACLE_ADDR>", feed_name="price"]]` (default `ifseveral` = `'last'`, not `'abort'`).
2. From `<ORACLE_ADDR>`, post unit A with message `{app: 'data_feed', payload: {price: 100}}`.
3. From the same `<ORACLE_ADDR>`, post unit B (sibling of A, i.e., same parents, not descending from A) with `{app: 'data_feed', payload: {price: 200}}`, such that both A and B end up with the same `latest_included_mc_index` and the same DAG `level` while still unstable (this is achievable by crafting parallel units with identical parent sets/witness lists so the DAG assigns them equal level).
4. Trigger the AA (post a unit paying it) while A and B are still unstable and tied.
5. During trigger evaluation, `readDataFeedValue` collects both A and B as candidates, finds `arrCandidates.length === 2`, and the comparator throws `"can't sort candidates ..."` uncaught, propagating out of the synchronous AA-formula evaluation call stack — confirmed by tracing `formula/evaluation.js:646` → `data_feeds.js:255-267` with no enclosing `try/catch` in the intervening call chain.

*Note: I was unable to fully verify from the available index whether "level" can be exactly tied for two sibling units and whether some intervening async boundary (e.g., inside `async.eachSeries`/promise wrapping in `aa_composer.js`) would turn the throw into an unhandled promise rejection versus a true process crash — this would need to be confirmed empirically in a running Devin session, since the full `aa_composer.js`/`graph.js` level-assignment logic was only partially retrievable through search.*
