### Title
Stack-scoped `ApiClient` tokens can read CCMenu build status of any stack, bypassing the token's `stack_id` scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` tokens can be minted with a `stack_id` restriction so that a token only authorizes access to one specific `Stack`, even if the token carries the `read:stack` permission. `Shipit::Api::BaseController` enforces this binding through its `stacks`/`stack` helper methods [1](#0-0) , which every other stack-scoped API controller relies on (e.g. `merge_requests_controller.rb`). `Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely and resolve the target stack directly from the URL parameter against the whole `Stack` table, only checking that the token has the generic `read:stack` permission bit, not that it is authorized for *this* stack [2](#0-1) .

### Finding Description
The binding that should hold is: `stack a token authorises == stack it touches`, i.e. `current_api_client.stack_id` should equal (or be nil, meaning "any") the `stack_id` param actually served.

- `BaseController#stacks` computes the authorized stack set from the token: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `BaseController#stack` resolves the requested stack from within that authorized set: `stacks.from_param!(params[:stack_id])` [1](#0-0) .
- `CCMenuController` redefines `stack` as `Stack.from_param!(params[:stack_id])`, which queries the entire `Stack` table with no reference to `current_api_client.stack_id` at all [3](#0-2) .
- The only authorization gate left is `require_permission :read, :stack`, which merely checks `current_api_client.permissions.include?('read:stack')` via `ApiClient#check_permissions!` [4](#0-3) . This check is scope-name based, not stack-instance based — it does not know or care which specific stack is being requested.

As a result, any token that carries `read:stack` permission — regardless of whether it was issued scoped to a single stack via `stack_id` — can be used against `CCMenuController#show` with an arbitrary `stack_id` in the URL to read another stack's CI/deploy status, bypassing the intended per-stack authorization boundary that every other API endpoint enforces through `BaseController#stack`.

This mirrors the report's bug class: a security-relevant scope (the LayerZero OFT `_debit`/`_credit` share accounting) was correctly enforced in the general mechanism but silently broken in one specific pathway, letting a value/authorization boundary (share value / stack scope) leak across the entity it was meant to isolate (chain / stack).

### Impact Explanation
This is an authorization-scope escalation: a token intentionally restricted to one stack (via `ApiClient.stack_id`) can read build/deploy status information for stacks it was never granted access to, purely because it hits `CCMenuController` instead of the properly-scoped controllers. This matches the specified High-impact class: "escalation into `Shipit.github_teams` authorization... or unauthenticated [/improperly-scoped] read of stack state, task streams or deploy output" — here it is a scope-check bypass yielding unauthorized read of another stack's state (last build status/label/time, activity, web URL) via a token whose intended authorization boundary was a single stack.

### Likelihood Explanation
Any holder of a `read:stack`-scoped `ApiClient` token — including tokens that were deliberately restricted to a single `stack_id` by an administrator, or tokens minted by `CCMenuUrlController` for a "CCMenu Client" — can trivially exploit this by substituting a different `stack_id` in the CCMenu URL/query params; no special privilege beyond possessing any valid `read:stack` token is required, and the request path (`GET /api/stacks/:stack_id/ccmenu`) is a normal, documented endpoint.

### Recommendation
Make `CCMenuController#stack` reuse the scoped lookup from `BaseController` instead of querying `Stack` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the `current_api_client.stack_id` authorization boundary consistently with every other stack-scoped API endpoint.

### Proof of Concept
1. Create (or have an admin create) an `ApiClient` restricted to `stack_id = A` with permission `read:stack` (e.g. through the mechanism used by `CCMenuUrlController#client`, or directly via the `ApiClient` model with `stack: stack_a`).
2. Using that token's `authentication_token`, issue: `GET /api/stacks/<owner>/<other-repo>/<other-env>/ccmenu?token=<token>` where the target `stack_id` corresponds to stack `B`, a stack the token was never scoped to.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `BaseController#stacks`), and `require_permission :read, :stack` only checks the permission name and not the specific stack, the request succeeds and returns stack `B`'s CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, etc.), even though the token was only authorized for stack `A`. # frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
