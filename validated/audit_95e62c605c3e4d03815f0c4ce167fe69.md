### Title
Cross-organization team membership forgery via `MembershipHandler#find_or_create_team!` trusting unvalidated `team.id` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to verify a webhook against using only the payload's own `organization.login` (or `repository.owner.login`) field, and `MembershipHandler#find_or_create_team!` then looks up the `Team` to mutate using only `params.team.id`, with no check that the team's `organization` matches the organization whose secret actually verified the request. An attacker who legitimately owns organization ORG_A (and thus knows/controls ORG_A's real webhook secret) can send a `membership` webhook whose `organization.login` is `org-a` (so signature verification succeeds against the attacker's real secret) but whose `team.id` is the `github_id` of a pre-existing `Team` row belonging to `org-b`, adding themselves as a member of that team.

### Finding Description
The broken binding: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` succeeding for `repository_owner == 'org-a'` should imply that any `Team` row mutated by the same request belongs to `org-a`; i.e. the equality `organization_that_signed == organization_that_owns(team_being_mutated)` must hold. It does not.

- `WebhooksController#verify_signature` derives `repository_owner` purely from attacker-supplied JSON: `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , and uses it only to select which `GithubHook::Organization`/secret to verify the HMAC against [2](#0-1) .
- `MembershipHandler#find_or_create_team!` finds/creates the `Team` solely by `github_id: params.team.id`; the `team.organization = params.organization.login` assignment only executes inside the `find_or_create_by!` block, which Rails only invokes when a **new** record is created — it is skipped entirely when a `Team` with that `github_id` already exists [3](#0-2) .
- `process` then does `team.add_member(User.find_or_create_by_login!(params.member.login))` for `action == 'added'` [4](#0-3) , creating a `Membership` row with no relation back to which organization's secret authenticated the request.

Exploit flow: attacker crafts a `membership` event payload with `organization.login = 'org-a'` (their own org — no `repository` key present in real membership payloads, so `repository_owner` resolves to `org-a`), `team.id = <github_id of a pre-existing Team owned by org-b>`, `member.login = <attacker's own login>`, `action: 'added'`, and signs it with `X-Hub-Signature` computed from ORG_A's real webhook secret. `verify_signature` fetches ORG_A's `GithubApp` and correctly verifies the signature (attacker genuinely controls this secret). `MembershipHandler#process` then finds the *existing* org-b `Team` by `github_id` (ignoring the `organization.login` field entirely since the record already exists) and appends the attacker as a member.

Existing guards do not close this gap: `verify_signature` only checks that *some* registered organization's secret matches the raw body — it never checks that the resolved organization equals the organization that owns the `team.id` being mutated. `ExplicitParameters` schema in `MembershipHandler` only validates types/presence of `team.id`, `organization.login`, `member.login`, not any cross-field consistency [5](#0-4) . `Team.find_or_create_by!` binds strictly to `github_id`, with the org column never re-validated on find [3](#0-2) .

### Impact Explanation
The attacker obtains a `Membership` row binding themselves to any pre-existing `Team` whose `github_id` they can guess or discover — including a team listed in `Shipit.github_teams`. `User#authorized?` is `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , so this directly flips `authorized?` to `true`, bypassing `force_github_authentication` for the entire Shipit instance and granting the attacker full authenticated access (deploys, rollbacks, merges, task streams) with no legitimate GitHub team membership in the real target organization. This is repeatable against any org whose team `github_id` is known, and any organization with a genuine `GithubHook::Organization` row can be used as the attacker's launching pad, so the blast radius spans all tenants sharing this Shipit instance. Matches "escalation into `Shipit.github_teams` authorization" (High) — and because it grants full authenticated Shipit access it can escalate further into Critical-class actions (deploys/rollbacks).

### Likelihood Explanation
Preconditions: attacker must own/control a GitHub organization with a genuine, correctly-configured `GithubHook::Organization` webhook installation on this Shipit instance (so they know their own real webhook secret) — a normal, unprivileged self-service setup. They must know the numeric `github_id` of a `Team` already present in Shipit's DB that's listed in `Shipit.github_teams` — team IDs are discoverable via GitHub's public/team API or by observing a legitimate membership event once (e.g., via GitHub UI/API for teams they can view, or brute-forcing small sequential IDs). No Shipit secrets, session, or API token are required. This is a single crafted HTTP POST, fully repeatable, low cost.

### Recommendation
In `MembershipHandler#find_or_create_team!`, always validate (not just set on create) that `params.organization.login == existing_team.organization`, and reject/raise if they don't match. Additionally, `WebhooksController#verify_signature` should ensure the resolved `repository_owner`/organization is cross-checked against the actual entity being mutated by each handler (e.g., pass the authenticated organization into the handler and have `MembershipHandler` refuse to mutate any `Team` whose `organization` column differs from it).

### Proof of Concept
minitest in `test/controllers/webhooks_controller_test.rb` (conceptual, illustrating the assertions needed — actual test file is out of scope per rules but described here for validation):
1. Create `shipit_teams(:shopify_developers)` fixture with `organization: 'org-b'`, `github_id: 48`, and add it to `Shipit.github_teams` via config/stub.
2. Register a `GithubHook::Organization` for `'org-a'` with a known/stubbed secret; stub `Shipit.github(organization: 'org-a').verify_webhook_signature` to return `true` (simulating a genuinely valid signature from ORG_A).
3. POST to `/webhooks` with header `X-Github-Event: membership`, body: `{ action: 'added', organization: { login: 'org-a' }, team: { id: 48, name: 'Developers', slug: 'developers', url: '...' }, member: { login: 'attacker' } }`.
4. Assert response `:ok`.
5. Assert `Membership.exists?(team: shipit_teams(:shopify_developers), user: User.find_by(login: 'attacker'))` is `true`.
6. Assert `User.find_by(login: 'attacker').authorized?` is `true`.
7. Both sides of the binding: `repository_owner` resolved (`'org-a'`) != `shipit_teams(:shopify_developers).organization` (`'org-b'`) — the mismatch persists after the request, confirming the broken binding.
