### Title
Cross-organization Team membership mutation via unscoped `github_id` lookup - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up an existing `Team` solely by `github_id`, with no check that the team's stored `organization` matches the organization whose webhook secret validated the request. A membership webhook validly signed by one onboarded organization's secret can therefore add or remove members on a `Team` record that actually belongs to a different onboarded organization, as long as the attacker knows/guesses that team's numeric GitHub `github_id`.

### Finding Description
The broken binding: the equality that should hold is `organization_that_signed_request (repository_owner used in Shipit.github(organization:)) == organization_that_owns_the_Team_row_being_mutated`. After tracing the code, this equality is **not enforced**.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) resolves `repository_owner` via `params.dig('repository','owner','login') || params.dig('organization','login')` (`webhooks_controller.rb:59-62`). For `membership` events there is no `repository` key, so `repository_owner` == `params['organization']['login']` — i.e. whatever organization the attacker puts in the payload's `organization.login`, as long as that org is a real, Shipit-onboarded org whose `webhook_secret` the attacker knows (per the stated precondition), the HMAC signature check passes.
- `MembershipHandler#process` / `#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`) then does:
  ```ruby
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
  ```
  The lookup key is `github_id` only. If a `Team` row with that `github_id` already exists (created earlier for a *different* organization, e.g. victim org B), `find_or_create_by!` returns that existing record and the block (which would set `organization`) never runs. The handler then unconditionally calls `team.add_member(member)` or `team.members.delete(member)` on that pre-existing record, mutating org B's team membership using a request whose signature was verified only against org A's secret.
- No other guard exists: `drop_unhandled_event` only checks the event has a registered handler; `ExplicitParameters` schema (`params do ... end` in the handler) only validates types/presence, not cross-field consistency between `organization.login` and the resolved team's real organization; there is no code anywhere that checks `team.organization == repository_owner` before mutating membership.

Attacker request: POST `/webhooks` with header `X-Github-Event: membership`, body `{"action":"added","team":{"id":<victim_team_github_id>,"name":...,"slug":...,"url":...},"organization":{"login":"org-a"},"member":{"login":"attacker-controlled-or-target-login"}}`, signed with org A's known `webhook_secret`. This passes `verify_signature` (org A) and then mutates the pre-existing `Team` row that actually belongs to org B.

### Impact Explanation
An attacker who controls (or knows the webhook secret of) one Shipit-onboarded organization can add arbitrary GitHub users (including accounts they control) to — or remove legitimate members from — a `Team` record belonging to a *different* onboarded organization, without ever authenticating as that organization. If the targeted `Team` is one of the teams referenced by `Shipit.github_teams` (used in `User#authorized?`, `app/models/shipit/user.rb:80-82`), this is a direct escalation path into Shipit's authorization system for a different tenant — matching the High-severity category "escalation into `Shipit.github_teams` authorization." It is repeatable against any victim team whose numeric `github_id` the attacker can obtain, and the blast radius spans all organizations sharing the Shipit instance.

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment with more than one organization registered in `Shipit.github` config; (2) attacker controls/knows a valid `webhook_secret` for at least one onboarded org (a precondition stipulated by the question, representing e.g. a customer/tenant admin who is not a global Shipit operator); (3) attacker knows the numeric GitHub `github_id` of a target team belonging to a different org (team IDs are not cryptographically secret and can often be discovered via GitHub's API/UI or from prior webhook traffic/logs); (4) the victim `Team` row must already exist in Shipit's database (created by any prior legitimate membership event) — the write is a no-op only for the `organization` field, but membership add/remove still executes regardless.

### Recommendation
Scope the `Team` lookup/creation by both `github_id` and the verified organization, and reject the webhook if they diverge, e.g.:
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  if team && team.organization != params.organization.login
    raise ArgumentError, "team #{params.team.id} does not belong to organization #{params.organization.login}"
  end
  team || Team.create!(github_id: params.team.id) do |t|
    t.github_team = params.team
    t.organization = params.organization.login
  end
end
```
Additionally, `WebhooksController#verify_signature` should be updated to cross-check that the payload's `organization.login` used for signature verification matches the `organization` field of any entity subsequently mutated by the handler, rather than trusting the payload's self-declared organization uncritically.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb (or webhooks_controller_test.rb)
test "membership webhook signed by org A cannot mutate a Team belonging to org B" do
  victim_team = Team.create!(github_id: 999, organization: 'org-b', slug: 'victim-team', name: 'Victim Team', api_url: 'https://api.github.com/teams/999')

  Shipit.github(organization: 'org-a') # assume org-a is configured with a known secret in test config

  request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: 999, name: 'Victim Team', slug: 'victim-team', url: 'https://api.github.com/teams/999' },
    organization: { login: 'org-a' }, # signed by org-a's secret
    member: { login: 'attacker-controlled-user' }
  }.to_json

  # sign with org-a's secret (attacker-known per precondition)
  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', org_a_secret, payload)
  request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { victim_team.reload.organization } do
    assert_difference -> { victim_team.members.count }, 1 do
      post :create, body: payload, as: :json
      assert_response :ok
    end
  end

  # Assertion: org-a's signature should NOT be able to mutate org-b's Team membership,
  # but the test demonstrates it does (add_member executes despite organization mismatch).
end
```
