### Title
`StatusHandler#process` writes commit statuses by global `sha` lookup with no repository binding, allowing a webhook from any GitHub App installation the attacker controls to forge status updates for commits belonging to unrelated stacks/repositories - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` is the only default handler that never calls `Handler#stacks` (which scopes lookups by `payload.dig('repository', 'full_name')`). Instead it resolves the target purely via `Commit.where(sha: params.sha)`, so any correctly-signed webhook - signed with a secret the attacker legitimately owns for their own GitHub App installation/org - can write a `Status` record onto a commit belonging to a completely different stack/repository, as long as the attacker knows that commit's SHA.

### Finding Description
The binding the codebase enforces elsewhere is: `repository_name (payload.dig('repository','full_name')) == scope of Commit/Stack mutated`. This is implemented via `Handler#stacks`: [1](#0-0) 

`PushHandler` and `CheckSuiteHandler` both consume `stacks`, which filters by `Repository.from_github_repo_name(repository_name)`: [2](#0-1) [3](#0-2) 

`StatusHandler`, however, never calls `stacks` and its `ExplicitParameters` schema requires only `sha`, `state`, and optional fields - no `repository` field at all: [4](#0-3) 

Its `process` method does a global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. Since `Commit#sha` is not scoped to any particular stack in this query, any commit row across the entire Shipit installation whose `sha` matches the attacker-supplied string is mutated, regardless of the `repository` field in the payload.

`WebhooksController#verify_signature` only proves the request was signed by the GitHub App secret belonging to `repository_owner = payload.dig('repository','owner','login')`: [5](#0-4) 

This proves *which org's secret* signed the payload - it does not bind the signature to the `sha`/`state`/`context` fields inside the same payload, and `StatusHandler` performs no such binding either. So an attacker who legitimately controls a GitHub App installation/org (e.g., their own org, with its own `webhook_secret` trusted by Shipit) can sign a `status` event whose `repository.full_name` is their own repo (satisfying `verify_signature`) but whose top-level `sha` is the SHA of a commit that belongs to a victim's stack in a completely different repository/org. Because Git commit SHAs are frequently public (visible in the victim's public git history, PR pages, other webhooks, CI logs, etc.), the attacker does not need any secret to learn a target SHA.

Exploit flow:
1. Attacker identifies a target commit `sha` belonging to a victim stack tracked in the same Shipit instance (e.g. from a public repo's commit history).
2. Attacker crafts a JSON body: `{"repository": {"full_name": "attacker/repo", "owner": {"login": "attacker-org"}}, "sha": "<victim sha>", "state": "success", "context": "ci/whatever"}`.
3. Attacker signs it with `X-Hub-Signature` using their own `webhook_secret` (valid, since they own that installation) and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` passes because it only checks the signature against `attacker-org`'s secret.
5. `StatusHandler#process` finds the victim's `Commit` row by global `sha` match and calls `commit.create_status_from_github!(params)`, writing a fabricated status (e.g., forced "success") onto the victim's commit.

`Commit#create_status_from_github!` → `add_status` re-evaluates `deployable?`/`blocking?` and can trigger `stack.schedule_merges` and `ContinuousDeliveryJob` if the new status is `pending` or `success`: [6](#0-5) [7](#0-6) [8](#0-7) 

None of `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema for `StatusHandler` validate that the `repository` in the payload owns the commit being mutated, so the divergence is real and unguarded.

### Impact Explanation
An attacker who controls any single GitHub App installation trusted by the Shipit instance can forge a fake CI status ("success"/"failure"/etc.) on any commit in any other tenant's stack, as long as they know its SHA. Since `deployable?`/`blocking?` and `schedule_continuous_delivery` are driven by commit status, this can be used to force an unauthorized deploy (marking a victim commit as passing CI so continuous delivery deploys it) or to block a legitimate deploy by marking a victim commit as failing, in a stack the attacker never authenticated for. This is a payload for one repository mutating another repository's commit/stack state - matching the "Critical: a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy" category. The blast radius spans all stacks/tenants hosted on the same Shipit instance, not just the attacker's own repository.

### Likelihood Explanation
Preconditions: the attacker needs a GitHub App installation whose `webhook_secret` Shipit already trusts (i.e., their own org/repo already onboarded to the Shipit instance - a normal, low-privilege prerequisite, not an operator credential) and the SHA of a target commit, which is typically public information. No Shipit session, API token, or GitHub secrets belonging to the victim are required. The attack is trivially repeatable against any commit whose SHA the attacker can learn, across any stack tracked by the Shipit instance, making it cheap and highly repeatable.

### Recommendation
In `StatusHandler#process`, restrict the `Commit` lookup to commits reachable from the webhook's own `repository` field, mirroring `PushHandler`/`CheckSuiteHandler`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`, and add `requires :repository do requires :full_name, String end` to the `ExplicitParameters` schema so the payload's repository is validated and used for scoping.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative - place under `test/` per repo conventions):
```ruby
test "StatusHandler mutates commits belonging to unrelated repositories" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')

  attacker_payload = {
    'repository' => { 'full_name' => 'attacker/unrelated-repo' },
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'attacker-forged-ci'
  }

  assert_equal 0, victim_commit.statuses.count

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  victim_commit.reload
  # Binding violated: repository field ('attacker/unrelated-repo') != victim_stack's repository,
  # yet the mutation still happened.
  assert_equal 1, victim_commit.statuses.count
  assert_equal 'success', victim_commit.statuses.last.state
end

test "PushHandler and CheckSuiteHandler do not mutate unrelated repositories (control)" do
  victim_stack = shipit_stacks(:shipit)
  attacker_payload_push = { 'repository' => { 'full_name' => 'attacker/unrelated-repo' }, 'ref' => "refs/heads/#{victim_stack.branch}", 'after' => 'b' * 40 }
  Shipit::Webhooks::Handlers::PushHandler.call(attacker_payload_push)
  # stacks resolves to Stack.none for 'attacker/unrelated-repo', so victim_stack.sync_github is never invoked.
end
```
This demonstrates the equality `repository_name-derived stack scope == mutation scope` holds for `PushHandler`/`CheckSuiteHandler` but is broken for `StatusHandler`, whose mutation scope is the unfiltered global `Commit.where(sha:)`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
