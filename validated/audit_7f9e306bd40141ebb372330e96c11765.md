### Title
Missing `return` after caught hash exception causes double-callback crash in private-payment processing - ([File: network.js])

### Summary
`handleSavedPrivatePayments()` in `network.js` computes a hash of an attacker-supplied private-payment head element inside a `try/catch`, but the `catch` block does not `return` after handling the error. Execution falls through and re-invokes the same downstream logic, ultimately calling the `async.each` iteratee callback (`cb`) a second time for the same row. A double-invoked callback inside `async.each` throws, and this codebase's global `uncaughtException` handler explicitly re-throws to crash the process. This gives any private-payment counterparty (or a hub forwarding such a payment) a way to crash a peer's ocore node/wallet process — structurally analogous to the Wireshark iSCSI dissector crash (CVE-2023-0415), where malformed input reaching a parsing/validation routine triggers an unhandled fault leading to denial of service.

### Finding Description
In `network.js`, `handleSavedPrivatePayments()` reads queued private-payment chains and, for each one, calls `validateAndSave()`: [1](#0-0) 

```
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
``` [2](#0-1) 

`objHeadPrivateElement.payload` is fully attacker-controlled: `arrPrivateElements` is the JSON that was previously queued from an untrusted `private_payment` message via `handleOnlinePrivatePayment()` and stored verbatim in `unhandled_private_payments.json` [3](#0-2) . A private-payment counterparty (the sender of the private chain, or a hub simply relaying it) fully controls the shape of this payload before it is ever structurally validated by `privatePayment.validateAndSavePrivatePaymentChain` (which only starts real validation after this point, see `private_payment.js`) [4](#0-3) .

If `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws (e.g., because the payload contains a value type the hashing/serialization code cannot handle, or a structure that causes an internal error), the `catch` block runs `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — which asynchronously calls `cb()` once the DB delete completes — but there is **no `return`** after this call. Execution therefore continues past the `catch` and immediately calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` with the very same malformed data. That call will eventually reach one of `ifOk`/`ifError`/`ifWaitingForChain`, each of which also calls `deleteHandledPrivateChain(..., cb)` or `cb()` directly [5](#0-4) .

The net effect is that the single `cb` supplied by `async.each`'s iteratee is invoked twice for the same row: once from the `catch` branch and once again from the `ifOk`/`ifError`/`ifWaitingForChain` branch of `validateAndSavePrivatePaymentChain`. The `async` library detects a callback called more than once and throws synchronously. That exception is not caught anywhere in this call chain, so it propagates up to Node's `process.on('uncaughtException')` handler: [6](#0-5) 

```
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	console.error('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```

which explicitly re-throws to terminate the process.

### Impact Explanation
Any counterparty able to initiate a private payment to a wallet-enabled node (light or full wallet) — a category explicitly in scope per the report's actor list ("private-payment counterparty") — can craft a payload that makes `objectHash.getBase64Hash` throw, causing the node process to crash via the double-callback / uncaught-exception path. A crashed node cannot process or relay units until manually restarted, which is a concrete denial-of-service impact on that node's ability to validate/confirm transactions, mirroring the crash-via-parsing impact of CVE-2023-0415. This is reachable purely by sending a malformed but structurally-plausible private payment element over the wallet device-message protocol; no compromise of a peer, hub, or node is required, only crafted application-level payload content.

### Likelihood Explanation
The trigger requires only that `objectHash.getBase64Hash()` throw for some payload shape reachable through the untrusted `private_payment` message path — this path stores attacker JSON directly (`JSON.stringify(arrPrivateElements)` at queue time, `JSON.parse(row.json)` at dequeue time) without prior schema validation of the head element's payload before this hash computation runs. Given the amount of freedom in JSON structure for `payload` (arbitrary nested objects/arrays/types), triggering an exception in the hashing/serialization routine is plausible, and the missing `return` guarantees the resulting crash path executes whenever that happens. I was not able to fully confirm from the indexed contents of `object_hash.js` which specific payload shapes make `getBase64Hash` throw (the file's contents beyond the function signature were not available in the index), so likelihood should be validated further by inspecting `object_hash.js` directly for the exact throwing conditions.

### Recommendation
Add a `return` after the `deleteHandledPrivateChain(...)` call in the `catch` block of `handleSavedPrivatePayments()`'s `validateAndSave` function so that execution does not fall through to `privatePayment.validateAndSavePrivatePaymentChain(...)` once the error has already been handled and `cb` already scheduled. More generally, audit all `try/catch` blocks in this file (and similar ones) that call `cb`/`deleteHandledPrivateChain` inside `catch` to ensure a `return` (or equivalent early exit) always follows, preventing any code path from invoking the same `async.each`/`async.eachSeries` callback more than once.

### Proof of Concept
1. As a private-payment counterparty (or the hub forwarding a `private_payment` message), send a `private_payment` message whose head element's `payload` field contains a value that causes `objectHash.getBase64Hash()` to throw an exception (exact triggering payload shape depends on `object_hash.js` internals, which should be inspected to construct a concrete value — e.g. a payload containing an unsupported type for the hashing routine).
2. The target wallet-enabled node queues this into `unhandled_private_payments` via `handleOnlinePrivatePayment` [3](#0-2) .
3. When `handleSavedPrivatePayments()` processes the queued row, `getBase64Hash` throws, the `catch` branch calls `deleteHandledPrivateChain(..., cb)`, then execution falls through and calls `privatePayment.validateAndSavePrivatePaymentChain(...)` with the same data, which invokes `cb` a second time.
4. `async.each`'s double-callback detection throws, which is uncaught and reaches `process.on('uncaughtException')`, which re-throws and crashes the node process [6](#0-5) .
