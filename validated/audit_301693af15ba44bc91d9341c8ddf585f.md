### Title
Cross-repository stack mutation via mismatched `repository.owner.login` (HMAC org selection) vs `repository.full_name` (stack lookup) - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/HMAC secret using `repository_owner` (`params.dig('repository','owner','login')`), while every `Handler` subclass resolves the target `Repository`/`Stack` using `payload.dig('repository','full_name')` via `Repository.from_github_repo_name`. These two payload reads are never cross-checked against each other, so an attacker who owns a legitimate GitHub App installation on their own org can forge a JSON body whose `repository.owner.login` matches their org (so the HMAC computed with their own known secret validates) while `repository.full_name` names an arbitrary victim org/repo, causing handlers to mutate the victim's stacks.

### Finding Description
The broken binding, stated as an equality that the code never enforces:
`repository_owner (params.dig('repository','owner','login'))` == `owner(repository.full_name (payload.dig('repository','full_name')))`

Trace:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(signature, raw_post)`. `repository_owner` is read from `params.dig('repository','owner','login') || params.dig('organization','login')` (webhooks_controller.rb:59-62).
- `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83) just HMAC-verifies the raw byte string against the secret configured for whichever organization `Shipit.github` resolved — it does not look at, or validate, any other field of the payload (in particular not `repository.full_name`).
- After signature verification, `WebhooksController#create` (webhooks_controller.rb:10-15) parses the same raw body and dispatches it unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`.
- Inside `Handler` (app/models/shipit/webhooks/handlers/handler.rb:32-38), `stacks` is computed as `Repository.from_github_repo_name(repository_name)&.stacks`, where `repository_name = payload.dig('repository', 'full_name')` — a completely independent read of the same JSON body, disconnected from `repository_owner`.
- Concrete handlers such as `PullRequest::ClosedHandler` and `PullRequest::LabeledHandler` resolve `repository` the same way (`Shipit::Repository.from_github_repo_name(params.repository.full_name)`) and then call mutating methods (`review_stack.archive!`, `stack.archive!`, `stack.unarchive!`) on whatever `Repository`/`Stack` that name resolves to.

Because only the raw request bytes are HMAC-checked (not any parsed field), the attacker fully controls the JSON structure. They can set `repository.owner.login` to their own org (so `Shipit.github(organization: repository_owner)` picks the GitHub App config whose `webhook_secret` they know, since they legitimately administer that org's App installation), while independently setting `repository.full_name` to `victim-org/victim-repo`. No code path anywhere compares `repository_owner` to the owner segment of `repository.full_name`; `ExplicitParameters` schemas in the handlers only validate types/presence of `repository.full_name`, not its relationship to `repository.owner.login`.

### Impact Explanation
An attacker who legitimately controls one org's GitHub App installation on a shared/multi-tenant Shipit instance can sign a webhook body with their own known secret and have it accepted, then have that payload's `repository.full_name` field steer `Handler` subclasses to mutate an entirely different org's `Repository`/`Stack` records (e.g., archiving/unarchiving review stacks via `ClosedHandler`/`LabeledHandler`). This is a payload for one repository mutating another's stack — a Critical-severity cross-tenant integrity violation. It is fully repeatable against any repository name the attacker can guess or discover, and repeatable per request with no rate limiting.

### Likelihood Explanation
Precondition: the Shipit instance must be configured for multiple GitHub orgs (`Shipit.github(organization:)` resolving different `webhook_secret` per org), and the attacker must have their own legitimate org onboarded (a normal, low-privilege multi-tenant scenario, not requiring any victim secret). Attacker cost is minimal: craft one JSON POST to `/webhooks/github` with a valid `X-Hub-Signature` computed with their own known secret, and mismatched `owner.login`/`full_name` fields. No GitHub-side interaction (real push/PR) is required since the controller does not verify the payload originated from GitHub for that named repo. Feasible and repeatable at will.

### Recommendation
In `Handler#repository_name` (or centrally before dispatch in `WebhooksController#create`), verify that the owner portion of `payload.dig('repository','full_name')` equals `repository_owner` (or `payload.dig('repository','owner','login')`) used for signature verification, and reject/ignore the event if they diverge. Alternatively, pass the already-authenticated `repository_owner` into handlers and require handlers to use it (not a second independent read of `full_name`) when resolving `Repository.from_github_repo_name`.

6. Assert response is `:ok` (signature accepted).
