### Title
Webhook signature is verified against the organization derived from the payload, but events are dispatched to the repository named in the same (unverified-for-binding) payload field — allowing cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the `X-Hub-Signature` against using `repository_owner`, a value read straight out of the untrusted JSON body (`repository.owner.login` or `organization.login`). Once the signature check passes, `Shipit::Webhooks::Handlers::Handler#repository_name` — used by every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`) to decide which `Stack`/`Repository`/`Team` to mutate — reads a *different* field from the *same* payload: `repository.full_name`. Nothing ties these two fields together. In a multi-organization Shipit deployment (a documented, supported configuration, see `test/dummy/config/secrets_double_github_app.yml`), anyone who controls the GitHub App installation for one organization (and therefore knows that organization's `webhook_secret`) can sign a payload whose `repository.owner.login`/`organization.login` matches their own org (so it passes `verify_webhook_signature`), while `repository.full_name` names a completely different organization's repository tracked by the same Shipit instance. This breaks the intended binding "organization that authenticated == repository being written to," mirroring the ERC1155A bug where the check was performed against one identity while the state mutation was applied to another.

### Finding Description
- `verify_signature` picks the verification key based on the payload, not on any pre-established trust boundary: [1](#0-0) [2](#0-1) 

- `Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization key present in `secrets.github`: [3](#0-2) 

- Once verification succeeds, every handler resolves the repository/stack to mutate from an entirely separate, never-cross-checked payload field: [4](#0-3) 

- `PushHandler#process` uses that lookup to enqueue real synchronization/deploy work against whatever stacks are found for `repository.full_name`: [5](#0-4) [6](#0-5) 

- Multi-organization configuration, where each org has its own `webhook_secret`/`app_id`, is a first-class, documented Shipit feature, not a hypothetical edge case: [7](#0-6) 

The binding that should hold is: `organization whose webhook_secret produced a valid signature == organization owning the repository that gets acted upon`. Because `verify_signature`'s `repository_owner` and `Handler#repository_name`'s `full_name` are independently read from the same attacker-controlled JSON body, that equality is never enforced — an attacker can make the two fields disagree.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. A party who legitimately controls a GitHub App installation for Organization A (and thus knows Org A's webhook secret, which is not a privileged Shipit credential — no `ApiClient` token, no Shipit account, no repository write access to Org B is needed) can forge signed webhook deliveries whose `repository.full_name` points at Organization B's repositories, as long as both orgs are configured in the same Shipit deployment (multi-org config is explicitly supported and documented). This can:
- Force `GithubSyncJob` to run against Org B's stacks, mutating commit/status state and, on stacks with continuous delivery enabled, triggering an **unauthorized deploy**.
- Drive `MembershipHandler`/team-membership webhooks for teams unrelated to the attacker's own org, tampering with `Shipit.github_teams` authorization data used to gate access to the whole application.

This satisfies the Critical bar ("an unauthorized deploy, rollback or merge") and/or the High bar ("escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
Exploitability requires only that the attacker administers a GitHub App installation for *any* organization configured in the target Shipit instance's multi-org secrets — a routine, low-privilege position relative to the other organizations tracked by the same instance. No Shipit session, API token, or GitHub write access on the victim org is needed; only knowledge of one's own org's `webhook_secret`, which the attacker legitimately possesses. Multi-org Shipit deployments (shared instance, distinct orgs/secrets) are the documented use case this feature exists for, making the attacker population realistic rather than theoretical.

### Recommendation
After signature verification, re-derive the organization strictly from the same field used to route the event (`repository.full_name`'s owner segment, or `organization.login`) and reject the request (422) if it does not match the organization whose secret validated the signature. Concretely, compute `repository_owner` once, use it consistently both to select the verification key and to constrain `Handler#repository_name`/`stacks` lookups (e.g., pass the verified organization into `Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization:) }` and have `Handler#stacks` scope by that organization), so the two must refer to the same entity.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), both tracking real stacks/repositories in the same Shipit instance.
2. Attacker legitimately administers `OrgA`'s GitHub App installation and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<sha attacker wants synced>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/production-repo"
     }
   }
   ```
4. Attacker computes `X-Hub-Signature` using `OrgA`'s `webhook_secret` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature verifies successfully.
6. `PushHandler#process` calls `Handler#repository_name`, which reads `repository.full_name` = `"OrgB/production-repo"`, looks up `OrgB`'s stacks, and enqueues `GithubSyncJob` against them — even though the request was never signed by `OrgB`'s webhook secret and the attacker has no relationship to `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
