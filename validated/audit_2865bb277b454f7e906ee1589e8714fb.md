Confirmed: `address_definition_change` is an ordinary, non-malicious message any address owner can send at any time (e.g. wallet key rotation), and `filterAttestedAddresses` in `storage.js` explicitly invalidates a prior attestation once such a change occurs after the attestation date. This gives a concrete, reachable mechanism for the analog.

### Title
Recipient address becomes permanently unattested (blacklisted-equivalent) after a routine key/definition change, freezing `spender_attested` asset funds held by an AA - (File: `validation.js`, `storage.js`)

### Summary
An Autonomous Agent (AA) that pays out a `spender_attested` asset to a recipient address it has committed to (e.g., stored once in a state variable such as `var['recipient']=trigger.address`, as in patterns like `test/samples/ico_with_milestones.oscript` and `test/samples/fundraising_proxy.oscript`) has no way to redirect or update that recipient if the recipient's attestation subsequently becomes invalid. Because the AA's oscript logic and stored state are immutable, once the intended payout is blocked at unit-validation time, the funds are permanently stuck in the AA balance — exactly the "recipient blacklisted after registration, no way to update" bug class from the report.

### Finding Description
For assets with `spender_attested: true`, every payment output address must pass an attestation check performed by `storage.filterAttestedAddresses` [1](#0-0) , and this same check is invoked from `validatePaymentInputsAndOutputs` for every output address of a transfer or issue message [2](#0-1) .

Crucially, `filterAttestedAddresses` only counts an attestation as valid if it was issued *after* the most recent stable `address_definition_change` for that address:
```sql
main_chain_index>IFNULL(
  (SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit)
  WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1),
0)
``` [3](#0-2) 

`address_definition_change` is a completely ordinary, permissionless message that any address owner can post at any time (e.g., to rotate keys or switch to a multisig definition), independent of any AA or attestor action [4](#0-3) , and it is validated/recorded generically in `validation.js` and `writer.js` [5](#0-4) [6](#0-5) .

The consequence: if a recipient address changes its own definition *after* being attested (a routine, benign action with no relation to the AA or the asset issuer), its earlier attestation is retroactively disqualified. Any subsequent attempt by an AA to pay that address a `spender_attested` asset will fail unit validation with `"some output addresses are not attested"` [7](#0-6) , causing the AA response to bounce (see `bounce()` in `aa_composer.js`) [8](#0-7) . Unlike the initial-registration-only mutability window in the referenced report, ocore AAs typically have exactly one, immutable code path for a given trigger condition — there is no built-in mechanism for the AA to detect that a stored recipient has lost attestation and route funds elsewhere, and the AA definition itself cannot be amended after deployment.

### Impact Explanation
Any AA design that (a) records a payout recipient once (state var, e.g., the original contributor/`trigger.address`) and (b) later disburses a `spender_attested` asset to that recorded recipient is exposed. If the recipient rotates their address definition (an entirely normal, un-coordinated wallet operation) between the time attestation was granted and the time of payout, the AA's payment will permanently fail validation. Since AA logic cannot be modified post-deployment and the state variable holding the recipient cannot be updated by any authorized party, the asset balance becomes permanently unspendable/frozen inside the AA — a concrete case of AA fund freezing.

### Likelihood Explanation
This requires no malicious actor: an ordinary user rotating their wallet keys (a security best practice) after having been attested but before an AA settles their share is sufficient to trigger the freeze. Any AA pattern that batches/delays payouts to previously-recorded addresses of a `spender_attested` asset (crowdsales, vesting, staking, escrow, reward distribution) is susceptible. The precondition (asset with `spender_attested: true`) is opt-in by the asset definer, but such assets are explicitly supported and demonstrated in the codebase's own sample AA scripts.

### Recommendation
- When designing/auditing AAs that hold or must later transfer `spender_attested` assets, avoid committing irrevocably to a single stored recipient address for payout; provide a fallback/redirect path (e.g., allow the recipient to supply an alternate, currently-attested address, or allow a privileged party to update the stored recipient) before final disbursement.
- Consider whether `filterAttestedAddresses`'s policy of invalidating attestations on any definition change (`storage.js:1960-1974`) is overly strict for cases where the address only rotates keys without changing its underlying identity/ownership, since it silently breaks unrelated smart-contract commitments.

### Proof of Concept
1. Attestor `Att` attests address `R` for asset `X` (`spender_attested: true`), recorded in `attestations` at MCI `m1`.
2. An AA is triggered by `R` and stores `var['recipient'] = trigger.address` (i.e., `R`) intending to later pay out asset `X` to `R` (pattern matches AA templates like `test/samples/fundraising_proxy.oscript`).
3. `R` posts an ordinary `address_definition_change` message (e.g., rotates to a new key set) at MCI `m2 > m1`, recorded in `address_definition_changes`.
4. A later trigger causes the AA to execute its payment message sending asset `X` to `var['recipient']` (= `R`).
5. During validation, `filterAttestedAddresses` finds no attestation for `R` with `main_chain_index > m2`, so `R` is excluded from `arrAttestedOutputAddresses` [9](#0-8) .
6. `validatePaymentInputsAndOutputs` returns `"some output addresses are not attested"` [7](#0-6) , the AA response bounces, and the asset amount stays trapped in the AA's balance indefinitely since the AA has no alternative code path or means to update `var['recipient']`.
