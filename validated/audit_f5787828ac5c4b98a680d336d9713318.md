### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status from *any* registered repository write a `Status` row against a victim stack's commit, which `Commit#blocked?` then treats as clearing every subsequent commit in that stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook purely by SHA, with no check that the webhook's `repository` matches the `Commit`'s own stack/repository. If a commit SHA is shared across two Shipit-tracked repositories (the common case for a public repo and any of its forks/mirrors that are also registered as Shipit stacks), a validly-signed webhook from one repository's own org secret can create a `Status` on a commit that actually belongs to a different repository's stack. Because `Commit#blocked?` scans `stack.commits.reachable.newer_than(last_deployed).older_than(self)` for `blocking?` statuses, one such forged `success` status on an early "blocking" commit removes the block for every later, undeployed commit in the *same victim stack* in one shot, and the `Status#schedule_continuous_delivery` callback then triggers an actual deploy of that backlog.

### Finding Description
The claimed broken binding: `webhook.repository.full_name == commit.stack.repository.full_name` for every `Commit` mutated by `StatusHandler#process`. Tracing the code shows this equality is never checked.

`StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
This query is global across the `commits` table - it is not scoped by `stack_id`, `repository_id`, or the payload's `repository.full_name`. `Commit#create_status_from_github!` then persists the status against that specific commit's own `stack_id`:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [2](#0-1) 

The only authentication performed before this point is organization-level HMAC verification keyed off `params.dig('repository', 'owner', 'login')`:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 
This only proves that the payload's claimed org owns a secret that signed it - it does not prove that the `sha` in the payload actually belongs to a commit in *that* org's repository. Since git commit SHAs are content hashes, any fork or mirror of a public repo shares identical SHAs with its upstream for unmodified history. If the attacker's own repository (which they legitimately own, per the rules) is also registered as a Shipit stack, a completely real, correctly-signed GitHub `status` webhook from the attacker's own repo/org - naming a SHA that is shared with the victim's repo history - reaches `StatusHandler#process` and is applied against the victim's `Commit` row and victim's `stack_id`.

Downstream, `Commit#blocked?`:
```ruby
def blocked?
  return false if stack.blocking_statuses.empty?
  stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)
end
``` [4](#0-3) 
and `Status::Common#blocking?`:
```ruby
def blocking?
  !success? && commit.blocking_statuses.include?(context)
end
``` [5](#0-4) 
scan the *whole undeployed range* of the stack, not just the mutated commit. Flipping the blocking commit N to `success` therefore flips `blocked?` to `false` for every commit N+1..N+k in the same range in one evaluation, and `Commit#deployable?` becomes true for all of them:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [6](#0-5) 
`Status` creation schedules continuous delivery on `after_commit`:
```ruby
after_commit :schedule_continuous_delivery, :broadcast_update, on: :create
...
def schedule_continuous_delivery
  commit.schedule_continuous_delivery
end
``` [7](#0-6) 
which is the mechanism that turns the newly-unblocked backlog into an actual deploy.

Existing guards do not close this gap: `verify_signature`/`GithubHook` only verifies the organization named in the payload owns a valid HMAC secret, it never cross-checks that the SHA belongs to that organization's repository; the `StatusHandler` `ExplicitParameters` schema only validates presence/type of `sha`/`state`/`context`, not repository ownership; there is no `Repository`- or `Stack`-scoped `where` clause anywhere in the `Commit.where(sha:)` call chain.

### Impact Explanation
A commit that is written for a repository that never authenticated it - the write is authenticated only under the attacker's own org/repo webhook secret, yet it lands on the victim's `Stack`'s `Commit`/`Status` rows and can unblock and trigger an unauthorized deploy of the victim's backlog. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." The blast radius per forged status write is every undeployed commit between `last_deployed_commit` and the forged commit in the victim stack, not just the single row that was mutated, and it is repeatable against any victim stack whose commit history intersects (via fork/mirror) a repository the attacker controls and has registered with Shipit.

### Likelihood Explanation
Preconditions: (1) the attacker must control a repository that is itself registered as a Shipit stack (so their own org's webhook secret is valid and their signed events reach `StatusHandler`), and (2) that repository's commit history must share at least one SHA with the victim's repository, which is trivially true for any GitHub fork of a public repo with unmodified history, or a mirrored/vendored commit. Given those two conditions - both plausible in any Shipit deployment that lets teams self-register stacks for their own forks/mirrors - the attack is a single legitimate signed webhook POST (no secrets need to be broken; the attacker signs with their own valid secret) and is fully repeatable against any stack sharing history with an attacker-controlled repo.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers, e.g. check-run handling) by the webhook's own repository, not by SHA alone - e.g. resolve `Repository` from `params.dig('repository', 'full_name')` (or the pre-verified `repository_owner`) first, and restrict `Commit.where(sha: params.sha)` to commits whose `stack.repository_id` matches that resolved repository. Reject or ignore status events whose declared repository does not match the tracked repository of the commit(s) found for that SHA.

### Proof of Concept
Minitest plan (webhook/model layer, no live GitHub):
1. Fixtures: create two `Stack`s, `victim_stack` (repository `victim/app`) and `attacker_stack` (repository `attacker/app-fork`), each with a `Commit` sharing the exact same `sha` value (simulating a forked history), using a chain like `soc_second` (blocking) -> `soc_third` (queued behind it) on `victim_stack`.
2. Assert baseline binding: `victim_stack.commits.find_by(sha: shared_sha).stack_id != attacker_stack.commits.find_by(sha: shared_sha).stack_id` (two different stacks, same sha) - confirming the equality `webhook.repository == commit.stack.repository` is meaningful and currently unchecked.
3. Simulate an attacker-authenticated webhook payload with `repository.full_name = "attacker/app-fork"`, `sha = shared_sha`, `state = "success"`, `context = <blocking context>`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.new(...).process` (or POST through `WebhooksController#create` with `GithubHook#verify_signature` stubbed true, matching existing test patterns in `test/controllers/webhooks_controller_test.rb`).
5. `assert_changes -> { victim_stack.commits.find_by(sha: shared_sha).reload.blocked? }, from: true, to: false` and additionally assert `deployable?` flips to `true` for the downstream `soc_third`-equivalent commit in `victim_stack`, even though no webhook naming `victim/app` was ever sent.
6. Assert `Status.where(stack_id: victim_stack.id, ...)` now contains a row whose creation was authenticated only by the attacker's org secret, demonstrating the cross-repository write.
