### Title
Unbounded growth of `latest_votes` (and upstream `LatestValidatorVotesForFrozenBanks` maps) via unlimited attacker-created vote-account pubkeys - ([File: core/src/consensus/heaviest_subtree_fork_choice.rs])

### Summary
`HeaviestSubtreeForkChoice::latest_votes: HashMap<Pubkey, SlotHashKey>` gains one permanent entry per distinct vote-account pubkey that has ever cast a vote, and nothing in `heaviest_subtree_fork_choice.rs` (or the upstream `LatestValidatorVotesForFrozenBanks` in `core/src/consensus/latest_validator_votes_for_frozen_banks.rs`) ever removes an entry once inserted, even when the pubkey has zero stake. An attacker who repeatedly creates fresh, minimally-funded vote accounts and casts a Vote instruction from each can grow this map without bound, purely by paying rent/fees for vote-account creation and vote transactions.

### Finding Description
In `generate_update_operations` (core/src/consensus/heaviest_subtree_fork_choice.rs:1010-1069), every incoming `(pubkey, new_vote_slot_hash)` pair is unconditionally inserted into `self.latest_votes` via `self.latest_votes.insert(*pubkey, *new_vote_slot_hash)` at line 1036. The `stake_update` value computed afterward (lines 1050-1068) is only used to decide whether to emit a `Subtract`/`Add` tree-weight `UpdateOperation` — a zero-stake pubkey still gets its entry inserted/kept in `latest_votes`; there is no `retain`, eviction, or stake/epoch-based cleanup anywhere else in this file for `latest_votes`.

Feeding this map is `LatestValidatorVotesForFrozenBanks::check_add_vote` (core/src/consensus/latest_validator_votes_for_frozen_banks.rs:22-95), which inserts into `max_gossip_frozen_votes` / `max_replay_frozen_votes` via `vote_map.entry(vote_pubkey)` with no stake check at all, and the struct itself carries an explicit acknowledgment of this gap: `// TODO: Clean outdated/unstaked pubkeys from this list.` (core/src/consensus/latest_validator_votes_for_frozen_banks.rs:11). Votes reaching this code originate from normal transaction replay/gossip observation of the vote program's `Vote` instruction; the vote program itself does not require the voting vote-account to have any delegated stake to process a valid `Vote` instruction — stake only affects consensus weighting, not instruction validity. Thus an unprivileged attacker can:
1. `CreateAccount` + vote-program `InitializeAccount` for a fresh throwaway vote pubkey (paying only rent-exempt minimum).
2. Submit a `Vote` instruction signed by themselves as authorized voter.
3. Close/withdraw and repeat with a new pubkey.

Each iteration adds a permanent entry to `latest_votes` (and to `max_gossip_frozen_votes`/`max_replay_frozen_votes`) that is never evicted, regardless of the fact that the vote-account has no real, lasting stake.

### Impact Explanation
This is a real, code-confirmed unbounded-memory-growth defect: `latest_votes` and the frozen-vote-tracking maps accumulate one entry per unique attacker-controlled pubkey forever, with no cap, no stake-based eviction, and no epoch-boundary cleanup (unlike the analogous `VoteStorage` in `core/src/banking_stage/vote_storage.rs`, which does implement `cache_epoch_boundary_info` retain-based eviction of unstaked/stale entries — showing the fork-choice path lacks the equivalent safeguard). Per-call processing cost is bounded (only the dirty-set of new votes is iterated in `generate_update_operations`), so this is not a per-call CPU blowup, but the persistent map size grows monotonically with attacker-created accounts across the life of the validator process, which is a legitimate resource-exhaustion/availability concern rather than a one-shot halt.

### Likelihood Explanation
Fully attacker-reachable with no elevated privilege: creating vote accounts and submitting `Vote` instructions from self-authorized voters is a normal, permissionless flow (system + vote program instructions only). The only cost is the rent-exempt minimum per vote account and standard transaction fees, both recoverable/cheap relative to the persistent state growth achieved, and repeatable indefinitely across epochs.

### Recommendation
Add stake/epoch-based eviction for `latest_votes` in `HeaviestSubtreeForkChoice` (e.g., at epoch boundaries, `retain` entries whose pubkey still has stake in the current/previous epoch's `epoch_stakes`, mirroring `VoteStorage::cache_epoch_boundary_info`'s `retain` in `core/src/banking_stage/vote_storage.rs:195-218`), and similarly implement the already-noted `// TODO: Clean outdated/unstaked pubkeys from this list.` in `LatestValidatorVotesForFrozenBanks`.

### Proof of Concept
Rust unit test plan (extending existing tests in `core/src/consensus/heaviest_subtree_fork_choice.rs`, e.g. near `test_add_votes_duplicate_zero_stake`):
```rust
#[test]
fn test_latest_votes_unbounded_zero_stake_growth() {
    let mut heaviest_subtree_fork_choice = setup_forks();
    let stake = 0; // simulate attacker vote accounts with no real stake
    let num_validators = 10_000; // simulate churned throwaway vote pubkeys
    let (bank, vote_pubkeys) =
        bank_utils::setup_bank_and_vote_pubkeys_for_tests(num_validators, stake);

    for &pk in &vote_pubkeys {
        heaviest_subtree_fork_choice.add_votes(
            [(pk, (1, Hash::default()))].iter(),
            bank.epoch_stakes_map(),
            bank.epoch_schedule(),
        );
    }

    // EXPECTED (if bounded): latest_votes.len() should be capped by real
    // active/staked vote-account set size (0 here, since stake == 0).
    // ACTUAL: latest_votes.len() == num_validators, proving unbounded growth
    // tied 1:1 to attacker-created pubkeys regardless of stake.
    assert_eq!(heaviest_subtree_fork_choice.latest_votes.len(), num_validators);
}
```
Extend this to loop across simulated epoch boundaries (calling `add_votes` with fresh `vote_pubkeys` batches per "epoch") and assert `latest_votes.len()` keeps growing linearly with cumulative attacker pubkeys rather than being bounded by `bank.epoch_stakes_map()`'s actual staked-vote-account count, demonstrating the missing eviction invariant.
