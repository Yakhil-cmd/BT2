### Title
Interest-rate index cache primed by one user's transient utilization spike is blindly trusted by every other user's transaction in the same block - ([File: mainnet/contracts/market/v0-4-market.clar], [File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
The externally reported vulnerability describes a validator (`EcdsaPreSignerImpl::validate_dealing_support`) that accepts a signed value without checking it against the original data it is supposed to attest to, letting one participant poison a value that is later blindly consumed to the detriment of other participants. Zest's vault/market interest-index caching system exhibits the same structural flaw: `market.clar`'s `index-cache` (and the underlying vault `index`/`lindex` state variables) are computed once per block from *whatever utilization happens to exist at the moment of the first accrual call*, are never re-validated, and are then reused verbatim by every subsequent, unrelated user transaction in that same block.

### Finding Description
Each vault (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, etc.) computes its new borrow/liquidity index from the *instantaneous* utilization ratio at call time: [1](#0-0) 

`utilization()` reads live `get-available-assets`/`total-debt`, `interest-rate()` interpolates a rate from that utilization, and `next-index`/`next-liquidity-index` apply that rate over the entire `time-delta` since `last-update` (which can be many blocks/seconds). The result is then permanently committed to vault state the first time `accrue` is invoked in a block: [2](#0-1) 

`market.clar` additionally memoizes this per-block result in a shared map keyed only by `{timestamp, aid}` — i.e., shared by every account and every transaction in the block, not scoped to the caller: [3](#0-2) [4](#0-3) 

This `accrue-and-cache` result is consumed, without any re-check, by every other user's `borrow`, `collateral-add`, `repay`, and notional-valuation logic that executes later in the same block: [5](#0-4) [6](#0-5) 

Exactly like the IC report's dealing-support flow — where a receiver could rewrite `internal_dealing_raw`/`requested_height` before signing, and downstream consumers (`build_transcript`) trusted the signed payload without checking it against the original dealing — here the *first* transaction to touch a given vault in a block determines the `index`/`lindex` that is cached and reused, and nothing checks that this value corresponds to the vault's "real"/steady-state utilization rather than a value the caller transiently engineered (e.g., a large same-block deposit that temporarily depresses utilization, immediately followed/preceded by a withdrawal) right before triggering accrual.

### Impact Explanation
An attacker who transiently manipulates utilization (via ordinary deposit/redeem calls, no flashloan needed since flashloans are whitelist-only and out of scope) immediately before being the first caller to trigger `accrue`/`accrue-and-cache` in a block can lock in an artificially low or high borrow/liquidity index for the *entire elapsed time-delta* since `last-update`. Because the cache is keyed only by `{timestamp, aid}` and not by caller, every other unrelated user (victims) whose transaction lands later in the same block — borrowing, repaying, adding/removing collateral, or being evaluated for health/liquidation — has their debt and collateral notional values computed from this manipulated, un-revalidated index. This can understate a victim's debt (blocking a legitimate liquidation, a form of temporary freezing of protocol funds/insolvency risk) or overstate it (pushing a healthy victim below their egroup LTV threshold and exposing them to improper liquidation, i.e., theft of collateral belonging to a user who did nothing wrong). Either outcome is caused entirely by the attacker's transaction and directly harms a third-party victim, matching the report's "signed but unvalidated content blindly consumed downstream" bug class.

### Likelihood Explanation
The attack requires the attacker to have enough capital to meaningfully move utilization for a single vault and to be able to order/schedule their transaction ahead of the accrual-triggering call in the same block (transaction ordering within a Stacks block is influenced by nonce/fee, which is realistic for a motivated attacker). No privileged role, oracle compromise, or DAO action is required — only ordinary user-facing entry points (`deposit`, `redeem`, `borrow`) are used.

### Recommendation
Do not let a single, unauthenticated instant-in-time utilization sample determine the index applied over the full elapsed `time-delta`. Either (a) validate/bound the per-call interest rate change against a time-weighted or checkpointed utilization rather than the spot value at the moment of the triggering call, or (b) scope the `index-cache` result to a maximum permissible index deviation and re-derive/re-verify it against the vault's actual committed `index`/`lindex` (analogous to checking a signed dealing's hash against the original dealing) before letting other users' transactions consume it.

### Proof of Concept
1. Vault V has not been touched for a long `time-delta` (e.g., since the previous day), so `last-update` is stale.
2. Attacker, in the same block, first calls `deposit` with a large amount into vault V, dropping `utilization()` sharply.
3. Attacker (or anyone) triggers a market operation (e.g., a tiny `borrow`/`repay`) that calls `accrue-and-cache`, which calls the vault's `accrue`. `next-index`/`next-liquidity-index` compute a very low rate (because utilization is artificially low) applied across the entire stale `time-delta`, and this index is permanently committed to vault state and cached in `market.clar`'s `index-cache` for the block.
4. Attacker immediately `redeem`s their deposit back out in the same block, restoring true utilization — but the cached/committed index for the block does not change.
5. Victims transacting later in the same block (`borrow`, `repay`, `collateral-add`, liquidation checks) all read the manipulated cached index via `get-cached-indexes`/`accrue-and-cache`, understating their true debt growth or otherwise skewing their health calculations relative to the vault's real state, to the attacker's benefit and the victims'/protocol's detriment.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
