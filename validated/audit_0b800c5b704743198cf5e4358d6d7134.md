### Title
Webhook signature verification is bound to `repository.owner.login`, not to the repository actually written — allows cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `repository.owner.login` (or `organization.login`) pulled from the *same untrusted JSON body* it is about to verify. Every webhook `Handler` then independently determines which `Stack`/`Repository` to mutate using a *different* field of that same body: `repository.full_name` (see `Handler#repository_name`). Because nothing ties `repository.owner.login` to `repository.full_name`, an attacker who legitimately controls one GitHub organization configured in this Shipit instance (and therefore knows that organization's `webhook_secret`) can forge a payload whose `repository.owner.login` matches their own org (so signature verification succeeds) while `repository.full_name` names a completely different organization's tracked repository. The write target is bound to a field the signature never actually authenticates for that target.

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and uses it purely to pick which configured GitHub App's `webhook_secret` to validate the raw body's `X-Hub-Signature` against:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [2](#0-1) 

Every concrete handler, however, resolves the actual stack/repository to act on from a *separate* JSON field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler`, for example, uses this to trigger a sync using an attacker-controlled `after` SHA:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 

Similarly, pull-request handlers resolve the target repository independently via `params.repository.full_name`, unrelated to whatever organization the signature check used: [5](#0-4) [6](#0-5) 

Because the whole raw body (containing both `repository.owner.login` and `repository.full_name`) is attacker-authored before signing, and the signature-selection field and the action-target field are never cross-checked, the equality the code implicitly assumes — `verified_organization == repository_actually_written.organization` — does not hold. An attacker who administers "OrgA" (and thus legitimately knows OrgA's `webhook_secret`, configurable per the multi-org support shown in `test/dummy/config/secrets_double_github_app.yml`) can:
1. Build a `push` (or `pull_request`) payload with `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/victim-repo"`.
2. Sign it with OrgA's `webhook_secret`.
3. POST it to the shared `/webhooks` endpoint.

`verify_signature` passes (OrgA's secret matches), but the handler acts on `OrgB/victim-repo` — a repository/stack that belongs to a completely different, unrelated GitHub organization/installation.

### Impact Explanation
This breaks the authentication boundary the webhook signature is meant to provide: possession of a valid secret for *any one* configured organization is sufficient to make Shipit act as if it received a trusted event for *any other tracked organization's repository*. Concretely this enables:
- Forcing `Stack#sync_github` with an attacker-chosen `expected_head_sha` against a victim repository/stack the attacker does not control, via `PushHandler`.
- Injecting/altering pull-request state (`github_pull_request=`) for a victim's pull requests via `AssignedHandler`/`EditedHandler`/`OpenedHandler`, all of which resolve their target purely from `repository.full_name`.
- Any handler built on `Handlers::Handler#stacks`/`#repository_name` inherits the same decoupling, so the blast radius spans push, pull_request, and other repository-scoped events.

Given that stack state feeds continuous deployment (`Stack.schedule_continuous_delivery`), merge-queue processing, and pull-request auto-provisioning, this cross-tenant write capability can influence deploy/merge decisions for repositories outside the attacker's own organization — matching the "cross-repository writes" / unauthorized deploy/merge impact class.

### Likelihood Explanation
Exploitability requires only that the attacker legitimately control the webhook secret of *one* organization configured on the shared Shipit instance (a normal, unprivileged position for any organization admin who installed Shipit's GitHub App on their own org) — no access to the victim organization, no Shipit session, and no `ApiClient` token is required. This is realistic for any multi-tenant Shipit deployment tracking more than one GitHub organization, which the engine explicitly supports (`Shipit.github_apps`, `test/dummy/config/secrets_double_github_app.yml`).

### Recommendation
In `Handlers::Handler` (and `WebhooksController#verify_signature`), require that `repository.full_name`'s owner segment (or `organization.login`) match the organization whose secret validated the signature, and reject the webhook otherwise. Do not let handlers independently re-derive the write target from an unauthenticated-relative-to-signature field; instead pass the verified organization through to handlers and scope all repository/stack lookups by it.

### Proof of Concept
1. Configure Shipit to track two GitHub orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker with legitimate knowledge of `OrgA`'s `webhook_secret` (e.g., an OrgA admin), craft a `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>`.
4. POST to the Shipit webhooks endpoint with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, validates successfully against OrgA's secret [2](#0-1) .
6. `PushHandler#process` resolves `stacks` from `repository.full_name` = `"OrgB/victim-repo"` [4](#0-3)  and triggers `sync_github(expected_head_sha: "deadbeef...")` on OrgB's stack — despite the request never being authenticated by OrgB.
