### Title
`Commit.where(sha:)` in `StatusHandler#process` is not scoped to the webhook's originating repository, allowing a fork's status webhook to mutate CI state of an unrelated stack sharing the same commit sha - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no comparison to `params.repository.full_name`, so any `Commit` row in the database with a matching sha—regardless of which stack/repository it belongs to—receives `create_status_from_github!`. Because git commit shas are content-addressed and identical between a repository and any of its forks, an attacker who owns a fork of a victim's public repo can send a webhook (signed with a valid app installation on their own fork) for a shared sha and flip Status state on the victim's `Commit` row too, as long as such a row exists in Shipit's `commits` table for that sha under a different stack.

### Finding Description
The broken binding is: `Commit.where(sha: params.sha).stack.repository.full_name == params.repository.full_name` for every row touched by the loop — this equality is never asserted anywhere in the code path.

`WebhooksController#create` parses the JSON, verifies the HMAC signature via `Shipit.github(organization: repository_owner).verify_webhook_signature`, then dispatches to `Shipit::Webhooks.for_event(event)` handlers [1](#0-0) . Signature verification is scoped to the *organization* the payload claims to belong to (`repository_owner`), fetched via `Shipit.github(organization:)` [2](#0-1) [3](#0-2) . This only proves the webhook was legitimately signed for *that organization's* configured secret; it says nothing about which `Commit`/`Stack` rows should be affected. `StatusHandler#process` then does:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

No filter restricts the query to commits whose `stack.repository` matches `params.repository`. If the same sha exists as separate `Commit` rows for two different stacks (victim's upstream repo and attacker's fork — plausible since forks share history and Shipit can end up importing/tracking both, e.g. via review-stack/PR sync flows that record fork commits verbatim), both rows get `create_status_from_github!` called, which writes a new `Status` and can flip the commit's deployability/CI state via `add_status` and `schedule_continuous_delivery` [5](#0-4) [6](#0-5) .

**Attacker's exact request**: an unprivileged attacker forks the victim's public repo (no code changes, so shas are byte-identical), has a GitHub App installation on their own account/fork, and triggers (or crafts) a `status` webhook event with `sha=<shared_sha>`, `state=success`, and `repository.full_name=attacker/fork`. This webhook is signed with the attacker-org's own legitimately configured webhook secret (their own installation), so `verify_webhook_signature` passes cleanly for their own organization — the signature check was never meant to, and does not, assert that the sha or resulting `Commit` rows belong to that organization's repository.

**Why existing guards fail**: `verify_signature` only authenticates "this payload came from a legitimately configured GitHub App installation for organization X"; it does not authenticate "this payload's sha/commit belongs to organization X's repository." The `ExplicitParameters` schema in `StatusHandler` only validates the shape of `sha`/`state`/etc., not repository ownership [7](#0-6) . No model validation or scope narrows `Commit.where(sha:)` to a repository.

### Impact Explanation
An attacker can write a `Status` record (and, transitively, alter `deployable?`/`blocked?` computations and trigger `schedule_continuous_delivery`) for a `Commit` belonging to a stack/repository they did not authenticate for and do not control, purely by controlling their own fork's webhook delivery. This matches the "payload for one repository mutating another's stack/commit" Critical category: a party with no privileges on the victim's Shipit stack can flip CI status to `success` on the victim's commit, potentially unblocking an otherwise-blocked deploy/merge that depends on required statuses. This is repeatable for every sha that happens to exist as tracked `Commit` rows in both the victim's and attacker's stacks (any commit predating the fork, or any commit cherry-picked/rebased identically).

### Likelihood Explanation
Exploitability depends entirely on Shipit actually having created two separate `Commit` rows sharing the identical sha under two different stacks — one being the attacker's own fork stack and one the victim's. This is the precondition stated in the prompt (review-stack/PR-sync flows importing fork commits verbatim) but I could not verify, from the available indexed code, that Shipit's github-sync/review-stack import path actually creates `Commit` rows for fork repositories under the victim's stack, or that a fork's own repository would independently be configured as a Shipit-tracked stack with its own GitHub App installation capable of sending signed webhooks. If forks are never onboarded as Shipit stacks (i.e., `Shipit.github(organization:)` would raise `GithubOrganizationUnknown` for an attacker-owned fork/org not present in `secrets.github`), the attacker cannot pass `verify_signature` at all, closing this off entirely. Given this significant unverified precondition, likelihood is uncertain rather than confirmed — but the code-level lack of repository scoping in the query itself is a genuine, verifiable root cause independent of that precondition.

### Recommendation
Scope the lookup in `StatusHandler#process` to the reporting repository, e.g. join through `stack.repository` and filter by `params.repository.full_name` (and ideally also `owner`/`id`) before calling `create_status_from_github!`, rejecting or ignoring commits whose stack's repository does not match the webhook's `repository` payload.

### Proof of Concept
```ruby
test "status webhook for a shared sha does not update commits belonging to a different repository" do
  victim_stack = shipit_stacks(:shipit)
  fork_stack = Shipit::Stack.create!(
    repository: Shipit::Repository.create!(owner: 'attacker', name: 'fork'),
    environment: 'production'
  )

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared commit')
  fork_commit = fork_stack.commits.create!(sha: shared_sha, message: 'shared commit')

  payload = Shipit::Webhooks::Handlers::StatusHandler.new(
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/fork', 'owner' => { 'login' => 'attacker' } }
  )
  payload.process

  # Assert: victim_stack.repository.full_name != 'attacker/fork', so victim_commit
  # should NOT receive a Status row from this webhook.
  assert_equal 0, victim_commit.reload.statuses.count
  assert_equal 1, fork_commit.reload.statuses.count
end
```
Note: this test requires confirming (via a Devin session with full repo/test access) that two `Commit` rows with an identical sha across different stacks is a reachable state in this codebase's github-sync/review-stack import logic, which I was unable to fully verify from the indexed context alone.
