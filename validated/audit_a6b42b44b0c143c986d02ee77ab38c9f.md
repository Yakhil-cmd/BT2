This confirms the multi-org config: `Shipit.github(organization:)` looks up `secrets.github[organization.downcase]` and each org has its own independent `webhook_secret` [1](#0-0) . This is the mechanism that lets a legitimate, unprivileged owner of a *different* registered organization ("attacker-org") sign a webhook body with their own valid secret while targeting another org's `team.id`.

### Title
Cross-organization Team/Membership mutation via unchecked `organization.login` vs `team.id` binding in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the signing organization's secret solely from `params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1) , but `MembershipHandler#find_or_create_team!` locates the target `Team` solely by `params.team.id` and never verifies that `team.organization == params.organization.login` [3](#0-2) . In a multi-tenant Shipit deployment (multiple orgs configured under `secrets.github`, each with its own `webhook_secret`), an organization owner can send a validly-signed `membership` webhook naming their own org in the top-level `organization.login` field while pointing `team.id` at a *different* org's team, causing `team.add_member`/`team.members.delete` to mutate that other org's `Membership` records.

### Finding Description
The broken binding is: **organization whose `webhook_secret` verified the request body == organization owning the `Team` referenced by `team.id`**. This should always hold but does not.

Trace:
1. `verify_signature` picks `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` reads only `repository.owner.login`/`organization.login` from the JSON body [4](#0-3) . It verifies the HMAC using that specific organization's `webhook_secret` [5](#0-4) .
2. Once signature verification passes, the handler dispatch (`Shipit::Webhooks.for_event('membership')`) invokes `MembershipHandler` on the raw parsed body without re-checking which organization was actually used to authenticate [6](#0-5) .
3. `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id)`, keyed purely on the numeric team ID, with `team.organization = params.organization.login` only applied inside the creation block (i.e., only on first creation of that `github_id`) [3](#0-2) . For any team that already exists in the database (the common case for a real, already-provisioned org team), the lookup returns the existing record and its `organization` column is left untouched — but the handler still executes `team.add_member(member)` / `team.members.delete(member)` against that pre-existing team, regardless of who authenticated the request [7](#0-6) .

Attacker request: An entity that owns/administers "attacker-org" — a second organization independently configured in Shipit's `secrets.github` with its own `webhook_secret` (a legitimate but distinct tenant, not a Shipit operator or maintainer of the target org) — sends `X-Github-Event: membership` with body `{"action":"added","organization":{"login":"attacker-org"},"team":{"id":<victim-team-github-id>, ...},"member":{"login":"attacker-controlled-login"},"repository":{"owner":{"login":"attacker-org"}}}`, signed with `attacker-org`'s own valid `webhook_secret`. `verify_signature` resolves and validates against `attacker-org`'s secret and passes. `MembershipHandler` then finds the victim org's pre-existing `Team` by `github_id` and appends the attacker-controlled user as a member of that team, or removes an existing member.

Existing guards do not catch this: `verify_signature`/`GithubApp#verify_webhook_signature` only prove *some* registered org's secret matches — not that the org matches the mutated resource's owner [5](#0-4) ; `ExplicitParameters` schema in `MembershipHandler.params` only enforces types/presence, not cross-field consistency [8](#0-7) ; and there is no `require_permission!`/session check on this unauthenticated webhook endpoint by design.

### Impact Explanation
Team membership feeds directly into authorization: `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [9](#0-8) , and `Shipit.github_teams` is derived from `Team` records configured via `github.oauth.teams` [10](#0-9) . If the victim team happens to be one of the `oauth.teams` gating access to the Shipit instance, an attacker who controls a separate registered org's webhook secret can grant an arbitrary GitHub login membership in that authorization-gating team, which — once that user authenticates via GitHub OAuth and a matching `User` record exists/gets created — escalates them into `Shipit.github_teams` authorization for the victim's Shipit instance. This matches the "High" severity category ("escalation into `Shipit.github_teams` authorization"). It is repeatable against any team whose numeric `github_id` is known or guessable, across any tenant configured in the same multi-org Shipit deployment.

### Likelihood Explanation
This requires a **multi-organization Shipit deployment** (`secrets.github` keyed by multiple orgs, each with independent `webhook_secret`, per `github_app_config`) [1](#0-0) . The attacker must control (own/administer) at least one such registered organization and thus know its own legitimate `webhook_secret`, then must know or guess the target team's numeric GitHub `github_id`. Team IDs are visible via GitHub's public/authenticated team API for teams the attacker can view, or via prior legitimate webhook deliveries. Given those preconditions, the attack is a single unauthenticated HTTP POST to `/webhooks`, fully repeatable and requires no Shipit session or Shipit-side secret beyond the attacker's own org's secret.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that `params.organization.login.downcase == team.organization.downcase` before mutating membership; reject (raise/drop) the event if they diverge. Additionally, `verify_signature` should bind the accepted event to the team's organization column (not the request body's own claimed org), e.g., pre-fetching the `Team` by `github_id` and re-validating that the request's authenticated organization matches `team.organization` prior to invoking `add_member`/`delete`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":membership cannot mutate a team belonging to a different organization" do
  victim_team = shipit_teams(:shopify_developers) # organization == 'shopify'
  @request.headers['X-Github-Event'] = 'membership'

  # Attacker authenticates with their OWN org's ('attacker-org') valid webhook secret,
  # but targets the victim's pre-existing team by github_id.
  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  body = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker-controlled-login' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  assert_difference -> { victim_team.reload.members.count }, 1 do
    post :create, body:, as: :json
    assert_response :ok
  end

  # Binding check: the org that authenticated ('attacker-org') != the org owning the mutated team ('shopify')
  refute_equal 'attacker-org', victim_team.organization
  assert_equal 'shopify', victim_team.organization
  assert_includes victim_team.members.map(&:login), 'attacker-controlled-login'
end
```
This demonstrates the divergence: signature verification succeeds against `attacker-org`'s secret while the mutated `Team`'s `organization` (`shopify`) remains different, proving the binding `verifying_org == team.organization` is broken.
