Confirmed: `system_vote_count` for `op_list` can be triggered by *any* unprivileged unit poster (only AAs are barred — `validation.js:1916-1917`), and the actual weight of every existing vote is recomputed from **live** balances at the moment the triggering unit stabilizes, not from balances held at (or since) the time the vote was cast.

### Title
Op-list (validator/witness) consensus takeover via instantaneous balance inflation at vote-count time - ([File: main_chain.js])

### Summary
`countVotes()` determines the winning `op_list` (the 12 Order Providers that anchor DAG stability, analogous to Shibarium's validator set) by summing the **current** stable-good byte balance of every address that has ever cast a `system_vote` for `op_list`, and picking the 12 candidates with the highest total voted balance. Because the balance is read fresh at count time rather than pinned to the time the vote was submitted or held over a lock-up period, any unprivileged unit poster can inflate their own balance for a moment, have a `system_vote_count` unit stabilize while the balance is inflated, and thereby buy outsized influence over the OP list — the same "acquire majority control for an instant, use it, then walk away" pattern that let the Shibarium attacker rent 4.6M BONE via flash loan to sign fraudulent validator checkpoints.

### Finding Description
`system_vote` (validation.js:1844-1883) lets any non-AA address register a vote for a full 12-address `op_list`. `system_vote_count` (validation.js:1913-1923) lets any non-AA address trigger the counting of votes for a subject — anyone, not just a voter, can post it. When a unit carrying `system_vote_count` for `op_list` stabilizes, `main_chain.js` calls `countVotes(conn, mci, 'op_list')`: [1](#0-0) 

The balance query sums `outputs.amount` for every address that ever appears in `system_votes` for the subject, filtered only by `is_stable=1 AND sequence='good'` at the moment of counting — i.e., "how much do you hold right now", not "how much did you hold when you voted" or "how much have you held continuously": [2](#0-1) 

The OP candidates are then ranked purely by this instantaneous `voter_balances` sum and the top `COUNT_WITNESSES` (12) become the new consensus OP list, permanently written to `system_vars` and broadcast to all nodes, which then swap their local witness lists accordingly: [3](#0-2) [4](#0-3) 

There is no mechanism requiring the voting balance to be locked, staked, or held for any minimum duration before or after the vote — only a lookback window (`since_timestamp`) on *when the vote itself was cast*, not on when the funds backing that vote's weight were acquired (main_chain.js:1807-1821). The `SYSTEM_VOTE_MIN_SHARE` quorum check similarly only measures whatever balance currently sits in the voting addresses, so it can be satisfied the same way it is exploited.

### Impact Explanation
The OP list determines the witnesses/order-providers used throughout `main_chain.js` and `storage.js` for `MAJORITY_OF_WITNESSES`-based stability determination (`updateStableMcFlag`, `determineIfStableInLaterUnits`, `findMinMcWitnessedLevel`). Just as compromising 10/12 Shibarium validator keys let the attacker forge a fraudulent bridge checkpoint, capturing a majority of the 12 OP seats lets an attacker:
- Control DAG stabilization and finality (author units that get treated as majority-witnessed), enabling double-spend-like disagreement between honest and attacker-influenced nodes on which units/balls are stable.
- Indirectly steer future protocol parameter votes (`threshold_size`, fee params) that ride the same `countVotes` mechanism.
- This is a network-wide, irreversible consensus-set change triggered from a single posted unit — not an operator/node compromise, but a protocol-level economic design flaw reachable by an ordinary unit poster.

Severity: High — a successful takeover of the OP list is a fundamental compromise of network consensus/stability guarantees, matching the "node disagreement on validity or stability" acceptance criterion.

### Likelihood Explanation
Exploitability depends on how easily an attacker can transiently inflate their own address's *stable* balance right before a `system_vote_count` unit stabilizes and drain it right after. Since ocore uses a DAG with `MAJORITY_OF_WITNESSES`-based stabilization delay rather than single-block finality, "instantaneous" here means "held long enough to become stable," which requires some capital lock-up (unlike Ronin/Shibarium's same-block flash loan). This raises the capital/timing cost compared to the EVM flash-loan case, but the underlying vulnerability class — vote weight computed from momentary balance rather than committed stake — is identical, and no additional privilege beyond posting a normal payment + `system_vote`/`system_vote_count` unit is required. I could not fully verify from the indexed code whether any additional stabilization-timing constraints (e.g., how quickly a large payment plus a vote-count unit can jointly stabilize) further reduce or amplify practical exploitability, since that depends on live network conditions (number of other posters, witness cooperation) not visible in static code.

### Recommendation
- Snapshot and lock the balance used for vote weighting at the time the `system_vote` is cast (or use a time-weighted / minimum-holding-period balance) instead of re-reading the live balance at `countVotes` time.
- Consider requiring voting balance to remain stable/unspent for a minimum age (analogous to `EMERGENCY_COUNT_MIN_VOTE_AGE` already used for unstable emergency votes) before it can count toward `op_list` weight.
- Add rate limiting / cooldown on how quickly a single address's voted balance can change between the vote and the count.

### Proof of Concept
1. Attacker address `A` casts a `system_vote` for `op_list` naming 12 addresses it controls (or a minority set to reach 8-of-12 majority when combined with existing votes), paying minimal fee.
2. Attacker acquires a large temporary byte balance into `A` (via payment(s) from another address/exchange) and waits for those outputs to become `is_stable=1, sequence='good'`.
3. Attacker (or anyone) posts a unit containing `system_vote_count` for `op_list`.
4. When that unit stabilizes, `countVotes()` (main_chain.js:1741-1871) sums `A`'s current large balance, ranks candidates, and — if this pushes attacker-controlled addresses into the top 12 — commits the new `op_list` to `system_vars`, changing the network's consensus witness set.
5. Attacker moves the funds out of `A` immediately afterward; the OP list change persists regardless.
