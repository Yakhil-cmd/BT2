### Title
Deterministic account IDs are network-agnostic, enabling cross-network address squatting/replay of `DeterministicStateInit` - (File: `core/primitives/src/utils.rs`)

### Summary
NEAR's NEP-616 "deterministic accounts" derive an account ID purely from a hash of the `DeterministicAccountStateInit` (contract code identifier + initial key/value data), with no network-specific salt (no chain ID / genesis hash / network ID). This is the exact bug class described in the report: a CREATE2-style deterministic address that is identical across all deployments/networks, enabling an attacker to pre-empt or hijack the address on a different network than the one the user intended, analogous to the Wintermute Gnosis Safe incident cited in the report.

### Finding Description
The deterministic account ID is computed as: [1](#0-0) 

i.e. `0s` + `keccak256(borsh(state_init))[12:32]`, where `state_init` only contains `code` (a `GlobalContractIdentifier`) and `data` (arbitrary key/value pairs) [2](#0-1) . There is no chain-specific component (no genesis hash, no `chain_id`, no network identifier) mixed into this hash, unlike, for example, the ETH wallet contract's global-contract-hash derivation which explicitly incorporates `chain_id`: `eth_wallet_global_contract_hash(&chain_id)` used during implicit account creation [3](#0-2) .

When a `DeterministicStateInit` action is submitted, the runtime strictly enforces that the receiver account ID must equal the address derived from the `state_init` content: [4](#0-3) 

Because this derivation is a pure function of `state_init` (code + data) and never of any network-distinguishing value, the same `state_init` produces the exact same account address on every NEAR network (mainnet, testnet, any future fork, or any other deployment sharing the same protocol). The `create_deterministic_account`/`action_deterministic_state_init`/`deploy_deterministic_account` flow that initializes state on first use is likewise network-agnostic [5](#0-4) [6](#0-5) .

### Impact Explanation
This mirrors the CREATE2 cross-chain replay/hijack pattern from the report: if a user (or a wallet/tooling flow) computes a deterministic account address off-chain for a given `state_init` and mistakenly funds/interacts with that address on the wrong NEAR network (e.g., sends a transfer or expects a specific access-controlled deterministic account to exist there), an attacker who is watching can be the first to submit the matching `DeterministicStateInitAction` with **different** state data (different code/owner data) on that network — since account creation for a not-yet-`uninit`→`active` account is not restricted to the originally-intended party, only to whoever first submits a valid `DeterministicStateInit` receipt for that derived ID. Because the initial `actor_id` for this transition is deliberately left as the *predecessor*, not the account itself (comment: "Unlike `CreateAccount`, this account creation does not change actor_id... to prevent hijacking"), the protection is against actor/permission hijack within one chain, but it does nothing to prevent a different party from being first to initialize the state on a different, unintended network where the same address is reachable — funds sent there by mistake (or by any cross-network assumption in wallets/bridges/tooling) can end up controlled by attacker-supplied code/data rather than the legitimate owner's intended state, i.e. unauthorized control over account state/funds is possible.

### Likelihood Explanation
Likelihood depends on external factors (multiple live NEAR networks/forks and users or tooling reusing state-init payloads/addresses across networks), similar to how the original report's issue was rated Medium and disputed on the grounds that only one network was in use at the time. Given NEP-616 deterministic accounts are a newer primitive intended to be composable/portable (their whole purpose is deterministic reproducibility of an address from data), and given NEAR already runs multiple long-lived networks (mainnet, testnet) plus potential future forks, this is a realistic but not certain-to-be-hit scenario — it requires a workflow where the same `state_init` bytes are computed/used across two networks.

### Recommendation
Mix a network-distinguishing value (e.g. `chain_id`/genesis hash, as already done for `eth_wallet_global_contract_hash`) into the `derive_near_deterministic_account_id` hash input, so the same `state_init` produces different addresses on different NEAR networks, eliminating cross-network address collision/replay.

### Proof of Concept
Conceptual (following the code paths identified above):
1. Compute `state_init` (code identifier + data) and derive `account_id = derive_near_deterministic_account_id(&state_init)` — this is identical regardless of which NEAR network it is later submitted to, per `core/primitives/src/utils.rs:470-477`.
2. A user intends to submit `DeterministicStateInitAction` with this `state_init` on Network A but a transaction/transfer targeting `account_id` is instead broadcast/executed on Network B (wrong network, tooling mixup, or future chain fork).
3. An attacker monitoring Network B submits a `DeterministicStateInitAction` receipt to the same `account_id` with attacker-controlled `state_init` (different code/data) before the legitimate owner does; validation in `runtime/runtime/src/action_validation.rs:413-428` only checks that `derive_near_deterministic_account_id(state_init) == receiver_id`, which the attacker's crafted `state_init` satisfies by construction.
4. Since the account is `uninit` on Network B, `action_deterministic_state_init` (`runtime/runtime/src/deterministic_account_id.rs:15-48`) initializes it with the attacker's code/data, and any funds transferred to that address on Network B are now controlled per the attacker's initialized state.

/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let data = borsh::to_vec(&state_init).expect("borsh must not fail");
    let hash = sha3::Keccak256::digest(&data);
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}

pub(crate) fn action_deterministic_state_init(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    maybe_account: &mut Option<Account>,
    account_id: &AccountId,
    receipt: &Receipt,
    action: &DeterministicStateInitAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // See https://github.com/near/NEPs/blob/master/neps/nep-0616.md#account-state
    // for the detailed description around deterministic account state.
    let storage_usage_config = &apply_state.config.fees.storage_usage_config;
    let account = match maybe_account {
        Some(account) => account,
        None => {
            // cspell:ignore nonexist
            // `nonexist` -> `uninit` account state transition
            // Create with zero balance now and check later how much of the
            // provided deposit is needed.
            let new_account = create_deterministic_account(Balance::ZERO, storage_usage_config);
            maybe_account.insert(new_account)
        }
    };
    if account.contract().is_none() {
        // `uninit` -> `active` account state transition
        deploy_deterministic_account(
            state_update,
            account,
            account_id,
            &action.state_init,
            result,
            storage_usage_config,
        )?;
    }

fn deploy_deterministic_account(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    state_init: &DeterministicAccountStateInit,
    result: &mut ActionResult,
    storage_usage_config: &StorageUsageConfig,
) -> Result<(), RuntimeError> {
    // Step 1: set contract code (includes storage usage accounting)
    use_global_contract(state_update, account_id, account, state_init.code(), result)?;
    if result.result.is_err() {
        return Ok(());
    }

    // Step 2: insert provided key-value pairs
    let mut required_storage_usage = account.storage_usage();
    for (key, value) in state_init.data() {
        let trie_key = TrieKey::ContractData { account_id: account_id.clone(), key: key.to_vec() };

        let value_bytes = value.len() as u64;
        let key_bytes = key.len() as u64;
        let extra_per_record_bytes = storage_usage_config.num_extra_bytes_record;

        let new_bytes = value_bytes
            .checked_add(key_bytes)
            .and_then(|acc| acc.checked_add(extra_per_record_bytes))
            .ok_or(IntegerOverflowError {})?;
        state_update.set(trie_key, value.clone());
        required_storage_usage =
            required_storage_usage.checked_add(new_bytes).ok_or(IntegerOverflowError {})?;
    }
    account.set_storage_usage(required_storage_usage);

    Ok(())
}
