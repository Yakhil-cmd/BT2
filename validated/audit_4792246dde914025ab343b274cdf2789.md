### Title
Cross-Organization Commit Status Forgery via Webhook Signature/Scope Mismatch - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound GitHub webhook based solely on `repository_owner`, a field taken from the attacker-supplied payload itself. Once verified, `StatusHandler#process` writes the `state`/`context`/`target_url` fields straight into the database by looking up commits with a **global, unscoped** `Commit.where(sha: params.sha)` query — unlike every other handler in this engine (`PushHandler`, `CheckSuiteHandler`, the `PullRequest` handlers), which all scope their side effects through `stacks`/`repository.review_stacks` derived from `repository.full_name`. This breaks the equality that should hold between "the organization whose secret verified this webhook" and "the repository/stack whose data gets mutated."

### Finding Description
`Shipit::WebhooksController#verify_signature` resolves the GitHub App config (and thus the `webhook_secret` used for HMAC verification) using `repository_owner`, computed from the same untrusted JSON body: [1](#0-0) [2](#0-1) 

Because Shipit can be configured to serve multiple independent GitHub organizations, each with its own `webhook_secret` (as shown in the multi-org config), any organization that has *any* legitimately configured Shipit GitHub App can compute a valid `X-Hub-Signature` for a payload it fully controls: [3](#0-2) 

After signature verification passes, the event is dispatched to a handler. Every "real" mutation handler scopes its DB writes to the repository asserted in the payload, via `Repository.from_github_repo_name(repository_name)`: [4](#0-3) 

For example `PushHandler` and `CheckSuiteHandler` both filter through `stacks` (repository-scoped): [5](#0-4) [6](#0-5) 

However, `StatusHandler#process` does **not** scope through `stacks`/`repository_name` at all — it queries commits globally by SHA and writes attacker-supplied status fields directly: [7](#0-6) 

This is the same bug class as the external report: a value is validated/authorized in one context (here, "which org's secret verified this request") but a *different*, unbound field/entity ("which repository's commit gets written") is the one actually acted upon. The `sha` in the payload is entirely attacker-controlled and is never checked against the repository that authenticated the request.

### Impact Explanation
Any Shipit-hosted organization's webhook secret (an organization that only has legitimate access to its *own* repositories) can be used to forge a `status` event whose `sha` matches a commit belonging to a **completely different**, victim organization's stack that is also hosted on the same Shipit instance. Since `Commit#create_status_from_github!` writes the state/context directly from the forged payload, the attacker can inject an arbitrary "success" status for a required CI context (`ci.require` in `shipit.yml`) onto a victim's commit. If that context gates automatic merging or is used by an operator to decide "is this commit green, can I deploy/merge it," this results in bypassing CI/merge-queue requirements and can lead to an unauthorized deploy/merge of code that never actually passed the real CI check — satisfying the Critical "unauthorized deploy or merge" bar. This requires that the attacker know the target commit's SHA (obtainable via the public GitHub repo, or Shipit's own UI/permalinks, which are commonly public within an org), and that the target repository is hosted alongside the attacker's own organization on the same shared Shipit instance.

### Likelihood Explanation
Requires the attacker to control (i.e., have legitimate admin access to configure) a GitHub App/webhook for at least one organization/repository already registered on the shared Shipit instance — a bar significantly lower than compromising the victim's own repository or Shipit account. Multi-tenant Shipit deployments serving several organizations (as explicitly supported by `config/secrets.*.yml`) are the primary exposure. Discovering a target commit SHA is low-effort for public repositories.

### Recommendation
`StatusHandler` (and any other handler that doesn't already scope through `stacks`) must scope its commit lookup by the repository asserted in the payload (as `PushHandler`/`CheckSuiteHandler` do), and that repository must be cross-checked against the organization that verified the webhook signature (`repository_owner`), not merely trusted independently. Concretely, replace `Commit.where(sha: params.sha)` with a lookup scoped to `stacks` (i.e., commits belonging to stacks whose repository matches `repository_name`), and add a check in `WebhooksController#verify_signature` (or in `Handler`) asserting that `payload.dig('repository','full_name')`'s owner matches the `repository_owner` used to select the verifying secret.

### Proof of Concept
1. Shipit instance hosts two orgs: `attacker-org` (attacker has legitimate GitHub App admin access, knows its `webhook_secret`) and `victim-org` (unrelated, hosts a stack tracking commit `abcd123...`, with a `shipit.yml` `ci.require` context `"ci/tests"`).
2. Attacker crafts a JSON body:
```json
{
  "sha": "abcd123...",         // real commit SHA from victim-org's tracked repo
  "state": "success",
  "context": "ci/tests",
  "target_url": "http://attacker.example",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
3. Attacker signs the raw body with `attacker-org`'s own `webhook_secret` and sets `X-Hub-Signature`, `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature (it's the attacker's own secret). [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: "abcd123...")` — matching victim-org's commit — and calls `create_status_from_github!(params)`, writing a forged "success" `ci/tests` status onto the victim's commit, without ever checking that `abcd123...` belongs to a stack under `attacker-org`. [7](#0-6) 

*Note: I was unable to fully trace, within the remaining tool budget, whether Shipit's merge-queue automerge / deploy-gating logic (`ci.require`) directly consumes `Status` records without any additional GitHub API cross-check — this connection is based on the documented `ci.require` feature and the `Commit#create_status_from_github!` write path, but the exact merge-gating code path was not directly inspected in this session.*
