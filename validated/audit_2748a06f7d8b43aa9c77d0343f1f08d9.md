### Title
Membership webhook signature bypass for organizations with unset `webhook_secret` allows unauthenticated Team membership writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives the org used for signature verification from attacker-controlled JSON (`organization.login` when `repository` is absent), and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank. Combined with `MembershipHandler`, an attacker can fabricate a `membership` event naming any org configured without a `webhook_secret` and get a `Shipit::Membership` row created/removed with no valid GitHub signature at all.

### Finding Description
The intended binding is: `verified == true` should imply the request carries a valid HMAC-SHA1 signature computed with that organization's real `webhook_secret`, i.e. an authenticated GitHub origin. The actual code breaks this: in `verify_webhook_signature` [1](#0-0) , `return true unless webhook_secret` — if the configured org has no secret set, ANY payload (correct signature, wrong signature, or missing header) is accepted. The org selected for this check comes straight from the attacker-supplied JSON body via `repository_owner`, which falls back to `params.dig('organization', 'login')` when the payload has no `repository` key [2](#0-1) . `membership` events naturally have no `repository` key (they're org-scoped), so `MembershipHandler`'s required params schema (`organization.login`, `team`, `member`) [3](#0-2)  is satisfied purely by attacker input, and `process` calls `find_or_create_team!` and `team.add_member(member)` using only that untrusted `organization.login` and `member.login` [4](#0-3) , writing a `Membership` record with zero authenticated actor. Existing guards do not stop this: `drop_unhandled_event` only checks the event type is registered [5](#0-4) ; `verify_signature`'s only failure mode is `GithubOrganizationUnknown` (unrecognized org, raised elsewhere in `Shipit.github`), which does not apply if the named org is configured but merely lacks a `webhook_secret`.

### Impact Explanation
For any Shipit-configured GitHub organization whose `webhook_secret` is nil/blank (a real, documented but non-enforced configuration state — see `docs/setup.md` showing `webhook_secret` as a normal optional secrets.yml key), an unauthenticated attacker can POST a crafted `membership` webhook and cause `Shipit::Team`/`Shipit::Membership` rows to be created or deleted for that org, effectively injecting or removing members of a `Shipit.github_teams`-backed authorization group. Since Shipit teams gate `require_permission!`/`User#authorized?` checks used for deploy/merge authorization elsewhere in the app, this is an escalation into `Shipit.github_teams` authorization — a High-severity, tenant-crossing (per-organization) impact, repeatable at will as long as the target org's secret remains unset.

### Likelihood Explanation
The only precondition is operator misconfiguration: an org entry in Shipit's GitHub config without a `webhook_secret`. This is not enforced anywhere in the code (`@webhook_secret = @config[:webhook_secret].presence` at [6](#0-5)  silently allows blank), so it is a plausible real-world state (e.g., an org configured for read-only/legacy use, or a bug in secrets provisioning), not a theoretical one. Once that condition holds, the attacker's cost is a single unauthenticated HTTP POST to `/webhooks` with no secrets, tokens, or GitHub App credentials required, and the attack is fully repeatable.

### Recommendation
`GitHubApp#verify_webhook_signature` should never short-circuit to `true` when `webhook_secret` is absent; instead it should fail closed (return `false`/raise), and Shipit should require/validate that every configured organization intended to receive webhooks has a non-blank `webhook_secret` at boot or config-load time. Additionally, `WebhooksController#repository_owner`'s fallback to `params.dig('organization','login')` should not be trusted as the sole basis for both org resolution and downstream processing without independent verification of a valid signature tied to that exact org.

### Proof of Concept
Minitest plan (controller test, no live GitHub, mirrors existing style in `test/controllers/webhooks_controller_test.rb`):
```ruby
test "membership webhook with unset org secret is not authenticated but still writes a Membership" do
  # Binding under test: verified == true  ⇒  request had a valid org-specific HMAC signature.
  # Simulate an org configured with a blank/nil webhook_secret (a real allowed config state).
  Shipit.github(organization: 'victim').stubs(:webhook_secret).returns(nil)

  @request.headers['X-Github-Event'] = 'membership'
  # No X-Hub-Signature header at all -- attacker sends nothing.
  payload = {
    action: 'added',
    team: { id: 999, name: 'Fake Team', slug: 'fake-team', url: 'https://example.com' },
    organization: { login: 'victim' },
    member: { login: 'attacker' }
  }.to_json

  assert_difference -> { Shipit::Membership.count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end
  # Left side (verified) was true; right side (an authenticated GitHub org request) was false.
  # A Membership row was created with no valid signature -- binding violated.
end
```
This demonstrates `verified` returning `true` (request accepted, `head(422)` not triggered) purely because `webhook_secret` was blank, and `Shipit::Membership.count` incrementing as a direct consequence, with no HMAC signature or GitHub credential ever presented.
