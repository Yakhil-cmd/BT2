### Title
Paired device can inject ANSI/CSI terminal escape sequences into chat text and device names delivered unsanitized to the wallet UI/terminal - ([File: wallet.js])

### Summary
`wallet.js`'s `handleMessageFromHub` accepts a `"text"` chat message from any paired ("correspondent") device, strips only a few known bracket patterns via regex, and then emits the raw string to the `"text"` event for display by the wallet/UI/console layer, with no filtering of ANSI/CSI control sequences. `device.js`'s `handlePairingMessage` similarly stores an attacker-supplied `device_name` after only stripping HTML-like tags (`<[^>]*>`), not terminal escape sequences, and that name is later read back and displayed (e.g., via `console.log`, or in any terminal-based/headless client) whenever the correspondent is referenced.

### Finding Description
In `wallet.js`, the `"text"` message case (lines 101-113) only validates that `body` is a non-empty string and strips a fixed set of `(prosaic-contract:...)`-style markers:
```
body = body
	.replace(/\(prosaic-contract:.+?\)/g, '')
	.replace(/\(arbiter-contract-offer:.+?\)/g, '')
	.replace(/\(arbiter-contract-event:.+?\)/g, '')
	.replace(/\(arbiter-dispute:.+?\)/g, '');
// the wallet should have an event handler that displays the text to the user
eventBus.emit("text", from_address, body, message_counter);
``` [1](#0-0) 

No control-character or ANSI/CSI escape-sequence sanitization is performed before the string is handed to consumers of the `"text"` event, which — per the inline comment — is expected to display the raw text to the user (in GUI wallets, this renders as HTML, but in terminal-based clients such as headless bots that log incoming chat directly, the string is written straight to the terminal).

Similarly, `device.js`'s `handlePairingMessage` sanitizes `device_name` only against HTML tags:
```
var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
``` [2](#0-1) 
This name is persisted to `correspondent_devices.name` and later retrieved by `readCorrespondents`/`readCorrespondent` [3](#0-2)  for display wherever the correspondent is referenced, again without stripping terminal control sequences.

This mirrors the croc bug class (CVE-2023-43620): an attacker-controlled string field (there, a filename; here, a chat message body or a pairing device name) that is intentionally displayed to the receiving party's terminal/UI is not scrubbed of ANSI/CSI escape sequences, letting the sender manipulate the receiver's terminal (e.g., hide/obscure text, move cursor, in vulnerable terminal emulators trigger OSC-based clipboard/keystroke injection or title-bar spoofing).

### Impact Explanation
Any already-paired correspondent device (or, for pairing, any device presenting a valid pairing secret) can send a chat "text" message or a pairing "device_name" containing raw ANSI/CSI/OSC escape sequences. If the receiving wallet's UI/event-handler or a terminal-based client (e.g., headless wallet bots that log the "text" event to stdout) renders this string to a terminal without sanitization, the attacker can manipulate the victim's terminal display — potentially misleading the victim about payment amounts/addresses shown nearby, hiding portions of subsequent legitimate output, or exploiting known OSC-sequence vulnerabilities in some terminal emulators. This is a social-engineering-enabling terminal injection rather than a smart-contract/consensus bug, so its severity depends on the terminal/host application's exposure, but it is a concrete, unauthenticated-content-driven attack surface reachable by a normal paired counterparty.

### Likelihood Explanation
Likelihood is moderate-to-high for any deployment that logs/displays chat text or device names on a terminal (headless wallet bots are common in the Obyte ecosystem and typically `console.log` incoming events). Any already-paired device (which is a low-privilege, easily-obtained relationship — pairing only requires knowing a shared pairing secret) can trigger this at will by sending a normal-looking chat message.

### Recommendation
Sanitize `body` in the `"text"` handler and `device_name` in `handlePairingMessage` by stripping/escaping all ASCII control characters (0x00-0x1F, 0x7F) and, in particular, ANSI escape sequences (`\x1B` followed by CSI/OSC sequences) before emitting to `"text"`/`"object"` events or persisting to `correspondent_devices.name`. Equivalent filtering should be applied wherever externally supplied text is expected to be logged or displayed in a terminal context (e.g., `console.log` calls that print `device_name`, chat bodies, or other correspondent-controlled strings).
