### Title
Deflationary ERC20 Token Accounting Discrepancy in Service-Chain Bridge Drains Bridge Reserves — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`requestERC20Transfer` in the Kaia service-chain bridge pulls `_value + _feeLimit` tokens from the caller via `safeTransferFrom`, but then emits a `RequestValueTransfer` event with the caller-supplied `_value` as the bridged amount. For deflationary ERC20 tokens (tokens that deduct a transfer fee on every `transfer`/`transferFrom`), the bridge actually receives less than `_value + _feeLimit`, yet the counterpart bridge operators faithfully relay the event and release the full `_value` on the destination chain. Each such request permanently drains the bridge's token reserves by the deflation amount.

### Finding Description

In `requestERC20Transfer`:

```solidity
// BridgeTransferERC20.sol L133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

The `safeTransferFrom` call transfers `_value + _feeLimit` tokens from the caller. For a deflationary token with deflation rate `d`, the bridge actually receives `(_value + _feeLimit) * (1 - d)` tokens. However, `_requestERC20Transfer` is called with the original `_value` and `_feeLimit` unchanged.

Inside `_requestERC20Transfer`, `_payERC20FeeAndRefundChange` transfers `fee` to the fee receiver and `feeRefund` back to the user from the bridge's balance — totalling `_feeLimit` tokens out. Then the `RequestValueTransfer` event is emitted with `_value`:

```solidity
// BridgeTransferERC20.sol L97-107
emit RequestValueTransfer(
    TokenType.ERC20,
    _from,
    _to,
    _tokenAddress,
    _value,          // <-- inflated: actual received was less
    requestNonce,
    fee,
    _extraData
);
``` [2](#0-1) 

The bridge relay in `node/sc/bridge_manager.go` reads `valueOrTokenId` directly from the event and calls `HandleERC20Transfer` on the counterpart chain with that value:

```go
// bridge_manager.go L338-343
case ERC20:
    handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to,
        ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
``` [3](#0-2) 

The counterpart bridge then releases `_value` tokens to the recipient — the full requested amount, not the deflation-reduced amount actually deposited.

**Net deficit per request (lock/unlock mode):**
- Bridge received: `(_value + _feeLimit) × (1 − d)`
- Bridge paid out (fee + refund): `_feeLimit`
- Bridge net held: `(_value + _feeLimit) × (1 − d) − _feeLimit`
- Bridge should hold to back counterpart release: `_value`
- **Deficit per call: `(_value + _feeLimit) × d`**

### Impact Explanation

In **lock/unlock mode**: the counterpart bridge releases `_value` tokens while the source bridge holds fewer. Repeated calls drain the bridge's entire ERC20 reserve, allowing the attacker (or any user) to extract more tokens from the counterpart chain than were ever deposited. This is an unauthorized transfer of bridged assets.

In **mintBurn mode**: the bridge attempts to burn `_value` tokens but only holds `(_value + _feeLimit) × (1 − d) − _feeLimit` tokens. If the bridge has pre-existing reserves, the burn succeeds and the counterpart mints `_value` tokens — inflating the token supply on the destination chain beyond what was burned on the source chain.

The corrupted value is the `valueOrTokenId` field in the `RequestValueTransfer` event, which is used verbatim by operators to call `handleERC20Transfer` on the counterpart bridge.

### Likelihood Explanation

Token registration requires `onlyOwner` (`BridgeTokens.sol` L57–71), so a deflationary token must first be registered by the bridge owner. [4](#0-3) 

However, once any deflationary token is registered, `requestERC20Transfer` is `public` with no access control — any user can trigger the accounting discrepancy. The bridge owner may register a deflationary token without realizing the bridge does not account for transfer fees. There is no on-chain check or documentation warning against deflationary tokens.

### Recommendation

1. **Measure actual received amount** using a balance-before/after pattern:
   ```solidity
   uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
   IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
   uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)) - balanceBefore;
   require(actualReceived >= _value, "deflationary token: insufficient received");
   ```
2. **Or restrict** deflationary tokens by requiring `actualReceived == _value + _feeLimit` and reverting otherwise, preventing deflationary tokens from being usable with the bridge.

### Proof of Concept

1. Bridge owner registers a deflationary ERC20 token (1% burn on every transfer) on both source and counterpart bridges.
2. Attacker approves the source bridge for `1000 + 0` tokens (`_feeLimit = 0`, bridge fee = 0).
3. Attacker calls `requestERC20Transfer(token, attacker2, 1000, 0, "0x")`.
4. Bridge receives `1000 × 0.99 = 990` tokens (10 burned by deflation).
5. `RequestValueTransfer` event emits `valueOrTokenId = 1000`.
6. Bridge relay calls `handleERC20Transfer(..., 1000, ...)` on counterpart chain.
7. Counterpart bridge releases `1000` tokens to `attacker2`.
8. Net loss to bridge: 10 tokens per call. After 100 calls, the bridge is short 1000 tokens and will be unable to fulfill legitimate withdrawals. [5](#0-4) [6](#0-5)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
