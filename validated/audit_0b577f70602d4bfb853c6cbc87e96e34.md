### Title
Caller-supplied swap route executes arbitrary pool code under the caller's signed auth tree, draining unrelated wallet funds - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Analogous to the PraisonAI flaw where an unsanitized `--mcp` string reached `anyio.open_process` with no allowlist, the controller's strategy entrypoints forward a caller-supplied `swap: StrategySwap` byte blob straight to `router.execute_strategy` with no allowlist of the pool/token addresses the route names. The router invokes whichever contract the route specifies, so a crafted route puts attacker-deployed code on the call stack *below the caller's `require_auth` tree*. Any `token.transfer(caller, attacker, amount)` that code makes is recorded as a child of the caller's authorization entry and executes once the caller signs the simulated tree — stealing arbitrary unrelated tokens from the caller's wallet, unbounded by the routed `amount_in`.

### Finding Description
`swap_collateral` (and `swap_debt`, `repay_debt_with_collateral`, `multiply`, `flash_position` via the same helper) authenticates the caller (`require_authorized_caller` / `require_owner_or_delegate` in `contracts/controller/src/strategies/swap_collateral.rs:40-47`) and passes the raw `swap` bytes into `swap_tokens`, which calls `router.execute_strategy(&controller, &amount_in, swap)` under the flash guard (`contracts/controller/src/strategies/swap.rs:36-38`). The controller only constrains its *own* grant (`authorize_transfer_as_current`, line 34) and its own balance deltas (`RouterOverspend`, `NoSwapOutput`, lines 42-54, 75-84). Neither the controller nor the router validates which `pool` addresses the decoded route hops name — `venues::dispatch_hop` calls `env.invoke_contract(&ctx.hop.pool, ...)` for whatever `SwapVenue`/`pool` pair the payload carries, with no registry or allowlist (`contracts/swap-aggregator/src/venues/mod.rs:34-40`). Because the venue call sits inside the transaction authorized by the account owner, Soroban's recording-mode simulation attaches any nested `token.transfer(victim, …)` made by a rogue pool as a child of the victim's `swap_collateral` auth entry; in enforcing mode it succeeds if the victim signed that tree. The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates exactly this: a `RogueHopPool.swap()` performing `transfer(alice → attacker, WALLET_BALANCE)` executes under Alice's `swap_collateral` signature, leaving her with the fair swap output but a drained wallet (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-226`). The threat model confirms this is reachable in production and offloads mitigation to the client (`docs/explanation/threat-model.md:154-165`).

### Impact Explanation
Theft of user funds beyond the routed amount: the victim loses any token balance their address holds, in any token (including assets never listed by the protocol), limited only by wallet balance. Neither the payload `min_out` check, the controller's measured-output gate, nor the final health-factor check bounds the loss, because the stolen transfer is a sibling authorization unrelated to swap economics.

### Likelihood Explanation
Any unprivileged attacker can deploy a malicious "pool" contract and craft a valid route naming it. Exploitation requires the victim to sign a poisoned route (e.g., delivered through a malicious/compromised quoting frontend or phishing flow) — the same trust assumption the protocol itself relies on, since route XDR is opaque packed bytes (`ops`/`assets`/`amounts`) and the documented mitigation is client-side decoding, not a contract invariant. No privileged access, timing, or market condition is needed.

### Recommendation
Enforce the invariant on-chain rather than in clients: the controller (or router) should require that every hop's `token_in`/`token_out` be previously registered protocol/whitelisted assets, and that each `pool` address resolve from a governance-approved venue registry — the direct analog of the upstream `ALLOWED_COMMANDS` fix. Alternatively, the router could sandbox hops so venue code can only pull `token_in` from the router (its own `authorize_as_current_contract` tree), which is already true for the router's grant but does not cover the *caller's* tree; the caller-side fix is to refuse routes whose auth tree contains children beyond the single input `transfer`.

// Attacker-deployed contract named as `hop_pool` in the route.
#[contractimpl]
impl RogueHopPool {
    pub fn swap(env: Env) {
        // Reads (victim, wallet_token, attacker, amount) from storage.
        token::Client::new(&env, &wallet_token)
            .transfer(&victim, &attacker, &amount); // joins victim's auth tree
    }
}
