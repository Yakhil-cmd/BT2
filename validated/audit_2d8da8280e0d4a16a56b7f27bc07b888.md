### Title
Cross-org webhook confused deputy: `repository.owner.login` selects signing app, `repository.full_name` selects mutated repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GithubApp`/`webhook_secret` used to verify the HMAC based on `params.dig('repository','owner','login')`, while every event handler (e.g. `PullRequest::OpenedHandler#repository`) resolves the target `Shipit::Repository` from the independent `params.repository.full_name` field of the same attacker-controlled JSON body. Because both fields are read from a single body that the attacker fully controls and signs with their own legitimately-owned `webhook_secret`, the two values can be made to diverge, letting an attacker mutate a repository/organization they do not own.

### Finding Description
The broken binding is: `organization_used_to_verify_signature (params.repository.owner.login) == organization_owning_the_mutated_repository (params.repository.full_name's owner segment)`.

Code path:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and fetches `github_app = Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` against `request.raw_post` using that app's `webhook_secret`. [2](#0-1) [3](#0-2) 
2. On success, `create` dispatches the raw parsed JSON to `Shipit::Webhooks.for_event(event)` handlers, e.g. `PullRequest::OpenedHandler`. [4](#0-3) 
3. `OpenedHandler#repository` resolves the target repository purely from `params.repository.full_name`, independent of `repository.owner.login`: [5](#0-4) 
4. `Repository.from_github_repo_name` just splits `full_name` on `/` and does a `find_by`, with no comparison to the org that authenticated the request. [1](#0-0) 
5. `respond_to_pull_request_opened?`/`provision?` then act on that resolved (potentially foreign) repository, invoking `ReviewStackAdapter#find_or_create!`, mutating `Stack`/`PullRequest` rows for org-A even though org-B's secret authenticated the request. [6](#0-5) 

Attacker's exact request: attacker owns org-B and its real `webhook_secret`. They craft a JSON body where `repository.owner.login = "org-B"` (so `verify_signature` selects and successfully HMAC-verifies against org-B's real secret) but `repository.full_name = "org-A/repo"` (a real Shipit-tracked repository they don't own), and `X-Github-Event: pull_request` / `action: opened`. They compute a valid `X-Hub-Signature` themselves using org-B's secret (which they legitimately possess) over that exact body and POST it to `/webhooks`. `verify_signature` passes because it verifies with org-B's secret against a body that was in fact signed with org-B's secret — the check never inspects `full_name`. The handler then resolves and mutates org-A's repository.

None of the listed guards prevent this: `verify_signature` only ties the app to `repository.owner.login`, not to `full_name`; `ExplicitParameters` schema on `OpenedHandler` only enforces types/presence of `repository.full_name`, not organizational consistency; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` in this unauthenticated webhook path since it's a machine-to-machine webhook, not a user session; `Repository` model validations only constrain character format of `owner`/`name`, not provenance.

### Impact Explanation
An attacker who owns any GitHub organization with its own Shipit-configured GitHub App/webhook_secret can trigger creation and mutation of `Shipit::Stack` and `Shipit::PullRequest` rows for any other tracked repository in a different, unrelated GitHub organization, purely by crafting a divergent JSON body signed with their own credentials. Since review-stack provisioning executes the target repository's `shipit.yml`/tasks, this is a payload for one repository (org-B, which "authenticated" the request) mutating another's stack (org-A) — matching the Critical category explicitly listed in scope ("a payload for one repository mutating another's stack, commit, task or team"). The attack is repeatable against any tracked repository whose org is configured on the same Shipit instance, for `pull_request`, `push`, `status`, `check_suite`, and `membership` events alike, since all of them derive the mutated target independently of `repository_owner`.

### Likelihood Explanation
Preconditions: the Shipit instance must be configured with multiple `GithubApp`/`webhook_secret` entries (documented and supported "Using Multiple Github Applications" setup), and the attacker must control at least one of those orgs (i.e., have installed the app themselves, a normal, unprivileged action open to any GitHub user who can create an org and install a public GitHub App, or simply be a legitimate customer/tenant on a multi-tenant Shipit deployment). No Shipit secrets, sessions, or API tokens are required — only the attacker's own real webhook_secret, which they legitimately hold. Cost is a single crafted HTTP POST; it is fully repeatable and scriptable against arbitrary target repositories tracked by the instance.

### Recommendation
In `WebhooksController#verify_signature` (or in each handler's `repository` resolution), enforce that the organization used to select/verify the webhook app equals the organization derived from `params.repository.full_name` (and any other identifying fields like `organization.login`) before dispatching to handlers — reject the request (422) if they diverge. Alternatively, have handlers re-derive/re-verify the owning organization of the resolved `Repository` against the authenticated `repository_owner` from the controller before performing any mutation.

test "rejects pull_request payload whose repository.full_name org differs from the authenticated repository.owner.login org" do
  # org-B is a real configured GithubApp the "attacker" legitimately controls
  # org-A/repo is an existing tracked Shipit::Repository the attacker does not own
  repo_a = shipit_repositories(:shipit) # owner: "shopify", name: "shipit-engine" e.g.
  configure_provisioning_behavior(repository: repo_a, behavior: :allow_all)

  payload = payload_parsed(:pull_request_opened)
  payload["repository"]["owner"]["login"] = "org-b"        # matches attacker's real webhook_secret
  payload["repository"]["full_name"] = repo_a.github_repo_name # "shopify/shipit-engine" - a different org

  body = payload.to_json
  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", ORG_B_REAL_SECRET, body)

  request.headers["X-Github-Event"] = "pull_request"
  request.headers["X-Hub-Signature"] = signature

  assert_no_difference -> { Shipit::Stack.count } do
    post :create, body: body, as: :json
  end
  # Currently FAILS: a Stack IS created for repo_a despite org-b's secret authenticating the request,
  # demonstrating equality repository_owner(auth) == full_name-org(mutated) is violated.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
