### Title
Cross-repository CI status injection via `StatusHandler` breaks the "authenticated organization" ↔ "repository written" binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a GitHub `status` webhook by resolving the signing GitHub App from `repository.owner.login` (or `organization.login`) in the payload. [1](#0-0) [2](#0-1)  That check only proves the payload is authentic *for the repository/organization named in the payload*. However, `Handlers::StatusHandler#process` never consults that repository field — it looks up and mutates commits globally by `sha` alone, across every stack in the installation. [3](#0-2) 

### Finding Description
The base `Handler` class exposes a `stacks` helper that *does* scope lookups to `payload.dig('repository', 'full_name')`, and most handlers (`PushHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`) use it or `Repository.from_github_repo_name(params.repository.full_name)` to bind their writes to the repository the webhook actually pertains to. [4](#0-3) [5](#0-4) [6](#0-5) 

`StatusHandler` breaks this pattern: its `process` method runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no repository/stack scoping whatsoever. [3](#0-2)  The equality the system is supposed to enforce is:

`organization/repository whose signature was verified == repository whose Commit rows are mutated`

For `StatusHandler` this collapses to only checking `sha == sha`, decoupled from the repository. Since Git commit SHAs are content hashes and are **not globally unique across repositories** (identical trees/parents/authors/timestamps/messages reproduce identical SHAs, and this is trivially reproducible for any commit whose full metadata is public, e.g. any commit on a public GitHub repo), an attacker who can trigger a legitimately-signed `status` event for *any* repository under *any* onboarded GitHub App/org can cause `Commit.where(sha: ...)` to match — and mutate — commit rows belonging to an entirely different tracked `Stack`/`Repository`.

### Impact Explanation
Writing a fabricated `success` status onto a `Commit` in a stack unrelated to the webhook's own repository directly feeds `Commit#deployable?`, which is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`. [7](#0-6)  A commit that is deployable becomes eligible for `trigger_deploy`/continuous delivery on the victim stack, and `add_status` also triggers `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`. [8](#0-7)  This is a cross-repository write that can produce an unauthorized deploy of a commit whose actual CI never passed on its own repository — matching the Critical impact category ("cross-repository writes, or an unauthorized deploy").

### Likelihood Explanation
Exploitation requires: (1) the attacker to have or obtain the ability to have a `status` event delivered and signed for *some* repository onboarded to the Shipit instance (e.g. their own repo under an onboarded org, or any repo where they can post commit statuses), and (2) a commit SHA collision with a commit tracked in a different, victim stack. Because commit SHAs are deterministic content hashes and the target commit's full git object metadata is public for any public repository, an attacker can reconstruct an identical commit object (e.g. via `git commit-tree`) in their own repo and post/trigger a status against that SHA. No possession of `webhook_secret`, `api_clients_secret`, or a privileged Shipit account is required — only ordinary GitHub-side ability to generate a commit status webhook, which GitHub itself will sign correctly for the sending app/organization.

### Recommendation
Scope `StatusHandler#process` (and any other handler) to the repository named in the webhook payload, mirroring what `Handler#stacks`/`repository_name` already provides: filter `Commit` by the `Stack`s belonging to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before matching on `sha`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Attacker controls (or has status-posting rights in) `attacker-org/decoy-repo`, which is separately onboarded to the same Shipit instance (or shares a GitHub App/org with the victim stack).
2. Attacker identifies a public commit SHA `X` that is tracked as part of `victim-org/important-repo`'s stack in Shipit (commit history is public).
3. Using `git commit-tree`/cherry-pick with identical tree, parents, author, committer, and message/timestamps, attacker reproduces a commit with the exact same SHA `X` inside `decoy-repo`.
4. Attacker (or CI they control) posts a GitHub commit status `success` for SHA `X` on `decoy-repo`. GitHub signs and delivers this `status` webhook with the legitimate `X-Hub-Signature` for `attacker-org`.
5. `WebhooksController#verify_signature` verifies the signature successfully because it's a genuine webhook from `attacker-org`'s GitHub App. [1](#0-0) 
6. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: 'X')`, matches the `Commit` row belonging to `victim-org/important-repo`, and calls `create_status_from_github!`, marking it `success` regardless of the actual CI state on `important-repo`. [3](#0-2) 
7. If that was the last blocking status, `important-repo`'s commit becomes `deployable?` and can be shipped/merged via continuous delivery, an unauthorized deploy triggered entirely from an unrelated repository's webhook.

      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state

      end

    end
