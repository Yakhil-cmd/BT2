### Title
Parameterized "base_aa" AAs delegate full control of their funds to an unverified, unpinned implementation address - (File: `aa_composer.js`, `aa_validation.js`)

### Summary
The Marmo bug is about a `relay()` function that uses `delegatecall` into an `_implementation` address chosen by the caller, giving that implementation full control over the wallet's storage/balance with no guarantee that the code executed is trustworthy. Ocore's Autonomous Agent (AA) "parameterized AA" (`base_aa`) mechanism has the same trust-delegation shape: a wrapper AA's own trigger execution — and therefore control over its own balance, state variables, and outgoing payments — is delegated entirely to whatever definition currently resides at an address chosen at AA-authoring time, but that definition is resolved lazily, at each trigger, and is never pinned or required to exist/be verified when the wrapper AA is created.

### Finding Description
When an AA definition has a `base_aa` field, `validateAADefinition` only checks that `base_aa` is a syntactically valid address; it never verifies that the address is currently defined, let alone that it is defined as a legitimate AA: [1](#0-0) 

At trigger time, `handleTrigger` in `aa_composer.js` redirects execution to whatever AA definition is currently stored for `template.base_aa`, fetched fresh via `storage.readAADefinition` using the trigger's own `mci`: [2](#0-1) 

This means the actual code that runs "as" the wrapper AA (with full access to its accumulated balance, its own state vars, and the ability to emit arbitrary `payment`, `data`, `asset`, `definition`, and `state` messages under the wrapper's own address) is not fixed or verifiable at the time the wrapper AA is created and users start sending funds to it — it is whatever definition later gets published and registered on-chain at `base_aa`. Just like Marmo's `relay()`, the wrapper AA's caller (any trigger sender/depositor) has no way to know in advance what logic will actually execute with full custody of the wrapper's funds; they must simply trust the AA author's claim about `base_aa`'s behavior, and that trust can be violated the moment `base_aa`'s definition is finally revealed/registered.

### Impact Explanation
Since `base_aa` need not exist (or be an AA) when the wrapper is authored, an AA author can publish and advertise a "parameterized AA" as reusing some documented, audited `base_aa` logic (this is the intended code-reuse pattern for `base_aa`/`params`), collect deposits into the wrapper's balance while `base_aa` is undeployed or looks benign, and later register a different, malicious AA definition at that same address. Because the address is fixed to the eventual content hash, only the party who already knows that content (i.e., the wrapper's author) can ever activate it — but nothing stops that same author from silently withholding the real definition until funds accumulate and then deploying malicious logic that drains the wrapper's entire base/asset balances to attacker-controlled addresses, mutates state, or issues/destroys assets under the wrapper's identity. This is a direct "AA fund loss" scenario reachable purely from posting units/triggers to a publicly deployed AA, matching the required impact category.

### Likelihood Explanation
`base_aa`/`params` (parameterized AAs) is a standard, documented AA feature intended to let independent addresses share one piece of logic, so wrapper AAs referencing not-yet-materialized `base_aa` addresses are a realistic, unremarkable deployment pattern rather than a contrived edge case. No additional privileged access is needed — any unprivileged AA author can construct such a wrapper, and any trigger sender/depositor interacting with a seemingly normal AA is exposed. Validation of AA definitions never requires or checks that `base_aa` currently resolves to any published, let alone benign, AA logic, so the trust gap is inherent to the current validation logic in `aa_validation.js` and the just-in-time resolution logic in `aa_composer.js`.

### Recommendation
Require `base_aa` to reference an address that is already registered as a valid AA at the time the parameterized (wrapper) AA definition itself is validated/registered (i.e., pin the referenced logic's existence, and ideally its content, at wrapper-creation time rather than resolving it lazily per trigger). At minimum, surface this risk clearly to users/depositors (e.g., wallets/explorers should refuse to treat a parameterized AA as "safe" until its `base_aa` is confirmed to exist and its source has been reviewed), analogous to the recommendation given for Marmo (whitelist/verify the implementation before trusting it with funds).

### Proof of Concept
1. Attacker crafts (off-chain) a malicious AA definition `M` that pays out the AA's entire balance to an attacker address, and computes `evil_addr = chash160(M)` without publishing `M`.
2. Attacker publishes a parameterized "wrapper" AA definition `W = ['autonomous agent', { base_aa: evil_addr, params: {...} }]` and markets it as reusing some legitimate, documented `base_aa` behavior. `aa_validation.js` accepts `W` because it only checks `isValidAddress(template.base_aa)`. [3](#0-2) 
3. Users send triggers/payments to `chash160(W)`, believing they are interacting with the advertised logic. While `evil_addr` is undefined, triggers to `W` simply bounce/error (`"base AA not found"`), so funds accumulate in `W`'s balance without any code having actually executed. [4](#0-3) 
4. Attacker later posts unit(s) that register `M` as the definition of `evil_addr` (making it a real AA).
5. The next trigger sent to `W` (or any subsequent trigger) causes `handleTrigger` to redirect to `M`, which executes with `address = chash160(W)` and full access to `W`'s accumulated balance, sending it wherever the attacker specifies.
