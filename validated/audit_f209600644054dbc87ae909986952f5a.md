### Title
Cross-repository forgery of commit statuses via `StatusHandler` breaks the organization-authenticated / repository-written binding - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to authenticate a webhook against based solely on `repository.owner.login` (falling back to `organization.login`) taken from the JSON body. `Webhooks::Handlers::StatusHandler`, however, applies the resulting `status` event to **any** commit in the entire Shipit database that matches the given `sha`, without ever checking that the commit belongs to a stack/repository owned by the organization that produced the valid signature. This breaks the binding "organization that authenticated == repository that is written," letting a party who legitimately controls one Shipit-tracked GitHub organization forge CI status updates for commits belonging to a completely different organization/repository tracked by the same Shipit instance.

### Finding Description
`verify_signature` picks the authenticating org purely from payload content: [1](#0-0) [2](#0-1) 

This determines only which `GitHubApp`/`webhook_secret` is used to check the HMAC signature via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the raw parsed params straight to the handlers, with no further tie between the authenticated organization and what the handler actually touches: [4](#0-3) 

`StatusHandler`'s parameter schema does not even require a `repository` key, and `process` resolves the target purely by commit SHA across the whole database: [5](#0-4) 

Compare this to every other handler (`PushHandler`, the `PullRequest::*` handlers), which at least scope to a repository derived from `repository.full_name` via `Handler#stacks`/`Repository.from_github_repo_name`: [6](#0-5) 

`StatusHandler` uniquely skips this scoping and calls `Commit.create_status_from_github!` directly on any matching commit, regardless of which stack/repository/organization it belongs to: [7](#0-6) 

The binding that should hold is:
`organization whose webhook_secret validated the signature == organization owning the repository/commit the handler mutates`

Before the attacker's request, this equality trivially holds for legitimate GitHub-originated webhooks (GitHub always sends a `repository` object matching the signing installation). After the attacker's request, the equality is broken: the signature is valid for organization A (which the attacker legitimately administers/owns the GitHub App installation for), but the mutated commit/stack belongs to organization B, because `StatusHandler` never re-derives or checks a repository at all.

### Impact Explanation
A `Status` created via `create_status_from_github!` feeds directly into CI-gating logic used for continuous deployment and the merge queue: [8](#0-7) 

and status transitions can enqueue `ProcessMergeRequestsJob`, which merges pending pull requests once `all_status_checks_passed?` is satisfied: [9](#0-8) 

By forging a `success` status for a victim organization's commit while authenticating with a different organization's valid webhook signature, an attacker can cause Shipit to treat a commit as CI-passing in a stack they do not own, enabling continuous deployment or auto-merge to proceed — an unauthorized deploy/merge triggered from outside the victim organization's trust boundary.

### Likelihood Explanation
Any organization onboarded to the same Shipit instance (however unrelated/low-privileged relative to the victim stack) can trigger this: the attacker only needs to control one legitimately configured GitHub App installation (their own webhook secret, which they set up themselves) and know/guess a commit SHA belonging to the victim stack (often discoverable from public repos, PRs, or commit links). No compromise of the victim's own credentials, GitHub App, or webhook secret is needed — only their own, unrelated organization's.

### Recommendation
Require and validate a `repository` field in `StatusHandler`'s params, and scope the commit lookup to `Repository.from_github_repo_name(params.repository.full_name)`'s stacks (as every other handler already does), rejecting the event if the repository named in the payload does not match a stack whose commits are otherwise being addressed. More generally, `WebhooksController` should verify that the organization used to select the `webhook_secret` in `verify_signature` matches the organization that owns the repository each handler subsequently writes to.

### Proof of Concept
1. Attacker legitimately administers GitHub organization `attacker-org`, which has a working Shipit GitHub App installation with a real, attacker-known `webhook_secret` (`Shipit.github(organization: 'attacker-org')`).
2. Attacker learns/observes a commit SHA `deadbeef...` that exists in `victim-org/victim-repo`, a stack tracked by the same Shipit instance.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "organization": {"login": "attacker-org"},
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required-check"
}
```
   signed with `attacker-org`'s real `webhook_secret` via `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker-org` (no `repository` key present, falls back to `organization.login`) and validates successfully against `attacker-org`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: 'deadbeef...')`, finds the commit in `victim-org/victim-repo`'s stack, and calls `create_status_from_github!`, recording a forged `success` status — with no check that `victim-org` has anything to do with `attacker-org`.
6. If that commit was pending on that status context for continuous deployment or merge-queue gating, the forged status can trigger deployment/merge automation on `victim-org/victim-repo`. [10](#0-9) [11](#0-10)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
