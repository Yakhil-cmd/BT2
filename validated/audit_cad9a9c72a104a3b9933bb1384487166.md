### Title
Webhook signature verification is bound to `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, enabling cross-organization webhook forgery in multi-tenant configurations - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate an incoming webhook against using `repository_owner`, derived from `payload.dig('repository','owner','login')` (or `organization.login`). However, every event handler that actually acts on the payload (`Shipit::Webhooks::Handlers::Handler#stacks`) resolves the target repository from a *different* payload field, `repository.full_name`, which is never cross-checked against the organization that was used to authenticate the request. In a Shipit deployment configured with multiple GitHub organizations (a documented, supported configuration, see `config/secrets.development.shopify.yml`), this decouples "who authenticated the payload" from "which repository/stack is acted upon."

### Finding Description
`verify_signature` picks the HMAC secret using the org derived from the payload itself: [1](#0-0) [2](#0-1) 

The signature is a valid HMAC-SHA1 over the *entire raw JSON body* using the secret belonging to whatever organization is named in `repository.owner.login`/`organization.login`: [3](#0-2) 

Once verification passes, every handler resolves the affected `Stack`/`Repository` purely from `repository.full_name`, independent of the field used for authentication: [4](#0-3) 

For example, `PushHandler` uses that resolved `stacks` collection to trigger `sync_github`: [5](#0-4) 

Because the attacker fully controls the raw JSON body they sign (they only need the secret of *one* configured organization — their own, legitimately assigned GitHub App), they can set `repository.owner.login` = OrgA (whose secret they hold) while setting `repository.full_name` = `OrgB/some-repo` (a repository/stack belonging to a completely different organization configured on the same shared Shipit instance). The signature computed with OrgA's secret over that full forged body is valid, `verify_signature` passes because it used OrgA's secret to check OrgA-attributed data, and the handler then acts on OrgB's stack using the untrusted `full_name` field.

This is exactly the "authenticated organization vs. written repository" trust binding described in the rules: the equality `organization_that_authenticated == repository_acted_upon` is not enforced anywhere between `WebhooksController#verify_signature` and `Handler#repository_name`.

### Impact Explanation
Handlers keyed off `repository.full_name` include not only `PushHandler` (forces `sync_github`, ingesting attacker-chosen commits) but also status/check-run handlers that record `commit_status`/`check_suite` results for the resolved stack's commits. Since commit deployability (and, when auto-deploy is enabled, whether a deploy actually ships) is derived from these ingested statuses, an attacker who legitimately controls only their own low-trust organization's webhook secret can forge success statuses for another organization's commits, potentially causing Shipit to treat unreviewed code as deployable/deployed for a repository they have no access to — a cross-repository/cross-tenant integrity violation and, in effect, an unauthorized-deploy vector to a repository outside the attacker's control.

### Likelihood Explanation
Exploitation requires the target Shipit instance to be configured for multiple GitHub organizations (explicitly supported and documented, `config/secrets.development.shopify.yml`), and requires the attacker to control one organization's legitimately-assigned webhook secret while targeting another organization/stack tracked by the same Shipit instance. This is a realistic scenario for shared/multi-tenant Shipit deployments, and requires no privileged Shipit account, `ApiClient` token, or GitHub App private key — only the webhook secret for the attacker's own, lower-trust organization.

### Recommendation
After `verify_signature` selects an organization's secret and validates the HMAC, re-validate that `repository.full_name`'s owner matches the `repository_owner` used to select that secret (or, equivalently, resolve the target `Stack`/`Repository` using the already-authenticated organization rather than trusting `full_name` independently) before invoking any handler.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. As someone who legitimately administers `OrgA`'s GitHub App (and thus knows `OrgA`'s `webhook_secret`), craft a `push` webhook JSON body where `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/some-tracked-repo"`.
3. Compute `X-Hub-Signature` as `sha1=HMAC_SHA1(OrgA_webhook_secret, raw_body)` and POST it to `/webhooks`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature against `OrgA`'s secret. [6](#0-5) 
5. `PushHandler#process` resolves `stacks` via `repository_name = payload.dig('repository','full_name')` = `"OrgB/some-tracked-repo"`, and triggers `sync_github` on `OrgB`'s stack despite the request never being authenticated with `OrgB`'s secret. [4](#0-3) [5](#0-4)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
