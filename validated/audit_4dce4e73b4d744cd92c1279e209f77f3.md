### Title
Webhook signature verification is bypassed per-organization when `webhook_secret` is unset, allowing cross-organization event forgery - (File: `lib/shipit/github_app.rb`)

### Summary
`GithubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the organization resolved from the payload, mirroring the reported bug class where an "empty"/missing check silently passes validation. Because the organization used to select which `GithubApp`/secret to verify against (`repository.owner.login`) and the repository actually acted upon (`repository.full_name`) are two independently attacker-controlled fields in the same unauthenticated JSON body, an attacker can pick an organization with no secret configured to satisfy the signature check, while pointing the payload's `repository.full_name` at a different, secret-protected organization's repository.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate against using only the payload's `repository.owner.login` (or `organization.login`): [1](#0-0) [2](#0-1) 

The verification itself contains the flawed "empty check" logic: [3](#0-2) 

`return true unless webhook_secret` means: if the resolved organization's config has no `webhook_secret` set (a supported, documented configuration — see `config/secrets.development.example.yml` and `docs/setup.md` which mark `webhook_secret` as optional/nil-able), **any** payload — regardless of actual signature — is treated as verified.

Meanwhile, the actual repository/stack acted upon by handlers is derived from a *different* field of the same payload, `repository.full_name`, with no correlation check to `repository.owner.login`: [4](#0-3) [5](#0-4) 

The trust binding that should hold is: `organization that authenticated (repository.owner.login → GithubApp/webhook_secret used)` == `organization whose repository is written (repository.full_name → Repository.from_github_repo_name)`. Because these are separate, non-cryptographically-linked JSON fields and the "no secret configured" branch skips validation entirely instead of rejecting or requiring the values to match, an attacker can break this equality: set `repository.owner.login` to an org with no `webhook_secret` (auto-passes verification) but set `repository.full_name` to `"other-org/protected-repo"` (an org that *does* have `webhook_secret` configured and is meant to be protected).

### Impact Explanation
This lets an unauthenticated, unprivileged network attacker forge push/status/check_suite/pull_request/membership events for repositories belonging to an organization that has webhook signing configured, as long as any other organization on the same Shipit instance is configured without a `webhook_secret`. This can trigger unauthorized `GithubSyncJob` runs, fabricate commit statuses accepted for deploy gating (`StatusHandler`), or manipulate review-stack lifecycle (archive/unarchive) for repositories the attacker does not control — a cross-organization/cross-repository write achieved purely by forging an HTTP POST to `/webhooks`, matching the "cross-repository writes" / "unauthorized deploy" impact tier.

### Likelihood Explanation
Requires only that the multi-organization Shipit config includes at least one organization without a configured `webhook_secret` (a supported, documented setup shown in `config/secrets.development.example.yml`), which is a realistic operational scenario during onboarding or for internal/low-risk orgs. No credentials, session, or GitHub App key are needed — the attacker only needs the `/webhooks` endpoint to be reachable, which it is by design.

### Recommendation
- Do not treat an unset `webhook_secret` as an implicit pass; require an explicit organization-level opt-out, or reject webhooks entirely when no secret is configured (`return false unless webhook_secret`, or fail closed with an explicit config flag).
- Cross-validate `repository.owner.login`/`organization.login` against `repository.full_name`'s owner segment before processing, rejecting mismatches.
- Consider deriving the verifying organization/app strictly from `repository.full_name` (the same field used to resolve the target repository) rather than a separate payload field, so the "authenticated org" and "written repo" are always the same value.

### Proof of Concept
1. Configure Shipit with two orgs: `orgA` (no `webhook_secret`) and `orgB` (`webhook_secret: s3cr3t`, owns repo `orgB/prod-app` tracked by Shipit).
2. POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/prod-app" }
}
```
3. `verify_signature` resolves `repository_owner` = `orgA`, calls `Shipit.github(organization: 'orgA').verify_webhook_signature(...)`, which returns `true` immediately since `orgA` has no `webhook_secret`.
4. `PushHandler#process` resolves `repository_name` = `orgB/prod-app` and processes the forged push, invoking `stack.sync_github(expected_head_sha: params.after)` on `orgB`'s protected stack, despite the request never carrying a valid signature for `orgB`. [6](#0-5) [3](#0-2) [7](#0-6)
