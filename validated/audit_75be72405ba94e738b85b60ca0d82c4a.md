### Title
Stack-scoped API token can read CCMenu build status of *any* stack — token/stack authorization binding bypass in `CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` overrides the base controller's stack resolution and looks up the stack directly by request parameter instead of through the stack-scoped relation used everywhere else in the API. This breaks the binding between "the stack a token is authorized for" and "the stack the request actually touches," letting a token that is scoped to one stack read build/deploy status for any other stack in the installation.

### Finding Description
Every other API controller resolves the target stack through `Shipit::Api::BaseController#stack`, which is derived from `#stacks`, itself filtered by the authenticated `ApiClient`'s `stack_id` when the client is stack-scoped: [1](#0-0) 

`CCMenuController`, however, defines its own private `stack` method that resolves directly from `Stack.from_param!(params[:stack_id])`, completely bypassing the `stacks` scoping relation: [2](#0-1) 

The `require_permission :read, :stack` declaration only checks that the `ApiClient`'s `permissions` array contains `read:stack`; it never checks that the specific stack being requested matches the client's `stack_id`: [3](#0-2) 

Stack-scoped, single-permission tokens are exactly what `CCMenuUrlController#fetch` mints for any logged-in Shipit user who can view a stack's settings page — a `read:stack`-only `ApiClient` bound to that one stack, embedded in a CCMenu URL: [4](#0-3) 

Because `CCMenuController#stack` ignores `current_api_client.stack_id`, that same low-privilege, single-stack token can be replayed against `GET /api/*/ccmenu.xml?stack_id=<other_stack>&token=<token>` for **any** stack in the installation, not just the one it was issued for, and the controller happily renders that other stack's deploy state: [5](#0-4) 

The rendered XML discloses the target stack's identifier, merge/lock status, whether a build is currently running, and the last build time/label: [6](#0-5) 

This is a concrete analog of the reported front-running bug's core defect class: a trust binding (which stack a credential is authorized to act on) is established at issuance time but never re-verified at use time, so the credential's authority silently expands to an entity it was never meant to cover — the same "scope A granted, scope B exercised" mismatch as authorizing Bob for Alice's account and having that authorization escape its intended boundary.

### Impact Explanation
This maps to the "High" impact category: unauthenticated/under-scoped read of stack state and deploy output. Any user who can obtain a CCMenu token for one stack (which only requires ordinary access to a single stack's settings page) can enumerate and read live build/deploy status — including whether deploys are running, last deploy time, and merge/lock status — for every other stack managed by the Shipit instance, including stacks they have no permission to view. This is a genuine authorization-boundary crossing enabled purely by application logic, not by possession of an over-privileged credential.

### Likelihood Explanation
Likelihood is high: no special privileges are needed beyond normal use of the product (viewing any single stack's settings page is enough to obtain a `read:stack` CCMenu token), the `stack_id` request parameter is trivially attacker-controlled, and the vulnerable code path (`CCMenuController#stack`) is reached on every request to the CCMenu endpoint.

### Recommendation
Remove the private `stack` override in `CCMenuController` and let it use the inherited `Shipit::Api::BaseController#stack`/`#stacks` methods, which already enforce that `params[:stack_id]` must be one of the stacks visible to `current_api_client` (i.e., restricted to `current_api_client.stack_id` when the client is stack-scoped). If a custom lookup is still desired, it must explicitly re-verify `stack.id == current_api_client.stack_id` whenever `current_api_client.stack_id?` is true, rejecting (404/403) otherwise.

### Proof of Concept
1. As any logged-in Shipit user with visibility into Stack A, visit Stack A's settings page and trigger the CCMenu URL fetch (`GET /stacks/A/ccmenu_url` via `CCMenuUrlController#fetch`), which mints and returns a URL like `https://shipit.example.com/api/1/stacks/A/ccmenu.xml?token=<token_A>` where `token_A` decodes to an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id. [7](#0-6) 
2. Replay the same token against a different, unrelated stack B that the user has no access to: `GET /api/1/stacks/B/ccmenu.xml?token=<token_A>`.
3. `CCMenuController#authenticate_api_client` authenticates `token_A` successfully, `require_permission :read, :stack` passes because the client has `read:stack`, and `CCMenuController#stack` resolves Stack B directly via `Stack.from_param!(params[:stack_id])`, ignoring that the token is scoped to Stack A. [8](#0-7) 
4. The response renders Stack B's live deploy status (running/sleeping, last build time, merge/lock status) even though `token_A` was never authorized for Stack B.
