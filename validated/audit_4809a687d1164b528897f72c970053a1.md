The reported CVE-2024-8361 is specific to SiliconLabs SiWx91x hardware firmware (WiseConnect), where the device's SHA2-224 implementation incorrectly returns a 256-bit digest, triggering a length-assertion crash. Searching the Polkadot SDK codebase for any SHA2-224 usage found no matches at all [1](#0-0) , and the crypto-hashing primitives module only exposes fixed-output functions such as `sha2_256`, `keccak_256`, `keccak_512`, `blake2_128`, `blake2_256`, and `twox_128/256`, each returning a compile-time-fixed-size array (`[u8; 32]`, `[u8; 16]`, etc.) rather than a runtime-variable length [2](#0-1) .

The same pattern holds in `StorageHasher` implementations (`Blake2_128`, `Blake2_256`, `Twox128`, `Twox256`) where `Output` is a fixed-size array type checked at compile time via the `hash()` signature, not a length computed or asserted at runtime [3](#0-2) . Contract/revive host functions (`hash_sha2_256`, `hash_keccak_256`, `hash_blake2_256`, `hash_blake2_128`) similarly write into a caller-provided fixed-size output buffer declared via `hash_fn!(sha2_256, 32)` macros [4](#0-3) , and the fixture/benchmark code confirms output buffers are always the expected fixed size (32 or 16 bytes) with no length-mismatch assertion path reachable by attacker-controlled input [5](#0-4) .

Since Rust's type system enforces fixed-size hash outputs at compile time (unlike a C/embedded implementation where a mismatched digest length could slip through and trigger a runtime assertion), and since SHA2-224 is not implemented anywhere in this codebase, there is no reachable "wrong hash length" runtime assertion/DoS analog through any signed extrinsic, contract call, or XCM path.
