### Title
CCMenu API token minted for one stack authorizes read access to every stack in the Shipit instance - (File: `app/controllers/shipit/ccmenu_url_controller.rb`)

### Summary
The Golom report shows a pre-check that verifies a weaker/wrong condition than what the settlement logic actually allows, letting a caller pass a check whose real-world guarantee doesn't hold. The analog in Shipit is `CCMenuUrlController#client`, which mints a `read:stack` `ApiClient` token without binding it to the requested stack, while `Api::CCMenuController` only checks the *permission string* (`read:stack`) — never that the token's implicit scope matches the `stack_id` in the request. The token that a user believes is bound to "this stack" is in fact valid for **any** stack.

### Finding Description
`CCMenuUrlController#fetch` builds a CCMenu polling URL for a specific stack and generates the bearer `token` embedded in that URL: [1](#0-0) 

```ruby
def fetch
  uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
  uri.query = { 'token' => client.authentication_token }.to_query
  render(json: { ccmenu_url: uri.to_s })
end
...
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```

The `ApiClient` is created with `permissions: %w[read:stack]` and **no `stack:` association**, so `stack_id` is `nil`. `ApiClient#check_permissions!` only verifies the operation/scope string exists in `permissions`; it never inspects which stack is being requested: [2](#0-1) 

The one control that *would* scope a client to a single stack lives in `Api::BaseController#stacks`/`#stack`: [3](#0-2) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

But `Api::CCMenuController` overrides `#stack` and bypasses this scoping entirely, resolving straight from the global `Stack` table: [4](#0-3) 

```ruby
require_permission :read, :stack
...
def show
  latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
  render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
end

private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

Even if this override didn't exist, the underlying `ApiClient` is not stack-scoped at all (`stack_id` is `nil`), so `stacks` would resolve to `Stack.all` regardless. Either way, the "pre-check" (`require_permission :read, :stack`) validates only the permission *label*, not the binding between the token and the specific stack the token's URL was generated for. This exactly mirrors the Golom bug class: the check validates a condition (`permissions.include?("read:stack")`) that is weaker than the implicit guarantee the caller relies on (this token only exposes stack X).

Unlike the rest of the API, `Api::CCMenuController#authenticate_api_client` accepts the token via a query-string `params[:token]` with no session, no `X-Shipit-User`, and no GitHub team check — it is explicitly designed to be hit unauthenticated by CI dashboard tools: [5](#0-4) 

### Impact Explanation
Any holder of a single CCMenu URL/token (embedded in a CI dashboard config, browser history, proxy/access logs, or shared screenshot) can substitute a different `stack_id` in the query string and read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock state) of **every other stack** hosted on that Shipit instance, including stacks belonging to repositories/teams the token holder was never authorized to view. This is an unauthenticated cross-stack read of deploy/task state, matching the High-severity bucket "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
High. No attacker action beyond obtaining one legitimate CCMenu token is required (these tokens are handed out in plaintext URLs meant for third-party polling tools, i.e., low-trust distribution by design), and the only "attack" is changing a URL query parameter (`stack_id`). The XML template exposes deploy status data confirmed by the test suite's own assertions on required fields.

### Recommendation
Bind the `ApiClient` created in `CCMenuUrlController#client` to the specific `stack` (`stack:` association, not just `creator`/`name`), and make `Api::CCMenuController#stack` use the inherited scoped `stacks.from_param!` instead of `Stack.from_param!` directly, so the permission check and the stack scope are enforced together rather than independently.

### Proof of Concept
1. As an authorized Shipit user, visit a stack's settings page and generate the CCMenu URL for `stack-A` (calls `CCMenuUrlController#fetch`), obtaining `token=T`. [6](#0-5) 
2. `token=T` corresponds to an `ApiClient` with `permissions: ["read:stack"]` and `stack_id: nil` (not bound to stack-A). [7](#0-6) 
3. Send `GET /api/ccmenu/stack-B?token=T` (any other stack the requester has no legitimate access to).
4. `Api::CCMenuController#authenticate_api_client` accepts `T` with no session/team check, `require_permission :read, :stack` passes because `T` has the `read:stack` string, and `#stack` resolves `stack-B` directly via `Stack.from_param!`, returning stack-B's deploy status XML. [8](#0-7)
