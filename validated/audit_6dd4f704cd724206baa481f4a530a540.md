### Title
API token scoped to one stack can read CCMenu build status of any other stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces per-token stack scoping by making the `stacks`/`stack` finder methods filter by `current_api_client.stack_id` before permission checks are meaningful, but `Api::CCMenuController` overrides `stack` to bypass that scoping, breaking the binding "stack a token authorizes == stack it touches."

### Finding Description
`ApiClient` can be scoped to a single `stack_id`, and `Api::BaseController#stacks` enforces that scope: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, with `stack` calling `stacks.from_param!(params[:stack_id])` [1](#0-0) . The permission check itself, `ApiClient#check_permissions!`, only verifies the operation/scope string (e.g. `read:stack`) is present in `permissions` — it never compares against `stack_id` [2](#0-1) . All enforcement of "this token may only touch its own stack" therefore depends entirely on `stacks`/`stack` being used as the lookup source.

`Api::CCMenuController` declares only `require_permission :read, :stack` [3](#0-2)  but overrides `stack` to bypass the scoped finder entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

`Stack.from_param!` looks up any stack in the system by owner/name/environment, with no scoping applied [5](#0-4) . Because `check_permissions!` only checks the permission bit and CCMenuController never consults `current_api_client.stack_id`, a token that is scoped to Stack A but merely holds the `read:stack` permission bit can supply any other stack's `stack_id` in the URL and successfully render that stack's CCMenu status.

The binding broken, as an equality:
`stack authorized by token (current_api_client.stack_id)` != `stack actually touched (params[:stack_id] resolved via Stack.from_param!)`.

Before the attacker's request: token is scoped to stack A only (`ApiClient#stack_id == A`), and normal endpoints (`Api::StacksController`, etc.) correctly restrict reads/writes to stack A via the `stacks`/`stack` scoping.
After the request: the same token, unmodified, is used against `GET /api/stacks/<owner>/<repo>/<env>/ccmenu`, where `<owner>/<repo>/<env>` identifies stack B (a different, unauthorized stack) — and the response contains stack B's name, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` [6](#0-5) .

### Impact Explanation
This is an unauthenticated-scope read of stack state: a token intentionally restricted to one stack (e.g. issued to a narrow integration or CI job, as seen in the `here_come_the_walrus` fixture which is scoped to a single stack with only `read:stack`) can enumerate build/deploy status information for any other stack hosted by the same Shipit instance, including stacks belonging to different repositories/teams that the token holder should have no visibility into. This matches the "High - ... unauthenticated read of stack state" impact category.

### Likelihood Explanation
Likelihood is high for anyone already holding any legitimately-issued, narrowly-scoped `ApiClient` token with `read:stack` permission (a normal, low-privilege credential meant to be handed to CI/monitoring tools) — no additional secrets, GitHub access, or elevated permissions are required. The only requirement is knowing or guessing another stack's `owner/repo/environment` path, which is often predictable/enumerable.

### Recommendation
Make `Api::CCMenuController#stack` use the scoped `stacks` collection from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so the `current_api_client.stack_id` restriction is honored consistently with the rest of the API surface.

### Proof of Concept
1. Create two stacks, A and B, under different repositories/environments.
2. Issue an `ApiClient` scoped to stack A only with `permissions: ['read:stack']` (mirrors fixture `here_come_the_walrus` [7](#0-6) ).
3. Authenticate with that token and call:
   `GET /api/stacks/<B-owner>/<B-repo>/<B-environment>/ccmenu`
4. Observe HTTP 200 with stack B's CCMenu XML (name, `lastBuildStatus`, etc.), despite the token being scoped only to stack A — confirmed by the controller test pattern showing `#show renders the xml` succeeds purely based on permission bit and does not vary based on `current_api_client.stack_id` [8](#0-7) .
