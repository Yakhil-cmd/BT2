### Title
Organization used to verify the webhook signature is not bound to the repository the payload's handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization configuration (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, which is read directly from the untrusted payload (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`): [1](#0-0) [2](#0-1) 

`Shipit.github(organization: ...)` resolves to a per-organization `GithubApp` instance, each with its own independently configured `webhook_secret`: [3](#0-2) [4](#0-3) 

Once the signature check passes, the raw, unvalidated payload is dispatched to event handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [5](#0-4) 

Handlers determine which repository/stack to operate on independently, using `payload.dig('repository', 'full_name')` — a completely separate field from the one used for signature verification (`repository.owner.login`): [6](#0-5) 

`PushHandler`, for example, uses this repository lookup to select every non-archived stack on the resolved branch and trigger a GitHub sync: [7](#0-6) 

This is exactly the trust-binding break described in the analog rules: "an organization that authenticated versus the repository that is written." The signature is verified against the `webhook_secret` belonging to the organization named in `repository.owner.login`/`organization.login`, but the code that actually acts on the payload (`Handler#repository_name`) trusts `repository.full_name`, an entirely independent, attacker-controlled field. Nothing ties the two together.

**Attack path**: In a Shipit deployment that hosts multiple GitHub organizations (each with its own `webhook_secret` configured under `Shipit.github(organization: X)`), an attacker who is a legitimate, unprivileged member/owner of their own onboarded organization ("orgA") knows their own org's `webhook_secret` (they configured the webhook themselves when onboarding their repo to this shared Shipit instance). They can POST directly to the webhook endpoint with:
- `repository.owner.login` = `"orgA"` (so `verify_signature` resolves and validates against orgA's own known secret — signature passes)
- `repository.full_name` = `"victim-org/victim-repo"` (an arbitrary repository already configured as a Stack in the same Shipit instance, but belonging to a different organization)

The signature check succeeds (computed correctly with orgA's secret), but the handler dispatched afterward (e.g. `PushHandler`) resolves stacks using `repository.full_name`, which points to the victim's repository, not orgA's.

### Impact Explanation
This lets an attacker who controls one legitimate onboarded organization forge webhook events (push, status, check_suite, membership, pull_request, etc.) that are processed against **any other repository/stack already configured in the same Shipit instance**, despite the signature only proving control of their own org's secret. Depending on which handler is targeted, this can force unauthorized sync/deploy-trigger flows for a cross-repository/cross-organization Stack — an authentication-boundary bypass where a credential valid for org A is treated as authorization to act on org B's repository, matching the "Critical: cross-repository writes / unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires only that the Shipit instance serves more than one GitHub organization, that the attacker's organization is one of the onboarded ones (a normal, unprivileged deployment state, not requiring any secret/token theft or repository write access to the victim's repo), and that the attacker can send a raw HTTP POST to the public `/webhooks` endpoint (`WebhooksController#create` is not protected by CSRF and is publicly routable). No privileged Shipit session, `ApiClient` token, or GitHub App private key is required — only knowledge of the attacker's own webhook secret, which they legitimately possess.

### Recommendation
Bind the value used to select the verification secret to the value later used to resolve the target repository/stack. Concretely, `WebhooksController#verify_signature` should derive `repository_owner` from the same `repository.full_name` field the handlers use (or handlers should re-validate that the resolved stack's repository owner matches the organization whose secret validated the signature) before dispatching to any handler.

### Proof of Concept
1. Register/onboard organization `orgA` on the shared Shipit instance; obtain its `webhook_secret` (legitimately known, since the attacker configured the webhook for their own org).
2. Craft a JSON payload: `{"ref": "refs/heads/master", "after": "<attacker sha>", "repository": {"owner": {"login": "orgA"}, "full_name": "victim-org/victim-repo"}}`.
3. Compute `X-Hub-Signature` as `sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>`.
4. POST to `/webhooks` with header `X-Github-Event: push` and the above body/signature.
5. `verify_signature` resolves `Shipit.github(organization: "orgA")` and validates successfully against `orgA`'s secret.
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and triggers `stack.sync_github(expected_head_sha: ...)` on the victim's stack, despite the signature only proving knowledge of orgA's secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
