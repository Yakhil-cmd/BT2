### Title
Fee-on-Transfer ERC20 Token Causes Counterpart Bridge Reserve Drain in Lock Mode — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`BridgeTransferERC20.requestERC20Transfer` pulls `_value + _feeLimit` from the caller via `safeTransferFrom`, but if the registered ERC20 token deducts a transfer fee, the bridge contract receives less than `_value + _feeLimit`. The `RequestValueTransfer` event is still emitted with the full caller-supplied `_value`, and the counterpart bridge's `handleERC20Transfer` unconditionally releases that full `_value` to the recipient. In lock mode this silently drains the counterpart bridge's reserves by the token's transfer-fee amount on every cross-chain request.

### Finding Description

`requestERC20Transfer` in `BridgeTransferERC20.sol` performs a single `safeTransferFrom` for `_value + _feeLimit` and then immediately calls `_requestERC20Transfer` with the same `_value`: [1](#0-0) 

No balance snapshot is taken before or after the pull. If the token charges a percentage fee on every transfer (fee-on-transfer tokens), the bridge receives `_value + _feeLimit - Δ` where `Δ` is the token's own transfer fee. The function then proceeds to:

1. Pay the bridge's own ERC20 fee to `feeReceiver` and refund the remainder of `_feeLimit` to the caller via `_payERC20FeeAndRefundChange`: [2](#0-1) 

2. Emit `RequestValueTransfer` with the original `_value` (not the actually-received amount): [3](#0-2) 

The counterpart bridge's operator reads `valueOrTokenId` from that event and calls `handleERC20Transfer` with the same `_value`: [4](#0-3) 

`handleERC20Transfer` then releases the full `_value` to the recipient with no further check: [5](#0-4) 

**Lock mode (non-mintBurn):** The source bridge locked `_value - Δ` tokens but the counterpart bridge released `_value` tokens. The counterpart bridge's reserve is short by `Δ` per transaction. After N transfers the counterpart bridge holds `N * Δ` fewer tokens than it should, eventually becoming unable to fulfill legitimate redemptions — locking user funds on the source chain permanently.

**MintBurn mode:** After paying fees/refunds the bridge holds `_value - Δ` tokens, then attempts `ERC20Burnable(_tokenAddress).burn(_value)`: [6](#0-5) 

Since the bridge only holds `_value - Δ < _value`, the burn underflows and the transaction reverts — a complete DoS for fee-on-transfer tokens in mintBurn mode.

### Impact Explanation

In lock mode: the counterpart bridge's ERC20 reserve is drained by `Δ` per cross-chain transfer. Any user who legitimately deposited tokens and later tries to redeem them may find the counterpart bridge insolvent — their tokens are permanently locked on the source chain. This is an unauthorized drain of bridged assets from the counterpart bridge's custody.

### Likelihood Explanation

Fee-on-transfer ERC20 tokens (deflationary tokens, tokens with auto-liquidity mechanisms) are a well-known token class. The bridge's `registerToken` function places no restriction on token type. Any operator who registers such a token, or any user who interacts with an already-registered fee-on-transfer token, triggers the drain. No special privilege beyond being a normal bridge user is required.

### Recommendation

Measure the actual amount received by comparing the bridge's token balance before and after the `safeTransferFrom`, and use that measured amount — not the caller-supplied `_value` — as the value recorded in `RequestValueTransfer`. For example:

```solidity
function requestERC20Transfer(...) public {
    uint256 balBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balBefore);
    // derive actual _value and _feeLimit from actualReceived, or revert if actualReceived < _value.add(_feeLimit)
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, actualValue, actualFeeLimit, _extraData);
}
```

Alternatively, document that fee-on-transfer and rebasing tokens must not be registered, and add a guard in `registerToken` that reverts if the token exhibits fee-on-transfer behavior (e.g., by performing a test transfer and checking the received amount).

### Proof of Concept

Assume a fee-on-transfer token with a 1% transfer fee is registered on both bridge sides in lock mode.

1. Alice calls `requestERC20Transfer(token, Bob, 100e18, 0, "")` on the source bridge.
2. `safeTransferFrom(Alice, bridge, 100e18)` executes; the token deducts 1%, so the source bridge receives `99e18`.
3. `_payERC20FeeAndRefundChange` pays 0 fee (feeLimit = 0), no refund.
4. `RequestValueTransfer` is emitted with `valueOrTokenId = 100e18`.
5. The bridge operator calls `handleERC20Transfer(..., Bob, token, 100e18, ...)` on the counterpart bridge.
6. `safeTransfer(Bob, 100e18)` executes; the counterpart bridge's reserve decreases by `100e18`.
7. Net: source bridge locked `99e18`, counterpart bridge released `100e18`. Counterpart bridge is short `1e18` per transfer.
8. After 100 such transfers the counterpart bridge is short `100e18` tokens. The next legitimate redeemer whose counterpart bridge balance is insufficient cannot withdraw — their source-chain deposit is permanently locked. [7](#0-6) [5](#0-4)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
