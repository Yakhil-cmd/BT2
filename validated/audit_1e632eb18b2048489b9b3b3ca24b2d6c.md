### Title
SSRF via attacker-controlled `arbiter_address` in arbiter contracts leading to unrestricted HTTP requests to ArbStore/arbiter URLs - (File: arbiters.js, arbiter_contract.js)

### Summary
`arbiters.getInfo`/`getArbstoreInfo` and `arbiter_contract.openDispute`/`appeal`/`getAppealFee`/`getArbstoreAddresses` resolve a URL for a given `arbiter_address` via `device.requestFromHub("hub/get_arbstore_url", ...)` and then issue outbound HTTP(S) requests to that URL with no validation that the URL/host is a legitimate external service (no scheme allow-list, no private/loopback/link-local IP filtering). The `arbiter_address` that seeds this lookup originates from the `arbiter_contract_offer` device message, which any paired correspondent (an unprivileged peer) can send with an arbitrary address of their choosing.

### Finding Description
When a peer (any paired device, not necessarily a trusted counterparty) sends an `arbiter_contract_offer` message, the receiving wallet only validates that `arbiter_address` is a syntactically valid Obyte address [1](#0-0) . It does not verify that this address corresponds to a legitimate, registered arbiter. The contract, including the attacker-chosen `arbiter_address`, is then stored locally [2](#0-1) .

Later, when the local wallet (or an automatic flow such as `arbiters.getInfo`, which is invoked from `openDispute`) needs arbiter details, it asks the hub for the URL associated with the attacker-supplied arbiter address: [3](#0-2) 
and then performs a raw `https.get`/`http.request` to that URL with no host/scheme validation: [4](#0-3) [5](#0-4) 

The only check performed on the returned URL is `isNonemptyString(url)` [6](#0-5) ; there is no restriction preventing the URL from pointing to `http://127.0.0.1/...`, `http://169.254.169.254/...` (cloud metadata), or other internal/private services reachable from the victim's node. The same unauthenticated resolve-then-fetch pattern is repeated for dispute/appeal flows in `arbiter_contract.js` (`openDispute`, `appeal`, `getAppealFee`, `getArbstoreAddresses`) [7](#0-6) [8](#0-7) .

This mirrors the reported bug class (CWE-918/SSRF): user- or peer-controlled input drives an outbound HTTP fetch without validating the destination, allowing the requester's own infrastructure to be used to reach internal-only endpoints.

### Impact Explanation
An attacker who is merely a paired device correspondent (no special privileges) can name themselves or a colluding address as `arbiter_address` in an `arbiter_contract_offer`. If the victim's hub returns an attacker-influenced or attacker-registered arbstore URL for that address (arbiter registration with the hub is itself not shown here to be strongly authenticated/verified against the hub-trust boundary the wallet relies on), the victim wallet's Node.js process will issue outbound HTTP(S) requests to that URL when displaying arbiter info or engaging in the dispute/appeal flow. This can be used to:
- Probe/attack internal network services or cloud metadata endpoints from the victim's machine (SSRF).
- Exfiltrate contract data (title, text, contact info, decrypted contract content, and — for private assets — asset/amount) to an attacker-controlled endpoint (`openDispute`/`appeal` POST bodies), since the URL used to POST this JSON is resolved via the attacker-associated `arbiter_address` and has no host allow-list [9](#0-8) .

This does not, by itself, produce a double-spend or supply inflation, but it does allow unauthorized data disclosure and internal network reconnaissance/attack triggered purely by an unprivileged peer message, which is a legitimate Medium-severity SSRF impact analogous to the reported vulnerability.

### Likelihood Explanation
Likelihood is moderate: it requires (1) the victim to already be paired with the attacker's device (a normal, low-barrier action in Obyte chat/wallet), and (2) the attacker to control or point at an `arbiter_address` whose arbstore URL (as resolved by the victim's hub) is attacker-chosen. Because the hub-side registration/lookup logic for `hub/get_arbstore_url` is not enforced client-side beyond the non-empty-string check, and no code path in `arbiters.js`/`arbiter_contract.js` validates the resolved host against a safe list or blocks private IP ranges, the client fully trusts whatever URL is returned and fetches it automatically as part of routine arbiter-contract handling.

### Recommendation
- Validate the arbstore/arbiter URL returned by `hub/get_arbstore_url` before use: enforce `https://` only, resolve and reject private/loopback/link-local/multicast IP ranges (RFC1918, 127.0.0.0/8, 169.254.0.0/16, ::1, fc00::/7, etc.), and disallow redirects to such ranges.
- Maintain an allow-list or registry-verification mechanism so that arbitrary `arbiter_address` values supplied by a peer in `arbiter_contract_offer` cannot cause the wallet to contact attacker-chosen hosts.
- Apply the same URL/IP validation used elsewhere in the codebase for `device_hub` (`network.isValidWsUrl`) to the URLs consumed in `arbiters.js`/`arbiter_contract.js`/`uri.js` `fetchUrl`.
- Add request timeouts and response size limits to all outbound HTTP calls in these files.

### Proof of Concept
1. Attacker pairs with victim's wallet as a normal correspondent.
2. Attacker sends `arbiter_contract_offer` device message with `arbiter_address` set to an address whose corresponding arbstore URL (as later resolved via the victim's hub) points to an internal service, e.g. `http://169.254.169.254` or `http://127.0.0.1:PORT`.
3. Victim wallet stores the contract after only syntactic validation [10](#0-9) .
4. When the victim's UI/flow calls `arbiters.getInfo(arbiter_address, ...)` (e.g., to show arbiter details) or the victim opens a dispute/appeal, the wallet calls `device.requestFromHub("hub/get_arbstore_url", arbiter_address, ...)` and then performs `http.get`/`https.get`/`httpRequest` directly on the returned URL with no destination validation [11](#0-10) [12](#0-11) .
5. The victim's node makes an outbound request to the internal/metadata endpoint, potentially leaking sensitive response data back through the `cb`/`resp` handling path, or exfiltrating contract JSON via `openDispute`/`appeal` POST bodies to the attacker-controlled endpoint.

Note: full confirmation of how `hub/get_arbstore_url` is populated/authenticated server-side (i.e., whether a hub enforces stricter binding between `arbiter_address` and a vetted arbstore URL) could not be completely traced within the indexed code; the client-side lack of destination validation in `arbiters.js` and `arbiter_contract.js` is confirmed directly from the code shown above.

function requestInfoFromArbStore(url, cb){
	http.get(url, function(resp){
		var data = '';
		resp.on('data', function(chunk){
			data += chunk;
		});
		resp.on('end', function(){
			try {
				cb(null, JSON.parse(data));
			} catch(ex) {
				cb(ex);
			}
		});
	}).on("error", cb);
}

function appeal(hash, cb) {
	getByHash(hash, function(objContract){
		if (objContract.status !== "dispute_resolved")
			return cb("contract can't be appealed");
		var command = "hub/get_arbstore_url";
		var address = objContract.arbiter_address;
		if (objContract.arbstore_address) {
			command = "hub/get_arbstore_url_by_address";
			address = objContract.arbstore_address;
		}
		device.requestFromHub(command, address, async function(err, url){
			if (err)
				return cb("can't get arbstore url:", err);
			err = await fillArbstoreAddresses(objContract);
			if (err)
				return cb(err);
			device.getOrGeneratePermanentPairingInfo(function(pairingInfo){
				var my_pairing_code = pairingInfo.device_pubkey + "@" + pairingInfo.hub + "#" + pairingInfo.pairing_secret;
				var data = JSON.stringify({
					contract_hash: hash,
					my_pairing_code: objContract.my_pairing_code,
					my_address: objContract.my_address,
					contract: {title: objContract.title, text: objContract.text, creation_date: objContract.creation_date, me_is_payer: objContract.me_is_payer, my_address: objContract.my_address, peer_address: objContract.peer_address, my_party_name: objContract.my_party_name, peer_party_name: objContract.peer_party_name, arbiter_address: objContract.arbiter_address, amount: objContract.amount, asset: objContract.asset},

		});
	});
}

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}
