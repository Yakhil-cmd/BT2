This confirms the vulnerability. The `Handler#stacks` (and thus `PushHandler`/`StatusHandler`) resolve the target repository from `payload.dig('repository', 'full_name')` [1](#0-0) , while the signature-verification step in `WebhooksController#verify_signature` selects which organization's GitHub App/webhook secret to check against based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) — a separate field in the same attacker-supplied JSON body [2](#0-1) . Since `raw_post` is parsed twice from the same unauthenticated request, an attacker who controls a Shipit-registered organization (and thus knows *that* organization's `webhook_secret`) can sign a payload whose `repository.owner.login` is their own org, while `repository.full_name` names a completely different, victim repository/stack. The signature check passes because it validates against the attacker's own org's secret, but the actual write (e.g. `stack.sync_github` in `PushHandler#process` [3](#0-2) , or `commit.create_status_from_github!` in `StatusHandler#process` [4](#0-3) ) is performed against the victim stack.

### Title
Webhook signature is verified against the payload's `repository.owner`/`organization` while the mutated stack is resolved from `repository.full_name`, allowing cross-repository writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` derives the GitHub App/organization whose `webhook_secret` is used to authenticate a webhook from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [5](#0-4) . The event handlers that actually act on the payload (`Handler#stacks`, used by `PushHandler` and others) instead resolve the target `Repository`/`Stack` from a different field in the same body: `payload.dig('repository', 'full_name')` [1](#0-0) . Nothing ties these two fields together, so the identity that is cryptographically authenticated is not the identity that is written to.

### Finding Description
The equality that should hold is: `organization whose secret authenticated the request == owner of the repository/stack that gets mutated`. In this codebase that becomes `params.dig('repository','owner','login') (or organization.login) == owner segment of payload.dig('repository','full_name')`, but this is never enforced.

The controller flow is:
1. `verify_signature` (a `before_action`) computes `repository_owner` from the untrusted JSON body and fetches `Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` against that organization's `webhook_secret` [6](#0-5) .
2. `create` re-parses the same `raw_post` and dispatches to handlers registered for the event, passing the full, untouched `params` hash [7](#0-6) .
3. Handlers such as `PushHandler` resolve the affected stacks purely via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and call `stack.sync_github` [3](#0-2) ; `StatusHandler` updates any `Commit` matching `params.sha` regardless of which repo it belongs to [4](#0-3) .

Because an attacker who owns/administers *any* organization/repository onboarded into this Shipit instance knows that org's `webhook_secret` (it is configured per-organization for legitimate use), they can produce a validly-signed webhook whose `repository.owner.login` names their own org (so verification succeeds) but whose `repository.full_name` names an unrelated victim repository/stack. The controller has no cross-check between the two.

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written," enabling cross-repository writes: an attacker can forge `push` events to trigger `stack.sync_github` on stacks they do not own, or forge `status` events to inject arbitrary commit statuses (`create_status_from_github!`) onto commits belonging to repositories/stacks they don't control, without ever holding a Shipit session, API token, or that victim org's actual `webhook_secret`.

### Likelihood Explanation
Medium-to-High: exploitation only requires the attacker to control (or have webhook-signing knowledge of) one organization already registered with this Shipit instance — a routine, low-privilege setup step for any tenant/org onboarded to a shared Shipit deployment — and to send a single crafted HTTP POST to the public `/webhooks` endpoint.

### Recommendation
After signature verification, re-derive `repository_owner` from the *same* field used by the handlers (`payload.dig('repository','full_name')`'s owner segment) and require it to match the organization whose secret validated the signature, rejecting the request (422) on mismatch. Equivalently, scope `Shipit.github(organization: ...)` lookup and the eventual `Repository.from_github_repo_name` lookup to the identical, single source field before any handler runs.

### Proof of Concept
1. Shipit hosts stacks for both `attacker-org/decoy` (attacker is admin, knows `webhook_secret` A) and `victim-org/victim-repo` (a stack the attacker has no access to).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known to exist in victim's commit history>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(secretA, body)` using their own known `webhook_secret` A, sets `X-Github-Event: push`, and POSTs to `/webhooks`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")`, verifies successfully against `secretA` [8](#0-7) .
5. `create` dispatches to `PushHandler`, which resolves stacks from `full_name = "victim-org/victim-repo"` and calls `sync_github`, mutating state on a repository the attacker never authenticated for [3](#0-2) .
