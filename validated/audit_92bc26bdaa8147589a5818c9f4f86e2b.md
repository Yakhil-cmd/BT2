### Title
Webhook signature verified against `repository.owner.login`'s secret while all event handlers act on the unrelated `repository.full_name` field, allowing an org with a legitimate Shipit-configured webhook to forge writes against any other repository's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to validate an inbound GitHub webhook based on `repository.owner.login` in the JSON body, but every webhook handler (`Shipit::Webhooks::Handlers::Handler#repository_name` and its callers) resolves the target `Repository`/`Stack` from the *separate* `repository.full_name` field in the same body. Nothing binds these two fields together beyond "same JSON blob" — an org that legitimately owns a Shipit-configured webhook secret can therefore forge a payload where `repository.owner.login` names its own org (so the signature check passes with a secret it legitimately possesses) while `repository.full_name` names a completely different, victim repository whose stacks/commits get mutated.

### Finding Description
`verify_signature` computes the app/secret to check the signature against using only the owner login: [1](#0-0) [2](#0-1) 

Every handler, however, resolves which repository/stack to operate on using an entirely different field of the same payload, `repository.full_name`: [3](#0-2) 

This is used directly by `PushHandler` (triggers `stack.sync_github`, which can lead to `GithubSyncJob` appending commits and enqueuing `CacheDeploySpecJob`, and can unblock continuous deployment): [4](#0-3) [5](#0-4) 

and by pull-request handlers that mutate stack state directly on a repository resolved from `full_name`, e.g. archiving/unarchiving review stacks: [6](#0-5) [7](#0-6) 

The invariant this exploits is exactly analogous to the reported bug class: the security check ("does this request come from an authorized organization?") is computed and validated on one piece of state (`repository.owner.login`, tied to a specific per-organization `webhook_secret` in `Shipit.github(organization:)`), while the state actually acted upon (`repository.full_name` → looked-up `Repository`/`Stack`) is a different field that is never cross-checked against the authenticated organization. This breaks the intended binding: `organization authenticated == repository written`. An organization X that is legitimately onboarded to this Shipit instance (and therefore knows its own `webhook_secret`, since it or its admin configured that webhook on GitHub) can sign a payload with `repository.owner.login = "X"` (so `Shipit.github(organization: "X")` uses X's own secret and the HMAC check passes) but set `repository.full_name = "victim-org/victim-repo"`, causing handlers to operate on victim-org's stacks.

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy" bar explicitly called out as Critical impact. A push-event forgery can trigger `sync_github` on a victim stack, appending GitHub-fetched commits and — if the victim stack has `continuous_deployment` enabled — cause an unauthorized deploy to be triggered on a repository the attacker's organization has no legitimate relationship with. Pull-request-event forgeries can archive/unarchive review stacks or mutate `PullRequest` records belonging to the victim repository. This is a cross-tenant write primitive gated only by "does the attacker's own organization have *any* webhook secret configured in this multi-tenant Shipit instance," not by any relationship to the victim repository.

### Likelihood Explanation
Requires the attacker to control (or be) an organization already onboard on the same Shipit instance with a configured `webhook_secret` for their own repositories — a low bar for any multi-tenant Shipit deployment serving multiple orgs, and importantly does not require compromising the victim's webhook secret, GitHub App key, or any Shipit session/API token. The attacker only needs to know the field names `repository.owner.login` vs `repository.full_name` are decoupled, which is straightforward from reading this controller and handler code.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), require that the organization portion of `repository.full_name` matches `repository.owner.login` (or, better, derive the target repository lookup solely from the same authenticated owner login) before dispatching to handlers, rejecting payloads where they diverge.

### Proof of Concept
1. Org `attacker-org` is onboarded to the shared Shipit instance and knows its own `webhook_secret` (as configured for its GitHub webhook integration).
2. Attacker crafts a `push` event payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<any sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` and sends it to `POST /webhooks` with `X-Github-Event: push` and the computed `X-Hub-Signature`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository_owner`) and validates the signature successfully against the attacker's own secret — see `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`, `app/models/shipit/stack.rb:612-614`), triggering `GithubSyncJob` and potentially a continuous deployment on a repository the attacker does not own.
