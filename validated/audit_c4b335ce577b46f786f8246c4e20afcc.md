### Title
Cross-tenant PullRequest forgery via mismatched `repository.owner.login` / `repository.full_name` and no-secret organization signature bypass - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) using `params.dig('repository','owner','login')`, while `Shipit::Webhooks::Handlers::PullRequest::AssignedHandler` resolves the target `Repository`/`Stack`/`PullRequest` using the independent field `params.repository.full_name`. Because these two attacker-controlled JSON fields are never checked for consistency, and because `GitHubApp#verify_webhook_signature` trivially returns `true` when the resolved organization has no `webhook_secret` configured, an attacker can forge a `pull_request` "assigned" webhook that authenticates against a no-secret organization while targeting and mutating a `PullRequest` record belonging to a completely different, secured organization/repository.

### Finding Description
The broken invariant is: *the organization whose `webhook_secret` verified the request* (`org_verify = params.dig('repository','owner','login')`) *must equal the organization that owns the repository/stack the handler writes* (`org_write = Repository.from_github_repo_name(params.repository.full_name).owner`). The code never enforces `org_verify == org_write`.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from `params.dig('repository','owner','login')` (or `organization.login`) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(header, raw_post)`.
2. `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) does `return true unless webhook_secret` — if the selected org has no configured `webhook_secret`, **any** signature (or even a garbage one) is accepted, and only `sha1=` is ever checked otherwise (the modern `X-Hub-Signature-256` is never inspected at all).
3. Once verification passes, `WebhooksController#create` parses the raw body and dispatches it to `Shipit::Webhooks::Handlers::PullRequest::AssignedHandler#process` (`app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb:41-45`).
4. `AssignedHandler#repository` calls `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — a completely separate, attacker-controlled field from the one used in step 1 — to find the `PullRequest` via `joins(:stack, stack: :repository)` and then calls `pull_request.update(github_pull_request: params.pull_request)`.

Exploit: the attacker sends a JSON body where `repository.owner.login = "attacker-org"` (an org configured in Shipit but with no `webhook_secret`, or any string, causing `verify_webhook_signature` to short-circuit `true` for that org), but `repository.full_name = "victim-org/victim-repo"`, matching a real tracked `Repository`/`Stack`/`PullRequest` belonging to a different, secured organization. `X-Github-Event: pull_request` and `X-Hub-Signature: sha1=anything` (or an org with no secret makes the value irrelevant). No `webhook_secret` for `victim-org` is ever checked because `repository_owner` used for verification is derived only from the (attacker-forged) `repository.owner.login`, not from `repository.full_name`.

Existing guards fail to catch this because: `verify_signature` only validates that *some* HMAC matches for the organization named in one attacker-controlled field, `drop_unhandled_event`/`ExplicitParameters` only validate the payload shape (not org-repository consistency), and `AssignedHandler` has no independent check that the verified organization matches the repository it is about to mutate.

### Impact Explanation
An attacker who controls no secrets at all can cause the Shipit instance to mutate `PullRequest` records for a different, secured tenant/repository by exploiting a no-secret (or attacker-registered) organization entry as a signature-bypass "key" while pointing the payload body at the victim's `repository.full_name`. This is a cross-tenant state-manipulation bug matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"), since `PullRequest#github_pull_request` is overwritten with attacker-chosen JSON (`title`, `state`, `head.sha`, `head.ref`, `assignees`, `labels`, `additions`/`deletions`) for a repository the attacker never authenticated against. This is repeatable against any stack/PR whose `number` and repo `full_name` the attacker can guess or discover.

### Likelihood Explanation
The bypass requires: (a) the target Shipit deployment supports multiple GitHub organizations (`github_default_organization` non-nil) and has at least one configured organization whose `webhook_secret` is unset/blank — a realistic misconfiguration for legacy/optional orgs — or that the attacker's own organization is registered without a secret; and (b) a target `PullRequest` matching `number` + a tracked repository `full_name`. No Shipit session, API token, or GitHub secret is needed; the attacker only needs to send one crafted HTTP POST, making this low-cost and fully repeatable.

### Recommendation
Enforce that the organization derived from `repository.full_name` (or the repository actually resolved by the handler) matches the organization used to select the `webhook_secret` in `verify_signature`, e.g., derive `repository_owner` consistently from a single trusted field and reject payloads where `repository.full_name`'s owner segment does not match `repository.owner.login`. Additionally, `GitHubApp#verify_webhook_signature` should not silently accept unsigned/no-secret payloads (`return true unless webhook_secret`) — organizations without a configured secret should reject signature-bearing requests, or webhook_secret should be mandatory per-organization. Also support and check the modern `X-Hub-Signature-256` header.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (ActionDispatch::IntegrationTest style)
test "forged pull_request assigned webhook mutates a different org's PullRequest" do
  victim_stack = shipit_stacks(:shipit) # owned by "shopify" org with a real webhook_secret
  victim_pr = shipit_pull_requests(:one) # belongs to victim_stack, number: 42

  # Configure "attacker-org" with NO webhook_secret in secrets.github
  # (simulate via Shipit.stubs(:github) or fixture secrets)

  body = {
    action: 'assigned',
    number: victim_pr.number,
    pull_request: {
      id: 999, number: victim_pr.number, url: 'https://api.github.com/x',
      title: 'FORGED TITLE', state: 'open', additions: 1, deletions: 1,
      head: { sha: 'deadbeef', ref: 'evil-branch' },
      user: { login: 'attacker' },
      assignees: [{ login: 'attacker' }],
      labels: []
    },
    repository: { owner: { login: 'attacker-org' }, full_name: 'shopify/shipit-engine' }, # mismatch!
    sender: { login: 'attacker' }
  }.to_json

  post '/webhooks',
    params: body,
    headers: {
      'X-Github-Event' => 'pull_request',
      'X-Hub-Signature' => 'sha1=0000000000000000000000000000000000000000', # irrelevant, attacker-org has no secret
      'Content-Type' => 'application/json'
    }

  assert_response :ok
  victim_pr.reload
  assert_equal 'FORGED TITLE', victim_pr.title # victim's PR mutated by attacker-org's unverified payload
end
```
This demonstrates `org_verify` ("attacker-org", unverified/no-secret) diverging from `org_write` ("shopify", the org actually owning the mutated `PullRequest`), confirming the broken invariant.
