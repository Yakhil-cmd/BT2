### Title
KLAY Bridge Fallback Function Hardcodes `msg.sender` as Counterpart-Chain Destination, Causing Permanent Asset Loss for Smart Contract Wallet Users — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`BridgeTransferKLAY`'s fallback function unconditionally uses `msg.sender` as the destination address on the counterpart chain. When the caller is a smart contract wallet (multisig, AA wallet), the same address on the counterpart chain may not exist or may be controlled by a completely different party, causing the bridged KLAY to be permanently lost or transferred to an unintended recipient.

---

### Finding Description

The fallback function in `BridgeTransferKLAY.sol` is:

```solidity
// () requests transfer KLAY to msg.sender address on relative chain.
function () external payable {
    _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
}
``` [1](#0-0) 

`_requestKLAYTransfer` then emits the cross-chain request with `_to = msg.sender`:

```solidity
emit RequestValueTransfer(
    TokenType.KLAY,
    msg.sender,   // from
    _to,          // to = msg.sender (set by fallback)
    address(0),
    msg.value.sub(_feeLimit),
    requestNonce,
    fee,
    _extraData
);
``` [2](#0-1) 

The bridge operator's Go relay picks up this event and calls `handleKLAYTransfer` on the counterpart bridge with the same `to` address:

```go
handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
``` [3](#0-2) 

`handleKLAYTransfer` then sends KLAY directly to `_to` via a low-level call:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [4](#0-3) 

The `requestKLAYTransfer` function correctly allows the caller to specify an explicit `_to`:

```solidity
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
``` [5](#0-4) 

Only the fallback path hardcodes `msg.sender` as the destination, providing no way for the caller to specify a different counterpart-chain address.

---

### Impact Explanation

When a smart contract wallet (Gnosis Safe, AA wallet, or any multisig) sends KLAY directly to the bridge contract (triggering the fallback), the bridge records `msg.sender` — the smart contract wallet's address — as the destination on the counterpart chain. Smart contract wallets are not guaranteed to be deployed at the same address on every chain (deployment depends on factory address, salt, and bytecode). Two outcomes are possible:

1. **Permanent loss**: No contract exists at that address on the counterpart chain. The `handleKLAYTransfer` low-level call succeeds (ETH/KLAY sent to an EOA-like empty address), but no one controls it.
2. **Theft**: A different EOA or contract happens to exist at the same address on the counterpart chain and receives the KLAY.

The corrupted value is the full bridged KLAY amount sent to the wrong `_to` address on the counterpart chain — an unauthorized transfer of bridged KLAY assets.

---

### Likelihood Explanation

Multisig and AA wallets are increasingly common in DeFi. The fallback function is a natural UX path (send ETH/KLAY to a contract address). A user operating a Gnosis Safe on the source chain who sends KLAY to the bridge address directly will silently trigger this path. There is no on-chain warning or revert. The loss is irreversible once the operator relays the event.

---

### Recommendation

Remove the fallback function's implicit `msg.sender` destination, or require callers to use `requestKLAYTransfer` with an explicit `_to` address. If the fallback must be retained for backwards compatibility, add a check that `msg.sender` is an EOA (e.g., `require(msg.sender == tx.origin, "use requestKLAYTransfer for contract wallets")`), or emit a warning event. The safest fix is to deprecate the fallback and require explicit destination specification via `requestKLAYTransfer`.

---

### Proof of Concept

1. Alice operates a Gnosis Safe at `0xAAA...` on the service chain (source).
2. Alice's Safe sends 10 KLAY directly to the bridge contract address, triggering the fallback.
3. The bridge emits `RequestValueTransfer` with `from = 0xAAA...`, `to = 0xAAA...`.
4. The bridge operator relays the event and calls `handleKLAYTransfer` on the parent chain (destination) with `_to = 0xAAA...`.
5. Bob controls EOA `0xAAA...` on the parent chain (same address, different controller — no Safe deployed there).
6. `handleKLAYTransfer` executes `_to.call.value(10 KLAY)("")` — succeeds, Bob receives 10 KLAY.
7. Alice's 10 KLAY is permanently transferred to Bob with no recourse.

The root cause is exclusively in `contracts/service_chain/bridge/BridgeTransferKLAY.sol` line 128, where `msg.sender` is passed as `_to` without any validation that the caller controls the same address on the counterpart chain.
