### Title
Integer-Division Truncation in `calculate_alpenglow_points` Silently Zeroes Small Delegators' Staking Rewards - (File: runtime/src/inflation_rewards/points.rs)

### Summary
`calculate_alpenglow_points` computes a delegator's earned reward for an Alpenglow epoch as `earned_credits * stake_amount / total_stake`, with `earned_credits` bounded by slots-per-epoch (~hundreds of thousands) and `total_stake` being a validator's total delegated stake (which can reach many millions of SOL, i.e. up to ~10^16+ lamports). Unlike the sibling reward paths in this codebase (`calculate_reward` in `vote_reward.rs`, `calculate_block_reward` in `calculation.rs`, and `commission_split`/`commission_split_preserve_lamports` in `inflation_rewards/mod.rs`), which explicitly reorder multiplication/division or use a "preserve lamports" remainder-assignment scheme to avoid losing whole-lamport rewards, `calculate_alpenglow_points` has no analogous safeguard. This is the same bug class as HAL-08: a reward-accrual division whose denominator can dwarf the numerator, causing legitimate stakers to be truncated to zero.

### Finding Description
In `calculate_alpenglow_points`, the reward for the epoch is:

```
earned_points = earned_credits * stake_amount / total_stake
``` [4](#0-3) 

`earned_credits` is per-epoch validator-vote credits (bounded roughly by the number of slots in an epoch), and `stake_amount` is the individual delegation's effective stake. `total_stake` is the validator's total delegated stake for the reward epoch, looked up from `reward_epoch_delegated_stakes`. For a small delegator (e.g., near the minimum stake amount) delegated to a large validator, `earned_credits * stake_amount` can be smaller than `total_stake`, causing the division to truncate to exactly `0`.

Crucially, in the `Alpenglow` branch of `calculate_stake_rewards`, `ag_points` **is** the final lamport reward — it is not later re-scaled by a `PointValue` ratio the way Tower-epoch points are: [2](#0-1) 

When `ag_points == 0`, the code calls `skip_reward(SkippedReason::ZeroPoints)`. Because this is not a Tower epoch, `advance_credits_for_skipped_reward` evaluates true whenever `new_credits_observed != stake.credits_observed` (which it will, since credits were legitimately earned that epoch), so `credits_observed` is advanced to consume that epoch's credits while paying `staker_rewards: 0, voter_rewards: 0`: [5](#0-4) 

Once `credits_observed` advances past those credits, they can never be redeemed again — the reward for that epoch is permanently and silently forfeited for that delegator, exactly mirroring the HAL-08 pattern where `accHaloPerShare` truncates to zero once total stake grows large relative to the reward rate, silently denying legitimate stakers their due rewards.

By contrast, the codebase's other reward-splitting logic explicitly guards against this exact class of bug:
- `calculate_reward` in `vote_reward.rs` multiplies the full reward numerator before dividing by the full stake-weighted denominator in `u128`, explicitly commented as "changes the order of operations to maintain precision." [6](#0-5) 
- `calculate_block_reward` similarly does `pending_delegator_rewards * stake / total_active_stake` in one `u128` expression, and any truncation there is non-destructive because `pending_delegator_rewards` remains in the vote account to be split again in future blocks — it isn't a one-shot, credits-consuming redemption. [7](#0-6) 
- `commission_split_preserve_lamports` was specifically introduced to assign fractional-remainder lamports to the voter "so no lamports are lost" for non-Tower epochs. [8](#0-7) 

`calculate_alpenglow_points` has none of these mitigations, and its result is consumed as a final, one-shot, credit-consuming reward amount rather than a value that persists in a redistributable pool.

### Impact Explanation
This results in misattributed/lost staking rewards: legitimate, unprivileged delegators with small stake relative to their chosen validator's total stake receive zero rewards for epochs where integer division truncates their share to zero, and the underlying credits are irrecoverably consumed (`new_credits_observed` still advances). The lamports that should have been paid to these stakers are not preserved anywhere (unlike the block-reward path's persistent `pending_delegator_rewards` pool) — they are effectively lost from the reward-distribution accounting for that stake account, a permanent denial of legitimately earned rewards for affected accounts. This falls within the "misattributed rewards" class of impact the review criteria calls out, occurring in the stake/epoch reward distribution path, reachable by any staker without special privileges.

### Likelihood Explanation
The bug triggers whenever a delegator's `earned_credits * stake_amount < total_stake` for the reward epoch. Given a fully-voting validator earning on the order of a few hundred thousand credits per epoch, and total delegated stake to large validators readily reaching the 10-million-SOL range, delegations near the network's minimum stake amount (or vote accounts recently receiving very few credits due to partial-epoch activation or brief delinquency) will realistically hit this truncation. This does not require adversarial behavior — it occurs during ordinary epoch-reward computation for any sufficiently small delegation to a sufficiently large validator, making it a live, non-theoretical condition of the Alpenglow rewards path.

### Recommendation
Rework `calculate_alpenglow_points` to avoid destructive truncation in the same way the sibling reward functions already do:
1. Preserve full precision by deferring the division as long as possible, or represent points in a fixed-point/points-based unit disjoint from lamports (as the Tower epoch already does via `PointValue`), so a follow-on multiplication by total epoch rewards over total points doesn't collapse small shares to zero.
2. Alternatively, do not advance `credits_observed` for stakes whose truncated reward is zero purely due to division rounding (mirroring the Tower path's `TooEarlyUnfairSplit` deferral in `commission_split`/`calculate_stake_rewards`), so the earned credits remain redeemable in a future epoch once enough credits have accumulated to produce a nonzero reward.
3. Or adopt the `commission_split_preserve_lamports`-style remainder handling so fractional lamports are not simply discarded for delegators.

### Proof of Concept
Given (all values as used by `calculate_alpenglow_points`, `runtime/src/inflation_rewards/points.rs:243-312`):
- `total_stake` (validator's total delegated stake) = 10,000,000 SOL = 1e16 lamports
- `stake_amount` (a single small delegator's effective stake) = 1 SOL = 1e9 lamports
- `earned_credits` for the epoch = 432,000 (typical full-epoch credit count)

```
earned_points = earned_credits * stake_amount / total_stake
              = 432_000 * 1_000_000_000 / 10_000_000_000_000_000
              = 432_000_000_000_000 / 10_000_000_000_000_000
              = 0   (truncated)
```

Because `ag_points == 0`, `calculate_stake_rewards` (`runtime/src/inflation_rewards/mod.rs:278-285`) returns a `CalculatedStakeRewards { staker_rewards: 0, voter_rewards: 0, new_credits_observed }` via `skip_reward`, advancing `credits_observed` for that stake account past the epoch's earned credits while paying zero lamports — the earned reward for that epoch is permanently lost for this delegator, even though the delegator legitimately participated in staking that epoch.

/// returns commission split as (voter_portion, staker_portion, was_split) tuple,
/// assigning any fractional-lamport remainder to the voter so no lamports are lost.
///
/// This is used only for non-Tower epochs, where small unfair splits no longer defer redemption.
#[cfg_attr(any(test, feature = "dev-context-only-utils"), qualifiers(pub(crate)))]
fn commission_split_preserve_lamports(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let staker_bps = MAX_BPS
                .checked_sub(split)
                .expect("commission cannot be greater than MAX_BPS");
            let staker_rewards = u128::from(on)
                .checked_mul(u128::from(staker_bps))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let staker_rewards = staker_rewards as u64;
            let voter_rewards = on
                .checked_sub(staker_rewards)
                .expect("staker rewards cannot exceed total rewards");

            (voter_rewards, staker_rewards, true)
        }
    }
