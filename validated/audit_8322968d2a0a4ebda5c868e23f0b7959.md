### Title
Global `Commit.where(sha:)` lookup in `StatusHandler#process` lets any authenticated-per-org webhook forge CI status on unrelated stacks sharing that sha - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit(s) solely by `sha`, with no `stack_id` or repository scoping, even though the `commits` table only enforces sha uniqueness per `(stack_id, sha)` via a composite unique index. A webhook attacker who controls a repository tracked by Shipit can trigger a status webhook whose signature is valid for their own organization, yet the handler will write/mutate `Status` rows on **every** `Commit` record across **every** stack that happens to share that 40-character sha, including unrelated repositories' commits.

### Finding Description
The broken binding is: `StatusHandler#process` assumes `sha == 1 commit == 1 repository`, while the DB invariant declared in `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb` is only `unique on (sha, stack_id)`. These are not equal — the same 40-char sha can legitimately exist in multiple stacks (e.g., forks sharing a common base commit, cherry-picked/rebased commits, or a base commit reused across many repos that Shipit tracks).

Code path:
- `app/controllers/shipit/webhooks_controller.rb#verify_signature` validates `X-Hub-Signature` against the webhook secret configured for `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the payload's `repository.owner.login` [1](#0-0) [2](#0-1) . This check only proves the payload was sent by a GitHub App/webhook configured for the attacker's **own** organization — it says nothing about which `sha` values are legitimate to reference.
- Once verified, `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with `params` requiring only `:sha` and `:state` [3](#0-2) . There is no `stack_id`/repository filter joining back to the repository that signed the webhook.
- `Commit#create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` and triggers hooks (`Hook.emit(:commit_status, ...)`, `Hook.emit(:deployable_status, ...)`) and can call `stack.schedule_merges` [4](#0-3) [5](#0-4) . Since `deployable?` and continuous delivery both key off the commit's synthesized `status`, injecting a fabricated `state: "success"` status directly affects the unrelated commit's deployability, and (if `continuous_deployment?` is enabled on that other stack) can schedule a real deploy via `ContinuousDeliveryJob`.
- The unique index confirms the sha collision scenario is architecturally expected/allowed at the DB layer: `add_index :commits, %i(sha stack_id), unique: true` [6](#0-5)  — i.e., the same sha is permitted to exist under many different `stack_id`s simultaneously, which is exactly the condition `StatusHandler#process` fails to filter on.

Attacker's exact request: attacker copies any 40-char sha that is already imported as a `Commit` in a Shipit-tracked stack (e.g., a widely forked base commit, or any commit merged in the past into a repo tracked by Shipit) and creates a commit with that same sha as HEAD in their own repo/branch (trivial via `git commit --allow-empty` amend tricks are not even required if the sha is directly reused/cherry-picked without modification — reusing byte-identical parent/tree/commit metadata reproduces the sha exactly). Attacker then triggers any CI provider connected to their own repo (or crafts a raw `POST /webhooks` GitHub status payload with `sha`, `state`, `repository.owner.login` set to their own org) so it passes `verify_signature` for their own org's webhook secret. The `state`/`description`/`target_url`/`context` are fully attacker-controlled `ExplicitParameters` fields.

Existing guards do not prevent this: `verify_signature` only authenticates the sender's own organization, not the `sha` scope; `drop_unhandled_event` only checks event name; the `ExplicitParameters` schema only requires the two fields the attacker fully controls; there is no `stack`/`repository` binding check inside `StatusHandler#process` at all.

### Impact Explanation
A malicious/compromised webhook sender for their own tracked repository can inject arbitrary CI status (`success`/`failure`/`pending`, arbitrary `description`/`target_url`/`context`) onto **any other stack's commit** that shares the same sha, without ever authenticating to that other repository. This can: (1) mark an unrelated commit as CI-`success`, satisfying `Commit#deployable?` and, combined with `stack.continuous_deployment?`, trigger an actual automated deploy of that unrelated stack (`ContinuousDeliveryJob`) — an unauthorized deploy triggered by a payload not belonging to that stack's repository; (2) block/poison an unrelated commit as `failure`, denial of legitimate deploys. This matches "Critical - a payload for one repository mutating another's stack/commit ... or an unauthorized deploy" since it crosses tenant/repository boundaries and can cause an unauthorized deploy.

### Likelihood Explanation
Preconditions: the attacker must control (or have push access to / can trigger a CI webhook for) at least one repository that Shipit tracks, and a sha collision must exist — i.e., another tracked stack's `Commit` row shares the exact same sha. This is realistic for forked repos sharing base/ancestor commits, monorepo splits, or any workflow where commits are cherry-picked/imported byte-for-byte across repos tracked by the same Shipit instance (common in mono-org multi-repo CI setups). No secrets are required beyond what the attacker already legitimately holds for their own repo's webhook delivery. The attack is repeatable per matching sha and requires no elevated Shipit role.

### Recommendation
Scope the lookup in `StatusHandler#process` (and the `params.sha` search) by the repository the payload was verified for — join through the target stack's `Repository` (matching `full_name`/owner from the payload) instead of the bare `sha`, e.g., `Commit.joins(:stack).merge(Stack.where(...matching repository from payload...)).where(sha: params.sha)`, ensuring a `sha` match can only affect commits belonging to the stack whose repository actually emitted the verified webhook.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "process only updates the commit belonging to the reporting repository" do
  stack_a = shipit_stacks(:shipit) # tracks repo A
  stack_b = create_stack # tracks unrelated repo B

  shared_sha = "a" * 40
  commit_a = stack_a.commits.create!(sha: shared_sha, ...)
  commit_b = stack_b.commits.create!(sha: shared_sha, ...)

  params = ExplicitParameters wrapping({
    sha: shared_sha, state: "success",
    repository: { full_name: stack_a.repository.full_name }
  })

  Shipit::Webhooks::Handlers::StatusHandler.new(params).process

  assert_equal "success", commit_a.reload.status.state
  # BEFORE FIX: commit_b also flips to "success" though its stack never sent this webhook.
  refute_equal "success", commit_b.reload.status.state
end
```
Both sides of the invariant to assert: `commit_a.stack_id != commit_b.stack_id` while `commit_a.sha == commit_b.sha`, and after `process`, only the commit belonging to the verified repository/stack should be mutated.
