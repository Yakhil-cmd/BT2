### Title
Stack-scoped ApiClient can read any stack's ccmenu.xml (bypasses `stacks` scope) - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController#stack` overrides `BaseController#stack` and resolves the target directly via `Stack.from_param!(params[:stack_id])` instead of going through the `stacks` scope (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`). This lets an `ApiClient` restricted to a single stack read the CCMenu XML (deploy state/output) of any other stack.

### Finding Description
The intended binding is: for any request authenticated by an `ApiClient` with `stack_id` set, `stack == current_api_client.stack` for every read action — i.e., the resolved `stack` must be a member of the `stacks` scope defined in `app/controllers/shipit/api/base_controller.rb` lines 74-76 [1](#0-0) .

`CCMenuController` overrides both `authenticate_api_client` (reading the token from `params[:token]` instead of Basic Auth) and `stack`: [2](#0-1) 

The overridden `stack` method calls `Stack.from_param!(params[:stack_id])` directly, never touching `stacks`/`current_api_client.stack_id`. `require_permission :read, :stack` only checks that the client's `permissions` array contains `"read:stack"` via `ApiClient#check_permissions!`, which has no notion of which specific stack is authorized: [3](#0-2) 

So for a client with `permissions: ["read:stack"]` and `stack_id: A`, requesting `GET /stacks/:B_param/ccmenu.xml?token=...` succeeds and returns stack B's deploy XML: `check_permissions!` passes (permission name matches), and `stack` resolves to B unconditionally. Every other `require_permission :read, :stack` controller that inherits `BaseController#stack` (lines 78-80) is correctly scoped by `stacks`; only `CCMenuController` breaks this invariant.

### Impact Explanation
An attacker holding any `ApiClient` token with `read:stack` permission — even one deliberately scoped by an operator to a single stack via `stack_id` — can enumerate/read the CCMenu status (latest deploy/rollback id, `ended_at`, running state, and rendered project name/activity) of every other stack in the Shipit instance, not just their authorized one. This is an unauthenticated-by-scope information disclosure of deploy state across tenants/stacks, matching the "unauthenticated read of stack state ... deploy output" High severity category. It is fully repeatable against every stack `to_param` value the attacker can guess or enumerate (stack params are typically `owner/repo/env`, often guessable/public on GitHub).

### Likelihood Explanation
Precondition: attacker must already possess a valid `ApiClient` token (issued by an operator) scoped to one stack. Given that, exploitation costs one HTTP GET with the token as `params[:token]` (per `authenticate_api_client` override) and the target stack's param — no other secret or privilege is needed, and it works against any stack in the instance. This matches the rules' definition of "attacker holding a valid ApiClient token" as the scoped precondition, and the bypass is deterministic and repeatable.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped `stacks` helper instead of `Stack.from_param!` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, mirroring `BaseController#stack`, so `current_api_client.stack_id` scoping is enforced for CCMenu reads as well.

### Proof of Concept
Minitest plan (`test/controllers/api/ccmenu_controller_test.rb`):
1. Create `stack_a = shipit_stacks(:shipit)` and `stack_b = create(:stack)` (or two distinct fixtures).
2. Create an `ApiClient` with `permissions: ['read:stack']`, `stack_id: stack_a.id`.
3. `get ccmenu_api_stack_url(stack_b), params: { token: api_client.authentication_token }`.
4. Assert response is `403`/`404` (expected per the `stacks` binding: `stack == current_api_client.stack`), but current code returns `200` with `stack_b`'s CCMenu XML — demonstrating the divergence:
   - Before fix: `response.status == 200` and body contains `stack_b`'s project name — binding violated.
   - After applying the recommended fix (`stacks.from_param!`): request against `stack_b` with an `ApiClient` scoped to `stack_a` raises `ActiveRecord::RecordNotFound` → `404`, matching the binding.
