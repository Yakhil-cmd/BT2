### Title
Missing venue/pool allowlist on strategy routes lets a rogue hop attach unauthorized token transfers to the caller's signed auth tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The express-jwt bug class is "a security-restricting allowlist (`algorithms`) is not enforced, so attacker-supplied input selects an arbitrary validation/execution path, bypassing authorization." The direct analog: `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` accept arbitrary `StrategySwap` route bytes and forward them to the swap aggregator without constraining which pools or token contracts the route may invoke. Because Soroban records every `require_auth` the route triggers as a child of the caller's signed authorization tree, a crafted route executes `transfer(victim, attacker, amount)` on any token the victim holds — theft that neither the input-transfer auth, the payload `min_out`, nor the controller's risk gates bound.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` snapshots balances, calls `authorize_transfer_as_current` for exactly one `token_in -> router` transfer of `amount_in`, then calls `router.execute_strategy(&controller, &amount_in, swap)` with fully attacker/user-controlled bytes [1](#0-0) . The only post-checks are `RouterOverspend` on the input token and `NoSwapOutput` on the output token [2](#0-1) . Nothing restricts which contract addresses the route may name as pools or intermediate tokens; the threat model confirms "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" [3](#0-2) .

A rogue hop contract can therefore invoke `token.transfer(victim, attacker, n)` on an unrelated wallet token. The host attaches that invocation to the caller's `require_auth` tree; when simulation returns the poisoned tree and the caller (or wallet UX that does not decode nested entries) signs it, the transfer executes. The harness test proves both directions: the honest tree rejects the rogue transfer, and the simulation-returned tree authorizes it and drains the wallet [4](#0-3) .

This is precisely the express-jwt shape: just as a missing `algorithms` pin lets the attacker choose HS256, the missing venue allowlist lets the route author choose arbitrary callee code that consumes the caller's authorization scope beyond the single intended input transfer.

### Impact Explanation
Theft of user funds. The loss is the caller's whole wallet balance of any token the rogue pool names — unbounded by `amount_in`, by the payload `min_out`, or by the post-swap health-factor gates, since the stolen transfer is orthogonal to the position. A malicious quote/route provider (or any channel that supplies `routeXdr` to users — phishing sites, compromised quote endpoints, malicious frontends) steals arbitrary token balances from every user who signs a composed `multiply`/`swap_debt`/`swap_collateral`/`repay_debt_with_collateral` transaction, and equally from direct `execute_strategy` users.

### Likelihood Explanation
The route bytes are opaque XDR produced off-chain; the SDK and docs instruct integrators to "pass it untouched" and only offer optional `verifyRouteBytes` helpers that do not enumerate downstream contract calls. An attacker needs only to get a victim to submit a poisoned route — the same trust assumption the express-jwt advisory relies on (attacker-controlled input reaching the verifier). The exposure is demonstrated end-to-end under enforced auth in the repository's own test. Mitigation rests entirely on every client decoding the signed authorization tree, which standard wallets do not expose legibly; the contracts themselves provide no enforcement, exactly like express-jwt <6.0.0 shipping with `algorithms` optional. Rated Medium-High: requires social/signing interaction, but the resulting loss is total and the fix is a contract-side allowlist.

### Recommendation
Enforce the constraint on-chain rather than delegating it to clients:
- Maintain an allowlist of permitted venue/pool (and pool-share-token) addresses in the swap aggregator, set via governance, and have the dispatcher reject instructions referencing non-allowlisted addresses.
- Alternatively/additionally, have the controller pass the expected callee set alongside `swap` so `execute_strategy` can reject any hop outside it.
- Until enforced, integrators must decode the simulated authorization tree and refuse any `require_auth` child beyond the single documented input transfer (`self -> router`, exact `amount_in`), as the threat model prescribes.

### Proof of Concept
```rust
// tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs
// A RogueHopPool registered as a route hop performs, inside the swap,
//   wallet_token.transfer(alice, attacker, WALLET_BALANCE)
// Victim calls controller.swap_collateral(alice, account_id, USDC, amount, ETH, route).

// 1. Honest route, honest tree -> succeeds, wallet untouched.
let benign = s.route_through_pool_stealing(0);
s.try_swap_with_signed_tree(&benign, &[]).unwrap();
assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

// 2. Rogue route, signed with the tree simulation returns
//    (which now contains the extra transfer invocation).
let stolen_transfer = MockAuthInvoke {
    contract: &s.wallet_token,
    fn_name: "transfer",
    args: (alice, attacker, WALLET_BALANCE),
    sub_invokes: &[],
};
s.try_swap_with_signed_tree(&rogue, &[stolen_transfer]).unwrap();
assert_eq!(s.wallet(&s.alice), 0);
assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
```
The swap itself returns `min_out`-satisfying output and passes the controller's `RouterOverspend`/`NoSwapOutput`/HF checks, so the transaction succeeds while the victim's unrelated wallet token is stolen.
