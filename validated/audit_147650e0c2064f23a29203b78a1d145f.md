### Title
Asset definer can retroactively replace the entire spender-attestor list, freezing coins already held by previously-attested users - (File: [storage.js](https://github.com/hirayap/ocore--008/blob/main/storage.js), [validation.js](https://github.com/hirayap/ocore--008/blob/main/validation.js))

### Summary
For `spender_attested` assets, the set of addresses allowed to move funds is not fixed at issuance time — it is always recomputed from the *latest* `asset_attestors` message published by the asset definer, with no requirement that a new list be a superset of (or otherwise compatible with) the previous one. A definer (including an AA acting as its own asset issuer) can therefore publish a fresh `asset_attestors` message that drops previously trusted attestors, instantly invalidating the attestation status of coin holders who legitimately acquired and were attested under the old list. This is the same root-cause pattern as the reported Perennial issue: a party with legitimate control over a parameter (definer/vault admin) can change that parameter to a value inconsistent with already-committed positions, with no validation against the prior state, causing holders' funds to become unspendable.

### Finding Description
When an asset has `spender_attested: true`, every payment of that asset is validated against the attestor list read for that asset at the time of the payment, not the list in force when the payer's coins/attestation were obtained:

- `storage.readAsset()` always selects the single **latest** `asset_attestors` unit (`ORDER BY level DESC LIMIT 1`) and treats its attestor set as authoritative going forward. [1](#0-0) 

- `loadAssetWithListOfAttestedAuthors()` then filters the authors of the current payment against that latest list only. [2](#0-1) 

- At validation time, `validatePayment()` rejects a payment if none of its authors is in the (latest) `arrAttestedAddresses`. [3](#0-2) 

The update itself, `validateAttestorListUpdate()`, only checks that the sender is the asset definer and that the new list is well-formed (sorted, valid addresses, size limit) — it performs **no comparison with the previous attestor list**, no requirement to include existing attestors, and no protection for addresses who were attested and received funds under the old list. [4](#0-3) 

This message type (`asset_attestors`) is explicitly available to AAs as a first-class response app, meaning an AA that defines and issues its own attested asset can also unilaterally rewrite the attestor list at any later trigger, just like an EOA definer. [5](#0-4) [6](#0-5) 

This mirrors the reported bug class exactly: a privileged party changes a parameter that existing users’ funds/positions implicitly depend on (in Perennial: `targetLeverage`/`maxCollateral`; here: the attestor set that gates spendability), without validating the new value against the old committed state, and the change is retroactively effective for everyone, including holders who took no action.

### Impact Explanation
Once a definer (human or AA) replaces the attestor list with a disjoint set, all coins held by addresses that were validly attested under the old list — and any coins already issued/transferred to them — become **frozen**: they can no longer satisfy `objAsset.arrAttestedAddresses.indexOf(...) === -1` in `validatePayment`, and any spend attempt is rejected. For an AA-issued asset this can also freeze the AA's own future issuance/payment logic if it depends on attestation of specific addresses (e.g., itself or a treasury address) that fall out of the new list. This is a fund-freezing condition reachable purely through a normal, permitted message type (`asset_attestors`), causing loss of usability of already-acquired, legitimately-held assets — matching the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
The `asset_attestors` message is a documented, supported feature (used deliberately for KYC/whitelisting-style assets) and is reachable by any asset definer with a single unit, or by an AA as a normal response message. No special privileges beyond being the asset's definer are required, and definer-controlled assets already assume the definer is trusted for cap/attestor management, but the code provides no safety net against a definer (or a poorly-written/rug-pulling AA) instantly revoking attestation for existing legitimate holders. This requires no consensus split or malicious peer — only a normal, valid unit from the definer address — making it straightforward to trigger.

### Recommendation
When processing `asset_attestors` updates, consider one of:
- Requiring or at least warning when new attestor lists remove addresses that have already attested/spent under the asset (i.e., enforce append-only or explicit-removal-with-timelock semantics), or
- Grandfathering already-attested holders for a fixed transition window instead of applying the newest list retroactively to every payment, or
- Making attestor-list changes take effect only for coins issued/attested after the change (à la denomination/cap semantics), so previously acquired attested balances remain spendable.

### Proof of Concept
1. Definer `D` creates asset `X` with `spender_attested: true`, `attestors: [A]`.
2. Attestor `A` attests address `U`. `U` receives units of `X` (via issue or transfer) and can freely spend them because `filterAttestedAddresses` finds `U` attested by `A`, per `storage.js:1960-1974`.
3. `D` publishes a new `asset_attestors` message for asset `X` with `attestors: [B]` (completely different attestor, no overlap with `A`). This passes `validateAttestorListUpdate` since it only checks the sender is `D` and the list is well-formed (`validation.js:2829-2864`).
4. `storage.readAsset()` now returns `B` as the sole attestor for `X` (`storage.js:1917-1946`), since it always selects the latest attestor-list unit.
5. `U` attempts to spend previously received `X`. `loadAssetWithListOfAttestedAuthors` finds `U` is not attested by `B`, so `validatePayment` returns `"none of the authors is attested"` (`validation.js:2115-2122`), permanently freezing `U`'s existing, legitimately-acquired balance without any action or fault of `U`'s. function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
