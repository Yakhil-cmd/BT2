### Title
Webhook signature verification is silently bypassed when an organization's `webhook_secret` is unset, allowing unauthenticated forgery of authorization-critical webhook events (e.g. team `membership`) - (File: `lib/shipit/github_app.rb`, `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The reported bug class is an identity/credential-binding mismatch: a value used to authenticate a request differs from (or is not truly enforced against) the value used to perform the sensitive action. In shipit-engine, the webhook pipeline authenticates a request by looking up a per-organization `GitHubApp` config keyed off the payload's own `repository.owner.login` / `organization.login` field, and then defers to that config's `verify_webhook_signature`. However, that verification method treats a *missing* `webhook_secret` as automatic success, which the setup documentation explicitly allows as an "optional" configuration. This breaks the intended binding "GitHub-issued signature == authenticated event" for any organization configured without a secret, letting an unprivileged external actor post arbitrary, unsigned JSON to `/webhooks` and have it processed as if it came from GitHub — including `membership` events that directly create/delete `Shipit::Team` and `Shipit::Membership` records, which gate `Shipit.github_teams` authorization.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` instance to validate against using data taken directly from the untrusted request body: [1](#0-0) [2](#0-1) 

The actual cryptographic check lives in `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Note the guard clause `return true unless webhook_secret` — if the organization entry in `secrets.yml` has no `webhook_secret` configured, **every** signature is accepted, regardless of whether `X-Hub-Signature` is present, well-formed, or matches anything. This is not a hidden implementation detail; the setup guide explicitly documents the webhook secret as optional: [4](#0-3) 

Once past `verify_signature`, the controller dispatches the entire attacker-controlled JSON body to registered handlers with no further authentication: [5](#0-4) 

Among the built-in handlers, the `membership` event handler (exercised in tests) creates `Team` records on the fly and adds/removes `Membership` rows purely from payload contents such as `organization.login`, `team`, and `member.login`: [6](#0-5) 

`Team`/`Membership` records are the backing store for `Shipit.github_teams`-based authorization elsewhere in the engine (oauth team scoping is read from the same GitHub App config structure that `webhook_secret` lives in): [7](#0-6) 

This is the structural analog of the reported bug class: the field/credential that is supposed to bind trust ("this event really came from GitHub for org X") is checked, but the checking logic itself has a documented no-op fallback, so the binding "signature verified == event authentic" silently degrades to "no verification happened at all" for any deployment that follows the documented optional-secret setup — exactly like defaulting a chain-specific value to a shared/absent value collapses a distinctness guarantee.

### Impact Explanation
An attacker with no Shipit account, no `ApiClient` token, and no GitHub credentials can POST directly to the public `/webhooks` endpoint. If any configured organization in that Shipit deployment omits `webhook_secret` (a state the project's own setup documentation presents as a valid, optional choice), the attacker can:
- Forge `membership` events to add themselves (or any GitHub login) to a `Team` that maps to `Shipit.github_teams`, escalating into privileged authorization groups.
- Forge `push`/`pull_request`/`status` events to manipulate `Stack` state (archive/unarchive review stacks, force sync jobs, fabricate commit statuses) for any repository tracked by that organization.

This matches the "High - escalation into `Shipit.github_teams` authorization" impact category, since it requires no credential, session, or repository access — only knowledge that a webhook secret was left unset, which is a supported and documented configuration state rather than a misuse of the engine.

### Likelihood Explanation
Likelihood is directly tied to operator configuration choice, but that choice is explicitly sanctioned by the project's own setup guide (`docs/setup.md`), so it is a realistic deployment state rather than a hypothetical misconfiguration outside documented usage. Any organization onboarded without setting `webhook_secret` is permanently exposed until the operator notices and fixes it; there is no compensating control in the controller or model layer.

### Recommendation
- Make `webhook_secret` mandatory for every configured GitHub organization; fail fast at boot/config-load time if it is missing rather than silently trusting unsigned payloads at request time.
- Change `GitHubApp#verify_webhook_signature` to return `false` (not `true`) when `webhook_secret` is blank.
- Update `docs/setup.md` to remove the "(optional)" designation for the webhook secret, or require an explicit `insecure_skip_webhook_verification: true` opt-in flag if unsigned webhooks must be supported for local development.

### Proof of Concept
1. Configure a Shipit instance with an organization entry that has GitHub App `app_id`/`installation_id`/`private_key` but no `webhook_secret` (a state permitted by `docs/setup.md`).
2. Without any signature header, POST to `/webhooks` with `X-Github-Event: membership` and a JSON body such as:
```json
{
  "action": "added",
  "organization": { "login": "<target-org>" },
  "team": { "id": <existing-team-id>, "name": "Developers", "slug": "developers", "url": "http://example.com" },
  "member": { "login": "attacker-controlled-login" }
}
```
3. Because `repository_owner` resolves to `<target-org>` and that org's `GitHubApp#verify_webhook_signature` returns `true` unconditionally (no `webhook_secret` set), `verify_signature` passes with `head(422)` never triggered, and the `membership` handler creates a `Membership` row granting the attacker's GitHub login access to the team, as demonstrated by the equivalent authenticated test flow: [8](#0-7)

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
