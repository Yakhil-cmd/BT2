### Title
Unbounded access-key enumeration in `TrieViewer::view_access_keys` allows resource-exhaustion via `view_access_key_list_sharded` - (File: `runtime/runtime/src/state_viewer/mod.rs`)

### Summary
`view_access_key_list_sharded` in `chain/jsonrpc/src/lib.rs` routes `EXPERIMENTAL_view_access_key_list` requests to `TrieViewer::view_access_keys`, which iterates the *entire* access-key trie range for an account and collects every key into a `Vec` with no size, count, or byte limit, unlike the sibling `ViewState` query path which enforces `state_size_limit` and page-size caps. An attacker who creates many access keys (or gas keys) on an account they control can drive that node to iterate and serialize an unbounded number of entries in a single RPC response.

### Finding Description
`chain/jsonrpc/src/lib.rs::view_access_key_list_sharded` forwards `RpcViewAccessKeyListRequest{account_id}` to the coordinator, which ultimately calls `QueryRequest::ViewAccessKeyList{account_id}` handling in `chain/chain/src/runtime/mod.rs`, which calls `self.view_access_keys(&shard_uid, *state_root, account_id)` [1](#0-0) . This dispatches to `TrieViewer::view_access_keys`:

```
pub fn view_access_keys(...) -> Result<Vec<(PublicKeyHandle, AccessKey)>, ...> {
    let prefix = trie_key_parsers::get_raw_prefix_for_access_keys(account_id);
    let access_keys = state_update.iter(&prefix)?.map(...).collect::<Result<Vec<_>, _>>();
    access_keys
}
``` [2](#0-1) 

Unlike `view_state`, which enforces a legacy `state_size_limit` gate and supports pagination via `after_key`/`limit` with per-page caps [3](#0-2) , `view_access_keys` has **no limit parameter at all** — it always collects the full result set into memory and returns it as one JSON response. The RPC request type `RpcViewAccessKeyListRequest` only carries `block_reference` and `account_id`, with no prefix/pagination fields [4](#0-3) , so the exploit surface is "number of access keys on an account," not a caller-supplied "prefix," contrary to the question's premise — `ViewAccessKeyList` has no prefix parameter to control.

I could not find any protocol-level cap on the number of access keys (full-access or function-call) or gas keys that can be added to a single account; adding a key only costs gas/storage rent per `AddKey`/`TransferToGasKey` action, which is an economic deterrent, not a hard enumeration limit enforced at query time.

### Impact Explanation
An account controlled by the attacker (self-funded, requiring only paying storage cost per key) can accumulate a very large number of access keys over time. Any subsequent unauthenticated `EXPERIMENTAL_view_access_key_list` (or `query` with `ViewAccessKeyList`) call against that account forces the serving RPC node to iterate the full trie range and build/serialize the entire access-key list in one response, with no cap comparable to `state_size_limit`/pagination on `ViewState`. This can lead to large memory allocation and CPU/bandwidth spent serializing a single response, which matches a resource-exhaustion / node-availability degradation class rather than a memory-safety panic. It is bounded in severity by the cost the attacker must pay in storage/gas to create the keys in the first place (near-linear cost to the attacker), which somewhat limits “High” severity but the finding is real: there is no matching defense on this specific query path.

### Likelihood Explanation
Feasible for any unprivileged account holder: an attacker only needs enough funds to add many `AddKey`/`TransferToGasKey` actions to their own account (paying storage rent), then issue the read-only `EXPERIMENTAL_view_access_key_list` RPC call against any public node. No special permission or race condition is required, and the query path is reachable via public JSON-RPC. The magnitude of the resulting response is proportional to attacker-paid storage cost, so this is a resource-amplification issue of moderate-to-high severity depending on the ratio between storage cost and RPC response cost, not a free/unbounded amplification.

### Recommendation
Add pagination/limit support to `ViewAccessKeyList`/`ViewGasKeyNonces` symmetrical to `ViewState`'s `after_key`/`limit`, and/or introduce a hard cap on the number of access keys returned per response (with a `RpcViewAccessKeyListError::InternalError`/dedicated error when exceeded), mirroring the `state_size_limit`/per-page cap pattern already used in `TrieViewer::view_state`.

### Proof of Concept
Integration test plan (e.g. in `chain/jsonrpc/jsonrpc-tests/tests/rpc_query.rs` or `test-loop-tests/src/tests/sharded_rpc.rs`):
1. Create a test account and submit many `AddKey` (or `TransferToGasKey`) transactions to add e.g. 10,000+ access keys to it (bounded only by test account balance).
2. Call `EXPERIMENTAL_view_access_key_list` (via `view_access_key_list_sharded`/`view_access_key_list_local`) against that account.
3. Assert that the response either: (a) is capped/paginated with a typed error/continuation token when the key count exceeds a configured limit, or (b) currently returns the full unbounded list (demonstrating the missing limit) — measure response payload size and node memory/CPU during serialization to confirm unbounded growth proportional to key count, contrasted with `ViewState`'s bounded behavior under `state_size_limit`.

    pub fn view_access_keys(
        &self,
        state_update: &TrieUpdate,
        account_id: &AccountId,
    ) -> Result<Vec<(PublicKeyHandle, AccessKey)>, errors::ViewAccessKeyError> {
        let prefix = trie_key_parsers::get_raw_prefix_for_access_keys(account_id);
        let access_keys =
            state_update
                .iter(&prefix)?
                .map(|key| {
                    let key = key?;
                    let key_handle = parse_key_handle_from_access_key_key(&key, account_id)
                        .map_err(|_| errors::ViewAccessKeyError::InternalError {
                            error_message: "Unexpected invalid access key from iterator"
                                .to_string(),
                        })?;
                    if let Some(_index) =
                        parse_nonce_index_from_gas_key_key(&key, account_id, &key_handle).map_err(
                            |_| errors::ViewAccessKeyError::InternalError {
                                error_message: "could not parse nonce index".to_string(),
                            },
                        )?
                    {
                        // This is a gas key nonce, skip it.
                        return Ok(None);
                    }
                    let access_key = near_store::get_access_key_by_handle(
                        state_update,
                        account_id,
                        &key_handle,
                    )?
                    .ok_or_else(|| {
                        near_primitives::errors::StorageError::StorageInconsistentState(format!(
                            "iterator yielded an access-key trie key with no value: {key_handle}"
                        ))
                    })?;

                    Ok(Some((key_handle, access_key)))
                })
                .filter_map_ok(|x| x)
                .collect::<Result<Vec<_>, errors::ViewAccessKeyError>>();
        access_keys
    }
