### Title
`MembershipHandler` binds team-membership writes to `team.id` only, letting any registered organization's valid webhook signature grant `Shipit.github_teams` membership for a team owned by a different org - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` purely by the globally-unique GitHub `team.id` in the payload, and never checks that `params.organization.login` matches the `organization` already stored on that `Team` row. Because `WebhooksController#verify_signature` derives which organization's secret to check *from the same attacker-controlled payload* (`repository_owner` → falls back to `params.organization.login` for membership events), a webhook that is validly signed for organization A can still write membership changes onto a `Team` that actually belongs to organization B, breaking the binding between "a `Membership` row exists" and "GitHub actually reported that membership for that team."

### Finding Description
Broken binding (equality form):
`Team.find_by(github_id: params.team.id).organization == params.organization.login` is **assumed** by `authorized?`/`Shipit.github_teams` but is **never enforced** by `MembershipHandler`.

Code path:
- `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . Membership payloads carry no `repository` key (per the handler's `ExplicitParameters` schema, only `team`, `organization`, `member` are required) [3](#0-2) , so `repository_owner` is entirely attacker-supplied via `organization.login`. The signature is therefore checked against *whichever organization's secret the attacker names*, not against the organization that actually owns the target team.
- `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` [4](#0-3) . If a `Team` row with that `github_id` already exists (e.g. the real "victim" team already tracked in `Shipit.github_teams`), it is reused as-is with no check that `params.organization.login` matches the existing row's `organization` column, and the handler proceeds to `team.add_member(member)` / `team.members.delete(member)` [5](#0-4) .
- `User#authorized?` trusts exactly these `Membership` rows: `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , and `force_github_authentication` gates every page render on this result [7](#0-6) .

Why other guards don't help: `drop_unhandled_event` and `check_if_ping` are irrelevant here; the `ExplicitParameters` schema only validates payload shape, not organizational ownership; `verify_signature` validates that *some* configured organization's secret matches, but that organization is picked by the attacker from the payload itself, not derived from the team being mutated.

Attack precondition: this requires a **multi-organization Shipit deployment** (supported and tested — see `test/dummy/config/secrets_double_github_app.yml`) where the attacker legitimately administers/controls a *different* registered organization ("attacker-org") and therefore knows that org's own webhook secret (set up when they configured that org's webhook), while the target `Team` (github_id) belongs to a separate "victim-org" already tracked in `Shipit.github_teams`. Under the stated threat model (no `webhook_secret` known for any org), this precondition is a boundary case: if Shipit is single-org, `Shipit.github(organization: 'attacker')` raises `GithubOrganizationUnknown` and the request is rejected with 422 before it ever reaches the handler — closing the attack in the common single-tenant case. The vulnerability is real and reachable only in the multi-org configuration, where it defeats the intended isolation between organizations' team ACLs.

### Impact Explanation
An attacker who legitimately controls one registered organization in a multi-org Shipit deployment can add an arbitrary GitHub login (including their own already-authenticated Shipit account) as a member of a `Team` row that is meant to represent membership in a *different* organization's GitHub team. If that team is part of `Shipit.github_teams`, this directly grants `User#authorized?` == true, bypassing the intended GitHub-team authorization gate and unlocking all pages/actions gated by `force_github_authentication`, as well as any `require_permission!`/team-scoped authorization built on `Membership`. This matches "escalation into `Shipit.github_teams` authorization" (High). It is repeatable against any `Team` row whose `github_id` the attacker can learn (often discoverable via public GitHub team/org APIs) and does not require compromising the victim organization's own secret.

### Likelihood Explanation
Requires: (1) a multi-org Shipit install, (2) the attacker administering/controlling a second organization already registered with Shipit (and thus knowing that org's webhook secret through legitimate setup, not theft), (3) the target victim `Team`'s GitHub `team.id` being known or guessable, and (4) the attacker having (or being able to create) a Shipit `User` matching the `member.login` they submit. Given these, the attack is a single unauthenticated `POST /webhooks` with a correctly HMAC-signed body — no GitHub API access, no privileged Shipit credentials, and it is fully repeatable. In a single-org deployment the attack is blocked upstream by `GithubOrganizationUnknown`.

### Recommendation
In `MembershipHandler#find_or_create_team!`, when a `Team` with the given `github_id` already exists, verify `team.organization == params.organization.login` before applying `add_member`/`delete`; reject (or drop) the event otherwise. More robustly, derive/verify webhook authenticity using the organization actually owning the resolved `Team`, not solely the attacker-supplied `organization.login` in the payload.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb` patterns, no live GitHub, using the existing multi-org fixture `test/dummy/config/secrets_double_github_app.yml`):

```ruby
test ":membership from org B cannot alter a team owned by org A" do
  # Arrange: victim team already tracked, owned by org "shopify"
  victim_team = shipit_teams(:testers) # organization: 'shopify', github_id: X
  attacker_member = shipit_users(:walrus)

  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' }, # second registered org, own secret
    member: { login: attacker_member.login },
  }.to_json

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = sign_with_attacker_org_secret(payload)

  assert_difference -> { victim_team.reload.members.count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  # Binding check: this Membership was NOT reported by org "shopify" (victim),
  # it was authorized using org "attacker-org"'s signature only.
  assert_includes victim_team.members, attacker_member

  session[:user_id] = attacker_member.id
  get :index, controller: 'shipit/stacks' # or root stacks page
  assert_response :ok # current_user.authorized? now true due to forged cross-org membership
end
```

Both sides of the binding diverge: `Team#organization` remains `'shopify'` while the accepted, validly-signed request originated from `'attacker-org'`, yet the `Membership` row and subsequent `authorized?` == true are created anyway.
