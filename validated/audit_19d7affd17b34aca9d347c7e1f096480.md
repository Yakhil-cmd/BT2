### Title
Unchecked ERC721 `transferFrom` in `requestERC721Transfer` Enables Unauthorized Cross-Chain NFT Bridging — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.sol` calls `IERC721.transferFrom` without any safety wrapper in both `requestERC721Transfer` and `handleERC721Transfer`. Unlike the ERC20 bridge, which correctly uses `SafeERC20.safeTransferFrom`, the ERC721 bridge makes raw external calls that silently succeed even if the underlying token does not actually transfer the NFT. For a non-standard ERC721 token registered on the bridge, this allows an attacker to emit a valid cross-chain transfer request without depositing the NFT, causing the counterpart bridge to release or mint an NFT the attacker never provided.

---

### Finding Description

`BridgeTransferERC20.sol` imports and uses `SafeERC20`:

```solidity
using SafeERC20 for IERC20;
// ...
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
``` [1](#0-0) [2](#0-1) 

`BridgeTransferERC721.sol` makes no equivalent safe call:

```solidity
// requestERC721Transfer — deposit path
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
_requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);

// handleERC721Transfer — withdrawal path (lock mode)
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
``` [3](#0-2) [4](#0-3) 

The `IERC721` interface declares `transferFrom` as `void` (no return value): [5](#0-4) 

Solidity 0.5.6 does not check whether the callee actually performed the transfer; it only checks that the low-level call did not revert. A non-standard ERC721 token whose `transferFrom` returns without reverting (e.g., returns `false` silently, or is a no-op) will be treated as a successful transfer by the bridge.

In `requestERC721Transfer`, the `transferFrom` is executed **before** `_requestERC721Transfer`, which carries the `onlyRegisteredToken` guard. If the token is registered and its `transferFrom` silently no-ops, execution continues into `_requestERC721Transfer`, which emits `RequestValueTransferEncoded` and increments `requestNonce`: [6](#0-5) 

The off-chain bridge relayer (`BridgeInfo.handleRequestValueTransferEvent`) observes this event and submits a `HandleERC721Transfer` transaction on the counterpart chain: [7](#0-6) 

The counterpart bridge then mints or unlocks the NFT to the attacker's `_to` address, despite the attacker never having deposited the token.

In `handleERC721Transfer` (lock mode), the nonce is consumed and the request is permanently marked as handled **before** the `transferFrom` call: [8](#0-7) 

If the transfer silently fails, the NFT is never delivered but the nonce slot is permanently consumed, permanently bricking that withdrawal.

---

### Impact Explanation

- **Deposit path (`requestERC721Transfer`)**: An attacker using a registered non-standard ERC721 token whose `transferFrom` silently no-ops can trigger a legitimate-looking cross-chain transfer request. The counterpart bridge will mint or unlock an NFT to the attacker without the attacker ever depositing anything. This is an **unauthorized mint/unlock of a bridged asset**.
- **Withdrawal path (`handleERC721Transfer`, lock mode)**: A silent failure causes the handle nonce to be permanently consumed without the recipient receiving the NFT, resulting in **permanent loss of a bridged asset**.

---

### Likelihood Explanation

The token must be registered by the bridge owner (`onlyOwner` on `registerToken`), which limits the attack to tokens the operator has explicitly allowed. However, non-standard ERC721 implementations that do not revert on failure exist in the wild (e.g., tokens with upgradeable proxies, tokens with pausable transfers that return instead of reverting, or tokens with custom access-control logic). The ERC20 bridge's use of `SafeERC20` demonstrates the project is aware of this class of risk; the omission in the ERC721 bridge is an inconsistency that creates a real exposure for any such registered token.

---

### Recommendation

Mirror the ERC20 bridge pattern. Add a `SafeERC721`-style low-level wrapper (analogous to `SafeERC20.callOptionalReturn`) that:
1. Verifies the target address contains contract code.
2. Performs a low-level `call` and asserts `success == true`.
3. Alternatively, use `safeTransferFrom` (the ERC721 variant that invokes `onERC721Received`) for the deposit path, which provides an additional confirmation callback.

At minimum, wrap both calls:

```solidity
// deposit
(bool ok,) = _tokenAddress.call(
    abi.encodeWithSelector(IERC721.transferFrom.selector, msg.sender, address(this), _tokenId)
);
require(ok, "ERC721 transferFrom failed");

// withdrawal (lock mode)
(bool ok2,) = _tokenAddress.call(
    abi.encodeWithSelector(IERC721.transferFrom.selector, address(this), _to, _tokenId)
);
require(ok2, "ERC721 transferFrom failed");
```

---

### Proof of Concept

1. Deploy a non-standard ERC721 token whose `transferFrom` emits no event and returns without reverting (a no-op).
2. Register this token on the source-chain bridge via `registerToken` (requires bridge owner, but this is a semi-trusted operator action that is within scope for registered tokens).
3. Call `requestERC721Transfer(tokenAddress, attackerAddressOnCounterpart, tokenId, "")`.
   - `IERC721(tokenAddress).transferFrom(msg.sender, address(this), tokenId)` executes and silently no-ops; the bridge does not hold the NFT.
   - `_requestERC721Transfer` proceeds, emits `RequestValueTransferEncoded`, increments `requestNonce`.
4. The off-chain relayer picks up the event and calls `handleERC721Transfer` on the counterpart bridge.
5. The counterpart bridge mints or unlocks `tokenId` to `attackerAddressOnCounterpart`.
6. The attacker now holds the NFT on the counterpart chain without ever depositing it on the source chain.
