### Title
Sybil signer-key splitting lets a single staker's Hare-round leftover slots exceed `floor(total_locked/threshold)+1` - (File: `stackslib/src/chainstate/nakamoto/signer_set.rs`)

### Summary
`pox_5_make_signer_set` aggregates stake amounts by `signer_key`, not by underlying staker/principal, then apportions `reward_slots` via floor-division plus a largest-remainder ("Hare") round that grants at most one bonus slot per distinct entry. A staker who splits one pool of locked STX across `N` distinct `signer_key` registrations (each ≥ `POX_5_SIGNER_SET_MIN_USTX` but below `threshold`) can claim up to `N` leftover-round slots instead of the single bonus slot a combined entry would receive, exceeding the weight a proportional allocation of their real locked STX would justify.

### Finding Description
The invariant that should hold is: for a given underlying staker with total locked STX `T`, `sum(weight assigned across all signer_keys the staker controls) == floor(T/threshold)` plus **at most one** leftover-round bonus slot, matching what a single combined entry of `T` would receive. This equality breaks because the Hare round in `pox_5_make_signer_set` operates per `signer_key` entry, and `signer_key` uniqueness is enforced only against a single `signer` (contract) via `signers` map / `verify-signer-key-grant` in `register-signer` (`stackslib/src/chainstate/stacks/boot/pox-5.clar:946-973`) — there is no aggregation or cap tied to the underlying staker principal in `pox_5_stake_entries`/`RawPox5Entry` (`stackslib/src/chainstate/nakamoto/signer_set.rs:339-455`) or in the apportionment itself (`stackslib/src/chainstate/nakamoto/signer_set.rs:873-911`).

Exploit flow: the attacker deploys `N` distinct `signer-manager` contracts (each a valid, unique `signer` principal), registers a distinct `signer_key` grant for each via `grant-signer-key`/`register-signer`, then issues `N` `stake` calls, each locking an amount just under `threshold` but above `POX_5_SIGNER_SET_MIN_USTX` (50,000 STX per `stackslib/src/chainstate/stacks/boot/mod.rs:73-75`), summing to the attacker's real total `T`. `pox_5_stake_entries` walks the pox-5 linked list and yields one `RawPox5Entry` per `signer_key` (`signer_set.rs:449-452`), so these become `N` separate `Apportionment` entries, each with `weight = floor(amount/threshold) = 0` and `remainder = amount` (near `threshold`) (`signer_set.rs:882-890`). In the Hare round (`signer_set.rs:896-911`), entries are sorted by remainder descending and each distinct entry independently receives up to one bonus slot — so the attacker's `N` entries can collectively win up to `min(N, leftover)` slots, whereas a single combined entry of the same `T` could win at most `floor(T/threshold) + 1`.

None of the listed guards prevent this: `validate-no-reentrancy`/`signer-manager-call-active`, `verify-signer-key-grant`, and `check-pox-lock-period` govern authorization and reentrancy of individual `stake`/`register-signer` calls, not the post-hoc, off-chain apportionment logic in `pox_5_make_signer_set`, which has no notion of "staker" at all — it only sees `(signer_key, amount_ustx)` pairs.

### Impact Explanation
Impact is signing weight/reward slots exceeding what the staker's locked STX would proportionally justify — matching the "High" category ("signing weight or reward slots exceeding locked value"). This grants the colluding staker disproportionate signing authority and reward-share relative to honest, non-Sybil stakers with identical total locked STX, at the expense of the shared, protocol-fixed pool of leftover slots (bounded by `reward_slots`, a fixed cycle parameter) that would otherwise go to other legitimate signers' fractional remainders. It does not mint or unlock STX/sBTC beyond what is actually locked, but it does let one principal capture more of the discrete reward-slot/signing-weight allocation than its proportional share, which is a repeatable strategy across every reward cycle a staker participates in.

### Likelihood Explanation
Preconditions are cheap and fully within an unprivileged staker's control: deploying `N` signer-manager contracts, obtaining `N` signer-key grants (self-signed, since the staker controls all the keys), and issuing `N` `stake` calls each above the 50,000 STX floor. No prepare-phase timing trick, bond-admin, or pause-admin privilege is needed — this works with ordinary `stake` calls during the normal window `check-pox-lock-period`/`verify-not-prepare-phase` already allow. The only real cost is the STX needed to reach `N × 50,000 STX` and the number of leftover slots actually available in that cycle (bounded by other signers' remainders and total `reward_slots`), which limits how many bonus slots a single staker can actually win, but does not eliminate the advantage — a staker with enough capital to run several 50k-STX-plus entries near `threshold` can reliably outcompete diversified, single-entry signers for leftover slots.

### Recommendation
Aggregate stake by underlying staker principal (not `signer_key`) before running the largest-remainder round, or cap the number of leftover-round wins per staker principal to 1 regardless of how many `signer_key`s that principal controls. Concretely, track a `staker` → `signer_key`s mapping in `pox_5_stake_entries`/`pox_5_make_signer_set`, sum `stacked_amt` and floor-weight per staker, compute a single combined remainder per staker, and only then run the Hare round over staker-level (not signer_key-level) apportionments, redistributing weight back down to the individual `signer_key`s afterward.

### Proof of Concept
Rust unit test in `stackslib/src/chainstate/nakamoto/tests/signer_set.rs` extending the existing `check_make_signer_set` harness:
1. Build `pox_constants` with `reward_slots() = R` (e.g., 10) via `test_pox_constants`.
2. Construct entry set A: a single `RawPox5Entry` with `amount_ustx = T` (e.g., `T = 9 * threshold_estimate - 1`).
3. Construct entry set B: `N` `RawPox5Entry`s with distinct `signer_key`s, each `amount_ustx = T/N` (all `< threshold`, summing to `T`), simulating one staker's Sybil split.
4. Run `pox_5_make_signer_set` on both sets with identical `pox_constants`.
5. Assert: `weight_A_total = floor(T/threshold) + (0 or 1)` (single entry, at most one bonus slot) while `weight_B_total = sum of weights across the N split entries`.
6. Assert `weight_B_total > weight_A_total` for constructed `T`, `N`, `threshold` where each split chunk's remainder ranks high enough to win a leftover slot (demonstrating `weight_B_total` exceeds `floor(T/threshold)+1`), proving the equality `sum(weight per staker) == floor(T/threshold)+{0,1}` is violated when the staker splits across `N` `signer_key`s.
