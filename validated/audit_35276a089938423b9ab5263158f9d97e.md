### Title
Asset definer can instantly change `asset_attestors` list with no timelock, freezing transfers of the `spender_attested` asset - ([File: validation.js])

### Summary
The Sherlock finding criticizes `allowedAsset`/`allowedCollection` because a privileged owner can flip them with no delay, immediately invalidating orders that were valid a moment before. `ocore` has a directly analogous mechanism for assets flagged `spender_attested`: the asset definer alone controls the trusted `attestors` list via the `asset_attestors` message, and this list takes effect for validation purposes as soon as the update unit is (near-)stable, with no timelock or grace period for holders who were legitimately attested under the old list.

### Finding Description
When an asset is created with `spender_attested: true`, every payment involving that asset requires all output addresses (and the issuer, on issuance) to be "attested" by one of the definer-chosen attestor addresses [1](#0-0) . Outputs are checked against the *current* attestor list via `storage.filterAttestedAddresses`, and any output address that fails the check causes the whole unit to be rejected [2](#0-1) .

The trusted attestor list itself can be replaced at any time by the definer using an `asset_attestors` message, gated only by an "only definer can edit" check with no cooldown or timelock [3](#0-2) .

When resolving which attestor list is currently in force, `storage.readAsset` always picks the single *latest* `asset_attestors` unit (by level, restricted only to units before/at `last_ball_mci`) and treats attestations issued under any older attestor list as void, because attestations are re-evaluated against whichever attestor set is "latest" at read time [4](#0-3) . There is no vesting/timelock period during which the old list remains valid in parallel with the new one — the moment the update unit is accepted (and eventually stabilizes), the previous attestor set is fully superseded.

This is architecturally identical to the reported bug: a single privileged actor (asset definer, analogous to the BvbProtocol owner) controls an allow-list (`attestors`, analogous to `allowedAsset`/`allowedCollection`) that gates whether other users' pending, already-broadcast, but not-yet-confirmed transactions/spends will validate — and can change it instantly to invalidate them.

### Impact Explanation
A malicious or compromised asset definer can:
- Swap out the attestor list right after users have obtained attestation from the old attestors, instantly turning previously-valid spend/issue/output addresses into "not attested" addresses. Any in-flight payment referencing those addresses as outputs will be rejected during validation ("some output addresses are not attested" / "issuer is not attested" / "none of the authors is attested") [5](#0-4) .
- If such an asset is used as a payment/collateral asset inside an Autonomous Agent, an AA that expects to pay out to (or receive from) an attested user address can have its outputs rejected or its funds effectively frozen/unspendable for legitimate attested holders, because the AA's payment message will fail asset-specific validation the instant the attestor list changes underneath it, with no notice period.
- This denies service to counterparties who did nothing wrong and had a valid attestation just prior to the definer's unilateral, un-timelocked action — the same "can deny the match of some orders"/DoS impact called out in the source finding, here manifesting as blocked or frozen asset transfers.

### Likelihood Explanation
Any asset definer who created a `spender_attested` asset can trigger this at will — no special privileges beyond being the original definer are required, and the change is a single, immediately-effective `asset_attestors` message [3](#0-2) . The likelihood of exercise depends only on definer intent/compromise, exactly mirroring the centralization risk in the original report.

### Recommendation
Introduce a timelock/grace-period for `asset_attestors` updates, e.g.:
- Keep the previous attestor list valid in parallel with the new one for a configurable delay (analogous to the `pendingAsset`/`3 days` pattern in the referenced fix), so that units built and broadcast against the old, still-legitimate attestor list continue to validate until the delay expires.
- Alternatively, have `storage.readAsset`/`filterAttestedAddresses` accept attestations that were valid at `last_ball_mci` of the unit under validation rather than strictly the newest attestor-list unit, preserving backward compatibility for a bounded window.

### Proof of Concept
1. Definer `D` creates asset `A` with `spender_attested: true` and attestor list `[X]` [6](#0-5) .
2. Attestor `X` attests user address `U`; `U` receives asset `A` and begins constructing a payment to counterparty `V` (also attested).
3. Before `U`'s payment unit stabilizes, `D` posts an `asset_attestors` message replacing the attestor list with `[Y]` (`Y` has not attested `U` or `V`).
4. Once `D`'s update unit is processed, `storage.readAsset` treats `[Y]` as the latest attestor list [7](#0-6) ; `U`'s already-broadcast payment to `V` now fails validation with "some output addresses are not attested" [8](#0-7) , even though it was fully valid when created and signed.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
