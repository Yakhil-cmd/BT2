### Title
Hardcoded mainnet `definer_address` for base asset breaks `asset[base].definer_address` on testnet - ([File: formula/common.js])

### Summary
`formula/common.js` hardcodes the base-asset (bytes) `definer_address` field to the mainnet Obyte distribution-fund address, with no `constants.bTestnet` branching, even though this address is network-specific — analogous to the reported hardcoded `WETH` address that only matches one deployment environment.

### Finding Description
`objBaseAssetInfo`, which backs the oscript/AA `asset[base].*` accessor, statically sets:
```
definer_address: 'MZ4GUQC7WUKZKKLGAS3H3FSDKLHI7HFO',
``` [1](#0-0) 
This object is consumed by the `asset[]` opcode evaluator in `formula/evaluation.js`, where `asset === 'base'` returns fields straight from `objBaseAssetInfo`, including `definer_address`, with no per-network override: [2](#0-1) 

That the value is network-specific is confirmed elsewhere in the codebase: `tools/supply.js` explicitly distinguishes the mainnet "distribution fund" address (`MZ4GUQC7WUKZKKLGAS3H3FSDKLHI7HFO`) from a different testnet address (`5ZPGXCOGRGUUXIUU72JIENHXU6XU77BD`) via `process.env.testnet`: [3](#0-2) 

The rest of the codebase consistently treats network-dependent identifiers (`GENESIS_UNIT`, `BLACKBYTES_ASSET`, and dozens of upgrade MCIs) as conditional on `constants.bTestnet`: [4](#0-3) 
but `formula/common.js`'s `definer_address` was left as a single, unconditional mainnet value, so on testnet (`constants.bTestnet === true`) any AA/oscript formula reading `asset[base].definer_address` gets the wrong (mainnet) address.

### Impact Explanation
Any autonomous agent that relies on `asset[base].definer_address` to authenticate/authorize logic (e.g., comparing it against a trusted address to gate a payment, unlock funds, or branch execution) will receive an incorrect value on testnet. This can cause an AA to make wrong access-control decisions — either wrongly denying legitimate flows (funds getting stuck/bounced, i.e. freezing) or, if an attacker can predict/exploit the mismatch in AA logic that assumes correctness of this field, incorrect fund routing. Because AA execution must be deterministic and consistent across all full nodes, this is a data-correctness bug baked into consensus-relevant formula evaluation rather than a display-only issue.

### Likelihood Explanation
Any unprivileged AA author can trivially write and deploy an autonomous agent on testnet that reads `asset[base].definer_address` (a documented, publicly usable oscript primitive), guaranteeing the bug is reachable by any AA trigger sender interacting with such an agent. No special privileges are required — only that the AA is deployed/used on the testnet network, which is one of ocore's two supported live networks.

### Recommendation
Make `definer_address` in `objBaseAssetInfo` network-aware, mirroring the pattern already used for `GENESIS_UNIT`/`BLACKBYTES_ASSET`:
```js
definer_address: constants.bTestnet ? '5ZPGXCOGRGUUXIUU72JIENHXU6XU77BD' : 'MZ4GUQC7WUKZKKLGAS3H3FSDKLHI7HFO',
```
or otherwise source it from an environment/config value consistent with how other network-specific constants are handled in `constants.js`.

### Proof of Concept
1. Run ocore with `testnet=1` (so `constants.bTestnet === true`).
2. Deploy an AA whose formula includes `asset[base].definer_address`.
3. Trigger the AA; observe that the evaluated value is `'MZ4GUQC7WUKZKKLGAS3H3FSDKLHI7HFO'` (the mainnet distribution-fund address) rather than the correct testnet address, even though the node is running on testnet — confirmed by contrasting with `tools/supply.js`'s explicit testnet/mainnet address split for the same conceptual entity.
