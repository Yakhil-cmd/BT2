### Title

Stale oracle prices can survive a permissionless governance oracle update inside `flash_position` - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary

`flash_position` caches oracle prices before invoking an attacker-controlled receiver, and the same `Context` remains in use after the callback. The receiver can permissionlessly execute a ready governance operation that changes the price-aggregator oracle, while final solvency checks continue using the prefetched price. A collateral price that was valid before the governance update can therefore create debt that would fail under the active oracle configuration, potentially causing protocol insolvency.

### Finding Description

`process_flash_position` creates one invocation-local `Context` before loading the account and validating the request [1](#0-0) . It then prefetches prices for the account, debt asset, collateral assets, and other extra assets before entering the callback window [2](#0-1) . The receiver callback is invoked inside that window, after balances are snapshotted but before collateral deposits and final risk checks are processed [3](#0-2) .

`Context::fetch_prices` deliberately retains prices that were already cached and only fetches missing assets [4](#0-3) . Later, `cached_price` reads only that invocation-local map and does not re-query the aggregator [5](#0-4) . Consequently, a change made to the aggregator during the callback is invisible to `enforce_post_pool_solvency`, which is reached through `strategy_finalize` using the same `Context` [6](#0-5) .

An attacker-controlled receiver can execute such a change because `governance::execute` permits `executor=None`, meaning anyone may drive a ready operation [7](#0-6) . The timelock prepares the scheduled operation and invokes its target directly [8](#0-7) . `AdminOperation::ConfigureAssetOracle` resolves to the price aggregator's `set_oracle` entrypoint, and `EditOracleTolerance` resolves to `set_tolerance` [9](#0-8) .

This is the same bug class as the external report: mutable external state is captured for an operation, control is transferred to an attacker, that state is changed, and the operation later continues using the pre-callback snapshot.

### Impact Explanation

If a ready governance operation makes collateral `C` resolve to a lower active price, the callback can activate that operation after `C`'s old higher price has already been cached. The final health-factor, collateral-value, and minimum-borrow-collateral checks still evaluate `C` at the stale price, allowing debt to remain open even though it is undercollateralized under the new oracle configuration [5](#0-4) [10](#0-9) .

The attacker can extract borrowed value and leave the protocol with debt whose real collateral value is insufficient. Depending on the price divergence and debt size, this can cause bad debt and protocol insolvency rather than merely causing an incorrect view or temporary denial of service.

### Likelihood Explanation

Exploitation requires a governance oracle operation to already be scheduled and inside its executable window. That window is publicly observable, and execution with `executor=None` requires no privileged authorization [7](#0-6) . `flash_position` accepts an attacker-chosen WASM receiver and passes attacker-controlled `data` to it [11](#0-10) .

The attack also requires the old cached price to produce a materially different risk result from the price returned by the newly configured oracle. That condition can occur during an oracle-source migration, correction of a stale feed, or a tolerance tightening that would reject or reprice the old feed [9](#0-8) .

### Recommendation

After the receiver callback and before collateral processing or final risk checks, invalidate and reprefetch external snapshots in `Context`, especially `token_prices` and `pool_sync_data`. One approach is to add a `Context::invalidate_external_snapshots` method and call it immediately after `invoke_receiver` returns, then call `prefetch_strategy_prices` again before `process_deposit` and `strategy_finalize` [12](#0-11) .

A more complete fix should separate mutation-derived market indexes and pending spoke-usage updates from independently refreshable oracle/configuration snapshots, so invalidating the latter cannot discard pool results recorded through `put_market_index` [13](#0-12) . A regression test should execute a ready `ConfigureAssetOracle` operation from a flash-position receiver and assert that final solvency uses the post-execution price.

### Proof of Concept

1. Governance has a ready `ConfigureAssetOracle` operation for collateral token `C`, switching it from a source returning price `P_old` to a source returning `P_new < P_old`.
2. An attacker deploys receiver contract `R` and calls controller `flash_position` with:
   - `caller = attacker`
   - `account_id = 0`
   - `mode = PositionMode::Long`
   - `debt = HubAssetKey { hub_id: H, asset: D }`
   - `amount = Q`, sized to pass health checks at `P_old` but fail at `P_new`
   - `receiver = R`
   - `data` containing the ready operation's `target`, `function`, `args`, `predecessor`, and `salt`
   - `collaterals = [(HubAssetKey { hub_id: H', asset: C }, min_C)]`
   - `refund_assets = []`
3. The controller caches the old `C` and `D` prices before invoking `R` [2](#0-1) .
4. Inside `execute_flash_position`, `R` calls `governance.execute(None, price_aggregator, "set_oracle", args, predecessor, salt)`, activating the lower-price configuration [7](#0-6) .
5. `R` swaps the flash-funded `D` into at least `min_C` of `C` and transfers it to the controller.
6. After the callback, the controller deposits the measured collateral and calls `strategy_finalize` without refreshing the cached price map [10](#0-9) .
7. `cached_price(C)` still returns `P_old`, so the position remains open and solvent under stale pricing even though the active aggregator configuration would return `P_new` and reject the same leverage [14](#0-13) .
