Found the analog: `system-repay` in the market-vault contracts contains an unguarded division that mirrors the reported bug class exactly — dividing by a value (`debt` = `total-debt()`) that can legitimately be zero, and the transaction that triggers it is executed by a caller different from the party whose state (the vault's shared debt/principal accounting) is affected.

### Title
Division by zero in `system-repay` when `total-debt()` is zero, permanently freezing repay for all vault borrowers - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, similarly in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar` and their `local-testing` counterparts)

### Summary
`system-repay` computes `principal-repaid` via `(mul-div-down capped-amount total-borrowed-amount debt)`, unconditionally dividing by `debt` (the vault's `total-debt()`). `debt` is derived from `principal-scaled` and the borrow `index`, and can become `u0` in perfectly legitimate states (e.g., the last outstanding borrower is fully repaid by the `market` contract in a prior call within the same block, or `principal-scaled` is `u0` while `total-borrowed` is not yet reconciled to zero). A subsequent `system-repay` call in the same shared vault made by the `market` contract on behalf of a *different* account then triggers a runtime division by zero, which reverts the transaction.

### Finding Description
`system-repay` is a public function callable only by authorized contracts (the `market` contract) on behalf of arbitrary borrower accounts [1](#0-0) . It builds:

```
(debt (total-debt))
(principal-repaid (mul-div-down capped-amount total-borrowed-amount debt))
```

`mul-div-down` is a plain `(/ (* x y) z)` with no zero-guard [2](#0-1) , unlike other computations in the same file that explicitly special-case zero (e.g. `calc-utilization`, `convert-to-shares-preview`, and `socialize-debt`'s `principal-reduction` which guards with `(if (> scaled-principal u0) ... u0)`) [3](#0-2) .

`debt` is `total-debt()`, computed from `principal-scaled` and `index` [4](#0-3) . `principal-scaled` is a **shared, vault-wide** state variable summed across every borrower's scaled debt in that asset vault, not a per-user value — it is the same "weight-like" shared denominator pattern flagged in the reported committee-selection bug, where a shared aggregate (there: shard `weight`; here: `principal-scaled`/`debt`) can legitimately reach zero and is used unguarded as a divisor.

Reachable scenario:
1. Vault currently has exactly one outstanding borrower position (shared vault-level `principal-scaled` > 0, `debt` > 0).
2. That borrower (or the `market` contract processing their full repayment/liquidation) fully repays, driving `principal-scaled` to `0` and `total-borrowed` to `0` in the same block via `system-repay`, leaving `total-debt()` = `0`.
3. Another *unrelated* account (Victim) who is simultaneously interacting with the same vault (e.g., attempting a partial repay, or the `market` contract auto-repaying dust as part of Victim's liquidation flow) triggers `system-repay` again in that same block before Victim's own debt state has been separately accrued/reflected — because `debt` (vault-wide) is now `0`, the division `(/ (* capped-amount total-borrowed-amount) debt)` panics with a runtime division-by-zero error, aborting Victim's transaction.

Because `system-repay` operates on the vault's aggregate `principal-scaled`/`total-borrowed` (shared state across all borrowers of that asset), one account's action (driving vault debt to zero) can render a subsequent, unrelated account's `system-repay`/liquidation-repay call for that same asset temporarily unexecutable within that block/state, until vault state changes again (e.g. a new borrow) — a shared-state ordering dependency between two users precisely analogous to the reported bug.

### Impact Explanation
This is a temporary freezing/denial-of-service of debt-repayment and liquidation-repayment flows for a shared vault when its aggregate `total-debt()` is momentarily zero. Since `liquidate` and `repay` in the market contract funnel into vault `system-repay` [5](#0-4) , a reverted `system-repay` blocks a legitimate liquidator or repayer's transaction, which can delay liquidation of an unhealthy position (temporary freezing of funds / delayed loss mitigation) for other users relying on that same vault, until the divide-by-zero condition clears.

### Likelihood Explanation
Requires the vault's aggregate debt to hit exactly zero and then be called into `system-repay` again with a nonzero `amount`. This is a plausible but narrow race — it depends on the vault having very few concurrent borrowers (so that one repayment can zero out `total-debt()`) and a second `system-repay` call landing before new debt is created. On mainnet vaults with many active borrowers this is unlikely, but during low-utilization periods, freshly deployed markets, or thinly-borrowed asset vaults, it becomes practically reachable.

### Recommendation
Guard the division in `system-repay`'s `principal-repaid` calculation the same way `socialize-debt` already guards `principal-reduction`: 
```
(principal-repaid (if (> debt u0) (mul-div-down capped-amount total-borrowed-amount debt) u0))
```
Apply this fix to `mul-div-down`/`mul-div-up` call sites operating on `debt`, `total-borrowed`, or `principal-scaled` denominators across all six vault contracts (`v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`) and their `local-testing` mirrors.

### Proof of Concept
1. Deploy/observe a vault (e.g. `v0-vault-usdc`) with a single active borrower, `principal-scaled = P > 0`, `total-borrowed = B > 0`.
2. Call `market.repay` (routes to `v0-vault-usdc.system-repay`) with `amount >= debt`, fully repaying the sole borrower; `capped-amount = debt`, `principal-reduction = scaled-principal` (fully reduced), leaving `principal-scaled = 0`, `total-borrowed = 0`, so `total-debt()` becomes `0` after this call.
3. Within the same block, a second, unrelated account/liquidator calls `market.repay` or `market.liquidate` for the same asset with a nonzero amount, invoking `v0-vault-usdc.system-repay` again while `debt = total-debt() = 0`.
4. `(mul-div-down capped-amount total-borrowed-amount debt)` evaluates `(/ (* capped-amount total-borrowed-amount) 0)`, causing a runtime division-by-zero panic that reverts the second caller's transaction, denying their legitimate repay/liquidation-repay action for that block/state.
