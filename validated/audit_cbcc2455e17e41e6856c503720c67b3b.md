### Title
Cross-organization webhook forgery: `organization.login` used for signature verification is never bound to the `repository.full_name` used to resolve the target Stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
The BakerFi bug is a class of "value used to gate an action ≠ value the action actually consumes." The same class exists in Shipit's webhook pipeline: the field used to *select the HMAC secret that authenticates the request* (`repository.owner.login`, i.e. the GitHub organization) is never checked against the field used to *resolve which `Repository`/`Stack` the event acts on* (`repository.full_name`). Anyone who legitimately controls one GitHub organization configured in Shipit (and therefore knows that organization's `webhook_secret`) can forge a signed payload whose `repository.owner.login` matches their own org (so it passes verification) while `repository.full_name` points at a stack belonging to a completely different organization.

### Finding Description
`WebhooksController#verify_signature` chooses which `GithubApp`/`webhook_secret` to validate against using a value taken straight out of the untrusted JSON body: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Once the signature check passes, the event is dispatched to the corresponding `Handler` subclass, all of which resolve the target `Repository`/`Stack` from a *different* field of the same payload, `repository.full_name`, with no cross-check that it belongs to the organization whose secret validated the request: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler`, `StatusHandler`, and `CheckSuiteHandler` all inherit this resolution and act on whatever `repository`/`full_name` is embedded in the (attacker-controlled) body: [4](#0-3) [5](#0-4) [6](#0-5) 

Shipit is documented to support multiple, independently configured GitHub organizations, each with its own `app_id`, `installation_id`, and `webhook_secret`: [7](#0-6) 

**Binding broken (equality that must hold but doesn't):**
`organization authenticated by the verified signature (repository.owner.login / organization.login)` **==** `repository actually written to by the handler (repository.full_name)`

Because the HMAC covers the raw byte payload but not any semantic constraint tying these two fields together, an attacker who is the legitimate owner/administrator of Organization A's GitHub App (and thus knows Org A's `webhook_secret` — a credential outside Shipit's own trust boundary, not a Shipit session, ApiClient token, or repository write access to the victim repo) can:
1. Build a JSON body with `repository.owner.login: "OrgA"` (so `repository_owner` resolves to Org A and the correct secret is used for verification) and `repository.full_name: "OrgB/victim-repo"` (a stack Shipit manages for a completely different, unrelated organization).
2. Compute a valid `X-Hub-Signature` using Org A's `webhook_secret`.
3. POST it to the shared `/webhooks` endpoint.

`verify_signature` succeeds (it only checks the byte-for-byte HMAC against Org A's secret), and the handler then acts on `OrgB/victim-repo` — a repository the attacker has no legitimate access to whatsoever.

### Impact Explanation
This lets an attacker with no relationship to the victim organization/repository (no Shipit account, no `ApiClient` token, no `webhook_secret` for that org, no repo write access) forge events that mutate state for that victim's stacks using the app's own trust in the (unrelated) verified organization:
- `StatusHandler#process` will create/attach a forged `Status` (`create_status_from_github!`) to any commit sha the attacker names, including a fabricated `state: "success"` — this directly manipulates the CI signal used by `Commit#deployable?`/`required_statuses`, which stacks with `continuous_deployment` enabled rely on to auto-trigger deploys. This can result in an **unauthorized deploy** of a commit that never actually passed CI, which is explicitly a Critical-impact outcome per the scope rules.
- `PushHandler#process` forces `stack.sync_github(expected_head_sha:)` on a foreign stack using the app's own GitHub credentials, letting an outside actor drive Shipit's polling/sync behavior against a repository they don't control.
- `CheckSuiteHandler#process` similarly schedules check-run refreshes for a foreign stack's commits.

### Likelihood Explanation
The multi-organization configuration (`Shipit.github(organization:)`, per-org `webhook_secret`) is a first-class, documented feature of the engine, not a hypothetical edge case. Any deployment of Shipit that manages more than one GitHub organization is exposed: the attacker needs only to be a legitimate GitHub App/webhook administrator for *any one* of the configured organizations, which is a much lower bar than compromising the victim organization or obtaining a Shipit-internal credential. No race condition, no rate limiting, no host misconfiguration is required — this is a straightforward, deterministic logic flaw in field validation.

### Recommendation
After verifying the signature, re-derive the organization/owner strictly from the same field used to select the secret, and reject the webhook if `repository.full_name`'s owner segment (or `repository.owner.login`) does not match the organization whose key validated the signature. Concretely, in `WebhooksController#verify_signature` (or in `Handler#repository_name`), assert `payload.dig('repository','full_name')&.split('/')&.first == repository_owner` before dispatching to handlers, and drop (422) any payload where these disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `config/secrets.development.shopify.yml` layout).
2. As the administrator of OrgA's GitHub App (who legitimately knows `webhook_secret_A`), build a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(webhook_secret_A, body)`.
4. `POST /webhooks` with `X-Github-Event: push` and the above signature/body.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies using `webhook_secret_A`.
6. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on a stack belonging to an organization the attacker never had access to — no boundary in the code prevents this cross-organization dispatch.
