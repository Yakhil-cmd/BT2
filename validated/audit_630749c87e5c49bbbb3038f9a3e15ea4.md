## Finding: WebAuthn admission path lacks relying-party (origin) binding, allowing cross-origin signature material to authenticate Aptos transactions

### Title
Missing WebAuthn origin/RP-ID binding in `PartialAuthenticatorAssertionResponse::verify_arbitrary_msg` allows off-chain-origin signing material to satisfy transaction admission - (File: `types/src/transaction/webauthn.rs`)

### Summary
The WebAuthn authenticator path used to admit Aptos transactions binds only the `challenge` field of `CollectedClientData` (set to the SHA3-256 digest of the `RawTransaction`) and the raw signature to the account's public key. It never validates the WebAuthn `type` field (should be `webauthn.get`) or the relying-party ID hash embedded in `authenticator_data`, both of which WebAuthn §7.2/§6.3.3 specify as mandatory to prove the assertion was produced for the intended origin/RP. [1](#0-0) 

### Finding Description
`verify_arbitrary_msg` at [1](#0-0)  performs exactly two checks before running signature verification:
1. That `collected_client_data.challenge` (base64url-decoded) equals the supplied `message` (the SHA3-256 digest of the `RawTransaction`).
2. That the ECDSA signature over `authenticator_data || SHA-256(client_data_json)` verifies against the `AnyPublicKey`.

There is no check of `collected_client_data.type` (the standard would require `"webauthn.get"`), and no check that the relying-party ID hash inside `authenticator_data` (the first 32 bytes) corresponds to an expected domain bound to the Aptos client/wallet. This authenticator is invoked as part of `AnySignature::verify`/`verify_arbitrary_msg` during `SignedTransaction::check_signature()`, which is the first admission gate hit in `AptosVM::validate_transaction` at [2](#0-1)  before mempool/VM prologue checks run.

Because only the challenge (an attacker-computable, fully-public value once a `RawTransaction` is constructed — sender, sequence number/nonce, gas price/limit, expiration, chain ID are either known or brute-forceable/guessable by anyone) is checked, any WebAuthn assertion produced by the user's authenticator for *any* relying party whose challenge happens to equal that digest will satisfy this admission check. WebAuthn's RP-ID binding exists precisely to prevent an assertion generated in one origin context (e.g., a malicious website invoking `navigator.credentials.get()`) from being replayed as though it were produced for a different origin/application (the Aptos wallet). Skipping that check collapses the origin-isolation guarantee WebAuthn is supposed to provide at the authenticator-binding step of transaction admission.

### Impact Explanation
An attacker-controlled website could construct a valid unsigned `RawTransaction` for a victim's account (sender address, next sequence number/nonce, gas parameters, expiration, chain ID are all either public or guessable), compute its SHA3-256 digest, and set that digest as the WebAuthn `challenge` when invoking `navigator.credentials.get()` on its own origin (unrelated to the Aptos wallet). If the victim's browser/authenticator produces an assertion (e.g., under some passkey UX flow that doesn't clearly disambiguate context, or via any flow where the site can trigger a generic WebAuthn ceremony against a discoverable credential), the resulting `PartialAuthenticatorAssertionResponse` would satisfy `verify_arbitrary_msg` and be accepted as a valid `AccountAuthenticator` for the victim's account, since only the challenge/digest and the raw signature are checked — not the origin or RP ID that should tie the assertion to the Aptos wallet's own domain. This is an authenticator-admission binding failure that lets a transaction execute with a wrongly-bound signing ceremony, i.e., unauthorized transaction admission under a signer whose consent context was never actually the Aptos transaction.

### Likelihood Explanation
Exploitation requires the attacker to get the victim's authenticator to sign an assertion whose challenge is the attacker-chosen digest, which in practice depends on browser/authenticator UX around passkey ceremonies (e.g., some flows allow arbitrary challenge values from any invoking origin without prominently displaying what is being signed). This is a real, previously-documented weakness class in WebAuthn integrations that skip RP-ID/type binding, and it does not require any privileged access — only that the victim performs a WebAuthn ceremony on a malicious page while holding an Aptos-secp256r1 passkey account. This is not certain to be trivially exploitable in every browser/authenticator configuration, but the code itself provides no defense-in-depth against it, which is the root cause finding.

### Recommendation
In `verify_arbitrary_msg` (and any other WebAuthn assertion verification path), in addition to the challenge check, validate:
1. `collected_client_data.ty == ClientDataType::Get` (or the expected fixed type).
2. The RP ID hash in the first 32 bytes of `authenticator_data` equals `SHA-256(expected_rp_id)` for the Aptos wallet's canonical RP ID.
3. Optionally, the `origin` field of `collected_client_data` against an expected origin allow-list, consistent with WebAuthn §7.2 steps 9–13.

### Proof of Concept
Not runnable without a live authenticator/browser context; the vulnerability is demonstrated structurally by the code path: `PartialAuthenticatorAssertionResponse::verify_arbitrary_msg` only compares `challenge` and verifies the signature [1](#0-0) , with no RP-ID/type validation, and this function is reachable from `SignedTransaction::check_signature()` used in transaction admission at [2](#0-1) . I was unable to fully verify, within available tool budget, whether any additional origin/RP-ID enforcement exists elsewhere in the request pipeline (e.g., wallet-SDK-side, outside this repo) — this would need to be checked in a follow-up session with broader visibility into client-side wallet integration code, since aptos-core itself is only the verifier of the cryptographic material, not the browser/authenticator ceremony.

    pub fn verify_arbitrary_msg(&self, message: &[u8], public_key: &AnyPublicKey) -> Result<()> {
        let collected_client_data: CollectedClientData =
            serde_json::from_slice(self.client_data_json.as_slice())?;
        let challenge_bytes = Bytes::try_from(collected_client_data.challenge.as_str())
            .map_err(|e| anyhow!("Failed to decode challenge bytes {:?}", e))?;

        // Check if expected challenge and actual challenge match. If there's no match, throw error
        challenge_bytes
            .as_slice()
            .eq(message)
            .then_some(())
            .ok_or(CryptoMaterialError::ValidationError)?;

        // Generates binary concatenation of authenticator_data and hash(client_data_json)
        let verification_data = generate_verification_data(
            self.authenticator_data.as_slice(),
            self.client_data_json.as_slice(),
        );

        // Note: We must call verify_arbitrary_msg instead of verify here. We do NOT want to
        // use verify because it BCS serializes and prefixes the message with a hash
        // via the signing_message function invocation
        match (&public_key, &self.signature) {
            (
                AnyPublicKey::Secp256r1Ecdsa { public_key },
                AssertionSignature::Secp256r1Ecdsa { signature },
            ) => signature.verify_arbitrary_msg(&verification_data, public_key),
            _ => Err(anyhow!(
                "WebAuthn verification failure, invalid key, signature pairing"
            )),
        }
    }
