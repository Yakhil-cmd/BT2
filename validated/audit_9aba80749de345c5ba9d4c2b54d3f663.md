### Title
Unbounded linear scan of the in-memory unstable-unit set in `data_feed`/`data_feed_exists` oscript functions causes AA-trigger processing to slow with network backlog - (File: data_feeds.js)

### Summary
`data_feeds.js` implements the oscript `data_feed()` / `data_feed_exists()` functions that AAs use to read/query data-feed messages. When these are called with the "unstable" lookup option (used to see not-yet-stable data feeds posted by AAs), the implementation performs a full `for...in` scan over `storage.assocUnstableMessages`, a global in-memory map that holds the messages of every currently-unstable unit in the entire DAG. This map has no size cap and grows purely as a function of how many units are currently posted-but-not-yet-stabilized on the network, which any unprivileged unit poster can influence simply by submitting ordinary units. This mirrors the reported bug class: an unbounded array/collection populated by unprivileged actions, then fully iterated inside a function every node must execute.

These loops iterate `for (var unit in storage.assocUnstableMessages)`, inspecting every unstable unit's messages for matching `data_feed` payloads before falling back to indexed kvstore lookups for stable data. `assocUnstableMessages` is filled for every unit as soon as it is saved (before it becomes stable) and only cleared once the unit stabilizes, so its size tracks the size of the currently-unconfirmed frontier of the whole DAG, not anything scoped to a single AA, address, or feed name.

Any AA author can write an AA whose response/state-update formula calls `data_feed(...)` or `data_feed_exists(...)` with the "unstable"/"all_unstable" option — a standard, publicly documented oscript primitive, not a privileged capability. Any unprivileged AA trigger sender can then invoke that AA by posting a normal trigger unit. Full nodes execute the AA deterministically as part of unit validation (`handleTrigger` → formula evaluation → `data_feeds.readDataFeedValue`/`dataFeedExists`), so the unbounded scan runs synchronously on every full node processing that trigger.

Unlike other places in oscript evaluation where the codebase explicitly guards against unbounded growth — e.g. array/dictionary literal size checks, `foreach` count limits, state-var value length caps, response-vars length caps — [3](#0-2) [4](#0-3) [5](#0-4) 
there is no analogous cap on the number of unstable units/messages scanned by `dataFeedExists`/`readDataFeedValue`.

### Impact Explanation
Because the number of unstable units is a function of network-wide unconfirmed traffic, a period of high transaction volume or a burst of ordinary valid units submitted deliberately (no special privilege required — just paying normal fees) inflates `assocUnstableMessages`. Every subsequent AA trigger that exercises `data_feed`/`data_feed_exists` with the "unstable" option then forces every full node to perform an O(size of unstable set) scan synchronously while validating/executing that trigger unit. Since AA execution must be deterministic and is part of the consensus-critical unit-processing pipeline, repeated invocation of such triggers while the unstable set is large degrades the throughput of unit validation/processing network-wide, slowing confirmation of new units — the closest analog to "network unable to confirm new units" in the validation rules. This is qualitatively the same DoS pattern as the reported `protectionInfos` issue: an attacker-influenceable, unbounded collection fully iterated inside a function that every participant must execute.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an AA that uses `data_feed`/`data_feed_exists` with the unstable option to exist (a normal, expected usage pattern for AAs reacting to fresh oracle data before stabilization), and (b) the unstable-unit set to be inflated, which can happen either organically during high network load or be induced by an attacker submitting many ordinary units in a short window. No special/privileged role (peer, hub, node) is needed — only unprivileged unit posting and AA-trigger sending, both explicitly in scope.

### Recommendation
Bound the "unstable" data-feed scan, e.g.:
- Track unstable data-feed messages in a dedicated index keyed by `(address, feed_name)` instead of iterating the entire `assocUnstableMessages` map for every lookup.
- Impose a hard cap on the number of unstable units/messages scanned per `data_feed`/`data_feed_exists` call (mirroring the caps already used elsewhere for arrays, dictionaries, and `foreach`), failing fast (formula fatal error) once the cap is exceeded.
- Alternatively, maintain a running, incrementally-updated cache of "candidate" unstable data-feed messages per `(address, feed_name)` pair rather than performing a full linear scan on each query.

### Proof of Concept
1. Deploy an AA whose trigger-response formula includes a call such as `data_feed([oracle_address], 'price', 'unstable')` or `data_feed_exists(...)` with the unstable option.
2. Flood the network with a large number of ordinary, valid, low-value units from multiple unprivileged addresses in a short time window, keeping many units in the unstable state (this is possible because stabilization requires witness-ordering and several following main-chain units, which lags behind burst submission).
3. While the unstable set is large, repeatedly send trigger units to the AA from step 1.
4. Each trigger causes every full node to execute: [6](#0-5) 
iterating the entire `assocUnstableMessages` map, increasing per-unit validation/execution latency proportionally to the size of the network-wide unstable set, degrading overall unit-processing throughput for all nodes.
