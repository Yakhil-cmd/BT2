## Title
Liquidator can force full-collateral seizure while only repaying debt for a small liquidated portion via the dust-remainder rounding gap in `liquidate()` - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The `liquidate()` function in `v0-4-market.clar` contains a "dust cleanup" branch that hands the liquidator the borrower's **entire remaining collateral balance** whenever the leftover collateral, converted to a debt amount, rounds down to zero. A liquidator can choose `debt-amount` such that this rounding condition is deliberately triggered, letting them seize collateral well beyond what their partial-liquidation debt repayment entitles them to — analogous to the reported `getGuessRate()` issue where a caller could pick inputs that zero out the intended cost/edge and receive an unearned payout.

### Finding Description
`calc-liquidation-params` computes a graduated `liq-pct-scaled`/`max-debt-usd` based on the borrower's current LTV, and `process-debt-asset`/`process-collateral-asset` cap the liquidator's requested `debt-amount` at `max-debt-usd`, deriving `coll-actual`/`coll-expected` proportionally [1](#0-0) . After scaling for storage, the contract computes how much collateral would remain (`coll-remaining`) and tries to convert that remainder to an equivalent debt amount using the *maximum* liquidation penalty: [2](#0-1) 

If `rem-coll-usd` (the dust collateral, denominated in USD) is small enough that `div-bps-down`/`mul-div-down` rounding collapses `remaining-debt-to-repay` to `u0`, the code sets `coll-final` to `user-coll-balance` — i.e., the liquidator receives **100% of the borrower's remaining collateral for that asset**, even though `debt-to-repay`/`debt-final` (and therefore the actual amount of debt repaid via `vault-system-repay`) was computed only for the smaller `coll-final-raw` amount [3](#0-2) .

Because the liquidator controls `debt-amount` (capped only by `max-debt-usd`), they can pick a value that lands `coll-final-raw` just below `user-coll-balance` by a dust margin small enough that, at `BPS + liq-penalty-max` precision, `rem-debt-usd` rounds to zero. This flips the full-seizure branch without requiring the borrower to actually be in the full-liquidation LTV zone, and without the liquidator paying for the extra collateral. This is the same bug class as the external report: a caller-chosen input drives an internal rate/rounding computation to zero, bypassing the mechanism (partial-liquidation proportionality) meant to bound how much value the caller can extract per action.

### Impact Explanation
The borrower (an unprivileged, unrelated principal to the liquidator) has collateral removed without commensurate debt repayment — collateral is seized beyond the bound the graduated liquidation formula intends to allow for the given LTV/penalty. This is a direct, uncompensated transfer of the borrower's collateral to the liquidator, i.e. theft of user funds at rest, though bounded to "dust"-sized amounts per call (mirroring the external report's Low-impact/High-likelihood classification, since it can be repeated across many partial liquidations to accumulate value).

### Likelihood Explanation
Any address can call `liquidate()` on any borrower once the borrower is in the partial-liquidation LTV zone; the attacker fully controls `debt-amount`, `collateral-ft`/`debt-ft`, and can compute off-chain exactly which `debt-amount` drives `coll-remaining`'s USD value below the rounding threshold at `liq-penalty-max`. No special privileges or races are required, making this reliably repeatable.

### Recommendation
Do not grant the full `user-coll-balance` merely because the *rounded* remaining-debt calculation hits zero. Either: (a) require `remaining-debt-to-repay` and the corresponding `coll-remaining` USD value to be below an explicit minimum "dust" threshold set independently of user-controlled `debt-amount` before granting the full-balance branch, or (b) always keep `coll-final = coll-final-raw` and let the tiny genuinely-unremovable dust be handled by a separate, non-collateral-seizing sweep mechanism, so a liquidator cannot engineer the rounding boundary to seize uncompensated collateral.

### Proof of Concept
1. Borrower has collateral (asset A) and debt (asset B) with LTV in the partial-liquidation zone, yielding some `max-debt-usd` cap.
2. Attacker (liquidator) computes off-chain a `debt-amount` value close to, but under, `max-debt-usd` such that `coll-final-raw` (derived via `scale-debt-for-liquidation`) leaves `coll-remaining` with a USD value where `div-bps-down(rem-coll-usd, BPS + liq-penalty-max)` truncates to `0`.
3. Attacker calls `market.liquidate(borrower, collA, debtB, debt-amount, 0, none, none)`.
4. Contract sets `remaining-debt-to-repay = u0` per lines 1477-1485, then `coll-final = user-coll-balance` per line 1486, seizing the borrower's full remaining collateral in asset A while only repaying debt proportional to `coll-final-raw`.
5. Repeating across borrowers/assets accumulates uncompensated collateral extraction. [4](#0-3)

;; Graduated liquidation parameter calculation
;; Combines the 4-step liquidation factor calculation into a single helper
;; Returns: { liq-pct-scaled: uint, liq-penalty: uint, max-debt-usd: uint }
(define-private (calc-liquidation-params
  (current-ltv uint)
  (ltv-liq-partial uint)
  (ltv-liq-full uint)
  (liq-penalty-min uint)
  (liq-penalty-max uint)
  (curve-exponent uint)
  (total-debt-usd uint))
  
  (let ((liq-pct-linear (calc-liq-factor current-ltv ltv-liq-partial ltv-liq-full))
        (liq-pct-scaled (calc-liq-factor-exp liq-pct-linear curve-exponent))
        (liq-penalty (calc-liq-factor-bound liq-pct-scaled liq-penalty-min liq-penalty-max))
        (max-debt-usd (calc-liq-debt-repay total-debt-usd liq-pct-scaled)))
    {
      liq-pct-scaled: liq-pct-scaled,
      liq-penalty: liq-penalty,
      max-debt-usd: max-debt-usd
    }))
