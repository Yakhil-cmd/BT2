### Title
Webhook signature is verified against the organization derived from the payload, but the repository acted upon is taken from the same untrusted payload without cross-checking - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App config (and therefore which `webhook_secret`) to validate a webhook against by reading `repository.owner.login`/`organization.login` straight out of the unauthenticated request body. Every webhook `Handler` then separately reads `repository.full_name` from that very same body to decide which `Stack`/`Repository` records to mutate. Nothing binds these two payload-derived values to each other. If any configured GitHub organization has no `webhook_secret` set (documented as optional/`nil` in `config/secrets.development.example.yml`), signature verification for that organization is a no-op, letting an attacker submit a payload whose `owner.login` names the unsecured org while `repository.full_name` names a stack belonging to a completely different, secured organization.

### Finding Description
`verify_signature` resolves the GitHub App by organization taken from the request body, then verifies (or trivially "passes") the signature: [1](#0-0) [2](#0-1) 

and `verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that resolved organization: [3](#0-2) 

Separately, every handler (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, `MembershipHandler`, etc.) resolves the target repository/stacks from a *different* payload field, `repository.full_name`, with no relationship enforced back to the organization used for signature verification: [4](#0-3) [5](#0-4) 

This mirrors the reported bug class: one code path binds/authenticates on field A (`organization`/`repository.owner.login`), while the acting path consumes field B (`repository.full_name`) from the same unverified request, and the two are never proven to be the same entity - "an organization that authenticated versus the repository that is written."

### Impact Explanation
Shipit explicitly supports multi-organization GitHub App configuration where `webhook_secret` is optional per org (`config/secrets.development.example.yml`, `docs/setup.md`). Any deployment that configures several organizations and leaves `webhook_secret` blank for even one of them (e.g., a low-value/test org) allows an attacker who can reach `/webhooks` to:
- Set `repository.owner.login`/`organization.login` to the org with no secret so `verify_signature` accepts the request unconditionally, then
- Set `repository.full_name` to a stack under a *different, secured* organization,
to trigger unauthenticated cross-repository state changes: forcing `Stack#sync_github` on a foreign stack (`push` event), injecting fabricated commit `Status` records (`status` event) that influence deployability checks, forcing `RefreshCheckRunsJob` (`check_suite`), or creating/deleting `Team`/`Membership`/`User` records (`membership` event) - all without ever needing the secured organization's own webhook secret. This is a cross-repository write achieved purely by exploiting the mismatch between the authentication scope and the mutation scope of the same request.

### Likelihood Explanation
Exploitability depends entirely on operator configuration (at least one configured GitHub organization without a `webhook_secret`), which the engine explicitly allows and documents as valid/optional, and does not warn against when multiple organizations are configured. No credentials, sessions, or tokens are required to reach `/webhooks`; `WebhooksController` skips CSRF protection and only gates on `verify_signature`. Any external attacker with network access to the instance can attempt this once they know (or guess) that a configured org lacks a secret.

### Recommendation
Bind repository identity to the exact organization whose secret validated the request: after resolving `repository_owner`/`github_app`, verify that `payload.dig('repository','full_name')` (or `organization.login`) belongs to that same organization before dispatching to handlers, and reject the webhook otherwise. Additionally, treat an unset `webhook_secret` for a configured organization as "verification required but misconfigured" (fail closed) rather than "verification skipped" (fail open), mirroring how `add_market()`'s explicit `LT.setStaker()` call in the external report was added to make the later, indirect path enforce the same invariant as the primary path.

### Proof of Concept
1. Configure Shipit with two GitHub organizations: `secure-org` (has `webhook_secret` set) and `open-org` (no `webhook_secret`, per the documented optional config).
2. POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secure-org/production-stack"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: 'open-org')`; since that org has no `webhook_secret`, `verify_webhook_signature` returns `true` and the request proceeds.
4. `PushHandler#process` resolves stacks via `Handler#stacks`, which looks up `Repository.from_github_repo_name('secure-org/production-stack')` - a repository under the *secured* organization - and calls `stack.sync_github(expected_head_sha: ...)`, an action the attacker was never authorized to trigger for `secure-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
