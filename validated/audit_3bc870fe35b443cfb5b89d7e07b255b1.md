### Title
Address-definition validation trusts unresolved nested `['address', ...]` references by default, letting an unproven inner definition satisfy signature requirements - (File: definition.js)

### Summary
`validateDefinition()`'s handling of the `['address', other_address]` operator contains a hard‑coded, unconditional default (`bAllowUnresolvedInnerDefinitions = true`) that treats a *nested address reference whose definition cannot be resolved* as automatically satisfying the "has a signature" requirement, exactly mirroring the DeepSeek‑TUI pattern of an insecure default (`allow_shell = true` / `auto_approve = true`) that silently grants trust/capability the poster never explicitly requested or the validator never actually verified.

### Finding Description
When an address (or asset) definition contains an `['address', 'BASE32']` clause, `validateDefinition()` tries to resolve the referenced address's definition via `storage.readDefinitionByAddress`. If it is not found in storage, it falls back to checking whether the current unit's authors supply a matching definition (`author.definition` whose chash equals `definition_chash`). If **no** matching author-supplied definition exists at all, the code does not fail — it silently succeeds: [1](#0-0) 

The comment right above the assignment (`// if (objValidationState.bAllowUnresolvedInnerDefinitions) return cb(null, true);`) shows this used to be a conditional, context-controlled flag; it has been replaced with an unconditional local `var bAllowUnresolvedInnerDefinitions = true;`, so **every** call path into this branch now behaves as if the flag were granted, regardless of caller intent. This is the same class of bug as the report: a security-relevant boolean silently defaults to the permissive value (`true`) instead of the safe value (`false`), so a decision that should require proof (a valid signature/definition behind the referenced address) is instead granted unconditionally, `cb(null, true)`, meaning `evaluate()` reports that this branch "has a signature" even though nothing has actually been authenticated.

Since `validateDefinition` is called for every new address/asset definition posted to the DAG (unit validation, shared-address templates, AA-issued asset conditions, etc.), any composed definition that references another, not-yet-defined address inside an `and`/`or`/`r of set` clause will have that branch treated as cryptographically satisfied at *definition-validation* time. This is distinct from evaluation time authentication (`validateAuthentifiers`, which does independently check paths/signatures), but definition validation is the gate that decides whether a definition is well-formed and "has a signature in every branch" (see the check `if (!bHasSig && !bAssetCondition) return handleResult("each branch must have a signature")` at the end of `validateDefinition`): [2](#0-1) 

Because the definition-validity check is fooled into believing a signature exists, a poster can construct definitions/asset-condition trees where one branch of an `or`/`weighted and`/`r of set` references an address with no resolvable definition, and that branch is unconditionally counted as "has sig" — inflating `count_options_with_sig` in the outer combinators without any real cryptographic backing.

### Impact Explanation
An attacker (any unpriviledged unit poster or asset issuer) can craft an address or asset spending-condition definition containing a nested `['address', X]` reference to an address that intentionally has no definition posted anywhere and is not co-authored in the same unit. Definition validation will treat that leg as satisfied (`bHasSig=true`) even though it corresponds to zero actual cryptographic proof. Depending on how it's combined (e.g., `['or', [['address', X], ['sig', {...}]]]`, or as one leg of a `weighted and`/`r of set` with low threshold), this can let a spending condition pass definition validation while offering weaker real security than declared, or be used to satisfy conditions used for asset `issue_condition`/`transfer_condition`/AA asset `attestors` checks, or shared-address templates (`wallet_defined_by_addresses.js`, `wallet_defined_by_keys.js`) that build addresses using this validator — leading to spending conditions that pass validation without the represented signature guarantee, i.e., unauthorized spending potential once such an address receives funds and the "phantom" branch is exercised at evaluation time via other legitimate paths, or node disagreement about a definition's validity between nodes with different states of `objUnit.authors`.

### Likelihood Explanation
The vulnerable code path executes on any unit that defines an address/asset condition (or asset issue/transfer condition, or an AA asset's `attestors`) containing a nested `address` reference — a routine, always-reachable feature of oscript definitions available to any unprivileged unit poster, asset issuer, or AA. No special network position, hub, or peer trust is required; it triggers purely from validating locally-authored or trigger-driven definitions.

### Recommendation
Restore the intended conditional behavior instead of the hard-coded `true`:
- Remove the unconditional `var bAllowUnresolvedInnerDefinitions = true;` and either delete the fallback entirely (fail closed: `return cb("definition of inner address "+other_address+" not found")`) or gate it behind a genuinely controlled `objValidationState.bAllowUnresolvedInnerDefinitions` flag that is explicitly set to `true` only in contexts where it is provably safe (e.g., during initial multi-author unit composition where the peer's key literally isn't known yet), and defaults to `false` everywhere else.
- Add a regression test ensuring a definition referencing a genuinely unresolved/absent inner address (with no matching co-author definition) fails `validateDefinition`.

### Proof of Concept
1. Compose a unit whose author's address definition is:
   `['or', [['address', 'UNRESOLVABLE_ADDR_WITH_NO_DEFINITION'], ['sig', {pubkey: attacker_pubkey}]]]`
   where `UNRESOLVABLE_ADDR_WITH_NO_DEFINITION` is a syntactically valid BASE32 address that has never posted a definition and is not one of the unit's co-authors.
2. Submit the unit for validation. In `evaluate()` for the `'address'` op, `storage.readDefinitionByAddress` calls `ifDefinitionNotFound`; since `arrDefiningAuthors.length === 0`, the code hits line 297 and returns `cb(null, true)` — i.e., this leg is reported as "has signature."
3. In the outer `'or'` combinator, `count_options_with_sig` becomes `2` (both legs report `true`), so validation of the overall definition succeeds and reports `bHasSig = true`, even though only one real signature (`sig`) actually exists behind the whole tree.
4. This proves the root cause: `validateDefinition` in `definition.js` (lines 284–304) grants "has signature" credit to a branch that was never cryptographically proven, purely due to the hard-coded `true` default, analogous to the reported CVE's insecure `allow_shell=true`/`auto_approve=true` defaults silently escalating trust beyond what was actually approved or verified.
