### Title
Unbounded iteration over `storage.assocUnstableMessages` in `data_feeds.dataFeedExists()` / `readDataFeedValue()` allows cheap DoS of every AA that reads oracle data feeds - (File: data_feeds.js)

### Summary
`data_feeds.js` implements the `data_feed[[...]]` and `in_data_feed[[...]]` oscript primitives used by Autonomous Agents to read oracle values. When these primitives run inside AA formula evaluation (`bAA === true`), the implementation always scans **the entire set of currently-unstable units in the DAG** (`storage.assocUnstableMessages`), not just the units authored by the oracle addresses named in the formula. This mirrors the reported bug class: an array/collection that grows through cheap, permissionless operations (any address can post a `data_feed` unit) and is later iterated in full inside a hot, frequently-invoked function, creating unbounded computation cost.

### Finding Description
In `formula/evaluation.js`, the `data_feed` and `in_data_feed` cases call: [1](#0-0) 
`dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ifseveral, objValidationState.last_ball_timestamp, ...)`, passing `bAA` positionally as the `unstable_opts` argument of `readDataFeedValue(arrAddresses, feed_name, value, min_mci, max_mci, unstable_opts, ifseveral, timestamp, handleResult)`. [2](#0-1) 

Because `bAA` is true for every AA formula evaluation, `bIncludeUnstableAAs` is always true when the code runs as part of AA trigger processing, forcing execution of this loop: [3](#0-2) 
```
for (var unit in storage.assocUnstableMessages) {
    var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
    ...
    if (_.intersection(arrAddresses, objUnit.author_addresses).length === 0)
        continue;
    storage.assocUnstableMessages[unit].forEach(function (message) { ... });
}
```
The `for...in` walks **every unit currently tracked in `storage.assocUnstableMessages`** before the address filter (`_.intersection`) is even checked, so the cost is proportional to the total number of unstable units carrying `data_feed`/`definition`/`system_vote` messages network-wide, regardless of whether they belong to the oracle the AA is querying.

`dataFeedExists()` (the backing function for `in_data_feed[[...]]`) has the identical unconditional pre-filter loop: [4](#0-3) 

Any address can permissionlessly post a unit containing a `data_feed` message (this is exactly how oracles publish data, and nothing restricts who may post one), which is added to `storage.assocUnstableMessages` and remains there — and therefore in the iterated set — until the unit stabilizes. By repeatedly posting many cheap `data_feed` units (or `definition`/`system_vote` messages, which use the same associative map) that stay unstable for a while, an attacker inflates the size of this collection at negligible cost.

### Impact Explanation
`data_feed[[...]]` / `in_data_feed[[...]]` are core, widely used AA primitives (price oracles, KYC/attestor checks, etc.), executed synchronously as part of deterministic AA trigger handling during `saveJoint` → `aa_composer.handleAATriggers()`. If the number of unstable units carrying data-feed/definition/system-vote payloads is inflated, **every** AA trigger that reads any oracle feed pays the full scan cost, on **every full node**, for **every trigger**. Because this happens inside the deterministic execution path that gates unit stabilization and further trigger processing, sufficiently large unstable-message backlogs can materially slow down or stall AA-trigger processing network-wide, delaying confirmation of the units depending on it. This is a Medium-severity computational DoS vector reachable by any unprivileged unit poster, analogous to the reported `getTotalDeposit()`/`getDepositOf()` unbounded-loop issue where a cheap, adversary-controlled write inflates a collection that a critical read path later iterates in full.

### Likelihood Explanation
Low cost, no special privilege required: anyone can post `data_feed` messages (there is no authorization check restricting who can be an "oracle"), and posting many such units cheaply grows `storage.assocUnstableMessages`. The attack becomes effective any time this map grows large relative to normal operation (e.g., during periods of DAG congestion or sustained spam), amplifying cost for any AA using `data_feed`/`in_data_feed`, which are extremely common in practice.

### Recommendation
- In `dataFeedExists()` and `readDataFeedValue()`, avoid the unconditional `for...in storage.assocUnstableMessages` scan. Maintain a secondary index keyed by author address (e.g., `assocUnstableMessagesByAuthor[address]`) so lookups only touch units authored by the addresses actually referenced by `arrAddresses`, rather than every unstable unit in the DAG.
- Alternatively, cap/charge oscript complexity proportional to the number of unstable units scanned so the cost is reflected in the AA's own complexity/oplimit budget rather than being externally imposed for free.

### Proof of Concept
1. Attacker controls address `X` (any address, no special role required).
2. Attacker repeatedly posts cheap units containing a `data_feed` message from `X` (arbitrary `feed_name`/value), keeping many of them unstable (e.g., by using low commissions/witness lists that slow stabilization, or simply during periods of network congestion), which populates `storage.assocUnstableMessages` for each such unit. [5](#0-4) 
3. Any legitimate AA that evaluates `data_feed[[oracles=..., feed_name=...]]` or `in_data_feed[[...]]` while these units remain unstable now executes the `for (var unit in storage.assocUnstableMessages)` loop over the inflated set on every node, for every trigger, before it even checks whether the unit's author matches the AA's queried `oracles` address. [6](#0-5) 
4. As the attacker keeps the unstable set large, AA trigger processing latency for all AAs using oracle feeds increases proportionally, network-wide, since every node performs the identical deterministic work.
