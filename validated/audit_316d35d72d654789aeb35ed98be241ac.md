### Title
CCMenuController bypasses stack-scoped ApiClient authorization, allowing a token authorized for one stack to read the build status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` can be scoped to a single stack via its optional `belongs_to :stack` association [1](#0-0) . `Api::BaseController` enforces this scope centrally by restricting the queryable `Stack` relation to `current_api_client.stack_id` whenever it is set, and `#stack` is derived from that scoped relation [2](#0-1) . `Api::CCMenuController`, however, defines its own `#stack` method that resolves directly via `Stack.from_param!(params[:stack_id])`, completely bypassing the scoped `stacks` helper [3](#0-2) . The only authorization check applied is `require_permission :read, :stack`, which merely verifies that `"read:stack"` is present in the client's `permissions` list and never compares the requested stack to the client's `stack_id` [4](#0-3) .

### Finding Description
This is a direct analog of the reported bug class: a verified credential legitimately authorizes one scope (`stack_id` bound to the token), but the code path that acts on the request uses a different, unchecked value (`params[:stack_id]`) for the actual resource touched. The equality that should hold and is broken is:

`current_api_client.stack_id == stack_id_actually_served`

In `Api::BaseController`, this equality is enforced by scoping the `Stack` relation before resolving `from_param!` [2](#0-1) . Every other controller that relies on the inherited `#stack`/`#stacks` methods (e.g. `Api::StacksController`) is protected. `Api::CCMenuController` re-defines `#stack` to query `Stack.from_param!(params[:stack_id])` unconditionally, so a stack-scoped token can address any stack in the installation simply by changing the `stack_id` route parameter [3](#0-2) .

The feature of scoping `ApiClient` to a single stack is not dead code — the test suite exercises exactly this scenario ("an api client scoped to a stack will only see that one stack") to confirm the base controller enforces per-stack isolation [5](#0-4) , proving the scoping mechanism is an intended security boundary that `CCMenuController` fails to respect.

### Impact Explanation
A caller in possession of a valid `read:stack` token that was only ever authorized for one specific stack (their own project) can call `GET /api/1/stacks/:stack_id/ccmenu.xml` for any other stack_id in the Shipit installation and receive that stack's deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`) [6](#0-5) . This is an authorization escalation beyond the credential's granted scope, matching the High-severity bucket "escalation into authorization... unauthenticated [i.e. out-of-scope] read of stack state" since the token holder reads state of stacks/repositories they were never granted access to.

### Likelihood Explanation
Likelihood is moderate-to-high in any multi-tenant Shipit deployment that issues per-stack scoped `read:stack` tokens (the scoping mechanism exists precisely for this purpose, per `belongs_to :stack, optional: true` and the covering test). Any holder of such a token needs no additional privilege — only to change the `stack_id` in the URL — to read arbitrary stacks' CI status.

### Recommendation
Remove the private `#stack` override in `Api::CCMenuController` and instead reuse the inherited, properly scoped `#stack`/`#stacks` helpers from `Api::BaseController` (i.e., resolve via `stacks.from_param!(params[:stack_id])`) so that stack-scoped tokens cannot address stacks outside their authorized `stack_id`.

### Proof of Concept
1. Create/obtain a stack-scoped `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to stack A (as exercised by `authenticate!(:here_come_the_walrus)` in the test suite) [7](#0-6) .
2. Using that client's `authentication_token`, call:
   `GET /api/1/stacks/<stack_B_id>/ccmenu.xml?token=<token>` where stack B is a different, unauthorized stack.
3. `CCMenuController#authenticate_api_client` accepts the token via the query string [8](#0-7) , `require_permission :read, :stack` passes because the permission list contains `read:stack` regardless of which stack is requested, and `#stack` resolves stack B directly via `Stack.from_param!`, returning stack B's build status even though the token was only authorized for stack A.
