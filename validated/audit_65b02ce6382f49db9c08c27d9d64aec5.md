### Title
Unvetted route contracts can attach wallet-draining transfers to strategy authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept caller-provided route bytes and invoke the configured router after authorizing only the controller's exact input transfer. The router dispatches those routes to payload-selected pool contracts without an on-chain venue-address allowlist. A malicious route contract can therefore execute below the user's `require_auth` tree and request an unrelated `token.transfer(user, attacker, amount)`; if the victim signs the simulated authorization tree, the transfer succeeds even though the requested lending operation appears legitimate. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Controller strategy swaps authorize only `token_in.transfer(controller, configured_router, amount_in)`, but they do not constrain which contracts the router reaches while interpreting the supplied `swap` payload. [1](#0-0) 

The router resolves venue behavior from the route and dispatches to the payload-selected pool address; the balance checks validate router-side input and output deltas, but do not prove that the called venue is an expected deployment or that it made no unrelated authorization requests. [4](#0-3) 

The strongest reachable path is `controller.swap_collateral(caller, account_id, current, amount, new, swap)`, where `caller` is the account owner and `swap` names an attacker-deployed contract behind a supported venue opcode. [5](#0-4) 

During the nested venue call, that contract can invoke an unrelated token's `transfer(victim, attacker, amount)`; Soroban records this as a child authorization beneath the victim's controller call, and enforcement accepts it when the victim signs that child invocation. [3](#0-2) 

The repository's harness demonstrates the complete behavior: simulation records the theft transfer under the victim's `swap_collateral` authorization, a root-only signed tree rejects it, and signing the poisoned simulated tree moves the victim's unrelated wallet tokens to the attacker. [6](#0-5) [7](#0-6) [3](#0-2) 

### Impact Explanation
A malicious route can steal arbitrary tokens from the wallet of the user who signs the poisoned authorization tree, independent of the routed collateral amount. [8](#0-7) [9](#0-8) 

The controller's measured output and final account-risk checks do not bound this loss because the stolen token need not be the swap input, the swap output, or a listed lending asset. [10](#0-9) [11](#0-10) 

### Likelihood Explanation
Execution requires user interaction because the victim must sign the authorization tree containing the rogue child transfer; an attacker cannot directly authorize another user's wallet. [7](#0-6) 

The practical exposure remains material because routes are opaque XDR bytes supplied to user-facing strategy calls, and the malicious transfer can be represented in simulation output as an additional authorization rather than as an obvious strategy argument. [12](#0-11) [13](#0-12) 

### Recommendation
Require every route hop's pool address and venue adapter to resolve to a governance-approved or otherwise trusted venue registry before invocation; payload-provided pool addresses must not be sufficient to place arbitrary contracts inside the authorization tree. [2](#0-1) 

Until routes are constrained on-chain, wallets and integrators must decode the route and reject any authorization tree containing child invocations other than the controller's expected exact input transfer. [14](#0-13) 

### Proof of Concept
1. Deploy a malicious contract exposing the ABI expected by a supported route opcode; its swap implementation preserves the router's expected input/output balance deltas and additionally calls `unrelated_token.transfer(victim, attacker, victim_balance)`. [15](#0-14) 
2. Construct `swap_collateral(victim, account_id, USDC, amount, ETH, swap)` where `swap` routes through the malicious contract while declaring a sufficient `min_out`. [5](#0-4) 
3. Simulate the transaction; the recorded victim authorization contains the controller call plus a child `unrelated_token.transfer(victim, attacker, victim_balance)`. [13](#0-12) 
4. If the victim signs that returned tree, the unrelated token balance moves to the attacker while the strategy can still satisfy its measured output and account checks. [3](#0-2)

**File:** docs/explanation/threat-model.md (L154-164)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
