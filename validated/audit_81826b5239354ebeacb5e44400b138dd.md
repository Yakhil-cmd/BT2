### Title
Rule-cap check runs per-tier inside the loop, letting a padded lower-precedence `security-patterns.yaml` silently starve the higher-precedence project-local override file - ([File: plugins/security-guidance/hooks/extensibility.py])

### Summary
`_load_user_patterns` iterates the three precedence tiers (`User`, `Project`, `Project (local)`) and checks `if len(rules) >= PATTERN_MAX_RULES: break` after each tier is fully loaded, rather than truncating only after all tiers are merged. A committed `.claude/security-patterns.yaml` (attacker-controlled repo content, e.g. via a PR) that supplies `PATTERN_MAX_RULES` (50) valid entries causes the loop to `break` before the gitignored, higher-precedence `.claude/security-patterns.local.yaml` is ever opened, so the project owner's local override/addition rules are silently dropped.

### Finding Description
`_config_paths` returns the three config locations in ascending precedence order — `User` → `Project` → `Project (local)` — with the comment stating "project local, gitignored" is meant to be the most authoritative, per-repo tier [1](#0-0) . `_load_user_patterns` loads each tier's file, validates its entries, appends them to the shared `rules` list, and only then evaluates the cap: [2](#0-1) 

Because the `len(rules) >= PATTERN_MAX_RULES` check sits inside the per-label loop and executes right after the `Project` tier is processed, a committed (non-gitignored, attacker-reachable via ordinary PR content) `security-patterns.yaml` with ≥50 valid entries makes the loop `break` before the `Project (local)` candidate path is even opened. The higher-precedence, user-authored `security-patterns.local.yaml` — meant to add or override behavior for that specific checkout — is never read, with no warning or debug_log entry beyond the generic truncation message that fires only when the final `rules` list itself exceeds the cap (which won't trigger here, since exactly 50 rules were loaded from `Project` alone).

This defeats the precedence invariant the module's own docstring promises ("Discovery, in precedence order... project local"), because the *volume* of lower-precedence content (fully attacker-controllable, since `Project`-tier `.claude/security-patterns.yaml` is ordinary repo content merged via normal PR review) determines whether higher-precedence content is loaded at all, rather than precedence determining what is kept.

### Impact Explanation
The custom pattern rules only add additive PostToolUse regex/substring "reminders" merged into the LLM review prompt — they cannot disable built-in patterns and are not used for command blocking or approval decisions. Still, this is a genuine trust-boundary/precedence bypass: it lets ordinary, PR-reviewable repository content (the checked-in `Project` tier) silently neutralize a repo maintainer's local, gitignored security configuration (`Project (local)` tier) intended to be authoritative for that specific working copy, weakening the project's custom security detection without any error surfaced to the user. This matches a trust-boundary-bypass class of impact rather than a hard RCE/secret-disclosure primitive.

### Likelihood Explanation
Fully feasible and repeatable: an attacker only needs to get a `.claude/security-patterns.yaml` with `PATTERN_MAX_RULES - 1` (49) or more syntactically valid entries merged into the repository (e.g., via a normal PR), which requires no special privilege beyond ordinary contribution. The victim's own `.claude/security-patterns.local.yaml` (gitignored, so its content is irrelevant to the attack — only its *existence* and intended enforcement matter) will then be skipped every time `load_for_session` runs for that checkout, deterministically and silently.

### Recommendation
Move the cap check outside the per-label loop so all three tiers are read and merged first (in precedence order), and only then truncate the combined list to `PATTERN_MAX_RULES`, preferring to keep the highest-precedence entries when truncating (e.g., truncate from the front of the lower-precedence entries, not indiscriminately from the end of the concatenated list). At minimum, log a debug warning when a lower-precedence tier's rule count alone reaches the cap, since that silently forecloses loading of higher-precedence tiers.

### Proof of Concept
Unit test in the style of the existing extensibility tests:
1. Create a temporary `cwd` with `.claude/security-patterns.yaml` containing 50 valid, distinct pattern entries (e.g. `rule_name: pad-N`, `substrings: ["padN"]`, `reminder: "pad"`).
2. Create `.claude/security-patterns.local.yaml` containing one distinguishing entry, e.g. `rule_name: local-override`, `substrings: ["localOverride"]`, `reminder: "must be enforced"`.
3. Call `load_for_session(cwd)` then `user_patterns()`.
4. Assert: `"user:local-override"` is present in the returned list's `ruleName` values.
5. Expected current (buggy) behavior: assertion fails — `local-override` is absent because the loop broke after the `Project` tier hit the 50-rule cap, before `Project (local)` was ever opened.
6. After the fix (merge-then-truncate with precedence-aware ordering), the assertion should pass, confirming the project-local rule is preserved regardless of `Project`-tier rule volume.

def _config_paths(cwd: Optional[str], basename: str) -> List[Tuple[str, str]]:
    """Existing config file paths, lowest precedence first (so concat reads in
    precedence order user → project → project-local). Truncation is done on
    the concatenated string, so lowest-precedence content is dropped last."""
    paths = [("User", os.path.expanduser(os.path.join("~", ".claude", basename)))]
    if cwd:
        paths.append(("Project", os.path.join(cwd, ".claude", basename)))
        # claude-security-guidance.local.md / security-patterns.local.yaml
        stem, ext = os.path.splitext(basename)
        paths.append(("Project (local)", os.path.join(cwd, ".claude", f"{stem}.local{ext}")))
    return paths
```

def _load_user_patterns(cwd: Optional[str]) -> List[Dict[str, Any]]:
    rules: List[Dict[str, Any]] = []
    for label, path in _config_paths(cwd, "security-patterns"):
        # _config_paths returns an extensionless stem (e.g.
        # ".claude/security-patterns" or ".claude/security-patterns.local");
        # try each supported extension.
        for ext in (".yaml", ".yml", ".json"):
            candidate = path + ext
            data = _read_config(candidate)
            if data is None:
                continue
            for entry in (data or {}).get("patterns", []):
                rule = _validate_pattern(entry, source=label)
                if rule:
                    rules.append(rule)
            break  # found one extension; don't double-load .yaml AND .json
        if len(rules) >= PATTERN_MAX_RULES:
            break
    if len(rules) > PATTERN_MAX_RULES:
        debug_log(f"extensibility: {len(rules)} user patterns > cap {PATTERN_MAX_RULES}; truncating")
        rules = rules[:PATTERN_MAX_RULES]
    return rules
```
