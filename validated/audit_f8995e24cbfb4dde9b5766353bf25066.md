### Title
Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` enables unauthorized merge-queue merges - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha` across the entire database, with no scoping to the repository that sent the webhook, and the controller-level signature check only proves the payload came from *some* registered GitHub org/app, not that the `sha` inside the payload actually belongs to that org's repository. An attacker who controls an unrelated repository B (and therefore a legitimately signed webhook channel) can forge a `status` event naming the head SHA of a pull request queued in a `merge_queue_enabled` stack of repository R, flipping both `Stack#merge_status` and `MergeRequest#all_status_checks_passed?` to `true` and triggering an unauthorized merge via `ProcessMergeRequestsJob`.

### Finding Description
Binding claimed: `actor authorizing merge of R's PR == actor who supplied the passing status`. Actual: an attacker on repository B, with no relationship to R, can supply the passing status that authorizes R's merge.

Code path:
- `WebhooksController#verify_signature` resolves the signing secret via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the untrusted JSON payload (`params.dig('repository','owner','login')`), see [1](#0-0)  and [2](#0-1) . This only proves the request was signed with organization B's (the attacker's own, legitimately configured) secret — it proves nothing about the `sha` field elsewhere in the same payload.
- `StatusHandler#process` then applies the status to **every** commit in the database matching that `sha`, regardless of which stack/repository it belongs to: [3](#0-2) 
- `Commit#create_status_from_github!` / `Status.replicate_from_github!` records the forged status tied to the commit's actual `stack_id`, unconditionally: [4](#0-3)  and [5](#0-4) .
- `Stack#merge_status` and `Stack#allows_merges?` derive purely from the resulting status/commit state: [6](#0-5) [7](#0-6) .
- `MergeRequest#all_status_checks_passed?` evaluates only the statuses attached to `head`: [8](#0-7) .
- `ProcessMergeRequestsJob#perform` reads exactly these two derived booleans and, if both are true, calls `merge_request.merge!`, which invokes `stack.github_api.merge_pull_request`: [9](#0-8) [10](#0-9) .

Exploit flow: attacker (a) obtains the public head SHA of the victim's queued PR (visible on GitHub / via the PR itself), (b) POSTs `/webhooks` with `X-Github-Event: status`, a payload whose `repository.owner.login` is the attacker's own org B (so the signature validates against B's webhook secret), and `sha` set to the victim commit's SHA and `state: success`, (c) the handler updates the (unrelated) victim commit's status, flipping `merge_status` to `success` and `all_status_checks_passed?` to `true`, (d) `ProcessMergeRequestsJob` (already scheduled or scheduled by any subsequent stack activity) merges the PR.

None of the listed guards prevent this: `verify_signature` validates a signature keyed by attacker-controlled `repository_owner`, not by SHA-repository binding; `ExplicitParameters` only validates payload shape (`sha`/`state` types), not ownership; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler#process`.

### Impact Explanation
A single forged webhook from an attacker's own repository allows fully automated, unauthorized merging of a pull request in any other onboarded repository/stack that has `merge_queue_enabled`, without any interaction from the PR author, reviewer, or Shipit operator. This is a cross-tenant authorization bypass: repository B's webhook traffic mutates repository R's stack/commit/merge state and triggers a privileged GitHub API action (`merge_pull_request`) using Shipit's own GitHub credentials. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." It is repeatable against any stack/PR whose head SHA the attacker can learn (trivial for public repos).

### Likelihood Explanation
Preconditions: the target stack must have `merge_queue_enabled: true` and a PR already queued (`pending`) or one the attacker also enqueues by other means; the attacker needs a Shipit-registered repository (or org) of their own to source a validly-signed webhook, and needs to know the victim commit's SHA (trivially available for any public GitHub PR, and often inferable even for private ones via other engine surfaces). No GitHub or Shipit secrets are required beyond the attacker's own legitimately-provisioned webhook secret for their own repo. This is low-cost, deterministic, and repeatable — not dependent on any actual SHA-1 collision, since the handler never checks the SHA belongs to the claimed repository/org at all.

### Recommendation
Scope `StatusHandler#process` (and any handler using `Commit.where(sha:)`) to the repository identified by the incoming payload: resolve the target `Stack`/`Repository` from `params.dig('repository','full_name')`/`owner`+`name`, and restrict the `Commit` lookup to `stack.commits.where(sha: params.sha)` (or otherwise verify the commit's `stack.repository.full_name` matches the payload's `repository.full_name`) before applying any status. Additionally, consider deriving the signature-verification key from the repository actually referenced by the commit being mutated, not solely from attacker-supplied `repository.owner.login`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, ActionDispatch::IntegrationTest):
```ruby
test "cross-repo status forgery merges an unrelated PR" do
  victim_stack = shipit_stacks(:shipit) # merge_queue_enabled: true, owned by repo R
  merge_request = shipit_merge_requests(:shipit_pending) # queued PR in R
  victim_sha = merge_request.head.sha

  # Binding under test, BEFORE:
  assert_not_equal 'success', victim_stack.merge_status
  refute merge_request.all_status_checks_passed?

  # Attacker controls repo B (their own org), with a legitimately configured webhook secret for B
  GithubApp.any_instance.stubs(:verify_webhook_signature).returns(true) # simulates a validly-signed payload from B

  forged_payload = {
    sha: victim_sha,           # victim's PR head SHA, taken from R, not B
    state: 'success',
    context: 'attacker/forged-ci',
    repository: { owner: { login: 'attacker-org' }, full_name: 'attacker-org/unrelated-repo' }
  }

  post '/webhooks', params: forged_payload.to_json,
       headers: { 'X-Github-Event' => 'status', 'Content-Type' => 'application/json' }

  # Binding under test, AFTER — should NOT change for repo R from an unrelated repo B's webhook:
  assert_equal 'success', victim_stack.reload.merge_status
  assert merge_request.reload.all_status_checks_passed?

  Shipit.github.api.expects(:merge_pull_request).once
  ProcessMergeRequestsJob.new.perform(victim_stack)
end
```
This demonstrates both halves of the equality (`merge_status == 'success'` and `all_status_checks_passed? == true`) becoming true from a single cross-repo forged status, and `merge_pull_request` being invoked without any actor authenticated against repository R.

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
