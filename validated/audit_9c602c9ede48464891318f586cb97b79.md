### Title
Cross-organization webhook forgery via organization-scoped signature verification not bound to the repository written by handlers - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the inbound `X-Hub-Signature` against by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted, attacker-supplied JSON body, while the downstream event handlers resolve the actual `Repository`/`Stack` to write to using a *different* field of that same untrusted body (`repository.full_name`). Nothing binds these two fields together, so the organization whose secret authenticates the request is not guaranteed to be the organization whose repository is actually mutated.

### Finding Description
`verify_signature` picks the GitHub App config purely from the payload: [1](#0-0) [2](#0-1) 

`Shipit::GitHubApp#verify_webhook_signature` then HMACs the raw body against whichever organization's `webhook_secret` was resolved from that *same* untrusted payload field: [3](#0-2) 

Shipit explicitly supports hosting multiple, independently-configured GitHub organizations from a single instance, each with its own `webhook_secret`/`app_id`/`private_key`: [4](#0-3) [5](#0-4) 

Once signature verification passes, `create` dispatches the raw parsed body to every registered handler for the event, with no re-check of which organization it belongs to: [6](#0-5) 

Every handler resolves its target repository from `payload.dig('repository', 'full_name')` — a field independent of the `owner.login`/`organization.login` field used for signature selection: [7](#0-6) [8](#0-7) [9](#0-8) 

Because `full_name` and `owner.login` are two independent, attacker-controlled JSON fields in the same request, an attacker who legitimately administers a *lower-trust* GitHub organization onboarded to the same Shipit instance (and therefore knows/controls that organization's `webhook_secret`, since GitHub signs webhook deliveries using whatever secret was configured for that org's app) can craft a payload where:
- `organization.login` / `repository.owner.login` = their own org ("OrgTwo") → used only to pick the secret that validates the HMAC,
- `repository.full_name` = `"OrgOne/some-tracked-repo"` → used by every handler to look up and mutate the actual tracked `Repository`/`Stack`/`Commit`/`PullRequest`.

`verify_signature` succeeds (the signature is valid for OrgTwo), but the handlers act on OrgOne's data. This breaks the binding "organization authenticated == repository written," letting the request pass authentication for one org while performing writes against another org's resources — a cross-repository/cross-organization write analogous to the report's core flaw (a value trusted and acted upon that is never actually covered/bound by the check that "verified" the request).

This is directly analogous to the external report's root cause: the bug there was that `l1BurntAmountOf[l1Depositor]` was updated using an untrusted ordering/value with no monotonic check tying it to what was actually verified/expected, letting a caller (anyone able to replay messages) desynchronize the state that gated fund distribution. Here, the "state that gates the write" (which secret authenticated the call) is never tied to "the state actually written" (which repository/stack is mutated), for the same structural reason: two independent fields of the same untrusted input are used for two different trust decisions without cross-validation.

### Impact Explanation
Depending on which handler is invoked, this allows an attacker who only controls one, less-trusted organization tracked by a shared Shipit instance to forge events against another organization's tracked repositories/stacks without ever holding credentials there:
- `PushHandler` triggers `stack.sync_github` for an arbitrary target stack/branch belonging to the victim org.
- `PullRequest::*Handler`s create/update `PullRequest`/review-stack records tied to the victim org's repository.
- `StatusHandler`/`CheckSuiteHandler` (registered as default handlers) create `Status`/check-run state on commits belonging to the victim org's repository — data Shipit's deploy safety logic consults when deciding whether a commit is deployable.

Writing to another organization's `Repository`/`Stack`/`Commit` state that this Shipit instance did not intend to trust the attacker's org with meets the "cross-repository writes" criterion, and forging commit-status/check-run state that feeds deploy-safety decisions can translate into an unauthorized deploy path.

### Likelihood Explanation
This requires the deployment to be configured with more than one GitHub organization (a documented, supported configuration) and requires the attacker to be a legitimate administrator/owner of one of the less-trusted organizations onboarded to the shared instance — not a privileged Shipit user, `ApiClient` token holder, or someone with access to the victim organization. Given multi-tenant Shipit deployments (shared internal deploy tooling serving many orgs/teams) are an intended use case per the documentation, this is a realistic configuration, though it does not apply to single-organization deployments where `repository_owner` must match the one configured organization or the request is rejected.

### Recommendation
In `WebhooksController#verify_signature` / `create`, after resolving `github_app` from the payload's claimed organization, re-validate that every `repository.full_name` referenced later in the payload/handlers actually belongs to that same organization (e.g., assert `repository.full_name.split('/').first == repository_owner`) before dispatching to handlers, rejecting the request otherwise.

### Proof of Concept
Given a Shipit instance configured with two organizations, `OrgOne` (victim, tracked repo `OrgOne/prod-app`) and `OrgTwo` (attacker-administered, webhook secret known to the attacker):

1. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "OrgOne/prod-app",
    "owner": { "login": "OrgTwo" }
  }
}
```
2. Attacker computes `X-Hub-Signature` using `OrgTwo`'s `webhook_secret` (which they control/know as an OrgTwo admin) over the raw body.
3. `verify_signature` resolves `Shipit.github(organization: "OrgTwo")` (from `repository.owner.login`) and validates the signature successfully against `OrgTwo`'s secret: [1](#0-0) .
4. `create` dispatches to `PushHandler`, which resolves the target stacks via `payload.dig('repository','full_name')` = `"OrgOne/prod-app"`: [7](#0-6) [10](#0-9) , triggering `stack.sync_github` for the victim's stack despite the request only being authenticated as belonging to `OrgTwo`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
