### Title
Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` purely by matching `sha` across the entire `commits` table, with no scoping to the repository that the webhook signature was verified against. Because git commit SHAs are content-addressed and portable between repositories, an attacker who controls an unrelated repository whose commits/statuses reach Shipit through a legitimate GitHub App installation can post a real, correctly-signed `status` webhook that attaches a forged `success` status to a commit that actually belongs to the victim stack.

### Finding Description
Binding claimed to hold: `repository_owner`/`repository.full_name` in the verified webhook payload == the repository that owns the `Commit` row being mutated. This binding is **broken**.

- `WebhooksController#verify_signature` only verifies that the payload was really sent by GitHub for the organization named in `payload['repository']['owner']['login']`, via `Shipit.github(organization: repository_owner)` and `GitHubApp#verify_webhook_signature` [1](#0-0) . It says nothing about which *stack/commit* the event is allowed to affect.
- `PushHandler`, the sibling handler, correctly scopes writes to the right tenant by resolving `stacks` from `Repository.from_github_repo_name(repository_name)` before touching any records [2](#0-1) [3](#0-2) .
- `StatusHandler#process`, in contrast, never uses `repository_name`/`stacks` at all. It does a global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . Any `Commit` row in the database with a matching `sha`, belonging to *any* stack/repository, is mutated.
- Because git SHA1s are a hash purely of commit content (tree, parents, author/committer, timestamps, message), an attacker can reproduce a byte-identical commit object (same sha) inside a repository they own — e.g. by fetching the object from the victim's public repository and re-pushing it — without any access to the victim repo's write permissions.
- The attacker's own repository, if covered by a GitHub App/webhook installation that Shipit is configured for, will have its own commit-status events delivered to Shipit with a legitimate GitHub signature (computed with the real secret for that org/app — the attacker does not need to know or forge the secret; GitHub computes and sends it for events on the attacker's own repo).
- `Commit#create_status_from_github!` then writes a `Status` for the victim's `Commit` row via `statuses.replicate_from_github!` [5](#0-4) , and `add_status` re-evaluates `deployable?`/`schedule_continuous_delivery`, `schedule_merges`, and emits `deployable_status`/`commit_status` hooks [6](#0-5) [7](#0-6) . If the victim stack has `continuous_deployment?` enabled and the forged status flips `success?` to true, `ContinuousDeliveryJob.perform_later(stack)` is queued with zero human review — `Shipit.user` (a system actor) is the one that ends up approving the ref for deploy, not an authorized operator of the victim stack.

I was not able to fully re-trace, within the remaining tool budget, the downstream chain from `ContinuousDeliveryJob` → `Stack#trigger_deploy`/`build_deploy` → `Task#run!` → `Command#start`/`PTY.spawn` to confirm the exact env keys (`GIT_ASKPASS`, `GITHUB_TOKEN`) passed to the shell. That specific final leg is asserted by the question but not independently re-verified here; the confirmed, exploitable defect is the tenant-isolation break in `StatusHandler`, which is sufficient on its own to falsify CI state for another team's stack and is the documented trigger for `schedule_continuous_delivery`.

### Impact Explanation
An attacker who owns an unrelated repository can forge a passing CI status on a commit belonging to a victim stack they do not control, as long as they can reproduce the sha (trivial for any public commit) and their own repo is wired into the same Shipit instance's GitHub App/webhook plumbing. This is a cross-tenant write: "a payload for one repository mutating another's stack/commit," matching the Critical impact category. If the victim stack has continuous deployment enabled, this can escalate into an unauthorized deploy being queued without any human review, since the deploy path is driven entirely by `Shipit.user` reacting to the (forged) commit status rather than by an authenticated operator action.

### Likelihood Explanation
Requires: (1) the victim stack/commit's sha, which is public for public repositories; (2) the attacker's own repository being covered by a GitHub App/webhook configuration that Shipit trusts (a real precondition — not guaranteed for arbitrary attacker repos, but common when Shipit's GitHub App/webhook is installed org-wide or when multiple orgs onboard their own apps); (3) the victim stack having `continuous_deployment?` enabled for the deploy-trigger escalation (the status-forgery itself requires none of that). The attack costs the attacker nothing beyond pushing a commit and posting a status to their own repo — fully repeatable against any commit sha they can reproduce, across any number of victim stacks in the same Shipit instance.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` is scoped: resolve the commit only within stacks belonging to the repository named in the verified payload (e.g. `stacks.commits.where(sha: params.sha)` using the `Handler#stacks`/`repository_name` helper) instead of a global `Commit.where(sha:)` lookup.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook for repo A cannot alter a commit belonging to repo B's stack" do
  victim_stack = shipit_stacks(:shipit)                     # repo owner/victim
  victim_commit = victim_stack.commits.create!(sha: "a" * 40, message: "victim work")

  # Attacker's payload claims a *different* repository, but reuses the victim's sha
  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  # Binding under test: only a status signed for victim_stack's own repository
  # should be able to flip victim_commit.status/state.
  assert_not_equal 'success', victim_commit.status.state,
    "status from an unrelated repository must not mutate the victim stack's commit"
end
```
This demonstrates that `StatusHandler` writes the forged status onto `victim_commit` even though the payload names `attacker/unrelated-repo`, confirming the missing repository-scoping is the root cause.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
