### Title
Cross-repository commit status forgery via SHA lookup in `Shipit::Webhooks::Handlers::StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits by a global `Commit.where(sha: params.sha)` lookup with no scoping to the repository that authenticated the webhook, so a `status` webhook validly signed for an attacker-owned repository can write attacker-controlled status content onto any other stack's commit row that happens to share the same SHA (trivially achievable via a fork, since git commit SHAs are content-addressed and identical across forks/mirrors of the same history). The resulting `Commit#add_status` then fires `Hook.emit(:commit_status, stack, ...)` / `Hook.emit(:deployable_status, stack, ...)` using the **victim's** stack but attacker-controlled `state`/`description`/`target_url` fields.

### Finding Description
The binding the system needs to hold is: `verified_org` (the GitHub organization whose signature was validated in `WebhooksController#verify_signature`, derived from `params.dig('repository','owner','login')`) `==` `commit.stack`'s owning repository, for every `commit` on which `StatusHandler` acts.

Trace:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only proves the raw payload was signed by GitHub for `repository_owner` — the org named inside the attacker's *own* payload. It never re-checks that org against anything downstream.
2. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
   ```ruby
   Commit.where(sha: params.sha).each do |commit|
     commit.create_status_from_github!(params)
   end
   ```
   This looks up *every* `Commit` row across *all* stacks/repositories sharing that `sha` — there is no `stack_id`/repository filter tying the lookup back to `repository_owner`/`repository.full_name` from the same payload.
3. `Commit#create_status_from_github!` → `add_status` (app/models/shipit/commit.rb:165-169, 366-386) persists a new `Status` from the attacker-supplied `params` (`state`, `description`, `target_url`, `context`, `created_at`) onto the matched commit, then emits:
   ```ruby
   Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status))
   Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
   ```
   `stack` here is `commit.stack` — i.e., whichever stack owns the matched `Commit` row, **not** the stack corresponding to the org that was verified in step 1.

Because git commit hashes are content-addressed and independent of which remote/org hosts them, an attacker who forks the victim's repository (or otherwise controls a repository sharing history with the victim) shares identical commit SHAs for any unmodified commits. The attacker can trigger a genuine, correctly-signed GitHub `status` webhook for their own fork (e.g., via the Statuses API on their own token/App install) referencing a SHA that also exists as a `Shipit::Commit` row under the victim's stack. `verify_signature` passes because the signature is valid for the attacker's own org. `StatusHandler` then finds and mutates the victim's `Commit` and fires the victim's configured outbound `Hook`s with attacker-chosen state/description/target_url.

None of the existing guards prevent this: `verify_signature` validates authenticity of the *payload's own claimed org*, not that the commit being mutated belongs to that org; `drop_unhandled_event` only filters by event type; there is no `ExplicitParameters` or model validation tying `sha` lookups to `repository.full_name`.

### Impact Explanation
The attacker can write a fabricated `Status` (arbitrary `state`, `description`, `target_url`, `context`) onto a commit belonging to a stack they do not control, and cause that victim stack's outbound `Hook`s (`:commit_status`, `:deployable_status`) to fire toward the victim's own configured external endpoints carrying victim-owned stack/commit identifiers plus attacker-forged CI content. If the victim stack has `continuous_deployment?` enabled and treats CI status as a deploy gate, this status write also feeds `Commit#deployable?`/`schedule_continuous_delivery`, which can influence auto-deploy behavior — this is a payload for one repository mutating another's commit/stack state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). It is repeatable against any victim stack/commit sharing a SHA with an attacker-controlled repository (trivial via fork), and scales to any number of shared-history commits.

### Likelihood Explanation
Preconditions are low-cost and fully attacker-controlled: fork or otherwise obtain a repository sharing commit history with the victim, install/point Shipit's GitHub App at the attacker's own repo (or use any repo the attacker already owns whose history overlaps the victim's), and issue a normal status update (e.g., via the GitHub Statuses API with the attacker's own token) on a shared-history commit. No Shipit session, API token, or secret is required — the attacker only needs a legitimately signed webhook for their own repository. Requires the victim stack to have `commit_status`/`deployable_status` hooks configured, which the question states is a common default.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run/other SHA-keyed handlers) to only mutate commits whose `stack.repository` matches the `repository.full_name`/owner declared in — and cryptographically verified for — the current webhook payload, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_from_verified_payload.id })`, rejecting/skipping any matched commit whose stack repository does not match the verified org/repo.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "status webhook signed for attacker repo must not mutate victim stack's commit / emit victim hooks" do
          shared_sha = 'deadbeef' * 5

          victim_stack = shipit_stacks(:shipit)
          victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared commit')

          attacker_repo_owner = 'attacker-org' # verified org per WebhooksController#verify_signature

          # Binding under test: verified_org (attacker-org) == victim_commit.stack's repository owner
          refute_equal attacker_repo_owner, victim_stack.repository.owner,
            "attacker org must not equal victim stack's repository owner"

          forged_params = ActionController::Parameters.new(
            sha: shared_sha,
            state: 'success',
            description: 'forged by attacker',
            target_url: 'https://attacker.example/evil',
            context: 'ci/forged'
          )

          expect_hook_emit(:deployable_status, victim_stack) do
            StatusHandler.new.call(forged_params) # simulating a payload validly signed only for attacker-org
          end

          victim_commit.reload
          # FAIL expected: victim's commit now carries an attacker-authored status,
          # and Hook.emit(:deployable_status, victim_stack, ...) fired from a payload
          # never authenticated for victim_stack's repository.
          assert_equal 'forged by attacker', victim_commit.status.description
        end
      end
    end
  end
end
```
This test demonstrates that `StatusHandler.call` — reachable purely from a webhook validly signed for the attacker's own repository — matches and mutates a `Commit` belonging to a different, victim-owned stack and triggers that victim stack's `Hook.emit(:deployable_status, ...)`, violating the `verified_org == commit.stack.repository_owner` binding.
