### Title
Webhook signature verified against `repository.owner.login`'s org secret, but the payload's `repository.full_name` (a separate, unsigned-relative field) selects the repository/stack actually mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/org config — and therefore the `webhook_secret` used to validate the HMAC — using `repository_owner`, read from the payload field `repository.owner.login` (or `organization.login`). But every webhook handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) resolves the *target* repository/stack from a different payload field, `repository.full_name`, via `Repository.from_github_repo_name`. Nothing ties these two fields together, so a valid signature computed with organization A's secret does not guarantee the payload's `full_name` also belongs to organization A.

### Finding Description
`Shipit.github(organization:)` supports per-organization GitHub App configuration, each with its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which app/secret to verify against purely from the payload's own `repository.owner.login` (falling back to `organization.login`): [2](#0-1) [3](#0-2) 

Once `verified` is true, the controller dispatches the *entire raw payload* to handlers regardless of which field was used for verification [4](#0-3) . Every handler then determines the affected repository/stack using a *different* payload field, `repository.full_name`: [5](#0-4) [6](#0-5) 

For example `PushHandler` uses `stacks` (built from `full_name`) to call `stack.sync_github` [7](#0-6) , and pull-request handlers likewise resolve `Repository.from_github_repo_name(params.repository.full_name)` independently [8](#0-7) .

The binding that should hold is:
`organization authenticated by verify_signature (repository.owner.login)` == `organization/repository actually written to (repository.full_name)`

Nothing in the controller or in `Handler#repository_name`/`Handler#stacks` enforces this equality. A JSON body is attacker-controlled in full except for the HMAC; an attacker who possesses (or can obtain, e.g. as a low-privileged admin of their *own* onboarded organization) the `webhook_secret` for organization A can craft a single payload where `repository.owner.login = "org-a"` (used to pick and validate against org A's secret) while `repository.full_name = "org-b/target-repo"` (used by every handler to pick the stack that gets acted on). The signature check passes because it only ever inspects org A's secret and the raw body HMAC — it never checks that `full_name`'s owner segment matches `repository.owner.login`.

### Impact Explanation
This breaks the trust boundary between "organization that authenticated the webhook" and "repository that is written," matching the explicitly in-scope binding category. Concretely, an attacker who only holds organization A's webhook secret can forge webhook events (`push`, `status`, `check_suite`, pull_request label/close events, membership events, etc.) that are processed as if legitimately sent by organization/repository B. Depending on which handler is targeted this can:
- Force `PushHandler` to trigger a `GithubSyncJob`/`sync_github` on org B's stacks with an attacker-chosen `expected_head_sha`.
- Feed forged commit `Status`/`check_suite` results into org B's stacks, which can drive continuous-deployment logic (`Stack` continuous delivery relies on green statuses/check runs) toward an unauthorized deploy.
- Archive/unarchive or otherwise mutate org B's review stacks via the pull_request handlers.

This is a cross-organization/cross-repository write achieved without any credential belonging to the target organization, satisfying the "cross-repository writes / unauthorized deploy" Critical/High impact bar.

### Likelihood Explanation
Requires only the `webhook_secret` of any one organization configured in the multi-tenant `secrets.github` config — not the target organization's secret, and no GitHub/Shipit session or API token. Any party operating a legitimate but low-trust organization entry in the same Shipit deployment can mount this against any other organization's repositories, so likelihood is Medium (the app must be run in the multi-org configuration for this to have cross-tenant impact).

### Recommendation
In `WebhooksController#verify_signature`, after establishing the verifying organization from `repository.owner.login`/`organization.login`, re-validate that every handler's `repository_name`/`full_name` owner segment matches that same organization before dispatch, or better, derive the target repository/organization from the *same* field used for signature selection so there is a single source of truth. Reject the event (422) on mismatch.

### Proof of Concept
1. Deploy Shipit with multi-org config: `secrets.github` containing both `org-a` (attacker knows `webhook_secret`) and `org-b` (victim, has stacks configured).
2. Craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac>` using org A's `webhook_secret` over the raw body.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: 'org-a')` and validates the HMAC successfully [2](#0-1) .
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('org-b/victim-repo')` [5](#0-4)  and enqueues `stack.sync_github(expected_head_sha: params.after)` for org B's stack [7](#0-6) , despite the request never being authenticated with org B's secret.

    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
