### Title
Single-Step Critical Address Setters in Bridge Contracts Allow Irrecoverable Loss of Bridge Control and Permanent Asset Lock — (File: `contracts/service_chain/bridge/BridgeCounterPart.sol`, `contracts/service_chain/bridge/BridgeTransfer.sol`, `contracts/libs/openzeppelin-contracts-v2/contracts/ownership/Ownable.sol`)

---

### Summary

The Kaia service-chain `Bridge` contract and its parent contracts expose three critical single-step address-change operations with no confirmation mechanism: `transferOwnership`, `setCounterPartBridge`, and `setFeeReceiver`. A single erroneous call by the bridge owner immediately and irrecoverably commits the wrong address, with no way to recover without the cooperation of the (potentially non-existent) new address. The highest-impact case is `transferOwnership`: the wrong address immediately becomes the sole owner of the bridge, permanently locking all bridged KLAY, ERC20, and ERC721 assets held in the contract.

---

### Finding Description

`Bridge.sol` inherits from `BridgeCounterPart`, `BridgeTransferKLAY`, `BridgeTransferERC20`, `BridgeTransferERC721`, and ultimately from `Ownable` (OpenZeppelin v2). [1](#0-0) 

The `Ownable` base used is the v2 variant, which implements a **single-step** `transferOwnership`:

```solidity
function transferOwnership(address newOwner) public onlyOwner {
    _transferOwnership(newOwner);
}
function _transferOwnership(address newOwner) internal {
    require(newOwner != address(0), "Ownable: new owner is the zero address");
    emit OwnershipTransferred(_owner, newOwner);
    _owner = newOwner;
}
``` [2](#0-1) 

There is no `pendingOwner` storage slot, no `acceptOwnership` step, and no way to cancel a mistaken transfer. The new address takes full ownership immediately.

`BridgeCounterPart.setCounterPartBridge` is equally single-step:

```solidity
function setCounterPartBridge(address _bridge) external onlyOwner {
    counterpartBridge = _bridge;
    emit CounterpartBridgeChanged(_bridge);
}
``` [3](#0-2) 

`BridgeTransfer.setFeeReceiver` is also single-step, delegating directly to `_setFeeReceiver`:

```solidity
function setFeeReceiver(address payable _feeReceiver) external onlyOwner {
    _setFeeReceiver(_feeReceiver);
}
``` [4](#0-3) 

`_setFeeReceiver` immediately overwrites `feeReceiver` with no confirmation: [5](#0-4)

### Impact Explanation

**`transferOwnership` (highest impact):** The bridge owner controls `registerOperator`, `deregisterOperator`, `setOperatorThreshold`, `setCounterPartBridge`, `setFeeReceiver`, and `setRunningStatus`. [6](#0-5)  If ownership is transferred to a wrong address, all of these functions become permanently inaccessible to the legitimate operator. The bridge cannot be paused, operators cannot be changed, and the counterpart bridge cannot be corrected. All KLAY, ERC20, and ERC721 assets held in the bridge contract are permanently locked — a direct loss of bridged assets.

**`setCounterPartBridge` (high impact):** The `counterpartBridge` address is the trusted peer for cross-chain value transfer. Setting it to a wrong address breaks the bridge's ability to authenticate cross-chain requests, potentially allowing a malicious counterpart to drain the bridge or permanently halting all cross-chain transfers.

**`setFeeReceiver` (medium impact):** Every KLAY and ERC20 bridge transfer pays a fee to `feeReceiver`. [7](#0-6)  Setting it to a wrong address permanently redirects all bridge fee revenue (KAIA and bridged ERC20 tokens) to an uncontrolled address — an unauthorized transfer of system-managed funds.

---

### Likelihood Explanation

The bridge owner is a single EOA or multisig managing the service-chain bridge. Address entry errors (copy-paste mistakes, wrong network address, stale clipboard) are realistic operational hazards, especially during bridge upgrades or operator rotations. The OpenZeppelin v2 `Ownable` used here predates the two-step `Ownable2Step` pattern introduced precisely because of this class of mistake. There is no zero-address guard on `setCounterPartBridge` or `setFeeReceiver`, and the zero-address guard on `transferOwnership` does not protect against a non-zero wrong address.

---

### Recommendation

1. **`transferOwnership`**: Replace `Ownable` (v2) with a two-step pattern: store a `pendingOwner`, require the pending owner to call `acceptOwnership()` to complete the transfer. This is the `Ownable2Step` pattern from OpenZeppelin v4+.

2. **`setCounterPartBridge`**: Introduce a `pendingCounterpartBridge` variable. The new counterpart bridge must call a confirmation function before `counterpartBridge` is updated.

3. **`setFeeReceiver`**: Introduce a `pendingFeeReceiver` variable with a similar two-step confirmation, or at minimum require the new address to be non-zero and emit an event with a time delay before the change takes effect.

---

### Proof of Concept

1. Bridge owner Alice calls `transferOwnership(wrongAddress)` — a typo or stale clipboard entry.
2. `_owner` is immediately set to `wrongAddress`. [8](#0-7) 
3. Alice calls `transferOwnership(correctAddress)` to recover — reverts with `"Ownable: caller is not the owner"` because Alice is no longer the owner.
4. `wrongAddress` (an EOA with no known private key, or a contract with no `transferOwnership` call path) can never call `transferOwnership` back.
5. All `onlyOwner` functions on the Bridge are permanently inaccessible. The bridge cannot be paused, operators cannot be rotated, and all KLAY/ERC20/ERC721 assets held in the bridge are permanently locked.

    function registerOperator(address _operator)
    external
    onlyOwner
    {
        require(operatorList.length < MAX_OPERATOR, "max operator limit");
        require(!operators[_operator], "exist operator");
        operators[_operator] = true;
        operatorList.push(_operator);
        emit OperatorRegistered(_operator);
    }

    // deregisterOperator deregisters the operator.
    //
    // Note that outstanding votes by the deregistered operator are not revoked.
    // This enables a subtle counterintuitive scenario.
    //
    // Suppose there are two operators A, B and C with threshold 2.
    // 1. Operator A votes on nonce N
    // 2. Owner deregisters A
    // 3. Operator B votes on nonce N, thereby executing the request N.
    // In this case the request was executed with A's vote after A is deregistered.
    //
    // The Owner shall recognize this issue and expect that operator deregistration
    // takes some time to be fully effective.
    function deregisterOperator(address _operator)
    external
    onlyOwner
    {
        require(operators[_operator]);
        delete operators[_operator];

        for (uint i = 0; i < operatorList.length; i++) {
           if (operatorList[i] == _operator) {
               operatorList[i] = operatorList[operatorList.length-1];
               operatorList.length--;
               break;
           }
        }
        emit OperatorDeregistered(_operator);
    }

    // setOperatorThreshold sets the operator threshold.
    function setOperatorThreshold(VoteType _voteType, uint8 _threshold)
    external
    onlyOwner
    {
        require(_threshold > 0, "zero threshold");
        require(operatorList.length >= _threshold, "bigger than num of operators");
        operatorThresholds[uint8(_voteType)] = _threshold;
        emit OperatorThresholdChanged(_voteType, _threshold);
    }
