### Title
Opaque router payloads can execute attacker-selected contracts under the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept an opaque `swap` byte payload and forward it to the configured router without constraining which venue contracts the route invokes. A malicious route can therefore place attacker-deployed contract code inside the caller’s authorized invocation and add an unrelated wallet-token transfer to the authorization tree. If the user signs the simulated poisoned tree, the attacker can steal wallet assets beyond the supplied collateral while the controller still sees a valid measured swap output.

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` is permissioned only by owner-or-delegate authorization and passes the attacker-influenced `swap` bytes into the strategy flow. [1](#0-0)  `process_swap_collateral` authenticates the caller, withdraws the selected collateral, and invokes `withdraw_and_swap_from_supply` with that opaque payload. [2](#0-1)  The common type defines `StrategySwap` as raw `Bytes`, so the controller cannot determine which contracts the router will call. [3](#0-2) 

`swap_tokens` forwards the unchanged `swap` payload to the configured router through `execute_strategy`. [4](#0-3)  The controller separately authorizes only its own exact input transfer and afterward verifies input spend plus positive output balance. [5](#0-4)  Those checks bound the controller’s assets, but they do not prevent router-selected code from requesting additional `caller.require_auth` authorization elsewhere in the invocation.

The same opaque payload reaches the router through `swap_debt`, `repay_debt_with_collateral`, `multiply`’s `swap`, and `multiply`’s third-asset `convert_swap`. [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker can deploy a venue contract that the router payload names, have that venue call `token.transfer(victim, attacker, victim_balance)`, and still return a valid output token payment to the controller. The malicious transfer appears as a child of the victim’s controller authorization during transaction simulation; signing that tree transfers unrelated wallet assets to the attacker. The repository’s regression test demonstrates this exact behavior: the simulated `swap_collateral` root contains a nested wallet-token `transfer(alice, attacker, WALLET_BALANCE)`, Alice’s wallet is emptied, and the controller receives the expected output collateral. [8](#0-7) 

This is theft of user funds outside the routed collateral amount. The protocol’s own measured input/output checks cannot detect it because the stolen transfer targets the caller’s wallet rather than the controller balance. [9](#0-8) 

### Likelihood Explanation
Exploitation requires the victim to submit or sign a malicious route and then sign the resulting authorization tree. That is feasible through a malicious frontend, copied route payload, compromised route-generation service, or misleading wallet/simulation presentation, and it does not require protocol privileges or a compromised controller. The authorization child is visible to an honest wallet that decodes the full tree, which reduces but does not eliminate the risk because `swap` is opaque to the controller and users commonly rely on integrator-generated routes.

### Recommendation
Do not allow route bytes to introduce arbitrary contracts beneath the caller’s authorization. Prefer a structured route format whose venue addresses are checked against an allowlist maintained by governance, or have the router prove that every invoked venue is allowlisted before it can run. At minimum, wallets and integrators must fully decode route payloads and reject any signed authorization tree containing children other than the expected token transfer; this client-side check should be documented as mandatory rather than sufficient. A stronger protocol-level fix is to isolate swaps behind a router/session design that cannot join route-venue calls to the user’s root authorization.

### Proof of Concept
1. Alice owns an account with USDC collateral and holds `WALLET_TOKEN` directly in her wallet.
2. An attacker deploys `RogueHopPool`, whose swap entrypoint executes `WALLET_TOKEN.transfer(alice, attacker, WALLET_BALANCE)`.
3. The attacker constructs a `swap_collateral` route whose encoded `swap` bytes cause the router to invoke `RogueHopPool` while paying the controller a valid `ETH` output.
4. Alice invokes `swap_collateral(alice, account_id, USDC, amount, ETH, malicious_swap)`.
5. Simulation records one authorized `swap_collateral` root containing an unexpected `WALLET_TOKEN.transfer(alice, attacker, WALLET_BALANCE)` child.
6. Alice signs the tree; the swap succeeds, Alice receives `ETH` collateral, and the attacker receives her entire `WALLET_TOKEN` balance.

The test implementation demonstrates the primitive with an attacker-selected hop contract invoked from the route and a nested token transfer draining Alice’s wallet while preserving the expected swap output. [10](#0-9) [11](#0-10)

```rust
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
```

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
