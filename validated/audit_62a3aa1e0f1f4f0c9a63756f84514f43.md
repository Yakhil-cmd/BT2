### Title
Unbounded loop over an attacker-inflatable set of unspent outputs in `iterateUnspentOutputs()` can freeze/degrade AA "send-all" payments - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `completePaymentPayload()` gathers inputs for an AA-generated payment by querying **all** unspent outputs sent to the AA address (`readStableOutputs`/`readUnstableOutputsSentByAAs`) and then iterating over them in `iterateUnspentOutputs()` with no cap on the number of rows processed. For "send-all" outputs the loop does not stop once the target amount is reached — it keeps consuming every remaining row. An external, unprivileged actor can inflate the number of unspent outputs held by an AA address by sending many small (just-above-dust) payments to it, growing this loop unboundedly, analogous to the reported `AssetManager.rebalance()` unbounded-loop issue.

### Finding Description
`completePaymentPayload()` builds the AA's outgoing payment inputs: [1](#0-0) 

The rows returned are filtered only by minimum amount (`FULL_TRANSFER_INPUT_SIZE`, to avoid dust that is immediately unprofitable), not by count: [2](#0-1) 

`iterateUnspentOutputs()` then walks the entire `rows` array: [3](#0-2) 

Critically, when the payment has a send-all output, the loop does **not** `break` after the target amount is reached — it only updates `send_all_output.amount` and `continue`s, so it keeps iterating (and appending to `payload.inputs`/`arrConsumedOutputs`) through every remaining unspent output belonging to the AA for that asset: [4](#0-3) 

Normally, `validatePaymentInputsAndOutputs()` in `validation.js` caps the number of inputs/outputs a payment message may have via `MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_OUTPUTS_PER_PAYMENT_MESSAGE`, but this cap is explicitly skipped for AA-generated units: [5](#0-4) 

An attacker who is not privileged in any way — any address that can post a unit — can send many small payments (each just above the `FULL_TRANSFER_INPUT_SIZE` dust threshold) to a target AA's address over time, since output-count is not limited at all (only value-per-output is filtered). This builds up an arbitrarily large set of unspent outputs owned by the AA. Any subsequent AA execution that constructs a send-all payment (a very common oscript pattern for "withdraw all funds"/exchange-style bounce or payout logic) will then have to iterate the entire, attacker-grown output set inside `iterateUnspentOutputs()`/`completePaymentPayload()`, growing `payload.inputs` without the normal per-message cap.

### Impact Explanation
Each additional consumed input increases `net_target_amount` by `FULL_TRANSFER_INPUT_SIZE` and recomputes the oversize fee (`getOversizeFee`), so the constructed response unit's size and fees grow proportionally to the attacker-controlled number of dust outputs. This can:
- Blow past protocol-level unit size limits, causing the AA's response-unit construction/validation (`validateAndSaveUnit`) to repeatedly fail and the trigger to bounce, permanently preventing that AA from completing a legitimate send-all payout — i.e., **freezing AA funds/functionality** for the send-all code path.
- Consume disproportionate node CPU/processing time evaluating a single AA response (unbounded synchronous loop over `rows`), degrading the responsiveness of AA execution more broadly (the loop is a plain synchronous `for`, not batched via `async`), which under sufficiently large dust sets amounts to resource-exhaustion DoS against the specific AA's operation, effectively freezing its ability to service triggers.

This satisfies the "AA fund loss or freezing" acceptance criterion, since the AA becomes unable to reliably execute its intended send-all payment logic once its address accumulates enough attacker-supplied dust outputs, and any funds intended to be paid out via that path can become stuck.

### Likelihood Explanation
Likelihood is moderate-to-high for AAs that implement a common "send everything you have" payout (send-all output, i.e. `amount` omitted). Triggering it requires only the ability to send ordinary payments to a public address (the AA address) — something any unprivileged unit poster can do — and there is no economic or protocol barrier preventing an attacker from sending many small transfers over time (each transfer only costs its own bytes+fees, and the dust filter (`FULL_TRANSFER_INPUT_SIZE`) does not prevent accumulation, only prevents an individual output from being immediately fee-negative). No special AA/composer bug or race condition is needed — this is a straightforward parameter (output count) that the reachable code fails to bound.

### Recommendation
- Add an explicit cap on the number of unspent outputs consumed per `completePaymentPayload()` call (e.g., a `LIMIT` clause in `readStableOutputs`/`readUnstableOutputsSentByAAs`, or breaking out of `iterateUnspentOutputs()` once a maximum input count is reached), independent of whether a send-all output is present.
- For send-all outputs, still enforce the general `MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_OUTPUTS_PER_PAYMENT_MESSAGE` bounds (i.e., stop consuming inputs once the cap is hit rather than exempting AA-generated payments via `!objValidationState.bAA`), and design a scheme for AAs to spend remaining dust across multiple response units instead of requiring all of it in one payment.

### Proof of Concept
1. Deploy/target an AA whose logic includes a "send-all" payment message on some trigger condition (a standard oscript pattern), e.g. `outputs: [{address: "{trigger.address}"}]` with no `amount`.
2. As an attacker, repeatedly send many small payments (amount slightly above `FULL_TRANSFER_INPUT_SIZE`, see `aa_composer.js` line 1149's dust filter) to the AA's address over a number of units/blocks — no special privileges required, this is a normal payment.
3. Once the AA's address has accumulated a very large number of unspent outputs, trigger the AA's send-all code path.
4. Observe that `completePaymentPayload()` (`aa_composer.js:1061-1245`) iterates every accumulated output in `iterateUnspentOutputs()` (`aa_composer.js:1102-1138`), continuously growing `payload.inputs`/`net_target_amount`/oversize fee because the send-all branch never `break`s, ultimately producing an oversized/invalid response unit that fails `validateAndSaveUnit()` and bounces — repeatable indefinitely to keep this code path perpetually failing.
