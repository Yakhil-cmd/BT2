### Title
Missing `return` after caught exception in `handleSavedPrivatePayments` leads to processing with corrupted state and a second, unguarded call that can throw an uncaught exception, crashing the node - ([File: network.js])

### Summary
This is the closest reachable analog to the SurrealDB HTTP-header panic (GHSA-m24x-r6q3-2vp9): untrusted, attacker-supplied data (a private-payment payload sent by any peer/device) reaches a hashing routine (`objectHash.getBase64Hash` → `string_utils.getJsonSourceString`) that throws on malformed input types (`null`, non-finite numbers, empty objects/arrays, unknown types, etc.). The `try/catch` guarding that call in `network.js`'s `handleSavedPrivatePayments` does not `return` on error, so execution falls through to code that uses the now-undefined hash and unconditionally re-invokes `privatePayment.validateAndSavePrivatePaymentChain` on the same malformed data outside of any try/catch, plus double-invokes the `async.each` iteratee callback path. Any synchronous throw at that point is uncaught and propagates to the process-level handler which explicitly re-throws to crash the node (`process.on('uncaughtException', ...) { ...; throw err; }`), exactly mirroring the DoS pattern in the advisory (parsing untrusted data throws → crash).

### Finding Description
In `network.js`, `handleSavedPrivatePayments` reads pending private payments and validates each chain: [1](#0-0) 

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
```

`getBase64Hash` (`objectHash.js` → `chash.getChash160`/`getJsonSourceString`, `string_utils.js`) throws on: [2](#0-1) 

- `null` values nested in the payload
- non-finite numbers
- empty objects/arrays (when `bAllowEmpty` isn't applicable in this call path)
- values of unsupported JS types

Because the `catch` block does not `return`, execution falls through:
1. `json_payload_hash` remains `undefined`, corrupting the `key` used for event-based deduplication/synchronization (`eventBus.emit(key, ...)`), and
2. `privatePayment.validateAndSavePrivatePaymentChain` is called a second time (in addition to the `cb` invoked asynchronously inside `deleteHandledPrivateChain`) on the very same malformed payload that already threw once, but this time with **no surrounding try/catch at all**. Any further processing of the same malformed structure (`arrPrivateElements[0].payload`) inside `validateAndSavePrivatePaymentChain`/`validation.js` (e.g., object-hash or payload-commission computations, several of which are also unguarded — see `validation.js:2421,2451,2458,2476`) can throw synchronously, and this throw is not caught anywhere in the call chain (`async.each` iteratee → `db.query` callback → `mutex.lock` callback).

This data path is reachable by any unauthenticated peer or paired device: private-payment chains are queued via `network.js`'s `private_payment` justsaying handler / `handleOnlinePrivatePayment`, persisted to `unhandled_private_payments`, and later replayed by `handleSavedPrivatePayments` — no capability or authentication is required to place a malformed payload into that queue.

An uncaught synchronous exception anywhere in this call stack is not caught by any `try/catch`, and eventually surfaces as a Node.js `uncaughtException`. `network.js` installs a handler for this that intentionally re-throws to terminate the process: [3](#0-2) 

```js
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	console.error('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```

This is directly analogous to the SurrealDB advisory: malformed, attacker-controlled data reaching a parsing/hashing routine that panics/throws instead of being safely rejected, crashing the server process and causing denial of service.

### Impact Explanation
A single malicious peer or paired device can queue a private-payment chain whose head payload contains a value that makes `getJsonSourceString`/`getBase64Hash` throw (e.g. a `null` inside a nested field, or another disallowed type/shape). When the node later processes its `unhandled_private_payments` queue (`handleSavedPrivatePayments`, run periodically and on catch-up), the missing `return` after the caught exception causes the code to fall through and re-invoke validation on the same malformed structure without protection, risking an uncaught synchronous exception. Given the explicit `throw err` in the global `uncaughtException` handler, this crashes the whole ocore node process — a network-wide denial-of-service vector reachable without authentication (any peer connection or paired device can deliver a `private_payment` message).

### Likelihood Explanation
Medium-High: the input path (`private_payment` justsaying / `handlePrivatePaymentChains` from a paired device) performs only shallow structural checks (`isNonemptyObject`, `isNonemptyString`, etc. — see `wallet.js:955-972`) before the payload ever reaches `getBase64Hash`; it does not validate that all nested values are of hashable types (no `null`s, no non-finite numbers, no unsupported types). Triggering the first throw is straightforward for an attacker; whether the second, unguarded call also throws depends on downstream validation logic, but the code omission (missing `return`) is unambiguous and demonstrably present.

### Recommendation
Add a `return` statement (or otherwise short-circuit) after handling the `catch` block in `network.js`'s `handleSavedPrivatePayments`/`validateAndSave` function, so that when `getBase64Hash` throws, the chain is deleted/reported and no further processing of the malformed payload occurs. Additionally, wrap the subsequent call to `privatePayment.validateAndSavePrivatePaymentChain` (and other object-hash/validation calls reachable from untrusted private-payment data) in try/catch that converts exceptions into `ifError` responses rather than allowing them to propagate to the global `uncaughtException` handler.

### Proof of Concept
1. As any peer or paired device, submit a `private_payment` message (via `handleOnlinePrivatePayment`/`handlePrivatePaymentChains`) whose head element's `payload` passes the shallow structural checks in `wallet.js:959-972` (non-empty objects/strings/arrays) but contains a nested field with a disallowed value for `getJsonSourceString`, e.g. a `null` value nested inside `payload` (not `payload.asset/inputs/outputs` themselves, which are checked, but an additional/extra field, or a numeric field set to `NaN`/`Infinity` if reachable).
2. The message is queued into `unhandled_private_payments` (since the unit is not yet known — `ifNew`/`savePrivatePayment` path in `network.js:2412-2440`).
3. When `handleSavedPrivatePayments` runs (triggered periodically or via `findAndHandleJointsThatAreReady`), `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws inside the `try` block at `network.js:2470`.
4. Because the `catch` block lacks a `return`, execution falls through to `network.js:2478-2479`, invoking `privatePayment.validateAndSavePrivatePaymentChain` a second time on the same malformed payload outside of any try/catch.
5. If this second, unguarded invocation throws synchronously (verification of this final trigger requires running `privatePayment.js`'s validation code against a concrete crafted payload, which was not fully traced in this review), the exception is uncaught, and the `uncaughtException` handler in `network.js:4530-4543` re-throws it, crashing the node process.

**Note on verification confidence:** I confirmed with certainty the missing `return` bug and the throwing behavior of `getJsonSourceString`/`getBase64Hash` on malformed input, and the crash-on-uncaught-exception behavior of the process handler. I was **not able to fully verify** (given tool/iteration limits) that the second call to `privatePayment.validateAndSavePrivatePaymentChain` with the corrupted state definitely throws synchronously for a specific concrete payload — this would need to be confirmed by tracing `private_payment.js`'s `validateAndSavePrivatePaymentChain` implementation and/or by running a live PoC against the code.

function getJsonSourceString(obj, bAllowEmpty) {
	let cache = new WeakMap();  // object to stringified result
	function stringify(variable){
		if (variable === null)
			throw Error("null value in "+JSON.stringify(obj));
		switch (typeof variable){
			case "string":
				return toWellFormedJsonStringify(variable);
			case "number":
				if (!isFinite(variable))
					throw Error("invalid number: " + variable);
			case "boolean":
				return variable.toString();
			case "object":
				// return cached result if already processed
				if (cache.has(variable))
					return cache.get(variable);
				let result;
				if (Array.isArray(variable)){
					if (variable.length === 0 && !bAllowEmpty)
						throw Error("empty array in "+JSON.stringify(obj));
					result = '[' + variable.map(stringify).join(',') + ']';
				}
				else{
					var keys = Object.keys(variable).sort();
					if (keys.length === 0 && !bAllowEmpty)
						throw Error("empty object in "+JSON.stringify(obj));
					result = '{' + keys.map(function(key){ return toWellFormedJsonStringify(key)+':'+stringify(variable[key]) }).join(',') + '}';
				}
				cache.set(variable, result);  // memoize for future references
				return result;
			default:
				throw Error("getJsonSourceString: unknown type="+(typeof variable)+" of "+variable+", object: "+JSON.stringify(obj));
		}
