### Title
Cross-repository status confusion — a `status` webhook validated for one repository can flip CI state (and trigger merges/deploys) on any commit sharing the same SHA in a different stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha)` instead of scoping through the authenticated repository, unlike every other handler which filters via `stacks` (which is derived from `payload.dig('repository','full_name')`). This lets a webhook that is cryptographically valid for repository A silently mutate `Status` rows — and trigger `stack.schedule_merges` — for any other stack B whose commit table happens to contain the same SHA value.

### Finding Description
The broken binding: the invariant should be `status.stack_id == authenticated_repository.stacks.map(&:id)`, i.e. a status can only ever be written against a commit belonging to the repository that signed the webhook. Instead the actual code enforces only `status.sha == params.sha`, with no repository/stack constraint at all: [1](#0-0) 

Compare this to `CheckSuiteHandler`, which correctly scopes through `stacks` (repository-derived) before touching commits: [2](#0-1) 

and to the base `Handler#stacks` helper that every other handler is expected to use, which resolves strictly via `Repository.from_github_repo_name(repository_name)`: [3](#0-2) 

Signature verification (`WebhooksController#verify_signature`) only proves that the payload was signed by *some* configured GitHub organization/app matching `params.dig('repository','owner','login')` — it says nothing about which stack's commits may be touched: [4](#0-3) 

So the exploit requires the attacker to control (or already have) a legitimately Shipit-registered GitHub organization/repository (so their own webhook signs with a valid `webhook_secret`/GitHub App for `repository_owner`), and to get a commit with a SHA that also exists in the victim's `commits` table. Git SHAs are content-addressed hashes of the whole commit graph (parents included), so getting two *unrelated* repositories to actually share a literal SHA collision under `Commit.where(sha: ...)` is only realistic when the objects are shared history (e.g., the victim repository was forked, or a commit was cherry-picked/copied with identical author/committer/timestamp/tree/parents) — not an arbitrary "any internet attacker, any victim" scenario. This significantly narrows, but does not eliminate, the practical blast radius: it works for forks/shared-history stacks (e.g., multiple stacks tracking the same underlying commit history, environments/branches of the same repo, or repositories that were forked from one another and haven't diverged at the shared commit).

Once the `Commit` record is found (regardless of which stack it belongs to), `commit.create_status_from_github!(params)` writes the status and calls `add_status`, which — on a state transition to `pending`/`success` — calls `stack.schedule_merges`: [5](#0-4) 

`schedule_merges`/merge-request processing can proceed to merge/deploy using the stack's configured bot identity (`bot_login`) if the stack's merge requirements (e.g. requiring `buildkite/deploy` to be green) are satisfied by the forged status, thereby shipping the victim stack's pending commit under the bot's authority — without the victim's own CI ever having reported success.

None of the existing guards prevent this: `verify_signature` validates organization-level authenticity, not stack/commit scoping; `ExplicitParameters` only validates the shape of `sha`/`state`/`context`, not repository ownership; there is no `Repository`/`stacks` filter anywhere in `StatusHandler`.

### Impact Explanation
A forged/cross-origin `status` payload can flip commit status (and, when the required context matches an unmet build requirement, trigger `Stack#schedule_merges` and a deploy running under the stack's configured `bot_login`) on a stack the attacker does not own or authenticate for, whenever the target commit's SHA is also present in the attacker-controlled/attacker-authenticated repository's commit history (fork/shared-history scenario). This is a real "payload for one repository mutating another's stack/commit" bug (Critical category per the rubric), but it is conditioned on SHA reuse across the two repos' `commits` tables, not on completely arbitrary unrelated repositories.

### Likelihood Explanation
Preconditions: (1) attacker must control a repository/org that is itself registered and signs valid webhooks in this Shipit instance (i.e., not a fully external/unauthenticated org — `verify_signature` still must pass for `repository_owner`), (2) the victim stack must require a status context (e.g., `buildkite/deploy`) that the attacker's forged status can satisfy, (3) the SHA must literally exist in both the attacker's authenticated repository context and the victim's `commits` table — realistically via forks/shared git history rather than arbitrary collision. This is a meaningfully privileged/narrow scenario (needing a Shipit-registered repo of one's own plus shared commit history with the victim), not the "any internet user" scenario implied by the question's framing, but it is fully reachable with no session, API token, or GitHub secret — only a working webhook signature for the attacker's own registered org.

### Recommendation
Scope `StatusHandler#process` by repository, mirroring `CheckSuiteHandler`/`Handler#stacks`: resolve commits only within `stacks.flat_map(&:commits)` (or `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`) instead of the bare `Commit.where(sha: params.sha)`, so a status can only affect commits belonging to the repository that authenticated the webhook.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or extend `webhooks_controller_test.rb`):
1. Create two `Repository`/`Stack` fixtures, `stack_a` (owned by "attacker/repo") and `stack_b` (victim), each with a `Commit` sharing the identical `sha` value ("`deadbeef...`") — simulating shared history.
2. Assert precondition equality: `stack_a.commits.find_by(sha: sha).id != stack_b.commits.find_by(sha: sha).id` (different commit rows, same sha).
3. POST a `status` webhook payload with `repository.full_name = "attacker/repo"`, `sha: <shared sha>`, `context: "buildkite/deploy"`, `state: "success"`, with a valid signature for `attacker`'s org.
4. Assert `stack_b.commits.find_by(sha: sha).statuses.where(context: "buildkite/deploy", state: "success").exists?` is **true**, proving the victim stack's commit was mutated by a webhook that only authenticated for the attacker's repository — i.e. `status.stack_id == stack_b.id` even though the authenticated `repository_name == "attacker/repo"` (`repository_name != stack_b.repository.full_name`), which is the broken equality.
5. If `stack_b` has a merge requirement satisfied by this context, additionally assert `ProcessMergeRequestsJob` is enqueued for `stack_b`, showing the merge/deploy path was armed.
