## Title
Asset definer can instantly and unilaterally revoke the attestor list of a `spender_attested` asset, freezing all holders' funds mid-flight - (File: validation.js)

### Summary
Obyte's asset issuance mechanism is trustless like NFTX vault creation: anyone can define a custom asset with `spender_attested: true`, meaning only addresses attested by a trusted set of `attestors` can hold/transfer it. That attestor list is not fixed at issuance — the asset **definer** can unilaterally publish an `asset_attestors` update message at any time to replace the list, with immediate effect and no cooldown, exactly mirroring the NFTX pattern where a vault manager instantaneously changes fees/features with `setFees()`/`setVaultFeatures()` and traps users who cannot react in time.

### Finding Description
When an asset is created with `spender_attested: true`, only addresses currently attested by an address in the asset's attestor list may send/receive it, enforced in `validatePayment`: [1](#0-0) 

The attestor list itself is a mutable, single-signature field controlled solely by the asset definer via the `asset_attestors` message. `validateAttestorListUpdate` only checks that the sender is `objAsset.definer_address` — there is no timelock, vote, or advance-notice mechanism: [2](#0-1) 

The "current" attestor list used for authorization is always the **latest stable** one, computed by `readAsset`/`storage.js`'s attestor-lookup logic that selects the most recent `asset_attestors` unit: [3](#0-2) 

and the attested status of any address is checked against that same latest list in `filterAttestedAddresses`/`loadAssetWithListOfAttestedAuthors`: [4](#0-3) 

Because the check is always against the *current* list (not the list in effect when the user was attested or acquired the asset), the definer can publish a new `asset_attestors` unit that drops previously-trusted attestors (or replaces them with attestors who will never attest existing holders). The moment that unit stabilizes, every holder whose only attestation came from a now-removed attestor instantly fails the `"none of the authors is attested"` / `"issuer is not attested"` checks in `validatePayment`, and can no longer transfer or spend the asset. There is no grace period, no way for holders to exit beforehand, and the change is retroactive to everyone already holding the asset — funds become frozen in place, just as NFTX vault managers could instantly disable redeem/swap features and trap NFTs/tokens.

### Impact Explanation
This is a direct AA/asset-fund-freezing analog to the NFTX bug class: a single privileged, permissionless-to-become party (the asset definer, analogous to the vault manager) can instantaneously and retroactively strip transfer rights from all current holders of a `spender_attested` asset. Holders who legitimately acquired the asset while properly attested can be locked out of moving or redeeming it with no warning, effectively freezing their funds. Because asset creation is fully permissionless (`validateAssetDefinition` only requires a single-author unit, no privileged setup), any user can be lured into acquiring a popular-looking custom asset and then be griefed by the definer.

### Likelihood Explanation
High reachability, moderate likelihood: any unprivileged unit poster can define an asset with `spender_attested: true` and later publish an `asset_attestors` message as sole author — no special privileges or coordination needed beyond being the original definer. Convincing users to accumulate the asset (e.g., presenting it as a legitimate/attested token) is a social step but requires no protocol-level cooperation; this mirrors exactly the "gain traction, then flip a switch" scenario in the original NFTX report.

### Recommendation
- **Short term**: Document that `spender_attested` assets carry definer risk — a definer can retroactively revoke the attestor list and freeze holders' ability to transfer the asset. Wallets/UIs should flag assets whose attestor list can still be changed by the definer.
- **Long term**: Consider requiring `asset_attestors` updates to only add attestors (not remove existing ones) once holders exist, or introduce a delay (e.g., N main-chain indices) before a new attestor list takes effect, giving holders time to exit or resolve attestation before losing spend rights, analogous to the recommended timelock for NFTX manager-only functions.

### Proof of Concept
1. Eve defines asset `X` with `spender_attested: true` and an initial attestor list `[Attestor A]` via the `asset` message validated in `validateAssetDefinition` (validation.js:2725).
2. Attestor A attests several users' addresses; those users acquire and hold asset `X`, confirmed by `validatePayment`'s attested-address check (validation.js:2115-2122).
3. Eve, as sole `definer_address`, later posts an `asset_attestors` message replacing the list with `[Attestor B]` (an attestor who will never attest anyone) — validated only via `validateAttestorListUpdate` (validation.js:2829-2848), no consent from holders needed.
4. Once this unit stabilizes, `readAsset`/`filterAttestedAddresses` (storage.js:1911-1992) recompute `arrAttestedAddresses` using only Attestor B's attestations.
5. All previous holders now fail `"none of the authors is attested"` in `validatePayment` (validation.js:2115-2122) when attempting to transfer, and their asset `X` balances become permanently unspendable — funds frozen with no recourse.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });

function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
}
