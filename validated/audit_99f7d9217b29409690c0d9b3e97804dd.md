### Title
`number_from_seed()` in oscript evaluation lets an unprivileged AA trigger sender pre-compute and grind the "random" outcome, allowing bias/theft in any lottery-style AA - (File: `formula/evaluation.js`)

### Summary
The reported bug describes a `PrizePool.drawRandomNumber()` function whose caller-controlled `_slots` parameter deterministically changes the "random" outcome, letting an unprivileged caller compute the result off-chain before committing it, and only post the transaction when it favors them. Obyte's oscript engine exposes an analogous primitive, `number_from_seed()`, that is fully deterministic and derived exclusively from caller-supplied input, so any AA that uses it for randomness (lotteries, games, prize draws) inherits the same "predict-then-commit" bias problem.

### Finding Description
`number_from_seed` is implemented in `evaluate()` as a pure, public, deterministic function of its evaluated parameters: [1](#0-0) 

The seed (`evaluated_params[0]`) is whatever value the enclosing AA formula computes — commonly built from `trigger.data`, `trigger.unit`, `trigger.address`, or other fields fully controlled/known by the unit's author before the unit is broadcast, since `trigger.data` is verbatim data that the poster embeds in the message and signs. `evaluation.js` and `formula/validation.js` place no restriction preventing the seed from depending on attacker-supplied trigger content: [2](#0-1) 

Because SHA-256 (used internally) and the full evaluation logic are public/deterministic, and the trigger sender constructs and signs the entire triggering unit locally before broadcasting it, an unprivileged trigger sender can:
1. Compute `number_from_seed(seed_expr)` locally for many candidate values of any attacker-chosen trigger-data field feeding into `seed_expr` (a "nonce"/"slot"-like parameter, exactly analogous to `_slots` in the reported bug).
2. Only broadcast the unit whose resulting "random" number favors them (e.g., picks them as lottery winner, grants a favorable payout ratio, etc.).
3. Any AA built on `number_from_seed(trigger.data.X)` — a documented and demonstrated pattern per the `test/formula.test.js` unit tests — is therefore not running unbiased randomness at all; the outcome is fully known and selectable by the poster before it is ever included in the DAG.

This mirrors the root cause in the external report: the entity that controls the input to a "random" draw can iterate over that input until the result favors them, and nothing in `evaluate()`/`validation.js` enforces that the seed be unknown or uncontrollable by the trigger's author (e.g., requiring a not-yet-existing future MC unit, an oracle-committed value, or a VRF proof bound to unpredictable data).

### Impact Explanation
Any AA (lottery, gambling AA, raffle, "51% attack game"-style contracts, etc.) that relies on `number_from_seed()` seeded (directly or indirectly) by trigger-controlled data can have its outcome biased by an unprivileged trigger sender. This can result in unauthorized extraction of AA-held funds (a poster reliably "winning" a payout they should not win) or unfair drain of a shared pool — an AA fund loss impact class.

### Likelihood Explanation
Exploitation requires no special privilege: any address can construct and locally evaluate candidate triggering units against the target AA's formula (since AA bytecode/oscript is public on-chain) before choosing which one to actually sign and broadcast. Grinding cost is cheap (a hash computation per candidate), and the primitive gives no built-in protection, so likelihood is high for any AA design that naively uses `number_from_seed` with attacker-influenced input.

### Recommendation
- Document and, where feasible, enforce that `number_from_seed()` (or any AA relying on it for fairness) must derive its seed only from data that is unknowable to the trigger's author at signing time (e.g., a future/independent oracle data feed committed after the trigger, or a value derived from post-trigger DAG state such as a not-yet-existing MC ball).
- Consider adding a built-in commit-reveal or VRF-based randomness primitive (oscript already has `vrf_verify`, see `formula/evaluation.js` around the `vrf_verify` case) as the recommended path for gambling/lottery AAs, and update AA-authoring guidance to explicitly warn against seeding `number_from_seed` with trigger-controlled fields.
- Add validation/lint warnings (similar to `formula/validation.js`) flagging when `number_from_seed`'s seed expression references `trigger.data` or `trigger.unit` directly, since these are attacker-grindable.

### Proof of Concept
1. Deploy an AA whose payout logic includes something like:
   `{ $win = number_from_seed(trigger.unit || trigger.data.nonce, 1, 100) == 1; if ($win) { pay out prize } }`
2. An attacker builds a candidate triggering unit with `data.nonce = 1`, computes its own future unit content/hash locally (author fully controls unit content and can predict its own signed unit hash before broadcast), and evaluates the formula off-chain using the same logic as `formula/evaluation.js`'s `number_from_seed` case (SHA-256 of the seed, take first 8 bytes, scale to `[min,max]`).
3. The attacker iterates `nonce = 1, 2, 3, ...` until the computed value equals `1` (the winning condition), then signs and broadcasts only that specific unit.
4. The AA evaluates the same deterministic formula on-chain and confirms the "win," paying out funds to the attacker — reproducing the same class of bias described in the original `drawRandomNumber()` report, where the caller controls a parameter that determines a supposedly random winning outcome.
