### Title
Webhook signature verification is fully bypassable when `webhook_secret` is unset, allowing forged `membership` events to grant authorization-team access — organization-authentication vs. repository/team-write binding broken (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the organization resolved from the untrusted payload, and `WebhooksController` uses that same untrusted payload field to pick which org's (potentially secret-less) config to verify against. Because `webhook_secret` is documented as *optional*, an unprivileged attacker with only a GitHub account (and knowledge/guess of a `login` and a real team) can POST directly to `/webhooks` and forge a `membership` "added" event that inserts a `Membership` row for their own `User`/`login`. Since `User#authorized?` derives access purely from `teams` membership rows populated by this same handler, this breaks the "GitHub identity authenticated by GitHub" vs. "`User`/`Team` state written and trusted by Shipit's authorization" binding, escalating to full engine access without ever completing GitHub OAuth org/team membership.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App config to check against using data taken straight from the still-unauthenticated JSON body: [1](#0-0) [2](#0-1) 

The actual HMAC check is performed by `GitHubApp#verify_webhook_signature`, which explicitly short-circuits to `true` when the org has no `webhook_secret` configured: [3](#0-2) 

The setup documentation explicitly marks `webhook_secret` as optional, i.e. this is a supported, documented configuration rather than a misuse of the engine: [4](#0-3) 

When verification is bypassed this way, the controller dispatches the raw attacker-controlled JSON straight to registered handlers with no further authentication: [5](#0-4) 

The `membership` event handler trusts the payload entirely to create/attach a `Team` and add an arbitrary `User` (looked up/created purely by `login` string) as a member: [6](#0-5) 

Shipit's whole authorization gate for the web UI/session is: [7](#0-6) [8](#0-7) 

So `Membership` rows created by a forged webhook are later read back verbatim by `authorized?` — there is no cryptographic/authoritative binding tying the `Team.add_member` write to an actually-verified GitHub organization membership event. The binding broken is: **organization that (fails to) authenticate the webhook == organization/team whose membership state is written and later trusted for authorization**, when `webhook_secret` is left blank (a documented, supported deployment option).

### Impact Explanation
This directly matches the specified High-impact category "escalation into `Shipit.github_teams` authorization." An attacker who:
1. Signs into Shipit via the normal GitHub OAuth flow with their own (otherwise unauthorized) GitHub account, creating a `User` row keyed on their `login`,
2. POSTs a forged `X-Github-Event: membership` webhook to `/webhooks` naming an authorized `Shipit.github_teams` team id/slug and `member.login` equal to their own login,

causes `Team#add_member` to attach their account to an authorized team, after which `User#authorized?` returns true and the attacker is granted full access to Shipit (stacks, deploys, rollbacks, task execution) — all without ever actually being a member of the real GitHub team/org. This is an authentication/authorization bypass with no repository write access, no `ApiClient` token, and no knowledge of any secret required, satisfying "unprivileged attacker."

### Likelihood Explanation
Requires only: (a) that the operator left `webhook_secret` blank — explicitly presented as optional in the setup docs rather than mandatory — and (b) that the attacker can reach the public `/webhooks` endpoint and complete an ordinary OAuth login. No credentials, GitHub App private key, or webhook secret are needed. Given the doc explicitly calls the secret "optional," this is a realistic, in-scope deployment configuration, not a violation of documented setup requirements.

### Recommendation
- Make `webhook_secret` mandatory (fail closed) rather than defaulting to "verified" when absent; refuse to process webhooks for orgs without a configured secret.
- Do not derive which org's secret to check from unauthenticated payload fields before any verification has occurred; instead validate against all configured secrets/orgs, or bind the resolved organization to the installation/App metadata rather than payload-controlled `repository.owner.login` / `organization.login`.
- For `membership` events specifically, cross-check the `organization.login` in the payload against the app's actual installation/organization scope before creating `Membership` rows, and consider additionally requiring that the acting `Shipit.github(organization:)` used for verification match the organization whose team is being modified.

### Proof of Concept
1. Deploy Shipit with `github.webhook_secret` left blank (a documented supported option) for the relevant organization.
2. As an attacker, sign in normally via `/github/auth/github` with your own unprivileged GitHub account (login `attacker`) — this creates a `Shipit::User` row for `attacker`, currently unauthorized.
3. Send, with any signature header value (ignored since `verify_webhook_signature` returns `true` when `webhook_secret` is nil):
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": <id_of_authorized_team>, "name": "Developers", "slug": "developers", "url": "https://api.github.com/teams/1" },
  "organization": { "login": "<authorized-org>" },
  "member": { "login": "attacker" },
  "repository": { "owner": { "login": "<authorized-org>" } }
}
```
4. `MembershipHandler#process` runs unauthenticated, creating a `Membership` linking `attacker` to the authorized `Team`.
5. Attacker reloads Shipit; `User#authorized?` now returns `true`, granting full application access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
