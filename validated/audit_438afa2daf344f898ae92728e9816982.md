### Title
Unauthenticated Cross-Organization Forged Commit Status Triggers Unauthorized Deploy - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook against the GitHub organization derived from the attacker-controlled JSON body (`repository.owner.login` / `organization.login`), but `StatusHandler#process` writes a `Status` to *any* commit in the database matched purely by `sha`, with no check that the commit belongs to a stack/repository under that authenticated organization. Because `verify_webhook_signature` returns `true` unconditionally when an organization has no `webhook_secret` configured (an explicitly optional setting per `docs/setup.md`), an attacker can pick any org in a multi-org Shipit install that has a blank secret to pass authentication, then forge a `status` event pointing at a commit sha belonging to a totally different, victim organization's stack. This can trigger `ContinuousDeliveryJob` and cause an unauthorized deploy.

### Finding Description
- `WebhooksController#verify_signature` selects the GitHub App/secret to validate against using `repository_owner`, itself read from the untrusted JSON payload: [1](#0-0) [2](#0-1) 

- `verify_webhook_signature` bypasses HMAC verification entirely when the selected organization has no `webhook_secret` configured: [3](#0-2) 

- The docs explicitly present `webhook_secret` as optional, and multi-org configs list it per-organization, so it is realistic for at least one configured organization to have a blank secret while others (the victims) have theirs configured: [4](#0-3) 

- Once "verified" (or bypassed), the controller dispatches the full attacker-controlled payload to handlers with no re-binding to the authenticated organization: [5](#0-4) 

- `StatusHandler#process` looks up commits **globally by `sha`** — it does not scope to `repository.full_name`, to the authenticated organization, or to any stack tied to that organization at all: [6](#0-5) 

- This is unlike other handlers (`PushHandler`, `PullRequest` handlers), which correctly scope via `Repository.from_github_repo_name(params.repository.full_name)`: [7](#0-6) [8](#0-7) 

- Creating a `Status` record triggers continuous delivery evaluation via an `after_commit` callback: [9](#0-8) [10](#0-9) 

- Which, if the target stack has `continuous_deployment: true` and is not locked/occupied, results in `Stack#trigger_continuous_delivery` calling `trigger_deploy`, which executes the stack's `shipit.yml` deploy steps on the deploy host: [11](#0-10) [12](#0-11) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated by verify_signature` ≠ `repository/stack whose commit is mutated by StatusHandler`. The signature check is keyed off one attacker-supplied field (`repository.owner.login`/`organization.login`), while the actual write operation (`Commit.where(sha: params.sha)`) is keyed off a completely different, unchecked field (`sha`) that can reference any commit in the system regardless of organization.

### Impact Explanation
This allows an unprivileged, unauthenticated external attacker (no Shipit session, no `ApiClient` token, no GitHub App private key, no webhook secret for the *victim* org) to forge a successful CI status for any commit sha known to them (commit shas are public information for public GitHub repositories, and often visible via GitHub's public commit API even without access to the target Shipit instance's UI). If the victim stack has continuous deployment enabled, this can directly cause `Stack#trigger_deploy` to run — i.e., an **unauthorized deploy**, which is explicitly listed as a Critical/High impact in scope.

### Likelihood Explanation
Requires: (1) the Shipit instance uses the multi-organization GitHub configuration (documented, supported feature) where at least one configured organization has no `webhook_secret` set (an optional field, and shown as blank/commented in the shipped example configs), and (2) the target stack has `continuous_deployment: true`. Both conditions are realistic and rely purely on documented, supported configuration patterns — no social engineering, no credential theft, and no reliance on host misconfiguration outside what the engine itself documents as valid.

### Recommendation
- In `StatusHandler#process` (and any other handler that mutates state based on payload identifiers), scope commit/stack lookups to the repository identified in the payload (`repository.full_name`), consistent with `Handler#stacks`/`Handler#repository_name`, and verify that repository belongs to the organization that was authenticated in `WebhooksController#verify_signature`.
- Do not allow `verify_webhook_signature` to silently return `true` for organizations with no configured secret when other organizations require one; either require a `webhook_secret` for every organization in multi-org configurations, or bind the authenticated organization explicitly to the resource being mutated and reject cross-organization writes.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `AttackerOrg` (no `webhook_secret` set) and `VictimOrg` (has a `webhook_secret`, hosts a stack with `continuous_deployment: true`), as supported by the documented multi-org config in `docs/setup.md`.
2. Attacker discovers (via public GitHub) the `sha` of a commit belonging to `VictimOrg`'s repository that has not yet passed its required CI checks.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim_commit_sha>",
  "state": "success",
  "context": "ci/required-context",
  "repository": { "full_name": "AttackerOrg/irrelevant-repo", "owner": { "login": "AttackerOrg" } }
}
```
No valid `X-Hub-Signature` is required because `AttackerOrg` has no `webhook_secret` configured, so `GitHubApp#verify_webhook_signature` returns `true` unconditionally (`app/lib/shipit/github_app.rb:76-77`).
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `VictimOrg` commit (unrelated to `AttackerOrg`), and creates a `success` `Status` on it.
5. `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob` for `VictimOrg`'s stack; if the commit is now deployable, `Stack#trigger_continuous_delivery` calls `trigger_deploy`, running the stack's real deploy steps — an unauthorized deploy triggered entirely through a forged webhook authenticated under an unrelated organization.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def trigger_deploy(*args, **kwargs)
      if changed?
        # If this is the first deploy since the spec changed it's possible the record will be dirty here, meaning we
        # cant lock. In this one case persist the changes, otherwise log a warning and let the lock raise, so we
        # can debug what's going on here. We don't expect anything other than the deploy spec to dirty the model
        # instance, because of how that field is serialised.
        if changes.keys == ['cached_deploy_spec']
          save!
        else
          Rails.logger.warning("#{changes.keys} field(s) were unexpectedly modified on stack #{id} while deploying")
        end
      end

      run_now = kwargs.delete(:run_now)
      deploy = with_lock do
        deploy = build_deploy(*args, **kwargs)
        deploy.save!
        deploy
      end
      run_now ? deploy.run_now! : deploy.enqueue
      continuous_delivery_resumed!
      deploy
    end
