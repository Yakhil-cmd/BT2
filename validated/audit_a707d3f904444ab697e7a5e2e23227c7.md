### Title
`X-Shipit-User` header lets any API token holder attribute deploys to an arbitrary victim identity - (File: `app/controllers/shipit/api/base_controller.rb`)

### Summary
`Shipit::Api::BaseController#identify_user` resolves `current_user` purely from the attacker-controlled `X-Shipit-User` request header, looking up any existing `User` by login with no check that this login corresponds to the `ApiClient#creator` or any other property of the authenticated token. `Api::DeploysController#create` passes this unverified `current_user` straight into `stack.trigger_deploy(commit, current_user, ...)`, so the resulting `Deploy#user_id`/audit trail is attributed to whichever login the attacker names in the header.

### Finding Description
The broken binding: the code implicitly assumes `current_user == the GitHub identity that authenticated this HTTP request`, but in fact `current_user == User.where('lower(login) = ?', request.headers['X-Shipit-User'].downcase).first`, an arbitrary value chosen by the caller.

Code path:
- `authenticate_api_client` (`app/controllers/shipit/api/base_controller.rb:48-61`) validates the Basic-Auth bearer token against `ApiClient.authenticate`, setting `@current_api_client` to the token's owning `ApiClient` record. This only proves who the *token* belongs to; it never inspects `X-Shipit-User`.
- `identify_user` (`app/controllers/shipit/api/base_controller.rb:69-72`) reads `request.headers['X-Shipit-User']` and looks up any `User` by case-insensitive login match, with **no relation whatsoever to `current_api_client`** (no comparison to `current_api_client.creator`, no team/permission check on the named user).
- `current_user` (`app/controllers/shipit/api/base_controller.rb:65-67`) memoizes `identify_user || AnonymousUser.new`.
- `Api::DeploysController#create` (`app/controllers/shipit/api/deploys_controller.rb:19-28`) only requires `deploy:stack` permission on the target stack (`require_permission :deploy, :stack`, checked via `require_permission!` → `current_api_client.check_permissions!`), and then calls `stack.trigger_deploy(commit, current_user, ...)`, writing the deploy record with `current_user` as its owner/actor.

Because `check_permissions!` only validates the *token's* scoped permissions (`app/models/shipit/api_client.rb:38-45`) and never touches `current_user`, any token with `deploy:stack` on a given stack can set `X-Shipit-User` to any existing login (e.g., an admin/approver) and have the resulting `Deploy` permanently recorded as triggered by that victim. Existing guards (`authenticate_api_client`, `require_permission!`, `ExplicitParameters` schema on `create`) all operate on the token/`ApiClient`, not on the asserted human identity, so none of them close this gap.

Attacker request:
```
POST /api/:stack_id/deploys
Authorization: Basic <base64 of attacker's own valid token, deploy:stack scoped to stack A>
X-Shipit-User: admin-victim-login
{ "sha": "<40-char sha of a commit on stack A>" }
```

### Impact Explanation
Each such request causes `Deploy#user_id` (and the audit/approval trail rendered in the UI and API) to falsely record that the named victim triggered the deploy, while the actual actor is the low-privilege token holder. This is an identity/attribution-forgery bug: it doesn't grant the attacker a permission they lack (they must already hold `deploy:stack` on the target stack), but it lets them forge who is accountable for that deploy — enabling scenarios like making it appear an admin approved/triggered a risky deploy, undermining audit logs, `SHIPIT_USER`/`EMAIL` values injected into deploy scripts (`lib/shipit/task_commands.rb`), and any downstream logic or reporting that trusts `Task#user`/`Deploy#user_id` as the authenticated actor. It is repeatable against any stack the attacker's token can deploy to, and against any existing login the attacker knows, but is bounded to stacks/tokens the attacker already has legitimate `deploy:stack` access to — it does not let them deploy stacks they cannot otherwise touch.

### Likelihood Explanation
Preconditions are minimal and match the described attacker model exactly: possession of any narrowly-scoped API token with `deploy:stack` on some stack (a normal, low-privilege self-service/CI credential), and knowledge of a victim's Shipit login (typically public via GitHub). No secrets, sessions, or special roles are needed. The header is unauthenticated and freely settable by any HTTP client, making this trivially and repeatably exploitable on every deploy/rollback request.

### Recommendation
Bind the asserted human identity to the authenticating `ApiClient`: either remove `identify_user`'s header-based lookup entirely and use `current_api_client.creator` as `current_user`, or require that the `X-Shipit-User` value be verified against a list of identities explicitly authorized to act through that specific `ApiClient` (e.g., only allow the header to be honored when `current_api_client.creator.login.casecmp?(user_login)`, or restrict the "impersonation" feature to a distinct, separately-audited permission scope tied to team membership checks via `User#authorized?`).

### Proof of Concept
```ruby
# test/controllers/api/deploys_controller_test.rb
test "#create attributes the deploy to the API client's creator, not an arbitrary X-Shipit-User header" do
  attacker_client = shipit_api_clients(:shipit)          # token with deploy:stack on @stack
  victim = shipit_users(:walrus)                          # distinct existing user, not attacker_client.creator
  assert_not_equal attacker_client.creator.login, victim.login

  authenticated_post(:create, params: { stack_id: @stack.to_param, sha: @commit.sha },
                      headers: { 'X-Shipit-User' => victim.login })

  deploy = Shipit::Deploy.last
  assert_response :accepted
  # Binding under test: current_user (deploy actor) must equal the authenticated ApiClient's creator
  refute_equal victim.id, deploy.user_id,
    "Deploy was forged as triggered by #{victim.login}, an identity unrelated to the authenticating token"
  assert_equal attacker_client.creator.id, deploy.user_id
end
```
Running this test against the current code fails (`deploy.user_id == victim.id`), demonstrating the forged attribution.
