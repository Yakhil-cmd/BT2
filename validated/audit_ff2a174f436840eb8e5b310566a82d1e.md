### Title
`StatusHandler#process` updates `Commit` rows across all stacks by `sha` alone, letting a fork owner forge CI status for a victim's stack sharing the same commit sha - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up `Commit.where(sha: params.sha)` with no scoping to the repository named in the webhook payload, then calls `commit.create_status_from_github!(params)` on every matching commit regardless of which `Stack`/repository it belongs to. Because the `commits` table's uniqueness constraint is `(sha, stack_id)` rather than `sha` alone, the schema explicitly anticipates the same sha existing under multiple stacks (e.g., forks sharing history), and this handler will write a `Status` to all of them from a single signed webhook.

### Finding Description
The binding the question probes is: every `Status` counted by `Commit#status` (via `Status::Group.compact`) must originate from a handler that checked `commit.stack`'s repository against the payload's repository. Tracing `Status::Group` (`app/models/shipit/status/group.rb`) and `Status::Common#success?`/`Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) confirms there is indeed no `stack_id`/repository check inside `Status::Group` or `Commit#status` — that logic only compacts/aggregates whatever `Status` rows already belong to `commit.statuses`, via the `belongs_to :commit`/`belongs_to :stack` associations on `Status` (`app/models/shipit/status.rb:11-12`).

The real question is whether the *handler layer* (which the binding says is where verification must occur) actually performs the repository check for every code path that creates a `Status`. It does not, for the `status` webhook event:

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) verifies the HMAC signature against `Shipit.github(organization: repository_owner)`, i.e., it verifies the payload was really sent by *some* GitHub App installation belonging to `repository_owner` taken straight from the attacker-controlled payload's `repository.owner.login`. This only proves "a legitimate GitHub webhook from repository X", not that repository X is the one whose stack is being mutated.
- `Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper that resolves `Repository.from_github_repo_name(repository_name)&.stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), and other handlers such as `CheckSuiteHandler` correctly use it: `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-16`) — scoping strictly to the calling repository's own stacks.
- `StatusHandler`, however, bypasses `stacks` entirely: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`). This is a global, unscoped lookup across every `Stack` in the installation.
- `commits.replicate_from_github!`/`Status.replicate_from_github!` (`app/models/shipit/status.rb:24-33`) then creates the `Status` row using `stack_id:` taken from `commit.stack_id` — i.e., the row is faithfully attributed to whichever commit was matched, not to the repository that actually sent the webhook. There is no assertion anywhere that `commit.stack.repository.full_name == payload['repository']['full_name']`.

**Exploit path**: An attacker who owns/forks a repository sharing commit history with a Shipit-tracked victim repository (a very common scenario: GitHub forks initially contain identical commit shas) can:
1. Fork the victim's tracked repository (or otherwise obtain a repo containing the exact same commit sha as one on the victim's stack — e.g., by cherry-picking/rebasing into an identically-content commit, which reproduces the same sha).
2. Configure a webhook (or use the fork's status API, which anyone with push access to their own fork can call, e.g. `POST /repos/{attacker}/{fork}/statuses/{sha}`) to send a `status` event with `state: "success"` for that shared sha.
3. GitHub delivers this `status` webhook to Shipit, correctly signed for the attacker's own organization/repository — `verify_signature` passes because it only checks the sender's identity, not the target stack.
4. `StatusHandler#process` matches `Commit.where(sha: params.sha)`, which returns the victim's `Commit` row too (same sha, different `stack_id`), and creates a `success` `Status` on it via `commit.create_status_from_github!`.
5. `Commit#status` (`Status::Group.compact`) now includes this forged `Status`, indistinguishable from a same-repo status, potentially flipping `Commit#success?`/`#deployable?` to true and enabling `next_expected_commit_to_deploy`/`trigger_continuous_delivery` to deploy the victim's commit.

Existing guards fail because: `verify_signature` authenticates only the caller's own repository/org, not the target of the mutation; `ExplicitParameters` schema for `StatusHandler` (`sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches`) contains no repository field to check; and neither `Status::Group` nor `Commit#status` perform any provenance check, exactly as the binding states — the difference from other handlers (`CheckSuiteHandler`) shows the intended pattern (scope via `stacks`/`Repository.from_github_repo_name`) exists in the codebase but is not applied in `StatusHandler`.

### Impact Explanation
A `success` (or `failure`) `Status` is written for a `Commit` belonging to a stack/repository the attacker does not control and never authenticated against, directly matching "a payload for one repository mutating another's stack, commit... or an unauthorized deploy." If the victim stack has `continuous_deployment: true` or a human triggers deploy based on the falsely-green CI state, this becomes an unauthorized deploy of a forged-successful commit — Critical impact. It is repeatable against any repository that shares (or can be made to share, via identical-content commits) a sha with the victim, and does not require any Shipit session, API token, or team membership.

### Likelihood Explanation
Preconditions: the attacker needs a GitHub repository they control that produces the exact same commit sha as a commit in the victim's tracked stack. This is trivially achievable via a straightforward fork before any diverging commits are made (a common state for freshly-forked, unmerged branches, or for a shared ancestor commit already present in the victim's history), and requires no special Shipit configuration, secrets, session, or team membership — only a GitHub account and repository. Cost is low; feasibility is high for the common fork/shared-history scenario; the attack is fully repeatable against any number of matching commits.

### Recommendation
In `StatusHandler#process`, scope the lookup to the reporting repository's own stacks, mirroring `CheckSuiteHandler`: replace `Commit.where(sha: params.sha)` with something like `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) } }`, using the existing `stacks`/`repository_name` helper from `Handler` so that only commits belonging to a stack whose repository matches the payload's `repository.full_name` are updated.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook updates commits across unrelated stacks sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = shipit_stacks(:cyclimse) # different repository entirely

  shared_sha = "deadbeefcafefeed1234567890abcdef12345678"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim work", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  attacker_stack.commits.create!(sha: shared_sha, message: "attacker fork", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  refute_predicate victim_commit, :success?

  # Payload signed for the attacker's own repository/org, naming only the attacker's repo
  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => attacker_stack.repo_name, "owner" => { "login" => attacker_stack.repo_owner } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  # Binding check: forged cross-repo status is indistinguishable from a same-repo status
  assert_predicate victim_commit, :success?
  assert_predicate victim_commit, :deployable?
end
```
This demonstrates that a `status` payload naming only the attacker's own repository still causes `Commit#success?`/`#deployable?` to flip true on a commit belonging to an entirely different stack, because `StatusHandler#process` and everything downstream (`Status::Group`, `Commit#status`) perform no `stack_id`-vs-payload-repository check.
