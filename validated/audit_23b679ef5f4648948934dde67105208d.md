### Title
Attestor-list update by an asset definer can permanently freeze already-held, fully-compliant balances of a `spender_attested` asset - ([File: validation.js])

### Summary
For assets defined with `spender_attested: true`, spendability of every output is re-evaluated at spend time against only the *current, latest* attestor list, not the list that was in force when the holder received/held the funds. This mirrors the JOJO `JUSDBank` bug class: an owner-controlled allow-list change (there: delisting a collateral token; here: replacing the attestor list) retroactively invalidates a holder's previously valid, fully-backed position, and the holder is left with no way to recover any of their balance, even though the coins are objectively theirs and were validly attested at the time they were received.

### Finding Description
An asset issuer (definer) can publish `asset_attestors` messages at any time to redefine the trusted attestor set for a `spender_attested` asset: [1](#0-0) 

When a later payment spends a UTXO of such an asset, `storage.readAsset` fetches only the **most recently published** attestor list for the asset (not the list that was valid when the output was created), and `filterAttestedAddresses`/`loadAssetWithListOfAttestedAuthors` determine "is attested" purely against that single latest list: [2](#0-1) [3](#0-2) 

The spend-side check in payment validation then hard-fails if the owner of the input being spent is not present in this *current* attestor list — with no fallback, grace period, or partial-withdraw path: [4](#0-3) 

Similarly, the issuer's ability to even receive new outputs is gated the same way for outputs: [5](#0-4) 

This is structurally identical to the JUSDBank bug: the historical, already-validated collateral/attestation state of a legitimate holder is discarded and replaced entirely by a single, definer-controlled "current allow-list" check. In JOJO, delisting the collateral zeroed out its contribution to `_maxMintAmount()` while the debt remained, blocking withdrawal of a fully solvent position. In ocore, replacing the attestor list zeroes out the holder's "is attested" status while their balance remains, blocking any and all spending of that balance — a strictly more severe outcome (total freeze vs. partial freeze), because there is no proportional/partial-withdraw mechanism and no historical grandfathering of previously-attested holders.

### Impact Explanation
Any address holding a `spender_attested` asset can have 100% of that balance permanently frozen unilaterally by the asset definer publishing a new `asset_attestors` list that drops the holder's attestor. Because the check (`storage.js:1917-1946`, `validation.js:2506`) only consults the single latest attestor-list unit, there is no way for the affected holder to prove/replay the older, still-technically-valid attestation to regain spendability — the funds are stuck in the holder's outputs forever (or until the definer restores a compatible list, which is entirely at the definer's discretion). This is a concrete "AA fund loss / freezing"-class and general fund-freezing issue reachable by any ordinary counterparty who ever received such an asset, triggered by a single unprivileged-looking `asset_attestors` message from the definer.

### Likelihood Explanation
`spender_attested` assets and the `asset_attestors` message are fully supported first-class features of the protocol (schema comment: "must subsequently publish and update the list of trusted attestors" — `initial-db/byteball-sqlite.sql:258`). Any asset definer can trigger this by simply posting a new `asset_attestors` unit; no special privilege beyond being the asset's `definer_address` is required, and the resulting freeze applies to all current holders not included in the new list, regardless of when or how validly they acquired their balance.

### Recommendation
When validating whether an output owner is "attested" for spending purposes, use the attestor list that was in effect at (or nearest before) the time the spent output was created/last validated, not solely the single most-recent list; alternatively, allow spending if the owner was attested by *any* list that was valid between receipt of the funds and the current last-ball MCI, or provide an explicit un-freeze/migration path (e.g., a bounded grace window, or crediting/allowing withdrawal against the historical attestation) so that legitimate prior holders are not retroactively and irrevocably stripped of already-held funds by a definer-controlled list update.

### Proof of Concept
1. Definer issues asset `X` with `spender_attested: true` and initial `attestors: [A1]`.
2. Attestor `A1` posts an `attestation` for holder `H`'s address (`writer.js:205-217`), satisfying `filterAttestedAddresses` (`storage.js:1959-1974`).
3. `H` receives a payment of asset `X` (validated fine under `validation.js:2115-2122`/`2506` since `H` is attested).
4. Definer later posts `asset_attestors` for asset `X` with a new list `[A2]` (dropping `A1`) — allowed by `validation.js:2829-2848`, requiring only that the author is the definer.
5. `H` attempts to spend their previously-received, fully valid output of asset `X`. `storage.readAsset` (`storage.js:1917-1946`) now returns only `[A2]` as `arrAttestorAddresses`; `loadAssetWithListOfAttestedAuthors`/`filterAttestedAddresses` find `H` is not attested by `A2`, and `validatePaymentInputsAndOutputs` rejects the spend with `"owner address is not attested"` (`validation.js:2506`).
6. `H`'s balance of asset `X` is now permanently unspendable — there is no partial-withdrawal or historical-attestation fallback, exactly analogous to the JUSDBank depositor being unable to withdraw any of their excedent collateral once the owner delists it, except here the freeze is total and permanent.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}

function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
