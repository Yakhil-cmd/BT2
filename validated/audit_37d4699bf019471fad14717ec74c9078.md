Based on my research, I've identified a clear and reachable analog in the ocore codebase to the reported RubiconRouter fee-omission bug: the bundled `uniswap_like_market_maker.oscript` AA sample (an authoritative reference pattern for AA developers using `ocore`'s AA engine) computes the "divest all" payout directly from `balance[base]` without reserving room for the unit's own `headers_commission`/`payload_commission`, mirroring the exact "max amount not adjusted for fee" root cause from the original finding.

### Title
Last liquidity divestor in an AA can never withdraw because full-balance payout leaves no bytes for unit fees, permanently locking funds - (File: test/samples/uniswap_like_market_maker.oscript, aa_composer.js)

### Summary
`ocore`'s AA execution engine (`aa_composer.js`) requires that any base-asset (bytes) payment message generated by an AA be funded from that same AA's actual byte balance, and that balance must also cover `headers_commission`, `payload_commission`, and (post-v4) `tps_fee`/`oversize_fee` for the response unit itself, exactly as enforced in `validatePaymentInputsAndOutputs` for the base asset: `total_input !== total_output + headers_commission + payload_commission + oversize_fee + tps_fee + burn_fee + vote_count_fee`. The bundled reference AA `uniswap_like_market_maker.oscript` computes the divest payout as `round($investor_share * balance[base])`, which for the last remaining investor (`$investor_share == 1`) equals the AA's *entire* current byte balance, leaving nothing to cover the unit's own commissions. This is functionally identical to the RubiconRouter bug: a "withdraw-all"/"max amount" computation that doesn't subtract the fee that will unavoidably be charged on top, so the operation that is supposed to work for 100% of the balance always fails.

### Finding Description
In `aa_composer.js`, when an AA sends a payment (`sendUnit`/`completePaymentPayload`), the base-asset payment message must fund not only the requested output amount but also `objUnit.headers_commission + objUnit.payload_commission` (+ `oversize_fee`, `tps_fee` when applicable) — see `aa_composer.js` `completePaymentPayload` (lines 1061-1139) and the corresponding validation rule in `validation.js` (lines 2661-2668) that enforces `total_input === total_output + headers_commission + payload_commission + oversize_fee + tps_fee + burn_fee + vote_count_fee`.

In `test/samples/uniswap_like_market_maker.oscript` (lines 67-100), the "divest MM shares" case computes:
```
$investor_share = $mm_asset_amount / var['mm_asset_outstanding'];
...
{ app: 'payment', payload: { asset: "base", outputs: [{address: "{trigger.address}", amount: "{ round($investor_share * balance[base]) }"}] } }
```
`balance[base]` here reflects the AA's currently tracked spendable byte balance (per `formula/evaluation.js` `readBalance`, lines 1510-1528, and `aa_composer.js` `updateInitialAABalances`). When the last investor divests (`$investor_share == 1`), the computed output amount equals 100% of `balance[base]`. Because the AA still must pay its own unit's headers/payload commission out of that same balance, the payment message will never fund successfully — `completePaymentPayload`'s input-selection (mirroring `inputs.js` `pickDivisibleCoinsForAmount`) can never find enough left over for fees, and the AA response bounces with an error analogous to `"not enough spendable funds ... for fees"` (see `composer.js` lines 538-546 for the equivalent wallet-side check). This is the direct oscript-level analog of the RubiconRouter `maxSellAllAmount`/`maxBuyAllAmount` bug: the "withdraw 100%" computation omits the mandatory protocol fee that is deducted on top of the requested amount, so the transaction that should succeed for the full balance always fails.

### Impact Explanation
Because `$investor_share` is deterministically 1.0 for the last remaining share-holder (there is no other way to reduce `var['mm_asset_outstanding']` to zero), the last investor's divest request will *always* bounce. Their MM shares (`$mm_asset`) and underlying pooled `$asset`/bytes remain locked in the AA with no code path in this AA template able to release them: any retry recomputes the same 100%-of-balance amount and bounces again. This constitutes a permanent freeze of AA-held funds for the affected user, matching the "AA fund loss or freezing" impact category — the residual value proportional to the last shareholder becomes unrecoverable through the AA's intended state machine.

### Likelihood Explanation
This requires no privileged access and no cooperation from other parties: any ordinary AA trigger sender who ends up being the last remaining MM-share holder (a state reachable through completely normal, permitted trade/divest activity by other users) will trigger this condition. Because `ocore` does not enforce fee-aware payout computation at the language level, and this exact "send 100% of `balance[]`" pattern is documented and shipped as reference guidance for oscript authors (also seen similarly in `test/samples/order_book_exchange.oscript`'s unguarded `withdraw` case, which sends `trigger.data.amount` without ever reserving margin for the AA's own commission), this bug class is straightforward for any AA developer using this template to inherit, and straightforward for an attacker/last-holder to trigger deterministically once shares approach depletion.

### Recommendation
- AA templates that compute a "send full/max balance" payout in the base asset must explicitly reserve margin for `headers_commission + payload_commission (+ oversize_fee + tps_fee)` before computing the output amount, e.g. `amount = balance[base] - RESERVED_FEE_MARGIN` (as correctly done in `test/samples/a_bank_without_percent.oscript`'s withdraw case, which requires `$fee <= var[$base_key]` as a precondition, and `test/samples/fundraising_proxy.oscript`, which subtracts `2000` "to account for fees").
- Alternatively, use the engine's native send-all output syntax (an output with no `amount` field), which `aa_composer.js`'s `completePaymentPayload` (lines 1069-1136) automatically computes as balance minus consumed fees/`storage_size`, instead of manually multiplying `balance[base]` by a computed share ratio.
- Document in the oscript/AA authoring guidance that `balance[base]` used to synthesize an exact payment amount must never be spent in full without a fee reserve, since the AA unit itself is fee-liable.

### Proof of Concept
1. Deploy `uniswap_like_market_maker.oscript` as an AA; two investors, A and B, each invest bytes+asset and receive MM shares (`mm_asset`), so `var['mm_asset_outstanding'] = shares_A + shares_B`.
2. Investor A fully divests: sends all of their `mm_asset` shares back. `$investor_share = shares_A / (shares_A+shares_B) < 1`, payout succeeds, `var['mm_asset_outstanding']` reduces to `shares_B`.
3. Investor B (now the sole remaining holder) sends all of their `mm_asset` shares to divest: `$investor_share = shares_B / shares_B = 1`. The computed base-asset payout is `round(1 * balance[base])` = the AA's entire byte balance.
4. `aa_composer.js`'s `sendUnit`/`completePaymentPayload` attempts to build the response unit's base payment message funding that full amount, but the AA must also fund `headers_commission + payload_commission` (and any `oversize_fee`/`tps_fee`) out of the same balance; there are insufficient bytes remaining, and per `validation.js`'s balance-equality rule (lines 2661-2668) the unit cannot be constructed/validated. The trigger bounces with a "not enough" error every single time investor B attempts to divest, permanently locking investor B's pooled bytes and asset share.
