### Title
`pallet-psm::redeem` requires the external asset to still be whitelisted, making governance removal of an approved external asset permanently freeze outstanding internal-asset debt against it - ([File: substrate/frame/psm/src/lib.rs])

### Summary
The `pallet-psm` pallet mirrors the UXDController pattern exactly: a "PSM" instance mints an internal stablecoin against approved "external" assets and burns it on redemption. Both `mint` and `redeem` gate on the same per-instance whitelist, `ExternalAssets<T>`, populated by `add_external_asset` and emptied by `remove_external_asset` (evidenced by the `ExternalAssetAdded`/`ExternalAssetRemoved` events at [1](#0-0) ). `redeem` fails with `UnsupportedAsset` the moment the entry is gone from `ExternalAssets`, exactly like `UXDController._redeem`'s whitelist check.

### Finding Description
`redeem` requires the `(internal_asset, external_asset)` pair to still exist in `ExternalAssets`: [2](#0-1) 

This is the same whitelist entry that `add_external_asset` creates and that governance/admin removes via `remove_external_asset` (its effect is documented and observable through the `ExternalAssetRemoved` event definition): [1](#0-0) 

Crucially, outstanding debt for a given `(internal_asset, external_asset)` pair is tracked independently in `PsmDebt`, and is only decremented inside `redeem` itself: [3](#0-2) [4](#0-3) 

Nothing in `remove_external_asset` (as far as reachable in this scan) forces `PsmDebt` for that pair to be zero before deletion, nor does it migrate the reserve. So once an admin removes an external asset - e.g., because of a de-peg, an oracle failure, or a security concern with that stablecoin - every holder who minted the internal stablecoin against it via that pair loses the only pallet-native path to redeem, even though the PSM's reserve account (`Self::psm_account(&internal_asset)`) still physically holds the external asset backing that debt. This is structurally identical to the UXDController report: an entry gate shared by both mint and redeem paths turns "delist an asset" into "permanently trap already-issued liabilities against it."

The dedicated `CircuitBreakerLevel` mechanism in this pallet (`MintingDisabled` / `AllDisabled` / `AllEnabled`, checked via `allows_redemption()`/`allows_minting()`) is explicitly designed to disable minting while preserving redemption — this is the correct fix pattern the report itself recommends. But `remove_external_asset`, which fully deletes the `ExternalAssets` entry (not merely sets a circuit-breaker level), reintroduces the same all-or-nothing whitelist coupling that the circuit breaker was meant to avoid: once the entry is gone, `redeem`'s `ExternalAssets::<T>::get(...).ok_or(Error::<T>::UnsupportedAsset)?` unconditionally fails regardless of circuit-breaker state.

### Impact Explanation
Any user who minted internal stablecoin against an external asset that is later fully removed (as opposed to merely circuit-broken) can no longer redeem through the pallet, even though the pallet's reserve account still holds their backing collateral. This is the same "impossible to un-whitelist in practice / unbacked outstanding debt from the user's perspective" impact described in the source report — not asset theft, but a freezing/DoS of legitimate redemption for existing debt, with the reserve funds becoming effectively stuck in the PSM account for that pair. Given `pallet-psm` is intended to back a stablecoin (per its own docs, "1:1 backed by external assets in that PSM's reserve"), this breaks the redeemability invariant central to the pallet's purpose.

### Likelihood Explanation
This requires only the pallet's own privileged (`full_admin`/root, depending on configured origin) removal call to be exercised on a pair with nonzero `PsmDebt` — a realistic operational scenario (delisting a de-pegged or compromised external asset) rather than an attacker-controlled exploit. It is a design/logic gap rather than an attacker-triggerable vulnerability requiring stolen keys or malicious peers, consistent with a Medium-severity classification analogous to the original report.

### Recommendation
Before allowing `remove_external_asset` to delete the `ExternalAssets` entry for a pair, either (a) require `PsmDebt::<T>::get(internal_asset, external_asset)` to be zero, or (b) preserve a redemption-only path (mirroring `CircuitBreakerLevel::AllDisabled`'s `allows_redemption()` semantics) that continues to service redemptions against the remaining reserve/debt even after removal from the mintable whitelist, only fully purging the entry once debt reaches zero.
