### Title
Unbounded Memory Allocation When Reading HTTP Responses in Askpass/Webhook/GitHub-App Token Handlers - ([File: main.go], [File: pkg/hook/webhook.go])

### Summary
`git-sync`'s HTTP-based credential and notification handlers — `CallAskPassURL()`, `RefreshGitHubAppToken()`, and the `Webhook.Do()` hook — read the entire HTTP response body into memory with `io.ReadAll`/`json.NewDecoder` and impose no maximum size limit, mirroring the exact bug class in CBST-01/CBST-12 (loading an unbounded, untrusted response into memory before/without any size check).

### Finding Description
`CallAskPassURL()` issues a GET request to the operator-configured `--askpass-url` and then reads the full response body unconditionally, with no `io.LimitReader` or content-length ceiling, both on the error path and the success path: [1](#0-0) 

The success-path read is likewise unbounded: [2](#0-1) 

The same pattern exists in `RefreshGitHubAppToken()`, which decodes the GitHub App token-exchange response with `json.NewDecoder(resp.Body).Decode(...)` and reads the error body with `io.ReadAll` — again with no size cap: [3](#0-2) 

And in the generic webhook hook, `Webhook.Do()` reads the full webhook response body unconditionally: [4](#0-3) 

These functions are invoked from `refreshCreds()`, which runs on every sync iteration whenever `--askpass-url` or GitHub App auth is configured: [5](#0-4) 

Unlike the Commit-Boost issue (where a size check existed but ran too late), these git-sync code paths have **no size check at all** — any response returned by the configured askpass/token/webhook endpoint (or an attacker able to influence that endpoint's response, e.g. via a compromised/MITM'd internal metadata service that `--askpass-url` typically points to) will be fully buffered in memory regardless of size.

### Impact Explanation
Because `refreshCreds()` (and thus these HTTP reads) execute on every sync attempt, a malicious or compromised response from the configured askpass/token/webhook endpoint can repeatedly force `git-sync` to allocate arbitrarily large buffers, exhausting memory and crashing the sidecar process. Since `git-sync` is typically deployed as the sole mechanism keeping a Kubernetes volume in sync, a crash-looping or OOM-killed `git-sync` container results in **persistent sync denial** — the shared volume stops receiving updates, and dependent application containers serve stale content indefinitely.

### Likelihood Explanation
This requires `--askpass-url`, GitHub App auth, or `--webhook-url` to be configured, and requires the response source to be attacker-influenced (e.g., a spoofed/compromised metadata endpoint, DNS hijack, or a malicious webhook target reachable by the pod). This is a plausible but not default configuration, so likelihood is Low-to-Medium — comparable to the "Low" likelihood rating given to the analogous Commit-Boost issue (CBST-01), which also required a malicious/compromised relay response.

### Recommendation
Wrap all response bodies with `io.LimitReader(resp.Body, maxSize)` (or `http.MaxBytesReader` where applicable) before calling `io.ReadAll` or `json.NewDecoder(...).Decode(...)` in `CallAskPassURL()`, `RefreshGitHubAppToken()`, and `Webhook.Do()`. Choose a `maxSize` appropriate to the expected payload (these responses are only expected to contain short `username=`/`password=` lines or small JSON tokens, so a few KiB is sufficient), and return an explicit `PayloadTooLarge`-style error if the limit is exceeded.

### Proof of Concept
1. Deploy `git-sync` with `--askpass-url=http://attacker-controlled-or-compromised-endpoint/creds`.
2. Point that endpoint to return an HTTP 200 response with an arbitrarily large body (e.g., several GiB of data) with `Content-Length` unset or chunked.
3. On the next sync iteration, `refreshCreds()` calls `git.CallAskPassURL(ctx)` at [6](#0-5) , which reads the entire body via `io.ReadAll(resp.Body)` at [2](#0-1)  with no size bound.
4. Repeated syncs (default `--period` 10s) cause repeated large allocations, exhausting the container's memory limit and causing the `git-sync` process/pod to be OOM-killed, halting all further synchronization (persistent denial of sync).
