### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` triggers unauthorized deploy - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits to attach a GitHub `status` webhook to purely by SHA, across the entire `commits` table, with no scoping to the repository that the webhook's signature was verified against. An attacker who controls any GitHub org/repo already known to the Shipit installation (i.e., can produce a validly-signed webhook for their own repository) can push a commit whose SHA collides with a commit in a victim's tracked stack, then fire a `status` webhook for that SHA. This creates a `Status` on the victim's `Commit`, which cascades into `Stack#trigger_continuous_delivery` and can trigger an unauthorized deploy of the victim's stack.

### Finding Description
The broken binding, stated explicitly: `repository_owner` used to select the `webhook_secret` in `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`) must equal the `Repository`/`Stack` whose `Commit` rows are mutated by the event handler. This equality does not hold for the `status` event.

Trace:
1. `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the payload and dispatches to `Shipit::Webhooks.for_event('status')`, which resolves to `Handlers::StatusHandler` (`app/models/shipit/webhooks.rb:19`).
2. `verify_signature` only checks that the HMAC signature matches the `webhook_secret` for the org named in `params.dig('repository','owner','login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`). It never constrains *which* `Commit`/`Stack` rows the handler is allowed to touch — it only proves the payload was signed by *some* org's secret.
3. Unlike `CheckSuiteHandler`, which scopes lookups through `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-34`, resolving `Repository.from_github_repo_name(repository_name)`), `StatusHandler#process` ignores `payload['repository']` entirely: [1](#0-0) . It runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` against the **global** `Commit` table, not scoped to the attacker's repository/stack.
4. `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) creates a `Status` row on whatever `Commit` matched, regardless of tenant.
5. `Status` has `after_commit :schedule_continuous_delivery, on: :create` (`app/models/shipit/status.rb:19`), which calls `commit.schedule_continuous_delivery` (`app/models/shipit/status.rb:42-44`).
6. `Commit#schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`) checks `deployable? && stack.continuous_deployment? && stack.deployable?` and enqueues `ContinuousDeliveryJob.set(wait: ...).perform_later(stack)` — the **victim's** stack, since `stack` is derived from the matched `Commit`, not from the attacker's payload.
7. `ContinuousDeliveryJob` calls `Stack#trigger_continuous_delivery` (`app/models/shipit/stack.rb:210-229`), which picks `next_commit_to_deploy` and calls `trigger_deploy`, ultimately spawning the victim's deploy `Task`/`Command`/`PTY.spawn` with the victim's deploy environment.

Exploit flow: Attacker registers/uses their own GitHub org+repo already onboarded to this Shipit instance (a legitimate but separate tenant), giving them a valid `webhook_secret` for their own org. They craft a commit (in their own repo) with content/parents/timestamps chosen to produce the exact same SHA-1 as a commit already tracked in `victim`'s stack — feasible since SHA-1 is content-addressed and reproducible when the victim's commit is public. They then send a `status` webhook (`POST /webhooks`, `X-Github-Event: status`) naming their own repository in `payload['repository']`, correctly signed with their own org's secret, with `state: 'success'` and the colliding `sha`. `verify_signature` passes (correctly signed for the attacker's own org). `StatusHandler#process` then matches and mutates the **victim's** `Commit` row because the lookup is by SHA only, causing an unauthorized deploy trigger on `victim`'s stack.

Why existing guards fail: `verify_signature` only authenticates "this payload was sent by org X," not "org X may only affect its own repository's records." `drop_unhandled_event` and the `ExplicitParameters` schema (`requires :sha, String; requires :state, String`) validate shape, not ownership. `stack.deployable?`/`force_github_authentication`/`require_permission!` are irrelevant here since no user session or API token is involved — this is a pure webhook-provenance binding failure specific to `StatusHandler`.

### Impact Explanation
An attacker with no privileges on the victim's repository, team, or Shipit installation can cause the creation of a `Status` on the victim's `Commit` and, if the victim's stack has `continuous_deployment: true` and is idle, trigger an unauthorized deploy of the victim's current HEAD to the victim's deploy host, executing whatever commands the victim's deploy spec runs via `Command`/`PTY.spawn` with the victim's deploy environment. This is a payload from one repository mutating another repository's stack/commit and causing an unauthorized deploy — matching the Critical impact category. It is repeatable against any stack tracked by the Shipit instance for which the attacker can produce a SHA-colliding commit in their own onboarded repository, and the blast radius spans across tenants of the same Shipit installation.

### Likelihood Explanation
Preconditions: attacker must control at least one GitHub repository already onboarded to the same Shipit instance (so a `webhook_secret` exists for their org) and be able to author/import a commit whose SHA-1 matches a commit already present in `victim`'s stack (straightforward if the victim's commit is public — clone/import it verbatim into the attacker's own repo history). Victim's stack must have `continuous_deployment: true` and be otherwise deployable/idle at the time. No GitHub credentials, session, or API token belonging to the victim or Shipit operator are required; only a same-instance repository owned by the attacker and the ability to POST a webhook. This is a real vulnerability in the engine's own webhook dispatch logic, independent of any GitHub API weakness.

### Recommendation
Scope `StatusHandler#process` to the repository named in the verified webhook payload, mirroring `CheckSuiteHandler`/`PushHandler`: resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and restrict the `Commit.where(sha: ...)` lookup to `commits` belonging to those stacks (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or a joined scope), so a status event can only mutate commits belonging to the repository that authenticated the request.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test ":status webhook for attacker's own repository must not create a Status on another tenant's commit with the same sha" do
  victim_stack = shipit_stacks(:shipit) # has continuous_deployment enabled in this scenario
  victim_stack.update!(continuous_deployment: true)
  victim_commit = victim_stack.commits.last

  # Attacker's own repo/org, separately onboarded, distinct from victim's repository
  attacker_repo_params = {
    'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true) # attacker's own valid secret

  body = {
    'sha' => victim_commit.sha,          # SHA collision with victim's tracked commit
    'state' => 'success',
    'context' => 'ci/attacker',
    'branches' => [{ 'name' => victim_stack.branch }]
  }.merge(attacker_repo_params).to_json

  request.headers['X-Github-Event'] = 'status'

  assert_no_enqueued_jobs(only: Shipit::ContinuousDeliveryJob) do
    assert_no_difference -> { victim_commit.statuses.count } do
      post :create, body: body, as: :json
    end
  end
end
```
Given the current code, this test **fails** (a `Status` is created on `victim_commit` and `ContinuousDeliveryJob` is enqueued for `victim_stack.id`), demonstrating the cross-tenant write and unauthorized-deploy trigger.
