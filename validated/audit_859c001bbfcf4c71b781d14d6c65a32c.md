### Title
Stale `login`-keyed lookup in `Shipit::User.find_or_create_by_login!` lets an attacker's GitHub-account permanently retain a Shipit `User` row that a later `membership` webhook can silently promote into `Shipit.github_teams` - ([File: app/models/shipit/user.rb])

### Summary
`Shipit::User.find_or_create_by_login!` resolves records purely by the `login` string, and the DB index on `users.login` is non-unique, so a row created for a GitHub account that once owned a given login is returned—and never re-validated against the account that currently owns that login—by any later call (PR authorship, team membership) using the same login string. Combined with `MembershipHandler`, which calls this same method to attach team membership, an attacker who transiently owns a login value can retain a `Shipit::User` row that gets attached to a team membership meant for a different, later account.

### Finding Description
The binding that must hold is: `User.find_by(login: L).github_id == current GitHub owner's id for login L`. This binding is **not** enforced.

`find_or_create_by_login!` is:
```ruby
def self.find_or_create_by_login!(login)
  find_or_create_by!(login:) do |user|
    user.github_user = Shipit.github.api.user(login)
  end
end
``` [1](#0-0) 

`find_or_create_by!` first does `find_by(login:)`; the block (which is the only place `Shipit.github.api.user(login)` is called to refresh `github_id`) only runs when a **new** record is created. If a row with that `login` already exists, it is returned as-is—its `github_id` is never re-checked against the current GitHub owner of that login.

`app/models/shipit/pull_request.rb#github_pull_request=` calls this method to set `user`/`assignees` from `github_pull_request.user.login`: [2](#0-1) 

`app/models/shipit/webhooks/handlers/membership_handler.rb#process` calls the exact same method to resolve a team member from a GitHub `membership` webhook payload's `member.login`, then attaches team membership to whatever row is returned: [3](#0-2) 

The schema confirms `login` has only a plain (non-unique) index, both historically and currently, so nothing at the DB layer prevents two rows, or a stale reused row, from sharing a login value: [4](#0-3) [5](#0-4) 

Meanwhile, real sign-in resolves users strictly by `github_id`, never by `login`:
```ruby
def self.find_from_github(github_user)
  return unless github_user.id
  find_by(github_id: github_user.id)
end
``` [6](#0-5) 
called from `GithubAuthenticationController#sign_in_github`: [7](#0-6) 

Exploitable sequence:
1. Attacker (owns a real GitHub account, `github_id = A`) registers/renames that account to a login string `L` that they know or guess a real, not-yet-onboarded org member will later use, and opens a pull request against a Shipit-tracked repository. This triggers `PullRequest#github_pull_request=`, which calls `User.find_or_create_by_login!('L')`, creating row `{id: R, login: 'L', github_id: A}` [8](#0-7) .
2. Attacker renames their GitHub account away from `L` (or deletes it), freeing the login. GitHub allows any account to later claim a freed login.
3. The real target account (`github_id = B`) later claims login `L` and is added to a GitHub team backing `Shipit.github_teams`. GitHub emits a legitimate, signature-verified `membership` webhook with `member.login = 'L'`.
4. `MembershipHandler#process` calls `User.find_or_create_by_login!('L')` [9](#0-8) . Because a row with `login='L'` already exists (row `R`, still `github_id = A`, the attacker's), `find_or_create_by!` returns that stale row instead of creating one for `github_id = B`. `team.add_member(member)` therefore attaches team membership to row `R`.
5. When the attacker (still owning `github_id = A`) subsequently authenticates via OAuth, `find_or_create_from_github` resolves by `github_id = A`, which is exactly row `R` — now carrying the team `Membership` that was meant for the real target. `User#authorized?` (`teams.where(id: Shipit.github_teams...).exists?`) [10](#0-9)  now returns true for the attacker.

None of the existing guards catch this: webhook signature verification confirms the `membership` event genuinely came from GitHub, but says nothing about whether the `login` in that payload still maps to the `User` row that a prior GitHub account created; `find_from_github` (used at login) is `github_id`-keyed and correct in isolation but is bypassed entirely by the `login`-keyed lookup used for webhook-driven writes.

### Impact Explanation
The stale-row reuse in `find_or_create_by_login!` lets an attacker-controlled `User` row (keyed to the attacker's real, unchanged `github_id`) receive a `Membership` intended for a different account, letting `User#authorized?` resolve `true` for the attacker without the attacker ever being a genuine member of any `Shipit.github_teams` team. This matches the High-severity category "escalation into `Shipit.github_teams` authorization." Independent of the team-escalation path, the same stale-lookup bug also causes commit authorship / `PullRequest#user` / assignee attribution to permanently point at the wrong `User` row once a login is reclaimed by a different GitHub account, which is a lower-severity data-integrity/attribution issue but not itself a listed Critical/High category.

### Likelihood Explanation
Requires: `Shipit.github_teams` non-empty (already a stated precondition); attacker must be able to squat/claim a GitHub login string that a real org member will later reclaim and use while being added to the relevant GitHub team, and the attacker must have previously interacted with the Shipit-tracked repo (opening a PR) under that login. The attacker fully controls steps 1–2 (registering/freeing a login) at zero cost, but step 3 (the real target reclaiming that exact freed login and being added to the team) is outside attacker control and depends on external, opportunistic timing. This makes the attack feasible but not reliably repeatable on demand against an arbitrary chosen victim; it is a patient, opportunistic username-squatting attack rather than an immediately triggerable one.

### Recommendation
- Make `users.login` a unique index at the DB layer, and stop treating `login` as a reliable, stable identity key for anything security-relevant.
- In `find_or_create_by_login!`, always refresh (or at least re-validate) `github_id` against the freshly fetched `Shipit.github.api.user(login)` result even when an existing row is found by `login`; if the fetched `github_id` differs from the existing row's `github_id`, do not silently reuse the row (create/repoint instead, and log/alert on the collision).
- In `MembershipHandler` and `PullRequest#github_pull_request=`, prefer resolving/creating users by `github_id` (from the webhook/API payload, which usually includes `id`) rather than by `login` alone.

### Proof of Concept
```ruby
# test/models/shipit/user_stale_login_test.rb
require 'test_helper'

module Shipit
  class UserStaleLoginTest < ActiveSupport::TestCase
    test 'find_or_create_by_login! reuses a stale row instead of the current github owner' do
      # Step 1: attacker's account (github_id 1) claims login 'shared-login'
      Shipit.github.api.expects(:user).with('shared-login').returns(
        stub(id: 1, login: 'shared-login', name: 'Attacker', email: nil, avatar_url: '', url: '', rels: nil)
      )
      attacker_row = User.find_or_create_by_login!('shared-login')
      assert_equal 1, attacker_row.github_id

      # Step 2/3: login is later reclaimed by a different real GitHub account (github_id 2),
      # e.g. via a `membership` webhook naming the same login string.
      Shipit.github.api.expects(:user).with('shared-login').never # block not invoked: record already exists by login
      reused_row = User.find_or_create_by_login!('shared-login')

      # Binding under test: reused_row.github_id should equal the CURRENT owner (2), but it doesn't.
      assert_equal attacker_row.id, reused_row.id
      assert_equal 1, reused_row.github_id # BUG: still attacker's github_id, not 2
      refute_equal 2, reused_row.github_id
    end
  end
end
```
This demonstrates, without any live GitHub call for the second lookup, that `find_or_create_by_login!` returns and preserves a stale `github_id` on `login` collision, which is the root cause enabling the `MembershipHandler`-driven team-membership misattribution described above.
