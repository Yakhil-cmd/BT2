### Title
Unsanitized attacker-controlled skill name printed to terminal via `fmt.Fprintf` allows ANSI/OSC escape sequence injection - (File: pkg/cmd/skills/update/update.go)

### Summary
`updateRun` prints the locally-cached skill name (`s.name` / `u.local.name`) directly via `fmt.Fprintf` to both `opts.IO.Out` and `opts.IO.ErrOut` without any terminal-escape sanitization, even though the codebase has an established `iostreams.Untrusted` wrapper specifically built to neutralize ANSI/OSC sequences before printing remote/untrusted content. The skill name is derived from a directory/path segment inside a skill's git tree, which an attacker fully controls when publishing a skill repository, and is not restricted the way GitHub owner/repo names are.

### Finding Description
`installedSkill.name` and `pendingUpdate.local.name` originate from `discovery.Skill` path segments discovered from a remote repository (`discovery.DiscoverSkills`) and are then used as install directory names by `installer.Install`, and are persisted/read back via `scanInstalledSkills`/`parseInstalledSkill` [1](#0-0) . A git tree entry name can contain almost any byte sequence except `/` and NUL, so an attacker publishing a skill repo can name a skill path segment with embedded ANSI/OSC escape bytes (e.g., terminal title/clipboard manipulation sequences).

Once such a skill is installed, `gh skill update` repeatedly echoes the raw name to the terminal without sanitization, e.g.: [2](#0-1) [3](#0-2) 

By contrast, the codebase already implements `iostreams.Untrusted`, whose doc comment states its exact purpose: "wraps string content the application did not author... so any fmt print path... renders the content with ANSI escape sequences neutralized" [4](#0-3) . This wrapper is not used anywhere under `pkg/cmd/skills/`, meaning the same class of untrusted-content-to-terminal issue that this type was built to prevent elsewhere in the CLI (e.g., gist/view, repo/read-file, run/view) is unmitigated in the skills update/list flow.

Note: `owner`/`repo` fields are constrained by GitHub's repository naming rules and are validated either through `ghrepo.FromFullName` (interactive prompt path) [5](#0-4)  or sourced from API-resolved repository identifiers, so they are unlikely to carry raw control bytes. The primary attacker-controlled vector is the skill `name` (path segment), not owner/repo.

### Impact Explanation
This is a terminal escape-sequence injection issue: an attacker-controlled skill name can inject ANSI/OSC sequences into the victim's terminal output when running `gh skill update` (and similarly in `gh skill list`, which shares the same pattern). Depending on the victim's terminal emulator, this can be used for output spoofing (hiding/altering displayed text, faking prior command output), window-title manipulation, or in vulnerable terminals, more dangerous OSC sequences (e.g., clipboard write via OSC 52). This maps to GitHub's "terminal escape sequence / output injection" bounty impact class — generally a low-to-moderate severity issue since it does not directly achieve code execution or credential exfiltration on its own but enables UI spoofing.

### Likelihood Explanation
Requires the victim to have previously installed a skill from an attacker-published repository (`gh skill install`) and to later run `gh skill update`. This is a realistic workflow for anyone using `gh skill` with skills sourced from public repos, and no special privileges are needed by the attacker beyond publishing a public repository with a maliciously-named skill directory/path segment.

### Recommendation
Wrap `s.name`, `u.local.name` (and, defensively, `owner`/`repo`) in `iostreams.Untrusted` (or otherwise strip control/escape characters) before any `fmt.Fprintf`/`fmt.Fprintln` call in `pkg/cmd/skills/update/update.go` that writes them to `opts.IO.Out`/`opts.IO.ErrOut`, consistent with how the CLI already sanitizes other untrusted remote content elsewhere.

### Proof of Concept
Go test plan for `pkg/cmd/skills/update`:
1. Stub `discovery.DiscoverSkills`/installer flow (or directly construct an `installedSkill{name: "\x1b]0;pwned\x07evil", owner: "o", repo: "r", treeSHA: "aaa"}` and a matching `pendingUpdate` with `newSHA: "bbb"`).
2. Call the update-listing code path (the loop at lines 354-365) with an `iostreams.Test()` IOStreams capturing `Out`.
3. Assert that the captured output bytes contain the raw `\x1b]0;...\x07` sequence unmodified (proving no sanitization), versus expected behavior where `iostreams.NewUntrusted(name).String()` would strip/neutralize it.
