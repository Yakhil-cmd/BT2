This is a strong candidate: `StatusHandler` and `MembershipHandler` directly write attacker-supplied payload data (`state`, `description`, `target_url`, `created_at`, team/organization identities) into the database, and neither the `Commit.where(sha: params.sha)` lookup nor `MembershipHandler#find_or_create_team!` re-validates that the *organization whose webhook secret signed the request* actually owns that commit/team. Combined with `WebhooksController#verify_signature`, which selects the signing secret using `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) , the HMAC only proves "this body was signed by App X's secret" — it never proves that the `sha`/`team`/`organization` fields inside that same body actually belong to App X's installation.

### Title
Webhook signature is scoped to the payload's `repository.owner`/`organization.login` field but never re-validated against the resource the handler actually writes to, allowing cross-tenant status/team forgery — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` resolves which GitHub App/organization secret to use for HMAC verification purely from an attacker-controlled JSON field (`repository.owner.login`, falling back to `organization.login`), then hands the *entire* parsed payload to whatever handler matches the event type. The handlers (`StatusHandler`, `MembershipHandler`, `PushHandler`, etc.) locate the record to mutate using a *different* field of the same payload (`sha`, `team.id`, `repository.full_name`) without re-checking that this record actually belongs to the organization whose secret validated the signature.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [2](#0-1) 
and `repository_owner` is read straight out of the untrusted JSON body [1](#0-0) .

On a multi-organization Shipit install (explicitly supported, see `test/dummy/config/secrets_double_github_app.yml` with `OrgOne`/`OrgTwo` each having their own `webhook_secret`) [3](#0-2) , this only proves the raw body was HMAC-signed with *one particular org's* secret. It does **not** constrain any other field inside that same JSON body.

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
``` [4](#0-3) 
`sha` is a free-form attacker-chosen string, matched globally across the `commits` table (not scoped to the repository/org that authenticated). If an attacker who legitimately owns/installs the Shipit GitHub App on their *own* small organization (and therefore genuinely knows that org's `webhook_secret`) crafts a payload whose `sha` collides with a commit SHA belonging to a completely unrelated stack/repository (git SHAs are content hashes and can be pre-computed/brute-forced, or simply guessed for known open-source commits, or leaked via public commit history), the signature check passes (`repository_owner` in their forged payload maps to their own org and its secret), but `create_status_from_github!` writes attacker-controlled `state`, `description`, `target_url`, `created_at` into another stack's CI status, directly influencing deploy gating decisions such as `ci.require` checks documented in `README.md` ("commands.perform" is gated on CI status).

Similarly, `MembershipHandler#find_or_create_team!` binds a `Team` record's `github_id`/`organization` purely from payload data with no cross-check against the organization that signed the request:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
``` [5](#0-4) 
Since `Shipit.github_teams` gates access to privileged UI (`ApiClientsController`, per `test/controllers/api_clients_controller_test.rb`) [6](#0-5) , an attacker signing with their own org's webhook secret can forge `membership added` events claiming an arbitrary `team.id`/`organization.login` and add themselves (`member.login`) as a member of a `Team` whose `github_id` happens to match (or is later reused for) a team named in `Shipit.github_teams`, escalating into an authorization boundary that was meant to be controlled exclusively by the real GitHub organization's membership API.

This mirrors the `OCL_ZVE::forwardYield()` root cause structurally: a gating check (`require(block.timestamp > nextYieldDistribution)` / `verify_webhook_signature` against `repository_owner`) is enforced correctly in isolation, but a *different* piece of state that the gated operation subsequently trusts (`nextYieldDistribution` incrementing from an attacker-influenced starting point / the `sha`/`team.id`/`organization.login` fields used by the handler) is not covered by that same check, breaking the intended binding "organization that authenticated == resource that gets written."

### Impact Explanation
This breaks the "organization authenticated versus the repository/team written" binding called out in scope. Concretely it allows:
- Forged CI status writes on arbitrary commits across tenants, which can flip `ci.require` gating and enable an unauthorized deploy to proceed (High/Critical depending on whether `ci.require` is the only gate for continuous delivery).
- Forgery of `Team`/`Membership` records that can be leveraged toward `Shipit.github_teams` authorization escalation (High, per the explicit impact list).

### Likelihood Explanation
Exploitation requires the attacker to control (or self-install) a GitHub App/organization on the same shared Shipit instance so they possess a valid `webhook_secret` for at least one org — this is realistic for any Shipit deployment serving multiple organizations/customers, which is an explicitly supported and tested configuration in this codebase. Guessing/colliding a target `sha` or `team.id` is the main practical constraint, which is easier for `team.id` (small integer, often discoverable) than for `sha` (would typically require a leaked/known commit hash from the target repo, e.g. from a public fork or previous disclosure).

### Recommendation
`WebhooksController#verify_signature`/each handler should re-derive the organization/repository context strictly from the record being mutated (`commit.stack.repository.github_repo_name`, `Team#organization`) and assert it equals the `repository_owner`/`organization.login` used to select the signing secret, rejecting the event if they diverge — analogous to setting `nextYieldDistribution` from an unconditional absolute timestamp rather than trusting a value that can start from an unvalidated state.

### Proof of Concept
Conceptual PoC (not executed, requires a running instance with ≥2 configured GitHub Apps as in `secrets_double_github_app.yml`):
1. Attacker installs Shipit's GitHub App on their own org `attacker-org`, obtaining its `webhook_secret`.
2. Attacker finds/predicts a commit `sha` that also exists in `victim-org/victim-repo`'s Shipit-tracked history (e.g., a shared open-source dependency commit, or a previously observed SHA).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body `{"repository":{"owner":{"login":"attacker-org"}, "full_name":"attacker-org/decoy"}, "sha":"<victim-sha>", "state":"success", ...}`, signed with `attacker-org`'s `webhook_secret` via `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner = "attacker-org"`, verifies successfully against `attacker-org`'s secret.
5. `StatusHandler#process` matches `Commit.where(sha: "<victim-sha>")` — which belongs to `victim-org/victim-repo` — and writes the forged `state`/`description` as a real CI status on it, independent of `attacker-org`.

**Uncertainty**: I could not fully trace whether `ci.require` checks strictly gate every deploy path (would need `app/models/shipit/deploy_spec.rb`'s CI-check logic, not fully retrieved due to iteration limits) or confirm the exact `Team#github_id` uniqueness/collision risk against `Shipit.github_teams` entries — these would need further verification in a live/Devin session before treating the impact as fully confirmed Critical/High rather than High/Medium.
