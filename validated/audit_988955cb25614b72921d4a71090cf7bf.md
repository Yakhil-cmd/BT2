### Title
Git subprocess stderr is printed unsanitized to the terminal via `CmdError.Error()` / `printError`, allowing ANSI/terminal escape injection - ([File: internal/run/run.go])

### Summary
`CmdError.Error()` in `internal/run/run.go` embeds raw git stderr bytes directly into the error string with no escape-sequence sanitization, and this string is ultimately written verbatim to the CLI's stderr via `printError` in `internal/ghcmd/cmd.go`. Because git stderr content can be influenced by an attacker who controls a repository's refs, hooks, or other repo content that git echoes back on failure, arbitrary terminal escape sequences (OSC/CSI) can reach the victim's terminal.

### Finding Description
`cmdWithStderr.Run()` captures the subprocess's stderr into a `bytes.Buffer` and wraps it in a `CmdError{Args, Err, Stderr}` when the command fails [1](#0-0) . `CmdError.Error()` then builds the final string as `fmt.Sprintf("%s%s: %s", msg, e.Args[0], e.Err)` where `msg` is the raw stderr text with no filtering of control/escape bytes [2](#0-1) . This differs starkly from the pattern used elsewhere in the same codebase (`pkg/iostreams/untrusted.go`'s `Untrusted` type, `pkg/iostreams/content.go`'s `ContainsEscapeSequence`/`CopyGuardedContent`, and `pkg/cmd/skills/list/list.go`'s `sanitizeForTerminal`), all of which explicitly strip or refuse ANSI escapes in content coming from outside the CLI's control before it reaches a terminal [3](#0-2) [4](#0-3) .

The wrapped error propagates up through `git.Command.Run()`, which further wraps it as a `GitError` whose `Error()` also just does `fmt.Sprintf("failed to run git: %s", ge.Stderr)` with no sanitization [5](#0-4) , and from there to `internal/ghcmd/cmd.go`'s `printError`, which does `fmt.Fprintln(out, err)` straight to the process's real stderr (`os.Stderr`), not through `iostreams.ContentOut`/`Untrusted` sanitization path [6](#0-5) .

However, the actual attacker control over git's stderr content is limited. Git subprocess stderr in normal `gh` operation (clone, fetch, push, checkout, etc.) is dominated by git's own fixed diagnostic strings (e.g., "fatal: not a git repository", "unknown config key ..."). While things like custom pre-receive/hook rejection messages, malformed refs, or repository names can appear in stderr in some flows, this requires the attacker to control a git *server*/hook that the victim explicitly clones/fetches/pushes to, which is a more constrained precondition than "publish a repo victim opens." Server-side hook messages are typically attacker-controlled only if the victim is pushing/fetching against an attacker-operated git remote (which the "attacker publishes repos" unprivileged threat model does cover, e.g., a malicious fork/remote the victim is instructed to add, or `gh repo clone`/`gh pr checkout` against an attacker repo whose server emits crafted hook-rejection text on push). This is plausible but narrower than the fully generic claim in the question.

### Impact Explanation
If reachable, this allows terminal escape sequence injection (e.g., OSC 0 title-bar spoofing, CSI colored/hidden text, or terminal query/response sequences) into the victim's terminal when a `gh` git subprocess fails against attacker-influenced content. This matches a low-severity "terminal/UI spoofing" impact class — it does not by itself achieve code execution, but could be used for phishing-style deception (e.g., disguising output, injecting fake prompts) on terminals that interpret dangerous escape codes.

### Likelihood Explanation
Exploitability depends on the victim running a `gh` subcommand that invokes a git subprocess whose failure and stderr content is influenced by the attacker (e.g., a server-side hook rejection message during `push`, or crafted error text returned by a malicious/compromised git remote the victim adds or is directed to). This requires the attacker to control a git server endpoint the victim interacts with, not merely a passive repository, refs, or comments. This is a real but narrower precondition than a generically "malicious repo," and the impact is limited to terminal spoofing on terminals that render dangerous OSC/CSI sequences (many modern terminal emulators sanitize or ignore dangerous sequences, though title-bar and color injection remain broadly effective).

### Recommendation
Sanitize `CmdError.Stderr` (and `GitError.Stderr`) before embedding it into `Error()`, consistent with the pattern already established by `pkg/iostreams/untrusted.go`'s `Untrusted.String()` sanitizer or `pkg/cmd/skills/list/list.go`'s `sanitizeForTerminal`. Wrap subprocess stderr content in `iostreams.NewUntrustedBytes(...)` (or apply the `asciisanitizer.Sanitizer` transform) at the point where it's captured in `cmdWithStderr.Run`/`Output`, so any downstream `%s`/`Error()` call automatically strips escape sequences before it can reach a real terminal via `printError`.

### Proof of Concept
Go-level PoC (does not require a real network host, only a git binary stub reachable via `exec.Cmd`, satisfying "reproducible Go test... git-stub" requirement):
```go
func TestCmdErrorDoesNotLeakEscapeSequences(t *testing.T) {
    cmd := exec.Command("sh", "-c", "printf '\\033]0;pwned\\007fatal: rejected'; exit 1")
    runnable := run.PrepareCmd(cmd)
    err := runnable.Run()
    require.Error(t, err)
    var cmdErr *run.CmdError
    require.ErrorAs(t, err, &cmdErr)
    // Current behavior: fails, because raw ESC byte passes through unsanitized.
    assert.NotContains(t, cmdErr.Error(), "\x1b")
}
```
Expected current result: the assertion fails, demonstrating `CmdError.Error()` contains the raw `\x1b]0;pwned\x07` sequence, confirming the injection reaches any caller (including `internal/ghcmd/cmd.go`'s `printError`) that prints `err.Error()` to the terminal without going through `iostreams.Untrusted`/`sanitizeForTerminal`.
