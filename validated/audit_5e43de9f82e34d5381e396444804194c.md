### Title
Cross-organization commit status forgery via unscoped SHA lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the GitHub *organization* whose webhook secret matches the payload's declared repository owner, but `Webhooks::Handlers::StatusHandler#process` never re-checks that the target `Commit` actually belongs to a repository owned by that same organization. It resolves the target purely by matching `sha` across the entire `commits` table.

### Finding Description
`WebhooksController#verify_signature` picks the HMAC secret using `repository_owner`, derived from the incoming JSON payload itself, and verifies the raw body against it: [1](#0-0) 

This only proves the event was genuinely signed by *some* configured GitHub organization/app (whichever `github_app = Shipit.github(organization: repository_owner)` resolves to) — it says nothing about which repository the handler is allowed to mutate.

Every other status-changing handler re-derives and scopes to the repository declared in the payload before acting, e.g. `PushHandler` and `CheckSuiteHandler` both call `stacks`, which is scoped through `Handler#repository_name` (`payload.dig('repository', 'full_name')`): [2](#0-1) [3](#0-2) [4](#0-3) 

`StatusHandler`, however, ignores `repository_name`/`stacks` entirely and looks the commit up **globally by SHA only**: [5](#0-4) 

Because `sha` is content-addressed, two different repositories tracked by the same Shipit instance (e.g. a fork of a tracked repository, or any repository sharing common ancestor commits) can contain commits with identical SHAs. An attacker who controls (or has push/CI access to) one GitHub organization that is *also* onboarded in this Shipit instance — even one entirely unrelated to the victim's repository — can trigger a genuine, correctly-signed `status` webhook from GitHub for their own repository using a commit SHA equal to a commit that already exists in another stack's `commits` table. `StatusHandler` will match that pre-existing `Commit` row and apply the attacker-supplied `state`/`context`/`description`/`target_url` to it via `commit.create_status_from_github!`: [6](#0-5) 

The equality that is supposed to hold is: **organization whose webhook secret signed the request == organization owning the repository the status is written to.** `StatusHandler` breaks this binding by never checking `repository_name` against the commit's `stack`.

### Impact Explanation
Commit status directly feeds `deployable?`, `blocked?`, and the merge/continuous-delivery pipeline: [7](#0-6) [8](#0-7) 

`add_status` calls `stack.schedule_merges` and can flip a commit from pending/failing to `success`, which is exactly the signal `deployable?`/merge-queue validation rely on to allow an automatic deploy or merge. An attacker who is a legitimate but unprivileged member of *some* org onboarded to the same Shipit instance can forge a "success" status on a commit belonging to a *different*, victim repository/stack, potentially causing Shipit to consider that commit deployable/mergeable without real CI having passed — an unauthorized deploy/merge condition (Critical impact per the rules).

### Likelihood Explanation
Requires that (a) the Shipit instance is multi-tenant — hosting stacks from more than one GitHub organization/app configuration (supported natively, see `config/secrets.development.shopify.yml` showing multiple orgs), and (b) the attacker can produce a commit SHA collision with a commit tracked in the victim stack (trivially achievable by forking the victim's public repository into their own onboarded org, since forks share identical commit objects/SHAs for shared history). No Shipit credentials, `ApiClient` tokens, or GitHub App private key access are needed — only a legitimate account and push/CI trigger rights in an org that is already configured in Shipit.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup by the stack(s) resolved from the payload's own `repository` field (same as `PushHandler`/`CheckSuiteHandler`), e.g. restrict to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Repository.from_github_repo_name(repository_name)` before matching `sha`, so a status can never be attributed to a commit outside the verified organization/repository.

### Proof of Concept
1. Onboard `attacker-org/victim-fork` (a fork of `victim-org/app`) to the Shipit instance with its own webhook secret configured for `attacker-org`.
2. Because it's a fork, commit `abc123...` exists identically in both `victim-org/app` (already tracked as a `Commit` row under stack `victim-org/app`) and `attacker-org/victim-fork`.
3. Attacker triggers (or GitHub naturally sends, e.g. via a CI integration on their fork) a `status` webhook event for `attacker-org/victim-fork` with `sha: "abc123..."`, `state: "success"`.
4. `WebhooksController#verify_signature` succeeds because the signature is valid for `attacker-org`'s webhook secret.
5. `StatusHandler#process` executes `Commit.where(sha: "abc123...")`, which matches the `Commit` row belonging to `victim-org/app`'s stack, and calls `create_status_from_github!`, marking the victim's commit as successful — despite the request never having been authenticated for `victim-org`.

      already_deployed = deployed?

      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)

        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
