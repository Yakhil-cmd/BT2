### Title
Commit author identity can be forged via an unauthenticated `Merge-Requested-By:` trailer in the raw commit message - ([File: app/models/shipit/user.rb])

### Summary
`User.find_or_create_author_from_github_commit` trusts a `Merge-Requested-By: <login>` line found anywhere in a commit's raw message and attributes the commit to that arbitrary, existing Shipit user, without checking whether the commit was actually produced by Shipit's own trusted merge flow. Because `GithubSyncJob` ingests every commit reachable on the tracked branch (fetched from GitHub's API, not the webhook body) and hands it to `Commit.from_github`, any commit whose message contains this trailer - whether pushed directly to the tracked branch or embedded in a PR title/description that ends up in a squash-merge commit message - will have its `author` silently overridden to the named victim.

### Finding Description
The broken binding: `Commit#author` should equal `Shipit::User` records the code creates through `MergeRequest#merge!`'s trusted merge path (an authenticated Shipit action, gated by `MergeRequest.request_merge!`), but instead it can equal any `login` string embedded in the raw git commit message by whoever authored that commit text.

Code path:
- `MergeRequest#merge_message` is the only intended producer of the trailer, writing `"#{title}\n\n#{MERGE_REQUEST_FIELD}: #{merge_requested_by.login}\n"` when Shipit itself performs a merge via `merge!`, using `merge_requested_by` set through the authenticated `MergeRequest.request_merge!` flow [1](#0-0) [2](#0-1) .
- However, `User.find_or_create_author_from_github_commit` has no way to distinguish a trustworthy Shipit-generated trailer from an attacker-supplied one - it simply regex-matches `github_commit.commit.message` for the pattern and, on match, calls `find_or_create_by_login!(match_info[1])`, creating/fetching an arbitrary `Shipit::User` and returning it as the commit author [3](#0-2) .
- `Commit.from_github` calls this method directly and assigns the result to `author:` on the new commit record [4](#0-3) .
- `GithubSyncJob#append_commit` calls `stack.commits.create_from_github!(gh_commit)` for every new commit fetched from `stack.github_commits` (the GitHub API, first-parent history of the tracked branch), triggered from the push webhook handler's `stack.sync_github` call [5](#0-4) [6](#0-5) .
- The project's own test suite confirms this is exercised as documented behavior, not merely theoretical: a commit message of `"commit to trigger staging build\n\nMerge-Requested-By: walrus\n"` authored by a generic "Shipit" committer causes `commit.author` to equal `shipit_users(:walrus)` [7](#0-6) .

Why existing guards fail: webhook signature verification (`verify_signature`) only authenticates that the HTTP payload came from GitHub's configured webhook secret, and confirms the *event* is legitimate; it does not - and cannot - verify who authored the *text* of a git commit message. `GithubSyncJob` deliberately re-fetches commits from GitHub's API rather than trusting the webhook body, but the actual git commit message on GitHub is exactly what gets parsed - and git commit messages are fully attacker-controlled content for any commit the attacker can get merged/pushed onto the tracked branch. `Octokit::NotFound` handling only guards against non-existent GitHub logins, not against forged-but-real ones [3](#0-2) .

Attacker exploitation requires the ability to get a commit with the crafted trailer merged into the tracked branch. This is feasible in at least two ways: (1) an attacker with push access to a branch the stack tracks pushes a commit with the trailer in its message; (2) an attacker opens a PR whose title/description contains the trailer text, and a maintainer performs a default squash-merge that carries the PR title/body verbatim into the merge commit message. Case (2) means the *commit creation* action is still performed by a legitimate maintainer, but the *content* of the trailer is attacker-supplied.

### Impact Explanation
Successful exploitation misattributes `Commit#author` to an arbitrary existing `Shipit::User` chosen by the attacker, corrupting the audit trail Shipit shows for that commit (`author` badges in UI, `_author.html.erb` views) and any downstream logic keyed on commit/merge-request authorship. This is repeatable against any stack/repository the attacker has push access to, or any repository whose maintainers perform default squash-merges without editing the commit message. The blast radius is limited to identity/attribution spoofing within the affected stack; it does not by itself grant deploy authorization, execute code, or leak credentials, since the attacker still needs either push access to the tracked branch or a maintainer to actually perform the merge action.

### Likelihood Explanation
Exploiting via direct push requires the attacker to already have write access to a branch Shipit tracks, which is a meaningfully privileged position (not truly "unprivileged" from GitHub's perspective, even though they hold no Shipit credentials). Exploiting via squash-merge title/description requires a maintainer to perform a default squash merge without editing the resulting commit message, which is plausible but depends on repository merge configuration and maintainer habits and is not guaranteed. Attacker cost is low once the precondition is met (crafting the trailer text is trivial), and the technique is fully repeatable across any commit or repository meeting the precondition.

### Recommendation
Only honor the `Merge-Requested-By` trailer for commits that Shipit itself produced through the trusted `MergeRequest#merge!` path (e.g., by correlating via the associated `MergeRequest#merge_requested_by` record rather than re-parsing the raw commit message text in `User.find_or_create_author_from_github_commit`), and stop trusting arbitrary commit-message content as an identity assertion for commits ingested generically via `GithubSyncJob`.

### Proof of Concept
```ruby
test '.create_from_github does not let an arbitrary commit message forge authorship' do
  attacker_commit = resource(
    sha: 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef',
    author: { id: 999999, login: 'attacker' },
    committer: { id: 999999, login: 'attacker' },
    commit: {
      author: { name: 'attacker', email: 'attacker@example.com', date: Time.now },
      committer: { name: 'attacker', email: 'attacker@example.com', date: Time.now },
      message: "innocuous change\n\nMerge-Requested-By: walrus\n"
    }
  )

  commit = @stack.commits.create_from_github!(attacker_commit)

  # Broken binding today: commit.author == shipit_users(:walrus)
  # Expected binding: commit.author should reflect the actual committer/author
  # (or an Anonymous/attacker-linked user), NOT an arbitrary victim login
  # embedded in an unauthenticated commit message.
  refute_equal shipit_users(:walrus), commit.author
end
```
This mirrors the existing passing test at [7](#0-6) , which currently asserts the vulnerable behavior (`assert_equal shipit_users(:walrus), commit.author`) is by-design rather than an authenticated attribution.

    def self.find_or_create_author_from_github_commit(github_commit)
      if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
        begin
          return find_or_create_by_login!(match_info[1])
        rescue Octokit::NotFound
          # Corner case where the merge-requested-by user cannot be found (renamed/deleted).
          # In this case we carry on and search for the commit author
        end
      end
      find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

    def append_commit(gh_commit)
      stack.commits.create_from_github!(gh_commit)
    end
