### Title
Incorrect restoration of privilege/scope state on error path in oscript function-declaration validation - (File: `formula/validation.js`)

### Summary
`formula/validation.js`'s `parseFunctionDeclaration` saves and restores several validator-wide state variables (`complexity`, `count_ops`, `bStateVarAssignmentAllowed`, `bInFunction`, `locals`) around the validation of a nested function body, but the restoration only happens on the success path. On the error path the function returns immediately without restoring the saved state, leaving the "privilege"/scope flags (in particular `bStateVarAssignmentAllowed` and `bInFunction`) set as if execution were still inside the nested function body.

### Finding Description
`exports.validate` in `formula/validation.js` keeps closure-scoped flags that gate which oscript operations are legal at the current point of formula validation: `bStateVarAssignmentAllowed` (whether `var[...]=` state assignments are allowed) and `bInFunction` (whether `return value;`/certain constructs are allowed), plus `complexity`/`count_ops` counters and the `locals` symbol table.

`parseFunctionDeclaration` (`formula/validation.js:1350-1392`) elevates/changes these before recursing into the function body: [1](#0-0) 

then calls `evaluate(body, function (err) {...})`: [2](#0-1) 

The callback only restores `complexity`, `count_ops`, `bStateVarAssignmentAllowed`, `bInFunction` and `locals` to their saved values in the success branch. If `err` is truthy, it does `return cb(err)` immediately, skipping the restoration lines entirely — this mirrors the CVE class of "restoration of privilege" not being performed correctly when an error/exception path is taken during recursive evaluation.

This is the analogous "restore-on-error" defect to ALPINE-CVE-2018-16802 (Ghostscript failing to properly restore privilege state when an exception interrupts an operation), reframed in ocore's oscript static validator: instead of restoring the OS-level privilege state, ocore fails to restore the validator's own privilege-like flags (`bStateVarAssignmentAllowed`, `bInFunction`) on the error branch of a nested `evaluate` call inside `parseFunctionDeclaration`.

### Impact Explanation
`bStateVarAssignmentAllowed` and `bInFunction` are the gate that decides whether state-variable assignment statements and function-only constructs (like bare `return value;`) are permitted at a given point in an AA (Autonomous Agent) definition's oscript. If, due to the missing restore-on-error, these flags leak set to `true` into the surrounding scope after a function declaration's body fails validation with an error, subsequent sibling statements in the same `getters`/definition validation pass could be evaluated with elevated permissions they should not have (e.g., statements outside of any function being treated as if they are inside one, or state-var assignment being allowed where it should not be). Because this code path executes during `validateAADefinition` when an Autonomous Agent's oscript definition is registered on the DAG (an untrusted, attacker-controlled definition), a corrupted validator state could let an attacker craft an AA definition that is accepted with statements it should have rejected, or that different nodes disagree on due to state accumulated across function declarations. That can translate into node disagreement on AA definition validity, which the "Validate" section calls out as an in-scope high-impact analog (node disagreement on validity/stability).

### Likelihood Explanation
The trigger requires only that an attacker post an AA definition (unprivileged unit poster path) containing a function declaration whose body deliberately fails validation (easy to construct, e.g., use an unknown/invalid operator or an out-of-scope opcode inside a `$f = (...) => {...}` body) placed before other statements that rely on `bStateVarAssignmentAllowed`/`bInFunction` being `false`. This is a purely oscript/AA-definition-validation code path (`formula/validation.js`, reached via `aa_validation.js`'s `validateAADefinition` → `validateFormula`), so it is reachable by any AA author without special privileges.

### Recommendation
Wrap the restoration of `complexity`, `count_ops`, `bStateVarAssignmentAllowed`, `bInFunction`, and `locals` in a `finally`-style pattern that executes regardless of whether `evaluate(body, ...)` calls back with an error, e.g.:
```js
evaluate(body, function (err) {
    var funcProps = { complexity, count_args, count_ops };
    complexity = saved_complexity;
    count_ops = saved_count_ops;
    bStateVarAssignmentAllowed = saved_sva;
    bInFunction = saved_infunction;
    assignObject(locals, saved_locals);
    if (err)
        return cb(err);
    if (funcProps.complexity > constants.MAX_COMPLEXITY)
        return cb("function exceeds complexity: " + funcProps.complexity);
    if (funcProps.count_ops > constants.MAX_OPS)
        return cb("function exceeds max ops: " + funcProps.count_ops);
    cb(null, funcProps);
});
```
This guarantees the validator's scope/privilege state is always restored before control returns to the caller, independent of whether the nested evaluation succeeded or failed — closing the same class of "restore on exception" gap that ALPINE-CVE-2018-16802 describes.

Because `parseFunctionDeclaration`'s error branch (`formula/validation.js:1375-1377`) returns before restoring `bStateVarAssignmentAllowed`/`bInFunction`, the subsequent top-level statement is validated with the leaked (function-scope) flags still active, potentially being accepted when it should be rejected — or vice versa, depending on which flag combination is exploited — leading to differing acceptance behavior versus what the intended language grammar specifies.
