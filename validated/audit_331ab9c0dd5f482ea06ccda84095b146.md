### Title
Webhook signature verified against a different organization's secret than the repository/stack the event actually targets - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports hosting multiple GitHub organizations in a single instance, each with its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which organization's secret to validate the HMAC against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) [2](#0-1) . However, once the signature check passes, the event handler that actually acts on the payload (e.g. `PushHandler`) resolves the target `Stack`/`Repository` from a *different* field of the same untrusted JSON body — the repository's `full_name`, via `Repository.from_github_repo_name` (`owner/name` split) [3](#0-2)  — and never re-checks that this repository belongs to the organization whose secret was used for verification.

### Finding Description
`verify_signature` fetches a `GitHubApp` instance scoped to whatever organization login appears in `repository.owner.login` and validates `X-Hub-Signature` against that organization's `webhook_secret` [4](#0-3) [5](#0-4) . This only proves the request body was signed by *someone who knows that organization's secret* (e.g. a legitimate admin of a smaller/less-trusted org tracked by the same Shipit instance, per the multi-org config supported in `lib/shipit.rb`'s `github_app_config`/`github_organizations` [6](#0-5)  and documented in `config/secrets.development.shopify.yml`).

Once verification passes, `WebhooksController#create` dispatches the raw parsed body to every handler for the event, unmodified [7](#0-6) . For a `push` event, `PushHandler#process` looks up target stacks and triggers `stack.sync_github(expected_head_sha: params.after)` [8](#0-7) , where the underlying stack/repository resolution is driven by the repository's `full_name` (`owner/name`) via `Repository.from_github_repo_name` [3](#0-2) .

The binding that should hold is: `organization whose secret signed the request == organization owning the repository the handler acts on`. Nothing in `verify_signature` or in the handler pipeline enforces that `repository.owner.login` (used for signature selection) equals the owner segment embedded in `repository.full_name` (used for stack resolution) — they are two independent fields inside the same attacker-controlled JSON body. A party who legitimately knows one organization's `webhook_secret` (i.e., is an admin of one of the smaller organizations hosted on the same Shipit instance) can craft a raw POST body where `repository.owner.login`/`organization.login` names their own organization (so the correct, known secret validates the HMAC) while `repository.full_name` names a repository belonging to a different, victim organization also tracked by the same Shipit install. This is the "organization that authenticated versus the repository that is written" binding break.

### Impact Explanation
An attacker who only possesses one hosted organization's `webhook_secret` can forge `push`/`status`/`check_suite` events that are cryptographically valid (for their own org) but whose `repository.full_name` targets a stack owned by an unrelated organization on the same Shipit instance. This lets them trigger `GithubSyncJob`/status updates/CI-check refreshes against a repository they do not control, and — because merge/deploy readiness in Shipit is itself driven by synced statuses/check-runs (e.g. `MergeRequest#all_status_checks_passed?` consulting synced check-runs, and continuous-deployment flows) — this can be leveraged toward triggering an unauthorized sync, and potentially cascade into unauthorized deploys/merges for a repository outside the attacker's authorization scope. This matches the "cross-repository writes" / "unauthorized deploy" impact class called out in scope.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration in `lib/shipit.rb`/`config/secrets.*.yml`) and requires the attacker to be a legitimate webhook-secret holder for at least one of those organizations — i.e., an org admin for one tenant of a multi-tenant Shipit deployment, but not for the victim organization. This is a real but non-trivial trust boundary (cross-tenant on a shared Shipit instance) rather than a fully anonymous attack.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after signature verification, re-derive and cross-check the organization/owner used for secret selection against the owner segment of every repository referenced deeper in the payload (e.g., `repository.full_name`, `organization.login`) before dispatching to handlers, rejecting the event if they diverge. Alternatively, resolve the target `Stack`/`Repository` strictly from the same field that was used to select the signing secret.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret known to the attacker, e.g. an org admin) and `victim-org` (tracked stacks the attacker has no access to), per the multi-org `github:` config schema.
2. Craft a JSON payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` selects `attacker-org`'s `GitHubApp`, validates the HMAC successfully [4](#0-3) .
5. `PushHandler#process` resolves stacks from `victim-org/victim-repo` via `full_name` and enqueues `GithubSyncJob`/state changes for the victim's stack [8](#0-7) , despite the attacker never having proven any relationship to `victim-org`.

*Note:* I was not able to open `app/models/shipit/webhooks/handlers/handler.rb` (the base `Handler` class defining the `stacks` helper used by `PushHandler`) in this session to cite the exact `full_name`-based lookup line-for-line; the resolution path is inferred from `PushHandler#process` calling `stacks.not_archived.where(branch:)` combined with `Repository.from_github_repo_name`'s `owner/name` parsing. A Devin session with full repository access could confirm the exact `stacks` implementation to close this gap.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
