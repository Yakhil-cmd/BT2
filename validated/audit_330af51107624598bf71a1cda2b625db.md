### Title
Unvalidated swap venues can execute attacker code below the caller’s authorization and steal unrelated wallet tokens - (File: `contracts/swap-aggregator/src/execute/mod.rs`)

### Summary
The strategy router accepts every pool and token address from caller-controlled route XDR and invokes that address through a venue adapter without an allowlist. A malicious “pool” can therefore run contract code beneath an otherwise ordinary `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` authorization tree. [1](#0-0) [2](#0-1) 

### Finding Description
Controller strategy entrypoints pass user-supplied `swap` bytes to the configured aggregator after authorizing only the controller’s exact input-token transfer. [3](#0-2)  The aggregator decodes route-selected `assets`, treating entries as both token contracts and venue/pool contracts. [4](#0-3)  Each swap instruction obtains `pool`, `token_in`, and `token_out` directly from that registry and dispatches the selected venue adapter. [2](#0-1) 

For example, the Soroswap adapter invokes `get_reserves` and `swap` on the payload-selected `pool`. [5](#0-4) [6](#0-5)  During either call, malicious pool code can call an unrelated token’s `transfer(victim, attacker, amount)`; because the victim’s `require_auth` context remains on the call stack, Soroban records that transfer as a child invocation under the victim’s controller authorization. [7](#0-6)  Transaction simulation therefore produces an authorization tree containing the unrelated wallet-token transfer, and enforcing mode executes it when that generated tree is signed. [8](#0-7) 

The controller’s post-call accounting only verifies that the configured router did not overspend the listed input token and returned a positive listed output token. [9](#0-8)  Those checks do not restrict other token contracts called by route-selected pool code. [10](#0-9) 

### Impact Explanation
A victim using a maliciously crafted route can lose unrelated wallet tokens in addition to the collateral being swapped, causing direct theft of user funds. [8](#0-7)  The swap can still return a valid `token_out` amount and satisfy the account’s final risk checks, so neither the router’s measured output nor the controller’s solvency checks bounds the stolen amount. [9](#0-8) [11](#0-10) 

### Likelihood Explanation
Any user can submit a strategy route containing an attacker-deployed pool address because route assets are not allowlisted. [12](#0-11) [2](#0-1)  The attack requires the victim to sign the simulated authorization tree containing the extra token transfer, so exploitation depends on a malicious route/provider and inadequate wallet-side inspection. [8](#0-7)  The malicious venue can nevertheless satisfy the router’s measured spend/output requirements and make the outer strategy appear successful. [13](#0-12) 

### Recommendation
Maintain an on-chain allowlist of approved venue/pool contracts and reject strategy routes whose `idx_a` resolves to an unapproved pool. The allowlist must cover every venue adapter and liquidity operation that treats an `assets` entry as executable contract code. In addition, clients should decode simulated authorization trees and reject any child token authorization other than the expected exact input transfer, but client validation should be defense-in-depth rather than the protocol’s only control.

### Proof of Concept
1. The attacker deploys a contract exposing the pool ABI used by a selected venue, such as `get_reserves` and `swap` for a Soroswap hop.
2. The malicious `swap` implementation first returns enough output, or causes output to be supplied, to satisfy the router’s positive-output and exact-spend measurements; it also calls `wallet_token.transfer(victim, attacker, victim_balance)`.
3. The victim submits `controller.swap_collateral(victim, victim_account, current, amount, new, malicious_route)` or invokes `swap_aggregator.execute_strategy(victim, amount, malicious_route)` directly.
4. The controller authorizes only `current.transfer(controller, router, amount)`, but the malicious pool executes below the victim’s `caller.require_auth()` context. [14](#0-13) [7](#0-6) 
5. `simulateTransaction` records the malicious wallet-token transfer as a child of the victim’s authorization entry; signing that tree authorizes the theft.
6. The route then completes with positive measured `new` output, the account passes `strategy_finalize`, and the victim retains a valid swapped position while losing the unrelated wallet token. [11](#0-10)

    sender.require_auth();

    if total_in <= 0 {
        panic_with_error!(&env, Error::InvalidAmount);
    }

    let StrategyPayload {
        amounts,
        assets,
        ops,
    } = payload;
    let program = Program::decode(&env, &ops, assets.len(), amounts.len());

    let input_token = assets.get_unchecked(program.token_in);
    let output_token = assets.get_unchecked(program.token_out);
