### Title
Arbitrary PR labels are injected as unsanitized environment variables into git subprocess execution, enabling GIT_ASKPASS RCE - ([File: app/models/shipit/review_stack.rb])

### Summary
`Shipit::ReviewStack#env` merges every pull-request label name (upcased) as an environment variable with value `"true"` into the environment used for `git clone`/`checkout`/task execution, with no allow-list or denylist filtering. Because `Command#unbundled_env` merges this hash directly into the environment passed to `PTY.spawn`, an attacker who can apply a label such as `GIT_ASKPASS` to their own pull request can inject `git`-honored environment variables (e.g. `GIT_ASKPASS`, `GIT_SSH`, `GIT_SSH_COMMAND`) into the subprocess that runs against their repository's review stack, resulting in remote code execution on the deploy host.

### Finding Description
The broken binding is: **every key merged into `Command#unbundled_env` should originate only from a ref/spec an authorized user approved (EXECUTION_TRUST)**, but `ReviewStack#env` derives keys directly from PR label names, which require no code review or spec approval.

Path:
1. `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` verbatim onto `stack.pull_request.labels`, with no filtering of label content: [1](#0-0) 
2. `Shipit::ReviewStack#env` upcases each label name and merges it into the stack's environment hash with value `"true"`: [2](#0-1) 
3. `TaskCommands#env` merges `@stack.env` (which includes the ReviewStack labels) together with other task-derived variables: [3](#0-2) 
4. `TaskCommands#clone`/`#checkout` invoke `git(...)` using this environment for the actual `git clone`/`git checkout` operations: [4](#0-3) 
5. `Command#unbundled_env` merges `@env` (attacker-influenced) directly over `BASE_ENV`/`PATH`, with no key allow-list: [5](#0-4) 
6. `Command#start` passes this merged hash straight to `PTY.spawn`: [6](#0-5) 

Root cause: unlike `deploy_spec.machine_env`, which is sourced from the repo's `shipit.yml` and can be scoped, and unlike `EnvironmentVariables#permit`, which explicitly whitelists variable names before they're allowed into an environment (`lib/shipit/environment_variables.rb:13-18,35-44`), `ReviewStack#env` performs no allow-listing at all — any label name becomes an env var key. `EnvironmentVariables#permit` is never called on the stack/review-stack env merge path.

Attacker's exact action: open (or already have) a pull request against a repository with `review_stacks_enabled` and a provisioning behavior satisfied (`allow_all`, or `allow_with_label` satisfied via a different, legitimate label), causing a `Shipit::ReviewStack` to be created for that PR. Then label the PR `GIT_ASKPASS` (or `GIT_SSH`, `GIT_SSH_COMMAND`, etc.) via a normal GitHub `pull_request` `labeled` webhook, which GitHub delivers with a valid signature since it is a real, unmodified GitHub event. `LabelCapturingHandler` requires only that the stack exists and is not archived — it applies no additional authorization check on which labels get captured: [7](#0-6) 

Existing guards (`verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema on `LabelCapturingHandler`) validate webhook authenticity and payload shape, but do not restrict which label *names* are permitted to become environment variable keys, so they do not prevent this divergence.

### Impact Explanation
Once the deploy or task next runs `git clone`/`checkout` on that review stack, `git` will treat `GIT_ASKPASS=true` (or a path/command supplied via another dangerous variable name used as the label) as an executable to invoke during authentication, executing arbitrary code as the Shipit deploy-host process user. This is Critical: RCE on the deploy host via `Command`/`PTY.spawn`. The blast radius is scoped to review-stack-enabled repositories but is repeatable per pull request/per label change and does not require any Shipit credential, session, or API token.

### Likelihood Explanation
Requires `review_stacks_enabled` and a provisioning behavior that lets the attacker's own PR get a review stack (`allow_all`, or `allow_with_label` satisfied by a distinct, benign label). Given the stipulated attacker capability of labeling their own PR, the cost is a single GitHub label action plus waiting for/triggering a deploy or task on the review stack. No secrets are needed since the webhook is a legitimate, signed GitHub event.

### Recommendation
In `ReviewStack#env`, whitelist/deny-list label-derived environment variable names (e.g., reject or drop labels matching reserved/dangerous names like `GIT_ASKPASS`, `GIT_SSH`, `GIT_SSH_COMMAND`, `LD_PRELOAD`, `BASH_ENV`, `PATH`, etc., or use a strict allow-list similarly to `EnvironmentVariables#permit`) before merging label-derived keys into the environment reaching `Command#unbundled_env`.
