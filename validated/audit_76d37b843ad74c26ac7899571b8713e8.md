### Title
Signature verification authenticates the payload's `repository.owner.login`/`organization.login` but stack lookup trusts the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate a webhook against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (fallback `organization.login`). [1](#0-0) [2](#0-1) 
Yet every event handler determines the actual `Repository`/`Stack` to act on from a *different* payload field, `repository.full_name`, via `Handler#repository_name` and `Repository.from_github_repo_name`. [3](#0-2) [4](#0-3) 
Nothing cross-checks that the owner segment of `full_name` matches `owner.login`. In a multi-organization deployment (`Shipit.github(organization:)` selects per-org config/secret, as documented and tested for multi-app setups), this breaks the intended binding: "organization authenticated" == "repository/stack written". [5](#0-4) [6](#0-5) 

### Finding Description
`verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and then validates `X-Hub-Signature` against that org's `webhook_secret` over the raw body. [7](#0-6) 
This only proves the request was signed with the secret belonging to whatever organization the attacker put in `repository.owner.login` (or `organization.login`). It does **not** prove anything about which repository/stack is subsequently acted upon.

`create` then dispatches the same raw JSON to handlers (`PushHandler`, `StatusHandler`, etc.), which resolve the target `Stack`/`Repository` purely from `payload.dig('repository', 'full_name')`: [8](#0-7) [3](#0-2) [9](#0-8) 

For a single-org deployment this is harmless, since only one secret/app exists. But Shipit explicitly supports multiple GitHub organizations sharing one instance, each with its own `webhook_secret`, selected purely by the `organization` key derived from attacker-controlled JSON. [10](#0-9) 
An actor who legitimately controls (or can obtain webhook deliveries/secrets for) one onboarded organization "OrgA" can compute a valid HMAC for a forged raw body whose `repository.owner.login` is `"OrgA"` (so the app/secret lookup and signature check pass) while its `repository.full_name` is set to `"OrgB/some-repo"` — a completely different organization's repository also configured on the same Shipit instance. The signature check passes because it only validates that *some* known secret signed the bytes, tied only to the `owner.login`/`organization.login` field; it never validates that this matches the `full_name` field the rest of the pipeline trusts to select the target `Stack`.

This is exactly the deployment-trust binding break called out by the report's bug class ("the protocol assumes fields are pegged/consistent but nothing enforces it"): here, "organization authenticated" != "repository actually written."

### Impact Explanation
This allows cross-repository/cross-organization webhook forgery: an attacker with legitimate access to one onboarded org's webhook secret can inject fabricated `push`, `status`, or `check_suite` events against a **different** organization's stacks, e.g.:
- `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)` for arbitrary stacks under the victim org, forcing Shipit's view of HEAD to an attacker-chosen SHA. [9](#0-8) 
- `StatusHandler` creates arbitrary commit statuses on victim commits via `commit.create_status_from_github!`, which can influence deploy-gating logic that consumes commit statuses. [11](#0-10) 

This is a cross-repository write achieved without ever authenticating against the victim organization's own webhook secret — matching the "cross-repository writes" / "unauthorized deploy" critical impact bar, since manipulating synced HEAD SHA and commit statuses can feed directly into deploy/merge decisioning for a repository/org the attacker was never authorized against.

### Likelihood Explanation
Requires: (1) the target Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration), and (2) the attacker to know/obtain a valid `webhook_secret` for at least one onboarded organization (e.g. their own org, if they have admin rights over its GitHub App settings, or if that org's secret is weak/leaked). Both conditions are plausible in real multi-tenant Shipit deployments and require no privileged access to the *victim* organization or to Shipit itself — only unprivileged control of a peer organization already onboarded to the same instance.

### Recommendation
In `WebhooksController#verify_signature`/`create`, require the organization used for signature verification (`repository_owner`) to match the resolved repository owner (`repository.full_name`'s owner segment) before dispatching to handlers, e.g. re-derive `repository_owner` from `full_name` (or validate `full_name.split('/').first == repository_owner`), or better, look up the target `Repository` first and use its stored, previously-validated `owner`/webhook configuration to select the verification secret, rather than trusting an independent, unauthenticated field of the same payload.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md`'s multi-app configuration). [12](#0-11) 
2. Attacker (an admin of `OrgA`'s GitHub App / who knows `OrgA`'s `webhook_secret`) crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against `OrgA`'s secret. [7](#0-6) 
5. `PushHandler` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s stack, despite the request never being authenticated with `OrgB`'s webhook secret. [9](#0-8) [4](#0-3)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
