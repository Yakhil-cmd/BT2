### Title
Unrecovered synchronous throws inside `dryRunPrimaryAATrigger`/`handleTrigger` let a routine race with concurrent stabilization crash the whole node - ([File: aa_composer.js])

### Summary
The IoTeX report fixes a case where a speculative/draft computation (the mint goroutine) races with a concurrent state-mutating commit path, hits a `db.ErrNotExist`-style hard error, and — because the panic isn't recovered — brings down the whole process. `ocore` has a structurally identical hazard: for every incoming payment unit addressed to an AA, `network.js`'s `ifOk` handler (when `conf.bDryRunNewTriggers` is set) speculatively evaluates the AA trigger via `aa_composer.dryRunPrimaryAATrigger()` [1](#0-0)  concurrently with the real, mutex-protected commit/stabilization pipeline (`writer.saveJoint`, `main_chain.stabilizeMci`/`advanceMcStability`, `aa_composer.handleAATriggers`) that mutates the very same shared in-memory caches (`storage.assocUnstableUnits`, `assocStableUnits`, `assocUnstableMessages`, `assocBestChildren`). Neither `dryRunPrimaryAATrigger` nor `estimatePrimaryAATrigger` take the `"write"` or `"handleJoint"` mutex that the real commit/stabilization path uses, so the two can interleave freely.

### Finding Description
`dryRunPrimaryAATrigger` is explicitly documented as a "let it crash now" speculative path [2](#0-1)  and is invoked automatically for any submitted or relayed unit that pays an AA address, without holding the write/stabilization locks [1](#0-0) . Its execution reads and internally asserts consistency of shared caches through `handleTrigger`, `storage.readUnitProps`, `storage.readJoint`, and asset/balance lookups [3](#0-2) [4](#0-3) .

Concurrently, the real commit path can be advancing main-chain stability (`stabilizeMci`, `determineIfStableInLaterUnitsAndUpdateStableMcFlag`) [5](#0-4) [6](#0-5) , or running `writer.saveJoint`, which mutates `assocUnstableMessages`, resets memory on rollback, and runs AA triggers/`forgetUnit` for rolled-back responses [7](#0-6) [8](#0-7) . These caches are guarded by strict self-consistency assertions that `throw Error(...)` synchronously the moment the in-memory state and the DB state diverge, e.g.:
- `storage.readUnitProps`: `throw Error("no unstable props of "+unit)` when a unit expected to be unstable is missing from `assocUnstableUnits` [9](#0-8) .
- `aa_composer.handlePrimaryAATrigger`: `throw Error(\`handlePrimaryAATrigger: unit ${unit} not found in cache\`)` [10](#0-9) .
- `estimatePrimaryAATrigger`: `throw Error("AA not found: " + address)` [11](#0-10) .

None of these throw sites, nor the calling chain in `dryRunPrimaryAATrigger`/`estimatePrimaryAATrigger`, is wrapped in a try/catch or promise-rejection guard analogous to the `defer`/`recover` the IoTeX fix adds around the mint goroutine. A synchronous throw raised deep in this callback tree becomes an uncaught exception (or unhandled promise rejection given the `async` handler at `ifOk`). `ocore` treats any such uncaught exception as fatal by design: the top-level handler explicitly re-throws to terminate the process — "crash the process to avoid ending up in an inconsistent state" [12](#0-11) .

### Impact Explanation
Any unprivileged unit poster can trigger this by simply sending a valid payment to an existing AA address — this is normal, permissionless AA-payment traffic, not privileged or malicious-peer behavior. If the timing lines up with ongoing stabilization/AA-trigger processing on that node (which happens continuously on any active full node/hub), the speculative dry run can read a torn/mid-mutation view of `assocUnstableUnits`/`assocStableUnits`/`assocUnstableMessages`, hit one of the hard consistency-assertion throws above, and crash the entire `ocore` process — a remote, repeatable denial of service against any node with `conf.bDryRunNewTriggers` enabled (this is precisely the "network unable to confirm new units" outcome the scope calls out, since a poster can keep resending triggers to force repeated crashes/restarts).

### Likelihood Explanation
The trigger condition (payment to an existing AA address) requires no special privilege and is part of ordinary protocol usage; `count_primary_aa_triggers` on the submitted unit is exactly what gates the dry-run call [1](#0-0) . The race window is real because `dryRunPrimaryAATrigger`/`estimatePrimaryAATrigger` never acquire the `"write"`/`"handleJoint"` mutexes that serialize the mutation of the shared caches, so any legitimately busy node (actively stabilizing MCIs or writing joints) is continuously exposed to the window. However, without live reproduction I cannot confirm the exact minimal sequence of concurrent operations needed to force one of the specific `throw` sites to fire versus the code paths tolerating the race safely in practice (e.g., some paths may re-fetch from DB and self-heal). This is a plausible, structurally supported race analogous to the IoTeX bug class, but its concrete exploitability window size is unverified against the current version of the index.

### Recommendation
Wrap the entire speculative/estimation call trees (`dryRunPrimaryAATrigger`, `estimatePrimaryAATrigger`, and the `handleTrigger` invocation they drive) in error containment that converts any thrown/rejected error into a normal callback error instead of letting it propagate to the process-level `uncaughtException` handler — mirroring the IoTeX fix's `defer`/`recover` around the mint goroutine, while explicitly leaving the real commit/stabilization path (`writer.saveJoint`, `stabilizeMci`, `handlePrimaryAATrigger`) as a hard-abort fatal path since that one guards actual ledger consistency. Additionally, consider having the speculative dry-run path take a shared read lock (or otherwise synchronize) against the `"write"`/`"handleJoint"` mutexes so it never observes caches mid-mutation, removing the race at its root rather than only containing the resulting crash.

### Proof of Concept
Conceptual (not executed against a live node):
1. Deploy/target an existing AA address `A`.
2. Continuously post/relay payment units to `A` from an unprivileged wallet while the node is under load (multiple units stabilizing, causing frequent `stabilizeMci`/`saveJoint` cache mutations to `assocUnstableUnits`/`assocUnstableMessages`/`assocStableUnits`).
3. Each qualifying unit triggers `dryRunPrimaryAATrigger` concurrently and without mutex coordination against the real stabilization/write path [1](#0-0) .
4. Given enough repetitions/timing attempts, the dry run's reads of the shared caches race with concurrent mutation by the write/stabilization path, hitting a `throw Error("no unstable props of "+unit)` or `"unit not found in cache"` assertion [9](#0-8) [10](#0-9) , which is uncaught and crashes the node process via the global `uncaughtException` re-throw [12](#0-11) .

Note: I was not able to execute this scenario or step through the runtime to confirm the exact race window materializes in practice; this PoC outline is derived purely from static code-path analysis of the cited files.

// marks the MCI stable, executes triggers, and updates tps fees
async function stabilizeMci(mci) {
	const conn = await db.takeConnectionFromPool();
	await conn.query("BEGIN");
	const batch = kvstore.batch();
	const count_aa_triggers = await markMcIndexStable(conn, batch, mci);
	await util.promisify(batch.write.bind(batch))({ sync: true });
	await conn.query("COMMIT");
	conn.release();
	if (count_aa_triggers > 0) {
		console.log(`executing ${count_aa_triggers} AA triggers after stabilizing MCI ${mci}`);
		// every trigger takes its own db connection
		const aa_composer = require("./aa_composer.js");
		await aa_composer.handleAATriggers();
	}
	if (mci >= constants.v4UpgradeMci) {
		console.log(`updating tps fees after stabilizing MCI ${mci}`);
		// get a new connection to write tps fees
		const conn = await db.takeConnectionFromPool();
		await conn.query("BEGIN");
		await storage.updateTpsFees(conn, [mci]);
		await conn.query("COMMIT");
		conn.release();
	}
}
