### Title
Webhook `repository.owner.login` used for signature-verification selection is never checked against `repository.full_name` used by handlers, allowing an unsigned/mis-keyed webhook to act on an arbitrary repository's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController` selects which GitHub App config (and therefore which HMAC secret) to verify a webhook against using `repository.owner.login` (or `organization.login`) from the untrusted JSON body, but every event handler that actually mutates state resolves the target `Stack`/`Repository` using a *different* field from the same body: `repository.full_name`. Nothing ties these two fields together, so the "organization whose secret authenticated the request" is not provably the "organization whose repository is written to" — exactly the class of binding break called out in the prompt (an org authenticated vs. a repo written).

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
```
and
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`repository_owner` is fully attacker-controlled JSON content — it is read from the *unverified* request body before the signature check has even succeeded. The app config (and thus the HMAC secret used to verify) is picked per-organization: `Shipit.github(organization:)` looks up `github_app_config(organization)` keyed by whatever organization name is present in the payload. [3](#0-2) 

Crucially, `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization: [4](#0-3) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```

Meanwhile every handler that performs the actual mutation resolves the target repository/stack from a completely different, unchecked field: `repository.full_name`: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process` uses this to enumerate stacks and call `stack.sync_github(expected_head_sha: params.after)`: [6](#0-5) 

The pull_request handlers similarly resolve the acted-upon `Repository`/`Stack` from `params.repository.full_name` independently of whatever `repository.owner.login` was used to pick the verifying app config, e.g. `OpenedHandler#repository`: [7](#0-6) 

**The binding that should hold:** `organization(used to select the verifying webhook_secret) == owner(repository.full_name acted upon by the handler)`. **What actually holds:** the controller trusts whatever `repository.owner.login`/`organization.login` value is present to pick a config, and if that particular organization happens to have no `webhook_secret` configured (documented as *optional* in `docs/setup.md`, "Webhook secret (optional)"), verification unconditionally succeeds — regardless of what `repository.full_name` says. The handler then acts on `repository.full_name`, which can name a completely different (and fully secured) organization/repository present in Shipit's own database, because `Repository.from_github_repo_name` is a pure DB lookup with no cross-check against `repository_owner`.

### Impact Explanation
An attacker who can identify (by observation of Shipit's public UI/stack list, which exposes `repo_owner`/`repo_name` via the stacks API and web UI) that at least one onboarded organization has no `webhook_secret` configured can send a completely unsigned POST to the public `/webhooks` endpoint with:
- `organization.login` (or `repository.owner.login`) set to that unsecured org, and
- `repository.full_name` set to `victim-org/victim-repo` (any other onboarded, secured repository), and
- `X-Github-Event: push`.

Because `verify_webhook_signature` short-circuits to `true` for the unsecured org, `verify_signature` passes, and `PushHandler` then resolves stacks for `victim-org/victim-repo` and calls `stack.sync_github(expected_head_sha: <attacker-chosen sha>)`. This lets an unauthenticated network attacker force Shipit to treat an attacker-chosen commit SHA as the expected head for another organization's stack, corrupting Shipit's view of what commit is at the tip of the branch and potentially triggering syncs/deploy-eligibility computations against a SHA the attacker controls even though they have no access to that org's repository or GitHub App. Depending on continuous-delivery configuration downstream, this can influence which commit is considered "expected"/deployable for a stack the attacker does not own, which is a cross-repository/cross-organization write and can lead toward an unauthorized deploy trigger for a repository the attacker has no legitimate access to — matching the "Critical: cross-repository writes / unauthorized deploy" impact bucket.

### Likelihood Explanation
Likelihood is not trivial to fully prove without runtime access, but the code path is unambiguous: `verify_signature` never checks that `repository_owner` corresponds to the organization implied by `repository.full_name`, and `verify_webhook_signature` explicitly documents/implements "no secret configured ⇒ always verified" as intended behavior (`webhook_secret` is called out as *optional* in the setup docs). Any multi-tenant Shipit deployment (multiple GitHub orgs configured under `secrets.github`) that has even one org without a webhook secret configured (a supported, documented configuration) is exposed. I could not fully verify from the index how far downstream `sync_github`'s effect on `deployable?`/continuous delivery propagates (files `app/models/shipit/stack.rb` and `commit.rb` show relevant methods but I was unable to read their full bodies in this pass), so the exact severity ceiling (informational commit-sync corruption vs. a full unauthorized deploy) is not fully confirmed from static reading alone.

### Recommendation
In `WebhooksController#verify_signature`, after establishing which organization's secret verified the signature, require that every handler invoked for that request only act on repositories whose owner matches the verified organization — i.e., validate `params.dig('repository', 'owner', 'login') == params.dig('repository', 'full_name').split('/').first` before dispatch, and additionally reject/require a non-blank `webhook_secret` for any organization configured in `secrets.github` (treat a missing secret as a hard misconfiguration rather than "auto-verified"), so that the identity used to authenticate a webhook is provably the same identity whose repository is subsequently mutated.

### Proof of Concept
Conceptual (not run, since this requires a live multi-org Shipit deployment with one org lacking `webhook_secret`, which cannot be exercised via static code reading):

```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "unsecured-org" }
  },
  "organization": { "login": "unsecured-org" }
}
```
Because `Shipit.github(organization: "unsecured-org")` resolves to a config with a blank `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally, `verify_signature` passes, and `Shipit::Webhooks::Handlers::PushHandler` then executes `Repository.from_github_repo_name("victim-org/victim-repo").stacks... .sync_github(expected_head_sha: "<attacker-chosen-sha>")`, acting on the victim organization's stack despite the attacker never possessing any credential for `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
