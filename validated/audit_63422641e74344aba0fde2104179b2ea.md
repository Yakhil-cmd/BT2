### Title
Tokens transferred directly to the `LiquidityPool` are permanently locked — no sweep or rescue path exists - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The bug class is "contract can receive tokens but has no way to send out unbooked funds." XOXNO Lending's `LiquidityPool` holds all user collateral and liquidity in its own SAC balance, and any address can push tokens to it via a direct `token.transfer`. The pool's cash book is only mutated through controller-called entrypoints, none of which can pay out more than booked `cash`, and no skim/rescue entrypoint exists on either the pool or the controller. Donated or accidentally sent tokens become permanently untouchable surplus.

### Finding Description
Every token that exits the pool is bound to a booked liability:

- `withdraw`, `borrow`, `claim_revenue`, `create_strategy` debit `cash` and transfer out exactly the booked amount.
- `repay` and `recapitalize` refund only the unapplied portion of a *measured inbound transfer made inside the same call* — `recapitalize` refunds `amount - min(amount, backing_shortfall)` out of funds the controller prefunded moments earlier (`contracts/controller/src/markets.rs:154-163` measures the delta of the new transfer, not the pre-existing balance).
- `flash_loan` reconciles the balance with strict equality, so pre-existing surplus cannot be extracted there either.

The protocol itself acknowledges this shape: `docs/explanation/threat-model.md` states "Direct donations do not rewrite those books," and `tests/test-harness/tests/pool_money_flow_audit.rs:86-96` pins that a direct `token.transfer` to the pool sits outside every market's `cash` — the token balance permanently exceeds tracked cash by the donated amount. Neither the pool ABI (`supply`, `borrow`, `withdraw`, `repay`, `net_settle`, `seize_positions`, `claim_revenue`, `recapitalize`, `flash_loan`, `create_strategy`, `upgrade`) nor any controller entrypoint exposes a sweep of untracked balance.

### Impact Explanation
Any tokens sent directly to the pool (or left in the controller outside a measured operation) are permanently frozen: no unprivileged caller and no privileged path can recover them, and they benefit no book. This matches the original report's "funds stuck forever" impact class (permanent freezing of funds). Additionally, venue rewards pushed to the pool for Aquarius LP collateral (per `threat-model.md`, claimable by any caller and pushed into the pool as unbooked donations) accrue to nobody — permanently stranded yield.

### Likelihood Explanation
Medium-low but nonzero: any user who transfers tokens to the pool address believing it deposits, mistaken contract-address recipients, or externally pushed LP rewards all create irreversible surplus. No privileged action or market condition is required for the loss; only a single errant transfer. Severity tracks the original's Medium: real loss is user-error driven, with the provable strand being the missing rescue path.

### Recommendation
Add a bounded rescue: a controller entrypoint that transfers `token.balance(pool) - sum(cash across the asset's markets)` to a configured accumulator, or route untracked surplus into revenue shares via `seize_positions`-style credit. Alternatively document and enforce that `cash == balance` is an invariant monitored off-chain.

### Proof of Concept
1. Any address calls `token.transfer(user, pool, X)` on a listed SAC — succeeds unconditionally.
2. `pool.get_reserves(hub_asset)` / `get_sync_data` still show unchanged `cash`; `token.balance(pool) = cash + X` (pinned by `pool_money_flow_audit.rs:86-96` and `views.rs:210-223`).
3. Iterate every pool and controller entrypoint: `withdraw`/`borrow`/`claim_revenue` are capped by booked `cash`; `recapitalize(payer, key, amt)` refunds only `amt - applied` from the caller's own prefunded transfer (`recapitalize.rs:44-58`); `repay` refunds only the overpayment of that call. No argument recovers the prior `X`.
4. `X` remains in `token.balance(pool)` forever — confirmed there is no `skim`/`sweep`/`rescue` function anywhere in `contracts/pool/src` or `contracts/controller/src`.

Caveat: the threat model frames donations as accepted behavior ("belongs to no market's cash book"); whether auditors score this Medium or as a documented design trade-off depends on judging "user can irreversibly lose funds to the contract" as a defect regardless of intent, same as the source finding.
