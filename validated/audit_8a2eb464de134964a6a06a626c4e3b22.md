### Title
Cross-tenant Status write via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
Every other webhook handler (`OpenedHandler`, `LabeledHandler`, `ClosedHandler`, `ReopenedHandler`, etc.) resolves the target repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` (or the equivalent `Handler#stacks` helper) before acting, scoping all writes to stacks that belong to the repository named in the payload. `StatusHandler#process`, however, queries `Commit.where(sha: params.sha)` globally, with no repository/stack scoping at all, so any webhook signed for the attacker's own GitHub org/repo can create a `Status` on a commit belonging to a completely different tenant's `Stack`, as long as the sha matches.

### Finding Description
The claimed uniform binding is: `Handler#stacks` scoping (`Repository.from_github_repo_name(repository_name).stacks`) == the DB scope actually used by every `process` method that touches persisted stack data.

- `Handler#stacks` [1](#0-0)  resolves `Repository.from_github_repo_name(repository_name)` from `payload.dig('repository', 'full_name')` and scopes to that repository's stacks.
- `OpenedHandler` (representative of the sibling handlers) resolves `repository` the same way and scopes its `ReviewStackAdapter` to `repository.review_stacks` [2](#0-1) .
- `StatusHandler#process` breaks this binding: it never calls `stacks`, never resolves `repository`, and instead runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . `Commit` is an unscoped `ActiveRecord` model spanning every stack of every repository/tenant [4](#0-3) .

The controller-level `verify_signature` only proves the webhook was signed for the org identified by `repository_owner` (from the payload's own `repository.owner.login`), using that org's GitHub App secret [5](#0-4) . It never checks that the `sha` in the payload actually belongs to a commit under that same repository. An attacker who owns/controls a GitHub repository (and thus its own valid webhook signature) can send a `status` event where `sha` is copied from a commit that exists in a different tenant's `Stack` (e.g., a sha the attacker learned from a public commit reference, mirrored repo, or fork lineage). Because `Commit.where(sha:)` is global, `create_status_from_github!` will locate and mutate that foreign commit's status via `add_status`, which further triggers `Hook.emit(:commit_status, ...)`, `Hook.emit(:deployable_status, ...)`, and `stack.schedule_merges` on the victim's stack [6](#0-5) , potentially flipping a foreign commit's CI status to "success" and triggering merge/deploy scheduling for a stack the attacker never authenticated against.

### Impact Explanation
The attacker can write a `Status` row (and thereby flip the computed `state`/`deployable?` of a commit) belonging to another tenant's `Stack`, purely by sending a signed webhook for their own repository with a sha that collides with a foreign commit. Because `deployable?` and `schedule_continuous_delivery` depend on status state, this can let an attacker force `success` status on a victim commit they don't control, contributing to unauthorized merges/deploys on that victim's stack — this matches "a payload for one repository mutating another's stack, commit, task or team" (Critical). It's repeatable against any sha the attacker can predict or observe (e.g., shared/forked repos, or bots publishing commit shas), across all tenants sharing the Shipit instance.

### Likelihood Explanation
Preconditions: the attacker needs a repository whose webhooks are configured/signable by them (they legitimately own it and get a real GitHub App/webhook secret for their own org from Shipit — this is normal for any onboarded repository) and knowledge of a sha that also exists as a `Commit` row for a foreign `Stack`. Sha collision/knowledge is realistic in mirrored/forked/monorepo setups or when shas are publicly visible (e.g. shared upstream repo forked into multiple Shipit-tracked stacks, or CI logs). No Shipit session, API token, or extra secrets are required beyond the attacker's own repository's legitimate webhook signature. This is directly reachable via `POST /webhooks` with a standard `status` event.

### Recommendation
Scope `StatusHandler#process` the same way as the sibling handlers: resolve `stacks` (or `repository`) from `params.repository.full_name` and restrict the commit lookup to `stacks.commits.where(sha: params.sha)` instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, not to be placed under out-of-scope `test/**` for delivery but described here for validation purposes):

1. Create two `Stack` records for two different repositories (`repo-a/repo-a`, `repo-b/repo-b`), each with a `Commit` sharing the same `sha` value (e.g. `"deadbeef"`).
2. Build a `status` webhook payload with `repository.full_name = "repo-a/repo-a"` and `sha: "deadbeef"`.
3. Assert the binding is violated:
   - `Shipit::Webhooks::Handlers::Handler.any_instance.expects(:stacks).never`
   - Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
   - Assert a `Status` was created on the `repo-b` commit (`commit_b.statuses.reload.count == 1`) even though the payload's `repository.full_name` was `repo-a/repo-a`.
4. Contrast with `OpenedHandler`: repeat with a `pull_request` `opened` payload for `repo-a` and confirm `repository` is resolved and no cross-repo write to `repo-b` occurs, demonstrating the asymmetry between `StatusHandler` and its siblings.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
