### Title
Cross-repository sha collision in `StatusHandler#process` forges CI status and bypasses `Commit#deployable?`, triggering unauthorized deploys - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` solely by `sha`, with no check that the webhook's `repository.full_name` matches the commit's owning stack/repository, unlike every other handler (`PushHandler`, `CheckSuiteHandler`) which scope through `stacks` derived from `Repository.from_github_repo_name`. Any commit sha collision across repositories (most practically via forked/shared git history) lets a `status` webhook signed for repository A write a `success` `Status` onto a commit that actually belongs to stack B, flipping `Commit#status`/`deployable?` for B without any `release_statuses` entry being created.

### Finding Description
Broken binding: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` should hold for every `Status` created from a webhook, but it is never checked.

Path: `WebhooksController#create` (after `verify_signature`, which is scoped per-organization via `Shipit.github(organization: repository_owner)` and `GitHubApp#verify_webhook_signature`) dispatches to `StatusHandler.call(params)`. `StatusHandler#process` does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
This ignores `payload.dig('repository', 'full_name')` entirely, contrary to `Handler#stacks`, which every sibling handler uses to scope operations to the repository that actually sent the webhook [2](#0-1) .

`create_status_from_github!` then creates a `Status` bound to the *found commit's own* `stack_id` (not the sending repository's stack) via `add_status`/`statuses.replicate_from_github!(stack_id, github_status)` [5](#0-4) . This mutates `Commit#status` for stack B even though the webhook was authenticated only for repository A's organization.

`Commit#deployable?` derives purely from this CI `status`/`success?`/`blocked?`, independent of `release_statuses`:
```
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [6](#0-5) 
`Commit#create_release_status!`, which writes the separate, gated `release_statuses` table, is never invoked by this path and remains untouched: `return unless stack.release_status?` guards that separate mechanism [7](#0-6) , confirming the release/approval gate itself is not bypassed — only the CI gate is.

`Stack#trigger_continuous_delivery` selects `next_commit_to_deploy` and gates only on `should_resume_continuous_delivery?`/`should_delay_continuous_delivery?`, both of which check `deployable?`, `deployment_checks_passed?`, `checks?`, `recently_pushed?`, `deploy_failed?` — none of which reference `release_status?`/`release_statuses`: [8](#0-7) [9](#0-8) 
So a forged CI `success` status is sufficient, by itself, to make `next_commit_to_deploy` return the forged commit and `trigger_continuous_delivery` call `trigger_deploy`, running the deploy task.

Why guards fail: `verify_signature` authenticates that the request came from GitHub for a known *organization* (via `Shipit.github(organization: repository_owner)` / `GitHubApp#verify_webhook_signature`), not that the specific `repository.full_name` in the payload matches the commit being mutated. Within an organization where the GitHub App is installed org-wide (a common, documented installation mode), any repository under that org yields validly-signed webhooks; `StatusHandler` then trusts `sha` alone to pick the target commit across *all* stacks in the database, not just the sender's repository's stacks.

### Impact Explanation
A `Status` record is written for stack B's commit without any interaction with, or authorization from, repository B's actual CI or maintainers — a payload legitimately originating from repository A mutates repository B's stack/commit state. Because `Commit#deployable?` and `Stack#next_commit_to_deploy`/`trigger_continuous_delivery` depend solely on this forged CI status (independent of the separate `release_status?` gate), this can trigger an unauthorized deploy task (running real deploy steps/commands) on stack B. This matches the Critical category: "a payload for one repository mutating another's stack, commit... or an unauthorized deploy." Repeatable against any commit sha the attacker can reproduce/collide with, for every organization where the GitHub App is installed across multiple repositories.

### Likelihood Explanation
Preconditions: the target Shipit deployment must have a GitHub App/webhook secret configured for an organization that hosts more than one repository tracked by Shipit (or a fork relationship producing shared commit shas), and the attacker needs the ability to push/commit and trigger a `status` event on *some* repository within that same organization (e.g., a low-privilege contributor to an unrelated repo, or a forked repo sharing initial history with the target). Practical sha collision is easiest via forks that share git history (identical content+parent hashes), which is a realistic, attacker-controllable scenario, not a hash-collision attack. Attacker cost is a single push/status update on a repo they can write to; no secrets, sessions, or tokens are required beyond what GitHub itself provides by legitimately signing the webhook for their own action. This is repeatable per stack/commit sha match.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the sending repository, mirroring `PushHandler`/`CheckSuiteHandler`, e.g. restrict to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a `Status` can only be created for commits belonging to the stack(s) associated with `payload.dig('repository', 'full_name')`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or extending `commits_test.rb`):
1. Create `stack_a` (repository `owner/repo-a`) and `stack_b` (repository `owner/repo-b`), with `stack_b.cached_deploy_spec` enabling `release_status?` (`config('status','context')` set) — assert `stack_b.release_status?` is `true`.
2. Create `commit_b` under `stack_b` with a known `sha` (e.g., `"deadbeefcafe"`), and assert baseline: `refute commit_b.deployable?` and `assert_predicate commit_b.last_release_status, :unknown?` (no `release_statuses` row exists: `assert_equal 0, commit_b.release_statuses.count`).
3. Build a webhook payload for repository `owner/repo-a` (different repo) with `sha: commit_b.sha, state: 'success', context: 'ci/travis'`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing HTTP layer, as the signature check is out of scope for this model-level proof).
5. Assert the equality that should hold but doesn't: `refute_equal payload.dig('repository','full_name'), commit_b.stack.repository.full_name` while asserting `commit_b.reload.deployable?` is now `true` (`assert_predicate commit_b, :deployable?`) — proving the CI gate flipped due to a cross-repository payload.
6. Assert the release gate is untouched: `assert_equal 0, commit_b.release_statuses.count` and `assert_predicate commit_b.last_release_status, :unknown?`.
7. Optionally assert `stack_b.next_commit_to_deploy == commit_b` to demonstrate the deploy-selection impact.
