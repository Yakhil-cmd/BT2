### Title
Webhook signature verification binds to the payload's `repository.owner.login`, not to the entity actually mutated by the handler, allowing cross-repository status/CI spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature using only `repository.owner.login` (or `organization.login`) from the *same untrusted payload* being verified, then hands the entire payload to a handler keyed on unrelated fields (a commit `sha` or a `repository.full_name`) that is not required to match the owner used for signature verification.

### Finding Description
`verify_signature` computes the signing organization from the payload itself: [1](#0-0) [2](#0-1) 

This only proves that the payload was signed with the secret belonging to whatever organization is *named* in `repository.owner.login`/`organization.login` in that same payload — it does not bind the signature to any specific repository being acted upon. The `StatusHandler`, which processes GitHub `status` events, then acts purely on the commit `sha` field, with no scoping to the repository/organization that produced the valid signature: [3](#0-2) 

`Commit.where(sha: params.sha)` is a global, unscoped lookup across every stack/repository tracked by the Shipit instance. Since Git SHAs are public/knowable (visible in Shipit UI, GitHub, PRs, etc.), an attacker who controls a GitHub organization/repository that is *also* connected to the same Shipit instance (and therefore knows or can trigger delivery of their own org's legitimate `webhook_secret`) can craft a `status` webhook payload where:
- `repository.owner.login` = attacker's own org (used only to pick the secret for signature verification), and
- `sha` = the SHA of a commit belonging to a completely different stack/repository owned by a different organization.

The signature check in `GitHubApp#verify_webhook_signature` only verifies the HMAC over the raw body using the attacker's own secret — it never cross-checks that `repository.owner.login` matches the repository whose commit is being updated: [4](#0-3) 

This breaks the intended binding: *organization authenticated (via HMAC secret) == repository/commit written*. `Commit#create_status_from_github!` → `add_status` then updates the commit's aggregate `status`, which can flip a commit from pending/unknown to `success`: [5](#0-4) [6](#0-5) 

That aggregate status directly feeds `deployable?` and `schedule_continuous_delivery`, which gate whether a commit can be deployed or auto-deployed via continuous delivery: [7](#0-6) [8](#0-7) 

For comparison, `PushHandler`/`CheckSuiteHandler` correctly scope to the requesting repository via `stacks` (`Repository.from_github_repo_name(repository.full_name)`), so this issue is specific to `StatusHandler`'s repository-agnostic `Commit.where(sha:)` lookup combined with the payload-derived (self-referential) signature verification target.

### Impact Explanation
An attacker with control of any GitHub organization/repository onboarded to the same Shipit instance (i.e., knowledge of that org's own legitimate webhook secret, which the app owner controls and can trigger deliveries for) can forge `status` events that mark arbitrary commits belonging to *other, unrelated stacks/repositories* as CI-`success`. Because `deployable?` and continuous delivery scheduling rely on this spoofed status, this can enable an unauthorized deploy (bypassing `ci.require` checks) on a victim stack that the attacker has no legitimate access to — satisfying the "unauthorized deploy" / cross-repository-writes impact bar.

### Likelihood Explanation
Requires the attacker to operate their own GitHub App/organization that is legitimately registered with the same Shipit instance (a "low-trust" onboarded org), plus knowledge of a target commit's SHA (routinely public). No compromise of the victim organization's secret, no Shipit session, and no API token are needed — only the ability to send an HTTP POST to `/webhooks` with a validly-signed-but-mismatched-repository payload.

### Recommendation
In `StatusHandler#process` (and any other handler operating on cross-stack-searchable identifiers), require that the commit's `stack.repository` matches the `repository.full_name`/`repository.owner.login` used to select the verifying `github_app`, e.g. scope the lookup via `stacks` (as `PushHandler`/`CheckSuiteHandler` already do) instead of a global `Commit.where(sha:)`. More generally, `verify_signature` should not derive the trust anchor purely from unauthenticated payload fields without the handler re-validating that the same repository is the one being mutated.

### Proof of Concept
1. Attacker owns GitHub org `attacker-org`, connected to the shared Shipit instance with its own valid `webhook_secret`.
2. Attacker discovers/knows the SHA of a commit `deadbeef123...` belonging to stack `victim-org/victim-repo` (e.g. from the public GitHub UI or Shipit's public stack page).
3. Attacker sends `POST /webhooks` with header `X-Github-Event: status`, body:
```json
{
  "sha": "deadbeef123...",
  "state": "success",
  "context": "ci/some-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
4. Signs the raw body with `attacker-org`'s legitimate `webhook_secret` and sets `X-Hub-Signature` accordingly. [1](#0-0) 
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature (it is correctly signed for that org).
6. `StatusHandler#process` runs `Commit.where(sha: "deadbeef123...")`, finds the victim's commit (unrelated to `attacker-org`), and calls `create_status_from_github!`, marking it `success` and potentially unlocking deploy/continuous-delivery eligibility for `victim-org/victim-repo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
