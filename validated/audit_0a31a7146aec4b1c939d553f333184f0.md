### Title
Multi-tenant webhook signature verified against `repository.owner.login` while the payload's `repository.full_name` (a different, unverified-binding field) determines which stack/organization is actually mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization deployments, `WebhooksController#verify_signature` selects which GitHub App/webhook secret to check the signature against using `repository_owner` (derived from `params.dig('repository','owner','login')` or the fallback `organization.login`), while the actual event processing in `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks` acts on the independent `repository.full_name` field. Nothing in the engine enforces that these two fields agree with each other beyond both being inside the same HMAC-signed body, so a party holding the secret for organization A can craft a request selecting org A's secret while pointing all effective processing (stack sync, PR handling, status updates, membership changes) at org B's repository/stack.

### Finding Description
`verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) picks the app/secret to validate the signature with:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This binds "organization that authenticated" to the value `repository.owner.login`. In `Shipit.github(organization:)` (`lib/shipit.rb:170-181`), each organization has its own configured `webhook_secret`, and in the multi-org config schema each org's key is fully independent - `github_app_config(organization)` looks the config up strictly by that string key. [2](#0-1) 

However, once the signature check passes, the actual event dispatch (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `create`) hands the *whole raw payload* to handlers, and every handler resolves the target repository/stack via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a separate, independently-controlled JSON field from `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`Repository.from_github_repo_name` splits this `full_name` on `/` and looks up any repository record by `owner`/`name`, with no cross-check against `repository_owner` used earlier for signature selection:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [4](#0-3) 

Because HMAC verification only proves "this payload byte-string was signed with organization A's secret" — it does not, and cannot on its own, prove any *semantic* consistency between `repository.owner.login` and `repository.full_name` inside that payload. Since the attacker constructs the entire raw body before signing (using a secret they legitimately hold for org A, e.g. from being invited to install the Shipit GitHub App on their own org, or by having leaked/rotated access to one tenant's secret), they can set:
- `repository.owner.login` = `"org-a"` (so `Shipit.github(organization: "org-a")` picks org A's secret, which the attacker can compute HMAC-SHA1 for)
- `organization.login` = `"org-a"` if used for the `membership` event
- `repository.full_name` = `"org-b/victim-repo"` (used by every handler to locate stacks to sync/mutate)

The engine equality that should hold is:
```
organization authenticated (repository.owner.login → webhook_secret) == organization whose repository/stacks are written (repository.full_name)
```
This equality is never enforced anywhere in `WebhooksController`, `Webhooks::Handlers::Handler`, or the individual handlers (`PushHandler`, `PullRequest::*Handler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`), all of which independently re-derive the acted-upon repository from `payload['repository']['full_name']` (or in `MembershipHandler`'s case, `payload['organization']['login']`, which is a different field than what's checked in some paths).

### Impact Explanation
This crosses a repository boundary that should be strictly per-tenant: a party who is entitled to send webhooks for one organization configured in `Shipit.github` can force Shipit to act on stacks belonging to a *different* organization's repository, e.g.:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: ...)` for any stack of the spoofed `full_name` repo/branch — forcing a `GithubSyncJob` and altering the tracked HEAD of a stack in another tenant's org [5](#0-4) .
- `StatusHandler`/`CheckSuiteHandler` can inject fabricated CI status/check results for another org's stack, which downstream feeds `deployable?`/CI gating logic used to permit deploys.
- `PullRequest` handlers can unarchive/archive/relabel review stacks belonging to another org's repository.

This is a cross-organization/cross-repository write achieved purely by crafting payload content, without needing the victim organization's own webhook secret, satisfying the "cross-repository writes" Critical impact class in a multi-tenant Shipit deployment (the documented multi-org config schema in `docs/setup.md`/`config/secrets.development.example.yml`).

### Likelihood Explanation
Exploitability requires the engine to be configured with the multi-organization `github:` schema (each org keyed with its own `webhook_secret`), which the project explicitly documents and supports (`lib/shipit.rb:170-200`, `docs/setup.md`). Any attacker who has (or can obtain) a webhook secret for one tenant org — which is by design distributed to that org's admins to configure their GitHub App/webhook — can perform this attack against any other tenant hosted on the same Shipit instance, without needing credentials for the victim org. This is a realistic scenario for organizations offering Shipit-as-a-service across multiple GitHub orgs/business units.

### Recommendation
After signature verification succeeds, re-derive the organization from the *same* field used to resolve `Shipit.github(organization: ...)` and enforce it equals the organization prefix of every `repository.full_name` (or `organization.login`) value consumed by handlers for that request; reject the webhook if they diverge. Concretely, pass the verified `repository_owner` into `Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization: repository_owner) }`, and have `Handler#repository_name`/`#stacks` (and `MembershipHandler`) assert that the resolved repository's `owner` matches `verified_organization` before acting, raising/discarding otherwise.

### Proof of Concept
Configuration (multi-org schema):
```yaml
github:
  org-a:
    webhook_secret: "org-a-secret"   # known to org-a's admin (the attacker)
  org-b:
    webhook_secret: "org-b-secret"   # unknown to the attacker
```
Attacker (an org-a admin who can configure org-a's GitHub App webhook and thus knows/controls `org-a-secret`) sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1("org-a-secret", raw_body)>
```
with body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
`repository_owner` resolves to `"org-a"`, so `verify_signature` validates against `org-a-secret`, which the attacker legitimately controls, and the check passes. `PushHandler#process` then looks up `Repository.from_github_repo_name("org-b/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on org B's stacks, none of which the attacker was ever authenticated for. This cannot currently be fully executed in the read-only index environment for confirmation; a Devin session with the multi-org config and a running instance would be needed to reproduce and validate end-to-end.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
