### Title
`CCMenuController` bypasses per-`ApiClient` stack scoping, letting a stack-scoped token read any stack's build/deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` can only touch the `Stack` it was scoped to (via `ApiClient#stack_id`) by routing all stack lookups through the `stacks`/`stack` helpers. `Shipit::Api::CCMenuController` overrides `#stack` and looks the stack up directly from `params[:stack_id]` via `Stack.from_param!`, completely skipping the `current_api_client.stack_id?` scoping check. This breaks the binding "the stack a token authorizes == the stack it touches": a token scoped to Stack A can be presented with `stack_id` for Stack B and will be granted read access to Stack B's state.

### Finding Description
`BaseController` defines the scoping contract used by every other API controller: [1](#0-0) 

`stacks` restricts the queryable set of stacks to the one the `ApiClient` is bound to (if any); `stack` resolves `params[:stack_id]` only within that restricted set. `require_permission` only checks that the client's `permissions` array contains e.g. `read:stack` — it never re-checks which specific stack is being accessed: [2](#0-1) 

`CCMenuController` requires `:read, :stack` but redefines `stack` to bypass the scoping entirely: [3](#0-2) 

Because `stack` here calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(...)`, any authenticated `ApiClient` (even one created with `stack_id` set to a single specific stack, as fixtures like `here_come_the_walrus` demonstrate: `stack: shipit`) can supply an arbitrary `stack_id` in the URL and retrieve `#show` data for a stack it was never granted access to.

Contrast with every other resource controller (`DeploysController`, `TasksController`, etc.), which rely on `BaseController#stack`/`#stacks` and therefore correctly enforce the token-to-stack binding: [4](#0-3) , [5](#0-4) .

### Impact Explanation
This is an authorization-scope escape: a legitimately-issued `ApiClient` token intended to be usable only for one `Stack` (e.g., issued to an external CI dashboard for a single low-sensitivity stack/environment) can be used to read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, lock state, etc.) of any other stack managed by the same Shipit instance — including stacks the token holder should have no visibility into. This matches the in-scope High-impact category "unauthenticated read of stack state" in spirit: the attacker authenticates with a token but reads state entirely outside the token's authorized scope, i.e., an unauthorized cross-stack read that the permission model was explicitly designed to prevent (`ApiClient#stack_id` scoping exists specifically for this purpose).

### Likelihood Explanation
Any holder of a valid `ApiClient` token — even one deliberately scoped to a single stack for least-privilege reasons — can trigger this by simply changing the `stack_id` segment of the CCMenu URL (`/ccmenu/*stack_id`, see `config/routes.rb` line 49-51). No special privilege beyond possessing any valid stack-scoped token with `read:stack` permission is required, and the request is a simple unauthenticated (from the target stack's perspective) GET.

### Recommendation
Remove the `stack` override in `CCMenuController` (or make it delegate through `stacks.from_param!`) so the same `ApiClient#stack_id` scoping enforced by `BaseController` applies here:

```ruby
private

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

Keep the custom `authenticate_api_client` (which permits token-in-query-string for CCTray clients) but ensure it still assigns `@current_api_client` before `stack`/`stacks` are evaluated, and add a regression test asserting a stack-scoped `ApiClient` receives 404/403 when requesting a different stack's CCMenu status.

### Proof of Concept
1. Create (or use fixture) `ApiClient` `here_come-the-walrus` scoped to `stack: shipit`, permission `read:stack` (see `test/fixtures/shipit/api_clients.yml`).
2. Using that client's `authentication_token`, request:
   `GET /ccmenu/*<other_stack_owner>/<other_stack_repo>/<other_env>?token=<here_come_the_walrus token>`
3. `CCMenuController#authenticate_api_client` authenticates the token successfully; `require_permission :read, :stack` passes because the client has `read:stack` in its `permissions` list.
4. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `stacks.from_param!`), resolving to the *other* stack rather than raising `ActiveRecord::RecordNotFound` as it would for every properly-scoped controller.
5. The response renders `shipit/ccmenu/project.xml` for the unauthorized stack, leaking its build/deploy status to a token holder who was only supposed to see the `shipit` stack. [6](#0-5)
