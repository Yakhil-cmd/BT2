### Title
AA-generated payments bypass MAX_INPUTS_PER_PAYMENT_MESSAGE, allowing dust-deposit DOS of AA balance spending - (File: aa_composer.js / validation.js)

### Summary
An attacker can send a large number of tiny ("dust") asset payments to an Autonomous Agent (AA) address. When the AA later needs to compose a payment that spends this asset (e.g., paying out a balance, refunding, or any state logic that sends the asset back), `aa_composer.js` builds the payment by pulling *all* unspent outputs for that asset/address with no `LIMIT` and iterating over them one by one in `iterateUnspentOutputs` until the target amount is accumulated. Because `validatePaymentInputsAndOutputs` explicitly skips the `MAX_INPUTS_PER_PAYMENT_MESSAGE` check for AA-generated units (`&& !objValidationState.bAA`), the composed unit can end up containing far more than the normal 128-input cap, unlike ordinary user-composed payments.

### Finding Description
`aa_composer.js`'s `completePaymentPayload` picks stable/unstable unspent outputs to satisfy an outgoing AA payment: [1](#0-0) 

The query that supplies rows to iterate has **no `LIMIT`**, and the explicit dust-attack mitigation only covers the base-byte asset: [2](#0-1) 

```
// byte outputs less than 60 bytes (which are net negative) are ignored to prevent dust attack: ...
"... AND asset"+(asset ? "="+conn.escape(asset) : " IS NULL AND amount>=" + FULL_TRANSFER_INPUT_SIZE)+" ..."
```

Note the `FULL_TRANSFER_INPUT_SIZE` dust filter is applied only when `asset` is falsy (i.e., only for the base byte asset). For any custom asset (`asset` truthy), there is no minimum-amount filter, so an attacker can flood the AA with arbitrarily many minimal-amount (e.g., amount=1) outputs of a custom asset that the AA accepts, without any dust filtering.

When the AA subsequently needs to spend that asset (any state/payment logic that sends the asset out, including simple pass-through/refund logic), `iterateUnspentOutputs` walks through the (unbounded) result set, pushing one `input` per row into `payload.inputs`, until the target amount is reached: [3](#0-2) 

Normally, `validatePaymentInputsAndOutputs` in `validation.js` caps the number of inputs per payment message: [4](#0-3) 

```
if (payload.inputs.length > constants.MAX_INPUTS_PER_PAYMENT_MESSAGE && !objValidationState.bAA)
    return callback("too many inputs");
```

but this check is **bypassed when `objValidationState.bAA` is true**, i.e. for units generated by AA responses. This means an AA-composed unit spending a dust-flooded asset balance can legitimately contain many more inputs than `MAX_INPUTS_PER_PAYMENT_MESSAGE` (128), unlike normal user payments which are hard-capped.

### Impact Explanation
This is directly analogous to the reported OpenQ bug class: an attacker-controlled, unbounded list of dust deposits is iterated in full whenever the victim contract (here, the AA) attempts to move funds of that asset. Consequences:
- The AA's payment-composing loop (`iterateUnspentOutputs`/`readStableOutputs`/`readUnstableOutputsSentByAAs`) must process every dust row for the flooded asset, which is unbounded in size and grows linearly with attacker-supplied spam, degrading AA processing time and potentially causing the AA to build oversized/invalid units (exceeding `MAX_UNIT_LENGTH` / storage constraints) when trying to pay out or refund that asset.
- Because the anti-spam cap `MAX_INPUTS_PER_PAYMENT_MESSAGE` is explicitly not enforced for AA units, an attacker can force an AA into producing payment messages with an arbitrarily large number of inputs for a custom asset, which can prevent the AA from ever successfully composing a valid/economical response for that asset — effectively freezing the AA's ability to spend/refund that asset balance (fund freezing), matching the "AA fund loss or freezing" impact class.
- This can be triggered by any unprivileged user simply by sending many minimal-amount custom-asset payments to a public AA address that is known to later forward/refund that asset, requiring no privileged capability, mirroring the "refunds disabled with dust deposits" bug class exactly (unbounded loop over an attacker-inflatable deposit list gating a legitimate accounting/spend operation).

### Likelihood Explanation
Likelihood is Medium: it requires (a) an AA that accepts and later sends out a non-base asset (a very common AA pattern — deposit/withdraw, DEX-like AAs, bridges), and (b) the attacker to spend gas/fees to send many small-amount deposits of that asset. Since custom assets can be created cheaply and issued by the attacker themselves (they only need "dust" quantities of some asset the AA is willing to accept, or even an asset the AA doesn't validate amount thresholds for), the barrier to executing this is low. The explicit code comment shows the developers were aware of and mitigated this exact dust-attack pattern for the base asset but left custom assets unprotected, and separately relaxed the input-count cap specifically for AA units — the combination is the root cause.

### Recommendation
- Apply the same or an equivalent dust-filtering threshold to non-base assets in `readStableOutputs`/`readUnstableOutputsSentByAAs` in `aa_composer.js` (e.g., a minimum asset-amount threshold configurable per-asset, or reject outputs whose value is not worth the input storage/fee overhead).
- Re-enforce (or introduce an AA-specific but still bounded) cap on `payload.inputs.length` for AA-generated payment messages in `validation.js`'s `validatePaymentInputsAndOutputs`, instead of fully exempting `objValidationState.bAA` from `MAX_INPUTS_PER_PAYMENT_MESSAGE`.
- Add a `LIMIT` to the SQL queries in `readStableOutputs`/`readUnstableOutputsSentByAAs` and iterate/merge in bounded batches, failing gracefully (bounce) rather than attempting to include unbounded inputs.

### Proof of Concept
1. Attacker creates or identifies a custom asset accepted by a target AA that performs pass-through/refund/withdraw logic for that asset.
2. Attacker submits thousands of minimal-amount (e.g., amount=1) payment units of that asset to the AA's address; each is accepted as a normal payment (no per-asset dust filter exists at deposit time).
3. Attacker (or another user) triggers the AA logic that causes it to send back/withdraw that asset balance.
4. `completePaymentPayload`'s `readStableOutputs` query returns all unspent dust outputs for the asset (no `LIMIT`), and `iterateUnspentOutputs` loops through all of them, building `payload.inputs` with thousands of entries.
5. Because `objValidationState.bAA` disables the `MAX_INPUTS_PER_PAYMENT_MESSAGE` check in `validation.js` (line 2137-2140), the resulting oversized payment message is not rejected for having too many inputs by that check, but its sheer size may exceed `MAX_UNIT_LENGTH` or make the response computationally expensive/uneconomical, causing the AA's response to bounce or fail repeatedly — freezing the AA's ability to move funds of that asset until manually mitigated.
