### Title
Independent `has`/`has one`/`seen` filter evaluations in address/asset definitions allow a single payment output to satisfy multiple distinct spending conditions, bypassing multi-payment requirements - (File: `definition.js`)

### Summary
Address (and asset issue/transfer) definitions in ocore can combine multiple `has`, `has one`, and `seen` clauses with `and`/`or`/`r of set` to require that several distinct payments be present in the spending unit (e.g. "pay fee A to address X" AND "pay fee B to address Y", or two separate outputs of a given amount). Each of these clauses is evaluated **independently** against the full, unconsumed list of the unit's payment messages. Nothing tracks which output/input has already been "used" to satisfy a previous clause, so the same single output can be matched by multiple separate `has`/`has one`/`seen` conditions simultaneously. This mirrors the Mantra DEX bug class: independent equality/existence checks against a shared pool of funds allow one payment to be double-counted, letting an attacker satisfy two distinct requirements while paying only once.

### Finding Description
The `has`/`has one` evaluation in `validateAuthentifiers` simply delegates to `evaluateFilter`, which scans `objUnit.messages` for any input/output matching the filter and returns true if at least one match exists: [1](#0-0) 

`evaluateFilter` itself has no concept of state carried over between separate calls - every invocation independently re-scans the full unit and returns any outputs/inputs that satisfy the filter: [2](#0-1) 

The `seen` op has the same structural issue against historical DB payments, running an independent `SELECT ... LIMIT 1` per clause with no exclusion of previously "consumed" matches: [3](#0-2) 

In contrast, `has equal`/`has one equal` was explicitly designed to correctly count matching *pairs* between two search criteria using a key-based map (`mapSecondKeyToCount`), showing that the developers are aware overlapping matches need de-duplication logic in some cases: [4](#0-3) 

However, this de-duplication is absent when combining plain `has`/`has one`/`seen` clauses via `and`. If a definition author writes something like:
```
['and', [
  ['has', {what: 'output', address: 'ESCROW_ADDR', amount: 1000}],
  ['has', {what: 'output', address: 'ESCROW_ADDR', amount: 1000}]
]]
```
intending to require **two separate** 1000-unit payments to `ESCROW_ADDR` before authorizing a spend, a single output of amount 1000 to `ESCROW_ADDR` will independently satisfy both `has` clauses, because each clause performs its own full scan and finds the same output. The `and` evaluator in `validateAuthentifiers` combines the two boolean results with a simple logical AND, with no tracking of which underlying output backed each `true`: [5](#0-4) 

This is the direct analog of the report's root cause: two separate fee-validation checks (`pool_creation_fee` and `denom_creation_fee`) that are supposed to represent two distinct payments are validated independently against the same submitted funds, allowing one payment to satisfy both checks.

### Impact Explanation
Any address or asset condition (used for escrows, multi-party payment gates, conditional releases, DEX-style contracts built on oscript definitions, or `issue_condition`/`transfer_condition` for assets) that relies on multiple `has`/`has one`/`seen` clauses to enforce that *distinct* payments (to distinct beneficiaries, or in distinct amounts meant to represent separate obligations) are all present can be bypassed with a single, smaller payment satisfying all of the clauses at once. This constitutes unauthorized spending / bypass of payment obligations that the definition author intended to be independently required - directly resulting in fund loss for whichever party expected all the distinct payments to be enforced (e.g. an escrow releasing funds after only a fraction of the required combined payment, or a fee-splitting contract paying out despite only one of several required fees having been paid).

### Likelihood Explanation
Any user or AA author can freely construct an address definition (or asset `issue_condition`/`transfer_condition`) that combines several `has`/`has one`/`seen` conditions with `and` expecting them to enforce independent payments. Any unprivileged unit poster who wants to spend from or interact with such an address only needs to craft a single unit containing carefully chosen outputs/inputs that happen to match multiple clauses simultaneously - well within reach of any user submitting a normal payment unit, no special privileges required.

### Recommendation
When evaluating multiple `has`/`has one`/`seen`/`sum` filters combined via `and`/`or`/`r of set` within the same evaluation of a definition, track which specific inputs/outputs (or DB rows, for `seen`) have already been consumed to satisfy an earlier clause, and exclude them when evaluating subsequent clauses of the same boolean expression - analogous to what `has equal`/`has one equal` already does via keyed counting. Alternatively, document this behavior explicitly as a known semantic limitation of definitions so that no combination of independent `has`-family clauses can be assumed to require distinct underlying payments, and add validation-time complexity/duplicate-clause warnings to discourage this unsafe pattern.

### Proof of Concept
1. Define an address `A` with definition:
```
['and', [
  ['sig', {pubkey: PUBKEY}],
  ['has', {what: 'output', address: 'X', amount: 1000}],
  ['has', {what: 'output', address: 'X', amount: 1000}]
]]
```
intended to require the spender to also pay 2×1000 to `X` (e.g., two separate service fees) before the signature-authorized spend is valid.
2. Attacker crafts a unit spending from `A`, with a single `payment` message whose `outputs` include only **one** output of `{address: 'X', amount: 1000}` (plus the change output back to `A`), and a valid signature.
3. During validation, `evaluate(['and', [...]])` calls `evaluate` on each `has` clause; both independently call `evaluateFilter('has', {address:'X', amount:1000}, ...)`, both find the same single output, and both return `true`. The overall `and` result is `true`, so the unit is accepted despite only one 1000-unit payment being made instead of the two intended. [6](#0-5)

	function evaluateFilter(op, filter, handleResult){
		var arrFoundObjects = [];
		for (var i=0; i<objUnit.messages.length; i++){
			var message = objUnit.messages[i];
			if (message.app !== "payment" || !message.payload) // we consider only public payments
				continue;
			var payload = message.payload;
			if (filter.asset){
				if (filter.asset === "base"){
					if (payload.asset)
						continue;
				}
				else if (filter.asset === "this asset"){
					if (payload.asset !== this_asset)
						continue;
				}
				else{
					if (payload.asset !== filter.asset)
						continue;
				}
			}
			if (filter.what === "input"){
				if (!Array.isArray(payload.inputs))
					continue;
				for (var j=0; j<payload.inputs.length; j++){
					var input = payload.inputs[j];
					if (!isNonemptyObject(input))
						continue;
					if (input.type === "headers_commission" || input.type === "witnessing")
						continue;
					if (filter.type){
						var type = input.type || "transfer";
						if (type !== filter.type)
							continue;
					}
					var augmented_input = objValidationState.arrAugmentedMessages ? objValidationState.arrAugmentedMessages[i].payload.inputs[j] : null;
					if (filter.address){
						if (filter.address === 'this address'){
							if (augmented_input.address !== address)
								continue;
						}
						else if (filter.address === 'other address'){
							if (augmented_input.address === address)
								continue;
						}
						else { // normal address
							if (augmented_input.address !== filter.address)
								continue;
						}
					}
					if (filter.amount && augmented_input.amount !== filter.amount)
						continue;
					if (filter.amount_at_least && augmented_input.amount < filter.amount_at_least)
						continue;
					if (filter.amount_at_most && augmented_input.amount > filter.amount_at_most)
						continue;
					arrFoundObjects.push({...(augmented_input || input), asset: payload.asset || "base", type: input.type || "transfer" });
				}
			} // input
			else if (filter.what === "output"){
				if (!Array.isArray(payload.outputs))
					continue;
				for (var j=0; j<payload.outputs.length; j++){
					var output = payload.outputs[j];
					if (!isNonemptyObject(output))
						continue;
					if (filter.address){
						if (filter.address === 'this address'){
							if (output.address !== address)
								continue;
						}
						else if (filter.address === 'other address'){
							if (output.address === address)
								continue;
						}
						else { // normal address
							if (output.address !== filter.address)
								continue;
						}
					}
					if (filter.amount && output.amount !== filter.amount)
						continue;
					if (filter.amount_at_least && output.amount < filter.amount_at_least)
						continue;
					if (filter.amount_at_most && output.amount > filter.amount_at_most)
						continue;
					arrFoundObjects.push({...output, asset: payload.asset || "base"});
				}
			} // output
		}
		if (arrFoundObjects.length === 0)
			return handleResult(false);
		if (op === "has one" && arrFoundObjects.length === 1)
			return handleResult(true);
		if (op === "has" && arrFoundObjects.length > 0)
			return handleResult(true, arrFoundObjects);
		handleResult(false);
	}
