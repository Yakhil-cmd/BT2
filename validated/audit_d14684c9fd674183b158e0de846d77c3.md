### Title
Recipient-Controlled Revert in `handleKLAYTransfer` Permanently Locks Bridged KLAY — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in the Kaia service-chain bridge updates nonce state and then makes an unchecked external call to the recipient address. If the recipient is a contract whose fallback reverts, the entire transaction reverts (rolling back the nonce update), and the KLAY transfer can never be completed. The KLAY remains permanently locked in the bridge with no admin escape hatch, directly mirroring the H02 "winner stalls the system" pattern.

---

### Finding Description

In `BridgeTransferKLAY.sol`, `handleKLAYTransfer` executes the following sequence:

1. Validates the nonce (`_lowerHandleNonceCheck`)
2. Collects operator votes (`_voteValueTransfer`)
3. Records the handled tx hash (`_setHandledRequestTxHash`)
4. Writes `handleNoncesToBlockNums[_requestedNonce]` and calls `_updateHandleNonce` — advancing `lowerHandleNonce` and `recoveryBlockNumber`
5. Emits `HandleValueTransfer`
6. Calls `_to.call.value(_value)("")` — an external call to the recipient
7. `require(ok, "handleKLAYTransfer: transfer failed")` — **reverts the entire transaction if the recipient reverts** [1](#0-0) 

Because step 7 causes a full EVM revert, all state mutations from steps 3–5 are rolled back. The nonce is never durably marked as handled. Operators can retry, but if the recipient contract is designed to always revert on receiving KLAY, every retry fails identically. There is no mechanism in the contract to skip, redirect, or administratively recover the stuck KLAY.

The `_updateHandleNonce` function advances `lowerHandleNonce` only when consecutive nonces starting from the current lower bound are filled in `handleNoncesToBlockNums`. A permanently stuck nonce N prevents `lowerHandleNonce` from advancing past N, which also freezes `recoveryBlockNumber` at the block preceding N. [2](#0-1) 

The bridge contract has no `emergencyWithdraw`, no nonce-skip function, and no owner-only bypass for failed transfers. The KLAY deposited on the source chain is already consumed; the corresponding KLAY on the destination chain is locked in the bridge forever.

---

### Impact Explanation

**Permanently locked bridged KLAY assets.** A recipient contract that reverts on receiving KLAY causes the bridge to hold the KLAY indefinitely with no recovery path. This satisfies the allowed impact criterion: *"Unauthorized transfer, mint, unlock, burn, fee charge, reward distribution, or key/nonce consumption affecting KAIA, bridged assets, or system-managed funds."*

Additionally, `recoveryBlockNumber` is frozen at the block of the last successfully handled nonce before N, causing the bridge's recovery scanner to repeatedly re-scan from that old block, wasting operator resources and potentially masking other missed events. [3](#0-2) 

---

### Likelihood Explanation

**Medium.** The trigger requires the recipient (`_to`) to be a contract with a reverting `receive`/fallback. This can occur:

- **Accidentally**: A multisig, proxy, or smart-contract wallet that does not implement a payable fallback is specified as `_to`. The sender may not know the recipient cannot accept KLAY.
- **Maliciously (leverage extraction)**: An attacker deploys a contract that reverts unless a side-payment condition is met, then induces a third party to bridge KLAY to that address. The attacker then demands payment to "fix" the contract — exactly the leverage scenario described in H02.

The attack requires no special privilege. Any user of the bridge on the source chain can specify an arbitrary `_to` address on the destination chain. [4](#0-3) 

---

### Recommendation

Replace the push-payment pattern with a pull-payment pattern:

1. Instead of `_to.call.value(_value)("")` with a hard `require`, store the claimable balance in a mapping: `pendingWithdrawals[_to] += _value`.
2. Add a `withdraw()` function that lets the recipient pull their KLAY.
3. This decouples the nonce-advancement logic from the recipient's ability to receive KLAY, eliminating the griefing vector.

Alternatively, if push semantics must be kept, handle the failure gracefully without reverting the nonce state — mark the nonce as handled regardless of transfer success, and store the KLAY for later claim:

```solidity
(bool ok, ) = _to.call.value(_value)("");
if (!ok) {
    pendingWithdrawals[_to] += _value;
}
// do NOT revert; nonce is already advanced
```

### Proof of Concept

1. Deploy a malicious recipient contract on the destination chain:
   ```solidity
   contract MaliciousRecipient {
       receive() external payable { revert("not yet"); }
   }
   ```

2. On the source chain, call `requestKLAYTransfer(maliciousRecipientAddr, value, "")` sending KLAY to the bridge. The source-chain KLAY is consumed.

3. Bridge operators observe the `RequestValueTransfer` event and call `handleKLAYTransfer` on the destination bridge with `_to = maliciousRecipientAddr`.

4. The call to `_to.call.value(_value)("")` triggers `MaliciousRecipient.receive()`, which reverts.

5. `require(ok, "handleKLAYTransfer: transfer failed")` causes the entire transaction to revert. `handleNoncesToBlockNums[N]` is never set; `lowerHandleNonce` stays at N.

6. Every subsequent operator retry fails identically. The KLAY is permanently locked in the bridge. The attacker can demand a side-payment to deploy a new contract that accepts KLAY, then have the sender re-initiate the transfer. [5](#0-4) [6](#0-5)
