### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while all event handlers act on the unrelated, unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC signature against using `repository_owner`, computed from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. Every event handler, however, resolves the actual `Stack`/`Repository` to mutate using a completely different, independently-controlled field: `payload.dig('repository','full_name')`. Because both fields come from the same unauthenticated JSON body and the signature only proves the payload was signed with *some* organization's secret — not that the two identity fields are consistent with each other — a request that authenticates against organization A can act on any other tracked repository B.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from the same untrusted JSON body that is being verified, and is used only to pick which GitHub App organization's `webhook_secret` to validate the signature against (`Shipit.github(organization: repository_owner)` → `GitHubApp#verify_webhook_signature`): [3](#0-2) 

Note also that `verify_webhook_signature` returns `true` (i.e. auto-passes) when no `webhook_secret` is configured for that organization: `return true unless webhook_secret`. So any organization tracked by Shipit that has not (yet) had a webhook secret configured accepts *any* payload unconditionally, regardless of signature.

Meanwhile, every `Shipit::Webhooks::Handlers::Handler` subclass — the code that actually mutates state — looks up the target `Repository`/`Stack` using an entirely different payload field, `repository.full_name`, never cross-checked against `repository.owner.login`/`organization.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

This is the exact analog of the reported bug class: the value that is authenticated (`repository.owner.login` used to pick the verifying secret) is never bound to the value that is actually acted upon (`repository.full_name` used to select the target stack/commit). The binding `verified_org == acted_repository.owner` is never enforced — analogous to how `_delegate` never re-validates that `address(0)` participates meaningfully in vote accounting.

### Impact Explanation
An attacker who can produce (or is handed, e.g. for one organization with no `webhook_secret` configured, which auto-passes verification) a valid signature for *any single* organization tracked by the Shipit instance can submit a webhook body whose `repository.owner.login`/`organization.login` matches that authenticated organization, but whose `repository.full_name` names a repository belonging to a *different* organization altogether. Handlers such as `StatusHandler` (writes commit CI statuses, which feed into deploy-safety checks used to gate whether a commit is "deployable"), `PushHandler` (triggers a GitHub sync job for arbitrary stacks), and the pull-request handlers (archive/unarchive review stacks, update PR metadata) will all act on the cross-organization target resolved purely from `full_name`. This can be used to spoof a passing CI status on a victim organization's commit, defeating the CI-required-status gate an operator relies on before allowing a deploy — an unauthenticated write into another organization's stack state.

### Likelihood Explanation
The webhooks endpoint is unauthenticated by design (it's the public GitHub webhook receiver) and relies entirely on `verify_signature` for trust. The vulnerable condition (organization with no `webhook_secret` configured, or an attacker holding the secret for one org via legitimate but limited relationship to that org) is a realistic deployment scenario in a multi-organization Shipit installation, since `webhook_secret` is explicitly optional per the `return true unless webhook_secret` fallback. The mismatch between the field used for authentication (`owner.login`/`organization.login`) and the field used for the actual database lookup (`full_name`) is present in every handler, so the bug is broadly reachable, not confined to a single event type.

### Recommendation
Bind the two identity fields: after signature verification succeeds, re-derive/validate that the organization portion of `repository.full_name` matches `repository_owner` (the value the signature was actually checked against) before dispatching to any handler, and reject the request otherwise. Additionally, consider making `webhook_secret` mandatory for any organization for which webhooks are accepted, removing the automatic-pass fallback.

### Proof of Concept
1. Shipit tracks two organizations: `org-victim/repo` (properly configured with `webhook_secret`) and `org-attacker` (GitHub App installed but no `webhook_secret` configured, or attacker otherwise knows `org-attacker`'s secret).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-victim/repo" }
}
```
3. `verify_signature` computes `repository_owner = "org-attacker"`, looks up `Shipit.github(organization: "org-attacker")`, and passes verification (no secret configured, or attacker knows it).
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, writing a `success` status for the victim organization's commit — even though the signature was never checked against `org-victim`'s secret. [6](#0-5)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
