### Title
Repository-independent `repository_owner` fallback lets a low/no-secret organization's key verify a forged webhook whose `repository.full_name` targets a different tenant's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's `webhook_secret` to check against using `repository_owner`, which falls back from `repository.owner.login` to the independently attacker-controlled `organization.login` field [1](#0-0) . `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler` (and `OpenedHandler`/`ReopenedHandler`/`LabeledHandler`) instead resolve the actual repository/stack purely from `params.repository.full_name`, which the schema requires but never ties to `repository.owner.login` or `organization.login` [2](#0-1) [3](#0-2) . In a multi-organization Shipit deployment, this lets an attacker who controls (or names) an org with no `webhook_secret` configured pass signature verification trivially and then write to a stack/repo belonging to a different, properly-secured organization.

### Finding Description
The broken binding, stated as an equality that the code should but does not enforce:
`organization_whose_secret_verified_request.login == repository_that_gets_mutated.owner.login`

Trace:
1. `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` where `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')` [4](#0-3) .
2. `Shipit.github` in multi-org mode (`github_default_organization` present, i.e. `secrets.github` keyed by org names) resolves `config = github_app_config(organization)` using that attacker-influenced `organization` string verbatim, with no relation to the payload's `repository.full_name` [5](#0-4) .
3. `GitHubApp#verify_webhook_signature` does `return true unless webhook_secret` [6](#0-5) . Any organization present in the multi-org config with no `webhook_secret` set (the shipped example configs default `webhook_secret:` to nil for every org, see `test/dummy/config/secrets_double_github_app.yml`) causes signature verification to pass unconditionally for any signature header, including a blank/garbage one.
4. Once verification passes, `Shipit::Webhooks.for_event('pull_request')` dispatches to handlers such as `LabelCapturingHandler`, `OpenedHandler`, `ReopenedHandler`. None of these handlers re-check that `params.repository.full_name`'s owner matches the organization that satisfied step 3 — they only require `repository.full_name` in the params schema and use it directly to look up `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) .
5. Attacker payload: `{"action":"reopened","number":1,"pull_request":{...,"labels":[{"name":"ATTACKER_ENV_KEY"}]},"repository":{"full_name":"victim-org/victim-repo"},"organization":{"login":"attacker-org"},"sender":{"login":"attacker"}}` with `X-Github-Event: pull_request` and an arbitrary/blank `X-Hub-Signature`. Because `repository` has no `owner.login` sub-key, `repository_owner` falls back to `organization.login` = `attacker-org`, which the attacker knows has no configured `webhook_secret`.
6. `LabelCapturingHandler#capture_labels` then runs `pull_request.update!(labels: params.pull_request.labels.map(&:name))` against `victim-org/victim-repo`'s `PullRequest` record [7](#0-6) , and for `ReopenedHandler`/`OpenedHandler` the same cross-tenant repository is used to create/unarchive a `ReviewStack` and provision it [8](#0-7) .

No existing guard prevents this: `verify_signature` never compares the org it authenticated against to `params.repository.full_name`'s owner; the `ExplicitParameters` schemas across all `PullRequest` handlers require `repository.full_name` but never `repository.owner.login`; `drop_unhandled_event` only checks the event type exists a handler for, not org binding.

Note: in single-organization deployments (`github_default_organization` is `nil`), `Shipit.github` ignores the passed `organization` value and always loads the single global config [9](#0-8) , so the same real secret is checked regardless of `repository_owner`, and this specific divergence has no effect there. The vulnerability is real only for multi-organization configurations (`github: { OrgOne: {...}, OrgTwo: {...} }`), which the engine explicitly documents and ships example config for.

### Impact Explanation
For multi-org Shipit installations, an attacker who can name (or control) at least one configured organization lacking a `webhook_secret` can forge arbitrary `pull_request` events that are authenticated as that low-security org yet mutate any other organization's `Repository`'s `ReviewStack`/`PullRequest`/labels — including creating/unarchiving stacks and queuing provisioning (`ReviewStackProvisioningQueue.add`) for repositories they do not own. Labels are later uppercased into environment variables in `ReviewStack#env` for that other tenant's provisioning/deploy commands, giving the attacker env-key injection into another tenant's deploy environment. This is a cross-tenant state-manipulation issue matching the "Critical: a payload for one repository mutating another's stack" category, repeatable against any repository across the installation's organizations for as long as one configured org lacks a secret.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment, (2) at least one configured organization in `secrets.github` with `webhook_secret` blank/unset — which is the out-of-the-box default in every shipped example (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), and (3) attacker knowledge of that org's login string, which is discoverable (it's a GitHub org name, often public). No Shipit credentials, GitHub App keys, or session are needed. This is a low-cost, fully repeatable attack per request once these operator-configuration preconditions hold.

### Recommendation
In `WebhooksController#verify_signature`, bind the authenticated organization to the repository actually referenced in the payload: derive `repository_owner` solely from `repository.owner.login` (or from `repository.full_name`'s owner segment) and reject the request (422) if that is absent, rather than falling back to the independently-controlled `organization.login`. Additionally, require every `webhook_secret` to be present (reject/log misconfiguration) for organizations enrolled in multi-org mode, and have each webhook handler validate that `params.repository.owner.login` (or the owner segment of `full_name`) matches the organization whose secret verified the request.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_cross_org_test.rb
require "test_helper"

module Shipit
  class WebhooksControllerCrossOrgTest < ActionDispatch::IntegrationTest
    test "forged organization fallback lets attacker-org secret authenticate a payload that mutates victim-org's PullRequest" do
      # Precondition: multi-org config where "attacker-org" has no webhook_secret,
      # "victim-org" does (simulated via Shipit.stubs(:github) or fixture secrets).
      victim_stack = shipit_stacks(:review_stack) # owned by "victim-org/victim-repo"
      victim_pr = victim_stack.pull_request

      body = {
        action: "reopened",
        number: victim_stack.environment.delete_prefix("pr").to_i,
        pull_request: {
          id: 1, number: 1, url: "u", title: "t", state: "open",
          additions: 1, deletions: 1,
          head: { sha: "abc", ref: victim_stack.branch },
          user: { login: "attacker" },
          assignees: [],
          labels: [{ name: "forged-label" }]
        },
        repository: { full_name: "victim-org/victim-repo" }, # no "owner" key
        organization: { login: "attacker-org" },              # attacker-org has no webhook_secret
        sender: { login: "attacker" }
      }.to_json

      post "/webhooks", params: body,
        headers: { "X-Github-Event" => "pull_request", "X-Hub-Signature" => "sha1=deadbeef" },
        as: :json

      assert_response :ok
      # Equality that should hold but doesn't:
      # organization_that_verified_signature ("attacker-org", no secret)
      #   != repository_owner_of_mutated_record ("victim-org")
      assert_equal ["forged-label"], victim_pr.reload.labels
    end
  end
end
```
Both sides of the invariant — the org that satisfied `verify_signature` ("attacker-org") and the org owning the mutated `PullRequest`/`ReviewStack` ("victim-org") — diverge, confirming the vulnerability.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
```
