### Title
Webhook signature verification is keyed off an attacker-controlled, unverified payload field, allowing team-membership forgery and `Shipit.github_teams` authorization bypass - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to check the HMAC signature against based on a field taken directly from the *unverified* request body, before any cryptographic check has occurred. Because `Shipit::GitHubApp#verify_webhook_signature` trivially returns `true` when that selected org has no configured secret, an attacker can pick any org name that has a blank/absent `webhook_secret` (a documented, optional configuration state) to make the signature check pass unconditionally, while other payload fields — used by the event handlers to decide what gets written — are completely independent of the field that was "verified." This is the same bug class as TRST-M-3: a value that gates a critical check (`getHatLevel`/admin check in the original report) is not itself bound to what is actually authorized/acted upon, letting attacker-controlled input silently break the intended trust boundary.

### Finding Description
`before_action :check_if_ping, :drop_unhandled_event, :verify_signature` runs `verify_signature`, which computes the org to authenticate against straight from the raw JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves a per-organization `GitHubApp` instance (Shipit explicitly supports multi-org configuration with independent `webhook_secret` per org): [3](#0-2) [4](#0-3) 

`verify_webhook_signature` unconditionally returns `true` if the selected org's `webhook_secret` is blank — which the documented default/example config explicitly sets to `nil`: [5](#0-4) [6](#0-5) 

The org value used to pick this (bypassable) check has no relationship to the resource actually mutated by the handler that subsequently runs. For `membership` events, `MembershipHandler` finds the `Team` purely by numeric GitHub `team.id`, not by the `organization.login` used for signature selection, and then mutates its membership: [7](#0-6) 

`User#authorized?` grants access to the whole Shipit application based purely on local `teams` membership rows populated by that handler: [8](#0-7) [9](#0-8) 

The broken binding, expressed as an equality that no longer holds:
`organization authenticated by verify_signature (repository_owner / organization.login)` ≠ `Team record actually written by MembershipHandler (keyed by numeric team.id, independent of that org)`.

### Impact Explanation
If any configured GitHub organization in a Shipit multi-org deployment has no `webhook_secret` set (an explicitly supported/"optional" configuration per `docs/setup.md`), an unauthenticated attacker can:
1. Send a forged `membership` webhook with `organization.login` set to that unsecured org (making `verify_webhook_signature` return `true` regardless of the `X-Hub-Signature` header).
2. Set `team.id` to the GitHub numeric ID of the actual team that gates access (`Shipit.github_teams`, configured via `oauth.teams`).
3. Set `member.login` to their own GitHub login and `action: "added"`.

`MembershipHandler` will find the existing authorized `Team` row by `github_id` (ignoring the mismatched `organization.login`) and add the attacker as a member, satisfying `User#authorized?` and bypassing the entire GitHub-team-based authorization gate — a full authentication/authorization bypass into the Shipit UI/API without any real GitHub team membership, OAuth login, webhook secret, or session. This meets the "High — escalation into `Shipit.github_teams` authorization" impact bar defined in scope.

### Likelihood Explanation
Requires only knowledge of: (a) one org name in the deployment's config lacking a `webhook_secret` (an unauthenticated attacker can simply probe/guess, or it may be the sole/default org since the documented default leaves `webhook_secret: nil`), (b) the public numeric GitHub team ID of the authorizing team (discoverable via the GitHub API for any org/team the attacker can view), and (c) their own GitHub login. No credentials, sessions, or tokens are needed — the request is a plain unauthenticated POST to `/webhooks`.

### Recommendation
- Never select the signing/verification organization from unauthenticated payload content. Verify against all configured webhook secrets (or a single well-known secret) independent of attacker-supplied `repository`/`organization` fields, or require `webhook_secret` to be mandatory (non-optional) for every configured organization.
- In `MembershipHandler#find_or_create_team!`, scope team lookup/update by both `github_id` and the already-verified organization, and reject events whose `organization.login`/`repository.owner.login` does not match the org whose secret produced a valid signature.
- Treat `verify_webhook_signature` returning `true` for a blank secret as a misconfiguration warning rather than a silent pass-through, especially for authorization-relevant events (`membership`).

### Proof of Concept
Given a deployment with two configured orgs (`OrgOne` with a real `webhook_secret`, `OrgTwo` with `webhook_secret: nil`, as allowed by the documented multi-org schema — see `test/dummy/config/secrets_double_github_app.yml`):

```
POST /webhooks HTTP/1.1
X-Github-Event: membership
X-Hub-Signature: sha1=anything-or-empty

{
  "action": "added",
  "team": { "id": 123456, "name": "Shipit Admins", "slug": "shipit-admins", "url": "https://github.com/..." },
  "organization": { "login": "OrgTwo" },
  "member": { "login": "attacker-github-login" }
}
```

- `repository_owner` resolves to `"OrgTwo"` via `params.dig('organization','login')` (`webhooks_controller.rb:61`).
- `Shipit.github(organization: 'OrgTwo').verify_webhook_signature(...)` returns `true` immediately because `webhook_secret` is blank (`github_app.rb:76-77`), regardless of the forged `X-Hub-Signature`.
- `MembershipHandler#find_or_create_team!` looks up `Team.find_or_create_by!(github_id: 123456)` — matching the real, pre-existing authorized team row (created earlier via legitimate `OrgOne` events) — and `team.add_member(User.find_or_create_by_login!('attacker-github-login'))` adds the attacker.
- On next login/session check, `current_user.authorized?` returns `true` for `attacker-github-login`, granting full access to the Shipit application.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
