### Title
Webhook signature verification is keyed on the attacker-controlled `repository.owner.login` field while handlers act on the equally attacker-controlled `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) directly out of the *unverified* JSON body. Once the signature check passes, every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers, etc.) resolves the target `Stack`/`Repository` using a *different* field from the same unverified body: `repository.full_name`. In a multi-organization Shipit deployment (as documented in `docs/setup.md` and `config/secrets.development.shopify.yml`, which support a `github:` hash keyed by multiple orgs each with its own `webhook_secret`), an attacker who controls one onboarded organization/installation knows that organization's own `webhook_secret`. They can therefore forge a signature that Shipit will accept (because `repository.owner.login` in the payload matches their own org) while setting `repository.full_name` to an arbitrary victim repository belonging to a *different* onboarded organization. This breaks the equality: `organization whose secret verified the signature == organization that owns the repository the handler writes to`.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` looks up the GitHub App config via:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is taken straight from the JSON body sent by the client — it is not authenticated at this point; it is merely used to pick which HMAC secret to validate against.

`Hook#DeliverySigner`/`GithubApp#verify_webhook_signature` only prove that the raw body was signed with *some* known secret; they never assert that the org owning that secret matches the repository referenced elsewhere in the same body: [2](#0-1) 

After signature verification succeeds, `create` re-parses the same raw body and dispatches to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Every handler resolves the affected stacks via `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Since Shipit supports multiple GitHub orgs in one instance, each with its own `webhook_secret` (`config/secrets.development.shopify.yml`, `docs/setup.md`), the signature-verification org (`repository.owner.login`) and the write-target org (derived from `repository.full_name`) are two independent, attacker-controlled fields with no cross-check that they refer to the same repository/org.

### Impact Explanation
An attacker who legitimately owns one onboarded GitHub organization (and thus knows/can obtain its `webhook_secret` for that installation) can forge a valid-signature webhook whose `repository.full_name` points at a stack belonging to a *different* onboarded organization. Depending on event type this can:
- Inject fake commit statuses / check-runs for a victim repository's commits, satisfying `ci.require`/`merge.require` checks and enabling an **unauthorized deploy or merge** of a victim's stack (`StatusHandler`, `CheckSuiteHandler`, merge-queue related handlers).
- Inject fake push events, creating bogus commits/records for a victim's stack, corrupting deploy history or triggering `ContinuousDeliveryJob`-driven auto-deploys for arbitrary shas.
This crosses the "unauthorized deploy/rollback/merge" and "cross-repository writes" impact bar defined in the rules.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured with more than one GitHub organization/App installation (multi-tenant `github:` config), which is an explicitly documented and supported deployment mode. Any user who is an admin of one such onboarded org already knows that org's `webhook_secret` (they configured/received it during App setup) and can freely POST arbitrary bodies to the public `/webhooks` endpoint — no Shipit session, `ApiClient` token, or repository write access on the *victim* repo is required, satisfying the "unprivileged attacker" scope constraint.

### Recommendation
Bind the two fields together: after selecting the app/secret via `repository.owner.login`, verify that `repository.full_name` (and `organization.login`, if present) actually belongs to that same organization before dispatching to handlers — e.g., require `repository.full_name.split('/').first.casecmp?(repository_owner)`, or better, resolve the target `Stack`/`Repository` first and then re-verify the signature using the secret configured for *that* repository's known/stored organization/installation, rejecting the payload if they diverge.

### Proof of Concept
1. Deploy Shipit with two orgs configured, e.g. `orgA` (attacker's own installation, secret known to attacker) and `orgB` (victim's installation).
2. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker signs the raw body with `orgA`'s known `webhook_secret` and sends it to `POST /webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` calls `Shipit.github(organization: 'orgA')` (from `repository.owner.login`), verifies successfully against `orgA`'s secret.
5. `StatusHandler` (via `Handler#stacks`/`#repository_name`) looks up `Repository.from_github_repo_name('orgB/victim-repo')` and records a forged successful status for the victim's commit, potentially unblocking a deploy/merge that requires that CI context — with no possession of `orgB`'s credentials at all.

      github_app = Shipit.github(organization: repository_owner)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
