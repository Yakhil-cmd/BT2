### Title
Operator-precedence bug in `provision?` allows PR label alone to create a Review Stack even when `review_stacks_enabled` is `false` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` intends `repository.review_stacks_enabled` to be a master switch gating all three provisioning behaviors, but Ruby operator precedence (`&&` binds tighter than `||`) makes `review_stacks_enabled` apply only to the `allow_all` branch. When the behavior is `allow_with_label`, any PR author can add a label matching `repository.provisioning_label_name` on their own PR and get a stack created regardless of `review_stacks_enabled`. The same bug is present in `ReopenedHandler#unarchive?`.

### Finding Description
The broken binding, stated as an equality that the operator expects but the code fails to enforce:

`stack_created == (repository.review_stacks_enabled AND provisioning_condition_matched)`

The actual code in `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:65-70`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` has higher precedence than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is only ANDed with the first disjunct. The second and third disjuncts—which govern the `allow_with_label` and `prevent_with_label` behaviors—are evaluated with no dependency on `review_stacks_enabled` at all. `NullRepository#review_stacks_enabled` returning `false` for untracked repos doesn't help either, because `provisioning_behavior_allow_with_label?`/`provisioning_behavior_prevent_with_label?` also return `false` there.

Exploit flow: operator sets `repository.review_stacks_enabled = false` (intending to fully disable review-stack automation) but leaves `repository.provisioning_behavior = :allow_with_label` and `provisioning_label_name = "some-label"` from a prior configuration, or sets `allow_with_label` without realizing `review_stacks_enabled` no longer gates it. An external contributor opens a PR against the repo and (per the audit's stated attacker capability) attaches a label whose `name` equals `repository.provisioning_label_name`. `pull_request_has_provisioning_label?` reads `params.pull_request["labels"]`, entirely attacker-controlled webhook payload data, at `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:72-78`. `provision?` returns `true` and `ReviewStackAdapter#find_or_create!` creates a `Stack` bound to the attacker's `head.ref`/environment, which subsequently gets queued for provisioning and can run the repository's `shipit.yml` tasks. [2](#0-1) [3](#0-2) 

No other guard intervenes: `respond_to_pull_request_opened?` only checks `params.action == "opened" && provision?`, `provisioning_label_name`/`provisioning_behavior` are plain attributes with no cross-field validation tying them to `review_stacks_enabled` in `app/models/shipit/repository.rb`, and there's no signature check inside the handler (webhook signature verification happens upstream and doesn't restrict payload content). [4](#0-3) [5](#0-4) 

The same precedence bug recurs in `ReopenedHandler#unarchive?`: [6](#0-5) 

### Impact Explanation
The affected repository's own `review_stacks_enabled = false` setting is silently bypassed for any repository configured with `allow_with_label` or `prevent_with_label`, allowing an external, unprivileged PR author to force creation and provisioning of a `Stack` and trigger execution of the repository's `shipit.yml` tasks (which can invoke `Command`/deploy tooling) against attacker-influenced branch/environment data. This is scoped to the single repository whose configuration matches the precondition (no cross-tenant mutation), but for that repository it is a full authorization bypass of the operator's intended "review stacks disabled" control, matching the Critical category of "an unauthorized deploy... bypassing the operator's disabled review_stacks setting."

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` with a non-nil `provisioning_label_name`, while `review_stacks_enabled` is `false` — a plausible, even likely, misconfiguration state (e.g., an operator disabling review stacks without resetting behavior/label fields, or intentionally trying to lock down while leaving stale settings). Attacker cost is a single PR open plus a label add on their own PR, fully repeatable per PR/environment number.

### Recommendation
Fix operator precedence by explicitly grouping so `review_stacks_enabled` gates every branch, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
```ruby
test "does not create stacks for allow_with_label repos when review_stacks_enabled is false, even with matching label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Running this against current code fails (`Shipit::Stack.count` increments by 1), demonstrating `repository.review_stacks_enabled == false` yet a `Stack` is created — proving the binding is broken.
