### Title
Webhook signature is verified against the payload's `repository.owner.login`/`organization.login`, but processing acts on the independent `repository.full_name` field, allowing cross-organization stack actions - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . That value picks the per-organization webhook secret via `Shipit.github(organization: repository_owner)` [2](#0-1) . However, every handler that actually acts on the payload resolves the target repository/stacks using a *different* field, `payload.dig('repository', 'full_name')` [3](#0-2) . Nothing in the code enforces that `repository.owner.login` (used to choose/verify the signing secret) is consistent with `repository.full_name` (used to select which stacks are acted upon).

### Finding Description
In a multi-tenant Shipit deployment, `config/secrets*.yml` supports configuring multiple independent GitHub organizations, each with its own `webhook_secret` [4](#0-3) . `Shipit.github(organization:)` looks up the config entry matching the organization name supplied, and `verify_webhook_signature` HMACs the raw POST body against that organization's own secret [5](#0-4) .

Because the entire raw request body is attacker-controlled JSON, and the HMAC only proves "this body was signed with organization X's webhook secret," an attacker who legitimately controls (or knows the webhook secret of) one onboarded organization ("orgA") can craft a payload where:
- `repository.owner.login` = `"orgA"` (or `organization.login` = `"orgA"`) — satisfies `verify_signature`, which picks orgA's secret and validates correctly since the attacker signs with their own known secret.
- `repository.full_name` = `"orgB/victim-repo"` — an arbitrary different organization/repository entirely unrelated to orgA.

`Handler#stacks` resolves the acted-upon repository purely from `repository.full_name`: `Repository.from_github_repo_name(repository_name)&.stacks` [3](#0-2) . For example, `PushHandler#process` finds all matching stacks by branch and calls `stack.sync_github(expected_head_sha: params.after)` using the attacker-supplied `after` SHA [6](#0-5) . This breaks the binding: *the organization that authenticated the webhook* ≠ *the repository whose stacks are written to*.

### Impact Explanation
This is a cross-repository/cross-organization write: an attacker who is a legitimate (low-trust) tenant of the Shipit instance for their own organization can forge webhook events (push, status, check_suite, membership, pull_request, etc.) that are processed as if they originated from a completely different organization's repository, because signature verification and payload processing are keyed off two different, unlinked fields in the same attacker-controlled JSON body. Depending on the handler, this can enqueue `GithubSyncJob` for a victim stack with an attacker-chosen head SHA, forge CI `status`/`check_suite` events that unblock deploy safety checks, or manipulate `Membership`/`Team` records — all attributed to a repository the attacker does not control. In deployments where CI status gating feeds into deploy trigger logic, this can escalate to an unauthorized deploy against a repository/organization the attacker has no legitimate access to.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured for more than one GitHub organization (a documented, supported configuration) and requires the attacker to control or know the webhook secret of at least one onboarded, lower-trust organization. This is a realistic scenario for shared/multi-tenant Shipit deployments where different teams/orgs are onboarded with differing trust levels but share one Shipit instance.

### Recommendation
Cross-validate that `repository.owner.login` (or `organization.login`) used for signature-secret selection is identical to the owner segment of `repository.full_name` before dispatching to handlers. Alternatively, verify the signature using a single global secret model, or bind the resolved GitHub App config to the actual repository being acted upon rather than to an independently attacker-suppliable field, and reject payloads where these two do not match.

### Proof of Concept
1. Shipit is configured with two organizations, `orgA` (attacker-controlled/known secret) and `orgB` (victim, has stacks tracked in Shipit).
2. Attacker builds a raw JSON push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `orgA`'s known webhook secret over this exact raw body.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and successfully verifies the signature against the attacker-known secret [2](#0-1) .
5. `PushHandler` is invoked with the full payload; `stacks` resolves via `full_name` = `"orgB/victim-repo"` [3](#0-2) , and `stack.sync_github(expected_head_sha: params.after)` runs for the victim's stacks using the attacker's forged SHA [6](#0-5) , despite the request never being authenticated for `orgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
