### Title
AA can freeze/lose bundled funds because it composes payments of a foreign asset without validating its `is_transferrable`/`transfer_condition`, letting a malicious asset issuer permanently block AA payouts — ([File: aa_composer.js])

### Summary
An unprivileged asset issuer can define an asset whose `transfer_condition` (or `is_transferrable`/`spender_attested`) can be toggled or is unsatisfiable by design (e.g., referencing a data feed the issuer controls), fund an AA with it, and cause the AA’s payout unit to fail consensus validation whenever the AA tries to forward that asset. Because the AA composer bundles the poisoned-asset payment together with other outputs/base-currency change in a single response unit, the entire response bounces, freezing legitimate payouts bundled with it — directly analogous to the OpenQ report where a pausable ERC20/NFT blocks `claimBalance`/`claimTiered` and reverts the whole claim transaction.

### Finding Description
When an AA composes an outgoing unit in `sendUnit`, for every non-base payment message it loads the asset definition via `storage.loadAssetWithListOfAttestedAuthors` and only rejects the payload if the asset `is_private` (`aa_composer.js` around the message-loop that calls `storage.loadAssetWithListOfAttestedAuthors` and checks `objAsset.is_private`) [1](#0-0) . It does **not** check `is_transferrable`, `spender_attested`, or evaluate `transfer_condition` before completing and broadcasting the payment. Those checks are only performed later, at network-wide consensus validation time in `validatePaymentInputsAndOutputs`, where a non-transferable asset that isn't being returned to the definer is rejected [2](#0-1) , and where `transfer_condition` is evaluated via `Definition.evaluateAssetCondition`, and failure of the condition rejects the whole payment message (`"transfer or issue condition not satisfied"`) [3](#0-2) .

Because this failure surfaces only when `validateAndSaveUnit` is called on the fully composed unit, the AA composer's `sendUnit` function treats any such failure as a fatal error for the entire response and calls `bounce(err)` [4](#0-3) . `bounce()` discards the previously computed `objStateUpdate`, restores balances, and produces only a minimal fallback unit that returns unused base-currency (minus bounce fees) to the trigger address — none of the bundled payments (including the legitimate ones for other assets) go through [5](#0-4) .

The asset's `transfer_condition` is an address-style condition (`Definition.validateDefinition` array of ops) that can reference conditions such as data-feed values authored by the asset definer, similar to `issue_condition`/`transfer_condition` validated at asset-definition time [6](#0-5) . A malicious definer can craft a `transfer_condition` that is satisfiable when funding the AA (so the deposit succeeds) but is later made unsatisfiable (e.g., by publishing/withholding a data feed value under their control), exactly mirroring the `pause()` toggle in the OpenQ report's malicious ERC20/NFT.

### Impact Explanation
Any AA (e.g., an escrow/bounty/vault-style AA analogous to OpenQ's bounty contract) that accepts deposits of arbitrary assets and later needs to pay them out — potentially bundled with base-currency or other-asset outputs in the same response unit — can have its entire payout response permanently blocked by depositing one asset with an unsatisfiable/togglable `transfer_condition` or with `is_transferrable=false`. This freezes funds inside the AA (the poisoned asset and any other funds bundled in the same message set) and denies legitimate claimants their payout, exactly as in the OpenQ finding where a single malicious token blocks `claimBalance`/`claimTiered` for the whole developer claim. This qualifies as AA fund freezing/loss of the sort explicitly in scope.

### Likelihood Explanation
Any address (not privileged) can issue an asset via a normal `asset` message and choose arbitrary `transfer_condition`/`is_transferrable` values at essentially the cost of one small unit, then fund a target AA with it through a normal payment trigger, exactly as any funder could in OpenQ by supplying a malicious ERC20/NFT. Because the AA composer performs no pre-check of `is_transferrable`/`transfer_condition` satisfiability before composing and broadcasting the payout, the vulnerable path is reachable by any unprivileged asset issuer targeting any AA that (a) accepts foreign-asset deposits and (b) bundles payouts of multiple assets/outputs together in one response.

### Recommendation
Before including a foreign asset in an outgoing AA payment (`completePaymentPayload`/`sendUnit` in `aa_composer.js`), check `objAsset.is_transferrable` for the intended destination and pre-evaluate `objAsset.transfer_condition` (mirroring the same logic used in `validatePaymentInputsAndOutputs`) so that unpayable assets are excluded from the bundled response rather than causing the whole unit to fail and bounce. Additionally, isolate asset-specific payment messages from unrelated ones so that a failure to send one poisoned asset does not force the entire multi-message response (including base-currency payouts) to bounce.

### Proof of Concept
1. Attacker issues asset `X` via an `asset` message with `is_transferrable: true` (initially) and `transfer_condition` referencing a data feed authored by the attacker's own address, e.g., `["in data feed", [[attacker_address], "oracle_feed", "=", "1"]]` (validated at definition time per `validateAssetDefinition`) [6](#0-5) .
2. Attacker publishes `oracle_feed=1` and sends a payment of asset `X` to a target AA (e.g., an escrow/bounty AA) as part of a trigger; deposit succeeds because the condition currently holds.
3. Before the AA processes a later trigger that would pay out asset `X` (bundled with other outputs) to a legitimate claimant, the attacker stops publishing `oracle_feed=1` (or publishes a different value), making the `transfer_condition` unsatisfiable.
4. When the AA composes its response and calls `sendUnit`, it includes the asset `X` payment without checking `transfer_condition` (`aa_composer.js` lines 1323–1331), then `validateAndSaveUnit` fails at `evaluateAssetCondition` (`validation.js` lines 2643–2659), triggering `bounce(err)` (`aa_composer.js` lines 1405–1411), which discards the entire bundled response including any legitimate asset/base-currency payouts, freezing all bundled funds and blocking the claimant.
