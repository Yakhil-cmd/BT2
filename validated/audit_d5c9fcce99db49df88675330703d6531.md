### Title
First-Writer-Wins Fixation of Shared-Address Signing-Path Routing via `new_shared_address` Device Message - (File: wallet_defined_by_addresses.js)

### Summary
The GHSA-98j2-3j3p-fw2v issue is a class of bug where an unauthenticated/unprivileged party can supply an identifier that is accepted as the key for a piece of state that the application will later trust as authoritative (session fixation: attacker sets an ID before the real "session" exists, and the system keeps trusting the attacker-supplied binding). The same "first writer wins on an externally-influenced key" pattern exists in ocore's shared-address (multisig) negotiation protocol. Any correspondent (paired) device can send a `new_shared_address` message whose contents are only checked for internal self-consistency (definition hashes to the claimed address, and per-path addresses match the definition) but never checked against who is actually authorized to be a co-signer for those paths. The message is written with `INSERT IGNORE`, so whichever `new_shared_address` message arrives first for a given `(shared_address, signing_path)` permanently wins, and any later — legitimate — message that would set the correct signer/device routing is silently dropped.

### Finding Description
`wallet_defined_by_addresses.js`'s `handleNewSharedAddress` [1](#0-0)  validates only that:
- `body.definition` hashes to `body.address` (`objectHash.getChash160`)
- each `signerInfo.address` in `body.signers` is a syntactically valid address
- the address at each signing path matches what `extractAddressPathsFromDefinition` derives from the definition
- every address leaf in the definition has a corresponding entry in `body.signers`

It never verifies that the sender of the message is actually one of the parties named in the definition, nor that the `device_address` values supplied for signing paths that are *not* the receiver's own addresses are correct. `determineIfIncludesMeAndRewriteDeviceAddress` only rewrites the device address for paths that resolve to the *receiver's own* `my_addresses`; for every other member address (i.e., third-party co-signers), the attacker-controlled `device_address` supplied in `body.signers[signing_path].device_address` is accepted as-is.

The resulting record is persisted by `addNewSharedAddress` using `INSERT IGNORE` on both `shared_addresses` and `shared_address_signing_paths` (whose primary key is `(shared_address, signing_path)`): [2](#0-1) . Because the address (`shared_address`) is deterministically computed as `chash160(definition)`, any attacker who can predict or observe a multisig/shared-address definition that a victim will later legitimately create (e.g. definitions built from previously observed addresses, prosaic/arbiter contract shared addresses, or brute-forced/guessed templates) can pre-emptively send a forged `new_shared_address` message naming themselves as the `device_address` for signing paths belonging to other, real co-signers. Because of `INSERT IGNORE`, this attacker-planted row wins permanently; the legitimate `new_shared_address` message that arrives afterward (from the real address owner or via `sendNewSharedAddress`/`forwardNewSharedAddressToCosignersOfMyMemberAddresses`) is dropped.

This routing table (`shared_address_signing_paths.device_address`) is exactly what `findAddress()` [3](#0-2)  uses to decide, for a non-local signing path, which device to forward the signing request to (`ifRemote`). It is also consulted by `getSigner().sign()` when composing a transaction that spends from the shared address [4](#0-3) , which sends `walletGeneral.sendOfferToSign(device_address, ...)` including the unsigned unit and, for private assets, `assocPrivatePayloads` — i.e., the full private payment chain content — directly to whatever `device_address` is stored, without any additional authorization check at send time.

### Impact Explanation
Because the signing-path→device routing is fixated by whichever `new_shared_address` message arrives first, an attacker (any paired device) can cause a victim's wallet to send a "sign" request for a shared/multisig address to the attacker's device instead of the legitimate co-signer's device:
- Confidential private-payment chain data (`assocPrivatePayloads`, i.e. the actual amounts/asset/chain contents of private-asset transactions) is disclosed to the attacker instead of the intended cosigner, breaking private-payment confidentiality.
- The attacker can intercept the multisig signing flow and either withhold a signature (denial of the transaction, i.e. fund freezing for that shared address) or attempt to manipulate the negotiation (e.g., refuse-to-sign injection, `eventBus.emit('refused_to_sign', ...)`), disrupting the victim's ability to spend from the shared address.
- Because the attacker fully controls the definition/`device_address` mapping they submit and this state is established before the legitimate flow runs, this is a fixation of trust routing analogous to CWE-384: the attacker "claims" the identifier (shared_address, signing_path) first, and the real owner's later legitimate claim is discarded by `INSERT IGNORE`.

### Likelihood Explanation
Exploitability requires the attacker to be a paired correspondent device of the victim (a normal, unprivileged relationship in ocore's device-messaging model) and to know or predict the multisig/shared-address definition and per-path addresses that the victim will eventually use (achievable in common flows such as prosaic/arbiter contract shared addresses, since deposit addresses/definitions are exchanged over the same paired-device channel before the parties finalize the arrangement, or in any protocol that reuses previously-observed addresses in definitions). The attack requires no unit posting, no hub/node compromise, and no special privileges beyond a normal device pairing — it is squarely reachable from the "wallet and contract message handling" attack surface named in scope.

### Recommendation
- Do not accept unauthenticated `device_address` bindings for signing paths that are not the receiver's own addresses; require independent confirmation (e.g., from the owning device itself, or via a signed statement) before trusting `body.signers[path].device_address` for third-party members.
- Replace `INSERT IGNORE` on `shared_address_signing_paths`/`shared_addresses` with logic that detects and rejects/reconciles conflicting `device_address` values for the same `(shared_address, signing_path)`, rather than silently keeping the first writer's value.
- Require the initiating negotiation (`createNewSharedAddressByTemplate`/`approvePendingSharedAddress` flow) to be the source of truth, and treat unsolicited `new_shared_address` messages that were not preceded by a matching negotiation with heightened scrutiny (e.g., prompt user confirmation before adding a shared address whose signing-path devices were never explicitly negotiated).

### Proof of Concept
1. Attacker device A pairs with victim device V (normal correspondent pairing).
2. Attacker observes/predicts an address definition `D` that names V's own address `addrV` at path `r.1` and a third co-signer address `addrC` at path `r.0`, such that `shared_address = chash160(D)`.
3. Attacker sends V a `new_shared_address` message: `{address: shared_address, definition: D, signers: {"r.0": {address: addrC, device_address: A_device_address}, "r.1": {address: addrV, device_address: ...}}}`.
4. `handleNewSharedAddress` passes all checks (definition hash matches, addresses match paths) and calls `addNewSharedAddress`, which `INSERT IGNORE`s `shared_address_signing_paths(shared_address, 'r.0', addrC, ..., A_device_address)`.
5. Later, the real co-signer for `addrC` sends the legitimate `new_shared_address` (or V independently negotiates the same shared address through the normal flow); due to `INSERT IGNORE` on the same primary key, V's stored `device_address` for path `r.0` remains `A_device_address`.
6. When V later spends from `shared_address` and needs `addrC`'s signature, `findAddress`/`getSigner().sign()` sends the unsigned unit and any private payloads to `A_device_address` (attacker), not to the real cosigner.

Note: I could not fully trace the exact `wallet.js` dispatch site (`case 'new_shared_address':`) that calls `handleNewSharedAddress` within the tool budget available, so the precise message-subject wiring in `wallet.js`'s `handleMessageFromHub` should be double-checked in a full read of that file; however, the grep confirmed `wallet_defined_by_addresses.js` is referenced once from `wallet.js`, consistent with a single dispatch call site for this device-message subject.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
