### Title
Webhook signature verification authenticates the wrong field, allowing cross-organization/cross-repository forgery of GitHub events (status, push, check_suite) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects *which* GitHub App/secret to check the HMAC signature against using an attacker-supplied field in the JSON body (`repository.owner.login` / `organization.login`), while the handlers that actually write data (`PushHandler`, `CheckSuiteHandler`, and especially `StatusHandler`) act on a *different*, also attacker-controlled field (`repository.full_name`, or in `StatusHandler`'s case, no repository scoping at all — just a bare commit `sha`). The signature never binds the "organization that authenticated" to the "repository/commit that is written," exactly the class of bug in the source report (a value used for one purpose is trusted for a completely different, unguarded purpose).

### Finding Description
Verification path, `app/controllers/shipit/webhooks_controller.rb:24-49`: [1](#0-0) [2](#0-1) 

The organization used to pick the GitHub App/secret (`repository_owner`) comes straight from the untrusted JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. In a multi-org Shipit deployment (explicitly documented and supported — "Using Multiple GitHub Applications", `docs/setup.md:181-209`), each org has its **own** `webhook_secret`, which that org's own maintainers legitimately possess (they generate it when creating their GitHub App).

Once the signature passes (verified against the *attacker-chosen* org's own secret), the actual data-mutating code never re-checks that organization against the data it writes:

- `Handler#repository_name`/`#stacks` derive the target `Stack`/`Repository` from `payload.dig('repository', 'full_name')` — a wholly separate, attacker-controlled field: [3](#0-2) 

- `PushHandler#process` and `CheckSuiteHandler#process` use that `stacks` scope (keyed on `full_name`, not on the verified `repository_owner`) to trigger `sync_github` / `schedule_refresh_check_runs!`: [4](#0-3) [5](#0-4) 

- `StatusHandler#process` is worse: it does not scope by repository at all, it simply looks up **any** `Commit` in the entire install matching the attacker-supplied `sha` and writes a status onto it: [6](#0-5) 

So the equality that should hold — *organization whose secret verified this request* == *organization/repository/commit whose records get mutated* — is never enforced. An org that legitimately controls its own GitHub App/webhook secret (an "unprivileged" party from Shipit's perspective — they hold no Shipit session, `ApiClient` token, or the *target* org's secret) can hand-craft a JSON body where `organization.login`/`repository.owner.login` = their own org (so `Shipit.github(organization: repository_owner)` picks their own app and `verify_webhook_signature` validates against their own known secret), but set `repository.full_name` (for push/check_suite) or the raw `sha` (for status) to point at a victim organization's stack/commit.

Additionally, even without any multi-org secret at all, `GithubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the selected org (`return true unless webhook_secret`) — and per `docs/setup.md`, the webhook secret is explicitly optional — further widening who can supply the attacker-chosen `repository_owner`/`full_name` pair with zero secret knowledge whatsoever.

### Impact Explanation
This breaks the binding "organization authenticated" vs "repository that is written," resulting in cross-repository/cross-organization writes:
- `StatusHandler` lets any org with its own valid (self-created) webhook credentials attach an arbitrary CI status (e.g., `state: "success"`, `context: "ci/required-check"`) to **any commit sha in the entire Shipit install**, including commits belonging to a completely unrelated tenant's stack, since the lookup is a global, unscoped `Commit.where(sha: ...)`. Forged green statuses can satisfy `required_statuses` checks (`deploy_spec.rb`) gating deploy/merge safety for victim stacks, moving toward an unauthorized deploy/merge.
- `PushHandler`/`CheckSuiteHandler` let the same attacker enqueue `GithubSyncJob`/check-run refreshes against a victim's stack by supplying that victim's `repository.full_name`, again authenticated only by the attacker's own org secret.

This satisfies the "Critical: cross-repository writes / an unauthorized deploy" impact bar, since it is achievable strictly through the engine's own signature-selection and handler-scoping logic, without needing the victim's secret, a Shipit session, or an `ApiClient` token.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured for multiple GitHub organizations (a documented, supported feature), and (2) the attacker to be one such onboarded tenant org holding their own legitimately-generated `webhook_secret` (not a privileged Shipit credential and not the victim's secret). Given that condition, forging the payload is trivial (a single crafted HTTP POST with a correctly computed HMAC using the attacker's own known secret). No target-side secret, session, or token is needed. I was not able to fully trace, within the remaining time, every downstream consumer of forged `Status` records (e.g., the exact merge-queue/auto-deploy gating chain in `MergeRequest`/`Stack`), so the precise blast radius of the forged CI-success status should be validated against `app/models/shipit/status/group.rb`, `app/models/shipit/merge_request.rb`, and `app/models/shipit/deploy_spec.rb`'s `required_statuses` usage.

### Recommendation
In `WebhooksController#verify_signature`/`Handler`, bind the two identities together: after verifying the signature against the org selected by `repository_owner`, every handler must re-derive its target scope from that *same verified* `repository_owner`/organization, not from `repository.full_name` or a bare `sha`, and must reject/ignore the event if the repository's actual owner (looked up from Shipit's own `Repository` record, not from attacker-supplied JSON) doesn't match the verified `repository_owner`. `StatusHandler` in particular must scope its `Commit` lookup by the repository resolved through the verified organization, not perform a global, cross-tenant `Commit.where(sha: ...)`.

### Proof of Concept
1. Deploy Shipit configured for two GitHub organizations, `attacker-org` (with `webhook_secret: S`) and `victim-org` (with `webhook_secret: T`, unknown to attacker), per `docs/setup.md`'s multi-org configuration.
2. Attacker (who owns `attacker-org`'s GitHub App and therefore knows `S`) crafts:
```json
{
  "sha": "<sha of a commit in victim-org's Shipit-tracked stack>",
  "state": "success",
  "context": "ci/required-check",
  "organization": {"login": "attacker-org"},
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner = "attacker-org"`, fetches `attacker-org`'s `GithubApp`, and the signature validates successfully (attacker knows `S`).
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)` — finds the victim's commit regardless of the verified organization — and calls `commit.create_status_from_github!(params)`, writing a forged "success" status onto `victim-org`'s commit.
