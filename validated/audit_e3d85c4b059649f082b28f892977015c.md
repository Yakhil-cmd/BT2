## Title
Merkle tree leaf/internal-node domain confusion allows forging fake proof membership - (File: `merkle.js`)

### Summary
`merkle.js`'s Merkle-tree construction, exposed to oscript/AA authors and triggerers via the `is_valid_merkle_proof` formula operator, hashes leaves and internal nodes with the exact same function and no domain-separation tag distinguishing "this is a leaf" from "this is a concatenation of two child hashes." This is structurally the same class of flaw as the reported Poseidon issue: a hash construction that fails to make different logical inputs (a raw leaf value vs. a pair of sibling hashes) produce provably distinct pre-images, enabling an attacker to forge a "valid" membership proof for a value that was never actually inserted as a leaf.

### Finding Description
`getMerkleRoot`/`getMerkleProof` build the tree bottom-up using a single `hash()` function for both leaves and internal nodes: [1](#0-0) 

`verifyMerkleProof` walks up from the claimed element, hashing it together with the supplied siblings, with no tag to indicate tree depth or node type: [2](#0-1) 

Because an internal node's hash is computed as `hash(childHashLeft + childHashRight)` and a leaf's hash is computed as `hash(element)`, there is no cryptographic distinction between "a leaf whose content happens to equal the base64 string `childHashLeft+childHashRight`" and "the actual internal node combining those two children." An attacker who knows any two adjacent hash values in the tree (trivially obtainable from any legitimate Merkle proof, since siblings are transmitted in plaintext) can:
1. Compute `fake_element = hash(leaf_i) + hash(leaf_{i+1})` (the concatenation string that is the true preimage of their parent node).
2. Submit `fake_element` as the "element" together with a proof that is one level shorter (using the parent's position and the siblings from that level upward).
3. `verifyMerkleProof` will compute `hash(fake_element)`, which equals the real parent node hash, and the proof will verify successfully as if `fake_element` were a genuine originally-inserted leaf.

This primitive is directly reachable by an unprivileged AA trigger sender through the oscript `is_valid_merkle_proof` operator, which accepts attacker-controlled `element` and `proof` from trigger data and calls straight into `merkle.verifyMerkleProof`: [3](#0-2) 

### Impact Explanation
Any AA that uses `is_valid_merkle_proof` to check membership of a value in an allow-list/claim-list (e.g., "is this address/secret/amount part of the whitelisted set committed via its Merkle root") can be bypassed: an attacker can construct a synthetic "element" (the concatenation of two real sibling hashes) that verifies as a member of the tree without ever having been a legitimate leaf inserted by the AA author. If the AA logic branches on `is_valid_merkle_proof` result to release funds, grant permissions, or mark a claim as fulfilled, this enables unauthorized access to AA-held funds or state — a concrete AA fund-loss scenario, matching the required impact bar (analogous to how the Poseidon report's missing injective padding lets an attacker construct one value's hash to masquerade as a different, distinct value's hash).

### Likelihood Explanation
The attack requires no cryptographic break — only knowledge of at least one pair of adjacent leaves' hash values, which is inherent to how Merkle proofs work (siblings are disclosed as plaintext hashes as part of any legitimate proof). Any AA design that publishes example proofs, has a public leaf set, or leaks even two sibling hashes gives an attacker everything needed to fabricate a valid-looking proof for an unregistered "element." Likelihood is high wherever `is_valid_merkle_proof` is used for anything beyond a purely cosmetic/informational check.

### Recommendation
Introduce domain separation in the hash function used by `merkle.js`, e.g. prefix leaf hashes and internal-node hashes with distinct tags (`hash("0x00" + element)` for leaves vs `hash("0x01" + left + right)` for internal nodes), matching standard second-preimage-resistant Merkle tree constructions (RFC 6962-style). This must be a coordinated protocol change since it alters all merkle roots/proofs; document the required leaf/node tagging convention for `merkle.js`, `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof`, and bump any relevant version guard so old and new proofs are not silently interchangeable.

### Proof of Concept
1. AA author commits to a Merkle root of a whitelist containing (among others) adjacent leaves `L0="alice"` and `L1="bob"`, and exposes/allows verification of proofs against this root via `is_valid_merkle_proof`.
2. Attacker requests (or otherwise learns, e.g. from a previous legitimate proof interaction) the Merkle proof for `L0`, obtaining `h0 = hash("alice")` and `h1 = hash("bob")` (the sibling of `L0`'s proof).
3. Attacker computes `fake_element = h0 + h1` (an 88+-character base64 string) and constructs a proof one level shallower than `L0`'s original proof (same remaining siblings/index above that level).
4. Attacker submits an AA trigger with `data.element = fake_element` and `data.proof` as constructed; the AA's `is_valid_merkle_proof(trigger.data.element, trigger.data.proof)` call returns `true`, even though `fake_element` was never inserted as a genuine whitelist leaf — `formula/evaluation.js` line 1768-1806 forwards straight into `merkle.verifyMerkleProof` (`merkle.js` line 84-102), which cannot distinguish the crafted concatenation from a real leaf hash.

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
