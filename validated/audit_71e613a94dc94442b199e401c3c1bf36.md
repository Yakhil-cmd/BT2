### Title
Unfiltered pull-request label names inject arbitrary environment variable keys (e.g. `RUBYLIB`) into the `deploy.override` process, bypassing Bundler's environment sanitization - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an environment-variable key with no allowlist, and that hash flows unfiltered into `Command#start`, where it is merged *after* the Bundler-sanitized `BASE_ENV`, letting a fork PR author override security-relevant variables such as `RUBYLIB` on the deploy host.

### Finding Description
The broken binding: `Command#unbundled_env` should satisfy `unbundled_env.keys ⊆ Bundler.unbundled_env.keys` for all Shipit-provided env inputs, but instead `unbundled_env = BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [1](#0-0)  lets the caller-supplied `@env` win for any key, including ones `Bundler.unbundled_env`/`Bundler.clean_env` normally strips (e.g. `RUBYLIB`, `RUBYOPT`).

`@env` reaching `Command` originates from `ReviewStack#env`, which merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into the stack env with no key allowlist: [2](#0-1) . Those label names are persisted verbatim from the webhook body by `LabelCapturingHandler#capture_labels`, which only validates that `labels[].name` is a `String` — any string, including `rubylib` — is accepted: [3](#0-2)  and the schema at [4](#0-3) .

`TaskCommands#env` (used to build every `deploy`/`rollback`/`dependencies` step, including `deploy.override`) merges `@stack.env` early and only re-overrides a fixed, unrelated set of keys afterward (`SHIPIT_USER`, `EMAIL`, `BUNDLE_PATH`, `SHIPIT_LINK`, `TASK_ID`, `IGNORED_SAFETIES`, `GIT_COMMITTER_*`), leaving any other label-derived key such as `RUBYLIB` untouched all the way to `Command.new`: [5](#0-4) . `Command#initialize` stores it as-is (`@env = env.transform_values { |v| v&.to_s }`) with no filtering: [6](#0-5) , and `Command#start` passes the resulting `unbundled_env` straight to `PTY.spawn`: [7](#0-6) .

Attacker's exact request: open a fork PR against a repository configured with `provisioning_behavior = allow_with_label`, include a `deploy.override` step in the fork's `shipit.yml` at the PR head, and apply/rename a label so its name uppercases to `RUBYLIB` (e.g. label text `rubylib`). No Shipit credentials, GitHub App key, or webhook secret are needed beyond the ability to label one's own PR (existing tests already exercise this exact webhook flow, e.g. `LabeledHandlerTest`/`LabelCapturingHandlerTest`, confirming the label-to-stack pipeline is reachable by ordinary PR/label webhooks) [8](#0-7) .

The injected value is fixed to the literal string `"true"` (not the attacker's chosen path text) — confirmed by the existing repo test asserting `env["WIP"] == "true"` [9](#0-8) . This means the attacker controls the environment-variable *name*, not its content. Because the review stack's working directory is the attacker's own fork checkout (their PR branch content), the attacker can still weaponize `RUBYLIB=true` by committing a `true/` directory in their branch containing files that shadow common library names (e.g. `true/openssl.rb`, `true/json.rb`); any `ruby`/`bundle`/`rake` invocation inside `deploy.override` with `RUBYLIB=true` resolves `./true` relative to the process cwd and will load the attacker's shadow file on `require`, achieving code execution in the deploy process. None of `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema restrict label text content, and no `EnvironmentVariables#permit`-style allowlist exists between `ReviewStack#env` and `Command#unbundled_env`.

### Impact Explanation
An unprivileged fork-PR author can force arbitrary environment-variable keys (not just `RUBYLIB` — any key, e.g. `LD_PRELOAD`, `GIT_SSH_COMMAND`, `BUNDLE_GEMFILE`) into the spawned deploy process on the Shipit host, overriding Bundler's environment sanitization. Combined with attacker control over the checked-out fork content, this is chainable into arbitrary code execution during any deploy/rollback/dependency step of the review-stack, i.e. Critical RCE on the deploy host via `Command`/`PTY.spawn`. Blast radius is scoped to the review stack's deploy process (which itself may have access to shared credentials/`GITHUB_TOKEN` used by the deploy host), and is repeatable on every labeled PR against any repository with `allow_with_label` enabled.

### Likelihood Explanation
Requires a repository configured with `provisioning_behavior: allow_with_label` and review stacks enabled — a supported, documented configuration, not a misconfiguration. Attacker cost is minimal: open a PR from a fork, add one label with the right text, and include a `deploy.override`/other step that invokes a ruby-based tool (`bundle`, `rake`, `ruby`) — a very common pattern in Shipit deploy pipelines. The primitive itself (env-key injection reaching `PTY.spawn`) is trivially and deterministically reproducible without any weaponization step.

### Recommendation
Do not derive environment-variable names from free-form pull-request label text. Either (a) drop the label-to-env feature entirely, or (b) enforce a strict allowlist/prefix (e.g. only `SHIPIT_LABEL_<safe-suffix>`) on the keys derived from `label_name.upcase`, and (c) make `Command#unbundled_env` authoritative for security-relevant variables (`RUBYLIB`, `RUBYOPT`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, etc.) by merging `BASE_ENV` **after** `@env` for that reserved set, so caller-supplied env can never override Bundler's sanitized values.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (or a new test/lib/shipit/command_test.rb case)
test "[allow_with_label] pull request label injects RUBYLIB into the deploy.override spawned process env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["rubylib"] # upcased -> "RUBYLIB"

  env = Shipit::TaskCommands.new(stack.trigger_continuous_delivery).env
  assert_equal "true", env["RUBYLIB"] # attacker-controlled key present, unfiltered

  command = Shipit::Command.new("env", env: env, chdir: Dir.tmpdir)
  command.start
  output = command.run
  assert_match(/^RUBYLIB=true$/, output) # confirms reaches PTY.spawn, i.e. Bundler's stripped RUBYLIB is overridden
end
```
Binding under test (both sides, before/after): expected `Command#unbundled_env["RUBYLIB"] == Bundler.unbundled_env["RUBYLIB"]` (nil/stripped); actual `Command#unbundled_env["RUBYLIB"] == "true"` because `@env.stringify_keys` is merged last in `lib/shipit/command.rb:104`. This mismatch is the vulnerability.

      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
