### Title
Webhook signature verification is a no-op for any organization without a configured `webhook_secret`, allowing forged `membership` webhooks to create/modify `Team` rows and grant attacker-controlled members team authorization - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally when the target organization has no `webhook_secret` configured, before ever inspecting the `X-Hub-Signature` header or the request body. `WebhooksController#verify_signature` uses this org-scoped check to gate `MembershipHandler`, which trusts `params.organization.login`, `params.team.id`, and `params.member.login` from the same unverified payload to create/update a `Team` and add a member to it.

### Finding Description
Claimed binding: `organization_that_cryptographically_verified_the_payload == organization_owning_the_Team_written_by_MembershipHandler`.

Trace:
- `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` — both fully attacker-controlled fields of the raw JSON body. [1](#0-0) [2](#0-1) 
- `verify_webhook_signature` is:
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  ...
end
``` [3](#0-2) 
When `@webhook_secret` for the resolved organization is blank (`nil`/empty), the method returns `true` before the `signature.split` line is ever reached — no `NoMethodError` path exists here, the check is simply skipped entirely, header present or absent, garbage or not.
- `MembershipHandler#find_or_create_team!` uses `params.organization.login` (the same attacker-controlled field used to resolve the "verifying" org) to set `team.organization`, and `params.team.id` to look up/create the `Team`; `params.member.login` is then added via `team.add_member(member)`. [4](#0-3) 

Because the "verification" for that organization is vacuous (always `true`), the binding is only nominally satisfied — the org name matches, but no secret-based proof ever occurred. An attacker who knows (or guesses) an organization configured in Shipit without a `webhook_secret` can POST to `/webhooks` with `X-Github-Event: membership` and a body naming that org, an arbitrary/target `team.id`, and their own GitHub login as `member.login`. This creates or reuses a `Team` row and calls `Team#add_member`, appending the attacker's account to that team's `members` association. [5](#0-4) 

No other guard intercepts this: `drop_unhandled_event` only checks that a handler exists for `membership`; `check_if_ping` doesn't apply; there is no `ExplicitParameters` check that ties `params.organization.login` to a pre-authenticated identity — the params schema only validates shape/types, not provenance. [6](#0-5) 

### Impact Explanation
For any organization whose `webhook_secret` is unset in Shipit's GitHub app configuration, an unauthenticated attacker can forge a `membership` webhook to add themselves (or any GitHub login) as a member of a `Team` row keyed by an arbitrary `github_id`. If that `github_id` matches (or is later matched against) an entry referenced by `Shipit.github_teams`, this is a direct escalation into team-scoped authorization for a tenant the attacker never proved control over — matching the High severity bucket ("escalation into `Shipit.github_teams`-adjacent authorization"). The attack is repeatable against every organization lacking a `webhook_secret`, and against arbitrary `team.id`/`member.login` combinations, with no rate limit on `/webhooks`.

### Likelihood Explanation
Exploitability strictly depends on Shipit runtime configuration: at least one organization's GitHub app config must have no `webhook_secret` set (the code explicitly treats this as an intentional "skip verification" branch, `webhook_secret = @config[:webhook_secret].presence`, rather than raising or defaulting to deny). This is a plausible configuration state — the design permits unset secrets, and nothing in the engine enforces that all configured organizations must have one. Attacker cost is a single unauthenticated POST with no GitHub credentials, no signature, and no timing requirements; it is trivially repeatable. I was not able to fully trace `Shipit.github(organization:)`'s behavior for organizations entirely absent from configuration (i.e., whether unlisted orgs raise `GithubOrganizationUnknown` or fall back to a default with no secret) within the available iterations — this affects whether the attack surface is "any org name" or "only orgs explicitly configured without a secret," but does not change that the `verify_webhook_signature` short-circuit itself is a genuine, unconditional bypass for any org that resolves with `webhook_secret` blank.

### Recommendation
Remove the `return true unless webhook_secret` short-circuit in `GitHubApp#verify_webhook_signature`; treat a missing `webhook_secret` as a hard misconfiguration that rejects all webhooks for that organization (fail closed, not fail open). Additionally, require `X-Hub-Signature-256`/`sha256` and reject requests with a missing/blank signature header explicitly, rather than relying on `signature.split` never being reached.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative addition)
test "membership webhook is accepted with no signature when org has no webhook_secret" do
  Shipit.stubs(:github).with(organization: 'no-secret-org').returns(
    Shipit::GitHubApp.new('no-secret-org', {}) # config without :webhook_secret
  )

  @request.headers['X-Github-Event'] = 'membership'
  # deliberately omit X-Hub-Signature entirely

  body = {
    action: 'added',
    team: { id: shipit_teams(:shopify_developers).github_id, name: 'x', slug: 'x', url: 'http://x' },
    organization: { login: 'no-secret-org' },
    member: { login: 'attacker' }
  }.to_json

  assert_difference -> { Shipit::Membership.count }, 1 do
    post :create, body: body, as: :json
    assert_response :ok
  end

  team = Shipit::Team.find_by(github_id: shipit_teams(:shopify_developers).github_id)
  assert_equal 'no-secret-org', team.organization
  assert team.members.map(&:login).include?('attacker')
end
```
Assertions on both sides of the binding: `verified_organization` (`'no-secret-org'`, accepted despite no signature) equals `team.organization` written by `MembershipHandler`, while no HMAC/secret-based check ever executed — demonstrating the binding is only nominally, not cryptographically, satisfied.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
