### Title
`StatusHandler#process` matches commits by `sha` alone with no repository/stack scoping, allowing a status webhook authenticated for one repository to flip `blocked?`/`deployable?` for a commit in a different stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits via `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, with no filter on `stack_id` or `repository.full_name` from the payload. [1](#0-0)  The `commits` table's uniqueness constraint is deliberately `(sha, stack_id)` rather than `sha` alone, confirming the schema expects the same sha to legitimately exist across multiple, unrelated stacks. [2](#0-1)  This means a validly-signed status webhook for Repository/Stack A can create a `Status` row on a same-sha commit belonging to Stack B, whose `blocking_statuses` policy the sender never authenticated against.

### Finding Description
**Binding claimed**: `blocking_statuses.repository == status.commit.stack.repository` should equal `webhook.repository (verified via webhook_secret)`. This is violated because nothing in the code path enforces it.

Trace:
1. `WebhooksController#verify_signature` picks the GitHub App/secret to check with by `repository_owner = params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [3](#0-2)  This only proves the request was signed by *some* org's real webhook secret matching the payload's declared `repository.owner.login` - it never checks that this owner/repository corresponds to the `sha` being reported, nor to the stack(s) that will actually be mutated.
2. `WebhooksController#create` dispatches the raw parsed params to `StatusHandler.call(params)` without any repository-scoping. [4](#0-3) 
3. `StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, across every stack. [1](#0-0) 
4. `Status.after_create` schedules continuous delivery and touches the commit; `Commit#blocking?`/`Status::Common#blocking?` is computed from `commit.blocking_statuses.include?(context)` and `!success?`, so writing `state: success` on the victim's blocking-status row for the victim's stack flips it non-blocking. [5](#0-4) 
5. `Commit#blocked?` re-scans `stack.commits.reachable.newer_than(last_deployed_commit).older_than(self).any?(&:blocking?)` for the *victim stack*, and since the poisoned status no longer reports `blocking?`, this now returns `false`. [6](#0-5) 
6. `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) then flips true for downstream victim commits, and `Stack#next_commit_to_deploy` / `trigger_continuous_delivery` select and deploy them. [7](#0-6) 

Why guards don't stop it: `verify_signature` authenticates the sender's org/repository identity, not the sha-to-repository binding; `drop_unhandled_event` only checks event type; the `ExplicitParameters` schema on `StatusHandler` (`requires :sha`, `requires :state`, etc.) only validates types/presence of fields, not their relationship to any specific stack. [8](#0-7)  No model validation on `Status`/`Commit` cross-checks the reporting repository against the commit's stack repository. [9](#0-8) 

The precondition for two stacks to share a `sha` is exactly what the unique index `(sha, stack_id)` was built to permit - forks, mirrors, or repositories with shared git ancestry tracked as separate Shipit stacks routinely share commit shas for historical/common-ancestor commits. Under a validly configured multi-organization Shipit deployment (documented and supported, see `docs/setup.md` "Using Multiple Github Applications"), a legitimate, GitHub-signed status event from Repository A's own webhook secret (which the operator of A rightfully possesses for their own tenant) can carry a `sha` that also appears in Stack B's commit history, and the engine will happily write a `success` status onto B's commit, defeating B's `blocking_statuses` compliance gate.

### Impact Explanation
The write is a `Status` record created for a commit belonging to a stack/repository the sender never authenticated for, directly satisfying the Critical category "a payload for one repository mutating another's stack, commit ... " and enabling "an unauthorized deploy." The blast radius spans any pair of Shipit-tracked stacks that ever share a commit sha (forks, mirrors, monorepo splits, or shared upstream history) - not limited to a single tenant pair, and repeatable per shared-sha commit and per CI event.

### Likelihood Explanation
Requires: (1) two stacks tracked by the same Shipit instance whose commit histories overlap on at least one sha (a very common real-world condition for forks/mirrors), and (2) the ability to get a validly-signed `status` webhook delivered referencing that shared sha. This is straightforward if the attacker legitimately controls one of the two repositories/stacks (owns its GitHub App/webhook config) and simply triggers CI/build status reporting against a commit sha that is shared with the victim stack - no secret of the victim's is ever needed. Exploit cost is low (a normal CI run or a direct signed API status update on the attacker's own repository); it is repeatable at will against any stack sharing history with the attacker's repository.

### Recommendation
Scope `StatusHandler#process` (and any similar handler resolving by `sha` alone, e.g. check-run/push handlers) to the specific stack(s) whose `repository.full_name`/owner matches the webhook's authenticated `repository`, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repo_owner: ..., repo_name: ... })` derived from `params.dig('repository', 'full_name')`, rather than a bare global `sha` lookup.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or extending `test/controllers/webhooks_controller_test.rb`):
1. Create two stacks/repos, `victim_stack` and `attacker_stack`, each with a `Commit` row sharing the identical `sha` (permitted by the `(sha, stack_id)` unique index).
2. On `victim_stack`, seed a chain: `blocking_commit` with a pending `soc/compliance` status (`blocking?` true), and a `downstream_commit` after it.
3. Assert `downstream_commit.blocked?` is `true` and `victim_stack.next_commit_to_deploy` does not equal `downstream_commit`.
4. Post a `status` webhook payload (stubbing/mocking signature verification as existing tests do) whose `repository` fields correspond only to `attacker_stack`, with `sha` equal to `blocking_commit.sha` and `state: 'success'`.
5. Assert the equality violation: before, `blocking_commit.stack_id == victim_stack.id` while the authenticated `repository` in the webhook belongs to `attacker_stack`; after `StatusHandler.call`/`post :create`, assert `blocking_commit.reload.blocking?` is now `false` and `downstream_commit.reload.deployable?` is `true`.
6. Assert `victim_stack.next_commit_to_deploy == downstream_commit` and that invoking `victim_stack.trigger_continuous_delivery` creates a `Deploy` for it - demonstrating the cross-stack unauthorized deploy trigger.

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin
        trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
      rescue Task::ConcurrentTaskRunning
      end
    end

    def schedule_merges
      ProcessMergeRequestsJob.perform_later(self)
    end

    def next_commit_to_deploy
      commits_to_deploy = commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)
      if maximum_commits_per_deploy
        commits_with_max_applied = commits_to_deploy.limit(maximum_commits_per_deploy)
        deployable_commits(commits_with_max_applied) || deployable_commits(commits_to_deploy)
      else
        deployable_commits(commits_to_deploy)
      end
    end

# frozen_string_literal: true

module Shipit
  class Status < Record
    include Common
    include DeferredTouch

    STATES = %w[pending success failure error].freeze
    enum :state, STATES.zip(STATES).to_h

    belongs_to :stack, required: true
    belongs_to :commit, required: true

    deferred_touch commit: :updated_at

    validates :state, inclusion: { in: STATES, allow_blank: true }, presence: true

    after_create :enable_ci_on_stack
    after_commit :schedule_continuous_delivery, :broadcast_update, on: :create
