### Title
Fee-on-Transfer ERC20 Tokens Cause Over-Minting / Reserve Drain in Service-Chain Bridge — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` (2-step path) and the 1-step `onERC20Received` path both pull tokens from the caller using the nominal `_value + _feeLimit` amount, then immediately emit a `RequestValueTransfer` event carrying the same nominal `_value`. If the bridged ERC20 token charges a fee on transfer, the bridge receives fewer tokens than `_value + _feeLimit`, yet the event—and therefore the counterpart-chain handler—still processes the full nominal `_value`. This breaks the fundamental bridge invariant that the amount locked/burned on the source chain equals the amount minted/unlocked on the counterpart chain.

---

### Finding Description

In `requestERC20Transfer` (2-step path):

```solidity
// BridgeTransferERC20.sol line 133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

The bridge pulls `_value + _feeLimit` from the caller. If the token deducts a transfer fee, the bridge actually receives `(_value + _feeLimit) × (1 − fee_rate)`. The nominal `_value` is then forwarded unchanged into `_requestERC20Transfer`:

```solidity
// BridgeTransferERC20.sol lines 93-107
if (modeMintBurn) {
    ERC20Burnable(_tokenAddress).burn(_value);   // burns nominal _value, not actual received
}
emit RequestValueTransfer(
    TokenType.ERC20, _from, _to, _tokenAddress,
    _value,          // ← inflated; actual received < _value
    requestNonce, fee, _extraData
);
```

The counterpart-chain operator reads `_value` from the event and calls `handleERC20Transfer` with that same figure:

```solidity
// BridgeTransferERC20.sol lines 68-72
if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), ...);  // mints nominal _value
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);               // unlocks nominal _value
}
```

The same flaw exists in the 1-step path via `ERC20ServiceChain.requestValueTransfer` → `onERC20Received`, where `transfer(bridge, _amount + _feeLimit)` delivers fewer tokens than `_amount + _feeLimit` to the bridge, but `onERC20Received` is called with the original nominal `_amount`.

Additionally, `_payERC20FeeAndRefundChange` in `BridgeFee.sol` (lines 74, 78, 85) issues further `safeTransfer` calls that also incur the token's transfer fee, compounding the shortfall in the bridge's actual balance.

---

### Impact Explanation

**mintBurn mode (source burns, counterpart mints):**
- Bridge receives `(_value + _feeLimit) × (1 − r)` tokens but attempts to `burn(_value)`.
- If `_feeLimit = 0` and `fee = 0` (no bridge fee configured): bridge holds only `_value × (1 − r)` and the `burn(_value)` call reverts → **permanent DoS** for that token via `requestERC20Transfer`.
- If the bridge has enough balance to cover the burn (e.g., `_feeLimit` is large): burn succeeds, but the counterpart chain mints the full nominal `_value` → **unbacked token supply created on the counterpart chain** (unauthorized mint of `_value × r` tokens per transfer).

**lock mode (source locks, counterpart unlocks):**
- Bridge locks fewer tokens than `_value` but the counterpart chain releases `_value` → **bridge reserve is drained faster than deposits**, eventually making the bridge insolvent and unable to fulfill legitimate withdrawals.

Both outcomes constitute unauthorized token creation or unauthorized asset transfer affecting bridged assets.

---

### Likelihood Explanation

- Any user can call `requestERC20Transfer` with any registered ERC20 token — no privilege required.
- Fee-on-transfer tokens exist in production (e.g., USDT on some chains, STA, PAXG, etc.) and any such token registered in the bridge immediately triggers the vulnerability.
- The bridge's token registration is operator-controlled, but once a fee-on-transfer token is registered (even inadvertently), every user-initiated transfer exploits the discrepancy.

---

### Recommendation

Apply the balance-delta pattern in `requestERC20Transfer` to measure the actual received amount, and use that as the canonical `_value` for the event and burn:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);

    // Derive actual _value and _feeLimit from actualReceived proportionally,
    // or require actualReceived == _value.add(_feeLimit) to reject fee-on-transfer tokens.
    require(actualReceived == _value.add(_feeLimit), "fee-on-transfer token not supported");

    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
```

The same fix must be applied to the 1-step path: `onERC20Received` should verify the bridge's balance increased by exactly `_value + _feeLimit` before proceeding.

---

### Proof of Concept

Assume a fee-on-transfer token `FeeToken` with 1% transfer fee is registered in the bridge (mintBurn mode, no bridge fee configured, `feeLimit = 0`).

1. Alice calls `requestERC20Transfer(feeToken, Bob, 100e18, 0, "0x")`.
2. Bridge calls `safeTransferFrom(Alice, bridge, 100e18)` → bridge receives `99e18` (1% fee taken).
3. `_requestERC20Transfer` calls `burn(100e18)` → **reverts** because bridge only holds `99e18`.
4. Alice's transaction fails; she cannot bridge `FeeToken` at all → **DoS**.

Alternatively, if Alice sets `_feeLimit = 2e18` (so bridge receives `(100 + 2) × 0.99 = 100.98e18`):
1. Bridge receives `100.98e18`.
2. `_payERC20FeeAndRefundChange` with `fee = 0`, `_feeLimit = 0` (no bridge fee) → no fee payment.
3. `burn(100e18)` succeeds (bridge has `100.98e18`).
4. `RequestValueTransfer` emits `_value = 100e18`.
5. Counterpart chain operator calls `handleERC20Transfer` → mints `100e18` to Bob.
6. But only `100e18` were burned on source (correct), yet Alice only paid `100.98e18 × (1 − 0.01) ≈ 99.97e18` net (the `_feeLimit` refund also incurs fee). The accounting is corrupted and the bridge's internal balance tracking diverges from reality over repeated transfers. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
