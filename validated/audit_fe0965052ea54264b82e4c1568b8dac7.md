### Title
Asset definer can revoke attestor status of an address that already holds `spender_attested` asset coins, permanently freezing those coins with no way to spend or return them - ([File: validation.js])

### Summary
The bug reported for Kairos is that a collateral NFT's identity can be mutated externally (evolved/burned into a new token) after it is locked in the lending contract, making the on-chain hard-coded reference to the collateral stale and the contract's ability to `safeTransferFrom` the collateral back permanently broken - freezing both the borrower's NFT and the lender's funds. The analogous root cause in `ocore` is that a `spender_attested` asset's **eligible-holder set (attestor list) is mutable after issuance and after coins are already held by an address**, and every subsequent spend of that asset re-checks attestation against the *current* list rather than the list in effect when the coins were received. If the definer removes an address (including an AA holding the asset as escrow/collateral) from the attestor list, that address's coins become permanently unspendable, with no path to recover them - mirroring the "evolved NFT" freeze.

### Finding Description
When an asset is defined with `spender_attested: true`, the definer supplies an initial `attestors` list and can update it later via an `asset_attestors` message, validated in `validateAttestorListUpdate`, which only checks that the sender is the asset's `definer_address` and that the new list is well-formed: [1](#0-0) 

`checkAttestorList` performs only formatting checks and does not consider who currently holds coins of the asset: [2](#0-1) 

`readAsset` in `storage.js` always resolves the attestor list to the *latest* stable list as of `last_ball_mci`, not the list that was in effect when a particular output was created: [3](#0-2) 

At the moment any holder tries to spend/transfer such an asset (public or private, divisible or indivisible), `validatePaymentInputsAndOutputs` re-checks the *current* owner address against `objAsset.arrAttestedAddresses` and rejects the transfer if the owner is no longer attested: [4](#0-3) [5](#0-4) 

The same check applies for issuance (`spender_attested` issuer check) in `validatePayment`: [6](#0-5) 

Because the attestor list can be changed by the definer at any time after coins already exist at a given address, and because spend validation is evaluated against the list current as of the *spending* unit (not the receiving unit), any address - including an AA that is holding the asset in escrow/as collateral for some business logic (e.g. a lending AA modeling a non-fungible collateral token as an indivisible `spender_attested`, `fixed_denominations`, cap=1 asset) - can be retroactively "un-attested." Once that happens, the holder can never again satisfy the `owner address is not attested` check, so the coin can never be moved out of that address by anyone, including the AA's own trigger logic trying to return the collateral to the original owner. This is the direct analog of the Kairos issue: the "collateral" (asset unit) is intact, but an external state change (attestor list update, analogous to the NFT "evolving" to a new collection address) permanently severs the previously-valid path to move/repay it.

### Impact Explanation
Any coins of a `spender_attested` asset held by an address that is later dropped from the attestor list become permanently frozen/unspendable - there is no bypass, appeal, or timeout mechanism. If such an asset is used as AA-held collateral (a natural analog to an NFT-backed lending contract on Obyte), both the escrowed collateral and any counter-value locked in the AA become permanently stuck: the borrower cannot repay, the AA cannot forward the collateral, and the lender cannot ever reclaim it, matching the Medium-severity "borrower/lender fund loss" impact of the original report.

### Likelihood Explanation
Triggering this requires only the asset's own definer to post a normal, otherwise-legitimate `asset_attestors` update message - a standard, expected feature of `spender_attested` assets and reachable by the asset issuer (an explicitly in-scope actor). No special network conditions or cooperation from other parties is required, and it can happen at any point after assets have been distributed to third-party addresses or AAs, making the scenario realistic for any dApp built on top of a spender-attested asset.

### Recommendation
When validating a transfer/spend of a `spender_attested` asset, evaluate the owner's attested status against the attestor list that was current at the time the specific output was created (or at least ensure attestor list updates cannot retroactively invalidate previously accepted, already-owned outputs), rather than always using the latest list as of the spending unit. Alternatively, provide an explicit unwind/exit path (e.g., a grace period, or an allowance for previously-attested holders to move funds to any attested address) so that legitimate holders, including AAs acting as escrow, are never permanently locked out of assets they already hold.

### Proof of Concept
1. Definer issues asset `X` with `spender_attested: true`, `fixed_denominations: true`, `cap: 1` (modeling a unique collateral token) and `attestors: [D]`, then attests address `A`.
2. Address `A` (could be an AA acting as an escrow/lending contract) receives a coin of asset `X` as collateral; this passes `validatePaymentInputsAndOutputs`'s attestation check because `A` is in the attestor list at that time.
3. Definer posts a new `asset_attestors` message removing `A` from the attestor list (validated purely via `validateAttestorListUpdate`, requiring only that the sender is the definer).
4. `A` (or the AA logic controlling `A`) attempts to spend/return the coin. `validatePaymentInputsAndOutputs` looks up `objAsset.arrAttestedAddresses` via the now-updated list, `A` is not in it, and the transfer is rejected with `"owner address is not attested"` (`validation.js:2506-2507` for public assets, `2432-2433` for private ones).
5. The coin at address `A` is now permanently frozen - there is no code path that allows `A` to spend it again unless the definer re-adds `A`, which the definer has no obligation to do, exactly paralleling the "evolved NFT" scenario where the borrower can never repay and the collateral (and locked value) is stuck forever.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
