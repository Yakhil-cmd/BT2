### Title
Webhook signature verified against an attacker-chosen organization while the routed target repository is a separate, unauthenticated field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the `X-Hub-Signature` against using a value pulled straight out of the *unauthenticated* request body (`repository.owner.login`, falling back to `organization.login`), while the handlers that actually mutate Shipit state (sync commits, create statuses, trigger merges/deploys) key off a *different* field from the same body, `repository.full_name`. These two fields are never cross-checked against each other, so the "organization that authenticated" and the "repository that is written" are not bound together.

### Finding Description
`verify_signature` computes the app/secret to check against from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (including `webhook_secret`) from `secrets.github`: [3](#0-2) 

Critically, `verify_webhook_signature` short-circuits to `true` whenever that organization has **no configured `webhook_secret`** — a legitimate, documented configuration state (seen in the dummy secrets fixture where `webhook_secret:` is left blank per-org): [4](#0-3) [5](#0-4) 

Meanwhile, once the request passes `verify_signature`, every handler resolves the target repository/stacks from a *separate* payload field, `repository.full_name`, with no relation back to `repository_owner`: [6](#0-5) 

and `PushHandler` uses those stacks to enqueue a GitHub sync for arbitrary refs/SHAs: [7](#0-6) 

The equality this design assumes but never enforces is:
`repository_owner` (used to pick the signature-verification secret) == owner(`repository.full_name`) (used to pick the stacks that get acted upon).

Both fields are independently attacker-supplied in the raw JSON body — `WebhooksController#create` parses the untouched `request.raw_post` and dispatches by event type only, with no consistency check between the two: [8](#0-7) 

**Attack path (no credentials required):** Since the GitHub webhook endpoint is deliberately public/unauthenticated (that is the whole point of a webhook receiver), an unprivileged network attacker can POST directly to `/github/webhooks` with:
- `repository.owner.login` set to any organization value that is either unknown to `Shipit.github_organizations` config *or* configured with a blank `webhook_secret` (a supported, documented state) — this makes `verify_webhook_signature` return `true` unconditionally, with **no secret and no valid `X-Hub-Signature` needed at all**.
- `repository.full_name` set to any repository actually tracked by Shipit (any organization/repo pair with a `Stack` configured), regardless of which "organization" was used to pass the signature check.

The `push`, `status`, `check_suite`, `membership`, `merge`, and `pull_request` handlers then act on the stacks/commits resolved from that unrelated `full_name`, e.g. enqueuing `GithubSyncJob` for a chosen `expected_head_sha`, injecting arbitrary commit statuses via `StatusHandler` (which additionally has no repo scoping at all — it queries `Commit.where(sha: params.sha)` globally): [9](#0-8) 

Forged/injected commit statuses feed directly into `Commit#add_status`, which schedules merges and continuous deployment: [10](#0-9) 
and `ProcessMergeRequestsJob` merges a PR once `all_status_checks_passed?` becomes true, using only forged status events: [11](#0-10) 

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written," letting an unauthenticated attacker cause the engine to record fabricated CI states and trigger sync/merge/deploy workflows for a repository/stack they never authenticated against. Forged `commit_status` events can flip a commit to "success," which `ProcessMergeRequestsJob` uses to auto-merge queued pull requests and which `ContinuousDeliveryJob`/deploy scheduling reacts to — i.e., an unauthorized merge/deploy trigger on a repository the attacker does not control, satisfying the Critical bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires: (a) the deployment has at least one organization entry with no `webhook_secret` configured, or an org name the attacker can freely choose that Shipit doesn't recognize handling gracefully but others accept blank secrets — this is an explicitly supported configuration shown in the repo's own fixtures, not a hypothetical misconfiguration invented for this report. No GitHub App private key, `ApiClient` token, or Shipit session is needed; the webhook endpoint is public by design. This is realistic wherever an operator has any org configured without a webhook secret (e.g., early setup, internal-only orgs assumed "trusted").

### Recommendation
Bind the field used for authentication to the field used for routing: after `verify_signature` succeeds, re-derive `repository_owner` from the same trusted source used to select the secret, and reject the payload if `repository.full_name`'s owner segment does not match `repository_owner`. Also scope `StatusHandler`'s `Commit.where(sha:)` lookup to commits belonging to stacks under the verified repository, not a global SHA search.

### Proof of Concept
1. Configure (or find deployed) Shipit with two orgs in `secrets.github`, one (`empty-secret-org`) having no `webhook_secret`.
2. POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "empty-secret-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
No `X-Hub-Signature` header (or any garbage value) is required because `verify_webhook_signature` returns `true` when `empty-secret-org` has no `webhook_secret`.
3. `verify_signature` passes; `PushHandler#process` resolves stacks via `repository.full_name = "victim-org/victim-repo"` and enqueues `GithubSyncJob` for that stack with the attacker-supplied SHA — an action the attacker was never authenticated to perform against `victim-org`. [7](#0-6)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
