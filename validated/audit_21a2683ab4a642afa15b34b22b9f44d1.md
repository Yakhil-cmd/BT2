Based on the investigation, I found an interesting analog worth flagging carefully: the `erc20_transactor.rs` XCM transactor that calls into arbitrary user-deployed ERC20 contracts (via `pallet-revive`) and assumes the exact `amount` requested was transferred, without verifying the actual balance delta.### Title
`ERC20Transactor` assumes ERC20 `transfer()` moved the exact requested amount, without verifying actual balance change - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` implement the XCM `TransactAsset` trait for ERC20 tokens deployed on `pallet-revive`. Both functions call an arbitrary ERC20 contract's `transfer()` function and, if the call does not revert and the ABI-decoded return value is `true`, unconditionally treat the full requested `amount` as having moved — without ever reading the actual balance of the source/destination account before and after the call. This is the exact bug class from the report: a custodian/transactor trusts a nominal transfer amount instead of checking the real balance delta, so a fee-on-transfer, deflationary, or otherwise non-standard ERC20 token can desynchronize the XCM holding register from the real on-chain balance.

### Finding Description
In `withdraw_asset_with_surplus` [1](#0-0) , the transactor calls `IERC20::transferCall{ to: checking_address, value: amount }` against the ERC20 contract identified by `asset_id`, using `pallet_revive::Pallet::<T>::bare_call` [2](#0-1) . If the call succeeds and decodes to `true`, the function credits an `AssetsInHolding` entry with `Erc20Credit(amount)` for the full nominal `amount` requested [3](#0-2)  — it never inspects `TransfersCheckingAccount`'s `balanceOf` before/after the call to confirm that exactly `amount` tokens actually landed there.

Symmetrically, `deposit_asset_with_surplus` transfers `amount` from the checking account to the beneficiary via the same pattern and reports success/weight-surplus purely based on the boolean return value of `transfer()` [4](#0-3) , again without verifying the beneficiary's actual balance increase.

`Erc20Credit` is documented explicitly as *not* enforcing runtime-level balance constraints: "the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime" [5](#0-4) . This assumption is only valid for standard, non-fee ERC20 tokens. If the underlying contract (which is arbitrary user-deployed EVM/PVM bytecode via `pallet-revive`) implements a deflationary/fee-on-transfer/rebasing `transfer`, `transferFrom` (i.e. it can move less than `value` to the recipient while still returning `true`), the XCM executor's holding register and any subsequent pool/asset accounting built on top of `Erc20Credit(amount)` will diverge from the real ERC20 balance held by `TransfersCheckingAccount`. This mirrors exactly the reported flaw: `safeTransferFrom` doesn't check actual transferred value, and downstream accounting assumes the nominal amount arrived.

### Impact Explanation
If exploitable, this causes an accounting desync between the XCM `AssetsInHolding` register (and thus downstream trust: further `DepositAsset`, fee payment, or a paired liquidity/backing accounting layer) and the real ERC20 balance in the checking/custody account. Repeated withdraw/deposit cycles through a fee-taking token could let the checking account's real balance drain faster than the XCM-side ledger believes, or let an attacker who controls the ERC20 contract manufacture more `AssetsInHolding` credit than tokens actually delivered, potentially enabling over-crediting of a beneficiary or insolvency in any pool/backing accounting that trusts `Erc20Credit`'s reported amount.

### Likelihood Explanation
Reachability is **not fully confirmed** from this investigation. `ERC20Transactor` is a generic building block in `cumulus/parachains/runtimes/assets/common`; I could not confirm within this session that it is wired into the live `AssetTransactors` tuple of a production Asset Hub runtime, nor whether the `Matcher`/asset registration used with it permits an attacker to register an arbitrary, attacker-controlled ERC20 contract as a valid reserve/transactable asset without a privileged/governance step. If asset registration for this transactor requires governance approval (as is typical for XCM reserve assets), the attacker precondition ("no privileged role, no governance control") would not be met, and this would not be independently exploitable by an unprivileged user. This must be verified against the actual runtime configuration before treating it as confirmed-exploitable; I flag it as a Medium-confidence structural finding rather than a fully proven exploit chain.

### Recommendation
Before crediting `AssetsInHolding` in `withdraw_asset_with_surplus`, read `balanceOf(checking_account)` before and after the `transfer()` call (or use the `Transfer` event value) and use the actual delta as the credited amount rather than the nominal `amount`. Symmetrically, in `deposit_asset_with_surplus`, verify the beneficiary's actual balance increase before reporting success, and propagate any shortfall back to the XCM executor (e.g., partial success/error) rather than assuming exact delivery. Additionally, restrict registrable ERC20 assets for this transactor to ones vetted to be standard-compliant (no fee-on-transfer/rebasing behavior), consistent with the standard ERC20 integration checklist referenced in the original report.

### Proof of Concept
No PoC was executed. This is a code-review-level finding based on direct inspection of `erc20_transactor.rs`; I did not have the ability to run a local Rust/FRAME integration test in this session, and I could not confirm the production wiring (whether this transactor is included in the live `AssetTransactors` config of Asset Hub or another parachain runtime, and whether the associated `Matcher`/asset-registration path is permissionless). These two points — (1) confirmed inclusion in a live runtime's XCM executor config, and (2) permissionless registration of an attacker-deployed ERC20 contract as a transactable asset — are required to escalate this from a structural code observation to a fully proven, reachable exploit, and should be verified in a follow-up session with full repository/tooling access.

		Box::new(Erc20Credit(self.0))

	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
