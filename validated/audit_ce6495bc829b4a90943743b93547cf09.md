### Title
`ERC20Transactor::withdraw_asset_with_surplus` credits XCM holding with the nominal requested amount instead of the amount actually confirmed transferred, allowing unbacked asset credit from a self-deployed ERC20 contract - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` performs an ERC20 `transfer()` call to a "checking account" and, on decoding a boolean `true` success return, credits `AssetsInHolding` with the caller-supplied nominal `amount` — the same value it asked the contract to move — rather than any independently verified balance delta. Because the asset identifier for this transactor (`ERC20Matcher`/`IsLocalAccountKey20`) is an arbitrary attacker-controlled `H160` contract address, the "amount actually transferred" is entirely defined by attacker-authored contract bytecode. This mirrors the reported DODO issue: trusting a nominal/requested amount instead of the value actually confirmed by the external call.

### Finding Description
`withdraw_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs:150-216` is wired into `AssetTransactors` on Asset Hub Westend (`cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs:222-246`). Its `ERC20Matcher` is defined as: [1](#0-0) 

`IsLocalAccountKey20` matches **any** `Location::new(0, [AccountKey20{..}])`: [2](#0-1) 

i.e. the "asset id" for this transactor is an arbitrary contract address that any user can deploy via `pallet_revive`. When an XCM program references this asset (e.g. via `WithdrawAsset`), the transactor performs: [3](#0-2) 

The code only checks that the contract call did not revert and that `transferCall` decoded to `true`. It never reads the checking account's actual token balance before/after the call, and never uses any value derived from the contract's real state change — it simply mints an `Erc20Credit(amount)` XCM holding entry equal to the value the caller requested. Since the target contract at `asset_id` is fully attacker-controlled, the attacker can deploy a trivial contract whose `transfer()` always returns `true` while performing no real balance change (or transferring less than `amount`), so the "actual amount received by the checking account" and the amount credited into `AssetsInHolding` diverge — exactly the invariant violated in the reported issue (trusting nominal amount instead of the amount actually confirmed by the external call's real effect).

### Impact Explanation
The bug produces an internal accounting mismatch: XCM holding is credited with more value than what the "checking account" (the asset's book-keeping account) actually received. Within the executing XCM program this fabricated holding can be redirected via `DepositAsset` to any beneficiary, effectively minting fictitious balance for that asset id. Whether this escalates to theft of real value from other users depends on whether any other component (asset-conversion pools, reserve-trust configuration on a remote chain, or a UI/indexer) treats this `AccountKey20` location as fungible/tradable collateral without additional identity checks — I was not able to fully verify within the available iterations whether Asset Hub's `pallet_asset_conversion` pool-asset-kind configuration accepts arbitrary `Location`/ERC20 asset ids as poolable assets, or whether any parachain/relay trusts Asset Hub as a reserve for arbitrary `AccountKey20` locations. That downstream verification is required to establish a concrete path to loss of *other users'* funds; absent it, the demonstrable, code-level fact is the accounting-integrity break itself (unbacked `AssetsInHolding` credit for a self-issued asset), which is a real breach of the "credited amount must reflect actually transferred amount" invariant but whose blast radius is currently limited to state associated with the attacker's own fabricated asset id unless further downstream trust is proven.

### Likelihood Explanation
Reaching this code requires only: (1) deploying an arbitrary contract through `pallet_revive` (a normal, unprivileged user action), and (2) submitting an XCM program that references that contract's address as an asset location, reachable through the standard `AssetTransactors` tuple. No governance, no privileged origin, and no validator/collator collusion is required — this is fully attacker-reachable with a signed origin.

### Recommendation
Do not trust the nominal `amount` for holding accounting. Before/after the ERC20 `transfer` call, read the checking account's actual token balance via a `balanceOf` call (or otherwise derive the real delta) and use that verified delta — not the caller-supplied `amount` — when constructing the `Erc20Credit` in `withdraw_asset_with_surplus`, mirroring the recommendation in the original report of using the return/confirmed value rather than the requested one. Symmetrically, `deposit_asset_with_surplus` should verify the checking account's real balance decreased by the intended amount before treating the deposit as fully settled.

### Proof of Concept
No executable Rust/FRAME integration test was run; this is a static-code finding based on direct reading of `erc20_transactor.rs` and its wiring in `asset-hub-westend/src/xcm_config.rs`. A full PoC would require: deploying a "fake ERC20" contract via `pallet_revive` whose `transfer()` unconditionally returns `true` without moving real balance, executing an XCM program (e.g. via `pallet_xcm::execute` or a local `WithdrawAsset`/`DepositAsset` sequence) referencing that contract's address as the asset, and asserting that `AssetsInHolding`/subsequent `DepositAsset` credits a `beneficiary` with `amount` while the checking account's real token balance did not change. This reproduction was **not executed** in this session — only the code paths were traced from `withdraw_asset_with_surplus` (lines 150–216) through the `ERC20Matcher` definition and the runtime's `AssetTransactors` tuple. Whether this translates into loss of *other users'* assets (via asset-conversion pools or cross-chain reserve trust) remains unverified and would need additional investigation of `pallet_asset_conversion`'s pool-asset-kind config and remote-chain `IsReserve` filters before this can be escalated beyond an accounting-integrity finding.
