### Title
Unbounded `u64` fee-accumulator overflow panics `update_fees`, permanently disabling `swap_base_input`/`swap_base_output` for a pool - (File: `programs/cp-swap/src/states/pool.rs`)

### Summary
`PoolState::update_fees` accumulates protocol, fund and creator trading fees into `u64` fields (`protocol_fees_token_0/1`, `fund_fees_token_0/1`, `creator_fees_token_0/1`) using `checked_add(...).unwrap()`. These fields are never bounded and only shrink when an admin/fund-owner explicitly calls `collect_protocol_fee` / `collect_fund_fee`. Because any unprivileged user can create a pool with a custom mint and repeatedly swap large amounts (attacker fully controls token supply/decimals for a self-created pool), the accumulated fee counters can be driven arbitrarily high across a sequence of swaps and eventually overflow `u64`, causing `checked_add(...).unwrap()` to panic and abort every subsequent swap on that pool until an authorized party collects the fees to bring the counter back down.

Each addition uses `.checked_add(...).unwrap()`, e.g. [2](#0-1) 

These `u64` counters (`protocol_fees_token_0/1`, `fund_fees_token_0/1`, `creator_fees_token_0/1`) are persisted in `PoolState`: [3](#0-2) 

The counters are monotonically increasing on every swap and are only decreased by privileged `collect_protocol_fee`/`collect_fund_fee` calls, which subtract at most the amount actually collected: [4](#0-3) 

There is no cap search hit for a `MAX_FEE_RATE` constant, and fee amounts are computed straight from `amount_in`/vault balances with no upper clamp other than `u64` vault sizes: [5](#0-4) 

This mirrors the root cause of the Panoptic finding: a value derived from user-chosen extreme inputs is accumulated into a fixed-width integer with an unchecked cast/unwrap, so once enough fee-bearing operations are performed the stored value overflows and the panic/revert becomes permanent for every future call that touches the same accumulator — a self/attacker-triggered DoS rather than a one-off revert.

### Impact Explanation
Once `protocol_fees_token_0` (or any of the sibling counters) is close to `u64::MAX`, the next swap in that direction will panic inside `update_fees`, reverting the transaction. Because the counter is not reset automatically, **every subsequent swap in that direction on the pool will also revert**, permanently freezing trading for that pool until the protocol/fund owner notices and calls `collect_protocol_fee`/`collect_fund_fee`. This is a denial-of-service on the swap functionality of a specific pool (not a direct theft), but for a permissionless/pool-creator-controlled pool built on a custom mint, the pool creator (or any user) can engineer this state deliberately, e.g. to grief its own pool's traders or to test/attack a pool whose fee owner is inattentive. Deposits/withdrawals are unaffected since they don't call `update_fees`, so LP principal is not frozen — this limits severity relative to the original High/Medium Panoptic finding, but the mechanism (rounding/accumulator growth → unchecked cast/unwrap panic → persistent inability to operate) is directly analogous.

### Likelihood Explanation
Reaching this state requires an attacker to control (or collude on) a pool with a custom mint of very large supply/decimals and to execute a handful of large-notional swaps, similar to the "external conditions and large token amounts" caveat that reduced the original finding to Medium severity. Because `amount_in` can be as large as the pool's vault balance (bounded only by `u64::MAX`) and `trade_fee_rate`/`protocol_fee_rate` are attacker-influenced only at pool-creation time via `AmmConfig` selection, a small number of large swaps against a high-supply custom token can push the fee accumulator toward overflow without needing astronomical real-world dollar value — this is comparable in likelihood to the original scenario.

### Recommendation
Replace the panicking `.unwrap()` calls in `update_fees` (and the related `collect_protocol_fee`/`collect_fund_fee` subtractions) with graceful error returns (e.g. `ok_or(ErrorCode::CalculationOverflow)?` or `checked_add(...).ok_or(...)?`), and/or saturate the accumulators instead of aborting so a single overflow does not permanently disable swaps. Consider capping trade fee accumulation per pool or auto-triggering a partial/forced collection path when counters approach `u64::MAX`.

### Proof of Concept
1. As an unprivileged user, create a new mint with supply near `u64::MAX` and initialize a CP-swap pool with it via `initialize`/`initialize_with_permission`.
2. Deposit a very large amount of both tokens (bounded by `u64::MAX` vault balances) to seed large liquidity.
3. Repeatedly call `swap_base_input` with `amount_in` close to the vault's balance, choosing a pool `AmmConfig` with the maximum allowed `protocol_fee_rate`/`trade_fee_rate`; each call increases `protocol_fees_token_0`/`fund_fees_token_0` via `update_fees`.
4. After enough iterations, `protocol_fees_token_0.checked_add(protocol_fee).unwrap()` in `update_fees` (`programs/cp-swap/src/states/pool.rs:339-343`) overflows `u64` and panics, aborting the transaction.
5. Every subsequent `swap_base_input`/`swap_base_output` in that direction on the pool now reverts the same way, denying trading on the pool until `collect_protocol_fee` (privileged) is called to reduce the counter. [1](#0-0) [6](#0-5)
