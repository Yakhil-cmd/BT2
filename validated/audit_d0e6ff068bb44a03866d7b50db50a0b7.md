### Title
Independent per-recipient rounding of headers-commission shares can inflate the byte supply - ([File: headers_commission.js])

### Summary
`calcHeadersCommissions()` splits a parent unit's `headers_commission` among multiple `earned_headers_commission_recipients` by rounding each recipient's share independently, exactly like the reported `feePerUser = estimatedFee / totalUsers` pattern. Because each recipient's cut is rounded to the nearest integer separately instead of the remainder being tracked and only distributed once, an attacker who controls the recipient list of a multi-authored unit can pick shares that make the sum of rounded amounts exceed the actual `headers_commission` being distributed, creating extra bytes that are not backed by any deduction elsewhere in the ledger.

### Finding Description
For every parent unit whose header commission is won by a child unit, the code computes each recipient's award as: [1](#0-0) 
```
var full_amount = assocWonAmounts[child_unit][payer_unit];
if (objUnit.assocEarnedHeadersCommissionRecipients) {
    for (var address in objUnit.assocEarnedHeadersCommissionRecipients) {
        var share = objUnit.assocEarnedHeadersCommissionRecipients[address];
        var amount = Math.round(full_amount * share / 100.0);
        arrValuesRAM.push("('"+payer_unit+"', '"+address+"', "+amount+")");
    };
}
``` [2](#0-1) 

The equivalent SQL path performs the same per-recipient rounding: [3](#0-2) 
```
SELECT punits.unit, earned_headers_commission_recipients.address, \n\
    ROUND(punits.headers_commission*earned_headers_commission_share/100.0) AS hc \n\
```

Each of these `(unit, address, amount)` rows is inserted into `headers_commission_contributions` and later summed unconditionally into `headers_commission_outputs`: [4](#0-3) 

`headers_commission_outputs` rows become directly spendable balances: they are read back and added to `total_input` when a `headers_commission`-type input is validated in a later payment message, with no cross-check that the summed contributions equal the original `punits.headers_commission`: [5](#0-4) 

The `earned_headers_commission_recipients` list and each `earned_headers_commission_share` are fully attacker-controlled fields of a posted unit; the only validation is that shares are positive integers summing to exactly 100: [6](#0-5) 

Because `Math.round` (and SQL `ROUND`) is applied independently per recipient rather than rounding down all shares and awarding the leftover remainder to one recipient, it is possible to choose a set of shares such that the sum of the independently-rounded amounts is strictly greater than `full_amount`. For example, with `full_amount = 3` and two recipients each holding 50%: `round(3*0.5) = round(1.5) = 2` for each recipient, so `2 + 2 = 4 > 3` — one extra byte materializes out of nothing. An attacker controlling both recipient addresses (e.g. two of their own addresses, or a single address listed with a duplicate-shares trick within the allowed author/recipient limits) receives real, later-spendable bytes exceeding the amount actually earned by the parent unit's headers commission.

### Impact Explanation
This is a genuine, if per-instance small, supply-inflation bug: `headers_commission_outputs.amount` values are treated by `validation.js`'s `total_input` accounting as legitimate money, spendable in future payment messages, with no invariant enforced anywhere that `SUM(contributions for a given payer unit) == payer_unit.headers_commission`. Repeated exploitation — an attacker posting many single-author "candidate" units, or crafting multi-author units with rounding-favorable share splits, and winning headers-commission ties across many parent units over time — allows continuous, unbacked minting of bytes, i.e. a slow but real inflation of the base-asset money supply, which the audit report class explicitly calls out as an acceptable impact category (supply inflation).

### Likelihood Explanation
Reachable by any unprivileged unit poster: `earned_headers_commission_recipients` is a standard field of any multi-authored unit, validated only for well-formedness and share-sum=100 (`validateHeadersCommissionRecipients`). Winning a header commission requires being the (pseudo-random, SHA1-tie-broken) winning child of a parent unit, which an attacker can boost their odds of by posting many candidate children; over the long run and across the large number of units processed by the network, the deterministic rounding-exploit share configuration guarantees the attacker's take is inflated whenever they win. The magnitude per event is small (bounded by roughly the number of controlled recipients divided by two, in bytes), but the exploit is repeatable indefinitely at no cost beyond normal unit-posting fees.

### Recommendation
Round down all recipient shares (`Math.floor`/SQL `FLOOR`) and award the remaining leftover (`full_amount - sum(floor_amounts)`) to a single, deterministically chosen recipient (e.g., the first/last in the sorted list), so that `sum(amount_i)` is always exactly `full_amount`. Apply the same fix to both the SQL (`ROUND` → `FLOOR` + remainder correction) and in-memory JS paths in `headers_commission.js`, and add a consistency assertion in `calcHeadersCommissions()` that verifies contributions summed per payer unit equal `punits.headers_commission` before writing to `headers_commission_outputs`.

### Proof of Concept
1. Create a 2-authored unit (author A, author B) whose header-commission-winning child specifies `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 50}, {address: B, earned_headers_commission_share: 50}]` — this passes `validateHeadersCommissionRecipients` since shares sum to 100.
2. Arrange (via posting many units, since winner selection is `SHA1`-tie-broken among sibling candidate children — see `getWinnerInfo`) for this unit to win a parent's headers commission where `headers_commission` (`full_amount`) is an odd number.
3. `calcHeadersCommissions()` computes `amount_A = Math.round(full_amount*0.5) `and `amount_B = Math.round(full_amount*0.5)`; for odd `full_amount` both round the same fractional `.5` up, so `amount_A + amount_B = full_amount + 1`.
4. Both rows are inserted into `headers_commission_contributions` and summed unconditionally into `headers_commission_outputs` (`headers_commission.js:221-227`), giving addresses A and B one extra spendable byte in total versus the real `headers_commission` collected from the payer unit.
5. Attacker (controlling both A and B) later spends this via a `headers_commission`-type input, which `validation.js` (`2582-2599`) accepts into `total_input` with no cross-check against the true earned amount — netting free bytes.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
