### Title
Stack-scoped API client tokens can read the CI/deploy status of any stack via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` tokens can be scoped to a single stack via `stack_id`, and `Shipit::Api::BaseController` enforces that scoping by resolving stacks through the `stacks` helper. `Shipit::Api::CCMenuController` overrides `stack` to bypass that helper, so a valid, stack-scoped token can be replayed against any `stack_id` in the URL and still get a `200 OK` with that other stack's build/deploy status.

### Finding Description
The bug-class analog here is: **a stack a token authorizes vs a stack it touches**.

`ApiClient#check_permissions!` only validates permission strings (`read:stack`, `write:stack`, etc.) — it never checks `stack_id`: [1](#0-0) 

Stack-level scoping is instead enforced only through the `stacks` method in the shared base controller, which restricts lookups to the client's assigned stack when `stack_id` is set: [2](#0-1) 

Every other API resource controller resolves the target stack through this scoped helper, e.g. `Shipit::Api::StacksController#stack`: [3](#0-2) 

`Shipit::Api::CCMenuController`, however, defines its own `stack` method that calls `Stack.from_param!` directly on the unscoped `Stack` model, completely bypassing the `stacks` scoping helper from `BaseController`: [4](#0-3) 

The controller only declares `require_permission :read, :stack`, which — as shown above — checks the permission string but not whether the authenticated client is authorized for *this particular* stack: [5](#0-4) 

This mirrors the reported bug class exactly: the multiplier/authorization decision (`read:stack` permission check) is made independently of the binding condition that should gate the specific object being acted upon (which stack the token is scoped to), so the check passes while the actual resource touched is different from the one authorized.

Before the attacker's request: a client with token T is scoped (`stack_id = A`) and is only supposed to see stack A's data (as enforced everywhere else in the API via `stacks`).
After the attacker's request: the same token T, sent to `GET /api/stacks/:stack_id/ccmenu?token=T` with `stack_id = B`, returns stack B's deploy/build status — an equality that should hold (`token.authorized_stack == stack_touched`) is broken.

### Impact Explanation
This qualifies as High severity per the rubric: "unauthenticated read of stack state, task streams or deploy output" — an attacker holding a legitimately-scoped, low-privilege token (e.g. a CCMenu client created by `CCMenuUrlController` for one stack, or any `read:stack`-only client meant to be restricted to a single stack) can enumerate/read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `activity`, etc., rendered in `shipit/ccmenu/project`) of any stack in the Shipit instance, not just the one it was authorized for. This crosses a repository/stack authorization boundary without needing elevated credentials.

### Likelihood Explanation
Likelihood is high: exploitation requires only possession of any valid `read:stack`-permission API token (even one deliberately scoped to a single stack) and knowledge/guessing of another stack's `stack_id`/param. The endpoint additionally accepts the token via a URL query parameter (`params[:token]`), as used by `authenticate_api_client` override: [6](#0-5) 
This makes the token easy to leak/reuse (e.g., via CI tool configs, browser history, logs) and trivial to replay against a different `stack_id`.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve the stack through the same scoped `stacks` helper used elsewhere (`stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so that a stack-scoped `ApiClient` cannot read data for stacks outside its `stack_id` scope.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to stack A (`stack_id = A.id`, `permissions: ['read:stack']`) — e.g. via `CCMenuUrlController#fetch`, which mints such a client and token for the current stack.
2. Note the token value.
3. Send `GET /api/stacks/:stack_id_of_B/ccmenu?token=<TOKEN>` where `B` is any other stack in the instance.
4. Observe a `200 OK` XML response rendering stack B's deploy status via `shipit/ccmenu/project`, despite the token being scoped to stack A — because `CCMenuController#stack` resolves via `Stack.from_param!` rather than `stacks.from_param!`.
