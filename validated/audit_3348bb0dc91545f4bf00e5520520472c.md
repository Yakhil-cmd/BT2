### Title
Webhook Signature Verified Against `repository.owner.login`, But Repository Actions Are Resolved From The Unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController` selects which GitHub App / `webhook_secret` to verify a webhook's HMAC signature against using `repository.owner.login` (or `organization.login`) pulled out of the *same* untrusted JSON body it is about to validate [1](#0-0) , and it falls back to `organization.login` when `repository` is absent [2](#0-1) . Every `Webhooks::Handlers::Handler` subclass, however, resolves the repository/stack to act on using a *different* field of the same body — `repository.full_name` — with no check that its owner segment matches the `repository.owner.login`/`organization.login` used for signature selection [3](#0-2) .

### Finding Description
The binding that should hold is:

`organization whose secret verified the request` == `organization owning the repository/stack the handler mutates`

Before the fix, this held only accidentally, because in a genuine GitHub webhook `repository.owner.login` and the owner segment of `repository.full_name` always match. The controller and the handlers never enforce this relationship in code — they independently `dig` two different keys out of the same JSON body:

- `WebhooksController#repository_owner` → `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, used only to pick `Shipit.github(organization: repository_owner)` for HMAC verification.
- `Handler#repository_name` → `payload.dig('repository', 'full_name')`, used by every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, `PullRequest::*`) to look up `Repository.from_github_repo_name(repository_name)` and thus the `Stack`s that get acted on [4](#0-3) .

Because Shipit supports multiple GitHub organizations each with their own `webhook_secret` (`Shipit.github(organization: ...)`), any party that legitimately controls a GitHub App/organization already onboarded into this Shipit instance knows (or can obtain) that organization's `webhook_secret`. That party can then POST an arbitrary, self-signed JSON body to the public `/webhooks` endpoint with:
- `repository.owner.login` (or `organization.login`) = their own org — so `verify_signature` picks their own org's secret and the HMAC passes,
- `repository.full_name` = `"victim-org/victim-repo"` — an arbitrary repository/stack belonging to a completely different organization on the same Shipit install.

The HMAC covers the raw POST body, but it only proves "this body was signed with organisation A's secret" — it says nothing about which repository the body's `full_name` claims to be, since nothing cross-validates the two fields.

### Impact Explanation
Analogous to the deck.impersonation report: a party authorized for one namespace (their own org) can make writes land in another namespace (a victim org's repository/stack) purely by mismatching two fields the server never reconciles. Concretely this allows:
- Forcing arbitrary `Stack#sync_github` refresh/resync cycles on any stack via a forged `push` event [4](#0-3) .
- Creating attacker-controlled `Status` records (state/description/target_url) on arbitrary commits of a repository the attacker does not own, as demonstrated by the "`:state` create a Status for the specific commit" test showing the handler trusts payload fields directly [5](#0-4) .
- Triggering `RefreshCheckRunsJob`/check-suite state changes and team-membership mutations for a victim repository/org — all cross-repository/cross-organization writes performed by an unprivileged, out-of-scope party for that repository.

This meets the Critical bar of "cross-repository writes" performed without the required trust relationship (control of the target org's secret).

### Likelihood Explanation
Requires the attacker to control the `webhook_secret` of at least one GitHub organization/app that this Shipit instance already trusts (multi-organization Shipit deployment). No Shipit session, `ApiClient` token, or the victim org's own secret is needed — the attacker only self-signs with their own org's secret while spoofing the `full_name` field that identifies the target repository. This is realistic for any Shipit instance serving more than one GitHub organization/team, which the engine explicitly supports via `Shipit.github(organization:)`.

### Recommendation
After computing `repository_owner` for secret selection, verify that it matches the owner segment parsed from `repository.full_name` (or `organization.login`) before dispatching to handlers; reject the request (422) on mismatch. Alternatively, have handlers derive the target repository strictly from the same `repository.owner.login`/`name` pair that was used to select the verifying secret, rather than trusting `full_name` independently.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` (secret `S1`) and `victim-org` (secret `S2`), each with their own GitHub App onboarded.
2. Attacker crafts a `push` webhook body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S1, body)` using their own org's known secret and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`), verifies the HMAC with `S1`, and passes [1](#0-0) .
5. `PushHandler` resolves the target via `repository.full_name` = `"victim-org/victim-repo"` [6](#0-5)  and calls `stack.sync_github` on `victim-org/victim-repo`'s stacks even though the request was signed by `attacker-org`'s secret [4](#0-3) .
