## Title
Merkle proof `siblings` length is never required to be non-zero, allowing a single-node "proof" to collapse membership verification into a trivial hash-equality check - ([File: merkle.js])

### Summary
`ocore`'s Merkle-proof primitives (`merkle.js`, used by both the `'in merkle'` address-definition operator and the `is_valid_merkle_proof` oscript/AA formula function) never enforce that a submitted proof contains at least one sibling hash. This mirrors exactly the class of bug described in the external report ("`merkleProof` length not checked" - Gearbox `AccountMining.sol`): when the sibling/proof array is empty, verification degenerates into checking `hash(element) == root` instead of proving that `element` is one of many leaves committed to by `root`. An attacker who controls the "element" value baked into their own address definition (or AA logic) can turn the intended "prove membership in an oracle-committed set" check into a trivial hash-preimage/collision game against whatever single value the oracle happens to publish under that feed name.

### Finding Description
`verifyMerkleProof` in [1](#0-0)  only loops over `proof.siblings`; if `proof.siblings.length === 0` the function reduces to `hash(element) === proof.root` with no requirement that the tree actually had more than one leaf.

This function is invoked directly, with no length check on the deserialized proof, in the address-definition authentifier handler for the `'in merkle'` operator: [2](#0-1) 

The definition-time validation of the `'in merkle'` term only validates the *element* string format (`element.match(...)`) - it never restricts or requires anything about the proof that will later be supplied as an authentifier: [3](#0-2) 

The same missing check exists in the oscript/AA-formula equivalent, `is_valid_merkle_proof`: the post-fix code checks `objProof.siblings.length > 50` (upper bound) but never checks that the length is `> 0`: [4](#0-3) 

Because `serializeMerkleProof`/`deserializeMerkleProof` explicitly support the zero-sibling case (`if (proof.siblings.length > 0) serialized_proof += ...`), a proof like `"0-<root>"` is a perfectly well-formed, accepted proof: [5](#0-4) 

The net effect: the "membership in an oracle-committed multi-element set" guarantee that `'in merkle'` and `is_valid_merkle_proof` are meant to provide can be satisfied by anyone who can make `sha256(element) == oracle_published_value`, without that value ever having been computed as a genuine Merkle root over a set containing `element`. Since oracles frequently publish arbitrary strings/hashes under a feed name for unrelated purposes (document hashes, commitments, arbitrary payload echoes, etc.), this creates a realistic path for a self-authored address definition or an AA distributing funds based on a whitelist Merkle root to be satisfied without the address/element actually being part of the intended list.

### Impact Explanation
Both consumers of this primitive are used to gate financial authorization:
- An address's spending definition can use `'in merkle'` as an authentication clause, so a bypass here means an address's private-key-independent spending condition can be satisfied fraudulently, leading to unauthorized spending from that address's outputs.
- `is_valid_merkle_proof` is directly usable inside oscript/AA formulas (see `formula/error/functions.js`), so an AA that pays out to addresses proving membership in an oracle-attested whitelist (airdrop, bounty, allowlist-gated escrow, etc.) can be tricked into releasing funds to a party that never was in the committed set, causing AA fund loss.

### Likelihood Explanation
Exploitation does not require breaking SHA-256 preimage resistance in general - it only requires that the attacker's chosen `element` (fixed at address-definition time, subject only to a loose 1–100 character format regex) end up matching some value the oracle *independently* publishes under the referenced `feed_name` for an unrelated purpose. This is plausible whenever an oracle: republishes user-supplied data verbatim, publishes hashes/commitments computed from short/attacker-influenced strings, or reuses a single feed name for both "real" Merkle roots and other single values. The complete absence of a `siblings.length > 0` (or equivalent "was this proof against a real multi-leaf tree") check means the security of the whole `'in merkle'` mechanism silently depends on oracle behavior outside of `ocore`'s control, rather than on cryptographic membership proof of a real set.

### Recommendation
- In `merkle.js`'s `verifyMerkleProof`, require `Array.isArray(proof.siblings) && proof.siblings.length > 0` before doing the verification (or make the zero-sibling/single-leaf case an explicit, separately-flagged code path rather than an implicit fallthrough).
- Mirror the same `siblings.length > 0` requirement in `is_valid_merkle_proof` in `formula/evaluation.js` (currently only an upper bound of 50 is enforced) and in the `'in merkle'` authentifier handling in `definition.js`.
- Document/communicate to oracle operators that a Merkle root over a single-element set is indistinguishable from a plain hash of that element, and that feed names used for Merkle roots must not be reused for arbitrary/attacker-influenced hash values.

### Proof of Concept
1. Attacker creates an address whose definition includes `['in merkle', [[oracle_address], 'whitelist', 'attacker_chosen_string']]`, as validated by `definition.js` lines 445–478 (only format of `'attacker_chosen_string'` is checked).
2. Attacker waits for/induces the oracle to publish, under feed name `'whitelist'`, a data-feed value `V` that happens to equal `sha256('attacker_chosen_string')` in base64 - plausible if the oracle echoes user-submitted hashes or commitments under that feed for unrelated business logic.
3. Attacker submits a unit spending from that address with authentifier `serialized_proof = "0-" + V` (index `0`, zero siblings, root `V`).
4. `definition.js` line 1014–1016 calls `merkle.deserializeMerkleProof` then `merkle.verifyMerkleProof('attacker_chosen_string', proof)`, which succeeds trivially since `hash(element) === proof.root === V` with no siblings.
5. `dataFeeds.dataFeedExists` at line 1020 confirms `V` was indeed published by the oracle (true, since it published it for an unrelated reason), and the authentifier check passes - authorizing the spend/AA payout despite `'attacker_chosen_string'` never having been part of any real committed whitelist.

// returns a string element_index-siblings_joined_by_dash-root
function serializeMerkleProof(proof){
	var serialized_proof = proof.index;
	if (proof.siblings.length > 0)
		serialized_proof += "-"+proof.siblings.join("-");
	serialized_proof += "-"+proof.root;
	return serialized_proof;
}

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
