### Title
Webhook signature verification key is selected from the same untrusted payload field, allowing organization/repository binding confusion - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which HMAC `webhook_secret`) is used to validate `X-Hub-Signature`, based on `repository_owner`, a field read directly out of the *unverified* request body. The actual repository/stack that is mutated by the webhook handlers is derived from a different field of that same unverified body, `repository.full_name`. Nothing enforces that these two fields agree, so an attacker who knows the name of *any* GitHub organization configured in a multi-org Shipit deployment can pick whichever organization's signature check is weakest (e.g. one configured without a `webhook_secret`) while pointing the payload's `repository.full_name` at a stack belonging to a completely different, properly-secured organization.

### Finding Description
`verify_signature` computes the verification key before the signature has been checked: [1](#0-0) [2](#0-1) 

`repository_owner` is taken straight from the JSON body (`params.dig('repository', 'owner', 'login')`), which is fully attacker-controlled at this point since no signature has been verified yet. It is used to fetch the org-specific GitHub App config via `Shipit.github(organization: repository_owner)`, and `verify_webhook_signature` explicitly treats a missing `webhook_secret` as automatically valid: [3](#0-2) 

Separately, once the request passes (or bypasses) this check, `WebhooksController#create` dispatches the *whole* raw payload to handlers: [4](#0-3) 

Every handler resolves its target `Stack`/`Repository` from a *different* field of the same payload, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

Shipit explicitly supports multiple GitHub App configurations per organization (one config block per org, each with its own optional `webhook_secret`): [7](#0-6) 

and the setup docs confirm `webhook_secret` is optional per app: [8](#0-7) 

The equality this breaks is: `organization authenticated by verify_signature (payload.repository.owner.login)` != `repository actually written by the handler (payload.repository.full_name)`. Since no code anywhere cross-checks that `repository.owner.login` matches the owner segment of `repository.full_name`, an attacker can supply a payload where these two fields diverge: use the org with no/weak `webhook_secret` to pass `verify_signature`, but point `repository.full_name` at a stack under a different, secured org.

### Impact Explanation
If any organization configured on the Shipit instance has no `webhook_secret` set (an explicitly supported, documented "optional" configuration), signature verification degrades to a no-op for payloads claiming that organization as `repository.owner.login`, `verify_webhook_signature` returns `true` unconditionally: [9](#0-8) . Combined with `repository.full_name` selecting an unrelated target stack, an unauthenticated attacker can forge GitHub events (`push`, `status`, `check_suite`, `pull_request`, etc.) against any stack tracked by the Shipit instance. Forging `status`/`check_suite` events can flip a malicious commit's CI state to "success," making it appear deployable and enabling an unauthorized deploy, satisfying the Critical-impact criterion for "an unauthorized deploy."

### Likelihood Explanation
Exploitability requires: (1) the target Shipit instance hosts more than one GitHub organization (a supported, documented configuration), and (2) at least one of those organizations has no `webhook_secret` configured. Both conditions are plausible in real deployments (the secret is explicitly optional per the setup docs), and the attacker needs only the organization's public login name, no secret, token, or privileged access, to exploit it. The `GithubOrganizationUnknown` rescue only rejects fully unconfigured org names, so the attack surface is any configured-but-unsecured org.

### Recommendation
Verify the webhook signature using the same repository context that will actually be acted upon (i.e., derive the verification key from `repository.full_name`'s owner, not a separately-trusted `repository.owner.login`), and reject (or require an explicit administrator opt-in with a warning) any organization configuration that omits `webhook_secret`. Additionally, cross-validate that `repository.owner.login`/`organization.login` matches the owner segment of `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Shipit is configured with two GitHub App entries, `OrgA` (has `webhook_secret` set) and `OrgB` (no `webhook_secret`, as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/victim-repo" },
  "sha": "<malicious-commit-sha>",
  "state": "success",
  "context": "ci/tests"
}
```
No valid `X-Hub-Signature` is required because `Shipit.github(organization: "OrgB")` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally.
3. `WebhooksController#create` forwards the payload to `StatusHandler`, which resolves the target via `payload.dig('repository', 'full_name')` = `"OrgA/victim-repo"`, marking the malicious commit as passing CI on `OrgA`'s stack, without ever validating a signature tied to `OrgA`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
