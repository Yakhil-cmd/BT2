### Title
`data_feed`/`in_data_feed` oracle reads in AAs have no default staleness enforcement — ([File: data_feeds.js])

### Summary
The oscript primitives `data_feed[[...]]` and `in_data_feed[[...]]`, which Autonomous Agents use to consume oracle price/data feeds, only filter results by an *optional* `min_mci` bound. If the AA author omits `min_mci` (as done even in the shipped sample contract), the primitive will happily return/accept the last value the oracle *ever* posted, no matter how old, exactly mirroring the reported Chainlink issue where `latestRoundData()` freshness (`updatedAt`) is never checked.

### Finding Description
`readDataFeedValue`/`readDataFeedByAddress` and `dataFeedExists`/`dataFeedByAddressExists` in `data_feeds.js` locate the most recent data-feed record satisfying `feed_name`/`relation`/`value` whose MCI falls in `[min_mci, max_mci]` [1](#0-0) [2](#0-1) . `max_mci` is always bound to the current `last_ball_mci`/`mci`, but `min_mci` defaults to `0` unless the oscript author explicitly supplies it [3](#0-2) [4](#0-3) . This means, absent an explicit `min_mci`, the search range is effectively "any block since genesis," so a value posted by the oracle years ago and never updated since will still be returned as valid.

Validation of the `data_feed`/`in_data_feed` parameters in `formula/validation.js` treats `min_mci` purely as an optional, syntactically-checked integer — there is no requirement that it be present, nor any recency/mci-distance check enforced by the engine itself [5](#0-4) [6](#0-5) .

The shipped sample contract in the codebase demonstrates exactly this unsafe usage pattern — it reads a price feed with no `min_mci`/freshness bound at all before making an irrevocable payout decision:
```
if (trigger.data.winner == 'yes' AND data_feed[[oracles='X55IWSNMHNDUIYKICDW3EOYAWHRUKANP', feed_name='GBYTE_USD']] > 60)
``` [7](#0-6) 

While it is technically possible for an AA author to fetch the matched `unit` (`what='unit'`) and separately call `unit[unit_hash].timestamp` to self-implement a staleness check [8](#0-7) , this is not the default or even the documented path, and none of the built-in helpers (`data_feed`, `in_data_feed`, `dataFeedExists`, `readDataFeedValue`) enforce or even nudge toward it — the "mci" returned internally for unstable AA candidates is not even the feed's real MCI (`mci: max_mci // it doesn't matter`) [9](#0-8) , further discouraging correct staleness verification by AA developers relying on internal semantics.

### Impact Explanation
Any AA that consumes an oracle data feed (e.g., price oracles for prediction markets, DEX-like contracts, or option contracts as in the shipped sample) without explicitly bounding `min_mci` will accept arbitrarily stale data as current. If the oracle operator stops posting updates (goes offline, is compromised, or the feed becomes economically unviable to maintain), any AA trigger sent by an unprivileged user can still be evaluated against the stale last-known value, causing the AA to release funds, settle a bet/option, or otherwise act on data that no longer reflects reality. This can lead to concrete unauthorized fund loss inside the AA, since a triggering user fully controls when to send the triggering unit and can time it to exploit outdated data.

### Likelihood Explanation
High likelihood in practice: the vulnerability is not a rare edge case but the *default* behavior of the primitive — a developer must actively opt in to safety by adding `min_mci`, and the shipped example contract in this very repository fails to do so. Any unprivileged AA trigger sender can exploit an AA relying on this default behavior once the underlying oracle becomes stale, with no special privileges required.

### Recommendation
- Require `min_mci` (or an equivalent explicit recency bound, e.g. `max_age`) as mandatory in `validateDataFeed`/`validateDataFeedExists` in `formula/validation.js`, rather than optional.
- Alternatively, expose the actual feed-record MCI/timestamp as part of the `data_feed[[...]]` result (not just via a secondary `unit[]` lookup) so staleness checks are cheap and natural to write, and fix the internal `mci: max_mci` placeholder in `readDataFeedValue` (`data_feeds.js`) to reflect the true MCI of the matched record for unstable candidates.
- Document and strongly encourage (or enforce via linting in oscript validation) that AAs consuming a data feed always pair it with a freshness/`min_mci` check, analogous to checking `updatedAt` after `latestRoundData()`.

### Proof of Concept
1. An oracle address `O` posts `GBYTE_USD = 65` at MCI 1000, then stops posting (goes offline/compromised).
2. An AA is defined exactly as in `test/samples/option_contract.oscript`:
   ```
   if (trigger.data.winner == 'yes' AND data_feed[[oracles='O', feed_name='GBYTE_USD']] > 60)
       var['winner'] = 'yes';
   ```
3. At MCI 50000 (long after the oracle stopped updating, and long after the real market price has fallen below 60), an unprivileged user sends a trigger unit with `data.winner = 'yes'`.
4. `readDataFeedValue`/`getDataFeed` in `formula/evaluation.js` searches `[min_mci=0, max_mci=50000]`, finds the stale `65` value posted at MCI 1000, and returns it — the AA settles `winner = 'yes'` and pays out based on data that is 49000 blocks stale, with no freshness check ever performed. 				break;
