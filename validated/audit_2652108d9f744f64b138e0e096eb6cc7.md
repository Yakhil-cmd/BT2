### Title
Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with a global, unscoped `Commit.where(sha: params.sha)` query, unlike `PushHandler` and `CheckSuiteHandler`, which both filter through `stacks` (i.e. `Repository.from_github_repo_name(repository_name)&.stacks`). Any organization with a valid GitHub App webhook secret can forge a `status` event for a sha that also exists in another tenant's stack and mutate that unrelated commit's CI status.

### Finding Description
The binding that must hold is: `repository_owner_that_signed_the_payload == repository_owning_every_Commit_row_mutated_by_the_handler`. `WebhooksController#verify_signature` only proves the payload was signed by `Shipit.github(organization: repository_owner)`'s webhook secret [1](#0-0) , it says nothing about which `Commit` rows the handler is allowed to touch.

`StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This query has no `repository`/`stack` scoping at all, whereas `PushHandler#process` scopes through `stacks.not_archived.where(branch:)` [3](#0-2)  and `CheckSuiteHandler#process` scopes through `stacks.where(branch:).each { |stack| stack.commits.where(sha:) }` [4](#0-3) , both of which derive `stacks` from `Repository.from_github_repo_name(repository_name)` in the base `Handler` class [5](#0-4) .

The `commit_id`/`sha` uniqueness constraint is only `(sha, stack_id)` unique — it explicitly allows the same sha to exist under multiple different `stack_id`s [6](#0-5) , which is exactly the scenario needed for shared commit history (forks, mirrors, shared upstream) or short-sha collisions across tenants.

Exploit flow: attacker owns/controls `org-attacker`'s GitHub App installation and thus its real `webhook_secret`. They POST to `/webhooks` with `X-Github-Event: status` and a valid signature, body `{'repository':{'owner':{'login':'org-attacker'}}, 'sha':'<shared-sha>', 'state':'success', 'context':'ci/attacker'}`. `verify_signature` resolves `Shipit.github(organization: 'org-attacker')` and correctly verifies the signature [7](#0-6) , then `StatusHandler.call` runs and iterates over every `Commit` row across all stacks/tenants whose `sha` matches, calling `commit.create_status_from_github!(params)` on each — including commits belonging to `org-victim`'s stack. That method creates a `Status` row, which can flip `commit.state` and trigger `ProcessMergeRequestsJob`/`enable_ci!`/`schedule_continuous_delivery` as shown in the existing test suite for `#add_status` [8](#0-7) , potentially gating or unblocking a victim's deploy pipeline.

No existing guard closes this gap: `verify_signature` only authenticates the org named in the payload, not the commits touched; `ExplicitParameters` only validates the shape of `sha`/`state`/etc., not ownership; there is no `require_permission!`/`Stack` scoping anywhere in `StatusHandler`.

### Impact Explanation
An attacker who owns any GitHub App installation pointed at Shipit can write `Status` rows onto commits belonging to a completely different tenant's `Stack`, as long as the sha happens to match (shared upstream history, cherry-picks, or forked repos sharing commits are common). This can flip a victim commit's CI state to `success`/`failure`, gating `merge_requests`/`deployable?` checks and causing an unauthorized deploy or blocking a legitimate one — squarely matching the "payload for one repository mutating another's stack/commit" Critical category. The attack is trivially repeatable against any sha the attacker can discover or guess (e.g., via a public repo's commit history that was forked/mirrored into a private Shipit-tracked stack).

### Likelihood Explanation
Preconditions are low-cost for the attacker: they only need their own legitimate GitHub App/organization installed on Shipit (which is a normal, unprivileged setup step available to anyone who can install a GitHub App), not any credential belonging to the victim. The only additional requirement is a sha collision, realistic for shared/forked repository histories or intentionally chosen colliding short shas. No session, API token, or Shipit-side secret is needed beyond the attacker's own webhook secret, which they legitimately possess for their own org.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` (or iterate `stacks.flat_map(&:commits).where(sha: params.sha)`) so only commits belonging to stacks whose repository matches the payload's `repository.full_name`/owner are updated, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```

### Proof of Concept
minitest plan (controller or handler-level test):
1. Create two `Repository`/`Stack` fixtures, `org-attacker/repo` and `org-victim/repo`, each with a `Commit` sharing the same `sha` value (allowed by the `(sha, stack_id)` unique index).
2. Stub/allow `Shipit.github(organization: 'org-attacker')#verify_webhook_signature` to return `true` (simulating a validly signed request from `org-attacker`'s real secret).
3. POST `/webhooks` with `X-Github-Event: status` and body `{'repository': {'owner': {'login': 'org-attacker'}}, 'sha': shared_sha, 'state': 'success', 'context': 'ci/attacker'}`.
4. Assert both `org_attacker_commit.statuses.reload` and `org_victim_commit.statuses.reload` now contain the forged `success` status — i.e. assert `create_status_from_github!` was invoked on the victim's commit despite the payload only authenticating `org-attacker`. Before the fix this assertion passes (vulnerable); after applying the `stacks`-scoped fix, only `org_attacker_commit` gets the new status and the victim's `statuses` count is unchanged.
