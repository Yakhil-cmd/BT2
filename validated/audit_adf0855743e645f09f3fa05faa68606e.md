### Title
CCMenu API token scoped to one stack can read the build status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the `stack` lookup helper defined in `Api::BaseController` in a way that discards the per-stack scoping enforced for every other API endpoint. This lets a `read:stack`-scoped `ApiClient` token that was only authorised for one stack read the CCMenu status (build state, last build label, activity, web URL) of any other stack in the installation, simply by changing the `stack_id` in the request path.

### Finding Description
`ApiClient` records can optionally be bound to a single `Stack` (`belongs_to :stack, optional: true`) [1](#0-0) . `Api::BaseController` enforces this binding for every controller that inherits from it by scoping the visible stacks to the token's `stack_id` when the token is stack-bound:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`Api::CCMenuController`, however, redefines `stack` to bypass `stacks` entirely and resolve the record directly from `Stack`:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [3](#0-2) 

`require_permission :read, :stack` on `#show` only checks that the token carries the `read:stack` permission string; it never checks that `current_api_client.stack_id` matches the requested `stack_id` [4](#0-3) [5](#0-4) . Because the override in `CCMenuController` re-implements `stack` without the `stacks` filter, the equality the rest of the API enforces — `current_api_client.stack_id == requested stack_id` (or `current_api_client.stack_id?` is false) — is silently dropped for this one endpoint.

This is the direct analog of the reported bug class: two code paths are supposed to share the same trust boundary (a token authorizes exactly the stack(s) in `stacks`), but one consumer (`CCMenuController#stack`) reimplements the lookup and skips the check, exactly like `ConcentratedLiquidityPosition.collect()` draining a balance that was supposed to be reserved for a different, disjoint accounting bucket.

### Impact Explanation
A stack-scoped `ApiClient` token (the class of token explicitly meant to be handed to lower-trust integrations, e.g. embedded in a CCMenu URL as shown in `CCMenuUrlController#fetch` which builds `?token=...` links per stack, [6](#0-5) ) can be replayed against `/api/stacks/:stack_id/ccmenu.xml` with any other stack's identifier to read that stack's build status, last build label/time, activity and web URL — data the token holder was never granted access to. This is an escalation into stack read authorization (cross-stack information disclosure) beyond the scope the deploying organization intentionally granted the token.

### Likelihood Explanation
Any holder of a stack-scoped, `read:stack` `ApiClient` token (a routine, low-privilege credential distributed for CI dashboards/status badges) can trigger this by simply substituting the `stack_id` route parameter — no additional secrets, GitHub access, or elevated session are required. This is straightforward to exploit for anyone already holding such a token.

### Recommendation
Have `Api::CCMenuController#stack` reuse the scoped `stacks` helper from `Api::BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the `current_api_client.stack_id` binding is enforced consistently with every other API controller.

### Proof of Concept
1. An administrator creates (or a user generates via the "CCMenu URL" feature) an `ApiClient` scoped to `Stack A` with `permissions: ['read:stack']`, and obtains its `authentication_token`.
2. The attacker (holder of that token) issues:
   `GET /api/stacks/<stack_B_param>/ccmenu.xml?token=<token_scoped_to_A>`
3. `authenticate_api_client` in `CCMenuController` authenticates the token successfully via `ApiClient.authenticate(token)` [7](#0-6) .
4. `require_permission :read, :stack` passes because the token has the `read:stack` permission string, regardless of which stack is requested [8](#0-7) .
5. `#show` calls `stack.deploys_and_rollbacks.last`, where `stack` resolves via the unscoped override to `Stack.from_param!(params[:stack_id])`, returning `Stack B` — a stack outside the token's authorised scope [9](#0-8) .
6. The response renders `Stack B`'s build status, proving the token's authorised stack (`A`) diverged from the stack actually touched (`B`).
