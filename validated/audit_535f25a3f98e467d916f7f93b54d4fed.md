Based on my research, I found a genuine analog in nearcore's protocol-parameter validation logic. Let me lay out the finding.

### Title
Missing lower-bound validation on `storage_amount_per_byte` allows storage staking economics to be configured into a "free storage" state, enabling unbounded state growth by unprivileged accounts - ([File: core/chain-configs/src/genesis_validate.rs])

### Summary
The Sherlock report describes a lending protocol where admin-settable economic thresholds (`minDebt`, `minBorrow`) can be configured to values so low that the protocol's intended economic safety mechanism (liquidation incentive) stops working, letting positions accrue as bad debt. The structurally identical pattern exists in nearcore's storage-staking economics: `storage_amount_per_byte` is the parameter that is supposed to guarantee every byte of on-chain state is backed by a locked balance [1](#0-0) , but nothing in genesis or runtime-config validation enforces that this value stays above a safe minimum, unlike several other economic/consensus parameters that do have explicit bound checks.

### Finding Description
`check_storage_stake` computes `required_amount = storage_amount_per_byte * billable_storage_bytes` and only fails if the account's balance is insufficient to cover that requirement [2](#0-1) . If `storage_amount_per_byte` is configured to a very low (non-zero, so not blocked by the explicit `calimero_zero_storage` guard) value, `required_amount` for any realistic amount of storage rounds down to a negligible number, meaning ordinary unprivileged accounts can grow arbitrarily large contract storage (`data: BTreeMap<Vec<u8>, Vec<u8>>`) while paying a vanishingly small locked balance - functionally "free storage."

This is directly analogous to the Sherlock finding: an economically-critical threshold is admin/genesis-configurable, is documented/tested as being safely reducible to exactly zero for some deployments (`test_calimero_storage_costs_zero` asserts `storage_amount_per_byte().is_zero()` is a supported configuration) [3](#0-2) , yet unlike other genesis/runtime parameters, it has no minimum-value sanity check anywhere in the validation pipeline.

By contrast, `genesis_validate.rs`'s `validate_processed_records` explicitly bounds several other economic/consensus values - e.g. rejecting `online_max_threshold <= online_min_threshold`, requiring `gas_price_adjustment_rate < 1`, and bounding numerator/denominator sizes to avoid overflow [4](#0-3) . `config_validate.rs` similarly enforces bounds like `tx_routing_height_horizon >= 2` [5](#0-4) . No equivalent check exists for `storage_amount_per_byte`, `min_gas_purchase_price`, or `account_creation_charge` in either `validate_genesis` or `RuntimeConfig::try_from` [6](#0-5) .

### Impact Explanation
If a network operator (mainnet, or more plausibly a custom/appchain deployment building on this codebase, similar to the Calimero zero-storage config already present) sets `storage_amount_per_byte` to a near-zero-but-nonzero value believing it is a safe cost-reduction knob (exactly the scenario the original report warns about for `minDebt`/`minBorrow`), any unprivileged account can submit ordinary `FunctionCall`/`DeployContract`/`CreateAccount` transactions to accumulate large amounts of trie state while being charged negligible locked balance. This is unbounded resource use / free storage matching the impact criteria: state bloat across all validators, increased witness/proof sizes, and potential chain-wide performance degradation or stall, all triggerable purely through normal transaction submission with no special privilege.

### Likelihood Explanation
Likelihood depends entirely on an operator misconfiguring `storage_amount_per_byte` to a very low value - the same "trusted admin sets an unsafe-but-technically-allowed value" precondition that the original Sherlock issue was judged Medium severity on. Since nearcore already ships a first-class code path (`calimero_zero_storage`) demonstrating this exact value is treated as a legitimate, low-friction configuration knob, and there is no validation anywhere preventing an operator from setting it to `1` yoctoNEAR/byte instead of `0`, the misconfiguration is realistic for non-mainnet deployments (which this codebase is explicitly designed to support via `RuntimeConfigStore::for_chain_id` and custom genesis/runtime configs).

### Recommendation
Add a genesis/runtime-config validation check (mirroring the bound checks already present in `genesis_validate.rs` for `online_min_threshold`/`online_max_threshold`/`gas_price_adjustment_rate`) that either: (1) rejects `storage_amount_per_byte` values below a documented safe floor unless a dedicated feature flag (as already exists for `calimero_zero_storage`) is explicitly enabled, or (2) requires operators to acknowledge via an explicit opt-in flag when deploying with sub-threshold storage economics, consistent with how zero-storage is already gated behind the `calimero_zero_storage` cargo feature rather than being reachable through arbitrary config edits.

### Proof of Concept
1. Deploy a nearcore-based chain with a custom `RuntimeConfig` where `fees.storage_usage_config.storage_amount_per_byte` is set to `1` yoctoNEAR (a value that passes all existing validation in `parameter_table.rs`/`genesis_validate.rs`).
2. As an unprivileged account, submit a stream of ordinary `FunctionCall` transactions to a deployed contract that writes large key-value entries to its storage trie.
3. Observe via `check_storage_stake` that `required_amount = storage_amount_per_byte(1) * billable_storage_bytes` remains far below the account's balance even after storing megabytes of data, since the multiplier is effectively negligible [7](#0-6) .
4. Repeat across many accounts to grow global state size with near-zero aggregate locked balance, demonstrating free/underpriced storage and unbounded resource growth with no code path currently preventing this misconfiguration.

pub fn check_storage_stake(
    account: &Account,
    account_balance: Balance,
    runtime_config: &RuntimeConfig,
) -> Result<(), StorageStakingError> {
    let billable_storage_bytes = account.storage_usage();
    let required_amount = runtime_config
        .storage_amount_per_byte()
        .checked_mul(u128::from(billable_storage_bytes))
        .ok_or_else(|| {
            format!(
                "Account's billable storage usage {} overflows multiplication",
                billable_storage_bytes
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    let available_amount = account_balance
        .checked_add(account.locked())
        .ok_or_else(|| {
            format!(
                "Account's amount {} and locked {} overflow addition",
                account.amount(),
                account.locked(),
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    if available_amount >= required_amount {
        Ok(())
    } else {
        if is_zero_balance_account(account) {
            return Ok(());
        }
        Err(StorageStakingError::LackBalanceForStorageStaking(
            required_amount.checked_sub(available_amount).unwrap(),
        ))
    }
