### Title
Terminal escape/OSC injection via unsanitized attacker-controlled markdown body/title text rendered by `Render` - (File: pkg/markdown/markdown.go)

### Summary
`Render` in [1](#0-0)  is a thin pass-through to `ghMarkdown.Render` (go-gh/glamour) with no output sanitization, and it is used across `gh pr view`, `gh issue view`, `gh release view`, `gh repo view`, `gh discussion view`, and comment rendering to print attacker-authored bodies directly to the terminal. Unlike other content paths in this codebase that explicitly neutralize ANSI/OSC escape sequences before writing untrusted bytes to a terminal, none of the `markdown.Render` call sites wrap the input/output in the `iostreams.Untrusted` sanitizer or the `asciisanitizer` transform, so literal control bytes embedded in a PR/issue body, comment, or release note text node can reach the terminal unmodified.

### Finding Description
`markdown.Render` at [1](#0-0)  forwards `text` straight to `ghMarkdown.Render(text, opts...)` with no pre- or post-processing. Its result is then written directly with `fmt.Fprint`/`fmt.Fprintf` to `io.Out` in numerous call sites, e.g.:
- `pkg/cmd/pr/view/view.go` (PR body) [2](#0-1) 
- `pkg/cmd/pr/shared/comments.go` (comment body) [3](#0-2) 
- `pkg/cmd/release/view/view.go` (release body) [4](#0-3) 
- `pkg/cmd/repo/view/view.go` (README) [5](#0-4) 
- `pkg/cmd/discussion/view/view.go` (discussion body/comments) [6](#0-5) 
- `pkg/cmd/pr/create/create.go` (title, printed raw with `cs.Bold`, and body via `markdown.Render`) [7](#0-6) 

None of these paths route the attacker-controlled body/title through `iostreams.NewUntrusted(...)` (whose `String()` applies the `asciisanitizer` transform to strip control bytes) as is done for gist raw content [8](#0-7)  or `iostreams.ContainsEscapeSequence` checks as used in `pkg/cmd/repo/read-file/read_file.go` [9](#0-8) . Markdown text-node content (as opposed to markdown syntax) is passed through by goldmark/glamour largely unmodified into styled ANSI spans, so a literal ESC byte (0x1B) embedded in an issue/PR body, comment, or release note is not markdown syntax and is not filtered by any sanitizer in this codebase before reaching the user's terminal via `Render`.

By contrast, the project explicitly acknowledges and defends against this exact class of attack in adjacent code paths — e.g., the acceptance test for `gh run view --log` [10](#0-9)  and the `copyLogWithLinePrefix` unit test asserting ESC bytes never reach output [11](#0-10)  — but the markdown rendering pathway used for `gh pr view`/`gh issue view`/`gh release view`/`gh repo view` has no equivalent guard.

However, I was **not able to verify** the actual byte-level behavior of `ghMarkdown.Render`/`glamour`'s ANSI renderer (whether it re-encodes/escapes control bytes found in text nodes, and whether hyperlink URIs are scheme-restricted to http/https for OSC 8 output) because the `go-gh` and `charmbracelet/glamour` package sources are external dependencies not present in this repository's index — only `go.mod`/`go.sum` references were found, not vendored source. This is the key uncertain link in the chain: if glamour's ANSI renderer itself already strips/escapes C0 control bytes and restricts hyperlink schemes internally (which is plausible for a terminal-rendering library), then no additional application-level bug exists here, and this would be a dependency-behavior question rather than a bug in this repo's code — which the audit rules direct me to reject if it depends "only on ... dependency bugs alone."

### Impact Explanation
If glamour does pass through literal control bytes/OSC sequences from text-node content (unverified), the impact would be terminal escape sequence injection reaching the victim's terminal when running `gh pr view`, `gh issue view`, `gh release view`, or `gh repo view` on attacker-published content, potentially including OSC 8 hyperlinks with non-http URIs, title-set/report sequences, or bracketed-paste manipulation. This maps to GitHub's RCE-in-gh bounty class only if it can be chained with a terminal-emulator vulnerability (e.g., bracketed-paste injection tricking the shell into executing attacker text) — the CLI itself does not execute the escape sequences; the victim's terminal emulator does.

### Likelihood Explanation
Cannot be assessed with confidence without access to `go-gh`/`glamour`'s actual rendering internals, which are outside this repository's indexed source. The repository's own code (`pkg/markdown/markdown.go` and all call sites) applies no control-byte sanitization to markdown-rendered output, which is inconsistent with the sanitization pattern applied everywhere else in the codebase for untrusted content, but I cannot confirm whether this is exploitable in practice or is already mitigated inside the vendored rendering library.

### Recommendation
Given the uncertainty about the dependency's internal handling, recommend: (1) confirm via a unit test whether `ghMarkdown.Render`/`glamour.TermRenderer` passes raw ESC (0x1B) bytes embedded in markdown text nodes and image/link title text through to its output unmodified; (2) if so, apply the existing `iostreams.Untrusted`/`asciisanitizer` transform to the *result* of `markdown.Render` (not just to raw/non-markdown content) at each call site before writing to `io.Out`, consistent with how gist raw content and run logs are already handled; (3) verify hyperlink emission (if any OSC 8 support is enabled) restricts schemes to `http`/`https` and encodes URIs so embedded control bytes cannot break out of the OSC 8 sequence.

### Proof of Concept
```go
// pkg/markdown/markdown_escape_test.go
package markdown

import (
    "strings"
    "testing"
)

func TestRender_DoesNotLeakControlBytesFromBody(t *testing.T) {
    payload := "Normal text \x1b]0;HIJACKED\x07 more text \x1b[31mred\x1b[0m"
    out, err := Render(payload)
    if err != nil {
        t.Fatal(err)
    }
    if strings.ContainsRune(out, '\x1b') {
        t.Fatalf("rendered markdown leaked raw ESC byte, terminal escape injection possible: %q", out)
    }
}
```
Expected assertion: the test should fail today if `ghMarkdown.Render` does not strip/neutralize embedded ESC bytes in text content, confirming the gap; if it already passes, the finding is invalid because the sanitization happens transparently inside the dependency and no application-level fix is needed. I could not execute this test against the actual `go-gh`/`glamour` versions pinned in `go.mod` to confirm the result, since those package internals were not available in the indexed codebase context.

func TestCopyLogWithLinePrefix_TerminalEscapeSequences(t *testing.T) {
	tests := []struct {
		name  string
		input string
	}{
		{
			name:  "OSC title set sequence",
			input: "normal prefix\x1b]0;HIJACKED TITLE\x07trailing text\n",
		},
		{
			name:  "CSI color sequence",
			input: "\x1b[31mRED TEXT\x1b[0m normal text\n",
		},
		{
			name:  "screen title set sequence used in original report",
			input: "\x1bk;echo this is an arbitrary command;\x1b\\\n",
		},
		{
			name:  "CSI window title query",
			input: "before\x1b[21tafter\n",
		},
		{
			name:  "multiple escape sequences",
			input: "\x1b]0;title\x07\x1b[31mred\x1b[0m\x1b[21t\n",
		},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			var buf bytes.Buffer
			err := copyLogWithLinePrefix(&buf, strings.NewReader(tt.input), "jobname\tstep\t")
			require.NoError(t, err)

			output := buf.String()
			assert.NotContains(t, output, "\x1b",
				"output should not contain raw ESC (0x1b) bytes, got: %q", output)
		})
	}
