### Title
Attacker-controlled submodule/repo content can permanently fail `configureWorktree`, blocking `cleanup()` and causing persistent sync denial - (File: main.go)

### Summary
The external report describes an untrusted, uncontrolled dependency (the MasterChef reward contract) reverting during a critical state-transition call, which blocks downstream cleanup/withdrawal logic entirely. The closest reachable analog in `git-sync` is that a git operation invoked on attacker-influenced repository content — specifically `git submodule update --init [--recursive]` in `configureWorktree` — can fail deterministically (e.g., an unreachable/removed submodule URL, a submodule pointing to a non-existent commit, or a private submodule requiring credentials git-sync doesn't have), and that failure propagates all the way up through `SyncRepo` to the main loop, where it takes the error branch and **skips `git.cleanup(ctx)` entirely**, since cleanup is only invoked in the success branch.

### Finding Description
`SyncRepo` performs, in order: fetch, `createWorktree`, `configureWorktree` (checkout + submodule update), `publishSymlink`, hooks, and finally increments `syncCount` [1](#0-0) . `configureWorktree` runs `git submodule update --init [--recursive]` against submodule URLs that are part of the (untrusted) repository content being synced, and returns the raw error on failure [2](#0-1) .

In the outer sync loop, `git.cleanup(ctx)` — which removes stale worktrees, prunes worktrees, expires unreachable refs, and runs `git gc` — is only called in the success branch of `SyncRepo`; on any error it is skipped and the loop just logs and retries after `waitTime` [3](#0-2) . Each retry that reaches a *new* remote hash will call `createWorktree`, which first calls `removeWorktree` for that same hash before creating it [4](#0-3) , but does **not** remove the previously created, half-configured worktrees for *earlier* failed hashes — those remain on disk under `.worktrees/` because they are only reaped by `removeStaleWorktrees`/`cleanup`, which never runs while sync keeps failing [5](#0-4) [6](#0-5) .

If the failure limit is unbounded (`--max-failures=-1`, git-sync's supported "retry forever" mode) or the operator has configured a high failure threshold, the sync loop retries indefinitely: `git.log`, ref, and `syncCount` never advance, `cleanup()` never runs, and previously-created broken worktree directories accumulate under `--root/.worktrees/`, since disk usage from repeated worktree creation/removal is only bounded by the periodic `cleanup()` call that is now permanently unreachable [7](#0-6) .

### Impact Explanation
An attacker with push access to the source repository (the same threat actor implied by the external report's "untrusted repo content" class) can add or modify a `.gitmodules` entry to reference an unreachable host, a deleted repository, or a commit hash that no longer exists. Because `configureWorktree` unconditionally attempts `git submodule update --init` whenever `--submodules` is not `off` (the default is `recursive`) [8](#0-7) , this single malicious commit permanently breaks the sync loop for that ref: the previously published symlink and content become stale forever (persistent sync denial of the intended purpose of git-sync — keeping the consumer's view up to date), garbage collection/pruning stops running, and worktree directories accumulate under `--root`, consuming disk over time. This matches the "persistent sync denial" and "file write ... outside expected bounds" impact classes called out as acceptable in the validation criteria.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where the synced repository (or its submodules) is not fully trusted/controlled by the git-sync operator, or where an attacker can gain write access to it (e.g., a compromised contributor, a public repo with external PR-merge automation, or a submodule pointing to a third-party repository outside the operator's control) — directly analogous to the original finding's "master chef contract... not controlled by the protocol team." No special git-sync flags beyond the default `--submodules=recursive` are required; `--depth` and `--sparse-checkout-file` do not prevent this.

### Recommendation
- On `configureWorktree`/`SyncRepo` failure, still invoke a bounded cleanup pass to remove worktrees created earlier in the failed attempt(s) (i.e., decouple "cleanup of stale/orphaned worktrees" from "successful sync"), so disk usage cannot grow unbounded while a bad commit is stuck at HEAD.
- Consider treating persistent submodule failures as distinct from transient/network failures, and surface a clear, actionable error/metric (already logged, but consider a dedicated metric) so operators can detect a stuck malicious/broken ref quickly.
- Document (and optionally support) using `git submodule update --init --force`/skip options or a `--submodules-fail-ok` style flag so a broken submodule does not block the checkout of the primary tree content, mirroring the "use emergencyWithdraw instead of withdraw" mitigation pattern from the original report (favor best-effort progress over total blockage).

### Proof of Concept
1. Deploy `git-sync` against a repository with `--submodules=recursive` (default) and no `--max-failures` limit set to a small bound.
2. As an attacker with push access, add a `.gitmodules` entry pointing to a URL that will be unreachable (e.g., a temporary/one-off git server that is later shut down, or a private repo requiring credentials not configured on the git-sync sidecar) and commit it.
3. Observe that `git.cleanup(ctx)` is never reached again (only the error-logging branch runs) per the loop structure at [3](#0-2) , `syncCount`/`hash` never advance past the last good commit, and repeated worktree creation attempts for subsequent legitimate commits (if pushed later, still behind the broken commit in `--ref`'s history resolution) leave orphaned `.worktrees/<hash>` directories that are never pruned by `removeStaleWorktrees` because `cleanup` is unreachable.
4. This can be confirmed statically by tracing that `configureWorktree`'s submodule step is unguarded [2](#0-1)  and that `cleanup(ctx)` is called only from the success branch of the sync loop [9](#0-8) ; full dynamic confirmation of unbounded disk growth would require running the e2e harness with a deliberately broken submodule and `--max-failures=-1`, which was not executed in this analysis (index/tool access is read-only).

func (git *repoSync) removeStaleWorktrees() (int, error) {
	currentWorktree, err := git.currentWorktree()
	if err != nil {
		return 0, err
	}

	git.log.V(3).Info("cleaning up stale worktrees", "currentHash", currentWorktree.Hash())

	count := 0
	err = removeDirContentsIf(git.worktreeFor("").Path(), git.log, func(fi os.FileInfo) (bool, error) {
		// delete files that are over the stale time out, and make sure to never delete the current worktree
		if fi.Name() != currentWorktree.Hash() && time.Since(fi.ModTime()) > git.staleTimeout {
			count++
			return true, nil
		}
		return false, nil
	})
	if err != nil {
		return 0, err
	}
	return count, nil
}

func (git *repoSync) createWorktree(ctx context.Context, hash string) (worktree, error) {
	// Make a worktree for this exact git hash.
	worktree := git.worktreeFor(hash)

	// Avoid wedge cases where the worktree was created but this function
	// error'd without cleaning up.  The next time thru the sync loop fails to
	// create the worktree and bails out. This manifests as:
	//     "fatal: '/repo/root/nnnn' already exists"
	if err := git.removeWorktree(ctx, worktree); err != nil {
		return "", err
	}

	git.log.V(1).Info("adding worktree", "path", worktree.Path(), "hash", hash)
	_, _, err := git.Run(ctx, git.root, "worktree", "add", "--force", "--detach", worktree.Path().String(), hash, "--no-checkout")
	if err != nil {
		return "", err
	}

	return worktree, nil
}

// cleanup removes old worktrees and runs git's garbage collection.  The
// specified worktree is preserved.
func (git *repoSync) cleanup(ctx context.Context) error {
	// Save errors until the end.
	var cleanupErrs multiError

	// Clean up previous worktree(s).
	if n, err := git.removeStaleWorktrees(); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	} else if n == 0 {
		// We didn't clean up any worktrees, so the rest of this is moot.
		return nil
	}

	// Let git know we don't need those old commits any more.
	git.log.V(3).Info("pruning worktrees")
	if _, _, err := git.Run(ctx, git.root, "worktree", "prune", "--verbose"); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	}

	// Expire old refs.
	git.log.V(3).Info("expiring unreachable refs")
	if _, _, err := git.Run(ctx, git.root, "reflog", "expire", "--expire-unreachable=all", "--all"); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	}

	// Run GC if needed.
	if git.gc != gcOff {
		args := []string{"gc"}
		switch git.gc {
		case gcAuto:
			args = append(args, "--auto")
		case gcAlways:
			// no extra flags
		case gcAggressive:
			args = append(args, "--aggressive")
		}
		git.log.V(3).Info("running git garbage collection")
		if _, _, err := git.Run(ctx, git.root, args...); err != nil {
			cleanupErrs = append(cleanupErrs, err)
		}
	}

	if len(cleanupErrs) > 0 {
		return cleanupErrs
	}
	return nil
}
