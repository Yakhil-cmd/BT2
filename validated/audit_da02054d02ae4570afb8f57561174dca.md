### Title
Cross-tenant `Team` mutation via unscoped `github_id` lookup in `MembershipHandler#find_or_create_team!` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a `membership` webhook against the org named in `params.dig('organization', 'login')` when `repository` is absent, and `Handlers::MembershipHandler` uses that same field to tag *newly created* `Team` rows. However, `find_or_create_team!` looks up existing teams solely by `github_id`, with no check that the matched `Team#organization` equals the authenticated `organization.login`, so a signed webhook from org A can mutate an existing `Team`/`Membership` row that belongs to org B.

### Finding Description
The broken binding is: `verified_org (params.dig('organization','login'), checked in WebhooksController#verify_signature via Shipit.github(organization: repository_owner))` MUST equal `mutated_team.organization` for every write performed by `MembershipHandler#process`. This holds only when `Team.find_or_create_by!(github_id: params.team.id)` creates a *new* record — the `do |team| ... team.organization = params.organization.login end` block only runs on the create path, as seen in `app/models/shipit/webhooks/handlers/membership_handler.rb` lines 38-42:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```
If a `Team` row with that `github_id` already exists (belonging to a different, unrelated org), `find_or_create_by!` returns the existing record untouched by the block, and `process` (`app/models/shipit/webhooks/handlers/membership_handler.rb` lines 22-34) proceeds to call `team.add_member(member)` or `team.members.delete(member)` on it — with zero verification that `team.organization == params.organization.login`.

`WebhooksController#repository_owner` (`app/controllers/shipit/webhooks_controller.rb` lines 59-62) falls back to `params.dig('organization', 'login')` exactly as `MembershipHandler` does, so the org used for *authentication* is the attacker's own configured org, not the org owning the target `Team`. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb` lines 24-49) only proves the raw body was signed with `Shipit.github(organization: repository_owner).webhook_secret` — i.e., the attacker's own org's secret in a multi-org deployment (`lib/shipit.rb` `github`/`github_app_config`, lines 170-200). It says nothing about the truthfulness of `params.team.id` or any other field in that same signed body, since the attacker fully controls the JSON payload for their own org.

Attack: attacker administers (or otherwise controls the webhook configuration/secret of) org2, an org onboarded into Shipit's multi-org `github:` config but with no relationship to `Shipit.github_teams` (which, per `lib/shipit.rb` line 256-258, is derived only from the *default* org's `oauth_teams`, i.e. `github.oauth_teams`). Attacker crafts a `membership` webhook body:
```json
{"action":"added","team":{"id":<victim_team.github_id>, ...},"organization":{"login":"org2"},"member":{"login":"attacker-login"}}
```
signs it with org2's known `webhook_secret`, and POSTs to `/webhooks` with `X-Github-Event: membership`. `verify_signature` succeeds because it only checks against org2's secret. `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler`, whose `find_or_create_team!` matches the existing `Team` row (owned by an unrelated org1) purely by `github_id`, and `add_member` inserts a `Membership` record binding the attacker's chosen user into org1's `Team`.

Existing guards do not stop this: `verify_signature` only authenticates the *sender org*, not per-field organization consistency in the payload; the `ExplicitParameters` schema (`params do ... end` in `membership_handler.rb`) only validates types/presence, not cross-referential organization matching; and `Team` has no uniqueness/validation tying `github_id` to `organization`.

### Impact Explanation
A successful attack adds (or removes) an arbitrary GitHub-login user in a `Team` row that belongs to a completely unrelated org/tenant, with no relation to the attacking org. If that `Team` is one of the entries returned by `Shipit.github_teams` (default-org `oauth_teams`), and `attacker-login` corresponds to a real GitHub user the attacker controls, `User#authorized?` (`app/models/shipit/user.rb` line 80-82) grants that user Shipit-wide authorization/access because it checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`. This is escalation into `Shipit.github_teams` authorization from an unrelated tenant — matching the High/Critical impact categories (authorization write across configured orgs with no policy relationship, escalation into `Shipit.github_teams`). It is repeatable against any `Team#github_id` the attacker can learn or guess, for as long as the attacker's own org remains configured in the multi-org `github:` config.

### Likelihood Explanation
Requires a multi-org Shipit deployment where at least two independently configured orgs exist, and the attacker controls (knows) the webhook secret/app for one of them — a realistic self-service/multi-tenant onboarding scenario per `docs/setup.md`. The attacker also needs to know or guess the target `Team#github_id` (GitHub team IDs, while globally unique, are exposed via GitHub's API/UI to team members and are small integers, making enumeration plausible for a determined attacker with any org membership). Given those preconditions, exploitation cost is a single crafted HTTP POST with a correctly signed body — no other Shipit secret or session is needed.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` AND `organization` (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and/or explicitly verify `team.organization == params.organization.login` before performing `add_member`/`members.delete`, raising or dropping the event otherwise.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership webhook from org2 cannot mutate a Team owned by org1" do
  org1_team = Shipit::Team.create!(github_id: 999, organization: 'org1', name: 'Org1 Team', slug: 'org1-team', api_url: 'https://x')
  attacker_user = shipit_users(:some_user)

  payload = {
    action: 'added',
    team: { id: 999, name: 'Org1 Team', slug: 'org1-team', url: 'https://x' },
    organization: { login: 'org2' }, # attacker's own, unrelated org
    member: { login: attacker_user.login }
  }

  # simulate verify_signature succeeding for org2 only
  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload.deep_stringify_keys)

  assert_not org1_team.reload.members.include?(attacker_user),
    "org2's webhook must not be able to add a member to org1's Team"
end
```
Assert both sides of the binding: `verified_org == 'org2'` (from `params.organization.login` used in `verify_signature`) while `mutated_team.organization == 'org1'` — they diverge, proving the vulnerability, since the code currently allows `org1_team.members` to include `attacker_user` after the call.
