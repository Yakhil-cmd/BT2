### Title
Cross-organization team membership forgery via unscoped `github_id` lookup in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up an existing `Team` solely by the GitHub-supplied `team.id` (`github_id`), and only sets `organization` when the record is newly created. Because a `membership` webhook is authenticated against the organization named in its own payload (`params.dig('organization','login')`), any organization configured in Shipit's multi-org `secrets.github` map can sign a payload whose `team.id` matches a *different* organization's already-created `Team`, letting the attacker add arbitrary members to that team without ever proving control of the target organization.

### Finding Description
The intended binding is: authorization for org X's team is only reachable through a webhook whose *verified* organization equals X, for every X in a multi-org deployment.

Trace:
- `WebhooksController#verify_signature` resolves the signing org from the request body itself: `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . For a `membership` event there is no `repository` key, so this organization is exactly `params['organization']['login']` — fully attacker-controlled content, only constrained by having to be a key present in `secrets.github` (i.e., some organization the operator has configured a GitHub App/`webhook_secret` for) [3](#0-2) .
- Once the signature check passes for organization C (any configured org, including one the attacker legitimately administers in a multi-org setup), `MembershipHandler#process` runs `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) do |team| ... end` [4](#0-3) . The `do...end` block (which assigns `team.organization = params.organization.login`) only executes on **creation**. If a `Team` with that `github_id` already exists (e.g., a real team under org X that is part of `Shipit.github_teams`), the `find` branch is taken, the `organization` field is never re-checked, and the code falls straight through to `team.add_member(member)` for `action == 'added'` [5](#0-4) .
- `User.authorized?` grants access purely by team membership: `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , with no re-validation that the membership record's team organization matches any expected org.

Root cause: the `Team` model's uniqueness/lookup key (`github_id`) is disconnected from the per-organization webhook trust boundary enforced in `verify_signature`. `MembershipHandler` never asserts `team.organization == params.organization.login` before mutating membership, so the org-scoping guarantee that `verify_signature` appears to provide is not actually enforced at the point where the sensitive write (`Membership` creation) happens.

Existing guards do not close this gap: `verify_signature` only proves the payload was signed by *some* configured organization's secret, not by the organization that owns the target `Team` row; `find_or_create_team!`'s creation block is irrelevant once the target `Team` already exists; `ExplicitParameters` schema only validates types/presence, not cross-organization consistency.

### Impact Explanation
An attacker who administers (or has been granted) any organization present in Shipit's `secrets.github` map — even one unrelated to the teams used for authorization — can forge a signed `membership` webhook (`action: 'added'`, `team.id` = target team's known GitHub numeric ID, `member.login` = attacker's own login) to insert a `Membership` row into a `Team` that belongs to a completely different organization. If that team is part of `Shipit.github_teams`, this directly grants the attacker (or any GitHub login they choose) `authorized?` status, i.e., escalation into `Shipit.github_teams` authorization for a stack/team they were never a legitimate member of. This is repeatable per team/organization pair and scales to every team configured across the multi-org deployment, since the same unscoped code path serves all organizations identically.

### Likelihood Explanation
Preconditions: the target team's numeric `github_id` must be known or guessable (team IDs are visible via GitHub's team API/URL to anyone with read access to that org, and are sequential/enumerable in practice), and the attacker must control at least one organization that the operator has configured in `secrets.github` (a realistic scenario in any multi-org Shipit deployment, as referenced by `docs/setup.md`'s `oauth.teams` list spanning multiple orgs). No GitHub App private key, `secret_key_base`, or the target organization's `webhook_secret` are required — only the attacker's own organization's webhook secret, which they control by definition. This is a low-cost, fully repeatable HTTP POST to `/webhooks` with a valid HMAC for the attacker's own org.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation to both `github_id` AND the verified organization, and reject (or explicitly no-op) when an existing `Team` for that `github_id` has an `organization` that does not match `params.organization.login`. Alternatively, pass the verified organization from the controller into the handler and assert equality against `team.organization` before calling `team.add_member`/`team.members.delete`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/membership_handler_test.rb` style, illustrative):
```ruby
test "membership webhook signed by org C cannot mutate team belonging to org X" do
  # Setup: two configured orgs "org-x" and "org-c" in secrets.github, each with distinct webhook_secret.
  team_x = Team.create!(github_id: 555, organization: 'org-x', slug: 'core', name: 'Core')
  Shipit.stubs(:github_teams).returns([team_x])

  payload = {
    'action' => 'added',
    'team' => { 'id' => 555, 'name' => 'Core', 'slug' => 'core', 'url' => 'https://api.github.com/teams/555' },
    'organization' => { 'login' => 'org-c' }, # attacker-controlled org, NOT org-x
    'member' => { 'login' => 'attacker' }
  }
  signature = sign_with_org_c_secret(payload.to_json)

  post '/webhooks', headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => signature }, body: payload.to_json

  team_x.reload
  # BROKEN BINDING: membership written into org-x's team despite verified org == org-c
  assert team_x.members.exists?(login: 'attacker')
  refute_equal 'org-c', team_x.organization
end
```
Both sides of the equality (`verified organization == 'org-c'` vs. `team.organization == 'org-x'`) diverge, and `attacker` is nonetheless added to `team_x`, which is part of `Shipit.github_teams`, granting unauthorized escalation.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
