### Title
Unbounded consolidation loop over attacker-created dust outputs can stall/freeze AA payment responses - (File: `aa_composer.js`)

### Summary
When an Autonomous Agent (AA) needs to send a base-asset (or asset) payment in response to a trigger, `aa_composer.js`'s `sendUnit()` → `completePaymentPayload()` → `iterateUnspentOutputs()` scans **all** of the AA's unspent outputs and greedily accumulates them as inputs until the target amount is reached, with **no upper bound** on the number of inputs it will add. The subsequent validation path explicitly **exempts AA-generated payments from the normal `MAX_INPUTS_PER_PAYMENT_MESSAGE` cap**. This is the same class of bug as the reported Uniswap V3 issue: an attacker can cheaply flood a target with many small "positions" (here: dust-value outputs sent to the AA's address) to force an unbounded, expensive loop in logic every full node must execute deterministically.

### Finding Description
`completePaymentPayload()` queries and iterates unspent outputs belonging to the AA address without any row/iteration limit: [1](#0-0) [2](#0-1) [3](#0-2) 

For a base-asset transfer, every added input increases `target_amount` by `FULL_TRANSFER_INPUT_SIZE` (the incremental unit-size cost of one input) at the same time it increases `total_amount` by `row.amount`: [4](#0-3) 

Because the query that selects candidate outputs deliberately allows outputs whose amount is only `>= FULL_TRANSFER_INPUT_SIZE` (chosen specifically to avoid *negative*-value dust, per the comment about "dust attack"): [5](#0-4) 

an attacker can send many small payments to the AA address with amounts set exactly at (or barely above) `FULL_TRANSFER_INPUT_SIZE`. Each such output, once picked up as an input, contributes almost no net progress toward `target_amount` (input value ≈ input's own size cost), so the loop must iterate through a very large number of these dust outputs before the gap closes — or may never close it, in which case the code falls through to trying to issue new asset coins or ultimately bounces with "not enough funds," having already paid the CPU/DB cost of scanning and looping through every dust row.

Compounding this, the standard `MAX_INPUTS_PER_PAYMENT_MESSAGE` cap that limits the number of payment inputs for ordinary units is explicitly **skipped when the payload was generated by an AA** (`objValidationState.bAA` is true), meaning there is no defensive ceiling analogous to the Uniswap tick-spacing/liquidity minimum the report recommends: [6](#0-5) 

Unlike the oscript formula interpreter — which enforces `MAX_COMPLEXITY`/`MAX_OPS`/statement-count limits via `formula/validation.js` and `formula/evaluation.js` — the native JS input-consolidation logic in `aa_composer.js` is **not** covered by any such complexity accounting, so this loop's cost is effectively uncapped and paid by every full node that executes the AA trigger (execution of AA triggers is deterministic and mandatory for all nodes advancing MC stability), analogous to how the Uniswap swap loop's cost is paid by every miner/validator executing the transaction.

### Impact Explanation
This is not merely a wasted-gas issue as in the original report; in ocore, AA trigger execution is part of consensus (every full node re-executes the trigger deterministically when advancing stability). If an attacker floods an AA address with many small, dust-threshold outputs (via ordinary payment units, cheap relative to draining an AA), then:
- Any subsequent trigger that causes the AA to make a base-asset payment (extremely common — e.g., bounce fees, normal responses) must scan/consolidate through the flood of dust outputs, causing excessive computation/DB load repeated by every node processing that trigger.
- In the worst case (dust sized at exactly the size-cost threshold), the consolidation never gathers enough funds, causing the AA to repeatedly bounce ("not enough funds for X bytes") on legitimate triggers, effectively **freezing the AA's ability to respond/spend its own funds** until the flood of dust outputs is drained (which itself requires the AA to successfully build transactions consuming them — the very thing being blocked).
- Because the normal `MAX_INPUTS_PER_PAYMENT_MESSAGE` safety cap is bypassed for AA-authored payments, there's no hard ceiling forcing the AA to fail fast/gracefully with a bounded-cost error; the loop can process an attacker-controlled, effectively unbounded number of rows.

This matches the "AA fund loss or freezing" and "network unable to process/confirm" impact classes: repeated, unbounded computation in a consensus-mandatory code path, and potential permanent inability of an AA to disburse funds.

### Likelihood Explanation
Likelihood is moderate-to-high difficulty (matching the report's "High" difficulty rating) but concretely reachable by any unprivileged user:
- Creating many small payment outputs to a target AA address only requires ordinary `payment` messages (bounded per unit by `MAX_OUTPUTS_PER_PAYMENT_MESSAGE`, but unbounded across many units over time).
- The attacker must spend real bytes to fund these dust outputs (unlike Ethereum's cheap "1 wei" positions), which raises the cost compared to the original Uniswap scenario, but the amount needed per dust output is deliberately minimized to just above the `FULL_TRANSFER_INPUT_SIZE` floor, making the attack comparatively cheap relative to the disruption caused to the AA (especially high-traffic AAs receiving many small payments from users, e.g., faucets, DEX AAs, oracles that legitimately receive many small payments).
- No special privileges (miner/hub/light-node capability) are required — a single ordinary poster of payment units can carry this out.

### Recommendation
- Bound the number of inputs an AA-generated payment message may include, even when `objValidationState.bAA` is true (e.g., still enforce `MAX_INPUTS_PER_PAYMENT_MESSAGE`, or a comparable AA-specific ceiling), so the validation step cannot be used to "launder" an oversized/expensive consolidation.
- In `iterateUnspentOutputs()`/`completePaymentPayload()`, cap the number of rows/iterations considered per invocation (e.g., stop after N inputs and either fail deterministically with a bounded-cost error or fall back to issuing new fund/consolidation in smaller batches over multiple triggers).
- Raise the dust filtering threshold so that an output's value must exceed its input's incremental size cost by a meaningful margin (not just `>= FULL_TRANSFER_INPUT_SIZE`), ensuring each consolidated input makes real progress toward `target_amount` and the loop provably terminates in O(target_amount / margin) iterations rather than being driven purely by attacker-chosen dust counts.
- Document and enforce these bounds explicitly (as recommended in the original report) so AA developers and node operators can reason about worst-case trigger-execution cost.

### Proof of Concept
1. Attacker identifies a target AA address `A` that is known to make base-asset payments in response to triggers (e.g., a bounce-fee refund AA, or any AA that pays out on success).
2. Attacker repeatedly posts ordinary `payment` units, each containing up to `MAX_OUTPUTS_PER_PAYMENT_MESSAGE` outputs to `A`, each output amount set to exactly `FULL_TRANSFER_INPUT_SIZE` bytes (the minimum value accepted by the dust filter in `readStableOutputs`/`readUnstableOutputsSentByAAs`).
3. Repeat over many units/time until thousands of such dust outputs accumulate as unspent outputs owned by `A`.
4. Any user now triggers `A` in a way that requires `A` to send a base-asset payment (a normal interaction).
5. `sendUnit()` → `completePaymentPayload()` → `iterateUnspentOutputs()` fetches and loops over all of `A`'s unspent outputs (line 1102-1137, 1140-1173 in `aa_composer.js`); because each dust input contributes essentially net-zero progress toward `target_amount`, the loop consumes many iterations without productively closing the funding gap, and the validation step does not cap the resulting number of inputs (`validation.js` lines 2137-2138 skip the cap for `bAA`), so the AA either produces an oversized/expensive response or bounces with "not enough funds," repeatable on every subsequent trigger until the dust is manually cleared — which itself faces the same bottleneck.
