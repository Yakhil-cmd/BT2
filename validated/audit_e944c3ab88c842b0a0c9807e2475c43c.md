### Title
Head-truncation in `cap_diff_for_prompt` lets attacker-padded diffs push dangerous changes past the review window - ([File: plugins/security-guidance/hooks/review_api.py])

### Summary
`cap_diff_for_prompt` truncates each file's diff to the first `DIFF_PER_FILE_BYTES` bytes and drops/omits any file content beyond `DIFF_TOTAL_BYTES` total, using pure byte-offset slicing with no awareness of which `+`/`-` hunks contain the actual dangerous change. Since the diff content it operates on is derived from real file diffs that Claude writes during a session (potentially steered by prompt-injected instructions in repository content), an attacker who can influence what gets written into a session's diff can pad benign content ahead of a dangerous edit (within one file, or via earlier files in the batch) so the dangerous hunk is silently truncated or omitted from what the review LLM ever sees.

### Finding Description
`cap_diff_for_prompt` [1](#0-0)  is invoked by `build_investigate_prompt` [2](#0-1)  to assemble the diff text that is sent to the agentic security-review model, and an equivalent copy (`_cap_files_for_prompt`) is used for the single-shot Stop-hook review [3](#0-2) .

The capping logic slices content from the **front**: `content[:DIFF_PER_FILE_BYTES]` for the per-file cap, and `content[:room]` for the running total-byte cap, with the tail dropped and replaced by a truncation marker string. `DIFF_PER_FILE_BYTES` defaults to 80,000 bytes and `DIFF_TOTAL_BYTES` to 400,000 bytes [4](#0-3) . Once the per-file budget is exhausted, remaining files in the batch are appended as `"[omitted by security-guidance: total diff byte cap reached]"` with zero content sent to the model [5](#0-4) .

Because the function has no notion of hunk boundaries, diff-hunk relevance, or "is this hunk security-sensitive," an attacker who can influence the content that ends up in the reviewed diff (e.g., via prompt-injected instructions embedded in repo files, issues, or other content that Claude reads and then acts on, causing it to emit a large amount of benign/verbose changes before or alongside a small dangerous edit) can arrange for the dangerous `+` lines to land past the 80 KB per-file boundary, or arrange for the malicious file to be ordered/sized such that the 400 KB total-diff budget is exhausted by other files first. In either case, the review model at `build_investigate_prompt`/Stop-hook path never receives the dangerous hunk's bytes at all — the model is asked to review the diff and returns `findings: []` for content it never saw, which then lets `analyze_code_security`/`agentic_review` proceed as if no vulnerability exists [6](#0-5) .

The truncation marker text (`"...[truncated by security-guidance: ...]"`) is written into the content so the model is nominally told something was cut, but nothing in the pipeline forces the reviewer to treat truncation itself as suspicious, nor is there any mechanism to prioritize hunks by risk before slicing — capping happens purely on raw byte offsets of already-selected diff text. The Stop-hook code comments even acknowledge diff-file-count prioritization exists but explicitly defer byte-level truncation to this function ("`_cap_files_for_prompt` already bounds bytes downstream") [7](#0-6) , with no equivalent hunk-level prioritization inside a single file's diff.

### Impact Explanation
This breaks the stated invariant that "prompt assembly must not let untrusted repo content suppress review of dangerous changes." By controlling diff size/ordering, dangerous changes can be pushed out of the reviewer's context window entirely, causing the security-review hook (Stop hook and/or agentic commit review) to silently pass a dangerous change as clean. This is a logic-level bypass of a required security guard (the LLM diff reviewer), matching "Logic-level service disruption caused by bypassing a required guard."

### Likelihood Explanation
Exploitability depends on an attacker being able to influence what content Claude writes into the diff during a session (e.g., via prompt injection from repository content that Claude reads and acts on, or via a large pre-existing file that a legitimate edit touches). The 80 KB per-file / 400 KB total thresholds are not small, so triggering this requires deliberately engineered padding, but this is straightforward to construct (e.g., a large generated-looking blob, verbose comments, or noise appended ahead of the malicious diff hunk). This is a plausible, reproducible condition rather than requiring privileged access — no admin/maintainer rights are needed, only the ability to get attacker-controlled content into a session's diff.

### Recommendation
Make truncation hunk-aware and risk-aware rather than pure byte-offset slicing: parse the diff into hunks before capping, prioritize/keep hunks matching high-risk sink patterns (exec/eval/shell/SQL/deserialization/network calls, permission/allowlist edits, etc.) regardless of position, and only truncate the lowest-risk hunks first. Alternatively/additionally, when any file is truncated or omitted, fail closed (block the Stop/commit action) rather than silently returning `findings: []` from a partial review, and surface truncation events as a hard warning that requires human/user acknowledgement rather than allowing the flow to proceed silently.

### Proof of Concept
Unit test plan for `cap_diff_for_prompt` in `plugins/security-guidance/hooks/review_api.py`:
1. Construct a single-file diff where the first ~85,000 bytes are benign padding (`+    # padding line\n` repeated) followed by a dangerous line, e.g. `+os.system(user_input)`.
2. Call `cap_diff_for_prompt([("app.py", crafted_diff)])` with default `DIFF_PER_FILE_BYTES=80000`.
3. Assert that `"os.system(user_input)"` is **not** present in the returned capped content — demonstrating the dangerous line is silently dropped rather than flagged/prioritized.
4. Repeat with two files: file A padded to ~410,000 bytes of benign diff, file B containing a small dangerous diff (`+eval(request.args['x'])`). Assert file B's content in the output is `"[omitted by security-guidance: total diff byte cap reached]"` and the dangerous string is absent from the assembled prompt text used by `build_investigate_prompt`.
5. Expected (failing) assertion for the fix: after remediation, the dangerous line/hunk should remain present (or the pipeline should fail closed) even when preceded by large amounts of benign padding.

def cap_diff_for_prompt(
    files: list[tuple[str, str]],
) -> tuple[list[tuple[str, str]], int]:
    """Cap per-file and total diff bytes; return (capped_files, bytes_dropped).

    Truncation markers are written inside the content so the reviewer
    knows the file is incomplete.
    """
    out: list[tuple[str, str]] = []
    dropped = 0
    total = 0
    for fp, content in files:
        if len(content) > DIFF_PER_FILE_BYTES:
            dropped += len(content) - DIFF_PER_FILE_BYTES
            content = (
                content[:DIFF_PER_FILE_BYTES]
                + "\n... [truncated by security-guidance: file exceeds per-file byte cap]"
            )
        room = DIFF_TOTAL_BYTES - total
        if room <= 0:
            dropped += len(content)
            out.append(
                (fp, "[omitted by security-guidance: total diff byte cap reached]")
            )
            continue
        if len(content) > room:
            dropped += len(content) - room
            content = (
                content[:room]
                + "\n... [truncated by security-guidance: total diff byte cap reached]"
            )
        total += len(content)
        out.append((fp, content))
    return out, dropped
```

def build_investigate_prompt(
    touched_paths: list[str],
    diff_files: list[tuple[str, str]],
    *,
    context_note: str = "",
) -> str:
    capped, _ = cap_diff_for_prompt(diff_files)
    diff_text = "\n\n".join(
        f"=== DIFF: {fp} ===\n{content}" for fp, content in capped
    )
    return (
        "Review this change for security vulnerabilities.\n\n"
        "Changed files (you may Read these and any other file in the repo):\n"
        + "\n".join(f"  - {p}" for p in touched_paths[:50])
        + context_note
        + "\n\nUnified diff (only + lines are new):\n\n"
        + diff_text
        + extensibility.guidance_block()
        + "\n\nInvestigate per the method in your instructions, then return "
        "the findings list."
    )
```
