## StatusHandler cross-repository status write via organization/repository binding mismatch — (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The webhooks signature check authenticates the *organization* named in the payload's `repository.owner.login` field, but the code that mutates state (`StatusHandler`, `PushHandler`, etc.) resolves the target repository from the independent `repository.full_name` field. These two fields are never cross-validated, so an attacker who legitimately controls (or has installed the Shipit GitHub App for) one organization/repository can forge a webhook whose signature is valid for their own organization's secret, while pointing `repository.full_name` at a completely different, victim repository/stack hosted on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization solely from the payload, not from any property tied to the actual data being mutated: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp`/webhook-secret configuration keyed by `repository.owner.login`, and `verify_webhook_signature` only proves that the HMAC over the *entire raw body* matches that organization's secret — i.e., it proves "this org signed this payload," nothing about which repo the payload claims to target.

Once verification passes, `create` dispatches to handlers, which resolve the affected `Stack`/`Repository` using a *different* field, `repository.full_name`: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository.owner.login` (used for authentication) and `repository.full_name` (used for the write) are independent JSON strings inside the same attacker-controlled request body — nothing in the code enforces that `full_name` starts with `owner.login`. An attacker who owns/administers *any* organization `attacker-org` that has installed the Shipit GitHub App (and therefore knows/controls that org's webhook secret in this multi-tenant Shipit instance) can:

1. Sign a `push`/`status`/`check_suite` payload with `repository.owner.login = "attacker-org"` (passes `verify_signature` using attacker-org's own secret).
2. Set `repository.full_name = "victim-org/victim-repo"` in the same payload.
3. `StatusHandler#process` will then look up `Commit.where(sha: params.sha)` across `victim-org/victim-repo`'s stacks and call `commit.create_status_from_github!(params)` — writing an arbitrary CI status (`state`, `description`, `target_url`, `context`) onto a commit belonging to a repository the attacker has no authorization over. [4](#0-3) 

Equally, `PushHandler` will invoke `stack.sync_github(expected_head_sha: params.after)` against the victim's stacks for the branch named in the forged payload: [5](#0-4) 

This is the direct structural analog of the `Trading._checkOwner` bug: the check (`_checkOwner`/`verify_signature`) validates one identity (`token owner`/`repository.owner.login`), while the actual operation is performed on behalf of a different, unverified identity (`operator`/`repository.full_name`). Just as Tigris's `_checkOwner` never confirms the caller is *authorized for the position being acted on*, Shipit's `verify_signature` never confirms the authenticated organization is *authorized for the repository being written to*.

### Impact Explanation
This is a cross-repository write: an entity authenticated only for organization A can forge commit statuses and trigger sync jobs against organization B's repositories/stacks on the same Shipit instance, without ever holding B's webhook secret, an `ApiClient` token, or a Shipit session. Forged commit statuses can influence CI-gated deploy eligibility (`required_statuses`/`blocking_statuses` checks elsewhere in the deploy pipeline), and forged pushes can force out-of-band `sync_github` calls against a victim's stack. This matches the "Critical: cross-repository writes / unauthorized deploy" impact bucket, since it lets one tenant tamper with another tenant's deployable state.

### Likelihood Explanation
Requires the attacker to control at least one organization/repository whose GitHub App webhook is configured on the same shared Shipit instance (i.e., be a legitimate, unprivileged tenant of a multi-tenant Shipit deployment) — no privileged Shipit account, `ApiClient` token, or session is needed. This is a realistic configuration for any Shipit instance serving more than one GitHub organization, which the engine explicitly supports via `Shipit.github(organization:)`.

### Recommendation
After signature verification, validate that `repository.owner.login` (or `organization.login`) matches the owner component parsed from `repository.full_name` before dispatching to any handler; reject the webhook (422) if they diverge. Alternatively, resolve the target `Repository`/`Stack` using the authenticated organization rather than the independent `full_name` field.

### Proof of Concept
1. Shipit instance configured with two tenants: `attacker-org` (webhook secret known to attacker, e.g. because attacker administers that GitHub org and installed the App themselves) and `victim-org/victim-repo` (an unrelated stack on the same instance).
2. Attacker crafts a `status` event payload:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/tests",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s webhook secret over the raw body.
4. `POST /webhooks` with header `X-Github-Event: status`. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature.
5. `StatusHandler#process` executes `Repository.from_github_repo_name("victim-org/victim-repo")`, finds the victim's commit by `sha`, and calls `commit.create_status_from_github!(params)`, writing a forged `success` status onto the victim repository's commit — despite the request only ever being authenticated for `attacker-org`.

      github_app = Shipit.github(organization: repository_owner)

      )

      ].join(' '))
    end
