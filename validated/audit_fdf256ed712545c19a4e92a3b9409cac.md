### Title
Unauthorized read of foreign stack build status via `Shipit::Api::CCMenuController#show`'s `NoDeploy` fallback bypassing token stack scoping - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to resolve `params[:stack_id]` against the unscoped `Stack` model instead of the `stacks` scope used by `Shipit::Api::BaseController`, which restricts lookups to `current_api_client.stack_id` when the token is stack-scoped. This lets any holder of a `read:stack` token query the CCMenu status (`show`) of any stack in the installation, including its name and `lastBuildLabel`/activity via the `NoDeploy` fallback when the target stack has no deploys.

### Finding Description
The broken binding: for a stack-scoped token, it must hold that `stack.id == current_api_client.stack_id`. `Shipit::Api::BaseController#stacks` enforces this: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `Shipit::Api::BaseController#stack` resolves via that scoped relation (`stacks.from_param!(params[:stack_id])`). [1](#0-0) 

`Shipit::Api::CCMenuController` overrides this accessor to bypass the scope entirely, resolving the stack from the unscoped `Stack` model: [2](#0-1) 

`show` then does `latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new` and renders the CCMenu XML with `stack` (an arbitrary, unauthorised stack) and `latest_deploy` (real deploy or the synthetic `NoDeploy`): [3](#0-2) 

The rendered view exposes `stack.to_param` (name), `stack.merge_status`, `deploy.running?` (activity), and `deploy.id` (`lastBuildLabel`, which is `0` for the `NoDeploy` sentinel): [4](#0-3) 

Attacker request: an attacker holding any valid `read:stack` API token (their own, scoped to their own stack via `ApiClient#stack_id`) sends `GET /api/stacks/:stack_id/cc_menu.xml?token=<their_token>` where `:stack_id` names a foreign stack. `require_permission :read, :stack` only checks `current_api_client.check_permissions!(:read, :stack)` — it checks the permission list, not stack ownership: [5](#0-4) 
Since `stack` in this controller is resolved without the `stacks` scope, the check never compares the resolved stack against `current_api_client.stack_id`, so the request succeeds against any existing stack, deployed or not.

### Impact Explanation
The endpoint discloses, for any stack in the Shipit installation: whether it exists, its `to_param` name, its `merge_status`, whether a deploy/rollback is currently running, and either the ID of its latest deploy/rollback or the sentinel "Sleeping"/`lastBuildLabel: 0` state when no deploy exists. This is an unauthenticated-with-respect-to-scope read of stack state across tenants (any repository/stack in the install), matching the High-severity category "unauthenticated read of stack state." It is fully repeatable against arbitrary stack IDs by any attacker possessing a stack-scoped `read:stack` token for a stack they control.

### Likelihood Explanation
Preconditions are low-cost: the attacker only needs a valid, legitimately-issued `read:stack` API token scoped to their own stack (a standard, low-privilege credential), and knowledge or guessability of a target stack's `id`/param. No GitHub secrets, session, or elevated role is required. The request is a single unauthenticated-scope GET; it can be repeated against every stack ID to enumerate the whole fleet.

### Recommendation
Remove the private `stack` override in `Shipit::Api::CCMenuController` (and the redundant `authenticate_api_client` override) so it inherits `Shipit::Api::BaseController#stack`, which resolves via the scoped `stacks` relation and thus raises/404s when `current_api_client.stack_id` doesn't match the requested stack.

### Proof of Concept
Minitest plan (`test/controllers/api/ccmenu_controller_test.rb` — out of scope to write, described for the fix verification):
1. Create `stack_a` (owned/authorized) and `stack_b` (foreign, zero `Deploy`/`Rollback` rows).
2. Create an `ApiClient` with `permissions: ['read:stack']` and `stack_id: stack_a.id`.
3. Assert binding before fix: `client.stack_id == stack_a.id` but request `GET api_stack_cc_menu_url(stack_b, token: client.authentication_token)` returns `200` and body contains `name="#{stack_b.to_param}"` and `lastBuildLabel="0"` — i.e., `stack_b.id != client.stack_id` yet access succeeds, proving the scope binding is violated.
4. After applying the recommended fix, assert the same request returns `404` (via `Stack.from_param!`/`RecordNotFound` on the scoped `stacks` relation), restoring `stack.id == current_api_client.stack_id` (or `Stack.all` when unscoped) as required.
