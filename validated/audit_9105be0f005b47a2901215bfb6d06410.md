## Title
Asset definer can front-run pending `spender_attested` asset transfers by updating the attestor list, freezing user payments - ([File: validation.js])

### Summary
Assets with `spender_attested=true` restrict who may hold/receive the asset to addresses attested by a definer-controlled attestor list. The definer can update this list at any time via a single, unprivileged `asset_attestors` message, and the list actually applied to a payment is resolved dynamically at validation time (the "latest" stable list as of the payment's `last_ball_mci`). This lets a malicious/opportunistic definer watch the unstable DAG for a pending transfer to a specific recipient and race to publish an `asset_attestors` update removing that recipient's attestor before the victim's payment stabilizes, causing the already-broadcast, fully-signed payment to fail validation and become permanently invalid/nonserial — the exact "owner front-runs a pending user operation by changing a privileged parameter" pattern described in the reference report, adapted to ocore's asset/attestor mechanism.

### Finding Description
An asset can require `spender_attested=true`, meaning every input/output address participating in a transfer must be attested by one of the addresses in `objAsset.arrAttestorAddresses`. This attestor list is *not* fixed at asset-creation time; it can be freely replaced by the definer at any later point via an `asset_attestors` message, gated only by an ownership check with no timelock or cooldown: [1](#0-0) 

When a payment for such an asset is validated, `storage.readAsset` resolves `arrAttestorAddresses` to whichever attestor-list unit is most recent and stable as of the payment's own `last_ball_mci`: [2](#0-1) 

The payment's output addresses are then checked against this dynamically-fetched list: [3](#0-2) 

and, for issuance, the issuer address is checked the same way: [4](#0-3) 

Because the list used for validation is whatever is latest and stable *at the time the unit's `last_ball` advances* — not the list that existed when the victim composed/broadcast the transfer — a definer who observes an unstable, pending transfer to a particular recipient can race to publish a new `asset_attestors` unit removing that recipient (or the issuer) from the attestor list before the victim's unit stabilizes. This mirrors the reported vulnerability class exactly: a privileged party (`owner`/definer) can unilaterally and instantly change a condition that a counterparty's already-submitted transaction depends on, with no timelock protecting against front-running.

### Impact Explanation
A successful race causes the victim's already-signed and broadcast payment unit to fail validation once it would otherwise stabilize ("some output addresses are not attested" / "issuer is not attested"), rendering that unit invalid. Because inputs referenced by an invalidated unit cannot be immediately reused without composing a fresh unit (and any downstream units built on it are likewise voided), this is a concrete freezing/denial-of-funds-availability attack against victims transacting in a `spender_attested` asset, entirely at the discretion of the asset definer, without any of the counterparties' consent or a required delay. This matches the "AA fund loss or freezing" acceptance criterion, since AA-issued or AA-consumed `spender_attested` assets are equally affected — an AA sending/receiving such an asset can have its trigger-driven payment logic silently invalidated by a definer's last-moment attestor-list change, causing bounces or stuck responses.

### Likelihood Explanation
Likelihood is moderate-to-high for anyone who issues or interacts with a `spender_attested` asset controlled by an adversarial or compromised definer: publishing `asset_attestors` is a single self-authored, inline message with no fees or delay beyond normal unit propagation (`composeAssetAttestorsJoint` in `composer.js:123-125`), so a definer merely needs to monitor the network for pending transfers of their asset and race to include a conflicting attestor update before the victim's unit's last ball advances — well within ocore's normal DAG-stabilization timing window.

### Recommendation
Bind the attestor list used for validating a specific payment to a snapshot taken no later than the point the payment message references (e.g., require the attestor-list unit referenced/available strictly before the paying unit was composed, or require attestor-list changes to only take effect after a mandatory minimum number of MC indices/timelock), so a definer cannot retroactively invalidate transfers that were valid under the attestor list known to the sender at composition time.

### Proof of Concept
1. Definer D issues asset A with `spender_attested=true`, `attestors=[X]`.
2. User attested by X composes and broadcasts a valid payment of asset A to recipient R (also attested by X), per `validatePaymentInputsAndOutputs` (`validation.js:2630-2641`).
3. D observes the unstable unit in the DAG and immediately posts an `asset_attestors` message replacing the attestor list with `[Y]` (excluding X) via `validateAttestorListUpdate` (`validation.js:2829-2848`), timed so it stabilizes before the victim's unit's `last_ball_mci`.
4. When the victim's unit is finally checked against the new stable state, `storage.readAsset`/`filterAttestedAddresses` (`storage.js:1917-1974`) now resolve `arrAttestorAddresses=[Y]`, R is no longer attested, and the payment fails with "some output addresses are not attested," permanently invalidating the victim's transfer.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
