## Analog Found: Missing self-reporting restriction in `pallet-nomination-pools::apply_slash` / `pallet-delegated-staking::do_slash`

### Title
Pool member can self-report their own pending slash via `apply_slash` and capture the `SlashRewardFraction` reporter reward that is meant for third-party callers - ([File: substrate/frame/nomination-pools/src/lib.rs])

### Summary
The Sherlock report describes a perpetual-exchange bug where a trader can call `liquidate()` on themselves and, because the liquidator and liquidated-trader roles are not required to be distinct, siphon back funds/incentives meant for a genuine third-party liquidator. The closest demonstrable analog in this Polkadot SDK snapshot is `pallet_nomination_pools::Pallet::apply_slash`, which is a permissionless extrinsic whose caller ("reporter") is never checked against the `member_account` being slashed.

### Finding Description
`apply_slash` is documented as "This call can be dispatched permissionlessly (i.e. by any account). If the execution is successful, ... caller may be rewarded with a part of the slash": [1](#0-0) 

The extrinsic takes the signed caller as `who` and an independently looked-up `member_account`, with no `ensure!(who != member_account, ...)` check, before calling `do_apply_slash(&member_account, Some(who), true)`: [2](#0-1) 

`do_apply_slash` forwards the caller as `reporter` straight through to `T::StakeAdapter::member_slash`: [3](#0-2) 

For the `DelegateStake` adapter, `member_slash` calls `Delegation::delegator_slash(pool_account, who, amount, maybe_reporter)`, which resolves to `pallet_delegated_staking::Pallet::do_slash`: [4](#0-3) 

Inside `do_slash`, the account being slashed (`delegator`) has `amount` removed from held balance, but if a `reporter` is supplied, `SlashRewardFraction * actual_slash` is carved out of the slashed credit and paid directly to that `reporter` via `T::Currency::resolve`, with only the remainder going to `T::OnSlash` (the protocol's slash sink, e.g. Treasury/burn): [5](#0-4) 

Because `apply_slash` never enforces `who != member_account`, a pool member with a pending slash can call `Pools::apply_slash(RuntimeOrigin::signed(self), self)`. In that call, they are simultaneously the offender being slashed and the "reporter" being rewarded, so `SlashRewardFraction` of their own slash amount — funds that the protocol's `T::OnSlash` handler (Treasury in production configs, e.g. `type OnSlash = Dap` on Asset Hub Westend) is designed to receive — is instead redirected back to the offender. [6](#0-5) 

This mirrors the reported bug class: the entity that should be penalized ("liquidated"/slashed) is not prevented from also acting as the incentivized party who triggers/finalizes that penalty ("liquidator"/reporter), letting them partially recapture funds that the protocol design intends to route elsewhere.

### Impact Explanation
The magnitude is bounded by `SlashRewardFraction`, which in the inspected runtime configs is 1%-10% of the slashed amount (`Perbill::from_percent(1)` on Asset Hub Westend/parachain staking runtime, `Perbill::from_percent(10)` in delegated-staking mocks): [7](#0-6) [8](#0-7) 

Unlike the original report's scenario (where self-liquidation let the attacker fully avoid loss and repeatedly extract value), here the offender still loses the bulk (90-99%) of their slash to their own balance being reduced — they cannot avoid the underlying penalty, only recapture a small percentage that the protocol intended to route to the `OnSlash` sink (e.g. Treasury) or to an honest third-party reporter. This is fund misdirection/diversion of protocol revenue, not unbounded theft or insolvency.

### Likelihood Explanation
High likelihood of triggerability: the caller only needs a pending slash on their own pool membership (a routine outcome of nominated-validator slashing) and a normal signed extrinsic call with `member_account` set to themselves. No privileged role, governance, or race condition is required. There is no code path that special-cases or rejects `who == member_account`.

### Recommendation
Add an explicit check in `apply_slash` (or in `do_apply_slash`/`do_slash`) that the reporter reward is only paid out when `who != member_account` (i.e., disallow self-reporting from receiving `SlashRewardFraction`), analogous to how lending/liquidation protocols require the liquidator to differ from the liquidated party. If self-application should remain permitted (to allow members to unblock their own withdrawal), the reward payout branch specifically should be skipped when caller and target coincide, sending the full slashed amount to `T::OnSlash`.

### Proof of Concept
Not executed against a live chain. Based on static analysis of the guarded code paths:
- `apply_slash` extrinsic: no `who != member_account` guard [2](#0-1) .
- `do_apply_slash`: forwards caller as reporter unconditionally [3](#0-2) .
- `do_slash` reporter-reward branch: pays `SlashRewardFraction * actual_slash` to `reporter` regardless of identity with `delegator` [9](#0-8) .
- Existing unit test `apply_pending_slash` demonstrates the reward mechanic with a distinct reporter account (400) different from the slashed delegators, confirming the reward-payment code path is live and testable, but no test exercises/blocks the `reporter == delegator` case: [10](#0-9) 

A minimal FRAME integration reproduction (not run here) would: set up a delegate-stake pool member with a pending slash, then call `Pools::apply_slash(RuntimeOrigin::signed(member), member_lookup)` and assert `Balances::free_balance(member)` increases by `SlashRewardFraction * actual_slash` relative to a control run where a distinct third-party account performs the same call — this is a straightforward mock-runtime test extension of the existing `apply_pending_slash`/pool `test-delegate-stake` test suites already present in the repo, but I did not execute it; confirming the exact numeric outcome and whether any higher-level filter (`T::Filter` in `pallet_nomination_pools::Config`) blocks this path would require running that test.

		pub fn apply_slash(
			origin: OriginFor<T>,
			member_account: AccountIdLookupOf<T>,
		) -> DispatchResultWithPostInfo {

				T::StakeAdapter::strategy_type() == adapter::StakeStrategyType::Delegate,

			let who = ensure_signed(origin)?;
			let member_account = T::Lookup::lookup(member_account)?;

			// If successful, refund the fees.
			Ok(Pays::No.into())
		}

	/// Slash member against the pending slash for the pool.
	fn do_apply_slash(
		member_account: &T::AccountId,
		reporter: Option<T::AccountId>,
		enforce_min_slash: bool,
	) -> DispatchResult {
		let member = PoolMembers::<T>::get(member_account).ok_or(Error::<T>::PoolMemberNotFound)?;

		let pending_slash =
			Self::member_pending_slash(Member::from(member_account.clone()), member.clone())?;

		// ensure there is something to slash.
		ensure!(!pending_slash.is_zero(), Error::<T>::NothingToSlash);

		if enforce_min_slash {
			// ensure slashed amount is at least the minimum balance.
			ensure!(pending_slash >= T::Currency::minimum_balance(), Error::<T>::SlashTooLow);
		}

		T::StakeAdapter::member_slash(
			Member::from(member_account.clone()),
			Pool::from(Pallet::<T>::generate_bonded_account(member.pool_id)),
			pending_slash,
			reporter,
		)
	}
