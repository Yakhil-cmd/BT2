### Title
Webhook Organization/Repository Binding Mismatch Allows Cross-Repository Forged Events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the incoming HMAC signature against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) straight from the attacker-controlled JSON body. [1](#0-0) [2](#0-1)  However, the event handlers that actually locate and mutate the target `Stack`/`Repository` use a *different* field from the same payload, `payload.dig('repository', 'full_name')`. [3](#0-2)  This creates a mismatch: the organization whose credential authenticates the request is not necessarily bound to the repository the handlers write to.

### Finding Description
In a multi-organization Shipit deployment (`config/secrets.yml` with the `github: { OrgOne: {...}, OrgTwo: {...} }` schema shown in `docs/setup.md` / `test/dummy/config/secrets_double_github_app.yml`), each organization has its own independent `webhook_secret`. [4](#0-3)  `Shipit.github(organization: repository_owner)` looks up the `GitHubApp` config purely by the org name string taken from the JSON body being verified, before that body's authenticity has been established. [5](#0-4) 

An attacker who legitimately administers a GitHub App installation for `OrgA` (one of the orgs configured in this Shipit instance) knows `OrgA`'s `webhook_secret` (e.g. because they installed and configured the GitHub App on their own organization/repository, which is an unprivileged, self-service action requiring no Shipit session, `ApiClient` token, or GitHub org-owner access to any *other* org). They can then construct an arbitrary webhook body where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` picks `OrgA`'s app/secret and the HMAC computed with the known `OrgA` secret validates), and
- `repository.full_name` = `"OrgB/victim-repo"` (a completely different org/repo that has a Stack configured in this same Shipit instance).

Since `verify_signature` only checks that *some* valid signature exists for the org named in the payload, and the handlers (`PushHandler`, `StatusHandler` via `Handler#stacks`/`#repository_name`, pull-request handlers, etc.) resolve the target purely via `repository.full_name`, the forged event is accepted and processed against `OrgB/victim-repo`'s stack — e.g. triggering `GithubSyncJob` for a push event, creating commit `Status` records, or manipulating a review stack's PR/label state — even though the authenticating organization (`OrgA`) has no relationship to `OrgB`'s repository. [6](#0-5) [7](#0-6) 

This is the equality that should hold but doesn't: `organization authenticating the webhook == organization owning the repository the handlers act on`. The engine currently binds the signature check to `repository.owner.login`/`organization.login`, while the write-path binds to `repository.full_name`, an independent, unauthenticated field in the same attacker-supplied JSON.

### Impact Explanation
This allows cross-repository writes without possessing the target repository's own webhook secret — matching the Critical-tier "cross-repository writes" impact class. An attacker controlling one tenant org in a multi-org Shipit deployment can spoof push/status/pull_request events for any other tenant's stack, forcing syncs, injecting fake commit statuses (which can gate/allow deploys depending on `shipit.yml` required statuses), or manipulating review-stack lifecycle (archiving/unarchiving) for repositories they do not own.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured for multiple GitHub organizations (the documented multi-tenant `github:` config schema), and (2) the attacker to control/administer at least one of the configured organizations' GitHub App installations (an unprivileged, ordinary action — installing a GitHub App on one's own org is self-service and requires no access to Shipit itself). Given those preconditions, exploitation only requires crafting and POSTing a JSON body with a valid HMAC for the attacker's own org — no Shipit session, `ApiClient` token, or knowledge of the victim org's secret is needed.

### Recommendation
Bind signature verification to the same field the handlers use to select the target repository. Concretely, derive the GitHub App/organization used for `verify_webhook_signature` from `repository.full_name`'s owner segment (or otherwise cross-check that `repository.owner.login` matches the owner segment of `repository.full_name` before verifying), and reject the request if the two disagree, rather than trusting `repository.owner.login`/`organization.login` independently of `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret`, per the multi-org schema.
2. Attacker installs/configures a GitHub App for `OrgA` (self-service) and thus knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
4. Attacker computes `X-Hub-Signature` using `OrgA`'s known `webhook_secret` over the exact raw body (`Hook::DeliverySigner`/`verify_webhook_signature` use `OpenSSL::HMAC.hexdigest('sha1', secret, message)`), and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and successfully verifies the signature using `OrgA`'s secret. [1](#0-0) 
6. `create` dispatches to `PushHandler`, whose `stacks` helper resolves `Repository.from_github_repo_name("OrgB/victim-repo")` from `repository.full_name`, and syncs/enqueues `GithubSyncJob` for `OrgB`'s stack, despite the request only being authenticated for `OrgA`. [3](#0-2) [6](#0-5)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
