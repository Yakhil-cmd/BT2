### Title
CCMenu API endpoint bypasses ApiClient stack scoping, letting a stack-scoped token read any stack's status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` restricts an `ApiClient` token that is bound to a single stack (`ApiClient#stack_id`) so it can only resolve stacks from `stacks.from_param!`, a scope limited to `Stack.where(id: current_api_client.stack_id)` [1](#0-0)  . `Shipit::Api::CCMenuController`, however, overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, completely bypassing that scoping [2](#0-1)  . The `require_permission :read, :stack` check only verifies the token's permission list contains `read:stack`, not that the target stack matches the token's `stack_id` [3](#0-2) [4](#0-3)  .

### Finding Description
The intended trust binding is: `token.stack_id == stack_being_touched` whenever an `ApiClient` is created with a `stack` association (a common configuration, as shown by the `here_come_the_walrus` fixture that has `stack: shipit` and only `read:stack` permission) [5](#0-4)  . This scoping is enforced correctly for the generic API controllers via `BaseController#stacks`/`#stack` [1](#0-0) , and is exercised in tests confirming "an api client scoped to a stack will only see that one stack" [6](#0-5) .

`CCMenuController` is reachable with the same bearer-style token (passed as a query-string `token` param, designed for unauthenticated CI dashboard consumption) [7](#0-6) . Instead of inheriting the scoped `stack` helper, it redefines `stack` to look up `Stack.from_param!(params[:stack_id])`, which resolves **any** stack in the system, not just the one the token is authorized for [8](#0-7) [9](#0-8) . Because `require_permission!` only checks `permissions.include?("read:stack")` and never compares `stack_id` to the resolved stack [4](#0-3) , any holder of a stack-scoped `read:stack` token can substitute an arbitrary `stack_id` in the URL and retrieve that other stack's CI/deploy status.

This is the same class of bug as the external report: a binding the system claims to enforce (the token → stack authorization) is checked in one code path (`BaseController#stack`) but silently dropped in a sibling code path (`CCMenuController#stack`) that handles the same authenticated request type.

### Impact Explanation
This is a High-severity escalation: it grants an unauthenticated-read-token holder (only scoped to their own stack) unauthorized read access to another stack's state — `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` [10](#0-9) . This matches the in-scope impact category "unauthenticated read of stack state, task streams or deploy output" since the CCMenu token is explicitly meant to be embeddable/URL-based (near-unauthenticated) and is designed for use outside the normal API authorization flow, yet it escapes its intended single-stack scope.

### Likelihood Explanation
High likelihood: any legitimately-issued stack-scoped CCMenu/API token (an intentional, low-privilege token type meant only to expose one stack's CI badge) can be replayed against `/stacks/<other_stack_id>/ccmenu.xml?token=<token>` with zero additional privileges, no organization membership, and no write access required.

### Recommendation
Have `CCMenuController#stack` reuse the scoped lookup from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so a stack-scoped `ApiClient` can never resolve a stack outside its authorized `stack_id`.

### Proof of Concept
1. An administrator creates (or the `CCMenuUrlController#fetch` flow creates) an `ApiClient` scoped to Stack A with only `permissions: ['read:stack']` and `stack_id: A`.
2. Using that token, issue: `GET /stacks/<STACK_B_ID>/ccmenu.xml?token=<TOKEN_A>` where Stack B is a stack the token was never associated with.
3. `CCMenuController#authenticate_api_client` accepts the token (valid signature) [7](#0-6) ; `require_permission :read, :stack` passes because the token has `read:stack` regardless of which stack [4](#0-3) ; `stack` resolves Stack B directly via `Stack.from_param!` [11](#0-10) , returning Stack B's build/deploy status XML — data the token was never authorized to read.
