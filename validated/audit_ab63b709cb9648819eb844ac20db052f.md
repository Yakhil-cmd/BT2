### Title
Membership webhook `removed` handler trusts `organization.login` for signature verification but resolves the `Team` by `github_id` alone, letting an unsigned webhook from any blank-secret org revoke membership in a privileged team owned by a different org - (File: app/models/shipit/webhooks/handlers/membership_handler.rb, app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used for signature verification purely from the attacker-supplied `organization.login` field in the payload [1](#0-0) , and `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that org's configured `webhook_secret` is blank [2](#0-1) . `MembershipHandler#process` then resolves the target `Team` solely by `params.team.id` (github_id), with no check that the payload's `organization.login` matches the team's real `organization` [3](#0-2) . This lets an attacker who knows only the `github_id` of a privileged team pick any org with a blank secret and delete an operator's membership without any signature ever being validated against the team's actual organization.

### Finding Description
Broken binding, stated as an equality: the code implicitly assumes `organization_that_verified_signature == organization_that_owns_the_team_membership_being_mutated`. In reality, for a `Team` found by `github_id`, `params.organization.login` (used only to pick the `GitHubApp`/secret for signature verification) can be entirely unrelated to `team.organization` (the value stored when the team row was created).

Path:
1. `WebhooksController#create` parses the raw JSON body and dispatches to handlers for the `X-Github-Event` header before any signature check has meaningfully applied cryptographic verification for orgs with no secret [4](#0-3) .
2. `verify_signature` computes `repository_owner` from `params.dig('organization', 'login')` when there is no `repository` key (true for `membership` events) [5](#0-4) , and looks up `Shipit.github(organization: repository_owner)`.
3. If that org is configured in Shipit with a blank/absent `webhook_secret`, `verify_webhook_signature` short-circuits: `return true unless webhook_secret` [6](#0-5)  — no HMAC is ever computed, so the attacker needs no secret and can even omit/fabricate `X-Hub-Signature`.
4. `MembershipHandler#process` runs `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` [7](#0-6)  — lookup key is `github_id` only; the `organization:` assignment only applies on the create branch, so for a pre-existing (real, privileged) team it is never re-checked or overwritten.
5. For `action == 'removed'`, it runs `team.members.delete(member)` [8](#0-7) , deleting the `Membership` row for the victim, regardless of which org's key verified the request.

Existing guards do not stop this: `drop_unhandled_event` only checks that a handler exists for the event type, `ExplicitParameters` only validates types/presence of `action`, `team.id`, `organization.login`, `member.login` (no cross-field/ownership constraint), and there is no `require_permission!`/`User#authorized?` check anywhere in the webhook path, since webhooks are inherently unauthenticated by design and rely entirely on the HMAC secret for trust — a trust which collapses to `true` for a blank-secret org.

Attacker request: `POST /webhooks` with `X-Github-Event: membership`, body `{"action":"removed","team":{"id":<real privileged team github_id>,"name":"x","slug":"x","url":"x"},"organization":{"login":"<org-with-blank-secret>"},"member":{"login":"<victim-operator-login>"}}`, and any/garbage `X-Hub-Signature` header (or none at all, if the org lookup succeeds and secret is blank).

### Impact Explanation
The attacker can silently remove a legitimate operator's membership from a `Team` referenced in `Shipit.github_teams`, which gates authorization for privileged actions (deploy, lock, rollback, etc., depending on host app configuration of `User#authorized?`/`require_permission!`). This is a write to an authorization record (`Membership`) triggered by a webhook whose "verification" was against an unrelated, unrelated-to-the-team, attacker-chosen organization. It matches the "authentication bypass (forged webhook ... accepted)" and "escalation/de-escalation into `Shipit.github_teams` authorization" impact categories. The blast radius spans any privileged team whose numeric `github_id` the attacker can learn or guess, and is repeatable indefinitely, and cross-tenant in that a completely different (blank-secret) org's identity is used to forge state for another org's team.

### Likelihood Explanation
Requires: (a) at least one org configured in Shipit with a blank `webhook_secret` (a realistic, sometimes-default/dev configuration state per `docs/setup.md`/`secrets.*.yml` examples), (b) knowledge of the numeric GitHub `team.id` (`github_id`) of a privileged team already tracked by Shipit (discoverable via GitHub's own team APIs or prior legitimate webhook traffic, not a secret), and (c) an existing `Membership` row for the victim. No Shipit credentials, sessions, or GitHub secrets are needed — a single unauthenticated HTTP POST suffices, making the attack cheap, fully repeatable, and requiring no interaction from the victim.

### Recommendation
Do not select the signature-verification `GitHubApp`/secret from attacker-controlled `organization.login`/`repository.owner.login` for events where team ownership matters; instead, cross-check that the resolved `Team#organization` matches the org whose secret verified the request, and reject (422) on mismatch. Additionally, `MembershipHandler#find_or_create_team!` should refuse to reuse an existing `Team` row when `params.organization.login` differs from `team.organization`, rather than silently ignoring the discrepancy. As defense in depth, treat a blank/unconfigured `webhook_secret` as "reject unless explicitly allowed" rather than "always verified," or at minimum log/alert and disable state-mutating handlers for such orgs.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/membership_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Seed a real operator: `user = Shipit.create(:user, github_login: 'victim')`.
2. Seed a privileged team owned by a real org with a configured (non-blank) secret: `team = Shipit.create(:team, github_id: 4242, organization: 'real-org')`; create `Membership.create!(team:, user:)`.
3. Configure Shipit with a second org `'blank-secret-org'` whose `webhook_secret` is blank/nil (via test fixture/secrets stub).
4. Assert precondition equality holds: `assert_equal 'real-org', team.organization` and confirm `Shipit.github(organization: 'blank-secret-org').send(:webhook_secret)` is blank.
5. POST to `/webhooks` with header `X-Github-Event: membership` and body:
   `{"action":"removed","team":{"id":4242,"name":"n","slug":"s","url":"u"},"organization":{"login":"blank-secret-org"},"member":{"login":"victim"}}`, with an arbitrary/garbage `X-Hub-Signature`.
6. Assert response is `200`/`204` (not `422`), and `assert_equal 0, Membership.where(team:, user:).count` — the membership was deleted despite the signature having been "verified" only against `blank-secret-org`, an org unrelated to `team.organization == 'real-org'`, proving the broken binding `organization_verified != team.organization`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
