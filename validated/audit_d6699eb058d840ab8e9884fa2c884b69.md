### Title
Webhook signature verification is scoped to `repository.owner.login` while stack mutation is scoped to `repository.full_name`, letting one tenant's signature authorize mutation of another tenant's repository - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App config (and thus the HMAC secret) to check using `repository.owner.login`, but every `Handler` (via `Handler#stacks` / `Handler#repository_name`) instead resolves the target `Repository`/`Stack` using `repository.full_name`. These are two independently attacker-controlled JSON fields in the same forged payload, and nothing asserts they agree, so a valid signature for organization A's app can be paired with a `full_name` naming organization B's repository.

### Finding Description
The broken binding, stated as an equality that the code never enforces:

`owner_of(Repository.from_github_repo_name(payload.repository.full_name)) == payload.repository.owner.login`

Trace:
- `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` reads `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) .
- `Shipit.github(organization:)` looks up the app config keyed by that organization name and verifies the HMAC using that org's `webhook_secret` [3](#0-2) . In multi-tenant deployments (as documented/fixtured by `test/dummy/config/secrets_double_github_app.yml`, e.g. `OrgOne`/`OrgTwo`), each organization has its own distinct `webhook_secret`.
- Once the signature is accepted, `WebhooksController#create` dispatches the raw JSON to handlers unchanged: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
- Every `Handler` subclass resolves the target repository/stack from `payload.dig('repository', 'full_name')`, not from `repository.owner.login`: `Handler#stacks` and `Handler#repository_name` [5](#0-4) . The same pattern (`Repository.from_github_repo_name(params.repository.full_name)`) repeats across `PullRequest::OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler` [6](#0-5) [7](#0-6) .

Exploit flow: an attacker who legitimately owns "OrgA" and its GitHub App installation (and therefore holds "OrgA"'s real `webhook_secret`) crafts a JSON body with `repository.owner.login = "OrgA"` and `repository.full_name = "victim-org/victim-repo"`, computes the HMAC-SHA1 over that exact raw body using OrgA's secret, and POSTs it to `/webhooks` with the matching `X-Hub-Signature`. `verify_signature` selects OrgA's app (because `repository_owner` reads `owner.login`, which the attacker set to "OrgA") and the signature validates correctly against the attacker's own secret. The dispatched handler then acts on `victim-org/victim-repo` because it reads `full_name`, an entirely separate, unchecked field. Depending on the event, this can enqueue a `GithubSyncJob` for the victim's stack (push), create/mutate `Status`/`Commit` rows for the victim (status), or archive/provision the victim's `ReviewStack` (pull_request labeled/closed/reopened) — all model-write paths reachable purely from an unprivileged POST.

Existing guards do not close this gap: `drop_unhandled_event` only checks the event type exists; `verify_signature` only checks HMAC validity for whichever org `owner.login` names; `ExplicitParameters` schemas validate field types/presence but never cross-validate `full_name`'s owner segment against `owner.login`; `Repository.from_github_repo_name` only splits and downcases `full_name`, with no ownership check [8](#0-7) .

### Impact Explanation
An attacker who legitimately controls one GitHub App installation/org on a multi-tenant Shipit instance can cause writes (job enqueue, `Commit`/`Status` rows, `ReviewStack` archive/unarchive/provisioning) against any other tenant's `Repository`/`Stack` records merely by editing `repository.full_name` in a payload they sign with their own secret. This is a cross-tenant mutation where a payload authenticated for one repository/org mutates a different, unrelated repository/org's Shipit-tracked state — matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" category. It's repeatable at will against any repository the attacker can identify by owner/name.

### Likelihood Explanation
This requires the Shipit instance to be configured for multiple GitHub App organizations (the multi-org `secrets.github` schema demonstrated by `test/dummy/config/secrets_double_github_app.yml`), where the attacker legitimately owns one of the configured orgs/installations and thus possesses a real `webhook_secret` for it. Given that precondition, the attack costs one crafted HTTP POST with a correctly-computed HMAC over attacker-controlled bytes — trivial and fully repeatable, requiring no session, API token, or victim secret.

### Recommendation
In `Handler#repository_name` (and everywhere handlers derive the target repository from `full_name`), cross-check that the owner segment of `repository.full_name` matches the `repository.owner.login`/organization that was actually used to verify the signature (e.g., pass the verified organization down from `WebhooksController` into the handler call, and reject/drop the event if `full_name`'s owner doesn't match it).

### Proof of Concept
Using `test/dummy/config/secrets_double_github_app.yml` (OrgOne/OrgTwo, each with distinct `webhook_secret`) and a `Stack` fixture owned by a `Repository` under `OrgTwo`:
1. Set `Shipit.github(organization: 'OrgOne').webhook_secret` to a known value; leave `OrgTwo` with its own distinct secret.
2. Build a push payload: `repository.owner.login = "OrgOne"`, `repository.full_name = "OrgTwo/repo"` (matching the `OrgTwo`-owned `Stack` fixture's `full_name`), sign the exact raw JSON body with `OrgOne`'s secret to produce `X-Hub-Signature`.
3. POST to `/webhooks` with `X-Github-Event: push` and that signature.
4. Assert `response` is `:ok` and `assert_enqueued_with(job: GithubSyncJob, args: [stack_id: org_two_stack.id, ...])` — proving OrgOne's signature caused a write targeting OrgTwo's stack, i.e. `owner_of(Repository.from_github_repo_name(full_name))` ("OrgTwo") diverged from the verifying org ("OrgOne") yet the mutation still occurred.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
