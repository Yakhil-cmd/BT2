### Title
Push-webhook triggers `GithubSyncJob` for any repository regardless of which organization's signature verified the request - ([File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate against based on `repository_owner`, which is read from the *same* JSON body that later determines which `Repository`/`Stack` the event acts on. In a multi-organization deployment (the documented `github: { org1: {...}, org2: {...} }` schema), the organization whose webhook secret authenticates the request is not cryptographically bound to the repository the handler subsequently writes to.

### Finding Description
The signature-check binds "authenticated organization" to a value taken from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is computed from `params.dig('repository', 'owner', 'login')` (or `organization.login`), and `Shipit.github(organization: repository_owner)` selects the per-organization `webhook_secret` used to verify the HMAC: [3](#0-2) 

Once the signature check passes, the raw payload is handed unmodified to the registered handler: [4](#0-3) 

The `Handler` base class then determines *which* repository/stacks to act on using a **different** field of the same payload — `repository.full_name` — with no re-check that this repository actually belongs to `repository_owner`: [5](#0-4) 

`PushHandler#process` uses that repository/stack resolution directly to trigger a git sync: [6](#0-5) 

Because the HMAC only proves "this body was signed with organization X's webhook secret," and organization X fully controls the content of that body (including `repository.full_name`), organization X can set `repository.owner.login` = `X` (so the signature check passes with its own known secret) while setting `repository.full_name` = `Y/some-repo`, a repository belonging to an entirely different configured organization `Y`. `Handler#repository_name` and `Handler#stacks` will resolve to `Y`'s `Repository`/`Stack` records via `Repository.from_github_repo_name`, and `PushHandler` will call `stack.sync_github(expected_head_sha: params.after)` on that unrelated stack.

This is the same class of bug as the reported `KlasterEcdsaModule.initForSmartAccount` issue: a value that is *acted upon* (`repository.full_name` → which `Stack` gets synced) is not actually covered by the same trust check that was supposedly established (`repository.owner.login` → which secret validated the signature), even though both values live in the same signed blob. The binding "organization that authenticated == organization that is written to" is broken.

### Impact Explanation
An administrator of any one GitHub organization configured in Shipit's multi-org `secrets.yml` (who legitimately controls that organization's GitHub App webhook settings, but has no access whatsoever to other organizations or their repositories in the same Shipit instance) can forge webhook events that are misattributed to an arbitrary other tracked repository. This lets them queue `GithubSyncJob` for a stack under a different organization/repository, forcing head-SHA resynchronization (`expected_head_sha`) and other push-triggered side effects (branch tracking, commit ingestion) for a target they don't own. This is a cross-repository write/side-effect that crosses an organizational trust boundary without any actual permission on the target repository — matching the "cross-repository writes" High/Critical impact bucket.

### Likelihood Explanation
Requires the attacker to legitimately administer one configured GitHub organization/App installation in a multi-org Shipit deployment (a realistic, documented configuration per `docs/setup.md` and `config/secrets.development.shopify.yml`), but requires no access to the victim organization, no Shipit account, and no API token. Crafting the forged webhook body and its self-computed HMAC is trivial once the attacker's own webhook secret is known (which it always is, since it's their own org's secret).

### Recommendation
After verifying the webhook signature for `repository_owner`, re-validate that the repository resolved by `Handler#repository_name` (`repository.full_name`) actually belongs to that same verified organization before dispatching to handlers — e.g., assert `repository.full_name.split('/').first.casecmp(repository_owner) == 0`, or resolve the `Repository` only within the scope of the verified organization rather than by a global `owner/name` lookup.

### Proof of Concept
1. Deploy Shipit with the multi-org schema, e.g. `github: { org-attacker: { webhook_secret: "attacker-secret", ... }, org-victim: { webhook_secret: "victim-secret", ... } }`.
2. Attacker is an admin of `org-attacker`'s GitHub App and knows `attacker-secret` (their own secret, legitimately).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-secret, body)` — this passes `verify_signature` because `repository_owner` resolves to `org-attacker`.
5. `WebhooksController#create` dispatches to `PushHandler`, whose `repository_name` reads `repository.full_name` = `org-victim/victim-repo`, resolving to the victim's actual tracked `Stack`, and triggers `stack.sync_github(expected_head_sha: "<attacker chosen sha>")` — a write against a repository the attacker does not control.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
