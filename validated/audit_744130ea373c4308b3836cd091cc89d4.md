### Title
Cross-repository status forgery — `StatusHandler#process` looks up commits by `sha` alone, with no check against the webhook payload's repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit(s) using only `Commit.where(sha: params.sha)`, never comparing the webhook's originating repository to `commit.stack.repository`. Because GitHub SHA1s are content-addressed and reproducible by anyone who can construct an identical commit object (same tree, parents, author/committer identities and timestamps, message), an attacker who owns any GitHub repository wired to the same Shipit instance can emit a `status` webhook for a SHA that happens to also exist as an undeployed commit on a victim stack, forging a `success` status that satisfies `Commit#deployable?` and triggers `ContinuousDeliveryJob` for the victim stack.

### Finding Description
The claimed binding is: `commit.deployable? == true` should only be reachable when `status.payload.repository == commit.stack.repository`. In the actual code this binding does not exist.

Path:
1. `Shipit::WebhooksController` verifies the HMAC signature of the incoming payload via `GitHubApp#verify_webhook_signature` (or `verify_signature`), which only proves the payload was signed with *some* configured webhook secret — for a `status` event this secret is per-repository/per-app-installation and is controlled by whoever owns the sending repository. An attacker who owns their own repo and connects it to the same GitHub App/Shipit installation legitimately possesses a valid signature for events *from their own repo*.
2. The controller dispatches to `Shipit::Webhooks::Handlers::StatusHandler#process`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 
This query is global across the `commits` table — it is not scoped to a `stack_id`, `repository_id`, or any value derived from `params.repository`/`params.repository_owner`. Any commit row anywhere in the Shipit database whose `sha` column matches the attacker-supplied `params.sha` is processed, regardless of which repository emitted the event.

3. `Commit#create_status_from_github!` → `add_status` → `statuses.replicate_from_github!` creates a `Status` row tied to the victim's `commit`/`stack`, then calls `stack.schedule_merges` and (via the `after_commit` callback chain on commit creation, or directly through `add_status`'s status-state transition) leads into `Commit#schedule_continuous_delivery`:
```ruby
def schedule_continuous_delivery
  return unless deployable? && stack.continuous_deployment? && stack.deployable?
  ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)
end
``` [2](#0-1) 
4. `deployable?` is:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [3](#0-2) 
`success?` is delegated to `status`, which is derived purely from the `statuses`/`check_runs` rows just created by the forged webhook — there is no repository provenance check anywhere in this chain.

Root cause: `StatusHandler#process` (and identically-shaped handlers for check-runs/statuses) resolve commits by `sha` only. Since SHA1 commit hashes are a function of tree contents + parent SHAs + author/committer name/email/timestamp + message (not of which repository stores them), an attacker can reconstruct a bit-identical commit object in their own repository (e.g., by cherry-picking/copying the exact tree and reusing the same authored/committer dates and identities) to produce a colliding SHA, then push a commit with that SHA to their own repo and immediately have GitHub (or a raw POST if they can source a signed request) emit a `status` event for it, which propagates into every stack that happens to contain a commit with the same SHA.

Existing guards do not close this gap: signature verification authenticates "a webhook from *a* connected repository," not "a webhook from *this specific* stack's repository"; there is no `ExplicitParameters` field or model validation constraining `Commit.where(sha:)` to the correct `stack_id`.

### Impact Explanation
A successful forgery causes Shipit to write a `Status` row for a repository/stack that never generated it, and — on any stack fixture with `continuous_deployment: true` and no blocking statuses/lock — enqueues `ContinuousDeliveryJob`, i.e., an **unauthorized deploy** of a victim's commit that never had a legitimate green CI run. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." The attack is repeatable against any stack whose HEAD/undeployed commit SHA the attacker can reproduce, and blast radius extends to every stack sharing a Shipit installation reachable by the attacker's own connected repository's webhooks.

### Likelihood Explanation
Preconditions are non-trivial but attacker-achievable without any Shipit secret: the attacker needs (a) a repository they control that is connected to the same Shipit/GitHub App installation (so their `status` webhooks are accepted and signed), and (b) the ability to produce a commit with an identical SHA1 to a specific undeployed commit on the victim stack — achievable by copying the exact commit object (tree, parents, author, committer, timestamps, message) into their own repo, since SHA1 does not encode the containing repository. This requires knowledge of the victim's exact commit metadata (obtainable from the victim's public/forked repo or PR diff) but no credentials. Given that, the exploit is a single webhook POST and is repeatable at will.

### Recommendation
Scope commit/status lookups by the originating repository, not just `sha`. In `StatusHandler#process` (and equivalent handlers), resolve the repository from the webhook payload (`params.repository.full_name`/owner+name) and join/filter `Commit` through `Stack`/`Repository` so only commits belonging to a stack whose `repository` matches the payload's repository are updated, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: params.repository_owner, name: params.repository_name })`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "a status webhook from a different repository cannot mark a victim stack's commit deployable" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment: true fixture
  victim_commit = victim_stack.commits.undeployed.last

  # Attacker's own connected repo emits a status for a SHA equal to victim_commit.sha,
  # but the payload's repository is NOT victim_stack.repository.
  payload = {
    sha: victim_commit.sha,
    state: 'success',
    repository: { full_name: 'attacker/unrelated-repo' }, # never checked
    context: 'ci/attacker'
  }

  assert_no_enqueued_jobs(only: ContinuousDeliveryJob) do
    Shipit::Webhooks::Handlers::StatusHandler.new(payload_hash: payload).process
  end

  refute victim_commit.reload.deployable?, "commit became deployable from a cross-repository status"
end
```
Both sides of the binding — `commit.stack.repository` (`victim/repo`) vs the webhook's `params.repository` (`attacker/unrelated-repo`) — never match, yet `StatusHandler#process` proceeds and `Commit#deployable?`/`ContinuousDeliveryJob` fire, proving the divergence.
