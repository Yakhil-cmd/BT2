### Title
Persistent starvation of the delayed-receipt queue via storage-proof-soft-limit exhaustion by local receipts processed ahead of the backlog - ([File: runtime/runtime/src/lib.rs], [File: core/parameters/src/config.rs])

### Summary
`WitnessConfig::main_storage_proof_size_soft_limit` is enforced per-chunk by checking `check_proof_size_limit_exceed()` *before* popping each receipt in three sequential phases: local receipts, then delayed receipts, then incoming receipts. Because local (new) receipts are processed before the delayed backlog every chunk, and `CongestionControlConfig::min_tx_gas` guarantees a non-zero amount of new-transaction gas is always admitted regardless of how large the delayed backlog is, an attacker can repeatedly submit cheap-gas/high-storage-proof transactions that saturate the soft limit during the local phase, causing `process_delayed_receipts` to break immediately without popping a single receipt — chunk after chunk.

### Finding Description
`process_receipts` in `runtime/runtime/src/lib.rs` calls the three phases in this fixed order: [1](#0-0) 

Each phase checks the same shared, running proof-size accumulator before processing each receipt: [2](#0-1) [3](#0-2) 

Because `process_local_receipts` runs first with an empty accumulator, it is effectively guaranteed at least one receipt of progress (soft-limit semantics — "things are added until the limit is exceeded"). But `process_delayed_receipts` checks the *already-accumulated* proof size from the local phase before popping anything from the backlog; if the local phase alone already pushed the total past `main_storage_proof_size_soft_limit`, the delayed-receipt loop `break`s on its very first iteration and zero backlog receipts are processed that chunk: [4](#0-3) 

Crucially, the amount of gas allowed for converting new transactions into local receipts is never driven to zero by congestion control — it is linearly interpolated between `max_tx_gas` and `min_tx_gas`, and `min_tx_gas` is a fixed non-zero floor: [5](#0-4) [6](#0-5) 

Storage-proof cost per byte read/removed is far cheaper (gas-wise) than `min_tx_gas` would allow, as documented (a single receipt can approach the ~4MB `main_storage_proof_size_soft_limit`/`per_receipt_storage_proof_size_limit`): [7](#0-6) 

So an attacker who owns an account on a target shard can, every chunk, submit one cheap-gas transaction engineered to generate storage proof close to the soft limit (e.g., many trie reads/removals against a wide trie subtree they control). Since this transaction fits well within the always-admitted `min_tx_gas` budget, it is converted to a local receipt and processed first in every chunk, saturating `main_storage_proof_size_soft_limit` before `process_delayed_receipts` gets to run. The delayed queue (which may hold other users'/attacker's own earlier receipts, including cross-shard receipts) never advances as long as the attacker keeps this up, chunk after chunk — a persistent starvation of the backlog with no hard integer bound ever reached.

### Impact Explanation
This is a liveness/availability violation: receipts that land in the delayed queue on the targeted shard can be denied progress indefinitely as long as the attacker keeps submitting low-gas/high-storage-proof transactions each chunk. This affects any user whose receipts are queued behind the attacker's induced backlog (e.g., cross-contract calls, cross-shard receipts), causing indefinite delay of their transaction execution — a chain-level "progress not preserved" / chunk-processing starvation bug on the shard, matching the "chain stall"-class impact (denial of service / unbounded resource growth in the delayed-receipts state) rather than direct fund loss.

### Likelihood Explanation
- Requires only an ordinary account (no validator/node privileges).
- Requires the attacker to control an account on the target shard and repeatedly submit transactions (one per chunk) engineered to generate storage proof close to `main_storage_proof_size_soft_limit` while staying within `min_tx_gas`.
- The mechanism (`process_local_receipts` → `process_delayed_receipts` → `process_incoming_receipts` ordering, plus `min_tx_gas` floor) is stable, deterministic protocol logic, not a rare race condition, so the attack is fully repeatable every chunk with no special timing needed.

### Recommendation
Reorder receipt processing so the delayed backlog is checked/processed before local/incoming receipts are allowed to consume the storage-proof budget (as originally documented in `docs/RuntimeSpec/Components/RuntimeCrate.md`), or reserve a portion of `main_storage_proof_size_soft_limit` specifically for delayed receipts so that local/incoming receipts cannot fully preempt backlog processing. Additionally, consider coupling `min_tx_gas`/local-receipt admission to the shard's storage-proof-size congestion state, not just gas-based congestion, so that a growing delayed backlog also throttles the local-receipt storage-proof budget.

### Proof of Concept
Integration test plan (extend `integration-tests/src/tests/features/storage_proof_size_limit.rs`):
1. Set `main_storage_proof_size_soft_limit` to a small value (as in existing `test_main_storage_proof_size_soft_limit`).
2. Pre-populate the delayed-receipt queue on a shard with N victim receipts (e.g., via a prior chunk that overflows the soft limit, as the existing test does).
3. Each subsequent chunk, have the attacker submit one cheap-gas transaction (well under `min_tx_gas`) to itself that is engineered to generate storage proof close to the soft limit (e.g., many distinct trie reads).
4. Produce M chunks (M bounded, e.g. 20) and assert:
   - Each chunk's `to_transactions()` includes the attacker's tx (i.e., admitted as local receipt each time).
   - `chunk.prev_outgoing_receipts()` / execution outcomes never include the victim delayed receipts across all M chunks (i.e., zero backlog progress), demonstrating that "progress is preserved" is violated — the victim receipts remain stuck past the bound within which they should have been included.
   - Optionally assert `delayed_receipts_count` in `apply_result` stays constant or grows over the M chunks instead of shrinking.

```rust
/// How much gas of the next chunk we want to spend on converting new
/// transactions to receipts.
fn chunk_tx_gas_limit(
    runtime_config: &RuntimeConfig,
    prev_block: &PrepareTransactionsBlockContext,
    shard_id: ShardId,
) -> Gas {
    // The own congestion may be None when a new shard is created, or when the
    // feature is just being enabled. Using the default (no congestion) is a
    // reasonable choice in this case.
    let own_congestion = prev_block.congestion_info.get(&shard_id).cloned();
    let own_congestion = own_congestion.unwrap_or_default();

    let congestion_control = CongestionControl::new(
        runtime_config.congestion_control_config,
        own_congestion.congestion_info,
        own_congestion.missed_chunks_count,
    );
    congestion_control.process_tx_limit()
}
```

```markdown
* `per_receipt_storage_proof_size_limit - 4 MB`
  * Executing a receipt generates storage proof. A single receipt is allowed to generate at most 4MB of storage proof. This is a hard limit, receipts which generate more than that will fail.
* `main_storage_proof_size_soft_limit - 4 MB`
  * This is a limit on the total size of storage proof generated by receipts in one chunk. Once receipts generate more storage proof than this limit, the chunk producer stops processing receipts and moves the rest to the delayed queue.
  * It's a soft limit, which means that the total size of storage proof could reach 8 MB (3.99MB + one receipt which generates 4MB of storage proof)
  * Due to implementation details it's hard to find the exact amount of storage proof generated by a receipt, so an upper bound estimation is used instead. This upper bound assumes that every removal generates additional 2000 bytes of storage proof, so receipts which perform a lot of trie removals might be limited more than theoretically applicable.
```
