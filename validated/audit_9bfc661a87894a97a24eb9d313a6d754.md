### Title
Definition/Address Malleability via Lossy UTF-8 Encoding of Lone Surrogates in `getSourceString` used by `getChash160` - (File: `string_utils.js`, `object_hash.js`, `chash.js`)

### Summary
`ocore`'s address derivation (`getChash160`) and the legacy (non-JSON) unit-signing hash both serialize JS objects into a plain string via `getSourceString` and then hash that string with `crypto.createHash(...).update(str, "utf8")`. Node's UTF-8 encoder silently replaces any unpaired ("lone") UTF-16 surrogate code unit in the JS string with the replacement character U+FFFD before hashing. Distinct input strings that differ only in the specific invalid surrogate value therefore encode to identical UTF-8 byte sequences and hash identically — the same root cause (lossy Unicode normalization feeding a hash/lookup) as CVE-2020-8929/GHSA-g5vf-v6wf-7w2r in Tink, where invalid byte sequences collapsed to the same hash-map key.

### Finding Description
`getSourceString` builds a component string directly from raw JS string values without any Unicode well-formedness normalization: [1](#0-0) 
This is then hashed for two ecosystem-critical purposes:
1. **Address derivation** — `getChash160` (used for every payment/AA address definition that is not the special `'autonomous agent'` array) always uses `getSourceString`, never the protected JSON variant: [2](#0-1) 
2. **Legacy unit signing hash** — `getUnitHashToSign` falls back to `getSourceString` for units without `version` or with `versionWithoutTimestamp`: [3](#0-2) 

The resulting string is hashed with an explicit `"utf8"` update in `chash.js`: [4](#0-3) 

By contrast, the newer JSON-based serializer used for the post-`aa2UpgradeMci` code paths explicitly guards against this exact class of bug by escaping lone surrogates before hashing: [5](#0-4) 

Because `getChash160`/definition hashing never uses this protected path, any oscript/definition or unit field that is a plain JS string containing an unpaired surrogate (e.g., a `data feed` name/value, an `in address book` label, or any other user-supplied string embedded in an address definition) will be silently mapped to U+FFFD when the definition string is turned into hash-input bytes. Two syntactically different definitions/objects that differ only in the specific invalid surrogate code point collapse to the same UTF-8 byte stream and therefore the same SHA-256/RIPEMD-160 digest and the same derived chash/address — exactly analogous to Tink's ciphertext-prefix collision caused by lossy Unicode-to-string conversion of raw bytes.

### Impact Explanation
If an attacker can construct two distinct address definitions (or, on the legacy path, two distinct unit contents) that differ only via such an invalid-surrogate substitution, both will hash to the identical `chash160`/unit-signing hash. This breaks the implicit uniqueness guarantee that "one address = one definition" and "one signed hash = one exact content": a party could reveal or authenticate against a definition variant different from the one the counterparty believes they are dealing with, or (on the legacy unit-hash path) a signature computed over one string variant would also validate against a different, "mutated" content that hashes to the same bytes. This is a integrity/malleability defect over addresses/unit content — the same class of issue the advisory flags (CWE-176/CWE-327: improper Unicode handling causing cryptographic malleability) — with potential downstream effects on definition/authentifier evaluation and hash-based validation consistency (`hasValidHashes` in `validation.js` only recomputes and compares hashes, so it cannot detect this kind of digest collision).

### Likelihood Explanation
Exploitation requires the attacker to control a string field that ends up embedded in an address definition or a legacy-version unit (e.g., data-feed name/value strings, or other free-form string components allowed by oscript definitions) and to be able to embed an unpaired UTF-16 surrogate in it — something JavaScript strings permit natively (e.g., via `String.fromCharCode(0xD800)`), and which no visible validation in `string_utils.js`/`chash.js` currently rejects. This makes the precondition realistic for any unprivileged unit/AA poster who controls definition or oscript string content, though the practical value hinges on actually finding two "distinct" definitions that are meaningfully different while colliding — this bounds the likelihood to Medium.

### Recommendation
Apply the same well-formedness normalization used in `getJsonSourceString`/`toWellFormedJsonStringify` to `getSourceString` (and to any hashing path in `chash.js`/`object_hash.js` that consumes raw strings), i.e., escape lone surrogates to a deterministic, injective representation (e.g., `\uXXXX`) before the UTF-8-lossy `crypto.createHash(...).update(str, "utf8")` call, so that no two distinct JS strings can ever encode to the same hash-input bytes.

### Proof of Concept
Conceptually (Node.js):
```js
var crypto = require('crypto');
var s1 = "feed" + String.fromCharCode(0xD800);       // lone high surrogate
var s2 = "feed" + String.fromCharCode(0xDFFF);       // different lone surrogate
console.log(Buffer.from(s1, 'utf8').equals(Buffer.from(s2, 'utf8'))); // true: both become "feed\uFFFD"
console.log(crypto.createHash('sha256').update(s1, 'utf8').digest('hex') ===
            crypto.createHash('sha256').update(s2, 'utf8').digest('hex')); // true
```
Embedding `s1` vs `s2` as a distinguishing field inside an address-definition array passed to `getChash160` (`object_hash.js:10-13` → `chash.js:122-127`, via `getSourceString`) yields the same derived `chash160`/address for two textually different definitions, demonstrating the collision reachable through normal address-definition construction.
