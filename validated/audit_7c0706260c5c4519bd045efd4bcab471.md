### Title
Cross-repository/stack commit-status forgery via unscoped `sha` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` processes GitHub `status` webhook events by looking up commits purely by `sha`, without ever checking that the `sha` belongs to the same repository whose webhook signature was verified. This breaks the binding "the organization/repository that authenticated the webhook" vs. "the repository/stack that is actually written," letting a status forged for one registered repository affect `Commit` records belonging to a completely different stack/repository if the sha happens to be shared or reused.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC using only `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`): [1](#0-0) [2](#0-1) 

This only proves that the request body was signed with the secret belonging to *some* organization Shipit tracks — it says nothing about which repository/stack the payload's data should be allowed to mutate. The actual write path for `status` events is: [3](#0-2) 

Unlike other handlers (`PushHandler`, pull-request handlers, etc.) which scope their effect through `Handler#stacks`/`Repository.from_github_repo_name(repository_name)` (i.e., bound to the exact `repository.full_name` in the signed payload): [4](#0-3) [5](#0-4) 

`StatusHandler#process` never consults `repository_name`/`stacks` at all — it queries `Commit.where(sha: params.sha)` globally across the entire `commits` table, which spans every `Stack`/`Repository` Shipit tracks: [6](#0-5) 

`Commit` rows belong to a `Stack` (`belongs_to :stack`), and applying a status calls `Commit#create_status_from_github!` → `add_status`, which updates the commit's cached status and, on transition to `pending`/`success`, calls `stack.schedule_merges`, and on any state change emits `deployable_status`/`commit_status` hooks: [7](#0-6) [8](#0-7) 

So the equality that should hold — "the repository whose webhook secret authenticated this request" == "the repository/stack whose `Commit` rows get mutated" — is not enforced. `StatusHandler` binds only on `sha`, a value fully attacker-controlled in the payload and not scoped to the authenticating repository at all.

### Impact Explanation
Because `sha` is git-content-addressed and not secret (visible on GitHub, in PR/commit URLs, CI logs, etc.), and because `StatusHandler` performs no cross-check against `repository.full_name`/`owner.login` beyond what was used purely to pick a signing key, any organization/repository legitimately registered in Shipit (even a low-value, low-privilege one an attacker administers) can send/trigger a genuinely-signed `status` webhook whose `sha` field targets a commit that exists in an entirely different tracked stack (e.g., a shared ancestor commit from a common upstream/fork, a cherry-picked/duplicated commit object, or any commit whose SHA the attacker can reproduce or otherwise cause to be posted). Doing so:
- Overwrites the target commit's CI status (`Commit#create_status_from_github!`), potentially flipping a failing/missing status to `success`.
- Triggers `stack.schedule_merges`, which can unblock or accelerate an unauthorized merge for a target stack the attacker has no legitimate write access to, satisfying the Critical "unauthorized deploy/merge" impact bar.
- Also affects deploy-readiness by clearing `deployable_status`, potentially unblocking an unauthorized deploy of an unrelated stack.

This crosses a genuine trust boundary: the webhook signature only proves "some tracked org sent this," not "this specific repository/stack authorized this specific commit's status," which is exactly analogous to the OTLM bug's failure to distinguish which balance/token a mutation should apply to.

### Likelihood Explanation
Exploitation requires: (1) the attacker controlling or having push access to at least one repository/organization already registered as a Shipit stack (a low bar in any multi-tenant/permissive Shipit deployment, matching the "permissionless" nature the sponsor called out in the analogous OTLM case), and (2) a `sha` collision/reuse across stacks, which is realistic in common setups — forked repositories, mirrored repositories, monorepo splits, or multiple `Stack` records pointing at the same underlying `Repository` (e.g., staging/production stacks of the same repo, or multiple environments) all frequently share identical commit objects and thus identical SHAs across different `Stack` rows. Given how common multi-stack/multi-environment configurations are in Shipit, this is a realistic, not merely theoretical, occurrence.

### Recommendation
Scope `StatusHandler#process` (and any other handler that currently ignores `Handler#stacks`) to the repository asserted in the signed payload, mirroring `PushHandler`'s pattern:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
This binds the mutation strictly to the `stack`/`repository` derived from `repository.full_name` in the same signed payload used for authentication, closing the gap between "who signed this" and "what gets written."

### Proof of Concept
1. Attacker administers `org-attacker/throwaway-repo`, which is registered as a Shipit stack (Shipit's GitHub App is installed on `org-attacker`, giving them a legitimately-signed webhook channel).
2. Attacker identifies (via public GitHub UI/Shipit UI) the `sha` of a commit belonging to `org-victim/important-repo`'s stack that currently has a failing/missing required CI status, blocking its merge queue.
3. Attacker causes GitHub to emit (or crafts, if they control the sending side of automation) a `status` event on their own org/repo referencing that `sha` with `state: "success"`, `context: <required-context>`, signed by `org-attacker`'s legitimate webhook secret.
4. `WebhooksController#verify_signature` validates the HMAC successfully because it only checks against `org-attacker`'s secret via `repository_owner`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the commit row in `org-victim/important-repo`'s stack (unscoped by repository), and calls `create_status_from_github!`, marking it "success."
6. `stack.schedule_merges` fires for `org-victim`'s stack, potentially triggering an unauthorized merge that the actual CI state never sanctioned.
