### Title
CCMenu API token scoped to one stack can read the CI status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` authenticates a request via a bare token in `params[:token]` and only checks the generic `read:stack` permission, but it resolves the target stack from the *entire* `Stack` table instead of the `ApiClient`-scoped collection used everywhere else in the API. This breaks the "stack a token authorises" == "stack a token touches" binding.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scoped stack resolution used by the rest of the API: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` is scoped to a specific stack, and `stack` builds on top of that scoped relation.

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely and resolves directly against the unscoped `Stack` table using only the URL parameter: [2](#0-1) 

It also overrides `authenticate_api_client` to accept the token from a query-string/param instead of the `Authorization` header (a legitimate concession for CI status tools that can't set custom headers), and falls back to the normal Basic-Auth flow if the param isn't present: [3](#0-2) 

The controller enforces only the coarse-grained `read:stack` permission via `require_permission`: [4](#0-3) 

`ApiClient#check_permissions!` verifies only that the permission name is in the client's `permissions` array — it never checks whether the `stack_id` on the token matches the `stack_id` param in the request: [5](#0-4) 

The client's `stack_id` scoping is a real security boundary elsewhere in the API — e.g. `BaseController#stacks`/`#stack` and the stacks index test confirm a stack-scoped client only sees its own stack: [6](#0-5) 

CCMenu tokens are minted specifically scoped to one stack and handed out as a plain URL (embedded in a CI-status-monitor URL), by `CCMenuUrlController`: [7](#0-6) 

Because that token only carries `permissions: ['read:stack']` and an HMAC-signed client id (no stack binding enforced server-side in this controller), and because `Api::CCMenuController#stack` looks up `Stack.from_param!(params[:stack_id])` against the whole table rather than `stacks.from_param!`, presenting the same token with a *different* `stack_id` in the URL returns CI/deploy status data for a different, unauthorized stack.

**Binding broken:** `ApiClient.stack_id` (the stack the token is authorized for) ≠ `stack_id` param actually used to resolve data (the stack the request touches). Before the attacker's request, the token's authorization is meant to equal a single stack; after crafting a request with a different `stack_id`, the two diverge and the check silently passes because only the permission name, not the resource, is validated.

### Impact Explanation
This grants unauthenticated-for-that-resource read access to another stack's deploy/build state (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock state, etc.) — an unauthorized cross-stack read of stack/task state, matching the "High" impact bucket ("unauthenticated read of stack state, task streams or deploy output"). It does not, by itself, grant write/deploy capability, since `write:stack`/`deploy:stack` permissions are unaffected, but it discloses potentially sensitive CI/deployment metadata (branch, deploy URL structure, lock reasons) for stacks the token holder was never meant to see.

### Likelihood Explanation
Likelihood is moderate: an attacker needs a valid CCMenu token (which is routinely distributed as a plain, unauthenticated-looking URL to any user who can view a stack's settings page and is designed to be pasted into third-party CI monitor tools). Any holder of one such token for one stack can enumerate `owner/repo/environment` triples for other stacks (which are not secret — they're on the corresponding pages/URLs) and swap the `stack_id` segment, since the controller performs no server-side check that the token's `stack_id` matches the requested one.

### Recommendation
In `Api::CCMenuController#stack` (and any other controller overriding the base `stack`/`stacks` scoping), reuse the scoped `stacks` collection from `BaseController` (`stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so a stack-scoped `ApiClient` cannot resolve stacks outside its `stack_id`.

### Proof of Concept
1. As a Shipit user with access to stack A, visit stack A's settings page; `CCMenuUrlController#fetch` calls `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, creating a token that is *intended* to be usable for stack A's CCMenu feed only. Capture the returned `ccmenu_url`, e.g. `.../api/stacks/orgA/repoA/env/ccmenu?token=<TOKEN>`. [8](#0-7) 
2. Modify the URL's `stack_id` path segment to point at a different, private stack B (`orgB/repoB/env2`) that the same token was never associated with, keeping the same `token`.
3. Send `GET /api/stacks/orgB/repoB/env2/ccmenu?token=<TOKEN>`.
4. `authenticate_api_client` succeeds because the token itself is valid (HMAC-verified `ApiClient#authenticate`): [9](#0-8) 
5. `require_permission :read, :stack` succeeds because `permissions` contains `read:stack` (no stack-identity check): [5](#0-4) 
6. `stack` resolves stack B directly from the unscoped `Stack` table: [10](#0-9) 
7. The response renders stack B's build/deploy status XML, disclosing data the token was never scoped to access.
