### Title
Bridge Fallback Uses `msg.sender` as Cross-Chain Recipient, Causing Permanent KAIA Loss When Called via Intermediate Contract — (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

The `BridgeTransferKLAY` fallback function unconditionally uses `msg.sender` as the KAIA recipient address on the counterpart chain. When the fallback is triggered through an intermediate contract (smart-contract wallet, multicall, proxy), the intermediate contract's address is recorded as the cross-chain recipient. Bridge operators faithfully relay that address to `handleKLAYTransfer` on the counterpart chain, permanently sending the user's KAIA to an address the user does not control.

---

### Finding Description

`BridgeTransferKLAY.sol` exposes two paths for a user to bridge KAIA:

1. `requestKLAYTransfer(address _to, …)` — caller explicitly names the recipient.
2. The unnamed payable fallback — uses `msg.sender` as the recipient.

```solidity
// File: contracts/service_chain/bridge/BridgeTransferKLAY.sol  line 126-129
// () requests transfer KLAY to msg.sender address on relative chain.
function () external payable {
    _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
}
``` [1](#0-0) 

`_requestKLAYTransfer` emits `RequestValueTransfer` with `_to = msg.sender`:

```solidity
// File: contracts/service_chain/bridge/BridgeTransferKLAY.sol  line 113-123
emit RequestValueTransfer(
    TokenType.KLAY,
    msg.sender,   // from
    _to,          // to  ← set to msg.sender by the fallback
    address(0),
    msg.value.sub(_feeLimit),
    requestNonce,
    fee,
    _extraData
);
``` [2](#0-1) 

Bridge operators observe this event and call `handleKLAYTransfer` on the counterpart chain, which unconditionally transfers KAIA to the recorded `_to` address:

```solidity
// File: contracts/service_chain/bridge/BridgeTransferKLAY.sol  line 98-99
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [3](#0-2) 

Additionally, `_payKLAYFeeAndRefundChange` in `BridgeFee.sol` also refunds excess fee to `msg.sender`, so the fee refund is also misdirected to the intermediate contract:

```solidity

require(ok, "refund fee failed");
``` [4](#0-3) 

---

### Impact Explanation

When a user sends KAIA to the bridge contract through any intermediate contract — a smart-contract wallet (Gnosis Safe, etc.), a multicall aggregator, or a proxy — `msg.sender` is the intermediate contract's address, not the user's EOA. The `RequestValueTransfer` event records the intermediate contract's address as `_to`. Bridge operators relay this faithfully to the counterpart chain. `handleKLAYTransfer` sends the KAIA to that address on the counterpart chain. Because the intermediate contract typically does not exist at the same address on the counterpart chain (or is not controlled by the user there), the KAIA is permanently inaccessible. This is an unauthorized, irreversible transfer of bridged KAIA away from the intended recipient — matching the allowed impact gate of "unauthorized transfer of KAIA."

---

### Likelihood Explanation

The likelihood is low-to-medium. Smart-contract wallets and multicall patterns are increasingly common. Any user who sends KAIA to the bridge address via a contract (rather than a raw EOA transaction) triggers this path. The fallback is the natural "send ETH/KAIA to bridge" UX pattern that many wallets and dApps use. No privileged access is required; any unprivileged user can trigger the loss accidentally.

---

### Recommendation

Remove the implicit `msg.sender`-as-recipient fallback, or require callers to explicitly specify the recipient. The safe path already exists:

```solidity
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable
``` [5](#0-4) 

Either:
- **Remove the fallback entirely**, forcing all callers to use `requestKLAYTransfer` with an explicit `_to`.
- **Or revert in the fallback** with a descriptive error directing users to `requestKLAYTransfer`.

---

### Proof of Concept

1. Deploy a simple multicall/proxy contract `Intermediary` on the service chain.
2. Fund `Intermediary` with KAIA.
3. From `Intermediary`, call `bridge.transfer(value)` (or use a low-level `.call{value: amount}("")`) targeting the bridge address — this triggers the fallback.
4. The bridge emits `RequestValueTransfer` with `to = address(Intermediary)`.
5. Bridge operators call `handleKLAYTransfer(txHash, Intermediary, Intermediary, amount, nonce, blockNum, "")` on the parent chain.
6. The parent-chain bridge executes `Intermediary.call{value: amount}("")` — sending KAIA to `Intermediary`'s address on the parent chain.
7. If `Intermediary` does not exist at that address on the parent chain (common for factory-deployed contracts with different nonces), the KAIA is sent to an EOA-equivalent address that no one controls, or to a contract the user does not own.
8. The user's KAIA is permanently lost with no recovery path, since the bridge nonce is already consumed and `handleKLAYTransfer` is idempotent (replay-protected by `_setHandledRequestTxHash`). [6](#0-5) [7](#0-6)
