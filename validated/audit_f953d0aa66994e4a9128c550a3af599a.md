### Title
`StatusHandler#process` writes commit statuses without validating the commit belongs to the webhook's own repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits purely by `Commit.where(sha: params.sha)` and never touches `Handler#repository_name` or `Handler#stacks`, unlike `PushHandler#process`, which scopes strictly to `stacks.not_archived.where(branch:)` derived from `repository_name`. Because git commit SHAs are shared identically across forks of the same base history, a `status` webhook whose signature is validly signed for the attacker's own (forked) repository can still match and mutate a `Commit` record that actually belongs to a different tenant's `Stack`.

### Finding Description
The binding that should hold for every write path is: `repository_name == payload.dig('repository','full_name')` gates the records touched, exactly as `Handler#stacks` enforces via `Repository.from_github_repo_name(repository_name)&.stacks` [1](#0-0) .

`PushHandler#process` respects this binding: it only ever mutates stacks reachable from `stacks`, which is derived from the webhook's own `repository_name` [2](#0-1) .

`StatusHandler#process` does not: [3](#0-2) 
It never calls `repository_name` or `stacks`; it queries `Commit` globally by `sha` alone and calls `commit.create_status_from_github!(params)` on whatever `Commit` rows match, regardless of which repository the inbound webhook's `repository.full_name` claims to be.

Root cause: git commit SHAs are content-addressed and are shared verbatim across forks and any repository that shares history (e.g., a public upstream repo tracked by Shipit and any fork of it). If repo A is tracked by a Shipit `Stack` and has a `Commit` row for SHA `abc123`, an attacker who forks A into repo B (a repo they own) and gets a `status` event for `abc123` delivered from B, will pass `verify_signature` (the signature is computed by GitHub against a real webhook secret registered for repo B's owner) yet the `StatusHandler` will still update the `Commit` row belonging to A's stack, because the lookup is `Commit.where(sha: params.sha)` with no repository filter.

Existing guards do not close this gap:
- `verify_signature`/`GitHubApp#verify_webhook_signature` only prove the webhook truly came from GitHub for the *claimed* repository/organization; they say nothing about which `Commit` rows the handler is allowed to touch [4](#0-3) .
- `ExplicitParameters` (`params do ... end` in `StatusHandler`) only validates the shape of `sha`/`state`/etc., not repository ownership [5](#0-4) .
- `Handler#repository_name`/`#stacks` exist precisely to provide this scoping, but `StatusHandler` simply never calls them [1](#0-0) .

### Impact Explanation
`Commit#create_status_from_github!` calls `add_status`, which can emit `Hook.emit(:deployable_status, ...)` and call `stack.schedule_merges`, and separately `Commit#schedule_continuous_delivery` can enqueue `ContinuousDeliveryJob` once a commit becomes `deployable?` [6](#0-5) [7](#0-6) . An attacker who forks a public repository already tracked as a Shipit stack can, from their own fork (a repository they own and fully control the webhook delivery for), send a validly-signed `status` event whose `sha` matches a shared ancestor commit that also exists in the victim stack. This causes a status to be written onto the victim's `Commit`, potentially flipping it to "success," unblocking `deployable?`, and triggering an unauthorized deploy via continuous delivery on the victim's stack — a cross-tenant mutation and potentially an unauthorized deploy, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy").

### Likelihood Explanation
Preconditions: the attacker must own/control a repository whose commit history overlaps (shares at least one identical SHA) with a victim repository already tracked by the target Shipit instance — trivially achievable by forking any public repo Shipit tracks. The attacker also needs the ability to have a `status` webhook delivered from that fork to the Shipit host, which only requires GitHub's own signing of the event for the attacker's own repository/organization (something achievable via self-service GitHub App/webhook installation on one's own repository) — no Shipit secrets, sessions, or tokens are required. This is repeatable against any stack whose tracked repository has public forks or shared history.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler#process` is scoped: restrict the `Commit` lookup to commits belonging to stacks under `Repository.from_github_repo_name(repository_name)`, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, instead of an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_scope_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerScopeTest < ActiveSupport::TestCase
        test "PushHandler scopes writes via repository_name/stacks" do
          Repository.expects(:from_github_repo_name).at_least_once
          payload = { 'ref' => 'refs/heads/master', 'after' => 'deadbeef',
                      'repository' => { 'full_name' => 'shopify/shipit-engine' } }
          PushHandler.call(payload)
        end

        test "StatusHandler never scopes writes via repository_name/stacks (unsafe)" do
          Repository.expects(:from_github_repo_name).never
          payload = { 'sha' => 'sharedsha1', 'state' => 'success',
                      'repository' => { 'full_name' => 'attacker/fork' } }
          StatusHandler.call(payload)
        end
      end
    end
  end
end
```
This demonstrates, at the code level, that `PushHandler` dereferences `Repository.from_github_repo_name` (via `stacks`) while `StatusHandler` never does, confirming the asymmetry that allows a `sha`-shared commit from an unrelated, attacker-controlled repository to update a victim stack's `Commit` status.
