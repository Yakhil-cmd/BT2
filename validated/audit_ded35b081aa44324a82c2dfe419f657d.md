### Title
Webhook signature verification is bound to the wrong organization, allowing cross-tenant forgery of GitHub events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-tenant Shipit deployment (multiple GitHub Apps/organizations configured under `secrets.github`), the webhook signature is verified against the secret of the organization named in the payload's `organization` field, but the event is subsequently *processed* against whatever repository is named in the payload's `repository.full_name` field. These two fields are never checked for consistency, so a valid signature from organization B's secret can be used to forge events for organization A's stacks.

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to use for HMAC verification via `repository_owner`: [1](#0-0) 

`repository_owner` prefers `repository.owner.login`, but explicitly falls back to the top-level `organization.login` when the repository object doesn't carry an owner: [2](#0-1) 

Because the attacker is POSTing an arbitrary crafted JSON body (not relaying an authentic GitHub delivery), they fully control whether `repository.owner.login` is present. By omitting it, they force `repository_owner` to resolve to the `organization.login` value of their choice — i.e., any organization configured in this Shipit instance whose secret they know (e.g., an org they administer, since GitHub App webhook secrets are typically set by the org's own app-installation admin, not by the Shipit operator, per the documented multi-org schema): [3](#0-2) [4](#0-3) 

`Shipit.github(organization: repository_owner)` then looks up that organization's independent `webhook_secret` and verifies the HMAC using it, which succeeds because the attacker signed the payload with the very secret they control.

Once the signature check passes, the request proceeds to `create`, which dispatches to handlers using the *same* raw, attacker-controlled `params`: [5](#0-4) 

But every handler resolves its target `Stack`/`Repository` from `payload.dig('repository', 'full_name')` — a field completely decoupled from the `organization` field used for authentication: [6](#0-5) 

For example, `PushHandler` acts on whatever stacks match `repository.full_name` and the given branch, regardless of which organization's secret was verified: [7](#0-6) 

This is structurally identical to the Perennial bug class described in the report: a value used to satisfy an authorization/limit check (`context.currentPosition`, here the *authenticating organization*) is not the value that ends up being acted upon (the *actual* position/repository being written), breaking the intended one-to-one binding between the authenticated principal and the resource affected.

### Impact Explanation
An attacker who controls (or is an app-admin of) any single organization configured in a multi-tenant Shipit instance can forge `push`, `status`, `check_suite`, or `pull_request` events for *any other* organization's repository also configured in that same instance, without ever knowing that other organization's webhook secret. This is a cross-tenant authentication bypass: the signature check authenticates one org, while the resulting side effects (syncing commits, updating statuses, refreshing check runs, driving continuous-deployment triggers via `stack.sync_github`) are applied to a completely unrelated org's stack. This matches the "authentication bypass" / "unauthorized deploy" criteria for Critical/High impact.

### Likelihood Explanation
Requires only an HTTP POST to the public `/webhooks` endpoint with a crafted JSON body and a valid HMAC signed with a secret the attacker legitimately knows (their own org's App webhook secret) — no privileged Shipit session, API token, or GitHub write access to the victim repository is needed. The only precondition is that the Shipit instance is configured for more than one GitHub organization, which is an explicitly documented and supported configuration.

### Recommendation
Bind signature verification and event processing to the same, non-attacker-controlled identity:
- Do not fall back `repository_owner` to `organization.login` when `repository` is present but incomplete; require `repository.owner.login` to be present for repository-scoped events.
- After verifying the signature, re-derive the resolved `Repository`/`Stack` owner from `payload.dig('repository', 'full_name')` and assert it matches the organization whose secret was used to verify the request before dispatching to handlers.

### Proof of Concept
1. Configure Shipit for two organizations, `OrgA` (victim, has stack `OrgA/app`) and `OrgB` (attacker-administered, has its own `webhook_secret_B`).
2. Attacker crafts a payload:
```json
{
  "organization": { "login": "OrgB" },
  "repository": { "full_name": "OrgA/app" },
  "ref": "refs/heads/master",
  "after": "<some_commit_sha_visible_via_github_api>"
}
```
Note: no `repository.owner.login` key.
3. Attacker signs the raw body with `webhook_secret_B` (known to them) and POSTs to `/webhooks` with `X-Github-Event: push` and `X-Hub-Signature: sha1=<hmac>`.
4. `repository_owner` resolves to `"OrgB"` → `Shipit.github(organization: "OrgB").verify_webhook_signature` succeeds.
5. `PushHandler` runs, resolves `Repository.from_github_repo_name("orga/app")`, and calls `stack.sync_github(expected_head_sha: ...)` on `OrgA`'s stack — an action the attacker was never authorized to trigger.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
