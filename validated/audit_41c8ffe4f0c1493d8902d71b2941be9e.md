### Title
Forged `membership` webhook accepted when an org's `webhook_secret` is unset, letting an attacker self-grant `Shipit.github_teams` membership - ([File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`GitHubApp#verify_webhook_signature` returns `true` whenever no `webhook_secret` is configured for the organization, so any request claiming to be from that organization passes signature verification unauthenticated. `MembershipHandler#process` then trusts the payload's `team.id` / `member.login` unconditionally and calls `Membership.create` (`Team#add_member`), so an attacker who merely controls the `organization.login` value in a POST to `/webhooks` can grant themselves membership in any `Team` row already present, including ones matching `Shipit.github_teams`.

### Finding Description
Broken binding: `Membership.exists?(team_id: T, user_id: attacker) == GitHub.reports_membership?(team_id: T, user: attacker)` should always hold for `T ∈ Shipit.github_teams`; the exploit makes the left side true while the right side is false.

- `WebhooksController#verify_signature` resolves the org from `params.dig('organization','login')` (attacker-controlled JSON body) and asks `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` unconditionally returns `true` when `@webhook_secret` is blank/nil - the exact precondition stated in the question ("genuinely configured but weak (nil) webhook_secret"). [3](#0-2) 
- `MembershipHandler#process` takes `params.team.id` and `params.member.login` straight from the (now-unverified) payload, finds/creates the `User`, and on `action: 'added'` calls `team.add_member(member)` -> `Membership.create` with no cross-check against GitHub's actual team roster. [4](#0-3) [5](#0-4) 
- `User#authorized?` grants access based purely on the local `Membership` table matching `Shipit.github_teams` IDs, with no live GitHub check. [6](#0-5) 
- `Authentication#force_github_authentication` gates every protected controller solely on `current_user.authorized?`. [7](#0-6) 

Existing guards fail here specifically because: `drop_unhandled_event`/`ExplicitParameters` only validate shape, not provenance; `verify_signature` is a no-op by design when `webhook_secret` is absent (the code comment/behavior at `lib/shipit/github_app.rb:76-77` treats "no secret configured" as "trust everything"); and `MembershipHandler` has no secondary authorization check (e.g., confirming via the GitHub API that the member is actually on the team) before writing to `Membership`.

Exploit flow: attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and JSON body `{"action":"added","team":{"id":<id of an existing Shipit::Team already in Shipit.github_teams>,"name":...,"slug":...,"url":...},"organization":{"login":"attacker-owned-org-with-nil-webhook_secret"},"member":{"login":"attacker"}}`. Because that org's `webhook_secret` is nil, `verify_signature` passes trivially regardless of the (even absent) `X-Hub-Signature` header. `MembershipHandler` creates/finds the attacker `User` and inserts a `Membership` row for the targeted team. The attacker then only needs a Shipit session bound to that `User` record (e.g., via a real, unprivileged OAuth login flow that creates/matches the same `login`) to have `current_user.authorized?` evaluate true.

### Impact Explanation
This is an authentication-bypass / privilege-escalation vector: the attacker obtains membership in a `Shipit.github_teams`-listed team without GitHub ever having added them, which flips `User#authorized?` to `true` and unlocks every `ShipitController` protected by `force_github_authentication` - stack views, deploy/rollback triggers, task streams, etc. The blast radius is global to the Shipit instance (not scoped to one repository) because `Shipit.github_teams` and `authorized?` are instance-wide checks, not per-organization. This matches the "escalation into `Shipit.github_teams` authorization" / "authentication bypass" categories. It is repeatable: the attacker can forge additional `membership` events at will for any org in `Shipit.github` config that lacks a `webhook_secret`, and also `action: 'removed'` to strip other users' memberships.

### Likelihood Explanation
The precondition is a genuine but plausible operator misconfiguration: `webhook_secret` left blank for one of potentially several configured organizations (multi-org config is explicitly supported and documented) — the docs and default config templates literally show `webhook_secret:` as an optional/blank field. No Shipit or GitHub secret is required by the attacker; they only need to know the `organization.login` string used in Shipit's config and the numeric `id` of a `Team` row already present with a handle in `Shipit.github_teams` (discoverable via team slugs/URLs, or simply guessable ID enumeration since `Team.find_or_create_by!(github_id: ...)` is create-on-demand). Cost is a single unauthenticated HTTP POST; the finding is fully repeatable and requires no privileged role, matching the attacker profile constraints.

### Recommendation
Do not treat "no `webhook_secret` configured" as "signature verified." `GitHubApp#verify_webhook_signature` should fail-closed (return `false`/raise, or refuse to process) when `webhook_secret` is blank, and Shipit should require/enforce a non-empty `webhook_secret` per configured organization at boot/config-validation time. Additionally, `MembershipHandler` should not be the sole source of truth for authorization-relevant `Membership` writes; consider reconciling membership changes against the GitHub API (as `Team#refresh_members!` already does) rather than trusting webhook payload content alone.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
```ruby
test "forged membership webhook grants unauthorized team access when webhook_secret is nil" do
  # Arrange: org config has nil webhook_secret (mirrors test/dummy secrets.yml default)
  Shipit.stubs(:github_teams).returns([team = shipit_teams(:shipit)]) # team already in Shipit.github_teams
  refute Shipit.github(organization: 'shopify').send(:webhook_secret) # left-hand side: no secret configured

  # Before: binding holds - no membership row exists for the attacker
  attacker = nil
  assert_no_difference -> { Membership.count } do
    attacker = User.find_or_create_by_login!('attacker')
  end
  refute Membership.exists?(team_id: team.id, user_id: attacker.id)

  # Act: forge membership webhook with no valid X-Hub-Signature
  @request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    team: { id: team.github_id, name: team.name, slug: team.slug, url: team.api_url },
    organization: { login: 'shopify' },
    member: { login: 'attacker' }
  }.to_json
  post :create, body: body, as: :json
  assert_response :ok

  # Assert: binding is now broken - Membership exists though GitHub never reported it
  assert Membership.exists?(team_id: team.id, user_id: attacker.id)

  # Downstream: authorized? flips true, protected controller returns 200 not 403
  session[:user_id] = attacker.id
  get :index, controller: 'shipit/stacks' # any force_github_authentication-protected action
  assert_response :ok # instead of :forbidden
end
```
This directly demonstrates: (1) `webhook_secret` is nil for the org (left side of guard), (2) the forged POST is accepted (`verify_webhook_signature` returns true), (3) a `Membership` row is created for a team GitHub never actually granted, and (4) `current_user.authorized?` becomes true, unlocking a protected controller action.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
