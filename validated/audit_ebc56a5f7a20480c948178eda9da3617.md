### Title
Cross-organization webhook forgery: signature verified against the payload's `repository.owner.login` but commit-status writes are looked up globally by `sha`, letting an attacker with one org's webhook secret inject fake CI statuses on any other organization's tracked commits - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify the HMAC signature against using `repository.owner.login` (or `organization.login`) taken from the attacker-supplied JSON body itself. [1](#0-0)  Once the signature check passes, the full raw payload is dispatched to handlers such as `StatusHandler`, which does not re-validate that the `repository` in the payload corresponds to the organization whose secret authenticated the request. Worse, `StatusHandler#process` looks up target commits **globally by `sha`**, with no scoping to any repository or organization at all. [2](#0-1)  This breaks the equality: `organization authenticated by signature == organization/repository whose data gets written`.

### Finding Description
Shipit supports hosting multiple GitHub organizations in one instance, each with its own GitHub App and its own `webhook_secret`, as documented in `docs/setup.md` ("Using Multiple Github Applications"). [3](#0-2)  `Shipit.github(organization:)` is looked up per-org, and `verify_webhook_signature` simply HMACs the raw body with that org's secret. [4](#0-3) 

The controller determines *which* org's secret to use purely from a field inside the same untrusted, attacker-controlled JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

Since the attacker fully controls the raw POST body and only needs it to be internally consistent with *a* secret they legitimately know (their own organization's GitHub App webhook secret, configured when they set up their own app installation), they can compute a valid `X-Hub-Signature` for a payload where:
- `repository.owner.login` = their own organization ("OrgA") — used only to pick which secret is checked;
- every other field of the payload (`sha`, `state`, `context`, `description`, `target_url`) is set to whatever they want.

The handler dispatch (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) then hands the entire attacker-controlled payload to `StatusHandler`, whose `process` method does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This lookup is a global `Commit.where(sha: ...)` query with no join/filter on `Repository`/`Stack`, and the base `Handler` class's `repository_name`/`stacks` helpers (which do scope by `payload.dig('repository','full_name')`) are not used by `StatusHandler` at all. [6](#0-5)  So the org whose secret validated the request (OrgA) has no bearing on which commit records actually get a forged status written to them — any commit sha tracked anywhere in the Shipit installation, belonging to any other organization/repository, is a valid target as long as the attacker happens to know (or can enumerate/guess) its 40-character sha, which is often publicly visible (e.g., via Shipit's own commit permalinks, GitHub, or CI logs) even for repositories the attacker has no access to.

Other handlers exhibit the same missing binding to varying degrees. `PushHandler` and `CheckSuiteHandler` do at least scope through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, [7](#0-6) [8](#0-7)  but that `full_name` field itself is never cross-checked against `repository.owner.login` used for signature verification — so an attacker signing with OrgA's secret can still set `repository.full_name` to `"OrgB/victim-repo"` and force an out-of-band `GithubSyncJob` or `schedule_refresh_check_runs!` on OrgB's stacks. `StatusHandler` is the most severe because it doesn't even require guessing the target repository's name — only a commit sha.

### Impact Explanation
An attacker who legitimately administers just one GitHub organization/App configured on a shared multi-tenant Shipit instance (and therefore knows their own app's `webhook_secret`, a credential the rules treat as attacker-controllable in this scenario since it is *their own*, not a stolen secret) can:
- Forge arbitrary GitHub commit-status webhooks (`state`, `context`, `description`, `target_url`) for any commit sha tracked by any stack across the entire Shipit installation, regardless of organization, via `Commit#create_status_from_github!`.
- Because Shipit's deploy pipeline can gate deploys on required/blocking commit statuses (per the "blocking statuses" feature noted in `CHANGELOG.md`), injecting a fake `"success"` status for a victim organization's commit can help unblock or influence a deploy decision that the attacker has no authorization over — an unauthorized-deploy-adjacent write across organizational trust boundaries.
- Similarly, forged `push`/`check_suite` events can trigger `GithubSyncJob` or `schedule_refresh_check_runs!` against a victim org's stacks that the attacker has no business relationship with, causing state changes (accessibility flags, check-run refresh, unwanted GitHub API calls made by the *victim's* GitHub App credentials) driven entirely by the attacker.

This satisfies the "organization authenticated versus the repository/commit that is written" binding break called out in the rules, and lands in the High impact band (escalation causing writes into another repository/stack's state without authorization) — bordering Critical if blocking-status gating is configured to actually influence unattended deploys.

### Likelihood Explanation
Likelihood is Medium-High **in the specific deployment topology this bug requires**: a single Shipit instance configured with multiple GitHub organizations/Apps (explicitly documented and supported per `docs/setup.md`). Any org admin in that shared instance is, by design, an "unprivileged attacker" with respect to every *other* org's data, yet can compute a valid signature using their own secret and freely control every other field of the JSON body, including the commit `sha` to target. No Shipit session, ApiClient token, or stolen secret is required — only the attacker's own legitimately-issued webhook secret and the raw `/webhooks` HTTP endpoint, which is unauthenticated by design (it's meant to be called by GitHub).

### Recommendation
- In `WebhooksController#verify_signature`, after determining the org to use for HMAC validation, re-validate that every repository/organization reference elsewhere in the same payload belongs to that same organization (e.g., assert `repository.full_name.split('/').first.casecmp(repository_owner) == 0`) before dispatching to handlers, rejecting mismatched payloads.
- In `StatusHandler#process`, scope the `Commit` lookup by the repository asserted in the payload (joining through `Stack`/`Repository`, as other handlers do via `Handler#stacks`), instead of a bare global `Commit.where(sha:)`.
- More generally, have `Handlers::Handler` centrally verify `payload.dig('repository','full_name')`'s owner matches the org used to authenticate the signature, so individual handlers can't accidentally bypass the binding.

### Proof of Concept
Given a Shipit instance configured with two orgs, `OrgA` (attacker's own app, secret known to attacker) and `OrgB` (victim, unrelated to attacker), and a victim commit with `sha = "deadbeefcafe...".`

1. Attacker crafts:
```json
{
  "sha": "deadbeefcafe...",   // an OrgB commit sha the attacker knows/guesses
  "state": "success",
  "context": "ci/required-check",
  "description": "forged by attacker",
  "repository": { "owner": { "login": "OrgA" } }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` using their own known secret for `OrgA`.
3. POST to `/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature matches — request is accepted. [9](#0-8) 
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeefcafe...")` — finds the OrgB commit — and calls `create_status_from_github!(params)`, writing the attacker-forged `"success"` status onto a commit that belongs to an organization/repository the attacker has no authorization over. [2](#0-1) 

I was not able to fully verify (due to index limits) the exact downstream logic of the "blocking statuses" deploy-gating feature referenced in `CHANGELOG.md` — i.e., precisely how a forged status of this kind influences deploy eligibility in the current codebase — so the specific severity of the deploy-gating consequence should be confirmed with a live/full-repo review before finalizing remediation priority.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
