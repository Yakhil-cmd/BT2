### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming `status` webhook purely by matching the bare `sha` string across the entire `commits` table, with no scoping to the repository/stack that authenticated the webhook. Because `Status#state` directly drives `Commit#deployable?`, `Commit#blocked?`, and `schedule_continuous_delivery`, a `status` payload legitimately delivered for one repository can flip `codecov/project` (or any required context) to `failure` on a *different* stack whose commits table happens to contain that SHA string, forcing a block or triggering `ContinuousDeliveryJob` divergence on a victim stack that never authenticated that event.

### Finding Description
The broken binding is: **"a status event authenticated for repository R may only mutate commits belonging to stacks whose `github_repo_name == R`"** — but the code enforces no such equality.

`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This is a plain string match on `Commit#sha` with no `stack_id`/`repository` predicate. `Commit.sha` values are opaque strings stored from `Commit.from_github` [2](#0-1)  and are never re-validated against the reporting repository at status-ingestion time — `create_status_from_github!` just calls `add_status`/`statuses.replicate_from_github!(stack_id, github_status)` on whatever `commit` records were matched [3](#0-2) .

Upstream, `WebhooksController#verify_signature` only authenticates at the **organization** level, not per-repository:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
``` [4](#0-3) 
and `GitHubApp#verify_webhook_signature` checks the HMAC against a single `@webhook_secret` configured per organization entry, with no per-repository binding [5](#0-4) . So a genuine, validly-signed `status` webhook from *any* repository under an organization that shares this webhook secret (a very common GitHub App/org-wide-webhook setup) authenticates the request, but nothing thereafter checks that `params['repository']['full_name']` matches the stack being mutated by `StatusHandler`. The handler's `params` schema doesn't even require or use the `repository` field at all [6](#0-5) .

Exploit flow:
1. Attacker has push/webhook-triggering ability on any repository under the same GitHub organization/App installation as the victim stack (e.g., their own low-privilege repo whose commits legitimately fire `status` events through the shared org webhook).
2. Attacker learns the victim's tracked commit SHA (trivially public — visible on the stack's UI/GitHub commit history).
3. Attacker triggers (or crafts, if they control CI on their own repo) a `status` event with `sha` set to the victim's SHA, `context: codecov/project`, `state: failure`.
4. This event is genuinely signed by GitHub using the shared org secret, so `verify_signature` passes.
5. `StatusHandler#process` matches `Commit.where(sha: <victim sha>)`, which returns the victim's `Commit` row belonging to the victim's stack — not the attacker's own stack — and calls `create_status_from_github!` on it.
6. `add_status` recomputes `previous_status`/`new_status`; if the transition drops the commit below the deployable simple_state, `stack.schedule_merges` is skipped and `deployable_status`/`commit_status` hooks fire for the victim stack [7](#0-6) .
7. If the victim stack has `continuous_deployment` enabled, `Commit#schedule_continuous_delivery` (fired via `Status#schedule_continuous_delivery` after_commit callback [8](#0-7) ) re-evaluates `deployable?`/`stack.deployable?` and enqueues `ContinuousDeliveryJob` accordingly [9](#0-8)  — meaning the forged `failure` can suppress an otherwise-ready auto-deploy, or conversely a forged `success` from the same mechanism can make an unreviewed commit appear deployable and get auto-shipped.

None of the listed guards prevent this: `verify_signature` authenticates the org, not the repo; `drop_unhandled_event`/`ExplicitParameters` only validate shape (`sha`, `state`, `context` are strings) not repository ownership; there is no `Repository`/stack scoping anywhere in `StatusHandler`.

### Impact Explanation
A webhook delivery authenticated for one repository can write a `Status` record — and trigger deploy-relevant side effects (`schedule_merges`, `ContinuousDeliveryJob`, `deployable_status`/`commit_status` hooks) — against a commit belonging to an entirely different stack/repository that never authorized it. This is a "payload for one repository mutating another's stack/commit" class finding. On a victim stack with `continuous_deployment` enabled, this can suppress a legitimate deploy (forged `failure`) or, in the reverse direction, make an unreviewed/broken commit appear deployable (forged `success`), directly affecting deploy/rollback outcomes. This is repeatable against any repository sharing an organization-level webhook secret with the victim, for any SHA the attacker can learn (which is always public).

### Likelihood Explanation
Preconditions: attacker needs a repository whose `status` webhooks are validly signed with the same organization-level `webhook_secret` Shipit uses for `Shipit.github(organization: repository_owner)` — a realistic and common configuration for org-wide GitHub App installations, since Shipit's signature check is organization-scoped, not repository-scoped. Beyond that, the attacker only needs the target's commit SHA, which is public. No Shipit session, API token, or GitHub secret theft is required beyond what a legitimate but unprivileged org member/collaborator already has. This is a low-cost, fully repeatable attack against any stack sharing the org's webhook configuration.

### Recommendation
Scope `StatusHandler#process` (and the equivalent check-suite/check-run handlers) to the repository that authenticated the webhook: require and validate `params.repository.full_name` (or `repository.owner.login` + `repository.name`) against `commit.stack.github_repo_name` before calling `create_status_from_github!`, e.g. `Commit.where(sha: params.sha).select { |c| c.github_repo_name == params.repository.full_name }`. Additionally, consider moving webhook signature verification to be repository-aware where the underlying GitHub App/webhook configuration supports per-repository secrets.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status for repo A's sha does not mutate a commit belonging to repo B's stack" do
  victim_stack = shipit_stacks(:shipit) # e.g. github_repo_name == "shopify/shipit-engine"
  victim_stack.update!(continuous_deployment: true)
  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...)
  victim_commit.statuses.create!(state: "success", context: "codecov/project", stack: victim_stack)

  # attacker's payload claims to originate from a different repository but reuses victim's sha
  forged_params = ExplicitParameters::Params.new(
    sha: victim_commit.sha,
    state: "failure",
    context: "codecov/project",
    repository: { full_name: "attacker/unrelated-repo" }
  )

  assert_no_difference -> { victim_commit.reload.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(forged_params).process
  end

  assert_equal "success", victim_commit.reload.status.state
  refute_enqueued_with(job: Shipit::ContinuousDeliveryJob, args: [victim_stack])
end
```
Before the fix, `Commit.where(sha: params.sha)` matches `victim_commit` regardless of `repository.full_name`, the assertion fails (a `Status(state: failure)` is created on `victim_stack`), demonstrating the cross-repository write.
