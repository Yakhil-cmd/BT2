## Title
Unauthenticated `coin_registry::new_currency<T>` allows frontrunning/squatting the derived `Currency<T>` registry slot for any type — ([File: crates/sui-framework/packages/sui-framework/sources/registries/coin_registry.move])

## Summary
`sui::coin_registry::new_currency<T>` derives the shared `Currency<T>` object at a deterministic address (via `derived_object::claim`) keyed *only* on the type `T`, and can be invoked by **any caller** for **any** type `T` that merely has the `key` ability — there is no requirement that the caller be the publisher of `T`'s defining module, hold a `Publisher`, or present an OTW. This is the same root cause as the reported `Aquifer.boreWell` bug: a publicly-computable, deterministic identity (there: CREATE2 `salt`; here: `CurrencyKey<T>()`) can be claimed by an unrelated third party before the legitimate owner acts, letting an attacker squat/poison the slot and permanently block ("DoS") the legitimate registration.

## Finding Description
`derived_object::claim<K>(parent, key)` computes a deterministic address from `hash(parent, key)` and aborts with `EObjectAlreadyExists` if that (parent, key) pair was already claimed: [1](#0-0) 

`coin_registry::new_currency<T>` uses this primitive with `CurrencyKey<T>()` as the key — a key derived solely from the type parameter `T`, which is public information and requires no proof of ownership: [2](#0-1) 

Critically, the type bound is only `T: /* internal */ key` — the "internal" comment signals an *intended* restriction that isn't actually enforced by the Move type system: any type with the `key` ability, defined in any module, published by anyone, can be substituted for `T`. Compare this to `display_registry::new<T>`, which enforces the analogous privilege correctly by requiring an `internal::Permit<T>` capability that only the module defining `T` can obtain: [3](#0-2) 

`coin_registry::new_currency<T>` has no equivalent `Permit<T>`/`Publisher` check — it only guards against double-registration via `assert!(!registry.exists<T>(), ECurrencyAlreadyExists)`: [4](#0-3) 

This mirrors the `boreWell` pattern exactly: the "salt" (here, `T`) is public and unauthenticated, and whoever calls `new_currency<T>` (or `finalize_registration<T>`, which also calls `derived_object::claim(&mut registry.id, CurrencyKey<T>())`) first wins the deterministic slot: [5](#0-4) 

## Impact Explanation
An attacker who observes a pending publish/registration transaction for a new coin type `T` (or simply predicts/targets a well-known coin type before its team registers it) can submit `coin_registry::new_currency<T>(...)` first, since the call requires nothing more than naming the type and does not require holding that coin's real `TreasuryCap`, `Publisher`, or any OTW for `T`:
- **Permanent DoS / fund-adjacent harm**: The legitimate team's subsequent call to `new_currency<T>` or `finalize_registration<T>` reverts with `ECurrencyAlreadyExists`, permanently preventing them from ever registering canonical on-chain `Currency<T>` metadata (name, symbol, decimals, icon, supply/regulatory state) at the expected derived address — a `Currency<T>` object address is a function only of `(CoinRegistry UID, T)`, so there is no alternate address to retry at.
- **Harmful smart-contract behavior / metadata poisoning**: The attacker's squatted `Currency<T>` carries attacker-chosen `decimals`, `symbol`, `name`, `description`, `icon_url`, and an attacker-controlled bogus `TreasuryCap<T>`/`treasury_cap_id`. Any wallet, explorer, or dApp that trusts `sui::coin_registry::Currency<T>` as the canonical metadata source for `T` (this is the framework's stated purpose — "a centralized way to store and manage metadata for all currencies in the Sui ecosystem") will display and act on forged data for a legitimate, un-related project's coin type.

This satisfies the "permanent fund lock" / "harmful smart-contract behavior" High-impact bucket from an unprivileged attacker model, matching the bounty-relevant analog of the `boreWell` DoS/squatting finding.

## Likelihood Explanation
High. No privileged role, timing race beyond ordinary mempool-frontrunning, or special capability is required — an unprivileged caller only needs to reference type `T` (public information, especially once a package is published, or even predictable from common naming conventions before publish) and pay gas. The `assert!(!registry.exists<T>(), ...)` check that should prevent re-registration is exactly the mechanism the attacker exploits to lock out the legitimate owner permanently.

## Recommendation
Gate `coin_registry::new_currency<T>` (and `finalize_registration<T>`) the same way `display_registry::new<T>` is gated: require proof of ownership of `T`, e.g. an OTW (`T: drop` one-time-witness, as already done in `new_currency_with_otw`) or an `internal::Permit<T>` / `Publisher` capability, before permitting the derived-object claim for `CurrencyKey<T>()`. The unrestricted `T: key`-only path in `new_currency` should be removed or restricted so that only the module that defines `T` (or a capability holder tied to `T`) can claim its `Currency<T>` slot.

## Proof of Concept
1. Team A prepares to publish coin module `victim::COIN` and plans to call `sui::coin_registry::new_currency<victim::COIN>(...)` right after their `TreasuryCap<victim::COIN>` is minted in `init`.
2. Attacker monitors the mempool/publish transaction (or simply predicts the well-known module path once the package is published), and submits (in the same or an earlier checkpoint) a call:
   `sui::coin_registry::new_currency<victim::COIN>(registry, decimals=0, symbol="SCAM", name="Scam", description="", icon_url="http://evil", ctx)`
   This only requires that `victim::COIN` already exists as a `key`-able type (true once the package publishes) and does not require holding `victim::COIN`'s real `TreasuryCap`.
3. `derived_object::claim(&mut registry.id, CurrencyKey<victim::COIN>())` succeeds for the attacker, occupying the unique deterministic address for `Currency<victim::COIN>`.
4. Team A's subsequent `new_currency<victim::COIN>(...)` call reverts with `ECurrencyAlreadyExists` — permanently, since the registry slot for `(registry, victim::COIN)` can never be reclaimed.
5. Wallets/explorers reading `sui::coin_registry::Currency<victim::COIN>` display the attacker's forged metadata as canonical.

Note: I was not able to fully verify in this session whether `coin::new_treasury_cap` (called internally by `new_currency`) imposes any additional restriction on `T` beyond `key` ability (its source in `coin.move` was not read before the session ended); this could affect whether the attacker's own `TreasuryCap<T>` is meaningfully mintable, but it does not change the core finding — the DoS/permanent-lock on legitimate registration and metadata-squatting via the unauthenticated `CurrencyKey<T>` derived-object claim stands independent of that detail.

public fun new_currency<T: /* internal */ key>(
    registry: &mut CoinRegistry,
    decimals: u8,
    symbol: String,
    name: String,
    description: String,
    icon_url: String,
    ctx: &mut TxContext,
): (CurrencyInitializer<T>, TreasuryCap<T>) {
    assert!(!registry.exists<T>(), ECurrencyAlreadyExists);
    assert!(is_ascii_printable!(&symbol), EInvalidSymbol);

    let treasury_cap = coin::new_treasury_cap(ctx);
    let currency = Currency<T> {
        id: derived_object::claim(&mut registry.id, CurrencyKey<T>()),
        decimals,
        name,
        symbol,
        description,
        icon_url,
        supply: option::some(SupplyState::Unknown),
        regulated: RegulatedState::Unregulated,
        treasury_cap_id: option::some(object::id(&treasury_cap)),
        metadata_cap_id: MetadataCapState::Unclaimed,
        extra_fields: vec_map::empty(),
    };

    (CurrencyInitializer { currency, is_otw: false, extra_fields: bag::new(ctx) }, treasury_cap)
}
