### Title
API client stack-scope escape via `Api::CCMenuController#stack` bypassing token's stack authorization - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` re-implements the `stack` lookup instead of using the scoped helper defined in `Shipit::Api::BaseController`, allowing an `ApiClient` token that is authorized for only one stack to read the CI/deploy status of *any* stack in the installation.

### Finding Description
`Shipit::Api::BaseController` enforces per-token stack scoping through two cooperating methods: `stacks`, which restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the token is bound to a specific stack, and `stack`, which resolves the requested record from that restricted relation (`stacks.from_param!(params[:stack_id])`). [1](#0-0) 

`Api::CCMenuController` overrides `stack` and bypasses this scoping entirely, resolving the record straight from `Stack.from_param!(params[:stack_id])` — the global, unscoped table: [2](#0-1) 

Authorization for this endpoint is enforced only via `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`. That method checks only whether the string `"read:stack"` is present in the client's `permissions` array — it never compares the token's bound `stack_id` against the stack being requested: [3](#0-2) 

This reproduces the report's bug class: the credential (`ApiClient` token) authorizes an operation on stack `S` (the one recorded in `api_clients.stack_id`), but the code path that services the request acts on whatever stack `T` is supplied in `params[:stack_id]`, without checking `S == T`. Concretely, the binding that should hold is:

`current_api_client.stack_id == stack.id`

but `Api::CCMenuController#stack` never evaluates this equality — it is checked (correctly) in `BaseController#stack`/`#stacks`, but that logic is dead code for this specific controller because of the override.

Every legitimate consumer of stack-scoped tokens is created via `CCMenuUrlController#client`, which mints an `ApiClient` with `permissions: %w[read:stack]` and a `stack:` binding intended to be limited to that single stack, then embeds its `authentication_token` in a CCTray URL: [4](#0-3) 

Because `Api::CCMenuController#authenticate_api_client` reads the token from a URL query parameter instead of Basic Auth headers, and because such tokens are embedded in copy/pasteable CCTray URLs shared with third-party CI dashboard tools, this scoping bypass is directly reachable by anyone who obtains one such URL (e.g. an unprivileged team member who was only meant to see one stack's build status). [5](#0-4) 

### Impact Explanation
An attacker holding a single-stack-scoped `read:stack` CCMenu token can enumerate `params[:stack_id]` for arbitrary stacks and retrieve their build/deploy status (`merge_status`, activity, last build time/label, `stack_url`) rendered by `app/views/shipit/ccmenu/project.xml.builder`, even though the token was only meant to authorize reading one specific stack. This is an unauthorized read of stack state/deploy output across a trust boundary that the application explicitly modeled (`ApiClient#stack_id`) and enforces everywhere else in the API namespace, matching the in-scope "High" category of escalation into stack-scoped authorization / unauthenticated (here: out-of-scope) read of stack state.

### Likelihood Explanation
Exploitation requires only possession of one legitimately-issued, stack-scoped CCMenu token/URL (no admin privileges, no signing secret, no session) — such URLs are designed to be shared externally with CI dashboard tools, making leakage plausible, and the request itself is a single unauthenticated GET with a different `stack_id` query/path parameter.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`), so that a stack-bound token can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. As a legitimate user, visit any stack's settings page to trigger `CCMenuUrlController#fetch`, which creates (or reuses) an `ApiClient` scoped to stack `A` with `permissions: ['read:stack']`, and returns a URL such as `https://shipit.example.com/api/*A/ccmenu.xml?token=<TOKEN>`. [6](#0-5) 
2. Take `<TOKEN>` and issue `GET /api/*B/ccmenu.xml?token=<TOKEN>` for a different, unrelated stack `B` that this client is not scoped to.
3. `authenticate_api_client` in `CCMenuController` accepts the token (it is valid, just not for `B`); `require_permission :read, :stack` passes because the token has `read:stack` in its permission list; `stack` resolves `B` directly via `Stack.from_param!`, bypassing the `stacks` scoping used everywhere else, and returns stack `B`'s CI status in the XML response — data the token was never authorized to see. [7](#0-6)
