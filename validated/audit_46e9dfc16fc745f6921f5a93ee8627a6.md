### Title
Unverified External Fetch via Attacker-Controlled Submodule URLs - (File: main.go)

### Summary
`git-sync` synchronizes an attacker-influenced remote repository and, when submodules are enabled, blindly runs `git submodule update --init` against whatever submodule URLs are declared in that repository's `.gitmodules` file. This is analogous to the UnizenIO "unverified external call" bug class: the process performs an outbound call to a destination that is fully attacker-controlled and never validated against an allow-list, host, or protocol restriction before the call is made.

### Finding Description
In `configureWorktree`, after checking out an attacker-influenced commit, `git-sync` unconditionally runs submodule initialization/update when `git.submodules != submodulesOff`: [1](#0-0) 

The submodule URLs come from `.gitmodules`, which is part of the synced (attacker-writable, if the attacker controls the upstream repo, a branch, or a permitted ref/PR merge) tree content — `git-sync` performs no verification of the target host/protocol before invoking `git submodule update --init [--recursive]`. This causes the process to make an unverified outbound network (or `file://`) request to any location an attacker places in `.gitmodules`.

Compounding this, `git-sync` configures a global `credential.helper cache --timeout 3600` for the whole git invocation environment: [2](#0-1) 

Because `credential.helper` is set globally (not scoped to a single remote/host), and the `origin` remote credentials are stored via `git credential approve`-style flows for the main `--repo`, any outbound git operation — including a submodule fetch to an attacker-supplied URL that matches the same protocol/host pattern the credential helper will offer — can result in credential/token disclosure to that attacker-controlled endpoint. Even without a credential match, the outbound request itself is an SSRF-style "unverified external call" from within the git-sync pod's network context, reachable purely by pushing/merging a `.gitmodules` change to the synced repo.

### Impact Explanation
- If the attacker can control or influence the `.gitmodules` content in the repository being synced (e.g., a pull-request branch that gets synced, or any writer to the tracked ref), they can force `git-sync` to issue outbound requests to arbitrary attacker-chosen hosts.
- If the target host coincidentally matches the credential-helper's cached scope (same host as `--repo`, e.g. via subpath tricks) or the attacker uses a crafted URL to make git present cached credentials, this can lead to credential/token disclosure — mapping to the "credential or token disclosure" impact class in the validation rules.
- At minimum, this is an internal network probing/SSRF primitive reachable from attacker-pushed repository content, satisfying the "reachable from untrusted repo content ... submodules" analog class.

### Likelihood Explanation
Requires `--submodules` to not be set to `off` (i.e., default or explicit `shallow`/`recursive`), which is the common non-default-hardened deployment mode of git-sync. No privileged operator action is needed beyond normal `git-sync` operation with submodules enabled and an attacker having write/PR access to a ref that git-sync tracks.

### Recommendation
- Restrict submodule fetch protocols and hosts (e.g., set `protocol.file.allow=user`, and consider `submodule.<name>.update=none` or an explicit allow-list of trusted submodule URLs) before running `git submodule update --init`.
- Scope `credential.helper` and stored credentials strictly to the configured `--repo` URL rather than a global cache with a broad timeout.
- Consider disabling recursive/automatic submodule fetch by default, requiring an explicit opt-in flag with documented risk.

### Proof of Concept
1. Attacker pushes or merges a branch/ref that `git-sync` is configured to track (`--ref`) containing a `.gitmodules` file with a submodule URL pointing to an attacker-controlled or internal-network host (e.g., `http://169.254.169.254/...` or an attacker HTTP listener).
2. `git-sync`'s next sync cycle calls `configureWorktree`, which runs `git submodule update --init` (and `--recursive` if configured) using that URL with no verification, per the code in `main.go:1733-1747`.
3. The attacker's server logs the outbound request (headers/credentials, if credential-helper offers them) or the internal service is probed — demonstrating the unverified-external-call analog to the UnizenIO exploit pattern. [1](#0-0) [2](#0-1)
