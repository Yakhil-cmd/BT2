### Title
Unauthenticated `membership` webhook forges GitHub team membership and escalates a user into `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`, `lib/shipit/github_app.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub organization whose webhook secret should verify the request purely from an attacker-supplied field of the same unverified JSON body, and `GitHubApp#verify_webhook_signature` treats a blank/unset `webhook_secret` as automatically verified. When an org is configured (as shown in this engine's own shipped configs) without a `webhook_secret`, any unauthenticated caller can POST a forged `membership` event that `MembershipHandler` will apply verbatim — adding an arbitrary GitHub-verified login to an arbitrary existing `Team`, which directly grants `Shipit.github_teams` authorization to that user's account.

### Finding Description
`WebhooksController` derives the organization used for signature verification straight from the request body: [1](#0-0) [2](#0-1) 

The verification itself is a no-op whenever the resolved `GitHubApp` has no configured `webhook_secret`: [3](#0-2) 

`webhook_secret` is explicitly documented and shipped as an optional field (this engine's own test/dev fixtures configure it as `null`): [4](#0-3) [5](#0-4) 

Once the (no-op) verification "passes", `create` dispatches the raw, attacker-controlled JSON to registered handlers: [6](#0-5) [7](#0-6) 

`MembershipHandler` then trusts the payload's `team`, `organization`, `member`, and `action` fields directly — it looks up/creates the `Team` by the payload's `team.id`, resolves the `User` by the payload's `member.login` (validated only by fetching that login from the GitHub API, not by checking real team membership), and immediately mutates team membership based on the payload's `action` value, with **no call to GitHub to confirm the claimed membership change actually occurred**: [8](#0-7) 

`Team#add_member` performs no additional authorization check: [9](#0-8) 

Authorization into the app is gated solely on membership in `Shipit.github_teams`: [10](#0-9) [11](#0-10) 

The broken binding, expressed as an equality that should hold but doesn't:
`organization/team membership claimed in the webhook payload` **should equal** `organization/team membership actually verified via a cryptographically-bound signature or a live GitHub API check` — but the code lets the same untrusted payload supply both the "authenticating" organization (`repository_owner`) and the "written" team membership state, with the HMAC check reduced to a tautology (`return true unless webhook_secret`) for any org lacking a configured secret. This is the direct structural analog of the Tapioca `Balancer._sendToken` bug: a privileged action (in Tapioca, choosing the Stargate poolId; here, granting `Shipit.github_teams` membership) is driven by a field that is never actually validated against the trusted source of truth (in Tapioca, the admin-configured `OFTData`; here, GitHub's actual team membership).

### Impact Explanation
This is a High-severity finding under "escalation into `Shipit.github_teams` authorization": an attacker who knows only (a) the target org's login (public information) and (b) an existing `Team#github_id` (also generally discoverable/guessable or brute-forceable, since `Team.find_or_create_by!` matches on `github_id` alone) can add their own real GitHub login to that `Team` via a forged, completely unauthenticated `membership` webhook, then log into Shipit via normal GitHub OAuth and pass the `authorized?` check, gaining full access to stacks, deploys, and rollbacks that were meant to be restricted to `Shipit.github_teams`.

### Likelihood Explanation
Likelihood is directly tied to whether `webhook_secret` is configured for the target GitHub App entry, which this engine's own documentation and shipped configuration files treat as optional, not mandatory. No session, `ApiClient` token, `webhook_secret`, or privileged account is required by the attacker — the entire attack surface is a single unauthenticated HTTP POST to the mounted `/webhooks` endpoint with a crafted `X-Github-Event: membership` header and JSON body.

### Recommendation
- Make `webhook_secret` mandatory for every configured `GitHubApp` (fail closed instead of `return true unless webhook_secret`).
- Bind the `MembershipHandler`'s target `Team`/`organization` to the same organization identity that was cryptographically verified during `verify_signature`, rather than trusting the payload's own `organization.login` / `team.id`.
- Do not mutate authorization-relevant state (`Team#add_member` / `team.members.delete`) purely from webhook payload contents; confirm the membership change against a live GitHub API call (similar to `Team#refresh_members!`) before applying it.

### Proof of Concept
1. Deploy Shipit with a `GitHubApp` entry for organization `Acme` that has `webhook_secret: null` (a supported, documented configuration, matching this engine's own `test/dummy/config/secrets.test.json`).
2. Discover or brute-force an existing `Team#github_id` belonging to a team listed in `Shipit.github_teams` (e.g., by requesting team info through the public GitHub API for `Acme`).
3. Send, without any authentication:
```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": <known_github_team_id>, "name": "Admins", "slug": "admins", "url": "https://api.github.com/teams/1"},
  "organization": {"login": "Acme"},
  "member": {"login": "attacker-github-login"}
}
```
4. `verify_signature` resolves `Shipit.github(organization: "Acme")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally regardless of any `X-Hub-Signature` header (see `lib/shipit/github_app.rb` lines 76–83).
5. `MembershipHandler#process` runs, creating/finding the `User` for `attacker-github-login` via the GitHub API and calling `team.add_member(member)` on the privileged team (`app/models/shipit/webhooks/handlers/membership_handler.rb` lines 22–43), with no verification that this membership actually exists on GitHub.
6. The attacker signs into Shipit via normal GitHub OAuth using `attacker-github-login`; `current_user.authorized?` now returns `true` because the user is a member of a `Shipit.github_teams` team, granting full access to stacks/deploys/rollbacks.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action

            team.add_member(member)
          when 'removed'

          end
        end

        end
