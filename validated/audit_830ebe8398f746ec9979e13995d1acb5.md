### Title
`ProxyType::NonTransfer` falsely declares itself a superset of `ProxyType::Auction`, letting a `NonTransfer` proxy self-grant an `Auction` proxy and reach `Registrar::swap`, a call its own filter explicitly denies - ([File: polkadot/runtime/westend/src/lib.rs])

### Summary
This is the same bug class Parity already fixed once in this codebase for Asset Hub Westend (`prdoc/pr_12769.prdoc`, regression test `non_transfer_proxy_is_not_a_superset_of_governance` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:2518-2559`): a `ProxyType::is_superset` relation that is not actually backed by the `filter` (`InstanceFilter`) permission set, letting a lower-privilege proxy delegate add itself as a higher-privilege proxy via `pallet_proxy::add_proxy`. The same unfixed pattern still exists in the Westend and Rococo **relay-chain** runtimes, where `ProxyType::NonTransfer` is declared a superset of *every* other `ProxyType` (`(ProxyType::NonTransfer, _) => true`), including `ProxyType::Auction`, even though `NonTransfer`'s own filter explicitly and deliberately excludes `paras_registrar::Call::swap`, while `Auction`'s filter admits the entire `Registrar` pallet including `swap`.

### Finding Description
In `polkadot/runtime/westend/src/lib.rs:950-1032` (and identically in `polkadot/runtime/rococo/src/lib.rs:918-1010`): [1](#0-0) 
declares `NonTransfer` admits only `Registrar::register`, `Registrar::deregister` and `Registrar::reserve`, with the comment "Specifically omitting Registrar `swap`" — a deliberate, explicit denial. [2](#0-1) 
`ProxyType::Auction` admits `RuntimeCall::Registrar(..)` in full (no call-variant restriction), which includes `swap`. [3](#0-2) 
`is_superset` returns `true` for `(NonTransfer, _)` for any other non-`Any` type, i.e. it unconditionally claims `NonTransfer ⊇ Auction`.

`pallet_proxy::do_proxy` authorizes `add_proxy`/`remove_proxy` dispatched through an existing proxy purely via `is_superset`, never re-checking the target type's `filter` against the acting proxy's own filter: [4](#0-3) 

Because `is_superset(NonTransfer, Auction) == true`, a delegate holding only a `NonTransfer` proxy can dispatch, on behalf of the real account, `proxy(real, None, add_proxy { delegate: <self>, proxy_type: Auction, delay: 0 })`. `add_proxy_delegate` performs no additional permission check beyond the `is_superset` gate already passed in `do_proxy`: [5](#0-4) 

The delegate now also holds an `Auction`-typed proxy over `real`, and can call `proxy(real, Some(Auction), Registrar::swap { id, other })`. `do_proxy` will `filter` the call against the `Auction` definition, which admits it — even though the delegate's originally-granted `NonTransfer` proxy type was specifically written to deny this exact call.

Note that `Registrar::swap` itself still requires `ensure_root_para_or_owner` (`polkadot/runtime/common/src/paras_registrar/mod.rs:331`, `617-631`), which checks that the *dispatch origin* (i.e. `real`, since `do_proxy` dispatches as `RawOrigin::Signed(real)`) is the para manager. This means the delegate cannot swap a para it does not own outright — but it can invoke `swap` on behalf of `real` for `real`'s own paras, which the account owner deliberately excluded from the broad `NonTransfer` grant, presumably because `swap` has consequential lease/deposit/scheduling effects (`polkadot/runtime/common/src/paras_registrar/mod.rs:316-374`) that they wanted to reserve for a narrower, explicitly-authorized proxy. This mirrors the Nextcloud CVE-2020-8223 root cause exactly: a delegated permission relationship is used to grant more capability than the delegate was actually assigned, because the "is superset" containment check and the actual permission filter are inconsistent.

### Impact Explanation
This lets a `NonTransfer` proxy delegate — who was never granted the ability to call `Registrar::swap` — reach it anyway by self-escalating through a permitted `add_proxy` call. `swap` alters the on-demand/lease-holding status, auction information and auction deposit binding of the real account's parachain registration, which is state the account holder chose not to delegate. This is a permission-boundary violation of the proxy's `filter`, matching a class Parity has already classified and fixed once (asset-hub-westend, `prdoc/pr_12769.prdoc`, issue #12724) as worth a runtime patch. Severity is bounded because the underlying `Registrar::swap` extrinsic still enforces `ensure_root_para_or_owner`, so no cross-account theft or unauthorized-para action against a third party's para occurs — the escalation is confined to actions the real account itself is authorized to take, executed by a delegate it did not intend to authorize for this specific call.

### Likelihood Explanation
Requires an attacker to already hold a legitimately-granted `NonTransfer` proxy over a victim account that also owns/manages a registered para — a realistic but non-trivial setup (proxies are commonly granted for convenience/automation). No governance, root, or additional privilege is needed beyond the `add_proxy`/`proxy` dispatch path, both of which are ordinary signed extrinsics reachable by any account holding a `NonTransfer` delegation.

### Recommendation
Do not use a blanket `(ProxyType::NonTransfer, _) => true` in `is_superset`. Either:
1. Enumerate `is_superset` per-pair (as already done correctly for other runtimes like `coretime-westend`/`people-westend`), only declaring containment where every call admitted by the subset filter is also admitted by the superset filter, or
2. Add an automated lattice-consistency test analogous to `proxy_type_superset_relation_matches_call_filters` (already present for asset-hub-westend at `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:2493-2516`) to the Westend and Rococo relay-chain runtime test suites, so that any `is_superset` claim is checked against `filter` for every representative call including `Registrar::swap`.

### Proof of Concept
Not executed against a live network (per instructions). Conceptual reproduction path validated by static analysis of the exact guarded code paths:
1. `real` grants `delegate` a `ProxyType::NonTransfer` proxy via `pallet_proxy::add_proxy`.
2. `delegate` calls `pallet_proxy::proxy(real, None, Call::Proxy(add_proxy { delegate: delegate.clone(), proxy_type: ProxyType::Auction, delay: 0 }))`. This passes `do_proxy`'s guard because `NonTransfer.is_superset(&Auction) == true` (`polkadot/runtime/westend/src/lib.rs:1027`), and `add_proxy_delegate` performs no further filter check.
3. `delegate` calls `pallet_proxy::proxy(real, Some(ProxyType::Auction), Call::Registrar(swap { id, other }))`. `Auction.filter(&swap_call) == true` (`polkadot/runtime/westend/src/lib.rs:1004-1010`), so the call dispatches as `real`, succeeding if `real` is `id`'s manager — a call `NonTransfer.filter` alone was written to deny (`polkadot/runtime/westend/src/lib.rs:975-978`).

I did not run this against any test harness or public network; this is a static-analysis-based finding pending a local `pallet_proxy` + Westend/Rococo runtime integration test to confirm dispatch success end-to-end, analogous to the existing `staking_proxy_can_manage_staking_operator` / `proxy_type_superset_relation_matches_call_filters` tests already in the asset-hub-westend test suite. I was also unable to verify whether the mainnet Polkadot/Kusama relay-chain runtimes (not present in this repository snapshot) share the same `ProxyType` definition; only Westend and Rococo relay runtimes were inspectable here.
