### Title
Cross-repository state mutation via `pull_request`/`unassigned` webhook where `repository_owner` (signature-verification org) is decoupled from `repository.full_name` (handler mutation target) - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to check using `repository_owner`, which falls back to `params.dig('organization','login')` when `repository.owner.login` is absent. The `pull_request` handlers, e.g. `Shipit::Webhooks::Handlers::PullRequest::AssignedHandler`, instead resolve the target repository from the independently-controlled `params.repository.full_name` field. Because these two fields are never cross-checked, a payload verified under one organization's (weak/no-secret) key can mutate `PullRequest` records belonging to a completely different, victim-owned repository.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:
`repository_owner` (used in `Shipit.github(organization: repository_owner)` for signature verification, [1](#0-0) , selector defined at [2](#0-1) ) **must equal** the owner of `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, which is what `AssignedHandler#repository`/`#pull_request` actually reads and mutates ( [3](#0-2) ).

Trace:
1. `WebhooksController#create` fans the parsed body out to every registered `pull_request` handler via `Shipit::Webhooks.for_event(event)` [4](#0-3) , and the default handler list includes `AssignedHandler`, which processes both `assigned` and `unassigned` actions [5](#0-4) .
2. `AssignedHandler`'s `ExplicitParameters` schema requires `repository.full_name` but does **not** require `repository.owner.login` [6](#0-5) .
3. `verify_signature` picks the verifying GitHub App/secret via `repository_owner`, which falls back to `organization.login` whenever `repository.owner.login` is omitted [2](#0-1) .
4. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for the selected organization: `return true unless webhook_secret` [7](#0-6) .
5. `AssignedHandler#process`/`#pull_request`/`#repository` resolve the mutation target purely from `params.repository.full_name`, independent of whichever organization's secret verified the request [8](#0-7) .

Attacker's request: `POST /webhooks` with `X-Github-Event: pull_request`, a valid HMAC-SHA1 signature computed against a "no-secret" organization's (nonexistent) key — which is accepted trivially per step 4 — and a JSON body:
```json
{
  "action": "unassigned",
  "number": <victim PR number>,
  "pull_request": { ... },
  "repository": { "full_name": "victim-org/victim-repo" },
  "organization": { "login": "attacker-or-unsecured-org" },
  "sender": { "login": "attacker" }
}
```
The `repository` object intentionally omits `owner.login` so `repository_owner` resolves to `organization.login`, satisfying `verify_signature` against a lenient/no-secret org config, while `AssignedHandler` still locates and mutates the victim's `PullRequest`/review-stack via `repository.full_name`.

Why existing guards fail: `verify_signature` only authenticates that *some* organization's secret matches; it never checks that this organization is the same one owning the repository the handler will touch. `drop_unhandled_event` and the `ExplicitParameters` schema only validate presence/types of fields, not cross-field consistency between `repository_owner` and `repository.full_name`. `Repository` model validations constrain format of a tracked full name but do not tie it back to the webhook's authenticating organization.

### Impact Explanation
An attacker who controls (or can send unauthenticated payloads under) any organization configured in the Shipit instance without a `webhook_secret` can forge `pull_request` events that mutate `PullRequest` assignee state for **any other tracked repository/organization's** review-stack, without ever possessing that victim organization's `webhook_secret`. This is a cross-tenant/cross-repository state manipulation, matching the "payload for one repository mutating another's stack" Critical impact category. The specific `AssignedHandler` side effect is limited to overwriting `github_pull_request` JSON/assignee data, but the same verification/lookup divergence pattern applies to other `pull_request` handlers (`ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, etc.) that also key off `repository.full_name` independent of `repository_owner`, so the blast radius includes stack archival/deprovisioning and provisioning of review stacks for repos the attacker's authenticated organization does not own. This is repeatable for every tracked repository whose `full_name` the attacker can guess/know.

### Likelihood Explanation
Exploitability strictly requires that at least one organization registered in Shipit's GitHub App configuration has no `webhook_secret` set (or the attacker otherwise knows a valid secret for some onboarded-but-weakly-configured org) — this is a deployment/configuration precondition, not guaranteed by the engine by default. Given that precondition, the attack costs a single unauthenticated HTTP POST with a hand-crafted JSON body and requires no GitHub session, API token, or Shipit privileges, and is trivially repeatable against any tracked repository whose name is known (repository names are generally public/discoverable).

### Recommendation
Enforce that the organization used to verify the webhook signature is the same organization that owns the repository the handler will act on: derive `repository_owner` strictly from `repository.owner.login` (or parse it out of `repository.full_name`) rather than falling back to the independently-controlled `organization.login`; alternatively, require `repository.owner.login` in every relevant handler's parameter schema and validate in `verify_signature`/`create` that this owner matches the tracked `Shipit::Repository`'s registered organization before dispatching to handlers. Additionally, treat organizations with a blank `webhook_secret` as unverifiable (reject, not accept) rather than trivially passing signature verification.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or a new handler test), no live GitHub:
1. Configure two orgs in `Shipit.github_apps` test config: `"victim-org"` with a real `webhook_secret`, and `"weak-org"` with no `webhook_secret` (or stub `Shipit.github(organization: "weak-org").verify_webhook_signature` to return `true` unconditionally per `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret` branch).
2. Create a tracked `Shipit::Stack`/`Shipit::Repository` for `"victim-org/victim-repo"` and an associated `Shipit::PullRequest` fixture (e.g. `shipit_pull_requests(:review_stack_review)`).
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, body:
   ```json
   { "action": "unassigned", "number": <victim PR number>, "pull_request": {...valid schema...},
     "repository": { "full_name": "victim-org/victim-repo" },
     "organization": { "login": "weak-org" }, "sender": { "login": "attacker" } }
   ```
   with no `repository.owner.login` key, and any/no `X-Hub-Signature` (since `weak-org` has no secret).
4. Assert on both sides of the equality:
   - `repository_owner` resolved by the controller equals `"weak-org"` (via `params.dig('organization','login')`).
   - The `PullRequest` record actually mutated belongs to `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")`, i.e. `"victim-org"` — a different organization than the one that verified the signature.
   - Assert the victim `PullRequest`'s `github_pull_request`/assignees were updated (`assert_changes -> { pull_request.reload.assignees }`), proving the mismatch was exploitable and the response was `200 OK`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
