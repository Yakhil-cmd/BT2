### Title
Cross-Organization Status Forgery via SHA-Only Matching Bypasses the Verified-Org Boundary in Webhook Signature Check - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the HMAC secret) used to validate a webhook based on an *unverified* field taken from the payload itself, while the downstream `status` event handler ignores organization/repository scoping entirely and matches purely on commit SHA. This breaks the intended binding "the organization whose secret validated this webhook == the repository/commit that gets mutated," letting a webhook that is legitimately signed for **Org A** forge CI status data for a commit that actually belongs to **Org B**, in a multi-tenant Shipit deployment.

### Finding Description
`verify_signature` reads the organization to check the signature against straight from the untrusted JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` picks one of potentially several configured GitHub Apps (Shipit explicitly supports multi-org deployments, one app/secret per org) and verifies the signature only against that org's `webhook_secret`: [3](#0-2) 

Because `verify_webhook_signature` returns `true` outright when `webhook_secret` is blank, and because the org used to pick the secret (`repository.owner.login`) is read from the same attacker-supplied body that will later be reinterpreted, nothing forces the "verified organization" to correspond to the repository/commit that the event handler actually mutates.

The `status` handler amplifies this: it resolves which `Commit` to update purely by SHA, with **no repository or stack scoping at all**: [4](#0-3) 

`Commit.where(sha: params.sha)` queries across the entire instance's commits table, not just commits belonging to the organization that was authenticated. This directly contradicts the base `Handler` class's own convention of scoping by `repository.full_name` used by every other handler (push, pull_request, etc.): [5](#0-4) 

**The broken equality:** "organization authenticated by `verify_signature` == organization/stack whose commit is mutated by the handler." `verify_signature` binds trust to `repository.owner.login`; `StatusHandler` acts on any commit matching `sha` regardless of repository/org. The webhook payload's `sha` field is never checked against the org that was authenticated.

### Impact Explanation
`Commit#create_status_from_github!` writes a `Status` record that directly feeds `Commit#deployable?` and `Commit#blocked?`, which gate continuous deployment and merge-queue eligibility: [6](#0-5) [7](#0-6) 

An attacker who controls (or is granted, or exploits an org configured without a `webhook_secret`, which the setup docs show as a valid/blank configuration) a webhook signed for **any one** organization served by the same Shipit instance can send a `status` event with an arbitrary `sha` belonging to a **different** organization's stack, forging a `success` state for that commit. If `stack.continuous_deployment?` is enabled, this can trigger `ContinuousDeliveryJob` and result in an **unauthorized deploy** of a commit the attacker never had CI/commit access to control — satisfying the "Critical: unauthorized deploy" bar. At minimum it allows silently overwriting the recorded CI status shown throughout the UI/API for another tenant's commits.

### Likelihood Explanation
Requires Shipit to be configured for multiple GitHub organizations (a documented, supported configuration in `docs/setup.md`) and for the attacker's own org's webhook to reach the shared `/github/webhooks` endpoint — no cross-org secret or GitHub App credentials of the victim org are needed, only knowledge/collision of a target commit SHA (which is public on GitHub) and control of one authenticated webhook source. This is a design gap in scoping, not a brute-force attack, making it realistically triggerable once multi-org hosting is in place.

### Recommendation
- In `StatusHandler` (and any other handler that doesn't already do so), scope commit/stack lookups by `repository.full_name` (or `stack.repository`) in addition to `sha`, exactly as the base `Handler#stacks` helper does, and ensure the resolved repository's owning organization matches the organization that authenticated the webhook.
- In `WebhooksController#verify_signature`, after successful signature verification, re-validate that `repository_owner` matches the organization owning the resolved `Repository`/`Stack` record before handlers run, rather than trusting it implicitly as an authorization boundary.
- Do not treat a blank/missing `webhook_secret` as an implicit "always verified" pass in multi-org configurations; require the operator to explicitly opt into skipping signature checks per-org.

### Proof of Concept
1. Deploy Shipit configured for two GitHub organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple GitHub Applications").
2. Obtain a validly signed webhook body for `OrgA` (e.g. by triggering any real event in OrgA's installed GitHub App, or by using an OrgA whose `webhook_secret` is left blank, which `verify_webhook_signature` treats as always-verified).
3. Craft a `status` event body: `{"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/somerepo"}, "sha": "<sha-of-a-commit-belonging-to-OrgB-stack>", "state": "success", "context": "ci/required"}`, signed with OrgA's secret (or unsigned if OrgA has no secret).
4. POST to `/github/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the OrgB commit (no organization check performed), and calls `create_status_from_github!`, marking it `success`.
6. If OrgB's stack has `continuous_deployment` enabled and the forged status makes the commit `deployable?`, a deploy of that commit is scheduled without any legitimate CI signal or OrgB authorization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
