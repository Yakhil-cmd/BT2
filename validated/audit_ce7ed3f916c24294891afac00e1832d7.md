### Title
Stack-scoped ApiClient tokens can read CCMenu build status for any stack, bypassing their stack authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` resolves the target stack directly from the request path instead of using the stack-scoping collection every other API controller relies on, so a token that is authorized only for one stack can be used to read the deploy/build status of any stack in the installation.

### Finding Description
`ApiClient` supports being scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . `Shipit::Api::BaseController` enforces that scoping through the `stacks`/`stack` helpers, which restrict lookups to `current_api_client.stack_id` when the client is scoped: [2](#0-1) 

Every other API resource controller (e.g. `Api::StacksController#stack`) uses this scoped `stacks.from_param!` helper. `Api::CCMenuController`, however, overrides `stack` to resolve the record directly from `Stack.from_param!(params[:stack_id])`, completely bypassing the `current_api_client.stack_id` restriction: [3](#0-2) 

The only authorization gate on this controller is `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`. That method only checks whether the string `"read:stack"` is present in the client's `permissions` array — it never checks which stack the client is scoped to: [4](#0-3) 

The intended binding is: *the stack a token authorizes (`api_client.stack_id`) == the stack the request touches (`params[:stack_id]`)*. `CCMenuController` breaks this by only checking the permission "shape" (`read:stack`) and letting the attacker supply an arbitrary `stack_id` in the path, exactly analogous to the reported bug class where a check is applied unconditionally to the wrong operand instead of being tied to the actual acting identity.

That the stack-scoping is a real, load-bearing security feature (not dead code) is demonstrated by the fixture `here_come_the_walrus` (`stack: shipit`) and the corresponding test asserting that a stack-scoped client only sees its own stack via `Api::StacksController`: [5](#0-4) 

`CCMenuController` has no equivalent test or guard, and its route is nested exactly like the scoped resources (`/stacks/*stack_id/ccmenu`) in `config/routes.rb`, so the same token that is meant to be confined to one stack can be pointed at any other stack's CCMenu endpoint.

### Impact Explanation
A stack-scoped `ApiClient` token with only `read:stack` permission — intended to expose build/deploy status for one stack (e.g. to a CI dashboard) — can be replayed against `/api/stacks/<other_owner>/<other_repo>/<other_env>/ccmenu` to read that other stack's latest deploy/rollback status and running state. This is an escalation of a narrowly-scoped credential into unauthorized read of deploy state across repositories/stacks the token was never granted access to, matching the High-impact category of "escalation ... unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Exploitation only requires possession of any valid, low-privilege, stack-scoped `read:stack` API token and knowledge or guessing of another stack's `owner/repo/environment` path (which is not secret — stack identifiers are visible throughout the UI/URLs). No additional privilege, session, or write access is needed beyond the token itself; the request is a single unauthenticated-relative-to-scope GET.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks.from_param!` helper from `BaseController` (as `Api::StacksController` and other nested resource controllers do) instead of calling `Stack.from_param!` directly, so lookups are constrained to `current_api_client.stack_id` whenever the client is stack-scoped.

### Proof of Concept
1. Create/obtain a stack-scoped `ApiClient` (`stack_id` set to Stack A, `permissions: ["read:stack"]`).
2. Authenticate with that token's basic-auth credentials against the API.
3. Send `GET /api/stacks/<owner-of-stack-B>/<repo-of-stack-B>/<env-of-stack-B>/ccmenu`.
4. `authenticate_api_client` succeeds (valid token) and `require_permission :read, :stack` succeeds (`check_permissions!` only checks the permission string) even though the token is scoped to Stack A.
5. `CCMenuController#stack` resolves Stack B via `Stack.from_param!(params[:stack_id])`, ignoring `current_api_client.stack_id`, and returns Stack B's CCMenu XML (latest deploy status) — data the token was never authorized to see.
