### Title
Cross-organization team membership forgery via `Team.find_or_create_by!` skipping organization re-validation - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` by `github_id` alone and only assigns `organization` inside the `create` block, never re-checking it on the find branch. Because webhook signature verification (`WebhooksController#verify_signature`) trusts whichever organization the attacker names in the payload (falling back to `params.dig('organization', 'login')` when no `repository` key is present), an attacker who legitimately controls a Shipit-registered organization's webhook secret can sign an arbitrary JSON body and add themselves (or anyone) to a pre-existing `Team` row that actually belongs to a different, victim organization.

### Finding Description
The binding that must hold is: for every `Team` record, `team.organization == <organization that actually owns that GitHub team>`. Once a `Team` row exists (created earlier from a genuine `shopify` membership webhook, `team.organization == 'shopify'`, `team.github_id == N`), the code in `app/models/shipit/webhooks/handlers/membership_handler.rb:38-43` does:

```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```

`find_or_create_by!` first attempts `Team.find_by(github_id: params.team.id)`; if found, the block (which sets `organization`) never runs — it only executes for newly-created records. `process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) then unconditionally calls `team.add_member(member)` on whatever `Team` was returned, with no check that `team.organization == params.organization.login`.

The signature check that is supposed to bind a payload to a specific organization is in `app/controllers/shipit/webhooks_controller.rb:24-49`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`repository_owner` is derived from the same attacker-controlled JSON body being verified. For a `membership` event (an org-level GitHub event that carries no `repository` object in real payloads), `repository_owner` falls back to `params.dig('organization', 'login')`. This means the secret used to validate the HMAC is chosen based on a field the attacker also controls in the raw body they are signing. An attacker who is a genuine member/admin of `attacker-org` (which is a `Shipit`-trusted org with its own configured webhook secret) can:

1. Learn or guess the numeric GitHub `github_id` of a team belonging to a different org already tracked by Shipit (e.g. `shopify`'s team, id `N` — GitHub team IDs are visible via various GitHub API/UI surfaces and are not organization-secret).
2. Craft a `membership` webhook JSON body with `team: { id: N, ... }`, `organization: { login: 'attacker-org' }`, `member: { login: 'mallory' }`, `action: 'added'`.
3. Sign it with `attacker-org`'s real webhook secret (which the attacker legitimately knows).
4. POST it to `/webhooks`. `verify_signature` resolves `repository_owner` to `'attacker-org'` and the signature validates correctly against that org's secret.
5. `MembershipHandler` finds the existing `Team` (github_id: N, organization: 'shopify') via `find_or_create_by!`, skips the create block, and calls `team.add_member(mallory)` — adding `mallory` to a team that belongs to `shopify`, despite the webhook being signed by, and describing, `attacker-org`.

No guard (`ExplicitParameters` schema, `drop_unhandled_event`, `verify_signature`) checks that `team.organization == params.organization.login` on the find branch, so the binding is broken specifically for reused `github_id`s.

### Impact Explanation
This lets an attacker who administers only their own (trusted) GitHub organization's Shipit webhook silently add arbitrary GitHub logins as members of a `Team` that Shipit believes belongs to a different organization, without any interaction from that organization. If that `Team` is referenced in `Shipit.github_teams` (`app/models/shipit/user.rb:80-82`, `lib/shipit.rb:256-258`), this is a direct escalation path into `Shipit.github_teams` authorization — an attacker (or an accomplice account) could be granted `User#authorized?` access to the entire Shipit instance by being added as a "member" of an authorization-gating team they were never actually a member of on GitHub. This matches the High severity category ("escalation into `Shipit.github_teams` authorization"). It is repeatable against any `Team` row whose `github_id` the attacker can enumerate/guess.

### Likelihood Explanation
Preconditions: attacker must control/administer one org that Shipit already trusts (has a configured `GithubHook`/webhook secret for a `GithubHook::Organization`) — the prompt states this is granted. Attacker needs the numeric `github_id` of a target team belonging to a different org, which is a non-secret integer often discoverable via public GitHub surfaces or brute-force (team IDs are sequential and not access-controlled the way org membership is). No Shipit session, API token, or GitHub App secret is required, only the attacker's own org's webhook secret, which they legitimately possess. This is a moderate-cost but fully repeatable exploit purely through crafted HTTP POSTs to `/webhooks`.

### Recommendation
In `find_or_create_team!`, re-validate/reset the organization on every invocation, not just at creation, e.g.:
```ruby
def find_or_create_team!
  team = Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
  raise ArgumentError, "Team #{team.github_id} organization mismatch" unless team.organization == params.organization.login
  team
end
```
Additionally, `repository_owner` in `WebhooksController` should not be derived from attacker-controlled payload alone for org-level events without cross-checking it against the resolved `GithubHook` record's own stored organization, to avoid signature verification being self-referential.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb
test "does not add members to a team owned by a different organization" do
  team = Shipit::Team.create!(github_id: 999, organization: 'shopify', name: 'Devs', slug: 'devs', api_url: 'http://x')

  Shipit::Webhooks::Handlers::MembershipHandler.new({
    'action' => 'added',
    'team' => { 'id' => 999, 'name' => 'Devs', 'slug' => 'devs', 'url' => 'http://x' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'mallory' },
  }).process

  team.reload
  assert_equal 'shopify', team.organization
  refute_includes team.members.map(&:login), 'mallory' # currently FAILS: mallory is added
end
```
This demonstrates the find branch never re-verifies `team.organization == params.organization.login` before mutating membership.
