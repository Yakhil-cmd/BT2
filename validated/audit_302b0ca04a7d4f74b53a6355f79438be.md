Based on my investigation, I found a genuine analog: the `WebhooksController` verifies the HMAC signature against the webhook secret of the organization named in one payload field, while the actual handlers (`Handler#repository_name`, `MembershipHandler#find_or_create_team!`) act on a *different* field of the same attacker-supplied JSON body without ever checking that it agrees with the verified organization.

### Title
Webhook signature verification binds to `repository.owner.login`, but handlers act on the independent, unverified `repository.full_name` / `organization.login` fields — allowing cross-organization/repository forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App / webhook secret to check the HMAC signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1)  Once the signature is accepted, the handlers that process the very same JSON payload derive the affected repository/organization from a *different* key that is never compared to the one used for verification: `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [3](#0-2) , and `MembershipHandler` reads `params.organization.login` directly to create/attach a `Team` [4](#0-3) .

### Finding Description
For a multi-organization Shipit installation, `Shipit.github(organization: repository_owner)` looks up the `GithubApp` config (and its `webhook_secret`) keyed by whatever organization string appears at `repository.owner.login` (or `organization.login`) in the inbound JSON. [5](#0-4)  The signature check only proves that whoever sent the request knows the webhook secret for *that* claimed organization — it says nothing about the `repository.full_name` field or the `organization.login` field consumed later by the event handler, since nothing in `verify_signature` cross-checks these fields against each other.

Concretely, for a `push` event the handler resolves the target `Stack`s via `Repository.from_github_repo_name(repository_name)` where `repository_name` comes from `repository.full_name`, and then calls `stack.sync_github` on every matching stack. [6](#0-5)  If a payload sets `repository.owner.login = "OrgA"` (used to fetch OrgA's webhook secret and pass signature verification) but `repository.full_name = "OrgB/some-repo"` (used to select which stack gets synced), a requester who knows OrgA's webhook secret can trigger `GithubSyncJob`/state changes for stacks that belong to a completely different, unrelated GitHub organization/repository that Shipit also serves.

Similarly, `membership` events are verified against `repository_owner` (falling back to `organization.login`), but `MembershipHandler` trusts `params.organization.login` to create/find a `Team` scoped to that organization and then adds or removes `Membership`s for arbitrary logins under that team. [7](#0-6)  Because `Shipit::User#authorized?` gates dashboard access purely on team membership (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [8](#0-7) , a forged membership payload that is validly signed for one organization but names a different organization's team/id can add an arbitrary GitHub login to a `Shipit.github_teams`-authorized team, escalating that account's dashboard authorization.

This matches the reported bug class ("privileged operation is gated on one identity/whitelist check but performed against a different, attacker-controlled value") applied to Shipit's binding between "an organization that authenticated" (the field used for HMAC verification) and "the repository/organization that is written" (the field used by the handler) — exactly one of the allowed analog categories.

### Impact Explanation
This crosses an authentication/authorization boundary between GitHub organizations that Shipit is configured to serve. An attacker who legitimately controls a webhook for Organization A (e.g., is an admin of an A repo configured in Shipit, and thus knows/can trigger OrgA's webhook secret) can forge events that are processed as if they came from Organization B, causing:
- Unauthorized stack syncs/deploys triggers for repositories/organizations they do not control (`push`, `check_suite`, `status` handlers act on `repository_name`/commit `sha` independent of the organization verified).
- Escalation into `Shipit.github_teams` authorization via forged `membership` events that add a user to a team ID belonging to a different organization, potentially granting dashboard access that should require actual GitHub org membership.

This fits the High-severity bucket: "escalation into `Shipit.github_teams` authorization" and touches deploy/task-triggering surfaces tied to `push`/`status` events.

### Likelihood Explanation
Requires the attacker to already have legitimate access to trigger a real, signed webhook for at least one organization hosted by the same Shipit instance (i.e., admin of a repo in one served GitHub org). Multi-tenant Shipit deployments (the `secrets.yml` `github:` block supports multiple named organizations, as seen in `test/dummy/config/secrets_double_github_app.yml`) are the realistic trigger scenario. [9](#0-8)  Single-organization deployments (the common case) are not exposed to this because `repository_owner` and `repository_name`'s implied organization would trivially coincide.

### Recommendation
In `WebhooksController#verify_signature` and in each `Handler`, ensure that the organization/repository fields used for signature selection and those used to select the affected `Stack`/`Team`/`Repository` are the same value — e.g., derive `repository_owner` from `repository.full_name`'s owner segment (or vice versa) so both checks reference one canonical field, and reject payloads where `repository.owner.login`, `organization.login`, and the owner portion of `repository.full_name` disagree.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (as supported by `Shipit.github_app_config`). [10](#0-9) 
2. As an admin of a repo in `OrgA`, capture/craft a `push` webhook payload but set:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgB/target-repo"`
3. Sign the raw body with OrgA's known `webhook_secret` and send `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature. [1](#0-0) 
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/target-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on OrgB's stack, even though the requester never proved control of OrgB. [6](#0-5)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
