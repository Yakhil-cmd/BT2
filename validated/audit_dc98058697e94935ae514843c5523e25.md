### Title
Unconditional re-checkout of the live, published worktree defeats atomic-publish guarantee, allowing partial-content exposure - ([File: main.go])

### Summary
`git-sync`'s core contract is that consumers only ever see the previous or the new revision, atomically, via a symlink swap [1](#0-0) . `SyncRepo` re-runs `configureWorktree` (which performs `git reset --hard <hash>`, a non-atomic, file-by-file checkout) on the *currently published* worktree even when the remote has not changed, and `sanityCheckWorktree` — by its own documented limitation — cannot detect a partial checkout, only that HEAD matches and `fsck` succeeds.

### Finding Description
In `SyncRepo`, when `currentHash == remoteHash`, the existing worktree is only sanity-checked, not rebuilt from scratch: [2](#0-1) 
`sanityCheckWorktree` explicitly documents that it "does not guarantee that the worktree has all the files checked out - git could have died halfway through and the repo will still pass this check," relying only on `rev-parse HEAD` and `fsck --connectivity-only`: [3](#0-2) 
Critically, `configureWorktree` — which performs the actual (non-atomic) `git reset --hard <hash>` file checkout — is invoked unconditionally on `newWorktree`, which equals `currentWorktree` (the live, symlinked directory) whenever `changed` is `false`: [4](#0-3) [5](#0-4) 
This directly mutates the directory that the published symlink already points at, bypassing the symlink-swap mechanism that is supposed to give atomicity. Each sync loop iteration runs under a caller-controlled timeout context (`--sync-timeout`), and all git subcommands (including this in-place `reset --hard`) are executed through that same cancellable context: [6](#0-5) 
If an attacker who controls the upstream repository content (in-scope untrusted input) commits a large tree, huge blobs, or otherwise makes checkout of the *unchanged* hash slow (e.g., large files, expensive filters, many objects), the `reset --hard` invoked on the live worktree can be interrupted by the sync-timeout cancellation or by a process restart while it is mid-write. Because `sanityCheckWorktree` cannot detect a half-written checkout, on the next loop the corrupted, partially-checked-out directory is accepted as valid and continues to be served through the "atomic" symlink to consumers — this is the same root-cause pattern as the referenced report: the code checks a superficial signal (`HEAD` hash / `fsck` success, analogous to `totalUnits == 0`) instead of the actual precondition that matters (full checkout completeness / true tax ratio), and thereby permits an operation that should have been guarded.

### Impact Explanation
This corrupts the contents behind the officially "atomic" symlink target that downstream containers/pods actually consume, causing them to read a partially updated / inconsistent directory — a direct violation of git-sync's core atomicity contract and falls under "publishing wrong or partial content."

### Likelihood Explanation
Requires an attacker who can influence the content fetched by git-sync (a malicious or compromised upstream repo/commit) to craft content whose non-atomic checkout is slow enough to be interrupted by `--sync-timeout` or a pod restart during a no-op sync cycle. This is plausible for any long-running git-sync deployment tracking a branch where an adversary can push large/slow-checkout commits, but does require some external trigger (timeout expiry or process interruption) to actually manifest the corruption, rather than being deterministically triggerable in a single request.

### Recommendation
- Only re-run `configureWorktree`/checkout logic on a fresh worktree (never in-place on the currently published directory); if reconfiguration (e.g., sparse-checkout toggle) is required for an unchanged hash, create a new worktree copy, checkout into it, then symlink-swap, mirroring the `changed` path.
- Strengthen `sanityCheckWorktree` to actually validate checkout completeness (e.g., `git status --porcelain` for unexpected missing files, or compare tree object list against working directory) rather than relying solely on `HEAD` hash and `fsck`.

### Proof of Concept
1. Point `git-sync` at an attacker-influenced/malicious upstream repo with a large tree and set a short `--sync-timeout`.
2. Let the initial sync succeed and publish the symlink normally.
3. On a subsequent no-op cycle (remote hash unchanged), `configureWorktree` re-runs `git reset --hard <hash>` on the same, currently-symlinked worktree directory.
4. Interrupt that cycle (timeout expiry, OOM-kill, or pod restart) mid-checkout.
5. On restart, `sanityCheckWorktree` (HEAD match + `fsck --connectivity-only`) passes despite the worktree having incomplete/stale files, so the corrupted directory continues to be served via the unchanged, still-published symlink — consumers observe partial content while git-sync reports success.

```go
// sanityCheckWorktree tries to make sure that the dir is a valid git
// repository.  Note that this does not guarantee that the worktree has all the
// files checked out - git could have died halfway through and the repo will
// still pass this check.
func (git *repoSync) sanityCheckWorktree(ctx context.Context, worktree worktree) bool {
	git.log.V(3).Info("sanity-checking worktree", "repo", git.root, "worktree", worktree)

	// If it is empty, we are done.
	if empty, err := dirIsEmpty(worktree.Path()); err != nil {
		git.log.Error(err, "can't list worktree directory", "path", worktree.Path())
		return false
	} else if empty {
		git.log.V(0).Info("worktree is empty", "path", worktree.Path())
		return false
	}

	// Make sure it is synced to the right commmit.
	stdout, _, err := git.Run(ctx, worktree.Path(), "rev-parse", "HEAD")
	if err != nil {
		git.log.Error(err, "can't get worktree HEAD", "path", worktree.Path())
		return false
	}
	if stdout != worktree.Hash() {
		git.log.V(0).Info("worktree HEAD does not match worktree", "path", worktree.Path(), "head", stdout)
		return false
	}
```
