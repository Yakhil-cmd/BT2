Confirmed: `pool_creator` is set once at pool initialization and stored immutably in `PoolState`, with no instruction anywhere in the program to update it. This confirms the analog is valid — the recipient address for creator fees is permanently fixed and unchangeable.

### Title
Permanent freezing of creator fees when `pool_creator` is a blocklistable-token-blocked address (e.g., USDC) - (File: `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
`collect_creator_fee` and `collect_creator_fee_permissionless` hard-code the fee recipient to the ATA of the immutable `pool_creator` pubkey stored in `PoolState`, with no way to redirect payment to an alternate address. If either pool token is a blocklist-capable token (e.g. USDC) and the `pool_creator` address is or becomes blocklisted by the token issuer, the accrued `creator_fees_token_0`/`creator_fees_token_1` can never be withdrawn from the vault by anyone, permanently freezing those funds inside the pool.

### Finding Description
`PoolState.pool_creator` is set once during pool initialization and is never updated anywhere in the program [1](#0-0) . Both creator-fee collection instructions strictly bind the destination token accounts to this fixed creator address:

- `CollectCreatorFee` requires the signer to equal `pool_state.load()?.pool_creator` and creates/uses the creator's own ATA [2](#0-1) , with the destination ATAs constrained to `associated_token::authority = creator` [3](#0-2) .
- `CollectCreatorFeePermissionless` lets anyone pay to create the ATA, but the `creator` account itself is constrained to `address = pool_state.load()?.pool_creator` and the destination ATAs are constrained to `associated_token::authority = creator` [4](#0-3) [5](#0-4) .

In both instructions, funds are moved via `transfer_from_pool_vault_to_user` directly to the creator-owned ATA before `pool_state.creator_fees_token_0/1` are zeroed [6](#0-5) . If the underlying mint enforces a blocklist (e.g., USDC-style `transfer` reverting for blocked addresses, as noted in the referenced weird-erc20 catalog), any attempt to create/transfer into the creator's ATA will revert unconditionally, since there is no alternate recipient parameter as exists in the admin fee-collection paths.

By contrast, the admin-only fee paths `collect_protocol_fee` and `collect_fund_fee` accept an arbitrary caller-supplied `recipient_token_0_account`/`recipient_token_1_account` with no owner constraint [7](#0-6) [8](#0-7) , so those fees can always be redirected to a non-blocklisted address. Only the creator-fee path lacks this flexibility, exactly mirroring the Cooler `claimRepaid` bug class where the recipient is hard-coded to a potentially-blocklisted address with no override mechanism.

### Impact Explanation
Once `creator_fees_token_0`/`creator_fees_token_1` accrue for a `pool_creator` that is blocklisted on a token such as USDC, those funds become permanently stuck in the pool's token vault — they are counted in `vault_amount_without_fee` [9](#0-8)  as a liability that can never be paid out, since neither `collect_creator_fee` nor `collect_creator_fee_permissionless` provides any mechanism to change the recipient. This is a permanent freezing of LP/creator funds with no recovery path (unlike the admin fee paths, which can always redirect to an unblocked recipient).

### Likelihood Explanation
Likelihood is moderate: it requires (a) the pool being created with a blocklist-capable token such as USDC as `token_0`/`token_1`, and (b) the `pool_creator` address being or becoming blocklisted by the token issuer (a real-world, externally-triggered event, not attacker-controlled). This mirrors the exact scenario described in the referenced Cooler report, which was rated Medium for the same reasoning: an external, plausible compliance action against one specific address that permanently locks funds with no on-chain remediation.

### Recommendation
Add a recipient parameter/account (with appropriate access control limited to the pool creator authorizing the transfer, similar to `collect_protocol_fee`/`collect_fund_fee`) so that if the default creator ATA cannot receive tokens, the creator (or a permissionless caller acting on the creator's instruction) can direct the fee payout to an alternate, non-blocklisted token account instead of being hard-locked to the ATA of the stored `pool_creator` pubkey.

### Proof of Concept
1. Initialize a pool where `token_0` (or `token_1`) is a USDC-like mint with issuer-controlled blocklisting, and set `pool_creator` to address `C`.
2. Perform swaps so that `creator_fee_on`/`enable_creator_fee` causes `creator_fees_token_0`/`creator_fees_token_1` to accrue in `PoolState` [10](#0-9) .
3. The token issuer blocklists address `C` (or `C`'s associated token account).
4. Any call to `collect_creator_fee` or `collect_creator_fee_permissionless` now fails at the `transfer_from_pool_vault_to_user` call into `creator_token_0`/`creator_token_1` because the ATA owner `C` is blocklisted, and there is no way to specify a different recipient [11](#0-10) .
5. The accrued `creator_fees_token_0`/`creator_fees_token_1` remain permanently locked in the pool vault, unclaimable by anyone.

```rust
pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;

    Ok(())
```
