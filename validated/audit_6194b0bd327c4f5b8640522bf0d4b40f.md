### Title
API token scoped to one stack can read CCMenu deploy status of any other stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` resolution method used by `Shipit::Api::BaseController` in a way that drops the stack-scoping check that `ApiClient#stack_id` is supposed to enforce, letting a stack-scoped token read the CCMenu (build/deploy status) output of any stack in the installation.

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true`, and `Shipit::Api::BaseController#stacks` enforces that scope for every endpoint that uses it: [1](#0-0) 

That is the intended binding: *token authorises stack X == stack actually touched must be X (or Stack.all if unscoped)*. `stack` in the base controller composes with `stacks` so this scope is respected everywhere it's used.

`Shipit::Api::CCMenuController`, however, defines its own `stack` method that bypasses `stacks` entirely and resolves directly from the raw request parameter: [2](#0-1) 

It also overrides `authenticate_api_client` to additionally accept the token via a query-string parameter (`params[:token]`) instead of only Basic-Auth headers: [3](#0-2) 

The permission check that runs before `show` only verifies the *operation* (`read:stack`) via `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`: [4](#0-3) 

`check_permissions!` only checks that `"read:stack"` is present in `permissions`; it never compares `current_api_client.stack_id` to the `stack_id` from the request. That comparison is only performed implicitly by `BaseController#stacks`, which `CCMenuController#stack` does not use.

The binding broken as an equality is:
`current_api_client.stack_id (the stack the token authorises) == params[:stack_id] (the stack the request actually touches)`

Before the flaw (in every other API controller that relies on `BaseController#stack`), this equality is enforced: a client created with `stack_id: A` querying `stack_id: B` gets a `RecordNotFound`/404 because `Stack.where(id: A)` doesn't contain `B`. In `CCMenuController`, the equality is never checked: `Stack.from_param!(params[:stack_id])` resolves any stack in the system regardless of `current_api_client.stack_id`.

### Impact Explanation
This is an authorization escalation: a token that was deliberately scoped to a single stack (e.g., via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)` as done by `Shipit::CCMenuUrlController`) can be used to read `lastBuildStatus`, `lastBuildLabel`, `activity`, and `webUrl` for any repository/stack managed by the Shipit instance, not just the one it was scoped to. This matches the "High — unauthenticated read of stack state, task streams or deploy output" impact category, because from the perspective of the *other* stack's owners, this is effectively an unauthenticated (out-of-scope-token) read of their deploy status. It does not require session cookies, a GitHub token, or admin privileges — only possession of a validly-signed `ApiClient` token that was meant to be limited to one stack (such tokens are routinely embedded in CCMenu URLs, e.g. shared with CI dashboard tools, and are lower-trust than a full API credential).

### Likelihood Explanation
Likelihood is high given normal usage patterns: `CCMenuUrlController#client` automatically mints exactly this kind of stack-scoped, `read:stack`-only token for every user who visits a stack's CCMenu URL widget: [5](#0-4) 

Any holder of such a token (which is designed to be embedded in third-party CI-status tools/URLs and is thus more exposed than a session cookie) can simply change the `stack_id` path segment in the request to `GET /api/stacks/:other_stack_id/ccmenu` to read status for a different stack. No special tooling or race condition is needed — a single crafted HTTP request suffices.

### Recommendation
Make `Shipit::Api::CCMenuController#stack` use the scoped `stacks` relation from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so stack-scoped tokens are constrained exactly as they are everywhere else in the API.

### Proof of Concept
1. As a legitimate user, visit stack `owner/repo-a`'s CCMenu URL, which creates (or reuses) an `ApiClient` scoped to `repo-a` with `permissions: ["read:stack"]` via `CCMenuUrlController#client`.
2. Capture that token (it is embedded in the returned `ccmenu_url` query string, e.g. shared in a CI dashboard config).
3. Send `GET /api/stacks/other-owner/repo-b/master/ccmenu?token=<captured_token>`.
4. `authenticate_api_client` in `CCMenuController` accepts the token via the query string and authenticates the `ApiClient` scoped to `repo-a`.
5. `require_permission :read, :stack` passes because the client has `"read:stack"` in its permissions (the check never verifies which stack).
6. `stack` resolves `repo-b` directly via `Stack.from_param!(params[:stack_id])`, bypassing the `stacks` scoping that would have restricted lookup to `repo-a` only.
7. The response renders `repo-b`'s build/deploy status XML, disclosing information the token was never authorized to access.
