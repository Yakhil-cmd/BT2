### Title
Cross-repository commit-status forgery via organization-scoped webhook signature vs. globally-scoped `sha` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The oracle bug averaged prices expressed in incompatible units (USD vs. per-foreign-asset) as if they were the same quantity. The structural analog in `shipit-engine` is a unit/scope mismatch between what the webhook signature authenticates (an *organization*, keyed off `repository.owner.login`) and what the `status` webhook handler actually mutates (*any commit row matching a `sha`, instance-wide, with no repository/organization check*). The two values that should be bound together — "organization that signed this payload" and "repository whose commit gets updated" — are never compared.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the webhook secret) to validate against using the *organization* named in the payload, falling back to `organization.login` if `repository` is absent: [1](#0-0) [2](#0-1) 

This only proves the request was signed by *some* app installation belonging to that organization — it says nothing about which specific repository within that organization (or which commit) the payload is entitled to affect.

`StatusHandler#process`, however, ignores the repository entirely and updates **any** commit in the whole Shipit instance whose SHA matches the payload's `sha` field: [3](#0-2) 

Compare this with `PushHandler`, which correctly scopes to the named repository via `Handler#stacks`/`#repository_name` (`payload.dig('repository', 'full_name')`) before acting: [4](#0-3) [5](#0-4) 

`StatusHandler` never calls `stacks`/`repository_name` at all — it does a bare `Commit.where(sha: params.sha)` lookup. The equality that should hold is:

`organization authenticated by verify_signature == organization owning the repository whose commit is being written`

but the code only checks the left side and never re-derives or compares it against the commit's actual stack/repository on the right side.

### Impact Explanation
Any organization configured in `Shipit.github` (including one whose `webhook_secret` is unset — several sample/dummy configs in this codebase leave `webhook_secret: # nil`, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no secret is set) can submit a `status` event that updates the CI status of a commit belonging to a *different* stack/repository than the one nominally tied to that organization's app installation, as long as the attacker knows (or guesses) the target commit's SHA — which is public information on GitHub. Commit statuses feed directly into the deploy-safety checks (`ci`/`blocking`/`hidden` status configuration is read from `shipit.yml` and gates whether a commit is deployable), so forging a `success` status for a commit in a stack the attacker does not control can defeat CI gating and enable an unauthorized deploy of that stack.

### Likelihood Explanation
Exploitability requires only the ability to trigger one authenticated (or unauthenticated, if `webhook_secret` is blank for that org) webhook delivery of a `status` event with an attacker-chosen `sha` — no access to the target repository or its GitHub App installation is needed, satisfying the "unprivileged attacker" bar. This is a straightforward oversight (missing repository/organization scoping in a single handler) rather than a theoretical or best-practice issue, since sibling handlers (`PushHandler`) demonstrate the correct scoping pattern that `StatusHandler` omits.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository/stacks derived from `payload.dig('repository', 'full_name')` (reusing `Handler#stacks`), just as `PushHandler` does, so a commit's status can only be updated by the organization/repository that actually owns it.

### Proof of Concept
1. Shipit hosts stacks for `org-a/repo-x` (webhook secret configured and known only to org A) and `org-b/repo-y` (any org, including one with no `webhook_secret` set, or one the attacker legitimately controls).
2. Attacker looks up a real commit SHA `deadbeef...` in `org-a/repo-x`'s pending deploy, which has a `blocking` CI check pending.
3. Attacker sends a `status` webhook to `/webhooks` with `X-Github-Event: status`, a valid signature computed with `org-b`'s secret (or no signature at all if `org-b`'s `webhook_secret` is blank), and body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/blocking-check",
  "repository": {"owner": {"login": "org-b"}, "full_name": "org-b/repo-y"}
}
```
4. `verify_signature` validates successfully against `org-b`'s app/secret. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")`, finds the commit belonging to `org-a/repo-x`, and marks the blocking CI check as `success`, even though the signing organization (`org-b`) has no relationship to `org-a/repo-x`.
