### Title
Webhook signature verification is keyed on a different payload field than the one handlers use to resolve the target repository/stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate the HMAC signature against using `repository_owner` (`params.dig('repository', 'owner', 'login')`), while the actual event handlers (`Shipit::Webhooks::Handlers::Handler#stacks`) resolve which `Stack`/`Repository` to act on using an entirely different field, `payload.dig('repository', 'full_name')`. Because these two independently-controlled JSON fields in the same POST body are never cross-checked, a party who legitimately controls one Shipit-registered GitHub organization (and therefore knows/controls its `webhook_secret`) can craft a signed request whose `repository.owner.login` matches their own org (so the signature check passes) but whose `repository.full_name` names a stack belonging to a different, victim organization/repository.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` verifies inbound webhooks like this: [1](#0-0) 

The `github_app` (and thus the secret checked) is selected purely from a body field: [2](#0-1) 

Meanwhile, every handler resolves the affected repository from a *different* body field, `repository.full_name`, completely independent of `repository.owner.login`: [3](#0-2) 

`PushHandler`, for example, uses that repository resolution to look up any non-archived stack on the named branch and force a GitHub sync using an attacker-supplied `after` SHA: [4](#0-3) 

Since HMAC verification only checks that the raw bytes are signed by *some* valid per-organization secret — and the org used to pick that secret (`repository.owner.login`) is not required to be consistent with `repository.full_name` — an attacker who is a legitimate administrator of Org A (and thus knows Org A's `webhook_secret`, since org owners configure it on the GitHub side) can sign a payload where `repository.owner.login = "org-a"` (secret used to verify = Org A's, which passes) but `repository.full_name = "org-b/victim-repo"`. This breaks the trust binding "the organization that authenticated the request" == "the repository that is acted upon by the handler."

### Impact Explanation
This does not directly grant RCE, token exfiltration, or an unauthorized deploy by itself: `PushHandler` only triggers `stack.sync_github(expected_head_sha: params.after)`, which schedules a `GithubSyncJob` to re-fetch commits/state for the victim stack using the *attacker's declared* `after` SHA, without an actual corresponding push having occurred on the victim repository. Other event types reachable the same way (`status`, `check_suite`, `commit_status`, `deployable_status`) similarly let an authenticated-but-wrong-org sender inject or forge commit statuses/check-run results for a victim stack via `Handler#stacks`, potentially manipulating merge-queue automation (`ProcessMergeRequestsJob`/`MergeRequest#all_status_checks_passed?`) into believing CI passed on a victim repository it should have no authority over — an escalation into CI/merge decisions for stacks the sender's org doesn't own. This is a cross-organization data/state injection but stops short of directly proving an unauthorized merge, deploy, or credential exfiltration without simulating the full merge-queue flow, which I was not able to fully trace to a concrete unauthorized-merge proof within the available context.

### Likelihood Explanation
Requires the attacker to already administer at least one GitHub organization/repository that is legitimately registered with Shipit (i.e., knows that org's configured `webhook_secret`) — this is a real but bounded precondition (multi-tenant Shipit installations commonly host many orgs with independent webhook secrets). No repository write access, session, or `ApiClient` token to the *victim* org is needed; only knowledge of one's own org's webhook secret, which is a much lower bar than compromising the victim.

### Recommendation
Cross-check that `repository.owner.login` (used to select the verifying secret) is consistent with the organization portion of `repository.full_name` before dispatching to handlers, or key `Handler#stacks`/`repository_name` resolution off the same verified identity used in `verify_signature`, rather than trusting an independent, unauthenticated-relative field in the payload body.

### Proof of Concept
1. Attacker administers `org-a`, a GitHub organization legitimately registered in Shipit's `secrets.yml`, and knows `org-a`'s `webhook_secret`.
2. Attacker crafts a JSON body for the `push` event:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...attackerchosen",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-secret, body)` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and the signature validates successfully.
5. `Shipit::Webhooks.for_event('push')` invokes `PushHandler.call(params)`, whose `stacks` resolves via `payload.dig('repository', 'full_name')` = `"org-b/victim-repo"`, finding and syncing a stack the attacker's org has no relationship to, using the attacker-supplied `after` SHA.

        params do
          requires :ref

        end

            .where(branch:)
