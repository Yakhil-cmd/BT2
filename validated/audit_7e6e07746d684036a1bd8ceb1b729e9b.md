### Title
Webhook signature verification is keyed off an attacker-controlled organization field decoupled from the repository actually acted upon - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify a webhook against by reading an untrusted field out of the incoming JSON payload, while the event handlers that actually mutate state key off a *different* field of the same payload to resolve the target repository/stack. If any organization configured on the Shipit instance has no `webhook_secret` set (an explicitly optional setting), an attacker can pick that organization to satisfy signature verification and then smuggle an arbitrary `repository.full_name` for the handlers to act on.

### Finding Description
`verify_signature` derives the GitHub App/organization to check against from the payload itself, before/independently of validating the payload's authenticity: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params`, which is populated from the attacker's own JSON body (`params.dig('repository','owner','login')` or the `organization.login` fallback) — there is no independent, verified source for which org's secret should apply.

The actual signature check in `GithubApp#verify_webhook_signature` short-circuits to `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

The docs confirm `webhook_secret` is optional per-organization, and multiple organizations can be configured independently, each with its own secret: [4](#0-3) 

Meanwhile, once signature verification passes, `create` re-parses the raw body and dispatches it to handlers, which independently resolve the target `Repository`/`Stack` from a *different* payload key (`repository.full_name`), decoupled from the `repository_owner` used for the signature check: [5](#0-4) [6](#0-5) 

This breaks the binding: `organization authenticated (repository_owner used to pick the webhook_secret) == repository written (repository.full_name resolved by the handler)`. An attacker only needs the payload's `repository.owner.login`/`organization.login` to name an org with no secret configured, while `repository.full_name` names a completely different, secured repository whose stacks they want to affect (e.g. triggering `GithubSyncJob`, fabricating commit `status`, `check_suite`, or `membership` events that create/modify `Team`/`User` records, per the tested handlers).

### Impact Explanation
This crosses a repository/authentication boundary explicitly called out as in-scope: unauthenticated forgery of GitHub webhook events for a repository the attacker does not control, as long as *any* configured organization on the instance lacks a webhook secret. Depending on which handlers are registered, this can be used to inject fabricated `push`/`status`/`check_suite` events that drive `GithubSyncJob`, `RefreshCheckRunsJob`, commit status creation, or team/user membership changes for a victim stack — i.e., an unauthorized influence on deploy-relevant state without any credential, matching the "unauthorized deploy" / cross-repository-write class of impact.

### Likelihood Explanation
Exploitability is conditional: it requires that the Shipit deployment configures at least one GitHub organization without a `webhook_secret` (explicitly supported and documented as optional) alongside at least one other, secured organization whose repositories the attacker wants to target. Where that precondition holds, exploitation requires no credentials at all — just a crafted POST to the public `/webhooks` endpoint with mismatched `repository.owner.login`/`organization.login` vs. `repository.full_name`.

### Recommendation
Verify the webhook signature using the actual raw payload against every configured GitHub App/organization webhook secret that could plausibly apply (or better, use a single/global secret verification independent of attacker-supplied org fields), and only after successful verification, resolve `repository_owner`/`repository.full_name` for dispatch. Do not let an unauthenticated field in the payload select which secret is used to authenticate that same payload. Additionally, do not allow `verify_webhook_signature` to silently pass (`return true`) for organizations lacking a secret when other organizations on the same instance do have one configured; a per-installation default-deny or a strong warning against mixed configurations should be enforced.

### Proof of Concept
1. Instance configures two organizations under `Shipit.github`: `org-nosecret` (no `webhook_secret`) and `org-secured` (with a `webhook_secret`, owning the victim stack/repository `org-secured/victim-repo`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "org-nosecret" },
    "full_name": "org-secured/victim-repo"
  },
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` computes `repository_owner` = `org-nosecret`, calls `Shipit.github(organization: "org-nosecret").verify_webhook_signature(...)`, which returns `true` immediately because that org has no `webhook_secret` (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
4. `create` dispatches the full JSON body to `Shipit::Webhooks.for_event('push')`, whose handler resolves the target via `payload.dig('repository','full_name')` = `org-secured/victim-repo` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), enqueuing a `GithubSyncJob` for the victim stack despite the request never being validated against `org-secured`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
