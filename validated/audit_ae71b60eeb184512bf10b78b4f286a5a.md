### Title
Webhook signature verification is keyed to an attacker-controlled field, allowing cross-organization event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC signature against using a field taken from the *unverified* JSON payload itself. In a multi-organization Shipit deployment (`Shipit.github_organizations` returning more than `[nil]`), an attacker who legitimately controls the webhook secret for their own GitHub organization/App installation can craft a payload whose signature-selection field points at their own org (so verification passes) while other payload fields (e.g. `repository.full_name`) point at a stack/repository belonging to a *different* organization. This breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the raw, unauthenticated request body: [1](#0-0) 
and uses it to pick the `GitHubApp` instance (and thus the `webhook_secret`) that the signature is checked against: [2](#0-1) 

`Shipit.github(organization:)` supports a per-organization secret config keyed by `github_organizations`: [3](#0-2) 

The HMAC check itself only proves that *some* field of the payload (`repository.owner.login` / `organization.login`) matches a known org's secret — it does not verify that the rest of the payload (the actual repository being referenced by handlers such as push/status/check_suite, e.g. `full_name`) belongs to that same organization. Since `verify_webhook_signature` signs/verifies the *entire* raw body, but the body's `repository_owner` field is exactly the value the attacker chooses to control which secret is checked, an attacker who owns one org's webhook secret can pick which secret validates their forged payload while embedding a different org's repository as the payload's actual target for the handler logic: [4](#0-3) 

This is the direct analog of the reported bug class: the field that GitHub's signature check is bound to (`repository.owner.login`, used only to pick the secret) is not the same field that downstream code trusts as the effective target of the action (repository/stack referenced by `full_name`, commit SHA, etc.), exactly like the Turnstile report where the registered recipient (verified action) diverges from the actual fee recipient (acted-upon field).

### Impact Explanation
If exploitable end-to-end, this would let an org that is a legitimate customer of a shared/multi-tenant Shipit instance forge push, status, or check_suite events for a *different* organization's repositories/stacks — e.g., triggering `GithubSyncJob`, injecting fabricated commit statuses, or manipulating check-run driven merge/deploy gating for a stack they do not own, purely because they hold the webhook secret for their own, unrelated GitHub App installation. That crosses the "cross-repository writes"/"unauthorized deploy" boundary described as High/Critical impact criteria.

### Likelihood Explanation
This requires: (1) the deployment to be configured with more than one GitHub organization/App (multi-tenant `secrets.github` keyed by org, per `github_organizations`), and (2) the attacker to already control a legitimate, valid webhook secret for at least one of the configured organizations (i.e., they are an authenticated tenant on the shared instance). Under the single-org (default) configuration documented in `docs/setup.md`, `github_default_organization` is `nil` and there is only one secret, so this scenario collapses to the normal case and is not exploitable. I could not fully confirm from the available index whether the `push_handler`/`status_handler`/`check_suite_handler` resolve the target `Stack` strictly by `repository.full_name` independent of the `repository.owner.login` used for secret selection — this would need to be verified in `app/models/shipit/webhooks/handlers/*.rb`, which I was not able to fully read before running out of tool calls.

### Recommendation
After verifying the signature, re-derive/validate that every organization-scoped field used later by handlers (`repository.full_name` owner segment, `organization.login`, etc.) is consistent with the `repository_owner` value that was used to select the verifying secret, and reject the webhook if they diverge. Alternatively, scope handler lookups (`Stack.find_by(...)`) to only repositories belonging to the same organization whose secret validated the payload.

### Proof of Concept
Conceptual (multi-org config required):
1. Deployment configures two orgs in `secrets.github`: `orga` and `orgb`, each with a distinct `webhook_secret`.
2. Attacker administers `orga`'s GitHub App and therefore knows `orga`'s `webhook_secret`.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: push` and a body where `repository.owner.login == "orga"` (so `verify_signature` selects and validates against `orga`'s secret, which the attacker computed correctly) but `repository.full_name == "orgb/victim-repo"`.
4. `verify_signature` passes (signature matches `orga`'s secret). The push handler then processes the event against `orgb/victim-repo`'s stack, using data the attacker fully controls, even though the attacker never had access to `orgb`'s webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
