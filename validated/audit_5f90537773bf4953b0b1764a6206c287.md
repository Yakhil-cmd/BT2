### Title
Cross-organization webhook forgery via signature-verification/repository-write mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret used to validate `X-Hub-Signature` based on `repository_owner`, a value read straight out of the untrusted JSON payload (`repository.owner.login`, falling back to `organization.login`). The actual repository that gets written to (synced, commits appended, stacks updated) is determined later by a *different* payload field, `repository.full_name`, consumed by `Handler#stacks`/`Handler#repository_name`. Because Shipit supports multiple configured GitHub organizations (`Shipit.github(organization: ...)`, see `config/secrets.development.shopify.yml`), an attacker who legitimately controls one low-trust configured organization (owns/knows its `webhook_secret`) can craft a payload whose `repository.owner.login` names their own org (so the signature check passes with a secret they know) while `repository.full_name` names a victim's actual tracked repository. The signature only proves the payload came from whoever holds the secret for the org named in `repository.owner.login`; it does not bind that identity to the repository object that `PushHandler`/`Handler#stacks` subsequently acts on.

### Finding Description [1](#0-0) 
`verify_signature` does:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where [2](#0-1) 
`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — fully attacker-controlled JSON content.

Downstream, `Handler#stacks` resolves the target using a different field: [3](#0-2) 
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
And `Repository.from_github_repo_name` splits this on `/` and looks up by `owner`/`name` independently: [4](#0-3) 

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack: [5](#0-4) 

**Binding broken**: *organization that authenticated (`repository.owner.login`, used to pick the verifying secret) ≠ repository that is written (`repository.full_name`, used to select the `Repository`/`Stack` to sync)*. HMAC-SHA1 over `raw_post` proves the request was signed by whoever holds the secret configured for the org named in `repository.owner.login` — it says nothing about which repository's `full_name` field is trusted. Nothing forces `repository.owner.login` to be a prefix of `repository.full_name`.

Before vs after the attacker's request:
- Before: attacker controls (or is a member of) Org `evil-org`, configured in `Shipit.github` with a known `webhook_secret`. Victim repo `victim-org/important-repo` is tracked by a Shipit stack, with its own distinct `webhook_secret` that the attacker does not know.
- Attacker sends a `push` event to `/github/webhooks` with body `{"repository": {"owner": {"login": "evil-org"}, "full_name": "victim-org/important-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen sha>"}`, signed with `evil-org`'s webhook secret.
- `verify_signature` computes `Shipit.github(organization: "evil-org").verify_webhook_signature(...)` — succeeds, because the attacker legitimately knows that secret.
- `PushHandler.call(params)` then resolves `Repository.from_github_repo_name("victim-org/important-repo")` and invokes `stack.sync_github(expected_head_sha: <attacker sha>)` on the victim's stack — a write the attacker was never authorized to trigger for that repository.

### Impact Explanation
This lets a party who only controls one (any) configured low-privilege GitHub organization/app installation forge sync events against any other tracked repository in the same Shipit instance, without ever proving control of the victim repository's own GitHub App/webhook secret. `sync_github` drives `GithubSyncJob`, which appends commits (`stack.commits.create_from_github!`) and can trigger `CacheDeploySpecJob`/continuous delivery machinery for the victim stack — i.e., unauthorized writes to the state of a repository/stack the attacker does not control, using an identity (their own org's secret) that was never scoped to that repository. This satisfies the "cross-repository writes" / unauthorized deploy-adjacent impact category, since it lets an unprivileged-relative-to-the-victim-repo actor inject fabricated sync/commit state and downstream deploy triggers for a stack they don't own.

### Likelihood Explanation
Requires the attacker to control (or know the webhook secret of) at least one GitHub organization/app installation configured in the same Shipit instance — a routine, low-privilege setup for any multi-tenant Shipit deployment (the engine explicitly documents multi-org config, see `config/secrets.development.shopify.yml`). No access to the victim's secret, `ApiClient` token, or repository write access is required — only a public HTTP POST to `/github/webhooks` with a crafted JSON body. Likelihood is high in any deployment that onboards more than one organization.

### Recommendation
Bind the field used to select the verifying secret to the same field used to resolve the target repository/stack: after signature verification, re-derive `repository_owner` from `repository.full_name` (the same field `Handler#repository_name` uses) rather than trusting `repository.owner.login`/`organization.login` independently, or explicitly assert `repository.full_name.downcase.start_with?("#{repository_owner.downcase}/")` before processing. Alternatively, look up the `Repository` record first (by `full_name`) and validate the signature using that repository's own owner-derived secret exclusively.

### Proof of Concept
1. Configure two orgs in Shipit, `evil-org` (attacker controls its GitHub App / knows its `webhook_secret`) and `victim-org` (attacker has no access), each tracked as separate stacks.
2. POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "evil-org" }, "full_name": "victim-org/important-repo" },
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
signed with `sha1=<HMAC-SHA1(evil-org's webhook_secret, raw_body)>` in `X-Hub-Signature`.
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "evil-org")` and validates successfully.
4. `PushHandler.call` resolves `Repository.from_github_repo_name("victim-org/important-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on the victim's stack — proving the attacker forged a state-mutating event against a repository/org whose secret they never possessed.
