## Analysis

The Base incident describes a temporary halt in block production caused by an internal bug that the team had to patch and redeploy — i.e., a liveness failure where the network momentarily could not confirm new blocks, even though no funds were at risk. The closest reachable analog in `ocore` is in the consensus/stability-determination code path that every unstable unit triggers when it is posted and validated, combined with the fact that any unhandled exception crashes the entire node process.

### Title
Unit-processing assertion failures in main-chain stability determination can crash every full node, halting confirmation of new units - ([File: main_chain.js])

### Summary
`main_chain.js`'s stability-determination routines (`determineIfStableInLaterUnits`, `findNextUpMainChainUnit`) enforce internal DAG invariants with hard `throw Error(...)` assertions (e.g. "not a single MC child?", "no best children of X?", "not a single mc tip") rather than graceful error handling. These routines run in the hot path of ordinary unit validation (`validateParents` in `validation.js` calls `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag` for every unit whose `last_ball` is not yet locally stable) and of unit writing (`writer.js` best-parent/level/witnessed-level cross-checks). Because `network.js` installs a global `process.on('uncaughtException', ...)` handler that re-throws to intentionally crash the process, any such assertion violation while processing a unit crashes the node. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Any unprivileged unit poster can broadcast a validly-signed unit whose `parent_units`/`last_ball_unit` DAG shape is accepted by the earlier structural checks (`validateParentsExistAndOrdered`, `validateParents`), yet still drives the deterministic-but-fragile stability algorithm into a state it treats as impossible. In `determineIfStableInLaterUnits`, the code assumes that querying `units` by `best_parent_unit=?` will always return exactly one row with `is_on_main_chain=1`, and throws a hard `Error` otherwise: [4](#0-3) 

The same class of "invariant must hold or crash" assertions exists in the main-chain walk (`no free units?`, `not a single mc tip`) and in `writer.js`, which independently recomputes best-parent/level/witnessed-level and calls `throwError` (a hard `throw` on the server) if its recomputation disagrees with what `validation.js` already computed: [5](#0-4) [6](#0-5) 

Because this logic executes for every posted unit that references a not-yet-stable `last_ball_unit`, and because `network.js`'s `handleJoint` invokes `validation.validate` synchronously inside the unit-processing pipeline, an exception thrown here is not caught as a normal validation error — it propagates to the global `uncaughtException` handler, which explicitly re-throws to crash the process: [7](#0-6) [3](#0-2) 

Since all full nodes run the identical deterministic algorithm over the identical DAG once the triggering unit propagates, a single crafted unit can crash every full node that processes it at roughly the same time, mirroring a network-wide "block production" halt.

### Impact Explanation
If such a unit propagates across the network, every full node (hub/witness/relay) that reaches the vulnerable code path crashes simultaneously via the `uncaughtException` handler, which is designed to terminate the process rather than degrade gracefully. This yields a network unable to confirm new units until operators manually detect, patch, and restart — directly matching the "block failure" class in the report (temporary confirmation halt requiring team intervention), without necessarily causing fund loss, matching the Medium severity of the source incident.

### Likelihood Explanation
Reaching one of these specific internal-invariant violations requires crafting a DAG/unit structure that survives all prior structural/semantic validation (`validateHashTreeParentsAndSkiplist`, `validateParentsExistAndOrdered`, `validateParents`, `validateWitnesses`) yet still produces a shape unanticipated by the stability-walk or best-parent-recompute code — a non-trivial but historically demonstrated class of bug in this codebase (note the accumulated hard-coded historical-unit "hacks" in `determineIfStableInLaterUnits` at lines 802-810, which show real past validation-error incidents of exactly this kind). [8](#0-7) 

### Recommendation
- Replace hard `throw Error(...)`/`throwError(...)` assertions in `main_chain.js` and `writer.js` consensus-critical paths with recoverable error handling (e.g., mark the unit as `known_bad`/reject it, or use `ifJointError`/`ifTransientError`) rather than crashing the whole process, when the violated condition is derivable from network-controlled DAG shape rather than pure internal programmer error.
- Add fuzz/property testing around `determineIfStableInLaterUnits`, `findNextUpMainChainUnit`, and `determineBestParent` with adversarially generated DAG shapes (multiple free tips, alt branches, mixed witness lists) to find inputs that violate the "exactly one MC child"/"exactly one best parent" invariants before they reach production.
- Consider isolating unit validation/consensus-walk logic in a subprocess or catching exceptions at the `handleJoint`/`saveJoint` boundary so a single malformed-but-signed unit cannot bring down the entire node process network-wide.

### Proof of Concept
Conceptually: an attacker composes a unit `U` whose `last_ball_unit` is not yet stable locally, and constructs (over time, as an ordinary unit poster) a DAG around it with alternate branches / free-unit structure engineered so that, when `validateParents` calls `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag(conn, last_ball_unit, objUnit.parent_units, ...)`, the internal query `SELECT unit, is_on_main_chain, main_chain_index, level FROM units WHERE best_parent_unit=?` returns zero rows, or more than one row with `is_on_main_chain=1`, tripping `throw Error("no best children of "+best_parent_unit+"?")` or `throw Error("not a single MC child?")` in `main_chain.js`. Once such a unit is broadcast, every full node that validates it hits the same deterministic code path and crashes via the global `uncaughtException` handler in `network.js`, halting confirmation of new units network-wide until the software is patched and nodes are restarted.
