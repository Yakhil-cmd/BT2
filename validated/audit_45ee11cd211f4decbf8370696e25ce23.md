### Title
Delimiter-injection in arbiter-contract hash binding allows content-boundary ambiguity - ([File: arbiter_contract.js])

### Summary
The OpenSSH advisory describes an authorization bypass caused by a list/field-delimiter (comma) that can appear inside attacker-controlled data (a certificate principal), letting the parser mis-split fields and defeat an intended restriction. The closest reachable analog in ocore is `arbiter_contract.getHashSrc()`, which builds the integrity-binding hash of an arbiter contract by joining several free-text, attacker-controlled fields with a fixed string delimiter `exports.DELIMITER = "[|#|]"`, with no check that the delimiter sequence is absent from those fields. [1](#0-0) [2](#0-1) 

### Finding Description
`getHashSrc()` concatenates `title`, `text`, `creation_date`, `payer_address`, `payer_name`, `arbiter_address`, `payee_address`, `payee_name`, `amount`, `asset` using `join(exports.DELIMITER)` (for contracts created after `NEW_HASH_DATE`): [3](#0-2) 

`title`, `text`, `my_party_name`, and `peer_party_name` are attacker-controlled free-form strings that are offered by the contract creator (`createAndSend`) and only checked to be non-empty strings/optional strings — never checked to exclude the literal delimiter sequence `"[|#|]"` — before being sent to the peer and hashed: [4](#0-3) 

Because the delimiter can legally occur inside `title` or `text` (and the party-name fields), an attacker who authors the contract (offeror side, reachable purely through the "sign"/"arbiter_contract_offer" device-message flow — no privileged role required) can construct two structurally different field sets whose `join(DELIMITER)` output is byte-identical, e.g. by shifting the delimiter boundary between `title` and `text` (`title="A[|#|]B", text="C"` vs. `title="A", text="B[|#|]C"`) while the SHA-256 hash computed via `getHash()` stays the same: [5](#0-4) 

This hash is trusted as a content-integrity anchor throughout the flow: `wallet.js` rejects a contract offer if `body.hash !== arbiter_contract.getHash(body)` both before and after swapping payer/payee roles, and the dispute-request handler in `wallet.js` recomputes the expected hash from decrypted contract content and compares it to `body.contract_hash`, which is in turn checked against `payload.contract_text_hash` inside a previously-signed on-chain unit: [6](#0-5) [7](#0-6) 

The hash also seeds the oscript data-feed name used by the shared address definition that actually pays out based on the arbiter's decision: `"CONTRACT_" + contract.hash` and `"CONTRACT_DONE_" + contract.hash` are embedded directly into the `["in data feed", …]` condition of the escrow address definition: [8](#0-7) 

Because the join is not injective (field-boundary ambiguity via delimiter injection), it is class-analogous to the OpenSSH bug: a "list/record separator" that is not excluded from attacker-supplied data allows semantically different inputs to be parsed/hashed identically, defeating a security-relevant binding.

### Impact Explanation
If two different `getHashSrc()` inputs (differing in how `title`/`text` are split, or differing in party names with the delimiter shifted) produce the same hash, `contract.hash` no longer uniquely identifies one specific set of contract terms. Since `contract.hash` is embedded as the on-chain data-feed name (`"CONTRACT_" + hash`) that the arbiter's decision unit writes to and that the escrow shared-address definition reads from, an attacker able to engineer such a collision between two contracts that share the same arbiter could cause the arbiter's single resolution unit to satisfy the `in data feed` condition for both escrow addresses, letting the wrong party claim escrowed funds — an AA/shared-address fund-loss scenario reachable purely from a paired-device contract-offer message, matching the required "AA fund loss" / "unauthorized spending" impact class.

### Likelihood Explanation
Exploitation requires the attacker to control the `title`/`text`/party-name fields of a contract they create (which is standard for the offeror in this flow) and to find two field partitions that hash-collide, i.e., a delimiter-boundary shift; this is a much weaker requirement than a full SHA-256 preimage/collision search because the attacker only needs the *pre-hash concatenation* to be identical, which is directly achievable by literally embedding `"[|#|]"` inside `title` and moving text between adjacent free-text fields. However, turning this into an actual double-payout requires the second, colliding contract to also be negotiated with the same arbiter and to reach the dispute/resolution stage, which needs additional off-chain social-engineering steps I could not fully verify from the code alone (e.g., whether the shared-address derivation or arbiter's per-contract bookkeeping introduces other implicit uniqueness checks I did not locate). I was not able to confirm within the available context whether the arbiter's dispute API or `arbiters.js`/arbstore server-side logic performs any additional uniqueness/idempotency check on `contract.hash` that would prevent two live contracts from sharing the same hash-derived feed name; this deserves confirmation in a live session before treating this as fully proven end-to-end.

### Recommendation
Reject (or escape) the delimiter sequence `"[|#|]"` inside `title`, `text`, `my_party_name`, and `peer_party_name` before hashing, or switch `getHashSrc()` to a length-prefixed / unambiguous encoding (e.g., hash each field separately and hash the concatenation of fixed-length digests, similar to `string_utils.getSourceString`'s approach of throwing on embedded join characters) so that no combination of user-controlled field values can produce a colliding pre-hash string for different logical inputs.

### Proof of Concept
1. Attacker (offeror) calls `arbiter_contract.createAndSend` with:
   - Variant A: `title = "Order#1[|#|]B"`, `text = "C"`, fixed `creation_date`, `amount`, `asset`, `arbiter_address`, `my_address`, `peer_address`.
   - Variant B: `title = "Order#1"`, `text = "B[|#|]C"`, same other fields.
2. Compute `getHashSrc()` for both: `[title, text, creation_date, payer_address, payer_name, arbiter_address, payee_address, payee_name, amount, asset].join("[|#|]")`. Because `"Order#1[|#|]B" + "[|#|]" + "C"` and `"Order#1" + "[|#|]" + "B[|#|]C"` produce the identical concatenated string, `getHash()` (SHA-256 of that string) is identical for both variants despite different intended `title`/`text` content.
3. Both variants pass the `body.hash !== arbiter_contract.getHash(body)` check in `wallet.js`'s `arbiter_contract_offer` handler since the hash matches the (differently-parsed) content.
4. If a second, independent contract is engineered (with matching amount/asset/addresses/arbiter but different title/text split) to reach the same hash, its shared-address definition embeds the same `"CONTRACT_" + hash` data-feed name as the first contract's escrow address, so a single arbiter resolution unit satisfies both `in data feed` conditions — enabling one arbiter decision to unlock two distinct escrows.

*(This PoC demonstrates the hash-collision mechanism concretely; full confirmation that this leads to actual double-payout in the shared-address escrow requires exercising the complete dispute/resolution flow, which I was not able to fully trace end-to-end from the indexed context alone.)*

```javascript
function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
```
