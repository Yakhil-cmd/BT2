### Title
Cross-organization webhook forgery via mismatched signing-key selection and repository binding - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), while the handlers that actually mutate state (`PushHandler`, `CheckSuiteHandler`, pull-request handlers, etc., via `Handler#repository_name`) resolve the target `Repository`/`Stack` from a *different* JSON field, `repository.full_name`. Because these two fields are independent and neither is cross-validated against the other, a party that legitimately possesses the webhook secret for *one* configured organization can forge a payload that is verified as coming from that organization but whose `repository.full_name` (and therefore the `Stack` acted upon) belongs to a completely different organization/repository configured on the same Shipit instance.

### Finding Description
`Shipit.github(organization: repository_owner)` is used to look up the per-organization `GithubApp` config (each org has its own `app_id`/`webhook_secret`, as shown in `config/secrets.development.shopify.yml`): [1](#0-0) [2](#0-1) 

`repository_owner` is read from `repository.owner.login` (or `organization.login`) — a field inside the same attacker-suppliable JSON body that is being verified: [2](#0-1) 

The HMAC signature (`verify_webhook_signature`) does bind the *entire raw body* to the chosen secret, so the body cannot be tampered with once the org is picked — but the org is picked from an attacker-controlled field before verification, and nothing later confirms that `repository.full_name`'s owner matches `repository.owner.login`: [3](#0-2) 

Once verified, the raw params are dispatched to handlers, all of which derive the target repository independently via `Handler#repository_name`, which reads `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

`PushHandler`, for example, uses this to look up all non-archived stacks on the matching branch and unconditionally trigger a GitHub sync with an attacker-supplied `expected_head_sha`: [5](#0-4) 

Because Shipit is explicitly multi-tenant at the webhook-secret level (distinct `app_id`/`webhook_secret`/`private_key` per organization, as seen in the sample secrets file), the entity legitimately entitled to know Org A's webhook secret (e.g., an admin who configured Org A's GitHub App in Shipit) is not entitled to act on Org B's repositories. This breaks exactly the binding described as in-scope: "an organization that authenticated versus the repository that is written."

**Equality that should hold, but doesn't:**
`organization whose secret produced a valid signature == organization owning the repository/stack the handler mutates`

**Before the crafted request:** Org A's secret can only be used to authenticate events genuinely originating from GitHub for Org A's own repositories (GitHub sets `repository.owner.login` and `repository.full_name` consistently and signs with the correct per-org secret).

**After the crafted request:** An actor holding only Org A's webhook secret submits a raw POST directly to `/webhooks` with `repository.owner.login = "orgA"` (so `verify_signature` selects and validates against Org A's secret) but `repository.full_name = "orgB/target-repo"`. The signature check passes (it only verifies the raw body against Org A's secret, which the attacker controls), and the dispatched handler (`PushHandler`, `CheckSuiteHandler`, PR handlers, etc.) resolves and mutates Org B's `Stack`/`Repository` records — a write that should have required Org B's own webhook secret.

### Impact Explanation
This allows an entity who is unprivileged with respect to Organization B (only privileged with respect to Organization A within the same Shipit instance) to trigger writes against Organization B's stacks — e.g., forcing `GithubSyncJob` runs with an attacker-chosen `expected_head_sha` on Org B's stacks via `PushHandler`, or scheduling check-run refreshes via `CheckSuiteHandler` — without ever possessing Org B's webhook secret or GitHub credentials. This is a cross-organization/cross-repository write performed purely by exploiting the mismatch between the authentication-selection field and the write-target field in the same unauthenticated-at-the-network-layer payload, matching the Critical "cross-repository writes" impact category.

### Likelihood Explanation
Likelihood is limited to environments where Shipit is configured with more than one organization/GitHub App (each with its own webhook secret) sharing the same Shipit deployment — a documented, supported configuration pattern. Any party who legitimately administers one such organization's GitHub App (and thus its webhook secret) can carry out this attack against any other organization/repository hosted on the same instance, without needing repository write access, an `ApiClient` token, or the target organization's secret.

### Recommendation
After signature verification, validate that the organization used to select the webhook secret (`repository.owner.login` / `organization.login`) matches the organization portion of `repository.full_name` (and any other repository identifiers used later by handlers) before dispatching to handlers. Reject the request if they diverge.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with distinct `webhook_secret` values (per `config/secrets.development.shopify.yml` pattern).
2. As an actor who knows `orgA`'s `webhook_secret` (e.g., the administrator who set up `orgA`'s GitHub App in Shipit), craft a push payload body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/target-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-30` selects `orgA`'s config via `repository_owner` (`repository.owner.login` = `orgA`) and the signature validates successfully.
5. `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) resolves stacks via `repository_name` = `repository.full_name` = `"orgB/target-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and triggers `stack.sync_github(expected_head_sha: "deadbeef")` on Org B's stack, even though the request was never signed with Org B's secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
