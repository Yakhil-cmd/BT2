### Title
Remote correspondent device can obtain silent, unconfirmed signatures on wallet funds via prosaic/arbiter contract "peer_device_address" bypass in signing confirmation logic - (File: wallet.js)

### Summary
The `getSigner().sign()` implementation in `wallet.js` is the code path used whenever a shared/multisig address must be co-signed by a remote paired device. It normally emits a UI event (`confirm_on_other_devices`, `confirm_contract_sign`, `confirm_contract_deposit`, `confirm_contract_claim`) so the user must approve any signing offer coming from a correspondent device before their key material effectively signs the proposed unit. However, when the requesting device address matches `peer_device_address` recorded for an existing `prosaic_contracts` / `wallet_arbiter_contracts` row for the address being signed, the code intentionally skips **all** of these confirmation events (`return cb(true)` at [1](#0-0) ), and the outer `async.series` callback (`wasConfirmationRequested`) then suppresses `confirm_on_other_devices` too ( [2](#0-1) ). This means once a device is recorded as a contract counterparty, any further "sign" offer it sends for that shared address is auto-signed without ever showing the human-readable transaction content to the user, which is the exact anti-pattern the analog report calls out (managing/using signing keys directly instead of surfacing a confirmation dialog with human-readable data).

### Finding Description
`sendOfferToSign`/the `sign` justsaying handler lets *any paired ("correspondent") device* request the current wallet to co-sign an arbitrary unsigned unit for a shared/multisig address that the local device is a member of [3](#0-2) . Validation of the unsigned unit's structure is done (payment outputs/inputs shape, hashes), but it does not check *values*, *destinations*, or *purpose* against what the human counterparty actually agreed to. When `getSigner()` is invoked to actually produce a signature for a remote device (`ifRemote`), it queries `prosaic_contracts` and `wallet_arbiter_contracts` for the shared address, and if the requesting `device_address` is the same as the already-recorded `peer_device_address`, the code assumes the transaction is part of an already-agreed-upon contract flow and does not fire any of the `confirm_contract_*`/`confirm_on_other_devices` UI events (`wallet.js` lines 2043-2096). This is a case where the wallet manages its own signing keys and produces valid signatures for a shared address on the say-so of a remote peer, without going through the "battle-tested user confirmation dialog" – directly analogous to the report's criticism of components performing signing operations without surfacing to the end user what is actually being signed.

### Impact Explanation
If a party is or becomes a recorded prosaic/arbiter contract peer for a shared address, the peer can, for the entire remaining lifetime of that shared address, submit `sign` requests for **any** unsigned unit spending from that address without triggering a confirmation prompt on the counterparty's device, as long as it is shaped as a valid payment. Because the check only compares device addresses (not transaction content, amount, or scope), this can be leveraged to obtain silent co-signatures for units that were never actually agreed upon (e.g. draining more funds than the contract terms, or moving funds to arbitrary destinations authorized by the shared-address definition but not by the human agreement), leading to unauthorized spending from the shared address funds.

### Likelihood Explanation
Exploitability requires the attacker to already be a correspondent device recorded in `prosaic_contracts`/`wallet_arbiter_contracts` (i.e., have previously engaged in a contract negotiation with the victim), which is attacker-controllable — any counterparty who trades with the victim through the prosaic/arbiter contract flow can subsequently send additional signing offers that bypass confirmation, so likelihood is moderate-to-high for anyone who has legitimately interacted with the victim once.

### Recommendation
Do not suppress confirmation dialogs purely based on `peer_device_address` matching. Instead, always surface the actual content of the unit being signed (amount, destination, asset) in a human-readable confirmation, and only auto-approve pre-agreed contract flows if the specific unit hash/content was cryptographically committed to during contract negotiation (e.g., compare against a previously stored expected payload/hash for that specific contract state, not just the peer device identity).

### Proof of Concept
1. Attacker device pairs with victim and establishes a prosaic or arbiter contract on a shared address (`prosaic_contracts`/`wallet_arbiter_contracts` row created with `peer_device_address` = attacker).
2. At any later point, attacker crafts a new unsigned unit spending from the shared address (different amount/destination than originally agreed) and sends it via the `sign` justsaying message (`wallet_general.sendOfferToSign` equivalent) referencing the shared address.
3. Victim's `getSigner().sign()` runs, finds a `prosaic_contracts`/`wallet_arbiter_contracts` row where `peer_device_address` equals the requesting device, and per [1](#0-0)  and [2](#0-1)  skips all `confirm_*` events.
4. The victim's device silently signs its portion of the multisig unit and returns the signature, without any popup shown to the user, allowing the attacker to complete the transaction.
