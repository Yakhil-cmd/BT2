### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` bypassing per-org webhook signature isolation - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the incoming payload was signed with the `webhook_secret` of the organization named in the attacker's own payload (`repository_owner`, taken from `params.dig('repository','owner','login')`), not that the payload is authorized for any particular `Commit`/`Stack`. `StatusHandler#process` then runs `Commit.where(sha: params.sha)`, a query unscoped by repository or organization, and mutates every matching commit's status regardless of which org/stack owns it, breaking the intended "signed-by-owning-org" binding.

### Finding Description
The binding the codebase implicitly relies on is:
`organization used to verify the signature (Shipit.github(organization: repository_owner))` == `organization owning every Commit record mutated by the handler`.

Trace:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `repository_owner` purely from attacker-controlled payload fields (`repository.owner.login` or `organization.login`, line 59-62), looks up `Shipit.github(organization: repository_owner)`, and validates the HMAC signature against that org's `webhook_secret`. This only proves the payload was signed by *some* configured org's secret that matches the attacker-supplied owner field — it says nothing about which `Commit`/`Stack` the payload's `sha` belongs to.
- `Webhooks::Handlers::StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. This query is global across the entire `commits` table, with no `stack_id`, no `repository`, no organization filter of any kind. `Commit#create_status_from_github!` (app/models/shipit/commit.rb:165-169) unconditionally creates/replicates a `Status` from the attacker-controlled payload attributes (`state`, `description`, `target_url`, `context`).
- Because `params.sha` is an arbitrary attacker-chosen string in the JSON body (not verified against any actual git object the attacker controls), an attacker who registers a webhook on their own low-privilege org repo (org-A, secret S_A) can sign a `status` event payload with `state: success` and any `sha` value with `S_A`, and if that `sha` happens to match a `Commit.sha` that belongs to a stack under org-B (a different, higher-value org configured via `Shipit.github(organization: 'org-B')`), the handler will write a new success `Status` onto org-B's commit.
- No other guard intervenes: `drop_unhandled_event` only checks that a handler exists for the event type; `ExplicitParameters` schema in `StatusHandler` only validates types/presence of `sha`/`state`/etc., not ownership; there is no `stack`/`repository` correlation check anywhere in the status-processing pipeline.

### Impact Explanation
A successful forged `success` status on a commit under an unrelated, higher-privilege org's stack can flip a blocking/required CI status, which per `Commit#deployable?` (app/models/shipit/commit.rb:227-229) and `Commit#blocked?` can make that commit appear deployable and unblock continuous delivery (`schedule_continuous_delivery`, lines 281-287) or unblock a manual deploy. This is a "payload for one repository mutating another's commit/stack" case explicitly listed as Critical impact — it lets a completely unrelated, unprivileged GitHub user forge CI/status state for another tenant's stack, potentially triggering deploys that should not occur, across the shared Shipit instance. Repeatable for any known/guessed 40-hex SHA of a commit already present in shipit's `commits` table (SHAs are often discoverable from public repos, PR pages, or the Shipit UI itself), and is not confined to a single stack — any stack sharing the colliding SHA is affected.

### Likelihood Explanation
Preconditions: a multi-org/GitHub App Shipit deployment (`Shipit.github_organizations` with per-org `webhook_secret`s) where at least one org is attacker-controllable (attacker can register a webhook on a repo/org they own or control) and the target commit's SHA is knowable (e.g., copied from a public GitHub repo, from the target stack's public commit list in Shipit's UI, or from a PR). The attacker needs zero Shipit credentials — only the ability to configure a webhook on their own repository (standard GitHub permission for any repo owner) and send/replay a signed payload. This is fully within the described "unprivileged attacker" capability set and requires no secret guessing beyond a real commit SHA, which is often public information.

### Recommendation
Scope the commit lookup by the verified organization/repository instead of a bare SHA match. `StatusHandler#process` (and similarly `CheckRunHandler`/other handlers using the same pattern) should join through `Stack`/`Repository` and filter by the repository identified in the verified payload (e.g., `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner, name: repository_name })`), ensuring the org that signed the request actually owns the repository/stack the commit belongs to. `Handler` base class or `WebhooksController` should thread the verified `repository_owner`/`repository` down to handlers so every handler can enforce this invariant, not just trust `params.sha` globally.

### Proof of Concept
Minitest plan (test/controllers/webhooks_controller_test.rb or test/models/webhooks/handlers/status_handler_test.rb style):
1. Configure two `GitHubApp` entries in secrets/test config, `org-A` (secret `S_A`) and `org-B` (secret `S_B`), matching `test/dummy/config/secrets_double_github_app.yml` pattern.
2. Create `stack_b` under `org-B` with a `Commit` `commit_b` with `sha = "deadbeef...".ljust(40,'0')` and no existing statuses (`commit_b.status.state` == `"unknown"`).
3. Build a `status` webhook JSON body with `repository.owner.login = "org-A"`, `sha = commit_b.sha`, `state = "success"`.
4. Sign the raw body with `S_A` (org-A's secret) and POST to `/webhooks` with header `X-Github-Event: status` and computed `X-Hub-Signature`.
5. Assert response is `200 OK` (not `422`), i.e., `verify_signature` accepted it using org-A's secret.
6. Reload `commit_b` and assert `commit_b.status.state == "success"` — i.e., an org-A-signed payload mutated org-B's commit status, violating `Shipit.github(organization: repository_owner) == organization owning Commit`.
