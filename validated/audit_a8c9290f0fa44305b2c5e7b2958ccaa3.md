### Title
Webhook signature verification is keyed on `repository.owner.login` while event processing trusts the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) taken straight from the untrusted JSON body. `GithubApp#verify_webhook_signature` then unconditionally accepts the request (`return true unless webhook_secret`) whenever that particular organization has no `webhook_secret` configured — which the project's own setup docs describe as optional. Every downstream event handler, however, resolves the actual `Stack`/`Repository` to act on using a *different* field of the same attacker-controlled payload: `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb`, `push_handler.rb`, the `pull_request/*` handlers). Because the field used to pick the verification key is never checked for consistency with the field used to pick the target repository, an attacker can forge a payload whose `owner.login` points at an org with no `webhook_secret` (bypassing signature verification) while `repository.full_name` points at a completely different, "protected" org/repo that Shipit tracks.

### Finding Description
The relevant binding that should hold is: **the organization whose secret verified the request == the organization/repository whose Stack the handler acts on.**

- Verification side:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

Since `repository.owner.login` and `repository.full_name` are two independent JSON fields in a request body that the attacker fully controls (this is a raw unauthenticated POST to `/webhooks`, not a real GitHub-originated request), there is no requirement that they be consistent. Documentation and fixtures confirm multi-organization installs are supported and that `webhook_secret` is optional per organization (`docs/setup.md`, `config/secrets.development.shopify.yml`), so it is realistic for at least one configured organization to have no secret while others do.

### Impact Explanation
If any organization configured in `Shipit.github` has a blank `webhook_secret`, an unauthenticated attacker can:
1. Set `repository.owner.login` (or top-level `organization.login`) to that unprotected org, causing `verify_webhook_signature` to short-circuit to `true` regardless of the (missing/garbage) `X-Hub-Signature` header.
2. Set `repository.full_name` to `victim-org/victim-repo`, a repository tracked under a *different*, properly secret-protected organization.
3. Trigger any webhook handler for that repo: force a `push` to make Shipit `sync_github` a stack, forge `status` updates on commits (`app/models/shipit/webhooks/handlers/status_handler.rb`-style handlers keyed the same way), fabricate `pull_request`/`check_suite` events that open/close/archive review stacks, or create arbitrary `Team`/`User` records via `membership` events — all scoped to repositories the attacker has no legitimate access to.

This breaks the authentication boundary the whole webhook signature mechanism exists to enforce, letting an unprivileged, unauthenticated actor manipulate stack/commit state for repositories they do not control — satisfying the "authentication bypass" / "unauthorized" criteria for a Critical/High severity finding.

### Likelihood Explanation
Exploitability depends entirely on the deployment having at least one configured GitHub organization without a `webhook_secret`. This is not a hypothetical edge case: the setup guide explicitly labels `webhook_secret` as "(optional)" (`docs/setup.md`), the shipped example secrets templates leave it `nil` by default, and Shipit is designed to support multiple organizations simultaneously (`test/dummy/config/secrets_double_github_app.yml`). Any team running a multi-org Shipit instance where even one org skipped configuring a webhook secret (e.g., a low-value/staging org) exposes every other org's repositories to this forgery, with zero credentials or session required — this is reachable directly at `POST /webhooks`.

### Recommendation
- Require `webhook_secret` for every configured GitHub App/organization (fail closed instead of `return true unless webhook_secret`), or at minimum warn/refuse startup if any org lacks one.
- After signature verification, re-derive the acting organization from the *same* field used to select the secret, and cross-check it against `repository.full_name`'s owner before dispatching to handlers — i.e., enforce `repository.owner.login == full_name.split('/').first` and that this matches the org whose secret validated the signature.
- Consider verifying the signature using a secret bound to the resolved `Repository`/`Stack` itself (via `full_name`) rather than a value taken from an unauthenticated field of the payload, closing the "chain ID"-style mismatch entirely.

### Proof of Concept
Preconditions: Shipit configured with two orgs, e.g. `unprotected-org` (no `webhook_secret`) and `victim-org` (has `webhook_secret`), and a tracked `Repository`/`Stack` for `victim-org/victim-repo`.

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef   (arbitrary/invalid)

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "unprotected-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
- `verify_signature` calls `Shipit.github(organization: "unprotected-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` immediately regardless of the bogus signature header [2](#0-1) .
- `PushHandler#process` then resolves `repository_name` from `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, looks up that `Repository`'s stacks, and calls `stack.sync_github(expected_head_sha: params.after)` for the victim's stack [4](#0-3)  — despite the request never being signed by `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
