## Title
Webhook signature verification silently no-ops when an organization is configured without a `webhook_secret`, letting an unauthenticated attacker impersonate GitHub for that organization - (File: `lib/shipit/github_app.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` instance to validate a webhook against using an **unauthenticated field from the webhook body itself** (`repository.owner.login` / `organization.login`), then delegates the actual cryptographic check to `GitHubApp#verify_webhook_signature`. That method contains an unconditional escape hatch: `return true unless webhook_secret`. Because Shipit's own documented multi-org configuration schema allows `webhook_secret` to be `nil` per organization (see `config/secrets.development.example.yml`), any organization onboarded without an explicit `webhook_secret` will accept **any** payload claiming to belong to it, with no signature check at all.

### Finding Description
The webhook signature binding that Shipit's own design assumes is: *"a GitHub organization has authenticated this payload" == "the payload's HMAC signature was verified against that organization's secret."* This binding is broken: [1](#0-0) [2](#0-1) 

`repository_owner` is read directly from the (attacker-controlled, unverified at this point) request body, and used to pick which `GitHubApp` configuration - and therefore which secret - to validate against: [3](#0-2) 

The actual verification method is: [4](#0-3) 

Line 77 (`return true unless webhook_secret`) means: if the organization named in the attacker-supplied payload maps to a `GitHubApp` config that has no `webhook_secret` set, `verify_webhook_signature` returns `true` regardless of the (missing, wrong, or absent) `X-Hub-Signature` header. `before_action :verify_signature` then does nothing to stop the request (`head(422) unless verified` is simply skipped because `verified` is `true`), and `create` proceeds to dispatch the forged payload to real handlers: [5](#0-4) 

Once past this check, an attacker with no GitHub credentials, no Shipit session, and no `webhook_secret` can drive any registered webhook handler with fully attacker-chosen JSON, for the org whose secret is unset: [6](#0-5) 

Concretely reachable, unprivileged effects include:
- `Handlers::StatusHandler` - forge a `success` commit-status webhook for any commit under that org's repos, which Shipit uses as a CI gate before allowing/auto-triggering deploys (`ci.require` checks driven by these commit statuses).
- `Handlers::PushHandler` / `PullRequest::*Handler` - fabricate push/PR events to create commits, open/merge review stacks, or move merge-queue state.
- `Handlers::MembershipHandler` - create arbitrary `Team`/`User` records on the fly (`test/controllers/webhooks_controller_test.rb:129-148` demonstrates this is a real side effect of the `membership` event).

This mirrors the donation-attack report's bug class exactly: a value used for both routing/selection ("which org's trust boundary applies") and later relied upon as if independently authenticated, when in fact the thing that was supposed to bind the payload to that trust boundary (the HMAC signature) is not actually enforced for that class of input (orgs with `webhook_secret: nil`).

### Impact Explanation
This escalates unauthenticated attacker-controlled payloads into privileged internal state changes without any credential: forged commit-success statuses can clear CI-gating requirements that stacks rely on before an (auto-)deploy is triggered, and forged `push`/`pull_request`/`membership` events mutate authorization-adjacent data (teams, users, merge/review-stack state). Per the engine's own multi-org example (`config/secrets.development.example.yml`), leaving `webhook_secret` unset for an org is an explicitly supported, documented configuration shape - not a deviation from how the engine is meant to be mounted - so this is a defect in the engine's own trust-binding logic (`lib/shipit/github_app.rb` line 77), not a hosting misconfiguration outside scope.

### Likelihood Explanation
Medium-High. Any Shipit installation that configures one or more GitHub organizations without a `webhook_secret` (a state the code and shipped example config explicitly support) is exploitable by simply POSTing to the public `/github/webhooks` (or equivalent mounted) endpoint with a JSON body naming that organization - no signature, no token, no session required. The only precondition is one org lacking `webhook_secret`, which the codebase treats as a normal, first-class case rather than an error.

### Recommendation
Remove the `return true unless webhook_secret` short-circuit in `GitHubApp#verify_webhook_signature`; instead, either require every configured organization to have a non-blank `webhook_secret` at boot (raise a configuration error if missing), or default to rejecting (`false`) when no secret is configured, so the presence of a valid signature is always mandatory rather than optional based on attacker-suppliable data.

### Proof of Concept
1. Configure two GitHub orgs in `secrets.yml`, one (`victim-org`) with no `webhook_secret` set (a valid documented configuration).
2. As an unauthenticated attacker, `POST /github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<any known commit sha in a victim-org repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {"owner": {"login": "victim-org"}, "full_name": "victim-org/app"}
}
```
No `X-Hub-Signature` header (or any garbage value) is needed.
3. `verify_signature` calls `Shipit.github(organization: "victim-org").verify_webhook_signature(...)`; because `victim-org`'s `webhook_secret` is blank, this returns `true` unconditionally (`lib/shipit/github_app.rb:77`).
4. `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler`, which records the forged `success` status against the target commit exactly as if GitHub had sent it, satisfying `ci.require` gating for that stack without any real CI having run.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
