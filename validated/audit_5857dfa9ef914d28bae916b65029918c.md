### Title
Cross-organization commit-status forgery via `status` webhook - unscoped `sha` lookup breaks the organization/repository binding ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` binds signature validation to whichever GitHub organization is named in the payload (`repository.owner.login` / `organization.login`), then resolves and runs a handler using a completely different, attacker-controlled field of the same payload. For the `status` event, `Shipit::Webhooks::Handlers::StatusHandler#process` never re-derives or checks the repository/stack that the signature was verified against — it looks up commits by `sha` alone, across every stack in the whole Shipit instance. This breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC against using `repository_owner`, taken from the JSON body itself: [1](#0-0) [2](#0-1) 

Shipit explicitly supports multiple, independently configured GitHub organizations sharing one Shipit instance, each with its own `webhook_secret` chosen by that organization's own GitHub App administrator when they create the app: [3](#0-2) [4](#0-3) [5](#0-4) 

Once the signature is accepted, the controller dispatches the raw, attacker-controlled JSON to every registered handler for the event, with no additional per-handler check that the payload's target repository matches the organization the signature was verified against: [6](#0-5) 

For the `status` event, the handler is: [7](#0-6) 

`process` runs `Commit.where(sha: params.sha)` — a query with **no scoping to a repository, stack, or organization at all** — and then calls `commit.create_status_from_github!(params)` for every matching commit anywhere in the database. This is unlike every other handler (`PushHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`), which all resolve `stacks`/`repository` from `payload.dig('repository', 'full_name')` via `Shipit::Repository.from_github_repo_name`: [8](#0-7) 

Since the field used to select the verifying secret (`repository.owner.login`) and the field that determines what gets mutated (`sha`, with no repository field required at all) are independent, an attacker who legitimately controls one onboarded GitHub organization (and therefore knows that organization's `webhook_secret`, which they themselves chose when creating their GitHub App per the setup docs) can sign an arbitrary JSON body with their own secret while setting `repository.owner.login` to their own org (so `verify_signature` passes) and `sha` to a commit SHA belonging to a **different** organization's stack. `StatusHandler` will happily create a `Status` record for that foreign commit.

### Impact Explanation
Writing a forged `Status` on a foreign commit directly feeds Shipit's deploy/merge automation: [9](#0-8) 
- `Status#state == 'success'` transitions the commit's `state`, and `add_status` calls `stack.schedule_merges` for `pending`/`success` transitions, which enqueues `ProcessMergeRequestsJob` for the **victim's own stack** — the merge-queue owner never issued this event.
- `commit.status`/`deployable?` are used to gate both manual and continuous deployment (`Commit#schedule_continuous_delivery`, `Stack#next_commit_to_deploy`, `Stack#deployable?`), so injecting a forged `success` status can make a previously non-deployable commit deployable, and — combined with `continuous_deployment: true` — trigger an actual deploy of attacker-chosen code to a stack the attacker does not control: [10](#0-9) [11](#0-10) 
- Because `ProcessMergeRequestsJob` merges any pending merge request once `all_status_checks_passed?`, a forged required-context success status can also cause an unauthorized merge: [12](#0-11) 

This falls squarely under "unauthorized deploy, rollback or merge," matching the Critical impact bucket in the rules.

### Likelihood Explanation
Exploitation only requires the attacker to control (be the admin of) one legitimate GitHub organization already onboarded onto a multi-tenant Shipit instance — a scenario the engine explicitly documents and supports (`config/secrets*.yml`, `docs/setup.md` "Using Multiple Github Applications", `test/dummy/config/secrets_double_github_app.yml` with `OrgOne`/`OrgTwo`). No repository write access, Shipit session, or `ApiClient` token to the *victim's* organization is needed — only the attacker's own, legitimately-issued `webhook_secret`. The forged HTTP POST to `/webhooks` is a single unauthenticated (from Shipit's perspective, "unprivileged for the target org") request with a known-good HMAC.

### Recommendation
`StatusHandler#process` (and any similarly unscoped handler) must resolve the repository from `payload.dig('repository', 'full_name')` the same way `PushHandler`/`PullRequest` handlers do, and must reject/ignore the event unless that repository's owning organization matches the organization whose secret verified the request. More generally, `WebhooksController#verify_signature` should pass the verified organization down to handlers (or handlers should re-derive and assert it) so no handler can act on a commit/stack/repository outside the organization bound to the signature.

### Proof of Concept
1. Attacker is the GitHub App administrator for `OrgTwo`, legitimately configured in Shipit's `secrets.yml` (multi-org setup) with `webhook_secret = S2`, which the attacker chose themselves when creating the App.
2. Attacker finds/knows the commit `sha` of an undeployed commit in `victim-org/victim-repo`, a completely unrelated stack hosted on the same Shipit instance, whose `shipit.yml` requires CI context `ci/required`.
3. Attacker builds a `status` webhook payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "OrgTwo" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S2, body)>` using their own known secret `S2`.
5. POST to `/webhooks` with header `X-Github-Event: status`.
6. `verify_signature` resolves `Shipit.github(organization: "OrgTwo")` and validates successfully against `S2`.
7. `StatusHandler#process` runs `Commit.where(sha: "<victim commit sha>")`, finds the commit under `victim-org/victim-repo`, and calls `create_status_from_github!`, creating a `success` status for `ci/required` on a commit the attacker never had access to — potentially unblocking deploy/merge for that stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
