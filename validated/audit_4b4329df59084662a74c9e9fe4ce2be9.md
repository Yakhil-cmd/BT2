### Title
Uncaught `throw Error("not 1 template")` in `definition template` authentifier evaluation crashes node on malformed unit - ([File: definition.js])

### Summary
The CVE describes a crash in `mod_authz_svn` when a client references a non-existent repository URL while in-repo authz rules are active — an unhandled lookup-miss on attacker-supplied input causes a process crash (DoS). The analog in ocore is the `'definition template'` operator evaluator, which assumes a referenced template unit always has exactly one stable `definition_template` message and `throw`s an uncaught `Error` otherwise, reachable by any unit poster who signs with (or is validated against) an address definition using this operator.

### Finding Description
When validating authentifiers of an author whose address definition (or a nested/attested address definition) contains a `['definition template', ['unit', {...}]]` clause, `evaluate()` queries the DB for the referenced template unit's stable `definition_template` payload: [1](#0-0) 

If the referenced `unit` does not exist, is not yet stable before `last_ball_mci`, or (due to a race/edge case) has more than one matching row, `rows.length !== 1` and the code executes `throw Error("not 1 template")` synchronously inside the `conn.query` callback, instead of calling `cb2(false)` or otherwise failing validation gracefully — mirroring the SVN bug where a lookup miss on attacker-controlled input crashes the handler rather than being rejected cleanly.

This code path is reached from `validateAuthor` → `validateAuthentifiers` in `validation.js`, which invokes `Definition.validateAuthentifiers` **without** a surrounding `try/catch`: [2](#0-1) 

Because the `throw` occurs inside an asynchronous DB-query callback (not inside a synchronous try/catch frame), it becomes an uncaught exception in Node.js rather than a value returned to `callback`. Compare this to `signed_message.js`, where the equivalent call is explicitly wrapped in `try/catch` specifically to guard against such exceptions: [3](#0-2) 

No such protection exists for the unit-validation path in `validation.js`.

### Impact Explanation
An unprivileged unit poster can construct and broadcast a unit whose author (or a co-author/nested address referenced via `'address'`/`'attested'`) uses an address definition containing a `'definition template'` clause that points at a unit which does not have exactly one stable `definition_template` message before the last ball. When any full node attempts to validate this unit's authentifiers, it hits the uncaught `throw`, which (absent an enclosing `try/catch` and depending on the process's uncaught-exception handling) can crash the node process handling the incoming unit — a denial-of-service against every full node that processes the malicious unit, potentially halting confirmation of new units across the network, directly analogous to the referenced CVE's crash-on-lookup-miss behavior.

### Likelihood Explanation
Likelihood is high for triggering the code path itself: any address whose definition contains `'definition template'` referencing a not-yet-stable, missing, or duplicated template unit will hit this line during normal authentifier validation of an incoming unit — no special privileges are needed, only crafting a definition and referencing unit combination and getting the unit accepted into the DAG/mempool for validation. The main uncertainty (not fully verifiable from source alone) is whether a higher-level process-wide handler (e.g., domain or `uncaughtException` listener in `network.js`) intercepts the exception before the process terminates, which would downgrade impact from a crash to a stalled/erroring connection; this should be confirmed against the full `network.js` uncaught-exception handling logic.

### Recommendation
Replace the `throw Error("not 1 template")` in the `'definition template'` case of `evaluate()` (both in `validateDefinition` and `validateAuthentifiers` in `definition.js`) with a graceful failure path (e.g., `cb2(false)` / `cb("template not found")`), matching the pattern used elsewhere in the same function for missing definitions (`ifDefinitionNotFound`). Additionally, wrap the `Definition.validateAuthentifiers`/`validateDefinition` invocation sites in `validation.js` (`validateAuthor`, asset-condition evaluation) in `try/catch` consistent with the protection already present in `signed_message.js`, so that any unexpected internal `throw` is converted into a validation failure rather than an uncaught exception.

### Proof of Concept
1. Attacker creates address A whose definition is `['definition template', ['unit', {}]]` where `unit` points to a real, existing unit U that either: (a) has no `definition_template` app message, or (b) has more than one (e.g., two authors each posting a `definition_template` payload in the same unit, if permitted by other validation rules), so the `SELECT payload FROM messages ...` query returns 0 or 2 rows.
2. Attacker posts a new unit signed by address A (with any authentifier), broadcasting it to the network.
3. Full nodes receiving the unit call `validateAuthor` → `Definition.validateAuthentifiers` → `evaluate()` on the `'definition template'` branch; the query resolves with `rows.length !== 1`, causing `throw Error("not 1 template")` inside the query callback in `definition.js` at the cited lines, uncaught by `validation.js`'s `validateAuthentifiers` wrapper, producing a runtime crash/DoS on nodes processing the unit.
