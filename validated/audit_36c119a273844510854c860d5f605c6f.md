This confirms the multi-org configuration design and the exact mismatch in field usage between `WebhooksController#verify_signature` and `Handler#repository_name`/`OpenedHandler#repository`.

### Title
Cross-tenant webhook forgery via unbound `repository.owner.login` vs `repository.full_name` fields - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) using `params.dig('repository','owner','login')`, but the pull-request/push/check_suite handlers resolve the target `Repository` using the independent `repository.full_name` field. Nothing in the request path enforces that these two fields describe the same organization, so any org validly registered in Shipit's multi-tenant `github:` config can forge a signature over a payload naming a different org's repository.

### Finding Description
The claimed binding is: `organization_that_signed_request (derived from params.dig('repository','owner','login'))` == `organization_that_owns_target_repository (derived from params.dig('repository','full_name').split('/').first)`. This must hold for HMAC verification to actually authenticate "this webhook is authorized to mutate this repository's Shipit state," but the code never checks it.

`WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), fetches the org's `GitHubApp` via `Shipit.github(organization: repository_owner)`, and validates `X-Hub-Signature` against that org's `webhook_secret` [1](#0-0) [2](#0-1) . `GitHubApp#verify_webhook_signature` performs a straightforward HMAC-SHA1 comparison keyed on that org's configured `webhook_secret` [3](#0-2) .

The signature check only proves "the request body was signed with `attacker-org`'s webhook secret." It does not constrain the content of the rest of the JSON body. Once verification passes, `Shipit::WebhooksController#create` dispatches the full, attacker-controlled `params` hash to the registered handler for the event [4](#0-3) . `Handler#repository_name` and `Handler#stacks` resolve the target Repository purely from `payload.dig('repository','full_name')` [5](#0-4) , and `OpenedHandler#repository` does the same via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5) . `Repository.from_github_repo_name` simply splits the string on `/` and does a `find_by` lookup with no ownership cross-check [7](#0-6) .

Shipit explicitly supports configuring multiple, independently-secreted GitHub orgs under one instance via `secrets.yml`'s multi-org schema (`docs/setup.md` "Using Multiple Github Applications"; `test/dummy/config/secrets_double_github_app.yml`) [8](#0-7) . In that deployment shape, an attacker who legitimately owns `attacker-org` (onboarded into the same Shipit instance with a real `webhook_secret`) can:
1. Compute a valid `sha1=` HMAC over an arbitrary JSON body using their own real `attacker-org` webhook secret.
2. Set `repository.owner.login` = `"attacker-org"` (so `verify_signature` picks the correct/attacker's own secret and passes) while setting `repository.full_name` = `"victim-org/victim-repo"`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, action `"opened"`.

`verify_signature` succeeds because it only checked the `attacker-org` secret against `attacker-org`'s own valid signature. `OpenedHandler#repository` then resolves `victim-org/victim-repo` from the database and, if that repository has review-stack auto-provisioning enabled, `ReviewStackAdapter#find_or_create!` provisions a `ReviewStack` scoped to the victim's repository — a record write for a repository whose organization never authenticated the request.

No other guard intervenes: `drop_unhandled_event` only checks the event type is registered [9](#0-8) ; the `ExplicitParameters` schema on `OpenedHandler` only validates types/presence of fields, not cross-field ownership [10](#0-9) ; `Repository` validations only constrain `owner`/`name` character sets, not which org may reference which repo [11](#0-10) .

### Impact Explanation
A cross-tenant write: an attacker who is a legitimate tenant of a shared, multi-org Shipit instance (owns `attacker-org` with a genuine registered `webhook_secret`) can forge webhook events that are attributed to `victim-org/victim-repo`, triggering `ReviewStack` (and, for other handlers, `Stack`/commit/status/PullRequest) creation or mutation for a repository belonging to a different, non-consenting organization on the same instance. This matches the "payload for one repository mutating another's stack/commit/task" Critical category. The attack is fully repeatable against any repository tracked in the shared Shipit instance and is not limited to `pull_request`/`opened` — `push`, `status`, and `check_suite` handlers derive their target repository the same way, via `Handler#repository_name`, so the same organization/repository mismatch reaches `GithubSyncJob` enqueuing, commit status writes, and check-run refreshes for arbitrary tracked repositories.

### Likelihood Explanation
This requires the specific deployment shape where Shipit is configured with the multi-org `github:` schema and hosts at least two mutually distrusting organizations, one of which is the attacker's own onboarded org with a real `webhook_secret`. Given that shape (which the engine explicitly documents and supports as a first-class feature), the attacker's cost is trivial: they already legitimately know their own org's webhook secret (it's their own GitHub App), and computing an HMAC-SHA1 over an arbitrary body is a single line of code. No Shipit session, API token, or victim secret is needed. It is fully repeatable and scriptable against any repository name known to the attacker.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization used to select/verify the webhook signature matches the owner segment of `payload.dig('repository','full_name')` (and `organization.login` where applicable) before dispatching to any handler; reject the request (422) on mismatch.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "signature valid for attacker-org does not authorize writes on victim-org's repository" do
  secrets = ActiveSupport::OrderedOptions.new
  secrets.github = {
    "attacker-org" => { webhook_secret: "attacker-secret" },
    "victim-org" => { webhook_secret: "victim-secret" }
  }.with_indifferent_access
  Shipit.stubs(:secrets).returns(secrets)

  victim_repo = shipit_repositories(:shipit) # owner: "victim-org", name: "victim-repo"
  victim_repo.update!(owner: "victim-org", name: "victim-repo", review_stacks_enabled: true, provisioning_behavior: :allow_all)

  body = pull_request_opened_payload
  body["repository"]["owner"]["login"] = "attacker-org"      # signing org == attacker
  body["repository"]["full_name"] = "victim-org/victim-repo" # target repo == victim
  json = body.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "attacker-secret", json)

  @request.headers["X-Github-Event"] = "pull_request"
  @request.headers["X-Hub-Signature"] = signature

  assert_difference -> { Shipit::ReviewStack.where(repository: victim_repo).count }, 1 do
    post :create, body: json, as: :json
  end
  assert_response :ok
  # Assert on the equality that should have held but didn't:
  # signing_org ("attacker-org") != target_repo_owner ("victim-org")
  # yet the request was accepted and a ReviewStack for victim_repo was created.
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
