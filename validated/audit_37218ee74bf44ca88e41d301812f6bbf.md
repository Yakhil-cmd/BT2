## Analysis Result

A concrete analog to the reported bug class ("draining funds using tokens approved for spending") exists in this codebase's swap path.

### Title
Missing owner/authority binding on `input_token_account` in `Swap` allows draining any account for which the signer holds SPL delegate approval - (File: `programs/cp-swap/src/instructions/swap_base_input.rs`)

### Summary
`deposit.rs` and `withdraw.rs` both explicitly bind the user's token accounts to the transaction signer via Anchor's `token::authority = owner` constraint [1](#0-0) , but the shared `Swap` accounts struct used by both `swap_base_input` and `swap_base_output` has no such binding on `input_token_account`/`output_token_account` — it is declared only as `#[account(mut)]` with `payer: Signer<'info>` as a separate, unrelated field [2](#0-1) .

### Finding Description
The instruction handler calls `transfer_from_user_to_pool_vault` using `ctx.accounts.payer` as the CPI `authority` and `ctx.accounts.input_token_account` as the `from` account [3](#0-2) . Anchor never verifies that `input_token_account.owner == payer.key()`. The only enforcement of authority happens inside the SPL `TransferChecked` CPI itself in `utils/token.rs` [4](#0-3) , which accepts either the account's direct owner **or an approved delegate** with sufficient `delegated_amount` as a valid signer.

This means any transaction signer who happens to hold an SPL `Approve` delegation on someone else's token account (e.g., a dangling/unrevoked approval granted for another integration, a relayer/permit-style flow, or a max-uint approval habit common among token holders) can pass that victim's token account as `input_token_account`, sign as `payer`, and set their own wallet as `output_token_account`. The pool will pull the victim's approved tokens into the vault and pay the swap proceeds to the attacker, exactly mirroring the Dexible root cause: a contract path that trusts "does this signer have spending rights over the presented account" without confirming the account actually belongs to that signer's own funds/intent.

### Impact Explanation
Any token balance for which a victim has an outstanding SPL delegate approval (regardless of why it was granted, or to whom) can be swapped out and redirected to an attacker-controlled account in a single transaction, with attacker-chosen `output_token_account`. This is concrete theft of user funds, matching the "unauthorized privileged effect / theft of user funds" acceptance criteria.

### Likelihood Explanation
Outstanding token delegations are common in the wild (many wallets/dApps leave standing approvals). No cooperation from the pool or Raydium is required — the attack is a single `swap_base_input`/`swap_base_output` call with attacker-chosen accounts and data, reachable by any unprivileged swapper, satisfying the "strongest reachable path from a single submitted transaction" validation bar.

### Recommendation
Add an explicit ownership/delegate-authority check in the `Swap` accounts struct (or in the handler) that constrains `input_token_account`'s effective spending path to the invoking `payer`, e.g. `token::authority = payer` analogous to `deposit.rs`/`withdraw.rs`'s `token::authority = owner` constraint, or explicitly reject transfers where `input_token_account.owner != payer.key()` (i.e., disallow delegate-based swaps entirely) unless delegate-based swaps are an intended, clearly scoped feature.

### Proof of Concept
1. Victim previously issues an SPL `Approve` for `delegate = D` on their `input_token_account` (for any unrelated reason/dApp) with some non-trivial `delegated_amount`.
2. Attacker, controlling keypair `D`, submits `swap_base_input` with: `payer = D` (signer), `input_token_account = victim_account`, `output_token_account = attacker_account`, other accounts (vaults, mints, pool_state) chosen legitimately for the target pool.
3. `transfer_from_user_to_pool_vault` succeeds because `D` is a valid delegate authority per SPL Token semantics [5](#0-4) ; Anchor never checked that `input_token_account` belongs to `payer`.
4. Swap output is transferred to `attacker_account` via `transfer_from_pool_vault_to_user`, completing the theft of victim's approved token balance.

pub fn transfer_from_user_to_pool_vault<'a>(
    authority: AccountInfo<'a>,
    from: AccountInfo<'a>,
    to_vault: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new(
            *token_program.key,
            token_2022::TransferChecked {
                from,
                to: to_vault,
                authority,
                mint,
            },
        ),
        amount,
        mint_decimals,
    )
}
