## Title
Signature verification keyed on attacker-controlled `organization`/`repository.owner.login` field allows forging webhook events for a different, victim repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This is the same root-cause pattern as the Otter Audits finding: a value is used to select the cryptographic material that is supposed to bind the request to its true origin, but the actual data acted upon is a *different* field in the same, otherwise-unauthenticated payload, and nothing ties the two together. In the Solana report, `prepare_market_order` derived the `transfer_authority` PDA from a hash that excluded `refund_token`, so the field controlling fund destination was never covered by the derivation used to authorize the action. In Shipit, `WebhooksController#verify_signature` selects *which* organization's `webhook_secret` to check against using `repository_owner` (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), but the event handlers act on a *different* field of the same payload - `repository.full_name` / `sha` / etc. - which is never cross-checked against the organization whose secret validated the request.

### Finding Description
`WebhooksController#verify_signature` computes: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`GithubApp#verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for that organization: [2](#0-1) 

Per the setup docs and secrets templates, `webhook_secret` is explicitly **optional**: [3](#0-2) 

Because the webhook secret is per-organization, and the organization used for verification is picked from `repository.owner.login` inside the same unauthenticated JSON body the attacker controls, an attacker who knows (or targets) any single configured organization with no `webhook_secret` set can send a raw, unsigned POST to `/webhooks` where:
- `repository.owner.login` == the org with no secret (verification trivially passes), while
- `repository.full_name`, `sha`, `ref`, `after`, etc. reference a completely different, victim organization/repository that *does* have a secret configured.

The event handlers never re-check that the acted-upon repository belongs to the organization that was actually verified:
- `PushHandler#process` looks stacks up purely by `branch`/`stacks` scope and calls `stack.sync_github(expected_head_sha: params.after)`: [4](#0-3) 
- `StatusHandler#process` writes a GitHub-origin commit status onto any local `Commit` matching `params.sha`, with no repository/org check at all: [5](#0-4) 

Both handlers derive their target `stack`/`Stack.where(...)` scope from `Shipit::Webhooks::Handlers::Handler`'s `stacks` helper based on `repository.full_name`, not from `repository_owner`/the org whose secret validated the HMAC. This breaks the binding: **organization that authenticated ≠ repository that is written**.

### Impact Explanation
Forged `status` events can flip commit-status/check state that Shipit's `ci.require`/`merge` gating relies on (`DeploySpec#required_statuses`, `MergeRequest#all_status_checks_passed?`) which feeds continuous-deployment and auto-merge logic: [6](#0-5) , [7](#0-6) . Forged `push` events can trigger `GithubSyncJob`/`sync_github` against a stack unrelated to the attacker's own (possibly-secretless) organization. Depending on `continuous_deployment`/merge-queue configuration on the victim stack, this can escalate to an **unauthorized deploy or unauthorized merge** — matching the "High/Critical: unauthorized deploy, rollback or merge" impact bucket, without the attacker ever holding an `ApiClient` token, a Shipit session, or the victim org's `webhook_secret`.

### Likelihood Explanation
Requires only: (1) at least one organization configured in `Shipit.github` without a `webhook_secret` (explicitly documented/templated as optional, so a common real-world configuration for single-org or low-security setups), and (2) the ability to send an arbitrary unauthenticated POST to the public `/webhooks` endpoint, which is exposed by design (no auth beyond the signature check it defeats). No repository write access, GitHub App keys, or Shipit accounts are needed — only knowledge of the target stack's repo full name/branch/SHA, which is public information for public repos or guessable/observable for others.

### Recommendation
Do not select the verification secret from attacker-supplied payload fields that are also used to identify the target repository/stack. Either:
- Require `webhook_secret` to be mandatory for every configured organization (reject requests / fail closed instead of `return true unless webhook_secret`), and
- After verifying the signature for organization X, assert that the repository/organization the handlers act on (`repository.full_name`'s owner, or `organization.login`) is actually owned by X before dispatching to handlers, rejecting any payload where these disagree.

### Proof of Concept
1. Configure Shipit with two orgs: `attacker_org` (no `webhook_secret`) and `victim_org` (has `webhook_secret` set), each with a stack tracking their own repo, per `config/secrets.development.shopify.yml`: [8](#0-7) 
2. POST to `/webhooks` with header `X-Github-Event: status` and no/garbage `X-Hub-Signature`, body:
```json
{
  "repository": { "owner": { "login": "attacker_org" }, "full_name": "victim_org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "attacker_org")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured) — request passes with 200/204.
4. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) writes a fabricated `success` status onto the victim's real commit, potentially satisfying `ci.require` for `victim_org`'s stack and unblocking an automatic merge/deploy that the attacker never had permission to trigger.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
