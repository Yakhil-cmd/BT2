### Title
Weak-curve signature forgery in oscript pluggable `is_valid_sig`/`vrf_verify` authentication - (File: formula/evaluation.js, signature.js)

### Summary
`is_valid_sig` and `vrf_verify` are oscript functions available to AA authors and any unit/trigger sender, allowing an author to embed a caller-supplied PEM public key and verify a caller-supplied signature against it as a "proof of authorization" mechanism inside an AA. `signature.js` supports many different ECDSA curve OIDs, including cryptographically weak curves (56–112-bit security: `secp112r1`, `secp112r2`, `secp128r1`, `secp128r2`, `secp160k1/r1/r2`, `sect113r1/r2`, `sect131r1/r2`, various `wap-wsg-idm-ecid-wtls*` curves) as pluggable "algorithms," analogous to MySQL's pluggable authentication mechanism (CVE-2016-0639) where an alternate, insecure authentication plugin can be selected in place of a trustworthy one.

### Finding Description
`signature.validateAndFormatPemPubKey()` accepts a PEM-encoded key and looks up its OID against `objSupportedPemTypes` [1](#0-0) . This table includes numerous small/weak curves alongside `secp256k1`, `prime256v1`, etc. A newer allow-list, `objSafePemTypes`, restricts acceptance to only strong curves, but it is only enforced when `bPostPemCurvesFix` is true [2](#0-1) .

`bPostPemCurvesFix` is derived from `mci >= constants.pemCurvesFixMci` at the call sites in `formula/evaluation.js`'s `is_valid_sig` and `vrf_verify` handlers [3](#0-2) [4](#0-3) . For any AA execution whose evaluation `mci` is below `constants.pemCurvesFixMci`, or any code path/mode that fails to pass `bPostPemCurvesFix=true`, `validateAndFormatPemPubKey` and `verifyMessageWithPemPubKey` will accept and verify against a weak curve [5](#0-4) [6](#0-5) . Test fixtures in the repo demonstrate that signatures over curves such as `secp112r1/r2` and `secp128r1/r2` are accepted as valid by `is_valid_sig` [7](#0-6) [8](#0-7) .

This is the same bug-class hint as CVE-2016-0639: a pluggable/negotiable authentication mechanism silently permits selection of a weak or bypassable plugin, undermining the intended integrity/confidentiality/authorization guarantee. Here, an AA that uses `is_valid_sig(message, pem_key, signature)` (or `vrf_verify`) as an authorization gate — e.g., "release funds to whoever proves control of this pubkey" — can be tricked or naturally exercised with a caller-supplied `pem_key` on a weak curve. Because curves like `secp112r1` have only ~56-bit discrete-log security (broken by modern hardware within practical cost/time, unlike `secp256k1`'s 128-bit security), an attacker who does not actually control the intended private key can, in principle, recover it and forge a valid signature, bypassing the authentication check entirely.

### Impact Explanation
If an AA's oscript logic uses `is_valid_sig`/`vrf_verify` with an externally supplied or historically-fixed weak-curve PEM key as an authorization/oracle check (a documented, intended use case per the AA formula language), an attacker who forges a signature under a weak curve can satisfy that check without holding the real private key. Depending on the AA's design this can lead to unauthorized withdrawal of AA-held funds, bypass of a data-feed/oracle authenticity check driving fund release, or other AA state manipulation — i.e., concrete AA fund loss, matching the "unauthorized spending / AA fund loss" impact bar required by the validation criteria.

### Likelihood Explanation
Exploitability depends on:
1. Whether the AA's evaluation MCI is below `constants.pemCurvesFixMci` (grandfathered historical executions) or any other invocation path that omits `bPostPemCurvesFix`, and
2. An attacker being able to break the discrete log of the specific weak curve used (feasible for curves at 56–96-bit security with modest compute; harder but not impossible up to 112–131-bit curves).

Because the fix (`objSafePemTypes` allow-list gated by `bPostPemCurvesFix`) already exists in the codebase, current-time newly-triggered AA executions at MCIs at/after `pemCurvesFixMci` are protected; the residual risk is limited to (a) validation of historical/old signed packages or definitions still referencing pre-fix MCIs, and (b) any code path that constructs `objValidationState` for a formula evaluation without correctly computing/propagating `bPostPemCurvesFix` from the current MCI. I could not fully trace every call site that constructs `bPostPemCurvesFix` (e.g., in `formula/validation.js`, `aa_composer.js`, `main_chain.js`, `storage.js` all reference `pemCurvesFixMci`) to confirm whether any remaining live path miscomputes it; this needs further verification.

### Recommendation
- Confirm that `bPostPemCurvesFix` is computed strictly from the current evaluation MCI (or the relevant AA-trigger/unit MCI) in *every* call path that reaches `is_valid_sig`/`vrf_verify`/`validateAndFormatPemPubKey`, with no path defaulting to `false`/`undefined` for post-fix MCIs.
- Consider retroactively rejecting AA logic (at bytecode-validation time in `formula/validation.js`) that references `is_valid_sig`/`vrf_verify` with hardcoded weak-curve PEM keys, independent of the MCI-gated runtime check.
- Consider removing/deprecating support for curves below a fixed security threshold (e.g., <128-bit) from `objSupportedPemTypes` entirely rather than only from `objSafePemTypes`, to eliminate the parsing/acceptance path altogether.

### Proof of Concept
1. Author an AA that stores a `pem_key` (attacker- or user-supplied) and uses `is_valid_sig(trigger.data.message, state[pem_key_var], trigger.data.signature)` to gate a fund-release branch (this is a documented supported pattern, as shown by the test suite) [9](#0-8) .
2. Have the AA's fund-release check execute at an MCI below `constants.pemCurvesFixMci` (or via any path where `bPostPemCurvesFix` is not set true), using a weak curve like `secp112r1`.
3. Off-chain, recover the private key for the weak-curve public key via a feasible discrete-log attack (practical for ≤80–96-bit curves, and increasingly costly but documented as feasible for the smallest curves in this list).
4. Submit a trigger unit with a forged signature satisfying `is_valid_sig`, causing the AA to release funds to the attacker without possessing the originally intended private key.

Note: I was not able to fully enumerate every code path that constructs the `bPostPemCurvesFix` flag (references also exist in `formula/validation.js`, `aa_composer.js`, `main_chain.js`, and `storage.js`) within the available exploration budget, so I cannot confirm with certainty whether a currently-reachable (post-fix-MCI) bypass path still exists versus this being fully mitigated for all new AA executions going forward.

function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}

function validateAndFormatPemPubKey(pem_key, algo, handle, bPostPemCurvesFix) {

	if (!ValidationUtils.isNonemptyString(pem_key))
		return handle("pem key should be a non empty string");

	//we remove header and footer if present
	var contentAloneB64 = pem_key.replace("-----BEGIN PUBLIC KEY-----", "").replace("-----END PUBLIC KEY-----", ""); 
	
	//we remove space, tab space or carriage returns
	contentAloneB64 = contentAloneB64.replace(/\s/g, "");

	if (contentAloneB64.length > 736) // largest is RSA 4096 bits
		return handle("pem content is too large");

	if (!ValidationUtils.isValidBase64(contentAloneB64))
		return handle("not valid base64 encoding" + contentAloneB64);

	var contentAloneBuffer = Buffer.from(contentAloneB64, 'base64');

	if (contentAloneBuffer[0] != 0x30)
		return handle("pem key doesn't start with a sequence");

//we determine start and length of algo/curve identifiers
	if (contentAloneBuffer[1] <= 0x7F){
		if (contentAloneBuffer[2] != 0x30)
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 4;
		var identifiersLength = contentAloneBuffer[3];
	} else if (contentAloneBuffer[1] == 0x81){
		if (contentAloneBuffer[3] != 0x30) 
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 5;
		var identifiersLength = contentAloneBuffer[4];
	} else if (contentAloneBuffer[1] == 0x82){
		if (contentAloneBuffer[4] != 0x30) 
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 6;
		var identifiersLength = contentAloneBuffer[5];
	} else {
		return handle("wrong length tag");
	}

	//we decode the length of identifiers
	if (identifiersLength != 13 && identifiersLength != 16 && identifiersLength != 19 && identifiersLength != 20)
		return handle("wrong identifiers length" + identifiersLength);

	//we isolate the identifiers
	var contentAloneHex = contentAloneBuffer.toString('hex')
	var typeIdentifiersHex = contentAloneHex.slice(identifiersStart * 2, identifiersStart *2 + identifiersLength *2);

	if (!objSupportedPemTypes[typeIdentifiersHex])
		return handle("unsupported algo or curve in pem key");

	if (bPostPemCurvesFix && !objSafePemTypes.has(typeIdentifiersHex))
		return handle("unsupported curve after pem curves fix MCI");

	if (algo != "any"){
		if (algo == "ECDSA" && objSupportedPemTypes[typeIdentifiersHex].algo != "ECDSA")
			return handle("PEM key is not ECDSA type");
		if (algo == "RSA" && objSupportedPemTypes[typeIdentifiersHex].algo != "RSA")
			return handle("PEM key is not RSA type");
	}

	if (objSupportedPemTypes[typeIdentifiersHex].algo == "ECDSA" && objSupportedPemTypes[typeIdentifiersHex].hex_pub_key_length != (contentAloneHex.length - identifiersStart * 2 - identifiersLength *2 - 8))
		return handle("wrong key length");

	//we add back header and footer
	pem_key =	"-----BEGIN PUBLIC KEY-----" + "\n";
	pem_key += contentAloneB64+"\n";
	pem_key += "-----END PUBLIC KEY-----";
	return handle(null,pem_key);
}
