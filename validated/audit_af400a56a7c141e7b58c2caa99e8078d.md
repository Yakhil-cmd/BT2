### Title
Webhook signature is verified against the organization named in an attacker-controlled field, while the repository actually written to is taken from an unrelated attacker-controlled field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization secret to validate the `X-Hub-Signature` against using `repository_owner`, a value read straight out of the unauthenticated JSON body. The event handlers that actually perform state-changing work (`PushHandler`, `StatusHandler`, etc.) resolve the *target* repository/stack from a different field of the same unauthenticated body: `payload.dig('repository', 'full_name')`. Because Shipit supports multiple GitHub organizations each with its own independent `webhook_secret`, an attacker only needs to hold (or exploit the absence of) the secret for *any one* configured organization to have their signature accepted, then point `repository.full_name` at a stack belonging to a *different* organization to have the handler act on it. This is the same class of bug as the FeeManager report: the thing verified (organization identity) is not the thing acted upon (target repository/stack).

### Finding Description
`verify_signature` picks the signing secret this way: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository','owner','login')` or, if absent, `params.dig('organization','login')` — both fully attacker-supplied JSON fields with no relation enforced to the rest of the payload.

`Shipit.github(organization:)` supports one GitHub App configuration *per organization*, each with its own independent `webhook_secret`: [3](#0-2) 

and if a given organization's `webhook_secret` is blank, verification is a no-op that always passes: [4](#0-3) 

Once the signature "passes" for organization `X`, the handler dispatch (`Shipit::Webhooks.for_event(event)`) processes the full raw payload, and every handler resolves its target stack independently via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — not `repository_owner`: [5](#0-4) 

`PushHandler` then queues a real sync job against whatever stacks match that `full_name`: [6](#0-5) 

`StatusHandler` goes further and writes attacker-supplied fields (`state`, `target_url`, `description`, `context`) directly onto a `Status` for a commit resolved the same way, as shown by the existing test: [7](#0-6) 

Multi-organization configuration with per-org secrets is a documented, supported deployment mode: [8](#0-7) [9](#0-8) 

**Binding that should hold:** `organization whose secret authenticated the request == organization that owns the repository the handler mutates`.
**What actually holds:** `repository_owner (used only to pick a secret) != repository.full_name's owner (used to pick the mutated stack/commit)` — nothing in `WebhooksController` or `Handler` cross-checks these two attacker-controlled fields against each other.

### Impact Explanation
In a multi-org Shipit deployment, an attacker who can produce a valid signature for *any one* configured organization (e.g., because that organization's `webhook_secret` is unset, or because the attacker has legitimate webhook access to a low-trust org tracked by the same Shipit instance) can forge `push`/`status`/etc. events whose `repository.full_name` points at a stack belonging to a *different, higher-trust* organization. This lets the attacker:
- Force `GithubSyncJob` to run against an unrelated organization's stack (`PushHandler`), an unauthorized cross-organization action, and
- Directly inject a forged `success` commit `Status` (`target_url`, `state`, `description`, `context` are all taken verbatim from the payload) onto a real commit of a victim stack, which can satisfy "deployable" / required-status gating used by Shipit before allowing a deploy — i.e., an unauthorized deploy path.

This matches the rules' Critical/High impact bar: cross-repository writes and the ability to influence an unauthorized deploy, achieved without ever holding the target organization's real webhook secret.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured with multiple GitHub organizations (a documented, supported configuration), and (2) the attacker to control or bypass the webhook secret for at least one of the configured organizations (trivial if any org's `webhook_secret` is left blank, since `verify_webhook_signature` then always returns true). No session, API token, or repository write access to the *target* organization is required — only the ability to send an HTTP POST to the public `/webhooks` endpoint. This is realistic for organizations that onboard several GitHub orgs (e.g., a sandbox/low-trust org alongside a production org) into one Shipit instance.

### Recommendation
Bind the two identities together before dispatching to handlers: derive the organization used for signature verification from the *same* field the handlers use to resolve the target repository (`repository.full_name`'s owner segment), and reject the request if `repository.owner.login`/`organization.login` disagrees with the owner segment of `repository.full_name`. Additionally, treat a blank/absent `webhook_secret` for a configured organization as a misconfiguration to warn about loudly, rather than silently disabling signature verification for that organization.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` (tracks the sensitive stack `org-a/victim-repo`) and `org-b` (either has no `webhook_secret` configured, or the attacker knows `org-b`'s secret, e.g. because they administer that GitHub App installation).
2. Attacker POSTs to `/webhooks` with `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "org-a/victim-repo", "owner": { "login": "org-b" } }
}
```
   signed (or unsigned, if `org-b` has a blank secret) so that `X-Hub-Signature` validates for `org-b`.
3. `WebhooksController#verify_signature` computes `repository_owner = "org-b"`, loads `org-b`'s `GitHubApp`, and the signature check passes. [1](#0-0) 
4. `PushHandler#stacks` resolves `Repository.from_github_repo_name("org-a/victim-repo")` and enqueues `GithubSyncJob` for that stack — an action against `org-a`'s repository triggered using only `org-b`'s trust. [5](#0-4) [6](#0-5) 
5. The equivalent forgery against the `status` event directly writes `state`, `target_url`, `description`, `context` from the payload onto a real commit in `org-a/victim-repo`, as demonstrated by the existing test asserting these fields are copied verbatim from the payload. [7](#0-6)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
