### Title
`Api::CCMenuController#stack` bypasses `current_api_client.stack_id` scoping via unscoped `Stack.from_param!` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController` overrides the private `stack` helper to call `Stack.from_param!(params[:stack_id])` directly instead of the base controller's scoped `stacks.from_param!(params[:stack_id])`. This drops the `current_api_client.stack_id` restriction entirely, so any authenticated API client — even one scoped to a single stack — can read CC-menu deploy/task status XML for any stack on the instance.

### Finding Description
The binding that must hold: `stack == stacks.from_param!(params[:stack_id])` where `stacks` is `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) .

`Api::StacksController` respects this binding: `stack` is defined as `@stack ||= stacks.from_param!(params[:id])` [2](#0-1) .

`Api::CCMenuController` breaks it. Its `stack` method is `@stack ||= Stack.from_param!(params[:stack_id])` [3](#0-2) , which resolves against the entire `Stack` table, ignoring `current_api_client.stack_id` regardless of which permission scoping the client was issued.

Regarding the dual-authentication-path premise in the question: both code paths ultimately funnel through `ApiClient.authenticate(token)`, which calls `message_verifier.verify(token).to_i` against the same `Shipit.api_clients_secret`-derived verifier [4](#0-3) . The override `authenticate_api_client` in `CCMenuController` calls `ApiClient.authenticate(params[:token])` directly and falls back to `super` (Basic Auth) only if that fails [5](#0-4) ; the base's Basic Auth path also ultimately calls `ApiClient.authenticate(token)` inside the `BasicAuth.authenticate` block [6](#0-5) . There is no cryptographic-strength divergence between the two paths — both are `ApiClient.authenticate` calls against the identical verifier — so the "weaker of the two auth paths" framing does not hold as a distinct vulnerability. The actual, demonstrable defect is that whichever path sets `@current_api_client`, the `stack_id` restriction that `check_permissions!`/`stacks` scoping is meant to enforce (as used correctly in `Api::StacksController`) is never applied in `CCMenuController#stack`.

Attacker request: `GET /api/1/stacks/:owner/:repo/:env/cc.xml?token=<valid token for ANY stack-scoped ApiClient with read:stack>`. The `require_permission :read, :stack` before_action only checks `permissions.include?('read:stack')` on the client [7](#0-6)  — it does not check `stack_id`. `stack` then resolves via unscoped `Stack.from_param!`, returning any stack matching `:owner/:repo/:env`, not just the one the token was scoped to.

### Impact Explanation
An attacker holding any single valid `ApiClient` token with `read:stack` permission (even one deliberately scoped to a single stack via `stack_id`) can enumerate and read the CC-menu XML — deploy status, last deploy/rollback outcome — of every stack on the Shipit instance, including stacks belonging to repositories/orgs they have no authorization for. This is unauthenticated-for-that-resource read of stack/task state across tenants, matching the "unauthorized read of stack state" High-severity category. It is fully repeatable against arbitrary stacks by varying `:owner/:repo/:env` in the URL.

### Likelihood Explanation
Preconditions: attacker needs one legitimate `ApiClient` token with `read:stack` permission (the question notes even a self-issued, stack-scoped token qualifies). No GitHub secrets, sessions, or elevated roles are required. Cost is a single HTTP GET per target stack; fully repeatable and trivially automatable.

### Recommendation
Change `Api::CCMenuController#stack` to use the scoped lookup consistent with the base controller: `@stack ||= stacks.from_param!(params[:stack_id])`, removing the private unscoped override so `current_api_client.stack_id` restrictions are enforced identically to `Api::StacksController`.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "CC menu leaks stacks outside the api client's stack_id scope" do
  scoped_stack = shipit_stacks(:shipit)
  other_stack  = shipit_stacks(:shipit_translations) # a different repo/env
  api_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped-client',
    permissions: ['read:stack'],
    stack_id: scoped_stack.id
  )

  get :show, params: {
    stack_id: [other_stack.repository.owner, other_stack.repository.name, other_stack.environment].join('/'),
    token: api_client.authentication_token
  }

  # Binding under test: stack resolved by CCMenuController must equal
  # stacks scoped to current_api_client.stack_id, i.e. it should be nil/404
  # since other_stack.id != api_client.stack_id.
  assert_response :not_found # currently fails: returns 200 with other_stack's XML
end
```
This demonstrates that `current_api_client.stack_id` (`scoped_stack.id`) is never checked against the resolved `stack.id` (`other_stack.id`) in `Api::CCMenuController`, confirming the broken binding.
