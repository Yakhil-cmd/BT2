### Title
Cross-organization webhook forgery via self-selected signature verification key - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization secret to verify a webhook's HMAC signature against by reading the organization/repository owner login directly out of the **same unverified JSON body** it is about to validate. Once verified, the raw `params` (including the `repository.full_name` field, which is never cross-checked against the org used for verification) are handed to `Shipit::Webhooks` handlers, which resolve the target `Stack`/`Repository` purely from `repository.full_name`. In a multi-organization Shipit deployment (explicitly documented and supported — see `docs/setup.md` "Using Multiple Github Applications"), this lets a party who legitimately controls one org's GitHub App webhook secret forge events that are attributed to, and mutate, a *different* organization's repositories/stacks.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` runs `verify_signature` as a `before_action`: [1](#0-0) 

`repository_owner` — the value used to select which `Shipit.github(organization:)` (and therefore which `webhook_secret`) is used for HMAC verification — is derived from the request body itself: [2](#0-1) 

The signature check (`verify_webhook_signature`) simply HMACs the raw body with whatever secret corresponds to that self-declared organization: [3](#0-2) 

Critically, nothing ties the organization used to select the verification secret to the `repository.full_name` that the event handlers subsequently trust to resolve which `Stack`/`Repository` to act on. For example `PushHandler` and the base `Handler` class resolve the target purely from `repository.full_name` in the payload: [4](#0-3) [5](#0-4) 

This is the same bug class as the external report: a field used to determine which key/authority validates the payload is *not itself covered* by an independent binding to the field that the payload actually acts upon. In the Chainlink report, deprecated/mismatched interface functions let a source feed's payload fields diverge from what was actually signed/verified. Here, the "signing key selection" field (`repository.owner.login` / `organization.login`) and the "acted-upon" field (`repository.full_name`) are two different, independently attacker-controlled JSON paths inside one request body, and only the org-selection field influences which secret validates the signature — the acted-upon field is unconstrained.

Concretely, the broken binding (as an equality that should hold but doesn't) is:
`organization_whose_secret_verified_the_signature == organization_owning_the_repository_that_handlers_act_on`

Before the (hypothetical) fix, these are computed from two independently-forgeable fields of the same unauthenticated body; after a fix they would need to be the same field / cross-validated.

### Impact Explanation
Shipit explicitly supports hosting multiple GitHub organizations from one instance, each with its own `app_id`/`webhook_secret` (`docs/setup.md`): [6](#0-5) 

An attacker who legitimately administers a GitHub App installed on *their own* organization (Org A) — which is a normal, low-privilege action available to anyone who can create a GitHub App and have a Shipit admin install it for their org, entirely independent of Org B's resources — knows Org A's `webhook_secret`. They can send a POST to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) = `"OrgA"` so `verify_signature` fetches and validates against Org A's secret, which the attacker controls and can sign correctly, and
- `repository.full_name` = `"OrgB/target-repo"`, a repository/stack belonging to an entirely different organization tracked by the same Shipit instance.

Because the signature check only validates that *some* org's secret matches, not that the org matches the repository being acted upon, the forged event is accepted and dispatched to handlers that key off `repository.full_name`. For the `push` event this triggers `PushHandler#process`, enqueuing `stack.sync_github(expected_head_sha: ...)` for Org B's stack — an unauthorized cross-organization deploy-sync trigger initiated without ever knowing Org B's real webhook secret. Other handlers (`status`, `check_suite`, `pull_request` family) are similarly reachable and can flip CI/check state, archive/unarchive Review Stacks, or otherwise manipulate Org B's `Stack`/`PullRequest` records — all through a signature that never should have been considered valid for that repository. This matches the required impact bar: an unauthorized cross-organization write against Shipit-managed deployment state, mediated entirely by the engine's own signature-selection logic, without needing Org B's credentials, an `ApiClient` token, or Org B's `webhook_secret`.

### Likelihood Explanation
This requires:
1. A Shipit instance configured for multiple GitHub organizations (documented, supported configuration).
2. Attacker control of a legitimate GitHub App installation/webhook secret for *any one* of those organizations (their own org, not the target's) — a normal, unprivileged action for anyone who runs their own GitHub organization and asks/gets it added to the shared Shipit instance.
3. Knowledge of a target repository's `full_name` that is tracked as a `Stack` on the same instance — typically public information.

No repository write access, `ApiClient` token, `api_clients_secret`, GitHub App private key, or the target org's `webhook_secret` are required — only a webhook secret belonging to an unrelated org on the same instance. This is a realistic scenario for any shared/central Shipit deployment serving several organizations, which is exactly the deployment topology the docs advertise.

### Recommendation
Bind the organization used to select the verification secret to the actual field the handlers will act on, and reject events where they diverge:
- After selecting `repository_owner` and successfully verifying the signature, re-derive the owner from `repository.full_name` (the field handlers use) and assert it matches `repository_owner` before dispatching to handlers; reject (422) on mismatch.
- Alternatively, verify the signature against *every* configured organization's secret and only accept the match whose organization equals the owner encoded in `repository.full_name`, never trusting an org identifier the payload itself supplies as the sole selector without cross-checking against the resource being mutated.
- Add a regression test asserting that a payload signed with Org A's secret but referencing an Org B repository is rejected.

### Proof of Concept
1. Configure a Shipit instance with two orgs (`OrgA`, `OrgB`) per `docs/setup.md`'s multi-app format, each with its own `webhook_secret`, both with repositories tracked as `Stack`s.
2. As an attacker who is only an admin of `OrgA`'s GitHub App (their own org), know `OrgA`'s `webhook_secret`.
3. Craft a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "full_name": "OrgB/target-repo", "owner": { "login": "OrgA" } }
   }
   ```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>`.
5. POST to `/webhooks` with header `X-Github-Event: push`.
6. In `verify_signature`, `repository_owner` resolves to `"OrgA"` (from `repository.owner.login`), so `Shipit.github(organization: "OrgA")` is used and the signature validates successfully — even though the payload's `repository.full_name` names an `OrgB` repository.
7. `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` runs `PushHandler`, which resolves the `Stack` via `Repository.from_github_repo_name("OrgB/target-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` — an unauthorized action against `OrgB`'s stack triggered solely with `OrgA`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:

      webhook_secret:
      private_key:
