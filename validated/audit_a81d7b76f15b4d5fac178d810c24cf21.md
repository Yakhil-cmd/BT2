### Title
Stack-scoped API token can read build/deploy status of any other stack via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup helper with a version that resolves the stack directly from the request parameter, bypassing the `ApiClient`-scoping filter that `Shipit::Api::BaseController` enforces everywhere else in the API.

### Finding Description
`ApiClient` records can be scoped to a single stack (`belongs_to :stack, optional: true`) [1](#0-0) . The binding this scoping is supposed to enforce is: *the stack a token is authorized for* must equal *the stack the token's requests actually touch*. `Shipit::Api::BaseController` implements this equality via `stacks`/`stack`:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Every other API controller (e.g. `Api::TasksController`, `Api::StacksController`) relies on this inherited `stack`/`stacks` method, so a token scoped to stack A raises `ActiveRecord::RecordNotFound` (surfaced as 404) if it tries to touch stack B, because `stacks` is pre-filtered to `Stack.where(id: current_api_client.stack_id)`.

`Api::CCMenuController`, however, redefines `stack` to bypass that scoping entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

This calls `Stack.from_param!` directly on the unscoped `Stack` model instead of on the `stacks` (client-scoped) relation [4](#0-3) . The `require_permission :read, :stack` before_action only checks that the token has the `read:stack` permission string in `ApiClient#check_permissions!` [5](#0-4) ; it never checks *which* stack that permission applies to — that check is solely delegated to (and in this controller, skipped by) the `stack` method.

Root cause: `Api::CCMenuController#stack` resolves the ref (`:stack_id`) an attacker is *permitted by the URL path* to name against the global `Stack` table, rather than against the set of stacks the authenticated `ApiClient` is *authorized* for — breaking the equality `token.authorized_stack == stack_touched_by_request`.

### Impact Explanation
Any valid `ApiClient` token that has been deliberately scoped to a single stack (a common configuration for least-privilege integrations, e.g. a per-project CI status widget) can instead read the CCMenu XML (build activity, last build status/label/time, web URL) of **any** stack in the Shipit instance by simply supplying a different `stack_id` — including private/other teams' stacks that the token owner was never meant to see. This is an authorization-boundary crossing: an unprivileged, narrowly-scoped credential is used to read deploy/task state belonging to a different, unauthorized repository/stack. Per the engine's stated High-severity criteria this is "unauthenticated read of stack state, task streams or deploy output" relative to what the credential was actually authorized for.

### Likelihood Explanation
High. Exploitation requires only possession of any valid `ApiClient` token scoped to one stack — no privileged account, no signature forgery, no session, and no additional credentials are needed. The attacker only needs to change the `stack_id` route/query parameter of a request they are already entitled to make against their own stack.

### Recommendation
Make `Api::CCMenuController#stack` reuse the inherited, client-scoped lookup instead of querying `Stack` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that a stack-scoped `ApiClient` can only resolve to the stack it was actually granted (mirroring `Api::BaseController#stack`), and add a regression test asserting that a token scoped to stack A receives a 404 (or equivalent) when requesting `Api::CCMenuController#show` for stack B.

### Proof of Concept
1. Create two stacks, A and B.
2. Create an `ApiClient` scoped to `stack: A` with permission `read:stack` (mirrors fixture `here_come_the_walrus` used in `test/controllers/api/stacks_controller_test.rb` for scoped-client tests) [6](#0-5) .
3. Authenticate as that client and request:
   `GET /api/stacks/{B.to_param}/ccmenu` (i.e. `Api::CCMenuController#show` with `stack_id` = B's param) using the token generated for the client scoped to A.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly rather than `stacks.from_param!`, the request succeeds and returns stack B's build/deploy XML, even though the token is authorized only for stack A — contrast with `Api::StacksController#index`, which correctly returns 0 results for an out-of-scope repo when using the same scoped client [7](#0-6) .
