## Verdict: Valid vulnerability found

### Title
Global (non-account-scoped) `allow_missing_txn_authentication_key` check lets an unprivileged attacker admit multi-agent transactions with an unauthenticated secondary signer — ([File: aptos-move/framework/aptos-framework/sources/transaction_validation.move])

### Summary
`multi_agent_common_prologue` in Move only checks the secondary signer's real authentication key when the `secondary_signer_public_key_hashes[i]` entry is `Some`. When the Rust-side `PrologueBuilder` supplies `None` for a secondary signer (which happens whenever that signer's `AccountAuthenticator` is `NoAccountAuthenticator` or `Abstract`, since both map to `optional_auth_key() == None`), the Move code falls back to `allow_missing_txn_authentication_key(secondary_address)`. That helper is **not scoped to the specific `secondary_address`** for its first disjunct — it only checks a network-wide feature flag.

### Finding Description
Rust side (`PrologueBuilder::new`) builds the per-secondary-signer key-hash vector purely from each authenticator's `optional_auth_key()`: [1](#0-0) 

`AuthenticationProof::optional_auth_key()` returns `None` both for `NoAccountAuthenticator` and for `Abstract` authenticators: [2](#0-1) 

On the Move side, `multi_agent_common_prologue` handles a `None` entry by calling `allow_missing_txn_authentication_key(secondary_address)` instead of verifying any real key hash: [3](#0-2) 

That helper is defined as: [4](#0-3) 

The first disjunct, `features::is_derivable_account_abstraction_enabled()`, is a **global feature toggle with no relationship to `transaction_sender`/`secondary_address` at all**. Unlike the second disjunct (`account_abstraction::using_dispatchable_authenticator(transaction_sender)`, which is properly scoped per-account), the derivable-AA disjunct returns `true` for *any* address the moment the network-wide feature is enabled — including an ordinary Ed25519 account that never opted into account abstraction and has no relationship to derivable AA at all.

Meanwhile, for the actual sender/fee-payer paths, real AA authentication is performed at the VM layer via `dispatchable_authenticate`, but **only** when the authenticator is `AuthenticationProof::Abstract`: [5](#0-4) 

`NoAccountAuthenticator` produces `AuthenticationProof::None` (not `Abstract`), so it never goes through `dispatchable_authenticate`/`account_abstraction::authenticate` — there is no cryptographic check anywhere in the pipeline for it. The only gate is the Move-side `allow_missing_txn_authentication_key`, which — as shown — can be satisfied for an arbitrary, real, non-AA account purely because of a global feature flag.

Consequently, an attacker can:
1. Pick any existing on-chain account address `V` (the victim's normal account) that they do not control.
2. Build a `MultiAgent` (or `FeePayer`) transaction listing `V` as a `secondary_signer_address`, with `NoAccountAuthenticator` as `V`'s `AccountAuthenticator`.
3. Submit it as sender using their own key for the actual signature requirement.
4. `account::exists_at(secondary_address)` trivially passes (the account is real), and `allow_missing_txn_authentication_key(V)` returns `true` once `DERIVABLE_ACCOUNT_ABSTRACTION` is enabled network-wide — with no check that `V` is actually a derivable-AA account or opted into any abstraction scheme.
5. The prologue admits the transaction, and the entry function executes with a `&signer` for `V`, despite `V` never authorizing or authenticating anything.

### Impact Explanation
This breaks the core multi-agent invariant that every listed secondary signer address must present a verifiable key-hash / valid authentication. It allows unauthorized transaction execution under the wrong signer set — an attacker can invoke entry functions requiring a `&signer` for a victim account they do not control (e.g., functions gated on `signer::address_of` checks, capability withdrawals, approvals, etc.), which is exactly the "Unauthorized transaction execution ... under the wrong sender, signer set" admission-impact category.

### Likelihood Explanation
The only precondition is that the `DERIVABLE_ACCOUNT_ABSTRACTION` feature flag is enabled on the network (a normal, non-privileged feature state, not requiring any leaked key or governance action by the attacker). Given this flag exists to support a rolled-out AA capability, this is a realistic production configuration. The attack requires no privileged capability from the attacker — only knowledge of a target address and standard unprivileged transaction submission via mempool/REST.

### Recommendation
Scope `allow_missing_txn_authentication_key`'s derivable-AA disjunct to the specific account, analogous to the dispatchable-authenticator disjunct — e.g., verify that `secondary_address`'s authentication key was actually derived via the domain/derivable-abstraction scheme (or otherwise confirm the account is genuinely using derivable AA) before permitting a missing key hash. A global feature flag alone must never authorize skipping authentication for an arbitrary account address.

### Proof of Concept
1. Enable `DERIVABLE_ACCOUNT_ABSTRACTION` feature (assume enabled in target network, as is standard).
2. Craft `TransactionAuthenticator::MultiAgent { sender: <attacker's valid Ed25519 authenticator>, secondary_signer_addresses: vec![victim_address], secondary_signers: vec![AccountAuthenticator::NoAccountAuthenticator] }` over a `RawTransaction` whose entry function requires a `&signer` for `victim_address` (e.g., a transfer-from function).
3. Submit via REST/mempool as an unprivileged attacker.
4. Observe that `run_prologue` (via `PrologueBuilder`/`multi_agent_common_prologue`) does not reject the transaction because `secondary_signer_public_key_hashes[0] == None` and `allow_missing_txn_authentication_key(victim_address)` returns `true` purely from the global flag.
5. Confirm the transaction commits and the entry function executed with `victim_address`'s `&signer`, without any signature or authentication ever having been produced by the victim.

*Note: I could not directly confirm the exact match-arm behavior of `AccountAuthenticator::verify()` for `NoAccountAuthenticator` in `types/src/transaction/authenticator.rs` (the specific arm was not retrieved in full), though `number_of_signatures()` returning `0` and `to_single_key_authenticators()` contributing nothing for this variant strongly indicate it performs no cryptographic check. If this is incorrect and `verify()` actually rejects `NoAccountAuthenticator` at the signature-verification layer for non-degenerate cases, that would be an additional independent gate — but the Move-side logic itself remains unsound as described, since `allow_missing_txn_authentication_key` still fails to bind the missing-key exemption to the specific account's AA status.*
