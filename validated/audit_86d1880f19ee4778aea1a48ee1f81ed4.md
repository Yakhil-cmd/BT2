### Title
Webhook signature is verified against `repository.owner.login` while the acted-upon repository is selected by the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to validate the HMAC with based on `repository.owner.login` (or `organization.login`) extracted from the raw, unverified JSON body, but the webhook handlers that actually act on the payload (e.g. `PushHandler`, `CheckSuiteHandler` via `Handler#repository_name`) look up the target repository using the separate `repository.full_name` field from that same body. Because both fields live in the attacker-supplied payload and are read independently, the "organization whose secret authenticated the request" and "repository that is actually written to" are never bound together, breaking the equality the check is supposed to enforce.

### Finding Description
`verify_signature` resolves the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats an organization with no configured `webhook_secret` as automatically verified: [3](#0-2) 

Once `verify_signature` passes, `create` dispatches the raw parsed body to every registered handler for the event: [4](#0-3) 

But the base `Handler` class - used by `PushHandler`, `CheckSuiteHandler`, etc. - resolves the target repository from a *different* JSON key, `repository.full_name`, not from `repository.owner.login`/`organization.login` used for signature selection: [5](#0-4) [6](#0-5) [7](#0-6) 

Because `repository.owner.login` and `repository.full_name` are independent strings in the same forged JSON body, an attacker can set `repository.owner.login` to an organization that Shipit has *no webhook_secret configured for* (so `verify_webhook_signature` returns `true` unconditionally per L77 above, regardless of the `X-Hub-Signature` header), while setting `repository.full_name` to `victim-org/victim-repo`, a fully protected stack. The signature check "authenticates" the harmless organization, but the write/action is performed against the unrelated victim repository - precisely the analog of the `_maxSumOfPrices` bug, where a value is validated but a different, uncontrolled value is what actually gets acted on.

### Impact Explanation
This equals an authentication-bypass / unauthorized-write vector: the binding `organization_verified_by_signature == organization_of_repository_acted_on` does not hold. Concretely, `PushHandler#process` (chosen for the `push` event) will locate `victim-org/victim-repo`'s stacks and call `stack.sync_github(expected_head_sha: params.after)` with attacker-supplied `ref`/`after` values, without any valid signature from `victim-org`'s actual webhook secret. `CheckSuiteHandler` similarly acts on the victim's commits/stacks (`schedule_refresh_check_runs!`) despite the signature belonging to a different, unrelated organization. Any downstream consumer that syncs GitHub state or triggers CI-based automation for a stack believing it originated from a signed GitHub event is effectively spoofable, satisfying the "unauthorized deploy/rollback trigger" class of impact when continuous deployment or CI-driven automation is wired to these events.

### Likelihood Explanation
Requires only the ability to send an unauthenticated HTTP POST to the public `/webhooks` endpoint (no session, no `ApiClient` token, no repository write access) and knowledge that at least one configured GitHub organization in `Shipit.github_setup` lacks a `webhook_secret` (a very common configuration for internal/staging orgs, or for any organization whose secret is unset/blank). No GitHub credentials for the victim org are needed at all, since the check never verifies that the signing organization matches the repository being mutated.

### Recommendation
Bind the verification target to the same field that handlers use for repository resolution: derive the organization used to select the webhook secret from `repository.full_name` (splitting on `/`) rather than the separate `repository.owner.login`/`organization.login`, or explicitly assert `repository.full_name.split('/').first == repository.owner.login` before dispatching to handlers. Additionally, do not allow `verify_webhook_signature` to short-circuit to `true` when `webhook_secret` is blank if the resolved repository actually belongs to a differently configured, secret-bearing organization; consider requiring an explicit secret for every tracked organization/repository pair or rejecting cross-field mismatches outright.

### Proof of Concept
1. Configure Shipit with two orgs: `open-org` (no `webhook_secret` set) and `victim-org` (a tracked, secret-protected org with an existing stack `victim-org/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "victim-org/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
No `X-Hub-Signature` header, or any arbitrary value, is required.
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"open-org"`, fetches `Shipit.github(organization: "open-org")`, and `verify_webhook_signature` returns `true` because `open-org` has no `webhook_secret` (`lib/shipit/github_app.rb:77`).
4. `create` dispatches to `PushHandler`, whose `Handler#repository_name` reads `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, loading the actual victim stacks and invoking `stack.sync_github(expected_head_sha: "deadbeef...")` - an action on `victim-org` performed under a signature check that authenticated `open-org`, not `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers

        params do
          requires :ref
          requires :after
```
