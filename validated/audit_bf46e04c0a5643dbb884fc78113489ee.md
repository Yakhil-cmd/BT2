Based on my investigation, I found a concrete analog: the `reject_new_shared_address` device-message handler in `wallet.js`, which deletes a pending shared (multisig) address record by an attacker-supplied hash, with no check that the sending device is actually a party to that pending address.

### Title
IDOR in `reject_new_shared_address` device-message handler allows any paired device to delete another user's in-progress multisig address setup — ([File: wallet.js])

### Summary
The `reject_new_shared_address` case in the device-message dispatcher only validates that `body.address_definition_template_chash` is syntactically a valid hash, then calls `walletDefinedByAddresses.deletePendingSharedAddress()` unconditionally, deleting the referenced pending shared-address records without verifying that the sending device (`from_address`) is actually one of the members participating in that specific pending multi-device address.

### Finding Description
In the hub-message dispatch switch in `handleMessageFromHub`, the handler is: [1](#0-0) 

It performs only a format check (`ValidationUtils.isValidAddress`) on the `address_definition_template_chash` parameter, then calls `deletePendingSharedAddress`, which executes unconditional deletes keyed solely by that value: [2](#0-1) 

Unlike other multi-party flows in the same file — e.g. `validateAddressDefinitionTemplate`, which explicitly checks `arrDeviceAddresses.indexOf(from_address) === -1` to make sure the sender is a listed member device — this delete path performs no such membership check: [3](#0-2) 

Compare this to sibling handlers in the same switch (`prosaic_contract_update`, `arbiter_contract_update`), which correctly look up the referenced object by hash and then verify `from_address` against the stored owner/cosigner before allowing any state mutation: [4](#0-3) [5](#0-4) 

The `reject_new_shared_address` path skips this ownership/membership verification entirely — this is structurally the same bug class as the Chamilo IDOR: an object is deleted by supplying its identifier (a hash) via a message parameter, with no server-side check that the requester is authorized to act on that specific object.

### Impact Explanation
`reject_new_shared_address` is reachable from any device that is a "correspondent" (paired device) of the victim — it is not restricted to members of the specific shared-address-in-creation. An attacker who is paired with the victim for an unrelated purpose (e.g. a normal chat/wallet correspondent) can send this message with a `address_definition_template_chash` value belonging to a shared address the victim is setting up with someone else entirely, silently deleting the victim's `pending_shared_addresses` and `pending_shared_address_signing_paths` rows. This disrupts/aborts the victim's in-progress multisig (shared address) wallet-creation flow, a denial-of-service/griefing effect on address/wallet formation for other users, without their consent and without being a participant in that specific address.

### Likelihood Explanation
The attacker must already be a known correspondent (paired device) of the victim — this matches the "paired device" actor class explicitly permitted by scope. The `address_definition_template_chash` is a content-hash over the definition template; an attacker who is a correspondent of one of the participants, or who intercepts/observes it via chat/forwarding flows, can trivially construct and send this message. No signature or membership proof of the target address is required.

### Recommendation
Before calling `deletePendingSharedAddress`, look up the `pending_shared_address_signing_paths`/`pending_shared_addresses` rows for the given `definition_template_chash` and verify that `from_address` corresponds to one of the `device_address` values recorded for that pending template (mirroring the membership check already implemented in `validateAddressDefinitionTemplate`). Reject the deletion with an error if the sender is not a listed member device for that specific pending shared address.

### Proof of Concept
1. Device A (victim) initiates creation of a shared/multisig address together with Device B, producing a `pending_shared_addresses` record identified by `definition_template_chash = H`.
2. Attacker Device C, who is merely a paired correspondent of Device A for unrelated reasons (and knows or infers `H`, e.g. by observing forwarded template messages), sends a device message:
   `{ subject: "reject_new_shared_address", body: { address_definition_template_chash: H } }`
3. `wallet.js` validates only that `H` looks like an address (hash format) and calls `walletDefinedByAddresses.deletePendingSharedAddress(H)`.
4. This deletes the `pending_shared_address_signing_paths` and `pending_shared_addresses` rows for `H` on Device A, without ever checking that Device C is a party to that address — silently aborting Device A's and Device B's in-progress shared-address setup.

**Note on uncertainty:** I was not able to fully trace how `address_definition_template_chash` values are learned by third parties in all deployment scenarios (e.g., whether they are ever broadcast/forwarded to non-member correspondents), so the practical ease of an attacker obtaining a valid `H` for a victim's in-progress shared address may vary; this affects likelihood but not the underlying missing-authorization root cause.
