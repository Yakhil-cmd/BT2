### Title
Cross-organization webhook impersonation via decoupled `repository.owner.login` and `repository.full_name` fields - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret using `params.dig('repository','owner','login')`, while `ReopenedHandler#repository` (and the sibling `OpenedHandler`/`LabeledHandler`) resolves the target `Shipit::Repository` using `params.repository.full_name` split on `/`. These are two independent, attacker-controlled JSON fields inside the same raw POST body, and nothing in the code enforces that they agree.

### Finding Description
The binding the question challenges: **organization whose `webhook_secret` verified the request == organization owning the `Repository` row the handler mutates**. Tracing the code shows this binding does not hold.

- `verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login')` and does `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) [2](#0-1) .
- `ReopenedHandler#repository` computes the target repository from a completely different field, `params.repository.full_name`, via `Shipit::Repository.from_github_repo_name` [3](#0-2) .
- `Repository.from_github_repo_name` derives the owner independently by splitting `full_name` on `/`: `repo_owner, repo_name = github_repo_name.downcase.split('/')` [4](#0-3) .
- The `ExplicitParameters` schema for `ReopenedHandler` only requires `repository.full_name` as a String; it never requires or validates `repository.owner.login` [5](#0-4) .
- `process` then unconditionally calls `stack.unarchive!` on the `ReviewStackAdapter` built from `repository.review_stacks` (i.e., the victim repository's review stacks) [6](#0-5) , and `unarchive!` will even auto-`create!` a new review stack if none exists [7](#0-6)  using attacker-controlled `pull_request.head.ref`, PR number, and sender login [8](#0-7) .

**Exploit flow:** Shipit supports multi-tenant GitHub App configuration, where distinct organizations each have their own `webhook_secret` (demonstrated by the two-org fixture `test/dummy/config/secrets_double_github_app.yml`). An attacker who administers "OrgA" (onboarded to the same Shipit instance) knows OrgA's `webhook_secret`. They POST to `/webhooks` with `X-Github-Event: pull_request` and a body where:
- `repository.owner.login = "OrgA"` (used only for signature-org lookup)
- `repository.full_name = "orgb/victim-repo"` (used only for the actual DB lookup/mutation target)
- `action = "reopened"`, with attacker-chosen `pull_request.head.ref`, labels, etc.

They sign the raw body with OrgA's `webhook_secret`. `verify_signature` looks up OrgA's app/secret and verifies successfully, since the signature was computed correctly for OrgA. `ReopenedHandler` then resolves and mutates the **victim's** `orgb/victim-repo` repository/stack, calling `stack.unarchive!` (or creating a review stack) with attacker-supplied PR head ref and metadata.

No existing guard prevents this: `drop_unhandled_event` and `check_if_ping` only filter by event type; the `ExplicitParameters` schema does not cross-validate `repository.owner.login` against `repository.full_name`; `verify_signature` never re-checks `repository.full_name`'s owner segment against the org whose secret was used.

### Impact Explanation
An attacker who administers any single organization onboarded to a shared multi-tenant Shipit instance can forge webhook events attributed to any other tracked organization's repositories, causing unarchiving/auto-provisioning of that victim organization's review stacks (which can trigger deploy/task infrastructure) with attacker-controlled branch refs and PR data, and no legitimate GitHub event from the victim org ever occurred. This is a cross-repository/cross-tenant write matching the "payload for one repository mutating another's stack" Critical impact category. It is fully repeatable against any repository whose `owner/name` is known and tracked in Shipit, and the same divergence affects `OpenedHandler` and `LabeledHandler` (both use the same `repository.owner.login`/`full_name` split pattern) — expanding blast radius to stack creation, provisioning, and archive/unarchive across all onboarded tenants.

### Likelihood Explanation
This requires a multi-tenant Shipit deployment where multiple organizations/apps are configured with distinct `webhook_secret`s (a supported and documented configuration, per `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`), and the attacker must legitimately administer one such onboarded organization (knowing only their own secret — no victim secrets, sessions, or tokens needed). Given that precondition, the attack is trivial: a single crafted HTTP POST with a correctly computed HMAC-SHA1 signature using the attacker's own known secret. It is fully repeatable and requires no interaction with the victim org.

### Recommendation
In `WebhooksController#verify_signature` and/or each handler's `repository` resolution, enforce that the organization used to select the webhook secret matches the owner segment of `repository.full_name` (or, better, always derive `repository_owner` from `repository.full_name` rather than the independent `repository.owner.login` field) before trusting `full_name` for any DB lookup. Reject the payload (422) if the two disagree.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "cross-org webhook cannot mutate a different org's repository" do
  # Org A's webhook secret known to the attacker who administers Org A.
  org_a_secret = "org-a-secret"
  Shipit.stubs(:github).with(organization: "OrgA").returns(
    Shipit::GithubApp.new("OrgA", webhook_secret: org_a_secret)
  )

  victim_repo = shipit_repositories(:shipit) # e.g. owner "shopify", name "shipit-engine"
  victim_repo.update!(review_stacks_enabled: true, provisioning_behavior: :allow_all)

  payload = {
    action: "reopened",
    number: 999,
    pull_request: {
      id: 1, number: 999, url: "https://x", title: "x", state: "open",
      additions: 1, deletions: 0,
      head: { sha: "abc", ref: "attacker-branch" },
      user: { login: "attacker" },
      assignees: [], labels: []
    },
    repository: {
      owner: { login: "OrgA" },       # used ONLY for signature org lookup
      full_name: victim_repo.github_repo_name # used to resolve mutated repo
    },
    sender: { login: "attacker" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", org_a_secret, payload)

  request.headers["X-Github-Event"] = "pull_request"
  request.headers["X-Hub-Signature"] = signature

  assert_difference -> { victim_repo.review_stacks.count }, 1 do
    post :create, body: payload, as: :json
  end
  assert_response :ok
end
```
This asserts both sides of the binding: the signature verifies against Org A's secret (`repository.owner.login == "OrgA"`), while the mutated record belongs to the victim repository resolved from `repository.full_name`, proving the two are decoupled.
