### Title
Cross-repository status forgery via unscoped SHA lookup in `StatusHandler` triggers merge using victim's `stack.github_api` credential - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` only proves that a webhook was signed with the secret of the organization named in the payload's own `repository.owner.login` field; it never checks that this organization actually owns the commit the payload claims to update. `StatusHandler#process` then looks up the target `Commit` purely by global `sha`, with no scoping to the repository/stack that the verified organization owns, so a status event legitimately signed by organization A can mutate a commit's status belonging to a completely different stack/organization B, and that forged "success" state can drive `ProcessMergeRequestsJob` to call `MergeRequest#merge!`, which invokes `stack.github_api.merge_pull_request` using Shipit's own credential for repo B.

### Finding Description
The broken binding is: `verified_org(payload) == owning_org(matched_commit.stack)`. Tracing the code shows this is never enforced.

1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and verifies the HMAC signature against `Shipit.github(organization: repository_owner)`'s configured `webhook_secret`. [1](#0-0) 
This only proves the request was signed with organization A's secret — it says nothing about which repository's commits the event body is allowed to touch.

2. `StatusHandler#process` ignores the `repository` context entirely and matches commits by `sha` alone, across the whole `commits` table (all stacks/orgs): [2](#0-1) 
The handler's params schema doesn't even require a `repository` field. [3](#0-2) 

3. `Commit` has no per-stack uniqueness/ownership guard preventing a matching `sha` from existing in an unrelated stack — `belongs_to :stack` is the only tie, and `create_status_from_github!`/`add_status` will happily apply the forged status and re-evaluate `Status::Group`, then call `stack.schedule_merges` if the resulting state is pending/success: [4](#0-3) [5](#0-4) 

4. `ProcessMergeRequestsJob` re-checks `all_status_checks_passed?` on the (now-forged) status and, if true, calls `merge_request.merge!`: [6](#0-5) 

5. `MergeRequest#merge!` then calls the victim stack's own credential to merge the victim's PR: [7](#0-6) 

Exploit flow: attacker legitimately owns/administers organization A, which is a separately onboarded tenant of the same Shipit instance (so they genuinely know org A's `webhook_secret`, satisfying `verify_signature`). Attacker learns the head commit SHA of a pending merge-queued PR in victim stack B (SHAs are typically public on GitHub). Attacker sends `POST /webhooks` with `X-Github-Event: status`, `repository.owner.login: "orgA"`, a valid signature computed with org A's secret, and body `{"sha": "<victim's head sha>", "state": "success", "context": "<required context>"}`. This passes `verify_signature` (org A is genuine) and `drop_unhandled_event`, then `StatusHandler` finds and updates the commit belonging to stack B because the lookup has no repository scoping. If this satisfies `all_status_checks_passed?` for the pending merge request, `ProcessMergeRequestsJob` merges the victim's PR using the victim stack's own `stack.github_api` credential — an action never authorized by any webhook genuinely originating from repo/org B.

None of the existing guards (`verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema on `StatusHandler`) close this gap, because they validate the signer's identity, not the target-record ownership of the payload's `sha`.

### Impact Explanation
A cross-tenant status forgery can cause Shipit to execute `stack.github_api.merge_pull_request` on a victim repository the attacker never authenticated against, using Shipit's own GitHub App/token credential for that repository. This is a state-changing, unauthorized merge on GitHub, matching the "Critical: a payload for one repository mutating another's stack/commit... or an unauthorized deploy/rollback/merge" category. It is repeatable against any stack/PR whose head commit SHA the attacker can learn, as long as the attacker controls any organization already onboarded into the same Shipit instance; blast radius spans all tenants of a shared/multi-team Shipit deployment.

### Likelihood Explanation
Exploitation requires: (1) the attacker administers some organization/repo that is already a legitimate, separately configured tenant in the same Shipit instance (so they know that org's real `webhook_secret`) — plausible in shared/company-wide Shipit deployments where multiple teams onboard independently; (2) knowledge of the victim's pending PR head commit SHA, which is normally public; (3) the victim stack must already have that PR queued (`pending`) with `merge_queue_enabled`, and the forged status context must be one that flips `all_status_checks_passed?` to true. These are realistic operational conditions for a multi-tenant Shipit install and require no secrets beyond what the attacker's own legitimately-configured org already provides them.

### Recommendation
Scope the `StatusHandler` (and any other sha-based lookup path) so that it only updates commits belonging to a stack whose configured repository matches the webhook's verified organization/repository, e.g. require and validate `params.repository.full_name` against `commit.stack.repository` (or `commit.github_repo_name`) before calling `create_status_from_github!`, rejecting/ignoring mismatches.

# test/models/webhooks/handlers/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status verified for org A must not mutate a commit owned by org B's stack" do
          victim_stack = shipit_stacks(:shipit) # e.g. repo "shopify/shipit-engine"
          victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim head')

          # Binding under test: verified_org(payload) == owning_org(matched_commit.stack)
          verified_org = 'attacker-org'
          owning_org   = victim_stack.repository.owner

          refute_equal verified_org, owning_org # the two sides of the binding differ

          payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'context' => 'ci/required',
            'repository' => { 'owner' => { 'login' => verified_org }, 'full_name' => "#{verified_org}/other-repo" }
          }

          Shipit::Webhooks::Handlers::StatusHandler.new(payload).process

          victim_commit.reload
          # FAILS today: the forged, cross-org-verified status is applied to victim_stack's commit
          refute_equal 'success', victim_commit.status.state,
            "status verified for #{verified_org} must not update a commit owned by #{owning_org}"
        end

        test "forged success enables merge! against victim stack.github_api" do
          merge_request = shipit_merge_requests(:shipit_pending)
          Shipit::Webhooks::Handlers::StatusHandler.new(
            'sha' => merge_request.head.sha, 'state' => 'success', 'context' => 'ci/required',
            'repository' => { 'owner' => { 'login' => 'attacker-org' } }
          ).process

          merge_request.stack.github_api.expects(:merge_pull_request)
            .with(merge_request.stack.github_repo_name, merge_request.number, anything, anything)

          ProcessMergeRequestsJob.new.perform(merge_request.stack)
        end
      end
    end
  end
end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
