`ReviewStack#env` label injection overwrites `GITHUB_TOKEN` with attacker-controlled literal `"true"` - ([File: app/models/shipit/task.rb])

### Summary
`Commands#base_env` sets `env['GITHUB_TOKEN']` to the real GitHub App/installation token, but `TaskCommands#env` and `DeployCommands`/`RollbackCommands` (via `TaskCommands#env`) call `.merge(@stack.env)` right after `super`, and `ReviewStack#env` merges in the pull request's GitHub labels upper-cased as env keys with the value `"true"`. Any unprivileged user who can label their own PR (`GITHUB_TOKEN`) can therefore overwrite the real GitHub token used by deploy/rollback/task commands with the literal string `"true"`, corrupting the credential used for all `git`/GitHub-authenticated subprocess calls for that stack's deploys.

### Finding Description
Binding claimed broken: `command.env['GITHUB_TOKEN'] == Shipit.github(organization: stack.repository.owner).token` for a `ReviewStack`'s commands.

Trace:
- `Commands#base_env` sets the real token: `'GITHUB_TOKEN' => github.token` [1](#0-0) , with `TaskCommands#github` scoping to the stack's org [2](#0-1) .
- `TaskCommands#env` builds on `super` (which returns `base_env`) and then merges `@stack.env`: `super.merge(@stack.env).merge(...)` [3](#0-2) .
- `ReviewStack#env` merges the pull request's labels, upper-cased, each mapped to `"true"`: `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` [4](#0-3) .
- Because `Hash#merge` gives precedence to the merged-in hash, if the PR carries a label literally named `GITHUB_TOKEN` (case-insensitive, since `.upcase` is applied), the resulting `@stack.env['GITHUB_TOKEN']` is `"true"`, which then overwrites the real token when `TaskCommands#env` merges `@stack.env` after `super`.
- Nothing after that in `TaskCommands#env` restores `GITHUB_TOKEN` (`deploy_spec.machine_env` and `@task.env` do not set it under normal attacker control).
- The corrupted hash eventually reaches `Command#unbundled_env`/`PTY.spawn` as the process environment for git/deploy commands [5](#0-4) , [6](#0-5) .
- Labels reach `PullRequest#labels` unauthenticated-but-webhook-signed via `LabelCapturingHandler#capture_labels`, which does `pull_request.update!(labels: params.pull_request.labels.map(&:name))` with no filtering or blocklist of reserved names [7](#0-6) . No reserved-name check exists anywhere in the codebase for label-derived env keys (confirmed by search).

Existing tests already demonstrate this exact merge mechanic for benign labels (`WIP`, `BUG`) [8](#0-7) [9](#0-8) , confirming the same code path applies to any label name including `GITHUB_TOKEN`.

Guard check: webhook signature verification (`GitHubApp#verify_webhook_signature`) authenticates that the payload came from GitHub for the repository in question, but it does not restrict *label content* — the PR author (an unprivileged repo contributor who can open PRs) fully controls label names via GitHub's UI/API, and GitHub forwards them verbatim; the webhook signature only proves the delivery is genuine, not that the label content is safe. No `ExplicitParameters` schema constraint, no `EnvironmentVariables#permit` filter, and no reserved-key blocklist prevents a label from being named `GITHUB_TOKEN`.

### Impact Explanation
Every deploy, rollback, or task command run against the affected `ReviewStack` will execute with `GITHUB_TOKEN=true` instead of the real installation token, breaking GitHub API/git authentication for that stack's deploy pipeline. This is a self-inflicted denial of correct behavior for the review stack tied to the labeled PR — it does not exfiltrate the real token nor allow cross-tenant/cross-repository mutation; the blast radius is limited to the single `ReviewStack` under the labeling PR author's own control (they can already label their own PR). It matches "authentication failure/corruption" of a value the app treats as trusted secret material, but does not rise to token exfiltration, RCE, or unauthorized deploy of another party's code — it corrupts an authentication credential used by the attacker's own stack's automated commands, causing operational breakage rather than granting the attacker additional privilege or access to secrets.

### Likelihood Explanation
Preconditions: repository must have review stacks enabled and provisioned for the PR (standard config for repos using this feature); attacker must be able to open a PR and add a label named `GITHUB_TOKEN` (or any case variant) to it, which is available to any contributor with label permission on their own PR (many repos allow this for external contributors, or the attacker could be a low-privileged collaborator). Cost is trivial — a single GitHub API/UI action. Fully repeatable against any `ReviewStack`, but only affects the attacker's own review-stack instance, not other stacks/repos/tenants.

### Recommendation
In `ReviewStack#env` (or in `Commands`/`TaskCommands`), filter/blocklist reserved environment variable names (`GITHUB_TOKEN`, `GITHUB_DOMAIN`, `GIT_ASKPASS`, etc.) from label-derived environment injection, or merge label-derived env keys *before* `base_env`/`github.token` assignment rather than after, so secrets always take final precedence. A minimal fix: in `app/models/shipit/review_stack.rb`, reject/skip labels whose upcased name matches any key already present in `super` that is considered sensitive (at minimum `GITHUB_TOKEN`), e.g. `labels.except(*RESERVED_ENV_KEYS)` before merging.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (or task_commands_test.rb)
test "#env does not allow a PR label to overwrite GITHUB_TOKEN" do
  stack = shipit_stacks(:review_stack)
  real_token = Shipit.github(organization: stack.repository.owner).token
  stack.pull_request.update!(labels: ["GITHUB_TOKEN"])

  env = Shipit::TaskCommands.new(shipit_tasks(:shipit_restart).tap { |t| t.stack = stack }).env

  assert_equal real_token, env["GITHUB_TOKEN"], "label should not be able to clobber GITHUB_TOKEN"
end
```
Expected current (vulnerable) behavior: assertion fails because `env["GITHUB_TOKEN"] == "true"` instead of `real_token`, confirming `command.env['GITHUB_TOKEN'] != Shipit.github(organization:).token`.
