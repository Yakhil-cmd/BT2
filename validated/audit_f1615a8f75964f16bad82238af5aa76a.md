### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` lookup enables unauthorized deploy - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits to attach a GitHub `status` webhook to by `sha` alone, with no scoping to the reporting repository, even though the base `Handler` class already provides a `stacks` helper scoped via `Repository.from_github_repo_name(repository_name)`. An attacker who controls any GitHub repository whose commit history shares a sha with a victim's tracked commit (trivially achieved by forking the victim's repo, since forked commits keep identical shas) can send a validly-signed webhook from their own repo and have the forged `success` status attached to the victim's commit in a completely different stack/tenant. This satisfies `Shipit::Commit#deployable?`'s CI gate and, combined with the fact that `locked?` defaults to `false` and is unrelated to repository identity, allows the victim stack to deploy that commit.

### Finding Description
The broken binding: `commit.locked? == false` is assumed to imply "no compensating control is needed beyond CI status," but the CI status itself is not bound to `commit.stack.repository`. Concretely: `Repository#full_name_from_payload == commit.stack.repository.full_name` is never checked in the status path.

Code path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) validates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-supplied payload (`app/controllers/shipit/webhooks_controller.rb:59-62`). This only proves the payload was signed with *some* app/org's webhook secret that matches the claimed `repository_owner` — for an attacker's own repo/fork, this is legitimately obtainable (they can install/configure the GitHub App or webhook on their own repository) with zero Shipit privilege.
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
   ```ruby
   Commit.where(sha: params.sha).each do |commit|
     commit.create_status_from_github!(params)
   end
   ```
   This is a global lookup by `sha` across *all* stacks/tenants, unlike other handlers (see `Handler#stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-34`) which scope by `Repository.from_github_repo_name(repository_name)`. `params.dig('repository', ...)`/`payload['repository']['full_name']` is never consulted here.
3. `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:24-33`) creates a `Status` row scoped to the *victim's* `stack_id`, using only the attacker-controlled `state`/`context`/etc.
4. `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`): `!locked? && (stack.ignore_ci? || (success? && !blocked?))`. Since `locked` defaults to `false` for any commit an operator hasn't manually locked, the only remaining gate is `success?`, which the forged status now satisfies.
5. Downstream, `Stack#next_expected_commit_to_deploy` (`app/models/shipit/stack.rb:332-342`) or an explicit `POST /api/stacks/:id/deploys` (`app/controllers/shipit/api/deploys_controller.rb:19-27`) can now select/accept this commit for deployment.

Existing guards do not mitigate this: `verify_signature` authenticates the *sender's own* organization, not that the sender is authorized for the *commit's* repository; `ExplicitParameters` only validates payload shape, not repository binding; there's no `Repository`/`Stack` scoping check anywhere in `StatusHandler`.

### Impact Explanation
An attacker who owns/forks any public (or even private, if attacker is a contributor) repository can, without holding any Shipit session, API token, or webhook secret belonging to the victim, cause a `Status` record with `state: 'success'` to be attached to a commit belonging to a victim stack/tenant they do not control, purely because the sha is shared (fork) or because the attacker constructs a repo whose commit graph intersects the victim's tracked commits. This flips `deployable?` for that commit in the victim's stack, enabling an unauthorized deploy trigger for a repository the attacker never authenticated against — matching the "Critical: a payload for one repository mutating another's stack/commit" and "unauthorized deploy" impact categories. This is repeatable against any commit sha the attacker can reproduce (fork scenario is the common/free case) and against any tenant configured on the same Shipit instance.

### Likelihood Explanation
Preconditions are minimal and match the common case: the victim commit's `locked` column is `false` (default). The attacker needs: (a) their own GitHub repository/fork with a webhook or app installation they control (no privilege on the victim), and (b) a commit sha that also exists as a tracked commit in the victim's stack — trivially satisfied by forking the victim's public repo, since forking preserves commit shas exactly. Cost is a single `git fork` + `push` + one crafted, self-signed `status` webhook POST. Fully repeatable and scriptable against any repository tracked by the shared Shipit instance.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the reporting repository, mirroring `Handler#stacks`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a `Status` write for a given webhook payload can only affect commits belonging to stacks tied to the `repository.full_name` in that same payload, closing the cross-tenant binding gap that `locked?` alone cannot cover.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (new/expand)
test "status webhook does not write a status for commits belonging to a different repository/stack" do
  victim_stack = shipit_stacks(:shipit) # tracks repo "shopify/shipit-engine"
  victim_commit = victim_stack.commits.create!(sha: "a" * 40, locked: false, ...)
  # attacker forks a different repo but shares the same commit sha (fork scenario),
  # or simply crafts a payload naming their own repo but the victim's sha.
  attacker_payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => "attacker/evil-fork", "owner" => { "login" => "attacker" } }
  }

  refute victim_commit.deployable? # baseline: locked == false, but no success status yet

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  victim_commit.reload
  assert victim_commit.success?, "forged status from unrelated repo should NOT apply, but current code applies it"
  assert victim_commit.deployable?, "commit becomes deployable purely from a cross-repo forged status, with locked? still false"
end
```
Both sides of the equality (`locked? == false` implies "safe absent operator action") diverge after the fix: post-fix, `StatusHandler` scopes by `stacks` derived from `payload['repository']['full_name']`, so the attacker's payload naming `attacker/evil-fork` never touches `victim_commit`, and `deployable?` remains `false`.
