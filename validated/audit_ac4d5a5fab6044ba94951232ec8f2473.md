### Title
Webhook signature verification is scoped to `repository.owner.login`, but every event handler resolves its target by the independent `repository.full_name` field, letting a webhook signed (or unsigned, if that owner has no `webhook_secret`) for one GitHub organization drive syncs on any tracked repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to check the `X-Hub-Signature` against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')`. Every handler that actually mutates state (`PushHandler`, pull-request handlers, etc.) instead resolves its target repository from the sibling, independently-attacker-controlled field `payload.dig('repository', 'full_name')` via `Handler#repository_name`. These two JSON fields are never cross-checked against each other, so the "organization whose secret authenticated the request" and "the repository that is written to" are two different bindings that are never proven equal.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is derived purely from `repository.owner.login` / `organization.login` in the JSON body [2](#0-1) .

`GitHubApp#verify_webhook_signature` at [3](#0-2)  short-circuits to `true` whenever that organization's `webhook_secret` is blank:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```
`webhook_secret` is documented as optional per-organization configuration (`docs/setup.md` line 30, "Webhook secret (optional)"), and Shipit explicitly supports hosting multiple GitHub organizations with independent per-org secrets (`docs/setup.md` "Using Multiple Github Applications", lines 182-209).

Once signature verification passes (or is skipped because the *claimed* owner org has no secret configured), `WebhooksController#create` dispatches the whole raw payload to handlers [4](#0-3) . Handlers never look at `repository.owner.login` again - they resolve the acted-upon repository solely from `repository.full_name`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler#process` then syncs every stack matching that repository/branch with an attacker-supplied `after` SHA: [6](#0-5) , which calls `Stack#sync_github` → `GithubSyncJob.perform_later(stack_id:, expected_head_sha:)` [7](#0-6) .

Equality that should hold but doesn't:
`organization_whose_secret_verified_the_request == owner_of(repository.full_name)`.

Because `repository.owner.login` and `repository.full_name` are two independently-settable JSON keys in the same unsigned-until-verified body, an attacker who controls (or is onboarded to) a GitHub organization Y configured in Shipit **without** a `webhook_secret` can send a POST to `/webhooks` with:
- `X-Github-Event: push`
- `repository.owner.login = "Y"` (an org with no secret → `verify_webhook_signature` returns `true` unconditionally, no `X-Hub-Signature` needed)
- `repository.full_name = "X/some-tracked-repo"` (a repository belonging to a *different*, secured organization X that is actually tracked by a Shipit stack)
- `after = <attacker-chosen SHA>`, `ref = refs/heads/<tracked-branch>`

This request never has to satisfy X's `webhook_secret` at all, yet it drives `GithubSyncJob` for X's stack with an attacker-chosen `expected_head_sha`, and other handlers (pull request assigned/closed/labeled/etc.) similarly resolve state purely off `repository.full_name` with no relation to the org that was checked.

### Impact Explanation
This breaks the deployment-trust binding "an organization that authenticated versus the repository that is written," matching the rules' accepted analog categories. The concrete effect is an unauthorized write into another organization's Shipit stack state: forcing/racing GitHub syncs, injecting attacker-influenced `expected_head_sha` values, and driving pull-request lifecycle handlers (open/close/labeled/assigned) against repositories the attacker does not own or have legitimate webhook credentials for. This can result in unauthorized deploy/rollback triggering paths (via forced sync + queue state) and false commit/status/PR state changes cross-tenant, without ever needing the actual GitHub App credentials, `webhook_secret`, or GitHub write access for the targeted organization/repository — satisfying the "cross-repository writes" / "unauthorized deploy" bar even though the strict signature itself is not cryptographically broken. The severity is highest in multi-organization deployments (explicitly supported and documented), and specifically whenever any onboarded organization is configured without a `webhook_secret` (an explicitly optional setting per the docs), which is a realistic misconfiguration this codebase does not guard against.

### Likelihood Explanation
Requires only: (1) the Shipit instance to onboard at least one GitHub organization without a `webhook_secret` — an officially supported, "optional" configuration — and (2) that instance to also host a stack for a different, secured organization/repository. No secret, session, or API token is needed; the attacker only needs to know (or guess) the `full_name` of a target repository tracked by the instance, which is often discoverable (Shipit stack URLs typically embed `owner/repo`).

### Recommendation
Bind signature verification to the same repository identity the handlers act on: derive the GitHub App/organization to verify against from `repository.full_name`'s owner segment (not a separately-controllable `repository.owner.login`/`organization.login` field), and require the resolved owner segment to exactly match the organization key actually configured/used to fetch the `webhook_secret`. Additionally, treat a missing `webhook_secret` for a configured organization as a hard failure (reject the webhook) rather than an implicit bypass, or require all organizations in a multi-org configuration to have a `webhook_secret` set.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`: `secured-org` (has `webhook_secret: <strong-secret>`) with a Shipit stack tracking `secured-org/target-repo`, and `attacker-org` (has `webhook_secret:` left blank/nil), matching the documented multi-org format in `docs/setup.md`.
2. As the attacker (no access to `secured-org`'s secret, no Shipit session), POST to `/webhooks`:
```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "secured-org/target-repo"
  }
}
```
3. `verify_signature` computes `repository_owner == "attacker-org"`, loads `attacker-org`'s `GitHubApp`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of any `X-Hub-Signature` header (`lib/shipit/github_app.rb:76-77`).
4. `PushHandler#process` resolves `repository_name` from `full_name` = `"secured-org/target-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), finds the real stack for `secured-org/target-repo`, and enqueues `GithubSyncJob` with the attacker-supplied `expected_head_sha` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`, `app/models/shipit/stack.rb:612-614`) — all without ever presenting `secured-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
