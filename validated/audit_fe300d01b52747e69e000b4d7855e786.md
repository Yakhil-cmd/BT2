### Title
Webhook signature is verified against the `repository.owner.login` organization while the actual repository/stack acted upon is taken from an unrelated, uncorrelated `repository.full_name` field, letting any org admin with a legitimately-configured Shipit GitHub App forge events for repositories belonging to other organizations - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which HMAC secret to check the payload against using `repository_owner`, a value read straight out of the untrusted JSON body (`repository.owner.login` or `organization.login`). The handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`, and even more so `StatusHandler`) use a *different*, equally attacker-controlled field (`repository.full_name`, or no repository scoping at all) to decide which `Stack`/`Commit` gets mutated. There is no code path that checks `repository_owner == owner(repository_full_name)`, so the "organization whose secret authenticated the request" and "the repository that is actually written to" are never bound together.

### Finding Description
`Shipit.github(organization:)` supports one `GitHubApp`/webhook secret per configured GitHub organization [1](#0-0) . In this mode, each organization that Shipit is configured for owns its own webhook secret, as shown in the multi-org fixture [2](#0-1) .

`WebhooksController#verify_signature` picks the secret to check with using `repository_owner`, which is parsed directly out of the JSON body the caller supplies: [3](#0-2) 

The HMAC is computed over `request.raw_post` (the whole body) using that organization's secret [4](#0-3) , so anyone who genuinely knows OrgOne's webhook secret (e.g. an OrgOne admin who created/owns the GitHub App used by Shipit for OrgOne) can sign *any* body they want, because the secret itself, not the body's semantic content, is what's validated.

Once the request passes signature verification, `WebhooksController#create` dispatches to the registered handlers with the raw parsed params, without re-checking `repository_owner`: [5](#0-4) 

The handlers determine which `Stack`/`Repository` to act on using `repository.full_name`, a completely separate field from the one used for signature-secret selection: [6](#0-5) 

`PushHandler` uses that repository scoping to queue syncs on arbitrary stacks: [7](#0-6) 

`StatusHandler` is worse: it does not scope by repository at all, it looks up commits **globally by sha** and writes a GitHub-reported CI status onto them: [8](#0-7) 

So the binding that should hold is:
`organization authenticated by verify_signature (repository_owner)` == `repository/commit actually written by the handler (repository.full_name / global sha lookup)`

This binding is never enforced anywhere in the request path.

### Impact Explanation
An attacker who legitimately administers *any one* of the GitHub organizations Shipit is configured for (a normal, unprivileged-relative-to-Shipit condition in a multi-tenant Shipit deployment) knows that organization's webhook secret. They can POST directly to the public, unauthenticated `/webhooks` endpoint (it is a plain `ActionController::Base` action, no Shipit session or `ApiClient` token required) with:
- `X-Github-Event: status`, `repository.owner.login = "OrgOne"` (so `verify_signature` validates against OrgOne's secret, which the attacker legitimately possesses), and
- an arbitrary `sha` belonging to a commit tracked under a completely different organization's stack, with `state: "success"`.

Because `StatusHandler` never checks which repository/organization the sha belongs to, this forges a passing CI status on a commit the attacker does not control and never actually passed CI for. If that stack's merge/deploy safety gating relies on commit statuses, this can push an unreviewed or unsafe commit past status-based safety checks, leading to an unauthorized deploy or merge on a repository/organization the attacker has no legitimate access to. Similarly, `PushHandler` can be used to force `GithubSyncJob` execution against any tracked stack belonging to another organization, using the payload's `after` sha (also unrelated to the authenticating organization). This is a cross-repository/cross-organization write achieved purely by exploiting the mismatch between the authenticated identity and the acted-upon resource — matching the required "unauthorized deploy" / "cross-repository writes" impact bar.

### Likelihood Explanation
Likelihood is high in any Shipit deployment that uses the documented multi-organization configuration (explicitly supported and documented) [9](#0-8) : any org admin who is legitimately entitled to configure a GitHub App for their own org automatically obtains the ability to forge events for every other organization tracked by the same Shipit instance, with no additional privilege escalation, session, or token required — only a raw HTTP POST to the public webhook endpoint.

### Recommendation
In `WebhooksController#verify_signature` (and/or in `Handler#repository_name`/`stacks`), cross-check that the organization used to select the verifying secret (`repository_owner`) matches the owner of the repository the handler will actually act upon (derived from `repository.full_name`) before dispatching to handlers. Reject the request (422) if they diverge. `StatusHandler` should additionally scope its `Commit` lookup to stacks belonging to the verified organization instead of doing an unscoped global `sha` lookup.

### Proof of Concept
1. Shipit is configured with `github: { OrgOne: {webhook_secret: S1, ...}, OrgTwo: {webhook_secret: S2, ...} }`, tracking a stack for `OrgTwo/victim-repo`.
2. Attacker administers `OrgOne` and legitimately knows `S1`.
3. Attacker crafts:
```json
{
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" },
  "sha": "<malicious-commit-sha-in-OrgTwo>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(S1, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` computes `repository_owner = "OrgOne"`, fetches `Shipit.github(organization: "OrgOne")`, verifies the HMAC using `S1` — passes.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` globally, finds the OrgTwo commit, and writes a fabricated "success" status onto it, even though the request was never authenticated as OrgTwo and the attacker has no access to OrgTwo's secret or repository.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
