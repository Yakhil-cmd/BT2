### Title
Stack-scoped `ApiClient` token authorises access to any stack's CCMenu status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor used by `BaseController` in a way that drops the scoping check that restricts an `ApiClient` token to the single `Stack` it was created for, allowing any valid stack-scoped API token to read CCTray/CCMenu build status for arbitrary stacks.

### Finding Description
`Shipit::Api::BaseController` implements the "token authorises stack X" binding through two cooperating methods: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the token is scoped to a stack, and `stack` (used by every other API controller, e.g. `StacksController#stack`) is built on top of `stacks`, so `Stack.from_param!` can only ever resolve within that authorised set: [2](#0-1) 

`Shipit::Api::CCMenuController`, however, defines its own `stack` method that calls `Stack.from_param!(params[:stack_id])` directly, bypassing `stacks` entirely: [3](#0-2) 

The permission check that runs before the action only validates the abstract permission string, not the specific stack instance: [4](#0-3) 

So the binding that should hold is: `token.stack_id == requested_stack.id` (when `token.stack_id` is set). Before this override, that binding holds for every API controller because they all go through `BaseController#stack`/`#stacks`. After the override in `CCMenuController`, the binding is broken: `require_permission :read, :stack` only asserts the token carries the string `"read:stack"` in its `permissions` array — it says nothing about *which* stack — and the actual stack lookup ignores the token's `stack_id` restriction altogether.

`CCMenuController` additionally allows unauthenticated callers to reach `authenticate_api_client` via a `token` query-string parameter, and this same weakened path is used regardless of authentication method: [5](#0-4) 

This matches the requested vulnerability class: "a stack a token authorises versus a stack it touches" — the token's declared/authorised stack (`current_api_client.stack_id`) diverges from the stack actually touched by the request (`params[:stack_id]` resolved unfiltered).

### Impact Explanation
Any `ApiClient` token — including one deliberately scoped by an operator to a single, low-sensitivity stack (via `ApiClient#stack_id`) — can be used to query the CCMenu/CCTray status endpoint of any other stack in the Shipit instance, as long as the token carries the generic `read:stack` permission. This is an unauthorized read of stack state (last build status, build label/time, web URL) for stacks the token holder was never granted access to, which is explicitly called out as a High-impact category ("unauthenticated/unauthorized read of stack state ... for a token whose authorised stack differs from the stack it touches"). It does not require any GitHub credentials, session, or privileged account beyond possessing *some* valid stack-scoped `ApiClient` token, which by design is meant to be handed out narrowly (e.g., via `CCMenuUrlController`, which mints tokens scoped to one stack and one permission): [6](#0-5) 

### Likelihood Explanation
Likelihood is high for anyone who already holds a legitimately-issued, narrowly-scoped `ApiClient` token (a routine, low-privilege credential meant to be embedded in a CI dashboard/CCTray client and thus more likely to leak or be shared than a full API credential). The attack requires only changing the `stack_id` path/query parameter to a different, arbitrary stack identifier — no additional secrets, no signature forgery, and no interaction with GitHub is needed. The existing test suite for this controller never exercises a stack-scoped client against a *different* stack, so the regression is untested and easy to miss: [7](#0-6) 

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the inherited, scope-aware `stacks` method (i.e. remove the private `stack` override, or reimplement it as `stacks.from_param!(params[:stack_id])`) so that the `current_api_client.stack_id` restriction from `BaseController#stacks` is enforced consistently with every other API controller.

### Proof of Concept
1. As an operator, create a stack-scoped API client for `stack-A` via `CCMenuUrlController#fetch` (or `ApiClient.create!(stack: stack_a, permissions: ['read:stack'], creator: some_user)`), obtaining `authentication_token`.
2. Using that token, issue `GET /api/stacks/stack-b/ccmenu.xml?token=<token>` (or Basic-Auth with the token) for `stack-B`, a stack the token was never scoped to.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(...)`, the request succeeds and returns `stack-B`'s CCMenu/build status, even though `current_api_client.stack_id` is `stack-A`'s id. Compare with `StacksController#show` using the same token against `stack-B`, which correctly raises a not-found/authorization error because it goes through the scoped `stacks` method.
