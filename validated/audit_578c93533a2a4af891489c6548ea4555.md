### Title
Webhook signature verification is keyed off an unverified payload field, letting an attacker with a no‑secret GitHub App entry forge events for any other configured repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to use for HMAC verification by reading `repository.owner.login` / `organization.login` directly out of the still‑unverified JSON body, before the signature check has run. [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the selected organization has no `webhook_secret` configured: [3](#0-2) 

Meanwhile the handlers that actually act on the payload (e.g. `PushHandler`, `StatusHandler`, pull-request handlers) determine *what to write to* using a completely different, independently attacker-controlled field: `repository.full_name` (or, for `StatusHandler`, just the commit `sha` with no repository scoping at all). [4](#0-3) [5](#0-4) [6](#0-5) 

This is the analog of M-45's root cause: a check ("already a request" / "verified") that is trivially satisfiable via a default/absent value (`rebalancingPeriod == 0` there, `webhook_secret.blank?` here), letting a caller override state belonging to a different, unrelated principal (another user's withdrawal allowance there, another organization's stacks here).

### Finding Description
Multi-tenant Shipit installations configure one `GitHubApp` per GitHub organization in `config/secrets.yml`, each with its own `webhook_secret`. The setup docs explicitly document this multi-org layout, and it is normal for individual orgs' entries to be missing/blank a `webhook_secret` (e.g. during onboarding, or intentionally in dev), as shown in the shipped example configs where `webhook_secret:` is left `nil`: [7](#0-6) [8](#0-7) 

The binding that should hold is: **the organization whose secret authenticated the request == the repository the handler is permitted to mutate**. Before the fix this equality is never enforced:

- `verify_signature` picks `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')` — read straight from the attacker-supplied JSON body.
- If *that* organization's config has `webhook_secret` blank/nil, `verify_webhook_signature` returns `true` unconditionally — no HMAC is checked at all, `X-Hub-Signature` can be anything.
- After "verification" passes, `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event)` handlers, which look up the target `Stack`/`Repository`/`Commit` using `repository.full_name` (or bare `sha`), a field completely disconnected from the `repository_owner` used to pick the secret. [9](#0-8) 

So an attacker only needs to find (or be an administrator of, or simply guess the name of) *any one* organization entry in the Shipit instance's config that has no `webhook_secret` set, and set `repository.owner.login` to that org's name in the JSON body, while pointing `repository.full_name` at a completely different, properly-configured, unrelated organization's stack. The request sails through `verify_signature` with a bogus/empty signature header, and the handler then acts on the *other* org's data.

Before the (hypothetical) fix: any org lacking a webhook secret is an open door to forge events scoped to *any* repository/stack in the whole instance, because the "authenticated organization" and "written repository" fields are never cross-checked.
After a correct fix: the handler would need to verify that the organization that authenticated the signature actually owns the `repository.full_name` (or `sha`'s stack) being mutated, or webhook_secret should be mandatory, closing the gap analogous to requiring `rebalancingPeriod != 0` in the original bug.

### Impact Explanation
This crosses the "authenticated organization vs. repository written" trust boundary called out in scope. Concretely, `StatusHandler` will create a commit status (`Commit.create_status_from_github!`) for *any* commit sha in the datastore with no repository check at all, and a `success` status on a commit under continuous-deployment can directly cause `Stack#trigger_continuous_delivery` to fire, i.e. an **unauthorized deploy** of a stack the attacker never had legitimate access to. `PushHandler` similarly triggers `stack.sync_github` for stacks resolved purely from the forged `repository.full_name`. This satisfies the Critical bar ("an unauthorized deploy").

### Likelihood Explanation
Exploitability depends entirely on at least one configured GitHub App entry in the instance's `config/secrets.yml` having a blank `webhook_secret` — which the project's own example/dev configs demonstrate is a normal, easy-to-reach state, and is not validated/prevented anywhere in `GitHubApp#initialize` or `WebhooksController`. No repository write access, GitHub App private key, or Shipit session/API token is required — only knowledge of one such org's name and a POST to the public webhooks endpoint, matching the "unprivileged attacker" requirement.

### Recommendation
- Require every configured organization to have a non-blank `webhook_secret` at load time (fail startup / raise) instead of silently treating a blank secret as "always verified."
- Bind the "authenticated organization" to the actual target: after resolving `Repository`/`Stack` from `repository.full_name` (or `Commit#sha`), assert its owning organization matches the organization whose secret verified the signature (`repository_owner`), rejecting the webhook otherwise.

### Proof of Concept
1. Instance is configured with two orgs in `config/secrets.yml`: `evil-org` (attacker controls a GitHub org by this name, or it simply exists with `webhook_secret: nil` per the shipped example configs) and `victim-org` (has properly configured stacks with `continuous_deployment: true`).
2. Attacker sends:
   ```
   POST /webhooks
   X-Github-Event: status
   X-Hub-Signature: sha1=0000000000000000000000000000000000000000
   {
     "organization": {"login": "evil-org"},
     "sha": "<sha of a commit belonging to victim-org's stack>",
     "state": "success",
     "context": "ci/forged"
   }
   ```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'evil-org')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — the bogus signature is accepted. [3](#0-2) 
4. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, creating a `success` status on the victim's commit despite the request never being authenticated by anything belonging to `victim-org`. [6](#0-5) 
5. If that commit's stack has `continuous_deployment: true`, the new `success` status can trigger `trigger_continuous_delivery`, deploying attacker-influenced state to `victim-org`'s stack without any legitimate credential for that organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
