### Title
Unauthenticated Team-Membership Forgery via Webhook Signature Bypass When `webhook_secret` Is Unset - (File: `lib/shipit/github_app.rb`)

### Summary
This finding is the same bug class as the reported `fee_amount` issue: a boundary/absence condition (`fees == 0`, here `webhook_secret` blank) causes a trust check to incorrectly resolve to "pass" instead of failing closed. In Shipit, `GitHubApp#verify_webhook_signature` treats the *absence* of a configured webhook secret as automatic, unconditional verification success, rather than requiring a valid signature. Combined with `MembershipHandler`, which mutates `Shipit.github_teams`-relevant `Membership` records straight from the (now unverified) webhook body, an unauthenticated network attacker can forge team-membership records and escalate into `Shipit.github_teams` authorization.

### Finding Description
`GitHubApp#verify_webhook_signature` is the sole gate protecting `POST /webhooks`: [1](#0-0) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

If `webhook_secret` is blank for the organization resolved from the request, the method returns `true` — i.e. "signature verified" — for *any* payload with *any* (or no) `X-Hub-Signature` header. This is structurally identical to the reported bug: a check that should require an explicit, positive match (`fees == 10000` / a real HMAC match) instead short-circuits to "pass" on the empty/zero case.

`WebhooksController#verify_signature` calls this with attacker-controlled data — `repository_owner` is read straight out of the unauthenticated JSON body before any verification occurs: [2](#0-1) 

`webhook_secret` is explicitly documented and configured as **optional**: [3](#0-2) 

and every shipped example/test config leaves it unset (`webhook_secret: # nil` / `"webhook_secret": null`): [4](#0-3) [5](#0-4) 

Once signature verification is bypassed, `WebhooksController#create` dispatches the raw, attacker-supplied body straight to registered handlers: [6](#0-5) 

The `membership` event is dispatched to `Handlers::MembershipHandler`, which creates/removes `Team`, `User`, and `Membership` records purely from body fields (`team.id/name/slug`, `member.login`, `action`), as shown by the test suite: [7](#0-6) 

Authorization in Shipit is entirely membership-record based, independent of the actual OAuth login flow: [8](#0-7) [9](#0-8) 

and `GithubAuthenticationController#callback` creates a session for *any* successfully OAuth-authenticated GitHub identity, without itself checking team membership — the `authorized?` gate is only enforced afterward, on the next request: [10](#0-9) [11](#0-10) 

This breaks the deployment-trust binding: "a GitHub identity versus the `User`/authorization state bound to the session" — the `Membership` records that gate `Shipit.github_teams` access should only ever be creatable from a payload GitHub has actually signed, but the boundary condition in `verify_webhook_signature` allows anyone to forge them.

### Impact Explanation
An attacker who knows (or discovers, since it's the documented default) that `webhook_secret` is unset can `POST` a forged `membership` `action=added` event to `/webhooks`, naming their own GitHub login and any team handle present in `Shipit.github_teams`. Shipit will create the corresponding `Team`/`User`/`Membership` rows. The attacker then completes the normal (legitimate) GitHub OAuth login as themselves; `find_current_user` will resolve to the `User` row now carrying a forged `Membership`, and `authorized?` will return `true`, granting full access to the Shipit UI/API for repositories restricted to `Shipit.github_teams` — this is a direct escalation into `Shipit.github_teams` authorization, one of the explicitly listed High-impact outcomes, without ever holding a Shipit session, API token, or the real webhook secret.

### Likelihood Explanation
High. `webhook_secret` is presented in the documentation as optional and left blank in every checked-in example/test configuration, and no other gate protects `/webhooks`. Exploitation requires only network access to the deployed instance, no credentials, and a JSON `POST`.

### Recommendation
Change `verify_webhook_signature` to fail closed when no secret is configured (e.g., reject/log instead of auto-accepting), or require `webhook_secret` to be mandatory at boot/config-validation time. Additionally, `MembershipHandler` (and any handler that mutates authorization-relevant state) should not be reachable at all unless signature verification genuinely validated a cryptographic match against a configured secret for the exact organization implicated by the event.

### Proof of Concept
1. Deploy Shipit with the documented/default configuration where `github.webhook_secret` is left blank (as in `config/secrets.development.example.yml` / `test/dummy/config/secrets.test.json`).
2. As an anonymous attacker, send:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "organization": {"login": "<configured-org>"},
  "team": {"id": 99, "name": "Trusted Team", "slug": "trusted-team", "url": "https://example.com"},
  "member": {"login": "attacker-github-login"}
}
```
`verify_webhook_signature` returns `true` (no secret configured) regardless of signature header, and `MembershipHandler` creates the `Team`/`Membership` records tying `attacker-github-login` to `trusted-team`.
3. Attacker logs into Shipit via the real GitHub OAuth flow using `attacker-github-login`.
4. `User#authorized?` finds the forged `Membership` and returns `true`, granting the attacker full access as if they were a legitimate member of `Shipit.github_teams`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    end

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
