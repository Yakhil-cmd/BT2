### Title
Signature verification keyed on `repository.owner.login` while handler resolves repository via `repository.full_name` allows cross-org forged `pull_request` webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` used to authenticate the HMAC signature solely from `repository.owner.login` (via `repository_owner`), while `LabelCapturingHandler` (and its siblings) resolve the actual `Repository`/`Stack` to mutate from the independent, attacker-controlled `repository.full_name` field. If any org configured on the Shipit instance has no `webhook_secret` set, an attacker can set `repository.owner.login` to that org and `repository.full_name` to `victim-org/victim-repo`, causing `verify_webhook_signature` to short-circuit true (`return true unless webhook_secret`) while the handler mutates a stack belonging to a completely different, secret-protected org.

### Finding Description
The broken binding, stated as an equality that the code assumes but does not enforce: `repository_owner (used in verify_signature) == owner(repository.full_name) (used in the handler's repository lookup)`. In `app/controllers/shipit/webhooks_controller.rb`, `verify_signature` picks the app/secret via `Shipit.github(organization: repository_owner)` [1](#0-0)  where `repository_owner` reads `params.dig('repository', 'owner', 'login')` [2](#0-1) . In `lib/shipit/github_app.rb#verify_webhook_signature`, if the resolved org's config has no `webhook_secret`, the method returns `true` unconditionally, skipping HMAC validation entirely: `return true unless webhook_secret` [3](#0-2) . Meanwhile `LabelCapturingHandler#repository` resolves the repository to act on using `params.repository.full_name`, completely independent of `repository.owner.login`: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [4](#0-3) , and `Repository.from_github_repo_name` simply splits the string on `/` with no cross-check against `repository.owner.login`: `repo_owner, repo_name = github_repo_name.downcase.split('/')` [5](#0-4) .

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, body `{"action":"unlabeled","number":N,"pull_request":{...,"labels":[{"name":"ATTACKER_INJECTED"}]},"repository":{"owner":{"login":"no-secret-org"},"full_name":"victim-org/victim-repo"},"sender":{"login":"attacker"}}`. `verify_signature` looks up `Shipit.github(organization: "no-secret-org")`; since that org has no `webhook_secret` configured, `verify_webhook_signature` returns `true` without checking `X-Hub-Signature` at all — the attacker needs no secret. The request proceeds to `LabelCapturingHandler`, which resolves `repository` from `full_name = "victim-org/victim-repo"`, finds the real `Repository`/`ReviewStack` under `victim-org`, and calls `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [6](#0-5) . Those attacker-chosen label strings persist on `victim-org`'s `PullRequest` and, per `ReviewStack#env`, later get uppercased into environment variable keys that flow into deploy/task commands for that stack — a payload aimed at one repo's org config mutating a different, unrelated org's stack state.

No existing guard prevents this: `drop_unhandled_event` only checks the event type exists; `verify_signature` never cross-validates `repository.owner.login` against `repository.full_name`'s owner segment; `ExplicitParameters` schema for `LabelCapturingHandler` only requires `repository.full_name` to be a `String`, with no relation constraint to `repository.owner.login`; no model validation ties the two together at the controller layer.

### Impact Explanation
An unauthenticated, unprivileged attacker can write arbitrary PR label data onto any tracked stack belonging to any org, as long as at least one org on the Shipit instance is configured without a `webhook_secret`. Since captured labels become uppercased environment variable keys/values consumed by `ReviewStack#env` and ultimately merged into deploy-time environments, this is a cross-tenant "payload for one repository mutating another's stack" scenario — matching the Critical impact category. It is repeatable against any repository/stack whose `full_name` the attacker can guess or discover, and the blast radius spans every org and repo hosted on the same Shipit instance, not just the misconfigured one.

### Likelihood Explanation
Requires the operational precondition that at least one configured GitHub org/app entry omits `webhook_secret` — a config choice not enforced as invalid by this engine. Given that precondition, exploitation costs nothing beyond crafting one unauthenticated HTTP POST with attacker-controlled JSON; no signature, session, API token, or GitHub credentials are needed, and the request is trivially repeatable.

### Recommendation
In `Shipit::WebhooksController#verify_signature`, derive the org used for signature verification from the same field the downstream handler uses to resolve the target repository (i.e., parse the owner from `repository.full_name`), or explicitly reject the webhook when `repository.owner.login` does not match the owner segment of `repository.full_name`. Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank for orgs that own tracked repositories — either require `webhook_secret` for every configured org or refuse to process webhooks for repositories under such orgs.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` (conceptual, not modifying restricted paths):
1. Configure two orgs in test config: `no-secret-org` (no `webhook_secret`) and `victim-org` (`webhook_secret` set), each stubbed via `Shipit.github(organization:)`.
2. Create a `Shipit::Stack`/`ReviewStack` and `PullRequest` fixture under `victim-org/victim-repo`.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no valid `X-Hub-Signature`, body: `repository.owner.login = "no-secret-org"`, `repository.full_name = "victim-org/victim-repo"`, `action = "unlabeled"`, `pull_request.labels = [{name: "INJECTED"}]`.
4. Assert `response.status == 200` (accepted despite invalid/absent signature) — left side of equality: `repository_owner == "no-secret-org"`; right side: owner of `repository.full_name == "victim-org"` — mismatch, proving the invariant "a `pull_request` event only affects the repository/stack whose secret authenticated it" is violated.
5. Assert `victim_org_pull_request.reload.labels == ["INJECTED"]`, proving the victim org's `PullRequest` was mutated using a signature check that was actually performed (trivially, due to no-secret) against an unrelated org.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
