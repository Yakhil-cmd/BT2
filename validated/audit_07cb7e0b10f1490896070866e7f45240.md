### Title
Unauthorized Cosigner Injection into Arbitrary Wallets via `my_xpubkey` Device Message - (File: wallet_defined_by_keys.js)

### Summary
`ocore`'s device-message handler accepts a `my_xpubkey` message even from a non-correspondent (unpaired) device and calls `addDeviceXPubKey(wallet, device_address, xPubKey, onDone)` with the `wallet` id taken verbatim from the attacker-controlled message body. The function correctly attributes the new `extended_pubkeys` row to the sender's own `device_address` (the "owner" is bound correctly), but it never verifies that `from_address` is actually one of the device addresses referenced in that wallet's `definition_template` (i.e., that the sender is a legitimate cosigner of the target wallet) before inserting/updating a row keyed on `(wallet, device_address)`. This mirrors the PeerTube CVE-2025-32946 pattern: the actor identity is set correctly, but the target resource id supplied in the request is trusted without an ownership/membership check.

### Finding Description
The message dispatcher in [1](#0-0)  handles subject `"my_xpubkey"` and is explicitly whitelisted to be processed from devices that are not even known correspondents: [2](#0-1) 

The handler only checks that `body.wallet` and `body.my_xpubkey` are non-empty strings within length limits, then calls `walletDefinedByKeys.addDeviceXPubKey(body.wallet, from_address, body.my_xpubkey, callbacks.ifOk)` — `wallet` is fully attacker-supplied: [1](#0-0) 

`addDeviceXPubKey` performs no check that `wallet` exists as a wallet the sender is entitled to join, nor that `device_address` (the sender) is part of that wallet's `definition_template`: [3](#0-2) 

Contrast this with the legitimate wallet-creation path `handleOfferToCreateNewWallet`, which explicitly validates via `validateWalletDefinitionTemplate` that `from_address` is one of the device addresses derived from the definition template before any wallet state is created: [4](#0-3) [5](#0-4) 

No equivalent membership check exists in `addDeviceXPubKey`, so any device that learns (or guesses/observes) a victim's wallet id (a base64 hash of the initiator's xPubKey, exchanged during pairing and visible on the wire/in message bodies) can insert an `extended_pubkeys` row for that wallet under its own `device_address`, effectively self-appointing as an (unauthorized) participant record tied to someone else's wallet — analogous to the PeerTube bug of associating a new owned resource with an arbitrary target id without checking that the id belongs to the caller.

### Impact Explanation
The injected row is picked up by every function that enumerates wallet participants by `SELECT ... FROM extended_pubkeys WHERE wallet=?`:
- `deriveAddress`, used whenever any new wallet address is derived, reads all extended_pubkeys rows for the wallet: [6](#0-5) 
- `issueAddress` iterates all `extended_pubkeys` rows for the wallet and sends the freshly-issued wallet address to every listed `device_address`, including the attacker's injected row, leaking the victim's addresses to the attacker: [7](#0-6) 
- `readCosigners`, used to enumerate/display a wallet's cosigners, throws an uncaught `Error("cosigner not found among correspondents...")` for any `extended_pubkeys` row whose `device_address` is not a known correspondent — which is guaranteed for the attacker's injected row since the victim never paired with the attacker: [8](#0-7) 

This can (a) leak newly generated receiving/change addresses of a victim wallet to an unrelated device, undermining privacy of a private/multisig wallet's cosigner set, and (b) crash/break any code path that calls `readCosigners` for the affected wallet, disrupting the victim's ability to operate that wallet (a denial-of-service against the wallet, i.e. a freezing effect on interacting with that wallet's funds) until the spurious row is manually purged from the database.

### Likelihood Explanation
The precondition is knowledge of a target `wallet` id. Wallet ids are base64 SHA-256 hashes of an xPubKey and are transmitted in cleartext device-message bodies (`create_new_wallet`, `my_xpubkey`, `wallet_fully_approved`, `new_wallet_address`) to cosigners and to the hub for relaying; a hub operator, a device that was briefly paired/unpaired, or anyone who intercepts/observes such traffic can obtain it. The attack requires no correspondent relationship — the code path is explicitly whitelisted for non-correspondents — and requires only a single crafted `my_xpubkey` justsaying message routed via the hub to the victim's device address, which any device can send once it knows (or is given) the victim's device address and wallet id.

### Recommendation
In `addDeviceXPubKey` (and in the `my_xpubkey` dispatch case in `wallet.js`), before inserting/updating `extended_pubkeys`, verify that `device_address` is one of the device addresses derivable from that wallet's stored `definition_template` (the same check already performed in `validateWalletDefinitionTemplate`/`handleOfferToCreateNewWallet`). Reject the message if the sender is not among the wallet's expected cosigner device addresses, and make `readCosigners` tolerant of unexpected rows (return an error instead of throwing) as defense in depth.

### Proof of Concept
1. Attacker device A learns victim's wallet id `W` (e.g., by observing a `create_new_wallet`/`my_xpubkey` device message exchanged between victim's own devices, or via a hub it operates).
2. Attacker crafts a device message with `subject: "my_xpubkey"`, `body: {wallet: W, my_xpubkey: "<attacker xpub>"}`, and sends it via the hub to the victim's device address (allowed even though A is not a correspondent of the victim, per the whitelist in `device.js`).
3. Victim's node processes the message via `wallet.js`'s `"my_xpubkey"` case and calls `walletDefinedByKeys.addDeviceXPubKey(W, A, "<attacker xpub>", ...)`, which unconditionally `INSERT`s/`UPDATE`s a row `(wallet=W, device_address=A, extended_pubkey=..., approval_date=now)` into `extended_pubkeys` without checking that `A` belongs to `W`'s definition template.
4. Subsequent calls to `issueAddress(W, ...)` on the victim's node now also notify device `A` of every newly issued address for wallet `W`, and any call to `readCosigners(W, ...)` throws an uncaught exception because `A` is not in `correspondent_devices`, disrupting the victim's wallet UI/flow for `W`.

		FROM extended_pubkeys LEFT JOIN correspondent_devices USING(device_address) WHERE wallet=?", 
		[wallet],

			rows.forEach(function(row){
				if (row.device_address === device.getMyDeviceAddress()){
					if (row.name !== null)
						throw Error("found self in correspondents");
					row.me = true;
				}
				else if (row.name === null)
					throw Error("cosigner not found among correspondents, cosigner="+row.device_address+", my="+device.getMyDeviceAddress());
			});
			handleCosigners(rows);
		}
	);
}

function deriveAddress(wallet, is_change, address_index, handleNewAddress){
	db.query("SELECT definition_template, full_approval_date FROM wallets WHERE wallet=?", [wallet], function(wallet_rows){
		if (wallet_rows.length === 0)
			throw Error("wallet not found: "+wallet+", is_change="+is_change+", index="+address_index);
		if (!wallet_rows[0].full_approval_date)
			throw Error("wallet not fully approved yet: "+wallet);
		var arrDefinitionTemplate = JSON.parse(wallet_rows[0].definition_template);
		db.query(
			"SELECT device_address, extended_pubkey FROM extended_pubkeys WHERE wallet=?", 
			[wallet], 
			function(rows){
				if (rows.length === 0)
					throw Error("no extended pubkeys in wallet "+wallet);
				var path = "m/"+is_change+"/"+address_index;
				var params = {};
				rows.forEach(function(row){
					if (!row.extended_pubkey)
						throw Error("no extended_pubkey for wallet "+wallet);
					params['pubkey@'+row.device_address] = derivePubkey(row.extended_pubkey, path);
					console.log('pubkey for wallet '+wallet+' path '+path+' device '+row.device_address+' xpub '+row.extended_pubkey+': '+params['pubkey@'+row.device_address]);
				});
				var arrDefinition = Definition.replaceInTemplate(arrDefinitionTemplate, params);
				var address = objectHash.getChash160(arrDefinition);
				handleNewAddress(address, arrDefinition);
			}
		);
	});
}
