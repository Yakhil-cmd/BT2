### Title
`Shipit.github` permanently memoizes `GitHubApp` (and its `webhook_secret`) per organization, causing stale webhook signature verification after credential rotation - ([File: lib/shipit.rb])

### Summary
`Shipit.github(organization:)` caches `GitHubApp` instances forever in the process-lifetime `@github` hash, and `GitHubApp#initialize` captures `webhook_secret` from the config at construction time into a `private` `attr_reader`. If the operator rotates `webhook_secret` in the secrets store without restarting the Shipit process, `WebhooksController#verify_signature` continues to verify incoming webhooks against the old, rotated-out secret because it reuses the memoized `GitHubApp` object rather than rebuilding it from current config.

### Finding Description
The binding that must hold is: `GitHubApp#webhook_secret` used by `verify_webhook_signature` for organization `org` **==** `Shipit.secrets.github[org][:webhook_secret]` (the currently configured value) at the time each request is verified.

Trace:
- `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` on every request: [1](#0-0) 
- `Shipit.github` looks up `@github[organization]` and only constructs a new `GitHubApp` `if` the entry is absent — `@github[organization] ||= GitHubApp.new(organization, config)` — even though `config = github_app_config(organization)` is freshly recomputed from `secrets` on every call: [2](#0-1) 
- `GitHubApp#initialize` captures the secret once, at construction: `@webhook_secret = @config[:webhook_secret].presence`, exposed only via a private reader, with no reload path: [3](#0-2) [4](#0-3) 
- `verify_webhook_signature` HMAC-compares the incoming `X-Hub-Signature` against `webhook_secret`, i.e. the stale, memoized value, not the live config: [5](#0-4) 

There is no reset/invalidation of `@github` anywhere in the codebase (confirmed no `reload!`/cache-busting logic exists outside test files). So once any request for organization `org` populates `@github[org]`, that `GitHubApp` — and its captured `webhook_secret` — lives for the remainder of the process, regardless of subsequent secret rotations in the underlying credentials/secrets store.

Exploit flow: attacker who has obtained a previously valid (now rotated-out) `webhook_secret` for `org` sends `POST /webhooks` with `repository.owner.login = org` and a valid HMAC computed with the old secret. As long as any earlier request already caused `Shipit.github(organization: 'org')` to memoize (which happens on essentially every legitimate webhook before rotation), the controller accepts the forged signature and dispatches to `Shipit::Webhooks.for_event(event)` handlers, exactly as if it came from GitHub.

None of the existing guards address this: `drop_unhandled_event` and `check_if_ping` only filter by event type; `verify_signature` is the exact code performing the (stale) check; there is no `ExplicitParameters` schema, `force_github_authentication`, or model validation involved before the signature check runs.

### Impact Explanation
An attacker holding a leaked, subsequently-rotated `webhook_secret` for an organization can continue to forge webhook payloads (`push`, `pull_request`, `status`, `check_suite`, etc.) that are dispatched by `Shipit::Webhooks.for_event`, driving stack state, commit status, and deploy-relevant webhook handling as if genuinely from GitHub — an authentication bypass on the webhook ingress. This affects only the specific organization whose secret leaked and was rotated, and is repeatable for the remainder of the process lifetime (until process restart) any number of times. This matches the "authentication bypass (forged webhook ... accepted)" Critical impact category structurally, but per the question's own framing the precondition (an already-leaked secret) narrows real-world severity — classified as High per the question's guidance, reflecting an authentication/staleness bug in credential rotation handling rather than a bypass achievable without any secret knowledge.

### Likelihood Explanation
Requires: (1) attacker previously obtained a valid `webhook_secret` for the target org (out of scope to explain how — assumed per the question), (2) the operator rotates that secret in the secrets/credentials store without restarting the Shipit process (an operationally plausible but not universal deployment pattern), and (3) `Shipit.github(organization:)` was already memoized for that org (true after essentially any request, including the operator's own webhook traffic, prior to rotation). Given these preconditions, the attack is trivial and fully repeatable — a single crafted HTTP POST with correct old-secret HMAC per exploitation.

### Recommendation
Do not permanently cache `GitHubApp` instances keyed only by organization; either re-read `webhook_secret` (and other config) from `Shipit.secrets` on each `verify_webhook_signature` call, or invalidate/rebuild the memoized `GitHubApp` when the underlying config for that organization changes (e.g. compare a config digest/version before reusing the cached instance in `Shipit.github`).

### Proof of Concept
```ruby
# test/unit/github_app_rotation_test.rb (concept, not to be run in this repo per OUT-OF-SCOPE rules)
test "Shipit.github memoizes a stale webhook_secret across rotation" do
  Shipit.instance_variable_set(:@github, nil)
  stub_secrets_github(x: { webhook_secret: "old-secret" })

  app = Shipit.github(organization: "x")
  old_secret_binding = app.send(:webhook_secret)
  assert_equal "old-secret", old_secret_binding

  # simulate live rotation without process restart
  stub_secrets_github(x: { webhook_secret: "new-secret" })

  # BROKEN BINDING: memoized instance's webhook_secret should equal
  # Shipit.secrets.github[:x][:webhook_secret] ("new-secret") but doesn't
  refetched = Shipit.github(organization: "x")
  assert_equal old_secret_binding, refetched.send(:webhook_secret) # still "old-secret"
  refute_equal "new-secret", refetched.send(:webhook_secret)
end
```
This demonstrates the memoized `webhook_secret` diverges from the live configured secret, which is the root cause enabling `verify_webhook_signature` to accept HMACs computed with a rotated-out secret.

    # Backward compatibility

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
