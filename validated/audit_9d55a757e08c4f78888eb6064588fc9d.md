### Title
Attacker-controlled repo content can force `SyncRepo` to fail deterministically, causing `--max-failures`/`os.Exit` to permanently halt sync (persistent sync denial) - (File: `main.go`)

### Summary
The C4 finding describes how `AutoExit`/`AutoRange` unconditionally trust externally-controlled NFT position state fetched inside `execute()`, so a single attacker-influenced input can make that state permanently invalid and the automated transformer will keep reverting forever, denying the position owner recovery/rebalancing. The structurally equivalent pattern in `git-sync` is the main sync loop's failure-handling logic in `main.go`: on any error from `git.SyncRepo`, the failure counter is incremented and, once it reaches `--max-failures` (which defaults to `0`, i.e. the very first failure), the whole process calls `os.Exit(1)` [1](#0-0) . Because git-sync persists its git state under `--root` across restarts, a remote commit that deterministically breaks one of the fixed pipeline steps (`fetch`, `reset`, `worktree add`, submodule update, sparse-checkout) will keep failing identically on every subsequent process restart, producing a durable denial of the sync/publish function rather than a transient one.

### Finding Description
`SyncRepo` runs a fixed sequence of git operations against content pulled from the (potentially attacker-writable) upstream repository: `fetch` [2](#0-1) , then `createWorktree`/`configureWorktree`, which performs `git reset --hard <hash>` and, unless `--submodules=off`, `git submodule update --init [--recursive] [--depth N]` on whatever `.gitmodules` / tree structure the attacker committed [3](#0-2) . If a committed tree causes any of these commands to fail (for example, a submodule pointing at an unreachable/invalid URL, a `.gitmodules` entry that conflicts with sparse-checkout configuration, or a path that collides with git-sync's own internal `.git`/`gitdir` rewrite at `worktree.Path().Join(".git")` [4](#0-3) ), `SyncRepo` returns an error every single sync attempt for that ref, since the underlying commit content driving the failure never changes.

Back in the main loop, this failure is counted and compared against `getMaxFailures()`, which returns `--max-failures` (default `0`) once past the initial-sync phase [5](#0-4) , and once the threshold is met the process performs `os.Exit(1)` unconditionally [6](#0-5) . Unlike a purely transient network error, an error rooted in the committed tree/ref content will reproduce identically on process restart because git-sync's local repository state under `--root` is retained and the same broken ref/commit is fetched and processed again, so the sidecar enters a permanent crash loop and never republishes the symlink that downstream consumers rely on (the "contract" described in `README.md:190-203`) [7](#0-6) .

### Impact Explanation
This is a persistent sync denial: once an attacker with write/push access to the synced ref lands a commit that trips one of the fixed git operations in `configureWorktree`/`fetch`, git-sync will exit on the very first attempt (default `--max-failures=0`) and will keep failing identically after every Kubernetes pod restart, because the on-disk repo state and the broken remote ref are unchanged. Consumers relying on the `--link` symlink contract stop receiving updates entirely (not just a missed rebalance, but total sync outage) until an operator intervenes manually (e.g., reverting the bad commit or wiping `--root`). This matches the class of impact called out in the source finding — "persistent sync denial" and "publishing wrong or partial content" is avoided (git-sync fails closed rather than publishing bad data), but the "denial" impact is directly analogous to the referenced AutoExit/AutoRange DOS.

### Likelihood Explanation
Likelihood depends entirely on whether the attacker has write access to the synced repository/ref (a git-sync administrator's threat model already assumes the synced repo may originate from an external, less-trusted source, e.g. a GitOps config repo with multiple contributors, or public repos with submodules from third parties). Given push access, this is trivially and reliably reproducible — no race condition or timing dependency is required, and the default configuration (`--max-failures=0`) makes even a single bad commit terminal. Operators who explicitly raise `--max-failures`/`--init-max-failures` to a negative value are not affected, so likelihood is conditioned on default or low failure-tolerance configurations.

### Recommendation
- Treat single-cycle git-command failures more defensively: distinguish between transient (network/timeout) errors and deterministic content-driven failures where retrying with the same input cannot succeed, and surface actionable diagnostics rather than a bare process exit.
- Consider not defaulting `--max-failures` to `0`, or documenting more prominently that a value of `0` means "any content-triggered failure is fatal and will recur across restarts."
- Add guardrails in `configureWorktree` for submodule operations (e.g., restricting protocols, validating `.gitmodules` before invoking `submodule update`) so malformed/malicious submodule configs fail predictably with a clear, isolated error rather than aborting the whole sync loop.

### Proof of Concept
1. Configure git-sync with defaults: `--repo=<attacker-writable-repo> --root=/mnt/git --link=link` (no `--max-failures` override, so it defaults to `0`) [8](#0-7) .
2. As a contributor with push access to `<attacker-writable-repo>`, add a submodule entry in `.gitmodules` pointing at a URL/protocol that will always fail to fetch/update in the git-sync container's network context (e.g., an unreachable host, or a path that conflicts with sparse-checkout state), and push this commit to the tracked ref.
3. On the next sync cycle, `git.fetch` succeeds but `configureWorktree`'s `git submodule update --init …` step fails deterministically [9](#0-8) , causing `SyncRepo` to return an error.
4. `main`'s loop increments `failCount` to `1`, which meets `getMaxFailures()==0`, so it logs "too many failures, aborting" and calls `os.Exit(1)` [6](#0-5) .
5. Because the broken commit is already the tip of the tracked ref and `--root` retains the git state, any pod/container restart re-fetches the same ref and hits the same submodule failure again, repeating step 3–4 indefinitely — the symlink is never updated and the sidecar never reaches ready state, verifying persistent sync denial.

// fetch retrieves the specified ref from the upstream repo.
func (git *repoSync) fetch(ctx context.Context, ref string) error {
	git.log.V(2).Info("fetching", "ref", ref, "repo", redactURL(git.repo))

	// Fetch the ref and do some cleanup, setting or un-setting the repo's
	// shallow flag as appropriate.
	args := []string{"fetch", git.repo, ref, "--verbose", "--no-progress", "--prune", "--no-auto-gc"}
	if git.depth > 0 {
		args = append(args, "--depth", strconv.Itoa(git.depth))
	} else {
		// If the local repo is shallow and we're not using depth any more, we
		// need a special case.
		shallow, err := git.isShallow(ctx)
		if err != nil {
			return err
		}
		if shallow {
			args = append(args, "--unshallow")
		}
	}
	if git.filter != "" {
		args = append(args, "--filter", git.filter)
	}
	if _, _, err := git.Run(ctx, git.root, args...); err != nil {
		return err
	}

	return nil
}

    One of the things in that directory is a symlink (see the --link flag) to
    the most recently synced data.  This is how the data is expected to be
    consumed, and is considered to be the "contract" between git-sync and
    consumers.  The exact target of that symlink is an implementation detail,
    but the leaf component of the target (i.e. basename "$(readlink <link>)")
    is the git hash of the synced revision.  This is also part of the contract.

    Why the symlink?  git checkouts are not "atomic" operations.  If you look
    at the repository while a checkout is happening, you might see data that is
    neither exactly the old revision nor the new.  git-sync "publishes" updates
    via the symlink to present an atomic interface to consumers.  When the
    remote repo has changed, git-sync will fetch the data _without_ checking it
    out, then create a new worktree, then change the symlink to point to that
    new worktree.
