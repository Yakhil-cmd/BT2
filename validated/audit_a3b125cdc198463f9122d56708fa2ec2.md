## Title
Webhook signature verified against `repository.owner.login`'s secret while the target repository/stack is selected from the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/HMAC secret to validate a webhook against using `repository.owner.login` (or `organization.login`) from the JSON body, but the actual repository/stack that gets mutated by the event handlers is resolved from the independent `repository.full_name` field via `Handler#repository_name`/`Repository.from_github_repo_name`. Because these two fields are never reconciled, an attacker who legitimately controls the webhook secret for *any* organization configured in Shipit can forge a payload whose `owner.login` matches their own org (so the signature check passes) while `full_name` points at a completely different organization's repository, causing Shipit to act on a stack the attacker does not own.

### Finding Description
Signature verification:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This only proves the caller possesses the webhook secret configured for organization `repository_owner`, which is fully attacker-controlled per Shipit's multi-tenant `github:` config (see multiple orgs configured in `test/dummy/config/secrets_double_github_app.yml` / `config/secrets.development.shopify.yml`). [2](#0-1) 

Once verified, every event handler resolves the *target* repository from a different field, `repository.full_name`, with no cross-check against `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`Repository.from_github_repo_name` simply splits `owner/name` and looks up any matching `Repository` row, regardless of which org's secret validated the request:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [4](#0-3) 

The binding that is broken: `organization authenticated by verify_signature (repository.owner.login)` == `organization of the repository actually written (repository.full_name)`. The `stake()`-style check only validates the first half but the second half is what handlers act on, exactly mirroring the reported bug class where a limit is checked against one accounting variable while the real state is governed by another that was never reconciled.

Concretely, `PushHandler#process` acts on `stacks` (derived from the forged `full_name`) and calls `stack.sync_github(...)` for any matching branch:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

The `status` webhook handler similarly creates/updates a `Status` for a commit belonging to whatever repository `full_name` resolves to (see test coverage creating a `Status` for `commit` based on `repository_params` merged into the payload). [6](#0-5) 

### Impact Explanation
An attacker who is a legitimate administrator of Organization A (and therefore knows Organization A's webhook secret because they installed Shipit's GitHub App on their own org) can send a webhook whose `repository.owner.login` is `"org-a"` (passing signature verification) but whose `repository.full_name` is `"org-b/victim-repo"`. This lets the attacker:
- Trigger `sync_github` / `GithubSyncJob` on Organization B's stacks via forged `push` events, and
- Inject forged commit `Status` records for Organization B's commits via forged `status` events, which can be used to satisfy Shipit's CI-gating checks (`ignore_ci`/status requirements) and enable an otherwise-blocked deploy.

This is a cross-organization write into another tenant's Shipit data using only credentials the attacker legitimately holds for their own, unrelated organization — matching the "Critical: cross-repository writes / unauthorized deploy" impact bar.

### Likelihood Explanation
Likelihood is Medium-High in any multi-tenant Shipit deployment (the shipped example configs explicitly support multiple organizations, e.g. `OrgTwo` in `test/dummy/config/secrets_double_github_app.yml`). Any org admin who can install/configure the Shipit GitHub App for their own org (an action requiring no special trust from Shipit's operator) already holds a valid secret for `verify_signature`, and the payload fields (`repository.owner.login` vs `repository.full_name`) are both attacker-controlled JSON in the same signed body — no additional secret or privilege is needed to decouple them.

### Recommendation
Reconcile the two identities before dispatching to handlers: derive the authorized organization once (from `repository.owner.login`), and require that `repository.full_name`'s owner segment matches that same organization before resolving `Repository`/`Stack` records in `Handler#stacks`. Reject (422) any webhook where `repository.full_name`'s owner does not equal the organization whose secret validated the signature.

### Proof of Concept
1. Attacker administers GitHub App installation for `org-a` on Shipit and knows `org-a`'s `webhook_secret` (legitimately, from Shipit's own multi-org config, e.g. as shown in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already known to belong to org-b/victim-repo>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `org-a`'s webhook secret and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and verifies successfully (`repository_owner` resolves to `org-a`). [7](#0-6) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")`, which is unrelated to `org-a`, and triggers `sync_github`/`GithubSyncJob` for `org-b`'s stack. [5](#0-4)

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      Rails.logger.info([

        "status=#{status}"
      ].join(' '))
    end
