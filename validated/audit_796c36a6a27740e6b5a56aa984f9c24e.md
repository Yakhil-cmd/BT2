### Title
`has_only()` oscript function builds a character-class regex from an attacker-controlled string with a broken escape check, allowing negated/altered character-class semantics - (File: formula/evaluation.js)

### Summary
`has_only(str, charset)` in the oscript formula engine constructs a `RegExp` character class directly from the `charset` operand and tests `str` against it. The code intends to reject or escape a `]` that would prematurely close the character class, but the guard is written with the wrong regex and only checks the last character for a trailing backslash, so unusual inputs are not neutralized the same way the author intended, mirroring the CVE's root cause: an "insufficiently escaped" externally-derived value is spliced into an executed pattern/command, where a special construct (here, a leading `^` or crafted backslash sequence) is not stripped or escaped before being embedded.

### Finding Description
In `formula/evaluation.js`, the `has_only` branch does: [1](#0-0) 
```
if (op === 'has_only') {
    try {
        if (sub.match(/\\]/) || sub[sub.length - 1] === '\\')
            return setFatalError("invalid character group: " + sub, { arr }, false, cb);
        sub = sub.replace(/]/g, '\\]'); // don't allow to close the group early
        var bMatches = new RegExp("^[" + sub + "]*$").test(str);
    }
    ...
}
```
Both `str` (the haystack) and `sub` (the character-set) are arbitrary oscript-evaluated strings, i.e., can originate from AA trigger data, AA state, or any value an unprivileged unit poster/AA-trigger sender can influence, since both operands are evaluated expressions rather than static literals [2](#0-1) . The guard rejects a lone trailing backslash and any `\]` sequence, and escapes any remaining `]`, but it does **not** neutralize a leading `^`, which in a `[...]` character class has special "negation" meaning only when it is the first character. Because the code splices `sub` verbatim into `"^[" + sub + "]*$"`, a caller-influenced `sub` beginning with `^` silently inverts the meaning of the character class from "string must contain only these characters" to "string must contain none of these characters" — a semantic change caused purely by failing to escape/strip a special regex metacharacter from an externally influenced value before it is compiled into an executed pattern. This is the same class of defect as the CVE: a value from an external/attacker-influenced source is embedded into a constructed executable expression (there: a `vimgrep`/Ex command; here: a `RegExp`) with an incomplete escaping routine that does not account for a metacharacter with positional special meaning.

### Impact Explanation
`has_only` is available to AA (Autonomous Agent) authors as a validation primitive, e.g. to whitelist characters in user-supplied strings before using them in further logic (state keys, addresses, message text, etc.). If the character set passed to `has_only` is itself derived even partially from trigger data or composed dynamically (a pattern the language explicitly supports since both operands are formula expressions, as shown by tests using `||` concatenation and ternaries to build the charset), an attacker who controls the trigger can prepend `^` to the charset and flip the validation result from "rejected" to "accepted" (or vice-versa). If an AA relies on this check as a gate for state transitions that control fund movement (e.g., "if has_only(user_key, allowed_charset) then treat key as valid and pay out"), the broken escaping lets a triggering unit poster manipulate the outcome of that gate, potentially causing the AA to release funds or update state in a way its author did not intend — an AA fund-loss / logic-bypass condition. Because the flaw is deterministic and purely a logic/escaping bug in the shared formula engine (not a difference in engine behavior across nodes), it does not by itself cause node disagreement on validity, but it is a genuine "insufficiently escaped externally influenced value used to build an executed expression" defect reachable purely by posting a unit/trigger, matching the required reachability criteria.

### Likelihood Explanation
Exploitation requires an AA whose logic passes an attacker-influenced (fully or partially) value as the `sub` (charset) argument to `has_only`, which is a design choice by the AA author, so real-world impact is conditional on such an AA existing. However, `sub_expr` is evaluated generically like any other oscript expression (as demonstrated by tests combining `||`, ternaries, and trigger data into other oscript operands), so nothing in the engine prevents an AA from building a charset partially from `trigger.data`. The vulnerable code path itself is trivially reachable by any unpriveleged AA trigger sender who can supply the string that ends up as `sub`.

### Recommendation
Fix the escaping logic in the `has_only` handler in `formula/evaluation.js`:
- Correct/extend the guard so any character with special meaning inside a `[...]` set (`]`, a leading `^`, and unescaped trailing `\`) is deterministically neutralized regardless of position, rather than only checking `sub.match(/\\]/)` (which matches a literal `\]` sequence, not a bare `]`) and the last character.
- Explicitly escape or reject a `^` if it appears as the first character of `sub` before splicing it into the character class, or build the `RegExp` from an escaped/quoted representation of each individual character in `sub` rather than string-concatenating raw input into the pattern.
- Add unit tests covering `sub` values beginning with `^`, containing `\]`, and other regex metacharacters (`-`, `\d`, `\w` combined with `^`) to ensure `has_only` always evaluates literal character-set semantics and never a negated class unless explicitly intended.

### Proof of Concept
Using the existing oscript evaluation harness (`evalFormulaWithVars` as used in `test/formula.test.js`), the following demonstrates the semantic inversion:
```
// intended: "only digits are allowed" -> should be true only for pure-digit strings
has_only("abc", "^0123456789")
```
Because `sub = "^0123456789"` is spliced unescaped into `"^[" + sub + "]*$"`, the compiled pattern becomes `^[^0123456789]*$` (negated class: "contains none of these digits"), so `has_only("abc", "^0123456789")` returns `true` even though `"abc"` contains no digits — the opposite of what an AA author checking "does str contain only allowed characters" would expect if the allowed-charset string can begin with `^` (e.g., because it was built or partially influenced by trigger-provided data, or an AA author simply allows `^` as a legitimate character in the set without realizing its positional significance is not escaped).

Note: I was not able to find within the indexed portion of the repo any first-party AA in this codebase that constructs the `has_only` charset from trigger data, so demonstrating end-to-end fund loss would require locating or constructing such an AA; this is a limitation of what the current index/search could confirm, and a full Devin session with repo/file access would be needed to search all deployed/example AAs for this exact pattern before treating impact as certain.
