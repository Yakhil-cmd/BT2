## Title
Asset definer can retroactively invalidate attestations via `asset_attestors`, permanently freezing funds already held by previously-attested users - (File: `validation.js`, `storage.js`)

### Summary
The reported Footium bug is a "trusted state overwrite" pattern: the owner of `FootiumPrizeDistributor` can call `setERC20MerkleRoot`/`setEthMerkleRoot` at any time, instantly invalidating every previously-valid Merkle proof and freezing funds that were reserved for the old root. Ocore has a structurally identical pattern for `spender_attested` assets: the asset **definer** can unilaterally post a new `asset_attestors` message that replaces the trusted attestor list used to authorize spending, with no continuity guarantee for holders who were legitimately attested under the previous list.

### Finding Description
When an asset is created with `spender_attested: true`, spending/output validation requires the owner address to be found in `objAsset.arrAttestedAddresses`, which is derived from attestations matching the **current, single latest** attestor list for that asset: [1](#0-0) 

`filterAttestedAddresses` only accepts attestation records whose `attestor_address` is in `objAsset.arrAttestorAddresses` — i.e. the current list, not any historically valid list: [2](#0-1) 

The check is enforced in payment validation for both issuance and transfer of the asset: [3](#0-2) [4](#0-3) [5](#0-4) 

The attestor list itself can be replaced at any time by the definer via a single-authored `asset_attestors` message. The only validation performed is that the sender is the asset's `definer_address` and that the new list is well-formed — there is no restriction preventing the definer from dropping/rotating attestors that had already attested existing holders: [6](#0-5) 

Because `readAsset`/`addAttestorsIfNecessary` only ever looks at the single most-recent `asset_attestors` unit (`ORDER BY level DESC LIMIT 1`), older attestor lists — and by extension the attestations issued by those older attestors — are completely discarded for authorization purposes as soon as a newer list becomes stable, exactly like a Merkle root replacement discarding all proofs generated against the old root.

### Impact Explanation
Any holder of a `spender_attested` asset who received/held coins based on an attestation from an attestor that is later removed from the list becomes permanently unable to spend those coins (`"owner address is not attested"`), unless a currently-listed attestor re-attests them — an action outside the holder's control. Since ordinary token holders are neither the asset definer nor an attestor, they have no way to prevent or reverse this: the definer can freeze/strand funds of any subset of legitimate, already-attested holders simply by publishing a new `asset_attestors` list, at will and after the fact. This is a fund-freezing/fund-loss condition equivalent in class to the reported Merkle-root issue, reachable purely from ordinary posted units (asset issuance + `asset_attestors` message) without any privileged node/hub/network-level capability beyond being the asset's own definer — the same "privileged owner action harms unprivileged counterparties" pattern flagged in the source report.

### Likelihood Explanation
This requires no special conditions beyond creating (or already having created) a `spender_attested` asset and subsequently posting a second `asset_attestors` message — both are ordinary, always-available operations for the asset definer, and the validation code imposes no cooldown, no grandfathering of previously attested addresses, and no requirement that the new list be a superset of the old one.

### Recommendation
When updating the attestor list, either (a) preserve authorization for addresses that were validly attested under the previous list until they explicitly opt into re-attestation, or (b) require that address-level attestations be checked against the attestor list that was current *at the time the attestation was issued* rather than only the single latest list, so that a definer cannot retroactively strip spending rights from already-attested holders.

### Proof of Concept
1. Definer issues asset `A` with `spender_attested: true` and initial `attestors: [X]`.
2. Attestor `X` posts an `attestation` message for holder `H`, who then receives/holds outputs of asset `A`.
3. `H` can spend those outputs today (validated via `validatePaymentInputsAndOutputs` → `filterAttestedAddresses` matching `X`).
4. Definer posts `asset_attestors` with `attestors: [Y]` (`Y != X`) — accepted by `validateAttestorListUpdate` because it only checks sender == definer and list well-formedness (`validation.js:2829-2848`).
5. `storage.readAsset` now returns `arrAttestorAddresses = [Y]`; `H`'s attestation from `X` no longer matches (`storage.js:1960-1974`).
6. Any subsequent payment spending `H`'s existing output of asset `A` fails validation with `"owner address is not attested"` (`validation.js:2506-2507`), permanently freezing `H`'s funds unless `Y` chooses to re-attest `H`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
