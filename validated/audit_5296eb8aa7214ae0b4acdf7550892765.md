### Title
Cross-repository Status webhook enables CI and mutates unrelated stacks via unscoped sha lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by `sha` alone, with no repository/stack scoping, then calls `commit.create_status_from_github!(params)` for every match. Because `Shipit::Status#enable_ci_on_stack` unconditionally calls `commit.stack.enable_ci!`, a signed `status` webhook for one repository can create a `Status` row on, and enable CI for, an entirely unrelated stack whose `Commit` table happens to contain a row with the same `sha` (e.g. a fork or mirrored history sharing commit hashes with the victim repo).

### Finding Description
The broken binding is: the handler assumes `commit.sha == params.sha` implies `commit.stack == webhook.repository`, i.e. `Commit.where(sha: params.sha).stack.github_repo_name == params.dig('repository','full_name')`. This equality is never checked.

Code path:
- `app/controllers/shipit/webhooks_controller.rb` `verify_signature` (lines 24-49) validates the HMAC signature using `Shipit.github(organization: repository_owner)`, which only proves the payload came from GitHub for a *trusted organization* already configured in Shipit — it says nothing about which specific repository within that trust boundary the event names, since `repository_owner`/`repository.full_name` in the JSON body are simply GitHub-supplied fields the org can freely populate for any repo it controls (including a fork the attacker owns inside that org).
- `app/models/shipit/webhooks/handlers/status_handler.rb` lines 20-24: [1](#0-0) 
does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with **no filter on repository/stack**, unlike other handlers (e.g. the `pull_request` handlers) which resolve the target repository/stack from `repository.full_name` before acting.
- `commit.create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` (app/models/shipit/commit.rb) creates the `Status` scoped to `commit`'s own `stack_id`, and `Status#enable_ci_on_stack` (app/models/shipit/status.rb lines 18, 38-40) then calls `commit.stack.enable_ci!` unconditionally, regardless of which repository actually sent the webhook.

Exploit flow: attacker controls or forks a repository inside a GitHub organization that already has Shipit's app/webhook installed (satisfying `verify_signature`), and can produce a genuine, GitHub-signed `status` event (e.g. by pushing a commit and letting any CI integration post a status, or via any repo they administer in that org). If that commit's `sha` collides with a `sha` already present in a victim stack's `Commit` table — which is common for forks/mirrors sharing git history with an upstream tracked repo — the resulting `Commit.where(sha: ...)` query returns the victim's `Commit` row too, and `enable_ci!` fires on the victim stack even though the victim stack's own CI has never reported anything, bypassing the intended "commits pending deploy gated by CI" protection.

Existing guards fail because: `verify_signature` authenticates the org, not the repository named inside the payload; and `StatusHandler` performs no additional repository/stack scoping before mutating state, unlike sibling handlers that do resolve `repository.full_name` to a specific stack first.

### Impact Explanation
An attacker-controlled webhook for repository A causes state (`Status` row creation and `stack.ci_enabled!` flip) to be written on a completely different repository/stack B that never sent or verified that event. This directly matches the Critical category "a payload for one repository mutating another's stack, commit, task or team": it flips victim stack B's CI gating flag and can create arbitrary-looking CI statuses for its commits, potentially unblocking deploys that were intentionally held back pending real CI results. It is repeatable against any stack whose commit history intersects (via shared/forked git history) with a repo inside the same GitHub org boundary Shipit trusts.

### Likelihood Explanation
Requires (1) attacker to belong to/administer a repository inside a GitHub org already configured with a valid Shipit webhook secret (so `verify_signature` passes) — this is within the stated threat model of "any GitHub user who can push to a fork ... and emit webhooks from a repository they own"; (2) a victim stack with `ci_enabled? == false` and a `Commit` row sharing a `sha` with the attacker's repo, which is a realistic condition for forked/mirrored repositories that share commit history. No Shipit secrets are needed beyond what the attacker's own repo naturally has access to for emitting a legitimately-signed webhook.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the stack(s) matching `params.dig('repository', 'full_name')` (or an equivalent verified repository identifier) before calling `create_status_from_github!`, mirroring the repository-scoping already used by other webhook handlers. Additionally, consider tightening `enable_ci_on_stack` to validate that the status originates from the stack's own configured repository rather than trusting the calling commit's association blindly.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two stacks, `victim_stack` (repo `victim/repo`, `ci_enabled: false`) and `attacker_stack` (repo `attacker/repo`), each with their own `GithubHook`/org config so `verify_signature` passes for the attacker's org only.
2. Create `Commit` rows for both stacks using the **same** `sha` value (simulating shared fork history): `victim_commit = Commit.create!(sha: 'deadbeef', stack: victim_stack, ...)` and `attacker_commit = Commit.create!(sha: 'deadbeef', stack: attacker_stack, ...)`.
3. Build a `status` webhook payload naming `attacker/repo` as the repository, signed with the attacker org's secret.
4. Assert equality claim before: `victim_stack.reload.ci_enabled?` is `false`.
5. POST the webhook to `/webhooks` (or invoke `StatusHandler.new.call(params)` directly) with `sha: 'deadbeef'`.
6. Assert `victim_stack.reload.ci_enabled?` is now `true` and `victim_commit.statuses.count == 1`, even though the webhook only named `attacker/repo` — demonstrating the cross-repository mutation.
