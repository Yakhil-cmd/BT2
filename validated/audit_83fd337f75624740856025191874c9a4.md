### Title
Arbiter-contract shared address has no timeout fallback — dispute funds can be permanently frozen if arbiter never resolves - ([File: arbiter_contract.js])

### Summary
The wallet's arbiter-contract feature locks contract funds into a shared multi-sig address whose spending conditions are entirely defined in `deriveSharedAddress()`. The only ways to move funds out of that address are (1) mutual cooperation of both counterparties, or (2) unilateral action gated by an `in data feed` clause that can only be satisfied by a data feed posted from the `arbiter_address`. There is no time-bound clause that lets either counterparty reclaim/withdraw funds if the arbiter never posts a resolution, mirroring the reported `QuailFinance.rotateLiquidity()` pattern where a single privileged party's inaction permanently freezes funds.

### Finding Description
`deriveSharedAddress()` builds the AND/OR spending definition for the shared address used by an arbiter contract: [1](#0-0) 

For a genuine dispute (neither side voluntarily concedes), the only path back to either party is the arbiter's decision, expressed as `["in data feed", [[contract.arbiter_address], "CONTRACT_" + contract.hash, "=", <party>]]`: [2](#0-1) 

For public assets, the "unilateral" paths (`arrDefinition[1][1]` / `arrDefinition[1][2]`) only let a party move funds by paying the *other* party the disputed amount — i.e. they only work if a party voluntarily concedes the dispute, not if they want to recover funds they believe are rightfully theirs: [3](#0-2) 

For private assets, the unilateral paths similarly require the *counterparty* to post a `CONTRACT_DONE_` data feed vouching that they were paid — again requiring cooperation of the other party, not a way to recover funds unilaterally: [4](#0-3) 

`openDispute()` transitions the contract to `in_dispute` and forwards the dispute to the arbstore/arbiter, but nothing in the protocol enforces that the arbiter must ever respond, and no timeout branch exists in the shared-address definition to allow either party to reclaim funds unilaterally after some elapsed time: [5](#0-4) 

This is structurally identical to the reported bug class: a privileged third party (`potCreator` / here, the `arbiter_address`) must take an action (`rotateLiquidity()` / here, post a `CONTRACT_<hash>` data feed) to release escrowed funds, and the funds' definitions cannot omit this requirement (arbiter decision is the whole point of dispute resolution), yet no fallback timeout exists to let depositors withdraw if that party is unavailable, malicious, or has lost their key.

### Impact Explanation
If an arbiter (chosen by both contract parties, but a single point of failure) loses their signing key, goes offline, is deregistered, or simply refuses/forgets to post a `CONTRACT_<hash>` data feed after a dispute is opened, the disputed funds in the shared address are permanently frozen — neither party can ever spend them, since the only unilateral spending paths require conceding the full amount to the other side, and the cooperative path requires an agreement that, by definition, does not exist once a dispute has arisen. This is a genuine, permanent fund-freezing condition for AA/wallet users engaging in arbiter contracts, reachable purely through normal use of the private-payment/arbiter-contract feature (posting a payment to a shared address and opening a dispute) — no malicious peer or node behavior is required beyond arbiter unavailability.

### Likelihood Explanation
Likelihood is realistic in the ordinary lifecycle of an arbiter contract: a dispute is opened whenever counterparties disagree, at which point resolution depends entirely on a single external actor (the arbiter) with no protocol-enforced SLA, key-recovery guarantee, or liveness requirement. Arbiter key loss, arbiter going out of business, or a non-responsive arbstore are all plausible real-world events, and once they occur, the freeze is irreversible because the definition contains no expiry/timeout branch.

### Recommendation
Add a time-bound fallback clause to the shared-address definition generated in `deriveSharedAddress()` — e.g. an `["and", [["address", offeror_address], ["address", acceptor_address]]]`-style clause guarded by elapsed time (using a data-feed-independent timestamp check or MCI-based condition) that becomes valid only after the dispute has been open for a defined duration, allowing the funds to be split according to a pre-agreed default (e.g., refunded 50/50, or returned to whoever paid in) if the arbiter fails to resolve the dispute within that window. This mirrors the report's recommendation of adding a time duration after which the privileged action is no longer required for participants to recover funds.

### Proof of Concept
1. Two parties, A (payer) and B (payee), create an arbiter contract with arbiter `X`, and A pays the contract amount into the derived shared address (`pay()`), per `arbiter_contract.js` lines 692-717.
2. B disputes the contract via `openDispute()` (arbiter_contract.js lines 262-319), moving status to `in_dispute`.
3. Arbiter `X` never posts a `data_feed` message with key `CONTRACT_<hash>` (key loss, going offline, or malice) — nothing in the protocol forces this.
4. Neither A nor B can construct a unit satisfying the shared-address definition: the cooperative "or" branch requires both signatures (unavailable in a real dispute), the unilateral branches require paying the *other* party the full amount (defeats the purpose of disputing), and the arbiter data-feed branches never become satisfiable.
5. The funds in the shared address, `contract.amount`, remain permanently unspendable with no protocol-level recovery path, confirmed by the absence of any timeout/expiry clause in `deriveSharedAddress()` (arbiter_contract.js lines 465-481, 494-512).

function openDispute(hash, cb) {
	getByHash(hash, function(objContract){
		if (!["paid", "in_dispute"].includes(objContract.status))
			return cb("contract can't be disputed");
		device.requestFromHub("hub/get_arbstore_url", objContract.arbiter_address, function(err, url){
			if (err)
				return cb(err);
			arbiters.getInfo(objContract.arbiter_address, async function(err, objArbiter) {
				if (err)
					return cb(err);
				err = await fillArbstoreAddresses(objContract);
				if (err)
					return cb(err);
				device.getOrGeneratePermanentPairingInfo(function(pairingInfo){
					var my_pairing_code = pairingInfo.device_pubkey + "@" + pairingInfo.hub + "#" + pairingInfo.pairing_secret;
					var data = {
						contract_hash: hash,
						unit: objContract.unit,
						my_address: objContract.my_address,
						peer_address: objContract.peer_address,
						me_is_payer: objContract.me_is_payer,
						my_pairing_code: objContract.my_pairing_code,
						peer_pairing_code: objContract.peer_pairing_code,
						encrypted_contract: device.createEncryptedPackage({
							title: objContract.title,
							text: objContract.text,
							creation_date: objContract.creation_date,
							plaintiff_party_name: objContract.my_party_name,
							respondent_party_name: objContract.peer_party_name,
							my_contact_info: objContract.my_contact_info,
							peer_contact_info: objContract.peer_contact_info,
						}, objArbiter.device_pub_key),
						my_contact_info: objContract.my_contact_info,
						peer_contact_info: objContract.peer_contact_info
					};
					db.query("SELECT 1 FROM assets WHERE unit IN(?) AND is_private=1 LIMIT 1", [objContract.asset], function(rows){
						if (rows.length > 0) {
							data.asset = objContract.asset;
							data.amount = objContract.amount;
						}
						var dataJSON = JSON.stringify(data);
						httpRequest(url, "/api/dispute/new", dataJSON, function(err, resp) {
							if (err)
								return cb(err);

							setField(hash, "status", "in_dispute", function(objContract) {
								shareUpdateToPeer(hash, "status");
								// listen for arbiter response
								db.query("INSERT "+db.getIgnore()+" INTO my_watched_addresses (address) VALUES (?)", [objContract.arbiter_address]);
								cb(null, resp, objContract);
							});
						});
					});
				});
			});
		});
	});
