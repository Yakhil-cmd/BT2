### Title
Duplicate-address double counting in `r of set` / `weighted and` signature threshold evaluation - (File: definition.js)

### Summary
`Definition.validateAuthentifiers()` (used by `validateDefinition()` at address-authorization time and later at signature-verification time) evaluates `r of set` and `weighted and` operators by iterating the `set` array and incrementing a plain counter/weight for every member whose signature check succeeds, without ever checking that the members of the set are distinct (different keys/paths/authors). This mirrors the reported `TreasuryVesting::approveOperation()` flaw, where a single actor's approval was counted against two independent counters instead of being restricted to one, because the code used two independent, non-exclusive `if` checks instead of mutually exclusive logic.

### Finding Description
`validateDefinition()`'s `r of set` handler counts `count_options_with_sig` over every element of `args.set` with no uniqueness constraint on the underlying `pubkey`/`hash`/`address` sub-definitions: [1](#0-0) 

The same absence of uniqueness checking exists for `weighted and`, which sums `weight` values contributed by each set member: [2](#0-1) 

At signature-verification time, `validateAuthentifiers()` repeats the identical unprotected counting pattern for `r of set` (counting members whose authentifier passes) and `weighted and` (summing weights of members whose authentifier passes): [3](#0-2) 

The actual per-slot signature check (`case 'sig'`) verifies the signature against `objValidationState.unit_hash_to_sign` and the `pubkey` argument only — it does not bind the signature to the specific set-member/path in any way that prevents the *same* signature value from being valid at multiple positions in the set when the same `pubkey` is listed more than once in the definition: [4](#0-3) 

Because a single ECDSA signature over `unit_hash_to_sign` verifies successfully regardless of which authentifier "path" it is attached to, if a shared/multisig address definition contains the same `pubkey` (i.e., the same private-key holder) at two or more positions of an `r of set`/`weighted and` set, that single key holder can supply the *same* signature value copied to each of those paths and have it counted once per occurrence — satisfying `required` (or `required` weight) alone, even though the address was nominally set up to require independent approval from multiple distinct co-signers. This is structurally identical to the reported bug: two logically-independent counters/slots are incremented by a single actor because the code does not enforce mutual exclusivity/uniqueness among the counted items.

### Impact Explanation
For any Obyte shared/multisig address whose definition uses `r of set` or `weighted and` with a repeated pubkey among the set members (whether created by a mistake in a wallet-composition tool, a malicious co-signer manipulating the shared-address template before all parties commit to it, or a poorly-audited definition template), one key holder can unilaterally satisfy the multisig authorization threshold and spend funds or trigger AA logic that was intended to require independent approval from multiple distinct parties. This is a concrete unauthorized-spending / access-control bypass of a multisig scheme, matching the "concrete unauthorized spending" acceptance criterion. The severity depends on the definition actually containing a duplicate key, so it is not a universal break of every multisig address, but any address built this way (including ones assembled programmatically, e.g. via `wallet_defined_by_addresses.js` shared-address templates or `createMultisigWallet()` style helpers) is silently vulnerable, and `ocore` performs no validation to reject or warn about such definitions.

### Likelihood Explanation
Exploitation requires a specific address definition shape (duplicate pubkey/hash/address entries inside `r of set`/`weighted and`), which is not the default for `createMultisigWallet()` (each device gets a distinct `pubkey@device_address`), so ordinary wallet-generated multisig addresses are not affected in the common case. However, `ocore` neither rejects nor warns about duplicated set members during `validateDefinition()`, so any custom/templated shared address (including those exchanged and approved via `wallet_defined_by_addresses.js`, or contract templates) that ends up with a duplicate signer is silently accepted as a valid definition, and the flaw is reachable purely by an unprivileged unit author posting authentifiers for such an address — no privileged network/hub access is required.

### Recommendation
In `Definition.validateDefinition()`'s `r of set` and `weighted and` cases (definition.js lines 147-233), and correspondingly in `Definition.validateAuthentifiers()` (lines 692-732), enforce that all leaf signing keys/addresses referenced within a single set are distinct (e.g., recursively collect the set of `pubkey`/`hash`/`address` values under each set member and reject the definition if any two members resolve to the same underlying authenticator). Alternatively/additionally, bind each authentifier’s validity to its specific path (e.g., include the path in the signed hash, or require a per-path nonce) so that a signature valid at one path cannot be copied and re-used at another path within the same unit.

### Proof of Concept
1. Construct an address definition:
```
["r of set", {
  required: 2,
  set: [
    ["sig", {pubkey: "A_base64_pubkey"}],
    ["sig", {pubkey: "A_base64_pubkey"}],   // duplicate of first entry
    ["sig", {pubkey: "B_base64_pubkey"}]
  ]
}]
```
   This passes `validateDefinition()` unmodified since there is no duplicate check in the `r of set` case (definition.js:147-185).
2. Compute the address as `objectHash.getChash160(arrDefinition)`, and have the holder of key `A` alone author a unit spending from this address.
3. In `objAuthor.authentifiers`, set the same signature string (signed once over `unit_hash_to_sign` with key `A`) at authentifier paths `r.0` and `r.1` (the two positions of the duplicated `A` entry in the set).
4. `validateAuthentifiers()`'s `r of set` handler (definition.js:692-711) evaluates both `r.0` and `r.1` via the `sig` case (definition.js:734-754); `ecdsaSig.verify(unit_hash_to_sign, signature, pubkey_A)` succeeds identically for both paths since the check does not depend on the path, giving `count = 2 >= required (2)`.
5. The unit is accepted as validly authorizing the spend, even though only the holder of key `A` ever produced a signature — key `B`'s cooperation was never obtained, defeating the intended 2-of-{A,B,A} (effectively meant to be 2-of-2 independent) authorization policy.
