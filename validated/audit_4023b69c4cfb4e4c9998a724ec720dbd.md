### Title
Node crash on attacker-crafted spending input referencing a stable output stuck in "temp-bad" sequence - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` contains a hard `throw Error(...)` (not a graceful `callback(err)`) when a transfer input spends a stable output whose `sequence` is `'temp-bad'`. Because this code runs inside a DB-query callback that is invoked while processing an attacker-supplied unit, the thrown exception is not caught by any `try/catch` in the call chain and bubbles up to Node's `process.on('uncaughtException')` handler in `network.js`, which explicitly re-throws to crash the process. This mirrors the ATS prefetch-plugin bug class: attacker-influenced input reaching a code path that crashes the service instead of being rejected as invalid.

### Finding Description
Inside `validatePaymentInputsAndOutputs`, when validating a `"transfer"` input, the code queries the source output and checks its stability/sequence: [1](#0-0) 

If `bStableInParents` is true (the source output's unit is before `last_ball_mci`, i.e., stable) and its `sequence` is `'temp-bad'`, the code executes `throw Error("spending a stable temp-bad output " + input.unit)` instead of calling `cb(err)` like every other rejection path in this function. All neighboring invalid-input conditions (e.g. `'final-bad'`, `"asset mismatch"`, `"output owner is not among authors"`) are handled by returning a validation error through `cb`, which safely propagates to `callbacks.ifUnitError`/`ifJointError` in `validate()`. The `temp-bad` branch is the only one that intentionally crashes the process, based on the assumption that a stable unit can never remain `'temp-bad'` (it should resolve to `'good'` or `'final-bad'` once stability is determined by `main_chain.js`/`writer.js`).

This invariant assumption is exactly the kind of "shouldn't happen" input-handling gap that led to the ATS prefetch crash: if any sequence-resolution edge case (e.g., timing/ordering issues in nonserial/double-spend resolution across parallel branches, an AA-related unit, or a unit accepted via hash-tree/catch-up path with a different-than-expected resolution order) leaves a stable output with `sequence='temp-bad'` in the `units`/`outputs` table, any subsequent unit — including one an attacker crafts on purpose — that spends that specific output will hit this `throw` during `validate()`.

`handleJoint()` in `network.js` invokes `validation.validate()` for every unit received from any peer (or self-posted), and the whole flow runs synchronously up the stack from the DB callback with no `try/catch` around this branch: [2](#0-1) 

The resulting uncaught exception hits the global handler, which crashes the process by design ("crash the process to avoid ending up in an inconsistent state"): [3](#0-2) 

### Impact Explanation
If an attacker (any unprivileged unit poster) can construct or discover a stable output whose owning unit is left with `sequence='temp-bad'` (e.g., through crafted competing double-spend units designed to leave the resolution in that state, or through a currently-unknown edge case in main-chain stabilization/sequence assignment), they can then broadcast a single follow-up unit spending that output. Every full node that receives and validates this unit will hit the `throw` and crash. Since the crash happens deterministically for identical input, this is a network-wide denial of service: nodes across the network stop processing and confirming new units until manually restarted, satisfying the "network unable to confirm new units" impact bar. It is reachable purely by posting units (no privileged/node-operator access needed).

### Likelihood Explanation
Exploitability hinges on being able to produce (or find) a stable output with `sequence='temp-bad'` — an invariant the codebase assumes cannot occur after stabilization. I was not able to fully confirm, within the available context, whether the sequence-resolution logic in `main_chain.js`/`writer.js` guarantees this invariant under all double-spend/branch-resolution orderings (e.g., interactions with `handleJoint`'s "possible AA" deferrals, catch-up hash-tree acceptance, or asynchronous resolution across multiple double-spend groups). If such an edge case exists, the crash is trivially and repeatably triggerable by any user; if the invariant genuinely always holds, the `throw` is dead code. This uncertainty should be resolved by reviewing `main_chain.js`/`writer.js`'s temp-bad → good/final-bad resolution paths for gaps, particularly around partially-processed nonserial units, catch-up scenarios, and units validated via `external_conn` (e.g., AA/light paths) that might commit sequence values out of the normal order.

### Recommendation
- Replace the `throw Error("spending a stable temp-bad output " + input.unit)` with a graceful `return cb("spending a stable temp-bad output " + input.unit)`, consistent with the `'final-bad'` branch immediately below it, so that any occurrence of this condition is treated as a normal unit-validation failure rather than a process crash.
- Audit `main_chain.js` and `writer.js` for any code path that can leave a stable unit's `sequence` as `'temp-bad'` and fix the resolution logic if a gap is found, to make sure the assumed invariant actually holds.
- Add a regression test that forces (via test hooks/mocked storage) a stable output with `sequence='temp-bad'` and asserts that unit validation returns a controlled error instead of throwing/crashing the process.

Conceptual PoC (exact trigger for reaching `sequence='temp-bad'` on a stable output could not be fully constructed from the available index and would need to be validated in a live/test node):

2. Post a new unit whose payment input is a `"transfer"` referencing an output of that stable, `temp-bad`-sequenced unit (`input.unit`, `input.message_index`, `input.output_index`).
