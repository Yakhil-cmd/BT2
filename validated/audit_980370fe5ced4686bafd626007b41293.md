### Title
Webhook signature verification is keyed off an attacker-controlled payload field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to use for HMAC verification based on a field taken directly from the untrusted request body (`repository.owner.login` or `organization.login`), rather than from any pre-established, out-of-band binding between the secret and the repository it is allowed to represent. In a multi-organization Shipit deployment, this breaks the equality that should hold: `organization whose secret authenticated the request == organization owning the repository the payload claims to mutate`.

### Finding Description
`Shipit.github` supports configuring one `GitHub App` (and one `webhook_secret`) per organization: `lib/shipit.rb:170-200` (`github`, `github_app_config`, `github_organizations`). The webhook signature check picks the secret to verify against using a value read straight out of the incoming JSON body: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) only checks that the HMAC over the raw body matches, using whichever secret was selected above — it never checks that the secret's organization actually corresponds to the repository named elsewhere in the same payload (e.g. `repository.full_name`, which is what handlers such as the push/status/pull_request handlers actually use to resolve a `Stack`).

Because the organization used to pick the secret is attacker-supplied, an actor who legitimately administers *any* GitHub organization/App that is also configured in this same multi-tenant Shipit instance (and therefore knows that organization's own `webhook_secret`, which they can freely rotate/read as an App admin of their own org) can craft a payload where:
- `repository.owner.login` = their own organization (so `Shipit.github(organization:)` picks a secret they know, letting them compute a valid HMAC), while
- `repository.full_name` / commit / branch / PR fields inside the very same signed payload = an arbitrary victim repository already tracked as a `Stack` in the same Shipit instance.

`verify_signature` only checks the HMAC integrity of the bytes, not that the claimed owner and the acted-upon repository are the same tenant. The downstream handlers dispatched via `Shipit::Webhooks.for_event(event)` (`app/models/shipit/webhooks.rb:6-41`) then act on `repository.full_name` to locate and mutate the victim stack (e.g. `GithubSyncJob` enqueue on `push`, commit `Status` creation, `check_suite` refresh, `pull_request`/merge-queue state transitions), with no re-derivation of which organization actually owns that repository.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" trust boundary explicitly called out in scope: an attacker who only administers their own onboarded organization can forge signed webhook events that write into another tenant's stack — creating commits, closing/merging pull requests via `PullRequest::ClosedHandler`, posting fake CI statuses that unblock deploys, or triggering `GithubSyncJob`/`CacheDeploySpecJob` against a repository they do not own. That is a cross-repository write achieved purely from data inside an attacker-forged (but validly-HMACed-with-their-own-secret) payload, without ever needing the victim's `webhook_secret`, an `ApiClient` token, or write access to the victim repository itself.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured for multiple GitHub organizations (the `github_organizations`/`github_app_config` multi-tenant schema in `lib/shipit.rb`), which is a documented, supported configuration, not an edge case. Any org admin able to install their own GitHub App/webhook against the shared Shipit instance can mount the attack purely by crafting an HTTP POST to `/webhooks`; no additional privilege on the victim side is required.

### Recommendation
Do not let the payload dictate which secret is used to validate itself. Bind webhook secrets and repository identity out-of-band: either (a) key the endpoint/secret selection off the URL path or App installation ID delivered via `X-GitHub-Hook-Installation-Target-ID`, not payload-derived login fields, or (b) after successfully verifying the signature, additionally assert that `repository.full_name`'s registered `Stack`/`Repository` actually belongs to the same `repository_owner` that produced the verified secret, rejecting the webhook otherwise.

### Proof of Concept
1. Attacker is an admin of `attacker-org`, which has its own GitHub App installed and configured under `secrets.github.attacker-org.webhook_secret` in this shared Shipit instance (multi-org config), so they know that secret.
2. Attacker crafts a `push` event JSON body with `repository.owner.login = "attacker-org"` (so `repository_owner` resolves to a secret they know) but `repository.full_name = "victim-org/victim-repo"` (a repository already tracked as a `Stack`).
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, raw_post)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the HMAC using the secret the attacker legitimately knows.
5. `Shipit::Webhooks.for_event("push")` dispatches `Handlers::PushHandler`, which resolves the `Stack` from `repository.full_name` ("victim-org/victim-repo") and enqueues `GithubSyncJob`, mutating the victim's stack state — despite the attacker never having any credential or access tied to `victim-org`.
