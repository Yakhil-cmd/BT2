The 51% attack game / team-asset pattern is the concrete analog: any user can create a "team" and become the **definer** of a freshly-issued custom asset (`payload.issued_by_definer_only: true`), and that asset is later used as the vehicle by which the AA pays out winnings to *all* contributors of that team in individual `payment` messages whose validity is checked against the asset's `issue_condition`/`transfer_condition` [1](#0-0) [2](#0-1) . Since the asset definer sets `issue_condition`/`transfer_condition` at asset-creation time and this condition is evaluated fresh on every subsequent transfer via `Definition.evaluateAssetCondition`, a malicious definer can encode a condition that they alone control (e.g. `attested`/`in data feed` on their own oracle address) and later flip it to make every transfer of that asset fail. [3](#0-2)  shows that any payment of a conditioned asset is validated by re-evaluating `issue_condition`/`transfer_condition` at validation time — this applies uniformly to every future transfer of the asset, not just the original issuance. When an AA composes a response unit containing a payment message in this asset (e.g. the game's payout to a winning contributor), it goes through `validateAndSaveUnit`, which calls the normal `validation.validate()` pipeline; any failure there causes the entire AA response for that trigger to bounce: `validateAndSaveUnit(objUnit, function (err) { if (err) return bounce(err); ...})` [4](#0-3) .



### Title
Attacker-controlled `transfer_condition`/`issue_condition` on a self-issued team asset permanently blocks payout of shared AA balances to all legitimate contributors - (File: aa_composer.js, validation.js, definition.js)

### Summary
An unprivileged unit poster can define a custom asset through the standard `asset` message and attach an `issue_condition`/`transfer_condition` that references only entities the poster controls (their own address via `attested`, or their own oracle address via `in data feed`). Any AA that dynamically issues or forwards such an attacker-defined asset to third parties (a common pattern, exemplified by the shipped `51_attack_game.oscript` / `fundraising_proxy.oscript` samples where each "team" is the definer of its own payout asset) will have every future `payment` message in that asset re-validated against the condition. Because the condition is evaluated at validation time on the current state of the network (e.g., a data feed value), the attacker who created the asset can toggle it to `false` at will and keep it `false` forever, permanently causing `validateAndSaveUnit` to fail and the whole AA response — including payouts owed to unrelated, honest contributors sharing the same asset/payout pool — to bounce.

### Finding Description
Custom assets in ocore carry optional `issue_condition`/`transfer_condition` fields that are arbitrary spending-condition expressions, validated once at asset-definition time [5](#0-4)  but *re-evaluated on every subsequent transfer or issue* of that asset: [3](#0-2) 

The evaluation is delegated to `Definition.evaluateAssetCondition`, which runs the full definition-evaluation engine, including references that are entirely controlled by the definer, such as `attested` (self-attestation) or `in data feed` (an oracle address the definer controls) [6](#0-5) [7](#0-6) . Nothing in asset-definition validation prevents the condition from depending solely on the definer's own oracle feed, and nothing re-checks that the condition is "neutral" with respect to future recipients.

AAs frequently let ordinary users become the **definer** of a fresh asset by simply emitting an `asset` message from within a trigger-handling branch — this is the exact mechanism used in the bundled `51_attack_game.oscript` sample, where each team founder's trigger unit becomes the author (and thus, per `objAsset.definer_address = issuer_address`) the definer of the team's payout-share asset [1](#0-0) . Later, the AA pays out to *every* contributor holding that asset in a single recurring code path: [2](#0-1) 

When the AA composes its response for any contributor's payout trigger, the resulting unit is validated via the normal validation pipeline inside `validateAndSaveUnit`, and any validation failure (including "transfer or issue condition not satisfied") causes the AA to `bounce()` the entire response for that trigger: [8](#0-7) 

Because the malicious founder set the condition to reference only their own oracle/attestation state, they can freely toggle it after other, unrelated users have already contributed bytes and are relying on the shared pool being redeemable. Once toggled to fail, every future trigger that would produce a payment message in that tainted asset is bounced — this affects **every legitimate contributor of that team**, not just the attacker, mirroring the `claimBounty()` DoS in the original report where a single malicious token funding call blocks all future claims for the whole bounty.

### Impact Explanation
Any AA (or oscript template) that lets end users define/issue their own custom payout asset and later relies on that asset to distribute funds to a pool of participants can be permanently DoS'd by one malicious participant. All the other contributors' funds and their `AND` payout branch tied to `var['winner']`/`var['finished']` become permanently unreachable once the attacker sets their asset's condition to always fail, because every response unit paying out in that asset will fail validation and bounce, and the AA state that gates payout (e.g., `var['finished']`) will typically already have advanced irrevocably, leaving no path for honest contributors to redeem their share. This is a persistent, deterministic denial of service on AA fund distribution, i.e., permanent freezing of funds for a whole class of legitimate users.

### Likelihood Explanation
Likelihood is high: creating an asset with `issue_condition`/`transfer_condition` referencing `attested`/`in data feed` on the creator's own address is fully permitted by asset-definition validation [5](#0-4) ; nothing restricts these conditions from depending exclusively on data the attacker controls. Any AA template that follows the common "let anyone create a pool/team and issue their own token to represent shares" pattern (as demonstrated by the bundled sample scripts) is exposed. No special privileges, timing races, or unusual network conditions are required — only a single malicious `asset`-definition message followed by later withholding an oracle/attestation value.

### Recommendation
- When an AA design allows a user to become the definer of an asset used for a shared payout pool, disallow (or explicitly warn against) `issue_condition`/`transfer_condition` fields referencing conditions solely controlled by the definer relative to the AA's own future payments, e.g., forbid `transfer_condition` from depending on data feeds/attestations from the definer address itself when the asset is later redeemed to third parties by the AA.
- Alternatively, AA authors should avoid trusting arbitrary user-issued assets with attacker-settable transfer conditions as the vehicle for shared payouts to multiple independent parties; use AA-internal state (`var[]`) accounting and native `base` asset payouts instead of forwarding a conditioned custom asset.
- At the protocol level, consider flagging (during `validateAssetDefinition`/AA `asset` message validation) `issue_condition`/`transfer_condition` expressions whose determining branches reference only the asset definer's own address/oracle, so that AA developers building generic pools are alerted at definition time that such an asset is not "unconditionally transferrable" and should not be used as a trustless payout medium.

### Proof of Concept
1. Attacker triggers a "create team" branch of an AA such as `51_attack_game.oscript`, causing the AA to emit an `asset` message whose `issue_condition`/`transfer_condition` is set (by controlling the messages template or via a variant AA that accepts attacker-supplied condition data) to `["in data feed", [[attacker_oracle_address], "flag", "=", 1]]`.
2. Attacker posts a data feed unit from `attacker_oracle_address` setting `flag=1`, satisfying the condition, and contributes funds to their own team, becoming its founder/definer.
3. Other honest users contribute to the same team, receiving proportional shares of the team's payout asset per the sample's contribution logic [9](#0-8) .
4. The team wins (51%) and the game finishes, advancing `var['finished']`/`var['winner']` state irrevocably.
5. Attacker stops posting `flag=1` (or posts `flag=0`), causing `evaluateAssetCondition` to return `false` for any future transfer/payment involving this asset.
6. Every subsequent "pay out the winnings" trigger from any contributor (honest or not) produces a response unit containing a `payment` message in the tainted asset; `validateAndSaveUnit` fails with "transfer or issue condition not satisfied," and `bounce()` is invoked [8](#0-7) , permanently preventing all contributors from claiming their share of the winnings.
