### Title
`ERC20Transactor` credits/debits a fixed XCM amount without verifying actual ERC20 balance delta, breaking holding-register/contract-balance parity for non-standard (fee-on-transfer/rebasing) ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` implement `xcm_executor::traits::TransactAsset` for arbitrary `pallet-revive` smart-contract tokens matched by `ERC20Matcher` (any local `AccountKey20` location, i.e. any deployed contract that speaks the `IERC20` ABI — not a curated/trusted asset list). Both functions call the contract's `transfer(to, value)` via `pallet_revive::Pallet::<T>::bare_call` and, on a `true` boolean return, unconditionally assume that exactly `amount` was moved, minting an `Erc20Credit(amount)` into the XCM holding register (`withdraw`) or reporting success for exactly `amount` (`deposit`). This is the same bug class as Allo's `_fundPool()`: trusting a token's declared transfer amount instead of measuring the actual balance delta.

### Finding Description
`withdraw_asset_with_surplus` at [1](#0-0)  resolves `(asset_id, amount)` via `Matcher::matches_fungibles(what)`, then encodes an `IERC20::transferCall { to: checking_address, value: amount }` and executes it with `bare_call`. On success (`is_success == true`) it constructs the XCM holding credit directly from the requested `amount`, not from any observed balance change: [2](#0-1) .

Symmetrically, `deposit_asset_with_surplus` transfers `amount` from the checking account to the beneficiary and, on `Ok(true)`, simply returns success without re-checking the beneficiary's or checking-account's actual balance change: [3](#0-2) .

The asset matcher that decides which contracts this transactor handles is `ERC20Matcher`, defined as any location that is a bare local `AccountKey20` junction — i.e. **any** deployed `pallet-revive` contract implementing `transfer(address,uint256) returns (bool)`, without any allow-list or trust requirement: [4](#0-3) . This mirrors the Allo report's premise that "the protocol allows ALL ERC20's" — here, XCM will attempt to transact any ERC20-shaped contract deployed on the chain, including one with fee-on-transfer or rebasing semantics that returns `true` for a `transfer` call while moving less (or more) than `value` in actual token balance.

Root cause parity with the report:
- Violated invariant: "amount requested to move == amount actually moved" is assumed rather than verified.
- Attacker-controlled input: an attacker can deploy (or already control) an ERC20 contract with `IERC20`-compatible `transfer` returning `true` but internally deducting a fee or rebasing balances, then use it in an XCM program (e.g. `WithdrawAsset`/`DepositAsset`) targeting `ERC20Transactor`.
- Missing check: no `balance_before`/`balance_after` comparison around the `bare_call`, unlike other in-repo tests for `pallet-assets`/`asset-conversion` that explicitly assert exact balances (e.g. [5](#0-4) ), those pallets don't have this issue because they are internal ledgers, not external contract calls.

### Impact Explanation
If an XCM program routes a fee-on-transfer or rebasing ERC20 through `ERC20Transactor`:
- On `withdraw_asset_with_surplus`: the checking account receives less than `amount` tokens, but the XCM executor's in-memory holding register is credited with the full `amount`. This lets the XCM program (e.g. via `DepositAsset` to a different beneficiary/chain, or further XCM hops) create and move more value in the holding register than was ever actually deposited into the checking account — an accounting desync that, depending on downstream XCM steps (e.g. `TransferReserveAsset` semantics or further `deposit_asset` calls back through the same transactor), risks the checking account's real ERC20 balance running low or negative relative to the assumed backing of holding-register credits repeatedly issued this way.
- On `deposit_asset_with_surplus`: if the beneficiary contract also implements a fee/hook (or the same fee-on-transfer contract is looped through it), the beneficiary receives less than `amount`, yet the executor and any XCM `event`/further steps treat the deposit as fully successful for `amount`.

This is an internal-accounting desynchronization between the XCM holding register and actual on-chain ERC20 balances, matching the reported Medium-severity impact class (accounting/actual-balance divergence, not necessarily a direct fund-drain in a single call, but compounding across repeated withdraw/deposit cycles through non-standard tokens).

### Likelihood Explanation
Reaching this code path requires only: (1) deploying an ERC20-ABI-compatible contract via `pallet-revive` (a normal, permissionless, non-privileged user action reachable through the standard `pallet-revive` `instantiate`/`upload_code` extrinsics), and (2) submitting an XCM program (e.g. via `pallet-xcm::execute` or a cross-chain message) that references this contract's `AccountKey20` location as the asset to withdraw/deposit. No governance, sudo, validator/collator privilege, or forged proof is needed — `ERC20Matcher` accepts any local `AccountKey20`-keyed asset by construction. This makes the precondition realistic and directly analogous to the original report's premise that "the protocol allows ALL ERC20's."

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the ERC20 `balanceOf` of the relevant account (checking account / beneficiary, and the source account) immediately before and after the `bare_call` to `transfer`, and use `balance_after - balance_before` (or `balance_before - balance_after` for the sender) as the amount credited/reported to the XCM holding register, instead of trusting the caller-declared `amount` and the boolean return value alone. Reject (return `XcmError::FailedToTransactAsset`) if the observed delta does not equal the requested `amount`, or explicitly support partial-amount accounting if fee-on-transfer tokens are meant to be supported at all.

### Proof of Concept
No executable Rust/FRAME integration test was run against a real deployed fee-on-transfer/rebasing ERC20 contract through `pallet-revive` + XCM in this session; this analysis is based on static code review of `ERC20Transactor` and `ERC20Matcher` only. To fully confirm exploitability, a Devin session should: (1) deploy a minimal Solidity ERC20 contract via `pallet-revive` whose `transfer()` deducts an internal fee but still returns `true`; (2) construct a local `AccountKey20` location for it; (3) drive it through `ERC20Transactor::withdraw_asset_with_surplus`/`deposit_asset_with_surplus` (directly or via a `pallet-xcm::execute` program); (4) assert that the XCM holding register / reported success amount diverges from the actual contract-measured `balanceOf` delta on the checking account and beneficiary. This reproduction was not executed here — the finding is presented based on code-path analysis of the missing balance-delta check, not a confirmed passing/failing test run.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
