## Analysis

The FreeRDP CVE (`smartcard_unpack_read_size_align()`) is a case where a missing count/bounds check lets attacker-influenced data reach a `WINPR_ASSERT`, which in verbose builds calls `abort()` and crashes the client. The equivalent bug class in `ocore` is a reachable, unguarded `throw Error(...)` inside a database-callback that is not caught anywhere in the call stack, which propagates as a Node.js `uncaughtException`. In this codebase that handler explicitly re-throws to kill the process: [1](#0-0) 

I found a concrete, reachable instance of this pattern in the **private payment chain** duplicate-check logic.

### Root cause

`validateAndSavePrivatePaymentChain()` in `private_payment.js` runs a "already have this output?" duplicate check before delegating to the asset-specific saver: [2](#0-1) 

For **divisible** (non-fixed-denomination) private assets, the query intentionally omits the `output_index` filter (only added `if (objAsset.fixed_denominations)`), so it matches *every* output row belonging to that `(unit, asset, message_index)` — but the code only handles `rows.length <= 1`; `rows.length > 1` is treated as an invariant violation and unconditionally throws: [3](#0-2) 

The invariant is false in practice: `validateAndSaveDivisiblePrivatePayment()` in `divisible_asset.js` inserts **one row per output** of the payment message (a normal divisible payment has ≥2 outputs — recipient + change): [4](#0-3) 

So once a normal divisible private-payment chain with multiple outputs has been saved once, the `outputs` table legitimately holds 2+ rows for that `(unit, asset, message_index)`. Any subsequent delivery of the *same* head private element (a resend/retry, or a payment counterparty/paired device deliberately replaying it) causes the duplicate-check query to return `rows.length > 1`, hitting the `throw Error("more than one output ...")` inside the `conn.query` callback — with no enclosing try/catch — crashing the process via the `uncaughtException` handler.

### Reachability

This path is reachable directly from an unprivileged private-payment counterparty / paired device sending a wallet chat message, without needing the unit to be unknown:
- `wallet.js` `handlePrivatePaymentChains()` accepts private payment chains from any paired device and calls `network.handleOnlinePrivatePayment()`: [5](#0-4) 
- `handleOnlinePrivatePayment()` in `network.js`, when the referenced unit is already known, calls `privatePayment.validateAndSavePrivatePaymentChain()` directly: [6](#0-5) 

### Title
Reachable Uncaught `throw Error` in Divisible Private-Payment Duplicate Check Crashes the Node — (File: `private_payment.js`)

### Summary
`validateAndSavePrivatePaymentChain()` in `private_payment.js` assumes at most one previously-saved output row can match `(unit, asset, message_index)` for divisible private assets, but the saving code (`divisible_asset.js`) legitimately inserts one row per output in the payment message. Any counterparty/paired device that resends (or a network retry that redelivers) an already-processed divisible private payment chain triggers `rows.length > 1`, hitting an unguarded `throw Error(...)` inside a DB callback that is never caught, producing a fatal `uncaughtException` that `network.js` intentionally re-throws to crash the process.

### Finding Description
The duplicate-detection SQL at `private_payment.js:62-69` filters only by `unit`, `asset`, `message_index` for divisible (non-fixed-denomination) assets — it deliberately skips `output_index`, which is only added for fixed-denomination (indivisible) assets. This means the query matches all outputs belonging to a payment message, and since divisible payments commonly carry 2+ outputs (payment + change), a resend of a previously fully-saved chain returns more than one row. The code only anticipates `rows.length <= 1` and treats `rows.length > 1` as an internal-consistency failure, throwing unconditionally rather than treating it as a legitimate duplicate. This throw occurs inside a `db.query` callback with no surrounding `try/catch`, so it becomes an uncaught exception that reaches the global handler.

### Impact Explanation
The global `uncaughtException` handler in `network.js` explicitly re-throws the error "to avoid ending up in an inconsistent state," terminating the node/wallet process. Because private payment chains are exchanged directly between wallets/paired devices (hub-mediated or direct), any counterparty in a private-asset transaction — or simply a duplicate delivery/resend of a legitimate message — can crash the recipient's process. This is a concrete denial-of-service against a wallet or full node processing private-asset payments, matching the severity class of the referenced FreeRDP client crash.

### Likelihood Explanation
High likelihood: divisible private payments with multiple outputs are the normal case (not an edge case), and simply causing/allowing a duplicate delivery of an already-accepted chain — trivially reproducible by any private-payment counterparty by re-sending the same `private_payment` message, or naturally by network retry/duplication — is sufficient to trigger the crash. No special privileges, node compromise, or protocol violation is required.

### Recommendation
In `private_payment.js`, make the divisible-asset duplicate check tolerant of multiple matching rows: iterate over all matched rows to determine whether the incoming chain is a full or partial duplicate of previously stored outputs, instead of asserting `rows.length <= 1`. Replace the `throw Error("more than one output ...")` with a graceful duplicate/mismatch resolution path (e.g., compare each incoming output against the corresponding stored row by `output_index`) so that legitimate resends can never crash the process, consistent with how the fixed-denomination branch already scopes by `output_index`.

### Proof of Concept
1. Attacker (a normal wallet counterparty) sends Victim a divisible private-asset payment with 2 outputs (recipient + change) via a `private_payment` wallet message; Victim validates and saves it, inserting 2 rows into `outputs` for that `(unit, asset, message_index)`.
2. Attacker resends the identical head private element (same `unit`/`message_index`/`asset`) to Victim again (e.g., replays the earlier device message).
3. `validateAndSavePrivatePaymentChain()` runs the duplicate-check query without an `output_index` filter, matching both previously-stored rows (`rows.length === 2`).
4. Code hits `throw Error("more than one output "+sql+' '+params.join(', '))` inside the `conn.query` callback, uncaught.
5. Node's `process.on('uncaughtException')` in `network.js` logs and re-throws, crashing the Victim's process.
