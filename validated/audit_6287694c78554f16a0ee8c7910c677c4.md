### Title
Hookify rule parser silently truncates regex patterns containing commas, causing configured `block` hooks to fail open - (File: `plugins/hookify/core/config_loader.py`)

### Summary
The Trail-of-Bits finding criticizes the Atlendis codebase for keeping validation logic outside of the constructor that actually consumes the data (`LoanState`), so a malformed/unvalidated value (`totalPaymentsCount == 0`) can silently propagate because the code assumes validation happened elsewhere. The `hookify` plugin has the same root-cause pattern: `config_loader.py`'s YAML-ish frontmatter parser builds `Condition`/`Rule` objects with **no validation** that the extracted `pattern`/`operator`/`field` values are complete or well-formed, and the downstream consumer (`RuleEngine`) never re-validates them either — it just trusts whatever `Rule.from_dict` produced. A specific parsing defect in the inline-dict path silently corrupts regex patterns that contain a comma (a very common regex construct, e.g. bounded quantifiers like `{1,5}`), turning an intended `action: block` PreToolUse rule into a no-op with no error or warning anywhere in the pipeline.

### Finding Description
`extract_frontmatter()` in [1](#0-0)  parses inline list items of the documented form `- field: command, operator: regex_match, pattern: ...` by naively splitting on every comma:

```python
if ':' in item_text and ',' in item_text:
    item_dict = {}
    for part in item_text.split(','):
        if ':' in part:
            k, v = part.split(':', 1)
            item_dict[k.strip()] = v.strip().strip('"').strip("'")
    current_list.append(item_dict)
```

If the `pattern` value itself contains a comma — which is extremely common in regex (e.g. `{1,5}`, `{2,}`), the split breaks the pattern into fragments: the part before the comma becomes a truncated `pattern`, and the part after the comma has no `:` so it is silently dropped entirely. No exception is raised (the truncated string like `rm\s{1` still compiles as a valid, but semantically different, regex), and `load_rule_file()` / `load_rules()` in [2](#0-1)  and [3](#0-2)  have no post-construction check that the parsed `Condition.pattern` is complete, that the field count matches the number of commas in the source, or that the regex still expresses the author's intent.

The consumer, `RuleEngine._check_condition` / `_regex_match` in [4](#0-3) , simply compiles and evaluates whatever pattern it receives; if it happens to be inert, the rule is treated as "not matched" — exactly like `blocking_rules` being empty — and the operation is allowed with no diagnostic in the `PreToolUse` output built in [5](#0-4) . This mirrors the report's core complaint: the object (`Rule`/`Condition`) is constructed without validating the very invariant its own comment claims to support (`# Inline comma-separated dict: "- field: command, operator: regex_match"`), and every downstream user of that object assumes it was validated upstream.

### Impact Explanation
A repo maintainer who configures `hookify` with an `action: block` `PreToolUse` rule to prevent Claude from running destructive Bash commands (as advertised throughout the hookify/hook-development documentation, e.g. `plugins/plugin-dev/skills/hook-development/references/migration.md`) can unknowingly ship a rule that never actually blocks anything, because their regex pattern used a bounded quantifier. This is a genuine hook/approval bypass: the developer believes a guard rail is active, but Claude (potentially acting under prompt injection from untrusted repository content, issues, or tool output) can execute the exact class of command the rule was meant to stop, with zero warning surfaced to the user (`userpromptsubmit.py`/PreToolUse hook exits 0 and prints nothing abnormal — see [6](#0-5) ).

### Likelihood Explanation
High for anyone following the documented inline-dict syntax with a realistic regex. Bounded quantifiers (`{1,3}`, `{2,}`) and comma-containing character alternations are idiomatic regex constructs that a maintainer writing a "block dangerous commands" rule would very plausibly use, and the failure is completely silent (no exception, no stderr, no lint warning from `validate-hook-schema.sh`, which only checks JSON hook schemas, not hookify's own markdown rule files).

### Recommendation
- Short term: After parsing an inline dict item, validate that the number of top-level `key: value` fragments produced equals the number of recognized keys expected (`field`, `operator`, `pattern`), and reject/`warn` on files whose parsed `Condition.pattern` fails to `re.compile` to something matching the raw substring after `pattern:`. Better: split only on the first two commas that immediately precede a recognized key (`, operator:`, `, pattern:`) rather than every comma, or require the multi-line dict form (which already avoids this bug) for any pattern containing a comma.
- Long term: Move all structural validation of `Rule`/`Condition` (non-empty `pattern`, valid `operator`, valid `action` value, and a round-trip check that reconstructing the source line from parsed fields matches) directly into `Rule.from_dict`/`Condition.from_dict`, and make `load_rule_file` refuse (not merely warn-and-skip) any rule whose `action == 'block'` fails this validation, so a broken safety rule cannot silently degrade to "no protection."

### Proof of Concept
1. Create `.claude/hookify.block-rm.local.md`:
```markdown
---
name: block-dangerous-rm
enabled: true
event: bash
tool_matcher: Bash
action: block
conditions:
  - field: command, operator: regex_match, pattern: rm\s{1,5}-rf
---
Blocked: dangerous rm -rf command detected.
```
2. Run the PreToolUse hook manually:
```bash
echo '{"hook_event_name":"PreToolUse","tool_name":"Bash","tool_input":{"command":"rm -rf /tmp/important"}}' \
  | python3 plugins/hookify/hooks/userpromptsubmit.py
```
3. Trace: `extract_frontmatter` splits `"field: command, operator: regex_match, pattern: rm\s{1,5}-rf"` on `,` into `["field: command", " operator: regex_match", " pattern: rm\s{1", "5}-rf"]`; the last fragment has no `:` and is dropped, so `Condition.pattern == "rm\s{1"` (truncated, no closing brace).
4. `RuleEngine._regex_match("rm\s{1", "rm -rf /tmp/important")` compiles the truncated pattern fine (Python treats the unterminated `{1` as literal text) but it does **not** match the actual command text, so `_rule_matches` returns `False`, `blocking_rules` stays empty, and `evaluate_rules` returns `{}` — i.e., the tool call is allowed with no `permissionDecision: deny` and no error printed anywhere, despite the maintainer's explicit intent to block it.

def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules
```

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule

    except (IOError, OSError, PermissionError) as e:
        print(f"Error: Cannot read {file_path}: {e}", file=sys.stderr)
        return None
    except (ValueError, KeyError, AttributeError, TypeError) as e:
        print(f"Error: Malformed rule file {file_path}: {e}", file=sys.stderr)
        return None
    except UnicodeDecodeError as e:
        print(f"Error: Invalid encoding in {file_path}: {e}", file=sys.stderr)
        return None
    except Exception as e:
        print(f"Error: Unexpected error parsing {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
        return None
```

def main():
    """Main entry point for UserPromptSubmit hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Load user prompt rules
        rules = load_rules(event='prompt')

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0
        sys.exit(0)
