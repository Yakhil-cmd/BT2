### Title
Cross-repository forged CI status injection via unscoped `StatusHandler` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController` verifies the GitHub webhook signature using an organization key derived from the payload's `repository.owner.login` (or `organization.login`) field, binding trust to *that* organization's `webhook_secret`. [1](#0-0)  However, `Shipit::Webhooks::Handlers::StatusHandler#process` never re-checks the repository the signed payload claims to originate from — it looks up commits globally by `sha` alone, across all stacks/repositories in the installation: [2](#0-1) . This breaks the binding "organization that authenticated == repository that is written": a `status` event that is validly signed for organization/repo A can be crafted to carry a `sha` belonging to a commit that lives in repo B's stack, and the handler will happily apply the forged status to B's commit.

### Finding Description
- The webhooks controller resolves which GitHub App/organization config (and therefore which `webhook_secret`) to use for HMAC verification purely from `params.dig('repository','owner','login')`: [3](#0-2) .
- All other handlers (`PushHandler`, `CheckSuiteHandler`, `PullRequest::OpenedHandler`, etc.) additionally scope their side effects through `Handler#stacks`, which resolves the target `Repository` via `payload.dig('repository', 'full_name')` — i.e., the same trusted field used for signature verification: [4](#0-3) .
- `StatusHandler`, by contrast, does not call `stacks` or filter by repository at all. It queries `Commit.where(sha: params.sha)` directly and invokes `commit.create_status_from_github!(params)` on every match, regardless of which repository/stack the `Commit` record actually belongs to: [2](#0-1) .
- `Commit#create_status_from_github!` writes a new `Status` record which feeds directly into `Commit#status`/`Commit#deployable?` and `Commit#schedule_continuous_delivery`, i.e., it directly participates in deploy-gating and, when `continuous_deployment?` is enabled, can trigger an automatic deploy: [5](#0-4) [6](#0-5) [7](#0-6) .

Concretely: if an attacker controls a GitHub organization/repository that is configured as a Shipit installation (this is the intended, legitimate way to send signed webhooks in a multi-org Shipit deployment via `Shipit.github_app_config`), they can compute or otherwise learn the SHA of a commit belonging to a *victim* stack/repository (commit SHAs of public commits, or ones the attacker can otherwise discover, are not secrets), then send a `status` webhook event whose top-level `repository.owner.login`/`full_name` is their own (so it passes signature verification against their own legitimately configured `webhook_secret`), but whose `sha` field matches the victim commit. `StatusHandler` will attach the forged status (e.g. `state: "success"`) to the victim's `Commit`, regardless of the fact the signed payload's `repository` field points to a different repo entirely.

### Impact Explanation
This crosses a genuine authentication/repository trust boundary: successful signature verification for organization A is treated as authorization to mutate CI status data for any repository B tracked by the same Shipit instance. Forged "success" statuses can make an otherwise blocked/untested commit `deployable?` (bypassing `blocking_statuses`/CI gating) and, on stacks with `continuous_deployment?` enabled, can trigger `ContinuousDeliveryJob`, resulting in an unauthorized/unreviewed deploy of a commit whose real CI never passed. This matches the "Critical - unauthorized deploy" category since it enables a cross-repository write of authoritative deploy-gating state and can lead to shipping code that never passed the victim repository's actual CI checks.

### Likelihood Explanation
Exploitation requires the attacker to be able to trigger a validly-signed webhook (i.e., control a repository/organization onboarded into the same Shipit instance, or be able to trigger a `status` event on any repo Shipit is configured for) and to know a target commit SHA in the victim stack. In multi-tenant Shipit deployments serving many independent organizations/repos with per-organization `github` config and `webhook_secret` (as documented in `secrets.development.example.yml`), this is a realistic scenario: any onboarded org can forge a `status` event carrying a foreign SHA. Commit SHAs for public repos are trivially discoverable; even for private repos, they routinely leak through CI logs, PR pages, or existing Shipit UI. No compromise of the victim's own credentials or webhook secret is required.

### Recommendation
`StatusHandler#process` (and any other handler that performs data mutation) must scope the affected `Commit` by the stack(s) belonging to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, mirroring what `Handler#stacks` already does for other handlers, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
This ensures a signed webhook for organization A can only ever mutate commits/statuses that belong to repositories owned by organization A, restoring the intended binding between the organization whose signature was verified and the repository whose data is written.

### Proof of Concept
1. Attacker's organization `evil-org/evil-repo` is a legitimately configured GitHub App installation on the target Shipit instance (own `webhook_secret`).
2. Attacker discovers a commit SHA `abc123...` belonging to `victim-org/victim-repo`, tracked by a Shipit stack with `continuous_deployment: true`.
3. Attacker sends `POST /webhooks` with header `X-Github-Event: status`, correctly HMAC-signed with `evil-org`'s webhook secret, and body:
```json
{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/forced",
  "repository": { "owner": { "login": "evil-org" }, "full_name": "evil-org/evil-repo" }
}
```
4. `verify_signature` succeeds (signature matches `evil-org`'s secret for `evil-org`'s payload) via [3](#0-2) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's `Commit` (belonging to `victim-org/victim-repo`), and calls `create_status_from_github!`, injecting a fabricated "success" status: [2](#0-1) .
6. If `victim-org`'s stack has `continuous_deployment?` enabled, `Commit#schedule_continuous_delivery` may enqueue `ContinuousDeliveryJob`, deploying the commit based on the forged status: [7](#0-6) .
