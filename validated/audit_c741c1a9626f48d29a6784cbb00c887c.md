### Title
Improper Authorization in `new_shared_address` device-message handler allows an unprivileged correspondent to silently register attacker-controlled shared-address definitions naming the victim as cosigner - ([File: wallet_defined_by_addresses.js])

### Summary
`handleNewSharedAddress()` in `wallet_defined_by_addresses.js` accepts and persists a fully attacker-supplied multisig ("shared address") definition without verifying that the sending device is actually one of the participants who negotiated it, and without requiring any explicit user confirmation, unlike the sibling `create_new_shared_address` / `approve_new_shared_address` flow which does prompt the user before accepting a definition.

### Finding Description
The `new_shared_address` device message is routed straight into `handleNewSharedAddress(body, callbacks)`: [1](#0-0) 

Note that `from_address` (the sender of the device message) is **not** passed into `handleNewSharedAddress` at all, so the function has no way to know or check who actually sent the message.

Inside `handleNewSharedAddress`, the only checks performed are structural/self-consistency checks: that `body.definition` hashes to `body.address`, that the `signers` map's addresses match the leaves of the definition, and that every leaf has a signer entry: [2](#0-1) 

It never checks that the message actually originated from one of the `device_address` values embedded in `body.signers`, nor that the sender is a party genuinely entitled to introduce a shared address including the local wallet's real address as a cosigner. The only "authorization" gate is `determineIfIncludesMeAndRewriteDeviceAddress`, which simply checks whether one of the addresses in the payload happens to be a `my_addresses`/`shared_addresses` entry already known locally - it does not verify sender identity or intent: [3](#0-2) 

Once these checks pass, `addNewSharedAddress` is called and the shared address + its `shared_address_signing_paths` rows are inserted **immediately and automatically**, with no user-facing confirmation dialog: [4](#0-3) 

This is in stark contrast to the legitimate address-creation path, `create_new_shared_address` → `validateAddressDefinitionTemplate` → `create_new_shared_address` event, which is explicitly designed to "trigger a confirmation dialog" so "user needs to approve creation of the shared address": [5](#0-4) 

Because `device.js` allows any already-paired correspondent (and, for a few whitelisted subjects, even unpaired devices) to deliver arbitrary `hub/message` payloads that are dispatched to `handleMessageFromHub`, any correspondent device can send a spoofed `new_shared_address` message naming the victim's real address as one signer and an attacker-controlled address as another, with an `"or"` (rather than `"and"`) combinator, or otherwise obfuscated author-friendly-looking definitions: [6](#0-5) 

The wallet has no mechanism analogous to the OAuth report's missing "confidential vs public client" separation: just as `react-oauth-flow` blindly trusts front-end-supplied secret material instead of enforcing a server-side authorization boundary, ocore's wallet blindly trusts peer-supplied shared-address definitions/signers instead of enforcing that the shared address was actually negotiated with the claimed cosigners, silently registering it into `shared_addresses` / `shared_address_signing_paths`.

### Impact Explanation
`shared_addresses` and `shared_address_signing_paths` entries are subsequently trusted throughout the wallet - e.g. by `findAddress`/`readFullSigningPaths` (used to decide who must co-sign a payment) and `readSharedAddressCosigners`/`readAllControlAddresses` (used to determine which correspondent devices are considered legitimate cosigners for a shared address): [7](#0-6) [8](#0-7) 

An attacker can pre-register a definition such as `["or", [["address", victim_address], ["address", attacker_address]]]` that superficially looks like a shared/joint address (and is displayed/tracked as such client-side, e.g. via the `new_address` event) but in reality only requires the attacker's own signature to spend. If the victim is later socially engineered (e.g., via the associated arbiter/prosaic-contract flows, which build on the same `wallet_defined_by_addresses` primitives) into treating this address as a genuine multisig/escrow address and depositing funds into it, the attacker can unilaterally drain the funds — a concrete unauthorized-spending scenario stemming from improper authorization of who may register shared-address definitions naming the victim.

### Likelihood Explanation
The prerequisite is only that the attacker be a paired correspondent device (a normal, low-privilege actor in the ocore hub/device model — no hub, node, or network compromise required), which matches the "unprivileged... paired device" reachability constraint. Sending the crafted `new_shared_address` payload requires no cryptographic breaking, only satisfying the definition/signer self-consistency checks, which are checks over attacker-supplied data and thus trivially satisfiable.

### Recommendation
- Pass `from_address` into `handleNewSharedAddress` and require that it matches one of the `device_address` values in `body.signers` for the specific paths mapped to addresses the receiver does not already control.
- Do not auto-insert a new `shared_addresses`/`shared_address_signing_paths` record on receipt of an unsolicited `new_shared_address` message; instead require the same explicit user-approval flow used by `create_new_shared_address`/`approve_new_shared_address`, or at minimum require that a `pending_shared_addresses` record was created locally beforehand (i.e., the receiver actually initiated or approved this address).
- Warn/require extra confirmation when a definition combinator (`or`/`r of set` threshold) would allow spending without the local user's cosignature.

### Proof of Concept
1. Attacker device pairs with victim device (normal, unprivileged pairing via `device.js` pairing flow).
2. Attacker computes `arrDefinition = ["or", [["address", victim_address], ["address", attacker_address]]]`, `address = objectHash.getChash160(arrDefinition)`.
3. Attacker sends a `hub/message` with `subject: "new_shared_address"` and body `{address, definition: arrDefinition, signers: {"r.0": {address: victim_address, device_address: victim_device_address}, "r.1": {address: attacker_address, device_address: attacker_device_address}}}`.
4. Victim's `wallet.js` `case "new_shared_address"` dispatches directly to `handleNewSharedAddress` (no confirmation prompt); all structural checks pass because the attacker constructed a self-consistent definition.
5. `addNewSharedAddress` inserts the record; victim's wallet now silently "knows about" and may display this address as a shared/multisig address it is part of, while the attacker alone can spend any funds sent to it.

// It is possible that my device address is not mentioned in the definition if I'm a member of multisig address, one of my cosigners is mentioned instead
function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
