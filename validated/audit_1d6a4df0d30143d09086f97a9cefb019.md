This confirms the vulnerability. `Team.add_member` performs no organization check at all, and `find_or_create_by!` in `MembershipHandler#find_or_create_team!` only executes the block (which sets `organization`) when creating a new record — on an existing match by `github_id`, the pre-existing `organization` is left untouched while a new member is appended.### Title
Cross-organization `membership` webhook lets attacker's own signed org add themselves to a victim org's `Team` via `github_id` collision - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the org named in the payload itself (`repository_owner`), then `MembershipHandler#find_or_create_team!` looks up `Team` solely by `github_id`, with no check that the found record's `organization` matches the authenticated org. An attacker who owns any distinct GitHub org configured in Shipit can therefore send a `membership` `added` event naming their own org, but with `team.id` equal to a victim `Team`'s `github_id`, causing `team.add_member(member)` to add the attacker as a member of the victim team.

### Finding Description
The binding that should hold is: `verified_organization == params.dig('organization','login')` and this org must equal the `organization` of the `Team` record mutated by `github_id`. In fact:

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) resolves `repository_owner` via `params.dig('repository','owner','login') || params.dig('organization','login')` and verifies the signature using `Shipit.github(organization: repository_owner)`'s own `webhook_secret`. For a `membership` event, there is no `repository` key, so `repository_owner` == `params.dig('organization','login')`. An attacker who legitimately owns a configured org (`attacker-org`) can sign a request with their own `webhook_secret` and it verifies successfully — this is by design and not itself a flaw.
- `MembershipHandler#find_or_create_team!` (app/models/shipit/webhooks/handlers/membership_handler.rb:38-43) does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login; ... }`. The block that assigns `organization` only executes on **creation**. If a `Team` row with that `github_id` already exists (e.g. created earlier for `shopify`), `find_or_create_by!` returns the existing record unchanged — its `organization` remains `'shopify'`, but the code proceeds to operate on it under the attacker's authenticated request.
- `MembershipHandler#process` (lines 22-33) then calls `team.add_member(member)` for `action == 'added'`, and `Team#add_member` (app/models/shipit/team.rb:41-43) performs `members.append(member) unless members.include?(member)` with **no organization check whatsoever**.
- `User#authorized?` (app/models/shipit/user.rb:80-82) grants authorization based purely on `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, so if the victim `Team` is part of `Shipit.github_teams`, the attacker becomes authorized.

Exploit flow: attacker POSTs `X-Hub-Signature` computed with their own `attacker-org` `webhook_secret`, and JSON body:
```json
{
  "action": "added",
  "team": {"id": <victim_team_github_id>, "name": "...", "slug": "...", "url": "..."},
  "organization": {"login": "attacker-org"},
  "member": {"login": "attacker-login"}
}
```
Signature check passes (attacker's own secret matches their own org), `drop_unhandled_event`/`ExplicitParameters` schema don't reject this (all required fields present), and `find_or_create_team!` resolves to the pre-existing victim `Team` by `github_id`, silently ignoring that it belongs to `shopify` rather than `attacker-org`. No existing guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters`, `force_github_authentication`, `require_permission!`) checks organization consistency between the authenticated org and the `Team.organization` column on lookup.

The only real-world constraint is that the attacker must know/guess the victim team's numeric GitHub `github_id` — but this is a GitHub-side value, not a Shipit secret, and is often discoverable (e.g. via the GitHub API for teams the attacker can see, or leaked in prior webhook logs/other integrations); it is not a Shipit credential and doesn't require any Shipit secret.

### Impact Explanation
A successful request grants the attacker's own GitHub-identified user membership in a `Team` belonging to a different, victim organization, without ever possessing that organization's `webhook_secret`. If that `Team` is listed in `Shipit.github_teams` (lib/shipit.rb:256-258), `User#authorized?` (app/models/shipit/user.rb:81) now returns `true` for the attacker, granting them full Shipit authorization normally reserved for members of the victim org's privileged team — matching the "escalation into `Shipit.github_teams` authorization" High/Critical impact category. This is repeatable against any `Team` row whose `github_id` the attacker can learn, across any number of distinct victim organizations configured in the same Shipit instance, as long as the attacker controls at least one other configured org's webhook secret.

### Likelihood Explanation
Preconditions: (1) the Shipit instance is configured with the multi-org GitHub schema (`Shipit.github(organization:)`), (2) the attacker legitimately owns/administers a second GitHub organization that is also configured in this Shipit instance (with its own `webhook_secret`), and (3) the attacker knows the numeric `github_id` of the victim team. Given the multi-tenant nature this feature implies, condition (2) is plausible in shared Shipit deployments serving multiple orgs. Condition (3) requires reconnaissance but is not a Shipit secret. No Shipit session, API token, or victim-org secret is needed — cost is a single crafted HTTP POST to `/webhooks` with a correctly-computed HMAC using the attacker's own known secret.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the authenticated `repository_owner`/`params.organization.login` matches the existing `Team#organization` before mutating it; if it doesn't match, reject/drop the event instead of operating on the mismatched record. Equivalently, scope the lookup by both `github_id` and `organization` (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)` or raise/log and abort if an existing record's `organization` differs) so a `github_id` collision across organizations cannot be exploited to mutate another org's team membership.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "membership webhook from a different, attacker-controlled organization cannot add members to another org's team" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify', existing github_id
  attacker_org = 'attacker-org'
  # Assume Shipit.github(organization: 'attacker-org') is configured with its own webhook_secret in test secrets

  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: attacker_org },
    member: { login: 'attacker-login' }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', Shipit.github(organization: attacker_org).send(:webhook_secret), payload)

  assert_no_difference -> { victim_team.members.count } do
    post shipit.github_webhooks_path,
      params: payload,
      headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => signature, 'Content-Type' => 'application/json' }
  end

  refute victim_team.members.exists?(login: 'attacker-login')
end
```
Before the fix, this test fails: the request is accepted (`repository_owner == 'attacker-org'` verifies against `attacker-org`'s secret), `Team.find_or_create_by!(github_id: victim_team.github_id)` returns `victim_team` unchanged (`organization` still `'shopify'`), and `team.add_member(member)` inserts a `Membership` linking `attacker-login` to `victim_team`, asserting the described equality break: `authenticated_org ('attacker-org') != team.organization ('shopify')` while the mutation still proceeded.
