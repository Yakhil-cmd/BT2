### Title
`OpenedHandler#provision?` operator-precedence bug lets `review_stacks_enabled: false` repositories still create ReviewStacks; combined with `webhook_secret: nil` this is reachable from a fully unauthenticated POST - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` is written as `A && B || C || D` instead of `A && (B || C || D)`, so `repository.review_stacks_enabled` only gates the `allow_all?` branch and does **not** gate `allow_with_label?`/`prevent_with_label?` branches. Combined with `GitHubApp#verify_webhook_signature` returning `true` when no `webhook_secret` is configured for the organization, an attacker who need not even be a GitHub user can POST a crafted `pull_request` "opened" payload directly to `WebhooksController#create` and cause `ReviewStack.create!` + `Shipit::ReviewStackProvisioningQueue.add` to run for a repository with `review_stacks_enabled: false`.

### Finding Description
The claimed-safe binding is: `review_stacks_enabled == true` must be required for **any** provisioning path in `provision?`. The actual code is: [1](#0-0) 

Ruby operator precedence makes `&&` bind tighter than `||`, so this evaluates as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

For a repository configured with `provisioning_behavior: allow_with_label` and `review_stacks_enabled: false`, if the incoming PR carries the configured label, the second disjunct is `true` independent of `review_stacks_enabled`, so `provision?` returns `true`. This contrasts with the correctly parenthesized sibling logic in `LabeledHandler#respond_to_label_change?`, which explicitly `&&`s `repository.review_stacks_enabled` with the whole `(archive? || unarchive?)` expression [2](#0-1) , confirming the opened-handler is a bug relative to the intended design elsewhere in the codebase.

`respond_to_pull_request_opened?` then just checks `params.action == "opened" && provision?` [3](#0-2) , and on success calls `ReviewStackAdapter#find_or_create!`, which writes a `ReviewStack` row using attacker-controlled `params.pull_request.head.ref` as `branch` and enqueues it for provisioning [4](#0-3) .

On the entry-point side, `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, and `GitHubApp#verify_webhook_signature` explicitly returns `true` when `webhook_secret` is blank: `return true unless webhook_secret` [5](#0-4) . This is an intentional fallback for orgs without a configured secret, not itself new engine misbehavior, but it does mean that for any org that hasn't set `webhook_secret`, signature verification is a no-op — the request "repository_owner" is taken straight from the attacker-supplied JSON body [6](#0-5) , and the handler resolves the target `Repository` from the same attacker-supplied `params.repository.full_name` [7](#0-6) .

Neither `drop_unhandled_event`, `ExplicitParameters` schema validation, nor any model validation on `Repository`/`ReviewStack` checks `review_stacks_enabled` before writing the row — that check exists only inside the buggy `provision?` predicate. `ExplicitParameters` merely enforces the payload shape (types/presence), not authorization, and the request path requires no session, no `ApiClient` token, and no real GitHub interaction whatsoever, satisfying the question's premise that this is reachable by a fully anonymous requester when the target org has no `webhook_secret` set.

### Impact Explanation
For a targeted `Repository` with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) and `review_stacks_enabled: false`, an unauthenticated internet requester can write a `ReviewStack` record and push it into `Shipit::ReviewStackProvisioningQueue`, which is later picked up by `ReviewStackProvisioningQueue#work` to call `stack.provisioner.provision?` / `stack.provision` — i.e., an operation the operator explicitly disabled at the repository level (`review_stacks_enabled: false`) still gets triggered. This is a repository-scoped authorization/config bypass: a stack gets created and queued for provisioning for a repository that opted out of review stacks. Whether this escalates all the way to `PTY.spawn`/`Command` execution depends on the downstream `provisioner.provision?`/`stack.provision` implementation (not fully traced here), but at minimum it is an unauthorized database write and queuing of a privileged background operation for a repository/branch the attacker fully controls (`head.ref` is attacker-supplied). The bug is repeatable against any repository configured with `allow_with_label`/`prevent_with_label` and `review_stacks_enabled: false`, and — separately and more broadly — against any organization that has not configured `webhook_secret`, regardless of `review_stacks_enabled`. This matches "record written for a repository that did not authenticate/enable it" and potentially "unauthorized deploy/provision," landing at High/Critical depending on what `stack.provision` executes.

### Likelihood Explanation
Two independent preconditions are required, both plausible misconfigurations rather than default-secure states: (1) the organization's `webhook_secret` must be unset/blank for signature bypass, and (2) the target repository must have `review_stacks_enabled: false` with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label`. Given both, the attack is a single crafted JSON POST with no GitHub account, no secrets, and is trivially repeatable (each POST with a new `number`/`environment` creates a new `ReviewStack`). If `webhook_secret` is configured (the documented/expected setup), the whole path is blocked at `verify_signature` regardless of the `provision?` bug, so likelihood in a properly configured deployment is low; the finding is real but conditional on the missing-secret misconfiguration plus the `provision?` logic bug.

### Recommendation
Fix the operator precedence in `provision?` to require `review_stacks_enabled` for all branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Separately (out of scope for this specific file but relevant to the compound exploit), consider hard-failing webhook delivery when `webhook_secret` is not configured for an organization rather than silently accepting unsigned payloads.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_precedence_test.rb
test "does not provision when review_stacks_enabled is false even with matching label" do
  repository = shipit_repositories(:shipit).tap do |r|
    r.update!(review_stacks_enabled: false, provisioning_behavior: 'allow_with_label')
  end

  params = ExplicitParameters::Params.new(
    action: 'opened',
    number: 42,
    pull_request: {
      id: 1, number: 42, url: 'http://x', title: 't', state: 'open',
      additions: 1, deletions: 1,
      head: { sha: 'abc123', ref: 'evil-branch' },
      user: { login: 'attacker' },
      assignees: [],
      labels: [{ name: repository.provisioning_label_name }]
    },
    repository: { full_name: repository.full_name },
    sender: { login: 'attacker' }
  )

  assert_no_difference -> { Shipit::ReviewStack.count } do
    Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params).process
  end
end
```
And, to demonstrate the controller-level bypass (no signature required when `webhook_secret` is nil), a full-stack test posting to `POST /webhooks` with header `X-Github-Event: pull_request`, no `X-Hub-Signature`, against a `Shipit.github_app` config lacking `webhook_secret`, asserting `head :ok` is returned and that `Shipit::ReviewStack.count` does not increase once `provision?` is fixed (currently it does increase, demonstrating the bug).
