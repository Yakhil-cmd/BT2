This maps directly onto the "organization that authenticated versus the entity that is written" binding described in the task rules. `WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to check the HMAC against using a value pulled from the *repository* portion of the untrusted payload, while `MembershipHandler#process` later mutates `Team`/`Membership` records using a completely different, independently-supplied `organization.login` field from the same payload. Neither the parameter schema nor the controller cross-checks that these two values refer to the same GitHub organization.

### Title
Membership webhook signature is verified against `repository.owner.login`'s org while the actual write targets an unrelated `organization.login` — cross-org `Shipit.github_teams` privilege escalation - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` derives the "authenticating organization" from `repository.owner.login` (falling back to `organization.login` only when the `repository` key is entirely absent), and uses that organization to pick the `GitHubApp`/`webhook_secret` used to validate `X-Hub-Signature`. `MembershipHandler`, however, never reads `repository.owner.login` — it creates/updates `Team` records and adds/removes `Membership` rows using the payload's independent `organization.login` field. An attacker who can produce a validly-signed (or unsigned-but-accepted, when a configured org has no `webhook_secret`) payload for *any* organization the app is configured for can set `repository.owner.login` to that organization (to pass signature verification) while setting `organization.login`/`team.id` to a *different*, victim organization, adding an arbitrary GitHub login as a member of a `Shipit::Team`. Since `Shipit.github_teams` gates `current_user.authorized?` in `Authentication#force_github_authentication`, this is a direct authorization escalation into the app.

### Finding Description
- Signature verification selects the app/secret from the payload's own `repository.owner.login`: [1](#0-0) [2](#0-1) 

- `verify_webhook_signature` treats a blank `webhook_secret` as automatically verified, and only checks the `sha1` `X-Hub-Signature` header: [3](#0-2) 

- `MembershipHandler` uses an entirely separate field, `organization.login`, to determine which `Team` gets created/mutated and which member gets added, without any reference to `repository.owner.login`: [4](#0-3) 

- `Shipit.github` resolves the `GitHubApp` (and thus the `webhook_secret` used above) purely from the string passed in, with no relationship enforced to any other payload field: [5](#0-4) 

- Team membership, populated via this webhook, is exactly what gates application access: [6](#0-5) 

The binding that should hold is: `organization used to select/verify the webhook_secret == organization whose Team/Membership records are mutated`. Before the vulnerable code path, this holds because in genuine GitHub-emitted `membership` events there is no `repository` key at all, so `repository_owner` correctly falls back to `organization.login` — the same value the handler uses. After an attacker directly POSTs to `/webhooks` (the endpoint has no other authentication and is intentionally public for GitHub to reach), they fully control both fields independently: they can supply a `repository` object (satisfying `repository_owner` dig) pointing at an organization X for which they can satisfy/bypass the signature check, while supplying an unrelated `organization.login`/`team.id` pointing at victim organization Y. The equality is broken because the controller never verifies `repository.owner.login == organization.login` and the handler never re-derives the acting organization from the signature-verified value.

### Impact Explanation
This breaks into "escalation into `Shipit.github_teams` authorization" (explicitly listed High-impact category). An unprivileged external attacker, with no repository write access, no `ApiClient` token, and no session, can add an arbitrary GitHub login (including themselves) to any `Shipit::Team` that is configured in `Shipit.github_teams`. Since `Authentication#force_github_authentication` grants access to the whole Shipit UI/API surface (deploys, tasks, stacks, etc.) to anyone belonging to one of those teams, this is a full authentication/authorization bypass for the deployment tool.

### Likelihood Explanation
Exploitability depends only on being able to satisfy signature verification for *some* organization configured in the multi-org `github:` secrets block (a configuration explicitly documented and supported, see `docs/setup.md` "Using Multiple Github Applications"). This is trivially satisfiable if any configured org has an unset `webhook_secret` (documented as optional), and otherwise requires only knowledge of one org's webhook secret — not the victim org's. No repository write access or session/token is required, matching the "unprivileged attacker" scope of this exercise.

### Recommendation
Bind the two identities together explicitly: derive the acting/verifying organization for every event from a single canonical field, and have `MembershipHandler` (and any other org-scoped handler) validate that `params.organization.login` matches the organization used to verify the signature (`repository_owner`), rejecting the webhook otherwise. Alternatively, always require `organization.login` (never `repository.owner.login`) for `membership` events specifically, and never allow a payload to carry both an unrelated `repository` and `organization` sub-object for the same event.

### Proof of Concept
1. Deploy Shipit with two orgs configured under `github:` (as in `test/dummy/config/secrets_double_github_app.yml`), e.g. `OrgAttacker` (no `webhook_secret` set, or one known to the attacker) and `OrgVictim` (has a `Shipit::Team` referenced by `Shipit.github_teams`).
2. POST directly to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": <victim_team_github_id>, "name": "Victim Team", "slug": "victim", "url": "https://example.com" },
  "organization": { "login": "OrgVictim" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "OrgAttacker" } }
}
```
3. `verify_signature` computes `repository_owner` = `"OrgAttacker"` (present in `repository.owner.login`), and calls `Shipit.github(organization: "OrgAttacker").verify_webhook_signature(...)`, which passes trivially if `OrgAttacker`'s `webhook_secret` is blank/known.
4. `MembershipHandler#process` runs unaffected by the organization used for verification: it creates/finds `Team` by `params.team.id` (the victim's team) and adds `attacker-github-login` as a member — see `find_or_create_team!` in `app/models/shipit/webhooks/handlers/membership_handler.rb`.
5. If `OrgVictim`'s team is listed in `Shipit.github_teams`, the attacker's user is now authorized, per `Authentication#force_github_authentication`, to fully use the Shipit deployment application.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
