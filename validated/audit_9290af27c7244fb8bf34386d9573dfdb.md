### Title
Unprivileged `DepositDelegatorRewards` instruction lets any transaction sender permanently block a vote account's authorized withdrawer from closing or fully withdrawing the account - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The `DepositDelegatorRewards` vote instruction (SIMD-0123) allows *any* signer who controls lamports to deposit funds into *any* vote account and increment its `pending_delegator_rewards` field, without the vote account or its authorized withdrawer needing to sign or consent. The `withdraw` instruction later refuses to close the vote account, or reduces the maximum withdrawable balance, whenever `pending_delegator_rewards > 0`. This lets an attacker front-run (or simply pre-empt) an authorized withdrawer's close/withdraw transaction by submitting a cheap, unsigned-by-victim deposit, denying the legitimate owner's withdrawal/close operation — the same "attacker-controlled recipient parameter that mutates victim-keyed state and blocks a subsequent legitimate operation" pattern described in the Omnipool `depositFor`/`withdraw` front-running report.

### Finding Description
`deposit_delegator_rewards` only requires the *source* account (the depositor) to be a signer; the vote account itself is never required to sign or authorize the deposit: [1](#0-0) 

Because of this, any address can call `VoteInstruction::DepositDelegatorRewards` against an arbitrary vote account and increment its `pending_delegator_rewards`: [2](#0-1) 

The vote program's `withdraw` instruction consults `pending_delegator_rewards` in two places that directly gate the legitimate authorized withdrawer's ability to move funds out of the account:

1. It refuses to fully close the vote account (`remaining_balance == 0`) if `pending_delegator_rewards > 0`: [3](#0-2) 

2. It raises the minimum required remaining balance by `pending_delegator_rewards` for any partial withdrawal: [4](#0-3) 

An attacker who wants to block a validator's authorized withdrawer from closing or fully draining its vote account simply issues `DepositDelegatorRewards` with a minimal `deposit` amount (as small as 1 lamport, since a `0` deposit is a documented no-op) against the victim's vote account right before (or in place of) the intended withdraw/close transaction. This is functionally identical to the Omnipool bug: the attacker supplies a victim-controlled address as an instruction account and mutates state (`pending_delegator_rewards`) keyed to that victim address without the victim's consent, which then trips a guard in a later, legitimate operation belonging to the victim.

### Impact Explanation
- The authorized withdrawer's `Withdraw` transaction targeting `remaining_balance == 0` will fail with `InstructionError::InsufficientFunds` as long as `pending_delegator_rewards > 0`, denying account closure.
- Partial withdrawals are also capped more tightly, since `min_balance` now includes `pending_delegator_rewards` in addition to the rent-exempt minimum.
- The attack is inexpensive (a single lamport plus the deposit's own transaction fee) and can be repeated any time `pending_delegator_rewards` returns to zero (e.g., after each epoch's block-reward distribution drains it — see `calculate_block_reward` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`), letting an attacker sustain indefinite denial-of-service against a target vote account's withdrawal/close capability for negligible ongoing cost.
- This does not directly steal funds, but it is a fund-locking/DoS primitive reachable by any unprivileged transaction sender, matching the "loss of user funds"/"lock user funds" impact class of the reference report.

### Likelihood Explanation
Likelihood is medium: exploitation requires only knowledge of the target vote account's pubkey (public information) and a small amount of lamports, with no special permissions. The attacker must act opportunistically (e.g., watch the mempool/gossip for withdraw/close transactions targeting a specific vote account) to maximize disruption, similar to the front-running assumption in the original Omnipool report, but even without front-running, a persistent attacker can proactively keep `pending_delegator_rewards` non-zero on a target vote account to block closures indefinitely.

### Recommendation
- Require the authorized withdrawer (or vote account) to explicitly authorize/opt in to accepting delegator-reward deposits, rather than allowing an arbitrary unauthorized sender to mutate `pending_delegator_rewards` for any vote account.
- Alternatively, decouple the withdraw-blocking logic from an attacker-triggerable value: e.g., allow the authorized withdrawer to withdraw down to the rent-exempt minimum regardless of `pending_delegator_rewards`, and separately account for/reserve delegator rewards without gating the withdrawer's own principal.
- At minimum, impose a floor on `deposit` (reject zero/negligible amounts) so that griefing via minimal deposits is not cost-free, and consider rate-limiting or capping how often `pending_delegator_rewards` can be replenished by third parties within a short window relative to legitimate withdraw attempts.

### Proof of Concept
1. Identify a target vote account `V` with authorized withdrawer `W` who intends to fully withdraw/close the account (`remaining_balance == 0`).
2. Attacker `A` (holding at least 1 lamport) submits:
   ```
   VoteInstruction::DepositDelegatorRewards { deposit: 1 }
   accounts: [vote_account: V (writable, NOT signer), source: A (writable, signer), system_program]
   ```
   This succeeds per `deposit_delegator_rewards` (programs/vote/src/vote_state/mod.rs:936-988), setting `V`'s `pending_delegator_rewards = 1` (or higher, accumulating across repeated calls) — see the accepted test flow at `programs/vote/src/vote_processor.rs:5110-5140` demonstrating a successful deposit updates `pending_delegator_rewards`.
3. `W` submits `Withdraw { lamports: full_balance }` targeting `V` intending to close the account. This now fails with `InstructionError::InsufficientFunds` due to the check at `programs/vote/src/vote_state/mod.rs:1090-1092` (`pending_delegator_rewards > 0`).
4. `A` repeats step 2 whenever `pending_delegator_rewards` returns to zero (e.g., after epoch reward distribution), sustaining denial of `W`'s ability to close/fully withdraw the vote account at negligible ongoing cost.
