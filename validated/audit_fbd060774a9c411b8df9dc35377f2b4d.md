### Title
Webhook signature verification keys off an unauthenticated `repository.owner.login`/`organization.login` field while write actions use the independently attacker-controlled `repository.full_name` field, enabling cross-tenant/cross-repository webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-tenant deployments of this engine (multiple GitHub orgs configured under `secrets.github`, each with its own `webhook_secret`), `WebhooksController#verify_signature` selects *which* organization's HMAC secret to verify the inbound webhook against using a field taken from the still-unauthenticated JSON body (`repository.owner.login` / `organization.login`). Once the signature check passes, the handler dispatch layer instead uses a *different* unauthenticated field, `repository.full_name`, to decide which `Repository`/`Stack` the event actually mutates. Because nothing ties these two fields together, an org that can authenticate a webhook (using its own known secret) is not the org whose repository actually gets written.

### Finding Description
`verify_signature` picks the verifying `GitHubApp` (and thus the HMAC secret) via `repository_owner`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up the per-organization secret via `github_app_config(organization)`, which is exactly the tenant-keyed config the operator sets up for each onboarded GitHub org: [3](#0-2) 

After the signature check passes, `create` hands the *entire* raw JSON body to the registered handlers: [4](#0-3) 

Handlers, however, do not use `repository.owner.login`; they resolve the affected `Repository`/`Stack` from a separate field, `repository.full_name`: [5](#0-4) 

Both `repository.owner.login` and `repository.full_name` are attacker-supplied JSON fields inside the same HTTP body, and the HMAC signature (`X-Hub-Signature`) covers the raw body as a whole—but which *secret* is used to validate that signature is chosen using one of those fields before authentication has occurred, and the field that determines *what gets acted on* is a different one. There is no check anywhere that `repository.full_name`'s owner matches the org whose secret validated the signature. This breaks the binding: **organization authenticated (`repository.owner.login`, used to pick the verifying secret) ≠ repository written (`repository.full_name`, used by handlers)**.

### Impact Explanation
On a shared/multi-tenant Shipit install serving several customer GitHub organizations (each configured under a distinct key in `secrets.github` with its own `webhook_secret`, as documented in `docs/setup.md` and `README.md`), any tenant that knows its own webhook secret (which it necessarily does, having configured its own GitHub App) can craft a JSON payload where:
- `repository.owner.login` (and/or `organization.login`) = the attacker's own org — so `verify_signature` validates the HMAC using the attacker's own known secret and passes.
- `repository.full_name` = `"victim-org/victim-repo"` — so the actual event handler (e.g. `push`, `status`, `check_suite`, `pull_request` handlers) resolves and mutates the victim organization's `Repository`/`Stack` records.

This yields cross-repository/cross-tenant writes: e.g. forging `push` events to enqueue `GithubSyncJob` against the victim's stack, forging `status` events to fabricate commit statuses that gate deploy/merge decisions, or forging `pull_request` events (closed/labeled/opened) to manipulate the victim's merge queue — all without ever possessing the victim org's webhook secret, GitHub App key, or any Shipit session/API token. This matches the Critical bucket ("cross-repository writes" / "unauthorized deploy").

### Likelihood Explanation
Exploitability requires only: (1) the target instance be configured for more than one GitHub organization (a documented, supported multi-tenant configuration), and (2) the attacker control (or be) one of the onboarded, non-victim organizations — an unprivileged position relative to other tenants on the same instance. No repository write access, App private key, or Shipit session is required; the attacker only needs the webhook secret of their own, already-trusted org, which they legitimately possess.

### Recommendation
- **Short term:** After signature verification succeeds, re-validate that the repository/organization asserted in `repository.owner.login` (used to select the verifying secret) matches the organization owning `repository.full_name` (used by handlers) before dispatching to any handler; reject mismatches with `422`.
- **Long term:** Bind webhook verification and event dispatch to the same authenticated identity — derive both the verifying secret *and* the acted-upon repository from a single, consistently-scoped field (or from the installation/App identity resolved via GitHub's `installation.id`), rather than two independently attacker-controlled JSON fields, and document this invariant explicitly for future webhook handler authors.

### Proof of Concept
Given a Shipit instance configured with two tenant orgs, `attacker-org` (secret known to the attacker) and `victim-org` (secret unknown):

```
POST /github_authentication/... (webhooks endpoint)
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1 of body using attacker-org's webhook_secret>

{
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```

`verify_signature` computes `Shipit.github(organization: "attacker-org")` and validates the HMAC successfully (attacker knows this secret). Signature check passes, `create` runs, and the `push` handler resolves the target via `repository.full_name` → `victim-org/victim-repo`, enqueuing `GithubSyncJob` (and equivalently for `status`/`pull_request`/`check_suite` handlers) against the victim's stack — despite the signature never having been validated against `victim-org`'s secret.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
