### Title
Unbounded disk write in `downloadAsset` during `gh extension install` enables disk exhaustion DoS - ([File: pkg/cmd/extension/http.go])

### Summary
`downloadAsset` streams a GitHub release asset body directly to disk via `io.Copy(f, resp.Body)` with no maximum size enforcement, no `Content-Length` validation, and no bounded reader. An attacker who publishes a malicious extension release can serve an arbitrarily large or effectively infinite response body, causing `gh extension install` to write unbounded data to the victim's filesystem until disk space is exhausted.

### Finding Description
`downloadAsset` (`pkg/cmd/extension/http.go`, invoked from `Manager.installBin` in `pkg/cmd/extension/manager.go`) fetches the asset URL from a release the attacker controls, opens the destination binary path, and copies the entire response body straight to disk: [1](#0-0) 

There is no check of `resp.ContentLength`, no `io.LimitReader` wrapping `resp.Body`, and no maximum-size cap before or during the `io.Copy` call. Since the attacker fully controls the content and size of a release asset for their own repository (assets are fetched by URL obtained from the attacker's own release metadata via `fetchLatestRelease`/`fetchReleaseFromTag`), they can serve a response with a missing/false `Content-Length` and a streaming, effectively unbounded body (e.g., using chunked transfer encoding that never terminates or is extremely large). `gh extension install` will then attempt to write that entire stream to `destPath` (the extension binary path) with no upper bound, exhausting the victim's disk.

None of the existing safeguards in this code path — `safeurl` URL validation, HTTP status checks (`resp.StatusCode > 299`), or `api.HandleHTTPError` — address body size; they only validate the URL/host and status code, not the payload length.

### Impact Explanation
This matches the "unbounded resource consumption" impact class named in scope: an attacker-controlled extension release can cause disk exhaustion / denial of service on the victim machine during normal use of `gh extension install`, potentially destabilizing the host (failing writes for other processes, crash of services relying on free disk space).

### Likelihood Explanation
The precondition is minimal: the attacker only needs to publish a public extension repository and release with a malicious/oversized asset — no privileges, tokens, or victim interaction beyond the victim voluntarily running `gh extension install <attacker-repo>`, which is the normal intended use of the feature. This is fully repeatable and requires no timing or race conditions.

### Recommendation
Enforce a maximum download size for extension binary assets, e.g., wrap `resp.Body` with `io.LimitReader(resp.Body, maxSize)` and treat truncation as an error (or check `resp.ContentLength` against a cap before starting the copy, keeping in mind `Content-Length` can be absent/false and should not be solely relied upon). Abort and clean up the partially written file if the limit is exceeded.

### Proof of Concept
```go
func TestDownloadAsset_UnboundedBody(t *testing.T) {
    reg := &httpmock.Registry{}
    reg.Register(
        httpmock.REST("GET", "assetpath"),
        func(req *http.Request) (*http.Response, error) {
            // Simulate an attacker-controlled endless/huge streaming body,
            // no Content-Length set.
            pr, pw := io.Pipe()
            go func() {
                buf := make([]byte, 1<<20) // 1MB chunks
                for {
                    if _, err := pw.Write(buf); err != nil {
                        return
                    }
                }
            }()
            return &http.Response{
                StatusCode: 200,
                Body:       pr,
                Header:     http.Header{},
            }, nil
        },
    )
    client := &http.Client{Transport: reg}

    tmpFile := filepath.Join(t.TempDir(), "ext-binary")
    url, _ := safeurl.NewSafeURL("https://example.com/assetpath")

    done := make(chan error, 1)
    go func() { done <- downloadAsset(client, url, tmpFile) }()

    select {
    case <-time.After(2 * time.Second):
        // downloadAsset has already written well beyond any reasonable
        // extension binary size limit and has not stopped.
        info, _ := os.Stat(tmpFile)
        require.Greater(t, info.Size(), int64(50<<20), "expected downloadAsset to have written unbounded data without a size cap")
    case err := <-done:
        t.Fatalf("expected downloadAsset to still be copying unbounded data, got early return: %v", err)
    }
}
```
Expected (failing) result with current code: the write is unbounded and keeps growing indefinitely / test observes no cap enforced, confirming the missing `io.LimitReader`/size-check as shown at `pkg/cmd/extension/http.go` lines 100–111.
