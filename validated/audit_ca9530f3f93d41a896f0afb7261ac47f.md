### Title
Webhook signature verification failure does not halt request processing, allowing unsigned/forged GitHub webhooks to mutate stack state - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` records that verification failed by calling `head(422)`, but never stops the callback chain (no `throw(:abort)`, no explicit `return`), and `#create` unconditionally dispatches the parsed payload to registered handlers. On modern Rails (this engine requires `rails >= 8.1.1`), `before_action` callbacks only halt when the callback explicitly throws `:abort` — merely calling `head`/`render` no longer implicitly stops the chain (that auto-halt behavior was removed in Rails 5). As a result, an attacker who sends a webhook request with an invalid or missing `X-Hub-Signature` still gets their JSON payload run through `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`.

### Finding Description
The verification check only sets the response head and logs, without halting: [1](#0-0)  The `create` action then runs unconditionally regardless of what happened in the prior `before_action`: [2](#0-1) 

The signature check itself is delegated to `GithubApp#verify_webhook_signature`, which does correctly compute an HMAC-SHA1 over the raw body: [3](#0-2)  But since the controller doesn't halt on `verified == false`, this cryptographic check becomes advisory rather than enforced — the binding "the organization that authenticated the request" versus "the organization/repository whose state is written by the handler" is broken. The `for_event` lookup dispatches to real state-mutating handlers (`PushHandler`, `StatusHandler`, `MembershipHandler`, `CheckSuiteHandler`, PR handlers) as declared in `app/models/shipit/webhooks.rb`: [4](#0-3) 

This is the direct analog of the reported bug class: the `verified`/`succeeded` boolean is computed and even used to set a response, but the failure is never propagated to actually stop the subsequent logic — the same "denoted but not enforced" error-handling pattern from the external report's `call` helper.

### Impact Explanation
This allows an unauthenticated, unprivileged attacker (no GitHub App secret, no Shipit session, no API token) to POST arbitrary attacker-crafted JSON to `/github/webhooks` with any (or no) `X-Hub-Signature` and have it processed by real handlers as if it came from GitHub. Depending on handler, this can: enqueue `GithubSyncJob` for arbitrary stacks, forge commit statuses, fabricate `check_suite` results affecting deploy gating, or create/modify `Team`/`User` records via the membership handler — i.e., state mutation and CI/deploy-gating data are attacker-controlled without any authenticated GitHub relationship. This crosses the "GitHub organization that authenticated" vs "repository/stack whose state is written" trust boundary described in the rules, qualifying as unauthorized writes to stack state / deploy gating without needing repository write access or a Shipit session.

### Likelihood Explanation
High. The endpoint is public (it's the GitHub webhook receiver, mounted by design at a fixed unauthenticated route), requires only crafting an HTTP POST with an `X-Github-Event` header and JSON body, and the flaw is a straightforward Rails filter-chain misuse present on every request. No exotic conditions are needed beyond knowledge of the webhook route and event handler payload shapes (both are open-source/documented).

### Recommendation
In `verify_signature`, explicitly halt the request when verification fails, e.g. `throw(:abort) unless verified` (or `return head(422) unless verified`), and add a regression test asserting that `Shipit::Webhooks.for_event` handlers are never invoked when the signature check fails (currently the existing test only asserts `assert_response :unprocessable_entity`, not that no jobs were enqueued/no handler ran).

### Proof of Concept
1. Attacker sends:
```
POST /github/webhooks
X-Github-Event: push
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   (invalid)
Content-Type: application/json

{"ref": "refs/heads/master", "after": "<attacker-chosen sha>", "repository": {"full_name": "victim/repo", "owner": {"login": "victim-org"}}}
```
2. `verify_signature` computes `verified = false`, calls `head(422)`, logs, but does not halt.
3. `create` still executes: `Shipit::Webhooks.for_event('push')` returns `[Handlers::PushHandler]`, which is invoked with the attacker's `params`, causing `GithubSyncJob` to be enqueued for the targeted stack with an attacker-chosen `expected_head_sha` — this can be verified against the existing test `test ":push with the target branch queues a GithubSyncJob"` (`test/controllers/webhooks_controller_test.rb` around lines 23-32), which shows the exact enqueue behavior triggered by `create`, but note the "verifies webhook signature" test at lines 94-107 never asserts that the job/handler was *not* run despite the 422 status.       github_app = Shipit.github(organization: repository_owner)
```ruby
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
