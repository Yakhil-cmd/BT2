### Title
CCMenu token issued for one stack grants unauthenticated read access to every stack's deploy state - ([File: app/controllers/shipit/ccmenu_url_controller.rb], [File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` token intended to expose a single stack's build status to third-party monitoring tools (CCMenu), but the token is never bound to that stack, and the endpoint that consumes it (`Api::CCMenuController`) bypasses the engine's own per-token stack-scoping mechanism. Any authenticated Shipit user who requests a CCMenu URL for one stack receives a token that can read the CI/deploy status of **every** stack in the instance, not just the one they requested it for — breaking the binding "the stack a token authorizes" vs. "the stack it touches," analogous to the report's core class of missing enforcement between an approved value and the value actually acted on.

### Finding Description
`Api::BaseController` implements the intended scoping mechanism for stack-restricted `ApiClient`s: [1](#0-0) 
`stacks` limits the queryable set to `current_api_client.stack_id` when the client is scoped, and `stack` looks up the requested `params[:stack_id]` only within that scoped set. This is verified for other API controllers, e.g. the test proving a stack-scoped client ("here_come_the_walrus", fixture bound to `stack: shipit`) only ever sees that one stack: [2](#0-1) 

`Api::CCMenuController`, however, does not use this shared helper at all — it overrides `stack` to resolve directly from the raw request parameter, with no reference to `current_api_client.stack_id`: [3](#0-2) 

Separately, the token that is supposed to represent "read access to this one stack" is created without ever binding a `stack`: [4](#0-3) 
`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` passes no `stack:` attribute, and additionally always reuses the same record per user (matched only on `creator` + the constant name `'CCMenu Client'`), regardless of which stack the URL was generated for. `ApiClient#stack` is `optional: true`, so this client's `stack_id` is `nil`: [5](#0-4) 

The generated `authentication_token` is a bare `SimpleMessageVerifier` signature of the row id with no expiry and no embedded stack constraint: [6](#0-5) 

Putting this together: whatever `stack_id` was passed when the URL was generated is irrelevant to what the resulting token can access, because (a) the client record has no `stack_id`, and (b) even if it did, `CCMenuController#stack` never consults it. The token only carries the coarse `read:stack` permission, checked by `require_permission :read, :stack`: [7](#0-6) 
which is satisfied for any stack ID supplied at request time.

### Impact Explanation
Any user who can trigger `CCMenuUrlController#fetch` for a single stack they are permitted to view obtains a URL/token (`?token=...`) that is designed to be embedded in external, non-Shipit-authenticated tooling (CI dashboards / CCMenu clients) — i.e., it is meant to leave the trust boundary of the authenticated Shipit session. That same token can be replayed against `Api::CCMenuController#show` with an arbitrary `stack_id`, returning build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock state, etc.) for stacks the user was never scoped to and that Shipit's own per-client stack restriction is supposed to prevent. This is an unauthenticated (from Shipit's session perspective) read of stack state across the whole instance, matching the "High — unauthenticated read of stack state" impact bucket.

### Likelihood Explanation
High. No admin/owner compromise is required — the flaw is triggered by the intended, documented per-stack "get my CCMenu URL" feature available to any ordinary authenticated user; no unusual configuration or privileged action is needed to obtain the over-broad token, and the token itself does not expire.

### Recommendation
- Bind the token to the requested stack: pass `stack: stack` into `ApiClient.create_with(...)`/`find_or_create_by!` in `CCMenuUrlController#client`, and include the stack id in the uniqueness lookup so distinct stacks get distinct, correctly-scoped clients.
- Make `Api::CCMenuController#stack` reuse the base controller's scoped `stacks`/`stack` helpers (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so a stack-scoped `ApiClient` cannot be used against any other stack.

### Proof of Concept
1. As a normal Shipit user with access to `stack-A`, open its settings and let the browser extension/CCMenu integration call `PUT /merge_status/... /ccmenu_url` (`CCMenuUrlController#fetch`) for `stack-A`. This returns a URL containing `token=<T>`.
2. Take that token `T` and issue `GET /api/*stack-B*/ccmenu?token=T` for any other stack `stack-B` in the same Shipit instance that the user has no special relation to.
3. `Api::CCMenuController#authenticate_api_client` resolves `T` to the user's shared `'CCMenu Client'` `ApiClient` (no `stack_id`), `require_permission :read, :stack` passes because the client has `read:stack`, and `#stack` resolves `stack-B` directly from `params[:stack_id]` — the request returns `stack-B`'s live build/deploy status even though the token was minted while viewing only `stack-A`.
