### Title
Unauthenticated GitHub webhooks can forge `membership` events to escalate arbitrary GitHub users into `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`, `lib/shipit/github_app.rb`)

### Summary
### Finding Description
The BribeVault report describes a privileged role (`DEFAULT_ADMIN_ROLE`) that can bypass the intended trust chain (user's own `approve`/allowance) to move funds it was never meant to control. The engine-level analog is a broken binding between "the GitHub organization that is asserted to have signed a webhook" and "the fact that the payload was actually produced by GitHub at all."

`WebhooksController#verify_signature` resolves which `GithubApp` config to check against purely from attacker-supplied JSON fields (`repository.owner.login` or, absent that, `organization.login`), then calls `github_app.verify_webhook_signature`: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` short-circuits to `true` whenever no `webhook_secret` is configured for that organization: [3](#0-2) 

The webhook secret is explicitly documented as **optional** in the setup guide: [4](#0-3) 

`WebhooksController` has no session/authentication requirement at all (it's a plain `ActionController::Base`, unlike `Shipit::Authentication`-protected controllers), so this endpoint is reachable by any unauthenticated network client.

Once "verified," the `membership` event is dispatched to `MembershipHandler`, which trusts the payload's `organization.login`, `team`, and `member.login` fields to create/update a `Team` and add or remove `Membership` records — with zero corroborating call back to GitHub to confirm the asserted membership actually exists: [5](#0-4) 

`User.find_or_create_by_login!` only fetches public profile info for the given login (no ownership or authorization proof) and `Team#add_member` unconditionally appends the membership: [6](#0-5) [7](#0-6) 

Authorization to use Shipit is gated solely on team membership recorded in the database: [8](#0-7) 

**Binding broken:** `organization that authenticated the webhook` (supposed to equal "GitHub actually sent this, for this org") **≠** `organization/team membership actually written and later trusted for authorization`. When `webhook_secret` is unset — a state the project itself documents as a supported, optional configuration — the "authenticated organization" side of that equation is vacuous (`verify_webhook_signature` always returns `true`), yet the engine still treats the payload as GitHub-truth and mutates the authorization-relevant `Membership` table.

### Impact Explanation
An attacker who completes a normal, real GitHub OAuth login (any GitHub account, no special privilege) can additionally POST a forged `membership` webhook naming their own login as `added` to a `Shipit::Team` whose `handle` matches one of `Shipit.github_teams`. Because `User#authorized?` only checks the local `teams` association, this grants the attacker full authorized access to Shipit — i.e., escalation into `Shipit.github_teams` authorization, and from there, the ability to trigger deploys/rollbacks on stacks gated by that authorization. This matches the explicitly allowed High-severity impact category ("escalation into `Shipit.github_teams` authorization") and can chain to the Critical category ("unauthorized deploy, rollback").

### Likelihood Explanation
Likelihood is contingent on the operator leaving `webhook_secret` unset, which the shipped setup documentation presents as an optional field ("Webhook secret (optional)"), not a hardened default. Any deployment following the literal documentation without additionally setting a secret is exposed, and the attack requires no credentials, tokens, or special network position — only knowledge of a valid organization name (public) and a team handle configured in `Shipit.github_teams` (often discoverable/guessable, e.g., "org/developers"). This is a plausible, low-effort, unprivileged path.

### Recommendation
1. Make `webhook_secret` mandatory (fail application boot / reject all webhook processing) rather than allowing signature verification to silently pass when unset.
2. For `membership` events, do not trust the payload as sole source of truth for granting `Shipit.github_teams` authorization — corroborate with a live GitHub API check (e.g., confirm the asserted member is actually on the org's team) before creating/deleting `Membership` rows, or at minimum re-validate team membership periodically via `Team#refresh_members!` rather than trusting incremental webhook deltas alone.
3. Update `docs/setup.md` to state that omitting `webhook_secret` disables all webhook authenticity checks and is unsafe for any environment where `Shipit.github_teams` gates access.

### Proof of Concept
1. Deploy Shipit per `docs/setup.md` without setting `webhook_secret` (a documented, valid "optional" configuration).
2. Attacker (any GitHub user) completes normal OAuth login to Shipit; `authorized?` currently returns false since they aren't on an authorized team.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and no/garbage `X-Hub-Signature`, body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "shopify" },
  "member": { "login": "attacker-login" }
}
```
4. `verify_signature` calls `Shipit.github(organization: "shopify").verify_webhook_signature(...)`, which returns `true` because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`).
5. `MembershipHandler#process` runs, creating/finding `Team(organization: "shopify", ...)` and calling `team.add_member(User.find_or_create_by_login!("attacker-login"))` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`).
6. If that team's handle is in `Shipit.github_teams`, the attacker's next request to any Shipit page passes `current_user.authorized?` (`app/models/shipit/user.rb:80-82`), granting full application access despite never actually being a GitHub team member.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
