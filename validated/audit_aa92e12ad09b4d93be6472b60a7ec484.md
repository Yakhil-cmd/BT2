### Title
`collect_creator_fee` / `collect_creator_fee_permissionless` permanently revert (and freeze accrued fees) if the pool creator's token account becomes frozen/blacklisted - (File: `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
Both creator-fee-collection instructions always route the collected `creator_fees_token_0`/`creator_fees_token_1` to the ATA of the immutable `pool_state.pool_creator` address. If that account (or its underlying mint, e.g. a Token-2022 mint with freeze authority / permanent delegate) is or becomes frozen/blacklisted, the SPL transfer inside these instructions will always revert, and — unlike the Cooler analog where the lender could rotate their address — there is no instruction anywhere in the program to update `pool_creator`, so the accrued creator fees become permanently unclaimable.

### Finding Description
`PoolState.pool_creator` is set once at pool initialization and is never mutated afterwards [1](#0-0) . Both fee-collection paths derive the destination token accounts as the creator's own associated token accounts and unconditionally transfer the full accrued `creator_fees_token_0`/`creator_fees_token_1` there:

- `CollectCreatorFee` requires the creator to sign and sends to `creator_token_0`/`creator_token_1`, ATAs owned by `creator` [2](#0-1) , then performs the transfer via `transfer_from_pool_vault_to_user` [3](#0-2) .
- `CollectCreatorFeePermissionless` allows anyone to trigger collection, but the destination is still fixed as the ATA of the same `pool_state.pool_creator` [4](#0-3) , with the identical transfer call [5](#0-4) .

Because `pool_creator` cannot be changed and both entry points always target that same fixed recipient, if the recipient's associated token account is frozen (Token-2022 freeze authority action, or blacklist enforced via a permanent delegate / transfer hook on the mint), the token transfer instruction will unconditionally fail with every call, exactly mirroring the root cause in the reported Cooler issue (`repayTo` forced to a single, non-updatable address). This is the same bug class: forcing a token transfer to a party whose account/authority can independently freeze, with no fallback recipient and no way to reroute funds.

### Impact Explanation
`creator_fees_token_0`/`creator_fees_token_1` are tracked inside `PoolState` and subtracted from the vault balance available to LPs via `vault_amount_without_fee` [6](#0-5) , meaning these tokens are held in the pool vaults but permanently earmarked for the creator. If the creator's account is frozen, this earmarked balance becomes permanently locked inside the vault with no code path to ever release it — it is not simply the creator "losing access" but tokens that are stuck in program-owned vaults forever, since collection can only ever target that one recipient.

### Likelihood Explanation
This requires either token_0 or token_1 to be a mint type where accounts can be frozen or blacklisted post-creation (e.g., Token-2022 mints with a freeze authority, or with a permanent-delegate/transfer-hook extension enforcing a blacklist) and the specific creator's account being frozen. This is plausible given the program explicitly supports Token-2022 (`token_0_program`/`token_1_program`, `Token2022` usages throughout `collect_fund_fee.rs`, `collect_protocol_fee.rs`, `collect_creator_fee*.rs`).

### Recommendation
Allow the pool creator to designate/rotate a receiving token account (or add an admin/creator-controlled path to redirect creator fees to a different address) instead of hardcoding the ATA derived from the immutable `pool_state.pool_creator`, similar to the recommendation for the Cooler issue (never force transfers to a single unchangeable, potentially-frozen address).

### Proof of Concept
1. Initialize a pool where `token_0_mint` is a Token-2022 mint with a freeze authority (or permanent delegate extension used for blacklisting).
2. Perform swaps so `creator_fees_token_0` accrues in `pool_state`.
3. Freeze the creator's associated token account for `token_0_mint` (or blacklist the creator address via the mint's extension).
4. Call `collect_creator_fee` or `collect_creator_fee_permissionless` — the `transfer_from_pool_vault_to_user` call to `creator_token_0` reverts every time, and since `pool_creator` can never be updated, the accrued `creator_fees_token_0` remains permanently stuck in `token_0_vault`.

    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
