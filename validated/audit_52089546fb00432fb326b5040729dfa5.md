### Title
Cross-organization webhook auth bypass allows attacker-org to control victim-org's ReviewStack lifecycle via `repository.owner.login`/`repository.full_name` mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives which org's `webhook_secret` to validate a webhook against solely from `params.dig('repository','owner','login')` (or the fallback `organization.login`), while the actual repository/stack acted upon downstream is resolved from the independent field `params.repository.full_name`. Because these two attacker-controlled JSON fields are never checked for consistency, an attacker who owns/administers their own org's Shipit GitHub App (and thus knows that org's `webhook_secret`) can forge a `pull_request` `labeled`/`unlabeled` webhook whose `repository.owner.login` is set to their own org (passing signature verification) but whose `repository.full_name` names a victim org's repository, causing `ReviewStackAdapter#archive!`/`unarchive!` to repeatedly mutate the victim's `Stack` (deprovision/reprovision via `Shipit::ReviewStackProvisioningQueue.add`).

### Finding Description
The claimed binding is: `organization authenticating call N == Stack.repository.owner`. Tracing the code shows this binding is never actually established:

- `verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and looks up `Shipit.github(organization: repository_owner)` to fetch that org's `GitHubApp#verify_webhook_signature`: [1](#0-0) [2](#0-1) 
- The webhook body is raw JSON parsed from `request.raw_post`, fully attacker-controlled, and dispatched to handlers without any cross-field validation: [3](#0-2) 
- `LabeledHandler`/`UnlabeledHandler`'s `ExplicitParameters` schema only requires `repository.full_name`; it never requires or validates `repository.owner.login`, so nothing forces the two fields to agree: [4](#0-3) 
- The handler resolves the target `Repository` (and thus the `Stack`) purely from `params.repository.full_name` via `Repository.from_github_repo_name`, independent of whichever org's secret authenticated the request: [5](#0-4) [6](#0-5) 
- `ReviewStackAdapter#archive!`/`unarchive!` act on `stack` (found via `scope.find_by(environment:)`, scope being `repository.review_stacks`) with no re-check of which org authenticated the call: [7](#0-6) 
- Shipit explicitly supports multiple independently-configured GitHub Apps/orgs, each with its own `webhook_secret`, confirming this multi-tenant scenario is a supported deployment: [8](#0-7) [9](#0-8) 

Attacker request: a `pull_request` webhook (`X-Github-Event: pull_request`, action `labeled` or `unlabeled`) with body `{"action":"labeled","repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},...}`, signed with `X-Hub-Signature` computed using `attacker-org`'s own known `webhook_secret`. `verify_signature` looks up `attacker-org`'s config and successfully verifies the signature (since the attacker knows their own secret), then the handler resolves and mutates `victim-org/victim-repo`'s `Stack`.

Regarding `stack_attributes`: it unconditionally hardcodes `ignore_ci: false, continuous_deployment: false` and never derives these from any authenticated approval, so that specific sub-claim is not itself exploitable — the real defect is the org-identity/repository mismatch enabling repeated `archive!`/`unarchive!` cycles on an arbitrary victim `Stack`. [10](#0-9) 

Existing guards do not close this gap: `verify_signature` only proves the payload was signed by *some* configured org's secret, not that it's authorized for the specific repository named inside the payload; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence, not owner/full_name consistency; and `ReviewStackAdapter` has no knowledge of, or means to check, which org's secret authenticated the request.

### Impact Explanation
An attacker who controls only their own org's GitHub App/webhook_secret can repeatedly `archive!`/`unarchive!` (deprovision/reprovision) a victim org's `ReviewStack`, driving it through `Shipit::ReviewStackProvisioningQueue.add`/`remove_from_provisioning_queue` and `deprovision`/provisioning cycles, and creating a fake `PullRequest` record attributed to an arbitrary `sender.login` on the victim's stack (`ReviewStackAdapter#create!`). This is a cross-tenant write: a payload authenticated under one org mutates another org's `Stack`/`PullRequest` records and triggers real infrastructure provisioning/deprovisioning actions — matching the Critical category "a payload for one repository mutating another's stack."

### Likelihood Explanation
Requires: (1) the victim repo has `review_stacks_enabled` and `provisioning_behavior_allow_with_label` (or `prevent_with_label`) configured; (2) the Shipit instance hosts multiple GitHub orgs/apps (the documented multi-org config), one of which the attacker legitimately owns/administers and thus knows its `webhook_secret`. Given those preconditions — both plausible in any multi-tenant Shipit deployment — the attack is trivial and free: send arbitrary `labeled`/`unlabeled` JSON payloads over HTTP with a valid HMAC computed from a secret the attacker already possesses, repeatable indefinitely against any victim repo/PR whose `full_name` is known.

### Recommendation
In `WebhooksController`, after successfully verifying the signature for `repository_owner`, additionally require that `repository.full_name`'s owner segment matches `repository_owner` (or, more robustly, resolve the target `Repository`/org from the DB first and verify the signature against that specific repository's own configured org, rejecting any request where the two disagree). Also enforce this invariant in `ReviewStackAdapter`/`Handler` by validating `params.repository.full_name.split('/').first.casecmp(authenticated_organization) == 0` before any `archive!`/`unarchive!`/`create!` mutation.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative)
test "labeled webhook authenticated by attacker-org secret can archive victim-org stack" do
  victim_repo = shipit_repositories(:victim) # owner: "victim-org", review_stacks_enabled: true, provisioning_behavior: allow_with_label
  stack = create_review_stack(repository: victim_repo, environment: "pr1", archived_since: nil)

  payload = {
    action: "labeled",
    number: 1,
    pull_request: { id: 1, number: 1, url: "u", title: "t", state: "open",
                     additions: 1, deletions: 1,
                     head: { sha: "s", ref: "branch" },
                     user: { login: "attacker" },
                     assignees: [], labels: [] }, # no provisioning label -> archive? true
    repository: { owner: { login: "attacker-org" }, full_name: "victim-org/victim-repo" },
    sender: { login: "attacker" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", ATTACKER_ORG_WEBHOOK_SECRET, payload)

  post "/webhooks", params: payload, headers: {
    "X-Github-Event" => "pull_request",
    "X-Hub-Signature" => signature,
    "Content-Type" => "application/json"
  }

  assert_response :ok
  assert stack.reload.archived? # victim stack mutated using attacker-org's own secret
end
```
Assert both sides of the binding: `authenticated_org = "attacker-org"` vs `stack.repository.owner = "victim-org"` — they differ, yet the mutation still succeeds, proving the vulnerability.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
