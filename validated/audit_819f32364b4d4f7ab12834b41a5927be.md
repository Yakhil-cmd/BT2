### Title
Webhook signature is bound to `repository.owner.login`, not to the repository acted upon, allowing cross-organization forged webhooks in multi-tenant Shipit deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to authenticate an inbound webhook from the attacker-controlled JSON field `repository.owner.login` (or `organization.login`), but the handlers that actually act on the payload key off a *different* attacker-controlled field, `repository.full_name`, without ever cross-checking the two. In a Shipit instance configured for multiple GitHub organizations, this breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` computes which org's secret to use like this: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up per-organization config (`app_id`, `webhook_secret`, etc.) from `secrets.github`, which is explicitly documented to support multiple independently-trusted GitHub organizations sharing one Shipit instance: [3](#0-2) [4](#0-3) 

Once the signature check passes (using the secret belonging to the organization named in `repository.owner.login`), the raw JSON body is dispatched unmodified to event handlers: [5](#0-4) 

Handlers resolve the target `Stack`/`Repository` from a completely different field, `repository.full_name`: [6](#0-5) 

and `Repository.from_github_repo_name` performs a bare DB lookup on `owner`/`name` columns with no relation back to which GitHub App/org authenticated the request: [7](#0-6) 

Nothing in `WebhooksController`, `Handler`, or `Repository` asserts that `repository.owner.login` (used for signature verification) equals the owner segment of `repository.full_name` (used to select the target Stack). Since HMAC verification only proves the whole raw body was signed by *some* known organization's secret — not that the body's `repository.full_name` matches that organization — an attacker who administers the GitHub App/webhook for Org A (and thus legitimately possesses Org A's `webhook_secret`, as documented in `docs/setup.md`) can compute a valid `X-Hub-Signature` over a forged body where `repository.owner.login: "OrgA"` (to pass the check) but `repository.full_name: "OrgB/victim-repo"` (to select a stack belonging to an unrelated tenant, Org B, hosted by the same Shipit instance).

Downstream handlers act purely on `repository.full_name`, e.g.:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` on every non-archived stack of the resolved repository: [8](#0-7) 
- `PullRequest::ClosedHandler` archives review stacks of the resolved repository: [9](#0-8) 

Both derive their target strictly from `params.repository.full_name`, which the org-A-scoped signature never constrains.

### Impact Explanation
This is a cross-tenant / cross-repository trust-boundary break: possession of one organization's legitimate webhook credential lets an attacker inject arbitrary, validly-"signed" GitHub events that are attributed to and acted upon for a different organization's repositories/stacks hosted on the same Shipit instance. Depending on which handler is triggered this can force spurious commit syncs (`GithubSyncJob` → `CacheDeploySpecJob`), archive review stacks belonging to Org B, or manipulate PR-driven review-stack lifecycle state for repositories the attacker has no access to — a cross-repository write not gated by any authorization the target organization controls. This matches the Critical "cross-repository writes" category, since the write path (`Stack`/`ReviewStack` mutation) is fully reachable with only a foreign organization's own webhook secret and no credential belonging to the victim organization.

### Likelihood Explanation
Requires only that the Shipit deployment be configured in the documented multi-organization mode and that the attacker administers (or otherwise legitimately holds the webhook secret for) at least one onboarded, lower-trust organization — a normal, unprivileged position relative to any other tenant on the same instance. No access to the victim org's secret, GitHub App, or Shipit session is needed; the attacker only needs to know another tenant repository's `owner/name` in Shipit, information that is often public.

### Recommendation
In `WebhooksController#verify_signature` / `#repository_owner`, cross-validate that the organization whose `webhook_secret` verified the signature matches the owner segment of every `repository.full_name` (and `organization.login`) referenced by the payload before dispatching to handlers; reject the request otherwise. Alternatively, resolve the target `Repository`/`Stack` using the authenticated organization as an additional lookup constraint (e.g., `Repository.from_github_repo_name` scoped to `owner: repository_owner`) rather than trusting `full_name` alone.

### Proof of Concept
1. Shipit is configured with two organizations in `secrets.yml`: `orga` (attacker-administered, webhook secret known to attacker) and `orgb` (victim, has stack `orgb/victim-repo`).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(orga_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orga")` and verifies successfully using `orga`'s secret [1](#0-0) .
5. `PushHandler` resolves `Repository.from_github_repo_name("orgb/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack [8](#0-7) , even though the signature never involved `orgb`'s credentials.

    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
