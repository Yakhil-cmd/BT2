### Title
Fee-on-Transfer ERC20 Token Causes Bridge Reserve Drain via Inflated `RequestValueTransfer` Amount — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

The Kaia service-chain bridge's `requestERC20Transfer` and the 1-step `ERC20ServiceChain.requestValueTransfer` path both assume that `safeTransferFrom` / `transfer` delivers exactly the requested number of tokens to the bridge contract. When a fee-on-transfer (deflationary) ERC20 is registered, the bridge receives fewer tokens than `_value + _feeLimit`, yet emits `RequestValueTransfer` with the full `_value`. The counterpart bridge's `handleERC20Transfer` then releases the full `_value` to the recipient. Repeated over many transfers, the destination bridge's token reserves are drained faster than the source bridge accumulates them, eventually making withdrawals impossible.

---

### Finding Description

**2-step path — `requestERC20Transfer`:**

```solidity
// BridgeTransferERC20.sol L133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

With a fee-on-transfer token at rate `r`, the bridge receives `(_value + _feeLimit) × (1 − r)` instead of `_value + _feeLimit`. [1](#0-0) 

`_requestERC20Transfer` then calls `_payERC20FeeAndRefundChange`, which issues additional `safeTransfer` calls (to `feeReceiver` and back to `from`) — each of which also incurs the token's transfer fee, further reducing the bridge's actual balance. [2](#0-1) 

Despite the shortfall, `_requestERC20Transfer` emits `RequestValueTransfer` with the original `_value`:

```solidity
// BridgeTransferERC20.sol L97-107
emit RequestValueTransfer(
    TokenType.ERC20,
    _from, _to, _tokenAddress,
    _value,          // ← full amount, not what was actually received
    requestNonce, fee, _extraData
);
``` [3](#0-2) 

**1-step path — `ERC20ServiceChain.requestValueTransfer`:**

```solidity
// ERC20ServiceChain.sol L44-47
function requestValueTransfer(uint256 _amount, address _to, uint256 _feeLimit, bytes calldata _extraData) external {
    require(transfer(bridge, _amount.add(_feeLimit)), "requestValueTransfer: transfer failed");
    IERC20BridgeReceiver(bridge).onERC20Received(msg.sender, _to, _amount, _feeLimit, _extraData);
}
```

`transfer` delivers `(_amount + _feeLimit) × (1 − r)` to the bridge, but `onERC20Received` is called with the original `_amount`, which flows unchanged into `_requestERC20Transfer` and the emitted event. [4](#0-3) 

**Counterpart bridge settlement:**

The off-chain bridge manager reads `valueOrTokenId` directly from the `RequestValueTransfer` event and calls `HandleERC20Transfer` with that full value:

```go
// bridge_manager.go L338-343
case ERC20:
    handleTx, err = bi.bridge.HandleERC20Transfer(
        auth, txHash, from, to, ctpartTokenAddr,
        valueOrTokenId,   // ← the inflated _value from the event
        requestNonce, blkNumber, extraData)
``` [5](#0-4) 

`handleERC20Transfer` on the destination bridge then releases exactly `_value` tokens (or mints them in mintBurn mode):

```solidity
// BridgeTransferERC20.sol L71
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [6](#0-5) 

---

### Impact Explanation

**Lock mode (non-mintBurn):** Per transfer of `_value` with fee rate `r` and `_feeLimit`:

- Source bridge locks: `(_value + _feeLimit) × (1 − r) − _feeLimit` (net, after fee-refund outflows)
- Destination bridge releases: `_value`
- Per-transfer shortfall: `(_value + _feeLimit) × r`

After `N` transfers the destination bridge is short `N × (_value + _feeLimit) × r` tokens. When the deficit exceeds the bridge's reserve, all subsequent `handleERC20Transfer` calls revert, permanently freezing withdrawals for all users who have already locked tokens on the source side — an unauthorized drain of bridged assets.

**MintBurn mode:** The source bridge burns `_value` tokens (line 94), but only received `(_value + _feeLimit) × (1 − r)`. If `(_value + _feeLimit) × (1 − r) < _value`, the burn call will revert (insufficient balance), causing the entire request to fail. If the token's fee is small enough that the bridge holds enough to burn, the destination mints the full `_value`, inflating supply relative to what was destroyed. [7](#0-6) 

---

### Likelihood Explanation

Any user can call `requestERC20Transfer` or `ERC20ServiceChain.requestValueTransfer` with a registered fee-on-transfer token. No special role is required. The trigger is a normal, unprivileged bridge deposit. The only prerequisite is that a fee-on-transfer token has been registered by the bridge owner — a realistic scenario given that many real-world ERC20 tokens (e.g., tokens with configurable transfer fees) can be registered without any on-chain validation of their transfer semantics. There is no guard in `registerToken` or `_requestERC20Transfer` that checks for fee-on-transfer behavior. [8](#0-7) 

---

### Recommendation

1. **Measure actual received amount:** In `requestERC20Transfer`, record the bridge's token balance before and after `safeTransferFrom`, and use the delta as the canonical locked amount:

```solidity
uint256 before = IERC20(_tokenAddress).balanceOf(address(this));
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(before);
require(actualReceived >= _value, "fee-on-transfer token: insufficient received");
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, actualReceived.sub(_value), _extraData);
```

2. **Token registration validation:** Add a check during `registerToken` that performs a test transfer and verifies the received amount equals the sent amount, rejecting fee-on-transfer tokens.

3. **Documentation:** Clearly document that fee-on-transfer and rebasing ERC20 tokens are not supported by the bridge.

---

### Proof of Concept

**Setup:** Deploy a fee-on-transfer ERC20 token with a 1% transfer fee. Register it on both the parent and child bridges in lock mode.

**Steps:**

1. Alice approves the parent bridge for `1000 + 100` (value + feeLimit) tokens.
2. Alice calls `requestERC20Transfer(tokenAddr, bob, 1000, 100, "0x")`.
3. `safeTransferFrom` is called for `1100` tokens. Due to the 1% fee, the bridge receives `1100 × 0.99 = 1089` tokens.
4. `_payERC20FeeAndRefundChange` transfers `fee` to feeReceiver (bridge sends `fee`, feeReceiver gets `fee × 0.99`) and refunds `feeRefund` to Alice (bridge sends `feeRefund`, Alice gets `feeRefund × 0.99`). Bridge net balance after: `1089 − fee − feeRefund = 1089 − 100 = 989` tokens locked for `_value = 1000`.
5. `RequestValueTransfer` event emits `valueOrTokenId = 1000`.
6. The off-chain bridge manager reads the event and calls `handleERC20Transfer` on the child bridge with `_value = 1000`.
7. Child bridge transfers `1000` tokens to Bob.

**Result:** Source bridge locked `989` tokens; destination bridge released `1000` tokens. Shortfall of `11` tokens per transfer. After ~90 such transfers, the destination bridge's reserve is fully drained, and all subsequent withdrawals revert. [9](#0-8) [2](#0-1) [4](#0-3) [5](#0-4)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
```
