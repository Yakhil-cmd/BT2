Confirmed: `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb`) does not use the `stacks`/`repository_name` scoping helper that `Handler` provides (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, which scopes lookups via `Repository.from_github_repo_name(repository_name)`). Instead it looks up commits globally: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) . Meanwhile signature verification in `WebhooksController#verify_signature` only checks that the payload's `repository.owner.login`/`organization.login` matches a known, authenticated GitHub organization — it says nothing about which specific repository/stack is written to [2](#0-1) .

### Title
Cross-repository/cross-organization CI status forgery via unscoped `StatusHandler` commit lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` updates commit CI status for every `Commit` row matching a raw `sha`, with no repository/organization scoping, even though the webhook signature that authorized the request only proves the sender controls the GitHub App/secret for one organization.

### Finding Description
The equality that should hold is: `organization authenticated via HMAC signature == organization/repository whose commit status is written`. `WebhooksController#verify_signature` resolves the GitHub App/secret purely from `repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`) [3](#0-2) , and once `Shipit.github(organization: repository_owner).verify_webhook_signature` returns true, the entire JSON `params` (not just the verified organization/repository fields) is dispatched to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .

Other handlers (e.g. `PushHandler`) correctly re-derive the target `stacks` from `Repository.from_github_repo_name(repository_name)` via the base `Handler#stacks`/`#repository_name` helpers, which key off `payload.dig('repository', 'full_name')` [5](#0-4) [6](#0-5) . `StatusHandler`, however, never calls `stacks`/`repository_name` at all — it only requires `sha`/`state`/etc. as parameters and matches commits globally: `Commit.where(sha: params.sha)` [7](#0-6) . This means the signature check binds "which organization sent this webhook," but the write binds to "any commit row in the entire Shipit database whose SHA matches," across every organization/repository/stack. This is the analog of the Nouns Builder bug: two values (`totalSupply` incremented vs. burned-token accounting) that are supposed to move in lockstep silently diverge — here, "authenticated organization" and "repository actually written" diverge because the handler drops the scoping that other handlers correctly apply.

### Impact Explanation
Any actor who can produce a validly-signed `status` webhook for *some* organization/repository configured in this Shipit instance (i.e., one where they legitimately administer a GitHub App/webhook, or where the org's webhook secret has otherwise been provisioned to them, which is a normal, unprivileged setup step for that org's own repo — not a privileged Shipit credential) can inject a forged commit status (e.g., `state: success`) for any `Commit` row in any *other* organization's stack, as long as the SHA values collide. SHA collisions across repositories are not exotic: forks, mirrors, vendored/synced repos, and monorepo splits routinely share identical commit SHAs for shared history. `Commit#deployable?` and `Commit#blocked?` gate deploy/merge eligibility on `status`/`blocking_statuses` derived from these forged status rows [8](#0-7) , and `add_status` triggers `stack.schedule_merges` and continuous delivery scheduling once a commit becomes `success` [9](#0-8) . This can let an attacker who is unprivileged with respect to the victim organization/stack force a required-CI check to appear green on a victim's commit, enabling an unauthorized deploy or merge in a stack they do not control — satisfying the "unauthorized deploy/merge" Critical-impact bar.

### Likelihood Explanation
Requires the attacker to control a legitimately signed webhook channel for at least one organization/repository hosted on the same Shipit instance (a realistic, unprivileged-with-respect-to-the-victim scenario for any multi-tenant Shipit deployment), plus a SHA collision with a commit tracked in the victim's stack (realistic for forks/mirrors sharing history, or via engineered collision if the attacker can also push identical commits to their own repo). No access to the victim's webhook secret, API tokens, or Shipit session is required — only the divergence between the signature-verification scope and the unscoped `Commit.where(sha:)` lookup in `StatusHandler`.

### Recommendation
Have `StatusHandler` scope its commit lookup the same way `PushHandler` does: resolve the target stack(s) via `Repository.from_github_repo_name(repository_name)` / the base `Handler#stacks` helper and filter `Commit.where(sha: params.sha, stack: stacks)` (or equivalent) so a status update can only ever be applied to commits belonging to the repository whose signature was actually verified.

### Proof of Concept
1. Configure two organizations/repos in the same Shipit instance: `org-a/repo-a` (attacker-administered, webhook secret known to attacker) and `org-b/repo-b` (victim), where `repo-b` is a fork of/shares history with `repo-a`, so both track a commit with SHA `abcdef123...`.
2. Attacker computes a valid `X-Hub-Signature` for `org-a`'s webhook secret over a `status` event payload: `{"sha": "abcdef123...", "state": "success", "repository": {"owner": {"login": "org-a"}}}`.
3. `WebhooksController#verify_signature` resolves `repository_owner` as `org-a`, fetches `Shipit.github(organization: 'org-a')`, and the signature verifies successfully [10](#0-9) .
4. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: 'abcdef123...').each { |commit| commit.create_status_from_github!(params) }`, updating the status of the commit in `org-b/repo-b`'s stack even though the signature only proved control of `org-a` [1](#0-0) .
5. The forged `success` status can now satisfy `Commit#deployable?`/CI requirements in `org-b`'s stack, potentially enabling an unauthorized deploy/merge there.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
