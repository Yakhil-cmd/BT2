### Title
`provision?` operator-precedence bug bypasses `repository.review_stacks_enabled`, allowing unreviewed `shipit.yml` step execution via review-stack provisioning - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`PullRequest::OpenedHandler#provision?` combines `review_stacks_enabled` with three provisioning-behavior checks using `&&`/`||` without parentheses, so Ruby operator precedence only gates the `allow_all` branch and not the `allow_with_label`/`prevent_with_label` branches. If a repository has `review_stacks_enabled == false` but `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, an attacker who can open a PR and add/omit a label on their own fork can still trigger `ReviewStackAdapter#create!` → `ReviewStackProvisioningQueue.add` → provisioning, which will eventually run the deploy/review_checks steps of the PR branch's `shipit.yml` unreviewed by any Shipit operator.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == false` implies `provision? == false` for all provisioning behaviors, i.e. `review_stacks_enabled` gates the entire provisioning decision, not just one branch of it.

The actual code is: [1](#0-0) 

Due to Ruby precedence (`&&` binds tighter than `||`), this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So when `review_stacks_enabled` is `false` but `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, the first clause is `false`, but the second or third clause can still independently evaluate to `true`, making `provision?` return `true` and bypassing the intended global disable flag.

Both settings are set by an authenticated repository operator through `RepositoriesController#update_params`, which permits `:review_stacks_enabled` and `:provisioning_behavior` independently: [2](#0-1) 

This means an operator can toggle `review_stacks_enabled` off (e.g., to disable the feature, perhaps in response to abuse) while `provisioning_behavior` remains `allow_with_label` or `prevent_with_label` from a prior configuration — these are two independent form fields, and unchecking one does not reset the other. Once that state exists, any unprivileged GitHub user who can open a pull request against the repository and add (or omit) a label on their own PR fully controls the outcome of `provision?`, causing `OpenedHandler#process` to call `ReviewStackAdapter#find_or_create!`, which creates the `ReviewStack` and enqueues it for provisioning: [3](#0-2) 

From there, provisioning proceeds through the standard review-stack task pipeline, which reads `deploy`/`review_checks` steps from the PR branch's `shipit.yml` via `DeploySpec::FileSystem#load_config` and executes them via `Command`/`PTY.spawn` — the same execution path used for any legitimately enabled review stack, with no additional operator review step in between. None of the existing guards (`verify_signature`, `ExplicitParameters`, `require_permission!`) apply here because this is not an authentication bypass on the webhook itself — the webhook signature and payload schema are valid — the flaw is purely in the authorization *decision* (`provision?`) made after the webhook is authenticated.

### Impact Explanation
Once triggered, the review stack executes attacker-influenced `shipit.yml` `deploy`/`review_checks` steps on the deploy host via `Command`/`PTY.spawn`, with the process's `GITHUB_TOKEN` and other deploy-time environment variables available to the spawned process. This is Critical: arbitrary command execution on the deploy host, achievable by any unprivileged contributor who can open a PR, contingent on the repository being in the specific misconfigured state (`review_stacks_enabled: false` + `provisioning_behavior` set to a label-based mode). The blast radius is scoped to that repository's deploy host/credentials, not other tenants' stacks, since `provision?` and `repository` resolution are scoped to the PR's own repository via `Repository.from_github_repo_name`.

### Likelihood Explanation
Exploitation requires a specific, non-default repository configuration: `review_stacks_enabled == false` combined with `provisioning_behavior` in (`allow_with_label`, `prevent_with_label`). This is a plausible real-world sequence (operator initially enables review stacks with label-gated behavior, then later unchecks "enabled" without resetting the behavior dropdown), but it is not the default state and is not attacker-controlled — it depends on an operator's prior/independent configuration choices. Given that precondition, the attacker's cost is trivial (open a PR, add/remove a label) and fully repeatable against that repository.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three behaviors:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style, illustrative only — not part of this analysis's deliverable since `test/**` is out of scope for changes but valid as a proof structure):
1. Build a `Repository` with `review_stacks_enabled: false`, `provisioning_behavior: "allow_with_label"`, `provisioning_label_name: "preview"`.
2. Construct `OpenedHandler` params for a PR with `action: "opened"` and a label named `"preview"`.
3. Assert binding before fix: `repository.review_stacks_enabled == false` yet `handler.send(:provision?) == true`.
4. Assert `Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter#find_or_create!` is invoked and a `ReviewStack` record is created/enqueued via `ReviewStackProvisioningQueue.add`.
5. After applying the parenthesization fix, re-run and assert `provision? == false` and no `ReviewStack` is created, confirming the binding `review_stacks_enabled == false ⇒ provision? == false` now holds for all `provisioning_behavior` values.
