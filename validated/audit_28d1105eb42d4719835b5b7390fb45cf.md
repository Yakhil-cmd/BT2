`StatusHandler#process` matches `params.sha` against **all** `Commit` rows with no repository/stack scoping, letting any repository's status webhook mutate another repository's commit statuses - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` without ever resolving or checking `payload.dig('repository', 'full_name')` against a real `Shipit::Repository`. Every other handler in this engine (`PushHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler`) goes through the base class's `stacks` method, which resolves `Repository.from_github_repo_name(repository_name)` first and returns `Stack.none` if the repo is unknown, so an unresolvable/unrelated repository name safely short-circuits to no-op. `StatusHandler` skips this resolution entirely, so a status webhook naming an arbitrary/nonexistent `repository.full_name` still writes a `Status` on any pre-existing `Commit` whose `sha` matches, purely via handler logic, independent of HTTP signature verification.

### Finding Description
Broken binding, stated as an equality that should hold but doesn't:
`repository_name_from_payload` (i.e., `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) should equal `commit.stack.repository` for every `Commit` that `create_status_from_github!` is applied to — enforced by `stacks` in the base `Handler` — but `StatusHandler` never calls `stacks`/`repository_name` at all.

Code path:
- `app/models/shipit/webhooks/handlers/handler.rb:32-38` defines `stacks` (`Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`) and `repository_name` (`payload.dig('repository', 'full_name')`), intended as the repository-scoping guard for subclasses. [1](#0-0) 
- `PushHandler#process` and `CheckSuiteHandler#process` both scope their DB writes through `stacks`, so an unrelated/unknown `repository.full_name` yields `Stack.none` and is a safe no-op. [2](#0-1) [3](#0-2) 
- `StatusHandler#process` instead does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, an unscoped, global query across the whole `Commit` table, with no repository resolution. [4](#0-3) 
- `Commit#create_status_from_github!` writes a real `Status` row and triggers `Hook.emit(:commit_status, ...)`/`Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` based on state transitions — real business-logic side effects on the commit's actual stack, regardless of what repository name the webhook claimed. [5](#0-4) [6](#0-5) 

`Handler.call`/`Handler#initialize` only validates the shape of the payload via `ExplicitParameters` (`sha`, `state`, etc.), not the repository's resolvability, so a payload with `repository.full_name => 'totally/unrelated'` passes parameter validation fine and reaches `process`. [7](#0-6) 

Since `sha` is a global, non-namespaced column on `Commit` (`Commit.where(sha: ...)` has no `stack_id` filter), any repository can submit a `status` webhook whose `sha` collides with a commit that legitimately belongs to a completely different tracked repository/stack, and the handler will write a status onto that unrelated commit. This is reachable purely by calling `StatusHandler.call(payload_hash)` — no signature or HTTP layer participates in this defect, confirming the vulnerability is entirely inside handler business logic. `verify_signature`/`GithubApp#verify_webhook_signature` only gates whether the webhook request reaches `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `WebhooksController#create`; it does not, and cannot, validate that `repository.full_name` in the payload matches the repository whose secret was used, nor does it constrain which commits `StatusHandler` may touch once invoked. [8](#0-7) 

### Impact Explanation
An attacker who controls a repository/organization that Shipit is configured to receive webhooks from (i.e., has a valid `webhook_secret` for *some* GitHub App/org registered in `Shipit.github_teams`/`Shipit.github`) can craft a `status` event payload with a real `sha` shared with, or guessed for, a commit belonging to a different tracked repository/stack, and have `StatusHandler` write a `Status` (e.g., `state: 'success'`) onto that unrelated stack's commit. Because `Commit#create_status_from_github!` triggers `stack.schedule_merges` on success/pending transitions and `Hook.emit(:deployable_status, ...)`, this can make an unrelated stack's commit appear "green"/deployable, potentially triggering a continuous-deployment merge or deploy for a stack the attacker does not own — this is a cross-tenant integrity violation matching "a payload for one repository mutating another's stack/commit" (Critical). The blast radius covers every tracked `Stack`/`Repository` on the Shipit instance that shares SHA space with the attacker's payload (SHA collision likelihood is a separate concern — the code path is unconditional regardless of collision probability).

### Likelihood Explanation
Preconditions: the attacker needs a webhook-signature-valid channel into the `status` event pipeline (i.e., control of a repository/org already registered with Shipit, so `verify_signature` passes for their own org) — this is within the stated attacker model ("any internet user who can send HTTP requests... including POST /webhooks" combined with "GitHub user who can... emit webhooks from a repository they own"). Once past `verify_signature` (which validates only that the signature matches *some* configured org, not that the claimed repository is legitimate or related to the target commit), reaching the vulnerable code requires no further privilege — `repository.full_name` is taken from the payload verbatim and never checked for resolvability. The exploit is directly and repeatably demonstrable purely at the Ruby layer, as posed in the question, with zero network/signature machinery: `StatusHandler.call('sha' => commit.sha, 'state' => 'success', 'repository' => {'full_name' => 'totally/unrelated'})`.

### Recommendation
Scope `StatusHandler#process` through the base class's repository-resolution helper, mirroring `PushHandler`/`CheckSuiteHandler`, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or more efficiently, join through `Stack`/`Repository` (`Commit.joins(:stack).merge(stacks).where(sha: params.sha)`), ensuring `repository_name` resolves to a real `Shipit::Repository` before any `Commit` row is touched, so an unresolvable or mismatched `repository.full_name` is a safe no-op just like in every other handler.
