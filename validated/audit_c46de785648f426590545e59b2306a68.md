## Analysis Result



### Title
`ProxyType::NonTransfer` fails open on Asset Hub Rococo, letting a `NonTransfer` proxy delegate move the real account's assets - (File: `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/lib.rs`)

### Summary
`ProxyType::NonTransfer` is documented and intended to permit "any call that does not transfer funds or assets" on behalf of the proxied ("real") account. It is implemented as a **deny-list**, so any call family that is not explicitly listed is allowed by default — it fails open. On Asset Hub Westend this exact defect was found and fixed (see `prdoc/pr_12771.prdoc`), extending the deny-list to cover `ForeignAssets`, `PoolAssets`, `AssetConversion`, `Psm`, `PolkadotXcm`, `Revive`, `Vesting::vested_transfer`, and `Indices::transfer`/`force_transfer`. The identical filter on Asset Hub Rococo (`asset-hub-rococo-runtime`) was never updated and still only denies `Balances`, `Assets`, `NftFractionalization`, `Nfts`, `Uniques`.

This is the exact same "deny-list fails open" mistake previously found and documented for `asset-hub-westend-runtime`, where the fix explicitly called out that `ForeignAssets`/`PoolAssets` (other `pallet-assets` instances transferring value like `Assets`), `AssetConversion` (swaps/liquidity), `Psm` (mint/redeem), `PolkadotXcm` (`transfer_assets`/`teleport_assets`/`send`/`execute`), `Revive` (contract calls/instantiations carrying `value`), `Vesting::vested_transfer`, and `Indices::transfer`/`force_transfer` were all reachable by a `NonTransfer` proxy despite the documented "cannot transfer funds or assets" guarantee: [3](#0-2) [4](#0-3) 

The Rococo runtime wires in the same pallet families (`ForeignAssets`, `PoolAssets`, `AssetConversion`, `PolkadotXcm`, `Revive`, `Vesting`, `Indices` are all referenced in the same file), yet its `NonTransfer` deny-list was not extended, so the identical gap persists unpatched there.

This maps onto the same violated invariant as the Solidity report: a permission gate meant to block a category of state-affecting operations (spend-permission approval vs. proxy-instance-filter) has a code path (value == 0 vs. call family absent from deny-list) that silently bypasses the check, letting an unprivileged actor (spender vs. proxy delegate) trigger an authenticated action against the victim's account/wallet that the gate was supposed to prevent.

### Impact Explanation
A delegator who grants only a `NonTransfer` proxy (explicitly intending to withhold the ability to move funds/assets) unknowingly grants the delegate the ability to: swap/move liquidity via `AssetConversion`, transfer `ForeignAssets`/`PoolAssets`, execute arbitrary XCM `send`/`execute` or `transfer_assets`/`teleport_assets` via `PolkadotXcm`, make value-carrying `Revive` contract calls, perform `Vesting::vested_transfer`, or `Indices::transfer`/`force_transfer` (which repatriates the reserved deposit) — all while `filter()` returns `true` (permitted) for `ProxyType::NonTransfer`, contradicting its documented and expected semantics. This is a direct violation of the delegator's expressed authorization boundary and can result in asset loss, matching the "Low" risk classification of the source report (contained blast radius, requires the delegate to actually exploit the omission, no privileged prerequisite beyond a normal, unprivileged `add_proxy` grant).

### Likelihood Explanation
Any account owner can grant a `NonTransfer` proxy via the standard, unprivileged `Proxy::add_proxy` extrinsic — no governance, root, or validator involvement is required. Once granted, the delegate (attacker) needs only to submit a normal signed `Proxy::proxy` extrinsic wrapping one of the un-denied calls (e.g., `PolkadotXcm::transfer_assets`) as `RuntimeOrigin::signed(delegate)`, which is guaranteed to pass `filter()` since it isn't in the deny-list. This requires no forged inherents, no validator collusion, and no race condition — it is deterministically reachable on every block.

### Recommendation
Port the fix from `prdoc/pr_12771.prdoc` to `asset-hub-rococo-runtime`: extend `ProxyType::NonTransfer::filter` in `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/lib.rs` to also deny `ForeignAssets`, `PoolAssets`, `AssetConversion`, `Psm` (if present), `PolkadotXcm`, `Revive`, `Vesting::vested_transfer`, and `Indices::transfer`/`force_transfer`, mirroring `asset-hub-westend-runtime`'s corrected filter. More durably, consider converting `NonTransfer` from a deny-list to an allow-list (or adding a CI/test lint, as was added for Westend via `non_transfer_proxy_rejects_value_moving_calls`) so newly added pallets that move value are rejected by default rather than requiring an explicit addition to the deny-list.
