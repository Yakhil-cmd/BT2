### Title
Accrual-time `i128` overflow in debt valuation permanently freezes a whale market before the index cap engages - (File: common/src/rates/index.rs)

### Summary
The crash-class analog maps onto the pool's interest accrual: every state-mutating and accrual-driving entrypoint first calls `global_sync`, which multiplies the total scaled debt (`borrowed`, a `Ray` whose raw value can approach `i128::MAX`) by the growing `borrow_index`. `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` with a checked `i128` multiplication that panics with `GenericError::MathOverflow` once scaled-debt × index exceeds the `i128` domain — long before `MAX_BORROW_INDEX_RAY` ever clamps the index in `update_borrow_index`. Once a market crosses that value ceiling, every subsequent call that touches the market panics inside accrual, permanently freezing all supplied and borrowed funds in that market.

### Finding Description
Interest accrual runs inside `interest::global_sync` (`contracts/pool/src/interest.rs:20-33`), which loops `accrue_chunk` over elapsed millisecond windows and invokes `accrue_step`, whose internals call `calculate_supplier_rewards` (`common/src/rates/index.rs:73-89`). That function computes:

```rust
let old_total_debt = borrowed.mul(env, old_borrow_index);
let new_total_debt = borrowed.mul(env, new_borrow_index);
```

`Ray::mul` performs `I256` intermediate math but returns an `i128`-bounded `Ray`; when `borrowed.raw() * borrow_index.raw() / RAY` exceeds `i128::MAX`, it panics (`MathOverflow`). The only guard on index growth is the cap in `update_borrow_index` (`common/src/rates/index.rs:13-19`), which clamps the *index* at `MAX_BORROW_INDEX_RAY` but does nothing about `borrowed` — a `Ray` scaled amount that grows with `10^decimals` precision and the total debt principal. For high-decimal assets (e.g., 18 decimals), `borrowed.raw()` for a whale-scale book is ~`10^27+`, so the product `borrowed * index` overflows at an index multiplier of only ~170x, far below the index cap. The repo's own test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`) demonstrates exactly this: after accrual panics, `try_withdraw_raw` and `try_repay` both fail with `MATH_OVERFLOW`, and `last.borrow_index < MAX_BORROW_INDEX_RAY` confirms the cap never engaged.

Root cause: there is no saturating or early-exit path when `borrowed * borrow_index` overflows — the check exists for the index but not for the debt-value product. Because `global_sync` runs at the top of every market operation (supply, borrow, withdraw, repay, liquidate, `update_indexes`), the panic is unrecoverable: no code path can write a smaller `borrowed` without first accruing.

### Impact Explanation
Permanent freezing of user funds for the affected market. Once `borrowed * borrow_index` exceeds the `i128` ceiling, every entrypoint that accrues — `withdraw`, `repay`, `supply`, `borrow`, `liquidate`, `clean_bad_debt`, `update_indexes` — panics in `accrue_step` before touching positions. Suppliers cannot exit, borrowers cannot repay (so their collateral in other markets is also frozen against eventual bad debt), and liquidators cannot clear the book. The market is bricked indefinitely, matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
A single unprivileged address can set up the precondition: supply a whale-scale principal into a high-decimals market (caps can be lifted or are already large), borrow near maximum utilization through a second account with collateral in another market, then simply let `update_indexes` (permissionless) accrue. At the steep segment of a jump rate curve (e.g., the XLM curve at 98% utilization), the index compounds past the ~170x value ceiling over a long horizon — each `update_indexes` call only needs one chunk to overflow, and accrual is chunked at `MAX_COMPOUND_DELTA_MS` so no single call exceeds its domain; the overflow is in the *value* product, not the time delta. No privileged action, oracle manipulation, or leaked key is required — only capital and time, which is realistic for a griefing/attack scenario and requires no victim cooperation. Likelihood is bounded by the capital requirement (whale-scale funding on a high-decimal market) and the long accrual horizon, fitting Medium severity.

### Recommendation
Make debt-value computations in `accrue_step`/`calculate_supplier_rewards` overflow-safe: use `I256` intermediates for `borrowed * borrow_index` and clamp/saturate the resulting `Ray`, or cap `borrowed`'s effective scaled value (a total-debt ceiling analogous to `MAX_BORROW_INDEX_RAY`) so the product stays in-domain. Additionally, add a defensive check in `update_borrow_index`/`accrue_chunk` that detects when `borrowed * old_index` is near the `i128` boundary and freezes index growth (clamp index at the largest value that keeps the product representable) rather than panicking, preserving withdraw/repay paths so users can unwind.

### Proof of Concept
The repo already contains a deterministic reproduction in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`:

```rust
let principal = BILLION * 10i128.pow(18);       // whale supply, 18-decimal asset
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;                // ~98% utilization
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

// advance time in yearly steps; eventually:
t.try_update_indexes_for(&["BIG18"])            // panics: MathOverflow in accrue_step
// afterwards:
t.try_withdraw_raw(BOB, "BIG18", 1)             // panics: MathOverflow
t.try_repay(ALICE, "BIG18", 1.0)                // panics: MathOverflow
// assert!(last.borrow_index < MAX_BORROW_INDEX_RAY) — cap never engaged
```

On-chain equivalent: an attacker supplies a large principal to a high-decimals market, borrows near the utilization kink from a collateralized second account, then calls `update_indexes` (or waits for any keeper/user call) repeatedly. The first call whose chunk pushes `borrowed * borrow_index` past `i128::MAX` bricks the market; all suppliers' and borrowers' funds in that market become permanently unrecoverable.
