This confirms the analog: `Handler#stacks` resolves the target stack via `payload.dig('repository', 'full_name')` [1](#0-0) , while `WebhooksController#verify_signature` selects which GitHub App/secret to validate the HMAC against using a *different* field, `repository.owner.login` (or the `organization.login` fallback) [2](#0-1) . Both fields live inside the same attacker-suppliable JSON body, so nothing forces `repository.full_name` to belong to the same organization whose secret was used to sign the request.

### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while the target stack is resolved from the unrelated `repository.full_name` field, allowing cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` picks the `Shipit.github(organization:)` app/secret to validate `X-Hub-Signature` using `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')` [3](#0-2) . Once the signature check passes, every event handler (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) determines which `Stack`/`Repository` the event applies to using `Handler#stacks`, which reads a completely different key, `payload.dig('repository', 'full_name')` [1](#0-0) . Because the whole JSON body is attacker-controlled up to the byte, an org that can produce a validly-signed webhook for its own org (i.e., anyone who knows/controls the webhook secret configured for *some* organization onboarded into this Shipit instance) can freely set `repository.full_name` to point at a stack belonging to a completely different, unrelated organization/repository, and Shipit will process it as if it legitimately came from that other repository.

### Finding Description
The trust binding that should hold is: `organization whose secret validated the signature == organization/repository the event handler acts upon`. Instead:
- Signature verification binds trust to `repository.owner.login` / `organization.login` only [4](#0-3) .
- Handlers bind action to `repository.full_name`, an independent field of the same JSON body [5](#0-4) .

The HMAC over `request.raw_post` is real and does cover the whole body, so a genuinely-signed webhook cannot have its bytes altered in transit. But that is irrelevant here: the attacker is the one *constructing* the payload from scratch and sending it directly to Shipit's webhook endpoint. As long as they know the webhook secret for organization `A` (this is plausible in any Shipit deployment onboarding multiple orgs/GitHub Apps, since each org's admin is typically the one who configures/knows that org's own webhook secret), they can freely set `repository.owner.login = "A"` (to pass signature selection) while setting `repository.full_name = "B/victim-repo"` (to select the actual target stack processed by handlers). Nothing cross-checks that `repository.owner.login` is a prefix of `repository.full_name`.

### Impact Explanation
Depending on which event is spoofed, this enables:
- `push` event: enqueues `GithubSyncJob` for the victim stack with an attacker-chosen `expected_head_sha`, forcing a resync against forged head data.
- `status`/`check_suite` events: inject fabricated CI/check-run statuses on the victim's commits (`Status`, `CheckRun` records), which can flip merge-queue and deploy gating (`ci.require`, `merge.require`) to make an unreviewed or failing commit appear CI-green, potentially enabling an unauthorized/incorrectly-gated deploy or merge.
- `membership` event: create/remove `Team`/`Membership`/`User` records tied to the victim's organization data, since it too resolves via `full_name`/org fields not covered by the signing org.

This crosses "cross-repository writes" and can facilitate an "unauthorized deploy, rollback or merge" — matching the Critical/High impact bar defined in scope.

### Likelihood Explanation
Exploitability requires only: (1) knowledge of a webhook secret for *any* one organization onboarded to the Shipit instance (attacker's own org, if self-service onboarding is supported, or any org whose secret leaked), and (2) the ability to send an arbitrary HTTP POST to the public `/webhooks` endpoint — no Shipit session, `ApiClient` token, or repository write access to the *victim* repo is required. This is a plausible, unprivileged-attacker path against the engine's own routing/verification logic, not a hypothetical.

### Recommendation
Bind signature verification and stack resolution to the same field. Concretely, derive both the organization used for signature verification and the repository used for event routing from the same canonical value (e.g., always use `repository.full_name`, splitting owner from it) rather than trusting two independently-controlled JSON keys. Alternatively, after selecting the target `Stack`/`Repository` via `full_name`, assert that its owner matches the `repository_owner` (or `organization.login`) that was used to select the signing secret, and reject the webhook (422) if they differ.

### Proof of Concept
1. Attacker onboards/administers organization `attacker-org` in the target Shipit instance (or otherwise knows its configured webhook secret `S_A`).
2. Attacker crafts a raw JSON body for a `status` (or `push`) event:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(S_A, raw_body)` and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")`, which succeeds because the attacker legitimately knows `S_A` [6](#0-5) .
5. `StatusHandler`/`Handler#stacks` resolves the target via `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, and records the forged `success` status against the victim's commit/stack, independent of who signed the request [1](#0-0) .

**Uncertainty note:** I could not fully inspect `push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`, and `membership_handler.rb` bodies (only confirmed the shared `Handler#stacks`/`repository_name` base method) before running out of tool calls, so I can't cite the exact downstream write for each event type. The core routing/verification mismatch in `handler.rb` and `webhooks_controller.rb`, however, is fully confirmed from the code read.
