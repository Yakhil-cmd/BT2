### Title
Webhook signature is verified against an attacker-chosen organization while the processed event body targets an arbitrary repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to check the HMAC against by reading `repository_owner`, which is derived from Rails' merged `params` (query string + body). The actual event payload that gets dispatched to handlers, however, is `JSON.parse(request.raw_post)` — the raw body only. Because Rails merges query-string parameters over body-parsed parameters for identical keys, an unauthenticated caller can pick, via the query string, which organization's secret is used to authenticate the request, while the signed raw body can reference an entirely different organization/repository. This breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` computes the org used for HMAC verification from the controller's `params` helper: [1](#0-0) [2](#0-1) 

`repository_owner` calls `params.dig('repository', 'owner', 'login')`, where `params` is `ActionController::Parameters`, built by Rails by merging the JSON body params with the query-string params — with query-string values taking precedence over body values for identical keys (`ActionDispatch::Http::Parameters#parameters` does `request_parameters.merge!(query_parameters)`).

Separately, `create` re-parses the payload directly from the raw body and dispatches it to handlers: [3](#0-2) 

The HMAC itself is computed only over `request.raw_post` and checked with the secret for whatever org `repository_owner` resolved to: [4](#0-3) 

Because the org used to pick the verification secret (`repository_owner`, influenced by the query string) is decoupled from the org/repo actually described in the signed body (used later by `create` and by handlers such as `PushHandler`, `MembershipHandler`, status/commit handlers), an attacker who legitimately controls one organization/repository connected to the same Shipit instance (and therefore knows or can set that org's `webhook_secret`) can:

1. Craft an arbitrary JSON body describing an event for **any other** repository/organization tracked by Shipit (e.g. a `push` event for `victim-org/victim-repo`, or a fabricated `commit_status`/`membership` event).
2. Sign that raw body with their own known `webhook_secret`.
3. POST to `/github/webhooks?repository[owner][login]=<attacker-org>` (or `organization[login]=<attacker-org>`), so `verify_signature` resolves to the attacker's own org config and successfully verifies the attacker-computed signature.
4. `create` then parses the same raw body and hands the victim-targeting payload to the matching handler, e.g. `PushHandler#process`, which locates the stack purely by `branch`/repository data embedded in the (spoofed) body and calls `stack.sync_github(...)`: [5](#0-4) 

or `MembershipHandler`, which creates/edits `Team`/`Membership` records purely from body-supplied `team`/`organization`/`member` fields with no cross-check against the org whose secret verified the request: [6](#0-5) 

### Impact Explanation
This crosses the required boundary: an unprivileged actor who is only entitled to send authenticated webhook traffic for their own connected organization can instead forge trusted GitHub events for repositories/organizations they do not control. Depending on the handler abused, this yields:
- Forged `push`/`commit_status`/`check_suite`/`deployable_status` events for a victim stack, driving `GithubSyncJob`, marking commits deployable, or otherwise manipulating deploy-readiness state on a stack the attacker does not own (cross-repository writes / potential unauthorized deploy path).
- Forged `membership` events that create arbitrary `Team`/`Membership` rows tied to any `organization`/`slug`, which is the same mechanism `User#authorized?` consults to decide whether a logged-in GitHub identity is allowed to use the app at all — a path toward escalation into `Shipit.github_teams` authorization if the forged team happens to match a configured team handle.

This satisfies the "High" bar (unauthenticated manipulation of stack/task state via a broken authentication binding) and, depending on stack continuous-deployment configuration, can approach the "Critical" unauthorized-deploy bar.

### Likelihood Explanation
The webhook endpoint is unauthenticated by design (it exists precisely to accept unauthenticated GitHub-originated traffic, gated only by the HMAC). The only "credential" needed by an attacker is knowledge of a `webhook_secret` for *any* organization already connected to the instance — most naturally their own organization/repository, which they are expected to be able to configure to interoperate with Shipit legitimately. No GitHub App private key, Shipit session, or `ApiClient` token is required, and the query-string-over-body parameter precedence is a standard, easily reproducible Rails behavior rather than an edge case.

### Recommendation
Derive the organization used for signature verification from the same raw, signed body that is later dispatched (i.e., parse `request.raw_post` once, before verification, and use that parsed hash consistently for both the secret lookup and the event payload), and never resolve `repository_owner` via the ambient `params` method, which is contaminated by query-string values. Additionally, after verifying the signature, re-validate that the repository/organization embedded in the body actually belongs to the organization whose secret validated the request before invoking any handler.

### Proof of Concept
1. Attacker connects/legitimately owns `attacker-org` in the same Shipit instance and knows `attacker-org`'s configured `webhook_secret` (`S_attacker`).
2. Attacker builds a raw JSON body for a `push` event that names the victim stack's branch/repository, e.g.:
```json
{"ref":"refs/heads/master","after":"deadbeef...","repository":{"full_name":"victim/victim-repo","owner":{"login":"victim-org"}}}
```
3. Attacker computes `signature = "sha1=" + HMAC_SHA1(S_attacker, raw_body)`.
4. Attacker sends:
```
POST /github/webhooks?repository[owner][login]=attacker-org
X-Github-Event: push
X-Hub-Signature: sha1=<signature>
Content-Type: application/json

<raw_body above>
```
5. `verify_signature` calls `repository_owner` → `params.dig('repository','owner','login')` → resolves to `"attacker-org"` from the query string (overriding the body's `victim-org`), so `Shipit.github(organization: 'attacker-org')` is used, and `verify_webhook_signature(signature, raw_body)` succeeds because it was computed with `S_attacker`.
6. `create` re-parses `request.raw_post`, getting the body with `victim-org/victim-repo`, and dispatches it to `PushHandler`, which looks up the matching `Stack` by branch and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — despite the request never being signed by anything belonging to `victim-org`.

Note: exact downstream impact (e.g., whether `sync_github` alone triggers a deploy) depends on stack `continuous_deployment`/CI settings not fully enumerated here; the membership-based authorization escalation path (`MembershipHandler` → `Team`/`Membership` → `User#authorized?`) was traced through the model code but its exact interaction with a given deployment's `Shipit.github_teams` configuration is environment-specific and could not be fully validated in this pass.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
