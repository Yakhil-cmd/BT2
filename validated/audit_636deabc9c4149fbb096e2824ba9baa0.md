### Title
Cross-organization webhook forgery via `repository_owner` fallback mismatch lets attacker mutate another tenant's `PullRequest` record - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization GitHub App configuration, `WebhooksController#verify_signature` selects the signing secret to verify a webhook using `repository_owner`, which falls back to `params.dig('organization', 'login')` when `repository.owner.login` is absent. `AssignedHandler` (and other handlers), however, resolve the target `Repository`/`Stack` from the independently-attacker-controlled `params['repository']['full_name']`. An attacker who can authenticate as one configured organization (e.g. one whose `webhook_secret` is unset, making verification a no-op) can therefore forge a `pull_request` `assigned` event that is "verified" against organization A but whose payload's `repository.full_name` points at organization B's repository/stack, causing `Shipit::PullRequest#update` to persist attacker-controlled title/labels/assignees/commit data for B's production stack.

### Finding Description
The broken binding is:
`verifier_org = params.dig('repository','owner','login') || params.dig('organization','login')` (used in `WebhooksController#verify_signature` / `repository_owner`, app/controllers/shipit/webhooks_controller.rb:59-62 and :25) should equal `target_repo_org = params.dig('repository','full_name').split('/').first` (used in `AssignedHandler#repository`, app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb:67-69). These are read from different, independently attacker-settable JSON fields, so nothing enforces `verifier_org == target_repo_org`.

Path:
1. `WebhooksController#create` parses raw JSON and dispatches to handlers before any per-repository authorization beyond the signature check (`app/controllers/shipit/webhooks_controller.rb:10-15`).
2. `verify_signature` computes `repository_owner` from `repository.owner.login`, falling back to `organization.login` if the former is omitted (`app/controllers/shipit/webhooks_controller.rb:59-62`), then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` (`:25-29`).
3. `Shipit::GitHubApp#verify_webhook_signature` returns `true` unconditionally if that organization's `webhook_secret` is not configured (`lib/shipit/github_app.rb:76-83`: `return true unless webhook_secret`). Multiple documented Shipit setups leave `webhook_secret` blank/nil per-org (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`), which is a supported, non-error configuration state (`Shipit.github`/`github_app_config` in `lib/shipit.rb:170-200` explicitly support per-organization config lookup).
4. `AssignedHandler` never consults `repository_owner`; it loads the target repository purely from `params.repository.full_name` (`app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb:67-69`) and finds the `Shipit::PullRequest` for that repository's stack (`:53-65`), then calls `pull_request.update(github_pull_request: params.pull_request)` (`:44`), which writes `title`, `state`, `additions`, `deletions`, `user`, `assignees`, `labels`, and resolves/creates a `Commit` via `stack.github_api.commit` for the attacker-supplied `head.sha` (`app/models/shipit/pull_request.rb:36-50`).

Exploit request: attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, a signature computed for organization A's (no-secret) HMAC (trivially satisfied since verification is skipped), and a body omitting `repository.owner.login`, setting `organization.login = "OrgA"` (the lenient org) and `repository.full_name = "OrgB/victim-repo"` (a real production stack under organization B, whose secret the attacker never possesses), `action: "assigned"`, plus a valid `number`, `pull_request` object (attacker-chosen title/labels/assignees/head sha of an existing commit), and `sender`.

Because `verify_signature` never checks that the organization used for verification matches the organization implied by `repository.full_name`, the request passes verification against OrgA while `AssignedHandler` mutates OrgB's persisted `PullRequest` row - a payload authenticated for one tenant's organization mutating another tenant's stack/PR/commit records, exactly the class of "payload for one repository mutating another's stack" described as Critical impact.

Existing guards do not stop this: `drop_unhandled_event` only checks the event has a handler; `ExplicitParameters` in `AssignedHandler` only validates JSON shape, not organizational consistency; `rescue Shipit::GithubOrganizationUnknown` only triggers if the fallback organization name is entirely unknown to Shipit's config, not when it's a legitimately configured but differently-scoped organization.

### Impact Explanation
The attacker can overwrite `title`, `labels`, `assignees`, `additions`/`deletions`, and trigger creation/association of a `Commit` record on another organization's production `Stack`'s `PullRequest`, without ever knowing that organization's webhook secret. This is repeatable against any `PullRequest`/`number` combination that already exists for the victim stack, and against any victim organization configured on the same multi-tenant Shipit instance, as long as at least one other organization in the same instance has a missing/lenient `webhook_secret`. This matches "a payload for one repository mutating another's stack, commit, task or team" (Critical). It does not directly invoke `merge!`/`PTY.spawn`, since `AssignedHandler` only touches `Shipit::PullRequest`, not `Shipit::MergeRequest`, so it stops short of a directly demonstrated unauthorized deploy/merge/rollback from this specific handler alone.

### Likelihood Explanation
Preconditions: Shipit must be configured with multiple GitHub organizations (a supported, documented pattern — `docs/setup.md`, "Using Multiple Github Applications"), and at least one configured organization must have no `webhook_secret` set (also a documented default state in example configs). Given that, the attack costs the attacker nothing beyond crafting an HTTP request — no GitHub credentials, no Shipit session, no knowledge of the victim organization's secret. It is fully repeatable and requires no interaction with the real GitHub API. The main uncertain precondition is whether a concrete production deployment actually leaves one organization's `webhook_secret` unset; this cannot be verified from the engine code alone (it depends on operator configuration), but the code permits and documents this state without any warning or cross-check.

### Recommendation
Bind signature verification to the same organization/repository used by the handler: derive `repository_owner` and the handler's repository strictly from `params.repository.full_name`'s owner segment, refuse to fall back to `organization.login` for repository-scoped events, and reject events where the two disagree. Additionally, treat a missing `webhook_secret` for any configured organization as a configuration error (log/alert, or refuse boot) rather than silently accepting all signatures for that organization.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Configure two organizations via `test/dummy/config/secrets_double_github_app.yml`-style fixture: `OrgA` with `webhook_secret: nil`, `OrgB` with a real `webhook_secret`, and seed a `Shipit::Stack` for `OrgB/victim-repo` (production environment) with an existing `Shipit::PullRequest` (`number: 2`, known `title`/`labels`).
2. Assert the binding before the request: `pull_request.title != attacker_title` and `pull_request.labels != attacker_labels`.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no `X-Hub-Signature` (or any garbage signature), body: `{ action: 'assigned', number: 2, organization: { login: 'OrgA' }, repository: { full_name: 'OrgB/victim-repo' }, pull_request: { ...attacker-chosen title/labels/assignees/head sha of an existing commit... }, sender: { login: 'attacker' } }` (no `repository.owner.login`).
4. Assert `response).to have_http_status(:ok)` (verification succeeded via OrgA's nil secret).
5. Reload `pull_request` and assert `pull_request.title == attacker_title` and `pull_request.labels == attacker_labels`, proving OrgB's record was mutated by a payload verified only against OrgA.
