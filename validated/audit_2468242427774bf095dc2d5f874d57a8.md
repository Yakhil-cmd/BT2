### Title
Webhook signature verification authenticates the organization from `repository.owner.login`, but handlers act on the repository from the unrelated `repository.full_name` field, allowing cross-organization forgery of commit statuses/pushes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature using the organization named in `repository.owner.login` (or `organization.login`) of the incoming JSON payload, itself attacker-supplied. Once the signature checks out, the entire payload is dispatched to handlers that determine which repository/commit to actually mutate using a *different* field of the same payload — `repository.full_name`. Nothing cross-checks that these two fields refer to the same organization, so an operator who legitimately onboarded their own GitHub organization (and thus knows that organization's own `webhook_secret`) can forge a validly-signed webhook whose `repository.owner.login` is their own org but whose `repository.full_name` points at a victim organization's repository, causing Shipit to write state (e.g., commit statuses) for a repository they do not own or administer.

### Finding Description
`WebhooksController#verify_signature` computes the authenticating organization purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a per-organization `GitHubApp` instance whose `webhook_secret` is configured independently per organization: [3](#0-2) [4](#0-3) 

The HMAC signature only proves the sender knows the `webhook_secret` belonging to whatever organization is named in `repository.owner.login` — a field fully controlled by the sender in the raw JSON body being signed. It does **not** prove that the rest of the payload (in particular `repository.full_name`, `sha`, `branches`, etc.) genuinely originates from or pertains to that same organization.

After signature verification passes, the full payload is dispatched to handlers: [5](#0-4) 

Handlers resolve the target repository via a completely different payload field, `repository.full_name`: [6](#0-5) 

For example, `StatusHandler` writes a `Status` record directly from attacker-controlled fields (`state`, `description`, `target_url`, `context`) onto any `Commit` matching the given `sha`, with no scoping to the authenticating organization at all: [7](#0-6) 

Similarly, `PushHandler` triggers a GitHub sync job against any stack whose repository matches `repository.full_name`/branch, again independent of the authenticating organization: [8](#0-7) 

The broken binding, expressed as an equality that must hold but doesn't:
`organization authenticated by verify_signature (repository.owner.login / organization.login)` == `organization implied by repository.full_name used by Handler#stacks / Repository.from_github_repo_name`.

Before the attack: an attacker who legitimately owns/administers "attacker-org" (and thus knows the `webhook_secret` Shipit issued/holds for that org) can only affect stacks/repos under "attacker-org".
After the attack: by setting `repository.owner.login = "attacker-org"` (so the signature verifies against attacker-org's secret) while setting `repository.full_name = "victim-org/victim-repo"` in the same signed raw body, the attacker causes Shipit to act on "victim-org/victim-repo" — a repository/organization the attacker never authenticated as and does not own.

### Impact Explanation
This is a cross-tenant/cross-repository write achieved with only the credentials of an unrelated, unprivileged organization the attacker legitimately controls (no Shipit account, no `ApiClient` token, no victim's `webhook_secret`, and no GitHub write access to the victim repo are required). Concretely:
- `StatusHandler` allows forging arbitrary commit statuses (`success`/`failure`, descriptions, target URLs) for commits belonging to a victim's tracked repository. Since Shipit's deploy/merge safety gating is commonly driven by required CI statuses on commits, this can be used to fabricate a passing status on a victim commit, contributing to an unauthorized deploy/merge decision — a cross-repository write satisfying the report's "Critical" impact bar.
- `PushHandler` can force a sync/resync of a victim stack it does not own, an unauthorized action against a repository outside the attacker's own tenant.

### Likelihood Explanation
Requires only that the attacker legitimately onboard (or already control) any single GitHub organization/App configuration recognized by the Shipit instance (a routine, low-privilege action in a multi-tenant Shipit deployment), and be able to send an HTTP POST with a crafted JSON body and a valid `X-Hub-Signature` computed with their own org's secret. No special network position, no victim credentials, and no compromise of the victim's GitHub App or webhook secret are needed.

### Recommendation
After signature verification, re-derive the "authenticated organization" and require that `repository.full_name`'s owner segment (and/or `organization.login`) match the same organization used to select the verifying `GitHubApp`/secret. Reject the event (422) on mismatch before dispatching to any handler, mirroring how `new_private_client()` should validate that `private_clients_acc` corresponds to the version encoded in `root_state` rather than trusting the caller-supplied account/field in isolation.

### Proof of Concept
1. Attacker legitimately configures/owns GitHub organization `attacker-org`, which Shipit is configured with (`Shipit.github(organization: 'attacker-org')` resolves to a valid `GitHubApp` with a known/derivable `webhook_secret`, e.g. because the attacker installed the Shipit GitHub App on their own org).
2. Attacker crafts a raw JSON body for a `status` event:
```json
{
  "sha": "<victim commit sha tracked by Shipit>",
  "state": "success",
  "description": "forged",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s own `webhook_secret` over this exact raw body (`OpenSSL::HMAC.hexdigest('sha1', webhook_secret, body)`), per [4](#0-3) .
4. POST to `/webhooks` with headers `X-Github-Event: status` and the computed signature.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"` [2](#0-1) , looks up `Shipit.github(organization: 'attacker-org')`, and successfully verifies the signature since it matches attacker-org's own secret.
6. `create` dispatches to `StatusHandler`, which resolves the target purely from `sha` [7](#0-6)  and writes a forged `Status` for the victim's commit, entirely unrelated to `attacker-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
