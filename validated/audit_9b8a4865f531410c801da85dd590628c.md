### Title
Cross-organization webhook forgery leads to unauthorized commit-status injection and triggered deploys - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret used to authenticate an inbound webhook based on `repository.owner.login` (falling back to `organization.login`), but the handlers that actually act on the payload (e.g. `StatusHandler`, `PushHandler`) key their writes off a completely different field — `repository.full_name` or a bare `sha` lookup that isn't scoped to the authenticating organization at all. In a multi-organization Shipit deployment, this breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`Shipit.github(organization:)` looks up a **per-organization** config (including its own `webhook_secret`) via `github_app_config(organization)` [1](#0-0) . `WebhooksController#verify_signature` picks that organization solely from the JSON payload field `repository.owner.login` (or `organization.login`), and verifies the HMAC signature using that org's secret: [2](#0-1) 

Once the signature check passes, `create` re-parses the *entire* raw body and dispatches it to handlers unmodified: [3](#0-2) .

The handlers, however, do not re-derive or cross-check the organization used for signing:
- `Handler#repository_name` (base class used by push/pull_request handlers) keys off `payload.dig('repository', 'full_name')`, not `owner.login`: [4](#0-3) 
- `StatusHandler#process` doesn't even look at the repository at all — it matches **any** `Commit` row across the whole database by raw `sha`, and writes an attacker-controlled state/description/target_url/context: [5](#0-4) 

Because `repository.owner.login` (used to pick the signing secret) and `repository.full_name` / commit `sha` (used to select what gets mutated) are independent JSON fields inside the same signed body, an attacker who legitimately controls a GitHub App/organization "OrgA" already onboarded into this Shipit instance (and therefore knows OrgA's `webhook_secret`) can forge a payload where:
- `repository.owner.login = "OrgA"` (chosen secret for verification), and
- the actual mutation target (`repository.full_name` for push/pull_request events, or the raw `sha` for status events) references a repository/commit that belongs to a different tenant organization "OrgB" hosted on the same Shipit instance.

Because the signature only proves "this body was produced with OrgA's secret," not "this body only talks about OrgA's repositories," the forged webhook is accepted and dispatched to handlers that write into OrgB's data.

### Impact Explanation
This escalates into unauthorized writes across the authorization boundary the app is supposed to enforce per-organization. The clearest concrete impact is via `StatusHandler`: an attacker can inject a fabricated `success` CI status onto **any commit in any stack on the instance** merely by knowing the sha (shas are not secrets — they leak via PRs, GitHub UI, etc.). `Commit#create_status_from_github!`/`Status` creation triggers `schedule_continuous_delivery`, and if the target stack has `continuous_deployment` enabled, this can cause `ContinuousDeliveryJob`/`trigger_continuous_delivery` to fire and deploy the forged-"green" commit: [6](#0-5) [7](#0-6) [8](#0-7) . This is an unauthorized deploy triggered by an attacker who does not control the target organization/repository — matching the "High: unauthorized deploy" impact bucket. It also lets an attacker forge commit-status webhooks (spoofed CI results) for repositories they have no access to, i.e., a cross-organization/cross-repository write.

### Likelihood Explanation
Likelihood is high in any Shipit deployment configured for more than one GitHub organization (the multi-org `github:` config schema explicitly supported by `Shipit.github_app_config`) [9](#0-8) . Any tenant organization admin — an "unprivileged attacker" with respect to other tenants — already knows their own organization's webhook secret (they configure it on GitHub's side and hand it to the Shipit operator), and can freely craft arbitrary POST bodies with mismatched `owner.login`/`full_name`/`sha` fields, since nothing in the verification logic checks internal consistency of the payload.

### Recommendation
After verifying the HMAC signature for the resolved `repository_owner`, additionally verify that every organization-identifying field actually used by downstream handlers (`repository.full_name`'s owner segment for push/pull_request/check_suite/pull_request handlers, and the owning stack's organization for `StatusHandler`'s commit lookup) matches the organization whose secret validated the signature. Concretely: derive the acting organization consistently in one place, pass it explicitly to handlers, and have `StatusHandler` scope its `Commit.where(sha:)` lookup to commits belonging to stacks under that verified organization instead of searching all commits instance-wide.

### Proof of Concept
1. Shipit instance is configured with two GitHub App/organization entries — `orga` and `orgb` — each with distinct `webhook_secret`s, per the multi-org config schema in `lib/shipit.rb`.
2. Attacker legitimately administers `orga`'s GitHub App, and thus knows `orga`'s webhook secret (`SECRET_A`).
3. Attacker crafts a `status` event body:
```json
{
  "sha": "<known sha of a commit belonging to orgb/some-private-repo>",
  "state": "success",
  "description": "forged",
  "context": "ci/forged",
  "repository": { "owner": { "login": "orga" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner == "orga"`, fetches `Shipit.github(organization: "orga")`, and the HMAC check passes because it was signed with `SECRET_A`.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — with no scoping to `orga` — finds the `orgb` commit, and creates a `Status` record with attacker-controlled `state: "success"`, potentially triggering `ContinuousDeliveryJob` and an unauthorized deploy on `orgb`'s stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

module Shipit
  module Webhooks

          accepts :target_url, String

        def process

        end
      end

module Shipit
  class ContinuousDeliveryJob < BackgroundJob
    include BackgroundJob::Unique

    queue_as :deploys
    on_duplicate :drop

    def perform(stack)
      return unless stack.continuous_deployment?

      # If there is a schedule defined for this stack, make sure we are within a
      # deployment window before proceeding.
      return if stack.continuous_delivery_schedule && !stack.continuous_delivery_schedule.can_deploy?

      # checks if there are any tasks running, including concurrent tasks
      return if stack.occupied?

      stack.trigger_continuous_delivery
    end
  end
