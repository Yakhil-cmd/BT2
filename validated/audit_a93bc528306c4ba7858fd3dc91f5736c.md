## Title
A malicious/broken secondary‑AA recipient can permanently block a legitimate co‑recipient from receiving its share of a fee/payout by bouncing, causing the whole primary AA response (and both payments) to be reverted - (File: `aa_composer.js`)

### Summary
`aa_composer.js` implements "secondary triggers": whenever a primary AA response sends a payment to another AA address in the same response unit, that AA is invoked as a chained ("secondary") trigger. If *any* of the secondary AAs invoked from a single response bounces, `handleSecondaryTriggers` propagates the failure and causes the *entire primary AA response to be reverted*, undoing all state changes and all payments made by that response — including the payment(s) to the other, well-behaved recipient(s). This is the exact analog of the reported issue: a fee/payout is split between two counterparties in a single atomic operation, and one counterparty (here, a malicious or broken AA) can unconditionally refuse to be paid, thereby blocking the other counterparty from ever getting paid, since the distribution logic can be retried indefinitely with the same result.

### Finding Description
When an AA response unit pays out to one or more other AA addresses, `sendUnit` collects those addresses via `addOutputAddresses` and, after the response unit is saved, calls `handleSecondaryTriggers(objUnit, arrOutputAddresses)`: [1](#0-0) 

`handleSecondaryTriggers` looks up which of the paid addresses are AAs and invokes `handleTrigger` for each of them with `bSecondary = true`, running them in series via `async.eachSeries`: [2](#0-1) 

If any one of these secondary AA invocations bounces, the `async.eachSeries` final callback receives an error and, because the *outer* trigger is not itself secondary (`!bSecondary`), it calls `revert(...)` for the whole primary response: [3](#0-2) 

`revert()` rolls back all state and balance changes made by the primary AA in this invocation, all the way back to the savepoint taken before it ran, and discards any responses already produced (including the payment to the other, honest recipient): [4](#0-3) 

A secondary AA can trivially force this failure path: it only needs to call `bounce(...)` in its own oscript logic (e.g., unconditionally, or under attacker-controlled conditions), which sets `bBouncing = true` and, since it is invoked with `bSecondary = true`, immediately calls `finish(null)`, which returns an error object to the caller instead of a response unit: [5](#0-4) 

Consequently, a design like the reported one — a single distributor AA that pays two counterparty addresses (e.g., two fee-collector AAs, similar to `evFeeCollector`/`dzhvFeeCollector` in the Solidity report) within the same response — is not resilient to one counterparty being malicious, compromised, or simply badly written: that counterparty AA can deterministically bounce every time it is triggered, which reverts the *entire* distribution, denying funds to the innocent counterparty as well, on every retry.

### Impact Explanation
This causes permanent freezing of funds for the honest party: because the primary distributor's state/balance changes are rolled back on every attempt (`ROLLBACK TO SAVEPOINT initial_balances`), retrying the distribution produces the identical outcome forever, as long as the malicious AA keeps bouncing. The honest counterparty can never be paid its share via this path, and the distributor AA's payout logic is effectively griefed indefinitely by one participant. This matches the "AA fund loss or freezing" impact category.

### Likelihood Explanation
Likelihood is High in any AA design that pays multiple AA-controlled addresses atomically in one response (fee-splitting, revenue-sharing, matching/auction settlement AAs, etc.), since any AA author (including one of the payees) can control whether their own AA bounces, and this requires no privileged access — just deploying an AA definition that always calls `bounce()`.

### Recommendation
AA authors that need to pay out to multiple independent parties in a single response should avoid making the whole operation atomic across untrusted secondary AAs. Options include: (1) sending payments to plain (non-AA) addresses instead of AA addresses when possible, (2) queueing/crediting each party's share in state variables and letting each party pull/claim their own share via a separate, independent trigger (so one party's AA logic cannot affect another party's ability to claim), or (3) never relying on the secondary-trigger success of an externally-controlled AA as a precondition for retaining state changes made to pay other, unrelated parties.

### Proof of Concept
1. Deploy `TeamAAA` (Team A's malicious/broken collector AA) whose only logic is:
```
{
  bounce_fees: {base: 10000},
  messages: [{
    app: 'state',
    state: `{ bounce('always fail'); }`
  }]
}
```
2. Deploy `TeamBAA` (Team B's honest collector AA) with normal accept logic.
3. Deploy `DistributorAA` whose trigger handler, on being called (e.g. a `claim` action), sends a single payment message with two outputs in the same response unit: one to `TeamAAA` and one to `TeamBAA`, per `evTeamShare`/`dzhvTeamShare` style split.
4. Trigger `DistributorAA`. In `sendUnit`, both `TeamAAA` and `TeamBAA` addresses end up in `arrOutputAddresses`, and `handleSecondaryTriggers` invokes both as secondary triggers (`aa_composer.js:1720-1741`).
5. `TeamAAA`'s trigger execution calls `bounce('always fail')`, causing its own `finish(null)` with `bBouncing=true` and `bSecondary=true` to return an error via `onDone` (`aa_composer.js:1671-1689`).
6. `async.eachSeries`'s final callback receives this error, and because the outer call is not secondary, `revert(...)` is invoked (`aa_composer.js:1743-1750`), rolling back `DistributorAA`'s state/balances via `ROLLBACK TO SAVEPOINT initial_balances` (`aa_composer.js:1759-1783`).
7. Result: `TeamBAA` never receives its share even though it behaved correctly, and every subsequent call to `DistributorAA`'s claim logic repeats the same outcome, permanently freezing Team B's funds inside `DistributorAA`.
