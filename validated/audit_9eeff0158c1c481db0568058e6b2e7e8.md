### Title
`RemoveValidator` governance vote lacks minimum-council-size guard, allowing a single proposer to empty the validator set — (File: `kaiax/gov/headergov/impl/header.go`, `kaiax/gov/headergov/impl/api.go`)

---

### Summary

The `checkConsistency` function that validates `RemoveValidator` governance votes returns `nil` immediately in `"none"` governance mode and only guards the governing node in `"single"` mode. No check verifies that the resulting council would retain a minimum number of validators. A council member who is the proposer of the last block in an epoch can cast a single `RemoveValidator` vote listing every other validator; the vote is ratified at the epoch boundary, collapsing the council to one member and destroying BFT fault tolerance. The codebase itself acknowledges the gap with an explicit `// TODO-kaiax: add removevalidator vote check` comment in the `Vote` API.

---

### Finding Description

**Incomplete guard in `checkConsistency`**

`checkConsistency` in `kaiax/gov/headergov/impl/header.go` (lines 193–203) handles `RemoveValidator` votes as follows:

```go
case gov.AddValidator, gov.RemoveValidator:
    params := h.GetParamSet(blockNum)
    // compare with governing node only in single mode.
    if params.GovernanceMode != "single" {
        return nil          // ← no check at all in "none" mode
    }
    if slices.Contains(vote.Value().([]common.Address), params.GoverningNode) {
        return ErrGovNodeInValSetVoteValue
    }
    return nil              // ← no minimum-size check in "single" mode either
```

In `"none"` mode the function returns `nil` unconditionally. In `"single"` mode it only prevents the governing node from being listed in the vote value; it does not prevent the governing node from removing every other validator.

**Acknowledged gap in the `Vote` API**

`kaiax/gov/headergov/impl/api.go` lines 74–81:

```go
err := api.h.checkConsistency(nextBlock, vote)
if err != nil {
    return "", err
}

// TODO-kaiax: add removevalidator vote check   ← developer-acknowledged missing check

api.h.PushMyVotes(vote)
```

The TODO appears immediately after `checkConsistency` returns, confirming the developer knew the existing check was insufficient for `RemoveValidator` votes.

**`VerifyVote` inherits the same gap**

`VerifyVote` (lines 61–110 of `header.go`) terminates with `return h.checkConsistency(blockNum, vote)`. Because `checkConsistency` does not enforce a minimum council size, a block header containing a council-emptying `RemoveValidator` vote passes block-level verification without error.

**`applyVote` applies the removal unconditionally**

`kaiax/valset/impl/getter_council.go` lines 236–258:

```go
func applyVote(header *types.Header, council *valset.AddressSet, governingNode common.Address) bool {
    ...
    for _, address := range addresses {
        if address == governingNode { continue }
        switch voteKey {
        case gov.RemoveValidator:
            if council.Contains(address) {
                council.Remove(address)   // no floor check
            }
        }
    }
    return originalSize != council.Len()
}
```

After ratification at the epoch boundary, `applyVote` removes every listed address without checking whether the resulting council is empty or below the BFT minimum.

**Broken invariant in consensus**

`consensus/istanbul/core/core.go` lines 81–87:

```go
func calcQuorumSize(qualifiedLen int, committeeSize uint64) int {
    size := min(qualifiedLen, int(committeeSize))
    if size < 4 {
        return size   // quorum == 1 when only 1 validator remains
    }
    return int(math.Ceil(float64(2*size) / 3))
}
```

With a single qualified validator, quorum collapses to 1. That validator can seal every block unilaterally, eliminating all BFT fault tolerance. With zero validators, `size = 0` and downstream consensus logic receives an empty committee, causing undefined/panic-level behavior.

---

### Impact Explanation

After the malicious epoch-boundary ratification:

- **Council state is persistently corrupted**: `writeCouncil` in `getter_council.go` writes the shrunken council to the chain KV store; every subsequent `GetCouncil` call returns the broken set.
- **BFT consensus invariant is broken**: The protocol requires ≥ 4 validators for `ceil(2n/3)` quorum. With 1 validator, quorum = 1; the single remaining validator controls block production and finality with no fault tolerance.
- **Chain halt or single-party takeover**: Honest nodes that were removed can no longer propose or commit blocks. The remaining validator either halts the chain (if it goes offline) or produces all blocks unilaterally.

This matches the "invalid state transition / consensus divergence on honest nodes" impact gate.

---

### Likelihood Explanation

- **`"none"` governance mode**: Any council member who is the proposer of the last block in an epoch can trigger this. In `RoundRobin` or `Sticky` proposer-policy mode the proposer schedule is deterministic, so the attacker can plan the exact block. In `WeightedRandom` mode the attacker must wait for a lucky epoch-end slot.
- **`"single"` governance mode**: The governing node alone can trigger this, which is a privileged but single-party action with no additional collusion required.
- The vote value accepts a `[]common.Address` slice (see `parseValidatorVote` lines 278–286 of `getter_council.go`), so all other validators can be listed in one vote.
- No on-chain guard, no `VerifyVote` rejection, and no `applyVote` floor check exist to stop the ratification.

---

### Recommendation

1. **In `checkConsistency`** (`header.go`), for `gov.RemoveValidator`, fetch the current council and verify that `len(council) - len(removedAddresses) >= minCouncilSize` (where `minCouncilSize` should be at least 1, and ideally 4 to preserve BFT fault tolerance). Return a new `ErrCouncilTooSmall` error if the check fails.

2. **In the `Vote` API** (`api.go`), replace the `// TODO-kaiax: add removevalidator vote check` placeholder with the same council-size check before `PushMyVotes` is called.

3. **In `applyVote`** (`getter_council.go`), add a post-removal guard: if `council.Len() == 0`, revert the removal and return `false`.

---

### Proof of Concept

**Setup**: 4-validator network, `"none"` governance mode, `RoundRobin` proposer policy, epoch = 1000.

1. Validator A calculates it will be the proposer of block 999 (last block of epoch 0).
2. Validator A calls `governance_vote("governance.removevalidator", [addrB, addrC, addrD])`.
3. The vote is inscribed in `header.Vote` of block 999.
4. `VerifyVote` → `checkConsistency` returns `nil` (none mode, early return at line 197 of `header.go`).
5. Block 999 is accepted by all honest nodes.
6. At block 1000 (epoch boundary), `getExpectedGovernance` collects the last `RemoveValidator` vote from epoch 0 (block 999). `VerifyGov` confirms the governance data matches. The ratification is written to `header.Governance`.
7. `PostInsertBlock` → `HandleGov` → `AddGov` stores the ratification.
8. `applyVote` removes B, C, D from the council. `writeCouncil` persists `[addrA]`.
9. From block 1001 onward, `GetCouncil` returns `[addrA]`. `calcQuorumSize(1, committeeSize)` = 1. Validator A is the sole proposer and committee member. B, C, D are permanently excluded from consensus. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

func applyVote(header *types.Header, council *valset.AddressSet, governingNode common.Address) bool {
	voteKey, addresses, ok := parseValidatorVote(header)
	if !ok {
		return false
	}

	originalSize := council.Len()
	for _, address := range addresses {
		if address == governingNode {
			continue
		}
		switch voteKey {
		case gov.AddValidator:
			if !council.Contains(address) {
				council.Add(address)
			}
		case gov.RemoveValidator:
			if council.Contains(address) {
				council.Remove(address)
			}
		}
	}
	return originalSize != council.Len()
}
