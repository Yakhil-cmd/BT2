## Analysis

The GSP report describes a classic "admin changes price → attacker sandwiches the change" bug: because the price update and the user's trade are separate transactions, an attacker who sees the price-update transaction in the mempool can insert a trade before it (at the old price) and another after it (at the new price), extracting value that should have accrued to LPs.

Obyte (ocore) has no traditional mempool, but it has an analogous mechanism that produces the same effect: **the deterministic ordering of AA-trigger execution is derived from a unit's `level` (i.e., its position in the DAG, chosen by whoever creates the unit through parent selection), not from wall-clock arrival order**. This gives any user free choice over whether their own unit is ordered *before* or *after* a specific pending (not-yet-stable) unit, simply by choosing to omit it or include it as a parent.

Both `handleAATriggers` in `main_chain.js` and `aa_composer.js` compute execution order the same way: [1](#0-0) [2](#0-1) 

The bundled/official oscript sample pattern demonstrates exactly the vulnerable design that the GSP report warns about — a privileged address sets an exchange/conversion rate in AA state, and any other user's trigger unit that arrives later is executed at that rate: [3](#0-2) [4](#0-3) 

Because units reference parents freely and only need to become stable (there is no atomicity between the rate-setting unit and any other unit posted around the same time), an attacker who observes the unconfirmed rate-change unit can:
1. Post a "buy" trigger unit whose parents deliberately exclude the rate-change unit → it gets a lower `level` and is guaranteed to execute (be ordered) **before** the rate change, using the old rate.
2. Post a "sell" trigger unit that includes the rate-change unit as one of its parents → its `level` is necessarily higher, guaranteeing it executes **after** the rate change, using the new rate.

This is the direct DAG analog of mempool front/back-running: instead of racing gas price, the attacker manipulates parent selection to control relative `level`, which the protocol uses as the sole tiebreaker for trigger execution order within an MCI.

### Title
Unprivileged AA-trigger senders can sandwich a privileged price/exchange-rate update by choosing parent units to control trigger execution order - (File: `main_chain.js`, `aa_composer.js`)

### Summary
ocore executes AA (autonomous agent) triggers in an order determined purely by `mci, level, unit, address` (`main_chain.js` `handleAATriggers`, `aa_composer.js` `handleAATriggers`). A unit's `level` is chosen by its author via free parent selection. Any AA that implements a privileged "set exchange rate / ideal price" pattern (as shown in the bundled `sell_asset_for_bytes.oscript` sample, and similar patterns using `data_feed[[...]]` oracle prices in `option_contract.oscript`/`futures_contract.oscript`) can be sandwiched: a user observing the not-yet-stable rate-update unit can post a "buy" trigger with lower level (executes before the update, old price) and a "sell"/reverse trigger that includes the rate-update unit as a parent (executes after, new price), extracting the price delta risk-free from the AA's balance — functionally identical to the reported `GSPVault::adjustPrice` sandwich.

### Finding Description
- AA trigger execution order is fixed by SQL `ORDER BY ... level, unit, address` with no other tie-breaking related to causal intent: [1](#0-0)  and [5](#0-4) .
- `level` is an attacker-controllable value: any address composing a unit chooses its parent units, and a unit's level is derived from its parents. Referencing (or omitting) a specific pending unit as a parent directly controls whether the new unit's level is guaranteed to be higher (later) or can remain lower (earlier) than that pending unit.
- The bundled oscript example demonstrates the exact vulnerable pattern the external report describes: a privileged address sets `var['rate']` via a `state` message, and subsequent triggers convert bytes to asset (or vice versa) strictly at the currently stored `rate`, with no timelock, no minimum-received check supplied by the caller, and no atomic bundling with the rate-setting unit: [6](#0-5) .
- The same class of exposure applies to any AA that reacts to `data_feed` oracle-price updates for pricing trades in the surrounding cases, since the trigger relying on the new price and the data-feed unit itself are two independent, non-atomic units whose relative processing order is attacker-influenceable via level selection, e.g. `option_contract.oscript`/`futures_contract.oscript` samples reading `data_feed[[oracles=..., feed_name='GBYTE_USD']]`: [7](#0-6) .

### Impact Explanation
An unprivileged AA-trigger sender can guarantee execution ordering relative to a known pending price/rate-changing unit and extract the price delta from the AA's balance (funds belonging to other users/depositors of that AA), exactly mirroring the "steal funds from the LPs" impact of the original report. This is a concrete unauthorized-fund-extraction / AA-fund-loss scenario reachable by any wallet capable of posting a trigger unit to a public AA.

### Likelihood Explanation
Likelihood is High for any AA author who follows the documented/bundled sample pattern of a privileged rate-setter combined with a purely formulaic conversion for other users, since:
- No special privileges are required by the attacker — only the ability to see an unstable/pending unit (readily available, since units are gossiped before stabilization) and choose parents for their own units.
- The mechanism (parent selection controlling level, and level controlling AA-trigger execution order) is a core, well-documented and unavoidable part of ocore's consensus/AA design, not a bug that can be "patched away" without changing execution-order semantics.
- The condition already exists in bundled reference oscript samples, which developers are likely to base real AAs on.

### Recommendation
- For AA authors: avoid single-unit "set the price, everyone else trades at whatever the stored price currently is" patterns. Instead require price/rate updates to include a minimum-received/maximum-paid guard supplied by the trader (slippage protection), analogous to `amountOutMin` patterns, or require a delay (e.g., store `pending_rate` plus `activation_mci`) so a new rate only becomes effective at a future, unpredictable MCI, preventing same-window sandwiching.
- Consider adding oscript/ojson documentation or lint warnings (and updating bundled samples such as `sell_asset_for_bytes.oscript`) to discourage the vulnerable "privileged instant rate change with no timelock/slippage guard" pattern, since it is easy to copy verbatim into production AAs.

### Proof of Concept
1. Deploy (or use) an AA implementing the `sell_asset_for_bytes.oscript` pattern: a privileged address can set `var['rate']` instantly via `trigger.data.exchange_rate`, and any user sending >100000 bytes receives `round(bytes_amount * var['rate'])` of the asset at the currently stored rate.
2. Maintainer broadcasts (but does not yet have stabilized) a unit setting `exchange_rate` from `R1` to `R2 > R1`.
3. Attacker, seeing this pending unit, immediately:
   - Crafts unit A (buy at `R1`): sends bytes to the AA, selecting parents that do **not** include the maintainer's pending unit, so A's `level` is lower/independent and gets ordered for execution before the rate-change unit is applied (or is simply mined and stabilized in an earlier or concurrent MCI position with lower level).
   - Crafts unit B (sell/back-run at `R2`): sends the asset received from A back to the AA (or to a paired sell case), selecting the maintainer's rate-change unit as one of its parents, guaranteeing B's `level` is higher than the rate-change unit and thus B is ordered/executed strictly after the new rate `R2` takes effect.
4. Once all three units stabilize, `handleAATriggers`/`main_chain.js` execute them in `level` order: A processes at `R1`, the rate update takes effect, then B processes at `R2`, letting the attacker realize the difference `(R2-R1)` risk-free at the expense of the AA's balance, identical in effect to the reported `adjustPrice` sandwich.
