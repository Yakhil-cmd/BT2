## Title
Webhook signature verification key is selected via a request field not covered by the signature it validates, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify against using `repository_owner`, which is read from Rails' merged `params` object rather than from the exact bytes (`request.raw_post`) that are both signed and later processed by the event handlers. Because Rails merges query-string parameters over JSON body parameters when building `params`, an attacker can decouple "which secret is checked" from "what payload is actually acted upon," analogous to the referenced report's core flaw: a value used to gate/compute a security check diverges from the value that governs the actual state-changing effect.

### Finding Description
`verify_signature` derives the organization used for secret lookup from `params`, not from the raw body: [1](#0-0) [2](#0-1) 

`repository_owner` is computed via `params.dig('repository', 'owner', 'login')`. Rails' `ActionDispatch::Http::Parameters#parameters` builds `params` as `request_parameters.merge(query_parameters)`, meaning **query-string parameters override JSON body parameters** for colliding keys. This is standard, well-known Rails behavior, not a bug in Rails itself — but it means an attacker fully controls `repository_owner` independently of the actual JSON body, simply by appending `?repository[owner][login]=<org>` to the webhook URL.

Meanwhile, the actual event processing in `create` re-parses the **raw POST body** directly, completely ignoring the query string: [3](#0-2) 

So the two code paths consume two different, independently-controllable sources for the "organization" concept:
- Signature verification: organization derived from attacker-controlled `params` (query string can win).
- Event effect: organization/repository derived from `request.raw_post` JSON body, consumed later by handlers via `payload.dig('repository', 'full_name')`. [4](#0-3) 

`verify_webhook_signature` also short-circuits to `true` whenever an organization's `webhook_secret` is unset/blank: [5](#0-4) 

`config/secrets.development.example.yml` and the docs explicitly document `webhook_secret` as optional (`# nil`), including in multi-organization configurations: [6](#0-5) 

**Binding broken:** `organization_used_for_signature_check == organization_whose_data_is_actually_written` is expected to hold, but an attacker can make `organization_used_for_signature_check` (via query string `repository[owner][login]`) point to any Shipit-configured organization that has no `webhook_secret` configured, while the actual JSON body (used by `create` → handlers) targets a completely different, fully-secured organization/repository.

### Impact Explanation
In any Shipit deployment configured for multiple GitHub organizations (a documented, supported configuration) where at least one configured organization has no `webhook_secret` set, an unauthenticated attacker can forge arbitrary webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) for **any other configured organization/repository**, including ones that do have a secret configured — because the check never actually validates a signature over the org that the payload claims to represent; it validates against whichever org the attacker names via the query string, and that org's check can be trivially bypassed if its secret is blank.

Concrete consequences reachable via handlers acting on a fully forged payload:
- `PushHandler` triggers `stack.sync_github(...)`, which can affect deployability state of a victim stack/branch. [7](#0-6) 
- `MembershipHandler` creates/attaches a `User` to a `Team` based purely on unauthenticated payload content (`team`, `organization`, `member` fields), escalating team membership without any real GitHub verification. [8](#0-7) 

This escalates into `Shipit.github_teams` authorization (adding an attacker-controlled user login to a team that may be checked for access in `Shipit::Authentication#force_github_authentication`), and can corrupt commit/status/deploy state for repositories the attacker does not control — matching the High-severity impact bucket ("escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
Requires no privileged credentials, no session, and no valid webhook secret for the targeted (victim) organization — only that the Shipit instance is configured with at least one additional organization lacking a `webhook_secret`, which is an explicitly documented supported/optional configuration. The bypass itself (query-string parameter override in Rails' merged `params`) is a standard, reliably reproducible HTTP mechanic requiring only a crafted URL and JSON body — no timing windows, no race conditions, and no dependence on the host misconfiguring anything beyond using the officially documented optional `webhook_secret: nil` setting for any one organization.

### Recommendation
- In `WebhooksController#verify_signature`, derive `repository_owner` exclusively from the same source used to process the event (i.e., parse `request.raw_post` once, cache it, and use that parsed JSON for both signature-org selection and event dispatch) — never from `params`, which mixes query string and body.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank without also requiring some other assurance (or make this an explicit, loudly-logged/config-time-warned mode rather than a silent pass); at minimum, require every configured organization in a multi-org setup to have a non-blank `webhook_secret`, and fail startup/validation otherwise.
- After verifying the signature, additionally assert that `repository_owner` used for verification equals the owner login inside the verified raw body, rejecting mismatches.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `victim` (has `webhook_secret: s3cr3t`) and `sandbox` (has `webhook_secret:` left blank/nil), as permitted by the documented multi-org schema.
2. Attacker sends:
   ```
   POST /webhooks?repository[owner][login]=sandbox
   X-Github-Event: membership
   Content-Type: application/json

   {
     "action": "added",
     "team": {"id": 999, "name": "Admins", "slug": "admins", "url": "https://x"},
     "organization": {"login": "victim"},
     "member": {"login": "attacker-github-login"}
   }
   ```
   (No valid `X-Hub-Signature` header needed.)
3. `verify_signature` computes `repository_owner` as `"sandbox"` from the query string (overriding any body value due to Rails' `request_parameters.merge(query_parameters)`), fetches `Shipit.github(organization: "sandbox")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. `create` re-parses `request.raw_post` (the real JSON body referencing `victim`/`organization.login`) and dispatches to `MembershipHandler`, which creates/attaches `attacker-github-login` to team `Admins` under organization `victim` — with no valid signature ever having been checked against `victim`'s actual `webhook_secret`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
