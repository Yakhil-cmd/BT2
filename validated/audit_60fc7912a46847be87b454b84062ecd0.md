### Title
Stack-scoped API token bypasses stack authorization in CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
### Finding Description
`Shipit::Api::BaseController` implements the intended authorization binding "`stack` a token authorises == `stack` it touches" via its `stacks`/`stack` helper methods: any request is expected to be scoped to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` has a `stack_id` set (e.g. the `here_come_the_walrus` fixture, scoped to the `shipit` stack) [1](#0-0) .

`Api::CCMenuController`, however, overrides this `stack` accessor and resolves the target stack directly from `Stack.from_param!(params[:stack_id])`, completely bypassing the `current_api_client.stack_id` scoping performed by the base controller's `stacks` method: [2](#0-1) 

The controller only enforces the generic `require_permission :read, :stack` permission check, i.e. it verifies the token *possesses* the `read:stack` permission string, but never verifies that the requested `stack_id` matches the stack the token is bound to [3](#0-2) . Any `ApiClient` with `read:stack` permission — regardless of its `stack_id` binding — can therefore fetch CCMenu status (build/deploy state) for any stack in the installation by simply passing a different `stack_id` param, or via query-string token as also demonstrated in tests [4](#0-3) .

This is the direct analog of the reported `whenNotPaused` bypass: sibling endpoints (`Api::StacksController`, `Api::CommitsController`, `Api::MergeRequestsController`, etc.) correctly go through the scoped `stacks`/`stack` helper inherited from `BaseController` [5](#0-4) , but `CCMenuController` re-implements the accessor and drops the scoping check — an inconsistency between functions that are supposed to share the same authorization guard, exactly like `restakeGGP`/`claimAndRestake` skipping the `whenNotPaused` modifier applied to their sibling functions `stakeGGP`/`withdrawGGP`.

### Impact Explanation
A stack-scoped `ApiClient` token (e.g. one deliberately created with `read:stack` permission and bound to a single, low-sensitivity stack via `ApiClient#stack_id`, as is the intended design pattern shown by the `CCMenuUrlController#client` helper which creates such minimally-scoped tokens: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)` [6](#0-5) ) can read the build/deploy state (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, lock status, etc., per the test expectations [7](#0-6) ) of **any other stack** in the Shipit installation, including stacks the token holder has no authorization to see. This satisfies the "unauthenticated/unauthorized read of stack state" High-severity impact category defined in scope, because a credential explicitly minted to be readable-only for one stack (a common integration pattern for exposing CI status badges, per the `CCMenuUrlController`) instead grants read access to the state of every stack.

### Likelihood Explanation
High likelihood: the `CCMenuUrlController` in this same engine actively mints exactly this kind of narrowly-scoped, `read:stack`-only token intended for embedding in external CI dashboards (CCTray/CCMenu widgets), which are inherently semi-public/lower-trust integrations. Any holder of such a token (which is designed to be shared with third-party CI status tools) needs only to change the `stack_id` request parameter to pull status data for unrelated stacks — no additional privilege, secret, or session is required beyond the token itself.

### Recommendation
In `Api::CCMenuController`, remove the custom `stack` override and use the inherited, properly scoped `stack`/`stacks` helpers from `Api::BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) so that `current_api_client.stack_id` scoping is enforced consistently with all other API controllers.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to `stack_id` = Stack A, with only `read:stack` permission (mirrors the `here_come_the_walrus` fixture and the pattern used by `CCMenuUrlController#client`).
2. Authenticate as this client and call:
   `GET /api/stacks/{owner}/{repo-of-stack-A}/{env}/ccmenu` — succeeds as expected.
3. Call `GET /api/stacks/{owner}/{repo-of-stack-B}/{env}/ccmenu` (a stack this token is *not* scoped to) using the same token.
4. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!`, the request succeeds and returns Stack B's build/deploy status XML, even though `current_api_client.stack_id` is bound to Stack A only — confirmed by the absence of any `stack_id` filtering in `app/controllers/shipit/api/ccmenu_controller.rb` lines 27-31, contrasted with the scoped implementation in `app/controllers/shipit/api/base_controller.rb` lines 74-80.
