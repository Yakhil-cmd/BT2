### Title
Webhook signature verified against `repository.owner.login`'s secret while handlers act on `repository.full_name`'s repo, enabling cross-organization stack mutation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC using `repository_owner` (`payload.dig('repository','owner','login')`), while `Webhooks::Handlers::Handler#repository_name` (used by `PushHandler`, `MembershipHandler`'s `stacks` helper, PR handlers, etc.) resolves the acted-upon repository via a completely independent JSON key, `payload.dig('repository','full_name')`. In a multi-organization Shipit deployment (`Shipit.github_organizations` with multiple entries, each with its own `webhook_secret`), an attacker who controls one configured organization (OrgA) can forge a JSON body where `repository.owner.login == 'OrgA'` but `repository.full_name == 'OrgB/victim-repo'`, sign it with OrgA's known secret, and have the handler mutate OrgB's `Stack`.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`organization_whose_secret_verified(raw_post) == organization_owning(Repository.from_github_repo_name(repository_name))`

- Signature verification: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` where `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) [2](#0-1) 
- `verify_webhook_signature` only checks that the raw bytes match an HMAC computed with the secret configured for the organization named by `repository_owner` [3](#0-2) . It performs no check that `repository.full_name` starts with that same organization login.
- Handler dispatch then re-parses the same raw body and calls handlers with the full payload [4](#0-3) .
- `Handler#repository_name` reads `payload.dig('repository', 'full_name')` independently and `stacks` looks up `Repository.from_github_repo_name(repository_name)` [5](#0-4) .
- `PushHandler#process` then calls `stack.sync_github` on every matching stack of that resolved repository [6](#0-5) .

Root cause: nothing in the request pipeline enforces that `repository.owner.login` (used to pick the verifying secret) is consistent with `repository.full_name` (used to pick the mutated record). These are two independent leaves of a single attacker-controlled JSON document; GitHub itself always keeps them consistent, but this engine does not re-derive or cross-check one from the other, so a fabricated body sent directly to `POST /webhooks` (bypassing GitHub entirely) can decouple them.

Precondition for exploitability: the deployment must be a **multi-org** Shipit config, i.e., `Shipit.github_organizations` returns more than one org key with distinct `webhook_secret`s (`github_app_config`/`github_default_organization` in `lib/shipit.rb`) [7](#0-6) . The attacker must be one of these configured organizations (OrgA), which they legitimately administer and for which they know their own `webhook_secret`. This is exactly the scenario the question describes. If the deployment uses the single-org/legacy config (`github_default_organization` is `nil`), `repository_owner` is unused for secret selection (falls back to the single `secrets.github` config) and the divergence has no effect, since only one secret exists globally.

Existing guards do not prevent this:
- `drop_unhandled_event` / `check_if_ping` only gate on event type, not payload consistency.
- `ExplicitParameters` schemas (e.g. `PushHandler.params`) validate presence of `ref`/`after`, not repository ownership.
- No model validation cross-checks the webhook's authenticating org against `Repository#full_name`.

### Impact Explanation
For a multi-tenant Shipit instance, an attacker who legitimately controls Organization A (and thus knows its `webhook_secret`) can send forged, signed webhook POSTs naming any other tenant's repository in `repository.full_name`. Depending on event/handler:
- `push` events drive `PushHandler#process` → `stack.sync_github(expected_head_sha: ...)` on the victim org's stacks, i.e., unauthenticated triggering of git sync against another tenant's repository/stack using the attacker's own credentials.
- Other repository-scoped handlers (`pull_request/*`, `status`, `check_suite`, etc.) that key off `repository_name`/`stacks` are similarly exposed to acting on the wrong tenant's `Repository`/`Stack` records.

This matches "a payload for one repository mutating another's stack" — Critical severity — because a signature that only proves knowledge of OrgA's secret is treated as authorization to write into OrgB's `Stack` state. Blast radius: every tenant organization configured in the same Shipit instance is at risk from any other tenant (or any org onboarded to that instance), not just a single pair.

Note: `MembershipHandler` is not affected by this specific divergence — it derives its organization from `params.organization.login` directly (the same field used as `repository_owner` fallback), not from `repository.full_name`, so team membership creation stays bound to the authenticating org [8](#0-7) .

### Likelihood Explanation
- Requires a multi-organization Shipit deployment (config keyed by multiple GitHub org names with independent `webhook_secret`s) — this is a supported and documented configuration mode per `lib/shipit.rb#github_app_config`/`github_organizations`.
- Attacker only needs to control/administer one such organization (OrgA), including installing/configuring a webhook with a secret they choose — a normal, unprivileged action available to any GitHub org owner.
- No Shipit session, API token, or knowledge of any other org's secret is needed.
- The attack is a single crafted HTTP POST to `/webhooks` with a valid `X-Hub-Signature` for OrgA and a `repository.full_name` pointing at OrgB's repo; fully repeatable and scriptable against any repository name already registered as a `Repository` in the shared Shipit instance.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`/`stacks`), enforce that the organization used to select the verifying `webhook_secret` matches the owner segment of `repository.full_name` before dispatching to handlers, e.g. reject (422) when `repository_owner != payload.dig('repository', 'full_name')&.split('/')&.first`. Prefer deriving `repository_owner` solely from `full_name` (single source of truth) rather than trusting the separate `owner.login` field.

### Proof of Concept
Minitest plan (extends existing `test/controllers/webhooks_controller_test.rb`/handler tests):
1. Configure two orgs in test secrets: `OrgA` with `webhook_secret: 'secretA'`, `OrgB` with `webhook_secret: 'secretB'`, ensuring `Shipit.github_organizations` includes both.
2. Create `repository = Repository.create!(owner: 'OrgB', name: 'victim-repo')` and an associated `stack` with `branch: 'master'`.
3. Build payload: `{ "ref" => "refs/heads/master", "after" => "deadbeef", "repository" => { "owner" => { "login" => "OrgA" }, "full_name" => "OrgB/victim-repo" } }`.
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', 'secretA', body)` — i.e., attacker-computable using only OrgA's known secret.
5. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: signature`.
6. Assert:
   - Left side of binding: `Shipit.github(organization: 'OrgA').verify_webhook_signature(signature, body)` returns `true` (attacker-controlled org verified the bytes).
   - Right side of binding: `Webhooks::Handlers::Handler.new(JSON.parse(body)).send(:repository_name)` resolves to `'OrgB/victim-repo'` — a different organization than the one that verified the signature.
   - Response status is `200`/`head :ok` (not `422`), proving no cross-check rejects the mismatch.
   - `stack.reload` shows `sync_github` was invoked (e.g., stub/mock `Stack#sync_github` and assert it was called with `expected_head_sha: 'deadbeef'` on OrgB's stack) despite the request only being authenticated as OrgA.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
