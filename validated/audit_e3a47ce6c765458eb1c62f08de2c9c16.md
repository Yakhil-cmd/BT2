### Title
Hash Collision via Undelimited Field Concatenation in Contract Hash Functions - (File: `arbiter_contract.js`, `prosaic_contract.js`)

### Summary
`arbiter_contract.js` and `prosaic_contract.js` compute a content-identifying `hash` for peer-to-peer contracts by concatenating variable-length, attacker/counterparty-controlled string fields (`title`, `text`, party names, etc.) with no delimiter or length prefix before hashing. This mirrors the reported `Mimc.hash` bug class: because field boundaries are not encoded in the hashed byte stream, different logical contract contents can serialize to the identical byte string and therefore produce the identical hash, breaking the hash's role as a unique/integrity commitment to the contract text.

### Finding Description
`prosaic_contract.getHash`/`getHashV1` compute:
```
crypto.createHash("sha256").update(contract.title + contract.text + contract.creation_date, "utf8").digest("base64")
``` [1](#0-0) 

`title` and `text` are free-form strings supplied when creating/accepting a prosaic contract offer over the device-messaging channel [2](#0-1) , with no separator between them. Shifting characters across the `title`/`text` boundary (e.g. `title="Pay100", text="ToBob"` vs `title="Pay10", text="0ToBob"`) yields the exact same concatenated string `"Pay100ToBob"+creation_date`, hence the exact same `hash`.

`arbiter_contract.getHashSrc` has the same flaw for its legacy branch, which is the currently-active branch since `exports.NEW_HASH_DATE = '2026-11-01'` has not yet been reached:
```
const src = contract.creation_date > exports.NEW_HASH_DATE
    ? [...].join(exports.DELIMITER)          // fixed path, not yet active
    : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");  // active path, no delimiter
``` [3](#0-2) 

The code base's own author later recognized this exact bug class and fixed it for arbiter contracts by introducing `exports.DELIMITER = "[|#|]"` for a future cutover date [4](#0-3) , but (a) the fix is not yet in effect (today's date is before `NEW_HASH_DATE`), and (b) `prosaic_contract.js`'s `getHash`/`getHashV1` were never patched at all.

This `hash` is not a cosmetic identifier — it is used as the primary lookup key for the contract (`getByHash`) and, critically, is embedded on-chain as `contract_text_hash` inside a unit's `data` message; `handleReceivedSigningUnit` validates the contract by comparing `payload.contract_text_hash` against the locally stored `contract.hash` [5](#0-4) . The hash is meant to bind the exact `title`/`text` the parties agreed to before a signing unit is posted.

### Impact Explanation
Because field boundaries are not delimited, a counterparty (the "peer" in a prosaic or arbiter contract exchange, or someone controlling the contract text at offer/accept/dispute time) can construct two different `(title, text)` pairs — e.g., one showing innocuous terms and one embedding different payment terms/obligations — that concatenate to the identical byte string and therefore share the identical `hash`/`contract_text_hash`. Since the on-chain `data` message and the wallet's persisted contract row are both keyed and integrity-checked only by this collision-prone hash, a party can present a benign contract for review/signature while a colliding variant with different terms validates against the same `contract_text_hash` on-chain, or can later substitute the locally stored `title`/`text` without invalidating the hash check in `handleReceivedSigningUnit`. In an arbitrated payment flow (funds held in a shared address released per arbiter decision based on contract terms), this undermines the non-repudiation guarantee the hash is designed to provide and can be leveraged to dispute or justify fund release under terms different from what was actually hashed/agreed, resulting in fund loss/freezing for one of the parties.

### Likelihood Explanation
Both `title` and `text` are attacker/counterparty-supplied free text with no format restriction, and constructing a boundary-shift collision requires no cryptographic effort — it is a simple string-splitting exercise, identical in spirit to the reported `Mimc.hash` example. The vulnerable code path in `arbiter_contract.js` is the currently active default (pre-`NEW_HASH_DATE`), and the vulnerable functions in `prosaic_contract.js` have no fix scheduled at all, making exploitation straightforward for any party engaging in a prosaic/arbiter contract negotiation.

### Recommendation
Use a length-prefixed or delimiter-based (with delimiter-escaping/rejection, as already done in `string_utils.getSourceString` via `STRING_JOIN_CHAR` and its `includes` checks [6](#0-5) ) serialization for all fields before hashing in `prosaic_contract.getHash`/`getHashV1` and in `arbiter_contract.getHashSrc`'s legacy branch. Ideally, replace both with the already-existing `objectHash`/`getSourceString` utilities that guarantee unambiguous serialization, and remove/backport the `DELIMITER`-based fix in `arbiter_contract.js` immediately rather than gating it behind a future date.

### Proof of Concept
```js
const crypto = require('crypto');
function getHash(contract) {
  return crypto.createHash("sha256")
    .update(contract.title + contract.text + contract.creation_date, "utf8")
    .digest("base64");
}

const date = "2026-01-01 00:00:00";
const c1 = { title: "Pay100", text: "ToBob",  creation_date: date };
const c2 = { title: "Pay10",  text: "0ToBob", creation_date: date };

console.log(getHash(c1) === getHash(c2)); // true — different contracts, identical hash
```
Both contracts serialize to the same string `"Pay100ToBob2026-01-01 00:00:00"`, producing identical `hash`/`contract_text_hash`, confirming the collision analogous to the reported `Mimc.hash` bug.
