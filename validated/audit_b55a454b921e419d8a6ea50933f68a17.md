Analog found: `WebhooksController` verifies a webhook's signature using the GitHub organization derived from `params.dig('repository','owner','login')` (or `organization.login`), but the handlers that execute repository-scoped writes look up the target repository/stacks using a completely independent field, `payload.dig('repository','full_name')`. These two fields live in the same attacker-influenced JSON body, and nothing ties them together after signature verification succeeds.

### Title
Webhook signature is verified against the organization in `repository.owner.login`, but stack writes are keyed off the unrelated `repository.full_name` field, allowing cross-organization/repository writes - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) [2](#0-1) . Once the signature is accepted, the raw parsed payload is dispatched unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) . Every handler (e.g. `PushHandler`) then resolves the target `Repository`/`Stack` set using a *different* field of the same payload: `payload.dig('repository', 'full_name')` via `Handler#repository_name` / `Handler#stacks` [4](#0-3) , and `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack on that branch [5](#0-4) .

Because the signature check and the repository-resolution step read two independent JSON keys, an attacker who can produce a validly-signed webhook body for *any* organization configured in Shipit (i.e. `repository.owner.login`/`organization.login` = OrgA, whose secret they know or control) can set `repository.full_name` to `OrgB/other-repo`, a completely different, unrelated repository/tenant tracked by the same Shipit instance. `verify_signature` will authenticate the request as "from OrgA" and let it through, but the handler will act on OrgB's stack.

### Finding Description
The trust binding that should hold is:
`organization authenticated by verify_webhook_signature == organization owning the repository whose Stack records get mutated`

Before the attacker's request: this equality holds implicitly only because in the intended usage a GitHub-originated webhook's `repository.owner.login` and `repository.full_name` always describe the same repository — GitHub itself constructs the payload.

After the attacker's request: the attacker fully controls the raw HTTP body (`request.raw_post`) that is JSON, so they control both `repository.owner.login` (used only for signature-organization lookup) and `repository.full_name` (used for the actual repository/stack lookup) independently. `Shipit.github(organization: repository_owner)` merely selects which configured `GithubApp`/secret is used to `verify_webhook_signature`; it plays no role afterward in constraining which repository the handler code is allowed to touch [1](#0-0) . The handler dispatch path never re-checks that `repository.full_name` belongs to `repository.owner.login`/`organization.login`.

This breaks the "organization authenticated vs repository written" binding described in the analog rules: the field that is cryptographically covered (implicitly, by virtue of which secret validated the HMAC) is the organization login, but the field actually acted upon by application logic (`full_name`) is a sibling field never itself covered by any binding check.

### Impact Explanation
If exploitable, this lets an attacker who controls (or has been given webhook access/secret for) one organization/repository onboarded into a shared Shipit instance forge webhook events (`push`, `pull_request`, `status`, `check_suite`, `membership`, etc.) that are accepted as authentic and then act on a victim organization's/repository's `Stack` records — e.g. forcing `sync_github` calls, injecting commit statuses, or manipulating pull-request/merge-queue state for a repository they do not own. This is a cross-repository/cross-tenant write achieved purely by crafting payload JSON, matching the "cross-repository writes" Critical impact category, and requires no repository write access or privileged Shipit account on the victim tenant.

### Likelihood Explanation
Exploitability depends entirely on whether a single Shipit deployment is configured to serve **multiple** GitHub organizations/tenants with **per-organization** `webhook_secret`s such that an attacker legitimately possesses or can obtain the secret for at least one onboarded organization (e.g. they administer a repo that was added to this Shipit instance). In a single-tenant Shipit install where only one organization/secret is configured, `Shipit.github(organization: ...)` always resolves to the same app regardless of the `repository_owner` value, so the practical blast radius is limited to repositories within that same GitHub App's scope. I could not fully verify from the available files whether/how multiple distinct organizations with independent secrets are configured (`Shipit.github` resolution logic and any per-organization app registry were not fully inspected in this pass), so likelihood in a typical single-org deployment is low; in a genuinely multi-tenant deployment it is high.

### Recommendation
After signature verification, re-derive/validate the organization that will be acted upon strictly from the signature-authenticating field, or verify that `repository.owner.login`/`organization.login` matches the owner implied by `repository.full_name` before invoking handlers. Alternatively, resolve the target `Repository`/`Stack` using the authenticated organization context (the one used to fetch the signing secret) rather than trusting `repository.full_name` verbatim from the unauthenticated-until-verified payload body.

### Proof of Concept
1. Attacker controls (or is granted webhook delivery for) organization `attacker-org`, which is configured in this Shipit instance with `webhook_secret` `S`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S, body)>` — a valid signature, since `verify_signature` looks up `Shipit.github(organization: "attacker-org")` per `repository_owner` [1](#0-0)  and that check passes with the attacker's own known secret.
4. `WebhooksController#create` dispatches the parsed params to `PushHandler.call(params)` [3](#0-2) .
5. `Handler#repository_name` reads `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, resolving stacks for the victim repository [4](#0-3) , and `PushHandler#process` calls `stack.sync_github(expected_head_sha: "deadbeef")` on the victim's `master`-branch stack [5](#0-4) , even though the signature only proved the request came from `attacker-org`.
