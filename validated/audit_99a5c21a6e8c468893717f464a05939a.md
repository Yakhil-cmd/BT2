### Title
Webhook membership handler trusts an unverified `organization` field, allowing authentication-bypass via forged team membership - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to check the HMAC signature against using the `repository.owner.login` (falling back to `organization.login`) field of the incoming payload. This "verified organization" is not the same value that the `membership` event handler actually acts on: `MembershipHandler#find_or_create_team!` and `#process` use the payload's own `organization.login` / `team.id` / `member.login` fields directly, without re-checking that they belong to the organization whose secret validated the request. Because signature verification is skipped entirely for any configured GitHub organization that has no `webhook_secret` set (a documented, valid configuration), an attacker can forge a `membership` webhook that is "signed" against a secret-less organization while writing team membership for a completely different organization — including the organization(s) listed in `Shipit.github_teams`, which gate application authorization.

### Finding Description
Signature verification and payload processing consume different, attacker-controlled fields from the same JSON body without binding them together:

- `verify_signature` selects the HMAC key by organization: `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`. [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` short-circuits to `true` when the selected organization has no `webhook_secret` configured: [3](#0-2) 

- `webhook_secret` is an explicitly optional setting ("If you've set a webhook secret ... you should copy it here"), and the shipped examples for dev/test even ship with it `nil`: [4](#0-3) [5](#0-4) 

- Once past this gate, `MembershipHandler` creates/updates a `Team` and its `Membership` using the payload's own `organization.login`, `team.id`, and `member.login` — none of which are cross-checked against the organization that was actually verified: [6](#0-5) 

- Application authorization is derived directly from `Team`/`Membership` rows created this way: `User#authorized?` checks membership in `Shipit.github_teams`, which are `Team` records resolved by `organization/slug` handle: [7](#0-6) [8](#0-7) [9](#0-8) 

- `force_github_authentication` gates the entire application on `current_user.authorized?`: [10](#0-9) 

**Binding that should hold:** `verified_organization` (the org whose `webhook_secret` produced a passing HMAC check) `== acted_organization` (the org whose `Team`/`Membership` the handler mutates). The engine never enforces this equality; both are independently attacker-supplied JSON fields (`repository.owner.login` vs. top-level `organization.login`), and `check_if_ping`/`verify_signature` never inspects `organization.login`'s relationship to `repository.owner.login`.

**Before the attack:** In legitimate GitHub-delivered webhooks, `repository.owner.login` and `organization.login` are always the same organization that owns the webhook and its secret, so the binding holds implicitly.

**After the attack:** An attacker who knows/controls no secret for the target org can still craft a payload where `repository.owner.login` (used for signature selection) points to any Shipit-configured organization with `webhook_secret` unset, while `organization.login` (used to write team membership) points to the organization backing `Shipit.github_teams`. The signature check passes trivially, and the handler executes the write against the unrelated, victim organization/team.

### Impact Explanation
This breaks the "GitHub identity/organization authenticated vs. the organization/team actually written" binding described in scope, and lets an unauthenticated network attacker plant a `Membership` row linking an arbitrary `login` to a `Team` that backs `Shipit.github_teams`. Since `User#authorized?` is computed purely from that `Membership`/`Team` association [7](#0-6) , this is a direct escalation into `Shipit.github_teams` authorization / authentication bypass for the entire Shipit instance (viewing stacks, task streams, and — since deploys/rollbacks are gated behind the same `authorized?` check — ultimately unauthorized deploy/rollback capability), matching the in-scope Critical/High impact categories.

### Likelihood Explanation
Likelihood is Medium: it requires (1) the Shipit deployment to host more than one GitHub organization (multi-tenant `github:` config, which the engine explicitly supports and documents), and (2) at least one of the configured organizations to have `webhook_secret` unset — a state the documentation treats as optional/acceptable and the project's own bundled dev/test config templates ship that way. Given that, no credentials, tokens, or repository access are required — only a POST to the public webhooks endpoint.

### Recommendation
- In `MembershipHandler` (and any other handler keyed on an "organization"/"repository" field), re-derive the acting organization from the same value used for signature verification (`repository_owner` in the controller) and reject/ignore the event if it disagrees with the payload's own `organization.login`/`repository.owner.login`.
- Do not allow `verify_webhook_signature` to silently pass (`return true unless webhook_secret`) for organizations used to grant authorization (`Shipit.github_teams`); require a webhook secret to be configured for any organization contributing to authorization decisions, or reject membership events from organizations with no configured secret.
- Consider validating that `team.id`/`organization.login` in `membership` events actually correspond to a team fetched live via the GitHub API for the verified organization, rather than trusting the payload's embedded team attributes wholesale.

### Proof of Concept
Preconditions: Shipit is configured with two organizations, e.g. `NoSecretOrg` (no `webhook_secret`) and `RealOrg` (backs `Shipit.github_teams`, has a `Team` with `github_id: 999`, `organization: "RealOrg"`, `slug: "developers"`).

1. Attacker (or victim, to bootstrap their own `login`) logs into Shipit once via GitHub OAuth so a `Shipit::User` row exists with `login: "attacker"`.
2. Attacker POSTs to the webhooks endpoint:
```
X-Github-Event: membership
Body:
{
  "action": "added",
  "team": {"id": 999, "name": "Developers", "slug": "developers", "url": "https://api.github.com/teams/999"},
  "organization": {"login": "RealOrg"},
  "member": {"login": "attacker"},
  "repository": {"owner": {"login": "NoSecretOrg"}}
}
```
3. `verify_signature` resolves `repository_owner` = `"NoSecretOrg"` [2](#0-1) , looks up `NoSecretOrg`'s `GitHubApp`, and `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank [11](#0-10) .
4. `MembershipHandler#process` runs using `organization.login = "RealOrg"` and `team.id = 999`, finds the existing `RealOrg/developers` team, and calls `team.add_member(User.find_or_create_by_login!("attacker"))` [6](#0-5) .
5. Attacker's existing session now satisfies `current_user.authorized?` via membership in `RealOrg/developers`, bypassing the intended GitHub-team gate [7](#0-6) [12](#0-11) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
