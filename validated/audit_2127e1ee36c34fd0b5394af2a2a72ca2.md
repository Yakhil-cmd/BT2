### Title
Git pathspec magic injection via unsanitized touched-file names allows diff-scope escape - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`get_git_diff` restricts its `git diff` call to a set of repo-relative paths built by `_diff_pathspec`, but those relative path strings are spliced verbatim as separate `git diff -- <pathspec>` arguments without disabling git's pathspec "magic" syntax. A file whose relative path begins with `:` (e.g. `:(exclude)`, `:(glob)`, `:(icase)`, `:!`, `:/`) is not treated as a literal filename by git but as a pathspec magic signature, letting an attacker-influenced filename widen or subvert the intended path restriction while still executing inside the correct repo/toplevel.

### Finding Description
`_diff_pathspec` (plugins/security-guidance/hooks/gitutil.py:70-88) correctly guards against the *repo-escape* case: it takes `os.path.realpath` of both `cwd` and each candidate path and drops any path whose relative form starts with `..`, which defeats symlink/`..`-based attempts to point the pathspec at files outside the repository. That part of the invariant ("never escape the intended repo target" at the filesystem/repo level) holds.

However, the surviving relative path strings are passed straight through to `git diff` as pathspec tokens after `--`: [1](#0-0) 
Git pathspecs are not plain strings — a component beginning with `:` is parsed as a magic signature (long form `:(exclude)`, `:(glob)`, `:(icase)`, `:(top)`, `:(literal)`, or short form `:!`, `:/`, etc.). Because `_diff_pathspec` never checks for or escapes a leading `:` in the computed relative path, a file that lands in the repo with a name whose repo-relative path starts with `:` is reinterpreted by git as pathspec magic instead of matched literally.

`get_git_diff`'s whole purpose in the "restrict to specific touched paths" call sites (per its own docstring, "If `paths` is given, the diff is restricted to those paths") is to scope the diff shown to the LLM reviewer/commit-review flow to only the files that were actually touched in the session. If one of those touched files has a magic-prefixed relative name, the pathspec list effectively stops being a precise allow-list:
- `:(glob)**` / `:(icase)*` style magic can broaden matching well beyond the intended file, pulling unrelated repo content into the diff that gets fed to the review LLM (`review_api.py`) — an unintended disclosure of code/diff to that sink.
- `:!<other-file>` (exclude magic) or a bogus glob can instead cause the intended file's own changes to be silently dropped from the pathspec match, letting a malicious edit evade the restricted review entirely, which subverts the "diff scoping must never escape the intended target" invariant in the opposite direction (under- rather than over-inclusion).

Because filenames are ordinary bytes on POSIX filesystems, `:` and `(`/`)` are legal filename characters, so a file created via any normal write path (including one driven by prompt-injected repo content instructing an agent to create such a file) can realize this string.

### Impact Explanation
This breaks the stated invariant that git path scoping must never escape the intended repo diff target: the pathspec restriction can be turned, via ordinary repo-controlled filenames, into either (a) a much broader match that discloses unrelated file diffs to the review LLM call, or (b) an exclude/glob pattern that removes the intended file from the reviewed diff, letting malicious changes bypass the security review the whole hook exists to perform. Both are within the "diff/local file disclosure to an unintended sink" and "review/export logic" impact categories called out for this bounty.

### Likelihood Explanation
Exploitation requires only the ability to get a file with a `:`-prefixed repo-relative path into the working tree before the Stop-hook/commit-review diff collection runs (e.g. via any tool call that creates/renames a file to such a name, potentially triggered by repo-embedded instructions). No elevated privileges, admin access, or leaked credentials are needed — this is squarely within the "unprivileged attacker, repo-controlled content" model. The `..`/symlink checks in `_diff_pathspec` do not touch this class of input at all, so nothing in the current code path stops it.

### Recommendation
Disable pathspec magic for all programmatically-derived paths before splicing them into the `git diff` command: either invoke git with `-c core.pathspecCompat=literal` / global `--literal-pathspecs` flag, or explicitly prefix each computed relative path with the `:(literal)` magic (`f":(literal){r}"`) in `_diff_pathspec`. Prefer `--literal-pathspecs` (or equivalently `GIT_LITERAL_PATHSPECS=1`) added to `GIT_CMD`/the specific `git diff` invocation in `get_git_diff`, so every path in the pathspec list is matched byte-for-byte with no magic interpretation, regardless of its leading characters.

### Proof of Concept
Unit test plan for `plugins/security-guidance/hooks/gitutil.py`:
1. Create a temp git repo with two tracked files: `a.py` (the "intended" file) and `secret/b.py` (an unrelated file that must stay out of scope).
2. Commit both, then modify both files' contents.
3. Create/rename a third file so that its repo-relative path is literally `:(glob)**` (or `:!secret/b.py`) and stage it as one of the `paths` passed into `get_git_diff(cwd, baseline_sha, paths=[os.path.join(cwd, "a.py"), os.path.join(cwd, ":(glob)**")])`.
4. Call `get_git_diff` and assert:
   - Expected (secure) behavior: the returned diff contains only `a.py`'s changes, never `secret/b.py`.
   - Observed (vulnerable) behavior: the returned diff also contains `secret/b.py`'s changes (over-broad match) or omits `a.py`'s changes entirely (exclude magic), demonstrating the pathspec restriction was subverted by the crafted filename.
5. Regression-check the fix by re-running the same test after adding `--literal-pathspecs` to the `git diff` invocation and confirming the diff is scoped exactly to `a.py`.
