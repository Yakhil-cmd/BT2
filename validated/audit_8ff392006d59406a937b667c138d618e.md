### Title
Signature verification keys on `repository.owner.login`/`organization.login` while all webhook handlers act on `repository.full_name`, allowing cross-organization stack manipulation - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-tenant Shipit deployments (multiple GitHub organizations configured under `secrets.github`, each with its own `webhook_secret`), the webhook signature check selects the signing key using one payload field, while every event handler dispatches writes based on a different payload field. An attacker who legitimately knows one organization's `webhook_secret` (e.g., the admin of an org that self-configures its own GitHub App in a shared Shipit instance) can forge a POST to `/webhooks` whose HMAC is valid for "their" org, but whose `repository.full_name` points at a repository belonging to a different, unrelated organization tracked by the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to verify against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`): [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a per-organization config (and thus a per-organization `webhook_secret`) via `github_app_config`, confirming that different orgs in the same instance can have distinct secrets: [3](#0-2) 

However, once the signature check passes, `WebhooksController#create` dispatches the *entire raw payload* to handlers, and every handler resolves the target repository/stack using `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` simply splits the attacker-controlled `full_name` string on `/` and does a DB lookup — there is no cross-check that the resolved repository's `owner` matches `repository.owner.login` (or the organization key used to select the webhook secret): [7](#0-6) 

Since these two fields — `repository.owner.login` (used to pick the verification key) and `repository.full_name` (used to pick the target repository/stack) — are independent, attacker-supplied JSON keys, a raw HTTP POST to `/webhooks` is not constrained to keep them consistent, unlike genuine GitHub-issued webhooks.

### Impact Explanation
This breaks the intended binding: *"the organization that authenticated" == "the repository that is written."* An attacker who is the legitimate administrator of Organization A (and therefore knows Org A's `webhook_secret`, since in the documented multi-org config schema each org's own GitHub App owner supplies that secret) can craft a payload where:
- `repository.owner.login` = `"org-a"` (or `organization.login` = `"org-a"`) → signature verified against Org A's secret, which the attacker legitimately knows.
- `repository.full_name` = `"org-b/critical-repo"` → the handler resolves and mutates Org B's `Stack`/`Repository` records.

For the `push` event this triggers `GithubSyncJob` for Org B's stack with an attacker-chosen `after` SHA via `PushHandler#process` (`stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }`), letting an Org A actor drive sync/deploy-eligibility state for a stack it has no legitimate relationship to. Other handlers keyed off `repository.full_name` (status, check_suite, pull_request family) are equally reachable, enabling cross-organization interference with deploy readiness and review-stack lifecycle (archive/unarchive, provisioning) for repositories the attacker does not own. This is a cross-organization/cross-repository write performed under another tenant's trust boundary, matching the required "cross-repository writes" impact class.

### Likelihood Explanation
This requires a Shipit instance configured with the documented multi-organization `github:` schema (explicitly supported and documented, see `config/secrets.development.shopify.yml` and `docs/setup.md`), and requires the attacker to be a legitimate (but unprivileged relative to Org B) owner/admin of at least one configured organization on the same shared instance — a realistic scenario for shared/self-service internal deploy platforms. No GitHub webhook delivery is actually needed; the attacker directly POSTs to the public `/webhooks` endpoint with a self-computed HMAC.

### Recommendation
After signature verification, assert that the organization used to select the verification key is consistent with the resolved repository's actual owner (e.g., re-derive/verify `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.owner == repository_owner` or equivalent) before dispatching to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `app/controllers/shipit/webhooks_controller.rb`, rejecting the request (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md` multi-org schema).
2. As the legitimate holder of `org-a`'s `webhook_secret`, compute `sha1=HMAC(secret_a, body)` over a crafted push payload body where:
   - `body["repository"]["owner"]["login"] = "org-a"`
   - `body["repository"]["full_name"] = "org-b/critical-repo"`
   - `body["ref"] = "refs/heads/master"`, `body["after"] = "<attacker chosen sha>"`
3. POST this body to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and verifies successfully against `secret_a`.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("org-b/critical-repo")` and enqueues `GithubSyncJob` for Org B's stack with the attacker-chosen `expected_head_sha`, despite the request never being authenticated for Org B.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
