### Title
Webhook signature verified against the org named in `repository.owner.login`, while push handling resolves the target stack from `repository.full_name` — allowing cross-repository `GithubSyncJob` writes ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks the GitHub App/secret to verify the HMAC using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')`. But the push handler resolves which `Stack` to mutate using a completely different, independently attacker-controlled field: `payload.dig('repository', 'full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`. Because the JSON body is a single POST that the attacker fully controls, these two fields can point at different organizations, so a signature valid for OrgOne's webhook secret authorizes a mutation against OrgTwo's stack.

### Finding Description
The binding that must hold is: **organization whose secret verified the signature bytes == organization owning the repository whose stack the handler mutates**, i.e. `params.dig('repository','owner','login') == payload.dig('repository','full_name').split('/').first`. This binding is never enforced.

- `verify_signature` in [1](#0-0)  calls `Shipit.github(organization: repository_owner)` and verifies the raw POST body against that organization's `webhook_secret`.
- `repository_owner` is defined as [2](#0-1) , reading only `repository.owner.login` (or `organization.login`) from the body.
- After verification, `#create` re-parses the same raw body and dispatches to handlers: [3](#0-2) .
- `Shipit::Webhooks::Handlers::PushHandler#process` resolves the target stacks via the base `Handler#stacks`/`#repository_name`, which reads a *different* field — `repository.full_name` — not `repository.owner.login`: [4](#0-3) , and [5](#0-4) .
- `Repository.from_github_repo_name` naively splits `full_name` on `/` and looks the repository up directly: [6](#0-5) .

Attacker request: attacker owns/controls an org "OrgOne" registered in Shipit's GitHub config (has legitimate access to OrgOne's `webhook_secret` since it's their own org's webhook). They POST to `/webhooks` with header `X-Github-Event: push`, a valid `X-Hub-Signature` computed over the raw body using OrgOne's secret, and a JSON body:
```json
{"repository":{"owner":{"login":"OrgOne"},"full_name":"OrgTwo/private-repo"},"ref":"refs/heads/master","after":"<sha>"}
```
`verify_signature` computes `repository_owner` = `"OrgOne"`, fetches OrgOne's `GithubApp`, and successfully verifies the signature (it was legitimately computed with OrgOne's secret over these exact bytes). Nothing re-checks that `full_name`'s owner also equals `"OrgOne"`. `#create` then dispatches to `PushHandler`, whose `repository_name` reads `"OrgTwo/private-repo"` from the same payload, looks up that `Repository`/`Stack`, and calls `stack.sync_github(expected_head_sha:)`, enqueuing `GithubSyncJob` for OrgTwo's stack — a job that will fetch commits and write `Commit` records for a repository never authenticated by this request.

None of the listed guards prevent this: `drop_unhandled_event` only checks the event name exists; the `ExplicitParameters` schema for `PushHandler` only requires `ref` and `after`, not repository owner consistency; there is no `force_github_authentication`/`User#authorized?`/`require_permission!` check in this webhook path (webhooks are meant to be verified by signature alone); `Repository` model validations only constrain character format, not cross-field consistency with the request that authenticated it.

### Impact Explanation
An attacker with a legitimate GitHub webhook secret for **any one** organization configured in `Shipit.github` (e.g., their own org that has a Shipit stack) can force `GithubSyncJob` — and by extension commit ingestion/cache invalidation — to run against **any other** organization's stack/repository configured in the same Shipit instance, as long as they can guess or discover the `full_name` of a tracked private repo. This is a cross-repository/cross-tenant write triggered by a payload that was never authenticated for the target repository, matching the "Critical: a payload for one repository mutating another's stack/commit" impact category. It is repeatable against any stack in the Shipit instance and is not limited to a single request.

### Likelihood Explanation
Preconditions are modest: Shipit must be configured with multiple GitHub organizations/apps (the multi-org `Shipit.github(organization:)` pattern), and the attacker needs a valid `webhook_secret` for at least one configured organization — which they can legitimately have if they administer a webhook for their own org's repo tracked by the same Shipit instance. No Shipit session, API token, or GitHub credentials for the victim org are required. The attacker only needs to know (or guess) the target repository's `owner/name`. This is a low-cost, fully repeatable, unauthenticated-relative-to-the-target attack.

### Recommendation
Enforce that the organization used to verify the signature matches the organization that owns the repository actually being mutated. Concretely, derive `repository_owner` from the same `full_name` field the handlers use (e.g., `full_name.split('/').first`), or after verification, re-validate that `payload.dig('repository','full_name')`'s owner matches `repository_owner` before dispatching to handlers, rejecting the request (422) on mismatch.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "push payload with mismatched repository.owner.login and repository.full_name enqueues GithubSyncJob for the wrong org's stack" do
  org_one_app = mock('org_one_github_app')
  org_one_app.stubs(:verify_webhook_signature).returns(true)
  Shipit.stubs(:github).with(organization: 'OrgOne').returns(org_one_app)

  org_two_repo = Repository.create!(owner: 'orgtwo', name: 'private-repo')
  org_two_stack = Stack.create!(repository: org_two_repo, branch: 'master', environment: 'production')

  body = {
    repository: { owner: { login: 'OrgOne' }, full_name: 'OrgTwo/private-repo' },
    ref: 'refs/heads/master',
    after: 'deadbeef'
  }.to_json

  request.headers['X-Github-Event'] = 'push'
  request.headers['X-Hub-Signature'] = 'sha1=irrelevant-because-stubbed'

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: org_two_stack.id, expected_head_sha: 'deadbeef']) do
    post :create, body: body, as: :json
  end
  assert_response :ok
end
```
This asserts both sides of the claimed binding explicitly: signature verification is stubbed to succeed only for `organization: 'OrgOne'` (the side that authenticated the bytes), while the enqueued job's `stack_id` belongs to `OrgTwo`'s stack (the side actually mutated) — demonstrating they diverge.
