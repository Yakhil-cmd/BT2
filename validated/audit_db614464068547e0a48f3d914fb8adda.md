### Title
Webhook signature verification uses `repository.owner.login` while event dispatch uses the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against based on `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body. Every `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves *which* `Repository`/`Stack` the event actually acts on using a completely different field of that same body: `repository.full_name` (`Handler#repository_name`). Nothing ties these two independently-read fields together, so the organization whose secret authenticated the request is not guaranteed to be the organization whose stack gets mutated.

### Finding Description
`WebhooksController#verify_signature` does: [1](#0-0) 

with `repository_owner` computed as: [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a *specific* per-organization `GithubApp` instance, each configured with its own `webhook_secret` (Shipit explicitly supports multi-organization configuration, see `config/secrets.development.example.yml` lines 18-38 and `docs/setup.md` lines 100-142). `verify_webhook_signature` only checks the signature against whichever organization's secret was picked by that attacker-controlled `repository_owner` field: [3](#0-2) 

Once the signature check passes, `create` dispatches the parsed JSON straight to handlers: [4](#0-3) 

But every handler determines the target `Repository`/`Stack` using a **different** JSON key, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

`Repository.from_github_repo_name` then does a case-insensitive lookup purely on that string: [6](#0-5) 

The binding that should hold is: `organization used to select the verifying webhook_secret == organization embedded in repository.full_name used to select the acted-upon Repository`. Because both values are read independently from the same unauthenticated body, and the HMAC only certifies "these raw bytes were signed by *some* configured org's secret," an attacker who legitimately controls (or otherwise obtains a signature for) **any one** configured organization's webhook secret can submit a payload where `repository.owner.login` names their own org (making `verify_signature` pass) while `repository.full_name` names a completely different, victim organization's repository. `PushHandler`, for example, would then run: [7](#0-6) 

against the victim's `Stack`, i.e. `stack.sync_github(expected_head_sha:)` is invoked on a stack that belongs to an organization the request was never actually authenticated for.

### Impact Explanation
This breaks the authentication boundary between "the organization whose credentials signed this webhook" and "the repository/stack that is mutated as a result," matching the required analog category exactly ("an organization that authenticated versus the repository that is written"). In a Shipit installation configured with multiple GitHub organizations (a supported and documented configuration), an entity that only controls one organization's webhook secret can forge events that act on stacks belonging to a different organization, forcing unscheduled resyncs (`GithubSyncJob`) and — if `continuous_deployment` is enabled on the targeted stack — potentially forcing an unauthorized deploy cycle to run against a stack it has no legitimate relationship to. I was not able to fully trace `Stack#sync_github`'s downstream effect on automatic deploy triggering within the available tool budget, so the exact extent to which this forces an actual `Deploy` (versus merely an unauthenticated forced resync/refresh) is not fully confirmed and should be verified against `app/models/shipit/stack.rb`.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (explicitly documented/supported) and requires the attacker to possess a valid webhook secret for at least one configured organization — which is a materially different, and much weaker, precondition than requiring credentials for the *victim* organization. Given the engine ships this multi-org pattern as a first-class documented feature, this is a realistically reachable misconfiguration-independent code path, not a theoretical one.

### Recommendation
Bind the two lookups together: after resolving the `Repository` via `full_name`, `WebhooksController#verify_signature` (or the handler dispatch layer) should re-derive `repository_owner` from that same resolved `Repository#owner` and confirm it matches the organization whose secret verified the signature, rejecting the request otherwise. Alternatively, verify the signature using the organization owning the `full_name`-resolved repository rather than the raw, independently-controlled `repository.owner.login` field.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret `S_A`) and `victim-org` (secret `S_V`), each with its own Stack (as supported by the multi-org config schema in `docs/setup.md`).
2. Craft body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<any-sha>"
}
```
3. Compute `X-Hub-Signature: sha1=<hmac(S_A, body)>` and `X-Github-Event: push`, POST to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and succeeds because the signature was made with `S_A`.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github` on `victim-org`'s stacks, even though the request was never authenticated for `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
