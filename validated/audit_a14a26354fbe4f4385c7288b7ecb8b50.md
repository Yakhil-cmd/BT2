Confirmed: `ApiClientsController` (app/controllers/shipit/api_clients_controller.rb) creates `ApiClient` records with only `name` and `permissions` — no `stack_id` — via the web UI, but `ApiClient` also `belongs_to :stack, optional: true` and `Stack has_many :api_clients` (app/models/shipit/stack.rb:41), and `Api::BaseController#stacks`/`#stack` (app/controllers/shipit/api/base_controller.rb:74-80) is the only place enforcing that scoping. `Api::CCMenuController` (app/controllers/shipit/api/ccmenu_controller.rb:29-31) redefines `stack` to call `Stack.from_param!(params[:stack_id])` directly, completely bypassing the `current_api_client.stack_id` restriction inherited from `BaseController`.

### Title
Stack-scoped API token can read status of any stack via CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
An `ApiClient` token that is deliberately scoped to a single `Stack` (via its `stack_id` column) is supposed to only ever authorize actions against that one stack, as enforced by `Api::BaseController#stacks`/`#stack`. The `Api::CCMenuController`, however, overrides `#stack` with an unscoped lookup, so the equality "stack the token authorizes == stack the token touches" is broken: a token minted for stack A can be replayed with `stack_id` for stack B and successfully read stack B's CI/deploy status.

### Finding Description
`Api::BaseController` establishes the security invariant that a stack-scoped `ApiClient` may only see the stack it was bound to: [1](#0-0) 
This is exercised and asserted in tests as "an api client scoped to a stack will only see that one stack": [2](#0-1) 

`ApiClient` itself stores this scoping as an optional `belongs_to :stack`: [3](#0-2) 

`Api::CCMenuController`, which only requires the generic `read:stack` permission (not tied to any particular stack), replaces the inherited scoped `stack` helper with a direct, unscoped `Stack.from_param!(params[:stack_id])` lookup and also swaps in a token-based authentication path: [4](#0-3) 

Because `stack` no longer goes through `stacks.from_param!` (i.e. `Stack.where(id: current_api_client.stack_id)`), the `stack_id` restriction configured on the `ApiClient` is never consulted for this endpoint. Any valid, unrevoked `ApiClient` token that carries `read:stack` — including ones created intentionally scoped to a single stack, such as those minted transparently by `CCMenuUrlController#fetch` for exposing a CI badge URL — can be replayed against `/api/stacks/:stack_id/ccmenu` for an arbitrary `stack_id` belonging to a different stack: [5](#0-4) 

### Impact Explanation
This crosses the "stack a token authorizes vs. stack it touches" trust boundary: an attacker who obtains a stack-scoped API token (e.g. from an embedded CI badge URL, a leaked build page, or a low-privilege integration credential meant for one project) can use it to read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, etc.) of any other stack managed by the Shipit instance, including private/internal ones the token holder has no legitimate access to. This matches the "High — unauthenticated read of stack state" impact category, since it grants read access beyond the credential's intended and enforced scope.

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` authentication token with the `read:stack` permission — no special privileges, write access, or knowledge of secrets are needed, and the `stack_id` query parameter is trivially guessable/enumerable (stacks are addressed via `owner/repo/environment` or numeric IDs). Because `CCMenuUrlController` mints such tokens on-demand for any authenticated user requesting a CI badge URL for a stack, a broad population of low-trust tokens scoped to individual stacks already exists in normal usage, making this readily reachable.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, scoped lookup (`stacks.from_param!(params[:stack_id])`) from `Api::BaseController` instead of calling `Stack.from_param!` directly, so that the `current_api_client.stack_id` restriction is honored exactly as it is for every other API controller. Add a regression test asserting that a stack-scoped token cannot retrieve CCMenu data for a stack other than the one it is bound to.

### Proof of Concept
1. As an authenticated Shipit user, visit a stack's page to trigger `CCMenuUrlController#fetch` for `Stack A`, obtaining a `ccmenu_url` containing an `ApiClient` `token` whose `stack_id` is scoped to Stack A.
2. Send `GET /api/stacks/<Stack B owner>/<Stack B name>/<Stack B environment>/ccmenu?token=<token from step 1>` where Stack B is a different, unrelated stack.
3. Observe that `Api::CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])` (app/controllers/shipit/api/ccmenu_controller.rb:29-31) rather than the scoped `stacks.from_param!`, so the request succeeds and returns Stack B's CI status XML, even though the token was only ever authorized for Stack A.

module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
