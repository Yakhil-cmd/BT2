### Title
Unauthenticated cross-stack disclosure of lock reason/build status via `CCMenuController#stack` bypassing `stack_id` scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` helper to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` relation, instead of using `BaseController#stacks`, which restricts lookups to `current_api_client.stack_id` when the token is scoped. This lets a client holding a token scoped to stack A fetch `cc.xml` for any stack B by simply passing B's `stack_id`, leaking lock reason/status, latest deploy status, and web URL for a stack the token was never authorized to access.

### Finding Description
The intended binding is: `stack the API request touches == current_api_client.stack_id` (when the client's token is scoped, i.e. `current_api_client.stack_id?` is true), enforced in `Shipit::Api::BaseController#stacks` at [1](#0-0) , which is used by `BaseController#stack` (`stacks.from_param!(params[:stack_id])`).

`CCMenuController` breaks this binding by defining its own `stack` method: [2](#0-1) 

Because it calls `Stack.from_param!` on the full `Stack` model rather than the scoped `stacks` relation, `current_api_client.stack_id` is never consulted when resolving which stack to render. `require_permission :read, :stack` at [3](#0-2)  only checks that the token's `permissions` array contains `read:stack` via `ApiClient#check_permissions!` at [4](#0-3)  — it never compares the resolved stack's id to `current_api_client.stack_id`. So a token scoped to stack A but holding `read:stack` permission passes the permission check for any stack, then `show` renders `stack.deploys_and_rollbacks` and lock state for whatever stack B was requested: [5](#0-4) .

Attacker request: `GET /stacks/:owner/:repo/:branch/cc_menu.xml?stack_id=<B's id or slug>&token=<A-scoped token>` (or via basic auth with A's token) — the `stack_id` param is fully attacker controlled and is never cross-checked against the token's authorized stack.

Existing guards that fail to prevent this: `require_permission!`/`check_permissions!` only validate the permission string, not stack scope; there is no `force_github_authentication` or session check on this API path; `Stack.from_param!` performs a lookup with no ownership filter and raises only if not found, not if unauthorized.

### Impact Explanation
Any holder of a stack-scoped API token with `read:stack` permission for stack A can retrieve stack B's CC-Menu XML, exposing `lock_reason`/lock status (rendered as failure state), latest deploy/rollback status, build label/time, and `webUrl` for stack B — a stack in a different repository the token was never granted access to. This is a cross-tenant, unauthenticated-scope read of stack state (lock status, deploy status), matching the High severity category "unauthenticated read of stack state." The attack is trivially repeatable against any stack id/slug in the installation, giving a full enumeration/exfiltration primitive across all tenants sharing the Shipit instance.

### Likelihood Explanation
The attacker only needs a valid API token scoped to any single stack with `read:stack` permission (a low, realistic precondition — many CI/CD integrations issue such scoped tokens) and knowledge/guessability of another stack's `stack_id`/slug (predictable, sequential IDs or well-known repo/branch slugs). No GitHub secrets, session, or elevated role is required. The request is a single unauthenticated-scope GET, fully repeatable at will.

### Recommendation
Remove the overridden `stack` method in `Shipit::Api::CCMenuController` (or reimplement it using the inherited `stacks` scoped relation) so it resolves `stacks.from_param!(params[:stack_id])` exactly like `BaseController#stack`, ensuring `current_api_client.stack_id` scoping is enforced for the CC-Menu endpoint just as it is for other API controllers.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (existing suite already includes `ApiControllerTestCase` helpers):
1. Create stack A and stack B (`Stack.create!` with distinct repositories/branches).
2. Create an `ApiClient` with `stack_id: A.id` and `permissions: ['read:stack']`, authenticate as this client (`authenticate!`/set token).
3. Call `stack_B.lock('super-secret-incident-details', @user)`.
4. `get :show, params: { stack_id: stack_B.to_param, token: @client.authentication_token }`.
5. Assert equality-before-fix: `current_api_client.stack_id == A.id` but the resolved `stack.id == stack_B.id`, i.e. `assert_not_equal current_api_client.stack_id, assigns(:stack)... == stack_B.id` (binding broken).
6. Assert response is `:ok` (not `:forbidden`/`:not_found`) and `assert_payload 'lastBuildStatus', 'Failure'` and that the rendered XML/`webUrl` corresponds to stack B, demonstrating leakage of stack B's lock/deploy state to a token scoped only to stack A.
