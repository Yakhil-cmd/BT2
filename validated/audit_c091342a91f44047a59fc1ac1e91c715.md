### Title
Cross-tenant CI status forgery via unscoped SHA lookup in `StatusHandler#process` allows any verified repository to write `state: 'error'` for another org's commit, flipping `deployable?` from `true` to `false` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit(s) solely by matching `params.sha` against the global `Commit` table, with no check that the commit belongs to the stack/repository that authenticated the webhook. Because `sha` values are attacker-choosable git commit hashes and Shopify/Shipit `verify_signature` only proves the payload came from *some* org's registered GitHub App/webhook secret (not that it came from the org owning the target commit's stack), an attacker controlling any onboarded repository can forge a `status` event referencing a victim commit's `sha` and write a `state: 'error'` status against it, flipping `Commit#deployable?` from `true` to `false`.

### Finding Description
The broken binding: `commit.stack.repository.full_name == payload['repository']['full_name']` should hold for every write performed by `StatusHandler#process`, but the handler never checks it — the actual invariant enforced is only `verify_signature(payload['repository']['owner']['login'])`, which is unrelated to `commit.stack_id`.

Code path:
1. `Shipit::WebhooksController#create` dispatches the parsed JSON payload to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which only checks that the HMAC matches `Shipit.github(organization: repository_owner)`'s `webhook_secret` — i.e., it authenticates *which org sent the request*, not which commit/stack the payload's `sha` is allowed to target: [1](#0-0) .
2. `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` across the entire database by `sha` alone, with no `stack_id`/`repository` scoping to the payload's `repository.full_name`, unlike the base `Handler` class which does provide a `stacks`/`repository_name`-scoped helper that this handler bypasses entirely: [2](#0-1) , [3](#0-2) .
3. `Commit#create_status_from_github!` unconditionally records the forged status under `commit.stack_id` via `statuses.replicate_from_github!(stack_id, github_status)`, recomputing `status`/`deployable?`: [4](#0-3) , [5](#0-4) .

Exploit flow: attacker owns/controls repository `attacker/evil`, which is legitimately onboarded to Shipit (any onboarded repo works — attacker doesn't need admin rights on the victim). Attacker crafts a `status` webhook payload with `repository.owner.login = "attacker"`, `sha = <victim commit sha>`, `state = "error"`, and signs it with `attacker/evil`'s own `webhook_secret` (which the attacker legitimately possesses, since it's their own repo's GitHub App/webhook config). This passes `verify_signature` (attacker org is legitimate), passes `drop_unhandled_event` (status is handled), and `StatusHandler#process` finds the victim's commit purely by matching `sha` — writing the forged `error` status onto the victim's `stack_id`. Since git SHAs are 40-hex content hashes that are public (visible on GitHub, PRs, commit pages), the attacker can trivially learn a specific victim commit's sha and target it precisely without needing to guess.

Existing guards fail because: `verify_signature` authenticates the sender org, not the target commit's owning org; `drop_unhandled_event` only checks event type; there's no `ExplicitParameters` validation binding `sha` to `repository.full_name`; no `Repository`/`Stack` model validation ties `Commit.sha` uniqueness or lookup to a specific repository at the handler layer.

### Impact Explanation
A cross-tenant write occurs: an attacker authenticated only as owner of their own unrelated repository can mutate a victim's `Commit`/`Status`/`Stack` state, sabotaging (not just falsely greenlighting) the victim's continuous deployment pipeline. This flips `Commit#deployable?` true→false, which blocks `Stack#continuous_deployment?` scheduling via `schedule_continuous_delivery` and can block merges via `stack.schedule_merges`. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any victim commit sha (once known) and any number of times, and generalizes to any onboarded repository as attacker.

### Likelihood Explanation
Preconditions: the attacker must control (or have push/webhook access to) at least one repository already onboarded into Shipit with a valid `webhook_secret`/GitHub App config — a low bar since Shipit is often self-service onboarding for engineering orgs. The victim commit's `sha` is public information obtainable from GitHub. No Shipit session, API token, or GitHub org membership is required for the victim's org. The attack is a single crafted HTTP POST to `/webhooks` signed with the attacker's own legitimate webhook secret, making it fully feasible and cheap to repeat.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the stack(s) belonging to the payload's `repository.full_name`, mirroring the `stacks`/`repository_name` helper already defined in `Handler`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a forged webhook from repository A can never write a status against a commit belonging to repository B's stack.

### Proof of Concept
Minitest plan (no live GitHub):
1. Set up two stacks/repositories: `shipit_stacks(:shipit)` (victim, e.g. `shopify/shipit-engine`) and a second `Stack`/`Repository` fixture owned by `attacker/evil-repo`, both onboarded normally.
2. Create `commit = shipit_commits(:first)` under the victim stack, and give it an existing successful status so `commit.deployable? == true` (e.g. call `commit.create_status_from_github!(state: 'success', ...)` or use existing fixture status).
3. Assert precondition: `assert commit.deployable?`.
4. Build a `status` webhook JSON payload with `sha: commit.sha`, `state: 'error'`, `branches: [{name: <victim branch>}]`, and `repository: { full_name: 'attacker/evil-repo', owner: { login: 'attacker' } }`.
5. Stub `Shipit.github(organization: 'attacker').verify_webhook_signature` (or configure a real webhook secret for `attacker`) to return `true`, simulating the attacker's legitimately-signed request for their own org.
6. `post :create` (or invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly) with `X-Github-Event: status`.
7. Assert the forged write succeeded cross-tenant: `assert_equal 'error', commit.reload.status.state` and `assert_not commit.deployable?` — proving the victim's deployable commit was sabotaged by a payload authenticated only against the attacker's unrelated repository.
