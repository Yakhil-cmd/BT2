### Title
Cross-organization stack sync via organization/repository binding mismatch in webhook signature verification - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook by deriving an *organization* name from the payload and checking the HMAC signature against that organization's configured `webhook_secret`. However, the code paths that actually act on the webhook (`Shipit::Webhooks::Handlers::Handler#stacks`, e.g. `PushHandler#process`) resolve the target `Stack`/`Repository` from an entirely different payload field: `repository.full_name`. Nothing ties the two together, so a party that legitimately controls one Shipit-configured GitHub organization (and therefore knows/can trigger delivery with that organization's `webhook_secret`) can craft a payload whose `repository.owner.login`/`organization.login` matches their own org (to pass signature verification) while `repository.full_name` points at a Stack belonging to a completely different organization.

### Finding Description
The binding that should hold is:
`organization authenticated by verify_signature == organization owning the repository the handler acts on`

In `verify_signature`: [1](#0-0) 

the organization used to look up the GitHub App/secret is: [2](#0-1) 

i.e. `params.dig('repository','owner','login') || params.dig('organization','login')`.

Once the signature check passes, `create` dispatches the *entire raw payload* to the registered handlers without any further binding to the verified organization: [3](#0-2) 

The handlers, however, resolve the affected `Stack` using a **different** payload field, `repository.full_name`, via `Handler#stacks`/`#repository_name`: [4](#0-3) 

and `PushHandler#process` uses that scope directly to trigger a sync on whatever stacks match: [5](#0-4) 

Because Shipit supports hosting multiple, independent GitHub organizations from a single installation (each with its own `webhook_secret`, as documented for `Using Multiple Github Applications`): [6](#0-5) 

an org boundary is supposed to exist between tenants. `repository.owner.login`/`organization.login` (used only for auth) and `repository.full_name` (used only for the actual mutating action) are never cross-checked against each other. A payload can legitimately claim `organization.login = "OrgA"` (so it's HMAC-signed and verified with OrgA's secret) while `repository.full_name = "OrgB/some-repo"` (so the handler locates and syncs OrgB's stack).

### Impact Explanation
This breaks the deployment-trust binding between "the organization whose credential authenticated this webhook" and "the repository/stack that the webhook handler is permitted to write to." An attacker who controls (or has delivery access to) one onboarded GitHub organization's webhook secret can forge push/status/pull_request events that are processed as if they originated from a different organization's repository, causing Shipit to enqueue `GithubSyncJob` (and other handler side effects such as archiving/unarchiving review stacks, updating pull request state, or creating statuses) for stacks that belong to organizations the attacker has no legitimate relationship with. Depending on continuous-deployment configuration downstream of a sync, this can escalate into unintended/unauthorized deploy scheduling for another tenant's stack, and in general constitutes a cross-repository/cross-tenant write, which the engagement rules classify as Critical impact.

### Likelihood Explanation
Exploitation requires the attacker to be able to produce a validly HMAC-signed delivery for *some* organization onboarded into the multi-org `config/secrets.yml` (i.e., they control that organization's webhook secret — a normal, intended capability for any legitimate customer organization using this Shipit instance, not a privileged Shipit account, API token, or GitHub App private key). No repository write access on the target organization and no Shipit session/API credential are needed; only the ability to send a POST to `/webhooks` with the crafted payload and a signature computed over it with their own org's secret. This is realistic in any deployment where Shipit is shared across multiple, mutually-untrusted GitHub organizations, which is a documented, supported configuration.

### Recommendation
Bind the two payload fields together at verification time (or at dispatch time): require that the organization derived from `repository.owner.login`/`organization.login` (used to select the webhook secret) matches the organization segment of `repository.full_name` before invoking any handler. Concretely, in `WebhooksController#verify_signature`/`create`, parse `repository.full_name` and reject (422) the request if its owner segment differs from `repository_owner`. Alternatively, have each `Handler` re-derive and re-validate the organization from `repository.full_name` against the organization that authenticated the request (passed down explicitly from the controller) rather than trusting `repository.full_name` in isolation.

### Proof of Concept
1. Shipit is configured (per `docs/setup.md`, "Using Multiple Github Applications") with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret`.
2. `OrgB` has a Stack tracking `OrgB/private-repo`.
3. An operator/admin of `OrgA` (who legitimately knows `OrgA`'s `webhook_secret`) crafts a `push` event payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgB/private-repo",
    "owner": { "login": "OrgA" }
  }
}
```
4. They compute `X-Hub-Signature: sha1=...` over the raw body using `OrgA`'s `webhook_secret` and POST it to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s `GitHubApp`, and the signature verifies successfully.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/private-repo")`, matching `OrgB`'s stack, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, enqueuing `GithubSyncJob` for `OrgB`'s stack — an action `OrgA` should never be able to trigger.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
