## Title
Type-confusion crash in `merkle.deserializeMerkleProof` reachable via attacker-supplied authentifier for an `'in merkle'` address-definition condition - (File: `merkle.js`, `definition.js`)

## Summary
CVE-2018-8105 is a heap buffer over-read/crash in xpdf's `JPXStream::fillReadBuf` caused by parsing an attacker-supplied stream without validating its structure/length before consuming it, leading to an out-of-bounds read and process crash. The analogous bug class in ocore is unvalidated parsing of an attacker-supplied string field (`serialized_proof`) that is fed directly into `merkle.deserializeMerkleProof()` without any type or format check, reachable by any address-definition author using the `'in merkle'` operator.

## Finding Description
`merkle.deserializeMerkleProof` blindly calls `serialized_proof.split("-")` and then `arr.pop()`/`arr.shift()`: [1](#0-0) 

It is invoked from the `'in merkle'` evaluation branch in `definition.js`, where `serialized_proof` is taken directly from `assocAuthentifiers[path]` — the authentifier value supplied by the unit author for that signing path, with only a truthiness check (`if (!assocAuthentifiers[path]) return cb2(false);`), no type check (e.g., `typeof === 'string'`): [2](#0-1) 

Authentifiers are populated from the unit's `authors[].authentifiers` map, which is attacker-controlled JSON content supplied in the posted unit; nothing upstream guarantees the value at a given path is a string before it reaches this code path (unlike, e.g., `sig` or `hash` conditions which impose explicit string-length checks elsewhere in `definition.js`). If the value is anything other than a string (e.g., a number, boolean, `null`, array, or object — all valid JSON leaf/subtree values for a path in the authentifiers map), `serialized_proof.split` throws a `TypeError` because `.split` is not defined on those types.

This mirrors the CVE's root cause pattern: a parsing routine consumes external, adversary-controlled data without first validating its shape, and the resulting out-of-bounds/type-invalid access crashes the process.

## Impact Explanation
`evaluate()` in `definition.js`'s definition-tree walker is invoked during unit validation (`validateAuthentifiers`/`validateDefinition`), which runs synchronously in the main validation path for any unit whose signer uses an address definition containing an `'in merkle'` clause (a documented, publicly available oscript definition primitive; addresses using it can be created by anyone and are commonly used, e.g., in AA-related or data-feed-gated multisig setups). An uncaught `TypeError` thrown deep inside this synchronous evaluation is not enclosed by a try/catch at this call site, so it propagates up and can crash the validating node process (denial of service), preventing that node from validating/confirming further units until restarted — directly satisfying the "network unable to confirm new units" impact bar for a single node, and if broadly triggered across full nodes, degrades network-wide confirmation.

## Likelihood Explanation
Any user can create an address whose definition includes `['in merkle', [[...]]]` and then post a unit signed by that address, supplying an arbitrary (non-string) JSON value as the authentifier for the corresponding signing path. This requires no special privileges — only the ability to define a smart address and post a unit, which is exactly the unprivileged unit-poster capability in scope. The trigger is a one-line JSON change to the authentifier value.

## Recommendation
In `definition.js`'s `'in merkle'` branch, validate that `assocAuthentifiers[path]` is a non-empty string before calling `merkle.deserializeMerkleProof`, e.g. reuse `ValidationUtils.isNonemptyString`. Additionally, harden `merkle.deserializeMerkleProof`/`verifyMerkleProof` to defensively check the input type and wrap parsing in a try/catch that yields `cb2(false)` (as is already done in `verifyMerkleProof`'s internal try/catch, but the `deserializeMerkleProof` call itself sits outside that guard) rather than allowing an unhandled exception to propagate.

## Proof of Concept
1. Create an address whose definition contains a signing path with condition `['in merkle', [['SOME_ORACLE_ADDR'], 'feed_name', 'expected_value']]`.
2. Compose and post a unit signed by that address where, in `unit.authors[0].authentifiers`, the value at that path is set to a non-string JSON value, e.g. `42` or `null` or `{}` instead of the expected `"index-sibling1-sibling2-root"` string.
3. During validation, `evaluate()` reaches the `'in merkle'` case, reads `assocAuthentifiers[path]` (the non-string value), and calls `merkle.deserializeMerkleProof(serialized_proof)`, which executes `serialized_proof.split("-")` and throws `TypeError: serialized_proof.split is not a function`, propagating out of the synchronous evaluation and crashing the validating node process.
