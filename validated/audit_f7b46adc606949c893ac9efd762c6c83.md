### Title
Unauthenticated user impersonation via `X-Shipit-User` header enables attribution of deploys to arbitrary users - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
`identify_user` derives `current_user` solely from the client-supplied `X-Shipit-User` request header, with no signature, session, or membership check binding it to the credential that actually authenticated the request (the `ApiClient` basic-auth token). Any caller holding a valid `ApiClient` token with `deploy:stack` permission can set this header to an arbitrary GitHub login and have `Deploy`/`Task` records attributed to that user.

### Finding Description
The broken binding: `current_user identity` should equal `the GitHub identity that authenticated this HTTP request`, but instead `current_user identity == User.where('lower(login) = ?', request.headers['X-Shipit-User'].downcase).first`, an attacker-controlled plaintext value [1](#0-0)  unrelated to the actual authenticated principal, which is the `ApiClient` resolved via `BasicAuth`/`ApiClient.authenticate(token)` [2](#0-1) .

Authorization for the request is checked only against the `ApiClient`'s own `permissions` array via `check_permissions!`, e.g. `require_permission :deploy, :stack` on `DeploysController`, which merely verifies the token has `deploy:stack` in its `PERMISSIONS` list [3](#0-2) [4](#0-3) . Nothing checks that the `User` looked up from `X-Shipit-User` is the token's creator, a team member, or otherwise entitled to be recorded as the actor.

`DeploysController#create` then calls `stack.trigger_deploy(commit, current_user, ...)`, persisting `current_user` as the deploy's `user`, so the impersonated login becomes attached to the resulting `Deploy` record [5](#0-4) .

Exploit flow: attacker obtains (or is issued) any `ApiClient` token scoped to a stack with `deploy:stack` permission — this is a legitimately provisioned but low-trust credential (e.g., a CI token meant only to trigger deploys as itself). Using that token for HTTP Basic auth, the attacker sends `POST /api/stacks/:id/deploys` with header `X-Shipit-User: <admin-login>` and a valid `sha`. `authenticate_api_client` succeeds off the real token; `identify_user` then binds `current_user` to the row matching the attacker-chosen login string, with no verification that this user ever consented to or authenticated this request.

Existing guards that were checked and do not close this gap: `verify_signature`/webhook code paths are unrelated (this is the REST API, not webhooks); `require_permission!`/`check_permissions!` validate only the token's scope, not the asserted `X-Shipit-User` identity; there is no `force_github_authentication` or session check inside the API controller stack, since `Api::BaseController` is intentionally token-authenticated and separate from the session-based `SessionsController`/`User#authorized?` flow.

### Impact Explanation
An attacker with any valid `deploy:stack`-scoped `ApiClient` token (regardless of the stack it was originally issued for, as `stacks` merely scopes which stack IDs are reachable, not who is credited) can attribute a real, executed deploy or rollback to any existing Shipit user, including a GitHub organization admin, by guessing/knowing their login. This is repeatable per request against any stack the token can reach, and falsifies the audit trail (`Deploy#user`) used to justify approvals in production tooling. This is a Critical impact per the rubric: an unauthorized deploy recorded as approved/triggered by an arbitrary user.

### Likelihood Explanation
The only precondition is possession of some valid `ApiClient` token with `deploy:stack` (or similar) permission — a credential that is expected to exist for CI/automation integrations and is far less privileged than full GitHub org admin access. No GitHub secrets, session, or webhook signature is required; the header is read verbatim with `.presence` and a case-insensitive `User` lookup [6](#0-5) . This is trivially and repeatably exploitable with a single crafted HTTP header.

### Recommendation
Do not trust `X-Shipit-User` as an unauthenticated identity claim. Either remove the header-based identity override entirely for token-authenticated requests, or require that the `ApiClient` explicitly authorize acting on behalf of a specific user (e.g., store an allowed `creator`/delegate list on the `ApiClient` and verify `user_login` matches it before performing the lookup), and audit-log the raw token identity alongside any asserted user.

### Proof of Concept
```ruby
# test/controllers/api/deploys_controller_test.rb (new test)
test "identify_user trusts unauthenticated X-Shipit-User header" do
  admin = shipit_users(:walrus) # some privileged user fixture
  low_priv_client = api_clients(:cyril) # token scoped with deploy:stack only
  stack = shipit_stacks(:shipit)

  authorization = ActionController::HttpAuthentication::Basic.encode_credentials(
    low_priv_client.authentication_token, ''
  )

  post api_stack_deploys_url(stack),
    params: { sha: shipit_commits(:cyril_last).sha },
    headers: {
      'Authorization' => authorization,
      'X-Shipit-User' => admin.login,
    }

  assert_response :accepted
  deploy = Deploy.last
  assert_equal admin, deploy.user # current_user identity != authenticated ApiClient identity
end
```
This demonstrates that `Deploy.last.user` equals the impersonated `admin` even though only the low-privilege `ApiClient` token authenticated the request, confirming the identity binding is broken.
