### Title
Webhook organization confusion in multi-app deployments lets an attacker with control of any configured GitHub org forge events for any other org's stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to validate a webhook's HMAC signature against based on the payload's `repository.owner.login` field, while every event `Handler` resolves the `Repository`/`Stack` it actually mutates using the payload's `repository.full_name` field. In a "Using Multiple GitHub Applications" deployment (a documented, supported Shipit configuration), these are two independent, attacker-controlled JSON fields inside the same unsigned-at-rest request body, so nothing forces them to refer to the same organization. An attacker who legitimately controls (and thus knows the webhook secret of) any one of the GitHub orgs configured in the multi-tenant Shipit instance can self-sign a payload whose `owner.login` names their own org (so signature verification passes) while `full_name` names an entirely different, victim org's repository (so the handler acts on the victim's `Stack`).

### Finding Description
`WebhooksController#verify_signature` picks the app/secret to check with: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the untrusted JSON body (`params.dig('repository', 'owner', 'login')`), and is used only to pick *which* org's `webhook_secret` the HMAC is checked against via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

Each org can be configured with its own distinct `webhook_secret` per the documented multi-org setup: [4](#0-3) 

Once the signature check passes, the controller dispatches the *entire* payload to handlers without re-checking which org it names: [5](#0-4) 

Every handler, however, determines the target `Repository`/`Stack` from a *different* field, `repository.full_name`, not `repository.owner.login`: [6](#0-5) [7](#0-6) [8](#0-7) 

Because `verify_signature` authenticates "this payload was signed by org A's secret" but the handlers act on "whatever repository `full_name` says," the equality that should hold —

`org whose secret validated the signature == org that owns the repository being mutated`

— is never enforced. An attacker who is a legitimate installer/owner of any org configured in the same Shipit instance (org A) knows org A's `webhook_secret` (they set it when creating their GitHub App per the setup docs) and can therefore self-sign an arbitrary payload:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  ...
}
```
`repository_owner` resolves to `"attacker-org"`, `verify_signature` checks the signature against org A's known secret and passes, and the dispatched handler (e.g. `PushHandler`, `PullRequest::OpenedHandler`, the `status`/`membership` handlers exercised in `test/controllers/webhooks_controller_test.rb`) then operates on `victim-org/victim-repo`'s `Stack`/`Repository`/`Commit`/`Team` records, which org A has no relationship to.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary explicitly in scope. Concretely, with a self-signed, attacker-controlled payload the attacker can, against a victim org they have no access to:
- Forge `push`/`status`/`check_suite` events to fabricate commit statuses and CI state for the victim's `Stack` (`Commit#deployable?` is driven by webhook-supplied `state`), pushing the accounting of "what is deployable" out of sync with reality and enabling an unauthorized deploy/continuous-deployment trigger for the victim stack.
- Forge `pull_request` `opened`/`closed`/`labeled` events to create, archive or unarchive Review Stacks on the victim's repository.
- Forge a `membership` event to manipulate `Team`/`Membership` records, which back `User#authorized?` and thus `Shipit.github_teams` authorization — directly matching the "escalation into `Shipit.github_teams` authorization" High-severity impact category.

None of this requires a Shipit session, `ApiClient` token, `webhook_secret` of the victim org, GitHub App private key, or write access to the victim's repository — only administration of any one other GitHub org wired into the same multi-tenant Shipit deployment.

### Likelihood Explanation
Requires the target Shipit instance to use the documented "Using Multiple GitHub Applications" configuration with more than one org, and the attacker to control (own the App installation for) one of those orgs — a realistic scenario for shared/hosted Shipit deployments serving multiple organizations or business units. No further privileges are needed beyond that.

### Recommendation
After selecting the app config from `repository_owner` and verifying the signature, the handler dispatch must also verify that the `repository.full_name`'s owner segment matches `repository_owner` (or, more robustly, resolve the target `Repository`/`Stack` and cross-check its owner against `repository_owner`/the app config used to validate the signature) before invoking any handler. Reject the event if they diverge.

### Proof of Concept
1. Configure Shipit with two orgs, each with a distinct `webhook_secret` (per `docs/setup.md`'s multi-org example): `attacker-org` (secret known to the attacker, who owns that org's GitHub App) and `victim-org` (tracks a stack for `victim-org/victim-repo`).
2. Attacker crafts a `push` payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker chosen sha>",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner == "attacker-org"`, loads attacker-org's `GitHubApp`, and the signature verifies successfully.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` (per `Handler#repository_name`) and calls `stack.sync_github(expected_head_sha: <attacker chosen sha>)` on the victim's stack — despite the attacker never having proven any relationship to `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
