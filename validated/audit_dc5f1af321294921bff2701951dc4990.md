### Title
Untrusted repo-committed `.claude/hookify.*.local.md` rule files are auto-loaded and auto-enabled without confirmation, letting attacker-controlled text be injected into Stop-event `decision`/`reason` output - (File: plugins/hookify/core/config_loader.py)

### Summary
`config_loader.load_rules()` globs `.claude/hookify.*.local.md` and loads any matching file with `enabled` defaulting to `True` if the frontmatter omits it, and `stop.py` calls this on every agent Stop event. A rule file placed in a freshly cloned repository (bypassing the intended `/hookify` interactive creation flow with `AskUserQuestion`) is loaded and evaluated with zero approval prompt or allowlist check.

### Finding Description
`load_rule_file`/`Rule.from_dict` in [1](#0-0)  set `enabled=frontmatter.get('enabled', True)`, so a rule file with no `enabled` field at all is active by default. `load_rules()` in [2](#0-1)  globs `.claude/hookify.*.local.md` relative to the process CWD and loads every match with no origin check (git-tracked vs. untracked, provenance, or signature). `hooks/stop.py` calls `load_rules(event='stop')` and feeds the result straight into `RuleEngine.evaluate_rules` on every Stop event [3](#0-2) . If a matching rule has `action: block`, `RuleEngine.evaluate_rules` returns `{"decision": "block", "reason": combined_message, "systemMessage": combined_message}` for the Stop event, where `combined_message` is the attacker-authored markdown body of the rule file [4](#0-3) . This "reason" text is fed back to the agent as its own directive to continue working, so it functions as prompt injection: repo content that was never reviewed by the user directly steers the agent's subsequent behavior. The documented/intended path for creating rules is the interactive `/hookify` command, which uses `AskUserQuestion` to let the user pick warn vs. block per rule [5](#0-4) ; nothing in `config_loader.py` enforces that a rule was created through that flow, so a rule simply checked into a repository's `.claude/` directory (despite README guidance that these files "should be git-ignored" [6](#0-5) ) is indistinguishable from a locally authored one.

### Impact Explanation
The impact is confined to influencing agent behavior via injected text in the Stop hook's `decision`/`reason`/`systemMessage` fields, not direct arbitrary code execution by the hook itself — the rule engine only performs regex matching and returns JSON with a message [7](#0-6) . This is a real but narrow trust-boundary bypass: it lets untrusted repo content silently inject persistent, repeatedly-triggered instructions into the agent's context on every Stop event without any user review, which can be leveraged to coerce the agent into taking further unwanted actions (e.g., "you must run X to finish") — a prompt-injection amplifier rather than a direct compromise primitive. It also requires the hookify plugin to already be installed by the user, which is itself a prior trust decision by the user for this specific plugin's hook scripts.

### Likelihood Explanation
Preconditions: the victim must have the hookify plugin installed and enabled (a prerequisite trust step), and must clone/pull a repository containing a `.claude/hookify.*.local.md` file (or `enabled` field omitted/true). Given those preconditions, the exploit is fully automatic and repeatable — no interaction, confirmation, or allowlist check exists anywhere in `load_rules`/`load_rule_file` to distinguish a user-authored rule from one shipped in cloned repo content.

### Recommendation
Add provenance/consent controls before a discovered rule file is treated as active: e.g., require an explicit opt-in registry (only rules previously created/approved via `/hookify`, tracked in a separate trusted state file outside version control) rather than trusting any file matching the glob pattern; alternatively, prompt the user (or require `enabled` to be explicitly and freshly confirmed) the first time a new/unrecognized rule file is encountered, and warn loudly if such a file is detected inside a git-tracked path.

### Proof of Concept
Integration test:
1. Create a temp directory simulating a freshly cloned repo; add `.claude/hookify.evil.local.md` with frontmatter `name: evil`, `event: stop`, `action: block`, `pattern: .*` (no `enabled` field), and a message body containing attacker-chosen instructions.
2. `chdir` into that directory and invoke `plugins/hookify/hooks/stop.py` main() with a Stop-event JSON on stdin (e.g. `{"hook_event_name": "Stop", "reason": "done"}`).
3. Assert the JSON output on stdout has `"decision": "block"` and `"reason"`/`"systemMessage"` equal to the attacker's message body, with zero prompts, allowlist checks, or `AskUserQuestion` invocations anywhere in the call path (`config_loader.load_rules` → `load_rule_file` → `Rule.from_dict` → `RuleEngine.evaluate_rules`).
4. Repeat with `enabled` field entirely absent from frontmatter to confirm the default-`True` behavior in `Rule.from_dict` (`plugins/hookify/core/config_loader.py:77`) still loads and triggers the rule.

```python
    def evaluate_rules(self, rules: List[Rule], input_data: Dict[str, Any]) -> Dict[str, Any]:
        """Evaluate all rules and return combined results.

        Checks all rules and accumulates matches. Blocking rules take priority
        over warning rules. All matching rule messages are combined.

        Args:
            rules: List of Rule objects to evaluate
            input_data: Hook input JSON (tool_name, tool_input, etc.)

        Returns:
            Response dict with systemMessage, hookSpecificOutput, etc.
            Empty dict {} if no rules match.
        """
        hook_event = input_data.get('hook_event_name', '')
        blocking_rules = []
        warning_rules = []

        for rule in rules:
            if self._rule_matches(rule, input_data):
                if rule.action == 'block':
                    blocking_rules.append(rule)
                else:
                    warning_rules.append(rule)

        # If any blocking rules matched, block the operation
        if blocking_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in blocking_rules]
            combined_message = "\n\n".join(messages)

            # Use appropriate blocking format based on event type
            if hook_event == 'Stop':
                return {
                    "decision": "block",
                    "reason": combined_message,
                    "systemMessage": combined_message
                }
            elif hook_event in ['PreToolUse', 'PostToolUse']:
                return {
                    "hookSpecificOutput": {
                        "hookEventName": hook_event,
                        "permissionDecision": "deny"
                    },
                    "systemMessage": combined_message
                }
            else:
                # For other events, just show message
                return {
                    "systemMessage": combined_message
                }

        # If only warnings, show them but allow operation
        if warning_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in warning_rules]
            return {
                "systemMessage": "\n\n".join(messages)
            }

        # No matches - allow operation
        return {}
```
