## Finding: Stale cached unit-props (`assocCachedUnits`) can make a node believe an unconfirmed unit is already "known", stalling catch-up

### Summary
The upstream Linux CVE fixes a bug where RDMA/siw kept a private, unsynchronized pointer to a `net_device` instead of relying on the authoritative `ib_device`-managed reference; the local link could go stale (freed) while still being dereferenced, causing UAF. The reachable analog in ocore is a similarly unsynchronized, long-lived cache — `storage.assocCachedUnits` — that stores a *partial* snapshot of a unit's properties (`level, witnessed_level, best_parent_unit, witness_list_unit`) which is treated by `isKnownUnit()`/`checkIfNewUnit()` as proof that the full unit is already known, even when the full joint body has never been received.

### Finding Description
`readStaticUnitProps()` populates a permanent, un-invalidated cache keyed by unit: [1](#0-0) 

`isKnownUnit()` treats the mere presence of an entry in `assocCachedUnits` (or `assocKnownUnits`) as sufficient evidence that a unit is fully known: [2](#0-1) 

The network layer explicitly documents the resulting hazard in a comment inside `ifNeedParentUnits`, when a peer says it needs the pruned/full content of a missing unit: [3](#0-2) 

The comment states: *"requestNewMissingJoints relies on checkIfNewUnit, which can say ifKnown() for a unit that only has stale props cached in assocCachedUnits, even though its full content is exactly what we are missing."* This mirrors the CVE's root cause pattern exactly — a locally-held, independently-lived reference (`assocCachedUnits[unit]`) that is not kept synchronized with the true lifecycle/completeness state of the referenced object (the fully-validated unit/joint), and is consulted by downstream logic (`isKnownUnit`) as if it were authoritative.

`assocCachedUnits` entries are only ever removed by `forgetUnit()` (used for archiving uncovered/voided units), not when a unit is merely referenced as a graph ancestor via `readStaticUnitProps`/`determineBestParent`/`buildListOfMcUnitsWithPotentiallyDifferentWitnesslists`, etc.: [4](#0-3) [5](#0-4) 

Since a wide variety of DAG/MC computations (`determineBestParent`, `buildListOfMcUnitsWithPotentiallyDifferentWitnesslists`, `findMinMcWitnessedLevel`, etc.) call `readStaticUnitProps` for parent units while walking the graph, a unit can get a `assocCachedUnits` entry purely from being referenced as an ancestor, long before (or even without) its own full joint ever being downloaded/validated by this node.

### Impact Explanation
Because `checkIfNewUnit`/`isKnownUnit` (per the acknowledged comment) can incorrectly report such a partially-cached unit as "known", `requestNewMissingJoints`/`ifNeedParentUnits` logic can skip re-requesting the unit's full body from peers. Concretely, this means a node can get stuck believing it already possesses a unit it never actually validated/stored, so it never re-requests the missing content and its descendants (any unit built on top of it) remain unvalidatable/unconfirmable on that node. This maps to the accepted impact class "a network unable to confirm new units" / "node disagreement on validity or stability" — the affected node diverges from the rest of the network's view of DAG completeness and stalls on advancing stability for that branch, without any privileged or malicious-peer action being strictly required (a normal unit whose ancestor unit only reached this node's memory as a best-parent/graph reference can trigger it).

### Likelihood Explanation
This requires no special privileges beyond normal unit posting/propagation. A unit poster (or any user submitting units and parent references during normal catch-up / graph traversal, e.g. `determineBestParent`) can cause a referenced ancestor unit to populate `assocCachedUnits` before its full joint is fetched by a given node, especially during catching up (`bCatchingUp`) or when pruned content requests interleave with graph traversal queries. The developers' own comment confirms the maintainers were aware this specific path is fragile ("even though its full content is exactly what we are missing"), indicating the condition is reachable in production flows rather than purely theoretical.

### Recommendation
- Make `assocCachedUnits` entries carry an explicit "full content available" flag, and have `isKnownUnit()`/`checkIfNewUnit()` only report a unit as known when the full joint (not just static graph props) has been persisted.
- Alternatively, invalidate/skip `assocCachedUnits` reliance inside `ifNeedParentUnits`/`requestNewMissingJoints` so that a peer-reported "need pruned content" signal always forces a re-request regardless of `assocCachedUnits` state, closing the exact gap the existing code comment warns about.
- Add regression coverage exercising: ancestor unit is referenced via `determineBestParent`/`readStaticUnitProps` populating `assocCachedUnits`, then a peer independently posts the same unit id needing hash-tree/pruned content, verifying that the missing unit's full body is still (re)requested and eventually validated.

### Proof of Concept
Not independently reproducible from static analysis alone: the trigger requires a specific catch-up/pruned-content-request race (a unit only known to a node via `assocCachedUnits` graph-prop caching, while its full body is requested via `ifNeedParentUnits`/hash-tree logic) that depends on timing across multiple peers and internal mutex/catch-up state which is not fully observable from the indexed code alone. The maintainers' inline comment at `network.js:1244-1246` is the strongest available evidence that this exact stale-cache-vs-authoritative-state divergence is a real, previously-identified hazard in this code path. function readStaticUnitProps(conn, unit, handleProps, bReturnNullIfNotFound){
	if (!unit)
		throw Error("no unit");
	var props = assocCachedUnits[unit];
	if (props)
		return handleProps(props);
	conn.query("SELECT level, witnessed_level, best_parent_unit, witness_list_unit FROM units WHERE unit=?", [unit], function(rows){
		if (rows.length !== 1){
			if (bReturnNullIfNotFound)
				return handleProps(null);
			throw Error("not 1 unit "+unit);
		}
		props = rows[0];
		assocCachedUnits[unit] = props;
		handleProps(props);
	});
