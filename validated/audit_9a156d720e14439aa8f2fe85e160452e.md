### Title
Webhook signature verification is bound to an attacker-chosen organization while event processing acts on a different, unverified repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) is used to validate the HMAC signature based on a field read straight out of the untrusted, unauthenticated JSON body. The actual event handlers that mutate stacks/commits, however, resolve their target repository from a *different* field of that same body, with no re-check that it belongs to the organization whose secret was used to authenticate the request. An attacker can therefore pick an organization configured in Shipit with a blank/known `webhook_secret` to pass signature verification, while pointing the payload's `repository.full_name` at a completely different, protected repository/stack.

### Finding Description
`verify_signature` picks the verifying `GitHubApp` using `repository_owner`, which is taken directly from the request body: [1](#0-0) [2](#0-1) 

The signature check itself is delegated to `GitHubApp#verify_webhook_signature`, which unconditionally returns `true` when that organization's configured `webhook_secret` is blank: [3](#0-2) 

Shipit explicitly supports multiple GitHub organizations each with their own independently configured secret (`docs/setup.md`, `config/secrets.development.shopify.yml`), so it is a supported, documented configuration for some organizations to exist with a different (or even absent/rotated-out) `webhook_secret` than others: [4](#0-3) 

Once `verify_signature` passes, `create` dispatches the entire raw payload to event handlers: [5](#0-4) 

Every handler resolves its target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` — a field completely independent of `repository_owner` used for the signature check: [6](#0-5) [7](#0-6) 

There is no requirement anywhere that `repository.full_name`'s owner matches `repository.owner.login`/`organization.login` used to select the verifying app. This breaks the equality the signature is supposed to enforce: `organization whose secret verified this request == organization owning the repository being acted upon`. An attacker who knows (or can rely on being blank for) any single configured organization's `webhook_secret` can forge a signature valid for that org while embedding an arbitrary `repository.full_name` belonging to any other Shipit-managed repository, causing handlers such as `PushHandler`, status/check-run handlers, and pull-request handlers to act on that unrelated stack without ever having presented a valid credential for it.

### Impact Explanation
This is an authentication bypass at the perimeter shared by all GitHub-originated engine mutations: an attacker can forge `push`, `status`, `check_suite`, `commit_status`/`deployable_status`, and `pull_request` events for any repository configured in Shipit as long as one org in the multi-tenant config has a weak/blank secret. Forged `push`/`status`/`check_suite` events feed directly into `Commit#deployable?` computation and `next_commit_to_deploy`, which gate continuous delivery and the merge queue — enabling an attacker to manufacture fake green CI state or mark commits "deployable," ultimately influencing an unauthorized deploy or merge on a repository they were never authenticated for. This matches the Critical bucket ("unauthorized deploy, rollback or merge") since the authentication boundary meant to bind "the org that just proved it owns this webhook" to "the repository being modified" is not enforced.

### Likelihood Explanation
Likelihood is high in any Shipit deployment using the documented multi-organization GitHub App configuration (explicitly documented in `docs/setup.md`), which is a normal/expected setup for hosting multiple orgs on one instance. No privileged account, session, or `ApiClient` token is required — only knowledge that some configured organization has no/weak `webhook_secret`, plus the ability to send an arbitrary HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Do not let the payload dictate which organization's secret is used to authorize mutation of a different repository. After selecting `github_app` via `repository_owner`, verify that every repository referenced by the payload's processed handlers (`repository.full_name`, or nested repos in pull_request payloads) belongs to the *same* organization that was used to select/verify the secret, and reject the request otherwise. Additionally, disallow (or loudly warn on) organizations configured with a blank `webhook_secret` in production, since this makes `verify_webhook_signature` a no-op for that org.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgOne` (attacker-known/blank `webhook_secret`) and `OrgTwo` (protected, secret unknown to the attacker) — a supported configuration per `docs/setup.md`.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/protected-repo" }
}
```
3. `repository_owner` resolves to `OrgOne`; `Shipit.github(organization: 'OrgOne')` is fetched and `verify_webhook_signature` returns `true` because `OrgOne`'s `webhook_secret` is blank (no `X-Hub-Signature` needed at all).
4. `PushHandler` then resolves `stacks` via `Repository.from_github_repo_name('OrgTwo/protected-repo')`, and enqueues `GithubSyncJob`/triggers `sync_github` against `OrgTwo`'s stack — despite never presenting any credential recognized by `OrgTwo`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks

            .where(branch:)
