## Analog Confirmed: `Api::CCMenuController` bypasses stack-scoping enforced everywhere else in the API

### Title
API client's stack-scope binding is broken in CCMenu endpoint, allowing a stack-scoped token to read any other stack's build/deploy status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
Every other controller in `Shipit::Api` resolves the target stack through `BaseController#stack`, which is `stacks.from_param!(...)` where `stacks` is filtered to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is scoped to a single stack. [1](#0-0)  `Api::CCMenuController` overrides this `stack` method to load directly by `params[:stack_id]` with `Stack.from_param!`, completely skipping the `current_api_client.stack_id?` scoping check. [2](#0-1) 

### Finding Description
The binding that should hold everywhere in the API is: *the set of stacks an `ApiClient` token authorizes == the set of stacks that controller action actually touches*. `ApiClient` supports an optional `belongs_to :stack`, and when present, `BaseController#stacks` restricts queries to that one stack. [3](#0-2) [1](#0-0) 

`Api::CCMenuController#stack` does not call the inherited `stacks` scoping helper at all - it calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model. [4](#0-3)  The only authorization gate left is `require_permission :read, :stack`, which merely checks that the string `"read:stack"` is present in `current_api_client.permissions` - it does not check *which* stack. [5](#0-4) [6](#0-5) 

This is structurally identical to the reported bug class: two code paths decode/authorize the same request differently. The "signed" part of the token (its `stack_id` binding, verified via `ApiClient.authenticate`/`SimpleMessageVerifier`) is checked and trusted for authentication, but the actual resource acted upon (`params[:stack_id]`) is taken from unverified, attacker-controlled input and never cross-checked against the token's bound stack - exactly the "payload field acted on but never covered by the verified signature/scope" pattern from the report, applied to stack scoping instead of calldata decoding.

Every comparable ApiClient token is generated with `read:stack` scoped to one specific stack for exactly this reason - see `CCMenuUrlController#client`, which mints a `read:stack`-only, stack-bound `ApiClient` specifically so the resulting CCMenu URL/token can be handed to third parties (CI dashboards, status monitors) without granting visibility into the rest of the installation. [7](#0-6)  The existence of `here_come_the_walrus`, a stack-scoped fixture ApiClient with only `read:stack`, and the existing test asserting that such a client "will only see that one stack" via `Api::StacksController#index`, confirms scoping-by-stack is an intended, load-bearing security boundary of the API, one which `CCMenuController` fails to enforce. [8](#0-7) [9](#0-8) 

The existing `Api::CCMenuControllerTest` suite never exercises a stack-scoped client against a *different* stack's `stack_id` param, so this gap is untested. [10](#0-9) 

### Impact Explanation
An attacker who legitimately holds (or has been handed, e.g. via a CCMenu URL shared for a single project's dashboard) a token scoped to stack A can pass any other `stack_id` in the request path and read that other stack's deploy/build status, lock state, and latest build label/time - information from a stack they were never authorized to access. This is an authorization-scope escalation: a credential explicitly minted with `stack: A` is used to read state for stack B, C, ... any stack in the installation. Per the engine's own scoping model this is a direct violation of the `read:stack` scope binding and matches the "High - escalation into unauthenticated read of stack state" impact bucket, since the token holder is not otherwise entitled to read that stack's state.

### Likelihood Explanation
Exploitation only requires one valid stack-scoped `read:stack` token (routinely distributed as CCMenu URLs to CI dashboard tools, external to the trusted operator population) and knowledge/guessing of another stack's `to_param` (repo owner/name/environment), which is often predictable or discoverable (e.g. via the public repo name). No privileged account, session, or additional secret is required beyond the one legitimately-scoped token that was meant to be limited to a single stack.

### Recommendation
Make `Api::CCMenuController#stack` use the same scoping as every other API controller, e.g. `stacks.from_param!(params[:stack_id])` (using the inherited `stacks` method that filters by `current_api_client.stack_id` when set), instead of calling `Stack.from_param!` unscoped.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to `stack: A` with `permissions: ['read:stack']` (this is exactly what `CCMenuUrlController#client` mints and hands out as a CCMenu URL).
2. Compute its `authentication_token` (as done via `ccmenu_url` / `token` param).
3. Issue `GET /api/stacks/:stack_B/ccmenu.xml?token=<token_scoped_to_A>` where `stack_B` is a different stack in the same Shipit installation.
4. Observe `Api::CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])` with no scoping check, `require_permission :read, :stack` passes because the token has the `read:stack` permission bit, and the response renders stack B's `deploys_and_rollbacks.last` build status/lock state - data the token was never authorized to see.

# frozen_string_literal: true

require 'test_helper'

module Shipit
  module Api
    class CCMenuControllerTest < ApiControllerTestCase
      setup do
        authenticate!
        @stack = shipit_stacks(:shipit)
      end

      test "a request with insufficient permissions will render a 403" do
        @client.update!(permissions: [])
        get :show, params: { stack_id: @stack.to_param }
        assert_response :forbidden
        assert_json 'message', 'This operation requires the `read:stack` permission'
      end

      test "#show renders the xml" do
        get :show, params: { stack_id: @stack.to_param }
        assert_response :ok
        assert_payload 'name', @stack.to_param
      end

      test "can authenticate with query string token" do
        request.headers['Authorization'] = 'bleh'
        get :show, params: { stack_id: @stack.to_param, token: @client.authentication_token }
        assert_response :ok
        assert_payload 'name', @stack.to_param
      end

      test "xml contains required attributes" do
        get :show, params: { stack_id: @stack.to_param }
        project = get_project_from_xml(response.body)
        %w[name activity lastBuildStatus lastBuildLabel lastBuildTime webUrl].each do |attribute|
          assert_includes project, attribute, "Response missing required attribute: #{attribute}"
        end
      end

      test "locked stacks show as failed" do
        @stack.lock('test', @user)
        get :show, params: { stack_id: @stack.to_param }
        assert_payload 'lastBuildStatus', 'Failure'
      end

      test "stacks with no deploys render correctly" do
        stack = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')
        get :show, params: { stack_id: stack.to_param }
        assert_payload 'lastBuildStatus', 'Success'
      end

      private

      def get_project_from_xml(xml)
        Hash.from_xml(xml)['Projects']['Project']
      end

      def assert_payload(key, value)
        @project ||= get_project_from_xml(response.body)
        assert_equal(value, @project[key])
      end
    end
  end
end
