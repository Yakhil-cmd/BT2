### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login`, but event handlers act on `repository.full_name` — allowing cross-organization forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This engine supports multi-tenant GitHub App configuration where each GitHub organization has its own `webhook_secret`. `WebhooksController#verify_signature` selects *which* organization's secret to validate the HMAC against by reading an untrusted field from the JSON body itself, then only checks that the signature matches *that* organization's secret. Every downstream event handler, however, resolves the `Repository`/`Stack` to mutate using a *different* field of the same JSON body (`repository.full_name`), which is never cross-checked against the organization used for signature verification. This is the same class of bug as the credit-line report: a boolean/derived value used for authorization (`autoLiquidation`/"which secret verifies this request") is decoupled from the actual state that gets acted upon (`collateral transfer`/"which repository gets mutated").

### Finding Description
`verify_signature` picks the GitHub App/organization used to check the HMAC purely from attacker-controlled JSON fields: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a **per-organization** `webhook_secret` from `secrets.github`, confirming that different organizations can (and, per the docs, are expected to) have distinct secrets in a shared Shipit instance: [3](#0-2) [4](#0-3) 

Once `verified` is true, `create` blindly dispatches to handlers with the raw parsed body, and every handler resolves the repository/stack to act on from a *different* JSON field, `repository.full_name`, that was never bound to the organization used to select the verifying secret: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

Because the HMAC is computed over the entire raw body (`request.raw_post`), it does prove the payload was signed by *some* organization's secret, but it never proves that `repository.owner.login`/`organization.login` (the field used to pick the secret) equals the owner encoded in `repository.full_name` (the field used to pick the actual `Repository`/`Stack` to mutate). Equality that should hold but doesn't:

`organization authenticated (repository.owner.login used to select the webhook_secret) == organization written (owner segment of repository.full_name used to resolve the Repository/Stack)`

An operator of a tenant organization "OrgA" onboarded onto the shared Shipit instance legitimately knows/controls OrgA's `webhook_secret` (they configured it when installing their own GitHub App, per `docs/setup.md`). Because the verification step never checks that `full_name`'s owner matches the verified organization, that same attacker can POST a crafted JSON body directly to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) = `"OrgA"` (so the signature check passes using the secret they legitimately possess),
- `repository.full_name` = `"OrgB/some-repo"` (a repository belonging to a completely unrelated tenant organization also hosted on the same Shipit instance).

The `verify_signature` step passes (correct signature for OrgA), yet every handler (`PushHandler`, `PullRequest::ClosedHandler`, `PullRequest::LabeledHandler`, etc.) will operate on OrgB's `Repository`/`Stack` because they only ever consult `full_name`.

### Impact Explanation
This breaks the trust boundary between tenants of a multi-organization Shipit deployment without requiring any Shipit session, `ApiClient` token, or GitHub App private key belonging to the victim organization — only knowledge of a secret the attacker legitimately owns for their *own* onboarded organization. Concretely, an attacker can:
- Force `PushHandler` to enqueue `GithubSyncJob`/sync operations against another org's stack (`app/models/shipit/webhooks/handlers/push_handler.rb`).
- Force `PullRequest::ClosedHandler#process` to call `review_stack.archive!`, deprovisioning another org's review stack (`app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb`).
- Trigger `labeled_handler`/`unlabeled_handler` to archive/unarchive stacks belonging to a repository they do not own.

This is a cross-repository/cross-organization write triggered purely by exploiting the mismatch between the field used for authentication and the field used to identify the resource being mutated, matching the "cross-repository writes" Critical-impact category.

### Likelihood Explanation
High for any deployment using the documented "Using Multiple Github Applications" feature (`docs/setup.md`), since it is an explicitly supported and expected configuration. Any tenant organization onboarded to a shared Shipit instance can mount this attack against any other tenant with zero additional privileges beyond their own legitimate `webhook_secret`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after determining the verifying organization, assert that it matches the owner segment of `repository.full_name` (or `organization.login` for org-scoped events) before dispatching to any handler — i.e., reject the request if `repository_owner != full_name.split('/').first` (case-insensitively), analogous to requiring `msg.sender == creditLineConstants[_id].lender` in the referenced report.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. mirroring `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`), each with its own `webhook_secret`.
2. As the legitimate operator of `OrgOne` (who knows `OrgOne`'s `webhook_secret`), craft a `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```
3. Sign the body with `OrgOne`'s webhook secret and set `X-Hub-Signature` accordingly, POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"OrgOne"`, fetches `OrgOne`'s app, and successfully verifies the signature (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgTwo/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and triggers `stack.sync_github` on `OrgTwo`'s stack — despite the attacker never having any credential, session, or permission tied to `OrgTwo`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
