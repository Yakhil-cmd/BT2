### Title
Webhook signature is verified against `repository.owner.login`, but repositories are looked up by the unverified `repository.full_name` — allowing cross-organization commit-status/push forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App organization secret to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (or `organization.login`), but every webhook `Handler` resolves the target `Stack`/`Repository` using a *different* field of the same payload: `payload.dig('repository', 'full_name')`. [1](#0-0) [2](#0-1) 

### Finding Description
Shipit is designed to be multi-tenant: `config/secrets*.yml` configures one GitHub App/`webhook_secret` per organization (e.g. `somegithuborg`, `someothergithuborg`). [3](#0-2) 

When a webhook arrives, `verify_signature` resolves the signing secret using `repository_owner`, which is read from `repository.owner.login` (or `organization.login`):
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

This only proves the raw body was HMAC-signed with *some organization's* configured `webhook_secret` — i.e., it proves the sender controls a GitHub App installation for the org named in `repository.owner.login`. It does **not** prove that org owns the repository the handlers actually act on.

Every `Handler` subclass (push, pull_request variants, status is looked up separately, etc.) resolves the repository/stack independently via `payload.dig('repository', 'full_name')`:
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`Repository.from_github_repo_name` splits `full_name` on `/` and looks up by `owner`/`name` columns directly, independent of `repository.owner.login`: [5](#0-4) 

Since an attacker who legitimately controls (or has compromised) a GitHub App installation for **their own** onboarded organization (org A) can freely construct arbitrary JSON payload bytes and sign them with org A's `webhook_secret`, they can set:
- `repository.owner.login = "orgA"` (satisfies `verify_signature`)
- `repository.full_name = "orgB/victim-repo"` (targets a stack belonging to a completely different, unrelated organization/repository tracked by the same Shipit instance)

The equality that should hold — `organization that authenticated == organization that owns the repository written` — is broken: the code authenticates org A but writes/acts on org B's repository.

### Impact Explanation
This crosses a real trust boundary between tenants of the same Shipit instance (an "unprivileged" cross-org attacker relative to org B, since they only have legitimate access to org A). Concrete exploitable handlers:

- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on any not-archived stack tracking `orgB/victim-repo`/target branch. [6](#0-5)  This can trigger sync/refresh of undeployed commits and, combined with `continuous_deployment`, cause an unreviewed/attacker-influenced deploy to be triggered on victim org's stack.
- `StatusHandler#process` calls `commit.create_status_from_github!(params)` for any `Commit` matching an attacker-chosen `sha`, letting the attacker inject a fake, arbitrary CI status (`state`, `context`, `description`, `target_url`) for a commit belonging to org B. [7](#0-6)  Since `ci.require`/blocking statuses gate whether a commit is `deployable?`, an attacker can forge a passing status to make an otherwise-unreviewed/failing commit deployable, leading to an **unauthorized deploy**.
- PullRequest handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) similarly resolve `repository` via `params.repository.full_name` alone and can archive/unarchive or provision review stacks belonging to org B. [8](#0-7) 

This matches the required High/Critical impact bar: "unauthorized deploy" via forged CI status/push triggering, achieved purely by exploiting the signature-vs-lookup binding mismatch — no `ApiClient` token, repository write access, or privileged Shipit account is required, only legitimate possession of one org's own webhook secret (which any onboarded, low-trust organization has).

### Likelihood Explanation
Any organization onboarded into a shared Shipit deployment (multi-org setups are explicitly supported, see `config/secrets.development.shopify.yml`) automatically holds a valid `webhook_secret` for itself. [3](#0-2)  Crafting a raw JSON POST body with mismatched `owner.login` vs `full_name` and signing it with that org's own secret requires no special access beyond that — this is a low-effort, directly reachable path via `POST /webhooks` (`WebhooksController#create`). [9](#0-8) 

### Recommendation
After locating the `Repository`/`Stack` via `full_name` in each `Handler`, verify that the resolved `Repository#owner` matches the `repository_owner` (or `organization.login`) that was used to select the verifying `webhook_secret` in `WebhooksController#verify_signature`, and reject the webhook (422) if they differ. Alternatively, derive the verification organization strictly from `repository.full_name`'s owner segment (splitting it the same way `Repository.from_github_repo_name` does) rather than trusting a separate `owner.login`/`organization.login` field, so a single authenticated field drives both signature-secret selection and repository resolution.

### Proof of Concept
1. Shipit instance configured with two orgs, `orgA` (attacker-controlled/legitimate customer) and `orgB` (victim), each with distinct `webhook_secret`s, and org B has a tracked `Stack` for `orgB/victim-repo`.
2. Attacker (a legitimate GitHub App admin for `orgA`) crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "orgB/victim-repo", "owner": { "login": "orgA" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(orgA_webhook_secret, body)` using their own org A secret.
4. `POST /webhooks` with `X-Github-Event: status`. `verify_signature` reads `repository_owner => "orgA"`, fetches org A's `github_app`, and the signature verifies successfully. [10](#0-9) 
5. `StatusHandler#process` finds `Commit.where(sha: ...)` for the victim's commit (unrelated to org A) and calls `create_status_from_github!`, injecting a forged "success" CI status for org B's commit — with no verification tying org A's authenticated identity to org B's repository. [11](#0-10) 
6. If `ci.require` includes `ci/required-check` and this status is the last missing requirement, the victim commit becomes deployable, and continuous delivery (or a subsequent legitimate deploy click) ships it — an unauthorized deploy enabled entirely by the forged cross-org webhook.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
