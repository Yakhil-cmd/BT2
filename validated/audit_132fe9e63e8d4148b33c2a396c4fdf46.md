## Title
Merkle proof verification in `verifyMerkleProof` accepts intermediate tree nodes as valid leaves, breaking membership soundness for `is_valid_merkle_proof()` and `in merkle` — ([File: merkle.js])

### Summary
`ocore`'s Merkle library, exposed to AA authors through the oscript function `is_valid_merkle_proof()` and to address owners through the `in merkle` authentifier condition, reimplements the exact "Node-as-Leaf" flaw described in the external report: the proof path length is never checked against the tree's actual depth, so a hash of two known sibling nodes can be resubmitted as a "leaf" together with a truncated sibling path and still recompute the same, real Merkle root.

### Finding Description
`verifyMerkleProof` in `merkle.js` hashes the caller-supplied `element` once and then folds it up through an attacker-controlled `siblings` array of arbitrary length, with no check that `siblings.length` matches the depth of the tree that produced `proof.root`: [1](#0-0) 

The code even carries an acknowledging comment that this is a known limitation:
`// Node-as-Leaf issue might matter in some cases` [2](#0-1) 

`deserializeMerkleProof` likewise performs no structural validation of the proof beyond splitting a string: [3](#0-2) 

Because a Merkle tree is built by iteratively hashing sibling pairs (`getMerkleRoot`/`getMerkleProof`), the hash of any two adjacent nodes `hash(h0 + h1)` is numerically identical to a genuine internal node of the tree: [4](#0-3) 

An attacker who knows any two sibling hashes anywhere in a public tree can therefore submit `element = h0 + h1` together with only the *remaining upper* siblings, and `verifyMerkleProof` will recompute the exact same, legitimate root — successfully "proving" inclusion of a value (the concatenated hash string) that was never one of the tree's real leaves.

This primitive is reachable by any unprivileged AA trigger sender via the `is_valid_merkle_proof` oscript function: [5](#0-4) 
Note that only `siblings.length > 50` and non-empty-string checks are enforced (`bPostPemCurvesFix`); there is no check that the number of siblings matches the depth implied by the actual, trusted root that an AA might be comparing against.

The same unguarded `verifyMerkleProof` call is also reachable through the `in merkle` address-definition authentifier, evaluated during unit validation for any address that includes this definition element: [6](#0-5) 
with the syntactic constraints on `element` fixed only at definition-creation time: [7](#0-6) 

### Impact Explanation
`is_valid_merkle_proof` is a general-purpose primitive intended for AA authors to implement custom membership checks (whitelists, airdrops, off-chain attestation sets, etc.), verified against a fixed/trusted root (e.g., stored via a data feed or hardcoded in AA params), exactly the same pattern flagged in the original report for zkSync's `MailboxFacet`. Because the library does not bind the proof length to the tree's real depth, any AA relying on "does `is_valid_merkle_proof` return true for this fixed root" as its sole gate for granting funds, unlocking a reward, or admitting a claim is vulnerable: an attacker can mint arbitrarily many additional "valid" memberships out of any pair of known sibling hashes in the public tree (and, recursively, out of pairs of those forged intermediate values), inflating the effective membership set far beyond the intended, finite leaf set. In AA designs that pay out a fixed reward on successful proof verification (a natural design given the function returns only a boolean, not the leaf position or content), this directly enables **fund loss from the AA** through unbounded/duplicated claims beyond what the original tree author intended.

### Likelihood Explanation
The `is_valid_merkle_proof` function is exposed as a first-class oscript primitive to any AA author, and the resulting AA is triggered by any unprivileged sender, so the bug is fully reachable without special privileges. Exploitation only requires knowledge of the (typically public) list of leaves used to build the whitelist/reward tree and elementary SHA-256/hash concatenation — no cryptographic break is needed, since the "forged" leaf is simply the concatenation of two genuine sibling hash strings.

### Recommendation
- Require the proof to carry (or the verifier to be given) the expected tree depth/leaf count and reject any proof whose `siblings.length` does not exactly match `ceil(log2(N))` for the known `N`.
- Alternatively, tag leaf-level hashing distinctly from internal-node hashing (e.g., domain separation, such as prefixing leaves with `0x00` and internal nodes with `0x01` before hashing) so that an internal node's hash can never collide with a valid leaf hash.
- Document in `merkle.js` and in the `is_valid_merkle_proof`/`in merkle` oscript documentation that callers verifying membership against a trusted root MUST additionally bind/validate the expected proof depth, mirroring the mitigation adopted upstream (commit `7eb51d9` / doc note `5f02309` in the zkSync report).

### Proof of Concept
1. Build a public Merkle tree of leaves `L0..L7` with `merkle.getMerkleRoot`, and publish `root` (e.g., via a data feed, or hardcoded in an AA's whitelist parameter), as in `merkle.js` `getMerkleRoot`/`getMerkleProof`.
2. An AA is written (a common, natural pattern) such that:
   ```
   $ok = is_valid_merkle_proof(trigger.data.leaf, trigger.data.proof);
   if ($ok AND trigger.data.proof.root == known_root)
       pay reward to trigger.address;
   ```
3. Compute `h0 = hash(L0)`, `h1 = hash(L1)` (both public/derivable from the published leaf set).
4. Submit a trigger with `leaf = h0 + h1` and `proof = { index: 0, siblings: [<remaining upper-level siblings only, skipping the leaf-level sibling>], root: known_root }`.
5. `merkle.verifyMerkleProof` (`merkle.js:84-102`) hashes `leaf` to reproduce the real internal node hash, then walks the shortened `siblings` array up to `known_root`, returning `true` even though `leaf` was never one of the tree's original elements.
6. The AA pays out, allowing repeated forged claims for every sibling pair in the tree, well beyond the number of legitimate leaves.

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){

function getMerkleProof(arrElements, element_index){
	if (element_index < 0 || element_index >= arrElements.length)
		throw Error("invalid index");
	var arrHashes = arrElements.map(hash);
	var index = element_index;
	var arrSiblings = [];
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		var overIndex = null;
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			if (i === index){
				arrSiblings.push(arrHashes[hash2_index]);
				overIndex = i/2;
			}
			else if (hash2_index === index){
				arrSiblings.push(arrHashes[i]);
				overIndex = i/2;
			}
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
		if (overIndex === null)
			throw Error("overIndex not defined");
		index = overIndex;
	}
	// add merkle root
	//arrSiblings.push(arrHashes[0]);
	return {
		root: arrHashes[0],
		siblings: arrSiblings,
		index: element_index
	};
}

function deserializeMerkleProof(serialized_proof){

	var proof = {};
	proof.root = arr.pop();

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
