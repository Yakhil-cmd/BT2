### Title
Stack-scoped ApiClient tokens can read CCMenu status for any stack, bypassing per-stack authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` restricts an `ApiClient` to only the stacks it was granted access to by scoping the `stacks` relation on `current_api_client.stack_id`, and every other API controller resolves the requested stack through that scoped relation. `CCMenuController`, however, overrides `#stack` to resolve the `stack_id` param directly against `Stack.from_param!`, completely bypassing the per-client stack restriction while still relying on the same coarse-grained `read:stack` permission check.

### Finding Description
`ApiClient` supports being scoped to a single stack via its optional `stack` association [1](#0-0) . `Shipit::Api::BaseController` enforces this scoping for stack lookups: [2](#0-1) 

Every controller that resolves `stack` through the inherited `stacks`/`stack` helpers (e.g. `Api::DeploysController`, `Api::StacksController`) is therefore bound by the equality `requested_stack ∈ {stacks authorized to current_api_client}`.

`CCMenuController` breaks this binding by redefining `#stack` to query `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(params[:stack_id])`: [3](#0-2) 

The action still only checks the coarse `read:stack` permission bit via `require_permission :read, :stack` [4](#0-3) , which calls `ApiClient#check_permissions!` — a check that only inspects the `permissions` array and never consults `stack_id` [5](#0-4) .

As a result, any token bearer holding an `ApiClient` with `read:stack` permission — even one deliberately scoped to a single stack by setting `ApiClient#stack` (a supported, documented pattern exercised in fixtures such as `here_come_the_walrus`) — can supply an arbitrary `stack_id` to `GET /api/stacks/:stack_id/ccmenu.xml` and receive that other stack's latest deploy/rollback id, status and running state, i.e. `stack a token authorises != stack it touches`.

### Impact Explanation
This is an authorization-scope escalation: a token intentionally restricted to stack A discloses deploy status/state of any other stack B on the installation, which falls under "unauthenticated read of stack state" for stacks outside the token's granted scope (the attacker is authenticated as a low-privilege client but reads state they were never authorized for).

### Likelihood Explanation
Exploitation only requires possession of any `ApiClient` token carrying `read:stack` permission scoped to a specific stack; no session, GitHub identity, or elevated privilege is needed. The `stack_id` route parameter is directly attacker-controlled.

### Recommendation
Change `CCMenuController#stack` to reuse the inherited, properly scoped `stacks` relation (`stacks.from_param!(params[:stack_id])`) instead of querying `Stack` unscoped, so the per-client stack restriction enforced elsewhere in `Api::BaseController` also applies to the CCMenu endpoint.

### Proof of Concept
1. Create (e.g. via console/seed, mirroring the `here_come_the_walrus` fixture) an `ApiClient` scoped to `stack: stack_A` with `permissions: ['read:stack']`.
2. Using that client's Basic-Auth token, call `GET /api/stacks/:stack_B_id/ccmenu.xml` where `stack_B` is a different stack.
3. Observe the response returns `stack_B`'s latest deploy/rollback status even though the token was only authorized for `stack_A`, because `CCMenuController#stack` resolves via `Stack.from_param!` rather than the scoped `stacks` relation used by `Api::BaseController#stack`.
