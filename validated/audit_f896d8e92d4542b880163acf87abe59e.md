## Title
CCMenu API token scope bypass allows reading any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The GaugeController report describes a data-validation flaw where a bonus is computed from a percentage (`voting_balance / voting_total`) that isn't validated to be fair/bounded at the moment it is used, letting an early actor exploit an implicit trust assumption (100% initial supply) that no longer holds once other users are minted. The analogous flaw in shipit-engine is a broken trust binding between the stack an `ApiClient` token is scoped to (`ApiClient#stack_id`) and the stack the token is actually allowed to touch when hitting `Shipit::Api::CCMenuController#show`. The base controller enforces this binding via a scoped `stacks`/`stack` helper, but `CCMenuController` overrides `stack` with an unscoped lookup, silently dropping the binding.

### Finding Description
`Shipit::Api::BaseController` defines the intended binding between a token and the stacks it may access: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` resolves the requested resource through that restricted relation. This is the binding: `stack_id_used_by_controller ∈ { current_api_client.stack_id }` when the client is scoped.

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 

It resolves the stack via `Stack.from_param!(params[:stack_id])` against the full `Stack` table, not through the client-scoped `stacks` relation. Authorization is only checked with `require_permission :read, :stack`, which validates that the client's permission list contains the string `"read:stack"` — a coarse operation/scope check, not a check that the specific `stack_id` in the request matches the client's `stack_id`: [3](#0-2) 

Any client whose token has `read:stack` (even one created purposely scoped to a single stack, e.g. via `CCMenuUrlController`) can therefore query `#show` with an arbitrary `stack_id` and receive build/deploy status for any stack in the installation, not just the one it was issued for: [4](#0-3) 

Before this pull request/behavior: the equality `stack accessed == stack authorized (current_api_client.stack_id)` held for every endpoint inheriting `BaseController#stack`. After: `CCMenuController` breaks that equality — `stack accessed` is user-controlled via `params[:stack_id]` and is independent from `current_api_client.stack_id`.

### Impact Explanation
This is an unauthenticated-scope escalation: a token minted with `read:stack` permission and bound to one specific stack (the common case, since `CCMenuUrlController` always creates a stack-scoped client) can read build/deploy state — `lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl` — of every other stack managed by the Shipit instance. This matches the High-impact category of "escalation into authorization scope" / "unauthenticated read of stack state, task streams or deploy output" relative to what the credential was meant to authorize.

### Likelihood Explanation
Low difficulty to exploit: it only requires possession of any valid CCMenu token (these tokens are embedded in plaintext CCMenu URLs distributed to CI dashboards/build monitors, per `CCMenuUrlController#fetch`), and changing the `stack_id` path/query parameter. No signature, permission, or stack membership beyond generic `read:stack` is checked against the requested stack.

### Recommendation
In `Shipit::Api::CCMenuController`, resolve `stack` through the scoped `stacks` helper (i.e., call `stacks.from_param!(params[:stack_id])` as `BaseController#stack` does) instead of the unscoped `Stack.from_param!`, so the client-to-stack binding enforced by `ApiClient#stack_id` is honored for this endpoint as well.

### Proof of Concept
1. Create/obtain a CCMenu URL for Stack A via `CCMenuUrlController#fetch`, which mints an `ApiClient` scoped to Stack A with `permissions: %w[read:stack]` and returns a token in the query string. [5](#0-4) 
2. Send `GET /api/stacks/:stack_id_of_B/ccmenu.xml?token=<token_scoped_to_A>` — swapping `stack_id` to any other stack B in the same installation.
3. `authenticate_api_client` in `CCMenuController` authenticates the token successfully (it is valid), and `require_permission :read, :stack` passes because the token has `read:stack` in its permission list. [6](#0-5) [7](#0-6) 
4. `stack` resolves `Stack.from_param!(params[:stack_id])` against the unscoped `Stack` table, returning Stack B despite the token being scoped only to Stack A, and the response discloses Stack B's build status. [8](#0-7)
