### Title
Missing liquidation grace period on organic oracle-staleness recovery lets liquidators atomically push a price update and liquidate before borrowers can react - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
Zest's `liquidate()` function accepts an optional `price-feeds` argument that lets *any* caller push a fresh Pyth price update in the very same transaction that performs the liquidation. [1](#0-0)  While a feed is stale (beyond `max-staleness`, checked in `oracle-timestamp-fresh`), all price-dependent state changes (`borrow`, `collateral-add/remove`, `liquidate`) revert with `ERR-ORACLE-INVARIANT`, which effectively "freezes" the market for that asset exactly like the sequencer-down freeze described in the Sherlock report. [2](#0-1)  The protocol only grants a liquidation grace period when the DAO *manually* calls `set-pause-liquidation` to unpause — there is no grace period tied to the organic resolution of an oracle-staleness freeze. [3](#0-2)  This means the first liquidator to successfully deliver a fresh price update after a staleness gap can, in the same atomic call, immediately liquidate any position that became under-collateralized during the gap — the borrower gets zero blocks of warning to add collateral, which is the same "no grace period" harm accepted as valid Medium in the referenced report.

### Finding Description
`price-resolve` only rejects prices that are stale (`delta > max-staleness`) or non-monotonic; it does not track how long a feed has been stale before finally being refreshed, nor does it grant borrowers any window after a staleness gap closes. [4](#0-3)  When a Pyth feed is not refreshed for longer than `max-staleness`, any function needing that price fails with `ERR-ORACLE-INVARIANT`, so no state-changing action (including the borrower's own `collateral-add`) can succeed — this is a de-facto freeze of the position, structurally identical to "settlement can't occur" during Arbitrum sequencer downtime cited in the original report.

`liquidate()` itself is the mechanism that lifts this freeze: it takes an optional `price-feeds` blob and calls `write-feeds` to push new Pyth prices on-chain *before* computing health and executing the liquidation, all in one transaction. [5](#0-4)  Because the liquidator controls exactly which transaction first supplies the fresh price after a staleness gap, they can time the price update to coincide with the moment the position becomes unhealthy and execute the liquidation in the same atomic call — the borrower has no intervening block to react (e.g., top up collateral) between "frozen/stale" and "liquidatable."

The only grace-period safety net in the codebase (`liquidation-grace-periods` / `is-liquidation-paused`) is wired exclusively to the manual DAO pause/unpause flow (`set-pause-liquidation`, `set-liquidation-grace-period`), not to the price-feed staleness/freshness state machine. [6](#0-5) [7](#0-6)  So any organic feed outage (Pyth network issue, no one bothering to relay updates, etc.) that self-resolves is never protected by a grace period, unlike a DAO-initiated pause.

### Impact Explanation
This lands on temporary freezing of funds becoming unfair liquidation — the borrower's collateral is seized without any chance to react to the price move that accumulated during the staleness window, mirroring the accepted Medium in the referenced report (root cause is temporary freezing, but the effect is depositors being liquidated before they can salvage their position).

### Likelihood Explanation
Likelihood is moderate: it requires (1) a genuine oracle staleness gap exceeding the asset's `max-staleness` (default freshness window is short, ~120s per `docs/oracle.md`, but real outages of upstream Pyth publishers or network congestion can exceed this), and (2) a borrower whose position crosses the liquidation threshold during that gap. Any address can act as the liquidator supplying the `price-feeds` update, so no special privilege is needed once the staleness condition occurs.

### Recommendation
Tie a liquidation grace period to oracle-staleness recovery, not just manual DAO pause/unpause: when `price-resolve` observes that the incoming timestamp closes a staleness gap larger than some threshold (e.g., feed was stale for longer than `max-staleness`), automatically set/extend `liquidation-grace-periods` for the affected asset (or globally) before allowing `liquidate()` to proceed, analogous to the existing `set-pause-liquidation` grace-period logic but triggered by the oracle path rather than only by DAO action.

### Proof of Concept
1. A Pyth feed used by asset `X` stops being refreshed on-chain (e.g., publisher outage) for longer than `max-staleness`; `price-resolve` now reverts with `ERR-ORACLE-INVARIANT` for any call needing `X`'s price, effectively freezing borrow/collateral operations for positions using `X`.
2. During this freeze, the market price of `X` moves such that a borrower's position would be liquidatable under the new (unposted) price, but the borrower cannot see/react to this because no on-chain price reflects it and they cannot post their own transaction to fix health if the position looks healthy under the last stored price.
3. A liquidator obtains the latest signed Pyth update off-chain and calls `liquidate(borrower, ..., price-feeds: (some (list update)))`. Inside the same transaction, `write-feeds` pushes the new price via `verify-and-update-price-feeds`, `price-resolve` now succeeds and reflects the big price jump, `is-healthy`/`current-ltv` immediately shows the position as under-collateralized, and the liquidation executes in the same atomic call. [8](#0-7) 
4. The borrower had zero blocks between the price becoming known on-chain and being liquidated, because both events occur in the same transaction — no grace period from `liquidation-grace-periods` applies since that map is only populated by DAO-triggered `set-pause-liquidation`/`set-liquidation-grace-period`, not by this oracle-staleness-resume path.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

(define-public (liquidate
                (borrower principal)
                (collateral-ft <ft-trait>)
                (debt-ft <ft-trait>)
                (debt-amount uint)
                (min-collateral-expected uint)
                (collateral-receiver (optional principal))
                (price-feeds (optional (list 3 (buff 8192)))))
  (let (
    (feeds-check (try! (write-feeds price-feeds)))
    (liquidator contract-caller)
    (position (try! (get-liquidation-position borrower)))
    (pos-full (try! (get-full-position borrower)))
    (mask (get mask position))
    (group (try! (get-egroup mask)))

    (coll-address (contract-of collateral-ft))
    (debt-address (contract-of debt-ft))
    (coll-asset (try! (get-asset coll-address)))
    (debt-asset (try! (get-asset debt-address)))
    (coll-aid (get id coll-asset))
    (debt-aid (get id debt-asset))

    ;; accrue FIRST - populates cache for zToken price resolution
    (u-debt (accrue-user-debts (get debt pos-full)))
    (u-coll (accrue-user-collateral (get collateral pos-full)))

    ;; NOW safe to resolve prices (cache is populated)
    (assets (get-assets mask))
    (notional-valued-assets (get-notional-evaluation { position: position, assets: assets }))
    (total-collateral-usd (get collateral notional-valued-assets))
    (total-debt-usd (get debt notional-valued-assets))

    ;; LTC thresholds, liq params, health
    (ltv-liq-partial (buff-to-uint-be (get LTV-LIQ-PARTIAL group)))
    (ltv-liq-full (buff-to-uint-be (get LTV-LIQ-FULL group)))
    (liq-penalty-min (buff-to-uint-be (get LIQ-PENALTY-MIN group)))
    (liq-penalty-max (buff-to-uint-be (get LIQ-PENALTY-MAX group)))
    (curve-exponent (buff-to-uint-be (get LIQ-CURVE-EXP group)))

    ;; LTV = (debt x 10,000) / collateral
    ;; handle edge case: If collateral = 0, return max LTV (BPS) or 0 if debt also 0
    (current-ltv   (if (is-eq total-collateral-usd u0)
                       (if (is-eq total-debt-usd u0) u0 BPS)
                       (mul-div-down total-debt-usd BPS total-collateral-usd)))
    
    ;; Oracle frontrunning protection: prevent same-block liquidation
    ;; This blocks flash-loan based attacks where user borrows + gets liquidated in same block
    (last-borrow-block (get last-borrow-block position))
    (same-block-check (asserts! (not (is-eq last-borrow-block stacks-block-height)) ERR-LIQUIDATION-BORROW-SAME-BLOCK))

    ;; health check (FAIL-FAST) 
    ;; Check position is liquidatable BEFORE calling calc-liq-factor
    (health-check  (asserts! (>= current-ltv ltv-liq-partial) ERR-HEALTHY))
