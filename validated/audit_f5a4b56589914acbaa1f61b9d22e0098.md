### Title
Webhook signature verification is bound to a different repository field than the one used to select which commits/stacks get written - allows cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to validate the HMAC signature based on `repository_owner`, which is parsed from the JSON body itself (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Every downstream handler, however, resolves the repository/commit to act on from a *different* field of the same attacker-controlled body (`payload.dig('repository','full_name')` for repository lookups, or a bare `sha` for `StatusHandler`, with no repository scoping at all). Because the signature only proves "this body was HMAC-signed with the secret belonging to whatever org `repository.owner.login` says," and not "this body's `repository.full_name`/`sha` values belong to that org," an attacker who owns one configured GitHub App/secret can forge events that mutate state for any other org/repo/commit tracked by the same Shipit instance. This is the same class of bug as the reported `distribute()` issue: a value used to satisfy a check (`offer.aprBps` timed against `_duration`) is not the same value bound at settlement time (`block.timestamp`), breaking the invariant the check was meant to enforce. Here the "check" (signature verification keyed by `repository_owner`) is not cryptographically bound to the "write" (repository/commit resolution keyed by `full_name`/`sha`).

### Finding Description
`verify_signature` in `WebhooksController` picks the `GitHubApp` (and its `webhook_secret`) via:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

`Shipit.github` supports per-organization secrets when the deployment is configured for multiple GitHub Apps/orgs, exactly as documented and fixtured (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md` "Using Multiple Github Applications"): [3](#0-2) 

The signature (`X-Hub-Signature`) is verified over the raw request body using `HMAC(secret_for(repository_owner), raw_post)` — it proves the payload was signed by *some* known org's secret, keyed on `repository.owner.login`, but not that every other field inside that same payload is truthful for that org.

Once verification passes, the generic `Handler` base class and concrete handlers resolve the actual object being written using a **separate field**:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`StatusHandler` is worse: it does no repository scoping at all, it just matches any commit row by SHA across the entire installation:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

`create_status_from_github!` persists a `Status` row that directly feeds `Commit#deployable?`/`#state`, which is exactly what Shipit's deploy-gating logic (`ci.require`, "green CI") relies on: [6](#0-5) [7](#0-6) [8](#0-7) 

`PushHandler` and the pull-request handlers similarly key off `repository.full_name`/`repository.owner.login`-agnostic lookups derived purely from the JSON body, e.g.: [9](#0-8) 

**Binding that should hold, but is broken:**
`org_that_signed_the_request == org_that_owns_the_repository/commit_being_mutated`

Before the attack (intended invariant): the org resolved by `repository_owner` (used to pick the secret) is the same org whose repo/commit the handler subsequently writes to, because in a genuine GitHub-originated webhook `repository.owner.login` and `repository.full_name`'s owner are the same value.

After the attack: an attacker who controls (or has access to) the webhook secret for *any one* configured org (e.g., their own GitHub org with a Shipit-managed test repo/App) crafts a raw JSON body where:
- `repository.owner.login` = `"attacker-org"` (so `repository_owner` resolves to the secret the attacker controls, and `verify_webhook_signature` passes),
- `repository.full_name` = `"victim-org/victim-repo"` (or, for the `status` event, simply `sha` = a known victim commit SHA with no repository field needed at all),

and signs the whole body with `attacker-org`'s `webhook_secret`. The signature check passes because it only validates the payload was signed by the org resolved from `repository.owner.login`; it never validates that `full_name`/`sha` are consistent with that org.

### Impact Explanation
This breaks a cross-repository write boundary listed as in-scope: an unprivileged party who only holds credentials/secret for one configured GitHub App can forge webhook events that mutate `Status`/`Commit`/`Stack`/`PullRequest` records belonging to a different, unrelated repository/organization managed by the same Shipit instance.

Concretely:
- Via `status` events, the attacker can inject a fabricated `success` status for an arbitrary commit SHA of a victim repo (no repository scoping is even attempted), directly flipping `Commit#deployable?` to true and unblocking CI-gated deploys (`ci.require`) for that commit — an unauthorized deploy enabler.
- Via `push`/`check_suite`/`pull_request` events, the attacker can trigger `GithubSyncJob`/`RefreshCheckRunsJob` and pull-request state changes (`stack.unarchive!`, review-stack provisioning, PR label/edited/assignee updates) for a victim's stack, since `Repository.from_github_repo_name` only depends on the forged `full_name` string.
- This qualifies as "cross-repository writes" and "escalation into an unauthorized deploy," both explicitly listed as accepted High/Critical impacts.

The practical severity depends on the deployment having more than one org configured with distinct `webhook_secret`s (an explicitly supported and documented configuration, not a mis-deployment), and on the attacker legitimately controlling one such secret (e.g., operating their own onboarded org/App on the same Shipit instance). Given multi-org support is a first-class documented feature (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`), this is a realistic configuration.

### Likelihood Explanation
Any tenant/org already onboarded to a shared, multi-org Shipit instance can exploit this without any additional privilege escalation, session, or token — they simply craft and POST a JSON body with mismatched `owner.login` vs `full_name`/`sha` fields and sign it with their own legitimate webhook secret. No GitHub-side cooperation or repository write access to the victim's actual GitHub repo is required, since Shipit's local database state (statuses, commits, stacks, pull requests) is mutated directly by the webhook handler, independent of GitHub's own webhook delivery.

### Recommendation
Bind the org used for signature verification to the same field(s) used for the write, and re-verify inside each handler:
- After resolving `repository_owner` for signature verification, cross-check that the resolved organization also matches the owner encoded in `repository.full_name` (and in `organization.login` if present) before dispatching to handlers.
- In `StatusHandler`, scope the `Commit` lookup by `stack.repository` (derived from the verified/matching `repository.full_name`), not by a bare, cross-tenant SHA match.
- More generally, make `Handler#stacks`/`#repository_name` derive the repository from the same trust-anchored value used in `verify_signature`, rather than trusting the payload independently in two separate stages.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (as supported by `Shipit.github`/`github_app_config`) [10](#0-9) , and have `victim-org/victim-repo` tracked with an existing commit `SHA_V` pending CI (`ci.require` configured).
2. As the operator of `attacker-org` (who legitimately knows `attacker-org`'s `webhook_secret`), craft a `status` webhook body:
   ```json
   {
     "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/anything"},
     "sha": "SHA_V",
     "state": "success",
     "context": "ci/required"
   }
   ```
3. Sign the raw body with `HMAC-SHA1(attacker-org_webhook_secret, body)` and send it to `POST /webhooks` with header `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the signature check succeeds because it was indeed signed with that secret.
5. `StatusHandler#process` runs `Commit.where(sha: 'SHA_V')` — matching the victim's commit regardless of `attacker-org` never having any relationship to `victim-repo` — and creates a `success` `Status` on it, flipping `Commit#deployable?` to true and unblocking the victim's deploy gate.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
