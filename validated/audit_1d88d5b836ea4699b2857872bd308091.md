### Title
Webhook signature is verified against the organization derived from the payload's `owner.login`/`organization.login`, while every handler acts on a different, unchecked payload field (`repository.full_name`), allowing a malicious GitHub App owner to trigger stack syncs/deploys for any other organization's repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret`) used to validate the HMAC signature based on `repository_owner`, which is read from the same untrusted, attacker-controlled JSON body (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`). Once the signature checks out, `WebhooksController#create` dispatches the *entire raw payload* to every registered handler, and each handler resolves the target `Repository`/`Stack` using a completely different field of that same payload: `payload.dig('repository', 'full_name')` (see `Handler#repository_name` / `Handler#stacks`). Nothing ties the authenticated organization to the repository that is ultimately acted upon.

### Finding Description
The trust binding that should hold is:
`organization authenticated by verify_signature == owner of the repository whose Stack is mutated by the handler`

`repository_owner` (used to select the signing secret) is derived from: [1](#0-0) 

`verify_signature` uses this value to pick which `Shipit.github(organization: ...)` app's secret verifies the HMAC signature: [2](#0-1) 

But the raw, already-signed body is handed unmodified to every handler: [3](#0-2) 

Every handler resolves the affected repository/stacks from a *different* JSON key, `repository.full_name`, with no cross-check against the organization used for signature verification: [4](#0-3) 

Since Shipit supports multiple GitHub Apps/organizations (`github.<org>.webhook_secret` in `config/secrets.yml`), an attacker who legitimately controls one onboarded GitHub App/organization (and therefore knows that organization's `webhook_secret`) can compute a valid HMAC-SHA1 signature over an arbitrary JSON body. Because `repository.owner.login` (used only for secret selection) and `repository.full_name` (used to select the `Stack` to act on) are never checked against each other, the attacker can set:
- `repository.owner.login` = their own organization (so the correct/known secret is used and signature verification passes), and
- `repository.full_name` = `victim-org/victim-repo` (an entirely different, unrelated organization/repository that Shipit also tracks).

`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, and the `PullRequest::*` handlers all resolve `stacks`/`repository` purely from `repository.full_name` and then act (`sync_github`, `schedule_refresh_check_runs!`, label-driven stack provisioning/archival, `create_status_from_github!`), for example: [5](#0-4) [6](#0-5) 

The equality that should be enforced — organization authenticated == owner of repository acted upon — is broken: signature verification only proves "this request was signed by *some* organization Shipit knows about," not "this request was signed by the owner of the repository named in `repository.full_name`."

### Impact Explanation
An attacker who is the legitimate admin of one onboarded GitHub organization/App in a multi-org Shipit deployment can forge webhook events (push, check_suite, pull_request, status) that are cryptographically valid (signed with their own known secret) but target a completely different, victim organization's repository/stack, because the target is chosen from an unauthenticated field. This can force `PushHandler` to invoke `stack.sync_github(expected_head_sha: ...)` against a victim's stack, or trigger review-stack provisioning/archival and status changes on a victim's PRs/commits — effectively an unauthorized cross-repository/cross-organization write into Shipit's state for repositories the attacker does not own. This is a cross-repository-writes class of finding under the impact rubric (Critical).

### Likelihood Explanation
Requires the deployment to be configured with multiple GitHub Apps/organizations (the documented "Using Multiple Github Applications" configuration) and requires the attacker to control at least one of the onboarded organizations/Apps and its `webhook_secret` — a lower-privileged position than any of the victim organizations. Given that Shipit explicitly supports and documents multi-org setups, this is a realistic configuration, and no repository write access or session on the victim side is needed.

### Recommendation
After verifying the signature, re-derive `repository_owner`/organization strictly from the same field used by the handlers (`repository.full_name`), or explicitly check that `repository.full_name`'s owner matches the organization that authenticated the signature before dispatching to handlers. Alternatively, scope handler lookups (`Handler#stacks`) to only the authenticated organization rather than trusting `repository.full_name` unconditionally.

### Proof of Concept
1. Deploy Shipit with two organizations configured under `github:` in `secrets.yml`: `attacker-org` (attacker knows `webhook_secret`) and `victim-org` (attacker does not know its secret).
2. Attacker crafts JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org-webhook-secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')`, verifies successfully with the attacker's own known secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `sync_github` on the victim's stack — a write triggered by an attacker who authenticated only as `attacker-org`.
