### Title
Membership webhook signed by any tenant's own secret can mutate an arbitrary Team by attacker-chosen `github_id` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#repository_owner` falls back to `params.dig('organization','login')` when `repository` is absent, so `verify_signature` authenticates the payload against whichever organization's secret the attacker chooses to sign with (their own). `MembershipHandler` then uses the fully attacker-controlled `params.team.id` to look up or create a `Team` and mutate its membership, with no check that the team belongs to the authenticating organization.

### Finding Description
The broken binding: the organization used to verify the payload (`repository_owner` → `Shipit.github(organization: repository_owner)`, `app/controllers/shipit/webhooks_controller.rb:25,59-62`) should equal the organization that owns the `Team` record being mutated (`Team.find_or_create_by!(github_id: params.team.id)`, `app/models/shipit/webhooks/handlers/membership_handler.rb:39-42`). These are never checked to be the same tenant.

Path: attacker sends `POST /webhooks` with header `X-Github-Event: membership`, a body with no `repository` key, `organization: {login: 'attacker-org'}`, and `team: {id: <protected-team-github-id>, name, slug, url}`, `member: {login: attacker's own github login}`, signed with `attacker-org`'s own legitimate `webhook_secret` (which the attacker controls as admin of that real tenant). `repository_owner` returns `'attacker-org'` (`webhooks_controller.rb:61`), `verify_signature` fetches `Shipit.github(organization: 'attacker-org')` and successfully verifies since the attacker used the correct secret for their own org. `check_if_ping`/`drop_unhandled_event` do not block `membership` events since a `MembershipHandler` is registered. `MembershipHandler#process` then calls `find_or_create_team!`, which trusts `params.team.id` — a value from the JSON body under full attacker control and with zero relation to `attacker-org`'s real GitHub team IDs — to locate or create a `Team`, then calls `team.add_member(member)` (`membership_handler.rb:22-33`), adding the attacker (or any specified login) as a member of that team. If `<protected team id>` corresponds to a `Team` referenced in `Shipit.github_teams` for authorization (`lib/shipit.rb`), this directly escalates the attacker into a privileged authorization group.

No existing guard prevents this: `verify_signature` only proves the request was signed by *some* known organization's secret — it never checks that the `team`/`organization` referenced in the payload actually belongs to that organization on GitHub's side. `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not ownership. There is no cross-check between `repository_owner`/`organization.login` and `params.team.id`.

### Impact Explanation
An unprivileged attacker who legitimately administers any Shipit-configured GitHub organization (i.e., knows only their own `webhook_secret`) can add arbitrary GitHub users (including themselves) to any `Team` record in Shipit by guessing/enumerating `github_id` values, without needing any relationship to that team's real organization. If that team is part of `Shipit.github_teams` (used for authorization, e.g. `app/models/shipit/user.rb`, `app/controllers/concerns/shipit/authentication.rb`), this is escalation into privileged Shipit authorization — matching the High severity category "escalation into `Shipit.github_teams` authorization." The action is repeatable against any `github_id` and any member login, across tenants.

### Likelihood Explanation
Preconditions: attacker must be a legitimate admin of at least one organization already configured in Shipit (has a real `webhook_secret` for that org) — this is a normal, low-cost precondition for many multi-tenant Shipit deployments where any onboarded team can send webhooks. No knowledge of the victim organization's secret, GitHub App key, or Shipit session/API token is required. The `team.id`/`github_id` values may be guessable (sequential/small integers) or leaked via public GitHub API. This is straightforward to reproduce with a single crafted HTTP POST.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the `organization.login` in the payload matches the `Team#organization` already on file when the team exists (reject mismatches), and additionally validate in `WebhooksController` that for org-scoped fallback events, the `Team`/entity being mutated is scoped/owned by the verified organization before allowing creation or mutation. At minimum, reject `membership` events where an existing `Team` with that `github_id` has a different `organization`, and require additional authorization (e.g., calling GitHub's API to confirm the team belongs to the verifying org) before creating new teams from webhook data.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative, minitest, no live GitHub)
test "membership webhook signed by attacker-org can mutate a foreign team" do
  protected_team = shipit_teams(:some_protected_team) # existing Team with github_id: 999, organization: 'victim-org'

  payload = {
    action: 'added',
    team: { id: protected_team.github_id, name: 'whatever', slug: 'whatever', url: 'http://x' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker' }
  }.to_json

  Shipit.stubs(:github).with(organization: 'attacker-org').returns(stub(verify_webhook_signature: true))

  request.headers['X-Github-Event'] = 'membership'
  request.headers['X-Hub-Signature'] = 'sha1=attacker-org-signature'

  assert_difference -> { protected_team.reload.members.count }, +1 do
    post :create, body: payload
  end

  assert_equal 'victim-org', protected_team.organization # binding claimed unchanged
  assert_includes protected_team.members.map(&:login), 'attacker' # but membership mutated by attacker-org's signature
end
```
This demonstrates: LHS (`repository_owner` == `'attacker-org'`, verified) vs RHS (`Team#organization` == `'victim-org'`, mutated) — the two are unequal, yet the mutation succeeds, confirming the vulnerability.
