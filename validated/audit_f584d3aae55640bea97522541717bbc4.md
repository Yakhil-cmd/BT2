### Title
Silently-ignored `os.RemoveAll` return value when disabling sparse-checkout can leave stale filters in place and publish partial content - ([File: main.go])

### Summary
`configureWorktree` in `main.go` calls `os.RemoveAll(gitSparseConfigPath)` without checking its return error when `git.sparseFile == ""`, mirroring the reported bug class (an important state-changing call's return/error value is discarded, allowing a failure to pass silently).

### Finding Description
When git-sync is (re)configured without `--sparse-checkout-file`, `configureWorktree` is supposed to "unconfigure" any previously-set sparse checkout by deleting the worktree's `info/sparse-checkout` file: [1](#0-0) 

The call `os.RemoveAll(gitSparseConfigPath)` returns an `error`, but the code neither captures nor checks it. If the removal fails (e.g., due to a permission problem, a race with another process, a read-only filesystem remount, or a filesystem error on the mounted `--root` volume), the function proceeds as if disabling sparse-checkout succeeded. Immediately afterward, `configureWorktree` runs `git reset --hard <hash> --` on the worktree: [2](#0-1) 

If the stale `info/sparse-checkout` file remains and git's sparse-checkout feature is still considered active for that worktree (per the "undocumented behavior" the code's own comment references at the link), the `reset --hard` can continue to filter files according to the old, now-supposed-to-be-disabled sparse pattern. The function still returns `nil` overall (no error propagated from `configureWorktree`), so `SyncRepo` proceeds to call `syncHooks.beforePublish`, `git.publishSymlink`, and `syncHooks.afterPublish` as if the sync were fully correct: [3](#0-2) 

This is architecturally analogous to the Solidity report: an important call's return value (`withdrawAndUnwrap`'s `bool`, here `os.RemoveAll`'s `error`) is discarded, so a failure of a state-transition step is invisible to the caller, and the outer workflow (fund withdrawal there; symlink publish here) proceeds under the false assumption that the step succeeded.

### Impact Explanation
If the analog manifests, git-sync could publish (via the atomic symlink swap that is the tool's documented "contract" — see `README.md:190-203`) a worktree that is missing files that should have been included, because a stale sparse-checkout filter silently continues to exclude them. Consumers of the `--link` symlink (e.g., sidecar-consuming application containers in Kubernetes) would then read an incomplete/partial checkout while git-sync reports success (`updated successfully`, `good sync count` metric incremented), with no error surfaced to logs or the `--error-file`. This matches the "publishing wrong or partial content" impact category.

### Likelihood Explanation
This requires (a) a prior sync that had `--sparse-checkout-file` set (leaving `info/sparse-checkout` populated) and (b) a subsequent reconfiguration/restart without that flag, combined with (c) an `os.RemoveAll` failure on that specific file at that moment (permission/filesystem transient error). This is a narrower trigger than the original report (which fires on every unstake call); it depends on an operational misconfiguration/transition plus a filesystem-level failure, so likelihood is low-to-moderate and mostly relevant to unprivileged/non-adversarial failure conditions rather than a directly attacker-controlled trigger from repo content alone. I was not able to fully verify git's exact semantics for whether merely deleting `info/sparse-checkout` (without an accompanying `git sparse-checkout disable` or config toggle) reliably disables filtering in all git versions; the code comment itself references "undocumented behavior," so the precise conditions for silent-partial-content are git-version-dependent and could not be conclusively confirmed from the repository alone.

### Recommendation
Check and handle the error from `os.RemoveAll(gitSparseConfigPath)` explicitly in `configureWorktree` (main.go:1690), returning/wrapping the error so that `SyncRepo` aborts the sync (and is retried) instead of proceeding to publish under a possibly-stale sparse-checkout state:
```go
if git.sparseFile == "" {
    if err := os.RemoveAll(gitSparseConfigPath); err != nil {
        return fmt.Errorf("error removing sparse-checkout config: %w", err)
    }
}
```
Additionally, consider explicitly running `git sparse-checkout disable` (or equivalently clearing `core.sparseCheckout`) rather than relying solely on file deletion, to remove dependence on undocumented git behavior.

### Proof of Concept
Not fully constructible from static repository review alone: reproducing this requires inducing an `os.RemoveAll` failure on `info/sparse-checkout` at the precise moment `configureWorktree` runs with `git.sparseFile == ""` (e.g., by making the `.git/worktrees/<hash>/info` directory or file transiently read-only/locked), then observing whether the subsequent `git reset --hard` still excludes previously-sparse-filtered files while git-sync reports a successful sync. Confirming the exact git-version-dependent filtering behavior would require running the actual `git` binary in the target environment, which was outside the scope of this static code review.
