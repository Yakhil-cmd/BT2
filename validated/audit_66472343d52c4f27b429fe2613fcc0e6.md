Found the key match: `Shipit::EnvironmentVariables#interpolate` falls back to the host process `ENV` when a `$VAR` referenced in a shipit.yml step is not present in the whitelisted/permitted `env` hash that was checked by `#permit`.

### Title
Environment-variable whitelist bypassed via `$VAR` interpolation falling back to host process `ENV` - (File: `lib/shipit/environment_variables.rb`)

### Summary
`EnvironmentVariables#permit` enforces that only whitelisted deploy/task/rollback variables are accepted from user/API-supplied `env` params. However, `EnvironmentVariables#interpolate`, used by `Command#interpolate_environment_variables` to substitute `$VAR` references inside `shipit.yml` step commands, does not consult the same whitelist: for any variable not found in the (already-permitted) `@env` hash it falls back to the live process `ENV`, i.e. the deploy host's own environment, which can contain secrets such as `GITHUB_TOKEN`, database credentials, or other operator-provided host environment variables never intended to be exposed to `shipit.yml` step authors.

### Finding Description
The whitelist binding is: "environment key permitted" (`EnvironmentVariables#permit`, checked against `deploy_variables`/`rollback_variables`/task `variables`) versus "environment key spawned" (the key actually available to the process at command execution/interpolation time). These are supposed to be the same set — only variables explicitly declared in `shipit.yml`'s `variables:` sections (plus a small set of framework-injected keys) should ever reach the executed command.

`permit` enforces the whitelist strictly by raising `NotPermitted` for any key present in the caller-supplied `env` that isn't in `variable_definitions`: [1](#0-0) [2](#0-1) 

But `interpolate`, invoked from `Command#interpolate_environment_variables` when expanding `$VAR` tokens inside the `steps` arrays defined in `shipit.yml` (e.g. `cap $ENVIRONMENT deploy:restart`), does not raise or fail closed when a referenced variable is absent from the sanitized `@env`; instead it silently falls back to `ENV[variable]`, the deploy host's own process environment: [3](#0-2) [4](#0-3) [5](#0-4) 

This is the same class of bug as the `StabilityPool` report: two supposedly-equal state slices (the whitelist-checked set vs. the set actually consulted/used) silently diverge — here, `permit`'s enforced whitelist is bypassed by `interpolate`'s unchecked fallback path, so the "permitted" environment-key set and the "spawned"/interpolated environment-key set are not the same.

### Impact Explanation
An attacker who can define/modify `shipit.yml` `steps` for a stack (a repository maintainer merging into the deployed branch — an action the engine already trusts for defining deploy behaviour) can add a step referencing `$SOME_HOST_SECRET_NAME`. If that name happens to match a variable set in the shipit application's own process environment (which commonly includes secrets injected via container/orchestration env vars, cloud credentials, etc.), the value is substituted into the executed shell command and thus exfiltrated into the task output/log, which the requesting stack's collaborators can read. This crosses the trust boundary between "variables the stack owner declared and was allowed to supply" and "the deploy host's actual process environment," and can lead to credential exfiltration from the deploy host.

### Likelihood Explanation
Likelihood is Low: it requires the attacker to control `shipit.yml` content for a tracked repository (already a level of trust) and to guess or know the name of a secret environment variable present on the host process. It does not require an `ApiClient` token, session, or special privilege beyond repo write access already contemplated as an unprivileged-relative-to-host-secrets actor. This mirrors the report's "Low likelihood / High impact" profile.

### Recommendation
Make `EnvironmentVariables#interpolate` fail closed like `#permit` does: raise `NotPermitted` (or otherwise refuse to substitute) when a referenced `$VAR` is not present in the already-whitelisted `@env`, instead of falling back to `ENV[variable]`. Remove the `ENV[variable]` fallback in `lib/shipit/environment_variables.rb` line 25, or explicitly re-check the whitelist before allowing that fallback.

### Proof of Concept
1. As the owner of a tracked repository, add to `shipit.yml`:
```yaml
deploy:
  override:
    - "echo $SOME_SECRET_ENV_VAR_ON_HOST"
```
2. Trigger a deploy for the stack.
3. `Command#interpolate_environment_variables` calls `EnvironmentVariables.with(env).interpolate(argument)`; `SOME_SECRET_ENV_VAR_ON_HOST` is not in the deploy's permitted `env` (`deploy_variables`), so `interpolate` falls back to `ENV.fetch` on the Shipit host process, embedding the host's actual secret value into the interpolated shell command that is then executed and streamed to the task/deploy output visible to stack collaborators.

```ruby
    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
```

```ruby
    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
```
