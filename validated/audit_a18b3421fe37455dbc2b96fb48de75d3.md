### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every handler acts on the unrelated, unverified `repository.full_name` field, letting a possessor of one organization's webhook secret forge events against any other stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
This mirrors the reported bug class: a check is performed against one field, but a decision/mutation is executed based on a different field that is never cross-validated against the first, so the "authenticated" identity and the "acted-upon" identity can diverge.

In `WebhooksController#verify_signature`, the organization used to look up the GitHub App/webhook secret to verify the HMAC signature is taken from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) — a value fully controlled by whoever is crafting the JSON body. `Shipit.github(organization: repository_owner)` selects the app/secret configured for that organization, and `verify_webhook_signature` only proves that the HMAC over the raw body matches that organization's secret: [3](#0-2) 

Once verification passes, `WebhooksController#create` dispatches the event to handlers with the same, attacker-controlled JSON: [4](#0-3) 

But every handler resolves which `Stack`/`Repository` to act on using a *different* field, `repository.full_name`, via the shared `Handler` base class: [5](#0-4) 

`stacks` calls `Repository.from_github_repo_name(repository_name)`, which just splits the string on `/` and does a DB lookup — with no check that the resolved repository's owner equals `repository_owner`, the organization whose secret was actually used to authenticate the request: [6](#0-5) 

Because the whole raw POST body — including both `repository.owner.login` and `repository.full_name` — is under attacker control before it is signed, anyone who legitimately possesses a webhook secret for *any* organization configured in this Shipit instance (e.g. their own GitHub org with the Shipit GitHub App installed) can construct a payload where `owner.login` = their own org (so `verify_signature` picks their own, known secret and passes) while `repository.full_name` = an entirely different organization/repo's `owner/name` that also has a Stack configured in the same Shipit instance. The signature check binds "the organization that authenticated" (`repository_owner`), but the handlers act on "the repository that is written" (`repository.full_name`) — exactly the equality the rules call out as a valid analog target: `authenticated_organization == acted_upon_repository` is never enforced.

`PushHandler`, for example, will then run `stack.sync_github(expected_head_sha: params.after)` for the victim stack: [7](#0-6) 

### Impact Explanation
This lets a party with legitimate webhook credentials for one organization/repository forge webhook events (`push`, `status`, `pull_request`, `membership`, etc.) that are dispatched against a *different* stack belonging to a different repository/organization in the same Shipit deployment — a boundary the app is meant to enforce per-tenant via the GitHub App/organization-scoped webhook secret. For `push`, this drives `GithubSyncJob` to fetch and append commits and, depending on stack configuration, can advance the stack's known head and feed the deploy pipeline (safety checks, continuous deployment) for a stack the attacker does not own or administer. This is a cross-tenant authorization boundary break rooted in the engine's own signature-verification logic (not a host misconfiguration), satisfying the "unauthorized deploy" / cross-repository-impact bar.

### Likelihood Explanation
Exploitability requires only that the attacker already legitimately controls a webhook secret for some organization known to this Shipit instance (i.e., they administer at least one org/app installation configured in Shipit) — no `ApiClient` token, GitHub App private key, or repository write access to the *victim* repository is needed. This is a realistic multi-tenant scenario for any Shipit instance serving more than one GitHub organization, matching the "unprivileged attacker breaking a deployment-trust binding" scope of this analysis.

### Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler`), after signature verification, assert that the organization/owner used to select the verifying secret (`repository_owner`) equals the owner segment of `repository.full_name` (and of `repository.owner.login` used by handlers) before dispatching to handlers. Reject the webhook (422) if they diverge, so the authenticated organization and the repository acted upon are the same value, closing the confused-deputy gap.

### Proof of Concept
1. Attacker administers `attacker-org` with the Shipit GitHub App installed; Shipit stores a webhook secret `secretA` for `attacker-org` (`Shipit.github(organization: 'attacker-org')`).
2. Attacker crafts a JSON push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(secretA, raw_body)` themselves (they legitimately know `secretA`).
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` looks up the app for `repository_owner == "attacker-org"`, verifies the HMAC against `secretA`, and passes.
5. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github` on the victim stack — an action the attacker has no legitimate authorization to trigger.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
