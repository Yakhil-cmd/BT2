## Analog Found

### Title
Spender-attested asset transfers can permanently trap AA vault funds when the attestor revokes a receiver's attestation before payout - (File: `validation.js`, `storage.js`)

### Summary
Obyte's `spender_attested` asset type is the protocol-level equivalent of a "blockable" token like USDT/USDC: the asset definer publishes a list of trusted attestors, and any output/spender address must be attested by that list *at the moment the payment unit is validated*, not at the moment funds were deposited. The attestor list itself can be changed at any time via an `asset_attestors` message. An AA (autonomous agent) acting as a vault that records a pending payout to a specific user address in persistent state — then later emits the actual `payment` message to that address in a follow-up trigger — can have that payout unit permanently rejected if the attestor revokes the recipient's attestation in between, exactly mirroring the SolverVaults "blocklisted receiver locks funds" bug class. Since AA logic has no protocol-level "cancel/edit destination" primitive, the coins remain stuck in the AA's `aa_balances` indefinitely unless the AA author explicitly coded a recovery path.

### Finding Description
For any asset with `spender_attested: true`, both issuance and transfer validation require that all output addresses be currently attested: [1](#0-0) 

The attestor list backing this check is read from the latest `asset_attestors` unit relative to the last stable ball, i.e., it can be updated at any time by the asset's definer: [2](#0-1) [3](#0-2) 

This is precisely analogous to USDT/USDC's blacklist: the ability to revoke a specific address's authorization to receive an asset lives outside the control of the vault (AA) and can change after the vault has already committed to a payout for that address in on-chain/on-DAG state.

An AA that implements a withdrawal/vault pattern typically (a) accepts a `spender_attested` asset deposit, records the depositor's claimable balance in a state var, and (b) on a later "withdraw" trigger, emits a `payment` message paying that balance back to `trigger.address` (see the generic bank/vault patterns in the codebase): [4](#0-3) 

If, between the deposit and the withdraw trigger, the asset's attestor revokes the recipient's attestation, the withdraw trigger's `payment` message will fail unit validation with `"some output addresses are not attested"`. Because this failure happens during `sendUnit`/`validateAndSaveUnit` in the AA composer, the whole response unit bounces: [5](#0-4) 

Unlike a same-trigger failure (which rolls back state and refunds the trigger's own coins via `bounce()`), the balance record that made the user eligible to withdraw was already committed in an *earlier*, already-stable unit. That commitment is not undone by the later failed withdrawal attempt — the AA's oscript has no generic mechanism to let the user redirect payment to a different (still-attested) address, because the destination is implicit (`trigger.address`) and the AA logic, once deployed, cannot be altered to add a "change receiver" feature. The funds remain permanently held in the AA's `aa_balances` for that asset with no protocol-level way to release them.

### Impact Explanation
This freezes user funds inside AA-based vaults holding `spender_attested` assets: the receiving address's eligibility can be revoked unilaterally by the asset's attestor/definer after a legitimate claim has already been recorded, and the AA (unless specifically coded with a cancel/edit-destination feature analogous to what the original report recommends) has no way to complete or redirect the payment. This is an AA fund-freezing condition reachable purely by posting ordinary units (an `asset_attestors` message from the definer plus a withdraw trigger from the user) — no privileged network role is required.

### Likelihood Explanation
Likelihood depends on adoption of `spender_attested` assets combined with AA vault patterns that defer payout to a later trigger (a common and encouraged AA design, as shown in the bundled sample AAs). Any asset issuer choosing to use `spender_attested` (e.g., for KYC/AML-gated tokens) inherently creates this risk for any AA vault built on top of that asset, since revocation is a normal, expected admin action for such assets, not an edge case.

### Recommendation
- AA design guidance/tooling should document that `spender_attested` (and similarly `transfer_condition`) assets can invalidate a previously-recorded claim before payout, and that vault-style AAs must build in a way for depositors to update/redirect their registered payout address, or to reclaim value in another form (e.g., convert to a different receivable asset) if the original address becomes unattested.
- Consider adding a core-level primitive or reference AA library pattern that decouples "amount owed" from "fixed destination address," letting the state var payout be retried against a caller-supplied (and re-validated) address on each withdrawal attempt rather than baking in `trigger.address` from an earlier, since-invalidated context.

### Proof of Concept
1. Asset definer issues asset `X` with `spender_attested: true` and attestor list `[A]` (`validateAssetDefinition`, `validateAttestorListUpdate`).
2. Attestor `A` attests user address `U` (`attestation` message).
3. `U` deposits asset `X` into vault AA `V`; `V`'s oscript records `var['balance_U'] = amount` in a `state` message, matching the pattern in [6](#0-5) .
4. Attestor `A` posts a new `asset_attestors` message removing `U` from the attestor list (`validateAttestorListUpdate`, `validation.js:2829`).
5. `U` posts a withdraw trigger to `V`. `V` emits `{app:'payment', payload:{asset:X, outputs:[{address:U, amount:...}]}}`.
6. During validation, `storage.filterAttestedAddresses` finds `U` no longer attested; `validatePaymentInputsAndOutputs` returns `"some output addresses are not attested"` (`validation.js:2632-2641`), so `aa_composer.js` bounces the response unit (`aa_composer.js:1405-1413`).
7. The earlier `var['balance_U']` state (committed in step 3's stable unit) is untouched — `U`'s asset `X` balance stays locked inside `V`'s `aa_balances` with no oscript path to reroute or reclaim it, since the AA's fixed logic always targets `trigger.address`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
