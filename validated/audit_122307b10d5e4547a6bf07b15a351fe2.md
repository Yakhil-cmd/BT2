### Title
Cross-tenant status forgery via unscoped SHA lookup in `StatusHandler` allows suppressing a blocking status on another stack's commit - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits to attach a status to using a bare, repository-agnostic `Commit.where(sha: params.sha)` query, unlike every other webhook handler in the engine which first resolves `Repository.from_github_repo_name(params.repository.full_name)` and scopes all writes to that repository. Because git commit SHAs are content-addressed and not repository-scoped, a validly-signed webhook delivered by a repository the attacker legitimately controls can attach a `success` status to a `Shipit::Commit` row belonging to an unrelated stack, provided the SHA of an attacker-crafted (or forked) commit collides with an intermediate commit of the victim's stack.

### Finding Description
The binding the question describes should hold: `blocking status for stack A's pipeline == statuses originating from stack A's own repository's CI`, i.e. only statuses whose webhook was authenticated for repo A's organization/repository should be able to affect `blocking?` on stack A's commits.

Trace:
- `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the attacker-controlled JSON payload (`params.dig('repository','owner','login')`, line 61). This authenticates *that the payload was signed by the GitHub App installed for that org*, not that the SHA inside the payload belongs to that org's repository. [1](#0-0) [2](#0-1) 
- Once signature verification passes for the attacker's own repository/org (repo B, which they legitimately own and which emits the webhook), `Shipit::Webhooks.for_event` dispatches to `StatusHandler.call(params)`. [3](#0-2) 
- `StatusHandler#process` never inspects `payload['repository']` at all; it only requires `sha`, `state`, `context`, etc., and resolves commits globally: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [4](#0-3) 
- Contrast with sibling handlers, all of which scope via the base `Handler#stacks`/`repository_name` helper or an explicit `Repository.from_github_repo_name(params.repository.full_name)` lookup before touching any record (`opened_handler.rb`, `closed_handler.rb`, `edited_handler.rb`, `labeled_handler.rb`, etc.). [5](#0-4) [6](#0-5) 
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!`, which `find_or_create_by!` on `state/description/target_url/context/created_at` with no uniqueness on `context`, so multiple `Status` rows for the same `context` can coexist on a commit. [7](#0-6) [8](#0-7) 
- `Commit#statuses` is ordered `created_at: :desc`. `Status::Group#initialize` does `reject_hidden(statuses.to_a.uniq(&:context))`, which keeps only the first (i.e. most recent, by `created_at`) status per `context`. [9](#0-8) [10](#0-9) 
- `Status::Common#blocking?` is `!success? && commit.blocking_statuses.include?(context)`. [11](#0-10) 
- `Commit#blocked?` walks `stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)`. [12](#0-11) 

Attacker's exact request: attacker owns repo B, which has the same GitHub App installed (or otherwise has a legitimately-signed webhook delivery path to this Shipit instance, per the audit's own stated attacker capability of being able to "emit webhooks from a repository they own"). Attacker creates/obtains a commit in repo B whose SHA is byte-identical to an intermediate commit on tenant A's stack — trivially achievable by forking the (typically public) repo A, since forked commit objects are literally identical SHA-1 hashes to the upstream commit, or by crafting a commit with identical tree/parent/author/committer/timestamps/message. Attacker then triggers (or fabricates via their own CI integration) a `status` GitHub event for that SHA with `state: success` and `context` equal to the exact blocking context already failing/pending on tenant A's commit, with a `created_at` newer than the existing failing status. The signature check passes because it only verifies the payload was signed for repo B's org, not that the SHA belongs to repo B. `StatusHandler` then finds tenant A's `Commit` row purely by SHA match and attaches the forged `success` status to it.

Why existing guards fail: `verify_signature` authenticates the *sender org*, not the *SHA-to-repository binding*; `drop_unhandled_event` only filters unhandled event types; there is no `ExplicitParameters` constraint tying `sha` to `repository.full_name`; and `StatusHandler` uniquely among handlers omits the `Repository.from_github_repo_name` scoping present everywhere else in `app/models/shipit/webhooks/handlers/`.

### Impact Explanation
A newer `success` status for the blocking context becomes the "kept" status per context in `Status::Group`, so `blocking?` flips to `false` on the affected intermediate commit of tenant A's stack, and `Commit#blocked?` on any downstream commit of stack A evaluates `false` where it should be `true`. This unblocks `deployable?` and the deploy button/API for stack A, allowing an unauthorized deploy of code on tenant A's stack that never passed tenant A's own CI/compliance check (e.g. a `ci.blocking` gate like `soc/compliance`). This is a payload originating from repository B mutating stack/commit state for tenant A, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy"). It is repeatable against any tenant/stack whose commit SHAs the attacker can reproduce (trivial for any public upstream repo via fork).

### Likelihood Explanation
Preconditions: (1) attacker's repo/org must have a legitimately signed webhook delivery path to the shared Shipit instance (the audit's threat model explicitly grants "emit webhooks from a repository they own" as an attacker capability); (2) the target repository (tenant A) must be public or otherwise have commit metadata (tree, parents, author/committer, timestamps, message) available to the attacker so they can reproduce an identical SHA, which is the common case for forkable/public GitHub repositories; (3) the `ci.blocking` context name must be known/guessable, which is visible in the target's `shipit.yml`/GitHub status checks in typical public-repo setups. No Shipit secrets are required. Attacker cost is low: one fork + one crafted status webhook per exploitation, fully repeatable.

### Recommendation
Scope `StatusHandler#process` (and `CheckRunHandler`, if it has the same pattern) to only apply statuses to commits belonging to the repository identified by the webhook payload, mirroring the pattern used by the PR handlers: resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and restrict the `Commit` lookup to that repository's stacks (e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { id: repository.id })`), rejecting or ignoring statuses whose payload repository doesn't match any commit's owning repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "#process does not attach a status to a commit belonging to a different repository sharing the same SHA" do
  stack_a = shipit_stacks(:shipit) # tenant A
  intermediate = stack_a.commits.create!(sha: "deadbeef" * 5, ...)
  intermediate.statuses.create!(stack: stack_a, state: 'failure', context: 'soc/compliance', created_at: 1.hour.ago)
  head = stack_a.commits.create!(sha: "cafebabe" * 5, ...)

  assert_predicate intermediate, :blocking?
  assert_predicate head, :blocked? # binding holds before attack

  # Attacker forges a webhook for repo B containing the SAME sha as `intermediate`
  forged_params = OpenStruct.new(
    sha: intermediate.sha,
    state: 'success',
    context: 'soc/compliance',
    created_at: Time.current.to_formatted_s(:db)
  )

  Shipit::Webhooks::Handlers::StatusHandler.call(
    'sha' => forged_params.sha, 'state' => 'success', 'context' => 'soc/compliance',
    'created_at' => forged_params.created_at,
    'repository' => { 'full_name' => 'attacker/repo-b' } # repo B, NOT stack A's repository
  )

  intermediate.reload
  head.reload
  refute_predicate intermediate, :blocking?   # binding is broken: flipped by repo B's payload
  refute_predicate head, :blocked?            # deploy gate bypassed on stack A
end
```
Assertions on both sides of the binding: before the forged webhook, `intermediate.blocking?` and `head.blocked?` are both `true` (statuses originated from stack A itself). After processing a webhook whose `repository.full_name` is `attacker/repo-b`, both become `false`, demonstrating that `StatusHandler` applied a status not scoped to stack A's repository, breaking the equality `blocking status for stack A == status originating from stack A's own repository`.
