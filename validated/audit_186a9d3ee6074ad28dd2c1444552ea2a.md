### Title
Single reverting secondary AA trigger cancels an entire primary AA response, blocking payouts to all other outputs in the same batch - (File: aa_composer.js)

### Summary
When a primary AA response contains a payment message with multiple output addresses, and one or more of those addresses are themselves Autonomous Agents (AAs), `handleSecondaryTriggers()` fires a trigger unit to *each* AA address in the output list sequentially using `async.eachSeries`. If any single secondary AA trigger bounces (fails), the code unconditionally reverts the entire primary response, undoing payouts to *all* other output addresses in that same message — including well-behaved, non-AA recipients who had nothing to do with the failure.

### Finding Description
`handleSecondaryTriggers` iterates over all AA addresses found among a primary AA response's output addresses and calls `handleTrigger` for each one in series: [1](#0-0) 

If any of these child (secondary) triggers bounces, `cb(bounce_message)` is called, which aborts the `async.eachSeries` loop at that element and short-circuits processing of any remaining rows. The final callback then reverts the *entire* primary trigger, not just the branch that failed: [2](#0-1) 

`revert()` rolls back the DB save-point, clears all accumulated `stateVars`, and empties `arrResponses`, wiping out every output and state change produced by the primary trigger, including outputs destined for addresses whose secondary triggers had already succeeded or that were plain non-AA recipients unaffected by the failure: [3](#0-2) 

This mirrors the reported bug class: a sequential loop over multiple recipients where a single recipient's failure (here, a secondary AA intentionally or accidentally bouncing, e.g. via a formula that always throws/bounces) blocks/cancels the outcome for every other recipient processed in the same batch, rather than isolating the failure to just the offending recipient.

### Impact Explanation
Any user or contract that triggers a primary AA which pays out to multiple addresses in one message — where at least one of those addresses is an AA — can have their entire batch of payouts undone if just one target AA (which could be deployed/controlled by an attacker, or simply buggy/adversarial) bounces its secondary trigger. This causes legitimate recipients in the same output list to be denied their funds even though their own portion of the logic succeeded, and the depositing/triggering unit's assets get returned via bounce rather than being distributed as the primary AA intended. This is an AA fund-flow disruption issue: honest counterparties lose their expected payout purely due to the unrelated failure of another output address processed later/earlier in the same list.

### Likelihood Explanation
Any attacker who controls (or can post) an AA address that is included as one of the outputs of a victim AA's payment message can deliberately make their own secondary trigger bounce (e.g., using a formula that always fails validation or intentionally calls `bounce()`), guaranteeing the primary response — and thus all co-outputs in the batch — gets reverted. This requires no special privilege: posting/deploying an AA and getting it included as a payout target (e.g., a lending, DEX, or multi-recipient distributor AA that pays arbitrary user-specified addresses) is sufficient.

### Recommendation
Do not revert the entire primary response when a single secondary AA trigger bounces. Instead, isolate the failure to the specific secondary trigger (already-bounced funds for that AA remain within its own trigger/response), and allow other secondary triggers and the primary response's other outputs to proceed unaffected. If full reversion is intentional application-level semantics, this should be clearly documented so AA authors avoid depositing multiple independent payouts within a single response reliant on secondary triggers to unrelated addresses.

### Proof of Concept
1. Deploy `AA_Victim` that, in a single trigger response, sends payment outputs to `Alice` (regular address), `Bob` (regular address), and `AA_Attacker` (an AA address).
2. Deploy `AA_Attacker` whose bound formula always causes a bounce (e.g., `bounce("always fail")` unconditionally in its trigger handling).
3. Trigger `AA_Victim`. The stabilized unit causes `handleSecondaryTriggers` to iterate the output AA addresses, calling `handleTrigger` for `AA_Attacker`.
4. `AA_Attacker`'s trigger bounces, `cb(bounce_message)` propagates, and `revert()` is invoked on `AA_Victim`'s primary trigger, rolling back the save-point.
5. Result: Alice and Bob never receive their intended payouts from `AA_Victim`, even though their portion of the logic had nothing to do with `AA_Attacker`'s failure — funds are returned to the trigger's sender via bounce instead of being distributed as designed.
