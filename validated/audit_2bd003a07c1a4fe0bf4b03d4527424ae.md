### Title
Cross-organization webhook forges membership in an unrelated org's privileged `Team` via `github_id` collision - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by the attacker-supplied `team.id` (`github_id`), and only sets `organization`/`github_team` inside the `find_or_create_by!` creation block, which is skipped when a `Team` with that `github_id` already exists. Combined with `verify_webhook_signature` returning `true` unconditionally for any org lacking a configured `webhook_secret`, an attacker can pick any configured-but-unsecured org, submit a `membership` webhook whose `team.id` collides with the real `github_id` of an existing privileged `Team` belonging to a *different* org, and get an attacker-chosen login added as a member of that real team.

### Finding Description
Intended binding: the org whose webhook signature was verified (`params.organization.login`, checked via `Shipit.github(organization: repository_owner).verify_webhook_signature`) should equal the `organization` of the `Team` row being mutated (`Team#organization`).

Actual code: [1](#0-0) 
`Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login; team.github_team = params.team }` keys the lookup only on `github_id`. The block that assigns `organization` runs only on record *creation*; if a `Team` with that `github_id` already exists (e.g. a real, privileged team belonging to org B), `find_or_create_by!` returns that existing row untouched, ignoring `params.organization.login` entirely. `process` then unconditionally calls `team.add_member(User.find_or_create_by_login!(params.member.login))`: [2](#0-1) 
`Team#add_member` simply appends the member with no authorization or org-consistency check: [3](#0-2) 

Signature verification is scoped to whichever org the *payload itself* names (`repository_owner`/`organization.login`), and is a no-op if that org has no `webhook_secret` configured: [4](#0-3) [5](#0-4) 

Exploit flow: attacker finds/knows the numeric `github_id` of a real, existing `Team` belonging to a privileged org B (team IDs are not secret — visible via GitHub API/UI for public teams, or guessable/enumerable). Attacker sends an unsigned `membership` webhook to `POST /webhooks` with `X-Github-Event: membership`, `organization.login` = some org A that Shipit has configured but for which no `webhook_secret` is set (verification trivially passes), `team.id` = org B's real team's `github_id`, `action: "added"`, `member.login` = attacker's own GitHub login. `find_or_create_by!` finds the pre-existing org-B `Team` row (the creation block never runs), and `team.add_member` persists a `Membership` linking the attacker's user to that real org-B team — a payload nominally scoped to org A mutates org B's data.

No other guard intervenes: `drop_unhandled_event`/`ExplicitParameters` only validate the JSON shape, not cross-org ownership; there is no validation in `Team` tying `github_id` to `organization` uniqueness/consistency, and `User#authorized?` trusts team membership rows directly: [6](#0-5) 

### Impact Explanation
If org B's colliding `Team` is one of the teams configured in `Shipit.github_teams`, the attacker's own GitHub-authenticated `User` (created via `User.find_or_create_by_login!`, which fetches real GitHub identity for the supplied login) becomes a member of that privileged team, causing `authorized?` to return `true` for that user going forward — a full escalation into Shipit's authorization model without ever being invited by org B, matching the "escalation into `Shipit.github_teams` authorization" and "payload for one repository/org mutating another's team" criteria. This is repeatable against any org configured without a `webhook_secret` and any `Team` row whose `github_id` the attacker can learn, across all tenants sharing this Shipit instance.

### Likelihood Explanation
Preconditions: (1) at least one org configured in `Shipit.github_apps` lacks a `webhook_secret` (a real, documented risk of misconfiguration since `webhook_secret` is optional per-org, not enforced), (2) attacker needs the target `Team`'s numeric `github_id`, which is discoverable via GitHub's team/org APIs or UI for teams the attacker can view, or by brute-forcing plausible IDs since they are sequential/small integers. No Shipit credentials, session, or API token are required — only the ability to POST to `/webhooks`. Attacker cost is a single unauthenticated HTTP request.

### Recommendation
Scope the `Team` lookup by both `github_id` and `organization` (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and verify on every request (not just at creation) that the resolved `Team#organization` equals `params.organization.login` before performing `add_member`/`delete`; raise/drop the event otherwise. Additionally consider requiring `webhook_secret` to be present for every configured org (fail closed rather than open when absent).

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership webhook cannot add a member to a team from a different, unverified organization" do
  privileged_team = shipit_teams(:some_privileged_team) # organization: "org-b", github_id: 4242
  payload = {
    'action' => 'added',
    'team' => { 'id' => privileged_team.github_id, 'name' => 'x', 'slug' => 'x', 'url' => 'https://x' },
    'organization' => { 'login' => 'org-a-without-secret' },
    'member' => { 'login' => 'attacker-login' }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)

  refute_includes privileged_team.reload.members.map(&:login), 'attacker-login',
    "team.organization (#{privileged_team.organization}) must not accept members via a payload verified under a different org"
end
```
Both sides of the intended equality — `params.organization.login` ("org-a-without-secret", the org whose signature was checked) and `Team#organization` ("org-b", the row actually mutated) — diverge, and the current code lets the mutation proceed anyway, confirming the vulnerability.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
