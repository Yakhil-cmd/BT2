### Title
Webhook organization used for signature verification is not bound to the repository the payload writes to, allowing cross-tenant sync/status forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The external report's bug class is: a numeric field is committed under a signature/hash but the code that consumes the value never re-validates it against the invariant the rest of the system assumes (probability ≤ 10,000), letting the attacker's own signed input warp downstream aggregate state in their favor. The reachable analog in this engine is a similar "verified-field vs. acted-upon-field" mismatch in the multi-organization webhook path: the HMAC signature is verified against the GitHub App config selected by `repository.owner.login` (or `organization.login`), but the handlers that actually mutate state resolve the target `Stack`/`Repository` from the independent, **unverified-as-bound** `repository.full_name` field of the same JSON body.

### Finding Description
`WebhooksController#verify_signature` computes which organization's `webhook_secret` to check against using:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)` [2](#0-1) , using `Shipit.github_app_config(organization)` to pick per-organization `webhook_secret` in a multi-tenant deployment [3](#0-2) .

Once the HMAC is accepted, the raw, fully attacker-controlled JSON body is dispatched unchanged to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) . Every handler then resolves the actual repository/stack to write to from a *different* field of the same body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler#process` uses this to trigger `stack.sync_github(expected_head_sha: params.after)` [6](#0-5) , and `StatusHandler#process` uses `Commit.where(sha: params.sha)` combined with `commit.create_status_from_github!(params)` to write commit statuses [7](#0-6) . The pull-request handlers similarly resolve their target repository/stack from `params.repository.full_name` independent of `repository_owner` [8](#0-7) .

The equality that the signature verification is supposed to enforce is:
`organization signing the request == organization owning the repository being mutated`

but the code actually enforces only:
`organization(repository.owner.login) == HMAC signer`
while separately trusting
`repository(repository.full_name) == target of stacks/commits mutated`

These two fields (`repository.owner.login` and `repository.full_name`) are never cross-checked against each other, so an attacker who legitimately controls a GitHub App/organization installation with a known `webhook_secret` on this Shipit instance (e.g., their own onboarded org) can craft a payload where `repository.owner.login` matches their own org (making the HMAC verify successfully with their own secret) while `repository.full_name` names an arbitrary **different** org/repo that is also configured in this Shipit instance. The handler layer will happily act on the state of that unrelated repository's stacks/commits.

### Impact Explanation
This breaks a cross-tenant boundary: forged `push` events could trigger `stack.sync_github` for a victim organization's stack that the attacker's app/org has no legitimate relationship with, and forged `status` events could inject/alter commit statuses (`commit.create_status_from_github!`) on a victim's commits, potentially unblocking or misrepresenting deployability checks used to gate deploys. This is a cross-repository/cross-organization write achieved without holding the victim's own webhook secret, satisfying the "cross-repository writes" / "unauthorized deploy" impact bar for a multi-tenant Shipit installation.

### Likelihood Explanation
Exploitability strictly requires the attacker to control at least one legitimate `webhook_secret` for an organization/app config configured on the target Shipit instance (i.e., a multi-org deployment where multiple tenants share the same Shipit engine, and the attacker is one of those legitimate tenants). Given that constraint, likelihood is moderate: this class of scenario is realistic for shared/hosted Shipit deployments serving several organizations, since nothing in `verify_signature` or the handlers cross-validates `repository.owner.login` against `repository.full_name`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handlers::Handler`), assert that `payload.dig('repository', 'full_name')` starts with (or otherwise matches) the same organization login used to select the verifying `webhook_secret` (i.e., `repository_owner`). Reject the request (422) if these two identities diverge, so the signing organization is always bound to the repository being mutated.

### Proof of Concept
Given a multi-tenant `secrets.yml` with two orgs, `attacker-org` (attacker-controlled, legitimate `webhook_secret`) and `victim-org` (unrelated tenant), an attacker can:
1. Build a `push` payload: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen-sha>"}`.
2. Sign the raw body with `attacker-org`'s known `webhook_secret` and send it as `X-Hub-Signature` with `X-Github-Event: push`.
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC verifies successfully because the attacker legitimately owns that secret [2](#0-1) .
4. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` [5](#0-4)  and calls `stack.sync_github(expected_head_sha: <attacker-chosen-sha>)` on the victim's stack [6](#0-5)  — a cross-organization write the attacker should not be able to trigger.

Note: This finding depends on the target Shipit instance being configured for multiple GitHub organizations (`Shipit.github_organizations` returning more than `[nil]`) [9](#0-8) ; in a single-org deployment the verifying secret and the acted-upon repository are the same tenant, so the crossing boundary only manifests in shared/multi-tenant setups.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
