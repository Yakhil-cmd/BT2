### Title
Membership webhook writes team membership keyed only by numeric `github_id`, bypassing the organization binding enforced by webhook signature verification - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a `membership` webhook against the GitHub App/webhook secret of the organization named in the payload (`organization.login`), but `MembershipHandler#find_or_create_team!` looks up the target `Team` **only** by the attacker-suppliable numeric `github_id`, never checking that the matched team actually belongs to the organization that produced the signature. An attacker who controls their own GitHub organization (and therefore its legitimate webhook secret) can forge a signed `membership` event whose `team.id` matches an existing `Team` row that Shipit created for a *different*, victim organization, and use it to add themselves (or any GitHub login) to that team.

### Finding Description
Signature verification is performed in `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) [2](#0-1) 

For `membership` events (which carry no `repository` key), `repository_owner` falls back to `organization.login`, i.e. the *attacker's own organization* if the attacker sends the webhook from an app installed on their org — the signature check succeeds because the attacker legitimately knows their own org's `webhook_secret`.

Processing then happens in `MembershipHandler`: [3](#0-2) [4](#0-3) 

`find_or_create_team!` calls `Team.find_or_create_by!(github_id: params.team.id)`. This lookup is scoped **only by `github_id`** — not by `organization`. If a `Team` record with that `github_id` already exists (created earlier for a legitimate victim organization via `Team.find_or_create_by_handle`, e.g. `Shipit.github_teams` config, or through a prior legitimate membership event), `find_or_create_by!` returns the *existing* record without re-checking or updating `organization`: [5](#0-4) 

The handler then executes `team.add_member(member)` for `action: 'added'`, using a `member.login` that the attacker fully controls in the same forged payload: [6](#0-5) 

This membership is authorization-relevant: `User#authorized?` grants access to the whole Shipit application if the user belongs to any `Team` whose `id` is in `Shipit.github_teams`: [7](#0-6) [8](#0-7) 

**Binding broken (equality that should hold but doesn't):**
`organization that authenticated the webhook (signature verified against organization.login)` ≠ `organization owning the Team row whose membership is mutated (looked up by github_id only)`.

Before the attack: victim's `Shipit.github_teams` Team row (e.g. `github_id: 12345`, `organization: "victim-org"`) has only legitimate members.
After the attack: the same row now includes the attacker (or any attacker-chosen GitHub login) as a member, added via a webhook signed by an unrelated organization ("evil-org") that the attacker fully controls.

Team `github_id` values for organizations are discoverable through GitHub's public API (`GET /orgs/{org}/teams` for teams the attacker can see, or by having once been a collaborator/member), so guessing/knowing the target `github_id` is feasible without any privileged Shipit credential.

### Impact Explanation
This escalates into `Shipit.github_teams` authorization — one of the explicitly listed High-severity impacts. Adding an arbitrary GitHub identity to a `Team` that gates `force_github_authentication` effectively grants that identity full authenticated access to the Shipit application (stacks, deploys, API client creation depending on further checks), without ever needing a legitimate invitation to the victim's real GitHub team, an `ApiClient` token, or a Shipit session cookie beforehand — only control of one's own GitHub organization/app installation to sign the forged webhook.

### Likelihood Explanation
Requires only: (1) the attacker owns/administers any GitHub organization with a Shipit-recognized GitHub App/webhook config (attacker's own org, likely a normal onboarding requirement, not a privileged Shipit credential), and (2) knowledge of the victim's team's numeric `github_id`, obtainable via GitHub's public team APIs or historical membership. No Shipit account, cookie, or API token is required to send the webhook itself — only a valid signature computable from the attacker's own webhook secret. This is a realistic, unprivileged-attacker path, directly analogous to the reported bug class (a validation/authorization check enforced in one code path but omitted in a related one — here, the org-scoped signature check is not reflected in the team lookup scope).

### Recommendation
Scope the `Team` lookup in `MembershipHandler#find_or_create_team!` (and any other webhook-driven `Team` mutation) by both `github_id` **and** `organization` (matching the organization that produced the verified signature), rejecting/creating a new record rather than reusing/mutating a team belonging to a different organization. Additionally, verify that `params.organization.login` matches the `repository_owner` used for signature verification before trusting `team`/`member` fields in the payload.

### Proof of Concept
1. Attacker creates/owns GitHub org `evil-org`, installs the same type of GitHub App Shipit expects, and knows `evil-org`'s `webhook_secret` (legitimately configured for their own org).
2. Attacker discovers (via GitHub's public team API, or prior legitimate access) the numeric `github_id` of a `Team` Shipit already tracks for `victim-org` (e.g. one of `Shipit.github_teams`).
3. Attacker crafts a `membership` webhook payload:
```json
{
  "action": "added",
  "team": { "id": <victim_team_github_id>, "name": "Victim Team", "slug": "victim-team", "url": "https://api.github.com/teams/<id>" },
  "organization": { "login": "evil-org" },
  "member": { "login": "attacker-github-login" }
}
```
4. Attacker signs the raw body with `evil-org`'s webhook secret (`X-Hub-Signature: sha1=...`) and POSTs to `/webhooks` with `X-Github-Event: membership`.
5. `verify_signature` resolves `repository_owner` to `"evil-org"` and successfully verifies the signature using `evil-org`'s secret.
6. `MembershipHandler#find_or_create_team!` finds the pre-existing `victim-org` `Team` row by `github_id` alone and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`, granting the attacker's GitHub identity membership in a team that authorizes access to Shipit under `User#authorized?`.

      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end
