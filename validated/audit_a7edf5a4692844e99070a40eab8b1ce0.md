### Title
CCMenu API token authorizes one stack but is honored against any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` authenticates a caller by verifying an `ApiClient` token, but then resolves the target `Stack` directly from `params[:stack_id]` without checking that the authenticated `ApiClient` is actually scoped to that stack. Every other API controller resolves the stack through the `stacks` scope, which restricts the visible stacks to `current_api_client.stack_id` when the client is stack-scoped. The CCMenu endpoint skips this scoping, so a token that authorizes exactly one stack ("the stack a token authorises") can be replayed with a different `stack_id` in the URL to read a different stack's build status ("the stack it touches").

### Finding Description
`Shipit::ApiClient` supports being restricted to a single stack via its `stack` association, and `Shipit::Api::BaseController#stacks`/`#stack` enforce that restriction for the rest of the API: [1](#0-0) 

`ApiClient#check_permissions!` only checks the coarse `permissions` array (e.g. `read:stack`) and has no notion of *which* stack the operation targets: [2](#0-1) 

`CCMenuController`, however, authenticates the same way (`ApiClient.authenticate(params[:token])`) but resolves the stack independently of the authenticated client: [3](#0-2) 

Because `stack` here is `Stack.from_param!(params[:stack_id])` instead of `stacks.from_param!(params[:stack_id])`, the `current_api_client.stack_id` restriction from `BaseController` is never applied. Any `ApiClient` token that carries `read:stack` permission — including one created and scoped to a single stack, such as the fixture `here_come_the_walrus` (`stack: shipit`) — passes `authenticate_api_client` and `require_permission :read, :stack`, and can then be pointed at an arbitrary `stack_id` in the URL to read that other stack's CCMenu payload (name, last build status/label/time, web URL): [4](#0-3) 

Contrast this with `Api::HooksController`, which correctly derives `stack_id` from the scoped `stack` helper before scoping its `Hook` queries: [5](#0-4) 

Before the attack: a token minted for stack A (`stack_id` set to A on the `ApiClient` row) is only ever supposed to resolve stack A via `stacks`/`stack`.
After the attack: the same token, submitted with `stack_id` = B in the CCMenu route, resolves stack B directly through `Stack.from_param!`, bypassing the per-client stack binding entirely. The equality that should hold — `token.authorized_stack == stack_touched_by_request` — is broken.

### Impact Explanation
This is an unauthenticated-relative-to-target read: a holder of a stack-scoped, low-privilege `read:stack` token can enumerate and read the build/deploy status of stacks they were never granted access to, across repository/team boundaries, matching the High-impact category of "unauthenticated read of stack state ... output" for stacks outside the token's authorized scope.

### Likelihood Explanation
Any environment issuing stack-scoped `ApiClient` tokens (which is a documented, supported configuration — see the `here_come_the_walrus` fixture and the "an api client scoped to a stack will only see that one stack" test) is affected. Exploitation only requires changing the `stack_id` path segment of a request that already carries a valid, narrowly-scoped token — no additional privilege is needed.

### Recommendation
Change `CCMenuController#stack` (and any other controller resolving `Stack` outside of `BaseController#stack`) to resolve through the scoped `stacks` relation, e.g. `stacks.from_param!(params[:stack_id])`, so the stack actually touched is always constrained by `current_api_client.stack_id` the same way it is throughout the rest of the API.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id = A` with `permissions: ['read:stack']` (as in fixture `here_come_the_walrus`).
2. Obtain its `authentication_token`.
3. Request `GET /api/stacks/<owner>/<repo-B>/<branch-B>/ccmenu?token=<token>` for a different stack B.
4. Observe `Shipit::Api::CCMenuController#show` renders stack B's CCMenu status (name, last build status/label/time, web URL) despite the token being scoped only to stack A, because `stack` in `app/controllers/shipit/api/ccmenu_controller.rb` bypasses the `stacks` scoping used everywhere else.
