### Title
Missing Cosigner Authorization Check in Multisig Signing Request Handler Allows Any Paired Device to Trigger Unauthorized Spend Requests - (File: wallet.js)

### Summary
`wallet.js`'s `handleMessageFromHub` handler for the `"sign"` subject accepts a signing request for any locally-controlled address from **any device that is merely a correspondent** (paired via the lightweight, self-service pairing mechanism in `device.js`), without verifying that the sender is actually listed as an authorized cosigner of that address. The verification check exists in the code but is explicitly commented out, mirroring the OpenClaw bug class where a trivially-obtained pairing/correspondent relationship is trusted as sufficient authorization for a privileged action instead of checking the real permission list (here, the shared-address signing-path membership).

### Finding Description
When a device receives a `"sign"` message, `findAddress` dispatches to `ifLocal` if the target address is one of the recipient's own (possibly shared/multisig) addresses: [1](#0-0) 

The check that would confirm the sender (`from_address`) is actually a legitimate cosigner of `body.address` is present only as a comment:

//    if (sender_rows.length !== 1)

``` [2](#0-1) 

Contrast this with the `ifRemote` branch of the same handler, which *does* correctly verify that the requester is a listed cosigner before forwarding the signing request: [3](#0-2) 

Reaching this code path only requires becoming a "correspondent" device, which is achieved via the self-service pairing flow (`handlePairingMessage`) — any device that obtains a `pairing_secret` (e.g., shared casually, brute-forced, or leaked in a QR/URI) becomes a trusted correspondent with no further vetting: [4](#0-3) 

Because `correspondent_devices` membership (established merely by pairing) is treated as sufficient trust to originate a `"sign"` request for *any* of the victim's local addresses — including shared/multisig addresses the sender has no legitimate cosigning role in — this is the same root-cause pattern as CVE-2026-44110: a low-assurance pairing/correspondent store is used as an authorization allowlist for a privileged command, instead of checking the actual permission set (`shared_address_signing_paths` / `extended_pubkeys`, analogous to the room control-command allowlist).

### Impact Explanation
An attacker who merely pairs with a victim's wallet device (trivial, self-service, no privileged relationship needed) can send crafted `"sign"` requests referencing the victim's addresses, including shared/multisig addresses where the victim is a cosigner alongside others. This triggers unit validation and a `"signing_request"` event carrying an attacker-supplied `unsigned_unit` (payment message, outputs, private payloads) for the local wallet to process/sign, even though the attacker was never granted a signing path for that address. In multi-device or multisig setups this bypasses the intended cosigner allowlist and can be leveraged to solicit signatures on attacker-crafted transactions (e.g., redirecting outputs), enabling unauthorized spending from shared funds if the request is acted upon — the exact class of harm (unauthorized spend) called out for this bug family.

### Likelihood Explanation
Pairing with a target device is a normal, low-barrier operation by design (pairing secrets are meant to be shared to establish new correspondents), so an attacker can trivially become a "correspondent" without ever being added as a legitimate cosigner of any shared address. Once paired, sending a `"sign"` message with an arbitrary local `address`/`signing_path` requires no further authorization, directly hitting the unguarded `ifLocal` branch.

### Recommendation
Restore and enforce the cosigner check that was commented out in the `ifLocal` branch: before emitting `"signing_request"` or invoking `network.handleOnlineJoint`, verify that `from_address` is actually a listed signer for `body.address`/`body.signing_path` (e.g., via `shared_address_signing_paths` or `extended_pubkeys`), returning `callbacks.ifError("sender is not cosigner of this address")` otherwise — matching the check already correctly performed in the `ifRemote` branch.

### Proof of Concept
1. Attacker device pairs with victim's wallet device using a pairing secret (self-service `pairing` message), becoming a `correspondent_devices` entry.
2. Victim's wallet has a shared/multisig address `S` where the victim is one cosigner and unrelated third parties are the others; the attacker device is not a cosigner of `S`.
3. Attacker sends a device message: `{subject: "sign", body: {address: S, signing_path: "r.0", unsigned_unit: <attacker-crafted unit>}}`.
4. `handleMessageFromHub` → `findAddress` resolves `S` as local → `ifLocal` is invoked with no check that the attacker is an authorized signer of `S`.
5. The wallet proceeds to validate/emit `"signing_request"` for the attacker-supplied unit, soliciting the victim to sign a transaction from address `S` that the attacker was never entitled to request signatures for, bypassing the intended cosigner allowlist.
