### Title
CCMenu controller bypasses ApiClient stack-scoping, allowing a stack-scoped token to read the build status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the stack-resolution logic used by every other API controller, replacing the scope-checked lookup with a raw, unscoped `Stack.from_param!(params[:stack_id])`. This breaks the trust binding "the stack a token authorizes" (`ApiClient#stack_id`) vs. "the stack the request actually touches" (`params[:stack_id]`), letting a stack-scoped API token read build/deploy status for any stack in the instance, not just the one it was issued for.

### Finding Description
Every other controller under `Shipit::Api` inherits stack resolution from `BaseController`, which enforces scoping to the authenticated client's stack: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is scoped to a specific stack (`stack_id` present), and only falls back to `Stack.all` for unscoped/global clients.

`CCMenuController`, however, does not use `stack`/`stacks` from `BaseController`; it defines its own `stack` method that ignores `current_api_client` entirely and resolves any stack the caller names in the URL: [2](#0-1) 

The `require_permission :read, :stack` declaration only checks that the authenticated `ApiClient#permissions` array contains `"read:stack"` — it never checks that the *specific* stack being accessed matches the client's `stack_id`: [3](#0-2) 

So the equality that should hold is:
`current_api_client.stack_id == stack.id` (when `stack_id` is present)

but for CCMenu it is never enforced — `stack` is derived purely from `params[:stack_id]`, independent of the authenticated token's `stack_id`.

`ApiClient` records can be scoped to a single stack (the `belongs_to :stack, optional: true` association plus `stack_id` filtering in `BaseController#stacks`), a feature that is exercised by other read-only API consumers. Because `CCMenuController` skips this filter, any valid, currently-authenticated `read:stack` token — including one that was legitimately scoped to a single stack via the `ApiClient` model — can be replayed against `/api/stacks/:stack_id/ccmenu.xml` for an arbitrary `stack_id` and will successfully render that other stack's data.

### Impact Explanation
The rendered CCMenu XML exposes stack build state (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) for the targeted stack: [4](#0-3) 

This is an unauthenticated-relative-to-the-target-stack read of stack/deploy state: a caller holding a token that should only be able to see stack A's CI/deploy status can enumerate and read the status of every stack in the Shipit instance, including private/internal stacks the token was never granted access to. This matches the "unauthenticated read of stack state, task streams or deploy output" High-severity category — it is a scope-authorization boundary bypass, structurally identical to the reported bug class (a value that should be constrained by a verified/authorized binding, but is instead taken unchecked from attacker-controlled input).

### Likelihood Explanation
Exploitation requires only a valid, currently-issued `read:stack` API token (the minimum-privilege client type Shipit issues for CCMenu/status-reading use cases) and knowledge or guessing of another stack's `to_param` (often just `owner/repo/environment`, which is frequently public or predictable). No write access, no session, and no elevated permission is required — only substitution of the `stack_id` route parameter. This is a straightforward, deterministic bypass with no timing/race conditions, making it highly likely to be exploitable by anyone holding a low-privilege, single-stack-scoped token.

### Recommendation
Make `CCMenuController` reuse `BaseController`'s scoped resolution instead of bypassing it:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that `stacks` (which filters by `current_api_client.stack_id` when scoped) is always consulted, restoring the invariant that a scoped token can only ever resolve to the stack it was issued for.

### Proof of Concept
1. As an admin, create two stacks, `stack-a` and `stack-b`.
2. Create/observe an `ApiClient` with `permissions: ["read:stack"]` scoped to `stack-a` (`stack_id` set to stack-a's id) — e.g. via the CCMenu URL flow at `app/controllers/shipit/ccmenu_url_controller.rb`, or any other mechanism that produces a stack-scoped, `read:stack`-only token.
3. Using that token's `authentication_token`, request:
   `GET /api/stacks/stack-b_owner/stack-b_repo/stack-b_env/ccmenu.xml?token=<stack-a-scoped-token>`
4. Observe the response returns HTTP 200 with `stack-b`'s build status XML (`lastBuildStatus`, `lastBuildLabel`, etc.), even though the token was only ever authorized for `stack-a`. Compare against any other `Api::*Controller` (e.g. `StacksController#show` for `stack-b` with the same token), which correctly returns 404/empty results due to `stacks.from_param!` scoping — confirming `CCMenuController` is the outlier that skips the scope check. # frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
