### Title
Rule engine field extraction omits `old_string`/`old_text` support for `MultiEdit`, silently bypassing block rules that Edit-based rules would catch - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._extract_field` implements tool-specific fallback extraction for `Edit`/`Write` (supporting `old_text`/`old_string`, `new_text`/`new_string`, `content`, `file_path`) but the `MultiEdit` branch only supports `file_path` and `new_text`/`content` — it has no case for `old_text`/`old_string`. Any block rule authored against the "old string" representation of an edit (e.g., to prevent stripping a security marker, secret pattern, or safety check from a file) matches when the operation is performed via `Edit` but is silently skipped when the semantically identical operation is performed via `MultiEdit`.

### Finding Description
`_rule_matches` (`plugins/hookify/core/rule_engine.py:96-125`) requires every `Condition` to resolve to a non-`None` field value via `_extract_field`; if the field can't be extracted, `_check_condition` returns `False` and the rule is treated as non-matching [1](#0-0) .

In `_extract_field`, the `Edit`/`Write` branch explicitly maps `old_text`/`old_string` to `tool_input.get('old_string', '')`: [2](#0-1) 

But the `MultiEdit` branch only handles `file_path` and `new_text`/`content`, concatenating `new_string` across all edits — there is no equivalent extraction of `old_string`/`old_text`: [3](#0-2) 

Since `MultiEdit`'s `tool_input` structure nests `old_string`/`new_string` pairs inside an `edits` array rather than at the top level, the generic "direct field" check at the top of `_extract_field` (`if field in tool_input`) also cannot find `old_string` for `MultiEdit`, so extraction returns `None` for that field [4](#0-3) .

This is invoked from `plugins/hookify/hooks/pretooluse.py`, which loads user-defined `.claude/hookify.*.local.md` rules and dispatches `Bash`, `Edit`, `Write`, `MultiEdit` (all bucketed to the `file` event) directly into `RuleEngine.evaluate_rules` based on the `tool_name`/`tool_input` that Claude Code passes for the tool call actually executed [5](#0-4) . Because Claude's tool selection (Edit vs. MultiEdit) can be steered by attacker-supplied repository/prompt content (via ordinary prompt-injection through file/issue/PR content processed in a session), an attacker who cannot directly force the model to call a specific tool can still influence its choice, and any block-rule author who wrote a condition on `old_text`/`old_string` intending to cover file-edit operations broadly will have that protection silently bypassed whenever the edit is performed with `MultiEdit` instead of `Edit`.

### Impact Explanation
This breaks the invariant "a matching block rule must reliably deny the protected operation": a rule with `tool_matcher: "Edit|MultiEdit"` (or `"*"`) and a condition on `old_text`/`old_string` will correctly block dangerous `Edit` calls but pass through functionally identical `MultiEdit` calls without any warning or block, because the condition field resolves to `None` and is treated as non-matching. This is a logic-level guard bypass / misbinding of security state as described in the target impact class — a security control that appears effective is quietly inert for one of the four documented tool types the plugin explicitly claims to support.

### Likelihood Explanation
No special privileges are needed: this only requires (1) a repo/user that has configured a hookify block rule referencing `old_text`/`old_string` for file-edit protection, and (2) the model performing the edit via `MultiEdit` rather than `Edit` — a routine and common occurrence, further steerable via ordinary prompt-injection content in the repository that the agent processes. The bug is deterministic and 100% reproducible given those preconditions.

### Recommendation
Add `old_text`/`old_string` handling to the `MultiEdit` branch of `_extract_field`, mirroring the `new_text`/`content` concatenation logic (e.g., `' '.join(e.get('old_string', '') for e in edits)`), so rules behave consistently across `Edit`, `Write`, and `MultiEdit`.

### Proof of Concept
Unit test against `RuleEngine.evaluate_rules`:
1. Define a block `Rule` with `tool_matcher="Edit|MultiEdit"`, `Condition(field="old_string", operator="contains", pattern="SECURITY_CHECK")`.
2. Case A — `tool_name="Edit"`, `tool_input={"file_path": "x.py", "old_string": "# SECURITY_CHECK", "new_string": ""}` → assert `evaluate_rules` returns a `deny`/`block` result.
3. Case B — `tool_name="MultiEdit"`, `tool_input={"file_path": "x.py", "edits": [{"old_string": "# SECURITY_CHECK", "new_string": ""}]}` → currently returns `{}` (no block), demonstrating the bypass; expected/fixed behavior should also return a `deny` result identical to Case A.
