### Title
Cross-Organization Webhook Signature Confusion Enables Forged Deploy-Triggering Events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-GitHub-App deployments, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification based on an attacker-controlled JSON field (`repository.owner.login` / `organization.login`), while the downstream event handlers act on a *different* field (`repository.full_name`) to resolve the actual `Stack`/`Repository` to mutate. An attacker who legitimately controls (or is an admin/installer of) any one of the organizations configured in `secrets.github` can craft a raw POST body whose signature validates against their *own* known `webhook_secret`, while the payload's `repository.full_name` points at a completely different, victim organization's stack. This is the same class of bug as the reported `TokenSale._processPrivate` flaw: one value (`amount`/decimal precision, here `repository_owner`) is used for the check/authorization step while a related but distinct value (`transferred amount`/state update, here `repository.full_name`) is the one actually acted upon — the two are never enforced to be equal.

### Finding Description
`verify_signature` computes the signing organization purely from attacker-supplied JSON: [1](#0-0) 

That organization is used to pick the `GitHubApp` instance whose `webhook_secret` verifies the HMAC over the raw body: [2](#0-1) [3](#0-2) 

Multiple, independently-secreted GitHub App configurations are a supported, documented deployment mode: [4](#0-3) [5](#0-4) 

Once the signature check passes, the entire raw body is re-parsed and dispatched to event handlers keyed only by the `X-Github-Event` header, with no re-validation that `repository.owner.login` (used for signing) matches the repository actually referenced by the payload's `full_name`: [6](#0-5) 

Repositories/stacks are resolved from the `owner`/`name` pair embedded in the payload (e.g. `repository.full_name`), independent of whichever `repository.owner.login` value was used to select the signing secret: [7](#0-6) [8](#0-7) 

Because the endpoint is a public, unauthenticated HTTP POST (not a GitHub-mediated relay — the engine itself computes the HMAC over whatever body it receives), the attacker fully controls both the signature-selecting field and the action-consuming field independently, breaking the equality that should hold:
`organization whose secret authenticated the request == organization/repository the handler is permitted to act on`.

### Impact Explanation
An attacker who is the legitimate installer/admin of *any one* org configured in a multi-org Shipit deployment (and therefore knows that org's `webhook_secret`) can forge signed webhook events that are processed as belonging to any *other* configured org's repository. This can:
- Trigger `GithubSyncJob` with attacker-chosen `expected_head_sha` for a victim stack, per the `push` handler dispatch shown in tests.
- Inject fabricated commit `status`/`check_suite` results for a victim's commits, which downstream deploy/merge gating logic treats as authoritative CI signal — enabling an unauthorized deploy or merge decision for a repository the attacker does not control.

This satisfies the "unauthorized deploy, rollback or merge" Critical/High impact criteria, since it lets an attacker manipulate deploy-gating state for a repository outside their authorization scope using only a webhook secret belonging to an unrelated org.

### Likelihood Explanation
Requires the deployment to use the multi-organization GitHub App configuration (documented, supported feature) and requires the attacker to control/administer at least one of the configured GitHub Apps (i.e., know one org's `webhook_secret`) — a realistic scenario for shared/multi-tenant Shipit installations serving several organizations. No GITHUB webhook relay validation ties the signing org to the acted-upon repository, so exploitation is a direct, unauthenticated HTTP request to `/webhooks` with a crafted JSON body and matching HMAC header.

### Recommendation
After successful signature verification, re-derive the acting organization strictly from the same field used for signing (`repository.owner.login` / `organization.login`) and require that it matches the organization implied by `repository.full_name` before dispatching to any handler. Alternatively, scope handler dispatch/lookup to only the `GitHubApp`/organization that successfully verified the signature, rejecting any payload whose `repository.owner.login` differs from the verifying organization.

### Proof of Concept
1. Deploy Shipit configured with two GitHub App organizations, `OrgA` (attacker-controlled installer, secret known to attacker) and `OrgVictim` (hosts stack `OrgVictim/prod-repo`), per `lib/shipit.rb#github_app_config`.
2. Attacker crafts JSON body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgVictim/prod-repo" },
  "sha": "<attacker-chosen-sha>",
  "state": "success",
  "target_url": "https://ci.example.com/fake"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and sends `POST /webhooks` with `X-Github-Event: status`.
4. `verify_signature` selects `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and validates successfully against the attacker's own known secret: [2](#0-1) [3](#0-2) 
5. `create` dispatches the parsed body to the `status` handler, which resolves and mutates commit status for `OrgVictim/prod-repo` using `full_name`, despite the signature having authenticated only `OrgA`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
