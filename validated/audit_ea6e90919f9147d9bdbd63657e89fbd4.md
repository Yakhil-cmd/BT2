### Title
Attacker-controlled PR label names inject `SSH_ASKPASS`/arbitrary env keys into `git` subprocess invocations — (File: app/models/shipit/review_stack.rb / lib/shipit/stack_commands.rb / lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) directly into the environment hash with no key allowlist, and `LabelCapturingHandler#capture_labels` persists label names verbatim from the webhook payload. `StackCommands#env` merges `@stack.env` unfiltered into the environment used for `git` invocations in `StackCommands#fetch`/`#git_clone`, and `Command#start` passes that hash straight to `PTY.spawn`, so an attacker-chosen label such as `SSH_ASKPASS` becomes an environment variable inherited by the `git` subprocess.

### Finding Description
The broken binding is: `stack.env.keys` should be a subset of a defined, safe environment-variable allowlist, but instead `stack.env.keys ⊇ pull_request.labels.map(&:upcase)` with zero restriction.

Trace:
1. `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) writes `pull_request.update!(labels: params.pull_request.labels.map(&:name))` directly from the webhook body — label names are free-form strings from `POST /webhooks`, validated only as `String` by the `params` schema (no charset/allowlist restriction, as shown by the test accepting emoji label names).
2. `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does:
   ```ruby
   super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })
   ```
   There is no key filtering/allowlist here — any label name becomes an env var key.
3. `StackCommands#env` (`lib/shipit/stack_commands.rb:13-15`) does `super.merge(@stack.env)`, again with no filtering.
4. `StackCommands#fetch` / `#git_clone` (`lib/shipit/stack_commands.rb:27-35`, `112-114`) call `git(..., env:, chdir: ...)`, which becomes `Command.new("git", ..., env: env)` (`lib/shipit/commands.rb:28-33`).
5. `Command#start` (`lib/shipit/command.rb:85-105`) builds `unbundled_env = BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` and calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` — the merged hash, including any attacker-supplied key such as `SSH_ASKPASS`, is passed as the literal `env` argument to `Process`/`PTY.spawn`, so it becomes the subprocess's environment.

Contrast this with the deliberately-restricted paths: user-supplied deploy/task variables from `TasksController#task_params`/`DeploysController#deploy_params` are passed through `EnvironmentVariables#permit` (`lib/shipit/environment_variables.rb:13-18`), which raises `NotPermitted` for any key not in the `deploy_variables`/`variables` allowlist (`app/models/shipit/task_definition.rb:63-65`, `app/models/shipit/deploy_spec.rb:174-180`). No equivalent `permit` call is applied to `ReviewStack#env`'s label-derived keys before they are merged into the `git` command's env — this is the guard that exists elsewhere in the codebase but is absent for the label-to-env-var mechanism.

Because `git` (and the `ssh`/`ssh-askpass` chain it may invoke for SSH remotes) honors process environment variables such as `SSH_ASKPASS`, an attacker who can add a label to their own pull request (as scoped in the audit rules) can set `SSH_ASKPASS` — or other consequential variables like `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `LD_PRELOAD` if the shell honors it — on the process environment of the `git fetch`/`git clone` invocations that run for their own `ReviewStack`.

### Impact Explanation
This is a Remote-Code-Execution-class primitive: the attacker controls an environment variable in the process spawned via `PTY.spawn` for `git` operations on the Shipit deploy host (`lib/shipit/command.rb:92`). If `git` ends up shelling out to `ssh` for the repository's remote (e.g. an `ssh://` git URL) under conditions where OpenSSH consults `SSH_ASKPASS` (no controlling terminal, or `SSH_ASKPASS_REQUIRE=force` also settable by the same mechanism), the attacker-named program is invoked with `ssh`'s privileges on the deploy host. The blast radius is scoped to the review stack/repository whose PR carries the label, but it runs as the same user executing all other Shipit tasks — a container escape or reused deploy credentials could extend the blast radius further. This matches the Critical/RCE class (`Command`/`PTY.spawn`) called out in the audit's impact categories.

### Likelihood Explanation
Preconditions: the repository must have Review Stacks enabled with `provisioning_behavior` of `allow_with_label` (or `allow_all`, since `capture_labels?`/`ReviewStack#env` do not check the provisioning behavior at all — once a `ReviewStack` exists, any label capture applies). The attacker only needs to be able to add a label to a PR and have that PR tracked by an existing `ReviewStack` (per the audit's assumption that an unprivileged actor can do this). No secrets, tokens, or maintainer/team access are required. The exploit is fully repeatable: every `fetch`/`git_clone` triggered for that stack (on every push, PR sync, or periodic re-fetch) re-executes with the poisoned environment. Actual code execution requires `git`'s `ssh` invocation to consult `SSH_ASKPASS` (dependent on transport being SSH and terminal conditions, or use of `SSH_ASKPASS_REQUIRE=force` which the same unfiltered channel can also inject) — so full RCE reliability depends on transport/OpenSSH configuration, but the underlying invariant violation (fork-controllable key reaching the `git` subprocess env with no allowlist) is unconditional and directly demonstrable.

### Recommendation
Apply an explicit allowlist to `ReviewStack#env`'s label-derived keys, mirroring `EnvironmentVariables#permit` used for deploy/task variables — e.g., only allow keys matching a repository-configured label-prefix pattern (e.g., `LABEL_*`), or explicitly reject any key colliding with sensitive environment variable names (`SSH_ASKPASS`, `GIT_ASKPASS`, `GIT_SSH_COMMAND`, `LD_PRELOAD`, `SSH_ASKPASS_REQUIRE`, `PATH`, etc.) before merging into `super` in `app/models/shipit/review_stack.rb:84-93`. Additionally, consider not exposing label-derived environment variables to the `git fetch`/`git_clone` invocations in `lib/shipit/stack_commands.rb` at all — restrict `@stack.env`'s label-derived portion to task/deploy steps where they were originally intended for template substitution, not raw `git` process environments.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (or a new stack_commands_test.rb)
test "SSH_ASKPASS label reaches the git fetch subprocess environment" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.update!(labels: ["ssh_askpass"])

  commands = Shipit::StackCommands.new(stack)
  stack.stubs(:clear_git_cache!)
  stack.git_path.stubs(:exist?).returns(false)

  command = commands.fetch

  # Binding under test: stack.env keys must be a subset of an allowlist;
  # here it is NOT, and SSH_ASKPASS leaks into the git invocation env.
  assert_equal "true", command.env["SSH_ASKPASS"]
  assert_equal %w[git], command.args.first(1)
end
```
This demonstrates the equality `command.env["SSH_ASKPASS"] == "true"` holds after only labeling a PR — the value that should never be attacker-settable in a `git` subprocess's environment.
