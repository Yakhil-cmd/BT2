### Title
Webhook signature is validated against the sender-org's own secret, not the org that owns the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the inbound HMAC against by reading `repository.owner.login`/`organization.login` straight out of the *untrusted, attacker-suppliable* JSON body, then uses that same body's `repository.full_name` to decide which `Shipit::Repository`/`Stack` the event actually acts on.

### Finding Description
`verify_signature` computes the org used for secret lookup from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves the app config (and its `webhook_secret`) purely from this attacker-supplied string: [3](#0-2) 

The signature check (`OpenSSL::HMAC.hexdigest` compared with `X-Hub-Signature`) proves only that *the payload was signed by whichever org's secret was looked up* — i.e. it proves the payload came from the GitHub App installed on `repository.owner.login`. It does **not** independently bind that org to the repository the downstream handlers operate on.

Downstream handlers (e.g. `PushHandler`) trust `repository.full_name` (via `Repository.from_github_repo_name`) to locate the target `Stack`/`Repository`, and take action such as enqueuing `sync_github`: [4](#0-3) [5](#0-4) 

In this Shipit deployment model, a single instance can be configured with multiple independent GitHub Apps/organizations (each with its own `webhook_secret`), as shown in the multi-app secrets fixture: [6](#0-5) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon repository) are two independent strings inside the *same* JSON body that is only integrity-protected as a whole against a secret chosen by one of those fields, an operator that controls **their own** legitimate GitHub App installation (e.g. `OrgTwo` in the multi-org config) knows that org's `webhook_secret` and can craft a raw JSON payload where `repository.owner.login = "orgtwo"` (so `verify_signature` looks up and passes with OrgTwo's own known secret) while `repository.full_name = "orgone/victim-repo"` — a completely different, unrelated organization's repository tracked by the same Shipit instance. Signature verification succeeds because it is computed against the full raw body using OrgTwo's own secret, which the attacker legitimately possesses, yet the handler that runs afterward (`PushHandler`, `status`, `check_suite`, `membership`, `pull_request` handlers, etc.) resolves the target `Stack`/`Repository`/`Team` using `full_name`/`repository` fields that point at OrgOne's resources. This breaks the equality "organization that authenticated == repository that is written": the org whose secret authenticated the request is not enforced to be the owner of the repository the handlers mutate.

This lets an attacker who legitimately administers one configured GitHub App/org on a shared Shipit instance forge webhook events (pushes, statuses, check-suite completions, pull-request events, membership changes) that get processed as if they originated from a completely different tenant/organization also hosted on that instance, triggering unauthorized `sync_github` jobs, fake commit statuses, fabricated check-run states that can gate/unblock deploys, or forged PR/review-stack lifecycle events against repositories/stacks the attacker does not control.

### Impact Explanation
This crosses a repository-ownership boundary: a party who is only trusted for organization A's webhook traffic can inject events that are processed against organization B's repositories/stacks on the same shared Shipit engine, causing unauthorized state changes to another tenant's deployment pipeline (e.g., forcing sync jobs, forging commit/check statuses that gate merges and deploys). This corresponds to the report's "High" bucket (escalation across an authorization/repository boundary via unauthenticated/mis-authenticated processing of cross-tenant state).

### Likelihood Explanation
Requires the Shipit instance to be configured with multiple GitHub App organizations (a supported, documented configuration — see `test/dummy/config/secrets_double_github_app.yml`), and requires the attacker to control (administer) at least one of those configured GitHub Apps so they know its `webhook_secret`. Given that setup, forging the cross-owner payload is straightforward (single crafted HTTP POST), so likelihood is Medium, gated by the multi-tenant configuration precondition.

### Recommendation
After signature verification succeeds for organization `O` (derived from `repository.owner.login`/`organization.login`), enforce that every repository-scoped identifier processed by the handlers (`repository.full_name`, `repository.owner.login` used again downstream, `organization.login`) is consistent with `O` — i.e., reject the event if `repository.full_name.split('/').first != O`. Alternatively, resolve the target `Repository`/`Stack` first, then verify the signature using the secret configured for *that* repository's owner exclusively, never trusting attacker-suppliable org fields to pick the verification key independently from the field used to pick the acted-upon resource.

### Proof of Concept
1. Configure Shipit with two organizations, `orgone` and `orgtwo`, each with distinct `webhook_secret` values (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the administrator of the `orgtwo` GitHub App (attacker), craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "orgtwo" },
    "full_name": "orgone/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgtwo_webhook_secret, raw_body)>` using the attacker's legitimately known `orgtwo` secret.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "orgtwo")`, validates the HMAC successfully against `orgtwo`'s secret.
6. `PushHandler#process` resolves stacks via `repository.full_name = "orgone/victim-repo"`, and enqueues `sync_github` for OrgOne's stack — despite the request never being signed by anything associated with OrgOne.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
