Now I have enough information to write the finding. The pattern is clear:

- `_requestKLAYTransfer` checks `isRunning` (and `isLockedKLAY`) before allowing outbound transfers
- `handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer` do **not** check `isRunning` (or lock flags) before executing inbound asset transfers

This is the direct Kaia analog of the `setbidtobuy`/`islisted` bug.

### Title
`handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` bypass `isRunning` and lock-state guards, allowing asset transfers when the bridge is stopped — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

### Summary

The bridge contracts expose a `setRunningStatus(false)` / `start(false)` mechanism and per-token lock flags (`lockKLAY`, `lockToken`) that are intended to halt all asset movement. These guards are correctly enforced on the **outbound** request path (`_requestKLAYTransfer`, `_requestERC20Transfer`, `_requestERC721Transfer`), but are entirely absent from the **inbound** handle path (`handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer`). Operators can therefore drain KLAY and tokens from a bridge that the owner has explicitly stopped.

### Finding Description

`BridgeTransfer` stores two categories of "halt" state:

1. `isRunning` — a global bridge-pause flag set by the owner via `setRunningStatus(false)`.
2. `isLockedKLAY` / `lockedTokens[token]` — per-asset lock flags set by the owner via `lockKLAY()` / `lockToken()`.

The outbound request functions correctly enforce both:

```solidity
// BridgeTransferKLAY.sol _requestKLAYTransfer
function _requestKLAYTransfer(...) internal unlockedKLAY nonReentrant {
    require(isRunning, "stopped bridge");   // ← guard present
    ...
}
``` [1](#0-0) 

```solidity
// BridgeTransferERC20.sol _requestERC20Transfer
function _requestERC20Transfer(...) internal
    onlyRegisteredToken(_tokenAddress)
    onlyUnlockedToken(_tokenAddress)          // ← lock guard present
{
    require(isRunning, "stopped bridge");     // ← guard present
    ...
}
``` [2](#0-1) 

The inbound handle functions have **no such checks**:

```solidity
// BridgeTransferKLAY.sol handleKLAYTransfer — no isRunning, no isLockedKLAY check
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }
    ...
    (bool ok, ) = _to.call.value(_value)("");   // ← KLAY sent unconditionally
    require(ok, "handleKLAYTransfer: transfer failed");
}
``` [3](#0-2) 

```solidity
// BridgeTransferERC20.sol handleERC20Transfer — no isRunning, no lock check
function handleERC20Transfer(...) public onlyOperators {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }
    ...
    IERC20(_tokenAddress).safeTransfer(_to, _value);  // ← tokens sent unconditionally
}
``` [4](#0-3) 

```solidity
// BridgeTransferERC721.sol handleERC721Transfer — no isRunning, no lock check
function handleERC721Transfer(...) public onlyOperators {
    ...
    IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId); // ← NFT sent unconditionally
}
``` [5](#0-4) 

The `isRunning` flag is declared in `BridgeTransfer` and is the direct analog of `sell.islisted` in the seed report — it signals the owner's intent to halt the bridge — but it is never read by any of the three handle functions. [6](#0-5) 

### Impact Explanation

When the bridge owner calls `setRunningStatus(false)` or `lockKLAY()` / `lockToken()` (e.g., in response to a security incident or planned maintenance), they expect all asset movement to stop. Because the handle functions ignore these flags, registered operators can still submit `handleKLAYTransfer` / `handleERC20Transfer` / `handleERC721Transfer` transactions that push KLAY, ERC-20, or ERC-721 tokens out of the bridge contract to arbitrary recipient addresses. This constitutes **unauthorized transfer of bridged assets** against the explicit intent of the bridge owner, matching the "Unauthorized transfer … affecting KAIA, bridged assets, or system-managed funds" impact gate.

### Likelihood Explanation

Operators are registered by the owner and are normally automated relayer nodes. However:
- The owner's only recourse to stop handle-side transfers is to also deregister every operator — a separate, non-obvious step not documented as required alongside `setRunningStatus(false)`.
- Any operator node that continues processing its event queue after a bridge pause (the normal automated behavior) will trigger the vulnerability without any malicious intent.
- A malicious or compromised operator can exploit the window between the owner's pause and operator deregistration to drain the bridge.

### Recommendation

Add `isRunning` and the relevant lock checks to all three handle functions, mirroring the outbound path:

```solidity
// BridgeTransferKLAY.sol
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
+   require(isRunning, "stopped bridge");
+   require(!isLockedKLAY, "locked");
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}

// BridgeTransferERC20.sol
function handleERC20Transfer(...) public onlyOperators {
+   require(isRunning, "stopped bridge");
+   require(!lockedTokens[_tokenAddress], "locked token");
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}

// BridgeTransferERC721.sol
function handleERC721Transfer(...) public onlyOperators {
+   require(isRunning, "stopped bridge");
+   require(!lockedTokens[_tokenAddress], "locked token");
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}
```

Alternatively, introduce a shared internal modifier `onlyRunning` and `onlyUnlockedAsset` applied uniformly to both request and handle paths.

### Proof of Concept

1. Owner deploys bridge, registers token, registers two operators, sets threshold to 1.
2. Owner calls `start(false)` (sets `isRunning = false`) to pause the bridge.
3. Operator calls `handleKLAYTransfer(txHash, from, attacker, 1000 ether, nonce, blockNum, "")`.
4. The call succeeds — `isRunning` is never read — and 1000 KLAY is transferred to `attacker`.
5. Repeat with `handleERC20Transfer` / `handleERC721Transfer` for token/NFT assets.

The same scenario applies when `lockKLAY()` or `lockToken()` is used instead of `start(false)`: the lock flag is checked on the request path but not on the handle path, so locked assets can still be transferred out by operators.
