### Title
Unsynchronized shared `lightBatch` reused across concurrent AA dry runs enables cross-request state corruption on light nodes - (File: aa_composer.js)

### Summary
`dryRunPrimaryAATrigger` allocates a KV batch either per-call (`kvstore.batch()`) or, for light nodes, uses a single shared module-level object `lightBatch` (aa_composer.js:278). This function is exposed to arbitrary network peers via the `light/dry_run_aa` request handler (network.js:3939-3963) with no request throttling or serialization, and is also invoked internally without any lock when a new unit with `count_primary_aa_triggers` arrives (network.js:1271-1281). Because Node.js callbacks interleave on I/O (multiple `conn.query`/promisified DB calls inside `handleTrigger`), two concurrent dry runs for different AAs/triggers can both be writing into and later calling `batch.clear()`/mutating the very same `lightBatch` object concurrently.

### Finding Description
This mirrors the root cause of CVE-2024-42075: a resource meant to represent one logical "mapping"/session (the kernel arena's VMA, here the KV write batch for a single dry-run trigger evaluation) is shared across multiple concurrent user-triggered operations without any reference counting or lock protecting its lifecycle. In the kernel, `mremap` created a second VMA referencing the same arena without incrementing a refcount, so `arena_vm_close()` on one VMA freed state still used by the other, producing a use-after-free. In ocore, `lightBatch` (aa_composer.js:278) is the analogous shared, unguarded resource: it is written to for the duration of `handleTrigger()` (which does async DB round-trips) and is explicitly cleared with `batch.clear()` at the end of every dry run (aa_composer.js:295, and also in `revert()` at aa_composer.js:1779). If a second `light/dry_run_aa` request (or the automatic dry-run path in `network.js:1271`) starts while a prior dry run for the same node is still in flight — entirely plausible since both are reachable without any `mutex.lock` around `dryRunPrimaryAATrigger` itself — the second call's writes/`clear()` on `lightBatch` will corrupt or wipe the pending writes of the first call's still-executing trigger evaluation, and vice versa. ### Impact Explanation
`handleTrigger`'s in-memory results (`objValidationState`, `stateVars`, `arrResponses`, byte/asset balances) are computed correctly since they don't depend on the batch, but the batch backs the KV-store state-var writes that would be used if the same trigger data were reused, and its premature `clear()` from an interleaved request can silently drop or corrupt writes belonging to a concurrent evaluation. On a light node this affects the accuracy of dry-run results returned to a light wallet (`light/dry_run_aa` is used to preview AA responses) and the automatic dry-run sanity check performed before a full node finalizes acceptance of a new unit invoking an AA (network.js:1271, gated by `conf.bDryRunNewTriggers`). Silent corruption in this pre-flight check could let a malformed/erroring AA trigger unit pass the "let it crash now" guard and instead be accepted, or cause spurious errors that reject valid triggers — a node-disagreement/wrong-acceptance class of impact. I could not fully verify whether corrupted `lightBatch` state could propagate into a persisted (non-rolled-back) write path, since every call to `dryRunPrimaryAATrigger` ends in `ROLLBACK` at the SQL layer and `batch.clear()` before release; the concrete fund-loss/double-spend chain therefore depends on exact interleaving that I was not able to trace end-to-end with the available tools.

### Likelihood Explanation
`light/dry_run_aa` is reachable by any connected peer without prior authentication (network.js:3939), and nothing serializes calls to it — unlike `handleAATriggers`, which is protected by `mutex.lock(['aa_triggers'], ...)` (aa_composer.js:62), `dryRunPrimaryAATrigger` has no such lock. A peer can trivially fire multiple overlapping `light/dry_run_aa` requests (or trigger the automatic dry-run path by broadcasting AA-triggering units in quick succession) to force interleaving of the shared `lightBatch` object.

### Recommendation
Allocate a fresh batch per dry-run invocation instead of reusing a shared module-level `lightBatch`, i.e. always use `kvstore.batch()` in `dryRunPrimaryAATrigger` regardless of `conf.bLight`, or wrap calls to `dryRunPrimaryAATrigger` in a dedicated `mutex.lock(['dry_run_aa'], ...)` so overlapping dry runs are serialized like `handleAATriggers` already is.

### Proof of Concept
1. As a light node operator (or remote peer), send two overlapping `light/dry_run_aa` requests for two different AA addresses/triggers in quick succession over the same or different websocket connections.
2. Because `conf.bLight` is true, both calls obtain the same `lightBatch` object (aa_composer.js:278) rather than independent batches.
3. Due to the async DB operations inside `handleTrigger` (multiple `conn.query` calls), the two dry runs interleave; when the first call finishes it executes `batch.clear()` (aa_composer.js:295) while the second call's `handleTrigger` may still be populating the same batch, corrupting/erasing its pending writes.
4. Observe (with added instrumentation/logging) that the second dry run's batch content no longer matches what `handleTrigger` computed for it, demonstrating the missing per-call isolation of the shared resource — analogous to the missing per-mapping refcount in the kernel arena bug. [4](#0-3)
