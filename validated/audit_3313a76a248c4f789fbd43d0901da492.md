### Title
Cross-tenant CI-status injection via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the commit(s) to update purely by `sha` value, with no scoping to the repository/stack that emitted the webhook, even though `sha` is only unique per `(stack_id, sha)` at the database level. Any repository that shares a commit sha with another tracked stack (e.g. a common upstream ancestor commit) can cause a legitimately-signed `status` webhook from its own org/repo to mutate the `Status`/state of an unrelated stack's commit.

### Finding Description
The broken binding: `StatusHandler#process` assumes `sha == globally unique commit identifier (one commit == one repository)`, but the actual schema invariant, enforced by the `index_commits_on_stack_id_and_sha` migration, is `unique(stack_id, sha)` — sha is only unique **within a stack**, not globally. [1](#0-0) 

Code path:
1. GitHub sends a `status` webhook. `WebhooksController#create` runs `verify_signature`, which validates the HMAC against the webhook secret configured for `Shipit.github(organization: repository_owner)` — this authenticates the *organization*, not which specific repo/stack inside it the sha belongs to. [2](#0-1) 
2. `StatusHandler.params` only requires `:sha` and `:state` — there is no repository-derived scoping applied in `process`. [3](#0-2) 
3. `process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a raw, stack-unscoped lookup. [4](#0-3) 

Contrast with `CheckSuiteHandler`, which correctly scopes: it first resolves `stacks` via `Repository.from_github_repo_name(repository_name)` (derived from the webhook's own `payload['repository']['full_name']`) and only queries `stack.commits.where(sha:)` within that stack. [5](#0-4) [6](#0-5) 

`StatusHandler` has no equivalent restriction, so `Commit.where(sha:)` returns every `Commit` row across every stack/tenant sharing that sha — including a base/ancestor commit imported into an upstream tracked repo's stack and later duplicated into an unrelated fork's history.

Exploit flow: attacker forks/branches a repository whose org has the Shipit GitHub App installed (so GitHub will send a validly-signed webhook for their own repo). The fork's history includes a commit sha that is identical to a commit already imported into a separate, unrelated Shipit-tracked stack (common upstream ancestor). Attacker triggers CI on their own branch/PR for that sha; GitHub emits a real, correctly-signed `status` webhook to the Shipit host. `StatusHandler#process` matches **both** the attacker's own `Commit` row and the unrelated upstream stack's `Commit` row (same `sha`, different `stack_id`), and calls `commit.create_status_from_github!(params)` on both — writing CI status data onto a commit belonging to a repository/stack the attacker never authenticated for.

Existing guards don't stop this: `verify_signature` only proves the request came from a real GitHub org, not which stack the sha "belongs" to; `ExplicitParameters` only validates types (`sha`/`state` presence), not scope; there is no `require_permission!`/`stacks` filtering in `StatusHandler` unlike `CheckSuiteHandler`/`PushHandler`.

### Impact Explanation
A validly-authenticated webhook from one repository/org can mutate `Status` records (state, description, target_url, context) on a `Commit` belonging to a completely different, unrelated tracked stack, via `Commit#create_status_from_github!`. This can flip a commit from failing to passing (or vice versa) in another tenant's stack, affecting deployability decisions (`ProcessMergeRequestsJob` is enqueued on relevant status transitions) and release status reporting. This is a payload for one repository mutating another's stack/commit data — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: (1) Shipit tracks a stack containing a commit sha that also exists in the attacker-controlled repository's history (realistic for forks that share upstream ancestor commits, cherry-picks, or squash-merges with identical trees); (2) the attacker's repo/org has the GitHub App/webhook installed (common for any repo under an org Shipit already tracks, or the attacker's own tracked repo). No Shipit credentials, session, or API token are needed — the attacker only needs to run CI on a commit sha they can influence in their own repo. This is repeatable against any stack that happens to share a commit sha with an attacker-reachable repository, though it depends on such a sha collision existing (not exploitable for arbitrary, unrelated stacks without a shared sha).

### Recommendation
Scope `StatusHandler#process` to the stacks/repositories derivable from the webhook's own payload, mirroring `CheckSuiteHandler`/`PushHandler`: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` and restrict the commit lookup to `stack.commits.where(sha: params.sha)` (or otherwise verify the commit's owning stack's repository matches the webhook's repository) before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/status_handler_test.rb`, not shown here since `test/**` is out of scope for the fix but is where the proof lives):
1. Create `stack_a` and `stack_b` (different `Repository`/`Stack` records).
2. Create `commit_a = Commit.create!(sha: "a" * 40, stack: stack_a, ...)` and `commit_b = Commit.create!(sha: "a" * 40, stack: stack_b, ...)` — same sha, different `stack_id`, both allowed by the `unique(stack_id, sha)` index.
3. Build a payload `{ 'sha' => 'a'*40, 'state' => 'success', 'repository' => { 'full_name' => stack_a's repo full name } }` (as if the webhook originated only from `stack_a`'s repo).
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `commit_a.reload.status.state == 'success'` (expected) **and** `commit_b.reload.status.state == 'success'` (the bug) — i.e., a single webhook scoped to `stack_a`'s repository mutated `commit_b`, which belongs to `stack_b`, proving the binding "sha == one repository" is false while the code behaves as if it were true.
