## Title
Stack-Scoped API Token Can Read CCMenu Build Status of Any Stack — Token-to-Stack Authorization Bypass in `CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

## Summary
`Shipit::Api::CCMenuController` overrides the `stack` resolver used by `Shipit::Api::BaseController` and, in doing so, drops the stack-scoping check that normally binds an `ApiClient`'s authorized stack to the stack it is allowed to touch. A `read:stack`-scoped `ApiClient` token that is supposed to be limited to a single stack can be replayed against the CCMenu endpoint to read the build/deploy status of *any* stack in the Shipit instance.

## Finding Description
`Shipit::ApiClient` supports scoping a token to a single stack via the `stack_id` column: `Shipit::Api::BaseController#stacks` restricts the visible collection to `Stack.where(id: current_api_client.stack_id)` whenever the client is scoped, and `#stack` resolves the requested id only from within that restricted collection: [1](#0-0) 

`Shipit::Api::CCMenuController` inherits from `BaseController` but redefines `stack` to bypass this scoping entirely, resolving directly against the global `Stack` table: [2](#0-1) 

The controller only enforces a coarse-grained permission check (`require_permission :read, :stack`), which merely verifies the token carries the `read:stack` permission string, not that the token is scoped to the requested stack: [3](#0-2) [4](#0-3) 

The controller additionally widens the authentication surface by accepting the token via a URL query parameter instead of only HTTP Basic Auth: [5](#0-4) 

This exact pattern — a token that authorizes access to Stack A being usable to touch Stack B — is the direct analog of the reported bug class: a binding (`ApiClient.stack_id` == stack acted upon) that is enforced in one code path (`BaseController#stacks`/`#stack`) but silently dropped in another code path (`CCMenuController#stack`) that reuses the same underlying credential and permission model.

Concretely: `test/fixtures/shipit/api_clients.yml` defines `here_come_the_walrus` as a client scoped to the `shipit` stack with only `read:stack`: [6](#0-5) 
Using `BaseController`-derived endpoints, this client is correctly restricted to stack `shipit` only, as shown by the test asserting a scoped client only sees one stack in `#index`: [7](#0-6) 
But when the same token's `authentication_token` is presented to `Api::CCMenuController#show` with a *different* `stack_id` in the URL, `stack` resolves unconditionally via `Stack.from_param!`, with no re-check of `current_api_client.stack_id`.

## Impact Explanation
This breaks the authorization binding "a stack a token authorises versus a stack it touches." A caller holding a token intentionally minted and distributed for a single stack (e.g., handed to a low-trust external CI/status dashboard integration) can use that same token to read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`, lock state) for every other stack managed by the Shipit instance, including stacks the token owner was never meant to have visibility into. This matches the specified High-impact category: "unauthenticated read of stack state, task streams or deploy output" via a token that should not carry that authorization. It does not require RCE-level access to demonstrate — only possession of any valid `read:stack` token, scoped or not.

## Likelihood Explanation
Likelihood is high for any deployment that issues scoped `ApiClient` tokens (the engine explicitly supports this via `ApiClient#stack_id` and documents/tests it), because:
- No privileged action or GitHub credential is required — only a previously-issued Shipit `ApiClient` token, which is the intended level of access for many integrations (CCMenu clients, low-trust dashboards, etc.).
- CCMenuController accepts the token as a URL query parameter, which is easy to leak and easy to replay against arbitrary `stack_id` values by any party who obtains it.
- The bypass is a direct code-path divergence (`stacks.from_param!` vs. `Stack.from_param!`), not a timing or race condition, so it is 100% reproducible.

## Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the same stack-scoped collection used elsewhere:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
reusing (or reimplementing) `BaseController#stacks`, so that a client scoped to `stack_id` X cannot resolve any stack other than X, consistent with the rest of the API surface.

## Proof of Concept
1. As an administrator, create an `ApiClient` scoped to Stack A only, with permission `read:stack` (e.g., via the `here_come_the_walrus`-style fixture or the `/api_clients` UI setting `stack_id`).
2. Obtain that client's `authentication_token`.
3. Send:
   `GET /api/stacks/<STACK_B_ID>/ccmenu.xml?token=<TOKEN_SCOPED_TO_A>`
   where `STACK_B_ID` refers to a different stack the token was never granted access to.
4. Observe: the response returns `200 OK` with Stack B's CCMenu project XML (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc.), even though the same token against `/api/stacks` (`BaseController`-derived endpoints) would only ever list/show Stack A, per `Api::BaseController#stacks`/`#stack`.
