### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on `repository.full_name` (and, for status events, on no repository scope at all) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC signature based on `repository.owner.login` (falling back to `organization.login`), but the handlers that actually mutate state resolve their target repository/stack from the independent `repository.full_name` field - or, in the case of `StatusHandler`, from no repository field at all. Nothing ties these two fields together, so a party who legitimately controls the webhook secret for one GitHub organization tracked by a shared Shipit instance can forge a validly-signed payload whose "owner" is their own org but whose effective target is a completely different, unrelated stack/commit.

### Finding Description
The verification step is: [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The `organization` used purely to pick which `webhook_secret` verifies the raw body is taken from `repository.owner.login`. This field is completely independent from the field that the event handlers use to determine *which repository/stack the event actually applies to*: [2](#0-1) 

`Handler#stacks`/`#repository_name` resolve the target via `payload.dig('repository', 'full_name')`, which is then split into owner/name in `Repository.from_github_repo_name`: [3](#0-2) 

Nothing enforces that `repository.full_name`'s owner segment equals `repository.owner.login`. Since the whole JSON body is attacker-controlled (only the HMAC signature must match a legitimately-known secret), an operator/administrator of *any* GitHub organization that is registered with the same Shipit instance (a common deployment shape - see the multi-org config format in `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml`) can sign a payload with their own real webhook secret while setting `repository.full_name` to point at a stack belonging to a different organization tracked by the same Shipit instance.

The impact is most severe for `StatusHandler`, which doesn't even use the repository field to scope its effect - it looks up commits globally by SHA across the entire installation: [4](#0-3) 

```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Since `Commit#deployable?` depends on the commit's aggregated status state: [5](#0-4) 

and status writes drive deploy-gating hooks/side effects (`deployable_status` emission, `stack.schedule_merges`, continuous-delivery scheduling) via `Commit#add_status` in `app/models/shipit/commit.rb`, an attacker who controls a signature-valid webhook secret for org A can forge a fabricated "success" CI status for a commit belonging to org B's stack, marking an unreviewed/failing commit "deployable" and potentially triggering an unauthorized continuous deploy in an organization/repository they do not control.

### Impact Explanation
This breaks the binding `verified organization == organization/repository the event applies to`, matching the reported bug class ("index/field used for verification differs from the index/field used for the effective write"). It allows cross-tenant writes across GitHub organizations sharing one Shipit instance: fabricating commit CI statuses (and by extension, deployability) for a repository/organization the attacker does not administer, and being able to influence `push`/`pull_request` handlers to act on an arbitrary `repository.full_name` while only holding the webhook secret of an unrelated org. This can lead to an unauthorized deploy being triggered off a forged "success" status, which falls in the Critical/High impact bucket described in the rules ("an unauthorized deploy").

### Likelihood Explanation
The webhook endpoint (`WebhooksController`) is unauthenticated public HTTP (only HMAC-checked), reachable by anyone. The precondition is that the attacker legitimately knows one org's `webhook_secret` configured on the shared Shipit instance (e.g., because they administer a low-privilege org/repo that is also integrated into the same instance as more sensitive stacks) - this is not a privileged Shipit credential, GitHub App private key, or `api_clients_secret`, and does not require write access to the *targeted* repository. This is a realistic scenario for any Shipit deployment configured with multiple independent GitHub organizations (explicitly supported per `config/secrets.development.example.yml`).

### Recommendation
- Cross-check that the organization used to select/verify the webhook secret (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers; reject the request otherwise.
- In `StatusHandler`, scope the `Commit.where(sha: ...)` lookup to commits belonging to stacks under the verified organization, rather than searching globally by SHA.
- More generally, thread the verified organization through to every handler and have `Handler#stacks`/`#repository_name` validate consistency with it rather than trusting `repository.full_name` unconditionally.

### Proof of Concept
1. Shipit is configured with two GitHub orgs, `org-a` and `org-b`, each with its own `webhook_secret` (per the documented multi-org config shape).
2. Attacker legitimately administers `org-a`'s webhook (knows `org-a`'s `webhook_secret`) but wants to affect a stack under `org-b`.
3. Attacker crafts a `status` event payload:
```json
{
  "sha": "<sha-of-target-commit-in-org-b-stack>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac_sha1(org-a-secret, raw_body)>` and POSTs to `/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s `github_app`, and verifies successfully because the signature is genuinely computed with `org-a`'s secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which is not restricted to `org-a`'s repositories, and creates a "success" `Status` on the target commit belonging to `org-b`'s stack via `commit.create_status_from_github!`.
7. The forged status can make the `org-b` commit satisfy `Commit#deployable?`, potentially triggering continuous delivery or allowing a manual deploy of a commit that never actually passed CI in `org-b`.

Note: I was unable to fully trace `Commit#create_status_from_github!` and `ContinuousDeliveryJob` bodies within the indexed content (only method signatures/references were found via grep, not their full source), so the exact automatic-deploy trigger chain from a forged "success" status could not be fully confirmed line-by-line; a Devin session with full repository access would be needed to verify the exact continuous-delivery trigger path end-to-end.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",

        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

      ].join(' '))
    end
