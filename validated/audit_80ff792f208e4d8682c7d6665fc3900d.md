### Title
Owner/full_name org split lets an unauthenticated attacker forge a `pull_request` webhook that is "authenticated" against a secret-less org while mutating a different org's stack; the review-stacks provisioning gate is bypassable, letting `LabelCapturingHandler` poison the review stack's environment - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which org's `GitHubApp`/secret to verify a webhook against using attacker-controlled `params.dig('repository','owner','login')`, but every handler resolves the *actual* repository/stack to mutate from a separately attacker-controlled `params.repository.full_name`. If any org configured on the Shipit instance has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` returns `true` unconditionally, letting the attacker "authenticate" as that org while pointing `full_name` at a victim org's repository. Separately, `OpenedHandler#provision?` has an operator-precedence bug that provisions a review stack even when `review_stacks_enabled` is `false` for two of its three provisioning-behavior branches, and `LabelCapturingHandler` never checks `review_stacks_enabled` at all before writing attacker-supplied PR label names into `PullRequest#labels`, which `ReviewStack#env` turns into uppercase environment variables.

### Finding Description
The broken binding: the org whose secret authenticates the request (`repository_owner` in `WebhooksController#repository_owner`, line 61) is assumed to equal the org that owns the repository actually mutated (`Repository.from_github_repo_name(params.repository.full_name)` in every PR handler, e.g. `label_capturing_handler.rb` lines 110-113). Nothing in `verify_signature` (`app/controllers/shipit/webhooks_controller.rb` lines 24-49) ties these two together.

`Shipit.github(organization: repository_owner)` (line 25) resolves a `GitHubApp` keyed on the attacker-supplied owner login. `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb` lines 76-83) does:
```
return true unless webhook_secret
```
so any org configured without a `webhook_secret` (a state explicitly shown as a normal/example configuration in `config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, and `test/dummy/config/secrets_double_github_app.yml`, all containing `webhook_secret: # nil`) accepts *any* unsigned payload. [1](#0-0) [2](#0-1) 

An attacker who names such a secret-less org in `repository.owner.login` (or `organization.login`) passes signature verification trivially, then sets `repository.full_name` to a victim repository belonging to a *different* org. Every `pull_request` handler resolves the mutated repository/stack purely from `full_name`: [3](#0-2) 

On top of that, `OpenedHandler#provision?` has a precedence bug:
```
repository.review_stacks_enabled &&
  repository.provisioning_behavior_allow_all? ||
  (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
  (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
`&&` binds tighter than `||`, so `review_stacks_enabled` only gates the `allow_all` branch; the `allow_with_label` and `prevent_with_label` branches provision a stack regardless of `review_stacks_enabled`. [4](#0-3) 

`LabelCapturingHandler#capture_labels?` never checks `review_stacks_enabled` at all — it only requires the action type and `stack.present? && !stack.archived?`: [5](#0-4) 
Once a stack exists (via the precedence bug or any prior legitimate provisioning), `labeled`/`unlabeled`/`reopened` events write `params.pull_request.labels.map(&:name)` straight into `PullRequest#labels`: [6](#0-5) 
`ReviewStack#env` then folds every label name into the deploy/provision environment as an uppercased key set to `"true"`, merged over the base stack env: [7](#0-6) 

Existing guards (`drop_unhandled_event`, `ExplicitParameters` schema in the handler, `Repository.from_github_repo_name`, `force_github_authentication`) do not check that the org authenticating the webhook matches the org owning `full_name`; none of them close this gap. `GithubOrganizationUnknown` only fires when the named org is *not configured at all*, not when it's configured without a secret.

### Impact Explanation
An attacker with no Shipit credentials, no GitHub App secret, and no relationship to the victim org can, in an installation using the multi-org github config (`Shipit.github(organization:)` keyed lookup) where at least one configured org has no `webhook_secret`, forge `pull_request` webhooks that are accepted as "authenticated" while mutating a completely different org's `ReviewStack`/`PullRequest` records — a payload for one repository/org mutating another's stack, matching the Critical "cross-tenant mutation" category. The immediate write is attacker-controlled label names becoming environment variables merged into the stack's deploy/provisioning environment (`ReviewStack#env`), which is consumed by the provisioner/`Command` pipeline that ultimately shells out; this is the mechanism the question describes as leading toward RCE on the deploy host, though the exact `Command#args`/`PTY.spawn` env-injection mechanics were not re-traced in this session and remain an assumption carried from the question rather than independently re-verified end-to-end here. Repeatable per-request, against any repository whose org shares a Shipit deployment with any secret-less org.

### Likelihood Explanation
Requires: (a) a multi-org Shipit `github:` config (keyed by org) — the single-org schema is unaffected because `Shipit#github` ignores the passed `organization` param entirely when `github_default_organization` is nil; (b) at least one configured org without a `webhook_secret` (shown as a normal example default in shipped config templates); (c) the victim repository/org resolved via `full_name` exists and has a `ReviewStack`. Given (a)+(b), attacker cost is a single crafted HTTP POST with no secrets needed — fully repeatable and scriptable.

### Recommendation
- In `WebhooksController#verify_signature`, verify the signature using the org that actually owns the resolved repository (derived consistently from `repository.full_name`, not a separately attacker-controlled `owner.login`/`organization.login`), and reject the request if the two disagree.
- Require every configured org to have a non-blank `webhook_secret` in production (fail closed) rather than allowing `verify_webhook_signature` to return `true` when unset.
- Fix `OpenedHandler#provision?` parenthesization so `review_stacks_enabled` gates all three branches: `repository.review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`.
- Add a `repository.review_stacks_enabled` check to `LabelCapturingHandler#capture_labels?`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "owner/full_name split lets a secret-less org forge a pull_request labeled event for another org's stack" do
  Shipit.stubs(:secrets).returns(ActiveSupport::OrderedOptions.new.tap { |s|
    s.github = {
      "attacker_org" => { app_id: 1, installation_id: 1, webhook_secret: nil, private_key: TEST_KEY },
      "victim_org"   => { app_id: 2, installation_id: 2, webhook_secret: "real-secret", private_key: TEST_KEY }
    }
  })

  repository = shipit_repositories(:shipit) # belongs to victim_org, review_stacks_enabled: false
  stack = shipit_review_stacks(:existing_review_stack_for_repository)

  payload = {
    "action" => "labeled",
    "number" => stack_pr_number,
    "pull_request" => {
      "id" => 1, "number" => stack_pr_number, "url" => "...", "title" => "x",
      "state" => "open", "additions" => 0, "deletions" => 0,
      "head" => { "sha" => "a" * 40, "ref" => "feature" },
      "user" => { "login" => "attacker" },
      "assignees" => [],
      "labels" => [{ "name" => "MALICIOUS_ENV_KEY" }]
    },
    "repository" => {
      "full_name" => "victim_org/shipit-app", # resolves to victim stack
      "owner" => { "login" => "attacker_org" } # picks secret-less org for verification
    },
    "sender" => { "login" => "attacker" }
  }.to_json

  request.headers['X-Github-Event'] = 'pull_request'
  # no X-Hub-Signature needed: attacker_org has no webhook_secret

  post :create, body: payload, as: :json
  assert_response :ok

  stack.pull_request.reload
  # Binding under test:
  #   authenticating_org (attacker_org, unsigned) != mutated_repo_org (victim_org)
  # yet the write succeeded:
  assert_includes stack.pull_request.labels, "MALICIOUS_ENV_KEY"
  assert_equal "true", stack.reload.env["MALICIOUS_ENV_KEY"]
end
```
This demonstrates the write is accepted for `victim_org`'s stack despite being "authenticated" only against `attacker_org`'s (secret-less) config, and despite `review_stacks_enabled` being `false` on the repository, because `LabelCapturingHandler` never checks that flag.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
