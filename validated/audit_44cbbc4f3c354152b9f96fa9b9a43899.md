### Title
Bad-debt socialization gate uses static `liq-penalty-max` instead of the graduated `liq-penalty`, causing premature loss-socialization onto all vault suppliers - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
In `liquidate()`, the check that decides whether a borrower's position has genuinely "no collateral left" (and therefore must have its residual debt socialized across every supplier of the vault) is computed with the wrong penalty variable — `liq-penalty-max` (the theoretical ceiling) — instead of `liq-penalty` (the actual graduated penalty computed for this specific liquidation via `calc-liquidation-params`). This is the same class of bug as the Tunnl report: a formula that is supposed to use a dynamically-derived percentage instead uses a different, related-but-wrong percentage constant, which skews the resulting amount and flips downstream branching logic that other, unrelated parties depend on.

### Finding Description
`liquidate()` computes the *actual*, graduated liquidation penalty for the current liquidation as `liq-penalty`, derived from `calc-liquidation-params` based on the borrower's current LTV: [1](#0-0) 

This `liq-penalty` is correctly used to size the actual seized collateral and repaid debt (`process-collateral-asset`, `calc-final-liquidation-amounts`): [2](#0-1) 

However, immediately after execution, the code estimates how much of the position's residual debt could still be repaid using the borrower's *other* collateral (collateral outside the asset currently being liquidated), in order to decide whether the position is truly unrecoverable and must be bad-debt-socialized: [3](#0-2) 

This calculation divides by `(+ BPS liq-penalty-max)` — the fixed ceiling parameter of the e-group — instead of `(+ BPS liq-penalty)`, the actual penalty rate that was just used to size this liquidation. The same wrong-variable pattern also appears a few lines earlier, in the "remaining dust collateral" branch that decides whether to sweep 100% of `user-coll-balance` to the liquidator: [4](#0-3) 

Because `liq-penalty <= liq-penalty-max` (the graduated penalty only reaches its ceiling deep in "full liquidation" territory), plugging in `liq-penalty-max` always produces a *larger* divisor than the correct one, which *understates* `other-debt-repayable` (and `remaining-debt-to-repay`). A smaller (or zero-rounded) `other-debt-repayable`/`remaining-debt-to-repay` biases the `no-collateral-left` condition toward `true` even when the borrower's remaining collateral, valued at the *correct* graduated penalty, could still cover the residual debt.

`no-collateral-left = true` triggers `fold socialize-debt-asset ...`, which for each remaining debt asset calls into the corresponding vault's `socialize-debt`, permanently writing down `lindex` (the liquidity index shared by every zToken holder of that vault) in proportion to the "lost" debt: [5](#0-4) 

That write-down (`new-lindex`) is applied to the *entire* supplier base of the vault, not just the liquidated position — it is a shared-state mutation triggered unilaterally by the liquidator's transaction that permanently dilutes every other supplier's share value.

### Impact Explanation
The liquidator (attacker/unprivileged caller) triggers `liquidate()`. The victims are all other suppliers of the affected debt-asset vault(s), whose `lindex` (and thus the value of their zTokens) is shared state they do not control.

- Without the bug: `other-debt-repayable`/`remaining-debt-to-repay` would be computed with the correct, lower `liq-penalty`, producing a larger (correct) repayable estimate. In borderline cases where the position's other collateral genuinely could still cover the residual debt at the true penalty rate, `no-collateral-left` would correctly evaluate to `false`, and the debt would remain on the borrower's books for a subsequent (partial) liquidation instead of being written off.
- With the bug: the inflated divisor (`liq-penalty-max`) rounds the repayable estimate down, sometimes to zero, and `no-collateral-left` incorrectly evaluates to `true`. This causes `socialize-debt-asset` to fire prematurely, permanently reducing `lindex` for the vault and socializing a loss onto every supplier even though the position was not actually unrecoverable.

This directly maps to the "socialization charged to all suppliers" category and results in permanent freezing/loss of supplier funds (their share of vault assets is permanently reduced) — this is a Critical/High impact per the rubric (protocol insolvency risk / permanent loss of unclaimed yield/principal value for a class of victims who did not initiate the triggering transaction).

The parallel bug in `remaining-debt-to-repay` (lines 1476-1486) additionally lets the liquidator sweep 100% of `user-coll-balance` (rather than the correctly proportional `coll-final-raw`) whenever the miscalculated dust-debt rounds to zero, meaning the liquidator can seize collateral beyond the bound implied by the correctly graduated penalty — harming the borrower.

### Likelihood Explanation
This triggers on essentially every partial liquidation of a multi-collateral position where `liq-penalty < liq-penalty-max` (i.e., any position not already at the maximum LTV/full-liquidation tier) and where the position has more than one collateral asset or the residual debt/collateral split lands near the rounding boundary. Since graduated liquidation is the normal/common case (the whole point of `calc-liq-factor-exp`/`calc-liq-factor-bound` is to scale penalty below the max for most liquidations), the wrong-variable substitution is live on a large fraction of real liquidations, not just an edge case — making likelihood high.

### Recommendation
Replace `liq-penalty-max` with `liq-penalty` (the graduated penalty already computed for this liquidation) in both locations:
- `remaining-debt-to-repay` computation (lines ~1480).
- `other-debt-repayable` computation (lines ~1518-1524).

This ensures the "is the position truly unrecoverable" check and the "sweep-remaining-dust" check use the same penalty rate that was actually applied to size the liquidation, preventing premature bad-debt socialization and preventing over-seizure of collateral.

### Proof of Concept
Conceptual walk-through (parameters illustrative):
1. E-group configured with `liq-penalty-min = 500` bps, `liq-penalty-max = 1000` bps, and graduated curve such that at the borrower's current LTV, `calc-liquidation-params` returns `liq-penalty = 600` bps (well below the 1000 bps ceiling).
2. Borrower has two collateral assets: sBTC (being liquidated) and a small amount of STX left over. The USD value of the leftover STX, correctly discounted at 600 bps, would be enough to cover $50 of residual debt (`other-debt-repayable` > 0 → `no-collateral-left` should be `false`).
3. Because the code discounts using `liq-penalty-max = 1000` bps instead, `other-debt-repayable` rounds down to `u0`.
4. `no-collateral-left` evaluates to `true`, `socialize-debt-asset` fires, and the residual debt is written off against the vault's `lindex`, permanently diluting every zToken holder of that vault — even though the borrower's leftover STX collateral, if it had been evaluated correctly, could have covered it and left the debt outstanding for a later liquidation instead of socializing it.
