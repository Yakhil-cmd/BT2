The reported Solidity bug's real defect is: an entry point accepts a **caller-supplied, unvalidated token/contract identity**, then credits the caller with "amount" of value based on **self-reported contract behavior rather than a verified balance delta**. I found a structurally identical pattern in Polkadot SDK's XCM ERC20 asset transactor, which is live and wired into the Asset Hub Westend runtime.

### Title
ERC20Transactor trusts arbitrary contract's `transfer()` boolean return instead of verifying actual balance movement, allowing fabricated fungible credit in XCM holding - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` match **any** XCM `AssetId` of the form `{parents:0, interior: X1(AccountKey20{key, network})}` to an arbitrary, attacker-controlled H160 address and directly `bare_call`s that contract's `transfer()` [1](#0-0) . There is no whitelist/registry check on the target contract — this mirrors HardVault's `deposit(address token, ...)` accepting any `token` without validation. Success is determined solely by decoding the contract's own boolean return value, with **no independent verification that the checking account's real ERC20 balance changed by `amount`** [2](#0-1) . This is the same "asset self-reports vs real balance-diff" trust failure as the audited HardVault report.

### Finding Description
`ERC20Transactor` is registered in `AssetTransactors` for `asset-hub-westend-runtime`, active in the live `XcmConfig` [3](#0-2) . Per its own PRDoc, "asset ids of the form `{parents:0, interior: X1(AccountKey20{key, network})}` will be matched by this transactor and the corresponding `transfer` function will be called in the smart contract whose address is `key`" — any user can reference **any deployed contract** as a fungible asset simply by encoding its address as an `AccountKey20` junction; no registration or trust check exists [4](#0-3) .

In `withdraw_asset_with_surplus`, the transactor calls `transferCall{to: checking_address, value: amount}` on the attacker-chosen contract and, if the ABI-decoded return is `true`, unconditionally mints `Erc20Credit(amount)` into the XCM holding via `AssetsInHolding::new_from_fungible_credit` [5](#0-4) . The `Erc20Credit` type explicitly documents that "the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime" [6](#0-5)  — i.e., the runtime performs **no balance-before/after check**, exactly the missing safeguard flagged in the original HardVault report. An attacker who deploys a trivial contract whose `transfer()` always returns `true` (regardless of actual token movement) can cause arbitrary amounts of fungible "credit" to appear in the XCM holding register for that instruction, entirely fabricated and unbacked by any real value transfer.

### Impact Explanation
The fabricated holding credit is a first-class `Asset` inside the XCM executor's holding register for the remainder of the program. If that holding is subsequently used against real value — e.g. `ExchangeAsset` against a permissionless `pallet-asset-conversion` pool paired with this attacker's fake "ERC20" location, or deposited into a pool/beneficiary that treats it as real value — the attacker can extract genuine backed assets (native currency or `pallet-assets`) in exchange for tokens that were never actually transferred. This is an unbacked-issuance/theft primitive, not merely an availability or economic issue.

### Likelihood Explanation
Reachability requires no privilege: any signed account can submit an XCM program via `pallet-xcm`'s permissionless local-execution entry points referencing an `AccountKey20` asset id pointing at a contract they deployed via `pallet-revive`, and (separately) create/fund an asset-conversion pool pairing that location with a real asset, both of which are ordinary permissionless user actions on Asset Hub. The only remaining step needed to fully weaponize this into a concrete theft-of-funds PoC is confirming that `pallet-asset-conversion`'s pool/liquidity paths on this runtime treat the ERC20 `Location` asset kind through the same non-verifying transactor (rather than through a separately-checked path) — this dependency was not fully traced within the available investigation scope, so likelihood is assessed as credible but not fully proven end-to-end.

### Recommendation
`withdraw_asset_with_surplus`/`deposit_asset_with_surplus` should query the ERC20 contract's `balanceOf` for the checking account before and after the `transfer` call and use the **measured balance delta** — not the contract's self-reported boolean — as the amount credited/debited into `AssetsInHolding`, consistent with the standard "fee-on-transfer / malicious token" mitigation recommended in the original report (verify actual balance movement rather than trusting the token contract's return value).

### Proof of Concept
Not executed. A full PoC would require (1) deploying a `pallet-revive` contract implementing `transfer(address,uint256) -> bool` that always returns `true` without moving balance, (2) submitting an XCM program via `pallet-xcm::execute` with `WithdrawAsset` referencing that contract's address as an `AccountKey20` fungible asset id, and (3) demonstrating the resulting `AssetsInHolding` contains the fabricated `amount`, then optionally chaining `ExchangeAsset`/pool interaction to convert it to real value. This was not run against the actual test harness in this investigation; the finding rests on static code and configuration evidence tracing the entry point, the missing balance-delta check, and the live runtime wiring.
