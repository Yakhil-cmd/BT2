## Title
Open Redirect via unvalidated `omniauth.origin` in OAuth callback - ([File: app/controllers/shipit/github_authentication_controller.rb])

## Summary
`GithubAuthenticationController#callback` redirects to `request.env['omniauth.origin']` with no validation that the value is a same-application path, so an attacker who controls the `origin` param on the OAuth initiation request can force the victim's authenticated browser to be redirected to an attacker-controlled external URL after login completes. Note: the question mislabels the file as `lib/shipit/task_commands.rb`; the actual code lives in `app/controllers/shipit/github_authentication_controller.rb`.

## Finding Description
The claimed-safe binding is: `return_url == a path scoped to this Shipit application` (i.e., `return_url` should always resolve to a route within `Shipit::Engine`). The code instead does: [1](#0-0) 

`return_url` is taken directly from `request.env['omniauth.origin']`, which OmniAuth populates from the `origin` request parameter (or `Referer` header) captured at `/github/auth/github` before redirecting to GitHub. Neither `sign_in_github` nor `callback` performs any check that `return_url` is a relative path or belongs to the app's host — it is passed straight into `redirect_to(return_url)`, and Rails' `redirect_to` does not restrict non-open-redirect protection by default for absolute URLs.

Exploit flow: an attacker sends a victim a link such as `/github/auth/github?origin=https://evil.example/callback`. The victim, who has a legitimate GitHub account and is not otherwise compromised, clicks it, completes the real OAuth handshake with GitHub, and lands back on `/github/auth/callback`. At that point `session[:user_id]` and `session[:authenticated]` are correctly set for the victim (the authentication itself is not forged), but `redirect_to(return_url)` sends the now-authenticated browser to `https://evil.example/callback`, an origin fully controlled by the attacker.

None of the existing guards apply here: `verify_signature`/webhook signature checks are irrelevant to this human-browser OAuth flow; `force_github_authentication` and `User#authorized?` govern access to Shipit resources, not the redirect target; there is no `ExplicitParameters` schema or host allowlist applied to `omniauth.origin` in this controller.

## Impact Explanation
This is a classic **open redirect** immediately following authentication. It does not by itself leak `github_access_token`, `session[:user_id]`, or any Shipit secret — Rails session cookies are not appended to the URL, and `session[:user_id]` remains scoped to the legitimate `shipit` domain cookie, so an external site does not receive the session token merely from the redirect. The concrete exploitable value is: the victim's browser lands on an attacker page immediately after establishing a trusted-looking session, which can be leveraged for phishing (a convincing "re-login"/consent page impersonating Shipit), or chained with other flows to look legitimate.

This does not meet the Critical bar (no forged webhook/session/API token acceptance, no secret exfiltration, no cross-repository stack mutation) and does not clearly meet the High bar either, since it is not "session fixation / forced OAuth completion" in the sense of forcing a *particular* attacker-chosen identity to bind to the victim's session — the victim's own GitHub identity is what gets signed in, unchanged. The redirect happens post-authentication and does not escalate into `Shipit.github_teams`, expose unauthenticated stack/task data, or carry GitHub credentials via SSRF.

## Likelihood Explanation
Low cost for the attacker (send a link with a crafted `origin`/`Referer` query parameter) and no privileges required, but the realized impact is limited to a UI-redirect/phishing primitive rather than credential or data exfiltration, since the session cookie is not disclosed to the third-party origin by the redirect alone.

## Recommendation
Validate `return_url` before redirecting: restrict it to relative paths within the engine (e.g., reject any value containing `://` or a `Host`, or use `URI.parse` plus an explicit check that `uri.host.nil?`), falling back to `root_path` otherwise, similar to Rails' recommended open-redirect mitigation.

```ruby
# frozen_string_literal: true

module Shipit
  class GithubAuthenticationController < ActionController::Base
    include Shipit::Engine.routes.url_helpers

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end

    def logout
      reset_session
      redirect_to(root_path)
    end

    private

    def sign_in_github(auth)
      user = User.find_or_create_from_github(auth.extra.raw_info)
      user.update(github_access_token: auth.credentials.token)
      user.id
    end
  end
```
