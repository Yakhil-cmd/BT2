## Confirmed cross-organization write via mismatched signature-authenticated identity vs. acted-upon repository field

### Title
Webhook signature is verified against the organization declared in `repository.owner.login`, but every event handler acts on `repository.full_name` — a different, unauthenticated field in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the HMAC against based on `repository_owner`, which is read from `payload.dig('repository', 'owner', 'login')`. [1](#0-0) [2](#0-1)  Every downstream event handler (e.g. `PushHandler`) instead resolves the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')`. [3](#0-2)  These are two independent, attacker-controlled JSON fields inside the same payload. In a multi-organization deployment (`Shipit.github(organization:)` supports a per-organization `webhook_secret` map), an attacker who legitimately administers/owns their own GitHub App installation for `attacker-org` (and therefore knows `attacker-org`'s `webhook_secret`) can forge a `push` payload where `repository.owner.login = "attacker-org"` (so the correct secret is used and the HMAC validates) but `repository.full_name = "victim-org/victim-repo"`.

### Finding Description
The equality that should hold is: `organization whose secret authenticated the payload == organization/repository the payload's handlers act on`. This engine breaks that binding:

- `verify_signature` computes `Shipit.github(organization: repository_owner)` from `repository.owner.login` (or `organization.login` fallback) and checks `verify_webhook_signature(signature, raw_post)` against that organization's `webhook_secret`. [4](#0-3) 
- `GitHubApp#verify_webhook_signature` is a pure HMAC-SHA1 check of the raw body against a secret keyed only by the resolved `organization` — it says nothing about which repository the body's *other* fields reference. [5](#0-4) 
- `Shipit.github` explicitly supports "Using Multiple Github Applications", where each organization has its **own independent `webhook_secret`**. [6](#0-5) [7](#0-6) 
- Once the signature passes, `WebhooksController#create` dispatches the entire parsed payload to handlers (e.g. `Handlers::PushHandler`), unconditionally. [8](#0-7) 
- `Handler#stacks` / `#repository_name` resolve the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` — a field that was never used to select the verifying secret. [3](#0-2) 
- `Repository.from_github_repo_name` simply splits `owner/name` from that string and looks up any repository in the datastore, regardless of which org's secret validated the request. [9](#0-8) 

Since HMAC-SHA1 authenticates the *bytes* of the body, not any specific field's semantic meaning, an attacker who controls one organization's webhook secret (via their own legitimate GitHub App installation on `attacker-org`) can freely author the JSON body, including setting `repository.full_name` to point at any other repository/stack tracked by this Shipit instance, while keeping `repository.owner.login` set to `attacker-org` so the signature check passes with the secret they know.

### Impact Explanation
This results in **unauthorized deploy/rollback triggering across organizations/repositories** the attacker does not control: `PushHandler#process` invokes `stack.sync_github(expected_head_sha:)` on any stack whose repository matches the forged `full_name`, which enqueues `GithubSyncJob` and can drive continuous-deployment/merge-queue behavior for a victim's stack using a body the attacker fully authored (arbitrary `ref`, `after` SHA, etc.). Depending on which handler is targeted (`push`, `status`, `check_suite`, `membership`), this can falsify CI status, alter merge-queue state, or synchronize/trigger deploys for repositories outside the attacker's own organization — a cross-repository write achieved purely by exploiting the mismatch between the field used for authentication (`repository.owner.login`) and the field used for the actual write action (`repository.full_name`). This matches the "an organization that authenticated versus the repository that is written" binding explicitly called out as in-scope.

### Likelihood Explanation
Requires only that the target Shipit deployment be configured with **multiple GitHub organizations**, each with its own `webhook_secret` (a documented, supported configuration in `docs/setup.md`/`README.md`), and that the attacker legitimately controls (owns/administers) at least one of those configured organizations' GitHub App — a standard, unprivileged capability relative to any *other* tracked repository. No access to the victim's secrets, GitHub App, or Shipit account is needed. The webhook endpoint (`/webhooks`) is unauthenticated by design (session/API-token free) and only gated by this signature check, so this is directly reachable by anyone who can hit the public endpoint and knows one org's secret.

### Recommendation
Bind the signature-verifying identity to the identity actually acted upon: after computing `repository_owner` for secret selection, re-validate that `payload.dig('repository', 'full_name')` (or `organization.login` for org-level events like `membership`) belongs to the *same* organization used to select the `webhook_secret`, rejecting (422) on mismatch. Alternatively, remove per-organization secret lookup keyed on attacker-controlled payload content and instead determine the target Stack organization from the resolved repository record (looked up first), verifying the signature with that repository's *known, persisted* organization/secret rather than a value taken from the unauthenticated request body.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (per `docs/setup.md` "Using Multiple Github Applications").
2. Attacker legitimately owns the GitHub App for `attacker-org` and thus knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the HMAC validates successfully. [1](#0-0) 
6. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves stacks via `repository.full_name = "victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack. [3](#0-2) [10](#0-9)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

**File:** lib/shipit.rb (L170-200)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
