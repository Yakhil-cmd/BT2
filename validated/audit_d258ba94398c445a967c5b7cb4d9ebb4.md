### Title
Sandwich/Front-Running of AMM-style AAs via Public Pre-Stabilization Visibility of Trigger Units - (File: `test/samples/uniswap_like_market_maker.oscript`, `main_chain.js`)

### Summary
Autonomous Agents (AAs) that implement AMM-style pricing — exactly the pattern shipped as an official ocore reference implementation in `test/samples/uniswap_like_market_maker.oscript` — compute swap/issue amounts from the AA's *current* on-chain reserve balance minus the trigger's own incoming output, the same "balance-diff" pattern flagged as vulnerable to front-running in the external DODO `buyShares()` report. Because Obyte units (including AA triggers) are broadcast and visible in the public DAG well before they are processed (which only happens once their MCI becomes stable), any unprivileged AA trigger sender can observe a pending, unstabilized trade against such an AA and race a competing trigger to be sequenced ahead of (or immediately after) it, extracting value exactly as in the classic front-running/sandwich scenario described in the report.

### Finding Description
The reference AMM AA computes its trade ratio like this: [1](#0-0) 

`$asset_balance` and `$bytes_balance` are derived from the AA's live pool reserves (`balance[...]`) at the moment the trigger is *executed*, minus the trigger's own inbound output — the direct analog of `GSPFunding.sol`'s `baseBalance/quoteBalance - reserve`. The price/ratio a trader receives thus depends entirely on what other triggers have already been applied to the pool by the time this trigger runs, not on what the pool looked like when the trader broadcast their unit.

Crucially, AA triggers are not processed at broadcast time. They are queued into `aa_triggers` only once their MCI stabilizes, and are executed in a fully deterministic but publicly-computable order: [2](#0-1) 

and consumed later by: [3](#0-2) 

Both queries order pending triggers by `level`/`mci` and then by the unit hash (`ORDER BY units.level, units.unit, address`), i.e., ordering is a public, computable function of unit content that is known before stabilization. Since the entire DAG of unstable units (including outputs sent to any AA address) is broadcast and visible to all peers before the MCI stabilizes and the trigger fires, an attacker can:
1. Watch the p2p network / DAG for a large pending payment to the AMM AA address (visible as soon as it is broadcast, long before it is stable/executed).
2. Craft and broadcast their own trigger unit choosing parents/timing so that it lands in the DAG with a smaller `level`/unit hash than the victim's unit (or in an earlier MCI), guaranteeing it is processed first by `handleAATriggers`.
3. Buy right before the victim's large trade (moving `$asset_balance`/`$bytes_balance` favorably), let the victim's trade execute at the now-worse ratio, then reverse the position immediately after — a sandwich attack functionally identical to the mempool front-running described against `buyShares()`.

This is possible precisely because, unlike a hidden mempool, the whole causal graph of not-yet-executed AA triggers is public and their relative execution order is a deterministic, attacker-computable function of content the attacker fully controls before stabilization.

### Impact Explanation
A trader interacting with an AMM-style AA (a pattern explicitly documented and shipped by ocore itself) can have their trade sandwiched: they receive a worse `$issue_amount`/`$amount` than the pool state at broadcast time implied, while the attacker extracts the difference risk-free. This constitutes AA fund loss for genuine users and unauthorized value extraction, matching the High severity of the original report (unfair minting/mispriced swaps at LPs'/traders' expense).

### Likelihood Explanation
Any AA trigger sender can reach this: no special privileges, no reliance on a malicious hub/witness/node, and no need to break consensus — only observation of publicly broadcast, not-yet-stable units and timely submission of a competing trigger, which is a normal, unprivileged wallet operation. The deterministic `level`/unit-hash ordering used by `handleAATriggers` gives the attacker a computable target to game rather than needing to control ordering directly.

### Recommendation
AAs built on the "read `balance[asset]` and diff against `trigger.output`" pattern should not be treated as front-running-safe by default; ocore's own documentation/sample for this pattern should be updated to warn authors and/or provide a safer primitive (e.g., commit-reveal, minimum-output/slippage guard parameters supplied by the trigger and checked against the realized ratio, TWAP-based pricing, or explicit `bounce` when a large discrepancy vs. an expected price passed in `trigger.data` is detected) so that AA authors copying the reference AMM pattern do not inherit this bug class.

### Proof of Concept
1. Deploy an AA using the exact logic from `test/samples/uniswap_like_market_maker.oscript` (invest/exchange cases at lines 33-66 and 102-123).
2. Victim broadcasts a large "exchange bytes to asset" trigger unit (visible immediately on the DAG, not yet stable).
3. Attacker, observing this unstable unit, immediately broadcasts their own "exchange asset to bytes" or "invest" trigger, choosing parents so their unit's `level`/hash sorts before the victim's per the `ORDER BY units.level, units.unit, address` clauses in `handleAATriggers` (`main_chain.js:1705`, `aa_composer.js:68`).
4. Once the MCI stabilizes, `handleAATriggers` executes the attacker's trigger first, shifting `$asset_balance`/`$bytes_balance`; the victim's trigger is then processed against the now-worse reserves, receiving a worse `$amount`/`$issue_amount` than expected at broadcast time; attacker reverses their position in a follow-up trigger to realize the profit.
