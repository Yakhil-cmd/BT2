## Finding: Asset definer can retroactively freeze a spender-attested asset holder's balance by updating the attestor list

### Title
Asset definer can permanently freeze another user's coin balance by removing their address from the attestor list of a `spender_attested` asset — (File: `validation.js`)

### Summary
Ocore lets anyone define a custom asset with `spender_attested: true`, meaning only addresses on a definer-controlled "attestor" allowlist may hold/spend that asset. The definer fully controls this list via a single, unprivileged `asset_attestors` message and can update it at any time, with no restriction preventing the removal of an address that already holds a balance. Because the payment-validation code always checks the *current* (most recent, before-last-ball) attestor list — not the list that was in effect when the coins were received — a definer can mint/transfer coins to a victim while their address is attested, then remove that address from the list, permanently freezing every output the victim owns in that asset, including self-payment/change. This mirrors the reported pattern of a privileged party (here, the asset definer, analogous to the "option token creator") controlling an address-approval mechanism (analogous to the blocklisted "receiver") that determines whether a counterparty can ever move funds they already committed to the system.

### Finding Description
When an asset is defined with `spender_attested: true`, `validateAssetDefinition` requires an initial attestor list [1](#0-0) . Later, the definer alone can replace this list via an `asset_attestors` message — `validateAttestorListUpdate` only checks that the asset actually requires attestors and that the author is the definer; it performs no check preventing removal of addresses that currently hold balances of the asset [2](#0-1) .

When any payment of that asset is validated (`validatePaymentInputsAndOutputs`), if `spender_attested` is set, **all** output addresses — including change/self outputs — must be in the attestor list, or the payment is rejected outright: `"some output addresses are not attested"` [3](#0-2) .

Crucially, `storage.readAsset` always resolves the attestor list to the **latest** `asset_attestors` unit stable/confirmed before the payment's `last_ball_mci`, not the list that existed when the victim's coins were originally issued/received [4](#0-3) . The wallet-side composer performs only a shallow guard (checking that *some* author is attested, not that every relevant output/change address will remain attested) [5](#0-4) , so a spend attempt that used to be valid can be silently rejected at validation time once the definer edits the list.

### Impact Explanation
A definer can:
1. Define an asset with `spender_attested: true` and an attestor list that includes a victim's address.
2. Issue or transfer asset units to the victim, who accepts them because their address is currently attested.
3. Publish a new `asset_attestors` message removing the victim's address from the list.
4. From that point on, any payment message that includes the victim's address as an output — including the victim trying to move their own coins to themselves as change, or to a third party — fails validation with `"some output addresses are not attested"`.

The victim's entire balance of that asset becomes permanently unspendable (frozen), since there is no protocol mechanism to recover coins whose holder address has been excluded from the attestor list, and this exclusion is entirely under the unilateral control of the definer, executed via a single ordinary unit. This directly parallels the reported class of bug: a privileged, attacker-controlled allowlist/denylist that a counterparty implicitly trusts when accepting value, and that can be weaponized after the counterparty has already committed funds/value, permanently locking them.

### Likelihood Explanation
This requires only that a victim accept and hold a `spender_attested` asset from an untrusted/malicious definer — a realistic scenario for any asset distributed as a reward, payment, or in a swap, since `spender_attested` assets look legitimate (e.g., can be advertised as KYC/compliance tokens) and the flag alone does not indicate that the definer will act maliciously with subsequent attestor updates. No special privileges beyond being an asset definer (open to anyone) are required, and the state-changing action (`asset_attestors`) is a normal, single-author message.

### Recommendation
- Consider validating that a payment's output addresses remain attested to the version of the attestor list in effect at the time the input coins were themselves received/attested (i.e., not allowing a definer to retroactively invalidate previously-attested holders), or
- Provide a bounded grace period / prior-list fallback so that funds already held by a previously-attested address remain spendable (e.g., to the definer or a neutral escrow) even after removal from the list, avoiding irrecoverable freezing, or
- Surface/warn wallet users prominently when accepting a `spender_attested` asset that the definer can unilaterally freeze already-held balances at any time, so this risk is explicit rather than implicit.

### Proof of Concept
1. Attacker A defines asset `X` with `is_transferrable: true`, `spender_attested: true`, `attestors: [A, B]` (`validateAssetDefinition`, `validation.js:2725-2827`).
2. A issues/sends units of `X` to victim address `B`. Since `B` is attested, this succeeds (`validatePaymentInputsAndOutputs`, `validation.js:2630-2641`).
3. A posts a new `asset_attestors` message for asset `X` with `attestors: [A]` only, dropping `B` (`validateAttestorListUpdate`, `validation.js:2829-2848` — no check against holders).
4. `B` now attempts any payment of asset `X` (even change-only to self). `storage.readAsset` resolves the current attestor list `[A]` (`storage.js:1917-1946`), `B` is not in it, and `validatePaymentInputsAndOutputs` rejects the unit with `"some output addresses are not attested"` (`validation.js:2637-2638`).
5. `B`'s entire balance of asset `X` is now permanently unspendable.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
