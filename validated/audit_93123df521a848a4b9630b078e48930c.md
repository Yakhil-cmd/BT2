### Title
Header-commission over-issuance via independent per-recipient rounding in `calcHeadersCommissions()` - (File: headers_commission.js)

### Summary
`calcHeadersCommissions()` splits a parent unit's `headers_commission` fee among the recipients listed in `earned_headers_commission_recipients` by rounding each recipient's share independently, instead of rounding once and distributing the remainder deterministically. Because each of the (up to `MAX_AUTHORS_PER_UNIT`) recipients is rounded separately, the sum of the individually-rounded amounts can exceed the original fee amount that was actually paid by the payer unit, creating bytes/units out of thin air.

### Finding Description
When a child unit wins the headers commission for a parent unit, the commission is split among recipients defined in `objUnit.assocEarnedHeadersCommissionRecipients` (derived from `earned_headers_commission_recipients`, whose `earned_headers_commission_share` values are validated only to sum to exactly 100 in `validateHeadersCommissionRecipients()`) [4](#0-3) . In `calcHeadersCommissions()`, for each recipient the code computes `Math.round(full_amount * share / 100.0)` independently [1](#0-0) , and the MySQL fast-path does the analogous `ROUND(punits.headers_commission*earned_headers_commission_share/100.0)` per row [2](#0-1) .

This is structurally the same rounding-asymmetry bug class as the reported Uniswap issue: two values that are supposed to be inverses/complements of a single fixed quantity (`full_amount`) are each rounded independently rather than rounding once and deriving the remainder, so their sum does not necessarily equal the original quantity. With standard "round half up," splitting a fee among an odd combination of shares (e.g., two 50/50 recipients when `full_amount` is odd, or three 33/33/34 recipients) predictably rounds every share up, producing a sum strictly greater than `full_amount`.

The resulting `arrValues` rows are inserted into `headers_commission_contributions` without any check that `SUM(amount) per payer_unit == full_amount` — the only consistency check in the code compares the SQL-derived and in-memory RAM-computed results against each other (`_.isEqual`), not against the original fee, so both paths would agree while both silently over-mint [5](#0-4) . These contributions are then aggregated straight into spendable `headers_commission_outputs` via `SUM(amount) ... GROUP BY main_chain_index, address` with no reconciliation against the payer's actual `headers_commission` field [3](#0-2) . Those outputs later become spendable bytes via `headers_commission` type inputs validated with `mc_outputs.calcEarnings()` and accepted as `commission` at face value in `validatePaymentInputsAndOutputs()` [6](#0-5) .

### Impact Explanation
An attacker who controls (or colludes to author) a unit with `earned_headers_commission_recipients` can pick a combination of addresses/shares that guarantees the sum of independently-rounded amounts exceeds the winning headers commission's true value by 1 (or more, scaling with the number of recipients, bounded by `MAX_AUTHORS_PER_UNIT`). Every subsequent headers-commission win by that unit as a "winner child" mints the extra byte(s) as genuinely spendable `headers_commission_outputs`, which is a supply-inflation bug: new base-currency value is created without a corresponding fee payment, deterministically and repeatably.

### Likelihood Explanation
This requires only posting a normal unit with a crafted `earned_headers_commission_recipients` list — something any unprivileged unit author can construct — and then being selected as the "winner child" for headers commission (a routine, permissionless, deterministic process based on hash comparison in `getWinnerInfo()`) [7](#0-6) . No special privileges, timing, or network position are required; the attacker only needs to control the share percentages of their own unit's recipients, which is fully attacker-chosen. This makes the likelihood high given the low bar to construct the triggering shares.

### Recommendation
Round only the last recipient's amount as `full_amount - sum(previous rounded amounts)` (or otherwise compute one recipient's share as the remainder) so that the sum of all recipient amounts always equals `full_amount` exactly, both in the SQL query and the JS in-memory calculation, mirroring the general fix pattern of rounding once and deriving remainders rather than rounding each independent share.

### Proof of Concept
1. An attacker crafts a unit `U` naming two recipients A and B, each with `earned_headers_commission_share = 50` (sum = 100, passes `validateHeadersCommissionRecipients`).
2. `U` (or a descendant single-author unit under attacker's control) becomes the deterministic headers-commission "winner child" for a parent unit whose `headers_commission` fee is an odd number, e.g. `full_amount = 101`.
3. `calcHeadersCommissions()` computes `amount_A = Math.round(101*50/100) = Math.round(50.5) = 51` and `amount_B = Math.round(101*50/100) = 51`, for a combined total of 102 [1](#0-0) .
4. Both rows are inserted into `headers_commission_contributions` and later summed into `headers_commission_outputs`, minting 102 spendable bytes from a 101-byte fee — 1 byte created out of nothing, repeatable on every winning unit constructed this way.
