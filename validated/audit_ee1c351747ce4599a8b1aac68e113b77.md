### Title
Cross-organization team-hijacking via unscoped `Team.find_or_create_by!(github_id:)` in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` looks up an existing `Team` solely by `github_id`, without verifying that the webhook's authenticated organization (`params.organization.login`) matches the `Team#organization` already stored. Because `WebhooksController#verify_signature` only proves that a payload was signed by *some* configured org's `webhook_secret`, not that it is authoritative for the referenced team, any organization onboarded to the same Shipit instance can forge a `membership`/`added` event that adds an attacker-controlled GitHub login to a team owned by a completely unrelated organization.

### Finding Description
The broken binding, stated as an equality that must hold but does not: `verifying_organization (params.organization.login, authenticated via Shipit.github(organization: repository_owner).verify_webhook_signature) == target.organization (Team#organization of the team matched by github_id)`.

Trace:
- `WebhooksController#verify_signature` derives `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)`. [1](#0-0)  This only proves the request was HMAC-signed with the `webhook_secret` belonging to whatever org the payload claims (`repository_owner`) — it never checks that this org is the one that owns the target team.
- The payload is fully attacker-authored JSON, signed with the attacker's own real `webhook_secret` for their own org (which they legitimately possess as the owner of that org's GitHub App). Nothing forces `team.id` in the payload to correspond to a real team in the attacker's own org.
- `MembershipHandler#process` calls `find_or_create_team!`, which does: `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }`. [2](#0-1)  The `organization` assignment inside the block only runs on *creation*. If a `Team` with that `github_id` already exists (created earlier by its real, legitimate organization), `find_or_create_by!` simply returns the existing record — with no check that `params.organization.login == team.organization`.
- `process` then unconditionally calls `team.add_member(member)` for action `'added'`, and `Team#add_member` appends the member without any organization check. [3](#0-2)  The `Membership` model only enforces `user_id` uniqueness scoped to `team_id`, no organization binding at all. [4](#0-3) 

Exploit flow: attacker owns org A and org B, each with a configured GitHub App and known `webhook_secret` (this is standard, self-service GitHub App setup — no Shipit secret is required). Attacker learns/guesses the victim team's `github_id` (an integer, potentially discoverable via prior legitimate webhooks, public team pages, or simple enumeration). Attacker crafts two `membership`/`added` JSON payloads, each referencing `team.id = <victim_github_id>` but with `organization.login` = org A and org B respectively, and `member.login` set to attacker-controlled GitHub usernames. Each payload is HMAC-signed with the correct secret for its own org and POSTed to `/webhooks`. Both pass `verify_signature` (each org's own secret matches its own payload). Both handlers resolve to the *same* existing `Team` row (matched only by `github_id`) and call `add_member`, inserting two `Membership` rows for the victim team, owned by users from two unrelated orgs.

None of the existing guards catch this: `verify_signature` authenticates the org named in the payload, not the org owning the target team; `drop_unhandled_event` only filters unhandled event types; the `ExplicitParameters` schema in `MembershipHandler.params` only validates shape/types, not cross-record authorization; `Membership` validation only prevents duplicate `(user_id, team_id)` pairs.

### Impact Explanation
An attacker who owns any GitHub org configured in Shipit's `github` secrets config can insert arbitrary GitHub users (including logins they control) into any `Team` record already present in the Shipit database, regardless of which org actually owns that team. If the targeted `Team` is one of `Shipit.github_teams` — the set gating application access via `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) and enforced in `force_github_authentication` — [5](#0-4) [6](#0-5)  then the attacker can log in via OAuth as the injected user and gain full authenticated access to the Shipit instance (stacks, tasks, deploys, rollbacks), which they were never authorized for. This matches the High-severity category "escalation into `Shipit.github_teams` authorization." It is repeatable against any team whose `github_id` is known/guessable, from any number of unrelated attacker-owned orgs, and is not a one-off edge case.

### Likelihood Explanation
Preconditions: the Shipit instance must be configured for multiple GitHub organizations (documented "Using Multiple Github Applications" setup), and one org must be attacker-controlled with a self-created GitHub App and its own real `webhook_secret` — both trivially obtainable by any GitHub user with no Shipit privileges. The only non-trivial requirement is knowing the target `Team#github_id`, an integer that may be learned from prior webhook deliveries, GitHub UI/API team pages, or brute-forced (GitHub team IDs are sequential integers, not secrets). No Shipit session, API token, or GitHub App private key is required. This is feasible and repeatable at low attacker cost.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/match to both `github_id` and `organization` (e.g., `Team.find_by(github_id: params.team.id)` and raise/drop the event if the found team's `organization` does not equal `params.organization.login`, only creating new teams when no conflicting record exists), and add a model-level validation ensuring a `Team`'s `organization` cannot silently diverge from the webhook's verified organization when mutated by webhook handlers.

### Proof of Concept
```ruby
test ":membership forged from unrelated org cannot mutate another org's team" do
  target_team = shipit_teams(:shopify_developers) # organization: 'shopify'

  # Forged event 1: attacker org A
  @request.headers['X-Github-Event'] = 'membership'
  Shipit.stubs(:github).with(organization: 'attacker-org-a').returns(
    stub(verify_webhook_signature: true)
  )
  post :create, body: {
    action: 'added',
    team: { id: target_team.github_id, name: target_team.name, slug: target_team.slug, url: target_team.api_url },
    organization: { login: 'attacker-org-a' },
    member: { login: 'attacker-user-1' },
    repository: { owner: { login: 'attacker-org-a' } }
  }.to_json, as: :json

  # Forged event 2: attacker org B
  Shipit.stubs(:github).with(organization: 'attacker-org-b').returns(
    stub(verify_webhook_signature: true)
  )
  post :create, body: {
    action: 'added',
    team: { id: target_team.github_id, name: target_team.name, slug: target_team.slug, url: target_team.api_url },
    organization: { login: 'attacker-org-b' },
    member: { login: 'attacker-user-2' },
    repository: { owner: { login: 'attacker-org-b' } }
  }.to_json, as: :json

  target_team.reload
  # Both sides of the binding checked: verifying org != target.organization ('shopify') for both requests,
  # yet both memberships were inserted.
  assert_includes target_team.members.map(&:login), 'attacker-user-1'
  assert_includes target_team.members.map(&:login), 'attacker-user-2'
  refute_equal 'attacker-org-a', target_team.organization
  refute_equal 'attacker-org-b', target_team.organization
end
```
