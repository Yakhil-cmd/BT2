### Title
Missing newline validation on AA-formula `data_feed`/`in_data_feed` `feed_name` allows data-feed key injection — (File: `data_feeds.js`, `formula/evaluation.js`)

### Summary
The oscript/AA formula functions `data_feed[[...]]` and `in_data_feed[[...]]` let an AA read or test values posted to a data feed by naming the feed with `feed_name`, which can be a dynamic expression derived from attacker-controlled trigger data. Unlike the unit-level `data_feed` message validators, which explicitly reject `\n` in `feed_name`/value [1](#0-0) , the runtime evaluator for the formula functions never checks for embedded newlines in the dynamically-computed `feed_name` before using it to build a `\n`-delimited leveldb key.

### Finding Description
When an AA formula evaluates `data_feed`/`in_data_feed`, the `feed_name` is taken directly from the evaluated parameter with only a type/emptiness check — no newline or length check: [2](#0-1) [3](#0-2) 

The static AA-definition-time validators (`validateDataFeed` / `validateDataFeedExists` in `formula/validation.js`) only reject empty `feed_name`; they never check for `\n`, and moreover this check is skipped entirely whenever `feed_name` is itself a formula/expression (not a literal string) rather than a compile-time constant: [4](#0-3) [5](#0-4) 

This resolved `feed_name` is passed to `dataFeedExists`/`readDataFeedValue`, which build leveldb key prefixes by naively joining `address`, `feed_name`, and value with `\n` as a delimiter, with no escaping: [6](#0-5) 

Because the delimiter (`\n`) is not escaped or forbidden in `feed_name` at evaluation time, an attacker who controls `feed_name` (e.g. via `trigger.data.feed_name` in an AA that composes the feed name from trigger input) can embed `\n` sequences to fabricate an arbitrary `key_prefix`/range-query bound that matches a completely different, real key that some oracle previously wrote for the same address under a different feed name and value — even though `data_feed`/`in_data_feed` message writes are themselves protected against `\n` in `feed_name` (`validation.js:1936`, `aa_validation.js:100`). The read side has no equivalent protection when the name is computed dynamically inside the formula engine.

### Impact Explanation
An AA that grants funds or executes logic conditioned on `data_feed`/`in_data_feed` (e.g., "if oracle posted `delivery_confirmed`=`yes` for this address, release payment") can have its feed-name matching subverted. By injecting a newline-crafted `feed_name` through trigger data, an attacker can make the underlying leveldb range query match an unrelated, already-existing key from the same oracle address (a different feed name/value/mci combination), forging satisfaction (or defeat) of the oracle condition the AA author intended to enforce. This can lead to unauthorized release of AA funds or bypass of an oracle-gated condition — i.e., concrete unauthorized spending/fund loss from an AA.

### Likelihood Explanation
Reachable by any unprivileged unit poster who can trigger an AA that builds a `data_feed`/`in_data_feed` `feed_name` from trigger data (a common, encouraged oscript pattern for flexible oracle lookups). No special privileges, hub/peer compromise, or node cooperation are required — only crafting a trigger unit with a `feed_name` string containing `\n`.

### Recommendation
In the formula evaluator (`formula/evaluation.js`, `getDataFeed` and the `in_data_feed` case), after resolving `feed_name` (and similarly `oracles`/other string params interpolated into kvstore keys) at evaluation time, reject values containing `\n` and enforce the same length limit used for the on-chain message validators (`constants.MAX_DATA_FEED_NAME_LENGTH`/`MAX_DATA_FEED_VALUE_LENGTH`), mirroring the checks already present in `validation.js` and `aa_validation.js` for the `data_feed` app message.

### Proof of Concept
1. Deploy an AA that on trigger reads `data_feed[[oracles=<oracle_address>, feed_name=trigger.data.feed_name, feed_value=trigger.data.feed_value]]` (or `in_data_feed`) and releases funds when the check succeeds.
2. Have the same oracle address previously post an unrelated data feed, e.g. `feed_name="secret_other_feed"`, `value=42`, at some MCI — this data is legitimately stored under key `'df\n'+oracle+'\nsecret_other_feed\nn\n<encoded 42>\n<mci>'`.
3. Send a trigger unit with `trigger.data.feed_name` crafted to contain `\n` such that the computed `key_prefix` in `dataFeedByAddressExists` (`data_feeds.js:139`) collides with the unrelated stored key from step 2, while `trigger.data.feed_value`/relation are chosen to match.
4. Observe the AA's `data_feed`/`in_data_feed` check evaluates as satisfied despite the oracle never having posted the specific feed_name/value the AA author intended, causing the AA to execute its fund-releasing branch.
