### Title
`machine.environment` from a fork's `shipit.yml` reaches `PTY.spawn` unfiltered, enabling loader-variable injection (e.g. `PERL5LIB`) into `ruby`/`bundle` dependency steps - ([File: app/models/shipit/deploy_spec.rb])

### Summary
`DeploySpec#machine_env` returns `config('machine', 'environment')` verbatim from the checked-out `shipit.yml`, and `TaskCommands#env` merges it directly into the environment hash passed to `Command#start`/`PTY.spawn` with no whitelist check, unlike deploy/rollback/task variables which are always passed through `EnvironmentVariables#permit`. Since a review stack's working directory is checked out at the PR's head commit, the fork branch author fully controls the `shipit.yml` `machine.environment` block, including loader variables such as `PERL5LIB`, `RUBYOPT`, or `BUNDLE_*`, which will affect any `ruby`/`bundle` step run via `TaskCommands#install_dependencies`.

### Finding Description
The broken binding is: the set of environment variables reaching `PTY.spawn` for a review-stack dependency step should equal `Command#env` restricted to variables explicitly declared/whitelisted for that stack (as is done for deploy/rollback/task variables), but in practice it equals `Command#env` **plus every key the fork author placed under `machine:` `environment:` in their own `shipit.yml`**, unfiltered.

Trace:
- `TaskCommands#install_dependencies` builds `Command.new(command_line, env:, chdir: steps_directory)` using `deploy_spec.dependencies_steps!` [1](#0-0) .
- `TaskCommands#env` merges, among other things, `deploy_spec.machine_env` directly, with no call to `EnvironmentVariables.permit` [2](#0-1) .
- `DeploySpec#machine_env` returns `config('machine', 'environment') || {}`, i.e., whatever the `shipit.yml` author wrote, with zero sanitization [3](#0-2) .
- Compare this to `filter_deploy_envs`/`filter_rollback_envs`, which explicitly route user-supplied env through `EnvironmentVariables.with(env).permit(deploy_variables)` to enforce a whitelist [4](#0-3) . `EnvironmentVariables#permit` raises `NotPermitted` for any key not in the declared variable list [5](#0-4) . `machine_env` has no equivalent guard.
- `deploy_spec` for a task is loaded from the checked-out working directory (`DeploySpec::FileSystem.new(@task.working_directory, @stack)`), reading whichever `shipit.yml`/`.shipit/shipit.yml` is present at that commit [6](#0-5) [7](#0-6) .
- `Command#start` merges `@env` into the process environment sent to `PTY.spawn` with no denylist of loader/interpreter variables (`PERL5LIB`, `RUBYOPT`, `LD_PRELOAD`, etc.) [8](#0-7) .

Exploit flow: an attacker forks the repository, adds a `shipit.yml` (or `.shipit/shipit.yml`) on their branch containing `machine: environment: PERL5LIB: /path/to/attacker/perl/lib`, and opens a PR against a repository that provisions review stacks for PRs. When the stack's dependency step (a `ruby`/`bundle` command, e.g., `bundle install`) is scheduled via `PerformTaskJob` → `TaskCommands#install_dependencies` → `Command#start`, the attacker-controlled `PERL5LIB` is present in the spawned process's environment. If any `perl` invocation occurs in that toolchain (directly or via a subprocess spawned by `bundle`/`ruby` extension builds), it will pick up modules from the attacker path, achieving code execution on the deploy host.

Existing guards (`EnvironmentVariables#permit`, `VariableDefinition` whitelisting) apply to deploy/rollback/task variables but are never invoked for `machine_env`, so they do not prevent this divergence.

### Impact Explanation
Successful exploitation results in code execution during a dependency-installation step on the Shipit deploy host, under whatever OS user runs task/deploy jobs — this matches the Critical RCE impact category (`Command`/`PTY.spawn`). The blast radius is scoped to whichever repository's review stack runs the tainted step, but is repeatable by any unprivileged contributor able to open a PR against a repo that has review stacks enabled and Ruby/Bundler based dependency discovery, since the fork author fully controls the `shipit.yml` consumed for their own PR's working directory.

### Likelihood Explanation
Preconditions: the target repository must have review stacks (PR-based stacks) enabled, use a Ruby/Bundler dependency-detection path (`BundlerDiscovery`/`RubygemsDiscovery`) so a `bundle`/`ruby` step runs, and the operator/host environment's `ruby`/`perl` toolchain must actually consult `PERL5LIB` (or another loader variable) at some point in the dependency step (e.g., a native-extension build shelling to `perl` via `mkmf`/`extconf.rb`, which is common for gems with C extensions). Attacker cost is minimal — pushing a `shipit.yml` to their own fork branch and opening a PR — and the attack is fully repeatable across any PR/commit on the same or different target repositories that meet the preconditions.

### Recommendation
Apply an explicit whitelist/denylist to `machine_env` before merging it into the process environment: either (a) require repository maintainers to declare permitted `machine.environment` variable names (similar to `deploy_variables`) and run `EnvironmentVariables.with(deploy_spec.machine_env).permit(machine_variables)` in `TaskCommands#env`, or (b) reject or strip known interpreter/loader variables (`PERL5LIB`, `RUBYOPT`, `RUBYLIB`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_INSERT_LIBRARIES`, `BUNDLE_GEMFILE`, etc.) from `machine_env` and any fork-controlled config before it is merged into `Command`'s env. For review stacks specifically, consider not honoring `machine.environment` from the fork's own `shipit.yml` at all, sourcing it only from the base branch/trusted configuration.

### Proof of Concept
minitest plan (`test/unit/task_commands_test.rb` or similar), no live GitHub required:
1. Build a `Shipit::Stack`/`Shipit::ReviewStack` fixture whose `deploys_path`/working directory contains a `shipit.yml` with:
   ```yaml
   machine:
     environment:
       PERL5LIB: /tmp/attacker-perl-lib
   dependencies:
     override:
       - "bundle install"
   ```
2. Construct `Shipit::TaskCommands.new(task)` for that stack/commit and call `install_dependencies`.
3. Assert the binding is broken: `command = task_commands.install_dependencies.first; assert_equal '/tmp/attacker-perl-lib', command.env['PERL5LIB']` — i.e., the fork-supplied `PERL5LIB` reaches the `Command#env` used for the `bundle install` step, whereas the expected (safe) binding would raise `Shipit::EnvironmentVariables::NotPermitted` or otherwise strip the key, exactly as happens today for an un-whitelisted deploy/task variable (see `test/unit/environment_variables_test.rb` for the equivalent assertion pattern on `filter_deploy_envs`).
4. Optionally assert the same value is present in the hash actually passed to `PTY.spawn` by stubbing `PTY.spawn` in `Command#start` and inspecting the first argument.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
