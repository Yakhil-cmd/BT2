### Title
Cross-organization Team hijack via unscoped `github_id` lookup in `MembershipHandler#find_or_create_team!` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` record using only `github_id`, with no check that the webhook's verifying organization matches the organization that owns that `Team` row. Because `WebhooksController#verify_signature` authenticates the *organization*, not the *team*, any organization configured on the same Shipit instance can forge a `membership` webhook that adds an arbitrary user to a **pre-existing** privileged `Team` belonging to a different organization, as long as the attacker supplies that team's numeric GitHub `id`.

### Finding Description
The claimed binding is: *the org whose `webhook_secret` verified the payload == the org that owns the `Team` row `github_id` resolves to*. Tracing the code shows this binding is not enforced:

- `WebhooksController#verify_signature` picks the signing org from the payload itself (`repository.owner.login` or, as fallback, `organization.login`) and looks up that org's app config/secret via `Shipit.github(organization: repository_owner)`: [1](#0-0) [2](#0-1) 
  This only proves the request was signed by *some org's* secret (`attacker-org`'s, if `attacker-org` is a configured tenant on the same Shipit instance via `secrets.github`/`github_app_config`) — it says nothing about which `Team` row the payload is entitled to touch. [3](#0-2) 

- `MembershipHandler#find_or_create_team!` then does: [4](#0-3) 
  `Team.find_or_create_by!(github_id: params.team.id)` finds by `github_id` alone. The `do |team| ... team.organization = params.organization.login end` block only executes on **creation**; when a `Team` with that `github_id` already exists (e.g., a privileged team like `shopify_developers` seeded/created earlier), the existing record is returned unchanged and the attacker-supplied `organization` value is never checked against it.

- `process` then unconditionally does `team.add_member(member)`, appending the attacker-controlled `User` (`member.login`) to `team.members`: [5](#0-4) [6](#0-5) 

- `User#authorized?` grants app-wide access if the user belongs to any team in `Shipit.github_teams`: [7](#0-6) [8](#0-7) 

No `ExplicitParameters` schema check, model validation, or controller-level guard cross-checks `params.organization.login` against the `Team#organization` already stored for that `github_id`. The `Team` model exposes no uniqueness/organization-scoping validation on `github_id` either: [9](#0-8) 

**Exploit flow**: `attacker-org` must be a tenant configured in this Shipit deployment (it has its own entry, and thus its own `webhook_secret`, in `secrets.github`/`github_app_config`), but it is *not* listed in `Shipit.github_teams`. The attacker sends a `membership` webhook signed with `attacker-org`'s own secret, with `action: 'added'`, `team: { id: <github_id of a Shipit.github_teams team belonging to a different org>, name, slug, url }`, `organization: { login: 'attacker-org' }`, `member: { login: 'attacker' }`. `verify_signature` passes because the signature matches `attacker-org`'s secret. `find_or_create_team!` matches the existing privileged `Team` row by `github_id` and ignores that it was signed by a different org. `attacker` is added as a member of that team, and `User#authorized?` now returns true for the attacker, granting full application access.

### Impact Explanation
This is a High-severity authorization bypass: an attacker who controls (or merely operates a webhook endpoint appearing to belong to) any organization configured on a shared Shipit instance can escalate an arbitrary GitHub login into membership of a `Shipit.github_teams` team belonging to a wholly different, privileged organization, bypassing the app's entire authorization gate (`User#authorized?`). Once membership is granted, the attacker (or anyone controlling that GitHub login) obtains full authenticated access to the Shipit instance — deploy triggers, stack management, API client management, etc. The attack is repeatable for any known `github_id` of any team currently used for authorization, and affects all tenants sharing the Shipit instance, i.e., cross-tenant blast radius.

### Likelihood Explanation
Preconditions: (1) the Shipit deployment must host multiple GitHub organizations as tenants, each with its own `webhook_secret` (supported by `Shipit.github_app_config`); (2) `attacker-org` must be one such configured tenant (which the "unprivileged attacker" in this scenario administers), even though it's excluded from `Shipit.github_teams`; (3) the attacker must know the numeric GitHub `team.id` of a team currently listed in `Shipit.github_teams` — these IDs are not inherently secret and can be observed via GitHub API responses, team badge/API URLs, or brute-forced given they are small sequential integers. Given these preconditions, exploitation costs a single unauthenticated-but-signed HTTP POST to `/webhooks`, is fully repeatable, and requires no privileged Shipit session, token, or secret beyond the attacker's own legitimately-issued `attacker-org` webhook secret.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/raise if an existing `Team` with that `github_id` belongs to a different `organization` than the one that signed the webhook, instead of silently reusing it.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":membership from a different org cannot hijack an existing privileged team" do
  privileged_team = shipit_teams(:shopify_developers) # belongs to org "shopify", in Shipit.github_teams
  Shipit.stubs(:github_teams).returns([privileged_team])
  attacker = shipit_users(:attacker) # not currently a member of any Shipit.github_teams team

  # Simulate attacker-org's own valid webhook secret verifying successfully
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  @request.headers['X-Github-Event'] = 'membership'
  post :create, as: :json, body: {
    action: 'added',
    team: {
      id: privileged_team.github_id,   # known/guessed github_id of an existing Shipit.github_teams team
      name: privileged_team.name,
      slug: privileged_team.slug,
      url: privileged_team.api_url
    },
    organization: { login: 'attacker-org' }, # NOT the org that owns privileged_team
    member: { login: attacker.login }
  }.to_json
  assert_response :ok

  # Binding under test: org that verified the webhook ("attacker-org")
  # should NOT equal org owning the matched Team ("shopify") -- but exploit proves it is bypassed.
  assert_not_equal 'attacker-org', privileged_team.reload.organization
  assert_includes privileged_team.members, attacker
  assert attacker.authorized?, "attacker gained authorization via cross-org team hijack"
end
```
This demonstrates that a webhook verified solely by `attacker-org`'s secret can add `attacker` to `privileged_team` (owned by `shopify`), making `attacker.authorized?` true — confirming the broken binding between the verifying organization and the organization actually owning the matched `Team` row.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
