### Title
`Api::CCMenuController#stack` bypasses the ApiClient's stack scope, allowing a token authorized for one stack to read the state of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController` overrides the base `stack` lookup method with an unscoped `Stack.from_param!(params[:stack_id])`, breaking the binding between "the stack(s) an `ApiClient` token is authorized for" and "the stack whose data is actually returned."

### Finding Description
`Shipit::Api::BaseController` establishes the stack-scoping trust binding used by every other API controller: [1](#0-0) 

`stacks` restricts the visible set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is scoped to a single stack (`current_api_client.stack_id?`), and `stack` resolves `params[:stack_id]` only within that scoped relation via `stacks.from_param!(...)`. This is the mechanism that enforces "a stack a token authorizes == a stack it can toutouch," matching a `read:stack`-scoped client such as the `here_come_the_walrus` fixture, which is bound to a single stack: [2](#0-1) 

However, `Api::CCMenuController` defines its own `stack` method that ignores this scoping entirely and resolves the stack directly from the global `Stack` relation: [3](#0-2) 

Because `show` calls this local `stack` method (not `BaseController#stack`), any authenticated `ApiClient` — including one whose `stack_id` restricts it to a single, specific stack — can pass an arbitrary `stack_id` param and read data belonging to a completely different stack, as long as it still passes the `require_permission :read, :stack` permission check (which only checks the `read:stack` string permission, not the stack scope): [4](#0-3) 

This mirrors the bug class in the report: a comparison/authorization check exists (`require_permission`), but the actual object acted upon (`stack`) is resolved through a path that never re-applies the intended scope restriction — the equivalent of the `<=`/`>` sign inversion silently letting through values that should have been rejected. The broken binding is:

`ApiClient.stack_id` (the stack the token is authorized for) == `stack` used to render the CCMenu XML (the stack actually touched)

which, for `CCMenuController`, is not enforced.

### Impact Explanation
This allows a legitimately-issued but stack-scoped API token (e.g. distributed to a CI dashboard for a single stack) to read build/deploy status, lock state, and last-build metadata for any stack in the Shipit instance via `Api::CCMenuController#show`, including stacks the token holder should have no visibility into. This is an unauthenticated-scope read of stack state across repositories/stacks — matching the "High — unauthenticated read of stack state ... deploy output" impact category, since it crosses the authorization boundary the `ApiClient.stack_id` scoping is supposed to enforce.

### Likelihood Explanation
Medium: exploitation only requires possession of any valid `ApiClient` token that has `read:stack` permission (even one deliberately scoped to a single stack) and knowledge/guessing of another stack's `to_param` (typically `owner/repo/environment`, which is often predictable or discoverable). No special privileges beyond a legitimately-issued scoped token are needed.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it to reuse `BaseController#stacks.from_param!(params[:stack_id])`) so that stack-scoped `ApiClient` tokens cannot resolve stacks outside their authorized scope, consistent with every other API controller.

### Proof of Concept
1. Create/obtain an `ApiClient` token scoped to `stack_id` = Stack A, with permission `read:stack` (e.g. equivalent to the `here_come_the_walrus` fixture).
2. Authenticate to `Api::CCMenuController#show` using HTTP Basic auth with that token (or via the `token` query param, per `authenticate_api_client` override) and pass `stack_id` = Stack B (a stack the client is not scoped to).
3. Observe that `Stack.from_param!(params[:stack_id])` resolves Stack B unconditionally, and the controller renders Stack B's CCMenu XML (name, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`), even though the token is only authorized for Stack A. Compare with `Api::StacksController` or `Api::LocksController`, which correctly restrict resolution to `stacks.from_param!` and would reject the cross-stack access.

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end
```
