### Title
`provision?` ignores `repository.review_stacks_enabled` for `allow_with_label`/`prevent_with_label` behaviors, allowing unauthorized ReviewStack creation - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` uses Ruby operator precedence such that `review_stacks_enabled` only gates the `allow_all` branch, while the `allow_with_label` and `prevent_with_label` branches are evaluated unconditionally. A repository with `review_stacks_enabled: false` and `provisioning_behavior: :allow_with_label` will still have a `ReviewStack` created and queued for provisioning when a PR carries the configured label.

### Finding Description
The broken binding: the operator claims `repository.review_stacks_enabled` gates all provisioning decisions, but in code it only gates the first disjunct. [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

In Ruby, `&&` binds tighter than `||`, so this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present?) || (prevent_with_label? && !label_present?)`.

With `review_stacks_enabled == false` and `provisioning_behavior == :allow_with_label`, the first term is `false`, but the second term `(allow_with_label? && label_present?)` evaluates purely on the label and behavior flags, independent of `review_stacks_enabled`. If the PR carries the label matching `repository.provisioning_label_name`, `provision?` returns `true`.

`process` then calls `respond_to_pull_request_opened?` and, if true, invokes `ReviewStackAdapter#find_or_create!` → `create!`, which creates a `Shipit::ReviewStack`, attaches the pull request, and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)` for actual provisioning/deployment. [2](#0-1) [3](#0-2) 

Exploit request: an attacker who can open a pull request against a repository configured with `review_stacks_enabled: false, provisioning_behavior: :allow_with_label`, and can apply the configured label to their own PR (labels on one's own PR are attacker-controlled), sends (or GitHub relays) a `pull_request` `opened` webhook to `POST /webhooks` with `pull_request.labels` containing that label name. No existing guard prevents this: `params` schema validation only checks structure, not business rules; webhook signature verification, `drop_unhandled_event`, and `ExplicitParameters` do not check `review_stacks_enabled` at all — the omission is in `provision?` itself, so no other layer catches it.

### Impact Explanation
This causes a `Shipit::ReviewStack` (and associated `Shipit::PullRequest`) to be created and queued for provisioning against a repository whose operator explicitly disabled review stacks via `review_stacks_enabled: false`. This is a record written and a provisioning workflow queued (which subsequently runs deploy/provision tasks) for a repository configuration that did not authorize it — matching "a payload for one repository mutating another's [config's] stack" / unauthorized provisioning category. It is repeatable against any repository with this specific misconfiguration (`review_stacks_enabled: false` + `allow_with_label` or `prevent_with_label`), for every PR the attacker can label.

### Likelihood Explanation
Requires a specific repository configuration: `review_stacks_enabled: false` combined with `provisioning_behavior: :allow_with_label` (or `:prevent_with_label`) and a set `provisioning_label_name`. This is a plausible operator setup — e.g. an operator who briefly disabled review stacks but left the behavior/label configured, expecting `review_stacks_enabled` to be an authoritative kill switch. Attacker cost is trivial: open a PR and add a label they control on their own fork/PR (or omit a label for `prevent_with_label`). No secrets needed.

### Recommendation
Fix operator grouping in `provision?` to ensure `review_stacks_enabled` gates every branch, e.g.:

```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:

```ruby
test "does not create stacks when review_stacks_enabled is false even with allow_with_label and matching label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # repository.review_stacks_enabled == false
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```

Before the fix, this assertion fails because `Shipit::Stack.count` increases by 1 (a `ReviewStack` is created), demonstrating that `repository.review_stacks_enabled == false` does not equal the actual gating behavior of `provision?` for the `allow_with_label` branch. After applying the recommended fix, the assertion passes.
