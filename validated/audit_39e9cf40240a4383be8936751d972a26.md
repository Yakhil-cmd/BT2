### Title
Attacker-controlled commit content can permanently block symlink publication, causing persistent stale-content denial - (File: main.go)

### Summary
The Malt Dutch-auction bug is a "prevent-finalization" attack: an attacker crafts input that keeps a state-transition function from ever reaching its finalize/commit step, letting the attacker freeze the system in a state favorable to them. The closest reachable analog in `git-sync` is that `SyncRepo()` only calls `git.publishSymlink()` — the atomic "finalize" step of the sync contract — *after* `createWorktree()` and `configureWorktree()` succeed [1](#0-0) . Both of those steps execute git operations (`worktree add`, `reset --hard`, `submodule update --init [--recursive]`, sparse-checkout setup) directly against attacker-influenced repository content [2](#0-1) . Anyone who can push a commit to the tracked ref (or point a submodule at a malicious/broken remote) can make `configureWorktree` deterministically fail forever, which means `publishSymlink` is never reached, and the `--link` symlink is permanently frozen at the old hash while the sync loop keeps retrying/erroring on every period.

### Finding Description
`git-sync`'s documented contract is that the `--link` symlink update is the sole atomic publication point, and it is only flipped once fetch, worktree creation, and worktree configuration have all completed successfully [3](#0-2) . In `SyncRepo`, the order is: fetch → (if changed) `createWorktree` → `configureWorktree` → `beforePublish` hook → `publishSymlink` → `afterPublish` hook [1](#0-0) .

`configureWorktree` runs `git submodule update --init [--recursive] [--depth N]` unconditionally whenever submodules are not disabled (the default is `recursive`) [2](#0-1) , and also does a hard reset to the fetched hash [4](#0-3) . Any of these git subcommands can be made to fail (or hang until `--sync-timeout` expires) purely via content in the commit that was fetched — e.g. a `.gitmodules` entry pointing at an unreachable/invalid URL, a submodule commit that doesn't exist, or a sparse-checkout file interaction that git rejects. Because `configureWorktree` returns an error, `SyncRepo` returns before ever calling `publishSymlink`, so the "atomic" publish step described in the contract simply never runs — indefinitely, on every retry, since the loop refetches the same broken commit each period and gets the same failure [5](#0-4) .

This mirrors the Dutch-auction root cause exactly: a state machine has a designed "finalize" transition, but an earlier, attacker-influenced step is on the critical path to that transition and can be made to never succeed, so the finalize step is permanently starved. In Malt, that froze the price at a favorable point for the attacker; in `git-sync`, it freezes the published tree at the last-good commit, denying legitimate updates.

### Impact Explanation
The primary impact is **persistent sync denial**: consumers of the shared volume never receive new commits once the poisoning commit is fetched, with no operator-visible corruption (the old symlink target still resolves), which can mask the fact that updates have silently stopped. If `--max-failures` is reached, the process exits and is presumably restarted by the orchestrator (e.g., Kubernetes), re-fetching and re-failing on the same bad commit indefinitely — a crash-loop denial of service. This matches the accepted "persistent sync denial" impact category. There is no direct code execution or credential disclosure in this path, and no partial/corrupt content is *published* (since `publishSymlink` never runs) — the failure mode is availability, not integrity of what's already served.

### Likelihood Explanation
Likelihood depends entirely on the trust model: this only matters when `git-sync` follows a ref (branch/tag) written to by parties who should not have unilateral ability to freeze the sync (e.g., a monitored/shared branch, or a repo with submodules pointing to third-party sources outside the operator's control). Because `--submodules` defaults to `recursive`, any repo with submodules is exposed by default unless explicitly disabled. An attacker with commit/push access to the tracked ref, or control over a referenced submodule's remote, can trivially trigger this by committing a `.gitmodules` change with a broken/unreachable submodule URL — no special git-sync flags are required beyond the default submodule behavior. This is a real but narrower likelihood than a public-HTTP-triggered bug, since it requires push/commit access to content that ends up in the tracked history.

### Recommendation
1. Make submodule/worktree configuration failures distinguishable from transient/network failures, and consider decoupling "publish last known-good" from "must fully reconfigure worktree every sync" so a newly broken commit doesn't retroactively block re-publication of an already-valid state.
2. Add a circuit breaker/alerting path (metrics + `--error-file`, which already exists) that clearly flags "stuck on hash X for N consecutive failures" so operators can detect a frozen symlink instead of silently serving stale content.
3. Consider allowing `--submodules=off` guidance to be surfaced more prominently for use cases where submodule remotes are not fully trusted, and document that a stuck/broken submodule reference permanently blocks the atomic publish contract.

### Proof of Concept
Conceptual reproduction (matches the pattern in `test_e2e.sh`'s worktree/config tests):
1. Start `git-sync` with defaults (`--submodules` unset, i.e. `recursive`) tracking a branch.
2. Let it complete an initial successful sync (symlink published, hash `A`).
3. Push a new commit `B` to the tracked branch that adds a `.gitmodules` entry referencing a submodule URL that is unreachable (or a commit SHA that doesn't exist in that submodule).
4. Observe: `git.fetch` succeeds (fetches commit `B`), `createWorktree` succeeds, but `configureWorktree`'s `git submodule update --init ...` call fails every sync cycle [2](#0-1) .
5. `SyncRepo` returns an error before reaching `git.publishSymlink` [6](#0-5) ; the `--link` symlink remains pointed at worktree `A` forever, even though upstream has moved to `B` and beyond, until the offending commit/submodule reference is fixed or removed.
