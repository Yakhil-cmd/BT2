### Title
`StatusHandler#process` matches commits by `sha` alone, letting a status webhook for an attacker-controlled repository trigger `ContinuousDeliveryJob` on an unrelated victim stack sharing that sha - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no scoping to the repository/stack the webhook actually originated from. Because GitHub App webhook signatures are verified at the app level (not per-repository), any repository where the app is installed can deliver a `status` event whose `sha` happens to also exist as a `Commit` row on a completely different, higher-privilege stack, causing that victim commit to receive a new `Status`, which fires `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob.perform_later(stack)` for the victim stack.

### Finding Description
The broken binding is: **the repository/stack that authenticated and originated the webhook == the repository/stack whose `Commit` row is mutated and whose `ContinuousDeliveryJob` is scheduled**. This does not hold.

`StatusHandler#process` is: [1](#0-0) 
It queries `Commit.where(sha: params.sha)` across the entire `commits` table, with no `stack_id`/repository filter, and calls `commit.create_status_from_github!(params)` on every matching row regardless of which repository sent the webhook.

`create_status_from_github!` creates a `Status` record via `add_status`: [2](#0-1) 

`Status` has an `after_commit ... on: :create` callback that unconditionally calls back into the commit: [3](#0-2) 

`Commit#schedule_continuous_delivery` then evaluates `deployable?` (based on the commit's own aggregated status, now including the attacker-injected `success` status) and the **victim** stack's real `continuous_deployment?`/`deployable?` configuration, and enqueues `ContinuousDeliveryJob.perform_later(stack)` for the victim stack: [4](#0-3) 

Exploit flow: an attacker who has push/webhook-triggering rights on any repository the Shipit GitHub App is installed on (e.g., their own low-privilege repo/stack with `continuous_deployment?` disabled) can produce a commit whose sha is identical to a commit that also exists as a `Commit` row in a victim stack (trivial via forking or sharing git history with the victim repo, since a git sha is a hash of tree/parent/author/committer content and is portable across remotes). Pushing/updating a commit status (`state: success`) on the attacker's repo/commit generates a GitHub `status` webhook with that shared `sha`. This webhook is verified only via the app-wide webhook secret (not scoped per repository), and `StatusHandler#process` then applies the status update to **every** `Commit` row with that sha across all stacks — including the victim's — regardless of which repository actually sent it.

Existing guards fail to prevent this because: the webhook signature check authenticates that GitHub sent the payload for *some* installed repository, not that the payload's `sha` belongs to the repository that triggered it; `StatusHandler`'s `ExplicitParameters` schema only validates the shape of `sha`/`state`, not repository ownership; and `Commit#deployable?`/`schedule_continuous_delivery` only re-checks the (already-compromised) commit and the real, authorized `continuous_deployment?` setting of the resolved stack, which is precisely the victim stack in this scenario.

### Impact Explanation
This allows a payload originating from one (attacker's) repository to mutate another stack's `Commit`/`Status` records and trigger an unauthorized continuous deployment (`ContinuousDeliveryJob.perform_later(victim_stack)`) on a different tenant's stack that never emitted the corresponding webhook. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." The blast radius spans all stacks sharing the vulnerable `Commit.where(sha:)` lookup, i.e., any two stacks (regardless of tenant) whose commit histories intersect at a given sha.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository where the Shipit GitHub App/webhook is installed and to which they can push or otherwise trigger a real `status` event, and (b) a sha that collides with a `Commit` row belonging to the victim stack — realistically achievable by forking/mirroring the victim's repository (shared git history yields identical commit shas) or by two stacks legitimately tracking the same underlying repository (a very common Shipit setup, e.g. staging/production stacks for one repo). No Shipit secrets, sessions, or elevated roles are required; the only "cost" is causing GitHub to emit one legitimate `status` webhook event, which is trivial (e.g., posting a commit status via a CI integration the attacker controls on their own fork). This is repeatable per matching sha/stack pair.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers) to the repository that generated the webhook — e.g., resolve the target stack(s) via `Stack.where(repository: repository_from_payload)` before filtering by `sha`, rather than a global `Commit.where(sha: params.sha)`. Alternatively, verify `payload.repository.full_name` against `commit.stack.repository.full_name` before invoking `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook for one stack does not trigger continuous delivery on an unrelated stack sharing the sha" do
  attacker_stack = shipit_stacks(:shipit) # continuous_deployment? disabled
  victim_stack = shipit_stacks(:cyclimse) # continuous_deployment? enabled, deployable? true
  shared_sha = "a" * 40

  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)

  payload = { sha: shared_sha, state: "success", context: "ci" }

  ContinuousDeliveryJob.expects(:perform_later).with(victim_stack).never

  Shipit::Webhooks::Handlers::StatusHandler.new(...).call # simulate delivery attributed to attacker's repo

  # Assert binding: only attacker_stack (the authenticated origin) may be affected,
  # victim_stack's continuous_deployment? being true must not be reachable
  # via a webhook that never came from victim_stack's repository.
end
```
