Confirmed: `reset_session` is only called in `logout` and in the `requires_fresh_login?` branch of `force_github_authentication` — never in the OAuth `callback` action that establishes the authenticated session.### Title
Session Fixation via GitHub OAuth Callback Not Regenerating the Session - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
The bug-class from the external report (`updateCompartmentsReduceLiq` mutating balances without re-validating the invariant that should hold afterward) maps to a binding in shipit-engine between "the GitHub identity that completed OAuth" and "the `User` bound to the Rails `session`." The engine writes `session[:user_id]` on OAuth completion but never invalidates/rotates the pre-existing session, so an attacker-controlled session ID can be bound to a victim's account.

### Finding Description
`GithubAuthenticationController#callback` sets the authenticated identity directly into the existing session without first calling `reset_session`: [1](#0-0) 

Compare this to `logout`, and to the only other `reset_session` call site in the codebase, `Authentication#force_github_authentication`, which explicitly resets the session when a stale token is detected: [2](#0-1) 

The binding that should hold is: `session_id after login == a freshly minted session_id`, i.e. the pre-authentication session must not survive privilege escalation from `AnonymousUser` to a real `User`. Instead, `sign_in_github(auth)` only computes the id and assigns `session[:user_id] = sign_in_github(auth)` plus `session[:authenticated] = true`, reusing whatever session cookie the browser already presented: [3](#0-2) 

Because `Authentication#find_current_user` trusts `session[:user_id]` unconditionally for all subsequent requests (`stacks`, `repositories`, `api_clients`, deploy/rollback/task triggers, and the `/events` Pubsub stream mounted at the engine root), whoever controls that session ID after the victim authenticates gains the victim's authenticated identity: [4](#0-3) 

The OAuth callback route accepts `GET` (in addition to `POST`), which allows the flow to be driven/observed via ordinary navigation and origin redirection, making the fixation scenario practical to set up: [5](#0-4) 

### Impact Explanation
An attacker who can plant a session cookie in a victim's browser (e.g., via a subdomain, a response-splitting bug, or simply pre-setting a cookie for the Shipit host before the victim logs in) and then lure the victim into completing the GitHub OAuth login, ends up sharing the victim's authenticated session. Since `current_user`/`current_api_client`-independent session-based endpoints in this engine gate access to stack management, deploy/rollback/task triggering, API client creation, and repository administration, this is an authentication-bypass-class impact: the attacker obtains full access to the victim's Shipit account and its `Shipit.github_teams` authorization without ever presenting valid GitHub credentials themselves.

### Likelihood Explanation
Exploitation requires the standard session-fixation precondition (attacker able to fix/set a session cookie value in the victim's browser prior to login) plus getting the victim to complete an OAuth login while that cookie is active. No `webhook_secret`, `ApiClient` token, GitHub App private key, or privileged account is needed — only the ability to influence the victim's cookie jar and induce a login, which is the exact "session fixation / forced OAuth completion" class explicitly listed as an acceptable High-severity impact.

### Recommendation
Call `reset_session` at the start of `GithubAuthenticationController#callback`, before assigning `session[:user_id]`/`session[:authenticated]`, so a brand-new session ID is issued upon every successful authentication (mirroring the pattern already used in `logout` and in `force_github_authentication`'s stale-token branch).

### Proof of Concept
1. Attacker obtains/sets a fixed session cookie value for the Shipit host in the victim's browser (classic fixation precondition — e.g., cookie planted before any TLS-protected write, or via a cooperating subdomain).
2. Attacker sends the victim a link to `GET /github/auth/github?origin=...`, initiating GitHub OAuth using the fixed session.
3. Victim completes GitHub login; `GithubAuthenticationController#callback` runs `session[:user_id] = sign_in_github(auth)` on the *same* (attacker-known) session, without a `reset_session` call. [1](#0-0) 
4. Attacker reuses the fixed session cookie in their own browser and is now recognized as the victim by `Authentication#find_current_user`, gaining access to the victim's stacks, deploys, rollbacks, task triggers, and API client management under the victim's GitHub-team authorization.

```ruby
    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
```

```ruby
      user = User.find_or_create_from_github(auth.extra.raw_info)
      user.update(github_access_token: auth.credentials.token)
      user.id
    end
```
