### Title
Cross-organization webhook forgery: signature verified against `repository.owner.login`/`organization.login` while the write target is selected from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments (`secrets.github` keyed by organization, see `Shipit.github_organizations`/`Shipit.github_app_config`), `WebhooksController#verify_signature` selects which organization's `GitHubApp` (and therefore which `webhook_secret`) is used to validate the inbound HMAC using a field (`repository_owner`) that is completely decoupled from the field the handlers later use to decide which `Repository`/`Stack` is written to (`repository.full_name`). This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` resolves the signing app purely from the payload: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`verify_webhook_signature` on `GitHubApp` returns `true` unconditionally if that organization has no `webhook_secret` configured: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Meanwhile, the actual event handlers (`PushHandler`, all `PullRequest::*Handler`s) determine which `Repository`/`Stack` to mutate purely from `payload.dig('repository', 'full_name')`: [4](#0-3) [5](#0-4) [6](#0-5) 

`repository_owner` (used only for choosing the signing key) and `repository.full_name` (used to select the actual `Repository`/`Stack` acted upon) are two entirely independent JSON fields in the same attacker-controlled request body - the signature never covers "the org whose key I used matches the org that owns the repository I'm about to write to." An HMAC signed with organization A's secret still validates a payload whose `repository.full_name` targets organization B's repository, as long as `repository.owner.login`/`organization.login` is set to A. This is the exact analog of the reported bug class: a field consumed downstream (`packetId` used in `addPacketsToInventory`) that was never covered by the value actually validated (the zeroed array) — here, the org identity that is cryptographically checked is not the org identity that is subsequently trusted to authorize the write.

In the common single-org deployment this is latent (`repository_owner` and `full_name`'s owner segment always match in legitimate traffic, and there is only one key). It becomes concretely exploitable in multi-tenant deployments explicitly supported by the codebase (`secrets.github` keyed per-organization, cf. fixture `test/dummy/config/secrets_double_github_app.yml` showing `OrgOne`/`OrgTwo` each with independent, potentially-blank `webhook_secret`). Any organization onboarded with `webhook_secret: nil` (a supported, non-error configuration per `verify_webhook_signature`'s early return) becomes a skeleton key: an attacker sets `repository.owner.login` to that org (bypassing signature checking entirely) and `repository.full_name` to a repository belonging to a *different*, fully-secured organization, causing Shipit to sync/mutate that stack (`stack.sync_github`, `ReviewStackAdapter#find_or_create!`, `stack.archive!`/`unarchive!`) with no valid signature for the targeted org at all.

### Impact Explanation
This crosses a credential/authentication boundary: state-changing webhook actions (triggering GitHub sync jobs that fetch/deploy from a specific SHA, opening/archiving review stacks, updating pull request state) are performed against a target repository selected independently of whichever organization's key was actually used to authenticate the request. In a multi-organization install this is a cross-tenant forgery of GitHub webhook authority, letting an unprivileged external attacker (no Shipit session, no `ApiClient` token, no knowledge of the targeted org's `webhook_secret`) trigger actions against another organization's stacks by exploiting a laxer-configured organization's endpoint. This maps to the "escalation into authorization" / unauthorized-action class of High-impact findings.

### Likelihood Explanation
Requires the operator to run Shipit with multiple `github` organizations configured (a documented, supported configuration) where at least one organization omits `webhook_secret` (also an explicitly supported/non-error state, verified by the `return true unless webhook_secret` early exit and the double-app test fixture). Given that precondition, exploitation requires only a single unauthenticated POST to `/webhooks` with a crafted JSON body — no secrets, tokens, or sessions needed.

### Recommendation
Bind the two identities before acting: after resolving `github_app` from `repository_owner`, verify that the owner segment of `payload.dig('repository', 'full_name')` matches `repository_owner` (case-insensitively) before dispatching to any handler; reject (422) on mismatch. Additionally, treat a missing `webhook_secret` for a configured organization as a hard configuration error rather than an implicit signature bypass, or require an explicit `disable_webhook_verification` flag instead of silently trusting unsigned payloads.

### Proof of Concept
Given a Shipit instance configured with two organizations, `OrgOne` (no `webhook_secret`) and `OrgTwo` (has stacks and a `webhook_secret`):

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   # irrelevant, OrgOne has no secret
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": {"login": "OrgOne"},
    "full_name": "OrgTwo/protected-repo"
  }
}
```

`verify_signature` resolves `github_app = Shipit.github(organization: "OrgOne")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of the (fabricated) `X-Hub-Signature`. `PushHandler#process` then resolves `stacks` from `payload.dig('repository','full_name')` = `"OrgTwo/protected-repo"` and enqueues `stack.sync_github(expected_head_sha: params.after)` against `OrgTwo`'s stack — with no valid signature ever produced for `OrgTwo`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
