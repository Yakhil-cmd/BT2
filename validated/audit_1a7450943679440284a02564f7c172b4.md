### Title
Webhook signature is verified against the payload's claimed organization, but the write target (repository/commit/stack) is resolved from a different, unverified payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *unauthenticated* JSON body, before the signature has been checked. The handlers that actually persist data (e.g. `PushHandler`, `StatusHandler`) resolve the target `Repository`/`Stack`/`Commit` using a *different* payload field, `repository.full_name`. In a multi-organization Shipit installation these two fields are never cross-checked, so the organization whose key authenticates the request is not bound to the repository whose data gets written.

### Finding Description
`verify_signature` picks the GitHub App config to check the signature against using only attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up the per-organization config (`app_id`, `webhook_secret`, etc.) by downcasing this attacker-supplied string and indexing into `secrets.github`: [3](#0-2) 

Signature verification is a no-op whenever that organization's `webhook_secret` is blank/unset (a legitimate configuration for some orgs, e.g. `webhook_secret: null` shown for `OrgTwo` in the dummy multi-app secrets fixture): [4](#0-3) [5](#0-4) 

Once `head(422)` isn't triggered, `WebhooksController#create` dispatches the entire raw payload — including the `repository.full_name` field — to the registered handlers: [6](#0-5) 

But every handler resolves the *actual write target* (which `Repository`/`Stack`/`Commit` gets mutated) from `repository.full_name`, a completely separate field from the one used for signature/org selection: [7](#0-6) 

Nothing in `Handler#stacks`/`Handler#repository_name`, nor in `WebhooksController#verify_signature`, checks that `repository.owner.login` (used to pick the signing org) matches the owner encoded in `repository.full_name` (used to pick the write target). In a single-organization deployment these two are always the same object from GitHub's perspective, so the gap is invisible. In a multi-organization deployment (the schema explicitly supported by `Shipit.github_organizations` / `github_app_config`), an attacker who only knows or controls the (possibly unset) webhook secret for one configured organization can forge:
```json
{ "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/protected-repo" }, "sha": "<real sha in OrgOne stack>", "state": "success", "context": "required-ci-check" }
```
`verify_signature` authenticates this as a legitimate `OrgTwo` webhook (using `OrgTwo`'s secret, which may be blank), while the `status` handler writes a commit status onto a commit that belongs to `OrgOne/protected-repo`'s stack, as confirmed by the existing status-handler test which creates `Status` records purely from the payload's `sha`/`state`/`context`/`repository` fields: [8](#0-7) 

This is the equality break called out in scope: "an organization that authenticated versus the repository that is written."

### Impact Explanation
Commit statuses gate the merge queue (`ci.require`) and continuous deployment eligibility. Forging a `success` status for a required CI context on an arbitrary commit in a different organization's stack — while authenticating under an org boundary that was never meant to cover that repository — can push a commit into a deployable/mergeable state it should never have reached, i.e. an unauthorized deploy/merge, one of the explicitly accepted High/Critical impacts. The `push` handler is equally affected: `GithubSyncJob` is enqueued with an attacker-chosen `expected_head_sha` for `OrgOne`'s stack even though the signature was validated only against `OrgTwo`'s secret.

### Likelihood Explanation
Requires a Shipit instance configured with more than one GitHub organization (a documented, supported configuration — see `github_app_config`/`secrets_double_github_app.yml`) where at least one configured organization has no `webhook_secret` (also a documented, explicitly supported state, since `verify_webhook_signature` returns `true` when blank) or whose secret the attacker otherwise knows. No session, API token, or repository write access is needed — only the ability to send an unauthenticated HTTP POST to the public webhooks endpoint, matching the "unprivileged attacker" scope.

### Recommendation
After verifying the signature, re-derive the organization strictly from `repository.full_name`'s owner segment (or vice versa) and reject the request (`422`) if it disagrees with `repository.owner.login`/`organization.login` used for the signature check. Alternatively, verify the payload against the webhook secret of the organization that actually owns `repository.full_name`, never the organization named in a different, less-trusted field of the same unauthenticated body.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` (has a repo/stack with `ci.require: ["required-ci-check"]`) and `OrgTwo` (`webhook_secret: null`, per the supported multi-org schema).
2. POST to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/protected-repo" },
  "sha": "<real head sha of an undeployed commit in OrgOne/protected-repo>",
  "state": "success",
  "context": "required-ci-check",
  "target_url": "https://attacker.example/fake",
  "description": "forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```
No `X-Hub-Signature` (or any signature, since `OrgTwo` has no secret) is required for `verify_signature` to pass, per `verify_webhook_signature`'s early `return true unless webhook_secret`.
3. `WebhooksController#create` dispatches to `Handlers::StatusHandler`, which resolves the target `Commit` via `Repository.from_github_repo_name("OrgOne/protected-repo")` and records the forged `success` status, potentially satisfying `OrgOne`'s merge-queue/CD required-status check for a commit the attacker never had write access to.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
