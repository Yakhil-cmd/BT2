### Title
Unauthenticated GitHub webhook forgery when an organization's `webhook_secret` is unset bypasses signature verification and escalates into `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`, `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
The reported bug class is a broken trust binding: a value used to authorize an action (`block.number` as a timing proxy) is not actually backed by the guarantee the code assumes (accurate, monotonic time on Optimism). The equivalent binding in this engine is: *"the organization whose secret is used to verify a webhook signature" == "the organization whose payload data is trusted and acted upon."* This binding breaks whenever a configured GitHub organization has no `webhook_secret` set, because `GitHubApp#verify_webhook_signature` then trivially returns `true` regardless of the actual (or absent, or forged) signature, letting an unauthenticated actor's payload be processed as if it were verified.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` instance to use for verification based on an attacker-controlled field of the JSON payload (`repository.owner.login` / `organization.login`): [1](#0-0) [2](#0-1) 

That `GitHubApp` object's `verify_webhook_signature` method has this early return: [3](#0-2) 

`return true unless webhook_secret` — if the organization resolved from the attacker-supplied `repository_owner`/`organization.login` field has no `webhook_secret` configured, **any** payload is accepted as "verified," independent of the actual `X-Hub-Signature` header contents.

This is not a hypothetical: the engine's own multi-organization test fixture explicitly configures two organizations with `webhook_secret: # nil`: [4](#0-3) [5](#0-4) 

and the setup docs describe the webhook secret as merely "optional": [6](#0-5) 

Once past `verify_signature`, `WebhooksController#create` parses the raw body again and dispatches it, unauthenticated except for the signature check, to all registered handlers: [7](#0-6) 

One of the built-in handlers, `MembershipHandler`, creates/looks up a `Team` by attacker-supplied `team.id`/`organization.login`, and adds or removes an arbitrary `member.login` from that team purely from payload fields, with no cross-check against GitHub's actual team membership: [8](#0-7) [9](#0-8) 

`Team.add_member` / `Team#members` persists this in the local `Membership` table: [10](#0-9) 

Shipit's own controller-level authorization gate (used by `RepositoriesController` and others) checks membership in `Shipit.github_teams`, which resolves to these same locally-synced `Team`/`Membership` records rather than a live GitHub API call at request time: [11](#0-10) 

### Impact Explanation
For any organization configured without a `webhook_secret` (an explicitly supported, documented, and test-fixtured configuration), an unauthenticated network attacker can:
1. POST a forged `membership` webhook naming that organization, a `Shipit.github_teams`-authorized team, and their own GitHub login as `member.login` with `action: "added"`.
2. Because `verify_webhook_signature` returns `true` unconditionally for that organization, the forged event is processed exactly as a legitimate GitHub-originated one.
3. `MembershipHandler` creates the `Membership` row, and the attacker's GitHub identity is now recognized by Shipit's own authorization checks as belonging to an authorized team — enabling them to authenticate into Shipit (via the standard GitHub OAuth login flow, since they only need to *be a member of an authorized team*, which is now true in Shipit's database) and gain access to protected functionality: viewing stacks, triggering deploys/rollbacks, and viewing task output/streams.

This matches the "High" impact bucket: escalation into `Shipit.github_teams` authorization via a webhook signature-verification bypass, achievable by an unprivileged, unauthenticated external attacker — no session, API token, or webhook secret knowledge required (the attack specifically exploits the *absence* of a secret, not knowledge of one).

### Likelihood Explanation
Likelihood is conditioned on deployment configuration: it requires at least one configured GitHub organization/app with a blank `webhook_secret`. This is not a hardening failure that requires ignoring documentation — the setup guide itself describes the webhook secret as "(optional)", and the engine's own test suite (`secrets_double_github_app.yml`) ships and exercises exactly this configuration. Any Shipit operator who follows the documented "optional" guidance and skips setting a webhook secret for one or more organizations is silently exposed to full unauthenticated webhook forgery for that organization, with no warning anywhere in the code or docs that omitting the secret disables signature verification (as opposed to, say, being rejected or requiring an explicit "insecure" opt-in flag).

### Recommendation
- Do not treat a blank `webhook_secret` as "skip verification, allow everything." Either: (a) require a `webhook_secret` to be configured for every organization at boot/config-validation time, or (b) if unset, reject all incoming webhooks for that organization (fail closed) rather than accepting them unconditionally.
- Update `docs/setup.md` to state clearly that omitting the webhook secret disables authenticity checking entirely, not just that it is "optional".
- In `MembershipHandler` (and other trust-sensitive handlers such as those touching `Team`/`Membership`), consider requiring a live GitHub API confirmation of membership rather than trusting webhook payload contents outright, especially since these records feed directly into `Shipit.github_teams` authorization decisions.

### Proof of Concept
Given a Shipit deployment configured with an organization `acme` that has no `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), and where `Shipit.github_teams` includes `acme/deployers`:

```
POST /webhooks HTTP/1.1
X-Github-Event: membership
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   (arbitrary/garbage, never validated)
Content-Type: application/json

{
  "action": "added",
  "team": {"id": 1, "name": "deployers", "slug": "deployers", "url": "https://api.github.com/teams/1"},
  "organization": {"login": "acme"},
  "member": {"login": "attacker-controlled-github-login"}
}
```

`verify_signature` resolves `repository_owner` = `"acme"` → `Shipit.github(organization: "acme")` → `verify_webhook_signature` returns `true` because `webhook_secret` is blank for `acme` (see `lib/shipit/github_app.rb:76-77`). `MembershipHandler#process` then creates/finds `Team` `acme/deployers` and appends `attacker-controlled-github-login` as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`, `app/models/shipit/team.rb:41-43`). The attacker then logs into Shipit via the normal GitHub OAuth flow using that GitHub account and is now recognized as a member of an authorized team, bypassing the intended `Shipit.github_teams` gate.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
