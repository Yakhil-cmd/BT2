### Title
Unhandled exception in merkle-proof authentifier deserialization causes node crash / validation halt - (File: definition.js)

### Summary
`validateAuthentifiers()`'s `'in merkle'` branch deserializes an attacker-supplied authentifier string via `merkle.deserializeMerkleProof(serialized_proof)` with no error handling, unlike the sibling `is_valid_merkle_proof` oscript function which explicitly wraps proof verification in `try/catch`.

### Finding Description
When an address definition contains an `'in merkle'` condition, the authentifier value supplied by the unit's author (`assocAuthentifiers[path]`) is passed directly to `merkle.deserializeMerkleProof()`: [1](#0-0) 

`deserializeMerkleProof` naively splits the string on `-` and uses `arr.pop()`/`arr.shift()`: [2](#0-1) 

The resulting `proof` object is passed to `merkle.verifyMerkleProof()`, which is itself defensively wrapped in try/catch and returns `false` on any internal exception: [3](#0-2) 

The problem is upstream of `verifyMerkleProof`: `deserializeMerkleProof` performs no length/format validation, so a specially crafted `serialized_proof` string can produce a `proof` object whose fields have unexpected types (e.g., `proof.index` as a non-numeric string, or `proof.siblings` containing non-string/garbage tokens from a string with an unusual number of `-`-separated fragments — analogous to the "stray element" mis-structuring in the WDDX bug that corrupted the parser's internal pop/stack bookkeeping). Because there is no try/catch around the `deserializeMerkleProof()` call itself in `definition.js` (only around the downstream `verifyMerkleProof` call in the oscript formula evaluator, not here), any exception thrown while constructing or later consuming this malformed proof object inside `validateAuthentifiers` (e.g., when it flows into `dataFeeds.dataFeedExists(...)` using `proof.root` which may be `undefined`/malformed) propagates as an uncaught exception in unit-validation code executed for every node when validating a normal signed unit's authentifiers.

### Impact Explanation
`validateAuthentifiers` runs during core unit validation (signature/authentifier checking), a hot path reachable by any unprivileged unit poster whose address (or any address definition referencing `'in merkle'`) is validated by every full node. An uncaught exception thrown from this deep, synchronous-style callback chain is not guaranteed to be caught by the outer validation error handlers (contrast with `is_valid_merkle_proof` in `formula/evaluation.js`, which explicitly wraps the analogous call), which can crash the node process or leave validation state inconsistent — a network-wide denial-of-service / inability-to-confirm-units risk, matching the CVE-2016-7132 bug class (malformed serialized structure mishandled by pop-based reconstruction logic, leading to a crash/DoS via unexpected null/undefined values).

### Likelihood Explanation
Exploitability requires a live address definition (already established, e.g., a shared address or AA-adjacent multi-sig definition) that includes an `'in merkle'` clause, and for that path to be present in `assocAuthentifiers` when the corresponding branch's authentifier field is supplied. This is a legitimate, documented oscript definition feature reachable by any user who sets up such an address; the attacker fully controls the string passed as the authentifier for that path since it comes straight from the posted unit's `authors[].authentifiers`.

### Recommendation
Wrap the `merkle.deserializeMerkleProof(serialized_proof)` call in `definition.js`'s `'in merkle'` branch (and ideally strengthen `deserializeMerkleProof` itself) in a try/catch and validate the parsed proof's shape (types/lengths of `root`, `index`, `siblings`) before use, mirroring the defensive handling already present for `is_valid_merkle_proof` in `formula/evaluation.js`.

### Proof of Concept
1. Create/use an address whose definition includes an `'in merkle'` condition at some `path`.
2. Post a unit authored by that address where `authors[].authentifiers[path]` is set to a malformed string designed to produce an inconsistent `proof` object from `deserializeMerkleProof` (e.g., a string with unusual `-` placement causing `proof.root`/`proof.index` to be `undefined` or non-string), such that downstream consumption of `proof.root` (e.g., in `dataFeeds.dataFeedExists`) throws.
3. Submit the unit to a full node for validation; observe the uncaught exception during `validateAuthentifiers`.

Note: I was unable to fully trace every downstream consumer of `proof.root`/`proof.siblings` inside `dataFeeds.dataFeedExists` and its SQL parameter binding to confirm a guaranteed unhandled-exception path versus a benign "not found" result in all code paths — this could reduce the finding to a lower-severity issue if that function tolerates malformed inputs gracefully. This uncertainty should be verified by a maintainer/Devin session with full file access.

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
