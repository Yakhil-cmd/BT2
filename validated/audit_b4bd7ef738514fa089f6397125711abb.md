### Title
Unbounded `unhandled_private_payments` storage via unlimited fake private-payment chains from a private-payment counterparty - (File: network.js)

### Summary
`handleOnlinePrivatePayment()` in `network.js` accepts private-payment chains from a peer/private-payment counterparty and unconditionally persists the entire JSON-serialized chain into the `unhandled_private_payments` table with only minimal structural checks (`unit` hash length, `message_index`/`output_index` non-negativity), before any real validation of the payment chain, amounts, or ownership occurs.

### Finding Description
`handleOnlinePrivatePayment` validates only that `arrPrivateElements` is a non-empty array and that `unit`, `message_index`, `output_index` on the head element have the right type/format: [1](#0-0) 

If the unit referenced by the chain is not yet known (`ifNew`/`ifKnownUnverified`), or if it's a light client receiving a multi-element chain, the code unconditionally calls `savePrivatePayment`, which inserts the full JSON-stringified `arrPrivateElements` array into the `unhandled_private_payments` table, with no cap on the number of elements in the chain, no cap on the size of each element's payload, and no fee/commission or proof-of-work requirement: [2](#0-1) [3](#0-2) 

The only real content-shape validation before persistence happens in `handlePrivatePaymentChains` (device/wallet path) which merely checks that fields are non-empty objects/strings/arrays — it does not bound array sizes, string lengths, or the number of chains/elements: [4](#0-3) 

Unlike ordinary units, which must pay `headers_commission`/`payload_commission` sized to their serialized length before being accepted onto the DAG (`validation.js`), private-payment JSON blobs queued in `unhandled_private_payments` are stored speculatively, prior to and independent of that unit ever being validated or paid for, and can reference a `unit` value that never actually gets posted (the row simply lingers keyed by `unit`). Because `INSERT ... IGNORE` is keyed on `(unit, message_index, output_index)`, an attacker who is a legitimate private-payment counterparty (or device peer) can generate unlimited distinct fake `unit` hashes (which pass `isValidBase64` format checks without needing to be real, previously-broadcast units) each paired with an arbitrarily large `arrPrivateElements` JSON array (long chains, large payload objects, big blinding strings, etc.), and have the node store each as a new row with no rate limit, no total-size limit, and no cost — repeatedly, forever, exhausting local database/disk resources. This is the direct analog of the Discourse draft-key issue: unauthenticated/low-cost creation of unlimited server-side records keyed by attacker-controlled, unbounded-length data.

### Impact Explanation
An attacker acting as a private-payment counterparty or paired device can flood a victim node's `unhandled_private_payments` table with unlimited large records, exhausting disk/DB storage and degrading node performance (background processing via `handleSavedPrivatePayments` re-reads and re-JSON-parses all pending rows repeatedly). This can render the targeted node unable to process legitimate private payments and can more broadly degrade node availability, which the rules classify as "a network unable to confirm new units" for the affected node, or at minimum a Medium-severity resource exhaustion condition directly analogous to the referenced Discourse advisory.

### Likelihood Explanation
Likelihood is Medium/High for the specific target because no signature, payment, or proof-of-work is required to hit this path — only structural type validity for `unit`/`message_index`/`output_index`, both of which are trivial to construct programmatically. It can be triggered by any device paired with the victim's wallet or by a peer that has previously exchanged the "private_payment" justsaying with the victim (or by a light client's own hub relaying `private_payments` messages), consistent with the "private-payment counterparty or paired device" reachable actor allowed by this scan's scope.

### Recommendation
Add hard limits on: (1) the maximum number of elements per `arrPrivateElements` chain, (2) the maximum serialized JSON size stored in `unhandled_private_payments`, and (3) the maximum number of pending unhandled private-payment rows per peer/device-address, with periodic purging of stale/unverifiable entries (similar to `TEMP_DATA_PURGE_TIMEOUT` for temp_data). Reject oversized or excessive chains before the `INSERT` in `savePrivatePayment`, mirroring the size/commission-based anti-spam checks already applied to on-DAG units in `validation.js`/`object_length.js`.

### Proof of Concept
1. As a paired device or private-payment counterparty, repeatedly send `private_payments` messages (or `private_payment` justsaying messages) to the victim node, each with a freshly generated random 44-byte base64 `unit` string (need not correspond to a real unit) and an `arrPrivateElements` array containing many chain elements with large `payload.outputs`/`inputs` arrays and long `blinding` strings.
2. Because `handleOnlinePrivatePayment`/`handlePrivatePaymentChains` only check structural validity (`isValidBase64`, `isNonnegativeInteger`, non-empty arrays/objects) and never bound total size or count, each message results in a new row inserted into `unhandled_private_payments` via `savePrivatePayment` (network.js:2390-2401).
3. Repeat with new random `unit` values indefinitely (the `INSERT ... IGNORE` dedup key is `(unit, message_index, output_index)`, so each new fake `unit` bypasses deduplication) to grow the table without bound, consuming disk space and slowing down `handleSavedPrivatePayments`'s periodic full-table scan.

function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
		return callbacks.ifError("malformed private chain");
