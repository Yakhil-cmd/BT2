### Title
Missing Zero-Address Validation for `_to` in Bridge Transfer Functions Enables Permanent KLAY Burn — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`requestKLAYTransfer` and `handleKLAYTransfer` in `BridgeTransferKLAY.sol` accept a user-supplied `_to` address with no `require(_to != address(0))` guard. An unprivileged user who passes `address(0)` as the recipient causes the bridge to lock their KLAY on the source chain, consume the request nonce, and then irrecoverably send the KLAY to `address(0)` on the destination chain via a low-level call that succeeds silently.

---

### Finding Description

`requestKLAYTransfer` forwards the caller-supplied `_to` directly into `_requestKLAYTransfer` without any zero-address check:

```solidity
// BridgeTransferKLAY.sol line 132-135
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);   // _to unchecked
}
```

`_requestKLAYTransfer` emits `RequestValueTransfer` with `_to = address(0)` and increments `requestNonce`:

```solidity
// BridgeTransferKLAY.sol line 103-124
function _requestKLAYTransfer(address _to, uint256 _feeLimit, bytes memory _extraData)
    internal unlockedKLAY nonReentrant
{
    require(isRunning, "stopped bridge");
    require(msg.value > _feeLimit, "insufficient amount");
    uint256 fee = _payKLAYFeeAndRefundChange(_feeLimit);
    emit RequestValueTransfer(TokenType.KLAY, msg.sender, _to, address(0),
        msg.value.sub(_feeLimit), requestNonce, fee, _extraData);
    requestNonce++;
}
```

Bridge operators observe the event and call `handleKLAYTransfer` on the destination chain, also without a zero-address check on `_to`:

```solidity
// BridgeTransferKLAY.sol line 62-100
function handleKLAYTransfer(
    bytes32 _requestTxHash, address _from, address payable _to,
    uint256 _value, uint64 _requestedNonce, uint64 _requestedBlockNumber,
    bytes memory _extraData
) public onlyOperators nonReentrant {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }
    _setHandledRequestTxHash(_requestTxHash);
    handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
    _updateHandleNonce(_requestedNonce);
    emit HandleValueTransfer(...);
    (bool ok, ) = _to.call.value(_value)("");          // _to = address(0), succeeds
    require(ok, "handleKLAYTransfer: transfer failed");
}
```

In Solidity 0.5.6 on Kaia's EVM, `address(0).call.value(_value)("")` returns `(true, "")` — the call succeeds and the KLAY is sent to the zero address, permanently burning it. The handle nonce is consumed and the request tx hash is marked handled, so the transfer cannot be retried.

The same missing check exists in `requestERC20Transfer` and `requestERC721Transfer` in `BridgeTransferERC20.sol` and `BridgeTransferERC721.sol`, though the destination-chain impact there may be partially mitigated by the token contracts' own zero-address guards (ERC20 `_mint` and ERC721 `transferFrom` both revert on `address(0)`). However, in `modeMintBurn = false` mode for ERC20, `safeTransfer` to `address(0)` may succeed depending on the token implementation, and the source-chain tokens are already locked in the bridge regardless.

---

### Impact Explanation

- **Unauthorized burn of bridged KLAY**: Any user who accidentally (or deliberately) passes `address(0)` as `_to` in `requestKLAYTransfer` will have their KLAY permanently destroyed on the destination chain.
- **Nonce consumed**: The request nonce is incremented on the source chain and the handle nonce is consumed on the destination chain, making recovery impossible — the transfer cannot be replayed.
- **No recovery path**: The bridge contract has no mechanism to refund or re-route a handled transfer.

---

### Likelihood Explanation

- The trigger is a single unprivileged call to `requestKLAYTransfer(address(0), ...)` — no special role required.
- Accidental zero-address submission is a realistic user error (e.g., uninitialized variable, copy-paste mistake, frontend bug).
- The bridge is a production service-chain component actively used for cross-chain KLAY transfers.

---

### Recommendation

Add a zero-address guard in `_requestKLAYTransfer` (covers both the fallback and `requestKLAYTransfer` entry points) and in `handleKLAYTransfer`:

```solidity
// In _requestKLAYTransfer:
require(_to != address(0), "zero recipient");

// In handleKLAYTransfer:
require(_to != address(0), "zero recipient");
```

Apply the same guard to `_requestERC20Transfer`, `requestERC20Transfer`, `handleERC20Transfer`, `_requestERC721Transfer`, `requestERC721Transfer`, and `handleERC721Transfer`.

---

### Proof of Concept

1. Deploy `Bridge` on source chain (child chain) and destination chain (parent chain) with operators configured.
2. Call on source chain:
   ```solidity
   bridge.requestKLAYTransfer{value: 1 ether}(address(0), 1 ether, "");
   ```
   — succeeds; emits `RequestValueTransfer` with `_to = address(0)`; `requestNonce` increments.
3. Operator observes event and calls on destination chain:
   ```solidity
   bridge.handleKLAYTransfer(txHash, sender, address(0), 1 ether, 0, blockNum, "");
   ```
   — `address(0).call.value(1 ether)("")` returns `(true, "")`; handle nonce consumed; 1 KLAY burned.
4. Verify: destination chain `address(0)` balance increased by 1 KLAY; source chain bridge balance decreased; nonce permanently consumed; no refund possible. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
