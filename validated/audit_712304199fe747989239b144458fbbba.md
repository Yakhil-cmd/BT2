### Title
Uncaught type-assumption exceptions in oscript formula evaluation can crash AA trigger processing - (File: formula/evaluation.js)

### Summary
The `safeName()` bug is a class of vulnerability where code assumes an external/untrusted value will always have a specific type, and throws an uncaught exception when that assumption is violated by attacker-supplied data. In `ocore`, the `evaluate()` function in `formula/evaluation.js`, which executes oscript/AA formulas driven directly by attacker-controlled trigger data (`trigger.data`), contains multiple `throw Error(...)` statements guarding "impossible" type states (e.g. `toOscriptType`, `toJsType`, and the `substring` opcode's start/length handling) that are not wrapped in the same `setFatalError`/`fatal_error` soft-failure mechanism used elsewhere in the same file.

### Finding Description
Most type-mismatch branches in `evaluate()` are defensively handled via `setFatalError(...)`, which sets a `fatal_error` flag and returns `false` through the callback chain rather than throwing — this is the "safe" pattern used for bounding AA/oscript execution failures without crashing the node process, analogous to what BoringCrypto's `safeName()` does for token metadata. However, several code paths instead use raw `throw Error(...)`:

- `toOscriptType(x)` / `toJsType(x)` in `formula/evaluation.js:3235-3255` throw `Error("unknown type in toOscriptType:" + x)` / `"unknown type in toJsType:" + x` when converting AA state variables or trigger-derived values between JS and oscript representations. [1](#0-0) 
- The `substring` opcode throws `Error("unknown type of start in substring: " + start)` and `Error("unknown type of length in substring: " + length)` if the evaluated sub-expression resolves to a type the code doesn't expect. [2](#0-1) 
- `json_parse` also has a final `throw Error("unknown type of json parse: " + (typeof json))` fallback after all typical JSON result types (`object`, `number`, `string`, `boolean`) are checked. [3](#0-2) 

These functions operate on values built from `wrappedObject`, `Decimal`, and primitive JS types that originate from AA trigger `data` payloads (attacker-controlled, since anyone can post a unit with a `data` message addressed to an AA) or from state variables that another (possibly malicious) AA response wrote. Because oscript is a dynamically-typed intermediate representation with many possible value shapes (numbers, decimals, booleans, strings, wrapped objects, arrays), an attacker who can craft a formula/trigger combination that reaches one of these "impossible" branches with an unexpected shape (e.g., a `NaN`/non-finite `Decimal`, `undefined`, or `null` slipping through prior checks) triggers a raw JS exception instead of a contained `setFatalError`.

### Impact Explanation
Unlike Solidity, where an unhandled revert in `name()` only breaks that specific ERC20 call, an uncaught JavaScript exception thrown synchronously inside `evaluate()`'s callback chain during AA trigger processing is not guaranteed to be caught by a `try/catch` at every call site, particularly because `evaluate()` is deeply asynchronous (nested callbacks via `async`, DB queries, etc.) — a `throw` from inside an async callback frequently escapes any enclosing `try/catch` set up by the caller and becomes an uncaught exception at the process level. If it occurs during full-node AA trigger execution (not response evaluation/dry run), this can crash the node process or leave the AA/unit processing pipeline in an inconsistent state, since node.js does not automatically resume execution after an uncaught exception in an async callback. This maps to "network unable to confirm new units" if it propagates to full node core validation/AA-execution workers, since AA execution is mandatory, deterministic, and consensus-critical: all full nodes must execute the same AA trigger and reach the same state, and a crash prevents that node from continuing to process the DAG.

### Likelihood Explanation
Reaching these specific `throw` branches requires crafting an oscript formula/trigger combination where prior type-narrowing logic (`Decimal.isDecimal`, `typeof === 'boolean'`, `instanceof wrappedObject`) fails to fully classify a value before it reaches the `else throw` fallback. This requires deep knowledge of the oscript type coercion internals and likely fuzzing/testing of formula edge cases (e.g., combining `json_parse`, arithmetic producing non-finite `Decimal`s, or nested wrapped-object results) to find an input for which none of the `if` branches match. This is a plausible but non-trivial attack surface, consistent with a Medium severity finding — it is a defensive-programming gap of the same class as the reported `safeName()` issue, but exploitability depends on finding a concrete state-value combination that evades all prior branch checks.

### Recommendation
Replace the raw `throw Error(...)` statements in `toOscriptType`, `toJsType`, the `substring` opcode's start/length type checks, and the `json_parse` fallback with the same `setFatalError(...)` pattern used throughout the rest of `evaluate()`, so that any unexpected/unclassified value type results in a bounded formula-evaluation failure (returning `false`/rejecting the trigger) instead of an uncaught JS exception that can propagate out of the async evaluation chain and destabilize node processing.

### Proof of Concept
Concrete exploitation requires identifying a specific AA formula + trigger `data`/state-variable combination that produces a value not matching any `typeof`/`instanceof`/`Decimal.isDecimal` check in `toOscriptType`/`toJsType` or the `substring` start/length branches — for example, a `Decimal` NaN or a `Symbol`/`function`-typed value slipping through a chain of `evaluate()` calls before being converted at `formula/evaluation.js:3235-3255` or `formula/evaluation.js:2077-2106`. Full verification of a triggering input would require running the formula evaluator (`test/formula.test.js` harness) against candidate expressions to confirm an uncaught throw actually escapes the async callback chain rather than being caught by an outer handler in `aa_composer.js`; this could not be fully confirmed with static/indexed inspection alone. function toOscriptType(x) {
	if (typeof x === 'string' || typeof x === 'boolean' || x instanceof wrappedObject)
		return x;
	if (typeof x === 'number')
		return createDecimal(x);
	if (Decimal.isDecimal(x))
		return toDoubleRange(x);
	if (typeof x === 'object' && x !== null)
		return new wrappedObject(x);
	throw Error("unknown type in toOscriptType:" + x);
}

function toJsType(x) {
	if (x instanceof wrappedObject)
		return x.obj;
	if (Decimal.isDecimal(x))
		return x.toNumber();
	if (typeof x === 'string' || typeof x === 'boolean' || typeof x === 'number' || (typeof x === 'object' && x !== null))
		return x;
	throw Error("unknown type in toJsType:" + x);
}
