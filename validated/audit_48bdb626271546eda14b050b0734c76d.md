## Title
Ed25519 precompile accepts zero-signature "quorum" as valid, letting an attacker craft a spoofed sig-verify instruction with no actual signatures — ([File: precompiles/src/ed25519.rs])

### Summary
The `ChainlinkAtlasWrapper`/`ChainlinkDAppControl` bug is a missing quorum check that lets `transmit()` succeed with an empty signer array, breaking a downstream consumer's trust assumption that "verification succeeded" implies "N signers attested." The directly analogous defect in Agave lives in the Ed25519 signature-verification precompile: `agave_precompiles::ed25519::verify` will return `Ok(())` for an instruction that declares `num_signatures == 0`, as long as no trailing offset/signature bytes are present, meaning the precompile "verifies" zero signatures successfully.

### Finding Description
`verify()` in [1](#0-0)  reads the declared signature count from `data[0]` and only rejects a zero count when `data.len() > SIGNATURE_OFFSETS_START`:

```rust
let num_signatures = data[0] as usize;
if num_signatures == 0 && data.len() > SIGNATURE_OFFSETS_START {
    return Err(PrecompileError::InvalidInstructionDataSize);
}
```

If an attacker submits an Ed25519 precompile instruction with `data.len() == SIGNATURE_OFFSETS_START` (i.e., just the two-byte header, no offsets/signature/pubkey/message bytes) and `num_signatures = 0`, the function computes `expected_data_size == SIGNATURE_OFFSETS_START`, the size check passes, the `for i in 0..num_signatures` loop runs zero times, and the function returns `Ok(())`. This is a "quorum of zero" — the precompile instruction succeeds without validating any signature at all.

This is inconsistent with the sibling `secp256r1` precompile, which unconditionally rejects `num_signatures == 0`: [2](#0-1) . The `secp256k1` precompile has the same permissive zero-signature acceptance pattern as `ed25519` (`count == 0 && data.len() > 1`): [3](#0-2) .

Any unprivileged transaction sender can include such an instruction; both `secp256k1` and `ed25519` are always-enabled precompiles reachable from ordinary transactions: [4](#0-3) . The transaction-wide signature-count accounting used for cost/fee purposes (`num_ed25519_instruction_signatures`, `num_secp256k1_instruction_signatures`) is likewise derived straight from `data[0]` without any minimum-count enforcement: [5](#0-4) .

### Impact Explanation
On-chain programs that use the well-established Solana pattern of "check the Instructions sysvar for a preceding Ed25519/secp256k1 precompile verify instruction, and trust that its success implies the intended signer(s) attested to the message" (the same trust model as `ChainlinkDAppControl.transmit()` relying on `verifyTransmitSigners()`) can be fooled: a zero-signature, minimal-length precompile instruction will still appear in the transaction and still "succeed," even though it verified nothing. A program that fails to also check `data[0]/num_signatures >= required_quorum` before trusting the precompile's success would treat an unauthenticated instruction as authenticated, enabling unsigned/unauthorized actions (analogous to unsigned fund movement or unauthorized privilege exercise) for any program built on this common precompile-attestation pattern — exactly the trust-assumption break described in the original report.

### Likelihood Explanation
This requires no privileged access — any transaction sender can construct the minimal, zero-signature instruction bytes and submit it in a standard transaction. It is deterministic behavior in the precompile, so it is trivially and reliably reproducible on any Agave validator/leader.

### Recommendation
Make Ed25519 (and secp256k1) precompile verification unconditionally reject `num_signatures == 0`, matching the stricter secp256r1 behavior at [6](#0-5) , rather than only rejecting it when extra trailing data is present. This removes the "vacuously true" success path and forces callers/consumers to always see at least one verified signature when the precompile instruction returns `Ok`.

### Proof of Concept
Construct an Ed25519 program instruction with:
- `data[0] = 0` (num_signatures)
- `data[1] = 0` (padding byte)
- total `data.len() == SIGNATURE_OFFSETS_START` (no offsets struct, no signature/pubkey/message bytes)

Submitting this as an instruction in an otherwise normal transaction causes `agave_precompiles::ed25519::verify` at [7](#0-6)  to return `Ok(())` without performing any cryptographic check, as confirmed by the existing unit test pattern for the analogous secp256k1 zero-count case (`test_count_is_zero_but_sig_data_exists`) which only fails when *extra* data is appended: [8](#0-7) ; no equivalent test exists to reject a bare zero-length-data, zero-signature Ed25519 instruction.

```rust
pub fn verify(
    data: &[u8],
    instruction_datas: &[&[u8]],
    _feature_set: &FeatureSet,
) -> Result<(), PrecompileError> {
    if data.len() < SIGNATURE_OFFSETS_START {
        return Err(PrecompileError::InvalidInstructionDataSize);
    }
    let num_signatures = data[0] as usize;
    if num_signatures == 0 && data.len() > SIGNATURE_OFFSETS_START {
        return Err(PrecompileError::InvalidInstructionDataSize);
    }
    let expected_data_size = num_signatures
        .saturating_mul(SIGNATURE_OFFSETS_SERIALIZED_SIZE)
        .saturating_add(SIGNATURE_OFFSETS_START);
    // We do not check or use the byte at data[1]
    if data.len() < expected_data_size {
        return Err(PrecompileError::InvalidInstructionDataSize);
    }
```
