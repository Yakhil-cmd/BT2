## Finding

The webhook signature verification in `WebhooksController` selects which organization's secret to verify against using an attacker-controlled field of the *unverified* payload, and this field is never checked against the (different) field the event handlers subsequently use to decide which repository/stack to mutate. [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`repository_owner` is read straight from the raw JSON body (`JSON.parse(request.raw_post)` happens again identically in `create`) before the signature is even checked — it is fully attacker-supplied content, not GitHub-verified metadata. Shipit supports hosting multiple, independently-secreted GitHub App organizations in a single instance: [3](#0-2) 

Each organization has its own `webhook_secret`. Event handlers, however, resolve the *target* repository/stack from a **different** payload field, `repository.full_name`, inside the very same JSON body: [4](#0-3) [5](#0-4) 

Nothing enforces `repository.owner.login == owner(repository.full_name)`. Since this is a direct HTTP POST to `/webhooks` (no GitHub source-IP or App-installation binding is enforced beyond the HMAC), an attacker who knows the `webhook_secret` for *any one* organization configured in this shared Shipit instance (e.g. one they legitimately onboarded/administer) can craft a fully custom JSON body: set `repository.owner.login`/`organization.login` to their own org (so `verify_signature` picks their known secret and passes), while setting `repository.full_name` to a completely different, victim organization's repository already tracked by Shipit.

This breaks exactly the binding: **organization that authenticated (`repository_owner` used to pick the verifying secret) ≠ repository that is written (`repository.full_name` used by the handler)**.

### Exploitable consequences
- `PullRequest::ClosedHandler#process` calls `review_stack.archive!` for any repo resolvable via `Repository.from_github_repo_name(params.repository.full_name)` — an attacker can archive/deprovision another organization's review stack. [5](#0-4) 
- `PullRequest::OpenedHandler`/`ReopenedHandler` can create or unarchive review stacks for a victim repository with attacker-chosen branch/PR metadata, which enqueues real provisioning/deploy work on Shipit's infrastructure for that repo. [6](#0-5) 
- `PushHandler#process` triggers `stack.sync_github` for the victim's stacks using an attacker-forged `after` SHA. [7](#0-6) 

These are exactly cross-repository/cross-organization writes performed without any credential tied to the victim organization — only knowledge of a different, unrelated organization's webhook secret.

### Title
Webhook signature verification uses the payload's own (attacker-controlled) organization field, decoupled from the repository the event handler actually writes to - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to validate an inbound webhook's HMAC using `repository_owner`, derived from the untrusted JSON body (`repository.owner.login` or `organization.login`). Handlers then resolve which `Repository`/`Stack` to mutate using a separate field, `repository.full_name`, from that same untrusted body. Nothing ties these two fields together, so a valid signature computed with organization A's secret can be paired with a forged `repository.full_name` pointing at organization B's repository.

### Finding Description
Because `/webhooks` is a plain POST endpoint validated only by HMAC-SHA1 over the raw body using a secret selected from the body itself, an attacker who possesses the `webhook_secret` for any one organization onboarded to a multi-tenant Shipit instance can produce a payload that:
1. Sets `repository.owner.login` (or `organization.login`) to their own org, so `Shipit.github(organization: repository_owner).verify_webhook_signature` succeeds using the secret they know.
2. Sets `repository.full_name` (used independently by every `Shipit::Webhooks::Handlers::Handler` subclass via `Repository.from_github_repo_name(repository_name)`) to a victim organization's repository already tracked by the instance.

The signature check never re-derives or re-validates the organization against the repository the handler will actually act on, breaking the equality `verified_organization == owner(repository_written_to)`.

### Impact Explanation
This allows an attacker who legitimately controls one tenant organization's GitHub App webhook secret to perform unauthorized, cross-organization writes against a completely different organization's Shipit stacks: archiving/creating/unarchiving review stacks (triggering real provisioning/deploy pipelines), forcing `sync_github` calls, and manipulating pull-request-driven state — all without ever authenticating to, or holding credentials for, the victim organization. This meets the Critical bar of "cross-repository writes / an unauthorized deploy."

### Likelihood Explanation
Any Shipit deployment configured with the documented multi-organization `github:` secrets layout (as shown in `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`) is affected. The only prerequisite is that the attacker knows the `webhook_secret` of at least one hosted organization — plausible in shared/self-service Shipit deployments where different teams each supply their own GitHub App secret to the same instance.

### Recommendation
Do not select the verifying organization/secret from attacker-controlled payload content that is separate from the field(s) used to determine the write target. Instead:
- Verify the signature using the secret tied to the specific `Repository`/`Stack` (or its owning organization) that `repository.full_name` resolves to, not a value read independently from the same untrusted body, or
- After verification, re-check that `repository.owner.login` (the field used to select the secret) matches the owner segment of `repository.full_name` (the field used to write), rejecting the request if they differ.

### Proof of Concept
1. Configure/onboard Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (multi-app config as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who knows only `OrgA`'s `webhook_secret`, craft a `pull_request` "closed" event JSON body with `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/victim-repo"` (a real repo/stack already tracked under `OrgB`), plus valid `pull_request`/`sender` sub-fields.
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: pull_request`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature.
5. `PullRequest::ClosedHandler` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `review_stack.archive!`, mutating `OrgB`'s stack despite the attacker never holding any `OrgB` credential.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
