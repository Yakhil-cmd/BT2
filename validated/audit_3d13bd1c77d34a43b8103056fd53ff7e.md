## Title
Webhook signature verification selects the GitHub App/secret using an unverified payload field, decoupling the authenticating organization from the repository actually acted upon - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and thus which `webhook_secret`) to verify the incoming signature against using `repository_owner`, a value read straight out of the **unverified** JSON body. Handlers that subsequently act on the payload (e.g. `StatusHandler`) never re-validate that this owner matches the repository/commit actually being mutated. In a multi-organization deployment, this lets an attacker choose an organization whose app config has no `webhook_secret` configured to trivially satisfy signature verification, then forge an event that mutates state belonging to a completely different, victim-configured repository.

### Finding Description
`verify_signature` resolves the signing app before any authenticity check has occurred: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')`, taken from the raw, attacker-controlled `request.raw_post` before `verify_webhook_signature` runs. `Shipit.github(organization: repository_owner)` then looks up per-organization app config: [3](#0-2) 

and `verify_webhook_signature` trivially succeeds whenever that organization's `webhook_secret` is blank: [4](#0-3) 

The documented multi-app configuration schema explicitly allows `webhook_secret` to be `nil` per organization: [5](#0-4) 

Meanwhile, the code that actually acts on the event payload uses a *different* field from the same unverified body - `repository.full_name` - to select the target stacks: [6](#0-5) 

Nothing cross-checks that `repository.owner.login` (used to pick the signing secret) is consistent with `repository.full_name` (used to pick the target). Worse, `StatusHandler` does not even use the repository field at all - it matches on commit SHA globally, across every stack in the instance: [7](#0-6) 

**Equality broken**: *organization that authenticated the webhook* (`repository_owner` → app/secret used in `verify_signature`) ≠ *repository/commit actually written* (`repository.full_name` / `Commit.where(sha:)` used by handlers).

### Impact Explanation
Before the attack: only GitHub, holding each organization's real `webhook_secret`, can produce events accepted by Shipit for that organization's repositories.

After the attack: an unprivileged external attacker who knows (a) any organization name configured in Shipit's multi-app `github:` config with a blank `webhook_secret` (nil secrets are explicitly supported/documented) and (b) the `owner/repo` full name of a *different*, properly-secured target stack, can send a self-signed (or unsigned) POST to `/github/webhooks` with `repository.owner.login` set to the weak/unconfigured org and `repository.full_name`/commit `sha` set to the victim stack. Signature verification passes trivially (`return true unless webhook_secret`), and the handler (e.g. `StatusHandler`) mutates state - such as marking an arbitrary commit's CI status as `success` - on the victim stack. This can unblock merges/deploys that are gated on CI status, i.e. an unauthorized deploy/merge, without ever holding a Shipit session, API token, or the victim organization's webhook secret.

### Likelihood Explanation
Requires only that a Shipit instance is configured for multiple GitHub organizations and at least one configured organization has no `webhook_secret` set - a configuration explicitly presented as valid/optional in `docs/setup.md` and the example secrets files. No privileged access, session, or GitHub credential is required; the attacker only needs network access to the public webhook endpoint and knowledge of an org name and a target `owner/repo`/commit sha.

### Recommendation
- Verify the webhook signature using the app/secret corresponding to the repository actually referenced by `full_name`/commit ownership, not a value chosen independently and prior to verification.
- Require every configured organization to have a non-blank `webhook_secret` (fail closed instead of `return true unless webhook_secret`).
- Scope `StatusHandler` (and any other handler) lookups by the repository asserted in the payload, not purely by commit SHA, and cross-validate that `repository.owner.login` matches the resolved repository's owner before dispatching handlers.

### Proof of Concept
1. Configure Shipit with two organizations: `WeakOrg` (no `webhook_secret`) and `VictimOrg` (has `webhook_secret`, hosts a stack requiring successful CI status to deploy/merge).
2. POST to `/github/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or any bogus value), body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "repository": { "owner": { "login": "WeakOrg" }, "full_name": "WeakOrg/anything" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "WeakOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` and the request is accepted.
4. `StatusHandler#process` runs `Commit.where(sha: "<victim-commit-sha>")`, finds the commit belonging to `VictimOrg`'s stack, and creates a forged `success` status on it, regardless of the org/repo used to pass signature verification.

```ruby
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
