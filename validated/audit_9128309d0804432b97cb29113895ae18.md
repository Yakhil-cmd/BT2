## Title
Cross-tenant status forgery via unscoped commit lookup in `StatusHandler#process` enables unauthorized PR merge - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

## Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target `Commit` purely by `sha`, with no scoping to the repository that sent the webhook, unlike its sibling handlers (`PushHandler`, `CheckSuiteHandler`) which both scope through `Handler#stacks` (derived from `payload.dig('repository', 'full_name')`). Because git commit SHAs are content-addressed and identical commits legitimately exist across repositories (forks, cherry-picks, mirrors), an attacker who owns/controls a different repository connected to the same Shipit instance can send a genuinely-signed `status` webhook for a SHA that also happens to be a victim's `MergeRequest#head`, forging arbitrary `success` statuses onto the victim's stack and satisfying `MergeRequest#all_status_checks_passed?`, leading to an unauthorized `merge!`.

## Finding Description
Broken binding: `payload.dig('repository', 'full_name')` (the repository that authenticated the webhook) == `commit.stack.repository` (the repository whose merge gating that status is used for). This equality is enforced in `PushHandler` and `CheckSuiteHandler` via `Handler#stacks`: [1](#0-0) 

`PushHandler` uses `stacks.not_archived.where(branch:)` and `CheckSuiteHandler` uses `stacks.where(branch: ...)` then `stack.commits.where(sha: ...)` — both scoped through the repository derived from the webhook payload: [2](#0-1) [3](#0-2) 

`StatusHandler`, however, never calls `stacks`/`repository_name` at all — it queries `Commit` globally by `sha`: [4](#0-3) 

`commit.create_status_from_github!(params)` then writes the status using the *found commit's own* `stack_id`, not any stack derived from the payload: [5](#0-4) [6](#0-5) 

Exploit flow: the attacker obtains the exact commit object of the victim's open PR head (trivial for public repos, or if the attacker is a collaborator/fork owner — git commits are content-addressed, so the SHA is identical without any hash collision). The attacker pushes/replicates that commit into a repository they control that is itself connected to the same Shipit instance (any org/repo onboarded to this multi-tenant Shipit deployment). GitHub genuinely signs `status` events for that repository with that org's real `webhook_secret`, so `WebhooksController#verify_signature` legitimately passes for `repository_owner` = attacker's own org: [7](#0-6) 

The attacker (or their CI, which they fully control) then emits one `status` webhook per `context` required by `deploy_spec.merge_request_required_statuses`, each with `state: 'success'`, for the shared SHA. `StatusHandler#process` finds the victim's `Commit` row (matched purely by SHA) and creates `Status` records on the victim's `stack_id` — with the attacker choosing state/context/description at will since these are `accepts`-only params: [8](#0-7) 

Once all required contexts are present and successful, `MergeRequest#all_status_checks_passed?` returns `true`: [9](#0-8) 

which feeds `reject_unless_mergeable!` returning `false`, allowing the queue processor to proceed to `merge!`, causing GitHub API calls to merge the victim's PR using the victim stack's own credentials: [10](#0-9) 

No existing guard closes this gap: `verify_signature` only proves the sender's own org identity, not that the target commit belongs to that org's stack; `ExplicitParameters` schema on `StatusHandler` has no repository field requirement; and `Commit`/`Status` models have no uniqueness/ownership check tying a status write back to the reporting repository.

## Impact Explanation
A payload that authenticates as repository A can write `Status` rows against a `Commit`/`Stack` belonging to repository B, causing an unauthorized merge of repository B's pull request using repository B's own configured merge credentials — this is a "payload for one repository mutating another's... task or team" / "unauthorized merge" scenario, matching Critical severity. The blast radius spans every stack hosted on the same multi-tenant Shipit instance whose PR head SHA an attacker can reproduce in a repository they control.

## Likelihood Explanation
Requires: (1) a Shipit instance handling more than one GitHub organization/repository (the standard multi-tenant deployment model implied by `Shipit.github(organization:)`), (2) attacker control of at least one repository connected to that same instance, and (3) the ability to reproduce the victim's exact head commit object elsewhere (trivial for public repos or any repo the attacker can fork/read, since git SHAs are content-addressed — no cryptographic collision needed). Attacker cost is low: push a duplicated commit to their own repo and let their own CI (or a direct forged request replaying real GitHub event bodies) emit `status` events; this is fully repeatable per required context and per target stack.

## Recommendation
Scope `StatusHandler#process` by the reporting repository the same way `PushHandler`/`CheckSuiteHandler` do: resolve `stacks` via `Handler#stacks` (from `payload.dig('repository', 'full_name')`) and only update `Commit`/`Status` records that belong to those stacks, e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |c| c.create_status_from_github!(params) } }`, rejecting/ignoring shas that don't belong to the sending repository's stacks.

## Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` style, not creating live GitHub calls):
1. Create `stack_victim` (repository `victim/repo`) and `stack_attacker` (repository `attacker/repo`), each with its own `Repository` record.
2. Create `commit = stack_victim.commits.create!(sha: 'deadbeef...')` and a `merge_request` on `stack_victim` with `head: commit`.
3. Stub `stack_victim.cached_deploy_spec.merge_request_required_statuses` to `['ci/build']`.
4. Build a `status` webhook payload with `repository.full_name = 'attacker/repo'`, `sha: commit.sha`, `state: 'success'`, `context: 'ci/build'`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, simulating a legitimately-signed request from `attacker/repo`).
6. Assert the binding before: `commit.statuses.where(context: 'ci/build').count == 0` and `merge_request.all_status_checks_passed? == false`.
7. Assert the binding after: `commit.statuses.where(context: 'ci/build').count == 1` and its `stack_id == stack_victim.id` even though the payload's repository was `attacker/repo`, and `merge_request.all_status_checks_passed? == true`.
8. Optionally assert `merge_request.reject_unless_mergeable! == false` and mock `stack_victim.github_api.merge_pull_request` to show `merge_request.merge!` proceeds to call it, demonstrating the forged cross-tenant status directly enables `merge!`.
