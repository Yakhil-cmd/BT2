### Title
Pull request label name collides with `VariableDefinition` name and overrides operator-intended default in `Command#interpolate_environment_variables` - (File: `app/models/shipit/review_stack.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/command.rb`)

### Summary
`ReviewStack#env` injects every pull-request label, uppercased, as `"true"` into the stack's environment hash before the task's own explicit env overrides are merged on top in `TaskCommands#env`. Because deploy-spec `VariableDefinition` defaults are never force-merged into `@task.env` anywhere in the command pipeline, a PR label whose uppercased name matches an operator-declared variable name (e.g. a safety-toggle variable) survives into the final environment handed to `Command`/`PTY.spawn`, silently overriding the operator's intended default value.

### Finding Description
The broken binding: for a `command_line` referencing `$FOO` (Shipit uses bare `$VAR`, not `${VAR}`, per the regex in `lib/shipit/environment_variables.rb:23`), the intended equality is `env['FOO'] == VariableDefinition('FOO').default` (or the user's explicit override), never `env['FOO'] == 'true'` from an attacker-controlled label.

Path:
1. `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into the stack env. Labels come from `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`), which stores `params.pull_request.labels.map(&:name)` straight from the incoming webhook payload — the PR author fully controls this list.
2. `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) builds the final environment as:
   `super.merge(@stack.env).merge({hardcoded keys}).merge(deploy_spec.machine_env).merge(@task.env)`.
   `@task.env` is merged last, so it wins on key collision — but it only contains whatever env keys were actually stored on the `Task`/`Deploy` record. Operator-declared defaults from `deploy_spec.default_deploy_env` (`app/models/shipit/deploy_spec.rb:124-126`) are a standalone helper that is not referenced anywhere in this merge chain, so a variable the deploy did not explicitly set is simply absent from `@task.env`.
3. When a variable name is absent from `@task.env`, nothing overrides the label-derived key injected by `ReviewStack#env` in step 1, so it flows unchanged into `Command#env` (`lib/shipit/command.rb:31-34`).
4. `Command#interpolate_environment_variables` (`lib/shipit/command.rb:51-55`) calls `EnvironmentVariables.with(env).interpolate(argument)`, which does **not** call `EnvironmentVariables#permit` (the whitelist filter) — `permit` is only used earlier by `DeploySpec#filter_deploy_envs`/`#filter_rollback_envs` on the *user-submitted* env params, not on the final merged runtime env. So there is no re-validation step at the point the value reaches the shell command executed via `PTY.spawn` (`lib/shipit/command.rb:92`).
5. Variable names declared by the operator are also disclosed through `TaskDefinition#as_json` (`app/models/shipit/task_definition.rb:50-61`, `variables: variables.map(&:to_h)`), which an attacker can read via the API/UI to discover exact target names to squat with a label.

Exploit: an attacker who can label their own PR (per the stated attacker capabilities) adds a label whose uppercased text matches an operator-declared `VariableDefinition` name that is not always explicitly re-submitted on every deploy (e.g. a safety/behavior toggle default such as the `SAFETY_DISABLED` example in `test/fixtures/shipit/stacks.yml:119`). When the review stack's continuous-delivery/deploy task runs without that variable being explicitly re-submitted, the label value `"true"` silently replaces the intended default in the command's environment and therefore in the interpolated `command_line` / underlying shell process environment.

### Impact Explanation
The attacker can flip any deploy/rollback/task-time variable that the operator intended to default to a safe value, for any PR-driven review stack they can label, without ever needing to submit that variable explicitly through the deploy form. Depending on what the operator's `shipit.yml` command_line does with that variable (e.g. disabling a safety check, changing a deployment target, enabling a dangerous code path), this can result in a command executing that should not have executed as configured — matching the "unauthorized deploy" / `Command`/`PTY.spawn` execution-alteration impact category. The blast radius is scoped to the repository's own review stacks (not cross-tenant), but it is fully repeatable per PR/label and requires no privileged role.

### Likelihood Explanation
Preconditions: review stacks must be enabled for the repository, the deploy spec must declare a `VariableDefinition` whose name an attacker can guess or read via the exposed `TaskDefinition#as_json`, and the triggered task must not have that variable explicitly re-submitted (e.g. continuous-delivery-triggered deploys, or manual deploys where the field is left at its "unset" state). Attacker cost is a single PR label add, entirely within capabilities already granted to any PR author who can label their own PR. This is realistic for continuous-delivery review-stack workflows where env variables are rarely-if-ever explicitly re-submitted per deploy.

Note: I was not able to fully trace `Deploy#env`/`Task#env` and the deploys controller within the available tool budget to conclusively confirm whether every deploy in practice always explicitly submits all declared variables (which would close this gap) or leaves unset variables absent from `@task.env` (which leaves it open, as the code in `TaskCommands#env` and `DeploySpec#default_deploy_env` strongly suggests). This should be verified against `app/models/shipit/deploy.rb`, `app/models/shipit/task.rb`, and `app/controllers/shipit/deploys_controller.rb` before treating this as fully confirmed.

### Recommendation
- In `TaskCommands#env`, explicitly merge `deploy_spec.default_deploy_env` (or the equivalent for rollback/task variables) before merging `@task.env`, so every declared variable always has a deterministic operator-approved value present prior to any label-derived keys.
- Alternatively/additionally, namespace pull-request-label-derived env keys (e.g. prefix with `LABEL_`) in `ReviewStack#env` so they can never collide with operator-declared `VariableDefinition` names.
- Apply `EnvironmentVariables#permit` (or an equivalent explicit precedence resolution) at the point `Command` builds its final env, rather than relying purely on hash-merge ordering.

module Shipit
  class TaskCommandsReviewStackVariableCollisionTest < ActiveSupport::TestCase
    test "label named after a VariableDefinition overrides the operator's default in the command env" do
      stack = shipit_stacks(:review_stack)
      stack.pull_request.labels = ["FOO"] # attacker-controlled PR label

      stack.cached_deploy_spec = create_deploy_spec(
        "deploy" => {
          "variables" => [
            { "name" => "FOO", "title" => "operator safety toggle", "default" => "0" }
          ]
        }
      )

      deploy = stack.trigger_continuous_delivery
      # simulate a deploy where the "FOO" variable was never explicitly submitted:
      deploy.env = {}

      command = Shipit::DeployCommands.new(deploy)
      cmd = Shipit::Command.new('echo $FOO', env: command.env, chdir: '.')

      # Broken binding demonstrated: expected operator default, got attacker label value
      assert_equal "0", cmd.env["FOO"], "expected VariableDefinition default '0'"
      # actual observed behavior (vulnerability):
      # assert_equal "true", cmd.env["FOO"]
    end
  end
end

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
