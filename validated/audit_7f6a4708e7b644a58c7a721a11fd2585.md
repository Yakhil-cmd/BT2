### Title
Webhook signature verification is bypassed for any GitHub organization configured without a `webhook_secret`, enabling forged `membership` events that grant unauthorized `Shipit.github_teams` access - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to validate against by reading an **unauthenticated, attacker-controlled** payload field (`repository.owner.login`), and `GithubApp#verify_webhook_signature` treats a missing/blank `webhook_secret` as automatically valid. Since `webhook_secret` is documented as optional, any organization configured without one accepts arbitrary unsigned webhook payloads. This breaks the intended binding between "the organization whose credentials authenticate the request" and "the organization on whose behalf the request is processed," letting an unauthenticated attacker forge a `membership` event that inserts an arbitrary GitHub login into a `Shipit.github_teams`-tracked team, bypassing the team-based authorization gate.

### Finding Description
The webhook endpoint is public and unauthenticated by design; its only protection is the HMAC signature check: [1](#0-0) 

`repository_owner`, used to pick which `Shipit.github(organization: ...)` configuration (and thus which `webhook_secret`) to validate the signature against, is read straight from the unverified JSON body: [2](#0-1) 

The actual verification is: [3](#0-2) 

`return true unless webhook_secret` means that for any configured GitHub organization whose `webhook_secret` is left blank (explicitly called out as optional in the setup flow), signature verification always succeeds — the `X-Hub-Signature` header content is never checked. Because `repository_owner` is attacker-controlled, an attacker only needs the request to name an organization that Shipit has configured without a webhook secret in order for `verify_signature` to accept a completely fabricated payload with any event type, including `membership`: [4](#0-3) 

The `membership` handler adds/removes `Team` memberships based on the payload's `member`/`team` fields (confirmed by the controller test suite exercising membership creation/removal from raw JSON params). Team membership is exactly what gates application access: [5](#0-4) [6](#0-5) 

**Binding broken:** `organization authenticated by verify_webhook_signature` should equal `organization whose team/membership state is mutated by the handler`. Before the attack, both sides require possession of the org's real `webhook_secret` (or a real GitHub App delivery). After the attack — when a configured org has no `webhook_secret` — the left side collapses to "always true" while the right side remains fully attacker-controlled via the unverified payload, so any caller can mutate team membership for that organization without ever authenticating as GitHub.

### Impact Explanation
This escalates into `Shipit.github_teams` authorization (per the rules, a listed High-impact category): an attacker who can identify or guess a Shipit-tracked organization slug with no webhook secret configured can add their own (or anyone's) GitHub login to a team that `Shipit.github_teams` recognizes, granting themselves access to view/trigger deploys, tasks, and other stack operations gated by `current_user.authorized?`.

### Likelihood Explanation
Likelihood depends on operator configuration: it requires at least one configured GitHub organization to have an empty/blank `webhook_secret`, which the project's own setup documentation and example configs (`config/secrets.development.example.yml`, `docs/setup.md`) explicitly present as an optional field with no warning about the resulting bypass of signature verification for that organization. Given the field is optional and its security implication is undocumented, this is a realistic misconfiguration rather than a contrived edge case, and requires no credentials, tokens, or repository access to exploit once present.

### Recommendation
- Treat a missing/blank `webhook_secret` as "reject all webhooks for this organization" rather than "accept all webhooks unsigned," or make `webhook_secret` mandatory for any organization that registers hooks used for authorization-relevant events (e.g., `membership`).
- Do not select the verification secret using an unauthenticated payload field; if multiple organizations are configured, verify the signature against all configured secrets (or require the org to be resolved from a trusted, pre-registered source) before trusting `repository_owner`/`organization.login` from the body.
- Add explicit warnings in `docs/setup.md` / secrets templates that omitting `webhook_secret` disables webhook authentication entirely.

### Proof of Concept
1. Shipit is configured with two GitHub orgs, e.g. `trusted-org` (has `webhook_secret` set) and `legacy-org` (left blank, as the example config permits).
2. Attacker sends an unauthenticated `POST /webhooks` with header `X-Github-Event: membership` and no valid `X-Hub-Signature`, with body:
```json
{
  "action": "added",
  "organization": { "login": "legacy-org" },
  "team": { "id": 1, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/..." },
  "member": { "login": "attacker-controlled-account" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "legacy-org").verify_webhook_signature(...)`, which returns `true` unconditionally because `legacy-org`'s `webhook_secret` is blank (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
4. `Handlers::MembershipHandler` processes the forged payload, and `attacker-controlled-account` becomes a member of the `deployers` Team.
5. If `Shipit.github_teams` includes `legacy-org/deployers`, the attacker's GitHub account now passes `User#authorized?` on next login, granting access to Shipit without ever proving control of `legacy-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
