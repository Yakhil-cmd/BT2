### Title
Cross-organization webhook forgery via mismatched signature-selection field and stack-resolution field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The Shipit webhook endpoint picks which `webhook_secret` to verify a request's signature against using `repository.owner.login` (or `organization.login`) taken from the *unauthenticated* JSON body, but the event handlers that actually mutate state resolve the target `Stack`/`Repository` using a completely different field, `repository.full_name`. Because nothing binds these two fields together, an attacker who controls the `webhook_secret` for any one organization configured on the Shipit instance can forge a validly-signed webhook whose `repository.owner.login` matches their own organization (to pass signature verification) while `repository.full_name` names a repository belonging to a different organization, causing Shipit to act on that other organization's stack.

### Finding Description
`WebhooksController#verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [3](#0-2) 
where `repository_owner` reads `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [4](#0-3) .

The HMAC is computed over the entire raw body using the secret belonging to whatever organization `repository.owner.login` claims — an attacker who knows/controls that org's `webhook_secret` can produce a valid signature for *any* body content they like, since HMAC only proves "this secret produced this exact byte string," not "the byte string's other fields are internally consistent."

After the signature check, `create` dispatches the raw parsed JSON to handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) ). Every handler resolves its target stacks via `Handler#stacks`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [1](#0-0) 

`repository.owner.login` (used for signature/secret selection) and `repository.full_name` (used for stack resolution) are independent, attacker-controlled JSON keys within the same signed body. The binding the system implicitly relies on — "the org whose secret verified this payload" == "the org that owns the repository being acted on" — is never actually checked.

### Impact Explanation
This breaks the "an organization that authenticated versus the repository that is written" trust boundary described for this class of bug. Concretely, on a multi-tenant Shipit instance (multiple `github:` entries in `secrets.yml`, each a distinct organization with its own `webhook_secret`), an attacker who is a legitimate, unprivileged member/admin of Organization B (and therefore knows or can configure Org B's webhook secret through normal, non-privileged GitHub App/webhook setup for their own org) can forge a `push`, `status`, `check_suite`, or `pull_request` webhook whose `repository.owner.login`/`organization.login` says `"org-b"` (to select and pass verification against Org B's secret) but whose `repository.full_name` says `"org-a/some-repo"`. Shipit will accept the signature and then run handler logic (e.g. `PushHandler#process` calling `stack.sync_github`) [6](#0-5)  against Organization A's stack — a cross-organization write the attacker has no legitimate authority over. This matches the "cross-repository writes" / unauthorized deploy-adjacent Critical/High impact category, since sync/status/check-suite events can trigger deploy-relevant state changes (undeployed commit counts, CI status records, merge status) on a repository the attacker does not control.

### Likelihood Explanation
Exploitability depends on the deployment configuration: it requires a Shipit instance configured to serve multiple GitHub organizations/tenants (multiple entries under `github:` in `secrets.yml`, as shown in `config/secrets.development.shopify.yml`) [7](#0-6) , and requires the attacker to be a legitimate webhook-secret holder for at least one of those organizations (which is a normal, unprivileged capability — anyone who can register a GitHub App/webhook for their own org on the shared instance gets a `webhook_secret`, they don't need any Shipit credential, session, or API token). No `ApiClient` token, Shipit session, or GitHub App private key for the *target* org is needed — only knowledge of one's *own* org's webhook secret, which is exactly the credential a legitimate but unprivileged/isolated tenant would already possess. This makes it a genuine cross-tenant trust-boundary break within the engine's own webhook-handling code, not something requiring privileged access to the victim's resources.

### Recommendation
Bind the field used for signature/secret selection to the field used for state mutation: after selecting `github_app` via `repository_owner`, re-validate that `payload.dig('repository', 'full_name')` (or `payload.dig('repository', 'owner', 'login')`) actually belongs to the same organization the secret was selected for (e.g., assert `repository.full_name.split('/').first.casecmp(repository_owner) == 0`) before dispatching to handlers. Alternatively, look up the `Repository`/`Stack` first from `full_name`, derive the organization from the *stored* `Repository#owner` (trusted, previously-synced value) rather than from the unauthenticated payload, and use that to select the `webhook_secret`.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `org-a` (secret `SECRET_A`, owns repo `org-a/prod-app` with an existing Stack) and `org-b` (secret `SECRET_B`, attacker's own registered org).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-b" },
    "full_name": "org-a/prod-app"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(SECRET_B, body)` using their own legitimately-known `SECRET_B`.
4. `POST /webhooks` with header `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: 'org-b')` (from `repository.owner.login`), verifies against `SECRET_B` — succeeds.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('org-a/prod-app')`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on Organization A's stack — a write the attacker triggered using only Org B's secret, with no authority over Org A.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
