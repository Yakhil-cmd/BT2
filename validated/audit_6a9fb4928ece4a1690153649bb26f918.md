### Title
Cross-organization status forgery lets a lower-privileged GitHub App organization set commit statuses on any repository's commits, bypassing deploy CI gating - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature is verified against the `webhook_secret` of the GitHub organization named in the payload's `repository.owner.login` (or `organization.login`) field [1](#0-0) , but `StatusHandler` never re-checks that the target `Commit` actually belongs to a repository/stack owned by that same organization — it resolves commits purely by `sha` across the whole `commits` table [2](#0-1) .

### Finding Description
Shipit supports hosting multiple GitHub organizations behind one instance, each with its own GitHub App / `webhook_secret` [3](#0-2) . Signature verification in `WebhooksController#verify_signature` selects the app/secret to verify against using only the organization identified in the payload: [4](#0-3) 

That establishes the intended binding: *the org whose secret signed the payload == the org whose data may be mutated*. However, once the signature passes, the dispatched handler is free to interpret the payload however it likes. Most handlers (`PushHandler`, pull-request handlers) correctly scope their side effects to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` via `Handler#stacks` [5](#0-4) , keeping owner and repository consistent.

`StatusHandler` breaks this binding: it looks up commits by `sha` alone, with no scoping to `repository.full_name`/owner at all: [6](#0-5) 

Git commit SHAs are 40-character hex identifiers computed from tree content and are not secret — they are visible in URLs, PR links, CI logs, etc. A party that operates (or has takeover of) any one of the configured organizations' GitHub Apps can send a validly-signed `status` webhook (signed with *their own* org's `webhook_secret`) whose `repository.owner.login` matches their own org (so it passes `verify_signature`), while the `sha` field references a commit that exists in a *different* organization/repository tracked by the same Shipit instance. `StatusHandler#process` will happily create/attach that status to the matching `Commit` record regardless of which repository/stack it belongs to [2](#0-1) .

This directly maps to the report's bug class: "organization that authenticated" (the org whose webhook secret signed the request) is silently substituted for "the repository that is written" (any repository whose commit SHA happens to match), exactly the same kind of identity/binding confusion as the original Phabricator finding where a viewer's permission was substituted for the file's actual ownership.

### Impact Explanation
Shipit gates deploys on commit CI status (via `blocking_statuses` / `CommitChecks`, referenced from `Commit#create_status_from_github!` and `Stack`) [7](#0-6) . Because `StatusHandler` allows any configured organization's validly-signed webhook to set a `success` status on a commit belonging to a *different* organization's stack, an attacker who controls (or compromises) one low-privileged organization's GitHub App can force the required CI status on a commit in a different, higher-privileged organization's repository being tracked by the same Shipit instance — clearing the blocking-status check and enabling an unauthorized deploy of code that never actually passed CI for that repository. This satisfies the "unauthorized deploy" High-impact criterion.

### Likelihood Explanation
Requires: (1) the Shipit host to be configured for multiple GitHub organizations (documented, supported configuration) [3](#0-2) ; (2) knowledge of a target commit SHA in another org's repository (SHAs are not secret, and commit visibility can extend to public repos/PR links even if the org config is otherwise separated); (3) control of a webhook-app installation for at least one of the configured organizations. No Shipit login, `ApiClient` token, or GitHub write access to the target repository is required. Likelihood is moderate: it is realistic in shared/multi-tenant Shipit deployments where the sub-orgs do not fully trust each other's webhook senders, which is precisely the scenario the `github:` multi-org config section anticipates.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository named in the payload (`payload.dig('repository','full_name')`), analogous to how `Handler#stacks`/`PushHandler` scope by repository, e.g. join through `Stack`/`Repository` and only update commits belonging to stacks whose repository matches the payload's `repository.full_name`. More generally, add a repository-ownership check as a shared concern in `Handler` so every handler, not just `PushHandler`, verifies that the entity it mutates belongs to the organization that produced/verified the webhook.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with distinct `webhook_secret`s, per the multi-org `github:` config [8](#0-7) .
2. `org-b` has a private/sensitive stack tracking commit `deadbeef...` which is pending/blocked on a required CI status.
3. As the operator (or compromiser) of `org-a`'s GitHub App, send a `status` webhook to `/webhooks` with `X-Github-Event: status`, `repository.owner.login = org-a`, signed with `org-a`'s `webhook_secret`, but with `sha = deadbeef...` (the `org-b` commit) and `state = success`, `context = <the blocking context>`.
4. `WebhooksController#verify_signature` validates the signature against `org-a`'s secret and succeeds [9](#0-8) .
5. `StatusHandler#process` finds `Commit.where(sha: 'deadbeef...')` — which belongs to `org-b`'s stack — and calls `create_status_from_github!`, marking the blocking status green [2](#0-1) .
6. `org-b`'s stack now reflects a passing CI status it never actually received, potentially unblocking an otherwise-gated deploy.

Note: I was unable to fully trace `Commit#create_status_from_github!` and the exact `blocking_statuses`/deploy-gating logic within this session (only the method name was located, not its body), so the precise mechanics of how a forged status unblocks a deploy should be confirmed by a follow-up review of `app/models/shipit/commit.rb`, `app/models/shipit/commit_checks.rb`, and `app/models/shipit/stack.rb`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
