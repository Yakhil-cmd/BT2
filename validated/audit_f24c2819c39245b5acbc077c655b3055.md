### Title
Unescaped delimiter in arbiter-contract hash allows contract-hash collision leading to unauthorized escrow fund release - (File: arbiter_contract.js)

### Summary
The CVE describes curl silently dropping a security-relevant `Secure` cookie attribute because a tab character (instead of a space) was accepted as the attribute separator, letting attacker-controlled bytes cross a delimiter boundary that the parser assumed was safe. The analogous root cause in ocore is `arbiter_contract.js`'s `getHashSrc()`, which builds the value used as the on-chain "contract identity" (`contract.hash`) by joining several free-text, counterparty-controlled fields with a fixed, unescaped delimiter string. Because the delimiter itself is not forbidden inside the joined fields, an attacker can shift field boundaries (or, in the pre-`NEW_HASH_DATE` code path, there is no delimiter at all) so that two contracts with different economic terms produce the same `contract.hash`.

### Finding Description
`getHashSrc()` computes the identity hash of a private arbiter contract by string-concatenating counterparty-controlled fields: [1](#0-0) 

- `contract.title` and `contract.text` are free-form strings supplied by whichever peer creates/offers the contract (`createAndSend`), and `my_party_name`/`peer_party_name` are similarly free text.
- The "new" hash path joins fields with `exports.DELIMITER = "[|#|]"` [2](#0-1) , but nothing in `createAndSend`/`store`/`respond` rejects or escapes the delimiter substring when it appears inside `title`, `text`, or the party-name fields.
- The legacy path (`creation_date <= NEW_HASH_DATE`) has *no* delimiter between fields at all, making boundary-shifting collisions trivial.

Because `getHashSrc` is not an injective encoding of the tuple `(title, text, creation_date, payer_address, payer_name, arbiter_address, payee_address, payee_name, amount, asset)`, a counterparty can choose `title`/`text`/party names so that the resulting concatenated string — and hence the sha256 `contract.hash` — collides with the hash of a different, legitimate contract that has different `amount`/`asset`/party names but the same total string.

This matters because `contract.hash` is used downstream as a security-relevant identifier, not just a display id:
- It is embedded in the arbitration-escrow shared-address definition as the data-feed key `"CONTRACT_" + contract.hash`, which the arbiter posts to release funds: [3](#0-2) 
- The `"in data feed"` conditions that gate release of escrowed funds are keyed purely on `[oracle, "CONTRACT_"+hash, "=", address]`, independent of `amount`/`asset` of that specific contract: [4](#0-3) 
- `getContactsHash`/data-message validation also trusts `contract.hash` as the anchor identifying "this contract" when verifying signed transactions: [5](#0-4) 

If a malicious counterparty crafts contract B whose `getHashSrc()` output collides with an already-arbitrated contract A that shares the same arbiter, then when the arbiter posts `CONTRACT_<hash> = winner_address` to resolve contract A, that same data-feed entry also satisfies the `"in data feed"` branch of contract B's shared-address definition, because the branch only checks the colliding hash key and the address, not the amount or asset actually escrowed for B. This lets the attacker release B's escrowed funds (with different amount/asset than A) using an arbitration outcome that was never actually issued for B — a fund-loss/fund-misdirection condition analogous to the CVE's "security attribute silently misapplied due to delimiter confusion."

### Impact Explanation
This is reachable by an unprivileged private-payment counterparty (the "peer" in an arbiter contract) who fully controls `title`, `text`, and party-name fields sent to the victim via `createAndSend`/`respond`. A successful collision lets the attacker cause an arbiter's legitimate dispute resolution for one contract to also unlock escrowed funds of a second, unrelated contract sharing the same arbiter — i.e., concrete unauthorized fund release/loss for the victim's escrowed asset, without the arbiter or victim's participation in that second decision.

### Likelihood Explanation
Exploitability depends on finding a second-preimage-style collision in the concatenation scheme (not in SHA-256 itself), by manipulating attacker-controlled `title`/`text`/party-name strings to reproduce another target contract's exact concatenated byte string except for the parts that differ (amount/asset are numeric/short and can be brute-forced or grinded via title/text padding, since these fields are otherwise unrestricted in content and length). This requires the attacker to know or predict the exact fields of a target contract (e.g., their own prior contract with the same arbiter, or a contract whose terms are visible to them as a party) and to control the offer sent to the victim, making it a realistic but constructed active attack rather than trivial for arbitrary strangers — hence rated as reachable but requiring targeted crafting.

### Recommendation
Use a delimiter/encoding scheme that cannot appear in the joined field values (e.g., length-prefix each field, or hash each field independently with `objectHash`/canonical JSON before combining, as is done elsewhere in ocore for object hashing). At minimum, reject or escape occurrences of `exports.DELIMITER` inside `title`, `text`, and party-name fields before computing `getHashSrc`, and retire the legacy no-delimiter path. Additionally, the shared-address "in data feed" conditions should bind to more than the bare contract hash (e.g., include amount/asset/parties in the data-feed key or condition) so that a hash collision cannot cross-authorize an unrelated escrow.

### Proof of Concept
1. Attacker (party B) knows a target arbiter contract A with fields `(title_A, text_A, date_A, payer_A, name_A, arbiter, payee_A, name_A2, amount_A, asset_A)` whose `getHashSrc()`/`getHash()` produced `hash_A`, already escrowed and being arbitrated.
2. Attacker crafts contract B, choosing `title_B`/`text_B`/party names such that
   `[title_B, text_B, date_B, payer_B, name_B, arbiter, payee_B, name_B2, amount_B, asset_B].join(DELIMITER)` equals the same byte string as contract A's concatenation (e.g., by embedding the literal `DELIMITER` string inside `title_B`/`text_B` to shift field boundaries so that surplus content lands in the position of `amount_A`/`asset_A`, effectively re-creating A's exact string while B's structured fields differ), producing `hash_B === hash_A`.
3. Attacker sends contract B offer to the victim via `createAndSend`, victim accepts, and a shared address is derived with `"in data feed", [[arbiter], "CONTRACT_" + hash_B, "=", address]` — this is identical to A's condition since `hash_B === hash_A`.
4. When the arbiter later resolves dispute A and posts `CONTRACT_<hash_A> = winner`, this data-feed post also satisfies B's shared-address condition, letting the attacker (or whichever address `winner` is) withdraw B's escrowed funds without any arbitration ever having occurred for contract B.

Note: I was not able to fully verify from the indexed code whether any UI/API layer (outside `arbiter_contract.js`) imposes length/character restrictions on `title`/`text`/party-name fields that might reduce the practical feasibility of constructing the collision string; a Devin session with full repository access (including client/UI code not covered by the index) would be needed to confirm this and to prototype the exact collision construction. function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}

function getContactsHash(contract) {
	const payer_pairing_code = contract.me_is_payer ? contract.my_pairing_code : contract.peer_pairing_code;
	const payee_pairing_code = contract.me_is_payer ? contract.peer_pairing_code : contract.my_pairing_code;
	const payer_contact_info = contract.me_is_payer ? contract.my_contact_info : contract.peer_contact_info;
	const payee_contact_info = contract.me_is_payer ? contract.peer_contact_info : contract.my_contact_info;
	const src = [payer_contact_info || '', payer_pairing_code || '', payee_contact_info || '', payee_pairing_code || ''].join("|");
	return crypto.createHash("sha256").update(src, "utf8").digest("base64");
}
