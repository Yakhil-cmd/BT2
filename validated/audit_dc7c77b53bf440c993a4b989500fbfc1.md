### Title
Webhook organization/repository binding mismatch allows unauthorized cross-repository sync/deploy triggers - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on one field of the attacker-supplied JSON body (`repository.owner.login`, or `organization.login` as fallback), while the downstream event handlers select the actual repository/stack to act on based on a *different, uncorrelated* field of the same body (`repository.full_name`). When a Shipit install is configured for multiple GitHub organizations (a documented and supported configuration) and at least one of those organizations has no `webhook_secret` configured (also explicitly documented as "optional"), signature verification for that organization is a no-op, letting an unprivileged network attacker submit a fully-forged payload whose `owner.login` names the unprotected org but whose `repository.full_name` names a stack belonging to a different, "protected" organization.

### Finding Description
`verify_signature` resolves the signing organization purely from attacker-controlled payload content: [1](#0-0) [2](#0-1) 

The actual GitHub App/secret lookup and HMAC check happen in `GithubApp#verify_webhook_signature`, which explicitly treats a missing `webhook_secret` as "always verified": [3](#0-2) 

Shipit supports configuring one `webhook_secret` per organization (`config/secrets*.yml`), and the setup docs and example config both mark `webhook_secret` as *optional*, defaulting to `nil`: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (trivially, for the unprotected/nil-secret org), the raw JSON is dispatched to handlers, e.g. `PushHandler`, which resolves the target *stack* using a completely independent field of the same attacker-supplied body — `repository.full_name` — with no cross-check against the `owner.login`/`organization.login` value that was used to select the verifying secret: [6](#0-5) [7](#0-6) 

This is the exact bug class from the external report applied to Shipit's trust model: the value used to authenticate the request (the *organization* whose secret is checked) is not the value that binding the request should authorize (the *repository* that is written to / synced). In the Linea report, `_isNativeLayer` was trusted from the sender-controlled message without being cross-verified against the destination's own state, letting an attacker mint tokens for the wrong asset. Here, `repository.owner.login` is trusted to pick the verification key while `repository.full_name` is trusted to pick the write target, and nothing enforces `repository.full_name` actually belongs to `repository.owner.login`'s organization.

**Equality binding that should hold, but doesn't:**
`organization whose secret authenticated the payload == organization owning the repository/stack the handler mutates`

**Before attacker's request:** For a legitimately-delivered GitHub webhook, `repository.owner.login` and `repository.full_name`'s owner segment are always consistent because GitHub itself constructs the whole payload before signing it.

**After attacker's request:** Because the whole request body is attacker-controlled JSON (not individually signed per-field), and the org named by `owner.login` has no `webhook_secret` (so `verify_webhook_signature` short-circuits `true`), the attacker can freely set `repository.full_name` to any other organization's `owner/repo`, breaking the equality: the payload is "authenticated" for org A but its effects land on org B's stack.

### Impact Explanation
An unprivileged, unauthenticated attacker (the `/webhooks` endpoint requires no session or API token — only signature verification, per `authenticate_api_client`/`Authentication` are not used here) can:
- Trigger `PushHandler#process` against any stack in the system by naming its `repository.full_name`, forcing `Stack#sync_github`, which is the same mechanism that feeds continuous deployment (`Stack.schedule_continuous_delivery` deploys any stack flagged `continuous_deployment: true` once new commits are synced): [8](#0-7) 
- Similarly forge `pull_request`, `status`, `check_suite` or `membership` events against arbitrary repositories/teams, since none of those handlers validate that the target repository/organization matches the one whose secret gated the request.

This can result in an unauthorized deploy being queued for a stack the attacker does not control, satisfying the "Critical: unauthorized deploy" bar, contingent on the target stack having `continuous_deployment` enabled or another downstream action (merge, status manipulation) being reachable via the mismatched routing.

### Likelihood Explanation
This requires a specific but realistic and documented deployment shape: multi-organization Shipit configuration where at least one configured organization has `webhook_secret` unset (explicitly presented as optional/nil in the official setup docs and example secrets files). Given that shape, exploitation needs no credentials, no session, and no API token — only knowledge of the unprotected organization's name and the target stack's `owner/repo`, both of which are typically public information (Shipit's own repo listing/stack pages).

### Recommendation
- Cross-validate that `repository.full_name`'s owner segment matches the organization (`repository.owner.login` / `organization.login`) whose secret was used for HMAC verification, rejecting the webhook otherwise.
- Do not treat a missing `webhook_secret` as "always verified"; instead fail closed (reject) unless the operator has explicitly opted into an "unauthenticated webhooks" mode, and warn loudly when any configured organization lacks a secret in a multi-org setup.
- Have handlers resolve the target repository from the same trust-verified identity used for signature checking, rather than deriving it independently from attacker-supplied payload fields.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/organizations as in `test/dummy/config/secrets_double_github_app.yml`: `OrgOne` (attacker-visible, `webhook_secret: nil`) and `OrgTwo` (victim org with a real stack, e.g. `OrgTwo/victim-repo`), mirroring the documented "optional" webhook secret shown in `config/secrets.development.example.yml`.
2. Craft a JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/victim-repo"
  }
}
```
3. POST it to `/webhooks` with header `X-Github-Event: push` and any (or no) `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `OrgOne`, whose `webhook_secret` is `nil`, so `GithubApp#verify_webhook_signature` returns `true` unconditionally.
5. `PushHandler#process` resolves the target repository via `payload.dig('repository', 'full_name')` = `"OrgTwo/victim-repo"`, and triggers `Stack#sync_github` for the victim's stack — an action never authenticated for `OrgTwo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
