### Title
Missing Zero-Address Validation for Bridge Recipient Enables Permanent Burn of Bridged Funds - (File: `bridge/evm/contracts/BridgeVault.sol`)

### Summary
This is the same *"missing address validation before a fund-moving operation"* root cause as the Elys `MsgUpdateBrokerAddress.ValidateBasic` report, but manifesting in Sui's native token bridge. On the Sui→Ethereum claim path, the recipient address extracted from a signed bridge message is checked only for **length** (32 bytes on the Move side, 20 bytes on the EVM decode side) but never checked for being the **zero address**. When the recipient is `0x0`, `BridgeVault.transferETH` performs a low-level `call` that succeeds against an address with no code, silently and irrecoverably burning the withdrawn ETH.

### Finding Description
`BridgeUtils.decodeTokenTransferPayload` (and its V2 counterpart `BridgeUtilsV2.decodeTokenTransferPayloadV2`) only validate that the encoded `recipientAddress` is exactly 20 bytes long — there is no check that the decoded value is non-zero: [1](#0-0) 

That decoded `recipientAddress` flows unchecked into `SuiBridge.transferBridgedTokensWithSignatures` → `_transferTokensFromVault`, which also performs no zero-address check before dispatching the transfer: [2](#0-1) 

For the ETH path, `BridgeVault.transferETH` unwraps WETH and then does a raw low-level call to the recipient: [3](#0-2) 

A low-level `call{value: amount}("")` to `address(0)` **succeeds** (there is no code to execute, and EOA/empty-account transfers always succeed), so `require(success, ...)` does not catch it. The ETH is unwrapped from WETH and sent to `0x000...000`, which is unspendable — a permanent, irreversible burn of the bridged value.

On the Move/Sui side, nothing prevents a caller from specifying an all-zero `target_address` when constructing a token-transfer bridge message; `message.move`'s `create_token_bridge_message`-style constructors validate chain IDs and lengths but not that the address is non-zero: [4](#0-3) 

The committee will sign any well-formed, chain-valid message — it has no reason to reject a syntactically valid but semantically "burn" recipient address, so a message with recipient `0x00...00` will be legitimately co-signed and become claimable via `transferBridgedTokensWithSignatures`.

### Impact Explanation
This matches the allowed **High** impact class: *"unintended permanent burning below the 10B SUI cap"* / *"permanent fund lock."* Once funds are routed to `address(0)` through this path, they are permanently and irrecoverably destroyed with no recovery mechanism in the vault or bridge contracts.

### Likelihood Explanation
Likelihood is limited by the fact that specifying the zero address as one's own bridge recipient is typically a self-inflicted action (a misconfigured wallet, integration bug, or malformed client input) rather than something an attacker can use to steal funds from a third party — the sender chooses their own destination address on the Sui side. It is nonetheless a reachable, unprivileged, public-input flaw: no special role is required to trigger it, and no existing guard (length check, chain-id check, or committee signature check) rejects the zero address at any point in the pipeline (Move message construction → committee signing → EVM decode → vault transfer).

### Recommendation
Add explicit non-zero (and reserved-address) validation for the bridge recipient at the earliest possible point in the trust chain:
- In `bridge/sources/message.move`, assert the target address is non-zero when constructing token bridge messages.
- In `BridgeUtils.decodeTokenTransferPayload` / `BridgeUtilsV2.decodeTokenTransferPayloadV2`, `require(recipientAddress != address(0), ...)`.
- Defense in depth: add the same check in `SuiBridge._transferTokensFromVault` / `BridgeVault.transferERC20` / `BridgeVault.transferETH` before dispatching funds.

### Proof of Concept
1. On Sui, initiate a token bridge transfer (`send_token`-style call) specifying `target_address = 0x0000000000000000000000000000000000000000` (20 zero bytes, padded to the expected Sui/EVM target encoding) and a supported `destinationChainID`.
2. The Sui bridge module encodes this into a valid `BridgeMessage` (chain-id and length checks pass since only the *format*, not the *value*, is validated) — see `create_token_bridge_message`-style payload builders in `message.move`.
3. The bridge committee observes the valid on-chain event and produces valid signatures over the message (no additional recipient validation exists in Move-side checks).
4. Anyone calls `SuiBridge.transferBridgedTokensWithSignatures(signatures, message)` on Ethereum. `verifyMessageAndSignatures` passes, `decodeTokenTransferPayload` returns `recipientAddress = address(0)` (only the 20-byte length is checked), and `_transferTokensFromVault` calls `vault.transferETH(payable(address(0)), amount)`.
5. `BridgeVault.transferETH` unwraps WETH and executes `address(0).call{value: amount}("")`, which returns `success = true`. The `require(success, ...)` passes, `isTransferProcessed[nonce]` is marked true, and the withdrawn ETH is permanently lost at `0x0`.

/// Blocklist Message Format:
/// [message_type: u8]
/// [version:u8]
/// [nonce:u64]
/// [chain_id: u8]
/// [blocklist_type: u8]
/// [validator_length: u8]
/// [validator_ecdsa_addresses: byte[][]]
public fun create_blocklist_message(
    source_chain: u8,
    seq_num: u64,
    // 0: block, 1: unblock
    blocklist_type: u8,
    validator_ecdsa_addresses: vector<vector<u8>>,
): BridgeMessage {
    chain_ids::assert_valid_chain_id(source_chain);

    let address_length = validator_ecdsa_addresses.length();
    let mut payload = vector[blocklist_type, (address_length as u8)];
    let mut i = 0;

    while (i < address_length) {
        let address = validator_ecdsa_addresses[i];
        assert!(address.length() == ECDSA_ADDRESS_LENGTH, EInvalidAddressLength);
        payload.append(address);

        i = i + 1;
    };

    BridgeMessage {
        message_type: message_types::committee_blocklist(),
        message_version: CURRENT_MESSAGE_VERSION,
        seq_num,
        source_chain,
        payload,
    }
}
