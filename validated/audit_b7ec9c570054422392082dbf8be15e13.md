### Title
Webhook signature is verified against the payload's `repository.owner.login`, but every event handler dispatches on `repository.full_name` — allowing a webhook signed for Organization A to act on any repository/stack, including ones owned by a different onboarded organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `Shipit::GitHubApp` (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Every downstream handler, however, resolves the stack(s)/repository to mutate using a *different* field of the same JSON body: `payload.dig('repository', 'full_name')`. Nothing ties the verified `owner.login` to the `full_name` that is actually acted upon. In a multi-organization Shipit deployment (a configuration explicitly documented and supported), a webhook correctly signed with Organization A's secret can carry a `repository.full_name` pointing at Organization B's repository, and Shipit will process it as if it were legitimately from Organization B.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby

verified = github_app.verify_webhook_signature(
  request.headers['X-Hub-Signature'],
  request.raw_post
)
```
where `repository_owner` is: [2](#0-1) 

`verify_webhook_signature` in `GitHubApp` just checks the raw body against the org-specific `webhook_secret`: [3](#0-2) 

Once verification passes, `create` dispatches the parsed JSON to all handlers for the event: [4](#0-3) 

All handlers derive the target repository/stack purely from `repository.full_name`, unrelated to `repository_owner`: [5](#0-4) 

For example `PushHandler` uses `stacks` (i.e., `Repository.from_github_repo_name(repository_name)`) to trigger `stack.sync_github`: [6](#0-5) 

`PullRequest::OpenedHandler` independently re-derives the repository from `params.repository.full_name` to decide whether to auto-provision a review stack: [7](#0-6) 

The engine explicitly documents and supports hosting multiple, independently-configured GitHub Apps/organizations from a single Shipit instance, each with its own `webhook_secret`: [8](#0-7) 

**The broken binding, stated as an equality that the code assumes but never enforces:**
`organization used to authenticate the signature (repository_owner from repository.owner.login)` == `organization that owns the repository actually written to (derived from repository.full_name)`

Before the attacker's request: for legitimate GitHub-originated webhooks, `repository.owner.login` and `repository.full_name`'s org prefix are always consistent, because GitHub itself constructs the payload from the actual event source. Both sides of the equality coincide by construction, so the missing check is never observed in normal operation.

After the attacker's request: nothing in `verify_signature`, `create`, or any `Handler` subclass asserts that `full_name`'s org segment matches `repository_owner`. An attacker who can produce a validly-signed payload for *any one* organization configured in the same Shipit instance (e.g., they administer that org's GitHub App/webhook settings, or that org's webhook_secret otherwise leaks) can set `repository.full_name` to `OtherOrg/other-repo` while keeping `repository.owner.login`/`organization.login` equal to the org whose secret they hold. The signature check passes because it only validates the raw bytes against Org A's secret; the handler layer then blindly acts on `OtherOrg/other-repo`.

### Impact Explanation
This breaks the organization/repository trust boundary between tenants of a shared Shipit instance:
- Via `PushHandler`, an attacker can force `stack.sync_github(expected_head_sha: …)` on a stack belonging to a repository they have no legitimate access to, driving Shipit's view of the deployable HEAD for another org's stack (`app/models/shipit/webhooks/handlers/push_handler.rb`).
- Via `PullRequest::OpenedHandler`/`ReviewStackAdapter`, an attacker can trigger auto-provisioning of review stacks for a foreign repository if that repository has review-stack provisioning enabled (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`).
- Via `StatusHandler`, arbitrary commit statuses can be injected against commits of a foreign stack, which factor into CI-gated deploy checks (`app/models/shipit/webhooks/handlers/status_handler.rb`).

Depending on which handler is abused and how the target repository's `shipit.yml`/CI-gating is configured, this can influence which commit is considered deployable/mergeable, i.e., it can contribute to an unauthorized deploy or an unauthorized merge decision on a repository the attacker does not own — matching the Critical impact bucket ("cross-repository writes ... unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitation requires the attacker to possess a valid `webhook_secret` for at least one organization configured in the same multi-tenant Shipit instance (e.g., because they are a legitimate but lower-trust org admin on Org A, or that org's webhook config leaked) while targeting a repository belonging to Org B on the same instance. This is a realistic scenario specifically because the engine documents and supports hosting many independent organizations from one Shipit deployment; the org boundary is exactly the boundary Shipit purports to enforce via `Shipit.github(organization:)`/`github_teams`, yet the webhook signature-to-payload binding does not respect it. No GitHub App private key, `api_clients_secret`, or Shipit session is needed — only knowledge of one tenant org's webhook secret, which is a much weaker credential than full repository write access.

### Recommendation
After successfully verifying the signature, re-derive `repository_owner` from the same trusted source used for verification and assert that the organization portion of `payload.dig('repository', 'full_name')` (and any other org-identifying field used by handlers, e.g. `organization.login`) matches it before dispatching to handlers. Reject (422) the webhook if there is a mismatch. Alternatively, pass the verified `repository_owner` explicitly into each handler and have `Handler#repository_name`/`#stacks` scope lookups to that verified owner rather than trusting the unauthenticated `full_name` field independently.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`) with two organizations, `OrgA` and `OrgB`, each with its own GitHub App/`webhook_secret`.
2. As an attacker who controls (or has leaked) `OrgA`'s `webhook_secret` (e.g., an OrgA admin with access to the GitHub App's webhook settings, but with no access whatsoever to `OrgB`), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "full_name": "OrgB/private-repo", "owner": { "login": "OrgA" } }
}
```
3. Sign the raw body with `OrgA`'s `webhook_secret` using HMAC-SHA1, matching `DeliverySigner`/`verify_webhook_signature` semantics, and send it as `X-Hub-Signature` with `X-Github-Event: push` to `POST /github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: 'OrgA')` (from `repository.owner.login`) and successfully verifies the signature against `OrgA`'s secret: `app/controllers/shipit/webhooks_controller.rb:24-38`.
5. `create` dispatches to `PushHandler`, which resolves `stacks` from `payload.dig('repository', 'full_name')` = `"OrgB/private-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on OrgB's stack — despite the attacker never having any credential, secret, or access tied to OrgB.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
