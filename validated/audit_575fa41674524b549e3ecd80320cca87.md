### Title
`status` webhook updates commits across every stack sharing a SHA, not just the authenticating repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with a bare, cross-stack `Commit.where(sha: params.sha)` lookup, with no repository/stack scoping tied to the webhook's authenticated origin. Combined with `review_stacks_enabled: true, allow_all` auto-provisioning review stacks (whose base history shares SHAs with the canonical stack), a webhook that is validly signed for one repository/organization can still write a `Status` onto a `Commit` belonging to a different stack that merely happens to share the SHA.

### Finding Description
The broken binding: the code assumes `Commit#sha == authenticated_repository`, i.e. that a `sha` in a signed webhook can only belong to the repository whose secret produced that signature. In reality `sha` is a global, attacker-chosen string and `Commit` records are scoped per `stack_id`, not globally unique.

Path:
1. `Shipit::WebhooksController#create` parses JSON and dispatches to `Webhooks.for_event('status')` → `StatusHandler`. [1](#0-0) 
2. `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` (attacker-supplied JSON) and validates the signature using `Shipit.github(organization: repository_owner)`'s webhook secret. [2](#0-1) [3](#0-2) 
3. `GitHubApp#verify_webhook_signature` only checks the HMAC against that organization's `webhook_secret`; it never cross-checks that the `sha` field, or any commit resolved from it, actually belongs to a repository under that organization. [4](#0-3) 
4. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a bare SHA match against the entire `commits` table, with no `stack_id`/repository filter at all. [5](#0-4) 
5. `Commit#create_status_from_github!` writes a `Status` for whatever `stack` that matched commit belongs to, and that write drives `deployable?`, `blocked?`, and `schedule_continuous_delivery`/merge queue behavior for that stack. [6](#0-5) [7](#0-6) [8](#0-7) 

Exploit flow: an attacker who owns or forks a repository can obtain a validly-signed `status` webhook for their own org (they know or can independently register a GitHub App/webhook secret for their own repository). If `review_stacks_enabled: true, allow_all` is set on a victim stack, opening a PR against that stack auto-provisions a review stack whose base commits are the same underlying Git objects (same SHA) as the canonical/production stack's history, because both stacks sync from the same upstream Git ancestry. The `Commit` rows across those different `stack_id`s legitimately can carry the identical `sha` string. The attacker sends `POST /webhooks` with `X-Github-Event: status`, a payload whose `repository.owner.login` matches an org they control (so the signature check passes), but whose `sha`/`context: ci/smoke`/`state: success` matches a commit that also exists (by SHA) in the victim's stack. Because `StatusHandler#process` iterates `Commit.where(sha: ...)` unfiltered by repository, every stack with a matching commit SHA — including the victim's — gets a new `success` `Status`, potentially flipping `deployable?` for the victim's commit and triggering `schedule_continuous_delivery`/merge processing there.

Existing guards do not close this: `verify_signature` authenticates only the claimed organization from the attacker-controlled payload field, not a binding between that organization and the `sha` being asserted; `drop_unhandled_event`, `ExplicitParameters` (the `params do ... end` schema in `StatusHandler`) only validate types/presence, not repository scoping; there is no `Repository`/`Stack` lookup or `require_permission!` anywhere in this handler.

### Impact Explanation
A successfully forged/cross-repo `status` event lets an unprivileged GitHub user flip CI/deployability state (`ci/smoke: success`) for a commit belonging to a stack they do not own, provided that stack shares a commit SHA with a repository the attacker legitimately controls (trivially achievable via `review_stacks_enabled: true, allow_all`, since forks/PR branches share upstream commit history/SHAs with the base repo). This can unblock a required status check and enable an unauthorized deploy/merge decision on the victim stack — "a payload for one repository mutating another's stack, commit... or an unauthorized deploy" — matching the Critical impact category. It is repeatable against any stack sharing SHAs with an attacker-controlled repository, and the blast radius scales with how many stacks/tenants ingest commits from a shared upstream (monorepo forks, review-stack fan-out).

### Likelihood Explanation
Preconditions: the victim stack must have `review_stacks_enabled: true` with `allow_all` (or otherwise share commit ancestry/SHAs with a repo the attacker controls); the attacker needs only the ability to open a PR/fork a repo and obtain a validly-signed webhook for their own org (something any GitHub user with a repo can normally set up if the Shipit instance's GitHub App secret is per-organization and attacker owns that org, or trivially if a shared/global webhook secret is used across organizations, which is common in some deployments). No Shipit session, API token, or team membership is required. The cost is a single crafted HTTP POST with correct HMAC for the attacker's own org context, replayable at will.

### Recommendation
Scope `StatusHandler#process` (and any similar bare `Commit.where(sha: ...)` cross-stack lookups) by the authenticated repository: resolve the target `Stack`/`Repository` from the verified webhook context (e.g., match `params.dig('repository','full_name')` against the `Repository`/`Stack` actually configured with that `GithubHook`/webhook secret) and restrict the `Commit` lookup to `stack.commits.where(sha: params.sha)` for that specific repository, rather than a global SHA match. Additionally, bind `verify_signature`'s organization/repository claim to the repository that owns the specific `GithubHook` record whose secret validated the signature, instead of trusting the payload's `repository.owner.login` for downstream authorization decisions.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "a status webhook only affects commits belonging to the authenticating repository's stack" do
  victim_stack = shipit_stacks(:shipit) # review_stacks_enabled: true, allow_all
  attacker_stack = shipit_stacks(:cyclimse) # different repository/org

  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  # LHS of the invariant: only attacker_stack's commit should change
  assert_equal "unknown", victim_commit.reload.status.state
  assert_equal "unknown", attacker_commit.reload.status.state

  params = ActionController::Parameters.new(
    sha: shared_sha, state: "success", context: "ci/smoke"
  )
  Shipit::Webhooks::Handlers::StatusHandler.new.call(params) # simulates POST /webhooks with a signature valid only for attacker's org

  # RHS: assert divergence — victim_commit changed despite the webhook only being authenticated for attacker's repo
  assert_equal "success", attacker_commit.reload.status.state   # expected
  assert_equal "unknown", victim_commit.reload.status.state, # THIS FAILS today: victim_commit also becomes "success"
    "status webhook for one repo must not affect another stack's commit"
end
```
This demonstrates that `Commit.where(sha: params.sha)` in `app/models/shipit/webhooks/handlers/status_handler.rb` [5](#0-4)  writes to `victim_commit` even though the webhook was never authenticated for `victim_stack`'s repository, breaking the stated invariant "a `ci/smoke` status affects only the repository that authenticated it."

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
