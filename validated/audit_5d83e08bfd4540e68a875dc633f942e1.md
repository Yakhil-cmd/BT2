### Title
Webhook signature is verified against the organization named in the payload while the write actions (commit status, push sync) are scoped to a repository/commit named elsewhere in the same unsigned-at-verification-time payload, enabling cross-repository forgery - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb, app/models/shipit/webhooks/handlers/push_handler.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to HMAC-verify a webhook against using `repository_owner`, a value read straight out of the untrusted JSON body. The actual mutation performed by the handler (`StatusHandler#process`, `PushHandler#process`) is scoped by a *different* field of the same body (`sha` globally, or `repository.full_name`), which is never required to correspond to the organization whose secret validated the request. Any principal who can produce a validly-signed webhook for **one** configured GitHub organization on the Shipit instance can forge events that write to **any other** repository/stack/commit tracked by that instance.

### Finding Description
The binding that should hold is: `organization whose secret authenticated the webhook == repository/commit that the webhook payload is permitted to mutate`. This binding is broken.

1. `WebhooksController#verify_signature` derives the signing organization purely from body content, before any cryptographic check has succeeded: [1](#0-0) [2](#0-1) 

2. `GithubApp#verify_webhook_signature` only checks that the HMAC over the *entire* raw body matches the secret configured for that one organization: [3](#0-2) 

3. Once verification passes (using organization A's secret), the handler that actually performs the write does not re-check that field against organization A at all:
 - `StatusHandler#process` writes a CI status to any `Commit` matching `sha`, with **no repository/owner scoping whatsoever**: [4](#0-3) 
 - `PushHandler#process` and the base `Handler#stacks`/`Handler#repository_name` resolve the affected stack from `repository.full_name`, a body field independent from `repository.owner.login` used for signature routing: [5](#0-4) [6](#0-5) 

Because Shipit is explicitly designed to be multi-tenant (multiple independent GitHub organizations, each with its own `webhook_secret`, can be configured on one instance): [7](#0-6) 

an attacker who legitimately controls (or is an admin of) one onboarded organization "A" — and therefore knows/can trigger a validly-signed webhook for A — can send a `push` or `status` webhook whose signature is computed over a payload where `repository.owner.login` = "A" (so it verifies against A's secret) but `repository.full_name` (for push) or `sha` (for status, no scoping at all) references a repository/commit belonging to an entirely unrelated organization "B" tracked by the same Shipit instance. Signature verification succeeds because the HMAC only proves "this body was signed with A's secret" — it says nothing about which repository the body is allowed to reference — yet the resulting side effect (syncing commits/triggering `sync_github`, or fabricating a `commit_status`) is applied to organization B's stack.

This is the structural analog of the reported bug class: a value that is checked/authenticated (the organization tied to the verified signature) is not the same value that is subsequently acted upon (the repository/commit written to), and the code never re-derives or re-checks the acted-upon value against the authenticated one.

### Impact Explanation
- Via `StatusHandler`, an attacker with a validly-signed webhook for any one onboarded org can forge a `success` commit status for a commit sha in a completely different, unrelated tracked repository/stack. Since Shipit's merge-queue/CI-gating and deploy eligibility logic relies on `Commit` statuses, this can be used to fabricate green CI on a victim repository and enable an unauthorized deploy or merge-queue advancement — matching the "unauthorized deploy, rollback or merge" / cross-repository write impact tier.
- Via `PushHandler`, the same cross-org confusion can trigger `stack.sync_github` for a victim's stack using attacker-controlled `after` (expected head sha), affecting sync state of a repository the attacker does not own.
- This does not require compromising `GITHUB_TOKEN`, an `ApiClient` token, or `webhook_secret` of the *target* organization — only possession of a secret for *any* organization configured on the same multi-tenant Shipit instance, which is a materially weaker credential than "repository write access to the victim repo" and crosses the credential/repository boundary the rules describe.

### Likelihood Explanation
Requires: (a) the Shipit instance to host more than one GitHub organization (documented supported configuration), and (b) the attacker to control or compromise the webhook secret of at least one of those organizations (e.g., as a legitimate but lower-trust tenant/org admin on a shared Shipit deployment). This is a realistic operating mode for shared/self-hosted Shipit instances serving multiple teams/orgs, which is explicitly supported by the config format shown in `config/secrets.development.shopify.yml`.

### Recommendation
- In `StatusHandler` and any other handler that resolves a target `Commit`/`Stack` from webhook payload fields, scope the lookup by the organization that was cryptographically verified (`repository_owner` used in `verify_signature`), not solely by `sha` or `full_name` taken from an independent part of the body.
- Reject (422) any webhook whose `repository.full_name` organization segment does not match the organization whose secret validated the signature, closing the gap between the authenticated identity and the entity being written to.
- For `StatusHandler` specifically, add repository-level scoping (e.g., require and check `payload.dig('repository','full_name')` against the `Commit`'s stack's repository) before applying the status update.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (as supported per `config/secrets.development.shopify.yml`).
2. As an admin/holder of `org-a`'s webhook secret, craft a `status` event JSON body:
```json
{
  "sha": "<commit-sha-belonging-to-org-b-repo>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "org-a" } }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac_sha1(org_a_webhook_secret, body)>` and POST to `/github/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s `GithubApp`, and the signature verifies successfully (see `lib/shipit/github_app.rb:76-83`).
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then finds `Commit.where(sha: params.sha)` — matching the commit that actually belongs to `org-b`'s repository — and calls `create_status_from_github!`, writing a forged `success` status onto org B's commit despite the webhook only ever being authenticated as belonging to org A.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
