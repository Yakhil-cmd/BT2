### Title
Stale `index-cache` after `socialize-debt` lets zToken collateral be over-valued for the rest of the block - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`v0-4-market.clar` caches vault `{index, lindex}` per `{timestamp, aid}` so that multiple operations in the same block avoid repeated cross-contract accrual calls [3](#0-2) . The cache is populated by whichever caller happens to touch that asset first in the block and is blindly reused (cache HIT) by every other caller for the remainder of that block, without re-checking whether the vault's underlying state changed. The vault's `socialize-debt` function writes a permanently reduced `lindex` directly into vault storage when bad debt is written off, independent of the market's cache [4](#0-3) . If `index-cache` was primed before `socialize-debt` executes in the same block, later market calls in that block keep using the old, higher `lindex`.

### Finding Description
`accrue-and-cache` is the single choke point market operations use to get vault indexes: on a cache hit it returns the stored value without calling the vault at all [3](#0-2) . This cache is used both for debt-index-based scaled-debt accounting and for zToken collateral valuation (`accrue-user-collateral`/`accrue-and-cache` on the underlying vault id for zTokens) [5](#0-4) .

`socialize-debt` on the vault reduces `lindex` proportionally to the loss taken by the vault when bad debt is written off, and updates `principal-scaled`/`total-borrowed`/`assets` accordingly — but it does not go through `accrue-and-cache`, and it has no way to invalidate the market's already-populated cache entry for that `{timestamp, aid}` key [4](#0-3) .

Sequence within one block:
1. Attacker (or any user) calls a market op (e.g. `collateral-add`) that touches a zToken and primes `index-cache` for that vault's `{timestamp, aid}` with the pre-loss `lindex`.
2. A liquidation elsewhere in the same block realizes bad debt and the market/liquidation flow triggers `socialize-debt` on the vault, permanently lowering the real `lindex` to reflect the loss to suppliers.
3. Because `index-cache` was already primed in step 1, any subsequent market call in the same block (e.g. attacker's own `borrow` or `collateral-add`/health check) reads the stale, higher `lindex` from the cache instead of the vault's true, written-down value.

The victim here is the pool of other suppliers/borrowers: the attacker's collateral (denominated in zTokens whose value depends on `lindex`) is valued using the pre-writedown exchange rate for the rest of the block, letting the attacker borrow against value that no longer exists after the loss was socialized, and pushing the resulting undercollateralization/insolvency onto the rest of the pool's suppliers. Note the shared state is `index-cache`, keyed only by `{timestamp, aid}` with no versioning against the vault's actual `lindex`/`last-update`, so it cannot detect that the underlying vault state changed mid-block.

### Impact Explanation
This falls under protocol insolvency / temporary freezing-of-funds impact: the attacker extracts borrowing capacity based on a stale, inflated zToken exchange rate right after (in the same block as) a bad-debt socialization event, worsening the shortfall that must ultimately be absorbed by all suppliers of the affected vault.

### Likelihood Explanation
Requires precise same-block ordering: an attacker (or opportunistic bot) must have zToken collateral touched right when a socialize-debt-triggering liquidation lands in the same block, and must front-run/back-run the market interaction relative to the liquidation. This is a narrow but realistic MEV-style ordering window since block producers/sequencers control tx ordering within a block, and `socialize-debt` is a normal liquidation-driven event, not attacker-controlled directly.

### Recommendation
Invalidate or bypass the `index-cache` entry whenever `socialize-debt` (or any vault call that mutates `lindex`/`index` outside `accrue-and-cache`) executes within the same block — e.g., have `socialize-debt` call back into the market to `map-delete` the corresponding `index-cache` key, or key the cache additionally on a vault-side monotonically increasing "state version" counter that `socialize-debt` bumps, so any cache entry created before the writedown is treated as stale.

### Proof of Concept
1. Block N, Tx1: Attacker calls `collateral-add` supplying zToken X; this calls `accrue-and-cache` for X's underlying vault, populating `index-cache-{N, aid-X}` with `lindex = L0`.
2. Block N, Tx2: A separate liquidation on the same vault triggers `socialize-debt`, reducing real vault `lindex` to `L1 < L0` to reflect a loss.
3. Block N, Tx3: Attacker calls `borrow` (or another `collateral-add`) using the same zToken X as collateral; `accrue-and-cache` hits the cache and returns the stale `L0` instead of `L1`.
4. The health check in `borrow`/`collateral-add` values the attacker's zToken collateral using `L0`, letting them borrow more than the post-loss collateral value supports, with the shortfall ultimately borne by the vault's other suppliers.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))

    (print {
      action: "socialize-debt",
      caller: contract-caller,
      data: {
        scaled-amount: scaled-amount,
        debt-reduction: debt-reduction,
        principal-reduction: principal-reduction,
        old-lindex: current-lindex,
        new-lindex: new-lindex,
        old-total-assets: old-total-assets,
        principal-scaled: (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0),
        total-borrowed: (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0),
        index: idx
      }
    })

    (ok true)))

(define-private (accrue-collateral-asset
  (coll-entry { aid: uint, amount: uint })

    (if (is-ztoken aid)

                        (if (is-eq aid zsBTC) sBTC
                        (if (is-eq aid zstSTX) stSTX
                        (if (is-eq aid zUSDC) USDC
                        (if (is-eq aid zUSDH) USDH
                        (if (is-eq aid zstSTXbtc) stSTXbtc
                        ;; will cause ERR-UNKNOWN-VAULT with any value over 64
                        u100))))))))

            (unwrap-panic (accrue-and-cache vault-id))
            acc))
