### Title
`handleERC20Transfer` / `handleERC721Transfer` Accept Arbitrary `_tokenAddress` Without Registered-Token Validation — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

`handleERC20Transfer` and `handleERC721Transfer` enforce `onlyOperators` but omit the `onlyRegisteredToken` guard that is present on every request-side path. The two access controls — operator identity and token registration — are checked independently on different code paths rather than being jointly enforced on every asset-moving call. A single operator (default threshold = 1) can therefore call either handle function with an arbitrary `_tokenAddress`, causing the bridge to mint or transfer tokens for a contract that was never whitelisted.

---

### Finding Description

`BridgeTransferERC20._requestERC20Transfer` and `BridgeTransferERC721._requestERC721Transfer` both carry the `onlyRegisteredToken(_tokenAddress)` modifier, ensuring that only tokens explicitly registered by the owner can be deposited into the bridge. [1](#0-0) [2](#0-1) 

The corresponding handle functions — `handleERC20Transfer` and `handleERC721Transfer` — carry only `onlyOperators` and perform no token-registration check at all: [3](#0-2) [4](#0-3) 

`_tokenAddress` is a caller-supplied parameter. After the operator check passes and `_voteValueTransfer` reaches threshold, the contract unconditionally calls either:

- `ERC20Mintable(_tokenAddress).mint(_to, _value)` / `ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(...)` (in `modeMintBurn = true`), or
- `IERC20(_tokenAddress).safeTransfer(_to, _value)` / `IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId)` (in `modeMintBurn = false`)

on whatever address the operator supplied.

The `BridgeOperator` constructor sets the default threshold to **1** for all vote types: [5](#0-4) 

So a single operator can reach threshold and execute the transfer without any co-signer.

The vote key in `_voteValueTransfer` is `keccak256(msg.data)`, which binds the vote to the exact calldata: [6](#0-5) 

This prevents vote-mixing across different parameter sets, but it does not compensate for the missing `onlyRegisteredToken` guard — an operator simply submits calldata that contains the unregistered token address and the vote immediately closes at threshold 1.

---

### Impact Explanation

**`modeMintBurn = true` (mint/burn bridge):** The bridge holds minting rights on registered tokens. If a token is deregistered (or was never registered), the bridge may still retain its minter role. An operator can call `handleERC20Transfer` with that token address and mint an arbitrary `_value` to any `_to` address, inflating supply and draining value from legitimate holders.

**`modeMintBurn = false` (lock/unlock bridge):** The bridge holds token balances. Any ERC20/ERC721 tokens sitting in the bridge contract — including deregistered tokens or tokens accidentally sent directly — can be drained by an operator calling the handle function with the corresponding address.

In both cases the corrupted value is a real token balance or minted supply: an unauthorized transfer or mint of bridged assets.

---

### Likelihood Explanation

- Default operator threshold is 1; a deployment that never raises the threshold is immediately exploitable by the single registered operator.
- Even with threshold > 1, a subset of colluding operators below the "majority-validator collusion" bar (e.g., 2-of-3) can execute the attack.
- The attack requires no external precondition beyond operator registration, which is a normal operational step.
- The `deregisterToken` path (owner removes a token but bridge retains its balance or minting rights) creates a realistic trigger that does not require any key compromise.

---

### Recommendation

Add `onlyRegisteredToken(_tokenAddress)` to both handle functions, mirroring the request side:

```solidity
// BridgeTransferERC20.sol
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,
    ...
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // ADD
{
    ...
}
```

```solidity
// BridgeTransferERC721.sol
function handleERC721Transfer(
    ...
    address _tokenAddress,
    ...
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // ADD
{
    ...
}
```

Optionally also add `onlyUnlockedToken(_tokenAddress)` to prevent handling of locked tokens, consistent with the request-side invariant. [7](#0-6) 

---

### Proof of Concept

Setup: bridge deployed with `modeMintBurn = false`, one operator (default threshold = 1), token `T` registered and then deregistered (bridge still holds 1000 T).

```
// 1. Owner registers token T, users deposit 1000 T into bridge.
bridge.registerToken(T, cT);
// ... users deposit ...

// 2. Owner deregisters T (e.g., token migration).
bridge.deregisterToken(T);
// Bridge still holds 1000 T; registeredTokens[T] == address(0).

// 3. Operator drains the bridge.
bridge.handleERC20Transfer(
    bytes32(0),          // _requestTxHash (arbitrary, not yet handled)
    address(0),          // _from (irrelevant)
    attacker,            // _to
    T,                   // _tokenAddress — NOT registered, no check
    1000 ether,          // _value
    999,                 // _requestedNonce (above lowerHandleNonce)
    block.number,
    ""
);
// Threshold = 1 → _voteValueTransfer returns true immediately.
// IERC20(T).safeTransfer(attacker, 1000 ether) executes.
// Bridge balance of T: 0. Attacker balance: 1000 T.
```

The same pattern applies to `handleERC721Transfer` and to the `modeMintBurn = true` case (replace `safeTransfer` with `mint`).
