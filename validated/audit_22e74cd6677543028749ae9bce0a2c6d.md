### Title
Direct SPL `burn` on LP-token accounts desynchronizes `PoolState.lp_supply` from real circulating supply, permanently trapping vault funds - (File: `programs/cp-swap/src/instructions/withdraw.rs`)

### Summary
The report's bug class — an external actor burning tokens through a path that doesn't update the tracked total-supply counter — has a direct analog in this AMM. `PoolState.lp_supply` is a program-maintained counter that is only incremented/decremented inside the `deposit`/`withdraw` instructions via `pool_state.lp_supply.checked_add/checked_sub`, not derived from the actual LP mint's on-chain supply. Because any LP holder fully owns their `owner_lp_token` account, they can call `spl_token`/`token_2022`'s `Burn` instruction directly (bypassing the Raydium CP-swap program entirely) to destroy LP tokens without ever going through `withdraw`. This desynchronizes `pool_state.lp_supply` (used as the denominator in the constant-product LP↔trading-token conversion) from the real circulating LP supply.

### Finding Description
`lp_supply` is explicitly documented as "True circulating supply without burns and lock ups" and is stored on `PoolState`: [1](#0-0) 

It is only ever mutated inside the program's own instructions — incremented in `deposit`: [2](#0-1) 

and decremented in `withdraw`, paired with a `token_burn` CPI: [3](#0-2) 

The `token_burn` helper itself is a thin CPI wrapper with no linkage back to `pool_state.lp_supply` — it simply issues a `Burn` instruction with the LP token owner as authority: [4](#0-3) 

Because the LP mint's `Burn` instruction only requires the token account owner's signature (not the pool authority PDA or any Raydium-specific gate), an LP holder can submit a standalone `spl_token::Burn` / `token_2022::Burn` transaction against their own `owner_lp_token` account, reducing the mint's real `supply` field without ever touching `programs/cp-swap/src/instructions/withdraw.rs`. `pool_state.lp_supply` is left unchanged, exactly mirroring the reported `GolemTokenNetworkBatching.burn()` flaw where burned tokens are removed from circulation but the tracked `totalSupply` isn't updated.

Both `deposit` and `withdraw` use `pool_state.lp_supply` as the divisor in `CurveCalculator::lp_tokens_to_trading_tokens`: [5](#0-4) 

so once `lp_supply` overstates the real circulating LP supply, every subsequent withdrawal computes `token_amount = lp_token_amount / lp_supply * vault_amount`, i.e. a share strictly smaller than the holder's true proportional claim on the vaults.

### Impact Explanation
Once the real supply is permanently below the recorded `lp_supply`, the sum of everyone's true proportional claims (based on their actual, non-burned LP balances divided by the inflated `lp_supply`) can never add up to 100% of the vault balances. As LP holders redeem via `withdraw`, the last holder(s) will receive less than the full remaining vault amount, and the residual token_0/token_1 balance becomes permanently unclaimable — no LP tokens exist anymore to redeem it, and there is no admin/sweep path for this dust. This is a permanent freezing of LP funds inside the pool's vaults, growing in proportion to however much LP supply is destroyed via direct burns.

### Likelihood Explanation
Any unprivileged liquidity provider who holds LP tokens can trigger this with a single, unprivileged transaction calling the standard SPL Token / Token-2022 `Burn` instruction on their own `owner_lp_token` account — no interaction with the Raydium program, no special permissions, and no validator/off-chain assumptions required. The only "cost" to the attacker is giving up their own LP position, but this can be done with a trivial amount of LP tokens to permanently lock a proportional amount of pool funds, and is not something any other user or the protocol can prevent or reverse.

### Recommendation
Do not rely on a program-maintained `lp_supply` counter that can be bypassed by direct SPL `Burn` calls. Instead, always read the LP mint's actual `supply` field (`lp_mint.supply`) at the time of `deposit`/`withdraw` computations instead of, or reconciled against, `pool_state.lp_supply`, so any externally-burned tokens are immediately reflected in the curve math. Alternatively, restrict burn authority on the LP mint/token accounts so LP tokens can only be destroyed through the program's own `withdraw` instruction (e.g., by requiring a delegate/authority check that routes all burns through `token_burn` in `programs/cp-swap/src/utils/token.rs`).

### Proof of Concept
1. LP holder Alice deposits liquidity via `deposit`, receiving `X` LP tokens; `pool_state.lp_supply` becomes `S`.
2. Instead of calling the program's `withdraw`, Alice submits a standalone transaction invoking `token_2022::burn` (or `spl_token::burn`) directly on her `owner_lp_token` account for amount `B` (`B < X`), authorized by her own signature as token account owner. This is accepted by the SPL Token program with no dependency on the Raydium program.
3. `lp_mint.supply` decreases by `B`, but `pool_state.lp_supply` (still `S`) is untouched, since only `programs/cp-swap/src/instructions/withdraw.rs:178` decrements it and that code path was never executed.
4. All subsequent `withdraw` calls by any LP now compute `lp_tokens_to_trading_tokens(lp_token_amount, pool_state.lp_supply=S, ...)`, understating each holder's true share by a factor of `S / (S-B)`.
5. As all remaining LP tokens are eventually redeemed, a residual balance proportional to `B` remains in `token_0_vault`/`token_1_vault` that no existing LP token can ever claim, permanently freezing that portion of pool funds.

pub fn token_burn<'a>(
    authority: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    from: AccountInfo<'a>,
    amount: u64,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    token_2022::burn(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::Burn {
                from,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
    )
}
