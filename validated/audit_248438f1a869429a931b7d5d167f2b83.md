### Title
Webhook signature verification is bound to `repository.owner.login`, not to `repository.full_name` the handlers act on, allowing cross-organization forged events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body, while every event handler (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolves the repository/stack to mutate using a *different* field of the same body, `repository.full_name`. Nothing binds these two fields together, so an org that legitimately owns one webhook secret can sign a payload whose `full_name` points at a different organization's repository, and have it processed as if it came from GitHub for that other repository.

### Finding Description
`verify_signature` picks the GitHub App/secret to validate against like this: [1](#0-0) 

`repository_owner` is read straight from the still-unverified body: [2](#0-1) 

Once the signature "passes" (i.e. matches *some* configured org's secret), the entire parsed body is dispatched to all handlers registered for the event, with no re-scoping to the org that was used to verify it: [3](#0-2) 

Every handler, however, determines *which repository/stack to act on* using a different field entirely, `repository.full_name`: [4](#0-3) 

For example `PushHandler` forces a resync of any stack under that `full_name`: [5](#0-4) 

and `StatusHandler` writes a GitHub commit status onto *any* commit matching a `sha`, with no repository scoping check at all: [6](#0-5) 

Shipit explicitly supports one independent `webhook_secret` per GitHub organization for multi-tenant installs, which is exactly the configuration that lets an authenticated-but-unprivileged org holder mint valid signatures at will: [7](#0-6) [8](#0-7) 

The broken binding, expressed as an equality that no longer holds:
`organization whose webhook_secret verified the signature == organization/repository (repository.full_name) whose Stack/Commit the handler mutates`

### Impact Explanation
In a multi-org Shipit instance (the documented "Using Multiple GitHub Applications" configuration), the administrator of Org A — who legitimately possesses Org A's `webhook_secret` because they configured GitHub's webhook delivery for their own org, and who has zero privileges over Org B's repositories/stacks in the same instance — can HMAC-sign an arbitrary crafted payload with Org A's secret while setting `repository.full_name` (and other fields such as `sha`) to reference Org B's repository/commit. Handlers such as `StatusHandler` will then create a forged "success" commit status on Org B's commit, which can flip `Commit#deployable?`/`required_statuses` gating and lead to an **unauthorized deploy of another organization's stack**, or `PushHandler`/`CheckSuiteHandler` can be abused to force syncs/refreshes on stacks the attacker doesn't own. This is a cross-organization write achieved purely by exploiting the mismatch between the signature-verification identity and the identity the handler code actually trusts — no `ApiClient` token, GitHub App private key, or Shipit session is required.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with the documented multi-organization GitHub App schema (an intended, supported configuration, not an undocumented deployment), and (2) the attacker being a legitimate holder of one org's `webhook_secret` (any org admin who onboarded their own org into that Shipit instance) but having no rights on the target org. Given that, forging the HTTP request is trivial — no GitHub interaction is needed at all, only a raw POST with a correctly computed `sha1=` HMAC using their own known secret.

### Recommendation
Bind the two identities together explicitly: after selecting the GitHub App/secret via `repository_owner`, re-verify that every field the handlers subsequently trust (`repository.full_name`'s owner segment, or `organization.login`) is consistent with that same `repository_owner`, and reject the request (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` using the already-authenticated organization identity rather than re-parsing an independent field of the unverified-at-that-point body, and have handlers reject any repository whose owner does not match the organization that authenticated the webhook.

### Proof of Concept
1. Deploy Shipit with the multi-org config schema, e.g. two orgs `OrgA` (attacker-controlled, `webhook_secret: secretA`) and `OrgB` (victim, has a stack with a locked/undeployable commit `deadbeef`).
2. Attacker computes `sig = HMAC-SHA1(secretA, body)` for:
   ```json
   {
     "sha": "deadbeef",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status` and `X-Hub-Signature: sha1=<sig>`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, verifies with `secretA`, passes.
5. `StatusHandler#process` runs against `Commit.where(sha: "deadbeef")` — which belongs to `OrgB` — and creates a `success` status, independent of which org the signature was for.
6. If this satisfies `OrgB`'s required statuses, an unauthorized deploy of `OrgB`'s stack becomes possible without any credential belonging to `OrgB`.

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
