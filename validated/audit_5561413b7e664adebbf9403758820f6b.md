## Title
Stack-scoped ApiClient tokens can read any stack's build status via CCMenu, bypassing the stack authorization binding - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup helper inherited from `BaseController` in a way that discards the per-`ApiClient` stack scoping, so any valid `ApiClient` token — even one deliberately restricted to a single stack — can query the CCMenu status endpoint for **any** stack in the installation.

### Finding Description
`Shipit::Api::BaseController` enforces the binding "the stacks an `ApiClient` may touch == the stacks it was scoped to" through the `stacks` helper: [1](#0-0) 
`stacks` restricts the queryable relation to `current_api_client.stack_id` when the client is stack-scoped, and every other resource controller (`StacksController`, `DeploysController`, `HooksController`, `MergeRequestsController`, `TasksController`, etc.) resolves its `stack` through this scoped relation, e.g. `stacks.from_param!(params[:id])`.

`CCMenuController`, however, defines its own private `stack` method that ignores this scoping entirely and resolves the stack directly from the global `Stack` model: [2](#0-1) 

`require_permission :read, :stack` only checks that the `ApiClient`'s `permissions` array contains `read:stack` — it never checks which stack that permission applies to: [3](#0-2) 

The only authorization/scoping mechanism for a stack-restricted client is the `stacks` helper in `BaseController`, and `CCMenuController` bypasses it entirely by calling `Stack.from_param!(params[:stack_id])` directly, and by also allowing authentication via a query-string `token` param (`authenticate_api_client`), which is confirmed to work in the test suite: [4](#0-3) [5](#0-4) 

This breaks the equality: `stack(s) an ApiClient token authorizes == stack(s) the request actually touches`. A token created and scoped to Stack A (e.g. fixture `here_come_the_walrus`, which is explicitly scoped to `shipit_stacks(:shipit)`) can hit `GET /ccmenu/*stack_id?token=<token>` with `stack_id` set to Stack B and receive Stack B's CCMenu XML, even though the token was never granted access to Stack B.

### Impact Explanation
This is a low-privileged-attacker-reachable authorization boundary bypass: possession of any `read:stack`-permissioned `ApiClient` token (however narrowly scoped by its creator) is sufficient to read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock status, etc.) for every stack managed by the Shipit instance, not just the one the token owner intended to authorize. This is an unauthorized cross-stack read of stack state, matching the documented High-impact category ("escalation into `Shipit.github_teams` authorization ... unauthenticated read of stack state, task streams or deploy output" in spirit — here it is an authorization-scope escalation rather than fully anonymous access, since a valid, otherwise-limited token is required).

### Likelihood Explanation
Any organization that issues stack-scoped `ApiClient` tokens for narrow purposes (e.g., embedding CCMenu URLs in CI dashboards) is exposed. Exploitation only requires a valid token with `read:stack` and knowledge/guessing of another stack's `stack_id` (owner/repo/branch/env path), no special privileges or additional credentials are needed.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` relation used everywhere else in the API (i.e., `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`), so that stack-scoped `ApiClient` tokens cannot resolve stacks outside their `stack_id` scope.

### Proof of Concept
1. Create an `ApiClient` scoped to Stack A with permission `read:stack` (as in fixture `here_come_the_walrus`, scoped to `shipit_stacks(:shipit)`).
2. As the holder of that token, issue: `GET /ccmenu/<stack_B_owner>/<stack_B_repo>/<stack_B_branch>?token=<token_scoped_to_A>`.
3. Observe that `CCMenuController#show` renders Stack B's project XML (build status, activity, last build label) despite the token never being granted `read:stack` on Stack B — because `stack` resolves via unscoped `Stack.from_param!` rather than the scoped `stacks` relation used by `BaseController`.
