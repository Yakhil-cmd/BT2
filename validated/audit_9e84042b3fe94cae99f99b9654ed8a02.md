### Title
`BASH_ENV` injection via unfiltered PR label names reaching `tasks.<name>.steps` process env - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as `"true"` into the stack's environment with no allowlist, and `TaskCommands#env`/`DeployCommands#env` merge `@stack.env` directly (unfiltered by `TaskDefinition#filter_envs`/`EnvironmentVariables.permit`) before constructing `Command.new(..., env:, ...)`, whose `unbundled_env` is passed unmodified to `PTY.spawn`. An unprivileged fork PR author who labels their own PR `bash_env` (case-insensitive, becomes `BASH_ENV=true`) can therefore inject `BASH_ENV` into the environment of any `tasks.<name>.steps` command that later runs for that review stack.

### Finding Description
The broken binding: the engine assumes `env` reaching `Command#start`/`PTY.spawn` is always constrained to `Shipit.env`, deploy-time constants, and explicitly whitelisted `deploy.variables`/`task.variables` (enforced via `EnvironmentVariables#permit`, see `filter_deploy_envs`/`filter_rollback_envs`/`TaskDefinition#filter_envs`) [3](#0-2) [4](#0-3) [5](#0-4) . In reality, `ReviewStack#env` bypasses this: it merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" } }` directly, with no allowlist check at all [6](#0-5) .

`pull_request.labels` is populated straight from webhook payload label names via `LabelCapturingHandler#capture_labels`, which calls `pull_request.update!(labels: params.pull_request.labels.map(&:name))` with no sanitization or allowlist [7](#0-6) . This handler runs for `opened`/`labeled`/`unlabeled`/`reopened` actions on any active stack, which under `provisioning_behavior=allow_all` is auto-created for any fork PR [8](#0-7) . Labels are attacker-controlled: any GitHub user who can open a PR against their own repo can name/apply a label on it, and label-add events on the PR trigger the webhook.

Downstream, `TaskCommands#env` does `super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)` [9](#0-8) , and `perform`/`install_dependencies` build `Command.new(command_line, env:, chdir: steps_directory)` directly from that merged, unfiltered `env` for `tasks.<name>.steps` [10](#0-9) . Unlike the API-triggered `env` parameter path (which is filtered through `EnvironmentVariables.permit` in `filter_deploy_envs`/`TaskDefinition#filter_envs`/`rollback_params`), the `@stack.env` (and thus the label-derived keys) is never passed through any allowlist before reaching `Command.new`. `Command#unbundled_env` then merges this env over `BASE_ENV`/`ENV['PATH']` and hands it unmodified to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [1](#0-0) [11](#0-10) . Since `BASH_ENV` is a bash-recognized variable naming a file to be sourced on non-interactive shell startup, having it land in `env` for a non-interactively-invoked `tasks.<name>.steps` command that is later executed via `sh -c`/bash allows arbitrary file sourcing if the attacker can also place that file somewhere accessible on the deploy host's filesystem (e.g., under the checked-out fork working directory, since `chdir` is the task's `working_directory`, which is the attacker's own cloned fork content).

Existing tests explicitly confirm the unfiltered merge behavior at both the `ReviewStack#env`, `DeployCommands#env`, and `TaskCommands#env` levels, showing labels reach these envs verbatim uppercased with no permit-list applied: [12](#0-11) [13](#0-12) [14](#0-13) .

None of the existing guards prevent this: `EnvironmentVariables#permit` is applied only to the explicit `env` params on deploy/rollback/task API triggers (`filter_deploy_envs`, `filter_rollback_envs`, `TaskDefinition#filter_envs`, `rollback_params`), not to `Stack#env`/`ReviewStack#env` itself, which is unconditionally merged into every task/deploy command's environment.

### Impact Explanation
Any command run under `tasks.<name>.steps` (or the deploy/dependency-install steps, since they share the same `TaskCommands#env`) for a review stack inherits attacker-chosen environment key/value pairs limited to `KEY=true` where `KEY` is the uppercased PR label name. This lets a fork-PR author inject sensitive shell-interpreted variables such as `BASH_ENV`, `ENV`, `PROMPT_COMMAND`, `IFS`, or other process-affecting variables into commands executed by the Shipit deploy host for that stack. Combined with the attacker's control over the checked-out repository content (a file the injected `BASH_ENV` can point to, if a bash shell sources it non-interactively when invoking the step), this can escalate to command execution on the deploy host — a Critical RCE impact scoped to the review stack of the repository the attacker controls (their own fork/PR), since `pull_request.labels` and `ReviewStack#env` are scoped per-stack/per-repository via `repository.review_stacks`.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` and `provisioning_behavior` set to `allow_all` (or the attacker's label matches an `allow_with_label` gate) so that `OpenedHandler`/`LabelCapturingHandler` create/update the review stack for an unprivileged PR [15](#0-14) . Given that, attacker cost is trivial: open a PR from a fork and add a label named `bash_env` to their own PR — no secrets, tokens, or privileged roles required, and no webhook signature bypass is needed since this is a legitimate signed webhook from the repository the attacker owns. This is fully repeatable and requires only standard GitHub PR/label permissions on the attacker's own repository.

### Recommendation
Do not let `ReviewStack#env`/`Stack#env` inject unwhitelisted keys into command environments. Either: (1) remove the PR-label-to-env mechanism entirely, or (2) restrict label-derived env keys to an explicit per-repository allowlist (e.g., configured in `shipit.yml`) and reject/strip any label name that collides with sensitive/shell-special variable names (`BASH_ENV`, `ENV`, `IFS`, `LD_PRELOAD`, `PATH`, etc.), and (3) run all label-derived keys through `EnvironmentVariables#permit` against the task/deploy's declared `variables` before merging into the env passed to `Command.new`.

### Proof of Concept
minitest plan (`test/lib/shipit/task_commands_test.rb` or a new test file):
```ruby
test "#env does not leak BASH_ENV from a pull request label" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["bash_env"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env

  assert_nil env["BASH_ENV"], "BASH_ENV should never be attacker-controllable via PR labels"
end
```
Given the current code, `stack.env["BASH_ENV"]` equals `"true"` (per `ReviewStack#env`'s uppercasing merge, analogous to the existing `WIP`/`BUG` assertions in `test/models/shipit/review_stack_test.rb:59-65` and `test/lib/shipit/task_commands_test.rb:6-16`), and this value is merged unfiltered into `TaskCommands#env` and subsequently into `Command#unbundled_env` fed to `PTY.spawn`, demonstrating the equality `"attacker's PR label" == "process env key reaching PTY.spawn"` holds rather than being blocked.
