Confirmed: Shipit supports true multi-tenant GitHub App configuration, where each organization has its own independent `webhook_secret` under `secrets.github[organization]`, resolved via `Shipit.github_app_config` and `Shipit.github(organization:)`. [1](#0-0) 

### Title
Webhook signature verification binds only to `repository.owner.login`, not to the `repository.full_name` acted upon, allowing cross-organization webhook forgery in multi-tenant deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The webhook signature-verification step selects which organization's `webhook_secret` to validate the HMAC against using `repository.owner.login` (or `organization.login`) taken from the **unverified** JSON body. Every downstream webhook handler, however, resolves the actual `Repository`/`Stack` to act on using `repository.full_name` — a sibling field inside the same attacker-supplied JSON body that is never cross-checked against `repository.owner.login`. In a multi-tenant Shipit deployment (multiple GitHub organizations each configured with their own `webhook_secret`), an attacker who legitimately controls the webhook secret for Organization A can forge a webhook payload where `repository.owner.login = "orgA"` (so the signature validates against orgA's secret) while `repository.full_name = "orgB/some-repo"` (a completely different organization's repository/stack). The signature check passes, but the event is processed against Organization B's stack.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from payload content that hasn't been authenticated yet: [2](#0-1) [3](#0-2) 

`Shipit.github(organization: repository_owner)` looks up a per-organization `webhook_secret` via `github_app_config`, confirming Shipit is designed for independent secrets per organization: [1](#0-0) 

`GitHubApp#verify_webhook_signature` then does a pure HMAC compare using whichever secret was selected: [4](#0-3) 

Once verification "succeeds," `WebhooksController#create` dispatches the *entire raw payload* — including the `repository.full_name` field — to handlers: [5](#0-4) 

Every default handler resolves the concrete repository/stack strictly from `repository.full_name`, with no re-validation that it belongs to the organization whose secret validated the signature: [6](#0-5) [7](#0-6) [8](#0-7) 

This is the exact structural analog to the Nouns DAO bug class: the field that is **checked/authenticated** (`repository.owner.login`, used to pick the signing secret) is not the same field that is **acted upon** (`repository.full_name`, used to resolve the target repository/stack). Nothing in the payload schema or the controller enforces that `full_name` must start with `owner.login`, and there is no code path re-deriving/verifying that relationship.

### Impact Explanation
This breaks the equality "organization that authenticated == repository that is written." In a multi-tenant Shipit instance (multiple orgs configured under `secrets.github`), an attacker who is a legitimate admin/webhook-owner of *one* onboarded organization (A) — who thus knows or can trigger delivery of a validly-signed payload using A's `webhook_secret` — can forge JSON bodies claiming any `repository.full_name` belonging to organization B. Depending on which event/handler is targeted this enables, among others:
- Archiving/unarchiving/creating review stacks for org B's repositories (`pull_request` handlers).
- Injecting fake commit statuses / check runs for org B's commits, which downstream drives `all_status_checks_passed?` and merge-queue auto-merge logic in `MergeRequest#merge!`, potentially triggering an **unauthorized merge** into org B's repository.
- Triggering `GithubSyncJob` re-syncs, membership/team writes for org B (`membership` handler creates `Team`/`User`/`Membership` records tied to org B), affecting org B's `Shipit.github_teams` authorization data.

The most severe realizable consequence — forged CI/check-run status webhooks feeding the merge queue's `all_status_checks_passed?` check, followed by automatic `merge!` — constitutes an unauthorized merge into a repository the attacker does not control, matching the required "Critical: unauthorized deploy, rollback or merge" impact bar.

### Likelihood Explanation
Exploitability requires: (1) a Shipit deployment configured for more than one GitHub organization (each with independent `webhook_secret`s) — a supported and documented configuration, not a hypothetical; (2) the attacker legitimately controls or can obtain a validly-signed delivery for at least one onboarded organization (e.g. they are an admin of their own org's repo that is connected to the same Shipit instance, or exfiltrate one org's `webhook_secret`, which is a much lower bar than compromising the whole app). Given cross-tenant Shipit installations are an intended use case (`github_organizations`, `github_app_config`), and forging the JSON body is trivial once one valid secret is known, likelihood is assessed as medium-to-high in that configuration profile, low in single-org deployments (where this collapses to a no-op since there's only one secret and one org).

### Recommendation
After the signature check passes, re-derive `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and assert its `owner` matches (case-insensitively) the `repository_owner` value that was used to select the verifying `webhook_secret`. Reject the delivery (422) if they diverge. This closes the gap between the field verified by the signature-selection logic and the field every handler actually acts upon.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (`secrets.github[:orgA][:webhook_secret]`, `secrets.github[:orgB][:webhook_secret]`), both with stacks/review-stacks provisioning enabled.
2. As an attacker who is an admin of `orgA` (and therefore knows/controls delivery of `orgA`'s `webhook_secret`, e.g. by configuring their own webhook delivery to the Shipit endpoint), craft a `pull_request` (or `status`/`check_suite`) JSON payload with:
   - `repository.owner.login = "orgA"`
   - `repository.full_name = "orgB/target-repo"`
   - `action = "opened"`, plus the other fields required by `OpenedHandler#params`.
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, raw_body)>` and POST to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")`, which validates successfully against `orgA`'s secret.
5. `OpenedHandler#process` resolves `repository` via `Repository.from_github_repo_name("orgB/target-repo")` and provisions/mutates a review stack for `orgB`'s repository, despite the request never having been signed by anything belonging to `orgB`.
6. Repeating with a forged `status`/`check_suite` payload that flips org B's PR head commit to `success` allows the merge-queue job (`ProcessMergeRequestsJob` → `MergeRequest#merge!`) to merge a pull request in `orgB`'s repository without any legitimate CI or org B authorization.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
