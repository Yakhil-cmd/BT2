### Title
Unsanitized asset metadata `name` is stored and propagated verbatim to wallet clients, enabling stored HTML/script injection - (File: wallet.js)

### Summary
`ocore`'s wallet layer downloads and caches asset "metadata" (the display `name` of an asset) from `data` messages posted by an asset's registry address, and later serves that raw string back to any peer/wallet requesting it (via `hub/get_asset_metadata` and `readAssetMetadata`) without any character filtering or escaping. This mirrors the Backdrop CMS advisory pattern: a privileged-but-limited actor (there, a user with "administer fields"; here, any address that can act as an asset's registry/issuer) supplies a free-text label that downstream UIs display, but the core never sanitizes it before storage/redistribution, pushing the sanitization burden — and the resulting stored-XSS risk — entirely onto every consumer.

### Finding Description
When a wallet needs the display name of an asset, it calls `fetchAssetMetadata()`, which fetches a "metadata unit" from the registry address and reads the `data` message payload for that asset: [1](#0-0) 
It only validates that `payload.name` is truthy — there is no character allow-list, no HTML-escaping, and no rejection of control/markup characters: [2](#0-1) 
The raw value is written straight into the `asset_metadata` table and handed back to the caller as `objMetadata.name`: [3](#0-2) 

`readAssetMetadata()` later reads this same unescaped `name` column out of the DB and returns it (`suffix ? name+'.'+suffix : name`) to any internal caller / GUI layer that renders asset lists, balances, or payment confirmation dialogs: [4](#0-3) 

Additionally, a hub-facing RPC re-serves whatever was stored for an asset (`metadata_unit, registry_address, suffix`) to any requesting peer without re-validation: [5](#0-4) 

The underlying schema also shows the intended use is a short display label (`name VARCHAR(20)`), reinforcing that this field is meant purely for UI presentation, not for programmatic/hash-like use — exactly the "field label" class of injection in the Backdrop advisory: [6](#0-5) 

Because any address can issue an asset and act as (or delegate to) a registry address for that asset's metadata unit, the `name` value is attacker-controlled free text that flows unsanitized from a posted DAG unit into wallet storage and back out to every client that queries asset metadata — the same "administer fields → unsanitized label → later rendered" chain as the Backdrop CVE, translated to `ocore`'s asset-metadata mechanism.

### Impact Explanation
If any downstream wallet UI (light wallet apps, GUI wallets, textcoin/payment confirmation screens) renders `asset_metadata.name` as HTML/innerHTML rather than as plain text, an attacker who issues an asset (or controls/spoofs a registry address that other wallets trust for suffix resolution) can inject a name such as `<img src=x onerror=...>` (bounded by the 20-character column, still enough for compact payloads). This name is then persisted locally and served to every peer/light client that requests `hub/get_asset_metadata` or refreshes asset metadata, resulting in stored/persistent script execution in the wallet UI context of victims who view balances, payment history, or confirmation dialogs involving that asset. This can lead to UI spoofing of payment amounts/recipients (tricking users into confirming malicious transactions) — a realistic path to unauthorized spending consistent with the required impact bar.

### Likelihood Explanation
Likelihood is moderate: it requires (a) issuing/controlling an asset whose metadata registry resolves to an attacker-controlled or attacker-influenced address, and (b) a downstream renderer that does not itself HTML-escape the `name` before display. Since `ocore` is a shared backend used by multiple wallet frontends, the sanitization gap here means every consumer must independently defend against this, which is exactly the systemic risk class the Backdrop advisory flags — a core omission that downstream code is not guaranteed to compensate for.

### Recommendation
- Enforce a strict character allow-list (e.g., alphanumeric, limited punctuation) on `payload.name`/`suffix` in `fetchAssetMetadata()` before writing to `asset_metadata`, rejecting or stripping `<`, `>`, `&`, quotes, and control characters.
- HTML-encode the `name`/`suffix` values at the point `readAssetMetadata()` returns them, or clearly document that the returned name must be treated as untrusted and escaped by every consumer.
- Apply the same validation on the `hub/get_asset_metadata` server-side response path in `network.js` before it is cached/served to peers.

### Proof of Concept
1. Issue an asset and register a "registry" address you control (or one used for suffix resolution).
2. Post a `data`-app unit from that registry address with payload `{asset: "<ASSET_UNIT>", name: "<script>", decimals: 0}` (Note: actual payload size is limited by the `VARCHAR(20)` name column, but short breakout payloads such as `<img src=x onerr>` or bytes designed to break out of a non-escaping template are sufficient).
3. Any wallet that calls `readAssetMetadata`/`fetchAssetMetadata` for that asset stores the payload's `name` verbatim in `asset_metadata.name` — confirmed by the unescaped `INSERT ... VALUES (asset, metadata_unit, registry_address, suffix, payload.name, decimals)` at [7](#0-6) .
4. Any UI that renders this stored `name` field without escaping executes the injected markup/script, and any peer calling `hub/get_asset_metadata` receives the same unsanitized value for redisplay [5](#0-4) .
