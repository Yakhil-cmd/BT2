### Title
Webhook signature verified against the payload's self-declared organization while the mutated repository is taken from the same untrusted payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC signature against by reading `repository_owner` from the **unverified** JSON body, then verifies the signature using that organization's config. The actual `Stack`/`Repository` that the webhook handler subsequently mutates is resolved from `repository.full_name` in that same untrusted body, independent of which organization's secret passed verification. In a multi-organization Shipit deployment (`Shipit.github_organizations`), this breaks the intended binding "organization that authenticated == repository that is written," analogous to the vault bug where `vault_total_balance` (one side of an invariant) was not kept in sync with `vault.total_shares` (the other side).

### Finding Description
`verify_signature` computes the verifying app from attacker-supplied data before the signature has been checked: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up per-organization config (`github_app_config`) and builds a `GitHubApp` whose `webhook_secret` may be blank for a given organization; if so, `verify_webhook_signature` short-circuits to `true`: [3](#0-2) [4](#0-3) 

Once `verify_signature` passes, `create` re-parses the same raw body and hands it to the event handlers untouched: [5](#0-4) 

Handlers (e.g. `PushHandler`) resolve which `Stack` to mutate strictly from `payload.dig('repository', 'full_name')`, with no relation to `repository_owner` used for signature selection: [6](#0-5) [7](#0-6) [8](#0-7) 

This is the same class of bug as the report: two values that must move together (`repository_owner` used for verification vs. `repository.full_name` used for the write) are read from the same attacker-controlled input and never cross-checked against each other, so the "signed" side and the "acted-upon" side can point at different entities.

### Impact Explanation
In any Shipit installation using the multi-organization config schema (`github: { org_a: {...}, org_b: {webhook_secret: nil} }`, as documented in `docs/setup.md`), an unauthenticated attacker who knows (or can guess) the name of an organization configured without a `webhook_secret` can craft a JSON body with `repository.owner.login` (or `organization.login`) set to that unsecured organization while setting `repository.full_name` to any other repository/stack managed by Shipit, including ones belonging to organizations that *do* have a secret configured. `verify_signature` will authenticate the request (because the unsecured org's `verify_webhook_signature` returns `true` unconditionally), and the handler will then act on the unrelated target repository/stack (e.g. trigger `GithubSyncJob`, create commit statuses, alter memberships/teams, or drive merge/deploy-adjacent state depending on event type) — a cross-repository/cross-organization write performed by an unauthenticated party. This matches the "cross-repository writes" Critical-impact category defined in scope.

### Likelihood Explanation
Requires: (1) the operator to run Shipit with the multi-organization GitHub config schema, and (2) at least one configured organization to have a blank/absent `webhook_secret` (explicitly supported per `docs/setup.md` — `webhook_secret: # nil`). Given that combination, no credentials, no session, and no prior access are needed — only network access to `POST /github/webhooks` and knowledge of the vulnerable organization's name in `secrets.github`. Organization names are often discoverable (they are used in webhook delivery URLs, GitHub org pages, etc.), and multi-org shared deployments are an explicitly documented setup pattern, which raises likelihood beyond purely theoretical.

### Recommendation
Bind signature verification to the repository that will actually be mutated, not to an attacker-chosen organization field: derive the verifying organization from `repository.full_name`'s persisted `Repository#owner` (or otherwise ensure the organization used to select the `webhook_secret` matches the resource acted upon), and reject/log any request where the two diverge. Alternatively, require every configured organization in the multi-org schema to have a non-blank `webhook_secret`, and fail closed if a organization's secret is missing rather than treating it as "always verified."

### Proof of Concept
1. Configure Shipit with the multi-org schema:
   ```yaml
   github:
     safe_org:
       app_id: 1
       installation_id: 1
       webhook_secret: # blank — intentionally unset by an operator
     secured_org:
       app_id: 2
       installation_id: 2
       webhook_secret: real-secret
   ```
2. `secured_org/target-repo` is a real Shipit-managed stack (tracked branch `main`).
3. Attacker sends, with no `X-Hub-Signature` needed to be valid:
   ```
   POST /github/webhooks
   X-Github-Event: push
   Body: {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "safe_org" },
       "full_name": "secured_org/target-repo"
     }
   }
   ```
4. `repository_owner` resolves to `safe_org` → `Shipit.github(organization: "safe_org")` → `webhook_secret` blank → `verify_webhook_signature` returns `true` regardless of the actual header. [3](#0-2) 
5. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("secured_org/target-repo")` and enqueues `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on that stack, even though the request was never signed with `secured_org`'s real secret. [7](#0-6)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
