### Title
Cross-repository commit-status forgery via `StatusHandler` — organization the webhook signature authenticates is never bound to the repository whose commit status gets written ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the raw payload was signed by *some* configured GitHub organization's webhook secret — it never constrains *which repository's* data the payload is allowed to mutate. `StatusHandler#process` then looks up the target `Commit` **solely by its git SHA, instance-wide**, with no check that the SHA belongs to a stack/repository owned by the organization that authenticated the request. This is the same bug class as the Superfluid finding: the value that is verified (the org that signed) is narrower than the value that is actually acted upon (any commit, in any repository, anywhere in the Shipit instance).

### Finding Description
The webhook signature check picks the verifying `GitHubApp`/secret using only the organization name embedded in the payload: [1](#0-0) [2](#0-1) 

That verification produces no guarantee about which specific repository's records may be written — it only proves "this payload was signed with organization X's secret." Every registered handler receives the exact same `params` regardless of that scope: [3](#0-2) 

`StatusHandler`, however, resolves the target record purely by `sha`, with **no repository/organization scoping at all**, unlike `PushHandler` which at least resolves stacks through `Repository.from_github_repo_name(repository.full_name)`: [4](#0-3) [5](#0-4) 

Because Shipit explicitly supports hosting multiple, independently-owned GitHub organizations/tenants behind one instance (each with its own app/webhook secret and OAuth teams): [6](#0-5) [7](#0-6) 

a webhook that is validly signed for **organization A** (`repository.owner.login = A`) is nonetheless able to write a commit status onto a `Commit` belonging to a stack/repository under a completely different, unrelated **organization B**, as long as the attacker can supply a `sha` value that also exists as a tracked `Commit` in B's stack (SHAs are public/derivable git object hashes, and identical commits frequently exist across forks/mirrors/vendored subtrees). `Commit#create_status_from_github!` writes the forged state directly from webhook `params` (`state`, `description`, `target_url`, `context`) without any additional GitHub API round-trip to confirm authenticity against the actual commit's real repository.

Binding broken (equality that should hold but doesn't):
`organization that authenticates the webhook (via verify_signature)` == `organization owning the repository whose Commit status is mutated (via StatusHandler#process)`.

Before the attacker's request: only organization A's secret can produce a `status` payload verified as originating from A.
After: that verified-for-A payload can mutate commit-status state belonging to organization B's stack, because `StatusHandler` never checks repository ownership — it only filters by `sha`.

### Impact Explanation
Commit statuses drive Shipit's deploy/merge safety gating (`Commit#create_status_from_github!`, statuses page, merge queue required-status checks). An attacker who is merely a legitimate contributor on one tenant organization (A) hosted by the same multi-org Shipit instance — requiring no Shipit session, no `ApiClient` token, no GitHub App private key, and no write access to the victim organization B — can forge a passing/failing commit status against a commit tracked under organization B's stack, which can be leveraged to satisfy required-status gates and enable an unauthorized merge/deploy in a completely different organization's stack. This is a cross-repository/cross-organization write crossing an authentication boundary, matching the "unauthorized deploy, rollback or merge" / "cross-repository writes" impact bar.

### Likelihood Explanation
Requires only: (1) the target Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration), (2) the attacker to have legitimate ability to trigger a genuinely GitHub-signed `status` webhook from any one of those organizations (e.g., being a collaborator/CI integrator on any repo in org A), and (3) knowledge of a SHA that is also tracked as a `Commit` in the victim stack (obtainable from public commit history, forks, or coincidentally shared commits). No cryptographic bypass of any organization's individual webhook secret is needed — the flaw is purely in `StatusHandler`'s missing repository-scoping check.

### Recommendation
In `StatusHandler#process`, restrict the `Commit.where(sha: params.sha)` lookup to commits belonging to stacks whose `Repository#owner` matches the authenticated `repository_owner`/organization from the verified webhook (mirroring how `PushHandler`/`Handler#stacks` resolve via `Repository.from_github_repo_name`), rejecting or ignoring statuses for commits outside the authenticated organization's repositories.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own real webhook secret (as in `test/dummy/config/secrets_double_github_app.yml`), both tracking stacks with commits.
2. Note (or predict) a commit SHA, `sha_victim`, tracked by a stack under `OrgB` (e.g., via GitHub's public commits API, a shared vendored dependency commit, or a mirrored/forked repo commit that coincides with `OrgB`'s tracked SHA).
3. As a legitimate GitHub integrator/contributor on `OrgA` (no relationship to `OrgB` needed), produce/have GitHub deliver a `status` event whose body sets `"sha": "sha_victim"`, `"state": "success"`, and `repository.owner.login = "OrgA"`. GitHub signs this payload with `OrgA`'s webhook secret.
4. `WebhooksController#verify_signature` validates the signature successfully against `OrgA`'s secret (app/controllers/shipit/webhooks_controller.rb:24-30).
5. `StatusHandler#process` executes `Commit.where(sha: "sha_victim")`, finds the `Commit` under `OrgB`'s stack (no ownership check performed), and calls `create_status_from_github!`, writing a forged "success" status onto `OrgB`'s commit — usable to unblock `OrgB`'s merge queue/deploy gating despite the attacker having no access whatsoever to `OrgB`.
