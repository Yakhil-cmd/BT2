Webhook signature key selection is not bound to the repository being written, enabling cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to validate an inbound webhook based on `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated JSON body, while the handlers that actually mutate state (e.g. `PushHandler`) resolve the target `Repository`/`Stack` using a different, unrelated field of the same unauthenticated body: `repository.full_name`. Because these two fields are never cross-checked, an attacker who legitimately controls webhook delivery for *any* GitHub organization configured in this Shipit instance can forge a payload whose `repository.owner.login` matches their own org (so the signature check passes with a secret they know) but whose `repository.full_name` points at a completely different, victim organization's repository.

### Finding Description
The equality this breaks is: **organization that authenticated == repository that is written**.

- `verify_signature` looks up the GitHub app/secret using the org derived from the raw, unverified payload: [1](#0-0) [2](#0-1) 

- The actual HMAC comparison only proves "this payload was signed by whoever owns the org named in `repository.owner.login`/`organization.login`" — it says nothing about whether the *rest* of the payload (in particular `repository.full_name`) genuinely belongs to that org: [3](#0-2) 

- Every handler, however, resolves the mutation target purely from `repository.full_name`, with no reference back to the org used for signature verification: [4](#0-3) 

- `PushHandler` then uses that repository's stacks to trigger a sync to an attacker-chosen `after` SHA: [5](#0-4) 

- `Repository.from_github_repo_name` performs a pure lookup by owner/name parsed out of `full_name`, with no relation to the org that authenticated the request: [6](#0-5) 

So the invariant "a webhook that is cryptographically valid for organization X may only affect repositories that belong to organization X" is never enforced — the same unauthenticated JSON body supplies both the *key selector* and the *target selector*, and they are never checked against each other.

### Impact Explanation
In a Shipit deployment configured for multiple GitHub organizations (each with its own `webhook_secret` in `Shipit.github`), an attacker who legitimately owns/administers one of those organizations (and therefore legitimately knows that org's webhook secret, as it is delivered to their own webhook endpoint by GitHub) can forge a `push` (or other) webhook whose `repository.owner.login` is their own org but whose `repository.full_name` names a victim organization's repository/stack. `verify_signature` will pass because the signature is computed correctly against the attacker's own known secret. `PushHandler` will then locate the victim `Stack` (via `Repository.from_github_repo_name`) and call `stack.sync_github(expected_head_sha: params.after)` with an attacker-controlled SHA — effectively a cross-organization write into another tenant's stack state, forged with an identity that was never actually verified against that tenant. This is a cross-repository/cross-tenant integrity break driven entirely by unauthenticated data, not by compromising any privileged credential.

### Likelihood Explanation
Any organization onboarded to a shared/multi-tenant Shipit instance can perform this attack against any other onboarded organization's repositories, using nothing but their own legitimate webhook secret and a hand-crafted JSON body — no `ApiClient` token, no session, no GitHub App private key, and no push access to the victim repository are required. This is realistic anywhere Shipit is run as a shared service across multiple GitHub orgs, which is an explicitly supported configuration (`Shipit.github(organization:)` is org-keyed).

### Recommendation
After signature verification, re-derive the organization from the same field the handlers use to select the mutation target (`repository.full_name`'s owner segment, or the actual `Repository` record's `owner`) and reject the request if it doesn't match the organization whose secret validated the signature. Do not allow `repository.owner.login`/`organization.login` and `repository.full_name` to diverge across signature verification and handler dispatch — treat them as a single, mutually-consistent binding rather than two independently-trusted payload fields.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` (secret known to the attacker, who legitimately administers that org's GitHub webhook) and `victim-org` (contains a Shipit-tracked repository/stack).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature using the attacker's own known secret. [1](#0-0) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` (from `repository_name`, i.e. `full_name`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — a state-changing action on `victim-org`'s repository triggered and "authenticated" solely via `attacker-org`'s credentials.
