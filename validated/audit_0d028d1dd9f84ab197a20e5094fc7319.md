### Title
Assertion-style crash via mismatched recursion-depth counter in oscript formula validation - (File: formula/validation.js)

### Summary
CVE-2020-23309 is an internal assertion failure (`context_p->stack_depth == context_p->context_stack_depth`) inside JerryScript's statement parser, triggered by malformed/edge-case script input that desynchronizes an internal depth counter, crashing the engine. ocore's oscript formula validator (`formula/validation.js`) implements the same pattern: a mutable `depth` counter incremented/decremented around every recursive `evaluate()` call, guarded by an explicit consistency assertion at the top level: `if (depth !== 0) throw Error("mismatched depth " + depth);` [1](#0-0) [2](#0-1) . This is directly analogous to the JerryScript bug class: a hand-maintained stack/recursion-depth invariant checked via a hard assertion, not a graceful error path.

### Finding Description
`exports.validate` in `formula/validation.js` parses an oscript formula with `nearley` and recursively walks the AST via a local `evaluate(arr, cb, bTopLevel)` closure [3](#0-2) . Every call wraps the callback so that `depth++` happens on entry and `depth--` happens whenever `cb` fires [1](#0-0) . After the whole tree is evaluated, the code asserts `depth === 0` and `throw`s an `Error` if not [2](#0-1) . This throw is unconditional and not inside a `try/catch` that could turn it into a normal validation error — it is a hard runtime exception raised from deep inside asynchronous `async.eachSeries` callback chains used throughout the ~150 opcode cases of the switch statement (e.g. `and`/`or`, `ternary`, `func_call`, `remote_func_call`, `foreach`/`map`/`filter`/`reduce`, `local_var_assignment`, `ifelse`, `block`, `main`, etc.) [4](#0-3) [5](#0-4) [6](#0-5) .

The invariant `depth === 0` is only guaranteed to hold if every `evaluate()` call's `cb` is invoked **exactly once** for every AST node, in every one of the dozens of manually written branches. Given the sheer number of hand-coded async control-flow paths (nested `async.eachSeries`, chained callbacks, early returns via `return cb(...)`, fallthrough `switch` cases such as `case 'input': case 'output': ... case 'attestation':` at lines 397-410, and `case 'trigger.initial_unit': ... case 'storage_size':` at lines 448-462) [7](#0-6) [8](#0-7) , any single case where `cb` is called zero or two times for a given node — a double-invocation of a callback, a missed callback on an error branch, or a callback fired outside its matching `evaluate()` wrapper — desynchronizes the depth counter exactly like the JerryScript `stack_depth` mismatch. Because `formula/validation.js` is invoked directly from unit/AA validation (`aa_validation.js` calls `validateFormula`/`formulaValidator.validate` while validating AA definitions, getters, `if`/`init` conditions, state updates, asset/data-feed formulas, etc.) [9](#0-8) [10](#0-9) , a formula crafted to trigger such an imbalance would cause `throw Error("mismatched depth " + depth)` to fire during normal unit validation. Since this exception is thrown from within callbacks driven by `async.eachSeries`/nested closures (not synchronously from the code the caller wrapped in `try/catch`), it becomes an **uncaught exception** that can crash the Node.js process handling validation on every node that processes the offending unit.

### Impact Explanation
If a formula (in an AA definition, AA getters, `if`/`init` fields, state-var assignment, data feed, or asset condition) can be crafted to desynchronize the `depth` counter, every full node / hub that validates the unit containing that formula would hit the same `throw`, producing a deterministic, network-wide crash of the validating process. Because formula validation happens on unit/AA-definition validation — reachable by any unprivileged unit poster or AA author — this matches the "network unable to confirm new units" impact category: nodes that crash cannot keep validating and advancing the DAG, and repeated posting of such a unit could be used to repeatedly crash restarting nodes/hubs.

### Likelihood Explanation
Reachability is straightforward and requires no privileges: any user can attach an AA definition (`definition.js`/`aa_validation.js`) or post a unit whose payload/formula fields get validated by `formula/validation.js`. However, actually engineering a specific opcode/formula combination that causes a callback to fire zero or two times for the same AST node requires careful analysis of the ~150-case switch and its many nested `async.eachSeries`/chained-callback constructs; I was not able to identify, from the available code inspection alone, a concrete callback-imbalance bug in a single pass (the branches reviewed line-by-line were each internally consistent in calling `cb` exactly once). This keeps confirmed exploitability uncertain — the vulnerable *pattern* (assertion-style depth invariant fed by extensive hand-written async recursion) is clearly present and structurally analogous to the CVE, but a concrete crafted-formula PoC that flips the assertion was not found in this review.

### Recommendation
- Replace the hard `throw Error("mismatched depth " + depth)` with a caught/logged validation failure (`return callback({ error: 'internal depth mismatch' })`) so any latent callback-imbalance bug degrades to a formula-validation rejection instead of crashing the process.
- Wrap the top-level `evaluate(...)` invocation and the whole `exports.validate` in a `try/catch` (and ensure it also catches errors thrown asynchronously, e.g., via `process.on('uncaughtException')` scoping or converting the recursive evaluator to use explicit stack-safe recursion with invariant checks that never throw).
- Audit every `switch` case in `formula/validation.js` for exactly-once callback invocation, particularly the fallthrough cases and the `foreach`/`map`/`filter`/`reduce`/`remote_func_call` cases with nested `async.eachSeries`, to rule out any double-callback or dropped-callback path.
- Add fuzz/property tests that assert `depth === 0` never throws (i.e., convert the assertion into a test-time-only check) across a wide corpus of malformed/edge-case oscript formulas, analogous to how the referenced JerryScript issue was found via fuzzing malformed statements.

### Proof of Concept
No concrete triggering formula was confirmed during this review; deriving one would require systematically fuzzing `formula/validation.js`'s `evaluate()` switch cases (especially the `async.eachSeries`-nested and fallthrough branches) with deeply nested/malformed oscript ASTs to find a path where `cb` is invoked other than exactly once per node, thereby flipping `depth !== 0` at the top-level check in `exports.validate` [2](#0-1) .
