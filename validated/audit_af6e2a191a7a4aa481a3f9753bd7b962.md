### Title
AA balance/storage updates are committed to the DB before trigger execution succeeds, with no rollback path for secondary (chained) AA triggers - (File: aa_composer.js)

### Summary
`handleTrigger()` in `aa_composer.js` mutates persistent state (`aa_balances`, `aa_addresses.storage_size`) via SQL `UPDATE`/`INSERT` queries immediately upon receiving a trigger, *before* the AA's bytecode/oscript has been executed and validated to completion. [1](#0-0)  A `SAVEPOINT initial_balances` is created to allow these speculative writes to be undone if the response later needs reverting [2](#0-1)  — but this savepoint is only created `if (!bSecondary)`. For secondary (AA-to-AA) triggers, no savepoint is taken, and `revert()` for a secondary trigger simply calls `bounce(err)` without ever issuing `ROLLBACK TO SAVEPOINT initial_balances`. [3](#0-2) 

### Finding Description
The trigger-handling flow is destructive-first: balances for the invoked AA address are updated in `aa_balances` (and later `aa_addresses.storage_size` in `updateStorageSize()`) as soon as the trigger is processed, well before the oscript messages have been validated/executed and before it is known whether the AA response will succeed or bounce. [4](#0-3) 

For a *primary* trigger, a `SAVEPOINT initial_balances` is issued right after these balance writes, so if the AA bounces, `revert()` can undo the writes with `ROLLBACK TO SAVEPOINT initial_balances`. [5](#0-4) 

For a *secondary* trigger (an AA calling another AA), `updateInitialAABalances()` explicitly skips creating the savepoint: `if (!bSecondary) conn.addQuery(arrQueries, "SAVEPOINT initial_balances");`. [2](#0-1)  Yet `revert()` is generic and is called for secondary triggers too — in that branch it only calls `bounce(err)` and returns, never touching the database at all: `if (bSecondary) return bounce(err);`. [6](#0-5)  The in-memory `stateVars` and response cache are cleared, but the already-executed SQL `UPDATE aa_balances SET balance=balance+? ...` / `INSERT INTO aa_balances ...` for the secondary AA's address are left standing in the enclosing DB transaction (the outer transaction owned by `handleAATriggers`/`writer.saveJoint`), since there is no savepoint to roll back to and no explicit compensating `UPDATE` reversing the added balance. [3](#0-2) 

This mirrors the reported bug class exactly: a destructive/state-altering operation is executed unconditionally before the operation it depends on (full trigger validation/execution) is known to succeed, and the rollback/recovery mechanism that exists for the "happy path" (primary triggers) is missing for a specific code path (secondary triggers), leaving no way to undo the change once failure is detected.

### Impact Explanation
Secondary AA triggers are reachable by any AA author whose bytecode sends coins to another AA address (a very common, unprivileged pattern) — this is entirely triggerable by a single posted unit that invokes an AA which in turn pays another AA. If the secondary AA's execution ultimately fails/bounces (a common intentional or user-driven condition, e.g. hitting `bounce()` due to invalid state, error, or logic hitting an unhandled exception), the balance credit already applied to `aa_balances` for that address is not reverted. This creates a discrepancy between the AA's persisted `aa_balances` row and its true asset holdings backed by real `outputs`/`inputs`, i.e., AA fund accounting becomes inflated for the bounced AA — a form of double counting/supply inflation within the AA subsystem, or conversely can cause future spend attempts by that AA to fail/succeed incorrectly, leading to fund loss or freezing for the AA and its users. This matches the acceptable “concrete AA fund loss/freezing” impact class.

### Likelihood Explanation
Chained AA calls are a standard use case, and any bounce condition of a secondary AA (which is easy to script deliberately, e.g., have the secondary AA’s bytecode intentionally bounce or reach a data-limit condition) will unconditionally hit this un-reverted code path. No special privileges are needed beyond being able to define/post a unit that triggers a chain of two AAs, which is entirely within reach of an ordinary AA author/trigger sender.

### Recommendation
Always take a savepoint before applying speculative balance/storage changes for a trigger, including secondary triggers, and always roll back to that savepoint in `revert()` regardless of `bSecondary`. Concretely: remove the `if (!bSecondary)` guard around `SAVEPOINT initial_balances` in `updateInitialAABalances()`, and change `revert()` to issue `ROLLBACK TO SAVEPOINT initial_balances` before calling `bounce(err)` in the `bSecondary` branch as well, ensuring the compensating rollback matches the actual savepoint nesting for chained triggers.

### Proof of Concept
1. Deploy AA `A` whose bytecode, upon receiving a trigger, sends a payment to AA `B`.
2. Deploy AA `B` whose bytecode, given certain trigger data/state, deterministically calls `bounce()` (e.g., through an intentional `bounce("...")` statement or a state precondition failure) after receiving funds.
3. Post a unit that triggers `A`, causing `A` to invoke `B` as a secondary trigger.
4. Trace execution: `handleTrigger()` for `B` runs `updateInitialAABalances()`, applying `UPDATE aa_balances SET balance=balance+<amount>` for `B` — but because `bSecondary` is true, no `SAVEPOINT initial_balances` is created. [2](#0-1) 
5. `B`'s execution reaches `bounce()`, and the failure propagates to `revert()`, which for `bSecondary === true` only calls `bounce(err)` without issuing any `ROLLBACK`. [3](#0-2) 
6. When the encompassing transaction commits (in `writer.saveJoint`), the balance increment applied to `aa_balances` for `B` remains persisted despite `B`'s response being bounced, leaving `aa_balances` inconsistent with `B`'s actual on-chain outputs.

Note: this analysis is based on static reading of `aa_composer.js`; I was not able to execute the AA test suite in this environment to empirically confirm the end-to-end persisted-balance discrepancy, so the final commit behavior of the enclosing transaction in `writer.saveJoint`/`handleAATriggers` (i.e., whether any other compensating mechanism exists further up the call stack) should be verified by a Devin session with runtime access before treating this as a fully confirmed exploit.
