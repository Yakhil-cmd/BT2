### Title
Untrusted swap route can execute attacker code beneath the caller’s authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary

`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept caller-controlled route bytes and pass them to the configured router without restricting which downstream venue contract the route invokes. A malicious venue can therefore execute inside the transaction beneath the account owner’s `require_auth` context and request token transfers unrelated to the lending operation. If the caller signs the authorization tree produced by simulation, that venue can transfer arbitrary wallet tokens to an attacker. [1](#0-0) [2](#0-1) 

### Finding Description

`swap_collateral` authenticates only the root caller and account ownership before forwarding `swap` to the strategy path. [3](#0-2) 

`swap_tokens` snapshots input and output balances, grants the configured router one exact controller-token transfer authorization, and calls `router.execute_strategy(controller, amount_in, swap)`. [4](#0-3) 

Those checks bound only the controller’s token-in spend and require a positive token-out receipt; they do not constrain calls made by route-selected third-party code. [5](#0-4) 

The repository’s adversarial test uses a route-named pool that calls `token.transfer(victim, attacker, amount)` from inside `execute_strategy`; recording mode attaches that transfer beneath the caller’s `swap_collateral` authorization. [6](#0-5) [7](#0-6) 

Enforcement rejects the transfer when the signed tree omits it, but succeeds when the victim signs the simulated tree containing the malicious transfer. [8](#0-7) 

### Impact Explanation

An attacker can steal unrelated tokens from the account owner’s wallet, not merely the collateral amount supplied to the route. The stolen token need not be listed by the lending protocol, and neither the measured router output nor the final account-risk check bounds this side effect. [9](#0-8) [5](#0-4) 

This is theft of user funds and can meet Critical severity where the victim’s wallet balance substantially exceeds the routed collateral.

### Likelihood Explanation

The attacker can deploy the malicious venue and encode it in route bytes supplied to any reachable route-based controller operation, such as `swap_collateral(caller, account_id, current, from_amount, new, swap)`. [10](#0-9) 

Execution additionally requires the victim to sign the authorization tree returned by simulation rather than inspecting and rejecting the unexpected child token transfer. [11](#0-10) 

That prerequisite lowers practical likelihood but does not eliminate the protocol boundary issue: quote/wallet flows commonly present simulated authorization trees for signing, and the test demonstrates that the poisoned tree is accepted as valid authorization. [12](#0-11) 

### Recommendation

Constrain route execution so user-supplied strategy payloads cannot invoke unlisted or attacker-controlled venue contracts. Alternatively, introduce an explicit route-venue allowlist or hash-pinned approved venue set and reject route execution when any hop target is absent. [4](#0-3) 

At the client boundary, display and enforce an expected authorization tree for every route-based operation: the tree should contain only the explicitly expected token pulls and no unrelated token transfers. Clients should refuse signing whenever simulation adds any other child invocation. [13](#0-12) 

### Proof of Concept

The in-repository PoC deploys `RogueHopPool` with `(victim, wallet_token, attacker, amount)`, then its `swap` function calls `token::Client::transfer(victim, attacker, amount)`. [14](#0-13) 

The route embeds that pool as `hop_pool`, supplies USDC as `token_in`, and requests ETH as `token_out`. [15](#0-14) 

Calling `try_swap_collateral(alice, account_id, USDC, SWAP_IN_USDC, ETH, route)` reaches the malicious pool through `execute_strategy`. [16](#0-15) 

Simulation records the unrelated wallet-token transfer as a child of Alice’s `swap_collateral` authorization, and the test shows Alice’s entire `WALLET_BALANCE` moving to the attacker while the lending swap still receives the expected output. [7](#0-6) 

In enforced mode, the same call succeeds once Alice signs the simulated tree containing that child transfer; the assertions show the wallet balance decreases from `WALLET_BALANCE` to zero and the attacker receives it. [12](#0-11)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
}
