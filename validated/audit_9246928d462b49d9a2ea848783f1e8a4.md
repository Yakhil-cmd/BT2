### Title
`borrow`/`withdraw` can revert on `InsufficientCollateral` due to a stale stored liquidation threshold until the permissionless `update_account_threshold` reconcile is called - (File: contracts/controller/src/risk/params.rs)

### Summary
The bug class is "a limit/health check reads a stale cached value and reverts a call that should succeed, forcing a separate reconcile transaction." In XOXNO Lending, each supply position snapshots its `liquidation_threshold`, `liquidation_bonus`, `liquidation_fees`, and `loan_to_value` at creation (`get_or_create_supply_position`), and later edits to the spoke listing via `editAssetInSpoke` do **not** propagate to existing positions. The HF gate in `require_post_pool_risk_gates` computes health factor from these stored values. When governance *raises* the liquidation threshold, a borrower's account keeps the old, lower LT, so `borrow` (and `withdraw` of other collateral legs) can revert with `InsufficientCollateral` even though the account is healthy under the live listing. Recovery requires anyone to call the permissionless `update_account_threshold(caller, has_risks, account_ids)` — the exact `reconcileSignerCount` shape from the source report.

### Finding Description
- `calculate_account_risk_totals` uses the position's stored LT, and `require_post_pool_risk_gates` in `contracts/controller/src/risk/validation.rs:49-53` reverts with `CollateralError::InsufficientCollateral` when `health_factor < 1`.
- The borrow path only refreshes stored **LTV** (`restamp_listed_supply_ltv`, `contracts/controller/src/risk/params.rs:44-64`; per `docs/reference/runbooks/liqvid-listing-params.md:376-389`, "Every borrow and every withdrawal refreshes the stored LTV ... The stored LT, bonus and fee refresh together, and only" on supply to that leg, withdrawal *of that same leg* leaving a balance, or `update_account_threshold`).
- Therefore, after `edit_asset_in_spoke` raises LT (a change favoring the *borrower*, not the liquidator, so the `apply_gated_liquidation_params` HF ≥ 1.05 gate at `params.rs:76-93` does not block propagation), an account whose HF is between the stale and live thresholds has `borrow` revert `InsufficientCollateral`.
- For `withdraw`, `merge_withdraw_leg` restamps only the withdrawn leg; a *different* supply leg holding a stale lower LT still drags the post-withdraw HF below 1 and reverts the whole call.
- The stale tuple is only repairable via `update_account_threshold` (`params.rs:124-144`), which is permissionless — mirroring `reconcileSignerCount`: the user must make an extra gas-costly call, and the revert message misleads them into thinking they are genuinely undercollateralized.

### Impact Explanation
Temporary freezing of funds / unexpected reverts: a borrower's `borrow`, `withdraw`, `multiply`, `swap_collateral`, or `repay_debt_with_collateral` (all of which run `require_post_pool_risk_gates`) reverts until a third-party restamp occurs. A user cannot self-heal within the failing call; they must submit a separate `update_account_threshold` transaction, and integrators simulating only the live listing see spurious `InsufficientCollateral` failures.

### Likelihood Explanation
Requires a governance `editAssetInSpoke` that raises LT (or LTV for paths that don't refresh it) while accounts hold positions stamped with older, tighter parameters. The stale-tuple design is documented and intentional (`liqvid-listing-params.md:362-374`), and runbooks explicitly instruct keepers to batch `update_account_threshold` after parameter edits (`liqvid-listing-params.md:458-466`), so the divergence window is a normal operational state, not an edge case. Any unprivileged borrower in the affected band hits the revert deterministically.

### Recommendation
Refresh the stored LTV/LT tuple inside the risk-gate path itself rather than relying on a separate keeper call. Concretely, in `require_post_pool_risk_gates` (or in `restamp_listed_supply_ltv`, which already runs on borrow), apply `refresh_supply_risk_params` for *favorable* direction changes (higher LT/LTV) unconditionally — favorable changes can never hurt the borrower, so they don't need the `THRESHOLD_UPDATE_MIN_HF_RAW` gate that `apply_gated_liquidation_params` applies to liquidator-favoring changes. This is the analog of calling `reconcileSignerCount` inside `claimSigner`, or of checking the limit against the live value.

### Proof of Concept
1. Alice supplies 10,000 USDC (spoke config LT = 8000) and borrows close to the limit; her stored position carries LT 8000.
2. Price drifts so her HF at LT 8000 is 0.99 but at LT 8500 is 1.05.
3. Governance executes `edit_asset_in_spoke` raising USDC LT to 8500. Alice's stored LT remains 8000 (`params.rs:56-61` only updates on refresh paths).
4. Alice calls `borrow` (or `withdraw` on a different collateral leg). `restamp_listed_supply_ltv` refreshes LTV only; `calculate_account_risk_totals` uses stored LT 8000 → HF 0.99 → `assert_with_error!(hf >= Wad::ONE)` reverts `InsufficientCollateral` (`validation.rs:49-53`), even though the live listing yields HF 1.05.
5. Any address then calls `update_account_threshold(caller, true, [alice_id])`; `sync_account_thresholds` restamps LT to 8500 (`params.rs:191-205`, final HF gate at `params.rs:221-234` passes since HF ≥ 1.05), and Alice's borrow now succeeds — confirming the revert was a stale-value artifact, matching the source report's `reconcileSignerCount` recovery pattern.

Caveat: I verified the refresh-path table via `docs/reference/runbooks/liqvid-listing-params.md` and `params.rs`; I did not exhaustively trace `merge_supply_leg`/`merge_withdraw_leg` and every strategy entrypoint, so the exact set of paths that restamp the full tuple should be confirmed against `positions/` code during remediation.
