### Title
Webhook signature verification keys off an attacker-controlled `repository.owner.login` field that is decoupled from the `repository.full_name` field the handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify the incoming webhook signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback) taken directly from the untrusted JSON body. [1](#0-0) [2](#0-1) 

However, every event handler (`PushHandler`, `StatusHandler`, `MembershipHandler`, the `PullRequest::*Handlers`) resolves the actual `Repository`/`Stack` to act on using a *different* field from the same payload: `repository.full_name`. [3](#0-2) [4](#0-3) 

Shipit is explicitly designed to be multi-tenant: `config/secrets.*.yml` maps multiple independent GitHub organizations, each with its own `webhook_secret`, `private_key`, and `oauth` config, to a single Shipit instance. [5](#0-4) 

Because HMAC verification is done over the full raw body using the secret selected by the (forgeable) `repository.owner.login`, and `repository.full_name` is a completely independent field within that same body, the two fields are not bound together by any check.

### Finding Description
`verify_signature` computes: `github_app = Shipit.github(organization: repository_owner)` then validates `X-Hub-Signature` against `request.raw_post` using that organization's `webhook_secret`. [1](#0-0) 

The equality that should hold is:
`organization_whose_secret_signed_the_request == organization_that_owns_the_repository_the_handler_writes_to`

But the engine only ever proves:
`HMAC(secret_of(repository.owner.login), raw_body) == X-Hub-Signature`

Since the entire `raw_body` — including `repository.full_name` — is attacker-authored plaintext when the attacker legitimately possesses *any one* organization's `webhook_secret` on this multi-tenant instance (e.g., they administer/own the GitHub App installation for Organization A, one of potentially many orgs configured on the same Shipit deployment), they can freely construct a payload where:
- `repository.owner.login = "org-a"` (used only to pick the secret for HMAC verification)
- `repository.full_name = "org-b/victim-repo"` (used by every handler to look up the actual `Repository`/`Stack`)

and sign the whole body with Organization A's secret. The signature check passes because it only validates that *some* known secret produced the signature - it never checks that the secret's organization matches the organization referenced by `repository.full_name`, which is what the handlers actually act on.

This breaks the binding rule "an organization that authenticated versus the repository that is written": the org authenticated by the signature (org A) is not required to equal the org whose repository/stack gets mutated (org B).

### Impact Explanation
With a forged `repository.full_name` pointing at an org-B stack, an attacker who only controls org-A's webhook secret can drive Shipit write-paths scoped to org B without ever having any credential, GitHub App installation, or `ApiClient` access to org B:
- `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` on every non-archived stack matching the forged branch, forcing Shipit to sync (and treat as ready-to-deploy) commit SHAs of the attacker's choosing for org B's stacks. [6](#0-5) 
- The `PullRequest` handlers (`OpenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`) resolve `Repository.from_github_repo_name(params.repository.full_name)` and call `stack.archive!`/`unarchive!`/create review stacks for org B, based entirely on attacker-supplied PR/label content signed only with org A's secret. [7](#0-6) [8](#0-7) 

Because Shipit stacks drive continuous-deployment/merge automation from synced commit/PR/status state, injecting attacker-chosen commit SHAs and PR/label state into a victim organization's stack can lead to unauthorized deploy/merge automation being triggered against org B's repository - a cross-organization write whose true origin (org B) was never authenticated. This satisfies the Critical bar of "cross-repository writes" / "an unauthorized deploy, rollback or merge" defined in scope.

### Likelihood Explanation
Requires only that the attacker legitimately controls (or has been given) the `webhook_secret` for any single organization configured on the shared Shipit instance — not a privileged Shipit account, `ApiClient` token, or any credential for the victim organization. Multi-tenant deployment of Shipit across several orgs sharing one instance is the documented, supported configuration, so this is a realistic deployment shape, not a hypothetical one. [5](#0-4) 

### Recommendation
Bind the two checks together: after resolving `repository_owner` for secret selection, additionally verify that `repository.full_name`'s owner segment matches `repository_owner` (or, more robustly, resolve the target `Repository`/`Stack` first and use *that* repository's own organization to select the webhook secret, rejecting the request if it disagrees with `repository.owner.login`). This should be enforced centrally in `WebhooksController#verify_signature` before any handler runs against `repository.full_name`. [9](#0-8) 

### Proof of Concept
1. Deploy Shipit configured with two organizations sharing one instance, per `config/secrets.*.yml`: `org-a` (attacker-controlled GitHub App/webhook secret `SECRET_A`) and `org-b` (victim, unrelated secret). [5](#0-4) 
2. Attacker builds a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, body)>` themselves, since they know `SECRET_A`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` computes `repository_owner = "org-a"`, fetches org A's `GitHubApp`, and validates the signature against org A's secret - it passes. [1](#0-0) 
6. `Webhooks.for_event('push')` runs `PushHandler`, which uses `payload.dig('repository', 'full_name')` = `"org-b/victim-repo"` to find org B's `Stack` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, mutating org B's stack state using only org A's credentials. [3](#0-2) [6](#0-5)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
