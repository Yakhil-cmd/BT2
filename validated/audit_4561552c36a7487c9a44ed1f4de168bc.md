Cross-tenant CI status forgery via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, a query with no `repository`/`stack`/organization filter. The signature check in `WebhooksController#verify_signature` only proves the payload came from *some* organization matching the `repository.owner.login` in the JSON body, but the handler that writes the `CommitStatus` never re-checks that binding against the `Commit` record(s) it mutates.

### Finding Description
The claimed binding — organization that verified the HMAC (`repository_owner` from `params.dig('repository','owner','login')`, checked in `verify_signature` via `Shipit.github(organization: repository_owner).verify_webhook_signature`) equals organization owning the `Commit` written by the handler — is broken.

Trace:
1. `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the raw JSON and dispatches to `Shipit::Webhooks.for_event(event)` handlers, passing the whole `params` hash.
2. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) picks the `GitHubApp` for `repository_owner` (org A) and verifies the byte signature against org A's `webhook_secret`. This only proves "these bytes were signed by org A"; it says nothing about which `Commit` row in the database should be affected.
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries **globally** across all `Commit` rows in the database by `sha` alone — no join/filter on `stack`, `repository`, or `repository_owner`. `Commit#create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/commit.rb:165-169`) writes a `CommitStatus` using the row's own `stack_id`, whichever stack that happens to be.
4. There is no uniqueness constraint or validation forcing `sha` to be unique across stacks/repositories — the index added in `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb` is `(stack_id, sha)`, i.e., it explicitly permits the same `sha` value to exist under multiple different `stack_id`s/repositories. There is also no `validates :sha` uniqueness check in `app/models/shipit/commit.rb`.

Exploit flow: an attacker who owns/controls a GitHub organization/repo "org-A" onboarded into Shipit (their own tenant, with its own `webhook_secret`) creates a commit whose 40-char sha is identical to a sha already present in org-B's Shipit stack (attacker can engineer this via reproducible git object construction — same tree/parents/timestamps/author/committer/message hash to identical sha, a purely local git operation requiring no org-B secrets). Attacker then triggers (or fabricates, since only org-A's signature is checked and payload content like `sha` is fully attacker-controlled) a `status` webhook POST to `/webhooks` with `X-Github-Event: status`, signed with org-A's `webhook_secret`, with `repository.owner.login` = org-A, and `sha` = the colliding value. `verify_signature` passes (org-A's own valid signature over org-A-controlled bytes). `StatusHandler#process` then matches **every** `Commit` row in the DB with that `sha`, including org-B's, and calls `create_status_from_github!(params)` on it, writing a `CommitStatus` (potentially `state: "success"`) onto org-B's commit.

Existing guards do not prevent this: `verify_signature` binds signature validity to org-A only, not to the specific `Commit`/stack being mutated; `drop_unhandled_event` and `ExplicitParameters` schema only validate presence/type of `sha`/`state`, not repository scope; there is no `require_permission!` or stack-scoping check inside `Webhooks::Handlers::Handler`/`StatusHandler`.

### Impact Explanation
An attacker fully controlling only their own onboarded org/repo can write a `CommitStatus` (including `state: "success"`) onto an unrelated organization's `Commit`, directly flipping `Commit#deployable?`/`Commit#blocked?` semantics used to gate merges and deploys for org-B's stack — this is a cross-repository/cross-tenant write of deploy-gating CI status, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge." It is repeatable against any stack/commit whose sha the attacker can predict or reproduce, and blast radius spans every tenant sharing the Shipit instance.

### Likelihood Explanation
Preconditions: attacker needs their own Shipit-onboarded org (any GitHub org/repo added to the Shipit instance's config with its own `webhook_secret` — realistic if Shipit is a multi-tenant/internal platform onboarding many teams' repos) and the ability to construct a git commit whose sha collides with a target commit in another repo. Colliding an *arbitrary* target sha requires either (a) coincidental sha reuse (e.g., both derived from identical empty/boilerplate commits — plausible for automated bot commits, initial commits, or cherry-picked identical patches across repos) or (b) sha collision engineering (currently infeasible for SHA-1 preimage but git object duplication with identical content is trivial and common in practice, e.g., copied repos/forks/vendored subtrees, or two stacks referencing the same shared monorepo commit). The attacker cost is a normal webhook POST from their own onboarded org; no privileged Shipit role or secret from org-B is needed. The vulnerability itself (missing scoping) is unconditionally present in the code regardless of collision likelihood.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogously other handlers using bare `sha`/`ref` lookups, e.g. check_run/push handlers) by repository: join through `Stack`/`Repository` and filter by `repository.owner == repository_owner` and/or `repository.name == params.dig('repository','name')` from the payload before writing any status, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner, name: repo_name })`. Alternatively, resolve the handler dispatch per-repository (already partially done via `repository_owner`) and pass the target `Repository`/`Stack` explicitly into `Handler#call` so `process` can filter `commit.stack.repository == repository`.

### Proof of Concept
Under `test/models/webhooks/handlers/status_handler_test.rb` (or similar), add a minitest:
```ruby
test "does not write a status onto a commit belonging to a different repository" do
  repo_a = shipit_stacks(:shipit).repository  # org-A repo
  repo_b = shipit_stacks(:shipit2)&.repository || create_stack!(repository: shipit_repositories(:cocoapods)).repository # org-B repo

  colliding_sha = "a" * 40
  commit_a = repo_a.stacks.first.commits.create!(sha: colliding_sha, message: "org-A commit")
  commit_b = repo_b.stacks.first.commits.create!(sha: colliding_sha, message: "org-B commit")

  params = Shipit::Webhooks::Handlers::StatusHandler.params_schema.new(
    sha: colliding_sha, state: 'success', context: 'ci/attacker'
  )

  # Simulate handler invocation as would be reached only after org-A's webhook signature verified
  Shipit::Webhooks::Handlers::StatusHandler.new.call(params)

  commit_a.reload
  commit_b.reload

  assert commit_a.statuses.exists?(state: 'success'), "expected commit_a (same org) to receive status"
  refute commit_b.statuses.exists?(state: 'success'),
    "SCOPE VIOLATION: org-B's commit received a status derived from org-A-signed bytes"
end
```
Both sides of the binding before: `verified_org == org-A`; after write: `commit_b.stack.repository.owner == org-B` yet the status was written — the equality `verified_org == repository owning the mutated Commit` fails, confirming the cross-tenant scope violation.
