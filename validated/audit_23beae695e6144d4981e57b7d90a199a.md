### Title
Cross-Repository Status Forgery via Unscoped `Commit.where(sha:)` Lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves which `Commit` record to update purely by `sha`, with no scoping to the repository/organization whose webhook signature was actually verified. Because Git commit hashes are content-addressed, an attacker who legitimately controls *any* GitHub organization onboarded to this Shipit instance can reproduce a byte-identical commit (same tree, parent, author, committer, timestamps, message) inside their own attacker-controlled repository, obtaining an identical SHA to a commit that exists in a victim stack tracked by the same Shipit instance. They can then trigger a `status` webhook from their own, properly-authenticated organization referencing that SHA, and Shipit will attach the forged status to the victim's `Commit` row.

### Finding Description
The webhook signature check in `WebhooksController#verify_signature` only proves that the payload was signed by *some* configured GitHub organization — it binds the signature to `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), then fetches the app for that organization: [1](#0-0) [2](#0-1) 

The base `Handler` class shows the *intended* binding: most handlers scope subsequent writes to the stacks belonging to the repository named in the payload via `Repository.from_github_repo_name(repository_name)`: [3](#0-2) 

`StatusHandler`, however, does not use `stacks`/`repository_name` scoping at all — it looks up commits **globally by SHA only**, across every stack/repository tracked by the Shipit instance: [4](#0-3) 

This breaks the equality the signature verification is supposed to establish: `organization that authenticated == repository that is written`. The signature only proves the payload came from organization *A* (the attacker's own configured org), but `StatusHandler` writes to whatever `Commit` row happens to match the given `sha`, which may belong to an entirely different organization/repository *B*.

Since Git SHAs are computed purely from commit content (tree, parent(s), author, committer, message, timestamps) and not from which repository stores them, an attacker can reconstruct a byte-identical commit object (all of this metadata is visible on any commit page/API for a public or otherwise-visible repo) inside a repository they control, producing the exact same SHA that already exists as a `Commit` in a victim's Shipit-tracked stack. They then perform a normal GitHub `status` API call (or push) on their own repo/commit, which GitHub signs with the attacker's own real `webhook_secret` — passing `verify_signature` legitimately — while `params.sha` collides with the victim's commit.

`StatusHandler#process` will then call `commit.create_status_from_github!(params)` on the victim's `Commit`, letting the attacker set an arbitrary `state` (e.g. `success`), `context`, `description`, and `target_url` for that commit.

### Impact Explanation
Commit statuses gate deployability in `Stack#branch_status`, which inspects `commit.status.simple_state` for undeployed commits to decide whether the branch is in a deployable state: [5](#0-4) 

By forging a `success` status on a victim's blocking/pending commit from an unrelated, attacker-controlled organization, an attacker with no relationship to the victim's repository, GitHub org, Shipit session, or API tokens can flip a required CI gate to green and enable an **unauthorized deploy** of the victim stack — satisfying the Critical impact bar ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
The attacker needs: (1) their own organization/repository already onboarded to the same multi-tenant Shipit instance (a normal, unprivileged tenant relationship, not a privileged Shipit account), and (2) knowledge of the exact commit metadata of the target commit (readily available via GitHub's public commit/API pages for any repo the attacker can see, or for repos they collaborate on). Reproducing an identical commit object with matching author/committer timestamps is straightforward since Git allows setting these explicitly (`GIT_AUTHOR_DATE`, `GIT_COMMITTER_DATE`, exact tree contents, exact message). No credential theft, session, or GitHub App private key is required — only the ability to author a webhook-triggering GitHub event (a push or a `POST .../statuses`) on a repository the attacker legitimately controls.

### Recommendation
Scope `StatusHandler#process` (and any other unscoped handler) to the repository actually named in the payload, mirroring the base `Handler#stacks` pattern, e.g. restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Stack`/`Repository` derived from `payload.dig('repository','full_name')`, so a commit can only be updated by a webhook whose verified organization/repository actually owns that commit's stack.

### Proof of Concept
1. Onboard `attacker-org/attacker-repo` as a legitimate Shipit stack (normal tenant onboarding), obtaining a real, working `webhook_secret` for `attacker-org`.
2. Identify a target commit in `victim-org/victim-repo` (a stack tracked by the same Shipit instance) — read its tree SHA, parent SHA(s), author/committer name, email, and exact timestamps from GitHub's public commit view/API.
3. Locally create a commit object with identical tree contents, parent, author/committer info and timestamps (using `GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE` env vars and `git commit-tree`), producing the identical SHA in `attacker-repo`.
4. Push this commit to `attacker-repo`, then call `POST /repos/attacker-org/attacker-repo/statuses/{sha}` with `state: success` (or trigger it via GitHub UI/API in a way that fires the `status` webhook).
5. GitHub signs and delivers the webhook to Shipit using `attacker-org`'s real `webhook_secret`; `WebhooksController#verify_signature` passes since it is validated against `attacker-org`.
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, matching the victim's `Commit` row (same SHA, different repo), and calls `create_status_from_github!`, writing a forged `success` status onto `victim-org/victim-repo`'s commit — potentially unblocking an unauthorized deploy of the victim stack.
