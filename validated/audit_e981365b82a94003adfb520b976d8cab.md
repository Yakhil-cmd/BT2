### Title
Webhook HMAC signature is verified against the organization from an unsigned-binding payload field, while writes are performed against an unrelated `repository.full_name`/`sha` — enabling cross-repository status/state injection - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives the GitHub App/organization used to validate the HMAC signature from the payload itself (`repository.owner.login` or `organization.login`), not from any independently trusted source [1](#0-0) . Once the signature check passes, the actual write logic in `Shipit::Webhooks::Handlers::Handler` resolves the target `Repository`/`Stack` using a *different* payload field, `repository.full_name` [2](#0-1) , and handlers such as `StatusHandler` write directly against `Commit.where(sha: params.sha)` with no additional check that the commit belongs to the org that was actually authenticated [3](#0-2) .

### Finding Description
This is the same class of bug as the Sherlock M-2 report: a security-relevant check is performed on one piece of state (`checkpointProtection` reads the *account's* last checkpoint), while the operation actually acts on a different, related-but-independently-mutable piece of state (whether the *slash-target* itself was recently touched). Here, the binding that should hold is:

`organization whose secret validated the HMAC` == `organization that owns the repository/commit actually mutated`

In the webhook flow:
1. `repository_owner` is read straight out of the untrusted JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [4](#0-3) .
2. That value selects which GitHub App config (and therefore which `webhook_secret`) is used to verify `X-Hub-Signature` [5](#0-4) .
3. If verification succeeds, `Shipit::Webhooks.for_event(event)` handlers run against the raw parsed `params`, and each handler independently re-reads `repository.full_name` from the same body to find the `Stack`/`Repository`/`Commit` to act on [6](#0-5) , or, for `status`, resolves target rows purely by `sha` with no repository scoping at all [3](#0-2) .

Nothing in the code enforces that `repository.owner.login` (the field bound to the verified signature) equals the owner embedded in `repository.full_name` (the field the handler actually acts on), or that the `sha` used by `StatusHandler` belongs to a commit under that same, authenticated organization.

A user who legitimately configures a Shipit GitHub App installation/webhook secret for **their own** organization (`attacker-org`) knows that secret and can therefore produce a validly-signed HTTP request body to Shipit's `/webhooks` endpoint. Nothing prevents them from putting arbitrary, unrelated values into `repository.full_name` (for `push`/`check_suite`) or `sha` (for `status`) inside that same signed body — fields that were never part of the "does this signature match this organization" check, only used afterwards by handlers that trust the payload's content wholesale.

### Impact Explanation
Concretely reachable, unprivileged-but-Shipit-registered-org write path:
- `StatusHandler` creates a CI `Status` for an arbitrary `sha` supplied in the attacker's self-signed payload, with no verification that the commit belongs to a stack under the organization whose secret produced the signature [3](#0-2) . If that `sha` matches a commit belonging to a victim repository/stack tracked by the same Shipit instance, the attacker can inject fabricated CI state (e.g., a fake "success") for that victim commit.
- `PushHandler`/`CheckSuiteHandler` similarly resolve the acted-upon `Stack` via `Repository.from_github_repo_name(repository_name)` taken from the unverified `full_name` field [7](#0-6) [8](#0-7) , letting an attacker who controls only their own org's webhook secret trigger a `GithubSyncJob`/check-run refresh against a completely different, victim-owned repository's stack.

Because commit CI status is used by Shipit to gate merges/deploys elsewhere in the engine, forging status for a victim's commit is a cross-repository write that can influence deploy/merge decisions on a repository the attacker does not control and was never authorized to touch — this satisfies the "cross-repository writes" Critical-impact bucket.

### Likelihood Explanation
Requires only that the attacker already has a legitimately configured Shipit GitHub App/organization on the same Shipit instance (i.e., they know a `webhook_secret` for *some* org registered in `Shipit.github`) — this is a much lower bar than compromising the target org or obtaining `GITHUB_TOKEN`/`api_clients_secret`. It does not require a Shipit session, an `ApiClient` token, or repository write access to the victim repo, matching the "unprivileged attacker" framing of the analog.

### Recommendation
After verifying `X-Hub-Signature` against `repository_owner`, re-validate that every payload field subsequently used to resolve the target entity (`repository.full_name`'s owner segment, and any `sha`/commit lookups in `StatusHandler`) is consistent with that same, already-authenticated owner/organization before performing any write — i.e., bind the "authenticated organization" and the "organization actually written to" so they cannot diverge within a single signed request.

### Proof of Concept
1. Attacker registers/operates `attacker-org` as a Shipit-tracked GitHub organization and knows its `webhook_secret`.
2. Attacker crafts a `status` event JSON body: `{"sha": "<victim-commit-sha>", "state": "success", "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/some-repo"}, ...}` and computes `X-Hub-Signature` with `attacker-org`'s webhook secret.
3. POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org`, and the signature validates successfully (line 24-30 of `webhooks_controller.rb`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, matching the victim's commit purely by `sha` with no organization/ownership check, creating a forged CI status entry for a repository the attacker does not own.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
