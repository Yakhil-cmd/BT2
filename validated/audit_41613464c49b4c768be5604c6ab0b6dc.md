### Title
Webhook signature verification is bound to the wrong organization, allowing forged `status`/`push` events for a victim's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GithubApp`/`webhook_secret` to check the HMAC signature against using `repository.owner.login` (or `organization.login`) from the attacker-supplied JSON body. The event handlers that actually mutate state (`StatusHandler`, `PushHandler`, etc.) resolve their target `Commit`/`Repository`/`Stack` from a *different* field of the same body (`params.sha` globally, or `repository.full_name`). Nothing ties the organization whose secret was checked to the repository/commit that is ultimately written to.

### Finding Description
`verify_signature` computes the authenticating organization purely from payload content: [1](#0-0) [2](#0-1) 

It fetches a per-organization `GithubApp` and validates the signature with that org's `webhook_secret`: [3](#0-2) 

Critically, if that organization's `webhook_secret` is blank/unset, `verify_webhook_signature` returns `true` unconditionally, so **any** signature (even none) is accepted for that organization.

Once verification passes, the event handler resolves what to actually act on from a separate field of the same attacker-controlled body:
- `StatusHandler#process` looks up commits **globally by sha, with no repository scoping at all**: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) 
- `PushHandler`/other handlers scope via `Handler#stacks`, which uses `payload.dig('repository', 'full_name')` — a value independent of the `repository.owner.login` used for signature verification: [5](#0-4) 

Because the JSON body is entirely attacker-controlled (only the header signature must "verify"), an attacker can:
1. Set `repository.owner.login` (or `organization.login`) to any organization configured in the multi-tenant Shipit deployment whose `webhook_secret` is blank (or one whose secret the attacker knows, e.g. their own sandbox org that also has the Shipit GitHub App installed).
2. Set the payload's `sha`/`repository.full_name` to point at a commit/stack belonging to a completely different, secret-protected organization.

The signature check passes trivially against organization A (blank secret), while the mutation is applied to organization B's stack — breaking the binding "organization that authenticated == repository that is written," exactly the class of check-then-act mismatch called out in the report (verifying one thing, acting on another).

### Impact Explanation
- `StatusHandler` has no repository scoping whatsoever, so a forged `status` webhook can flip any existing commit's CI state to `success` for a stack under a different, secret-protected organization. If that stack has `continuous_deployment` enabled, a success status can trigger `trigger_continuous_delivery`/an unauthorized deploy, matching the "unauthorized deploy" impact criterion.
- `PushHandler` can queue a `GithubSyncJob` with an attacker-chosen `expected_head_sha` for a victim's stack once cross-org signature confusion is achieved via `repository.full_name`.
- This effectively bypasses the per-organization webhook trust boundary that `webhook_secret` is meant to enforce.

### Likelihood Explanation
Requires: (a) a multi-organization Shipit deployment, and (b) at least one configured organization/GithubApp with a blank `webhook_secret` (explicitly supported/expected per `verify_webhook_signature`'s early-return), or one whose secret the attacker legitimately has (e.g., an org they administer that is also configured on the same Shipit instance). Given `webhook_secret` is documented as optional per-org config, this is a realistic operational configuration, not a hypothetical one.

### Recommendation
Bind signature verification to the same repository/organization that the handler will act on: derive the authenticating organization from the exact `repository.full_name`/owner used later by `Handler#stacks`, and make `StatusHandler` (and any handler operating on bare `sha`) scope its lookups to the repository resolved from the verified payload rather than a global `Commit.where(sha:)`. Additionally, consider requiring `webhook_secret` to be present for all configured GitHub Apps/organizations rather than silently trusting unsigned payloads.

### Proof of Concept
1. Configure two organizations in `Shipit.github` config: `org-a` with `webhook_secret: nil`/blank, and `org-b` (victim) with a real `webhook_secret`, both with stacks tracked by Shipit.
2. POST to `/webhooks` with header `X-Github-Event: status`, no or arbitrary `X-Hub-Signature`, and body:
```json
{
  "repository": {"owner": {"login": "org-a"}, "full_name": "org-a/anything"},
  "sha": "<sha of a commit belonging to org-b's tracked stack>",
  "state": "success"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "org-a")`, whose blank `webhook_secret` makes `verify_webhook_signature` return `true` regardless of signature. [3](#0-2) 
4. `StatusHandler#process` then updates the status of the commit matched purely by `sha` — belonging to org-b's stack — creating a forged success status and potentially triggering continuous deployment for org-b's stack without ever knowing org-b's real `webhook_secret`. [4](#0-3)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
