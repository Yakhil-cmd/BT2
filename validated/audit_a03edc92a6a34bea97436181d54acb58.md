This is a standalone `promise_batch_create`/`promise_batch_action_transfer` — it is **not** chained (`.then(...)`) to the promise that performs the real transfer/ERC-20 call, and is not chained to the `rlp_execute_callback` that determines final success/failure. The actual action promise is only constructed later, further down the function, and can even fail to be constructed (`action_to_promise(target, action)?` at line 469 returns early with `Err`, e.g. `UnsupportedAction::AddFullAccessKey` or the `"Expected function call action..."` branch in `nep_141_storage_balance_callback`), after the fee refund promise has already been created. Because both promises are dispatched from the same receipt, batch/data-receipt ordering does not gate the refund on the outcome of the real action.

### Why this matches the report's bug class
Just like `buy_state_rebalance` charging its rebalance fee without verifying that `from_amount`/`to_amount` actually moved funds, `inner_rlp_execute` schedules the fee-refund transfer without validating that the corresponding user-intended action (`ft_transfer`, base transfer, etc.) will actually execute or succeed. Both are "charge-on-intent, not charge-on-effect" bugs: the fee is deducted from the victim account (the wallet) based on unvalidated/unchecked downstream effects. [2](#0-1) 

### Title
Wallet Contract relayer fee is refunded before/independent of the underlying action's success - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
`inner_rlp_execute` schedules the NEAR transfer that compensates the relayer for a fee-bearing Ethereum-emulated action (`EOABaseTokenTransfer`/`ERC20Transfer`) as an independent promise, before the promise implementing the actual transfer/ERC-20 call is even created, and without linking success of the latter to the former.

### Finding Description
`inner_rlp_execute` parses the RLP-encoded Ethereum transaction into a Near `Action` and a `TransactionKind`. When the resulting `TransactionKind` carries a non-zero `fee` (used to compensate a relayer for gas), the code immediately builds a standalone promise batch to transfer that fee to `predecessor_account_id` (the relayer) [1](#0-0) . Only afterwards does the function build the promise that performs the actual instructed action, via `action_to_promise` for the generic case, or dedicated branches for `ERC20Transfer`/`EOABaseTokenTransfer` [3](#0-2) . That second promise can fail to even be created (`action_to_promise(target, action)?` returns `Err` and the whole call aborts with an error) or can fail at execution time (e.g. the `ft_transfer` call itself reverts on insufficient token balance) — in either case the relayer-fee refund transfer has already been dispatched and is not rolled back, because it is a sibling promise/receipt rather than a dependent one.

### Impact Explanation
The wallet's NEAR balance can be drained via the fee refund even when the "real" action the user paid the fee for never completes. Since `predecessor_account_id != current_account_id` is the only gating condition (i.e., any relayer other than the wallet itself), a relayer that is authorized to call `rlp_execute` (via `register_relayer`'s `FunctionCall` access key, see `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/relayer.rs:21-52`) collects the fee unconditionally, decoupling payment from delivery of the paid-for action. This directly matches the OS-SYM-ADV-01 pattern of "fee charged without verifying the underlying operation had any effect."

### Likelihood Explanation
Triggering it requires control of, or collusion with, a registered relayer for the specific wallet contract instance and requires the (Ethereum-signed) transaction to specify a nonzero `fee`. This limits blast radius mostly to the wallet owner's own relayer arrangement rather than an arbitrary third party being drained, and the per-instance `has_in_flight_tx` guard and nonce increment prevent unlimited repeated replay of the exact same signed transaction. Exploitation would need a relayer that intentionally submits transactions engineered to fail downstream (e.g., NEP-141 transfers that revert) while still collecting the attached fee.

### Recommendation
Chain the relayer fee-refund transfer to the same promise/callback that determines the outcome of the underlying action (e.g., pay the fee only inside `rlp_execute_callback` after observing `PromiseResult::Successful`, or make the fee transfer a dependent step of the action promise itself), so the relayer is compensated only when the user's intended action actually executes successfully.

### Proof of Concept
1. Wallet owner grants a `FunctionCall` access key to a relayer via `register_relayer` (as in `test_register_relayer`, `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/relayer.rs:26-52`).
2. Owner signs an Ethereum transaction representing an ERC-20 `transfer` call with a nonzero `gas_price` (mapped to `fee`) but insufficient token balance so the underlying `ft_transfer` will fail at execution time, or otherwise crafts calldata such that `action_to_promise` returns `Err` (e.g., attempting an unsupported `AddFullAccessKey` action).
3. Relayer submits this via `rlp_execute`. `inner_rlp_execute` immediately fires the fee-refund transfer to the relayer at lines 382-384 before constructing the real action promise.
4. The real action later fails (contract-level revert) or `action_to_promise` errors out; `rlp_execute_callback`/error path reports failure to the caller, but the fee-refund transfer to the relayer has already completed and is not reverted.
5. Repeating with different nonces (each valid once) lets a colluding relayer keep collecting fees while the wallet's paid-for action never actually happens, draining the wallet's NEAR balance over many transactions.
