### Title
Silent hang / stalled AA formula evaluation on empty nearley parse results - (File: formula/evaluation.js)

### Summary
CVE-2020-13649 concerns JerryScript's `js-scanner.c` mishandling an edge case in the parser's result-list handling (empty/NULL result after certain conditions), leading to a NULL pointer dereference or assertion failure instead of a clean error. `formula/evaluation.js`'s final result-dispatch logic exhibits an analogous "unhandled parser result state" defect: it assumes the nearley parser always yields either exactly one result or more than one, but never explicitly handles the case of zero results, silently doing nothing instead of surfacing an error.

### Finding Description
`exports.evaluate` parses the oscript/ojson formula with nearley and then dispatches on the parse result: [1](#0-0) 

The dispatch logic is:
- if `parser.results` is truthy, has length `1`, and `parser.results[0]` is truthy → evaluate it and always invoke `callback`.
- otherwise (the `else` branch) → only handles the sub-case `parser.results.length > 1` ("ambiguous grammar") and invokes `callback('ambiguous grammar', null)`.

There is no `else` for the case where `parser.results.length === 0` (a syntactically-fed-but-not-fully-reduced formula, which nearley represents as an empty results array rather than throwing) or where `parser.results[0]` is falsy despite `length === 1`. In those situations, `callback` is **never invoked** — the asynchronous AA/formula evaluation call simply hangs forever with no error and no result.

This mirrors the CVE-2020-13649 bug class: the parser/scanner has an "in-between" state (partial or degenerate parse) that the surrounding code fails to treat as an error, instead of crashing (as in JerryScript) it leaves the ocore evaluation pipeline stuck in an unresolved state.

The related `formula/validation.js` parser dispatch (used to pre-validate formulas before evaluation) uses a similarly shaped try/catch around `nearley.Parser`/`.feed()`, but does not perform the same explicit `results.length` checks before invoking downstream logic, so it is unclear whether validation reliably rejects every formula that would produce zero parse results in evaluation — this repo does not vendor the `nearley` library source, so the precise conditions under which `.feed()` succeeds without throwing yet yields `results.length === 0` could not be fully confirmed from the indexed code.

### Impact Explanation
`formula/evaluation.js`'s `exports.evaluate` is the core interpreter for both AA (`getters`, trigger response formulas) evaluation and address-definition formula evaluation. It is reachable by any user who defines an AA (`autonomous agent` ojson definitions with formulas) or by anyone who sends a trigger to an AA whose formula, params, or state cause a formula string with the degenerate parse property to be constructed and (re-)evaluated at runtime (formulas can be dynamically built, e.g. via string concatenation into `${...}` expressions, `bounce`, `remote_func_call` targets, etc.). If such a formula reaches the "zero results, non-ambiguous" branch, `callback` is never called, which:
- stalls the AA trigger-response computation used during unit/bounced-response construction, and
- since this evaluation occurs synchronously within the validation/response-generation pipeline for a unit, it can stall processing of that unit on any node evaluating it, causing that node to be unable to finalize/confirm the affected unit — a "network unable to confirm new units" condition scoped to units interacting with the affected AA, and inconsistent behavior between nodes if the hang is non-deterministic (e.g., dependent on garbage collection/other node-local factors) — potentially leading to disagreement about validity or stability among nodes evaluating the same trigger.

### Likelihood Explanation
Reachability requires constructing/feeding a formula string to nearley such that `.feed()` succeeds (no thrown parse error) yet yields an empty `results` array rather than one full derivation — a known nearley behavior for partially-matched/ambiguous EBNF-heavy grammars (this repo's `formula/grammars/oscript.js` grammar is generated with many EBNF macro expansions). Because `formula/validation.js` performs a structurally similar but not necessarily identical results check before allowing execution, whether a genuinely malicious/attacker-controlled formula can reach this exact degenerate state through the normal AA-definition and trigger-submission path could not be conclusively confirmed from the available code (nearley's internal `.results` implementation is an external dependency not present in the indexed repository content).

### Recommendation
Add an explicit `else if (!parser.results || parser.results.length === 0)` branch in `exports.evaluate` (and audit the analogous dispatch path in `formula/validation.js`) that calls `callback('parse failed: no results', null)` (or similar), ensuring every parse outcome — zero results, one result, or multiple ambiguous results — always resolves the callback instead of silently hanging.

### Proof of Concept
Could not be fully constructed without the ability to run `nearley` against `formula/grammars/oscript.js`/`oscript.ne` to identify a concrete formula string that triggers `.feed()` success with `results.length === 0`. This would need to be validated by instrumenting `parser.feed(formula)` in `formula/evaluation.js` (around line 109) and fuzzing formula inputs to find one where `parser.results` is an empty array after a successful feed, then confirming that `exports.evaluate`'s `callback` is never invoked for that input.
