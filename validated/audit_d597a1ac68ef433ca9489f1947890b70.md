### Title
`data_feed[[...]]` formula op lets an AA read a single unconfirmed (unstable) oracle value with no minimum observation window, enabling instant price manipulation - (File: data_feeds.js, formula/evaluation.js)

### Summary
The reported bug is about a TWAP window of only 10 seconds being trivially manipulable because it reflects the state of a single block rather than an average over many blocks/time. The closest reachable analog in `ocore` is the `data_feed` oscript operator used inside Autonomous Agents: when evaluated inside an AA (`bAA=true`), it is allowed to read a data-feed value from a unit that is **not yet stable** (not yet part of the finalized DAG), i.e. a value with zero confirmation depth. This is the DAG-based equivalent of using a price snapshot from "within a single block" — there is no minimum age/stability requirement analogous to a TWAP window, so a single, just-posted, adversary-controlled unit can be consumed immediately by dependent AA logic.

### Finding Description
`formula/evaluation.js`, case `'data_feed'`, calls: [1](#0-0) 
`dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ifseveral, objValidationState.last_ball_timestamp, function(objResult){...})`, passing `bAA` (true when the formula is being evaluated as part of an AA's response/bound state).

In `data_feeds.js`, `readDataFeedValue` treats this flag as `bIncludeUnstableAAs`: [2](#0-1) 

When set, it scans `storage.assocUnstableMessages` — units that have not achieved MC stability — and if exactly one candidate matches, it is returned immediately as the data-feed value with no further age or count-of-confirmations requirement: [3](#0-2) 

This means a value posted by an oracle in a brand-new, still-unstable unit (potentially the very same round of units that also contains the AA-triggering unit) can be consumed by the AA's formula the moment it is broadcast, with no equivalent of an averaging/observation window. Anyone who can get an oracle address to post a data point (or an AA author who designs the AA to trust unstable feeds, then a trigger sender who races to trigger right after a manipulated post) can push a single, momentary, unconfirmed value into fund-affecting AA logic (e.g. exchange rate, collateral ratio, liquidation threshold) before the network has had a chance to reach consensus/stability on it — the DAG analog of "TWAP based on a single block."

By contrast, the non-AA / stable path (`dataFeedByAddressExists`, `readDataFeedByAddress`) only reads from `kvstore` records for **stable** data feeds, i.e., values that have gone through MC stabilization: [4](#0-3) 
There is no similar restriction applied to the unstable/AA fast-path.

### Impact Explanation
An AA whose payout, collateral valuation, exchange rate, or liquidation decision depends on `data_feed[[...]]` reading unstable oracle data can be manipulated by whoever controls (or colludes with) the oracle address to post a single, momentary, non-finalized data point and then immediately fire (or wait for) an AA trigger that consumes it — before the value has any chance to be corrected, contested, or averaged. This can produce unauthorized fund transfers, incorrect payouts, or AA fund loss, directly matching the "Accept only concrete... AA fund loss" criterion.

### Likelihood Explanation
Reaching this path requires only posting a `data_feed` message from an address the target AA is configured to trust as an oracle, and then having any trigger evaluate the AA's formula while that message is still unstable — both of which are actions available to an ordinary unit poster / AA trigger sender, no privileged network role needed. AA authors who intend to read the *very latest* value on purpose (rather than a stabilized value) commonly use this unstable-read behavior for responsiveness, making the pattern realistic and exploitable in production AAs relying on this feature for pricing.

### Recommendation
For price/financial-decision–critical data feeds read from within AAs, require either: (a) that the feed value be sourced only from stable (`is_stable=1`) data, forcing consumers to explicitly opt into unstable reads (e.g. gate it behind a new formula option rather than making it implicit for all `bAA` evaluations), or (b) enforce a minimum confirmation/stability depth or multi-sample averaging window on unstable data-feed reads used by AA formulas, mirroring the TWAP fix of widening the observation window instead of trusting an instantaneous, unconfirmed value.

### Proof of Concept
1. Deploy/target an AA whose formula includes `data_feed[[oracles="ORACLE_ADDR", feed_name="price"]]` used to compute a payout or swap rate, with `unstable_opts`/`bAA` context enabling the unstable read path shown in `data_feeds.js:205-249`.
2. As the oracle (or a party who can convince/collude with the oracle to post once), post a single unit containing `data_feed` message with an extreme, favorable `price` value; do not wait for it to stabilize.
3. Immediately submit an AA trigger unit that references this still-unstable oracle unit in its DAG ancestry (`latest_included_mc_index` within `[min_mci, max_mci]`) so `readDataFeedValue`'s `bIncludeUnstableAAs` branch finds exactly one candidate and returns it right away, before any competing/opposing price data can be posted or before the unit could be orphaned/replaced.
4. The AA computes its payout using this momentary manipulated value, resulting in an incorrect (attacker-favorable) fund transfer — analogous to exploiting a single-block TWAP snapshot.
