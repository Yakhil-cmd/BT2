### Title
Cross-organization webhook forgery: signature scope selected by unauthenticated `repository.owner.login`/`organization.login` field, while handlers act on the unrelated `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to verify the HMAC signature against by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted JSON body, then hands the *same* body to handlers that instead resolve the target `Repository`/`Stack` from `repository.full_name`. Nothing binds these two fields together, so a valid signature computed with one organization's `webhook_secret` can be attached to a payload whose `repository.full_name` points at a completely different organization's repository.

### Finding Description
`verify_signature` derives the signing org purely from request content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a distinct `GitHubApp` (and its own `webhook_secret`) per organization from `secrets.github`, explicitly supporting multiple tenants/organizations on one Shipit instance: [3](#0-2) 

Once the signature check passes (`verify_webhook_signature` only performs an HMAC comparison, unaware of *which* repository is being acted on), `create` hands the raw parsed body straight to the handlers: [4](#0-3) 

But every handler resolves its target `Repository`/`Stack` from `repository.full_name`, a field that is never checked against `repository.owner.login`: [5](#0-4) [6](#0-5) 

The equality that should hold but doesn't:
`organization whose webhook_secret authenticated the request` == `organization that owns the repository the handler mutates`.

An attacker who legitimately administers Organization A's GitHub webhook (and therefore knows/controls A's `webhook_secret`, which is a normal, unprivileged action for any org owner wiring up their own repo to a shared Shipit instance) can:
1. Build a payload with `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/victim-repo"`.
2. Sign it with OrgA's `webhook_secret`.
3. POST it to `/webhooks`.

`verify_signature` resolves `Shipit.github(organization: "OrgA")` and the HMAC check succeeds, since it was computed correctly for OrgA. The handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) then looks up `Repository.from_github_repo_name("OrgB/victim-repo")` and acts on OrgB's Stack — an organization the attacker never authenticated as and has no legitimate access to.

### Impact Explanation
This lets an attacker who only controls their own organization's webhook secret forge authenticated-looking webhook events against any other organization's stacks tracked by the same Shipit instance, e.g.:
- `push` events force `stack.sync_github(expected_head_sha: ...)` on a victim stack.
- `status`/`check_suite` events inject forged commit statuses/check runs, which can influence deploy safety checks (`safe to deploy` gating) for a victim's repository.
- `membership`/`pull_request` events can create/alter Teams, Memberships, and ReviewStacks tied to the victim's repository.

This is a cross-organization write into state the attacker does not own, matching the "Critical — cross-repository writes" bucket, because it lets an unprivileged actor (an admin of some unrelated org configured in the same multi-tenant Shipit deployment) inject events that mutate a different organization's repository/stack state without ever authenticating as that organization.

### Likelihood Explanation
This requires a multi-organization Shipit deployment (i.e., `secrets.github` configured with more than one organization key, which `github_organizations` explicitly supports) where the attacker administers or controls the webhook secret for at least one of the configured organizations — a normal, unprivileged action available to any GitHub org owner who legitimately connects their org's repos to the shared instance. No `ApiClient` token, `api_clients_secret`, GitHub App private key, or Shipit session is required — only the ability to compute a valid HMAC with a secret the attacker legitimately possesses for their own org.

### Recommendation
Bind the verified signature to the exact repository being mutated instead of an org name pulled from the payload: after determining `event`/`repository_owner`, re-derive the organization strictly from `repository.full_name`'s owner segment (or resolve the target `Repository` first, then verify the signature using that repository's own known/expected GitHub organization/app), rejecting the request if `repository.owner.login`/`organization.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` in `secrets.github` (a supported deployment mode per `Shipit.github_organizations`).
2. As the administrator of `OrgA`'s GitHub webhook (attacker), know `OrgA`'s `webhook_secret` (you set it when wiring your org's webhook to Shipit).
3. Build a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
4. Compute `X-Hub-Signature: sha1=HMAC_SHA1(OrgA_webhook_secret, body)`.
5. POST to `/webhooks` with `X-Github-Event: push`.
6. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches OrgA's app, and the signature verifies successfully.
7. `PushHandler#process` resolves stacks via `repository.full_name = "OrgB/victim-repo"` [7](#0-6)  and triggers `stack.sync_github(expected_head_sha: "deadbeef")` on `OrgB`'s stack, despite the request never having been signed by `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
