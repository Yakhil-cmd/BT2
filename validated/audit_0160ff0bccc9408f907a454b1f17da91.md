### Title
Arbitrary, unvalidated `pool_creator` in `initialize_with_permission` can permanently freeze accrued creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` lets the pool-creating `payer` designate an arbitrary, unchecked `creator` account as the pool's `pool_creator`. This value is never validated to be a signer-capable address, related to `payer`, or otherwise able to receive/move tokens. Once swaps accrue creator fees into `pool_state.creator_fees_token_0/1`, the only two ways to redeem them (`collect_creator_fee` and `collect_creator_fee_permissionless`) either require `pool_creator` itself to sign, or send the funds into an ATA whose *authority* is `pool_creator`. If `pool_creator` is set to an address with no controllable private key (e.g. a mint, a foreign PDA, a burn address, or simply a typo'd pubkey), the accrued creator fees become permanently locked with no code path to recover them.

### Finding Description
In `InitializeWithPermission`, `creator` is declared as a bare `UncheckedAccount` with no constraints: [1](#0-0) 

The permission check in this instruction only gates the `payer` (via the `permission` PDA keyed on `payer.key()`), not the `creator` field: [2](#0-1) 

`creator.key()` is written directly into `pool_state.pool_creator` at pool initialization with no verification that it is a real, controllable account: [3](#0-2) [4](#0-3) 

Trading activity subsequently accrues `creator_fees_token_0`/`creator_fees_token_1` on the pool via `update_fees`: [5](#0-4) 

The only two ways to withdraw those fees both hard-depend on `pool_creator` being usable:
- `collect_creator_fee` requires `creator` to be a `Signer` matching `pool_state.pool_creator`: [6](#0-5) 
- `collect_creator_fee_permissionless` allows anyone to trigger collection, but the destination ATA's `associated_token::authority` is still `creator` (i.e. `pool_creator`), so the tokens land under an authority that may never be able to sign a further transfer: [7](#0-6) [8](#0-7) 

There is no `update_pool_creator`/admin instruction anywhere in the program to correct or reassign `pool_creator` after pool creation, confirmed by the fact that `pool_creator` is only referenced in `pool.rs`, `collect_creator_fee.rs`, and `collect_creator_fee_permissionless.rs`. This is directly analogous to the `OgvStaking.stake(amount, duration, to)` issue: the instruction accepts an unchecked destination/beneficiary account without validating it can actually operate on (or unlock) the associated funds, leading to loss of user/protocol value.

### Impact Explanation
Once `creator_fees_token_0/1` accumulate against a pool whose `pool_creator` is not a controllable keypair, those tokens are permanently stuck: `collect_creator_fee` can never succeed (no one can produce `creator`'s signature), and `collect_creator_fee_permissionless` will only move the funds into an ATA owned by the same unusable authority, not actually recover them for anyone. This is a permanent freezing of protocol/creator fee funds contributed by every swap on that pool, satisfying the "permanent freezing of user or LP funds" impact bar. Because `initialize_with_permission` is reachable by any account holding a `Permission` PDA (a normal, non-privileged pool-creation flow), and `creator` is fully attacker-chosen, this can be triggered in a single transaction with attacker-chosen accounts and data.

### Likelihood Explanation
Any account with a valid `Permission` PDA (obtained via the standard, non-privileged `create_permission_pda` flow available to pool creators) can call `initialize_with_permission` and set `creator` to any pubkey they choose, without any relationship check to `payer` or a signer requirement. This can happen accidentally (mistyped/rotated `creator` key) or intentionally (setting `creator` to a mint address, program PDA, or other address with no private key), making the loss of creator fees straightforward to trigger and easy to overlook until fees have already accrued.

### Recommendation
- Require `creator` in `InitializeWithPermission` to either be `payer` itself, or a `Signer`, so pool_creator is proven to be a controllable keypair at pool-creation time.
- Alternatively, verify off-chain/on-chain that the designated `creator` account is a standard wallet (not a PDA/mint/program-owned account) before recording it as `pool_creator`.
- Add an admin/governance-gated `update_pool_creator` instruction to allow recovery if a pool ends up with an unusable `pool_creator`, mirroring the recommended `stakeFor`-style explicit-and-validated design from the referenced report.

### Proof of Concept
1. Attacker (or any user) obtains a `Permission` PDA for their `payer` key via the normal `create_permission_pda` flow.
2. Attacker calls `initialize_with_permission`, supplying `creator` = an arbitrary pubkey they do not control the private key for (e.g., an existing SPL mint address, or a random keypair whose secret is discarded).
3. `pool_state.pool_creator` is set to this address per `pool_state.initialize(...)`.
4. Users swap against the pool; `update_fees` accrues `creator_fees_token_0/1` normally.
5. Anyone calls `collect_creator_fee_permissionless`; the ATA created has `authority = creator` (the unusable address), and fees are transferred there.
6. No transaction can ever move those tokens further, because doing so requires a signature from `creator`, which does not exist — the creator fee is permanently frozen.
