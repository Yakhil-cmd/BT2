## Title
`Api::CCMenuController#stack` bypasses the `ApiClient`'s stack scope, letting a token authorized for one stack read the CI status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The `SynthVault.harvestSingle` bug in the report is a "verified-scope vs. acted-on-scope" mismatch: the code checks one thing (a lock-up requirement) but then acts on a broader, attacker-influenced quantity (the whole pool balance) instead of only the delta it actually earned. The same class of bug exists in `Shipit::Api::CCMenuController`: the permission check (`require_permission :read, :stack`) only validates that the presented `ApiClient` token has the *literal string* `read:stack` permission, but the controller's `stack` lookup does not apply the token's stack scope (`ApiClient#stack_id`) the way every sibling API controller does — it queries `Stack.from_param!(params[:stack_id])` directly. A token that is authorized (and intended by its issuer) to read status for a single stack is authorized against, but not bound to, that stack.

### Finding Description
`Shipit::Api::BaseController` defines the safe/authoritative resolution path used by all other API controllers: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the token is scoped to a stack (`ApiClient#stack_id?`), and `stack` resolves `params[:stack_id]` only within that restricted relation. `Api::StacksController`, `Api::DeploysController`, `Api::TasksController`, etc. all inherit and use this `stack`/`stacks` helper, so a stack-scoped `ApiClient` (e.g. `here_come_the_walrus` in fixtures, `stack: shipit`) can only ever resolve stacks it was scoped to: [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [3](#0-2) 

`require_permission :read, :stack` only calls `ApiClient#check_permissions!`, which is a flat permission-string membership check with no notion of *which* stack: [4](#0-3) 

So the equality that is verified is `token.permissions.include?("read:stack")`, while the equality that should hold — and holds everywhere else in the API — is `requested_stack.id == token.stack_id` (when the token is stack-scoped). `CCMenuController#stack` breaks this binding: `stack_id` in `check_permissions!` never sees the requested stack, and `stack` resolves against the *global* `Stack` relation, not `stacks` (the client-scoped relation). The endpoint is also reachable with only a bare `token` query-string parameter (no basic-auth/session), consistent with the intended low-friction CI status use case (`CCMenuUrlController` mints such a token with `permissions: %w[read:stack]`, scoped to one stack) — but the token, once obtained, works against **any** stack ID, not just the one it was minted for: [5](#0-4) [6](#0-5) 

### Impact Explanation
This matches the High-severity bucket "escalation into `Shipit.github_teams` authorization ... unauthenticated read of stack state, task streams or deploy output": a holder of a single stack-scoped CCMenu token (which is handed out via URLs, e.g. embedded in third-party CI dashboards/CCMenu clients, and travels as a plain query-string `token`) can enumerate `stack_id` values and read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, lock state, etc., rendered by `shipit/ccmenu/project`) for every stack in the installation, not just the one the token's creator authorized. This is a cross-stack, unauthorized read of stack/deploy state using a token that was only ever meant to be scoped to one stack.

### Likelihood Explanation
High. No privileged access is required beyond obtaining any single valid stack-scoped `read:stack` token (these are self-served: any logged-in user can hit `CCMenuUrlController#fetch` for a stack they can view, minting a `permissions: %w[read:stack]` client for themselves) and then guessing/enumerating `stack_id` (`owner/repo/environment`, largely predictable/discoverable) on the `/api/stacks/*stack_id/ccmenu` route. No additional secret is needed beyond the one legitimately obtainable token.

### Recommendation
Make `Api::CCMenuController#stack` resolve through the scoped `stacks` relation (as `BaseController#stack` and every other controller does) instead of the unscoped `Stack.from_param!`, e.g. `stacks.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient#stack_id` is actually enforced against the requested `stack_id`.

### Proof of Concept
1. As any authenticated Shipit user with access to stack `A`, visit `CCMenuUrlController#fetch` for stack `A` (e.g. via the settings page CCMenu URL), obtaining a URL containing `token=<T>` where `T` authenticates an `ApiClient` with `permissions: ["read:stack"]` and `stack_id = A.id`.
2. Send `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu?token=<T>` for an arbitrary stack `B` the user does not have access to.
3. `authenticate_api_client` succeeds (token `T` is valid). `require_permission :read, :stack` passes because `T.permissions` includes `"read:stack"` (no stack comparison is made).
4. `stack` resolves via `Stack.from_param!(params[:stack_id])`, returning stack `B` directly, bypassing the `stacks` (`current_api_client.stack_id` scoped) relation that the rest of the API enforces.
5. The response renders `B`'s deploy/CI status (`lastBuildStatus`, lock state, etc.), even though token `T` was only authorized/intended for stack `A`.
