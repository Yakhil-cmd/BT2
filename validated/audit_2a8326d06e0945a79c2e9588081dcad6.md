## Analysis: CtrlChar/Markdown-style Injection Analog in ocore

The Snap UI report describes untrusted peer-supplied strings being rendered directly into a user-facing approval dialog and, worse, becoming the exact content that gets cryptographically signed, letting a malicious counterparty control-character/markdown-disguise what the signer actually approves. The closest reachable analog in `hirayap/ocore--018` is the `prosaic_contract_offer` / `arbiter_contract_offer` handling in `wallet.js`, where the peer-controlled `title`/`text` fields are (a) forwarded verbatim into the local chat/contract UI event, and (b) later used as the literal `signed_message` string that the recipient cryptographically signs when accepting the contract.

### Title
Uncontrolled control-character/Markdown injection in arbiter/prosaic contract `title`/`text` used as both displayed content and the literal signed message - (File: wallet.js)

### Summary
`wallet.js` accepts `arbiter_contract_offer` and `prosaic_contract_offer` device messages from any paired correspondent and only checks that `title`/`text` are present/non-empty strings, with no restriction on embedded control characters, bidi/RTL override sequences, or markdown-like syntax. [1](#0-0) [2](#0-1)  These fields are stored and surfaced to the wallet UI via a `"text"` chat event carrying a base64-encoded contract blob, and critically, `objContract.title` is later used verbatim as the exact string the counterparty must cryptographically sign to accept the contract. [3](#0-2) [4](#0-3) 

### Finding Description
When a paired device sends `arbiter_contract_offer`, the recipient validates only structural properties (address validity, hash match, date format, and that `title`/`text`/`my_pairing_code` are non-empty strings): [5](#0-4) 

No sanitization is applied to the contents of `title` or `text`. Unicode control characters (e.g., right-to-left override `U+202E`, zero-width characters, or newline/format characters) or markdown-like sequences can be embedded, since `isNonemptyString` merely checks type and non-emptiness. The contract is then stored via `arbiter_contract.createAndSend`/`store` and surfaced to the counterparty's wallet through the standard chat/contract UI channel (as `objContract.title` in `getAllByStatus`, and as the base64 contract blob emitted through the `"text"` event for prosaic contracts). [6](#0-5) [7](#0-6) 

The dangerous consequence is not just cosmetic display corruption: when the offeree accepts, the response flow requires `objSignedMessage.signed_message` to equal `objContract.title` **exactly**, byte-for-byte: [8](#0-7) [3](#0-2) 

This mirrors the reported bug class precisely: a less-trusted peer (the contract offeror) supplies free-form text that (1) is rendered to the user in a confirmation UI to decide whether to accept a binding arbiter contract (which subsequently derives a shared address and commits funds via `deriveSharedAddress`/`me_is_payer`), and (2) is the very content that gets signed as proof of agreement. Embedding bidi-override or invisible characters lets an attacker make the *displayed* title/terms (e.g., payer/payee role, amount context, party name) look different from what is *actually* stored/signed, since terminal/GUI rendering of such strings can reorder or hide substrings. A user who visually confirms what looks like a benign or favorable contract can end up signing an agreement whose real (unicode-manipulated) content differs from what was displayed, without any code path re-validating that the visually-approved text matches the byte content being signed.

### Impact Explanation
This can mislead a wallet user into cryptographically committing to (signing) contract terms they did not intend to accept, based on a spoofed visual representation of `title`. Since accepting an arbiter contract leads to derivation of a shared address and eventual real payments governed by `me_is_payer`/`amount`/`asset` (`arbiter_contract.js`), a successful spoof can result in the victim unknowingly agreeing to be the payer, agreeing to wrong terms, or authorizing a transaction flow they would have rejected had the true content been rendered—i.e., a concrete loss-of-funds/social-engineering vector reachable purely from a paired device sending crafted contract-offer messages, no privileged network position required.

### Likelihood Explanation
The trigger requires only that the attacker be a paired correspondent device of the victim (a normal, low-privilege pairing relationship established via a pairing code) and send a single crafted `arbiter_contract_offer`/`prosaic_contract_offer` justsaying message with control characters embedded in `title`/`text`. No cryptographic breaks, timing races, or elevated network access are needed—only that the victim's wallet UI displays these strings raw (which the checked validation in `wallet.js` does not prevent, since it never strips/encodes control characters).

### Recommendation
- Sanitize `title` and `text` (and any other peer-supplied free text later used as *signed content* or *shown in confirmation UI*) by stripping or rejecting non-printable/control characters (including bidi override characters `U+202A`-`U+202E`, `U+2066`-`U+2069`, and other C0/C1 control codes) before storing/displaying, in the same validation block at `wallet.js:617-635` and `wallet.js:455-471`.
- Enforce a strict allow-list character set or length-bounded printable-only validation for contract `title`/`text` at ingestion time in `wallet.js`, matching what is later signed in `wallet.js:932-936` and `wallet.js:568-571`, so the signed content and any rendered content cannot diverge in meaning.
- When rendering these fields for user confirmation, escape/encode them (e.g., render within a fixed-width/pre-formatted context) rather than raw injecting into rich text, and consider re-confirming a normalized/escaped version of the exact bytes to be signed.

### Proof of Concept
1. Device A pairs with Device B (normal pairing flow).
2. Device A calls `arbiter_contract.createAndSend` with `title` containing an embedded RTL-override sequence designed to visually swap which party is displayed as payer, e.g. `title = "You will receive 100 GBYTE\u202E" + reversedMaliciousTerms`.
3. Device B receives `arbiter_contract_offer`; `wallet.js` validation at lines 617-635 passes because `title` is a non-empty string of the correct hash.
4. Device B's wallet UI displays the visually-misleading `title` to the user in the accept/decline confirmation dialog.
5. The user accepts, believing the displayed (spoofed) terms; `arbiter_contract.respond` signs `objContract.title` (the real, unicode-manipulated string) as `signed_message`, sent back to Device A.
6. `wallet.js:932-936` validates the signature against `objContract.title` matching exactly — validation succeeds because the signed bytes are self-consistent, even though what the user saw did not reflect the actual agreed terms — completing an accepted, signed contract whose fund-moving implications the victim did not intend.
