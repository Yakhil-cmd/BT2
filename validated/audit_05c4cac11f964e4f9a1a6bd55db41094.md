## Analysis

The Discourse advisory describes an endpoint that accepts an attacker-chosen `user_id` without verifying consent, letting the caller "impersonate" another account and cause a privileged action (a DM conversation) to be executed *on that account's behalf*. The reachable analog in this program is the `creator` account in `initialize_with_permission`.

### Title
Unconstrained `creator` account in `initialize_with_permission` lets any permissioned payer impersonate an arbitrary account as pool owner - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` splits the "payer" (who signs and funds pool creation) from the "creator" (who is recorded as `pool_state.pool_creator` and thereafter holds the exclusive, signer-gated right to collect accrued creator fees via `collect_creator_fee`). Unlike the standard `initialize` instruction, the `creator` account here is never required to sign, and is never constrained to equal `payer` or to match `permission.authority`.

### Finding Description
In the regular pool-creation path, `creator` is declared as a `Signer<'info>` and simultaneously funds the pool: [1](#0-0) 

In `initialize_with_permission`, this identity is split: `payer` is the `Signer`, while `creator` is only an `UncheckedAccount` with no signer requirement and no address/constraint tying it to `payer` or to the loaded `permission` PDA: [2](#0-1) [3](#0-2) 

The `permission` account is loaded (requiring only that a `Permission` PDA seeded by `payer.key()` already exists, per `create_permission_pda`) but its `authority` field is never read or compared against `creator` anywhere in the instruction body: [4](#0-3) 

The attacker-chosen `creator.key()` is written directly into `pool_state.pool_creator` with no validation: [5](#0-4) 

That field subsequently gates a privileged, signer-checked action — only the account recorded as `pool_creator` can sign for `collect_creator_fee`: [6](#0-5) 

and it is the unconditional fee-destination for `collect_creator_fee_permissionless`, which anyone can trigger: [7](#0-6) 

Because `creator` never has to sign or consent, any account that has been granted a `Permission` PDA (as `payer`) can name an arbitrary, unrelated pubkey as `pool_creator` for a new pool — attributing pool ownership/creator-fee-recipient status to a victim account without that account's knowledge or authorization, exactly analogous to the referenced report's arbitrary `user_id` impersonation.

### Impact Explanation
This breaks the authorization invariant enforced everywhere else in the program (`initialize.rs` requires `creator` to sign): a privileged role (`pool_creator`), which controls a signer-gated fund-collection instruction and is the fixed destination of the permissionless fee-sweep instruction, can be assigned to any account without consent. This enables impersonation-style abuse (misattributing pool ownership/creator status to a real, unrelated address to imply endorsement, or to permanently bind creator-fee accounting to an address the actual pool-funding party never intended), which is an unauthorized privileged effect on program state.

### Likelihood Explanation
Exploitation requires only that the caller (payer) already holds a valid `Permission` PDA — a reachable, single-transaction path with fully attacker-chosen `creator` account and no additional signatures needed. Any permissioned pool-creation flow is affected.

### Recommendation
Constrain `creator` in `InitializeWithPermission` to either be a `Signer`, or add an explicit `address = permission.authority` (or `address = payer.key()`) constraint so the recorded `pool_creator` can only be an account that has actually authorized/consented to the role, matching the invariant already enforced in `initialize.rs`.

### Proof of Concept
1. Attacker A obtains a `Permission` PDA for `payer = A` via `create_permission_pda` (requires only that the fixed program-admin/`create_permission_pda_owner` signs — a permissioned but not creator-bound grant).
2. A calls `initialize_with_permission` supplying `payer = A` (signs, funds the pool) and `creator = V` (any victim/target pubkey, no signature required).
3. `pool_state.pool_creator` is set to `V`'s key with no validation that `V` authorized this.
4. The pool now permanently records `V` as its creator; `collect_creator_fee` can only ever be signed by `V`, and `collect_creator_fee_permissionless` will always route creator fees to `V`'s ATA — all without `V`'s consent or knowledge, fulfilling the impersonation bug class described in the report.

```rust
#[derive(Accounts)]
pub struct CreatePermissionPda<'info> {
    #[account(
        mut,
        constraint = (owner.key() == crate::admin::ID || owner.key() == crate::create_permission_pda_owner::ID) @ ErrorCode::InvalidOwner
    )]
    pub owner: Signer<'info>,

    /// CHECK: permission account authority
    pub permission_authority: UncheckedAccount<'info>,

    /// Initialize config state account to store protocol owner address and fee rates.
    #[account(
        init,
        seeds = [
            PERMISSION_SEED.as_bytes(),
            permission_authority.key().as_ref()
        ],
        bump,
        payer = owner,
        space = Permission::LEN
    )]
    pub permission: Account<'info, Permission>,

    pub system_program: Program<'info, System>,
}

pub fn create_permission_pda(ctx: Context<CreatePermissionPda>) -> Result<()> {
    let permission = ctx.accounts.permission.deref_mut();
    permission.authority = ctx.accounts.permission_authority.key();
    Ok(())
}
```
