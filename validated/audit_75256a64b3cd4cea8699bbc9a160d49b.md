### Title
Cross-repository sha collision in `StatusHandler#process` allows unauthorized `ContinuousDeliveryJob` enqueue via `Commit#schedule_continuous_delivery` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits solely by `Commit.where(sha: params.sha)`, with no check that the webhook's `repository.full_name` matches the `stack.repository` of the commit being updated. Combined with `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery`, a `status` webhook signed by an attacker's own GitHub org/repo can create a `success` `Status` on a victim's `Commit` row (if the shas happen to collide) and directly trigger `ContinuousDeliveryJob.perform_later(stack)` for the victim's stack.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack.repository == payload.repository.full_name`, but no code enforces this equality.

Path:
1. `WebhooksController#verify_signature` only checks that the webhook signature matches the `webhook_secret` configured for `repository_owner` (from `params.dig('repository','owner','login')`) — i.e., it verifies *who sent the payload*, not *which commit/stack the payload is allowed to affect*. [1](#0-0) 
2. `StatusHandler#process` then looks up commits **by sha only**, with zero scoping to the repository named in the payload:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 
3. `Commit#create_status_from_github!` → `add_status` creates a `Status` row tied to `commit.stack_id`, and `Status` fires `schedule_continuous_delivery` on create: [3](#0-2) 
4. `Commit#schedule_continuous_delivery` re-checks `deployable?`, `stack.continuous_deployment?`, `stack.deployable?` using the **victim's own stack** (fetched via `commit.stack`, not derived from the payload), and enqueues:
```ruby
def schedule_continuous_delivery
  return unless deployable? && stack.continuous_deployment? && stack.deployable?
  ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)
end
``` [4](#0-3) 

Root cause: nothing in this call chain checks that the sha resolved to a commit whose `stack.repository` matches the `repository` field of the webhook payload that was actually signature-verified. `verify_signature` authenticates the *sender's organization*, but the subsequent commit lookup is global across the entire `commits` table, unscoped by stack or repository. If a victim commit and an attacker-controlled commit share a sha (a precondition explicitly granted by the question), the attacker's own valid webhook (signed with their own org's `webhook_secret`) will mutate the victim's commit/stack state.

This is distinct from, but produces, the exact effect described in the question: `ContinuousDeliveryJob` gets scheduled for the victim stack even though the underlying CI success signal originated from the attacker's repository.

### Impact Explanation
An attacker who owns/controls a repository under a GitHub organization that has any Shipit-configured GitHub App/webhook secret can, by crafting a commit whose sha collides with a victim commit tracked by a Shipit stack with `continuous_deployment: true`, cause an unauthorized `success` `Status` to be recorded against the victim's commit and trigger `ContinuousDeliveryJob`, which — if the victim stack is `deployable?` (unlocked, unoccupied) — leads to `stack.trigger_continuous_delivery`, i.e. an **unauthorized deploy** on victim infrastructure. This matches the Critical impact category ("payload for one repository mutating another's stack/commit... or an unauthorized deploy"). The blast radius spans any stack/repository tracked in the same Shipit instance, since `Commit.where(sha:)` is global and not scoped per tenant/org/repo.

### Likelihood Explanation
Exploitation strictly requires the granted precondition of an exact sha collision between an attacker-controlled commit and the victim's head commit — a real full-length SHA-1 commit-object collision is not a trivial thing to engineer (commit sha depends on tree, parent(s), author/committer identity and exact timestamps, and message), so the practical likelihood of satisfying this precondition against an arbitrary, unknown victim commit is low without additional information leakage (e.g., publicly known scaffold/initial commits, or a maintainer copying a commit byte-for-byte across repos, as the question stipulates). However, *given* that precondition, no other control in the code path (signature check, `ExplicitParameters` schema, model validations) prevents the divergence — the vulnerability is a genuine, unguarded architectural gap in `StatusHandler`, not merely theoretical noise, since the missing repository-scoping check is unconditional and independent of collision difficulty.

### Recommendation
In `app/models/shipit/webhooks/handlers/status_handler.rb`, scope the commit lookup to the same repository as the webhook payload, e.g. join through `stack` and filter `stack.repository`/`github_repo_name` against `params.name` (or the payload's `repository.full_name`), before calling `create_status_from_github!`. This restores the binding `commit.stack.repository == payload.repository.full_name` that is currently missing.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or extend `test/controllers/webhooks_controller_test.rb`):
```ruby
test ":status webhook from repo A must not mutate a commit belonging to stack of repo B with same sha" do
  victim_stack = shipit_stacks(:shipit) # repository e.g. "shopify/shipit-engine"
  victim_stack.update!(continuous_deployment: true)
  colliding_sha = "deadbeef" * 5 # 40 chars, contrived collision
  victim_commit = victim_stack.commits.create!(sha: colliding_sha, message: "victim", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  # Attacker's payload references a different, attacker-owned repository
  attacker_payload = {
    'sha' => colliding_sha,
    'state' => 'success',
    'name' => 'attacker/evil-repo',
    'repository' => { 'full_name' => 'attacker/evil-repo', 'owner' => { 'login' => 'attacker' } },
    'branches' => [{ 'name' => victim_stack.branch }]
  }

  # Signature check passes because it's signed with attacker org's own webhook secret
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  assert_no_enqueued_jobs only: ContinuousDeliveryJob do
    # BEFORE fix: this currently DOES enqueue ContinuousDeliveryJob.perform_later(victim_stack),
    # proving commit.stack (victim_stack) != payload.repository ("attacker/evil-repo")
    post :create, body: attacker_payload.to_json, as: :json, headers: { 'X-Github-Event' => 'status' }
  end

  assert_equal 0, victim_commit.reload.statuses.count
end
```
Assertion on both sides of the binding: `victim_commit.stack.repository.full_name` (e.g. `"shopify/shipit-engine"`) must equal the webhook's `attacker_payload['repository']['full_name']` (`"attacker/evil-repo"`) for the status/job to be created — currently they are never compared, so the test demonstrates `ContinuousDeliveryJob` firing for `victim_stack` off of `attacker/evil-repo`'s webhook alone.
