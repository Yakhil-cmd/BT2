### Title
`StatusHandler#process` matches commits by bare SHA with no repository scoping, letting a webhook authenticated for one repo flip CI status on another stack's commit - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no filter tying the match to the repository that authenticated the webhook. Because Git SHAs are content-addressed and identical across forks/mirrors of a repo, an attacker who owns a fork/repo can trigger GitHub to send a genuinely-signed `status` webhook containing a SHA that is shared with a victim stack, and that status write lands on the victim's `Commit` row for that SHA regardless of which repository actually generated it.

### Finding Description
The broken binding: the invariant the codebase is supposed to enforce is `commit.stack.repository == webhook.repository`, but `StatusHandler#process` never checks it: [1](#0-0) 
This is in contrast to sibling handlers such as `CheckSuiteHandler`, which correctly scope through `stacks` (derived from `Repository.from_github_repo_name(repository_name)`) before touching any commit: [2](#0-1) 
and the base `Handler` class exposes exactly this helper (`stacks`, keyed off `payload.dig('repository', 'full_name')`) that `StatusHandler` simply does not use: [3](#0-2) 

Path to reach it:
1. `Shipit::WebhooksController#create` parses the body and dispatches to handlers for the `status` event, guarded only by `verify_signature`, which checks the HMAC signature against the webhook secret associated with `repository_owner` (the org/user in the payload) — not against a specific repository or stack: [4](#0-3) 
Note `verify_signature` proves only "this payload was really sent by GitHub for this org/app installation" — it does not, and cannot, prove "this payload's SHA belongs to the same repository as the stack it will be applied to."
2. `Commit.where(sha: params.sha)` is a global lookup across all stacks/repositories that happen to have a `Commit` row with that SHA: [5](#0-4) 
3. `create_status_from_github!` -> `add_status` writes the `Status`, and on a state transition schedules merges / fires `deployable_status` hooks that drive auto-merge and auto-deploy behavior for whichever stack owns that commit row: [6](#0-5) 
4. `Status#after_create`/`after_commit` callbacks enable CI on the stack and schedule continuous delivery for the affected commit's stack — again with no re-validation that the originating repository matches: [7](#0-6) 

Exploit flow: an attacker forks (or otherwise controls) a public repository that shares commit history with a victim's Shipit-tracked repository (e.g., they fork the victim repo, or the victim's repo is itself a fork/mirror situation, or simply any repo where a common ancestor SHA also exists in the victim stack's commit table because the victim previously pulled/merged that SHA). The attacker triggers their own CI (or any status-posting integration) on their fork for that shared SHA with `context: ci/jenkins`, `state: success` (or `failure`/`error` to block). GitHub genuinely signs and delivers this `status` webhook for the attacker's own repo/org. `verify_signature` passes because the signature is valid for that org. `StatusHandler` then updates the `Status` row keyed only by bare SHA, hitting the victim's `Commit` (same SHA, different stack/repository), potentially satisfying the victim stack's CI requirements and unblocking/triggering an auto-merge or auto-deploy that executes under the stack's configured bot identity (`Shipit.user`/`bot_login`).

Why existing guards fail: `verify_signature` authenticates the *sender org*, not the *SHA-to-repository binding*; `ExplicitParameters` in `StatusHandler.params` validates the shape of the payload (`sha`, `state`, `context`, etc.) but not repository ownership; there is no repository/stack scoping equivalent to `CheckSuiteHandler`'s `stacks.where(...)`.

### Impact Explanation
A `status` webhook that is 100% legitimately signed for repository/org A can write a CI status onto a `Commit` belonging to stack/repository B, as long as both repositories contain a `Commit` row with the same SHA (an ordinary, frequent occurrence for forks, mirrors, and shared history). This status write can flip a victim stack's CI gate to `success` (enabling continuous merge/deploy of attacker-influenced state) or to `failure`/`error` (blocking legitimate deploys — a denial-of-availability for releases). Because merges and deploys triggered this way run under the stack's configured bot identity, this is a cross-tenant "payload for one repository mutating another's stack/commit" case, matching the Critical impact category (unauthorized deploy/merge/block driven by data that did not authenticate for that repository). The blast radius covers any pair of stacks (attacker-controlled repo and victim repo) that share any commit SHA, which is common for fork-based workflows.

### Likelihood Explanation
Preconditions: the attacker needs a GitHub repo/org where they can receive genuinely-signed webhooks from GitHub (i.e., a repo/org with the Shipit GitHub App/webhook installed — trivially achievable if they own a repo under the Shipit installation scope, e.g., a fork of the victim's public repo under their own account) and a SHA that is shared with the victim's tracked commit history (trivial via forking, since Git SHAs are content-addressed and preserved across forks). No Shipit credentials, sessions, or secrets are required — only ordinary GitHub actions (forking, pushing, or having their own CI/status integration post a status). This is straightforward and repeatable against any victim stack whose repository has been forked or shares history with an attacker-accessible repository.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring `CheckSuiteHandler`: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` (or equivalently filter `Commit.where(sha: params.sha)` by `stack: stacks`) before applying `create_status_from_github!`, so a status can only affect commits belonging to stacks whose repository matches `payload.dig('repository', 'full_name')`.

### Proof of Concept
Minitest sketch under `test/models/shipit/webhooks/handlers/status_handler_test.rb` (not present verbatim in the indexed code, to be authored):
1. Create two stacks, `victim_stack` (repo `victim/repo`, with `bot_login`/`Shipit.user` configured, `continuous_delivery`/merge requiring `ci/jenkins`) and `attacker_stack` (repo `attacker/fork`).
2. Create two `Commit` rows with the *same* `sha` — one under `victim_stack`, one under `attacker_stack` — representing a shared ancestor commit.
3. Build a `status` payload with `repository.full_name = "attacker/fork"`, `sha` = the shared SHA, `context: "ci/jenkins"`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature check, since that's orthogonal to this handler-level bug).
5. Assert equality-before/after: BEFORE, `victim_commit.status.for("ci/jenkins")` != `success` (or `unknown`); AFTER, `victim_commit.reload.status.for("ci/jenkins").state == "success"`, proving that a payload whose `repository.full_name` is `attacker/fork` mutated `victim_stack`'s commit — violating the invariant "a status for `ci/jenkins` only affects the repository that authenticated it."
6. Optionally assert that `stack.schedule_merges` (or a deploy job) was enqueued for `victim_stack` as a result, demonstrating downstream ship/block impact.

    def self.by_sha(sha)
      raise AmbiguousRevision, "Short SHA1 #{sha} is ambiguous (too short)" if sha.to_s.size < 6

      commits = where('sha like ?', "#{sha}%").take(2)
      raise AmbiguousRevision, "Short SHA1 #{sha} is ambiguous (matches multiple commits)" if commits.size > 1

      commits.first
    end

    def self.by_sha!(sha)
      by_sha(sha) || raise(ActiveRecord::RecordNotFound, "Couldn't find commit with sha #{sha}")
    end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
