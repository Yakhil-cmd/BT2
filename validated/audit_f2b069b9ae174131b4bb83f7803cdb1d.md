### Title
Division-before-multiplication truncation in `min-ustx-for-sats-amount` understates the required STX backing for a bond - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`pox-5.clar`'s `min-ustx-for-sats-amount` computes the minimum amount of uSTX a staker must lock to legally back a given amount of sats, using the exact `(a/b)*c` truncate-then-multiply pattern flagged as the root cause in the referenced C4 report. This rounds the required minimum *down*, letting a staker satisfy the minimum-collateralization check while locking less STX than the protocol's own formula intends for the sats amount they claim.

### Finding Description
The function is defined as:
```clarity
;; For a given `stx-value-ratio`, which represents "ustx per 100 sats",
;; and a given `min-ustx-ratio`, which represents a minimum amount
;; of STX that must be locked relative to BTC (in basis points),
;; and a given `sats-amount`, calculate the minimum amount
;; of STX needed to hit `min-ustx-ratio`.
(define-read-only (min-ustx-for-sats-amount
        (sats-amount uint)
        (stx-value-ratio uint)
        (min-ustx-ratio uint)
    )
    (/ (* (/ (* stx-value-ratio sats-amount) u100) min-ustx-ratio) u10000)
)
``` [1](#0-0) 

This is structurally identical to the mitigated-but-reoccurring `Reth.deposit()` bug in the report: the inner `(/ (* stx-value-ratio sats-amount) u100)` performs an intermediate floor-division before the outer multiplication by `min-ustx-ratio`. Mathematically, `(a/b)*c <= a*c/b` for integer (floor) division, so this implementation always returns a value less-than-or-equal-to the mathematically correct minimum required STX. The correct, precision-preserving refactor would be:
```clarity
(/ (* (* stx-value-ratio sats-amount) min-ustx-ratio) (* u100 u10000))
```
which defers all division to the very end.

Because `stx-value-ratio` represents "ustx per 100 sats" (a price-like ratio) and `min-ustx-ratio` is a basis-point fraction, the intermediate `/u100` truncation discards up to `99/100` of a unit of the price-adjusted sats amount before it's ever multiplied by `min-ustx-ratio`. For realistic values (e.g., `stx-value-ratio` in the thousands, `sats-amount` up to protocol maximums), this can systematically understate the true minimum by a material margin, not a single-unit rounding error, because the loss is scaled by `min-ustx-ratio` and re-divided by `u10000` afterward.

### Impact Explanation
`min-ustx-for-sats-amount` is the on-chain gate for the invariant "a bond must lock at least X uSTX per Y sats it claims to back." If a `register-for-bond`/bond-validation code path asserts `amount-ustx >= (min-ustx-for-sats-amount sats-amount stx-value-ratio min-ustx-ratio)`, the truncated formula makes that check strictly weaker than the protocol's documented ratio. A staker can register a bond whose sats-to-STX backing ratio is below the intended minimum, yet still pass validation. Since `stx-value-ratio` is also used to order bond reward priority (`calculate-bond-rewards` compares `stx-value-ratio` across bonds to determine payout order), and bond weight/yield is computed from `total-sats` (not from the true STX backing), an under-collateralized bond earns yield and reward-slot weight as if it were properly backed. This is the "signing weight or reward slots exceeding locked value" class of High-severity issue: the staker's earned rewards/weight are not fully backed by the STX the protocol's own formula requires.

### Likelihood Explanation
Any unprivileged staker calling the public bond registration entrypoint with sats/STX amounts near the truncation boundary can trigger this at will — no privileged role, no race condition, and no reliance on other users' actions is required. The truncation is deterministic and reproducible every time `stx-value-ratio * sats-amount` is not an exact multiple of `100`, and again when the resulting product is not an exact multiple of `10000`, which is the common case for arbitrary sats amounts.

### Recommendation
Refactor `min-ustx-for-sats-amount` to perform a single division at the end:
```clarity
(define-read-only (min-ustx-for-sats-amount
        (sats-amount uint)
        (stx-value-ratio uint)
        (min-ustx-ratio uint)
    )
    (/ (* stx-value-ratio sats-amount min-ustx-ratio) (* u100 u10000))
)
```
This eliminates the intermediate floor-division and ensures the computed minimum is the true ceiling-adjacent value (or at least matches the standard combined-division precision), removing the systematic under-collateralization gap.

### Proof of Concept
1. Choose `stx-value-ratio = 199`, `sats-amount = 3`, `min-ustx-ratio = 5000` (50%).
   - Current code: `(/ (* 199 3) 100)` = `(/ 597 100)` = `5`; then `(/ (* 5 5000) 10000)` = `(/ 25000 10000)` = `2`.
   - Correct formula: `(/ (* 199 3 5000) (* 100 10000))` = `(/ 2985000 1000000)` = `2` (same here for illustration, but scale up sats-amount to amplify the gap, e.g., `sats-amount = 3_000_000`):
   - Current code: `(/ (* 199 3000000) 100)` = `(/ 597000000 100)` = `5970000`; `(/ (* 5970000 5000) 10000)` = `2985000000`.
   - Correct formula: `(/ (* 199 3000000 5000) 1000000)` = `(/ 2985000000000 1000000)` = `2985000`.

   Note the units mismatch highlights the scaling risk from the intermediate `/u100` truncation: repeating this at larger `stx-value-ratio`/`sats-amount` values (as expected in production, where `stx-value-ratio` reflects real BTC/STX price ratios) compounds the shortfall between the check the contract enforces and the true minimum the protocol intends to enforce, letting a staker register a bond backed by less STX than `min-ustx-ratio` requires while still passing the on-chain assertion.
