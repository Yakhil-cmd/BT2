## Title
Webhook signature is verified against the organization's secret keyed by `repository.owner.login`/`organization.login`, but event handlers act on the unrelated `repository.full_name` field, letting any org configured in a multi-tenant Shipit install forge events for another org's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App's webhook secret to use for HMAC verification based on a payload field (`repository.owner.login`, falling back to `organization.login`) that is itself part of the *unverified* request body. Handlers (e.g. `PushHandler`, `Handler#repository_name`) then act on a different payload field, `repository.full_name`, to look up the target `Stack`/`Repository`. Nothing ties these two fields together, so a signature that is valid for organization A only proves the request was signed with A's webhook secret - not that the `repository.full_name` used by the handler actually belongs to A.

### Finding Description
`verify_signature` computes the "trusted" organization purely from attacker-controlled JSON before the signature has been checked: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` maps that string to a specific `GitHubApp` (and its `webhook_secret`) in a multi-tenant configuration such as the one shown in `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`, each with its own `webhook_secret`): [3](#0-2) 

The HMAC is computed over `request.raw_post` and does check the whole payload is untampered relative to *that* organization's secret, but it says nothing about which repository the payload's business fields refer to. Handlers derive the actually-affected repository/stack from a completely different key, `repository.full_name`: [4](#0-3) 
and `PushHandler` uses that to find stacks and trigger a GitHub sync of commits: [5](#0-4) 

Because `verify_signature` never checks that `repository.owner.login`/`organization.login` (used to pick the secret) is the same organization as `repository.full_name`'s owner (used by the handler), an org that legitimately owns a GitHub App entry in Shipit's multi-org config (e.g. `OrgOne`) can sign a payload with `OrgOne`'s webhook secret while setting `repository.full_name` to `OrgTwo/victim-repo`. The signature check passes (it only validates the raw bytes against `OrgOne`'s secret), and `PushHandler`/other handlers then act on `OrgTwo`'s stack: enqueuing `GithubSyncJob`, appending forged commits, and driving continuous delivery/merge logic for a repository the attacker does not control.

This is the same class of bug as the underlying report: a field that is authenticated (here, the organization tied to the signing secret) is not the same field that later drives privileged state changes (the repository actually written to), because the binding between the two is never enforced.

### Impact Explanation
This breaks a cross-organization/cross-repository write boundary: `organization authenticated by webhook signature == repository actually mutated by the handler` does not hold. An attacker who legitimately controls (or compromises) one org's GitHub App/webhook secret in a multi-tenant Shipit deployment can inject fabricated push/status/check_suite/pull_request events that are processed as if they came from a completely different, victim organization's repository - enqueuing `GithubSyncJob`, creating fake commits (`stack.commits.create_from_github!`), archiving/unarchiving review stacks, or affecting merge/CI status for stacks that belong to other tenants. Depending on continuous delivery configuration this can lead to unauthorized deploys being triggered for a repository the attacker never had write access to - matching the High-severity category "escalation ... unauthorized deploy, rollback".

### Likelihood Explanation
Requires a Shipit deployment configured with multiple GitHub organizations (the documented multi-tenant schema, e.g. `secrets_double_github_app.yml`) where the attacker legitimately controls one of the configured orgs/apps (or that org's webhook secret is otherwise exposed) but not the target org's repository. Given that Shipit explicitly supports and documents this multi-org configuration, this is a realistic deployment shape, though it does depend on that specific multi-tenant setup rather than the default single-org config.

### Recommendation
In `verify_signature`, after resolving `github_app` from `repository_owner`, additionally verify that every repository-identifying field the handlers will use (`repository.full_name`'s owner, or `organization.login` for org-scoped events) is consistent with the same organization used to select the secret, rejecting the webhook (422) if they diverge. Alternatively, derive the handler's target repository from the same authenticated organization value rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who controls `OrgOne`'s GitHub App/webhook secret, craft a push webhook payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/victim-repo"
  }
}
```
3. Sign the raw JSON body with `OrgOne`'s `webhook_secret` and send it to `/webhooks` with `X-Github-Event: push` and the resulting `X-Hub-Signature`.
4. `verify_signature` calls `Shipit.github(organization: 'OrgOne')` (from `repository.owner.login`) and the HMAC check passes because it was actually signed with `OrgOne`'s secret.
5. `Shipit::Webhooks::Handlers::PushHandler#process` runs and resolves `stacks` via `Repository.from_github_repo_name('OrgTwo/victim-repo')`, enqueuing sync/deploy-related jobs for `OrgTwo`'s stack despite the attacker having no relationship with `OrgTwo`. [6](#0-5) [4](#0-3) [7](#0-6)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
