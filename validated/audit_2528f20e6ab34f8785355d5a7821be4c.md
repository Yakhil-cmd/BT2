### Title
`liquidate` has no minimum-seizure parameter: a stale or front-run liquidation can repay debt and seize nothing - (File: contracts/controller/src/positions/liquidation/mod.rs)

### Summary
`Controller::liquidate` is a permissionless exchange: the liquidator authorizes token transfers of `debt_payments` to the pool and, in return, receives seized collateral (Transfer mode) or supply shares (Credit mode). The seizure amount is computed entirely at execution time from current prices, indexes, and the liquidation curve — the caller can cap their *input* but cannot express any minimum *output*. Planning silently drops collateral legs whose seizure rounds to zero tokens or zero shares, and `require_non_empty_payments` is only applied to `result.repaid`, never to `result.seized`. The protocol's own documentation confirms the outcome: "The contract accepts a liquidation that repays debt and seizes nothing, so the liquidator would pay and receive no collateral." This is the same bug class as `FeeCollector.claimFees`: a permissionless swap with no caller-specified min-out.

### Finding Description
In `liquidate` (`contracts/controller/src/positions/liquidation/mod.rs`), the plan is built at execution time via `build_liquidation_plan`, which derives `seized_collaterals` from live `Context`-cached prices and indexes. `require_non_empty_payments(env, &result.repaid)` (mod.rs:66) guards the repayment side only. `calculate_seized_collateral` drops any leg that rounds to zero (math.md: "Planning drops legs that round to zero tokens or zero shares"), and `scale_seizures_to_received` only scales by under-delivery. The liquidator then pulls `pull` tokens in `apply_liquidation_repayments` regardless of what `seized` contains (apply.rs:54-65).

A liquidator simulates `get_liquidation_estimate`, signs the planned `debt_payments` auth tree, and submits. If state changes before inclusion — a competing liquidation alters the account's `proportion_seized`/bonus band, interest accrual shifts the plan, or a price/aggregator update reprices collateral (including Aquarius LP collateral whose value an attacker can move with own pool trades) — every seizure leg can round to zero while the repayment legs remain positive. The transaction still succeeds: the liquidator's tokens are transferred to the pool and `apply_liquidation_seizures` iterates an empty vector. Unlike the router, which enforces `amounts[min_out]` before payout (`SlippageExceeded = 5`), the controller deliberately "never checks a minimum output" (ADR-0011) — and for `liquidate` there is no payload field where the caller could even encode one.

### Impact Explanation
Theft of user funds: the liquidator loses the pulled `debt_payments` and receives zero (or dust) collateral. The lost repayment is credited against the borrower's debt, so funds are not recoverable. Because `liquidate` is permissionless and the auth tree commits the liquidator to fixed transfer amounts, any unprivileged actor can induce the loss by changing plan-relevant state (e.g., submitting a competing liquidation of the same account, or moving an LP-collateral price within the aggregator's tolerance bands) in the ledger before the victim's transaction executes. Severity: Medium–High — unconditional code path, but loss requires the signed transaction to land after an adverse state change.

### Likelihood Explanation
Liquidation bots necessarily sign `debt_payments` before execution, based on an earlier `get_liquidation_estimate` simulation; on Stellar there is always a gap between simulation and inclusion. Competing liquidators for the same account are the norm, and each prior liquidation changes `proportion_seized`, the bonus, and remaining collateral. Whole-unit (sub-3-decimal) collateral legs and rounding-to-zero leg dropping make a non-empty `repaid` with an empty `seized` a reachable plan outcome rather than an edge case; the docs explicitly instruct integrators to guard against it client-side because the contract does not.

### Recommendation
Mirror the fix suggested in the external report: let the caller specify minimums. Add an optional `min_seized: Vec<HubPayment>` (or a `min_seized_usd_wad` scalar) argument to `liquidate`, and after `scale_seizures_to_received` revert with a new error when the measured seizure falls below the declared floor. Alternatively, revert whenever `result.repaid` is non-empty and `seized` is empty, so the "pay and receive nothing" outcome cannot be committed on-chain. Until enforced, document the recommended estimate-then-bound-check flow for bot builders, matching how the swap router enforces `min_out` inside `routeXdr`.

### Proof of Concept
1. Borrower account has HF < 1 with a single tiny collateral leg (e.g., a low-priced token whose USD seizure for the planned repayment rounds to < 1 base unit).
2. Liquidator L calls `get_liquidation_estimate(account_id, [(debt_hub_asset, P)], SeizeMode::Transfer)`; it returns a non-empty `repaid` plan and a marginal `seized_collaterals` list.
3. Before L's transaction executes, the collateral price ticks down via an accepted oracle update (or a competing liquidation changes the plan band), such that each seizure leg rounds to zero and is dropped by `calculate_seized_collateral`.
4. L's signed `liquidate` executes: `build_liquidation_plan` returns `repaid = [(debt, P)]`, `seized = []`; `require_non_empty_payments(&result.repaid)` passes; `apply_liquidation_repayments` pulls `P` debt tokens from L; `apply_liquidation_seizures` iterates the empty vector; the call succeeds and emits `LiquidationEvent`.
5. Result: L paid `P` and received 0 collateral; the borrower's debt decreased by `P`.
