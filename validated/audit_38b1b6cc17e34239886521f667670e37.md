### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha: params.sha)` lookup, exploitable with well-known/degenerate SHAs - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no constraint tying the lookup to the repository that sent the webhook. Any attacker who controls a repository (or a public repo with a well-known empty-tree/empty-commit SHA that coincidentally also exists on a victim's stack) can send a `status` webhook naming that SHA and have it applied to the victim's `Shipit::Commit`, regardless of which repository actually owns that commit in Shipit's database.

### Finding Description
The broken binding is: `commit.stack_id` (the stack that owns the matched `Shipit::Commit` row) should equal the stack derived from `payload.dig('repository', 'full_name')` (the repository that actually sent the webhook), but the code never establishes or checks this equality.

`StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This is a global, table-wide lookup by `sha` alone. The base `Handler` class does provide a `repository_name`/`stacks` helper derived from `payload.dig('repository', 'full_name')` that other handlers use to scope their side effects to the sending repository, but `StatusHandler` never calls it: `stacks` is defined at `app/models/shipit/webhooks/handlers/handler.rb` lines 32-38, and `StatusHandler` (lines 1-28 of `status_handler.rb`) has no reference to it at all.

Because git SHA-1 identifiers are content-addressed and not namespaced per repository, the same SHA can legitimately (and, for degenerate objects like the empty tree `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, deterministically) exist as a `Commit` row belonging to a completely different stack/repository than the one the attacker controls. An attacker:
1. Creates or uses any GitHub repository they control and connects/points it at their own Shipit-reachable webhook endpoint (or any repo already registered with Shipit, since `POST /webhooks` is unauthenticated aside from signature verification, and signature verification only proves the payload came from *a* legitimate GitHub webhook for *some* repo, not that the named `sha` belongs to that repo).
2. Sends a `status` event payload with `sha` set to the well-known empty-tree SHA (or any SHA they can arrange to collide with a victim's existing commit, e.g., an empty merge commit) and an arbitrary `state`/`description`/`target_url`.
3. `StatusHandler.process` matches every `Commit` row across all stacks with that `sha`, including the victim's, and calls `commit.create_status_from_github!(params)` on it, which writes a new `Status` row and can flip the commit's computed state (`stack.commits` `deployable?`), potentially triggering `schedule_continuous_delivery` and downstream deploy behavior on the victim's stack.

No existing guard prevents this: webhook signature verification (if configured) only authenticates that GitHub sent the payload for the attacker's own registered repo — it does not constrain which `sha` values the payload may reference. `ExplicitParameters` only validates types/presence, not repository ownership. There is no `stack_id`/`repository_id` filter added to the `Commit.where` query.

### Impact Explanation
A single unauthenticated (from Shipit's perspective, though technically signed by GitHub for the attacker's own repo) webhook lets an attacker write `Status` records onto a victim's `Shipit::Commit`, mutating that commit's CI/status state as seen by Shipit. This can affect `deployable?`/`blocked?` computations and continuous-delivery scheduling (`schedule_continuous_delivery`) for a repository the attacker never authenticated against, i.e., a payload for one repository mutating another's stack/commit state — matching the Critical "payload for one repository mutating another's stack, commit, task or team" category. The degenerate-SHA variant requires zero reconnaissance of the victim, since the empty-tree/empty-commit SHA is universal, though it still requires the victim to actually have a `Commit` row with that exact SHA (e.g., from an empty merge or GitHub-generated no-op commit), which is a real but less common precondition than the general SHA-collision case.

### Likelihood Explanation
The attacker only needs a repository they control (or any repo capable of emitting a `status` webhook to the Shipit endpoint) and the ability to name an arbitrary `sha` in that webhook, both trivially available to any GitHub user. The universal empty-tree SHA requires no per-victim reconnaissance, but does depend on the victim stack having ever recorded a `Commit` with that exact SHA, which narrows applicability compared to the general cross-repo SHA-collision variant but remains plausible for stacks with squash-merge or empty-commit workflows.

### Recommendation
Scope the lookup to the sending repository, e.g., resolve `stacks` (already available via the base `Handler#stacks` helper) and constrain the query to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a `status` webhook can only mutate commits belonging to stacks associated with the repository that sent it.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` conceptually, not to be created by this audit but described):
1. Create `stack_victim` for repository `victim/repo` and seed `commit = victim_stack.commits.create!(sha: "4b825dc642cb6eb9a060e54bf8d69288fbee4904", ...)`.
2. Build a `status` webhook payload with `repository.full_name = "attacker/repo"` (unrelated, not associated with `stack_victim`) and `sha: "4b825dc642cb6eb9a060e54bf8d69288fbee4904"`, `state: "failure"`.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
4. Assert before: `commit.status.state != "failure"`. Assert after: `commit.reload.status.state == "failure"` — demonstrating the equality `commit.stack_id == stack_for("attacker/repo").id` was never checked, and the attacker's payload mutated `stack_victim`'s commit.
