### Title
Unvalidated P2P Staking Info Injection Corrupts Reward Distribution and Causes Consensus Divergence — (`datasync/downloader/queue.go`)

---

### Summary

During fast-sync, staking information received from a remote peer is written directly to the local database with **no content validation**. A malicious peer can supply fabricated `CouncilStakingAmounts` for any staking-interval block. Because those amounts are later consumed verbatim by `assignStakingRewards` and `generateProposerListWeighted`, the victim node computes wrong state roots for pre-Kaia blocks, causing it to reject canonical blocks and diverge from the honest chain.

---

### Finding Description

`queue.DeliverStakingInfos` contains a `validate` closure that is a permanent no-op:

```go
// datasync/downloader/queue.go  lines 956-958
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil          // ← always passes, no content check
}
``` [1](#0-0) 

Contrast this with `DeliverReceipts`, which cryptographically verifies every receipt against `header.ReceiptHash`:

```go
validate := func(index int, header *types.Header) error {
    if types.DeriveReceiptsRoot(...) != header.ReceiptHash {
        return errInvalidReceipt
    }
    return nil
}
``` [2](#0-1) 

The accepted `result.StakingInfo` is then persisted unconditionally in `commitFastSyncData`:

```go

    d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum,
        staking.ToStakingInfo(result.StakingInfo))
}
``` [3](#0-2) 

The same absence of validation exists in the explicit recovery path `SyncStakingInfo`, which only checks that the returned `BlockNum` matches the expected value — it never verifies the staking amounts against the on-chain state:

```go

### Impact Explanation

**Reward distribution corruption.** For pre-Kaia blocks, `GetStakingInfo` reads from the database (not from state):

```go
if !isKaia {
    if si := ReadStakingInfo(s.ChainKv, sourceNum); si != nil { ... }
}
``` [6](#0-5) 

`assignStakingRewards` then distributes KAIA proportionally to the injected amounts:

```go
excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess)
``` [7](#0-6) 

Inflated amounts for the attacker's validator increase its share of every staking-reward epoch in the affected range.

**Proposer-list corruption.** Before the Kore hardfork, `generateProposerListWeighted` weights each validator's slot count by its staking amount:

```go
weight := uint64(math.Round(stakingAmounts[addr] * 100 / totalStakes))
``` [8](#0-7) 

Falsified amounts shift the proposer schedule, causing the victim to expect a different proposer than the rest of the network.

**State-root divergence / canonical execution break.** Because reward distribution is part of `FinalizeState`, a different staking-info record produces a different post-block state root. The victim node will reject every canonical block whose state root it cannot reproduce, permanently stalling synchronisation — matching the "persistent corruption of trie/state/snapshot data that breaks canonical execution" impact class.

---

### Likelihood Explanation

- **Trigger**: any connected peer (semi-trusted) during fast-sync or via the `SyncStakingInfo` recovery path.
- **Precondition**: victim node must be fast-syncing to a pre-Kaia head, or an operator must invoke `SyncStakingInfo` against a malicious peer.
- **No cryptographic barrier**: the staking-info wire format (`P2PStakingInfo`) carries no signature or Merkle proof; the only guard is the block-number equality check, which a malicious peer trivially satisfies.
- **Persistence**: once written, `WriteStakingInfo` overwrites the DB entry; the corruption survives restarts. [9](#0-8) 

---

### Recommendation

1. **Implement the missing validation** in `queue.DeliverStakingInfos`: re-derive the staking info from the block's state root (via `StakingModule.getFromState`) and compare it against the peer-supplied data before writing to DB.
2. **Remove the `TODO-Kaia-Snapsync` placeholder** and treat absent validation as a build-blocking issue.
3. **Apply the same guard in `SyncStakingInfo`**: after receiving a `P2PStakingInfo`, verify its contents against the canonical state at `stakingInfo.BlockNum` before calling `PutStakingInfoToDB`.

---

### Proof of Concept

1. Run a modified Kaia node that, when serving `StakingInfoRequestMsg`, returns a `P2PStakingInfo` with `CouncilStakingAmounts` inflated for the attacker's validator address (e.g., set to `math.MaxUint64 / numValidators`).
2. Connect a victim node (fast-sync mode, pre-Kaia target head) to the malicious peer.
3. The victim calls `handleStakingInfoMsg` → `pm.downloader.DeliverStakingInfos` → `queue.DeliverStakingInfos` with `validate` returning `nil`. [10](#0-9) 

4. `commitFastSyncData` writes the falsified record to DB.
5. After fast-sync, the victim node attempts to process the next canonical block. `GetDeferredReward` reads the falsified staking info, computes a different reward distribution, and produces a state root that does not match the block header — the block is rejected and the node stalls.

// handleStakingInfoMsg handles staking information response message.
func handleStakingInfoMsg(pm *ProtocolManager, p Peer, msg p2p.Msg) error {
	if pm.chainconfig.Istanbul == nil || pm.chainconfig.Istanbul.ProposerPolicy != uint64(istanbul.WeightedRandom) {
		return errResp(ErrUnsupportedEnginePolicy, "the engine is not istanbul or the policy is not weighted random")
	}

	// A batch of stakingInfos arrived to one of our previous requests
	var stakingInfos []*staking.P2PStakingInfo
	if err := msg.Decode(&stakingInfos); err != nil {
		return errResp(ErrDecode, "msg %v: %v", msg, err)
	}
	// Deliver all to the downloader
	if err := pm.downloader.DeliverStakingInfos(p.GetID(), stakingInfos); err != nil {
		logger.Debug("Failed to deliver staking information", "err", err)
	}
	return nil
