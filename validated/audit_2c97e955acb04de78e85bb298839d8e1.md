### Title
Single Failing Submodule Aborts Entire Worktree Configuration, Causing Persistent Sync Denial - ([File: main.go])

### Summary
`git-sync`'s `configureWorktree` runs a single, all-or-nothing `git submodule update --init [--recursive] [--depth N]` command to update every submodule of a checked-out commit. If any one submodule in that set fails to initialize/update (unreachable host, disallowed protocol, bad credentials, etc.), the whole command fails and `configureWorktree` returns an error, aborting the entire sync for that commit — even though the top-level content and all other submodules were fine. This mirrors the reported bug class: a per-item failure inside an aggregate operation (there: `payoutFor` for one market breaking the whole `findMarketFor` loop; here: one submodule breaking the whole `configureWorktree`/`SyncRepo` call) instead of being isolated or gracefully skipped.

### Finding Description
`configureWorktree` performs the submodule update as one shell-out to git with no per-submodule isolation: [1](#0-0) 

If this call fails, the error propagates directly out of `configureWorktree` and is returned by `SyncRepo` without any partial success handling: [2](#0-1) 

The outer sync loop in `main` treats any `SyncRepo` error uniformly: it increments `failCount`, logs, and retries on the next period, re-fetching and re-attempting the *same* target ref/commit every cycle: [3](#0-2) 

Crucially, there is no mechanism to fall back to a previously good worktree, skip the problematic submodule, or advance the "current" hash — `SyncRepo` returns before `publishSymlink` is ever reached, so the symlink is never updated: [4](#0-3) 

If `maxFailures` is exceeded, the process exits, and (per the container's restart policy) will simply repeat the identical failure on restart, since the underlying condition (the bad submodule at that commit) is unchanged: [5](#0-4) 

### Impact Explanation
An attacker who can introduce a commit into the tracked ref (e.g., a merged pull request, a compromised contributor, or any actor with push access to the synced branch/tag) can add or modify a `.gitmodules` entry so that one submodule out of many is guaranteed to fail — for example, pointing it at an unreachable host, a URL using a protocol blocked by the runner's git config (`protocol.*.allow`), or credentials that will not resolve. From that commit onward, **every** sync attempt fails at the submodule-update step, so:
- The published `--link` symlink is frozen at the last good commit and never advances, even for unrelated top-level file changes bundled in later commits.
- This is a persistent sync denial: legitimate, unrelated updates to the watched ref become permanently undeliverable until an operator manually intervenes (reverts the bad submodule or reconfigures git-sync), because git-sync has no mechanism to isolate or skip the failing submodule and always retries the whole commit as a unit.

This matches the accepted "persistent sync denial" impact category.

### Likelihood Explanation
Likelihood depends entirely on the threat model assumption that an attacker can get an arbitrary commit accepted onto the tracked ref (the same assumption underlying the "attacker-pushed commit" class named in scope). Given that assumption, triggering the failure is trivial and requires no special flags beyond the default submodule handling (`--submodules=recursive`, which is the default) being enabled; no privileged operator/node behavior is required.

### Recommendation
- Do not let a single submodule failure abort the entire sync of a commit. Consider running submodule updates per-submodule (e.g., iterate `git config -f .gitmodules --get-regexp path` and call `git submodule update --init <path>` individually), collecting/logging failures similarly to the existing `multiError` pattern used in `cleanup`/`removeDirContentsIf` (`main.go:1553-1588`, `main.go:1795-1798`), so that one bad submodule does not block the top-level checkout or unrelated submodules.
- Alternatively, treat submodule-update failures as non-fatal for publication (publish the top-level worktree state and surface the submodule error via metrics/logs) rather than failing `SyncRepo` outright, restoring forward progress for the rest of the tree.

### Proof of Concept
1. Configure `git-sync` with `--repo=<attacker-influenced repo>` and default `--submodules=recursive`.
2. Attacker (with push access to the tracked ref) adds a commit whose `.gitmodules` includes a submodule pointing to an unreachable or protocol-restricted URL (as demonstrated feasible via the project's own e2e submodule tests, which explicitly toggle `protocol.file.allow`) alongside legitimate top-level file changes: [6](#0-5) 
3. On the next sync cycle, `git fetch`/`reset` succeed, `createWorktree` succeeds, but `configureWorktree`'s `git submodule update --init` call fails because of the bad submodule entry (`main.go:1744`), so the whole `SyncRepo` call returns an error before `publishSymlink` runs.
4. Every subsequent cycle repeats the same failure (`main.go:1056-1063`), so the `--link` target never advances past the last commit before the malicious one — a permanent denial of legitimate sync progress until the offending commit is removed from the ref or the operator otherwise intervenes.
