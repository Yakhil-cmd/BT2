### Title
Unhandled `throw` in `readDataFeedValue`'s candidate-sorting logic can crash AA execution and cause node disagreement - (File: `data_feeds.js`)

### Summary
`data_feeds.js:readDataFeedValue()` aggregates candidate data-feed values across multiple oracle addresses' *unstable* AA-authored units, exactly like `BondAggregator.findMarketFor` aggregates candidate markets across multiple markets. When it finds more than one ambiguous candidate that ties on both `latest_included_mc_index` and `level`, the `Array.sort()` comparator executes `throw Error("can't sort candidates "+a+" and "+b)` [1](#0-0) . This is a synchronous, uncaught exception raised from deep inside AA trigger/formula evaluation, exactly analogous to `BondBaseSDA.payoutFor` reverting inside `BondAggregator.findMarketFor`'s loop and breaking the whole aggregation - except here the failure is an unhandled JS exception rather than a graceful bounce.

### Finding Description
`readDataFeedValue` is called (via `formula/evaluation.js`) whenever an oscript formula evaluates a `data_feed[[oracles=...]]` expression with `unstable_opts` enabled (the default context used while evaluating AA triggers, so that an AA can react to data feeds posted by other AAs that are not yet stable) [2](#0-1) .

Inside the aggregation loop, for every unstable unit authored by an AA and matching the requested oracle addresses and mci range, it pushes a candidate `{value, latest_included_mc_index, level, unit, mci}` [3](#0-2) .

If more than one candidate is collected and `ifseveral !== 'abort'`, the code sorts candidates by `latest_included_mc_index` then `level`. If two candidates tie on *both* fields (a routine situation in a DAG, since two unrelated AA-authored units can easily share the same `latest_included_mc_index` and the same `witnessed level`, e.g., two different oracle AAs responding to sibling triggers around the same DAG depth), and `bIncludeAllUnstable` is false (the normal AA-trigger case, as opposed to `'all_unstable'`), the comparator throws instead of returning a value:

```js
if (bIncludeAllUnstable) // still ambiguous, sort randomly (it's OK outside AAs)
    return 1;
throw Error("can't sort candidates "+a+" and "+b);
``` [4](#0-3) 

`Array.prototype.sort` runs synchronously; a `throw` inside its comparator propagates synchronously up the call stack of whatever invoked `readDataFeedValue`/`readDataFeedValueByParams`, which is itself invoked synchronously-in-callback from formula evaluation during AA trigger handling (`aa_composer.js` `evaluateAA`/`handleTrigger`). Unlike the rest of the AA evaluation pipeline - which is carefully designed so that any formula/getter error results in a graceful `bounce()` of the AA response - this particular failure mode is a raw, unhandled `Error` thrown mid-`sort()`, not funneled through the `setFatalError`/`cb(err)` error-handling convention used everywhere else in `formula/evaluation.js`. If nothing upstream wraps this call in a `try/catch`, it becomes an uncaught exception in the unit-validation/AA-execution path that every full node must run in order to process the triggering unit and reach consensus on the resulting state-variable/response changes.

### Impact Explanation
This mirrors the Bond `findMarketFor` bug class: a read/aggregation helper that loops over multiple candidate items and unconditionally reverts/throws when hitting one specific, easily-reachable data condition, instead of gracefully resolving or reporting the ambiguity. In ocore the consequence is more severe than a reverted read call:

- Because AA trigger execution is part of the deterministic ledger-processing pipeline that every full node runs to agree on new AA state, an uncaught exception here can crash the node process (or otherwise abort processing) while handling a *legitimately postable* AA trigger unit.
- If different nodes fail to process the triggering unit consistently (e.g., some nodes crash/restart at different times, or the exception interacts differently with concurrent async work), this can produce node disagreement on the validity/state of an AA response, or an inability of affected nodes to advance the DAG for units that depend on the triggering unit - i.e., a network unable to confirm new units in that vicinity, which is one of the explicitly recognized high-impact outcomes for this bug class.
- Because AAs commonly aggregate values from multiple oracle/AA data feeds (as intended in this very API), this is reachable by an ordinary, unprivileged user simply sending an AA trigger unit at a moment when two qualifying unstable data-feed-posting AA units happen to tie on `latest_included_mc_index` and `level` - not by a malicious peer, hub, or privileged operator.

### Likelihood Explanation
Ties on `(latest_included_mc_index, level)` between two different unstable AA-authored units are a normal, expected occurrence in a DAG (two siblings built on the same parents at the same witnessed level), not a contrived edge case. Any AA design that reads a `data_feed` value contributed by more than one oracle/AA address (a supported and encouraged pattern per the API's own `oracles` array parameter) is exposed. Any user who sends a valid trigger to such an AA while this tie condition exists in the unstable DAG region will hit this code path. No special privileges, malicious peers, or protocol-level attacks are required - only ordinary AA usage with more than one oracle address, which is a documented feature of `readDataFeedValueByParams`/`data_feed[[oracles=...]]` [5](#0-4) .

### Recommendation
Do not `throw` inside the `Array.sort()` comparator (or anywhere in this aggregation path) for an ambiguous-but-legitimate data condition. Instead:
- Treat an unresolved tie the same way the code already treats the `'abort'`/`bIncludeAllUnstable` cases: return a well-defined, non-throwing result (e.g., set `objResult.bAbortedBecauseOfSeveral = true`, or resolve the tie deterministically, e.g., by unit hash) and route the error back through the callback-based error-handling convention (`setFatalError`/`cb(err)`) already used throughout `formula/evaluation.js` and `formula/validation.js`, so that ambiguity results in a graceful AA `bounce()` rather than an uncaught process-level exception.
- Ensure any remaining `throw` sites within `data_feeds.js` (`readDataFeedValue`'s "unstable unit not in assoc" checks, `dataFeedExists`'s equivalent checks) are audited and wrapped so they cannot propagate uncaught through the AA-trigger/unit-validation pipeline.

### Proof of Concept
1. Deploy AA `Oracle1` and AA `Oracle2`, each of which, upon receiving a trigger, posts a `data_feed` message for the same `feed_name` (e.g., `price`), with the same value, as part of their `messages` response.
2. Craft two trigger units so that the resulting `Oracle1` and `Oracle2` response units end up as siblings sharing the same `latest_included_mc_index` and the same `witnessed level` (straightforward to arrange by posting both trigger units on the same parents/mci around the same time - a routine DAG occurrence, not requiring any protocol violation).
3. Deploy a consumer AA `Consumer` whose oscript formula queries:
   `data_feed[[oracles=Oracle1_ADDR, Oracle2_ADDR, feed_name='price']]` while `Oracle1`'s and `Oracle2`'s responses are still unstable.
4. Any unprivileged user sends a trigger unit to `Consumer`.
5. During AA trigger evaluation, `formula/evaluation.js` calls `data_feeds.readDataFeedValueByParams` → `readDataFeedValue`, which collects both `Oracle1` and `Oracle2`'s candidate values, finds them tied on `(latest_included_mc_index, level)`, and executes the `sort()` comparator's `throw Error("can't sort candidates ...")` [1](#0-0) , producing an uncaught exception in the unit-validation/AA-trigger-processing path instead of a graceful bounce of the `Consumer` trigger.
