### Title
`Api::CCMenuController` bypasses per-`ApiClient` stack scoping, letting a stack-scoped token read CCMenu status for any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
Every other API controller resolves the current stack through `Api::BaseController#stack`, which is derived from `stacks`, a set scoped down to `current_api_client.stack_id` when the client is stack-scoped. `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, skipping that scoping entirely. Any authenticated `ApiClient` with `read:stack` permission can therefore fetch CCMenu deploy/task status for a stack it was never authorized for, simply by changing the `stack_id` path segment.

### Finding Description
`Api::BaseController` establishes the binding "stack a token authorizes == stack it touches": [1](#0-0) 
`stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` whenever the `ApiClient` carries a `stack_id`, and `stack` is always resolved via that scoped relation (`stacks.from_param!`). All permission-bearing controllers built on this base (`DeploysController`, `RollbacksController`, `Api::StacksController`, etc.) inherit this scoped `stack` method, so `require_permission :deploy, :stack` / `:read, :stack` is enforced against the very same stack the token is scoped to.

`Api::CCMenuController` breaks this equality: [2](#0-1) 
It declares `require_permission :read, :stack` (line 6), which only checks that the permission string `read:stack` is present on `current_api_client.permissions` — it performs no comparison against `current_api_client.stack_id`. The controller's private `stack` method (lines 29-31) is overridden to call `Stack.from_param!(params[:stack_id])`, bypassing the scoped `stacks` relation from the base class entirely. As a result, the check "does this token have `read:stack`" and the object actually rendered ("this particular stack") are decoupled: the token authorizes reads for one stack, but the code path touches whichever stack is named in the URL.

`ApiClient.check_permissions!` confirms the permission check is purely capability-based and stack-agnostic: [3](#0-2) 

The route is scoped only by a `stack_id` path parameter, not enforced by ownership: [4](#0-3) 

Note that `Api::CCMenuController` also swaps token transport (query-string `params[:token]` instead of Basic-Auth) via its own `authenticate_api_client` override, which is intentional for the CCMenu XML use case, but it doesn't change the core scoping bug — any valid stack-scoped `read:stack` token, however obtained, is affected.

### Impact Explanation
A `Shipit::ApiClient` created with `stack_id` set and only `read:stack` permission (the exact shape produced by `CCMenuUrlController#client`, or by an admin issuing a narrowly-scoped read-only token intentionally restricted to one stack/repository) can be replayed against `GET /api/stacks/:stack_id/ccmenu` for any other stack in the Shipit instance. This discloses task/deploy status information (latest deploy id, running state, end time, project name) for stacks the token holder has no authorization to see — an unauthorized read of stack state that crosses the deployment-trust boundary the rest of the API enforces ("a stack a token authorizes" vs "a stack it touches").

### Likelihood Explanation
Any party in possession of a valid, narrowly stack-scoped API token (e.g., a CI job, external status dashboard, or a leaked CCMenu URL meant for one project) can trivially exploit this by substituting a different `stack_id` in the request path — no additional privilege, secret, or session is required beyond the token itself.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and rely on the base class's scoped `stacks.from_param!` (or otherwise validate `params[:stack_id]` against `current_api_client.stack_id` when the client is stack-scoped) so the CCMenu endpoint enforces the same stack-authorization binding as every other API controller.

### Proof of Concept
1. Admin issues (or CCMenu flow auto-creates) an `ApiClient` scoped to `stack_id = A` with permissions `['read:stack']`.
2. Attacker (or the legitimate holder of that token for stack A) sends:
   `GET /api/stacks/other-owner/other-repo/other-env/ccmenu?token=<stack-A-token>`
3. `require_permission :read, :stack` passes because the token has `read:stack` in `permissions`, independent of which stack is requested.
4. `stack` resolves via `Stack.from_param!(params[:stack_id])`, returning stack B (unrelated to the token's `stack_id`).
5. The controller renders stack B's latest deploy/task status in the XML response, disclosing state the token was never authorized to see.

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
```
