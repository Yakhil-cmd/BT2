### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` but events are dispatched against a different, unbound field `repository.full_name` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), but the event handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolve the target `Repository`/`Stack` using the independent field `repository.full_name`. These two attacker-supplied JSON fields are never cross-validated against each other.

### Finding Description
`verify_signature` computes `repository_owner` purely from the JSON body and uses it to pick the `GithubApp` instance whose secret is used to verify `X-Hub-Signature`: [1](#0-0) [2](#0-1) 

Crucially, if that resolved app has no `webhook_secret` configured, verification is skipped entirely and any payload is accepted: [3](#0-2) 

Once the request passes (or is unconditionally accepted because the org has no secret), the full raw JSON body is handed unmodified to every registered handler: [4](#0-3) 

Handlers, however, do not use `repository.owner.login`/`organization.login` (the field that gated the signature check) to find the target — they use `repository.full_name`: [5](#0-4) 

and act on whatever `Stack`s that `Repository` has, e.g. `PushHandler` enqueues a sync for any matching stack using `params.after`/`branch`: [6](#0-5) 

Because `repository.owner.login` (used to pick/authenticate the signing organization) and `repository.full_name` (used to pick the acted-upon repository) are independent, attacker-controlled strings, the equality the engine implicitly assumes — "the organization whose secret validated this payload == the repository being mutated by this payload" — does not hold. An attacker who can get *any* payload accepted for an unsecured/organization-less app configuration (e.g. `repository.owner.login` pointing at an org entry that exists in `Shipit.github_apps` config but has no `webhook_secret` set, so `verify_webhook_signature` short-circuits to `true`) can set `repository.full_name` to a completely different, fully-secured organization/repository (e.g. `secured-org/production-repo`) and have Shipit process a forged `push`, `status`, `pull_request`, `check_suite`, or `merge_status` event against that protected stack — without ever knowing `secured-org`'s webhook secret.

### Impact Explanation
This breaks the deployment-trust binding between "the organization that authenticated the webhook" and "the repository that is written to." Depending on the event type dispatched, this enables:
- Forged `push` events triggering `GithubSyncJob`/`sync_github` against a protected stack.
- Forged `status`/`check_suite`/`merge_status` events manipulating `deployable_status`, which downstream can gate automatic merges/deploys.
This constitutes an unauthorized effect on a repository/stack the attacker has no legitimate credential for — matching the Critical "unauthorized deploy, rollback or merge" bar, since it can influence merge/deploy readiness signals for a stack outside the attacker's authenticated organization boundary.

### Likelihood Explanation
Exploitability depends on at least one organization entry in the Shipit GitHub Apps configuration lacking a `webhook_secret` (or an attacker otherwise obtaining a valid signature for any one org). Given `verify_webhook_signature` explicitly treats a blank secret as always-valid, and multi-tenant Shipit deployments commonly configure many orgs (some staging/internal orgs configured without secrets during setup), this is a realistic misconfiguration rather than a purely theoretical one, and the code contains no defense-in-depth check that `repository.full_name`'s owner matches the field used for signature-organization selection.

### Recommendation
In `WebhooksController#verify_signature`, after resolving the signing organization, cross-validate it against `repository.full_name`'s owner segment (and `repository.owner.login`) before dispatch, rejecting the payload if they diverge. Additionally, `GithubApp#verify_webhook_signature` should not silently accept unsigned payloads for organizations with no `webhook_secret`; configuration validation should require a secret for every configured app.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `unsecured-org` (no `webhook_secret`) and `secured-org` (has stacks and a `webhook_secret`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "secured-org/production-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "unsecured-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/incorrect) `X-Hub-Signature` header.
4. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("secured-org/production-repo")` and enqueues a sync/deploy-affecting job for that stack, even though no signature covering `secured-org` was ever verified.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
