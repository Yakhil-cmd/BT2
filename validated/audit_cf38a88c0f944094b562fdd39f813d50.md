## Title
Cross-organization CI status forgery via `StatusHandler`'s unscoped commit lookup enables unauthorized deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController` verifies the GitHub webhook `X-Hub-Signature` using the `webhook_secret` of the organization derived from the payload (`repository.owner.login`, falling back to `organization.login`), but the actual side effect performed by `StatusHandler` is applied to **any** commit in the entire Shipit database matching a SHA, with no check that the commit belongs to a stack/repository owned by the organization whose secret validated the signature. This breaks the binding "organization that authenticated the signature" == "repository/commit that gets written," analogous to the ETH/WETH mismatch in the cited report where the value checked (`address(this).balance >= underlyingAmount`) differs from the value actually acted upon.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate against using only the payload-supplied organization identity: [1](#0-0) [2](#0-1) 

That verified `params` blob is then handed unmodified to the event handler: [3](#0-2) 

`StatusHandler#process`, however, never re-derives or checks the repository/organization at all — it looks up commits **globally by SHA** across every stack/repository tracked by the Shipit instance: [4](#0-3) 

Compare this with every other handler in the codebase (`PushHandler`, `CheckSuiteHandler`, the `pull_request/*` handlers), all of which scope their lookups through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before touching any records: [5](#0-4) [6](#0-5) [7](#0-6) 

`StatusHandler` is the sole outlier: it acts on `params.sha` with no `repository`/`organization` scoping whatsoever, so the value that was cryptographically bound to the verified organization (the payload's `repository`/`organization` login used to pick the `webhook_secret`) is never the value that governs which record is mutated (`params.sha`, matched globally).

In a multi-tenant deployment (`Shipit.github` supports per-organization configuration, see `lib/shipit/github_app.rb` and `config/secrets.development.example.yml`'s commented multi-org block), any organization with its own valid, correctly-configured GitHub App/webhook_secret can send a `status` event whose `repository`/`organization.login` matches its own org (so `verify_signature` passes) while setting `sha` and `state` to reference a commit belonging to a **completely different organization's stack**. `commit.create_status_from_github!` will create a matching `Status` for that foreign commit: [8](#0-7) 

### Impact Explanation
`Commit#deployable?` and `Commit#blocked?` (and thus the deploy-gating logic used throughout the app) rely directly on the `statuses`/`status` computed from these records: [9](#0-8) 

By forging a `success` status for a target commit in a stack the attacker does not own or have any legitimate GitHub access to, the attacker can flip `deployable?` to `true` for that commit (assuming CI wasn't blocking) and even trigger `schedule_continuous_delivery` / `ContinuousDeliveryJob`, resulting in an **unauthorized deploy** of a commit that never actually passed the target organization's real CI. This satisfies the "unauthorized deploy" Critical-impact category, since the write ability granted by one organization's signature is being exercised against another organization's repository/stack, entirely bypassing repository-write/authentication boundaries the signature check was meant to enforce.

### Likelihood Explanation
Requires a Shipit instance configured for more than one GitHub organization (documented, first-class multi-tenant configuration support in `lib/shipit/github_app.rb`/`secrets.yml`), and requires the attacker to control (or have legitimately configured) any one of those organizations' GitHub App webhook secrets — a low bar relative to compromising the target organization. No repository write access, GITHUB_TOKEN, or session/API token is needed; only knowledge of one tenant's own `webhook_secret`, which that tenant's administrator inherently possesses. The attacker only needs to know or guess a target commit SHA that Shipit already tracks (visible via the public/organization-visible Shipit UI, commit lists, or GitHub itself).

### Recommendation
Scope `StatusHandler#process` to the repository indicated in the payload (as all other handlers do), and cross-check that the resolved repository's owning organization matches the organization whose secret validated the request signature, e.g. filter through `stacks`/`Repository.from_github_repo_name(payload.dig('repository','full_name'))` before touching `Commit` records, exactly like `PushHandler`/`CheckSuiteHandler` already do.

### Proof of Concept
1. Deploy Shipit configured with two tenants, `org-a` (attacker-controlled webhook secret) and `org-b` (victim, tracks stack `org-b/victim-repo` with commit `deadbeef` currently pending/failing CI).
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/attacker-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(org-a's webhook_secret, body)>` and POSTs to `/github/webhooks`.
4. `WebhooksController#repository_owner` resolves to `org-a`; `verify_signature` succeeds using `org-a`'s legitimate secret.
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` — matching the commit in `org-b/victim-repo` — and calls `create_status_from_github!`, creating a forged `success` status unrelated to `org-a`.
6. If this flips `deployable?` to true for that commit, a subsequent deploy trigger (e.g. continuous deployment) ships the victim commit despite it never passing `org-b`'s real CI — an unauthorized deploy achieved purely by signing with an unrelated org's secret.
