### Title
Forged `status` webhook, using signature-bypass on any org with no `webhook_secret`, mutates commit statuses on ANY stack via unscoped `Commit.where(sha:)` lookup, triggering `merge!` when `merge_queue_enabled` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` whenever the organization resolved from the *attacker-controlled* `repository.owner.login`/`organization.login` field has no `webhook_secret` configured, so an attacker can pick any such org to pass signature verification with no valid secret. `StatusHandler#process` then runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` with zero scoping to the authenticated organization/repository/stack, so the forged status is applied to whatever commit row happens to match that SHA — even one that belongs to an entirely different, properly-secured stack. If that target stack has `merge_queue_enabled: true`, a forged "success" status can flip a pending merge request past `all_status_checks_passed?` and cause `ProcessMergeRequestsJob` to call `merge_request.merge!`.

### Finding Description
The broken binding: the code implicitly assumes `authenticated_org(payload) == owning_org(Commit.find_by(sha: payload.sha).stack)`. That equality does not hold anywhere in the code.

- `Shipit::WebhooksController#verify_signature` resolves `repository_owner` purely from the JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`), which is fully attacker-controlled input, and looks up the corresponding `GitHubApp` via `Shipit.github(organization: repository_owner)`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` short-circuits to `true` if that org's `webhook_secret` is blank: `return true unless webhook_secret`. [3](#0-2) 
- Once verification "passes," `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to `StatusHandler`, whose `process` method resolves `Commit` purely `by sha`, with no filter on `stack_id`, `repository`, or the org that was authenticated: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [4](#0-3) 
- `Commit#create_status_from_github!` → `add_status` creates the `Status` record, and if the commit's simple status transitions (e.g., to `success`/`pending`), it calls `stack.schedule_merges`, which for stacks with `merge_queue_enabled: true` enqueues `ProcessMergeRequestsJob`. [5](#0-4) [6](#0-5) 
- `ProcessMergeRequestsJob#perform` checks `merge_request.all_status_checks_passed?` and, if satisfied, calls `merge_request.merge!`, using the GitHub App's own credentials against the *victim* repository. [7](#0-6) 

**Attacker's exact request**: The attacker sends `POST /webhooks` with `X-Github-Event: status`, a body containing `repository.owner.login` (or `organization.login`) set to any GitHub org for which the operator did not configure a `webhook_secret` (which the docs explicitly call "optional" — `config/secrets.development.example.yml` even ships with `webhook_secret: # nil` by default), and `sha` set to the head commit SHA of a pull request queued in a *different*, `merge_queue_enabled: true` stack (a SHA the attacker can trivially learn by opening/inspecting the target PR on GitHub, or from the target's public CI logs/README). No `X-Hub-Signature` value need be valid, and none of Shipit's session/API-token/team-membership checks are involved because `/webhooks` is unauthenticated by design.

**Why existing guards fail**: `verify_signature` only proves the request originated from *some* org's key material or, if that org has no secret, proves nothing at all — the check exists per-organization, not per-commit/per-stack. `StatusHandler` performs no secondary check that the resolved `Commit`'s `stack.repository` actually corresponds to the org that was "authenticated" in `verify_signature`. There is no `stack_id`/`repository` filter in the `Commit.where(sha:)` call, so the cross-tenant binding is never enforced.

### Impact Explanation
An attacker who controls (or merely knows the existence of) any GitHub org that has no `webhook_secret` configured on this Shipit installation can forge `status` events that mutate `Status` records for commits belonging to *any other* stack on the same installation — a payload from one repository mutating another's stack/commit, explicitly listed as Critical impact. When the target stack has `merge_queue_enabled: true`, this is amplified beyond a benign status write: it can drive `ProcessMergeRequestsJob#perform` to call `merge_request.merge!`, causing an unauthorized merge on the victim repository using the Shipit GitHub App's credentials. This is repeatable against any stack/commit whose SHA the attacker can learn, is not limited to a single tenant, and matches "unauthorized deploy, rollback or merge" from the Critical impact list.

### Likelihood Explanation
Preconditions: (1) the Shipit installation must have at least one configured GitHub org/app entry with no `webhook_secret` (a state the docs present as normal/optional, and the shipped example config defaults to `nil`), and (2) the target stack must have `merge_queue_enabled: true` and open merge requests gated on status checks that a forged "success" status can satisfy. Attacker cost is a single unauthenticated HTTP POST; the target commit SHA is public GitHub information obtainable without any privilege. Repeatable indefinitely, no rate limiting or replay protection observed at this layer. Likelihood is high wherever a multi-org Shipit deployment has any org onboarded without a webhook secret — a config choice explicitly permitted by this engine's own documented setup.

### Recommendation
- Do not allow `verify_webhook_signature` to return `true` when no secret is configured; treat a missing `webhook_secret` as "reject all webhooks for this org" (fail closed) rather than "accept all," or require `webhook_secret` to be mandatory in `Shipit.github` config validation.
- Independently of the signature fix, scope `StatusHandler` (and any other handler resolving records purely by `sha`) to the authenticated `repository_owner`/`repository.full_name`, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner, ... })`, so a valid signature for org A can never mutate a commit belonging to org B's stack.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "forged status webhook for a secret-less org mutates a commit belonging to a different, merge_queue_enabled stack" do
  victim_stack = shipit_stacks(:shipit) # merge_queue_enabled: true
  victim_stack.update!(merge_queue_enabled: true)
  merge_request = shipit_merge_requests(:shipit_mergeable_pending_ci) # pending, gated on required status context
  victim_commit = merge_request.head

  # Attacker-chosen org has no webhook_secret configured (default/no-secret app config)
  attacker_org_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => merge_request.stack.required_statuses.first, # publicly known required check name
    'repository' => { 'owner' => { 'login' => 'attacker-controlled-org-without-secret' } }
  }.to_json

  request.headers['X-Github-Event'] = 'status'
  # No valid X-Hub-Signature is set / signature verification is bypassed because
  # Shipit.github(organization: 'attacker-controlled-org-without-secret').webhook_secret is blank

  assert_enqueued_with(job: Shipit::ProcessMergeRequestsJob, args: [victim_stack]) do
    post :create, body: attacker_org_payload, as: :json
    assert_response :ok
  end

  # Binding under test: authenticated_org == owning_org(commit.stack) should hold; it does not.
  assert_not_equal 'attacker-controlled-org-without-secret', victim_stack.repository.owner
  assert victim_commit.reload.statuses.exists?(state: 'success', context: merge_request.stack.required_statuses.first)
end
```
This demonstrates the cross-tenant write (`Status` created for `victim_commit` from a forged, unauthenticated-for-that-stack request) and the downstream `ProcessMergeRequestsJob` enqueue that can lead to `merge_request.merge!` being invoked against the victim repository.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
