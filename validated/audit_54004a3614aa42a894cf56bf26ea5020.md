### Title
`SwapFirstAssetTrader::refund_weight` executes AssetConversion swap with no minimum-output protection, enabling sandwich extraction on XCM fee refunds - ([File: cumulus/primitives/utility/src/lib.rs])

### Summary
The Uniswap-based report flags a swap executed with `amountOutMinimum = 0`, meaning any attacker who manipulates the pool price around the trade can force a bad execution price and pocket the difference. The Polkadot SDK analog is `SwapFirstAssetTrader::refund_weight`, which performs a real AMM swap against `pallet-asset-conversion` while passing `None` as `amount_out_min` — the FRAME equivalent of a zero/absent slippage bound — during XCM execution.

### Finding Description
`SwapFirstAssetTrader` is a `WeightTrader` used to let XCM programs pay delivery/execution fees in a non-native asset by swapping it into the runtime's `Target` fee asset via `pallet-asset-conversion`'s `SwapCredit` trait.

- In `buy_weight` [1](#0-0) , the user's asset is exchanged for an *exact* amount of `Target` fee using `swap_tokens_for_exact_tokens`, which inherently bounds the amount of input asset spent (the caller controls the input by definition of "exact output").
- However, in `refund_weight`, when unused weight must be refunded back into the user's original asset, the code calls:
```rust
let refund = match SwapCredit::swap_exact_tokens_for_tokens(
    vec![Target::get(), refund_swap_asset],
    refund,
    None,
);
``` [2](#0-1) 

Here `amount_out_min` is hardcoded to `None`. Looking at the trait definition and pallet implementation, `None` disables the minimum-output check entirely: [3](#0-2) [4](#0-3) 

This is functionally identical to `sellForETH`'s `amountOutMinimum = 0` in the audited report: the swap will execute at whatever price the on-chain AMM pool currently reflects, with zero downside protection for the account being refunded.

### Impact Explanation
`pallet-asset-conversion` pools are public, permissionlessly tradable AMM pools (constant-product, per `get_amount_out`/`get_amount_in` in `substrate/frame/asset-conversion/src/lib.rs`). Any signed account can submit ordinary `swap_exact_tokens_for_tokens` / `swap_tokens_for_exact_tokens` extrinsics against the exact same pool used by `SwapFirstAssetTrader`. An attacker who can predict or trigger an upcoming refund swap (triggered deterministically at the end of XCM execution proportional to unused weight) can:
1. Front-run: swap into the pool to shift the price against the refund direction.
2. Let the refund execute at the manipulated price via `swap_exact_tokens_for_tokens(..., None)`, causing the refunded account to receive materially less than fair value.
3. Back-run: reverse the price-manipulating swap, capturing the difference as profit.

This does not require any privileged role — any user can submit XCM programs (e.g., `BuyExecution` with a non-`Target` asset that routes through `SwapFirstAssetTrader`) and any third party can submit ordinary swap extrinsics on the same public pool. The victim (whichever account's XCM refund is diminished) loses value; the extracted value is a genuine, deterministic value transfer captured by the sandwiching party.

### Likelihood Explanation
Likelihood is Medium-Low bounded by real-world constraints:
- The refund amount is generally small relative to `buy_weight` (it represents only unused weight), which caps attacker profit per sandwich and may make gas/transaction costs of the attack exceed the extractable value for most XCM calls, mirroring BOB's own "risk accepted" rationale that this pattern is intended for small amounts.
- The attack does require the attacker to predict the block/transaction in which a given XCM message will be processed by `SwapFirstAssetTrader`, which is feasible since XCM execution timing on these public parachains (asset-hub-rococo/westend, penpal) is generally observable in the mempool/block production process, but this needs an active searcher monitoring the target pool.
- Unlike `buy_weight` (which is bounded to an exact target amount, limiting attacker profit to at most the input-token-side slippage), `refund_weight`'s uncapped `None` bound has no ceiling on the acceptable loss ratio.

### Recommendation
Pass a computed `amount_out_min` to `swap_exact_tokens_for_tokens` in `refund_weight`, derived from a `quote_price_exact_tokens_for_tokens` call (as is already done for `buy_weight`/`quote_weight`) with an acceptable slippage tolerance, and fail gracefully (returning `None` refund, i.e., forfeiting to `total_fee`, similar to existing error-handling branches) rather than accepting an unconstrained price when swapping the refund back.

### Proof of Concept
No executable PoC was run; this report is based on static code analysis and reachability confirmation only. Evidence gathered:
- `SwapFirstAssetTrader` is instantiated in production runtime XCM configs: `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/xcm_config.rs`, `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`, and `cumulus/parachains/runtimes/testing/penpal/src/xcm_config.rs` [5](#0-4) .
- The `None` `amount_out_min` argument is directly visible in the `refund_weight` implementation [6](#0-5) .
- `pallet-asset-conversion`'s own test suite (`swap_should_not_work_if_too_much_slippage`, `swap_credit_insufficient_amount_bounds`) confirms that when `amount_out_min`/`amount_in_max` are supplied, the pallet enforces `ProvidedMinimumNotSufficientForSwap`/`ProvidedMaximumNotSufficientForSwap`; when `None` is passed, this protection is bypassed by design [7](#0-6) .

Due to the effort constraints of this analysis, I did not build and execute a full integration test (e.g., XCM emulated test in `cumulus/parachains/integration-tests/emulated/tests/assets`) demonstrating an end-to-end sandwich with concrete before/after balances. That remains open and would be the next step to fully substantiate quantifiable loss. The existing `cumulus/primitives/utility/src/tests/swap_first.rs` test harness could be extended to simulate a pool-price shift between `buy_weight` and `refund_weight` calls to demonstrate the reduced refund value deterministically.
