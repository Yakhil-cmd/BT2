### Title
Webhook signature verifies the payload's `repository.owner.login` organization while all mutating handlers act on the independently-controlled `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, derived from the JSON body itself (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Every mutating webhook handler (`PushHandler`, `CheckSuiteHandler`, PR handlers, etc.) instead resolves the target `Stack`/`Repository` from a *different* field in the same body — `payload.dig('repository','full_name')` via `Handler#repository_name`/`#stacks`. Nothing ties these two fields together, so the organization whose secret authenticated the request is not the repository that ends up being written to.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` picks the GitHub App config for HMAC verification purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

The base `Handler` class — used by `PushHandler` (which triggers `stack.sync_github`) and `CheckSuiteHandler` (which schedules check-run refreshes) — resolves the affected repository/stack from a completely separate, unvalidated field of the same payload: [3](#0-2) [4](#0-3) 

There is no code anywhere that asserts `repository.full_name` starts with `repository.owner.login`. Since the entire raw body is HMAC-signed, this is normally not exploitable for a single-tenant, single-secret deployment because GitHub itself always emits a self-consistent payload for real events. But Shipit explicitly supports **multiple GitHub Apps/organizations**, each with its own `webhook_secret`, keyed by organization name in `config/secrets.yml` (see `docs/setup.md` "Using Multiple Github Applications" and the corresponding fixture): [5](#0-4) 

`GithubApp#verify_webhook_signature` further shows the secret is looked up per-organization and, if that organization's `webhook_secret` is blank (as literally configured for `OrgTwo` above), the check is bypassed entirely: [6](#0-5) 

Putting this together: an attacker who is able to produce a valid signature for *any one* organization configured on this Shipit instance (either because that org's `webhook_secret` is blank/misconfigured, as the shipped multi-org example demonstrates is a supported configuration shape, or because they control that org's own App/webhook secret as its administrator) can submit an arbitrary POST body where `repository.owner.login`/`organization.login` names that org (satisfying `verify_signature`) while `repository.full_name` names an entirely unrelated victim repository tracked by the same Shipit instance. `Handler#stacks` will resolve to the victim's `Repository`/`Stack` via `Repository.from_github_repo_name(repository_name)`, and e.g. `PushHandler#process` will call `stack.sync_github(expected_head_sha: params.after)` on it, or `CheckSuiteHandler` will trigger check-run refresh state changes on the victim stack.

### Impact Explanation
This breaks the binding "organization authenticated == repository written," letting an entity that only controls credentials for one (possibly low-privilege or misconfigured) organization on a multi-tenant Shipit instance forge webhook-driven state changes (sync triggers, check-run state, PR metadata writes) against a repository/stack belonging to a completely different, victim organization it has no access to. This is a cross-repository write across organizational trust boundaries, matching the Critical impact bucket.

### Likelihood Explanation
Requires: (a) Shipit configured with multiple GitHub Apps/organizations (a documented, supported configuration), and (b) the attacker controlling or knowing the webhook secret for at least one configured organization (including the degenerate but supported case of a blank `webhook_secret`). This is a realistic misconfiguration/multi-tenant scenario explicitly documented and fixtured in the repo, not a purely theoretical one, but it does depend on the operator's multi-org setup, so likelihood is moderate rather than certain.

### Recommendation
In `Handler#repository_name`/`#stacks`, cross-check that the resolved repository actually belongs to the same organization that was used to select and verify the webhook signature (i.e., assert `repository.full_name.split('/').first == repository_owner` before processing), or pass the verified organization down into each handler and use it (not attacker-controlled `full_name` alone) to scope repository/stack lookups.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`: `VictimOrg` (tracked stack `VictimOrg/app`) and `AttackerOrg` (attacker controls its App/webhook secret, or its `webhook_secret` is left blank as in the shipped `secrets_double_github_app.yml` example).
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/app" }
}
```
3. Attacker computes `X-Hub-Signature` using `AttackerOrg`'s webhook secret (or omits/uses any value if that org's secret is blank).
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` and validates successfully. [1](#0-0) 
5. `PushHandler` resolves `Repository.from_github_repo_name("VictimOrg/app")` via `Handler#repository_name` and calls `stack.sync_github` on the victim's stack, even though the request never authenticated against `VictimOrg`. [3](#0-2)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
