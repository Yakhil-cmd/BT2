### Title
Membership webhook `team.id` (`github_id`) lookup is not scoped to the verifying organization, allowing a tenant to mutate another tenant's team roster - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#process` resolves the target `Team` solely by the GitHub-global `team.id` (`github_id`) via `find_or_create_team!`, and then executes `team.members.delete(member)` for `action == 'removed'` without ever checking that the team's `organization` matches the organization whose webhook secret validated the request. In a Shipit deployment configured for multiple GitHub organizations (multi-tenant), an operator of one legitimately-configured organization can sign a `membership` webhook with their own valid secret but supply a `team.id` belonging to a different organization's privileged team, causing that team's roster to be mutated.

### Finding Description
The binding this depends on is: **organization verifying the signature (`repository_owner` used in `Shipit.github(organization: repository_owner).verify_webhook_signature`) == organization owning the mutated `Team` (`team.organization`)**. Tracing the code shows this binding is never enforced:

- `WebhooksController#verify_signature` looks up the webhook secret via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the JSON payload (`repository.owner.login` or, for org-level events like `membership`, the `organization.login` sub-object) [1](#0-0) . This only succeeds if that organization name corresponds to a **real, separately-configured** organization in Shipit's own secrets configuration (raising `GithubOrganizationUnknown` -> 422 otherwise).
- `MembershipHandler#find_or_create_team!` resolves (or creates) the `Team` using only `params.team.id` as the `github_id` key, with no `WHERE organization = params.organization.login` constraint: `Team.find_or_create_by!(github_id: params.team.id) { ... }` [2](#0-1) .
- `process` then dispatches on `action`; for `'removed'` it calls `team.members.delete(member)` directly on whatever `Team` record was found, with no re-check of `team.organization == params.organization.login` [3](#0-2) .

Consequently, if the attacker controls (or is an admin of) organization `A`, which is a legitimately configured Shipit tenant with its own real `webhook_secret`, they can send a correctly-signed `membership` `removed` webhook whose `organization.login` is `A` (so `verify_signature` passes against `A`'s real secret) but whose `team.id` is the `github_id` of a privileged team belonging to organization `B`. Because `find_or_create_team!` ignores the organization entirely when matching on `github_id`, it resolves `B`'s team, and the handler deletes the targeted operator's `Membership` row for that team - `Membership.exists?(team: B_team, user: operator)` flips from `true` to `false`, deauthorizing a legitimate operator in organization `B` using only organization `A`'s credentials.

Existing guards do not stop this: `verify_signature` only proves the request was signed by *some* configured organization, not that this organization owns the `team.id` referenced in the payload; the `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not cross-field ownership; and `Team.find_or_create_by!` has no organization-scoping clause.

### Impact Explanation
The attacker can deauthorize any legitimate operator from any privileged `Shipit::Team` whose numeric GitHub `team_id` they know or can enumerate (GitHub team IDs are not secret and are exposed in various GitHub API responses/URLs), as long as the attacker controls at least one org that is itself configured as a real, distinct Shipit tenant. This is a cross-tenant authorization mutation: a payload verified under one organization's identity mutates another organization's team/authorization state, matching the in-scope "payload for one repository/tenant mutating another's team" Critical impact category. It is repeatable against any team `github_id` and any member login, and since `Team` records back stack authorization (`Shipit.github_teams` style checks elsewhere in the app rely on `Team`/`Membership`), removing a membership can silently strip deploy/merge authorization from a legitimate operator.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured with multiple distinct GitHub organizations (multi-tenant), each with its own `webhook_secret`, and requires the attacker to control (or administer) at least one of those tenant organizations with a legitimate webhook secret provisioned to them by the Shipit operator - this is a realistic scenario for any Shipit deployment serving several customer/business-unit organizations. The attacker additionally needs the numeric GitHub `team_id` of the target team, which is discoverable via GitHub's public API/UI. Given these preconditions, the attack is a single HTTP POST, fully repeatable, and requires no session, no API token, and no secrets beyond the attacker's own legitimately-issued webhook secret for their own organization.

### Recommendation
Scope the `Team` lookup (and any mutation) to the organization that verified the webhook, e.g., change `find_or_create_team!` to `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)` and additionally assert in `process` that the resolved `team.organization == params.organization.login` before performing `add_member`/`delete`, raising/dropping the event otherwise.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership 'removed' from org A cannot delete membership on org B's team" do
  team_b = shipit_teams(:org_b_privileged_team) # github_id: 999, organization: 'org-b'
  operator = shipit_users(:operator)
  Shipit::Membership.create!(team: team_b, user: operator)

  assert Shipit::Membership.exists?(team: team_b, user: operator)

  # Payload signed only with org-A's own webhook secret, but referencing org-B's team id
  payload = {
    action: 'removed',
    team: { id: team_b.github_id, name: team_b.name, slug: team_b.slug, url: team_b.api_url },
    organization: { login: 'org-a' }, # attacker-controlled tenant, real secret for org-a
    member: { login: operator.login }
  }.to_json

  Shipit::Webhooks::Handlers::MembershipHandler.call(JSON.parse(payload))

  # BEFORE: exists? == true ; AFTER: exists? == false, despite org-a never owning team_b
  refute Shipit::Membership.exists?(team: team_b, user: operator)
end
```
This demonstrates the equality `verifying_organization ('org-a') == team.organization ('org-b')` is false yet the mutation still succeeds, confirming the vulnerability.

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)

            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end
