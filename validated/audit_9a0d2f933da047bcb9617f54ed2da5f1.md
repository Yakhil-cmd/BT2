### Title
Unvalidated route payload lets injected hop contracts execute arbitrary calls under the victim's signature - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The TechDocs advisory is a sanitization-bypass/injection class: attacker-supplied content that should have been neutralized is delivered verbatim to the victim's context. The analog in XOXNO Lending is the opaque `swap: Bytes` route that every controller strategy forwards unvalidated into the swap router. The router keeps no allowlist of the pool/token addresses the payload names, so an attacker-authored route can put arbitrary Wasm on the call stack *below the victim's `require_auth` entry*. That injected code can then call `token.transfer(victim, attacker, amount)`; Soroban records it as a child of the victim's own authorization tree, and it executes the moment the victim signs that tree — draining wallet funds far beyond the routed amount.

### Finding Description
Every routed strategy (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `swap_tokens_or_passthrough`) accepts a caller-provided `StrategySwap` and passes it verbatim to `router.execute_strategy` with no decode or constraint on which contracts the route may invoke. The controller's defenses only bound the *routed* funds: it grants exactly one `authorize_transfer_as_current` for `amount_in`, rejects overspend, requires positive measured output, and runs final risk gates. None of these bound what payload-named third-party code does elsewhere in the transaction. The router calls whatever `assets`/`ops` entries the XDR names (no venue allowlist), and a rogue "hop pool" invoked mid-route runs with the victim's auth entry as its ancestor. Per the protocol's own threat model, "a token transfer that such code makes from the caller is recorded ... as a child of the caller's authorization entry, and it executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount." The regression test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the mechanics end-to-end: recording-mode simulation attaches the stolen `transfer` as a child of `swap_collateral`, and enforcement executes it when signed.

### Impact Explanation
Theft of user funds. A victim interacting through a malicious/compromised front end or quote service receives a `routeXdr` that embeds an attacker-deployed hop contract. Simulation returns an authorization tree containing a hidden `token.transfer(victim, attacker, X)` child for any token the victim holds — including tokens the protocol never listed. If the wallet/client signs the returned tree without decoding each child (exactly the bypass the advisory describes: content that one path would sanitize is served raw through another), the victim loses arbitrary wallet balances while the swap itself settles normally and passes every controller gate. Severity: Medium — requires tricking the victim into signing a poisoned tree, matching the advisory's `UI:R` profile.

### Likelihood Explanation
The attacker needs no privilege: they craft the route bytes and lure the victim (phished UI, malicious quote backend, or a client that auto-signs simulation output). The code path is fully reachable through `swap_collateral`/`multiply`/`execute_strategy`. Likelihood is tempered because an honest client decodes the route and refuses trees with foreign children, and the protocol's threat model explicitly assigns that check to the client — but nothing in the on-chain path prevents the injection.

### Recommendation
Constrain the blast radius on-chain rather than relying on every client to decode routes: (1) governance- or registry-maintained allowlist of pool/venue addresses the router may invoke, so payload-named contracts outside known venues revert; (2) document in the controller's interface that `swap` must be treated as executable code and that signers must reject auth trees with children beyond the single input `transfer`; (3) prefer a fixed-venue dispatcher (opcode → immutable adapter address) so the payload can select behavior but never the callee.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates the full chain: `UnlistedPoolRouter::execute_strategy` invokes the payload-named `hop_pool`, and `RogueHopPool::swap` calls `token::transfer(victim → attacker, WALLET_BALANCE)`. In recording mode the host attaches that transfer as a child of the victim's `swap_collateral` entry (`simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry`, lines 195–227), and enforcing mode executes it when the poisoned tree is signed (`enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer`, lines 229–269) — Alice's `WALLET_BALANCE` of an unrelated token goes to the attacker while her swap still pays out. The controller forwards the bytes untouched at `swap_tokens` (`authorize_transfer_as_current` then `router.execute_strategy(&controller, &amount_in, swap)`), and `docs/explanation/threat-model.md:154-165` acknowledges the router "keeps no allowlist" of payload-named addresses.
