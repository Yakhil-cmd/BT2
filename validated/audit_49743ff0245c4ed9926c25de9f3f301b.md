Based on the investigation, the actual root cause is confirmed but the exploit narrative in the question needs correction regarding the specific preconditions.

### Title
`Shipit::Api::CCMenuController#stack` bypasses `current_api_client.stack_id` restriction, allowing a stack-scoped `ApiClient` token to read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController#stack` (the "intended" implementation) scopes stack lookup through `stacks`, which restricts to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped [1](#0-0) . `CCMenuController` overrides this private method with `Stack.from_param!(params[:stack_id])`, completely dropping the `current_api_client.stack_id` check [2](#0-1) . Any `ApiClient` bearing `read:stack` permission — regardless of the stack it was scoped to at creation — can therefore read the CCMenu XML (build status/labels) of an arbitrary stack by changing `stack_id` in the URL.

### Finding Description
The broken binding is: `stack.id == current_api_client.stack_id` (when `current_api_client.stack_id` is present) must hold before rendering, per `BaseController#stacks` [3](#0-2) . `CCMenuController#stack` never evaluates this; it resolves the stack from `params[:stack_id]` alone via `Stack.from_param!` [2](#0-1) , so `stack.id` can be any value regardless of `current_api_client.stack_id`.

Regarding the specific token minted by `CCMenuUrlController#fetch`: its `client` method builds the `ApiClient` via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` without ever passing `stack:` to `create_with` [4](#0-3) . Consequently this particular client's `stack_id` is always `nil`, and per `BaseController#stacks`'s own logic (`current_api_client.stack_id? ? Stack.where(...) : Stack.all`), such a client is *already* unrestricted across all stacks even under the "correct" scoped implementation — for this client, the override in `CCMenuController` produces no different result. The genuine, exploitable divergence is for **any other `ApiClient` that is legitimately created with a stack restriction** (e.g. through the API client management UI/API, where `stack:` is explicitly set to scope a token to one stack). Such a token is intended to only see that one stack via the properly-scoped API endpoints, but because `CCMenuController#stack` ignores `current_api_client.stack_id`, that same token can be replayed against `GET /stacks/:any_other_stack/ccmenu?token=<scoped_token>` and will render that other stack's build status, bypassing its intended single-stack restriction.

### Impact Explanation
An `ApiClient` token intentionally scoped to stack A (via `stack_id`) can be used to read build status/labels (XML) of any other stack B through `Api::CCMenuController#show` [5](#0-4) . This is an unauthenticated-for-that-tenant read of stack state across tenant boundaries, matching the "High: unauthorized read of stack state" category. It does not achieve RCE, credential exfiltration, or a write into another stack's state — it is confined to disclosure of CCMenu status data (build pass/fail, last deploy time). Repeatable for any number of stacks, for as long as the leaked/legitimate scoped token remains valid.

### Likelihood Explanation
Requires possession of a valid `ApiClient` token that itself was deliberately created with a non-nil `stack_id` restriction (this is not the case for tokens generated via the "Fetch URL" flow in `CCMenuUrlController`, whose clients always have `stack_id == nil` and are therefore already stack-unrestricted by design). Given such a scoped token, exploitation is trivial: a single GET request with a substituted `stack_id` path param. No secrets, no GitHub interaction, no session required beyond having obtained the token through any legitimate means.

### Recommendation
Remove the override in `Shipit::Api::CCMenuController` and rely on `BaseController#stack`/`#stacks`, or explicitly re-implement the scope check: `@stack ||= stacks.from_param!(params[:stack_id])`.

### Proof of Concept
1. Create two stacks A and B in different repositories.
2. Create an `ApiClient` with `permissions: %w[read:stack]` and `stack: stack_A` (simulating a properly stack-scoped token, as opposed to the always-nil-stack_id token from `CCMenuUrlController`).
3. `GET /stacks/#{stack_B.to_param}/ccmenu?token=<that client's authentication_token>`.
4. Assert `response.status == 200` and that the rendered XML corresponds to stack B's latest deploy/status, proving the stack-A-scoped token read stack B's data — i.e., assert `current_api_client.stack_id == stack_A.id` while `stack.id == stack_B.id` in the exploited request, violating the intended equality.
