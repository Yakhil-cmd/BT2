### Title
Missing zero/invalid-address validation on `creator` in `InitializeWithPermission` permanently locks accumulated creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`InitializeWithPermission` accepts an arbitrary `creator: UncheckedAccount<'info>` with no ownership or non-zero validation, then stores it as `pool_state.pool_creator` and unconditionally turns on creator-fee collection (`enable_creator_fee = true`).

### Finding Description
In `Initialize`/`InitializeWithPermission`, the `creator` account is declared with only a `/// CHECK:` comment and no `constraint`/`address` check: [1](#0-0) 

Whatever pubkey is supplied by the transaction's account list is written directly into the pool state as `pool_creator`, with no requirement that it be a signer, an existing account, or a non-default pubkey: [2](#0-1) 

Unlike `Initialize` (permissionless path, `enable_creator_fee = false`), `initialize_with_permission` always sets `enable_creator_fee = true`, so creator fees are actively carved out of every subsequent swap into `creator_fees_token_0`/`creator_fees_token_1`: [3](#0-2) 

Later, the only way to claim those accumulated fees requires either a signature from the recorded `pool_creator` (`CollectCreatorFee`) or building an ATA for that same address (`CollectCreatorFeePermissionless`): [4](#0-3) [5](#0-4) 

If `creator` is set to `Pubkey::default()` (all-zero, the "zero address" analog of the reported Solidity bug), the System Program ID, or any other address with no known private key, `CollectCreatorFee` can never be signed (no keypair exists for those addresses), and `CollectCreatorFeePermissionless` will only be able to push the accumulated fees into an ATA owned by an address nobody controls. Either way, the creator-fee share of every swap that flows through that pool becomes permanently unrecoverable.

### Impact Explanation
This is a permanent freezing of value that is diverted from swap fees on every trade in the pool — value that would otherwise be part of the fee ledger available to the fee model's intended distribution (protocol/fund/creator split). Because `enable_creator_fee` is forced `true` for pools created via `initialize_with_permission`, this is not an opt-in griefing vector limited to the creator's own funds; every unprivileged swapper who trades against the pool contributes fees that get permanently locked once the pool is seeded with an uncontrollable `creator` address. This matches the "unbacked/insolvent fee-ledger accounting" and "permanent freezing of funds" impact classes.

### Likelihood Explanation
`initialize_with_permission` is gated by a `Permission` PDA tied to `payer`, so only a permissioned account can create such a pool — however, the report scope explicitly includes `initialize_with_permission` as an in-scope, reachable entry point. Any permissioned caller (or one who is careless/compromised) can supply `Pubkey::default()`, the System Program ID, or any other uncontrolled address as `creator` in a single transaction with attacker/careless-chosen accounts, with no on-chain check preventing it. This requires no special timing or race condition, only a single call to `initialize_with_permission` with the malformed account.

### Recommendation
Add an explicit constraint on the `creator` account in both `Initialize` and `InitializeWithPermission` account structs, e.g.:
```rust
#[account(constraint = creator.key() != Pubkey::default() @ ErrorCode::InvalidCreator)]
pub creator: UncheckedAccount<'info>,
```
Additionally consider requiring `creator` to be a `Signer` (or otherwise proven reachable/controllable) before enabling `enable_creator_fee = true`, so that no pool can be initialized with an unclaimable fee recipient.

### Proof of Concept
1. A permissioned account calls `initialize_with_permission` (having obtained a valid `Permission` PDA), passing `creator = Pubkey::default()` (or any other address with no known private key) as the `creator` account — this passes because `creator` has no validation beyond `UncheckedAccount`. [6](#0-5) 
2. `pool_state.initialize(...)` stores this address as `pool_creator` and sets `enable_creator_fee = true`. [2](#0-1) 
3. Any unprivileged user swaps against the pool via `swap_base_input`/`swap_base_output`; a portion of every trade fee accrues into `pool_state.creator_fees_token_0/1`.
4. No one can ever successfully call `CollectCreatorFee` (requires a signature from `pool_creator`, which is uncontrollable), and `CollectCreatorFeePermissionless` only forwards the tokens into an ATA owned by the same uncontrollable address — permanently locking the accumulated creator fees.
