Confirmed: this is a genuine multi-tenant Shipit deployment (`Shipit.github_organizations`, `github_app_config(organization)` in `lib/shipit.rb:170-200`), where each organization has its own `webhook_secret` configured under `secrets.github[org]`.

The binding that breaks is: **the organization whose secret authenticated the webhook signature** (`repository_owner = params.dig('repository','owner','login')`, an attacker-controlled field read from the *unverified* JSON body) vs. **the repository that handlers actually act on** (`payload.dig('repository','full_name')`, a separate, independently attacker-controlled field never cross-checked against `repository_owner`).

### Title
Cross-organization webhook forgery via mismatched signature-org and target-repository fields - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-tenant Shipit deployment, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the **unverified** JSON body, before the signature is checked. All downstream event handlers (`Shipit::Webhooks::Handlers::Handler#stacks`, `PushHandler`, the `PullRequest::*Handler`s) instead resolve the target `Repository`/`Stack` using `repository.full_name`, a second, independent field in the same body. Nothing binds these two fields together, so a valid signature computed with Org A's `webhook_secret` can be replayed with `repository.full_name` set to `OrgB/some-repo`, causing handlers to act on Org B's stacks despite the signature only proving knowledge of Org A's secret.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 
selects the `github_app` (and thus the `webhook_secret` used in `verify_webhook_signature`) via `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both read from `request.raw_post` before signature verification occurs.

`lib/shipit.rb#github`/`#github_app_config` shows each organization can have its own distinct `webhook_secret` in `secrets.github[org]`: [2](#0-1) 

Once `verify_signature` passes (using Org A's secret because `repository.owner.login == "OrgA"`), `WebhooksController#create` dispatches the *entire* raw payload to handlers: [3](#0-2) 

Handlers, however, never look at `repository.owner.login`. They resolve the affected repository purely from `repository.full_name`: [4](#0-3) [5](#0-4) 

and `Repository.from_github_repo_name` simply splits `full_name` on `/` and looks it up by owner/name with no relationship to the field used for signature-org selection: [6](#0-5) 

So the equality the app implicitly (and incorrectly) assumes is:
`organization-that-authenticated-the-signature (repository.owner.login) == organization-of-repository-that-is-written (repository.full_name)`

Because both fields live in the same attacker-controlled JSON body and neither is cross-validated, an entity that legitimately controls (or has leaked) Org A's `webhook_secret` — e.g. an admin of their own onboarded GitHub App/org in this multi-tenant install — can send:
```json
{"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}, "ref": "refs/heads/master", "after": "<attacker-controlled sha>"}
```
signed with Org A's secret. `verify_signature` verifies successfully against Org A's secret, and `PushHandler` then calls `stack.sync_github(expected_head_sha: params.after)` on Org B's stack, forging Org B's push/sync state without ever possessing Org B's `webhook_secret`.

### Impact Explanation
This lets a party who is a legitimate, low-privilege tenant of the Shipit instance (controls one organization's GitHub App/webhook secret) forge webhook events attributed to a different organization/repository it does not control — triggering `GithubSyncJob`, fabricating `status` results (`StatusHandler`), archiving/unarchiving `ReviewStack`s via `pull_request` label handlers, or creating `Membership`/`Team` records cross-tenant. This crosses the "cross-repository writes" boundary called out as a Critical/High impact, since state belonging to a repository/organization is mutated using authentication material that only proves control of a different, unrelated organization.

### Likelihood Explanation
Requires the attacker to already control one organization's `webhook_secret` in a multi-org Shipit deployment (i.e., be a legitimate onboarded tenant, not require GitHub App private keys or Shipit session credentials). Given that Shipit explicitly supports multi-organization configuration (`github_app_config`), and tenants are expected to be mutually distrusting in such setups, this is a realistic configuration for any Shipit install offering multi-tenant onboarding.

### Recommendation
Bind signature verification to the same repository identity used by handlers: derive the verifying organization from `repository.full_name`'s owner segment (or require it to match `repository.owner.login`) rather than trusting `organization.login`/`repository.owner.login` alone, and reject the webhook if the two disagree. Alternatively, after verifying with the org selected by `repository_owner`, re-check that `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.owner == repository_owner` before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations, `orga` and `orgb`, each with a distinct `webhook_secret` (per `docs/setup.md` multi-org instructions / `secrets.github[org]`).
2. As the operator/attacker who legitimately possesses `orga`'s `webhook_secret`, construct a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {"owner": {"login": "orga"}, "full_name": "orgb/victim-repo"}
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orga_webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"orga"`, fetches `Shipit.github(organization: "orga")`, and successfully verifies the signature against `orga`'s secret.
5. `PushHandler#process` resolves the target repository from `repository.full_name` = `"orgb/victim-repo"` and enqueues `GithubSyncJob`/`sync_github` against `orgb`'s stack — a cross-organization write achieved with only `orga`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
