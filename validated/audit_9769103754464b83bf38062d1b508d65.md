## Title
Membership webhook `repository_owner` selection lets one org's `webhook_secret` authenticate a `Team`/`Membership` mutation attributed to a different org - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController#verify_signature` picks the GitHub App/`webhook_secret` to validate the HMAC signature using `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , while `MembershipHandler#find_or_create_team!` attributes the resulting `Team`/`Membership` write to `params.organization.login` independently [2](#0-1) . Because the request body is a raw attacker-controlled JSON POST (not a real GitHub payload), an attacker can populate both `repository.owner.login` and `organization.login` with different values, causing their own org's `webhook_secret` to authenticate a signature that ends up mutating a Team record attributed to a victim org.

## Finding Description
The broken binding as an equality that must hold but doesn't:
`repository_owner` (used to select the verifying `GitHubApp`/`webhook_secret` in `verify_signature`) `== params.dig('organization','login')` (used by `MembershipHandler` to attribute the `Team.organization`).

Trace:
- `POST /webhooks` is handled by `Shipit::WebhooksController#create`, with `before_action :check_if_ping, :drop_unhandled_event, :verify_signature` [3](#0-2) .
- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`, then does `Shipit.github(organization: repository_owner)` and verifies the raw request body against that org's configured `webhook_secret` via `GitHubApp#verify_webhook_signature` [4](#0-3) [5](#0-4) .
- Because `params` comes directly from the attacker's own raw JSON body, the attacker fully controls which keys are present. If the attacker includes `repository.owner.login = "attacker-org"` (an org they own, with a legitimately configured `webhook_secret`) alongside `organization.login = "victim-org"`, the `||` fallback is short-circuited: `repository_owner` resolves to `"attacker-org"`, so verification uses the attacker's own known `webhook_secret` — which the attacker can correctly compute the HMAC for.
- `verify_signature` passes (no `head(422)`), so `create` runs: `Shipit::Webhooks.for_event('membership').each { |handler| handler.call(params) }` [6](#0-5) .
- `MembershipHandler#process` never re-checks `repository_owner`; it reads `params.organization.login` directly to find-or-create a `Team` and add/remove a member [7](#0-6) , using the attacker-supplied `"victim-org"` value.

Root cause: the field used to select/verify the authenticating secret (`repository.owner.login`, falling back to `organization.login`) is not the same field that the handler treats as the target-of-record (`organization.login`) once `repository.owner.login` is present. No code re-validates that the two match after signature verification passes.

Existing guards don't stop this: `drop_unhandled_event` only checks that a handler is registered for the event name, not payload content [8](#0-7) ; `ExplicitParameters` schema in `MembershipHandler` only requires `organization.login` to be a `String`, it doesn't cross-check it against `repository.owner.login` or against whichever org string was used for signature verification [9](#0-8) .

## Impact Explanation
An attacker who owns any repository/org with a valid `webhook_secret` configured in Shipit (a normal, unprivileged onboarding scenario for a self-service Shipit deployment) can forge a `membership` webhook payload that is authenticated against their own secret but is attributed, by `MembershipHandler`, to an arbitrary victim organization string of their choosing. This lets the attacker create/modify `Team` rows and add/remove `Membership` rows for a `Team` under an org they don't control, potentially manipulating `Shipit.github_teams`-derived authorization (`Team#organization`) since Team/membership records feed into permission checks elsewhere in the engine. This is a cross-tenant mutation authenticated by the wrong party's secret — matching the "payload for one repository mutating another's ... team" Critical impact category. It's fully repeatable against arbitrary victim org strings from a single attacker-controlled account, requiring only that the attacker's own org is configured with a `webhook_secret` in Shipit.

## Likelihood Explanation
Preconditions: the attacker must have a repository/organization already registered in Shipit's GitHub App configuration with a `webhook_secret` set (a realistic precondition since Shipit supports self-service/multi-org configuration and organizations onboard their own webhook secrets). No Shipit session, API token, or GitHub secret belonging to the victim is needed. The attacker only needs to craft a raw JSON body and compute an HMAC-SHA1 with a secret they already know (their own), which is a trivial and repeatable action from any internet host capable of reaching `POST /webhooks`.

## Recommendation
Bind signature verification to the same field the handler will act on: derive `repository_owner` from `organization.login` first (or require exact equality between `repository.owner.login` and `organization.login` when both are present and reject otherwise), and pass that single validated organization value into the handler rather than letting `MembershipHandler` independently re-read `params.organization.login`. Concretely, have `verify_signature` compute the authoritative org value once, store it (e.g., via `request.env` or a param override), and have `MembershipHandler#find_or_create_team!` use that authoritative value instead of trusting the raw `params.organization.login` a second time.

## Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual additions)
test "membership event with mismatched repository.owner.login and organization.login is verified using the attacker org's secret but mutates the victim org's Team" do
  attacker_secret = "attacker-secret"
  Shipit.stubs(:github).with(organization: "attacker-org").returns(
    Shipit::GitHubApp.new("attacker-org", webhook_secret: attacker_secret)
  )

  payload = {
    action: "added",
    team: { id: 1, name: "Core", slug: "core", url: "https://api.github.com/teams/1" },
    repository: { owner: { login: "attacker-org" } }, # picked by verify_signature
    organization: { login: "victim-org" },            # used by MembershipHandler
    member: { login: "some-user" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", attacker_secret, payload)

  post :create, body: payload, headers: {
    'X-Github-Event' => 'membership',
    'X-Hub-Signature' => signature,
    'Content-Type' => 'application/json'
  }

  assert_response :ok
  team = Shipit::Team.find_by(github_id: 1)
  refute_nil team
  # Equality check both sides of the binding:
  assert_equal "attacker-org", nil # side A: value used to select webhook_secret (repository.owner.login)
  assert_equal "victim-org", team.organization # side B: value written by handler (organization.login)
  # Demonstrates side A != side B: a secret belonging to attacker-org authenticated a mutation attributed to victim-org.
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
