### Title
Commit-message spoofing of `Merge-Requested-By:` trailer allows attribution of arbitrary commits to a victim `Shipit::User` - ([File: app/models/shipit/user.rb])

### Summary
`Shipit::User.find_or_create_author_from_github_commit` trusts any line matching `Merge-Requested-By: <login>` found anywhere in a commit's raw GitHub message and unconditionally resolves the commit's `author` to that GitHub login via `find_or_create_by_login!`, without verifying that the named login actually authored, committed, or requested the merge of that commit. Because commit messages are attacker-controlled content (in a PR from their own fork), and this trailer is only intended to be produced by Shipit itself (`MergeRequest#merge_message`, `app/models/shipit/merge_request.rb:262-266`), an attacker can forge it in their own commit to have Shipit misattribute authorship of that commit to any existing GitHub login once the commit lands in a branch Shipit ingests.

### Finding Description
The security invariant being violated: **commit author `User` row == the GitHub account that actually authored/pushed that commit**. The code that is supposed to preserve this is: [1](#0-0) 

`github_commit.commit.message` is raw, attacker-controlled text taken verbatim from GitHub's commit object (`Commit.from_github`, `app/models/shipit/commit.rb:105-125`), with no check for who wrote it or whether it is actually a Shipit-generated merge commit. The regex `/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/` uses Ruby's line-anchored `^`/`$`, which matches on any line inside a multi-line message — not just a trailer Shipit itself appended. An attacker who can push a commit with a body such as:

```
some innocuous change

Merge-Requested-By: victim-login
```

on a branch/PR in their own fork causes this line to appear verbatim in the commit that eventually gets merged (e.g., via a plain GitHub "rebase and merge" or "merge commit" performed by a maintainer through the normal GitHub UI rather than Shipit's merge queue, which preserves original commit text). Once that commit lands on a branch Shipit tracks, ingestion (`GithubSync` / commit-creation path, `app/jobs/shipit/github_sync_job.rb`, ultimately calling `Commit.create_from_github!` → `Commit.from_github` → `User.find_or_create_author_from_github_commit`) matches the forged trailer and calls `find_or_create_by_login!(match_info[1])`, which look up or creates a `Shipit::User` for `victim-login` and sets it as `commit.author` — with no cross-check against `github_commit.author`/`github_commit.commit.author` (the real committer identity).

Existing guards do not prevent this: webhook signature verification, `ExplicitParameters`, and stack authorization only govern which stack/repository is affected, not the trustworthiness of commit message content once a commit is legitimately synced for that stack. There is no code path that compares the regex-derived login against the actual GitHub commit author/committer before trusting it.

### Impact Explanation
Once a commit is misattributed, `Commit#author` returns the victim's `Shipit::User` row (`app/models/shipit/commit.rb:31-33`). If a later task's `@task.author` derives from this commit (task/deploy attribution flow), `TaskCommands#env` in `lib/shipit/task_commands.rb:33-48` emits `SHIPIT_USER => "#{@task.author.login} (...) via Shipit"`, `EMAIL => @task.author.email`, and `GIT_COMMITTER_EMAIL => @task.user&.email` using the victim's login/name/email into the deploy output/environment that the attacker (as a contributor to that repository) can view. This is an authorization/audit-trail integrity break: deploy/merge actions get falsely attributed to a user who never touched the commit, and the victim's email is exposed in task output. This affects only the single repository/stack where the attacker can get a commit merged (not cross-tenant), and requires an existing Shipit `User` row for `victim-login` (or one is auto-created via `find_or_create_by_login!`).

### Likelihood Explanation
Exploitation requires: (1) the attacker can get a commit containing the forged trailer merged into a branch that a Shipit stack tracks — this is not fully within the attacker's control, since it depends on a maintainer merging the PR in a way that preserves the original commit message (rebase/fast-forward merge, or a squash merge that includes the commit body verbatim, both common GitHub defaults depending on repo settings). This makes the attack **conditional on maintainer/repo merge-strategy behavior**, not something the attacker can trigger unilaterally purely via webhook POSTs. The victim's login must be guessable/known (trivial — any public GitHub username). No Shipit secrets are needed. Given typical GitHub "rebase and merge" or "squash and merge (keep commit messages)" configurations, this is realistically triggerable by a low-privileged contributor.

### Recommendation
Do not trust the `Merge-Requested-By` trailer from arbitrary GitHub commit message text. Only apply it when the commit is verified to be a merge produced by Shipit's own merge flow (e.g., cross-reference against `stack.merge_requests` by PR number, as already done for `merge_requested_by` in `Commit#identify_merge_request`, rather than re-deriving from free-text commit message in `find_or_create_author_from_github_commit`), or require it be sourced from Shipit-controlled state (`MergeRequest#merge_requested_by`) instead of parsing the raw GitHub commit message a second time.

### Proof of Concept
```ruby
test "find_or_create_author_from_github_commit trusts a forged Merge-Requested-By trailer" do
  victim = shipit_users(:walrus)
  attacker_github_commit = resource(
    sha: 'deadbeef',
    commit: {
      author: { name: 'attacker', email: 'attacker@evil.com', date: Time.now.utc },
      committer: { name: 'attacker', email: 'attacker@evil.com', date: Time.now.utc },
      message: "innocuous change\n\nMerge-Requested-By: #{victim.login}\n"
    },
    author: { id: 999_999, login: 'attacker' },
    committer: { id: 999_999, login: 'attacker' }
  )

  resolved_author = Shipit::User.find_or_create_author_from_github_commit(attacker_github_commit)

  # BROKEN BINDING: commit author User row should equal the actual GitHub committer ("attacker"),
  # not the name forged in the message body.
  refute_equal victim, resolved_author, "author should not be spoofable via a forged commit-message trailer"
end
```
This test is expected to currently **fail** (i.e., `resolved_author == victim`), demonstrating the spoofing.

    def self.find_or_create_author_from_github_commit(github_commit)
      if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
        begin
          return find_or_create_by_login!(match_info[1])
        rescue Octokit::NotFound
          # Corner case where the merge-requested-by user cannot be found (renamed/deleted).
          # In this case we carry on and search for the commit author
        end
      end
      find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
    end
