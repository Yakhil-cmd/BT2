### Title
Unbounded future oracle timestamp acceptance can permanently freeze price resolution for a shared asset feed - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`oracle-timestamp-fresh` in `v0-4-market.clar` mis-handles the case where a submitted price timestamp is greater than the current `stacks-block-time`: it silently sets the staleness delta to `u0` instead of validating it, so *any* future-dated timestamp always passes the staleness check. Because the corresponding `last-update` map entry is keyed only by `{type, ident}` (i.e., per oracle feed, not per caller), any single unprivileged caller who submits (via `write-feeds`/borrow/withdraw/liquidate) a price update whose timestamp is ahead of `stacks-block-time` permanently raises the monotonic floor for that feed, causing all subsequent price resolutions from every other user of that asset to revert until real time catches up.

### Finding Description
`price-resolve` validates freshness and monotonicity against a **shared** map `last-update`, keyed by `{type: (buff 1), ident: (buff 32)}` — i.e., one entry per oracle feed, shared by every user, position, and operation (borrow, withdraw, liquidate, health checks) that depends on that asset's price: [1](#0-0) 

The freshness check is: [2](#0-1) 

If `ts > stacks-block-time`, `delta` is forced to `u0`, so `(<= delta max-staleness)` is unconditionally true — there is no upper bound check rejecting timestamps that are unreasonably far in the future.

`price-resolve` then unconditionally advances the shared floor whenever the new timestamp exceeds the stored one: [3](#0-2) 

Once `last-update[key]` is set to a timestamp beyond the real/current `stacks-block-time`, every subsequent legitimate price submission for that same feed by *any other user* fails the `(>= ts prev)` monotonicity check inside `oracle-timestamp-fresh`, because their genuine, current-time price update's `ts` will be less than the inflated `prev`. This makes price resolution for that asset revert with `ERR-ORACLE-INVARIANT` for everyone, not just the caller who submitted the bad timestamp.

Price feeds are attacker-reachable through `write-feeds`, which is invoked with a caller-supplied `(optional (list 3 (buff 8192)))` of raw Pyth feed blobs on ordinary user-facing operations (borrow/withdraw/liquidate/collateral-add etc.), meaning any unprivileged user can trigger a price update as a side effect of their own transaction: [4](#0-3) 

### Impact Explanation
Attacker: any unprivileged user who submits a Pyth update (obtained through normal Pyth channels) whose signed publish-time is ahead of the current Stacks block time for a given feed identifier. Victim: every other user of the protocol who holds a position (collateral/debt) denominated in that asset and needs a health check, borrow, withdrawal, or liquidation to succeed.

Without the attacker's transaction: legitimate users can resolve the price for that asset each block as new Pyth data arrives, and can borrow/withdraw/get liquidated normally.

With the attacker's transaction: the shared `last-update` entry for that feed is pinned to a timestamp beyond real time. Every subsequent caller's genuinely fresh price submission for the same feed has `ts < prev` and is rejected by `oracle-timestamp-fresh`, so `price-resolve`/`price-multi-resolve` revert for that asset until enough real time has elapsed to exceed the poisoned value. During that window, positions using that asset as collateral or debt cannot be correctly evaluated — borrowing, withdrawal, and (critically) liquidation of unhealthy positions in that asset are blocked. This is a shared-state DoS affecting third parties' funds, landing on the "temporary freezing of funds" impact class (and can escalate toward insolvency if liquidations are blocked long enough during an adverse price move).

### Likelihood Explanation
The bug is directly reachable by any user through routine operations that accept `price-feeds`, since `write-feeds` accepts arbitrary caller-provided feed blobs and forwards them to Pyth verification without any bound on how far in the future the attested publish-time may be. The magnitude of the freeze is bounded by how far ahead of `stacks-block-time` a validly-signed Pyth VAA's publish-time can be (dependent on clock/verification drift between Pyth/wormhole attestation and Stacks block time), so the practical severity ranges from a short-lived to a longer freeze depending on how much drift is achievable/observed in production, which could not be fully quantified from static code review alone.

### Recommendation
Fix `oracle-timestamp-fresh` to also bound timestamps that exceed `stacks-block-time` (reject or clamp, rather than treat as automatically fresh), e.g., reject if `ts - stacks-block-time` exceeds an allowed clock-skew tolerance, instead of forcing `delta` to `0`. Consider also making the monotonicity floor per-updater-invariant safe (e.g., cap accepted `ts` to `stacks-block-time + small_tolerance` before it is allowed to update `last-update`).

### Proof of Concept
1. Attacker submits, through any user-facing entrypoint accepting `price-feeds` (e.g. `borrow`, `withdraw`, `collateral-add`), a validly Pyth/wormhole-signed feed blob for asset `X` whose `publish-time` is ahead of the current `stacks-block-time` (even by the natural clock skew that exists between Pyth attestation and Stacks block timestamps).
2. `write-feeds` → Pyth verification succeeds (signature is valid); `price-resolve` is later invoked (by the attacker's own tx or a subsequent one) with this `ts`.
3. `oracle-timestamp-fresh` computes `delta = 0` because `ts > stacks-block-time`, so the staleness check passes trivially, and `(>= ts prev)` passes since `prev` is the previous (lower) real value; `last-update[{type,ident}]` is set to the future `ts`.
4. Any other user submits a genuinely fresh, current-time Pyth price for feed `X` in a later transaction. `oracle-timestamp-fresh` computes `(>= ts prev)` as false because `ts < prev` (the poisoned future value), so `price-resolve` returns `ERR-ORACLE-INVARIANT`.
5. All borrow/withdraw/liquidate operations depending on asset `X`'s price fail for every user until real time passes the poisoned future timestamp.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
