### Title
Malicious AA can force revert of an entire primary AA response, freezing payouts meant for other honest output addresses in the same response - ([File: aa_composer.js])

### Summary
`handleTrigger()` builds a single AA response unit containing all `payment` outputs generated by one execution of an AA (`sendUnit()`), then hands off to `handleSecondaryTriggers()` to invoke any AA addresses that were among those outputs as secondary triggers. If any secondary AA bounces, the code does not just fail that one output — it reverts the *entire* primary response, including payments to any other, unrelated, honest recipients in the same unit, and replaces it with a bounce refund to the trigger sender. This is the same "one recipient can force revert of a multi-party payout" bug class as the reported Sablier `_cancel()` issue, where the recipient's ability to make their own leg of the transfer fail is used to block funds intended for a completely different party.

### Finding Description
When a primary AA composes payment `messages`, all outputs (potentially addressed to several parties, some of which may themselves be AAs) are bundled into one response unit via `sendUnit()`: [1](#0-0) 

After the unit is saved, `handleSecondaryTriggers()` looks up which output addresses are AAs and, for each one, recursively invokes `handleTrigger()` as a secondary trigger: [2](#0-1) 

If any of those secondary AA triggers bounces (returns an error), and this is happening for a *primary* (non-secondary) trigger, the code calls `revert()` for the whole primary response rather than only failing the one secondary leg: [3](#0-2) 

`revert()` then rolls back all state changes and cached responses to the savepoint taken before the primary trigger executed, discarding the entire response unit — including any outputs to other, unrelated output addresses in that same unit — and replaces it with a plain bounce (refund of the trigger amount minus bounce fee back to the trigger sender): [4](#0-3) 

Because the payout to potentially several different parties is bundled atomically into one unit, any party that is paid via an AA address (rather than a plain wallet address) can act as the "recipient who reverts the transfer": they simply design (or configure via prior state) their AA so that it always bounces when receiving funds from the target primary AA. This forces `revert()` on every invocation, which cancels the entire multi-party payout — including the portion due to the *other*, honest party — and instead bounces the whole amount back to whoever posted the trigger. This mirrors exactly the reported bug class: a participant who controls how their leg of a multi-party transfer resolves can unilaterally block the delivery of funds to the other legitimate party in the same atomic operation.

### Impact Explanation
Any AA design that pays out to multiple parties in a single response — e.g., escrow, marketplace, auction, or payment-splitting AAs where one of the parties is (or can register) an AA address — is vulnerable to having its payouts permanently frozen/redirected by the counterparty. The counterparty AA can always bounce on receipt, so the intended recipients never get paid; the funds are bounced back to the trigger sender instead. This is a concrete AA fund-freezing/denial primitive reachable by any ordinary AA author who becomes a counterparty in another AA's multi-output response.

### Likelihood Explanation
Likelihood is high for any AA logic that includes an AA address among its output addresses (a fairly common pattern for AA-to-AA composition and payment splitting), since the attacker only needs to author an AA that always bounces on receiving these payments — no elevated privilege or race condition is required. It is fully reachable by an ordinary unprivileged AA author.

### Recommendation
Do not let the failure of one secondary AA's trigger revert the entire primary response's payment outputs to unrelated addresses. Instead, treat a bounced secondary AA output the same way a bounce is currently handled only for that AA (i.e., the secondary AA's own bounce should only affect its own state/balance, refunding its own share), while leaving the already-included payments to other, non-bouncing output addresses in the primary response intact and final.

### Proof of Concept
1. Deploy AA `X` designed to always fail validation/bounce whenever it receives a trigger (e.g., an `init`/`bounce(...)` unconditionally).
2. Deploy AA `P` (primary) whose response, for some trigger, sends outputs to two addresses in a single response unit: `X` (attacker-controlled) and `honest_address` (a normal wallet or another AA that should legitimately be paid).
3. Trigger `P`. `sendUnit()` builds and saves the response unit paying both `X` and `honest_address`.
4. `handleSecondaryTriggers()` sees `X` is an AA and invokes it as a secondary trigger; `X` bounces.
5. Because `bSecondary` is false at the primary level, `async.eachSeries`'s error handler calls `revert(...)` (`aa_composer.js:1749`), which rolls back the whole response, including the leg meant for `honest_address`, and instead bounces the funds back to whoever posted the trigger to `P`.
6. `honest_address` never receives its intended payment as long as `X` keeps bouncing, demonstrating funds freezing/denial for a third party caused solely by the choice of `X`'s owner.
