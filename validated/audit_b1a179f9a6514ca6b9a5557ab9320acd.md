### Title
Signature verification bound to `repository.owner.login` while all webhook handlers act on the unchecked `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App config (and thus the HMAC `webhook_secret`) used to authenticate a webhook based on `repository.owner.login` (or the fallback `organization.login`), but every event handler that actually performs the write (creating commit statuses, enqueuing sync/deploy jobs, scheduling check-run refreshes) resolves its target repository/stack from the completely separate `repository.full_name` field. These two JSON fields are never cross-checked, so a valid signature computed with one organization's webhook secret can be replayed with a `repository.full_name` pointing at a stack that belongs to a different, unrelated organization/repository.

### Finding Description
`verify_signature` computes `repository_owner` purely from attacker-controlled JSON: [1](#0-0) 

and uses it only to pick which `GitHubApp`/`webhook_secret` verifies the HMAC: [2](#0-1) 

Once the signature check passes, the raw, unmodified `params` (the full attacker JSON body) is dispatched to handlers: [3](#0-2) 

Every handler resolves the affected stacks from `repository.full_name`, a field the signature check never inspects: [4](#0-3) 

For example `PushHandler` triggers a GitHub sync for any stack matching that repo/branch: [5](#0-4) 

`StatusHandler` writes commit statuses (which gate deployability) purely by SHA, with no repository ownership check at all: [6](#0-5) 

and `CheckSuiteHandler` schedules check-run refreshes the same way: [7](#0-6) 

The binding that should hold is: `organization whose secret authenticated the request == organization owning the repository that gets written`. Because `repository.owner.login`/`organization.login` (used for auth) and `repository.full_name` (used for the write) are independent, unrelated JSON keys with no cross-validation, that equality is not enforced.

`Shipit.github(organization:)` shows each configured organization has its own independent `webhook_secret`: [8](#0-7) [9](#0-8) 

An operator running a multi-tenant Shipit instance (multiple GitHub organizations configured under `secrets.github`, as documented) knows the `webhook_secret` for their own organization "A" (they set it when creating their GitHub App). They can send a POST directly to `/webhooks` (this endpoint is public/unauthenticated apart from the HMAC check — no `ApiClient` token or session required) with:
- `X-Github-Event: status` (or `push`, `check_suite`)
- `X-Hub-Signature` computed with organization A's known `webhook_secret` over a JSON body where `repository.owner.login = "A"` (or `organization.login = "A"`) to pass `verify_signature`
- `repository.full_name = "B/victim-repo"` — a repository/stack tracked under a completely different organization "B" that they have no access to

`verify_signature` succeeds (secret A matches, since only `repository_owner` = A is inspected), and the handler then acts on stacks under `B/victim-repo`.

### Impact Explanation
This breaks the deployment-trust binding "an organization that authenticated versus the repository that is written," letting an attacker who only controls one tenant's webhook secret write to another tenant's data:
- Forge commit statuses (`StatusHandler`) on arbitrary commits of a victim stack, which can satisfy CI/deployability checks and enable an unauthorized deploy of that stack.
- Trigger `GithubSyncJob`/check-run refresh cycles on a victim stack (`PushHandler`, `CheckSuiteHandler`), causing state confusion or triggering task pipelines tied to that stack's `shipit.yml`.

This matches the Critical-tier impact "unauthorized deploy" (via forged passing commit status) and cross-repository writes across tenant boundaries.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub organization (a supported, documented configuration via `secrets.github`) and that the attacker controls one of those organizations' GitHub Apps (i.e., is a legitimate but semi-trusted tenant). No `ApiClient` token, no session, no GitHub App private key of the *victim* org, and no repository write access to the victim repo are needed — only the attacker's own org's `webhook_secret`, which they legitimately possess. This is a realistic misuse path in any shared/multi-org Shipit deployment.

### Recommendation
After signature verification, re-derive the organization from the same trusted config used to verify the signature and assert it matches the owner encoded in `repository.full_name` (or, better, look up the `Repository`/`Stack` via `Repository.from_github_repo_name` and confirm its recorded owner/organization equals `repository_owner` used for signature verification) before dispatching to any handler. Reject the webhook if the two do not match.

### Proof of Concept
1. Configure Shipit with two organizations, `A` and `B`, each with its own `webhook_secret` (per `config/secrets.*.yml`), and a stack tracking `B/victim-repo`.
2. As an operator/holder of org `A`'s `webhook_secret`, compute `X-Hub-Signature: sha1=<hmac>` over a JSON body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/tests",
     "repository": { "owner": { "login": "A" }, "full_name": "B/victim-repo" }
   }
   ```
   using secret A.
3. `POST /webhooks` with header `X-Github-Event: status` and the above body/signature.
4. `verify_signature` looks up `Shipit.github(organization: "A")` and validates successfully against org A's secret.
5. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb) writes a `success` status on the victim commit belonging to stack `B/victim-repo`, without ever checking that `A` owns that repository — potentially unblocking an unauthorized deploy of the victim stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
