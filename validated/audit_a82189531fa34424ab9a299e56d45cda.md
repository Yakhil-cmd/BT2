### Title
CEI Violation in `_requestERC20Transfer` Allows Reentrancy to Emit Duplicate Bridge Transfer Requests — (File: `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`_requestERC20Transfer` in `BridgeTransferERC20.sol` increments `requestNonce` **after** making external calls to the ERC20 token contract. This violates the Checks-Effects-Interactions pattern. Unlike `_requestKLAYTransfer` (which carries `nonReentrant`), `_requestERC20Transfer` has no reentrancy guard. A registered ERC20 token with a transfer callback can re-enter the bridge during fee payment, causing two `RequestValueTransfer` events to be emitted with sequential nonces. Bridge operators on the counterpart chain process both events, resulting in an unauthorized double transfer of bridged assets.

---

### Finding Description

`_requestERC20Transfer` executes two external calls before updating `requestNonce`:

```
_payERC20FeeAndRefundChange(...)   // external call #1 — IERC20.safeTransfer to feeReceiver/from
ERC20Burnable(_tokenAddress).burn(_value)  // external call #2 (modeMintBurn)
emit RequestValueTransfer(..., requestNonce, ...)
requestNonce++                     // state update — AFTER both external calls
``` [1](#0-0) 

`_payERC20FeeAndRefundChange` calls `IERC20(_token).safeTransfer` to pay the fee receiver and optionally refund the caller: [2](#0-1) 

The developer comment in `BridgeFee.sol` explicitly acknowledges that `_payKLAYFeeAndRefundChange` **requires its caller to be `nonReentrant`**, and lists `_requestKLAYTransfer` as the sole safe caller: [3](#0-2) 

No equivalent protection exists for `_payERC20FeeAndRefundChange`. `_requestKLAYTransfer` carries `nonReentrant`: [4](#0-3) 

`_requestERC20Transfer` carries no such modifier: [5](#0-4) 

The same pattern exists in `_requestERC721Transfer`, which makes two external calls (`_tokenAddress.call(...)` for tokenURI and `ERC721Burnable.burn`) before incrementing `requestNonce`: [6](#0-5) 

---

### Impact Explanation

**Broken invariant:** `requestNonce` must be incremented before any external call so that every `RequestValueTransfer` event carries a unique, already-committed nonce. During the window between the external calls and `requestNonce++`, the nonce is stale.

**Re-entry path (ERC20):** A registered ERC20 token whose `transfer`/`transferFrom` implementation fires a callback (e.g., ERC777 `tokensReceived`, or a custom `onTokenTransfer` hook) can call `bridge.onERC20Received(...)` during `_payERC20FeeAndRefundChange`. `onERC20Received` is `public` with no access control beyond `onlyRegisteredToken(msg.sender)`: [7](#0-6) 

**Execution trace (non-mintBurn mode, fee > 0):**

1. Outer call enters `_requestERC20Transfer`; `requestNonce = N`.
2. `_payERC20FeeAndRefundChange` calls `IERC20(token).safeTransfer(feeReceiver, fee)`.
3. Token's callback fires → re-enters `bridge.onERC20Received` → `_requestERC20Transfer` (inner call).
4. Inner call: `_payERC20FeeAndRefundChange` completes; emits `RequestValueTransfer` with `requestNonce = N`; `requestNonce++` → `N+1`.
5. Outer call resumes; emits `RequestValueTransfer` with `requestNonce = N+1`; `requestNonce++` → `N+2`.

Two `RequestValueTransfer` events (nonces N and N+1) are emitted in a single transaction. Bridge operators on the counterpart chain call `handleERC20Transfer` for both nonces. In non-mintBurn mode the destination bridge transfers `value_inner + value_outer` tokens to the attacker, while the source bridge only received `value_outer + feeLimit` tokens from the attacker. The difference (`value_inner`) is drawn from other users' funds locked in the destination bridge — an unauthorized transfer of bridged assets.

---

### Likelihood Explanation

**Trigger requirement:** A registered ERC20 token with a transfer callback. Token registration is an owner-privileged operation, making this a semi-trusted actor scenario. However:

- ERC777 tokens are widely deployed and have mandatory `tokensReceived` hooks.
- Custom ERC20 tokens with `onTokenTransfer` callbacks (e.g., LINK-style) are common.
- A bridge owner may register a legitimate ERC777 token without recognizing the reentrancy risk, since the KLAY path is guarded but the ERC20 path is not.

The asymmetry between the guarded KLAY path and the unguarded ERC20 path is a strong indicator that this was an oversight rather than an intentional design choice.

---

### Recommendation

Add `nonReentrant` to `_requestERC20Transfer` (and `_requestERC721Transfer`) or, equivalently, move `requestNonce++` to before the first external call:

```solidity
// CEI-compliant fix: increment before external calls
uint64 currentNonce = requestNonce;
requestNonce++;

uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);
if (modeMintBurn) {
    ERC20Burnable(_tokenAddress).burn(_value);
}
emit RequestValueTransfer(..., currentNonce, ...);
```

Alternatively, import `ReentrancyGuard` (already used by `BridgeTransferKLAY`) and apply `nonReentrant` to `_requestERC20Transfer` and `_requestERC721Transfer`.

### Proof of Concept

```solidity
// Malicious ERC20 token registered on the bridge
contract MaliciousERC20 is ERC20 {
    BridgeTransferERC20 bridge;
    bool attacking;

    // Called by bridge during _payERC20FeeAndRefundChange → safeTransfer
    function transfer(address to, uint256 amount) public returns (bool) {
        if (!attacking && to == feeReceiver) {
            attacking = true;
            // Re-enter bridge with value2 = large amount
            bridge.onERC20Received(msg.sender, attacker, LARGE_VALUE, 0, "");
            attacking = false;
        }
        return super.transfer(to, amount);
    }
}
```

1. Owner registers `MaliciousERC20` on the bridge.
2. Attacker sends `value + feeLimit` tokens to bridge, triggering `onERC20Received`.
3. During fee payment, `transfer` re-enters `onERC20Received` with `value2 = LARGE_VALUE`.
4. Inner call emits `RequestValueTransfer(nonce=N, value=LARGE_VALUE)`.
5. Outer call emits `RequestValueTransfer(nonce=N+1, value=value)`.
6. Bridge operators process both on the counterpart chain.
7. Attacker receives `LARGE_VALUE + value` tokens on the destination chain, having deposited only `value + feeLimit` on the source chain.

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
