## Validate: the broken binding

The security property that should hold is:

```
Status.stack_id == (the stack whose repository actually authenticated this webhook)
```

i.e. for `commit.create_status_from_github!` to attach a `Status` to a `Commit` belonging to stack `S`, the webhook that triggered it must have been signed for the GitHub organization/repository that owns `S`.

What the code actually does is:

```
Status.stack_id == (any stack owning any Commit row whose sha == params.sha)
```

which is a **different, broader set** whenever the same git commit sha is reachable from more than one stack's `commits` table (e.g. a PR head commit that exists both in a victim's tracked repository and in an attacker's own fork/repository, which is exactly how GitHub PR head shas work — the object is identical in both remotes).

## Finding Description

`Shipit::Webhooks::Handlers::StatusHandler#process` is:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Unlike other handlers, it does **not** scope the query through the repository named in the webhook payload. Compare `CheckSuiteHandler`, which correctly uses `stacks.where(branch: ...)` (derived from `payload.dig('repository','full_name')`) before touching any commit:

```ruby
def process
  stacks.where(branch: params.check_suite.head_branch).each do |stack|
    stack.commits.where(sha: params.check_suite.head_sha).each(&:schedule_refresh_check_runs!)
  end
end
``` [2](#0-1) 

`Shipit::Webhooks::Handlers::Handler` even provides that scoping helper (`stacks`, built from `repository_name`), but `StatusHandler` never calls it:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`WebhooksController#verify_signature` only proves that the request was signed with the webhook secret belonging to `params.dig('repository','owner','login')` — it proves *who sent the webhook*, not *which commit rows the webhook is allowed to mutate*:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end
``` [4](#0-3) 

There is no uniqueness constraint or model-level check forcing `sha` to be unique across `Commit` (it is only scoped per-stack in practice via `stack.commits.by_sha`), so `Commit.where(sha: ...)` can legitimately match rows in unrelated stacks/repositories that happen to share a git commit sha — which is routine for identical commits reachable from a fork and its upstream (same tree/parents/authorship ⇒ identical SHA-1, no hash break required).

`create_status_from_github!` then writes a real `Status` row attributed to that commit's actual `stack_id`:

```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [5](#0-4) 

That `Status` then feeds `MergeRequest#all_status_checks_passed?` / `#any_status_checks_failed?`, both of which construct a `Shipit::Status::Group` (`StatusChecker`-equivalent) purely from `head.statuses_and_check_runs`, with no re-check of which repository originated each status:

```ruby
def all_status_checks_passed?
  return false unless head
  StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
end
``` [6](#0-5) 

`schedule_merges`/`reject_unless_mergeable!` ultimately call `merge!`, which performs a real `stack.github_api.merge_pull_request` against the victim's repository once the (forged-context) status makes the checks appear satisfied.

**Attack**: attacker is the (legitimate) author/operator of some other repository/org tracked by the same multi-tenant Shipit instance (or any repository sharing a git object with the victim's PR head, e.g. via fork). That other repository's real CI posts a `status` webhook — correctly signed with *that* org's real webhook secret — with `sha` equal to the victim `MergeRequest`'s head sha and `context` equal to the victim stack's `required_statuses` entry (public/guessable, e.g. `ci/travis`). `verify_signature` passes because the signature genuinely matches the attacker's own org's secret. `StatusHandler#process` then matches the victim's `Commit` row (same sha, different stack) and writes a passing `Status` under the victim's `stack_id`, satisfying `all_status_checks_passed?` for the victim `MergeRequest` and letting `merge!` proceed without the victim repository's actual CI ever reporting success.

Existing guards do not stop this: `verify_signature` authenticates the sender's own org, not the target of the mutation; `drop_unhandled_event` and `ExplicitParameters` only validate the JSON shape, not repository ownership; there is no `stacks`-based scoping in `StatusHandler` as there is in every sibling handler.

## Impact Explanation

A cross-tenant/cross-repository write: a status genuinely authenticated only for repository/org A ends up creating a `Status` row against a `Commit`/stack belonging to repository/org B, and that forged status can satisfy `MergeRequest#all_status_checks_passed?`, causing `Shipit` to call `stack.github_api.merge_pull_request` and merge a PR into the victim repository without the victim's real CI ever passing. This is an authentication-bypass / unauthorized-merge class issue ("payload for one repository mutating another's ... stack, commit, task", "unauthorized ... merge") and is repeatable against any stack/commit sha collision the attacker can arrange, across the whole multi-tenant install.

## Likelihood Explanation

Requires: (a) the Shipit instance tracks more than one GitHub org/repository (multi-tenant), or the attacker otherwise controls a repository that can send a genuinely GitHub-signed `status` webhook; (b) a `Commit` row with an identical sha exists under the victim's stack (naturally true for any PR opened from a fork, since the head commit object is literally shared between fork and upstream, no SHA-1 break needed); (c) the attacker knows the victim's required status context string (commonly public, e.g. `ci/travis`, `ci/circleci`). None of these require any Shipit secret, session, or privileged role — only the ability to run one's own repository's CI and know the PR's head sha, both trivially available to an unprivileged PR author.

## Recommendation

Scope `StatusHandler#process` the same way `CheckSuiteHandler` does: resolve the target stacks from `payload.dig('repository','full_name')` via the `stacks` helper, and only update commits reachable within those stacks, e.g.:

```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```

This ensures a `Status` can only be attached under the stack/repository that the webhook was actually signed for.

## Proof of Concept

Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or similar):
1. Create two stacks/repositories, `victim_stack` (org `victim-org`) and `attacker_stack` (org `attacker-org`), each with its own `github_app`/webhook secret configured in `Shipit.github`.
2. Create a `Commit` with `sha: SHARED_SHA` under `attacker_stack`, and set that same `SHARED_SHA` as the `head` of a `MergeRequest` under `victim_stack` (`merge_queue_enabled: true`, `cached_deploy_spec.required_statuses` including `ci/travis`).
3. Build a `status` webhook payload: `{ sha: SHARED_SHA, state: 'success', context: 'ci/travis', repository: { full_name: 'attacker-org/attacker-repo' } }`, signed with `attacker-org`'s real webhook secret via `GithubApp#verify_webhook_signature` (i.e. a genuinely valid signature for that org).
4. POST it to `/webhooks` with `X-Github-Event: status`.
5. Assert: `Status.where(stack_id: victim_stack.id, context: 'ci/travis').exists?` is `true` even though `victim_stack`/`victim-org` never sent this webhook — demonstrating the equality `Status.stack_id == authenticated_stack` is violated.
6. Extend: stub `victim_stack.github_api.merge_pull_request` and assert it gets called after `merge_request.reload.all_status_checks_passed?` returns `true` and `schedule_merges`/`merge!` runs, proving the merge occurs off a status never authenticated for `victim_stack`.
