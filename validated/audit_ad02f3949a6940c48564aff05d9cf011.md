## Finding: Private fixed‑denomination asset transfers skip the "final‑bad"/sequence validation that public and divisible‑asset transfers receive

### Summary

For indivisible (fixed‑denomination) private assets, `validatePaymentInputsAndOutputs` in `validation.js` takes a completely different code path for `transfer` inputs than every other asset type. Instead of independently looking up the spent output's on‑chain status, it trusts a pre‑populated `objValidationState.src_coin` object and skips the sequence/stability checks that are mandatory for every other kind of spend. [1](#0-0) 

### Finding Description

For all "normal" transfer inputs (public payments, or divisible private payments), `validatePaymentInputsAndOutputs` queries the real `units`/`outputs` tables for the source output and enforces:

- rejecting spends of an output that is stable and marked `temp-bad`/`final-bad` (i.e., the losing branch of a resolved double‑spend),
- rejecting spends of a non‑serial (`sequence !== 'good'`) unstable output unless "spend unconfirmed" rules explicitly allow inheritance of the bad sequence. [2](#0-1) 

For **private, fixed‑denomination** assets, however, the code takes an entirely different branch (comment: "we can't look up src output in the database because we validate the entire chain before saving anything"). It trusts `objValidationState.src_coin`, which is populated purely from the *client‑supplied* private‑payment chain data (`objPrevPrivateElement.output`) in `indivisible_asset.js`, and never re‑derives or checks `is_stable`/`sequence`/`main_chain_index` for the source output at all: [3](#0-2) [4](#0-3) 

The only sanity check performed on the private branch is that the *hash* of the revealed output matches the `output_hash` committed in the ancestor unit's public payload: [5](#0-4) 

That hash-binding proves the *content* (address/blinding/amount) of the output is authentic, but it proves nothing about whether the *unit that created this output* was later ruled `final-bad`/non-serial by network consensus (e.g., because it was the losing side of a double-spend). Public/divisible transfers explicitly re-check this via `src_output.sequence`/`main_chain_index` (validation.js:2456-2461, 2481-2497); the private, fixed-denomination transfer branch has no equivalent check.

This mirrors the reported bug class: a field that should only be derivable/trustable from a privileged, independently-verified source (the DB-backed sequence/stability computation that the trusted validation pipeline performs for every other spend type) is instead accepted from attacker-controlled input (`src_coin`, built from client-supplied private-element JSON) without re-validating the property the check exists to enforce.

### Impact Explanation

An attacker who authored (or came into possession of) both branches of a double-spent private, fixed-denomination coin can construct a private-payment chain that spends the branch which the network has already resolved as `final-bad`/non-serial. Because the private-asset transfer path never queries `sequence`/`is_stable`/`main_chain_index` for that source output, a node validating the chain will accept a transfer whose source coin should be dead. This is a supply/double-spend integrity issue affecting private, fixed-denomination assets: it allows spending (and thus double-spending) an output the DAG has permanently invalidated for regular payments.

### Likelihood Explanation

Reachable by any user able to send/post a private-payment chain for a fixed-denomination private asset (no special privilege required); this is exactly the flow triggered by `network.handleOnlinePrivatePayment` / `wallet.handlePrivatePaymentChains`, i.e., ordinary wallet-to-wallet private payments. Triggering the double-spend scenario requires the attacker to actually possess/control a double-spent chain (e.g., by spending the same private coin down two paths and getting one branch orphaned/`final-bad`), which is achievable by a single malicious sender without cooperation from other nodes. [6](#0-5) 

### Recommendation

For the `objAsset.is_private && objAsset.fixed_denominations` branch in `validatePaymentInputsAndOutputs` (validation.js:2415-2441), independently verify the stability/sequence status of the unit that produced `src_coin.src_output` (e.g., by querying `units` for `objPrevPrivateElement.unit`'s `sequence`/`is_stable`/`main_chain_index`) and apply the same `temp-bad`/`final-bad`/non-serial rejection and sequence-inheritance logic used in the public/divisible-asset branch, rather than trusting the client-supplied chain data unconditionally.

### Proof of Concept

1. Attacker creates a fixed-denomination private asset and issues a coin to address A.
2. Attacker crafts two conflicting transfer units spending the same private coin (classic double-spend), one to address B and one to address C, both descending from the same parent DAG state.
3. The network resolves the conflict; one branch's unit becomes stable with `sequence='final-bad'`.
4. Attacker (or colluding recipient) still possesses the full private-element chain for the `final-bad` branch (blinding, output, hash-consistent data) and sends it via `private_payment_chains`/`handlePrivatePaymentChains` to a victim node, spending it further.
5. `validatePrivatePayment` → `initPrivatePaymentValidationState` → `validatePayment` → `validatePaymentInputsAndOutputs` hits the `objAsset.is_private && objAsset.fixed_denominations` branch (validation.js:2415-2441), which never queries `sequence`/`main_chain_index` for the source unit, so the `final-bad` status is never checked, and the transfer is accepted despite spending an output the network has already invalidated.
