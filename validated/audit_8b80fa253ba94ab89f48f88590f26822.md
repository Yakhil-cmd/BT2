Confirmed: `ERC20Matcher` matches any local `AccountKey20` location to an arbitrary `H160` contract address [1](#0-0) , meaning any deployed ERC-20 contract (permissionless deployment via `pallet-revive`) can be addressed through XCM without any allow-list/registration check in the transactor itself. This confirms attacker-reachability: a user deploys a fee-on-transfer/deflationary ERC-20 contract and then uses `pallet-xcm`'s `execute`/`transfer_assets` extrinsics (which route through `AssetTransactors` including `ERC20Transactor`) to interact with it.

### Title
ERC20Transactor credits/debits the full nominal `amount` into XCM holding instead of the actual ERC20 balance delta, breaking accounting for fee-on-transfer/deflationary tokens - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` perform an ERC-20 `transfer()` call for `amount` and, provided the call returns `true` (success) and does not revert, unconditionally treat `amount` as the amount actually moved — crediting `Erc20Credit(amount)` into the XCM holding register on withdraw, and treating `amount` as fully deposited on deposit. Neither function checks `TransfersCheckingAccount`'s or the beneficiary's actual ERC-20 balance before/after the call. This is the exact bug class from the referenced report ("maintain before/after balance for fee-on-transfer tokens"), reachable here because any user can deploy an arbitrary ERC-20 contract via `pallet-revive` and have it matched by `ERC20Matcher` (any `AccountKey20` location), with no registration/allow-list gate in the transactor.

### Finding Description
- `withdraw_asset_with_surplus` (lines 150-216) calls `IERC20::transferCall{to: checking_address, value: amount}` from the user's account, then—if the call succeeds and returns `true`—constructs `AssetsInHolding::new_from_fungible_credit(what.id, Box::new(Erc20Credit(amount)))` [2](#0-1) . If the ERC-20 contract charges a transfer fee/burns a percentage/rebases, `TransfersCheckingAccount` actually receives less than `amount`, but the XCM executor's holding register is credited with the full nominal `amount`.
- `deposit_asset_with_surplus` (lines 225-306) does the mirror operation: it transfers `amount` from `TransfersCheckingAccount` to the beneficiary and, on a truthy `transfer()` return, reports success with no shortfall accounting [3](#0-2) . If the token is fee-on-transfer, the beneficiary receives less than `amount` while `TransfersCheckingAccount` is debited the full `amount`; the difference is permanently lost from `TransfersCheckingAccount`'s real balance without ever being reflected in XCM's internal bookkeeping.
- `Erc20Credit`'s own doc comment concedes this design: "This type ... does not perform runtime-level balance enforcement... actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime" [4](#0-3) . In other words, the design explicitly trusts the nominal `amount`, never the observed balance delta — precisely the flaw the report calls out for fee-on-transfer/deflationary/rebasing tokens.
- Compare this with the native `FungibleAdapter`'s `withdraw_asset`/`deposit_asset` in the same codebase, which operate on `pallet_balances`/`pallet_assets` internal ledgers where a "fee on transfer" concept cannot exist (transfers there are atomic ledger mutations, not external calls to untrusted logic) [5](#0-4) . `ERC20Transactor` is different: it delegates the actual value movement to arbitrary, attacker-deployed contract bytecode via `pallet_revive::Pallet::<T>::bare_call`, so the FRAME-side assumption "transferred == amount" no longer holds, exactly mirroring the Solidity fee-on-transfer bug class.
- `ERC20Transactor` is wired into AssetHub Westend's runtime as part of `AssetTransactors` [6](#0-5) , so it is reachable from any signed `pallet_xcm::execute`/`transfer_assets*` extrinsic that references an `AccountKey20` asset location matching a user-deployed ERC-20 contract, matched permissionlessly by `ERC20Matcher` [7](#0-6) .

### Impact Explanation
Because the XCM executor's internal holding register (and any subsequent reserve-transfer/derivative-minting logic built on top of it) trusts the nominal `amount` rather than the ERC-20 contract's actual balance delta:
1. On `withdraw_asset`, a fee-on-transfer token lets a user credit XCM holding with more value than actually reached `TransfersCheckingAccount`, silently under-collateralizing whatever escrow/backing invariant `TransfersCheckingAccount`'s real balance is supposed to represent.
2. On `deposit_asset`, `TransfersCheckingAccount` is debited the full `amount` while the beneficiary receives less, permanently leaking the fee out of the checking account with no XCM-level accounting of the loss.

This is a genuine value-accounting break rather than a purely economic/front-running issue, matching the report's Medium-severity classification: it is a bookkeeping/asset-integrity defect (accounted vs. actually-transferred mismatch), not user error, not privileged-role required, and not merely gas/griefing.

### Likelihood Explanation
Deploying a fee-on-transfer/deflationary/rebasing ERC-20 contract under `pallet-revive` requires no privilege — it's a standard permitted contract deployment. Using it through `pallet_xcm::execute`/`transfer_assets` also requires no privilege. `ERC20Matcher`'s `IsLocalAccountKey20`/`AccountKey20ToH160` match any 20-byte account location without any owner/registration allow-list, so there is no gate preventing an attacker from choosing their own malicious ERC-20 contract as the asset to transact [8](#0-7) . Likelihood is High for anyone motivated to test this path; whether it currently causes protocol-level loss depends on what other logic in AssetHub Westend actually relies on `TransfersCheckingAccount`'s balance as collateral for cross-chain representations of ERC-20 assets — I could not fully trace whether/if ERC20-backed foreign-asset minting on other chains is currently enabled/wired for this transactor within the indexed portion of the codebase, so the ultimate blast radius (mere leaked fee vs. genuine cross-chain unbacked issuance) is not fully confirmed from what's indexed.

### Recommendation
Measure the actual ERC-20 balance delta of `TransfersCheckingAccount` (in `withdraw_asset_with_surplus`) and of the beneficiary (in `deposit_asset_with_surplus`) before and after the `bare_call` to `transfer()`, and use that observed delta — not the nominal `amount` — to construct `Erc20Credit`/report success. If the observed delta is less than `amount`, either fail the operation (`FailedToTransactAsset`) or credit/report only the actual amount moved, so XCM-level accounting can never diverge from real on-chain ERC-20 balances.

### Proof of Concept
No executable Rust/FRAME integration test was run against a real boundary (no terminal access in this environment); this analysis is based on static code review of `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` and its wiring into `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`, confirming:
- The missing before/after balance check in both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`.
- Permissionless matching of arbitrary ERC-20 contracts via `ERC20Matcher`/`IsLocalAccountKey20`.
- Actual inclusion of `ERC20Transactor` in the live `AssetTransactors` tuple for AssetHub Westend.

A concrete reproduction would require: (1) deploying a minimal fee-on-transfer ERC-20 via `pallet_revive`, (2) issuing a signed `pallet_xcm::execute` with a `WithdrawAsset`/`DepositAsset` program referencing that contract's `AccountKey20` location, and (3) asserting that XCM holding/subsequent deposit amounts diverge from `TransfersCheckingAccount`'s actual on-chain ERC-20 balance change — this execution was not performed here.

pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}

	fn deposit_asset(
		mut what: AssetsInHolding,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(), (AssetsInHolding, XcmError)> {
		tracing::trace!(
			target: "xcm::fungible_adapter",
			?what, ?who,
			"deposit_asset",
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungible(&asset).map(|amount| (asset.id, amount)));
		let Some((asset_id, amount)) = maybe else {
			return Err((what, MatchError::AssetNotHandled.into()));
		};
		let Some(who) = AccountIdConverter::convert_location(who) else {
			return Err((what, MatchError::AccountIdConversionFailed.into()));
		};
		let Some(imbalance) = what.fungible.remove(&asset_id) else {
			return Err((what, MatchError::AssetNotHandled.into()));
		};
		// "manually" build the concrete credit and move the imbalance there.
		let mut credit = fungible::Credit::<AccountId, Fungible>::zero();
		credit.saturating_subsume(imbalance);
		Fungible::resolve(&who, credit).map_err(|unspent| {
			tracing::debug!(target: "xcm::fungible_adapter", ?asset_id, ?who, ?amount, "Failed to deposit asset");
			(
				AssetsInHolding::new_from_fungible_credit(asset_id, Box::new(unspent)),
				XcmError::FailedToTransactAsset("")
			)
		})?;
		Ok(())
	}

	fn withdraw_asset(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> result::Result<AssetsInHolding, XcmError> {
		tracing::trace!(
			target: "xcm::fungible_adapter",
			?what, ?who,
			"withdraw_asset",
		);
		let amount = Matcher::matches_fungible(what).ok_or(MatchError::AssetNotHandled)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		let credit = Fungible::withdraw(&who, amount, Exact, Expendable, Polite).map_err(|error| {
			tracing::debug!(target: "xcm::fungibles_adapter", ?error, ?who, ?amount, "Failed to withdraw asset");
			XcmError::FailedToTransactAsset(error.into())
		})?;
		Ok(AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(credit)))
	}
