### Title
Double-counting of Bitcoin-locked sats via replayed L1 lockup outpoints in `register-for-bond` - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`verify-l1-lockups` / `validate-l1-lockup` in `pox-5.clar` compute the sats a staker is credited with by verifying Bitcoin lockup outputs (SPV header + Merkle proof) and de-duplicating outpoints only **within the single call's own list**. There is no persisted, cross-call registry of already-consumed `(txid, output-index)` outpoints, so the same on-chain lockup output can be resubmitted in a later call to be credited again.

### Finding Description
`validate-l1-lockup` [1](#0-0)  checks that an outpoint hasn't already appeared in the *current* fold accumulator via `seen-outpoints` (`asserts! (is-none (index-of? seen-outpoints outpoint)) ERR_DUPLICATE_LOCKUP_OUTPOINT`), then adds the amount to `sum`. This accumulator (`seen-outpoints`, capped at `(list 10 ...)`) is freshly initialized to `(list)` on every call to `verify-l1-lockups` [2](#0-1) , and is never checked against, or written into, any contract-level persistent map that would remember outpoints consumed by *previous* calls (no `used-outpoints`/`consumed-lockup` map exists anywhere in `pox-5.clar` per the exhaustive search of lockup/outpoint identifiers in the contract).

Because the only replay protection is the ephemeral per-call list, a staker can call the bond/lockup-registration path (`register-for-bond`/rollover flow that consumes `verify-l1-lockups`'s `sum`) multiple times — e.g. for a second bond-index, or after a rollover to a new bond — presenting the *same* Bitcoin transaction output (same `txid`/`output-index`) that funded the first registration, and have it validated and summed again since the SPV/Merkle checks (`verify-block-header`, `parse-block-header`, Merkle-proof verification) only prove the output *exists on Bitcoin*, not that it hasn't already been claimed.

This mirrors the PHAR bug class: a locally-scoped bounds/uniqueness check (`buffer[tmp_len]`/`seen-outpoints`) that is valid for the immediate operation but omits the broader invariant (staying inside the true buffer / staying unique across the whole system), letting an attacker exploit the gap between "checked within this call" and "checked globally."

### Impact Explanation
Sats credited from an L1 Bitcoin lockup back the staker's stake weight/signing weight and reward eligibility inside pox-5. If the same BTC-locked output can be counted toward multiple registrations, the staker obtains reward-eligible/signing weight that exceeds the actual BTC value locked on Bitcoin — a double-counting of a commitment that was never actually re-locked, directly breaking the equality "sats credited == sats currently locked once on L1." This falls under Critical ("double-counting a commitment or reward") per the rules.

### Likelihood Explanation
Reachable by any unprivileged staker who already possesses one valid L1 lockup proof (a normal artifact of the intended flow) and simply resubmits the identical outpoint payload to a second `register-for-bond`-style call. No admin, miner, or third-party key is required — the exploit only needs the attacker's own previously-submitted proof data, replayed.

### Recommendation
Persist consumed L1 outpoints in a durable Clarity map (e.g. `used-l1-outpoints { txid, output-index } -> bool`), and have `validate-l1-lockup` check and set this map (not just the transient `seen-outpoints` fold accumulator) so an outpoint can only ever be credited once across the contract's entire lifetime, not just once per call.

### Proof of Concept
1. Staker locks BTC via the timelock script and obtains a valid Merkle/SPV proof for output `(txid=T, index=0)`.
2. Staker calls the bond registration path once, `verify-l1-lockups` validates `T:0` and credits `sum = amount`.
3. Staker calls the bond registration path again (e.g., a second bond, or after an unstake/rollover creating a new bond-index) submitting the identical lockup `{ tx, output-index: 0, header, leaf-hashes, ... }` for `T:0`.
4. `validate-l1-lockup`'s only duplicate check (`seen-outpoints`) is reinitialized to empty for this new call, so `T:0` passes and is credited again, doubling the staker's recognized sats without any new BTC being locked.

**Note:** I was unable to fully rule out the existence of a persisted outpoint-tracking map outside `pox-5.clar` (e.g., a companion Rust-side ledger) within the available search iterations; the grep coverage was limited to identifiers like `used-outpoints`/`processed-outpoint`/`outpoint-used` and did not exhaustively review every map defined in `pox-5.clar`. If such a persistent registry exists elsewhere, this finding would not hold — a follow-up review of all `define-map` declarations in `pox-5.clar` and their write-sites for `register-for-bond` is recommended to confirm.
