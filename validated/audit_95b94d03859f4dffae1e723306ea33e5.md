### Title
Regular Expression Denial of Service (ReDoS) in `isValidEmail` reachable via textcoin recipient address in `sendMultiPayment` - (File: validation_utils.js)

### Summary
`validation_utils.js` exposes `isValidEmail()`, which is used to decide whether a payment recipient string should be treated as a textcoin email recipient in `wallet.js`'s `sendMultiPayment` flow, and also in `uri.js`'s `parseUri` for validating a pasted/scanned payment-request URI address. The regex used for email validation contains a classic ReDoS-prone construct with nested unbounded quantifiers, allowing catastrophic backtracking on crafted, non-matching input.

### Finding Description
`isValidEmail` is implemented as: [1](#0-0) 

The domain-matching alternative contains `(([a-zA-Z\-0-9]+\.)+[a-zA-Z]{2,})$` — an outer `+` wrapped around a group that itself contains an inner `+` over the same/overlapping character class, terminated only by a required trailing dot inside the group and a final anchor. This is the textbook ReDoS pattern (`(X+\.)+` style ambiguity): for an input that is a long run of characters matching `[a-zA-Z\-0-9]` with no terminating dot/valid TLD (e.g., many repeated letters followed by a character that fails the final match), the regex engine must try an exponential number of ways to partition the run into `(X+\.)` groups before concluding there is no match. This mirrors the reported `csv-parse` `__isInt()` issue in bug class: a "malformed" regex processing crafted input pathologically slowly, but here in ocore's own email validator rather than in a dependency.

`isValidEmail` is called from wallet payment composition when a payment output address is not a valid Obyte address, to decide whether to treat it as a "textcoin" email recipient: [2](#0-1) 

It is also invoked in URI parsing for wallet payment-request links: [3](#0-2) 

In both call sites, `isValidAddress` (a fast, fixed 32-char check) is tried first and fails quickly for non-address strings, after which `isValidEmail` is called on the same attacker/user-controlled string with no length limit before the vulnerable regex runs.

### Impact Explanation
This is a wallet-side denial-of-service: an attacker who can get a victim's wallet to evaluate a crafted "address" string as a payment output (e.g., by supplying a malicious recipient string through automated payment tooling, a bot, or a specially crafted payment-request URI/link handed to the user) can force the Node.js event loop to hang for a very long time while evaluating the vulnerable regex, since `isValidEmail`/`parseUri` execute synchronously on the main thread. This can freeze the wallet application and block it from processing legitimate payments, confirmations, or device messages while the regex evaluation is stuck, satisfying the "node unable to confirm/serve" criterion for wallets that are also full nodes or that block their I/O loop during this call. There is no funds-loss or consensus-divergence impact — this is confined to availability of the local wallet process.

### Likelihood Explanation
Reachability is user/wallet-side rather than from an unprivileged unit poster, AA trigger, or asset issuer directly into node validation logic; it requires the address string to reach `isValidEmail` through the wallet's own payment-composition code (`sendMultiPayment`) or URI-parsing code (`parseUri`), both of which are typically invoked with locally supplied or user-pasted strings, not with data taken from the DAG. This lowers the likelihood significantly compared to a validation.js/AA-trigger-reachable bug, since it depends on the wallet software route accepting attacker-influenced recipient text (e.g. programmatic integrations feeding external addresses, or a malicious URI shared with a user) rather than any consensus-critical or trustlessly-reachable path.

### Recommendation
Replace the vulnerable domain regex with a non-backtracking, length-bounded equivalent (e.g., split on `.` and validate each label with a simple character-class check and length limit, or use an atomic/possessive-quantifier equivalent), and/or impose a hard maximum length check (e.g., reject strings longer than typical email length, such as 254 characters) on the input to `isValidEmail` before running the regex, in `validation_utils.js`.

### Proof of Concept
Calling the exported function directly demonstrates the hang:
```js
const ValidationUtils = require('./validation_utils.js');
const payload = 'a'.repeat(50) + '!'; // many chars, no valid TLD/dot ending
console.time('email');
ValidationUtils.isValidEmail(payload); // takes exponentially longer as length grows
console.timeEnd('email');
```
Increasing the repeat count (e.g., from 30 to 40 to 50 `a`'s) shows execution time roughly doubling per additional character, confirming exponential/catastrophic backtracking rather than linear-time evaluation, and this same string can be delivered as a `to_address` argument to `wallet.js`'s payment composition path [4](#0-3)  or as the address portion of a URI passed to `uri.js`'s `parseUri` [3](#0-2) .
