### Title
Webhook signature verification keys off `repository.owner.login`, but every handler acts on the independently-attacker-controlled `repository.full_name` — allowing an attacker with one organization's webhook secret to trigger actions on any other organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
When Shipit is configured with multiple GitHub Apps (one per organization, per `docs/setup.md`'s "Using Multiple Github Applications" section), `WebhooksController#verify_signature` selects which per-organization `webhook_secret` to validate the HMAC against using `repository_owner`, derived from the attacker-supplied JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Every webhook `Handler` (push, status, check_suite, pull_request, membership) instead resolves the target `Stack`/`Repository`/`Team` using a *different* field of the same attacker-supplied body: `payload.dig('repository', 'full_name')` (via `Repository.from_github_repo_name`) or `payload.dig('organization','login')`/`team` for membership events. Because these are two independent JSON fields inside the same signed byte-string, an attacker who legitimately controls one organization's webhook secret (i.e., is an admin/installer of a Shipit-connected GitHub App for "org-A") can craft a payload where `repository.owner.login` = `"org-A"` (so the correct, known secret is selected and the HMAC passes) while `repository.full_name` = `"org-B/victim-repo"` (an entirely different organization's repository that the attacker has no access to). The signature check only binds the *organization that authenticates*, not the *repository that is written to*.

### Finding Description [1](#0-0) 

`verify_signature` computes `repository_owner` purely from the JSON body and uses it to pick the `GitHubApp`/secret: [2](#0-1) 

`Shipit.github(organization:)` looks up a distinct secret per organization when the multi-org config schema is used (as documented and tested): [3](#0-2) [4](#0-3) [5](#0-4) 

`verify_webhook_signature` is a plain HMAC-SHA1 check over the raw JSON bytes using the secret selected above — it says nothing about which repository/org the payload's *content* actually targets: [6](#0-5) 

Every handler ignores `repository.owner.login` entirely and instead resolves the target stacks/team from a separate field, `repository.full_name` (owner+name) or `organization.login`: [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) 

Because `repository.owner.login` (used for signature-key selection) and `repository.full_name` (used for target resolution) are two independent, attacker-controlled JSON fields inside the same signed body, an attacker who legitimately knows one organization's `webhook_secret` can sign a payload with `repository.owner.login` set to their own org, while setting `repository.full_name` to any other organization's repository registered in Shipit. The `verify_signature` step only proves "this byte-string was signed by someone who knows org-A's secret" — it does not prove any relationship between org-A and the repository named inside the payload for the purpose of dispatching the push/status/check_suite handler.

**Binding broken:** `organization that authenticated == repository that is written` — before the attack this holds (GitHub itself only ever sends payloads where these two fields are consistent, since it computes the signature using the actual installation/org secret over its own generated payload); after the attacker's forged request, `repository.owner.login` (org-A, correctly authenticated) ≠ `repository.full_name`'s owner (org-B, unauthenticated, victim).

### Impact Explanation
This crosses the "cross-repository writes / unauthorized deploy" bar defined in the rules. Concretely:
- Via `PushHandler`, an attacker can force any `Stack` under `org-B/victim-repo` matching a chosen branch to call `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen `after` SHA — triggering a GitHub sync against a repository the attacker doesn't control, and, if continuous deployment/merge queue behavior is enabled, potentially triggering downstream deploy/merge activity for a commit the attacker names, without ever having write access to `org-B`.
- Via `CheckSuiteHandler`/`StatusHandler`, an attacker can fabricate check-run/status refresh events for arbitrary commits on stacks belonging to a victim organization, corrupting the CI/merge-queue state used to gate deploys.
- Via the `membership`/`pull_request` handlers, similarly-scoped cross-organization spoofing of team membership or PR label/close/open events is possible.

The severity is bounded by what a legitimate webhook of that type is allowed to do to an arbitrary stack (which is already significant: it can influence sync/merge-queue/CI status that ultimately gates automatic deploys), but it does not itself grant RCE or direct GITHUB_TOKEN exfiltration, so I frame this as a cross-organization/cross-repository write and unauthorized-action vector rather than full RCE.

### Likelihood Explanation
This requires the deployment to be configured with the multi-organization GitHub App schema (`docs/setup.md`, "Using Multiple Github Applications") and requires the attacker to be a legitimate administrator/owner of at least one of the organizations connected to that Shipit instance (i.e., they know that org's `webhook_secret` because they configured/received it, or because Shipit's own webhook secret for their org is exposed to them as an app installer). This is a real "insider-across-tenants" threat model that the multi-org feature explicitly targets (multiple, mutually distrusting organizations sharing one Shipit instance), making the likelihood credible for any multi-tenant Shipit deployment — the exact scenario the feature was built for.

### Recommendation
`WebhooksController#verify_signature` (or the handlers) should also assert that the organization whose secret validated the signature matches the owner of the `repository`/`organization` object that the handler is about to act on, e.g. compare `repository_owner` against the resolved `Repository#owner` (or reject if the two differ) before invoking any handler, rather than trusting `repository.full_name`/`organization.login` unconditionally once signature verification succeeds for *some* organization.

### Proof of Concept
1. Configure Shipit with the multi-org schema, e.g. `org-A` and `org-B`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker is an installer/admin of the Shipit GitHub App for `org-A` and thus knows `org-A`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "org-A" }, "full_name": "org-B/victim-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-A secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` reads `repository_owner` = `"org-A"`, fetches `Shipit.github(organization: "org-A")`, and the HMAC check passes because the attacker legitimately knows that secret. [11](#0-10) 
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("org-B/victim-repo")`, entirely bypassing any check that `org-A` (the authenticated party) is related to `org-B` (the acted-upon repository), and calls `stack.sync_github(expected_head_sha: <attacker sha>)` on `org-B`'s stack.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
