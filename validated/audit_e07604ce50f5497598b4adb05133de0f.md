### Title
`push` webhook signature is authenticated against `repository.owner.login` while stack/repo lookup keys off `repository.full_name`, letting a no-secret org's payload sync an unrelated victim repository's stacks - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/push_handler.rb)

### Summary
`WebhooksController#verify_signature` resolves the `GitHubApp` (and thus the HMAC secret) using only `repository.owner.login` from the request body, and `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that org's configured `webhook_secret` is blank. Because `PushHandler` locates the target stacks from a completely different field, `repository.full_name`, an attacker who forges a payload with `owner.login` pointing at a no-secret-configured org can put an arbitrary victim repository's `full_name` in the same payload and drive `sync_github` against that victim's stacks.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`organization_that_authenticated_the_request (params.dig('repository','owner','login'))` should equal `organization_that_owns_the_mutated_stack (Repository.from_github_repo_name(params.dig('repository','full_name')).owner)`.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` (or `organization.login`) and calls `Shipit.github(organization: repository_owner)` to fetch the `GitHubApp` config for that org: [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `@webhook_secret` is blank for that org: [3](#0-2) 
- Once verification passes, `WebhooksController#create` dispatches the raw parsed JSON body to `Shipit::Webhooks.for_event(event)` handlers, with no further check tying the authenticated org back to the payload's repository: [4](#0-3) 
- `PushHandler#process` resolves stacks via the base `Handler#stacks`, which uses `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository', 'full_name')` — a completely different field than the one used for signature verification: [5](#0-4) [6](#0-5) 

Nothing in this chain requires `repository.owner.login` (used for authentication) to be consistent with the owner implied by `repository.full_name` (used for the actual DB write target). GitHub itself would always send consistent values, but the attacker forges the entire JSON body directly, so this coupling is not enforced server-side. Existing guards do not close the gap: `drop_unhandled_event` only checks the event type is handled at all [7](#0-6) , `ExplicitParameters` in `PushHandler` only requires `ref` and `after` to be present/typed, not that `full_name`'s owner matches the authenticating org [8](#0-7) , and the `GithubOrganizationUnknown` rescue only fires when the org name in `owner.login` is entirely absent from config, not when it is present but has a blank secret [9](#0-8) .

Exploit flow: attacker sends `POST /webhooks` with `X-Github-Event: push`, body `{"repository": {"owner": {"login": "no-secret-org"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/<victim-branch>", "after": "<attacker-chosen-sha>"}`. Because `no-secret-org` is a configured Shipit org with `webhook_secret` blank, `verify_webhook_signature` returns `true` with zero HMAC checked. `PushHandler` then finds `victim-org/victim-repo`'s non-archived stacks on the given branch and calls `stack.sync_github(expected_head_sha: params.after)`, which triggers a GitHub sync/refresh cycle for that victim stack — appending commits and re-evaluating deploy state (`blocked?`, driven by `blocking_statuses`) for a repository the attacker never authenticated against.

### Impact Explanation
The attacker causes state mutation (a GitHub sync, commit ingestion, and CI/status-driven `blocked?` re-evaluation) on a stack belonging to a repository/org that did not authenticate the request — this is exactly the "one repo's payload writes another repo's records" cross-tenant category called out as Critical. Repeatable against any victim repository whose `full_name` the attacker knows, as long as any Shipit-configured org exists with a blank `webhook_secret`. Combined with `blocking_statuses`, forcing a resync can shift `blocked?` state and affect deploy gating for the victim stack, amplifying blast radius beyond simple commit ingestion into continuous-delivery control flow.

### Likelihood Explanation
Requires: (1) at least one org configured in Shipit's `secrets.github` multi-org config without a `webhook_secret` set (a plausible misconfiguration, not a Shipit default), and (2) knowledge of the victim repository's `full_name` and target branch, both of which are public/discoverable information for any repo the attacker can see on GitHub. No Shipit credentials, session, or API token are needed — only the ability to send an HTTP POST to `/webhooks`. This is low-cost and fully repeatable.

### Recommendation
Bind webhook authentication to the same repository identity used for the mutation: derive the org used to look up the `GitHubApp` config from `repository.full_name` (or verify `repository.owner.login` matches the owner segment of `repository.full_name`) before dispatching to handlers. Additionally, treat a present-but-secretless org config as a hard misconfiguration (fail closed / require `webhook_secret`) rather than silently returning `true` from `verify_webhook_signature`.

### Proof of Concept
Minitest plan (no live GitHub) under `test/controllers/webhooks_controller_test.rb`:
1. Configure two orgs in `Shipit.secrets.github` (or stub `Shipit.github_app_config`): `"no-secret-org"` with `webhook_secret: nil`, and `"victim-org"` unrelated.
2. Create `shipit_stacks(:shipit)` or a fixture stack belonging to repository `victim-org/victim-repo` with `blocking_statuses` configured (e.g. via `DeploySpec` fixture) and record its current `stack.blocked?` / `updated_at` / commit count.
3. POST to `/webhooks` with `X-Github-Event: push`, no `X-Hub-Signature` header, body:
   `{"repository": {"owner": {"login": "no-secret-org"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/<victim-branch>", "after": "<forged-sha>"}`.
4. Assert `response.status == 200` (verification passed with no secret).
5. Assert `GithubSyncJob` was enqueued with `stack_id: victim_stack.id, expected_head_sha: "<forged-sha>"` — proving the payload authenticated under `no-secret-org` mutated `victim-org/victim-repo`'s stack.
6. Assert the binding: `payload_owner_login ("no-secret-org") != victim_stack.repository.owner ("victim-org")` while the sync job still targeted `victim_stack.id`, demonstrating the authenticated identity and the mutated identity diverge.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
