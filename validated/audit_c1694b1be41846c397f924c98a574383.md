### Title
Cross-organization webhook forgery: signature verified against payload's `organization`/`repository.owner` while handlers act on the unrelated `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a delivery against using the organization derived from the *attacker-controlled JSON body* (`repository.owner.login` or `organization.login`), not from any independently-trusted routing key. Every downstream `Handler` then re-reads the body and resolves the target `Repository`/`Stack` using a **different** field of the same body, `repository.full_name`. Because the HMAC only proves "this body was signed with Org X's secret," and nothing ties `repository.owner.login`/`organization.login` to `repository.full_name`, a party who legitimately holds Org X's webhook secret (e.g., because they administer Org X, one of possibly several organizations configured on a shared Shipit instance) can forge a webhook that verifies as "from Org X" while its `repository.full_name` points at Org Y's repository, causing Shipit to act on Org Y's stacks without ever having Org Y's secret.

### Finding Description
`verify_signature` computes the app/secret lookup key like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

`repository_owner` is taken straight from the untrusted payload: [2](#0-1) 

The signature only proves the raw bytes were HMAC-signed with `github_app.webhook_secret` — a secret that is **per-organization** on multi-tenant installs, as documented and fixtured (`OrgOne`/`OrgTwo` each with their own `webhook_secret`, `app_id`, `private_key`): [3](#0-2) , [4](#0-3) , and the per-org secret is stored on `GithubApp#@webhook_secret`: [5](#0-4) , [6](#0-5) .

After `verify_signature` passes, `create` re-parses the same raw body and dispatches it to handlers: [7](#0-6) . Every handler's base class resolves the affected `Stack`s using a *different* payload field, `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login`: [8](#0-7) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Same pattern for pull-request driven review-stack creation: [9](#0-8)  resolves `repository` purely from `params.repository.full_name`, and for team/membership management: [10](#0-9)  binds a `Team` to `params.organization.login` — again taken from the same forgeable body, with the HMAC only proving *an* org's secret was used, not *that* org's identity relative to the acted-upon fields.

**Broken binding:** `organization authenticated (via HMAC keyed on repository_owner) == organization whose repository/stack is written (repository.full_name / organization.login used by handlers)`. Nothing in the code enforces this equality; the two fields are read independently from the same untrusted JSON and only one of them (`repository_owner`) is used to pick the verification key.

### Impact Explanation
On any Shipit deployment that configures more than one GitHub organization (a supported, documented configuration — see `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`'s per-app `github:` block), a party who is a legitimate administrator of Organization A's GitHub App (and thus knows Org A's `webhook_secret`, which is not the app's global `GITHUB_TOKEN`/private key but is still a credential scoped to Org A only) can sign a payload with Org A's secret while setting `repository.full_name` (or `organization.login` for `membership` events) to point at Organization B. This is a genuine cross-organization boundary violation: the entity that authenticates (Org A) differs from the entity that gets written (Org B). Consequences include:
- Forged `pull_request`/`push` events causing Shipit to auto-create review stacks and drive deploy pipelines for Org B's repositories (`ReviewStackAdapter.find_or_create!`), i.e., unauthorized deploy actions against a repository the attacker was never authorized to touch.
- Forged `membership` events creating/modifying `Team` records keyed by `organization.login` = Org B, which feeds directly into `Shipit.github_teams` authorization checks used by `User#authorized?`, letting an Org A administrator manipulate Org B's access-control team membership data.

This matches the "escalation into `Shipit.github_teams` authorization" / "unauthorized deploy" impact classes.

### Likelihood Explanation
Exploitation requires the instance to be configured with multiple GitHub organizations sharing one Shipit deployment (an explicitly supported and documented topology) and requires the attacker to control/administer at least one of those organizations' GitHub Apps — a normal, unprivileged-relative-to-other-tenants position, not a Shipit session, API token, or the app's own private key. No cryptographic break is needed; the flaw is purely in which payload field is trusted for authorization versus which is trusted for the write target.

### Recommendation
After `verify_signature` succeeds, re-derive the same organization identifier that was used to select the signing key (`repository_owner`) and assert it matches the organization implied by every field the handlers subsequently use (`repository.full_name`'s owner segment, `organization.login`, etc.) before dispatching to handlers. Reject the delivery if they diverge. Alternatively, route/verify per-repository rather than per-organization-derived-from-body, or bind the verification key to the `Repository`/`Stack` record already known to Shipit rather than to organization data supplied in the same untrusted payload it is meant to authenticate.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an administrator of `OrgA`'s GitHub App (attacker), craft a `pull_request` (`opened`) webhook JSON body with:
   - `repository.owner.login = "OrgA"` (or omit `repository` and set `organization.login = "OrgA"`)
   - `repository.full_name = "OrgB/target-repo"`
3. Sign the raw body with `OrgA`'s `webhook_secret` using the same HMAC-SHA1 scheme as `Hook::DeliverySigner`/`GithubApp#verify_webhook_signature`, and send it to `POST /github/webhooks` with header `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature against `OrgA`'s secret.
5. `Webhooks::Handlers::PullRequest::OpenedHandler` resolves `repository` via `Shipit::Repository.from_github_repo_name("OrgB/target-repo")` and invokes `ReviewStackAdapter.find_or_create!` on `OrgB`'s stacks, creating/driving a review stack for `OrgB`'s repository despite the attacker never possessing any `OrgB` credential.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
