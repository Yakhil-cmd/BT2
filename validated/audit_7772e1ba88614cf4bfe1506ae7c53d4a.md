### Title
Webhook signature is verified against the wrong field, letting one onboarded GitHub organization write status/sync events onto other organizations' stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The NFTX report is about a mutable trust anchor (`nftxVaultFactory`) being swappable without migrating the state that other contracts implicitly trust it to own. The Shipit analog is `WebhooksController#verify_signature`, which selects *which* organization's webhook secret to validate a payload against using one field, while the handlers that actually mutate state key off a *different, unverified* field from the same payload. The binding "organization authenticated == repository written" is broken.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to pick the `GitHubApp`/`webhook_secret` purely from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). `Shipit.github(organization: repository_owner)` then looks up that org's config in `secrets.github` via `github_app_config`, and the HMAC signature is checked against that org's `webhook_secret`: [3](#0-2) 

Once the signature check passes for `repository_owner`, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the **entire raw payload** to handlers, which never re-derive or cross-check the organization/repository against the one used for signature verification: [4](#0-3) 

- `Handler#stacks` resolves the target stack from `payload.dig('repository', 'full_name')` — a *different* JSON path than the one used for signature selection (`repository.owner.login`) — and this value is never checked for consistency with `repository_owner`: [5](#0-4) 

- `StatusHandler#process` doesn't even use `repository_name`/`stacks` at all. It writes a status onto **any** commit in the entire installation matching `params.sha`, with no repository binding whatsoever: [6](#0-5) 

- `PushHandler#process` resolves stacks via `Repository.from_github_repo_name(repository_name)` (again from `repository.full_name`) and triggers `stack.sync_github`: [7](#0-6) 

In Shipit's multi-organization mode, `secrets.github` can hold a distinct `webhook_secret` per organization key, each corresponding to a separately-installed GitHub App pointed at the same shared `/webhooks` endpoint: [8](#0-7) 

Because the signature check only binds to `repository.owner.login` (used purely to pick a secret) and never to `repository.full_name` (used by handlers to select which stack/commit to mutate), an attacker who legitimately controls one onboarded organization's webhook secret (they configured it themselves when installing their own GitHub App against the shared Shipit instance) can forge a payload where `repository.owner.login` = their own org (so the signature validates with their own known secret) but `repository.full_name` (and/or `sha`) refer to a **different, victim organization's** repository/stack tracked by the same Shipit instance.

### Impact Explanation
This breaks the binding "organization authenticated == repository/stack written," matching the "Critical: cross-repository writes / unauthorized deploy" severity bucket:
- Via `status` events, the attacker can post arbitrary CI `state`/`context`/`description` (e.g., `success`) onto any commit sha across any stack in the instance, without any per-repository scoping, potentially satisfying `ci.require` and enabling deploys that should have been blocked.
- Via `push` events, the attacker can force `GithubSyncJob`/`sync_github` against arbitrary victim stacks belonging to other onboarded organizations, which is only bounded to be "reachable," not "owned," by the authenticating org.

This requires no privileged Shipit account, no `ApiClient` token, and no access to the victim organization's actual GitHub App/webhook secret — only knowledge of the attacker's own legitimately-configured organization webhook secret, which fits the "unprivileged attacker" framing of the analog.

### Likelihood Explanation
This is only exploitable when a single Shipit instance onboards multiple GitHub organizations under `secrets.github` with per-org `webhook_secret`s (the multi-tenant `github_organizations`/`github_app_config` path). In that configuration, likelihood is high: the attack requires only crafting a raw HTTP POST to the shared `/webhooks` endpoint with a mismatched `repository.owner.login` vs `repository.full_name`/`sha`, signed with a secret the attacker legitimately possesses for their own organization. In the default single-org schema (`github_default_organization.nil?`), the impact collapses to "one trusted org can write into other stacks within the same org" since there's only one webhook secret — still a break of the intended per-repository isolation, but less severe cross-tenant impact.

### Recommendation
Bind signature verification and payload processing to the same value:
- After signature verification succeeds for `repository_owner`, re-derive and enforce that `payload.dig('repository', 'full_name')`'s owner matches `repository_owner` before dispatching to handlers.
- In `Handler#stacks` and `StatusHandler#process`, explicitly verify that the resolved `Repository`/`Stack`/`Commit` belongs to the organization that was authenticated for this request, rejecting the event (204/422) otherwise.
- Consider passing the authenticated organization down to handlers explicitly (rather than re-deriving it independently from untrusted payload fields), so there's a single source of truth for "which org signed this."

### Proof of Concept
1. Shipit instance is configured with two onboarded orgs, `attacker-org` and `victim-org`, each with their own GitHub App and `webhook_secret` under `secrets.github`.
2. Attacker knows `attacker-org`'s webhook secret (they configured it in their own GitHub App settings pointing at the shared `/webhooks` endpoint).
3. Attacker crafts a `status` event payload:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "<victim-org commit sha tracked by Shipit>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s webhook secret and posts to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` computes `repository_owner = "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the HMAC check passes.
6. `StatusHandler#process` runs unconditionally against `Commit.where(sha: params.sha)`, writing a fabricated `success` status onto the victim commit — with no check that the commit belongs to `attacker-org`.

Note: I was unable to fully confirm from the indexed code alone what triggers automatic deploys on a "success" status being posted (e.g., `continuous_deployment`/merge-queue logic) — the `Stack#sync_github`/`ContinuousDeliveryJob` interaction would need to be traced further in a full checkout to confirm the exact downstream "unauthorized deploy" chain end-to-end.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",

      ].join(' '))
    end

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
