### Title
Stale `Account.owner` lets the previous NFT holder keep owner/delegate authority after `position-nft::transfer` - (File: contracts/controller/src/account.rs)

### Summary
Every value-moving entrypoint on an existing account (`withdraw`, `borrow`, `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`, `flash_position`, and the `SeizeMode::Credit` receiver check in `liquidate`) gates on `require_owner_or_delegate(env, account_id, caller, &account.owner)`, which compares the caller against `Account.owner` — the owner address snapshotted into the `Account` struct at creation time in `create_account` [1](#0-0) . Account ownership, however, actually lives in the position NFT: `require_account_owner` resolves the *live* owner through `storage::account_owner` (the NFT `owner_of` lookup), not through `account.owner` [2](#0-1) . Because the controller is never notified on `position-nft::transfer`, the stored `Account.owner` is never rewritten, so `require_owner_or_delegate` checks a stale principal instead of the authority of record.

### Finding Description
The bug class from the report — an operation proceeding because the permission check validates the wrong authentication context — maps directly onto the controller's dual notions of ownership:

- `create_account` writes `Account { owner: owner.clone(), .. }` once at mint [3](#0-2) .
- `require_owner_or_delegate` and `is_owner_or_delegate` trust that stored `owner` field, including as the key under which `storage::get_delegates(env, account_id, owner)` is looked up [4](#0-3) .
- The genuinely authoritative check `require_account_owner` ignores `account.owner` and queries `storage::account_owner(env, account_id)` — the NFT owner — confirming the NFT is the source of truth [2](#0-1) .
- `position-nft` `transfer`/`transfer_from` are stock OpenZeppelin entrypoints; nothing calls back into the controller to rewrite `Account.owner` (per the project's own auth table, NFT transfer "moves … control of a whole lending account" and old-owner delegates "go inactive") [5](#0-4) .

Attack path for a single unprivileged address:

1. Alice owns `account_id = A` holding collateral and calls `position-nft::transfer(from=alice, to=bob, token_id=A)` — e.g. an OTC account sale, or Bob phishes an `approve`/`transfer_from`.
2. `Account.owner` still equals `alice`. Bob's `add_delegate`/`renew_account` work (they use `require_account_owner`), but every value-moving path uses `require_owner_or_delegate`.
3. Alice calls `controller::withdraw(caller=alice, account_id=A, withdrawals=[(collateral_asset, 0 /* withdraw-all sentinel */)], to=Some(alice))`. `caller.require_auth()` passes (she signs), `require_owner_or_delegate` passes against the stale `account.owner == alice`, `require_external_recipient` only rejects protocol contracts, and the withdraw-all sentinel pays out her entire former collateral [6](#0-5) .
4. Equivalently Alice (or a still-listed delegate of Alice, since the delegate map is keyed under the stale `owner`) calls `borrow(caller=alice, account_id=A, borrows=[...], to=alice)` and draws debt proceeds to herself, stranding Bob with an insolvent account. The same stale-owner path admits `multiply`, `swap_collateral`, `repay_debt_with_collateral`, and naming account `A` as a `SeizeMode::Credit` receiver in `liquidate` [7](#0-6) .

The only post-conditions are `enforce_post_pool_solvency`, which the ex-owner satisfies by withdrawing only up to solvency or by borrowing within the LTV of collateral she no longer owns.

Caveat on verification: this finding depends on `storage::get_account` returning the stored `Account.owner` verbatim rather than re-resolving it through the NFT on every load. I was unable to read `contracts/controller/src/storage/account.rs` within the iteration limit, so the staleness of the returned `owner` field is inferred from (a) `require_account_owner` deliberately using a separate live `storage::account_owner` lookup, and (b) the documented invariant that NFT transfer is what moves account control and deactivates prior delegates. If `get_account` re-stamps `owner` from the NFT, the inconsistency — and the finding — disappears.

### Impact Explanation
Theft of user funds: the seller/prior holder of a lending-account NFT (or a phishing-driven `transfer_from`) can withdraw all collateral to an arbitrary `to` address, or borrow against it and keep the proceeds, after ownership has already moved. Every secondary-market account transfer is at risk for the full collateral value plus borrowable capacity, and the new owner cannot prevent it — `remove_delegate` only clears delegate entries keyed under their own (new) owner key, not the stale ones.

### Likelihood Explanation
High under the staleness assumption: `position-nft::transfer` is a standard, permissionless-by-owner entrypoint explicitly listed as in-scope, requires no governance action, and the exploit needs only the ex-owner's signature on one `withdraw`/`borrow` call. Likelihood is bounded only by how often accounts change hands and by the unverified `get_account` behavior noted above.

### Recommendation
Make the NFT the single source of truth on every value-moving path: either resolve `owner` inside `storage::get_account` via `storage::account_owner`/`nft owner_of` (and key delegate storage under that live owner), or replace `require_owner_or_delegate`'s `account.owner` argument with the live NFT owner. Remove the duplicated `owner` field from `Account`, and add a regression test that transfers the NFT then asserts the prior owner fails `withdraw`, `borrow`, `multiply`, and `SeizeMode::Credit` receiver checks while the new owner succeeds.

pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}

/// Requires the owner or a registered, active manager delegated by that owner.
pub(crate) fn require_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) {
    if is_owner_or_delegate(env, account_id, caller, owner) {
        return;
    }
    panic_with_error!(env, GenericError::NotAuthorized);
}

position-nft::burn | caller-auth | INV-STOR-03, INV-STOR-01 | Any address may invoke, but require_auth on the construction-time controller address means only the controller's own invocation passes; a third party cannot burn, and the controller burns only after it deletes the account's entries.

position-nft::transfer | caller-auth | INV-AUTH-02 | from.require_auth authorizes the move and the stock update rejects any from that is not the token owner, so only the holder can move the whole account; delegate grants from the previous owner go inactive.
position-nft::transfer_from | caller-auth | INV-AUTH-02 | spender.require_auth authorizes the move, which needs spender to be the owner, the token's live approved address, or an operator the owner approved for all; the stock update then rejects any from that is not the owner, and the transfer clears the token approval.

position-nft::approve_for_all | caller-auth | INV-AUTH-02 | owner.require_auth authorizes the grant and the storage key is (owner, operator), so a caller can only give an operator power over its own NFTs; the grant expires at live_until_ledger.

pub(crate) fn process_withdraw(
    env: &Env,
    caller: &Address,
    account_id: u64,
    withdrawals: &Vec<HubPayment>,
    to: Option<Address>,
) -> Vec<HubPayment> {
    validation::require_authorized_caller(env, caller);

    let mut account = storage::get_account(env, account_id);
    require_owner_or_delegate(env, account_id, caller, &account.owner);

    let recipient = to.unwrap_or_else(|| caller.clone());
    let mut cache = Context::new(env);
    require_external_recipient(env, &mut cache, &recipient);
    let aggregated = payments::aggregate_payments(env, withdrawals, payments::ZeroLeg::MeansAll);

    let paid = settle_withdraw(env, &mut account, &recipient, &aggregated, &mut cache);
    let _ = enforce_post_pool_solvency(env, &mut cache, &mut account);

    finalize_position_flow(
        env,
        account_id,
        &account,
        &mut cache,
        PositionSides::Supply,
        true,
    );
    paid
}
