### Title
Reused Worktree Directory Not Cleaned of Untracked Files Before Publishing via Symlink - (File: main.go)

### Summary
`git-sync` publishes each synced revision by creating a git worktree and then atomically flipping a symlink to it, guaranteeing consumers only ever see a complete, consistent checkout [1](#0-0) . The mechanism that prepares the worktree's contents, `configureWorktree`, brings the working tree to the desired commit using `git reset --hard <hash> --`, which only resets **tracked** files and does not remove untracked files that may already be present in that worktree directory [2](#0-1) . This mirrors the reported `AdapterV1.sol` bug class: an operation trusts the "current state" of a resource (there, the adapter's PSM balance; here, the worktree directory's file set) without verifying that only the expected/tracked content is present, so any leftover material introduced by a prior step silently flows into the next output.

### Finding Description
`configureWorktree` is not only invoked right after a brand-new worktree is created by `createWorktree` (which does start from a clean directory via `removeWorktree` + `worktree add`) [3](#0-2) . It is also invoked in `SyncRepo` against a worktree that **already existed** on disk, whenever `changed` or `git.syncCount == 0`, on the rationale that "it might not have all the correct settings" and should simply be reconfigured in place [4](#0-3) . In that reused-directory path, `configureWorktree` performs:
- Overwriting `.git` gitdir pointer [5](#0-4) 
- Optional sparse-checkout file writes [6](#0-5) 
- `git reset --hard <hash> --` to bring tracked content to the new commit [2](#0-1) 
- `git submodule update --init [--recursive]` [7](#0-6) 

None of these steps call `git clean` to remove untracked files/directories. `git reset --hard` explicitly leaves untracked paths untouched. If any untracked file was ever written into that worktree directory — e.g., left over from a prior sparse-checkout configuration that stopped excluding a path, a submodule checkout that later becomes unlisted, a build/hook artifact, or any process that wrote into the worktree between syncs — that file persists across ref changes and is exposed to consumers through the symlink `--link`, which is the documented "API" contract of git-sync [8](#0-7) .

This is structurally identical to the reported bug: `_addLiquidity` trusted `PSM.balanceOf(address(this))` — the full ambient state — rather than the amount actually intended for that operation, so an out-of-band credit (the 1inch refund) silently became part of the next computation. Here, `configureWorktree` trusts the ambient directory contents combined with a partial (tracked-only) reset, rather than guaranteeing the directory exactly matches the target commit, so out-of-band files silently become part of what is published.

### Impact Explanation
This matches the "publishing wrong or partial content" acceptance criterion: consumers reading through `--link` could see files that do not belong to the currently synced commit, in violation of git-sync's core atomicity/consistency contract [9](#0-8) . Depending on what the untracked leftover is (e.g. a script consumed by a hook, a config file an app blindly trusts), this can range from stale/incorrect data being served to potential downstream code execution in consumers that execute files out of the synced directory.

### Likelihood Explanation
The reused-worktree code path is reached in normal operation (not just crash-recovery) any time `syncCount == 0` at process start with an already-populated `--root`, or whenever the target hash changes and the destination worktree directory pre-exists from a previous run [10](#0-9) . Since sparse-checkout files, `.git` info files, and submodule configuration are all attacker-influenceable via the synced repository content (the untrusted upstream ref), an attacker controlling the remote repo across two consecutive commits (e.g., commit A includes an unwanted file path within sparse-checkout scope, commit B narrows/removes it from sparse-checkout or moves it out of the tree) could get git-sync to leave that file behind in the worktree on a reused directory, without it being cleaned before the symlink flips.

### Recommendation
In `configureWorktree`, after (or as part of) `git reset --hard <hash> --`, also run `git clean -ffdx` (or equivalent) to remove all untracked files and directories, including ignored ones, so that only content tracked at `hash` is present before the worktree is published via the symlink. This closes the gap where a previously-existing worktree directory can carry forward untracked artifacts across syncs.

### Proof of Concept
1. Start git-sync against a repo where `--sparse-checkout-file` is configured to include path `extra/payload` at commit A; let it sync, so `extra/payload` is checked out into worktree `A`.
2. Push commit B on the same ref that removes `extra/payload` from the tree (or from sparse-checkout scope) but keeps the same underlying worktree directory in play (e.g., restart git-sync so `syncCount == 0` while `--root` already contains worktree `A`, or trigger `changed == false` re-sync path with the same hash).
3. Observe that `configureWorktree` runs `git reset --hard B --` on the existing directory; since `extra/payload` is untracked at commit B (or excluded via sparse-checkout) it is not removed by `reset --hard`, and no `git clean` call exists in `configureWorktree` [11](#0-10) .
4. `extra/payload` remains on disk in the worktree that gets published via `--link`, even though it is not part of commit B's tree — demonstrating that stale/unexpected content is served to consumers in violation of the atomic sync contract.

// createWorktree creates a new worktree and checks out the given hash.  This
// returns the path to the new worktree.
func (git *repoSync) createWorktree(ctx context.Context, hash string) (worktree, error) {
	// Make a worktree for this exact git hash.
	worktree := git.worktreeFor(hash)

	// Avoid wedge cases where the worktree was created but this function
	// error'd without cleaning up.  The next time thru the sync loop fails to
	// create the worktree and bails out. This manifests as:
	//     "fatal: '/repo/root/nnnn' already exists"
	if err := git.removeWorktree(ctx, worktree); err != nil {
		return "", err
	}

	git.log.V(1).Info("adding worktree", "path", worktree.Path(), "hash", hash)
	_, _, err := git.Run(ctx, git.root, "worktree", "add", "--force", "--detach", worktree.Path().String(), hash, "--no-checkout")
	if err != nil {
		return "", err
	}

	return worktree, nil
}
