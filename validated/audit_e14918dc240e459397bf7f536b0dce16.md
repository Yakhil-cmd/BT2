### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while event handlers act on the unrelated `repository.full_name` field, allowing cross-tenant webhook forgery in multi-GitHub-App deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC `webhook_secret`) used to validate an inbound webhook using only `repository.owner.login` (falling back to `organization.login`). Once the signature check passes, the actual event `Handler` (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the `Stack`/`Repository` to mutate using a completely different, unauthenticated-relative-to-signature field: `repository.full_name`. Nothing forces these two payload fields to agree, so a tenant that legitimately owns a `webhook_secret` for their own GitHub organization can forge a webhook whose `owner.login` matches their own org (making the signature check pass) while `full_name` points at a repository belonging to a different, unrelated organization tracked by the same Shipit instance.

### Finding Description
`verify_signature` computes the "authenticating" identity purely from the owner login: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization key when the engine is configured for multiple GitHub organizations, which is a documented and supported deployment mode: [3](#0-2) [4](#0-3) 

Once `verified` is true, `Shipit::Webhooks.for_event(event)` dispatches the raw JSON `params` to handlers, none of which re-check `repository.owner.login`. Instead, the base `Handler` resolves the target `Stack` solely from `repository.full_name`: [5](#0-4) 

`PushHandler`, for example, uses this `stacks` scope to look up and act on a `Stack` matching the branch, triggering a GitHub sync: [6](#0-5) 

The binding that should hold is: **organization that authenticated the webhook signature == organization that owns the repository being written to**. Because `verify_signature` reads `repository.owner.login` and the handlers read `repository.full_name`, these are two independently-attacker-controlled JSON fields in the same payload with no cross-validation, so the equality can be broken at will by anyone able to craft an arbitrary JSON body signed with a `webhook_secret` they legitimately hold for their own organization.

### Impact Explanation
In a multi-org Shipit deployment (`config/secrets.yml` keyed by GitHub organization, as documented and tested): [7](#0-6) 

an org admin who legitimately possesses their own org's `webhook_secret` (e.g. "OrgOne") can:
1. Set `repository.owner.login` (or `organization.login` for events lacking `repository`) to their own org so `verify_signature` selects and validates against their own known secret.
2. Set `repository.full_name` to `victim-org/victim-repo`, a stack tracked under a different tenant on the same Shipit instance.

The forged event is then processed as if it genuinely originated from GitHub for the victim's repository. This is most impactful for the `status` event: an attacker can post a fabricated `state: "success"` CI status against an arbitrary sha of the victim's repository. Since Shipit's deploy gating relies on stored `Status` rows (`required_statuses`/CI checks) to decide whether a commit is deployable, forging a passing status for a victim commit can bypass CI gating for that stack, enabling deployment of a commit that never actually passed CI — an unauthorized-deploy-enabling authorization bypass across tenant boundaries. It can also be used with the `push`/`check_suite` events to force out-of-band syncs/refreshes of a victim stack at will.

### Likelihood Explanation
The attacker needs only a `webhook_secret` for an organization they legitimately administer within a shared, multi-tenant Shipit deployment — not any victim-specific secret, API token, or session. This is a realistic configuration (explicitly documented as "Using Multiple GitHub Applications"), and no additional privilege is required beyond crafting an arbitrary JSON body and computing an HMAC-SHA1 with a key the attacker already owns. This significantly increases likelihood in shared/multi-org Shipit installs.

### Recommendation
Bind webhook verification and event processing to the same, GitHub-supplied source of truth. Concretely:
- Derive the organization used both for signature verification and for repository resolution from a single field (e.g. always `repository.full_name`'s owner segment, or verify that `repository.owner.login` matches the owner parsed out of `repository.full_name` before dispatching to handlers).
- Reject the webhook if the owner used for `Shipit.github(organization:)` lookup does not match the owner of the repository the handler is about to act on.

### Proof of Concept
Given a multi-org Shipit instance with orgs `OrgOne` (attacker-controlled, `webhook_secret: s1`) and `OrgTwo` (victim, stack `OrgTwo/service`):

```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(s1, body)>

{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": {
    "owner": { "login": "OrgOne" },       // used by verify_signature -> passes with s1
    "full_name": "OrgTwo/service"          // used by StatusHandler/Handler#stacks -> writes to victim stack
  }
}
```

`WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgOne")` and validates successfully using the attacker's own `s1` secret, per: [1](#0-0) 

The dispatched `StatusHandler` (subclass of `Handler`) then resolves `stacks` via `repository.full_name = "OrgTwo/service"`, per: [8](#0-7) 

and records a forged "success" status against the victim's commit — despite the request only ever being authenticated as belonging to `OrgOne`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
