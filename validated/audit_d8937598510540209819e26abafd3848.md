Found the critical binding break: the webhook signature is verified against a GitHub App keyed by `repository_owner` (org derived from the **unverified** payload's `repository.owner.login`), but the handler that actually mutates state (`Repository.from_github_repo_name`) is keyed by a *different* payload field — `repository.full_name` — which is never checked for consistency with `repository.owner.login`.

### Title
Webhook organization used for signature verification is not bound to the repository full_name that is actually written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate `X-Hub-Signature` against using `repository_owner`, computed from the request body's `repository.owner.login` (or `organization.login`) [1](#0-0) [2](#0-1) . Once the signature check passes, the raw, attacker-controlled `params` hash is dispatched unchanged to every registered handler for the event [3](#0-2) . Handlers determine which `Stack`/`Repository` to mutate using an entirely different field: `repository.full_name`, via `Repository.from_github_repo_name` [4](#0-3) . Since GoldLink's report is about a callee computing a value from one set of inputs while the caller's authorization check gates on a different (never-cross-validated) value, the exact same class of defect exists here: the signature check authenticates `repository.owner.login`, but the actual write target is selected by `repository.full_name`, and nothing enforces that `full_name` starts with `owner.login`.

### Finding Description
In a multi-organization Shipit deployment (`Shipit.github(organization: ...)`, documented and tested via `secrets_double_github_app.yml` for exactly this use case) [5](#0-4) , each org has its own `webhook_secret`. An attacker who controls (or is a legitimate, unprivileged GitHub user/admin of) one onboarded organization "OrgAttacker" knows or can obtain that org's `webhook_secret` value is verifiable — they can compute a valid HMAC using **their own** org's secret. If they set `repository.owner.login = "OrgAttacker"` (so `verify_signature` selects and validates against OrgAttacker's real secret, passing) but set `repository.full_name = "OrgVictim/some-repo"` in the same JSON body, the check-boundary (`repository_owner`) and the mutation-boundary (`repository.full_name`) point at two different organizations. `verify_signature` succeeds because it only ever inspects the owner-login sub-object, never cross-checking it against `full_name`, and `Handler#repository_name` blindly reads `full_name` to find the target `Repository`/`Stack` [4](#0-3) .

This breaks the intended binding: *"organization whose secret authenticated the request" == "repository that gets written."* Handlers like `PushHandler` then trigger `stack.sync_github(expected_head_sha:)` for any stack under the victim repository [6](#0-5) , and PR handlers (`OpenedHandler`, `LabeledHandler`, etc.) can archive/unarchive review stacks or update pull-request records belonging to a repository under a completely different, unauthenticated organization [7](#0-6) [8](#0-7) .

### Impact Explanation
This allows an attacker with control of, or webhook-delivery capability into, one org configured in a multi-org Shipit instance to forge webhook-driven state changes (sync/queue git commits, archive/unarchive review stacks, update PR metadata, trigger merges/label-based provisioning behavior) against stacks/repositories belonging to a *different* organization on the same Shipit instance, without ever possessing that other organization's `webhook_secret`. This crosses a genuine authentication boundary (the org-keyed webhook secret) to affect a repository it was never authorized for — matching the "High: unauthenticated ... cross-boundary write" class called out in scope, and can escalate toward unauthorized deploy/rollback behavior indirectly (e.g., forcing archive/unarchive of production-adjacent review stacks, or forcing resync of a competitor stack's commit history that a downstream continuous-deployment policy might then act on).

### Likelihood Explanation
Requires a multi-organization Shipit configuration (explicitly supported and documented) [9](#0-8)  where the attacker legitimately controls one of the configured GitHub orgs/apps (thus its `webhook_secret`) but targets a different org's repositories tracked by the same instance. This is plausible for shared/hosted Shipit deployments serving multiple orgs, but not exploitable in the common single-org deployment (`github_default_organization` nil case, where all repos share the same secret regardless).

### Recommendation
In `WebhooksController#verify_signature` (or immediately after, before dispatching to handlers), reject the request if `repository_owner` does not match the owner segment parsed from `repository.full_name` (or `organization.login`, when present). Alternatively, have `Handler#repository_name`/`stacks` re-derive the repository strictly from the same `repository.owner.login` field used for signature verification instead of trusting `full_name` independently.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgAttacker` and `OrgVictim`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As a user with delivery access to `OrgAttacker`'s webhook (or anyone who knows `OrgAttacker`'s `webhook_secret`), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgAttacker" },
    "full_name": "OrgVictim/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgAttacker_webhook_secret, body)>` and POST to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "OrgAttacker")` and validates successfully against the attacker's own known secret [1](#0-0) .
5. `PushHandler#process` resolves the target via `Repository.from_github_repo_name("OrgVictim/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on `OrgVictim`'s stacks [4](#0-3) [6](#0-5) , despite the request never being authenticated against `OrgVictim`'s webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
