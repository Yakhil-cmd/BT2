### Title
Webhook organization used for signature verification is never bound to the repository the payload writes to, allowing cross-organization stack forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) [2](#0-1) . Once the signature is accepted, every event handler instead resolves the target `Stack`/`Repository` using a completely different field, `payload.dig('repository', 'full_name')`, via `Handler#repository_name`/`#stacks` [3](#0-2) . Because the HMAC covers the raw JSON body, an attacker who legitimately owns a GitHub organization with the Shipit GitHub App installed (a supported, documented multi-org configuration, see `docs/setup.md` "Using Multiple Github Applications") [4](#0-3)  can self-sign an arbitrary payload where `repository.owner.login`/`organization.login` matches their own org (so `verify_signature` passes using their own valid `webhook_secret`) while `repository.full_name` is set to any other org/repo string entirely unrelated to the org that authenticated the request.

### Finding Description
The security invariant Shipit is supposed to enforce is: *the organization whose webhook secret signed the request == the repository whose stacks are mutated by the resulting handler*. That equality is never checked.

- `verify_signature` looks up `Shipit.github(organization: repository_owner)` and validates `X-Hub-Signature` against that organization's configured `webhook_secret` [1](#0-0) .
- `repository_owner` is derived from the same untrusted JSON body being verified [2](#0-1) .
- After verification, `create` dispatches to handlers with the raw parsed JSON `params` [5](#0-4) .
- `Handler#stacks` resolves the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` [3](#0-2) , a field independent from `repository.owner.login`.
- `PushHandler#process` uses those stacks to trigger `stack.sync_github(expected_head_sha: params.after)` for any branch matching `ref` [6](#0-5) .
- `StatusHandler#process` writes a `Commit` status (`create_status_from_github!`) purely by matching `sha`, with no repository/org binding at all [7](#0-6) .

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the mutated `Stack`) are two independently attacker-supplied fields inside the same self-signed body, an org that is cryptographically authenticated is never checked to be the same org/repo the handler acts on. This is the direct analog of the reported issue: `Depositor#withdrawFromGauge` validated an NFT belonged to `depositReceipt` generally, but never checked it was minted by *that* `Depositor`, letting one depositor's authenticated action manipulate another depositor's state. Here, `verify_signature` validates the signer is *some* configured organization, but never checks it is the *same* organization/repository the payload subsequently mutates.

### Impact Explanation
An attacker who is a legitimate customer/org-admin in a multi-org Shipit deployment (i.e., has their own org with the app installed and thus knows their own `webhook_secret`) can forge webhook events attributed to any other tenant's repository:
- Force `GithubSyncJob`/`sync_github` execution and injection of fabricated commits against another organization's `Stack` (`PushHandler`).
- Inject fabricated commit statuses (`StatusHandler`) that other stacks' CI-gating/merge logic rely on, since `Commit.where(sha:)` has no organization scoping at all.
- More broadly, any handler that trusts `repository.full_name` without an org binding is exposed to cross-tenant writes to stack/commit/deploy state — this matches the "cross-repository writes" Critical impact category, since it lets one authenticated tenant write into another tenant's repository/stack state without ever having GitHub write access to that repository.

### Likelihood Explanation
This requires the deployment to run Shipit in the documented multi-organization mode (multiple GitHub Apps/orgs configured under `github:` in `secrets.yml`) [4](#0-3) , and for the attacker to control at least one such org (a normal, low-privilege position for a tenant in a shared Shipit instance, not requiring any victim credentials, private keys, or GitHub write access to the victim repo). The attacker only needs to compute a valid `X-Hub-Signature` with their own known secret and craft the JSON body — no interaction with the victim org is needed.

### Recommendation
Bind the field used to select the verifying organization to the field used to resolve the target repository/stack. Concretely:
- After `verify_signature` resolves `repository_owner` and the matching `github_app`, re-derive the target repository strictly from the verified organization (e.g. require `payload.dig('repository', 'full_name')` to start with `"#{repository_owner}/"`), or pass the verified `repository_owner`/`github_app` through to `Handler` and have `Handler#stacks` scope `Repository.from_github_repo_name` to repositories owned by that verified organization, rejecting/dropping events where they diverge.

### Proof of Concept
1. Deploy Shipit configured with two GitHub Apps/orgs, `attacker-org` (attacker controls it, knows its `webhook_secret`) and `victim-org` (hosts the target `Stack`).
2. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, body)` and sends it as a `push` event to `POST /github/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature (attacker knows this secret) — request passes [1](#0-0) .
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and triggers `sync_github(expected_head_sha:)` on victim stacks matching branch `master`, despite the request being authenticated only for `attacker-org` [3](#0-2) [6](#0-5) .

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

      webhook_secret:
      private_key:

        secret:
        teams:
    someothergithuborg:

      installation_id:
      webhook_secret:
      private_key:
