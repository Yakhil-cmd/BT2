### Title
CCMenu token minted for one stack grants global `read:stack` access to all stacks' task output - (File: app/controllers/shipit/api/outputs_controller.rb)

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` with `read:stack` permission but never binds it to the requested stack via the `stack` association, leaving `stack_id` `nil`. `Api::BaseController#stacks` treats a `nil` `stack_id` as "no restriction" and returns `Stack.all`, so the token generated for stack A is fully valid against `Api::OutputsController#show` for any other stack B, exposing `task.chunk_output` for arbitrary tasks.

### Finding Description
The claimed binding is: `current_api_client.stack_id == task.stack_id`. Tracing the code shows this is never enforced:

- `CCMenuUrlController#fetch` creates the client with `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — no `stack:` is passed, so `stack_id` is `NULL`. [1](#0-0) 
- The client is looked up/created by `(creator, name)` only, so the *same* client/token is reused (and returned) for every stack that user ever requests a CCMenu URL for. [2](#0-1) 
- `Api::BaseController#stacks` is `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`. Since `stack_id` is `nil`, `stack_id?` is `false`, so it resolves to `Stack.all` — completely unscoped. [3](#0-2) 
- `Api::OutputsController#show` only enforces `require_permission :read, :stack` (checked via `ApiClient#check_permissions!`, which merely checks the string `"read:stack"` is in the `permissions` array — it has no notion of *which* stack) and then does `stack.tasks.find(params[:task_id])`, where `stack` resolves through the unscoped `stacks` relation. [4](#0-3) 
- `ApiClient#check_permissions!` confirms the scope is purely a string match with no stack awareness. [5](#0-4) 

So after tracing: `current_api_client.stack_id` is `nil` and `task.stack_id` is stack B's id — they never match, yet no code path rejects the request. The intended restriction (`Stack.where(id: current_api_client.stack_id)`) simply doesn't activate for `nil`, defaulting instead to "all stacks," which is the opposite of a safe default.

Exploit flow: a user visits the CCMenu-URL page for stack A (`GET /stacks/:owner/:repo/:branch/ccmenu_url` handled by `CCMenuUrlController#fetch`), receives a token in the returned `ccmenu_url`. That token — via HTTP Basic auth handled in `Api::BaseController#authenticate_api_client` — is then presented to `GET /api/stacks/:stack_b_id/tasks/:task_id/output`, which renders `task.chunk_output` for stack B without any additional check, because `stacks` resolved to `Stack.all`.

None of the existing guards catch this: `require_permission` only checks the permission *name* string, not stack ownership; `authenticate_api_client` only validates the signed token integrity, not stack scope; there is no `stack_id` equality check anywhere in `Api::BaseController` or `Api::OutputsController`.

### Impact Explanation
Any user who has been issued a CCMenu token for one stack (via the normal `fetch` UI flow) can use that same token to read `chunk_output` for tasks belonging to any other stack in the Shipit instance, including stacks/repositories they have no legitimate access to. Deploy task output can contain environment values echoed by `Command`/`PTY.spawn`-driven deploy tasks, so this is an unauthorized cross-tenant read of deploy output/state, matching the High-severity category "unauthenticated read of stack state, task streams or deploy output" (and can rise toward Critical if the leaked output contains deploy-time secrets). It is fully repeatable: the same long-lived token (tokens are not expiring, signed via `SimpleMessageVerifier`) can be replayed indefinitely against any `stack_id`/`task_id` pair.

### Likelihood Explanation
Preconditions are low: the attacker needs to be any Shipit user who is authorized to view the CCMenu URL for at least one stack (a very common, low-privilege capability in most Shipit deployments). No GitHub secrets, webhook secrets, or `api_clients_secret` are needed since the token is legitimately issued to them. Cost is a single authenticated request to obtain the token and one further request per target stack/task to exfiltrate output — trivially repeatable across every stack/task ID in the instance.

### Recommendation
Bind the CCMenu client to the requesting stack when it's created (`ApiClient.create_with(permissions: %w[read:stack], stack: stack).find_or_create_by!(...)`), include the stack in the `find_or_create_by!` lookup key (not just `creator`/`name`) so a distinct token is minted per stack, and ensure `Api::BaseController#stacks`/`OutputsController` reject access when `task.stack_id != current_api_client.stack_id` for stack-scoped clients.

### Proof of Concept
```ruby
# test/controllers/api/outputs_controller_test.rb
test "a CCMenu token minted for stack A cannot read stack B's task output" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # a different stack
  user = shipit_users(:walrus)

  # Simulate CCMenuUrlController#fetch minting the client for stack A
  client = ApiClient.create_with(permissions: %w[read:stack])
                     .find_or_create_by!(creator: user, name: 'CCMenu Client')
  assert_nil client.stack_id # confirms token is not bound to stack A

  task_b = shipit_tasks(:cyclimse_deploy) # belongs to stack_b

  authorization = ActionController::HttpAuthentication::Basic
                    .encode_credentials(client.authentication_token, '')
  get api_stack_task_output_path(stack_b, task_b),
      headers: { 'Authorization' => authorization }

  # Fails today: request succeeds and leaks stack_b's output despite
  # client.stack_id (nil) != task_b.stack_id
  assert_response :success
  assert_equal task_b.chunk_output, response.body
end
```
