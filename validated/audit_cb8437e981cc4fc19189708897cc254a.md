### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but downstream handlers act on the unrelated `repository.full_name` field — allowing a legitimate multi-org Shipit admin to forge actions against a repository/organization they do not own - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate the incoming HMAC signature against using `repository_owner`, a value read straight out of the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`). Once that check passes, `create` dispatches the *entire* raw payload to event handlers, all of which resolve the target `Stack`/`Repository` using a **different** field of the same payload: `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb`). Nothing ties `repository.owner.login` (the field used to pick the verifying secret) to `repository.full_name` (the field used to pick the object being mutated). In a Shipit installation configured with multiple GitHub organizations (`Shipit.github_organizations`, `Shipit.github_app_config`, documented under "Using Multiple Github Applications" in `docs/setup.md`), anyone who legitimately administers *their own* org's GitHub App (and thus knows *their own* `webhook_secret`) can forge a webhook whose `repository.owner.login` is their own org (so the signature check passes with their own secret) but whose `repository.full_name` points at a repository belonging to a completely different, victim organization.

### Finding Description
- `verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and uses it to pick a `GitHubApp` instance via `Shipit.github(organization: repository_owner)`, then checks `github_app.verify_webhook_signature(signature_header, raw_post)`. [1](#0-0) [2](#0-1) 
- `verify_webhook_signature` HMACs the raw request body with the `webhook_secret` belonging to whichever organization was resolved above. [3](#0-2) 
- Once verification succeeds, `create` blindly hands the *whole parsed payload* to every registered handler for the event. [4](#0-3) 
- Every handler (push, pull_request opened/closed/reopened/edited/labeled/unlabeled/label-capturing, status, membership, check_suite) resolves the affected repository/stack using `payload.dig('repository', 'full_name')`, an entirely separate field from the one used to select the verifying secret. [5](#0-4) [6](#0-5) [7](#0-6) 
- `Repository.from_github_repo_name` simply splits `full_name` on `/` and looks the record up by `owner`/`name` — it never re-validates against the org that authenticated the request. [8](#0-7) 
- Multi-org support (each org with its own `app_id`/`webhook_secret`) is a first-class, documented deployment mode. [9](#0-8) 

**Binding broken:** *the organization whose secret authenticated the request* ≠ *the repository/organization whose stack is actually written to*. The signature only proves "this body was HMAC-signed by OrgA's app secret"; it says nothing about which repository the same body's `full_name` field claims to target. Any org admin in a multi-org Shipit deployment (who legitimately possesses their own org's `webhook_secret`, e.g. by configuring their own GitHub App as documented) can produce a validly-signed request body whose `repository.owner.login` is their own org, but whose `repository.full_name` is `"victim-org/victim-repo"`.

### Impact Explanation
Because handler logic exclusively trusts `repository.full_name` to select the `Stack`/`Repository`/`PullRequest`/`ReviewStack`, this crosses a genuine repository-trust boundary in a multi-tenant Shipit install:
- Trigger `stack.sync_github` on a victim stack (`PushHandler`), forcing unwanted GitHub syncs.
- Archive/unarchive review stacks or close/reopen PRs belonging to a victim repository (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `UnlabeledHandler`).
- Add/remove `Membership` records or create `Team`/`User` records tied to the victim org via the `membership` event.
- Post fabricated `commit_status`/`check_suite` results into a victim stack's commit history, influencing deploy gating.

This is a cross-repository write reachable by a party who is authenticated only for their own tenant, matching the "cross-repository writes" high/critical impact class.

### Likelihood Explanation
Requires: (1) the operator runs Shipit in the documented multi-organization mode with more than one GitHub App configured, and (2) the attacker is an admin of at least one of those onboarded orgs (i.e., possesses that org's own `webhook_secret`, which they legitimately configured themselves — no privileged Shipit credential needed). This is a realistic scenario for any Shipit instance serving multiple independent teams/organizations, which is exactly the use case the multi-org configuration exists for.

### Recommendation
After signature verification succeeds for `repository_owner`, re-derive the repository target the same way and assert consistency: parse `repository.full_name` and require that its owner segment (case-insensitively) equals `repository_owner`/the organization that validated the signature, rejecting (422) on mismatch. Equivalently, in `Repository.from_github_repo_name`/handler resolution, refuse to act on any `full_name` whose owner differs from the verified webhook organization.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `attacker-org` and `victim-org`, each with its own installed GitHub App and `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. As the (legitimate) admin of `attacker-org`, know `attacker-org`'s `webhook_secret`.
3. Craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac_sha1(attacker-org secret, raw_body)>` and `X-Github-Event: push`, then POST to `/webhooks`.
5. `verify_signature` resolves `repository_owner == "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the HMAC matches → verification passes.
6. `PushHandler#process` runs `Repository.from_github_repo_name("victim-org/victim-repo")`, finds the victim's stacks, and calls `stack.sync_github(expected_head_sha: params.after)` — an action on a repository the attacker does not control, authenticated only via `attacker-org`'s own secret.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
