### Title
Security Commit-Review Hook Marks Commits as "Reviewed" Even When the Underlying LLM Security Scan Fails, Permanently Bypassing Future Review - ([File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
The `security-guidance` plugin's `PostToolUse` hook is supposed to run an LLM-based security review on every committed diff before permanently recording the commit SHA as "reviewed" so that later `git push` sweeps skip it. The hook writes this "reviewed" state unconditionally after *attempting* the review, rather than gating it on the review actually completing successfully. This mirrors the referenced report's root cause: a credit/side-effect ("fee taken" / here, "review passed") is finalized based on an operation being *initiated* rather than *succeeding*.

### Finding Description
In `handle_commit_review_posttooluse`, the review is executed via either the agentic path or the single-shot `analyze_code_security` fallback: [1](#0-0) 

Immediately afterward, regardless of whether the LLM call succeeded, timed out, or hit an API error, the code records the commit as reviewed: [2](#0-1) 

The comment explicitly documents the design: the SHA is "marked regardless of whether findings were emitted." Later, when `concrete_guidance` is empty, the code treats it identically to "no security issues found," even in cases where an API error occurred, which is only surfaced as a passive metrics field: [3](#0-2) 

Because the SHA is already persisted in the reviewed-shas store before this branch executes, a failed/erroring LLM call (analogous to the GMX "position execution fails" case) still results in the commit being credited as "reviewed" — the analog of the referrer still collecting their fee despite the trade failing. The persisted state is consumed later by the push-sweep hook, which treats any SHA in the reviewed set as already covered and advances its diff base past it: [4](#0-3) 

This means a commit that was never actually scanned for vulnerabilities (due to a transient LLM/API failure) permanently exits the review pipeline — the security-review hook can be silently defeated any time the underlying LLM call fails, with no automatic re-attempt.

### Impact Explanation
This falls under the "hook bypass" trust-boundary category. The `security-guidance` plugin exists specifically to catch vulnerabilities introduced by (potentially malicious or careless) commits before/around a push. If a commit containing a real vulnerability happens to be committed while the LLM call errors out (rate limit, network blip, API 5xx, SDK failure), that commit is marked reviewed and will never be flagged by the subsequent push-sweep, effectively and silently disabling the safety net for that code change. This is a confirmed logic flaw in the shipped hook script, not a hypothetical — the code and its own inline comments demonstrate the intentional but flawed "mark regardless of outcome" behavior.

### Likelihood Explanation
LLM API errors, timeouts, and SDK import failures are explicitly anticipated and handled elsewhere in this same file (`agentic_fallback`, `llm._last_call_claude_http_error`), indicating they are a realistic, non-rare occurrence in production use of this hook (network flakiness, rate limits, model outages). Every time such a failure coincides with a commit, the review-bypass triggers automatically with no attacker interaction required.

### Recommendation
Do not call `_append_reviewed_shas` when the review path terminated due to an error (agentic fallback failure without a successful single-shot completion, or `llm._last_call_claude_http_error is not None`). Only persist the SHA as reviewed once a genuine, completed analysis (success or confirmed no-findings) has occurred; on error, leave the SHA unmarked so a later push-sweep or retry can still catch it — mirroring the recommended fix in the referenced report of crediting/finalizing state only on confirmed success rather than at the start of the operation.

### Proof of Concept
1. Configure the `security-guidance` plugin with `ENABLE_CODE_SECURITY_REVIEW` on.
2. Introduce a code change containing a detectable vulnerability (e.g., command injection).
3. Simulate/force an LLM call failure during the commit-review hook (e.g., temporarily block network access to the API, or trigger an HTTP error so `llm._last_call_claude_http_error` is set and `concrete_guidance` is empty).
4. Observe that `_append_reviewed_shas` still executes at [5](#0-4) , persisting the commit SHA to the reviewed-shas store despite no successful review having occurred.
5. Push the branch; observe in `handle_push_sweep_posttooluse` that the vulnerable commit is excluded from the diff sent for review because it is already in `reviewed`, per [4](#0-3) , permanently bypassing detection of the introduced vulnerability.

    # push-sweep state: record this commit as reviewed (full 40-hex sha) so a
    # later `git push` can advance its diff base past it. Recorded here — after
    # the review ran but before any exit path — so it's marked regardless of
    # whether findings were emitted. `shas` holds abbreviated refs from
    # `[branch sha]`; resolve to full so set-membership in the push-sweep is
    # exact. Best-effort; failures here never block the review result.
    try:
        full_shas = []
        for s in shas:
            r = subprocess.run(
                [*GIT_CMD, "rev-parse", "--verify", "-q", s],
                cwd=repo_root, capture_output=True, text=True, timeout=5,
            )
            if r.returncode == 0:
                full_shas.append(r.stdout.strip())
        _append_reviewed_shas(repo_root, full_shas, vulns_found=len(vulns or []))
    except Exception:
        pass
