### Title
`StatusHandler` writes `Status` rows onto commits matched by SHA alone, with no repository ownership check, corrupting `Commit#status`/`#deployable?`/`#blocked?` from a foreign repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, with no comparison of the webhook's `repository.full_name` against the commit's own `Stack`/`Repository`. Every other webhook handler that touches a `Stack`/`Commit` (`PushHandler`, `CheckSuiteHandler`, the pull-request handlers) scopes through `Handler#stacks`, which derives the target `Stack`s from `Repository.from_github_repo_name(repository_name)` - `StatusHandler` is the outlier that skips this scoping entirely.

### Finding Description
Binding claimed by the question: for every `Status` row folded into `Commit#status` via `Status::Group.compact(self, statuses_and_check_runs)` [1](#0-0) , the row's owning repository must equal the repository of the `Commit`'s own `Stack`, i.e. `status.stack.repository == commit.stack.repository`.

`Status::Group.new`/`.compact` performs no such check - it only dedupes by `context`, filters hidden statuses, and sorts; it accepts whatever `statuses_and_check_runs` (i.e. `commit.statuses + commit.check_runs`) contains [2](#0-1) . `Commit#statuses_and_check_runs` is simply the commit's own associations [3](#0-2) , so the only place a repository/stack equality could be enforced is at write-time, when a `Status` row is created and associated to a `Commit`.

That write path is `StatusHandler`:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 
This looks up **every** `Commit` row across **all stacks/repositories** sharing the given `sha`, with zero reference to `payload['repository']`. Contrast with the base `Handler`, which exposes a `stacks` helper explicitly scoped to the webhook's own repository via `Repository.from_github_repo_name(repository_name)` [5](#0-4) , and with `PushHandler`/`CheckSuiteHandler`, which both use `stacks` to scope their side effects to the correct repository [6](#0-5) [7](#0-6) . `StatusHandler` never calls `stacks` and never touches `payload['repository']`.

`create_status_from_github!` writes the status onto the matched `Commit`'s own `stack_id` [8](#0-7) , and `add_status` recomputes `status` (clearing the `@status` memo via `reload`) and fires `Hook.emit(:commit_status, ...)` / `:deployable_status` and `stack.schedule_merges` based on the transition [9](#0-8) . This directly feeds `Commit#status`, which memoizes `Status::Group.compact(self, statuses_and_check_runs)` [1](#0-0) , and which `MergeRequest#any_status_checks_failed?`/`#any_status_checks_missing?`/`#all_status_checks_passed?` all consume via `StatusChecker.new(head, head.statuses_and_check_runs, ...)` [10](#0-9) .

**Exploit path**: SHA1 git commit hashes are content-addressed and deterministic (tree, parents, author/committer identity+timestamp, message). An attacker forks a target public repository tracked by Shipit (or otherwise obtains/creates a repository containing a commit with an identical SHA to one already tracked as a `Shipit::Commit`, e.g. by re-pushing the same commit object to their own repo). They configure (or already have) a GitHub webhook on their own repository set to send `status` events to the Shipit host. `verify_signature` in `WebhooksController` selects the signing app via `Shipit.github(organization: repository_owner)` using `payload['repository']['owner']['login']` from *the attacker's own repository* [11](#0-10)  - this is exactly the "emit webhooks from a repository they own" capability granted to the attacker by the rules, and GitHub itself computes a valid HMAC for that webhook using the correctly configured app secret for the attacker's own installation/org. The signature check therefore validates a webhook that is legitimately theirs to send, while the payload body's `sha`, `state`, `context`, etc. are entirely attacker-controlled content describing a commit that also exists (by SHA) in a completely unrelated tracked stack.

`StatusHandler.process` then finds the unrelated `Commit` row purely by `sha` equality and writes a forged `Status` (e.g. `state: 'success'`) onto it, flipping `Commit#status`/`#deployable?` for a repository the attacker never authenticated against.

**Why existing guards don't stop this**: `verify_signature` only proves the payload came from *some* GitHub repository/org that Shipit trusts enough to have a configured secret - it says nothing about whether that repository is the one owning the `Commit` being mutated. `drop_unhandled_event` only checks the event type is registered. The `ExplicitParameters` schema for `StatusHandler` only requires `sha`/`state` be present and well-typed, not that they belong to the sending repository [12](#0-11) . No model validation on `Status` or `Commit` enforces repository consistency between the webhook source and the target row.

### Impact Explanation
An unprivileged GitHub user who owns any repository can, via a legitimately-signed `status` webhook from their own repo, write arbitrary `Status` rows (state `success`/`failure`/`error`/`pending`, arbitrary `context`/`description`/`target_url`) onto `Commit` rows belonging to any other tracked stack that happens to share a commit SHA. This directly flips `Commit#status`, `#deployable?`, and `#blocked?` for a stack the attacker has no access to, and can flip `MergeRequest` merge-readiness checks (`any_status_checks_failed?`, `all_status_checks_passed?`) since those consume the same corrupted `statuses_and_check_runs`. If continuous deployment is enabled on the victim stack, `stack.schedule_merges` / `ContinuousDeliveryJob` can be triggered from `add_status`'s transition logic, meaning a forged "success" status from a foreign, attacker-controlled repository can contribute to triggering an unauthorized deploy. This matches "Critical - a payload for one repository mutating another's stack, commit ... or an unauthorized deploy."

### Likelihood Explanation
Preconditions: the attacker needs a commit whose SHA1 also exists in a Shipit-tracked stack. This is trivially achievable for any public/open-source project tracked by Shipit: fork the target repo (git preserves identical SHAs for all pre-fork commits), and configure a webhook on the fork pointed at the Shipit webhooks endpoint. No Shipit credentials, GitHub App secrets, or team membership are required - only the capabilities explicitly granted in scope ("push to a fork", "emit webhooks from a repository they own"). This is fully repeatable against any tracked stack/commit whose SHA can be reproduced in an attacker-controlled repo, at zero cost per request.

### Recommendation
In `StatusHandler#process`, scope the commit lookup the same way `PushHandler`/`CheckSuiteHandler` do: resolve `stacks` from `Repository.from_github_repo_name(repository_name)` (i.e. `payload['repository']['full_name']`) and only update `Commit`s belonging to those stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Commit#stack` and assert `commit.stack.repository == stacks.first.repository` before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status webhook from an unrelated repository must not alter a commit belonging to a different stack" do
          victim_commit = shipit_commits(:first) # belongs to shipit_stacks(:shipit), repo shopify/shipit-engine
          attacker_repo_full_name = "attacker/unrelated-fork"

          # Binding under test, BEFORE:
          # status.stack.repository == victim_commit.stack.repository  -- for every status folded into victim_commit.status
          before_state = victim_commit.status.state

          payload = ExplicitParameters::Parameters.define {
            requires :sha, String
            requires :state, String
            accepts :description, String
            accepts :target_url, String
            accepts :context, String
            accepts :created_at, String
          }.parse!(
            'sha' => victim_commit.sha,
            'state' => 'failure',
            'context' => 'forged/attacker-context',
            'repository' => { 'full_name' => attacker_repo_full_name, 'owner' => { 'login' => 'attacker' } }
          )

          StatusHandler.new(
            'sha' => victim_commit.sha,
            'state' => 'failure',
            'context' => 'forged/attacker-context',
            'repository' => { 'full_name' => attacker_repo_full_name, 'owner' => { 'login' => 'attacker' } }
          ).process

          victim_commit.reload

          # AFTER: assert the equality claimed by the binding STILL holds -- it should, but it does not.
          created_status = victim_commit.statuses.find_by(context: 'forged/attacker-context')
          assert_nil created_status,
            "StatusHandler must not create a Status row for a Commit not owned by the webhook's own repository"
          assert_equal before_state, victim_commit.reload.status.state,
            "Commit#status must not change from an unrelated repository's webhook"
        end
      end
    end
  end
end
```
Running this against the current `StatusHandler#process` (`Commit.where(sha: params.sha)` with no repository scoping) fails both assertions: a `Status` row with context `forged/attacker-context` is created on `victim_commit`, and `victim_commit.status.state` changes to `failure`, proving the binding `status.stack.repository == commit.stack.repository` is not enforced anywhere in the write path feeding `Commit#status`.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

        def compact(commit, statuses)

          case group.size

            group.statuses.first
