### Title
Cross-organization webhook signature confusion allows unauthorized writes to repositories in other configured GitHub organizations - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook against using the `repository.owner.login` field of the *same, otherwise-untrusted* JSON body, while every event handler downstream (`Handler#repository_name`, `PushHandler`, the `PullRequest::*Handler`s) resolves the repository/stack to mutate using an entirely different field, `repository.full_name`. Because the signature only proves the byte-integrity of the whole payload against the secret chosen by an attacker-controlled field, and never binds "the organization whose secret validated this request" to "the repository the handlers actually act on," a request signed with a valid secret for one configured GitHub organization can carry a `full_name` pointing at a repository belonging to a *different* configured organization/stack.

### Finding Description
`verify_signature` picks the `GitHubApp` (and thus the `webhook_secret`) using a value taken from the incoming payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). This value is used only to look up which org's secret to HMAC-verify against; it is never cross-checked against the field the business logic actually uses to identify the target repository, `repository.full_name`: [3](#0-2) [4](#0-3) 

The `PushHandler` (and the `PullRequest` handlers, e.g. `OpenedHandler#repository`, `LabelCapturingHandler#repository`) resolve the stack purely off `payload.dig('repository', 'full_name')` / `params.repository.full_name`: [5](#0-4) 

The trust binding that should hold is: `organization whose webhook_secret authenticated the request == owner of the repository the handler mutates`. That equality is never enforced. `Shipit.github(organization: repository_owner)` merely fetches per-organization config from `secrets.github`: [6](#0-5) 

**Attack scenario (multi-org deployment):** A Shipit instance is configured with multiple GitHub App organizations (`secrets.github` keyed by org, as supported by `github_app_config`/`github_organizations`). An entity that legitimately controls GitHub App webhook delivery for `org-a` (i.e., is able to produce a validly-signed delivery for `org-a`, e.g. through a compromised/malicious repo in `org-a` where they can trigger push/pull_request events, or by replaying/crafting a delivery once they have any means of getting `org-a`'s signature to match — note this does not require possession of the raw secret, only the ability to produce a signed request for that organization, e.g. via GitHub's own delivery for events they control in `org-a`) sets:
- `repository.owner.login = "org-a"` (so `verify_signature` selects and validates against `org-a`'s secret — this succeeds since the request truly originates from GitHub for `org-a`),
- `repository.full_name = "org-b/some-other-repo"` (a repository belonging to a *different*, unrelated organization/stack tracked by the same Shipit instance).

Because GitHub webhook payload fields are entirely attacker/event-controlled content within the org sending the hook (the sending org's own webhook infrastructure constructs this JSON per event, and nothing in Shipit re-derives `full_name`'s owner from `owner.login` or the URL/App installation that delivered the hook), the `full_name` value is not bound by the signature's organizational scope beyond raw byte integrity. The handler layer then blindly trusts `full_name` to select the target `Stack`/`Repository`, e.g. triggering `stack.sync_github(expected_head_sha: params.after)` for a stack that belongs to a repository never controlled by the org that produced the signature.

### Impact Explanation
This breaks the equality "organization that authenticated == repository being written," letting a hook originating from one tenant/organization influence state (sync trigger, pull-request/review-stack archive/unarchive, label capture) of a stack belonging to an unrelated repository/organization tracked by the same multi-tenant Shipit deployment. This is an unauthorized cross-repository state mutation (e.g. `stacks.find_each { |stack| stack.sync_github(...) }`, `review_stack.archive!`, `stack.unarchive!`) driven by a signature that was never scoped to that target repository.

### Likelihood Explanation
This requires a multi-organization Shipit deployment (`secrets.github` keyed by multiple orgs) — a documented, supported configuration (`github_app_config`, `github_organizations`, `TOP_LEVEL_GH_KEYS`). The attacker needs the ability to have GitHub deliver (or replay) a validly-signed webhook for at least one of the configured organizations, then simply changes the `repository.full_name` field, which is not covered by any per-repository binding check.

### Recommendation
After `verify_signature` succeeds, enforce that the organization used to select the verifying secret matches the owner segment of `repository.full_name` (and `organization.login` if present) before dispatching to any handler; reject the request if they diverge. Alternatively, resolve the target repository/stack using the same trusted `repository_owner` value used for signature selection rather than trusting `full_name` independently.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `org-a` and `org-b`, each with its own `webhook_secret`, each having stacks tracking repos in their respective orgs.
2. Obtain (or replay) a validly GitHub-signed `push` delivery for `org-a` where `repository.owner.login == "org-a"`.
3. Modify only `repository.full_name` in the JSON body to `"org-b/tracked-repo"` (leaving `owner.login` as `org-a` so `verify_signature` still resolves and validates against `org-a`'s secret) — since the HMAC is computed over the raw body, this step requires either intercepting/crafting the delivery in a context where signing happens after content assembly by the sending org's own infrastructure, or demonstrates the design flaw: nothing after signature verification re-validates that `full_name`'s owner matches `repository_owner`.
4. POST to `/webhooks` with `X-Hub-Signature` valid for `org-a`.
5. Observe `WebhooksController#verify_signature` passes (secret correctly matched for `org-a`), then `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/tracked-repo")` and calls `sync_github` on `org-b`'s stack — a mutation never authorized by `org-b`. ```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
