Based on my analysis, I found a valid analog vulnerability in the webhook signature verification flow.

### Title
Webhook signature verified against organization derived from unsigned payload, while stack lookup uses a different unsigned field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify a webhook's HMAC against by reading `repository.owner.login` (or `organization.login`) out of the **unverified** JSON body, before the signature has been checked. Once verification passes, `Handler#stacks` looks up the target `Repository`/`Stack` using an entirely different field of the same unverified body: `repository.full_name`. Nothing binds the organization that was used to select/verify the signing secret to the repository that is actually acted upon.

### Finding Description
`verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and uses it to fetch the appropriate `GitHubApp`/secret via `Shipit.github(organization: repository_owner)`, then calls `verify_webhook_signature` with that secret against the raw body. [1](#0-0) [2](#0-1) 

This is exactly the multi-org configuration documented in the setup guide, where each GitHub organization has its own `app_id`/`webhook_secret` pair. [3](#0-2) [4](#0-3) 

Once the signature check passes, the event handler (e.g. `PushHandler`) resolves the target `Stack` using `payload.dig('repository', 'full_name')` — a **different key of the same payload**, not re-validated against `repository_owner`. [5](#0-4) [6](#0-5) 

The binding that should hold is: `organization authenticated (repository.owner.login used to pick the secret) == organization whose repository is written (repository.full_name used to find the Stack)`. Because `verify_signature` never cross-checks these two fields, a party who legitimately controls a GitHub App installation on **their own** organization (Org A) — and therefore legitimately knows Org A's `webhook_secret` — can sign an arbitrary payload with Org A's secret while setting `repository.full_name` to `OrgB/some-repo`, a stack belonging to a completely different, unrelated organization/tenant configured in the same Shipit instance. The signature verifies (it was computed over Org A's secret and matches `repository.owner.login: "OrgA"`), but the `PushHandler`/other handlers will act on `OrgB`'s stack, triggering `sync_github` (which can queue syncs, and depending on handler, trigger continuous deployment via `Stack.schedule_continuous_delivery` reacting to updated branch state) for a repository the attacker does not control and was never authorized to authenticate for.

This mirrors the reported bug class: a value trusted for one purpose (recapitalization/authorization state keyed off one accounting) is silently reused/acted upon in a different accounting context (the actual underlying asset value) without re-validation — here, the "authenticated organization" is trusted for signature purposes but the "repository actually written to" is taken from an unrelated, unchecked field of the same attacker-supplied body.

### Impact Explanation
This breaks the authentication boundary between tenants (organizations) hosted on a single Shipit instance using the documented multi-org `github:` configuration. An attacker who is legitimately an admin of their own small/throwaway GitHub organization (with its own installed App and known `webhook_secret`) can forge webhook events that Shipit will treat as authenticated for an arbitrary victim organization's stacks, causing unauthorized `sync_github` triggers and downstream continuous-delivery/deploy scheduling for repositories/stacks they do not own — an unauthorized cross-repository action driven by forged, cross-tenant trust.

### Likelihood Explanation
Requires the attacker to control at least one legitimately configured GitHub organization/App entry within the same multi-org Shipit deployment (a realistic scenario for any organization hosting Shipit for many independent teams/orgs, as explicitly documented as a supported configuration). No `ApiClient` token, no repository write access to the victim repo, and no privileged Shipit account are required — only knowledge of a secret for an org that is itself legitimately, but separately, configured in the same instance. This is a plausible, code-verified path, not a full end-to-end proof (I could not execute the webhook endpoint to confirm final side effects of `sync_github` beyond what's shown in `PushHandler`).

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, cross-validate that the organization used to select the signing secret (`repository.owner.login`) matches the organization implied by `repository.full_name` (and any other repository identifiers used by handlers) before dispatching to handlers. Reject the webhook if these fields disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per documented multi-org setup). [4](#0-3) 
2. As an attacker who controls `OrgA`'s GitHub App (and thus knows `OrgA`'s `webhook_secret`), craft a `push` event JSON body with `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/victim-repo"`.
3. Compute `X-Hub-Signature` using `OrgA`'s `webhook_secret` over this exact raw body.
4. POST to `/webhooks`. `verify_signature` resolves `repository_owner = "OrgA"`, fetches `OrgA`'s app/secret, and verification succeeds. [1](#0-0) 
5. `PushHandler#stacks` then resolves the target via `repository.full_name = "OrgB/victim-repo"`, and calls `stack.sync_github` on `OrgB`'s stack — a stack the attacker was never authorized to authenticate for. [5](#0-4) [6](#0-5)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
