### Title
Cross-repository status webhook forgery bypasses `Commit#deployable?` because commit lookup and lock state are not repository-bound - ([File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: app/models/shipit/commit.rb])

### Summary
`Shipit::Commit#deployable?` gates a deploy purely on `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, none of which reference the repository that originated the CI signal. The actual vulnerability is upstream: `StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, a global, repository-agnostic lookup, and webhook signature verification (`WebhooksController#verify_signature`) is scoped only to the GitHub organization, not the specific repository. Any attacker who can trigger a legitimately-signed status webhook for a commit SHA they control (e.g., by forking the tracked repo and running their own CI against the identical commit object) can flip `success?` to true on the victim stack's tracked `Commit` row, and `locked?` provides no protection because it defaults to `false` for virtually every commit.

### Finding Description
The claimed binding — "none of `!locked?`, `stack.ignore_ci?`, `success?`, or `blocked?` consult the requesting repository's identity" — holds true against the code:

- `deployable?` is exactly `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [1](#0-0) .
- `locked?` is driven by `lock_author_id`, a column on the `Commit` row itself with no repository reference [2](#0-1) ; it defaults to unset for any commit that was never explicitly locked.
- `blocked?` only inspects other commits within the *same stack* between the last deploy and this commit, again with no cross-repository semantics [3](#0-2) .

The exploitable root cause is that nothing upstream of `deployable?` binds the incoming status to the repository that the target `Stack`/`Commit` actually tracks:

- `StatusHandler#process` resolves every `Commit` matching the SHA in the payload, across all stacks, and immediately records the (attacker-controlled) status against each: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . Its `params` schema only requires `sha`/`state` and accepts `description`, `target_url`, `context`, `created_at`, `branches` — it never validates the payload's `repository`/`name` field against the commit's owning stack [5](#0-4) .
- `WebhooksController#verify_signature` resolves the signing key by `repository_owner` (organization login), not by the specific repository: `github_app = Shipit.github(organization: repository_owner)` [6](#0-5) . Any repository under that same GitHub organization/App installation shares the same webhook secret, so a legitimately-signed webhook from an attacker-owned repository in that org passes signature verification.

Exploit flow: an attacker forks (or otherwise obtains write access to a repository containing) a commit whose SHA is identical to a commit already tracked by a victim `Stack` (trivial if the attacker forks the exact tracked repository — git object hashes are content-addressed and identical across forks/mirrors). The attacker then posts a `success` status to that SHA via the GitHub Status API on their own repository. GitHub delivers a correctly-signed webhook (signed with the org-level secret) to Shipit's `/webhooks` endpoint. `StatusHandler#process` matches the SHA against **every** `Commit` row with that SHA, including the victim's, and creates a `success` status on it regardless of which repository actually authored the event. On the victim's `Commit`, `success?` becomes true, `blocked?` is false (no blocking statuses conflict), `locked?` is false (default), so `deployable?` returns true — enabling `stack.continuous_deployment?` (`schedule_continuous_delivery`, `app/models/shipit/commit.rb:281-287`) or a manual deploy trigger to proceed as if the victim repository's own CI had passed.

None of the listed guards stop this: `verify_signature` only checks organizational identity, not per-repository identity; `drop_unhandled_event` only filters unsupported event types; the `ExplicitParameters` schema for `StatusHandler` has no repository field to validate; `locked?`/`blocked?`/`ignore_ci?` are all repository-agnostic by design.

### Impact Explanation
A successful forged status write causes the `success` state, and thus deploy eligibility (`deployable?`), to be recorded on a `Commit` belonging to a stack/repository the attacker does not control and never authenticated against — this is a payload from one repository mutating another repository's stack/commit state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The attack is repeatable against any commit SHA the attacker can reproduce (most straightforwardly, any public commit in the tracked repository, since forking preserves SHAs), and against any stack in the same GitHub organization/App installation, i.e., it is not limited to one victim repository.

### Likelihood Explanation
Preconditions: the victim commit must be untracked by a manual lock (`lock_author_id` nil — the default state for almost all commits) and the attacker must be able to get a webhook delivered and signed using the same organization-level secret Shipit uses for the victim's stack (realistic if the attacker owns/forks any repository within the same GitHub organization/App installation, or the tracked repository is public and forkable). No Shipit session, API token, or Shipit-side secret is required — the attacker relies entirely on GitHub's own, legitimate signing of events for a repository they control. This is a low-cost, repeatable attack requiring only fork/push access and use of the standard GitHub Status API.

### Recommendation
Bind status/check-run processing to the repository, not just the SHA: `StatusHandler#process` (and the equivalent check-run handler) should filter `Commit.where(sha: params.sha)` further by `stack.github_repo_name == params.name` (or `repository.full_name`) before creating a status, so a status is only ever attached to commits that belong to the reporting repository. Signature verification should additionally validate that the repository asserted in the payload matches an authorized repository for that organization/installation, not just that the organization-level secret is correct.

### Proof of Concept
```ruby
# test/models/shipit/commit_test.rb (or a new webhook integration test)
test "forged status webhook from an unrelated repository makes an unlocked victim commit deployable" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, message: "victim commit", author: shipit_users(:walrus), committer: shipit_users(:walrus))

  assert_equal false, victim_commit.locked?
  assert_equal false, victim_commit.deployable?

  # Simulate StatusHandler#process receiving a validly-signed status webhook
  # whose payload references an attacker-owned repository but the same sha.
  forged_params = OpenStruct.new(sha: victim_commit.sha, state: "success", description: nil, target_url: nil, context: "ci", created_at: Time.now.iso8601)
  Commit.where(sha: forged_params.sha).each { |c| c.create_status_from_github!(forged_params) }

  victim_commit.reload
  assert_equal false, victim_commit.locked?   # lock state untouched, still false
  assert_equal true, victim_commit.success?
  assert_equal true, victim_commit.deployable? # became deployable purely from the forged, repo-unbound status
end
```
This proves the equality claimed in the question — `locked?` is `false` both before and after the forged webhook, and `deployable?` flips to `true` with no lock-related interaction, purely as a result of the repository-agnostic status write reachable via `StatusHandler#process`.
