### Title
Persistent Sync Denial via Oversized/Complex Repository Content Exceeding `--sync-timeout` - ([File: main.go])

### Summary
`git-sync` wraps every `git` invocation (fetch, worktree checkout, submodule update) in a single `context.Context` bounded by `--sync-timeout` (default `120s`), enforced through `exec.CommandContext` in the command runner. An attacker who controls content pushed to the synced upstream repository (e.g. a public repo, a branch an attacker can push to, or a submodule repo referenced by `.gitmodules`) can grow the cost of a sync cycle — via large blobs/history, or deeply nested `--submodules=recursive` chains — to the point where the full fetch→worktree→submodule-update sequence can never complete inside the configured timeout window. This is directly analogous to the Gravity Bridge finding: an unbounded, attacker-influenced growth factor (validator set size / repo complexity) eventually exceeds a fixed resource budget (block gas limit / `--sync-timeout`), permanently preventing forward progress.

### Finding Description
Each sync iteration creates a single timeout-bound context and runs the whole sequence of git operations under it: [1](#0-0) 

That context is passed through `fetch`, `createWorktree`, `configureWorktree` (checkout + `submodule update --init --recursive`), which are all executed via `git.Run(ctx, ...)`: [2](#0-1) [3](#0-2) 

The underlying command runner enforces the deadline via `exec.CommandContext` and returns a `DeadlineExceeded` error if the timeout is hit mid-command: [4](#0-3) 

On failure, the outer loop increments `failCount` and retries after the normal period; by default `--max-failures` is `-1` (unbounded), so `git-sync` retries forever rather than aborting: [5](#0-4) 

`--submodules` defaults to `recursive`, meaning every submodule (including nested submodules controlled by third parties) is recursively cloned and checked out as part of the same timeout-bound operation: [6](#0-5) [7](#0-6) 

None of `fetch`, `checkout`, or `submodule update` have an independent, tunable sub-timeout or a size/complexity cap distinct from the single global `--sync-timeout`; the only mitigations (`--depth`, `--submodules=shallow|off`, `--sparse-checkout-file`) are operator-configured, not enforced defaults, and even `--depth` only bounds commit history, not blob size, submodule fan-out, or submodule nesting depth.

### Impact Explanation
If the upstream repository's content (or a submodule it references) grows large/complex enough that a full fetch + worktree checkout + recursive submodule update cannot finish within `--sync-timeout`, every sync attempt fails identically and permanently:
- No new commit is ever published via the atomic symlink, so the workload backed by `git-sync` is permanently stuck on stale (or, on first sync, entirely absent) content — a persistent sync denial.
- Because `--max-failures` defaults to unbounded retries, the process does not even fail fast; it loops forever consuming fetch/CPU/disk resources without making progress, and (per the "Atomic Symlink Contract") the readiness signal never gets set if this happens on the very first sync, so dependent pods never become ready.
- Attackers with only push access to the synced repository (or one of its submodules) — no privileged/operator access to git-sync itself — can trigger this by pushing oversized content or bloated/deeply-nested submodules, matching the "attacker-pushed commit" threat model.

This matches the accepted impact class of "persistent sync denial."

### Likelihood Explanation
Likelihood is Medium-to-Low in practice: it requires (a) `git-sync` configured to sync a repository (or submodule) an attacker can write to, and (b) the attacker being able to grow that content past whatever `--sync-timeout` the operator has configured, which competes with the git host's own push size/time limits. It is more easily triggered against smaller/default timeout deployments (`120s`) or when `--submodules=recursive` is left at its default and a submodule is attacker-controlled, similar to how the original Gravity issue required validator-set growth during a period of larger block gas limits before a later reduction "bricked" it.

### Recommendation
- Apply independent, per-step timeouts/limits (fetch, checkout, submodule update) rather than one shared deadline for the entire multi-stage operation, so a slow submodule chain cannot silently consume the whole budget.
- Bound submodule recursion depth/count, or require an explicit opt-in allowlist for submodule URLs, since `--submodules=recursive` currently fetches whatever a remote `.gitmodules` (possibly attacker-controlled) declares.
- Consider a default non-unbounded `--max-failures` so operators are alerted/paged instead of the process silently retrying forever without progress.
- Document/emit a distinct, actionable error/metric when repeated `DeadlineExceeded` failures occur, to make persistent stalls observable rather than indistinguishable from transient network failures.

### Proof of Concept
1. Configure `git-sync --repo=<attacker-writable-repo> --root=/data --link=current --submodules=recursive --sync-timeout=120s` (defaults).
2. As the attacker (who has push access to the repo, or to a submodule the repo references), commit a chain of nested submodules (e.g. 50+ levels deep, each pointing to a distinct remote), or push large blobs, such that a full `fetch` + `worktree add` + `submodule update --init --recursive` sequence exceeds 120 seconds.
3. Observe that `git.SyncRepo` fails with `context deadline exceeded` from `pkg/cmd/cmd.go:85-87` on every iteration.
4. Since `--max-failures` defaults to `-1`, `git-sync` never exits and never publishes a new symlink target — the link stays on the last-known-good hash (or is never created on first sync), demonstrating persistent denial of forward sync progress purely from attacker-controlled upstream content growth.

// fetch retrieves the specified ref from the upstream repo.
func (git *repoSync) fetch(ctx context.Context, ref string) error {
	git.log.V(2).Info("fetching", "ref", ref, "repo", redactURL(git.repo))

	// Fetch the ref and do some cleanup, setting or un-setting the repo's
	// shallow flag as appropriate.
	args := []string{"fetch", git.repo, ref, "--verbose", "--no-progress", "--prune", "--no-auto-gc"}
	if git.depth > 0 {
		args = append(args, "--depth", strconv.Itoa(git.depth))
	} else {
		// If the local repo is shallow and we're not using depth any more, we
		// need a special case.
		shallow, err := git.isShallow(ctx)
		if err != nil {
			return err
		}
		if shallow {
			args = append(args, "--unshallow")
		}
	}
	if git.filter != "" {
		args = append(args, "--filter", git.filter)
	}
	if _, _, err := git.Run(ctx, git.root, args...); err != nil {
		return err
	}

	return nil
