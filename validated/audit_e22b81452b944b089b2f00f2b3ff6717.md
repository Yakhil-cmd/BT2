### Title
`deposit()` mints zero shares without reverting, letting a victim's principal be silently redistributed to existing shareholders - (File: mainnet/contracts/vault/v0-vault-usdh.clar / v0-vault-sbtc.clar / v0-vault-ststx.clar / v0-vault-ststxbtc.clar / v0-vault-stx.clar / v0-vault-usdc.clar)

### Summary
Analogous to the Badger Citadel `Funding.getAmountOut()`/`deposit()` bug (an amount-conversion helper can return `0` and the caller-facing function does not guard against it), the Zest vault `deposit()` function computes the shares to mint via `convert-to-shares-preview` but — unlike `redeem()` in the same file — never asserts that the computed share amount is non-zero before minting.

### Finding Description
`deposit()` computes `inkind` via `convert-to-shares-preview amount`, which rounds down (`mul-div-down amount ts ta`) [1](#0-0) . It only checks the raw input `(> amount u0)` and a slippage bound `(>= inkind min-out)`, then mints `inkind` shares to the caller with no `(> inkind u0)` check [2](#0-1) .

By contrast, `redeem()` in the very same contract explicitly guards against a zero output: `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` [3](#0-2) . This asymmetry mirrors the Citadel finding exactly: one side of a conversion path has no protection against a zero-value result, while the parallel path does.

If the share price (`ta`/`ts`) is high enough — which can occur once the vault has been running for a while and accrued interest has pushed `total-assets` far above `total-supply` for any depositor whose contribution is small relative to the pool — `convert-to-shares-preview` can round `inkind` down to `0` for a legitimate, honestly-sized deposit made with the default `min-out` of `0`. The transaction succeeds: `receive-underlying` pulls the depositor's tokens into the vault, `var-set assets` increases by the full deposit amount, but `ft-mint?` mints `0` zft to the depositor. The depositor's funds are absorbed into `assets` and become part of the collateral base backing all *existing* shareholders' zft, permanently diluting/transferring the new depositor's principal to them with no compensation.

This is the write-up's exact bug class: a conversion helper returns `0` under a specific state and the caller does not defend against it, but here the consequence is worse than a revert — it is a silent, irreversible fund loss for the caller and a silent gain for existing holders (a stranger's position/shared pool state, `assets` / `total-supply`, is manipulated so that one transaction benefits others at the depositor's expense).

### Impact Explanation
This lands on **Critical — direct theft of user funds at rest**: the victim depositor's underlying tokens are moved into the vault's `assets` accounting with zero shares minted in return, and those funds become claimable pro-rata by all other zft holders on redemption. Because `deposit()`'s only safeguard is the caller-supplied `min-out`, any integrator or user who does not set a nonzero `min-out` (the parameter defaults to `0` in normal wallet flows and is not enforced by the contract to be nonzero) is exposed.

### Likelihood Explanation
Likelihood is moderate: it requires the vault's `total-assets-preview`/`total-supply` ratio to already be skewed enough that a normal-sized deposit rounds to `0` shares, which becomes increasingly likely over time as interest (`total-debt`) accrues while `total-supply` stays low (e.g., a low-TVL vault, or one where most zft has been redeemed) — see `total-assets-preview`, which adds accrued interest before rounding [4](#0-3) . No privileged action or admin misconfiguration is required — it is purely a function of ordinary vault growth combined with a small enough deposit and default `min-out=0`.

### Recommendation
Add `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` to `deposit()` in every vault contract, mirroring the existing guard already present in `redeem()`, so the transaction reverts instead of silently minting zero shares.

### Proof of Concept
1. Vault has been live long enough that `total-assets-preview` (current `assets` + accrued but unrealized borrower interest, per `total-assets-preview`) is large relative to `total-supply` (e.g., after most early depositors redeemed, leaving very few `zft` outstanding against sizeable residual debt/interest).
2. Victim calls `deposit(amount, min-out: 0, recipient: victim)` with a normal, modest `amount`.
3. `convert-to-shares-preview` computes `mul-div-down amount ts ta` [1](#0-0) , which rounds to `0` because `amount * ts < ta`.
4. `deposit()`'s checks pass (`amount > 0`, `inkind(0) >= min-out(0)`), `receive-underlying` pulls the victim's tokens, `assets` increases, but `ft-mint? zft 0 victim` mints nothing [5](#0-4) .
5. Victim has permanently lost `amount` of underlying with zero zft to show for it; the loss is captured by existing zft holders' increased backing.

            u0
