### Title
`in_data_feed` formula evaluation accepts data-feed messages from unstable units regardless of `sequence` status - ([File: data_feeds.js])

### Summary
The reported bug class is "the oracle/data-feed retrieval mechanism does not correctly account for the conditions under which posted data becomes authoritative," causing dependent protocol logic to act on data that should not be trusted. In `ocore`, the analogous mechanism is the AA data-feed lookup code in `data_feeds.js`, which is used by both the `data_feed[[...]]` and `in_data_feed[[...]]` oscript operators. These two code paths implement inconsistent filtering of unstable candidate units when scanning `storage.assocUnstableMessages` for AA-authored data feeds.

### Finding Description
`readDataFeedValue`, used by the `data_feed` formula operator, explicitly excludes units whose `sequence` is not `'good'` when scanning unstable AA-authored messages: [1](#0-0) 

`dataFeedExists`, used by the `in_data_feed` formula operator (and by the `in data feed` address-definition condition), performs the equivalent scan but omits the `sequence` check entirely: [2](#0-1) 

Both functions are invoked from the same AA-formula evaluation context with the same `bAA` flag: [3](#0-2) [4](#0-3) 

Units with `sequence` set to `'temp-bad'` (pending conflict resolution) or `'final-bad'` (finally rejected as non-serial, typically due to a double-spend) still appear in `storage.assocUnstableMessages`/`storage.assocUnstableUnits` before/around finalization. `readDataFeedValue` correctly treats such units as if they never posted the feed, but `dataFeedExists` does not: any AA-authored unit that is currently intersecting `arrAddresses` (i.e., authored by the oracle/self address referenced in `in_data_feed`) and carries a matching `data_feed` message will satisfy the `in_data_feed` condition even while it is `temp-bad`/on track to become `final-bad`.

### Impact Explanation
`in_data_feed` is commonly used in AA oscript as a self-attestation / gating pattern, e.g. an AA verifying that the triggering address (acting as its own "oracle") has posted a specific value before allowing a payout or state change. Because the sequence filter is missing, a unit that is going to be excluded from the stable ledger (its `data_feed` message will never actually be recorded/applied) can still satisfy `in_data_feed[[...]]` during evaluation while the unit is unstable. This lets an attacker construct a scenario where an AA authorizes a fund release, state transition, or condition check based on a data-feed message that is subsequently discarded because its unit resolves to `final-bad`. This is a fund-loss/inconsistency vector for AAs and constitutes disagreement between nodes evaluating validity/state at different points relative to finalization, mirroring the original report's core issue: "the oracle-lookup mechanism does not correctly reflect what will ultimately be authoritative data."

### Likelihood Explanation
Triggering requires only that the attacker (or a party controlling the referenced oracle address, including "this address" self-oracle patterns) posts a unit carrying the desired `data_feed` message while simultaneously creating a conflicting double-spend that will make that unit `temp-bad`/`final-bad`. This is fully within reach of a single unprivileged AA trigger sender who controls the "oracle" address used in the `in_data_feed` check — a normal and encouraged oscript pattern — making the likelihood non-trivial for any AA relying on `in_data_feed` for self-referential gating.

### Recommendation
Add the same `objUnit.sequence !== 'good'` filter used in `readDataFeedValue` to the unstable-unit scan in `dataFeedExists`: [5](#0-4) 
so both `data_feed` and `in_data_feed` operators apply identical eligibility rules to unstable AA-authored messages, ensuring `in_data_feed` cannot return `true` for a message whose containing unit is not (or will not be) part of the good/serial sequence.

### Proof of Concept
1. Deploy an AA whose bounce/response logic includes a guard such as `in_data_feed[[oracles='this address', feed_name='proof', feed_value='1']]` gating a payout — a documented self-attestation idiom.
2. From the triggering address, broadcast two units nearly simultaneously that spend the same output (classic double-spend setup), where one of the conflicting units also carries a `data_feed` message `{proof: 1}` and is used as (or chained to) the AA trigger.
3. While the conflict is unresolved, the unit is `temp-bad` but still present in `storage.assocUnstableMessages`/`assocUnstableUnits`.
4. AA formula evaluation of `in_data_feed[[...]]` via `dataFeeds.dataFeedExists` (called from `formula/evaluation.js` `in_data_feed` case) scans this unit without checking `sequence`, finds the `proof=1` message, and returns `true`, allowing the AA to execute the gated payout.
5. The conflicting unit later resolves to `final-bad`; its `data_feed` message is never written to the stable data-feed store (confirmed by the differing `sequence` filter in `readDataFeedValue`), meaning the ledger's authoritative state never actually contained this data feed — yet the AA already acted on it as if it had.
