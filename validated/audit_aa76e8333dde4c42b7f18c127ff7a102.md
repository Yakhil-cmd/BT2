### Title
Windows path traversal via unsanitized `file.Name` in `writeToOutput` allows writing outside `--output` directory - ([File: pkg/cmd/repo/read-file/read_file.go])

### Summary
`writeToOutput` builds the destination path with `dest = filepath.Join(dest, file.Name)` (read_file.go:279) using the raw `name` field returned by the GitHub Contents API, with no sanitization such as `filepath.Base` or a `".."`/absolute-path check. On Windows, `filepath.Join` treats backslash as the path separator, so a file whose Git blob name (created on a Linux/macOS-hosted repo, where backslash is a legal filename byte) contains a sequence like `..\..\..\AppData\evil.txt` will cause the join to escape the intended `--output` directory when a Windows victim runs `gh repo read-file ... --output outdir/`.

### Finding Description
`fetchFile` in `pkg/cmd/repo/read-file/http.go` populates `repoFile.Name` directly from `contentsResponse.Name` (the API's `name` JSON field) with no validation: [1](#0-0) 

That value flows unmodified into `writeToOutput`, which only checks for symlinks/existing files/clobber, then does: [2](#0-1) 

Git tree entry names on a Linux/macOS-hosted repository can legally contain backslash characters (backslash is not a path separator in Git or on those filesystems — only `/` and NUL are forbidden). An attacker can therefore create a file in their own public repository whose single path-component name is literally `..\..\..\AppData\evil.txt` (or any Windows-meaningful traversal sequence). GitHub's Contents API `name` field returns this string verbatim. When a Windows victim runs `gh repo read-file <path> --repo attacker/repo --output outdir/`, `writeToOutput` sees `asDir == true` (trailing slash) and computes `filepath.Join("outdir/", "..\\..\\..\\AppData\\evil.txt")`. On Windows, `filepath.Join` (using `\` as `os.PathSeparator`) resolves the `..` segments against the OS separator, producing a path outside `outdir/`, e.g. under the user's `%USERPROFILE%` or `AppData`, and `writeFileF` (`os.WriteFile`) then writes attacker-controlled content there. No existing check (no `filepath.Base`, `filepath.Clean` + prefix check, or `.` component rejection) stops this in `writeToOutput`.

### Impact Explanation
This is an arbitrary file write outside the intended `--output` directory (Path Confinement violation) on Windows victims, matching GitHub's bounty impact class "file write outside the intended path." Depending on the target path chosen by the attacker (e.g. Startup folder, `.bashrc`-equivalent, SSH config, or overwriting existing files if `--clobber` is used or the target doesn't pre-exist), this could lead to persistence or further compromise of the victim's machine.

### Likelihood Explanation
Requires: (1) attacker publishes a public repo/branch with a maliciously-named file (trivial, git allows backslash bytes in filenames when the repo is created on Linux/macOS, which GitHub's backend uses); (2) victim is on Windows; (3) victim runs `gh repo read-file <path> --output <dir>/` (with a trailing separator, or an existing directory) against the attacker's repo/ref. This is plausible via social engineering-adjacent but still "ordinary usage" scenarios (e.g., victim following a README instruction to run `gh repo read-file` against a shared repo/PR). No token, no admin rights, no MITM needed — purely a crafted public repository. Feasibility is moderate: requires Windows victim plus the `--output` flag with directory semantics, but is fully repeatable and deterministic.

### Recommendation
Sanitize `file.Name` before joining: use `filepath.Base(filepath.Clean(strings.NewReplacer("\\", "/").Replace(file.Name)))` or equivalent to strip any path separators (both `/` and `\`) and reject any resulting empty name, `.`, or `..`. Alternatively, after computing `dest`, verify (e.g., via `filepath.Abs` + `strings.HasPrefix` after `filepath.Clean`, or by computing `filepath.Rel` and checking it doesn't start with `..`) that the resolved path stays within the resolved `output` directory before writing, and fail closed otherwise.

### Proof of Concept
Go unit test against `writeToOutput` (in `pkg/cmd/repo/read-file`), run on `GOOS=windows` (or using a Windows-style separator injected directly since `filepath.Join`'s behavior is OS-dependent — this specifically requires running on/targeting Windows semantics):

```go
func TestWriteToOutput_WindowsTraversal(t *testing.T) {
    dir := t.TempDir()
    outDir := filepath.Join(dir, "outdir") + string(os.PathSeparator)
    require.NoError(t, os.MkdirAll(outDir, 0755))

    file := &repoFile{
        Name:    `..\..\..\evil.txt`, // as returned verbatim by contentsResponse.Name
        Content: []byte("pwned"),
    }

    dest, err := writeToOutput(file, outDir, false)
    require.NoError(t, err)

    // Assert the resolved dest stays within outDir; expected to FAIL on Windows today,
    // demonstrating the escape.
    absOut, _ := filepath.Abs(outDir)
    absDest, _ := filepath.Abs(dest)
    require.True(t, strings.HasPrefix(absDest, absOut+string(os.PathSeparator)),
        "dest %q escaped output dir %q", absDest, absOut)
}
```
Expected: on a fix, the assertion passes (name is sanitized to a bare basename `evil.txt` inside `outdir/`); on current code running under Windows path semantics, `dest` resolves outside `outDir`, proving the escape.
