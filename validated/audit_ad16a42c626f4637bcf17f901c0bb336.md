## Title
AA formulas can read still-unstable ("future") data-feed values, letting a trigger sender pick the most favorable of several pending oracle prices before they are finalized - ([File: data_feeds.js])

## Summary
The GMX report describes traders picking a favorable price from a *range of prices available within the same not-yet-finalized block*, using a trigger price that is resolved together with (rather than strictly before) the trade. Ocore has a structurally analogous mechanism: when an AA formula evaluates `data_feed[[...]]`, it does not only look at already-stable, finalized data-feed rows — it also scans `storage.assocUnstableMessages`, i.e. data-feed values that have been posted but not yet stabilized, and picks the "best" (`ifseveral='last'`) candidate among possibly multiple concurrently-unstable values.

## Finding Description
`data_feed[[...]]` in oscript is evaluated by `formula/evaluation.js`'s `'data_feed'` case, which calls: [1](#0-0) 

passing `bAA` (true whenever evaluation happens inside AA execution) as the `unstable_opts` argument to `dataFeeds.readDataFeedValue`.

Inside `readDataFeedValue`, when `unstable_opts` is truthy, the function builds a list of *unstable* candidate values in addition to the stable, kv-store-persisted ones: [2](#0-1) 

It then resolves ties/multiplicity by sorting on `latest_included_mc_index` and `level` and taking the last (highest) one when `ifseveral` is `'last'` (the default): [3](#0-2) 

Crucially, this happens *before* the units carrying those data-feed messages are stabilized — `storage.assocUnstableMessages[unit]` entries are only moved into the durable, ordered `df\n...` kvstore index at stabilization time, in `addDataFeeds()`: [4](#0-3) 

Until that point, several different data-feed postings for the same `feed_name`/oracle can simultaneously exist as "unstable", each attached to a unit whose finality (and thus whose value will ultimately "count") is not yet fixed. The `readDataFeedValue` picking logic exists specifically to let AAs react to oracle-AA price updates before they're fully final (this is intentional, to keep AA-to-AA feeds responsive), but it means the *value an AA formula uses to gate execution can be chosen from among several as-yet-unconfirmed candidates* rather than a single already-finalized value, in the same way GMX orders could resolve against a *range* of prices available within the still-open block.

An attacker who triggers a price-sensitive AA (e.g., a futures/options-style contract like `test/samples/futures_contract.oscript` or `option_contract.oscript`, which both call `data_feed[[oracles=..., feed_name=...]]` to compare against a settlement/threshold price) at a moment when multiple not-yet-stable oracle-AA price updates exist can influence which of those pending values ends up being read (`ifseveral='last'` picks the highest `level`/`latest_included_mc_index` candidate, not necessarily the economically "correct" or fully-final one), and can time their trigger unit's placement in the DAG to land alongside the price update most favorable to them before the network's MC/finality settles the ambiguity.

## Impact Explanation
If an AA's payout/settlement logic depends on `data_feed[[...]]` read while multiple unstable candidate values are simultaneously pending, an attacker (trigger sender, potentially colluding with or acting as the price-posting AA) can bias which price is used for their trigger's outcome, extracting value at the expense of the AA's other counterparty/liquidity providers — directly analogous to the GMX "free look into the future" issue. This can cause AA fund loss for the counterparty side and inconsistent/unfair settlement outcomes.

## Likelihood Explanation
Exploitation requires: (1) an AA that gates a payout decision on `data_feed[[...]]` without pinning `min_mci`/waiting for stabilization, and (2) the ability to have or observe multiple unstable postings for the referenced oracle/feed_name near the trigger's MCI. Because `readDataFeedValue`'s unstable branch specifically requires the feed-poster's unit to itself be an AA response (`objUnit.bAA`) unless `unstable_opts==='all_unstable'` (used only by the light-client `light/get_data_feed` RPC, not by AA formula evaluation), practical exploitation is narrower than a generic oracle race — it mainly threatens AA-to-AA price relay patterns, still a legitimate and documented usage pattern (e.g., DEX/derivative AAs consuming a price-oracle AA's output). This keeps likelihood at Medium/High depending on adoption of such patterns.

## Recommendation
- For AA-consumed `data_feed[[...]]` reads that gate financial settlement, require the referenced posting to have already reached a stable/finalized MCI before it can be used (i.e., do not fold `storage.assocUnstableMessages` candidates into the resolution for the `data_feed` oscript primitive), or expose an explicit "stable only" mode for financially sensitive lookups.
- Where responsiveness to fresh unstable oracle-AA updates is required by design, disambiguate `ifseveral` ties deterministically by canonical DAG order (not `level`, which can be influenced by unit construction) and document that AAs relying on unstable prices are exposed to non-final-value risk, encouraging AA authors to require a `min_mci` buffer analogous to `REQUEST_EXPIRATION_BLOCK_AGE` in the referenced GMX fix.

## Proof of Concept
1. Deploy an oracle AA `O` that posts a `data_feed` message with a price whenever triggered (a realistic pattern for AA-to-AA price relays).
2. Deploy a settlement AA `S` (pattern as in `test/samples/futures_contract.oscript`/`option_contract.oscript`) whose payout branch does `data_feed[[oracles=O, feed_name='PRICE']] > X` without a `min_mci` constraint.
3. Craft/post two units in quick succession that both trigger `O` to emit differing price updates that remain simultaneously unstable (different DAG branches/levels) at the same `latest_included_mc_index` window.
4. Post the trigger to `S` at a moment where `readDataFeedValue`'s unstable branch in `data_feeds.js` lines 211-273 will resolve `arrCandidates` and, via the `level`-based sort, select the update most favorable to the attacker's position in `S`, before the DAG finality settles which branch/price truly persists.

function readDataFeedValue(arrAddresses, feed_name, value, min_mci, max_mci, unstable_opts, ifseveral, timestamp, handleResult){
	var bLimitedPrecision = (max_mci < constants.aa2UpgradeMci);
	var start_time = Date.now();
	var objResult = { bAbortedBecauseOfSeveral: false, value: undefined, unit: undefined, mci: undefined };
	var bIncludeUnstableAAs = !!unstable_opts;
	var bIncludeAllUnstable = (unstable_opts === 'all_unstable');
	if (bIncludeUnstableAAs) {
		var arrCandidates = [];
		for (var unit in storage.assocUnstableMessages) {
			var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
			if (!objUnit)
				throw Error("unstable unit " + unit + " not in assoc");
			if (!objUnit.bAA && !bIncludeAllUnstable)
				continue;
			if (objUnit.sequence !== 'good')
				continue;
			if (objUnit.latest_included_mc_index < min_mci || objUnit.latest_included_mc_index > max_mci)
				continue;
			if (_.intersection(arrAddresses, objUnit.author_addresses).length === 0)
				continue;
			storage.assocUnstableMessages[unit].forEach(function (message) {
				if (message.app !== 'data_feed')
					return;
				var payload = message.payload;
				if (!ValidationUtils.hasOwnProperty(payload, feed_name))
					return;
				var feed_value = payload[feed_name];
				if (value === null || value === feed_value || value.toString() === feed_value.toString())
					arrCandidates.push({
						value: string_utils.getFeedValue(feed_value, bLimitedPrecision),
						latest_included_mc_index: objUnit.latest_included_mc_index,
						level: objUnit.level,
						unit: objUnit.unit,
						mci: max_mci // it doesn't matter
					});
			});
