### Title
Webhook organization used for signature verification is unbound from the repository the event actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization secret to validate an inbound webhook against by reading an unauthenticated field out of the still-unverified JSON body (`repository.owner.login`), while the handlers that subsequently act on that same body select the `Repository`/`Stack` to mutate from a *different* field (`repository.full_name`). Because the HMAC signature covers the whole raw request body and is computed by whoever crafts the payload, anyone who knows the `webhook_secret` for *any one* organization configured on the Shipit instance can forge a signature over a payload whose `repository.full_name` points at a completely different organization's repository/stack.

### Finding Description
`verify_signature` derives the org used to look up the verification secret purely from the payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: ...)` uses that same attacker-supplied string to select which secret in `secrets.github` to verify against: [3](#0-2) 

Once the HMAC check passes, `create` hands the full, attacker-controlled `params` hash to every registered handler for the event: [4](#0-3) 

But the base `Handler` class resolves the target `Stack`/`Repository` from a *different* payload key, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

There is no invariant enforced anywhere that `repository.owner.login` (the field used to pick the verifying secret) must equal the owner portion of `repository.full_name` (the field used to pick the acted-upon repository). The signature only proves "whoever sent this knew *some* configured org's secret and built this exact byte string" — it says nothing about which repository the byte string claims to describe. In a multi-organization Shipit deployment (`secrets.github` keyed by multiple orgs, each with its own `webhook_secret`, per `TOP_LEVEL_GH_KEYS`/`github_app_config`), any org onboarded onto the shared instance knows its own `webhook_secret` and can therefore forge an event that is verified as coming from its own org but whose `repository.full_name` — and therefore the `Stack` acted upon by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc. — belongs to a different tenant's repository entirely.

This is exactly the "organization that authenticated versus the repository that is written" trust binding: `verified_org` (from `repository.owner.login`) should equal `owner(acted_repository)` (from `repository.full_name`), but nothing enforces it.

### Impact Explanation
With a forged but validly-signed (using one's own org secret) `status` or `check_suite` webhook whose `repository.full_name` names a victim org's repository, an attacker can mark an arbitrary commit on the victim's stack as CI-passing/deployable through `StatusHandler`/`CheckSuiteHandler`, or trigger sync/deploy-adjacent jobs via `PushHandler` → `GithubSyncJob`, for a stack they have no legitimate access to. Combined with continuous deployment or a subsequent deploy trigger, this can lead to an unauthorized deploy of a commit onto a stack belonging to a different, unrelated organization — matching the "unauthorized deploy" High-impact bucket.

### Likelihood Explanation
Requires the attacker to control (or be the admin of) at least one organization already onboarded to the same multi-tenant Shipit installation, so they know that org's `webhook_secret`. This is a real, supported configuration (`secrets.github` can be keyed by multiple orgs per `github_organizations`/`github_app_config`), and no unprivileged internet caller can exploit this without such a secret, but it's a boundary Shipit implicitly promises to keep (org A cannot affect org B's stacks) that is not enforced.

### Recommendation
After verifying the signature, cross-check that the organization used for verification (`repository.owner.login` / `organization.login`) matches the owner of the repository named in `repository.full_name` before dispatching to handlers, and reject (422) any webhook where they disagree. Alternatively, resolve the target `Repository`/`Stack` using the verified organization rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (`secrets.github.org_a.webhook_secret`, `secrets.github.org_b.webhook_secret`), both stored per `app/models/shipit/webhooks_controller.rb` / `lib/shipit.rb:196-200`.
2. As an admin of `org-a` (who legitimately knows `org-a`'s `webhook_secret`), craft a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature` as `sha1=` + HMAC-SHA1(`org-a`'s `webhook_secret`, raw JSON body).
4. POST to `/webhooks` with `X-Github-Event: push` and the computed signature.
5. `verify_signature` looks up `Shipit.github(organization: 'org-a')` and successfully verifies the signature against `org-a`'s secret (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `PushHandler#process` resolves the target stacks via `Repository.from_github_repo_name('org-b/victim-repo')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and triggers `stack.sync_github(expected_head_sha: ...)` on `org-b`'s stack — despite the request only ever being validated against `org-a`'s secret.

Problem: In `app/controllers/shipit/webhooks_controller.rb`, `verify_signature` selects the GitHub App/organization (and thus the `webhook_secret`) used to validate an inbound webhook's HMAC signature based on `params.dig('repository', 'owner', 'login')` (see `repository_owner` method), which is itself an unauthenticated field taken from the raw JSON body before the signature has been checked. Once verification passes, `create` forwards the full raw `params` hash to the registered handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`). However, `app/models/shipit/webhooks/handlers/handler.rb`'s `repository_name` method (used by `stacks`) resolves the actual `Repository`/`Stack` to act on from a *different* field, `payload.dig('repository', 'full_name')`. Nothing enforces that the organization used to pick the verifying secret (`repository.owner.login`) matches the owner encoded in `repository.full_name`. In a multi-organization Shipit deployment (`secrets.github` keyed by multiple orgs per `lib/shipit.rb`'s `github_organizations`/`github_app_config`), anyone who knows the `webhook_secret` for one onboarded organization can forge a fully self-crafted, correctly-signed webhook payload (signature covers the whole raw body, computed by the attacker) whose `repository.owner.login` names their own org (so verification passes) but whose `repository.full_name` names a different organization's repository, causing handlers like `PushHandler`, `StatusHandler`, and `CheckSuiteHandler` to act on a foreign `Stack`/`Repository` (e.g., forging passing CI status, or triggering sync jobs) that they should have no access to — potentially enabling an unauthorized deploy of that foreign stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
