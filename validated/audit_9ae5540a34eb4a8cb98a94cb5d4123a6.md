### Title
Cross-organization stack re-provisioning via decoupled `repository.owner.login` and `repository.full_name` in webhook payload - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/unlabeled_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook using `params.dig('repository','owner','login')`, but `UnlabeledHandler#repository` (and the base `Handler#stacks`) resolve the actual `Shipit::Repository`/`ReviewStack` to mutate using the independent field `params.repository.full_name`. Because these two JSON fields are never checked for consistency, an org that is a legitimate but distinct Shipit tenant can sign a payload with its own real webhook secret while naming a victim org's repository in `full_name`, causing `Shipit::ReviewStackProvisioningQueue.add` and `stack.unarchive!` to run against a repository/stack the signing org never authenticated for.

### Finding Description
The intended binding is: `org whose webhook_secret verified the HMAC (repository.owner.login) == org that owns the Shipit::Repository/ReviewStack being mutated (derived from repository.full_name)`.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` purely from `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) , then verifies the signature against `Shipit.github(organization: repository_owner).verify_webhook_signature`, which uses that org's own `webhook_secret` [3](#0-2) .
- Once verified, `WebhooksController#create` dispatches the raw parsed `params` (the full attacker-controlled JSON) to the handler, unmodified [4](#0-3) .
- `UnlabeledHandler`'s `ExplicitParameters` schema only requires presence of `repository.full_name`; it does not require or cross-check `repository.owner.login` at all [5](#0-4) .
- `UnlabeledHandler#repository` resolves the actual `Shipit::Repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5) , completely independent of the field used for signature verification.
- `handle` then calls `stack.unarchive!` when `unarchive?` is true per the resolved (victim) repository's `provisioning_behavior_allow_with_label?` policy [7](#0-6) [8](#0-7) , and `ReviewStackAdapter#unarchive!` calls `Shipit::ReviewStackProvisioningQueue.add(stack)` followed by `stack.unarchive!` inside a transaction [9](#0-8) .

Attacker request: the attacker controls "attacker-org", a distinct, legitimately-configured Shipit tenant (multiple orgs each with their own `webhook_secret`/GitHub App are a supported configuration, as shown in `config/secrets.development.shopify.yml` [10](#0-9) ). The attacker crafts an `unlabeled` pull_request payload JSON with `repository.owner.login: "attacker-org"` (so `verify_signature` fetches and checks against the attacker's own known `webhook_secret`) but `repository.full_name: "victim-org/prod-repo"`, and a PR `number` matching a real archived `ReviewStack` in the victim repo. The attacker signs this payload with their own secret and POSTs it to `/webhooks` with `X-Github-Event: pull_request`.

Existing guards do not stop this: `drop_unhandled_event` only filters unregistered event types; `verify_signature` verifies HMAC integrity against the wrong (attacker-controlled) org's secret because the org name it looks up is itself taken from the unauthenticated payload; the `ExplicitParameters` schema validates structure/types but never asserts `repository.owner.login == repository.full_name.split('/').first`; and no model validation in `Repository`/`Stack` enforces that resolution is scoped to the verifying org.

### Impact Explanation
A successful request causes `Shipit::ReviewStackProvisioningQueue.add` to enqueue re-provisioning and `stack.unarchive!` to run for a repository/stack belonging to an org that never authenticated the request — i.e., a payload from one repository/org mutating another org's stack, which re-triggers infrastructure provisioning (an unauthorized deploy-adjacent action) on victim infrastructure. This is repeatable against any archived `ReviewStack` in any victim repository whose `full_name` the attacker knows, as long as the victim repo has `provisioning_behavior_allow_with_label?` configured, across every tenant sharing the same Shipit instance. This matches the Critical category: "a payload for one repository mutating another's stack ... or an unauthorized deploy."

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment where the attacker legitimately controls one configured org/GitHub App (a supported, documented configuration), (2) the victim org's repository has `review_stacks_enabled` and `provisioning_behavior_allow_with_label?` set, and (3) an existing archived `ReviewStack` for a guessed/known PR number. Cost to the attacker is a single crafted HTTP POST using their own valid signature; no victim secrets are needed. Feasibility is high given the attacker fully controls the payload body and only needs knowledge of the victim's repository name and an in-scope PR number, both discoverable via public GitHub data.

### Recommendation
Bind repository resolution to the verified org: after `verify_signature` succeeds, require that the org derived from `params.repository.full_name` (the part before `/`) matches `repository_owner` used for verification, rejecting (422) on mismatch. Alternatively, resolve `Shipit::Repository` for webhook handlers scoped by the verified `repository_owner` rather than trusting `full_name` alone, and add this consistency check as a `before_action` in `WebhooksController` shared by all handlers.

### Proof of Concept
Add a minitest to `test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/unlabeled_handler_test.rb`:
1. Configure two orgs in test secrets: `attacker-org` (with a known `webhook_secret`) and `victim-org` (owning `shipit_repositories(:shipit)`, full_name `victim-org/prod-repo`).
2. Create and archive a `ReviewStack` for `victim-org/prod-repo` PR #N with `provisioning_behavior_allow_with_label?` true and the provisioning label present in the payload.
3. Build a JSON payload for event `pull_request`/action `unlabeled` with `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/prod-repo"`, `number = N`.
4. Sign the payload with `attacker-org`'s webhook secret and set `X-Hub-Signature`.
5. POST to `/webhooks` with `X-Github-Event: pull_request`.
6. Assert response is `:ok` (not `422`), and assert `Shipit::ReviewStackProvisioningQueue.expects(:add).with(stack_belonging_to_victim_org)` is invoked / assert `stack.reload.archived?` is `false` — proving `repository_owner` ("attacker-org") used to verify the signature diverges from the org actually mutated ("victim-org"), demonstrating the equality claimed in the binding does not hold.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
