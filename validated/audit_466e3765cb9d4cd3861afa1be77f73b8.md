The core of this question is whether the round byte in `header.Extra` is truly authenticated by 2F+1 validator signatures. Let me trace the exact code path.

**Step 1: How `pfReport` reads the round**

`pfReport` in `kaiax/vrank/impl/getter.go` reads the round via `v.RoundReader.Round(header)`, which resolves to `IstanbulSealer.Round`:

The round is the last byte of the vanity area in `header.Extra`. [1](#0-0) 

**Step 2: Is the round byte covered by signatures?**

The README claims: *"It cannot be forged because the round byte is part of the header hash that 2F+1 validators sign with their committed seals."*

But `istanbulFilteredHeader` — used to compute both `SigHash` and `HeaderHash` — **explicitly zeroes the round byte before hashing**:

```go

Neither the proposer seal (over `SigHash`) nor the committed seals (over `HeaderHash`) cover the round byte. The README's claim is factually incorrect per the code.

**Step 3: What guard does `verifySeals` actually provide?**

In the permissionless path, `verifySeals` does check the round — but differently:

```go

``` [3](#0-2) 

This check requires: (a) `Author(header) == GetProposer(blockNum, inflated_round)`, and (b) committed seals satisfy quorum for the inflated round's committee.

**Step 4: Can both guards be bypassed?**

- **Guard (a)**: The proposer seal is signed over `SigHash` which zeroes the round byte, so `Author(header)` always recovers the actual signer regardless of the round byte. The check passes if and only if the attacker is also the proposer at the inflated round. Since the proposer list is deterministic and public, a byzantine validator can inspect it and pick an inflated round where they appear as proposer.

- **Guard (b)**: The committed seals are signed over `HeaderHash` which also zeroes the round byte, so the same committed seals are cryptographically valid for any round value. The committee check passes if the committee at the inflated round is a superset of (or equal to) the committee at the actual round. When `CommitteeSize >= len(qualified)` — i.e., the committee is the full qualified validator set — the committee is identical for all rounds and this check always passes.

**Step 5: Attack feasibility**

A single byzantine validator who is the proposer at actual round R can:
1. Inspect the proposer list and find round R+K where they are also the proposer.
2. Set `header.Extra[IstanbulExtraVanity-1] = R+K`.
3. The block passes `verifySeals`: author matches proposer at round R+K, and committed seals (signed over the round-zeroed hash) satisfy the committee quorum.
4. `pfReport` enumerates proposers for rounds `[0, R+K)` instead of `[0, R)`, falsely adding proposers at rounds `R..R+K-1` to the failure list.
5. `applyBlocksForPFS` increments PFS scores for those proposers. [4](#0-3) 
6. `fetchVRankCtx` in valset uses these inflated PFS scores in the next epoch-boundary state transition, affecting validator reward distribution. [5](#0-4) 

**Conclusion: The attack requires a single byzantine validator (no majority collusion) who is the proposer at the inflated round, and a committee that does not shrink between rounds. This is within the threat model.**

### Title
Round Byte Unauthenticated in Committed Seals Allows Byzantine Proposer to Inflate PFS Scores and Manipulate Validator Rewards — (`kaiax/vrank/impl/getter.go`, `consensus/istanbul/sealer.go`)

### Summary
The Istanbul consensus round byte stored at `header.Extra[IstanbulExtraVanity-1]` is zeroed before computing both `SigHash` and `HeaderHash`, meaning it is not covered by the proposer seal or the 2F+1 committed seals. A byzantine block proposer who also appears as proposer at a higher round can write an inflated round value into the header, pass `verifySeals`, and cause `pfReport` to falsely enumerate proposers for rounds that never failed — inflating their PFS scores and corrupting validator reward distribution at the next epoch boundary.

### Finding Description
`istanbulFilteredHeader` (used by both `SigHash` and `HeaderHash`) unconditionally zeroes `newHeader.Extra[IstanbulExtraVanity-1]` before hashing. [6](#0-5)  This means neither the proposer's ECDSA seal nor the 2F+1 committed seals authenticate the round byte. The `verifySeals` check in `block_validator.go` does read the round byte and checks `Author == GetProposer(blockNum, round)`, but since `Author` is recovered from a seal over the round-zeroed `SigHash`, the check passes whenever the attacker is the proposer at the inflated round — a condition the attacker can arrange by inspecting the deterministic proposer list. [7](#0-6) 

`pfReport` then iterates `r ∈ [0, round)` and calls `GetProposer(blockNum, r)` for each, appending all results to the failure list. [8](#0-7)  With an inflated round, proposers who never failed are included. `applyBlocksForPFS` accumulates these into the PFS map, and `fetchVRankCtx` feeds the corrupted PFS into the valset transition at epoch boundaries, altering reward shares. [5](#0-4) 

### Impact Explanation
Falsely elevated PFS scores cause legitimate proposers to be penalized at epoch-end state transitions, reducing or eliminating their validator reward shares. This constitutes unauthorized manipulation of KAIA reward distribution — an in-scope impact. Up to `maxRound - 1` proposers can be falsely penalized per manipulated block.

### Likelihood Explanation
Requires a single byzantine validator who (a) is selected as proposer at the actual round and (b) also appears as proposer at some higher round in the same block's proposer list. Both conditions are deterministic and inspectable in advance. No majority collusion, key compromise, or external service access is needed. The attack is repeatable every time the attacker is selected as proposer.

### Recommendation
Include the round byte in the signed hash. Remove the `newHeader.Extra[IstanbulExtraVanity-1] = 0` line from `istanbulFilteredHeader` so that `SigHash` and `HeaderHash` cover the actual round value. Alternatively, encode the round in the RLP payload (alongside `Validators`, `Seal`, `CommittedSeal`) so it is covered by the existing signature scheme. The `verifySeals` check alone is insufficient because it only constrains the author identity, not the round value itself.

### Proof of Concept
1. Deploy a 4-validator permissionless-fork chain. Validator V is proposer at round 0 for block N, and also proposer at round 3 for block N (from the proposer list).
2. V produces block N normally (actual round 0), collects 2F+1 committed seals.
3. V overwrites `header.Extra[IstanbulExtraVanity-1] = 3` before broadcasting.
4. `verifySeals`: `Author(header)` = V; `GetProposer(N, 3)` = V → passes. Committee is full validator set → committed seals satisfy quorum → passes.
5. Call `GetPfReport(N)`: returns `[Proposer(N,0), Proposer(N,1), Proposer(N,2)]` — three entries instead of zero.
6. Call `GetPFS(N)`: PFS scores for those three proposers are incremented by 1 each, despite none of them having failed.

func istanbulFilteredHeader(h *types.Header, keepSeal bool) *types.Header {
	newHeader := types.CopyHeader(h)
	if len(newHeader.Extra) < IstanbulExtraVanity {
		return nil
	}
	var istanbulExtra *IstanbulExtra
	err := rlp.DecodeBytes(newHeader.Extra[IstanbulExtraVanity:], &istanbulExtra)
	if err != nil {
		return nil
	}

	if !keepSeal {
		istanbulExtra.Seal = []byte{}
	}
	istanbulExtra.CommittedSeal = [][]byte{}

	payload, err := rlp.EncodeToBytes(istanbulExtra)
	if err != nil {
		return nil
	}
	newHeader.Extra[IstanbulExtraVanity-1] = 0
	newHeader.Extra = append(newHeader.Extra[:IstanbulExtraVanity], payload...)
	return newHeader
