### Title
Unsolicited `new_shared_address` device message is accepted without verifying it corresponds to a shared-address creation the local wallet ever initiated or approved - ([File: wallet_defined_by_addresses.js])

### Summary
`handleNewSharedAddress()` in `wallet_defined_by_addresses.js` [1](#0-0)  is invoked by `wallet.js` whenever a paired correspondent device sends a `"new_shared_address"` message [2](#0-1) . This handler accepts and permanently records a brand-new multi-signature address definition as one of the wallet's own "shared addresses" as long as (a) the given definition hashes to the given address, (b) every `["address", ...]` leaf in the definition has a matching entry in the `signers` map, and (c) the local device's own address appears somewhere among the member addresses. It never checks that the local wallet previously initiated (`createNewSharedAddressByTemplate`) or approved (`approvePendingSharedAddress`) the creation of *this specific* shared address, nor does it correlate the message with any `pending_shared_addresses`/`pending_shared_address_signing_paths` row created by a genuine `create_new_shared_address` → `approve_new_shared_address` handshake. This is structurally analogous to the Casdoor SAML flaw: a "response" message is accepted as legitimate purely because it is well-formed and self-consistent, without verifying it corresponds to a previously issued, locally-tracked request.

### Finding Description
The legitimate multi-party flow for creating a shared (multisig) address is:
1. Initiator calls `createNewSharedAddressByTemplate`, which stores a `pending_shared_addresses` row and asks each member device to approve via `create_new_shared_address` [3](#0-2) .
2. Members approve via `approve_new_shared_address`, tracked per `definition_template_chash` in `pending_shared_address_signing_paths` [4](#0-3) .
3. Once all approvals are collected, the initiator sends the final `new_shared_address` message to every member.

However, `handleNewSharedAddress()` (which processes the *final* `new_shared_address` message) is completely decoupled from steps 1–2. It performs only local structural validation of the message itself:
```
if (body.address !== addr) return callbacks.ifError(...);
... // signer addresses match "address" leaves in the definition
determineIfIncludesMeAndRewriteDeviceAddress(body.signers, ...);
validateAddressDefinition(body.definition, ...);
addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
``` [1](#0-0) 

There is no lookup of `pending_shared_addresses`/`pending_shared_address_signing_paths` to confirm this address/definition was ever requested by the local user, no binding to a `definition_template_chash` the user approved, and no requirement that the sender (`from_address`) is the same device that made the original offer. `determineIfIncludesMeAndRewriteDeviceAddress` only checks that *some* address in the definition belongs to the local wallet or a shared address it already knows about [5](#0-4) ; it does not verify provenance of the request. `validateAddressDefinition` only checks oscript syntactic/semantic validity of the definition, not whether it grants the attacker unilateral control [6](#0-5) .

Because `extractAddressPathsFromDefinition` only extracts leaves at the `address`, `hash`, and `in merkle` operators [7](#0-6) , an attacker (any already-paired correspondent — e.g. a chat contact, textcoin claimant, or arbiter counterparty) can craft a definition such as:
```
["or", [
  ["address", VICTIM_ADDRESS],
  ["sig", {pubkey: ATTACKER_PUBKEY}]
]]
```
supplying `signers = {"r.0": {address: VICTIM_ADDRESS, device_address: VICTIM_DEVICE_ADDRESS}}` — this satisfies every check in `handleNewSharedAddress` (the single `address` leaf has a matching signer entry, and the local device is "included" via that address), yet the actual spending condition is an `or`, meaning the attacker's `sig` branch alone can authorize spending, without ever needing the victim's cooperation. The wallet nonetheless records this address in `shared_addresses` / `shared_address_signing_paths` [8](#0-7)  and treats it as if it were a jointly-controlled address the user had actually agreed to create.

### Impact Explanation
Any funds a victim wallet subsequently sends to (or receives at, believing it is a legitimate cooperative multisig/business address) this bogus "shared address" can be spent unilaterally by the attacker through the `sig`/`or` branch, since the definition never truly requires the victim's signature. This yields direct unauthorized loss of funds sent to an address the wallet UI represents as jointly controlled — a concrete unauthorized-spending outcome reachable from a single unsolicited device message sent by any already-paired correspondent, without any confirmation that the local user ever requested or approved creation of that shared address.

### Likelihood Explanation
The attacker only needs to be a paired correspondent of the victim (a low bar — e.g. established via a legitimate chat, textcoin transfer, or arbiter contract pairing) and to send one crafted `new_shared_address` justsaying message. No prior request from the victim, no race condition, and no privileged network position is required; the handler processes the message unconditionally once basic self-consistency checks pass.

### Recommendation
Bind acceptance of `new_shared_address` to a locally tracked pending request: require that `body.address_definition_template_chash` (or an equivalent identifier of the original template) exists in `pending_shared_addresses`/`pending_shared_address_signing_paths`, that the sending `from_address` matches the expected initiator, and that all `signers` device addresses match those the local user actually approved for that specific pending template — mirroring the check already used in `approvePendingSharedAddress`. Reject `new_shared_address` messages that do not correspond to any outstanding, locally-initiated/approved shared-address creation.

### Proof of Concept
1. Attacker device A pairs with victim device V (e.g., through a normal chat pairing or textcoin exchange).
2. Attacker crafts `arrDefinition = ["or", [["address", V_ADDRESS], ["sig", {pubkey: A_PUBKEY}]]]` and computes `address = chash160(arrDefinition)`.
3. Attacker sends V a `"new_shared_address"` device message: `{address, definition: arrDefinition, signers: {"r.0": {address: V_ADDRESS, device_address: V_DEVICE_ADDRESS}}}`.
4. `wallet.js`'s `new_shared_address` case calls `walletDefinedByAddresses.handleNewSharedAddress(body, ...)` [2](#0-1) , which passes all checks (hash matches, signer entry matches the sole `address` leaf, V's address is a member) and calls `addNewSharedAddress`, persisting the address as a shared address of V's wallet [8](#0-7) .
5. V's wallet UI now shows this address as a shared/multisig address involving V. If V (or a third party believing it's a cooperative address) sends funds there, attacker A can immediately spend them alone via the `sig` branch — no cooperation from V's key is required, despite V believing the address requires joint control.

// Checks if any of my payment addresses is mentioned.
// It is possible that my device address is not mentioned in the definition if I'm a member of multisig address, one of my cosigners is mentioned instead
function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

// Returns a map of signing_path -> address for every ["address", ...] leaf in the definition
function extractAddressPathsFromDefinition(arrDefinition) {
	var result = {};
	function traverse(arr, path) {
		if (!Array.isArray(arr) || arr.length < 2) return;
		var op = arr[0];
		var args = arr[1];
		switch (op) {
			case 'or':
			case 'and':
				if (Array.isArray(args))
					for (var i = 0; i < args.length; i++)
						traverse(args[i], path + '.' + i);
				break;
			case 'r of set':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i], path + '.' + i);
				break;
			case 'weighted and':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i].value, path + '.' + i);
				break;
			case 'address':
				result[path] = args;
				break;
			case 'hash':
				result[path] = 'secret';
				break;
			case 'in merkle':
				result[path] = ''; // empty address
				break;
		}
	}
	traverse(arrDefinition, 'r');
	return result;
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
