### Title
`StatusHandler#process` never re-validates repository ownership per request, so a replayed/forged `status` webhook can repeatedly overwrite a target commit's CI status - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by SHA (`Commit.where(sha: params.sha)`), with no check that the payload's `repository.full_name`/`owner` matches the commit's own stack/repository. `Commit#create_status_from_github!` → `Status.replicate_from_github!` then unconditionally `find_or_create_by!`s a new `Status` row from attacker-supplied `state`/`description`/`created_at`, with no ownership re-verification per call. Once a single forged request is accepted for a given org context (via any prior org-confusion/signature path), every subsequent replay with a different `state`/`created_at` is processed identically and immediately becomes the commit's "current" status.

### Finding Description
The binding that should hold is: `commit.status.state == state written by the last request whose payload.repository.owner matches commit.stack.repository.owner`. In the actual code this binding is broken because nothing in the write path checks repository/stack ownership per Status write:

- `WebhooksController#verify_signature` only authenticates that *some* signature matches *some* org's `webhook_secret`, extracted from `repository_owner` in the current payload [1](#0-0) . It does not bind that org to the specific commit/stack being mutated.
- `StatusHandler#process` loads commits by SHA only, with no filter on `repository_name`/stack, unlike other handlers (e.g. `PullRequest::LabelCapturingHandler`) that scope through `stacks`/`repository_name`: [2](#0-1) 
- `Commit#create_status_from_github!` → `Status.replicate_from_github!` performs a bare `find_or_create_by!` keyed on `state`, `description`, `target_url`, `context`, `created_at` — every distinct `state`/`created_at` combination creates a brand-new `Status` row with no re-check of who is allowed to write it: [3](#0-2) [4](#0-3) 
- The "current" status per CI `context` is derived purely from ordering: `has_many :statuses, -> { order(created_at: :desc) }` and `Status::Group#initialize` does `statuses.to_a.uniq(&:context)`, keeping the *first* (i.e., most-recent-by-`created_at`) row per context: [5](#0-4) [6](#0-5) . `created_at` is an attacker-controlled string field accepted by the handler (`accepts :created_at, String`), so an attacker can always set a `created_at` that beats any real CI timestamp, guaranteeing their forged status remains the "significant" one indefinitely.

Because none of these steps persist or re-check any binding between "the org that authenticated this particular request" and "the org that owns the commit/stack being written," a forged request, once accepted for any reason (e.g. a prior signature/org-confusion bypass), can be replayed an unlimited number of times with arbitrary `state` values, and each replay independently succeeds and independently determines the commit's displayed/gating status.

### Impact Explanation
Each successful forged/replayed request creates a new `Status` row on the victim commit and, through `Status::Group`'s "most recent per context" selection, immediately becomes the value read by `Commit#deployable?` (`success? && !blocked?`) and surfaced in the UI/API [7](#0-6) . This is repeatable indefinitely and against any commit whose SHA the attacker knows (SHAs are not secret), enabling persistent deploy-gate manipulation (e.g., forcing `success` to unblock a deploy, or forcing `failure`/`error` to block one) on another organization's stack — this matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback."

### Likelihood Explanation
This finding is conditioned on the attacker already having one accepted forged `status` webhook for the target commit (via a signature/org-confusion path established elsewhere, out of scope for this specific question). Given that precondition, replay is trivial and cheap: it is a stateless HTTP POST with no additional secret, token, or session required, and the handler and model layers apply no per-write ownership re-check or idempotency guard, so repetition is unrestricted and deterministic.

### Recommendation
In `StatusHandler#process`, scope commit lookup to the repository named in the payload (e.g., via `stacks`/`Repository.from_github_repo_name(repository_name)`) instead of a global `Commit.where(sha: params.sha)`, and reject/ignore statuses for commits whose `stack.repository` does not match the payload's `repository.full_name`/owner. Additionally, do not trust the attacker-supplied `created_at` for ordering/selecting the "current" status; use server-received time or validate it is monotonic and bounded.

### Proof of Concept
```ruby
# test/models/commits_test.rb (conceptual addition)
test "create_status_from_github! is not idempotent/ownership-guarded and can be replayed to override status" do
  commit = shipit_commits(:first) # belongs to org A's stack

  # Simulate first forged request (already accepted via assumed org-confusion elsewhere)
  commit.create_status_from_github!(OpenStruct.new(
    state: 'success', description: 'forged-1', context: 'ci/forged',
    created_at: 10.years.from_now.to_formatted_s(:db), target_url: nil
  ))
  assert_equal 'success', commit.reload.state

  # Replay with a different forged state - no ownership re-check occurs
  commit.create_status_from_github!(OpenStruct.new(
    state: 'failure', description: 'forged-2', context: 'ci/forged',
    created_at: 20.years.from_now.to_formatted_s(:db), target_url: nil
  ))

  # Binding check: latest status reflects the second forged (non-owning-org) request,
  # demonstrating unrestricted repeatable override with no re-verification.
  assert_equal 'failure', commit.reload.state
end
```
This demonstrates that `create_status_from_github!`/`Status.replicate_from_github!` will accept and apply an unlimited sequence of forged updates for the same commit with no ownership re-check, and that the attacker fully controls which value is treated as "current" via the `created_at` field.
