### Title
`StatusHandler#process` writes commit statuses via a global `Commit.where(sha:)` lookup with no repository/stack scoping - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` inherits `Handler#repository_name` and `Handler#stacks` from `app/models/shipit/webhooks/handlers/handler.rb` but never calls either in `#process`. Instead it resolves target rows with a bare `Commit.where(sha: params.sha)`, which matches any commit row in the entire database sharing that SHA, regardless of which repository's status event triggered the webhook.

### Finding Description
Broken binding as an equality:
- Claimed-safe binding: `self.stacks.joins(:commits).where(sha: params.sha)` (scoped to the repository identified by `payload.dig('repository','full_name')`).
- Actual binding in code: `Commit.where(sha: params.sha)` (global, unscoped) — [1](#0-0) .

These are not equal: the base `Handler` class defines both helpers explicitly for this purpose — [2](#0-1)  — and `StatusHandler` simply omits using them, unlike a repository-safe implementation would.

Root cause: `Commit.sha` is only unique within the context of a stack/repository's own git history in Shipit's data model (`belongs_to :stack` on `Commit`, no global uniqueness constraint enforced at this layer) — [3](#0-2) . Multiple stacks tracking related repositories (e.g. forks sharing ancestor commits, or mirrors) can have `Commit` rows with identical `sha` values. `StatusHandler#process` mutates every row matching that SHA via `commit.create_status_from_github!(params)` — [4](#0-3)  — which writes a new `Status` and fires `Hook.emit(:commit_status, ...)`/`:deployable_status` and can trigger `stack.schedule_merges`, i.e. actual state mutation and downstream automation (continuous delivery/merge scheduling) for a stack the incoming webhook's repository did not identify — [5](#0-4) .

Exploit path: The webhook is only accepted after `WebhooksController#verify_signature`, which validates the signature using `Shipit.github(organization: repository_owner)` where `repository_owner` is taken from the *incoming* payload's `repository.owner.login` — [6](#0-5) [7](#0-6) . This only proves the event genuinely originated from GitHub for *some* repository under an org/account already configured in Shipit — it says nothing about which stack's commits should be touched. Once past signature verification, `StatusHandler.call(params)` runs unscoped, so a status event for repository B's commit with SHA `X` will update every `Commit` row with `sha = X`, including ones belonging to unrelated stack A, if such a collision exists (most realistically via a fork/mirror sharing git ancestry, since SHA-1 values are deterministic over commit content and identical for shared history).

Why other guards don't help: `drop_unhandled_event`/`check_if_ping` only filter event types; `ExplicitParameters` (`params do ... end`) only validates payload shape, not repository identity; there is no `require_permission!`/`stacks.find_by!` equivalent inside `StatusHandler#process` to bind the mutation back to the repository that the (now-verified) webhook actually came from.

### Impact Explanation
A validly-signed status webhook for one repository can cause a `Status` record to be created/mutated on a `Commit` belonging to a completely different `Stack`, and can trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`, i.e. it can influence continuous-delivery/merge behavior of a stack the attacker's repository has no relationship with. This matches the "payload for one repository mutating another's stack/commit/task" Critical category, since it is a write, not merely a read, and is repeatable against any commit SHA collision the attacker can arrange (e.g., via a fork sharing ancestor commits already tracked as a `Commit` row for the victim stack).

### Likelihood Explanation
Exploitation requires: (1) the attacker's own repository/org must already be a trusted GitHub App/webhook-secret scope known to `Shipit.github(organization: ...)` (otherwise `verify_signature` raises `Shipit::GithubOrganizationUnknown` and the request is rejected with 422), and (2) a `Commit.sha` collision between the attacker-controlled repository and the victim stack's tracked commits — realistically achievable only through shared git ancestry (fork/mirror relationship) rather than a raw SHA-1 collision. This narrows real-world feasibility to multi-repo/multi-stack deployments sharing the same GitHub organization/app installation where forks or mirrored histories exist; it is not exploitable from an arbitrary, unrelated internet attacker with no relationship to the target org's GitHub App installation.

### Recommendation
Scope the lookup in `StatusHandler#process` to the requesting repository, e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or equivalently iterate `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`, using the inherited `Handler#stacks`/`#repository_name` helpers so the mutation is bound to the stack(s) that belong to the repository identified in the verified payload.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
test "#process only mutates commits belonging to the reporting repository's stacks" do
  victim_stack = shipit_stacks(:shipit)
  attacker_repo = Shipit::Repository.create!(owner: 'attacker-org', name: 'evil-fork')
  attacker_stack = Shipit::Stack.create!(repository: attacker_repo, environment: 'production')

  shared_sha = victim_stack.commits.first.sha
  Shipit::Commit.create!(stack: attacker_stack, sha: shared_sha, message: 'shared ancestor')

  payload = {
    'repository' => { 'full_name' => attacker_repo.full_name },
    'sha' => shared_sha,
    'state' => 'success'
  }

  handler = Shipit::Webhooks::Handlers::StatusHandler.new(payload)
  handler.expects(:stacks).never # StatusHandler never scopes via #stacks

  assert_no_difference -> { victim_stack.commits.first.statuses.count } do
    handler.process
  end
end
```
This demonstrates the binding inequality: `Commit.where(sha:)` (global) mutates the victim stack's commit status even though the payload's `repository.full_name` names only the attacker's repository, and `#stacks`/`#repository_name` are never invoked to scope the write.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
