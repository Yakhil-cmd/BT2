## Analysis: Unrestricted `BlockRevenue` commission-in-basis-points update enables front-running of delegator rewards

The reported bug class — an admin instantly setting a fee to 100% right before a payout is computed, stealing the counterparty's share — has a concrete analog in Agave's vote-account commission logic, specifically for the **`BlockRevenue`** commission kind introduced by SIMD-0123/SIMD-0291.

### Root cause

`update_commission_bps` in `programs/vote/src/vote_state/mod.rs` explicitly removes the epoch-timing restriction that protects the legacy commission field: [1](#0-0) 

The comment at line 844, `// No commission update rule, per SIMD-0249 and SIMD-0291.`, states this is intentional for both `InflationRewards` and `BlockRevenue` commission kinds — the authorized withdrawer can change the commission at any slot, with no restriction to "first half of epoch" like the legacy `update_commission` enforces via `is_commission_update_allowed`.

`vote_processor.rs` confirms `UpdateCommissionBps` dispatches directly to `update_commission_bps` with no additional timing gate, only feature-activation checks: [2](#0-1) 

For the legacy commission field and for `InflationRewards` bps, this removal of the in-instruction timing rule is safe because the runtime **separately delays the effective commission by reading it from a snapshot taken a full epoch earlier** (`snapshot_epoch_vote_accounts`), as seen in `redeem_delegation_rewards`: [3](#0-2) 

`CachedVoteAccounts` documents this protection explicitly ("saved a full epoch before being used to prevent last minute commission rugs"): [4](#0-3) 

However, `calculate_block_reward` — the function that computes each delegator's share of SIMD-0123 block revenue — reads from `distribution_epoch_vote_accounts`, i.e. the **live/current-epoch vote account state**, not the epoch-delayed snapshot used for inflation rewards: [5](#0-4) [6](#0-5) 

This means there is no analogous delay mechanism protecting `block_revenue_commission_bps` the way there is for `inflation_rewards_commission_bps`. Combined with the removal of the in-instruction timing rule, a vote account's authorized withdrawer can call `UpdateCommissionBps { kind: BlockRevenue, commission_bps: 10_000 }` immediately before block-revenue accrual/distribution to capture 100% of `pending_delegator_rewards` that should be split with delegators, then revert the commission afterward — directly mirroring the `PumpV1.setFeeRate` front-running pattern (unbounded fee, no timelock, front-runnable to steal the counterparty's share).

### What I could not fully verify

I was unable to inspect the full body of the `DepositDelegatorRewards` instruction handler (only its dispatch entry was visible) or the exact code path that splits `pending_delegator_rewards` using `block_revenue_commission_bps` at deposit/accrual time. This means I can describe the mechanism with confidence (unrestricted, non-delayed commission for `BlockRevenue`) but cannot cite the exact line where the commission split against `pending_delegator_rewards` occurs. Given the ask-only mode and no further tool calls being available, this should be verified directly in `programs/vote/src/vote_processor.rs` (`VoteInstruction::DepositDelegatorRewards` handler) and wherever `pending_delegator_rewards` is populated/split before being read by `calculate_block_reward`.

Because this analysis requires code changes to confirm and potentially fix, and per current instructions I am in ask-only mode, I have not produced a plan. If you want a background agent to add a delay mechanism for `block_revenue_commission_bps` analogous to the inflation-commission snapshot, or to confirm the exploit path in `DepositDelegatorRewards`, let me know and I can prepare a plan for that.

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
