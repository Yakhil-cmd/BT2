### Title
Denial of Service via Front-Running of Shared Oracle `last-update` Cache - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
Any address can advance the global, per-oracle-identifier `last-update` timestamp cache in `market.clar` simply by submitting a fresh price feed as part of an unrelated public call (`collateral-add`, `borrow`, `liquidate`, `supply-collateral-add`, etc.). Because `price-resolve` requires the caller's own embedded price feed timestamp to be `>=` the value currently stored in this shared cache, an attacker can front-run any other user's pending transaction with a marginally newer price update, causing the victim's transaction — built with an equally valid but now "stale-relative" price feed — to revert with `ERR-ORACLE-INVARIANT`.

### Finding Description
`market.clar` maintains a single, asset-identifier-keyed map that is written and read by every unauthenticated caller: [1](#0-0) 

Price resolution enforces monotonicity against this shared value: [2](#0-1) [3](#0-2) 

`oracle-timestamp-fresh` rejects any submitted price whose timestamp is *older* than what is already recorded for that `{type, ident}` key (`(>= ts prev)`), and `price-resolve` unconditionally advances `last-update` whenever a newer timestamp is observed — from *any* caller, not just the one who "owns" the pending operation. Every state-changing entrypoint that accepts an optional `price-feeds` argument (`borrow`, `collateral-add`, `collateral-remove`, `liquidate`, `supply-collateral-add`, etc.) funnels into this same shared map via `write-feeds`/`price-resolve`.

Because Pyth/DIA price update payloads are public data (not tied to any specific submitter), an attacker can:
1. Observe a victim's pending transaction (e.g., `borrow` or `liquidate`) in the mempool, which embeds a valid price feed with timestamp `T1`.
2. Front-run it with any trivial call of their own (e.g., a 1-unit `collateral-add`) embedding a slightly newer valid price feed with timestamp `T2 > T1` for the same asset identifier, which sets `last-update[key] = T2`.
3. When the victim's original transaction executes, `oracle-timestamp-fresh(T1, T2, max-staleness)` evaluates `T1 >= T2` as `false`, so `price-resolve` returns `ERR-ORACLE-INVARIANT` and the victim's entire transaction reverts.

This is directly analogous to the reported bug class: a piece of state (there, `_userLoans[loanId].isActive`; here, `last-update[{type, ident}]`) is shared across unrelated, unprivileged callers, and whoever writes it first can force a subsequent, otherwise-valid transaction from a different user to revert.

### Impact Explanation
The most damaging application of this is against liquidations. A borrower with an unhealthy position (or a colluding third party) can watch the mempool for a liquidator's `liquidate` call — which necessarily embeds a fresh price feed to pass the health check: [4](#0-3) 

and can repeatedly front-run each liquidation attempt with a marginally newer (but otherwise legitimate) price update for the same asset. Every such front-run forces the liquidator's `price-resolve` call to fail on the freshness monotonicity check and the whole `liquidate` transaction to revert, without the attacker needing any special privilege and without cost beyond a trivial deposit/repay transaction. Repeated indefinitely (each block, a new front-run), this can indefinitely stall liquidation of an under-collateralized position while its collateral value continues to deteriorate, increasing bad-debt risk and threatening protocol insolvency — landing in the Critical impact category. At minimum, it grants victims (any user submitting `borrow`/`collateral-add`/`liquidate` with embedded price feeds) reliably griefable, gas-wasting transaction failures.

### Likelihood Explanation
Likelihood is high: the attack requires no special access, no flashloan, and no privileged role — only the ability to observe pending transactions and submit a cheap transaction with a marginally newer, still-valid price update for the targeted asset before the victim's transaction is mined. Pyth/DIA feed updates for major assets are published frequently, so an attacker nearly always has access to a "fresher" valid feed to use for the front-run.

### Recommendation
Do not enforce global cross-caller timestamp monotonicity for oracle freshness. Freshness should be validated purely against the current transaction's own embedded feed and `stacks-block-time`/`max-staleness` (as already partially done via `oracle-timestamp-fresh`'s delta check), without requiring the submitted timestamp to be `>=` a globally-shared, arbitrarily-advanceable `last-update` value written by unrelated callers. If the monotonicity check exists to prevent price regression (e.g., stale zToken index caching), scope that state per-transaction/per-block context rather than as a persistent cross-user map, or allow a caller's own feed to be accepted as long as it satisfies staleness bounds independent of what other unrelated callers most recently wrote.

### Proof of Concept
1. Borrower Alice's position is unhealthy; Liquidator Bob submits `liquidate(alice, ...)` embedding a Pyth price update with timestamp `T1` for asset X, sufficient to make Alice's position liquidatable.
2. Alice (or a colluder) observes Bob's pending transaction and submits a trivial `collateral-add`/`supply-collateral-add` call for a different (or even the same) asset, embedding a newer valid Pyth update for asset X with timestamp `T2 > T1`. This transaction is mined first, setting `last-update[{TYPE-PYTH, ident-X}] = T2` via `price-resolve` (`mainnet/contracts/market/v0-4-market.clar:373-395`).
3. Bob's `liquidate` transaction is then processed: `price-resolve` calls `oracle-timestamp-fresh(T1, T2, max-staleness)`, which returns `false` because `T1 < T2` (`mainnet/contracts/market/v0-4-market.clar:365-371`), so the call returns `ERR-ORACLE-INVARIANT` and the entire `liquidate` transaction reverts.
4. Alice's under-collateralized position survives the block; Alice/collaborator repeats step 2 in subsequent blocks to keep stalling liquidation attempts against Bob (or any other liquidator) at negligible cost to herself.

```text
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
```
