### Title
Unbounded `borrowed * borrow_index` arithmetic permanently freezes an oversized market - (File: `common/src/rates/simulate.rs`)

### Summary
The pool’s interest-accrual path multiplies scaled debt by the borrow index before applying the configured `MAX_BORROW_INDEX_RAY` cap. On a sufficiently large market, `scaled_to_original(borrowed, borrow_index)` can exceed `i128::MAX` while `borrow_index` remains below its cap, causing `MathOverflow`. Because mutating pool paths synchronize interest first, the panic can permanently block withdrawals, repayments, liquidations, and further index updates for that market.

### Finding Description
The permissionless controller entrypoint `update_indexes(env, caller, assets)` forwards caller-selected `HubAssetKey` values to the pool after only caller authorization. [1](#0-0) [2](#0-1) 

Pool accrual calls `accrue_step` for each elapsed chunk. [3](#0-2)  The first step computes `borrowed_original` as `scaled_to_original(env, borrowed, borrow_index)` before calculating the new index. [4](#0-3)  `scaled_to_original` delegates to `Ray::mul`, which calls the non-saturating `mul_div_half_up` primitive and panics with `MathOverflow` when the result cannot fit in `i128`. [5](#0-4) [6](#0-5) 

The intended borrow-index ceiling is `1e36` raw RAY, but the code applies that cap only after `borrowed * borrow_index` has already been evaluated for utilization. [7](#0-6) [8](#0-7)  Consequently, total debt value can cross the `i128` value ceiling while every persisted share count and index individually remains within its configured domain.

The repository’s own regression scenario demonstrates the failure: a one-billion-token, 18-decimal market at 98% utilization eventually makes `try_update_indexes_for(["BIG18"])` fail with `MATH_OVERFLOW`, while the stored `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. [9](#0-8) 

### Impact Explanation
This is permanent freezing of user funds for the affected market. The regression test verifies that after the accrual panic, both a withdrawal and a repayment fail with `MATH_OVERFLOW`. [10](#0-9)  The same accrual-before-mutation design also prevents later liquidations and index synchronization from bypassing the overflowing value calculation. [11](#0-10) 

Suppliers cannot recover deposits, borrowers cannot close debt, and liquidators cannot safely resolve distressed positions. Since `update_indexes` is permissionless, any unprivileged caller can trigger the first accrual that reaches the overflow boundary once market size, utilization, and elapsed time place the product over `i128::MAX`. [1](#0-0) 

### Likelihood Explanation
Likelihood is conditional on an unusually large market and sustained high utilization, but it does not require privileged access or oracle manipulation. A market can reach the dangerous state through ordinary `supply` and `borrow` calls, after which a single `update_indexes(caller, vec![hub_asset])` call exercises the vulnerable multiplication. [12](#0-11) [1](#0-0) 

The triggering state is economically significant rather than technically exotic: the test uses a one-billion whole-token market with 18 decimals and 98% borrowed. [13](#0-12)  Once such state exists organically, the attacker only has to submit the permissionless accrual transaction; they do not need to own the trapped funds. This supports a High finding.

### Recommendation
Bound the RAY-denominated position values before multiplication, or make the accrual path use a checked/saturating value calculation that clamps `borrow_index` before evaluating `borrowed * borrow_index`.

At minimum:

1. In `accrue_step`, detect that `borrowed` is nonzero and `borrow_index` is above `i128::MAX / borrowed`, then clamp the effective borrow index to `MAX_BORROW_INDEX_RAY` or another protocol-defined safe index before calling `scaled_to_original`.
2. Apply the same ordering to `supplied * supply_index` so the supply side cannot independently hit the same value ceiling.
3. Add an invariant or pre-accrual assertion that scaled shares multiplied by their capped indexes remain representable.
4. Keep the regression in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`, but change its expectation so accrual clamps rather than reverting and subsequent withdrawal/repayment succeeds.

The fix should preserve the existing accounting invariant that indexes remain capped and non-decreasing while ensuring value calculation cannot panic before the cap is applied. [8](#0-7) 

### Proof of Concept
A single unprivileged user, or multiple unprivileged addresses, can reach the vulnerable path:

1. Supply a large amount of an 18-decimal hub asset through `Controller::supply(caller, 0, spoke_id, vec![(BIG18, amount)])`.
2. Supply collateral and borrow approximately 98% of that market through `Controller::borrow(caller, account_id, vec![(BIG18, debt)], None)`.
3. Let ledger time advance until the next compound step would make `borrowed * borrow_index / RAY` exceed `i128::MAX`.
4. Call `Controller::update_indexes(caller, vec![BIG18])`.
5. The call reverts with `MathOverflow` inside `accrue_step -> scaled_to_original -> Ray::mul -> mul_div_half_up`. Subsequent `withdraw` and `repay` calls revert at the same accrual step.

The repository contains a direct executable model of this sequence in `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`. [14](#0-13)

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
