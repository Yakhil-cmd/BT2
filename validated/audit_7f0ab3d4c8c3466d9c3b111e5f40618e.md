### Title
Cross-Organization Commit Status Forgery via Webhook Signature/Repository Binding Mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController` selects which GitHub organization's `webhook_secret` to verify an inbound webhook's HMAC signature against, based on an attacker-controlled JSON field (`repository.owner.login` / `organization.login`) rather than on the resource the payload actually mutates. Several webhook handlers, most notably `StatusHandler`, then act on data (a bare commit `sha`) with no re-validation that the authenticated organization actually owns the affected commit/repository/stack. In a multi-organization Shipit deployment this breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` resolves the signing secret like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), and `Shipit.github(organization: repository_owner)` picks a **different `webhook_secret` per organization** when the multi-org config schema is used: [3](#0-2) 

This is a documented, supported configuration (`config/secrets.development.example.yml` shows multiple orgs each with their own `webhook_secret`). Consequently, the signature only proves "this payload was signed by *some organization's* secret" — it says nothing about which repository/commit the payload's body claims to affect.

Downstream, `StatusHandler#process` never re-checks that the affected commit belongs to a stack/repository owned by the authenticating organization; it matches purely on `sha`, globally across the whole Shipit installation: [4](#0-3) 

Any organization configured in `secrets.github` (i.e., any org onboarded to this Shipit instance, which is not a privileged Shipit account/session/token) can send a POST to the public, unauthenticated `/webhooks` endpoint with:
- `X-Hub-Signature` computed with *their own* org's `webhook_secret` (which they legitimately know, since they configured their own GitHub App),
- `repository.owner.login` set to their own org login (so `verify_signature` picks their own secret and passes),
- `sha`, `state: 'success'`, and `context` set to reference a commit that actually belongs to a *different* organization's stack.

`Commit.where(sha: params.sha)` will match the victim's commit if that sha happens to exist in Shipit's database (e.g., because it was pushed to the victim's tracked branch), and `commit.create_status_from_github!` will create/overwrite a `Status` for it — forging a "green" CI status the attacker never earned.

### Impact Explanation
A forged, favorable commit status can satisfy `ci.require` / deployability checks (`Commit#deployable?`, `README.md` §CI) for a stack the attacker has no access to, potentially enabling continuous delivery or a deploy trigger to ship a commit whose real CI never passed — this crosses into "unauthorized deploy" territory (Critical per the given impact rubric). Even absent CI-bypass exploitation, this is a cross-organization write into another org's data (Status records) performed with credentials scoped to a different organization, i.e., a cross-tenant integrity violation.

Related handlers share the same weak/no repository-scoping pattern and widen the blast radius:
- `CheckSuiteHandler` scopes by `stacks` derived from `payload.dig('repository','full_name')` with no cross-check against the authenticating org either [5](#0-4) .
- `MembershipHandler` trusts `params.organization.login` to attach team membership, again without verifying it matches the org whose secret authenticated the request [6](#0-5) .

### Likelihood Explanation
Exploitability requires the target Shipit instance to be configured with **multiple** GitHub organizations (a first-class, documented feature — see `config/secrets.development.example.yml` and `docs/setup.md`), and requires the attacker to control at least one of those organizations' own GitHub App/webhook secret — which is not a privileged Shipit credential, just ownership of one of the several onboarded orgs. In single-organization deployments (the common case) this is not exploitable because there is only one secret. Likelihood is therefore Medium: real in multi-tenant Shipit installs, not applicable to single-org installs.

### Recommendation
- After signature verification, re-derive the organization that should be authoritative for the payload from a field that cannot diverge from the one used to select the secret (or better, from the actual `repository.full_name`'s owner) and reject the webhook if `repository.owner.login`/`organization.login` doesn't match the repository/stack being mutated.
- In `Handlers::Handler` and specifically `StatusHandler`, scope commit/status lookups by the repository derived from `repository.full_name`, not merely by `sha`, and assert that repository's owner matches the authenticated organization.
- Apply the same repository/organization-ownership assertion in `MembershipHandler` and `CheckSuiteHandler`.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (`secrets.github.org-a.webhook_secret`, `secrets.github.org-b.webhook_secret`), and `org-b` has a stack tracking commit `abc123...`.
2. An operator of `org-a` (who legitimately knows only `org-a`'s webhook secret) crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "org-a" } },
  "sha": "abc123...",
  "state": "success",
  "context": "ci/required-check"
}
```
3. They compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a-secret, body)>` and POST it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `"org-a"`, fetches `org-a`'s secret, and the signature checks out.
5. `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, finds the commit belonging to `org-b`'s stack (unrelated to `org-a`), and creates a "success" `Status` for it via `commit.create_status_from_github!`, even though `org-a` has no relationship to that repository/commit. # frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
