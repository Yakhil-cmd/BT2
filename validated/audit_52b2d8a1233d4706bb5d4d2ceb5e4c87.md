## Analysis Result

### Title
Incomplete data-feed sanitization for formula-computed `feed_name`/value in AA responses allows LevelDB key injection - (File: aa_validation.js, main_chain.js)

### Summary
osCommerce's CVE-2018-18966 is a class of "incomplete blacklist" bug: a filter (banning `.html`) is enforced on one code path but is bypassed because a second, equally reachable interpretation path (IE rendering HTML inside a `.eml` file) is not covered by the same filter. `ocore` has an analogous gap in data-feed sanitization: the `\n`-injection / length checks that protect the flat-string LevelDB key namespace used for data feeds are applied only to literal (non-formula) `feed_name`/value payloads, and are explicitly skipped whenever an Autonomous Agent (AA) computes them via an oscript formula.

### Finding Description
When an AA definition is statically validated, `data_feed` payload fields are checked for length and embedded `\n` only if they are **not** formulas: [1](#0-0) 

If `getFormula(feed_name)` or `getFormula(value)` returns a formula (i.e., the field is dynamically computed from the trigger), these checks are deliberately skipped — the comment/logic defers validation "to runtime." This is the counterpart of the ordinary-unit path, which always enforces these checks for `data_feed` messages: [2](#0-1) 

At AA execution time, the formula is evaluated and substituted into the outgoing message by `aa_composer.js`'s `replace()`/`evaluateAA()` machinery, which resolves `if`/`init` formulas and general string values but does not re-apply the `MAX_DATA_FEED_NAME_LENGTH` / `MAX_DATA_FEED_VALUE_LENGTH` / `\n`-rejection checks that exist for literal fields (`aa_composer.js:589-618`, `757-816`).

When the resulting AA response unit becomes stable, `main_chain.js`'s `addDataFeeds()` writes the feed directly into the key/value store using a flat, `\n`-delimited string key, trusting that the payload was already sanitized: [3](#0-2) 

Because the key format is `'df\n'+address+'\n'+feed_name+'\ns\n'+strValue+'\n'+strMci`, a `feed_name` or string `value` that contains an embedded `\n` (or is unexpectedly long) can inject extra path segments into this key, corrupting the namespace boundaries that `readDataFeedValue`/`dataFeedExists` rely on for range-based lookups (`data_feeds.js`).

### Impact Explanation
Any account that can trigger an AA with attacker-controlled parameters that flow into a `data_feed` message's formula-computed `feed_name` or `value` (a fully unprivileged action — anyone can send an AA trigger unit) can produce a stored data-feed key whose `\n`-delimited structure does not match what other AAs' `in data feed`/`data_feed[[...]]` conditions expect when parsing/serializing the same components. This can forge or shadow the appearance of a specific oracle feed entry, which is commonly used by other AAs to gate token issuance, conditional payouts, or price-based distributions. A successful collision/forgery of a data-feed key can cause an AA to release funds based on a spoofed feed value it never legitimately received, resulting in AA fund loss, or cause different nodes' key/value stores to diverge in what they resolve for a given `(oracle, feed_name)` pair — a node-disagreement-on-stability condition on data-feed-dependent AA computations.

### Likelihood Explanation
Exploitation only requires posting a trigger unit to an oracle/relay AA whose definition builds a `data_feed` message with a formula for `feed_name` or a string value (a normal, supported oscript pattern, not a privileged operation). No hub, peer, or operator compromise is needed — the reachable trust boundary is "unprivileged AA trigger sender."

### Recommendation
Re-apply the same length and `\n`-rejection checks (`constants.MAX_DATA_FEED_NAME_LENGTH`, `constants.MAX_DATA_FEED_VALUE_LENGTH`, rejection of embedded `\n`) to the *evaluated* `feed_name`/value strings in `aa_composer.js` immediately after formula substitution, before the resulting `data_feed` message is included in the AA response unit — mirroring the checks already enforced in `validation.js` (lines 1933-1944) for ordinary units, so that no code path (static or formula-derived) can produce a data-feed payload that violates the invariants the key/value store namespace depends on.

### Proof of Concept
Conceptual PoC (not executed against a live node):
1. Deploy an AA whose definition includes `{"app":"data_feed","payload":{"[feed_name formula, e.g. trigger.data.name]": "[value formula, e.g. trigger.data.val]"}}`.
2. Send a trigger unit whose `data.name` or `data.val` contains an embedded `\n` character, e.g. `"attacker_feed\ns\nforged_value\n00000123"`, and a controlled length designed to align with the byte offsets `readDataFeedValue` uses when scanning `df\n<address>\n<feed_name>\n...` keys.
3. Because `aa_validation.js` (lines 96-111) skips length/`\n` checks for formula-derived fields, the AA definition passes validation, and `main_chain.js`'s `addDataFeeds()` (lines 1587-1616) writes the malformed key verbatim.
4. A separate AA that queries `data_feed[[oracles=<oracle_addr>, feed_name="target_feed", ...]]` (or `in data feed`) can then match against the attacker-crafted key fragment instead of the intended feed entry, depending on how `data_feeds.js`'s range scan parses the corrupted key — potentially triggering an unintended payout.

Note: I could not, within the available tool budget, fully confirm whether a later runtime re-validation step exists elsewhere in `aa_composer.js` that closes this gap before the response unit is finalized; this uncertainty should be verified by a maintainer with full repository access (e.g., via a Devin session) before treating this as fully confirmed.
