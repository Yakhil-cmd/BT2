### Title
GITHUB_TOKEN exfiltration via unrestricted `$VAR` interpolation of attacker-authored `shipit.yml` deploy/task steps - ([File: lib/shipit/command.rb], [File: lib/shipit/task_commands.rb], [File: lib/shipit/environment_variables.rb])

### Summary
`EnvironmentVariables#interpolate` substitutes any `$WORD` token found in a step string with whatever value exists under that key in the full command `env` hash, with no whitelist check at all. Because `TaskCommands#env` builds that hash by merging `Commands#base_env` (which contains `GITHUB_TOKEN`) with stack/task data, and `TaskDefinition#steps` is populated verbatim from the repository's own `shipit.yml` (`deploy`/`tasks` steps), any step string such as `echo $GITHUB_TOKEN` will have the live GitHub token substituted in and printed to task output by `Command#run`/`#stream!`.

### Finding Description
The claimed binding is: *"every key substituted by `EnvironmentVariables#interpolate` into a step string ∈ keys approved by the deploy spec's whitelist (`permit`)"*. Tracing the code shows this equality does **not** hold.

- `EnvironmentVariables#interpolate` performs no whitelist check whatsoever: [1](#0-0) 
  It simply does `@env.fetch(variable) { ENV[variable] }` for every `$WORD` occurrence in the string, `Shellwords.escape`s the value, and substitutes it. The `permit`/whitelist method (`sanitize_env_vars`) exists as a *separate* method used only to sanitize user-submitted deploy variables (`filter_deploy_envs`, `filter_rollback_envs`, `TaskDefinition#filter_envs`), not the env consumed by `interpolate`. [2](#0-1) 

- `Command#interpolated_arguments` (called from `Command#start` before `PTY.spawn`) runs `interpolate` over `@args`, which are the raw step strings: [3](#0-2) 

- The `env` passed into each step's `Command` comes from `TaskCommands#env`, which chains `super` (i.e. `Commands#env` → `base_env`) before merging stack/task data: [4](#0-3) [5](#0-4) 

- `base_env` unconditionally sets `'GITHUB_TOKEN' => github.token` (and optionally `GIT_ASKPASS`), and this exact hash is used by `TaskCommands#perform`/`#install_dependencies` for every step, not just internal `git` plumbing commands: [6](#0-5) 

- The step strings themselves (`deploy`, `rollback`, `tasks.*.steps`) are sourced directly from the repository's `shipit.yml`: [7](#0-6) [8](#0-7) 

Root cause: the whitelist infrastructure (`permit`/`VariableDefinition`) only governs which *user-supplied deploy-time variables* are accepted into `@task.env`; it was never applied to gate which environment keys a step string is allowed to *reference* via `$VAR` interpolation. Since the full merged env (including `GITHUB_TOKEN`) is what `interpolate` reads from, any step author can pull in that secret.

Exploit flow: a repository owner (or, per the question's stated precondition, an attacker who triggers review-stack creation despite `review_stacks_enabled: false` via the `provision?` precedence bug in `opened_handler.rb`/`reopened_handler.rb`) authors a `shipit.yml` on their PR branch containing a deploy or custom task step like `echo $GITHUB_TOKEN`. When that review stack's deploy/task is run, `TaskCommands#perform` builds `Command`s with the full env (containing `GITHUB_TOKEN`), `Command#start` interpolates `$GITHUB_TOKEN` into the actual token value, and the resulting command line/stdout (visible to the PR author who is the stack's actor) contains the live token.

No existing guard stops this: `filter_deploy_envs`/`filter_rollback_envs`/`TaskDefinition#filter_envs` are not invoked for the env passed to `perform`'s `Command.new(command_line, env:, chdir: ...)`, and `EnvironmentVariables#interpolate` has no filtering logic at all.

### Impact Explanation
A repository's `GITHUB_TOKEN` (the Shipit GitHub App/installation token used for all git/GitHub API operations for that organization) can be printed directly into task output that the PR author can view, matching the Critical-impact category "exfiltration of `GITHUB_TOKEN` ... or deploy-time secrets." Because the token is often scoped at the organization/installation level (not per-stack), leaking it grants the attacker whatever GitHub API/git privileges that token carries across every repository the installation can access — a serious cross-tenant blast radius. The attack is trivially repeatable on every deploy/task run once the malicious step is merged into the branch used for the stack.

### Likelihood Explanation
This requires: (1) a stack (review or regular) whose `shipit.yml` is sourced from content the attacker controls, and (2) the attacker being permitted to trigger a deploy/task on that stack (as the review-stack PR author is, per Shipit's actor/deployable model). For "Allow All" review stacks this is an explicit, low-cost path (open a PR from a fork with a malicious `shipit.yml`). For the `review_stacks_enabled: false` case, it additionally requires the separately-flagged `provision?` operator-precedence defect in `opened_handler.rb`/`reopened_handler.rb` to cause stack creation despite the flag being off. Either way, once a stack executes attacker-authored steps, exploitation is a one-line `shipit.yml` change with no further privilege needed.

### Recommendation
Restrict what `EnvironmentVariables#interpolate` is allowed to substitute: only permit interpolation of variables declared safe for step-string exposure (documented script parameters and explicitly-declared deploy/task `variables:`), and exclude infrastructure-only secrets (`GITHUB_TOKEN`, `GIT_ASKPASS`) from the env hash handed to user-authored step commands, reserving them for the internal `git` helper commands only. Concretely, split the `env` used by `TaskCommands#perform`/`#install_dependencies` from the `env` used by `Commands#git`, and apply `EnvironmentVariables#permit` (or an equivalent explicit whitelist) before interpolating step strings.

### Proof of Concept
In a minitest (e.g. `test/unit/command_test.rb`), construct a `Command` mimicking a deploy step referencing `$GITHUB_TOKEN`:
```ruby
test "attacker-authored step can exfiltrate GITHUB_TOKEN via interpolation" do
  token = 'aS3cr3Tt0kEn'
  command = Shipit::Command.new('echo $GITHUB_TOKEN', env: { 'GITHUB_TOKEN' => token }, chdir: '.')
  output = command.run
  assert_includes output, token
end
```
And at the integration level, build a `TaskCommands`/`DeployCommands` subclass test with a stubbed `deploy_spec.deploy_steps!` returning `['echo $GITHUB_TOKEN']`, stub `Shipit.github(...).token` to a known value, run `@commands.perform.first.run`, and assert the stubbed token string appears in the output — demonstrating that the binding "step-string-referenced keys ⊆ whitelist-approved keys" is false because no whitelist is applied at interpolation time.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
