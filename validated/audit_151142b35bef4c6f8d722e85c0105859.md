### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` while every handler acts on the separate, unverified `repository.full_name` field, allowing cross-tenant event forgery on any multi-org install that has one organization with no `webhook_secret` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook against using `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) . All downstream handlers (`PushHandler`, `StatusHandler`, `MembershipHandler`, pull-request handlers, etc.) never consult `repository_owner` again — they independently re-derive their target repository/team from a *different* payload field, `repository.full_name` (via `Handler#repository_name`) [2](#0-1) , or from `params.organization.login`/`params.team` for membership events [3](#0-2) .

### Finding Description
The equality that should hold is:

`organization used to select+verify the HMAC signature == organization/repository the handler actually mutates`

but the code never enforces it. `verify_signature` picks the `GitHubApp` (and thus the `webhook_secret`) using only `repository_owner` [4](#0-3) . `Shipit.github(organization:)`/`Shipit::GitHubApp#verify_webhook_signature` then checks the signature — but critically:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [5](#0-4) 

If the organization resolved from `repository_owner` has no `webhook_secret` configured (`nil`), **verification is entirely bypassed** and the raw payload — including the `repository.full_name` field the handlers actually operate on — is accepted unauthenticated. This "no secret ⇒ any signature accepted" fallback is exercised explicitly in this engine's own documented multi-org configuration schema, which shows `webhook_secret: # nil` as a valid per-organization value [6](#0-5) .

Because `verify_signature` keys off `repository.owner.login`/`organization.login` while the handlers key off the unrelated `repository.full_name` (`PushHandler`/`Handler#stacks` via `Repository.from_github_repo_name(repository_name)` [2](#0-1) , `PushHandler#process` [7](#0-6) , `StatusHandler#process` matching by raw `sha` across all commits [8](#0-7) , or `MembershipHandler#process` adding/removing team membership using `params.organization.login`/`params.team`/`params.member.login` [9](#0-8) ), an unauthenticated caller can:

1. Send `POST /github_hooks` (the webhooks route is mounted with no session/token requirement — `WebhooksController` skips CSRF and only gates on `verify_signature` [10](#0-9) ).
2. Set `repository.owner.login` (or `organization.login`) to any organization that is configured in this Shipit instance's `secrets.yml` with a blank `webhook_secret` — a configuration this engine's own docs/example explicitly support for multi-org installs.
3. Because that org has no secret, `verify_webhook_signature` returns `true` for the entire raw body, regardless of what else the body contains.
4. Populate `repository.full_name`, `team`, `organization.login`, `member.login`, `sha`, etc. with values that target a *completely different, secured* org/stack/team also hosted on the same Shipit instance.
5. The handler for the declared `X-Github-Event` acts on those forged fields as if genuinely delivered by GitHub for that repo/team.

### Impact Explanation
This crosses the "GitHub identity vs the payload field acted on" trust boundary analogous to the ERC4626 bug (verify one thing, act on another): the signature check authenticates "this org," but the mutation targets "that repo/team" from an unauthenticated field. Concrete unauthorized effects, all requiring zero credentials:

- `MembershipHandler` lets an attacker fabricate `membership` events (`action: 'added'`) to insert an arbitrary GitHub login into an arbitrary `Team`, including any team listed in `Shipit.github_teams`, directly escalating into Shipit's authorization model (`User#authorized?` checks membership in `Shipit.github_teams`) [11](#0-10)  — this is explicitly called out as High severity in the rubric ("escalation into `Shipit.github_teams` authorization").
- `PushHandler` can force `GithubSyncJob`/`sync_github` on an arbitrary stack belonging to a different, secured org [7](#0-6) .
- `StatusHandler` can forge CI/commit statuses for arbitrary commits across the whole instance (not scoped by org at all) [8](#0-7) , which can be used to satisfy `ci.require` deploy gates and enable an unauthorized deploy.

### Likelihood Explanation
This requires no session, API token, or GitHub credential — only that the operator has configured at least one organization in the shared multi-org `secrets.yml` without a `webhook_secret`, a pattern this repository's own sample config (`config/secrets.development.shopify.yml`) presents as a normal, supported layout for multi-tenant installs. Any Shipit instance serving more than one GitHub organization where a lower-trust org's App was set up without a webhook secret (e.g. during onboarding, or intentionally for an internal/test org) exposes every other, properly-secured org hosted on the same instance to this forgery. It does not depend on the host failing to mount the engine as documented — the `verify_webhook_signature` fail-open behavior and the mismatched field usage are in the engine's own code path that ships with multi-org support.

### Recommendation
- In `WebhooksController#verify_signature`/`GitHubApp#verify_webhook_signature`, never treat a missing `webhook_secret` as "verification passed"; require an explicit, documented opt-out (or fail closed) so that at minimum a misconfigured/secret-less org cannot forge events.
- Re-validate, inside every handler (`PushHandler`, `StatusHandler`, `MembershipHandler`, pull-request handlers), that `repository.full_name` / `organization.login` / `team.organization` actually belongs to the same organization that was used to select and verify the webhook signature (`repository_owner`), rejecting the event otherwise.
- Scope `StatusHandler`'s commit lookup and any cross-model lookups by the verified organization/repository rather than a bare `sha`/`full_name` match.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `secure-org` (with `webhook_secret: <real-secret>`) and `throwaway-org` (with `webhook_secret:` left blank), as shown supported in `config/secrets.development.shopify.yml`.
2. As an unauthenticated attacker, `POST /github_hooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/999"},
  "organization": {"login": "throwaway-org"},
  "member": {"login": "attacker-github-login"}
}
```
No `X-Hub-Signature` (or any value) is required because `throwaway-org` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally [12](#0-11) .
3. `MembershipHandler#process` creates/uses `Team` `999` with `organization: "throwaway-org"` and adds `attacker-github-login` as a member [9](#0-8) . If team id `999` is later reused/aliased to (or the attacker separately creates) a team that overlaps with one configured in `Shipit.github_teams` for `secure-org`, the attacker's GitHub login gains `authorized?` status against the secured org's Shipit deployment authorization check [11](#0-10)  — without ever having proven membership in, or credentials for, `secure-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
