Found it: `CCMenuController` overrides `stack` to bypass the stack-scoping that `require_permission` is supposed to enforce.

### Title
CCMenu API leaks stack state across stacks for tokens scoped to a single stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`ApiClient` tokens can be scoped to a single stack via `stack_id`, and every other API controller resolves the target stack through `BaseController#stacks`, which restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped [1](#0-0) . `CCMenuController`, however, overrides the private `stack` helper to look the stack up directly with `Stack.from_param!(params[:stack_id])`, bypassing the `stacks` scoping entirely [2](#0-1) .

### Finding Description
The binding that should hold is: **"stack a token authorizes" == "stack a token can read via `#show`."** `require_permission :read, :stack` only checks that the token has the `read:stack` permission string; it does not check *which* stack is being accessed [3](#0-2) , [4](#0-3) . The actual stack-scoping enforcement lives entirely in `BaseController#stack`/`#stacks`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

Every other stack-scoped controller (`CommitsController`, `TasksController`, `HooksController`, etc.) relies on this inherited `stack`/`stacks` method, so a token scoped to stack A cannot address stack B's resources through `params[:stack_id]` [5](#0-4) , [6](#0-5) .

`CCMenuController` redefines `stack` locally instead of using the inherited scoped version:
```ruby
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

This is the same bug class as the reported `INDEXER_ROLE` mismatch: a control meant to gate access (there, a role constant; here, the stack-scoping override) silently diverges from the value that is actually enforced elsewhere, breaking the "authorized scope == accessed scope" binding via a copy/override mistake rather than a signature check.

### Impact Explanation
An `ApiClient` token that is deliberately scoped to a single stack (e.g., `here_come_the_walrus`, scoped to stack `shipit` per the fixture) is intended to only ever see that one stack's data [7](#0-6) . Because `CCMenuController#stack` ignores `current_api_client.stack_id`, any holder of such a scoped, `read:stack`-permitted token can pass an arbitrary `stack_id` param and retrieve the CCMenu (CI dashboard) XML for a stack outside its authorized scope — including that stack's name, last build status, last build label, and last build time [8](#0-7) . This is an unauthorized read of stack state that the token's `stack_id` scoping was specifically designed to prevent, matching the "unauthenticated/unauthorized read of stack state" High-impact category in scope.

### Likelihood Explanation
Likelihood is high for anyone who already holds a stack-scoped API token (the same minimal privilege level assumed for other in-scope findings): no additional privilege, secret, or session is needed beyond the token itself, and the parameter (`stack_id`) is already part of the normal request shape for this endpoint (`get :show, params: { stack_id: @stack.to_param, token: @client.authentication_token }` in existing tests) [9](#0-8) .

### Recommendation
Remove the local `stack` override in `CCMenuController` and rely on the inherited `BaseController#stack`/`#stacks` methods so stack-scoped tokens are constrained consistently with every other API controller.

### Proof of Concept
1. Create two stacks, A and B.
2. Issue an `ApiClient` token scoped to stack A only (`stack_id: A.id`) with `read:stack` permission.
3. Call `GET /api/stacks/:B_stack_id/ccmenu.xml?token=<token>` (or via basic auth with the token).
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!`, the request succeeds and returns stack B's CCMenu XML (name, last build status/label/time), even though the token is only authorized for stack A.
