### Title
Cross-organization authentication confusion in webhook signature verification allows forged GitHub events (status/push) for repositories belonging to other organizations - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to use for HMAC verification based on an attacker-controlled field (`repository.owner.login` or `organization.login`) taken from the still-unverified JSON body, while the downstream `Handler` classes identify the target repository/stack from a *different* field in that same body (`repository.full_name`). Because these two fields are never checked for consistency, an attacker can pick an organization whose GitHub App has no `webhook_secret` configured to trivially satisfy signature verification, while pointing `full_name` at a completely different, "strong" organization's repository to have the payload processed against it.

### Finding Description
`verify_signature` computes the organization used to pick the `GithubApp` config purely from the raw, unauthenticated JSON payload: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` unconditionally passes when no secret is configured for that organization: [3](#0-2) 

Shipit's documented multi-org configuration allows each org's `webhook_secret` to be independently set or left blank ("optional"): [4](#0-3) 

Once past `verify_signature`, `WebhooksController#create` dispatches the *entire* payload to event handlers, which independently resolve the target repository from a different JSON key (`repository.full_name`), never cross-checked against the `repository.owner.login`/`organization.login` used for authentication: [5](#0-4) [6](#0-5) 

This is the exact class of bug described in the report: the value that is validated/regulated (here, "which secret authenticates this request") is decoupled from the value that is actually acted upon (here, "which repository/stack this request writes to"), exactly like `joiningFee`/`setJoiningFee` being decoupled from the amount actually minted. The binding that should hold is:

`organization authenticated by verify_signature == organization owning the repository the handlers act on`

but nothing enforces this equality — both are independent, attacker-supplied fields of the same unauthenticated JSON body.

Concretely, `Shipit::Webhooks::Handlers::StatusHandler#process` will create/update a commit `Status` for any commit SHA that exists in the DB, sourced purely from `params.sha` and `params.state`, regardless of which organization "authenticated" the request: [7](#0-6) 

`PushHandler#process` similarly resolves stacks via `repository_name` (i.e. `full_name`) and triggers a GitHub sync for any matching stack: [8](#0-7) 

### Impact Explanation
An attacker with no Shipit credentials can forge webhook events attributed to a repository/organization they don't control, as long as *any other* organization configured on the same Shipit instance (a legitimate, low-value org, or one whose admin left `webhook_secret` blank as the docs explicitly allow) is used as the "authenticating" identity. This breaks the "organization authenticated vs. repository written" binding and lets an attacker:
- Forge `status` events to mark arbitrary commits (of real, tracked stacks) as CI-`success`, which can be used to make Shipit consider unsafe commits deployable — an unauthorized-deploy-class impact.
- Forge `push` events to trigger `stack.sync_github` on arbitrary tracked stacks.
- Forge `pull_request`/`membership` events to archive/unarchive review stacks or manipulate team membership for repositories outside the attacker's control.

This matches the "unauthorized deploy" / "escalation into authorization boundary" impact bar, achieved purely by exploiting a decoupling between the field used for authentication and the field used for the write.

### Likelihood Explanation
Requires only that the Shipit deployment be configured for multiple GitHub organizations (a documented, supported configuration) where at least one configured org has no `webhook_secret` set — itself a documented "optional" setting, not a misconfiguration outside the engine's design. No credentials, tokens, or write access are needed; the attacker only needs to know or guess the login of such a weakly configured org and craft a JSON body with mismatched `repository.owner.login` and `repository.full_name`.

### Recommendation
In `WebhooksController#verify_signature`, after signature verification succeeds, assert that the organization that authenticated the request (`repository_owner`) matches the owner segment of the `repository.full_name` (or `organization.login`) that handlers will use to resolve the target repository, rejecting the request (422) on mismatch. Additionally, disallow relying on a blank `webhook_secret` to unconditionally pass verification when the engine hosts more than one GitHub organization, since it defeats organization isolation.

### Proof of Concept
Assume a Shipit instance configured with two orgs: `weak-org` (no `webhook_secret` set) and `strong-org` (tracks stack `strong-org/prod-app`, with commit `abcdef123` pending deploy).

```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything-or-omitted

{
  "sha": "abcdef123",
  "state": "success",
  "context": "ci/tests",
  "repository": {
    "owner": { "login": "weak-org" },
    "full_name": "strong-org/prod-app"
  }
}
```
1. `verify_signature` computes `repository_owner = "weak-org"`, loads `Shipit.github(organization: "weak-org")`, whose `webhook_secret` is blank → `verify_webhook_signature` returns `true` unconditionally, regardless of the supplied `X-Hub-Signature`.
2. `create` dispatches the payload to `StatusHandler`, which looks up `Commit.where(sha: "abcdef123")` — a commit belonging to `strong-org/prod-app`, unrelated to `weak-org` — and calls `create_status_from_github!`, marking it `success` under attacker control, without ever validating that `strong-org` and `weak-org` are the same tenant.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
