### Title
Webhook signature verification silently no-ops when an organization's `webhook_secret` is unset, allowing unauthenticated forgery of trusted GitHub events (e.g. `membership`) that mutate `Team`/`User` records used for `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
The Chainlink report shows a trust binding that is supposed to hold ("the settlement price must be covered by a validated round in the correct epoch") silently degrading into "any value is accepted" once its guard condition can't be satisfied, letting an attacker-observable gap propagate into state changes. The engine analog is `WebhooksController#verify_signature`, which is meant to bind "the organization whose secret signed this payload" to "the organization whose data (teams, users, repositories) is mutated by the payload," but the underlying check (`GithubApp#verify_webhook_signature`) unconditionally treats an unset `webhook_secret` as "verified," collapsing the binding to "no verification at all."

### Finding Description
`WebhooksController#verify_signature` selects which organization's GitHub App config to check against using data taken straight from the unauthenticated request body: [1](#0-0) [2](#0-1) 

The actual cryptographic check lives in `GithubApp#verify_webhook_signature`: [3](#0-2) 

`return true unless webhook_secret` means that for any organization configured without a `webhook_secret` (which is the documented/sample default — see `webhook_secret: null` in the dummy secrets fixture), **every** payload claiming to belong to that organization is accepted as authentic, regardless of the actual `X-Hub-Signature` header: [4](#0-3) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the attacker-supplied JSON body directly to the registered handler for the claimed event type with no further authentication: [5](#0-4) 

Handler tests demonstrate that a `membership` event payload is trusted to create `Team` and `User` records on the fly purely from body content: [6](#0-5) 

`User#authorized?` — the predicate that governs whether a logged-in GitHub identity is allowed to use the app at all — is driven entirely by `Team`/`Membership` rows: [7](#0-6) 

The broken equality is: **"organization whose secret verified this request" is supposed to equal "organization whose `Team`/`User`/`Membership` state this request is permitted to mutate."** With no `webhook_secret` configured (the shipped default), that equality collapses to "any request claiming to be from this organization," letting an unprivileged, unauthenticated attacker forge `membership` webhooks that insert `Membership` rows tying an arbitrary GitHub login to a `Team` matching `Shipit.github_teams`.

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization (High/Critical per the listed impact classes): a fabricated `Membership` row makes `User#authorized?` return `true` for a login the attacker controls, without that login ever actually belonging to the required GitHub team. Combined with the standard OAuth login flow (which looks up/creates the `User` by GitHub login), this lets an attacker who merely knows/controls a GitHub login bypass the team-membership gate that is supposed to be the sole authorization check for using the deployed Shipit instance, potentially leading to unauthorized deploys/rollbacks once "authorized."

### Likelihood Explanation
No credentials, GitHub App private key, `ApiClient` token, or existing Shipit session are required — only knowledge of the target organization's login name (public) and reachability of the `/webhooks` endpoint. The only precondition is that the relevant organization's `webhook_secret` is unset, which is the value shown in the project's own sample/test configuration, indicating this is a realistic default rather than an exotic misconfiguration.

### Recommendation
Do not treat an absent `webhook_secret` as "verified." Require every organization entry to define a `webhook_secret` (fail closed / raise at boot or reject the request with 422) before any handler is permitted to run, especially for privilege-bearing events such as `membership`, `team`, and `organization`. Consider additionally binding handler side-effects to the organization that was actually verified (`repository_owner`) rather than trusting nested payload fields (`team`, `member`, `organization`) independently.

### Proof of Concept
1. Deploy Shipit with an organization configured with `webhook_secret: null` (the documented default, e.g. as in `test/dummy/config/secrets.test.json`).
2. As an anonymous attacker, `POST /webhooks` with header `X-Github-Event: membership` and a body such as:
```json
{
  "action": "added",
  "team": { "id": <id-of-a-required-team>, "slug": "developers", "name": "Developers", "url": "https://example.com" },
  "organization": { "login": "<target-org>" },
  "member": { "login": "attacker-controlled-login" }
}
```
No valid `X-Hub-Signature` is required because `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank [3](#0-2) .
3. This creates/updates `Team` and `Membership` records exactly as shown by the existing test coverage [6](#0-5) , granting `attacker-controlled-login`'s eventual `User` record membership in a team that satisfies `Shipit.github_teams`, so `User#authorized?` returns `true` [7](#0-6)  once that GitHub login completes a normal OAuth login.

Note: I was unable to directly inspect the `membership` webhook handler's source file within the indexed context (only its behavior via `test/controllers/webhooks_controller_test.rb`); a Devin session with full repository access would be needed to confirm the exact handler implementation details.

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
