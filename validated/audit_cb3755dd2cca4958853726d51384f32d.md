### Title
Unapproved shared-address membership hijack leaks private payment chains to attacker devices - (File: `wallet_defined_by_addresses.js`)

### Summary
`handleNewSharedAddress()` in `wallet_defined_by_addresses.js` accepts a `new_shared_address` device message from any paired correspondent and silently inserts the address, its definition, and the sender-supplied `signers` map (address ↔ device_address bindings) into the local `shared_addresses` / `shared_address_signing_paths` tables — without any owner confirmation step and without verifying that the claimed `device_address` for each member path actually controls that address. This mirrors the Nextcloud Circles flaw where a user could become a member of a "Secret Circle" without approval by the owner, causing subsequent leakage of information that should be restricted to genuine members.

### Finding Description
The intended flow for creating a shared (multisig) address requires an explicit round of `create_new_shared_address` → user confirmation → `approve_new_shared_address` before a `new_shared_address` message is ever sent, as documented in the comment above `approvePendingSharedAddress`: [1](#0-0) 

However, the actual message handler that processes an incoming `new_shared_address` justsaying, `handleNewSharedAddress()`, performs no cryptographic or state check that this approval round ever happened. It only validates that:
1. the `address` equals the chash of `definition`,
2. each `signerInfo.address` is syntactically valid,
3. addresses embedded in `signers` match addresses found inside `definition`,
4. every definition leaf has a corresponding signer entry. [2](#0-1) 

`determineIfIncludesMeAndRewriteDeviceAddress()` only requires that at least one address in the payload be an address the receiving node already knows (`my_addresses` or an existing `shared_addresses` entry); it does not require that the receiving user has agreed to this exact shared address/definition: [3](#0-2) 

There is no requirement that the `device_address` claimed for any *other* member's signing path actually be verified as controlling that member address — the sender fully controls this mapping. Once accepted, `addNewSharedAddress()` unconditionally writes these attacker-supplied `device_address` bindings into `shared_address_signing_paths`: [4](#0-3) 

These bindings are subsequently trusted, without re-verification, by the private-payment forwarding logic. Whenever a private payment chain touches a shared address, all device addresses on record for that shared address automatically receive the full private payment payload (amounts, addresses, blinding factors, prior chain): [5](#0-4) [6](#0-5) 

This is the exact analog of the reported bug class: an entity can insert itself as a "member" of a private group construct (here, a shared address) without the legitimate owner explicitly approving that specific membership, and thereafter automatically receives private data intended only for verified members.

### Impact Explanation
An attacker who is merely a paired correspondent of the victim (no special privilege) can:
1. Choose one of the victim's already-known public addresses (`VICTIM_ADDR`) plus their own address, and construct a definition such as `["or", [["address","VICTIM_ADDR"], ["address","ATTACKER_ADDR"]]]`.
2. Send a `new_shared_address` message naming this new shared address, with `signers` claiming `VICTIM_ADDR` is controlled by the victim's own device (satisfying the "I am a member" check) and `ATTACKER_ADDR` by the attacker's device.
3. The victim's node accepts this without any prompt, adding the shared address and both signing-path bindings to its local DB.
4. Any subsequent private payment sent to (or spent from) that shared address is automatically forwarded in full (amounts, blinding factors, prior chain of outputs) to the attacker's device, because the attacker's device is recorded as a legitimate co-member — even though the victim never approved sharing this data with the attacker for this address.

This results in disclosure of confidential financial data (private-asset payment history/amounts) to an unauthorized party, exactly analogous to the "leaking private information" impact described in CVE-2021-37630.

### Likelihood Explanation
The prerequisite is only that the attacker be a paired correspondent of the victim (a very low bar — pairing is routine and often automated via QR/URI), and know one address the victim already uses (addresses are commonly shared for receiving payments). No cryptographic proof of address ownership is required for the other member entries, and the message is processed automatically with no UI confirmation gate in the protocol handler itself.

### Recommendation
- Require an explicit local approval/confirmation step (mirroring the unused `create_new_shared_address` / `approve_new_shared_address` handshake) before `handleNewSharedAddress()` commits a brand-new shared address definition that the local user did not initiate.
- Do not trust attacker-supplied `device_address` bindings for member addresses that are not the local device's own address; require independent verification (e.g., a message signed by the claimed device, or restrict membership updates to addresses actually reachable/verifiable) before adding them to `shared_address_signing_paths`.
- Gate automatic forwarding of private payment chains (`forwardPrivateChainsToOtherMembersOfAddresses`/`forwardPrivateChainsToOtherMembersOfOutputAddresses`) on explicitly user-approved shared-address memberships only.

### Proof of Concept
1. Attacker pairs with Victim as a normal correspondent.
2. Attacker learns `VICTIM_ADDR` (a normal payment address Victim has shared for receiving funds).
3. Attacker builds `arrDefinition = ["or", [["address","VICTIM_ADDR"], ["address","ATTACKER_ADDR"]]]`, computes `shared_address = chash160(arrDefinition)`, and constructs `signers = {"r.0": {address:"VICTIM_ADDR", device_address:"<victim_device>"}, "r.1": {address:"ATTACKER_ADDR", device_address:"<attacker_device>"}}`.
4. Attacker sends a device message `{subject:"new_shared_address", body:{address: shared_address, definition: arrDefinition, signers: signers}}` to Victim.
5. Victim's `handleNewSharedAddress()` accepts it (VICTIM_ADDR passes the "I am a member" check) and stores `shared_address_signing_paths` rows including `ATTACKER_ADDR -> attacker_device`, with no prompt shown to Victim.
6. Any private-asset payment later sent to `shared_address` triggers `forwardPrivateChainsToOtherMembersOfOutputAddresses`, which queries `shared_address_signing_paths` and forwards the full private payment chain to `attacker_device` automatically, disclosing private transaction data that Victim never agreed to share.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
