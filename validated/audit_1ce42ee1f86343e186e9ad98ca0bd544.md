Based on my investigation, I found a strong analog in the AA formula evaluator's Merkle-proof verification path, which mirrors the kernel bug's pattern: an object returned from a parsing/deserialization routine is dereferenced without a null-check before use.

### Title
Null pointer dereference in `is_valid_merkle_proof` formula evaluation via malformed proof string - (File: `formula/evaluation.js`)

### Summary
The `is_valid_merkle_proof()` oscript function deserializes an attacker-supplied proof string with `merkle.deserializeMerkleProof()` and then, only under a version-gated branch, accesses `objProof.siblings` before ever validating that `objProof` itself is a non-null object. If the deserializer returns `null`/`undefined` (or a value without the expected shape) for a malformed string, the property access throws a `TypeError` outside of the surrounding `try/catch`, which only wraps the later `merkle.verifyMerkleProof()` call.

### Finding Description
In `formula/evaluation.js`, the `is_valid_merkle_proof` case parses the proof: [1](#0-0) 

- `merkle.deserializeMerkleProof(proof)` is called on an attacker-controlled string (`arr[2]`, the `proof_expr` in an AA formula, itself sourced from `trigger.data` or other unit/trigger content) with no validation of its return value.
- The subsequent `if (bPostPemCurvesFix) { if (!Array.isArray(objProof.siblings) ...) }` check dereferences `objProof.siblings` directly. If `deserializeMerkleProof` returns `null` (a common return value for "failed to parse" in this codebase's style, mirrored elsewhere e.g. `getPrivateProfileFromJsonBase64` returning `null` on bad input, [2](#0-1) ), then `objProof.siblings` throws `TypeError: Cannot read properties of null`.
- Crucially, this dereference happens **before** the `try { res = merkle.verifyMerkleProof(...) } catch (e) { res = false; }` block, so the exception is **not** caught: [3](#0-2) 

This is structurally the same bug class as CVE-2023-6176: a value derived from untrusted/attacker-crafted input is dereferenced without validating that it is non-null before use, and the crash occurs on a path meant to be defensively guarded (the kernel's scatterwalk assumed non-null SG state; here, the evaluator assumes `deserializeMerkleProof` always returns a well-formed object).

### Impact Explanation
Formula evaluation for AA triggers runs inside the node's stateless/state AA-response processing pipeline while validating/executing units and AA responses that everyone on the network must agree on. An uncaught `TypeError` thrown mid-evaluation (outside the guarding `try/catch`) is a fatal, unhandled JS exception in the async evaluation chain. Depending on how the caller (`formula/evaluation.js`'s outer `evaluate`/AA response bounce-back logic) wraps this call, this can crash the node process or leave AA/unit validation in an inconsistent state, causing:
- A network-wide denial of service if the trigger is broadcast (nodes crash/hang while validating the same trigger/unit), preventing new units from being confirmed — directly matching the "no vulnerability without concrete impact" bar (network unable to confirm new units).
- Alternatively, if only some nodes crash (e.g., due to differing internal states or race conditions in exception propagation), this could cause node disagreement on validity of the AA response.

### Likelihood Explanation
Any unprivileged AA trigger sender can construct a formula-defined AA (or trigger data consumed by such an AA) that calls `is_valid_merkle_proof(element, proof)` with `proof` set to a string that `merkle.deserializeMerkleProof` cannot parse into a well-formed object. Since `proof_expr` can come directly from `trigger.data`, exploitation only requires posting a unit that triggers an AA using this formula function — no special privileges, hub cooperation, or peer trust required.

### Recommendation
Add a defensive check immediately after deserialization to ensure `objProof` is a non-null object before any property access, e.g.:
```js
objProof = merkle.deserializeMerkleProof(proof);
if (!objProof || typeof objProof !== 'object')
    return cb(false);
```
Alternatively, move the `Array.isArray(objProof.siblings)` check inside the existing `try/catch`, or make `merkle.deserializeMerkleProof` itself throw/return a sentinel that is checked unconditionally regardless of `bPostPemCurvesFix`.

### Proof of Concept
1. Define an AA whose bound state formula (or a trigger-driven `if`) contains:
   `is_valid_merkle_proof(trigger.data.element, trigger.data.proof)`
2. Send a trigger unit with `data.proof` set to a string that decodes (e.g., via base64/JSON in `deserializeMerkleProof`) to `null` or a non-object value, while still passing the earlier length/type checks (`isNonemptyString`, `length <= 1024`).
3. When `bPostPemCurvesFix` is true (i.e., post-upgrade, the normal current state), evaluation reaches `objProof.siblings` on a `null`/non-object `objProof`, throwing an uncaught `TypeError` outside the `try/catch`, propagating through the AA formula evaluator.

Note: I was unable to directly inspect the implementation of `merkle.deserializeMerkleProof` (its file was not returned by my searches within the available iterations), so I cannot 100% confirm its exact failure-mode return value (`null` vs. throwing vs. returning `{}`). This is the main uncertainty in this finding — if `deserializeMerkleProof` always throws on malformed input (which would be caught only if that call were inside the `try` block, which it currently is not for the `bPostPemCurvesFix` branch) or always returns a well-formed object with an empty `siblings` array, the crash may not materialize. Confirming this requires reading `merkle.js`, which should be done before treating this as fully validated.
