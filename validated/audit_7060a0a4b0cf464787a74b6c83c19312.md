This confirms the exploit chain end-to-end: `StatusHandler#process` at `app/models/shipit/webhooks/handlers/status_handler.rb:20-24` looks up `Commit.where(sha: params.sha)` — a bare SHA with no scoping to the repository/org that was authenticated — and calls `commit.create_status_from_github!(params)`, which flows into `Commit#add_status` at `app/models/shipit/commit.rb:366-384`, which can trigger `stack.schedule_merges` and, via `Stack#trigger_continuous_delivery`/`deployable?`, an actual automated deploy once a commit's status becomes `success`. ### Title
Webhook signature verified against attacker-controlled `repository.owner.login` while handlers act on the unrelated `repository.full_name`/`sha`, enabling cross-organization status forgery and unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository_owner`, a field taken directly from the unverified JSON body. Once verification passes, the full, attacker-supplied JSON payload — including an entirely independent `repository.full_name` (or, for `status` events, a bare `sha` with no repository binding at all) — is dispatched to handlers that mutate state for whatever repository/commit those fields name. There is no requirement that the organization whose secret validated the signature match the repository/commit actually acted upon.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read from the attacker-supplied raw body itself, and is used solely to pick which per-organization `webhook_secret` verifies the HMAC signature (`lib/shipit/github_app.rb#verify_webhook_signature`, `start="76" end="83"`). [2](#0-1)  Once the signature check passes for organization X, the entire raw JSON body — unmodified — is handed to every registered handler for the event:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Handlers then act on fields decoupled from `repository_owner`. `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [4](#0-3) , which can name any repository tracked by Shipit, not necessarily one owned by the authenticating organization. Worse, `StatusHandler` doesn't even look at `repository` at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

Any org whose webhook secret is known to the attacker (e.g. an org admin who configured their own org's Shipit GitHub App/webhook, as legitimately allowed) can craft a raw POST body themselves — bypassing GitHub entirely — with `repository.owner.login` set to their own org (so `verify_signature` picks their known secret and the HMAC checks out) while `sha`/`repository.full_name` reference a commit/repository belonging to a completely different, unrelated organization tracked by the same Shipit instance. The binding broken is: **the organization whose secret authenticated the request ≠ the repository/commit the handler actually writes to.**

### Impact Explanation
A forged `status` event with `state: success` for an arbitrary commit `sha` belonging to a victim stack causes `Commit#create_status_from_github!` → `add_status` to record a passing CI status. `add_status` schedules `stack.schedule_merges` and — critically — feeds `Commit#deployable?`, which is consulted by `Stack#trigger_continuous_delivery`. For any victim stack with continuous deployment enabled, this results in an **unauthorized automated deploy** triggered purely by a forged webhook signed with a different organization's secret, as demonstrated by `test/models/commits_test.rb:233-243`, where a `success` status directly enqueues `ContinuousDeliveryJob` and creates a `Deploy`. [6](#0-5) [7](#0-6)  This qualifies as Critical impact ("unauthorized deploy") under the defined criteria.

### Likelihood Explanation
Exploitation requires only that the attacker knows one organization's `webhook_secret` configured in Shipit (routine for any org admin who set up their own org's GitHub App integration) and be able to reach the `WebhooksController#create` endpoint with an arbitrary raw body and matching `X-Hub-Signature` header — no Shipit session, `ApiClient` token, or repository write access is required. The only constraint is that a target `sha`/`full_name` exists in the shared Shipit database, which is trivially discoverable for any multi-tenant deployment.

### Recommendation
Bind the field used for signature-key selection to the field(s) actually acted upon by every handler. Concretely: after selecting `github_app` via `repository_owner`, re-derive and enforce that `repository.full_name`'s owner matches `repository_owner` before dispatching to handlers, and change `StatusHandler` to scope `Commit.where(sha: params.sha)` to commits belonging to stacks under the authenticated repository/organization rather than a bare, repository-agnostic SHA lookup.

### Proof of Concept
1. Attacker administers GitHub org `attacker-org`, which is configured in Shipit's `secrets.yml` with `webhook_secret: S`. Attacker knows `S` because they set it themselves when wiring up the webhook.
2. Attacker crafts a raw JSON body directly (bypassing GitHub) for a `status` event:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" },
  "sha": "<victim commit sha in victim-org/victim-repo tracked by the same Shipit instance>",
  "state": "success",
  "context": "ci/forged"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, raw_body)` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `webhook_secret` (`S`), and the HMAC check passes — the signature is valid because attacker knows `S`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit (unrelated to `attacker-org`), and records a fabricated `success` status on it.
6. If the victim stack has `continuous_deployment: true`, this triggers `schedule_merges`/`trigger_continuous_delivery`, resulting in an unauthorized deploy of the victim's stack.
