### Title
Cross-tenant `Status` row injection via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` and applies the webhook payload to every match, with no filter on the webhook's own `repository.full_name`. Any organization that can send a validly-signed `status` webhook for its own repository can write attacker-controlled `description`/`target_url`/`context`/`state` into a `Status` row belonging to a completely different stack, as long as a `Commit` with the same sha exists there (e.g. shared history between a public upstream and any fork). This is rendered in the victim stack's commit/status UI.

### Finding Description
The claimed binding is: `organization that authenticated the webhook (repository_owner used in verify_signature) == organization owning the stack whose Status row is written`. Tracing the code shows this is **not enforced**:

- `WebhooksController#verify_signature` only checks that the payload is validly signed for `repository_owner` (`Shipit.github(organization: repository_owner)`), i.e. it authenticates *who sent this specific payload*, not *which stacks it may mutate*. [1](#0-0) 
- Every other handler in the codebase (`PullRequest::OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) explicitly scopes its `Shipit::Repository`/`stack` lookup via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before mutating anything, and the base `Handler` class even provides a `stacks` helper scoped to `Repository.from_github_repo_name(repository_name)`. [2](#0-1) 
- `StatusHandler#process`, however, never calls `repository_name`/`stacks`. It does a **global** lookup by sha:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
- `Commit#create_status_from_github!` unconditionally calls `statuses.replicate_from_github!(stack_id, github_status)`, which writes `state`, `description`, `target_url`, `context`, `created_at` verbatim from the webhook payload into a `Status` row tied to `commit.stack_id` — the victim's own stack, not the attacker's. [4](#0-3) [5](#0-4) 

Attack flow: the attacker controls (or forks) a repository tracked by Shipit as its own separate stack. If a commit sha in that repository's history is identical to a sha that also exists in a victim's stack (trivially true for forks that share upstream history, or any repository sharing commit history with the victim's tracked branch/PRs), the attacker triggers a GitHub `status` event on their own repo (this is entirely within their control — they own the repo and can push commits/set commit statuses via their own CI or the GitHub API). GitHub signs this webhook with the attacker's own org's secret, which passes `verify_signature` because it checks the signature against `repository_owner` from the *attacker's* payload, not against the stack being mutated. `StatusHandler#process` then finds **all** `Commit` rows across the DB with that sha — including the victim's — and writes a `Status` with the attacker's chosen `target_url`/`description`/`context` onto the victim's stack.

The `ignore_ci?` element from the prompt matters only for the *impact framing*: even where CI state doesn't gate deploys (`stack.ignore_ci?` true, per `Commit#deployable?`), the `Status` row is still created and rendered in the victim's UI (`commit.statuses`, dashboard), so attacker-controlled free text/links land in another tenant's interface regardless of whether it ever influences deploy decisions. [6](#0-5) 

No existing guard prevents this: `drop_unhandled_event`/`verify_signature` only gate on event type and per-org signature, not per-stack ownership of the sha being modified; there is no `ExplicitParameters` constraint tying `sha` to `repository`; and unlike the PR handlers, `StatusHandler` performs zero `Repository.from_github_repo_name` scoping.

### Impact Explanation
An attacker who owns/controls any repository tracked by Shipit (no special privilege needed beyond that) can inject attacker-chosen `description`, `target_url`, and `context` strings into a `Status` record belonging to an unrelated victim stack, as long as a matching commit sha exists on both sides. This is a genuine cross-repository/cross-tenant data write — one org's webhook mutating another org's records — matching the "Critical: payload for one repository mutating another's stack/commit" category. It is repeatable per shared sha and does not require compromising the victim; only a sha collision with the victim's tracked commit history is needed (trivially achievable with forks, since GitHub forks share full commit history with upstream). It also fires `enable_ci_on_stack`/`schedule_continuous_delivery` hooks on the victim's stack as a side effect. [7](#0-6) 

### Likelihood Explanation
Preconditions: (1) attacker owns/controls a GitHub repository that Shipit tracks as some stack (any tenant, including a fork of the victim's repo qualifies since Shipit auto-creates a `Repository`/`Stack` when receiving webhooks for unknown repos, per `WebhooksControllerTest` "create github repository which is not yet present in the datastore"); (2) a commit sha exists in both the attacker's repo history and the victim's tracked stack (near-guaranteed for forks). Attacker cost is low: sending a `status` webhook is trivial via GitHub's own status API or by pushing a commit through a CI integration on their own repo — no Shipit secrets, sessions, or tokens are required. This is fully repeatable against any stack sharing history with an attacker-controlled repo.

### Recommendation
Scope `StatusHandler#process` (and `Commit#create_status_from_github!`/`refresh_statuses!` callers reachable from webhooks) to only the commits belonging to stacks under the repository named in the webhook payload, mirroring the pattern used by the PR handlers (`Repository.from_github_repo_name(params.repository.full_name)` → `.stacks` → `.commits.where(sha: params.sha)`), rather than a bare `Commit.where(sha: ...)` across the entire database.

### Proof of Concept
Minitest plan (model/controller test, no live GitHub, following existing patterns in `test/controllers/webhooks_controller_test.rb`):
```ruby
test "status webhook for attacker repo must not create a Status on an unrelated victim stack sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)          # victim tenant
  attacker_stack = shipit_stacks(:cyclimse)      # unrelated tenant/repo, distinct repository
  shared_sha = "deadbeefcafefeedfacefeedbeefcafefeedface"

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  # Binding under test:
  # organization authenticated by verify_signature (attacker_stack.repository.owner)
  # == organization owning the stack whose Status is written (victim_commit.stack.repository.owner)? Should be TRUE for a safe write; here it's FALSE and must therefore be rejected.
  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  request.headers['X-Github-Event'] = 'status'

  body = {
    'sha' => shared_sha,
    'state' => 'success',
    'description' => 'PWNED - injected by attacker',
    'target_url' => 'https://evil.example.com/phish',
    'context' => 'attacker/ctx',
    'repository' => { 'full_name' => attacker_stack.repository.github_repo_name,
                       'owner' => { 'login' => attacker_stack.repository.owner } }
  }.to_json

  assert_no_difference -> { victim_commit.reload.statuses.count } do
    post :create, body:, as: :json
  end
end
```
Both sides of the equality (`attacker org` vs `victim stack's org`) should be compared before allowing the write; the test asserts no `Status` is created on `victim_commit` when the authenticated organization differs from the commit's own stack's organization — currently this assertion fails because `StatusHandler#process` writes the `Status` regardless.
