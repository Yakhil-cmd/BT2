### Title
Cross-organization webhook forgery via unbound `repository.owner.login` vs `repository.full_name` fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the **unverified** JSON body, while the handler that actually acts on the payload resolves the target repository from a **different, independent** field: `repository.full_name`. Because these two fields are never cross-checked, an attacker who controls a legitimate GitHub App installation registered in Shipit (i.e. knows *some* configured `webhook_secret`) can forge a webhook whose `repository.owner.login` matches their own org (so the correct secret is picked and the signature verifies) but whose `repository.full_name` points at a completely different, victim organization's repository.

### Finding Description
`verify_signature` computes the app/secret to check against like this: [1](#0-0) 

`repository_owner` is derived purely from the request body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization app config (secret, credentials) — this is confirmed by the multi-org configuration supported by the engine (`OrgOne`/`OrgTwo` blocks under `github:`): [3](#0-2) [4](#0-3) 

Once the signature check passes, the payload is dispatched to handlers unmodified: [5](#0-4) 

Every handler (e.g. `PushHandler`) resolves the target `Stack`/`Repository` from a *separate* field of the same untrusted payload — `repository.full_name` — via `Handler#repository_name`/`#stacks`, with no re-check that this repository belongs to the same organization whose secret was used to authenticate the request: [6](#0-5) [7](#0-6) 

The equality that should hold but doesn't:
`organization used to select/verify the HMAC secret (repository.owner.login)` == `organization that owns the repository actually acted upon (repository.full_name)`.

Because both values live in the same attacker-controlled JSON body and are read independently, an attacker who legitimately controls a GitHub App installation for `attacker-org` (registered in Shipit's `github:` config, thus possessing/knowing that org's `webhook_secret`) can:
1. Set `repository.owner.login` = `attacker-org` and `organization.login` = `attacker-org` so `verify_signature` picks `attacker-org`'s secret.
2. Sign the raw body with `attacker-org`'s real webhook secret so `verify_webhook_signature` succeeds.
3. Set `repository.full_name` = `victim-org/victim-repo` so `PushHandler` resolves and acts on the victim's `Stack`, enqueuing `GithubSyncJob` with an attacker-chosen `expected_head_sha`/`ref`, on a repository the attacker has no legitimate relationship to.

### Impact Explanation
This breaks the trust binding between "the organization whose credentials authenticated this HTTP request" and "the repository/stack this request is allowed to mutate." It allows cross-organization forged events to be delivered as if legitimate for stacks belonging to an organization the attacker does not control, letting the attacker drive `GithubSyncJob`/stack synchronization (and any other webhook-triggered side effects, e.g. `pull_request`, `status`, `check_suite` handlers, `membership` team/user creation) on a victim's repository purely by owning a different, unrelated GitHub App installation on the same Shipit instance. This is only meaningfully exploitable on multi-organization Shipit deployments (which the engine explicitly supports, per the `OrgOne`/`OrgTwo` config), and requires the attacker to control a second, legitimately-registered organization's webhook secret — not the victim's.

### Likelihood Explanation
Requires a multi-tenant Shipit deployment where more than one GitHub organization is configured, and the attacker to control (or be an admin of) one of those other configured organizations/App installations. This is a realistic operating mode for the engine (explicitly tested via `secrets_double_github_app.yml`), but is a narrower precondition than a single-org deployment, so likelihood is moderate rather than trivial.

### Recommendation
After verifying the signature, re-derive/validate that `repository.full_name`'s owner matches the `repository_owner`/`organization.login` value that was used to select the verifying secret, and reject the payload (422) if they diverge. Alternatively, thread the already-authenticated organization through to `Handler#repository_name`/`#stacks` and scope repository lookups to that organization instead of trusting the payload's `full_name` in isolation.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker, who administers the `attacker-org` GitHub App, crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(attacker-org webhook_secret, body)>` and `X-Github-Event: push`, and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and verifies successfully against the attacker's own known secret (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler#process` resolves `Repository.from_github_repo_name('victim-org/victim-repo')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and enqueues `GithubSyncJob` for the victim's stack using the attacker-controlled `after` SHA — despite the request never being signed by anything belonging to `victim-org`.
