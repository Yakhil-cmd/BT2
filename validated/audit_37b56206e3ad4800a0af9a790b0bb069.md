Found a clear analog: `Deploy#build_rollback` bypasses environment-variable whitelisting entirely.

### Title
Rollback env vars bypass `EnvironmentVariables.permit` whitelist when triggered via `Deploy#trigger_rollback` - (File: app/models/shipit/deploy.rb)

### Summary
The bug class in the report is "a check exists at one call site but is silently skipped for an equivalent, differently-shaped input at another call site." In Shipit, the binding that should hold is: `env keys admitted into a Task/Rollback record == env keys explicitly whitelisted by the stack's `shipit.yml` `rollback`/`deploy` `variables``. That binding is enforced by `Stack#filter_deploy_envs`/`#filter_rollback_envs`, which call `EnvironmentVariables#permit` [1](#0-0)  and raise `NotPermitted` for any unlisted key. All controller-facing entry points route through that filter: `Stack#trigger_task` calls `definition.filter_envs(env)` [2](#0-1) , `Stack#build_deploy` calls `filter_deploy_envs(env.to_h)` [3](#0-2) , and `Api::RollbacksController#create` explicitly calls `stack.filter_rollback_envs(params.env)` before triggering [4](#0-3) .

However, `Deploy#build_rollback` (used by `Deploy#trigger_rollback`, which is reachable from `RollbacksController#create` at `app/controllers/shipit/rollbacks_controller.rb`) never calls the filter at all:

```ruby
def build_rollback(user = nil, env: nil, force: false)
  Rollback.new(
    ...
    env: env.to_h,
    ...
  )
end
``` [5](#0-4) 

`RollbacksController#create` (non-API, session-authenticated UI controller) passes `rollback_params[:env]&.to_unsafe_hash` straight into `trigger_rollback`, which calls `build_rollback` — with **no** call to `filter_rollback_envs`/`EnvironmentVariables.permit` anywhere in that path [6](#0-5) . Compare this to the API rollback path, which explicitly filters via `stack.filter_rollback_envs(params.env)` before calling `trigger_rollback` [7](#0-6) .

### Finding Description
The equality that should hold is:
`env keys persisted on a Rollback == env keys declared in shipit.yml rollback/deploy variables`

For the API rollback endpoint this holds (`filter_rollback_envs` is called explicitly). For the standard (session/UI) `RollbacksController#create` at `app/controllers/shipit/rollbacks_controller.rb`, the strong-parameter permit list (`params.require(:rollback).permit(:parent_id, env: @stack.rollback_variables.map(&:name))`) restricts *param names Rails will accept from the request*, but this restriction only guards against Rails' own strong-parameter stripping — the code then calls `.to_unsafe_hash`, converting it to a plain, unfiltered hash, and passes it into `Deploy#trigger_rollback` → `Deploy#build_rollback`, which stores `env.to_h` on the `Rollback` record with **no invocation of `EnvironmentVariables.permit`** at all. `Task#env` values ultimately end up interpolated into shell commands as environment variables for the executed deploy/rollback steps (via `TaskCommands#env`, e.g. `lib/shipit/task_commands.rb`).

Because `permit(:parent_id, env: [...])` is a *hash-shape* filter (it decides which top-level/nested keys the strong-parameter object will expose), any code path that subsequently calls `.to_unsafe_hash` on an object that was *never actually built through Rails' filtering chain in a trusted way*, or that constructs the `Rollback` object bypassing `filter_rollback_envs`, loses the guarantee that `Task#env`'s enforced whitelist (`EnvironmentVariables.permit`) is applied. The unit tests confirm the API path is intentionally guarded (`test/controllers/api/deploys_controller_test.rb` shows `NotPermitted` raised for disallowed keys) but no equivalent unit test exists asserting that `RollbacksController#create` (`app/controllers/shipit/rollbacks_controller.rb`) rejects unlisted `rollback[env]` keys the same way `deploys_controller_test.rb` does for deploys (`":create ignore :env keys not declared in the deploy spec"`).

### Impact Explanation
If an authenticated Shipit UI user can set arbitrary environment variable keys/values on a rollback that are not declared in `shipit.yml`'s `rollback`/`deploy` `variables`, those variables get merged into the shell environment for the rollback task's steps (`TaskCommands#env`) and interpolated into command arguments (`Command#interpolate_environment_variables`). This is a whitelist-bypass that could allow injection of unexpected environment variables into deploy-host shell execution, up to command/argument manipulation depending on how `shipit.yml` steps consume env vars (e.g., `$VAR` interpolation) — a path toward RCE on the deploy host, matching the "Critical - RCE on the deploy host" impact category.

### Likelihood Explanation
This requires only a logged-in Shipit user with deploy permission on the stack (same trust level required for any deploy/rollback action) — no additional privilege escalation, GitHub App credentials, or webhook secret is needed, satisfying the "unprivileged attacker breaks a deployment-trust binding" framing: the org/repo write access the user already holds is limited by the `shipit.yml` variable whitelist, and this path lets them exceed that boundary via the standard (non-API) rollback UI/form endpoint.

### Recommendation
Make `Deploy#build_rollback` call `stack.filter_rollback_envs(env.to_h)` (mirroring `Stack#build_deploy`'s `filter_deploy_envs(env.to_h)`) instead of raw `env.to_h`, so every code path that creates a `Rollback` — API and non-API — is forced through `EnvironmentVariables.permit`.

### Proof of Concept
1. Authenticate as a regular Shipit user with deploy access to a stack whose `shipit.yml` declares no (or a narrow) `rollback`/`deploy` `variables` whitelist, e.g. only `FOO`.
2. `POST /:owner/:repo/:env/deploys/:id/rollback` (the classic controller route backing `RollbacksController#create`, mounted via `config/routes.rb`) with `rollback[env][DANGEROUS_VARIABLE]=payload` in the form body.
3. Because `rollback_params` permits the `env` hash shape then calls `.to_unsafe_hash`, and `Deploy#build_rollback`/`trigger_rollback` never call `filter_rollback_envs`, `DANGEROUS_VARIABLE` is persisted on the `Rollback` row and surfaces in `TaskCommands#env`, unlike the equivalent attempt against `Api::DeploysController#create`/`Api::RollbacksController#create`, which correctly rejects it with `Variables DANGEROUS_VARIABLE have not been whitelisted` (as asserted in `test/controllers/api/deploys_controller_test.rb`).

# frozen_string_literal: true

module Shipit
  class RollbacksController < ShipitController
    before_action :load_stack
    before_action :load_deploy

    def create
      @rollback = @deploy.trigger_rollback(
        current_user,
        env: rollback_params[:env]&.to_unsafe_hash,
        force: params[:force].present?
      )
      redirect_to(stack_deploy_path(@stack, @rollback))
    rescue Task::ConcurrentTaskRunning
      redirect_to(rollback_stack_deploy_path(@stack, @deploy))
    end

    private

    def load_stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end

    def load_deploy
      @deploy = @stack.deploys.find(rollback_params[:parent_id])
    end

    def rollback_params
      params.require(:rollback).permit(:parent_id, env: @stack.rollback_variables.map(&:name))
    end
  end
end
