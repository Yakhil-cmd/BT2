### Title
CCMenuController#stack bypasses ApiClient stack scoping, allowing cross-stack read via a stack-scoped token - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` overrides `BaseController#stack` and resolves the target stack with `Stack.from_param!(params[:stack_id])` against all stacks, instead of `stacks.from_param!` which restricts the lookup to `Stack.where(id: current_api_client.stack_id)` when the authenticating `ApiClient` is stack-scoped. Any `ApiClient` record that has a `stack_id` set (the schema and `BaseController#stacks` explicitly support this scoping model) and the `read:stack` permission can therefore be used to read the CCMenu XML (deploy/task state) of *any* stack, not just the one it is scoped to.

### Finding Description
The intended binding is: `stack_touched ∈ Stack.where(id: current_api_client.stack_id)` whenever `current_api_client.stack_id?` is true. `BaseController#stacks` enforces this: [1](#0-0) . `CCMenuController` however defines its own private `stack` method that ignores this scoping entirely and looks the stack up globally: [2](#0-1) .

`require_permission :read, :stack` only checks that `"read:stack"` is in `current_api_client.permissions`, via `ApiClient#check_permissions!`, and never compares `stack_id`: [3](#0-2) . Authentication is done by verifying the signed token and loading the `ApiClient` row by id, again with no stack check: [4](#0-3) , backed by `ApiClient.authenticate`: [5](#0-4) .

Attacker request: with a valid token for an `ApiClient` whose `stack_id` is set to stack A's id and permissions include `read:stack`, `GET /api/stacks/:stack_b_id/cc_menu.xml?token=<token>` resolves `stack` to stack B via `Stack.from_param!`, then `#show` calls `stack.deploys_and_rollbacks` and renders deploy/task state for stack B: [6](#0-5) . This succeeds even though `current_api_client.stack_id` is A, not B — the scoping check that exists in `BaseController#stacks` is silently skipped by this controller's override.

Note: the specific `ApiClient` auto-created by `CCMenuUrlController#fetch` does **not** set `stack_id` at all (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`) [7](#0-6) , so tokens obtained through that exact flow are already unscoped (`current_api_client.stack_id?` is false, so `stacks` would return `Stack.all` even under the correct implementation). The vulnerability is nonetheless real and independently exploitable for any `ApiClient` row that does have `stack_id` populated (the column and the `belongs_to :stack, optional: true` association exist, and `BaseController#stacks` is written specifically to enforce scoping for such clients) — for those, `CCMenuController` is the one endpoint in the API namespace that bypasses the scoping guard entirely.

### Impact Explanation
A token intended to be restricted to one stack (tenant/repository) can be used to read deploy/task status (`deploys_and_rollbacks`, latest deploy state, running/ended status) of any other stack in the installation via the CCMenu XML endpoint. This is an unauthenticated-for-that-tenant read of stack state/deploy output across tenants, matching the "High - unauthenticated read of stack state, task streams or deploy output" category. It is repeatable against arbitrary stack ids by simply changing `:stack_id` in the URL while reusing the same token.

### Likelihood Explanation
Exploitation requires possession of a valid, signed `ApiClient` token that has `read:stack` permission and (for the divergence to matter) a populated `stack_id`. Through the code paths in this engine that are reachable by end users (`CCMenuUrlController#fetch`), the created client is never stack-scoped, so this specific bug does not add capability beyond what that client already has. The bug becomes a real, distinct privilege violation whenever any stack-scoped `ApiClient` with `read:stack` exists (e.g., provisioned by an operator/other tooling using the `stack_id` column and `belongs_to :stack` association that the codebase supports) — for such a client, hitting `CCMenuController` instead of the properly-scoped stack API endpoints defeats the intended restriction at zero additional attacker cost.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped `stacks` relation instead of the global `Stack` model, matching `BaseController#stack`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Remove the private `stack` override entirely so the controller inherits `BaseController#stack`/`#stacks`, ensuring `current_api_client.stack_id` scoping is enforced consistently across all API controllers.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "scoped api client cannot read another stack's cc_menu" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # a different stack fixture
  client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'Scoped Client',
    stack_id: stack_a.id,
    permissions: %w[read:stack]
  )

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }

  # Binding under test: stack_b ∈ Stack.where(id: client.stack_id) is false
  assert_not Stack.where(id: client.stack_id).exists?(id: stack_b.id)
  # Current (buggy) behavior returns 200 with stack_b's data instead of 403/404
  assert_response :forbidden # currently fails: actual response is :ok, exposing stack_b's deploy state
end
```
