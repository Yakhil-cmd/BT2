## Cross-organization Status forgery via webhook signature/repository binding mismatch

### Title
Webhook signature authenticates an organization but `StatusHandler` writes to commits without checking that binding, permitting cross-organization Status forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The external Curve report describes a smart contract that checks a proxy condition (amount == 1 == "disabled") but fails to re-validate that condition after the underlying value legitimately changes, letting the system act on stale state. The structural analog here is a `verify_signature` step that authenticates *which GitHub organization* is calling, but the downstream `StatusHandler` never re-checks that the object being mutated (`Commit`) actually belongs to that authenticated organization. The "verified" fact (organization X signed this payload) is silently detached from the fact actually acted upon (write a `Status` on commit Y, which may belong to organization Z).

### Finding Description
`WebhooksController#verify_signature` picks which `GitHubApp`/secret to verify against using fields taken directly from the unauthenticated request body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config in a multi-tenant setup, and `verify_webhook_signature` explicitly returns `true` (bypassing verification) whenever that organization has **no `webhook_secret` configured**: [3](#0-2) 

This multi-org shape is a documented, in-scope configuration (`docs/setup.md` "Using Multiple GitHub Applications"), and `webhook_secret` is explicitly optional (`webhook_secret: # nil`) per the example configs: [4](#0-3) 

Once "verified", `WebhooksController#create` dispatches the *entire raw payload* to the handler, keyed only by event type — with no re-scoping to the organization that was authenticated: [5](#0-4) 

`StatusHandler#process` then updates any `Commit` whose `sha` matches the payload, with **no repository/organization scoping at all**: [6](#0-5) 

Compare this to `PushHandler` and `CheckSuiteHandler`, which at least scope through `stacks` (derived from `repository.full_name`) before acting: [7](#0-6) [8](#0-7) 

`StatusHandler` has no equivalent check tying `params.sha` back to the organization identified by `repository_owner` during signature verification. `Commit` records for stacks belonging to *every* configured organization live in the same table and are globally addressable by `sha`, so any organization that can get a webhook accepted (including one whose `webhook_secret` is unset, or any organization whose secret the caller legitimately knows because they administer that org's own GitHub App) can forge a `status` event naming a `sha` that belongs to a completely different organization's stack.

**The broken binding, stated as an equality that fails**:
`organization authenticated by verify_signature (repository_owner from payload)` ≠ `organization owning the repository/stack that Commit#sha actually belongs to`

Before the attack: only pushes/statuses genuinely originating from GitHub for organization A's repos can create `Status` rows on organization A's commits.
After the attacker's forged request: an entity that only controls (or is unauthenticated for) organization B's webhook endpoint can create/overwrite a `Status` (state, target_url, description, context) on a commit belonging to organization A's stack, as demonstrated directly by the existing test that shows *any* payload with a known `sha` creates a status regardless of provenance: [9](#0-8) 

### Impact Explanation
Shipit uses `Status` records to gate whether a commit is deployable (CI/checks required before deploy). Forging a passing `Status` on a commit belonging to a stack the attacker has no relationship to lets that commit satisfy required-check gating it should not satisfy, enabling an unauthorized deploy of that commit on someone else's stack — this maps to the "unauthorized deploy" Critical-impact category, achieved purely by authenticating as a different, unrelated GitHub organization than the one whose commit is mutated.

### Likelihood Explanation
This requires a Shipit deployment configured with multiple GitHub organizations (a documented, supported configuration) where at least one tenant's `webhook_secret` is unset (an explicitly supported, example-documented value) or where an attacker otherwise controls webhook delivery for one tenant. Given that, no additional credentials, session, or repository write access are required — only knowledge of a target `sha` value (commit SHAs are not secret; they are visible in git history, PRs, and CI). This is a plausible misconfiguration/multi-tenant scenario explicitly supported by the code and docs, but it does depend on that specific optional configuration state, so it is not universally exploitable by default (single-org deployments with a webhook secret are not affected this way).

### Recommendation
`StatusHandler` (and any other handler that resolves objects independently of the `stacks`/`repository_name` scoping already used by `Handler#stacks`) must verify that the resolved `Commit`'s stack/repository owner matches the organization identified during signature verification (`repository_owner` in `WebhooksController`), rejecting the event otherwise. More generally, `verify_webhook_signature` returning `true` for organizations with no configured secret should be reconsidered for multi-org installs, since it allows one tenant's absent secret to become an implicit trust bypass for writes that are not properly scoped to that tenant.

### Proof of Concept
1. Deploy Shipit with multi-org config: Organization `attacker-org` has `webhook_secret: nil`; Organization `victim-org` has stacks with real commits.
2. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, no valid `X-Hub-Signature` (or any signature, since `verify_webhook_signature` short-circuits to `true` for `attacker-org`), and body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}},
  "sha": "<sha of a commit belonging to victim-org's stack>",
  "state": "success",
  "context": "required-check",
  "target_url": "https://example.com"
}
```
3. `verify_signature` resolves `repository_owner` = `attacker-org`, whose blank secret makes `verify_webhook_signature` return `true` — request is accepted.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds/updates the commit belonging to `victim-org`, creating a forged passing `Status`, as shown directly by the handler code with no organization/repository scoping. [6](#0-5)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
