### Title
Quadratic-time input/output duplicate-key checks in payment message validation - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs()` and `validateMessage()` track "seen" keys (`arrInputKeys`, `arrOutputAddresses`) in plain JavaScript arrays and de-duplicate them with `Array.prototype.indexOf()` inside loops that iterate over every input/output of every message in a submitted unit. Because `indexOf()` is O(n) and it is called once per element, the overall complexity of duplicate detection is O(n²) in the number of inputs/spend-proofs contained in the unit, mirroring the algorithmic-complexity class described in the Apache Thrift Node.js advisory (inefficient/unbounded-cost processing of attacker-supplied input in the receive/validation path).

### Finding Description
`objValidationState.arrInputKeys` is a shared array that accumulates one key per payment input and per spend-proof, across *all* messages of the unit (units may contain up to `constants.MAX_MESSAGES_PER_UNIT` messages, each with up to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` inputs). Each call scans the entire array built so far via `indexOf`, so validating a unit with `n` total inputs/spend-proofs costs O(n²) string comparisons instead of O(n) (which a `Set`/hash map would give). The same pattern is used for `arrOutputAddresses` while validating outputs: [3](#0-2) 

This code path is reached by `validatePaymentInputsAndOutputs`, called from `validateMessage`/`validateMessages`, which is invoked for every unit submitted by any unprivileged peer through the normal `validate()` flow: [4](#0-3) 

An attacker does not need any special privilege — any address can author a unit with the maximum allowed number of payment messages and inputs, each just large enough to pass the earlier size/commission checks, and force the validating node to perform a large number of redundant linear scans before the unit is finally accepted or rejected.

### Impact Explanation
Unit validation in ocore is performed synchronously in the Node.js event loop (single-threaded). A crafted unit that maximizes messages × inputs (bounded only by `MAX_MESSAGES_PER_UNIT`, `MAX_INPUTS_PER_PAYMENT_MESSAGE`, `MAX_SPEND_PROOFS_PER_MESSAGE`, and the overall `MAX_UNIT_LENGTH`) can multiply the cost of what should be a linear validation pass, since every node that receives and validates the unit (full nodes, hubs, witnesses) pays the same O(n²) cost. Repeated submission of such maximal units by a single unprivileged poster can degrade validation throughput node-wide, delaying processing/confirmation of legitimate units queued behind it — falling under the accepted "network unable to confirm new units" impact category.

### Likelihood Explanation
Likelihood is high in terms of reachability: constructing a syntactically valid unit with the maximum number of messages/inputs requires no special keys, funds, or privileges beyond being able to post a unit (issue inputs or plausible-looking inputs can be crafted to pass through the loop until they fail late, after the expensive duplicate-key bookkeeping has already run for all preceding inputs). The actual DoS severity is bounded by `MAX_UNIT_LENGTH`, which caps the maximum number of inputs a single unit can carry, limiting how large `n` can practically get in one unit — but an attacker can still submit many such maximal units in succession to compound the effect.

### Recommendation
Replace the linear-scan duplicate-key arrays (`arrInputKeys`, `arrOutputAddresses`, and any other array-based "already seen" tracking used during per-unit validation) with `Set`/`Map`/`Object.create(null)`-based lookups so that membership tests and insertions are O(1), making overall validation cost linear (O(n)) in the number of inputs/outputs/spend-proofs.

### Proof of Concept
1. Author a unit with the maximum allowed number of payment messages (`MAX_MESSAGES_PER_UNIT`), each containing the maximum allowed number of transfer inputs (`MAX_INPUTS_PER_PAYMENT_MESSAGE`), while staying under `MAX_UNIT_LENGTH`.
2. Submit the unit to a node via the normal unit-posting path so it reaches `validate()` → `validateMessages()` → `validateMessage()`/`validatePaymentInputsAndOutputs()`.
3. Observe that for each input processed, `objValidationState.arrInputKeys.indexOf(input_key)` rescans the entire array accumulated so far [1](#0-0) , producing O(n²) growth in validation CPU time as `n` (total inputs across the unit) grows toward its maximum, compared to the O(n) cost a hash-based structure would incur.
