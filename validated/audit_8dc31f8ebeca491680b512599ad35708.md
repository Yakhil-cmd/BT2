### Title
Capped divisible asset with `issued_by_definer_only=false` allows unlimited supply inflation - ([File: validation.js])

### Summary
An asset defined with `cap` set, `fixed_denominations=false`, and `issued_by_definer_only=false` is supposed to have a hard total-supply cap, but the double-spend/uniqueness check used to prevent duplicate "issue" inputs is scoped per issuing address instead of globally per asset. Any number of distinct addresses can each independently issue a full `cap` amount of the asset, causing the real minted supply to be `cap × N` instead of `cap`.

### Finding Description
When validating a payment message that issues a divisible asset, `validatePaymentInputsAndOutputs` in `validation.js` enforces that a capped, non-fixed-denomination issue must have `serial_number === 1` and `amount === objAsset.cap`: [1](#0-0) [2](#0-1) 

The only mechanism preventing a *second* issue of the same capped asset is the "double spend" uniqueness check built from `doubleSpendWhere`/`doubleSpendVars`. Crucially, the address clause is added *only when the asset is not `issued_by_definer_only`*: [3](#0-2) 

```
doubleSpendWhere = "type='issue'";
...
doubleSpendWhere += " AND denomination=?";
if (objAsset){
    doubleSpendWhere += " AND serial_number=?";
}
if (objAsset && !objAsset.issued_by_definer_only){
    doubleSpendWhere += " AND address=?";
    doubleSpendVars.push(address);
}
```

This mirrors the pattern in the external report: a limit-enforcing check (`max_issued_serial_number=0` style logic for a global cap) is instead evaluated against a *narrower* scope (per-address) than the scope the cap is supposed to apply to (per-asset, globally), so several independently-valid "join"/"issue" requests can each pass the check and collectively blow past the intended maximum — exactly like archivers each individually passing the `archivers.size >= max` check while `joinRequests` (the pending/in-flight set) was never counted.

Here, when `issued_by_definer_only` is `false`, the uniqueness key used for the double-spend query is effectively `(asset, denomination, serial_number, address)`, matching the DB unique constraint `byAssetDenominationSerialAddress(asset, denomination, serial_number, address, is_unique)`: [4](#0-3) 

Since `serial_number` is forced to `1` and `amount` is forced to equal `cap` for every issue of this asset, and the uniqueness is keyed by `address` as well, every distinct address can issue its own `serial_number=1`, `amount=cap` input exactly once, with no conflict against any other address's issue of the same asset. There is no code path that sums or restricts the *total* number of addresses/units that may perform this issue for the same asset. Contrast this with the `issued_by_definer_only=true` case, where the address clause is omitted and the query becomes global for `(asset, denomination, serial_number)`, correctly limiting issuance network-wide to a single winner.

Nothing in `validateAssetDefinition` rejects the combination `cap` + `issued_by_definer_only=false` + `fixed_denominations=false`: [5](#0-4) 

so an asset issuer (an ordinary unprivileged unit poster) can freely define such an asset.

### Impact Explanation
This is a supply-inflation bug reachable by any asset issuer/poster, with no privileged network role required. A "capped" divisible asset can be minted far beyond its advertised cap simply by having multiple addresses each post a valid issue unit, multiplying the real circulating supply by the number of distinct issuing addresses. Any wallet, exchange, or AA that trusts the asset's declared `cap` (e.g., for pricing, collateral, or accounting) is exposed to unbounded, protocol-accepted inflation of that asset — a concrete "supply inflation" impact.

### Likelihood Explanation
The attack requires no special privileges: any address can define the vulnerable asset (`cap` set, `issued_by_definer_only:false`, `fixed_denominations:false`) and then have any number of its own or colluding addresses each issue one full-cap batch. Every step passes existing validation rules (`validation.js`'s `validatePaymentInputsAndOutputs`), so honest nodes will accept and stabilize all these issuing units as valid, "good" units.

### Recommendation
For capped, non-fixed-denomination assets, the uniqueness/double-spend check for `type='issue'` must be scoped globally per `(asset, denomination, serial_number)` regardless of `issued_by_definer_only`, i.e., drop the `address` clause whenever `objAsset.cap` is set (mirroring how the indivisible-asset path enforces the cap globally via the shared `asset_denominations.max_issued_serial_number` counter). Alternatively, require `issued_by_definer_only === true` whenever `cap` is set for divisible, non-fixed-denomination assets, and reject the combination in `validateAssetDefinition`.

### Proof of Concept
1. Address `D` posts an asset-definition message:
```json
{
  "cap": 1000000,
  "is_private": false,
  "is_transferrable": true,
  "auto_destroy": false,
  "fixed_denominations": false,
  "issued_by_definer_only": false,
  "cosigned_by_definer": false,
  "spender_attested": false
}
```
This passes `validateAssetDefinition` (no rule forbids `cap` with `issued_by_definer_only=false`).

2. Address `A` posts a single-authored payment message for this asset:
```json
{
  "asset": "<asset_unit>",
  "inputs": [{ "type": "issue", "amount": 1000000, "serial_number": 1 }],
  "outputs": [{ "address": "A", "amount": 1000000 }]
}
```
This validates: `serial_number===1`, `amount===cap`, and the double-spend query is `type='issue' AND denomination=1 AND serial_number=1 AND address='A'` — no prior match, accepted.

3. Address `B` (a different address entirely, unrelated to `A`) independently posts:
```json
{
  "asset": "<asset_unit>",
  "inputs": [{ "type": "issue", "amount": 1000000, "serial_number": 1 }],
  "outputs": [{ "address": "B", "amount": 1000000 }]
}
```
The double-spend query becomes `... AND address='B'`, which finds no conflicting row (A's issue used `address='A'`), so this is also accepted.

4. Repeat with addresses `C`, `D`, ... — each mints another full `1,000,000` units of the "capped" asset. Total minted supply grows without bound, violating the declared `cap`.
