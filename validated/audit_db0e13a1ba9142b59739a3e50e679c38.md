### Title
Cross-organization webhook forgery via `repository_owner`/`repository.full_name` divergence lets an org without `webhook_secret` authenticate a forged event for another org's repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to verify against using `repository_owner`, which falls back to the top-level `organization.login` field when `repository.owner.login` is absent. `LabelCapturingHandler` and the base `Handler` instead resolve the target repository/stack from the independently attacker-controlled `params.repository.full_name`/`payload.dig('repository','full_name')`. An attacker can set `organization.login` to an org that has no `webhook_secret` configured (for which `verify_webhook_signature` unconditionally returns `true`) while pointing `repository.full_name` at a stack belonging to a *different*, properly secured organization, causing the forged event to be processed as authentic for that victim repository.

### Finding Description
The broken binding, stated as an equality that the code assumes but does not enforce: `repository_owner used to select the verifying GitHubApp == owner of repository.full_name used to resolve the target Repository/Stack`.

Trace:
- `WebhooksController#repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) .
- `verify_signature` uses that value to fetch a `GitHubApp` and check `verify_webhook_signature(signature, raw_post)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved org's config has no `webhook_secret` set: `return true unless webhook_secret` [3](#0-2) .
- Once verification passes, `create` dispatches to handlers with the raw parsed JSON, unfiltered by the org used for verification: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
- `LabelCapturingHandler` (and the base `Handler#stacks`/`repository_name`) resolve the actual target repository purely from `params.repository.full_name` / `payload.dig('repository', 'full_name')`, never re-checking that this repository's owner matches the org that authenticated the request: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) , and `Repository.from_github_repo_name(repository_name)&.stacks` with `repository_name = payload.dig('repository', 'full_name')` [6](#0-5) .
- Once dispatched, `capture_labels` persists attacker-supplied label names onto the resolved stack's `PullRequest`: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [7](#0-6) , which `ReviewStack#env` later upcases into deploy-time environment variables merged into the stack's env [8](#0-7) .

Exploit request: attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, body `{"action":"reopened","number":N,"pull_request":{...,"labels":[{"name":"MALICIOUS_FLAG"}]},"repository":{"full_name":"victim-org/target-repo"},"organization":{"login":"lenient-org"},"sender":{"login":"attacker"}}`. Note `repository.owner.login` is intentionally omitted, so `repository_owner` falls back to `organization.login = "lenient-org"`. If `lenient-org` is configured in `Shipit.github_apps`-equivalent config without a `webhook_secret`, `verify_webhook_signature` returns `true` for *any* signature (even a missing/garbage one), regardless of the actual signing secret of `victim-org`. The handler then resolves and mutates `victim-org/target-repo`'s stack using the attacker-controlled `repository.full_name`, satisfying the required schema field (`requires :repository do requires :full_name, String end`), independent of the `organization` field used for auth.

Existing guards do not close this gap: `verify_signature` never compares `repository_owner` against `repository.full_name`'s owner; `ExplicitParameters` schema for `LabelCapturingHandler` only requires `repository.full_name` be a String, it does not require `repository.owner.login` to be present or consistent with `organization.login`; `drop_unhandled_event` and `check_if_ping` are unrelated gating steps that don't affect this; there is no model-level revalidation that the mutated stack's repository owner matches the authenticated org.

### Impact Explanation
An unprivileged attacker who owns any repository in an org lacking a `webhook_secret` (or who simply forges the `organization.login` field to name such an org) can get arbitrary, unauthenticated writes accepted as if properly signed for **any other repository/stack** on the instance, as long as that repository's `full_name` is known (repo names are public). Concretely, via `LabelCapturingHandler`, the attacker can inject arbitrary strings that become uppercased environment variables merged into the victim `ReviewStack#env`, which is consumed by deploy/task commands — this is a payload for one org mutating another org's stack, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" and "authentication bypass (forged webhook ... accepted)". The same divergence generalizes to every other webhook handler that resolves target repos from `payload.dig('repository','full_name')` while the controller authenticates by `organization.login`, broadening blast radius across all repositories/stacks whose owning org is not the one selected for verification.

### Likelihood Explanation
The only precondition is that the Shipit deployment configures at least one GitHub organization without a `webhook_secret` (explicitly supported by the code via `return true unless webhook_secret`, and documented in `docs/setup.md`/`template.rb` as an allowed configuration) — the question's premise ("victim stack where org configured without webhook_secret" / "org configured without webhook_secret stack") states this is exactly the scenario in play. Given that, the attack costs a single unauthenticated HTTP POST with attacker-fully-controlled JSON body and headers; no GitHub account interaction, no valid signature, and no privileged Shipit role are required. It is fully repeatable against any repository whose `full_name` the attacker knows.

### Recommendation
In `WebhooksController#verify_signature`, derive the authenticating organization from the same field the handlers use to resolve the target repository (`params.dig('repository', 'full_name')`'s owner segment), or, after verification, re-validate that `repository_owner` matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting the request (422) on mismatch. Additionally, do not allow `verify_webhook_signature` to short-circuit to `true` when `webhook_secret` is blank for organizations that also own repositories accessible through the fallback path — require an explicit "verification disabled" opt-in rather than treating a missing secret as always-valid, or require `repository.owner.login` to be present and match the top-level `organization.login` in the payload.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "pull_request reopened forged via organization fallback authenticates against org without webhook_secret but mutates a different org's stack" do
  # Setup: configure two orgs in Shipit.github config -
  #   "lenient-org" with no webhook_secret
  #   "victim-org" with webhook_secret = "s3cr3t"
  # Precondition equality to falsify:
  #   repository_owner (used for verify_signature) == owner_of(repository.full_name) (used by handler)
  victim_stack = shipit_stacks(:review_stack_on_victim_org) # repository full_name "victim-org/target-repo"

  payload = {
    action: "reopened",
    number: victim_stack.pull_request.number,
    pull_request: {
      id: 1, number: victim_stack.pull_request.number, url: "http://x",
      title: "t", state: "open", additions: 1, deletions: 1,
      head: { sha: "a" * 40, ref: "feature" },
      user: { login: "attacker" },
      assignees: [],
      labels: [{ name: "INJECTED_ENV_FLAG" }]
    },
    repository: { full_name: "victim-org/target-repo" }, # no owner.login key
    organization: { login: "lenient-org" }, # drives repository_owner fallback
    sender: { login: "attacker" }
  }.to_json

  post "/webhooks", params: payload, headers: {
    "X-Github-Event" => "pull_request",
    "X-Hub-Signature" => "sha1=deadbeef", # garbage / unrelated to victim-org's secret
    "CONTENT_TYPE" => "application/json"
  }

  assert_response :ok
  # Assert both sides of the equality diverge and the forged event was still accepted for victim-org's repo:
  assert_not_equal "lenient-org", "victim-org" # repository_owner != owner_of(repository.full_name)
  assert_equal ["INJECTED_ENV_FLAG"], victim_stack.pull_request.reload.labels
  assert_equal "true", victim_stack.reload.env["INJECTED_ENV_FLAG"]
end
```
This demonstrates that a request whose signature is verified against `lenient-org` (no secret) is nonetheless accepted and used to mutate `victim-org/target-repo`'s `PullRequest#labels` and `ReviewStack#env`, confirming the authentication-selector/target-resolution divergence.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
