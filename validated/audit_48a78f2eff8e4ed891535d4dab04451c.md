## Analysis

The bug class in the TWAP report is: a value the code trusts (rate) is used without applying the scaling/verification that other consumers assume was applied, producing wrong results. The strongest structural analog in `shipit-engine` is a **stack a token authorizes versus a stack it actually touches** — `Shipit::ApiClient#stack_id` is meant to scope a token to a single stack, but `Api::CCMenuController` resolves the target stack without ever consulting that scope.

### Root cause

`Shipit::Api::BaseController` defines the scoping used everywhere else in the API: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is stack-scoped, and `stack` resolves `params[:stack_id]` **through** that restricted relation. Every other API controller (e.g. `Api::StacksController`, `Api::TasksController`) inherits this and is therefore bound: `token.stack_id == resolved_stack.id` (or the token is unscoped).

`Api::CCMenuController` overrides both authentication and stack resolution and breaks that binding: [2](#0-1) 

`stack` calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model instead of `stacks.from_param!(...)`, so the `current_api_client.stack_id` filter is never applied. The only check performed is `require_permission :read, :stack`, which merely verifies the permission string `read:stack` is present in `ApiClient#permissions` — it does not verify which stack the permission applies to: [3](#0-2) 

### Why this is exploitable and matches the deployment-trust binding

The CCMenu endpoint is specifically designed to hand out narrowly-scoped, read-only tokens embedded in a bare URL (no `Authorization` header, no session) so that external CI-status tools can poll one stack: [4](#0-3) 

That controller creates an `ApiClient` scoped to `stack_id: <this stack>` with `permissions: %w[read:stack]`, and the token is placed in the URL query string: [5](#0-4) 

Because such tokens are transmitted as plain URL query parameters (any CI dashboard, proxy log, browser history, or referrer leak can expose them), the entire security model relies on the token being usable for only the one stack it was minted for. `CCMenuController#stack`'s bypass of `stacks` means a leaked/observed CCMenu token — issued and intended for stack A — can be replayed with a different `stack_id` parameter to read deploy/rollback status of **any stack in the installation**, including stacks the token was never authorized for. The equality that should hold, `token.stack_id == stack.id`, is never checked on this endpoint; only `token.permissions.include?("read:stack")` is checked, which is true for every CCMenu token regardless of which stack it was scoped to.

### Title
Stack-scoped CCMenu API tokens can read the status of any stack, not just the stack they were issued for - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController#stack` resolves `params[:stack_id]` via `Stack.from_param!` directly, bypassing `Api::BaseController#stacks`, which is the only place that enforces `current_api_client.stack_id` scoping. This lets any valid CCMenu token — regardless of which stack it was created for — retrieve the CI/deploy status of every stack in the installation.

### Finding Description
`ApiClient#stack_id` is the mechanism the engine uses to restrict a token to a single stack [6](#0-5) . Every standard API controller relies on `stack` calling `stacks.from_param!`, which applies that restriction [7](#0-6) . `CCMenuController` overrides `stack` with `Stack.from_param!(params[:stack_id])`, entirely skipping the `stacks` scoping relation [8](#0-7) . Authorization is instead limited to `require_permission :read, :stack`, which only checks that the string `read:stack` is present in the token's `permissions` array and never compares it against the requested stack ID [3](#0-2) . Since `CCMenuUrlController` mints exactly this kind of token — scoped to one stack, delivered as a bare query-string secret meant for third-party polling tools [9](#0-8)  — the intended binding "token authorizes stack A" is silently broken to "token can read any stack."

### Impact Explanation
This is an unauthenticated-scope escalation: a low-privilege, single-stack, read-only token (the kind purpose-built to be embedded in unauthenticated URLs polled by external CI dashboards) becomes a universal read credential for every stack's deploy/rollback history and status across the Shipit installation. This satisfies the High-impact bar of "escalation into authorization... or unauthenticated read of stack state... deploy output," since an attacker who observes one leaked CCMenu URL (a routine occurrence, since these are designed to be embedded in third-party CI status tools without further protection) gains read access to deployment state of stacks never intended to be exposed by that token.

### Likelihood Explanation
Likelihood is high: CCMenu URLs are explicitly designed for embedding in unauthenticated third-party polling clients, so their leakage via logs, referrer headers, or browser history is expected/normal usage, not a sophisticated attack. Exploitation requires no privileges beyond possession of any single valid CCMenu token, and the request is a simple unauthenticated GET with a different `stack_id` parameter.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation from `Api::BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so that a stack-scoped `ApiClient#stack_id` is always enforced regardless of which controller performs the lookup.

### Proof of Concept
1. As a legitimate user, request the CCMenu URL for stack `foo/bar` via `CCMenuUrlController#fetch`; this creates an `ApiClient` with `stack_id: <foo/bar's id>` and `permissions: ["read:stack"]`, and returns a URL like `.../api/stacks/foo/bar/staging/ccmenu.xml?token=<TOKEN>`.
2. Obtain `<TOKEN>` (e.g., via a leaked CI dashboard configuration, proxy access log, or referrer header — the token is designed to be embedded in plaintext URLs).
3. Send `GET /api/stacks/other-org/other-repo/production/ccmenu.xml?token=<TOKEN>` — a stack the token was never scoped to.
4. `CCMenuController#authenticate_api_client` authenticates the token successfully via `ApiClient.authenticate(params[:token])` [10](#0-9) ; `require_permission :read, :stack` passes because the token has `read:stack`; `stack` resolves `other-org/other-repo` directly via `Stack.from_param!`, ignoring that the token's `stack_id` points elsewhere [8](#0-7) .
5. The response renders `other-org/other-repo`'s latest deploy/rollback status, which the token was never authorized to access.
