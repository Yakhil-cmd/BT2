### Title
Malicious secondary-AA recipient can force revert of a primary AA's entire response, DoSing any AA that routes payments through an untrusted address - (File: aa_composer.js)

### Summary
In `handleTrigger`, when a primary AA response unit pays bytes/assets to another address that is itself an Autonomous Agent, `handleSecondaryTriggers` automatically fires a secondary trigger on that recipient AA. If the secondary AA's execution bounces (reverts), the entire primary AA response — including all state changes and outputs meant for the original, legitimate trigger sender — is rolled back via `revert()`. This is the exact analog of the reported issue: an untrusted payment recipient can unilaterally revert a transfer/payment flow that a victim contract (here, an AA) is trying to execute for someone else, causing denial of service.

### Finding Description
`handleSecondaryTriggers` collects all AA addresses that received outputs from the primary AA's response unit and re-invokes `handleTrigger` on each of them as a secondary trigger: [1](#0-0) 

If any of these secondary AA invocations bounces, the `async.eachSeries` callback treats this as an unrecoverable error and calls `revert()` on the *entire* primary trigger flow (unless the current context is itself secondary, in which case it just re-bounces upward): [2](#0-1) 

`revert()` rolls the whole unit back to the savepoint, discards all state var changes and any outputs the primary AA intended to send to the real trigger sender, and re-runs `bounce()` on the primary trigger instead: [3](#0-2) 

Because any Obyte address the primary AA pays to can be an AA address, and any AA author can define an AA whose logic unconditionally calls `bounce(...)` for any incoming trigger, an attacker can deploy such a "reverting" AA and register it as the destination for outputs from a victim AA (e.g. as a configurable fee-recipient, payout address, or any dynamically-chosen counterparty address in the victim's oscript). Once a payment output is routed to the attacker's AA, every trigger to the victim AA that produces that same output will bounce, discarding the intended payout/withdrawal to the genuine user as well. This mirrors the Sherlock finding precisely: a "fee receiver" (or any downstream payee) that is a smart-contract-like entity (here, an AA) can revert the token-transfer hook (here, the secondary trigger) and thereby block the primary operation for everyone relying on it.

### Impact Explanation
Any AA that sends part of its payout/response to an externally-controlled or attacker-influenceable address risks a full DoS of its "withdrawal"/payout logic: as soon as that address is (or becomes) an AA that always bounces, every user attempting to trigger the victim AA gets bounced along with it, because the whole unit — including their own legitimate output — is reverted by `revert()`. This can freeze funds/functionality for all users of a vault-like or multi-recipient AA, not just the attacker, satisfying the "AA fund loss or freezing" / DoS-of-confirmation criteria.

### Likelihood Explanation
Likelihood is high in any composable AA design where a payment destination is not hardcoded to a known, trusted, non-AA address (e.g., configurable fee recipients, referral addresses, or any address supplied via trigger data/state that could be redefined to point to an attacker-controlled AA). No special privileges are needed — anyone can post an AA definition and become the trigger address that eventually receives an output from the target AA.

### Recommendation
- Document and, where practical, mitigate this composability risk at the engine level, e.g., by decoupling secondary-trigger failures from the primary response's fate for pure "value transfer" outputs, or by capping/guarding automatic secondary-trigger cascades so that a bounce in a downstream AA does not retroactively revert outputs already committed to unrelated recipients.
- At minimum, strongly document for AA authors (and provide oscript guard patterns) that any address they pay MUST be treated as untrusted since it may be an AA that bounces, and that the correct pattern is a pull-based claim (store a `var[address]` balance for the recipient to withdraw via their own trigger) rather than pushing all payouts unconditionally in one atomic response.

### Proof of Concept
1. Deploy `EvilAA`: `{"autonomous agent", {messages:[{app:'state', state:'{bounce("always fail");}'}]}}` (or any variant of the "just_a_bouncer" style AA at `test/samples/just_a_bouncer.oscript` that always calls `bounce()`).
2. Deploy `VaultAA`, an AA that, similar to the `chain of AAs` pattern shown in the test suite, sends part of its output to a configurable "fee/payout" address alongside the user's withdrawal amount, e.g. following the structure in [4](#0-3)  where `primary_aa` pays `secondary_address`.
3. Set `VaultAA`'s payout/fee address to `EvilAA`'s address (directly or by having a user trigger set it, depending on the vault's design).
4. Any user triggers `VaultAA` to withdraw funds. `VaultAA`'s response unit includes an output to `EvilAA`, causing `handleSecondaryTriggers` to invoke `EvilAA` as a secondary trigger, which immediately bounces.
5. Per `aa_composer.js:1743-1749`, this bounce propagates to `revert()`, rolling back the entire `VaultAA` response — the withdrawing user receives nothing and `VaultAA`'s state (e.g., recorded withdrawal) is undone, while `VaultAA`'s own trigger gets bounced. Every subsequent withdrawal attempt is dosed the same way as long as `EvilAA` remains the configured recipient.
