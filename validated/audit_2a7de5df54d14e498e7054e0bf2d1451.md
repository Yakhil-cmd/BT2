This confirms the finding. `StatusHandler#process` at [1](#0-0)  does a global lookup `Commit.where(sha: params.sha)` across *all* stacks in the database and calls `create_status_from_github!` on every matching row, with no filtering by `stacks` (the `Repository.from_github_repo_name(repository_name)&.stacks` scope defined in the base `Handler` class at [2](#0-1)  is never invoked by this handler.

The signature verification in `WebhooksController#verify_signature` only proves that the payload was signed by the `webhook_secret` belonging to `repository_owner` (i.e., the org named in `payload['repository']['owner']['login']`) — see [3](#0-2)  and [4](#0-3) . It does **not** verify that the SHA referenced in the payload actually belongs to a commit within that owner's repository. Since git SHAs are content-addressed and not cryptographically bound to a specific repository, an attacker who owns any onboarded repo can craft/copy a commit whose SHA matches an existing commit in a victim's stack (trivial for well-known content like an empty tree, or by copying a public commit hash), sign a valid webhook with their own secret, and have `Commit.where(sha: ...)` match the victim's row cross-tenant.

### Title
Cross-tenant Status write via SHA-only lookup with no repository ownership check — (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone across the entire `commits` table and writes a `Status` for every match, without verifying that the webhook's authenticated repository (`repository_name`) actually owns that commit's stack. Because the webhook signature only proves who signed the request, not which repository the SHA belongs to, an attacker who controls a repository onboarded into Shipit can inject a `Status` into any other stack whose commit SHA they can guess or duplicate.

### Finding Description
The binding that must hold is: `repository_name` (derived from `payload['repository']['owner']['login']`, verified against the signer's `webhook_secret` in `WebhooksController#verify_signature`) must equal `commit.stack.repository.full_name` for every `Commit` mutated by the handler. `StatusHandler#process` never checks this:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

The base `Handler` class provides a `stacks` helper scoped to `Repository.from_github_repo_name(repository_name)` specifically for this purpose [2](#0-1) , but `StatusHandler` doesn't use it, doing a bare `Commit.where(sha:)` instead. `Commit#sha` has no `unique` scoping to a repository/stack; SHAs are attacker-choosable (they can push any tree/commit content to their own onboarded repo and obtain any target SHA, or simply reuse a publicly known SHA, e.g. the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`). The signature check in `verify_signature` only authenticates that the request was signed with the org's `webhook_secret` for `repository_owner` [5](#0-4)  — it says nothing about whose commit the `sha` field references.

Exploit flow: attacker onboards `attacker/repo` as a Shipit stack, creates a commit whose SHA equals a SHA present in `victim-org/victim-repo`'s stack, then `POST /webhooks` with `X-Github-Event: status`, body `{state: 'success', sha: SHARED_SHA, repository: {owner: {login: 'attacker'}}}`, signed with the attacker's own `webhook_secret`. The controller verifies the signature successfully (it's genuinely signed by the attacker's secret) and dispatches to `StatusHandler`, which finds the victim's `Commit` row by `sha` and calls `create_status_from_github!`, writing a `Status` into the victim's stack.

### Impact Explanation
An unprivileged attacker who only owns a repository onboarded into Shipit can write arbitrary CI `Status` rows (state, description, target_url, context) into commits belonging to any other stack in the same Shipit instance, without any relation to that stack's repository. Since deployability/mergeability in Shipit is often gated on `Status` (`deployable?` checks `success?` via combined statuses, per `Commit#deployable?` at [6](#0-5) ), this can be used to falsely mark a victim's commit as CI-passing, potentially triggering `schedule_continuous_delivery` and an unauthorized deploy [7](#0-6) . This matches "Critical: a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy."

### Likelihood Explanation
Preconditions: attacker must have any repository onboarded as a Shipit stack (a normal, unprivileged onboarding action), and must be able to produce/guess a SHA shared with a target commit in a victim stack (trivial with well-known empty-tree/blob SHAs, or any publicly known open-source commit SHA copied into their own repo's history). No Shipit session, API token, or victim's webhook secret is needed — only the attacker's own `webhook_secret`, which they legitimately possess for their own repo. This is fully repeatable against any stack/commit combination sharing a SHA.

### Recommendation
Scope the commit lookup to the authenticated repository, mirroring other handlers: use `stacks.flat_map(&:commits)` or join through `Stack`/`Repository` so only commits belonging to stacks whose `Repository.from_github_repo_name(repository_name)` matches are updated, e.g.:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

### Proof of Concept
1. In a minitest, create `victim_stack` (repository `victim-org/victim-repo`) with `victim_commit` having `sha: SHARED_SHA`.
2. Create `attacker_stack` (repository `attacker/repo`) with `attacker_commit` having the same `sha: SHARED_SHA`.
3. Assert precondition: `Status.where(stack_id: victim_stack.id, commit_id: victim_commit.id).exists?` is `false`.
4. POST to `/webhooks` with header `X-Github-Event: status`, body `{sha: SHARED_SHA, state: 'success', repository: {full_name: 'attacker/repo', owner: {login: 'attacker'}}}`, signed with `attacker/repo`'s `webhook_secret` (stub/allow `Shipit.github(organization: 'attacker').verify_webhook_signature` to return true, matching real signature flow).
5. Assert `Status.where(stack_id: victim_stack.id, commit_id: victim_commit.id).exists?` is now `true`, proving cross-tenant write from an attacker-signed request referencing only its own repository.
