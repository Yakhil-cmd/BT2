### Title
Cross-organization Team forgery via webhook `organization`/`repository.owner` mismatch - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify a webhook against using `repository_owner`, which reads `repository.owner.login` first and only falls back to `organization.login` if the `repository` key is absent. `MembershipHandler#find_or_create_team!`, however, persists `Team#organization` from `params.organization.login` unconditionally, with no check that it matches the org whose secret verified the request signature.

### Finding Description
The broken binding is:
`repository_owner` (computed at [1](#0-0)  and used to pick the verifying `webhook_secret` at [2](#0-1) ) is expected to equal `params.organization.login` (used to set `Team#organization` at [3](#0-2) ), but nothing enforces this.

`repository_owner` reads `params.dig('repository', 'owner', 'login')` first, falling back to `params.dig('organization', 'login')` only when `repository` is absent from the payload. Since a `membership` webhook body is entirely attacker-supplied JSON in a raw HTTP POST to `/webhooks`, an attacker who controls a legitimate org ("attacker-org") registered with its own `webhook_secret` in the multi-tenant Shipit config can craft a payload containing both:
- `"repository": {"owner": {"login": "attacker-org"}}` (drives which `webhook_secret` verifies the HMAC — the attacker's own, known secret), and
- `"organization": {"login": "shopify"}` (an unrelated org, only used later by `MembershipHandler`).

`verify_signature` calls `Shipit.github(organization: repository_owner)` → resolves to attacker-org's `GitHubApp`, and `GitHubApp#verify_webhook_signature` ( [4](#0-3) ) succeeds because the attacker signs the body with their own org's `webhook_secret`. The request passes signature verification entirely legitimately for "attacker-org," but `MembershipHandler#process` never re-checks `repository_owner`/`repository.owner.login` — it only reads `params.organization.login` ( [5](#0-4) ) and `params.team.id` (attacker-chosen, unused by any existing `Team`) to create a new `Team` row stamped `organization: "shopify"`.

No other guard intervenes: `drop_unhandled_event` only checks a registered handler exists for the event; the `ExplicitParameters` schema only requires `organization.login` to be a `String`, not that it match `repository_owner`; there is no model validation on `Team#organization` tying it to the verified org (confirmed via the handler code and no comparison anywhere in `MembershipHandler` or `Team.find_or_create_by!`).

### Impact Explanation
The attacker can create an arbitrary `Team` row (`github_id` of their choosing, `organization: "shopify"`) and immediately add themselves (`params.member.login`) as a member via `team.add_member(member)` in `MembershipHandler#process` ( [6](#0-5) ), while the request was only ever verified against the attacker's own org. This is a cross-tenant write: a payload verified for "attacker-org" mutates a record attributed to "shopify." If `Team#organization`/slug is later matched against `Shipit.github_teams` for authorization purposes, this forged Team/membership could feed into escalation of privileges tied to the "shopify" tenant — matching the High/Critical impact categories (payload for one repository/org mutating another's team data, potential escalation into `Shipit.github_teams` authorization). This is repeatable against any target organization name and any unused `team.id`, as often as the attacker wants, using only their own legitimate org's webhook secret.

### Likelihood Explanation
Preconditions: the Shipit instance must be configured for multiple organizations (each with its own `GitHubApp`/`webhook_secret`), and the attacker must control at least one such organization (own it, per the stated attacker capability of "emit webhooks from a repository they own"). Given that, the attacker's cost is minimal — one crafted JSON POST with a valid HMAC signature computed from a secret they legitimately possess. No GitHub relay is required since Shipit accepts any raw POST to `/webhooks` with a correct signature for the *resolved* org, and the resolution logic itself is attacker-influenced via the `repository`/`organization` payload fields.

### Recommendation
In `MembershipHandler` (and any other multi-key handler relying on both `repository.owner.login` and `organization.login`), require that `params.organization.login` equals the `repository_owner` value that was used to select the verifying `webhook_secret` (e.g., pass the verified organization through to handlers and assert equality before calling `find_or_create_team!`), rejecting the event otherwise.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":membership payload verified for one org cannot create a Team for another org" do
  # Assume two GithubHook::Organization-backed apps are configured:
  #   Shipit.github(organization: 'attacker-org') with webhook_secret 'attacker-secret'
  #   Shipit.github(organization: 'shopify')      with webhook_secret 'shopify-secret'
  @request.headers['X-Github-Event'] = 'membership'

  body = {
    action: 'added',
    team: { id: 999_999, name: 'Forged', slug: 'forged', url: 'https://example.com' },
    organization: { login: 'shopify' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', 'attacker-secret', body)
  @request.headers['X-Hub-Signature'] = signature

  assert_difference -> { Team.count }, 1 do
    post :create, body: body, as: :json
    assert_response :ok
  end

  team = Team.find_by(github_id: 999_999)
  # Binding check: repository_owner (verifying org) == params.organization.login (persisted org)?
  refute_equal 'attacker-org', team.organization
  assert_equal 'shopify', team.organization # proves cross-org write despite verification against attacker-org
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
