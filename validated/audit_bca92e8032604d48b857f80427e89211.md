### Title
`Api::CCMenuController#stack` bypasses the `stacks` scope, allowing any scoped `ApiClient` token to read `lastBuildStatus`/`lastBuildLabel`/`webUrl` for arbitrary stacks - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController` overrides the base `#stack` helper with its own implementation that resolves the stack directly from `params[:stack_id]` via `Stack.from_param!`, instead of going through `BaseController#stacks`, which is the mechanism that restricts stack-scoped `ApiClient` tokens to their own `stack_id`. As a result, any valid API token — even one created for a single stack (e.g. the CCMenu token minted by `CCMenuUrlController`) — can be replayed against `GET /api/stacks/*stack_id/ccmenu` for any other stack in the installation and will successfully render that stack's build status metadata.

### Finding Description
The intended binding is: for a scoped client, `stack.id == current_api_client.stack_id` (enforced in `BaseController#stack` via `BaseController#stacks`):
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`Api::CCMenuController` redefines `#stack` and drops the `stacks` scope entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

So for this controller, `stack` never intersects with `current_api_client.stack_id` — the equality the system is supposed to enforce is broken by omission. `#show` only calls `require_permission :read, :stack` (a before_action checking `check_permissions!(:read, :stack)`), which only verifies that the token's `permissions` array includes the string `read:stack` — it does not check `stack_id` at all:
```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [3](#0-2) 

Any token with `read:stack` permission — including a stack-scoped CCMenu token created by `CCMenuUrlController#client` (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)`) — passes the permission check for every request regardless of which stack is requested. [4](#0-3) 

Exploit flow: an attacker who legitimately owns Stack A obtains a CCMenu token (`GET /ccmenu/A` via `CCMenuUrlController#fetch`, or any other `read:stack`-permissioned token they hold). They then issue `GET /api/stacks/B/C/D/ccmenu?token=<their token>` for any other stack path in the system. `authenticate_api_client` (overridden in `CCMenuController` to accept `params[:token]`) succeeds, `require_permission :read, :stack` passes because the token has `read:stack`, and `#stack` resolves stack B/C/D directly from `Stack.from_param!`, bypassing the `stacks` scope. `#show` then renders `stack.deploys_and_rollbacks.last` build status/label and `webUrl` for the victim stack via `shipit/ccmenu/project.xml.builder`. [5](#0-4) [6](#0-5) 

None of the standard guards catch this: `verify_signature`/webhook checks are irrelevant (this is a token-authenticated API path), `ExplicitParameters` isn't used here, and `require_permission!` only checks the permission string, not the `stack_id` binding that `stacks` is designed to enforce.

### Impact Explanation
An attacker holding any single `read:stack`-permissioned `ApiClient` token — including one legitimately scoped to their own stack — can enumerate build status (`lastBuildStatus`), last deploy/rollback id (`lastBuildLabel`), build timestamp, and `webUrl` for every stack in the Shipit installation by repeating the request with different `stack_id` path segments. This is a cross-tenant unauthenticated read of deploy/rollback state, matching the High severity category "unauthenticated read of stack state ... across tenants." It is fully repeatable per request and has no dependency on privileged credentials beyond the attacker's own scoped token.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs one valid `ApiClient` token with `read:stack` permission, which is routinely handed out per-stack via the "Fetch URL" CCMenu feature in the stack settings page (`app/views/shipit/stacks/settings.html.erb`, `CCMenuUrlController#fetch`). No GitHub credentials, session, or elevated role is required. The attack is a single unauthenticated-relative-to-other-tenants GET request per target stack, trivially scriptable, and requires only knowledge of the target stack's identifier (owner/repo/env), which is often guessable or discoverable.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the base `stacks` scope instead of calling `Stack.from_param!` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures that scoped tokens (`current_api_client.stack_id?`) are restricted to their own stack, consistent with every other controller inheriting from `Api::BaseController`.

### Proof of Concept
Minitest plan (`test/controllers/api/ccmenu_controller_test.rb`):
```ruby
test "a token scoped to one stack cannot read another stack's ccmenu data" do
  other_stack = shipit_stacks(:cyclimse) # any stack fixture other than @stack
  @client.update!(stack_id: @stack.id, permissions: %w[read:stack])

  get :show, params: { stack_id: other_stack.to_param, token: @client.authentication_token }

  # Binding under test: stack.id == current_api_client.stack_id must hold
  assert_response :not_found, "expected scoped token to be denied access to a foreign stack"
end
```
Before the fix, this fails: the request returns `200 OK` and the response body contains `other_stack`'s `lastBuildLabel`/`webUrl`, because `#stack` in `Api::CCMenuController` resolves `other_stack` via `Stack.from_param!` without checking `@client.stack_id`. After changing `#stack` to `stacks.from_param!(params[:stack_id])`, the scoped `stacks` relation (`Stack.where(id: current_api_client.stack_id)`) raises `ActiveRecord::RecordNotFound` for the foreign stack, and the test passes with `:not_found`.
