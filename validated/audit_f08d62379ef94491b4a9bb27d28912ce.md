### Title
Cross-repository/cross-stack commit mutation via unscoped `Commit.where(sha:)` in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with a bare `Commit.where(sha: params.sha)`, with no scoping to the webhook's originating repository/stack and no exclusion of `detached: true` rows. Because a `status` webhook is authenticated per-organization (via `WebhooksController#verify_signature`) but not scoped to which `Commit` rows it may mutate, a webhook legitimately delivered for one repository can create statuses on, and trigger merge-queue processing for, `Commit` rows belonging to an unrelated stack whenever the SHAs collide — which happens naturally for shared/ancestor commits between a repo and any fork of it, and is not blocked even if the matched row is `detached`.

### Finding Description
The broken binding: business logic elsewhere requires
`stack.commits.reachable(detached: false)` == `commits eligible to affect deploy/merge state`
(see `Commit.reachable` at `app/models/shipit/commit.rb:55`, used by `blocked?` at `commit.rb:236`, `Deploy#commits`/`#commits_since` at `app/models/shipit/deploy.rb:166,172`, and `GithubSyncJob#spec_cache_target` at `app/jobs/shipit/github_sync_job.rb:77`).

`StatusHandler#process` breaks this and an even more basic tenancy binding:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This query is global across the entire `commits` table: not scoped to `detached: false`, and not scoped to the repository that authenticated the webhook. Contrast with the sibling `CheckSuiteHandler`, which correctly scopes through `stacks` (derived from the payload's `repository.full_name`) before touching commits: [2](#0-1) 
and the base `Handler#stacks` helper that performs this repository-scoped lookup: [3](#0-2) 

`StatusHandler` never calls `stacks`, so it never restricts matches to the repository named in the incoming payload.

Exploit path: `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) authenticates the webhook against `Shipit.github(organization: repository_owner)`'s configured `webhook_secret`, where `repository_owner` is read straight from the payload (`repository.owner.login`). This proves the request genuinely came from GitHub for *that* organization/repo — it says nothing about which `Commit` rows may be touched. An attacker who owns/controls a public repository that is a fork of (or shares commit history with) a repository tracked by a *different*, victim Shipit stack can:
1. Have their own repo/fork registered with Shipit (any repo an unprivileged user pushes to, with Shipit's GitHub App/webhook configured on it — standard for public-repo CI integrations).
2. Push or re-trigger CI on a commit whose SHA is shared with the upstream/victim repo (ancestor commits keep identical SHAs across forks because git SHAs are content-addressed).
3. GitHub sends a validly signed `status` event for the attacker's own repo/org to `POST /webhooks`.
4. `verify_signature` passes (correctly, for the attacker's own org).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the **victim's** `Commit` row(s) sharing that SHA in any stack, including ones marked `detached: true` (rebased away, and thus excluded from `stack.commits.reachable` everywhere else).
6. `commit.create_status_from_github!(params)` → `add_status` fires `Hook.emit(:commit_status, ...)` / `Hook.emit(:deployable_status, ...)` for the **victim's stack**, and calls `stack.schedule_merges` (enqueuing `ProcessMergeRequestsJob` for the victim stack) if the injected state is `pending` or `success` (`app/models/shipit/commit.rb:374-384`).

None of the existing guards catch this: `verify_signature` only authenticates the organization named in the payload, not the set of `Commit` rows a handler is permitted to touch; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape of `sha`/`state`/etc., not ownership; `Commit.reachable`/`detached` scoping is simply never applied by this handler.

### Impact Explanation
An attacker controlling any repository that shares commit SHAs with another, unrelated Shipit-tracked repository (trivially true for public GitHub forks) can inject fabricated CI statuses onto that other stack's commits — including detached/historical ones — causing `Hook.emit` webhooks to fire with falsified data and `ProcessMergeRequestsJob` to be enqueued against a stack the attacker does not own or administer. This is a payload for one repository mutating another's stack/commit state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable against any victim stack/repository that shares ancestor commit history with an attacker-controlled fork, and can be replayed indefinitely by re-emitting status events.

### Likelihood Explanation
Preconditions: the attacker needs a repository registered with Shipit's GitHub App/webhook that shares commit ancestry (identical SHAs) with a victim Shipit stack — a very common topology for open-source forks or repositories mirrored into multiple stacks. No Shipit session, API token, or webhook secret is required; the only requirement is that GitHub itself signs and delivers the event for the attacker's own repo, which happens automatically on ordinary CI activity (e.g., re-running/forcing a status check) on a shared commit. Attacker cost is low: no privileged access, no secret material, just ordinary GitHub actions on a repo they control.

### Recommendation
Scope `StatusHandler#process` the same way `CheckSuiteHandler` does: resolve `stacks` from the payload's `repository.full_name` first, then operate only on `stack.commits.where(sha: params.sha)` (optionally restricted to `.reachable`) instead of the global, unscoped `Commit.where(sha:)`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (illustrative)
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossStackTest < ActiveSupport::TestCase
        test "status webhook for repo A must not mutate a detached commit belonging to repo B's stack" do
          victim_stack = shipit_stacks(:shipit) # tracks repo "shopify/shipit-engine"
          shared_sha = "deadbeef" * 5

          victim_commit = victim_stack.commits.create!(
            sha: shared_sha, message: "shared ancestor",
            author: shipit_users(:walrus), committer: shipit_users(:walrus),
            authored_at: Time.now, committed_at: Time.now, detached: true
          )

          # Binding under test, stated as equality BEFORE tracing:
          # expected: Commit.where(sha: shared_sha) mutated by a "status" webhook
          #           == only commits in stacks whose repository authenticated this webhook
          #           AND detached: false
          # actual:   Commit.where(sha: shared_sha) == every commit row with that sha, any stack, any detached flag

          payload = {
            "sha" => shared_sha, "state" => "success",
            "repository" => { "full_name" => "attacker/forked-repo", "owner" => { "login" => "attacker-org" } }
          }

          assert_difference -> { victim_commit.statuses.count }, 1 do
            StatusHandler.call(payload)
          end

          assert victim_commit.reload.detached?, "commit should still be logically detached"
          assert_equal "success", victim_commit.statuses.last.state,
            "attacker-originated payload mutated a detached commit belonging to a different repository/stack"
        end
      end
    end
  end
end
```
This demonstrates that a payload whose `repository` does not match the victim stack's repository, and whose target `Commit` is `detached: true`, still results in a mutation — violating the `reachable`/tenancy binding enforced everywhere else in the codebase.
