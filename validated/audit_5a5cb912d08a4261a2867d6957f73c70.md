### Title
Auto-destroy assets sent to an AA are unconditionally burned by consensus even when the AA's redemption logic bounces, permanently freezing the collateral they represent - (File: aa_composer.js, validation.js)

### Summary
An Autonomous Agent (AA) that implements a lock/mint/redeem pattern — locking a base asset or another asset inside the AA and issuing a wrapped `auto_destroy` receipt token that users are meant to pay back to the AA in order to unlock the collateral — is exposed to the same failure mode as the reported bridge bug: the receipt token can be destroyed by the protocol without the AA ever releasing the corresponding collateral, because the `auto_destroy` burn is enforced unconditionally at the consensus/validation layer, independent of whether the AA's oscript logic actually executes the intended unlock branch.

### Finding Description
`ocore` lets an asset (including one defined inline by an AA via an `asset` message) be marked `auto_destroy: true`. Any output of such an asset sent to the asset's `definer_address` becomes permanently unspendable at the protocol level: [1](#0-0) [2](#0-1) 
This rejection fires purely based on `owner_address === objAsset.definer_address`; it does not depend in any way on whether an AA that is the definer actually processed the triggering unit successfully. The destruction is a pure consensus rule checked when an attempt is later made to spend that output.

When the definer of such an asset is an AA, `aa_composer.js` mirrors this rule by excluding any output of an `auto_destroy` asset sent to the AA's own address from the pool of funds the AA can use for further payments: [3](#0-2) 

This means once a payment of the wrapped/receipt asset lands on the AA address, it can never be spent again by the AA — it is burned unconditionally, regardless of what the AA's `messages`/`cases` logic does with the trigger.

The AA's own bounce mechanism, however, tries to refund whatever assets were received in the trigger back to the sender whenever none of the oscript's `cases` match or execution fails for any reason: [4](#0-3) 
`bounce()` iterates `trigger.outputs` (including the received wrapped asset) and attempts to build a payment message sending `bounced_amount` back to `trigger.address` via `sendUnit`. But because the just-received `auto_destroy` output is excluded from the AA's spendable balance (as shown above), the AA has no way to actually refund that asset back to the user if the asset is capped (`issued_by_definer_only` + `cap`, the normal configuration for a 1:1 backed receipt token — see `aa_validation.js` asset case, which explicitly supports defining such assets inside an AA): [5](#0-4) [6](#0-5) 

So the sequence of events for a lock/mint/redeem AA built on this primitive is:
1. User locks collateral (base bytes or another asset) in the AA; AA issues a capped, `issued_by_definer_only`, `auto_destroy` receipt asset `W` to the user, one unit of `W` per unit of collateral.
2. To redeem, the user is expected to pay `W` back to the AA in a trigger whose `if` case matches the "redeem" branch, causing the AA to release the locked collateral.
3. If the redeem trigger fails to match any `if` case for any reason (malformed `trigger.data`, wrong amount, an unrelated concurrent case matching first, a bug in the oscript's condition, insufficient bounce fee for a secondary asset, etc.), the AA's default behavior bounces the unit.
4. The bounce logic tries to refund the received `W` back to the user, but the AA cannot spend `W` it just received (excluded by the `auto_destroy`/definer exclusion) and cannot mint fresh `W` because the asset is capped — the refund of `W` silently cannot occur.
5. Regardless of the bounce outcome, the `W` output that was paid to the AA is now permanently unspendable (burned) by protocol rule, while the collateral it represented was never released because the "redeem" case never executed.

The net effect: the receipt/wrapped asset is destroyed, but the corresponding locked value inside the AA is never paid out — an exact analog to "user burns L2 token without the bridge unlocking L1 token", except here the burn is enforced by the ledger itself as soon as the token reaches the AA, decoupled entirely from the AA's business logic.

### Impact Explanation
Any AA that uses the natural `auto_destroy` + `issued_by_definer_only` + `cap` pattern to implement a vault/bridge (lock collateral, mint a capped receipt token, redeem by returning the token) can permanently freeze user collateral whenever a redemption trigger fails to match the expected `if` case — a very plausible occurrence given oscript formula errors, data feed issues, race conditions between concurrent triggers changing state variables, or simple user mistakes in `trigger.data`. This is a fund-freezing bug for the AA's held collateral (base bytes or other locked assets), matching a High-severity "permanently locked funds" class, since there is no way to recover: the receipt token proving the claim is unconditionally destroyed by consensus the moment it reaches the AA, independent of the AA's actual response.

### Likelihood Explanation
Any developer following the officially documented and test-suite-demonstrated pattern of defining an asset from within an AA (`test/samples/create_an_asset.oscript`, `aa_validation.js`'s `asset` case, `aa.test.js`'s `auto_destroy` tests) to build a redeemable/capped receipt token is likely to hit this: bounces are a normal, expected part of AA execution (the whole `bounce_fees`/`bounce()` machinery exists precisely to handle mismatched or invalid triggers), and nothing in the AA framework warns that an `auto_destroy` asset payment is burned unconditionally before/regardless of the AA's case matching. This makes the bug class easy to trigger unintentionally through any of the many conditions that cause a legitimate redemption trigger to fail to match its intended `if` case.

### Recommendation
- Document and/or enforce that assets with `auto_destroy: true` defined by an AA should never be treated as "safe to bounce": the AA's `bounce()`/`sendUnit` logic should detect when a trigger carries an `auto_destroy` asset for which the AA is the definer, and refuse to accept the burn as final unless the redeem case's business logic actually completed (e.g., by validating case conditions before allowing the auto-destroy semantics to finalize, or by disallowing default bounce paths from silently eating such assets).
- Alternatively, at the protocol level, consider deferring/ tying the auto-destroy finality to whether the AA's execution that received the payment actually completed a matching, non-bounced response, so that a bounced trigger does not still result in the received `auto_destroy` asset becoming permanently unspendable.
- At minimum, update AA-authoring documentation/samples to explicitly warn that `auto_destroy` assets received by an AA are burned unconditionally by consensus regardless of the trigger's outcome, and that redemption/bridge AAs must carefully guard against unmatched `if` cases (e.g., by using a catch-all case that reliably executes the release logic or explicitly bounces before any `auto_destroy` payment is even accepted as a valid trigger).

### Proof of Concept
1. Define an AA `Vault` with:
   - Case A (`define`): issues asset `W` with `{cap: N, issued_by_definer_only: true, auto_destroy: true, is_transferrable: true, fixed_denominations: false, cosigned_by_definer: false, spender_attested: false}` (as validated by `aa_validation.js`'s `asset` case) and locks `N` bytes contributed by the first depositor.
   - Case B (`redeem`): triggered `if: "{trigger.output[[asset=$W]] > 0 AND trigger.data.redeem}"`, releases `trigger.output[[asset=$W]]` bytes back to `trigger.address`.
2. A user deposits and receives `W`.
3. The user later sends `W` back to `Vault` but omits `trigger.data.redeem` (or any other case-condition mismatch, e.g., sends slightly malformed data). Case B's `if` doesn't match, no other case matches, and `Vault` calls `bounce('no messages')` per `aa_composer.js`'s default bounce path (`aa_composer.js:1868-1877`, `aa_composer.js:909-945`).
4. `bounce()` attempts to refund the `W` amount received in the trigger back to the user by building a payment message and calling `sendUnit`. `completePaymentPayload`'s `readStableOutputs`/`readUnstableOutputsSentByAAs` (`aa_composer.js:1140-1160`) exclude the just-received `W` output from spendable funds since `assetInfos[W].auto_destroy && assetInfos[W].definer_address === Vault`. Because `W` is capped, no additional `W` can be issued to cover the refund either.
5. The `W` output paid to `Vault` is now unspendable forever per `validation.js:2504-2505`'s consensus check ("this output was destroyed by sending it to definer address"), while the bytes locked in `Vault` corresponding to that `W` are never released, since case B never executed. The user's collateral is permanently stuck in `Vault` with no recovery path.
