### Title
Cross-repository Status forgery via unscoped `StatusHandler#process` sha lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits purely by `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike every other webhook handler which restricts itself to `stacks` derived from `payload.dig('repository', 'full_name')`. Because `Commit` shas are indexed per `(stack_id, sha)` and not globally unique, an attacker who can trigger genuinely-signed GitHub webhooks from a repository they control (e.g. a fork sharing commit history with a victim repo, or any repo within the same GitHub App installation/org) can attach forged `Status` rows to a victim commit belonging to a completely different stack/repository.

### Finding Description
The expected binding is: for every `Status` row folded into `Status::Group.compact(commit, statuses)`, the webhook that produced it must satisfy `payload.dig('repository', 'full_name') == commit.stack.repository.full_name`. This is exactly what the base class enforces for other handlers via: [1](#0-0) 

`StatusHandler#process`, however, never calls `stacks` and instead does a bare global lookup: [2](#0-1) 

`Commit` is only indexed/scoped by `(stack_id, sha)` — sha is not globally unique across stacks/repositories (migration `20170524104615_index_commits_on_stack_id_and_sha.rb`), so `Commit.where(sha: params.sha)` can and will match commit rows belonging to unrelated stacks whenever two repositories happen to share a commit sha (trivially true for forks, since Git commit hashes are content-addressed and forks retain byte-identical shas for shared history).

`WebhooksController#verify_signature` only authenticates that the payload is validly signed for *some* organization (`Shipit.github(organization: repository_owner)`), it does not verify that the specific `repository` inside the payload is the one the sha actually belongs to: [3](#0-2) 

So an attacker who owns/controls a repository within the same GitHub org/App installation (e.g. a public fork of the victim's repo, which they can create with zero privileges) can:
1. Fork the victim's public repository (shares identical commit shas for existing history).
2. Use GitHub's own Statuses API on their own fork (using their own `repo:status` write scope on the fork they own) to set several statuses with different `context` values and `state: success` against a shared sha.
3. GitHub delivers a genuinely, correctly-signed webhook per status to Shipit's `/webhooks` (signed using the org/installation's real secret — the attacker never needs to know it).
4. `StatusHandler#process` matches `Commit.where(sha: params.sha)` and finds the **victim's** commit row (different stack, different repository) and calls `commit.create_status_from_github!(params)` on it.
5. Each call writes a `Status` row scoped to the victim commit's own `stack_id` via `statuses.replicate_from_github!(stack_id, github_status)`: [4](#0-3) [5](#0-4) 
6. `Commit#status` recomputes via `Status::Group.compact(self, statuses_and_check_runs)`: [6](#0-5) 
and `Status::Group#select_significant_status` treats the group as `success` once no non-success, non-ignored status remains: [7](#0-6) 
7. `Commit#deployable?` (`success? && !blocked?`) and `MergeRequest#all_status_checks_passed?` (via `StatusChecker < Status::Group`) both flip to true purely from forged, self-authored CI results on an unrelated repository: [8](#0-7) [9](#0-8) 

Existing guards do not stop this: `verify_signature` authenticates the org, not the repo-to-sha binding; `ExplicitParameters` only validates the shape of `sha`/`state`/`context`, not repository ownership; and there is no `subset`/uniqueness validation tying a `Status` to the repository that actually built the commit.

### Impact Explanation
A payload legitimately signed for repository A (attacker-controlled) is used to write authenticated-looking `Status` rows for repository B's stack/commit (victim), satisfying the rubric's "payload for one repository mutating another's stack, commit ... or an unauthorized deploy/rollback/merge." Once `deployable?` and `all_status_checks_passed?` flip true, `ProcessMergeRequestsJob` will merge the victim's pull request and/or continuous delivery will deploy the commit: [10](#0-9) 
This is repeatable against any victim repository whose commits happen to share a sha with a repo the attacker controls (trivially arranged via forking), so it is not limited to a single tenant. Severity: Critical.

### Likelihood Explanation
Preconditions are cheap for an unprivileged attacker: fork a public target repository (shares full commit history/shas), and use the GitHub Statuses API on the fork (which the attacker legitimately owns) to post several distinct `context` values with `state: success`. No Shipit session, API token, or webhook secret is required — GitHub signs the resulting webhooks using its own configured secret for the org/installation. The only environmental requirement is that the attacker's repository shares a GitHub App/webhook configuration scope (organization) with the victim's, which is common for any org that allows member-owned forks or repos.

### Recommendation
Scope `StatusHandler#process` (and any other handler doing sha-only or global lookups) to commits whose `stack.repository` matches the payload's `repository.full_name`, mirroring the `Handler#stacks` helper, e.g. restrict the lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent, and add a model-level/service-level assertion that a `Status` can only be recorded against a `Commit` whose `stack.repository` equals the webhook's `repository`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — actual file is out of scope per rules but describes the reproduction):
```ruby
victim_stack = shipit_stacks(:shipit) # repo: "shopify/shipit-engine"
attacker_stack = shipit_stacks(:other) # repo: "attacker/shipit-engine-fork"
shared_sha = "deadbeef"

# Create a commit in the victim stack with the shared sha
victim_commit = victim_stack.commits.create!(
  sha: shared_sha,
  author: shipit_users(:shipit),
  committer: shipit_users(:shipit),
  authored_at: Time.now,
  committed_at: Time.now,
  message: "shared history"
)

# Attacker creates a status on their own fork (legitimately signed by GitHub)
attacker_payload = {
  "sha" => shared_sha,
  "state" => "success",
  "context" => "ci/attacker-ci-1",
  "description" => "Forged CI",
  "created_at" => Time.now.iso8601,
  "repository" => {
    "full_name" => "attacker/shipit-engine-fork",
    "owner" => { "login" => "attacker" }
  }
}

# Before: victim commit is not deployable (no statuses)
assert_not victim_commit.reload.deployable?

# Attacker sends multiple forged status webhooks (all legitimately signed for their repo)
3.times do |i|
  payload = attacker_payload.merge(
    "context" => "ci/attacker-ci-#{i}",
    "state" => "success"
  )
  # Simulate webhook delivery (signature verified by controller)
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)
end

# After: victim commit is now deployable (forged statuses attached)
assert victim_commit.reload.deployable?, "Victim commit should NOT be deployable from attacker's CI"
assert_equal 3, victim_commit.statuses.count
assert victim_commit.statuses.all? { |s| s.context.start_with?("ci/attacker") }
```

The test asserts that `victim_commit.reload.deployable?` becomes true despite the statuses originating from a completely different repository's webhook, proving the binding is broken. [11](#0-10)

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
