This is exactly the documented and already-mitigated staleness scenario — not a novel vulnerability.

The codebase explicitly documents and handles this via redundant post-processing filters at every consumption site:

1. `AccountsIndex::upsert` docs state: "The primary and secondary indexes are not updated atomically, and a brief inconsistency is acceptable: the secondary index is only consulted for `scan`, which is only supported on frozen banks, and is never used as a source of truth for gets/stores." [1](#0-0) 

2. `AccountsIndex::update_secondary_indexes` explicitly documents that stale entries never cause false positives because the primary index and account data are re-checked, and results are "ultimately filtered out by post-scan filters, like in `get_filtered_spl_token_accounts_by_owner()`." [2](#0-1) 

3. `AccountsDb::index_scan_accounts`, which is what actually consumes `SecondaryIndex::get()` results via `get_index_key_pubkeys`, fetches the live account via `do_load` for each candidate pubkey and passes the real, current account state to `scan_func` — not the stale index entry itself. [3](#0-2) 

4. At the RPC layer, `get_filtered_spl_token_accounts_by_owner` and `get_filtered_program_accounts` push additional `Memcmp`/owner filters on top of the index scan specifically to defend against this staleness, with an explicit comment: "an account may remain in storage as a zero-lamport `AccountSharedData::Default()`... We include the redundant filters here to avoid returning these accounts." [4](#0-3) 

5. There's a dedicated regression test, `test_get_filtered_indexed_accounts`, that reproduces exactly the attacker scenario (owner reassignment across roots) and asserts that a post-processing filter (`account.owner() == &program_id`) correctly excludes the stale entries, demonstrating the mitigation works as designed: "This demonstrates the need for a redundant post-processing filter." [5](#0-4) 

Because every consumer of `SecondaryIndex::get()` (the scan path, and the RPC `getProgramAccounts`/token-by-owner paths) re-validates the actual current account owner/data before returning or using results, a stale secondary-index entry cannot cause double-attribution of lamports, duplicated stake/vote membership, or any consumer trusting `get()` as authoritative — no such consumer exists in this codebase. The claimed "consumer that treats `get()` results as authoritative" is not something that exists in Agave; the design assumes and defends against exactly this staleness. Additionally, stake/vote accounting itself never queries this secondary index at all — it operates on the primary accounts index and live account state directly, so there's no reachable path from this staleness into reward/stake lamport accounting.
