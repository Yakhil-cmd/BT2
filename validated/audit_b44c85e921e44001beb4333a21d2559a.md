### Title
Webhook signature verification keys off `repository.owner.login` while handlers dispatch on `repository.full_name`, allowing a registered org to forge webhooks for any other org's Stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret using `repository.owner.login` from the JSON body, but `Handler#stacks` (used by `PushHandler`) locates the target `Stack` using the unrelated `repository.full_name` field from the same body. Because nothing enforces that these two fields agree, an attacker who legitimately owns an organization registered in `Shipit.github_apps` (with a real, attacker-known `webhook_secret`) can sign a payload with their own secret while setting `repository.full_name` to `victim-org/victim-repo`, causing Shipit to run `PushHandler` against the victim's `Stack`.

### Finding Description
The broken binding: the code implicitly assumes `payload.dig('repository','owner','login') == payload.dig('repository','full_name').split('/').first`, but this equality is never checked.

- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and picks `github_app = Shipit.github(organization: repository_owner)`, then checks the HMAC against that app's `webhook_secret`: [1](#0-0) [2](#0-1) 
- On success, `create` dispatches the *entire raw payload* to every handler for the event, unmodified: [3](#0-2) 
- `PushHandler#process` resolves the target Stacks via `Handler#stacks`, which uses `repository.full_name` — a completely different JSON field than the one used for signature selection: [4](#0-3) [5](#0-4) 
- `Repository.from_github_repo_name` splits `full_name` on `/` and does a plain `find_by(owner:, name:)` lookup with no relation back to `repository_owner`: [6](#0-5) 

Exploit flow: In a multi-org configuration (`Shipit.github_apps` keyed per organization, per `docs/setup.md`'s "Using Multiple GitHub Applications" schema), the attacker registers/owns `attacker-org` and knows its `webhook_secret` (they configured it themselves when installing their own GitHub App). They send `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<sha>",
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" }
}
```
signed with `X-Hub-Signature` computed using `attacker-org`'s real secret over the raw body. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` (a real, existing config) and the HMAC matches, so the request passes. `PushHandler` then looks up `Repository.from_github_repo_name("victim-org/victim-repo")` and, if that repo/stack exists in Shipit, calls `stack.sync_github(expected_head_sha: params.after)` on the victim's Stack — an operation the attacker has no authorization to trigger.

`drop_unhandled_event`, `ExplicitParameters` schema validation (`PushHandler` only requires `ref`/`after`, not owner-consistency), and `Repository`/`Stack` validations do nothing to prevent this divergence; none of them compare `repository_owner` to the owner segment of `repository.full_name`.

### Impact Explanation
An attacker with a legitimate, self-owned GitHub App/org registration in Shipit can force `GithubSyncJob` to run against an arbitrary victim Stack that they do not own or control, purely by crafting the `repository.full_name` field independently of the field used for signature verification. `GithubSyncJob` uses `stack.github_api` (`Shipit.github(organization: stack.repository.owner)`), i.e. it goes on to use the *victim's own* configured GitHub App to fetch real upstream commits and create `Shipit::Commit` records/trigger `CacheDeploySpecJob` for the victim's stack [7](#0-6) [8](#0-7) . This is an unauthenticated cross-tenant trigger: any org owner registered in Shipit can force sync/task-creation activity on any other tenant's Stack merely by mismatching the `owner` and `full_name` fields of a forged webhook, which is exactly the "payload for one repository mutating another's stack" Critical category. It is fully repeatable against any Stack/repository combination present in the Shipit instance, for any event type whose handler resolves the target via `repository.full_name` (push, status, check_suite, pull_request, etc.), since none of them cross-check against `repository_owner`.

### Likelihood Explanation
Preconditions: Shipit must be configured with the multi-organization `github_apps` schema (documented and supported) and the attacker must have legitimately registered/installed their own GitHub App for `attacker-org` in that config — a realistic scenario for any Shipit instance serving multiple external orgs/teams. No Shipit session, API token, or victim secrets are required; the attacker only needs their own real webhook secret, which they control by definition. The attack is a single crafted HTTP POST, trivially repeatable and scriptable, and requires no interaction from the victim.

### Recommendation
In `WebhooksController#verify_signature` and/or `Handler#stacks`, cross-validate that `repository_owner` (`repository.owner.login`) matches the owner segment of `repository.full_name` (or resolve the target Stack via `repository.owner.login` + `repository.name` rather than the independently-supplied `full_name`); reject the webhook (422) whenever they diverge.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "signed payload from attacker-org cannot target victim-org's stack via full_name mismatch" do
  victim_repo  = shipit_repositories(:shipit) # owner "shopify", stack fixture :shipit
  attacker_secret = "attacker-known-secret"
  Shipit.stubs(:github_app_config).with("attacker-org").returns(webhook_secret: attacker_secret)

  payload = {
    "ref" => "refs/heads/#{victim_repo.stacks.first.branch}",
    "after" => "deadbeef",
    "repository" => {
      "owner" => { "login" => "attacker-org" },
      "full_name" => victim_repo.full_name # "shopify/shipit-engine"
    }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", attacker_secret, payload)

  request.headers['X-Github-Event'] = 'push'
  request.headers['X-Hub-Signature'] = signature

  # binding under test: repository_owner ("attacker-org") == owner of repository.full_name ("shopify")?
  assert_not_equal "attacker-org", victim_repo.owner

  assert_no_enqueued_jobs(only: GithubSyncJob) do
    post :create, body: payload, as: :json
  end
  assert_response :ok # currently passes verify_signature and reaches PushHandler — vulnerability
end
```
Expected (fixed) behavior: request should be rejected with `422` because `repository_owner` ("attacker-org") does not match the owner segment of `repository.full_name` ("shopify"), and no `GithubSyncJob`/`Commit` should ever be created for `victim_repo`'s stack.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
