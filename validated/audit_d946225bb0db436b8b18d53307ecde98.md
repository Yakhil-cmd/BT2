### Title
Webhook signature verification silently bypassed when the attacker-controlled `repository`/`organization` field selects a GitHub App configured without a `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which HMAC secret) to validate an inbound webhook against by reading `repository_owner`, a value taken directly from the **unauthenticated** JSON body (`params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')`), *before* any signature check occurs: [1](#0-0) [2](#0-1) 

That organization name is used to look up the corresponding `GitHubApp` instance: [3](#0-2) 

and `GitHubApp#verify_webhook_signature` **unconditionally returns `true` if that org's `webhook_secret` is blank**: [4](#0-3) 

This binding breaks the equality the engine relies on: *"organization whose secret authenticated the request" == "organization/repository the payload claims and that handlers subsequently act on."* Because `repository_owner` is read from the untrusted payload before verification, and because the multi-org config schema explicitly allows (and the shipped example/dev configs show) an organization entry with `webhook_secret` left blank (`config/secrets.development.shopify.yml`, `config/secrets.development.example.yml`, `docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml` `OrgTwo`), an attacker who knows (or guesses) that such an organization is configured can craft a payload naming that organization and have `verify_webhook_signature` return `true` with **no valid HMAC at all**. The whole raw payload — including any other repository/organization identifiers used deeper in the handler logic (e.g. `push`, `membership`, `pull_request` handlers) — is then treated as authentic by `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [5](#0-4) 

### Impact Explanation
This crosses the "organization authenticated vs. repository/organization written" trust boundary called out in scope: an attacker who has no GitHub App credentials, no webhook secret, and no session can forge webhook events (push syncs, `membership` handlers that create/delete `Team`/`User`/`Membership` records, `pull_request` handlers that drive the merge queue, etc.) for any stack in the installation, as long as the target Shipit deployment has at least one configured organization with a blank `webhook_secret` — a configuration pattern that ships in the project's own example/dev secrets files and documentation. This can lead to spoofed CI/status/membership state and, through the `pull_request`/merge-queue handlers, influence over merge/deploy decisions — matching the High-severity criteria (escalation into authorization state, unauthenticated read/write of stack state) in scope.

### Likelihood Explanation
Likelihood is **conditional but realistic**: it requires the deployment to use the multi-organization config schema with at least one org lacking a `webhook_secret`. This is not a hypothetical corner case — it is exactly what the shipped `config/secrets.development.shopify.yml`, `config/secrets.development.example.yml`, and `docs/setup.md` multi-org example show as the "normal" template, and nothing in the code warns or fails loudly when a configured org has no secret (unlike the "unknown organization" case, which is logged and rejected). An operator who copies these templates for additional orgs without setting `webhook_secret` unknowingly leaves every org sharing that name fully open to spoofed webhooks.

### Recommendation
- Treat a missing/blank `webhook_secret` for a *configured* organization as a hard misconfiguration (raise/refuse to boot, or reject the webhook with 422) rather than silently trusting the payload (`lib/shipit/github_app.rb#verify_webhook_signature`).
- Do not derive the organization used for signature verification from the unauthenticated JSON payload; if this is unavoidable in multi-org setups, verify the signature against *all* configured organizations' secrets (or require a per-org path/token) rather than trusting the attacker-supplied `repository_owner`.
- Update the shipped example/dev secrets files and `docs/setup.md` to make `webhook_secret` mandatory for every organization to avoid encouraging this insecure pattern.

### Proof of Concept
1. Deploy Shipit with the multi-org schema, configuring `OrgTwo` (or any org) with `webhook_secret:` left blank, mirroring `config/secrets.development.shopify.yml`.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: membership` and a body such as:
   ```json
   {
     "action": "added",
     "organization": { "login": "OrgTwo" },
     "team": { "id": 1, "name": "Admins", "slug": "admins", "url": "https://example.com" },
     "member": { "login": "attacker-controlled-user" }
   }
   ```
   with no `X-Hub-Signature` header (or an arbitrary bogus one).
3. `verify_signature` resolves `repository_owner` = `"OrgTwo"`, calls `Shipit.github(organization: "OrgTwo").verify_webhook_signature(...)`, which returns `true` immediately because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`), bypassing authentication entirely.
4. `create` then dispatches the forged, unsigned payload to the real `membership` handler, creating/mutating `Team`/`User`/`Membership` records as if GitHub had sent it.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
