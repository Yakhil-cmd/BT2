### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled` gate, allowing unauthorized `ReviewStack` provisioning - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`provision?` intends to require `repository.review_stacks_enabled` for *all* provisioning behaviors, but Ruby's `&&`/`||` precedence only applies that gate to the `allow_all` branch. Repositories with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (or `prevent_with_label`) will still provision a `ReviewStack` from an attacker-labeled PR.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == true` must hold before `ReviewStackAdapter#create!` is invoked, for every provisioning behavior. The actual code is:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [3](#0-2) 

Because `&&` binds tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. The `review_stacks_enabled` check is scoped only to the first disjunct. For a repository with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label`, an attacker opens a PR against that repository and adds the label matching `repository.provisioning_label_name` (both label and PR content are attacker-controlled on a repo they can open PRs against). `pull_request_has_provisioning_label?` becomes true, the second disjunct evaluates true regardless of `review_stacks_enabled`, and `provision?` returns true [4](#0-3) . `process` then calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which unconditionally creates a `ReviewStack` row with `branch: params.pull_request.head.ref` [5](#0-4)  and enqueues it via `ReviewStackProvisioningQueue.add(stack)` [6](#0-5) , making the PR branch/`shipit.yml` eligible for provisioning/execution. No other guard intervenes: `Repository` model validations only constrain `owner`/`name` format, not `review_stacks_enabled` interaction with `provisioning_behavior` [7](#0-6) , and `ReviewStackAdapter#create!`/`find_or_create!` perform no re-check of `review_stacks_enabled` at all [8](#0-7) .

### Impact Explanation
An unprivileged GitHub user who can open a PR and label it on any repository configured with `review_stacks_enabled: false, provisioning_behavior: allow_with_label` (or `prevent_with_label`, by simply not adding the label) causes creation of a `Shipit::ReviewStack` (a `Shipit::Stack` subclass) that the repository owner explicitly disabled via `review_stacks_enabled = false`. This is a policy/authorization bypass: a record is written for a repository configuration that did not opt into this workflow, and the stack becomes eligible for provisioning and command execution against the attacker's own branch content (`shipit.yml`), matching the "unauthorized deploy" / cross-tenant-policy-mutation category of Critical impact. It is repeatable against any repository matching the precondition combination.

### Likelihood Explanation
Requires no secrets or privileged role — only that a target repository has `review_stacks_enabled: false` combined with `provisioning_behavior: allow_with_label` (or `prevent_with_label`), which per the `Repository` schema/enum are independent, plausible configuration states [9](#0-8) . Attacker cost is trivial: open a PR and add a label they control. This is a straightforward, deterministic bug (operator precedence), not a probabilistic race.

### Recommendation
Fix operator precedence so `review_stacks_enabled` gates every branch, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
