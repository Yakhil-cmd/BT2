### Title
Signed orders lack contract-binding (no `this_address`/verifying-AA equivalent) enabling cross-AA signature replay - ([File: formula/evaluation.js])

### Summary
Ocore's oscript signature primitive `is_valid_signed_package()` verifies only that a `signed_message` was signed by a given address — it does not bind the signature to the specific Autonomous Agent (AA) that is meant to consume it. This is the exact analog of the reported EIP-712 bug: the "domain" of the signed data omits the equivalent of `verifyingContract`, so the same signature can be validly replayed against any AA that shares the signing address's trust and the same field layout, exactly as a Hook bid signed for one `verifyingContract` could be replayed elsewhere once the wrong address was baked into the domain separator.

### Finding Description
The core hashing routine for signed packages, `getSignedPackageHashToSign`, hashes only `{signed_message, authors, last_ball_unit, version}` — there is no field that ties the signature to a specific consuming contract (AA) address: [1](#0-0) 

`is_valid_signed_package` in the formula evaluator then simply checks that the given address signed that content; it performs no check that the package was intended for `this_address` (the currently executing AA): [2](#0-1) 

Because the framework does not enforce contract-binding, it becomes the oscript author's responsibility to manually embed the AA's own address inside `signed_message` and check it, exactly as EIP-712 relies on developers to correctly set `verifyingContract`. The official sample `payment_channels.oscript` does this correctly by embedding a `channel` field and validating `trigger.data.sentByPeer.signed_message.channel != this_address`: [3](#0-2) 

However, the other official sample, `order_book_exchange.oscript`, omits this binding entirely. The order id is derived only from order content and `last_ball_unit`, never from `this_address`, and `is_valid_signed_package` is called without any check that the order was meant for this particular exchange AA: [4](#0-3) 

This mirrors the reported root cause precisely: the underlying primitive (EIP-712 domain separator / `getSignedPackageHashToSign`) does not fold in the identity of the "verifying contract" (AA address), so unless every author manually re-implements that binding (as `payment_channels.oscript` does but `order_book_exchange.oscript` does not), a signed authorization can be validly consumed by a different, unintended AA instance.

### Impact Explanation
If a second AA is deployed with the same or compatible `order_book_exchange`-style bytecode/logic (e.g., a fork, a copy-cat exchange, or a future version deployed by a different definer), a trader's previously signed order — intended only for interaction with one exchange AA — remains a valid, cryptographically verifiable input to any other AA that also accepts `is_valid_signed_package(order, order.address)` without checking a contract-identity field. An attacker or a second AA operator can submit that same signed order as a trigger to their own AA and have it executed there, causing the trader's balance bookkeeping in that AA to be debited/credited in a way the trader never authorized for that specific contract — the equivalent of unauthorized order execution / fund movement described in the source report as "signature collision and potential replay attacks."

### Likelihood Explanation
Any unprivileged AA author who copies or is inspired by the `order_book_exchange.oscript` sample (which is shipped as a canonical example in this repository) will reproduce the missing-binding pattern, since nothing in `is_valid_signed_package` or `getSignedPackageHashToSign` forces contract-binding by default. Given that one official sample (`payment_channels.oscript`) explicitly needs this manual defense and the other (`order_book_exchange.oscript`) omits it, the likelihood of real AAs shipping this bug is high and requires no privileged access — merely posting an AA trigger with a replayed signed order.

### Recommendation
Make the equivalent of EIP-712's `verifyingContract` a mandatory, automatically-enforced part of the signed-package hash rather than an opt-in convention:
- Extend `getSignedPackageHashToSign` (and/or `is_valid_signed_package`) to optionally or always incorporate the address of the AA invoking verification (`this_address`) into the hashed content, so a package signed for one AA cannot validate under a different AA by construction.
- At minimum, update documentation/samples so `is_valid_signed_package` usage always requires and enforces an explicit contract-binding field (as done in `payment_channels.oscript`), and audit/fix `order_book_exchange.oscript` to include such a check.

### Proof of Concept
1. Alice signs an order via `signMessage`/`is_valid_signed_package` intended for exchange AA `A` (bytecode = `order_book_exchange.oscript`), producing `signed_message = {address: Alice, sell_asset, buy_asset, sell_amount, price}` and a signature over `getSignedPackageHashToSign`.
2. A second AA `B` is deployed with identical or compatible oscript logic (same `if` clause calling `is_valid_signed_package(trigger.data.order1, $order1.address)`), with `B != A`.
3. Anyone (not necessarily Alice) submits Alice's already-published signed order as `trigger.data.order1` to AA `B`.
4. `is_valid_signed_package` succeeds in `B` exactly as it did in `A`, since neither `getSignedPackageHashToSign` nor `is_valid_signed_package` binds the package to `this_address` of the invoking AA — `formula/evaluation.js` lines 1653-1699 perform no such check.
5. AA `B` executes the trade against Alice's balance state within `B`, something Alice never authorized for contract `B`.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
