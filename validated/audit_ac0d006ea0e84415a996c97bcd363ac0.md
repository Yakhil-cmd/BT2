### Title
Session fixation on GitHub OAuth login — no session reset on privilege escalation (`[File: app/controllers/shipit/github_authentication_controller.rb]`)

### Summary
The reported Firedancer bug is a class of "trust binding" failure: a buffer is sized/managed for one context (a single transaction) but is silently reused across a broader context (multiple transactions), so state established before the loop is not re-validated/re-scoped for each iteration. The closest analog in shipit-engine that breaks a deployment-trust binding is the OAuth login flow, where the *session identifier established before authentication* is never invalidated once GitHub authentication succeeds — i.e., the binding "session id used pre-login" vs "session id trusted post-login (as an authenticated `User`)" is not enforced to be equal/rotated.

### Finding Description
`GithubAuthenticationController#callback` completes the OmniAuth GitHub flow and immediately writes the authenticated user identity into the *existing* session, without ever calling `reset_session`: [1](#0-0) 

Compare this to `Authentication#force_github_authentication`, which explicitly calls `reset_session` in the one place the engine authors did think about invalidating a session (when a stale/legacy GitHub token is detected): [2](#0-1) 

No equivalent `reset_session` exists on the success path of `callback`. `session[:user_id]` and `session[:authenticated]` are simply merged into whatever session container already existed for the browser at the time the OAuth dance began: [3](#0-2) 

The unprivileged-attacker-relevant binding this breaks: "the session an unauthenticated visitor is given" should not be trusted-equal to "the session used to identify an authenticated `User`" once authentication succeeds — the pre-auth session must be discarded/rotated at the trust boundary. Here it is not. Since `current_user` is derived purely from `session[:user_id]` (`app/controllers/concerns/shipit/authentication.rb:40-42`), whoever controls the *session container* at the time `session[:user_id]` is written controls `current_user` afterward, and no server-side session ID rotation occurs to defeat a fixed/known session.

### Impact Explanation
This maps directly to the "session fixation / forced OAuth completion" High-impact category defined by the engine's own trust model: an attacker able to fix or predict a victim's session (e.g., because the session cookie was set/observed before the trust boundary, such as via a shared parent-domain cookie, a proxy, or an earlier unauthenticated visit to `Shipit.host`) and who then lures the victim into completing the GitHub OAuth handshake, ends up with a session that is now bound to the victim's `User` record — because the engine never rotates or invalidates the session on privilege escalation. This grants the attacker `current_user`-level access (trigger deploys/rollbacks/tasks, create `ApiClient`s bound to the victim, etc.) without ever needing GitHub credentials, an `ApiClient` token, or a webhook secret.

### Likelihood Explanation
The engine relies entirely on `session[:user_id]` for authentication (`find_current_user`) and the only `reset_session` call in the authentication path is for the unrelated "stale legacy token" case, not for the login-success path. This is a structural gap rather than a one-off bug, and it requires no privileged credential, GitHub App key, webhook secret, or prior repository access — only the ability to have the victim's browser use a session container the attacker controls or knows before OAuth completion, which is exactly the scenario the "session fixation / forced OAuth completion" impact category is meant to cover.

### Recommendation
Call `reset_session` (and re-issue `session[:authenticated]`/`session[:user_id]` afterward) at the start of `GithubAuthenticationController#callback`, before trusting `request.env['omniauth.auth']`, mirroring the pattern already used in `Authentication#force_github_authentication`. This ensures the session identifier is rotated at every authentication-privilege boundary, not merely on detection of a stale legacy token.

### Proof of Concept
Conceptual PoC (cannot be executed in ask-only/no-filesystem mode, but the flaw is directly readable from the code):
1. Attacker visits the Shipit instance, obtains/knows a session cookie value `S` (e.g. via cookie injection on a shared parent domain, XSS on a co-hosted subdomain, or simply setting `S` in a link if the deployment's session store allows externally supplied IDs).
2. Attacker sends the victim a link to `/github/auth/github` while the victim's browser is using session `S`.
3. Victim completes the real GitHub OAuth login. `GithubAuthenticationController#callback` executes `session[:user_id] = sign_in_github(auth)` on session `S` without calling `reset_session`.
4. Attacker, who already possesses session `S`, is now authenticated as the victim, confirmed by `find_current_user` in `app/controllers/concerns/shipit/authentication.rb:40-42` returning the victim's `User` for any request bearing session `S`. [1](#0-0) [4](#0-3)

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      # We need to set this so that the /events and /sidekiq endpoint
