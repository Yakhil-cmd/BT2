### Title
Webhook signature verified against `repository.owner.login` while the synced Stack is resolved from a separate, unvalidated `repository.full_name` field, allowing cross-tenant forced `sync_github` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb, app/models/shipit/webhooks/handlers/push_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/secret to check the HMAC using `params.dig('repository','owner','login')`, but `Handler#repository_name`/`Handler#stacks` (used by `PushHandler#process`) resolve the target `Stack` using the independent `params.dig('repository','full_name')` field from the same JSON body. Because these two fields are never cross-checked, an attacker who controls a legitimate org/webhook_secret (OrgA) can sign a payload whose `repository.full_name` names an unrelated org's repo (OrgB), causing `Stack#sync_github` to run for OrgB's stack with an attacker-chosen `expected_head_sha`.

### Finding Description
The broken binding is:
`repository_owner_used_for_signature (params.dig('repository','owner','login'))` == `repository_owner_of_the_stack_synced (params.dig('repository','full_name').split('/').first)`

This equality is assumed by the system but never enforced.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` purely from `params.dig('repository', 'owner', 'login')` [1](#0-0)  and uses it to pick the `GitHubApp` (and thus the `webhook_secret`) via `Shipit.github(organization: repository_owner)` [2](#0-1) .
2. If that org's secret verifies the HMAC, the request proceeds and `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs [3](#0-2) .
3. `PushHandler#process` looks up stacks via `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` [4](#0-3) .
4. `Handler#stacks` and `Handler#repository_name` derive the target repository from `payload.dig('repository', 'full_name')`, a completely separate JSON field from `repository.owner.login` used for signing [5](#0-4) .
5. `Repository.from_github_repo_name` splits `full_name` on `/` and does an independent DB lookup by `owner`/`name`, with no reference to which org's secret validated the request [6](#0-5) .

Because JSON allows `repository.owner.login` and `repository.full_name` to disagree, an attacker who owns/controls OrgA (and thus its `webhook_secret`) can sign a push payload with `repository.owner.login`="OrgA" (so verification passes using OrgA's secret) while setting `repository.full_name`="OrgB/production-repo" (so the handler acts on OrgB's stack). No existing guard checks this: `verify_signature` never inspects `full_name`, and `PushHandler`'s `ExplicitParameters` schema only requires `ref` and `after`, not that `full_name`'s owner matches the verified organization [7](#0-6) .

The exploit request: `POST /webhooks` with header `X-Github-Event: push`, `X-Hub-Signature` computed with OrgA's `webhook_secret`, and body containing `repository: {full_name: "OrgB/production-repo", owner: {login: "OrgA"}}, ref: "refs/heads/main", after: "<attacker-chosen sha>"`.

### Impact Explanation
`stack.sync_github(expected_head_sha: <attacker sha>)` is invoked for OrgB's stack — a record write/action for a repository that did not authenticate the request, satisfying "a payload for one repository mutating another's stack." `sync_github` enqueues `GithubSyncJob`, which fetches commits via the stack's own `github_api`/GitHub App credentials and can append commits reachable from the attacker-named sha [8](#0-7) . If OrgB's stack has `continuous_deployment` enabled, appended/undeployed commits become eligible for automatic deploy via the continuous delivery machinery, meaning the attacker can effectively force a commit selection for OrgB's deploy pipeline using nothing but their own org's webhook secret. This is a cross-tenant confused-deputy: any org configured in `Shipit.github` can target any other org/stack, and the attack is trivially repeatable against arbitrary `full_name`/branch/sha combinations. This matches "Critical - a payload for one repository mutating another's stack ... or an unauthorized deploy."

### Likelihood Explanation
Preconditions: Shipit must be configured with more than one GitHub org (`Shipit.github(organization: ...)` multi-tenant mode) and the target Stack must exist for `branch` with `continuous_deployment` enabled — both realistic, commonly-documented Shipit deployments. The attacker only needs to control/register one org as a GitHub App/org in Shipit's config (their own throwaway org) and know its `webhook_secret` — a resource they legitimately possess, no privileged access to OrgB required. Constructing the payload and signature is a single HTTP request, fully repeatable and requires no live GitHub interaction.

### Recommendation
Cross-validate `repository.owner.login` against `repository.full_name` before dispatching to handlers, e.g. in `WebhooksController#verify_signature` (or centrally in `Handler#stacks`), assert `params.dig('repository','full_name').split('/').first.casecmp?(repository_owner)` and reject (422) on mismatch. Alternatively, derive `repository_name` used by `Handler#stacks` from the already-verified `repository_owner` plus the repo's `name` field rather than trusting the client-supplied `full_name` independently.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (minitest, no live GitHub)
test "push signed by OrgA cannot sync/deploy OrgB's stack" do
  # Configure two orgs in Shipit.github secrets: OrgA (attacker-controlled) and OrgB (victim)
  org_a_secret = "org-a-secret"
  org_b_stack = shipit_stacks(:org_b_production) # continuous_deployment: true, branch: 'main', repository.full_name: 'OrgB/production-repo'

  attacker_sha = "a" * 40
  payload = {
    ref: "refs/heads/main",
    after: attacker_sha,
    repository: {
      full_name: "OrgB/production-repo",
      owner: { login: "OrgA" }
    }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", org_a_secret, payload)
  request.headers['X-Github-Event'] = 'push'
  request.headers['X-Hub-Signature'] = signature

  # Sanity: verify OrgA's secret indeed matches OrgA's org, not OrgB's, before tracing
  assert_equal "OrgA", JSON.parse(payload).dig("repository", "owner", "login")
  assert_equal "OrgB", JSON.parse(payload).dig("repository", "full_name").split("/").first

  Shipit::Stack.any_instance.expects(:sync_github).with(expected_head_sha: attacker_sha)

  post :create, body: payload, as: :json
  assert_response :ok # signature verified using OrgA's secret, yet OrgB's stack was targeted
end
```
This asserts both sides of the binding explicitly (`OrgA` for signature verification vs `OrgB` for the stack acted upon) and shows they diverge while `sync_github` is still invoked for OrgB's stack.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
