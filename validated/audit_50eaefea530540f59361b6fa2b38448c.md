### Title
Cross-organization `Team` collision via unscoped `github_id` lookup in `MembershipHandler` allows escalation into `Shipit.github_teams` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` solely by `params.team.id` (GitHub's global team numeric id), never checking that `params.organization.login` matches the `organization` already stored on that `Team` row. Any GitHub organization legitimately onboarded into Shipit (i.e. configured with its own `webhook_secret`) can therefore deliver a validly-signed `membership` webhook whose `team.id` collides with the `github_id` of a `Team` that belongs to a *different*, privileged organization, and cause `team.add_member(member)` to add an attacker-chosen user to that privileged `Team`.

### Finding Description
The binding assumed safe is: *the `Team` row matched by `find_or_create_by!(github_id: params.team.id)` belongs to the organization whose signature verified the webhook*, i.e. `team.organization == repository_owner_verified_by(webhook_secret)`. This binding is not enforced.

Code path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) verifies the HMAC using `Shipit.github(organization: repository_owner)`'s `webhook_secret` — this only proves the request came from *some* org onboarded to Shipit whose secret matches `repository_owner` (here, `organization.login` in the payload for a `membership` event). It does not restrict which `team.id` values that org is allowed to reference.
- `MembershipHandler#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`) does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }`. The block that sets `organization`/`slug`/etc. only executes on **creation**. If a `Team` row with that `github_id` already exists (e.g. a privileged team seeded/created earlier for organization Y), `find_or_create_by!` returns the existing record unchanged — its `organization` still reads `Y`, but the handler proceeds to operate on it based on an X-signed webhook.
- `MembershipHandler#process` (lines 22-34) then unconditionally calls `team.add_member(member)` for `action == 'added'`, with no check that `team.organization == params.organization.login`.
- `Team#add_member` (`app/models/shipit/team.rb:41-43`) appends the member with no authorization check.
- `User#authorized?` (`app/models/shipit/user.rb:80-82`) grants privileged access if `teams.where(id: Shipit.github_teams.map(&:id)).exists?`. If the collided `Team`'s primary key `id` is one of `Shipit.github_teams.map(&:id)`, the attacker-controlled `member` becomes authorized.

Attack: attacker controls organization X, which is a GitHub org legitimately onboarded to Shipit (its own `webhook_secret` configured, so its real `membership` webhooks pass `verify_signature`). Attacker creates/uses a team in X whose GitHub-assigned numeric team id happens to equal the `github_id` of a pre-existing privileged `Team` row (belonging to organization Y, referenced in `Shipit.github_teams`). Attacker adds any GitHub user (including themselves) to that team in X. GitHub delivers a correctly-signed `membership` "added" webhook to Shipit with `team.id` = colliding id and `organization.login` = X. `find_or_create_team!` returns the existing privileged `Team` (organization Y) instead of creating a new X-scoped team, and `team.add_member` adds the attacker's user to it.

No existing guard prevents this: `verify_signature` only authenticates the org, not the `team.id` namespace; the `ExplicitParameters` schema only enforces types/presence, not cross-field consistency between `team.id` and `organization.login`; there is no validation on `Team` tying `github_id` to `organization` at write time in this handler.

### Impact Explanation
A successful collision lets an attacker-controlled GitHub user become a member of a `Team` row whose `id` is listed in `Shipit.github_teams`, which flips `User#authorized?` to `true` for that user — full authorization bypass into Shipit's privileged-team gate (`app/models/shipit/user.rb:80-82`). This is repeatable for any privileged `Team`/organization pair whose `github_id` the attacker can align with a team they control, and is not limited to one repository — authorization is global once granted. This matches the **High** severity category: "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Preconditions: (1) Shipit must be configured multi-tenant, trusting more than one GitHub organization (attacker's org X must be legitimately onboarded with its own `webhook_secret`) — this is a normal Shipit deployment pattern (`Shipit.github(organization:)` supports per-org config). (2) The attacker needs a team in org X whose numeric `github_id` collides with the target privileged `Team`'s `github_id`. GitHub team ids are globally sequential, not attacker-chosen, so exact collision against an already-existing arbitrary id is not trivially attacker-controlled in general; however, it becomes highly likely in common real-world conditions such as: newly provisioned Shipit + GitHub environments where ids are low/sequential, staging/test environments, or organizations created close in time to the target — and the underlying code flaw (no organization-scoping of `github_id`) is deterministic and always exploitable given any id match, with no additional secret knowledge required beyond controlling org X's own webhook delivery.

### Recommendation
Scope the `Team` lookup/creation by both `github_id` and the verified `organization`, and reject (or create a distinct row for) memberships where `params.organization.login` does not match the found `Team#organization`. For example, in `find_or_create_team!`, look up by `github_id` and `organization: params.organization.login` together (or add a uniqueness validation on `[:github_id, :organization]` and raise/`return` if a `github_id` collision is detected across a different `organization`), and add an explicit guard in `process` before calling `team.add_member`/`team.members.delete` asserting `team.organization == params.organization.login`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_collision_test.rb
test "cannot escalate into a privileged Team from a different organization via team.id collision" do
  privileged_team = Shipit::Team.create!(
    github_id: 42,
    organization: 'legit-org',
    slug: 'admins',
    name: 'Admins',
    api_url: 'https://api.github.com/teams/42'
  )
  attacker_user = shipit_users(:walrus) # some user record

  payload = {
    'action' => 'added',
    'team' => { 'id' => 42, 'name' => 'evil-team', 'slug' => 'evil-team', 'url' => 'https://api.github.com/teams/42' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => attacker_user.login }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)

  privileged_team.reload
  # BINDING VIOLATED: attacker's user added to the privileged Team belonging to 'legit-org'
  assert_includes privileged_team.members, attacker_user
  assert_equal 'legit-org', privileged_team.organization # organization field unchanged, yet membership mutated
end
```

          team = find_or_create_team!
