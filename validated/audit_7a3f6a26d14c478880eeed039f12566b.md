### Title
Unauthenticated organization impersonation via `webhook_secret`-less signature bypass leads to forged `membership` webhooks escalating into `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's HMAC secret to check against by reading an unauthenticated field straight out of the still-unverified JSON body, and `GithubApp#verify_webhook_signature` treats a missing/blank `webhook_secret` as an automatic pass. Because `webhook_secret` is documented as optional per-organization, any organization configured without one accepts arbitrary forged webhook deliveries. This is functionally the same class of bug as the ABDKMathQuad report: a payload-driven decision (which trust domain a value belongs to) that is never actually bound by the cryptographic check meant to protect it. The concrete exploitable consequence is a forged `membership` event that creates a `Shipit::Membership` row linking an attacker-chosen GitHub login to an existing `Shipit::Team`, which flips `User#authorized?` to true and grants full application access — an escalation into `Shipit.github_teams` authorization.

### Finding Description
`verify_signature` derives the organization used for verification entirely from the (still unauthenticated) request body: [1](#0-0) [2](#0-1) 

That organization's `GithubApp` instance is then used to check the signature: [3](#0-2) 

`return true unless webhook_secret` means that for any configured organization that has not set a `webhook_secret` (explicitly documented as optional in `docs/setup.md`), **all requests are treated as verified regardless of the `X-Hub-Signature` header or body**. Since `repository_owner` (the value that decides *which* organization's — possibly secret-less — trust context is used) comes from the attacker-controlled payload itself, an attacker can freely pick any organization known to the Shipit instance that lacks a webhook secret and have their forged payload accepted as legitimate.

Once accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw, attacker-supplied `params` to handlers with no further validation: [4](#0-3) 

The `membership` handler (exercised by test fixtures) creates users/teams/memberships purely from payload fields such as `member.login` and `team.id`: [5](#0-4) [6](#0-5) 

A `Membership` row directly satisfies `User#authorized?`, which is the sole gate protecting every engine controller: [7](#0-6) [8](#0-7) 

**Binding broken (equality):**
`organization_verified_by_signature == organization_whose_team_membership_is_written`
When `webhook_secret` is blank for the org selected by the attacker-controlled `repository_owner` field, the left side of this equality is vacuously true for *any* payload, so the binding collapses entirely — the "signature" no longer proves anything about the payload's origin, yet the `membership` handler still trusts and acts on that payload's `team`/`member` fields.

### Impact Explanation
A successful forged `membership` webhook lets an unauthenticated network attacker add an arbitrary GitHub login to any existing `Shipit::Team` (referenced by a guessable/enumerable numeric `id`), which via `User#authorized?` grants that login full, authenticated access to the Shipit UI/API for every stack — deploys, rollbacks, secrets exposure in task output, etc. This matches the High-impact category "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Likelihood depends entirely on whether an organization configured in the multi-org `Shipit.github` config has an empty/unset `webhook_secret` — a state explicitly presented as valid and optional in `docs/setup.md`, and reachable without any privileged credential, GitHub App key, or `ApiClient` token. Any Shipit deployment supporting several organizations (as shown by the multi-org fixture `test/dummy/config/secrets_double_github_app.yml`) where at least one org omits the secret is directly exploitable by a fully unauthenticated internet attacker who simply knows the `/webhooks` endpoint and one valid org/team id (both discoverable via normal, unauthenticated use of the Shipit UI).

### Recommendation
- Make `webhook_secret` mandatory for every configured GitHub organization; refuse to boot (or refuse to accept webhooks for) any org lacking one, instead of silently returning `true` from `verify_webhook_signature`.
- Do not let the payload itself determine which trust domain (organization secret) is used to verify itself; resolve `repository_owner`/organization from data already known to Shipit (e.g. the target `Stack`/`Repository` record) rather than from unauthenticated JSON.
- In the `membership` handler, cross-check that the webhook's asserted `organization.login`/`team` actually belongs to the organization whose secret validated the request before creating/altering `Membership` records.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgOne` (has `webhook_secret`) and `OrgTwo` (no `webhook_secret`), as in `test/dummy/config/secrets_double_github_app.yml`.
2. As an unauthenticated network client, `POST /webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": { "login": "OrgTwo" },
  "team": { "id": <existing Shipit::Team id in Shipit.github_teams> },
  "member": { "login": "attacker-github-login" }
}
```
No valid `X-Hub-Signature` is required — `verify_webhook_signature` returns `true` because `OrgTwo` has no `webhook_secret`.
3. `WebhooksController#create` dispatches the payload to the membership handler, which creates/finds `User(login: "attacker-github-login")` and inserts a `Membership` linking it to the targeted team, exactly as exercised in `test/controllers/webhooks_controller_test.rb:159-165`.
4. The attacker then authenticates to Shipit via the normal GitHub OAuth login flow (`app/controllers/shipit/github_authentication_controller.rb`) using the `attacker-github-login` GitHub account; `User#authorized?` now returns `true` due to the forged `Membership`, granting full access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
