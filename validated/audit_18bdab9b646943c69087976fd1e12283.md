### Title
Unauthenticated stack lock/backlog/merge-status disclosure via `MergeStatusController#check` - (File: app/controllers/shipit/merge_status_controller.rb)

### Summary
`Shipit::MergeStatusController#check` is exempted from `force_github_authentication` via `skip_authentication only: %i[check show]`, but unlike its sibling action `show`, it never re-checks `current_user.logged_in?` before exposing the stack's internal `merge_status` (`locked`, `backlogged`, `failing`, `pending`, etc.) through the HTTP status code (200 vs 503) and the response body. This lets any unauthenticated caller probe arbitrary org/repo pairs via the `referrer` param and learn private deploy-pipeline state.

### Finding Description
The broken binding: `stack.merge_status` (internal lock/backlog/CI state) should be disclosed only when `current_user.logged_in?` == `true`, matching the guard already present in `show`: [1](#0-0) 
`show` explicitly renders `'logged_out'` and skips rendering `stack_status` unless the user is logged in. `check`, registered in the very same `skip_authentication` list, has no such guard: [2](#0-1) 
`stack_status` resolves the stack purely from request params — either `stack_id` or, more relevant to the attack, from the `referrer` URL's org/repo (case-insensitively) plus `branch` (defaulting to `production`) — with no ownership or session check at all: [3](#0-2) 
An attacker sends `GET /merge_status/check?referrer=https://github.com/<org>/<repo>/pull/1` (optionally with `&branch=<name>`) with zero cookies/headers. If a stack matching that org/repo/branch exists, the response is `200 ok` (merge_status success) or `503 <state>` where `<state>` is the literal internal status string (e.g. `locked`, `backlogged`, `pending`, `failing`) taken from `Stack#merge_status`. This distinguishes: (a) whether the org/repo/branch has a configured Shipit stack at all, and (b) its current lock/backlog/CI state — all without authentication. `force_github_authentication` (which would normally gate all controller actions) is bypassed entirely for `check`: [4](#0-3) 
No other guard (`ExplicitParameters`, model validations, `require_permission!`, `EnvironmentVariables#permit`) applies to this read-only path, and comparable read endpoints such as `Api::CCMenuController` do enforce `require_permission :read, :stack` before exposing deploy state — confirming `check`'s omission is inconsistent with the rest of the engine's authorization model. [5](#0-4) 

### Impact Explanation
This is an unauthenticated read of internal stack state — matching the "unauthenticated read of stack state" High-severity category. Any internet caller can, for any org/repo/branch they can guess, learn (a) whether a Shipit stack is configured for it, and (b) live lock/backlog/CI-failure status, repeatable indefinitely and across arbitrary tenants/org-repo pairs hosted on the same Shipit instance, since resolution is keyed purely off attacker-supplied `referrer`/`branch` strings with no per-tenant authorization. This does not itself grant write access, execute commands, or leak credentials/tokens, but it discloses information (`show`'s own logic treats this as sensitive enough to gate behind login) to unauthorized parties and can be used to time or profile a target org's deploy pipeline.

### Likelihood Explanation
Preconditions are minimal: the target Shipit instance must have `check` mounted (default route, `/merge_status/check`) and at least one `Stack` configured for the guessed org/repo/branch. No Shipit or GitHub secrets, sessions, or team membership are required — `check` is unconditionally listed in `skip_authentication`. Attacker cost is a single unauthenticated HTTP GET request per probe; this is trivially automatable and repeatable.

### Recommendation
Add the same authorization guard used in `show` to `check` — require `current_user.logged_in?` (and ideally `current_user.authorized?`) before computing/rendering `stack_status`, returning a generic response (e.g., 404/403) for anonymous callers instead of leaking merge state via status code and body.

### Proof of Concept
```ruby
# test/controllers/merge_status_controller_test.rb (conceptual addition)
test "GET check without any session discloses locked state" do
  session.delete(:user_id) # no ApiClient token, no session, unauthenticated
  stack = shipit_stacks(:shipit)
  stack.update!(lock_reason: 'Maintenance operation')

  get :check, params: { referrer: "https://github.com/#{stack.repo_owner}/#{stack.repo_name}/pull/1", branch: stack.branch }

  # Binding under test: unauthenticated caller should NOT learn internal lock state,
  # i.e. response.status should equal what an anonymous `show` request returns (200/blank),
  # not encode `stack.merge_status`.
  assert_response :success          # currently fails: renders 503
  assert_not_includes response.body, 'locked'  # currently fails: body == 'locked'
end
```
This demonstrates that `check`, unlike `show` (which returns blank/login-prompt for anonymous users), leaks `stack.merge_status` via HTTP status and body with zero authentication.
