Now I found the critical piece: `StatusHandler#process` matches on `Commit.where(sha: params.sha)` **globally, with no repository/stack scoping at all**, and `Status#create_status_from_github!` sets a commit's CI state to `success`, which directly triggers `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → an actual `Deploy` when the stack has `continuous_deployment` enabled.

### Title
Cross-repository forged CI status triggers unauthorized continuous deployment - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `status` webhook handler resolves the target `Commit` purely by SHA, without verifying that the `repository` field in the payload (which is bound to the signature-verifying organization) matches the `stack`/`repository` that owns that commit. Combined with the fact that `verify_webhook_signature` binds trust only to `repository.owner.login` while the payload's SHA is applied against a global `Commit` lookup, an attacker who controls (or gets GitHub to sign) a webhook for **any** repository configured on the Shipit instance can create a forged `success` status for a commit SHA that happens to also exist in an unrelated, higher-privilege stack (e.g., a shared/vendored commit, cherry-pick, or SHA collision across mirrored/forked repos tracked by the same Shipit instance), causing that other stack to deploy.

### Finding Description
`WebhooksController#verify_signature` derives `repository_owner` from `params.dig('repository', 'owner', 'login')` and verifies the signature using the GitHub App configured **for that organization**: [1](#0-0) 

However, the equality the app implicitly assumes — "organization whose secret signed the payload" == "repository the payload event actually writes to" — is never enforced. `Handlers::StatusHandler#process` resolves the target purely from the attacker-controlled `sha` field with **no repository or stack constraint whatsoever**: [2](#0-1) 

`Commit#create_status_from_github!` then creates a `Status` row, and `Status` has an `after_commit` callback that unconditionally schedules continuous delivery for whichever stack owns that commit: [3](#0-2) 

`Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob#perform` triggers `stack.trigger_continuous_delivery`, which builds and enqueues a real `Deploy` if `continuous_deployment?` is enabled and no lock/occupied state blocks it: [4](#0-3) [5](#0-4) 

Because `StatusHandler` never checks `payload.dig('repository','full_name')` (unlike `PushHandler`, which does scope via `Handler#stacks`/`#repository_name`), the binding "organization authenticated by signature" ≠ "stack whose commit received the forged status" is broken. Any Shipit instance tracking multiple repositories/orgs (a documented, supported configuration — `config/secrets.*.yml` explicitly supports a `github:` map keyed by multiple organizations) is exposed: a webhook correctly signed for organization A can still write a `success` status onto a commit SHA that belongs to a stack tracked under organization B, as long as that SHA exists as a `Commit` row in Shipit's database (e.g. shared history from a fork, template repo, subtree, or monorepo split into multiple tracked stacks with overlapping SHAs).

### Impact Explanation
This breaks the "an organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. The concrete effect is an **unauthorized deploy**: a stack with `continuous_deployment: true` can be deployed by an attacker who never had commit or repository access to that stack, merely by causing (or replaying) a signed `status` event from a *different, unrelated* organization/repository they do control, as long as they can produce a matching commit SHA tracked in Shipit's `commits` table. This matches the report's "unbounded trust window" bug class analog: the webhook payload's `sha` field is acted upon system-wide, while only `repository.owner` is checked by signature verification — a payload field acted on but never covered by the verified binding to the target resource.

### Likelihood Explanation
Requires the attacker to control at least one repository/organization already integrated with the same Shipit instance (a normal, low-privilege scenario for large deployments with many tracked stacks/teams) and to find or engineer a SHA collision or shared commit between their repo and the victim stack's repo (e.g., forked repos, template repos, monorepo-derived stacks, or commit reused across mirrors) — plausible in shared/organizational deployments of Shipit but not trivial to hit against an arbitrary unrelated victim.

### Recommendation
In `Handlers::StatusHandler` (and any other handler resolving records purely by SHA/id), scope the `Commit` lookup to the repository derived from `payload.dig('repository', 'full_name')`, exactly as `Handler#stacks`/`#repository_name` already does for `PushHandler`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining through `Repository.from_github_repo_name(repository_name)`.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `org-a` and `org-b`, each with its own `webhook_secret` (documented multi-org configuration in `config/secrets.development.shopify.yml`).
2. Create a stack for `org-b/victim-repo` with `continuous_deployment: true`, and ensure it has an undeployed commit with SHA `deadbeef...` (this SHA can be engineered/shared, e.g., by cherry-picking the exact victim commit into `org-a/attacker-repo`, which produces the identical SHA, then having it synced into Shipit via the normal `push` webhook of `org-a`).
3. As the owner of `org-a/attacker-repo`, trigger a real GitHub `status` webhook (properly signed with `org-a`'s `webhook_secret`) reporting `state: success` for SHA `deadbeef...` with `repository.full_name = "org-a/attacker-repo"`.
4. `WebhooksController#verify_signature` verifies successfully against `org-a`'s secret. `StatusHandler#process` matches `Commit.where(sha: "deadbeef...")`, finds the commit belonging to `org-b/victim-repo`'s stack, and creates a `success` `Status` for it.
5. `Status#schedule_continuous_delivery` fires, `ContinuousDeliveryJob` runs, and `org-b/victim-repo`'s stack deploys the commit — despite the attacker never having write access to `org-b`.

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin
        trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
      rescue Task::ConcurrentTaskRunning
      end
    end
