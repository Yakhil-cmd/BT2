### Title
Fork PR `shipit.yml` `machine.environment` unfiltered into `deploy.override` process env, enabling `RUBYOPT` injection / RCE - (File: `app/models/shipit/deploy_spec.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/command.rb`)

### Summary
`DeploySpec#machine_env` returns the raw `config('machine', 'environment')` hash parsed straight from the checked-out `shipit.yml`, and `TaskCommands#env` merges it unfiltered into the environment passed to `Command.new`. Because a `ReviewStack`'s working directory is checked out from the fork PR's own branch, an unprivileged fork author fully controls this hash and can set `RUBYOPT`, which then overrides the sanitized `Bundler.unbundled_env` base in `Command#unbundled_env` and gets injected into every `ruby`/`bundle`/`rake` invocation of the `deploy.override` steps, including on `prevent_with_label` repos.

### Finding Description
The broken binding: the code implicitly assumes `deploy_spec.machine_env == config('machine','environment')` is a value that only a trusted maintainer of the merged branch controls, but for a `ReviewStack` it is instead `config('machine','environment') == <fork_author_controlled shipit.yml>`.

Trace:
- `DeploySpec::FileSystem#initialize` reads config from `@app_dir` [1](#0-0) , and that `@app_dir` is the task's working directory checked out from the stack's `branch` — for review stacks this branch is `params.pull_request.head.ref`, i.e., the fork branch, set at stack creation time [2](#0-1) .
- `DeploySpec#machine_env` returns `config('machine', 'environment') || {}` verbatim, with no allow-list filtering [3](#0-2) . This is unlike `deploy_variables`/`rollback_variables`, which are passed through `EnvironmentVariables#permit` via `filter_deploy_envs`/`filter_rollback_envs` [4](#0-3) .
- `TaskCommands#env` merges `deploy_spec.machine_env` directly into the hash later passed to `Command.new(command_line, env:, ...)` for every deploy step, including `deploy.override` steps [5](#0-4) .
- `Command#unbundled_env` computes `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — `BASE_ENV` is derived from `Bundler.unbundled_env`/`Bundler.clean_env`, which strips Bundler/Ruby pollution such as `RUBYOPT`, but the attacker-supplied `@env` (containing `RUBYOPT`) is merged last and wins [6](#0-5) [7](#0-6) .
- `Command#start` spawns the process with this env via `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [8](#0-7) .

Exploit flow: attacker opens a PR from their own fork with `.shipit/shipit.yml` containing:
```yaml
machine:
  environment:
    RUBYOPT: "-r/path/to/evil"
deploy:
  override:
    - "bundle exec rake deploy"
```
On a `prevent_with_label` repo, the review stack is created/unarchived per `LabeledHandler`/`ReviewStackAdapter` logic once the provisioning label state matches (`archive?`/`unarchive?` derived from `provisioning_behavior_prevent_with_label?` and the label's presence) [9](#0-8) . Regardless of the label-gating semantics, once the review stack is provisioned and a deploy task runs against the fork branch's checked-out `shipit.yml`, the `deploy.override` step's `Command` inherits `RUBYOPT` set by the fork author, causing any `ruby`/`bundle`/`rake` invocation to `require` the attacker's file at startup — arbitrary Ruby code execution on the deploy host.

No existing guard intercepts this: `filter_deploy_envs`/`filter_rollback_envs` only apply to `deploy.variables`/`rollback.variables`, not to `machine.environment`; there is no allow-list, no key denylist (e.g., for `RUBYOPT`, `BUNDLE_GEMFILE`, `LD_PRELOAD`), and no signature/permission check gates the *content* of the fork's `shipit.yml` before it's parsed and merged into the spawn env.

### Impact Explanation
This yields Critical Remote Code Execution on the Shipit deploy host: `RUBYOPT=-r/path/to/evil` forces every subsequent `ruby`, `bundle`, or `rake` invocation in the `deploy.override` phase to load attacker-controlled code before doing anything else, running with the privileges of the Shipit deploy worker (which typically holds `GITHUB_TOKEN`/deploy credentials, filesystem access, and network access to internal infrastructure). It is repeatable for any repository configured with review stacks and `prevent_with_label` (or `allow_with_label`, which shares the same `machine_env` code path) by any GitHub user capable of opening a pull request from a fork.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` and use ReviewStacks with a fork-based PR workflow; the attacker needs no special privileges beyond opening a PR from their own fork and getting a review stack provisioned (which, depending on label workflow, may just require the PR being open with the repo's default label state, or getting any collaborator to apply/keep the provisioning label as normal review workflow does). The attacker cost is minimal — a single YAML file — and the vulnerability is deterministic and fully reproducible without any GitHub secrets or live API dependency.

### Recommendation
Do not allow arbitrary `machine.environment` keys to override the base process environment for review-stack tasks controlled by untrusted branches. Concretely:
- Apply an allow-list (similar to `EnvironmentVariables#permit` for `deploy_variables`) to `machine_env`, or explicitly deny known dangerous keys (`RUBYOPT`, `BUNDLE_GEMFILE`, `GEM_PATH`, `LD_PRELOAD`, `RUBYLIB`, etc.).
- For `ReviewStack` tasks specifically, ignore or strictly sanitize `machine.environment` sourced from fork branches, or require it to come from the base repository's trusted configuration rather than the PR head.
- In `Command#unbundled_env`, re-apply `Bundler.unbundled_env`/`clean_env` sanitization *after* merging `@env`, so fork-supplied keys cannot resurrect stripped Ruby/Bundler environment variables.

### Proof of Concept
minitest plan (`test/unit/task_commands_test.rb` or `test/models/deploy_spec_test.rb`):
1. Build a `Shipit::ReviewStack` whose `branch` points to a fixture fork checkout containing a `shipit.yml` with:
   ```yaml
   machine:
     environment:
       RUBYOPT: "-r/tmp/evil_marker"
   deploy:
     override:
       - "ruby -e 'File.write(%(/tmp/evidence), ENV[%(RUBYOPT)])'"
   ```
2. Instantiate `Shipit::DeploySpec::FileSystem.new(app_dir, review_stack)` against that checkout and assert:
   `deploy_spec.machine_env == { "RUBYOPT" => "-r/tmp/evil_marker" }`
3. Build `TaskCommands.new(task).perform` (or directly call `TaskCommands#env`) and assert:
   `task_commands.env["RUBYOPT"] == "-r/tmp/evil_marker"`
4. Construct `Shipit::Command.new(command_line, env: task_commands.env, chdir: ...)` and assert that:
   `command.unbundled_env["RUBYOPT"] == "-r/tmp/evil_marker"`
   (i.e., it survived the `Bundler.unbundled_env`/`BASE_ENV` sanitization), proving the binding "the `deploy.override` step inherits no fork-controllable key such as `RUBYOPT`" is false: `env_reaching_PTY_spawn["RUBYOPT"] == "-r/tmp/evil_marker"` while the intended invariant requires `env_reaching_PTY_spawn["RUBYOPT"] == nil`.
