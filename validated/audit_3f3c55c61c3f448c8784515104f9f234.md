### Title
`StacksController#create` lets a stack-scoped API token write a stack for any repository, bypassing the token-to-stack authorization binding - ([File: app/controllers/shipit/api/stacks_controller.rb])

### Summary
The external report describes an LSP0/LSP20 pattern where a pre-execution permission check ("post-execution check required") is disconnected from the actual side-effect that ultimately runs, because the two are never bound together (the delegatecall can destroy the contract before the follow-up check fires). The same class of bug — a *permission check disconnected from the resource actually acted upon* — exists in Shipit's API: `ApiClient#check_permissions!` only checks that the token has the `write:stack` permission string, but never checks that the target of the `create` action matches the single stack the token was scoped to via `stack_id`.

### Finding Description
`ApiClient` supports being scoped to a single stack via `belongs_to :stack, optional: true` / `stack_id` [1](#0-0) . `BaseController#stacks` enforces this scoping for reads and for any action that resolves an existing stack: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `#stack` calls `stacks.from_param!(params[:id])` [2](#0-1) .

Permission enforcement itself is scope-string-only and target-agnostic: `check_permissions!(operation, scope)` merely checks `permissions.include?("#{operation}:#{scope}")` — it has no notion of *which* stack is being operated on [3](#0-2) .

`StacksController#create` requires only the `write:stack` permission (`require_permission :write, :stack, only: %i[create update destroy]`) and then builds a brand-new `Stack` directly from attacker-supplied `repo_owner`/`repo_name`/`environment`/`branch`, via `Repository.find_or_create_by(owner: repo_owner, name: repo_name)` — with no reference to `stacks` or `current_api_client.stack_id` at all: [4](#0-3)  and [5](#0-4) .

By contrast, `update` and `destroy` correctly route through `stack` → `stacks.from_param!`, which *does* enforce the stack_id binding [6](#0-5) , and `index` explicitly documents/test-covers that a stack-scoped client "will only see that one stack" [7](#0-6) .

This is the exact equality binding called out in scope: **a stack a token authorises (its assigned `stack_id`) versus a stack it touches (any repository/environment reachable through `create`)**. Just as the LSP20 post-execution check never verifies the delegatecall didn't already destroy the account, `require_permission :write, :stack` on `create` never verifies the acted-upon resource is the one the token is authorized for — because for `create` there is no pre-existing resource to compare against, and the code doesn't restrict creation to the client's own repo/stack namespace at all.

### Impact Explanation
An API token that is deliberately scoped to a single stack (e.g. the `here_come_the_walrus` fixture pattern) but that also carries `write:stack` — a realistic minimal-privilege combination for automation that manages settings on its own stack — can create new stacks for arbitrary GitHub repositories/organizations it was never meant to touch [8](#0-7) . This is a cross-repository write: the token can register deployment pipelines (`repo_owner`, `repo_name`, `branch`, `deploy_url`, `continuous_deployment`) against repositories outside its authorized scope, which then become manageable/deployable stacks in the Shipit instance. This matches the in-scope Critical bucket "cross-repository writes."

### Likelihood Explanation
Any holder of a `write:stack`-permissioned, stack-scoped API token (the intended low-privilege deployment-automation case) can trigger this with a single authenticated `POST` request supplying attacker-chosen `repo_owner`/`repo_name`; no additional access, repo write permission, or session is required beyond the token itself, which is the expected credential for using this endpoint at all. The test suite even documents that `create` accepts arbitrary `repo_owner`/`repo_name` with only the generic `write:stack` permission check and never exercises the stack-scoped-client case for `create` [9](#0-8) , indicating the missing scoping is untested and unenforced.

### Recommendation
In `StacksController#create`, when `current_api_client.stack_id?` is set, reject the request (a stack-scoped token has no legitimate need to create additional stacks), or otherwise assert that the resulting `repository`/`environment` matches the client's own assigned stack before saving. This restores the same binding that `#stack`/`stacks` already enforces for `show`, `update`, `destroy`, and `index`.

### Proof of Concept
1. Provision an `ApiClient` with `stack_id` set to stack A's id and `permissions: ['write:stack']` (a plausible "manage my own stack" token).
2. Authenticate with that token and send:
   `POST /api/stacks` with `repo_owner: "victim-org"`, `repo_name: "victim-repo"`, `environment: "production"`, `branch: "main"`.
3. Observe (per `StacksController#create` [8](#0-7) ) that a new `Stack`/`Repository` record for `victim-org/victim-repo` is created and returned with `200 OK`, despite the token being scoped only to stack A — confirming the token-to-stack binding is not enforced on `create`.
