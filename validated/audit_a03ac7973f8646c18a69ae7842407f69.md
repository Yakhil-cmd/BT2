### Title
AA input-selection loop for non-base assets can accumulate unbounded dust inputs, causing the AA's payment message to exceed `MAX_INPUTS_PER_PAYMENT_MESSAGE` and freezing the AA's asset funds - ([File: aa_composer.js])

### Summary
This is the closest analog to the `CamelotRewardsAdapter.claimRewards` gas-DoS report in ocore's architecture. `ocore` has no gas metering, but it enforces hard structural limits per unit (e.g. `MAX_INPUTS_PER_PAYMENT_MESSAGE`) at consensus validation time. When an AA composes a response payment (`aa_composer.js`, `sendUnit` → `completePaymentPayload` → `readStableOutputs`/`iterateUnspentOutputs`), it selects unspent outputs of the paying asset with an unbounded SQL query (no `LIMIT`) and no dust-amount floor for non-base assets, unlike the analogous coin-selection routine in `inputs.js`. An attacker who posts many tiny-amount transfers of a custom asset to an AA address can force the AA, on its next payout of that asset, to accumulate more inputs than `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` permits, causing the generated response unit to fail consensus validation every time — effectively bricking the AA's ability to ever spend that asset (fund freezing), analogous to `claimRewards` DoS from an unbounded position count.

### Finding Description
In `aa_composer.js` inside `sendUnit`/`completePaymentPayload`, `readStableOutputs` builds the candidate input set for an AA's payment message: [1](#0-0) 
Note the WHERE clause: for the base asset there is a dust floor (`amount>=FULL_TRANSFER_INPUT_SIZE`), explicitly commented as protection against a "dust attack: spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond." For a named asset (`asset ? "="+conn.escape(asset) : ...`), **no minimum amount floor is applied**, and critically the query has **no `LIMIT`** at all, unlike the coin-selection code path used elsewhere in the codebase: [2](#0-1) 
which explicitly limits the query to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2` rows.

`iterateUnspentOutputs` then loops over every returned row and pushes one input per row into `payload.inputs` until the accumulated `total_amount` reaches the `target_amount`: [3](#0-2) 

Because there is no per-query row cap and no minimum-amount filter for non-base assets, an attacker can send the AA a large number of very-small-amount outputs of an asset the AA is known to forward or pay out (e.g. a cashback/rebate/forwarder AA). Once the AA needs to pay out an amount in that asset that requires consuming enough of these dust outputs to exceed `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`, the resulting `payload.inputs.length` will be rejected by consensus validation: [4](#0-3) 
`sendUnit` later calls `validateAndSaveUnit`, and if that fails, the entire trigger response is bounced: [5](#0-4) 

Because bounce still consumes the trigger, and the underlying asset balance and its dust outputs remain unchanged in the AA's UTXO set, every subsequent attempt to pay out that asset (deterministically re-selecting the same oldest-first outputs, since the query is `ORDER BY main_chain_index, unit, output_index`) will again select the same too-many dust inputs, causing the AA to be permanently unable to output that asset — a fund-freezing condition, entirely reachable by an unprivileged unit poster who simply sends many small-value asset outputs to a known AA address.

### Impact Explanation
This can permanently freeze an AA's stored balance of an asset: the AA becomes structurally unable to construct a valid payment message in that asset because doing so always requires more inputs than the protocol allows in a single payment message (`MAX_INPUTS_PER_PAYMENT_MESSAGE`), and there is no mechanism in the current code path to select a bounded subset of inputs (`LIMIT`) or reject dust for non-base assets the way it does for bytes. This matches the "AA fund freezing" acceptance criterion.

### Likelihood Explanation
Reachable by any unprivileged user: simply post ordinary payment messages of a custom asset with tiny amounts, spread across many outputs, to an AA address that is known to eventually pay out that asset (forwarder/cashback/DEX-style AAs commonly do this). No special privileges, timing, or race conditions are required; only many small transfers, each of which is a normal valid unit.

### Recommendation
Apply the same dust-avoidance protections used for the base asset to non-base assets in `readStableOutputs`/`readUnstableOutputsSentByAAs` (e.g., a configurable minimum-amount floor per asset, or per-transfer economic cost), and add an explicit `LIMIT constants.MAX_INPUTS_PER_PAYMENT_MESSAGE - 2` (as already done in `inputs.js`) to the SQL query in `aa_composer.js`, ensuring the AA never attempts to build a payment message that structurally cannot pass validation, and consider merging/consolidating dust UTXOs opportunistically to prevent unbounded accumulation.

### Proof of Concept
1. Deploy/observe an AA `A` that at some point sends outputs of asset `X` to arbitrary recipients (a common pattern in DEX/cashback/forwarder AAs).
2. As an unprivileged user, post `N` (> `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`) ordinary payment units, each transferring 1 unit of asset `X` to address `A`, in many small separate outputs (below any reasonable economic value but still valid, since no minimum floor is enforced for non-base assets in `aa_composer.js:1149`).
3. Trigger the AA logic that pays out asset `X` from `A` in an amount requiring it to sum more than `MAX_INPUTS_PER_PAYMENT_MESSAGE` of these dust outputs (e.g., by making prior larger outputs unavailable/spent, or by simply waiting until the AA's set of `X` UTXOs consists only of these dust outputs).
4. Observe: `readStableOutputs` returns all matching dust rows unbounded; `iterateUnspentOutputs` pushes all of them into `payload.inputs`; the resulting response unit fails `validatePaymentInputsAndOutputs`'s `payload.inputs.length > constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` check; the trigger bounces. Because the same deterministic oldest-first selection will occur again, the AA is now permanently unable to pay out asset `X`.

Note: I was not able to independently confirm within the available index the exact numeric value of `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (the constant definition itself was not retrievable via search, though its usage confirms the check exists in `validation.js`); a Devin session with full repository access could confirm the exact threshold and simulate this scenario end-to-end.
