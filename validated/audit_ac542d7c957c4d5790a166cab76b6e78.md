### Title
Signature verification keys off `repository.owner.login` while stack-targeting keys off `repository.full_name`, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). All webhook event handlers, however, determine which `Stack`/`Repository` to act on using a *different* payload field, `payload.dig('repository', 'full_name')`, via `Shipit::Webhooks::Handlers::Handler#repository_name`. In a multi-organization Shipit deployment (as documented in `config/secrets.development.example.yml`, which explicitly supports per-organization `github:` blocks with distinct `webhook_secret`s), these two fields are never checked for consistency with each other.

### Finding Description
The trust binding that should hold is:

`organization whose webhook_secret validated the HMAC` == `organization/repository that the handler acts on`

In `verify_signature`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The secret used to check the signature is selected purely from `repository.owner.login` (attacker-controlled JSON, not itself authenticated by anything beyond the HMAC that is about to be checked against it). Meanwhile, every handler resolves the target repository from a *different* field:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

Because `repository.owner.login` and `repository.full_name` are two independent, attacker-supplied strings inside the same JSON body, an attacker who possesses (or has learned/leaked) the `webhook_secret` configured for *any one* organization onboarded to the Shipit instance (e.g. their own low-privilege org "attacker-org") can craft a payload where:
- `repository.owner.login` = `"attacker-org"` (so `Shipit.github(organization: "attacker-org")`'s secret is used to validate the HMAC, which the attacker can compute correctly), and
- `repository.full_name` = `"victim-org/victim-repo"` (an unrelated organization/repo also configured in the same Shipit instance).

The HMAC only proves the request was signed with `attacker-org`'s secret; it says nothing about which repository the payload is allowed to reference. `PushHandler` (and other handlers) then act on `Repository.from_github_repo_name("victim-org/victim-repo")`'s stacks using this forged-but-"verified" payload:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [3](#0-2) 

This is directly analogous to the reported YieldMath bug class: a value that is verified/covered (the organization used to pick the signing secret) is not the same value that downstream logic actually acts upon (the repository/stack targeted), so the "verified" state silently applies to the wrong entity — an authenticated organization vs. the repository that is written.

### Impact Explanation
An attacker who controls the webhook secret of one onboarded organization can forge webhook events (e.g. `push`, `status`, `pull_request`) that appear "signature verified" but target stacks belonging to a completely different, victim organization/repository configured on the same Shipit instance. This can trigger `GithubSyncJob` against the victim's stack with attacker-chosen `expected_head_sha`, influence commit/status ingestion for the victim repository, or manipulate review-stack/PR lifecycle handlers tied to the victim repo — effectively cross-repository/cross-organization write access to Shipit's internal state for repositories the attacker does not own. This matches the "cross-repository writes" / unauthorized-action class called out as valid High/Critical impact.

### Likelihood Explanation
This requires the Shipit instance to be configured for multiple GitHub organizations (explicitly supported and documented in `config/secrets.development.example.yml`) and requires the attacker to know/possess the `webhook_secret` for at least one of the onboarded organizations — plausible if the attacker administers their own org's GitHub App/webhook config in a shared multi-tenant Shipit deployment, a scenario the engine is explicitly built to support. No GitHub App private key, `api_clients_secret`, or Shipit session is needed — only a valid webhook secret for any one configured organization, which is a normal, non-privileged credential for that organization's admins.

### Recommendation
Bind signature verification to the *same* repository identity the handlers use to select the target stack. Concretely:
- Use `payload.dig('repository', 'full_name')` (or derive the organization from it) — not a separately-read `repository.owner.login`/`organization.login` — to select which `webhook_secret`/GitHub App is used in `verify_signature`.
- After verifying the signature, additionally assert that the resolved `Repository`'s configured owner/organization matches the organization whose secret validated the signature, rejecting the webhook otherwise.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`, each with its own `webhook_secret`: `attacker-org` and `victim-org`.
2. As an entity that controls `attacker-org`'s webhook secret, craft a `push` event payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Sign the raw body with `attacker-org`'s `webhook_secret` and set `X-Hub-Signature` accordingly.
4. POST to `/github/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` from `repository.owner.login` and successfully verifies the HMAC.
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef")` on the victim's stack — a webhook signed by an unrelated organization's secret alters state for a repository the attacker does not control.

      github_app = Shipit.github(organization: repository_owner)

      Rails.logger.info([
