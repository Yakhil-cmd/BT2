### Title
Webhook signature verification is bound to `repository.owner.login` while event handlers act on the unrelated `repository.full_name` — allows unauthenticated cross-repository writes ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's webhook secret to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) taken directly from the untrusted, attacker-controlled JSON body. Every webhook `Handler` (e.g. `PushHandler`), however, resolves the target `Repository`/`Stack` to mutate using a *different* field of that same untrusted body: `repository.full_name`. Nothing ties these two fields together, and if any configured GitHub App organization has no `webhook_secret` set (an explicitly supported, documented configuration — see `docs/setup.md`: "Webhook secret (optional)"), signature verification is bypassed entirely for that organization. This breaks the trust binding: "organization that authenticated" (`repository.owner.login`) ≠ "repository that is written" (`repository.full_name`).

### Finding Description
`verify_signature` computes the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

Meanwhile, the actual object acted upon by every default handler (`PushHandler`, `PullRequest::*Handler`, etc.) is resolved from a *different* payload key, `repository.full_name`, via `Handler#stacks`/`#repository_name`, with no cross-check that its owner prefix matches `repository.owner.login` used for signature routing: [4](#0-3) [5](#0-4) [6](#0-5) 

Since `webhook_secret` is documented as optional per GitHub App/organization (`docs/setup.md` line 30 — "Webhook secret (optional)"), a Shipit deployment integrating multiple GitHub Apps/organizations (as directly supported by `test/dummy/config/secrets_double_github_app.yml`, which configures per-organization `webhook_secret`) can have one organization without a secret configured. An unauthenticated attacker can then:
1. Send a POST to `/webhooks` with `X-Github-Event: push`.
2. Set `repository.owner.login` (or `organization.login`) to the organization lacking a `webhook_secret` — causing `verify_webhook_signature` to short-circuit to `true` with no valid signature required.
3. Set `repository.full_name` to `victim-org/victim-repo` — an entirely different, secret-protected organization's repository.
4. `PushHandler#process` will look up stacks for `victim-org/victim-repo` (via `Repository.from_github_repo_name`) and trigger `stack.sync_github`, effectively injecting spoofed head SHAs/branch state for a repository the attacker has no push authority over — with no cryptographic guarantee tying the forged event to that repository's owner at all.

### Impact Explanation
This crosses the "unprivileged attacker" boundary explicitly called out in scope: an organization whose credentials (webhook secret) authenticated the request is not the repository that is written by the resulting handler. The practical effect is unauthorized, unauthenticated manipulation of a victim stack's synced commit/branch state (`GithubSyncJob`, `Membership`/`Team` mutations via `membership` events, PR/commit status writes via `StatusHandler`, `PullRequest` handlers) for any repository/organization configured in the same Shipit instance, as long as at least one other configured GitHub App organization has no webhook secret. This can escalate to unauthorized deploy triggers downstream (deploys are driven off synced commit state) and forged commit statuses/PR metadata — matching the "Critical: cross-repository writes / unauthorized deploy" bar.

### Likelihood Explanation
Requires only that a Shipit installation configures more than one GitHub App/organization (a fully supported and tested configuration — `secrets_double_github_app.yml`) and that at least one of those organizations omits `webhook_secret` (also documented as optional). No credentials, tokens, or GitHub App keys are needed by the attacker — only network access to `POST /webhooks`, which is an unauthenticated, publicly reachable endpoint by design (`skip_before_action :verify_authenticity_token`, no `Authentication` concern included). This is a realistic operational misconfiguration rather than a theoretical one, since the setup docs and test fixtures both present per-organization optional secrets as a normal pattern.

### Recommendation
- Reject webhook signature verification when `webhook_secret` is not configured, rather than treating it as automatically verified (`return true unless webhook_secret` in `lib/shipit/github_app.rb` should instead fail closed, or require `webhook_secret` to be mandatory for all configured GitHub Apps).
- Bind the field used to select the verifying organization to the same field used by the handlers to resolve the target repository, i.e., validate that `repository.full_name`'s owner segment matches `repository.owner.login`/`organization.login` before dispatching to handlers, or resolve the target `Repository` first and use its persisted `owner` to select the verifying `GitHubApp`, never trusting a second independent payload field for authorization-relevant identity.

### Proof of Concept
1. Configure two GitHub Apps in `secrets.yml`: `OrgA` (attacker-accessible or no `webhook_secret` configured) and `OrgB` (victim org, `webhook_secret` set, hosting `Shipit::Stack` for `OrgB/victim-repo`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefattackerchosen",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
No `X-Hub-Signature` header (or a garbage one) is required as long as `Shipit.github(organization: "OrgA").verify_webhook_signature` returns `true` (no secret configured for `OrgA`), per [7](#0-6) .
3. `WebhooksController#create` dispatches to `Shipit::Webhooks::Handlers::PushHandler`, which resolves `OrgB/victim-repo`'s stack via `repository.full_name` and calls `stack.sync_github(expected_head_sha: "deadbeefattackerchosen")`, per [8](#0-7)  and [6](#0-5) , mutating `OrgB`'s stack state without ever presenting a valid `OrgB` signature.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
