### Title
Tokens sent directly to a pool outside an accounting call are permanently stranded - (File: `contracts/pool/src/cache/cash.rs`)

### Summary
The pool tracks reserves using its internal `cash` field rather than its actual token balance, so a direct token transfer to the pool creates an unbooked surplus that no unprivileged recovery path can return. [1](#0-0) 

### Finding Description
`Cache::credit_cash` is the only mechanism that records inbound liquidity, while `Cache::transfer_out` moves tokens without reducing `cash`. [2](#0-1)  Normal inbound pool operations are routed through the controller, which transfers tokens before invoking the owner-restricted pool entrypoint; an unsolicited direct token transfer therefore increases `token.balance(pool)` without increasing any market's `cash`. [3](#0-2) 

The architecture explicitly documents that direct donations do not automatically increase booked cash. [4](#0-3)  The pool ABI exposes accounting operations and views, but no generalized `recover`, `rescue`, or `sweep` function for the `balance - cash` surplus. [5](#0-4) 

### Impact Explanation
A payer who accidentally transfers excess market tokens directly to the pool cannot recover them through `repay`, `recapitalize`, `withdraw`, or a dedicated rescue path because those tokens were never booked as `cash` or credited to an account. [6](#0-5)  The donation can remain locked as unallocated physical custody even though all protocol-level account balances and market reserves remain unchanged. [7](#0-6) 

### Likelihood Explanation
Any unprivileged address can reach this state by invoking the token contract's `transfer(sender, pool, amount)` rather than routing the payment through `Controller::supply`, `Controller::repay`, or `Controller::recapitalize`. [8](#0-7)  This is an accidental-excess-payment scenario rather than an attack against another user's existing position. [1](#0-0) 

### Recommendation
Add a narrowly scoped recovery path for a payer to reclaim the pool token balance above all markets' tracked `cash` for that asset, preferably callable through the controller and attributable to the original payer only if donation provenance is tracked. [2](#0-1)  Alternatively, expose an owner-governed surplus sweep that computes `token.balance(pool) - sum(cash across every market using that token)` and cannot draw from tracked reserves. [9](#0-8) 

### Proof of Concept
1. Create or select a pool market for token `T`. [10](#0-9) 
2. Record `cash = Pool.get_reserves(hub_asset)` and `balance = T.balance(pool)`. [11](#0-10) 
3. Call `T.transfer(user, pool, excess)` directly without invoking `Controller::supply`, `repay`, or `recapitalize`. [12](#0-11) 
4. Observe that `balance` increases by `excess` while `get_reserves(hub_asset)` and all user supply/debt positions remain unchanged. [4](#0-3) 
5. The pool surface has no unprivileged operation that returns this unbooked `balance - cash` surplus to the sender. [13](#0-12)

    /// Increases accounting cash by `amount`. Rejects negative amounts and overflow.
    pub(crate) fn credit_cash(&mut self, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        self.cash = self
            .cash
            .checked_add(amount)
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));
    }

    /// Decreases accounting cash by `amount`. Rejects negative amounts or
    /// insufficient reserves.
    pub(crate) fn debit_cash(&mut self, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        self.require_reserves(amount);
        self.cash = self
            .cash
            .checked_sub(amount)
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));
    }

    /// Transfers `amount` of the market asset from the pool to `recipient`.
    ///
    /// Rejects negative amounts; zero is a no-op. Does not adjust accounting cash.
    pub(crate) fn transfer_out(&self, recipient: &Address, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        if amount == 0 {
            return;
        }
        let tok = token::Client::new(&self.env, &self.params.asset_id);
        tok.transfer(&self.env.current_contract_address(), recipient, &amount);

## Custody and accounting

The pool tracks cash in an accounting book. Supply, repayment, and
recapitalization credit the tokens actually received; direct donations do not
automatically increase booked cash. When a token delivers less than requested,
the pool books the smaller measured amount. Measurement cannot establish that an
arbitrary token is safe.

/// Asserts that the driven and sibling market cash sums to at most the pool token balance.
///
/// Markets on one asset share the token balance, so a per-market `cash <= balance`
/// check cannot detect an overdraw.
fn assert_cash_matches_balance(
    env: &Env,
    pool: &LiquidityPoolClient<'_>,
    pool_addr: &Address,
    asset: &Address,
    state: &PoolStateRaw,
) {
    let sibling = pool_state(pool, &hub_asset_in(asset, SIBLING_HUB_ID)).cash;
    let tracked = state.cash + sibling;
    let balance = pool_balance(env, asset, pool_addr);
    assert!(
        tracked <= balance,
        "tracked cash across markets on this asset exceeds token balance: \
         driven={} sibling={} balance={}",
        state.cash,
        sibling,
        balance,
    );
