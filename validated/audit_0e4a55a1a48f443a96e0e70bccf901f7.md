### Title
Off-by-One in `--max-failures` Check Causes Premature Sync Abort (Persistent Sync Denial) - (File: main.go)

### Summary
The consecutive-failure counter in the main sync loop uses `failCount >= maxFails` to decide when to abort, but `failCount` is incremented *before* the comparison and starts counting from 1 on the first failure. This causes git-sync to abort one failure earlier than the documented and intended threshold, mirroring the reported off-by-one pattern where a "count so far" is compared against a limit without accounting for the increment that already occurred.

### Finding Description
In the main sync loop, `failCount` is incremented on every failed `git.SyncRepo` call, and the abort decision is made immediately afterward: [1](#0-0) 

```go
failCount := 0
...
getMaxFailures := func() int {
    if !initialSyncDone && initMaxFailuresSet {
        return *flInitMaxFailures
    }
    return *flMaxFailures
}
for {
    ...
    if changed, hash, err := git.SyncRepo(ctx, syncHooks); err != nil {
        failCount++
        updateSyncMetrics(metricKeyError, start)
        if maxFails := getMaxFailures(); maxFails >= 0 && failCount >= maxFails {
            log.Error(err, "too many failures, aborting", "failCount", failCount, "maxFailures", maxFails)
            os.Exit(1)
        }
        log.Error(err, "error syncing repo, will retry", "failCount", failCount)
    } else {
    ...
```

The documented semantics of `--max-failures` (and `--init-max-failures`) are: "The number of consecutive failures **allowed** before aborting" [2](#0-1) . This means N failures should be tolerated, with the (N+1)-th failure triggering the abort — the `0` special case documents this exactly ("If not specified, this defaults to 0, meaning any sync failure will terminate git-sync", i.e. 0 tolerated failures → abort on the 1st).

However, because `failCount` is pre-incremented (1-based) and the check is `failCount >= maxFails` (not `>`), the loop actually aborts on the N-th failure instead of the (N+1)-th:
- `maxFails = 0`: first failure → `failCount=1 >= 0` → abort (matches doc, coincidentally, since 0 is the boundary case).
- `maxFails = 3`: 1st failure `1>=3` false, 2nd `2>=3` false, 3rd `3>=3` true → abort. Only 2 failures are actually tolerated instead of the documented 3.

This is structurally identical to the reported class of bug: a running count is compared with `>` / `>=` against a limit without correcting for the pending increment/inclusive boundary, causing the effective limit to be off by one.

### Impact Explanation
This causes **persistent/premature sync denial**: git-sync will terminate (`os.Exit(1)`) one consecutive-failure earlier than the operator configured via `--max-failures` / `--init-max-failures`. In environments where git-sync is deployed as a long-running Kubernetes sidecar with transient upstream connectivity issues (the exact use case `--init-max-failures` is designed to tolerate, per the flag's own documentation: "This phase is useful for tolerating transient connectivity issues at startup while still giving up eventually" [3](#0-2) ), the pod/container will abort and restart-loop sooner than intended, reducing the effective fault tolerance the operator explicitly configured. This is a functional/availability defect rather than a data-integrity or credential-disclosure issue, so I classify it as low/medium severity — it degrades resilience rather than causing wrong content publication or credential leakage.

### Likelihood Explanation
This triggers deterministically any time `--max-failures` (or `--init-max-failures`) is set to a positive value and consecutive sync failures occur (e.g., transient network issues, remote unavailability, or an attacker able to cause `git.SyncRepo` failures such as a hostile/unreachable ref or auth hiccup). No special flags beyond setting `--max-failures N > 0` are required; the bug affects the default configuration path whenever this flag is used with N > 0.

### Recommendation
Change the abort condition to be strictly greater than the configured limit, consistent with "N failures allowed":
```go
if maxFails := getMaxFailures(); maxFails >= 0 && failCount > maxFails {
```
Alternatively, increment and compare pre-increment count against `maxFails` with `>=` maintaining 0-based semantics consistently (e.g., check before incrementing: `if failCount >= maxFails` then increment). Either fix should preserve the existing test showing `--max-failures=0` aborts on the very first failure.

### Proof of Concept
1. Run `git-sync --repo=file:///does/not/exist --root=$ROOT --link=link --period=100ms --max-failures=3`.
2. Observe via logs (`failCount`/`maxFailures` fields logged at [4](#0-3) ) that the process calls `os.Exit(1)` after only the **3rd** consecutive failure, not after a 4th failure as the "3 failures allowed before aborting" documentation implies.
3. Compare against the existing e2e test `e2e::init_max_failures_exceeded` [5](#0-4) , which only asserts that the process eventually fails (`assert_fail`) but does not verify the exact failure count, meaning this off-by-one is currently unguarded by tests.
