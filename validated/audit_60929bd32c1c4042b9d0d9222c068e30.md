### Title
Cross-repository forged commit status injection via unscoped SHA lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook purely by `Commit.where(sha: params.sha)`, with no filter on the repository/stack that authenticated the webhook. Any commit row in the database whose SHA matches the attacker-supplied SHA — regardless of which stack or repository it belongs to — receives a `Status` row built verbatim from attacker-controlled `target_url`/`description` fields.

### Finding Description
The claimed binding is: `Status#stack_id == the stack whose repository authenticated the webhook payload`. Tracing the code shows this binding is broken.

`StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) processes the webhook as:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This query is **not scoped by repository or stack** — it matches every `Commit` row across every stack in the installation with the same `sha`. `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) then calls:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
```
`stack_id` here is taken from the matched `Commit` record, not from any authenticated repository/stack context of the inbound webhook. `Status.replicate_from_github!` (`app/models/shipit/status.rb:24-33`) persists `github_status.target_url`, `description`, `state`, and `context` verbatim under that `stack_id`.

The webhook itself is authenticated only at the transport level (`webhooks_controller.rb` verifies the HMAC signature against the configured `webhook_secret`, i.e., it proves the payload came from *a* GitHub App/webhook config known to Shipit), but this signature check says nothing about which repository the SHA belongs to. Because GitHub commit SHAs are content-addressed and not globally unique-to-one-repo (identical trees/commits can exist in unrelated repositories, forks, or even be trivially crafted to collide with a known victim SHA structure via cherry-pick/rebase without changing the hash — or more simply, an attacker who forks/mirrors the victim repo and pushes the exact same commit will have a `Commit` row with the same `sha` created under their own stack, but the handler's `Commit.where(sha:)` still hits **all** stacks, including the victim's, if the victim commit exists in the DB with that sha), an attacker who operates *any* Shipit-monitored repository (including one they fully control) can send/trigger a `status` webhook citing a SHA equal to a victim commit and inject arbitrary `target_url`/`description` content into the victim stack's `Status` record.

None of the listed guards address this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that the sender knows the shared webhook secret for some configured hook — every repository added to the Shipit instance typically shares/derives from the same app configuration, so this does not bind the payload to a specific repository. `ExplicitParameters` (the `params do ... end` block) only validates field types/presence, not repository ownership. There is no `force_github_authentication`, `require_permission!`, or stack-scoping check inside `StatusHandler#process` or `Commit#create_status_from_github!`.

### Impact Explanation
An attacker who controls (or can trigger webhooks for) any repository monitored by the same Shipit instance can write attacker-chosen `target_url` and `description` strings into a `Status` row scoped to another tenant's stack, as long as they can produce/reference a commit SHA present in the victim's commit history (e.g., by mirroring/forking the victim repo, or targeting SHAs from public commits shared across forks). This is displayed on the victim stack's UI (task/commit status listing) to any unauthenticated viewer of that stack, since Shipit's stack/commit UI is typically world-readable within the org. This matches the "payload for one repository mutating another's stack, commit, task" Critical category, and the stored/reflected content on the victim UI also has High-adjacent stored-content implications. The blast radius spans every stack whose commit table happens to contain the targeted SHA — this is not limited to a single victim if the attacker can enumerate/guess shared SHAs (e.g., forked repos sharing history).

### Likelihood Explanation
Preconditions are low: the attacker needs only to control a repository already registered as a Shipit stack (or reuse an existing low-privilege stack) and be able to send a validly-signed `status` webhook event (which GitHub sends automatically for CI on any repo/fork the attacker owns) whose `sha` matches a commit SHA that also exists in the victim's `commits` table (trivial for a fork of the victim repo, since forking preserves commit SHAs exactly). No Shipit secrets, session, or elevated GitHub permissions are required beyond owning/forking a repository and letting GitHub sign the webhook with the app's normal webhook secret (which is per-installation, not per-repository, in typical GitHub App setups). This is fully repeatable — every push/status event on the attacker's fork can carry an arbitrary `description`/`target_url`.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the stack(s)/repository that the webhook is actually associated with (e.g., filter `Commit.where(sha: params.sha, stack_id: stack.id)` where `stack` is resolved from the webhook's `repository.full_name`/installation context), mirroring how other handlers (e.g., `PushHandler`) resolve the target stack from the payload's repository before touching any records.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_test.rb (conceptual)
test "status webhook cannot write into a stack it did not authenticate for" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')

  attacker_stack = Shipit::Stack.create!(repository: shipit_repositories(:other), environment: 'staging')
  # attacker's own repo happens to contain a commit with the same sha (e.g. via fork)
  attacker_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')

  params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: 'a' * 40,
    state: 'failure',
    description: '<script>attacker payload</script>',
    target_url: 'https://attacker.example/phish'
  )

  Shipit::Webhooks::Handlers::StatusHandler.new(params).process

  victim_status = victim_commit.statuses.last
  assert_equal victim_stack.id, victim_status.stack_id
  assert_equal 'https://attacker.example/phish', victim_status.target_url
  assert_equal '<script>attacker payload</script>', victim_status.description
end
```
This asserts that `Status#stack_id` (victim) received attacker-controlled `target_url`/`description` despite the webhook never being authenticated by/for the victim's repository, confirming the binding failure.
