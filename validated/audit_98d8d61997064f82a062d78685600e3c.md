### Title
Webhook signature verification org does not bind to the repository being mutated, enabling cross-tenant review-stack unarchival - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a payload's HMAC using `repository_owner`, which is read from the attacker-controlled `repository.owner.login` (or `organization.login`) field of the same JSON body. `ReopenedHandler#process` (and the other `PullRequest` handlers) instead resolve the target `Repository` from a *different*, independently attacker-controlled field, `repository.full_name`. Nothing enforces that these two fields refer to the same tenant, so a payload correctly signed with one organization's webhook secret can name a completely different organization's repository/stack to mutate.

### Finding Description
The broken binding, stated as an equality that must hold but does not:
`organization_that_signed_payload (params.dig('repository','owner','login'))` == `organization_owning_mutated_stack (Repository.from_github_repo_name(params.repository.full_name).owner)`

Trace:
- `WebhooksController#verify_signature` at [2](#0-1)  computes `github_app = Shipit.github(organization: repository_owner)` and verifies the raw body HMAC against that org's `webhook_secret`.
- `repository_owner` is derived purely from the payload: [3](#0-2) .
- Once verified, `WebhooksController#create` dispatches the *entire raw JSON* (unmodified) to handlers: [4](#0-3) .
- `ReopenedHandler` schema requires only `repository.full_name` (no `owner`/`login` correlation is validated) and resolves the repository from it: [5](#0-4) .
- `Repository.from_github_repo_name` does a flat `owner/name` lookup with no tie back to which org's secret verified the request: [1](#0-0) .
- If `unarchive?` evaluates true (attacker controls `provisioning_behavior_*`-relative labels within their forged `pull_request.labels`), `ReopenedHandler#process` calls `stack.unarchive!` -> `ReviewStackAdapter#unarchive!`, which unconditionally unarchives an archived stack and enqueues `ReviewStackProvisioningQueue.add(stack)` (which in turn drives `GithubSyncJob`/provisioning): [6](#0-5)  and [7](#0-6) .

Root cause: Shipit's multi-organization mode (documented at `docs/setup.md`, "Using Multiple Github Applications") configures a separate `webhook_secret` per organization key via `Shipit.github_app_config`/`Shipit.github` [8](#0-7) . The controller uses one payload field (`repository.owner.login`) to pick the secret, while every handler uses a *different* payload field (`repository.full_name`) to pick the target record. GitHub itself would always keep these consistent for genuine deliveries, but the attacker is not relying on GitHub's delivery pipeline — they only need to know their own org's `webhook_secret` (which they, as the admin who created/installed the App on their own org, legitimately possess per `docs/setup.md`) and can POST an arbitrary raw body directly to `/webhooks` with a correctly computed `X-Hub-Signature`.

Existing guards do not catch this: `verify_signature` only checks the HMAC is valid for *some* org config, not that the org matches the acted-upon repository; `drop_unhandled_event`/`check_if_ping` are unrelated; the `ExplicitParameters` schema in `ReopenedHandler` validates types/presence, not cross-field ownership; `Repository` validations only constrain `owner`/`name` character sets, not that the owner matches the authenticating org.

### Impact Explanation
An attacker who administers a GitHub App/org onboarded into a multi-org Shipit deployment can force a `GithubSyncJob` to run and a review stack's provisioning to be re-enqueued for a target stack belonging to an entirely different, unrelated organization/repository — a payload for one tenant mutating another tenant's stack. This is repeatable against any archived review-stack PR number the attacker can guess/enumerate under any victim repository configured on the same Shipit instance, and matches the Critical category ("a payload for one repository mutating another's stack").

### Likelihood Explanation
Requires: (1) the Shipit instance is configured in multi-organization mode with the attacker controlling one of the onboarded orgs (and thus knowing that org's `webhook_secret`); (2) the victim repo has `review_stacks_enabled` and a matching `provisioning_behavior_*`/label configuration; (3) an archived review stack exists for a PR number the attacker names. Attacker cost is a single crafted HTTP POST with a valid HMAC for their own secret — no victim secret, session, or credential is needed. This is fully repeatable and scriptable.

### Recommendation
Bind repository resolution to the same organization that authenticated the webhook: after `verify_signature`, ensure `repository_owner` from the payload's `repository.owner.login`/`organization.login` matches the resolved `Repository#owner` before any handler runs (e.g., reject if `Repository.from_github_repo_name(payload.repository.full_name)&.owner != repository_owner.downcase`), or better, pass the verified `repository_owner` into handlers and require they scope lookups by it rather than trusting `full_name` alone.

### Proof of Concept
Minitest plan (controller-level, no live GitHub):
1. Configure `Shipit.secrets.github` with two orgs, `attacker-org` (webhook_secret `"attacker-secret"`) and `victim-org` (webhook_secret `"victim-secret"`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Create `victim_repo = shipit_repositories(:...)` with `owner: "victim-org"`, `review_stacks_enabled: true`, `provisioning_behavior: allow_with_label`, `provisioning_label_name: "deploy-me"`.
3. Create and archive a review stack for PR `#42` under `victim_repo` (`stack.archive!`), assert `stack.archived_at.present?`.
4. Build a `pull_request`/`reopened` JSON body with `repository.full_name = "victim-org/victim-repo"`, `repository.owner.login = "attacker-org"`, `number: 42`, `pull_request.labels = [{"name" => "deploy-me"}]`.
5. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest("sha1", "attacker-secret", raw_body)`.
6. `assert_enqueued_with(job: GithubSyncJob, args: [stack_id: stack.id, ...])` while POSTing to `/webhooks` with `X-Github-Event: pull_request` and the above signature/body.
7. Assert both sides of the binding explicitly: `signing_org = "attacker-org"` (verified) vs `mutated_stack.repository.owner = "victim-org"`; assert they differ, and assert `stack.reload.archived_at.nil?` (successfully unarchived) despite the mismatch.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
