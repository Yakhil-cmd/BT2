### Title
`StatusHandler` writes commit statuses by bare `sha` across every stack/repo, letting a status from an attacker-controlled repository flip CI state (and trigger bot-driven auto-deploy) on an unrelated victim stack sharing the same SHA - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, with no filter on the repository that authenticated the webhook. Because commit `sha` is not unique to a single Shipit stack/repository (the same commit object can legitimately exist in multiple stacks — forks, mirrors, monorepos split across multiple Shipit stacks, vendored/cherry-picked commits), a GitHub `status` webhook that is validly signed for the attacker's own repository can update the `Status`/`Commit` state of a commit belonging to a completely different, unrelated stack, including one where `bot_login` is configured and auto-triggered deploy/merge behavior (`schedule_continuous_delivery`, `schedule_merges`) depends on that CI state.

### Finding Description
The broken binding: the code should enforce
`commit.stack.github_repo_name == payload.repository.full_name` (or at minimum `commit.stack_id == stack_that_authenticated_the_webhook`)
before writing a status, but it never checks this. Instead, in [1](#0-0) , every `Commit` row across the *entire database* matching the bare SHA string is updated via `commit.create_status_from_github!(params)`.

`Commit#create_status_from_github!` ( [2](#0-1) ) writes a new `Status` record for the commit and, through `add_status` ( [3](#0-2) ), re-evaluates `previous_status`/`new_status` and calls `stack.schedule_merges` and (via `after_commit`/`deployable?`) `schedule_continuous_delivery` ( [4](#0-3) ) whenever the state becomes pending/success. These continuous-delivery and auto-merge code paths run using the stack's configured bot identity (`bot_login`) rather than any identity tied to the webhook sender — so the attacker's forged/legitimate-but-foreign status can cause a real ship or unblock on the victim stack without the attacker ever touching the victim's repository.

Existing guards do not prevent this:
- `verify_signature` ( [5](#0-4)  and `GitHubApp#verify_webhook_signature`, [6](#0-5) ) only verifies that the *organization named in the payload* signed the payload with that organization's configured webhook secret. It says nothing about which specific repository or stack the status is allowed to affect — a genuine webhook for the attacker's own repository (in an org where the Shipit GitHub App/webhook is installed) passes this check trivially.
- The `ExplicitParameters` schema for `StatusHandler` only validates the shape of `sha`/`state`/`context` etc. ( [7](#0-6) ); it does not scope by repository.
- `drop_unhandled_event` and `check_if_ping` are unrelated to repo scoping.

The attacker's exact request: a normal, real GitHub `status` webhook (event type `status`) originating from a repository the attacker owns/controls, for a commit whose SHA also exists as a `Commit` row in a victim `Stack` (e.g., because the victim stack tracks a mirror/fork of the same upstream history, or a commit was cherry-picked/rebased identically into both repos), with `context: ci/e2e`, `state: success` (or `failure`/`error` to block). Because the query is `Commit.where(sha: ...)` with no repository predicate, this single genuine webhook updates the status of the matching commit row in the victim stack.

### Impact Explanation
A payload authenticated for one repository mutates commit/CI state belonging to another stack it never authenticated — this is the "payload for one repository mutating another's stack/commit" category. If the victim stack has `continuous_deployment?` enabled and/or auto-merge (`schedule_merges`) configured, flipping the `ci/e2e` status to `success` can cause `schedule_continuous_delivery` to enqueue `ContinuousDeliveryJob`, which deploys using the stack's configured bot identity, resulting in an unauthorized deploy of whatever commit was pending on the victim stack. Conversely, flipping the status to `failure`/`error` can block deploys/merges on the victim stack (denial of legitimate delivery). This is repeatable for any SHA collision the attacker can arrange and is not limited to a single victim — any stack whose commit history intersects the attacker-controlled repository's commit SHAs is affected.

### Likelihood Explanation
Preconditions: (1) the attacker needs a repository where they can emit a genuinely GitHub-signed `status` webhook to the Shipit host — i.e., a repo under an organization/installation already configured in Shipit's `github_apps`/webhook setup; (2) the attacker needs a commit SHA that is *also* present as a `Commit` row in a victim stack. This second condition is the main constraining factor: it requires identical commit objects (same tree, message, author/committer timestamps) to exist in two different repositories tracked as separate Shipit stacks — realistic in fork/mirror/vendoring/monorepo-split scenarios, but not universal. Given that precondition, the exploit costs the attacker nothing beyond a normal `git commit`/CI status update on their own repository, and is fully repeatable against any stack sharing SHAs with attacker-reachable repositories.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogously in `CheckRunHandler`/`push`-style handlers if they share this pattern) by the repository that authenticated the webhook, e.g. join through `stack.repository` matching `params.dig('repository','full_name')` or `repository_owner`/`repository_name` extracted from the payload, instead of a bare `Commit.where(sha:)` across all stacks. Concretely: resolve the `Repository`/`Stack` from the payload's `repository.full_name`, and only update commits belonging to that repository's stacks.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` style, no live GitHub):
1. Create `stack_victim` with `bot_login`/GitHub app configured requiring `ci/e2e`, `continuous_deployment: true`, belonging to repository `victim/repo`.
2. Create `stack_attacker` belonging to repository `attacker/repo`.
3. Create a `Commit` with `sha: "deadbeef..."` under `stack_victim` (pending status).
4. Create a `Commit` with the **same** `sha: "deadbeef..."` under `stack_attacker`.
5. Build a `StatusHandler::Params` payload as if received for `attacker/repo` (`sha: "deadbeef...", context: "ci/e2e", state: "success"`), and call `StatusHandler.new.call(payload)` (bypassing signature verification layer, since that only validates origin, not scope).
6. Assert: `stack_victim.commits.find_by(sha: "deadbeef...").status.success?` becomes `true`, and/or that `stack_victim.deployable?`/`schedule_continuous_delivery` was invoked (e.g. via `assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_victim])`), even though the webhook only ever authenticated for `attacker/repo`.
7. The binding under test: BEFORE — `stack_victim.commits.find_by(sha:).status.state == "pending"` AND `payload.repository == "attacker/repo"` (different repo than victim). AFTER — `stack_victim.commits.find_by(sha:).status.state == "success"`, proving the equality `commit.stack.repository == payload.repository` was never enforced.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
