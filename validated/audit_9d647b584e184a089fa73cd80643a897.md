Confirmed: this Shipit deployment supports a **multi-tenant** GitHub App configuration, where each key under `secrets.github` is a distinct organization with its own `webhook_secret`, selected dynamically via `Shipit.github(organization: repository_owner)` [1](#0-0) . This confirms the binding-break analog.

### Title
Webhook signature is verified against the secret of the organization named in `repository.owner.login`/`organization.login`, while the actual repository/stack acted upon is resolved from the independent `repository.full_name` field, allowing a legitimate tenant organization to forge writes against another organization's stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and thus which `webhook_secret`) to use for HMAC verification based on `repository_owner`, computed from the attacker-controlled JSON body itself (`repository.owner.login`, falling back to `organization.login`) [2](#0-1) . Once the signature check passes, `#create` re-parses the same raw body and dispatches it to handlers, which resolve the target repository/stack from an entirely different field: `repository.full_name` [3](#0-2) . Nothing ties `repository.owner.login` to `repository.full_name`'s owner segment before the payload is acted on.

### Finding Description
Shipit supports hosting multiple GitHub organizations behind one instance, each with its own App config, including its own `webhook_secret`, looked up via `Shipit.github_app_config(organization)` [4](#0-3) . This is a legitimate multi-tenant boundary: organization A's secret should only ever authorize actions on organization A's repositories.

The webhook signature check breaks this boundary:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`repository_owner` is derived from the same raw JSON body being verified - it is attacker-supplied content, not a value asserted by GitHub's routing/signing infrastructure. It only determines which stored secret is used to *check* the HMAC, but does not constrain which repository ends up being processed.

Downstream, every webhook handler independently derives the target repository from a *different* field, `repository.full_name`:

```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

e.g. in `PushHandler#process`, `PullRequest::ClosedHandler#process` (archives a review stack), `PullRequest::LabeledHandler#process` (archives/unarchives a stack), and `ReviewStackAdapter#unarchive!`/`#create!` (creates/provisions stacks, invokes `deprovision`) [6](#0-5) [7](#0-6) [8](#0-7) .

An administrator/owner of a legitimate but low-trust tenant organization ("Org A") already possesses that organization's own `webhook_secret` (it's their own credential in their own GitHub App/webhook config, not a stolen secret). They can craft an arbitrary JSON payload where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` selects Org A's secret, which they can correctly sign with),
- `repository.full_name` = `"OrgB/some-repo"` (a repository actually tracked by Shipit, belonging to an unrelated, more-privileged organization "Org B").

Because the two fields are never cross-checked, the request passes signature verification under Org A's key, then is routed to handlers that treat it as an event for `OrgB/some-repo`, letting Org A trigger writes against Org B's stacks (e.g., forcing `sync_github`/`GithubSyncJob` on an arbitrary "after" SHA of Org A's choosing, or archiving/unarchiving/creating review stacks for repositories they don't own).

### Impact Explanation
This is a cross-repository/cross-organization write performed by a tenant that authenticated only for its own organization, exactly the "organization that authenticated versus the repository that is written" binding this task targets. Concretely reachable, unprivileged-relative-to-Org-B actions include:
- Forcing `GithubSyncJob`/`sync_github` on Org B's stack with an attacker-chosen `expected_head_sha` via `PushHandler` [6](#0-5) .
- Archiving/unarchiving/creating review stacks belonging to Org B via the `PullRequest` handlers and `ReviewStackAdapter`, including invoking `deprovision`/provisioning-queue logic on Org B's infrastructure [8](#0-7) .

This is a cross-repository write crossing an organizational trust boundary that the multi-tenant GitHub App configuration is meant to enforce.

### Likelihood Explanation
Any organization onboarded as a tenant on a shared Shipit instance (i.e., any entry under `secrets.github` with a legitimate, non-privileged, low-trust relationship to the operator) can perform this attack using only their own already-configured webhook secret - no interception, no privileged Shipit account, and no access to Org B's credentials are required. The only prerequisite is that the instance hosts more than one organization, which is an explicitly supported and documented deployment mode (`github_organizations`, `github_app_config`) [9](#0-8) .

### Recommendation
Verify that the field(s) actually used to resolve the acted-upon repository (`repository.full_name`, `organization.login` where relevant) belong to the same organization whose secret was used for signature verification, rejecting the request otherwise. Alternatively, derive `repository_owner` for secret selection from `repository.full_name`'s owner segment (splitting exactly as `Repository.from_github_repo_name` does) so the same value governs both key selection and downstream repository resolution.

### Proof of Concept
1. Attacker controls organization `OrgA`, configured in Shipit's `secrets.github` with its own `webhook_secret` (`SECRET_A`), which they legitimately know.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/production-app"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(SECRET_A, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and verifies successfully since the body was signed with `SECRET_A` [10](#0-9) .
5. `create` dispatches to `PushHandler`, which resolves stacks via `Repository.from_github_repo_name("OrgB/production-app")` (through `Handler#stacks`/`#repository_name`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on Org B's stack [3](#0-2) [6](#0-5) , despite the request never being signed by Org B's secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
