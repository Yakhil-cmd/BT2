### Title
Webhook signature verification keys off `repository.owner.login`, but handlers act on the independently-read `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which organization's* `webhook_secret` to validate the HMAC signature against using `repository_owner`, a value read straight out of the untrusted JSON body (`params.dig('repository', 'owner', 'login')` or `organization.login`) - before the signature has been checked. Every `Handler` subclass, however, decides *which `Repository`/`Stack` to mutate* using a different field of the same body, `payload.dig('repository', 'full_name')` [1](#0-0) . In a multi-organization Shipit deployment (supported directly by config, see `config/secrets.development.shopify.yml`), these two fields are never cross-checked against each other, and the HMAC only proves "whoever produced these exact bytes knew *an* organization's secret" - not that `owner.login` and `full_name`'s owner match.

### Finding Description
`verify_signature` resolves the signing key before validating anything: [2](#0-1) 
`repository_owner` is taken verbatim from the JSON body: [3](#0-2) 

`GitHubApp#verify_webhook_signature` only proves the raw POST body was HMAC-signed with *that organization's* `webhook_secret` [4](#0-3) . It says nothing about whether the `repository` object embedded in that same body actually belongs to that organization - it's a self-consistency check the attacker fully controls, because the attacker is the one constructing the raw body and its signature (this isn't a relayed GitHub webhook, it's a POST directly to the Shipit endpoint).

Downstream, every handler (e.g. `PushHandler`) resolves the target `Repository`/`Stack` using a *different* field, `repository.full_name` [5](#0-4) [6](#0-5) , via `Repository.from_github_repo_name` [7](#0-6) .

So the binding that should hold is: `organization whose secret authenticated the request == owner of the repository being written to`. Nothing enforces that equality. An attacker who legitimately controls a GitHub organization configured in Shipit (i.e., they installed/administer the Shipit GitHub App on their own org and thus know that org's `webhook_secret`) can:
1. Craft an arbitrary JSON body where `repository.owner.login` / `organization.login` = their own org (so `verify_signature` fetches their known secret), but `repository.full_name` = `"victim-org/victim-repo"`.
2. Compute a correct `X-Hub-Signature` over that exact body using their own secret.
3. POST it to `/webhooks`. `verify_signature` succeeds (correct secret for the org named in the payload), and the event handler then acts on `victim-org/victim-repo`'s `Stack`s.

For `push`, this triggers `stack.sync_github(expected_head_sha: params.after)` on the victim's stack [6](#0-5) , letting the attacker force-refresh/point the victim stack's tracked head at a commit SHA of their choosing (subject to what `sync_github` validates), without ever having credentials for the victim's GitHub organization.

### Impact Explanation
This crosses the exact "organization that authenticated vs. repository that is written" trust boundary called out for this analog class. Depending on the handler exercised (`push`, `status`, `check_suite`, `pull_request`, `merge`, etc.), the attacker can influence deploy-state-affecting jobs (`GithubSyncJob`, `RefreshCheckRunsJob`, `RefreshStatusesJob`) for a repository/stack they do not own or have write access to, using only their own, legitimately-obtained org webhook secret. This is a cross-repository write via unauthorized webhook impersonation.

### Likelihood Explanation
Requires the attacker to control at least one GitHub organization/webhook_secret configured in the target Shipit instance (i.e., a legitimate but unprivileged-relative-to-other-orgs tenant in a multi-org deployment) — this is the only "credential" needed, not a Shipit session, ApiClient token, or GitHub App private key for the victim org. Multi-org configuration is a first-class supported feature (`config/secrets.development.shopify.yml`, `TOP_LEVEL_GH_KEYS`), so this is a realistic deployment shape, not a hypothetical one.

### Recommendation
After `verify_signature` succeeds, re-derive `repository_owner` (or require it) and assert it matches the owner embedded in `repository.full_name` before any handler resolves/mutates a `Stack`/`Repository`, or bind the resolved `github_app`/organization explicitly into `Handler#stacks` so a handler can only ever act on repositories whose owner equals the organization that authenticated the request.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` (secret known to attacker, e.g. because they administer that org's GitHub App installation) and `victim-org` (has a `Stack` tracked in Shipit).
2. Build payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org's webhook_secret, raw_body)>`.
4. `POST /webhooks` with header `X-Github-Event: push` and the above body/signature.
5. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and validates successfully against the attacker's own secret [2](#0-1) .
6. `PushHandler` resolves stacks via `repository.full_name = "victim-org/victim-repo"` and calls `sync_github` on them [6](#0-5) , affecting a repository the attacker never authenticated for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
