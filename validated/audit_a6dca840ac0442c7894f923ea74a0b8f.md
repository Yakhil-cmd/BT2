### Title
Unauthenticated webhook processing when `webhook_secret` is unset enables forgery of `membership` events and escalation into `Shipit.github_teams` authorization - ([File: lib/shipit/github_app.rb])

### Summary
When a Shipit deployment configures its GitHub App without a `webhook_secret` (explicitly documented as "optional" in `docs/setup.md`), `Shipit::WebhooksController` performs no authentication at all before dispatching webhook payloads to their handlers. This lets an unauthenticated attacker POST an arbitrary JSON body to `/webhooks` and have it processed as a genuine GitHub event. Combined with `MembershipHandler`, which blindly trusts the `team.id` and `member.login` fields of a `membership` event to add a user to a `Team` record, an attacker can grant themselves membership in a `Team` that is part of `Shipit.github_teams`, bypassing the org/team-based access control entirely.

### Finding Description
`WebhooksController#verify_signature` selects a GitHub App config based on a payload-controlled field and then verifies the signature against it: [1](#0-0) 

The actual verification, however, is a no-op when no secret is configured for that organization: [2](#0-1) 

`docs/setup.md` explicitly documents the webhook secret as optional during GitHub App setup, and `config/secrets.development.example.yml` / `template.rb` ship with `webhook_secret:` blank by default, so this is a supported, reachable configuration state rather than a misuse of the engine. [3](#0-2) [4](#0-3) 

Once the signature check is bypassed, `create` dispatches the parsed body to every registered handler for the event type with zero further validation of provenance: [5](#0-4) 

`MembershipHandler#process` uses attacker-controlled `team.id`, `organization.login`, and `member.login` fields to find-or-create a `Team` and unconditionally append the named user as a member — there is no call back to GitHub to confirm the membership is real: [6](#0-5) [7](#0-6) 

Application-wide authorization is gated purely on this local membership data: [8](#0-7) [9](#0-8) 

`Shipit.github_teams` resolves the configured `oauth.teams` handles (e.g. `"MyOrg/developers"`) to real `Team` records with `github_id`s fetched live from the GitHub API at first use: [10](#0-9) [11](#0-10) 

**The broken equality binding:** the identity that is allowed to attest "this GitHub account is a member of this authorized team" (i.e., GitHub itself, via a properly signed webhook or the app's own API) is supposed to equal the identity that Shipit actually records as authoritative for team membership. Because signature verification silently degrades to "always verified" when `webhook_secret` is blank, an unauthenticated network attacker becomes that identity — the entity that "authenticates" the membership event (nobody) is no longer bound to the entity that GitHub actually reports the membership for.

### Impact Explanation
An attacker who knows (or guesses via `Team#find_or_create_by_handle`/prior observation) the `github_id` of one of the organization's authorized teams can send a forged `membership` webhook naming their own real GitHub login as `member.login` with `action: "added"`. This creates/updates a local `Membership` row tying their `User` to that `Team`, with no verification against actual GitHub team membership. When the attacker subsequently authenticates through the legitimate GitHub OAuth flow with their own account, `User.find_or_create_from_github` matches the existing `github_id`, and `current_user.authorized?` returns true because the local `Membership` already exists — bypassing the `Shipit.github_teams` authorization check entirely (`app/controllers/concerns/shipit/authentication.rb`). This grants full, authenticated application access (deploys, rollbacks, task triggers) to someone never actually granted access via GitHub. This matches the explicitly in-scope High-severity impact: "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
This requires only that the deployment left `webhook_secret` unset — a state the project's own setup documentation and default templates explicitly support ("Webhook secret (optional)"). No credentials, tokens, or privileged access of any kind are required; the attacker only needs network access to the `/webhooks` endpoint and knowledge of a target team's numeric GitHub team ID (obtainable from the GitHub UI/API for any team the attacker can view, or via reconnaissance of the target org). This is a realistic misconfiguration surface, not a theoretical one, and the exploitation path (single unauthenticated POST + a normal OAuth login) is straightforward.

### Recommendation
- Make `webhook_secret` mandatory at boot/configuration-validation time (fail fast if `Shipit.github(organization:).webhook_secret` is blank), rather than silently accepting unsigned/unverifiable webhooks.
- In `GithubApp#verify_webhook_signature`, do not treat an absent secret as an automatic pass; instead reject with a clear configuration error.
- Defense in depth: in `MembershipHandler`, cross-check the reported membership against the GitHub API (as `Team#refresh_members!` already does) rather than trusting the webhook body outright, especially for teams referenced by `Shipit.github_teams`.

### Proof of Concept
1. Deploy Shipit with a GitHub App configured but `webhook_secret` left blank (a documented, supported configuration).
2. Look up the numeric GitHub `team.id` for one of the teams listed in `github.oauth.teams` (e.g. via `GET /orgs/{org}/teams`, which is often visible without special privileges, or otherwise known/leaked).
3. Send, without any GitHub-issued signature, a raw request:
```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": <authorized_team_github_id>, "name": "Developers", "slug": "developers", "url": "https://api.github.com/teams/1" },
  "organization": { "login": "target-org" },
  "member": { "login": "attacker-github-login" }
}
```
Because `verify_webhook_signature` returns `true` when no `webhook_secret` is configured (`lib/shipit/github_app.rb:76-78`), this payload is accepted and processed exactly as if GitHub had sent it.
4. `MembershipHandler#process` creates/reuses the `Team` by `github_id` and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`, creating a local `Membership` row.
5. The attacker logs into Shipit through the normal GitHub OAuth flow using their real `attacker-github-login` account. `sign_in_github` finds the pre-existing `User` (matched by `github_id`), and `current_user.authorized?` now returns `true` due to the forged `Membership`, granting full access despite never being a genuine member of the authorized GitHub team.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
    end
