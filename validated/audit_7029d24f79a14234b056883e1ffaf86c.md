### Title
Unvalidated swap-route venues can execute malicious contract code beneath the caller’s authorization and drain wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Severity: Medium. `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept opaque caller-supplied route bytes and forward them to the configured router after authorizing only the controller’s exact input-token transfer. [1](#0-0)  The route format permits arbitrary pool addresses, and venue dispatch invokes those addresses without an allowlist, allowing a malicious “pool” to request a token transfer from the transaction signer. [2](#0-1) [3](#0-2) 

### Finding Description
The controller treats `swap` as opaque bytes: `swap_tokens` only checks that it is non-empty, authorizes `token_in.transfer(controller, router, amount_in)`, and calls `router.execute_strategy`. [4](#0-3) [1](#0-0)  For example, `swap_collateral` authorizes the caller, withdraws collateral, and passes the supplied route into this path. [5](#0-4) [6](#0-5) 

The router payload’s `assets` registry supplies each hop’s `pool`, `token_in`, and `token_out`; `Program::decode` validates registry bounds but does not verify that `pool` is a legitimate or approved venue contract. [7](#0-6) [2](#0-1)  The Soroswap adapter then invokes attacker-selected pool code through `get_reserves` and `swap`. [8](#0-7) [9](#0-8) 

A rogue pool can call `wallet_token.transfer(victim, attacker, amount)` from inside its `swap` function; simulation records that transfer as a child of the victim’s `swap_collateral` authorization, and enforcing mode executes it when the victim signs that poisoned tree. [10](#0-9) [11](#0-10)  The router and controller still see valid input spend and positive output, so the normal strategy accounting can complete while the unrelated wallet token is stolen. [12](#0-11) 

### Impact Explanation
A malicious route provider can cause theft of arbitrary tokens held by the victim’s wallet, including tokens unrelated to the lending position or swap route. [13](#0-12)  The loss is not bounded by the swap input because the rogue pool can request an independent `transfer` under the victim’s authorization tree. [11](#0-10) 

### Likelihood Explanation
Exploitation requires the victim to submit a malicious route and sign the resulting authorization tree, so it is not an unauthenticated direct drain. [14](#0-13)  The route is nevertheless opaque XDR supplied off-chain, and any pool address can be embedded in the address registry, making a malicious quote or prepared transaction a practical delivery mechanism. [15](#0-14) [2](#0-1) 

### Recommendation
Enforce a governance-managed allowlist of valid pool contracts for each venue before executing a route, and reject any payload whose pool or token addresses are not approved. [2](#0-1)  As defense in depth, SDKs and wallets should decode `StrategyPayload`, simulate the complete transaction, display all authorization children, and reject any child invocation other than the expected token pull. [11](#0-10) 

### Proof of Concept
1. Deploy `RoguePool` implementing the Soroswap-facing `get_reserves` and `swap(amount_0_out, amount_1_out, to)` ABI. [8](#0-7) [16](#0-15) 
2. Prefund `RoguePool` with enough `token_out` to pay the requested output.
3. In `RoguePool::swap`, call `token::Client::new(&env, &victim_wallet_token).transfer(&victim, &attacker, &victim_balance)`, then transfer the requested `token_out` amount to `to`. [17](#0-16) 
4. Build `StrategyPayload` with `amounts = [requested_out]`, `assets = [rogue_pool, token_in, token_out]`, and one instruction using opcode `0`, mode `All`, `idx_a = 0`, `idx_b = 1`, and `idx_c = 2`; the packed header uses version `1`, `token_in = 1`, `token_out = 2`, `min_out = 0`, `op_count = 1`, and `weight_count = 0`. [18](#0-17) [19](#0-18) 
5. Have the victim invoke `swap_collateral(caller = victim, account_id, current = token_in_hub_asset, amount, new = token_out_hub_asset, swap = payload)`; the controller withdraws the collateral and forwards the route to the router. [20](#0-19) [6](#0-5) 
6. Simulation records the unrelated wallet-token transfer under the victim’s `swap_collateral` authorization; signing that tree transfers the victim’s wallet tokens to the attacker while the swap still produces the expected collateral output. [21](#0-20) [12](#0-11)
