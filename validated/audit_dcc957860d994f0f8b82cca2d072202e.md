### Title
Per-organization webhook signature bypass when a configured GitHub App has no `webhook_secret` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to verify a request against based on an attacker-controlled field in the *unauthenticated* JSON body (`repository.owner.login` / `organization.login`). `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that app's `webhook_secret` is blank. In a multi-organization Shipit deployment (`Shipit.github_organizations`), any organization entry lacking a `webhook_secret` becomes a skeleton key: an attacker can address a webhook payload to that organization to skip HMAC verification entirely, then have the handler act on a `repository.full_name` field belonging to a *different*, protected organization's stack, because the field used to select the verifying secret is not the same field cryptographically bound to the payload once the check is skipped.

### Finding Description
The binding that should hold is: *the organization whose secret authenticated the request* == *the organization/repository whose data is written by the handler*. This binding is broken because:

1. `repository_owner` is read straight out of the untrusted JSON body: [1](#0-0) 

2. That value picks the `GitHubApp` instance used only for signature verification: [2](#0-1) 

3. `verify_webhook_signature` treats a missing `webhook_secret` as automatic success: [3](#0-2) 

4. Once `verify_signature` passes (for *any* reason, including this bypass), the full untrusted `params` — including the `repository.full_name` used to resolve stacks — is handed to handlers with no further authentication: [4](#0-3) [5](#0-4) [6](#0-5) 

The check in `verify_signature` mirrors the BondNFT `_transfer` bug: a guard is checked against one piece of state (`epoch[bond.asset]`, here: "does org X's app have a secret") while the actually-acted-upon state (`bond.expireEpoch`, here: "which repository's stack gets synced/written") is a different field from the same payload that isn't covered by that guard. `repository_owner` (used to pick the verifying key) and `repository.full_name` (used by `PushHandler`/other handlers to resolve the `Stack`/`Repository`) are two independent reads of the same untrusted body; nothing forces them to refer to the same GitHub App/organization, and if the selected app has no secret, neither is ever cryptographically validated.

### Impact Explanation
Multi-tenant Shipit installations configure `secrets.github` with one entry per GitHub organization (`github_app_config`/`github_organizations` in `lib/shipit.rb`, lines 190-200). If an operator provisions an organization without a `webhook_secret` (e.g., for local/dev usage, or simply an oversight since the field is optional per `TOP_LEVEL_GH_KEYS`), that organization becomes an authentication bypass for the *entire* webhooks endpoint, not just its own stacks: an unauthenticated caller can craft a `push`, `status`, `check_suite`, `pull_request`, or `membership` payload whose `repository.owner.login`/`organization.login` names the secret-less org, but whose `repository.full_name` (or `member`/`team` fields for `membership`) names a stack/repository belonging to a different, properly-secured organization. This lets an unauthenticated attacker forge GitHub events causing `GithubSyncJob` to run for another org's stack, forge commit statuses, or add arbitrary users/teams (`MembershipHandler`) — i.e., unauthorized writes into stack state without holding any real GitHub webhook secret.

### Likelihood Explanation
Requires a specific deployment condition: multiple GitHub organizations configured under `secrets.github`, with at least one lacking `webhook_secret`. This is plausible because `webhook_secret` is optional and per-organization (not globally enforced), and the "return true unless webhook_secret" fallback in `GitHubApp#verify_webhook_signature` exists specifically for the single-org backward-compatible schema, but is reused unmodified for the multi-org case where an omission in one org's config has global blast radius. No credentials, session, or GitHub access are required by the attacker.

### Recommendation
- In multi-organization mode (`github_default_organization` present / `github_organizations` returns more than `[nil]`), require `webhook_secret` to be present for every configured organization, and fail closed (reject, don't allow) if it is missing, rather than falling back to `true`.
- Cross-check that `repository_owner` (used to select the verifying app) matches the owner implied by the `repository.full_name`/other identifying fields actually consumed by the handler before dispatching, so verification is bound to the same repository/org the handler acts on.

### Proof of Concept
1. Configure two organizations in `secrets.github`: `protected-org: { webhook_secret: "s3cr3t", app_id: ..., installation_id: ... }` and `open-org: { app_id: ..., installation_id: ... }` (no `webhook_secret`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "full_name": "protected-org/secret-repo", "owner": { "login": "open-org" } }
}
```
No valid `X-Hub-Signature` is required because `Shipit.github(organization: "open-org")` yields a `GitHubApp` whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`).
3. `verify_signature` passes, `PushHandler` runs `Repository.from_github_repo_name("protected-org/secret-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef")`, causing a `GithubSyncJob` against `protected-org`'s stack — all without ever authenticating against `protected-org`'s real secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
