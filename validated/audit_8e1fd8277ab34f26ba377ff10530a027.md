### Title
Open Redirect via unsanitized `omniauth.origin` in `GithubAuthenticationController#callback` - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` sets `session[:user_id]` from the OAuth result and then redirects to `request.env['omniauth.origin']` without validating that the target is a same-origin/internal path. Since the OmniAuth gem's default request phase persists the `origin` query parameter into the session and restores it into `env['omniauth.origin']` on callback, an attacker can craft a login link with an external `origin` and have the victim's browser redirected off-site immediately after authenticating.

### Finding Description
The broken binding: `return_url == request.env['omniauth.origin']` is treated as `return_url ⊆ Shipit::Engine.routes` (a trusted, in-engine path), but no such constraint is enforced anywhere in the code: [1](#0-0) 

`return_url = request.env['omniauth.origin'] || root_path` is used verbatim in `redirect_to(return_url)` with no scheme/host check, no `only_path` enforcement, and no allow-list comparison against `Shipit.host`. `GithubAuthenticationController` is a bare `ActionController::Base`, not `include Shipit::Authentication`, so none of the engine's authorization guards (`force_github_authentication`, `current_user.authorized?`) apply here — they are irrelevant to this redirect anyway, since this is the controller that *establishes* the session.

Exploit flow:
1. Attacker sends victim a link to `/github/auth/github?origin=https://attacker.example/phish` (the OmniAuth request-phase middleware, mounted via `OmniAuth::Builder` at `path_prefix: '/github/auth'`, stores the `origin` param in the Rack session before initiating the GitHub OAuth dance) — confirmed by the engine's own tests exercising the `origin=` query param pattern for internal paths, e.g. `assert_redirected_to '/github/auth/github?origin=http%3A%2F%2Ftest.host%2Fapi_clients'`: [2](#0-1) 
2. Victim completes real GitHub OAuth (they are a legitimate, unsuspecting Shipit user).
3. OmniAuth's callback phase restores `env['omniauth.origin']` from the session, and `callback` in `github_authentication_controller.rb` sets `session[:user_id] = sign_in_github(auth)` then `redirect_to(return_url)`, sending the now-authenticated browser to the attacker's external URL.

No existing guard (`verify_signature`, `force_github_authentication`, `User#authorized?`, model validators) inspects this redirect target — those all apply to different controllers/paths and none constrain `omniauth.origin`.

### Impact Explanation
This is an open redirect chained onto the login flow: the attacker does not steal `github_access_token` or `session[:user_id]` directly (those stay server-side/in the httponly cookie), but they can complete a forced-OAuth-completion / phishing chain — sending a victim to an attacker page immediately after establishing a trusted session, which can be used for credential phishing, further token-grabbing via a fake "re-authenticate" page, or chaining with other bugs (e.g. an open redirect is a classic building block for OAuth authorization-code interception in other flows, and satisfies the "session fixation / forced OAuth completion" High-severity category listed in the rules). It affects any Shipit user who clicks the crafted link; it is repeatable against any victim and does not depend on the target repository/stack — this is an engine-wide login-flow issue, not scoped to one tenant.

### Likelihood Explanation
Attacker cost is very low: they need only construct a URL with a benign-looking Shipit host and a malicious `origin` query parameter and get a legitimate user to click it (standard phishing precondition, not requiring any Shipit secret, session, or privileged role). No non-default Shipit configuration is required — `Shipit.github.oauth?` merely needs to be enabled, which it must be for GitHub login to function at all. This is fully feasible under the attacker model described (any internet user).

### Recommendation
Validate `return_url` before redirecting: require it to be a relative path (`URI.parse(return_url).host.nil?`) or match `Shipit.host`, falling back to `root_path` otherwise. E.g.:
```ruby
return_url = request.env['omniauth.origin']
return_url = root_path unless return_url.present? && URI.parse(return_url).host.nil?
```
wrapped in a rescue for malformed URIs, defaulting to `root_path` on any parse failure.

### Proof of Concept
```ruby
# test/controllers/github_authentication_controller_test.rb
test ":callback redirects to attacker-controlled origin (open redirect)" do
  auth = OmniAuth::AuthHash.new(
    credentials: OmniAuth::AuthHash.new(token: 's3cr3t'),
    extra: OmniAuth::AuthHash.new(
      raw_info: OmniAuth::AuthHash.new(
        id: 44, name: 'Shipit User', email: 'shipit-user@example.com',
        login: 'shipit-user', avatar_url: 'https://example.com',
        api_url: 'https://github.com/api/v3/users/shipit-user'
      )
    )
  )
  @request.env['omniauth.auth'] = auth
  @request.env['omniauth.origin'] = 'https://attacker.example/phish'

  get :callback

  assert_not_nil session[:user_id] # victim is now authenticated
  assert_redirected_to 'https://attacker.example/phish' # equality holds: leaked off-engine redirect
end
```
This demonstrates `return_url == request.env['omniauth.origin']` with an attacker-controlled external value, and that the post-login `redirect_to` follows it unchanged, confirming the missing identity-binding/scope check.

```ruby
    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
```
