### Title
Unallowlisted PR-label-derived env keys reach `PTY.spawn` for shell-interpreted `shipit.yml` steps - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the task environment with no key allowlist, and `LabelCapturingHandler#capture_labels` writes these label names verbatim from the webhook payload. That environment reaches `Command#unbundled_env`, which merges it unfiltered into the hash passed to `PTY.spawn` for shell-interpreted deploy/task steps, so an unprivileged fork PR author can inject arbitrary environment variable *keys* (fixed value `"true"`) into the deploy host's process environment.

### Finding Description
The broken binding: the set of keys reaching `PTY.spawn` should equal the deploy spec's `machine_env` keys ∪ declared `VariableDefinition` names, but in practice it equals `BASE_ENV keys ∪ {any uppercased PR label name}` — there is no allowlist anywhere in this path.

Trace:
- `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` over `super` with no key filtering: [1](#0-0) .
- `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` straight from the webhook body into `pull_request.labels`, with only a String type check (Grape params schema), no name allowlist — confirmed by the test asserting even emoji label names are accepted verbatim: [2](#0-1) .
- `TaskCommands#env` merges `@stack.env` (which is `ReviewStack#env` for review stacks) into the final task environment, after which `deploy_spec.machine_env` and `@task.env` are merged on top — but nothing removes or filters the label-derived keys already present: [3](#0-2) .
- `Command#unbundled_env` merges `BASE_ENV`, `PATH`, and `@env.stringify_keys` with **no key allowlist at all**: [4](#0-3) .
- `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, and deploy/task steps are passed as a single command-line string (e.g. `Command.new(command_line, env:, chdir:)` in `TaskCommands#perform`), which Ruby's `Process.spawn`/`PTY.spawn` executes through `/bin/sh -c` when given a single string argument containing shell syntax: [5](#0-4) [6](#0-5) .
- `EnvironmentVariables#permit`, which does enforce an allowlist against `variable_definitions`, is a separate, opt-in helper (used, e.g., for the `${VAR}` interpolation guard) and is **not** invoked on the path that builds `Command#env`/`unbundled_env`: [7](#0-6) .

Important correction to the question's framing: the *value* assigned for a label-derived key is always the literal string `"true"` (`labels[label_name.upcase] = "true"`), not an attacker-supplied value. So the attacker controls the environment variable **key** (any label they can name on their own PR) but not its value. A vulnerable dynamic-linking scenario (e.g. `LD_LIBRARY_PATH`) would require the fixed value `"true"` to be a meaningful hijack target — this requires the deploy step's current working directory (`@task.working_directory`, which is the checked-out PR branch content, per `Task#working_directory` / `steps_directory`) to contain a relative subdirectory literally named `true` with attacker-supplied shared objects, and requires a subprocess spawned by the shell step to dynamically link against a library name the attacker has spoofed inside that directory. This is a real, if narrow and configuration-dependent, injection primitive: absence of any key allowlist lets a fork PR author set overriding values for **any** env var name via label, not just `LD_LIBRARY_PATH`.

### Impact Explanation
An unprivileged fork PR author who can get a review stack provisioned (repository must have `review_stacks_enabled`/an allowing `provisioning_behavior`) and can attach arbitrary labels to their own PR can inject arbitrary environment variable keys (with fixed value `"true"`) into every shell-interpreted step Shipit runs for that review stack's deploys/tasks/rollbacks (`DeployCommands`, `RollbackCommands`, `TaskCommands` all build on `TaskCommands#env`/`Command#unbundled_env`). Because the checked-out PR content is also under attacker control (as the working directory for the shell steps), this can be chained into `LD_LIBRARY_PATH`-style library-search-path hijacking against binaries spawned during `shipit.yml` steps, yielding code execution on the deploy host — matching the Critical RCE category, but only when the operator's `shipit.yml` steps spawn dynamically-linked binaries susceptible to `LD_LIBRARY_PATH`/similar hijacking and label-based provisioning is enabled for the repository. The blast radius is scoped to the review stack for that repository/PR; it does not cross-contaminate other stacks or repositories directly, though a compromised deploy host afterwards can affect all tenants sharing it.

### Likelihood Explanation
Preconditions: the target repository must have review-stack provisioning enabled for external/fork PRs (`allow_all` or `allow_with_label` with an attacker-satisfiable label), and the operator's `shipit.yml` steps must be shell-interpreted (single-string steps are the norm) and must invoke dynamically-linked binaries in a way susceptible to `LD_LIBRARY_PATH`-style hijacking from a repo-relative `true` directory. Attacker cost is low (open a PR, add a label, push a `true/` directory with a spoofed shared object) and is repeatable per PR/label. However, achieving actual RCE (not just env key injection) depends heavily on the specific `shipit.yml` deploy tooling's library-loading behavior, which is operator-configuration-dependent rather than guaranteed by this engine alone.

### Recommendation
Restrict the keys merged into the task/command environment from PR-label-derived data (and generally from any `Stack#env`/`ReviewStack#env` source) to a fixed, engine-controlled allowlist (e.g., reuse `EnvironmentVariables#permit` against the deploy spec's declared `machine_env`/`VariableDefinition` names) before the hash reaches `Command#unbundled_env`/`PTY.spawn`. Alternatively, prefix/namespace label-derived keys (e.g. `LABEL_<NAME>`) so they can never collide with security-sensitive environment variable names like `LD_LIBRARY_PATH`, `LD_PRELOAD`, `PATH`, `BASH_ENV`, `RUBYOPT`, etc.

### Proof of Concept
minitest plan (`test/models/shipit/review_stack_test.rb` or `test/lib/shipit/task_commands_test.rb` style):
```ruby
test "#env allows PR labels to inject security-sensitive keys with no allowlist" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["ld_library_path"]

  env = stack.env
  assert_equal "true", env["LD_LIBRARY_PATH"]  # attacker-controlled KEY reaches env, unfiltered

  task_env = Shipit::TaskCommands.new(shipit_tasks(:shipit_restart).tap { |t| t.stack = stack }).env
  assert_equal "true", task_env["LD_LIBRARY_PATH"]

  command = Shipit::Command.new("echo hi", env: task_env, chdir: Dir.tmpdir)
  assert_equal "true", command.unbundled_env["LD_LIBRARY_PATH"]  # reaches PTY.spawn's env hash unfiltered
end
```
This demonstrates the equality break: `Set(keys in PTY.spawn env)` includes `LD_LIBRARY_PATH` even though it is absent from `deploy_spec.machine_env` and from any declared `VariableDefinition`, violating the invariant that the env keyset should be restricted to those two sources. Note the assigned value is always `"true"`, not attacker-chosen, which limits (but per the `LD_LIBRARY_PATH` relative-directory mechanism does not eliminate) exploitability toward RCE.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)

      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
