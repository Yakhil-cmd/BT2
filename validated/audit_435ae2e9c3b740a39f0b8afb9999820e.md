**Rationale:** The CVE describes a C/C++ bug where `loadModule` in WAVM's `Include/Inline/CLI.h` performs a fixed-length `memcmp`-style magic-byte comparison without first checking that the file buffer is at least 4 bytes long, causing an out-of-bounds read/crash on files shorter than the compared prefix.

I searched the Polkadot SDK for the analogous pattern — code that inspects a magic-number/prefix on attacker-supplied blobs before further processing:

- `RuntimeBlob::new` checks `raw_blob.starts_with(b"PVM\0")` [1](#0-0) 
- `bare_upload_code` / genesis build / EVM state overrides check `code.starts_with(&polkavm_common::program::BLOB_MAGIC)` [2](#0-1) [3](#0-2) 
- `sp_maybe_compressed_blob::decompress` checks `blob.starts_with(&ZSTD_PREFIX)` on the PVF/validation-code decompression path used before hashing/preparing untrusted validation code [4](#0-3) 

In every one of these cases, the check uses Rust's `slice::starts_with`, which internally handles the case where the haystack is shorter than the needle by simply returning `false` — it never indexes past the end of the buffer, so there is no out-of-bounds read possible regardless of input length (including empty or 1–3 byte inputs). This is a fundamental memory-safety guarantee of Rust slices, unlike the raw pointer/fixed-size `memcmp` comparison in the C++ WAVM code that the CVE describes.

I also checked the lower-level blob-length extraction path (`polkavm::ProgramBlob::blob_length`/`parse`) reachable from `extract_code_and_data` [5](#0-4) , but that parsing logic lives inside the external `polkavm` dependency crate, not in-scope production FRAME/runtime code, and per the scan rules dependency-only findings are excluded.

No reachable, in-scope Rust code performs an unchecked fixed-length comparison analogous to the CVE's missing length check; the safe `starts_with` idiom used throughout precludes the underlying bug class (OOB read on short/attacker-controlled magic-byte input).
