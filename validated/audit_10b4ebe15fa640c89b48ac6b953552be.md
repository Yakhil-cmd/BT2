### Title
Cross-organization commit-status forgery via unscoped `StatusHandler` lookup, allowing signature verification of one org to write CI status onto any repository's commit - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the untrusted request body, then verifies the signature against the raw payload with that org's secret. Once verification succeeds, `Shipit::Webhooks::Handlers::StatusHandler#process` looks up the target `Commit` **solely by `sha`**, with no scoping to the repository/organization whose secret authenticated the request. This breaks the "organization that authenticated versus the repository that is written" binding described in the class of bug this report is analog to (approving/authorizing against one identity while acting on a different, unchecked target).

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-49) picks the `github_app` via `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the JSON body (`params.dig('repository','owner','login')`), and verifies `X-Hub-Signature` against `request.raw_post` using that org's `webhook_secret`. [1](#0-0) [2](#0-1) 
- After verification, `create` dispatches the parsed body to all registered handlers for the event type: [3](#0-2) 
- `StatusHandler#process` resolves the affected record with a global, unscoped query: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. It never checks `repository.full_name`/`owner.login` against the commit's stack/repository, unlike the base `Handler#stacks`/`repository_name` helpers that other handlers use. [4](#0-3) [5](#0-4) 

Because Shipit's GitHub App config is inherently multi-tenant (multiple organizations, each with its own `webhook_secret`, are configured side by side): [6](#0-5) 

an operator who legitimately controls one configured organization (and therefore legitimately possesses that org's `webhook_secret`, since they set up the GitHub App integration for it) can compute a valid `X-Hub-Signature` for an arbitrary payload of their choosing, using their own org's secret. The signature only proves "this body was signed by org A's secret" - it says nothing about which repository's data is inside that body. `verify_signature` re-derives the org purely from the body's `repository.owner.login`, so the attacker simply sets that field to their own org (to pass verification) while setting the `status` event's `sha` field to a commit belonging to a *different, victim* stack tracked by the same Shipit instance. `StatusHandler` will then happily attach a forged CI status to that victim commit, because it looks the commit up by `sha` alone, globally, with no cross-check against the org that actually authenticated the request.

### Impact Explanation
Commit statuses gate whether a commit is `deployable?`: `Commit#deployable?` returns true when `success? && !blocked?` (or CI is ignored). [7](#0-6) 
`create_status_from_github!` feeds directly into `status`/`deployable?` via `add_status`, and successful status changes trigger `stack.schedule_merges` and continuous delivery scheduling. [8](#0-7) [9](#0-8) [10](#0-9) 
An attacker who controls their own org's webhook secret (a credential they legitimately hold for their own tenant, not a Shipit session/ApiClient/API secret) can therefore forge a "success" status for a specific commit SHA belonging to a victim's stack in the same multi-tenant Shipit instance, if they can guess/know that SHA (commit SHAs of the target repo are frequently public, e.g. on GitHub, or observable via Shipit's own UI). This can satisfy the `ci.require` gating and `continuous_deployment?` conditions, leading to an unauthorized/unintended deploy being scheduled for the victim's stack - a cross-tenant integrity violation of the org-vs-repository binding, without ever touching the victim org's actual `webhook_secret`.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured with more than one GitHub organization (a documented, supported configuration shown in `config/secrets.development.shopify.yml`), (2) the attacker to legitimately administer one of those organizations' GitHub App integration (so they know that org's own `webhook_secret` - not a privileged Shipit credential, ApiClient token, or the victim's secret), and (3) knowledge of a target commit SHA in the victim stack, which is typically discoverable (public repos, Shipit's own commit listing pages, etc.). No Shipit session, ApiClient token, or GitHub write access to the victim repo is required, matching the "unprivileged attacker" framing of this analysis.

### Recommendation
- In `StatusHandler` (and any other handler using global lookups), scope the query by the repository resolved from the authenticated organization/hook, not solely by `sha`. Use the same `repository_name`/`stacks` resolution already available via `Handler#stacks` and cross-check it against `repository_owner`/the org whose secret validated the signature.
- In `WebhooksController#verify_signature`, after successfully verifying with a given org's secret, enforce that any repository/organization actually acted upon by downstream handlers for this request belongs to that same authenticated org, rejecting mismatches.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` (attacker-administered) and `orgB` (victim), each with distinct `webhook_secret`s, as shown in `config/secrets.development.shopify.yml`.
2. Attacker knows `orgA`'s `webhook_secret` (they legitimately configured their own GitHub App installation) and knows the SHA of a commit tracked under a stack belonging to `orgB` (e.g. from public GitHub or the Shipit UI).
3. Attacker crafts a `status` event JSON body:
```json
{
  "repository": {"owner": {"login": "orgA"}},
  "sha": "<victim_orgB_commit_sha>",
  "state": "success",
  "context": "ci/forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(orgA_webhook_secret, body)>` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` as `orgA`, fetches `orgA`'s `webhook_secret`, and verification succeeds because the attacker signed with the correct (their own) secret. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (belonging to `orgB`'s stack), and calls `create_status_from_github!`, recording a forged "success" status against it - despite the request never being authenticated by `orgB`'s secret. [11](#0-10)

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
