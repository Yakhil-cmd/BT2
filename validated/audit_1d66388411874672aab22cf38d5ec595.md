### Title
Bad-debt write-down can be dodged by early suppliers - (File: contracts/pool/src/interest.rs)

### Summary

Residual bad debt is only written into a market’s `supply_index` when liquidation cleanup or `clean_bad_debt` executes, while ordinary withdrawals pay suppliers at the pre-write-down index. [1](#0-0) [2](#0-1) [3](#0-2) 

A debt-free supplier who observes a newly insolvent account can therefore call `withdraw` before the write-down, receive unimpaired cash, and concentrate the subsequent loss on the suppliers who remain. [4](#0-3) [5](#0-4) 

### Finding Description

`Controller::withdraw` accepts a vector of `(HubAssetKey, i128)` legs, and controller-side `process_withdraw` treats an amount of zero as a full withdrawal. [6](#0-5) [7](#0-6) [8](#0-7) 

The withdrawal path only requires caller authorization and ownership or delegation of the withdrawing account; the account-level solvency check happens after the pool payout. [9](#0-8) 

In the pool, withdrawal resolves shares against the current `supply_index`, burns them, checks cash reserves, applies the utilization and nonzero-supply guards, debits cash, and transfers the proceeds. [10](#0-9) [11](#0-10) 

Withdrawal does not call `require_backed_market`; moreover, `backing_shortfall` counts all outstanding debt shares at their ceiled face value until those shares are removed. [12](#0-11) 

Permissionless `clean_bad_debt` requires the account to have debt, be insolvent, and have remaining collateral at or below `BAD_DEBT_USD_THRESHOLD`. [13](#0-12) [14](#0-13) 

Cleanup submits all remaining deposit positions and all debt positions to `seize_positions`; the pool’s borrow-side handling reduces the debt market’s supply index by the remaining bad-debt ratio. [15](#0-14) [16](#0-15) 

Because that write-down applies only to shares still present at execution time, suppliers who exited beforehand avoid their pro-rata share while remaining suppliers absorb a larger fraction. [17](#0-16) [18](#0-17) 

### Impact Explanation

This is a Medium-severity unequal-loss-allocation issue that directly transfers an insolvency loss from faster suppliers to slower suppliers. [5](#0-4) 

The included harness demonstrates that a supplier holding 75% of the market can exit at the old index and increase the remaining 25% supplier’s loss by more than three times. [19](#0-18) 

The last supplier is additionally trapped because `require_supply_for_debt` prevents burning the final supply shares while borrowed shares remain outstanding. [20](#0-19) 

### Likelihood Explanation

The attacker only needs to own or control a supply position and invoke `withdraw(caller, account_id, [(debt_asset_key, 0)], Some(caller))`; no privileged role or leaked key is required. [4](#0-3) [21](#0-20) 

The trigger is public: after prices make an account insolvent but before liquidation or cleanup has executed, the affected market still pays withdrawals at the old supply index. [22](#0-21) 

The attack is bounded by available pool cash, the configured utilization ceiling, account-level post-withdrawal solvency, and the need for another supplier to remain or for the attacker to leave a dust balance. [11](#0-10) [23](#0-22) 

### Recommendation

Recognize eligible bad debt before market withdrawals can price supply claims at the stale index, rather than waiting for a later liquidation cleanup call. [10](#0-9) [3](#0-2) 

A practical design is to record a per-market pending-bad-debt obligation when a permissionless valuation identifies an eligible insolvent account, then apply the corresponding supply-index write-down or withdrawal haircut before allowing exits in that market. [24](#0-23) [25](#0-24) 

If immediate write-down is not possible, withdrawal should at least enforce a backing check that subtracts pending unrecoverable debt from `cash + outstanding_debt`, and the last-supplier restriction should be paired with an exit haircut rather than concentrating the full loss on that supplier. [26](#0-25) 

### Proof of Concept

The repository already contains a direct reproduction in `supplier_can_exit_ahead_of_bad_debt_writedown`. [27](#0-26) 

1. Bob supplies 75 ETH and Carol supplies 25 ETH to the same debt market. [28](#0-27) 
2. Alice supplies USDC collateral and borrows ETH. [29](#0-28) 
3. A public collateral-price fall makes Alice liquidatable, but no bad-debt write-down has yet run. [30](#0-29) 
4. Bob executes a full ETH withdrawal before liquidation and receives at least his displayed pre-crash supply balance. [31](#0-30) 
5. A subsequent liquidation socializes the residual debt, and Carol’s loss is asserted to be more than three times the loss she would have borne if Bob had not exited first. [32](#0-31) 

The corresponding user call is `Controller::withdraw(bob, bob_account_id, vec![(ETH_HUB_ASSET, 0)], Some(bob))`, followed by either a liquidation that leaves socializable residual debt or `clean_bad_debt(caller, alice_account_id)` when Alice’s remaining collateral is within the dust threshold. [4](#0-3) [33](#0-32)

```rust
pub(crate) fn apply_bad_debt_to_supply_index(cache: &mut Cache, bad_debt: Ray) {
    let total_supplied_value = cache.supplied().mul(cache.env(), cache.supply_index());

    if total_supplied_value == Ray::ZERO {
        return;
    }

    let capped = bad_debt.min(total_supplied_value);
    let remaining = total_supplied_value.checked_sub(cache.env(), capped);

    let reduction_factor = remaining.div_floor(cache.env(), total_supplied_value);
    let new_supply_index = cache
        .supply_index()
        .mul_floor(cache.env(), reduction_factor);

    cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
```

```rust
/// Panics with `PoolInsolvent` if the market has a positive backing shortfall.
///
/// Backing = cash + ceiled debt value; claims = floored supply value.
pub(crate) fn require_backed_market(env: &Env, cache: &Cache) {
    assert_with_error!(
        env,
        backing_shortfall(cache) == 0,
        CollateralError::PoolInsolvent
    );
}

/// Asset units by which supplier claims exceed cash + debt (0 if solvent).
pub(crate) fn backing_shortfall(cache: &Cache) -> i128 {
    let supplied_claim = cache.unscale_supply_floor(cache.supplied());
    let outstanding_debt = cache.unscale_borrow_ceil(cache.borrowed());
    let backing = cache.cash().saturating_add(outstanding_debt);
    supplied_claim.saturating_sub(backing).max(0)
}

/// Panics with `PoolInsolvent` if supplied is zero while borrowed debt is non-zero.
pub(crate) fn require_supply_for_debt(env: &Env, cache: &Cache) {
    if cache.supplied() == Ray::ZERO && cache.borrowed() != Ray::ZERO {
        panic_with_error!(env, CollateralError::PoolInsolvent);
    }
```
