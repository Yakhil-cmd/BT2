### Title
A single un-withdrawable dust `RcCrowdloanContribution` permanently blocks `unreserve_crowdloan_reserve` for the whole `(block, para_id)` key - ([File: pallets/ah-ops/src/lib.rs])

### Summary
`do_unreserve_crowdloan_reserve` gates the release of a depositor's `RcCrowdloanReserve` on `contributions_withdrawn`, which simply checks whether *any* `RcCrowdloanContribution` entry still exists for the `(block, para_id)` prefix. If even one contribution entry can never be successfully transferred out via `do_withdraw_crowdloan_contribution` (e.g. because the transfer amount is dust and would create a sub-ED balance, or the pot lacks sufficient reducible balance), that entry is never removed, `contributions_withdrawn` never returns `true`, and every legitimate depositor's reserve for that `(block, para_id)` is frozen forever with no escape hatch in this pallet.

### Finding Description
`unreserve_crowdloan_reserve` is a permissionless, signed-origin-callable extrinsic [1](#0-0) . It calls `do_unreserve_crowdloan_reserve`, which requires `contributions_withdrawn(block, para_id)` to be `true` before releasing `RcCrowdloanReserve` [2](#0-1) . `contributions_withdrawn` only checks whether the `RcCrowdloanContribution` map is empty for that `(block, para_id)` prefix, regardless of which depositor owns the stuck entry [3](#0-2) .

`do_withdraw_crowdloan_contribution` is also permissionless (any signed origin can supply an arbitrary `depositor`) [4](#0-3) . It calls `RcCrowdloanContribution::take(...)` first, then attempts `Currency::transfer(&pot, &depositor, contribution, Preservation::Expendable)` [5](#0-4) . If this transfer fails, the function returns `Err(Error::FailedToWithdrawCrowdloanContribution)`. Because FRAME wraps dispatchable execution in an implicit storage transaction, an `Err` return rolls back the `take()` as well, so the contribution entry is *not* removed and remains permanently stuck at that key — every future retry hits the exact same failure deterministically.

A genuine failure mode for the transfer exists independent of `Preservation::Expendable` on the sender: if `contribution` is a dust amount below the existential deposit and the `depositor` account does not currently exist, the mutate/mint into a brand-new sub-ED balance account fails, since pallet_balances disallows creating an account below ED. This is a real, deterministic, unconditional failure — not something that can be "fixed" by retrying.

However, on closer inspection, the specific attacker scenario in the question (attacker drains the pot below ED "via unrelated transfers") does not hold: the pot account referenced in `RcCrowdloanContribution` is an on-chain derived/migrated account, and nothing in this pallet or the described call sequence gives an unprivileged attacker the ability to *reduce* the pot's balance below what is required to cover the remaining contributions — `Preservation::Expendable` explicitly permits full reaping of the sender (pot) account, so a low pot balance alone (as long as it covers `contribution`) does not cause failure. The realistic root cause is dust-below-ED failures at the *receiver* side (an un-created `depositor` account receiving less than ED), which stems from real migrated contribution data, not attacker-supplied balances at runtime. An attacker cannot fabricate new `RcCrowdloanContribution` entries or alter existing ones; they can only permissionlessly *trigger* withdrawal attempts on entries that already exist from the migration.

That said, the underlying logic flaw is real and reachable through the normal, permissionless call path: any contribution entry that fails to transfer (for whatever the reason — dust-to-new-account, or any other transient/permanent transfer failure) becomes permanently un-removable, and since `contributions_withdrawn` requires the *entire* prefix to be empty, this permanently blocks the unrelated `unreserve_crowdloan_reserve` caller(s) sharing that `(block, para_id)`. There is no governance/root escape function in this pallet to force-clear a stuck `RcCrowdloanContribution` entry or to force-unreserve a `RcCrowdloanReserve` bypassing the check.

### Impact Explanation
If any single `RcCrowdloanContribution` under a `(block, para_id)` key is permanently un-withdrawable, the fund creator's `RcCrowdloanReserve` deposit (typically 500 DOT) for that crowdloan is frozen indefinitely, with no code path in this pallet to force-release it. This matches the "permanent fund freeze" scoped impact, though it is a data-triggered/self-inflicted freeze from real migrated dust balances rather than an attacker-fabricated balance manipulation.

### Likelihood Explanation
The exploitability depends entirely on whether such an un-withdrawable dust contribution can occur in the actual migrated crowdloan data (e.g. tiny leftover contributions below ED to accounts that don't otherwise exist). This is plausible in practice for real crowdloan datasets, but it is **not** something an unprivileged attacker can manufacture at will as described (attacker cannot drain the pot below ED via ordinary transfers, since `Preservation::Expendable` allows full reaping and the pot is not attacker-controlled). The attacker's only real lever is to permissionlessly call `withdraw_crowdloan_contribution` for arbitrary depositors to accelerate exposure of a pre-existing stuck entry, not to create one.

### Recommendation
- Add a privileged (governance/root) recovery extrinsic to force-remove a stuck `RcCrowdloanContribution` entry (crediting/burning the dust appropriately) or to force-unreserve `RcCrowdloanReserve` independent of `contributions_withdrawn`, so a single unresolvable dust entry cannot permanently freeze other depositors' reserves.
- Alternatively, change `do_withdraw_crowdloan_contribution` to tolerate the dust-creation failure (e.g. fall back to `Preservation::Preserve`/burn dust into an alternate destination such as treasury) rather than reverting and leaving the entry stuck forever.
- Reconsider `contributions_withdrawn` to only guard the specific reserve being released rather than requiring the entire `(block, para_id)` contribution set to be empty, if that is feasible given the data model.

### Proof of Concept
Rust unit test in `pallets/ah-ops/src/tests.rs`:
1. Insert two `RcCrowdloanContribution` entries under the same `(block, para_id)`: one normal contribution to an existing account, one dust contribution (amount < ED) to a non-existent `AccountId`, both drawn from the same `pot` funded with exactly the sum of both contributions (well above ED).
2. Insert a `RcCrowdloanReserve` entry for a third `depositor` account at the same `(block, para_id)`.
3. Call `withdraw_crowdloan_contribution` for the normal contribution — assert it succeeds and the entry is removed.
4. Call `withdraw_crowdloan_contribution` for the dust contribution — assert it returns `Error::FailedToWithdrawCrowdloanContribution` and assert via storage read that the `RcCrowdloanContribution` entry for the dust depositor **still exists** (i.e., the `take()` was rolled back).
5. Call `unreserve_crowdloan_reserve` for the reserve depositor — assert it returns `Error::ContributionsRemaining` indefinitely, even after repeated retries, proving no code path can ever release the reserve deposit.
