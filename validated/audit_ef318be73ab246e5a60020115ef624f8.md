### Title
Private-asset transfer validation trusts sender-supplied `src_coin` amount instead of the actual global spent-state of the source output - ([File: indivisible_asset.js])

### Summary
The Namada incident stemmed from a mismatch between what the ledger's live state actually held and what a client-facing component (indexer) trusted, letting an attacker spend/sweep shielded funds that a stale, unauthenticated view claimed were still available. The closest reachable analog in ocore is in the private (indivisible) asset payment-chain validator: when validating a transfer of a private, fixed-denomination coin, the core "double spend"/ownership check for the *source* coin is not resolved from the authoritative global `outputs` table (as it is for public payments), but is instead pre-populated by the validator itself into `objValidationState.src_coin` directly from the previous (chain-supplied, unverifiable at that point) private element, and never cross-checked against the true `is_spent` state of that output.

### Finding Description
For public and non-fixed-denomination payments, `validatePaymentInputsAndOutputs` in `validation.js` resolves the amount/denomination/address of a spent input by querying the authoritative `outputs`/`units` tables and checking stability/sequence there [1](#0-0) .

For private, fixed-denomination assets, this lookup is explicitly skipped because "we validate the entire chain before saving anything," and the code instead trusts a pre-populated `objValidationState.src_coin` object supplied by the caller: [2](#0-1) .

That `src_coin` is populated in `indivisible_asset.js`'s `validatePrivatePayment` purely from the previous private element in the (attacker/peer-supplied) chain — `prev_hidden_output.amount`, `src_output.address`, `src_output.blinding` — with no lookup into the authoritative `outputs` table to confirm that output actually still exists unspent with that amount/denomination: [3](#0-2) .

The only cross-check performed is `validateSpendProof`, which merely confirms the spend proof hash recorded in the `spend_proofs` table for *this* unit/message_index matches a hash computed from the (self-supplied) `amount`/`blinding`/`address` values — it does not verify those values against the real prior output row: [4](#0-3) .

The actual double-spend/consumption bookkeeping only happens later, atomically, at save time via `UPDATE outputs SET ... WHERE unit=? AND message_index=? AND output_index=? AND is_spent=0`, guarded inside a DB transaction in `validateAndSavePrivatePaymentChain`: [5](#0-4) , wrapped by BEGIN/COMMIT in `private_payment.js`: [6](#0-5) .

This design means the entire correctness of amount/ownership for a private-asset transfer chain rests on the private chain elements supplied by the sender/peer being internally consistent and never independently reconciled with the real state of the source output prior to commit — structurally analogous to Namada's MASP indexer trusting a value that diverged from the authoritative on-chain state, enabling a value discrepancy to be exploited before it's caught.

### Impact Explanation
If a peer can supply a private payment chain whose intermediate `payload.outputs[].amount`/denomination for an already-spent or non-existent output differs from the true value recorded when that coin was created (e.g. by constructing a forged/rewritten prior link in the private chain, or replaying/mixing chain elements from unrelated units before the recipient has validated and persisted the true chain), a wallet/hub validating this chain would compute `total_input` and spend proofs purely from attacker-controlled numbers, potentially permitting unauthorized transfer/inflation of a private, fixed-denomination asset's value at the receiving node, or allowing a spend to be accepted where the true source output was already consumed. This is a fund-loss/double-spend class of impact, matching a Medium-severity, protocol-level asset-integrity bug.

### Likelihood Explanation
Exploitation requires an attacker to control (or MITM) the private-payment chain delivered to the victim's node — reachable by any unprivileged sender of a private-payment chain (via `handlePrivatePaymentChains`/`handleOnlinePrivatePayment` in `network.js`/`wallet.js`), since these entry points accept externally supplied `arrPrivateElements`/`chains` and hand them directly to `validateAndSavePrivatePaymentChain` [7](#0-6) . This is directly reachable by a private-payment counterparty as specified in scope, without needing a malicious node/hub/witness. However, forging a consistent chain that also matches an `output_hash` binding (`objectHash.getBase64Hash(objPrivateElement.output)` must equal the hidden output's `output_hash`) constrains the attack; the amount value itself is not covered by that hash-check for prior (non-current) elements' `prev_hidden_output.amount`, since only `address`/`blinding` are hashed for `output_hash`, while `amount` is carried in cleartext in `payload.outputs[i].amount` and is exactly the value trusted into `spend_proof`/`src_coin`. This warrants confirmation via code-level reasoning rather than dynamic proof, since full exploitability depends on interactions across `buildPrivateElementsChain`, `parsePrivatePaymentChain`, and the recipient's own prior knowledge of legitimately-received chains — which is not fully traced here due to complexity/time constraints.

### Recommendation
For private, fixed-denomination transfers, do not trust `src_coin.amount`/`denomination`/`address` purely from the caller-supplied previous private element. Where the previous output is locally known (already validated and stored, e.g., because this node was the previous chain's earlier participant or cosigner), cross-check the supplied private-chain values against the node's own `outputs` row for `(src_unit, src_message_index, src_output_index)` before accepting `objValidationState.src_coin`. At minimum, ensure `output_hash` binds the `amount` field (not just `address`+`blinding`) so that any prior output's declared amount cannot be altered without invalidating the whole hash-chain of proofs back to the original `issue` element, and audit `buildPrivateElementsChain`/`parsePrivatePaymentChain` to ensure the entire chain is transitively verified against the immutable issue-time amount rather than trusting each link's self-reported `amount`.

### Proof of Concept
