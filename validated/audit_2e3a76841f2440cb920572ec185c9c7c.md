### Title
Cross-repository Status webhook injection via unscoped `Commit.where(sha:)` lookup breaks the org→repo webhook authorization binding - (File: app/models/shipit/webhooks/handlers/status_handler.rb, app/models/shipit/merge_request.rb#all_status_checks_passed?)

### Summary
`StatusHandler#process` applies an incoming `status` webhook to every `Commit` in the database whose `sha` matches the payload, without checking that the payload's `repository` matches the commit's actual `stack.github_repo_name`. Because GitHub webhook signatures (`verify_signature` in `app/controllers/shipit/webhooks_controller.rb`) are validated per-organization (via `Shipit.github(organization: repository_owner)`), not per-repository, any repository within the same organization/App installation as the victim stack can produce a validly-signed `status` event that Shipit will apply to a commit belonging to a completely different stack/repository, as long as the attacker can make the SHA match.

### Finding Description
The claimed binding is: `stack.github_repo_name` (the repo the CI provider is authorized to report on) `==` the repository whose GitHub App/webhook_secret signed the consumed `Status`. Tracing the code shows this binding does not actually exist at the repository granularity:

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) resolves the signing key via `Shipit.github(organization: repository_owner)` — keyed by **organization only** (`lib/shipit.rb:170-181`, `github_app_config`). There is no per-repository secret.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is global across the entire `commits` table — it never filters by `params['repository']['full_name']` or checks it against `commit.stack.github_repo_name`. Compare with `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), which scopes via `stacks...where(branch:)` (repository-scoped through the `stacks` helper); `StatusHandler` has no equivalent scoping.
- `MergeRequest#all_status_checks_passed?` (`app/models/shipit/merge_request.rb:193-197`) simply reads `head.statuses_and_check_runs` — it has no way to know a `Status` row was created from a webhook signed by a different repository's GitHub App installation within the org.
- `ProcessMergeRequestsJob#perform` (`app/jobs/shipit/process_merge_requests_job.rb:21-30`) calls `merge_request.all_status_checks_passed?` and, if true, `merge_request.merge!`, which calls `stack.github_api.merge_pull_request(stack.github_repo_name, ...)` (`app/models/shipit/merge_request.rb:169-176`).

Exploit flow (organization-scoped confused deputy): a Git commit SHA1 is a pure content hash of tree/parents/author/committer/message/timestamps — it is not bound to any repository. An attacker who (a) opens a PR against the victim's merge-queue-enabled repo, and (b) also controls (owns, or has push access to) any other repository in the **same GitHub organization/App installation**, can construct a commit with identical byte content in their own repo, reproducing the exact same SHA as their PR's head commit. They then trigger a real, GitHub-signed `status` webhook on their own repo (e.g., by calling the Statuses API themselves or via a controlled CI job) reporting `success` for that SHA. GitHub signs this webhook with the organization's real `webhook_secret` — it passes `verify_webhook_signature` legitimately. `StatusHandler` then matches `Commit.where(sha: ...)` and writes a `success` Status onto the **victim's** commit, because the lookup is not scoped to the originating repository. `all_status_checks_passed?` then returns true, `reject_unless_mergeable!` passes, and `merge!` invokes `stack.github_api.merge_pull_request` for the victim repository — merging attacker-controlled code without it ever being built by the victim repository's actual configured CI.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema in `StatusHandler.params`) validate that *some* payload from *some* repo in the org was properly signed, but none of them validate that the specific repository named in the payload is the one that owns the target `Commit`/`Stack`. `force_github_authentication`, `User#authorized?`, and `require_permission!` are irrelevant here since this path is webhook-only, no session is involved.

### Impact Explanation
This allows an unprivileged GitHub organization member (or anyone able to push to some repo within the org's App installation, e.g. their own throwaway repo they created under the org, if the org permits repo creation, or more directly any repo where they have any write access) to inject fabricated CI success into a completely unrelated stack/repository's commit and trigger an unauthorized merge of attacker-controlled code into the victim repo's default branch via `stack.github_api.merge_pull_request`. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "unauthorized... merge." Repeatable against every stack sharing the same GitHub App installation/organization as the attacker's accessible repo; blast radius scales with however many repos/stacks that org's Shipit installation manages.

### Likelihood Explanation
Preconditions: (1) `merge_queue_enabled: true` on victim stack, (2) attacker able to open a PR (any GitHub user for public repos, or org member for private), (3) attacker controls at least one other repository under the same organization/App installation registered with this Shipit instance — realistic for large orgs with many repos/teams sharing a single GitHub App, and explicitly enabled/documented via the "Using Multiple Github Applications"/single-org multi-repo setup in `docs/setup.md`. Constructing a colliding SHA requires crafting identical raw commit content (tree/parents/author/committer/timestamps/message) in the attacker's own repo, which is fully within attacker control (no cryptographic break required, since SHA1 collision isn't needed — just byte-identical content, which is trivial for content the attacker authors themselves). No Shipit secrets are required. Cost is low, and it's repeatable against any stack in the org.

### Recommendation
`StatusHandler#process` (and `Commit.by_sha`-based lookups reachable from webhooks) must scope by the repository named in the payload, not just SHA: resolve `stack` via `params.dig('repository','full_name')` (or `repository_owner`+name) and restrict `Commit.where(sha: params.sha, stack: matching_stack)` before calling `create_status_from_github!`. Additionally, consider binding webhook signature verification to the specific repository/App installation rather than only the organization, and/or validate that `head.pull_request?`/`stack.github_repo_name` matches the reported `repository.full_name` before accepting a `Status` for merge-queue purposes.

### Proof of Concept
Minitest plan (model/job-level, no live GitHub):
```ruby
test "status webhook from a different repository in the same org can poison an unrelated stack's commit" do
  victim_stack = shipit_stacks(:shipit)               # merge_queue_enabled: true
  other_stack  = shipit_stacks(:cyclimse)              # different repo, same org/App installation
  colliding_sha = "deadbeef" * 5

  merge_request = MergeRequest.request_merge!(victim_stack, 99, shipit_users(:walrus))
  merge_request.update!(head: Commit.create!(stack: victim_stack, sha: colliding_sha, message: "attacker PR"))
  merge_request.update!(mergeable: true, merge_status: "pending")

  # attacker forges a validly-"signed" status webhook naming the OTHER repo, but for the colliding SHA
  Commit.create!(stack: other_stack, sha: colliding_sha, message: "attacker's own repo commit")
  status_params = ExplicitParameters::Params.new(
    sha: colliding_sha, state: "success", context: "ci/required", branches: []
  )
  Shipit::Webhooks::Handlers::StatusHandler.new.call(status_params.to_h) # simulates a validly-signed webhook

  assert merge_request.reload.all_status_checks_passed?  # binding broken: victim stack's commit now shows success

  Shipit.github.api.expects(:merge_pull_request).with(victim_stack.github_repo_name, 99, anything, anything).once
  ProcessMergeRequestsJob.new.perform(victim_stack)
end
```
Assertions on both sides of the equality: `stack.github_repo_name` (victim) vs. the repository actually named in/authorizing the forged `status` payload — the test shows they differ yet `merge_pull_request` is still invoked for the victim stack.
