### Title
Webhook signature verification is keyed to a different field than the one used to select the repository/commit acted upon, allowing forged webhook events to affect stacks belonging to other organizations - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on `params.dig('repository', 'owner', 'login')`, while the handlers that subsequently act on the very same request body select the target `Stack`/`Commit` using an entirely different field (`repository.full_name`, or for `StatusHandler`, no repository field at all). In multi-tenant installations where at least one configured organization has no `webhook_secret` set, this decouples "the organization whose credentials authenticated the request" from "the repository/commit that gets written to."

### Finding Description
`Shipit::WebhooksController#verify_signature` resolves the signing key via: [1](#0-0) [2](#0-1) 

which calls `Shipit.github(organization: repository_owner)` and then `verify_webhook_signature`: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank — no HMAC check is performed at all in that case. `webhook_secret` is documented and configured per-organization as optional, and multiple fixtures/dummy configs show organizations deliberately configured with `webhook_secret: nil` alongside organizations that do set a secret: [4](#0-3) [5](#0-4) 

After the signature gate passes, `create` dispatches the same request body to registered handlers: [6](#0-5) 

Handlers resolve the target `Stack` using `payload.dig('repository', 'full_name')`, a field completely independent of `repository.owner.login` used for signature-key selection: [7](#0-6) [8](#0-7) 

`StatusHandler` is even less scoped: it looks up `Commit` purely by SHA, with no repository/owner check whatsoever, and writes a GitHub-sourced status to it: [9](#0-8) 

The binding that should hold is:
`organization authenticated (via webhook_secret keyed by repository.owner.login)` == `repository/commit written (via repository.full_name / commit sha)`

Because (a) the secret-selection key and the write-target key are different JSON fields in the same attacker-controlled body, and (b) verification is skipped entirely for any organization configured without a `webhook_secret`, an attacker can pick `repository.owner.login` = an org with no secret configured (bypassing HMAC verification outright) while setting `repository.full_name` (or `sha`, for status events) to point at a stack/commit belonging to a *different*, secured organization. `Repository.from_github_repo_name` performs a plain DB lookup with no cross-check against the authenticated organization: [10](#0-9) 

### Impact Explanation
This breaks a deployment-trust binding: an unprivileged, unauthenticated network attacker can forge webhook events processed as if they came from the real GitHub App, for repositories that do have a properly configured (and secret) `webhook_secret`, by simply setting `repository.owner.login` to any org lacking a secret. Concretely:
- Via `StatusHandler`, they can inject arbitrary commit statuses (e.g. forge a "success" CI status) onto **any** commit SHA in the system regardless of stack/repository, without any repository scoping at all.
- Via `PushHandler`/`GithubSyncJob`, they can trigger unscheduled syncs against arbitrary stacks.
- Via `CheckSuiteHandler`/`PullRequest` handlers, they can trigger membership changes, review-stack archival, or check-run refreshes for stacks they do not own.

Because Shipit's continuous-delivery/auto-deploy flow depends on commit statuses/checks being green, forging a status on a commit in a protected repo's stack could contribute to triggering an unauthorized deploy — this specific downstream effect (status → CD auto-trigger) was not independently re-verified line-by-line in this pass and should be confirmed, but the primary vulnerability (cross-organization write via a spoofable webhook with no cross-repository binding check) is confirmed by the code cited above.

### Likelihood Explanation
Exploitability requires only that the Shipit deployment configures more than one GitHub organization (the documented multi-tenant mode) and that at least one configured organization has no `webhook_secret` set — a state the project's own documentation and fixtures treat as a normal, supported configuration (`webhook_secret: # nil`). No GitHub App private key, session, or `ApiClient` token is required; the attacker only needs to know the webhook endpoint URL and the name of any org configured without a secret (which is not treated as sensitive).

### Recommendation
- Reject the request if the derived `repository_owner`'s organization has no `webhook_secret` configured, or require an explicit opt-in ("insecure/no-signature") flag rather than silently returning `true`.
- After signature verification, cross-check that the authenticated organization (`repository_owner` used to select the webhook secret) matches the owner segment of `repository.full_name` (and, for status/check events, the owning organization of the resolved `Commit`/`Stack`) before processing the payload.
- In `StatusHandler`, scope the `Commit` lookup by the repository resolved from the authenticated organization instead of a bare SHA lookup across the whole system.

### Proof of Concept
1. Configure Shipit in multi-tenant mode with two orgs: `SecureOrg` (has `webhook_secret` set) hosting a real, deployed stack, and `OpenOrg` (no `webhook_secret`, e.g. as in `test/dummy/config/secrets_double_github_app.yml`).
2. POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or any garbage value), and body:
```json
{
  "repository": { "owner": { "login": "OpenOrg" } },
  "sha": "<sha-of-a-commit-belonging-to-SecureOrg-stack>",
  "state": "success"
}
```
3. `verify_signature` calls `Shipit.github(organization: "OpenOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — the request is accepted.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and writes a forged "success" status onto the `SecureOrg` commit, with no ownership check performed anywhere in the chain [9](#0-8) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
