### Title
`StatusHandler#process` applies GitHub status webhooks to any `Commit` row matching a sha, without scoping to the reporting repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha` (`Commit.where(sha: params.sha)`) and writes the incoming status to every matching row, regardless of which repository the webhook came from. Unlike `Handler#stacks`, which scopes lookups through `Repository.from_github_repo_name(repository_name)`, `StatusHandler` never checks `payload.dig('repository', 'full_name')` against the commit's own stack/repository, so a status generated by one repository's CI can be written onto a `Commit` belonging to an unrelated stack that happens to share the same sha (e.g., via a fork sharing git history).

### Finding Description
The broken binding is: **the repository that authenticated the webhook (`repository_owner`/`repository.full_name` from the payload) == the repository whose `Commit` rows get mutated**. This does not hold.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) verifies the HMAC using `Shipit.github(organization: repository_owner)` - this authenticates that the payload was legitimately signed for that *organization's* GitHub App installation, it says nothing about which `Commit`/`Stack` should be affected. [1](#0-0) 
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This query is global across the entire `commits` table - it is not filtered by `payload.dig('repository', 'full_name')` or by the commit's `stack_id`/`Repository`. Contrast with the base `Handler#stacks` helper, which properly scopes by repository: [3](#0-2) 
`StatusHandler` does not use this `stacks` scoping at all.

Root cause: sha values are attacker-influenceable in the sense that git commit shas are content-addressed and shared across forks - forking a public repository reproduces identical shas for shared history. An attacker who forks the victim's public GitHub repository and has (or triggers) a CI system on their fork that posts a `status` webhook for that shared sha, will have GitHub sign and deliver that webhook using the same GitHub App credentials/webhook secret used for legitimate installations. `verify_signature` only checks that the payload was signed for *some* known organization/App installation - it does not check that the reported repository is the one owning the `Commit` row being updated.

Downstream, `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) and `UndeployedCommit#deploy_disallowed?` (`app/models/shipit/undeployed_commit.rb:39-41`) derive their result from `status`/`success?`, which is populated purely from `statuses` rows written by `create_status_from_github!`. Once the forged status is attached to the victim's `Commit` row, `deploy_disallowed?` flips from `true` to `false`, and `StacksHelper#deploy_button`/`redeploy_button` (`app/helpers/shipit/stacks_helper.rb:21-36`) render an enabled (non-`btn--disabled`) deploy action for a legitimate operator viewing the victim stack's dashboard.

None of the listed guards prevent this: `verify_signature` authenticates the org, not the repository-to-commit binding; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape of the `status` payload (sha/state/etc.), not ownership; there is no `require_permission!`/`stacks` scope check inside `StatusHandler`.

### Impact Explanation
An attacker who forks a victim's public repository can, via their own fork's CI (or by installing the same public GitHub App on their own account/org and firing a `status` event for a shared-history sha), cause Shipit to write an arbitrary state/description/target_url onto the victim stack's `Commit` row for any shared sha. This flips `deployable?`/`deploy_disallowed?` on the victim stack, causing the dashboard to present an enabled deploy button to a legitimate operator for a commit whose real CI state was never actually green on the victim's own repository/branch. If an operator clicks it, `StacksController` creates a real `Deploy` job that will execute deploy commands (`Command`/`PTY.spawn`) against the victim's actual infrastructure. This is a cross-tenant integrity break where one repository's (attacker-controlled) CI signal mutates another repository's (victim's) deploy precondition state, matching the "payload for one repository mutating another's stack/commit" Critical category.

### Likelihood Explanation
Preconditions: the victim's repository must be public (or otherwise forkable) so that the attacker can obtain a fork sharing commit shas; the GitHub App used by Shipit must be installable by third parties (or already installed on an org the attacker controls) so that GitHub will produce a validly-signed webhook for the attacker's own status event; the victim commit's sha must be one that is shared between the fork and the tracked repository (true for any commit that predates or is untouched by the fork's divergence, which is common for base/parent commits still visible in the "undeployed commits" list). This is fully repeatable - the attacker can repeat for any sha they can reproduce via forking, against any stack in the Shipit instance, at no cost beyond forking a repo and pushing a commit/CI status.

I was not able to fully confirm from the available index whether `Shipit.github(organization:)` resolution is dynamic per-GitHub-App-installation (meaning any org that installs the shared public App would automatically pass `verify_signature`) or requires a per-organization static secret pre-registered in Shipit's own configuration (which would materially narrow the attack to orgs already trusted by the Shipit operator). This distinction affects exactly which "unprivileged" actors can produce a validly-signed forged status, but does not change the core finding that `StatusHandler#process` itself performs no repository-scoping once a signature is accepted.

### Recommendation
Scope `StatusHandler#process` the same way other handlers do: resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` and only update `Commit` rows whose `stack_id` belongs to those stacks (e.g., `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), rejecting/ignoring statuses for shas that don't belong to the reporting repository's own stack(s).

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/status_handler_test.rb` conceptually, though `test/**` is out of scope for grading - described here for engineering reference):
1. Create `stack_a` for repository `attacker/fork` and `stack_b` for repository `victim/repo`.
2. Create a `Commit` with the same `sha` (`"deadbeef"`) under both `stack_a` and `stack_b` (simulating shared fork history), with `stack_b`'s commit initially having no successful status.
3. Assert before: `UndeployedCommit.new(stack_b_commit, index: 0).deploy_disallowed?` is `true`.
4. Invoke `StatusHandler.call('sha' => 'deadbeef', 'state' => 'success', 'repository' => { 'full_name' => 'attacker/fork', 'owner' => { 'login' => 'attacker' } })` (bypassing controller-level signature verification, simulating an already-verified webhook for `attacker/fork`).
5. Reload `stack_b_commit`; assert after: `UndeployedCommit.new(stack_b_commit, index: 0).deploy_disallowed?` is now `false`, even though no status was ever reported for `victim/repo`.
6. This demonstrates the equality "reporting repository == mutated commit's repository" is violated by `StatusHandler#process`'s unscoped `Commit.where(sha: params.sha)` lookup.
