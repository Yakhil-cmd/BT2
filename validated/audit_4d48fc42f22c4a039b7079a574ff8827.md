### Title
`StatusHandler#process` matches commits by SHA only, letting an attacker's own-repo webhook flip `enable_ci!` on an unrelated victim stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up `Commit.where(sha: params.sha)` with no repository scoping, then calls `commit.create_status_from_github!` for every matching row regardless of which repository the signed webhook actually belongs to. Because git commit SHAs are content-addressed and shared across forks/mirrors of a public repository, an attacker who owns their own GitHub repo (with a valid webhook secret for their own org) can emit a genuine, correctly-signed `status` event referencing a SHA that also exists in a victim stack's commit history, causing `Status#enable_ci_on_stack` to call `commit.stack.enable_ci!` on the victim's stack.

### Finding Description
The claimed binding is: `commit.stack == Repository.from_github_repo_name(payload['repository']['full_name']).stacks` — i.e., the stack whose CI flag gets mutated should be the stack owned by the repository named in the signed payload. This binding is broken.

- `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only verifies the HMAC signature against the GitHub App/organization derived from `repository.owner.login` in the payload [1](#0-0) . It proves the payload was sent by a party with a valid secret for *that org*, not that it's authorized to act on any other org's stacks.
- `Shipit::Webhooks::Handlers::Handler` exposes a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)` [2](#0-1) , but `StatusHandler#process` does not use it at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
This query is global across all stacks/repositories in the Shipit instance — it never checks `payload['repository']['full_name']` against `commit.stack`'s repository.
- `Commit#create_status_from_github!` creates a `Status` row tied to `commit.stack_id` [4](#0-3) .
- `Status` has `after_create :enable_ci_on_stack`, which unconditionally calls `commit.stack.enable_ci!` [5](#0-4) .

Exploit flow: an attacker creates/controls a public GitHub repository `attacker/repo` (e.g., a fork of, or a repo sharing commit ancestry with, `victim/prod`, or simply one whose commit graph happens to include an identical SHA — trivially arranged by forking a public victim repo, since forks preserve identical SHAs for shared history). The attacker installs/enables the Shipit webhook integration on their own repo (something an unprivileged GitHub user can freely do for a repo they own), then sends a legitimate `status` webhook event from GitHub (or replays one) with `sha` set to a commit hash that also exists as a `Commit` row belonging to `victim/prod`'s stack in the Shipit database. `verify_signature` passes because the signature is valid for the attacker's own org. `StatusHandler#process` ignores `repository.full_name` entirely and matches on `sha` across the whole `commits` table, hitting the victim's commit row, creating a `Status` on the victim's stack, and firing `enable_ci_on_stack`, flipping `ignore_ci` on `victim/prod`.

None of the existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, model validations) prevent this, because they only validate signature/shape of the attacker's own payload — they never enforce that the matched `Commit`/`Stack` belongs to the repository named in that payload.

### Impact Explanation
This is a cross-repository stack-state mutation: an untrusted party controlling only their own repository's webhook can flip the `ignore_ci` semantics of an arbitrary victim stack whose commit history happens to share a SHA with the attacker's repo (trivial to arrange via forking any public repository tracked by the Shipit instance). `Stack#enable_ci!` — once flipped — changes CI-gating behavior for that stack going forward (affecting `Commit#deployable?` via `stack.ignore_ci?`, and hence `continuous_deployment?` merge/deploy eligibility) [6](#0-5) . This is repeatable against any stack tracking a repository with public/forkable history, and blast radius extends to every tenant/stack in the shared Shipit instance, matching the "payload for one repository mutating another's stack" Critical category.

### Likelihood Explanation
Preconditions: the victim stack must have a `Commit` row whose `sha` also exists in a repo the attacker controls (or can otherwise induce a valid signed webhook for) — straightforward via public GitHub forks, since forking preserves SHAs of shared history, or via any commit whose hash the attacker can predict/observe (SHAs of public commits are not secret). No Shipit secrets, sessions, or team membership are required; the attacker only needs a repo they own with the GitHub webhook enabled, which is self-service. This is low-cost and repeatable per-request.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers) to the repository named in the payload, e.g. restrict the commit lookup to `stacks.flat_map(&:commits)` or join through `Repository.from_github_repo_name(repository_name)` before matching by `sha`, mirroring the `stacks` helper already defined in `Handler`. Additionally, `Status#enable_ci_on_stack` should not unconditionally trust any created `Status` row without confirming provenance from the correct repository/stack pairing.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status event for foreign repo but matching sha enables CI on unrelated victim stack" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, message: 'victim commit')

  refute victim_stack.reload.ignore_ci?

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' },
  }

  Shipit::Stack.any_instance.expects(:enable_ci!)

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)
end
```
This demonstrates that a payload whose `repository.full_name` ("attacker/unrelated-repo") does not match the stack owning the matched commit (`victim_stack`) still results in `enable_ci!` being invoked on `victim_stack`, confirming the broken binding `commit.stack != Repository.from_github_repo_name(payload['repository']['full_name']).stacks`.
