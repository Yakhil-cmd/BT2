### Title
Cross-organization webhook confusion enables victim `ReviewStack` unarchiving/re-provisioning via forged `unlabeled` event - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/unlabeled_handler.rb])

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate against using `repository.owner.login` from the untrusted payload, but `UnlabeledHandler` (via `ReviewStackAdapter`/`Repository.from_github_repo_name`) resolves the actual affected repository/stack using the independent `repository.full_name` field from the same payload. An attacker who controls a webhook-emitting repo in their own organization can decouple these two fields, sign the payload with their own valid `webhook_secret`, and name a victim's repository in `full_name`.

### Finding Description
The claimed binding is: `organization used to verify webhook signature (params.repository.owner.login)` == `organization owning the ReviewStack that is unarchived/re-provisioned (derived from params.repository.full_name)`. This binding is broken.

- `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, i.e. it verifies the HMAC using the config (and secret) belonging to whatever org is embedded in `repository.owner.login` [1](#0-0) [2](#0-1) .
- `UnlabeledHandler#repository` resolves the actual `Repository` (and thus `ReviewStack`) using `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) , and `Repository.from_github_repo_name` simply splits `full_name` on `/` and does a DB lookup, with no cross-check against `repository.owner.login` [4](#0-3) .
- `repository.owner.login` and `repository.full_name` are two independent keys in the same attacker-supplied JSON body; nothing in `ExplicitParameters` schema, `drop_unhandled_event`, or `verify_signature` enforces `full_name.split('/').first == repository.owner.login`.
- `UnlabeledHandler#handle` calls `stack.unarchive!` (via `ReviewStackAdapter#unarchive!`) when `provisioning_behavior_allow_with_label?` is true and the label is absent from `pull_request.labels` (also attacker-controlled) [5](#0-4) , and `ReviewStackAdapter#unarchive!` enqueues `ReviewStackProvisioningQueue.add(stack)` and calls `stack.unarchive!` [6](#0-5) .

Exploit flow: attacker owns organization "attacker-org" configured in Shipit's multi-org `github:` secrets (a supported, documented deployment mode, see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), and thus knows/can compute a valid signature with "attacker-org"'s `webhook_secret`. Attacker POSTs to `/webhooks` an `X-Github-Event: pull_request` body with `action: "unlabeled"`, `repository.owner.login: "attacker-org"`, `repository.full_name: "victim-org/victim-repo"`, and `pull_request.labels` lacking the victim repo's configured provisioning label, signed with attacker-org's secret. `verify_signature` looks up and successfully verifies against attacker-org's `GitHubApp`, so the request passes. `UnlabeledHandler` then resolves the real `victim-org/victim-repo` `Repository`/`ReviewStack` and, if that repo uses `allow_with_label` provisioning behavior and has an archived `ReviewStack` for the matching PR/environment, calls `stack.unarchive!` and enqueues it for provisioning — a cross-tenant write and forced re-provisioning of a repository the attacker never authenticated for.

### Impact Explanation
The attacker forces a state mutation (`ReviewStack.unarchive!`) and a provisioning/deploy-trigger enqueue (`ReviewStackProvisioningQueue.add`) on a victim organization's stack that the attacker's webhook credentials never authorized. This is a cross-tenant payload — one organization's valid webhook signature is used to mutate another organization's `ReviewStack` — matching the "payload for one repository mutating another's stack" Critical category. It is repeatable against any victim repository/PR-environment combination as long as an archived `ReviewStack` exists and the repo uses `allow_with_label`/`prevent_with_label` provisioning behavior, and the blast radius spans every tenant configured under the same Shipit instance.

### Likelihood Explanation
This requires the deployment to be configured with the documented multi-organization `github:` secrets schema (distinct `webhook_secret` per org) — this is an explicitly supported and documented configuration (`docs/setup.md`, `secrets_double_github_app.yml`), not a fringe case. The attacker needs: (1) to control (or register as) an organization/app entry already configured in Shipit's `github` secrets with a valid `webhook_secret` they know (e.g., an org they administer that is legitimately onboarded to the same Shipit instance for their own repos), (2) knowledge that a victim repository/organization also uses the instance with review-stacks enabled and `allow_with_label`/`prevent_with_label` behavior, and (3) an existing archived `ReviewStack` for a matching PR number/environment in the victim repo. Given these preconditions are realistic for shared/multi-tenant Shipit installs, the attack is cheap (a single crafted, self-signed HTTP POST) and fully repeatable.

### Recommendation
In `WebhooksController#verify_signature` and/or in `Handler#stacks`/`UnlabeledHandler#repository`, enforce that the organization used to select the webhook secret (`repository.owner.login`) matches the owner portion of `repository.full_name` before processing (reject with 422 on mismatch). Alternatively, always derive the verifying organization from `full_name`'s owner segment rather than a separate `owner.login` field, and validate the two are consistent for every payload before any handler performs lookups or mutations.

### Proof of Concept
Minitest plan (controller-level, e.g. in `test/controllers/webhooks_controller_test.rb`, using a multi-org secrets fixture like `secrets_double_github_app.yml`):
1. Configure two orgs, `OrgOne` (attacker) and `OrgTwo` (victim), each with distinct `webhook_secret`s.
2. Create `shipit_repositories` entry for `OrgTwo/victim-repo` with `review_stacks_enabled: true`, `provisioning_behavior: allow_with_label`, `provisioning_label_name: "deploy-me"`.
3. Create an archived `ReviewStack` under that repository for `environment: "pr42"`.
4. Build a `pull_request`/`unlabeled` JSON payload with `repository.owner.login = "OrgOne"`, `repository.full_name = "OrgTwo/victim-repo"`, `pull_request.number = 42`, `pull_request.labels = []` (no `deploy-me` label), `pull_request.state = "open"`.
5. Sign the raw payload body with `OrgOne`'s `webhook_secret` and set `X-Hub-Signature`/`X-Github-Event: pull_request` headers.
6. POST to `/webhooks`.
7. Assert response is `:ok` (200), assert the `ReviewStack` for `OrgTwo/victim-repo` `pr42` is `reload.archived? == false`, and assert it was added to `ReviewStackProvisioningQueue` (or `assert_enqueued_with`/queue membership check) — proving `organization verifying signature (OrgOne)` != `organization owning mutated stack (OrgTwo)` yet the mutation succeeded.
