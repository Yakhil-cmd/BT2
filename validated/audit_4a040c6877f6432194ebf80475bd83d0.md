### Title
Webhook signature is verified against a GitHub-owner key that is never checked against the repository the payload actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken straight from the untrusted JSON body. The actual write target used by every event handler (`Repository.from_github_repo_name`) is derived from a *different* field in the same untrusted body — `repository.full_name` — and the two are never cross-checked. Anyone who legitimately knows the `webhook_secret` for one configured GitHub organization in a multi-organization Shipit deployment can forge a signed payload whose `repository.full_name` points at a repository belonging to a completely different organization, causing Shipit to sync/deploy a stack it has no authorization boundary for.

### Finding Description
`verify_signature` computes the signing key from attacker-controlled JSON, not from any independently authenticated source: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')`. Every downstream handler, however, resolves the affected `Repository`/`Stack` using a sibling field, `repository.full_name`, in the base `Handler` class: [3](#0-2) 

Nothing in the controller or in `Handler` enforces that `repository.owner.login` (used to pick the HMAC secret) is the actual owner segment of `repository.full_name` (used to pick the target repository/stack). Since both fields come from the same unauthenticated JSON body — the only trust anchor is the HMAC signature computed with the secret selected by `repository.owner.login` — an attacker who knows the `webhook_secret` for *any* organization configured in `Shipit.github(organization:)` (e.g., their own org in a shared/multi-tenant Shipit instance, as shown by the multiple orgs configured in `test/dummy/config/secrets_double_github_app.yml`) can sign a payload where `repository.owner.login` is their own org (so the correct secret is selected and the HMAC validates) while `repository.full_name` names a repository belonging to an entirely different organization.

For a forged `push` event, `PushHandler#process` will look up stacks for that unrelated repository's `full_name` and immediately trigger a resync with an attacker-chosen `after` SHA: [4](#0-3) 

This breaks exactly the trust binding called out in the rules: "an organization that authenticated versus the repository that is written." The webhook signature only proves the request was signed with organization A's secret; it does not — and is never checked to — prove anything about the repository named in `repository.full_name`, yet that unchecked field is what determines which repository/stack is acted upon.

### Impact Explanation
This allows cross-organization writes: an attacker who is entitled to configure/administer only one GitHub App/organization in a shared Shipit deployment can force `GithubSyncJob`/stack syncs (and by extension deploy triggers, since `sync_github` drives what Shipit believes is deployable) against stacks belonging to a different, unrelated organization's repository, without ever having credentials, membership, or write access to that target repository. This matches the "cross-repository writes" / "unauthorized deploy" impact category.

### Likelihood Explanation
Requires: (1) Shipit configured for more than one GitHub organization (a documented, supported configuration — see `test/dummy/config/secrets_double_github_app.yml`), and (2) the attacker legitimately possessing the `webhook_secret` for at least one of those organizations (e.g., because they administer that org's GitHub App, which is a normal, unprivileged-with-respect-to-the-victim-org position). No access to the victim organization, its repository, or any Shipit-issued credential is needed. This is a realistic misconfiguration/multi-tenancy scenario rather than a purely theoretical one, though it is contingent on multi-org deployment.

### Recommendation
When resolving the target repository/stack in `Handler#repository_name` (and anywhere else `repository.full_name` is used), verify that the owner segment of `full_name` matches the `repository.owner.login` (or `organization.login`) that was used to select the verification secret in `WebhooksController#verify_signature`. Reject the webhook (422) if they diverge. More robustly, look up the `webhook_secret` using the same fully-qualified value (`full_name`'s owner) that is later used for repository resolution, so a single field drives both authentication and authorization decisions.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker administers `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` payload:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies successfully with the known secret. [5](#0-4) 
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on a stack the attacker has no relationship to. [3](#0-2) [4](#0-3)
