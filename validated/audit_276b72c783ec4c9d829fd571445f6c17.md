### Title
Cross-repository forged CI status via unscoped `StatusHandler` commit lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to validate a signature using `repository_owner`, derived from the *attacker-controlled* payload (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) [1](#0-0) [2](#0-1) . Once the signature is accepted for that organization, the event is dispatched to handlers with the raw JSON body, and nothing re-confirms that the entity the handler subsequently mutates actually belongs to the organization/repository whose key validated the signature. `Handlers::StatusHandler#process` is the worst offender: it looks up commits globally by SHA across the entire `commits` table, with no repository/stack scoping at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! (params) }` [3](#0-2) . This breaks the intended binding "organization that authenticated == repository being written."

### Finding Description
The verified binding should be: *organization whose webhook secret validated the signature* == *organization owning the repository/commit the handler mutates*. In `WebhooksController`, `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(...)`, purely to select which HMAC secret to check the raw body against [1](#0-0) . `repository_owner` is read straight out of the same JSON body that's being verified, from `repository.owner.login` (or `organization.login`) [2](#0-1) .

Other handlers (e.g. `PushHandler`, the `pull_request/*` handlers) scope their side effects to `Repository.from_github_repo_name(repository_name)` / `.stacks`, i.e. they at least filter by the `repository.full_name` field taken from the same payload node used for signature routing [4](#0-3) [5](#0-4) . `StatusHandler`, however, does not use `repository_name`/`stacks` scoping at all — it queries `Commit.where(sha: params.sha)` unconditionally across every stack/repository tracked by the whole Shipit instance [6](#0-5) .

An attacker who controls (or has push access in) any GitHub organization/repository that Shipit is configured to trust — including receiving real webhook deliveries for their own low-privilege org, whose `webhook_secret` may even be unset (`verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank) [7](#0-6)  — can send a raw `status` event where `repository.owner.login`/`organization.login` names their own trusted org (so signature verification passes) while `sha` is set to a commit SHA belonging to a completely unrelated stack/organization tracked by the same Shipit instance. Because `StatusHandler` never checks that the found `Commit` belongs to a stack under the authenticated organization, it will happily attach a forged CI status (`state: success`) to that foreign commit.

Creating a `Status` record triggers `after_commit :schedule_continuous_delivery` on `Commit`/`Status` [8](#0-7) , and `Commit#create_status_from_github!` feeds into the commit's `deployable?`/state machinery used to gate deploys and continuous delivery [9](#0-8) , [10](#0-9) . Faking a `success` status on a foreign commit can therefore make an otherwise CI-failing/untested commit appear deployable and, on stacks with `continuous_deployment: true`, cause it to be automatically deployed — all without the attacker ever having credentials, write access, or a valid webhook secret for the victim organization/repository.

### Impact Explanation
This is an unauthorized-deploy primitive that crosses organizational boundaries: an attacker with trust in Organization A (their own, potentially with no configured `webhook_secret`) can inject arbitrary CI status data for commits in Organization B's repositories, tricking Shipit's deployability/continuous-delivery gating into treating a commit as CI-passing when it never was, and potentially triggering an automatic, unauthorized deploy or rollback decision. This satisfies the "unauthorized deploy" High-impact criterion, since it escalates a webhook payload for one trusted-but-unrelated organization into a cross-repository state write on another organization's stack.

### Likelihood Explanation
Likelihood is high for any Shipit deployment using the multi-organization GitHub App configuration (`config/secrets*.yml` `github:` keyed by org, as documented) [11](#0-10) , or any deployment where at least one configured org has no `webhook_secret` set (`verify_webhook_signature` degrades to `return true` in that case) [12](#0-11) . The `status` event handler requires only a valid signature for *some* trusted org and a target commit SHA, which is typically public information (visible via GitHub's API/UI) for any repository Shipit tracks.

### Recommendation
In `StatusHandler#process` (and any other handler that doesn't already do so), scope the `Commit` lookup to stacks belonging to the repository named in the payload (`payload.dig('repository','full_name')`), consistent with `Handler#stacks`/`#repository_name`, and reject/ignore events where the authenticated organization does not match the owner of that repository. More generally, `WebhooksController#verify_signature` should assert that `repository_owner` (used to pick the HMAC key) equals the organization owning the repository the handler is about to mutate, rather than trusting them as independently-controlled fields of the same unverified JSON body.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker-controlled, e.g. `webhook_secret` unset) and `OrgB` (victim, contains a tracked stack/commit with `sha = "deadbeef..."`) — as supported by the documented multi-org config [11](#0-10) .
2. POST to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim OrgB commit sha>",
  "state": "success",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
(`repository.owner.login` is deliberately set to `OrgA` so `repository_owner` resolves to `OrgA`, whose key validates/bypasses the signature check, while `sha` targets a commit that actually lives under `OrgB`.)
3. `WebhooksController#verify_signature` validates against `OrgA`'s secret (or passes unconditionally if unset) [1](#0-0) .
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the OrgB commit (no org/stack filter), and calls `create_status_from_github!`, creating a forged `success` `Status` on it [3](#0-2) .
5. If OrgB's stack has `continuous_deployment: true`, `schedule_continuous_delivery` fires and the forged-success commit can be deployed automatically.

Note: I could not fully trace `Commit#deployable?`/`Stack#schedule_continuous_delivery` end-to-end within the available context (only partial `commit.rb` and referenced test excerpts were indexed); a Devin session with full repository access would be needed to confirm the exact downstream deploy-trigger conditions.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
