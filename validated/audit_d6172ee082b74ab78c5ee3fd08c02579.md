### Title
Naive prefix truncation in `cap_diff_for_prompt` can silently drop or omit attacker-placed high-risk diff content before the security review model ever sees it - ([File: plugins/security-guidance/hooks/review_api.py])

### Summary
`build_investigate_prompt` caps each file's diff at `DIFF_PER_FILE_BYTES` (80,000) and the total diff at `DIFF_TOTAL_BYTES` (400,000) via `cap_diff_for_prompt`, but the capping logic is pure byte-prefix truncation/omission with no regard for where the security-relevant `+` lines fall in the file or in the file ordering. An attacker who controls diff content (e.g., large generated code, padding, or vendored-looking filler placed before/within a file) can push the actual malicious change past the truncation boundary, or past the cumulative total-byte boundary for later files, causing that content to never reach the investigate-stage prompt at all.

### Finding Description
`cap_diff_for_prompt` (`plugins/security-guidance/hooks/review_api.py:31-64`) iterates `files: list[tuple[str, str]]` in whatever order they were assembled (ultimately derived from `git diff` output order, i.e., alphabetical-ish per-file ordering from `parse_diff_into_files` in `gitutil.py`) and:
- Per-file: if `len(content) > DIFF_PER_FILE_BYTES`, it keeps only `content[:DIFF_PER_FILE_BYTES]` and appends a truncation marker — a hard prefix cut with no attempt to locate/anchor high-risk lines.
- Total: once cumulative `total >= DIFF_TOTAL_BYTES`, subsequent files are entirely replaced with `"[omitted by security-guidance: total diff byte cap reached]"` — the whole file's diff (including any dangerous `+` lines) is dropped, not merely trimmed. [1](#0-0) 

Because truncation/omission is purely byte-offset and file-order driven, an attacker who authors the diff (e.g., a large legitimate-looking file change, verbose docstrings/comments, or an early large low-risk file in the same commit) can arrange for:
1. A single file whose dangerous edit is deliberately placed after 80,000 bytes of benign padding within that file — the dangerous lines are cut and replaced by only a marker, so `build_investigate_prompt`'s diff text never contains them.
2. Multiple files where earlier files (by `git diff` order, which is path-name driven) consume the 400,000-byte total budget, causing a later file containing the truly dangerous change to be entirely replaced by the omission marker.

`build_investigate_prompt` then feeds this already-lossy `diff_text` directly into the investigate-stage LLM prompt with no re-check that flagged "changed files" (`touched_paths`) actually have their content represented in the diff body: [2](#0-1) 

There is a partial, unrelated mitigation elsewhere (`_prioritize_diff_files` in `gitutil.py`) that re-orders files by a security-risk-token heuristic when the *file count* exceeds a cap, but that only applies to which files are selected, not to `cap_diff_for_prompt`'s per-file/total byte truncation, so it does not protect against the byte-budget truncation described above. There is no mechanism that guarantees high-risk `+` lines survive truncation — the cap only ever keeps a byte prefix.

### Impact Explanation
This is a Security-control bypass: the two-stage agentic review (`build_investigate_prompt` investigate stage → `build_refute_prompt` self-refute stage) is the mechanism the security-guidance plugin relies on to catch vulnerabilities before code is committed/merged. If the dangerous diff content is truncated/omitted before it ever reaches the model, the review will return `findings: []` or omit the relevant finding for reasons entirely outside the model's control — the control is silently routed around. This matches "Security-control bypass that silently disables or routes around blocking, review, or permission boundaries," since a large but otherwise unremarkable diff can be crafted so that the actual vulnerable lines are never inspected, without any error or warning surfaced to the user beyond a generic truncation marker buried in the prompt.

### Likelihood Explanation
- Preconditions: attacker only needs to submit a commit/diff to a repo under review (ordinary repository-controlled content) with either (a) a single file whose diff exceeds ~80KB with the dangerous edit placed after the cutoff, or (b) enough total diff volume (>400KB) with the dangerous file's `git diff --name-only` position ordered after enough benign volume.
- Feasibility: both conditions are easy to construct deterministically since `DIFF_PER_FILE_BYTES`/`DIFF_TOTAL_BYTES` are known constants (also overridable via env vars, but attacker doesn't need that — defaults are public in the shipped code) and `git diff` file ordering is deterministic/predictable (path-based).
- Repeatability: fully deterministic and repeatable — not timing-dependent or racy.

### Recommendation
Change `cap_diff_for_prompt` so that truncation is content-aware rather than pure byte-prefix:
- Prioritize/preserve high-signal lines (e.g., all `+`/`-` hunk lines matching `_SECURITY_RISK_PATH_TOKENS`-style heuristics, or simply always keep hunk headers plus a bounded sample from the *end* of large files, not just the head) when a file must be trimmed.
- When the total-byte cap is reached, instead of omitting entire remaining files outright, apply a shared per-file mini-budget so every touched file gets at least a minimal representation (e.g., its diff hunk headers and first/last N lines) rather than a full omission.
- Emit the truncation/omission decision as an explicit signal to the caller (not just inline prompt text) so the invoking pipeline can escalate (e.g., flag "N files omitted from review due to size" as a separate advisory) rather than relying on the LLM to notice a marker string.
- Add unit tests asserting that a crafted diff with a dangerous line placed after the per-file/total cap boundary still results in that line being present (or an explicit non-silent escalation) in the built prompt.

### Proof of Concept
Unit test plan for `plugins/security-guidance/hooks/review_api.py`:
```python
def test_per_file_truncation_drops_high_risk_line():
    padding = "x" * (review_api.DIFF_PER_FILE_BYTES - 10)
    dangerous = "\n+os.system(user_input)  # DANGEROUS"
    content = padding + dangerous
    prompt = review_api.build_investigate_prompt(
        ["app.py"], [("app.py", content)]
    )
    # Expected (desired) invariant: dangerous line must survive
    assert "os.system(user_input)" in prompt
    # Actual current behavior: fails because content is prefix-truncated
    # before the dangerous line and only a truncation marker remains.

def test_total_cap_omits_entire_later_file():
    big_benign = ("a.py", "+" + "y" * (review_api.DIFF_TOTAL_BYTES))
    dangerous_file = ("z_exploit.py", "+eval(request.GET['q'])")
    prompt = review_api.build_investigate_prompt(
        ["a.py", "z_exploit.py"], [big_benign, dangerous_file]
    )
    # Expected: dangerous file content should still appear in some form
    assert "eval(request.GET" in prompt
    # Actual: z_exploit.py's diff is replaced entirely by
    # "[omitted by security-guidance: total diff byte cap reached]"
```
Both assertions currently fail against the existing implementation, confirming that `build_investigate_prompt`/`cap_diff_for_prompt` can consistently drop attacker-placed high-risk diff lines from the review model's context.

```python
def build_investigate_prompt(
    touched_paths: list[str],
    diff_files: list[tuple[str, str]],
    *,
    context_note: str = "",
) -> str:
    capped, _ = cap_diff_for_prompt(diff_files)
    diff_text = "\n\n".join(
        f"=== DIFF: {fp} ===\n{content}" for fp, content in capped
    )
    return (
        "Review this change for security vulnerabilities.\n\n"
        "Changed files (you may Read these and any other file in the repo):\n"
        + "\n".join(f"  - {p}" for p in touched_paths[:50])
        + context_note
        + "\n\nUnified diff (only + lines are new):\n\n"
        + diff_text
        + extensibility.guidance_block()
        + "\n\nInvestigate per the method in your instructions, then return "
        "the findings list."
    )
```
