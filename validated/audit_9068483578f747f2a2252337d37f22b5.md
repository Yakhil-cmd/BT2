### Title
`StatusHandler#process` matches commits by bare `sha` across all repositories, letting any org-authenticated webhook mutate a shared-sha commit belonging to a different stack/repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` without any scoping to the repository named in the webhook payload, unlike the base `Handler#stacks` helper which resolves `Repository.from_github_repo_name(repository_name)`. Any `status` webhook whose signature verifies for *some* organization will update every `Commit` row in the database that happens to share that sha, regardless of which repository the status actually came from, which can move a victim stack's `next_commit_to_deploy` and `continuous_delivery_delayed_since`.

### Finding Description
The broken binding: the equality that should hold is `commit.stack.repository.full_name == payload.dig('repository','full_name')` for every `Commit` mutated by `create_status_from_github!` in `StatusHandler#process`. In the actual code this equality is never checked: [1](#0-0) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` iterates over *all* commits sharing that sha across the whole `commits` table/all stacks, whereas the base `Handler` class explicitly provides a `stacks` helper scoped by `Repository.from_github_repo_name(repository_name)` that other handlers use: [2](#0-1) 

`create_status_from_github!` then creates a `Status` row tied to `stack_id` (the commit's own stack, not the webhook's originating repo), and `after_commit` on `Status` schedules `Commit#schedule_continuous_delivery` unconditionally: [3](#0-2) [4](#0-3) [5](#0-4) 

That queues `ContinuousDeliveryJob`, which calls `Stack#trigger_continuous_delivery`, which recomputes `next_commit_to_deploy` and flips `continuous_delivery_delayed_since` via `continuous_delivery_delayed!`/`continuous_delivery_resumed!` purely off the now-attacker-influenced `Status`/`Commit#deployable?` state: [6](#0-5) [7](#0-6) [8](#0-7) 

**Why signature verification does not save this**: `verify_signature` checks the HMAC against a per-organization config keyed by `params.dig('repository','owner','login')`, and `verify_webhook_signature` uses `SecureCompare` against the configured `webhook_secret` for that org: [9](#0-8) [10](#0-9) 

This proves the webhook was genuinely sent by GitHub for *some* repository owned by the org matching `repository_owner`, but it says nothing about which specific repository's commit history the `sha` in the payload belongs to. `Commit.where(sha: params.sha)` has no `.where(stack_id: stacks.pluck(:id))`-style filter, so a real, validly-signed `status` event from an attacker-controlled repository (which shares that org's `webhook_secret`, or shares a sha with a victim commit through common ancestry, forking, or cherry-picks) reaches and mutates a commit belonging to a stack the attacker's repository never authenticated for.

**Attacker request/PR**: attacker forks (or otherwise shares commit history with) the victim's tracked branch, so many commits (particularly the merge-base and any un-rebased history) carry identical shas in both repositories. Attacker's own repository/CI (which they fully control) emits a `status` event on that shared sha; GitHub signs and delivers it; `POST /webhooks` succeeds signature verification for the attacker's own org; `StatusHandler#process` then updates the `Status` (and, transitively, `deployable?`/`next_commit_to_deploy`) for the victim's commit row that happens to share that sha, because the lookup is global.

**Call sequence confirmed**: `StatusHandler#process` → `Commit#create_status_from_github!` → `Status#replicate_from_github!` (creates a `Status` row scoped to the commit's real `stack_id`, not the webhook's repo) → `Status#schedule_continuous_delivery` (`after_commit on: :create`) → `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob.perform_later(stack)` → `Stack#trigger_continuous_delivery` → `next_commit_to_deploy` / `should_delay_continuous_delivery?` / `should_resume_continuous_delivery?` recomputed off the injected status.

### Impact Explanation
The attacker gains repeatable, unauthenticated (from the victim's perspective) control over one bit of state per matching-sha commit: whether that commit is `deployable?` (via injected `success`/`failure`/`error`/`pending` `Status` rows), which flows into `next_commit_to_deploy`, `continuous_delivery_delayed_since`, and ultimately whether/when `Stack#trigger_continuous_delivery` fires a real `Deploy` for the victim stack. This is a genuine cross-tenant write: a `Status` record is created for a stack/commit that never authenticated the request that created it. Blast radius is limited to stacks that have commits sharing a sha with a repository the attacker can genuinely emit webhooks from (their own fork/repo, sharing the same Shipit-configured organization's `webhook_secret`, or the same commit history) — it does not grant direct code execution, token exfiltration, or arbitrary deploys of attacker-chosen commits, only indirect scheduling/state manipulation of a victim's existing commits. This matches "a payload for one repository mutating another's stack/commit" (Critical bucket) in terms of mechanism, but the actual observable effect is confined to delaying/advancing continuous-delivery decisions on already-existing, already-vetted commits shared between the two histories, not injecting a malicious payload for deployment.

### Likelihood Explanation
Preconditions are demanding and largely outside the attacker's control:
1. Victim stack must have `continuous_deployment: true`.
2. Attacker must control a repository that genuinely authenticates against the *same* `webhook_secret`/organization entry configured in Shipit as the victim's org (GitHub Apps typically use one webhook secret per app across all installations, so this is plausible if attacker can install/use the same app on a repo they own, but Shipit's `verify_signature` still requires `Shipit.github(organization: repository_owner)` to resolve to a known, configured organization — an attacker's personal fork under an unrelated login will hit `GithubOrganizationUnknown` and be rejected with 422).
3. A commit sha must genuinely be shared between the attacker's repository and the victim's tracked branch (achievable via forking/shared history, not via hash brute-forcing).

Given these constraints, the attack is feasible primarily in multi-tenant Shipit deployments where multiple repositories/forks fall under the same configured GitHub organization/app installation, and is repeatable at will by the attacker toggling their own CI status on the shared commit.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository named in the payload, mirroring `Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
or equivalently join through `Repository.from_github_repo_name(repository_name)` before querying `Commit`, so a status can never be attributed to a commit outside the repository that authenticated the webhook.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two stacks/repositories `victim/repo` and `attacker/repo` under the same Shipit-configured organization (so `verify_signature` passes for both), each with `continuous_deployment: true`.
2. Create a `Commit` with `sha: 'deadbeef'` under `victim_stack` (`victim_commit`) and a distinct `Commit` row with the same `sha: 'deadbeef'` under `attacker_stack` (`attacker_commit`) — representing the shared-sha scenario from forked history.
3. Assert baseline: `refute victim_commit.reload.deployable?` (no statuses yet), and `assert_nil victim_stack.next_commit_to_deploy` or record its current value `before_value = victim_stack.next_commit_to_deploy`.
4. Build a `status` payload naming only `sha: 'deadbeef', state: 'success'` and `repository.full_name: 'attacker/repo'` (never mentioning `victim/repo`), and call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert `victim_commit.reload.deployable?` flips to `true` purely from the attacker-named-repo payload: `assert victim_commit.reload.deployable?`.
6. Assert `victim_stack.next_commit_to_deploy` changed as a function of the attacker's payload: `refute_equal before_value, victim_stack.reload.next_commit_to_deploy`.
7. Repeat with `state: 'failure'` and show the value flips back, and that `victim_stack.continuous_delivery_delayed_since` toggles via `trigger_continuous_delivery`, proving the equality `attacker_repo_full_name == victim_repo_full_name` was never enforced.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
