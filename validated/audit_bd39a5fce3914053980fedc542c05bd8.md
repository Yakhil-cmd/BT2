### Title
Stale `Account.owner` lets the previous NFT holder keep full spending authority after a position transfer - (File: contracts/controller/src/account.rs)

### Summary
`require_owner_or_delegate`/`is_owner_or_delegate` authenticate callers against `account.owner`, a field frozen inside the stored `Account` struct at account creation, while `require_account_owner` authenticates against `storage::account_owner` (the live position-NFT `owner_of`). When the account NFT is transferred via `position-nft::transfer`/`transfer_from`, nothing updates `account.owner`, so the seller retains owner-level authority over the account and can withdraw its collateral or borrow against it. The new owner is simultaneously locked out of those same paths because `caller == account.owner` fails for them.

### Finding Description
`Account.owner` is set once in `create_account_with` (`account.rs:64-70`) and never rewritten; there is no transfer hook or setter — the NFT contract is stock OpenZeppelin enumerable (`contract.rs:131-173`) with no controller callback. Authorization for all money-moving entrypoints flows through `is_owner_or_delegate` (`account.rs:115-127`), which returns `true` when `caller == account.owner` — the *stale* field, not the NFT owner. `require_owner_or_delegate` (`account.rs:130-140`) therefore keeps accepting the previous owner indefinitely after a sale/transfer. Contrast `require_account_owner` (`account.rs:143-148`), which uses `storage::account_owner` and correctly reflects the live NFT holder — the codebase already recognizes NFT ownership as authoritative for `add_delegate`/`remove_delegate`/`renew_account`, but the account-position paths consult the stale field instead. The declared invariant file even asserts transfers deactivate the previous owner's delegates (`permissionless_entrypoints.txt:111-112`) while remaining silent on the stale owner itself.

### Impact Explanation
Any account whose NFT has ever changed hands is drainable by every prior owner (transfers accumulate; `account.owner` is whichever address was recorded at creation — a transfer chain never rewrites it, but note only the *creation-time* owner and its delegates pass). Concretely, after selling the NFT, the original owner calls `controller::withdraw(account_id, withdrawals, to)` — `process_withdraw` passes `require_owner_or_delegate` (`supply.rs:147-150`) and pays out to the attacker's chosen `to` — or calls `controller::borrow` to draw max debt against collateral belonging to the buyer. This is direct theft of the buyer's collateral, executed by a currently unprivileged (non-holder) address.

### Likelihood Explanation
The trigger is the ordinary, advertised feature of transferring positions (the NFT exists precisely so accounts are tradable). The attacker needs zero cooperation: they sell or transfer the NFT, then at any later point submit `withdraw`/`borrow`/`swap_collateral`/`repay_debt_with_collateral` — all gated only by the stale-owner check. No price manipulation, no privileged access, no timing window. The only nuance: `account.owner` remains the *first* owner, so the exploiter is the account creator (or earliest recorded owner), and any intermediate buyers are exposed the moment they take custody.

### Recommendation
Resolve authority from a single source: have `is_owner_or_delegate`/`require_owner_or_delegate` compare `caller` against `storage::account_owner` (live NFT `owner_of`) rather than the cached `account.owner`, or keep `account.owner` synchronized via a controller-invoked ownership-refresh on every authenticated path. Delegates should also be keyed/validated against the current owner so stale grants cannot survive a sale.

### Proof of Concept
1. Alice calls `controller::supply` with `account_id = 0`; `create_account` mints NFT id 1 to Alice and stores `Account{ owner: alice, .. }`.
2. Alice transfers NFT 1 to Bob via `position-nft::transfer`. Bob is now `owner_of(1)`; `Account.owner` still equals `alice` — nothing rewrites it.
3. Alice calls `controller::withdraw(1, vec![HubPayment{hub_asset, amount}], Some(attacker_addr))`. `process_withdraw` → `require_owner_or_delegate` → `is_owner_or_delegate` returns `true` because `caller == account.owner == alice` (`account.rs:121-122`), despite Alice holding no NFT.
4. `settle_withdraw` pulls the collateral from the pool and pays `attacker_addr`. Post-pool solvency is checked against Alice's view of the account, which permits withdrawal of idle collateral. Bob's collateral is stolen; Bob himself fails `require_owner_or_delegate` on the same paths since `bob != account.owner`.

Confidence caveat: this assumes `storage::account_owner` reads the live NFT owner (consistent with `position-nft`'s "token owner is the account owner" contract and with `require_account_owner` being used for owner-only ops); if it instead also reads the stored field, the impact shifts to permanent freezing of the buyer's funds (new owner can never pass any owner/delegate gate), which is still a valid High-severity analog but via a different vector. I could not read `contracts/controller/src/storage/account.rs` within the available iterations to confirm which source it uses.
