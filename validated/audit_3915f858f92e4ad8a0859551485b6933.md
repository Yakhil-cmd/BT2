### Title
Webhook signature verification is bound to a different payload field than the one used to select the target repository, allowing cross-organization forged deploy triggers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` picks the `GitHubApp` (and its `webhook_secret`) used to verify the HMAC signature from one field of the untrusted payload (`repository.owner.login` / `organization.login`), while the downstream `Handler` subclasses (e.g. `PushHandler`) resolve the actual repository/stack to act on from a *different* field of the same payload (`repository.full_name`). Nothing enforces that these two values refer to the same organization/repository, so a request that is validly signed for one organization's secret can be crafted to act on any other organization's repository known to the Shipit instance.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` and looks up the `GitHubApp` (and its per-organization `webhook_secret`) solely from that value: [1](#0-0) [2](#0-1) 

If the HMAC over the raw JSON body validates against that organization's `webhook_secret`, the request is accepted and dispatched: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 

Every concrete handler, however, resolves the repository/stack to operate on independently, from `params.dig('repository', 'full_name')` (base `Handler#repository_name`/`#stacks`) or `params.repository.full_name` in the pull-request handlers: [4](#0-3) [5](#0-4) 

Because `verify_webhook_signature` only proves "this body was HMAC-signed with organization X's secret" — it never asserts that `repository.owner.login` (used for the secret lookup) equals the owner encoded in `repository.full_name` (used by the handler to pick the target `Stack`/`Repository`) — the two are only coincidentally equal for real GitHub-issued payloads. An attacker who legitimately controls the webhook secret for one onboarded organization (e.g. because they administer a Shipit-connected org/repo and configured that webhook themselves) can craft an arbitrary JSON body where `repository.owner.login`/`organization.login` = their own org (so the signature check picks and validates against a secret they know), while `repository.full_name` = `"other-org/other-repo"` for a completely different organization's stack. `PoolAddressesProvider.getPool()` in the Aave finding is the same class of bug: a value that authorizes a resource is trusted once and reused for a *different* purpose (here, org-A's HMAC secret is trusted to authorize action against org-B's repository) instead of being re-validated against the actual object being mutated.

The broken equality binding is:
`organization authenticated by verify_signature (repository_owner) == organization of the repository the dispatched Handler actually writes to (params.repository.full_name)`

This equality is assumed but never checked.

### Impact Explanation
A successfully forged `push` webhook causes `PushHandler#process` to invoke `stack.sync_github(expected_head_sha: params.after)` on any tracked stack whose repository full name the attacker names, for branches they choose — effectively an attacker-triggered, unauthorized sync/deploy pipeline kick-off against a repository/organization the attacker has no legitimate relationship with. Other handlers (`status`, `membership`, pull-request handlers) are equally reachable cross-organization, letting an attacker create fake commit statuses, add themselves to a fabricated `Team`/`membership` record tied to an org they don't belong to, or manipulate review-stack provisioning for arbitrary repositories. This crosses a repository/organization trust boundary using credentials (a webhook secret) that were only ever meant to authorize actions for the attacker's own organization — matching the "unauthorized deploy" / "cross-repository writes" impact bar.

### Likelihood Explanation
Requires the attacker to already know a valid `webhook_secret` for at least one organization connected to the running Shipit instance (something they'd possess if they configured that organization's GitHub webhook themselves) and requires that the target instance hosts multiple organizations behind one webhook endpoint — a normal, documented multi-tenant Shipit configuration. No repository write access, GitHub App key, or Shipit session/API token is needed for the *target* organization; only a valid secret for *any one* configured organization is needed, matching the "unprivileged attacker" framing in the rules.

### Recommendation
After signature verification, re-derive the organization from the same field used to select the verifying secret and require the `repository.full_name` (or `organization.login`) referenced by the dispatched handler to belong to that same, already-authenticated organization before invoking any handler. Reject the webhook (422) if the two disagree.

### Proof of Concept
1. Attacker administers `org-a`, a legitimate organization connected to the shared Shipit instance, and knows `org-a`'s `webhook_secret` (they configured the GitHub webhook themselves).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "org-b/victim-repo", "owner": { "login": "org-a" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(org-a webhook_secret, raw_body)` and POSTs to `/github/webhooks`.
4. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login')` = `"org-a"`, fetches `Shipit.github(organization: "org-a")`, and the signature validates successfully. [6](#0-5) 
5. `create` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` (from `repository.full_name`, unrelated to the `org-a` secret that authenticated the request) and calls `stack.sync_github(expected_head_sha: ...)` for `org-b`'s stack. [4](#0-3) [7](#0-6)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
