### Title
Unbounded `cases` array in AA definition validation causes CPU-exhaustion DoS during unit validation - (File: aa_validation.js)

### Summary
`validateFieldWrappedInCases` in `aa_validation.js`, which validates the `cases`-wrapped fields of an AA definition (`messages`, `payload`, `outputs`, `choices`, etc.), limits only the nesting **depth** (`MAX_DEPTH = 100`) but places no cap on the **number of elements** in a single `cases` array. Every case can carry an `if` and/or `init` oscript formula, each of which must be parsed by the nearley GLR parser. An attacker can post a unit that defines an Autonomous Agent (reachable by any ordinary unit poster via the `definition` message app, or by an AA that programmatically creates a nested AA) with a single `cases` array containing a very large number of entries, each with distinct `if`/`init` formula strings (to defeat the parser cache), forcing every validating node to perform a large amount of expensive, uncached formula parsing synchronously on Node.js's single-threaded event loop. This is directly analogous to the Discourse bug, where creating/updating a resource (a custom sidebar section) with unbounded nested data caused a request-time denial of service.

### Finding Description
`validateFieldWrappedInCases` recurses per `cases` level and validates each case's `if`/`init` formulas, but only bounds recursion depth, not breadth: [1](#0-0) 

Compare this to other array-like AA-definition fields that *do* enforce explicit item-count caps, e.g. poll choices (`MAX_CHOICES_PER_POLL`) and asset denominations (`MAX_DENOMINATIONS_PER_ASSET_DEFINITION`): [2](#0-1) [3](#0-2) 

`cases` has no such array-length check anywhere in `validateFieldWrappedInCases`, and it is used to wrap `messages`, `payload`, `outputs`, and `choices`: [4](#0-3) [5](#0-4) [6](#0-5) 

Each `if`/`init` formula in a case is validated with `getFormula` and, in the recursive branch, is fed through the nearley oscript grammar parser: [7](#0-6) 

This validation path (`validateAADefinition`) is invoked synchronously by any node validating a unit that contains an app=`definition` message defining a new AA — this is reachable by any unprivileged unit poster: [8](#0-7) 

Formula parsing uses nearley (a GLR parser), and the parser cache only helps when the exact same formula string repeats; an attacker using many distinct trivial-but-unique formula strings (e.g. varying whitespace/constants) defeats the cache: [9](#0-8) 

### Impact Explanation
Since AA definition validation runs synchronously in the Node.js event loop during unit validation (both live and during catchup/stabilization), a single crafted unit with a `cases` array containing many entries with unique `if`/`init` formulas forces every full node (and every node re-validating on stabilization) to spend disproportionate CPU parsing/validating those formulas while blocking the event loop. Because unit validation must complete before the node can process other units, gossip, or RPC requests, this can stall a node's ability to validate/relay/confirm other units for the duration of processing the malicious unit, and repeated posting of such units can produce a sustained denial of service that impedes network-wide confirmation of new units — matching the accepted impact class "a network unable to confirm new units."

### Likelihood Explanation
The `definition` app message is reachable by any ordinary unit author (no special privileges, no AA execution required) as part of normal, low-cost unit posting; the only constraint is overall unit/message payload size limits (`MAX_UNIT_LENGTH`), but formula strings can be kept short while still being numerous and syntactically distinct, and `MAX_DEPTH` restricts nesting depth only, not the number of sibling cases at a single level. This makes the attack straightforward to construct and inexpensive for the attacker relative to the CPU cost imposed on validating nodes.

### Recommendation
Add an explicit maximum item-count check (analogous to `MAX_CHOICES_PER_POLL` / `MAX_DENOMINATIONS_PER_ASSET_DEFINITION`) on the `cases` array length inside `validateFieldWrappedInCases` in `aa_validation.js`, and/or bound the total aggregate number of formulas validated across the whole `cases` tree (not just per-level), so that the total CPU work for parsing case formulas in a single AA definition is capped independent of how the array is nested.

### Proof of Concept
Craft an AA-defining unit whose `messages` field is a `cases`-wrapped structure at a single depth level containing, e.g., 5,000–10,000 case objects, each with a syntactically distinct `if` formula (e.g. `"{1+" + i + "==" + (i+1) + "}"`) and a distinct `init` formula. Post this unit to the network via the normal `definition` app message flow. Each validating node's call to `aa_validation.validateAADefinition` → `validateFieldWrappedInCases` will invoke `formulaValidator.validate` (nearley parse) thousands of times for this single unit, consuming significant CPU synchronously before the unit can be accepted or rejected.

**Note on verification limits:** I was unable to directly confirm the exact per-parse CPU cost of the nearley oscript grammar or the precise `MAX_UNIT_LENGTH` value/how many such cases fit within one unit's byte budget (the constants.js content for these specific numeric limits was not fully retrievable via the index). A background Devin session with full repository access would be needed to benchmark actual parse latency per formula and compute the maximum feasible `cases` array size under `MAX_UNIT_LENGTH`, to precisely quantify the DoS magnitude.
