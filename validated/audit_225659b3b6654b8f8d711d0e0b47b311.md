### Title
Cross-tenant status forgery: `StatusHandler#process` mutates commits by global `sha` lookup with no binding to the webhook's verified `repository_owner` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the attacker-controlled `repository.owner.login` field of the same payload. `StatusHandler#process` then applies the status update to `Commit.where(sha: params.sha)` with no filter tying the matched commit's `stack`/organization back to the payload's `repository`, so a validly-signed webhook from organization A can mutate a commit's status that belongs to organization B's stack.

### Finding Description
The binding that should hold is: `repository_owner used to select the GitHub App / verify signature == organization owning the stack/commit actually mutated`. In code:

- Signature verification: [1](#0-0)  selects the app/secret via `repository_owner`, which is derived purely from `params.dig('repository', 'owner', 'login')` [2](#0-1) . This is fully attacker-controlled JSON in the raw POST body and only needs to name an org the attacker legitimately owns (org A) for a valid `webhook_secret` (org A's own secret) to pass.
- Mutation: `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . This query is **global across the entire `commits` table** — it is not scoped by `stack_id`, by the payload's `repository.full_name`, nor by `repository_owner`. Any commit row anywhere in the database whose `sha` matches is updated, via `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` [4](#0-3) , which writes a new `Status` row against that commit's actual `stack`, plus triggers `Hook.emit` and `stack.schedule_merges` side effects [5](#0-4) .

Exploit flow: attacker owns `attacker/repoA` in Shipit with a legitimate `webhook_secret` for their own org. Victim has `victim/repoB` tracked as a Shipit stack containing a commit with sha `X` (git SHAs are not secrets — they're visible in any public GitHub URL, PR, or commit log). Attacker crafts a `status` webhook body with `repository.owner.login = 'attacker'` (so `repository_owner` resolves to their own org and their own valid HMAC signature verifies) but `sha = X` (the victim's commit). `verify_signature` passes because it only checks the org named in `repository`, never cross-checking it against `sha`'s actual owning stack. `StatusHandler#process` then finds `Commit` row `X` (belonging to `victim/repoB`'s stack) and writes a forged status/state onto it, which can flip `deployable?` and trigger `stack.schedule_merges` / continuous deployment on the victim's stack.

None of the listed guards prevent this: `verify_signature` checks only the org-vs-secret pairing, never repository identity vs. the row being mutated; `ExplicitParameters` (`ParamsHandler`/`params do ... end` block) validates only field types/presence (`sha`, `state`, etc.), not ownership [6](#0-5) ; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler#process`.

### Impact Explanation
A single HTTP POST to `/webhooks` signed with an attacker's own, legitimately-owned org's `webhook_secret` can write forged CI/status data (`state`, `description`, `target_url`, `context`) onto a commit belonging to a completely different, unrelated organization's stack. This is a payload-for-one-repository mutating another's commit/stack — directly matching the specified Critical impact category. Because `add_status` triggers `stack.schedule_merges` when the new status is `pending?` or `success?`, an attacker who can enumerate/observe a victim's commit SHA (publicly visible on GitHub) can force a fabricated "success" status onto that commit, potentially unblocking merges or continuous deployment on the victim's stack — an unauthorized deploy trigger. This is repeatable against any known commit SHA, across arbitrary victim stacks/organizations, at no cost beyond having any Shipit-registered org of their own.

### Likelihood Explanation
Preconditions: the attacker needs (1) their own organization already configured in `Shipit.github` (i.e., an org that legitimately has a `webhook_secret`) — realistic for any onboarded, unprivileged customer of a shared Shipit instance — and (2) knowledge of a target commit's SHA, which is not secret (visible in public repos, PR links, commit logs). No Shipit session, API token, or victim's secret is required. This is a low-cost, fully repeatable, unauthenticated-relative-to-victim attack; the only "authentication" needed is of the attacker's own tenant, which is unprivileged and self-service.

### Recommendation
In `StatusHandler#process` (and any other handler doing similar sha-based lookups), scope the `Commit` lookup by the stack(s) belonging to the payload's actual `repository.full_name`/`repository_owner`, e.g. `Stack.where(repository: repo).commits.where(sha: params.sha)`, rather than a bare global `Commit.where(sha: ...)`. More generally, every webhook handler must derive the target `Stack`/`Repository` from the same `repository` object used for signature verification, and reject/no-op if the mutated record's repository does not match.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style, no live GitHub calls):
1. Create `victim_repo = Shipit::Repository.create!(owner: 'victim', name: 'repoB')` (or equivalent) and `victim_stack` under it; create `victim_commit = Commit.create!(stack: victim_stack, sha: 'deadbeef...'40hex)`.
2. Create `attacker_repo`/`attacker_stack` for `owner: 'attacker'`, configure `Shipit.github(organization: 'attacker')` with a known test `webhook_secret`.
3. Build payload: `{ 'repository' => { 'full_name' => 'attacker/repoA', 'owner' => { 'login' => 'attacker' } }, 'sha' => victim_commit.sha, 'state' => 'success', 'context' => 'ci' }`.
4. POST to `/webhooks` with `X-Github-Event: status` header and `X-Hub-Signature` computed as `sha1=` HMAC using attacker's own `webhook_secret` over the raw body.
5. Assert response is `200 OK` (signature verified as attacker/org A).
6. Assert `victim_commit.reload.statuses.last.state == 'success'` and `victim_commit.stack_id == victim_stack.id` — i.e., **the equality `repository_owner (attacker) == owning org of mutated row (victim)` fails**, proving the binding break: the row mutated belongs to `victim_stack`, not any stack under `attacker`'s repository.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
