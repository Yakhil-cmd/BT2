### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but handlers act on the repository named in `repository.full_name`, allowing cross-organization status/deploy forgery in multi-app installs - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
When Shipit is configured with multiple GitHub Apps (one per GitHub organization, as documented in `docs/setup.md` "Using Multiple Github Applications"), `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from the *same, attacker-controlled* JSON body (`repository.owner.login`, or `organization.login`) rather than from any property tied to which secret actually produced the signature. The downstream handlers, however, key off a *different* field of that same body — `repository.full_name` (or, for `StatusHandler`, an unscoped `sha`) — to decide which `Repository`/`Stack`/`Commit` to act on. Because these two fields are never cross-validated against each other, a party who only knows the webhook secret of Organization A can forge a signed payload whose `repository.owner.login` is `"OrgA"` (so it authenticates) while its `repository.full_name` (or `sha`) references Organization B's repository/commit, causing Shipit to act on Org B's data using only Org A's credentials.

### Finding Description
`WebhooksController#verify_signature` resolves the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) purely from request payload content: [2](#0-1) [3](#0-2) 

`Shipit.github(organization:)` looks up per-organization app config keyed by this attacker-supplied string: [4](#0-3) 

This is the documented multi-tenant configuration where each organization has its own `app_id`, `installation_id`, and — critically — its own `webhook_secret`: [5](#0-4) 

Once `verify_signature` passes, `WebhooksController#create` dispatches to handlers using the *entire raw payload*, not just the field that was used for organization/secret selection: [6](#0-5) 

Handlers resolve the affected repository from `repository.full_name`: [7](#0-6) 

used e.g. by `PushHandler`, which triggers a real sync/deploy pipeline for whatever stack matches: [8](#0-7) 

Most severely, `StatusHandler` doesn't even consult `repository.full_name` — it matches globally on `sha` across all repositories/organizations and writes an attacker-supplied CI status onto any matching commit: [1](#0-0) 

The equality this breaks is: **the organization whose secret authenticated the request** (`repository_owner` / `Shipit.github(organization:)`) is assumed to equal **the organization/repository whose data is written** (`repository.full_name`, `sha`). Nothing enforces that `repository.owner.login == repository.full_name.split('/').first`, nor that a commit matched by bare `sha` belongs to the same organization that signed the request.

### Impact Explanation
An attacker who administers (or otherwise knows the `webhook_secret` of) any one GitHub organization configured in a multi-app Shipit install can forge HMAC-valid webhook requests that write arbitrary CI status (`state`, `description`, `target_url`, `context`) onto commits belonging to a *different* organization's stacks, or trigger `GithubSyncJob`/`schedule_refresh_check_runs!` for that other organization's stacks. Since Shipit deploy pipelines commonly gate deploys on commit statuses/checks (`StatusHandler` → `create_status_from_github!`, `CheckSuiteHandler` → `schedule_refresh_check_runs!`), an attacker can inject a fabricated "success" status for a commit in an org they have no access to, potentially satisfying deploy conditions and enabling an unauthorized deploy of that stack — a cross-organization/cross-repository write achieved without ever holding a Shipit session, `ApiClient` token, or credentials for the victim organization. This matches the Critical impact category "cross-repository writes, or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Exploitability only requires: (1) a Shipit install configured with the documented multi-organization GitHub App schema, and (2) the attacker controlling/knowing the `webhook_secret` for any one of the configured organizations (e.g., because they administer that org's own GitHub App, which is a normal, low-privilege position relative to the *other* organizations hosted on the same Shipit instance). The `/webhooks` endpoint is intentionally unauthenticated (no session, no `ApiClient` token) beyond the HMAC check, so once the attacker can compute a valid signature for their own org's secret, they fully control every other field in the JSON body, including `repository.full_name`, `sha`, and `organization.login`.

### Recommendation
Cross-validate the payload after signature verification: require that the organization used to resolve the `GitHubApp`/`webhook_secret` (`repository_owner`) matches the owner encoded in `repository.full_name` (and, for events like `status` that only carry a `sha`, resolve/scope the target commit's stack repository owner before trusting the payload) before invoking any handler. Reject the webhook if these do not match, rather than only checking that the raw body was signed by *some* configured organization's secret.

### Proof of Concept
1. Configure Shipit with two organizations per `docs/setup.md`'s multi-app schema: `OrgA` (attacker-controlled GitHub App, known `webhook_secret_A`) and `OrgB` (victim, `webhook_secret_B`, unknown to attacker), each having existing stacks/commits.
2. Attacker crafts a JSON body for the `status` event:
   ```json
   { "sha": "<sha of a commit in an OrgB stack>", "state": "success", "context": "ci/build",
     "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/some-repo"} }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(webhook_secret_A, body)`.
4. `WebhooksController#verify_signature` computes `repository_owner` → `"OrgA"`, calls `Shipit.github(organization: "OrgA")`, and the signature verifies successfully [9](#0-8) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the OrgB commit regardless of which organization authenticated the request — and calls `commit.create_status_from_github!(params)`, writing a forged "success" status controlled entirely by the attacker onto OrgB's commit [1](#0-0) .
6. If OrgB's stack deploy gating relies on this status/check, the attacker has caused an unauthorized deploy trigger for a stack in an organization for which they hold no credentials.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified
