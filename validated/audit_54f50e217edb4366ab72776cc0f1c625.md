## Analysis: Cross-context replay of `is_valid_signed_package` signed packages in AA oscript

### Title
Unscoped signed-package validation in `is_valid_signed_package` allows a user's signature intended for one purpose/AA to be replayed to authorize unrelated actions in a different AA - (File: `formula/evaluation.js`)

### Summary
The Pterodactyl bug is a purpose-confusion vulnerability: Wings accepts *any* panel-issued JWT that contains the expected claim shape (`server_uuid`, `user_uuid`, `unique_id`), regardless of which endpoint the token was originally minted for, because the token carries no purpose/scope claim. The analogous construct in ocore is the generic "signed package" object (`{version, signed_message, authors, last_ball_unit}`) produced by `signMessage()` in [1](#0-0)  and verified by `validateSignedMessage()` / exposed to oscript via `is_valid_signed_package()` in [2](#0-1) .

### Finding Description
`is_valid_signed_package(signed_package, address)` only proves two facts: (1) `address` produced a valid signature over the exact bytes of `signed_package` (via `objectHash.getSignedPackageHashToSign`), and (2) if `last_ball_unit` is present, that unit was stable at or before the evaluating MCI, per [3](#0-2) . Field validation only rejects unknown top-level keys (`hasFieldsExcept(signedPackage, ['signed_message', 'last_ball_unit', 'authors', 'version'])`) - [4](#0-3) . The actual payload, `signed_message`, is completely free-form and carries **no protocol-enforced purpose/audience/scope field** binding it to a specific AA address, a specific trigger, or a single use.

Because any AA author can write `is_valid_signed_package(trigger.data.signed_package, some_address)` and accept whatever shape of `signed_message` they choose to trust, the framework provides no way to distinguish "a signature the user produced intentionally for AA-A's protocol" from "the same signature blob replayed against AA-B by an unrelated party who merely observed it on-chain, in a chat message, or in another dApp's data." This mirrors the report's root cause precisely: the verifier (Wings/`is_valid_signed_package`) checks only generic, reusable claims (`server_uuid`/pubkey+signature) instead of a claim that is scoped to the specific intended action, letting a credential minted for context A be redeemed in context B.

Concretely: a user may sign a `signed_message` package once (e.g., to authorize a withdrawal amount, confirm a price, or accept a contract term for legitimate AA-A, as shown in the test fixture at [5](#0-4) ). That exact object is visible to anyone who received it (chat message, unit data, AA state, or public trigger data). An unrelated third party can then set up AA-B whose oscript merely calls `is_valid_signed_package($replayed_package, victim_address)` and, since the check only verifies "victim_address signed this blob," AA-B will treat it as a fresh, contextually valid authorization from the victim - even though the victim never intended for that specific message to authorize anything in AA-B.

### Impact Explanation
Any AA author (an unprivileged unit poster who can define and deploy an AA) can build an AA whose payout/state-transition logic is gated by `is_valid_signed_package(trigger.data.signed_package, victim_address)` against a signed_message shape that matches something the victim has already produced for a different legitimate purpose (e.g., an exchange-order signature, a contract acceptance, or any application-level "prove you are `victim_address`" pattern using the standard `signMessage` helper). Triggering that AA with the replayed package can cause AA-controlled funds to be released to the attacker, or state to be corrupted, effectively bypassing the intended one-time/one-context authorization semantics that the original protocol (which produced the signed_message) relied upon. This can lead directly to AA fund loss for victims who rely on `signMessage`-based off-chain/cross-protocol proofs, satisfying the "concrete unauthorized spending / AA fund loss" bar.

### Likelihood Explanation
Exploitability requires: (1) the attacker to observe a `signed_message` package previously produced by the victim (these are commonly shared over chat, embedded in units, or posted as AA trigger data, so they are not secret), and (2) an AA (which the attacker fully controls, since AAs are permissionlessly deployable) written to accept that same message shape. Because `signed_message` content and shape are entirely up to convention rather than enforced by the protocol, and nothing in `is_valid_signed_package` binds the signature to a specific target AA address, trigger, or single use, this is a systemic, framework-level gap rather than a one-off misconfiguration in a specific AA.

### Recommendation
Add protocol-level domain separation to signed packages consumed by `is_valid_signed_package`: require/allow a mandatory `app`/`aa_address` or `purpose` field embedded in the hashed structure (so the signature is only valid for a given consuming AA address), and encourage/document a nonce or single-use enforcement mechanism (e.g., automatically tracking consumed `signed_message` hashes per AA in state vars) so the same signature cannot be replayed across different AAs or multiple times. At minimum, update `formula/evaluation.js`'s `is_valid_signed_package` documentation and `signMessage()` in `signed_message.js` to strongly warn AA/dApp authors that they must embed their own AA address and a nonce inside `signed_message` themselves, since the framework performs no scope binding.

### Proof of Concept
1. Victim uses the standard wallet `signMessage` flow (as in [1](#0-0) ) to sign `{signed_message: {order: 11, pair: "GB/USD", amount: 1.23, price: 42.3}, ...}` for a legitimate exchange AA, and shares the resulting package (as demonstrated by the test object shape in [6](#0-5) ).
2. Attacker copies this exact `signed_package` object.
3. Attacker deploys a malicious AA whose oscript contains `if (is_valid_signed_package(trigger.data.signed_package, 'VICTIM_ADDRESS')) { ... pay out funds / authorize action ... }` with no additional binding of `signed_message` to this specific AA.
4. Attacker sends a trigger to their AA with `data.signed_package` = the victim's replayed package.
5. `is_valid_signed_package` in [7](#0-6)  returns `true` because the signature and address check out, even though the victim never intended to authorize anything on this attacker-controlled AA, allowing the attacker's AA logic to execute as if the victim had approved it.
