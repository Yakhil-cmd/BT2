### Title
Fee-on-Transfer ERC20 Tokens Cause Bridge Reserve Drain via Nominal-Amount Accounting — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` and `onERC20Received` record and relay the caller-supplied `_value` parameter without verifying the actual token amount received by the bridge contract. For fee-on-transfer ERC20 tokens, the bridge receives fewer tokens than `_value` but emits `RequestValueTransfer(_value)`. The counterpart bridge then releases the full nominal `_value` to the recipient, draining its reserves by the fee delta on every cross-chain transfer.

---

### Finding Description

`requestERC20Transfer` pulls `_value + _feeLimit` from the sender and immediately passes the original `_value` to `_requestERC20Transfer`: [1](#0-0) 

No before/after balance check is performed. `_requestERC20Transfer` then emits `RequestValueTransfer` with the unverified `_value`: [2](#0-1) 

The 1-step path `onERC20Received` is equally affected — it forwards whatever `_value` the token contract supplies, again without a balance check: [3](#0-2) 

On the counterpart chain, `handleERC20Transfer` unconditionally releases the full nominal `_value` to the recipient: [4](#0-3) 

For a token with a 1% transfer fee and a transfer of `_value = 100`:

| Step | Expected | Actual (fee-on-transfer) |
|---|---|---|
| Source bridge receives | 100 + feeLimit | (100 + feeLimit) × 0.99 |
| `RequestValueTransfer` emits | 100 | 100 (nominal, unchecked) |
| Destination bridge releases | 100 | 100 |
| Net delta per transfer | 0 | −1 token from dest reserves |

The `_payERC20FeeAndRefundChange` helper in `BridgeFee.sol` also performs `safeTransfer` calls for fee and refund without accounting for the fee-on-transfer deduction, compounding the discrepancy: [5](#0-4) 

---

### Impact Explanation

In **lock/unlock mode** (`modeMintBurn = false`): the destination bridge's liquidity pool is drained by the fee delta on every transfer. After enough transfers, the bridge cannot fulfill legitimate withdrawals — bridged assets are permanently locked on the source chain with no corresponding liquidity on the destination.

In **mint/burn mode** (`modeMintBurn = true`): `burn(_value)` is called on the bridge's balance after `safeTransferFrom` received less than `_value`. If the shortfall is large enough, the burn reverts (insufficient balance), making the bridge non-functional for that token. If it does not revert, the total supply on the destination chain inflates relative to the locked supply on the source chain.

---

### Likelihood Explanation

Any operator who registers a fee-on-transfer ERC20 token (e.g., STA, early USDT with fee mode, or any custom token with a transfer tax) via `registerToken` triggers this path. The bridge has no allowlist enforcement that excludes such tokens. A single registered fee-on-transfer token is sufficient to trigger the drain on every transfer. [6](#0-5) 

---

### Recommendation

1. **Measure actual received amount** in `requestERC20Transfer` using a before/after balance check:
   ```solidity
   uint256 before = IERC20(_tokenAddress).balanceOf(address(this));
   IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
   uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)) - before;
   require(actualReceived >= _value, "fee-on-transfer: insufficient received");
   ```
2. **Emit the actual received amount** (not the caller-supplied `_value`) in `RequestValueTransfer`.
3. **Validate `_value` in `onERC20Received`** against the actual balance change, since the token contract controls the `_value` argument.
4. **Document or enforce** that only standard ERC20 tokens (no fee-on-transfer, no rebasing) may be registered via `registerToken`.

---

### Proof of Concept

1. Deploy a fee-on-transfer ERC20 token (1% fee on every `transfer`/`transferFrom`).
2. Register it on both the parent and child bridge via `registerToken`.
3. Alice calls `requestERC20Transfer(token, Bob, 100, 10)` on the parent bridge.
   - Bridge pulls 110 tokens; receives 108.9 (1% fee).
   - Fee/refund transfers further reduce bridge balance.
   - `RequestValueTransfer` emits `valueOrTokenId = 100`.
4. Bridge operators call `handleERC20Transfer(..., 100, ...)` on the child bridge.
   - Child bridge calls `safeTransfer(Bob, 100)`.
   - Bob receives 99 tokens; child bridge loses 100 from reserves.
5. Repeat: each round-trip drains the child bridge by ~1 token while the parent bridge locked ~98.9 tokens.
6. After enough transfers, `handleERC20Transfer` reverts with insufficient balance — all pending withdrawals are permanently stuck. [7](#0-6) [8](#0-7)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
