## Title
Multisig `transaction_context::multisig_payload()` reflects unvalidated inline payload, diverging from actual executed/approved payload when `abort_if_multisig_payload_mismatch` is disabled - (File: `aptos-move/framework/aptos-framework/sources/transaction_context.move`)

### Summary
`transaction_context::multisig_payload()`/`inner_entry_function_payload()` are populated from `TransactionMetadata.multisig_payload`, which is built directly from the raw `SignedTransaction`'s inline payload — not from the on-chain-stored, owner-approved payload, and not from the value returned by `multisig_account::get_next_transaction_payload` that actually gets executed. When `features::abort_if_multisig_payload_mismatch_enabled()` is disabled, `multisig_account::validate_multisig_transaction` does not enforce that an owner-supplied inline payload matches the stored payload, so a divergent inline payload can pass prologue validation while the exposed transaction-context payload continues to reflect the attacker/owner-supplied (unapproved) content rather than what owners actually approved or what gets executed.

### Finding Description
`TransactionMetadata::new` sets the `multisig_payload` field straight from `txn.payload()` (the caller-supplied `SignedTransaction`), independent of what is stored on-chain for the multisig transaction: [1](#0-0) 

This field is exposed via `as_user_transaction_context()`, which is what backs the native `multisig_payload_internal()` used by Move's `transaction_context::multisig_payload()`: [2](#0-1) [3](#0-2) [4](#0-3) 

Separately, `multisig_account::validate_multisig_transaction` is the prologue check invoked by the VM with the executing owner's `provided_payload` (built from the executable in the transaction) and the multisig account address: [5](#0-4) 

Critically, the payload-equality check is gated behind the `abort_if_multisig_payload_mismatch_enabled()` feature flag: [6](#0-5) [7](#0-6) 

When this feature is disabled, an owner submitting a transaction with an inline payload that diverges from `transaction.payload` (the one owners actually approved when creating/voting on the multisig transaction) is **not rejected** by `validate_multisig_transaction`. The VM's `execute_multisig_transaction` then calls into `get_next_transaction_payload` (Move-side, in `multisig_account.move`) to determine what actually executes — this function is separate from the value already captured in `TransactionMetadata.multisig_payload` used by `transaction_context`. Meanwhile, `transaction_context::multisig_payload()` was already fixed at metadata-construction time from the raw transaction's inline payload, so any Move code that queries `transaction_context::multisig_payload()`/`inner_entry_function_payload()` during execution observes the caller-supplied inline content, not necessarily the payload owners voted/approved on-chain, and not necessarily the payload that is ultimately executed by `get_next_transaction_payload`.

This creates a scenario where the value observable through the transaction-context API can diverge from (a) the owner-approved stored payload, and (b) the value chosen for actual execution — undermining any Move module logic that relies on `transaction_context::multisig_payload()` as an authoritative reflection of what owners approved, whenever `abort_if_multisig_payload_mismatch` is off.

### Impact Explanation
This affects transaction-context integrity for multisig execution: any downstream Move logic (e.g., custom modules gating behavior on `transaction_context::multisig_payload()`) can be shown content that owners did not approve, while the feature-flag intended to guarantee this invariant (`abort_if_multisig_payload_mismatch`) is off by default on some networks/at some point in time. This is a genuine violation of the "observable payload equals approved payload" invariant described in the question, but it is gated entirely behind an *already-known, intentionally staged* feature flag (`ABORT_IF_MULTISIG_PAYLOAD_MISMATCH`, id 70) — the code and its comments show this is a documented, tracked "fix" (`"Whether the multisig v2 fix is enabled..."`) rather than a silent unknown flaw: [8](#0-7) 

The actual entry-function/script that gets executed is still resolved through `get_next_transaction_payload` and `execute_multisig_transaction`, which independently determine execution content from on-chain state — I was not able to fully confirm within the available tool budget whether `get_next_transaction_payload` always prefers the stored payload over the provided one in all code paths (I saw only its call site, not its full body). This is a material gap: if `get_next_transaction_payload` always uses the stored payload for execution when one exists, then actual execution semantics remain correct/approved, and the vulnerability is scoped strictly to the `transaction_context` observability API (an information/consistency issue for Move code reading the context, not a direct fund-loss/authorization-bypass at the execution layer).

### Likelihood Explanation
Requires: `multisig_v2_enhancement` enabled, `abort_if_multisig_payload_mismatch` disabled (a real historical/possible network state, as it's a distinct, separately-gated feature flag), a multisig transaction created with a stored payload, and the executing owner supplying a different inline payload at execution time — all achievable by an unprivileged multisig owner. The precondition (mismatch-abort flag disabled) is plausible on networks that haven't activated feature 70 yet.

### Recommendation
- Since I could not fully verify whether `get_next_transaction_payload`'s actual execution content path prefers the stored payload unconditionally, a background engineering session should read the full body of `get_next_transaction_payload` in `aptos-move/framework/aptos-framework/sources/multisig_account.move` to confirm execution semantics are unaffected.
- Regardless, consider making `transaction_context::multisig_payload()` always populate from the value actually used for execution (post `get_next_transaction_payload` resolution) rather than from the raw inline transaction payload in `TransactionMetadata::new`, so the two never diverge irrespective of the `abort_if_multisig_payload_mismatch` flag state.

### Proof of Concept
Not able to be fully constructed/verified in this review: an e2e test would need to (1) disable `abort_if_multisig_payload_mismatch`, (2) create a multisig transaction with a stored payload P1, (3) execute with inline payload P2 ≠ P1, (4) assert that `transaction_context::multisig_payload()` (as observed by a test module) shows P2 while the transaction, if it executes, either executes P1 (confirming context/execution divergence) or is rejected. I did not have tool budget remaining to write/run this test or confirm `get_next_transaction_payload`'s full body, so the execution-side severity (whether unapproved *content* actually executes, versus only being *observable* via transaction_context) remains unconfirmed.

fn native_multisig_payload_internal(
    context: &mut SafeNativeContext,
    _ty_args: &[Type],
    _args: VecDeque<Value>,
) -> SafeNativeResult<SmallVec<[Value; 1]>> {
    context.charge(TRANSACTION_CONTEXT_MULTISIG_PAYLOAD_BASE)?;

    let user_transaction_context_opt = get_user_transaction_context_opt_from_context(context);
    let enum_option_enabled = context.get_feature_flags().is_enum_option_enabled();
    if let Some(transaction_context) = user_transaction_context_opt {
        if let Some(multisig_payload) = transaction_context.multisig_payload() {
            let inner_entry_fun_payload =
                if let Some(entry_function_payload) = multisig_payload.entry_function_payload {
                    let num_bytes = num_bytes_from_entry_function_payload(&entry_function_payload);
                    context.charge(
                        TRANSACTION_CONTEXT_MULTISIG_PAYLOAD_PER_BYTE_IN_STR
                            * NumBytes::new(num_bytes as u64),
                    )?;
                    let inner_entry_fun_payload =
                        create_entry_function_payload(entry_function_payload)?;
                    create_option_some(enum_option_enabled, inner_entry_fun_payload)?
                } else {
                    create_option_none(enum_option_enabled)?
                };
            let multisig_payload = Value::struct_(Struct::pack(vec![
                Value::address(multisig_payload.multisig_address),
                inner_entry_fun_payload,
            ]));
            Ok(smallvec![create_option_some(
                enum_option_enabled,
                multisig_payload
            )?])
        } else {
            Ok(smallvec![create_option_none(enum_option_enabled)?])
        }
    } else {
        Err(SafeNativeError::abort_with_message(
            error::invalid_state(abort_codes::ETRANSACTION_CONTEXT_NOT_AVAILABLE),
            "Transaction context is not available (multisig payload can only be accessed during transaction execution)",
        ))
    }
}

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );

        // If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
    }
