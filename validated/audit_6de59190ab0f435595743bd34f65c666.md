This is a legitimate finding confirmed by the code. The claim accurately describes the code behavior as documented.### Title
Unauthenticated webhook processing when `webhook_secret` is not configured - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever `@webhook_secret` is blank, meaning any Shipit installation configured without a `webhook_secret` accepts and processes any `POST /webhooks` request regardless of the `X-Hub-Signature` header. `WebhooksController#create` then dispatches the unauthenticated payload straight into `Shipit::Webhooks.for_event(event).each(&:call)(params)`, causing side effects (e.g. commit creation, sync jobs, team/membership mutation) driven entirely by attacker-supplied JSON.

### Finding Description
The broken binding is: `request-authenticated == request-processed`. `WebhooksController#create` should only invoke handlers when the webhook signature is verified, but `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) only calls `head(422)` when `verified` is false — it does not halt the filter chain (no `and return` / no `throw(:abort)`), and critically, `verify_webhook_signature` itself returns `true` when no secret is configured:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [1](#0-0) 

`@webhook_secret` is set via `@config[:webhook_secret].presence` at initialize time [2](#0-1) , so any organization config lacking a `webhook_secret` key produces `nil`, and `verify_webhook_signature` becomes a no-op that always returns `true`, irrespective of whether `X-Hub-Signature` is present, malformed, or entirely absent.

Attacker flow: send `POST /webhooks` with `X-Github-Event` set to a handled event (e.g. `push`) and a JSON body describing an existing `repository.owner.login` mapping to an org with no `webhook_secret` configured, and omit `X-Hub-Signature` entirely. `check_if_ping` passes (not ping), `drop_unhandled_event` passes (handler exists for `push`), `verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` [3](#0-2)  and calls `verify_webhook_signature(nil, raw_post)`, which short-circuits to `true` because `webhook_secret` is `nil`. Then `create` executes `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3)  with fully attacker-controlled `params`.

No other guard intervenes: `drop_unhandled_event` only filters by event name, not by authenticity; there is no `ExplicitParameters` schema validation on this controller filtering the payload's authenticity; and `force_github_authentication`/`User#authorized?`/`require_permission!` are irrelevant to this unauthenticated, session-less controller.

### Impact Explanation
Once a target Shipit deployment has an organization configured without `webhook_secret`, any internet user can trigger arbitrary handled webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) for that organization's repositories with a forged payload, causing state-changing side effects such as `GithubSyncJob` enqueuing, `Commit`/`Status` creation, or `Team`/`Membership` mutation — all attributed to a webhook that was never actually sent by GitHub. This is a full authentication bypass of the webhook trust boundary for that organization, matching the "Critical - authentication bypass (forged webhook ... accepted)" category. The blast radius is scoped to organizations/tenants whose config omits `webhook_secret`; organizations with a properly configured secret are not affected since `SecureCompare.secure_compare` is enforced in that branch.

### Likelihood Explanation
This requires no attacker capability beyond sending HTTP requests to the public `/webhooks` endpoint (which is designed to be unauthenticated at the network layer, relying solely on the signature). The only precondition is operational: the specific Shipit organization config must omit `webhook_secret` (a misconfiguration, not a code defect that inherently affects all deployments, but the class itself provides no safeguard, warning, or fail-closed default against it). Given that, exploitation cost is trivial and fully repeatable against any repository under that mis-configured organization.

### Recommendation
Change `GitHubApp#verify_webhook_signature` to fail closed: if `webhook_secret` is blank, treat every request as unverified (return `false`) rather than `true`, or raise/log a configuration error at boot/initialize time requiring `webhook_secret` to be present. Additionally, `WebhooksController#verify_signature` should `head(422) and return` (or use `throw(:abort)`) explicitly rather than continuing to `create` — though this is secondary once the `GitHubApp` fail-open default is fixed.
