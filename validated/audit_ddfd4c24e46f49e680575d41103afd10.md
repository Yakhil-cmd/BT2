### Title
Webhook Signature Bypass via Missing `webhook_secret` on One Org Grants Unauthenticated Write Access to Any Tracked Repository - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration to validate a webhook against using an **unverified** field taken straight from the JSON body (`repository.owner.login`), and `GitHubApp#verify_webhook_signature` unconditionally accepts any payload when that org's `webhook_secret` is blank. Because the org used for signature verification and the repository actually acted upon by the event handlers are two independently-controlled fields in the same untrusted payload, an attacker can pick an org with no configured secret to pass verification while pointing the rest of the payload at a completely different, secret-protected repository that Shipit tracks.

### Finding Description
`before_action :check_if_ping, :drop_unhandled_event, :verify_signature` runs before `create`. `verify_signature` does:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read directly from the JSON body before any signature check is performed — it is entirely attacker-controlled. `Shipit.github(organization:)` looks up that org's configured `GitHubApp` and `verify_webhook_signature` is:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

If **any** configured organization has a blank `webhook_secret` (a documented and supported configuration — see the multi-org example in `docs/setup.md` and the shipped fixture `config/secrets.development.shopify.yml` which sets `webhook_secret: # nil` for both sample orgs), then setting `repository.owner.login` to that org's name makes `verify_signature` always pass, regardless of the actual `X-Hub-Signature` header or the true payload origin.

Once past `verify_signature`, the actual event handlers resolve the target Stack/Repository using a **different** field of the same payload: `repository.full_name`, e.g.

```ruby
def repository
  @repository ||=
    Shipit::Repository
    .from_github_repo_name(params.repository.full_name) || NullRepository.new
end
``` [3](#0-2) 

and `PushHandler`/status handlers likewise select stacks by branch/repository derived from the body, not from `repository_owner`: [4](#0-3) 

This is the equality the deployment trust model is supposed to enforce and which is broken here: **organization authenticated (`repository.owner.login`, checked against a per-org `webhook_secret`) ≠ repository acted upon (`repository.full_name`, used by every handler to locate the Stack/Repository/PullRequest to mutate)**. Nothing ties these two payload fields together or re-validates that `full_name`'s owner matches the org whose secret was checked.

### Impact Explanation
With multi-org configuration (explicitly documented/supported, `docs/setup.md:182-209`) and any single org left without a `webhook_secret`, an unauthenticated attacker can forge `push`, `status`, `check_suite`, `pull_request`, or `membership` webhook events for **any other organization's tracked repository**, bypassing the HMAC signature entirely. This lets an attacker:
- Trigger `GithubSyncJob`/`sync_github` for arbitrary stacks with a forged `expected_head_sha`, influencing which commit is considered "head" and eligible for deploy.
- Forge `status` events to mark arbitrary commits as CI-passing (`Status` records), enabling deploy of a commit that never actually passed CI (an unauthorized ship path).
- Forge `pull_request`/`membership` events to manipulate merge-queue state, labels, or team membership records used for authorization (`Shipit.github_teams` checks in `Authentication`).

This satisfies the "High" bar (escalation into `Shipit.github_teams` authorization, or state manipulation feeding into deploy decisions) and can reach the "Critical" bar (unauthorized deploy) via the forged CI-status path, since deploys/continuous delivery gate on `Commit#statuses`, which webhooks populate without further authorization checks.

### Likelihood Explanation
Requires the deployment to configure more than one GitHub organization (a supported, documented feature) with at least one org lacking a `webhook_secret` — a realistic and easy-to-make misconfiguration, and one the project's own sample config (`config/secrets.development.shopify.yml`) demonstrates by leaving `webhook_secret` nil for multiple orgs. No credentials, tokens, or prior access are required — only knowledge of the org name lacking a secret (discoverable via a probe payload since a wrong org yields 422 `GithubOrganizationUnknown` vs. a right-but-secretless org yields 200/204).

### Recommendation
Do not let an unverified payload field determine which secret is used to verify the payload, and never treat "no secret configured" as automatically-verified for cross-organization traffic:
- Require every configured GitHub organization to have a non-blank `webhook_secret` in production (fail closed instead of `return true unless webhook_secret`), or
- Cryptographically bind the verified organization to the repository actually processed: after selecting `github_app` for `repository_owner`, reject the event unless `repository.full_name`'s owner also equals `repository_owner`, and reject if the resolved `Stack`/`Repository`'s configured/expected organization differs from the one whose secret validated the request.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `org-a` (no `webhook_secret` set) and `org-b` (real `webhook_secret`, tracks `org-b/secret-repo`).
2. POST to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/secret-repo"
  }
}
```
No valid `X-Hub-Signature` is required, since `Shipit.github(organization: "org-a").verify_webhook_signature` returns `true` (blank secret) per `lib/shipit/github_app.rb:76-83`. The `status` handler resolves the commit/stack via `repository.full_name` = `org-b/secret-repo` [5](#0-4) , forging a passing CI status for `org-b`'s repository without ever presenting `org-b`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

          params.ref.gsub('refs/heads/', '')
        end
