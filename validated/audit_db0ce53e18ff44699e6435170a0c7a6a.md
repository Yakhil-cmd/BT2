### Title
Unbounded submodule recursion in `configureWorktree()` allows attacker-pushed commits to force persistent sync-timeout / crash-loop denial - (File: main.go)

### Summary
`configureWorktree()` unconditionally runs `git submodule update --init --recursive` (when `--submodules` is not `off`) against whatever `.gitmodules` content is present in the fetched commit, with no bound on the number or nesting depth of submodule entries. This is directly analogous to the OpenQ `H-7` bug class: an unbounded, attacker-influenced collection (there, the deposit list; here, the submodule graph) is iterated inside a single operation whose cost scales with attacker-controlled input, and once that operation exceeds the enforced resource budget (`--sync-timeout` instead of the block gas limit), the overall workflow (refunds there, sync there) is denied.

### Finding Description
In the sync loop, each pass calls `SyncRepo()` → `configureWorktree()`: [1](#0-0) 

`git.submodules` defaults to recursive per the documented flag, and there is no cap on the number of `[submodule ...]` stanzas in `.gitmodules`, nor on recursion depth, before invoking `git submodule update --init --recursive`. Anyone with push access to the synced upstream repository (the same "attacker-pushed commit" threat model used to reach git-sync) can commit a `.gitmodules` file referencing thousands of submodules (or deeply/circularly nested submodule chains across multiple repos), each of which requires its own network fetch/clone during this single call.

The entire sync attempt is bounded only by a single `context.WithTimeout(ctx, *flSyncTimeout)` wrapping the whole `SyncRepo` call: [2](#0-1) 

and the underlying git process is invoked with `exec.CommandContext(ctx, ...)`: [3](#0-2) 

When the submodule graph is large enough to exceed `--sync-timeout`, the context deadline kills the git process, `SyncRepo` returns an error, and `failCount` increments. Once `failCount` reaches `--max-failures`, the process calls `os.Exit(1)`: [4](#0-3) 

Because the failing commit remains at the head of the tracked ref, every subsequent restart (e.g. under a Kubernetes restart policy) will re-fetch the same oversized submodule set, time out again, and re-exit — a persistent denial of sync analogous to funds being permanently locked by the unbounded-loop OOG in `DepositManager.refundDeposit()`.

### Impact Explanation
This causes **persistent sync denial**: the sidecar can be driven into a permanent crash-loop (or an indefinitely stuck "in progress" state per attempt) by a single attacker-controlled commit, with no automatic recovery, because the offending ref stays at the head and each sync attempt repeats the same expensive/failing operation. This blocks legitimate updates for the consumer container relying on `--link`, matching the "persistent sync denial" impact category.

### Likelihood Explanation
Likelihood is moderate and conditioned on the threat model explicitly permitted here (attacker-pushed commit to the synced repo, e.g. an untrusted contributor, compromised upstream, or a repo that accepts PR-triggered mirroring). No git-sync flag currently bounds the number of submodules or recursion breadth (only `--depth` bounds per-repo history depth, and `--submodules=off` disables the feature entirely but is not the default). Default `--submodules` is recursive, so any deployment using default settings against an untrusted upstream is exposed. I was unable to verify from the available context whether git itself imposes any internal ceiling on submodule count/parallelism that would further bound worst-case cost, so the severity depends on how aggressively `--sync-timeout` and `--max-failures` are tuned by the operator.

### Recommendation
- Add an explicit limit (flag-configurable) on the number of submodules processed by `configureWorktree`, or refuse/skip submodule update when `.gitmodules` entry count exceeds a safe threshold, logging and treating it as a fatal-but-recoverable condition rather than a silent timeout loop.
- Consider capping recursive submodule depth independent of `--depth` (which only limits git history depth, not submodule fan-out).
- On repeated `context.DeadlineExceeded` failures tied to the same commit hash, avoid an unconditional retry of the identical operation (e.g., skip submodule init or mark the ref as bad) instead of relying purely on `--max-failures` → process exit → external restart, which reproduces the same failure.

### Proof of Concept
1. Attacker (or any contributor with push rights to the tracked branch) commits a `.gitmodules` file referencing a very large number of submodule URLs (e.g., thousands of small `file://` or `https://` repos), or a submodule chain with `submodule.<name>.update = ... --recursive` fan-out across many nested submodules.
2. Deploy `git-sync` with default `--submodules=recursive` and a modest `--sync-timeout` (e.g., the documented default of 120s) against this repo.
3. On the next fetch, `SyncRepo()` detects the new commit and calls `configureWorktree()`, which runs `git submodule update --init --recursive` over the full submodule set: [1](#0-0) 
4. If the submodule set is sized so that cloning it exceeds `--sync-timeout`, `git.Run` returns a `context.DeadlineExceeded` error, `failCount` increments, and once it reaches `--max-failures`, `os.Exit(1)` is invoked: [2](#0-1) 
5. On restart, the same commit is still HEAD, so the process repeats steps 3–4 indefinitely, producing a persistent sync-denial/crash loop until an operator manually intervenes (e.g., changing `--ref`, disabling submodules, or removing the offending commit from history).
