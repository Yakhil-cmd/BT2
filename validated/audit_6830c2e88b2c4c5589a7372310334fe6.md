Confirmed. `Shipit::Api::StacksController#stack` and other API controllers scope through `stacks.from_param!` (which is filtered by `current_api_client.stack_id` when the token is stack-scoped), but `Shipit::Api::CCMenuController#stack` at [1](#0-0)  calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, bypassing the `stacks` scoping helper entirely.

### Title
Stack-scoped API token can read any stack's CI status via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with a `stack_id`, e.g. via the CCMenu URL flow) may only touch the single stack it was authorized for, by routing all stack lookups through the `stacks` helper: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [2](#0-1) . `CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` model instead of `stacks.from_param!`, so the `require_permission :read, :stack` check only verifies the token carries the generic `read:stack` permission string, never that the requested `stack_id` matches the stack the token was minted for [3](#0-2) .

### Finding Description
This is the same class of bug as the reported `_getRoyaltyPercentage` issue: a value that is supposed to be validated/bound to a specific authorized context (royalty percentage bound to `salePrice`; here, a stack ID bound to the token's `stack_id`) is instead used raw, breaking the equality `token.authorized_stack == stack_accessed`.

- `ApiClient#stack_id` is meant to restrict a token to one stack, as used by `CCMenuUrlController#client`, which creates a `read:stack`-only, stack-scoped client: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` bound to `stack.id` [4](#0-3) .
- The intended enforcement lives in `BaseController#stacks`/`#stack`, which every other API controller (e.g. `Api::StacksController#stack` at [5](#0-4) ) relies on to filter by `current_api_client.stack_id`.
- `CCMenuController` instead defines its own `stack` using `Stack.from_param!(params[:stack_id])`, completely ignoring `current_api_client.stack_id` [1](#0-0) .
- `check_permissions!` only checks the permission string is present, not the target object: `required_permission = "#{operation}:#{scope}"; unless permissions.include?(required_permission) ... end` [6](#0-5) .

As a result, any stack-scoped, `read:stack`-only CCMenu token (which any authenticated Shipit user can mint for any stack they can view, via `GET /stacks/:stack_id/ccmenu_url`) can be replayed against `/api/stacks/:stack_id/ccmenu.xml` with an arbitrary `stack_id` for a different, unrelated stack, and it will succeed because the scoping check is skipped.

### Impact Explanation
This meets the High-impact bar of "escalation into unauthenticated/unauthorized read of stack state" — a token deliberately minted to expose CI/deploy status for one stack only can be used to read `lastBuildStatus`, `lastBuildLabel` (last deploy id), `activity` (Building/Sleeping), and lock status of any other stack in the instance, as rendered by `app/views/shipit/ccmenu/project.xml.builder`. This crosses a repository/stack authorization boundary the token system is explicitly designed to enforce.

### Likelihood Explanation
Likelihood is high given ease of exploitation: no special privilege is needed beyond having minted (or obtained) any single stack-scoped CCMenu token — trivial for any authenticated user of the Shipit instance, and the request only requires swapping the `stack_id` path/query parameter.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped `stacks` helper from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so stack-scoped tokens cannot be replayed against stacks outside their authorized scope.

### Proof of Concept
1. As an authenticated Shipit user with access to Stack A, visit `GET /stacks/:stackA_id/ccmenu_url` to obtain a stack-scoped, `read:stack`-only token via `CCMenuUrlController#fetch` [7](#0-6) .
2. Note the returned `ccmenu_url` contains `?token=<TOKEN>` bound to Stack A's `id` as `ApiClient#stack_id`.
3. Send `GET /api/stacks/:stackB_id/ccmenu.xml?token=<TOKEN>` for an unrelated Stack B that the token was never authorized for.
4. Observe the request succeeds (200 OK) and returns Stack B's `lastBuildStatus`, `lastBuildLabel`, `activity`, and `webUrl`, because `CCMenuController#stack` looked up `Stack.from_param!(params[:stack_id])` directly rather than through `current_api_client`-scoped `stacks`.
