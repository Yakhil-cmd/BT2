### Title
Rounding Errors in Headers-Commission Share Distribution Enable Byte Supply Inflation - (File: `headers_commission.js`)

### Summary
`calcHeadersCommissions()` splits a parent unit's `headers_commission` among multiple `earned_headers_commission_recipients` using plain floating-point `Math.round()` per recipient instead of an amount-conserving integer split. Because every recipient's share is rounded independently, the sum of the rounded amounts can exceed the actual `headers_commission` that was paid/burned by the payer unit, creating extra spendable "headers_commission" balance that is not backed by any corresponding byte deduction.

### Finding Description
The distribution logic computes each recipient's cut like this: [1](#0-0) 

and, on the SQL-verification path, the same rounding is repeated per recipient: [2](#0-1) 

`earned_headers_commission_recipients` (and their `earned_headers_commission_share` percentages) are fields freely chosen by the unit's author and are only lightly structurally validated in `validation.js`/`writer.js`; there is no FullMath-style "round the last recipient down to make the total add up" mechanism. Each recipient's payout is computed as `Math.round(full_amount * share / 100.0)` independently, so:

- With `full_amount = 150` and `share = 1` split across 100 recipients (1% each), each recipient computes `Math.round(1.5) = 2` (JS rounds `.5` up), so the total distributed is `100 * 2 = 200` bytes, i.e. `50` bytes more than the `150` bytes the payer unit actually committed as its `headers_commission`.
- This is directly analogous to the reported Sherlock issue: a rate/percentage split performed with naive rounding instead of a precision-preserving, amount-conserving method (e.g. `FullMath.mulDivRoundingUp` combined with "last recipient gets the remainder" logic), causing the sum of parts to diverge from the whole.

The resulting rows are inserted into `headers_commission_contributions`, which later become spendable "headers_commission"-type MC inputs via `addHeadersCommissionInputs()`/`addMcInputs()`: [3](#0-2) 

Since these inputs are treated by validation as legitimate spendable earnings tied to `main_chain_index` ranges, any surplus credited here becomes real spendable bytes with no matching debit elsewhere in the DAG, breaking the byte-conservation invariant that the total supply is fixed.

### Impact Explanation
An attacker who authors ordinary units (nothing privileged required) can set `earned_headers_commission_recipients` to many small-share addresses under their own control so that each individual `Math.round()` computation rounds up. Repeating this pattern across the units the attacker authors that end up winning headers commissions allows systematically extracting more bytes than were ever paid by the corresponding payer units — a concrete, unbounded (given enough repetitions) supply-inflation bug, not merely a "dust" rounding nuisance. This matches the "concrete supply inflation" bar required for a valid finding.

### Likelihood Explanation
Likelihood is high for an economically motivated actor: authoring units and setting `earned_headers_commission_recipients`/shares is entirely permissionless and requires no special role (any address that becomes a "child unit" author eligible for headers commission can specify this field). The only constraint is winning the headers-commission lottery for a parent unit, which happens routinely on the network, so the attack can be repeated at scale over time to compound gains, exactly as described in the referenced report ("small losses/gains compounding over time").

### Recommendation
Replace the independent `Math.round()` calls with an amount-conserving distribution:
- Compute each recipient's share using integer arithmetic (e.g. round down, `Math.floor`, for all recipients except the last).
- Assign the last recipient (or a designated "remainder" recipient) `full_amount - sum(previous rounded amounts)` so that the total distributed always equals `full_amount` exactly.
- Apply the same fix consistently to both the in-RAM path and the SQL-verified path in `headers_commission.js` (lines ~176-188 and ~192-206) so they remain identical, and audit `storage.js`'s analogous `Math.floor(total_tps_fees_delta * share / 100)` splitting in `updateTpsFees` for the same conservation property.

### Proof of Concept
1. Attacker controls addresses A1..A100 and posts a unit that becomes the winning child of a parent unit whose `headers_commission` (`full_amount`) is 150 bytes.
2. The unit sets `earned_headers_commission_recipients` = 100 entries, each `{address: Ai, earned_headers_commission_share: 1}`.
3. In `calcHeadersCommissions()`, for each recipient: `amount = Math.round(150 * 1 / 100.0) = Math.round(1.5) = 2`.
4. Total inserted into `headers_commission_contributions` = `100 * 2 = 200` bytes, versus the `150` bytes actually paid by the parent unit — a `50`-byte surplus created from nothing.
5. Each `Ai` can later spend its `2`-byte "headers_commission" input via `addHeadersCommissionInputs()`/`addMcInputs()` in `inputs.js`, turning the surplus into real, spendable bytes, violating total supply conservation. Repeating this across many won headers commissions compounds the inflation.
