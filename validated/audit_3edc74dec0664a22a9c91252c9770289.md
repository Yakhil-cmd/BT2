### Title
Webhook signature verification authenticates the GitHub organization while a different field (`repository.full_name`) is used to select the target Stack, allowing cross-organization sync/deploy triggers - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
This is the same bug class as the Oraclize report: a piece of attacker-controlled data (a "name") is trusted and used to select a resource/action in one place, while a *different* attacker-controlled field is what actually gets acted upon downstream, and nothing forces the two to be consistent. In Shipit's webhook pipeline, `WebhooksController#verify_signature` picks *which* GitHub App/secret to validate the incoming signature against using `repository.owner.login` (or `organization.login`), but the handlers invoked in `create` operate on the full parsed JSON body, including `repository.full_name`, to decide which `Stack`/repository is updated. These two fields are never checked for consistency.

### Finding Description
`WebhooksController` determines which organization's webhook secret to use for HMAC verification via: [1](#0-0) 

and then verifies the signature over the *entire* raw body using that organization's secret: [2](#0-1) 

Once verification passes, `create` dispatches the *entire parsed payload* (not just the `repository_owner` field) to the registered handlers for the event: [3](#0-2) 

The push-event flow enqueues a `GithubSyncJob` keyed off the `repository` in the body — e.g. the test asserts a job is enqueued with `stack_id: @stack.id` derived from the payload's `repository` (its `full_name`), completely independent of which organization's secret validated the request: [4](#0-3) 

In other words, `repository.owner.login` (used to select and authenticate against a webhook secret) and `repository.full_name` (used by the handler to pick which local `Stack` to write to) are two independent fields inside the same signed body. On a Shipit instance configured to serve multiple GitHub organizations (each with its own GitHub App/webhook secret, as documented for `Shipit.github(organization:)`), an operator who legitimately owns one organization's GitHub App can freely choose that org's `webhook_secret` value and can craft an arbitrary raw POST body (since HMAC only proves the body wasn't tampered with by a third party, not that its *fields are self-consistent*). By setting `repository.owner.login` to their own organization (so `verify_signature` selects and validates against a secret they know) while setting `repository.full_name` to a different, victim organization's tracked repository, the request passes signature verification yet the push handler acts on the victim stack — triggering `GithubSyncJob`/commit ingestion, and depending on `continuous_deployment` settings, cross-repository state changes for a repository the attacker does not own.

This is the same root cause pattern the analog report highlights: no sanitization/consistency binding between the field used to authenticate a request and the field the code actually acts on when constructing/selecting a target.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" boundary explicitly called out in the rules. It can force Shipit to record/sync commits, statuses, or check-runs (and with `continuous_deployment` enabled, trigger deploys) for a repository/stack belonging to a different organization than the one whose credentials actually authenticated the request — an unauthorized cross-repository write/deploy trigger.

### Likelihood Explanation
Exploitability requires the deploying organization to run a multi-tenant Shipit instance backing multiple GitHub Apps/organizations (a configuration the engine explicitly supports via `Shipit.github(organization:)` and documented in `config/secrets.yml`). An attacker only needs control of one such organization's GitHub App (i.e., knowledge of its own `webhook_secret`, which they control when creating their own App) to forge a raw webhook body naming a different organization's repository. No Shipit session, API token, or GitHub write access to the victim repository is required — only the ability to POST to the public `/webhooks` endpoint with a self-signed body.

### Recommendation
- Short term: In `WebhooksController#verify_signature`/`create`, ensure the field used to select the verifying GitHub App/secret (`repository.owner.login` / `organization.login`) is the *same* field subsequently used by every handler to resolve the target `Stack`/repository; reject the payload if `repository.full_name`'s owner does not match `repository_owner`.
- Long term: Bind webhook secrets to the specific repository/stack they're associated with (not just organization-level), and validate that every handler resolves its target strictly from data that was covered by the exact same authenticated identity used in signature verification.

### Proof of Concept
1. Shipit instance configured with two GitHub Apps, one for `attacker-org` (secret known to the attacker who created it) and one for `victim-org` (tracks `victim-org/victim-repo` as a Shipit `Stack`).
2. Attacker crafts a JSON body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "after": "<attacker-chosen sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s secret, and the HMAC matches → request passes [2](#0-1) .
5. `create` dispatches the full body to the push handler, which reads `repository.full_name` ("victim-org/victim-repo") to enqueue `GithubSyncJob` against the victim's `Stack` [3](#0-2) , causing Shipit to ingest attacker-controlled commit/state data for a repository the attacker never authenticated against.
