Based on my investigation, I found a plausible admission-boundary flaw in the multisig transaction validation flow, though I was unable to fully verify two details before running out of tool calls (noted below).

### Title
Multisig payload-mismatch check is feature-gated, allowing approved-payload substitution — ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`validate_multisig_transaction`, the Move prologue function invoked by the VM both during mempool validation and at the start of transaction execution, is supposed to guarantee that the payload actually executed for a multisig transaction is the same payload that owners voted to approve. For transactions created via the "full payload stored on-chain" path (as opposed to the "hash-only" path), this guarantee is only enforced when the on-chain feature flag `abort_if_multisig_payload_mismatch_enabled` is turned on.

### Finding Description
In `aptos-move/framework/aptos-framework/sources/multisig_account.move`, `validate_multisig_transaction` performs two different types of provided-payload checks: [1](#0-0) 

- If the transaction was created with only a `payload_hash` stored on-chain, the hash of the `payload` supplied at execution time is always checked (`sha3_256(payload) == *payload_hash`), regardless of feature flags.
- If the transaction was created with the **full payload** stored on-chain (`transaction.payload`), the match between the supplied `payload` and the stored `transaction.payload` is only asserted when `features::abort_if_multisig_payload_mismatch_enabled()` is true.

If that feature is not enabled, an owner who has accumulated the required number of approvals for a multisig transaction can execute it while substituting a **different, unapproved payload** (a different entry function or different arguments) at the transaction-submission boundary, because the on-chain approval count is bound only to the sequence number, not to the actual bytes that get executed in that code path.

The actually-executed payload is selected in `execute_multisig_transaction` in `aptos-move/aptos-vm/src/aptos_vm.rs`, which forwards the submitter-supplied `provided_payload` (built from the transaction's own executable, e.g. an `EntryFunction`) into the Move function `get_next_transaction_payload`: [2](#0-1) 

I was not able to fully inspect `get_next_transaction_payload`'s implementation in the time available to confirm precisely how it reconciles `provided_payload` with the stored `transaction.payload` when both are non-empty and the mismatch-check feature is disabled — this is the key remaining uncertainty.

### Impact Explanation
If confirmed, this breaks the "approval set binds to the intended action" invariant called out in the Admission Pivots: owners' votes are supposed to approve a specific payload, but the admission check (prologue) that runs before execution does not enforce that binding unless a specific governance feature flag is turned on. This could allow an owner (who is authorized to submit execution, but not necessarily to unilaterally choose the payload) to execute an entry function that was never approved by the multisig quorum — potentially moving funds or invoking privileged multisig-owned code paths that the other signers never approved.

### Likelihood Explanation
Exploitability depends entirely on whether `abort_if_multisig_payload_mismatch_enabled` is set to `false` on a given network. I could not verify the current default/enabled status of this feature flag in this codebase snapshot, nor fully trace `get_next_transaction_payload`'s selection logic. Given the feature's name and gating pattern (a targeted fix flag), it is plausible this was already identified and is being rolled out, meaning the finding may already be mitigated by default on production networks but potentially still live on networks/testnets where the flag has not been enabled.

### Recommendation
- Verify the default state of `abort_if_multisig_payload_mismatch_enabled` in the current release; if disabled by default, treat the payload-match assertion as unconditional (remove the feature gate) so both full-payload and hash-only multisig transactions always bind the approved payload to the executed payload.
- Audit `get_next_transaction_payload` to ensure it never silently prefers a submitter-provided payload over the on-chain approved payload when the two differ and full payload storage was used.

### Proof of Concept
Not constructed — this requires confirming (1) the default value of `abort_if_multisig_payload_mismatch_enabled` on a live network/genesis config, and (2) the exact selection logic in `get_next_transaction_payload`, neither of which I could verify with the remaining tool budget. I recommend a follow-up session specifically to inspect `get_next_transaction_payload` in `multisig_account.move` and the feature-flag default in `aptos-move/framework/move-stdlib/sources/configs/features.move` / genesis configuration before treating this as confirmed.
