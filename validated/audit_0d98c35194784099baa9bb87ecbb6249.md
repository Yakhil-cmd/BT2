## Title
Multi-tenant GitHub App: signature verified against `repository.owner.login`'s org secret while all handlers act on `repository.full_name`'s repository, letting a no-secret org forge writes into a victim's review stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

## Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to check using only `repository.owner.login` (via `repository_owner`) [1](#0-0) , but every `pull_request` handler (including `LabelCapturingHandler`) resolves the target repository/stack independently from `params.repository.full_name` [2](#0-1) . `GitHubApp#verify_webhook_signature` additionally returns `true` unconditionally when no `webhook_secret` is configured for that resolved org [3](#0-2) . These two facts together mean an attacker can pick any organization with no configured webhook secret for `owner.login` while pointing `full_name` at a real, secret-protected victim org/repo, and the request will be accepted and dispatched against the victim's stack.

## Finding Description
The broken binding: the code implicitly assumes `repository.owner.login == full_name.split('/').first`, i.e. that the org used to authenticate the webhook is the same org whose repository/stack is mutated. This is never enforced.

- `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` where `repository_owner` reads `params.dig('repository', 'owner', 'login')` [4](#0-3) .
- `Shipit.github` looks up `github_app_config(organization)` from `secrets.github`; if that org key doesn't exist it raises `GithubOrganizationUnknown` and the request is rejected with 422 [5](#0-4) . But if the org key **does** exist yet has no `webhook_secret` configured, `verify_webhook_signature` returns `true` for **any** signature/body [6](#0-5) .
- Once verification passes, `WebhooksController#create` dispatches `params` (the raw JSON, unrelated to which org authenticated it) to all `pull_request` handlers, including `LabelCapturingHandler` [7](#0-6) .
- `LabelCapturingHandler#repository` resolves the acted-upon repository from `params.repository.full_name`, completely independent of `owner.login` used for signature selection [8](#0-7) . On `action=opened` with `stack.present?`, it calls `capture_labels`, persisting `params.pull_request.labels.map(&:name)` onto `stack.pull_request` [9](#0-8) [10](#0-9) .

Exploit flow: attacker registers/controls an org `attacker-org` that is configured in Shipit's multi-tenant `secrets.github` map but with no `webhook_secret` set (or attacker finds any such org in the deployment's configured org list — the question stipulates this "no-secret org" exists). Attacker crafts a `pull_request` `opened` webhook body with `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/victim-repo"` (a real repository with `review_stacks_enabled` and `allow_all` provisioning). Since `attacker-org` has no webhook secret, `verify_webhook_signature` returns `true` regardless of the `X-Hub-Signature` header content. The request passes `verify_signature`, and `LabelCapturingHandler` (and other `pull_request` handlers such as `OpenedHandler`, since `Webhooks.for_event('pull_request')` runs the full chain [11](#0-10) ) act on `victim-org/victim-repo` as if the request had been authenticated by that org's secret.

Existing guards do not stop this: `drop_unhandled_event` only checks the event type exists; the `ExplicitParameters` schema only validates shape, not that `owner.login`'s org matches `full_name`'s org prefix; there is no `Repository` validation tying `full_name`'s org segment back to the authenticating org.

## Impact Explanation
This is a cross-tenant repository/stack mutation: a request that only proved control of `attacker-org`'s (secret-less) webhook channel is used to write into `victim-org/victim-repo`'s review-stack `PullRequest` labels, and — because `allow_all` review-stack provisioning auto-creates and provisions stacks for any opened PR against that repository and those labels are later uppercased into `ReviewStack#env` and merged into the environment used to execute `shipit.yml`/`Command`/`PTY.spawn` for that stack's tasks — attacker-controlled label strings can influence environment variables consumed by scripts executed on the Shipit deploy host for the victim's stack. This matches the "payload for one repository mutating another's stack" / potential RCE class in scope, and is repeatable against any repository whose `full_name` the attacker can specify, for any org lacking a `webhook_secret` in the shared Shipit deployment.

## Likelihood Explanation
Preconditions: the Shipit deployment must be running the multi-tenant GitHub App config (`secrets.github` keyed by organization) and must have at least one configured organization without a `webhook_secret` set (this is an operator misconfiguration risk, not guaranteed present in every deployment) — the question's "owner/full_name split verification gap" explicitly assumes such a no-secret org exists. The victim repository must have `review_stacks_enabled: true` and `provisioning_behavior: allow_all`. Given those two conditions, the attack is trivial and free for an unauthenticated attacker: a single `POST /webhooks` request with attacker-chosen JSON, no valid signature needed against the victim's secret at all.

## Recommendation
In `WebhooksController#verify_signature` (or in each handler's repository resolution), enforce that the organization used to select the webhook secret (`repository.owner.login` / `organization.login`) matches the organization segment of `repository.full_name` before dispatching to handlers; reject the request (422) on mismatch. Additionally, do not treat a missing `webhook_secret` as automatic pass-through — either require `webhook_secret` to be configured for every org accepted by `Shipit.github`, or explicitly fail closed when `webhook_secret` is blank for multi-tenant deployments.

## Proof of Concept
minitest plan (no live GitHub):
1. Configure test secrets with two orgs: `victim-org` (has `webhook_secret: "s3cr3t"`) and `attacker-org` (github app config present but no `webhook_secret`).
2. Create `Shipit::Repository` for `victim-org/victim-repo` with `review_stacks_enabled: true`, `provisioning_behavior: allow_all`.
3. Build a `pull_request` `opened` payload with `repository.owner.login = "attacker-org"`, `repository.full_name = "victim-org/victim-repo"`, `pull_request.labels = [{name: "EVIL"}]`.
4. POST to `/webhooks` with `X-Github-Event: pull_request` and an arbitrary/garbage `X-Hub-Signature` header (not matching `victim-org`'s secret).
5. Assert response is `200 OK` (not `422`), i.e. `verify_signature` passed via `attacker-org`'s missing-secret bypass — this is the equality violation: authenticating org (`attacker-org`) ≠ mutated repo's org (`victim-org`).
6. Assert `Shipit::Stack` was created/updated for `victim-org/victim-repo` and that `stack.pull_request.labels` includes `"EVIL"`, proving the payload authenticated by `attacker-org` mutated `victim-org`'s stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
