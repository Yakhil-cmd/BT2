### Title
Webhook signature verification keys off `repository.owner.login` while every event handler dispatches on `repository.full_name`, letting a payload authenticated for one org act on any other org's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to validate the inbound webhook's HMAC using `repository_owner`, which is read straight out of the JSON body (`params.dig('repository', 'owner', 'login')` or the `organization` sub-object). [1](#0-0) 
Once the signature check passes, `create` hands the *entire* raw params hash to every registered handler for the event, and each `Handler` looks up the target `Stack`/`Repository` using a completely different field of the same payload: `repository.full_name`. [2](#0-1) [3](#0-2) 

Because `Shipit` supports one `GitHubApp`/secret per organization (`Shipit.github(organization: repository_owner)`, `github_app_config`), the field that authenticates the request (`repository.owner.login`) and the field that determines which repository's Stacks get mutated (`repository.full_name`) are never checked for consistency. [4](#0-3) 

### Finding Description
The binding this breaks is: **organization that authenticated == repository that is written**.

`verify_webhook_signature` returns `true` unconditionally whenever the resolved organization's `webhook_secret` is blank (`return true unless webhook_secret`): [5](#0-4) 

In a multi-organization Shipit deployment (the schema explicitly supported by `github_app_config`/`TOP_LEVEL_GH_KEYS`), it is normal for an operator to configure some organizations without a `webhook_secret` (the shipped fixtures and setup docs show `webhook_secret:` left blank), because that org may not yet be wired up, may be a low-security sandbox org, or the operator simply hasn't rotated in a secret. `verify_signature` uses whatever `repository.owner.login` value is present in the untrusted, attacker-supplied JSON body to pick which org's `GitHubApp` (and thus which secret, if any) is used to check the signature: [6](#0-5) 

An unprivileged attacker who can reach the `/webhooks` endpoint (no auth required, it's a public webhook receiver) can therefore craft a JSON body where:
- `repository.owner.login` = an organization configured in `secrets.github` **without** a `webhook_secret` (so `verify_webhook_signature` short-circuits to `true` regardless of the `X-Hub-Signature` header sent, or even no correct HMAC at all beyond format `sha1=...`), and
- `repository.full_name` = any other, unrelated, privileged repository tracked by Shipit (e.g. `AcmeCorp/prod-secrets-repo`), which is the value every `Handler#stacks`/`Handler#repository_name` actually acts on: [7](#0-6) [8](#0-7) 

Since these two fields live in the same JSON body but are read by two unrelated code paths (controller vs. handler) with no cross-check that `repository.full_name`'s owner equals the `repository_owner` used for verification, the "authentication" performed by `verify_signature` provides no actual guarantee about which repository's Stacks are subsequently mutated.

This is the structural analog of the reported bug: the GodMode admin account is trusted/authorized for lamport bookkeeping (`reclaim_rent`) but declared with permissions (`read-only`) that don't match what is actually acted upon (mutated) in `add_ephemeral_multiplier`, breaking the binding between the account that is authorized and the account that is written. Here, the organization that is authorized (via signature) is not the same entity as the repository that is written (via `full_name`).

### Impact Explanation
An attacker who knows (or guesses) that some organization in a target's multi-org Shipit config has no webhook secret configured can forge `push` (and other) webhook events for **any** repository/stack tracked by that Shipit instance, not just the unsecured org's own repos. Depending on which handler fires this can:
- Force `PushHandler` to trigger `stack.sync_github(expected_head_sha:)` against a chosen branch/head SHA for a stack belonging to a fully different, secured organization, corrupting the commit history Shipit believes is deployable and potentially causing an unauthorized deploy/rollback of unintended revisions.
- Drive `StatusHandler`/`CheckSuiteHandler`/`MembershipHandler` to inject fabricated CI status, check-run, or team-membership data for that other org's stacks, which downstream deploy-gating logic (`Stack` deployable checks, `Shipit.github_teams` authorization) relies on — i.e., escalation into `Shipit.github_teams` authorization and unauthenticated manipulation of deploy gating for a repository outside the attacker's control.

This matches the required High/Critical impact categories: escalation into `Shipit.github_teams` authorization and/or an unauthorized deploy/rollback, achieved purely by an unauthenticated actor hitting the public webhooks endpoint.

### Likelihood Explanation
Requires only network access to the public `/webhooks` endpoint (no session, token, or repository access needed) and a Shipit deployment with more than one GitHub org configured where at least one has no `webhook_secret` set — a configuration explicitly supported and documented (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`), not an edge case invented for this analysis. No social engineering, TLS interception, or credential theft is required.

### Recommendation
After parsing the payload, validate that `repository.owner.login`/`organization.login` (the value used for `verify_signature`) matches the owner embedded in `repository.full_name` before dispatching to handlers, or better: derive the org used to select the `GitHubApp` for verification directly from the `Repository` record already registered for `repository.full_name`, rather than trusting an unverified field of the same untrusted payload. Additionally, disallow/require a non-blank `webhook_secret` for every configured organization so `verify_webhook_signature` can never silently accept unsigned traffic.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `UnsecuredOrg` (no `webhook_secret`) and `TargetOrg` (tracked stack `TargetOrg/critical-app`, secured with a secret the attacker does not know).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "UnsecuredOrg" },
    "full_name": "TargetOrg/critical-app"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "UnsecuredOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the `X-Hub-Signature` header value. [5](#0-4) 
4. `create` then dispatches the full payload to `PushHandler`, which resolves the stack via `repository.full_name = "TargetOrg/critical-app"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `TargetOrg`'s stack — a stack the attacker was never authenticated against. [8](#0-7)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
