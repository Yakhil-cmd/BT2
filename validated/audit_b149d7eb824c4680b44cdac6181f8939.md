### Title
Griefing/freezing of shared-address funds via malicious redefinition of a nested member `address` reference - (File: `definition.js`)

### Summary
`ocore` lets a multi-signature ("shared") address definition reference a co-signer indirectly, using the `['address', BASE32]` operator instead of embedding that member's public key directly. Whenever the shared address is used (spent from), every validating node re-resolves and re-evaluates that member's *current* address definition on-chain, at the `last_ball_mci` in effect for the unit being validated. Because the referenced member fully controls his own address definition and can change it unilaterally (via an `address_definition_change` message that only he needs to sign), he effectively controls a piece of "validation logic" that all other co-signers' future spending transactions depend on — directly analogous to the reported Solidity issue, where an order's creator controls an `additionalValidationContract` that a third-party filler is forced to execute.

### Finding Description
`Definition.validateDefinition()`'s `evaluate()` handles the `'address'` op by dynamically reading the referenced address's current definition and recursively evaluating it as part of the calling (outer, e.g. shared/multisig) definition: [1](#0-0) 

The complexity/op counters (`complexity`, `count_ops`) accumulate across this recursive evaluation and are bounded by `MAX_COMPLEXITY`/`MAX_OPS`: [2](#0-1) 

Crucially, this re-resolution happens **every time** a unit signed by the shared address is validated — not just once at address-creation time — precisely because the referenced address can be redefined later. The code comments explicitly document this as a known risk: [3](#0-2) 

`validateAuthentifiers()` (the signature-checking counterpart) performs the same dynamic lookup of the referenced member's definition when verifying signatures on any unit spent from the shared address: [4](#0-3) 

A member address's owner controls his own definition unilaterally, and can change it via `address_definition_change`, which is authorized solely by that address's own author, with no cosigner involvement required: [5](#0-4) 

Because a member's own definition can independently approach `MAX_COMPLEXITY`/`MAX_OPS` on its own (it is validated standalone when first defined), and its complexity is *added* to the complexity of the outer definition when resolved via `'address'`, a malicious member can craft/redefine his own address definition (something he fully controls without any cosigner's consent) so that once nested inside the shared address's definition, the *combined* complexity or op count exceeds `constants.MAX_COMPLEXITY` / `constants.MAX_OPS`. From that point forward, `validateDefinition`/`validateAuthentifiers` return `"complexity exceeded ..."` / `"number of ops exceeded ..."` for **every** unit spent from the shared address — freezing all co-signers' funds, including honest ones, not just the malicious member's share. This is the exact griefing pattern from the report: an unprivileged party (a shared-address member, analogous to the order creator who sets `additionalValidationContract`) controls an entity (his own address definition, analogous to the `ValidationContract`) that a counterparty (the other co-signers, analogous to the filler) is forced to invoke/evaluate as part of an otherwise-legitimate operation, and can turn that entity malicious after the fact to grief the counterparty.

### Impact Explanation
Once the referenced member's redefinition pushes the combined complexity/op count past the protocol limits, all future spends from the shared/multi-signature address will permanently fail validation on every node (deterministically, since all nodes apply the same limits and re-read the same current definition). This is a genuine, protocol-visible fund-freezing condition for the honest co-signers of a shared address — they cannot spend jointly-controlled funds any more, and there is no way to "undo" another member's own address definition. This matches the accepted impact class of "AA/wallet fund loss or freezing" and is reachable purely by a single unprivileged party posting ordinary `address_definition_change` units for an address they solely control.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an existing shared/multisig address whose definition references a member indirectly via `['address', BASE32]` (a documented, supported pattern for multisig wallets using `wallet_defined_by_addresses.js`/`arbiter_contract.js` so that members can rotate keys without re-signing with all cosigners), and (b) that member being willing to sacrifice his own membership benefit to grief the others. No cryptographic secrets or races are needed — the attacker only signs an ordinary `address_definition_change` for an address he already controls, well within his rights, but engineered to make the nested evaluation blow past `MAX_COMPLEXITY`/`MAX_OPS`.

### Recommendation
- When resolving a nested `['address', ...]` definition inside another definition, count/cap the complexity and ops contributed by that inner definition independently and re-validate that the *combination* stays under limits at the moment the outer definition is first established (already partly done), but additionally re-check and reject/roll back (or refuse to activate) a member's `address_definition_change` if it would push complexity/op counts of any *shared address that already references it* over the limit — i.e., validate redefinitions against all known dependents, not just the redefining address in isolation.
- Alternatively, decouple "signature verification" complexity budgets from "structural" (spending-condition) complexity so that a member's ability to independently redefine his own signing scheme cannot retroactively invalidate joint spending conditions that other, non-consenting parties depend on.
- Document/enforce a hard sub-limit per nested `'address'` reference (e.g., reserve a fixed complexity budget per referenced member) so no single co-signer's definition growth can ever exceed the shared budget regardless of how it's redefined later.

### Proof of Concept
1. Alice and Bob create a 2-of-2 shared address `S` whose definition is `['and', [['address', 'ALICE_ADDR'], ['address', 'BOB_ADDR']]]` (standard pattern supported by `wallet_defined_by_addresses.js`, see `getMemberDeviceAddressesBySigningPaths`/`validateAddressDefinitionTemplate` at `wallet_defined_by_addresses.js:439-528`).
2. `ALICE_ADDR`'s initial definition is a simple `['sig', {pubkey: ...}]` (complexity ≈ 1).
3. After `S` is created and funded jointly, Alice posts an `address_definition_change` for `ALICE_ADDR` (validated purely under her own single-signer authority per `validation.js:1719-1745`) to a new definition that is deeply nested (e.g., many levels of `and`/`or`/`r of set`), sized so that it alone stays within `MAX_COMPLEXITY` when validated standalone (as required when the change is accepted), but which, once resolved inside `S`'s `['address', 'ALICE_ADDR']` reference during future spend validation (`definition.js:269-304`), pushes the cumulative `complexity`/`count_ops` counters (`definition.js:103-111`) past `constants.MAX_COMPLEXITY`/`MAX_OPS`.
4. From that point on, any unit spending from `S` (signed correctly by both Alice and Bob) fails `validateDefinition`/`validateAuthentifiers` with `"complexity exceeded at ..."` or `"number of ops exceeded at ..."`, permanently freezing the funds held at `S` for Bob (and Alice herself, though she caused it) — mirroring the reported scenario where a party-controlled "validation" entity is weaponized against a counterparty who has no control over it.

*(Note: exact numeric thresholds for `MAX_COMPLEXITY`/`MAX_OPS` were not confirmed from `constants.js` content in this session due to search-index limitations on that file's content; a full session with direct file access would be needed to compute the precise nesting depth required to trigger the overflow.)*
