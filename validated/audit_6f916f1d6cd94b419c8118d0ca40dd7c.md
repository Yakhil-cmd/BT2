Based on my research, I found a genuine engine-level analog: private-asset payments sent to an AA address never trigger the AA and permanently sit uncounted in its balance/output set, mirroring the "late-arriving funds get stuck forever" pattern from the report — except here it's not a design choice of a particular AA script but a structural exclusion baked into the core trigger-selection query.

### Title
Payments in private assets sent to an AA address never trigger execution and become permanently unspendable - (File: main_chain.js)

### Summary
`ocore`'s AA trigger-selection logic in `main_chain.js` explicitly excludes outputs of private assets from ever queuing an AA trigger. Because private-asset outputs are also excluded from `aa_balances` accounting elsewhere in the codebase, bytes/asset value sent to an AA address using a private asset become permanently invisible to the AA and can never be spent, refunded, or otherwise accounted for — a structural, protocol-level analog of the "late-arriving funds get stuck forever" bug class, except it applies to *every* private-asset transfer to any AA, not merely a coordination-timing edge case.

### Finding Description
When a main-chain index stabilizes, `handleAATriggers()` in `main_chain.js` selects units whose payments to a known AA address should trigger execution: [1](#0-0) 
The `WHERE` clause requires `outputs.asset IS NULL OR is_private=0`, i.e. private-asset outputs are unconditionally excluded from generating an `aa_triggers` row. This same exclusion appears in `insertAADefinitions` when AA balances are (re)computed for an AA that has just been defined: [2](#0-1) 
and again in `checkBalances()`'s reconciliation query, which only counts non-private outputs (or private outputs belonging to AA responses) toward an AA's balance: [3](#0-2) 
There is no validation-time rejection of a public unit sending a private-asset payment to an AA address; `validateAATrigger` in `validation.js` only inspects `m.payload && m.payload.outputs` for public payment messages and does not special-case or reject private assets targeting AA addresses: [4](#0-3) 
An unprivileged unit poster can therefore issue or transfer a private asset and send an output to any AA address. The unit validates and stabilizes normally, its `outputs` row is recorded with `is_private=1`, but because every downstream mechanism used to (a) create an `aa_triggers` entry and (b) recompute `aa_balances` filters out `is_private=1` rows, the AA never executes in response to this payment and its internal balance ledger never reflects the transferred value. The value is not double-spent nor destroyed at the ledger level (the output row exists, spendable in principle by whoever controls the AA address's private key — which for an AA is nobody, since AAs have no private key), so it is permanently stuck, unreachable by the AA's own `bounce`/response logic or by any subsequent trigger, because the trigger-selection query will never surface this MCI/unit/address combination again (it is a one-time, per-mci-stabilization query keyed by `main_chain_index`).

### Impact Explanation
This falls under "AA fund loss or freezing." Because AAs cannot spend a private-asset output whose existence they never learn about (no trigger fires, no balance updates), any value sent this way is unconditionally and permanently frozen. This differs from the report's coordination/timing bug in that it requires zero misconfiguration on the AA author's part — it's a systemic gap in how private-asset outputs interact with AA triggering, reachable by any wallet or script that composes a private-asset payment to an AA address (whether through carelessness or via a UI/dApp that does not specifically special-case AA destinations).

### Likelihood Explanation
Likelihood is more than a hypothetical concern: private assets are a first-class, freely composable feature (`indivisible_asset.js`, `divisible_asset.js`), and nothing in the wallet-level guard `checkAAOutputs`/`aa_addresses.js` (`checkAAOutputs`) rejects private-asset destinations to AAs; that function only checks bounce-fee sufficiency for public outputs sent to AAs: [5](#0-4) 
Any user or application composing a private-asset transfer with an AA as the recipient — for example, by mistake, or via third-party tooling unaware of the restriction — triggers this permanent freeze with a single unit.

### Recommendation
Either (a) reject at validation time any payment message whose output address is a known AA and whose asset `is_private=1` (mirroring the existing `checkNotAAs`/AA-destination checks already present for other message types), so such units simply fail to validate, or (b) extend the AA-trigger and AA-balance-accounting queries to include private-asset outputs sent to AAs (which would require rethinking how privacy and public AA execution interact, since AAs cannot process hidden payloads). Option (a) is the minimally invasive fix and is consistent with the existing pattern in `aa_composer.js` where AAs are explicitly forbidden from *sending* private assets ("sending private asset from AA").

### Proof of Concept
1. Define any simple AA at address `AA_ADDR` (e.g., a bounce-back script).
2. Issue a new private asset (`is_private: true`) using `indivisible_asset.js`/`divisible_asset.js` composer helpers.
3. Compose and post a private-asset payment whose output sends value to `AA_ADDR` (nothing in `validateAATrigger` or `checkAAOutputs` blocks this).
4. Wait for the unit's MCI to stabilize; observe in `aa_triggers` (empty — no row is inserted because `handleAATriggers`'s query filtered out the private output) and in `aa_balances` (unchanged for `AA_ADDR`) that the AA never sees or accounts for the payment.
5. The output remains marked `is_spent=0` in the `outputs` table but is permanently unreachable because the AA address has no private key to sign a spending transaction, and the AA's own logic (triggered only via `aa_triggers`) never fires for this value.

function checkAAOutputs(arrPayments, handleResult) {
	var assocAmounts = {};
	arrPayments.forEach(function (payment) {
		var asset = payment.asset || 'base';
		payment.outputs.forEach(function (output) {
			if (!assocAmounts[output.address])
				assocAmounts[output.address] = {};
			if (!assocAmounts[output.address][asset])
				assocAmounts[output.address][asset] = 0;
			assocAmounts[output.address][asset] += output.amount;
		});
	});
	var arrAddresses = Object.keys(assocAmounts);
	readAADefinitions(arrAddresses, function (err, rows) {
		if (err)
			return handleResult(err);
		if (rows.length === 0)
			return handleResult();
		var arrMissingBounceFees = [];
		rows.forEach(function (row) {
			var arrDefinition = JSON.parse(row.definition);
			var bounce_fees = arrDefinition[1].bounce_fees;
			if (!bounce_fees)
				bounce_fees = { base: constants.MIN_BYTES_BOUNCE_FEE };
			if (!bounce_fees.base)
				bounce_fees.base = constants.MIN_BYTES_BOUNCE_FEE;
			for (var asset in bounce_fees) {
				var amount = assocAmounts[row.address][asset] || 0;
				if (amount < bounce_fees[asset])
					arrMissingBounceFees.push({ address: row.address, asset: asset, missing_amount: bounce_fees[asset] - amount, recommended_amount: bounce_fees[asset] });
			}
		});
		if (arrMissingBounceFees.length === 0)
			return handleResult();
		handleResult(new MissingBounceFeesErrorMessage({ error: "The amounts are less than bounce fees", missing_bounce_fees: arrMissingBounceFees }));
	});
}
