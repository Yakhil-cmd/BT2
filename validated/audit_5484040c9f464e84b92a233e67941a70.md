### Title
Webhook organization used for signature verification is decoupled from the repository the payload is allowed to mutate, enabling cross-repository forged commit statuses/pushes - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) [2](#0-1) . However, every event handler resolves the target `Repository`/`Stack` to act on using a *different* field of the same JSON body: `payload.dig('repository', 'full_name')` [3](#0-2) . Nothing enforces that `repository.owner.login` (used to pick the signing secret) and `repository.full_name` (used to pick the acted-upon repository) refer to the same GitHub organization/repo. This is exactly the "organization that authenticated versus the repository that is written" trust binding described in the rules.

### Finding Description
Shipit supports multiple GitHub Apps/organizations configured against one instance; `Shipit.github(organization: ...)` looks up per-organization config and raises `GithubOrganizationUnknown` if the org isn't registered [4](#0-3) , confirmed by the "unknown github organization" test [5](#0-4) . Each configured organization has its own `webhook_secret`, checked via HMAC-SHA1 in `GitHubApp#verify_webhook_signature` [6](#0-5) .

The signature check binds trust to `repository_owner`:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

But the handler that performs the actual state mutation resolves the target repository independently, from `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

Because a webhook body is a single flat JSON hash entirely controlled by the caller (this is an unauthenticated public endpoint, protected only by the HMAC signature), an attacker who legitimately administers *any* GitHub organization/app already registered with this Shipit instance can:
1. Set `repository.owner.login` (and/or top-level `organization.login`) to their own org, so `Shipit.github(organization: repository_owner)` resolves to a `GitHubApp` config whose `webhook_secret` the attacker knows (because they configured that GitHub App's webhook for their own org).
2. Sign the payload with that known secret to produce a valid `X-Hub-Signature`, passing `verify_signature`.
3. Set `repository.full_name` to `"victim-org/victim-repo"` — an entirely different repository already tracked by Shipit that the attacker has no access to.

`Shipit::Webhooks.for_event(event)` then dispatches the attacker-controlled `params` hash to the real handler, which resolves stacks using `repository.full_name` (the victim repo), not `repository.owner.login` (the org whose secret was actually verified) [7](#0-6) .

The `status` event handler is the most directly damaging instance of this pattern: it creates a `Status` record for a commit purely from payload fields (`sha`, `state`, `target_url`, `description`, `context`) with no round-trip verification against GitHub, as shown by the existing test:
```ruby
body = JSON.parse(payload(:status_master)).merge(repository_params).to_json
post :create, body:, as: :json
status = commit.statuses.last
assert_equal status_payload['state'], status.state
``` [8](#0-7) 

Since the commit is looked up by `sha` within the repository resolved from `repository.full_name` (not the signature-verified `repository.owner.login`), an attacker who owns any org registered with the Shipit instance can forge a `success` status on a specific commit sha of the victim's tracked repository, as long as that sha exists in the victim stack's known commits.

### Impact Explanation
Forged commit statuses on a repository the attacker does not control can satisfy Shipit's deploy/merge-queue safety checks (required statuses) for that stack, enabling an unauthorized deploy or merge queue advance on a repository/organization the attacker has no legitimate access to — this is a cross-repository write / unauthorized-deploy class impact explicitly listed as Critical in scope.

### Likelihood Explanation
The webhook endpoint is public and unauthenticated aside from the HMAC check [9](#0-8) . The only precondition is that the attacker legitimately administers at least one GitHub organization/App already configured on the same shared Shipit instance (a realistic scenario for any multi-tenant/shared Shipit deployment, and not a privileged Shipit role). No Shipit session, `ApiClient` token, or leaked secret is required — only knowledge of a secret the attacker legitimately possesses for their own org.

### Recommendation
Bind the signature-verification identity to the same repository field used for state mutation: derive `repository_owner` and the acted-upon `repository_name` from the identical payload path, and additionally verify inside each handler that `payload.dig('repository', 'owner', 'login')` matches the owner segment of `payload.dig('repository', 'full_name')` before resolving stacks or mutating commit/status state. Reject the webhook if these are inconsistent.

### Proof of Concept
1. Attacker legitimately controls GitHub org `attacker-org`, which is registered as a GitHub App in this Shipit instance with known `webhook_secret` `S`.
2. Attacker crafts payload:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"},
  "sha": "<existing sha in victim stack>",
  "state": "success",
  "target_url": "https://ci.example.com/fake",
  "description": "forged",
  "context": "ci/required-check",
  "branches": [{"name": "master"}]
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S, raw_body)` and sends `POST /webhooks` with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature using `S` [1](#0-0) .
5. `StatusHandler` (dispatched via `Shipit::Webhooks.for_event('status')`) resolves the target commit/repository based on `sha`/`repository.full_name` = `victim-org/victim-repo` and creates/updates a `Status` marking the victim's commit as `success`, as reproduced by the existing test pattern [8](#0-7) , even though the verified signature only proves control of `attacker-org`, not `victim-org`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
