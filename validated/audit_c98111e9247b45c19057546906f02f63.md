The Push handler (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) uses `stacks`, which resolves via `Handler#stacks`/`#repository_name` reading `payload.dig('repository', 'full_name')` [1](#0-0) , a field the `WebhooksController#verify_signature` never checks — it only reads `params.dig('repository','owner','login')` (or `organization.login`) to pick which per-organization secret to verify against [2](#0-1) [3](#0-2) . Since `Shipit.github(organization:)` looks up a distinct `GitHubApp`/secret per configured org in multi-org deployments [4](#0-3) , and `verify_webhook_signature` is HMAC over the full raw body using that org's secret only [5](#0-4) , this is enough to write up the finding.

### Title
Webhook signature binds `repository.owner.login` but handlers act on the unverified `repository.full_name`, enabling cross-repository/cross-organization writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository.owner.login` (falling back to `organization.login`), but every `Shipit::Webhooks::Handlers::Handler` subclass resolves the target `Repository`/`Stack` from a *different* JSON field in the same payload — `repository.full_name` — which is never covered by that authentication decision. In a multi-organization Shipit deployment (explicitly supported, see `docs/setup.md` "Using Multiple GitHub Applications"), each organization has its own independent `webhook_secret`. An attacker who legitimately controls one tenant organization's webhook secret can forge a raw POST to `/webhooks` where `repository.owner.login` names their own org (so signature validation passes with their own secret) while `repository.full_name` names a repository/stack belonging to an entirely different, unrelated organization tracked by the same Shipit instance.

### Finding Description
`verify_signature` computes the authenticating organization strictly from the `repository.owner.login`/`organization.login` keys: [6](#0-5) 

That organization name is used only to select which `GitHubApp` (and thus which `webhook_secret`) verifies the HMAC signature over the raw request body [5](#0-4) , and `Shipit.github(organization:)` maintains one distinct secret per org key configured under `secrets.github` [4](#0-3) .

However, once the signature check passes, `Shipit::Webhooks.for_event(event)` dispatches to handlers that identify the affected `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')`: [1](#0-0) 

Nothing ties `repository.owner.login` (the field the signature check trusts) to `repository.full_name` (the field the handlers trust) within the same payload. Since the HMAC covers the raw JSON body as a whole but the verification step reads only `repository.owner.login`/`organization.login` from it, an attacker who legitimately possesses a valid secret for *any* one organization configured in the instance can compute a valid signature over a payload whose `repository.full_name` (and other fields) reference a completely different organization's repository/stack.

Concretely, for the `push` event, `Shipit::Webhooks::Handlers::PushHandler#process` finds stacks by branch on `stacks` (derived from `repository.full_name`) and calls `stack.sync_github(expected_head_sha: params.after)`: [7](#0-6) 

This binding is exactly the pattern named in scope: "an organization that authenticated versus the repository that is written."

### Impact Explanation
This breaks the equality `organization_that_signed(payload) == organization_that_owns(repository_acted_on)`. An attacker who administers (and therefore knows the webhook secret for) one tenant org onboarded onto a shared, multi-org Shipit instance can forge webhook deliveries that are cryptographically valid (per the org-selection logic) yet target another tenant's `Stack`/`Repository` records. Depending on handler, this can:
- force `GithubSyncJob` to run against a victim stack with an attacker-chosen `expected_head_sha`, effectively steering what commit Shipit believes is at the head of a victim's tracked branch — an unauthorized/cross-repository write and a step toward an unauthorized deploy of forged commit metadata,
- inject forged commit `Status` records (`StatusHandler`) or forge PR/team/membership data belonging to a victim org.

This satisfies the required Critical impact category "cross-repository writes" / "unauthorized deploy."

### Likelihood Explanation
Requires the attacker to legitimately hold a webhook secret for at least one organization configured in the same multi-tenant Shipit instance — a realistic and explicitly documented deployment topology (`docs/setup.md`, "Using Multiple GitHub Applications"), not a compromise of the Shipit host or any privileged Shipit session/API-client token. No GitHub write access to the victim's repository, no Shipit login, and no `api_clients_secret` are needed; only the ability to send a raw HTTP POST to the public `/webhooks` endpoint with a self-signed body.

### Recommendation
Bind the same field for authentication and for resolution: derive both the signing organization *and* the target repository lookup from the identical, already-verified value (e.g., require that `repository.full_name`'s owner segment equals `repository.owner.login`/`organization.login` used in `verify_signature`, and reject the webhook otherwise), or better, resolve the `Repository` scoped to the authenticated organization rather than trusting the free-form `full_name` string globally.

### Proof of Concept
1. Shipit is configured (per documented multi-org setup) with two tenant orgs: `org-attacker` (secret `S_A`, known to the attacker who manages that org's GitHub App) and `org-victim` (secret `S_V`, unknown to attacker), each tracking stacks in Shipit.
2. Attacker crafts a JSON push payload: `{"ref": "refs/heads/main", "after": "<attacker-chosen sha>", "repository": {"owner": {"login": "org-attacker"}, "full_name": "org-victim/private-repo"}}`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_A, raw_body)` using the secret they legitimately know for `org-attacker`.
4. POST to `/webhooks` with header `X-Github-Event: push`. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'org-attacker')` and the signature validates successfully [8](#0-7) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('org-victim/private-repo')` [1](#0-0)  and calls `sync_github(expected_head_sha: <attacker-chosen sha>)` on the victim org's stack, despite the request never being authenticated by `org-victim`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
