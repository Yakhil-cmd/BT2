**Analysis:**

The exploit claim conflates two unrelated subsystems: `AccessPath`/`Path` encoding (used for state-key resolution in storage) and authenticator/authentication-key checks in transaction admission (`txn_authentication_key` in `aptos-move/aptos-vm/src/transaction_validation.rs` and `aptos-move/framework/aptos-framework/sources/transaction_validation.move`). These are independent code paths.

Key facts that invalidate the claim:

1. `Path` is a Rust `enum { Code(ModuleId), Resource(StructTag), ResourceGroup(StructTag) }` serialized/deserialized exclusively via `bcs::to_bytes`/`bcs::from_bytes`, not via manual byte-offset parsing. <cite repo="Ellentat/aptos-core--012" path="types/src/access_path.rs" start="76="82" /><cite repo="Ellentat/aptos-core--012" path="types/src/access_path.rs" start="148="151" />

2. The `PathType` byte comparison (`p if p == PathType::Resource as u8`) referenced in the question only exists inside `impl fmt::Display for AccessPath`, a debug/printing routine — it is never used to resolve or validate a `StateKey`. <cite repo="Ellentat/aptos-core--012" path="types/src/access_path.rs" start="196="219" />

3. Actual `StateKey`/`Path` reconstruction always goes through strict BCS deserialization of the full `StructTag`/`ModuleId` structure (address, module, name, type args), not a "first byte + fixed HashValue-length segment" scheme. `bcs::from_bytes::<Path>` will reject any malformed or mismatched encoding rather than silently aliasing to a different resource. <cite repo="Ellentat/aptos-core--012" path="types/src/access_path.rs" start="242="256" /><cite repo="Ellentat/aptos-core--012" path="types/src/state_store/state_key/mod.rs" start="211="222" />

4. `AccessPath`/`StateKey` resolution occurs during execution/state access, not during the pre-execution admission checks (sequence number, expiry, chain-id, sender/authenticator binding) that live in the VM prologue and mempool/vm-validator. Authentication-key verification is handled entirely separately, e.g. in `account.move`'s `rotate_authentication_key`/`get_authentication_key` and the VM's `txn_authentication_key` prologue logic, with no dependency on `AccessPath::path` byte layout. <cite repo="Ellentat/aptos-core--012" path="aptos-move/framework/aptos-framework/sources/account/account.move" start="423="432" />

There is no code path where a raw path byte vector influences the sender/signer/authentication-key binding checked during transaction admission, so this does not meet the required impact of "accepting a transaction under an unintended auth key." The scenario as described does not correspond to any actual bypass in this codebase.
