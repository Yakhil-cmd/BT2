### Title
Arbitrary `sender` in `PreStxOp`/`StackStxOp` allows unsigned re-locking of a victim's STX and reward-address hijacking - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`PreStxOp::parse_from_tx` derives the `sender` used for a subsequent `StackStxOp` purely from an arbitrary Bitcoin transaction output address, with no cryptographic proof that the attacker controls the corresponding Stacks account. `process_stacking_ops` then executes `stack-stx` with `tx-sender = sender`, letting anyone lock a victim's already-unlocked STX into a reward cycle chosen by the attacker while directing the reward payout to an attacker-controlled `reward_addr`.

### Finding Description
The equality that should hold is: **number of times a given `STXBalance` is transitioned from unlocked → locked == number of times the true owner of that balance authorized a stacking action (by signing a Stacks transaction or delegating).** This is broken because the burnchain-op path to `stack-stx` never checks a Stacks-level signature for the `sender`.

- `PreStxOp::parse_from_tx` takes `outputs[0].address` — any Bitcoin output address chosen by whoever builds the transaction — and converts it directly to `op.output: StacksAddress` with no ownership proof: [1](#0-0) 
- `StackStxOp::parse_from_tx` is later invoked by `burnchain.rs` with `sender = &pre_stack_stx.output`, i.e., that same attacker-chosen address becomes `StackStxOp.sender`: [2](#0-1) 
- `StackStxOp::get_sender_txid` only requires that the StackStxOp's Bitcoin input spend vout=1 of the PreStxOp (a UTXO the attacker itself created and can freely spend), not vout=0 (the "sender" address) — so nothing about vout=0 needs to be attacker-owned: [3](#0-2) 
- `process_stacking_ops` then runs the `stack-stx` contract call directly `as tx-sender = sender.clone()`, i.e., as whatever address the attacker put in the `PreStxOp` output, with no Stacks-transaction signature check: [4](#0-3) 
- Inside `pox-4.clar`'s `stack-stx`, all guards are self-consistent with `tx-sender` and are satisfiable by the attacker: `check-caller-allowed` trivially passes because it's a direct call (tx-sender calls itself), `is-none (get-stacker-info tx-sender)` only blocks if the victim is *currently* stacking (so it passes once a prior lock has expired or STX was never locked), `stx-get-balance tx-sender >= amount-ustx` passes as long as attacker picks an amount at or below the victim's known/public balance, and `consume-signer-key-authorization` only verifies a signature from the attacker's own self-chosen `signer-key` over attacker-chosen `pox-addr`/`reward-cycle`/`max-amount`/`auth-id` — it authenticates the *signer*, not the *stacker*: [5](#0-4) 

Exploit flow: the attacker crafts a Bitcoin `PreStxOp` whose first output address equals the victim's Stacks address (no private key of the victim required — Bitcoin lets anyone pay to any address), and a second output that the attacker controls. In a subsequent transaction, the attacker spends that second output to build a `StackStxOp` naming `reward_addr = attacker's own PoX address`, `signer_key`/`signer-sig` self-generated by the attacker, and `stacked_ustx <= victim's current unlocked balance`. Once mined, `process_stacking_ops` executes `stack-stx` as `tx-sender = victim`, locking the victim's STX for `num_cycles` reward cycles with rewards flowing to the attacker's `reward_addr` — all without any Stacks transaction signed by the victim.

None of the existing guards (`check-caller-allowed`, `is-none (get-stacker-info tx-sender)`, `is-none (get-check-delegation tx-sender)`, balance check, `consume-signer-key-authorization`) verify that the party who benefits from the resulting reward slot (the `signer_key`/`reward_addr` holder) is the same party whose STX is being locked (`tx-sender`/`sender`). They only prevent double-stacking of an already-locked account, not unauthorized stacking of an unlocked one.

### Impact Explanation
The victim's STX get locked (temporarily frozen, an "unsigned stacking action" — High) for up to `num_cycles` reward cycles without their consent, and the corresponding BTC/sBTC PoX reward slot is credited to a `reward_addr` chosen entirely by the attacker, meaning the attacker collects PoX rewards backed by collateral they never owned or risked (theft of PoX rewards — Critical). This is repeatable against any account whose current unlocked balance and address are publicly known (which is all accounts, since STX balances/PoX status are public chain state), each time the account is unlocked and the attacker is willing to spend a small Bitcoin fee to submit the `PreStxOp`/`StackStxOp` pair.

### Likelihood Explanation
Preconditions: the victim account must not currently have `get-stacker-info` set (i.e., not mid-stack) and must hold sufficient unlocked STX — both are public and satisfied by essentially any liquid Stacks account, especially right after any unlock. Attacker cost is limited to Bitcoin transaction fees for the `PreStxOp` + `StackStxOp` pair and self-generated signer key material; no interaction with or cooperation from the victim or any privileged role is required. This is fully within the stated attacker capability of "craft burnchain stacking ops from their own Bitcoin inputs."

### Recommendation
Bind the `sender`/stacker identity cryptographically to the account whose STX is being locked — e.g., require the `PreStxOp`'s first output to be provably controlled by the same key used to sign the linking Bitcoin input (as is already effectively required for vout=1), or require an explicit Stacks-side authorization (a signature from the stacker's own key, analogous to `signer-sig`) covering `(sender, pox-addr, reward-cycle, amount, lock-period)` before `stack-stx` is allowed to execute via a burnchain op. At minimum, require `reward_addr`/`signer_key` provenance to be checked against `sender` so an unrelated third party cannot redirect rewards away from the STX owner.

### Proof of Concept
Rust integration test (pattern from `stacks-node/src/tests/neon_integrations.rs` around line 3051, and unit-test helpers `PreStxOp::new`/`StackStxOp::new` in `stackslib/src/chainstate/burn/operations/stack_stx.rs`):
1. Fund `victim` account; let victim briefly stack-and-unlock via a legitimate `stack-stx` so `get-stacker-info` is `none` and `stx-account victim` shows unlocked balance `B`.
2. As `attacker`, construct `PreStxOp { output: victim_stacks_addr, .. }` and broadcast it via the attacker's own BTC inputs/outputs (no victim key material used).
3. Construct `StackStxOp { sender: victim_stacks_addr (implicit via burnchain.rs derivation), reward_addr: attacker_pox_addr, stacked_ustx: B, signer_key: attacker_pubkey, signer_sig: attacker_self_signed, .. }`, spending vout=1 of the `PreStxOp` tx.
4. Mine both, and process via `process_stacking_ops`.
5. Assert: (a) `stx-account victim` now reports `locked > 0` and `unlock-height` set, though no Stacks transaction signed by `victim` exists in the mempool/chain; (b) the reward set entry for that cycle references `attacker_pox_addr` as the PoX payout address for `victim`'s locked amount — demonstrating the equality "locks == owner-authorized actions" and "reward-addr controller == STX owner" are both violated.

                if *vout != 1 {

                    Ok(txid)
                }
