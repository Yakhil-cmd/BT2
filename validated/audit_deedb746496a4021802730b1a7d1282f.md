### Title
Cross-organization webhook signature confusion allows forging `membership` events to escalate into `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App (and thus the `webhook_secret` used to validate `X-Hub-Signature`) based on `repository.owner.login`, falling back to `organization.login` only when `repository` is absent [1](#0-0) . The `membership` event handler, however, trusts `organization.login` from the very same payload to decide which `Team` (and hence which GitHub organization) receives the membership change [2](#0-1) . In a multi-organization Shipit deployment (`github: { orgA: {...}, orgB: {...} }`, as documented and supported) [3](#0-2) , these two fields can be set independently in one payload, breaking the binding "organization that authenticated == organization that is written."

### Finding Description
`repository_owner` (used to select the org whose `webhook_secret` verifies the signature) is derived as:
```ruby
params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
``` [4](#0-3) 

That value is passed to `Shipit.github(organization: repository_owner)` to pick the correct `GitHubApp`/`webhook_secret` for HMAC verification [5](#0-4) .

Meanwhile, `MembershipHandler#find_or_create_team!` uses `params.organization.login` (a *different* JSON key, only required to exist as `organization.login`, independent of `repository.owner.login`) to create/find a `Team` and grants/revokes membership for the specified GitHub user login [6](#0-5) .

Because signature verification is keyed off `repository.owner.login` while the actual write (`Team.organization`, `Membership` creation) is keyed off `organization.login`, an attacker who legitimately controls one small/low-trust GitHub organization onboarded to the same Shipit instance (and therefore knows or can compute a valid signature using that org's `webhook_secret`) can craft a single webhook POST where:
- `repository.owner.login = "orgA"` (the attacker's own org, satisfies signature verification)
- `organization.login = "orgB"` (a victim org actually used for authorization)
- `team = { id, slug, name, url }` matching a team referenced in `Shipit.github_teams` (the `oauth.teams` config used to gate application access)
- `member.login = <attacker's GitHub login>`
- `action = "added"`

The `X-Hub-Signature` header is computed over the raw JSON body using orgA's secret, which the controller validates successfully via `Shipit.github(organization: 'orgA').verify_webhook_signature` [5](#0-4) . The request then reaches `MembershipHandler#process`, which creates/updates a `Team` scoped to `orgB` and adds the attacker's GitHub user to it as a member, entirely disregarding which org's secret actually authenticated the request [2](#0-1) .

`Shipit.github_teams` (built from `oauth.teams` config) is exactly what gates access to the whole application via `User#authorized?`:
```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
``` [7](#0-6)  and enforced in `force_github_authentication` [8](#0-7) . If the forged team/org corresponds to a team listed in `Shipit.github_teams`, the attacker's `User` row (created on first GitHub OAuth login, matched purely by GitHub login) is now a `Membership` of that `Team`, satisfying `authorized?` without ever being a real member of `orgB` on GitHub.

### Impact Explanation
This breaks the deployment-trust binding "the organization whose credential authenticated the webhook request" versus "the organization whose data (team membership) is actually written." It allows an attacker who only controls a peripheral, low-value GitHub organization/webhook_secret in a multi-org Shipit deployment to forge team membership records for an unrelated (target) organization, and thereby escalate into `Shipit.github_teams` authorization — one of the explicitly listed High-severity impacts ("escalation into `Shipit.github_teams` authorization"). Once authorized, the attacker gains full access to the Shipit UI/API for all stacks, including creating `ApiClient`s with `deploy:stack`/`write:stack` permissions, triggering deploys, and reading task output — well beyond the org they legitimately control.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with the documented multi-organization `github:` config (a supported and documented setup, not a misconfiguration) [3](#0-2) ; (2) the attacker legitimately administers/controls at least one of the configured GitHub orgs (or otherwise knows its `webhook_secret`); (3) `Shipit.github_teams` (oauth.teams) is configured to restrict access, which is the primary use case for that setting. This is a realistic scenario for shared/multi-tenant Shipit deployments where different orgs share one Shipit instance but are not meant to trust each other.

### Recommendation
- Derive the organization used for signature verification and the organization used by every webhook handler (including `MembershipHandler`) from the *same* trusted field, and cross-check them: reject any payload where `organization.login` (or any org-like field consumed by a handler) does not match the `repository_owner`/org that successfully verified the signature.
- In `MembershipHandler` (and any other handler that writes org-scoped data), explicitly verify that `params.organization.login` equals the organization whose `webhook_secret` was used to authenticate the request, rejecting the event otherwise.
- Consider scoping each configured GitHub App's webhook endpoint/secret strictly to events for that same organization at the controller level, rather than trusting attacker-controlled JSON fields to select both the verifying secret and the write target independently.

### Proof of Concept
Preconditions: Shipit configured with `github: { orgA: {webhook_secret: SECRET_A, oauth: {teams: ["orgB/admins"]}}, orgB: {webhook_secret: SECRET_B} }` (attacker controls orgA and knows `SECRET_A`; `orgB/admins` gates app access).

```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, body)>

body = {
  "action": "added",
  "team": { "id": 999, "name": "Admins", "slug": "admins", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "orgB" },
  "member": { "login": "attacker-gh-login" },
  "repository": { "owner": { "login": "orgA" } }
}
```

1. `verify_signature` computes `repository_owner = "orgA"`, loads `Shipit.github(organization: "orgA")`, and validates the signature against `SECRET_A` — passes.
2. `MembershipHandler#process` runs with `params.organization.login = "orgB"`, creating/finding `Team(organization: "orgB", slug: "admins")` and adding `attacker-gh-login` as a member.
3. Attacker logs into Shipit via GitHub OAuth with `attacker-gh-login`; `User#authorized?` finds their new `Membership` in the `orgB/admins` team (which is in `Shipit.github_teams`) and grants access to the whole application, bypassing the intended org/team restriction.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?

          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')

        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
