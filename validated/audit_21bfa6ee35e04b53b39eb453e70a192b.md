## Title
Webhook signature is verified against an attacker-controlled organization while `StatusHandler` writes to commits chosen only by a payload `sha` with no repository/organization ownership check - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The 2021-04-meebits report shows a value used to produce an outcome (`randomIndex()`) that is never bound to what the attacker actually committed to (the mint payment), letting the attacker pick a favorable outcome for free. The structural analog here is a **binding mismatch inside the webhook trust boundary**: the field used to select *which organization's secret verifies the signature* is not the same field used to select *which record the event handler writes to*.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization from the JSON body itself, then verifies the raw body's HMAC against that organization's `webhook_secret`: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` itself only proves the raw bytes were HMAC-signed with *some* organization's secret — it says nothing about which repository/records the body's other fields should be trusted to describe: [3](#0-2) 

Shipit is multi-tenant: `Shipit.github(organization: ...)` resolves to whichever GitHub App/org config matches `repository_owner`. Any user who has installed their own GitHub App integration for their own organization in this Shipit instance legitimately knows that organization's `webhook_secret` (they configured it). Nothing stops them from crafting an arbitrary JSON body, signing it with their own org's secret, and setting `repository.owner.login` to their own org (so `verify_signature` passes) while every *other* field in the body is fully attacker-controlled.

`Webhooks::Handlers::StatusHandler`, which handles GitHub `status` events, does not re-derive or check the repository/organization at all — it looks up commits **globally by `sha`**, with no scoping to the organization that was actually authenticated: [4](#0-3) 

Contrast this with `PushHandler`, which at least re-derives a `repository_name`/`stacks` scope from `repository.full_name` via `Handler#stacks`: [5](#0-4) 

`StatusHandler` uses no such scoping — the binding "organization whose secret authenticated this request" is never checked against "repository owning the commit being written."

### Impact Explanation
An attacker who only controls their own org's GitHub App integration (no access to the victim's webhook secret, repo, or a Shipit session/API token) can forge a `status` webhook event carrying any `sha` value and any `state`/`description`/`target_url`/`context`. If that `sha` matches a commit belonging to a *different* stack/repository (e.g. a PR head commit on a repo with merge-queue automation enabled), `Commit#create_status_from_github!` will create a fabricated `Status` for that unrelated commit's stack. Because `Stack#allows_merges?` gates automatic merging on `merge_status == 'success'` (driven by these same `Status`/`commit_status` records), an attacker could inject a fabricated "success" status onto a victim's PR commit and cause the merge-queue automation to merge a PR that never actually passed CI — an unauthorized merge triggered purely by forging a webhook that is authenticated under the attacker's own, unrelated organization.

### Likelihood Explanation
Requires: (1) the target Shipit instance be configured for more than one GitHub organization (multi-tenant), (2) the attacker be an admin of one such configured org (which they can be, since they only need to install their own GitHub App), and (3) knowledge of a target commit `sha` on a merge-queue-enabled stack (obtainable by watching the victim's public/private repo activity via any legitimate access, e.g., viewing the PR). No repository write access, Shipit session, or `ApiClient` token is required, matching the "unprivileged attacker" premise of the rules.

### Recommendation
Bind the verified organization to the record being mutated: after `verify_signature` succeeds, every handler must derive the acted-upon `Repository`/`Stack` from the same `repository.owner.login`/`full_name` pair that authenticated the request, and refuse to act if the commit/stack's owning repository does not match the authenticated organization. `StatusHandler` in particular must scope `Commit.where(sha: ...)` to commits belonging to the authenticated organization's repositories only.

### Proof of Concept
1. Attacker registers/configures their own GitHub App for `attacker-org` in the multi-tenant Shipit instance and knows its `webhook_secret`.
2. Attacker observes a victim's public PR head commit sha `abc123` on `victim-org/victim-repo`, a stack with `merge_queue_enabled: true`.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/anything"},
  "sha": "abc123",
  "state": "success",
  "context": "ci/forged",
  "description": "forged",
  "target_url": "https://example.com"
}
```
signed with `attacker-org`'s webhook secret via `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner => "attacker-org"`, fetches `attacker-org`'s `webhook_secret`, and the signature validates — see [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: "abc123")` (no repo check) and calls `create_status_from_github!`, writing a fabricated success status onto the victim's commit — see [4](#0-3) .
6. If `victim-org/victim-repo`'s merge queue relies on this status, the PR can be auto-merged based on the forged status.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
