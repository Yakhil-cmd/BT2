### Title
Webhook organization used for signature verification is decoupled from the repository actually mutated, enabling cross-tenant forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) [2](#0-1) . Every event handler, however, resolves the target `Repository`/`Stack` from a *different* JSON field: `payload.dig('repository', 'full_name')` [3](#0-2) . Because these are two independently attacker-controlled fields inside the same unsigned-until-verified JSON body, nothing binds "the organization whose secret validated this request" to "the repository whose stacks this request will mutate."

### Finding Description
In a multi-tenant Shipit deployment, `Shipit.github(organization:)` looks up a per-organization config block (each with its own `app_id`, `private_key`, and `webhook_secret`) from `secrets.github` [1](#0-0) . `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)` [4](#0-3) . `verify_webhook_signature` is a plain HMAC-SHA1 comparison against `webhook_secret` for the resolved organization [5](#0-4) .

The organization used for secret selection (`repository.owner.login`) and the repository used for the actual mutation (`repository.full_name`) are read from the same untrusted, attacker-supplied JSON body but are two unrelated keys. An operator of *any one* tenant organization configured in this Shipit instance knows their own `webhook_secret` (it is the value they configured in their own GitHub App settings). That operator can POST directly to `/webhooks` (bypassing GitHub entirely — no other authentication is required, `verify_authenticity_token` is explicitly skipped [6](#0-5) ) with a forged payload where `repository.owner.login = "attacker-org"` (so `verify_signature` validates the HMAC against the attacker's own known secret) but `repository.full_name = "victim-org/victim-repo"` (so the dispatched handler operates on a completely different tenant's stacks).

This breaks the equality the deployment-trust model relies on: `organization authenticated == organization whose repository is written`. Handlers such as `PushHandler` would then call `stack.sync_github(expected_head_sha: params.after)` on a victim stack using attacker-chosen `ref`/`after` values [7](#0-6) , and `PullRequest::OpenedHandler`/`ClosedHandler`/`ReopenedHandler` similarly resolve `Repository.from_github_repo_name(params.repository.full_name)` to provision, archive, or unarchive review stacks belonging to the victim organization [8](#0-7) [9](#0-8) .

### Impact Explanation
This lets an attacker who legitimately controls one tenant/organization inside a shared multi-org Shipit instance forge webhook events that are processed as if targeting a *different* organization's repositories/stacks, without ever needing that victim organization's webhook secret. Depending on the handler reached, this can trigger unauthorized sync (`sync_github`), archive/unarchive of review stacks, or status/check-run manipulation on a repository the attacker does not control — a cross-tenant integrity break analogous to "cross-repository writes."

### Likelihood Explanation
Requires a genuinely multi-tenant Shipit deployment (multiple `secrets.github` organization blocks), which is an explicitly supported configuration shape (`github_default_organization`, `github_app_config`) [10](#0-9) . The attacker only needs to be an authorized administrator of *any one* of the configured organizations (i.e., know that org's own webhook secret) — no access to the victim org, no Shipit session, and no `ApiClient` token is required, since the webhook endpoint is unauthenticated aside from the HMAC check.

### Recommendation
Bind the two lookups together: derive the repository/stack scope used by handlers from the same trust-checked field used for signature verification (e.g., verify against the organization derived from `repository.full_name`'s owner segment, or reject the payload if `repository.owner.login` does not match the owner portion of `repository.full_name`). Alternatively, after verifying the signature for organization `O`, restrict `Repository.from_github_repo_name` lookups to repositories whose owner is `O`.

### Proof of Concept
1. Multi-tenant Shipit instance configured with two GitHub organizations: `attacker-org` (attacker is a legitimate admin, knows `webhook_secret_A`) and `victim-org` (unrelated tenant).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, raw_body)` and POSTs directly to the engine's `/webhooks` endpoint with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` → `"attacker-org"`, loads `webhook_secret_A`, and the HMAC validates successfully [4](#0-3) .
5. `PushHandler#process` resolves `stacks` from `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` [3](#0-2) , and calls `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` on the victim's stack [11](#0-10) , despite the request only being authenticated as `attacker-org`.

    # nil signifies the single github app config schema is being used

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
