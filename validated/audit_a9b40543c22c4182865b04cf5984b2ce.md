### Title
CCMenu API endpoint bypasses per-token stack scoping, allowing cross-stack disclosure of build status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack directly with `Stack.from_param!(params[:stack_id])`, instead of going through the scoped `stacks` collection that every other API controller uses. This mirrors the MIPS report's pattern of a "value acted on but never covered by the binding that is supposed to constrain it" — here the binding broken is "a stack a token authorizes" (`ApiClient#stack_id`) versus "a stack it touches" (any `stack_id` param, unscoped).

### Finding Description
`Shipit::Api::BaseController` establishes the authorization binding between an `ApiClient` and the stack(s) it may act on: [1](#0-0) 

`stacks` returns only the client's authorized stack when `current_api_client.stack_id?` is true; `stack` (used by `StacksController`, `TasksController`, etc.) is always derived from this scoped collection, e.g.: [2](#0-1) 

`CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [3](#0-2) 

The `require_permission :read, :stack` before_action only checks that the token's `permissions` array contains `"read:stack"` — it never checks that the requested `stack_id` matches the client's authorized `stack_id`: [4](#0-3) 

Meanwhile, tokens for this exact endpoint are minted by `CCMenuUrlController` scoped to one specific stack via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, with the `stack` association set from the current stack in scope: [5](#0-4) 

The binding that should hold is:
`ApiClient#stack_id == stack_id used to authorize the request == stack whose data is rendered`

After the fix it should equal; as implemented, `CCMenuController#stack` breaks the third equality by re-resolving the stack purely from `params[:stack_id]`, ignoring `ApiClient#stack_id`.

### Impact Explanation
Any holder of a valid CCMenu token (created legitimately for Stack A, which the requester was authorized to view at token-creation time) can query `GET /api/:stack_id/ccmenu.xml?token=...` for an arbitrary `stack_id` belonging to any other stack in the Shipit instance and receive that stack's build status, last build label, activity, and lock state — all without ever being authorized on that other stack. This is an unauthenticated (relative to the target stack) read of stack state, matching the "unauthenticated read of stack state" High-impact category, since the token's authorization was scoped to one stack but the code path touches whichever stack ID is supplied.

### Likelihood Explanation
Exploitation only requires possession of any valid CCMenu token (which is a low-privilege, easily obtainable `read:stack`-only token created automatically by `CCMenuUrlController#fetch` for any stack a user can view) and knowledge/guessing of another stack's `to_param` (repo/environment slug or numeric ID, both discoverable/enumerable). No signature forgery, no elevated credentials, and no interaction with the token-issuing stack are needed — only a crafted request path. This is straightforward to trigger by any authenticated Shipit user who has been issued a CCMenu token for at least one stack.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped collection like every other API controller:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
where `stacks` is inherited from `BaseController` and respects `current_api_client.stack_id?`. This restores the equality between the stack an `ApiClient` is authorized for and the stack whose data is served.

### Proof of Concept
1. As User A, visit Stack A's CCMenu URL page, triggering `CCMenuUrlController#fetch`, which creates/reuses an `ApiClient` scoped to `stack_id: StackA.id` with `permissions: ["read:stack"]`, and returns a URL like `/api/stack-a-slug/ccmenu.xml?token=<tokenA>`.
2. Confirm the token is scoped: `ApiClient.find_by(name: 'CCMenu Client', creator: userA).stack_id == StackA.id`.
3. As an attacker holding `tokenA` (e.g., leaked via browser history, logs, or shared link — the token is embedded in a bookmarkable URL), request a different, private stack B: `GET /api/stack-b-slug/ccmenu.xml?token=<tokenA>`.
4. `authenticate_api_client` (overridden in `CCMenuController`) accepts `tokenA` via `ApiClient.authenticate(params[:token])`, `require_permission :read, :stack` passes because `tokenA`'s permissions array contains `"read:stack"` (no stack-id comparison), and `stack` resolves Stack B directly via `Stack.from_param!(params[:stack_id])`, bypassing the `stack_id` scope. The response renders Stack B's build status (`lastBuildStatus`, `lastBuildLabel`, `activity`) even though `tokenA` was only ever authorized for Stack A.

Note: I was unable to fully verify from the index alone whether any additional route-level constraint (e.g., in `config/routes.rb`) restricts `stack_id` to the creating client outside the controller — based on the code reviewed, no such constraint exists, but a full confirmation would benefit from exercising the actual routes/test suite in a Devin session.

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])

    end

    end
  end
