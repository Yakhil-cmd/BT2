### Title
Unguarded division-by-zero in Alpenglow voting reward calculation when epoch total stake is zero - (File: `runtime/src/block_component_processor/vote_reward.rs`)

### Summary
The Alpenglow voting-reward path computes each validator's per-slot Lamport reward with `total_stake_lamports` (the epoch's total active stake) as part of the division denominator, without ever guarding against that value being zero. This mirrors the C4 finding's root cause — a denominator derived from a caller-influenced aggregate (`totalSupply` there, `total_stake` here) that unprivileged actors (stakers) can drive toward zero, causing a division-by-zero panic in reward code that every validator executes deterministically.

### Finding Description
`calculate_reward` builds the reward denominator directly from `epoch_state.slots_per_epoch` and the caller-supplied `total_stake_lamports`, then performs an unchecked `numerator / denominator` division: [1](#0-0) 

`total_stake_lamports` is populated straight from `EpochStakes::total_stake()` with no non-zero check anywhere along the call path: [2](#0-1) [3](#0-2) 

`total_stake` itself is a plain `u64` accumulated by summing every vote account's delegated stake for the epoch, with no floor enforced: [4](#0-3) 

Notably, other reward/points computations in the same codebase already defend against this exact class of bug by explicitly checking for a zero stake denominator before dividing — `calculate_block_reward` returns `0` when `total_active_stake == 0`, and `calculate_alpenglow_points` uses `.filter(|stake| *stake != 0)` and returns an error path instead of dividing: [5](#0-4) [6](#0-5) 

`calculate_reward` in `vote_reward.rs` is the outlier that omits this guard, so if `total_stake_lamports` for the rewarded epoch is ever `0`, the `numerator / denominator` integer division panics (Rust panics on division by zero rather than saturating or returning an error).

### Impact Explanation
Because reward crediting via `RewardState::calculate_reward` / `update_account` runs as part of deterministic bank/block processing for every validator, a panic here is not merely a single-node crash — it is a consensus-breaking, cluster-wide halt at that slot/epoch boundary, since every node executing the same block will hit the identical panic. This falls squarely in the "epoch-boundary halt" impact category.

### Likelihood Explanation
Reaching `total_stake_lamports == 0` requires essentially all delegated stake for the epoch to be withdrawn/deactivated by stakers (unprivileged users) before the reward-computation slot for that epoch is processed — directly analogous to "everybody burns their shares" in the original report. On a large, decentralized mainnet-class cluster this is very unlikely, but it is a realistic failure mode for smaller clusters (e.g., testnets, private/permissioned deployments, or a cluster nearing complete stake exit) where the total active stake set is small and can plausibly reach zero, and nothing in the code path prevents it from being computed and dividing by it.

### Recommendation
Add an explicit zero-check on `total_stake_lamports` in `calculate_reward` (mirroring the guard already used in `calculate_block_reward` and `calculate_alpenglow_points`), short-circuiting to `(0, 0)` rewards when total stake is zero, rather than allowing an unchecked integer division to panic.

### Proof of Concept
1. Drive an epoch's `EpochStakes::total_stake()` to `0` by having stakers deactivate all delegated stake before the reward-calculation slot for that epoch executes (see `parse_epoch_vote_accounts`, which sums delegated stake with no minimum floor: [4](#0-3) ).
2. When `RewardState::try_new`/`calculate_reward` subsequently processes a reward slot for that epoch, `total_stake` (`self.total_stake`) is passed unchecked into `calculate_reward` ( [3](#0-2) ).
3. Inside `calculate_reward`, `denominator = slots_per_epoch as u128 * total_stake_lamports as u128` evaluates to `0`, and `numerator / denominator` panics with "attempt to divide by zero" ( [1](#0-0) ), crashing every validator processing that block deterministically.

        let mut total_stake: u64 = 0;

        for (key, (stake, account)) in epoch_vote_accounts.iter() {
            total_stake += *stake;

            if *stake == 0 {

            if let Some(authorized_voter) = vote_state.get_authorized_voter(leader_schedule_epoch) {
                let node_vote_accounts = node_id_to_vote_accounts
                    .entry(*vote_state.node_pubkey())
                    .or_default();

                node_vote_accounts.total_stake += stake;
                node_vote_accounts.vote_accounts.push(*key);

                epoch_authorized_voters.insert(*key, *authorized_voter);
            }
        }

        (
            total_stake,
            node_id_to_vote_accounts,
            epoch_authorized_voters,
        )
