### Title
Webhook signature is verified against an attacker-chosen organization while the write path targets a repository from a different, unvalidated payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/webhook secret to validate an incoming webhook against using `repository_owner`, a value taken directly from the untrusted, unauthenticated JSON body. The event handlers that actually perform writes (create commit statuses, sync commits, merge/archive stacks, etc.) resolve the target `Repository`/`Stack` from a *different* field of that same body (`repository.full_name`, or `sha`/`branches` with no repository scoping at all in `StatusHandler`). Because the field used to pick the authenticating secret is never cross-checked against the field(s) used to select the record being mutated, an attacker who controls (or can trigger) a webhook for one organization/repo can make Shipit act on data belonging to a completely different stack, as long as signature verification passes for the org they choose.

### Finding Description
The controller's authentication step is:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This picks the `webhook_secret` to verify against purely from `repository.owner.login` inside the JSON body the request itself supplied — a field that is not authenticated until *after* this very check runs. `GitHubApp#verify_webhook_signature` further weakens this: if the chosen organization's `webhook_secret` is blank/not configured, verification is skipped entirely and returns `true`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

Shipit explicitly supports multiple GitHub organizations sharing one instance, each with its own independently configured `webhook_secret`: [3](#0-2) 

Once the signature check passes (using the secret selected by `repository.owner.login`), `WebhooksController#create` dispatches to handlers using the raw, still-unvalidated `params` hash:

`StatusHandler` is even less scoped: it doesn't use `repository` at all, and mutates any commit in the database matching the attacker-supplied `sha`, across all stacks:
```ruby

    commit.create_status_from_github!(params)

``` [6](#0-5) 

Writing a forged commit status can flip a commit's CI state, which directly drives the merge queue (`MergeRequest::StatusChecker`, `stack.schedule_merges`) and continuous-deployment triggers: [7](#0-6) [8](#0-7) 

**The binding that should hold:** "the organization whose secret authenticated this webhook" == "the organization/repository whose records are written by this webhook." Instead: `repository_owner` (used to pick the verifying secret) and `repository.full_name` / `sha` (used to pick the mutated `Stack`/`Commit`) are two independent, attacker-controlled fields in the same unauthenticated JSON body, with no cross-validation between them.

### Impact Explanation
If any organization configured on the Shipit instance has no `webhook_secret` set (explicitly optional/`nil` per `config/secrets.development.example.yml` and `docs/setup.md`), or if its secret is otherwise known/guessable, an attacker can craft a payload with `repository.owner.login` set to that weakly/unprotected organization (so `verify_webhook_signature` returns `true` trivially) while setting `repository.full_name` (or, for `status` events, just `sha`) to reference a stack belonging to a *different, properly-secured* organization. This lets an unprivileged external actor:
- Forge commit statuses/CI results for arbitrary stacks across organizations, which can flip merge-queue gating (`reject_unless_mergeable!`, `any_status_checks_missing?`/`failed?`) and continuous-deployment triggers, leading to an unauthorized deploy or merge condition being satisfied.
- Trigger `GithubSyncJob`/other handler-side effects against a stack that is not associated with the organization that "authenticated" the request.

This crosses the "repository written vs. organization authenticated" boundary called out as in-scope, and its downstream effect (forged status feeding the merge queue / CD) lands in the High-impact bucket ("escalation into `Shipit.github_teams` authorization" adjacent trust decisions and unauthorized ship/merge conditions).

### Likelihood Explanation
Exploitability depends on the deployment having at least one configured organization with a blank/leaked `webhook_secret` while another organization's stacks are the actual target — this is a realistic misconfiguration explicitly enabled by the documented multi-org feature (test/dev configs ship with `webhook_secret: # nil` by default). Given that setup, the attack requires no credentials at all: a single unauthenticated POST to `/webhooks` with a crafted JSON body.

### Recommendation
Do not let any field inside the unauthenticated request body determine trust. Concretely:
1. Verify the webhook signature independently for every configured `Shipit.github_organizations`, or bind the raw request to a specific, pre-registered secret per delivery endpoint, rather than selecting the secret using `repository.owner.login`/`organization.login` read from the same untrusted body.
2. After successful signature verification, re-validate that the repository/organization the signature was verified for matches the repository/organization that handlers subsequently act upon (`repository.full_name`, and `sha`→commit→stack resolution in `StatusHandler`) before performing any write.
3. Treat `webhook_secret: nil` as "this organization's webhooks are unauthenticated" and either forbid mixing an unauthenticated org with authenticated orgs on the same instance, or scope unauthenticated orgs' webhook processing so it can never affect other organizations' stacks.

### Proof of Concept
Conceptual PoC (cannot be executed here, but derivable directly from the cited code):
1. Configure Shipit with two organizations: `SecureOrg` (has `webhook_secret` set) and `OpenOrg` (no `webhook_secret` configured — a supported, documented configuration).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "OpenOrg" }, "full_name": "OpenOrg/some-repo" },
  "sha": "<sha of a commit belonging to a SecureOrg-owned stack>",
  "state": "success",
  "context": "ci/forged"
}
```
No `X-Hub-Signature` needed, or any value, since `Shipit.github(organization: "OpenOrg").verify_webhook_signature` returns `true` unconditionally (`webhook_secret` blank).
3. `WebhooksController#create` dispatches to `StatusHandler#process`, which runs `Commit.where(sha: params.sha)` — matching the commit in `SecureOrg`'s stack regardless of `repository.full_name` — and calls `commit.create_status_from_github!`, forging a success status on a commit that belongs to a different, properly-secured organization's stack.
4. This forged status can flip `Commit#status`, trigger `stack.schedule_merges`, and satisfy merge-queue/CD checks (`app/models/shipit/commit.rb:379-384`, `app/models/shipit/merge_request.rb:14-39`) for a stack the attacker never authenticated against. [9](#0-8) [10](#0-9) [2](#0-1)

# frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
