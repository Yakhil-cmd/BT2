### Title
Webhook authentication binds to `repository.owner.login`, but event handlers act on the independently-parsed `repository.full_name` - a per-organization webhook_secret can be bypassed to write into a different, protected organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` config (and thus the HMAC secret) to validate a webhook against using `repository_owner`, which is read straight out of the untrusted JSON payload (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). [1](#0-0) [2](#0-1)  Every event handler, however, resolves the actual `Repository`/`Stack` to act on using a *different* field parsed independently from the same payload: `repository.full_name`. [3](#0-2) [4](#0-3)  Nothing ties these two fields together, and `GitHubApp#verify_webhook_signature` explicitly disables signature verification whenever the resolved organization has no `webhook_secret` configured: `return true unless webhook_secret`. [5](#0-4) 

### Finding Description
Shipit supports hosting multiple GitHub organizations from a single instance, each with its own independent config block (`app_id`, `installation_id`, `webhook_secret`, etc.), as shown in the multi-org secrets fixture. [6](#0-5)  `Shipit.github(organization:)` looks up the config purely by organization name, defaulting to an unauthenticated bypass (`return true unless webhook_secret`) when that particular organization's `webhook_secret` is blank — and the setup docs explicitly describe `webhook_secret` as optional. [7](#0-6) [8](#0-7) 

The binding that should hold is: `organization authenticated by verify_signature == organization owning the repository the handler writes to`. In the current code that equality is never enforced. `WebhooksController#verify_signature` picks the signing organization from `repository.owner.login` and, if that specific organization has no `webhook_secret`, accepts the request unconditionally regardless of the (attacker-supplied) `X-Hub-Signature` header. [1](#0-0)  The handlers that then execute (`PushHandler`, `StatusHandler`, `PullRequest::*Handler`, etc.) ignore `repository.owner.login` entirely and instead resolve the target repository/stack from `repository.full_name` via `Repository.from_github_repo_name`, which performs a bare owner/name lookup with no cross-check against the authenticated organization. [9](#0-8) [3](#0-2) 

Because the JSON request body is entirely attacker-controlled when POSTed directly to `/webhooks` (there is no requirement that `repository.owner.login` and `repository.full_name` reference the same org/repo), an attacker can craft a payload where:
- `repository.owner.login` = an organization configured in Shipit **without** a `webhook_secret` (satisfies `verify_signature` unconditionally, no valid GitHub signature needed).
- `repository.full_name` = `"<other-protected-org>/<repo>"`, i.e., a repository belonging to a *different*, fully-secured organization that does have `stacks` configured.

The request passes `verify_signature` because the selected `GitHubApp` for the spoofed owner has no secret, then the dispatched handler (e.g. `PushHandler`) resolves the real target stack via `full_name` and calls `stack.sync_github(expected_head_sha: params.after)`, or other handlers archive/unarchive review stacks, create statuses, etc. — all against a repository in an organization the attacker never authenticated for. [10](#0-9) 

### Impact Explanation
This breaks the "organization that authenticated versus repository that is written" trust binding without needing any credential, GitHub webhook secret, repository access, or Shipit session — the attacker only needs Shipit configured for at least two organizations where one lacks a `webhook_secret` (an explicitly documented, supported, optional configuration). The attacker can trigger `GithubSyncJob` (via `PushHandler`) and status/PR-state mutations (`StatusHandler`, `PullRequest::*Handler`) against a stack belonging to an organization they have no relationship with, causing unauthorized sync/deploy-triggering actions and state manipulation on that stack — a cross-organization write into deployment state that should require that specific org's own webhook credential.

### Likelihood Explanation
Exploitability is entirely conditioned on the deployment having at least one organization configured without a `webhook_secret`. This is documented as "optional" in the setup guide, and the multi-org config fixture in the codebase explicitly demonstrates an org with `webhook_secret: # nil` coexisting with organizations that do set one. [8](#0-7) [6](#0-5)  Where that condition holds, no credentials or special access are required — a single unauthenticated POST to `/webhooks` with a forged JSON body suffices.

### Recommendation
In `WebhooksController#verify_signature`, ensure the organization used to select the signing secret is the same organization that owns the repository the dispatched handler will act on — e.g., derive both from `repository.full_name` (single source), or explicitly validate that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatching. Additionally, reconsider `GitHubApp#verify_webhook_signature`'s fallback of `return true unless webhook_secret`; treating a missing secret as "verification passed" is unsafe for multi-org deployments where sibling organizations do enforce a secret, and should at minimum require a secret whenever the Shipit instance hosts more than one organization.

### Proof of Concept
Preconditions: Shipit configured for two organizations, `unsecured-org` (no `webhook_secret`) and `secured-org` (has `webhook_secret`), with `secured-org/target-repo` mapped to an active `Stack`.

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json
(no valid X-Hub-Signature required)

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "secured-org/target-repo"
  }
}
```
- `WebhooksController#verify_signature` computes `repository_owner = "unsecured-org"`, fetches that org's `GitHubApp`, and `verify_webhook_signature` returns `true` unconditionally because `unsecured-org` has no `webhook_secret`. [1](#0-0) [5](#0-4) 
- `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("secured-org/target-repo")` (from `repository.full_name`) and enqueues `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on that stack — despite the request never having been authenticated for `secured-org`. [3](#0-2) [10](#0-9)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
