## Analysis

This confirms a multi-tenant binding break analogous to the sequencer-status bug: a value used to authenticate a request (`repository_owner`/`organization.login`, which selects the per-organization `webhook_secret`) is never checked against the value that the resulting handlers actually act on (`repository.full_name`), which is only covered by `ExplicitParameters` type validation, not by the HMAC signature scope.

`WebhooksController#verify_signature` picks the GitHub App config solely from `params.dig('repository','owner','login') || params.dig('organization','login')` and verifies `X-Hub-Signature` against that organization's `webhook_secret`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `webhook_secret` per organization in a multi-org install (`github_app_config`/`TOP_LEVEL_GH_KEYS`), so different organizations in the same Shipit instance legitimately hold different secrets: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` forwards the *entire raw payload* to handlers, and the handler base class picks the target repository from a completely different, unauthenticated field: `payload.dig('repository', 'full_name')`: [4](#0-3) [5](#0-4) 

Nothing enforces `repository.owner.login == repository.full_name.split('/').first`. This is the exact equality break requested: "an organization that authenticated versus the repository that is written." `StatusHandler` directly persists attacker-controlled `state`/`description`/`target_url`/`context` from the payload onto any commit matching the given `sha` across the whole install: [6](#0-5) 

Because commit statuses gate CI-required checks for deploy eligibility, and the org used for signing is decoupled from the repo whose commits are updated, an attacker with legitimate control of Org A's webhook secret (any GitHub org owner who is one of the tenants configured in `secrets.yml`'s multi-org `github:` block) can forge a signed webhook whose `repository.owner.login` is `Org A` but whose `repository.full_name`/`sha` target a stack belonging to `Org B`, injecting a fabricated "success" CI status on Org B's commit and enabling an unauthorized deploy.

### Title
Webhook signature is verified against the payload's `repository.owner`/`organization` field while handlers act on the unrelated `repository.full_name`, allowing cross-organization commit-status forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate `X-Hub-Signature` using `repository.owner.login` (or `organization.login`) taken from the untrusted request body. Once verified, the full payload—including the completely independent `repository.full_name` field—is dispatched to handlers such as `StatusHandler`, which trust it to locate and mutate `Commit` records belonging to any stack, regardless of which organization's secret actually authenticated the request.

### Finding Description
Shipit supports multiple GitHub organizations in one instance, each with its own `webhook_secret` (`lib/shipit.rb#github_app_config`). The webhook signature check picks the secret using `repository_owner`, computed purely from the attacker-supplied JSON body:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This value is used only to select which secret verifies the HMAC. It is never cross-checked against `repository.full_name`, the value handlers actually use to look up the target `Repository`/`Stack`/`Commit` (`Handler#repository_name` / `StatusHandler#process`). A payload can therefore declare `organization.login = "org-a"` (satisfying the signature check with Org A's secret) while setting `repository.full_name = "org-b/critical-repo"` and an arbitrary `sha`, causing `StatusHandler` to write a forged CI status onto a commit that belongs to a totally different, unrelated organization/stack.

### Impact Explanation
Commit statuses gate `ci.require` checks that block or allow deploys and merges in Shipit. An attacker who legitimately controls the webhook secret for one tenant organization configured on the same Shipit instance (e.g., they are an org admin who can view/rotate their own GitHub App's webhook secret) can forge signed webhooks that pass Shipit's signature check yet manipulate CI status, pull-request, or push-triggered sync state for a *different* organization's stacks hosted on the same instance. This can be used to mark failing/unreviewed commits as CI-passing, satisfying deploy-gating logic and leading to an unauthorized deploy on another tenant's stack — meeting the "unauthorized deploy" bar.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (documented, supported configuration — `config/secrets.development.shopify.yml`, `docs/setup.md` multi-org examples) where the attacker is a legitimate but low-privilege tenant admin for one org and targets another org sharing the same instance. No repository write access, GitHub App private key, or `ApiClient` token is required — only the ability to know/derive their own org's `webhook_secret` and POST directly to the public `/webhooks` endpoint.

### Recommendation
After signature verification, re-derive the organization from `repository.full_name` (or `organization.login`) and require it to match the organization whose secret validated the signature; reject the webhook otherwise. Handlers should never resolve the target repository from a payload field that wasn't itself covered by the same trust boundary as the signing organization.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with distinct `webhook_secret`s, both hosting stacks on the same instance (per `docs/setup.md` multi-org setup).
2. As an attacker who is an owner/admin of `org-a`'s GitHub App (thus knows `org-a`'s `webhook_secret`), craft a `status` event JSON body:
```json
{
  "sha": "<commit sha of org-b's stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/critical-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a-secret, body)>` and POST to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` as `org-a`, validates successfully against `org-a`'s secret.
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb`) updates the status on `org-b`'s commit, satisfying required CI checks and enabling an unauthorized deploy on `org-b`'s stack — despite the request never being authenticated for `org-b`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
