### Title
Signature verification keys on `repository.owner.login` while handlers act on `repository.full_name` - unauthorized cross-repository webhook writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which HMAC `webhook_secret`) to validate a webhook against using `repository_owner`, a value read straight out of the untrusted JSON body. The dispatch logic that actually determines *which* `Repository`/`Stack` gets mutated instead reads a different, independently-attacker-controlled field, `repository.full_name`. Since HMAC verification only proves "this body was signed with organization X's secret", not "this body's `repository.full_name` belongs to organization X", an attacker who legitimately controls one tenant organization in a multi-org Shipit deployment can forge a correctly-signed webhook whose `repository.owner.login` matches their own org (so it authenticates) while `repository.full_name` names a repository belonging to a different, victim organization.

### Finding Description
`verify_signature` computes the app/secret to check against solely from `repository_owner`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (`webhook_secret`, app id, etc.) from `secrets.github`, confirming this engine supports multiple independently-configured GitHub organizations sharing one Shipit instance: [3](#0-2) 

Once the signature is accepted, `create` dispatches the *raw, unvalidated* JSON body to every registered handler for the event, with no re-check that the payload's repository actually belongs to the organization that produced a valid signature: [4](#0-3) 

Every handler then resolves the target `Stack`/`Repository` using a *different* JSON field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

Because `owner.login` and `full_name` are two independently attacker-supplied strings inside the same signed JSON body, nothing forces them to be consistent. An attacker who is a legitimate tenant of org `attacker-org` (with their own real `webhook_secret`) can send a body where `repository.owner.login = "attacker-org"` (so `verify_signature` selects and validates against the secret they actually know) but `repository.full_name = "victim-org/victim-repo"` (so the handler acts on a stack/repository they do not own). This breaks the intended binding "the organization that authenticated == the repository that is written."

Concretely, `StatusHandler` writes an arbitrary `Status` (`state`, `target_url`, `description`, `context`) for an arbitrary `sha` on whatever repository `full_name` names, entirely driven by the request body: [6](#0-5) 

Similarly `PushHandler` enqueues a `GithubSyncJob` keyed off `stack_id`/`expected_head_sha` derived from `repository.full_name` and `after`: [7](#0-6) 
and `Membership`/`PullRequest::OpenedHandler` resolve target repositories the same way via `Repository.from_github_repo_name`: [8](#0-7) 

### Impact Explanation
A tenant with legitimate, unprivileged webhook access to one organization on a shared Shipit instance can forge signed events that write fake commit statuses, trigger provisioning of review stacks, or enqueue sync jobs against a repository belonging to an entirely different organization it has no access to. Since Shipit's deploy/merge gating (`deployable_status`, commit statuses) can depend on these commit-status records, an attacker can inject a fabricated "success" status for an arbitrary sha on a victim stack, which is the kind of trust-boundary break this analysis targets (an unauthorized status/state write across a repository the attacker does not control), potentially contributing to an unauthorized deploy decision on the victim's stack.

### Likelihood Explanation
Requires the Shipit instance to be configured in the multi-organization `secrets.github` mode (keyed by org, each with its own `webhook_secret`), which is an explicitly supported, documented configuration in `lib/shipit.rb` (`github_app_config`, `TOP_LEVEL_GH_KEYS`). Any org admin/webhook holder for one tenant org is, by definition, unprivileged with respect to other tenants' repositories, and only needs to know or guess another tenant's `repository.full_name` (often discoverable/public) to mount the attack — no secrets from the victim org are needed.

### Recommendation
After a signature is verified for organization X, re-derive/validate that `repository.full_name`'s owner segment (and/or `repository.owner.login`) equals X before handlers are allowed to act on it, rather than trusting two independent unauthenticated fields for two different purposes. Alternatively, bind handler dispatch to `repository_owner` (the value actually covered by signature-selection logic) instead of re-parsing `full_name` separately.

### Proof of Concept
1. Deploy Shipit with multi-org config: org `attacker-org` (secret `S_A`) and org `victim-org` (secret `S_V`), both configured under `secrets.github`.
2. Attacker crafts a `status` event body:
```json
{
  "sha": "<any sha in victim repo>",
  "state": "success",
  "target_url": "http://attacker.example/fake-ci",
  "description": "forged",
  "context": "ci/forged",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker signs the raw body with `S_A` (their own legitimate secret) and sets `X-Hub-Signature`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and the signature validates successfully.
5. `create` dispatches to `StatusHandler`, which resolves the stack via `repository.full_name == "victim-org/victim-repo"` and writes the forged `Status` on the victim's commit, as demonstrated by the existing test flow at [6](#0-5) , but with `repository.owner.login` and `repository.full_name` pointing to two different organizations.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
