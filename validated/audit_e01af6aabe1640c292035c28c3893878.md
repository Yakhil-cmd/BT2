## Title
`DeploySpec::FileSystem#build_config` follows unbounded `inherit_from` path traversal outside the checkout directory - ([File: app/models/shipit/deploy_spec/file_system.rb])

## Summary
`build_config` resolves the `inherit_from` key by joining `path.dirname` with an attacker-controlled string and checking only `Pathname#exist?`, with no canonicalization or containment check against `@app_dir`. A malicious `shipit.yml` committed to a repository/PR can set `inherit_from: ../../../etc/shipit-secrets.yml` (or any relative path with `..` segments) and have that file's YAML content parsed via `SafeYAML.load` and deep-merged into the stack's deploy/task configuration.

## Finding Description
The binding the question asserts should hold is:
`inherits_from_path == a Pathname confined under @app_dir` (i.e., `inherits_from_path.to_s.start_with?(@app_dir.to_s)`).

In `app/models/shipit/deploy_spec/file_system.rb`:
```ruby
SHIPIT_CONFIG_INHERIT_FROM_KEY = "inherit_from"
def build_config(path, config_obj)
  return config_obj if config_obj.blank? || !config_obj.key?(SHIPIT_CONFIG_INHERIT_FROM_KEY)

  inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))
  if inherits_from_path.exist?
    inherits_config_obj = read_config(inherits_from_path)
    config_obj = inherits_config_obj.deep_merge(config_obj)
    path = inherits_from_path
  end

  build_config(path, config_obj)
end

def read_config(path)
  SafeYAML.load(path.read) if path.exist?
end
``` [1](#0-0) 

`path.dirname.join(...)` performs no `.cleanpath`/`.realpath` and no check that the result stays under `@app_dir`. Since `config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY)` is fully attacker-controlled (it comes straight from the repo's checked-out `shipit.yml`, loaded through `read_config` -> `SafeYAML.load(path.read)`), a value like `../../../etc/shipit-secrets.yml` or `../other-stack-checkout/shipit.yml` produces a path outside `@app_dir` that will be read and merged if it exists on the host filesystem.

However, the actual exploitability hinges on whether such a path exists on the host and whether its content is attacker-reachable/useful. The existing test suite already exercises this exact mechanism — `test/models/shipit/deploy_spec/file_system_test.rb` — with tests like `'#load_config builds proper config if inherit_from is present'` and `'#load_config builds valid config if inherit_from path is missing'`, confirming the code performs exactly the join-then-`exist?`-then-merge behavior described, with no path containment check. [2](#0-1) 

Root cause confirmed: no canonicalization/bounding of `inherits_from_path` against `@app_dir`. This part of the finding is valid as a code-level defect.

That said, I could not fully verify, given available tool budget, whether the *impact* rules to a scored severity:
- What lives on the host filesystem outside the checkout that a traversal could reach (e.g., is there truly another stack's cached shipit.yml at a discoverably-relative path, or secrets files) is host/deployment-specific and not something the engine's code guarantees exists.
- I could not confirm within this session whether `@app_dir` is a per-stack unique directory under a shared parent (e.g. `Shipit.checkouts_path/stack_id/...`), which would determine whether `../<sibling-stack>/shipit.yml` is a realistic, repeatable cross-tenant path. My searches for `checkout_path`/`git_path`/`Shipit.checkouts_path` returned matches in `lib/shipit/stack_commands.rb`, `app/models/shipit/stack.rb`, and `app/models/shipit/deploy_spec.rb`, but I ran out of iterations before reading their content to confirm the directory layout precisely.

Given the rule "Require exact file/method support and a reproducible minitest proof under `test/`" — the code-level defect (unbounded join, no containment check) is real and demonstrable purely with the existing method, independent of what happens to exist outside `@app_dir` on a given host. The impact claim (reading another stack's cached config, secrets, etc.) is plausible but its magnitude depends on host directory layout that I couldn't fully confirm.

## Impact Explanation
If a sibling directory or file reachable via `..` traversal exists and contains YAML, its contents get deep-merged into the deploy spec, and per `config_obj = inherits_config_obj.deep_merge(config_obj)` this can introduce keys like `deploy.override`/`deploy.pre` steps that end up executed as shell commands by `Command#start` (per `DeploySpec#deploy_steps` consumption downstream, not re-verified here). This maps to the "Critical - RCE on the deploy host via `Command`" category if a traversal target with attacker-influenced content is reachable, or to "unauthorized deploy" behavior. However, the actual reachable filesystem content is host-configuration-dependent, and I did not verify that any other stack's config or secrets file is placed at a fixed, predictable relative path from a victim stack's checkout in this codebase's default checkout layout.

## Likelihood Explanation
The attacker only needs to control a `shipit.yml` in their own repository/branch, which requires being an unprivileged pull-requester or fork owner — this precondition is trivially satisfiable. However, achieving *impactful* traversal requires that some file exists at a specific relative offset from the checkout root on the shared host, which is an operational/deployment detail outside this engine's code guarantee, and not something confirmed as universally true across Shipit deployments.

## Recommendation
Canonicalize `inherits_from_path` (e.g., `inherits_from_path.expand_path` or `.cleanpath`) and explicitly assert it remains a descendant of `@app_dir` (e.g., `inherits_from_path.to_s.start_with?("#{@app_dir.expand_path}/")`) before calling `read_config`; reject/ignore `inherit_from` values that escape the checkout directory.

## Proof of Concept
```ruby
test '#build_config does not follow inherit_from paths outside @app_dir' do
  Dir.mktmpdir do |root|
    app_dir = Pathname.new(root).join('checkout').tap(&:mkpath)
    outside_dir = Pathname.new(root).join('outside').tap(&:mkpath)
    outside_dir.join('secret.yml').write("deploy:\n  override:\n    - cat /etc/shadow\n")

    app_dir.join('shipit.yml').write("inherit_from: ../outside/secret.yml\ndeploy:\n  pre:\n    - noop\n")

    stack = shipit_stacks(:shipit)
    deploy_spec = Shipit::DeploySpec::FileSystem.new(app_dir, stack)

    loaded_config = deploy_spec.send(:load_config)

    # Binding under test: inherits_from_path should stay within app_dir.
    refute loaded_config["deploy"]["override"]&.include?("cat /etc/shadow"),
      "traversal outside @app_dir should not be merged into config"
  end
end
```
This asserts the equality `inherits_from_path confined under @app_dir` on both sides: before the fix, `outside/secret.yml`'s `deploy.override` entry is merged in (equality broken); after adding a containment check, it is not (equality holds).
