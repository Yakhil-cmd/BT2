### Title
Webhook signature is verified against the payload's `repository.owner.login`, while the actual write target is selected from the unrelated `repository.full_name` field, allowing cross-organization/cross-repository forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against using only `repository.owner.login` (or `organization.login`), while every webhook `Handler` resolves the actual repository/stack to mutate using the independent `repository.full_name` field. Nothing enforces that these two fields describe the same repository, so a signature that is valid for organization A can be replayed with a payload whose `full_name` points at a repository belonging to organization B, causing Shipit to act on B's stack with attacker-controlled data.

### Finding Description
`verify_signature` derives the verifying organization purely from the owner login sub-field: [1](#0-0) [2](#0-1) 

The chosen `github_app` (`Shipit.github(organization: repository_owner)`) checks the raw HMAC signature using that organization's own `webhook_secret`: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization (`return true unless webhook_secret`), and per the documented multi-org configuration format, `webhook_secret` is an optional, per-organization key — some orgs in a Shipit install may simply have it `nil`: [4](#0-3) 

Meanwhile, every event handler ignores `repository.owner.login` entirely and instead resolves the target repository/stack from `repository.full_name`: [5](#0-4) 

For example, `PushHandler` uses that repository's stacks to trigger a GitHub sync with an attacker-supplied `after` sha: [6](#0-5) 

The same pattern (`Repository.from_github_repo_name(params.repository.full_name)`) is used by the pull-request handlers to locate/mutate stacks and pull requests, e.g. `opened_handler.rb`, `labeled_handler.rb`, `closed_handler.rb`, all of which act on a repository chosen independently of the field used for authentication: [7](#0-6) 

**The broken equality**: `organization used to verify signature (repository.owner.login / organization.login)` == `organization/repository whose stack is written to (repository.full_name)`. An attacker who can obtain (or who benefits from an org with no `webhook_secret` set) a validly-signed payload for organization A can set `repository.full_name` to `"VictimOrg/victim-repo"` while keeping `repository.owner.login` (and thus the verifying app) pointed at organization A. Signature verification passes against A's secret (or trivially passes if A has no secret configured), but the handler mutates a stack belonging to a completely different organization B.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Concrete effects on a victim stack tracked by Shipit, without requiring the attacker to authenticate to, or hold any credential for, that victim organization:
- `push` events can force `stack.sync_github(expected_head_sha: ...)` with an attacker-chosen `after` sha on a stack the attacker does not own, injecting a fabricated head commit for the merge/deploy pipeline.
- `pull_request` events (opened/labeled/closed/edited) can create, archive, or mutate PR-backed review stacks and their cached GitHub pull-request metadata (labels, state) on a victim's repository.

Because Shipit's deploy eligibility and CI-status logic (`Commit#deployable?`, merge-queue processing) is driven by data synchronized through these webhook-triggered paths, this is a cross-repository, cross-organization write capability that can influence which commits are considered deployable — satisfying the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Exploitability depends on the attacker being able to produce a validly-signed payload for at least one organization configured on the Shipit instance while controlling the payload's `repository.full_name`. This is straightforward in two realistic situations documented by the engine itself:
1. Any Shipit deployment with multiple GitHub organizations configured (a documented, supported setup) where at least one org's `webhook_secret` is left blank (shown as the default in the example secrets files) — signature verification is skipped entirely for that org (`return true unless webhook_secret`), letting anyone forge a signature "for" it while targeting a different org's repository.
2. An attacker who legitimately controls a GitHub App/organization that is one of the multiple orgs configured on the shared Shipit instance can always produce validly-signed webhook deliveries for their own org, then substitute `repository.full_name` to point at another tenant's repository.

Both scenarios require no Shipit session, `ApiClient` token, or privileged GitHub access to the victim organization — only reachability of the public `/webhooks` endpoint, which is unauthenticated by design.

### Recommendation
Cross-validate that the organization used to select the verifying `webhook_secret` matches the organization embedded in `repository.full_name` (or otherwise derive the verifying app strictly from `repository.full_name`'s owner segment, not from `repository.owner.login`/`organization.login`, which can diverge). Additionally, do not silently treat a missing `webhook_secret` as "verified"; require an explicit signature bypass configuration rather than an implicit `nil`-secret default.

### Proof of Concept
1. Shipit is configured with two organizations, e.g. `AttackerOrg` (webhook_secret left blank, or attacker controls a real GitHub App installed on it) and `VictimOrg` (tracks stack `VictimOrg/victim-repo`), per the multi-org `secrets.yml` format in `docs/setup.md`.
2. Attacker crafts a `push` webhook payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "full_name": "VictimOrg/victim-repo",
       "owner": { "login": "AttackerOrg" }
     }
   }
   ```
3. Attacker computes/sends `X-Hub-Signature` using `AttackerOrg`'s `webhook_secret` (or sends no valid HMAC at all if that org's secret is unset).
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"AttackerOrg"` [2](#0-1)  and verifies successfully against `AttackerOrg`'s app/secret [1](#0-0) .
5. `PushHandler#process` resolves the target stacks via `repository.full_name = "VictimOrg/victim-repo"` [5](#0-4)  and calls `stack.sync_github(expected_head_sha: params.after)` with the attacker-chosen sha on the victim's stack [8](#0-7) .

Note: I was unable to fully inspect `Shipit.github(organization:)`'s dispatch implementation in `lib/shipit.rb` (only grep matches were retrievable, not full file contents) and the `Shipit::Webhooks::Handlers::StatusHandler` source before running out of tool calls, so the exact mechanics of organization-to-config lookup and the status-forging variant of this issue could not be fully confirmed against source and should be verified directly in a full checkout.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
