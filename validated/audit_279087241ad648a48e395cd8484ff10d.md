### Title
Insolvent accounts with debt legs whose smallest unit exceeds the collateral-backed quote can neither be liquidated nor permissionlessly cleaned, leaving permanent bad debt - (File: contracts/controller/src/positions/liquidation/math.rs)

### Summary
When an account becomes insolvent (`C < D`), the liquidation quote drops to `floor(C / (1 + base))` and every offered repayment leg is trimmed to whole debt-token units, rounding down. A leg whose kept amount rounds to zero is dropped entirely; if no leg survives, `liquidate` reverts with `InvalidPayments` and `check_bad_debt_after_liquidation` is never reached. The permissionless fallback `clean_bad_debt` additionally requires `total_collateral <= $5`. An insolvent account whose collateral sits above the $5 dust cap but whose every debt leg's smallest native unit is worth more than the backed quote therefore has no unprivileged recovery path at all: every `liquidate` reverts and `clean_bad_debt` rejects it, while the debt keeps accruing interest against supplier principal.

### Finding Description
For an insolvent account, `normalize_repayment_plan` sets `ideal_repayment_usd = min(D, floor(C / (1 + base)))` and, when the offer exceeds it, calls `process_excess_payment` with `keep_within_quote = true`, which floors each kept leg to whole token units and removes legs whose kept amount reaches zero (`contracts/controller/src/positions/liquidation/math.rs:188-205`, `math.rs:665-716`). `liquidate` then enforces `require_non_empty_payments(&result.repaid)` at `contracts/controller/src/positions/liquidation/mod.rs:66`, so an all-dropped plan aborts before any seizure, repayment, or bad-debt check.

The permissionless cleanup gate is `is_socializable_bad_debt`: `total_debt > total_collateral && total_collateral <= BAD_DEBT_USD_THRESHOLD` ($5 WAD) at `contracts/controller/src/positions/liquidation/curve.rs:25-27`, applied both inside `liquidate` (`apply.rs:301-315`) and by standalone `clean_bad_debt`. The only mechanism for collateral above $5 is the owner-only `force_socialize_bad_debt`, i.e. a privileged path.

Concretely: let the debt token have decimals `d` and price `P` per whole token. One base unit is worth `P × 10^-d` USD. If every debt leg satisfies `P × 10^-d > floor(C / (1 + base))`, the kept amount floors to zero for every leg regardless of the offered amount (larger offers are only trimmed harder), so no valid `debt_payments` vector exists. Combining with the $5 cleanup cap, the stuck region is:

```text
$5 < C  and  min over debt legs of (unit_usd_i) > floor(C / (1 + base))
```

This is reachable by any borrower: supply collateral, borrow a low-decimal, high-price debt asset (e.g. a 3-decimal token priced at $10,000/unit → one base unit ≈ $10), then let the collateral price fall until `C` lands between $5 and ~$9.52. With base bonus 5% the backed quote is `floor(6/1.05) = $5.71 < $10`, so every liquidation reverts and `clean_bad_debt` rejects `C = $6 > $5`. The test `an_insolvent_trim_drops_a_leg_whose_smallest_unit_exceeds_the_backed_quote` in `contracts/controller/tests/positions/liquidation_math.rs:857-868` confirms the plan drops the leg whole and produces a zero repayment.

Unlike the analogous Opyn scenario (where liquidation was merely unprofitable), here the protocol also lacks a `donate`-style escape: a direct token transfer to the pool is an unattributed donation that does not reduce the borrower's scaled debt, and `repay` on behalf of the account earns no bonus — a liquidator would pay face value for zero collateral. Seizure in `SeizeMode::Credit` changes nothing because the revert happens at the repayment-plan stage, before seize-mode handling.

### Impact Explanation
Protocol insolvency. The account's debt (plus compounding borrow interest) is permanently unsecured while collateral remains above the dust cap but below one debt unit; suppliers of the debt market absorb the loss only if governance eventually invokes the privileged `force_socialize_bad_debt` runbook, which writes the shortfall down onto the market's supply index. Until then, the insolvent debt inflates the book's reported backing and the gap grows with interest accrual. Each additional stuck account compounds the loss. A borrower can also deliberately engineer this state (borrow the coarse-unit asset, let collateral decay) at no cost, since their collateral is already lost.

### Likelihood Explanation
Requires a listed borrowable asset whose single base unit exceeds the collateral-backed quote of some insolvent account — realistic for low-decimals (≤3) or high-unit-price tokens, and for any token whose price appreciates sharply after the borrow (the unit value scales with price, so appreciation of the *debt* asset alone widens the stuck band from below). It also requires collateral to crash into the `$5 < C < unit_usd × (1 + base)` window, which is a normal consequence of a price shock rather than an exotic state. No privileged action, oracle manipulation, or leaked key is needed; the borrower simply takes a position that later becomes insolvent, which is the default liquidation path every market is designed around. Note the docs (`docs/explanation/threat-model.md:310-312`) acknowledge that above the dust threshold an insolvent account "may require the governed force-socialize runbook", but they do not address the case where *no liquidation offer can ever execute*, which is strictly worse than a merely unprofitable one.

### Recommendation
- Make the insolvency trim unit-aware: when `keep_within_quote` rounding would zero out every leg, either keep one base unit on the cheapest leg and let `seize_all`/`scale_seizures_to_received` proportionally reduce the collateral awarded, or permit a seizure-negative leg that the pool's excess-refund path already tolerates.
- Alternatively, extend `check_bad_debt_after_liquidation`/`clean_bad_debt` eligibility to cover accounts that are unliquidatable by construction: `total_debt > total_collateral` and `floor(C / (1 + base)) < min(unit_usd over debt legs)`, regardless of the $5 cap.
- A cheaper short-term mitigation is a permissionless `sponsor_repay`-style path that credits a third party's repayment against the debt without bonus, so adverse conditions cannot strand the obligation the way Opyn's `donate` gap did.

### Proof of Concept
1. Governance lists `COL` (7 decimals, $1, threshold 75%) and `EXP` (3 decimals, $10,000 — one base unit = $10).
2. Alice supplies 21,000 `COL` ($21,000) and borrows 2 `EXP` units ($20,000); HF ≈ 0.79·… wait, use thresholds such that HF ≥ 1 at open (e.g. supply more or borrow less); position opens healthy.
3. `COL` price crashes to ~$0.0003/unit: `C = $6.30`, `D = $20,000` → HF ≪ 1, insolvent.
4. Any liquidator calls `liquidate(liquidator, alice_id, [(EXP, 2)], SeizeMode::Transfer)`. `curve_repayment_usd = floor(6.30/1.05) = $6.00`; `process_excess_payment` keeps `floor(6.00 / 10) = 0` EXP base units on the leg → leg dropped → `repaid` is empty → revert `InvalidPayments` (`mod.rs:66`). Same for any smaller or split offer — the kept amount can never reach 1 base unit while `C/(1+base) < $10`.
5. `clean_bad_debt(alice_id)` reverts: `is_socializable_bad_debt` requires `C ≤ $5` and `C = $6.30`.
6. The account persists with $20,000+ of accruing unsecured debt; only privileged `force_socialize_bad_debt` can socialize it, writing the loss onto `EXP` suppliers. Mirrored by unit test `an_insolvent_trim_drops_a_leg_whose_smallest_unit_exceeds_the_backed_quote` and the boundary test `test_bad_debt_socialization_triggers_under_threshold`, which only passes because its collateral falls *below* $5.
