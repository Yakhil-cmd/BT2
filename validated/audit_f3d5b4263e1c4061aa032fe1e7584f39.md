### Title
Asset definer can retroactively revoke attestor trust to make a `spender_attested` counterparty's address "unattested," blocking any AA payment owed to it and forcing bounce/denial of legitimate repayments - (File: `validation.js`, `aa_composer.js`)

### Summary
Assets in ocore can be marked `spender_attested`, meaning any address that receives or spends the asset must be attested by one of the asset's currently-trusted attestors. The trusted attestor list is not immutable: the asset **definer** can publish an `asset_attestors` message at any time to replace it. Attestation validity is re-derived from the *current* attestor list rather than being permanently bound to the historical attestor set, so revoking/rotating the attestor list can retroactively invalidate a previously-attested address. If an AA (autonomous agent) implements a lending/settlement protocol that pays out a `spender_attested` asset to a counterparty (e.g., a lender being repaid), that counterparty — if it controls or colludes with the asset definer — can cause its own receiving address to become "unattested" after receiving the loan, making it impossible for the AA to ever validly pay it back. This mirrors the reported bug class: a lender-equivalent party gets itself "blacklisted" from receiving the debt asset to force the counterparty into default/loss.

### Finding Description
`readAsset()` resolves a `spender_attested` asset's attestor list by looking only at the **latest** `asset_attestors` unit for that asset: [1](#0-0) 

`filterAttestedAddresses()` then only counts an address as attested if it was attested by an attestor that is currently in that latest list: [2](#0-1) 

Only the asset **definer** may publish a new `asset_attestors` update, and the update completely replaces the trusted attestor set: [3](#0-2) 

During payment validation, every output address of a `spender_attested` asset payment is required to be currently attested, or the whole payment (and unit) is rejected: [4](#0-3) 

When an AA composes a payment in such an asset, it checks only the **sender's** balance/attestation state while building the message — it does not pre-check whether the intended **recipient** is (still) attested: [5](#0-4) 

The resulting unit is only validated at the very end, right before being saved; if validation fails (e.g., "some output addresses are not attested"), the AA response is bounced: [6](#0-5) 

Because the attestor list can be freely rotated by the definer at any later moment, an address that was validly attested when a loan/deposit was made can become "delisted" afterward simply by the definer swapping out the attestor that vouched for it. Any AA logic that must eventually pay this address back in the `spender_attested` asset (e.g., loan repayment, escrow release, reward distribution) will have every such payment rejected at validation and bounced, indefinitely, for as long as the address remains unattested under the current list — exactly analogous to an ERC20 token owner blacklisting a lender's address to block a `transferFrom` repayment.

### Impact Explanation
An AA that relies on a `spender_attested` asset for counterparty payouts (e.g., a Cooler-style lending AA denominated in such an asset) can be manipulated by the asset's definer (who may be, or collude with, the payee/"lender") to make repayment to that payee permanently invalid. This forces:
- Repeated bounced triggers whenever repayment is attempted (denial of service against a specific legitimate payment path), and/or
- Whatever default/liquidation logic the AA implements when it cannot deliver funds to the counterparty, causing the counterparty-side beneficiary to be unable to collect owed funds while the other side (e.g. a borrower posting collateral) can be pushed toward default handling, mirroring the fund-loss scenario in the referenced report. This is a fund-freezing / forced-default condition reachable purely through normal, permitted `asset_attestors` messages and AA triggers — no privileged network/node behavior required.

### Likelihood Explanation
The precondition (an asset defined with `spender_attested: true`, whose attestor list is controlled by the definer) is a standard, documented ocore asset feature, not a hypothetical extension. Any AA author who builds a lending/escrow contract on top of such an asset — or any asset issuer acting as their own attestor and later revoking their own attestor slot — can trigger this at will, at any time after receiving the initial payout, with a single ordinary `asset_attestors` unit. No race condition or unusual timing is needed.

### Recommendation
- Have AA logic that pays out attested assets pre-check, at payment time, whether the destination address is currently in `objAsset.arrAttestedAddresses` before committing to send, and implement a fallback (e.g., hold-and-claim pattern, or explicit error state) instead of relying on bounce semantics.
- Consider binding attestation validity to the attestor list version that was in force at attestation time (rather than only the latest list) so previously-valid attestations aren't retroactively invalidated by later `asset_attestors` updates, unless that is an intended trust-revocation feature — if it's intended, document clearly that AA designers must not treat "currently attested" as a stable, funds-safe precondition for counterparties.

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true` and an initial attestor list `[Att1]`.
2. `Att1` attests `Lender` address (`app: attestations`), satisfying `filterAttestedAddresses`.
3. An AA-based lending contract accepts collateral and issues/records a loan denominated in asset `A`, expecting to later pay `repay` amount of `A` back to `Lender`.
4. Before repayment, the definer (controlled by or colluding with `Lender`) publishes a new `asset_attestors` message removing `Att1` from the trusted list: [3](#0-2)  — allowed because they are the definer.
5. `storage.readAsset`'s `addAttestorsIfNecessary` now resolves the latest attestor list without `Att1`: [1](#0-0) ; `Lender`'s prior attestation from `Att1` no longer counts per `filterAttestedAddresses`: [2](#0-1) .
6. Any subsequent AA trigger attempting to repay `Lender` in asset `A` fails at `validatePaymentInputsAndOutputs` with `"some output addresses are not attested"`: [4](#0-3) , causing `aa_composer.js`'s `validateAndSaveUnit` to bounce the response: [6](#0-5) .
7. Repayment can never succeed while `Lender` remains unattested under the current list, forcing the AA into a stuck/default state to the detriment of the counterparty (e.g., borrower loses collateral or the transaction is permanently un-settleable).

			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
