### Title
`StatusHandler#process` matches commits by bare SHA across every stack/repository, letting an authenticated event for one repo mutate another repo's stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Commit` belongs to a single `Stack` (and therefore a single repository), but `StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no join or filter on `stack.repository`/`repository_owner`. Any commit row in the entire installation whose `sha` happens to equal the incoming `params.sha` gets `create_status_from_github!` applied, regardless of which repository's GitHub App/webhook secret authenticated the request.

### Finding Description
The broken binding: the code should guarantee `commit.stack.repository.owner == repository_owner_that_signed_this_request`, for every `commit` mutated by a `status` event. It does not.

Trace:
- `WebhooksController#verify_signature` only checks that the HMAC matches the webhook secret configured for `Shipit.github(organization: repository_owner)` [1](#0-0) . This proves the sender knows the org-level secret, but performs no per-repository/per-stack authorization.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no scoping by repository, stack, or `repository_owner` at all [2](#0-1) .
- `Commit belongs_to :stack` [3](#0-2) , and applying a status via `create_status_from_github!`/`add_status` triggers `stack.schedule_merges`, hook emission (`deployable_status`), and can flip a stack's ship/block state [4](#0-3) .
- Contrast with `CheckSuiteHandler`, which correctly scopes to `stacks.where(branch: ...)` before touching commits [5](#0-4) , showing the missing scoping in `StatusHandler` is an inconsistency/omission rather than an intentional design.

However, tracing the realistic exploitability further weakens the "unprivileged attacker, any org" framing in the question:
- `verify_signature` still requires a valid signature for the specific `repository_owner` GitHub organization/app configured in Shipit [6](#0-5) . An attacker with no Shipit secrets and no control over a Shipit-configured GitHub App/organization cannot produce a validly signed `status` webhook for an arbitrary `sha`/`context`/`state` of their choosing. Unknown organizations are rejected outright via `GithubOrganizationUnknown` [7](#0-6) .
- So the exploitable surface is narrower than "any internet user": it requires (a) a commit SHA collision between the victim's tracked commit and some commit reachable by CI in a repository that *is* connected to a Shipit-configured GitHub App/organization, and (b) that CI genuinely emits a `status` event with `context: github-actions` for that SHA. Practically this means same-organization repositories (which share one org-level webhook secret) that happen to reuse identical commit objects (e.g., forks sharing history, shared base/merge commits, template-generated identical first commits) are the realistic blast radius — not truly arbitrary cross-tenant/cross-organization forgery, because SHA-1 preimage/second-preimage attacks against a chosen target commit are not practically feasible, and the org-level webhook secret gate still applies.
- `review_stacks_enabled`/`allow_all` is not itself part of the missing scoping check; it only affects how easily an attacker-authored PR gets a stack auto-provisioned and how quickly that stack executes `shipit.yml`. It amplifies impact once a same-org SHA collision exists, but is not required to demonstrate the underlying scoping bug (a same-org status collision on a normal, non-review stack is sufficient to prove the missing binding).

### Impact Explanation
Within a Shipit-configured GitHub organization/app, a `status` webhook (with a valid org-level signature) for one repository's commit can flip the CI/deploy-eligibility state (`deployable_status`, `schedule_merges`) of any other stack in the installation whose `commits` table happens to contain a row with the same `sha` — a write attributed to a repository that did not itself send/authenticate that status. This can move a target stack into a shippable state it should not be in, or block a shippable commit, matching the "Critical — a payload for one repository mutating another's stack/commit" class described in the rules. It does not, however, constitute unauthenticated/cross-organization forgery, since a valid organization-scoped webhook signature is still required.

### Likelihood Explanation
Requires: (1) the attacker/CI event source to be a genuinely-signed `status` payload for an organization already configured in Shipit (`Shipit.github(organization:)`), and (2) a real SHA collision between the sending repository's commit and a commit tracked in a target stack — realistic mainly for repositories sharing git history (forks, shared base commits, template-generated identical initial commits) inside the same org, not for arbitrary chosen victims. `review_stacks_enabled: true, allow_all` further lowers the bar only for auto-provisioning of the *attacker's own* stack, not for the cross-stack SHA-collision write itself. Overall likelihood is low-to-moderate and scoped to same-organization, history-sharing repositories, rather than the "any unprivileged internet attacker vs. any victim stack" scenario in the prompt.

### Recommendation
Scope `StatusHandler#process` (and any other bare `Commit.where(sha: ...)` lookups) to commits belonging to stacks whose repository matches the authenticated `repository_owner`/`repository.full_name` from the webhook payload, e.g. `Commit.joins(:stack).merge(Stack.where(...)).where(sha: params.sha)`, mirroring the scoping already done in `CheckSuiteHandler`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status for repo A does not affect a commit with the same sha tracked by repo B's stack" do
  shared_sha = "a" * 40

  stack_a = shipit_stacks(:shipit) # repository X
  stack_b = create_stack(repository_owner: "other-owner", repository_name: "other-repo")

  commit_a = stack_a.commits.create!(sha: shared_sha, ...)
  commit_b = stack_b.commits.create!(sha: shared_sha, ...)

  params = { sha: shared_sha, state: "success", context: "github-actions" }
  # Signed/validated only for stack_a's organization
  Shipit::Webhooks::Handlers::StatusHandler.new(...).call(params.merge(repository: { full_name: stack_a.repository.full_name }))

  assert_equal "success", commit_a.reload.status.state   # expected: authenticated repo updates
  assert_not_equal "success", commit_b.reload.status.state # BUG today: commit_b is also updated because StatusHandler ignores repository scoping
end
```
Both `commit_a` and `commit_b` currently receive the status because `StatusHandler#process` filters solely by `sha` [2](#0-1) , confirming the missing repository binding — but note this demonstration and any real-world exploitation require a genuine SHA collision and a validly-signed request for a Shipit-configured organization; it is not exploitable by a fully unauthenticated/unaffiliated internet attacker against an arbitrary victim.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
