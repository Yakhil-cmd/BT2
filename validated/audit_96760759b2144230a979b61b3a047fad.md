### Title
Stale Genesis KIP71 Config Propagated to Sub-Bridge Causes Persistent Bridge Transaction DoS After Governance Update — (`node/sc/main_bridge_handler.go`)

### Summary

`handleServiceChainParentChainInfoRequestMsg` in the main bridge reads KIP71 fee parameters from the immutable genesis `chainCfg.Governance.KIP71` instead of the live governance module. The sub-bridge receives this stale `UpperBoundBaseFee` and unconditionally overwrites its `remoteGasPrice` with it. Every anchoring transaction submitted to the parent chain is then priced at the genesis ceiling. After a governance vote raises `UpperBoundBaseFee`, the actual parent-chain base fee can legally exceed the genesis ceiling, causing all bridge transactions to be rejected by the parent-chain tx pool and permanently halting cross-chain asset settlement until the bridge is manually restarted.

### Finding Description

**Root cause — main bridge sends genesis-frozen KIP71 config:**

In `handleServiceChainParentChainInfoRequestMsg`, the main bridge constructs `parentChainInfo` by reading `chainCfg.Governance.KIP71.*` directly from the genesis `*params.ChainConfig`:

```go
// node/sc/main_bridge_handler.go:143-153
chainCfg := mbh.mainbridge.blockchain.Config()          // immutable genesis config
pcInfo := parentChainInfo{
    nonce,
    mbh.mainbridge.txPool.GasPrice().Uint64(),          // current base fee (correct)
    params.KIP71Config{
        LowerBoundBaseFee: chainCfg.Governance.KIP71.LowerBoundBaseFee,  // STALE
        UpperBoundBaseFee: chainCfg.Governance.KIP71.UpperBoundBaseFee,  // STALE
        ...
    },
    ...
}
```

The live governance module (`govModule.GetParamSet()`) is never consulted. Governance votes that update `UpperBoundBaseFee` or `LowerBoundBaseFee` are invisible to this path.

**Sub-bridge unconditionally overwrites gas price with stale ceiling:**

When the sub-bridge receives the response it first sets `pAccount.gasPrice` to the current gas price, then immediately overwrites `remoteGasPrice` with the stale `UpperBoundBaseFee`:

```go
// node/sc/sub_bridge_handler.go:187-191
func (sbh *SubBridgeHandler) setRemoteChainValues(pcInfo parentChainInfo) {
    sbh.setRemoteGasPrice(pcInfo.GasPrice)   // sets pAccount.gasPrice to current value
    if pcInfo.IsMagmaEnabled {
        sbh.remoteGasPrice = pcInfo.KIP71Config.UpperBoundBaseFee  // overwrites with stale genesis ceiling
        sbh.subbridge.bridgeAccounts.SetParentKIP71Config(pcInfo.KIP71Config)
    }
}
```

**Every anchoring transaction uses the stale ceiling as its gas price:**

```go
// node/sc/sub_bridge_handler.go:339
types.TxValueKeyGasPrice: new(big.Int).SetUint64(sbh.remoteGasPrice),
```

**Divergence condition:** `NextMagmaBlockBaseFee` caps the base fee at the *current* `UpperBoundBaseFee`. After governance raises it (e.g., from 750 Gwei to 1 500 Gwei), the parent-chain base fee can legally climb above the genesis ceiling. The sub-bridge submits transactions priced at the old ceiling (750 Gwei), which is now below the actual base fee, so the parent-chain tx pool rejects them with `ErrGasPriceBelowBaseFee` / `ErrFeeCapBelowBaseFee`.

### Impact Explanation

All bridge anchoring transactions (and any other bridge-operator transactions priced via `remoteGasPrice`) are permanently rejected by the parent chain after a governance `UpperBoundBaseFee` increase. Cross-chain value transfers and anchoring halt. Bridged assets on the service chain cannot be settled or withdrawn to the parent chain until an operator manually restarts the bridge node (which re-syncs the stale value from the same broken path, providing no relief). This constitutes a persistent DoS on bridged-asset settlement.

### Likelihood Explanation

Governance updates to KIP71 parameters (`UpperBoundBaseFee`, `LowerBoundBaseFee`) are a normal operational activity on Kaia mainnet. Any such vote that raises `UpperBoundBaseFee` above the genesis value immediately triggers the condition. No attacker capability is required; the failure is automatic and deterministic once the base fee climbs past the genesis ceiling.

### Recommendation

Replace the genesis-config read in `handleServiceChainParentChainInfoRequestMsg` with a live governance parameter lookup:

```go
// node/sc/main_bridge_handler.go
// Replace:
chainCfg := mbh.mainbridge.blockchain.Config()
kip71 := chainCfg.Governance.KIP71

// With:
blockNum := mbh.mainbridge.blockchain.CurrentBlock().Number().Uint64()
pset := mbh.mainbridge.govModule.GetParamSet(blockNum + 1)
kip71 := params.KIP71Config{
    LowerBoundBaseFee:         pset.LowerBoundBaseFee,
    UpperBoundBaseFee:         pset.UpperBoundBaseFee,
    GasTarget:                 pset.GasTarget,
    MaxBlockGasUsedForBaseFee: pset.MaxBlockGasUsedForBaseFee,
    BaseFeeDenominator:        pset.BaseFeeDenominator,
}
```

Additionally, in `setRemoteChainValues`, the sub-bridge should also compute the gas price dynamically from the received KIP71 config rather than blindly using `UpperBoundBaseFee` as a fixed ceiling.

### Proof of Concept

1. Deploy a service chain connected to a Magma-enabled parent chain with genesis `UpperBoundBaseFee = 750 Gwei`.
2. Submit a governance vote on the parent chain to raise `UpperBoundBaseFee` to `1 500 Gwei`.
3. Drive parent-chain gas usage above the old target so the base fee climbs past `750 Gwei`.
4. Observe that the sub-bridge's `remoteGasPrice` remains `750 Gwei` (genesis value) even after re-syncing via `SyncNonceAndGasPrice()`.
5. All anchoring transactions submitted by the sub-bridge are rejected by the parent-chain tx pool (`ErrGasPriceBelowBaseFee`), halting cross-chain settlement indefinitely.
