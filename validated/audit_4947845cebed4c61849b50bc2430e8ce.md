The reported bug's root cause is fundamentally tied to a Solidity pattern: an unprivileged caller supplies arbitrary calldata (`zeroExTradeData`) that gets executed via a low-level call to an attacker-influenced `swapTarget`, and the contract infers "trade success" solely from a naive `tokensBought == 0` balance-delta check — which the attacker can satisfy independently of the real trade (e.g., via a `receive()` callback that injects a trivial amount of the target token). This requires two things that don't exist together anywhere in this Sui repository's in-scope Move/runtime code:

1. An entry point that accepts and forwards **arbitrary attacker-controlled calldata** to an **unknown/attacker-influenced external contract or address**.
2. A **post-call balance-delta check** used as the sole proof of correct execution, decoupled from the actual value that was supposed to move.

In Move on Sui, cross-module calls are statically typed against fixed signatures — there is no analog to `target.call(arbitrary_bytes)`. Sui's own "flash loan" pattern (DeepBook `borrow_flashloan_base`/`return_flashloan_base`) enforces repayment via the hot-potato type system and exact-amount struct equality (`assert!(repayment.value() == amount)`), not via a snapshot-and-diff balance check that could be gamed by a reentrant callback [1](#0-0) , and PTB-level static verification (hot potato clique/count rules) additionally guarantees the loan must be settled atomically within the same transaction before other operations can proceed [2](#0-1) .

I checked the one place in-repo that does use an old-balance/new-balance delta pattern reminiscent of the report — `SuiBridge.bridgeERC20` in the EVM bridge contracts, which computes `amountTransfered = newBalance - oldBalance` after a `safeTransferFrom` [3](#0-2) . However, this is a deposit path where the only external call is `SafeERC20.safeTransferFrom` from `msg.sender`'s own token to the vault — there is no attacker-supplied arbitrary calldata, no external call to an attacker-chosen target, and the balance delta only affects the depositor's own credited amount (protecting against fee-on-transfer tokens), not a cross-user fund-theft primitive like the one described in the report. The bridge's withdrawal path (`transferBridgedTokensWithSignatures`) is driven by validated, signed committee messages rather than user-supplied trade calldata [4](#0-3) .

Since the enabling precondition — an unprivileged caller injecting arbitrary calldata into an untrusted external call whose "success" is verified only by a spoofable balance delta — is absent in both the Move VM/framework and the in-scope bridge contracts, there is no reachable analog producing a Critical/High "theft via malicious external call data" outcome here.

### The Algorithm

- Each input to the PTB starts off in its own clique with a count of zero.
- When values are used (by reference or by-value) together in a command, their cliques are merged, adding together each clique’s count.
- The count of the arguments’ merged clique is decremented for each hot value moved (taken by-value and not copied).
- If the command is a Move call for a non-public `entry` function, the count of the arguments’ merged clique must be zero at this point.
  - Note that this means a non-public `entry` function _can_ take hot values! They must just be the last hot values in their clique.
- Results of each command are included in the arguments’ merged clique. The clique’s count is incremented for each hot result value.
- **NOTE:** Shared objects taken by-value have a special rule in that during the accounting for the result values, the argument’s merged clique’s count is set to infinity.
  - See the “Limitations” section below for more detail
