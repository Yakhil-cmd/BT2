### Title
Unbounded growth of `system_votes` enables an unprivileged unit-poster to bloat `countVotes()` queries executed during every MCI stabilization, degrading/blocking main-chain progress - ([File: main_chain.js])

### Summary
`countVotes()` in `main_chain.js` is executed synchronously as part of `markMcIndexStable()` whenever a `system_vote_count` message stabilizes for a subject [1](#0-0) . It begins by doing an unbounded `SELECT DISTINCT address FROM system_votes WHERE subject=?` and then builds a comma-joined, unbounded `IN(...)` SQL clause and later an unbounded multi-row `INSERT INTO voter_balances` statement from every distinct voter address ever recorded for that subject [2](#0-1) [3](#0-2) . Both `system_vote` and `system_vote_count` messages can be authored by any ordinary (non-AA) address in a normal unit, subject only to lightweight format checks [4](#0-3) [5](#0-4) , and every vote is permanently appended to `system_votes`/`op_votes`/`numerical_votes` on stabilization without any bound on the number of distinct addresses [6](#0-5) . This is structurally the same bug class as the reported `GetAllBalances`-in-`InitGenesis` issue: an attacker-inflatable, unbounded collection is iterated and materialized in-line inside a critical, must-run-by-every-node consensus step.

### Finding Description
Any address can post a `system_vote` message (once `v4UpgradeMci`/devnet activation has passed) as long as the payload has the right shape - a sorted, unique, valid-address `op_list`, or a numeric value for `threshold_size`/`base_tps_fee`/`tps_interval`/`tps_fee_multiplier` [7](#0-6) . There is no cap on how many distinct addresses may cast a vote for the same subject over time, and every vote is durably inserted into `system_votes` (and `op_votes`/`numerical_votes`) on stabilization [6](#0-5) .

`system_vote_count` is likewise postable by any regular address [5](#0-4) , and once it stabilizes for a subject it is queued and processed for *every* node as the very last step of `markMcIndexStable`, i.e. it is on the hot path of MCI stabilization that every full node must execute to advance the chain [8](#0-7) [1](#0-0) .

Inside `countVotes()`:
- `address_rows` is fetched with no `LIMIT`, so it scales with the total number of distinct addresses that have ever voted for the subject [9](#0-8) .
- `strAddresses` is built by string-concatenating an escaped value per address and embedded directly into a `WHERE ... IN(${strAddresses})` query [10](#0-9) .
- Every resulting balance row is turned into another concatenated value tuple and used to build a single `INSERT INTO voter_balances (...) VALUES ...` statement whose size is proportional to the number of distinct voter addresses [3](#0-2) .

Since an attacker can trivially create arbitrarily many addresses (each address is free to derive) and pay only minimal unit fees to author a `system_vote` unit from each, the size of `system_votes` and hence the size of these generated SQL statements is entirely attacker-controlled and unbounded, exactly mirroring the "any user can deposit an unbounded number of tokens" pattern from the reported Cosmos SDK issue, except here the "deposit" is a vote row.

### Impact Explanation
`countVotes()` runs inline during `markMcIndexStable`, which is required for the network to finalize new main-chain indices, i.e. for the DAG to stabilize and for new units to be confirmed [11](#0-10) [12](#0-11) . If the number of distinct voter addresses is inflated to be very large, the resulting queries and generated SQL text (`IN(...)`, bulk `INSERT`) become correspondingly large, which can slow down or, depending on the underlying DB engine's statement-size/duration limits, fail this step on every node, stalling MCI stabilization for that subject and thus the associated consensus progress. Because `countVotes()` for `op_list` also determines the active order-provider set used to reset the witness cache and update `storage.systemVars.op_list` [13](#0-12) , a stall/failure here can also affect the network's ability to agree on OP list changes, which underlies stability determination itself. This matches the required impact bar: node disagreement on validity/stability or a network unable to confirm new units.

### Likelihood Explanation
Reaching this path requires only: (1) posting cheap `system_vote` units from many distinct self-controlled addresses over time to grow `system_votes`, and (2) posting a `system_vote_count` unit for that subject, both of which are permitted to any unprivileged unit author once the relevant activation MCI has passed [14](#0-13) . No special privileges, AA logic, or protocol exceptions are needed, making this reachable by any ordinary wallet user willing to pay ordinary unit fees for enough addresses/votes.

### Recommendation
Bound and paginate the voter-address query and downstream bulk statements instead of materializing every historical distinct voter address in one query/one `IN`/`INSERT` statement. For example, cap the number of *effective* voters considered (e.g., only count the highest-balance N addresses per subject, or require a minimum balance/deduplicate before insertion), and build the balance and `voter_balances` population using batched/paginated queries rather than a single unbounded `IN(...)`/multi-row `INSERT` built from string concatenation of an arbitrarily large address set, analogous to iterating a bounded, hard-capped candidate set (as recommended for the original `GetAllBalances`/`IsAnyGT` fix).

### Proof of Concept
1. After the relevant activation MCI, generate `N` (e.g. tens of thousands) distinct wallet addresses.
2. From each address, author and get stabilized a minimal unit containing a valid `system_vote` message (e.g., `subject: "threshold_size"`, a valid positive integer value) - this is accepted by validation with no cap on distinct addresses [15](#0-14) .
3. Once `system_votes` accumulates a very large number of distinct addresses for that subject, post a `system_vote_count` unit for the same subject; this queues `countVotes(conn, mci, subject)` for the stabilizing MCI [8](#0-7) [1](#0-0) .
4. Observe that `countVotes()` must build/execute a `WHERE address IN(...)` clause and an `INSERT INTO voter_balances VALUES (...)` statement whose size scales with `N` [16](#0-15) , measurably degrading (or, at sufficiently large `N` against the deployed DB engine's limits, failing) the MCI-stabilization step on every node that processes this MCI.
