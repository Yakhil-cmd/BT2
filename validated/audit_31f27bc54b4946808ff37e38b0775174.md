### Title
Webhook signature is verified against `repository.owner.login`, but the mutated repository is selected via unrelated, unchecked `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#repository_owner` picks the organization used for signature verification purely from `params.dig('repository','owner','login') || params.dig('organization','login')`, while `Handler#repository_name` independently reads `payload.dig('repository','full_name')` to select which `Repository`/`Stack` gets mutated. Nothing in the request pipeline asserts that the owner segment of `full_name` equals `repository.owner.login`, so an attacker who can pass signature verification for org A can point `full_name` at a repository belonging to org B.

### Finding Description
The broken binding, stated as an equality that the code never enforces:
`repository.owner.login == repository.full_name.split('/').first`

Trace:
- `verify_signature` resolves the GitHub app config to use for HMAC verification via `Shipit.github(organization: repository_owner)` [1](#0-0) .
- `repository_owner` is computed solely from `repository.owner.login` (preferred) or `organization.login` (fallback) [2](#0-1) .
- Once `verified` is truthy, `create` dispatches the *entire raw payload* to every registered handler for the event, with no re-derivation or re-check of the owner [3](#0-2) .
- Each `Handler` independently determines the target repository/stack from `payload.dig('repository','full_name')` via `repository_name`/`stacks`, completely decoupled from whatever value was used for signature verification [4](#0-3) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for the resolved organization: `return true unless webhook_secret` [5](#0-4) .

Exploit flow: the attacker crafts a JSON body with `repository.owner.login = "safe-org"` (an org configured in Shipit without a `webhook_secret`, or one whose secret the attacker can otherwise satisfy) and `repository.full_name = "evil-target/repo"`. `verify_signature` resolves `Shipit.github(organization: "safe-org")`, calls `verify_webhook_signature`, which short-circuits to `true` because `safe-org` has no configured secret — no HMAC knowledge is required at all. The request then passes to the handler, which uses `full_name` ("evil-target/repo") to look up and mutate the target stack, entirely under a different, secret-protected organization.

None of the existing guards catch this: `drop_unhandled_event` only checks the event type; `verify_signature` never inspects `full_name`; `ExplicitParameters` schemas used by handlers validate structural shape of subfields, not cross-field owner consistency; there is no `Repository`- or `Stack`-level validation that ties incoming webhook owner to the resolved repository's actual GitHub owner.

### Impact Explanation
An attacker who controls (or who targets) any Shipit-configured organization lacking a `webhook_secret` can forge webhooks that mutate stacks belonging to a completely different, secret-protected organization. This satisfies the "payload for one repository mutating another's stack, commit, task or team" Critical criterion — e.g. forged `push`, `status`, or `check_suite` events can flip commit status, enqueue `GithubSyncJob`s, or otherwise alter task/commit state for a repository the attacker has no legitimate relationship with. The attack is repeatable against any repository/stack in the instance merely by varying `full_name`, as long as one exploitable (secretless, or otherwise satisfiable) source organization exists.

### Likelihood Explanation
Exploitability strictly depends on operational configuration: it requires at least one organization registered in `Shipit.github_configs` (or equivalent) that has no `webhook_secret` set, or one whose secret the attacker can otherwise obtain/guess. If every configured organization has a strong `webhook_secret`, this path is not exploitable, since `verify_webhook_signature` will correctly reject unsigned/mis-signed requests for all of them. The code path itself (owner/full_name decoupling) is unconditionally present and unguarded, but the "attacker with zero secrets" precondition in the rules is only satisfiable when a secretless/misconfigured org exists in the deployment.

### Recommendation
In `Handler#repository_name` (or centrally in `WebhooksController`), assert that the owner segment of `repository.full_name` matches `repository_owner` used for signature verification, rejecting (422) any payload where they diverge. Additionally, consider requiring `webhook_secret` to be present for all configured organizations (fail closed rather than `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`).

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "signature for org without secret allows mutating another org's repo via mismatched full_name" do
  # Precondition binding under test:
  # repository.owner.login ("safe-org") == full_name.split('/').first ("evil-target") ?
  owner_login = "safe-org"
  full_name = "evil-target/repo"
  assert_not_equal owner_login, full_name.split('/').first

  # safe-org has no webhook_secret configured -> verify_webhook_signature short-circuits true
  Shipit.stubs(:github).with(organization: owner_login).returns(GitHubApp.new(owner_login, {}))

  stack = shipit_stacks(:shipit) # belongs to a different org/repo entirely
  Repository.expects(:from_github_repo_name).with(full_name).returns(stack.repository)

  request.headers['X-Github-Event'] = 'push'
  body = {
    repository: { owner: { login: owner_login }, full_name: full_name },
    ref: "refs/heads/#{stack.branch}",
    after: 'deadbeef'
  }.to_json

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: stack.id, expected_head_sha: 'deadbeef']) do
    post :create, body: body, as: :json # no X-Hub-Signature header sent at all
  end
  assert_response :ok
end
```
This demonstrates that `repository_owner` ("safe-org") and the real mutation target derived from `repository.full_name` ("evil-target/repo") are independently attacker-controlled and never cross-validated, letting a signature valid (or trivially bypassable) for one organization authorize mutation of another organization's stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
