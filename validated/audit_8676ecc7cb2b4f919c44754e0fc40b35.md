### Title
Webhook signature scopes trust to a GitHub organization while `StatusHandler` writes CI status globally by commit SHA, enabling cross-organization forced deploys - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook against the `GitHubApp` selected by `params.dig('repository','owner','login')` (or `organization.login`), i.e. it proves "this payload was signed by GitHub for organization X." [1](#0-0) [2](#0-1)  But the `status` event handler never checks which organization/repository the payload claims to belong to — it looks up commits by SHA alone, across the entire installation: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [3](#0-2)  This breaks the equality "organization that authenticated == repository that is written": the signature only proves the sender controls org X, yet the effect (a CI status write) applies to any stack in any organization whose commit table happens to contain a matching SHA.

### Finding Description
The webhook entry point parses the raw body once and dispatches it to handlers for the given `X-Github-Event`: [4](#0-3) . Signature verification picks the `GitHubApp` (and therefore the `webhook_secret` to HMAC-check against) using `repository_owner`, itself derived from the untrusted JSON body: [2](#0-1) . Shipit explicitly supports multiple GitHub organizations, each with its own `github_app_config`/`webhook_secret` selected via this same organization key: [5](#0-4) .

The base `Handler` class does provide a `repository_name`/`stacks` helper that scopes work to a specific `Repository`: [6](#0-5) , and `PushHandler` uses it: [7](#0-6) . `StatusHandler`, however, ignores this scoping entirely and resolves the target purely by commit SHA, which is a global, unscoped lookup across every stack/organization configured in the Shipit instance: [8](#0-7) .

`Commit#create_status_from_github!` creates a `Status` record, and `Status` after-create/after-commit callbacks call `enable_ci_on_stack` and `schedule_continuous_delivery`: [9](#0-8) . `Commit#schedule_continuous_delivery` enqueues a `ContinuousDeliveryJob` for the *commit's actual stack* whenever the commit becomes `deployable?` and the stack has `continuous_deployment?` enabled: [10](#0-9) , and `deployable?` only requires a `success` status and no blocking state: [11](#0-10) . This is confirmed by existing tests showing that creating a `success` status directly triggers a real `Deploy`: [12](#0-11) .

**Equality broken (before vs. after the attack):**
- Before: `verify_signature` authenticates "org A sent this webhook" == StatusHandler "writes status to a commit that belongs to org A's repositories."
- After: An attacker who legitimately controls (or has CI/status-write access to) a repository in org A — whose `GitHubApp` is properly configured and signs correctly, or whose `webhook_secret` happens to be unset (`return true unless webhook_secret` in `lib/shipit/github_app.rb`, line 76-77) — can send a validly-signed `status` webhook whose `sha` matches a commit that actually lives in org B's repository/stack (a distinct organization/customer tracked by the same Shipit instance). Because SHA-1 commit hashes are content-addressed (tree, parents, author, committer, message, timestamps) and not bound to a specific remote/organization, an attacker can reproduce an identical commit (e.g. by cherry-picking/copying commit metadata) in a repository they control, giving it the same SHA as a target commit in org B's repo, then trigger a CI status webhook from their own repo/org for that SHA.

### Impact Explanation
If the SHA collision lands on a commit belonging to a stack with `continuous_deployment: true`, the forged `success` status causes `Commit#schedule_continuous_delivery` to enqueue `ContinuousDeliveryJob`, which ultimately calls `Stack#trigger_continuous_delivery` → `trigger_deploy`, deploying code the victim organization never approved via this path: [13](#0-12) . This is an unauthorized deploy triggered purely by cross-organization data (an unbound `sha` field), qualifying as "an unauthorized deploy" per the Critical/High impact criteria. It also constitutes a cross-repository write: an org-A-authenticated webhook mutates `Status`/`Commit` state belonging to org B's stack.

### Likelihood Explanation
Exploitation requires: (1) the attacker to control or have CI/status-posting rights in at least one repository/organization already integrated with the target Shipit instance, and (2) the ability to produce a commit with an identical SHA to a target commit in a different tracked repository — feasible since SHA-1 is content-derived and an attacker who can observe a target's public commit metadata can reproduce an identical commit object in their own repo. Multi-organization Shipit deployments are explicitly documented and supported, and per-org `webhook_secret` is optional (defaults to unset in example configs), further lowering the bar in some deployments. The core code defect — `StatusHandler` never validating that `params.sha`'s commit belongs to the authenticated organization/repository — is present regardless of configuration correctness.

### Recommendation
In `StatusHandler#process`, restrict the `Commit` lookup to only those commits whose stack's repository matches the authenticated `repository_name`/organization from the webhook payload (mirroring the `stacks`/`repository_name` scoping already used by `Handler`/`PushHandler`), instead of a global `Commit.where(sha: params.sha)` scan. Additionally, consider passing the verified organization from `WebhooksController` into the handler so handlers can assert the payload's claimed repository actually belongs to the organization whose secret authenticated the request.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `GithubApp`/`webhook_secret`, both tracking stacks in Shipit (multi-org config as documented in `docs/setup.md`).
2. Org B has a stack `org-b/victim-repo` with `continuous_deployment: true` and a commit `C` with SHA `deadbeef...` currently in `pending`/no CI status.
3. Attacker, who has push/CI access to their own `org-a/attacker-repo`, creates a commit in `attacker-repo` with identical tree/parents/author/committer/message/timestamps as commit `C`, producing the same SHA `deadbeef...`.
4. Attacker's CI (or attacker directly, if they can trigger arbitrary status webhooks for their own repo) sends GitHub a `status` event for `attacker-repo` at SHA `deadbeef...` with `state: success`. GitHub signs this webhook with `org-a`'s webhook secret and delivers it to Shipit's `/webhooks` endpoint.
5. `WebhooksController#verify_signature` selects `Shipit.github(organization: 'org-a')` and validates the signature successfully (it is a legitimate org-a webhook).
6. `Shipit::Webhooks::Handlers::StatusHandler#process` runs `Commit.where(sha: 'deadbeef...')`, which matches commit `C` belonging to `org-b/victim-repo`, and calls `commit.create_status_from_github!(params)`.
7. The new `success` `Status` on commit `C` makes it `deployable?`; `Commit#schedule_continuous_delivery` fires because `org-b`'s stack has `continuous_deployment: true`, enqueuing `ContinuousDeliveryJob` and ultimately deploying commit `C` on `org-b`'s stack — a deploy that org B never authorized, triggered entirely by an org-A-signed webhook.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
