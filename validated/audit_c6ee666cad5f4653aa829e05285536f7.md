### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled` for `prevent_with_label`/`allow_with_label` behaviors - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`provision?` combines `review_stacks_enabled` with the provisioning-behavior checks using `&&`/`||` without parentheses, so `review_stacks_enabled` only gates the `allow_all` branch. When `provisioning_behavior` is `prevent_with_label` (or `allow_with_label`), the branch evaluates independently of `review_stacks_enabled`, letting an attacker-opened PR with no labels trigger `ReviewStackAdapter#find_or_create!` and enqueue a `ReviewStack` even though the operator disabled review stacks entirely.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == true` must equal the actual gate applied before stack creation. Tracing `provision?`: [1](#0-0) 

Ruby operator precedence makes this:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So for a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: :prevent_with_label`, the third disjunct `(prevent_with_label? && !has_label?)` is `true && true == true` regardless of the first disjunct's `review_stacks_enabled` term. `respond_to_pull_request_opened?` then returns true for `action == "opened"`, and `process` calls `ReviewStackAdapter#find_or_create!`, which calls `create!`, creating a `Shipit::ReviewStack` and calling `Shipit::ReviewStackProvisioningQueue.add(stack)`: [2](#0-1) [3](#0-2) 

The attacker's exact action: open a pull request (from any fork/branch they control) against a repository whose owner has explicitly disabled review stacks (`review_stacks_enabled: false`) and set `provisioning_behavior: :prevent_with_label`, without applying any label to the PR. No signature/session bypass is needed here — this is a request-shape bug in the authorization logic itself, exploitable through the normal, correctly-signed webhook delivery for that PR (the attacker doesn't forge the webhook; they simply cause GitHub to emit a legitimate `pull_request.opened` event by opening the PR).

Existing guards do not stop this: signature verification (`verify_signature`) and the `ExplicitParameters` schema validate that the payload is well-formed and from GitHub, but they say nothing about the semantic gating of `review_stacks_enabled`, and no other check in `ReviewStackAdapter#create!` re-validates `review_stacks_enabled` before creating the stack and enqueueing the provisioning job.

Existing tests corroborate that this specific combination (`review_stacks_enabled: false` + `prevent_with_label`) is untested: the only `prevent_with_label` test in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (lines 159-172) uses the default `provisioning_enabled: true`, never exercising the disabled case, which is consistent with this gap going unnoticed.

### Impact Explanation
Any unprivileged GitHub user able to open a pull request against a repository configured this way can force Shipit to create a `Shipit::ReviewStack` record and enqueue it via `Shipit::ReviewStackProvisioningQueue.add(stack)` — work the repository operator explicitly opted out of by setting `review_stacks_enabled: false`. This is a write for a repository configuration state that should prevent all such writes. It is repeatable per PR/per repository matching the misconfiguration (any repo with `prevent_with_label` and `review_stacks_enabled: false`), and each new unlabeled PR against such a repo triggers a fresh provisioning-queue entry. This maps to "a record written for a repository that did not authenticate/authorize it" — an unauthorized provisioning action bypassing an explicit operator-level control.

### Likelihood Explanation
Requires the specific repository configuration `review_stacks_enabled: false` with `provisioning_behavior: :prevent_with_label` (an operator misconfiguration/edge-case combination, not the default). No secrets, tokens, or elevated GitHub permissions are needed — the attacker only needs to be able to open a PR (e.g., against a public repo, or their own fork if Shipit is configured to track it) without labeling it. The cost is essentially zero and the action is trivially repeatable.

### Recommendation
Add parentheses to make the gating explicit and applied uniformly:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks when review_stacks_enabled is false, even with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false, # review_stacks_enabled == false
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [] # no labels

  Shipit::ReviewStackProvisioningQueue.expects(:add).never

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Assert both sides of the binding: before the fix, `repository.review_stacks_enabled` is `false` while `Shipit::ReviewStackProvisioningQueue.add` still fires and `Shipit::Stack.count` increases — demonstrating the divergence; after the fix, both sides match (no stack created, queue not called).
