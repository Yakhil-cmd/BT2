Based on the investigation, the closest analog in `ocore` to the Tuleap "improper permissions" bug — where a party can access/trigger disclosure of data they should not be authorized for — is in the device-to-device `"sign"` message handler in `wallet.js`. It deliberately skips a cosigner-membership check before proceeding to expose signing-request details (including any private payment payloads attached to the request) to the local wallet UI/event bus, based solely on the fact that the sender is *a* paired correspondent — not necessarily a legitimate cosigner of the target address.

### Title
Missing cosigner-authorization check in device "sign" message handler discloses private payment payload data to unauthorized correspondents - (File: wallet.js)

### Summary
The `"sign"` case of `handleMessageFromHub` in [1](#0-0)  lets any paired correspondent device request that the local wallet sign an arbitrary unsigned unit for one of the wallet's local addresses, optionally attaching `private_payloads`. When the target address resolves locally (`findAddress` → `ifLocal`), the code intentionally does **not** verify that the requesting device is actually a cosigner of that address before proceeding — the check is explicitly commented out: [2](#0-1) .

### Finding Description
`findAddress`'s `ifLocal` branch is reached whenever the target `body.address` happens to be hosted on the current device, regardless of who the sender is [3](#0-2) . The `"sign"` handler in `wallet.js` performs strict structural validation of `body.unsigned_unit` and `private_payloads` (payload hash checks, output/blinding validation, etc. at [4](#0-3) ), but this validation only proves internal consistency of the attacker-supplied payload — it does not verify that the sender is actually one of the address's legitimate cosigners (`extended_pubkeys` for wallet-based multisig, or `shared_address_signing_paths` for shared addresses).

The removed check would have been:
```js
//db.query("SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?", [row.wallet, from_address], function(sender_rows){
//    if (sender_rows.length !== 1)
//        return callbacks.ifError("sender is not cosigner of this address");
```
Because this is disabled ("the commented check would make multilateral signing impossible"), any correspondent device that merely knows a wallet's local address and a valid signing path can:
1. Craft a `signed_message`/unsigned unit naming an arbitrary local address as author, and
2. Trigger the `"signing_request"` event (surfaced to whatever UI/automation is listening) at [5](#0-4)  and [6](#0-5) , passing along `assocPrivatePayloads`, `objUnit`, and the sender's `from_address` and `signing_path`, without the local wallet ever confirming the requester is a genuine cosigner of that address.

This is analogous to the Tuleap CVE-2024-37167 pattern: a party who should not have visibility/interaction rights over an item (here, a wallet address's signing/private-payment flow) is nonetheless granted the interaction because an authorization check that should gate visibility/action was removed or bypassed.

### Impact Explanation
An unprivileged paired device (any correspondent, not a true cosigner) can repeatedly probe or spam `"sign"` requests against victim-owned addresses, forcing the wallet to process crafted units/private payloads and surface `signing_request` events. Depending on how a given wallet UI/automation handles `signing_request` (e.g., auto-approval flows, bots, or unattended signing services built on ocore), this missing authorization boundary can lead to unauthorized signature generation or leakage of transaction details for addresses the sender has no legitimate claim to, undermining the multisig/shared-address trust model without any prior action from the address's real owners other than being paired as a correspondent.

### Likelihood Explanation
Likelihood is bounded by the fact that most wallet UIs display a confirmation dialog to the human user before actually signing, so full exploitation to unauthorized spend generally requires an unattended/automated signer. However, reaching the disclosure/trigger point itself requires no privilege beyond being a paired correspondent device, which is a very low bar (pairing is user-initiated but common in exchange/bot integrations), and the code path is reached unconditionally once `ifLocal` resolves, making the entry point trivially reachable.

### Recommendation
Reinstate (and generalize for shared addresses, not just wallet-based multisig) a cosigner-membership check in the `"sign"` handler before emitting `signing_request` or proceeding to `network.handleOnlineJoint`: verify `from_address` is present in `extended_pubkeys` for the address's wallet, or in `shared_address_signing_paths.device_address` for the resolved shared/member address, and reject with `ifError` otherwise. If multilateral signing support requires broader sender sets, restrict it to sets provably derivable from the unit's own definition/authors rather than any known correspondent.

### Proof of Concept
1. Pair with a victim device as an ordinary correspondent (standard pairing flow).
2. Learn one of the victim's local wallet addresses and a valid `signing_path` (addresses are often shared for receiving payments).
3. Send a `"sign"` device message to the victim with `body.address` set to that address, a crafted `unsigned_unit` whose `authors` include that address, and optionally forged `private_payloads` that satisfy the hash/structure checks in [4](#0-3) .
4. Observe that `findAddress` resolves `ifLocal` and the victim's wallet emits `signing_request` with the attacker-controlled unit/payload data at [2](#0-1) , with no verification that the attacker is a genuine cosigner — proving the authorization gate is missing.
