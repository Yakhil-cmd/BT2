### Title
Unfiltered PR label names become arbitrary shell-interpreted environment keys (`ENV`/`BASH_ENV`/`LD_PRELOAD`/etc.) reaching `PTY.spawn` for deploy steps - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an environment-variable *key* with value `"true"`, with no allowlist, before that hash flows through `TaskCommands#env`/`DeployCommands#env` into `Command#unbundled_env` and finally `PTY.spawn`. Because `shipit.yml` steps are single command strings executed via a shell, an attacker who can label a PR (assumed capability per the rules) can inject shell-startup-sensitive variable names such as `ENV`, `BASH_ENV`, `LD_PRELOAD`, `RUBYOPT`, etc. and control code executed on the deploy host.

### Finding Description
The broken binding: the set of keys in the environment hash reaching `PTY.spawn` should equal `deploy_spec.machine_env.keys ∪ declared_VariableDefinition_names`, but in fact it equals that set **∪ pull_request.labels.map(&:upcase)**, because:

- `ReviewStack#env` does `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` and merges this unconditionally into the stack's `env` with no key allowlist: [1](#0-0) 
- `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` straight from the webhook body onto `pull_request.labels`: [2](#0-1) 
- `TaskCommands#env` merges `@stack.env` (containing the attacker-controlled keys) into the final env used to build each step's `Command`, with later merges (`machine_env`, `@task.env`) only adding/overriding specific keys — they never strip unexpected ones: [3](#0-2) 
- `Command#unbundled_env` merges `BASE_ENV`, `PATH`, and `@env.stringify_keys` (the full unsanitized hash) and that result is passed directly to `PTY.spawn`: [4](#0-3) 
- `Command#start` invokes `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, and since deploy steps such as `'bundle exec cap $ENVIRONMENT deploy'` are single strings (not argv arrays), Ruby's `Process.spawn`/`PTY.spawn` runs them through a shell: [5](#0-4) 

Existing tests confirm this merge is intentional and unrestricted, not a filtering step: `test/models/shipit/review_stack_test.rb` explicitly asserts `stack.env["WIP"]`/`["BUG"]` become `"true"` from labels `["wip", "bug"]`: [6](#0-5) , and `test/lib/shipit/task_commands_test.rb` shows the same propagates into `TaskCommands#env`: [7](#0-6) 

Why the existing allowlist (`EnvironmentVariables#permit`) doesn't help: it is only invoked via `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` and `TaskDefinition#filter_envs`, which sanitize the *user-supplied* `env` param submitted through controllers (e.g. `RollbacksController#rollback_params`, task trigger endpoints) against `VariableDefinition` names: [8](#0-7) [9](#0-8)  and [10](#0-9) . That allowlist is never applied to `@stack.env` (the PR-labels-derived hash) inside `TaskCommands#env`/`DeployCommands#env`, so the label-derived keys sail through completely unchecked.

Exploit flow: attacker opens a fork PR against a repository with review stacks enabled, applies a label literally named `env` (any case) to their own PR. GitHub sends a signed, legitimate `pull_request` `labeled` webhook (no forged signature required — this is real GitHub-originated traffic). `LabelCapturingHandler` stores `"ENV"` as a label. When the stack (review stack or its continuous-deployment counterpart) next runs any shell-interpreted step, `ENV=true` (or a path the attacker chooses via the label, since `label_name.upcase` is only case-transformed, not value-controlled — value is always `"true"` in this handler) ends up in the process environment passed to `PTY.spawn`. Depending on the shell invoked as `sh` on the deploy host, this can trigger a shell startup-file read (e.g., bash invoked as `sh` in POSIX-compatibility mode reads `$ENV`) or, with other injectable keys reachable the same way (e.g., label named `bash_env`, `ld_preload`, `rubyopt`), directly hijack execution of the deploy step.

### Impact Explanation
This is a Critical-class Remote Code Execution vector on the Shipit deploy host: an unprivileged fork PR author's PR label controls keys in the exact environment hash handed to `PTY.spawn` for deploy/task shell steps, with no allowlist protecting `@stack.env`. The blast radius is scoped to whatever repository/stack the labeled PR belongs to, but is repeatable on every review-stack task/deploy run for that stack, and any repository with review stacks enabled is affected identically.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`repository.review_stacks_enabled`) and `shipit.yml` must define shell-interpreted (string) deploy/task steps — both very common configurations. The rules stipulate the attacker capability to label their own PR is given. The attacker cost is a single label addition; no secrets, tokens, or privileged roles are required, and the exploit is fully repeatable across every deploy/task run of that stack.

### Recommendation
Apply the same `EnvironmentVariables#permit` allowlist (or an explicit denylist of dangerous keys) to `ReviewStack#env`'s label-derived hash before merging it into the command environment, restricting label-derived keys to a safe, namespaced prefix (e.g. `LABEL_<NAME>`) instead of raw uppercased label names, and never allow label-derived data to introduce arbitrary top-level environment keys like `ENV`, `BASH_ENV`, `LD_PRELOAD`, `RUBYOPT`, `PYTHONSTARTUP`, `PATH`, etc.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (new test)
test "#env allows a PR label to inject the ENV shell-startup variable with no allowlist" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["env"]

  env = stack.env

  assert_equal "true", env["ENV"]
end

# test/lib/shipit/task_commands_test.rb (new test)
test "#env propagates attacker-controlled ENV key from PR label into command env with no allowlist" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["env"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  assert_equal "true", env["ENV"]

  command = Shipit::Command.new("echo hi", env:, chdir: ".")
  assert_equal "true", command.unbundled_env["ENV"]
  # command.unbundled_env is exactly what is passed to PTY.spawn in Command#start
end
```
Both assertions demonstrate the binding violation: the environment hash reaching `Command#unbundled_env`/`PTY.spawn` contains a key (`ENV`) that is neither in `deploy_spec.machine_env` nor any declared `VariableDefinition`, sourced solely from an attacker-controlled PR label.

        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)

      rescue Errno::EACCES

      end
      @started = true
      self
    end
