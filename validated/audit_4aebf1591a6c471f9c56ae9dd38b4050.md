### Title
Same-Chain AA Price Oracle Manipulation via Unconfirmed `data_feed` Reads Enables Flash-Loan-Style Exploits - (File: data_feeds.js)

### Summary
`readDataFeedValue()` in `data_feeds.js` contains a fast-path (`bIncludeUnstableAAs`) that lets AA formula evaluation read `data_feed` values posted by *other, still-unstable* AA response units — units that have not reached economic finality (are not yet on a stable main chain) [1](#0-0) . This path is exactly what powers AA-to-AA composability inside a single trigger cascade: `formula/evaluation.js`'s `data_feed` op calls `dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ifseveral, ...)`, passing the AA-execution flag `bAA` as `unstable_opts` [2](#0-1) . Because a whole chain of primary+secondary AA triggers is executed synchronously and atomically as part of processing one posted trigger unit (`handleTrigger` → `handleSecondaryTriggers`) before any of it is stable [3](#0-2) , an attacker who controls two chained AAs can post an arbitrary "oracle" value in one AA and have a second, chained AA consume that unconfirmed value to price an irreversible fund transfer — all inside a single atomic unit-processing pass, with no intervening stabilization/finality boundary. This is structurally analogous to a flash-loan price-manipulation exploit: manipulate a price signal and consume it for profit within one atomic transaction.

### Finding Description
`readDataFeedValue()`'s unstable branch scans `storage.assocUnstableMessages` for `data_feed` messages authored by the requested oracle address(es), filtering only by `latest_included_mc_index` range and `sequence === 'good'` — not by real stability/finality [4](#0-3) . When several unstable candidates exist it picks the "last" one by `(latest_included_mc_index, level)` ordering [5](#0-4) .

These unstable messages are populated the moment a unit is written (`saveJoint`), long before the unit's `mci` stabilizes: [6](#0-5) 

`data_feed`/`in_data_feed` formula ops invoke this exact code path from within AA execution (`bAA` truthy ⇒ `unstable_opts` truthy) [7](#0-6) , [8](#0-7) .

Crucially, AA execution is not one isolated unit: a single trigger unit posted by an ordinary user can fan out into a whole chain of primary + secondary AA responses, all processed and committed together atomically in `handlePrimaryAATrigger`/`handleTrigger`/`handleSecondaryTriggers` [9](#0-8) , [3](#0-2) . Within that single cascade, one AA can emit a `data_feed` message and a *later* AA in the same cascade can immediately read it via the unstable fast-path — the value never had to survive DAG reorg/finality to be acted upon.

### Impact Explanation
Any DeFi-style AA that trusts a `data_feed[[oracles=...]]` value to gate an irreversible payout (mint, swap, loan issuance, collateral release, etc.) — especially designs that compose with other AAs for pricing, a pattern explicitly supported by this unstable-read fast path — can be manipulated by an attacker who:
1. Deploys/controls an "oracle" AA `O` that posts an attacker-chosen `data_feed` value derived from trigger data.
2. Deploys/controls or targets a consumer AA `V` that is triggered as a secondary step in the same chain and reads `data_feed[[oracles="O", ...]]`, pricing a fund transfer off it.
3. Sends a single trigger unit that fires `O` first and `V` second (secondary trigger), so `V` consumes `O`'s brand-new, zero-finality value within the same atomic cascade, before the manipulated feed has any chance to be reverted, contradicted, or reach economic finality.

This yields concrete unauthorized fund transfer / AA fund loss: the consumer AA executes real payments using a price that only existed transiently and was fully attacker-controlled, with no stabilization checkpoint in between.

### Likelihood Explanation
Reachable by any unprivileged user: defining an `['autonomous agent', ...]` and triggering AAs is a standard, permissionless action available to any unit poster. Chaining a self-serving "oracle" AA into a price-consuming AA in one trigger is a normal, documented AA-composability pattern (see `handleSecondaryTriggers`, and the existing "chain of AAs" tests), meaning the primitives needed for the attack already exist and are exercised in the codebase's own test suite [10](#0-9) . The only prerequisite is that a target AA (attacker's own, or a real DeFi AA with a flexible/attacker-influenceable `oracles` parameter, or one that composes with other AAs for pricing) reads a `data_feed` without requiring `min_mci` to guarantee real stability.

### Recommendation
- For value-transferring logic, require `data_feed`/`in_data_feed` reads to only accept values that are already economically final (i.e., disallow or strongly discourage the unstable/`bAA` fast path for price-critical AA logic; require `min_mci` bounded to a stable point).
- Add provenance/cooldown checks so a `data_feed` value produced by AA `O` cannot be consumed by another AA within the very same primary-trigger cascade that produced it — i.e., disallow same-cascade producer→consumer data_feed reads for a configurable minimum number of MCIs.
- Document prominently for AA authors that `data_feed[[...]]` reads inside AA execution can return values from units that have not reached stability, and that pricing logic must not treat these as final.

### Proof of Concept
1. Deploy AA `O` (oracle): on any trigger, emits `{app:'data_feed', payload:{price: trigger.data.price}}` — an attacker-controlled arbitrary numeric feed, then forwards remaining bytes to AA `V`.
2. Deploy AA `V` (vault/consumer): on trigger, evaluates `data_feed[[oracles="O", feed_name="price"]]` and sends `amount = received_bytes * price` of some asset to `trigger.initial_address`.
3. Attacker sends a single unit: payment to `O` with `data:{price: 999999999}`.
4. Within one atomic `handlePrimaryAATrigger` cascade: `O` executes first, its `data_feed` message is immediately added to `storage.assocUnstableMessages` (per `writer.js:603-613`), then `O`'s bytes-forwarding payment triggers `V` as a secondary trigger in the same cascade; `V`'s formula evaluation reads `O`'s just-posted, completely unstable `price` value via the `bIncludeUnstableAAs` path (`data_feeds.js:205-274`) and pays out based on the attacker-chosen extreme price — before that price has any chance to be reorganized away or reach main-chain stability.
