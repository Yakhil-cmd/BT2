### Title
Webhook Signature Verification Uses a Different Field Than the One Used for Repository/Stack Resolution, Allowing Cross-Organization Forged Events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate an inbound webhook against based on `repository.owner.login` (or `organization.login`) pulled from the **unverified** JSON body, while the downstream event handlers act on a completely different, also-unverified field: `repository.full_name`. In a multi-organization Shipit deployment, this decouples "the organization whose secret authenticated the request" from "the repository whose state is written," breaking the binding `authenticated_org == written_repository`.

### Finding Description
`WebhooksController#verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up a **per-organization** webhook secret when Shipit is configured for multiple GitHub Apps (one per org), as documented and tested: [2](#0-1) [3](#0-2) [4](#0-3) 

`GitHubApp#verify_webhook_signature` only proves that the raw body was HMAC-signed with *that organization's* secret — it says nothing about which repository the body claims to describe: [5](#0-4) 

Once signature verification passes, `WebhooksController#create` dispatches the **entire unverified JSON body** to handlers: [6](#0-5) 

Every handler resolves the target `Stack`/`Repository` using `repository.full_name` from that same body — a field that was never checked against `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) 

Because `repository.owner.login` (used to pick the verification key) and `repository.full_name` (used to pick the acted-upon repository) are independent JSON fields inside the same unsigned-until-verified body, and the signature covers only the raw bytes (not any structural binding between these two fields), an operator of *any* GitHub organization/app configured on the shared Shipit instance can self-craft a webhook body where `repository.owner.login` = their own org (so they can compute a valid HMAC with their own legitimately-known webhook secret) while `repository.full_name` = a stack belonging to a **different** tenant organization on the same instance.

Before vs. after the crafted request:
- Before: `verified_org(request) == acted_upon_repo_org(request)` is an implicit assumption the code relies on but never enforces.
- After the attacker's POST: `verified_org(request) = OrgOne` (attacker's own org secret) while `acted_upon_repo_org(request) = OrgTwo/victim-repo` (a different tenant's stack) — the equality is broken.

### Impact Explanation
Handlers reachable this way include, at minimum:
- `PushHandler`, which triggers `stack.sync_github(expected_head_sha:)` (enqueuing `GithubSyncJob`) for any stack matching the forged branch/repo, causing commit ingestion against a victim stack it does not administer [8](#0-7) .
- `StatusHandler`, which creates a `Status` on any `Commit` matching the forged `sha`, letting the attacker inject a fabricated `success` CI status onto a real commit of a victim stack it does not own [9](#0-8) . Since Shipit gates deploy availability on commit statuses, this can make a victim commit appear "deployable" and is a direct path toward an **unauthorized deploy** on a stack the attacker has no legitimate access to — matching the Critical impact bar ("unauthorized deploy, rollback or merge").
- `PullRequest` handlers (opened/labeled/closed/reopened) resolve `Repository.from_github_repo_name(params.repository.full_name)` the same way and can provision/deprovision review stacks for a victim repository [10](#0-9) .

This satisfies the required binding category: "an organization that authenticated versus the repository that is written" is broken, with a concrete write path (fabricated commit status / sync / review-stack provisioning) into a tenant the attacker does not control.

### Likelihood Explanation
This is only exploitable on Shipit instances configured with the documented multi-organization GitHub App schema (`docs/setup.md`, "Using Multiple Github Applications") [11](#0-10) , where distinct tenant organizations share one Shipit deployment. Any party who legitimately owns/administers one of the configured GitHub Apps (and therefore its own `webhook_secret`) — which by design is an unprivileged, mutually-distrusting tenant relative to the other organizations on the same instance — can compute a valid signature for a body whose `repository.full_name` names another tenant's stack. No GitHub push access, Shipit session, or API token to the victim org is required; the only credential needed is the attacker's own webhook secret for their own org.

### Recommendation
Bind the two fields cryptographically or at minimum reconcile them before dispatch:
- After `verify_signature` succeeds, re-derive the organization strictly from the same field the handlers use (`repository.full_name`'s owner segment, or `repository.owner.login`) and reject the request if the org used to select the webhook secret does not match the owner of `repository.full_name`.
- Alternatively, resolve the target `Stack`/`Repository` and confirm its configured GitHub organization matches the organization whose secret verified the signature before invoking any handler.

### Proof of Concept
Given a Shipit instance configured with two organizations, `OrgOne` and `OrgTwo`, each with its own GitHub App/webhook secret (per `docs/setup.md`'s multi-org schema), and a victim stack tracking `OrgTwo/victim-repo`:

1. Attacker administers `OrgOne`'s GitHub App and therefore knows `OrgOne`'s `webhook_secret`.
2. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" },
  "sha": "<real sha of a commit on the victim stack>",
  "state": "success",
  "context": "ci/build"
}
```
3. Attacker computes `sha1=HMAC-SHA1(OrgOne_webhook_secret, body)` and sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<computed>
```
4. `verify_signature` calls `Shipit.github(organization: 'OrgOne')`, verifies successfully against the attacker's own known secret [12](#0-11) .
5. `StatusHandler#process` runs against `Commit.where(sha: params.sha)`, creating a forged success status on a commit belonging to `OrgTwo/victim-repo`, a repository the attacker has no legitimate relationship with [9](#0-8) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
