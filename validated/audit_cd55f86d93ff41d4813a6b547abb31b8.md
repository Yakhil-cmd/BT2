### Title
EIP-7702 Delegation Breaks `isContractAddr` EOA/Contract Distinction in Treasury Rebalance System Contracts — (`contracts/testing/system_contracts/TreasuryRebalance.sol`, `TreasuryRebalanceV2.sol`)

---

### Summary

`TreasuryRebalance.sol` and `TreasuryRebalanceV2.sol` use `extcodesize` via `isContractAddr()` to distinguish EOAs from contracts in their `approve()` and `checkRetiredsApproved()`/`checkZeroedsApproved()` functions. Under EIP-7702 (enabled in Kaia's Prague hardfork), a delegated EOA carries a 23-byte delegation designator (`0xef0100` + 20-byte target), making `extcodesize` return 23. This breaks the EOA/contract distinction, causing the approval workflow to misroute a delegated EOA into the contract path, where it calls `getState()` on the delegation target. If the target does not implement `getState()`, the call reverts and blocks `finalizeApproval()`, preventing the treasury rebalance from executing. These contracts are production system contracts confirmed by Go bindings in `contracts/bindings/rebalance/` and direct use in `blockchain/system/rebalance.go`.

---

### Finding Description

**Root cause — `isContractAddr` uses `extcodesize`:** [1](#0-0) [2](#0-1) 

Both contracts implement:
```solidity
function isContractAddr(address _addr) public view returns (bool) {
    uint256 size;
    assembly { size := extcodesize(_addr) }
    return size > 0;
}
```

Under EIP-7702, `extcodesize` of a delegated EOA returns 23 (the delegation prefix `0xef0100` + 20-byte target address), so `isContractAddr` returns `true` for any 7702-delegated EOA.

**Bifurcated approval logic in `approve()`:** [3](#0-2) 

```solidity
bool isContract = isContractAddr(_retiredAddress);
if (!isContract) {
    require(msg.sender == _retiredAddress, "retiredAddress is not the msg.sender");
    _updateApprover(_retiredAddress, msg.sender);
} else {
    (address[] memory adminList, ) = _getState(_retiredAddress);  // calls getState() on the address
    require(_validateAdmin(msg.sender, adminList), "msg.sender is not the admin");
    _updateApprover(_retiredAddress, msg.sender);
}
```

The same bifurcation exists in `TreasuryRebalanceV2.approve()`: [4](#0-3) 

**Re-evaluation at `finalizeApproval()` time:**

`checkRetiredsApproved()` and `checkZeroedsApproved()` re-run `isContractAddr` at finalization time, not at approval time: [5](#0-4) [6](#0-5) 

This means the EOA/contract classification can change between `approve()` and `finalizeApproval()`.

**EIP-7702 is live in Kaia's Prague hardfork:** [7](#0-6) [8](#0-7) 

**Production use — `RebalanceTreasury` directly zeroes balances:** [9](#0-8) 

The core calls `CheckZeroedsApproved` (line 296) and then executes `state.SetBalance(addr, big.NewInt(0))` for every zeroed address. If `CheckZeroedsApproved` reverts, the rebalance aborts.

---

### Impact Explanation

**Primary impact — DoS on treasury rebalance finalization:**

1. EOA `A` is registered as "zeroed" (holds treasury KAIA to be redistributed).
2. EOA `A` calls `approve(A)` — at this point `isContractAddr(A)` returns `false`, so the `msg.sender == A` path succeeds and the approval is recorded.
3. EOA `A` subsequently submits a `TxTypeEthereumSetCode` transaction to delegate to contract `C` (for any reason — e.g., adopting a smart wallet).
4. The contract owner calls `finalizeApproval()`, which calls `checkZeroedsApproved()`.
5. `isContractAddr(A)` now returns `true` (extcodesize = 23).
6. `_getState(A)` is called, which executes `C`'s code via the delegation. If `C` does not implement `getState()`, the call reverts.
7. `finalizeApproval()` reverts. The contract cannot advance to `Approved` status.
8. `RebalanceTreasury` in the core reads `status != 2` → returns `ErrRebalanceBadStatus` → the treasury rebalance does not execute at the target block.

**Secondary impact — unauthorized approval bypass:**

If EOA `A` delegates to a contract `C` that implements `getState()` returning an attacker-controlled admin list, any address in that list can call `approve(A)` and record a valid approval — bypassing the `msg.sender == A` identity check that was the intended guard for EOA-registered addresses. Combined with `checkZeroedsApproved()` accepting this approval, the rebalance can be finalized with a forged consent, causing `state.SetBalance(A, 0)` to execute against `A`'s KAIA balance.

---

### Likelihood Explanation

**DoS path**: Moderate. Any "zeroed"/"retired" EOA that adopts EIP-7702 delegation (e.g., for smart-wallet use) between the `approve()` call and `finalizeApproval()` triggers this. The EOA owner need not intend to block the rebalance; the delegation is set up for unrelated reasons. The window between `approve()` and `finalizeApproval()` is explicitly designed to be open (the contract owner calls `finalizeApproval()` after collecting all approvals).

**Bypass path**: Low. Requires the EOA owner to deliberately delegate to a contract implementing `getState()` with an attacker-controlled admin list. The EOA owner must sign the EIP-7702 authorization, making them complicit. However, the EOA owner may not realize this breaks the rebalance contract's approval model.

---

### Recommendation

Update `isContractAddr` in both contracts to detect and exclude EIP-7702 delegation designators (prefix `0xef0100`, total length 23 bytes):

```solidity
function isContractAddr(address _addr) public view returns (bool) {
    uint256 size;
    assembly { size := extcodesize(_addr) }
    if (size == 23) {
        bytes memory prefix = new bytes(3);
        assembly { extcodecopy(_addr, add(prefix, 32), 0, 3) }
        // EIP-7702 delegation designator: 0xef0100
        if (uint8(prefix[0]) == 0xef &&
            uint8(prefix[1]) == 0x01 &&
            uint8(prefix[2]) == 0x00) {
            return false; // treat delegated EOA as EOA
        }
    }
    return size > 0;
}
```

This mirrors the `ParseDelegation` logic already present in the Kaia Go codebase: [10](#0-9)

### Proof of Concept

**Setup:**
- Deploy `TreasuryRebalanceV2` with `rebalanceBlockNumber = N`.
- Register EOA `A` (controlled by key `k_A`) as a zeroed address.
- Register allocated address `B` with some amount.
- Call `finalizeRegistration()`.

**Step 1 — EOA approves:**
```
// EOA A calls approve(A)
// isContractAddr(A) = false (no code yet)
// msg.sender == A → passes
// A's approval recorded: zeroeds[0].approvers = [A]
```

**Step 2 — EOA sets up 7702 delegation:**
```
// EOA A submits TxTypeEthereumSetCode with auth:
//   auth = { chainId, address: C, nonce: n, v, r, s }
// where C implements getState() returning ([attacker], 1)
// After this tx: extcodesize(A) == 23
```

**Step 3 — Owner calls `finalizeApproval()`:**
```
// checkZeroedsApproved() iterates zeroeds
// isContractAddr(A) = true  ← changed!
// _getState(A) calls A.getState()
//   → executes C's code via delegation
//   → if C has no getState(): REVERT → finalizeApproval() fails
//   → if C returns ([attacker], 2): approvers.length(1) < req(2) → REVERT
```

**Result:** `finalizeApproval()` reverts. The contract status never reaches `Approved`. At block `N`, `RebalanceTreasury` reads `status != 2` and returns `ErrRebalanceBadStatus`. The treasury rebalance does not execute. All zeroed addresses retain their balances; all allocated addresses receive nothing. [11](#0-10) [4](#0-3) [6](#0-5) [2](#0-1)

// DelegationPrefix is used by code to denote the account is delegating to
// another account.
var DelegationPrefix = []byte{0xef, 0x01, 0x00}

// ParseDelegation tries to parse the address from a delegation slice.
func ParseDelegation(b []byte) (common.Address, bool) {
	if len(b) != 23 || !bytes.HasPrefix(b, DelegationPrefix) {
		return common.Address{}, false
	}
	var addr common.Address
	copy(addr[:], b[len(DelegationPrefix):])
	return addr, true
}

func RebalanceTreasury(state *state.StateDB, chain backends.BlockChainForCaller, header *types.Header) (*rebalanceResult, error) {
	var (
		err    error
		caller RebalanceCaller

		result   = newRebalanceReceipt()
		isKIP160 = chain.Config().IsKIP160ForkBlock(header.Number)
		isKIP103 = chain.Config().IsKIP103ForkBlock(header.Number)
	)

	if isKIP160 {
		caller, err = rebalance.NewTreasuryRebalanceV2Caller(chain.Config().Kip160ContractAddress, backends.NewBlockchainContractBackend(chain, nil, nil))
	} else if isKIP103 {
		caller, err = NewKip103ContractCaller(state, chain, header)
	} else {
		return nil, errors.New("rebalancing shouldn't be executed unless the block number is kip103 or kip160 hard fork")
	}
	if err != nil {
		return nil, err
	}

	// Retrieve 1) Get Zeroed
	if err = result.fillZeroed(caller, state); err != nil {
		return result, err
	}

	// Retrieve 2) Get Allocated
	if err = result.fillAllocated(caller, state); err != nil {
		return result, err
	}

	// Validation 1) Check the target block number
	if blockNum, err := caller.RebalanceBlockNumber(nil); err != nil || blockNum.Cmp(header.Number) != 0 {
		return result, ErrRebalanceIncorrectBlock
	}

	// Validation 2) Check whether status is approved. It should be 2 meaning approved
	if status, err := caller.Status(nil); err != nil || status != 2 {
		return result, ErrRebalanceBadStatus
	}

	// Validation 3) Check approvals from zeroeds
	if err = caller.CheckZeroedsApproved(nil); err != nil {
		return result, err
	}

	// Validation 4) Check the total balance of zeroeds are bigger than the distributing amount
	totalZeroedAmount := result.totalZeroedBalance()
	totalAllocatedAmount := result.totalAllocatedBalance()
	if isKIP103 && totalZeroedAmount.Cmp(totalAllocatedAmount) < 0 {
		return result, ErrRebalanceNotEnoughBalance
	}

	// Execution 1) Clear all balances of zeroeds
	for addr := range result.Before.Zeroed {
		state.SetBalance(addr, big.NewInt(0))
		result.After.Zeroed[addr] = big.NewInt(0)
	}
	// Execution 2) Distribute KAIA to all allocateds
	for addr, balance := range result.After.Allocated {
		// if an allocated has KAIA before the allocation, it will be burnt
		currentBalance := state.GetBalance(addr)
		result.Burnt.Add(result.Burnt, currentBalance)

		state.SetBalance(addr, balance)
	}
