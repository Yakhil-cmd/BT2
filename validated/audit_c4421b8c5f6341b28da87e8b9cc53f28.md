### Title
Cross-repository Status forgery via unscoped `sha` lookup in `StatusHandler#process` combined with attacker-controlled `created_at` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit solely by `Commit.where(sha: params.sha)`, with no check that the commit belongs to the repository whose webhook secret was used to authenticate the request. An attacker who legitimately controls a separate, Shipit-onboarded repository (their own fork or a repository sharing history with the victim, so that a commit `sha` collides) can send a validly-signed `status` webhook for their own org and write an arbitrary `Status` (`state`, `context`, `description`, `target_url`, and attacker-chosen `created_at`) onto a victim stack's commit. This flips `Commit#status`'s hierarchy-based (first-failure-wins) result and hence `deployable?`/`blocked?` for the victim stack.

### Finding Description
The broken binding is: `signature verified for repository_owner == org that authorized the webhook` should equal `stack/repository that the resulting Status record is written into`, but it does not.

- `WebhooksController#verify_signature` only checks that the payload is signed with the secret belonging to the org named in `params.dig('repository','owner','login')` (`app/controllers/shipit/webhooks_controller.rb:24-49`). It authenticates *an org*, not that the org matches the commit the payload will mutate.
- `Handler` provides a `stacks`/`repository_name` helper explicitly meant for this kind of scoping (`app/models/shipit/webhooks/handlers/handler.rb:30-38`), and other handlers (`opened_handler.rb`, `edited_handler.rb`, etc.) use `Repository.from_github_repo_name(params.repository.full_name)` to scope writes to the correct repository.
- `StatusHandler#process` does **not** use this at all: [1](#0-0) 
It looks up commits globally by `sha` across the entire `commits` table, with no `stack_id`/`repository` filter.
- For each matched commit (which belongs to whatever stack it belongs to, irrelevant of the authenticated org), it calls `create_status_from_github!(params)`, which delegates to: [2](#0-1) 
- `Status.replicate_from_github!` writes the attacker-supplied `created_at` verbatim, and it also participates in the `find_or_create_by!` uniqueness key, so the attacker fully controls whether a new row is created or an existing one is matched: [3](#0-2) 
- `params.created_at` is only typed as `String` with no format/monotonicity/clock validation: [4](#0-3) 
- `Commit#statuses` is ordered `created_at DESC`, and `Status::Group` (used by `Commit#status`) does `statuses.to_a.uniq(&:context)`, which keeps the *first* (i.e., most-recent-by-created_at) entry per context — an attacker-forged status with a newer `created_at` and the same `context` as a legitimate one silently displaces it: [5](#0-4) [6](#0-5) 
- Even without matching `context`, `select_significant_status` implements first-failure-wins hierarchy: any injected non-success status becomes the commit's significant status: [7](#0-6) 
- `Commit#status` is what `deployable?`, `blocked?`, and CI/CD scheduling (`add_status`, `schedule_continuous_delivery`, `Hook.emit(:deployable_status, ...)`) all rely on: [8](#0-7) [9](#0-8) 

**Attack**: attacker owns/administers a repository already onboarded to the same Shipit instance (so they legitimately know that repo's webhook secret, e.g. because they configured the GitHub App/webhook themselves, which is a normal, unprivileged onboarding action for a repo they control). They arrange for a commit sha in their own repo to be identical to a commit sha tracked in a victim's stack (trivial via forking an unmodified upstream history, cherry-picking, or reusing well-known identical commits such as empty initial commits). Their own CI posts a real, correctly-signed GitHub `status` webhook for that sha with attacker-chosen `state`, `context`, and `created_at`. `StatusHandler#process` finds *every* `Commit` row across the whole database with that sha — including the victim's — and writes the forged `Status` onto it.

None of the existing guards prevent this: `verify_signature` validates org identity but not repo-to-commit binding; `drop_unhandled_event`/`ExplicitParameters` only validate payload shape; there is no `Repository`/`stack` filter anywhere in `StatusHandler`.

### Impact Explanation
A payload authenticated for one repository/org mutates another tenant's `Status` records, directly altering `Commit#status` (hierarchy, first-failure-wins) for a stack the attacker does not own. This can flip `deployable?`/`blocked?`, suppress a legitimate failing status (enabling an unauthorized deploy of a broken commit) or inject a false failure (blocking a victim's legitimate deploy), and triggers `Hook.emit(:deployable_status, ...)`/`schedule_continuous_delivery`. This matches the Critical category "a payload for one repository mutating another's stack, commit... or an unauthorized deploy." Blast radius is any commit sha collision across tenants sharing the same Shipit instance, and is repeatable per matching sha.

### Likelihood Explanation
Requires: (1) attacker legitimately controls a repository/org already onboarded to the target Shipit instance (so they know that org's webhook secret — a normal precondition for any org using Shipit, not a privilege escalation), and (2) a commit sha collision with the victim's tracked commit, which is realistic for forked/mirrored histories or well-known identical commits (not a cryptographic SHA-1 collision). Cost is low — a single crafted/replayed webhook POST. Feasibility is moderate-to-high in any multi-tenant Shipit deployment; repeatable at will.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup by the repository the authenticated webhook belongs to (mirroring the pattern already used in other handlers via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`/`stacks`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining `commits` to `stacks`/`repositories` matching the payload's `repository.full_name`. Additionally, do not trust client-supplied `created_at` for ordering-sensitive writes without validating it against server time / commit creation time, and ideally derive it from `Time.current` when not previously recorded.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub):
1. Create `stack_a` (victim) and `stack_b` (attacker), each with a `Commit` sharing the identical `sha: "deadbeef..."` but different `stack_id`.
2. Give the victim commit an existing passing `Status` (`context: "ci/build"`, `state: "success"`, `created_at: 1.hour.ago`).
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` where `payload['repository']['full_name']` is `stack_b`'s repo, `sha` is the shared sha, `state: "failure"`, `context: "ci/build"`, `created_at: Time.current.iso8601`.
4. Assert: `victim_commit.reload.status.state == "success"` before the call, and after the call `victim_commit.status.state == "failure"` (hierarchy flips due to the injected status with newer `created_at` winning `uniq(&:context)` and being non-success) — demonstrating cross-repo mutation of the victim's hierarchy purely from a payload authenticated for `stack_b`'s repository.
5. Assert `Shipit::Status.where(stack_id: stack_a.id, context: "ci/build").count == 2` (i.e., the forged status was written under the victim's `stack_id`, not the attacker's), proving the write crossed the tenant boundary.
