## Title
Unbounded `eventBus` listener accumulation via unresolved `payment_notification` device messages leads to permanent memory leak (analog of CVE‑2016‑9916) - (File: wallet.js)

### Summary
CVE‑2016‑9916 is a QEMU memory leak where an untrusted guest can repeatedly trigger a code path that is missing a cleanup operation in the 9p-proxy backend, causing unbounded host memory growth. The closest reachable analog in `ocore` is in the wallet device-message handler `handleMessageFromHub`, in the `payment_notification` case, where an `eventBus.once` listener is registered for a unit that the caller fully controls, and that listener is only removed if the referenced unit is ever locally received/saved. Any paired device correspondent (an attacker who has established or intercepted a pairing) can send an unbounded stream of `payment_notification` messages, each referencing a unit hash that will never actually be broadcast/saved, causing permanent, unbounded accumulation of listeners and closures on the shared `eventBus`.

### Finding Description
In `wallet.js`, the `payment_notification` message subject is handled as: [1](#0-0) 

```js
case 'payment_notification':
    var current_message_counter = ++message_counter;
    var unit = body;
    if (!ValidationUtils.isStringOfLength(unit, constants.HASH_LENGTH))
        return callbacks.ifError("invalid unit in payment notification");
    var bEmitted = false;
    var emitPn = function(objJoint){
        if (bEmitted) return;
        bEmitted = true;
        emitNewPublicPaymentReceived(from_address, objJoint.unit, current_message_counter);
    };
    eventBus.once('saved_unit-'+unit, emitPn);
    storage.readJoint(db, unit, {
        ifNotFound: function(){
            console.log("received payment notification for unit "+unit+" which is not known yet, will wait for it");
            callbacks.ifOk();
        },
        ifFound: function(objJoint){
            emitPn(objJoint);
            eventBus.removeListener('saved_unit-'+unit, emitPn);
            callbacks.ifOk();
        }
    });
    break;
```

The only requirement to reach `ifNotFound` (and thus register a permanent `eventBus.once('saved_unit-'+unit, emitPn)` listener that is *never* removed) is that `unit` is a syntactically valid 44-byte base64 hash string that does not yet exist in local storage — this is entirely attacker-controlled: the sender only needs to supply an arbitrary, non-existent (but well-formed) unit hash. Since this hash will never correspond to a real unit that gets saved, `saved_unit-<hash>` will never fire, and the registered listener (plus its closure over `from_address`, `current_message_counter`, `bEmitted`) is retained by the `eventBus` singleton (`event_bus.js`) forever. [2](#0-1) 

Because a single correspondent can send an unlimited number of such messages (each with a distinct fake hash), the number of registered `saved_unit-*` event names and listener closures grows without bound — this is the same bug class as CVE‑2016‑9916: a "missing cleanup operation" reachable by an untrusted peer causing host/process memory consumption (and possibly process crash from `EventEmitter` warnings/OOM). The `eventBus.setMaxListeners(40)` guard only limits listeners *per event name*, not per unique event name, so it does not mitigate this leak since each notification uses a distinct `'saved_unit-'+unit` key.

For contrast, the sibling code path in `private_profile.js` has the exact same missing-cleanup pattern (an `eventBus.once('saved_unit-'+unit, handleJoint)` that is removed only on an explicit `network.requestHistoryFor` error, never on success/timeout when the unit never arrives): [3](#0-2) , corroborating that this is a systemic pattern rather than an isolated typo.

### Impact Explanation
This does not directly enable spending fraud, double-spends, or AA fund loss, but it satisfies the accepted-impact bar of "a network unable to confirm new units" in a degraded sense at the node level: continuous unbounded memory growth on a full/light wallet node processing device messages from a malicious or compromised paired correspondent will eventually exhaust process memory, causing the node/wallet process to crash or become unresponsive (denial of service), mirroring the QEMU host-memory-exhaustion impact of CVE‑2016‑9916. Because `wallet.js` message handling underlies wallet operation for private payments/pairing, sustained exploitation can render the wallet client unusable, disrupting a user's ability to receive/confirm transactions.

### Likelihood Explanation
Likelihood is High for any already-paired correspondent (a normal, unprivileged wallet-to-wallet relationship established through the standard pairing/chat flow) since:
- No cryptographic material or elevated privilege is needed beyond an existing device pairing.
- The attacker only needs to send `payment_notification` messages with syntactically valid but never-to-be-broadcast unit hashes (e.g., freshly-generated random 32-byte values, base64-encoded).
- The message is processed automatically without user interaction, and the handler always returns `ifOk()`, giving the attacker no negative feedback and unlimited retry capability.

### Recommendation
- Bound the lifetime of the `eventBus.once('saved_unit-'+unit, emitPn)` registration with a timeout (e.g., `setTimeout` that calls `eventBus.removeListener('saved_unit-'+unit, emitPn)` after a fixed window such as a few minutes), mirroring the pattern already used elsewhere for `assocUnitsWaitingForPrunedContent` expiry.
- Alternatively, track outstanding notification units in a bounded map keyed by unit hash and reject/ignore new notifications from the same correspondent once a per-peer or global cap is reached.
- Apply the same fix to the analogous listener leak in `private_profile.js`'s `parseAndValidatePrivateProfile`.

### Proof of Concept
1. Establish a normal device pairing with a victim wallet (as any legitimate correspondent).
2. Repeatedly send device messages of type `payment_notification` where `body` is a freshly-generated random, well-formed 44-character base64 string (valid `HASH_LENGTH`) that does not correspond to any real unit and will never be broadcast.
3. Each message causes the victim's `handleMessageFromHub` to hit the `ifNotFound` branch and register a new permanent `eventBus.once('saved_unit-'+unit, emitPn)` listener that is never cleaned up. [4](#0-3) 
4. Repeat indefinitely; observe steady, unbounded growth in the victim process's `eventBus`/`EventEmitter` internal listener maps and overall heap usage until the process degrades or crashes.
