### Title
Global oracle "last-update" monotonic-timestamp cache can be poisoned by a future-dated price feed, freezing price resolution for all users of that asset - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`v0-4-market.clar` validates freshness of oracle price feeds with `oracle-timestamp-fresh`, then persists the feed's timestamp into a **global, shared** map `last-update` keyed only by `{type, ident}` (i.e. per price-feed, not per user/tx). Any unprivileged caller can drive this write by simply passing `price-feeds` into any public function (`borrow`, `collateral-add`, etc.), which internally calls `write-feeds` → `price-resolve`. Because the freshness check special-cases timestamps that are ahead of `stacks-block-time` (treating them as automatically "fresh" with `delta = 0`), a caller who submits (or merely relays, via legitimate Pyth relaying/clock skew) a price whose `publish-time` is even slightly ahead of the chain's current `stacks-block-time` can push that future timestamp into the shared `last-update` map. Every subsequent price resolution for that same feed - triggered by any other, unrelated user - then fails the monotonic check `(>= ts prev)` until real time/Pyth publish-time catches up to the poisoned value, since a correct, later Pyth update will still have a timestamp smaller than the artificially-inflated `prev`.

This means a future-dated feed timestamp is accepted as "fresh" instead of being rejected as invalid, and is also `>= prev` (since it's larger than anything seen so far), so it passes the monotonicity check too.

`price-resolve` then unconditionally records this timestamp into the shared, feed-keyed map whenever it's newer than the currently stored value: [2](#0-1) 

The map itself has no per-user or per-transaction scoping - it is one entry per `{type, ident}` shared by the entire protocol: [3](#0-2) 

`write-feeds` is reachable from any public market entry point via the caller-supplied `price-feeds` parameter (`borrow`, `collateral-add`, etc. all take `(price-feeds (optional (list 3 (buff 8192))))` and call `write-feeds` before resolving prices): [4](#0-3) [5](#0-4) 

Because `write-feeds`/`price-resolve` accepts any valid Pyth-signed feed the caller decides to relay, and Pyth-signed `publish-time` can (even without malicious intent, due to normal cross-chain propagation/clock skew) exceed the current Stacks block's `stacks-block-time`, this is a write into shared global state by one caller that is then read/consumed by every other unrelated caller who subsequently needs a price for that same asset. Once `last-update` is inflated with a future timestamp, all legitimate subsequent price updates for that feed (which necessarily carry smaller, correct timestamps until real time actually reaches the poisoned value) will fail `(>= ts prev)` and revert with `ERR-ORACLE-INVARIANT`, blocking price resolution for that asset entirely.

### Impact Explanation
Attacker: any address able to call a public market function with a `price-feeds` payload (no special privilege required). Victim: any other user needing a live price for the affected asset (to borrow, add/remove collateral, or be liquidated). Shared state: the global `last-update` map, keyed only by `{type, ident}`, with no isolation between callers.

With the attacker's poisoning transaction: `last-update` for the targeted feed is set to a value in the future relative to true Pyth publish-time. Without it: `last-update` tracks the true, correctly-increasing publish-time and normal price resolution proceeds.

Victims cannot borrow, add/remove collateral, or have unhealthy positions correctly liquidated for the affected asset until real-world/Pyth time exceeds the poisoned timestamp - this is a temporary freezing of funds impact (in-scope, matching the report's DoS-by-shared-state-poisoning bug class), and if the poisoning window coincides with a price move, positions that should be liquidated cannot be, risking additional loss to lenders.

### Likelihood Explanation
The special-case in `oracle-timestamp-fresh` that auto-passes any `ts > stacks-block-time` is a logic gap in this code, not a third-party oracle content error - a well-formed, signed, but slightly-future-dated feed (a routine occurrence with cross-chain price oracles due to network latency/clock differences) is enough to trigger the poisoning; no oracle compromise or forged signature is required. Any user can invoke `write-feeds` at will through ordinary public market calls.

### Recommendation
Reject feed timestamps that are ahead of `stacks-block-time` (treat `ts > stacks-block-time` as invalid, not as automatically fresh), and/or bound how far a stored `last-update` value may exceed the current block time before it can be relied upon to reject smaller-but-still-valid future timestamps.

### Proof of Concept
1. Attacker (or any relayer) observes a Pyth-signed price update for asset `X` whose `publish-time` is `T+Δ` while the current Stacks block's `stacks-block-time` is `T` (Δ arises from normal propagation lag/clock skew, no forgery needed).
2. Attacker calls any public market function (e.g., `borrow`) supplying this feed via `price-feeds`, triggering `write-feeds` → `price-resolve`. Because `ts(T+Δ) > stacks-block-time(T)`, `oracle-timestamp-fresh` returns `delta = 0`, passing staleness and monotonicity checks; `last-update` for `{type, ident}` is set to `T+Δ`.
3. A later block advances `stacks-block-time` to some `T' < T+Δ` (real Pyth publishes are correctly increasing but still behind the poisoned value). Any other user (victim) calling `borrow`/`collateral-add`/liquidation for the same asset submits the correct, newer, legitimate feed with `publish-time = T'' < T+Δ`.
4. `oracle-timestamp-fresh` evaluates `(>= T'' (T+Δ))` as `false`, so `price-resolve` returns `ERR-ORACLE-INVARIANT`, and the victim's transaction reverts - denying price resolution (and therefore borrow/collateral/liquidation) for that asset for every user until real publish-time surpasses `T+Δ`.

  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
