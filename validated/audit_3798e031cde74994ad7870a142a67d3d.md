### Title
Signature verification keyed on `repository.owner.login` while repository/stack resolution keyed on `repository.full_name` allows cross-organization forgery of `pull_request` webhooks that mutate another org's `PullRequest`/`ReviewStack` - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret to check with `Shipit.github(organization: repository_owner)`, where `repository_owner` is derived solely from `params.dig('repository','owner','login')`. `LabelCapturingHandler` (and its siblings) instead resolve the actual `Repository`/`Stack` to mutate via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, a completely independent field. Because `verify_webhook_signature` returns `true` unconditionally when the selected organization has no `webhook_secret` configured, an attacker can pick an org name with no secret for `repository.owner.login` while pointing `repository.full_name` at a victim org's real repository, letting an unsigned/forged payload write into the victim's `PullRequest` record and stack environment.

### Finding Description
The broken binding the code implicitly assumes is:
`org_used_to_verify_signature (params.repository.owner.login) == org_that_owns_the_mutated_repository (params.repository.full_name.split('/').first)`

This is never enforced. Tracing the path:

- `Shipit::WebhooksController#verify_signature` computes `repository_owner` purely from `params.dig('repository','owner','login')` (fallback `organization.login`), and fetches the GitHub App config for *that* org only: [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for that org, regardless of the signature header supplied: [3](#0-2) 
- Once signature check passes, `WebhooksController#create` dispatches to every registered handler with the raw, attacker-controlled `params`, with no re-validation of which org authenticated the request: [4](#0-3) 
- `LabelCapturingHandler#repository` resolves the mutated `Repository` using an entirely different field, `params.repository.full_name`, via `Shipit::Repository.from_github_repo_name`: [5](#0-4) 
- `Repository.from_github_repo_name` splits `owner/name` straight out of `full_name` and does a plain DB lookup, with no cross-check against `repository.owner.login`: [6](#0-5) 
- For a `reopened` action on an existing, non-archived review stack, `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` onto `stack.pull_request`: [7](#0-6) [8](#0-7) 
- `ReviewStack#env` then folds those attacker-controlled label names, upcased, into the stack's deploy environment as `"true"`-valued variables: [9](#0-8) 

**Attacker's exact request:** an unauthenticated `POST /webhooks` with header `X-Github-Event: pull_request` and a JSON body where `repository.owner.login = "attacker-controlled-no-secret-org"` (any org name configured in Shipit with no `webhook_secret`, or unconfigured but not raising `GithubOrganizationUnknown` — any org present in Shipit's github app config with a blank secret satisfies `return true unless webhook_secret`), while `repository.full_name = "victim-org/victim-repo"` matches a real `Repository` with an active `ReviewStack` for the PR's head ref, `action = "reopened"`, and an arbitrary `labels` array.

**Why existing guards fail:** `verify_signature` only asserts that *some* signing secret matched *some* org named in the payload's `repository.owner.login` field — it never asserts that this org is the owner of the repository named in `repository.full_name`, which is what every downstream handler (`LabelCapturingHandler`, `ClosedHandler`, `OpenedHandler`, `ReopenedHandler`, etc.) actually operates on. `drop_unhandled_event`, the `ExplicitParameters` schema (which only requires `full_name` be a `String`, not that it match `owner.login`), and `Repository.from_github_repo_name` provide no cross-validation either.

### Impact Explanation
An attacker with no Shipit credentials can forge a `pull_request` webhook, satisfy signature verification against an org they control or that has no configured secret, and have the payload write into a **different** organization's `PullRequest` record and `ReviewStack` deploy environment — this is a payload from one repository mutating another repository's stack state, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The immediate effect is arbitrary environment-variable injection (`LABEL_NAME=true`) into the victim stack's deploy/task commands via `ReviewStack#env`, which can flip conditional deploy logic depending on how the victim's deploy scripts consume these env vars, and (per the question's framing) combine with status-forging paths to set/clear `blocked?` on stacks with `blocking_statuses` configured, gating or forcing deploys. This is repeatable against any victim org/repo that has an active review stack, requiring only that the attacker find any Shipit-configured org lacking a webhook secret to use as the forged `owner.login`.

### Likelihood Explanation
Preconditions: (1) the victim org has `review_stacks_enabled` with an active, non-archived `ReviewStack` matching the forged PR's head ref; (2) some org name known to Shipit's config has no `webhook_secret` set (a realistic misconfiguration/staging-org scenario, or the attacker's own registered org used purely to satisfy the "known organization" check), or the attacker otherwise controls a valid secret for an org they name in `owner.login`. Attacker cost is a single unauthenticated HTTP POST with no need to know any Shipit or GitHub secret, and the attack is fully repeatable against arbitrary target stacks by varying `full_name`.

### Recommendation
Verify the webhook signature using the organization implied by `repository.full_name` (or, better, cross-check that `repository.owner.login` matches the owner segment of `repository.full_name` before proceeding), and reject the request if they diverge. Additionally, every handler that resolves a `Repository`/`Stack` via `full_name` should assert that the authenticated organization (the one whose secret validated the signature) matches the owner of that repository before performing any writes.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure two orgs in `Shipit.github_apps` config: `"attacker-org"` with `webhook_secret: nil`/blank, and `"victim-org"` with a real `webhook_secret`.
2. Create `Shipit::Repository.create!(owner: "victim-org", name: "victim-repo")`, a `Shipit::ReviewStack` for it with `blocking_statuses` configured and an associated `pull_request` whose current `labels` is `[]`, matching a known head ref.
3. Build a `pull_request` `reopened` payload: `repository.owner.login = "attacker-org"`, `repository.full_name = "victim-org/victim-repo"`, `pull_request.head.ref` matching the existing review stack's branch, `pull_request.labels = [{name: "MALICIOUS_FLAG"}]`.
4. POST to `/webhooks` with `X-Github-Event: pull_request` and any/garbage `X-Hub-Signature` (or omit it) — assert response is `200 OK` (not `422`), proving signature verification passed via the secret-less `attacker-org`.
5. Reload the victim's `pull_request` record and assert `pull_request.labels == ["MALICIOUS_FLAG"]` (before: `[]`, after: attacker-controlled value) — proving cross-org write.
6. Assert `review_stack.env["MALICIOUS_FLAG"] == "true"`, demonstrating the attacker-controlled environment variable injected into the victim's deploy environment, satisfying the equality-violation check: `repository.owner.login ("attacker-org") != full_name_owner ("victim-org")` yet the write succeeded.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
