### Title
Unauthenticated Device Message Crashes the Node via Unhandled `setTimeout` Exception — ([File: device.js])

### Summary
Any party that knows a wallet's device address (learned from pairing links, invoices, shared addresses, etc. — no correspondent relationship or authentication required) can send a crafted `hub/message` whose `encrypted_package` is addressed to an unrecognized ephemeral/permanent key. `decryptPackage()` responds to this case not with a normal error return but by scheduling a `throw Error(...)` inside a bare `setTimeout`, i.e. outside any `try/catch`. Because `network.js` installs a global `process.on('uncaughtException', ...)` handler that deliberately re-throws to kill the process, this single unauthenticated message brings down the entire node — the same bug class as CVE-2021-32795 (ASF DoS via a crafted, unauthenticated chat message causing a process crash through an uncaught exception in message handling).

### Finding Description
`handleJustsaying(ws, 'hub/message', body)` in `device.js` only checks that the message is internally consistent (hash matches, signature matches the attacker-controlled `pubkey`) and that `objDeviceMessage.to === getMyDeviceAddress()`. It does **not** require the sender to be a known correspondent before attempting to decrypt: [1](#0-0) 

The decryption is delegated to `decryptPackage()`. When the `dh.recipient_ephemeral_pubkey` field does not match the node's current temp key, previous temp key, or permanent key (trivially the case for any attacker who doesn't know these private/derived values), the function does not fail gracefully — it schedules an unconditional `throw` via `setTimeout`: [2](#0-1) 

Because this `throw` executes inside a `setTimeout` callback, it is not caught by the `try { doHandle() } catch (e) { ... }` wrapper used elsewhere (e.g. in `wallet.js`'s `handleMessageFromHub`), nor by any caller of `decryptPackage`. It becomes an uncaught exception at the process level. `network.js` explicitly re-throws on `uncaughtException` in order to "crash the process to avoid ending up in an inconsistent state": [3](#0-2) 

The result: a single unauthenticated device message with a bogus `recipient_ephemeral_pubkey` terminates the whole ocore process (wallet, full node, or hub instance), exactly mirroring the ASF advisory's pattern of an unauthenticated/unauthorized message reaching unguarded exception-prone code that the runtime turns into a fatal crash.

### Impact Explanation
This is a remote, unauthenticated Denial of Service against any ocore-based node/wallet that has device messaging enabled (which is virtually all wallets, since it underlies pairing, chat, private payments, and AA-related notifications). A single crafted `hub/message` justsaying — requiring only knowledge of the victim's device address, not correspondent status or any secret — kills the node process. Repeated attacks can keep a node offline indefinitely, preventing it from validating/relaying units, participating in consensus-relevant witnessing, or processing private payments, i.e., "a network unable to confirm new units" for the affected node's operator.

### Likelihood Explanation
High. Device addresses are not secret in the way private keys are — they are exchanged during pairing (via pairing URLs/QR codes) and are visible to hubs and to the receiving device's justsaying relay path. Any actor who has ever exchanged a pairing invitation or otherwise obtained a target's device address (e.g., an untrusted or later-unpaired party, or a hub itself relaying arbitrary crafted content) can trigger the crash without needing to break any cryptography — they only need their own valid keypair and to set an unpredictable/incorrect `recipient_ephemeral_pubkey`.

### Recommendation
- Wrap the "unknown key" branch of `decryptPackage()` so that the failure is reported synchronously (`return null` / emit `nonfatal_error`) instead of scheduling an unguarded `throw` in `setTimeout`.
- Remove or gate the `process.on('uncaughtException')` re-throw behavior so that a single malformed/malicious message cannot unconditionally kill the whole process; at minimum, ensure all message-handling code paths (including deferred/async callbacks) funnel errors through recoverable error handling rather than relying on the global handler.
- Add validation/rate limiting for `hub/message` senders who are not known correspondents before allowing them to trigger decryption attempts.

### Proof of Concept
1. Attacker generates an arbitrary secp256k1 keypair and derives their own `pubkey`/device address.
2. Attacker crafts `objDeviceMessage` with `to` = victim's known device address, `encrypted_package` containing syntactically valid `iv`, `authtag`, `encrypted_message` (any base64 strings) and `dh.sender_ephemeral_pubkey` / `dh.recipient_ephemeral_pubkey` set to values that do not match the victim's temp/prev-temp/permanent keys.
3. Attacker signs the message with their own private key so `hasValidHashes`/`ecdsaSig.verify` checks pass (device.js:163-172).
4. Attacker relays this justsaying as `hub/message` to the victim (via the hub or directly if reachable).
5. `decryptPackage()` executes the "unknown key" branch, scheduling `throw Error(...)` in `setTimeout` (device.js:429-436).
6. 100ms later the exception fires uncaught, hits `process.on('uncaughtException')` in `network.js`, and the process re-throws and crashes (network.js:4530-4543).
