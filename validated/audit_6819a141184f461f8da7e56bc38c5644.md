### Title
CCMenuController#stack bypasses per-token stack scoping, allowing a `read:stack` token minted for one stack to read any other stack's CCMenu status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController` scopes stack lookups to the authenticated `ApiClient`'s own `stack_id` via the `stacks` helper, but `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` relation, discarding that binding entirely. Any valid `read:stack` token, regardless of which stack it was issued for, can therefore fetch the CCMenu XML (deploy/rollback status) of any stack on the instance, including stacks in a completely different `Repository#owner`.

### Finding Description
The binding that should hold is: `current_api_client.stack_id == stack.id` (or `current_api_client.stack_id` is nil for global clients) whenever a scoped API client resolves a stack for a request.

In `Api::BaseController`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

This correctly restricts stack resolution to the client's authorized `stack_id` when one is set. However `Api::CCMenuController` defines its own `#stack`:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

This calls `Stack.from_param!` on the entire `Stack` table, never consulting `current_api_client.stack_id`. `require_permission :read, :stack` only calls `check_permissions!(operation, scope)`, which checks the `permissions` array for the string `"read:stack"` — it has no knowledge of `stack_id` and cannot enforce the binding:
```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [3](#0-2) 

Exploit flow: attacker obtains a `read:stack` token scoped to stack A (e.g., a public CCMenu badge URL for A, a documented, legitimate use case). Attacker sends `GET /api/stacks/:stack_id/cc_menu.xml?token=<tokenForA>` with `:stack_id` set to stack B's id/slug (B in a different `Repository#owner`). `ApiClient.authenticate` resolves the client (still scoped to A internally via `stack_id`), `require_permission!(:read, :stack)` passes because the permission list contains `read:stack`, and `#show` calls the overridden `#stack`, which resolves B unconditionally and renders B's `deploys_and_rollbacks` in the XML response.

Existing tests only exercise unscoped clients (`authenticate!` in `test/controllers/api/ccmenu_controller_test.rb` fetches the same stack the client belongs to), so there is no coverage proving the `stack_id` scope is enforced on this endpoint — because it isn't.

### Impact Explanation
An attacker with a legitimately-issued, narrowly-scoped API token for one stack/repository can read deploy/rollback status (last build status, label, time, activity, web URL) for any other stack on the Shipit instance, including stacks belonging to unrelated GitHub organizations. This is a cross-tenant unauthorized read of stack state, repeatable against any stack id/slug on the instance with a single request each, requiring no privilege beyond holding any valid `read:stack` token (which itself is commonly distributed via public CCMenu badge URLs). This matches the "High - unauthorized read of stack state" category.

### Likelihood Explanation
Preconditions are minimal and match normal Shipit usage: an `ApiClient` with `read:stack` permission scoped to a `stack_id` exists (created via the standard API client provisioning flow, e.g. for a CCMenu integration), and at least one other stack exists on the instance. No secrets, sessions, or elevated roles are needed — only a token the attacker was already handed for legitimate use on stack A. The attack is a single unauthenticated-cost HTTP GET with an attacker-chosen `stack_id` parameter, fully repeatable and enumerable across all stack ids/slugs.

### Recommendation
Remove the `#stack` override in `Api::CCMenuController` (or reimplement it using the scoped `stacks` helper from `BaseController`) so CCMenu lookups honor `current_api_client.stack_id`, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
relying on the inherited `stacks` method rather than `Stack.from_param!` directly.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb`, add a test that creates a client scoped to stack A (`@client.update!(stack: @stack, permissions: ['read:stack'])`) and a second stack B belonging to a different repository owner, then asserts:
```ruby
test "a token scoped to one stack cannot read another stack's cc_menu" do
  @client.update!(stack: @stack, permissions: ['read:stack'])
  other_stack = Stack.create!(repository: Repository.new(owner: "other-org", name: "other-repo"), branch: 'main')

  get :show, params: { stack_id: other_stack.to_param }

  assert_response :not_found # expected after fix; currently returns :ok
  # Before fix: assert_response :ok and assert_payload 'name', other_stack.to_param succeeds,
  # proving current_api_client.stack_id (@stack.id) != resolved stack.id (other_stack.id).
end
```
This demonstrates that `current_api_client.stack_id == @stack.id` while the resolved `stack.id == other_stack.id`, violating the required binding, and that the current implementation returns `200` with `other_stack`'s data.
