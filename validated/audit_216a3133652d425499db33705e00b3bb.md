### Title
CCMenuController#show ignores stack-scoped ApiClient token, allowing cross-stack read of build/deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` scopes the resolvable stacks to `current_api_client.stack_id` via its `stacks`/`stack` helpers, but `Shipit::Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, bypassing that scoping entirely. Any valid API token — even one issued for a single stack — can therefore be used to read the CCMenu XML status of any other stack by changing `params[:stack_id]`.

### Finding Description
The claimed binding is: `current_api_client.stack_id == stack.id` must hold before rendering.

In the base controller, this binding is enforced for every other API controller that relies on `stack`/`stacks`: [1](#0-0) 
`stacks` restricts the resolvable set to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `stack` resolves `params[:stack_id]` only within that restricted relation.

`CCMenuController` however overrides `stack` and resolves against the unscoped `Stack` model: [2](#0-1) 

`ApiClient.authenticate` only verifies the signed token and looks up the client by id — it performs no comparison to any stack: [3](#0-2) 

`require_permission :read, :stack` only checks that `"read:stack"` is in the client's `permissions` array; it never checks `stack.id` against `current_api_client.stack_id`: [4](#0-3) [5](#0-4) 

Attack: a client that holds a token issued for stack A (with `client.stack_id == A.id`, permission `read:stack`) sends `GET /stacks/:owner/:repo-B/ccmenu.xml?token=<token-for-A>` (or via Basic Auth) for any other stack B. `authenticate_api_client` succeeds because the token signature is valid and the client id resolves. `require_permission!(:read, :stack)` passes because the client has `read:stack` in its permissions. `stack` (overridden in `CCMenuController`) resolves stack B unconditionally via `Stack.from_param!`, with no re-check that `B.id == current_api_client.stack_id`. The XML for stack B (build status, last build label/time, activity, webUrl) is rendered and returned to the attacker.

None of the listed guards prevent this: `verify_signature`/webhook checks are irrelevant here (this is the read API, not the webhook path); `ExplicitParameters` is not used by this controller; `require_permission!` checks operation/scope strings only, not stack identity; and the `stacks` scope that would have prevented this is simply not used by `CCMenuController#stack`, which shadows it with its own unscoped lookup.

### Impact Explanation
An attacker who has legitimately obtained one CCMenu token (e.g. embedded in a CI status badge URL for their own stack) can enumerate and read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`, lock state via failure status) for every other stack hosted by the same Shipit instance, including private/internal repositories they have no access to. This is an unauthenticated (relative to the target stack) read of stack state — matching the "High: escalation ... unauthenticated read of stack state" impact category. It is fully repeatable per stack id and scales across all tenants/stacks on the instance.

### Likelihood Explanation
Preconditions: `Shipit.disable_api_authentication` is false (the default, non-degraded config) and the attacker holds any valid `ApiClient` token scoped to a single stack with `read:stack` permission — a routine, low-privilege credential (e.g. a CCMenu URL a repo maintainer legitimately shared for CI status badges). No secrets, GitHub credentials, or elevated roles are needed. Stack ids/slugs are guessable/enumerable (sequential or via owner/repo names), making this trivially exploitable with sequential probing as described.

### Recommendation
Remove the `stack` override in `CCMenuController` (or make it use the inherited scoped `stack`/`stacks` helper from `BaseController`) so that stack resolution is always constrained to `current_api_client.stack_id` when the client is stack-scoped, i.e. resolve via `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`.

### Proof of Concept
Minitest plan (in the spirit of, though `test/**` itself is out of scope for remediation credit, this documents the reproducible check):
1. Create two stacks, A and B.
2. Create an `ApiClient` with `stack_id: A.id`, `permissions: ['read:stack']`, generate `token_a = client.authentication_token`.
3. `GET api_ccmenu_path(stack_id: A.to_param), params: { token: token_a }` → assert `:ok`, capture XML, assert `name == A.to_param`.
4. `GET api_ccmenu_path(stack_id: B.to_param), params: { token: token_a }` (same token) → currently asserts `:ok` and `name == B.to_param`, proving that `current_api_client.stack_id (A.id) != stack.id (B.id)` yet the request succeeds and returns stack B's data — the binding is violated.
5. After the fix, this same request should assert `:not_found` (or `:forbidden`), because `stacks.from_param!` would scope resolution to `Stack.where(id: A.id)` and fail to find B.
