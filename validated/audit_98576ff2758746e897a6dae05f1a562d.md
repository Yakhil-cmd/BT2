Confirmed: `PushHandler` scopes to `stacks.not_archived.where(branch:)` derived from the payload's `repository.full_name`, but `StatusHandler#process` uses a completely unscoped `Commit.where(sha: params.sha)` with no repository or branch filter at all.### Title
`StatusHandler#process` updates commit status across all stacks/repositories sharing a sha, with no repository or stack scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits via a completely unscoped `Commit.where(sha: params.sha)`, ignoring the `repository.full_name` in the webhook payload entirely. Any `Commit` row in any stack (of the same repository or, in the case of shared history, a different one) whose `sha` matches the incoming status event's sha gets a new `Status` created, which can trigger `deployable_status`/`commit_status` hooks and `stack.schedule_merges`/continuous deployment - none of which is gated on the webhook's own repository/branch context.

### Finding Description
The broken binding is: `commit.stack` (the stack whose deploy/merge state gets mutated) should equal `stack_for(payload['repository']['full_name'], branch)` (the stack the status event actually concerns). Instead: [1](#0-0) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a bare `ActiveRecord::Base`-level query with no `stack_id`, no `repository_id`, and no use of the `stacks` helper that every other handler relies on. Compare with `PushHandler`, which correctly scopes through `Repository.from_github_repo_name(repository_name).stacks`: [2](#0-1) [3](#0-2) 

`Commit` rows are stored per-stack (`belongs_to :stack`) and the uniqueness index is `(sha, stack_id)`, not `(sha)` alone, meaning the schema explicitly permits — and the sync flow (`GithubSyncJob`) commonly produces — the same sha existing under multiple `Stack`/`Repository` combinations (e.g., a `staging` and `production` stack of one repository sharing history via fast-forward merges, or two Shipit-tracked repositories that are forks/subtrees sharing commit history): [4](#0-3) [5](#0-4) 

Attack flow: attacker pushes a throwaway branch to a repository already tracked by Shipit with (at minimum) two stacks — e.g. `staging` and `production` — where the pushed commit's sha is also present in the `production` stack's `commits` table (via a prior fast-forward). CI reports a status for that sha; GitHub emits a validly-signed `status` webhook for the *attacker's own repository/organization* (`verify_signature` only checks the webhook came from the correct GitHub org, it never checks which branch or which stack the sha belongs to): [6](#0-5) 

`StatusHandler#process` then updates the `Status` for **every** `Commit` row across the installation whose `sha` matches — including the `production` stack's row — via `commit.create_status_from_github!` → `add_status`, which emits `deployable_status` and calls `stack.schedule_merges` on success/pending states: [7](#0-6) 

No existing guard (`verify_signature`, `ExplicitParameters` schema, `drop_unhandled_event`) checks that the resolved `Commit`/`stack` belongs to the repository named in the payload; the `StatusHandler` is the only handler in the codebase that skips the `stacks` scoping helper entirely.

### Impact Explanation
This is a payload for one webhook context (a throwaway branch/CI run) mutating the commit/deploy state of an unrelated stack — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." Concretely, an attacker who can only push to a non-production branch of a tracked repo (or, in the cross-repo variant, any repo that happens to share commit history with a Shipit-tracked target, e.g. a public fork) can cause `production`'s undeployed commit to become `deployable?`/pass CI gating and trigger `ContinuousDeliveryJob`/merges without ever having interacted with the `production` branch or stack. This is repeatable against any repository/stack pair in the installation that shares commit shas, and is not limited to a single tenant — it is a global, unscoped query across the entire `commits` table.

### Likelihood Explanation
Preconditions: Shipit must track at least two stacks whose commit histories intersect on at least one sha (extremely common for `staging`/`production` pairs of the same repo using fast-forward promotion, and plausible for forked/subtree repos). The attacker needs no Shipit credentials — only the ability to get a `status` event fired for a shared sha from a GitHub org Shipit already trusts (e.g. push to a branch/PR that reuses a commit already merged toward production, and let normal CI post a status). Cost is low and the setup is realistic in typical CI/CD branching workflows.

### Recommendation
Scope `StatusHandler#process` by the payload's `repository.full_name` (and ideally `branches`), mirroring `PushHandler`/`Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restores the binding `commit.stack.repository == Repository.from_github_repo_name(payload['repository']['full_name'])`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status event for one repository does not update a commit belonging to a different stack sharing the same sha" do
  repo = shipit_repositories(:shipit)
  staging = shipit_stacks(:shipit) # tracks repo, branch: 'staging'
  production = Shipit::Stack.create!(repository: repo, environment: 'production', branch: 'production')

  shared_sha = 'deadbeef' * 5
  staging_commit = staging.commits.create!(sha: shared_sha, message: 'shared', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  production_commit = production.commits.create!(sha: shared_sha, message: 'shared', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  payload = {
    'sha' => shared_sha, 'state' => 'success',
    'repository' => { 'full_name' => repo.full_name },
    'branches' => [{ 'name' => 'staging' }]
  }

  assert_no_difference -> { production_commit.reload.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
  assert_difference -> { staging_commit.reload.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Currently, both `assert_no_difference`/`assert_difference` assertions on `production_commit.statuses.count` fail identically (both increment), proving the cross-stack write; after the fix, only the `staging` stack's commit is updated.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
