### Title
Unrestricted route execution can redirect a caller’s signed authorization to arbitrary token transfers - (File: contracts/controller/src/strategies/swap.rs)

### Summary

Router-backed strategy calls can place attacker-selected contract code below the caller’s signed `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` invocation. That nested code can request an unrelated `token.transfer(victim, attacker, amount)`; Soroban simulation records it as a child of the victim’s authorization tree. If the victim signs the simulated tree without rejecting unexpected children, the transfer succeeds even though the controller only intended to authorize a bounded strategy swap. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

`swap_tokens` obtains the configured router, authorizes one exact `token_in.transfer(controller, router, amount_in)`, and then calls `router.execute_strategy(controller, amount_in, swap)`. [4](#0-3) 

The authorization only constrains the controller’s own input transfer; it does not prevent route-selected code deeper in the transaction from requesting the original caller’s authorization for unrelated operations. [5](#0-4) [6](#0-5) 

`swap_collateral` authenticates `caller`, verifies account ownership or delegation, withdraws collateral, and passes caller-controlled `swap` bytes to the router path. [7](#0-6)  `swap_debt`, `repay_debt_with_collateral`, and `multiply` similarly authenticate the caller before routing borrowed or withdrawn funds through attacker-influenced strategy bytes. [8](#0-7) [9](#0-8) [10](#0-9) 

A malicious route can therefore include a contract that calls `token.transfer(victim, attacker, amount)`. Simulation records that call as a child of the victim’s root strategy authorization rather than as a separate visible top-level operation. [11](#0-10) 

### Impact Explanation

A victim can lose arbitrary balances of unrelated wallet tokens that were never supplied to the lending protocol. [12](#0-11) [13](#0-12) 

The malicious route can simultaneously return sufficient legitimate output to satisfy measured receipt and account-risk checks, so the unexpected transfer is not bounded by the swap amount, route minimum, collateral checks, or protocol solvency checks. [14](#0-13) [6](#0-5) 

### Likelihood Explanation

Exploitation requires the victim to submit and sign a malicious route. This can occur through a compromised route source or a client that signs the simulation-produced authorization tree without decoding and rejecting unexpected children. [6](#0-5) 

The harness confirms that an honest signed tree rejects the nested transfer, while signing the simulation-produced poisoned tree authorizes it and transfers the victim’s entire unrelated token balance. [15](#0-14) 

The external HTTP redirect flaw maps directly because authorization intended for one logical operation is replayed beneath a redirected execution context. Here, however, the signed authorization tree—not the mere presence of the malicious hop—ultimately enables the transfer. [16](#0-15) 

### Recommendation

Do not allow route bytes to select arbitrary executable venue contracts. Enforce an on-chain allowlist of venue contracts and callable functions in the router, or replace opaque venue selection with bounded route descriptors whose destinations are known and validated. [17](#0-16) 

Until routes are constrained, protocol clients must treat every simulated authorization tree as security-critical: decode all children and reject any entry other than the expected input transfer or explicitly declared nested operation. [18](#0-17) 

The protocol should also reject routes whose simulation adds children to the caller’s authorization tree beyond the documented strategy requirements, since post-swap balance and risk checks cannot detect unrelated wallet transfers. [19](#0-18) [20](#0-19) 

### Proof of Concept

1. Alice owns a normal account with USDC collateral and holds an unrelated token that the lending protocol never listed. [21](#0-20) 
2. An attacker supplies a `swap_collateral` route whose selected hop contract stores Alice’s address, that unrelated token address, the attacker’s recipient address, and Alice’s full wallet balance. [22](#0-21) [23](#0-22) 
3. Alice calls `swap_collateral(caller=alice, account_id, current=USDC, amount, new=ETH, swap=malicious_route)`. [24](#0-23) 
4. The controller withdraws the collateral and invokes the configured router with the route; the route invokes the attacker-controlled hop. [25](#0-24) [1](#0-0) 
5. The hop calls `token.transfer(alice, attacker, wallet_balance)`. Simulation attaches that invocation as a child of Alice’s `swap_collateral` authorization. [11](#0-10) 
6. If Alice signs that simulated tree, the unrelated wallet token is transferred to the attacker while the route can still return enough ETH to satisfy output and risk checks. [26](#0-25)

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,

        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
