### Title
Unprivileged stake-account closure during the reward distribution window causes the account's own earned reward to be silently burned - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
The reward distribution code assumes that a stake account that has been selected for a reward payout in the calculation phase can never disappear before the corresponding distribution block runs, and therefore states "there should never be rewards burned." This assumption is not enforced anywhere: a stake account owner can withdraw/close their own fully-deactivated stake account during the multi-block reward distribution window, which removes the account from `StakesCache`. When the account's scheduled partition is later processed, the reward is not credited to anyone — it is simply discarded ("burned"), permanently destroying value that had already been accounted for in the epoch's `EpochRewards` sysvar.

### Finding Description
Partitioned epoch rewards are computed once at the epoch boundary (`Calculation` phase) and then paid out gradually across up to 10% of the epoch's slots (`Distribution` phase) [1](#0-0) . During this window, `build_updated_stake_reward` looks up each scheduled stake account in the *current* `StakesCache` snapshot at the time its partition is processed, not the snapshot taken at calculation time: [2](#0-1) 

If the account is not found, `DistributionError::AccountNotFound` is returned, and the associated `stake_reward_amount` is added to `stake_reward_lamports_burned` instead of being credited to any account [3](#0-2) . The doc-comment on `store_stake_accounts_in_partition` explicitly states this should be unreachable: *"Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned."* [4](#0-3) 

However, no such stake-program restriction actually exists. `StakesCache::check_and_store` unconditionally removes a stake delegation from the cache whenever the account's lamports reach zero, with no check for an in-progress reward distribution: [5](#0-4) . A stake owner who has fully deactivated their stake in a prior epoch is permitted to withdraw the entire account balance (closing it to zero lamports) via the stake program's `Withdraw` instruction, independent of whether the bank is currently inside the reward-distribution interval — there is no `EpochRewardsActive`-style guard analogous to the vote-program's `pending_delegator_rewards` check (`programs/vote/src/vote_state/mod.rs`, which *does* protect against closing an account with pending rewards) [6](#0-5) . No equivalent protection exists for stake accounts in the reward-distribution path.

Because reward distribution is spread over many blocks (up to `slots_per_epoch / 10`), there is a real, non-trivial window in which a staker whose reward was already computed and included in the epoch's `total_rewards`/`distributed_rewards` accounting can close their own account before their partition is processed, causing their reward to be dropped via the `AccountNotFound` path.

### Impact Explanation
The reward has already been included in the `EpochRewards` sysvar's `total_rewards` and factored into the epoch's inflation accounting, but it is never actually paid to the staker nor to anyone else — it is unconditionally counted as "burned" and the capitalization increase that would otherwise occur is skipped [7](#0-6) . This breaks the code's own invariant that distribution never burns rewards, and it means a normal, permissionless account action (withdrawing one's own fully-deactivated stake) can cause deterministic, unrecoverable loss of an already-earned reward with no way for the owner to reclaim it — directly analogous to the reported bug class of tokens/rewards becoming permanently unusable due to a flawed two-phase (schedule-then-claim/distribute) design.

### Likelihood Explanation
Triggering this requires only unprivileged actions available to any stake account owner (deactivate stake, wait for cooldown to complete, then submit a `Withdraw` instruction for the full balance during the reward-distribution window of the following epoch) — no special privileges, validator role, or malicious cluster behavior are needed. The main uncertainty is precisely how many blocks/epochs of lead time are required for a stake to be "fully inactive" and eligible for full withdrawal relative to when its reward partition is processed; I was not able to fully verify the exact timing overlap between stake deactivation/cooldown completion and reward-partition scheduling within the available context, so the practical window size (and thus how easily an attacker/user could line this up) is not fully confirmed from the code inspected.

### Recommendation
Either (a) snapshot/lock the stake accounts selected for reward payout so that stake-program withdrawal/closure instructions are rejected for a pubkey with a pending, uncredited partitioned reward (mirroring the vote program's `pending_delegator_rewards` protection), or (b) change `store_stake_accounts_in_partition` so an `AccountNotFound` reward is not discarded but instead deposited into a recoverable location (e.g., credited to the destination of the withdrawal, or retained in the `EpochRewards` sysvar for later reconciliation) rather than being silently burned.

### Proof of Concept
Not independently reproduced in this analysis; conceptually: 1) delegate and then deactivate a stake account so it fully cools down by the start of epoch N; 2) at epoch N's boundary, the stake is included in `all_stake_rewards`/`partition_indices` for that epoch's distribution as a `DeactivatedStake` reward; 3) before that stake's partition block is reached, submit a `Withdraw` instruction emptying the stake account to zero lamports, causing `StakesCache::check_and_store` to evict it; 4) when the assigned partition block executes, `build_updated_stake_reward` returns `DistributionError::AccountNotFound`, and the reward amount is added to `stake_reward_lamports_burned` instead of being paid [8](#0-7) .

    pub(super) fn get_reward_distribution_num_blocks(

        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1

            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
