### Title
Cross-tenant `Team` membership forgery via unvalidated `team.id` in `membership` webhook — (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` looks up a `Team` solely by the attacker-supplied `params.team.id` (GitHub's numeric team id), never checking that this id actually belongs to the organization that signed the webhook. Because `Shipit::WebhooksController#create` only verifies that the *signing* organization (`params['organization']['login']`) owns a valid webhook secret, an attacker who is a legitimately configured tenant of a multi-tenant Shipit install can forge a `membership`/`added` event that references a foreign, privileged team's `github_id` and adds an arbitrary user (including themselves) to it.

### Finding Description
The broken binding is: `signing_org = params.dig('organization','login')` must equal `team.organization` for the `Team` record identified by `params.team.id` — this is never enforced.

Path:
- `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) resolves `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. For a `membership` event with no `repository` key, this is exactly `params['organization']['login']` — the attacker's own tenant org, whose secret the attacker legitimately possesses. [1](#0-0) [2](#0-1) 
- Once signature verification passes for the attacker's own org, `WebhooksController#create` dispatches unconditionally: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 
- `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { ... }`. The block (which sets `team.organization = params.organization.login`) only runs on **create**. If a `Team` row already exists with that `github_id` (e.g. a privileged team belonging to another org, created earlier through the legitimate `Team.find_or_create_by_handle`/GitHub API path used by `Shipit.github_teams`), `find_or_create_by!` returns the **existing** record untouched, ignoring the fact that its `organization` differs from the org that signed this request. [4](#0-3) 
- `process` then executes `team.add_member(member)` (or `team.members.delete(member)`) for `member = User.find_or_create_by_login!(params.member.login)`, both fully attacker-controlled fields. [5](#0-4) 

Exploit flow: attacker controls a Shipit-configured tenant org ("attacker-org") with its own webhook secret. They discover (or guess) the numeric GitHub `id` of a team that is a member of `Shipit.github_teams` (e.g. `shopify/developers`, whose `Team` record already exists with `organization: 'shopify'`). They POST `/webhooks` with `X-Github-Event: membership`, a valid HMAC signature computed with attacker-org's own secret, and body:
```json
{"action":"added","team":{"id":<victim_team_github_id>,"name":"x","slug":"x","url":"x"},"organization":{"login":"attacker-org"},"member":{"login":"attacker-org-user"}}
```
`verify_signature` passes (attacker-org's own secret matches attacker-org's own signature). `MembershipHandler` then finds the pre-existing victim `Team` by `github_id` and adds `attacker-org-user` to it, regardless of `organization` mismatch.

`Shipit::User#authorized?` (`app/models/shipit/user.rb:80-82`) becomes `true` for that user as soon as they belong to any team in `Shipit.github_teams` — which this handler just granted without any real GitHub membership. [6](#0-5) 

Existing guards fail because:
- `verify_signature` only proves the *organization field in the payload* matches a real, per-tenant webhook secret; it says nothing about which `team.id` is legitimate for that org.
- `MembershipHandler`'s `ExplicitParameters` schema requires `team.id`/`organization.login` to be present and well-typed, but does not require any relationship between them.
- `Team.find_or_create_by!` performs no organization-consistency check on the "found" branch.

### Impact Explanation
An attacker who controls any single Shipit-configured GitHub organization tenant can grant arbitrary GitHub logins membership in **any other tenant's** privileged `Shipit.github_teams` team, bypassing the `authorized?` gate that controls access to the entire Shipit UI/authentication (`Shipit::Authentication#force_github_authentication`). This is a cross-tenant escalation into `Shipit.github_teams` authorization — matching the "High: escalation into `Shipit.github_teams` authorization" impact category. It is repeatable against any team whose numeric `github_id` the attacker can learn, across arbitrary configured tenants, without needing the victim org's webhook secret.

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment (the `github_app_config`/`github_organizations` scheme in `lib/shipit.rb:170-200`) where the attacker legitimately administers one configured org; (2) `Shipit.github_teams` non-empty (teams-based restriction enabled); (3) knowledge of the target team's numeric GitHub `id` (discoverable via GitHub's public team API for many orgs, or via prior legitimate `membership` webhook traffic observed/logged). No secrets, sessions, or GitHub App keys are needed beyond the attacker's own tenant's webhook secret, which is a stated precondition. This is a single crafted HTTP POST, fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the found/created `Team#organization` equals `params.organization.login` before performing any membership mutation, and raise/drop the event otherwise (e.g. `raise ArgumentError` or simply `return` if `team.organization != params.organization.login`). Additionally, consider validating in `WebhooksController#verify_signature` that `params.dig('team')` (when present) is consistent with the verified `organization`.

### Proof of Concept
Under `test/models/webhooks/handlers/membership_handler_test.rb` (minitest, no live GitHub):
```ruby
test "membership handler must not mutate a team belonging to a different organization" do
  victim_team = Shipit::Team.create!(github_id: 999, organization: 'shopify', slug: 'developers', name: 'Developers', api_url: 'https://x')
  Shipit.stubs(:github_teams).returns([victim_team])

  attacker_user = Shipit::User.find_or_create_by_login!('attacker-org-user')
  refute attacker_user.authorized?

  params = {
    'action' => 'added',
    'team' => { 'id' => 999, 'name' => 'Developers', 'slug' => 'developers', 'url' => 'https://x' },
    'organization' => { 'login' => 'attacker-org' }, # NOT 'shopify'
    'member' => { 'login' => 'attacker-org-user' },
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new(params).call

  victim_team.reload
  attacker_user.reload
  # BROKEN BINDING: signing org ('attacker-org') != team.organization ('shopify'),
  # yet membership/authorization was still granted.
  assert_equal 'shopify', victim_team.organization
  refute victim_team.members.include?(attacker_user), "attacker should not have been added to a foreign org's team"
  refute attacker_user.authorized?, "authorized? must not become true without real GitHub team membership"
end
```
Prior to a fix, this test fails: `victim_team.members` includes `attacker_user` and `attacker_user.authorized?` is `true`, demonstrating the escalation.
