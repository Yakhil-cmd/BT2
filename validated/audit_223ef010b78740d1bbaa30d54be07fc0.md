### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` satisfies victim's required-status merge gate - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits to attach a GitHub Status to purely by `sha`, with no check that the webhook's `repository` matches the `stack`/`Repository` owning that commit. Because `Shipit::MergeRequest::StatusChecker` (built on `head.statuses_and_check_runs`) only matches statuses by `context` string against `deploy_spec.merge_request_required_statuses`, a Status row created for a commit sha shared across two different Shipit-tracked repositories/stacks can satisfy a victim stack's required-status gate even though it was reported by an unrelated repo's CI.

### Finding Description
The intended binding is: **the `(context, state)` pair that satisfies a victim stack's required status == the `(context, state)` reported by the CI system actually monitoring the victim repository's code**. This binding is broken because:

- `StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 
This query is **not scoped by repository**. Contrast with the base `Handler` class, which provides a `stacks` helper explicitly scoped via `Repository.from_github_repo_name(repository_name)` for other handlers to use [2](#0-1) ; `StatusHandler` never calls it and never reads `payload.dig('repository', 'full_name')` at all.

- `create_status_from_github!` writes a `Status` row keyed only by `stack_id`/commit, using the attacker-controlled `context`, `state`, `description`, `target_url` fields verbatim: [3](#0-2) .

- `MergeRequest#all_status_checks_passed?` then evaluates `StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?` [4](#0-3) , and `StatusChecker` (in `merge_request.rb`) compares `context` strings against `deploy_spec.merge_request_required_statuses` with no notion of which repository actually emitted the status [5](#0-4) .

Exploit flow: if `Commit` rows in two different Shipit-tracked repos/stacks ever share a `sha` value (e.g. one repo forked from or mirrors another, or the same underlying repository is tracked by two stacks), an attacker who controls one of those repos can emit a `status` webhook event with `context: 'ci/travis'`, `state: 'success'`, and `sha` equal to the colliding value. The webhook passes `WebhooksController#verify_signature`, which only checks the HMAC signature against `Shipit.github(organization: repository_owner)` derived from the attacker's own payload [6](#0-5) ; it performs no check that the SHA/commit actually belongs to that repository. `StatusHandler#process` then finds and updates **every** `Commit` row across the whole Shipit instance matching that `sha`, including the victim's, regardless of which repository the webhook nominally came from.

Existing guards do not close this gap: `verify_signature` only authenticates that the webhook body was signed by *some* configured GitHub organization/app — it never binds the signed request to the specific commit/stack being mutated. `drop_unhandled_event` and the `ExplicitParameters` schema only validate the shape of the payload (`sha`, `state`, `context` as plain strings), not their provenance. No `Repository`/`Stack` scoping check exists in `StatusHandler` unlike other handlers that use `stacks`.

### Impact Explanation
A successful forged status write causes a `Shipit::Status` row to be persisted against a commit belonging to a repository/stack the attacker does not control, with an attacker-chosen `context` and `state: 'success'`. If that context matches a victim stack's `merge_request_required_statuses`, `MergeRequest#all_status_checks_passed?` returns `true`, `reject_unless_mergeable!` no longer rejects for `ci_missing`/`ci_failing`, and the merge queue can proceed to call `merge!`, causing GitHub to actually merge the victim's pull request without its real CI having passed. This is a payload for one repository mutating another's stack/commit state and enabling an unauthorized merge — matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). The write is repeatable against any Commit row sharing a colliding sha, and blast radius spans every stack in the same Shipit instance since `Commit.where(sha:)` has no tenant boundary.

### Likelihood Explanation
This requires: (1) the victim's `deploy_spec.merge_request_required_statuses` including a context name (attacker-controlled strings, no allowlist tying them to a specific CI provider identity), and (2) a commit `sha` collision between the attacker-controlled repository and the victim's tracked commit — realistic when repos are forked/mirrored or when multiple stacks track the same underlying repository (common in multi-environment Shipit setups: staging/production stacks of the same repo share identical commit SHAs). Given those two realistic preconditions (explicitly granted in the question), the attacker cost is a single crafted, validly-signed `status` webhook from a repository they legitimately own — no Shipit credentials or secrets are required, only the ability to emit their own repo's webhooks (assumed available per the rules). The attack is fully repeatable on demand.

### Recommendation
Scope `StatusHandler#process` (and `commit.create_status_from_github!`) to the repository that emitted the webhook, mirroring the `stacks`/`Repository.from_github_repo_name` pattern used elsewhere: only update commits whose `commit.stack.github_repo_name` matches `payload.dig('repository', 'full_name')`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status for repo B's commit is applied to repo A's commit sharing the same sha" do
          victim_stack = shipit_stacks(:shipit) # tracks repo "shopify/shipit-engine"
          attacker_stack = Shipit::Stack.create!(repository: Shipit::Repository.create!(owner: 'attacker', name: 'evil-fork'))

          colliding_sha = 'a' * 40
          victim_commit = victim_stack.commits.create!(sha: colliding_sha, message: 'shared history commit')
          attacker_stack.commits.create!(sha: colliding_sha, message: 'shared history commit')

          victim_stack.cached_deploy_spec.stubs(:merge_request_required_statuses).returns(['ci/travis'])
          merge_request = Shipit::MergeRequest.create!(stack: victim_stack, number: 1, head: victim_commit)

          # Before: no status for the required context exists on the victim's commit
          checker_before = Shipit::MergeRequest::StatusChecker.new(
            victim_commit, victim_commit.statuses_and_check_runs, victim_stack.cached_deploy_spec
          )
          assert_equal false, checker_before.success?

          # Attacker-controlled payload, nominally about their own repo, but sha collides with victim's commit
          forged_payload = {
            'sha' => colliding_sha,
            'state' => 'success',
            'context' => 'ci/travis',
            'repository' => { 'full_name' => 'attacker/evil-fork', 'owner' => { 'login' => 'attacker' } }
          }

          StatusHandler.call(forged_payload) # simulates a validly-signed webhook from attacker's own repo

          # After: StatusHandler updated ALL commits matching sha, including the victim's, via the unscoped query
          victim_commit.reload
          checker_after = Shipit::MergeRequest::StatusChecker.new(
            victim_commit, victim_commit.statuses_and_check_runs, victim_stack.cached_deploy_spec
          )
          assert_equal true, checker_after.success?, "victim's required status was satisfied by a forged cross-repo status"
        end
      end
    end
  end
end
```
This demonstrates the binding `victim_required_context/state == status_from_victim's_own_CI` no longer holds: `checker_after.success?` becomes `true` purely because `StatusHandler#process` (`Commit.where(sha: params.sha)`) applied a status payload nominally scoped to `attacker/evil-fork` onto the victim's commit.
