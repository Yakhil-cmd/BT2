### Title
Unguarded double-free-style cache access in `forgetUnit` crashes the node when a purged unit's cache entry is accessed a second time - ([File: storage.js])

### Summary
`storage.forgetUnit()` unconditionally dereferences `assocUnstableUnits[unit].parent_units` and later `delete`s the cache entry, with no guard against being invoked twice (or against `assocUnstableUnits[unit]` already being absent). This is the JS/ocore analog of CVE-2018-14048: libpng's `png_free_data` crashed (SEGV) when a caller followed the "recommended" error-handling pattern and freed/accessed image data structures a second time after `png_read_image` already discarded them. In ocore, the same class of bug (freeing/forgetting a cache entry, then referencing it again through a different code path) causes an uncaught `TypeError: Cannot read properties of undefined` that crashes the whole node process, an availability-only impact matching the CVE's `C:N/I:N/A:H` vector.

### Finding Description
`forgetUnit` is the cache-eviction primitive used whenever an unstable unit is discarded from memory (bad-sequence purge, AA response revert, uncovered-unit archiving): [1](#0-0) 

It reads `assocUnstableUnits[unit].parent_units` before doing any existence check, and only afterward deletes `assocUnstableUnits[unit]` along with several other caches (`assocKnownUnits`, `assocCachedUnits`, `assocCachedUnitAuthors`, `assocCachedUnitWitnesses`, `assocBestChildren`). There is no flag or lock recorded to prevent a second call to `forgetUnit(unit)` for the same unit from a different caller.

`forgetUnit` is reachable from at least two independent, unprivileged-triggerable paths on the same in-memory unit:
1. AA trigger/response revert path - `aa_composer.revertResponsesInCaches` iterates `arrResponses`, and for each response unit calls `storage.forgetUnit` directly: [2](#0-1) 
This is invoked from `revert()` whenever an AA bounces/reverts a response: [3](#0-2) 

2. Uncovered/nonserial-unit purge path - `joint_storage.purgeUncoveredNonserialJoints` also calls `storage.forgetUnit(row.unit)` for units whose sequence became `final-bad`/`temp-bad`: [4](#0-3) 

Both paths operate on units that are attacker-influenced: an AA-response unit (posted by triggering an AA, reachable by any unprivileged unit poster) can also become classified `final-bad`/`temp-bad` and be picked up by the periodic `purgeUncoveredNonserialJointsUnderLock` sweep (scheduled every 60s in `network.js`'s `startRelay`). If the AA-revert path forgets the unit first and the periodic archiving sweep independently re-selects and re-archives the same unit before its `units` table state is fully synchronized (or vice versa, if `forgetUnit` is reached twice through overlapping revert/AA-response and archiving flows), the second `forgetUnit(unit)` call dereferences `assocUnstableUnits[unit].parent_units` on an already-deleted (`undefined`) entry, throwing an uncaught `TypeError`. Because this code runs outside of any `try/catch` in `writer`/`joint_storage`/`aa_composer`, the exception propagates to the top of the event loop and crashes the ocore process, exactly analogous to libpng's SEGV in `png_free_data` after being invoked once with the recommended (but redundant) error-handling call sequence.

### Impact Explanation
An uncaught `TypeError` thrown inside `forgetUnit` terminates the Node.js process (no `domain`/`process.on('uncaughtException')` recovery is present around these code paths), taking the entire node offline. Since this crash can be triggered by ordinary AA triggering / unit posting activity that produces the specific bad-sequence / AA-revert overlap, an attacker who can post units and trigger AAs can remotely force node crashes, matching the CVE's medium-severity availability-only impact (repeated crash = denial of service / inability to confirm new units for that node until restarted).

### Likelihood Explanation
Triggering requires crafting a sequence where the same unit is simultaneously subject to AA-response reversion and to the uncovered/nonserial purge sweep (or is otherwise reachable via two independent forget paths) within the ~10 second / 60 second windows those subsystems run on. This requires careful but purely unprivileged manipulation of unit posting and AA-trigger timing - no special network position, hub/node compromise, or key leakage is required, keeping this in the "unprivileged poster" reachable category. The exact reproduction requires deeper runtime/state verification (e.g. confirming the precise timing/DB-state overlap that lets the two sweeps race on the same unit) that could not be fully validated with static code review alone.

### Recommendation
Make `forgetUnit` idempotent/defensive: check `if (!assocUnstableUnits[unit]) return;` before dereferencing `parent_units`, and guard every caller (`aa_composer.revertResponsesInCaches`, `joint_storage.purgeUncoveredNonserialJoints`, and any other call site in `storage.js`) so a unit is forgotten at most once, logging (rather than crashing) on a redundant forget attempt.

### Proof of Concept
Conceptual reproduction (requires runtime verification):
1. Post a unit that triggers an AA and produces an AA response that later gets reverted/bounced, invoking `aa_composer.revertResponsesInCaches` → `storage.forgetUnit(response_unit)`.
2. Concurrently/soon after, have that same response unit end up marked `final-bad`/`temp-bad` and uncovered (no children, no ball) so that `joint_storage.purgeUncoveredNonserialJoints`'s periodic sweep (`purgeUncoveredNonserialJointsUnderLock`, run every 60s) selects it again and calls `storage.forgetUnit(row.unit)` a second time.
3. The second call executes `assocUnstableUnits[unit].parent_units` on an already-`undefined` cache entry, throwing `TypeError: Cannot read properties of undefined (reading 'parent_units')`, which is uncaught and crashes the node process.
