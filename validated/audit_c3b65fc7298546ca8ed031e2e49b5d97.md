### Title
Unhandled `throw Error()` for a "stable temp-bad" spent input crashes every validating node, halting network-wide unit confirmation — analogous to unhandled cross-shard tx error class (CVE-2023-33964) - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` checks the sequence of a spent source output that is stable in the current unit's parents. For the `final-bad` case it correctly returns a graceful validation error via `cb(...)`. For the `temp-bad` case, however, it instead does `throw Error("spending a stable temp-bad output " + input.unit)` inside a nested `conn.query` callback with no surrounding `try/catch`. [1](#0-0) 

This mirrors the MultiversX advisory's bug class: a specific error condition that arises during transaction/unit processing (an "invalid" state that was assumed unreachable) is not converted into a normal, per-unit rejection path, and instead trips code that halts/crashes the processing pipeline for everyone rather than just rejecting the single bad unit.

### Finding Description
By design, a unit's sequence can only be `good`, `temp-bad`, or `final-bad` while it is *unstable*. Once the unit becomes stable, `markMcIndexStable()` in `main_chain.js` deterministically resolves every `temp-bad` unit at that MCI to either `good` or `final-bad` — there is no code path that leaves a stable unit as `temp-bad`: [2](#0-1) 

Because of this invariant, `validatePaymentInputsAndOutputs()` assumes "stable + temp-bad" can never happen and, instead of treating it as an ordinary validation failure (as it does for the sibling `final-bad` case just one line below), it throws an uncaught `Error`: [3](#0-2) 

This `throw` occurs deep inside an asynchronous `conn.query()` callback, itself nested inside `async.eachSeries`/`async.series` iterators used by `validate()`. There is no `try/catch` anywhere in this call chain (`validate()` → `validateMessages()` → `validateInlinePayload()`/`validatePaymentInputsAndOutputs()`), and `network.js`'s `handleJoint()` also does not wrap the `validation.validate()` invocation in a `try/catch` — it only registers `ifUnitError`, `ifJointError`, `ifTransientError`, etc. callbacks, none of which are reached by a synchronous `throw`: [4](#0-3) 

A synchronous `throw` from inside a DB driver callback is not caught by any `try/catch` in `async`'s control-flow wrappers, so it propagates as an **uncaught exception** on the Node.js event loop, crashing the process. Because every full node (and hub) executes byte-for-byte identical, deterministic validation logic against the same unit content, if any code path can produce a "stable temp-bad" source output — whether via a subtle inconsistency in fork/competitor resolution under specific spend-timing/edge-case sequences, via light-node code paths that separately track sequence state (`light.js`, `joint_storage.js` also reference `temp-bad`), or via a future refactor that reintroduces the possibility — the resulting unit crashes **every node that processes it simultaneously and deterministically**, exactly as the advisory describes a network-wide notarization halt rather than a rejection of one bad transaction.

This is structurally the same bug class as the referenced MultiversX advisory: an "impossible" or insufficiently-hardened error branch during unit/transaction validation is handled by a hard failure (there: broken cross-shard notarization; here: `throw` instead of `cb(error)`), instead of a controlled, per-unit validation rejection, and it stops the network from confirming further units.

### Impact Explanation
If this branch is ever reachable (via a bug elsewhere in stabilization/sequence-resolution logic, a light-vendor/hub state desync, or a future code change that weakens the "temp-bad only while unstable" invariant), the impact is severe:
- Every full node and hub that receives/validates the triggering unit crashes with an uncaught exception, since the throw happens outside any recovery path.
- Because validation is deterministic and all honest nodes run the same code on the same unit, this is not a localized single-node failure — it can simultaneously halt the entire network's ability to validate and confirm new units, matching the "network unable to confirm new units" acceptance criterion.
- Even short of a full crash (e.g., if some deployment wraps top-level exceptions), the throw still short-circuits the transaction with an uncontrolled failure instead of the intended graceful `cb("spending a stable temp-bad output ...")` rejection that the adjacent `final-bad` branch demonstrates was the intended design, leaving the DB connection/transaction in an inconsistent state (no `ROLLBACK`/`conn.release()`/`unlock()` executed) that can leak connections/locks and cause the node to stall.

### Likelihood Explanation
This is a defense-in-depth invariant check, not something reachable in normal correct operation, since `markMcIndexStable()` resolves all `temp-bad` units before/at the moment of stabilization. The likelihood of an unprivileged unit poster reaching this exact line today, without an additional bug in stabilization or sequence bookkeeping, is uncertain and could not be conclusively proven from static analysis alone within the scope of this review. However, the asymmetric handling itself — silently `throw`ing instead of returning a normal validation error, unlike the structurally identical `final-bad` branch right next to it — is the exact same defect pattern the advisory patched (an error condition on a cross-shard/consensus-critical path that wasn't given the same graceful-rejection treatment as its sibling cases). Given that `main_chain.js`, `light.js`, and `joint_storage.js` all separately reference/manipulate `temp-bad` sequence state, there are multiple independent code paths that must stay perfectly synchronized for the invariant to hold; any drift in any of them turns this into a live, network-halting crash vector.

### Recommendation
- Replace the `throw Error("spending a stable temp-bad output " + input.unit)` with `return cb("spending a stable temp-bad output " + input.unit)`, mirroring the `final-bad` branch immediately below it, so any occurrence of this state is treated as an ordinary unit validation failure that only rejects the single offending unit (with proper `ROLLBACK`/`conn.release()`/`unlock()` performed by the existing `validate()` error path) rather than crashing the process.
- Audit all other `throw Error(...)` statements inside async DB-callback chains reachable from unprivileged unit content in `validation.js`, `definition.js`, and `main_chain.js` for the same asymmetry (i.e., checks that `throw` instead of invoking the surrounding `cb()`/`callback()` error path), and convert genuine "assumed impossible but externally influenceable" conditions into graceful rejections rather than hard throws.
- Add a top-level safety net (e.g., wrapping `validation.validate()` invocation in `handleJoint()` with `try/catch`, or a `domain`/`process.on('uncaughtException')` handler that safely purges the in-flight unit and its lock/connection) so a future latent invariant violation degrades to "reject this unit" rather than "crash the node."

### Proof of Concept
A conclusive, reproducible PoC unit that forces a stable output's sequence to remain `temp-bad` could not be constructed from static code review alone — it would require an additional invariant-breaking condition in stabilization or a separate desynchronized sequence tracking path (e.g., in `light.js` or `joint_storage.js`) that this review could not fully exhaust. The concrete, verifiable defect demonstrated here is the code-level asymmetry itself:

```js
// validation.js, inside validatePaymentInputsAndOutputs -> transfer input handling
if (bStableInParents) {
    if (src_output.sequence === 'temp-bad')
        throw Error("spending a stable temp-bad output " + input.unit);   // <-- crashes the node
    if (src_output.sequence === 'final-bad')
        return cb("spending a stable final-bad output " + input.unit);    // <-- graceful rejection
}
```

Given the identical preconditions (`bStableInParents === true`) for both branches, and that `final-bad` is handled gracefully while `temp-bad` is not, this is a clear, provable defect in error-path symmetry that a background engineering session should fix and, if possible, further investigate for concrete reachability (e.g., stress-testing fork/competitor resolution timing, or reviewing `light.js`/`joint_storage.js` sequence bookkeeping) using full repository access and a test harness, which is beyond the scope of this read-only code review.
