### Title
Byte-budget truncation in `cap_diff_for_prompt` lets padding-file diffs silently drop the malicious diff hunk from the security-review prompt - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_investigate_prompt` feeds `diff_files` through `cap_diff_for_prompt`, which accumulates a running `total` byte count across files in whatever order they arrive and, once the `DIFF_TOTAL_BYTES` budget is exhausted, replaces the ENTIRE remaining files' content with a placeholder string instead of preserving any of their real diff. Because file ordering is driven by ordinary `git diff` pathname order (and `_prioritize_diff_files` in `gitutil.py` only reorders by risk when the file *count* exceeds `MAX_DIFF_FILES`, not when byte size is large), an attacker who authors the reviewed commit/PR can prepend alphabetically-earlier, byte-heavy but benign-looking files to consume the 400,000-byte total cap before the reviewer ever reaches the file carrying the actual vulnerability.

### Finding Description
`cap_diff_for_prompt` (`plugins/security-guidance/hooks/review_api.py:31-64`) walks `files` in list order, tracking `total` bytes emitted so far: [1](#0-0) 

Once `room <= 0` for a given file, its content is fully replaced by `"[omitted by security-guidance: total diff byte cap reached]"` — none of the real diff for that file (and any subsequent file) reaches `build_investigate_prompt`'s output: [2](#0-1) 

The list fed into this function is not resorted by security relevance unless the *file count* exceeds `MAX_DIFF_FILES` — `_prioritize_diff_files` in `gitutil.py` only kicks in on that count threshold, using a risk/added-lines score, and even then the score is a heuristic that does not account for aggregate byte size against `DIFF_TOTAL_BYTES`: [3](#0-2) 

`_is_reviewable_source` accepts common data/config extensions (`.json`, `.yaml`, `.py`, etc.) and only excludes a short suffix denylist (`.min.js`, `.lock`, `_pb2.py`, `.pb.go`), so an attacker can add several large, legitimate-looking files (up to the 80,000-byte per-file cap each) that sort before the true payload file and are not filtered out: [4](#0-3) 

An attacker who controls the reviewed commit (e.g., an external contributor whose PR/commit is fed through this hook) crafts a diff with several padding files named to sort before their target file (e.g., `aaa_data.json` before `zzz_backdoor.py`), each near the 80,000-byte per-file cap, to exhaust the 400,000-byte total budget. The genuinely malicious file is then entirely replaced by the omission placeholder in the prompt the investigate-stage LLM receives, so the model never sees the dangerous lines and cannot flag them — the review silently no-ops for that file while still reporting a completed review.

### Impact Explanation
This breaks the review pipeline's core invariant that truncation must not consistently drop the high-risk lines a user expects reviewed. Because the omission is deterministic given file naming/ordering, an attacker fully controls which file's dangerous content is dropped from LLM visibility, causing the automated security-guidance review to silently pass a commit that contains a real vulnerability/backdoor. This matches "Security-control bypass that silently disables or routes around blocking, review, or permission boundaries" — the review appears to run normally (findings list still returned, possibly empty) while the actual malicious diff was never inspected.

### Likelihood Explanation
Preconditions are low-bar: the attacker only needs to be the author of the commit/PR content that flows into `get_git_diff`/`parse_diff_into_files` → `build_investigate_prompt` (an ordinary, unprivileged contribution flow — no elevated access needed beyond authoring a large diff). Constructing several ~80KB padding files with attacker-chosen names to precede the target file alphabetically is straightforward and fully deterministic; the interaction between `cap_diff_for_prompt`'s sequential accumulation and lack of byte-aware reprioritization is a direct, reproducible code property, not a probabilistic race.

### Recommendation
Have `cap_diff_for_prompt` (or its caller) apply the same risk-based prioritization as `_prioritize_diff_files` — sorted by security-relevant path tokens / added-line count — to the byte-budget allocation itself, not just to the file-count cap, so higher-risk files are guaranteed diff bytes before low-priority ones. Additionally, when a file is omitted for budget reasons, surface a partial/summarized signal to the model or user (e.g., filenames + risk score of omitted files) instead of a bare placeholder, so the omission is auditable rather than silent.

### Proof of Concept
Unit test in `plugins/security-guidance/hooks/` (extend or add near existing `review_api` tests):
1. Build `diff_files = [("aaa_padding1.json", "x"*80000), ("aaa_padding2.json", "x"*80000), ("aaa_padding3.json", "x"*80000), ("aaa_padding4.json", "x"*80000), ("aaa_padding5.json", "x"*80000), ("zzz_backdoor.py", "+os.system(user_input)")]` (5×80,000 = 400,000 bytes exactly saturating `DIFF_TOTAL_BYTES`).
2. Call `build_investigate_prompt(touched_paths=[fp for fp, _ in diff_files], diff_files=diff_files)`.
3. Assert: `"os.system(user_input)"` is NOT present in the returned prompt string, and `"zzz_backdoor.py"` section instead shows `"[omitted by security-guidance: total diff byte cap reached]"`.
4. This demonstrates that the review model's prompt never contains the dangerous line despite the file being part of the reviewed diff — confirming the truncation/ordering invariant violation.

```python
def build_investigate_prompt(
    touched_paths: list[str],
    diff_files: list[tuple[str, str]],
    *,
    context_note: str = "",
) -> str:
    capped, _ = cap_diff_for_prompt(diff_files)
    diff_text = "\n\n".join(
        f"=== DIFF: {fp} ===\n{content}" for fp, content in capped
    )
    return (
        "Review this change for security vulnerabilities.\n\n"
        "Changed files (you may Read these and any other file in the repo):\n"
        + "\n".join(f"  - {p}" for p in touched_paths[:50])
        + context_note
        + "\n\nUnified diff (only + lines are new):\n\n"
        + diff_text
        + extensibility.guidance_block()
        + "\n\nInvestigate per the method in your instructions, then return "
        "the findings list."
    )
```

```python
def _prioritize_diff_files(diff_files, cap):
    """When `diff_files` exceeds `cap`, return the top-`cap` by security
    relevance plus the count dropped. Otherwise return (diff_files, 0).

    Score = (risk_tokens_in_path, not_low_priority, added_lines). The
    added-lines proxy is `content.count('\\n+')` which counts diff additions
    cheaply without re-parsing hunks. This is a heuristic, not a guarantee —
    the goal is to review the likely-dangerous subset of an over-cap diff
    instead of reviewing nothing. Diffs that exceed the cap are typically
    large multi-file scaffolds, and the cross-file source→sink vulnerabilities
    in them concentrate in a handful of api/client/route files.
    """
    if len(diff_files) <= cap:
        return diff_files, 0

    def _score(item):
        fp, content = item
        low = fp.lower()
        # Prepend "/" so leading-slash patterns in _LOW_PRIORITY_PATH_TOKENS
        # match top-level dirs (git diff paths are repo-root-relative, e.g.
        # `migrations/001.py` not `/migrations/001.py`). Same trick as
        # _is_reviewable_source.
        low_slashed = "/" + low
        risk = sum(1 for t in _SECURITY_RISK_PATH_TOKENS if t in low)
        low_prio = (
            fp.endswith(_LOW_PRIORITY_SUFFIXES)
            or any(t in low_slashed for t in _LOW_PRIORITY_PATH_TOKENS)
        )
        # added_lines: count('\n+') over-counts by including '+++' header and
        # any literal '+' at line start in context, but it's a consistent
        # ordinal across files in the same diff which is all we need.
        added = content.count("\n+")
        return (risk, not low_prio, added)

    ranked = sorted(diff_files, key=_score, reverse=True)
    return ranked[:cap], len(diff_files) - cap
```
