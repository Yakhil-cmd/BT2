### Title
`chargeWithoutEvent()` Accepts KAIA Deposits Without State Guards, Permanently Locking User Funds — (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

`chargeWithoutEvent()` in `BridgeTransferKLAY` is an unrestricted, state-blind payable function. Any caller can send KAIA to the bridge at any time — including when the bridge is stopped (`isRunning = false`) or KLAY-locked (`isLockedKLAY = true`). Because no `RequestValueTransfer` event is emitted, the counterpart bridge never initiates a corresponding `handleKLAYTransfer`, and there is no user-facing withdrawal path. KAIA deposited this way is permanently trapped in the bridge contract.

### Finding Description

`_requestKLAYTransfer()` — the internal function backing both the fallback and `requestKLAYTransfer()` — enforces two critical guards before accepting KAIA:

```solidity
// BridgeTransferKLAY.sol lines 103-109
function _requestKLAYTransfer(address _to, uint256 _feeLimit, bytes memory _extraData)
    internal
    unlockedKLAY   // requires !isLockedKLAY
    nonReentrant
{
    require(isRunning, "stopped bridge");
    ...
``` [1](#0-0) 

`chargeWithoutEvent()` carries none of these guards:

```solidity
// BridgeTransferKLAY.sol line 139
function chargeWithoutEvent() external payable {}
``` [2](#0-1) 

The function is `external payable` with no `onlyOwner`, no `unlockedKLAY`, and no `isRunning` check. It silently accepts any amount of KAIA from any address in any bridge state, emitting nothing. The `BridgeTransfer` base contract contains no user-facing withdrawal function; the only egress path for KAIA is `handleKLAYTransfer`, which is `onlyOperators`. [3](#0-2) 

### Impact Explanation

A user who calls `chargeWithoutEvent()` while `isRunning = false` or `isLockedKLAY = true`:

1. Sends KAIA to the bridge contract — the call succeeds and KAIA is deducted from their account.
2. No `RequestValueTransfer` event is emitted — the off-chain bridge relayer (`BridgeManager.handleRequestValueTransferEvent`) never sees the deposit and never calls `handleKLAYTransfer` on the counterpart chain.
3. The user receives nothing on the counterpart chain.
4. There is no user-callable refund or withdrawal function; the only way KAIA leaves the bridge is via operator-gated `handleKLAYTransfer`.

The corrupted value is the user's KAIA balance: it is debited on the source chain and never credited anywhere. The funds are permanently locked in the bridge contract. [4](#0-3) 

### Likelihood Explanation

- The bridge owner can legitimately stop the bridge (`start(false)`) or lock KLAY (`lockKLAY()`) during maintenance or an incident.
- `chargeWithoutEvent()` is a public function with no access control; any user or script can call it.
- A user who is unaware of the bridge's current state, or who uses a script/UI that calls `chargeWithoutEvent()` for liquidity top-up, will silently lose funds.
- No on-chain revert occurs to warn the caller. [5](#0-4) 

### Recommendation

Add the same guards that `_requestKLAYTransfer` enforces:

```solidity
function chargeWithoutEvent()
    external
    payable
    onlyOwner       // or onlyOperators, depending on intended callers
    unlockedKLAY
{
    require(isRunning, "stopped bridge");
}
```

Alternatively, if the function must remain open to any caller for liquidity purposes, add a refund path: if `!isRunning || isLockedKLAY`, revert with a descriptive error so the caller's KAIA is returned.

### Proof of Concept

1. Bridge owner calls `lockKLAY()` — `isLockedKLAY = true`.
2. User calls `chargeWithoutEvent{value: 10 ether}()` — succeeds, no revert, no event.
3. User's balance decreases by 10 KAIA; bridge balance increases by 10 KAIA.
4. No `RequestValueTransfer` event is emitted; the relayer does nothing.
5. User calls `requestKLAYTransfer` — reverts with `"locked"`.
6. User has no way to recover the 10 KAIA deposited in step 2. [6](#0-5)
