Looking at the two relevant code paths carefully.

The code path is fully traced. The vulnerability is real.

**Attack chain:**

1. `fetchStakingInfos` sends block hashes to a peer requesting `P2PStakingInfo` for staking-interval blocks.
2. `handleStakingInfoMsg` → `DeliverStakingInfos` → `queue.DeliverStakingInfos`: the `validate` callback is an explicit no-op with a `// TODO-Kaia-Snapsync update validation logic` comment — no field in the peer-supplied `P2PStakingInfo` is checked against the locally-known header.
3. `reconstruct` blindly assigns `stakingInfoList[index]` to `result.StakingInfo`.
4. `commitFastSyncData` / `commitPivotBlock` call `PutStakingInfoToDB(result.StakingInfo.BlockNum, ...)` — the DB key is the **peer-supplied** `BlockNum`, not `result.Header.Number`.
5. `GetStakingInfo` reads from DB at `sourceNum` (locally computed). If the entry was written at `wrongNum`, the lookup returns nil and falls back to `getFromStateByNumber(sourceNum)`. After fast sync, historical state is unavailable → error propagates → block processing fails. If `wrongNum` is a valid staking interval block that will later be queried, the corrupted entry (with attacker-controlled `RewardAddrs`/`StakingAmounts`) is used for reward distribution.

**Contrast with `SyncStakingInfo`**: that path explicitly guards with `if d.stakingInfoRecoveryBlocks[0] != stakingInfo.BlockNum { return }` — the fast sync path has no equivalent check.

### Title
Unvalidated peer-supplied `P2PStakingInfo.BlockNum` during fast sync writes staking info at wrong DB key, corrupting reward distribution — (`datasync/downloader/queue.go`, `datasync/downloader/downloader.go`)

### Summary
During fast sync, the `DeliverStakingInfos` queue function accepts a `P2PStakingInfo` response from a remote peer and stores it verbatim in the `fetchResult` without validating any field. `commitFastSyncData` and `commitPivotBlock` then persist the staking info using the **peer-controlled** `result.StakingInfo.BlockNum` as the database key. A malicious peer can set `BlockNum` to any value and supply arbitrary `RewardAddrs`/`StakingAmounts`, writing corrupted staking info at an attacker-chosen DB slot while leaving the legitimately requested slot empty.

### Finding Description

`queue.DeliverStakingInfos` contains a deliberately empty `validate` callback:

```go
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
``` [1](#0-0) 

The `reconstruct` callback assigns the raw peer response to the fetch result:

```go
reconstruct := func(index int, result *fetchResult) {
    result.StakingInfo = stakingInfoList[index]
    result.SetStakingInfoDone()
}
``` [2](#0-1) 

Both `commitFastSyncData` and `commitPivotBlock` then use the peer-supplied `BlockNum` as the persistence key:

```go
d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
``` [3](#0-2) [4](#0-3) 

`PutStakingInfoToDB` writes directly to the key `stakingInfoKey(sourceNum)` with no further checks: [5](#0-4) 

By contrast, the `SyncStakingInfo` recovery path explicitly validates the returned `BlockNum` against the expected value and aborts on mismatch: [6](#0-5) 

### Impact Explanation

`GetStakingInfo` reads from the DB first, using a locally computed `sourceNum`: [7](#0-6) 

If the entry at `sourceNum` is absent (written at `wrongNum` instead), it falls back to `getFromStateByNumber(sourceNum)`. After fast sync, historical trie state is unavailable for pre-pivot blocks, so this call fails and the error propagates — breaking block processing for every block that references that staking interval. If `wrongNum` is itself a valid staking interval block that will later be queried, the attacker-controlled `RewardAddrs` and `StakingAmounts` are used for reward distribution, redirecting KAIA block rewards to attacker-chosen addresses.

The `P2PStakingInfo` struct carries all reward-sensitive fields: [8](#0-7) 

### Likelihood Explanation

Any peer that the syncing node connects to during fast sync can exploit this. No special privilege, governance key, or validator majority is required — only the ability to be a registered P2P peer, which is the normal fast-sync trust model. The attack is silent (no error is returned; only a log line is emitted with the wrong block number).

### Recommendation

In `queue.DeliverStakingInfos`, replace the no-op `validate` with a check that `stakingInfoList[index].BlockNum == header.Number.Uint64()`. In `commitFastSyncData` and `commitPivotBlock`, use `result.Header.Number.Uint64()` (or the locally computed staking-interval block number) as the DB key instead of `result.StakingInfo.BlockNum`, mirroring the guard already present in `SyncStakingInfo`.

### Proof of Concept

1. Stand up a fast-sync node requesting staking infos for interval block `N`.
2. Serve a `StakingInfoMsg` response where `P2PStakingInfo.BlockNum = M` (M ≠ N, but M is a valid staking interval block) and `CouncilRewardAddrs = [attacker_addr]`.
3. After sync, assert `ReadStakingInfo(db, M)` returns the injected data with `attacker_addr` as reward address, and `ReadStakingInfo(db, N)` returns nil.
4. Trigger `GetStakingInfo(N + 1)` (a block that references source block N): observe it falls back to state, fails (state unavailable), and block processing errors out — or, if M is queried, rewards flow to `attacker_addr`.
