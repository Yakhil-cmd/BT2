### Title
`sanityCheckWorktree` accepts partially-checked-out worktrees as valid, causing indefinite publication of incomplete content - ([File: main.go])

### Summary
The `BadgerYieldSource.balanceOfToken` bug is a "read-partial-state, report-as-whole" flaw: it derives a value that should represent the full/authoritative balance from a subset of the actual state (funds still in the Sett) and never corrects for the majority of state living elsewhere (the strategies). The closest reachable analog in `git-sync` is `repoSync.sanityCheckWorktree`, which is used to decide whether an on-disk worktree is "good" (and therefore safe to keep serving through the published `--link` symlink) by checking only a subset of the real state — `git rev-parse HEAD` plus `git fsck --connectivity-only` — while explicitly *not* verifying that the working tree actually contains all the checked-out files.

### Finding Description
In `main.go`, `sanityCheckWorktree` is documented as insufficient by its own comment: [1](#0-0) 

It only verifies (a) the worktree directory is non-empty, (b) `HEAD` matches the expected hash, and (c) `git fsck --connectivity-only` succeeds (an object-graph connectivity check, not a working-tree completeness check). None of these checks detect a working tree where `git reset --hard`/checkout was interrupted partway through writing files to disk.

This check gates the steady-state branch of `SyncRepo`. When the locally recorded hash equals the newly fetched remote hash, `git-sync` calls `sanityCheckWorktree` on the *existing* worktree instead of re-running `configureWorktree` (which performs the actual `git reset --hard` checkout): [2](#0-1) 

If the check passes, `changed` stays `false`, and the entire block that calls `git.configureWorktree` (the only place that re-materializes files via `git reset --hard hash`) is skipped: [3](#0-2) 

Because git object-store consistency (fsck) is independent of whether the working directory finished being written, a worktree that was left partially checked out (e.g., process killed by `--sync-timeout`, OOMKill, container restart mid-`reset --hard`) will still satisfy `sanityCheckWorktree` on the next loop iteration. Since the remote hash has not changed, `git-sync` treats the situation as "nothing to do" and never re-executes the checkout to repair the missing files. The `--link` symlink keeps pointing at this same worktree indefinitely, exactly as it did before the crash.

### Impact Explanation
This satisfies the accepted "publishing wrong or partial content" impact category: downstream consumers reading through the `--link` symlink (the documented "contract" for consumers, per `README.md:190-195`) receive an incomplete checkout while `git-sync` reports success (`setRepoReady`, `syncCount++` logged as "updated successfully") and metrics (`METRIC_GOOD_SYNC_COUNT`) reflect a healthy sync. There is no self-healing path: because the hash comparison, not content verification, drives `changed`, the incomplete worktree persists until the upstream ref changes to a *different* hash. This mirrors the core defect class of the reference report — a partial view of state is treated as authoritative and propagated to consumers.

### Likelihood Explanation
Triggering requires the checkout step (`git reset --hard`, submodule update, or sparse-checkout population in `configureWorktree`) to be interrupted after `git-sync` has already fetched/reset the bare repo but before the working tree is fully populated. This can be induced by an attacker who pushes a commit crafted to make the checkout unusually slow or large (many files, large blobs, deep submodule trees) combined with `--sync-timeout` or normal container lifecycle events (OOM kill, node eviction, `SIGKILL`) hitting mid-checkout — none of which require special flags beyond default sidecar operation. The likelihood of exact timing is moderate/environment-dependent rather than deterministic, and the eventual recovery does happen once the upstream ref advances, which limits — but does not eliminate — the persistence of the exposure.

### Recommendation
Strengthen `sanityCheckWorktree` to actually verify working-tree completeness relative to the tree object it claims to represent, e.g. via `git status --porcelain=v1 --ignored=no` compared against `git diff --stat HEAD` (or `git diff-index --quiet HEAD --`) to detect missing/staged-but-unwritten files, rather than relying solely on `HEAD` pointer equality and object-graph connectivity. Alternatively, persist an explicit "checkout complete" marker (written only after `configureWorktree` fully succeeds) and check that marker before trusting an existing worktree in the `currentHash == remoteHash` fast path.

### Proof of Concept
1. Start `git-sync` against a repository with a large tree/many files, or set an aggressively short `--sync-timeout`.
2. Push a commit whose checkout duration exceeds the timeout, or kill the `git-sync` container/process (e.g. `SIGKILL`) while `configureWorktree`'s `git reset --hard <hash>` (main.go:1729) is writing files to `.worktrees/<hash>`.
3. Restart `git-sync` without changing the upstream ref. `SyncRepo` computes `currentHash == remoteHash`, calls `sanityCheckWorktree`, which passes because `HEAD` already points at `<hash>` and `git fsck --connectivity-only` only checks object reachability, not working-tree completeness (main.go:1518-1533).
4. `changed` remains `false`; `configureWorktree` (and thus the repair checkout) is never invoked (main.go:1918-1945); the `--link` symlink continues to serve the partially-checked-out directory to consumers indefinitely, while metrics/logs report a healthy, up-to-date sync.

// sanityCheckWorktree tries to make sure that the dir is a valid git
// repository.  Note that this does not guarantee that the worktree has all the
// files checked out - git could have died halfway through and the repo will
// still pass this check.
func (git *repoSync) sanityCheckWorktree(ctx context.Context, worktree worktree) bool {
	git.log.V(3).Info("sanity-checking worktree", "repo", git.root, "worktree", worktree)

	// If it is empty, we are done.
	if empty, err := dirIsEmpty(worktree.Path()); err != nil {
		git.log.Error(err, "can't list worktree directory", "path", worktree.Path())
		return false
	} else if empty {
		git.log.V(0).Info("worktree is empty", "path", worktree.Path())
		return false
	}

	// Make sure it is synced to the right commmit.
	stdout, _, err := git.Run(ctx, worktree.Path(), "rev-parse", "HEAD")
	if err != nil {
		git.log.Error(err, "can't get worktree HEAD", "path", worktree.Path())
		return false
	}
	if stdout != worktree.Hash() {
		git.log.V(0).Info("worktree HEAD does not match worktree", "path", worktree.Path(), "head", stdout)
		return false
	}
