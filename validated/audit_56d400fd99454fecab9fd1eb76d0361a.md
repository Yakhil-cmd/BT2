### Title
`ERC20Transactor` credits the full nominal amount for fee-on-transfer ERC20 tokens, causing deterministic reverts on deposit — ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor` (wired into Asset Hub Westend's `AssetTransactors` in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs:222-246`) implements `TransactAsset` for arbitrary ERC20 contracts deployed through `pallet-revive`. On `withdraw_asset_with_surplus` it moves the ERC20 balance into a shared `TransfersCheckingAccount` via `IERC20::transfer` and, if the call returns `true`, credits the **full nominal `amount`** into the XCM holding register (`AssetsInHolding::new_from_fungible_credit(..., Erc20Credit(amount))`), regardless of what the checking account actually received. On `deposit_asset_with_surplus`, it attempts to move that same nominal `amount` out of the checking account to the beneficiary. For a fee-on-transfer ERC20 (a legal, standard-conforming ERC20 that deducts/burns a percentage on `transfer`), the checking account never actually holds `amount` — it holds `amount - fee`. The subsequent `transfer(amount)` call from the checking account will then fail (insufficient balance / contract logic), reverting the entire XCM operation. This is the direct Polkadot-SDK analog of the reported Notional bug: an accounting layer that assumes `transferred == credited`, which is false for fee-on-transfer tokens, causing every operation over such a token to revert.

### Finding Description
The root cause mirrors the external report precisely:

- In `AaveV3HoldingsOracle`/`ExternalLending`, `expectedUnderlying`/`withdrawAmount` is the *nominal* amount, but the actual balance delta after redeeming a fee-on-transfer token is smaller, so the `require(data.expectedUnderlying <= underlyingBalanceChange)` check always fails.
- In `ERC20Transactor::withdraw_asset_with_surplus` (`erc20_transactor.rs:150-216`), the code calls `IERC20::transferCall{ to: checking_address, value: amount }` and, upon a `true` return, immediately creates `Erc20Credit(amount)` — the full nominal amount — without checking that the checking account's ERC20 balance actually increased by `amount`. This is the same "trust the nominal value" flaw.
- In `ERC20Transactor::deposit_asset_with_surplus` (`erc20_transactor.rs:225-306`), the transactor later tries to move the *same nominal* `amount` out of the checking account (`IERC20::transferCall{ to: address, value: amount }`, line 253). Since the checking account's real ERC20 balance for this asset only increased by `amount - fee` in the corresponding withdraw step (fee-on-transfer tokens deduct a percentage on every `transfer`, including this one), the second `transfer` call will either revert or return `false` once the requested `amount` exceeds the checking account's real, fee-adjusted balance. The code handles this by returning `XcmError::FailedToTransactAsset("ERC20 contract transfer failed")` (line 284-287) or `"ERC20 contract reverted"` (line 274), aborting the whole XCM message.

Attacker path (no privileged role required):
1. Any signed account can deploy an arbitrary Solidity/PolkaVM contract via `pallet-revive` (`InstantiateOrigin = EnsureSigned<Self::AccountId>` in `asset-hub-westend/src/lib.rs:1387-1435`), including a standard fee-on-transfer ERC20 (e.g., a token that burns/redirects 1% on every `transfer`).
2. The attacker (or any user, since XCM `execute`/asset transfer is permissionless for signed accounts via `pallet_xcm::execute`/`transfer_assets`) references that contract's address as an `AccountKey20` XCM asset identifier, matched by `assets_common::ERC20Matcher` and routed to `ERC20Transactor`.
3. Any XCM program that performs `WithdrawAsset` followed by `DepositAsset` (or the local ERC20 XCM helper flow demonstrated in `withdraw_and_deposit_erc20s`, `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:1871-1936`) for this token deterministically fails at the deposit step, because the checking account never holds the full nominal `amount` credited during withdraw.

### Impact Explanation
This is a deterministic Denial-of-Service for any ERC20 registered on Asset Hub (Westend, and any future chain using `assets_common::ERC20Transactor`) that implements fee-on-transfer semantics: local transfers, and any XCM cross-chain transfer of that ERC20 asset class, will always revert once the deposit leg is attempted. This matches the "Medium" categorization of the original Notional finding (deterministic failure of a legitimate token category, not attacker theft of others' funds) — it is a self-contained availability break for a specific, standards-compliant token category rather than a cross-user fund-drain, since the checking account's per-asset (per-contract-address) balance is only touched by transfers of that specific ERC20 contract. I could not find, within available context, additional code paths where the inflated `Erc20Credit(amount)` credit is spent elsewhere within the same XCM program (e.g., passed to a `Trader` or `AssetExchanger` before the failing deposit) that would let the phantom credit be exploited to extract value from unrelated assets; this would need further tracing of `xcm_executor` holding-register consumption order in a live environment before elevating severity.

### Likelihood Explanation
Likelihood is high for reachability: deploying an ERC20 contract via `pallet-revive` and referencing it via XCM `AccountKey20` is fully permissionless and requires no privileged role, matching the `ERC20Transactor` matcher and checking-account wiring confirmed in `xcm_config.rs`. Fee-on-transfer ERC20s are a common, legitimate token pattern (deflationary/tax tokens), so this is not a contrived edge case; any user or protocol wishing to bridge such a token via Asset Hub's ERC20-XCM integration will hit this failure on the very first attempted transfer.

### Recommendation
- In `withdraw_asset_with_surplus`, measure the checking account's actual ERC20 balance delta (via `balanceOf` before/after, or the ERC20's `Transfer` event value) instead of assuming the nominal `amount` was received, and credit `AssetsInHolding` with the *actual* delta.
- In `deposit_asset_with_surplus`, transfer the credited (actual) amount rather than the original nominal `amount`, and again verify the beneficiary's realized balance delta rather than trusting the boolean return value alone.
- Alternatively, explicitly document/enforce (e.g., via a matcher check) that only ERC20 contracts with verified non-fee-on-transfer, unit-decimal `transfer` semantics may be registered as XCM-transactable assets through this transactor.

This finding is derived from static analysis of `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` and its wiring in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs:213-246`, cross-referenced with the working non-fee-on-transfer test `withdraw_and_deposit_erc20s` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:1871-1936`, which shows the normal successful flow (`beneficiary_amount == erc20_transfer_amount`) that would instead fail with `FailedToTransactAsset("ERC20 contract transfer failed")` if the deployed `MyToken` contract implemented a fee-on-transfer deduction. A concrete reproduction would require compiling a fee-on-transfer Solidity fixture (analogous to the existing `MyToken`/`Stipends.sol` fixtures under `substrate/frame/revive/fixtures/contracts/`), instantiating it via `bare_instantiate`, and repeating the `withdraw_and_deposit_erc20s` test body to observe the deposit-step revert — this execution was not performed here due to tool limitations (read-only static analysis only), so this should be validated experimentally by a background agent with Rust build/test tooling before being treated as fully confirmed.
