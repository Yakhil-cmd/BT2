### Title
Webhook Signature Verified Against `repository.owner.login`, but Sync/Status Actions Trust the Unverified `repository.full_name` — Cross-Repository Command Injection via Webhook Confusion - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')`. Once the signature check passes, the raw JSON payload is handed unmodified to the event handlers, which independently derive the *target* repository from `payload.dig('repository', 'full_name')`. Nothing binds these two fields together cryptographically — the signature only proves "this payload was signed with organization X's secret," not "the `repository.full_name` field genuinely belongs to organization X." An attacker who legitimately controls a repository (and therefore its own webhook secret) in one organization can forge a payload whose `repository.owner.login` matches their own org (so it passes verification) while `repository.full_name` names a completely different, victim-controlled repository/stack.

### Finding Description
The verification and consumption paths use two different fields out of the same untrusted JSON body:

- Signature/organization selection: [1](#0-0) [2](#0-1) 
- Target-repository/stack selection used by every handler: [3](#0-2) 

`Shipit.github(organization: repository_owner)` resolves a `GitHubApp` instance per organization, each carrying its own independently configured `@webhook_secret`: [4](#0-3) [5](#0-4) 

Because `repository.owner.login` and `repository.full_name` are both attacker-controlled fields inside the same JSON body that only needs to satisfy `HMAC(webhook_secret_of_owner_login, raw_body) == X-Hub-Signature`, an attacker who owns/administers **any** repository configured in Shipit (and thus knows or can set that repository's webhook secret through the normal GitHub webhook setup) can:
1. Set `repository.owner.login` = their own controlled organization (so `verify_signature` fetches *their* organization's `GitHubApp` and the HMAC computed with their own secret validates).
2. Set `repository.full_name` = the victim's `owner/repo` (any stack tracked by Shipit).

This breaks the intended binding: *the organization whose secret authenticated the request* ≠ *the repository whose stacks get written to*. Concretely:

- `PushHandler#process` resolves stacks via `repository_name` (i.e., the attacker-supplied `full_name`) and calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack/branch — letting the attacker enqueue a `GithubSyncJob` for a victim stack with a `SHA` of their choosing. [6](#0-5) 
- `StatusHandler#process` doesn't even scope by repository; it applies `commit.create_status_from_github!(params)` to *any* `Commit` row matching the attacker-supplied `sha`, using `state`/`description`/`context` fully controlled by the attacker. Combined with the owner/full_name confusion, an attacker authenticated only as one organization can forge CI status ("success") on a commit belonging to an unrelated victim stack, which can gate continuous-deployment logic. [7](#0-6) 

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out in scope. Forged/favorable CI statuses can influence `continuous_deployment` gating logic on a victim's stack, and forced `sync_github` calls can be used to manipulate a victim stack's known commit history/state — both are unauthorized cross-repository writes performed by an attacker who only possesses credentials (a webhook secret) for their own, unrelated repository. This satisfies the Critical bar of "cross-repository writes."

### Likelihood Explanation
Exploitability requires only that the attacker control (or configure) one GitHub repository already registered as a Shipit-tracked organization/repo — a routine, unprivileged setup step, not a privileged Shipit account or `ApiClient` token. No repository write access to the *victim* repo, no `webhook_secret` of the victim, and no compromise of Shipit internals is required. The only non-trivial part is knowing a valid target stack's branch/commit SHAs, which are public GitHub metadata.

### Recommendation
Bind verification and action to the same value: derive `repository_owner` and the resolved target repository from the same already-verified struct field, and additionally verify that the resolved `Repository`/`Stack`'s actual owner matches the organization whose secret validated the signature before executing any handler logic (e.g., compare `Repository.from_github_repo_name(repository_name).owner` against `repository_owner` post-verification, rejecting mismatches). Alternatively, look up the webhook secret via the resolved `Repository` record itself (post `full_name` lookup) rather than trusting the payload's `owner.login` field independently.

### Proof of Concept
1. Attacker registers/owns `attacker-org/attacker-repo` as a Shipit-tracked stack, thus knows the webhook secret configured for `attacker-org` (`Shipit.github(organization: 'attacker-org')`'s `webhook_secret`).
2. Attacker crafts a `push` (or `status`) webhook JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(attacker_webhook_secret, raw_body)`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`), which validates successfully using the attacker's own secret. [1](#0-0) 
5. `PushHandler.call(params)` then resolves stacks via `repository.full_name = "victim-org/victim-repo"` and triggers `sync_github` on the victim's stack — despite the request never having been signed by `victim-org`'s webhook secret. [3](#0-2) [6](#0-5)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
