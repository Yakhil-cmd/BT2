### Title
Signature verification org selection is decoupled from the repository whose ReviewStack gets provisioned - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to validate against using `params.dig('repository','owner','login')`, but `OpenedHandler#repository` resolves the target `Shipit::Repository` (and thus the `review_stacks` scope passed to `ReviewStackAdapter`) purely from `params.repository.full_name`. In a multi-org Shipit deployment these two fields are never checked against each other, so a signature that is valid for "attacker-org" can carry a payload whose `repository.full_name` names a completely different, review-stacks-enabled victim repository.

### Finding Description
The broken binding, stated as an equality that the code must but does not enforce:
`org_used_for_signature_verification (params.repository.owner.login) == org_that_owns_the_repository_being_mutated (owner segment of params.repository.full_name)`.

Trace:
- `verify_signature` in [1](#0-0)  computes `repository_owner = params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_body)`.
- In a multi-org config, `Shipit.github` maps that owner string to a distinct per-organization `webhook_secret` via `github_app_config` [2](#0-1) , exactly as documented for multi-tenant setups in `docs/setup.md` (commented multi-org example).
- Once the signature check passes, the raw JSON body (including the attacker-controlled `repository.full_name`) is dispatched unchanged to `Shipit::Webhooks.for_event(event)` handlers [3](#0-2) .
- `OpenedHandler#process` and `#repository` resolve the actual `Shipit::Repository` solely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name` [4](#0-3) . The handler's own params schema only requires `repository.full_name`, never `repository.owner.login` [5](#0-4) , so there is no re-derivation or cross-check against the owner used for signature verification anywhere in the handler chain.
- If provisioning is enabled on that resolved repository, `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` creates a `Shipit::ReviewStack` scoped to that (victim) repository using attacker-supplied `branch: params.pull_request.head.ref` and `environment: "pr#{params.number}"` [6](#0-5) .

Exploit flow (multi-org deployment only): the attacker legitimately administers "attacker-org" as one of the configured tenants in Shipit's multi-org `secrets.github` config, and therefore genuinely knows their own org's `webhook_secret` (they set it when installing their GitHub App). They send `POST /webhooks` with `X-Github-Event: pull_request`, a valid `X-Hub-Signature` computed with their own secret over the raw body, and a body where `repository.owner.login = "attacker-org"` (so verification picks their own secret) but `repository.full_name = "victim-org/victim-repo"` and arbitrary `pull_request.head.ref` / `number`. `verify_signature` passes because it only checks the HMAC against attacker-org's own secret; the actual mutated record belongs to victim-org's repository.

This fails to be caught by any existing guard: `verify_signature` never compares `repository.owner.login` against `repository.full_name`'s owner segment; `drop_unhandled_event` only checks event type; the `ExplicitParameters` schema in `OpenedHandler` only requires `repository.full_name`, not `owner.login`; and `Repository.from_github_repo_name` does no authorization check, it is a pure lookup by string [7](#0-6) .

Note: in the common **single-org** configuration, `Shipit.github(organization:)` ignores the `organization:` argument entirely and always uses the single global `secrets.github` config [8](#0-7) , so there the vulnerability is moot (only one secret exists, held by the operator, not any tenant). The finding is scoped to the documented multi-org configuration mode.

### Impact Explanation
An attacker who legitimately controls one tenant org in a multi-org Shipit deployment can force creation of a `Shipit::ReviewStack` (with attacker-chosen `branch` and `environment`) under any other tenant's tracked, review-stacks-enabled repository, without ever authenticating as that other tenant. This is a payload-for-one-repository-mutating-another's-stack scenario — a cross-tenant record write triggered by a signature that was never bound to the target repository. Downstream, `ReviewStackProvisioningQueue.add(stack)` queues real provisioning (branch checkout/build) for the victim repository, so this can lead to running provisioning/deploy commands against victim-owned infrastructure using attacker-controlled branch refs and PR numbers. It is repeatable against any tenant repository whose `full_name` the attacker can guess/know and that has review stacks enabled with `allow_all` or `allow_with_label`/`prevent_with_label` behavior satisfiable by attacker-controlled label state (which the attacker also fully controls in the forged payload). This matches the Critical category: "a payload for one repository mutating another's stack ... or an unauthorized deploy."

### Likelihood Explanation
Requires: (1) the Shipit instance uses the multi-org `secrets.github` config format (each org has its own `webhook_secret`) as documented in `docs/setup.md`; (2) the attacker legitimately owns/administers at least one such configured tenant org (so they know their own secret) — no privileged Shipit role, session, or victim secret needed; (3) the victim repository is already tracked by Shipit with `review_stacks_enabled` and a provisioning behavior the attacker can satisfy via label state they control in their own crafted payload. Given those preconditions, the attack is a single unauthenticated HTTP POST, fully repeatable, and requires no interaction with real GitHub webhook delivery (the endpoint accepts arbitrary raw JSON bodies as long as the signature matches).

### Recommendation
In `WebhooksController#verify_signature` (or in the shared `Shipit::Webhooks::Handlers::Handler`), after signature verification succeeds, derive the repository owner from `params.repository.full_name` and assert it equals `repository_owner` (the value used to select the signing organization) before dispatching to any handler; reject the request (422) on mismatch. Alternatively, resolve the target `Shipit::Repository` using the verified organization as a hard constraint (e.g., `Repository.find_by(owner: repository_owner, name: ...)`) rather than trusting the full `full_name` string independently.

### Proof of Concept
Minitest plan (multi-org config), no live GitHub:
1. Configure `Rails.application.credentials.github` with two orgs, `"attacker-org"` (webhook_secret `"attacker-secret"`) and `"victim-org"` (webhook_secret `"victim-secret"`), matching the multi-org schema.
2. Create `victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo", review_stacks_enabled: true, provisioning_behavior: "allow_all")`.
3. Build a `pull_request_opened`-style payload with `repository: { owner: { login: "attacker-org" }, full_name: "victim-org/victim-repo" }`, `pull_request.head.ref = "attacker-branch"`, `number: 999`.
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "attacker-secret", body.to_json)`.
5. `post :create, body: body.to_json, as: :json` with headers `X-Github-Event: pull_request`, `X-Hub-Signature: signature`.
6. Assert `response.status == 200` (signature accepted).
7. Assert `victim_repo.review_stacks.where(environment: "pr999", branch: "attacker-branch").exists?` is `true` — proving a `ReviewStack` was created under `victim-org/victim-repo` using a signature that only attacker-org's secret produced, i.e. the two sides of the equality (`repository_owner` used for auth vs. owner of the repository actually mutated) diverge.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
