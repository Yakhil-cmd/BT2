### Title
Private asset ("textcoin") payload file written with default world-readable permissions - (File: wallet.js)

### Summary
`storePrivateAssetPayload()` in [1](#0-0)  persists the mnemonic (a spendable private key derivation seed) and the private payment chain of a private-asset "textcoin" to disk via `fs.writeFile(fullPath, zipFile, cb)` without specifying a restrictive file mode. Node's `fs.writeFile` defaults to mode `0o666`, which combined with the typical process umask of `022` yields world-readable `0o644` files — the same insecure-permissions bug class described in the Hermes Agent advisory (GHSA-99f9-j8r3-p853), where secrets were written with default, world-readable permissions.

### Finding Description
When a wallet sends a private-asset payment to a non-hosted address (`sendMultiPayment` → `saveMnemonicsPreCommit` path, see [2](#0-1) ), and a `getPrivateAssetPayloadSavePath` callback is supplied, the resulting mnemonic and private payment chains are serialized into a ZIP and written to `fullPath` with `fs.writeFile(fullPath, zipFile, cb)` — no `{ mode: 0o600 }` option is passed, and no `fs.chmod` call restricts the permissions afterward: [3](#0-2) 

The stored object explicitly bundles the plaintext mnemonic together with the private-chain proof of the payment: [4](#0-3) 

Unlike the RocksDB/SQLite app-data directories, which are created with an explicit `0o700` mode in [5](#0-4)  and [6](#0-5) , this particular payload file is written to a caller-chosen path with no permission hardening at all, so it inherits the OS default umask. On typical multi-user Linux/macOS systems (umask `022`) the file ends up `-rw-r--r--`, readable by any local user or unprivileged process on the same host.

### Impact Explanation
The mnemonic in this file is a BIP-39 phrase from which `expandMnemonic()` derives a private key (`xPrivKey`) and a spendable single-sig address (`addrInfo.address`, `addrInfo.definition`), as shown in `receiveTextCoin`/`expandMnemonic`: [7](#0-6) . Anyone who reads this world-readable file can reconstruct the private key and claim/spend the private-asset funds addressed to that mnemonic before or instead of the intended recipient, and can also read the private payment chain contents (amounts, asset id, sender linkage) that were meant to stay confidential between the two payment counterparties. This is a direct path to unauthorized spending/theft of the private-asset funds and to loss of payment confidentiality, reachable by any local unprivileged user or process on the machine hosting the wallet.

### Likelihood Explanation
Exploitation only requires local filesystem read access — no cryptographic weakness or network position is needed. Any host that runs the wallet in a shared/multi-tenant environment (shared server, CI machine, or any account with weaker isolation) exposes this file to co-resident users by default umask behavior. The vulnerable code path is reached whenever an application built on ocore uses `getPrivateAssetPayloadSavePath` to send a private-asset textcoin to a file-based recipient, a documented supported flow.

### Recommendation
Explicitly set restrictive permissions when writing the private payload file, e.g. `fs.writeFile(fullPath, zipFile, { mode: 0o600 }, cb)`, and additionally call `fs.chmod(fullPath, 0o600, ...)` after creation to defend against umask misconfiguration, mirroring the `0o700` hardening already applied to the app data directories in `kvstore.js` and `sqlite_pool.js`.

### Proof of Concept
1. On a shared multi-user Linux host, run an ocore-based wallet and send a private asset payment where `opts.getPrivateAssetPayloadSavePath` points to e.g. `/tmp/payload.zip` (this is the intended, documented flow for sending indivisible/private assets to non-hosted recipients).
2. After `storePrivateAssetPayload` completes, as a second unprivileged local user run `ls -l /tmp/payload.zip` — observe permissions `-rw-r--r--` (mode 0644).
3. That second user reads the file, unzips `private_textcoin`, extracts `mnemonic`, and calls the same `expandMnemonic()`/`receiveTextCoin()` logic to derive the private key and claim the funds for themselves, before the legitimate recipient does.
