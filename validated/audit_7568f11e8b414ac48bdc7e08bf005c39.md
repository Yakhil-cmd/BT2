Note: `StatusHandler` at [1](#0-0)  only requires `sha` and doesn't even scope to a repository — it looks up commits globally by `sha`, which strengthens the finding below.

### Title
Webhook signature verification is keyed by a payload-controlled organization field that is decoupled from the repository the handler acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The webhook signature check in `WebhooksController#verify_signature` selects which GitHub App/secret to verify against using an unauthenticated field of the JSON body (`repository.owner.login` / `organization.login`), and silently treats the request as *verified* whenever that organization has no `webhook_secret` configured. The event handlers, however, act on a completely different field of the same body (`repository.full_name`, or in the case of `status` events, a bare `sha` with no repository scoping at all). Because these two fields are never cross-checked, and because `verify_webhook_signature` returns `true` when a secret is absent, an unauthenticated caller can pick any organization slot lacking a secret to short-circuit verification, then have handlers act on an arbitrary, unrelated repository/stack.

### Finding Description
`WebhooksController#verify_signature` derives the organization used for verification purely from the request body, before any signature check occurs: [2](#0-1) [3](#0-2) 

`GitHubApp#verify_webhook_signature` bypasses verification entirely when the selected organization has no configured secret: [4](#0-3) 

The webhook secret is documented as optional per organization, and Shipit explicitly supports multiple GitHub Apps/organizations in one instance: [5](#0-4) [6](#0-5) 

Once past `verify_signature`, the controller dispatches the parsed body to handlers without any re-validation that `repository.owner.login` matches the repository actually mutated: [7](#0-6) 

Handlers resolve the target repository/stack using a *different* field, `repository.full_name`, which has no relationship enforced with `repository.owner.login`: [8](#0-7) 

Worse, `StatusHandler` does not even use the repository field — it matches commits globally by `sha` across the entire installation: [1](#0-0) 

This breaks the trust binding: `organization authenticated (via signature check) == repository/commit written (via handler)`. The equality does not hold — the code authenticates against organization A's (or an org with no secret's) identity while writing to organization B's repository or to a globally-matched commit SHA.

### Impact Explanation
An unauthenticated attacker who knows (a) that at least one configured organization in the Shipit instance lacks a `webhook_secret` (discoverable by probing — an invalid/absent signature against that org slot still returns 200, while other orgs return 422), and (b) the `full_name` of a real target repository/stack (public information), can:
- Forge `push` events (`PushHandler`) to trigger `GithubSyncJob` against an arbitrary stack with an attacker-chosen `expected_head_sha`.
- Forge `status` events (`StatusHandler`) to create arbitrary commit `Status` records (state `success`) on *any* commit SHA in the entire Shipit database, since the handler performs no repository/stack scoping at all.
- Because `MergeRequest#all_status_checks_passed?` and `Commit#deployable?` rely on `Status` records to gate CI requirements, forged "success" statuses can enable an unauthorized automatic merge or deploy of a commit that never actually passed CI, meeting the "unauthorized deploy/merge" Critical impact bar.

This requires no Shipit session, no API token, no webhook secret, and no privileged GitHub account — only knowledge of a misconfigured (secret-less) org slot and a target repo name.

### Likelihood Explanation
Likelihood is moderate-to-high in any multi-tenant or "quick-start" Shipit deployment: the setup docs and secrets templates explicitly present `webhook_secret` as optional, so it is plausible that at least one configured GitHub App in a multi-org install has none set, especially for internal/test orgs added ad hoc. The attack requires no credentials at all — only trial requests to `/webhooks` with different `repository.owner.login` values to find one that returns 200 with a bogus signature, which is externally observable behavior.

### Recommendation
- Treat a missing `webhook_secret` as a configuration error, not as "always verified" — reject the webhook (422/500) instead of returning `true` from `verify_webhook_signature` when no secret is configured.
- Enforce that the organization used to select the verification key matches the organization embedded in `repository.full_name` (i.e., `repository.owner.login` must equal the first path segment of `repository.full_name`), rejecting mismatches before dispatching to handlers.
- Scope `StatusHandler` (and any other handler that looks up records by a bare identifier such as `sha`) to the repository/stack identified in the verified payload rather than searching globally across all commits.

### Proof of Concept
Assume a Shipit instance is configured with two orgs in `secrets.yml`: `trusted-org` (has `webhook_secret` set) and `test-org` (no `webhook_secret`, e.g. left blank during onboarding per the docs). `trusted-org/victim-repo` has a stack in Shipit.

```
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   # garbage, unverifiable

{
  "sha": "<victim commit sha awaiting real CI>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "test-org" }, "full_name": "trusted-org/victim-repo" }
}
```

- `repository_owner` resolves to `test-org`.
- `Shipit.github(organization: 'test-org').verify_webhook_signature(...)` returns `true` because `test-org` has no `webhook_secret` (`return true unless webhook_secret`).
- `StatusHandler#process` matches `Commit.where(sha: params.sha)` globally and creates a forged `success` `Status`, regardless of `repository.full_name`/owner mismatch, potentially unblocking a merge/deploy in `trusted-org/victim-repo`.

Note: I could not fully verify the exact multi-org lookup implementation of `Shipit.github(organization:)` (in `lib/shipit.rb`) within the available index — the citation above is based on `GitHubApp#verify_webhook_signature`'s documented behavior and the `WebhooksControllerTest` fixtures showing per-organization dispatch (`Shipit.github(organization: 'shopify')`). A full audit of `lib/shipit.rb`'s org-resolution/caching logic would benefit from a live Devin session with complete file access.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
