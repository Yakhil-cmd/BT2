### Title
Cross-organization webhook forgery via signature/repository field mismatch enables unauthorized commit status injection and deploy triggering - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The `GorplesCoin._update()` bug lets an excluded address break a trust binding between the address that is checked (`to`) and the address the fee logic is supposed to protect (`from`). The same class of bug exists in Shipit's webhook processing: the signature/organization check is performed against one payload field (`repository.owner.login` / `organization.login`), while the code paths that actually act on data use an entirely different, unrelated payload field (`repository.full_name`). Because these two fields are never cross-checked, an org that legitimately controls its own GitHub App/webhook secret on a multi-tenant Shipit instance can forge a validly-signed webhook that "authenticates as" its own org but "acts on" a completely different org/repo's stack.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the webhook secret used for HMAC verification) using `repository_owner`, which is derived only from the `repository.owner.login` (or `organization.login`) field of the JSON body: [1](#0-0) [2](#0-1) 

The signature itself is computed over the entire `raw_post` HMAC-signed with that org's `webhook_secret`: [3](#0-2) 

However, once the signature passes, handlers resolve which `Repository`/`Stack` to operate on using a **different** field — `repository.full_name` — via the shared `Handler#repository_name` helper: [4](#0-3) 

Nothing ties `repository.owner.login` (checked by signature verification) to `repository.full_name` (used to select the target `Repository`/`Stack`). In a multi-org deployment (`Shipit.github(organization:)` supports per-organization webhook secrets, see `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`), each organization admin knows their own org's `webhook_secret`. An attacker who administers "OrgOne" (with an installed GitHub App/webhook pointed at this Shipit instance) can freely construct an arbitrary JSON body, set `repository.owner.login` (or `organization.login`) to `"OrgOne"` so `verify_signature` selects and validates against OrgOne's known secret, but set `repository.full_name` to `"victim-org/victim-repo"` — a completely unrelated repository already tracked by the same Shipit instance under a different, victim organization.

Concretely, `Webhooks::Handlers::StatusHandler` will create a `Status` for any commit matching the attacker-chosen `sha`, using attacker-controlled `state`, `context`, `description`, `target_url` fields, with no additional GitHub-side verification: [5](#0-4) 

`Commit#create_status_from_github!` → `Status.replicate_from_github!` persists these attacker-supplied values directly, and `add_status` can enqueue `stack.schedule_merges` and fire `deployable_status`/`commit_status` hooks when the state transitions to `pending`/`success`: [6](#0-5) [7](#0-6) 

Since Shipit's merge-queue and continuous-deployment logic gate on commit status becoming `success` (`stack.schedule_merges`, `Status#schedule_continuous_delivery`), an attacker who owns any single organization onboarded to a shared, multi-tenant Shipit instance can forge a `success` status for a victim organization's commit they do not control, without ever passing CI, potentially triggering an unauthorized merge or deploy of that victim's stack.

The equality that should hold but doesn't: `signature_verified_for(payload.repository.owner.login) == target_of_write(payload.repository.full_name)`. `verify_signature` only proves the request was HMAC-signed by *some* configured organization's secret; it never proves that organization is the owner of the repository the handlers subsequently mutate.

### Impact Explanation
This breaks a repository/organization trust boundary in a multi-tenant Shipit deployment: possession of one organization's legitimate webhook secret allows forging actions (fake commit statuses, forced sync triggers via `PushHandler`, spurious team/membership creation via `MembershipHandler`) against any other organization/repository tracked by the same instance. Faked `success` statuses can unblock the merge queue or continuous deployment for a victim stack, constituting an unauthorized merge/deploy — matching the Critical impact bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires the deployment to use the documented multi-organization GitHub App configuration (`Shipit.github(organization:)` with distinct secrets per org, an explicitly supported and documented setup per `docs/setup.md`). Any org admin already onboarded (an "unprivileged attacker" relative to other tenants' repositories) can exploit this with a single crafted HTTP request; no GitHub session, `ApiClient` token, or the Shipit app's own webhook secret is needed — only the attacker's own org's secret, which they legitimately possess.

### Recommendation
Cross-validate the field used for signature/organization selection against the field used to resolve the target repository before any handler runs — e.g., derive `repository_name` for lookup from the same `repository.owner.login`/`organization.login` value that authenticated the request (or verify `repository.full_name`'s owner segment matches `repository_owner`), and reject the webhook if they diverge.

### Proof of Concept
1. Deploy Shipit with multi-org GitHub Apps configured for `OrgOne` (attacker-controlled) and `victim-org` (victim), per `docs/setup.md`'s "Using Multiple Github Applications" section.
2. Attacker knows `OrgOne`'s `webhook_secret` (they created that GitHub App).
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha they know from public GitHub or Shipit UI>",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "victim-org/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(OrgOne_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgOne")`, validates the signature successfully (it truly matches OrgOne's secret), and lets the request through.
6. `Webhooks::Handlers::StatusHandler#process` resolves the target repository via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, finds the victim's tracked commit by `sha`, and creates a `success` `Status` on it — potentially unblocking merges/deploys for `victim-org`'s stack despite the attacker having no access to that organization at all.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
