### Title
Stack-scoped ApiClient tokens bypass their `stack_id` restriction in `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController` overrides the base controller's `stack` resolution method in a way that removes the scoping enforced for stack-restricted `ApiClient` tokens, allowing a token that is only supposed to authorize access to one specific stack to read the CI/deploy status of any other stack in the installation.

### Finding Description
`ApiClient` records can optionally be bound to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . The intended trust binding is: "this token authorizes reads/writes only for `stack_id`". `Api::BaseController` enforces this binding by scoping the `stacks` relation to the client's `stack_id` before resolving any `:stack_id` param:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`Api::CCMenuController` inherits from `BaseController` and requires only `read:stack` permission via `require_permission :read, :stack` [3](#0-2) , but it then redefines `stack` to resolve directly against the unscoped `Stack` relation instead of the client-scoped `stacks` relation:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

This is the equality that breaks: `current_api_client.stack_id` (the stack the token is authorized for) `!=` the `stack_id` param used to serve `#show` (the stack actually touched). Any holder of a valid, stack-scoped `read:stack` token — the normal, least-privileged, documented way to issue a CCMenu URL via `CCMenuUrlController` [5](#0-4)  — can call `GET /api/*/ccmenu` with a different `stack_id` param and successfully read that other stack's build/deploy status, because `check_permissions!` only checks the permission bit, not the stack scope [6](#0-5) , and the overridden `stack` method never consults `current_api_client.stack_id`.

The controller additionally accepts the token via a plain query-string parameter (`params[:token]`) rather than only via the `Authorization` header [7](#0-6) , which is by design for CI status widgets, but it compounds the impact since these tokens are routinely embedded in unauthenticated GET URLs (CCMenu client URLs) and can leak via referrer headers, logs, or browser history — increasing the chance that a scoped, low-privilege token ends up in an attacker's hands and gets reused against unintended stacks.

### Impact Explanation
This breaks the "stack a token authorizes versus stack it touches" binding: a token deliberately scoped to a single stack (the least-privileged token type in the system, created e.g. by `CCMenuUrlController#client`) can be used to read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc., see `shipit/ccmenu/project` view/test assertions [8](#0-7) ) for any stack in the Shipit installation, not just the one it was issued for. This is an unauthorized cross-stack read of deploy/build state, matching the High-severity class "escalation into `Shipit.github_teams` authorization... unauthenticated read of stack state, task streams or deploy output" in that it escalates a narrowly-scoped credential into a global read capability.

### Likelihood Explanation
Exploitation only requires possessing any valid `read:stack` `ApiClient` token scoped to a single stack — which is the normal, intentionally minimal-privilege token type generated by `CCMenuUrlController` for embedding in third-party CI dashboard tools — and changing the `stack_id` parameter in the request URL. No additional privileges, write access, or secrets are required beyond the token itself.

### Recommendation
Remove the `stack` override in `Api::CCMenuController`, or reimplement it to go through the scoped `stacks` relation (as `BaseController#stack` does), e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so a stack-scoped token can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. Create/obtain a stack-scoped `ApiClient` (e.g. via `CCMenuUrlController#client`, or the `here_come_the_walrus` fixture which is scoped to the `shipit` stack) with `permissions: ['read:stack']` and `stack_id` pointing to Stack A.
2. Call `GET /api/*/ccmenu?token=<token>&stack_id=<Stack B id>` where Stack B is a different stack the token was never scoped to.
3. Observe the response returns Stack B's `lastBuildStatus`/`lastBuildLabel`/deploy info successfully, even though the token's `stack_id` restricts it to Stack A — confirmed by contrasting `BaseController#stacks`/`#stack` scoping logic with `CCMenuController#stack`'s direct `Stack.from_param!` call.
