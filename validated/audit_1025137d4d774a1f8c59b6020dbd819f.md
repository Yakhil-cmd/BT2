### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while every event handler acts on the unauthenticated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the HMAC signature against using a field taken straight out of the still-unverified JSON body, while every `Shipit::Webhooks::Handlers::Handler` subclass resolves the `Repository`/`Stack` to act on using a *different* field of that same unverified body (`repository.full_name`). Because the engine's own multi-org secrets schema explicitly supports an organization with `webhook_secret: nil` (verification short-circuits to always-true), an attacker who knows/guesses that a low-value org has no secret configured can select that org for signature "verification" while pointing `repository.full_name` at a completely different, privileged repository, causing Shipit to process an unauthenticated payload as if it came from GitHub for that other repository.

### Finding Description
`verify_signature` resolves the signing key like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read directly from the raw, unauthenticated request body (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`) *before* the signature has been checked. It is then used to pick the `GitHubApp` instance via `Shipit.github(organization: repository_owner)`, whose `webhook_secret` drives the HMAC comparison: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when no secret is configured for that organization (`return true unless webhook_secret`). The engine's own test fixtures demonstrate that a "webhook_secret: nil" organization is a supported configuration for multi-org GitHub App setups: [4](#0-3) 

Once the (bypassed) signature check passes, the actual write target is resolved by every handler independently, using a *different* field of the same attacker-controlled JSON body: [5](#0-4) 

This is the exact binding break the report describes: the field that gates authentication/authorization (`repository.owner.login` / `organization.login`, used to select the trust domain) is not the field that determines the resource acted upon (`repository.full_name`). An attacker who knows an organization configured with `webhook_secret: nil` can:

1. Send a POST to `/webhooks` with `X-Github-Event: push` (or `status`, `check_suite`, etc.).
2. Set `repository.owner.login` (or `organization.login`) to the no-secret org, satisfying `verify_signature` (any/no `X-Hub-Signature` value is accepted).
3. Set `repository.full_name` to any other repository name tracked by Shipit (e.g., a privileged production repo), causing `Handler#stacks` to resolve to that repository's real `Stack`s.
4. The handler then processes the forged event against the real, unrelated stack (queuing `GithubSyncJob`, creating a `Status`, updating `check_suite` state, etc.) as though GitHub had actually sent it.

### Impact Explanation
Handlers reachable this way include `PushHandler` (queues `GithubSyncJob` for arbitrary stacks), `StatusHandler` (writes fabricated commit `Status` rows), and `CheckSuiteHandler` (drives `RefreshCheckRunsJob`). Fabricated/forced CI status or check-suite state for a targeted repository can satisfy `ci.require` gates that Shipit's merge queue and deploy safety checks rely on (see `merge`/`ci` config in README), enabling commits to be treated as deployable/mergeable when they should not be, i.e., an unauthorized deploy/merge path — one of the explicitly accepted High/Critical impacts. No GitHub credentials, Shipit session, or `ApiClient` token are required; only knowledge that some org served by this Shipit instance is configured without a `webhook_secret`.

### Likelihood Explanation
Requires the operator to run a multi-org GitHub App configuration with at least one organization lacking a `webhook_secret` (a state the engine itself ships test fixtures for, so it is a supported, not theoretical, configuration) and for the attacker to discover which org that is. Given webhook endpoints are unauthenticated by design and the org name space is discoverable (e.g., via public GitHub org names), likelihood is moderate rather than trivial, but the vulnerable code path exists regardless of deployment specifics and requires zero credentials.

### Recommendation
Do not use attacker-supplied JSON fields to select the verification key before the signature is validated. Bind webhook signature verification and resource resolution to the same, single field (ideally validated by a fixed/global webhook secret, or by re-deriving `repository_owner` strictly from `repository.full_name` after signature success), and disallow (or loudly warn/deny) `webhook_secret: nil` for any organization once more than one GitHub App organization is configured, since it globally disables authentication for that org's payloads.

### Proof of Concept
Given a Shipit deployment configured with two organizations, `TrustedOrg` (has `webhook_secret` set) and `OpenOrg` (`webhook_secret: nil`), and `TrustedOrg/prod-app` tracked as a Shipit stack:

```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything-or-omitted

{
  "sha": "deadbeef",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example/fake",
  "branches": [{"name": "main"}],
  "organization": {"login": "OpenOrg"},
  "repository": {"full_name": "TrustedOrg/prod-app", "owner": {"login": "OpenOrg"}}
}
```

`repository_owner` resolves to `OpenOrg`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of the signature header. `StatusHandler`/`Handler#repository_name` then resolves `repository.full_name` = `TrustedOrg/prod-app`, and the fabricated `success` status is written against the real, unrelated `TrustedOrg/prod-app` commit, potentially satisfying a `ci.require` gate for that stack's deploy/merge pipeline.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
