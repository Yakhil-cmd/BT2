### Title
`membership` webhook writes team membership keyed only by GitHub team ID, letting an org authenticated by its own webhook secret modify a team belonging to a different organization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
This engine supports multi-tenant GitHub configuration, where each organization known to `secrets.github` has its own `webhook_secret` used to authenticate its own webhooks [1](#0-0) . `WebhooksController#verify_signature` picks the secret to validate against solely based on the organization/owner named in the *payload itself* (`repository.owner.login` or `organization.login`) [2](#0-1) . For `membership` events, `MembershipHandler` then locates/writes the `Team` record purely by the numeric `github_id` taken from the payload, with no check that the team's `organization` matches the organization that was actually authenticated [3](#0-2) .

### Finding Description
`Shipit.github(organization:)` resolves a distinct webhook secret per organization key present in `secrets.github` [1](#0-0) . In `WebhooksController#verify_signature`, the organization used to select that secret (`repository_owner`) is read directly from the untrusted JSON body, not from any independently-verified source: `params.dig('repository','owner','login') || params.dig('organization','login')` [4](#0-3) . This is by design for legitimate multi-org GitHub Apps: whichever org's secret matches the payload's declared org is accepted.

`MembershipHandler#process` then does:
```ruby
team = find_or_create_team!
member = User.find_or_create_by_login!(params.member.login)
case params.action
when 'added' then team.add_member(member)
...
```
where
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [3](#0-2) 

The lookup key is `github_id` alone (a globally unique GitHub team ID that is discoverable via the GitHub API), and `team.organization` is only assigned inside the `find_or_create_by!` block, i.e. **only on first creation**. If a `Team` row for that `github_id` already exists (created earlier by a legitimate membership sync belonging to a *different* organization), the `organization` field is never re-validated or re-written — the code simply mutates the pre-existing `Team`'s membership.

This produces the exact "equality that should hold but doesn't" pattern from the reported bug class: the value trusted for the *write* (`team`, resolved by `github_id`) is not the same value that was *authenticated* (`organization`, resolved from `verify_signature`'s `repository_owner`). Concretely:
- Binding that should hold: `organization authenticated by HMAC == organization that owns the Team being mutated`.
- What the code actually enforces: `github_id in payload == Team#github_id in DB` (no cross-check against the authenticated organization at all).

An attacker who legitimately administers **their own** GitHub organization that is also configured as a Shipit tenant (with a webhook secret they know, e.g. because they self-served install the GitHub App on their org) can send a `membership` webhook, signed with their own org's secret, whose JSON body claims an arbitrary `organization.login` won't even need to be forged since `repository_owner` derivation only decides which secret to check against — but the attacker fully controls the raw JSON body being signed, including `team.id` (set to a *target* org's team's GitHub ID) and `member.login` (an account they control). Because `verify_signature` succeeds (the signature matches the body, computed with a secret the attacker legitimately possesses for their own tenant), and `MembershipHandler` never checks that the found/created `Team#organization` equals the authenticated organization, the attacker's user gets added as a member of the target's `Team` record.

### Impact Explanation
If the target `Team` is one of `Shipit.github_teams` (the globally configured set of teams whose members are authorized to use the instance, via `User#authorized?`) [5](#0-4) [6](#0-5) , this is a direct escalation into `Shipit.github_teams` authorization — an attacker-controlled `User` becomes a "member" of an authorization team without ever being a real GitHub member of that team/org, and can then log in and use Shipit as an authorized user, including triggering deploys/rollbacks on stacks gated by that authorization. This matches the report's "High" impact bucket explicitly ("escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
Exploitation requires the attacker to control at least one organization/tenant that is configured in this Shipit instance's `secrets.github` multi-org config (so they hold a valid webhook secret for *some* org) and to know or guess the target team's numeric GitHub `github_id` (obtainable via GitHub's public/team API for any team they can see, or via prior enumeration). No repository write access, ApiClient token, or privileged Shipit account is required — only the ability to send an HTTP request to the public `webhooks#create` endpoint with a self-signed payload. This is a plausible, unprivileged-attacker path given the engine's declared multi-tenant support.

### Recommendation
In `MembershipHandler#find_or_create_team!`, cross-check the team's stored `organization` against the organization that `WebhooksController#verify_signature` actually authenticated (e.g., pass the authenticated organization into the handler and refuse to create/update a `Team` whose `organization` doesn't match, or scope the `find_or_create_by!` lookup to `github_id` **and** `organization` instead of `github_id` alone). Additionally, consider re-validating/updating `team.organization` on every webhook, not only at creation, and rejecting membership changes where the payload's claimed organization differs from the record's persisted organization.

### Proof of Concept
1. Attacker legitimately owns GitHub organization `attacker-org`, which is configured as a tenant in this Shipit instance's `secrets.github`, giving the attacker a legitimate `webhook_secret` for `attacker-org` (known to them as the org's GitHub App/webhook administrator).
2. Attacker looks up (via GitHub's public API) the numeric `id` of a `Team` already tracked by this Shipit instance that is included in `Shipit.github_teams` (the authorization gate) — say `target-org/admins`, `github_id = 999`.
3. Attacker crafts a `membership` webhook JSON body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "admins", "slug": "admins", "url": "https://api.github.com/teams/999"},
  "organization": {"login": "attacker-org"},
  "member": {"login": "attacker-controlled-user"}
}
```
4. Attacker computes `sha1=HMAC(attacker-org secret, body)` and POSTs it to `/github/webhooks` with `X-Github-Event: membership` and the computed `X-Hub-Signature`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"` (from the payload's `organization.login`) and successfully verifies the signature against `attacker-org`'s secret [7](#0-6) .
6. `MembershipHandler#process` runs `Team.find_or_create_by!(github_id: 999)`, finds the pre-existing `target-org/admins` `Team` row, and calls `team.add_member(attacker-controlled-user)` [3](#0-2) [8](#0-7) .
7. `attacker-controlled-user` is now a member of `target-org/admins` in Shipit's database and, if that team is part of `Shipit.github_teams`, passes `User#authorized?`, gaining authorized access to the instance.

**Uncertainty**: This analysis assumes the deployment actually uses the multi-organization `secrets.github` configuration form (keyed by organization) documented in `lib/shipit.rb#github_app_config`; if an operator only configures the single/legacy top-level `github:` schema, there is only one webhook secret for the whole instance and the "different authenticated org" framing doesn't apply the same way, though the underlying `github_id`-only lookup with organization only set on creation remains a latent inconsistency regardless. Confirming exactly how many organizations a given operator configures, and whether org self-service onboarding is exposed to arbitrary external parties, would require further investigation beyond what's available in this index.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end
