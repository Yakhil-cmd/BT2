### Title
Cross-tenant Status forgery via unscoped SHA lookup in `StatusHandler#process` corrupts `Commit#deployable?` for arbitrary stacks - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits to update purely by `sha`, with no check that the webhook's originating repository matches the `stack`/`repository` that owns that `Commit` row. An attacker who owns any GitHub repository wired into Shipit (their own fork, with a legitimately verifiable `webhook_secret`) can post a `status` webhook for a commit whose SHA collides with a commit in a victim's stack (trivial via forking a public repo, since git SHAs are content-addressed), and that forged status is written onto the victim's `Commit` row. This corrupts `Commit#deployable?`, which `Shipit::Api::DeploysController#create` trusts when `require_ci: true` is passed.

### Finding Description
Binding claimed broken, stated as an equality: `commit.deployable?` (for stack S, commit C) should equal `f(statuses written by webhooks whose signature was verified against S's own repository's webhook_secret)`. In the actual code, `commit.deployable?` equals `f(statuses written by webhooks for ANY commit with the same sha, regardless of which repository's webhook_secret verified them)`.

Trace:
- `Shipit::WebhooksController#verify_signature` verifies the incoming request's signature against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the payload's `repository.owner.login` [1](#0-0) [2](#0-1) . This check only proves the request came from *some* org/repo the attacker legitimately controls (their own installation's secret) — it says nothing about which `Commit` rows the handler is allowed to touch.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — matching purely by `sha` across the whole `commits` table, with no repository/stack scoping [3](#0-2) . Contrast this with `PushHandler#process`, which correctly scopes via `stacks` (derived from `Repository.from_github_repo_name(repository_name)`) before acting [4](#0-3) [5](#0-4) .
- `Commit#create_status_from_github!` unconditionally writes the status via `add_status` with no repository ownership check [6](#0-5) .
- `Commit#deployable?` then reads the corrupted status: `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [7](#0-6) .
- `Shipit::Api::DeploysController#create` trusts this: `param_error!(:require_ci, "Commit is not deployable") if params.require_ci && !commit.deployable?` [8](#0-7) .

Attack: Attacker forks the victim's public repository (or otherwise obtains a commit with an identical SHA to one reachable in the victim's stack — trivial since git SHAs are content-addressed over the identical commit history) and registers/owns a Shipit-connected repo for that fork with a valid webhook installation. Attacker (via their own GitHub token, no victim secrets needed) posts a `status` API call on their own repo for that SHA with `state: success`. GitHub delivers the webhook to Shipit's `/webhooks` endpoint, signed with the attacker's own org's `webhook_secret`; `verify_signature` passes because it checks against the attacker's own org. `StatusHandler#process` then finds and updates every `Commit` row across all stacks sharing that `sha`, including the victim's, marking it `success` in the victim's stack too. Later, a legitimate victim-side operator calling `POST /stacks/:id/deploys` with `require_ci: true` sees `commit.deployable?` return `true` even though CI never ran against the victim's own repository/webhook.

No existing guard stops this: `verify_signature` only authenticates the sender's own organization, not the target of the mutation; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape (`sha`, `state`, etc.), not repository scope; there is no `Repository`/`Stack` ownership check anywhere in `StatusHandler`.

### Impact Explanation
This is a payload from one repository mutating another's `Commit` state (Critical category: "a payload for one repository mutating another's stack, commit, task or team"). It defeats the `require_ci` safety check that a legitimate deploy-permission operator relies on, letting a commit that never passed CI in the victim's own repository be treated as deployable, potentially leading to an unauthorized/unsafe deploy. The attack is fully repeatable against any victim repository whose commit history (or a shared/forked prefix of it) the attacker can replicate, and works for every commit SHA the attacker can reproduce this way — it is not a one-off bypass but a systemic scoping bug in `StatusHandler`.

### Likelihood Explanation
Preconditions: attacker needs (a) a GitHub repository they own/control with a Shipit-connected stack (normal onboarding, no privileged secrets required), and (b) a commit whose SHA also exists in the victim's stack's commit history — achievable for any public/forkable repository by forking it, or by any commit shared across repos. Cost is low: one `status` API call via the attacker's own GitHub token/webhook. It does not require the victim's `webhook_secret`, session, or any Shipit privilege. The final step (an operator submitting `require_ci: true`) is a normal, expected legitimate action the question explicitly isolates as out of scope for the attacker to perform themselves — the vulnerability is that the *data* feeding that decision is corruptible cross-tenant.

### Recommendation
Scope `StatusHandler#process` (and any other handler that mutates `Commit`/`Status` records by SHA) to only the commits belonging to stacks of the repository identified in the verified webhook payload, mirroring the `stacks` helper already used by `PushHandler`/`CheckSuiteHandler`. E.g., change `Commit.where(sha: params.sha)` to `stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }` or equivalent, ensuring a status webhook can only ever update `Commit` rows tied to the repository/stack that the verified `webhook_secret` belongs to.

### Proof of Concept
Minitest plan (extends existing `test/controllers/webhooks_controller_test.rb` and `test/controllers/api/deploys_controller_test.rb` patterns):

```ruby
test "StatusHandler must not update commits belonging to a different repository sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)                     # victim's stack/repo
  attacker_stack = shipit_stacks(:some_other_repo_fixture)  # attacker-owned repo/stack

  # Create two Commit rows with the SAME sha but different stack_id, simulating a forked commit history
  shared_sha = 'deadbeef' * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'x', authored_at: Time.now,
                                                committed_at: Time.now, author: shipit_users(:shipit),
                                                committer: shipit_users(:shipit))
  attacker_stack.commits.create!(sha: shared_sha, message: 'x', authored_at: Time.now,
                                  committed_at: Time.now, author: shipit_users(:shipit),
                                  committer: shipit_users(:shipit))

  refute_predicate victim_commit.reload, :deployable?   # BEFORE: no statuses, not deployable

  # Attacker posts a status webhook for THEIR OWN repository, signed with THEIR OWN webhook_secret
  GithubApp.any_instance.stubs(:verify_webhook_signature).returns(true)
  request.headers['X-Github-Event'] = 'status'
  payload = {
    'sha' => shared_sha, 'state' => 'success', 'context' => 'ci/attacker',
    'repository' => { 'full_name' => attacker_stack.repository.full_name,
                       'owner' => { 'login' => attacker_stack.repository.owner } }
  }.to_json
  post :create, body: payload, as: :json

  # AFTER: assert the equality is broken - victim_commit.deployable? flipped due to attacker's own-repo webhook
  assert_predicate victim_commit.reload, :deployable?   # demonstrates cross-tenant corruption

  # Downstream: DeploysController#create with require_ci: true now silently accepts
  session[:user_id] = shipit_users(:walrus).id
  post :create, params: { stack_id: victim_stack.to_param, sha: shared_sha, require_ci: true }
  assert_response :accepted   # should have been :unprocessable_entity ("Commit is not deployable")
end
```

Both sides of the equality (`commit.deployable?` before vs. after the attacker's own-repo webhook, and the deploy controller's response before vs. after) diverge, confirming the AUTHORIZATION TRUTH binding is broken by `StatusHandler#process`'s unscoped `Commit.where(sha:)` lookup.
