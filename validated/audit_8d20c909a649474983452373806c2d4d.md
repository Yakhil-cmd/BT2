## Analysis

**Binding claimed (before tracing):** `repository_full_name in payload == repository of every stack/commit touched by the handler`.

This binding is upheld by every other handler through the shared `stacks` helper: [1](#0-0)  which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before scoping any query. `PushHandler#process` consumes this scoping directly (`stacks.not_archived.where(branch:)`), so it can only ever touch stacks whose `Repository.full_name` matches the payload: [2](#0-1)  Likewise `CheckSuiteHandler#process` scopes through `stacks` before touching commits: [3](#0-2) 

`StatusHandler#process`, however, never calls `stacks`, never touches `repository_name`, and performs a table-wide lookup keyed only on `sha`: [4](#0-3)  `Commit.where(sha: params.sha)` returns every `Commit` row across every stack/repository in the installation that happens to share that 40-hex sha, and calls `commit.create_status_from_github!(params)` on each one, which cascades into `Status.create!`, `enable_ci_on_stack`, and `schedule_continuous_delivery`: [5](#0-4) 

**Binding after tracing:** false — the two sides are not equal for `StatusHandler`. It is the only default handler in `Shipit::Webhooks.default_handlers` that omits any `repository`/`stacks` scoping: [6](#0-5) 

Checking the outer guard (`verify_signature`) does not close this gap: it only authenticates that the payload's *organization* (`repository.owner.login`) matches a configured `webhook_secret` for that org — [7](#0-6)  it says nothing about which `Commit`/`Stack` rows the handler is permitted to mutate. A commit sha is a pure function of tree/parents/author/committer/timestamp/message and is not repository-bound in git; an attacker who owns any repository already onboarded into the Shipit installation can reproduce an identical commit object (e.g. by fetching and re-pushing the victim's public commit, or via a shared fork) into their own repo, then use GitHub's real Status API to set a status on that sha. GitHub delivers a genuinely, correctly signed `status` webhook for the attacker's own org — passing `verify_signature` legitimately, no secret needed. `StatusHandler#process` then matches and mutates the victim's `Commit` row in a completely different `Stack`/`Repository`, regardless of the payload's own `repository` field.

### Title
Cross-repository Status injection via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits globally by `sha` with no repository/stack scoping, unlike every other default handler (`PushHandler`, `CheckSuiteHandler`, PR handlers) which route through `Handler#stacks`/`Repository.from_github_repo_name(payload.repository.full_name)`. Because a git commit sha is not bound to a single repository, an attacker who legitimately controls any onboarded repo can get a validly-signed `status` webhook delivered for a sha that also exists in a victim's differently-owned stack, causing Shipit to write a `Status` record against the victim's commit/stack.

### Finding Description
Broken binding: `repository_full_name in payload == repository of every record touched` (upheld by `PushHandler`/`Handler#stacks`) vs. `StatusHandler`'s actual scoping, which is `none`.

Path: `WebhooksController#create` parses the raw JSON body, verifies the signature against the org named in `payload['repository']['owner']['login']` [8](#0-7) , then dispatches to `Shipit::Webhooks.for_event('status') => [Handlers::StatusHandler]` [6](#0-5) . `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) , with no reference to `payload['repository']` or the base `Handler#stacks`/`repository_name` helpers [9](#0-8) . `create_status_from_github!` then creates a `Status`, which enables CI and schedules continuous delivery on the (foreign) stack [5](#0-4) .

Attacker request: as the owner/collaborator of any repository already tracked by the target Shipit installation, push (or otherwise reproduce) a commit object with an identical sha to one that exists in a victim's stack (trivial since git object identity is content-based, not repo-based — e.g. fetch the victim's public commit and push it as-is into the attacker's own repo/fork), then use GitHub's real Statuses API to set a status on that sha in the attacker's repo. GitHub delivers a genuinely-signed `status` webhook using the attacker's own org's real `webhook_secret`; `verify_signature` passes legitimately. `StatusHandler#process` then matches the victim's `Commit` row purely by `sha` and writes an attacker-controlled `Status` (state/description/context/target_url) against it.

Existing guards fail to prevent this because they operate at the wrong layer: `verify_signature` authenticates "this request came from the org named in the payload," not "this handler may only touch resources of the org named in the payload" — that second check is a per-handler responsibility that every handler except `StatusHandler` implements via `Handler#stacks`.

### Impact Explanation
The attacker can inject an arbitrary commit status (e.g., `state: success`) onto a commit belonging to a stack/repository they never authenticated against. If that victim stack has `continuous_deployment` enabled, a transition to `success`/`pending` schedules `ProcessMergeRequestsJob`/continuous delivery for the victim's stack — i.e., a payload authenticated for repository A causes state changes and potentially deploy-triggering side effects on repository B's stack. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." It is repeatable against any repository/stack whose tracked commit shas the attacker can reproduce or already knows (feasible for any public repo, or any repo sharing history/forks with the attacker's own repo).

### Likelihood Explanation
Preconditions: the attacker must control (or be a collaborator on) at least one repository already onboarded into the target Shipit installation, and must know/reproduce a sha that is also tracked by a victim stack in a different repository — both are attacker-achievable with no Shipit credentials, sessions, or secrets, since git shas are content-derived and commit objects are freely portable across repos, and GitHub itself will happily sign and deliver the resulting `status` webhook with the attacker's own legitimate org secret. No `webhook_secret`, session, or API token for the victim's org is ever needed. This is a real, cheap, repeatable attack path for any multi-tenant Shipit deployment (the engine's normal operating mode).

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: resolve `stacks` from `payload['repository']['full_name']` via the base `Handler#stacks`, and restrict the `Commit.where(sha: params.sha)` lookup to `stacks.flat_map(&:commits)` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) so a status webhook can only mutate commits belonging to the repository named in its own payload.

### Proof of Concept
Minitest plan (model-level, no live GitHub):
1. Create two `Stack`/`Repository` fixtures in different orgs (`owner_a/repo_a`, `owner_b/repo_b`), each with a `Commit` sharing the same `sha` value (e.g. `"deadbeef"*5`).
2. Build a `push` payload for `owner_a/repo_a` (`repository.full_name = "owner_a/repo_a"`, matching branch/after sha) and assert, after `PushHandler.new(payload).process`, that only `repo_a`'s stack's commits/sync state changed — `repo_b`'s stack is untouched (`assert_no_changes -> { repo_b_stack.reload.updated_at }`).
3. Build a `status` payload with `repository.full_name = "owner_a/repo_a"` but `sha` equal to the shared sha, and assert, after `StatusHandler.new(payload).process`, that **both** `Commit` rows (in `repo_a` and `repo_b`) gained a new `Status` (`assert_difference '[email protected] + [email protected]', 2`), proving the divergence: `PushHandler` mutates only the matching stack while `StatusHandler` mutates both regardless of payload's declared repository.
