### Title
Shared, already-expiring context reused for post-sync cleanup causes repeated cleanup failure and unbounded `.git` growth on attacker-controlled expensive repository content - (File: main.go)

### Summary
The main sync loop creates a single `context.WithTimeout(context.Background(), *flSyncTimeout)` and passes it both to `git.SyncRepo(ctx, ...)` and, immediately afterward, to `git.cleanup(ctx)` [1](#0-0) . This is directly analogous to the LayerZero report's root cause: an expensive, attacker-influenced operation consumes almost the entire allotted "budget" (there gas, here wall-clock time), leaving the subsequent bookkeeping/recovery step (there `_storeFailedMessage`, here `git.cleanup`) with an already-exhausted context, causing it to fail every cycle.

### Finding Description
`configureWorktree` performs `git reset --hard <hash>` and, if submodules are enabled, `git submodule update --init [--recursive]` against `ctx` [2](#0-1) . An untrusted upstream repository (the git-sync "repo" input, which is attacker-influenced content per the analog scope) can be crafted to make this checkout/submodule step arbitrarily expensive — e.g. very large blobs, deep/recursive submodules, or huge trees — consuming most of `*flSyncTimeout` before `SyncRepo` returns success.

Immediately after a successful (or even barely-successful) sync, the loop calls `git.cleanup(ctx)` using the *same* `ctx` object, which by then may have little or no time left before its deadline [3](#0-2) . Inside `cleanup`, the actual stale-worktree directory removal (`removeStaleWorktrees`) does not use `ctx` and will still run [4](#0-3) , but the git-level bookkeeping commands — `worktree prune`, `reflog expire --expire-unreachable=all`, and `gc`/`gc --auto`/`gc --aggressive` — all run `git.Run(ctx, ...)` with the near-expired context and will fail with `context.DeadlineExceeded` [5](#0-4) . `Runner.Run` explicitly detects and surfaces `ctx.Err() == context.DeadlineExceeded` as an error [6](#0-5) .

The loop only logs these cleanup failures (`log.Error(err, "git cleanup failed")`) and continues, so this is not immediately fatal to the process the way the LZ blocking channel is [7](#0-6) . But because a malicious/expensive upstream repository can reliably reproduce this every sync cycle, `git worktree prune` never removes the stale `.git/worktrees/<hash>` administrative entries and `git gc`/`reflog expire` never run, so loose objects and packs from every fetch keep accumulating in `.git` without bound.

### Impact Explanation
Repeated, deterministic failure of `worktree prune`/`reflog expire`/`gc` on every sync cycle leads to unbounded growth of the on-disk `.git` object store (no garbage collection ever completes), which is a form of "sustained crash or unbounded resource usage" against the git-sync host filesystem. Given enough cycles this can exhaust the volume backing `--root` (a shared `emptyDir`/PV in the sidecar model), which in turn breaks `git fetch`/`worktree add` for legitimate updates — i.e. persistent sync denial for the consuming application. This is a lower-severity analog than the LZ finding (no permanent protocol-level channel block, only degraded/failing housekeeping that requires repeated exploitation to manifest as denial), but it shares the same root cause pattern: an attacker-influenced expensive operation starves a shared time/resource budget needed by the subsequent cleanup/error-handling step.

### Likelihood Explanation
Requires: (1) git-sync configured with `--sync-timeout` sized close to what a normal sync takes for the legitimate repo, and (2) the upstream repository (or a ref/commit within it) being attacker-influenced enough to make checkout/submodule-update expensive (e.g., a git-sync deployment pulling PR branches, forked repos, or repos with attacker-writable submodule references). This is a realistic but not universal deployment pattern, so likelihood is Medium at best and depends heavily on operator-chosen timeout/submodule configuration, which somewhat weakens the analog compared to the original always-reachable LZ gas-forwarding bug.

### Recommendation
Use an independent, freshly-scoped context (with its own timeout) for `git.cleanup(ctx)` rather than reusing the `ctx` from the just-completed `SyncRepo` call, so that cleanup/GC always gets its own full time budget regardless of how much of the sync timeout the checkout step consumed. Optionally also emit a distinct metric/counter for repeated cleanup failures so operators can detect the condition before disk exhaustion occurs.

### Proof of Concept
Not independently reproducible from static analysis alone (requires controlling upstream repo size/submodule structure and tuning `--sync-timeout`); the code path is confirmed by:
1. `context.WithTimeout` created once per loop iteration and passed to both `SyncRepo` and `cleanup` [8](#0-7) .
2. `configureWorktree`'s `git reset --hard` / `git submodule update --init --recursive` consuming that context's budget on attacker-controlled repo content [2](#0-1) .
3. `cleanup`'s git commands (`worktree prune`, `reflog expire`, `gc`) using the same, now-expiring `ctx`, and `Runner.Run` converting an expired context into a returned error [5](#0-4) [6](#0-5) .

func (git *repoSync) removeStaleWorktrees() (int, error) {
	currentWorktree, err := git.currentWorktree()
	if err != nil {
		return 0, err
	}

	git.log.V(3).Info("cleaning up stale worktrees", "currentHash", currentWorktree.Hash())

	count := 0
	err = removeDirContentsIf(git.worktreeFor("").Path(), git.log, func(fi os.FileInfo) (bool, error) {
		// delete files that are over the stale time out, and make sure to never delete the current worktree
		if fi.Name() != currentWorktree.Hash() && time.Since(fi.ModTime()) > git.staleTimeout {
			count++
			return true, nil
		}
		return false, nil
	})
	if err != nil {
		return 0, err
	}
	return count, nil
}
