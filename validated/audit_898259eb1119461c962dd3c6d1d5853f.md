### Title
Membership webhook accepted without signature coverage when a configured GitHub org has no `webhook_secret`, allowing unauthenticated escalation into `Shipit.github_teams` authorization — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects a per-organization `GithubApp` config using an unauthenticated, self-declared field in the POST body (`repository.owner.login` / `organization.login`), then checks the HMAC signature against that org's `webhook_secret`. If that org's `webhook_secret` is unset (which the docs list as "optional"), `GithubApp#verify_webhook_signature` short-circuits and returns `true` for *any* body, with no signature coverage at all.

### Finding Description
`verify_signature` picks the app/secret to check against from the payload itself, before any cryptographic check is done: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` is the code that is supposed to bind the payload to a verified signature, but when no `webhook_secret` is configured for that organization it returns `true` unconditionally — i.e. nothing in the payload is "covered" by a verified signature in that case: [3](#0-2) 

This is a documented, supported configuration (`webhook_secret` is explicitly marked optional in setup docs and example secrets files): [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (trivially, because `webhook_secret` is blank for the attacker-chosen org), the raw JSON body is dispatched to registered handlers with zero further validation of provenance: [6](#0-5) 

The `membership` event handler trusts the body completely to create/find a `Team` and add or remove a `User` from it: [7](#0-6) 

`User#authorized?` — the gate used by `Shipit::Authentication#force_github_authentication` to allow access to the whole Shipit UI — is based purely on whether the local `User` row has a `Membership` in one of `Shipit.github_teams`: [8](#0-7) [9](#0-8) 

**The broken binding:** the org whose `webhook_secret` gates the payload's authenticity (`repository_owner`/`organization.login`, verified — or not — against that org's `GithubApp`) is not the same thing that is actually acted on by the handler (an arbitrary `team.id`/`member.login` pair, fully attacker-controlled when that org has no secret configured). When `webhook_secret` is blank for any one configured organization in `Shipit.github.*`, every `membership` (and `push`, `status`, `check_suite`, `pull_request`) event claiming that organization is accepted with no signature coverage whatsoever.

### Impact Explanation
An unauthenticated attacker who knows (or guesses) that a Shipit deployment has an organization configured without a `webhook_secret` can POST a forged `membership` event directly to `/webhooks` (no session, no `ApiClient` token, no GitHub App key, no secret knowledge required) with:
- `action: 'added'`
- `team: { id: <id of a team in Shipit.github_teams>, name, slug, url }`
- `organization: { login: '<org-without-secret>' }`
- `member: { login: '<attacker-controlled-github-login>' }`

This creates/updates a local `Membership` row granting the attacker's GitHub login access to a `Shipit.github_teams`-tracked team, satisfying `User#authorized?` and thus bypassing the entire authentication gate for the Shipit web UI (dashboards, deploy/rollback/task triggering, stack management) — an escalation directly into `Shipit.github_teams` authorization, matching the engine's own High-severity impact category.

### Likelihood Explanation
Requires only that one configured GitHub organization in a multi-org (or single-org) Shipit deployment has `webhook_secret` left blank — a state the project's own docs and example secrets templates present as a normal, optional choice, not a misconfiguration warning. No credentials, sessions, or tokens are needed to exploit it; the attacker only needs to know a valid `Shipit.github_teams` team id (discoverable via legitimate GitHub org membership APIs or via observing prior legitimate `membership` webhook payload shapes) and network access to the `/webhooks` endpoint.

### Recommendation
- Require `webhook_secret` to be present for every configured organization at boot/initialization, refusing to start (or refusing to process events for that org) if it is blank, instead of treating an absent secret as automatic verification success.
- Alternatively, make `verify_webhook_signature` fail closed (return `false`) when `webhook_secret` is blank, and update docs/examples to remove "optional" framing.
- Add defense-in-depth in `MembershipHandler` (and other org-authoritative handlers) by cross-checking `params.organization.login` against `Team#organization` and reconciling any conflicting values instead of trusting the incoming body outright.

### Proof of Concept
1. Deploy Shipit with two organizations configured under `Shipit.github`, where org `unsecured-org` has `webhook_secret: nil` (as allowed by `docs/setup.md` and `config/secrets.development.example.yml`), while another org has a properly configured secret.
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": {"id": 48, "name": "Ouiche Cooks", "slug": "ouiche-cooks", "url": "https://example.com"},
  "organization": {"login": "unsecured-org"},
  "member": {"login": "attacker-handle"}
}
```
No `X-Hub-Signature` header is required — `verify_signature` calls `Shipit.github(organization: 'unsecured-org')`, and `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank for that org (`lib/shipit/github_app.rb:76-77`).
3. `Shipit::Webhooks::Handlers::MembershipHandler#process` creates/reuses the `Team` with `github_id: 48` and adds a local `User` for `attacker-handle` as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`).
4. If team `48` is one of the ids in `Shipit.github_teams`, and the attacker subsequently completes GitHub OAuth login as `attacker-handle` (a normal, real GitHub account they control — no privileged access required), `User#authorized?` now returns `true` (`app/models/shipit/user.rb:80-82`), granting them full access to the Shipit UI for that instance.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
