### Title
Cross-repository `Status` forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` bypasses `Stack#blocking_statuses` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits to attach a GitHub status to purely by `sha`, with no scoping to the repository that sent the webhook. Because git commit SHAs are content-addressed and identical across forks/mirrors, an attacker who controls a repository (Repo B) sharing a commit SHA with a commit tracked by an unrelated Stack A (Repo A) can emit a legitimately-signed "status" webhook from Repo B and have Shipit write a `Status` record onto Stack A's commit, flipping `Commit#blocked?`/`Commit#deployable?` for a commit the attacker never had CI access to on Repo A.

### Finding Description
The broken binding is:
`repository whose blocking_statuses configuration applies (Stack A / Repository A)` == `repository that authenticated the status update (Repository B, owned by the attacker)`

This should always hold but does not, because:

- `StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This query is global across the entire `commits` table and is **not** filtered by the repository named in the webhook payload. Contrast this with the base `Handler` class, which provides a `stacks` helper explicitly scoped to the payload's repository via `Repository.from_github_repo_name(repository_name)`, and which other handlers (e.g. `PushHandler`, `CheckSuiteHandler`) correctly use:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [2](#0-1) 
`CheckSuiteHandler` correctly scopes to `stacks` before touching commits: [3](#0-2) 

`StatusHandler` alone ignores this scoping and matches commits by SHA only.

- `WebhooksController#verify_signature` only proves that the payload genuinely originated from the organization named in `payload['repository']['owner']['login']` (Repo B's org) — it says nothing about whether that repository's SHA belongs to that same repository's history:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
``` [4](#0-3) 
So the signature guard validates authenticity of the *sender*, not the sha-to-repository binding — it cannot prevent this exploit.

- Downstream, the write directly affects `Commit#blocked?`/`Commit#deployable?`:
```ruby
def blocked?
  return false if stack.blocking_statuses.empty?
  stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)
end

def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [5](#0-4) 
`blocking?` is driven by the commit's `status`, which is rebuilt from `statuses` (and `check_runs`) after `add_status` runs inside `create_status_from_github!`: [6](#0-5) 

**Exploit flow:**
1. Attacker forks/clones public Repository A (whose Stack A has `blocking_statuses` configured for e.g. `ci/travis`) into their own Repository B, preserving the exact commit SHA of a not-yet-CI-passed commit in Repo A (git SHAs are content-derived, so a faithful copy/fork reproduces identical SHAs).
2. Attacker's Repo B, which they fully control, emits a genuine GitHub "status" webhook (or attacker just calls the GitHub Statuses API on their own repo) for that SHA with `context: "ci/travis"`, `state: "success"`. This webhook is signed by GitHub for Repo B's org and passes `verify_signature` normally with no Shipit secret needed.
3. `StatusHandler#process` receives this payload and runs `Commit.where(sha: params.sha)`, which matches the Stack A commit (same sha, different repo) regardless of the fact the payload's `repository.full_name` is Repo B.
4. A `Status` row with state `success` and context `ci/travis` gets attached to the Stack A commit, changing `Commit#blocking?` to false, `Commit#blocked?` to false, and `Commit#deployable?` to true.
5. This can trigger continuous delivery (`schedule_continuous_delivery`) or allow a maintainer/automation on Stack A to deploy a commit that never actually passed CI on Repository A.

### Impact Explanation
This is a payload for one repository mutating another repository's commit/stack state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It results in an unauthorized bypass of a required/blocking CI check gating Stack A's continuous delivery, potentially leading to deployment of unverified code. The attack is repeatable against any commit SHA the attacker can reproduce in a repository they control (any public/forkable repo tracked by Shipit), and is not limited to a single stack — any stack tracking a commit whose SHA the attacker can reproduce is affected.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository under an organization known to Shipit (`Shipit.github(organization: ...)` must not raise `GithubOrganizationUnknown`) that they can emit webhooks/statuses from — this can be their own fork if forks share the parent org's app installation, or any org where Shipit's GitHub App is installed and the attacker can create a repo; and (b) a commit SHA that matches one already tracked in the target stack, which is trivially satisfiable by forking/mirroring the target repository (SHAs are content-addressed and identical across forks). No Shipit secrets, sessions, or API tokens are required. This is low-cost and repeatable — each forged status webhook, once accepted, immediately biases `blocked?`/`deployable?` for that commit.

### Recommendation
Scope `StatusHandler#process` to the repository named in the webhook payload the same way other handlers do, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`), ensuring a `Status` can only be attached to commits belonging to stacks whose repository matches the one that authenticated the webhook.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or similar):
```ruby
test "status webhook from repository B cannot flip blocked?/deployable? on a stack of repository A" do
  stack_a = shipit_stacks(:shipit) # tracks repository A
  stack_a.update!(deploy_spec_override_for_test_with_blocking_statuses: ['ci/travis']) # configure blocking_statuses = ["ci/travis"]

  commit = stack_a.commits.create!(sha: 'deadbeefcafedeadbeefcafedeadbeefcafe123')
  assert_equal true, commit.blocked? # LHS/RHS mismatch setup: no successful status yet -> blocked

  # Payload claims to originate from an unrelated Repository B, but reuses Repo A's commit sha
  payload = {
    'sha' => commit.sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'repository' => { 'full_name' => 'attacker/repo-b', 'owner' => { 'login' => 'attacker-org' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  commit.reload
  # Binding under test: repository authorizing the status (repo-b) != repository owning blocking_statuses (repo A's stack)
  assert_equal false, commit.blocked?, "status from an unrelated repository should not satisfy Stack A's blocking_statuses"
end
```
Before the fix, `Commit.where(sha: params.sha)` matches `commit` regardless of `payload['repository']`, the status is written, and `commit.blocked?` incorrectly becomes `false` — proving the cross-repository write. After applying the scoped fix (`stacks.each { |stack| stack.commits.where(sha: ...) }`), the payload for `attacker/repo-b` resolves to no stacks/commits (since Repo B isn't registered as Repository A), the status is never written, and `commit.blocked?` remains `true`.
