## Title
Webhook signature verification key is selected by `repository.owner.login`/`organization.login` while event handlers act on the unverified `repository.full_name` — allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (or `organization.login`), but every event handler that actually performs a write (e.g. `PushHandler`, PR handlers) resolves the target `Stack`/`Repository` using a *different* payload field: `payload.dig('repository', 'full_name')`. Because Shipit supports multiple independent GitHub Apps/organizations each with its own `webhook_secret` (as documented in `docs/setup.md:182-209` and implemented by `Shipit.github(organization:)` in `lib/shipit.rb:170-181`), a webhook signed with organization A's secret is only checked against fields that name organization A, but the handler that runs afterwards trusts `repository.full_name`, which can point at a completely different organization/repository (e.g. org B) also configured in the same Shipit instance.

### Finding Description
The verification and the action operate on different equalities:
- Verified binding: `HMAC(secret_for(repository.owner.login or organization.login)) == X-Hub-Signature` [1](#0-0) 
- Acted-upon binding: `Stack/Repository selected by repository.full_name` [2](#0-1) 

Nothing ties `repository.full_name` to `repository.owner.login`/`organization.login` — they are simply two independent fields inside the same untrusted, attacker-supplied JSON body. Any party who has push access to a repository owned by one org that has a Shipit-registered GitHub App (org A) can compute a valid signature for org A's `webhook_secret` over an arbitrary payload, then send that payload to `/webhooks` with `repository.owner.login` (or `organization.login`) set to `"org-a"` (so verification picks and passes org A's secret) while setting `repository.full_name` to `"org-b/victim-repo"` (a stack managed under a different, unrelated organization/app in the same Shipit deployment). `PushHandler#process` (or PR handlers) will then look up and act on `org-b/victim-repo`'s stacks using only `repository.full_name`, `ref`, and `after` from the forged payload. [3](#0-2) 

This breaks the intended equality "organization that authenticated the webhook == repository whose stacks are written," exactly the class of binding failure called out in the task rules (an organization that authenticated versus the repository that is written).

### Impact Explanation
A forged `push` webhook causes `stack.sync_github(expected_head_sha:)` to enqueue `GithubSyncJob` for a victim stack the attacker does not control, using an attacker-chosen `expected_head_sha`/`ref`. `GithubSyncJob` then fetches commits from GitHub for that stack via the Shipit-configured GitHub App/API credentials and appends them as new commits [4](#0-3) . If the target stack has continuous deployment enabled, or is manually deployed shortly after, an unauthorized/unexpected deploy of attacker-influenced ref/commit state can be triggered against a repository the attacker never had legitimate write access to — an unauthorized deploy across organizational trust boundaries, matching the "cross-repository writes / unauthorized deploy" High/Critical impact bar.

### Likelihood Explanation
Exploitability requires the attacker to control (or have push/webhook access to) at least one GitHub organization/repository already onboarded to the same shared Shipit instance with its own configured `webhook_secret` — a realistic scenario for the documented "Using Multiple GitHub Applications" multi-tenant setup. No Shipit session, API token, or `webhook_secret` for the *victim* org is required; only the attacker's *own* org's `webhook_secret`, which they inherently possess or can obtain since GitHub delivers it to org admins/webhook configuration.

### Recommendation
Verify the webhook signature using the organization actually referenced by the field the handlers use to select the target (`repository.full_name`'s owner segment), not a separately-dug `organization.login` fallback, and additionally assert that `repository.owner.login` (used for signature-key selection) matches the owner segment of `repository.full_name` (used for target resolution) before dispatching to handlers.

### Proof of Concept
1. Shipit is configured with two orgs, `org-a` and `org-b`, each with distinct `webhook_secret`s (per `docs/setup.md:182-209`), and both have stacks registered.
2. Attacker has legitimate push/webhook access to `org-a` and thus knows `org-a`'s `webhook_secret`.
3. Attacker crafts a `push` event payload:
```json
{
  "ref": "refs/heads/production",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-secret, body)` and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature against `org-a`'s secret [5](#0-4) .
6. `PushHandler` resolves stacks via `Repository.from_github_repo_name("org-b/victim-repo")` [2](#0-1)  and enqueues `GithubSyncJob` for `org-b`'s stack with attacker-controlled `expected_head_sha`.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

    def append_commit(gh_commit)
      stack.commits.create_from_github!(gh_commit)
    end
