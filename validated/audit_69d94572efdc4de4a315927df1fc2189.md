### Title
Webhook org-authentication is not bound to the acted-upon repository, allowing cross-repository status forgery and unauthorized merges (`Forkchoice-alike` binding break) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook delivery against the GitHub App belonging to the organization named in the payload (`repository.owner.login` / `organization.login`), but none of the event handlers verify that this same organization actually owns the repository/commit the handler subsequently acts on. `StatusHandler` in particular performs no repository scoping at all. This breaks the equality that should hold: `verified_organization == repository_owner_of_object_written`.

### Finding Description
`verify_signature` selects which `GitHubApp`/secret to check the `X-Hub-Signature` against purely from attacker-supplied JSON fields: [1](#0-0) [2](#0-1) 

That verification only proves "this payload was signed by the secret configured for organization X" (`repository_owner`); it does **not** prove that the payload's `repository.full_name` (used by most handlers) belongs to organization X, nor does it constrain what the handler operates on. The base `Handler#stacks` looks up the target purely from `repository.full_name`, a second, independent field from the same attacker-controlled JSON body: [3](#0-2) 

Worse, `StatusHandler` doesn't even use the `repository` field — it matches by commit SHA across the *entire* database, with zero organization/repository scoping: [4](#0-3) 

This is compounded by `GitHubApp#verify_webhook_signature`, which treats an *unconfigured* `webhook_secret` for the authenticating organization as an automatic pass: [5](#0-4) 

`webhook_secret` is explicitly documented as optional (`config/secrets.development.shopify.yml` ships `webhook_secret: # nil` for each org): [6](#0-5) [7](#0-6) 

So in any Shipit instance hosting more than one GitHub org where at least one org has no `webhook_secret` set (a documented, supported configuration), an attacker can send arbitrary unsigned/self-signed JSON claiming `repository.owner.login` = that unsecured org, while setting `sha`/`context`/`state` to target a commit that actually belongs to a completely different, secured organization's repository. Because `verify_webhook_signature` returns `true` for the unsecured org and `StatusHandler` never checks which repository the commit belongs to, the forged status is written straight into `Commit#create_status_from_github!` for the victim repository.

This downstream status is then consumed by the merge queue without any live re-check against GitHub: [8](#0-7) [9](#0-8) 

`reject_unless_mergeable!` only checks `merge_conflict?` (live GitHub `mergeable` flag) and `stale?`; CI success/failure is evaluated purely from locally-stored `Status`/`CheckRun` records that the forged webhook can inject. `merge!` then calls the GitHub API to actually merge the pull request: [10](#0-9) 

The same missing binding also applies to push/pull_request handlers, which trust `repository.full_name` from the JSON body to select the `Stack`/`Repository` acted upon (e.g. `PushHandler`, `OpenedHandler`, `ClosedHandler`), even though only the `repository.owner.login`/`organization.login` was cryptographically checked: [11](#0-10) [12](#0-11) 

### Impact Explanation
The consequence is a cross-organization/cross-repository write: an attacker with no Shipit session, no `ApiClient` token, and — for the `status`/push/PR paths against an org left without a `webhook_secret` — no credential at all, can inject arbitrary CI status records or trigger sync/archival actions for a stack/repository belonging to a *different*, secured organization hosted on the same Shipit instance. Fabricated "success" statuses can satisfy `merge_request_required_statuses`, causing Shipit's merge queue to execute an **unauthorized merge** of a pull request on a repository the attacker does not control — matching the "Critical: unauthorized deploy, rollback, or merge / cross-repository writes" impact tier.

### Likelihood Explanation
Likelihood depends on the deployment having at least one configured GitHub organization without a `webhook_secret` while hosting stacks for other, secured organizations — this is a documented, supported (not "not mounting the engine as documented") configuration, since `docs/setup.md` calls the webhook secret "optional." Given that, exploitation requires no privileged credential: the attacker only needs a target commit SHA (often public, e.g. visible from GitHub's own UI/API) and network access to the `/webhooks` endpoint. Even in the fully-secured configuration (every org has a secret), the underlying binding gap (`repository_owner` used for auth vs. `repository.full_name`/no-check used for the write) is a code-level flaw independent of credential possession, though exploiting it there requires knowledge of a valid secret and is out of scope per the rules.

### Recommendation
- In `StatusHandler` (and any handler relying on a global lookup), scope the lookup by the same `repository.full_name` that is nominally trusted, and additionally verify that `repository.full_name`'s owner matches the `repository_owner` that was cryptographically authenticated in `WebhooksController#verify_signature`.
- In `WebhooksController#verify_signature`, after selecting the `GitHubApp` by `repository_owner`, re-derive and compare the payload's `repository.full_name` owner against `repository_owner`, rejecting mismatches with `422`.
- Treat a missing `webhook_secret` as "verification required but impossible" only when explicitly and intentionally allowed (e.g., single-tenant / development mode), and log/alert loudly, rather than silently returning `true`.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `orgA` (no `webhook_secret`) and `orgB` (secured, hosts a real stack with an open PR whose merge queue requires a passing `ci/travis` status).
2. Find any commit SHA on `orgB`'s tracked branch (e.g., the head SHA of the open PR), obtainable from GitHub's public API/UI.
3. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": {"owner": {"login": "orgA"}, "full_name": "orgA/anything"},
  "sha": "<orgB PR head sha>",
  "state": "success",
  "context": "ci/travis",
  "created_at": "2026-09-01T00:00:00Z"
}
```
   No `X-Hub-Signature` needed, since `orgA` has no `webhook_secret` — `verify_webhook_signature` short-circuits to `true` at [13](#0-12) .
4. `StatusHandler#process` matches `Commit.where(sha: params.sha)` globally (no org/repo filter) and calls `create_status_from_github!`, writing a forged "success" `ci/travis` status onto the `orgB` commit.
5. When the merge queue next processes the PR (`ProcessMergeRequestsJob`/`reject_unless_mergeable!`), the forged status satisfies `any_status_checks_missing?`/`any_status_checks_failed?`, and `merge!` calls GitHub to merge the `orgB` pull request — an unauthorized merge performed without the attacker ever touching `orgB`'s webhook secret, API token, or GitHub credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
