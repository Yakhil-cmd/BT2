### Title
`Assets::mint` with `amount = 0` bypasses issuer permission check and asset-existence check, emitting a spoofed `Issued` event - ([File: substrate/frame/assets/src/functions.rs])

### Summary
`pallet_assets::Pallet::mint` (the public, `Signed`-only extrinsic) delegates to `do_mint`, which calls `increase_balance`. `increase_balance` returns `Ok(())` immediately when `amount.is_zero()`, before it ever loads `Asset::<T, I>::get(&id)` or invokes the `check` closure that enforces `check_issuer == details.issuer`. Back in `do_mint`, after this early-return success, the function unconditionally emits `Event::Issued { asset_id: id, owner: beneficiary, amount }`. Any signed account can therefore call `mint(origin, id, beneficiary, 0)` for an asset it does not control — or one that does not even exist — and get a genuine, on-chain `Issued` event recorded with themselves as the effective minter and an arbitrary `beneficiary`.

The zero-amount guard is the very first line of `increase_balance`, placed *before* `Asset::<T, I>::try_mutate` looks up the asset and *before* the `check` closure (issuer check) runs. When `amount == 0`:
- No `Asset::<T,I>::get`/`try_mutate` occurs, so **the asset does not even need to exist**.
- The `check_issuer == details.issuer` comparison in `do_mint`'s closure **never executes**, so **any signed account bypasses the "must be Issuer" requirement**.
- Control returns to `do_mint`, whose trailing `Self::deposit_event(Event::Issued { ... })` runs unconditionally, regardless of whether any state changed.

Net effect: an unprivileged signed account can produce authentic `pallet_assets::Event::Issued { asset_id, owner, amount: 0 }` events for any `asset_id` (real or non-existent) and any `beneficiary`, with no balance or `supply` change and no issuer/existence validation.

### Impact Explanation
No token balance, `Asset::supply`, or account state changes — `amount` is `0` and every mutation path is skipped. The impact is confined to spoofed/forged `Issued` events that misrepresent who authorized minting and for which asset. Off-chain indexers, exchanges, bridges, or UIs that trust `pallet_assets::Event::Issued` as proof that the recorded issuer/admin approved a mint (a reasonable assumption given the extrinsic's own documentation: "the sender must be the Issuer of the asset `id`") can be misled into believing an authorized mint occurred for an asset the caller has no relationship to, including assets that don't exist on-chain. This can also be weaponized to flood consumers of the `Issued` event with spam entries for arbitrary/non-existent `asset_id`s. This mirrors the reported bug class (missing `amount > 0` check letting an unprivileged caller emit a `Minted`/`Issued` event without a real mint), and is exposed identically here in `pallet-assets`, which backs Asset Hub and other production runtimes in this SDK.

### Likelihood Explanation
Trivially reachable: any account with a signing key and no special role or funds can dispatch `Assets::mint(origin, id, beneficiary, 0)` at any time — no governance, no admin/issuer role, no fee beyond standard transaction weight/fees, and works even for asset IDs that were never created. This makes the likelihood high for the "cosmetic/event-integrity" impact class, though bounded because no economic loss or fund manipulation occurs.

### Recommendation
Add an explicit `ensure!(!amount.is_zero(), Error::<T, I>::...)` (or equivalent) in `do_mint`/`mint` before delegating to `increase_balance`, or restructure `increase_balance` so the zero-amount short-circuit still performs the existence and issuer checks before returning, and gate `deposit_event(Event::Issued { .. })` in `do_mint` on `!amount.is_zero()` so a no-op mint cannot emit a state-implying event.

### Proof of Concept
Guard bypass is provable purely by code inspection/trace; execution was not run in this session (no code-execution tool access here). Minimal reproduction that a Devin agent/engineer can run against the existing `pallet-assets` mock (`substrate/frame/assets/src/tests.rs`):
```rust
#[test]
fn mint_zero_amount_bypasses_issuer_check_and_emits_issued_event() {
    build_and_execute(|| {
        // Asset 0 created by account 1 with issuer = 1; account 2 is NOT the issuer.
        assert_ok!(Assets::force_create(RuntimeOrigin::root(), 0, 1, true, 1));

        // account 2 (not the issuer, no admin/root privileges) mints amount=0
        assert_ok!(Assets::mint(RuntimeOrigin::signed(2), 0, 2, 0));

        // Balance/supply unaffected...
        assert_eq!(Assets::balance(0, 2), 0);

        // ...but a genuine Issued event was still emitted, falsely implying an authorized mint.
        System::assert_last_event(RuntimeEvent::Assets(crate::Event::Issued {
            asset_id: 0,
            owner: 2,
            amount: 0,
        }));

        // Even a non-existent asset id succeeds with amount = 0.
        assert_ok!(Assets::mint(RuntimeOrigin::signed(2), 999_999, 2, 0));
    });
}
```
Expected/actual: `Assets::mint` returns `Ok(())` in both calls even though account `2` is not the issuer of asset `0` and asset `999_999` was never created; `Event::Issued` is deposited in both cases. This has not been executed in a live sandbox in this session — it should be run with `cargo test -p pallet-assets mint_zero_amount_bypasses_issuer_check_and_emits_issued_event` to confirm before filing, but the guard-order defect is unambiguous from the source (`increase_balance`'s `if amount.is_zero() { return Ok(()); }` precedes both the `Asset::<T,I>::try_mutate` existence lookup and the `check` closure's issuer comparison, and `do_mint`'s `deposit_event` call is unconditional). 		id: T::AssetId,
		beneficiary: &T::AccountId,
		amount: T::Balance,
		maybe_check_issuer: Option<T::AccountId>,
	) -> DispatchResult {
		Self::increase_balance(id.clone(), beneficiary, amount, |details| -> DispatchResult {
			if let Some(check_issuer) = maybe_check_issuer {
				ensure!(check_issuer == details.issuer, Error::<T, I>::NoPermission);
			}
			debug_assert!(details.supply.checked_add(&amount).is_some(), "checked in prep; qed");

			details.supply = details.supply.saturating_add(amount);

			Ok(())
		})?;

		Self::deposit_event(Event::Issued { asset_id: id, owner: beneficiary.clone(), amount });

		Ok(())
	}
