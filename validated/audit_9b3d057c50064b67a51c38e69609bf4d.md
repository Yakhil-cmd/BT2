### Title
Missing recursion cap and process-group kill for `submodule update --init --recursive` allows orphaned git subprocesses to outlive `--sync-timeout` - ([File: main.go], [File: pkg/cmd/cmd.go])

### Summary
`configureWorktree` invokes `git submodule update --init --recursive` with no git-sync-imposed cap on submodule nesting depth, relying entirely on git's own behavior and the ambient `ctx` deadline from `--sync-timeout`. The command is launched via `exec.CommandContext` with no `SysProcAttr`/process-group setup and no `cmd.Cancel`/`WaitDelay` override, so when the context expires only the direct child git process is killed - any nested git subprocesses that `submodule update --recursive` spawns per submodule level are not guaranteed to be reaped, allowing continued CPU/disk consumption after git-sync has already reported failure.

### Finding Description
`configureWorktree` builds the submodule args unconditionally based on `git.submodules == submodulesRecursive` (the default) with no depth-limiting flag: [1](#0-0) 

This is run through `git.Run(ctx, ...)`, which routes to `cmd.Runner.Run` → `runWithStdin`, which builds the child process with `exec.CommandContext(ctx, command, args...)` and calls `cmd.Run()` with no `SysProcAttr` (no `Setpgid`), no custom `cmd.Cancel`, and no `WaitDelay`: [2](#0-1) 

`git submodule update --init --recursive` does not fork+exec a shell tree that the OS groups under one PGID by default in this configuration; each submodule level is processed by the parent `git` process spawning further `git clone`/`git fetch`/`git checkout` subprocesses as it descends the `.gitmodules` chain. Go's default `exec.CommandContext` behavior, absent an explicit `Cancel` function or process-group signaling, sends `SIGKILL` only to the direct child (`cmd.Process.Kill()`). Grandchild git processes spawned during recursive submodule init are not part of that direct kill target and, if already forked at the moment the context expires, can be reparented and continue running (continuing to write into `--root`) after `git.Run` returns the `context.DeadlineExceeded` error at: [3](#0-2) 

git-sync itself imposes no maximum submodule recursion depth check anywhere in `configureWorktree` — the only depth-related flag, `--depth`, controls git history shallow-clone depth, not submodule nesting levels: [4](#0-3) 

So a malicious repo with a very deep submodule-of-submodule chain (attacker-controlled repo content, well within the unprivileged threat model since the attacker only needs push/ref control over the synced repository) can make a single sync attempt run long enough to exceed `--sync-timeout`. Because there is no depth cap and no guaranteed process-group kill, the outer loop reports the sync as failed and starts a new cycle, while the orphaned recursive-submodule-update subprocess tree may continue consuming CPU and writing to `--root` concurrently with the next sync attempt.

### Impact Explanation
This matches the "persistent stall/exhaustion a consumer would suffer" impact class: unprivileged attacker-controlled repo content can trigger unbounded/uncapped recursive work whose process is not reliably terminated on timeout, leading to continued disk writes into `--root` and CPU consumption by orphaned processes racing with subsequent sync attempts operating on the same worktree/`.git` directory. This can corrupt worktree state, cause flapping "failure" reports even though work continues in the background, and amplify resource exhaustion (Kubernetes-relevant: sustained CPU/disk usage, wedged sync loop, worktree/fsck failures on the next cycle) without any privileged access.

### Likelihood Explanation
This requires only the default configuration: `--submodules=recursive` (the default) and any `--sync-timeout` value (default 120s). It requires the attacker to control the content of the repository being synced (already an accepted precondition), specifically to craft a chain of nested submodules deep/expensive enough that a single `submodule update --init --recursive` invocation exceeds `--sync-timeout`. No non-default flags are needed. Feasibility depends on OS scheduling timing (whether grandchild processes have already been forked at the moment of SIGKILL) — this is not 100% deterministic per run, but is reliably reproducible with a sufficiently deep/slow submodule chain and a tight timeout, and is a real fragility because git-sync makes no attempt to establish a process group for the child or to reap descendants.

### Recommendation
- Impose a git-sync-level cap on submodule recursion depth (e.g., reject or truncate submodule chains beyond a configurable maximum) before invoking `submodule update --init --recursive`, independent of git's own behavior.
- Run the git subprocess in its own process group (`SysProcAttr{Setpgid: true}` on Unix) and, on context cancellation, kill the entire process group (`syscall.Kill(-pgid, syscall.SIGKILL)`) instead of relying on `cmd.Process.Kill()` which only targets the direct child.
- Alternatively/additionally, set `cmd.Cancel` and `cmd.WaitDelay` on the `exec.Cmd` to guarantee prompt, complete termination of the full subprocess tree when the context is canceled, and verify via `cmd.Wait()` that no children remain running before proceeding to the next sync cycle.

### Proof of Concept
Integration test sketch:
1. Create a chain of 50 nested submodule repos (`sub0` containing `sub1` containing `sub2` ... `sub49`), each with a moderately large blob to slow processing, similar to `e2e::submodule_sync_default` in `test_e2e.sh`.
2. Run `GIT_SYNC --repo=file://$REPO --root=$ROOT --link=link --sync-timeout=1s` (short timeout, default `--submodules=recursive`).
3. Assert the sync reports failure via the error metric/log within a short bound after `--sync-timeout` elapses.
4. Immediately after "failure" is reported, poll `ps`/`/proc` for any `git` processes with `--root`/worktree paths in their cwd/argv still running, and check file mtimes under `$ROOT` continuing to change after the reported failure timestamp — expected (buggy) result: orphaned `git` subprocess(es) still running and writing files; expected (fixed) result: no `git` process remains and no further writes occur after the reported failure.
5. Confirm the next sync cycle does not race with leftover writes (e.g., via `fsck`/`sanityCheckWorktree` failing intermittently due to concurrent tree mutation) — see `sanityCheckWorktree`'s use of `git fsck --connectivity-only`, which can be a symptom of this concurrency issue. [5](#0-4)

func runWithStdin(ctx context.Context, log logintf, cwd string, env []string, stdin, command string, args ...string) (string, string, error) {
	cmdStr := cmdForLog(command, args...)
	log.V(5).Info("running command", "cwd", cwd, "cmd", cmdStr)

	cmd := exec.CommandContext(ctx, command, args...)
	if cwd != "" {
		cmd.Dir = cwd
	}
	if len(env) != 0 {
		cmd.Env = env
	}
	outbuf := bytes.NewBuffer(nil)
	errbuf := bytes.NewBuffer(nil)
	cmd.Stdout = outbuf
	cmd.Stderr = errbuf
	cmd.Stdin = bytes.NewBufferString(stdin)

	start := time.Now()
	err := cmd.Run()
	wallTime := time.Since(start)
	stdout := strings.TrimSpace(outbuf.String())
	stderr := strings.TrimSpace(errbuf.String())
	if ctx.Err() == context.DeadlineExceeded {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, ctx.Err(), stdout, stderr)
	}
	if err != nil {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, err, stdout, stderr)
	}
	log.V(6).Info("command result", "stdout", stdout, "stderr", stderr, "time", wallTime)

	return stdout, stderr, nil
