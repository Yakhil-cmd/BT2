### Title
Cross-organization webhook forgery via mismatched signature-verification field and repository-action field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify a signature against using `repository.owner.login` (or `organization.login`), but the actual event handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers) resolve the target `Repository`/`Stack` using a *different* attacker-controlled field, `repository.full_name`. These two fields are read from the same untrusted JSON body but are never bound to each other, so a signature valid for organization A can authorize a payload that writes to a stack belonging to organization B.

### Finding Description
`verify_signature` picks the GitHub App config to check the HMAC signature against based on `repository_owner`: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The signature is validated with `SecureCompare` against the HMAC computed with the `webhook_secret` configured for the *organization named in `repository.owner.login`* [3](#0-2) .

Once the signature passes, the same raw payload is dispatched to handlers, all of which resolve the target repository from a **different** field, `repository.full_name`: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and the pull-request handlers all key off `repository.full_name`/`params.repository.full_name` [5](#0-4) [6](#0-5) .

Because Shipit supports hosting multiple GitHub organizations from a single instance, each with its own `webhook_secret` in `config/secrets.yml`, and because a single shared `/webhooks` endpoint dispatches on `X-Github-Event` without validating that `repository.owner.login` matches `repository.full_name`'s owner segment, an attacker who legitimately controls a webhook-secret-bearing organization ("OrgA") can forge a raw JSON body where:
- `repository.owner.login = "OrgA"` (used only to select the verification secret)
- `repository.full_name = "VictimOrg/victim-repo"` (used to select which `Stack`/`Repository` record is acted upon)

Signing this body with OrgA's real `webhook_secret` produces a signature that `verify_signature` accepts, yet the handler that runs afterward mutates state belonging to `VictimOrg`, an organization the attacker was never authenticated for. This breaks the equality that should hold: *organization whose secret authenticated the request* == *organization/repository actually written to*.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Concretely, an attacker who is a legitimate app/webhook administrator for one org tracked by a shared Shipit instance can:
- Force `StatusHandler#process` to attach arbitrary CI statuses (`state: success`, arbitrary `context`) to any commit `sha` that exists in a victim stack's history [7](#0-6) . Since `MergeRequest#reject_unless_mergeable!`/`all_status_checks_passed?` rely on exactly these stored statuses via `StatusChecker` [8](#0-7) , forged "success" statuses can push a pending merge-queue PR in the victim repo past its CI gating.
- If that PR clears gating, Shipit's scheduled merge queue calls `stack.github_api.merge_pull_request(...)` using Shipit's own installation/App credentials [9](#0-8)  — i.e., an unauthorized merge into a repository the attacker does not control, performed with the app's GitHub credentials. This satisfies the "unauthorized deploy, rollback or merge" / "cross-repository writes" Critical-impact criteria.
- Independently, `PushHandler` lets the attacker trigger `GithubSyncJob`/resync for any tracked victim stack with an attacker-chosen `expected_head_sha`, and PR handlers let the attacker archive/unarchive review stacks or tamper with stored PR metadata for repositories they don't own.

### Likelihood Explanation
Exploitability requires the attacker to possess a valid `webhook_secret` for *some* organization configured in the same Shipit instance (a normal, unprivileged capability for anyone who administers a GitHub App/organization onboarded to a shared Shipit deployment, and not equivalent to holding a Shipit session, `ApiClient` token, or the target org's own secret). The `/webhooks` endpoint is a public, unauthenticated-by-source HTTP endpoint that accepts any POST body with a matching HMAC, and there is no cross-check between `repository.owner.login` and `repository.full_name`. This is a straightforward, deterministic bug (not requiring races or timing), so likelihood is high in any multi-organization Shipit deployment (a supported and documented configuration in `config/secrets.development.shopify.yml`).

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), require that the resolved verifying organization matches the owner segment of `repository.full_name` before dispatching to handlers — i.e., derive a single canonical "owner" from the payload and use it consistently for both signature-secret selection and repository resolution, rejecting payloads where they diverge. Alternatively, verify the signature using a secret bound to the resolved target repository/stack's own organization rather than a value taken from an independent, equally attacker-controlled field.

### Proof of Concept
1. Shipit instance is configured with two organizations, `OrgA` (attacker-administered) and `VictimOrg` (has a tracked `Stack`/`Repository` `VictimOrg/victim-repo` with an open merge-queue PR awaiting a required CI status), each with distinct `webhook_secret`s in `config/secrets.yml`.
2. Attacker builds a `status` event JSON body:
   ```json
   {
     "sha": "<head sha of victim PR>",
     "state": "success",
     "context": "<required context>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "VictimOrg/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner => "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature checks out — request proceeds.
5. `StatusHandler#process` is invoked with the same payload; it resolves the commit via `params.sha` (global lookup, no owner scoping) and records a fabricated passing status for the victim's commit, independent of `OrgA`/`VictimOrg` mismatch.
6. If a pending `MergeRequest` in `VictimOrg` was blocked only on that missing/failing status, the next merge-queue scheduling run merges the PR using Shipit's GitHub App credentials — an unauthorized cross-organization merge triggered entirely by an attacker who never authenticated as `VictimOrg`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
