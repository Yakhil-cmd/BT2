### Title
Near-cap supply makes the next accrual overflow `i128`, permanently freezing every verb on the market - (File: common/src/rates/simulate.rs)

### Summary
The admitted supply cap allows a market's scaled supplied total to reach essentially `i128::MAX`. Because every accrual step unscales `supplied` by the growing supply index (`scaled_to_original` → `supplied * supply_index / RAY`), the first positive accrual after a near-cap supply overflows `i128` and panics with `MathOverflow`. Since every pool mutation (`supply`, `withdraw`, `borrow`, `repay`, `seize_positions`, `net_settle`, `flash_loan`, `recapitalize`, `claim_revenue`) and the permissionless `update_indexes` run `global_sync` → `accrue_chunk` → `accrue_step` first, the panic is unrecoverable: the market — and all user funds in it — is frozen forever. This mirrors CVE-2016-9578: state shaped by unprivileged messages causes the protocol handler to crash on every subsequent message.

### Finding Description
- `common/src/validation.rs:48-56` `max_cap_for_decimals` admits caps up to `i128::MAX / 10^(27-decimals)`; a cap-max deposit therefore mints scaled shares `≈ i128::MAX / RAY * RAY` — i.e. `supplied` (scaled, RAY-domain) ≈ `i128::MAX`.
- `contracts/pool/src/interest.rs:20-33` `global_sync` runs before every mutation and calls `accrue_step` for any nonzero elapsed time.
- `common/src/rates/simulate.rs:60-62` `accrue_step` computes `supplied_original = scaled_to_original(supplied, supply_index)` and `borrowed_original` before anything else. `scaled_to_original` (`common/src/rates/scaling.rs:14-16`) is `scaled.mul(index)`; via `mul_div_half_up` (`common/src/math/fp_core.rs:108-118`) the widened `I256` product is converted back with `to_i128` (`fp_core.rs:300-303`), which panics `MathOverflow` once `supplied * supply_index / RAY > i128::MAX`.
- Once `supply_index` grows above `RAY` by any amount — which requires only a tiny borrow so that `calculate_supplier_rewards` produces nonzero rewards (`common/src/rates/index.rs:73-89`) — the accrual result exceeds `i128::MAX` and the panic fires on *every* subsequent call, including `update_indexes` itself (`contracts/controller/src/lib.rs:370`). Soroban reverts the whole transaction, so the committed index never advances and no retry path exists.
- The same panic also hits `supply_index_reward_shortfall`/`calculate_supplier_rewards` (`index.rs:60-63, 80-83`) and `apply_bad_debt_to_supply_index` (`interest.rs:74`), so liquidation-driven seizure and bad-debt write-down are equally dead.
- Confirmed reachable in-repo: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-362` demonstrates that once the RAY-value ceiling is exceeded, `withdraw` and `repay` permanently revert with `MATH_OVERFLOW` (the test reaches it via years of accrual; a near-cap deposit reaches it in one accrual). `docs/reference/formulas.md:434-437` acknowledges "value overflow can occur before the index ceiling and block repayment/withdrawal" — but the admitted caps make it user-triggerable, not a remote numeric corner.

### Impact Explanation
Permanent freezing of funds and protocol insolvency. After the freeze: suppliers cannot withdraw (each `withdraw` accrues first and panics), borrowers cannot repay, liquidations and `clean_bad_debt`/`seize_positions` cannot execute, and `recapitalize`/`claim_revenue` are dead too since all flow through `Cache::load` → `global_sync`. Any outstanding debt accrues to unrecoverable bad debt while collateral and supplied tokens are locked in the pool contract permanently.

### Likelihood Explanation
Reachable by a single unprivileged address via the documented entrypoints: `supply` an amount at (or near) the market's configured supply cap — the protocol explicitly admits caps up to `max_cap_for_decimals` — then open a small collateralized `borrow` so rewards > 0, then call `update_indexes` (permissionless) after any elapsed millisecond. The first accrual panics and the market is frozen. Feasibility scales with decimals: for a 0–2 decimal asset the cap-max is only ~170–17,000 whole tokens (though such assets are collateral-only); for 7 decimals it is ~1.7 million whole tokens. No privileged action, leaked key, or oracle manipulation is needed.

### Recommendation
Keep market totals inside the RAY-value domain, not just the scaled-share domain:
- Enforce caps such that `scaled_total * MAX_SUPPLY_INDEX_RAY / RAY` fits `i128` (e.g., cap `supplied` at `i128::MAX / 10^9`-ish headroom, or equivalently reduce `max_cap_for_decimals` by the index ceiling factor).
- Alternatively, make `scaled_to_original` saturate on the accrual path (like `mul_div_floor_saturating` already used by `calculate_scaled_cap`) so accrual degrades instead of trapping, keeping repay/withdraw/liquidate paths alive.
- At minimum, add a post-mutation guard in `supply`/`borrow` that simulates one accrual step and rejects deposits that would push `supplied`/`borrowed` over the representable-value ceiling.

### Proof of Concept
1. Governance lists a market for a 7-decimal token with `supply_cap = max_cap_for_decimals(7) ≈ 1.7e13` base units and any nonzero borrow rate curve (`borrow` at any utilization yields `rewards_increase > 0`).
2. Attacker acquires/mints the cap amount and calls `controller.supply(caller, hub, spoke, [leg(asset, cap_max)])`. `calculate_scaled_supply` succeeds: scaled shares ≈ `i128::MAX`.
3. Attacker supplies a small collateral position and calls `controller.borrow(...)` for a nonzero amount, putting utilization > 0.
4. Wait one millisecond; call `controller.update_indexes(caller, [(hub, asset)])` → `pool.update_indexes` → `ops::market::accrue` → `global_sync` → `accrue_step` → `scaled_to_original(supplied, supply_index')` with `supply_index' > RAY` → widened `I256` product exceeds `i128::MAX` → `to_i128` panics `MathOverflow`.
5. All subsequent `withdraw`, `repay`, `borrow`, `liquidate`, `seize_positions`, `claim_revenue`, `recapitalize`, and `update_indexes` calls on the market panic at the same line — permanent freeze, matching the harness test assertion `MATH_OVERFLOW` on `try_withdraw_raw`/`try_repay` after the index-value cliff.
