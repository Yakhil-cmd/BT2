### Title
CCMenu token grants `read:stack` on any stack instead of the requesting stack, because `stack:` is never assigned to the created `ApiClient` - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#client` mints an `ApiClient` scoped to `permissions: %w[read:stack]` but never sets `stack: stack`, leaving `ApiClient#stack_id` `nil`. Because `Api::BaseController#stacks` falls back to `Stack.all` whenever `current_api_client.stack_id?` is false, that token authenticates read access to every stack in the installation, not just the one whose CCMenu URL was requested.

### Finding Description
The binding that should hold is: `current_api_client.stack_id == stack.id` (the stack for which the CCMenu URL was generated). Tracing the code:

- `CCMenuUrlController#fetch` builds a URL containing `client.authentication_token` [1](#0-0) .
- `client` is created via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — note `stack:` is not passed anywhere, and the lookup key is only `creator` + fixed `name` [2](#0-1) . This means: (a) the resulting `ApiClient#stack_id` is `nil`, and (b) every call to `fetch` for the same user, regardless of which `stack.to_param` was requested, returns/reuses the exact same client/token (`find_or_create_by!` matches on `creator`+`name` only).
- `ApiClient.authenticate(token)` just verifies the signed id and loads the record — it does not check any stack binding [3](#0-2) .
- `Api::BaseController#stacks` is: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [4](#0-3) . Since `stack_id` is `nil`, `stack_id?` is `false`, so `stacks` resolves to `Stack.all`.
- `Api::TasksController` requires only `:read, :stack` (a permission-string check, not a stack-membership check) via `require_permission!` → `current_api_client.check_permissions!` [5](#0-4) [6](#0-5) , then resolves `stack` via `stacks.from_param!(params[:stack_id])` [7](#0-6) , which — because `stacks` is `Stack.all` — accepts **any** `stack_id` in the URL. `Api::StacksController#show`/`#index` have the identical issue [8](#0-7) , [9](#0-8) .

Exploit flow: an authenticated Shipit web-UI user (any user who can view a CCMenu URL for one stack they're permitted to see, e.g. via `GET /stacks/:owner/:repo/:env/ccmenu.json`-style route) obtains `token=T`. `T` is not restricted to that stack. The same token can then be replayed as `GET /api/stacks/<other_owner>/<other_repo>/<other_env>/tasks.json?token=T`, and the controller happily resolves `stacks` to `Stack.all`, returning task/deploy-log data for a stack the user was never individually authorized against through this mechanism.

No existing guard prevents this: `require_permission!` only checks the string permission list, not stack identity; `stacks.from_param!` trusts whatever `stacks` scope resolved to; and `ApiClient.authenticate` performs no stack check.

### Impact Explanation
Any user able to fetch one stack's CCMenu URL obtains a token that discloses task/deploy output (which can include commit messages, build logs, deploy status) for every stack managed by the Shipit instance, including stacks belonging to repositories the requester has no GitHub access to. This is an unauthenticated-scope read of stack state/task streams across tenants — matching the "High: escalation ... unauthenticated read of stack state, task streams or deploy output" category. It is fully repeatable: the same leaked token works against every stack's `/api/stacks/:id.json` and `/api/stacks/:id/tasks.json` (and task `show`) endpoints indefinitely, since `ApiClient` tokens don't expire and the record is reused across requests (`find_or_create_by!`).

### Likelihood Explanation
Preconditions: the attacker must be able to reach `CCMenuUrlController#fetch` for at least one stack (this generally requires being an authenticated Shipit user with view access to some stack — the exact authorization on that controller/route was not independently verified in this pass, but the vulnerability itself lies entirely in the token's scope, not in how it is obtained). Once a CCMenu token exists for any stack, no further secrets, GitHub credentials, or elevated roles are needed — the attacker simply reuses the query-string token against arbitrary `stack_id`s in the API. This is low-cost and highly repeatable.

### Recommendation
Bind the CCMenu `ApiClient` to the specific stack: `ApiClient.create_with(permissions: %w[read:stack], stack: stack).find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')` (or a per-stack unique name), so `stack_id` is always populated and `Api::BaseController#stacks` never falls back to `Stack.all` for these tokens.

### Proof of Concept
```ruby
# test/controllers/shipit/api/tasks_controller_ccmenu_scope_test.rb
require 'test_helper'

module Shipit
  module Api
    class CcmenuTokenScopeTest < ActionDispatch::IntegrationTest
      test "a CCMenu token for stack A cannot read tasks of stack B" do
        user = shipit_users(:walrus)
        stack_a = shipit_stacks(:shipit)
        stack_b = shipit_stacks(:cyclimse) # any other fixture stack

        # Simulate what CCMenuUrlController#client does today
        client = ApiClient.create_with(permissions: %w[read:stack])
                          .find_or_create_by!(creator: user, name: 'CCMenu Client')
        token = client.authentication_token

        # Binding under test: current_api_client.stack_id must equal stack_a.id
        assert_nil client.stack_id, "expected the CCMenu client to be unscoped (root cause)"

        get "/api/stacks/#{stack_b.to_param}/tasks.json", params: { token: token }

        assert_response :success # currently succeeds -- proves the leak
        # Expected (fixed) behavior: this should be :unauthorized or :not_found,
        # because the token was minted for stack_a, not stack_b.
      end
    end
  end
end
```
