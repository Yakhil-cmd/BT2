### Title
Webhook Signature Verification Selects Trust Key by `repository.owner.login`, But Event Handlers Act on `repository.full_name` — Cross-Organization Webhook Spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The auto-roll bug class is "a value used to authorize a critical calculation differs from the value that is actually verified/relied upon, letting an attacker manipulate the authorization input cheaply." The same shape exists in `WebhooksController#verify_signature`: it picks *which organization's secret* to check the HMAC against using `repository_owner` (`repository.owner.login`), but the event handlers that actually mutate state pick the *target repository* using a different payload field, `repository.full_name`. When a Shipit instance is configured for multiple GitHub organizations and any one organization has no `webhook_secret` set (a state the shipped example configs explicitly support), an attacker can forge a webhook whose "authenticating organization" is the unprotected one while its "acted-upon repository" belongs to a different, protected organization — bypassing signature verification entirely for that repository.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/secret to validate against with: [1](#0-0) [2](#0-1) 

`repository_owner` is taken straight from the untrusted, unverified request body (`params.dig('repository', 'owner', 'login')`) *before* any signature check occurs — it is the key used to select which secret is authoritative.

`verify_webhook_signature` treats an organization with no configured secret as automatically valid: [3](#0-2) 

Meanwhile, once verification passes, `create` dispatches the *entire* attacker-controlled payload to handlers: [4](#0-3) 

Every handler determines the actual repository/stacks to mutate using a **different** field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

Under legitimate GitHub traffic, `repository.owner.login` and the owner segment of `repository.full_name` always agree because GitHub generates both fields from the same real repository. But an attacker posting directly to the public `/webhooks` endpoint fully controls the JSON body and can set these two fields independently. Multi-organization deployments are explicitly documented and shipped with example configs where a per-org `webhook_secret` may legitimately be left blank/`nil`: [7](#0-6) [8](#0-7) 

**Attack:** send a forged webhook with `repository.owner.login = "OrgWithNoSecret"` (satisfies `verify_signature`, which trivially passes because `webhook_secret` is nil) and `repository.full_name = "ProtectedOrg/target-repo"`. The controller never re-validates that the org used for verification matches the org whose repository is being mutated. `Handler#stacks`/`#repository_name` resolves and operates on `ProtectedOrg/target-repo`'s `Stack`(s) using attacker-supplied event data, even though `ProtectedOrg` has a real `webhook_secret` that was never checked.

This is precisely the reported bug class's core error: a value that is authenticated/verified (`repository_owner` → which secret is used) is not the same value that is subsequently acted upon (`repository.full_name` → what gets mutated), i.e. "an organization that authenticated" ≠ "the repository that is written."

### Impact Explanation
Depending on which webhook event/handler is invoked, this allows an unauthenticated attacker to:
- Enqueue `GithubSyncJob` with an attacker-chosen `expected_head_sha` for a protected org's stack via `PushHandler` [9](#0-8) .
- Inject forged commit `status`/`check_suite` results for commits belonging to a protected repository via `StatusHandler`/`CheckSuiteHandler`, which feed directly into deploy-gating logic (`deployable?`, `merge_status`) [10](#0-9) [11](#0-10) .
- Manipulate `Team`/`Membership` records via the `membership` handler, which affects `Shipit.github_teams` authorization checks used to gate access to `ApiClientsController` and similar privileged pages.

This crosses the "escalation into `Shipit.github_teams` authorization" / "unauthorized... deploy" thresholds defined as High/Critical impact.

### Likelihood Explanation
Requires: (1) the operator to run Shipit with multiple GitHub organizations configured (a documented, supported setup), and (2) at least one configured organization lacking a `webhook_secret`. Both conditions are explicitly presented as normal, supported configuration in the shipped docs and default config templates, not as misconfiguration outside the documented deployment model. No credentials, session, or repository access are required by the attacker — only the ability to POST to the public `/webhooks` endpoint.

### Recommendation
After selecting `repository_owner` for signature verification, require that the actual owner segment of `repository.full_name` (and `organization.login`, if present) match `repository_owner` before processing; alternatively, resolve the organization/secret to verify against strictly from the same field (`repository.full_name`'s owner) that handlers use to select the target `Stack`/`Repository`, and reject events when a configured organization has no distinguishing secret rather than treating "no secret" as "always verified."

### Proof of Concept
Given a `secrets.yml` with two orgs, `OrgA` (no `webhook_secret`) and `ProtectedOrg` (has `webhook_secret`, with an existing `Stack` for `ProtectedOrg/target-repo`):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "ProtectedOrg/target-repo"
  }
}
```

- `verify_signature` computes `repository_owner = "OrgA"`, loads `OrgA`'s `GitHubApp` (no `webhook_secret`), and `verify_webhook_signature` returns `true` unconditionally — no HMAC comparison performed.
- `create` dispatches the payload to `PushHandler`, which resolves `repository_name = "ProtectedOrg/target-repo"` and enqueues `GithubSyncJob` for that stack with the attacker-supplied `after` SHA, despite `ProtectedOrg` having signature protection that was never checked.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
