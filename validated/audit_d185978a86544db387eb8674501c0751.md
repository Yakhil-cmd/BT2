[1](#0-0) ### Title
Stack-scoped `ApiClient` tokens bypass their stack binding via the CCMenu API endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` re-implements the `stack` resolver instead of using the scoped one inherited from `Shipit::Api::BaseController`, and its authorization check never validates that the resolved stack matches the authenticated `ApiClient`'s bound `stack_id`. As a result, any valid `ApiClient` token that carries `read:stack` permission — including ones deliberately scoped to a single stack — can read the build/deploy status of *any* stack in the installation by simply changing the `stack_id` path segment.

### Finding Description
`Shipit::ApiClient` supports being bound to a single stack: `belongs_to :stack, optional: true` [2](#0-1) . `Shipit::Api::BaseController` enforces this binding for every normal API resource by scoping the queryable stacks: `@stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` and resolving `stack` through that scope: `@stack ||= stacks.from_param!(params[:stack_id])` [3](#0-2) .

`Shipit::Api::CCMenuController`, however, overrides `stack` to resolve directly against the unscoped `Stack` model: `@stack ||= Stack.from_param!(params[:stack_id])` [4](#0-3) . The only authorization gate is `require_permission :read, :stack` [5](#0-4) , which calls `ApiClient#check_permissions!`. That method only checks whether the required permission string (e.g. `"read:stack"`) is present in the client's `permissions` array — it never checks `current_api_client.stack_id` against the requested stack: [6](#0-5) .

The equality that should hold is:
`stack the ApiClient.stack_id authorises == stack the CCMenuController#show actually renders`

Before the fix this equality only holds accidentally for tokens whose `stack_id` is blank (unscoped clients, where `BaseController#stacks` also returns `Stack.all`). But for any `ApiClient` explicitly bound to one stack (e.g. the "here_come_the_walrus" fixture used elsewhere in the test suite, `stack: shipit`, `permissions: [read:stack]`) [7](#0-6) , the binding is broken: that token, presented against `GET /api/stacks/:stack_id/ccmenu` for an *unrelated* `stack_id`, is accepted and returns that other stack's data. This route is reachable with only `read:stack` permission and a valid bearer/basic token — no elevated privilege is required beyond possessing any leaked or intentionally-scoped read-only token, e.g. a "CCMenu URL" token that an admin shares with a third-party CI dashboard tool [8](#0-7) .

### Impact Explanation
This is an unauthenticated-scope-escalation read: a token an operator explicitly restricted to one stack (project) can be used to read task/deploy status of every other stack managed by the same Shipit instance, including private/internal projects' deploy state, last build status, and labels — this matches the "High" impact bucket of "unauthenticated read of stack state, task streams or deploy output" via a broken authorization scope, since the token was never authorized to view other stacks.

### Likelihood Explanation
Any holder of a scoped, read-only `ApiClient` token — which by design is meant to be shared with lower-trust third parties (e.g. embedded in a CCMenu URL handed to a CI status widget) — can trivially exploit this by changing the `stack_id` in the request path. No cryptographic bypass, privileged account, or additional secrets are required; the attack only needs the low-trust token that was legitimately issued for one project.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the same scoped `stacks` method used by `Shipit::Api::BaseController` (i.e., remove the local override, or implement it as `stacks.from_param!(params[:stack_id])`) so that stack-bound `ApiClient` tokens can only ever resolve to their bound `stack_id`.

### Proof of Concept
1. As an admin, restrict an `ApiClient` to `stack_a` with `permissions: ['read:stack']` (as done for the `here_come_the_walrus` fixture) [7](#0-6) .
2. Authenticate as that client (`authenticate!(:here_come_the_walrus)`), then request `GET /api/stacks/<stack_b_owner>/<stack_b_name>/<stack_b_env>/ccmenu` for a different stack `stack_b` that the client is not bound to.
3. Because `CCMenuController#stack` uses `Stack.from_param!(params[:stack_id])` unscoped [4](#0-3)  and `check_permissions!` never compares `stack_id` [6](#0-5) , the request succeeds with `200 OK` and returns `stack_b`'s CCMenu XML (build status, last build label, web URL), despite the token only being authorized for `stack_a`.
