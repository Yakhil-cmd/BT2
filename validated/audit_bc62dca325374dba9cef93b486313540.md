### Title
Caller-supplied hop contracts can attach unauthorized wallet transfers to a signed swap authorization tree - ([File: `contracts/swap-aggregator/src/execute/mod.rs`])

### Summary
`execute_strategy` accepts a decoded route whose `SwapHop.pool` is taken directly from the route’s caller-controlled `assets` table and dispatches it to a venue without an allowlist or identity check. [1](#0-0) [2](#0-1)  Because `sender.require_auth()` authorizes the root call and Soroban records downstream calls that request sender authorization beneath it, a malicious hop can add a token transfer from the sender’s wallet to the simulation-derived authorization tree. [3](#0-2) [4](#0-3) 

### Finding Description
A hop resolves `pool`, `token_in`, and `token_out` solely from payload indexes, then calls `venues::dispatch_hop`; the dispatch selects an adapter based only on the declared `SwapVenue` and does not verify that `hop.pool` is a genuine venue contract. [1](#0-0) [5](#0-4)  The measured input and output checks bound only the routed input and output balances, not unrelated calls made by the selected hop contract under the sender’s authorization context. [6](#0-5)  The same exposure is reachable through controller strategy entrypoints such as `swap_collateral`, which calls the configured router with caller authentication and caller-supplied `swap` bytes. [7](#0-6) [8](#0-7) 

### Impact Explanation
A victim who signs a transaction containing the malicious route can lose unrelated wallet funds if the simulation-produced authorization tree contains the rogue pool’s token transfer as a child invocation. [9](#0-8)  The protocol’s min-output and positive-output checks do not prevent this loss because the malicious hop can return a valid output while also transferring the victim’s other token to the attacker. [10](#0-9) [11](#0-10)  This qualifies as theft of user funds, although it requires the victim to submit or sign the poisoned authorization tree. [12](#0-11) 

### Likelihood Explanation
Any unprivileged caller can supply route bytes to `execute_strategy`, and any account owner or delegate can reach the router through controller strategy functions with caller-selected `swap` bytes. [13](#0-12) [14](#0-13)  An attacker can deploy an arbitrary contract that implements the invoked venue-facing call shape and place its address in the route’s `assets` table; no on-chain registry or factory check authenticates it. [1](#0-0) [15](#0-14)  Exploitation depends on a user accepting the additional authorization-tree child, but transaction simulation can present that transfer as part of the same signed operation rather than as a separate permit or approval. [16](#0-15) 

### Recommendation
Restrict route pool addresses to governance-approved venue deployments, or bind each hop to a verifiable venue factory/registry lookup rather than trusting the payload’s `assets` table. [17](#0-16)  If permissionless venues are retained, the route format should include an explicit venue manifest and the router should fail closed unless every externally invoked pool is allowlisted or authenticated by a factory-derived address. [5](#0-4)  Wallet and API integrations should also simulate the final authorization tree and reject any child invocation other than the expected input transfer before signing. [12](#0-11) 

### Proof of Concept
The harness deploys an `UnlistedPoolRouter`-equivalent route in which the hop pool is an attacker-controlled `RogueHopPool`; the malicious pool’s `swap` call performs `token.transfer(victim, attacker, amount)` for an unrelated wallet token. [18](#0-17)  A simulation of `swap_collateral` records that transfer as a child of Alice’s controller authorization, proving that the malicious route is executed inside her signed authorization tree. [19](#0-18)  When the same tree is submitted with the rogue transfer listed, Alice’s wallet balance becomes zero and the attacker receives `WALLET_BALANCE`; when the transfer is absent, the host rejects it. [20](#0-19)

pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.

            token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);

    /// Decodes `swap_xdr` as a `StrategyPayload` and runs it for `sender`.
    ///
    /// Requires `sender` authorization. Pulls `total_in` of the input token, runs the
    /// instruction stream, applies fees, checks the minimum output, and returns the amount
    /// delivered to `sender`. Panics with `Error::InvalidRouteXdr` if the XDR does not decode.
    fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        renew_instance(&env);
        let payload = StrategyPayload::from_xdr(&env, &swap_xdr)
            .unwrap_or_else(|_| panic_with_error!(&env, Error::InvalidRouteXdr));
        execute::run(env, sender, total_in, payload)
    }
