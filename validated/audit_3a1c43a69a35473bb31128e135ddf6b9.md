### Title
Slippage-free refund swap in `SwapFirstAssetTrader::refund_weight` enables sandwich-attack value extraction during XCM fee-asset refunds - (File: cumulus/primitives/utility/src/lib.rs)

### Summary
`SwapFirstAssetTrader` is a `WeightTrader` used by asset-hub-rococo, asset-hub-westend, penpal, and the staking-async parachain runtime to let users pay XCM execution fees in a non-native asset by swapping it through `pallet_asset_conversion` (`SwapCredit`). When refunding unused weight fees back into the user's original asset, the trader calls `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min = None`, i.e. no minimum-output/slippage protection, mirroring exactly the pattern flagged in the USSD report (`amountOutMinimum: 0`).

### Finding Description
`SwapFirstAssetTrader::buy_weight` swaps the user-provided fee asset into the `Target` asset (e.g. native token) via `swap_tokens_for_exact_tokens`, which is bounded correctly by `fee` as the exact output [1](#0-0) .

However, `refund_weight`, invoked at the end of XCM execution to return unused weight fees to the user in their originally-paid asset, performs the reverse swap with no minimum-output guard: [2](#0-1) 

```rust
let refund = self.total_fee.extract(refund_amount);
let refund = match SwapCredit::swap_exact_tokens_for_tokens(
    vec![Target::get(), refund_swap_asset],
    refund,
    None,
) { ... }
```

Because `pallet_asset_conversion`'s `do_swap_exact_credit_tokens_for_tokens` only enforces the `amount_out_min` bound when `Some` is supplied [3](#0-2) , passing `None` here means the swap executes at whatever price the AMM pool has at execution time, with zero protection against price manipulation. This is architecturally identical to the reported EVM bug: `amountOutMinimum: 0` on `UniV3SwapInput`, which allowed sandwiching the swap and draining value from balance-delta accounting logic. Here the "balance-delta" accounting analog is `self.total_fee.extract(refund_amount)` — the refund credit amount is computed independent of the actual swap outcome, and any adverse price movement is absorbed silently.

This trader is wired directly into live `XcmConfig::Trader` tuples: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation
Any user-originated XCM message (local `pallet-xcm` `execute`/`send`, or an incoming XCM from a sibling/parent chain) that pays execution fees in a non-native, pool-backed asset and does not consume its entire weight allowance triggers this refund path. An attacker who can observe the pending message (e.g., via mempool visibility of the paired local extrinsic, or by controlling ordering of their own extrinsics within the same block/queue) can sandwich the `Target -> refund_swap_asset` swap by moving the pool price unfavorably immediately before it executes and reverting afterward, extracting the difference between the fair-value refund and the manipulated-price refund. The stolen value comes from the refunded user's fee overpayment, not from a privileged party, and requires no governance/validator/collator compromise — only ordinary DEX liquidity manipulation by an unprivileged actor, matching the report's stated root cause (zero `amountOutMinimum` enabling sandwiching).

Given this affects a fee-refund mechanism (bounded by weight-fee magnitudes, not full asset balances) rather than a direct fund-draining swap, the maximum extractable value per message is limited to the refund amount and the achievable slippage in the underlying pool — this bounds severity below the theft-of-arbitrary-funds category in the original report but still represents a real, repeatable value leak on every relevant XCM execution.

### Likelihood Explanation
Reachability requires only an ordinary user submitting an XCM message that pays fees in an asset other than `Target` and leaves unused weight (very common, since exact weight consumption rarely matches the weight limit purchased). No privileged role, governance action, or malicious collator/validator is needed — an unprivileged attacker able to place transactions/XCM messages around the victim's message in the block (a capability generally available to any network participant) is sufficient to attempt sandwiching. Actual profitability depends on pool depth/liquidity for the specific asset pair and the size of the refund, which varies per deployment and cannot be quantified generically from the code alone.

### Recommendation
Thread a caller-supplied or protocol-derived minimum-acceptable-refund bound through `refund_weight` instead of passing `None` to `SwapCredit::swap_exact_tokens_for_tokens`. At minimum, compute an `amount_out_min` from a recent quote (e.g., via `QuotePrice::quote_price_exact_tokens_for_tokens`) with a bounded tolerance, and treat a shortfall as "keep the refund in `Target`/no refund" rather than accepting an unbounded worst-case price.

### Proof of Concept
Not executed. This analysis is based on static code review of `cumulus/primitives/utility/src/lib.rs` (`SwapFirstAssetTrader::refund_weight`), `substrate/frame/asset-conversion/src/lib.rs` (`do_swap_exact_credit_tokens_for_tokens`), and the four runtime `xcm_config.rs` files confirming production wiring. No local Rust/FRAME integration test was run to empirically measure sandwich profitability against a live pool, and no on-chain/testnet reproduction was performed, per the no-execution constraint. A full PoC would require constructing an XCM-executor integration test that (1) sets up a pool with the `Target` and `refund_swap_asset`, (2) executes an XCM message with excess weight purchased in `refund_swap_asset`, (3) manipulates the pool balance via a bystander swap immediately before `refund_weight` executes, and (4) asserts the refunded amount is below the pre-manipulation fair-value quote — this reproduction was not carried out in this pass and remains unverified.
