### Title
Cross-organization CI status forgery via `StatusHandler` breaks the signing-organization ↔ target-stack binding, enabling unauthorized auto-merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook payload only against the GitHub App secret of the organization named inside the payload's own `repository.owner.login`/`organization.login` field [1](#0-0) . `StatusHandler#process`, however, never re-checks that binding: it looks up commits to update purely by SHA across the entire `Commit` table, with no scoping to the repository/organization that produced the signature [2](#0-1) . An org whose own webhook secret is legitimately configured on this multi-tenant Shipit instance can therefore forge a `status` event that is valid for its own organization but writes a CI status onto a commit belonging to a completely different tenant's stack, ultimately triggering an unauthorized GitHub merge through the merge-queue auto-merge path.

### Finding Description
The trust binding that should hold is:

`organization whose secret signed the payload == organization owning the repository/stack that the payload event actually mutates`

For the `push`, `pull_request`, and `membership` handlers this binding is enforced through `Handler#stacks`, which scopes any DB writes to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [3](#0-2) .

`StatusHandler` breaks this binding. Its `process` method is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This is a global lookup by `sha` alone, with no reference to `repository_name`/`stacks`, i.e. no check that the resolved commit's `stack.repository` is owned by the organization whose secret validated `X-Hub-Signature` in `WebhooksController#verify_signature` [1](#0-0) . Since `Shipit.github(organization: repository_owner)` is looked up per-organization (multiple orgs can be onboarded on the same Shipit deployment, as shown by the `shipit_push`/`cyclimse_push`/`shopify_membership` fixtures using different secrets per org) [4](#0-3) , any organization onboarded to the instance can produce a validly-signed payload (signed with its own, legitimately-known secret) whose `sha`/`state`/`context` fields target any commit that exists in any other tenant's stack.

Setting a forged `success` status on a victim commit feeds directly into consequential logic in `Commit#add_status`:
```ruby
def add_status
  ...
  if previous_status.simple_state != new_status.simple_state
    ...
    stack.schedule_merges if new_status.pending? || new_status.success?
  end
  new_status
end
``` [5](#0-4) 

`stack.schedule_merges` enqueues `ProcessMergeRequestsJob`, which merges pending pull requests once `all_status_checks_passed?`:
```ruby
merge_requests.select(&:pending?).each do |merge_request|
  merge_request.refresh!
  next unless merge_request.all_status_checks_passed?
  begin
    merge_request.merge!
  ...
``` [6](#0-5) 

`all_status_checks_passed?` is computed from the attacker-controlled `context`/`state` on the commit's statuses via `StatusChecker`, and `merge!` calls the GitHub API with the *stack's own* installation credentials to actually merge the PR:
```ruby
def all_status_checks_passed?
  ...
  StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
end

def merge!
  ...
  stack.github_api.merge_pull_request(
    stack.github_repo_name, number, merge_message, sha: head.sha, ...
  )
``` [7](#0-6) 

Because the required status `context` strings (e.g. `continuous-integration/travis-ci/push`) are ordinary, non-secret configuration values documented for any Shipit user [8](#0-7) , an attacker onboarded to the same multi-tenant Shipit instance (owning any organization with its own configured webhook secret) can forge the exact `context`/`state=success` combination required to satisfy a victim stack's merge queue, causing an unauthorized merge to be executed with the victim's own GitHub credentials.

### Impact Explanation
This is a cross-organization write: an unprivileged party (an admin of one onboarded organization on a shared Shipit instance) can affect the state — and ultimately trigger a real GitHub merge — of a stack belonging to a different organization/tenant, using only their own organization's legitimately configured webhook secret and public knowledge of a target commit SHA and required CI context name. This satisfies the Critical bucket "cross-repository writes / an unauthorized deploy, rollback or merge," since it results in `MergeRequest#merge!` invoking `stack.github_api.merge_pull_request` on a repository the attacker does not control, and can also flip `stack.enable_ci!` and schedule continuous delivery for a victim stack via `Status#enable_ci_on_stack`/`schedule_continuous_delivery` [9](#0-8) .

### Likelihood Explanation
Requires: (1) the attacker's own organization is one of the (potentially many) organizations onboarded on the shared Shipit instance (routine multi-tenant setup, see per-org secrets in `github_hooks.yml`), (2) knowledge of a target commit SHA (public on GitHub for public repos, or discoverable), and (3) knowledge of the victim stack's required CI status context (documented, commonly-used strings like CI provider names). No compromise of the victim's own secret, session, or ApiClient token is needed — only the attacker's own legitimately-possessed webhook secret for their tenant. This makes exploitation realistic in any Shipit deployment serving more than one organization/tenant.

### Recommendation
In `StatusHandler#process` (and any other handler that currently resolves objects purely by attacker-supplied identifiers such as `sha`), scope the lookup to the repository/organization that produced the verified signature: resolve the target `Repository`/`Stack` via `payload.dig('repository','full_name')` (as `Handler#stacks` already does for other handlers) before querying `Commit.where(sha: ...)`, and reject/ignore the event if the resolved stack's repository owner does not match the organization used in `WebhooksController#verify_signature`.

### Proof of Concept
1. Deploy Shipit with two onboarded organizations, `attacker-org` (attacker is admin, knows its GitHub App webhook secret) and `victim-org` (an unrelated tenant with a stack that has `merge_queue_enabled` and a pending mergeable PR requiring status context `ci/build`).
2. Attacker crafts a `status` webhook JSON body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/build",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/anything" }
   }
   ```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s own webhook secret (`HMAC-SHA1` over the raw body) and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature (`app/controllers/shipit/webhooks_controller.rb:24-38`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit belonging to `victim-org`'s stack, and calls `create_status_from_github!`, creating a `success` status with context `ci/build` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`).
6. `Commit#add_status` schedules `ProcessMergeRequestsJob` for the victim stack (`app/models/shipit/commit.rb:366-386`); the job finds the victim's pending PR now satisfying `all_status_checks_passed?` and calls `merge_request.merge!`, which performs `stack.github_api.merge_pull_request(...)` against `victim-org`'s repository (`app/models/shipit/merge_request.rb:164-176`) — an unauthorized merge triggered entirely from `attacker-org`'s own valid webhook signature.

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
      return false unless head

      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
    end
