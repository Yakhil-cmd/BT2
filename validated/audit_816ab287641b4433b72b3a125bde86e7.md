### Title
Asset definer can repeatedly and instantly toggle the `spender_attested` attestor list to front-run transfers and unfairly block/allow spends - (File: validation.js)

### Summary
For `spender_attested` assets, the asset definer alone controls the trusted-attestor list via `asset_attestors` messages, and this list can be updated with no rate limit, cooldown, or advance-notice delay, exactly like the Napier `poolOwner` who could freely reset `protocolFeePercent` at will. A malicious definer can watch the mempool/DAG for an incoming transfer of their own asset, publish a new `asset_attestors` unit that removes the counterparty's (or output address's) current attestor from the trusted set right before the transfer stabilizes, cause the transfer/issue validation to fail (`"some output addresses are not attested"` / `"owner address is not attested"`), and then revert the attestor list back to the original value to keep attracting depositors — repeating this indefinitely with each transaction it dislikes.

### Finding Description
`validateAttestorListUpdate` only checks that the update is single-authored and signed by the asset's definer; it imposes no restriction on how often or how quickly the list may change: [1](#0-0) 

The only guard against abuse in the same unit is a check that a single unit cannot carry more than one `asset_attestors` update — it does not prevent the definer from posting new updates in every subsequent unit: [2](#0-1) 

The live attestor list used to gate transfers/issues is simply "the latest `asset_attestors` unit stable/visible before `last_ball_mci`", so any new update takes effect essentially as soon as it stabilizes, with no timelock: [3](#0-2) 

That current list is then used to filter attested addresses immediately before checking `spender_attested` conditions on both outputs and issuers, for every payment of the asset: [4](#0-3) [5](#0-4) 

Because the mapping from attestor set to "is address X attested" is derived from a separate `attestations` table that the trusted attestors (who can be, or be controlled by, the definer) also publish freely, the definer can effectively toggle who is allowed to send/receive the asset unit-by-unit, indistinguishable in cost/effort from Napier's `setFeeParameter`.

### Impact Explanation
This is directly analogous to the Napier finding: a semi-trusted party (there: pool owner adjusting `protocolFeePercent`; here: asset definer adjusting the attestor list) can front-run specific transfers to selectively deny or allow them, with the state fully reversible immediately afterward. For an ocore private-payment counterparty or AA relying on a `spender_attested` asset, this can cause:
- Fund freezing: a spend that the counterparty prepared and expects to succeed is unfairly bounced/rejected because the definer front-ran with a list update, trapping funds in limbo (unresolved payment) or forcing repeated re-negotiation.
- Unfair selective treatment: the definer can allow their own colluding counterparties through while blocking others transacting the same asset at the same time, without any of the affected users being able to detect or prevent it in advance, since there is no delay between posting the update and it taking effect for validation.

### Likelihood Explanation
The `asset_attestors` message requires only the definer's signature and normal unit-composition/inclusion in the DAG — no witness cooperation, no special privilege beyond being the definer of an already-issued asset. Given assets are commonly used for KYC/attestation-gated tokens, a dishonest issuer has an easy, cheap, and repeatable mechanism to grief specific counterparties or extract preferential treatment, exactly mirroring the "set fee low to attract, then front-run to raise it, then reset" pattern from the Napier report.

### Recommendation
Introduce a mandatory delay/cooldown between `asset_attestors` updates (e.g., minimum number of MCIs since the previous update) analogous to a timelock, and/or require attestor-list changes to be announced with an effective MCI in the future so that in-flight transfers validated against the previously known list cannot be invalidated by a same-block update. Additionally, consider disallowing an `asset_attestors` update from affecting payments whose `last_ball_mci` predates the update's own stabilization, closing the front-running window entirely.

### Proof of Concept
1. Definer `D` issues a `spender_attested` asset `A` with attestor set `{X}`. Alice is attested by `X` and is expecting to receive/send `A`.
2. Alice broadcasts a `payment` unit sending `A` to Bob.
3. `D`, seeing Alice's pending unit (or simply wanting to selectively block her), posts an `asset_attestors` unit for asset `A` removing `X` (or replacing it with an attestor `Y` that has not attested Alice), referencing this in `validateAttestorListUpdate` (`validation.js:2829`) which only checks `D`'s signature.
4. Once `D`'s update stabilizes before Alice's payment's `last_ball_mci`, `filterAttestedAddresses`/`arrAttestedAddresses` (via `storage.js:1917-1946`, `validation.js:2630-2641`) no longer consider Alice's output address attested, and her payment is rejected with `"some output addresses are not attested"`.
5. `D` reverts the attestor list back to `{X}` immediately after, restoring normal operation and repeating the same trick on the next transfer they want to selectively block, with no cost beyond one extra unit per toggle and no delay preventing it.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
