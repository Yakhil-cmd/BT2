Confirmed: the `here_come_the_walrus` fixture is an `ApiClient` scoped to the `shipit` stack (`stack: shipit`) with only `read:stack` permission, and the general `stacks` scoping in `Shipit::Api::BaseController#stacks` (`app/controllers/shipit/api/base_controller.rb:74-76`) enforces `Stack.where(id: current_api_client.stack_id)` when a client is stack-scoped. `CCMenuController` overrides `stack` to `Stack.from_param!(params[:stack_id])` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`), which looks up on the entire `Stack` table, ignoring `current_api_client.stack_id` entirely. ### Title
CCMenu API token scope bypass allows reading any stack's build/deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack directly from `Stack.from_param!(params[:stack_id])`, completely bypassing the per-`ApiClient` stack scoping (`current_api_client.stack_id`) that every other API controller enforces via `Shipit::Api::BaseController#stacks`/`#stack`. A `read:stack`-scoped `ApiClient` token that is supposed to be confined to a single stack can therefore be replayed against any other stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scope-respecting lookup: [1](#0-0) 

This enforces the binding: `stack the ApiClient token authorizes == stack it touches`, via `current_api_client.stack_id`. `ApiClient` supports exactly this kind of restriction, as shown by the `here_come_the_walrus` fixture which is scoped to the `shipit` stack: [2](#0-1) 

and is confirmed to be enforced elsewhere in the API (e.g. `StacksController#index` returns only 1 stack for this scoped client): [3](#0-2) 

However, `CCMenuController` overrides `stack` to bypass this scoping and only checks the coarse-grained permission list (`read:stack`), not the specific `stack_id` the token is bound to: [4](#0-3) 

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(operation, scope)`, i.e. it verifies the client has the `read:stack` permission string in its list, not that the specific stack being read matches `current_api_client.stack_id`: [5](#0-4) 

Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!(params[:stack_id])`, any valid, authenticated `ApiClient` token with `read:stack` — even one deliberately scoped to a single stack — can be used to fetch the CCMenu/build status (including latest deploy/rollback state) of *any* stack in the Shipit instance simply by changing the `stack_id` route segment.

Compounding this, `CCMenuController` also accepts the token via a plain query-string parameter instead of `Authorization: Basic`: [6](#0-5) 

Query-string tokens are more likely to leak (browser history, proxy/access logs, Referer headers, CI dashboard bookmarklets), which increases the likelihood this scope-bypass is actually exploitable in practice — an attacker who obtains a stack-scoped CCMenu token can trivially escalate to any other stack.

### Impact Explanation
This crosses exactly the trust boundary called out for this analysis: "a stack a token authorises versus a stack it touches." It results in an unauthorized read of stack state/deploy output for stacks the token holder was never granted access to, which the rubric classifies as High impact (unauthorized read of stack state / deploy output).

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` authentication token that carries `read:stack` (even one deliberately scoped to a single, low-sensitivity stack via `stack_id`, as produced by `Shipit::CCMenuUrlController#client`, which creates such tokens). No repository write access, GitHub credentials, or webhook secret is needed — only an existing, narrowly-scoped API token, which is routinely embedded in CI dashboard / CCTray URLs and thus more exposed than typical Basic-Auth-only tokens.

### Recommendation
Have `CCMenuController#stack` reuse the scoped lookup (`stacks.from_param!(params[:stack_id])`) from `BaseController` instead of querying `Stack` directly, so the `current_api_client.stack_id` restriction is enforced consistently across all API controllers.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id` = Stack A with permission `read:stack` (e.g. via `CCMenuUrlController#fetch`, which mints exactly such a token for a specific stack).
2. As an attacker who obtains this token (e.g. via the generated CCMenu URL), send:
   `GET /api/stacks/<owner>/<stack-B-repo>/<stack-B-env>/ccmenu?token=<stolen-token>`
3. `CCMenuController#authenticate_api_client` accepts the token; `require_permission :read, :stack` passes because the client has `read:stack`; `stack` resolves Stack B via `Stack.from_param!`, ignoring that the token's `stack_id` points to Stack A.
4. The response renders Stack B's build/deploy status XML, even though the token was only ever authorized for Stack A — confirmed by contrast with `StacksController#index`, which correctly restricts a stack-scoped client to its single authorized stack (`test/controllers/api/stacks_controller_test.rb:217-223`).
