This is a multi-tenant Shipit configuration (`Shipit.github_organizations`, `github_app_config`) where each organization has its own `webhook_secret` used solely to authenticate the *signing organization*, not the repository the webhook actually targets.

### Title
Webhook signature is verified against the payload's `organization`/`owner.login` field while all handlers act on the independently-attacker-controlled `repository.full_name` field, allowing cross-organization stack writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC signature using `repository_owner`, which is read from `params.dig('repository','owner','login')` or falls back to `params.dig('organization','login')`. Once the signature check passes, `create` dispatches the raw JSON body unchanged to `Shipit::Webhooks.for_event(event)` handlers (e.g. `PushHandler`), which resolve the target `Repository`/`Stack` via `Repository.from_github_repo_name(repository_name)`, where `repository_name = payload.dig('repository', 'full_name')`. These are two independently attacker-suppliable JSON fields with no cross-validation that they refer to the same repository.

### Finding Description
The binding that must hold is: `organization whose secret verified the signature == organization that owns the repository/stack being mutated`. In a multi-org Shipit deployment (`Shipit.github_app_config(organization)`, `TOP_LEVEL_GH_KEYS`), each organization has a distinct `webhook_secret` [1](#0-0) .

`verify_signature` computes the signing org from `repository.owner.login` (or `organization.login`) and asks `Shipit.github(organization: repository_owner)` for that org's secret to check the HMAC [2](#0-1) .

After the signature check succeeds, the entire raw JSON body — not just the `owner.login` field that was checked — is handed to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .

`Handler#stacks` and `Handler#repository_name` derive the acted-upon repository from `payload.dig('repository', 'full_name')`, an entirely separate JSON key from `repository.owner.login` used above [4](#0-3) . `PushHandler#process` then loads and triggers a sync for every non-archived stack under that resolved repository, on the branch named in `ref` [5](#0-4) , and `Repository.from_github_repo_name` performs a case-insensitive lookup keyed only on the `owner/name` split from that `full_name` string [6](#0-5) .

Because GitHub's real webhook payloads keep `repository.owner.login` and `repository.full_name` mutually consistent, this divergence is normally invisible. But nothing in the controller enforces that consistency — an attacker who legitimately controls an organization onboarded to this Shipit instance (and therefore possesses/controls that organization's own GitHub webhook secret, since they administer their own org's webhook settings) can send a POST to `/webhooks` with a body where `repository.owner.login` matches their own org (so the correct, attacker-known secret is fetched and the HMAC validates) but `repository.full_name` is set to a **different organization's** `owner/repo` string that also happens to be provisioned in the same Shipit instance.

### Impact Explanation
This breaks the "authenticated organization == written repository" binding. `PushHandler` would trigger `stack.sync_github(expected_head_sha: params.after)` against a victim organization's stack that the attacker does not own on GitHub, using an attacker-forged `after`/`ref`, effectively achieving unauthorized writes/deploy-pipeline actions against a repository the requester never authenticated for. This matches the High-severity bar (escalation into cross-repository writes / unauthenticated write into another org's stack state) as it requires no `ApiClient` token, no repository write access on GitHub for the victim repo, and no privileged Shipit account — only ownership of any single organization already configured in the same multi-tenant Shipit deployment.

### Likelihood Explanation
Requires a multi-tenant Shipit deployment (multiple `github_app_config` orgs sharing one instance) and requires the attacker to control at least one onboarded organization (a realistic scenario for shared/managed Shipit instances serving several teams/orgs). Given that precondition, exploitation needs only a single crafted HTTP POST with a valid signature computed over attacker-controlled bytes using the attacker's own known secret — no additional privilege escalation.

### Recommendation
After signature verification succeeds for `repository_owner`, re-validate that `payload.dig('repository', 'full_name')` (and/or `organization.login`) is consistent with (i.e., owned by) that same `repository_owner`/organization before dispatching to handlers, or key `Handler#stacks` lookups off the same field used for signature verification instead of a separate, unchecked `full_name` value.

### Proof of Concept
1. Attacker controls org `attacker-org`, which is configured in the shared Shipit instance with webhook secret `S_attacker` (known to the attacker, since they manage their own org's GitHub webhook settings).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `repository_owner` resolves to `"attacker-org"`; `Shipit.github(organization: "attacker-org")` returns the attacker's own `webhook_secret`, so `X-Hub-Signature` computed by the attacker validates [7](#0-6) .
4. `PushHandler` resolves `repository_name` = `"victim-org/victim-repo"` via `Handler#repository_name` [8](#0-7)  and calls `Repository.from_github_repo_name("victim-org/victim-repo")` [6](#0-5) , then invokes `stack.sync_github(expected_head_sha: <attacker-chosen-sha>)` on `victim-org`'s stacks [5](#0-4) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
