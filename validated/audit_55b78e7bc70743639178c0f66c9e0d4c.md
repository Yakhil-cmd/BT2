### Title
Hardcoded NEP-141 storage deposit amount in the eth-implicit Wallet Contract causes ERC-20-emulated transfers to unregistered recipients to fail for tokens with higher storage bounds - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Wallet Contract (used to emulate Ethereum EOAs/ERC-20 transfers on NEAR via `rlp_execute`) hardcodes a single NEP-141 `storage_deposit` amount for *all* fungible tokens instead of querying each token's actual `storage_balance_bounds`, mirroring the Moonwell bug class of a hardcoded amount that is not valid for all assets it is applied to.

### Finding Description
`NEP_141_STORAGE_DEPOSIT_AMOUNT` is a single constant, `1_250 * MICRO_NEAR` yoctoNEAR (0.00125 NEAR), explicitly documented as being used because it is "the one used by the standard NEP-141 implementation, which essentially all tokens use": [1](#0-0) 

This constant is used unconditionally, for every ERC-20-emulated transfer (`ft_transfer`) to a receiver that is not yet registered with the token's NEP-145 storage standard, regardless of which NEP-141 token contract `target` actually is: [2](#0-1) 

The contract does not call `storage_balance_bounds` on the actual token contract to determine the real minimum required deposit; it only checks `storage_balance_of` for the receiver and, if unregistered, blindly attaches the hardcoded amount to `storage_deposit`: [3](#0-2) 

This is directly analogous to the reported Moonwell issue: a single hardcoded amount (`initialMintAmount = 1 ether` there, `NEP_141_STORAGE_DEPOSIT_AMOUNT = 0.00125 N` here) is applied uniformly to different tokens whose actual required amounts can differ, even though the NEP-141/NEP-145 standard does not fix `storage_balance_bounds.min` to any specific constant — it is contract-defined and can legitimately exceed 0.00125 NEAR (e.g., contracts with larger per-account storage records, or that intentionally set higher bounds).

### Impact Explanation
If a target NEP-141 token contract's `storage_balance_bounds.min` exceeds the hardcoded 0.00125 NEAR, the `storage_deposit` call chained with `ft_transfer` will fail (insufficient deposit), causing the whole batched receipt (both actions target the same NEP-141 contract) to fail atomically. The user's ERC-20-emulated transfer therefore always fails for that token/receiver pair as long as the receiver remains unregistered, effectively denying an on-chain, user-reachable operation (a transaction submitted via `rlp_execute`) for any token whose storage cost exceeds the hardcoded assumption. This is an availability/correctness bug reachable directly from a transaction submitted through the Wallet Contract's public `rlp_execute` entry point — not a validator/node-only or mocked-only path.

Unlike the Moonwell case (which risked deploy failure), here the practical consequence is transaction failure for legitimate users interacting with certain NEP-141 tokens, not fund loss, since the deposit is only spent if the whole batched call (storage_deposit + ft_transfer) succeeds. Failed cross-contract calls do trigger a refund path for `caller_deposit` in `rlp_execute_callback`, limiting the immediate loss-of-funds risk for the top-level attached deposit; however, the comment in the code explicitly acknowledges the assumption that "in the standard NEP-141 implementation it is impossible to have `Some` storage balance, but have it be insufficient to transact" is being relied upon, showing awareness of this fragile hardcoded-amount assumption for the failed-deposit case.

### Likelihood Explanation
Likelihood is limited by the fact that this only manifests for NEP-141 token contracts whose `storage_balance_bounds.min` genuinely exceeds 0.00125 NEAR. This is a real (not purely theoretical) risk since the NEP-141/145 standard does not restrict this bound to a fixed constant, but is somewhat mitigated by the intended deployment context assumed by the code's own comments ("essentially all tokens use" this value). No further investigation was possible to confirm which specific mainnet NEP-141 tokens (if any) currently use higher bounds; this is a design-level constant limitation, not a demonstrated on-chain failure.

### Recommendation
Replace the hardcoded `NEP_141_STORAGE_DEPOSIT_AMOUNT` with a per-token amount obtained via an on-chain `storage_balance_bounds` call to the actual `target`/`token_id` before performing `storage_deposit`, similar to how the recommended Moonwell fix specifies `initialMintAmount` per token in configuration rather than using one global constant. If the extra cross-contract call is undesirable for gas/complexity reasons, at minimum bound and validate the returned `storage_balance_bounds.min` against a safety ceiling (already partially motivated by the existing comment about "malicious token contracts with very high storage_balance_bounds") rather than silently assuming a fixed value works universally.

### Proof of Concept
Conceptual PoC (not executed, based on code paths read):
1. Deploy a NEP-141 token contract whose `storage_balance_bounds.min` is set higher than `1_250 * 10^18` yoctoNEAR (0.00125 NEAR) — permitted by the NEP-145 standard.
2. Deploy the Wallet Contract to an eth-implicit account and fund it.
3. Submit an RLP-encoded ERC-20 `transfer` transaction via `rlp_execute` targeting this token contract, sending to a receiver account not yet registered with the token.
4. Execution reaches `nep_141_storage_balance_callback`, sees `storage_balance_of` returns `None`, and issues `storage_deposit` with the hardcoded `NEP_141_STORAGE_DEPOSIT_AMOUNT` chained with `ft_transfer`: [2](#0-1) 
5. Because the attached deposit is less than the token's actual `storage_balance_bounds.min`, the `storage_deposit` action panics, causing the whole batched receipt to fail and the `ft_transfer` never executes — the user's transfer intent is unconditionally denied for this token.

/// This storage deposit value is the one used by the standard NEP-141 implementation,
/// which essentially all tokens use. Therefore we hard-code it here instead of doing
/// the extra on-chain call to `storage_balance_bounds`. This also prevents malicious
/// token contracts with very high `storage_balance_bounds` from taking lots of $NEAR
/// from eth-wallet-contract users.
const NEP_141_STORAGE_DEPOSIT_AMOUNT: NearToken = NearToken::from_yoctonear(1_250 * MICRO_NEAR);
const NEP_141_STORAGE_DEPOSIT_GAS: Gas = Gas::from_tgas(5);
