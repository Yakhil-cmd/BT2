### Title
`Api::BaseController#identify_user` trusts unauthenticated `X-Shipit-User` header for actor attribution on state-changing API operations - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
`Api::BaseController#current_user`/`#identify_user` resolve the acting user purely from the client-supplied `X-Shipit-User` header, with no cryptographic or session-based verification, and `require_permission!` only checks the token's scoped permissions via `current_api_client.check_permissions!`, never that `current_user` corresponds to the token holder. Any request bearing a valid but low-privilege `ApiClient` token can set `X-Shipit-User` to an arbitrary existing login and have that identity attributed as the actor of deploys, rollbacks, task triggers, and locks.

### Finding Description
The broken binding: `token-authenticated identity (current_api_client.creator)` should equal `attributed actor identity (current_user)`, but nothing in the engine enforces this equality.

- `authenticate_api_client` sets `@current_api_client` from HTTP Basic auth token verification: `app/controllers/shipit/api/base_controller.rb:48-61`.
- `identify_user` independently derives `current_user` solely from `request.headers['X-Shipit-User']`, doing a case-insensitive DB lookup with no signature, session, or relation to the authenticated `ApiClient`: `app/controllers/shipit/api/base_controller.rb:69-72`.
- `require_permission!` calls only `current_api_client.check_permissions!(operation, scope)`: `app/controllers/shipit/api/base_controller.rb:82-84`, and `ApiClient#check_permissions!` (`app/models/shipit/api_client.rb:38-45`) only checks the token's `permissions` array against `operation:scope` — it never touches `current_user` or the header.
- `current_user` (header-derived) is then used directly for attribution in state-changing actions:
  - `DeploysController#create` → `stack.trigger_deploy(commit, current_user, ...)` (`app/controllers/shipit/api/deploys_controller.rb:25`)
  - `RollbacksController#create` → `active_task.abort!(aborted_by: current_user, ...)` / `deploy.trigger_rollback(current_user, ...)` (`app/controllers/shipit/api/rollbacks_controller.rb:25,28`)
  - `TasksController#trigger`/`#abort` → `stack.trigger_task(..., current_user, ...)` / `task.abort!(aborted_by: current_user)` (`app/controllers/shipit/api/tasks_controller.rb:21,30`)
  - `LocksController#create`/`#update` → `stack.lock(params.reason, current_user)` (`app/controllers/shipit/api/locks_controller.rb:15,24`)

Attacker request: any low-privilege but valid `ApiClient` token with `deploy:stack`/`lock:stack` permission for a target stack, sent with header `X-Shipit-User: <maintainer-login>` where a `User` row with that login exists (e.g., synced from GitHub org membership). The token authenticates the request and passes `require_permission!`, but the created `Deploy`/`Task`/`Lock` record is attributed to the maintainer's `User` row, not the token's actual creator/holder.

Existing guards do not close this gap: `verify_signature`/webhook signature checks are irrelevant here (this is the token-authenticated API path, not webhooks); `require_permission!` checks only the `ApiClient`'s own permission list; `ExplicitParameters` schemas validate request params but not the header-derived actor; there is no code anywhere cross-referencing `current_api_client.creator` with `current_user`.

### Impact Explanation
An attacker holding any valid, even minimally-privileged, `ApiClient` token can cause deploys, rollbacks, task executions, and stack locks to be falsely attributed to an arbitrary existing Shipit/GitHub user. This is a genuine identity/attribution forgery for the actions listed in the audit rules ("unauthorized deploy, rollback" and false attribution of a "commit, task"), affecting whichever stack the token has permission on. This is repeatable per request and does not require any secret beyond a legitimately issued (even scoped-down) API token — it can be used to frame maintainers for deploys/rollbacks they did not initiate, undermining audit trails and any authorization logic that might trust `current_user` downstream (e.g., notifications, review/approval flows keyed to actor identity).

### Likelihood Explanation
Preconditions: attacker must already possess a valid `ApiClient` token with at least one action permission (`deploy:stack`, `lock:stack`, etc.) scoped to the target stack, and a `User` row for the target login must exist. Note that per the stated threat model ("They hold no ... `ApiClient` token"), an attacker with zero tokens cannot exploit this directly — this finding applies once *any* token (even a narrowly scoped, legitimately-issued one for an unrelated integration) is attacker-controlled or leaked, which is a materially lower bar than compromising `api_clients_secret` or a maintainer session. Given that scoped tokens are commonly distributed to CI systems/bots with narrower trust than a human maintainer, the identity-spoofing capability meaningfully exceeds what the token's permissions were intended to grant.

### Recommendation
Do not derive `current_user` for attribution purposes from an unauthenticated request header. Either remove `X-Shipit-User`-based attribution entirely for token-authenticated API requests, or bind it to the `ApiClient`: only honor `X-Shipit-User` if it matches `current_api_client.creator`, or require a distinct signed/authenticated channel (e.g., OAuth-authenticated user session behind the API) to set `current_user`. At minimum, `require_permission!` (or a new before_action) should verify that the header-supplied identity is authorized to act as itself in this context (e.g., only trusted internal callers with a specific elevated permission may set `X-Shipit-User`).

### Proof of Concept
Add to `test/controllers/api/deploys_controller_test.rb` (or a new integration test):
```ruby
test "#create attributes deploy to arbitrary X-Shipit-User rather than the token's real user" do
  attacker_client = shipit_api_clients(:some_low_priv_client_with_deploy_stack_permission)
  victim = shipit_users(:walrus) # a maintainer with an existing login

  authorization = "Basic #{Base64.strict_encode64(attacker_client.authentication_token + '--x')}"
  post :create, params: { stack_id: @stack.to_param, sha: @commit.sha },
       headers: { 'HTTP_AUTHORIZATION' => authorization, 'X-Shipit-User' => victim.login }

  deploy = @stack.deploys.last
  # Binding under test: token identity should equal attributed identity
  assert_not_equal attacker_client.creator_id, deploy.user_id,
    "current_user attribution diverged from authenticated token identity"
  assert_equal victim.id, deploy.user_id,
    "deploy was falsely attributed to the victim login supplied via unauthenticated header"
end
```
