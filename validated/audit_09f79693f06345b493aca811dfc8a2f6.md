### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while sync target is selected from the independently-controlled `repository.full_name` field, allowing cross-organization stack sync - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App / webhook secret to validate the HMAC signature by reading `repository.owner.login` (falling back to `organization.login`) out of the *unverified-at-that-point* JSON body [1](#0-0) . Once the signature check passes, every handler resolves the target `Stack` by looking up `Repository.from_github_repo_name` on a completely separate field, `repository.full_name` [2](#0-1) . Nothing enforces that `repository.owner.login` and the owner segment embedded in `repository.full_name` refer to the same organization.

### Finding Description
In a multi-organization Shipit deployment (explicitly documented and supported, see "Using Multiple Github Applications" in `docs/setup.md`), each organization has its own `webhook_secret`. `Shipit.github(organization: repository_owner)` selects the app/secret keyed by the *owner* field, then `verify_webhook_signature` just checks that the raw body HMACs correctly under that org's secret [3](#0-2) .

Since HMAC only proves "this exact byte string was produced by someone holding OrgA's webhook secret," and that byte string is entirely attacker-authored JSON (an attacker who owns/administers an installation of the Shipit GitHub App on their own `OrgA` knows `OrgA`'s webhook secret), the attacker can freely set every other field, including `repository.full_name`, to point at a *different* organization's repository (`OrgB/victim-repo`) while keeping `repository.owner.login` (or `organization.login`) equal to `OrgA` so the correct secret is selected. The signature will validate successfully because the whole crafted body was legitimately signed with `OrgA`'s secret, yet the handler that actually executes (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, `MembershipHandler`, PR handlers) resolves the `Stack`/`Repository`/`Commit` targets from `repository.full_name`/`sha`, not from the authenticated owner [4](#0-3) [5](#0-4) .

This is the same trust-binding break as the report's analog: "peer's declared address is acted upon but not what was authenticated/verified." Here, "the organization whose secret authenticated the request" ≠ "the repository the handlers act on."

### Impact Explanation
An attacker who controls (or has installed the Shipit GitHub App for) one organization/repository in a multi-tenant Shipit instance can forge webhook events attributed to any other org's repository tracked by the same instance:
- Forge `push` events to trigger `stack.sync_github(expected_head_sha: ...)` for a victim stack, forcing sync at an attacker-chosen SHA.
- Forge `status` events to inject fabricated commit statuses (`state`, `context`, `target_url`, `description`) onto arbitrary commits by `sha`, which can flip CI-gating logic used by `ci.require`/deploy safety checks.
- Forge `check_suite` events to trigger `schedule_refresh_check_runs!` on arbitrary stacks/commits.

Because deploy eligibility and continuous-deployment gating in Shipit rely on synced commit/CI state, forged `status`/`push` events can influence which commit is considered deployable, which is a cross-repository/cross-tenant integrity break reachable without holding any Shipit session or `ApiClient` token — only knowledge of one's own (attacker-owned) org's webhook secret, i.e., zero elevated privilege relative to the victim tenant.

### Likelihood Explanation
Requires the deployment to host multiple GitHub organizations behind a single Shipit instance (an explicitly documented, supported configuration) and requires the attacker to control a GitHub App installation (their own org) whose webhook events reach the same Shipit instance. Given that constraint, exploitation is trivial: craft one JSON body, sign it with the attacker's own known secret, and send it — no race conditions, no additional bypass needed.

### Recommendation
After signature verification, re-derive `repository_owner` used for signature selection and cross-check it against the owner segment of `repository.full_name` (and `organization.login` where applicable) before dispatching to handlers; reject the webhook if they don't match. Alternatively, bind webhook secrets per-repository/per-installation rather than trusting an attacker-supplied `owner.login` field to pick the verification key.

### Proof of Concept
1. Attacker owns `OrgA`, which has the Shipit GitHub App installed with known `webhook_secret = SECRET_A`. Shipit is also tracking `OrgB/victim-repo`.
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefattackersha",
  "repository": {
    "owner": {"login": "OrgA"},
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and verifies successfully against `SECRET_A` [6](#0-5) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` [2](#0-1)  and calls `stack.sync_github(expected_head_sha: "deadbeefattackersha")` on `OrgB`'s stack, despite the request never being signed by `OrgB`'s secret.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
