### Title
Cross-stack read of task/deploy state via CCMenu API endpoint ignoring `ApiClient#stack_id` scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController#stack` overrides the base controller's scoped lookup with an unscoped `Stack.from_param!(params[:stack_id])`, and permission enforcement (`require_permission!` → `ApiClient#check_permissions!`) only checks the permission string, never that `current_api_client.stack_id == stack.id`. A CCMenu token minted for stack A (via `CCMenuUrlController#fetch`) can therefore be replayed against any other stack B by simply changing `stack_id` in the URL.

### Finding Description
The security binding that should hold is: `current_api_client.stack_id == stack.id` for every record served by an `Api::BaseController` subclass. This is enforced in the base class via
`app/controllers/shipit/api/base_controller.rb:74-80`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

But `Api::CCMenuController` shadows `stack` with an unscoped lookup:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`require_permission :read, :stack` only calls `current_api_client.check_permissions!('read', 'stack')`, which merely checks that `"read:stack"` is present in the client's `permissions` array — it never compares `stack_id`: [3](#0-2) [4](#0-3) 

`CCMenuUrlController#fetch` mints a token for the current user's stack-scoped `ApiClient` (`create_with(permissions: %w[read:stack]) ... .find_or_create_by!(creator: current_user, ...)`) and embeds it in a shareable URL: [5](#0-4) 

Exploit: an attacker who has this shared CCMenu URL for stack A (token belongs to an `ApiClient` with `stack_id == A.id`) issues `GET /stacks/:B/ccmenu.xml?token=<A's token>`. `authenticate_api_client` (overridden in `Api::CCMenuController`) resolves the client via `ApiClient.authenticate(params[:token])` with no stack check at all: [6](#0-5) 
Then `stack` resolves B unscoped, `require_permission!` passes because `"read:stack"` is in the token's permission list, and `show` renders `stack.deploys_and_rollbacks.last` for B — data belonging to a stack the token was never authorized for: [7](#0-6) 

No other guard intervenes: `verify_signature`/webhook checks are irrelevant to this HTTP GET path, and `ExplicitParameters` schemas aren't used here.

### Impact Explanation
Any holder of a valid CCMenu URL for one stack can enumerate/read build status, last deploy SHA, running/locked state, and CI-menu metadata (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`) for **any** stack in the Shipit instance by only changing the `stack_id` path segment — an unauthenticated (relative to the target stack) cross-tenant read of deploy/task state. This matches the "High - unauthenticated read of stack state" category. It does not grant write/deploy capability (the token's actual permission is limited to `read:stack`), and it doesn't leak GitHub tokens or secrets, so it is not Critical, but it is repeatable against arbitrary stacks with no rate limiting and no additional secrets required.

### Likelihood Explanation
Preconditions: the attacker must obtain any one legitimate CCMenu token for some stack (these tokens are, by the feature's own design, meant to be pasted into third-party CI dashboard tools and shared/forwarded — the question's stated threat scenario of a "shared/forwarded link" is realistic and matches the intended low-friction use of CCMenu URLs). Given that, the attack is a single unauthenticated GET request with a modified `stack_id`; no further secrets, sessions, or GitHub credentials are needed. This is trivial to reproduce and fully repeatable across all stacks in the instance.

### Recommendation
In `app/controllers/shipit/api/ccmenu_controller.rb`, remove the overriding `stack` method (and rely on the inherited `stacks.from_param!` from `Api::BaseController`), so lookups are scoped by `current_api_client.stack_id` exactly like every other API controller. Also consider having `check_permissions!` explicitly verify `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` as a defense-in-depth measure.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token scoped to stack A cannot read stack B's ccmenu data" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.create!(owner: 'foo', name: 'bar'), branch: 'main')
  Deploy.create!(stack: stack_b, until_commit: stack_b.commits.create!(sha: '1'*40), since_commit: stack_b.commits.create!(sha: '0'*40), status: 'success')

  client_scoped_to_a = ApiClient.create!(stack: stack_a, creator: shipit_users(:walrus), name: 'CCMenu Client', permissions: %w[read:stack])

  get :show, params: { stack_id: stack_b.to_param, token: client_scoped_to_a.authentication_token }

  # Binding under test: current_api_client.stack_id == stack.id
  assert_equal stack_a.id, client_scoped_to_a.stack_id
  refute_equal client_scoped_to_a.stack_id, stack_b.id

  # If the bug exists, the request still succeeds and returns stack_b's data,
  # proving the binding was not enforced.
  assert_response :ok
  project = Hash.from_xml(response.body)['Projects']['Project']
  assert_equal stack_b.to_param, project['name']
end
```
Expected (fixed) behavior: this request should raise `RecordNotFound`/404 because `stacks.from_param!` would filter to `Stack.where(id: stack_a.id)`, which does not include `stack_b`.
