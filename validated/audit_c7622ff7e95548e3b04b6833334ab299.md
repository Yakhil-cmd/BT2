### Title
Instant-balance (non-time-weighted) snapshot lets an attacker skew system-parameter and witness-list voting - (File: main_chain.js)

### Summary
`countVotes()` in `main_chain.js` weighs every governance vote (op_list / threshold_size / base_tps_fee / tps_interval / tps_fee_multiplier) by the voter's **current stable balance at the exact MCI when the vote count is executed**, not by a time-weighted average of the balance held while the vote was outstanding. Any unprivileged address can trigger this count at a moment of its choosing by posting a `system_vote_count` message, so an attacker can move a large stable balance into a previously-voted address right before the count runs, capture the disproportionate weight, and move the funds away immediately afterward — exactly the "vote-then-retract-around-a-snapshot-boundary" pattern described in the GaugeController report, but applied to Obyte's on-chain system-variable/witness voting instead of gauge weights.

### Finding Description
Any address can cast a durable vote for a system subject via a `system_vote` message, which is merely logged with the vote's own value/timestamp [1](#0-0) . Any address (not just the voter, and not an AA) can later trigger tallying by posting a `system_vote_count` message; this is accepted by validation as long as one hasn't already been included in the unit [2](#0-1) . When the unit carrying that message becomes stable, `countVotes()` runs and computes each voter's weight as their **current** stable, unspent, good balance at that instant: [3](#0-2) 

This balance is aggregated with `SUM(balance)` per candidate/value and used to pick the top OPs (witness list) or the balance-weighted median for numeric parameters: [4](#0-3) 

Nothing in this logic checks how long the address has held the balance, nor does it use any time-weighted-average construct — it is a single point-in-time snapshot, structurally identical to `GaugeController._calculateReward` using instantaneous `g.weight` instead of `TimeWeightedAverage.calculateAverage`. The only "time" filter that exists (`since_timestamp`) restricts which **vote records** are eligible by their own timestamp [5](#0-4) , but it does nothing to prevent the *balance* used for weighting from being freshly and briefly acquired just before the count fires. An attacker who cast a vote long ago (so it passes the `since_timestamp` filter) can, immediately before triggering `system_vote_count`, receive a large stable transfer into the same voting address, wait for it to stabilize, fire the count, and then move the funds elsewhere in the very next unit — the count has already captured the inflated balance.

Because the attacker unilaterally controls the `system_vote_count` trigger unit (any address may post it, subject only to `objValidationState.bHasSystemVoteCount` uniqueness and post-v4-upgrade MCI gating) [2](#0-1) , the timing of the snapshot is entirely attacker-chosen, mirroring the "vote right before period boundary" precision-timing exploit condition from the external report.

### Impact Explanation
This lets a low-capital attacker with brief access to a large stable balance (e.g., a self-funded round-trip transfer, or coordination with an exchange withdrawal window) dominate:
- **`op_list` (witness list) elections** — determining which addresses become order-providing witnesses (OPs), directly affecting main-chain construction and stability for every node on the network.
- **Network economic parameters** (`base_tps_fee`, `tps_interval`, `tps_fee_multiplier`, `threshold_size`) — these govern unit fees and TPS congestion pricing; a skewed median could push fees to extremes, degrading the network's ability to confirm new units economically, or make spam cheap.

Since every node computes `countVotes()` deterministically from the same DB state, this does not itself cause node disagreement, but it does let an attacker unfairly and cheaply steer protocol-critical parameters that affect confirmation cost/throughput for the entire network — a concrete, network-wide, low-cost governance-manipulation vector.

### Likelihood Explanation
Any address can post `system_vote` and `system_vote_count` messages — no privileged role is required [2](#0-1) . The attacker fully controls when the tallying unit is posted, and thus controls the exact MCI at which balances are snapshotted. The only cost is obtaining a large stable balance for a short window (the time needed for a transfer to stabilize plus one more unit to move it away), which is realistic via self-funding, flash-style round trips, or timed large deposits/withdrawals — no protocol-level barrier prevents this.

### Recommendation
Weight votes by a time-weighted average of the voter's balance over the voting/eligibility window (analogous to `TimeWeightedAverage.calculateAverage` in the report), rather than the instantaneous balance at the moment `countVotes()` executes. Concretely:
- Require balances used in `bal_rows`/`voter_balances` to reflect holdings averaged (or held continuously) since the vote's own timestamp (or since `since_timestamp`), not merely "currently stable and unspent."
- Alternatively, require a minimum holding duration (e.g., balance must have been stable for N days before the count MCI) before it counts toward `SUM(balance)`.
- Consider decoupling the timing of `system_vote_count` from attacker control, e.g. only allowing counts at fixed, pre-scheduled MCIs rather than on-demand by any address.

### Proof of Concept
1. Attacker address `A` casts `system_vote` for subject `tps_fee_multiplier` (or `op_list`) with a small balance, timestamp `t0`, so it is within the eventual `since_timestamp` window computed in `countVotes` [5](#0-4) .
2. Shortly before triggering the count, attacker sends a very large amount of bytes into address `A` from another address they control; they wait until that output is `is_stable=1, sequence='good'`.
3. Attacker posts a unit containing `system_vote_count` for the same subject; this is valid per `validation.js` [2](#0-1)  and queues the subject for tallying once its MCI stabilizes [6](#0-5) .
4. When that MCI stabilizes, `countVotes()` runs `bal_rows`, which sums `A`'s currently-stable balance (now inflated) [3](#0-2) , and this weight decides the median/top-vote outcome [7](#0-6) .
5. Immediately after, attacker moves the large balance out of `A`. The system variable / witness list has already been updated using the momentary, now-departed balance, permanently affecting network parameters until the next vote count.
