### Title
CCMenu API endpoint bypasses ApiClient stack-scoping, letting any stack-scoped `read:stack` token read any stack's status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` authenticates callers with an `ApiClient` token and requires the `read:stack` permission, but it resolves the target stack with `Stack.from_param!(params[:stack_id])` instead of going through the shared, scope-enforcing `stacks`/`stack` helpers used by every other API controller. This breaks the equality that should hold between "the stack(s) an `ApiClient` token is authorized for" and "the stack the request actually touches."

### Finding Description
Every other endpoint under `Shipit::Api::BaseController` resolves the target stack through: [1](#0-0) 
which restricts the resolvable stacks to `current_api_client.stack_id` when the token is scoped to a single stack (`stack_id?`).

`CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 

The permission check performed via `require_permission :read, :stack` only verifies the string `"read:stack"` is present in the token's `permissions` array; it never inspects `stack_id`: [3](#0-2) 

So the only place the `stack_id` restriction is actually enforced across the codebase is the `stacks` scope in `BaseController`, and `CCMenuController` is the one controller that does not call it. Any `ApiClient` bearing the `read:stack` permission - even one that was created and is expected to be usable for exactly one stack - can retrieve the CCMenu XML status (`deploys_and_rollbacks.last`, deploy status, lock state) for **any** `stack_id` in the system by simply changing the `stack_id` query/path parameter.

This mirrors the report's root cause pattern: a security check ("is this delegated/scoped?") is correctly implemented in one code path but the actual execution path consumes a different, unchecked value/route, so the intended restriction silently never applies.

### Impact Explanation
`CCMenuController#show` renders deploy/rollback history, lock status, and success/failure state for a stack (`app/views/shipit/ccmenu/project.*`, `show.html.erb`). This is an unauthenticated (relative to the target stack) read of stack state/deploy output that the token was never authorized to view. Combined with `CCMenuUrlController`, which mints tokens via query-string URLs meant to be embedded in third-party CI dashboards (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`) and accepts the token via `params[:token]` (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`) rather than a header, these tokens are especially likely to leak (browser history, referrer headers, shared dashboards) and, once leaked, grant far more than the single stack they were generated for. This matches the in-scope "High" category: unauthenticated read of stack state/deploy output via escalation beyond the token's authorized scope.

### Likelihood Explanation
Exploitation requires possessing any valid `ApiClient` token that carries `read:stack` (including a deliberately narrow, single-stack-scoped one, or a leaked CCMenu URL token) — no additional privileges, session, or GitHub credentials are needed. Because CCMenu tokens are designed to be embedded in URLs for external tools, they are more exposure-prone than typical Basic-Auth API tokens, raising the realistic likelihood of an attacker obtaining one and pivoting it to read arbitrary stacks.

### Recommendation
Have `CCMenuController#stack` reuse the scoped `stacks` collection instead of calling `Stack.from_param!` directly, e.g. `stacks.from_param!(params[:stack_id])`, so `current_api_client.stack_id` scoping (when present) is enforced identically to every other API endpoint.

### Proof of Concept
1. Create (or obtain) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to stack A (e.g., via `ApiClient.create!(stack: stack_a, permissions: ['read:stack'], creator: user, name: 'ccmenu')`), or use a token minted by `CCMenuUrlController` for stack A.
2. Call `GET /api/1/stacks/:stack_a_id/ccmenu.xml?token=<token>` — succeeds as intended.
3. Call `GET /api/1/stacks/:stack_b_id/ccmenu.xml?token=<token>` for an unrelated stack B that the token was never granted access to.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `stacks`), the request succeeds and returns stack B's deploy/rollback status, proving the stack-scoping the token was issued with is not enforced on this endpoint.

Note: I could not find a UI path in `Shipit::ApiClientsController` that lets an operator set `stack_id` when creating a client (its `create_params` only permits `:name` and `permissions`) — stack-scoped tokens appear to be created only programmatically (as `CCMenuUrlController#client` does, though notably without setting `stack:` there either). This detail is based on the code available to the index; a Devin session with full repository access could confirm whether any other code path (e.g., seeds, rake tasks, or admin console usage) sets `ApiClient#stack_id` in practice.
