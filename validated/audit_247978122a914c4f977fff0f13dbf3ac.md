The CVE-2021-27935 issue concerns a web-application session mechanism (AdGuardHome storing a password hash inside a browser cookie, letting an attacker who steals the cookie offline-bruteforce the password). This class of bug requires a stateful HTTP session/cookie holding a derived credential secret that authorizes further privileged actions.

Polkadot SDK has no analogous mechanism reachable by an unprivileged network attacker:
- Account authentication is via asymmetric keypairs and signatures, not passwords/cookies; the keystore password only protects the local on-disk key file and is never transmitted or stored in a client-facing token [1](#0-0) .
- The RPC methods that touch keys/passwords (`author_insertKey`, `author_rotateKeys`, `author_hasKey`, etc.) are explicit "unsafe" methods gated by `check_if_safe`, meaning they are disabled on any endpoint exposed to untrusted/external callers by default [2](#0-1) .
- There is no session/cookie construct in the runtime, FRAME pallets, or node RPC layer that persists a password-derived hash to a client for reuse as a bearer credential.

Since there is no attacker-reachable entry point that stores or exposes a password-derived secret in a client-held token, no concrete Polkadot SDK analog to this CVE class exists.

impl KeystoreInner {
	/// Open the store at the given path.
	///
	/// Optionally takes a password that will be used to encrypt/decrypt the keys.
	fn open<T: Into<PathBuf>>(path: T, password: Option<SecretString>) -> Result<Self> {
		let path = path.into();
		fs::create_dir_all(&path)?;

		Ok(Self { path: Some(path), additional: HashMap::new(), password })
	}

	/// Get the password for this store.
	fn password(&self) -> Option<&str> {
		self.password.as_ref().map(|p| p.expose_secret()).map(|p| p.as_str())
	}
