### Title
API token scoped to one stack can read any stack's build status via the CCMenu API endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` tokens can be scoped to a single stack via `stack_id`, and `Shipit::Api::BaseController` enforces this scoping by resolving `stack`/`stacks` through `current_api_client.stack_id`. `Shipit::Api::CCMenuController`, however, overrides `#stack` to look the stack up directly from `Stack.from_param!(params[:stack_id])`, bypassing that scoping entirely, so a token authorized for stack A can be used to read build/lock status of stack B.

### Finding Description
The intended binding is: **stack a token authorises == stack a token can touch**. `Shipit::ApiClient` supports being scoped to one stack: `belongs_to :stack, optional: true` [1](#0-0) , and this scoping is enforced generically in `Shipit::Api::BaseController` via:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

This is confirmed as the security boundary by the test "an api client scoped to a stack will only see that one stack", which asserts a scoped client only sees 1 stack out of many via `StacksController#index` [3](#0-2) .

`Shipit::Api::CCMenuController`, which requires only the generic `read:stack` permission (not scoped to a particular stack), overrides `#stack` to bypass the `stacks` scoping helper entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(operation, scope)`, which checks that the client's permission list includes `"read:stack"` — it never checks which stack the client is scoped to: [5](#0-4) .

Before/after the attack:
- Before: an `ApiClient` with `stack_id = A` and `permissions: ["read:stack"]` can, per the design encoded in `BaseController#stacks`, only resolve/read stack A through this endpoint family.
- After (using CCMenuController): the same token, presented with `params[:stack_id] = B`, resolves `stack` to `Stack.from_param!(B)` with no ownership check, and `#show` renders `stack.deploys_and_rollbacks.last` (lock state, last build status/label, etc.) for stack B: [6](#0-5) .

The `CCMenuController` also supports query-string token authentication (`ApiClient.authenticate(params[:token])`) rather than only HTTP Basic auth [7](#0-6) , which is how these scoped tokens are typically distributed via `CCMenuUrlController` (creates an `ApiClient` with `permissions: %w[read:stack]`, embeds `authentication_token` in a URL) [8](#0-7) . This URL-embedded, low-privilege, single-stack-intended token is exactly the credential this bug turns into a read-any-stack token.

### Impact Explanation
This is a cross-stack unauthorized read: a token meant to authorize read access to one stack's CCMenu status can be used, unmodified, to read another stack's build/lock status by changing the `stack_id` request parameter. This matches the "High" impact category of "unauthenticated read of stack state, task streams or deploy output" (the token here is a low-privilege, easily distributed CCMenu URL token rather than a fully privileged Shipit account, and it is being used entirely outside its intended authorization scope).

### Likelihood Explanation
Any holder of a legitimate `read:stack`-scoped `ApiClient` token (e.g. a CCMenu URL as generated by `CCMenuUrlController`, which is designed to be embedded in third-party CI dashboard tools and is not treated as highly secret) can trivially exploit this by substituting a different `stack_id` in the request URL — no special access or race condition is required, and the misuse is purely a parameter substitution on an otherwise ordinary, unprivileged API request.

### Recommendation
Have `Shipit::Api::CCMenuController#stack` resolve the stack through the scoped `stacks` helper from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot read stacks other than the one it is scoped to.

### Proof of Concept
1. Create (or have) an `ApiClient` scoped to stack A (`stack_id = A.id`) with `permissions: ["read:stack"]`, e.g. via `CCMenuUrlController#fetch` for stack A, obtaining `authentication_token`.
2. Issue: `GET /api/stacks/:B_param/ccmenu.xml?token=<token-for-A>` where `B_param` is a different stack's identifier that this token was never granted access to.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unscoped (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`), and `require_permission :read, :stack` only validates the generic permission string, the request succeeds and returns stack B's CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, lock state, etc.), even though the token is only meant to authorize stack A.
