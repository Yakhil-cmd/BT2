Based on the code I was able to examine, I found a concrete analog to the `_abs` bug class: a verification step keyed on one payload field while the actual state-mutating logic is keyed on a different, independently-attacker-controlled field within the *same unsigned-until-verified* payload.

### Title
Webhook organization used for signature verification is decoupled from the repository the payload actually mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to use for HMAC verification based on `repository_owner`, which is read directly out of the *unverified* JSON body (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`). Event handlers, however, resolve the `Stack`/`Repository` to mutate using other fields of that same untrusted body (e.g. `repository.full_name`). Because both fields live inside attacker-supplied JSON, an operator of *any* organization onboarded to this Shipit instance can forge a payload whose `repository.owner.login` names their own org (so the signature check passes with a secret they legitimately possess) while other repository-identifying fields point at a different, victim organization's stack.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is computed from the raw, not-yet-verified body: [2](#0-1) . This value is used purely to pick *which* per-org `webhook_secret` (configured in `config/secrets*.yml`, see [3](#0-2) ) to HMAC-check against.

The binding the design relies on is:
`organization whose secret verified the signature == organization/repository that the payload's handler will act on`

That equality is never enforced. `Hook#create` dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` with the entire raw, attacker-supplied `params` hash (unfiltered) [4](#0-3) . Handlers (e.g. push, status, check_suite) independently look up the target `Stack`/`Repository` using fields like `repository.full_name` from that same JSON body, which is not cross-checked against `repository_owner`. Since the attacker controls the entire raw JSON body and computes the HMAC themselves (using a webhook secret belonging to an org they legitimately administer — because they installed the Shipit GitHub App on their own org/repo, which is a normal, unprivileged onboarding action, not a credential leak), they can set:
- `repository.owner.login` (or `organization.login`) = their own org, so `Shipit.github(organization: repository_owner).verify_webhook_signature` succeeds with their own secret, while
- `repository.full_name` (and other repo-identifying fields used deeper in the handler) = a victim org/repo that they do not control.

This is structurally identical to the `_abs` root cause: a value is computed/derived for one purpose (sign verification pathway keyed by `repository_owner`) but a *different, independently-forgeable* value in the same structure drives the actual effectful behavior (which `Stack`/`Repository` gets mutated), with no assignment/consistency check tying the two together.

### Impact Explanation
If exploitable, this lets an attacker who has legitimately onboarded any organization to the Shipit instance (a low-privilege, unprivileged-from-the-victim's-perspective action) forge webhook events against a **different** organization's repositories/stacks whose webhook secret they never had. Depending on which event/handler is reached, this could:
- Inject forged CI `status`/`check_suite` results for a victim's commits, which the merge queue (`MergeRequest#all_status_checks_passed?`, `StatusChecker`) and deploy gating logic rely on to decide whether a commit is deployable/mergeable — directly enabling an **unauthorized deploy or merge** into a repository the attacker does not own [5](#0-4) .
- Inject forged `push` events, corrupting the victim stack's commit history / triggering sync jobs.

This satisfies the "High" bar (unauthorized deploy/merge) or potentially higher if it can be chained into a merge on the victim repo.

### Likelihood Explanation
Low-to-Medium. It requires the attacker to control at least one organization/GitHub App installation registered with the same Shipit instance (multi-tenant deployments configuring several orgs in `secrets.yml`, as shown by the sample config listing multiple orgs) — this is plausible for SaaS-style or shared internal deployments of Shipit but not for single-tenant installs where only one org's secret exists. I was not able to fully verify, within the remaining tool budget, whether downstream handlers (`push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`) resolve the `Stack` via `repository.full_name` versus some field that is actually cross-validated elsewhere (e.g., a `Repository.find_by!(owner:, name:)` check that would coincidentally re-derive from `repository.owner.login`, closing the gap) — I could not read those files' contents before running out of iterations, so this remains **unconfirmed** and should be verified by inspecting `app/models/shipit/webhooks/handlers/push_handler.rb`, `status_handler.rb`, and `check_suite_handler.rb` directly, plus `Shipit::Repository`'s lookup key(s).

### Recommendation
Re-derive the repository/organization used to locate the `Stack`/`Repository` inside each handler strictly from the *same* field that was authenticated by `verify_signature` (or better, pass the authenticated `repository_owner`/org into the handler context and assert it matches the repository being mutated before proceeding), rather than trusting other fields of the same JSON body independently.

### Proof of Concept
Conceptual (unverified end-to-end due to inability to inspect handler internals in this session):
1. Attacker installs/owns a GitHub App organization `attacker-org` on this Shipit instance, obtaining its `webhook_secret`.
2. Attacker POSTs to `/webhooks` with body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  ...
}
```
   with `X-Github-Event: status` and `X-Hub-Signature` computed with `attacker-org`'s webhook secret.
3. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and verifies successfully.
4. The `status` handler processes the payload against `victim-org/victim-repo`'s stack/commit, injecting a forged passing status, if my (unverified) reading of the handler's repository-resolution logic is correct.

**Caveat:** Because I could not read `push_handler.rb`/`status_handler.rb`/`check_suite_handler.rb` contents in this session, I cannot confirm with certainty that they don't independently re-validate `repository.owner.login` against `repository_owner`/the authenticated org before mutating a stack. This should be confirmed by a follow-up review of those three files (and `Shipit::Repository`/`Stack.from_github_repo_name`-style lookups) before treating this as fully proven.
