### Title
Uncaught exception in `chash.isChashValid()` on malformed c-hash input reachable via `isValidChash()` / `isValidAddressAnyCase()` - ([File: chash.js])

### Summary
`chash.isChashValid()` decodes an address/asset c-hash and then unconditionally calls `separateIntoCleanDataAndChecksum(binChash)`, which throws an uncaught `Error` if the decoded bit-length is not exactly 160 or 288. This mirrors the reported Hiero `Bucket.keyEquals()` class of bug: a length-mismatch in a low-level decode/compare routine that is not defensively checked before use, causing an unhandled exception instead of a controlled `false`/rejection.

### Finding Description
`isChashValid()` only wraps the initial base32/base64 decode step in `try/catch`; any exception from the decode is caught and converted to `false`: [1](#0-0) 

However, the subsequent call to `separateIntoCleanDataAndChecksum(binChash)` is **not** guarded, and that function throws a bare `Error` whenever the bit-length of the decoded buffer is not exactly 160 or 288: [2](#0-1) 

`isChashValid()` is invoked through `validation_utils.isValidChash()`, which is used in two different ways:
- `isValidAddress()` first enforces a strict regex `/^[A-Z2-7]{32}$/` before calling `isValidChash`, which constrains the input to the valid base32 alphabet, making `base32.decode` reliably return a 20-byte (160-bit) buffer.
- `isValidAddressAnyCase()` calls `isValidChash(address, 32)` directly, **without** the charset/case regex guard: [3](#0-2) 

Because `isValidAddressAnyCase` skips the strict character-class check that `isValidAddress` performs, any 32-character string (mixed case, or characters accepted leniently by the `thirty-two` base32 decoder) can reach `base32.decode()` and yield a decoded buffer whose length differs from the expected 20 bytes. This propagates into `buffer2bin()` and then `separateIntoCleanDataAndChecksum()`, which throws `Error("bad length=...")` instead of returning `false`. This is structurally the same failure pattern as the referenced Hiero commit: a length-derived comparison/decode helper that assumes well-formed input and throws instead of failing safely, when called from a path that lacks the same input sanitation as its sibling function (`isValidAddress`).

### Impact Explanation
If this uncaught exception occurs on a code path invoked during unit/message validation (e.g., any place that uses `isValidAddressAnyCase` on attacker-supplied address strings without its own try/catch), it results in an unhandled exception thrown synchronously out of the validation call stack. Depending on where it surfaces, this can crash the Node.js process handling validation (killing the node) or abort processing of a legitimately-formed unit due to a poison-pill malformed address field elsewhere in the same batch — i.e., a scenario that can make the network unable to confirm new units if triggered on validating nodes, or cause inconsistent behavior between callers that do vs. don't wrap the call in try/catch (potential validity/stability disagreement).

### Likelihood Explanation
Exploitability depends on finding a call site that (a) uses `isValidAddressAnyCase` or otherwise calls `isValidChash`/`isChashValid` without the `/^[A-Z2-7]{32}$/` guard used in `isValidAddress`, and (b) does not itself wrap the call in a `try/catch`. I was not able to fully enumerate and confirm, within the tool budget, every caller of `isValidAddressAnyCase` and whether any of them process unauthenticated, attacker-controlled 32-character strings without an enclosing try/catch — this needs further investigation (e.g., in `definition.js`, `aa_validation.js`, `wallet_defined_by_addresses.js`, all of which reference `isValidAddress`-family functions).

### Recommendation
Harden `chash.isChashValid()` to fail safely (`return false`) instead of throwing when `separateIntoCleanDataAndChecksum` or `buffer2bin` encounter unexpected lengths, by wrapping the entire body (after decode) in the same `try/catch` that currently only covers the decode step. Additionally, audit all callers of `isValidAddressAnyCase`/`isValidChash` to ensure none process untrusted external input without either the strict regex pre-check used in `isValidAddress`, or an enclosing try/catch.

### Proof of Concept
Not able to construct a concrete end-to-end PoC (a specific unauthenticated call site invoking `isValidAddressAnyCase` on unsanitized attacker input) within the available investigation budget; this requires further tracing of all callers of `isValidAddressAnyCase`/`isValidChash` in `definition.js`, `aa_validation.js`, `wallet_defined_by_addresses.js`, and `light.js` to confirm a reachable, unguarded call path from a posted unit/message.

function separateIntoCleanDataAndChecksum(bin){
	var len = bin.length;
	var arrOffsets;
	if (len === 160)
		arrOffsets = arrOffsets160;
	else if (len === 288)
		arrOffsets = arrOffsets288;
	else
		throw Error("bad length="+len+", bin = "+bin);
	var arrFrags = [];
	var arrChecksumBits = [];
	var start = 0;
	for (var i=0; i<arrOffsets.length; i++){
		arrFrags.push(bin.substring(start, arrOffsets[i]));
		arrChecksumBits.push(bin.substr(arrOffsets[i], 1));
		start = arrOffsets[i]+1;
	}
	// add last frag
	if (start < bin.length)
		arrFrags.push(bin.substring(start));
	var binCleanData = arrFrags.join("");
	var binChecksum = arrChecksumBits.join("");
	return {clean_data: binCleanData, checksum: binChecksum};
}
