## Analysis

The go-ipfs/go-car bug class is: **untrusted attacker-controlled content processed by the tool triggers unbounded memory allocation**, leading to node crash/DOS. Looking for the closest analog in `git-sync`, the relevant path is not git's own object parsing (that would be a "dependency-only" bug in the `git` binary, out of scope), but git-sync's own command-output capture layer, which imposes no bound on the amount of data it buffers in memory from a subprocess whose output volume is influenced by attacker-controlled repository content (e.g., `.gitmodules` submodule fan-out).

### Title
Unbounded in-memory buffering of `git` subprocess output enables memory-exhaustion DOS from attacker-controlled repository content - (File: pkg/cmd/cmd.go)

### Summary
`git-sync`'s command runner captures the entire stdout/stderr of every invoked `git` subprocess into unbounded, growable `bytes.Buffer` objects, with no cap on size. Because several `git-sync` code paths (in particular submodule handling, which is enabled by default via `--submodules=recursive`) run `git` subcommands whose output volume is driven by attacker-controlled repository content (e.g., the number of entries in `.gitmodules`, or verbose/error output per submodule), a party with push access to the synced repository can craft content that forces `git-sync` to buffer an arbitrarily large amount of data in memory during a single sync attempt, causing memory exhaustion of the sidecar process.

### Finding Description
The subprocess execution helper `runWithStdin` in `pkg/cmd/cmd.go` allocates two empty `bytes.Buffer`s and attaches them as `cmd.Stdout`/`cmd.Stderr` with no maximum size, then reads the buffered contents into strings after the command completes: [1](#0-0) 

Every `git` invocation performed by `repoSync.Run`/`RunWithStdin` goes through this same unbounded-buffer path: [2](#0-1) 

During each sync, `configureWorktree` runs `git submodule update --init [--recursive]` against the untrusted, attacker-influenced content of the just-fetched commit (its `.gitmodules` file and submodule tree), with `submodules=recursive` being the **default** mode: [3](#0-2) [4](#0-3) 

An attacker with write access to the tracked repository (the "untrusted user input" analog to a malicious CAR file) can commit a `.gitmodules` file referencing a very large number of submodule entries (or deeply nested/recursive submodule chains). When `git submodule update --init --recursive` processes this, git itself emits per-submodule status/progress/error text to stdout/stderr. Because `git-sync` buffers that entire stream without any size limit before returning, the memory consumed by a single `SyncRepo` call scales with the amount of attacker-controlled submodule content, not with any bound set by `git-sync`.

### Impact Explanation
A malicious contributor to the synced repository can cause the `git-sync` sidecar container to consume large amounts of memory during a sync attempt, potentially triggering an OOM kill of the container. Because `git-sync` retries syncing on the configured `--period` and will re-attempt the same ref/commit, this can result in persistent sync denial (crash-loop) once the malicious commit becomes the target ref, satisfying the "persistent sync denial" impact criterion.

### Likelihood Explanation
This requires:
- The attacker to have push access to a branch/tag/ref that `git-sync` is configured to track (the same threat model as "untrusted user input" pushed to a repo).
- Default configuration is sufficient, since `--submodules` defaults to `recursive`.
No special git-sync flags beyond defaults are required. The primary variable is how much output git itself will produce for a maliciously large `.gitmodules`/submodule tree, and how much RAM is available to the sidecar container (commonly small in Kubernetes sidecar deployments), making this plausible for constrained deployments.

### Recommendation
- Impose a maximum size on `cmd.Stdout`/`cmd.Stderr` capture in `pkg/cmd/cmd.go` (e.g., wrap the buffers with an `io.LimitedWriter` or discard/truncate output beyond a configurable cap) rather than using unbounded `bytes.Buffer`.
- Consider adding a limit on the number of submodules processed per sync, or documenting/adding a flag to cap `--depth`/submodule recursion fan-out.
- Ensure memory/resource limits are documented so operators size the sidecar's memory request/limit for worst-case verbose output.

### Proof of Concept
1. Attacker with push access commits a `.gitmodules` file to the tracked branch containing e.g. 50,000 submodule entries (paths/URLs can be dummy or unreachable — git still emits output for each attempted resolution).
2. `git-sync`, configured with default `--submodules=recursive`, fetches this commit and calls `configureWorktree`, which runs `git submodule update --init --recursive`.
3. `git` emits proportionally large amounts of status/error text for each of the 50,000 entries to stdout/stderr.
4. `pkg/cmd/cmd.go`'s `runWithStdin` buffers all of this output in memory (unbounded `bytes.Buffer`) before `SyncRepo` returns, causing memory usage to spike in proportion to attacker-controlled input, potentially OOM-killing the sidecar on constrained memory limits. [5](#0-4) [6](#0-5)

```go
func runWithStdin(ctx context.Context, log logintf, cwd string, env []string, stdin, command string, args ...string) (string, string, error) {
	cmdStr := cmdForLog(command, args...)
	log.V(5).Info("running command", "cwd", cwd, "cmd", cmdStr)

	cmd := exec.CommandContext(ctx, command, args...)
	if cwd != "" {
		cmd.Dir = cwd
	}
	if len(env) != 0 {
		cmd.Env = env
	}
	outbuf := bytes.NewBuffer(nil)
	errbuf := bytes.NewBuffer(nil)
	cmd.Stdout = outbuf
	cmd.Stderr = errbuf
	cmd.Stdin = bytes.NewBufferString(stdin)

	start := time.Now()
	err := cmd.Run()
	wallTime := time.Since(start)
	stdout := strings.TrimSpace(outbuf.String())
	stderr := strings.TrimSpace(errbuf.String())
	if ctx.Err() == context.DeadlineExceeded {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, ctx.Err(), stdout, stderr)
	}
	if err != nil {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, err, stdout, stderr)
	}
	log.V(6).Info("command result", "stdout", stdout, "stderr", stderr, "time", wallTime)

	return stdout, stderr, nil
```
