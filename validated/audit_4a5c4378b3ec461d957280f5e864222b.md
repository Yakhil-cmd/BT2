### Title
Malicious swap venue can piggyback unrelated token transfers on the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy entrypoints accept caller-supplied swap-route bytes and execute the configured router while the account owner’s authorization remains active for the enclosing call. A route-selected venue can request a token transfer from that caller to an attacker; simulation records it as an additional child authorization, and an approving signer authorizes theft of unrelated wallet assets. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` authenticates `caller`, verifies ownership or delegation, and passes the caller-controlled `swap` bytes into `swap_tokens`. [3](#0-2)  `swap_tokens` invokes `router.execute_strategy(controller, amount_in, swap)` inside the guarded external call. [1](#0-0) 

The controller correctly scopes its own invoker authorization to `token_in.transfer(controller, router, amount_in)`, but that does not isolate the account owner’s root authorization from contracts reached by the route. [1](#0-0)  The harness demonstrates that a route-selected pool can call `token.transfer(alice, attacker, amount)` for a token unrelated to the protocol markets. [4](#0-3)  Simulation records that transfer as a child of Alice’s `swap_collateral` authorization, and enforcing mode executes it when the returned tree is signed. [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker can steal arbitrary SAC balances held by the account owner, not merely the collateral being swapped. [7](#0-6)  The demonstrated loss moves Alice’s entire unrelated wallet token balance while still delivering fair swap output, so the strategy’s measured-output and final-risk checks do not detect the theft. [8](#0-7)  This is theft of user funds, although the malicious child invocation must appear in and be covered by the signed authorization tree. [6](#0-5) 

### Likelihood Explanation
A single unprivileged attacker can deploy the malicious venue, construct route bytes that reach it, and induce a victim to submit `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` with those bytes. [9](#0-8)  The normal signing flow makes the injected transfer visible in simulation, so exploitation requires the wallet or user to approve an unexpected child invocation rather than silently bypassing authorization. [10](#0-9)  This limits the issue to Medium severity rather than a direct unauthorized-drains vulnerability. [11](#0-10) 

### Recommendation
Do not allow strategy routes to invoke unvetted pool or token addresses while a user’s root authorization is active; enforce a governance-controlled venue/pool allowlist or otherwise constrain route execution to known adapters and destinations. [12](#0-11)  Until that boundary exists, clients must decode route payloads and reject any simulated authorization tree containing children beyond the expected input pull—for controller strategies, an unexpected caller child such as an unrelated `transfer` must abort signing. [13](#0-12) [14](#0-13) 

### Proof of Concept
1. Alice supplies USDC and holds `WALLET_BALANCE` of an unrelated token; the configured router is given enough ETH to return fair output. [15](#0-14) 
2. The attacker encodes a route whose venue stores `(victim=alice, wallet_token, to=attacker, amount)`. [16](#0-15) 
3. Alice calls:

```rust
swap_collateral(
    alice,
    account_id,
    usdc_hub_asset,
    50_000_000_000,
    eth_hub_asset,
    malicious_route,
)
```

The controller authorizes only its own exact controller-to-router input transfer before executing the route. [1](#0-0) 
4. During the nested venue call, the malicious contract executes `token::Client::new(&wallet_token).transfer(&alice, &attacker, &amount)`. [4](#0-3) 
5. Simulation attaches that unrelated transfer as a child of Alice’s `swap_collateral` authorization; after Alice signs that tree, her wallet balance becomes zero and the attacker receives `WALLET_BALANCE`. [5](#0-4) [6](#0-5)

    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((

            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };

        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
