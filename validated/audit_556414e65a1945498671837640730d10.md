### Title
Unauthenticated null pointer dereference / node crash via malformed `private_payment` message - ([File: network.js])

### Summary
`network.js`'s `handleOnlinePrivatePayment()` dereferences `arrPrivateElements[0].payload.denomination` before validating that `payload` exists on the first private element. Any peer (or paired device via hub, since the same function is invoked with `bViaHub=true`) can send a `private_payment`/`private_payments` justsaying message whose head chain element omits the `payload` field, causing an immediate unhandled `TypeError: Cannot read properties of undefined (reading 'denomination')`, analogous to the MXIT null-pointer-dereference crash in CVE-2016-2365 where malformed protocol data triggers a crash before proper field validation.

### Finding Description
`handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks)` is the entry point that processes an incoming private-payment chain (used for private/hidden asset payments) sent by a network peer or forwarded via the hub from a paired device: [1](#0-0) 

The only check performed before dereferencing fields is `ValidationUtils.isNonemptyArray(arrPrivateElements)`, which merely confirms the array is non-empty — it does not validate that `arrPrivateElements[0]` is an object nor that it has a `payload` property:
```
if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
    return callbacks.ifError("private_payment content must be non-empty array");

var unit = arrPrivateElements[0].unit;
var message_index = arrPrivateElements[0].message_index;
var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
```
If the attacker sends `arrPrivateElements = [{}]` (or `[{unit:"...", message_index:0}]` without a `payload` field), `arrPrivateElements[0].payload` is `undefined`, and accessing `.denomination` on `undefined` throws a `TypeError`. This happens synchronously inside the justsaying/message handler, before any of the try/catch wrapping used elsewhere in the codebase (e.g. `handleMessageFromHub`'s `doHandle()` wraps the whole switch in `try/catch`, but `handleOnlinePrivatePayment` on the peer-to-peer path in `network.js` is called directly from message dispatch without an equivalent guard around this specific access).

This is directly reachable two ways:
1. Directly from any connected peer sending the `private_payment` justsaying message, per `sendPrivatePaymentToWs`/`sendJustsaying(ws, 'private_payment', arrPrivateElements)` convention that peers use to send private payment chains to each other: [2](#0-1) 
2. Via a paired device / hub forwarding path, where `wallet.js`'s `handlePrivatePaymentChains` validates each chain element's structure (`isNonemptyObject(e.payload)` etc.) before calling `network.handleOnlinePrivatePayment`: [3](#0-2) [4](#0-3) 
However, the direct peer-to-peer `private_payment` justsaying path in `network.js` does not perform the same payload-shape validation that `wallet.js`'s `handlePrivatePaymentChains` does, so an attacker connecting directly as a peer (not necessarily a paired device) can hit the unguarded code path in `handleOnlinePrivatePayment` with a bare `{}` element.

### Impact Explanation
A `TypeError` thrown synchronously in a message-handling code path that is not wrapped in a try/catch will propagate as an uncaught exception in Node.js, crashing the process (denial of service) unless some higher-level generic handler intervenes. This matches the "network unable to confirm new units" / node-crash impact class allowed by the rules: a successful exploit takes the target node offline, preventing it from validating and relaying units, and if repeated against multiple nodes could disrupt network availability.

### Likelihood Explanation
Likelihood is high: the attack requires only sending a single, trivially-crafted justsaying message (`private_payment` with one array element lacking a `payload` field) to a full node acting as a network peer; no authentication, private key, or special network position is required beyond being able to open a normal outbound/inbound peer connection, which is the ordinary operating mode of ocore nodes.

### Recommendation
Validate the full shape of `arrPrivateElements[0]` (and each element) before accessing nested fields in `handleOnlinePrivatePayment`, e.g. require `isNonemptyObject(arrPrivateElements[0])`, `isNonemptyObject(arrPrivateElements[0].payload)`, and valid types for `unit`/`message_index`/`output_index`/`denomination` before using them — mirroring the stricter checks already present in `wallet.js`'s `handlePrivatePaymentChains`. Additionally wrap the message-dispatch call site in `network.js` with a try/catch (as is done for `handleMessageFromHub`) so that any residual malformed-input exception is converted into a graceful `ifError` response rather than crashing the process.

### Proof of Concept
1. Connect to a target ocore node as a peer over its websocket interface.
2. Send a justsaying message:
```json
{"subject":"private_payment","body":[{}]}
```
(or via the batched form `{"subject":"private_payments","body":{"chains":[[{}]]}}` if routed through a permissive path that skips `wallet.js`'s stricter shape checks)
3. On the direct `private_payment` handling path, `handleOnlinePrivatePayment` executes `arrPrivateElements[0].payload.denomination`, throwing `TypeError: Cannot read properties of undefined (reading 'denomination')`, crashing/terminating the node process if uncaught at that call site.
