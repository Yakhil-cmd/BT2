### Title
Unallowlisted pull-request-label keys are merged verbatim into `ReviewStack#env`, letting a fork PR inject arbitrary environment variable names (e.g. `PYTHONPATH`) into the `dependencies.override` step - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an environment-variable *key* into the stack's env hash with no allowlist, and `LabelCapturingHandler#capture_labels` persists label names taken verbatim from the webhook body. `TaskCommands#env`/`DeployCommands` merge `@stack.env` into the environment used for `DeploySpec#dependencies_steps!` (the `dependencies.override` section), so a label such as `pythonpath` becomes `PYTHONPATH=true` in the child process environment when `Command#start` calls `PTY.spawn`.

### Finding Description
The broken binding: the code assumes `ReviewStack#env` produces only *safe, project-defined* variables, i.e. `stack.env.keys ⊆ deploy_spec.machine_env.keys ∪ {SHIPIT_USER, EMAIL, ...}`. In reality:

- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does:
```ruby
super.merge(pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" })
```
with **no key allowlist** — any label name becomes an env-var key. [1](#0-0) 

- `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` straight from the webhook JSON body, with only a `String` type check in `ExplicitParameters` — no format/charset validation (test explicitly asserts emoji labels are accepted). [2](#0-1) [3](#0-2) 

- `TaskCommands#env` (used by `install_dependencies`, which builds the `dependencies.override` `Command`s) merges `@stack.env` unfiltered:
```ruby
super.merge(@stack.env).merge('SHIPIT_USER'=>..., ...).merge(deploy_spec.machine_env).merge(@task.env)
``` [4](#0-3) 

- This is materially different from the explicit-input paths (`deploy_spec.filter_deploy_envs`, `filter_rollback_envs`, `TaskDefinition#filter_envs`) which run user-supplied env through `EnvironmentVariables#permit`, an explicit allowlist that raises `NotPermitted` for any key not in `deploy_variables`/`rollback_variables`/task `variables`. [5](#0-4) [6](#0-5) 

- `Command#start`/`unbundled_env` pass the merged hash directly into `PTY.spawn(unbundled_env, ...)` with no further filtering: [7](#0-6) 

Exploit flow: an unprivileged fork-PR author with `provisioning_behavior=allow_all` opens/labels their own PR with a label whose name uppercases to `PYTHONPATH` (e.g. `pythonpath`). `LabelCapturingHandler` (subscribed to `pull_request` webhook events, no signature bypass needed beyond normal webhook delivery) persists this label onto the `PullRequest` record tied to the `ReviewStack`. On the next `dependencies.override` run (or any `TaskCommands`/`DeployCommands`-derived command), `PYTHONPATH=true` is injected into the child process environment. Since the `dependencies.override` step's `chdir` is the checked-out working directory of the fork branch — content the attacker fully controls — the attacker can additionally commit a directory literally named `true` in their branch containing a malicious Python module; when any dependency-install python invocation performs an unqualified `import` matching a name shadowed in that directory, attacker code executes on the Shipit deploy host.

Existing guards do not stop this: `EnvironmentVariables#permit`'s allowlist only guards the explicit, user-submitted `env` params on the Deploy/Task/Rollback controllers, not the label-derived keys merged by `ReviewStack#env`; there is no equivalent allowlist call in `review_stack.rb` or `task_commands.rb` for this merge.

### Impact Explanation
An unprivileged fork-PR author can inject arbitrary environment-variable *names* (fixed value `"true"`) into every command run against their own review stack, including the `dependencies.override`/install steps that execute on the shared Shipit deploy host. Combined with control over the checked-out working directory content, this can escalate to code execution during dependency installation (e.g. via `PYTHONPATH`, or other tool-specific env vars like `NODE_OPTIONS`, `RUBYOPT`, `LD_PRELOAD` depending on what the `dependencies.override`/`deploy` steps invoke) — a Critical RCE-on-deploy-host class issue. Blast radius is limited to the attacker's own review stack/PR (their own checked-out branch/environment), but that is enough since the commands execute with the Shipit deploy host's privileges (GitHub tokens, shared filesystem, etc.), not inside an isolated per-PR sandbox.

### Likelihood Explanation
Requires `provisioning_behavior=allow_all` (or `allow_with_label`/labeling in general) enabling review stacks for the repository — a common configuration per `docs/review_stacks.md`. Attacker cost is trivial: open a PR from a fork and add one label with the desired uppercase-producing name (labels are freely creatable/settable by any collaborator with issue/PR write access on their own fork's PR, and label names are copied through GitHub webhooks with no filtering by Shipit). No secrets or elevated GitHub permissions are needed. It is repeatable at will against the attacker's own review stack for as long as it stays active.

### Recommendation
Do not merge pull-request label names directly as environment-variable keys in `ReviewStack#env`. At minimum: (1) restrict merged label-derived keys to project-declared variable names (route them through `EnvironmentVariables#permit` against `deploy_spec` variable definitions, mirroring `filter_deploy_envs`/`filter_rollback_envs`), or (2) namespace/prefix label-derived keys (e.g. `SHIPIT_LABEL_<NAME>`) so they cannot collide with sensitive interpreter/loader environment variables, and reject label names matching a denylist of dangerous variables (`PYTHONPATH`, `LD_PRELOAD`, `NODE_OPTIONS`, `RUBYOPT`, etc.).

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (or a new minitest)
test "#env does not allow labels to set unsafe environment variable keys" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["pythonpath"]

  env = stack.env

  refute_includes env.keys, "PYTHONPATH",
    "fork PR label should not be able to set PYTHONPATH for dependencies.override"
end

test "dependencies.override command inherits attacker-controlled PYTHONPATH from a PR label" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["pythonpath"]
  task = stack.trigger_continuous_delivery

  command = Shipit::TaskCommands.new(task).install_dependencies.first

  # demonstrates the broken binding: PYTHONPATH reaches the spawned process env
  assert_equal "true", command.env["PYTHONPATH"]
end
```
Both assertions demonstrate the equality `stack.env.keys` (attacker-influenced, unbounded) vs. the intended invariant `stack.env.keys ⊆ allowlisted deploy/machine variables` — the first test shows the invariant is currently violated (it will fail against current code), and the second shows the exact value reaching `Command#env`/`PTY.spawn`.
