### Title
Cross-repository status webhook updates foreign Stack's Commit via unscoped `Commit.where(sha:)` lookup enabling unauthorized deploy - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves commits with `Commit.where(sha: params.sha)` [1](#0-0)  without scoping to the repository that the webhook's signature authenticated, unlike `CheckSuiteHandler` which correctly scopes lookups through `stacks.where(branch: ...)` derived from the payload's `repository.full_name` [2](#0-1) . Because `sha` is a content-addressed value that can be identical across repositories that share git history (forks), a status event legitimately signed for repository A's org can update the `Commit` row (and thus `status`, `deployable?`) belonging to a completely different Stack B whose repository happens to contain the same commit sha.

### Finding Description
The intended binding is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` — i.e., a status/check webhook should only be able to mutate commits that belong to the stack(s) of the repository that produced (and cryptographically signed) the webhook.

`WebhooksController#verify_signature` validates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the same untrusted payload (`params.dig('repository', 'owner', 'login')`) [3](#0-2) . This only proves the webhook was really sent by GitHub for *some* repository owned by that org — it does not constrain which `sha` values the payload may reference or which `Commit` records may be touched afterward.

`Handler#stacks` correctly derives the authorized repository scope via `Repository.from_github_repo_name(repository_name)&.stacks` [4](#0-3) , and `CheckSuiteHandler` uses it to constrain the check-run update to that repository's own stacks/branches. However, `StatusHandler#process` bypasses this scoping entirely and queries the global `Commit` table by `sha` alone:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Exploit flow: an attacker owns/controls a GitHub repository (fork) that Shipit tracks as some Stack A, and that repository shares commit history with an unrelated Stack B (upstream or another fork) tracked by Shipit for a different tenant. The attacker sets a commit status (they have write access to their own repo) on a sha that is also present as a `Commit` in Stack B (inherited via shared fork ancestry, cherry-pick, or rebase-preserved sha). GitHub sends a legitimately signed `status` webhook for the attacker's own repo/org. `verify_signature` passes because the signature is genuine for that org. `StatusHandler#process` then updates **every** `Commit` row across the entire database matching that sha — including Stack B's — via `commit.create_status_from_github!(params)`, which ultimately affects `status`/`deployable?` used by `Commit#schedule_continuous_delivery`:

```ruby
def schedule_continuous_delivery
  return unless deployable? && stack.continuous_deployment? && stack.deployable?
  ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)
end
``` [5](#0-4) 

`deployable?` depends directly on the mutated status: `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [6](#0-5) . If a forged "success" status flips this to true on Stack B's already-existing undeployed commit while `continuous_deployment?` is enabled, an unauthorized deploy job for Stack B is scheduled — despite the webhook never having been sent for, or signed for, Stack B's repository.

None of the existing guards prevent this: `verify_signature` only validates org/signature match for the payload's *own* declared repository, not the set of `Commit`s that get touched; `drop_unhandled_event` and `ExplicitParameters` only validate presence/shape of `sha`/`state`, not repository ownership of the sha; and `force_github_authentication`/`User#authorized?` are irrelevant since this is an unauthenticated webhook endpoint, not a session-based one.

### Impact Explanation
A payload authenticated for repository/org A results in a database write (`Commit#status` via `create_status_from_github!`) on a `Commit` belonging to a foreign Stack B's repository, and can trigger `ContinuousDeliveryJob` for Stack B — an unauthorized deploy triggered by a party who never authenticated against Stack B's org/repository. This matches the Critical category: "a payload for one repository mutating another's stack, commit... or an unauthorized deploy." The attack is repeatable against any Stack whose tracked repository shares commit-sha history with a repository the attacker controls (a common situation for actively-forked open source projects on Shipit), and it requires no privileged Shipit role, API token, or GitHub secret — only ordinary push/status-setting access to a repo the attacker owns.

### Likelihood Explanation
Preconditions: (1) Shipit must be configured for the attacker's own org so that `Shipit.github(organization: repository_owner)` resolves a valid `GithubApp` and hence `verify_signature` passes for the attacker's own webhook — this is normal/expected for any tracked repository, not a special privilege; (2) a target Stack B must actually contain a `Commit` row with a sha equal to one reachable in the attacker's repository — realistic for forks of the same upstream, shared branches, or cherry-picked/rebase-preserved commits; (3) Stack B must have `continuous_deployment?` enabled for the full deploy trigger, though even without that precondition the cross-tenant `status` row mutation itself (unauthorized write to another tenant's `Commit`) is already a boundary violation. Attacker cost is low: control of one GitHub repository plus the ability to set a commit status via the GitHub API on a sha within their own repo's reachable history is sufficient, and the action is repeatable at will.

### Recommendation
Scope `StatusHandler#process` the same way `CheckSuiteHandler` does: resolve commits only through `stacks` (i.e., `Commit` records belonging to `Repository.from_github_repo_name(repository_name)&.stacks`), for example `stacks.flat_map(&:commits).where(sha: params.sha)` or an equivalent join that filters by the payload-derived repository before calling `create_status_from_github!`, so a status webhook can never mutate a `Commit` outside the repository whose signature was verified.

### Proof of Concept
Minitest plan (models/controller test, no live GitHub):
1. Create two Stacks, `stack_a` (repository `attacker/fork`) and `stack_b` (repository `victim/upstream`), each with a `Commit` row sharing an identical `sha` value "deadbeef..." (simulating shared fork history).
2. Enable `continuous_deployment?` on `stack_b` and ensure `stack_b`'s commit is otherwise `deployable?` pending a success status (no prior status, `pending?` true, so `deployable?` false initially — assert `stack_b.commits.first.deployable?` is false and `ContinuousDeliveryJob` has not been enqueued).
3. Post a `status` webhook payload whose `repository.full_name == 'attacker/fork'` and `sha == 'deadbeef...'`, `state: 'success'`, through `WebhooksController#create` with a valid signature computed for `attacker`'s org secret (stub `Shipit.github(organization: 'attacker')` to return a `GithubApp` whose `verify_webhook_signature` returns true).
4. Assert the equality that should hold: `commit.stack.repository.full_name == payload['repository']['full_name']` for every `Commit` mutated by `StatusHandler#process`. Show this is violated: assert `stack_b.commits.first.reload.status.success?` becomes true even though `stack_b.repository.full_name != 'attacker/fork'`.
5. Assert `stack_b.commits.first.deployable?` is now true and that `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob.perform_later(stack_b)` — confirming an unauthorized deploy trigger for `stack_b`, a tenant that never authenticated the webhook.
