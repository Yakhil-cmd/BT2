### Title
Autonomous Agents can receive fixed-denominations (NFT-like) assets but can never send them out, permanently freezing the funds - (File: aa_composer.js)

### Summary
An Obyte Autonomous Agent (AA) address accepts payments of any asset type into its balance, including "fixed_denominations" assets (indivisible, denomination-based assets analogous to NFTs). However, when the AA composes a response unit, any `payment` message that references a `fixed_denominations` asset is silently dropped before the unit is built, so the AA can never issue an output of that asset type. Since an AA address has no private key and is controlled solely by its oscript logic, any fixed-denominations asset sent to it is permanently stuck.

### Finding Description
When an AA is triggered, `updateInitialAABalances` in `aa_composer.js` credits the AA's `aa_balances` for every asset present in `trigger.outputs`, with no distinction for fixed-denomination assets. [1](#0-0) 

When the AA subsequently tries to compose a response (`sendUnit`), each non-base payment message is checked against the asset's info. If the asset is `fixed_denominations`, the code explicitly skips completing the payment payload with a comment "will skip it later": [2](#0-1) 

Later, the composer explicitly filters out any payment message whose asset is a fixed-denominations asset, removing it entirely from the outgoing unit: [3](#0-2) 

If, after this filtering, no messages remain, the trigger is treated as a "successful empty response" — the AA simply eats the funds and does nothing: [4](#0-3) 

Unlike private assets, which are explicitly bounced ("sending private asset from AA") to reject the trigger, fixed-denominations assets are not rejected — they are accepted into the AA's balance but the AA has no code path at all capable of spending them out, since indivisible-asset composition (`indivisible_asset.js`) relies on selecting discrete denomination outputs and generating spend proofs that the deterministic AA payment-message logic does not support. Because AA addresses are `["autonomous agent"]` definitions with no controlling private key, there is no alternative signing path to move these funds later either.

### Impact Explanation
Any fixed-denominations (indivisible/NFT-like) asset sent to an AA address — whether accidentally by a user or intentionally as part of an AA's designed workflow (e.g., an AA meant to hold and later pay out NFT-like collectibles as rewards, similar to OngoingBountyV1's NFT funding) — becomes permanently frozen. The AA's oscript can never construct a valid outgoing payment message for that asset type, since such messages are unconditionally stripped from every response unit. This is a permanent, irreversible loss of the funded asset with no recovery path, matching a Medium severity "AA fund loss/freezing" impact.

### Likelihood Explanation
This does not require any special privilege or malicious behavior. It is triggered by ordinary usage: anyone paying a fixed-denominations asset into an AA that is designed (or naively assumed) to be able to forward/pay out arbitrary assets it receives, or any oscript author who is unaware of this restriction and writes payout logic for fixed-denomination assets in an AA's `messages` template. Since the failure mode is silent (no bounce/error is raised — the trigger just becomes an "empty response" that consumes the funds), authors have no obvious signal warning them the payout will never happen.

### Recommendation
Either:
1. Reject/bounce triggers that fund an AA with a `fixed_denominations` asset (similar to how `is_private` assets are rejected today with "sending private asset from AA"), so users and AA authors get immediate, explicit feedback that such assets cannot be used with AAs, or
2. Implement genuine support for the AA to compose indivisible-asset payment outputs (selecting proper denominations from its balance) so that fixed-denominations assets funded to an AA can actually be paid out.

### Proof of Concept
1. Define and issue an asset with `fixed_denominations: true` and appropriate `denominations` (an indivisible/NFT-like asset) as shown in the validation rules in `validateAssetDefinition`. [5](#0-4) 
2. Deploy an AA whose oscript, upon receiving this asset, attempts to immediately or later forward it to another address via a `payment` message with `asset: "<the fixed-denominations asset>"`.
3. Send a unit paying an amount of the fixed-denominations asset to the AA address, triggering it.
4. Observe in `aa_composer.js` `sendUnit`/`completePaymentPayload` handling: the payment message for that asset is skipped (`if (objAsset.fixed_denominations) // will skip it later`) at [6](#0-5)  and then filtered out entirely at [7](#0-6) , resulting in either a stripped-down response unit without the intended payout or, if it was the only message, a silent "no messages after removing fixed denominations" empty response.
5. Confirm via `aa_balances` that the asset balance remains credited to the AA address indefinitely, with no oscript-level way to ever emit a valid outgoing payment for it — the funds are permanently frozen.
