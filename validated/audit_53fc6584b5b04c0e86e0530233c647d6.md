Based on the investigation, I found a directly analogous "check against stale in-memory state before it is durably updated" pattern in the AA trigger execution path, structurally similar to the ibc-hooks issue (a guard against duplicate/reentrant processing that reads state which is not yet committed/updated).

### Title
Check for "second primary trigger from the same unit" relies on an in-memory counter that is only updated after the entire trigger's DB transaction and batch commit completes - ([File: aa_composer.js])

### Summary
`handleTrigger()` guards against a unit being used to fire more than one primary AA trigger by testing `storage.assocStableUnits[trigger.unit].count_aa_responses`, but that counter is populated only after the *previous* trigger invocation for the same unit has fully finished its DB transaction, kvstore batch write, and commit inside `handlePrimaryAATrigger()`. This mirrors the ibc-hooks bug class: a guard that is supposed to prevent duplicate/re-entrant handling of the same message is evaluated against state that has not yet been durably updated, leaving a window in which the guard can be bypassed.

### Finding Description
`handleTrigger()` performs the duplicate-trigger check: [1](#0-0) 

This check only takes effect starting at `constants.pemCurvesFixMci`, i.e., it was introduced later as a corrective measure for double-processing of the same trigger unit — the same class of defect flagged in the external report (a state check that can be satisfied more than once for what should be a single-use trigger).

The counter it relies on, `count_aa_responses` on `storage.assocStableUnits[trigger.unit]`, is incremented only deep inside `handlePrimaryAATrigger()`, after `handleTrigger()` fully returns, the kvstore `batch.write` completes, and the SQL transaction is committed: [2](#0-1) 

Between the moment a unit is first accepted as a primary trigger (row inserted into `aa_triggers`, `handleTrigger` invoked) and the moment `count_aa_responses` is actually bumped and the `aa_triggers` row deleted, `storage.assocStableUnits[trigger.unit].count_aa_responses` remains falsy for that unit. If a second `aa_triggers` row for the same `unit` (targeting a different AA address, which is possible when a single payment message carries outputs to several AA addresses) is processed before the first invocation's commit lands, the "second primary trigger from the same unit is not allowed" check will not fire, allowing the same unit to drive more than one primary AA execution — exactly the class of window the ibc-hooks advisory describes (a callback-completion flag/commitment checked and cleared too late, allowing repeated invocation).

### Impact Explanation
If exploitable, this would allow a single posted unit to be counted as the primary trigger for more than one AA response chain concurrently, which the code was specifically hardened against at `pemCurvesFixMci`. Depending on how `trigger.outputs` (the paid-in amount) is consumed by AA logic across the two invocations, this can enable the same deposited funds to be "spent"/counted by more than one AA balance update, i.e., unintended duplication of a single payment's value across independent AA state machines — a fund-accounting/double-spend-style defect within the AA subsystem.

### Likelihood Explanation
Exploitability depends entirely on whether the per-unit trigger rows for the same unit but different AA addresses can be dispatched with overlapping/asynchronous processing (separate `db.takeConnectionFromPool` calls per `handlePrimaryAATrigger`) rather than being strictly serialized end-to-end (including the batch write and commit) before the next one starts. I was not able to confirm within the available tool budget whether the caller in `main_chain.js` serializes these calls with `async.eachSeries` awaiting full completion (including batch write/commit) of each trigger before starting the next for the same unit, or whether they can be initiated concurrently. This is the key remaining uncertainty.

### Recommendation
Ensure the "second primary trigger from the same unit" state is marked synchronously and durably (e.g., in an in-memory set keyed by unit, set at the moment the unit is accepted as a primary trigger, not only after the full downstream commit) before any other trigger for the same unit can be considered, so the check cannot be bypassed by overlapping/asynchronous processing of multiple `aa_triggers` rows sharing the same `unit`.

### Proof of Concept
Not able to construct a concrete PoC without confirming the concurrency model of the `aa_triggers` dispatch loop in `main_chain.js` (i.e., whether multiple `handlePrimaryAATrigger` calls for the same unit but different AA addresses can be initiated before the first one's batch write/commit completes). This would need to be verified directly against `main_chain.js`'s trigger-processing loop.
