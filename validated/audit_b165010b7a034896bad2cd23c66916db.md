### Title
Webhook signature is verified against the org named in an unauthenticated payload field while the repository actually mutated is taken from a different, unbound payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub organization's `webhook_secret` to check the HMAC signature against by reading `repository.owner.login` / `organization.login` straight out of the still-unverified JSON body. The handlers that actually mutate state (`GithubSyncJob`, commit-status handlers, membership handlers, etc.) resolve the target `Stack`/`Repository`/`Team` from other fields of that same unverified body (e.g. `repository.full_name`, `sha`, `member.login`). Because the field used to select the verification secret is never cryptographically bound to the fields used to decide what gets written, an attacker who can obtain a valid signature for *any* configured organization (in particular one that has no `webhook_secret` set, which the setup docs describe as optional) can forge a payload whose `owner.login` matches that low/no-security org while its actual target fields point at a stack/repository belonging to a different, victim organization.

### Finding Description
`verify_signature` is: [1](#0-0) 

`repository_owner` is derived purely from the unauthenticated request body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a per-organization `GithubApp` instance whose `webhook_secret` is optional configuration: [3](#0-2) 

and signature verification is a no-op when that organization has no secret configured: [4](#0-3) 

The multi-organization configuration schema explicitly documents `webhook_secret` as optional per organization: [5](#0-4) [6](#0-5) 

Once `verify_signature` passes, `create` dispatches the full, attacker-controlled JSON to the registered handlers: [7](#0-6) 

The equality this flow is supposed to preserve is:
`organization whose secret authenticated the request` == `repository/stack/team that the resulting handler mutates`

Nothing in `verify_signature` or in `Hook`/`Webhooks` ties `repository_owner` (used only to pick the HMAC key) to the actual target identifiers consumed later by handlers (`repository.full_name`, `sha`, `member.login`, `team` id, etc.), because those are independent, sibling keys in the same untrusted JSON body. If organization A ("owner.login": "a-org") is configured with `webhook_secret: nil` (or a secret the attacker can obtain/guess) while organization B is the actual owner of a sensitive stack, a request with `repository.owner.login = "a-org"` but `repository.full_name = "b-org/victim-repo"` sails through `verify_signature` (since A requires no valid signature) and is then handed unmodified to the push/status/membership handlers, which act on `b-org/victim-repo`.

I was not able to retrieve and cite the exact push-event handler source in this pass (only its test behavior was visible, e.g. `GithubSyncJob` being enqueued keyed off `repository.full_name` in `push_master` fixtures per `test/controllers/webhooks_controller_test.rb`), so the exact resolution code for `repository.full_name → Stack` is inferred from test behavior rather than directly cited; this should be independently confirmed by a Devin session reading `app/models/shipit/webhooks/handlers/push_handler.rb` (or equivalent) end to end.

### Impact Explanation
If confirmed, this allows an unauthenticated caller to inject forged `push`/`status`/`check_suite`/`membership` events for a victim organization/repository as long as any other configured organization on the same Shipit instance has a weak or absent `webhook_secret`. Depending on the handler this can trigger unintended `GithubSyncJob` runs, fabricate commit statuses that gate deploys, or manipulate `Team`/`Membership` records that feed into `Shipit.github_teams` authorization — i.e. cross-repository/cross-organization writes and potential escalation into `Shipit.github_teams` authorization, matching the High/Critical impact classes in scope.

### Likelihood Explanation
Requires the operator to run Shipit with multiple GitHub organizations where at least one has no (or a weak) `webhook_secret` configured — a supported and documented configuration, not a misconfiguration outside the engine's own code. No session, API token, or GitHub write access is needed; only a POST to the public `/webhooks` endpoint with a crafted JSON body and, at most, a valid signature for the weak organization.

### Recommendation
Bind signature verification to the same identifier that handlers use to select their mutation target (e.g., resolve the `Repository`/`Stack` first via `repository.full_name`, and use that repository's own organization/secret for verification instead of a separately-read `owner.login`/`organization.login`), or require every configured organization to have a non-blank `webhook_secret` and reject requests when the org derived for verification doesn't match the org implied by the resource actually being written to.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `weak-org` (no `webhook_secret`) and `victim-org` (has `webhook_secret` set), each per `config/secrets.development.example.yml` multi-org schema.
2. Build a push payload: `{"repository": {"owner": {"login": "weak-org"}, "full_name": "victim-org/secret-repo"}, "after": "<sha>", ...}`.
3. POST to `/webhooks` with `X-Github-Event: push` and any `X-Hub-Signature` value (or omit it) — `verify_signature` calls `Shipit.github(organization: "weak-org").verify_webhook_signature(...)`, which returns `true` unconditionally since `weak-org` has no `webhook_secret` (`app/controllers/shipit/webhooks_controller.rb:24-38`, `lib/shipit/github_app.rb:76-83`).
4. The handler receives the full parsed body, keyed off `repository.full_name = "victim-org/secret-repo"`, and processes it as a legitimate event for `victim-org`'s stack.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```markdown
## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
```
