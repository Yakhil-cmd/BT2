## Title
Webhook signature is verified against `repository.owner.login` but handlers act on `repository.full_name` — cross-organization/repository forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check by looking up `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from `params.dig('repository','owner','login')`. Every webhook handler, however, resolves the target `Repository`/`Stack` using a *different* field of the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')` (via `Shipit::Webhooks::Handlers::Handler#repository_name`). These two fields are never checked against each other, so the binding "organization whose secret authenticated the request" == "repository that gets written to" is not enforced.

### Finding Description [1](#0-0) 

`verify_signature` picks the `GithubApp`/secret purely from `repository_owner`: [2](#0-1) 

Meanwhile every default handler (`PushHandler`, `StatusHandler`, pull-request handlers, `CheckSuiteHandler`, etc.) resolves the repository/stack to mutate using `repository.full_name`, taken from the very same JSON body but a different key: [3](#0-2) [4](#0-3) 

Because `repository.owner.login` (used for signature-org selection) and `repository.full_name` (used for target-repository resolution) are independent, attacker-controlled JSON keys inside the same raw POST body, nothing stops the values from being inconsistent. An entity that legitimately owns/administers **one** GitHub organization configured in Shipit (i.e., one that installed the Shipit GitHub App and therefore knows its own `webhook_secret`) can compute a valid HMAC signature for a payload whose `repository.owner.login` equals their own org (so `verify_signature` picks their own, valid secret and passes), while setting `repository.full_name` to `"victim-org/victim-repo"` — a completely different, unrelated repository/stack already registered in the same Shipit instance.

This breaks the equality that should hold: `organization that authenticated the request == organization/repository the request is permitted to mutate`. The webhook signature only proves "the caller knows the secret for org X"; it does not prove "the caller controls the repository named in `full_name`".

### Impact Explanation
Depending on which event type is abused, an attacker who controls only their own (unrelated) GitHub App installation can act as an authenticated webhook sender against a victim stack that belongs to a different organization/repository already registered with the same Shipit instance:

- `push` (`PushHandler`): forces `Stack#sync_github(expected_head_sha: ...)` on the victim stack with an attacker-chosen `after` SHA. If the target SHA is one that exists in the victim's history (or through the sync path), this can trigger a deploy through continuous deployment on a stack the attacker has no legitimate access to.
- `status`/`check_suite`: can flip commit/check statuses used to gate deploy eligibility (`deployable_status`, merge/CD gating), enabling an unauthorized deploy decision on the victim stack.
- `pull_request` handlers (`opened`, `closed`, `labeled`, etc.): can archive/unarchive review stacks, or manipulate labels used for merge automation on a repository the attacker does not own.

This matches the "unauthorized deploy or cross-repository writes" high/critical impact bar, since the attacker is triggering mutations on a stack/repository outside of the organization whose credentials actually authenticated the request — precisely the kind of deployment-trust binding break called out in the rules (organization authenticated ≠ repository written).

### Likelihood Explanation
Exploitability requires the attacker to be the legitimate administrator of **any one** GitHub organization/App installation that has been separately onboarded onto the same shared Shipit instance (a realistic scenario for a shared/self-hosted Shipit deployment serving multiple orgs/teams, as documented in `docs/setup.md`/`config/secrets.*.yml` supporting multiple `github:` entries keyed by org). No Shipit session, `ApiClient` token, or GitHub write access to the victim repository is required — only knowledge of one's own org's webhook secret, which the attacker legitimately possesses. The forged payload is a plain crafted JSON body sent to the public `/webhooks` endpoint with a correctly computed `X-Hub-Signature` for the attacker's own org.

### Recommendation
After selecting the signing organization from `repository_owner`, verify that the resolved `Repository`/`Stack` (looked up via `repository.full_name`) actually belongs to that same organization before dispatching to handlers — e.g., compare `repository.full_name.split('/').first` (or the resolved `Repository#owner`) against `repository_owner`, and reject (422) on mismatch. Alternatively, derive the signing organization strictly from `repository.full_name`'s owner segment rather than from the separate `repository.owner.login` field, so a single canonical value drives both authentication and authorization.

### Proof of Concept
1. Attacker is the admin of `attacker-org`, which has installed the Shipit GitHub App with `webhook_secret = S` (a real, legitimately obtained secret for their own org).
2. Attacker crafts a `push` webhook payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and verifies the signature against `S` — it passes, because the payload was indeed signed with `attacker-org`'s real secret. [5](#0-4) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')`, which is unrelated to `attacker-org`, and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — without ever validating that `victim-org` matches `attacker-org`. [6](#0-5)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
