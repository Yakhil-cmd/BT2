Based on my investigation, I found a concrete analog that fits the required binding pattern: the webhook signature verification selects which GitHub App (and thus which `webhook_secret`) to verify against using an **unauthenticated field from the very payload being verified**, while the event handlers that act on the payload use a **different, independently-controlled field** (the repository `full_name`) to decide which `Stack` to mutate.

### Title
Webhook signature is verified with a secret selected by an attacker-controlled payload field, decoupled from the repository the event actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` (and its `webhook_secret`) used to validate `X-Hub-Signature` based on `repository_owner`, a value read out of the **unverified** JSON body itself, before the signature has been checked. In multi-organization deployments (`Shipit.github(organization:)`), this creates a mismatch between "the organization whose secret authenticated the request" and "the repository the resulting handlers actually write to."

### Finding Description
`repository_owner` is computed purely from the request body: [1](#0-0) 

That value is used to select the GitHub App config whose `webhook_secret` verifies the signature: [2](#0-1) 

`Shipit.github` resolves per-organization configs, and Shipit explicitly supports multiple GitHub Apps/organizations, each with its own (optionally-`nil`) `webhook_secret`: [3](#0-2) [4](#0-3) 

`GitHubApp#verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for the resolved organization: [5](#0-4) 

After `verify_signature` passes, the actual event handlers (`Shipit::Webhooks.for_event(event)`) act on `params`, which include `repository.full_name`, `repository.owner.login`, `sha`, etc. — fields that are equally unverified and not required to be consistent with the `repository_owner` used to pick the verifying secret. Nothing in `WebhooksController#create` re-validates that the repository fields acted upon belong to the same organization/webhook_secret pairing that was used in `verify_signature`. This breaks the binding: **{organization whose secret authenticated this delivery} ≠ {repository this delivery is allowed to write to}**.

Concretely, if an operator configures two orgs, e.g. `OrgOne` (no `webhook_secret` configured, i.e. `nil`) and `OrgTwo` (has a `webhook_secret` and a Stack under it), an attacker with no GitHub credentials can:
1. Send a webhook (e.g. `push`, `status`, `check_suite`, `membership`) with `repository.owner.login` (or `organization.login`) set to `OrgOne`.
2. `verify_signature` resolves `Shipit.github(organization: "OrgOne")` and, since `OrgOne.webhook_secret` is `nil`, `verify_webhook_signature` returns `true` unconditionally — no valid signature is required at all.
3. The same payload's `repository.full_name` can reference a Stack that actually lives under `OrgTwo` (repositories are looked up by `full_name`, independent of the `repository_owner` used for signature selection), so handlers such as `GithubSyncJob`, commit `status` creation, `check_suite` processing, or `membership`/`Team` mutation act on `OrgTwo`'s stack data without ever having gone through `OrgTwo`'s webhook secret.

### Impact Explanation
This allows an unauthenticated party who merely knows that some configured organization has no (or a guessable/leaked) `webhook_secret` to forge webhook events that get processed as if legitimately delivered, and have those events act on a *different* organization's Stack (e.g. injecting fabricated commit statuses via the `status` event, or membership/team changes via `membership`, which can influence `Shipit.github_teams`-based authorization). This crosses a "GitHub identity authenticated the delivery" vs. "repository engine acts on" boundary and can escalate into unauthorized writes to stack/commit state and, through `membership`, into `Shipit.github_teams` authorization — matching the High-severity class "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Requires a multi-org Shipit deployment where at least one configured organization has `webhook_secret: nil` (explicitly documented and supported as a default/example configuration in `docs/setup.md` and `config/secrets.development.example.yml`), and at least one other stack/org that the attacker wants to affect. No GitHub credentials, no Shipit session, and no `ApiClient` token are required — only network access to the public `webhooks` endpoint, satisfying the "unprivileged attacker" requirement.

### Recommendation
Verify the webhook signature using the `webhook_secret` belonging to the organization that actually owns the `Stack`/`Repository` being mutated (resolved from trusted, already-persisted `Repository` records) rather than from the unauthenticated request body, and reject requests where no `webhook_secret` is configured instead of treating an absent secret as automatic success across all configured organizations.

### Proof of Concept
1. Configure Shipit with two orgs per `docs/setup.md`: `OrgOne` (`webhook_secret: nil`) and `OrgTwo` (`webhook_secret: <secret>`, with a Stack for `OrgTwo/some-repo`).
2. POST to `/webhooks` with header `X-Github-Event: status` and JSON body:
```json
{
  "sha": "<commit sha of OrgTwo/some-repo>",
  "state": "success",
  "context": "ci/fake",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/some-repo" }
}
```
No valid `X-Hub-Signature` header is supplied (or any arbitrary value).
3. `verify_signature` resolves `Shipit.github(organization: "OrgOne")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of the header/body — the request is accepted.
4. `create` action then runs the `status` handler against `OrgTwo/some-repo`'s commit, creating a forged status on it, even though `OrgTwo`'s webhook secret was never validated.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
