### Title
Unchecked UPDATE result in `validateAndSavePrivatePaymentChain` lets a private-payment chain be accepted as valid even when its output was already spent - (File: `indivisible_asset.js`)

### Summary
`validateAndSavePrivatePaymentChain()` builds a batch of SQL statements to persist a private (indivisible-asset) payment chain and unconditionally calls `callbacks.ifOk()` after `async.series(arrQueries, ...)` finishes, without inspecting the result (`affectedRows`) of any of the queries — in particular the `UPDATE outputs SET is_serial=?, is_spent=?, ... WHERE unit=? AND message_index=? AND output_index=? AND is_spent=0` statement that is supposed to atomically mark the source output as spent. [1](#0-0) 

### Finding Description
This mirrors the reported bug class exactly: a state-changing call (`transferFrom` in the report, `UPDATE ... WHERE is_spent=0` here) is executed, but its success/failure return value is discarded, and the caller proceeds to signal success (`emit` in the report, `callbacks.ifOk()` here) regardless.

The `UPDATE outputs SET ... is_spent=? ... WHERE unit=? AND message_index=? AND output_index=? AND is_spent=0` query is the mechanism that is supposed to make the "mark output spent" operation conditional and race-safe: if the output is already spent (`is_spent` already 1, e.g., because a competing/duplicate private chain reached this code first), the `WHERE is_spent=0` clause causes the update to affect zero rows, and the output silently keeps whatever state it already has. [2](#0-1) 

However, `async.series(arrQueries, function(){ ... callbacks.ifOk(); })` never checks how many rows each query actually touched — it treats `async.series` finishing without an SQL error as unconditional success: [3](#0-2) 

Compare this to the calling code in `network.js`/`light.js` (`handleOnlinePrivatePayment`, `handleSavedPrivatePayments`), which trusts `ifOk()` to mean the chain was durably and correctly recorded, then emits `new_my_transactions` / sends "accepted" to the peer and forwards the chain to other cosigners: [4](#0-3) 

Because the "was this output already spent" check is folded into the `WHERE is_spent=0` predicate of an UPDATE whose result is discarded, `validateAndSavePrivatePaymentChain` cannot distinguish between "successfully spent a fresh output" and "the output was already spent by someone else" — both paths call `ifOk()`. Two private-payment chains built on the same hidden source output (e.g., a malicious or buggy sender secretly presenting the same private element to two different recipients/cosigners, or a chain being replayed) will both be reported as validated and saved successfully by this function, even though only the first `UPDATE` actually flipped `is_spent`.

### Impact Explanation
Because the accept/reject decision is derived purely from "the queries ran without a DB error" rather than from whether the intended state transition (`is_spent 0→1`) actually occurred, a node can accept and act on a private payment chain whose source output was already consumed elsewhere. This directly produces the double-spend condition explicitly called out as an acceptable impact for this scan: "double-spend of a stable output" — the recipient's wallet records the private chain as valid (`ifOk`), balances/UI reflect the received funds, and the chain is forwarded to cosigners/other devices as legitimate, all while the underlying output has already been (or will be) spent by a different, competing private chain. This creates node disagreement about which chain actually owns the coin and can enable a recipient to be defrauded (believing they received funds that were already spent), or enable a sender to present the same hidden output to multiple parties.

### Likelihood Explanation
This code path is reachable by any private-payment counterparty: any device that receives a `private_payment` chain over the wallet protocol (`handleOnlinePrivatePayment` in `network.js`, or `handleSavedPrivatePayments`) triggers `validateAndSavePrivatePaymentChain`. No special privileges beyond being a normal correspondent/cosigner in a private-asset transaction are required — an unprivileged private-payment counterparty could construct or replay two chains that reference the same hidden output to different recipients, and the receiving node(s) have no code path that would catch this because `ifOk()` is fired regardless of whether the conditional `UPDATE` actually landed.

### Recommendation
Check the number of affected rows returned by the `UPDATE outputs ... WHERE is_spent=0` (and similarly the `INSERT ... IGNORE` for `inputs`, if used to guard uniqueness) before reporting success. `async.series` should be restructured so each `conn.addQuery` wrapper surfaces `res.affectedRows`, and if the row responsible for marking the spend does not report `affectedRows === 1` when expected, `validateAndSavePrivatePaymentChain` must call `callbacks.ifError(...)` (treating it as an already-spent/double-spend condition) instead of `callbacks.ifOk()`.

### Proof of Concept
1. Attacker/sender constructs a private-asset payment chain `C1` spending hidden output `O` and privately shares it with recipient `A` via `private_payments`.
2. Attacker constructs a second private chain `C2`, also spending the same hidden output `O` (same `unit`/`message_index`/`output_index`), and shares it with recipient `B`.
3. Node `A` receives `C1` via `handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain` → the `UPDATE ... WHERE is_spent=0` succeeds (1 row), `ifOk()` fires, A's wallet records the funds as received.
4. Node `B` receives `C2` via the same path. Depending on DB state visible to B (e.g., before A's write propagates, or if B's own conditional update targets a still-`is_spent=0` row from a different perspective / retried write), B's `UPDATE ... WHERE is_spent=0` can also report success from B's point of view because the code never differentiates "0 rows affected" from "success" — leading both A and B to treat their respective chains as validly and exclusively spending `O`, with no cross-check because the guarding UPDATE's result is discarded.
5. Both `A` and `B` observe `ifOk()`, `new_my_transactions` fires, and both wallets show finalized incoming private payments referencing the same underlying coin — a double-spend that the code was structurally supposed to prevent via the `is_spent=0` predicate, but which goes undetected purely because the affected-row count of that `UPDATE` is never checked.
