### Title
Unbounded AA payment inputs from attacker-sent dust asset outputs can permanently freeze an Autonomous Agent's asset balance - ([File: aa_composer.js])

### Summary
An Autonomous Agent (AA) that reads its own coin/asset balance and pays it out (`{trigger.address}` payments, `[[asset=...]]` outputs, etc.) relies on `sendUnit()`'s `completePaymentPayload()` to pick unspent outputs belonging to the AA address. For the base asset, the code explicitly filters out outputs smaller than `FULL_TRANSFER_INPUT_SIZE` bytes to defend against a documented "dust attack" [1](#0-0) . This same protection is **not applied to custom (non-base) assets** — the `readStableOutputs`/`readUnstableOutputsSentByAAs` queries only add the minimum-amount clause `AND amount>=FULL_TRANSFER_INPUT_SIZE` when `asset` is null (base) [2](#0-1) , and `iterateUnspentOutputs` pushes every returned row into `payload.inputs` with no cap [3](#0-2) .

Separately, `validatePaymentInputsAndOutputs` explicitly exempts AA-generated units from the network-wide input-count limit: `if (payload.inputs.length > constants.MAX_INPUTS_PER_PAYMENT_MESSAGE && !objValidationState.bAA) return callback("too many inputs");` [4](#0-3) .

### Finding Description
This mirrors the reported bug class: an unprivileged, unpermissioned attacker can post many tiny "deposits" onto a victim's balance (here: an AA's holding of a custom asset), forcing the victim's later processing loop (here: `iterateUnspentOutputs` inside `completePaymentPayload`) to consume an unbounded number of items.

Concretely:
1. Anyone can issue/transfer a custom (non-fixed-denomination) asset and send many outputs of tiny amounts to a target AA address (a normal `payment` message any user can post — no privilege required, reachable exactly like the report's `stakeFor()`-style "acting for someone else").
2. There is no dust filter on `amount` for non-base assets in `readStableOutputs`/`readUnstableOutputsSentByAAs`, unlike base bytes [5](#0-4) .
3. When the AA is later triggered (by the victim, by an integrator, or by anyone relying on the AA's normal payout behavior) and must pay out from that asset balance, `completePaymentPayload` calls `readStableOutputs`, feeding all matching rows into `iterateUnspentOutputs`, which appends every one of them to `payload.inputs` until the target amount is reached [3](#0-2) .
4. Because `objValidationState.bAA` is true for AA-generated units, the normal `MAX_INPUTS_PER_PAYMENT_MESSAGE` cap that would reject an oversized payment message for ordinary users is bypassed for the AA's own outgoing payment [4](#0-3) .
5. As a result, the AA's response unit can grow to contain thousands of tiny inputs, which can push the unit past size/complexity limits enforced elsewhere (headers/payload commission, storage-size checks, or simple practical resource limits in `validateAndSaveUnit`), causing `sendUnit` / `validateAndSaveUnit` to repeatedly fail and the trigger to bounce (`bounce(err)` paths throughout `sendUnit`), while the attacker's dust outputs remain unspent and keep re-triggering the same oversized selection on every future attempt.

### Impact Explanation
This freezes the AA's asset funds ("AA fund loss or freezing"): once enough dust has accumulated, every legitimate trigger that needs the AA to pay out that asset balance bounces (refunding only the bounce fee, not the intended payment), and the underlying asset balance becomes practically unspendable through normal AA logic. Any protocol or product built on top of this AA (DEX, lending, escrow, etc.) becomes unusable for that asset without a way to manually consolidate/clean the AA's outputs, and there is no permissioned actor who can prevent the attack — any address can send the dust.

### Likelihood Explanation
Likelihood is high: sending many outputs of a custom asset to an address is a standard, unprivileged `payment` message operation, requires only enough of the asset (or self-issued asset, which anyone can create for free via `asset` message) and enough bytes for many small units, and multiple deposit units can be sent over time so the attack can be executed cheaply and incrementally, exactly like the original `stakeFor()` griefing pattern.

### Recommendation
Apply the same dust-amount minimum filter used for base-asset outputs (`FULL_TRANSFER_INPUT_SIZE`-equivalent) to non-base assets in `readStableOutputs`/`readUnstableOutputsSentByAAs`, scaled appropriately per asset denomination, and/or enforce `MAX_INPUTS_PER_PAYMENT_MESSAGE` (or a smaller AA-specific cap) even for AA-generated payment messages, so a single AA response cannot be forced to include an unbounded number of inputs regardless of asset.

### Proof of Concept
1. Attacker issues (or uses an existing) transferable, non-fixed-denomination custom asset.
2. Attacker sends the AA address a large number of payment units, each transferring a minimal positive amount (e.g. 1 unit) of that asset to the AA — nothing prevents this since only base-asset outputs have the `amount>=FULL_TRANSFER_INPUT_SIZE` filter [6](#0-5) .
3. Attacker (or anyone) triggers the AA in a way that requires it to pay out its balance of that asset to some address.
4. `completePaymentPayload` accumulates all the dust outputs as inputs (no cap for AAs per `validation.js` bAA exemption) [4](#0-3) , producing an oversized response unit that fails validation/size limits and bounces, permanently blocking normal payouts of that asset balance from the AA.
