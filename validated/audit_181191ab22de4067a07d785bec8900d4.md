## Analog Found

### Title
Reachable assertion abort in payment input validation crashes the node process (DoS) - (File: `validation.js`)

### Summary
CVE-2019-9211 describes a reachable `assert()`/abort in PSPP's `write_long_string_missing_values()` that lets malformed input trigger a process-terminating assertion instead of a graceful error, causing denial of service. The Obyte/ocore codebase has an analogous pattern: several "should never happen" invariant checks inside `validation.js`'s payment-input validation are implemented as `throw Error(...)` executed inside asynchronous DB-query callbacks rather than returned as ordinary validation errors via `cb()`/`callback()`. Because these throws occur outside any enclosing `try/catch` (JS async callbacks break the synchronous call stack), they propagate to the process-wide `process.on('uncaughtException', ...)` handler in `network.js`, which deliberately re-throws to kill the process.

### Finding Description
In `validatePaymentInputsAndOutputs()`'s per-input `"transfer"` handling, the code queries the source output of a spent input and asserts internal invariants using `throw` instead of `cb(error)`: [1](#0-0) 

Specifically:
- `if (rows.length > 1) throw Error("more than 1 src output");`
- `if (src_output.sequence === 'temp-bad') throw Error("spending a stable temp-bad output " + input.unit);`

Both are guarded on the assumption that a *stable* unit can never keep `sequence='temp-bad'`, because `markMcIndexStable()` is supposed to resolve every stabilizing unit's `temp-bad` sequence to either `good` or `final-bad`: [2](#0-1) 

These `throw` statements execute inside the callback of `conn.query(...)`, i.e., on a fresh call stack, not inside the top-level `try { ... } catch(e) { return callbacks.ifJointError(...) }` block that only wraps the very first synchronous section of `validate()`: [3](#0-2) 

Because nothing catches the exception, it bubbles up to Node's global handler in `network.js`, which was intentionally written to crash the process on any uncaught exception "to avoid ending up in an inconsistent state": [4](#0-3) 

This is architecturally identical to the CVE's bug class: a "should never happen" internal invariant is enforced by aborting the whole process instead of returning a controlled error, and the condition is reachable through validation of externally supplied unit data (a payment input referencing an existing, stable output).

### Impact Explanation
If the invariant is ever violated — e.g., by a timing/edge-case bug in nonserial resolution, a crash/restart between `is_stable=1` being set and the sequence-finalization step in `markMcIndexStable()`'s `handleNonserialUnits()`, or any other path that leaves a stable output with `sequence='temp-bad'` — every full node that processes a unit spending that output will hit the same `throw` deep inside the shared `validate()` code path used for all incoming units, light-vendor posted units, and catch-up processing. Because `process.on('uncaughtException')` re-throws deliberately, the entire node process dies. If the triggering unit propagates normally through the network (as any valid-looking unit does), every full node that receives and validates it crashes in the same way, which can prevent the network from confirming new units until operators intervene — matching the accepted "network unable to confirm new units" impact bucket.

### Likelihood Explanation
Reaching this code path requires only posting an ordinary payment unit whose `transfer` input references a unit/output that is stable but for which the assumed-impossible `temp-bad` state actually holds. Triggering the precondition itself requires either an existing bug in the nonserial-resolution logic in `main_chain.js` or unusual timing/restart conditions; the assertion is intended as a last-resort safety net, so likelihood of the *precondition* is lower than a straightforward validation bug, but once the precondition exists, exploitation is a single crafted unit, and impact escalates to full node crash rather than a bounded validation error — consistent with the "reachable assertion abort" class described in the CVE.

### Recommendation
Convert all such invariant checks in `validatePaymentInputsAndOutputs()` (and similar ones elsewhere in `validation.js`/`main_chain.js` on async callback paths reachable via untrusted unit content) from `throw Error(...)` to `return cb(error)` (or a joint/unit error object), so that violations are treated as ordinary validation failures instead of taking down the whole node. If these are true internal invariants, keep them as `throw` only inside code that cannot be reached by attacker-controlled data, or wrap the query-callback logic in its own try/catch that converts unexpected assertion failures into a transient/joint error handled by the validation callback machinery instead of relying on the global `uncaughtException` handler.

### Proof of Concept
Conceptual PoC (would require a way to actually get a stable output into `sequence='temp-bad'`, e.g. via a bug in nonserial resolution or a crafted state left after a crash mid-stabilization):
1. Get a unit `U1` stabilized while its `sequence` remains `temp-bad` in the `units` table (bypassing the normal resolution in `handleNonserialUnits`).
2. Post a new unit `U2` whose payment message has a `"transfer"` input with `unit: U1`, referencing the (now stable) output.
3. When any full node validates `U2`, `validatePaymentInputsAndOutputs()`'s query callback finds `src_output.main_chain_index <= last_ball_mci` (stable) and `src_output.sequence === 'temp-bad'`, hitting:
   `throw Error("spending a stable temp-bad output " + input.unit);` (`validation.js:2458`)
4. The exception is uncaught, propagates to `process.on('uncaughtException')` in `network.js:4530-4543`, and the node process terminates.
