### Title
Missing global replay protection for L1 Bitcoin lockup outpoints allows double-counting a single BTC lockup across multiple `register-for-bond` calls - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`pox-5.clar`'s `register-for-bond` accepts a Bitcoin SPV proof of an L1 timelock output as a substitute for locking sBTC on Stacks. The de-duplication of Bitcoin outpoints (`txid`+`output-index`) used as proof is only enforced *within a single call* (a local fold accumulator), not against a persistent, contract-level record of previously consumed outpoints. This lets a staker reuse the exact same L1 Bitcoin lockup as proof-of-lock in more than one `register-for-bond` call over time, crediting `sats-total` (and the corresponding stake weight/reward eligibility) more than once for BTC that was only locked once.

### Finding Description
`register-for-bond` computes `sats-total` for the L1 lockup path via `verify-l1-lockups`, which folds over the caller-supplied list of Bitcoin outputs using `validate-l1-lockup`: [1](#0-0) 

The fold's accumulator seeds `seen-outpoints` as an empty list, `(list)`, on every invocation: [2](#0-1) 

`validate-l1-lockup` only checks that an outpoint has not already appeared *inside the current outputs list* (`index-of? seen-outpoints outpoint`) before appending it to that same transient accumulator: [3](#0-2) 

There is no persistent map (e.g. a `used-l1-outpoints` map keyed by `{ txid, output-index }`) anywhere in the contract that records an outpoint as "consumed" once it has been used to justify a `register-for-bond` sats credit — I searched the contract for any such map/state and found none. This means the exact same on-chain Bitcoin UTXO can be re-submitted as proof in a *second, independent* `register-for-bond` call and will pass all checks (`verify-block-header`, merkle proof, script-hash match, amount match) again, since none of those checks reference prior contract state.

The script itself binds the lockup to a specific `staker` principal (via `sha256(sha256(to-consensus-buff? staker))` baked into `construct-lockup-script`), which prevents a *different* principal from reusing someone else's lockup. However, it does not prevent the *same* staker from reusing their own already-proven lockup to register into a second bond (e.g., after their earlier bond ends and they roll into a new one, or in any subsequent bond period the outpoint's `unlock-burn-height` still satisfies), crediting `sats-total` for BTC that remains encumbered in exactly one Bitcoin output.

This breaks the equality the bond/stake mechanism is supposed to preserve: `sum(sats credited across all active bond memberships) == sats actually locked on Bitcoin`. A staker can inflate their credited sats (and therefore their `min-ustx-for-sats-amount` eligibility, target-rate reward calculation, and reward-weight in the reward set) by presenting one real BTC lockup multiple times across separate transactions.

### Impact Explanation
This is a double-counting of a Bitcoin lockup commitment. Because bond reward/weight and eligibility calculations use `sats-total` derived from `verify-l1-lockups`, reusing one BTC lockup across multiple bond registrations lets a staker claim more STX-eligible sats (and correspondingly more sBTC/stake rewards) than the amount of BTC actually locked, unbacked by any additional Bitcoin collateral. Per the grading rubric this falls under "double-counting a commitment or reward," a Critical-severity class of finding.

### Likelihood Explanation
Exploitation only requires an ordinary staker (not an admin, not another user's key) to call `register-for-bond` a second time — after their first bond/membership ends or in a separate later bond period — supplying the identical Bitcoin transaction/output/merkle-proof data used previously. No new BTC needs to be moved on Bitcoin; the same immutable on-chain proof is valid indefinitely since `verify-block-header`/merkle checks are purely historical facts about Bitcoin, not tied to consumption state in `pox-5`.

### Recommendation
Add a persistent map, e.g. `used-l1-outpoints: { txid: (buff 32), output-index: uint } -> bool` (or -> staker/bond-index), and have `validate-l1-lockup` (or `verify-l1-lockups`) `map-insert` each outpoint into it, asserting failure (`ERR_DUPLICATE_LOCKUP_OUTPOINT` or a new error) if the outpoint has already been consumed by any prior successful `register-for-bond` call, not just within the current call's output list.

### Proof of Concept
1. Staker locks BTC into the P2WSH output described by `construct-lockup-output-script(staker, unlock_height, staker_unlock_bytes, early_unlock_bytes)`.
2. Staker calls `register-for-bond(bond_index=0, ..., btc-lockup=(ok { outputs: [proof_for_that_output], staker-unlock-bytes }))`. `verify-l1-lockups` succeeds, `sats-total` = the output's sats, and the staker is registered/credited for bond 0.
3. Bond 0's membership ends (or the staker otherwise becomes eligible to register again, e.g., a later bond period whose `minimum-unlock-height` is still satisfied by the same lockup's `unlock-burn-height`).
4. Staker calls `register-for-bond(bond_index=1, ..., btc-lockup=(ok { outputs: [the *same* proof_for_that_output], staker-unlock-bytes }))` again. Because `seen-outpoints` is re-initialized to `(list)` for this new call and no global outpoint-usage map exists, all checks in `validate-l1-lockup` pass again, and `sats-total` is credited a second time for bond 1 — from BTC that was only ever locked once on Bitcoin.

Note: I was not able to fully trace, within the available tool budget, every guard in the surrounding `register-for-bond`/rollover logic (e.g., whether `existing-membership`/`ERR_ALREADY_REGISTERED` handling incidentally blocks this specific reuse path in all timing scenarios). The core defect — absence of any persistent, cross-transaction outpoint-consumption record in `validate-l1-lockup`/`verify-l1-lockups` — is confirmed directly from the contract source cited above.

;; Verify l1 lockup information for a staker. This asserts that each lockup
;; corresponds to the right timelock script for this staker, and that the lockup
;; occurred on-chain. If everything is valid, this returns the sum of all lockups in sats.
(define-private (verify-l1-lockups
        (staker principal)
        (bond-index uint)
        (lockups {
            outputs: (list 10
                {
                    height: uint,
                    tx: (buff 100000),
                    output-index: uint,
                    header: (buff 80),
                    leaf-hashes: (list 14 (buff 32)),
                    tx-count: uint,
                    tx-index: uint,
                    amount: uint,
                    unlock-burn-height: uint,
                }
            ),
            staker-unlock-bytes: (buff 683),
        })
    )
    (let (
            (bond (unwrap! (get-protocol-bond bond-index) ERR_BOND_NOT_FOUND))
            (accumulation (try! (fold validate-l1-lockup (get outputs lockups)
                (ok {
                    sum: u0,
                    staker: staker,
                    minimum-unlock-height: (get-bond-l1-unlock-height bond-index),
                    staker-unlock-bytes: (get staker-unlock-bytes lockups),
                    early-unlock-bytes: (get early-unlock-bytes bond),
                    seen-outpoints: (list),
                })
            )))
        )
        (ok (get sum accumulation))
    )
)
