### Title
ERC20 XCM Transactor doesn't support fee-on-transfer tokens, allowing asset-backing mismatch / unbacked issuance - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` credits the XCM `AssetsInHolding` register with the nominal `amount` requested in the XCM `Asset`, without verifying that the ERC20 checking account's actual balance increased by that same amount. Any deployed contract satisfying `IERC20` ABI shape (contract deployment via `pallet-revive` is permissionless) can be used as an XCM-transactable asset. A malicious/fee-on-transfer ERC20 contract can therefore cause the on-chain XCM accounting to diverge from the real token balance backing it.

### Finding Description
`ERC20Transactor` (used as one of the `AssetTransactors` on Asset Hub, see `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs:239-246`) lets XCM programs treat arbitrary Ethereum-style contract addresses (`AccountKey20` locations) as fungible assets, dispatching real Solidity `transfer()` calls through `pallet_revive::Pallet::<T>::bare_call` [1](#0-0) .

In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transfer(checking_account, amount)` on the user-supplied contract. If the call succeeds and returns `true`, it unconditionally mints an `Erc20Credit(amount)` into the XCM holding register — using the *requested* `amount`, not the actual balance delta observed on the checking account: [2](#0-1) 

There is no balance-before/balance-after comparison anywhere in this path — exactly the missing check called out in the original report (`balanceBefore`/`balanceAfter` diffing). A malicious ERC20 contract implementing a "fee on transfer" (or any other logic that credits the recipient less than `value` while still returning `true`) will cause:
- The `TransfersCheckingAccount` to receive less real value than `amount`.
- The XCM holding register (and any onward `DepositAsset`/reserve-transfer program built from it) to still account for the full nominal `amount`.

The symmetric `deposit_asset_with_surplus` path has the same blind-trust structure — it transfers `amount` out of the checking account based on the holding's nominal value [3](#0-2) , meaning any shortfall accumulated from fee-on-transfer withdrawals is drawn down from a shared account used by all ERC20-XCM users, not the specific token's own attacker-controlled logic.

That the matcher accepts *any* deployed contract, not a governance-curated allow-list, is confirmed by an existing integration test that deploys an arbitrary non-ERC20 contract and references it directly by its freshly-generated address as an XCM asset location: [4](#0-3) . The only validation performed is on the return-value shape/type (`bool` decode) of the `transfer` call — not on actual balance movement — as shown by the companion test `smart_contract_does_not_return_bool_fails` which only checks decode failures, not fee-skimming behavior.

Reachability / attacker entry point:
1. Deploy an arbitrary "ERC20" contract via `pallet-revive` (permissionless contract deployment) whose `transfer()` deducts an internal fee before crediting the recipient, but still returns `true`.
2. Submit a signed `pallet_xcm::execute` (or any reserve-transfer/`transfer_assets` extrinsic routed through `AssetTransactors`) that references this contract's address as an `AccountKey20` asset and withdraws/deposits it — exactly the pattern exercised in `smart_contract_not_erc20_will_error`.
3. `withdraw_asset_with_surplus` observes `true` and credits the full nominal amount to the XCM holding register, while the checking account only received `amount - fee`.

### Impact Explanation
This is the direct FRAME/XCM analog of the reported ERC20 fee-on-transfer issue: the protocol assumes `amount == actual amount received`, exactly the anti-pattern the report warns about. Consequences:
- If the withdrawn amount is subsequently reserve-transferred/teleported to another chain (minting a wrapped/derivative asset there 1:1 against the nominal amount), the destination chain mints more derivative value than was actually captured by the checking account — an unbacked issuance analogous to Critical severity classes called out in the scan instructions.
- Locally, the shared `TransfersCheckingAccount` balance is drawn down faster than accounted, eventually causing legitimate users' `deposit_asset_with_surplus` calls (drawing on the same pooled account) to fail or be under-collateralized, a systemic accounting break affecting all users of any ERC20 asset routed through this transactor, not just the attacker.

### Likelihood Explanation
Deploying a contract with `pallet-revive` and calling `pallet_xcm::execute`/asset-transfer extrinsics are ordinary, permissionless, unprivileged user actions (already demonstrated to be reachable by the repository's own test harness for arbitrary "ERC20-like" contracts). No governance, sudo, or validator/collator collusion is required.

### Recommendation
In `ERC20Transactor::withdraw_asset_with_surplus` (and symmetrically in `deposit_asset_with_surplus`), measure the checking/beneficiary account's real ERC20 `balanceOf` before and after the `transfer` call and credit/derive the `AssetsInHolding` amount (and any onward XCM instructions) from the observed delta rather than the nominally requested `amount`, matching the standard fee-on-transfer-safe pattern from the original report.

### Proof of Concept
Not executed. I did not have terminal/test-execution access in this session to run a live integration test. The reachability, however, is directly demonstrated by the repository's own existing test `smart_contract_not_erc20_will_error` [4](#0-3) , which shows that an arbitrary freshly-deployed `pallet-revive` contract address can be passed as an XCM asset into `withdraw_asset`/`deposit_asset` through this transactor. A full PoC would extend this test with a purpose-built "fee-on-transfer" ERC20 contract (transfers `value - fee` while returning `true`) in place of the "dummy" contract, and assert that `AssetsPallet`/checking-account real balance after the XCM program differs from the nominal `amount` credited in events/holding — this step (writing and compiling the malicious Solidity fixture and running the emulated test) is the part that remains unverified due to lack of execution access in this session.

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);

#[test]
fn smart_contract_not_erc20_will_error() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 10_000_000_000_000u128;

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));

		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let (code, _) = compile_module("dummy").unwrap();

		let Contract { addr: non_erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.build_and_unwrap_contract();

		let wnd_amount_for_fees = 1_000_000_000_000u128;
		let erc20_transfer_amount = 100u128;
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: non_erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.build();
		// Execution fails but doesn't panic.
		assert!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(2_500_000_000, 120_000),
		)
		.is_err());
	});
