## Analysis

The confirmed root cause lives in `app/controllers/shipit/webhooks_controller.rb`. The signature-verification step selects *which* GitHub App/webhook secret to validate the request against using one payload field:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

But every downstream `Handler` resolves the *repository that gets written to* from a **different** payload field, `repository.full_name`, via `Shipit::Repository.from_github_repo_name`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [1](#0-0) 

`Repository.from_github_repo_name` simply splits the string on `/` with no cross-check against `repository.owner.login`:

```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [2](#0-1) 

Multi-organization deployments are natively supported (`Shipit.github(organization:)` looks up a distinct `webhook_secret`/app config per GitHub org key in `secrets.github`) [3](#0-2) , and `Repository#github_app` similarly re-derives the app per-`owner` [4](#0-3) . This is exactly the class of bug in the external report: the field that is actually *checked* (`repository.owner.login`/`organization.login`, used to pick the HMAC secret) is never bound to the field that is *acted upon* (`repository.full_name`, used to select which `Stack`/`Repository` receives the sync/status/check-run/PR update).

### Attack path
1. Shipit is configured with `secrets.github` containing multiple organizations, e.g. `orga` (controlled by the attacker, who therefore knows `orga`'s `webhook_secret`) and `orgb` (a victim organization already onboarded with stacks in Shipit).
2. The attacker computes a valid `X-Hub-Signature` for an arbitrary JSON body using `orga`'s known webhook secret (`OpenSSL::HMAC.hexdigest('sha1', orga_secret, body)`), and sets `repository.owner.login = "orga"` (so `verify_signature` selects and successfully validates against `orga`'s secret) while setting `repository.full_name = "orgb/victim-repo"`.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orga")` and successfully verifies the signature, because the app never checks that `owner.login` matches `full_name`'s owner segment.
4. `Handler#stacks`/`#repository_name` then resolve `orgb/victim-repo` via `Repository.from_github_repo_name`, and the event handler (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers) acts on `orgb`'s real stacks — enqueuing `GithubSyncJob`, writing `Status`/`CheckRun` records, or archiving/mutating review stacks/pull requests for a repository the attacker does not control and for an organization whose secret they never had.

This is a forged cross-organization/cross-repository write: an attacker who only controls one onboarded GitHub organization in a multi-org Shipit deployment can spoof webhook events that mutate a different organization's stacks.

### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while all handlers act on the unrelated `repository.full_name`, enabling cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` chooses which organization's webhook secret to validate a request against based on `repository.owner.login` (falling back to `organization.login`), but every `Shipit::Webhooks::Handlers::Handler` subclass determines the actual repository/stack to mutate from the independent `repository.full_name` field, with no cross-validation between the two. In a multi-organization Shipit deployment, an attacker who legitimately controls one onboarded GitHub organization (and thus knows that organization's `webhook_secret`) can craft a webhook payload whose `owner.login`/`organization.login` names their own org (so the HMAC check passes) while `repository.full_name` names a different, victim organization's repository, causing Shipit to process the forged event against the victim's real `Stack`.

### Finding Description
`Shipit.github(organization:)` supports per-organization GitHub App configs, each with its own `webhook_secret` [3](#0-2) . The webhook signature check picks the app/secret using only the organization identity in the payload:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

Once the signature is accepted, `WebhooksController#create` dispatches the entire raw payload to all registered handlers for the event [6](#0-5) . Every handler resolves the repository to operate on from a completely different key, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [1](#0-0) 
and `Repository.from_github_repo_name` performs a bare lookup with no consistency check against the `owner.login` used for signing:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [2](#0-1) 

Because the signature-verified field (`owner.login`/`organization.login`) and the field the handlers act on (`full_name`) are never bound together, an attacker who is a legitimate administrator of one onboarded organization — and therefore knows that organization's `webhook_secret` — can produce a correctly signed payload that names a *different* organization's repository in `full_name`. Handlers such as `PushHandler` (queues `GithubSyncJob`, syncing arbitrary commits into the victim's stack) [7](#0-6) , `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, and the pull-request handlers (e.g. `closed_handler.rb`, which can `archive!` a review stack) [8](#0-7)  would all process the forged event against the victim organization's real records.

### Impact Explanation
This breaks a deployment-trust binding explicitly called out as High/Critical impact: "an organization that authenticated versus the repository that is written." An attacker who is only an admin of one onboarded, unprivileged organization can force Shipit to act (sync commits, write commit statuses, archive review stacks, enqueue check-run refreshes) on a different organization's stacks that they have no legitimate access to — an unauthorized cross-repository/cross-organization write triggered entirely by a spoofed webhook request, without any Shipit session, API token, or GitHub write access to the victim repository.

### Likelihood Explanation
Exploitability requires the deployment to use Shipit's multi-organization `secrets.github` schema with at least one organization controlled by an untrusted/lower-trust party and at least one other organization whose stacks are more sensitive — a configuration explicitly supported by `Shipit.github_app_config` [9](#0-8) . Given that configuration, no additional preconditions are needed: the attacker only needs to know their own organization's webhook secret (which they legitimately possess, since they configured/received it) and can compute a valid signature and submit an arbitrary JSON body directly to the public webhook endpoint.

### Recommendation
In `WebhooksController#verify_signature`, after successfully verifying the signature, cross-check that the organization used to select the webhook secret (`repository_owner`) actually matches the owner portion of `repository.full_name` (and of `organization.login` if present) before dispatching to handlers; reject the request (e.g., `head(422)`) on mismatch. Equivalently, have `Handler#repository_name`/`Repository.from_github_repo_name` reject repositories whose owner differs from the organization that was cryptographically verified for this request.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `orga` (attacker-known secret `SECRET_A`) and `orgb` (victim, onboarded with a real `Stack`).
2. Attacker builds a `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, body)>`.
4. POST to `/github/webhooks` (or the mounted webhook path) with that body and signature.
5. `verify_signature` calls `Shipit.github(organization: "orga")`, verifies successfully against `SECRET_A`.
6. `PushHandler#stacks` resolves `Repository.from_github_repo_name("orgb/victim-repo")` and enqueues `GithubSyncJob` against the victim's real stack, despite the request never having been signed by `orgb`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers

        params do
          requires :ref
          requires :after

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
