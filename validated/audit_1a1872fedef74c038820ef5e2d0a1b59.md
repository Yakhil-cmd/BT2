### Title
Unscoped cross-stack write via `Commit.where(sha:)` in `StatusHandler#process` forces merge-queue `merge!` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA with no repository/stack scoping, so a `status` webhook signed for one GitHub repository can write a `codecov/project` status onto a `Commit` row belonging to a different, unrelated stack that happens to share the same SHA (e.g., shared git history from a fork). On a victim stack with `merge_queue_enabled: true`, that spurious `success` status flips `Commit#status`, triggers `stack.schedule_merges`, and lets `ProcessMergeRequestsJob#perform` call `merge_request.merge!` based on the attacker-injected status.

### Finding Description
The broken binding: the intended invariant is `status.stack_id == webhook.authenticated_repository.stack_id`, i.e., a status can only be applied to commits belonging to the stack tied to the repository whose signature was verified. The actual code enforces only `status.sha == webhook.params.sha`, with no stack/repository check: [1](#0-0) 

`WebhooksController#verify_signature` authenticates the payload against `Shipit.github(organization: repository_owner)` — this proves the request came from a legitimate, signed GitHub webhook for *some* org/repo the attacker controls, but it does not bind the SHA being reported to that repository: [2](#0-1) 

`Commit#create_status_from_github!` → `add_status` then unconditionally recomputes `status`, emits hooks, and — critically — calls `stack.schedule_merges` whenever the new status is `pending` or `success`: [3](#0-2) [4](#0-3) 

`ProcessMergeRequestsJob#perform` then merges any pending merge request whose `all_status_checks_passed?` is now true because of the injected status, calling `merge_request.merge!` for the victim stack: [5](#0-4) 

Exploit flow: attacker forks the victim's public GitHub repository (an unprivileged action). Forked repos initially share identical commit SHAs with the upstream/victim repo (git is content-addressed). Attacker sets a commit status (`context: codecov/project`, `state: success`) on their own fork for a SHA that is also tracked as a `Commit` in the victim's Shipit stack (any commit already synced by `GithubSyncJob`, e.g. a PR head or shared ancestor). GitHub signs and delivers this webhook using the attacker's own org's webhook secret, which passes `verify_signature` because that check only validates *who signed it*, not *which stack the SHA belongs to*. `StatusHandler#process` then runs `Commit.where(sha: params.sha)`, matching the victim's `Commit` row too, and writes the attacker-controlled `success` status onto it.

Existing guards fail because: `verify_signature` scopes authentication to `repository_owner`/organization, not to the specific stack/repository being mutated; `drop_unhandled_event` only checks event type; the `ExplicitParameters` schema on `StatusHandler` validates shape (`sha`, `state`, `context`) but never cross-checks `params.repository` against the commit's `stack.repository`; there is no `Repository`-scoped lookup anywhere in `StatusHandler#process`.

### Impact Explanation
An attacker who owns/forks any repository can, via a single legitimately-signed webhook from GitHub, write a status onto a commit belonging to a completely different Shipit stack/tenant they do not control. On a stack with `merge_queue_enabled: true`, this status write is not inert — `Commit#add_status` calls `stack.schedule_merges`, and `ProcessMergeRequestsJob` will call `merge_request.merge!` once `all_status_checks_passed?` becomes true, producing an unauthorized merge action driven by attacker-forged CI signal. This is a cross-tenant "payload for one repository mutating another's stack/commit" and results in an unauthorized merge — matching the Critical impact category.

### Likelihood Explanation
Preconditions: victim stack has `merge_queue_enabled: true` and has already synced (via normal push activity) a `Commit` row with the same SHA the attacker can produce a signed status for. The most practical way to satisfy this is forking the victim repo (shared history SHAs) or having contributed a PR whose head commit was synced into the victim stack's `commits` table. No Shipit secrets, sessions, or API tokens are required — only ordinary GitHub repo/fork permissions the attacker already has over their own repository. The attack is repeatable against any stack sharing SHAs with an attacker-controlled repository.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers like `CheckSuiteHandler`) to the repository that authenticated the webhook: resolve `Repository` from `params.dig('repository', 'full_name')` (or organization + name) first, then constrain `Commit.where(sha: params.sha, stack: repository.stacks)` (or equivalent join through `Stack#repository`) before calling `create_status_from_github!`, rejecting/ignoring commits belonging to stacks whose repository does not match the authenticated payload.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or extending `commits_test.rb`):
1. Create two stacks/repositories, `victim_repo`/`victim_stack` (merge_queue_enabled: true, required status context `codecov/project`) and `attacker_repo`/`attacker_stack`, each with a `Commit` sharing identical `sha: "deadbeef..."`.
2. Create a pending `MergeRequest` on `victim_stack` for that commit that is otherwise ready to merge except for the missing `codecov/project` status.
3. Post a `status` webhook payload with `repository.full_name = attacker_repo.full_name` (stubbing `verify_signature` to true, matching existing test pattern), `sha` = shared sha, `context: 'codecov/project'`, `state: 'success'`.
4. Assert: `victim_stack.commits.find_by(sha: sha).statuses.where(context: 'codecov/project').exists?` becomes true — i.e., a status was written for `victim_stack` even though the payload's `repository.full_name` was `attacker_repo`.
5. Assert `ProcessMergeRequestsJob` is enqueued for `victim_stack`, and/or simulate job execution and assert `merge_request.reload.merged?` becomes true — proving the equality `status.stack_id == authenticated_repository.stack_id` is violated and drives an unauthorized `merge!`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
