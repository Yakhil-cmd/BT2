### Title
Delegate revocation via `remove_delegate` can be frontrun by the delegate draining the account - (File: contracts/controller/src/account.rs)

### Summary
`remove_delegate` is the only way an account owner revokes a position-manager delegate's authority, and the grant is binary — the owner cannot scope the delegate's power at grant time (no spending cap, expiry, or per-action permission). A delegate that observes a pending revocation transaction can frontrun it with `borrow(..., to = delegate)` or `withdraw(..., to = delegate)`, extracting the account's entire borrowing capacity or free collateral in the window before the revocation lands.

### Finding Description
The bug class in the reference report is: a reactive on/off flag (`toggleRoll`) is the only defense against an unwanted counterparty action, and the counterparty can frontrun the flag change to take the action anyway.

XOXNO Lending's analogue is delegate authority:

- Grants and revocations both flow through `set_account_delegate`, which only toggles membership in the owner's delegate list — there is no cap, expiry, or scoping on what a delegate may do while listed (`contracts/controller/src/account.rs:242-275`).
- `is_owner_or_delegate` treats a listed delegate identically to the owner for all spending verbs (`contracts/controller/src/account.rs:115-140`).
- `process_borrow` lets the delegate send the borrowed funds to itself (`to` defaults to `caller`, and `require_external_recipient` only excludes the pool and controller), drawing full debt against the victim's collateral (`contracts/controller/src/positions/debt.rs:33-57`). `withdraw` works the same way for unencumbered collateral.

So when an owner submits `remove_delegate(caller, account_id, delegate)`, the delegate — a contract or bot by design, since delegates must be registered active position managers — can observe the revocation and submit `borrow`/`withdraw` first (or land in an earlier position in the same ledger on Stellar's ordered transaction sets). The revocation then removes a grant whose value has already been extracted.

The design even acknowledges reactivation semantics: stale grants persist and reactivate if the NFT returns to the granting owner (`contracts/controller/src/storage/account.rs:223-247`), so revocation is explicitly a reactive, ordering-sensitive control rather than a preventive one.

### Impact Explanation
A delegate being revoked can, in the pre-revocation window, borrow the account's entire remaining capacity to its own address — converting the owner's collateral into bad debt or forced liquidation losses — or withdraw all non-locked collateral. This is theft of user funds / protocol insolvency bounded only by the account's solvency limits, which the borrow leg re-proves but does not prevent since the delegate drains exactly to the solvency boundary.

### Likelihood Explanation
Requires the victim to have delegated an active position manager (the normal intended usage — delegates are governance-approved managers meant to be bots), and the owner must later revoke. Delegates are persistent software agents that can monitor transaction submission cheaply; the race window exists on every revocation. The delegate is not a privileged protocol role — it is an ordinary address the owner chose to trust — so the path is reachable by an unprivileged actor once granted.

### Recommendation
Allow the owner to scope the grant at `add_delegate` time — e.g., per-delegate borrow/withdraw caps, a TTL, or a permission bitmask — so revoking is not the only defense and frontrunning yields bounded loss. Alternatively or additionally, apply a one-ledger (or N-ledger) cooldown between `remove_delegate` becoming effective, during which the delegate cannot spend but the owner can still unwind safely; or provide `remove_delegate` plus an atomic "revoke-and-freeze" that blocks delegate spending from the next ledger sequence.

### Proof of Concept
1. Owner Alice supplies 10,000 USDC collateral on account `A`.
2. Governance activates manager contract `M`; Alice calls `add_delegate(Alice, A, M)` (`contracts/controller/src/account.rs:229-232`).
3. Alice submits `remove_delegate(Alice, A, M)` (`contracts/controller/src/account.rs:235-238`).
4. `M` observes the pending revocation and submits, ordered ahead of it: `borrow(M, A, [(hub, USDC_market_debt_token), max_amount], to = M)` — `require_owner_or_delegate` passes because the grant is still live, and `to = M` pays `M` directly (`contracts/controller/src/positions/debt.rs:43-47`).
5. `M`'s borrow executes first; Alice's `remove_delegate` then succeeds but the debt and extracted funds remain. Alice's account is left at the solvency boundary, exposed to liquidation at the bonus.
