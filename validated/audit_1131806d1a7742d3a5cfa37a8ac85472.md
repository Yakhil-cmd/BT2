## Analysis

The PoolTogether bug is a "verification gate that can be silently satisfied" pattern: a value that should gate an action (the available balance) can end up not actually constraining the action under certain conditions. The closest analog in `shipit-engine` is in the webhook-authentication path, where the signature check that is supposed to gate all webhook-driven writes can be silently satisfied (always pass) for a given GitHub organization, while the write path (team/membership mutation, which feeds directly into the app's authorization system) still fully executes.

### Root cause

`GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as "always verified": [1](#0-0) 

`WebhooksController#verify_signature` picks which `GitHubApp` (and therefore which secret) to check against using an **attacker-controlled field from the unauthenticated JSON body itself** (`repository.owner.login` / `organization.login`), then treats a `true` result as full authentication for the entire payload: [2](#0-1) 

`webhook_secret` is documented and shipped as **optional**, and is `nil` by default in every example/template configuration (`config/secrets.development.example.yml`, `test/dummy/config/secrets.yml`, `template.rb`): [3](#0-2) [4](#0-3) 

If an operator (or a multi-org config where a second org is added without a secret, as in `test/dummy/config/secrets_double_github_app.yml`) leaves `webhook_secret` blank, then **any unauthenticated internet client** can POST forged webhook events to `/webhooks` for that organization, and they will be processed as fully "verified" GitHub events.

One of the built-in webhook handlers is `membership`, which creates/updates `Team` and `Membership` records directly from the (now-unverified) payload: [5](#0-4) 

`User#authorized?` — the gate used by `Shipit::Authentication#force_github_authentication` to decide whether a logged-in GitHub identity may use the whole application — is computed purely from `Team`/`Membership` rows: [6](#0-5) [7](#0-6) 

### Binding broken

`signature verified for organization O` (should imply "payload genuinely originates from GitHub for O") is asserted to equal `true` even when **no cryptographic check ever occurred**, because `verify_webhook_signature` short-circuits to `true` when `webhook_secret` is absent — yet the downstream write path (team/membership mutation, which is the exact data `authorized?` and thus `Shipit.github_teams` authorization relies on) executes identically to the case where a real signature was checked.

- Before: `webhook_secret` unset ⇒ `verify_webhook_signature` returns `true` unconditionally ⇒ any POST to `/webhooks` with a plausible `organization.login`/`repository.owner.login` is accepted as legitimate.
- After: attacker submits a forged `membership` event (`action: added`, `member: {login: attacker_login}`, `team: {slug: <team required by Shipit.github_teams>}`) ⇒ `Team`/`Membership` rows are created ⇒ attacker's `User#authorized?` becomes `true` ⇒ attacker bypasses the GitHub-team authorization gate for the entire Shipit UI/API without ever completing OAuth as a team member.

This is a genuine "escalation into `Shipit.github_teams` authorization" (explicitly listed accepted High impact), reachable by a completely unprivileged, unauthenticated network attacker, requiring no Shipit session, API token, or GitHub credentials — only that the deployment left `webhook_secret` unset for the targeted organization, which is the shipped default in every example/template configuration this engine provides.

### Uncertainty

I could not fully trace whether the multi-org lookup in `Shipit.github(organization:)` could itself be tricked into resolving to a *different, secret-protected* org's `GitHubApp` object in a way that bypasses even a configured secret (e.g., case normalization or unknown-org fallback edge cases) — that would require deeper reading of `lib/shipit.rb`'s `github` method and `GithubOrganizationUnknown` handling, which I did not have iterations left to fully inspect. The finding above stands independent of that: it only depends on at least one configured organization having a blank `webhook_secret`, which is the documented, shipped default.

### Title
Webhook signature verification silently passes when `webhook_secret` is unset, allowing unauthenticated forgery of `membership` events that escalate into `Shipit.github_teams` authorization - (File: lib/shipit/github_app.rb)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` without performing any cryptographic check when `webhook_secret` is blank, which is the default/example configuration shipped by the engine. `WebhooksController` treats that boolean as full proof the payload came from GitHub and then dispatches attacker-controlled JSON to handlers, including the `membership` handler that mutates `Team`/`Membership` records — records that directly back `User#authorized?`.

### Finding Description
`verify_signature` selects the `GitHubApp` to validate against using a field taken from the still-unverified request body (`repository.owner.login`), then calls `verify_webhook_signature`, which is a no-op success when that organization's `webhook_secret` is `nil`/blank [1](#0-0) . Because every shipped example config (`config/secrets.development.example.yml`, `test/dummy/config/secrets.yml`, `template.rb`) leaves `webhook_secret` empty by default, an operator can very plausibly run in this state. Once "verified," `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs unauthenticated, attacker-supplied JSON through built-in handlers, including the one that creates `Team`s and appends `Membership`s [5](#0-4) . `User#authorized?` is derived solely from `Membership`/`Team` rows [6](#0-5) , and is the sole gate enforced by `Shipit::Authentication` for every non-webhook controller [7](#0-6) .

### Impact Explanation
An unauthenticated attacker who can reach `/webhooks` can forge a `membership` event granting themselves membership in a team listed in `Shipit.github_teams`. Once they subsequently complete a normal GitHub OAuth login (with any GitHub account, since membership was fabricated server-side), `authorized?` returns `true` and they gain full access to Shipit's stacks, deploys, and tasks — an escalation into `Shipit.github_teams` authorization, one of the explicitly accepted High-severity impacts.

### Likelihood Explanation
Likelihood depends entirely on whether the operator leaves `webhook_secret` blank for a configured GitHub organization — which is the value in every shipped example/template config, making misconfiguration plausible in real deployments, especially multi-org setups where a second org's secret is easy to omit (as seen in `test/dummy/config/secrets_double_github_app.yml`).

### Recommendation
Fail closed instead of open: `verify_webhook_signature` should reject (or the controller should require) a non-blank `webhook_secret` per organization, or at minimum refuse to process trust-sensitive events (`membership`) when no secret is configured, rather than silently treating an absent secret as "verified."

### Proof of Concept
1. Deploy Shipit with an organization configured with `webhook_secret: nil` (the shipped default).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": { "login": "<target-org>" },
  "team": { "id": 1, "slug": "<team-in-Shipit.github_teams>", "name": "Team", "url": "https://example.com" },
  "member": { "login": "attacker-github-login" }
}
```
No `X-Hub-Signature` (or any garbage value) is required, since `verify_webhook_signature` short-circuits to `true` for the blank-secret org [8](#0-7) .
3. A `Membership` row is created for `attacker-github-login` in the required team, matching the behavior demonstrated in `test/controllers/webhooks_controller_test.rb` [9](#0-8) .
4. Attacker logs in via GitHub OAuth as `attacker-github-login`; `User#authorized?` now returns `true`, granting full Shipit access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
```
