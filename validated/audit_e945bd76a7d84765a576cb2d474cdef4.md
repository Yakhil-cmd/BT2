### Title
Webhook signature verification uses `repository.owner.login` while state mutation uses `repository.full_name`, letting a no-secret-org attacker forge `pull_request` events that write to any other repository's stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check based solely on `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) , and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's config has a blank `webhook_secret` [3](#0-2) . Nothing ties the verified `owner.login` to the `repository.full_name` that `LabelCapturingHandler` later uses to locate the target `Repository`/`ReviewStack` [4](#0-3) , so an attacker can authenticate as a no-secret org while pointing the payload's `repository.full_name` at an unrelated victim repository.

### Finding Description
The claimed invariant is: `verified_organization(request) == repository.full_name.owner(payload)`, i.e. the event should only be able to mutate state belonging to the organization/repository whose secret authenticated the request. Tracing the code shows this equality is never enforced.

1. `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` reads `params.dig('repository','owner','login')` [1](#0-0) .
2. `GitHubApp#verify_webhook_signature` short-circuits to `true` when `@webhook_secret` (from that organization's Shipit config) is blank [3](#0-2) . If the attacker's chosen `repository.owner.login` maps to a Shipit-configured organization with no `webhook_secret`, the request is accepted with any/no signature.
3. `WebhooksController#create` then parses the raw body and dispatches to handlers with the **full attacker-controlled** `params`, including whatever `repository.full_name` the attacker put in the body [5](#0-4) .
4. `LabelCapturingHandler#repository` resolves the target `Repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5) , and `Repository.from_github_repo_name` simply splits that string on `/` and does a `find_by(owner:, name:)` lookup [7](#0-6) . There is no check that this owner matches `repository.owner.login` used in step 1.
5. `review_stack` then locates the actual `ReviewStack` by `environment: "pr#{params.number}"` scoped to that resolved repository's `review_stacks` [8](#0-7) [9](#0-8)  — a real record for an unrelated, potentially fully-secured victim organization/repository.
6. For `action=reopened` (and `opened`/`labeled`/`unlabeled`), `capture_labels?` becomes true once a matching stack exists and isn't archived [10](#0-9) , and `capture_labels` persists `params.pull_request.labels.map(&:name)` — fully attacker-controlled strings — onto the victim's real `PullRequest` record [11](#0-10) .

Note: contrary to the question's framing, this handler's stack lookup is keyed by `repository.full_name` + PR number, not by commit SHA, so the "shared commit SHA" precondition is not actually required to reach `capture_labels`; it is a red herring for this specific handler. The real, and sufficient, exploit primitive is the decoupling of the org used for signature verification from the `repository.full_name` used for the write.

None of the listed guards catch this: `drop_unhandled_event` only checks the event type is registered [12](#0-11) ; `ExplicitParameters` (the `params do ... end` schema) only validates shape/types, not cross-field consistency between `repository.owner.login` and `repository.full_name` [13](#0-12) ; and `Repository` model validations only constrain format of `owner`/`name` on creation, not on lookup [14](#0-13) .

### Impact Explanation
An unauthenticated attacker can cause a webhook payload nominally "from" a no-secret organization to write into a `PullRequest`/stack belonging to a completely different, unrelated, possibly properly-secured repository — a payload for one repository mutating another's records, matching the Critical category explicitly listed in scope. The immediate effect demonstrated is corruption of `PullRequest#labels` on the victim's real review stack, driven entirely by attacker-supplied strings; per the question's own description this label list feeds into `ReviewStack#env` as uppercased environment keys, which would propagate attacker-controlled data into the victim's deploy environment (not independently re-verified in this trace, but consistent with `capture_labels`'s direct write path). This is repeatable against any Shipit organization configured with a blank `webhook_secret`, for any repository/PR number the attacker can guess or enumerate, with no rate limiting or authentication required.

### Likelihood Explanation
Preconditions: Shipit must have at least one organization configured without a `webhook_secret` (this is an operator configuration choice, but the vulnerable code path (`return true unless webhook_secret`) treats it as an implicit "no verification needed" rather than failing closed) [15](#0-14) . Given that, attacker cost is a single unauthenticated `POST /webhooks` with `X-Github-Event: pull_request` and a JSON body where `repository.owner.login` names the no-secret org and `repository.full_name`/`number` name the victim's real repo/PR. No secrets, tokens, or GitHub state on the attacker's side are needed beyond knowing the victim's `owner/repo` and an existing PR number (both are typically public/discoverable). Fully repeatable.

### Recommendation
Fail closed instead of open when `webhook_secret` is blank in `GitHub App#verify_webhook_signature`, and additionally require that the organization used to select the verifying config (`repository.owner.login`) matches the owner segment of the `repository.full_name` used by handlers before dispatching, rejecting mismatched payloads in `WebhooksController#verify_signature`.

### Proof of Concept
Minitest (webhooks_controller_test.rb style), no live GitHub:
```ruby
test "pull_request reopened with no-secret org owner writes to unrelated victim repository's PullRequest" do
  # Setup: victim repo/org configured WITH webhook_secret; attacker org configured WITHOUT webhook_secret
  victim_repo = shipit_repositories(:shipit) # owner/name with real ReviewStack + PullRequest, secret configured
  no_secret_org = "no-secret-org" # Shipit.github(organization: "no-secret-org").config has no webhook_secret

  before_labels = victim_repo.review_stacks.first.pull_request.labels

  payload = {
    action: "reopened",
    number: victim_pr_number,
    pull_request: { ... head: { sha: attacker_sha, ref: "..." }, labels: [{ name: "INJECTED_ENV=evil" }], ... },
    repository: { owner: { login: no_secret_org }, full_name: victim_repo.github_repo_name },
    sender: { login: "attacker" }
  }.to_json

  post "/webhooks", params: payload, headers: {
    "X-Github-Event" => "pull_request",
    "X-Hub-Signature" => "sha1=deadbeef" # bogus/irrelevant
  }, as: :json

  assert_response :ok
  after_labels = victim_repo.review_stacks.first.pull_request.reload.labels
  refute_equal before_labels, after_labels
  assert_includes after_labels, "INJECTED_ENV=evil"
end
```
This asserts the binding `verified_organization == repository.full_name.owner` is violated: verification succeeds for `no-secret-org`, yet the write lands on `victim_repo`, whose owner differs and whose own `webhook_secret` was never checked.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
