### Title
Cross-organization webhook spoofing via mismatched `repository.owner.login` and `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook against using `repository.owner.login` (or `organization.login`), but the event handlers that decide **which Stack/Repository in the database gets acted on** use a completely different field, `repository.full_name`, taken from the same unauthenticated JSON body. Nothing binds these two fields together, so a party who legitimately controls one organization's webhook secret can forge a payload that is verified against their own org's secret while making the handlers operate on a Stack belonging to a different (victim) organization/repository.

to pick the `Shipit.github(organization: ...)` config (and therefore the HMAC secret) used to verify `X-Hub-Signature`.

Once verification passes, `create` dispatches the raw, still-untrusted JSON to the registered handler: [3](#0-2) 

Every handler (e.g. `PushHandler`) determines the target Stack purely from `repository.full_name`, a field independent of `repository.owner.login`: [4](#0-3) [5](#0-4) 

Because the HMAC only proves "this payload was produced by someone who knows organization X's webhook secret," and the org used for that check (`repository.owner.login`) is a different JSON key than the one used to resolve the acted-upon Stack (`repository.full_name`), the equality the app implicitly relies on — *"the organization whose secret verified the signature" == "the organization that owns the repository being modified"* — is never enforced. An attacker who owns/administers their own GitHub App installation (organization "attacker-org", a credential they can legitimately obtain without any Shipit access) can send:

```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
signed with `attacker-org`'s real webhook secret. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')`, verifies successfully (attacker knows this secret), and the request proceeds. `PushHandler` then looks up the Stack for `victim-org/victim-repo` (via `repository_name`/`stacks`) and calls `stack.sync_github(expected_head_sha: params.after)`, letting the attacker drive sync behavior — including an attacker-chosen `expected_head_sha` — against a Stack they have no authorization over.

This is the direct analog of the Sherlock H-1 bug class: a verified/trusted binding (which tier boundary a removal check applies to) is computed from stale/incorrect state instead of the actually-affected entity, silently corrupting the intended invariant. Here, the verified binding is "which org's secret authorizes this payload," while the entity actually mutated is chosen from an unrelated, unauthenticated field in the same payload.

### Impact Explanation
This crosses the "organization authenticated vs. repository written" boundary called out explicitly in scope rules. An attacker with only their own GitHub App/org (no Shipit credentials, no access to the victim repo) can cause Shipit to process push/status/check_suite/pull_request events against a victim's Stack, influencing `sync_github`, commit/status records, or review-stack lifecycle (archive/unarchive) for repositories they do not control. Depending on which handler is targeted, this ranges from data-integrity corruption (fabricated commit statuses, spurious syncs) up to unauthorized state changes on stacks the attacker has no legitimate relationship to — matching the High-severity class "escalation... unauthenticated ... state" described in the rubric.

### Likelihood Explanation
Any actor can create a free GitHub App/organization and thus legitimately obtain a webhook secret they control. Crafting a payload with mismatched `owner.login` and `full_name` requires no special access — only knowledge of the JSON shape (which is public, documented GitHub webhook format) and one's own secret. No exploitation of the Shipit host, no session, and no GitHub write access to the victim repo are required, satisfying the "unprivileged attacker" bar.

### Recommendation
When verifying and processing a webhook, derive the authorizing organization and the acted-upon repository/organization from the **same** field, and reject the request if the repository referenced by `repository.full_name` (or `organization.login` for org-scoped events) does not belong to the organization whose secret validated the signature (e.g., compare `repository.full_name.split('/').first` against `repository_owner` before dispatching to handlers).

### Proof of Concept
1. Attacker creates GitHub App "attacker-org" per `docs/setup.md`, obtaining its `webhook_secret`.
2. Attacker computes `sha1=HMAC(webhook_secret, body)` for body:
```json
{"ref":"refs/heads/master","after":"<attacker-chosen-sha>","repository":{"full_name":"victim-org/victim-repo","owner":{"login":"attacker-org"}}}
```
3. POST to `/webhooks` with `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and successfully verifies the signature using the attacker's own secret.
5. `PushHandler#process` resolves the Stack via `repository.full_name` = `victim-org/victim-repo` (a field never checked against `attacker-org`) and calls `stack.sync_github(expected_head_sha: params.after)`, acting on the victim's stack despite the signature only proving control of `attacker-org`'s secret.

Note: full downstream impact of `Stack#sync_github`/`GithubSyncJob` (e.g., whether it can trigger deploy/rollback beyond metadata sync) could not be fully traced in this session due to tool-call limits; this should be verified in `app/models/shipit/stack.rb` and `app/jobs/shipit/github_sync_job.rb` before finalizing severity.
