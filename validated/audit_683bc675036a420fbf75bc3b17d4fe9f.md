### Title
Debt-value i128 overflow in interest accrual permanently freezes a market's funds — (`common/src/rates/index.rs`)

### Summary
The NSD report is a remote, repeatable crash of a service path → denial of service. The XOXNO Lending analog is stronger: a permanent one. Every state-changing pool verb (`supply`, `borrow`, `withdraw`, `repay`, `seize_positions`, `net_settle`, `claim_revenue`, `flash_loan`, `create_strategy`) runs `interest::global_sync` → `accrue_chunk` → `accrue_step` → `calculate_supplier_rewards` before mutating. That function computes `borrowed.mul(env, new_borrow_index)` and `borrowed.mul(env, old_borrow_index)` in RAY-scaled `i128`; when total scaled debt value exceeds `i128::MAX`, the checked multiplication panics with `MathOverflow`. The `MAX_BORROW_INDEX_RAY` cap does not prevent this, because the *value* (`shares × index`) overflows long before the *index* reaches its cap whenever the market holds a large principal in a high-decimal asset. Once the panic threshold is crossed, the market is bricked forever: no withdrawal, repayment, liquidation, or bad-debt cleanup can execute, because each accrues first. The repo's own test suite demonstrates exactly this freeze.

### Finding Description
`calculate_supplier_rewards` at `common/src/rates/index.rs:80-83` multiplies the aggregate scaled debt (`borrowed`, already ~`10²⁷` per unit of underlying at RAY) by the new borrow index (also RAY). For an 18-decimal market, `borrowed` scales as `principal × 10¹⁸ × 10²⁷`, so a principal near `10²⁷` units (≈1 billion tokens at 18 decimals) leaves only ~10⁴³ of headroom against `i128::MAX ≈ 1.7×10³⁸` in the product — the test shows the RAY-value ceiling is hit at ~170× index growth, which sustained high-utilization interest reaches in a few years, well below `MAX_BORROW_INDEX_RAY` (see `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`). Because `global_sync` is the first step of `Cache` mutation in `contracts/pool/src/ops/mod.rs:30-34` and `ops::market::accrue` (`contracts/pool/src/ops/market.rs:65-72`), a single panic in accrual blocks every entrypoint touching that `(hub, asset)` market. There is no code path that skips accrual, so the panic is unrecoverable — even `recapitalize`, `seize_positions` (bad-debt write-down) and `claim_revenue` are dead. This mirrors the NSD bug class: an unprivileged input sequence drives the service into a state where the request handler always crashes; here the crash is persistent in state, so a single trigger suffices.

### Impact Explanation
Permanent freezing of funds and a contract unable to operate: once the debt value crosses the i128 ceiling, every supplier's deposit in that market is locked indefinitely, all outstanding borrowers can never repay or be liquidated (accrued bad debt cannot be cleaned either, since `seize_positions`/`net_settle` accrue first), and pending protocol revenue is unclaimable. The test asserts exactly this: after the overflow, `withdraw` and `repay` both fail with `MathOverflow`.

### Likelihood Explanation
The attack path is fully unprivileged: `supply` and `borrow` are open controller entrypoints, and `update_indexes` is a permissionless keeper call (`contracts/controller/src/markets.rs:119-125`, confirmed by `test_permissionless_keeper_endpoints`). An attacker supplies a large amount of a listed high-decimal, low-unit-price asset, borrows near the utilization ceiling against their own collateral, then lets interest compound — calling `update_indexes` periodically to advance accrual — until the debt-value product crosses the ceiling. After that point no one's funds in that market can move. The barrier is capital and time rather than permission: it requires whale-scale principal (or a listed asset with a huge nominal supply) and sustained high utilization, which is why this is not Critical; the freeze window can also be approached faster on steep rate curves at high utilization. Rate-model parameters are governance-set, but caps/curves within documented bounds still reach the cliff, and nothing in the accrual path halts interest or caps total debt value to prevent it.

### Recommendation
Cap the *debt value*, not just the index: make `accrue_step`/`calculate_supplier_rewards` saturate (e.g., clamp `new_total_debt`/`supplier_rewards` to `i128::MAX` via the existing `mul_div_floor_saturating`/`I256` widening used elsewhere in `fp_core`) instead of panicking, so accrual degrades gracefully and later repayments reduce `borrowed` below the ceiling. Alternatively, enforce a borrow-side ceiling in asset/scaled terms per market (scaled `borrowed` bounded so `borrowed × MAX_BORROW_INDEX_RAY ≤ i128::MAX`) and reject borrows that would exceed it — the machinery exists in `calculate_scaled_cap`/`require_cap_within_asset_domain`. At minimum, let `seize_positions`/`repay` run on a last-good-index path so bad debt can still be unwound after the cliff.

### Proof of Concept
```rust
// Adapted from tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))      // 18-decimal listed market
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);

// Attacker: whale-scale supply + ~98% utilization self-funded borrow (permissionless).
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);

// Attacker (or anyone) advances accrual via the permissionless keeper.
loop {
    t.advance_time(YEAR_SECS);
    if t.try_update_indexes_for(&["BIG18"]).is_err() { break; } // MathOverflow
}

// Market permanently bricked: every verb accrues first and hits the same panic.
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
// borrow_index < MAX_BORROW_INDEX_RAY — the index cap never engaged.
```

Root cause: `borrowed.mul(env, new_borrow_index)` overflows `i128` in `common/src/rates/index.rs:80-83`; the panic propagates through `accrue_chunk` (`contracts/pool/src/interest.rs:39-53`), which is invoked unconditionally by `synced_market` (`contracts/pool/src/ops/mod.rs:30-34`) on every market-mutating entrypoint, so the freeze is total and irreversible for that market.
