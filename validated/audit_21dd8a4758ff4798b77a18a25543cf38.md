### Title
`StatusHandler#process` writes `Status` rows to commits across unrelated repositories because it never scopes by `repository_name`/`stacks` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits solely via `Commit.where(sha: params.sha)`, with no filter tying the query to the `repository.full_name` from the incoming webhook payload. Every other handler (`PullRequest::LabeledHandler`, `OpenedHandler`, `ClosedHandler`, etc.) calls `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` before touching any `Stack`/`Commit`, but `StatusHandler` skips this entirely. Because `sha` is only unique per `stack_id` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), not globally, a `status` webhook that is authenticated only for the attacker's own low-privilege repository can write `Status` records against `Commit` rows belonging to any other `Stack` in the database that happens to share the same commit SHA.

### Finding Description
The broken binding: for the write to be safely scoped, `repository_name` (`payload.dig('repository','full_name')` in `app/models/shipit/webhooks/handlers/handler.rb:36-38`) must equal the `full_name` of the `Repository` owning every `Stack` reachable through the `Commit` rows mutated by `process`. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) never computes or checks `repository_name`; it does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This queries `Commit` globally by `sha`, and `create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) writes a `Status` and triggers `Hook.emit(:commit_status, ...)`/`Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` (`app/models/shipit/commit.rb:366-386`) against whatever `stack` that `Commit` belongs to — regardless of which repository the webhook actually came from.

In contrast, `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-34`) scopes lookups to `Repository.from_github_repo_name(repository_name)&.stacks`, and the `PullRequest::*Handler` classes rely on that scoping before mutating any `Stack`/`Commit`/`MergeRequest`. `StatusHandler` is the outlier that bypasses this repository-ownership check.

`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only authenticates that the payload came from the GitHub organization/app owning `repository_owner` in the payload (the attacker's own repo/org) — it does not, and cannot, validate which `Commit`/`Stack` rows the handler subsequently touches. So a webhook that is cryptographically legitimate for the attacker's own repository is nevertheless free to mutate `Commit`/`Status` rows for a completely different repository's `Stack`, as long as a matching `sha` exists in the `commits` table (e.g., via shared git history — forks, subtree merges, cherry-picks, or monorepo splits that preserve identical commit objects/SHAs across repositories tracked as separate Shipit `Stack`s).

### Impact Explanation
An attacker who can only push to / open PRs on their own low-privilege repository (already onboarded to the same Shipit instance/org) can, via a forged-looking-but-legitimately-signed `status` webhook, cause `Status` rows to be created/replaced on `Commit`s belonging to an unrelated `Stack`. This is a cross-repository state mutation exactly matching the Critical category "a payload for one repository mutating another's stack, commit ... record." Downstream effects are severe: `create_status_from_github!` can flip a commit from `pending`/`error` to `success`, which feeds `deployable?`, `schedule_continuous_delivery`, and `stack.schedule_merges` in `app/models/shipit/commit.rb`, potentially triggering an unauthorized deploy or merge on a stack the attacker does not control. This is repeatable against any repository whose commit history overlaps (by SHA) with a repository the attacker controls.

### Likelihood Explanation
Requires: (1) attacker owns/controls a repository already registered with Shipit under an organization whose webhook signature Shipit will accept (this is a normal precondition, not a secret leak), and (2) at least one `Commit` SHA shared between the attacker's repo and the victim `Stack`'s repo — realistic via forks, subtree merges, vendored/cherry-picked commits, or monorepo splits, all of which preserve identical git commit objects (and thus identical SHA1s) without requiring any hash collision attack. Attacker cost is a single POST to `/webhooks` with a validly signed `status` event for their own repo; the flaw is deterministic and repeatable for every shared SHA.

### Recommendation
Scope `StatusHandler#process` to the requesting repository, mirroring `Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
or equivalently join through `Stack`/`Repository` in the `Commit` query so only commits belonging to `Repository.from_github_repo_name(repository_name)` are updated.

### Proof of Concept
Minitest (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, conceptually):
```ruby
test "process does not update commits belonging to a different repository's stack" do
  repo_a = shipit_repositories(:shipit)         # attacker's repo
  repo_b = create_repository(full_name: 'other-org/private-repo') # victim repo
  stack_b = create_stack(repository: repo_b)
  shared_sha = 'a' * 40
  commit_b = create_commit(stack: stack_b, sha: shared_sha)

  payload = {
    'repository' => { 'full_name' => repo_a.full_name },
    'sha' => shared_sha,
    'state' => 'success'
  }

  assert_no_difference -> { commit_b.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(payload).process
  end
end
```
Binding under test: `payload.dig('repository','full_name')` (`repo_a.full_name`) must equal the `full_name` of `commit_b.stack.repository` (`repo_b.full_name`) before `commit_b` may be mutated. Currently they differ, yet `commit_b.statuses.count` changes, demonstrating the cross-repository write. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
