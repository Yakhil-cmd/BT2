### Title
Cross-repository CCMenu API token stack-scope bypass allows unauthorized stack state disclosure - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides `BaseController#stack` with an unscoped `Stack.from_param!(params[:stack_id])` lookup, discarding the `current_api_client.stack_id` scoping that `BaseController#stacks`/`#stack` normally enforce. Any holder of a valid `ApiClient` token scoped to one stack can supply a different `stack_id` in the URL and read that other stack's build/deploy status.

### Finding Description
The broken binding is: `current_api_client.stack_id == stack.id` must hold for every request, but in `CCMenuController` it never does.

Path: `authenticate_api_client` ( [1](#0-0) ) calls `ApiClient.authenticate(params[:token])`, which only verifies the `SimpleMessageVerifier` signature and finds the client `by id` — it never checks `stack_id` against anything ( [2](#0-1) ). `check_permissions!` likewise only checks the permission string, not stack scope ( [3](#0-2) ).

`BaseController` defines a safe, scoped accessor: `stacks` resolves to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `stack` uses `stacks.from_param!(params[:stack_id])` ( [4](#0-3) ). `CCMenuController`, however, overrides this with its own private `stack` method that bypasses the scope entirely: `@stack ||= Stack.from_param!(params[:stack_id])` ( [5](#0-4) ).

`CCMenuUrlController#fetch` is the legitimate token-issuance path: it mints (or reuses) a `read:stack`-only `ApiClient` for the *current* stack and hands the user a URL with `stack_id` for that stack ( [6](#0-5) ). Nothing in this flow binds the *token* itself to a single stack for enforcement purposes — the token's `stack_id` column exists but `CCMenuController` never reads it.

Attacker flow: an unprivileged user with legitimate access to stack A obtains a CCMenu URL (`?token=<A-scoped-token>`) via the normal UI flow. They then request `GET /stacks/:owner/:repo/:env/ccmenu.xml?token=<A-token>&stack_id=<stack-B-param>` where stack B belongs to a different repository/tenant hosted on the same Shipit instance. `authenticate_api_client` accepts the token (valid signature, valid id) and `#stack` resolves stack B unconditionally, so `#show` renders stack B's latest deploy/build status.

Existing guards do not catch this: `require_permission :read, :stack` only checks that the permissions array contains `read:stack` — it says nothing about which stack ( [7](#0-6) ). The scoping mechanism exists in `BaseController#stacks`/`#stack` but is dead code for this controller because it's shadowed by the subclass override.

### Impact Explanation
The attacker exfiltrates build/deploy status (`activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) for any stack on the same Shipit host, regardless of repository ownership, using only a token they were legitimately issued for an unrelated stack. This is an unauthenticated (relative to the target stack) read of stack state across tenants — repeatable against any stack whose `to_param`/id is known or guessable, since `stack_id` params are typically `owner/repo/env`-style slugs. This matches the High severity category: "unauthenticated read of stack state, task streams or deploy output" across tenant boundaries.

### Likelihood Explanation
Preconditions are low-cost and realistic: `Shipit.disable_api_authentication` false (default in most deployments), and the attacker only needs to have been granted a CCMenu URL for any one stack they have legitimate UI access to (e.g., by visiting the stack page and using the "CCMenu" feature). No secrets, GitHub credentials, or elevated roles are required. The `stack_id` param for the target stack is derived from its `owner/repo/environment`, which is typically discoverable/guessable public information. This is trivially repeatable against any number of target stacks with a single held token.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reimplement it using the scoped `stacks` relation from `BaseController`), so lookups honor `current_api_client.stack_id` just like every other API controller: `@stack ||= stacks.from_param!(params[:stack_id])`.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token scoped to stack A cannot read stack B's ccmenu data" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "other", name: "repo"), branch: 'main')

  client_a = ApiClient.create!(creator: @user, name: 'A', permissions: %w[read:stack], stack_id: stack_a.id)

  request.headers['Authorization'] = 'bleh'
  get :show, params: { stack_id: stack_b.to_param, token: client_a.authentication_token }

  # Binding under test: current_api_client.stack_id == stack.id
  assert_not_equal client_a.stack_id, stack_b.id
  assert_response :not_found # or :forbidden, per fix — currently returns :ok with stack_b's data
end
```
