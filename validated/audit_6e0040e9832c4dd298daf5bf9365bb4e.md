### Title
Stack-scoped `read:stack` API token can read the CCMenu status of any stack, bypassing token stack scoping - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController#stack` restricts stack lookups to `current_api_client.stack_id` when the token is scoped to a single stack via `stacks.from_param!`, but `Shipit::Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model. `require_permission :read, :stack` only checks that the `read:stack` permission string is present in the token's permission list; it never checks whether the requested stack matches the token's `stack_id`. An attacker holding a legitimately obtained `read:stack` token scoped to stack A can therefore request the CCMenu XML for any other stack B, including a private/review stack from another organization's pull request, by simply guessing/enumerating its `environment`/slug.

### Finding Description
The intended binding is: for a stack-scoped token, `stack.id == current_api_client.stack_id` must hold for every resource the token can read. `BaseController` enforces this via [1](#0-0) 
where `stacks` is `Stack.where(id: current_api_client.stack_id)` when `stack_id?` is true, and the default `#stack` method calls `stacks.from_param!`, which is scoped by that `where` clause.

`CCMenuController` re-defines `#stack` and calls the unscoped class method instead: [2](#0-1) 

`require_permission :read, :stack` only delegates to `ApiClient#check_permissions!`, which checks `permissions.include?("read:stack")` — it has no knowledge of which stack is being requested: [3](#0-2) 

So for a stack-scoped token (`current_api_client.stack_id` set to stack A, `permissions: ["read:stack"]`), a request to `GET /:stack_id.xml?token=...` for stack B's slug never touches the `stacks` scope — it resolves stack B directly via `Stack.from_param!`, and `require_permission!` passes because the permission string `read:stack` is present regardless of which stack is being addressed. `StacksController#stack`, by contrast, correctly uses `stacks.from_param!` (scoped): [4](#0-3) 

Exploit flow: attacker legitimately obtains a CCMenu URL/token for their own stack A (a normal, permitted "legitimate CCMenu URL fetch"). That token carries `stack_id = A.id`, `permissions = ["read:stack"]`. Attacker then sends `GET /some_review_stack_slug.xml?token=<token>` where the slug identifies stack B — a private `Shipit::ReviewStack` created from another organization's PR. Because `CCMenuController#stack` bypasses the `stacks` scope, `Stack.from_param!("some_review_stack_slug")` returns stack B, and the response renders stack B's latest deploy/rollback status and stack metadata as CCMenu XML.

None of the existing guards catch this: `require_permission!` only validates the permission string, not the stack scope; the `stacks` scope that would have caught it is defined in the base class but deliberately not used by this subclass's override.

### Impact Explanation
A `read:stack` token issued/scoped for one stack can be used to read the deploy/rollback status (name, last deploy id, success/failure state, timestamps) of any other stack on the instance, including private review stacks tied to other organizations' pull requests. This is a cross-tenant unauthorized read of stack state — matching the High-severity category "escalation into ... unauthenticated read of stack state, task streams or deploy output" (here: escalation of a narrowly-scoped token into unlimited-stack read). It's repeatable against arbitrary stacks by iterating over `stack_id`/environment slugs, and doesn't require any secret beyond the attacker's own legitimately-issued scoped token.

### Likelihood Explanation
Preconditions: the Shipit instance must issue stack-scoped API tokens (an intended, supported feature via `ApiClient#stack_id`) and have review stacks/other stacks reachable by guessable slugs (e.g., `pr123`-style environment names, as referenced in `review_stack_adapter.rb`). The attacker only needs to already possess one legitimate, narrowly-scoped `read:stack` token (obtainable by fetching their own permitted CCMenu URL) and to guess/enumerate another stack's `stack_id`/slug — no privileged role, secret, or session is required. This is low-cost and fully repeatable.

### Recommendation
Change `CCMenuController#stack` to use the scoped `stacks.from_param!(params[:stack_id])` (inherited from `BaseController`) instead of calling `Stack.from_param!` directly, so stack-scoped tokens cannot address stacks outside their `stack_id` scope. Remove the overriding `#stack` method entirely if no CCMenu-specific behavior is needed, relying on the base class implementation.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a stack-scoped read:stack token cannot fetch CCMenu XML for a different stack" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cascade) # any other stack, simulating a private review stack

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped-client',
    stack_id: stack_a.id,
    permissions: ['read:stack'],
  )

  # sanity: token works for its own scoped stack
  get :show, params: { stack_id: stack_a.to_param, token: scoped_client.authentication_token }, format: :xml
  assert_response :ok

  # exploit: same token, different stack_id in the URL
  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }, format: :xml

  # Expected (fixed) behavior: 404/forbidden, i.e. stack.id != current_api_client.stack_id must be rejected
  assert_response :not_found
  # Actual (vulnerable) behavior observed: :ok, with stack_b's CCMenu XML rendered
end
```
This asserts the binding `stack.id == current_api_client.stack_id` (for scoped tokens) both before (stack A, passes) and after (stack B, should fail but currently succeeds), demonstrating the divergence caused by `CCMenuController#stack` bypassing the `stacks` scope.
