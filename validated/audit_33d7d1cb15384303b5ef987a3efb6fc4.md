Confirmed vulnerability. Here is the analog analysis.

### Title
Webhook signature verification keyed on `repository.owner.login`/`organization.login` while event dispatch is keyed on `repository.full_name`, allowing forged webhook events against any Stack/Team when any configured GitHub org has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound webhook based on `repository_owner`, a value read straight out of the untrusted JSON payload (`repository.owner.login` or, as a fallback, `organization.login`). `Shipit::Webhooks::Handlers::Handler#stacks`/individual handlers, however, resolve *which repository/stack/team is actually mutated* using a different field of the same untrusted payload: `repository.full_name` (or, for membership events, `organization.login` combined with an attacker-supplied `team.id`). Because these two payload fields are never checked against each other, and because `GitHubApp#verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for the organization selected for verification, an attacker can pick any organization without a configured secret to pass authentication and then supply a `repository.full_name`/`team`/`organization` referencing a completely different, protected organization's stack to have handlers act on it.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) short-circuits when no secret is configured for that organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

The multi-organization configuration format documented in `docs/setup.md:182-209` and exemplified in `config/secrets.development.shopify.yml` explicitly allows some organizations to have `webhook_secret: # nil`, i.e. no secret at all — a supported, non-privileged deployment state, not a misconfiguration requiring credentials.

Once `verify_signature` passes, `create` re-parses the same raw body and dispatches to handlers purely by event name:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Handlers resolve their target stack/repository from a *different* payload field, `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login` used above for authentication:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler` uses this to enqueue a real sync against any matching stack:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

`MembershipHandler` is even more direct: it trusts `organization.login` (a payload field) to create/attach a `Team`, and `team.id`/`member.login` to add/remove memberships, again independent of whichever organization's key was used for signature verification:
```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added' then team.add_member(member)
  when 'removed' then team.members.delete(member)
  end
end

def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [6](#0-5) 

`Team#members` participates directly in authorization: `User#authorized?` is gated on membership in any `Shipit.github_teams`-derived team (see `test/models/users_test.rb:252-265`), so forging membership additions against an existing `Team` record lets an unprivileged external actor add an arbitrary GitHub login as a member of a Shipit-recognized team. `PullRequest::ClosedHandler`/`UnlabeledHandler`/`LabeledHandler` similarly call `stack.archive!`/`unarchive!`/`review_stack.archive!` keyed only off `repository.full_name`.

This is the same class of defect as the reference report: a value is checked/authenticated (the organization owning the webhook secret) while a *different* value drives the actual state-changing action (the repository/team/stack acted upon), and nothing enforces that the two must agree — an equality the code implicitly assumes but never verifies: `authenticated_organization == owner(repository_written_to)`.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out in scope. Concretely, for any deployment where at least one configured GitHub organization has no `webhook_secret` (a supported, documented configuration, not a misconfiguration requiring credentials or privileged access), an unauthenticated internet attacker who knows/guesses that organization's login can:
- Force `GithubSyncJob`/`CacheDeploySpecJob` execution and continuous-delivery evaluation against arbitrary tracked stacks under any other organization (`PushHandler`).
- Archive/unarchive arbitrary review stacks or stacks belonging to any tracked repository, regardless of organization (`PullRequest::ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`).
- Create a `Team` object or add/remove arbitrary GitHub logins as members of an existing `Team`, directly manipulating the `Shipit.github_teams` authorization graph used by `User#authorized?` (`MembershipHandler`).
- Trigger `RefreshCheckRunsJob`/`RefreshStatusesJob` for arbitrary stacks (`CheckSuiteHandler`, out of documented scope of grep results but same dispatch pattern).

The membership-manipulation path meets the "High" bar explicitly listed (escalation into `Shipit.github_teams` authorization). No `ApiClient` token, GitHub App private key, or webhook secret for the *targeted* organization is required — only knowledge of some other configured organization's login that happens to lack a secret, which is visible from any Shipit UI/README/public GitHub org listing.

### Likelihood Explanation
Likelihood is credible but conditional: it requires the deployment to use the multi-organization `secrets.github` schema with at least one organization configured without a `webhook_secret`. This is a first-class, documented configuration (`docs/setup.md`, `config/secrets.development.shopify.yml`), not a hypothetical misuse, and webhook secrets are frequently left unset in early-stage or internal-only integrations since GitHub does not require one. Any instance meeting this condition is exploitable by a purely unauthenticated network attacker who can reach the webhook endpoint (unauthenticated by design, since it's meant to receive GitHub webhooks) and knows any one weak-secret org's login and any target repo's `full_name`.

### Recommendation
Verify the webhook signature using a secret tied to the *same* entity that the handler will act upon, not a payload-supplied field chosen before parsing intent. Concretely:
- Reject webhooks where `repository.owner.login` (or `organization.login`) does not match the owner of `repository.full_name` used later by handlers.
- Do not allow any organization's `verify_webhook_signature` to return `true` unconditionally when unconfigured; treat a missing `webhook_secret` as "reject all webhooks for this org" (or require an explicit opt-in flag), rather than silently authenticating everything.
- Have `Handler#stacks`/`repository_name` derive the repository from the same verified identity used in `verify_signature`, e.g. pass the authenticated organization through to handlers and assert equality before performing any write.

### Proof of Concept
Preconditions: `secrets.github` configured with the multi-org schema, where `OrgWeak` has `webhook_secret: nil` and `OrgStrong/valuable-repo` is a real, secret-protected stack.

1. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 1, "name": "Anything", "slug": "anything", "url": "https://example.com" },
  "organization": { "login": "OrgWeak" },
  "member": { "login": "attacker-controlled-login" },
  "repository": { "owner": { "login": "OrgWeak" }, "full_name": "OrgWeak/whatever" }
}
```
No `X-Hub-Signature` header, or any garbage value, is required.
2. `verify_signature` resolves `repository_owner` = `"OrgWeak"`, calls `Shipit.github(organization: "OrgWeak").verify_webhook_signature(...)`, which returns `true` immediately because `webhook_secret` is blank for `OrgWeak` (`lib/shipit/github_app.rb:76-77`).
3. `create` dispatches to `MembershipHandler`, which (per `app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`) finds or creates `Team` with `github_id: 1` and adds `attacker-controlled-login` as a member — using `team.id`/`organization.login` fields the attacker fully controls, unrelated to any org that actually owns a valid secret.
4. If `team.id` 1 corresponds to a real team backing `Shipit.github_teams`, `attacker-controlled-login`'s associated `User` becomes `authorized?` per `test/models/users_test.rb:262-265` logic, without ever presenting a valid signature for the organization that owns that team.

<br>

Related note (not escalated as a separate finding, but part of the same root-cause pattern): the same "field checked vs. field acted upon" mismatch exists between `EnvironmentVariables.permit` validation (keyed on `stack.cached_deploy_spec.deploy_variables`, computed from the latest reachable commit) and the actual environment injected by `TaskCommands#env`, which merges `@task.env` unfiltered and executes against whatever commit's `shipit.yml` is checked out (`app/models/shipit/deploy_spec.rb:174-180`, `lib/shipit/task_commands.rb:33-48`). This path, however, requires an authenticated `ApiClient` with `deploy:stack` permission to reach `build_deploy`/`trigger_deploy`, which is explicitly out of scope per the rules (requires an `ApiClient` token), so it is not escalated as a standalone finding here.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
