### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup enables unauthorized continuous deployment - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the commit(s) to update purely by `sha`, with no check that the sha belongs to the same repository/stack as the webhook's authenticated organization. Because `verify_signature` in `WebhooksController` only verifies that the payload's `repository.owner.login` matches the organization whose `webhook_secret` produced the signature, an attacker who controls any GitHub organization with a validly-configured Shipit webhook can post a genuinely-signed, real `status` event referencing a sha that also exists as a `Commit` in a completely different (victim) stack, and Shipit will happily attach a fabricated `success` status to that victim's commit.

### Finding Description
The broken binding is: `commit.stack.github_repo_name (real CI provider for the sha)` == `organization authenticated by verify_signature for this delivery`. The code never establishes this equality.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) resolves `Shipit.github(organization: repository_owner)` from the payload's own `repository.owner.login`/`organization.login` and checks the HMAC signature against that org's `webhook_secret`. This only proves the request came from *some* org whose secret matches the payload's claimed owner — it says nothing about which `Commit`/`Stack` rows the payload's `sha` will subsequently touch. [1](#0-0) [2](#0-1) 

- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This query is **global across all stacks** — it is not scoped to the repository/organization that authenticated the request. [3](#0-2) 

- `Commit#create_status_from_github!` unconditionally records the status using `stack_id` (the victim stack's id, since that's the commit's own `stack_id`), not the org that sent the webhook: [4](#0-3) 

- `Commit#deployable?` treats any `success?` status (with no blocking) as deployable, regardless of provenance: [5](#0-4) 

- `Stack#trigger_continuous_delivery` → `next_commit_to_deploy` → `deployable_commits` (via `Commit#deployable?`) will then pick this "deployable" commit and call `trigger_deploy(commit, Shipit.user, ...)`, running a real deploy: [6](#0-5) 

**Exploit flow:** an attacker who owns any GitHub organization/repository with a Shipit stack (and thus a real, valid `webhook_secret`) can:
1. Get a commit with the exact same sha as the victim's queued head commit into their own repository's git history (trivially true for a PR: a fork's branch commit shares the identical sha with the same commit once fast-forward-merged into the victim's default branch — git shas are content-addressed and identical for identical commit objects across repos/forks).
2. Have GitHub (legitimately, for their own repo) or themselves directly POST a `status` webhook to `/webhooks` with `sha` = that shared sha, `state: 'success'`, `context` = the victim stack's `ci.require` context. Since this is signed with the attacker's own org's real `webhook_secret`, `verify_signature` passes.
3. `StatusHandler#process` matches `Commit.where(sha: ...)` across **all** stacks in the DB, finds the victim's `Commit` row (same sha, different `stack_id`), and calls `create_status_from_github!` on it, inserting a `success` status credited to the victim stack, as if the victim's own CI had passed.
4. `ContinuousDeliveryJob#perform(victim_stack)` → `trigger_continuous_delivery` → `next_commit_to_deploy` now sees this commit as `deployable?` and triggers `trigger_deploy` as `Shipit.user`, deploying code that the victim's real CI never actually validated.

None of the existing guards (`verify_signature`, `ExplicitParameters` schema on `StatusHandler`, `force_github_authentication`, `Repository`/`Stack` validators) check that the `Commit` rows touched by a webhook belong to the stack/repository that authenticated the delivery.

### Impact Explanation
This lets an attacker who legitimately controls only their own GitHub org/repo forge a CI-passing status on an arbitrary victim Shipit stack whenever a shared commit sha exists (a routine occurrence via forks/PRs), causing an unauthorized deploy of code the victim's own CI never certified. This is a cross-tenant payload from one repository mutating another repository's `Commit`/`Stack` state, matching the Critical impact category ("a payload for one repository mutating another's stack, commit... or an unauthorized deploy").

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment: true`, a cached deploy spec, no active task, and a `ci.require` context (all common production configurations); attacker needs their own onboarded GitHub org/repo in Shipit (a normal, unprivileged action for any Shipit-managed tenant) and a commit sha shared with the victim (trivial via forking/PR fast-forward-merge workflows). No secrets, sessions, or elevated roles are required — only the attacker's own valid webhook credentials for their own repo. This is repeatable against any victim stack whose queued commit sha the attacker can reproduce.

### Recommendation
Scope the webhook's effect to the repository/organization that authenticated it. In `StatusHandler#process`, restrict the `Commit` lookup to commits belonging to stacks whose `Repository` matches the payload's `repository.full_name`/owner (e.g., `Commit.joins(:stack).merge(Stack.where(repository: repository_from_payload)).where(sha: params.sha)`), rather than a bare global `Commit.where(sha:)`. Apply the same repository-scoping check to any other webhook handler that resolves records purely by sha/id without validating the payload's `repository` against the target stack's repository.

### Proof of Concept
```ruby
# minitest, e.g. test/controllers/webhooks_controller_test.rb style
test "status webhook from attacker org cannot forge status for victim stack sharing sha" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment: true, ci.require configured
  victim_commit = victim_stack.next_commit_to_deploy_candidate_with_shared_sha # commit whose sha also exists in attacker's org's repo history

  attacker_owner = 'attacker-org'
  # Attacker's org has a real, validly configured webhook_secret in Shipit
  GithubHook.any_instance.stubs(:verify_signature) # not used; real signature check exercised
  Shipit.stubs(:github).with(organization: attacker_owner).returns(
    stub(verify_webhook_signature: true)
  )

  body = {
    sha: victim_commit.sha,
    state: 'success',
    context: victim_stack.cached_deploy_spec.required_statuses.first,
    repository: { owner: { login: attacker_owner } }
  }.to_json

  @request.headers['X-Github-Event'] = 'status'

  assert_difference -> { victim_commit.statuses.count }, 1 do
    post :create, body:, as: :json
  end

  freeze_time do
    assert_difference -> { Deploy.count }, 1 do
      ContinuousDeliveryJob.perform_now(victim_stack)
    end
  end

  # Binding check: the org that authenticated (attacker_owner) != victim_stack.repository.owner,
  # yet a Deploy was created for victim_stack purely from attacker's authenticated request.
  assert_not_equal attacker_owner, victim_stack.repository.owner
  assert victim_stack.deploys.last.present?
end
```

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin
        trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
      rescue Task::ConcurrentTaskRunning
      end
    end

    def schedule_merges
      ProcessMergeRequestsJob.perform_later(self)
    end

    def next_commit_to_deploy
      commits_to_deploy = commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)
      if maximum_commits_per_deploy
        commits_with_max_applied = commits_to_deploy.limit(maximum_commits_per_deploy)
        deployable_commits(commits_with_max_applied) || deployable_commits(commits_to_deploy)
      else
        deployable_commits(commits_to_deploy)
      end
    end
