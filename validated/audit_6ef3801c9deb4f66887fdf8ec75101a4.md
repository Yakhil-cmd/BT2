### Title
`ReopenedHandler#unarchive?` operator-precedence bug bypasses `review_stacks_enabled: false`, allowing PR close/reopen to unarchive/re-provision an attacker-controlled review stack - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` uses `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (...) || (...)` without parentheses, so `&&` binds tighter than `||`. This means `review_stacks_enabled` only gates the `allow_all` branch, not the `allow_with_label`/`prevent_with_label` branches, letting an attacker who fully controls a PR's labels and branch re-trigger `ReviewStack` unarchival/creation and re-queue provisioning even when the repository has explicitly disabled review-stack provisioning.

### Finding Description
Binding that should hold: `repository.review_stacks_enabled == false` ⇒ `respond_to_pull_request_reopened? == false` for all `provisioning_behavior` values.

Actual code: [1](#0-0) 

Ruby evaluates `&&` before `||`, so `unarchive?` is actually:
```
(review_stacks_enabled && allow_all?) ||
(allow_with_label? && has_label) ||
(prevent_with_label? && !has_label)
```
`review_stacks_enabled` is not applied to the second or third disjuncts. If an operator sets `review_stacks_enabled = false` but leaves `provisioning_behavior = allow_with_label` (or `prevent_with_label`) configured from a prior state — both fields are independently persisted via `update_params` in `RepositoriesController` and rendered as separate, unlinked form controls in `settings.html.erb` — the disable toggle has no effect on those two behaviors. [2](#0-1) [3](#0-2) 

Exploit flow: attacker opens/labels a PR from their own fork/branch to add the provisioning label, closes it, then reopens it (`action: reopened`). `ReopenedHandler#process` calls `stack.unarchive!` unconditionally once `unarchive?` returns true; `ReviewStackAdapter#unarchive!` either unarchives an existing archived stack or creates a brand-new one and adds it to `Shipit::ReviewStackProvisioningQueue`, using `params.pull_request.head.ref` (the attacker's branch) as the stack's `branch`. [4](#0-3) [5](#0-4) 

Existing guards do not stop this: `verify_signature`/`drop_unhandled_event` only confirm this is a genuine `reopened` webhook for the target repository — they don't validate `review_stacks_enabled`. `ExplicitParameters` only enforces payload shape. There is no `User#authorized?`/`require_permission!` check anywhere in this handler; `ReviewStackAdapter#user` merely looks up or creates a `Shipit::User` for `params.sender.login`, the PR author. The identical fix pattern that correctly guards `LabeledHandler#respond_to_label_change?` (`repository.review_stacks_enabled && (archive? || unarchive?)`, with `review_stacks_enabled` wrapping the whole disjunction) is absent from both `ReopenedHandler#unarchive?` and `OpenedHandler#provision?`. [6](#0-5) 

### Impact Explanation
For the target repository itself (not a distinct victim tenant), an attacker who can open/label/close/reopen their own PR can force `Shipit::ReviewStack` creation/unarchival and re-queue provisioning for a branch they fully control, despite the repository operator having explicitly disabled dynamic review-stack provisioning (`review_stacks_enabled: false`). Because the resulting stack's `branch` is attacker-supplied and provisioning/deploy pipelines subsequently read `shipit.yml`/steps from that branch, this re-enables the review-stack lifecycle (and any downstream provisioning/task execution wired to it) that the operator believed was turned off. This is repeatable indefinitely via close/reopen cycles and matches the Critical category of "an unauthorized deploy... or a payload... mutating another's stack" in spirit — here, an unauthorized reactivation of the provisioning/deploy pipeline against explicit operator configuration.

### Likelihood Explanation
Requires the specific but plausible operator misconfiguration: `review_stacks_enabled = false` while `provisioning_behavior` is `allow_with_label` (with label present) or `prevent_with_label` (with label absent) — a state reachable by simply unchecking the "Dynamically provision" checkbox without resetting the (separately persisted) behavior dropdown. No Shipit credentials, GitHub App secret, or team membership is needed — only the ability to open a PR, add/remove a label on it, and close/reopen it, which any GitHub user can do on their own PR. Attacker cost is trivial and the action is fully repeatable.

### Recommendation
Wrap the `review_stacks_enabled` check around the entire disjunction in both `ReopenedHandler#unarchive?` and `OpenedHandler#provision?`, mirroring `LabeledHandler#respond_to_label_change?`:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`:
```ruby
test "does NOT unarchive stacks when review_stacks_enabled is false, even for allow_with_label with label present" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  repository.review_stacks_enabled = false
  repository.provisioning_behavior = :allow_with_label
  repository.provisioning_label_name = "pull-requests-label"
  repository.save!

  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  # Binding under test: review_stacks_enabled == false must imply stack stays archived
  assert stack.reload.archived?, "Expected stack to remain archived when review_stacks_enabled is false"
end
```
Run against current code: the assertion fails (stack is unarchived and re-queued for provisioning), demonstrating the bypass. After applying the recommended fix, the assertion passes.
