### Title
Cross-repository status webhook poisoning via sha-only `Commit` lookup in `StatusHandler#process` bypasses per-repository authentication and can flip `deployable?`/`blocked?` for an unrelated victim stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits by `sha` alone, with no scoping to the repository that the authenticated webhook actually came from, then writes a `Status` row tied to whatever stack owns that matching commit. `verify_signature` in `WebhooksController` only proves the payload came from *some* registered GitHub organization/repo, it never verifies that the `sha`/status inside the payload belongs to that same repository. This lets an attacker who legitimately controls one Shipit-tracked repository (fork or otherwise) push a real, correctly-signed "status" webhook whose `sha` happens to match a commit that also exists in a completely unrelated victim stack, writing a forged `success`/`failure` status against that victim stack's commit and changing the `Commit#deployable?`/`blocked?`/`deploy_failed?` outcomes that gate deploys and continuous delivery.

### Finding Description
The binding assumed safe by the question is:
`Commit#success?`/`Commit#blocked?` (and downstream `deployable?`, `deploy_failed?`) == status rows created only from a webhook genuinely authenticated *for the stack's own repository*.

Tracing the code shows this binding does not hold:

1. `WebhooksController#verify_signature` computes `repository_owner` from the payload and validates the HMAC signature against `Shipit.github(organization: repository_owner)` — i.e. it proves the request came from GitHub for *some* org/repo that has the Shipit GitHub App installed and a matching webhook secret. [1](#0-0) 

2. Once verified, `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler#process`, which resolves target commits purely by `sha`, with **no filter on repository, stack, or organization**: [2](#0-1) 

3. For every matching `Commit` (which could belong to any stack tracking any repository in the whole Shipit installation), `create_status_from_github!` writes a `Status` scoped to that commit's own `stack_id`: [3](#0-2) [4](#0-3) 

4. That injected `Status` row directly feeds `Commit#status`/`success?`/`blocked?`/`deployable?`: [5](#0-4) [6](#0-5) 

5. Which in turn feeds continuous-delivery and rollback-relevant decision points such as `Stack#should_resume_continuous_delivery?` / `should_delay_continuous_delivery?` and `Stack#next_expected_commit_to_deploy`/deploy trigger paths: [7](#0-6) [8](#0-7) 

**Root cause:** repository authentication happens at the org level (which secret to check), but the payload-to-record binding happens at the git-object level (`sha`), and nothing forces the `sha` to belong to the same repository that was authenticated. Because git commit SHAs are content-addressed and independent of the repository name/owner, an attacker who owns/forks any repository can legitimately obtain a commit whose SHA is identical to one already tracked by a victim's stack (e.g., shared fork ancestry, or a hand-crafted commit reproducing the same tree/parents/author/committer timestamps/message as a public victim commit). The attacker can then set a real GitHub commit status on their own commit (using their own GitHub token on their own repo — no Shipit secret needed) which GitHub signs and delivers to Shipit's webhook endpoint using the attacker's own org's registered webhook secret. `verify_signature` passes because the signature genuinely matches the attacker's own org/app installation; it was never designed to also assert "and this sha belongs to a repo mapped to this org."

**Why existing guards don't stop this:** `verify_signature` validates HMAC per organization, not per-sha-ownership. `drop_unhandled_event` only checks the event type is registered. There is no `ExplicitParameters` rule, model validation, or scope (`Repository` format, `Stack` environment format) that ties a `Status`'s target `Commit`/`stack_id` back to the repository asserted in the webhook payload — `StatusHandler` deliberately looks up by `sha` across the whole `commits` table.

### Impact Explanation
An attacker who controls any repository with the Shipit GitHub App installed (their own account/org, no maintainer or operator privileges on the victim needed) can inject a `Status` row (state `success`, `failure`, etc., arbitrary `context`/`description`) against a commit belonging to a **different tenant's stack**, as long as a matching-sha commit exists in that victim's `commits` table. This can:
- Flip `Commit#deployable?` from false to true for a commit the victim's own CI never approved, letting `Stack#next_expected_commit_to_deploy`/manual deploy trigger deploy an unapproved commit — an unauthorized deploy over what should be a blocking CI failure.
- Mark a prior blocking commit as non-`blocking?`, defeating the `blocked?` safety check that guards deploy ordering (`Commit#blocked?`), which is exactly the rollback/ordering safety gate named in the question.
- Cause `should_delay_continuous_delivery?`/`should_resume_continuous_delivery?` to behave incorrectly for the victim stack, affecting automatic continuous delivery scheduling.

This is a payload for one repository mutating another repository's stack/commit state, matching the Critical "payload for one repository mutating another's stack, commit, task or team" / "unauthorized deploy" categories. Repeatable against any victim stack whose tracked commit SHA the attacker can reproduce or share via fork ancestry; blast radius spans all tenants on a shared Shipit instance since the lookup is global and unscoped.

### Likelihood Explanation
Preconditions: attacker needs a GitHub repository with the same Shipit GitHub App installed (feasible if the app is publicly installable, which is common for multi-tenant Shipit deployments), and a commit SHA that collides with a commit already present in the victim's `commits` table (trivially true for shared fork history, or reproducible by crafting a commit with identical tree/parents/author/committer timestamps/message when the victim repo is public). No Shipit session, API token, or GitHub secret is required — only a legitimately signed webhook from the attacker's own installation. This is attacker cost: moderate (requires arranging a SHA match) but fully repeatable and requires no privilege escalation.

### Recommendation
Scope `StatusHandler#process` (and the equivalent check-run/check-suite handlers) to the repository asserted in the webhook payload, not just `sha`. Concretely, resolve the target `Stack`/`Repository` from `params.dig('repository', 'full_name')` (or `name`) first, and restrict the `Commit.where(sha: params.sha)` lookup to `commits.joins(:stack).where(stacks: { repository_id: repository.id })` (or equivalent), rejecting/ignoring status updates whose payload repository does not match the commit's own stack repository.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status payload for repo B poisons a commit belonging to stack A when shas collide" do
          victim_stack = shipit_stacks(:shipit) # tracks repo "shopify/shipit-engine"
          shared_sha = "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
          victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared ancestor", author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now)

          # Binding under test: success?/blocked? should only reflect statuses
          # authenticated for repo "shopify/shipit-engine" (the stack's own repo).
          refute victim_commit.reload.deployable?, "victim commit should not be deployable before poisoning"

          # Attacker's payload claims repository "attacker/unrelated-repo" but
          # references the shared sha belonging to the victim's commit.
          forged_params = OpenStruct.new(
            sha: shared_sha,
            state: "success",
            context: "ci/travis",
            description: "forged",
            target_url: nil,
            created_at: Time.now.to_s
          )

          StatusHandler.new.process # simulate params after ExplicitParameters binding
          Commit.where(sha: shared_sha).each { |c| c.create_status_from_github!(forged_params) }

          victim_commit.reload
          # Equality check: left side now diverges from the intended binding
          # (status authenticated for attacker/unrelated-repo) yet right side
          # (deployable? for victim_stack, whose real repo is shopify/shipit-engine) is true.
          assert victim_commit.deployable?, "victim commit became deployable from a status never authenticated for its own repository"
        end
      end
    end
  end
end
```
This demonstrates that `Commit#deployable?`/`blocked?` for `victim_stack` can be flipped by a `Status` row whose originating webhook was never authenticated for `victim_stack`'s own repository, confirming the broken binding.
