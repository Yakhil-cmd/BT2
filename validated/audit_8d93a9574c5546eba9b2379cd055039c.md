## Finding

### Title
Cross-tenant Commit status forgery via unscoped SHA lookup in `StatusHandler#process` - (`app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, a global query across every stack in the installation, instead of scoping to the repository named in the verified webhook payload. Because webhook signature verification only proves the request came from the org that owns the payload's `repository`, but the commit-lookup step ignores that binding entirely, a status event legitimately signed for repo/stack S1 can create a `Status` on, and trigger continuous delivery for, an unrelated stack S2 whenever a `Commit` row with the same `sha` exists under S2.

### Finding Description
The broken binding: the equality the engine implicitly relies on is `commit.stack == webhook.repository.stack`, but the actual code enforces only `commit.sha == webhook.payload.sha`.

Path:
1. `Shipit::WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and verifies the signature via `Shipit.github(organization: repository_owner)` [1](#0-0) . This only proves the payload was sent by the GitHub org that owns S1 — it says nothing about which `Commit` rows should be affected.
2. `Handler` base class exposes a repository-scoped `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) [2](#0-1) , and `PushHandler` correctly uses it: `stacks.not_archived.where(branch:).find_each { ... }` [3](#0-2) .
3. `StatusHandler#process`, however, does not use `stacks` at all — it queries `Commit.where(sha: params.sha)` unscoped, then calls `commit.create_status_from_github!(params)` on every match regardless of which stack/repository it belongs to: [4](#0-3) .
4. `Commit#create_status_from_github!` creates a `Status` scoped to `commit.stack_id`, which is whatever stack that pre-existing `Commit` row belongs to — not the stack of the payload's repository [5](#0-4) .
5. `Status` has `after_commit :schedule_continuous_delivery, ... on: :create`, which calls `commit.schedule_continuous_delivery` [6](#0-5) , which (per the question's given code) evaluates `deployable?`/`continuous_deployment?` on `commit.stack` — i.e., S2, and enqueues `ContinuousDeliveryJob.perform_later(stack)` for S2.

Attacker exact action: the attacker owns/controls a repository in an org (S1's org), and any commit whose `sha` also exists in Shipit as an undeployed `Commit` row of victim stack S2 (a realistic scenario when repositories share git history, e.g., forks, shared upstream, or template repos, since GitHub SHAs are derived from tree+parent+metadata and identical commits across repos naturally share the same SHA). The attacker triggers (or GitHub auto-fires) a `status` webhook event for that sha with `state: success`, signed with S1's legitimate `webhook_secret` for S1's org. `verify_signature` passes because it only checks the org tied to the payload's `repository`, and `StatusHandler` then updates every `Commit` row across the entire database sharing that sha — including S2's.

Why guards fail: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate "this request came from org X"; they never constrain which `Commit`/`Stack` rows may be mutated. `ExplicitParameters` schema in `StatusHandler` only validates `sha`/`state` shape, not ownership. There is no `require_permission!`/`stacks` scoping check comparable to `PushHandler`'s.

### Impact Explanation
A payload authenticated for one tenant's repository can write a `Status` record and enqueue `ContinuousDeliveryJob.perform_later(stack)` for a completely different tenant's stack, i.e., an unauthorized deploy trigger on a repository the attacker never touched. This matches the "Critical: a payload for one repository mutating another's stack/commit ... or an unauthorized deploy" category. The blast radius is any stack in the installation that happens to have an undeployed `Commit` row sharing a sha with any repo/org the attacker (or any GitHub user able to fire a `status` event) controls — repeatable per matching sha.

### Likelihood Explanation
Preconditions: victim stack S2 has `ignore_ci?` false and an undeployed `Commit` whose sha coincides with a commit sha in an attacker-controlled repository's org (a real, non-cryptographic-collision scenario for forks/shared history/cherry-picks/rebases-preserving-sha). Attacker cost is minimal — sending or triggering one legitimately signed status webhook from their own repo. No Shipit secrets, sessions, or privileged roles required, matching the stated attacker model.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the payload's repository, mirroring `PushHandler`'s use of the `stacks` helper — e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so only commits belonging to a stack tracking the repository named in the verified payload are updated.

### Proof of Concept
minitest (e.g. in `test/models/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Create `stack_s1` for repo `attacker/repo` and `stack_s2` for repo `victim/repo`, with `stack_s2.ignore_ci?` false.
2. Create `Commit` `c1` under `stack_s1` and `Commit` `c2` under `stack_s2` with the identical `sha` value (simulating shared history), and ensure `c2` is undeployed and otherwise deployable once `success`.
3. Stub `GithubHook#verify_signature` (or `Shipit.github(organization: 'attacker').verify_webhook_signature`) to return true, simulating a legitimately signed webhook from the attacker's own org for `attacker/repo`.
4. POST a `status` webhook payload: `{ sha: c1.sha, state: 'success', repository: { full_name: 'attacker/repo', owner: { login: 'attacker' } } }`.
5. Assert both: `assert_difference('c2.statuses.count', 1) { post :create, ... }` — proving S2's commit received a status from S1's webhook — and `assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_s2])`, proving the deploy trigger reaches the untouched victim stack, while confirming `c1.statuses.count` also incremented as the "authorized" side, demonstrating the binding `commit.stack == payload.repository.stack` does not hold.
