### Title
Webhook signature verification is keyed on an attacker-controlled organization field that is decoupled from the repository the payload actually writes to - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
This is the closest reachable analog to the pyUmbral "curve specification" bug class: an operation (webhook processing) trusts a piece of caller-supplied context (which "curve"/organization to use) to select the verification material, instead of binding verification unambiguously to the data actually acted upon. Here, `WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to validate the HMAC against using an attacker-controlled field of the unauthenticated JSON body, while the actual write target (which `Stack`/`Repository` gets updated) is derived from a *different* field of that same body.

### Finding Description
`WebhooksController#verify_signature` selects the signing secret to validate against based on `repository_owner`, which is read straight out of the untrusted JSON payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a `GitHubApp` instance per organization from `secrets.github`, and `verify_webhook_signature` is defined as: [3](#0-2) 

Critically, `return true unless webhook_secret` (line 77) means that for any configured organization whose `webhook_secret` is left blank/nil (an explicitly supported, documented configuration — see `config/secrets.development.shopify.yml` shipping `webhook_secret: # nil`), **signature verification is bypassed unconditionally**, regardless of the `X-Hub-Signature` header content.

Meanwhile, once past `verify_signature`, the actual repository/stack that gets mutated is resolved from a **separate, independently-attacker-controlled** field of the same JSON body — `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) 

Because `repository.owner.login` (used to pick the verification secret) and `repository.full_name` (used to pick the repository/stack to write to) are two independent keys inside a single JSON object that the requester fully controls, there is no cryptographic binding forcing them to agree. This is structurally identical to the pyUmbral flaw: a security-relevant parameter (which curve / which org's secret governs the operation) is taken from context rather than tied canonically to the object actually operated on, so mismatches between "the identity that was verified" and "the entity actually written" are representable.

### Impact Explanation
If any organization configured in `secrets.github` has no `webhook_secret` set (the repo's own sample config explicitly ships this way, and this is a legitimate/documented operating mode for engine deployments that don't configure webhook secrets per org), an unauthenticated attacker can:
1. Set `repository.owner.login` to that unsecured organization's login so `verify_signature` trivially passes (`return true unless webhook_secret`).
2. Set `repository.full_name` to `victim-org/victim-repo` (any other configured, secured repository/stack) in the same JSON body.
3. Send arbitrary `push`, `status`, `check_suite`, etc. events that get dispatched to handlers, which resolve `Repository.from_github_repo_name(repository_name)` using `repository.full_name` — a value never covered by any signature check.

This can trigger `GithubSyncJob`/`sync_github` on stacks belonging to a *different, properly-secured* GitHub organization, forge commit statuses via `StatusHandler`, or otherwise inject unauthenticated webhook events cross-repository/cross-organization — an unauthorized write across repository/organization trust boundaries without any credential.

### Likelihood Explanation
Requires a Shipit deployment that configures at least one GitHub organization with no `webhook_secret` (an explicitly supported, sample-documented configuration) alongside at least one other organization/stack the attacker wants to target. No GitHub credentials, session, or API token are needed — the webhook endpoint is intentionally unauthenticated (`skip_before_action :verify_authenticity_token`) and reachable by anyone who can POST to it.

### Recommendation
- Do not let attacker-supplied payload fields select which secret governs verification. Bind the webhook secret lookup and the acted-upon repository to the same, single canonical field validated together (e.g., resolve organization from the URL path/route, GitHub App installation context, or `X-GitHub-Hook-Installation-Target-ID`, not from the JSON body).
- Treat organizations with a blank `webhook_secret` as invalid/unverifiable rather than auto-passing verification (`return true unless webhook_secret` should be `return false` or reject the request instead of admitting all payloads for that org).
- Cross-check that `repository.owner.login` (or the field used for secret selection) matches `repository.full_name`'s owner before processing, rejecting requests where they diverge.

### Proof of Concept
1. Deploy Shipit with two organizations configured in `secrets.github`: `orgA` (no `webhook_secret`) and `orgB` (has a stack/repo the attacker wants to affect, secret configured).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of any signature header.
4. `PushHandler#process` resolves `Repository.from_github_repo_name("orgB/target-repo")` and queues `sync_github` for that stack — a write triggered against `orgB`'s repository despite no valid signature ever being checked against `orgB`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
