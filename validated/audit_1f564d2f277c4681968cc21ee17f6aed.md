## Title
Webhook signature is validated against the payload's `repository.owner.login`, but events are applied to whatever `repository.full_name` is in the same untrusted body — allowing a valid signer for Organization A to inject/forge events for repositories owned by Organization B - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). [1](#0-0) [2](#0-1) 

Once the signature is accepted, every handler resolves the target `Repository`/`Stack` using a *different* field of the same untrusted JSON body: `payload.dig('repository', 'full_name')`. [3](#0-2) 

Shipit supports multiple GitHub App configurations, one per organization, each with its own independent `webhook_secret` (as shown by the two-org fixture `test/dummy/config/secrets_double_github_app.yml`). [4](#0-3) [5](#0-4) 

Because the field used to select/verify the signing secret (`repository.owner.login`/`organization.login`) is never cross-checked against the field used to resolve which repository/stack the event actually mutates (`repository.full_name`), anyone who legitimately controls (or knows the secret for) **one** configured organization's GitHub App can craft a POST to `/webhooks` whose `X-Hub-Signature` is valid for *that* org, while setting `repository.full_name` to point at a completely different, victim organization's repository/stack.

### Finding Description
The binding that should hold is:
`organization whose secret validated the signature == organization that owns the repository being written to`

Before the attacker's request: for a genuine GitHub-delivered webhook, `repository.owner.login` and `repository.full_name`'s owner segment are always the same value, because GitHub itself populates both fields from the same event source repo. The binding holds implicitly, but only by coincidence of GitHub's own payload construction — Shipit performs no explicit equality check between them.

After the attacker's request: the attacker (an administrator/owner of Organization A's installed Shipit GitHub App — i.e., someone who legitimately knows Org A's `webhook_secret`, e.g. because they configured the App in Org A's settings, or because it leaked, is misconfigured, or is a low-security default) sends a raw HTTP POST directly to Shipit's `/webhooks` endpoint (not through GitHub) with:
- `X-Hub-Signature` computed correctly using Org A's `webhook_secret`
- `repository.owner.login` = `"org-a"` (so `verify_signature` looks up and validates against Org A's secret and succeeds)
- `repository.full_name` = `"org-b/victim-repo"` (an entirely different org's repository that the attacker has no access to)

`verify_signature` passes because HMAC matches Org A's secret. `WebhooksController#create` then dispatches to `Shipit::Webhooks.for_event(event)` handlers, each of which resolves `stacks` via `Repository.from_github_repo_name(repository_name)` where `repository_name` comes from `payload.dig('repository', 'full_name')` — i.e., `"org-b/victim-repo"`. [6](#0-5) [3](#0-2) 

Downstream, handlers act on Org B's stacks with no further ownership check:
- `PushHandler#process` looks up Org B's non-archived stacks matching `branch` and triggers `stack.sync_github(expected_head_sha: params.after)` — the attacker fully controls `after` (an arbitrary SHA), letting them force a specific `expected_head_sha` for Org B's stack sync. [7](#0-6) 
- `StatusHandler#process` writes a fabricated commit status (`state`, `description`, `target_url`, `context`) onto any of Org B's commits matching an attacker-chosen `sha`, which can satisfy CI-gating (`ci.require`) and unblock/trigger a deploy for a repository the attacker does not own. [8](#0-7) 

The organization used for cryptographic authentication (Org A) and the organization whose data is mutated (Org B) are two independently attacker-controlled fields of the same JSON body — this is exactly the "organization authenticated vs. repository written" trust binding the analog targets, and it is broken because nothing in `WebhooksController` or `Handler` enforces `repository.owner.login == repository.full_name.split('/').first`.

### Impact Explanation
This breaks a cross-organization isolation boundary: possession of one organization's webhook secret should only authorize writing events for that organization's repositories. Instead it authorizes writing to any repository configured in the same Shipit instance, regardless of the organization boundary the GitHub Apps configuration was intended to enforce (as documented via the multi-org `secrets.yml` layout). Concretely, an attacker can inject forged commit statuses to satisfy CI requirements and manipulate `expected_head_sha` synchronization for a stack belonging to a different organization/repository than the one whose secret they possess, which can lead to an unauthorized deploy being triggered for that victim stack — matching the "unauthorized deploy" high-impact criterion.

### Likelihood Explanation
Exploitation requires only knowledge of a legitimately-configured `webhook_secret` for *any one* of the organizations registered in this Shipit instance (an inherent, expected credential for anyone administering that org's GitHub App/webhook settings) plus the ability to send an arbitrary HTTP POST to the public `/webhooks` endpoint — no Shipit session, `ApiClient` token, or GitHub write access on the victim repository is required. This is realistic for any Shipit deployment serving more than one organization, which the engine explicitly supports.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization used to resolve/verify the signing secret matches the owner segment of `repository.full_name` (and, where present, `organization.login`) before dispatching to any handler; reject the request (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with distinct `webhook_secret` values (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who administers `org-a`'s GitHub App (and thus knows `org-a`'s `webhook_secret`), build a JSON body for a `status` (or `push`) event where:
   - `repository.owner.login = "org-a"`
   - `repository.full_name = "org-b/victim-repo"`
   - `sha` = SHA of a real commit belonging to a stack under `org-b/victim-repo`
   - `state = "success"`, `context = "<required CI context for org-b's stack>"`
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(org-a_webhook_secret, raw_body)`.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. Observe `WebhooksController#verify_signature` succeeds (Org A's secret matches), and `StatusHandler#process` creates a forged success status on `org-b`'s commit — satisfying `ci.require` and potentially unblocking a deploy/merge for a stack the attacker never had access to.
