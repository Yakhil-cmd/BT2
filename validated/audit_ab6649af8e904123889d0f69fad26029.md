### Title
IDOR-style authorization bypass in `wallet.js` sign-request handler — controller trusts unverified `from_address` cosigner claim, disabling the real ownership check - (File: wallet.js)

### Summary
The Xibo CVE-2026-31956 root cause is a controller-level pattern: a data-access path relies on a caller-supplied identifier and skips the "does this caller actually own/have rights over this resource" check (`disableUserCheck`). The analogous pattern in ocore is in the `"sign"` message handler in `wallet.js`, where the check that the requesting device (`from_address`) is actually a legitimate cosigner of the local address is explicitly commented out, and the local ownership verification is fully delegated to the (unverified) `body.address` argument supplied by the remote peer.

### Finding Description
In `handleMessageFromHub`'s `"sign"` case, once `findAddress` resolves the address to a **local** key (`ifLocal`), the code that should verify the requester is actually a cosigner of that address has been disabled: [1](#0-0) 

Compare this with the `ifRemote` branch of the very same `findAddress` call, which *does* perform the ownership check before proxying/forwarding a signing request: [2](#0-1) 

`findAddress` itself resolves `body.address`/`body.signing_path` purely from local DB state (`my_addresses`, `wallet_signing_paths`, `shared_address_signing_paths`) without any reference to which device actually sent the request: [3](#0-2) 

So for the `ifLocal` case, **any correspondent device** (any peer that is a "device correspondent" of the victim wallet, which is trivially established via the pairing/handshake flow used throughout `wallet.js`) can send a `"sign"` request naming any local address it has learned of (e.g. a shared/multisig address it participates in via one path, or simply the victim's own address if it's a correspondent), and the handler will proceed straight to emitting the `signing_request` event / calling `network.handleOnlineJoint`, without confirming that `from_address` is actually listed as one of the address's authorized cosigners (`extended_pubkeys`/`wallet_signing_paths` for that specific `from_address`). The comment explicitly states this check was intentionally disabled "to make... multilateral signing possible" — i.e., a broad "disableUserCheck"-like relaxation applied globally instead of being scoped per-use-case, exactly matching the Xibo bug class (authorization check disabled/bypassed at the data-access layer, with reliance on the front-end/UI dialog — `eventBus.emit("signing_request", ...)` — as the only remaining gate).

### Impact Explanation
Because the server-side ownership check is removed, an unprivileged correspondent (any device paired as a chat/wallet correspondent, which requires no special privilege beyond exchanging pairing codes) can:
1. Trigger `network.handleOnlineJoint` validation of an attacker-crafted unit that references the victim's local address/wallet as an author, and
2. Cause the victim's wallet software to display a signing/confirmation dialog and emit `signing_request` with the attacker-controlled `objUnit` and `assocPrivatePayloads`, for an address the attacker does not actually co-own signing rights to per the definition.

This is analogous to the Xibo IDOR: the resource-owning check ("is this caller authorized against this specific resource/cosigner set") is missing at the point where a sensitive action (constructing/possibly signing a real value-transferring unit, or revealing which addresses/wallets the victim controls) is triggered by an externally supplied identifier. Depending on downstream UI/confirmation-dialog handling on the victim side, this can lead to information disclosure of wallet/address ownership relationships and can be leveraged to trick the user into unauthorized signing/spending flows, i.e., unauthorized value movement or private-payment/address information leakage — satisfying "concrete unauthorized spending" or "AA fund loss" style impact if the victim confirms the (attacker-shaped) transaction under false pretenses.

### Likelihood Explanation
Likelihood is Medium: the attacker only needs to be an established device correspondent (a common low-privilege capability in the wallet/AA ecosystem — akin to the "authenticated user" role in the Xibo advisory), and the request format (`address`, `signing_path`, `unsigned_unit`) is fully attacker-controlled and passes all the format/hash validations in the handler, which validate *shape* but never *authorization of the sender relative to the address*.

### Recommendation
Restore (and generalize, rather than delete) the ownership check inside the `ifLocal` branch: verify that `from_address` is an authorized cosigner/correspondent for `body.address` at `body.signing_path` (e.g., checking `wallet_signing_paths`/`shared_address_signing_paths`/`extended_pubkeys` for that specific device before emitting `signing_request` or calling `network.handleOnlineJoint`), while still allowing the legitimate multilateral-signing use case by scoping the check to "is `from_address` one of the participants referenced anywhere in the unit's other authors/definitions," not simply skipping verification altogether.

### Proof of Concept
1. Attacker device A pairs as a correspondent with victim device V (standard low-privilege pairing, no special role required).
2. A crafts a `"sign"` hub message: `{subject: "sign", body: {address: V_local_address, signing_path: "r", unsigned_unit: {authors: [{address: V_local_address}], messages: [...attacker-chosen payment message...]}}}` and sends it to V.
3. V's `findAddress` resolves `V_local_address` to `ifLocal` (since it is genuinely V's own address/key), and — per `wallet.js:332-339` — the (disabled) cosigner check is skipped entirely, so the handler immediately proceeds to hash/validate the unit and emit `signing_request`, regardless of whether A has any real signing relationship to `V_local_address`.
4. If V's UI auto-confirms multilateral/contract flows or the user is confused about the origin of the request (since the dialog does not enforce/attest that A is a proper cosigner), V may sign a transaction that benefits A.
