### Title
`MembershipHandler#process` mutates a `Team`'s `Membership` rows without verifying that the organization which validated the webhook signature matches `Team#organization` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#process` resolves the target `Team` solely by `github_id` and never checks that the organization which signed/verified the inbound webhook is the same organization that owns that `Team`. In a multi-tenant `github:` configuration (documented in `docs/setup.md`), an attacker who controls one tenant's weak/blank `webhook_secret` can forge a `membership` `removed`/`added` event that mutates a completely different organization's `Team`, including teams listed in `Shipit.github_teams` which gate authorization to the whole Shipit app.

### Finding Description
The claimed binding, stated as an equality, is:

`organization verified by Shipit.github(organization: repository_owner).verify_webhook_signature(...)` == `Team#organization` of the team being mutated by `MembershipHandler#process`.

Tracing the path:
1. `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes the org used to pick the verifying secret as:
`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`).
For a `membership` event, GitHub payloads have no `repository` key, so this falls back to `params.dig('organization', 'login')` — a value fully controlled by the attacker's own JSON body.
2. `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) returns `true` immediately `unless webhook_secret` (blank secret bypass), and otherwise only checks the HMAC against whatever per-organization secret is configured for the org named in step 1. If the attacker administers (or already knows the secret of) one configured tenant, they can produce a valid signature for that tenant's org name.
3. Once past `verify_signature`, `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-42`). The `organization` assignment only executes inside the `find_or_create_by!` block, i.e. **only when the record is newly created**. If a `Team` with that `github_id` already exists (a legitimate team, e.g. one in `Shipit.github_teams`), the existing record is returned untouched, and `params.organization.login` is discarded.
4. The handler then executes `team.add_member(member)` or `team.members.delete(member)` (lines 27-30) directly against that pre-existing `Team`, with no check that `params.organization.login` (or the org that validated the signature) equals `team.organization`.

**Attacker's exact request**: `POST /webhooks` with header `X-Github-Event: membership`, body:
```json
{
  "action": "removed",
  "team": { "id": <real target team github_id>, "name": "...", "slug": "...", "url": "..." },
  "organization": { "login": "<attacker-owned-tenant-with-known/blank-secret>" },
  "member": { "login": "<victim-admin-login>" }
}
```
signed with the attacker-known/blank secret for `<attacker-owned-tenant>`. This deletes the `Membership` row for the victim on the target `Team`. A follow-up `action: "added"` event with `member.login` set to the attacker's own login re-adds the attacker to that same `Team`.

Because `Team.add_member`/`members.delete` (`app/models/shipit/team.rb:41-43`) operate purely on the local `memberships` table and `User#authorized?` (`app/models/shipit/user.rb:80-82`) checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, this directly manipulates Shipit-side authorization team membership, independent of actual GitHub team state.

Existing guards do not prevent this:
- `verify_signature` only proves the request was signed by *some* configured tenant's secret; it never binds that tenant to the `team.organization` being mutated.
- `drop_unhandled_event`/`ExplicitParameters` only validate presence/type of fields (`Integer`/`String`), not organizational ownership.
- `find_or_create_team!`'s `organization` assignment is a create-only side effect, not an authorization check.

### Impact Explanation
A `Team` record used for authorization (`Shipit.github_teams`) can have its membership mutated (Memberships added/removed) by anyone who controls or knows the webhook secret of an *unrelated* tenant configured in the same Shipit instance. This is an escalation into `Shipit.github_teams` authorization (per the rules' High severity category) — an attacker can add themselves (or remove a legitimate admin then add themselves) to a team that grants `User#authorized?` == true, gaining access to the whole Shipit application (stacks, deploys, rollbacks) for organizations they have no relationship to. This is repeatable against any `Team` whose `github_id` the attacker can learn, and the blast radius spans every organization/tenant hosted by the same Shipit instance.

### Likelihood Explanation
Requires: (a) a multi-tenant `github:` configuration (explicitly documented and supported, see `docs/setup.md` "Using Multiple Github Applications"), (b) at least one configured tenant with a blank or attacker-known `webhook_secret`, and (c) the attacker knowing the numeric `github_id` of the target `Team` (obtainable via prior legitimate webhook traffic, GitHub API team listings, or Shipit's own webhook logs). Attacker cost is a single unauthenticated HTTP POST; no Shipit session or credentials are needed. This is a realistic misconfiguration pattern in multi-org Shipit deployments and fully reproducible without live GitHub access.

### Recommendation
In `MembershipHandler#process`, look up the `Team` scoped both by `github_id` **and** `organization: params.organization.login`, and reject/ignore the event if an existing `Team` with that `github_id` has a different `organization`. Additionally, bind webhook signature verification for `membership`/`organization`-scope events strictly to the `organization.login` field (not attacker-suppliable ambiguity), and cross-check that this verified organization matches the `Team#organization` before calling `team.add_member`/`team.members.delete`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/membership_handler_test.rb`):
1. Create two orgs' worth of fixtures: `Team` `shopify_developers` with `organization: 'shopify'`, `github_id: X`, already a member `admin_user`. Configure `Shipit.github` for two orgs, `'shopify'` (real secret) and `'attacker-org'` (blank/known secret).
2. Stub `GithubHook`/`verify_webhook_signature` such that only `attacker-org`'s signature check passes trivially (blank secret), while `shopify`'s does not receive/validate the attacker's signature.
3. POST a `membership` event with `organization: {login: 'attacker-org'}`, `team: {id: X, ...}` (the real `shopify_developers` github_id), `action: 'removed'`, `member: {login: admin_user.login}`.
4. Assert equality-before: `verified_org = 'attacker-org'`, `team.reload.organization = 'shopify'` → `verified_org != team.organization`.
5. Assert `assert_difference('Membership.count', -1) { post :create, ... }` succeeds and `shopify_developers.members.reload.exclude?(admin_user)` — proving the mutation occurred despite the mismatched binding, with no exception raised and `response.status == 200`.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
    end

    def handle
      "#{organization}/#{slug}"
    end
