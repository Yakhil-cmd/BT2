### Title
`StatusHandler#process` writes commit statuses by bare SHA with no repository scoping, letting a webhook authenticated for one repository flip CI state (and trigger auto-deploy) on an unrelated victim stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and writes a status to every matching row, without ever consulting `repository_name`/`stacks` like sibling handlers do. Because `Commit#sha` is not scoped or validated against the repository that authenticated the webhook, an attacker who controls (and can validly sign webhooks for) any repository can forge a `status` event whose `sha` matches a commit that also exists on a victim's stack, flipping that victim commit's `ci/kubernetes` status to `success` and, on a stack with a configured bot (`Shipit.user`) and continuous deployment, triggering an unauthorized auto-deploy.

### Finding Description
The broken binding: the invariant should be `commit.stack.repository.full_name == payload['repository']['full_name']` for every `Commit` mutated by a `status` webhook, i.e. the authenticated repository (verified via `verify_signature`/`repository_owner`) must equal the repository owning the commit being updated.

Trace:
- `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) only verifies the webhook signature against `Shipit.github(organization: repository_owner)` [1](#0-0) . This proves the sender controls the app installation for `repository_owner`, it says nothing about which `Commit` rows may be touched.
- `Handler` (the base class) exposes a repository-scoped helper, `stacks`, derived from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name(repository_name)` [2](#0-1) , which other handlers use to scope their side effects to the authenticated repository.
- `StatusHandler#process`, however, never uses `stacks`/`repository_name`. It resolves target commits purely by SHA: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . `Commit` belongs to a `Stack` (app/models/shipit/commit.rb:11) but there is no `WHERE stack_id IN (...)` filter, no `github_repo_name` comparison, and no uniqueness constraint tying a SHA value to a single repository.
- `commit.create_status_from_github!` → `add_status` replicates the GitHub status onto that commit's `statuses` and, if the simple state changes, calls `stack.schedule_merges` and can enqueue `ContinuousDeliveryJob` via `Commit#schedule_continuous_delivery` when `deployable? && stack.continuous_deployment? && stack.deployable?` [4](#0-3) [5](#0-4) . Auto-triggered deploys run under the stack's configured bot (`Shipit.user`), so this becomes an unauthorized ship/block on the victim stack.

Exploit flow: attacker owns/controls repository A (or any repo whose org GitHub App they can get a valid signature for). They read a real, public commit SHA belonging to victim stack B (many Shipit-tracked repos are public, or the attacker previously pushed a branch to a fork sharing history with the victim repo, producing an identical SHA that also lands in the victim's `commits` table via push events). The attacker sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for repository A, and payload `{"sha": "<victim-sha>", "context": "ci/kubernetes", "state": "success", "repository": {"full_name": "attacker/A", ...}}`. `verify_signature` passes (it only checks A's ownership). `StatusHandler#process` matches the `Commit` row belonging to victim stack B purely by SHA text and writes the forged `success` status onto it.

Existing guards fail here because they are all repository-owner-scoped at the transport/signature layer, but `StatusHandler` performs its persistence query without re-applying that scope at the model layer — unlike the `stacks` helper pattern in the shared `Handler` base class.

### Impact Explanation
A forged `ci/kubernetes` success (or failure) status is written into the victim stack's commit history without the victim's repository having ever produced that webhook. If the victim stack is configured with `bot_login`/`Shipit.user` and continuous deployment, this can immediately schedule an unauthorized deploy (`ContinuousDeliveryJob`) running as the bot identity — deploying attacker-influenced or arbitrary already-pushed code, or conversely permanently blocking deploys by forging a failing/error status for a required context. This matches "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy, rollback or merge," both listed as Critical. The attack is repeatable against any repository/stack pair sharing a SHA value and is not limited to a single victim.

### Likelihood Explanation
Preconditions: attacker needs the ability to have a validly-signed `status` webhook accepted for *some* repository/organization (i.e., attacker's own GitHub repo with the Shipit GitHub App installed, or any org for which `Shipit.github_secret`/app is configured that the attacker legitimately controls) — this is within the stated "unprivileged attacker" capability (owns a repo, can trigger status events for it). The harder precondition is a SHA collision with a commit already ingested into the victim's stack's `commits` table (via push/PR ingestion). This is realistic in fork/shared-history scenarios (attacker forks the victim's repo, or the victim repo is public and shares commits with attacker-controlled forks/branches), which is a common configuration for CI/CD tools. Attacker cost is low (one crafted HTTP request); the flip is repeatable per matching SHA.

### Recommendation
Scope `StatusHandler#process` to the authenticated repository, mirroring the base `Handler#stacks` pattern: resolve `stacks` from `payload.dig('repository', 'full_name')`, then restrict the commit lookup to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or equivalently `commit.stack.github_repo_name == repository_name`) before calling `create_status_from_github!`, so a status only ever mutates commits belonging to the repository that authenticated the webhook.

### Proof of Concept
minitest plan (add to `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two `Repository`/`Stack` fixtures for different `full_name`s (e.g. `attacker/A` and `victim/B`), the victim stack configured with `bot_login: 'shipit-bot'` (Shipit.user) and `continuous_deployment` enabled, requiring `ci/kubernetes`.
2. Create a `Commit` with `sha: 'deadbeef...'` under the victim stack (`stack: victim_stack`), with no status yet (`commit.deployable?` false because `success?` false).
3. Build a status webhook payload: `{"sha" => commit.sha, "state" => "success", "context" => "ci/kubernetes", "repository" => {"full_name" => "attacker/A", "owner" => {"login" => "attacker"}}}`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature verification, which is out of scope for the model-level assertion).
5. Assert equality violated: `commit.reload.status.state` becomes `"success"` and `commit.deployable?` becomes `true`, even though the payload's `repository.full_name` (`attacker/A`) does not equal `commit.stack.repository.full_name` (`victim/B`) — i.e. `assert_not_equal payload_repo_full_name, commit.stack.github_repo_name` while `assert commit.deployable?`.
6. Optionally assert `ContinuousDeliveryJob` was enqueued for `victim_stack` via `assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack])`, demonstrating the auto-deploy trigger from a payload that never authenticated for `victim/B`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
