### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while event handlers act on `repository.full_name` — cross-organization write via signature-authorized-org vs. repository-acted-upon mismatch ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Analogous to the reported `next_bin_array_index_with_liquidity` bug — where one field (`swap_for_y`) determines a decision (search direction) while a different, related-but-independent field (start/end index) is used elsewhere without the two ever being forced into agreement — Shipit's webhook pipeline picks the **authenticating organization** from one JSON field and picks the **repository to mutate** from a different JSON field, with no check that they refer to the same repository/organization.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using: [1](#0-0) [2](#0-1) 

i.e. `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`.

Every `Handler` subclass (push, status, check_suite, pull_request, etc.), however, resolves the actual local `Repository`/`Stack` to write to using a completely different field, `repository.full_name`: [3](#0-2) 

which is parsed as `owner/name` and looked up via `Repository.from_github_repo_name`: [4](#0-3) 

Shipit explicitly supports hosting **multiple GitHub organizations from a single install**, each with its own `webhook_secret`: [5](#0-4) 

Nothing in the code enforces that `repository.owner.login` (used to pick the signing key) equals the owner segment embedded in `repository.full_name` (used to pick the target `Repository`/`Stack`). Since JSON allows these two fields to be set independently, an attacker who legitimately administers a GitHub App installation for **their own** organization (`attacker-org`, with a known/self-configured `webhook_secret`) can craft a payload where:
- `repository.owner.login = "attacker-org"` (so `verify_signature` selects and validates against the attacker's own secret — signature check passes), and
- `repository.full_name = "victim-org/victim-repo"` (so the handler resolves and mutates a `Stack` belonging to `victim-org`, which the attacker has no legitimate access to).

This breaks the equality that should hold: `organization that authenticated == repository/organization that is written`.

### Impact Explanation
Handlers act on the mismatched `full_name` target with meaningful side effects: `PushHandler` triggers `stack.sync_github(expected_head_sha: params.after)` for the victim stack's branch, `StatusHandler` writes fabricated commit statuses via `commit.create_status_from_github!`, and `pull_request` handlers create/update `MergeRequest` records, capture labels, and can enqueue merges (`ProcessMergeRequestsJob` → `MergeRequest#merge!`, which calls `stack.github_api.merge_pull_request`). An attacker forging cross-org events can inject falsified CI/status data or trigger sync/merge-queue state changes against a stack they do not administer — a cross-repository write breaking a deploy-trust boundary, matching the report's Critical/High impact bar (unauthorized deploy/merge-queue manipulation, cross-repository writes).

### Likelihood Explanation
This requires the attacker to control (or self-register) a GitHub organization/App installation on the same shared Shipit instance — i.e., they must already possess a valid `webhook_secret` for *some* organization recognized by that Shipit deployment. That is a real, low-privilege scenario only in **multi-tenant Shipit installs** configured with the documented multi-org `github:` block (as shown in `config/secrets.development.example.yml`); it is not exploitable against a single-organization Shipit instance where only one `webhook_secret` exists (the attacker would need that one secret already, which is out of scope). Given that the multi-org config is a first-class, documented feature rather than a misconfiguration, this is a credible analog, though its real-world reach depends on operators actually running multi-org mode.

### Recommendation
After signature verification, re-derive the organization from the same field the handler will use (`repository.full_name`'s owner segment, or `organization.login` consistently) and assert it matches the organization whose secret validated the signature; reject the webhook (422) on mismatch. Alternatively, always verify using the owner parsed from `repository.full_name` (never a separate/independent field) so there is only one source of truth for both authentication and target resolution — eliminating the ambiguity the same way the referenced fix eliminated ambiguity in `next_bin_array_index_with_liquidity` by making the equal-boundary case explicit rather than implicit.

### Proof of Concept
Conceptual payload (attacker controls `attacker-org`'s `webhook_secret`):
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "deadbeef..."
}
```
1. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the exact raw JSON body.
2. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and successfully verifies the signature [1](#0-0) .
3. `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` runs `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: params.after)` against the victim's stack — despite the signature only proving control of `attacker-org`.

**Uncertainty / what I could not fully verify**: I could not confirm from the index whether `Shipit.github(organization:)` performs any additional cross-check (e.g., verifying the installation ID actually covers the named repository) before returning a `GitHubApp` instance — if such a check exists elsewhere (e.g., in `lib/shipit.rb`, not fully retrieved), it could mitigate this. Also, I could not verify whether GitHub Apps installations in practice restrict which repositories can appear in webhook deliveries for a given installation (a platform-level constraint that would only be bypassed by a *forged* request, not a genuine GitHub-delivered one) — this exploit path is specifically about attacker-forged HTTP requests to `/webhooks`, not genuine GitHub-originated deliveries. I recommend a Devin session with full repository/file access (including `lib/shipit.rb` in full) to confirm there is no additional organization/installation binding check before treating this as conclusively exploitable.
