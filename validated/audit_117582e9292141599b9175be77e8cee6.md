### Title
Cross-tenant webhook confusion: signature verified against attacker's org while push is applied to victim's stack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/push_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` to validate the HMAC using `repository_owner`, which reads `params.dig('repository','owner','login')`, but `Handler#stacks` resolves the target `Repository`/`Stack` using `payload.dig('repository','full_name')`. Because both fields are independently attacker-controlled JSON fields inside the same signed body, an attacker who owns `attacker-org` (and thus knows its `webhook_secret`) can set `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/monorepo"` to pass signature verification with their own secret while making `PushHandler#process` operate on the victim's stack.

### Finding Description
The broken binding: `organization_whose_secret_verified_signature (repository_owner = params.dig('repository','owner','login'))` == `organization_owning_target_stack (Repository.from_github_repo_name(payload.dig('repository','full_name')).owner)` is expected to hold, but is **not enforced anywhere** in the code.

Path:
1. `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(signature, request.raw_post)` [1](#0-0)  using `repository_owner` defined as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` does a straightforward HMAC-SHA1 compare against that organization's configured `webhook_secret` [3](#0-2) . If the attacker crafts the body themselves and knows their own org's secret, this check passes regardless of what other fields say.
3. On success, `WebhooksController#create` parses the full JSON body and dispatches it unmodified to the relevant handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
4. `Handler#stacks` resolves the target repository using a *different* field of the same payload: `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [5](#0-4) .
5. `PushHandler#process` uses this `stacks` scope to find non-archived stacks matching the pushed branch and calls `stack.sync_github(expected_head_sha: params.after)` [6](#0-5) , where `params.after` is also fully attacker-controlled (only required to be present per the `ExplicitParameters` schema, no format/ownership validation) [7](#0-6) .

Nowhere is `repository.owner.login` cross-checked against `repository.full_name`'s owner segment, nor is the `GitHubApp` instance used for signature verification tied to the `Repository`/`Stack` being mutated. `Repository.from_github_repo_name` does a plain case-insensitive DB lookup split on `/` with no ownership assertion tied to the verified organization [8](#0-7) . None of `drop_unhandled_event`, `check_if_ping`, the `ExplicitParameters` schema (`requires :ref; requires :after`), or model validations on `Repository`/`Stack` reference or restrict cross-field consistency between `owner.login` and `full_name`, so the divergence is real and unguarded.

Attacker request: attacker sends `POST /webhooks` with header `X-Github-Event: push`, `X-Hub-Signature: sha1=<HMAC using attacker-org's known webhook_secret over raw body>`, and a JSON body such as:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/monorepo"
  }
}
```
This passes `verify_signature` (attacker knows `attacker-org`'s secret), and `PushHandler#process` then calls `sync_github(expected_head_sha: <attacker-chosen sha>)` on any non-archived stack of `victim-org/monorepo` tracking `main`.

### Impact Explanation
This lets an attacker who controls only their own GitHub org/webhook secret force `Stack#sync_github` to run on an arbitrary victim tenant's stack with an attacker-chosen `expected_head_sha`, without any victim credential. This is a genuine cross-tenant write: a payload authenticated for one repository (attacker's) causes a state mutation for another repository/stack (victim's), matching the "Critical" category explicitly listed (payload for one repository mutating another's stack/commit/task). The blast radius spans every Shipit-managed victim stack whose branch name the attacker can guess/target (commonly `main`/`master`), and the attack is trivially repeatable against arbitrary repositories tracked by the same Shipit instance, since the attacker only needs to iterate `full_name` values while reusing their own valid signature.

### Likelihood Explanation
Preconditions are modest and attacker-controlled: the attacker only needs their own Shipit-configured GitHub org (or any org whose secret they know) with a `webhook_secret`, and knowledge/guess of a victim org/repo name and branch tracked by Shipit — no victim secret, session, or API token is required. Crafting the JSON body and HMAC is trivial scripting; this is a single unauthenticated HTTP POST, fully repeatable.

### Recommendation
Bind the organization used to select the `GitHubApp`/`webhook_secret` for signature verification to the same organization/repository that the handler acts upon: derive `repository_owner` and the acted-upon `Repository` from the same canonical field (e.g., always use `repository.full_name`'s owner segment, or validate `repository.owner.login == full_name.split('/').first`), and reject the webhook if they disagree. Additionally, `WebhooksController#verify_signature` should resolve the `Repository` first and verify against the `webhook_secret` configured for the repository's actual owner as read from `full_name`, not a separately attacker-suppliable `owner.login` field.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure two orgs in `Shipit.github` config/secrets fixture: `attacker-org` with `webhook_secret = "attacker-secret"`, and `victim-org` with `webhook_secret = "victim-secret"` (different, victim's unknown to "attacker").
2. Create `Repository.create!(owner: "victim-org", name: "monorepo")` and a `Stack` on it tracking branch `main`, `continuous_delivery: true` (or whatever flag governs `sync_github` eligibility).
3. Build a push payload body:
   ```ruby
   body = {
     ref: "refs/heads/main",
     after: "deadbeef" * 5,
     repository: { owner: { login: "attacker-org" }, full_name: "victim-org/monorepo" }
   }.to_json
   ```
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "attacker-secret", body)`.
5. POST to `/webhooks` with `X-Github-Event: push` and `X-Hub-Signature: signature`, raw body `body`.
6. Assert response is `200 OK` (not `422`), proving signature verification succeeded using `attacker-org`'s secret — i.e. assert LHS `repository_owner == "attacker-org"` is what authenticated the request.
7. Stub/mock `Stack#sync_github` (e.g., via `Shipit::Stack.any_instance.expects(:sync_github).with(expected_head_sha: "deadbeef"*5)`), and assert it is invoked on the `victim-org/monorepo` stack — proving RHS `Repository.from_github_repo_name(full_name).owner == "victim-org"` — demonstrating the two sides of the equality diverge (`attacker-org != victim-org`) while the mutation still occurs.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
