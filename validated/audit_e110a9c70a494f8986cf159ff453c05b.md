The key finding: `DenyReserveTransferToRelayChain`'s `ShouldExecute` implementation (from `xcm-builder`, not vendored in this repo) pattern-matches only the top-level instruction sequence of an `Xcm` program passed into `should_execute`. `DenyReserveTransferToRelayChain` bypass via nested `SetAppendix`/`SetErrorHandler` instructions - allows disallowed reserve-withdraw-to-relay messages to bypass Asset Hub's Barrier - (File: `system-parachains/asset-hubs/asset-hub-kusama/src/xcm_config.rs`)

### Summary
Asset Hub Kusama's `Barrier` wraps `DenyReserveTransferToRelayChain` directly, without the `DenyRecursively` adapter that other chains in this same repo use for the identical filter. `DenyThenTry`'s deny filters (as implemented in `xcm-builder`) match against the top-level instruction list of the incoming `Xcm` program; instructions nested inside a `SetAppendix`/`SetErrorHandler` inner program are not top-level and are therefore invisible to a non-recursive deny check.

### Finding Description
The Barrier is defined as: [1](#0-0) 

Contrast this with `bridge-hub-polkadot`, which protects against the exact same `DenyReserveTransferToRelayChain` filter but wraps it in `DenyRecursively`: [2](#0-1) 

and `bulletin-polkadot`, which does the same: [3](#0-2) 

This inconsistency across the repo is itself evidence of the underlying `xcm-builder` behavior: `DenyReserveTransferToRelayChain::should_execute` pattern-matches the top-level `Vec<Instruction>` slice handed to the barrier. Instructions embedded inside the inner `Xcm` field of `SetAppendix(Xcm(...))` or `SetErrorHandler(Xcm(...))` are not part of that top-level slice — they are opaque payload until the executor later runs them as a sub-program. `DenyRecursively` was introduced specifically to walk into these nested programs; its absence in `asset-hub-kusama`, `asset-hub-polkadot`, `coretime-kusama`, `coretime-polkadot`, `people-kusama`, `collectives-polkadot`, and `encointer` configs means those chains only deny the pattern at the top level.

Attack flow on Asset Hub Kusama:
1. A signed AH user calls `PolkadotXcm::execute` with a top-level program such as `Xcm([WithdrawAsset(..), BuyExecution(..), SetAppendix(Xcm([InitiateReserveWithdraw{ reserve: Parent, assets: Wild(All), xcm: Xcm(vec![]) }]))])`.
2. `DenyReserveTransferToRelayChain` inspects only the outer instruction list — `WithdrawAsset`, `BuyExecution`, `SetAppendix` — none of which match its deny patterns (`TransferReserveAsset`/`InitiateReserveWithdraw` to `Parent`). The message passes the `Deny` stage.
3. The `Allow` chain evaluates it: `TakeWeightCredit`/`AllowTopLevelPaidExecutionFrom<Everything>` accept it because it begins with `WithdrawAsset`+`BuyExecution` and is signed (origin computed via `WithComputedOrigin`).
4. The executor runs the main program, then executes the appendix. The appendix's `InitiateReserveWithdraw{reserve: Parent,...}` executes with the user's own origin, generating and sending an XCM message to the Relay Chain (`Parent`) via the configured `XcmRouter`/`ParentAsUmp`, exactly the operation `DenyReserveTransferToRelayChain` was meant to prevent at this call site.

The existing checks that should stop this — the `Deny` half of `DenyThenTry` — fail because they operate non-recursively; `WithComputedOrigin`/`AllowTopLevelPaidExecutionFrom` are origin/fee gates, not instruction-content gates, so they don't compensate for the missed pattern.

### Impact Explanation
Confirmed impact: the filter intended to block reserve-transfers/reserve-withdrawals targeting the Relay Chain from Asset Hub Kusama can be bypassed by an ordinary signed user by nesting the denied instruction inside `SetAppendix`/`SetErrorHandler`. This lets a user send an XCM message to the Relay Chain via UMP that the runtime's own security policy explicitly tries to disallow.

The further scoped claim — that this permanently halts the relay's UMP dispatch queue for AssetHub's inbound channel via `MessageQueue` — is **not verified** from the available code. Modern FRAME `pallet_message_queue` handles unprocessable/overweight messages by marking pages/messages as overweight and skipping them (round-robin per-queue processing), rather than permanently blocking the queue; I found no code in this repo confirming a permanent-halt mechanism, and the relay chain's `MessageQueue` implementation details needed to confirm or refute that specific DoS mechanism were not available in the indexed context. The concrete, provable impact is limited to: **barrier bypass allowing a disallowed reserve-withdraw-to-relay message to be forwarded**, which is a policy-filter defect, not a demonstrated permanent-queue-halt DoS.

### Likelihood Explanation
High feasibility for the bypass itself: any signed AH account can call `pallet_xcm::execute` directly with an XCM program it fully controls, requires no special privilege, proxy, or race condition, and is repeatable at will (bounded only by `MaxInstructions` and normal transaction fees). The comparison against sibling chains in the same repo (`bridge-hub-polkadot`, `bulletin-polkadot`) that already patched this exact gap with `DenyRecursively` strongly indicates the maintainers are aware of and have partially remediated this class of issue, but the remediation was not applied uniformly to `asset-hub-kusama`/`asset-hub-polkadot`/coretime/people/collectives/encointer.

### Recommendation
Wrap `DenyReserveTransferToRelayChain` (and any other content-based deny filters) in `DenyRecursively` in `asset-hub-kusama`'s (and `asset-hub-polkadot`'s, and the other affected chains') `Barrier` definition, matching the pattern already used in `bridge-hub-polkadot`/`bulletin-polkadot`:
```rust
pub type Barrier = TrailingSetTopicAsId<
    DenyThenTry<
        DenyRecursively<DenyReserveTransferToRelayChain>,
        ( ... existing allow list ... ),
    >,
>;
```
