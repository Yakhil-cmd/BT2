### Title
Webhook signature verification authenticates the payload's claimed organization, not the repository it acts on, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to verify the HMAC signature against using `repository_owner`, a field taken directly from the untrusted JSON body (`params.dig('repository', 'owner', 'login')`). [1](#0-0) [2](#0-1)  Once the signature is accepted, every registered handler resolves the actual `Repository`/`Stack` to act on using a *different* field from the same body, `repository.full_name`, via `Handler#repository_name` / `Handler#stacks`. [3](#0-2)  These two fields are never cross-checked against each other, so the organization whose secret authenticated the request is not bound to the repository the request is allowed to mutate — mirroring the reported bug class of a value that is checked/updated on one entity while a different, related entity is actually acted on.

### Finding Description
Shipit supports a multi-organization configuration where each GitHub org has its own `app_id`/`webhook_secret` (documented in `config/secrets.development.shopify.yml`). [4](#0-3)  `Shipit.github(organization:)` looks up the app/secret purely by the organization name passed to it. [5](#0-4) 

In `WebhooksController#verify_signature`, that organization comes straight from the request body being verified:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

This only proves the request was signed with the secret belonging to whatever organization the payload *claims* to be `repository.owner.login` — it does not constrain what repository the payload's handlers subsequently act on. Every handler resolves the target strictly from `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

Because `repository.owner.login` and `repository.full_name` are independent, attacker-controlled keys in the same unsigned-content-agnostic JSON blob (the signature only covers the raw bytes, not any semantic relationship between fields), an organization that legitimately owns a webhook secret for the Shipit instance (e.g. `attacker-org`, onboarded alongside `victim-org` on the same multi-tenant Shipit install) can:
1. Set `repository.owner.login = "attacker-org"` so `verify_signature` fetches and successfully verifies against `attacker-org`'s real secret.
2. Set `repository.full_name = "victim-org/victim-repo"` (and any other payload fields such as `sha`, `state`, `context`, `ref`, `after`) so the dispatched handler (`push`, `status`, `pull_request`, `check_suite`, `membership`, etc.) operates on `victim-org`'s stacks/commits instead of `attacker-org`'s.

This is the same class of bug as the report: a security-relevant value (`creditedNodeETH`, here "which org's identity is verified") is updated/checked against one entity while the code that depends on it (`nodeBalanceWei`, here "which repository is mutated") is computed from a different, unsynchronized entity.

### Impact Explanation
The webhooks controller dispatches to all handlers listed in `Hook::EVENTS`/`Webhooks::DEFAULT_HANDLERS` (push, status, check_suite, pull_request, membership, merge, etc.). Handlers such as the commit `status` handler create `Status` records straight from payload fields (`sha`, `state`, `description`, `context`, `target_url`) matched only by SHA within the resolved (forgeable) stack's commits — demonstrated in the controller test that asserts a `Status` is created from raw payload values. [7](#0-6)  If a victim stack's `shipit.yml` gates deploys/merges on required CI contexts (`ci.require`), an attacker who forges a passing status for `victim-org`'s commit — despite only holding a webhook secret for their own, unrelated `attacker-org` — can manufacture the CI-green signal that continuous delivery/merge automation relies on to trigger an unauthorized deploy or merge on a repository the attacker has no legitimate relationship to. Other handlers (`push`, `membership`, `pull_request`) similarly act on the attacker-chosen `full_name` target while only ever proving possession of a secret for a different org.

### Likelihood Explanation
Exploitation requires only that the attacker administers (or has been issued webhook credentials for) any single organization onboarded to the same multi-tenant Shipit instance as the victim — not a Shipit account, `ApiClient` token, or privileged Shipit role, and not GitHub write access to the victim's repository. Multi-org configuration is a documented, supported deployment mode [4](#0-3) , and the disconnect between the field used for signature-org selection and the field used for target resolution is present on every webhook dispatch path, with no code anywhere reconciling `repository.owner.login` and `repository.full_name`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#initialize`), after establishing which organization's secret validated the signature, reject (or re-derive) the payload if `repository.full_name`'s owner does not match the authenticated `repository_owner`. Concretely, compare `payload.dig('repository', 'full_name')&.split('/')&.first&.downcase` against `repository_owner.downcase` and return `422` on mismatch before any handler runs.

### Proof of Concept
1. Deploy Shipit with the multi-org `github:` schema, onboarding `attacker-org` (attacker controls this org's GitHub App and therefore knows its `webhook_secret`) and `victim-org` (hosts the target stack).
2. Craft a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example/fake"
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>` and POST it to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, verifies successfully against the attacker's own known secret. [1](#0-0) 
5. The dispatched status handler resolves the target stack via `repository.full_name = "victim-org/victim-repo"` [3](#0-2)  and records a forged `success` status for the victim's commit, despite the attacker never having proven any relationship to `victim-org`.

Note: I was not able to load the specific `status`/`check_suite` handler source files or the continuous-delivery/`ci.require` gating logic in this pass (index/tooling budget exhausted), so the exact mechanics of how a forged status feeds into an automatic deploy/merge decision should be confirmed by a follow-up review of `app/models/shipit/webhooks/handlers/status_handler.rb` (or equivalent) and the CI-requirement enforcement code before treating this as fully proven end-to-end; the signature/target-binding flaw itself, however, is confirmed directly from the cited controller and handler code.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      Rails.logger.info([

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
