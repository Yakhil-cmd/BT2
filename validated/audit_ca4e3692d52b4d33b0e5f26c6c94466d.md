### Title
`review_stacks_enabled` is not enforced for `allow_with_label`/`prevent_with_label` provisioning due to operator precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`PullRequest::OpenedHandler#provision?` uses `&&`/`||` in a way that only gates the `allow_all` behavior with `review_stacks_enabled`, leaving `allow_with_label` and `prevent_with_label` completely unguarded by that flag. A repository configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` will still provision a `ReviewStack` if the PR carries the configured label.

### Finding Description
The claimed broken binding: `review_stacks_enabled (false) == the gate enforced before ReviewStack creation (should be true, but the code allows false)`.

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is therefore only ANDed into the first disjunct. If `provisioning_behavior` is `allow_with_label` (or `prevent_with_label`), the whole expression can be `true` regardless of `review_stacks_enabled`'s value, since the second/third disjuncts never reference it.

Path: `process` calls `respond_to_pull_request_opened?` → `provision?`; if true, `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` runs, calling `create!`, which builds a `ReviewStack` with `branch: params.pull_request.head.ref` (attacker-controlled) and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)` for provisioning. [2](#0-1) [3](#0-2) 

Attacker request: open a pull request from a branch they control on a tracked repository whose `provisioning_behavior` is `allow_with_label`, adding the configured `provisioning_label_name` label to their own PR (label names are attacker-visible/settable on PRs they open in their own fork/repo context per the standard GitHub PR-label webhook payload fields consumed here: `pull_request.labels[].name`) — `pull_request_has_provisioning_label?` reads exactly this field. [4](#0-3) 

No other guard intervenes: `respond_to_pull_request_opened?` only additionally checks `params.action == "opened"`, and there is no separate `review_stacks_enabled` check anywhere else in this handler or in `ReviewStackAdapter`. [5](#0-4) 

The existing test suite confirms the intended behavior is untested for this combination: `configure_provisioning_behavior(provisioning_enabled: false, ...)` is only exercised with `behavior: :allow_all`, never with `:allow_with_label` or `:prevent_with_label`. [6](#0-5) [7](#0-6) 

### Impact Explanation
For any tracked repository with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (or `prevent_with_label`), an attacker who can open a PR and control its labels causes a `ReviewStack` to be created with an attacker-controlled `branch` and queued into `ReviewStackProvisioningQueue`, which drives `stack.provisioner.up` and ultimately shell command execution via `PTY.spawn` in `Command#start`. [8](#0-7) [9](#0-8) 
This is repeatable against every tracked repository configured this way and matches the Critical category: unauthorized stack creation for a repository whose operator explicitly disabled review-stack provisioning, leading to potential RCE via the provisioning pipeline.

### Likelihood Explanation
Preconditions: the target repository must already be onboarded in Shipit and configured with `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a plausible/documented configuration meant to disable auto-provisioning while still defining a label policy). No Shipit credentials are needed by the attacker; they only need normal PR/label permissions on their own PR, which any GitHub contributor to the repo (or webhook-simulator, subject to normal webhook auth not covered by this bug) has. This is a pure logic error, deterministic and trivially reproducible.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire expression:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to the analogous logic in `labeled_handler.rb`, `unlabeled_handler.rb`, and `reopened_handler.rb`, which share the identical pattern.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb
test "does not create stacks when review_stacks_enabled is false, even with allow_with_label and label present" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::ReviewStack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix: `Shipit::ReviewStack.count` increases by 1 (test fails). After applying the parenthesization fix, the assertion passes, confirming `review_stacks_enabled == false` correctly blocks provisioning regardless of `provisioning_behavior`/label state.
