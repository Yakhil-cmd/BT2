### Title
Uncaught `throw Error("not 1 template")` in `definition template` signature-path evaluation crashes the whole node - ([File: definition.js])

### Summary
`validateAuthentifiers()` in `definition.js` evaluates the `'definition template'` operator by querying for the referenced `definition_template` unit and expects **exactly** one matching row. If it gets zero or more than one rows, it does not report a validation error through the callback chain (as the sibling structural-validation code path does) but instead does a raw synchronous `throw`, executed inside a MySQL/SQLite query callback with no surrounding try/catch. This is directly analogous to CVE-2023-2829, where BIND crashes because a code path that "synthesizes" an answer from previously-accepted/cached data hits an unexpected/malformed record shape and asserts instead of failing gracefully.

### Finding Description
`definition.js` has two evaluators that walk an address definition tree and both implement the `'definition template'` op by querying the `messages`/`units` tables for the referenced template unit:

- The structural validator (`validateDefinition`'s internal `evaluate`, used when the definition is first checked) handles the "not exactly 1 row" case gracefully: [1](#0-0)

`validateAuthentifiers()` is invoked from `validation.js`'s `validateAuthor()` for every unit signed by an address using an existing (already-recorded) definition — i.e. on the ordinary, unprivileged unit-posting path: [3](#0-2) 

Because the query at line 806-818 is executed **outside any try/catch** (it's a raw DB-driver callback), the `throw` is not converted into a validation error. It propagates as an uncaught exception in the Node.js event loop, which `network.js`'s global handler simply logs and re-throws to kill the process: [4](#0-3) 

The mismatch between the two evaluators (`cb("template not found or too many")` vs. `throw Error("not 1 template")`) means that a definition which passed the structural check at authoring time can still hit the crashing path later, because the DB state referenced by the query (`sequence='good' AND is_stable=1 AND main_chain_index<=last_ball_mci`) can change between the time the definition was created/checked and the time it is actually used to authorize spending:
- The referenced `definition_template` unit can subsequently be voided to `sequence='final-bad'` (e.g., due to it being a competing/non-serial unit that later loses), causing the row to disappear from the `sequence='good'` filter and driving `rows.length` to `0`.
- The unit may simply not yet be stable at evaluation time in some validation contexts, again producing `0` rows.

### Impact Explanation
Hitting this line kills the process handling the transaction (full daemon or hub crash via `process.on('uncaughtException')` → `throw err`). Since `validateAuthentifiers` is invoked for ordinary unit validation whenever an address's definition includes the `'definition template'` operator, any node validating a transaction from such an address at the moment its referenced template unit is/becomes non-'good' can be crashed. On a hub or full node this is a denial-of-service: the node stops processing new units until manually restarted, and if triggered broadly (e.g., every full node re-validating the same problematic transaction from the network) can prevent the network from confirming units, matching the "network unable to confirm new units" bar for a valid analog.

### Likelihood Explanation
Reaching the crash requires:
1. An address whose definition uses `['definition template', [unit, params]]` — fully attacker-controlled (any user can define such an address).
2. The referenced unit's `definition_template` message row to fail the `sequence='good' AND is_stable=1 AND main_chain_index<=last_ball_mci` condition at authentifier-evaluation time, even though it satisfied it (or was otherwise accepted) at definition-authoring time.

The most reliable path for an attacker to force this is to make the referenced template unit non-serial (double-spend it so a competing unit wins and it becomes `sequence='final-bad'`), then post a spending unit from the address that uses the definition template. This is entirely achievable by a single unprivileged actor controlling both the address and the competing spend of the template-defining unit's inputs, without needing any peer, hub, or node cooperation.

### Recommendation
Change the `'definition template'` case in `validateAuthentifiers()`'s `evaluate()` (definition.js:802-819) to match the structural validator's behavior: instead of `throw Error("not 1 template")`, call `cb2(false)` (or propagate a proper validation failure) when `rows.length !== 1`, so that mismatched/missing/voided template references cause the unit to be rejected as an ordinary validation error rather than crashing the process. Additionally, audit other unhandled `throw` statements inside raw DB-callback contexts, i.e. `definition.js:795` and `definition.js:812`, for the same class of issue, ensuring they either wrap in try/catch or return validation errors via `cb`.

### Proof of Concept
1. Attacker creates unit `T` containing an `app: "definition_template"` message with some template body.
2. Attacker defines address `A` with `['definition template', [T, {...}]]` inside a signature branch (e.g., wrapped in `['and', [['sig', ...], ['definition template', [T, {}]]]]`) and funds it; at authoring/first-validation time `T` is stable/good, so `A`'s definition passes structural validation.
3. Attacker double-spends the inputs that funded/created `T` (or otherwise arranges a competing unit) so that `T` eventually stabilizes with `sequence='final-bad'`.
4. Attacker (or the address owner) posts a new unit spending from `A`, requiring authentifier evaluation of the `'definition template'` branch. `validateAuthor` → `validateAuthentifiers` → `evaluate()` runs the query in definition.js:806-808, gets 0 rows (since `T` is no longer `sequence='good'`), and executes `throw Error("not 1 template")` at definition.js:812 with no surrounding try/catch.
5. The uncaught exception is caught only by `process.on('uncaughtException')` in network.js:4530-4543, which logs it and then re-throws, terminating the Node.js process on every full node/hub that validates this unit — a straightforward, single-actor-triggerable denial of service.
