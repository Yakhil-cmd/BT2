### Title
Cross-organization team membership mutation via `Team.find_or_create_by!(github_id:)` trusting attacker-supplied `team.id` without binding to signing organization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` resolves a `Team` purely by the attacker-controlled `params.team.id`, with no check that the resolved team's `organization` matches the organization (`params.organization.login`) whose `webhook_secret` actually verified the request. An organization that can legitimately sign membership webhooks for itself can reference another organization's `github_id` and delete a `Membership` row from that other organization's authorization team.

### Finding Description
The binding that must hold is: `organization_that_signed_the_request (derived from repository_owner / params.organization.login, checked in WebhooksController#verify_signature) == team.organization (the tenant whose Membership rows are mutated)`. This does not hold.

`WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and validates the signature against `Shipit.github(organization: repository_owner).verify_webhook_signature`: [1](#0-0) [2](#0-1) 

Since membership events carry no `repository` key, `repository_owner` is simply `params['organization']['login']`, an attacker-supplied string, which is exactly the org value used to select the secret used for signature verification. An attacker who owns/administers org A can therefore submit `{organization: {login: 'org-a'}, ...}` signed with org A's genuine `webhook_secret`, and verification succeeds — this part is legitimate and does not check anything about the `team` object.

`MembershipHandler#process` then resolves the team purely from `params.team.id` and never revalidates it against the verified organization: [3](#0-2) 

`Team.find_or_create_by!(github_id: params.team.id)` looks up an existing row by `github_id` alone. If org B's team was previously created (e.g., via a legitimate `added` webhook from org B, or via `Team.find_or_create_by_handle`), that row already exists with `organization = 'org-b'`. Because the record is found (not created), the block (`team.organization = params.organization.login`) never runs, so the attacker's declared `organization` value is not even applied — the pre-existing org B row is returned and mutated: [4](#0-3) 

`team.members.delete(member)` on line 30 then removes the `Membership` join row for the attacker-named `member.login`, an org-B (or globally-resolved) `User`, from org B's team — despite the request only being authenticated as belonging to org A.

No other guard intervenes: `ExplicitParameters` only validates types/presence, not organization ownership of the referenced team ID; there is no `require_permission!`/`authorized?` check inside webhook handlers (webhooks are authenticated solely via HMAC signature, not per-object authorization); and `Team#members` has no scoping tying deletions back to the requesting organization.

### Impact Explanation
An attacker who controls (or can trigger webhook delivery for) any organization configured in Shipit can, using only that organization's own legitimate webhook secret, delete `Membership` rows belonging to a *different* organization's authorization team, as long as they can guess or discover that team's numeric GitHub `id` (team IDs are visible via GitHub's public/team APIs or UI in many configurations, and are sequential/enumerable). Since Shipit's `Shipit.github_teams` configuration gates deploy/merge authorization, this is a cross-tenant escalation/deauthorization primitive: it can strip a legitimate maintainer of org B from their authorization team, without org B's webhook secret, GitHub App credentials, or any privileged session. This is repeatable against any known team ID and any member login, for as long as the attacker's own organization remains configured in Shipit. It matches the Critical category: "a payload for one repository/organization mutating another's ... team."

### Likelihood Explanation
Preconditions are realistic for any multi-tenant Shipit deployment: at least two organizations (A, B) configured with their own `webhook_secret`s, and the attacker must control org A well enough to trigger genuine `membership` webhook deliveries (or POST arbitrary crafted membership payloads and sign them with a secret they legitimately hold for org A — e.g., a GitHub App/organization webhook they administer). The attacker needs to know org B's team `github_id`, which is typically discoverable (team IDs appear in GitHub API responses, URLs, or can be brute-forced sequentially). No Shipit secrets, sessions, or API tokens are required. This is a low-cost, deterministic, repeatable exploit given those preconditions.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and `#process`), verify that any existing `Team` matched by `github_id` belongs to the organization that verified the webhook signature (`params.organization.login` / `repository_owner`) before performing `add_member`/`delete`. If the found team's `organization` does not match, reject/no-op (and log) rather than mutate. Consider scoping the lookup itself, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and raise/drop the event on a mismatch instead of falling through to the pre-existing cross-org record.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb` style, using fixtures/existing signature stubbing):
```ruby
test ":membership from org A cannot delete org B's team membership" do
  org_a = 'org-a'
  org_b = 'org-b'

  # Pre-existing team belonging to org B, with an existing legit maintainer
  team_b = Shipit::Team.create!(github_id: 999, organization: org_b, slug: 'auth-team', name: 'Auth Team', api_url: 'https://example.com')
  maintainer = shipit_users(:walrus) # or User.find_or_create_by_login!('legit-maintainer')
  team_b.add_member(maintainer)

  Shipit.github(organization: org_a) # org A configured with its own webhook_secret
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate valid org-A signature

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'removed',
    team: { id: team_b.github_id, name: team_b.name, slug: team_b.slug, url: team_b.api_url },
    organization: { login: org_a },
    member: { login: maintainer.login }
  }.to_json

  assert_no_difference -> { Shipit::Membership.where(team_id: team_b.id, user_id: maintainer.id).count } do
    post :create, body: payload, as: :json
    assert_response :ok
  end
end
```
Binding assertions:
- Before: `Membership.exists?(team_id: team_b.id, user_id: maintainer.id) == true`, request verified against `org_a`'s secret (`repository_owner == 'org-a'`), while `team_b.organization == 'org-b'`.
- After (current code): `Membership.exists?(team_id: team_b.id, user_id: maintainer.id) == false` — proving `org_a (signing org) != org_b (mutated team's org)` yet the mutation proceeded, demonstrating the break. A fixed implementation should keep the membership row intact and instead reject or ignore the event.
