### Title
`MembershipHandler#process` resolves `Team` solely by `github_id`, letting a validly-signed "membership" webhook from one organization mutate another organization's `Membership` rows - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`find_or_create_team!` looks up a `Team` with `Team.find_or_create_by!(github_id: params.team.id)` and only sets `team.organization`/`team.github_team` inside the create block, which never runs when a `Team` with that `github_id` already exists. `params.action == 'removed'` then calls `team.members.delete(member)` on whatever `Team` row was found, without ever checking that `params.organization.login` (the org the webhook claims to be from, and the org used to select the verification secret) matches the resolved `team.organization`.

### Finding Description
Binding that should hold: `team.organization == params.organization.login` for every team mutated by `MembershipHandler#process`. The code never asserts this.

Path: `WebhooksController#create` → `Shipit::Webhooks.for_event('membership')` → `MembershipHandler#process`: [1](#0-0) [2](#0-1) 

`find_or_create_team!` finds by `github_id` alone; the `organization` field is only written on creation. If a `Team` row for `github_id: N` already exists (created earlier from a legitimate `membership` webhook belonging to the victim organization, e.g. fixture `shopify_developers` with `github_id: 1`, `organization: "shopify"`), any subsequent webhook carrying `team.id = 1` resolves to that same victim `Team` object regardless of what `organization.login` the new payload claims.

Signature verification is keyed off the payload's own claimed organization, not off the resolved `Team`: [3](#0-2) [4](#0-3) 

In a multi-tenant Shipit deployment (one GitHub App/secret per organization - a supported configuration per `Shipit.github_app_config`/`github_organizations`), an attacker who legitimately controls their own organization's GitHub App can produce a validly-signed webhook for `organization.login: "attacker-org"` while setting `team.id` to the victim organization's real GitHub team id. `Team.find_or_create_by!(github_id: ...)` finds the victim's `Team` row, and `team.members.delete(member)` (or `team.add_member(member)`) mutates the victim's `Membership` table. Nothing in `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema checks that the resolved `Team#organization` matches the payload's `organization.login`.

### Impact Explanation
`Membership` rows feed `User#authorized?` (`Shipit.github_teams.map(&:id)` membership check): [5](#0-4) 
An attacker controlling their own org's webhook signing key can therefore add or remove memberships in a completely different organization's `Team`, which is a cross-tenant authorization mutation (adding a user to a team used in `Shipit.github_teams` grants that user login access; removing revokes it). This is a genuine cross-tenant write ("a payload for one repository/org mutating another's ... team") and can escalate into `Shipit.github_teams` authorization, matching the Critical/High impact categories in the program rules. It is repeatable against any `github_id` the attacker knows (GitHub team IDs are discoverable via the public GitHub API for teams the attacker can query, or via prior legitimate webhook traffic), and requires no GitHub access to the victim org.

### Likelihood Explanation
This requires a multi-organization Shipit deployment where the attacker legitimately owns a GitHub App/organization already wired into the same Shipit instance (so they possess a valid webhook secret for their own org) - this is an explicitly supported configuration (`config/secrets.development.example.yml` documents the multi-org schema, `Shipit.github_app_config`/`github_organizations` implement it). Given that precondition, the attacker's cost is a single crafted HTTP POST with a valid HMAC signature for their own org and a `team.id` equal to the victim's known GitHub team id. No GitHub access to the victim org, no Shipit session, and no privileged role is needed.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify (or enforce) that the resolved `Team#organization` equals `params.organization.login` before returning it; if it does not match, drop/reject the event instead of mutating the existing team's memberships. Additionally, scope the `find_or_create_by!` lookup by `(github_id, organization)` rather than `github_id` alone, and update `team.organization` only via a controlled, re-verified path.

### Proof of Concept
```ruby
test ":membership removed cannot delete a membership belonging to a different organization" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: 1
  victim_member = shipit_users(:walrus)
  Membership.create!(team: victim_team, user: victim_member) unless victim_team.members.include?(victim_member)

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'removed',
    team: { id: victim_team.github_id, slug: victim_team.slug, name: victim_team.name, url: victim_team.api_url },
    organization: { login: 'attacker-org' }, # attacker's own, validly-signed org
    member: { login: victim_member.login },
    repository: { owner: { login: 'attacker-org' } }
  }

  assert_no_difference -> { Membership.where(team: victim_team, user: victim_member).count } do
    post :create, body: payload.to_json, as: :json
  end
end
```
Before the fix, this assertion fails: the victim's `Membership` row is deleted even though the signed payload's organization (`attacker-org`) does not own `victim_team` (`organization: 'shopify'`).
