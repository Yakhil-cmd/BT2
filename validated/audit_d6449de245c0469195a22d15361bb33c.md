### Title
Exposure of permanent device pairing secret to the Arbstore server during arbiter contract dispute/appeal - ([File: arbiter_contract.js])

### Summary
`arbiter_contract.js` sends the contract counterparty's permanent device-pairing secret (`peer_pairing_code`) and the local user's own permanent pairing secret (`my_pairing_code`) in plaintext to a third-party HTTP service (the "Arbstore") whenever a dispute or appeal is opened. This is directly analogous to CVE-2026-34087 (OATHAuth exposing a sensitive secret to an unauthorized actor): a long-lived authentication secret is disclosed to a party that was never meant to hold it, and that secret can later be reused to impersonate/pair with the victim's device.

### Finding Description
Every device in `ocore` has a single, long-lived "permanent pairing secret" generated once via `getOrGeneratePermanentPairingInfo()`: [1](#0-0) 
This secret, combined with the device pubkey and hub, forms a `pairing_code` (`device_pubkey@hub#pairing_secret`). Because it is flagged `is_permanent`, `handlePairingMessage()` never consumes/deletes it after use — “multiple peers can pair through permanent secret”: [2](#0-1) 
So anyone who ever learns this value can, at any future time, add themselves as a correspondent device of the victim (`from_address, pubkey` inserted into `correspondent_devices`) and is then treated as a known correspondent, unlocking the ability to send `sign`, `arbiter_contract_offer`, `new_wallet_address`, etc. to the victim's wallet.

In `arbiter_contract.js`, when an arbiter-contract offer is accepted, `respond()` shares `my_pairing_code` with the direct peer (intended, since this is required for cosigning): [3](#0-2) 

However, when a dispute is opened, `openDispute()` sends **both** `my_pairing_code` and `peer_pairing_code` — the counterparty's permanent secret — in the plaintext JSON body directly to the Arbstore's HTTP API (`/api/dispute/new`), not inside the `encrypted_contract` blob that protects the contract text/contact info: [4](#0-3) 
The same happens on appeal, where `my_pairing_code` is sent unencrypted to the Arbstore's `/api/appeal/new` endpoint: [5](#0-4) 

The Arbstore is only supposed to be trusted to relay dispute resolution data and post transaction proofs, yet through this API it receives the **permanent** device pairing secret of both contract parties — even though only the counterparty (via the intended one-time contract flow) needed it for cosigning. The Arbstore-side handler in `wallet.js` (`arbiter_dispute_request`) even persists `plaintiff_pairing_code`/`respondent_pairing_code` server-side: [6](#0-5) 
and the schema confirms these are stored in plaintext columns: [7](#0-6) 

Because the secret is *permanent* (reused across every contract, dispute, or appeal a user ever engages in — not per-session/per-counterparty), any compromise of the Arbstore server (or a malicious/curious Arbstore operator, or anyone who can read its dispute database/log) is sufficient to obtain a durable credential letting the attacker pair as a correspondent device with either the plaintiff or the respondent at will, indefinitely, without their knowledge — an unauthorized actor gaining a sensitive secret it should never have had, exactly the CWE-200 "Exposure of Sensitive Information to an Unauthorized Actor" class described in the OATHAuth advisory.

### Impact Explanation
Once an attacker (a malicious/compromised Arbstore) has the permanent `pairing_code` of a wallet, it can silently pair as that device without the user's action (pairing via a permanent secret bypasses the “correspondent not known” whitelist and immediately becomes a trusted correspondent — see `handlePairingMessage`). From that point on, the attacker's device is treated by the victim's wallet as a legitimate paired peer and can attempt device-message-driven attacks: `arbiter_contract_offer`, `sign` requests for shared/multisig addresses the attacker convinces the victim to add, phishing via `text`/`object` messages, or `new_wallet_address` invitations that lead to loss/misdirection of funds if the victim is careless. This qualifies as unauthorized access enabling potential fund loss/spending manipulation, matching the "High" severity intent of the report.

### Likelihood Explanation
The disclosure happens automatically and unconditionally any time a user opens a dispute or files an appeal on an arbiter contract — a normal, expected user action, not an edge case. No special privileges are required by the Arbstore operator; it simply needs to read data it already legitimately receives over its own API (or have its DB compromised). Given that both peer and self pairing codes are transmitted outside the encrypted contract envelope, the leakage is guaranteed to occur on every dispute.

### Recommendation
- Do not send the counterparty's `peer_pairing_code` (or even the reporter's own `my_pairing_code`) to the Arbstore at all; the Arbstore does not need a durable pairing secret — it only needs a way to notify/relay to the parties, which can be done through the arbiter's own paired-device messaging channel instead.
- If pairing information must be conveyed to the Arbstore, use short-lived, single-use, non-permanent pairing secrets generated specifically for this dispute (`startWaitingForPairing()`, which are consumable) rather than the account-wide permanent secret.
- Place any pairing/contact data required by the Arbstore inside the already-encrypted `encrypted_contract` payload rather than as plaintext JSON fields.
- Consider rotating/invalidating the permanent pairing secret if it may already have been exposed via this path in production Arbstores.

### Proof of Concept
1. Alice and Bob create an arbiter contract; Bob is Alice's counterparty and only Bob is meant to learn Alice's `my_pairing_code` through `arbiter_contract_offer`/`respond` (arbiter_contract.js:118-155).
2. Alice opens a dispute against Bob via `openDispute(hash, cb)` (arbiter_contract.js:262-319). The code builds `data.my_pairing_code = objContract.my_pairing_code` and `data.peer_pairing_code = objContract.peer_pairing_code` (Bob's permanent secret) and POSTs it as plaintext JSON to `<arbstore_url>/api/dispute/new` via `httpRequest`.
3. A malicious or compromised Arbstore now has permanent, reusable pairing codes for both Alice and Bob, persisted in its `arbiter_disputes` table (`plaintiff_pairing_code`, `respondent_pairing_code`) — see the schema at initial-db/byteball-sqlite-light.sql:911-930.
4. Using Bob's leaked permanent `pairing_code` (`device_pubkey@hub#pairing_secret`), the attacker calls `sendPairingMessage()` toward Bob's hub. `handlePairingMessage()` on Bob's device accepts it because the secret is valid and permanent (device.js:815-837), silently adding the attacker as a trusted correspondent device of Bob — without Bob approving or even being aware, months or years after the original dispute.
5. The attacker is now a paired correspondent and can send further device messages (`sign`, `arbiter_contract_offer`, `object`, etc.) that Bob's wallet will process as coming from a legitimate contact, enabling follow-on social-engineering/fund-risk attacks.
