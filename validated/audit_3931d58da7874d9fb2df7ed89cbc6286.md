### Title
Webhook signature is authenticated against one organization while the handler acts on an unrelated repository/commit taken from the same unverified payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/`webhook_secret` used to validate the HMAC signature based on `repository.owner.login` (falling back to `organization.login`) read directly from the untrusted JSON body. [1](#0-0) [2](#0-1)  Once the signature is accepted, the event handlers act on a *different* field of the same body: `Handler#repository_name` uses `repository.full_name` to look up the target repository/stacks, [3](#0-2)  and `StatusHandler#process` doesn't scope by repository at all, it matches purely on `sha` across the entire `Commit` table. [4](#0-3)  Nothing ties the org used to select the HMAC secret to the repository/commit that is actually mutated.

### Finding Description
On a multi-tenant Shipit install, `Shipit.github(organization: ...)` resolves per-organization GitHub App configuration (including a distinct `webhook_secret`) as documented for "Using Multiple Github Applications". [5](#0-4)  A coordinator who legitimately administers **one** onboarded GitHub organization (`org-A`) knows `org-A`'s `webhook_secret` (they configured it on their own GitHub org's webhook settings). That secret is only supposed to authorize events for `org-A`'s repositories.

The binding that should hold is:
`organization authenticated by HMAC (params.dig('repository','owner','login') / 'organization','login')` == `organization/repository actually written by the handler (payload.dig('repository','full_name') or commit lookup by sha)`

Because the attacker fully controls the raw JSON body they sign, they can set `repository.owner.login` (or `organization.login`) to `org-A` — so `verify_signature` selects `org-A`'s known secret and the HMAC check passes — while simultaneously setting `repository.full_name` to a victim's repo (e.g. `victim-org/victim-repo`) for `push`/`pull_request` events, or simply putting a victim commit's `sha` in a `status` event body (which has no repository scoping check at all). [4](#0-3)  The two representations of "which repo/org this event is about" diverge, exactly analogous to the Sherlock report's validated-vs-stored value divergence (`makerLimit`/`scale` truncation): one field is covered by the trust check, a different field is what downstream logic actually consumes.

`Repository.from_github_repo_name` performs no ownership cross-check against the authenticated organization either — it just splits `owner/name` and looks up the row. [6](#0-5) 

### Impact Explanation
- Forged `status` events let the attacker call `commit.create_status_from_github!` for **any** commit in **any** stack on the instance, regardless of which org's secret was used to authenticate the request, since `StatusHandler` does no repository scoping and matches by `sha` alone. [4](#0-3)  The status/CI-gate handling (`require_ci`, `commit.deployable?`) is exercised by the deploy flow shown in the deploy controller tests, so a forged "success" status can flip a victim commit's deployability and enable an unauthorized deploy of code that never passed the victim's real CI. [7](#0-6) 
- Forged `push` events let the attacker trigger `sync_github` against an arbitrary victim `Repository`/`Stack` chosen via `repository.full_name`, independent of the org whose secret authenticated the request. [3](#0-2) [8](#0-7) 

This is a cross-repository/cross-tenant write using credentials the attacker legitimately possesses for a different, unrelated org — matching the "cross-repository writes" / "unauthorized deploy" High/Critical criteria.

### Likelihood Explanation
Requires the attacker to be an onboarded but otherwise unprivileged organization admin in a multi-organization Shipit deployment (a realistic, documented deployment topology) who knows only their own organization's `webhook_secret` — no access to the victim's secret, `ApiClient` token, GitHub App private key, or repository write access is needed. This mirrors the original report's "malicious but bounded coordinator" trust model.

### Recommendation
After parsing the webhook payload, verify that the organization/owner used to select the HMAC secret is the same organization that owns the `repository.full_name` (and, for `status` events, restrict the `Commit` lookup to commits belonging to repositories under that authenticated organization) before dispatching to any handler. Reject the event if these do not match.

### Proof of Concept
1. Attacker is the legitimate GitHub org admin for `org-A`, onboarded to a multi-tenant Shipit instance, and knows `org-A`'s configured `webhook_secret`.
2. Attacker crafts a `status` webhook JSON body: `{"repository": {"owner": {"login": "org-A"}}, "sha": "<victim_commit_sha_in_org-B>", "state": "success", ...}`.
3. Attacker computes `X-Hub-Signature` using `org-A`'s known `webhook_secret` over this exact raw body and POSTs it to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "org-A")` and the HMAC check passes, because it is verified against `org-A`'s real secret and the exact body the attacker signed. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit belonging to `org-B`'s stack, and creates a forged "success" status on it. [4](#0-3) 
6. The victim commit is now marked deployable in `org-B`'s stack despite `org-A` never having any relation to it.
