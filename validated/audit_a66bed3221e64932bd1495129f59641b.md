This ocore code contains a genuine access-control gap analogous to the Coolify bug class: an authorization check that should scope a sensitive action to the authorized caller was explicitly disabled/removed, allowing any caller reachable over the same channel (a paired device) to trigger the sensitive action for a resource outside its authorized scope.

### Title
Missing cosigner-authorization check in device `"sign"` request handler allows any paired device to request signatures for local addresses it does not co-own - ([File: wallet.js])

### Summary
In `wallet.js`, `handleMessageFromHub`'s `"sign"` case forwards signing requests to `findAddress`, and in the `ifLocal` branch, the code that would verify that the requesting correspondent device (`from_address`) is actually a registered cosigner of the target local address has been intentionally commented out [1](#0-0) . By contrast, the `ifRemote` branch for the very same message explicitly enforces membership before acting: [2](#0-1) 

### Finding Description
`handleMessageFromHub` dispatches inbound device messages received from any paired correspondent (a device that only needs to complete the `"pairing"` handshake to become a correspondent) [3](#0-2) . Once paired, `subject: "sign"` messages are accepted from that correspondent device without further scoping beyond validating the unit's shape and that `body.address` appears among the unit's authors [4](#0-3) . When `findAddress` resolves the target address to a wallet/key hosted locally on this device, `ifLocal` is invoked and, absent the removed cosigner check, straight away proceeds to build the unit, validate it, and emit `signing_request` for user/automated confirmation and signing [5](#0-4) 

This exactly mirrors the Coolify pattern: an endpoint reachable by any already-authenticated peer (a paired correspondent device, analogous to an "authenticated user") is missing the authorization middleware/check that should restrict the action to a caller who is actually within scope for the targeted resource (a genuine cosigner of the address, analogous to the caller's own server/resource). The address-membership check (`authorAddresses.includes(body.address)`) only proves the address is *an* author of the attacker-supplied unit — it proves nothing about the relationship between `from_address` (the requesting device) and that address's actual authorized signer set (`wallet_signing_paths`/`extended_pubkeys`). Any correspondent who knows or guesses one of the victim's local wallet addresses (these are not secret — they appear in received payments, chat, shared-address setup, etc.) can submit arbitrary `unsigned_unit` content and drive the victim node into validating and emitting a `signing_request` for it, without ever having been established as a legitimate cosigner of that address.

### Impact Explanation
If the consuming application's `signing_request` handler auto-approves requests from known correspondents (e.g., automated multisig bots, exchange hot-wallet cosigner services, or any headless wallet built on this event without an independent membership check of its own), an unrelated paired device can cause the victim to sign and broadcast payments from its addresses to attacker-chosen destinations — i.e., unauthorized spending of the victim's funds. Even where a human confirmation dialog exists, the removed check means the UI cannot rely on "requesting device is a known cosigner" as a trust signal, undermining the multisig authorization model itself and enabling social-engineering/confused-deputy attacks (device impersonating a legitimate cosigner request). This satisfies the "concrete unauthorized spending" bar for a valid analog.

### Likelihood Explanation
Reaching this path requires only becoming a correspondent of the victim device, which is achieved via the standard, low-friction pairing flow (`"pairing"` subject, requiring only a pairing secret and is explicitly whitelisted for non-correspondents) [6](#0-5) . No special network position or malicious hub/peer is required — this is a normal correspondent using the documented device-messaging protocol, which is squarely in-scope (an unprivileged paired-device message sender). The remaining gate is downstream UI/automation trust behavior for `signing_request`, which is outside ocore but plausible for automated or trust-by-correspondent deployments (multisig bots), matching the "authenticated user reaching resources outside authorized scope" pattern from the Coolify analog.

### Recommendation
Restore (and complete) the cosigner-membership check in the `ifLocal` branch of the `"sign"` handler: before validating/emitting `signing_request`, verify that `from_address` corresponds to a device actually listed as a signer for `body.address`/`body.signing_path` (via `wallet_signing_paths` for wallet-defined-by-keys addresses and `shared_address_signing_paths` for shared addresses), mirroring the check already performed in the `ifRemote` branch (`other_device_addresses.includes(from_address)`). If multilateral signing to non-cosigner addresses must be supported, distinguish that use case explicitly and require an independent authorization signal (e.g., the address must be a contract-tracked peer address) rather than skipping the check entirely.

### Proof of Concept
1. Attacker device pairs with victim device using the standard pairing flow (`"pairing"` subject with a pairing secret obtained from any real interaction, e.g., a legitimate one-time chat/contract pairing).
2. Attacker learns one of the victim's local wallet addresses `A` (visible from any payment received from the victim, or from a shared-address negotiation).
3. Attacker sends a `"sign"` device message: `{address: A, signing_path: "r", unsigned_unit: {authors: [{address: A}], messages: [{app:"payment", payload:{outputs:[{address: attacker_address, amount: N}]}}], ...}}`.
4. On the victim's node, `findAddress` resolves `A` as local (`ifLocal`), and — because the cosigner check is commented out — the unit is validated and `signing_request` is emitted for confirmation/auto-signing, despite the attacker never having been registered as a cosigner of `A`.
5. If the consuming wallet automation trusts correspondent-originated `signing_request`s (common for bot/automated cosigners), the victim signs and broadcasts the attacker's payment, resulting in unauthorized spend.
