### Title
Full liquidation with bad-debt socialization can be permanently blocked by a single unresolvable debt-asset entry - (File: `local-testing/contracts/market/market.clar` / `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate()`'s bad-debt-socialization path folds over *all* of a borrower's other debt entries via `socialize-debt-asset`, and any single entry that fails to socialize (via `vault-socialize-debt`, `vault-accrue`, or `debt-remove-scaled`) causes the whole `liquidate()` call — for any liquidator, at any time — to revert with `ERR-BAD-DEBT-SOCIALIZATION-FAILED`.

### Finding Description
In `liquidate()` (`local-testing/contracts/market/market.clar:1556-1583`, mirrored in `mainnet/contracts/market/v0-4-market.clar:1533-1560`), once collateral is fully exhausted (`no-collateral-left`), the contract folds `socialize-debt-asset` over `fresh-debt-list` (the borrower's remaining debt entries across possibly multiple assets): [1](#0-0) 

`socialize-debt-asset` itself, on any single failure of `vault-socialize-debt`, `vault-accrue`, or `debt-remove-scaled`, sets `success: false` for the whole fold accumulator: [2](#0-1) 

`debt-remove-scaled` in the vault registry enforces `scaled-amount > u0` and internally `remove-user-scaled-debt` enforces `amount <= current-scaled-debt`: [3](#0-2) [4](#0-3) 

If a borrower's debt map ever contains, for a secondary asset, a scaled amount that is `u0` (or otherwise inconsistent with what `socialize-debt-asset` computes/passes), `debt-remove-scaled` reverts internally, `socialize-debt-asset` catches it via `unwrap!` and returns `success: false`, and the outer `asserts!` on line 1571/1548 then reverts the *entire* `liquidate()` call — undoing the collateral seizure and debt repayment for the primary asset that had already succeeded via `vault-system-repay` and `market-vault.collateral-remove`/`debt-remove-scaled` calls earlier in the same transaction (Clarity transactions are atomic, so those calls, though individually successful, get rolled back).

This mirrors the audited bug: a single problematic element in a batch/loop that a liquidator cannot control or skip causes the whole shared operation (liquidation + bad-debt socialization) to permanently fail, blocking every future liquidator (an unprivileged third party distinct from the borrower) from ever liquidating that specific position.

### Impact Explanation
If this state is reached and persists, the borrower's undercollateralized position can never be liquidated by anyone: `liquidate()` always reverts at the socialization step, regardless of which liquidator calls it or with what parameters, because the failure is intrinsic to the borrower's stored debt-list contents, not to caller-supplied inputs. Bad debt for that borrower can never be socialized/written off, meaning depositors in the affected vaults permanently bear the unrecoverable debt exposure without the vault ever writing it down — a form of temporary/permanent freezing of protocol funds/insolvency exposure that liquidators (an unprivileged party distinct from the borrower) cannot bypass.

### Likelihood Explanation
This requires the borrower's debt-list to reach an inconsistent state (e.g., a stale/zero-scaled secondary debt entry) at the exact moment `no-collateral-left` triggers socialization. Whether a legitimate user flow (partial repayments, multiple small borrows/repayments across assets, or accrual/rounding edge cases in `mul-div-down`) can actually leave a zero-but-still-listed scaled debt entry in the position's debt list was not fully verifiable from the retrieved code — the map deletion in `remove-user-scaled-debt` deletes entries when `updated-scaled-debt` reaches `u0`, which should normally prevent stale zero entries, but the exact invariant guaranteeing this in all borrow/repay/liquidate-multi interleavings could not be confirmed with certainty from the available index.

### Recommendation
Make `socialize-debt-asset` resilient to a single failing entry instead of forcing the entire `liquidate()` call to revert: either (a) skip a failing debt entry and continue socializing the others, recording which entries failed for later remediation via a dedicated admin/DAO recovery path, or (b) decouple the bad-debt socialization step from the collateral-seizure/debt-repayment step so that a failure in socialization does not roll back the liquidation that already completed successfully (e.g., perform socialization in a separate transaction/call that liquidators can retry per-asset).

### Proof of Concept
Not independently reproduced against a live contract; based on static analysis of `market.clar`/`v0-4-market.clar`'s `liquidate()`, `socialize-debt-asset`, and `market-vault.clar`'s `debt-remove-scaled`/`remove-user-scaled-debt`, showing that an `ERR-AMOUNT-ZERO`/`ERR-INSUFFICIENT-DEBT` failure on any single entry in the borrower's debt list during the fold causes the whole `liquidate()` call to abort via `ERR-BAD-DEBT-SOCIALIZATION-FAILED`, rolling back the already-successful primary-asset repay/seizure in the same atomic transaction.

(define-private (remove-user-scaled-debt (user-id uint) (asset-id uint) (amount uint))
  (let ((key { id: user-id, asset: asset-id })
        (current-scaled-debt (default-to u0 (get scaled (map-get? debt key)))) ;; graceful default to u0
        (legal? (asserts! (<= amount current-scaled-debt) ERR-INSUFFICIENT-DEBT))
        (updated-scaled-debt (- current-scaled-debt amount)))
    (if (is-eq updated-scaled-debt u0)
        (map-delete debt key)
        (map-set debt key { scaled: updated-scaled-debt }))
    (ok updated-scaled-debt)))
