### Title
CCMenuController#show bypasses `current_api_client.stack_id` scoping, letting any CCMenu token read every stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` restricts stack access to the client's authorised `stack_id` via `stacks.from_param!`, but `Api::CCMenuController` overrides `stack` with its own private method that calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` relation. Any valid CCMenu token — including one created with a narrow `stack_id` scope — can therefore fetch build/name/status data for every stack on the instance simply by varying the `stack_id` path/query parameter.

### Finding Description
The claimed binding is:
`{ stack_id : GET /ccmenu/:stack_id.xml with token T returns 200 } == { stack_id : stack_id == T.api_client.stack_id (or all stacks if stack_id is nil) }`

Base class scoping: [1](#0-0) 
`stacks` is limited to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `stack` resolves through that scoped relation.

`CCMenuController` however defines its own `stack`: [2](#0-1) 
This calls `Stack.from_param!(params[:stack_id])` on the full `Stack` table, completely ignoring `current_api_client.stack_id`. The only gate is `require_permission :read, :stack`, which just checks that the client's `permissions` array contains `"read:stack"` — a scope-independent, boolean check performed by `ApiClient#check_permissions!`: [3](#0-2) 

So the two sides of the binding diverge: the actual accessible set is "every stack in the database" as long as the token has the `read:stack` permission bit, regardless of the client's `stack_id` restriction. An attacker holding one leaked CCMenu token (even one deliberately scoped by an operator to a single stack) can iterate `stack_id` values (e.g. `owner/repo/branch` style `to_param` strings) against `GET /ccmenu/:stack_id.xml?token=...` and get `200` with XML containing the stack's `name` (which encodes `repo_owner/repo_name/environment`), `lastBuildStatus`, `lastBuildLabel`, etc. for stacks outside its authorised scope, and `404`/`RecordNotFound` for guesses that don't exist — enabling systematic enumeration of private repository/environment names across tenants.

Existing guards do not prevent this: `require_permission!` only checks the permission string, not stack identity; there is no re-application of `stacks` scoping in this controller; `Stack.from_param!` itself has no client-awareness.

### Impact Explanation
Any client with a `read:stack`-permissioned token — even one an operator explicitly scoped to a single stack via `stack_id` — can read the `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl` of every other stack in the instance, disclosing `repo_owner/repo_name/environment` triples and deploy state for repositories the token was never authorised to see. This is repeatable for every stack and is a cross-tenant authorization bypass / IDOR, matching the High-severity category of "escalation ... unauthenticated read of stack state."

### Likelihood Explanation
The attacker needs only one leaked/legitimate CCMenu API token with `read:stack` permission (a low, commonly-granted permission, since CCMenu is a read-only CI status feed) — no `stack_id`-unscoped token is required. Guessing/enumerating `stack_id` `to_param` values (owner/name/branch/env, often predictable or obtainable from PR/webhook metadata) is inexpensive, and the 200-vs-404 response cleanly oracles existence, so this is fully feasible and repeatable via `test/controllers/api/ccmenu_controller_test.rb`-style requests.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` relation from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` on the unscoped `Stack` model, so `current_api_client.stack_id` scoping is enforced identically to every other API controller.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a stack-scoped token cannot read another stack's status via CCMenu" do
  scoped_stack = shipit_stacks(:shipit)
  other_stack = Stack.create!(repository: Repository.new(owner: 'foo', name: 'bar'), branch: 'main')

  @client.update!(stack_id: scoped_stack.id, permissions: ['read:stack'])

  get :show, params: { stack_id: scoped_stack.to_param, token: @client.authentication_token }
  assert_response :ok # expected: within scope

  get :show, params: { stack_id: other_stack.to_param, token: @client.authentication_token }
  assert_response :not_found # BROKEN: currently returns :ok, proving the scoping bypass
end
```
Binding before: `authorized(token) = {scoped_stack.id}`. Binding after (observed): `accessible(token) = Stack.all` because `CCMenuController#stack` ignores `current_api_client.stack_id`, so `other_stack` returns `200` instead of the expected `404`.
