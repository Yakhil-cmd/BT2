## Title
Webhook signature verification binds to `repository.owner.login`, but every event handler acts on the independent `repository.full_name` field, letting an org whose webhook secret is known trigger sync/deploy actions on another org's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC signature against using `params.dig('repository','owner','login')` (falling back to `organization.login`), then verifies the *entire raw body* against that secret. Every downstream `Webhooks::Handlers::Handler` (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) instead resolves which `Repository`/`Stack` to mutate using a *different* JSON field in the same body: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so the identity that "authenticated" the payload (`repository.owner.login`) is not the identity that is actually written to (`repository.full_name`).

### Finding Description [1](#0-0) 
`verify_signature` picks the GitHub App config with `Shipit.github(organization: repository_owner)` and only checks the signature is valid for *that* organization's secret: [2](#0-1) 
`repository_owner` is read straight from the untrusted JSON body (`repository.owner.login` or `organization.login`).

Once the signature check passes, `create` dispatches to handlers with the raw parsed JSON: [3](#0-2) 

Handlers never look at `repository.owner.login` again. They resolve the target `Repository`/`Stack` purely from `repository.full_name`: [4](#0-3) [5](#0-4) 

Shipit explicitly supports hosting multiple GitHub organizations behind one instance, each with its own `webhook_secret` set by that org's own GitHub App administrator: [6](#0-5) 

The binding that should hold is: **organization that authenticated the request (owner of the `webhook_secret` used) == organization/repository being written to**. Instead:
- Before the attack: org A's admin only knows org A's `webhook_secret`; org A's webhook deliveries only ever contain `repository.owner.login == "orgA"` and `repository.full_name` values under org A.
- After the attack: org A's admin (who legitimately possesses org A's `webhook_secret` because they configured org A's GitHub App in Shipit) crafts an arbitrary JSON body with `repository.owner.login = "orgA"` (so `verify_signature` selects and validates against org A's known secret) but `repository.full_name = "orgB/victim-repo"`. The HMAC is computed correctly over the whole forged body using the known org A secret, so `verify_webhook_signature` returns `true`, and the handler then acts on org B's stack using attacker-controlled `ref`/`after`/`sha`/`state` values.

### Impact Explanation
A `push` event forged this way reaches `PushHandler#process`, which calls `stack.sync_github(expected_head_sha: params.after)` for stacks belonging to the victim organization's repository: [7](#0-6) [8](#0-7) 
This enqueues `GithubSyncJob`, which fetches commits via `stack.github_api` (the victim org's own GitHub App credentials, unaffected by the attacker) and, upon appending new commits, can lead to `schedule_continuous_delivery` / `ContinuousDeliveryJob` firing an actual deploy if the victim stack has `continuous_deployment` enabled: [9](#0-8) [10](#0-9) 
Because the sync is forced with `force_spec_cache`/an attacker-chosen `expected_head_sha`, this is a cross-organization write that can result in an unauthorized deploy of a stack the attacker has no access rights to - satisfying the Critical bar ("cross-repository writes" / "unauthorized deploy").

### Likelihood Explanation
This requires the attacker to be an administrator of *some* organization already onboarded to a shared multi-tenant Shipit instance (i.e., knows that org's own `webhook_secret`, which the docs explicitly say each org owner configures themselves) but has no authorization over the *victim* organization's repositories/stacks. Given Shipit's documented multi-org hosting model, this is a realistic, low-effort cross-tenant escalation: craft one JSON body, HMAC-SHA1 it with a secret the attacker legitimately possesses, and POST it to the shared `/webhooks` endpoint.

### Recommendation
In `WebhooksController`/`Webhooks::Handlers::Handler`, require that the repository/organization identity used to select and validate the webhook signature (`repository.owner.login` / `organization.login`) matches the repository identity actually used to resolve the target `Stack`/`Repository` (`repository.full_name`'s owner segment) before any handler runs. Reject the request (422) if they diverge.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `github.webhook_secret` (per `docs/setup.md` multi-org example) and each with at least one `Stack` whose `continuous_deployment` is enabled for `orgB`.
2. As an attacker who administers `orgA`'s GitHub App (and thus knows `orgA`'s `webhook_secret`), build a JSON payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-that-exists-on-orgB-repo>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>`.
4. `POST /webhooks` with header `X-Github-Event: push` and this body/signature.
5. Observe `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) succeeds because it validates against `orgA`'s secret, yet `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-23`) enqueues `GithubSyncJob` for `orgB`'s stack, syncing/deploying it without any authorization from `orgB`.
