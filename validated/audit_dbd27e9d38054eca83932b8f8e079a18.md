### Title
Diff-header text parsing (`"diff --git "` split + `a/... b/...` regex) desyncs from `-z` NUL-delimited path enumeration, letting an adversarial filename cause diff-content/file-path misattribution and reviewer bypass - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`_git_name_only` correctly enumerates changed paths using `git diff --name-only -z`, which is NUL-delimited and therefore safe for any byte sequence in a filename except NUL/`/`. `parse_diff_into_files` and `extract_file_paths_from_diff`, however, parse the *content* diff for those same paths by naive text splitting on the literal string `"diff --git "` and a line-anchored regex `^a/(.+?) b/(.+)$`, which is not robust against a path that itself contains that literal substring or diff-header-like tokens.

### Finding Description
`_git_name_only` (`plugins/security-guidance/hooks/gitutil.py`, lines 303-318) splits on `"\0"` and is authoritative for which paths are "in scope" for review — it feeds `compute_v2_review_set` in `diffstate.py` (lines 386-426), whose output set is turned into a `--` pathspec passed to `get_git_diff` (`gitutil.py` lines 391-427). That call runs a normal (non `-z`) `git diff` and hands the raw text to `parse_diff_into_files` / `extract_file_paths_from_diff` (`gitutil.py` lines 587-654), which:
- split the whole diff blob on the literal string `"diff --git "` (line 597/624), and
- extract the path from the first line via `re.match(r'^a/(.+?) b/(.+)$', lines[0])` (line 603/632).

Git does not escape a literal `diff --git ` occurring inside a path, and (unlike `_git_name_only`/`_git_status_porcelain`) `get_git_diff`'s `GIT_CMD` invocation does not pass `-c core.quotePath=false`, but more importantly quoting only covers control/non-ASCII bytes — an ASCII sequence such as `diff --git ` or a fabricated `" b/"` token embedded in a filename passes through unescaped. A crafted path (e.g. `evil.py b/decoy.txt\ndiff --git a/`) can therefore inject an extra, attacker-controlled `diff --git a/... b/...` boundary into the text stream that `file_diffs = diff_output.split("diff --git ")` consumes. This desynchronizes the naive splitter from git's actual per-file diff boundaries: a single file's diff can be split into two chunks whose first lines match the `a/... b/...` regex against attacker-chosen strings, so `_is_reviewable_source(file_path)` and the reviewer end up associating hunk content with a `file_path` that does not correspond to the blob that content actually came from.

Because `_git_name_only`/`_git_status_porcelain` (NUL-safe) and `parse_diff_into_files`/`extract_file_paths_from_diff` (naive-text) are the two parsers that must agree on the `(file_path ↔ content)` binding for the review pipeline to be trustworthy, and they use fundamentally different tokenizers, the TARGET_BINDING invariant is not guaranteed to hold for adversarial filenames.

### Impact Explanation
`_is_reviewable_source` gates whether a hunk's content is ever shown to the LLM security reviewer, based solely on the (possibly misattributed) `file_path`'s extension/basename. If the split desync causes a security-sensitive file's diff content (e.g. a `.py`/`.sh` change containing exfiltration code or a hardcoded secret) to be re-labeled under a non-reviewable extension (or under an unrelated benign path), the security-guidance review is silently bypassed for that content, or the content is reported to the user under a misleading path, obscuring the true origin. This matches a review/export-integrity/trust-boundary-bypass style impact rather than a confidentiality/RCE one.

### Likelihood Explanation
Exploitation requires the attacker to get a file with an adversarial name (containing the literal `diff --git ` substring or a fabricated `a/... b/...` header sequence) into the working tree that Claude Code will diff — e.g. via a malicious repo checkout, a PR branch, or prompt-injection instructing the agent to create such a file. This is unusual but filesystem-legal on Linux/macOS (any byte except NUL and `/`), and it does not require any elevated privilege, only ordinary "attacker can influence repository content" access, so it is within the stated threat model though the precondition (getting such an unusual filename accepted and diffed) makes it a low-frequency, proof-of-concept-grade issue rather than a routinely triggerable one.

### Recommendation
Replace the literal-string `"diff --git "` splitting and single-line regex header parsing in `parse_diff_into_files`/`extract_file_paths_from_diff` with a parser that uses the same NUL-delimited/unambiguous enumeration already computed by `_git_name_only`/`_git_status_porcelain` as ground truth (e.g., diff per-path using `git diff -- <single-path>` in a loop, or use `git diff --numstat -z`/patch-id-per-path) instead of re-deriving file boundaries from free-text heuristics. At minimum, cross-validate that the set of `file_path`s extracted by `parse_diff_into_files` exactly equals the NUL-delimited path set from `_git_name_only`, and fail closed (drop/flag) any diff whose derived path set diverges.

### Proof of Concept
Unit/fuzz test in the plugin's diff-parsing test module:
1. Construct a synthetic `diff_output` string simulating two files where the second file's path contains the literal substring `diff --git ` and where the injected fragment forms a syntactically valid `a/x b/y` header (e.g. path = `` `evil.py\ndiff --git a/injected b/injected2.py` ``).
2. Call `parse_diff_into_files(diff_output)` and `extract_file_paths_from_diff(diff_output)`.
3. Independently compute the "true" file→content mapping using an NUL-safe reference splitter (or a hand-verified expected mapping).
4. Assert that `parse_diff_into_files` returns exactly one `(file_path, content)` tuple per actual file and that each `file_path` matches the actual originating blob's true path — the test should currently FAIL, demonstrating the misattribution, e.g. content belonging to `evil.py` gets attached to `file_path == "injected2.py"` instead.
5. As an invariant/fuzz extension, generate random filenames embedding `diff --git `, `\na/`, and ` b/` substrings and assert `len(parse_diff_into_files(diff)) == number_of_actual_files` and no cross-contamination of hunk lines between files.
