The AddressWhitelist report describes an ownership-transfer bug where a whitelist check does not re-validate against the new owner. In this codebase, the only analogous "owner" fields are `AmmConfig.protocol_owner` and `AmmConfig.fund_owner`, whose transfer functions (`set_new_protocol_owner`, `set_new_fund_owner` in `programs/cp-swap/src/instructions/admin/update_config.rs`) are gated behind `owner.key() == crate::admin::ID` in `UpdateAmmConfig`, making them privileged-signer-only paths that are explicitly out of scope.

The `pool_creator` field on `PoolState`, which is the closest thing to an unprivileged-relevant "owner" identity (used in `collect_creator_fee` and `collect_creator_fee_permissionless`), is set once at pool creation via `pool_state.initialize(...)` [1](#0-0)  and there is no instruction that allows transferring or updating `pool_creator` afterward [2](#0-1) . There is also no whitelist-style data structure reachable by an unprivileged swapper, LP, or pool creator in `initialize`, `initialize_with_permission`, `deposit`, `withdraw`, `swap_base_input`, `swap_base_output`, or the token CPIs. Since the bug class requires a mutable owner/whitelist relationship reachable without privileged access, and no such reachable analog exists in the allowed scope, this report does not map to a valid finding here.
