### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` lookup in StatusHandler enables unauthorized PR merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits to attach a GitHub `status` webhook to using only `Commit.where(sha: params.sha)`, with no scoping to the repository that authenticated the webhook. Because the DB uniqueness constraint on `commits` is `[sha, stack_id]` (not globally unique on `sha`), an attacker who controls any repository can push/reference a commit whose sha equals the head sha of a victim's queued `MergeRequest` and fire a `status` webhook signed for their *own* org to write a fabricated `success` `Status` onto the victim's `Commit` row, causing `MergeRequest#all_status_checks_passed?` to pass and `ProcessMergeRequestsJob` to call `merge!` on the victim's PR.

### Finding Description
The broken binding is: **the repository whose `webhook_secret` authenticated the `status` payload == the repository whose `Commit`/`MergeRequest` gets mutated**. This does not hold.

- `WebhooksController#verify_signature` verifies the HMAC using `Shipit.github(organization: repository_owner)` where `repository_owner` comes from `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . This proves the request came from *some* repository belonging to that org — nothing more.
- The dispatched handler, `StatusHandler#process`, then does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
This is a *global, unscoped* query across every stack in the Shipit instance — it never uses `Handler#stacks`, which is the helper other handlers (e.g. `PushHandler`) use to scope to `Repository.from_github_repo_name(repository_name).stacks` [4](#0-3) [5](#0-4) .
- Crucially, `Commit` sha is only unique per `stack_id`, not globally: `add_index :commits, %i(sha stack_id), unique: true` [6](#0-5) , confirmed by the schema `t.index ["sha", "stack_id"] ... unique: true` [7](#0-6) . So two different stacks/repositories can legitimately hold `Commit` rows with the identical `sha` (this happens naturally with forks that share commit history, or can be engineered by an attacker who fetches/cherry-picks the exact victim commit — git shas are content-addressed and repo-independent).

Exploit flow:
1. Victim's stack has a queued `MergeRequest` with `merge_status: 'pending'` whose `head` is a `Commit` with sha `S`, currently missing/failing checks (`all_status_checks_passed?` false via `StatusChecker.new(head, head.statuses_and_check_runs, ...)` [8](#0-7) ).
2. Attacker fetches/pushes the identical commit (same sha `S`, since git shas are deterministic from content and not bound to any particular repo) into their own repo `attacker/evil`, opens a PR there.
3. Attacker sends `POST /webhooks` with `X-Github-Event: status`, body `{sha: S, state: 'success', repository: {owner: {login: 'attacker'}}}`, signed with attacker's own valid webhook secret for their own org. `verify_signature` passes because the signature is valid for `attacker`'s org — it does not check that `attacker` owns the repo tied to `sha`.
4. `StatusHandler#process` runs `Commit.where(sha: S)` and finds **both** the attacker's own commit row (if any) and the victim's `Commit` row with the same sha, then calls `create_status_from_github!` on **all** of them, writing a fabricated `success` `Status` on the victim's `Commit`.
5. `ProcessMergeRequestsJob#perform` (scheduled) calls `merge_request.refresh!`, then `merge_request.all_status_checks_passed?`, which now returns `true` because of the forged `Status` attached to `head` [9](#0-8) .
6. `merge_request.merge!` is invoked, calling `stack.github_api.merge_pull_request(...)` — an unauthorized merge of the victim's PR is triggered using CI approval fabricated from an unrelated repository [10](#0-9) .

None of the existing guards prevent this: `verify_signature` only authenticates the org that sent the payload, not the scope of which `Commit` rows the handler is allowed to mutate; `ExplicitParameters` schema on `StatusHandler` only validates types/presence of `sha`/`state`, not repo binding [11](#0-10) ; `drop_unhandled_event` and `force_github_authentication` are irrelevant to this path.

### Impact Explanation
An attacker who controls any single repository registered with Shipit (or even any repo tracked by a `Shipit.github_teams`-configured org, since only the org needs a valid webhook secret) can forge a `Status` on any `Commit` row in the entire installation whose sha they can predict or reproduce (most easily a shared-history commit from a fork of the target repo). This can flip `MergeRequest#all_status_checks_passed?` to true for a victim's queued PR and trigger `merge!`, causing an actual unauthorized merge via `stack.github_api.merge_pull_request` — a genuine "payload for one repository mutating another's commit/stack, leading to an unauthorized merge," matching the Critical severity category. It is repeatable against any stack/repo pairing where sha collision/reuse is achievable, and it doesn't require any Shipit credentials — only ownership of one legitimate (even brand-new, attacker-owned) GitHub repository connected to the Shipit instance.

### Likelihood Explanation
Preconditions: attacker needs their own registered/trackable GitHub repository with a working webhook secret (trivial to obtain — just create a repo and let Shipit's app be installed, or any org already onboarded to Shipit where attacker can open PRs). Attacker needs to know/reproduce the victim's queued MergeRequest head sha, which is public (visible on the victim's open PR) and trivially reproducible by fetching that exact commit into their own fork (git commit hashes are content-derived and identical across repos holding the same commit). The only additional requirement is that `ProcessMergeRequestsJob` run on schedule (it does, per `MergeRequest.schedule_merges`/cron) and that the victim stack has `merge_queue_enabled` and `allows_merges?`. This is a low-cost, highly repeatable attack requiring no privileged role, session, or secret.

### Recommendation
Scope `StatusHandler#process` (and any other handler using raw `Commit.where(sha:)` lookups) to the repository that authenticated the webhook, mirroring `PushHandler`'s use of `stacks`/`Repository.from_github_repo_name(repository_name)`. E.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a status update only ever touches commits belonging to stacks whose backing repository matches the payload's `repository.full_name`, closing the cross-tenant sha-collision path.

### Proof of Concept
Minitest (e.g. in `test/controllers/webhooks_controller_test.rb` or a new `status_handler_test.rb`):
```ruby
test "status webhook from unrelated repo must not affect another stack's commit with colliding sha" do
  colliding_sha = "cafebabe" * 5 # 40 hex chars
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = shipit_stacks(:cyclimse) # simulates a different repo/org

  victim_commit = victim_stack.commits.create!(sha: colliding_sha, message: "victim", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  attacker_commit = attacker_stack.commits.create!(sha: colliding_sha, message: "attacker", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  merge_request = victim_stack.merge_requests.create!(number: 999, head: victim_commit, merge_status: 'pending')

  # Before: assert the equality is broken across repos
  assert_not_equal victim_stack.repository.full_name, "attacker/evil"

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate attacker's own valid signature for their org only

  request.headers['X-Github-Event'] = 'status'
  payload = {
    'sha' => colliding_sha,
    'state' => 'success',
    'repository' => { 'owner' => { 'login' => 'attacker-org' }, 'full_name' => 'attacker/evil' }
  }.to_json

  post :create, body: payload, as: :json

  merge_request.reload
  refute merge_request.all_status_checks_passed?, "victim MergeRequest must not gain a status from an unrelated repo's webhook"
end
```
Given the current unscoped `Commit.where(sha:)` implementation, this test fails (the victim's commit gains the forged `Status` and `all_status_checks_passed?` becomes true), demonstrating the vulnerability; after applying the recommended `stacks`-scoped fix, the test passes.
