### Title
Cross-organization commit status forgery via `StatusHandler` unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub `status` webhook against the GitHub App/organization derived from `repository.owner.login` (or `organization.login`) in the payload, but `StatusHandler#process` never re-checks that field when applying the event — it looks up target commits solely by `sha` across the *entire* database, with no repository/organization scoping. This is the same class of bug as the Sherlock M-5 finding: the field verified by the trust boundary (`repository_owner`, used to select the signing secret) is not the same field used when performing the state-changing action (`sha`, used to pick which commit/stack gets written to).

### Finding Description
The webhook signature check in `app/controllers/shipit/webhooks_controller.rb` is: [1](#0-0) 

`repository_owner` is derived purely from the JSON payload: [2](#0-1) 

Signature verification thus proves only that *some* organization "O" (whose `webhook_secret` is configured in `Shipit.github`) signed this exact byte string, where "O" == `repository.owner.login`. It says nothing about which `sha`/stack the event is allowed to affect — the entire remaining payload (including `sha`) is attacker-controlled content that was merely signed by org O's secret, and Shipit trusts all of it.

`StatusHandler`, however, resolves the target purely by `sha`, without any repository/organization filter: [3](#0-2) 

`Commit.where(sha: params.sha)` is a global, unscoped query across all stacks/repositories/organizations configured in the Shipit instance — it is not restricted to commits belonging to the repository/organization that was actually used to verify the signature. `Commit#create_status_from_github!` then creates a `Status` for every matching commit, regardless of which org owns that commit's stack.

The equality the trust boundary is supposed to enforce is:
`organization used to verify signature (payload.repository.owner.login)` == `organization owning the repository/stack that gets a Status record written`.

`StatusHandler` breaks this equality: verification is bound to `repository.owner.login`, but the write is bound only to `sha`, a value with no cross-check against `repository.owner.login`/`repository.full_name` at all.

### Impact Explanation
Any party that legitimately controls a GitHub organization/repository already registered as a Shipit `github_hooks`/`github` app (i.e., can produce a validly-signed `status` webhook for *their own* org) can forge a `sha` value equal to a commit SHA that exists in a *different* organization's stack in the same Shipit instance (SHAs are public/enumerable via the target org's GitHub API, or simply guessable if reused). Sending a `status` event with `state: "success"` and that foreign `sha` will:

1. Pass signature verification (correctly signed by their own org's secret against `repository.owner.login` == their own org).
2. Create a `Shipit::Status` row on the *foreign* stack's commit via the unscoped `Commit.where(sha:)` lookup.
3. Trigger `Status#schedule_continuous_delivery` / `Commit#schedule_continuous_delivery`, which — if the foreign stack has `continuous_deployment` enabled and that commit is otherwise the head of an undeployed queue — can cause Shipit to deploy that commit to production, or otherwise satisfy CI gating so an unrelated deploy proceeds. This crosses the "unauthorized deploy" bar, and represents a cross-repository/cross-organization write of trusted CI-state data using credentials belonging to a different, unrelated organization.

### Likelihood Explanation
Any onboarded GitHub organization/repository with its own configured `webhook_secret` (a normal, unprivileged tenant of the Shipit instance) can exploit this by simply crafting a custom `status` webhook payload and computing the HMAC with their own secret — no compromise of another org's secret, no GitHub App private key, and no Shipit session/API token is required. The only extra knowledge needed is a target commit SHA belonging to another stack, which is often discoverable (public repos, or SHAs leaked via other Shipit-exposed data such as deploy pages/commit lists).

### Recommendation
In `StatusHandler` (and similarly in `CheckSuiteHandler`/other handlers that resolve targets independent of `repository.full_name`), scope the lookup by the repository identified in the payload, consistent with the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)`), e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
This binds the write to the same `repository.full_name`/organization used to select the signing secret, restoring the equality that verification is meant to guarantee.

### Proof of Concept
1. Attacker controls organization `attacker-org`, which is registered in Shipit with its own `webhook_secret` (`S_attacker`).
2. Target `victim-org/app` has an active stack in the same Shipit instance with `continuous_deployment: true`, and has an undeployed commit with known SHA `deadbeef...`.
3. Attacker builds a JSON body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(S_attacker, body)` and POSTs to `/github/webhooks`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against `S_attacker`.
6. `StatusHandler#process` executes `Commit.where(sha: "deadbeef...")`, which matches the victim's commit regardless of organization, creating a forged `success` status and potentially triggering continuous deployment on `victim-org/app`. [4](#0-3) [1](#0-0)

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
