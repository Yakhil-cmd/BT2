### Title
Bandwidth request generation can silently drop the entire backlog (all-zero bitmap) when a single buffered receipt/group pushes `total_size` past `max_single_grant` in one step - ([File: core/primitives/src/bandwidth_scheduler.rs])

### Summary
`BandwidthRequest::make_from_receipt_sizes` walks the buffered receipt (group) sizes and, for each one, advances `cur_value_idx` until it finds a `values[]` bucket ≥ `total_size`, setting that bit. If a single increment pushes `total_size` past `values[values.len()-1]` (`max_single_grant`) before any bit has ever been set, the loop breaks without setting any bit and the whole backlog is treated as if no bandwidth is needed, because `bitmap.is_all_zeros()` returns `true` and the function returns `None`. An attacker who fully controls receipt sizes sent to their own account across shards can engineer exactly this jump.

### Finding Description
The core loop is: [1](#0-0) 

```
total_size += receipt_size
if total_size <= base_bandwidth { continue }
while cur_value_idx < values.len() && values[cur_value_idx] < total_size { cur_value_idx += 1 }
if cur_value_idx == values.len() { break }     // <-- no bit set here
bitmap.set_bit(cur_value_idx, true)
```

`values[0] > base_bandwidth` and `values[values.len()-1] == max_single_grant` are both asserted by the repo's own unit test: [2](#0-1) 

The values feeding this loop are receipt-group sizes, each capped to `params.max_receipt_size` before being passed in: [3](#0-2) 

In the exact parameters used by the repo's own tests, `max_single_grant == max_receipt_size` (both `4 * 1024 * 1024`), as shown by the printed `values` array whose last element is `4194304`: [4](#0-3) 

Given this, if a shard's outgoing buffer already contains receipts summing to just under `base_bandwidth` (which produces no bit, by design, since `total_size <= base_bandwidth`), and the attacker then enqueues one more receipt/group whose size is close to `max_receipt_size`, the resulting `total_size` (`~base_bandwidth + max_receipt_size`) exceeds `max_single_grant` (`values.last()`). Because `cur_value_idx` was never advanced by a prior bit-setting iteration, the `while` loop runs all the way to `values.len()` in this single iteration, hits `if cur_value_idx == values.len() { break }`, and **exits without ever calling `set_bit`**. Since this is the only receipt group processed before the break, the bitmap remains all zeros, `is_all_zeros()` is `true`, and the function returns `None` even though the shard has a real, sizeable backlog waiting to be sent (potentially several MB).

This differs from the safe case demonstrated by the `two_max_size_receipts` test, where the first receipt (exactly `max_receipt_size`) sets the last bit *before* the second receipt causes the overflow-and-break; there, a bit was already set so the final bitmap is non-zero: [5](#0-4) 

The unsafe case (large jump on the very first over-threshold receipt) is not covered by any existing test, including the randomized test which draws receipt sizes uniformly and is unlikely to hit the precise "accumulate to just under base_bandwidth, then one huge jump directly over max_single_grant" pattern with high probability, though it is not a targeted adversarial test either: [6](#0-5) 

### Impact Explanation
When this triggers, `generate_bandwidth_request` (called per destination shard while building the chunk's outgoing `BandwidthRequests`) yields `None` for that shard-pair despite a real, non-trivial backlog: [7](#0-6) 

The bandwidth scheduler never sees a request for this link, so it will not grant any bandwidth for it, and the buffered receipts to that destination shard are stuck. This matches the "congestion / receipt accounting failure" impact class: receipts can be starved of bandwidth grants indefinitely because the protocol logic itself fails to represent the backlog, not because of scheduler contention. This does not directly cause fund loss but leads to indefinite receipt stalling for a shard-pair link, a protocol liveness/progress defect.

Note that once bandwidth eventually gets granted for other reasons (e.g., new smaller receipts arrive later and organically trigger correctly-sized requests, since `cur_value_idx` is reset each time `make_from_receipt_sizes` is called fresh from current buffer contents), the backlog can eventually be requested again on a subsequent block if buffer composition changes. The starvation is therefore conditional on the buffer's exact composition being recomputed identically (same "small tail + one huge jump" pattern) every time the request is regenerated, which an attacker can maintain by continuously refilling the buffer with the same size profile.

### Likelihood Explanation
The attacker only needs control over their own account's outgoing cross-contract calls to shape receipt sizes in the outgoing buffer to a shard they also control (both sides), which is fully within an unprivileged account holder's capability via public RPC. Concretely: (1) issue enough small function calls so the destination shard's buffered receipts to that target shard sum to just under `base_bandwidth` (tens of KB, cheap), then (2) issue one call producing a receipt at or near `max_receipt_size` (bounded by protocol's max receipt size limit, ~4MB by default). This is a two-step, fully attacker-controlled, reproducible sequence with no privileged access required. The main uncertainty is the exact production values of `base_bandwidth`/`max_single_grant`/`max_receipt_size` (only test values were verified here), but the flaw is structural: it exists whenever a single buffered group's size increment can exceed `max_single_grant - base_bandwidth`, which is architecturally possible since group sizes are capped only by `max_receipt_size`, and in the tested configuration `max_receipt_size == max_single_grant`.

### Recommendation
In `BandwidthRequest::make_from_receipt_sizes`, when `cur_value_idx` reaches `values.len()` (i.e., `total_size` exceeds `max_single_grant`), set the highest bit (`values.len() - 1`) before breaking, instead of breaking without setting any bit:
```rust
while cur_value_idx < values.len() && values[cur_value_idx] < total_size {
    cur_value_idx += 1;
}
if cur_value_idx == values.len() {
    bitmap.set_bit(values.len() - 1, true);
    break;
}
bitmap.set_bit(cur_value_idx, true);
```
This ensures that any backlog exceeding `max_single_grant` still results in a maximal (non-zero) bandwidth request, preserving the progress/no-starvation invariant.

### Proof of Concept
Add a targeted unit test (not covered by existing tests) alongside `test_make_bandwidth_request_from_receipt_sizes` in `core/primitives/src/bandwidth_scheduler.rs`:

```rust
#[test]
fn test_large_jump_past_max_single_grant_does_not_zero_out_request() {
    let max_receipt_size = 4 * 1024 * 1024;
    let params = BandwidthSchedulerParams::new(
        NonZeroU64::new(6).unwrap(),
        &make_runtime_config(max_receipt_size),
    );

    // Accumulate just below base_bandwidth (no bit set yet, by design).
    let below = params.base_bandwidth - 1;
    // One huge receipt that pushes total_size past max_single_grant in one step.
    let huge = max_receipt_size; // == params.max_single_grant in this config

    let sizes = [below, huge];
    let request = BandwidthRequest::make_from_receipt_sizes(
        ShardUId::single_shard().shard_id(),
        make_sizes_iter(&sizes),
        &params,
    )
    .unwrap();

    // There IS a real backlog (below + huge >> base_bandwidth), so a request
    // must not be None / all-zero.
    assert!(request.is_some(), "backlog exists but no bandwidth request was generated");
}
```
Expected current (buggy) behavior: `request` is `None` because the bitmap ends up all-zero. Expected fixed behavior: `request` is `Some(...)` with the last bit set. A broader fuzz/property test can also be added: for random sequences of receipt sizes fed through `make_from_receipt_sizes`, assert that whenever the cumulative sum exceeds `base_bandwidth`, the returned request is `Some` (never `None`) — this would catch the same class of "false-negative all-zero bitmap" bugs.

```rust
    fn generate_bandwidth_request(
        &self,
        to_shard: ShardId,
        trie: &dyn TrieAccess,
        shard_layout: &ShardLayout,
        side_effects: bool,
        params: &BandwidthSchedulerParams,
    ) -> Result<Option<BandwidthRequest>, StorageError> {
        // Get (group) sizes of receipts stored in outgoing buffer to the shard.
        let mut receipt_sizes_iter =
            self.get_receipt_group_sizes_for_buffer_to_shard(to_shard, trie, side_effects, params);

        // When making a bandwidth request to a child shard which has been split from a parent
        // shard, we have to include the receipts stored in the outgoing buffer to the parent shard
        // in the bandwidth request for sending receipts to the child shard. Forwarding receipts
        // from the buffer to parent uses bandwidth granted for sending receipts to one of the
        // children. Not including the parent receipts in the bandwidth request could lead to a
        // situation where a receipt can't be sent because the grant for sending receipts to a child
        // is too small to send out a receipt from a buffer aimed at a parent.
        if let Ok(parent_shard_id) = shard_layout.get_parent_shard_id(to_shard) {
            let parent_receipt_sizes_iter = self.get_receipt_group_sizes_for_buffer_to_shard(
                parent_shard_id,
                trie,
                side_effects,
                params,
            );

            receipt_sizes_iter = Box::new(parent_receipt_sizes_iter.chain(receipt_sizes_iter));
        }

        // There's a bug which allows to create receipts above `max_receipt_size` (https://github.com/near/nearcore/issues/12606).
        // This could cause problems with bandwidth scheduler which would generate requests for size above max size, and these
        // requests would never be fulfilled. For bandwidth requests let's pretend that all sizes are below `max_receipt_size`.
        // The same pretending logic is also present in `try_forward` which compares receipt size with outgoing limit.
        // This logic should also make it possible to do protocol upgrades that lower `max_receipt_size` without too much trouble.
        let sizes_iter = receipt_sizes_iter
            .map_ok(|group_size| std::cmp::min(group_size, params.max_receipt_size));

        // Create the bandwidth request based on buffered receipt (group) sizes
        BandwidthRequest::make_from_receipt_sizes(to_shard, sizes_iter, params)
```
