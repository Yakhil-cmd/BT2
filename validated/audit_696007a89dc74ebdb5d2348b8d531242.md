### Title
Unchecked `creator` account in `initialize_with_permission` allows setting `pool_creator` to the zero/unspendable address, permanently freezing accrued creator fees - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`InitializeWithPermission::creator` is declared as a raw `UncheckedAccount<'info>` with no signer requirement and no constraint validating it is a meaningful, spendable address. Its key is written directly into `PoolState.pool_creator` during pool creation, and the pool's creator-fee-collection paths trust that value unconditionally.

### Finding Description
In `initialize_with_permission.rs`, the `creator` account is documented only as `/// CHECK: creator of pool` and has no `address`, `signer`, or non-default-value constraint: [1](#0-0) 

Any account whose `permission` PDA exists can call `initialize_with_permission` and supply an arbitrary `creator` pubkey (e.g. the all-zero `Pubkey::default()`, which has no corresponding private key). That value is stored verbatim into `PoolState.pool_creator` via `pool_state.initialize(...)`: [2](#0-1) 

`PoolState.initialize` performs no validation on the `pool_creator` argument before storing it: [3](#0-2) 

As swaps occur on the pool, `update_fees` unconditionally accrues `creator_fees_token_0`/`creator_fees_token_1` regardless of who or what `pool_creator` is: [4](#0-3) 

These accrued creator fees can only be withdrawn through `collect_creator_fee` (requires `creator: Signer<'info>` constrained by `address = pool_state.load()?.pool_creator`) or `collect_creator_fee_permissionless` (requires an `UncheckedAccount` constrained the same way, with an ATA created for that `creator` address): [5](#0-4) [6](#0-5) 

If `pool_creator` is the zero pubkey (or any other address with no known private key), `collect_creator_fee` can never be satisfied since no signature can ever be produced for that key, and `collect_creator_fee_permissionless` will only ever move the funds into an SPL token account whose `authority`/owner is that same unspendable key — funds that can never be transferred out again because no one holds the corresponding private key.

### Impact Explanation
Every swap that occurs on such a pool routes an ever-growing balance of `creator_fees_token_0`/`creator_fees_token_1` into vault accounting that becomes permanently unrecoverable. This is a permanent freezing of pool funds (the creator-fee share of every trade), reachable by any account holding a valid `permission` PDA calling a single instruction (`initialize_with_permission`) with attacker-chosen `creator` account data. This matches the accepted impact class of "permanent freezing of user or LP funds."

### Likelihood Explanation
`initialize_with_permission` is directly reachable by anyone possessing a `Permission` account (the intended, expected caller class for this permissioned pool-creation entrypoint), and the vulnerable field is a plain instruction-supplied account with zero on-chain validation, requiring no unusual state or privileged compromise. The mistake is trivial: leaving `creator = Pubkey::default()` (or any keyless address) is a single click/typo away.

### Recommendation
Add an explicit check in `initialize_with_permission` (and defensively in `PoolState::initialize`) rejecting `creator.key() == Pubkey::default()` (and ideally requiring `creator` to at least be a non-program, non-zero pubkey), e.g.:
```rust
require_keys_neq!(ctx.accounts.creator.key(), Pubkey::default(), ErrorCode::InvalidCreator);
```
placed before `pool_state.initialize(...)` is invoked.

### Proof of Concept
1. Attacker obtains/holds a valid `Permission` PDA (the normal precondition for calling `initialize_with_permission`).
2. Attacker calls `initialize_with_permission` supplying `creator = Pubkey::default()` (or any other address they don't control the private key for) while all other accounts/mints are valid.
3. `pool_state.pool_creator` is now permanently set to an address with no signing capability.
4. Normal `swap_base_input`/`swap_base_output` traffic on this pool accrues `creator_fees_token_0`/`creator_fees_token_1` via `PoolState::update_fees`.
5. `collect_creator_fee` can never succeed (no one can sign as `pool_creator`); `collect_creator_fee_permissionless` succeeds but deposits the fees into a token account owned by the zero address, which is permanently unspendable — the funds are frozen forever.
