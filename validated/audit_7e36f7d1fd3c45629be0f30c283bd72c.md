### Title
Cross-repository commit status forgery via unscoped SHA lookup in StatusHandler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` accepts and applies a GitHub `status` webhook to *every* `Commit` record that matches the given `sha`, without ever requiring or consulting a `:repository` field. Because git commit SHAs are content-derived and identical commits routinely exist in multiple linked repositories (forks, mirrors, shared history), any repository owner who is linked into Shipit can cause GitHub to emit a legitimately-signed `status` event that Shipit then applies to an unrelated stack's commit, forging its CI status.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`params.repository.full_name == <repository that owns the Commit(s) being mutated>` — this equality is never even computed, because `StatusHandler#params` has no `:repository` field at all.

Compare the two handlers:
- `PullRequest::EditedHandler#params` requires `:repository { requires :full_name }` and scopes the write to `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any `PullRequest` record. [1](#0-0) 
- `StatusHandler#params` only requires `:sha` and `:state`, with no `:repository` block whatsoever. [2](#0-1) 

`StatusHandler#process` then performs a global, repository-agnostic lookup:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 

`Commit.where(sha: ...)` is not scoped by `stack_id` or repository — it can match commits belonging to any stack/repository in the installation, since `sha` is unique only in combination with `stack_id` (see `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`, which indexes `sha` per `stack_id`, not globally). The base `Handler` class does provide a `repository_name`/`stacks` helper that scopes lookups by `payload.dig('repository', 'full_name')`, [4](#0-3)  but `StatusHandler#process` never calls it — it goes straight from `sha` to `Commit`, bypassing repository binding entirely.

**Exploit flow:** An attacker who has push/maintainer access to their own GitHub repository that is linked into Shipit (a routine, unprivileged, self-service capability — no Shipit session or secret needed) can:
1. Identify a commit SHA that also exists in a victim stack's repository — trivially satisfied for any fork/mirror sharing history with an upstream project registered in Shipit, since forked commits keep the exact same SHA as upstream.
2. Use GitHub's own "Create a commit status" REST API (with their own personal GitHub token, no Shipit secret required) to set an arbitrary status (`success`, `failure`, etc.) on that SHA within their own repository.
3. GitHub, as the legitimate webhook sender for the attacker's linked repository, computes a **correctly signed** `status` webhook (using the real `webhook_secret` Shipit configured for that repo) and POSTs it to `/webhooks`.
4. `WebhooksController` verifies the signature successfully (it is genuinely valid — GitHub signed it) and dispatches to `StatusHandler` based on `X-GitHub-Event: status`.
5. `StatusHandler#process` finds *any* `Commit` row with that `sha` — including the one belonging to the victim's unrelated stack — and writes a forged status onto it via `create_status_from_github!`.

This bypasses `verify_signature` entirely (the signature is real), bypasses `drop_unhandled_event` (the event type is legitimately `status`), and is not caught by `ExplicitParameters` (the schema simply never asks for a repository).

### Impact Explanation
A forged commit status on a victim's `Commit` propagates directly into `Commit#status`, which feeds `deployable?`, `blocked?`, and `Hook.emit(:deployable_status, ...)`. [5](#0-4)  Setting a fabricated `success` status can unblock a commit that failed real CI in the victim stack, enabling an unauthorized deploy; setting a fabricated `failure`/`error` status can block or stall a victim's legitimate release. This is a cross-tenant integrity break: "a payload for one repository mutating another's stack, commit" — matching the Critical severity category. It is repeatable against any repository/stack pair that shares a commit SHA with an attacker-controlled linked repository, which is the common case for forks of any project onboarded into Shipit.

### Likelihood Explanation
Preconditions are modest: the attacker needs one repository already linked in Shipit that they control (a normal, low-privilege GitHub capability many open-source contributors/maintainers have), and a shared commit SHA with the target stack (trivial via forking/mirroring). No Shipit secret, session, or API token is required — the forged webhook is a byproduct of a genuine GitHub API call the attacker is authorized to make on their own repository. This is inexpensive, fully repeatable, and does not depend on any race condition or timing.

### Recommendation
Add a required `:repository` field to `StatusHandler#params` (mirroring `EditedHandler`) and scope the lookup by stack/repository, e.g.:
```ruby
requires :repository do
  requires :full_name, String
end
...
def process
  stacks.commits.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
using the existing `stacks` helper on `Handler`, so a status webhook can only mutate commits belonging to the repository that actually sent it.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
class StatusHandlerBindingTest < ActiveSupport::TestCase
  test "StatusHandler does not require :repository while EditedHandler does" do
    status_fields = Shipit::Webhooks::Handlers::StatusHandler.param_parser.fields.map(&:name)
    edited_fields = Shipit::Webhooks::Handlers::PullRequest::EditedHandler.param_parser.fields.map(&:name)

    refute_includes status_fields, :repository
    assert_includes edited_fields, :repository
  end

  test "a status payload with no repository mutates a commit in an unrelated stack" do
    victim_stack = shipit_stacks(:shipit)
    attacker_repo_commit_sha = "deadbeef" * 5

    commit = victim_stack.commits.create!(sha: attacker_repo_commit_sha, message: "shared history commit")

    payload = {
      "sha" => attacker_repo_commit_sha,
      "state" => "success"
      # no "repository" key at all
    }

    Shipit::Webhooks::Handlers::StatusHandler.call(payload)

    assert commit.reload.statuses.exists?(state: "success")
  end
end
```
Both assertions demonstrate the equality `params.repository.full_name == <owning repository>` is never established for `StatusHandler` (unlike `EditedHandler`), and that a payload lacking any repository identification successfully mutates a commit that could belong to any stack.
