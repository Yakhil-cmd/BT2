### Title
Permanent freezing of accumulated creator fees via a frozen/blacklisted creator token account in `collect_creator_fee` / `collect_creator_fee_permissionless` - ([File: programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs])

### Summary
`collect_creator_fee` and `collect_creator_fee_permissionless` push accumulated creator fees to a token account owned by `pool_state.pool_creator` via `transfer_checked`. If that destination token account is (or becomes) frozen by the mint's freeze authority — the standard SPL/Token-2022 blacklist-equivalent mechanism used by tokens like USDC/USDT — the transfer permanently reverts. Because `creator_fees_token_0`/`creator_fees_token_1` are only zeroed after a successful transfer, and that same accounting value is subtracted out of the pool's usable liquidity via `vault_amount_without_fee`, the corresponding tokens become permanently locked inside the pool's vault, unreachable by the creator or by LPs.

### Finding Description
`collect_creator_fee_permissionless` can be invoked by any unprivileged `payer`; the fee always flows to the fixed `creator_token_0`/`creator_token_1` ATA owned by `pool_state.pool_creator` [1](#0-0) . The instruction transfers `creator_fees_token_0`/`creator_fees_token_1` from the vault to that account and only resets the tracked amounts to zero after the transfer succeeds: [2](#0-1) 

The underlying transfer uses `token_2022::transfer_checked`, which will fail for any frozen destination token account (frozen state is a native SPL Token/Token-2022 feature, the exact analog of a USDC/USDT blacklist entry): [3](#0-2) 

`PoolState::vault_amount_without_fee` subtracts `protocol_fees + fund_fees + creator_fees` from the raw vault balance to compute the tradable/withdrawable reserves used by both `swap_base_input`/`swap_base_output` and `withdraw`: [4](#0-3) 

If the creator's fee-receiving token account becomes frozen (e.g., the mint issuer freezes it, or the creator's account is frozen for unrelated compliance reasons on a regulated token such as USDC/USDT), every call to `collect_creator_fee`/`collect_creator_fee_permissionless` reverts forever. The `creator_fees_token_0`/`creator_fees_token_1` counters can never be decremented, so the corresponding tokens remain locked inside `token_0_vault`/`token_1_vault` permanently — excluded from LP redemption math (`vault_amount_without_fee`) and unclaimable by the creator, with no alternate-recipient fallback anywhere in the instruction set (`collect_creator_fee` and `collect_creator_fee_permissionless` both hard-code the destination to the `pool_creator`'s own ATA).

This mirrors the reported Cooler bug class exactly: a push-based transfer to a fixed, potentially blacklistable/freezable address, with no pull-based recovery mechanism, causing funds to be permanently stuck once that address is blocked.

### Impact Explanation
The affected funds are real value sitting in the pool vaults (`token_0_vault`/`token_1_vault`) that becomes permanently unclaimable by any party — not the protocol admin, not the creator, not the LPs (since it's excluded from LP redemption accounting). This is a permanent freezing of pool funds triggered purely by standard token-freeze functionality, satisfying the "permanent freezing of user or LP funds" criterion. Severity is bounded by the fact that only the creator-fee-denominated portion is affected (not the full vault), but it grows unboundedly over time as swaps continue to accrue creator fees that can never be swept out.

### Likelihood Explanation
Likelihood is moderate: it requires the mint's freeze authority to freeze the specific pool-creator ATA. This is entirely plausible for pools created around regulated/freezable tokens (USDC, USDT, or any Token-2022 mint with a freeze authority), and once frozen, the trigger condition (calling the permissionless collect instruction) is fully unprivileged and requires only a single transaction — no special accounts or timing needed.

### Recommendation
Add a pull-based / escrow fallback for creator (and protocol/fund) fee collection: if the direct transfer to the recorded recipient fails (e.g., due to a frozen account), allow the fee to be redirected to a claimable escrow account controlled by the creator, or allow the creator to designate/update an alternate receiving token account, so that a frozen destination cannot permanently trap funds inside the vault.

### Proof of Concept
1. Create a pool where `token_0_mint` (or `token_1_mint`) is a token with a freeze authority (e.g., a Token-2022 mint or a USDC/USDT-like token) via `initialize`/`initialize_with_permission`.
2. Perform swaps so that `creator_fees_token_0` accumulates a nonzero balance in `pool_state` (tracked in `programs/cp-swap/src/states/pool.rs`).
3. Have the mint's freeze authority freeze the `pool_creator`'s associated token account for that mint (standard `FreezeAccount` instruction — no protocol code interaction needed).
4. Call `collect_creator_fee_permissionless` (or `collect_creator_fee`); the `transfer_checked` CPI in `programs/cp-swap/src/utils/token.rs` reverts because the destination account is frozen.
5. Every subsequent call reverts identically; `creator_fees_token_0` can never be reset to zero, permanently locking that amount inside `token_0_vault`, excluded from LP withdrawal math via `vault_amount_without_fee`.

pub fn transfer_from_user_to_pool_vault<'a>(
    authority: AccountInfo<'a>,
    from: AccountInfo<'a>,
    to_vault: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new(
            *token_program.key,
            token_2022::TransferChecked {
                from,
                to: to_vault,
                authority,
                mint,
            },
        ),
        amount,
        mint_decimals,
    )
}

    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }
