### Title
Cross-repository forged commit status triggers victim stack's `Hook.emit` webhooks - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by `sha` alone (`Commit.where(sha: params.sha)`), unlike every other handler which scopes lookups to the webhook's own `repository.full_name` via the shared `Handler#stacks` helper. Any commit sha that happens to exist in more than one Shipit-tracked stack (e.g., a fork sharing history with the upstream repository) lets an attacker who legitimately controls a webhook for one repository forge a status event that gets applied to a completely different, victim stack's `Commit`, firing `Hook.emit(:commit_status, ...)` / `Hook.emit(:deployable_status, ...)` for that victim stack.

### Finding Description
The broken binding: the code must ensure `commit.stack.repository == payload['repository']['full_name']` (the repository that authenticated/signed the webhook) before calling `commit.create_status_from_github!` and thus before `Commit#add_status` calls `Hook.emit(:commit_status, stack, ...)` / `Hook.emit(:deployable_status, stack, ...)` [1](#0-0) .

`StatusHandler#process` does not enforce this at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

Compare this to `PushHandler`, which restricts to `stacks.not_archived.where(branch:)`, where `stacks` is derived from `Repository.from_github_repo_name(repository_name)` — i.e., the repository named in the *authenticated* payload [3](#0-2) [4](#0-3) , and to `CheckSuiteHandler`, which explicitly does `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }` [5](#0-4) . `StatusHandler` is the only handler that skips the `stacks`/repository scoping entirely.

`WebhooksController#verify_signature` only validates that the raw POST body was HMAC-signed with the `webhook_secret` configured for `repository_owner` (derived from the payload's own `repository.owner.login`) [6](#0-5) . It does not verify any relationship between the payload's `sha` and the payload's `repository` — GitHub itself normally guarantees that binding for real events, but nothing in this codebase re-derives or checks it once the handler runs.

The `commits` table is indexed on `(stack_id, sha)`, not uniquely on `sha` alone [7](#0-6) , confirming that the same `sha` legitimately existing under multiple distinct `stack_id`s (e.g., forks, mirrors, repos with shared history) is an expected, supported condition — not a theoretical edge case.

**Attacker's exact path**: The attacker owns or administers a GitHub repository that (a) shares a commit sha with a repository tracked by a victim's Shipit stack (e.g., a public fork of the victim's open-source repo — forked commits retain identical SHAs), and (b) is itself configured as a Shipit stack (or belongs to an org with no `webhook_secret` configured, in which case `verify_webhook_signature` returns `true` unconditionally) [8](#0-7) . The attacker sends (or has their own CI trigger) a real, validly-signed `status` webhook for their own repository referencing the shared sha with an arbitrary `state`/`context`/`description`. `StatusHandler` ignores the payload's `repository` entirely and applies the status to every `Commit` row across all stacks matching that sha, including the victim's, which then fires `Hook.emit(:commit_status, victim_stack, ...)` and potentially `Hook.emit(:deployable_status, victim_stack, ...)` [9](#0-8) , delivering payloads to any `Hook` rows (Slack, deploy dashboards) configured on the victim stack.

### Impact Explanation
An attacker who controls one Shipit-tracked repository (or any repository under a Shipit-configured org lacking a `webhook_secret`) can cause arbitrary, attacker-chosen commit-status state transitions (`success`/`failure`/`error`/`pending`) to be recorded against a victim stack's commit and broadcast through that victim stack's configured `Hook`s to external systems (Slack, deploy dashboards) that trust these notifications, and can also flip `stack.schedule_merges` behavior for the victim (since `add_status` schedules merges on `pending`/`success` transitions) [10](#0-9) . This is a payload from one repository mutating another repository's stack/commit state and firing outbound notifications on its behalf — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Preconditions: the victim stack must have a `Commit` with a sha that also exists in a repository the attacker controls or influences (realistic for forks, mirrored/replicated repos, or monorepo splits with shared history), and the attacker's repository/org must produce a validly-signed webhook (either because they legitimately own that repo's Shipit-configured webhook, or the org has no `webhook_secret` set). This does not require any Shipit session, API token, or privileged GitHub role — only ownership of a repository that shares commit history with a tracked victim repo, which is a common, low-cost setup (e.g., forking a public repository). The attack is repeatable per shared sha and against any stack sharing that sha.

### Recommendation
Scope `StatusHandler#process` to the authenticated payload's repository, mirroring `CheckSuiteHandler`/`PushHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures `commit.stack.repository == payload['repository']['full_name']` holds before any `Hook.emit` call.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or controller-level):
1. Create two stacks, `victim_stack` (repository `victim/repo`) and `attacker_stack` (repository `attacker/repo`), each with a `Commit` sharing the same `sha` (e.g., `"deadbeef"`), and give `victim_stack` a `Hook` for `commit_status`.
2. Post a `status` webhook (`X-Github-Event: status`) whose JSON body's `repository.full_name` is `attacker/repo` and `sha` is `"deadbeef"`, signed with `attacker/repo`'s org secret (or unsigned if that org has none configured).
3. Assert: `victim_stack.commits.find_by(sha: "deadbeef").statuses.count` increased, and `Pubsubstub`/`Hook` delivery (`expect_hook_emit(victim_commit, :commit_status, ...)`) fired for `victim_stack`, even though the request never authenticated as `victim/repo`.
4. Before-fix: assertions pass (vulnerability confirmed). After applying the recommended `stacks`-scoping fix: assert no status is created on `victim_stack`'s commit and no `Hook.emit` fires for `victim_stack`.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
