### Title
Unvalidated swap routes can redirect execution through malicious pool contracts and steal unrelated caller tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy entrypoints accept caller-supplied `swap` bytes and pass them to the configured swap router without validating the route's destination contracts. Because route payloads can name arbitrary pool addresses, a malicious route can place attacker-controlled code below the caller-authorized strategy call. That code can request additional token transfers from the caller; transaction simulation then includes those transfers in the caller's authorization tree, and enforcing mode executes them if the poisoned tree is signed.

### Finding Description
`swap_collateral` accepts a caller-provided `StrategySwap` and forwards it into `withdraw_and_swap_from_supply` after only account authorization and market checks. [1](#0-0)  The shared router boundary treats `swap` as opaque route data, authorizes only the expected input-token transfer to the configured router, invokes `execute_strategy`, and validates only the controller's resulting balance deltas. [2](#0-1)  These checks bound the routed input and require positive output, but they do not restrict which pool or token contracts the route causes the router to invoke. The same pattern is reachable through `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`, each of which exposes caller-controlled swap bytes. [3](#0-2) 

This is analogous to the Better Auth issue: attacker-controlled input selects the eventual callback destination, while the protocol validates the primary operation but not the destination reached during that operation.

### Impact Explanation
A malicious route can invoke an attacker-controlled pool contract during a victim's otherwise valid strategy call. That contract can initiate a token transfer from the victim to the attacker. Soroban records this transfer as a child of the victim's strategy authorization; if the victim signs the simulated authorization tree without detecting the extra child, the transfer succeeds. The attacker can therefore steal wallet assets unrelated to the lending position, not merely the collateral supplied to the strategy.

### Likelihood Explanation
Exploitation requires a victim to submit an attacker-supplied or tampered route and sign the resulting authorization tree. The victim must be an account owner or delegate, and the strategy must otherwise produce positive measured output and pass the account's final risk checks. Those requirements reduce likelihood, but route data is opaque bytes and the poisoned child authorization can be difficult for a wallet or user to recognize. The resulting loss can exceed the routed amount, supporting Medium severity.

### Recommendation
Do not allow route payloads to select arbitrary executable contracts for calls made under a lending user's authorization tree. At the controller boundary, require routes to come from a protocol-approved route representation that binds every venue/pool address to an allowlist, or configure the router with a governance-managed pool allowlist and reject unlisted destinations. Wallets and integrators should additionally decode the full route and reject authorization trees containing unexpected child token transfers.

### Proof of Concept
1. Alice owns a debt-free lending account holding supplied USDC and also holds an unrelated wallet token.
2. An attacker deploys a contract exposing the pool interface expected by the route and embeds its address in a `swap_collateral` payload.
3. Alice calls:
   ```rust
   Controller::swap_collateral(
       env,
       alice,
       account_id,
       usdc_hub_asset,
       collateral_amount,
       eth_hub_asset,
       malicious_swap_bytes,
   )
   ```
   `swap_collateral` authorizes Alice and passes the opaque route to the swap layer. [4](#0-3) 
4. The controller authorizes only its exact input-token transfer to the configured router, then invokes `execute_strategy`; it does not inspect the pool addresses encoded inside `malicious_swap_bytes`. [5](#0-4) 
5. During route execution, the attacker-controlled pool calls:
   ```rust
   token::Client::new(&env, &unrelated_wallet_token)
       .transfer(&alice, &attacker, &alice_wallet_balance);
   ```
6. Simulation records the malicious transfer beneath Alice's `swap_collateral` authorization. If Alice signs that simulated tree, the unrelated wallet token moves to the attacker while the strategy can still return positive output and pass the controller's post-swap accounting checks. [6](#0-5)

pub(crate) fn process_swap_collateral(
    env: &Env,
    caller: &Address,
    params: SwapCollateralParams<'_>,
) {
    let SwapCollateralParams {
        account_id,
        current,
        from_amount,
        new,
        swap,
    } = params;

    require_authorized_caller(env, caller);

    assert_with_error!(env, current != new, GenericError::AssetsAreTheSame);
    config::require_hub_active(env, current.hub_id);
    require_positive_amount(env, from_amount);

    let mut account = storage::get_account(env, account_id);
    account::require_owner_or_delegate(env, account_id, caller, &account.owner);
    let mut cache = Context::new(env);
    // Check the destination before withdrawing existing collateral.
    require_can_supply(env, &mut cache, account.spoke_id, new);

    let extra_assets = vec![env, current.asset.clone(), new.asset.clone()];
    prefetch_strategy_prices(&mut cache, &account, &extra_assets);

    let swapped_amount = withdraw_and_swap_from_supply(
        env,
        &mut account,
        &mut cache,
        caller,
        current,
        from_amount,
        &new.asset,
        swap,
        events::PositionAction::SwColWd,
    );
