### Title
Duplicate entries in `r of set` / `weighted and` threshold sets let a single signer satisfy a multi-signer threshold - ([File: definition.js])

### Summary
The Obyte address-definition threshold operators `r of set` and `weighted and` count how many array elements ("set" members) are satisfied without ever checking that the members are distinct. A shared/multi-sig address whose definition places the *same* signing key (directly, or via a duplicated `['address', X]`/`['sig', {pubkey}]` leaf) at two or more positions of the `set` array can have its threshold satisfied by one private key producing valid authentifiers at each duplicated path, even though the address was intended to require signatures from several independent co-signers. This mirrors the reported Convergence bug, where an unchecked, attacker-controlled array of repeated identifiers was summed to inflate a value (voting power) that gates an authorization decision — here the "count" of independent signers gating spending authority.

### Finding Description
`Definition.validateDefinition()` implements `r of set` and `weighted and` purely as counters over `args.set`: [1](#0-0) 

and [2](#0-1) 

Neither branch verifies that the elements of `args.set` are semantically distinct (different addresses/pubkeys/definitions). The only structural checks are `args.set.length >= 2` and `args.required <= args.set.length` (or `<= total_weight`).

At authentication time, `validateAuthentifiers()` mirrors this counting logic: [3](#0-2) [4](#0-3) 

Each `set` element is evaluated independently at its own authentifier `path` (`path+'.'+index`), and `count`/`weight` is incremented whenever that specific leaf validates. Because signature/definition verification for a leaf depends only on the pubkey/address and the (path-independent) `unit_hash_to_sign`, an author who controls exactly one private key `A` can:
1. Craft (or, as one of several co-signers of a shared address created via `wallet_defined_by_addresses.js`, get accepted) a definition such as `['r of set', {required: 2, set: [['sig',{pubkey:A}], ['sig',{pubkey:A}], ['sig',{pubkey:B}]]}]`, and
2. Supply the *same* valid signature by key `A` under two different authentifier paths (`r.0` and `r.1`).

Both leaves independently validate (there is no cross-path uniqueness or distinct-signer check anywhere in `evaluate()`), so `count >= required` is satisfied using only one real keyholder — defeating the intended "2 independent signers" guarantee that the other co-signers of the shared address believed they were agreeing to. `wallet_defined_by_addresses.handleNewSharedAddress()` also performs no duplicate-member check on the definition it accepts: [5](#0-4) 

it only checks that every `signing_path` in the definition has a matching `signers` entry and vice versa, not that the underlying addresses/pubkeys referenced by different paths are distinct.

This is directly analogous to the reported bug class: an array supplied/controlled by an interested party (`OwnedAndDelegated.owneds`/`set`) is summed/counted (`_totalVotingPower` / `count_options_with_sig`) with no de-duplication, and that sum gates a security decision (voting power / spending authorization).

### Impact Explanation
Any shared/multi-signature Obyte address (used for escrow contracts, arbiter contracts, DAO/committee wallets, etc.) whose definition uses `r of set` or `weighted and` can be rendered spendable by fewer independent keyholders than the nominal `required`/threshold value implies, as long as one signing key appears at more than one leaf of the `set`. This constitutes unauthorized spending relative to the security guarantee the definition purports to provide (e.g., an "M-of-N" wallet is effectively "M-1-of-N" or even "1-of-N" if the colluding/duplicated key appears `required` times), since the protocol itself performs no distinct-signer or distinct-member enforcement.

### Likelihood Explanation
Exploitation requires that a malicious participant get a definition containing duplicated key/address leaves accepted as the shared address definition (e.g., during shared-address setup in `wallet_defined_by_addresses.js`, or by any single author defining their own address and later being trusted as a "committee" member in a system that assumes distinct M-of-N signers). Because the duplication can be masked behind nested `address`/`definition template` indirection, and because neither `validateDefinition` nor `handleNewSharedAddress` flags repeated members, a careless review of the JSON definition (which is what other co-signers typically check) will not obviously reveal the weakness, especially for larger sets or nested definitions.

### Recommendation
In `Definition.js`, for `r of set` and `weighted and` (and by extension `and`/`or` if used for authorization-strength arguments), require that all elements of `args`/`args.set` are structurally/semantically distinct — e.g., reject the definition if two `set` entries serialize to the same `['sig', {pubkey}]`, `['address', X]`, or otherwise resolve (after fully dereferencing nested `address`/`definition template` indirection) to the same terminal signing key. Additionally, `wallet_defined_by_addresses.handleNewSharedAddress()` should validate that no two `signing_path`s resolve to the same underlying address/pubkey unless explicitly intended and clearly surfaced to all co-signers.

### Proof of Concept
1. Party `A` (holding key `Ka`) and party `B` (holding key `Kb`) agree to create a shared 2-of-2-looking address using `wallet_defined_by_addresses.js`, with definition:
   `['r of set', {required: 2, set: [['sig',{pubkey:Ka}], ['sig',{pubkey:Ka}], ['sig',{pubkey:Kb}]]}]`
   (or the duplicate is hidden behind a `definition template`/nested `address` reference to `A`'s address).
2. `handleNewSharedAddress()` accepts it because it only checks that every `signing_path` has a corresponding `signers` entry, not that distinct paths map to distinct keys — [6](#0-5) .
3. When spending, party `A` produces one valid signature for the unit hash and supplies it as the authentifier for both `r.0` and `r.1` paths.
4. In `Definition.validateAuthentifiers`, the `r of set` evaluator at [3](#0-2)  independently validates both leaves as `true` (same key, same message, both verify), yielding `count = 2 >= required (2)`, so the unit is accepted as validly authorized — despite `B` never having signed.
