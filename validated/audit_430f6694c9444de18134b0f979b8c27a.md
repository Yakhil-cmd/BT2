### Title
Cross-Repository / Cross-Stack Read via `Api::CCMenuController` — Stack Reachable Through The API Token's Query-String Authentication Path Is Not Bound To The Token's `stack_id` Scope

### Summary
`Shipit::Api::BaseController` scopes an `ApiClient` to a single `Stack` when `stack_id` is set on the token: the intended binding is *"the stack a token authorises == the stack it touches"*. Every other API controller resolves the target stack through the scoped `stacks` relation (`stacks.from_param!`), but `Api::CCMenuController#stack` bypasses this scope and resolves the target directly via `Stack.from_param!(params[:stack_id])`, using only the `read:stack` permission string check (which is scope-agnostic). This lets any holder of a stack-scoped API token (e.g., a CCMenu token auto-created and exposed by `CCMenuUrlController`) read the CI/build status of *any* stack in the installation, not just the one it was authorized for.

### Finding Description
`ApiClient` can be created scoped to one stack (`belongs_to :stack, optional: true`), and `Api::BaseController#stacks` is the mechanism meant to enforce that scope: [1](#0-0) 

Controllers that respect the binding compute their target stack through this scoped relation, e.g. `Api::StacksController`: [2](#0-1) 

`Api::CCMenuController`, however, resolves the stack directly from the global `Stack` model, ignoring the `stacks` scope entirely: [3](#0-2) 

Its authorization is only `require_permission :read, :stack`, which is implemented as a scope-agnostic string check in `ApiClient#check_permissions!`: [4](#0-3) 

`check_permissions!` only verifies that `"read:stack"` is present in the client's `permissions` array — it has no knowledge of which `stack_id` the params reference versus which `stack_id` the token is bound to. Because `CCMenuController#stack` doesn't route through `stacks.from_param!`, the `current_api_client.stack_id?` restriction from `BaseController#stacks` (line 75) is never applied on this endpoint, so a stack-scoped `read:stack` token can view the CI status page (`show` action, which renders build history, last status, last build label, lock state, etc.) for any stack in the deployment, not only the one it was created for.

This class of token is not a privileged/administrative artifact: `CCMenuUrlController#fetch` mints a stack-scoped, `read:stack`-only `ApiClient` on demand for any authenticated Shipit user requesting a CCMenu URL for a stack they can see, and returns the token to the browser: [5](#0-4) 

A user who legitimately holds this "CCMenu Client" token for stack A can present it to `Api::CCMenuController#show` with a different `stack_id` (stack B) and, because `CCMenuController#stack` never checks `current_api_client.stack_id`, receive stack B's data anyway.

### Impact Explanation
This breaks the binding "a stack a token authorises == a stack it touches," which is explicitly listed as a qualifying analog. It results in unauthorized cross-stack read of deployment/build state (last build status, last build label, lock reason, activity) for stacks the token holder was never granted access to — matching the "unauthenticated/unauthorized read of stack state" High-impact criterion, since the exposed CCMenu token effectively becomes a master key to read every stack's CI status rather than the one stack it was scoped to.

### Likelihood Explanation
Likelihood is significant: CCMenu tokens are created and handed to end users automatically (`CCMenuUrlController#fetch`) any time a stack's CCMenu URL is requested, and the endpoint (`Api::CCMenuController#show`) accepts the token purely via query string per `CCMenuController#authenticate_api_client`. Any legitimate stack-scoped token holder — who need not be an administrator — can simply substitute a different `stack_id` in the URL to enumerate other stacks' status, requiring no additional privilege beyond having obtained one CCMenu URL.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped relation exactly as `Api::StacksController` does:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures `current_api_client.stack_id?` scoping from `BaseController#stacks` is enforced consistently across all API controllers, closing the gap where a scope-bound token can act on stacks outside its authorized scope.

### Proof of Concept
1. As an authenticated Shipit user with access to Stack A, visit `GET /A/ccmenu_url` (`CCMenuUrlController#fetch`); this auto-creates (or reuses) an `ApiClient` named "CCMenu Client" scoped to Stack A with `permissions: ['read:stack']`, and returns its `authentication_token`. [6](#0-5) 
2. Take that token and call the API endpoint directly for Stack B (any other stack in the installation), e.g.:
   `GET /api/B/ccmenu.xml?token=<token-scoped-to-A>`
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` instead of `stacks.from_param!(params[:stack_id])`, the `current_api_client.stack_id?` scope check in `BaseController#stacks` (which would have restricted results to Stack A only) is never invoked, and `check_permissions!` only validates the generic `read:stack` string — so the request succeeds and returns Stack B's build/CI status, despite the token only being authorized for Stack A. [7](#0-6)
