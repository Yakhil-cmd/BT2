### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit purely by `sha` string equality with no repository/stack ownership check, while the webhook signature is verified only against the organization named in the attacker-controlled payload itself. An attacker who owns a low-privilege GitHub organization with its own Shipit `webhook_secret` can sign a `status` event for their own org, but set `sha` to any known/leaked commit sha belonging to an unrelated stack/repository, causing `create_status_from_github!` to write attacker-controlled state onto that foreign commit.

### Finding Description
The broken binding is: verifying-organization (`repository_owner`, derived from the payload's own `repository.owner.login`/`organization.login` fields) MUST equal the organization that owns the stack/repository containing the commit being mutated. In `WebhooksController#verify_signature`, the organization used to look up the `github_app`/`webhook_secret` is read directly from the same JSON body the attacker controls: `repository_owner` reads `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , and `verify_signature` fetches `Shipit.github(organization: repository_owner)` and checks the HMAC against that org's own secret [2](#0-1) . So an attacker who owns `attacker-org` and knows its `webhook_secret` can produce a valid signature for a payload where `repository.owner.login = 'attacker-org'`.

That verified payload is then dispatched to `StatusHandler#process`, which does:
```
Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
``` [3](#0-2) 
This query is not scoped to any repository, stack, or organization — it matches every `Commit` row across the whole table whose `sha` column equals the attacker-supplied string, regardless of which stack/repo/org it belongs to. The `Commit` schema only indexes `stack_id` + `sha` for lookup performance [4](#0-3) ; it is not used to filter this handler's query.

For comparison, `PushHandler#process` scopes its lookup through `stacks.not_archived.where(branch:)` before acting [5](#0-4) , implying the base `Handler` class provides a repository-scoped `stacks` relation for handlers to use — `StatusHandler` simply never uses it, querying `Commit` globally instead.

Once matched, `create_status_from_github!` calls `add_status`, which creates a `CommitStatus`, recomputes `status`, and — critically — can call `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` if the new status becomes `pending` or `success` [6](#0-5) . This can flip a foreign, unrelated stack's commit deployability and trigger its merge queue, entirely without that stack's or organization's authorization.

Exploit flow:
1. Attacker controls `attacker-org` and its Shipit `webhook_secret` (a legitimate precondition — self-hosted Shipit supports multiple configured GitHub orgs/apps, and the attacker is only assumed to own one, unprivileged, org).
2. Attacker learns/guesses a commit sha belonging to `victim-org/repo`'s stack (e.g. from a public PR or CI log).
3. Attacker crafts JSON: `{"repository":{"owner":{"login":"attacker-org"}}, "sha":"<victim sha>", "state":"success", ...}`, signs it with `attacker-org`'s `webhook_secret`, and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` succeeds (verifying only that the attacker knows attacker-org's own secret).
5. `StatusHandler#process` matches the victim's `Commit` row purely by `sha` and writes the attacker-supplied status onto it, potentially unblocking the victim stack's merge/deploy pipeline.

No existing guard prevents this: `verify_signature` only authenticates "the caller knows secret for the org named in their own payload," not "the org owns the commit being mutated"; the `ExplicitParameters` schema for `StatusHandler` only validates types (`sha`, `state`, etc.), not ownership [7](#0-6) ; and `StatusHandler#process` performs no repository/stack filtering at all.

### Impact Explanation
This is a cross-tenant integrity violation: a payload authenticated for `attacker-org` mutates a `Commit`/`CommitStatus` belonging to an unrelated `victim-org` stack, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attacker can set arbitrary `state` (e.g. `success`), `description`, and `target_url` on the victim's commit, and because `add_status` triggers `stack.schedule_merges` on state transitions to `pending`/`success`, this can unblock or corrupt the victim's merge queue/deploy pipeline without any authorization from `victim-org`. The attack is repeatable against any stack/commit whose sha the attacker can learn, and scales across all Shipit organizations sharing this single-tenant instance's `Commit` table.

### Likelihood Explanation
Preconditions are modest for a multi-tenant Shipit deployment: the attacker must control at least one organization configured in `Shipit.github_teams`/config with its own `webhook_secret` (a normal, low-privilege customer of a shared Shipit instance), and must know a target commit sha (commit shas are frequently public — visible in PRs, CI logs, GitHub UI). No GitHub App private key, session, or API token is required. The attack is a single crafted HTTP POST, fully repeatable and scriptable against arbitrary target shas.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving records solely by GitHub-supplied identifiers) to the repository/organization that was authenticated in `verify_signature`. Use the base `Handler`'s repository-scoped `stacks` relation (as `PushHandler` does) to constrain `Commit.where(sha: params.sha)` to commits belonging to stacks whose repository matches `params.dig('repository','full_name')`/`repository_owner`, e.g. `stacks.joins(:commits).where(commits: { sha: params.sha })`, rather than querying `Commit` unscoped.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "status webhook signed for one org cannot mutate a commit belonging to another org's stack" do
  attacker_stack = shipit_stacks(:shipit) # stack under org "shopify" (attacker-controlled webhook_secret)
  victim_stack = Shipit::Stack.create!(repository: shipit_repositories(:other_org_repo)) # org "victim-org"
  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim commit")

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'owner' => { 'login' => 'shopify' }, 'full_name' => 'shopify/attacker-repo' }
  }.to_json

  # Signature verified only for "shopify" (attacker-owned org), using its own secret.
  Shipit.github(organization: 'shopify').stubs(:verify_webhook_signature).returns(true)

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body:, as: :json
  end
  # If the bug exists, victim_commit.statuses.count increases even though
  # the request was authenticated only for "shopify", not "victim-org".
end
```
The assertion `assert_no_difference` on `victim_commit.statuses.count` should fail against current code (proving the vulnerability): `Commit.where(sha: shared_sha)` matches `victim_commit` regardless of the authenticated organization, and `create_status_from_github!` writes a new status to it.
