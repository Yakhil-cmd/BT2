## Finding

### Title
API token scoped to one stack can read any stack's CI status via CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` restricted to a single stack (`current_api_client.stack_id?`) can only resolve stacks scoped to that ID via the `stacks`/`stack` helpers. `Shipit::Api::CCMenuController` overrides `#stack` and looks the stack up directly via `Stack.from_param!(params[:stack_id])`, bypassing the scoping entirely, so any valid but stack-scoped token can read the CCMenu status of an arbitrary stack.

### Finding Description
`BaseController` implements the trust binding "a stack a token authorizes == a stack it may touch": [1](#0-0) 

`stacks` restricts the visible collection to `Stack.where(id: current_api_client.stack_id)` when the `ApiClient` is scoped to a specific stack, and `stack` resolves `params[:stack_id]` only within that restricted collection.

`CCMenuController`, however, overrides `#stack` to bypass this scoping and resolve `params[:stack_id]` against the entire `Stack` table: [2](#0-1) 

The `require_permission :read, :stack` guard only checks that the token has the generic `read:stack` permission string via `ApiClient#check_permissions!`: [3](#0-2) 

`check_permissions!` never inspects `current_api_client.stack_id`, so it cannot detect that the requested `params[:stack_id]` differs from the stack the token was scoped to. The equality that should hold — `token.stack_id == params[:stack_id]` when the token is stack-scoped — is broken specifically in `CCMenuController#stack`, while the sibling code path in `BaseController#stack` (used by `StacksController`, `DeploysController`, etc.) enforces it correctly.

### Impact Explanation
An `ApiClient` deliberately scoped to a single stack (e.g., created via `CCMenuUrlController#client`, which mints a `read:stack`-only, stack-scoped token — see [4](#0-3) ) is meant to only ever see that one stack's status. Because of the bypass, the holder of that token — an "unprivileged" actor with respect to every other stack — can pass any other `stack_id` and read that stack's latest deploy/rollback status (build state, last build label, deploy timing) via the CCMenu XML endpoint, an unauthorized read of stack state across stack boundaries.

### Likelihood Explanation
The bug is trivially reachable by anyone who legitimately holds one CCMenu (or any other stack-scoped, `read:stack`-permissioned) API token — no additional privilege, secret, or session is required beyond the token itself; the attacker merely swaps the `stack_id` route/query parameter.

### Recommendation
Have `CCMenuController#stack` reuse the scoped `stacks` collection from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so stack-scoped tokens cannot resolve stacks outside their authorized `stack_id`.

### Proof of Concept
1. Stack A creates a CCMenu URL, minting an `ApiClient` with `permissions: ['read:stack']` and `stack_id: A.id` (`CCMenuUrlController#client`).
2. Using that token, request `GET /api/stacks/:stack_id_B/ccmenu.xml` with `token=<A's token>` and `stack_id` pointing at unrelated Stack B.
3. `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` (Stack B) regardless of the token's `stack_id` restriction, and `check_permissions!(:read, :stack)` passes because the token does have `read:stack`.
4. The response renders Stack B's latest deploy/build status, even though the token was only ever authorized for Stack A.
