### Title
`ReopenedHandler#unarchive?` unguarded operator precedence allows re-provisioning review stacks with `review_stacks_enabled == false` - (File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb)

### Summary
`ReopenedHandler#unarchive?` uses the same un-parenthesized `&&`/`||` expression as `OpenedHandler#provision?`. Because Ruby binds `&&` tighter than `||`, the `provisioning_behavior_allow_with_label?` and `provisioning_behavior_prevent_with_label?` disjuncts are evaluated independently of `repository.review_stacks_enabled`, so a repository with review stacks disabled can still have a stack created/unarchived and enqueued for provisioning.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == true` must gate every path that leads to `unarchive!`'s provisioning behavior. In the actual code: [1](#0-0) 

Ruby operator precedence makes this equivalent to:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So when `review_stacks_enabled == false` and `provisioning_behavior == "prevent_with_label"` and the PR carries no provisioning label, the third disjunct alone makes `unarchive?` return `true`, bypassing the `review_stacks_enabled` gate entirely. This mirrors the identical, already-acknowledged bug shape in `OpenedHandler#provision?`: [2](#0-1) 

`respond_to_pull_request_reopened?` gates only on `params.action == "reopened"` plus this broken `unarchive?`: [3](#0-2) [4](#0-3) 

When true, `process` calls `stack.unarchive!` on a `ReviewStackAdapter`. If no `ReviewStack` yet exists for `environment: "pr#{params.number}"` (the normal case for a repo where review stacks are supposedly disabled), `unarchive!` falls into `create!`, which builds a real `ReviewStack` record, attaches the `pull_request`, and immediately enqueues it for provisioning via `ReviewStackProvisioningQueue.add`: [5](#0-4) [6](#0-5) 

The provisioning queue subsequently calls `stack.provisioner.up` when `provision?` (which is unrelated to `review_stacks_enabled`) is satisfied: [7](#0-6) [8](#0-7) 

`NullRepository`/`Repository` expose the four independent config predicates used here, and nothing else re-checks `review_stacks_enabled` downstream in this path: [9](#0-8) 

**Attacker request:** An unprivileged PR author closes and reopens their own pull request (a `pull_request` webhook with `action: "reopened"`) against a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: "prevent_with_label"`, ensuring the PR carries no labels matching `provisioning_label_name`. No forged signature or privileged token is needed beyond the normal ability to open/close/reopen a PR (which triggers GitHub's own legitimately-signed webhook).

**Why existing guards don't help:** `verify_signature`/webhook signature checks validate the webhook is genuinely from GitHub for that repo — they don't validate the *content* of the boolean logic. `ExplicitParameters` only validates the payload's structural shape, not the intended `review_stacks_enabled` gate. Nothing else in `ReopenedHandler` re-checks `review_stacks_enabled` before calling `stack.unarchive!`.

### Impact Explanation
A repository that its owner deliberately configured with review-stack auto-provisioning disabled (`review_stacks_enabled: false`) can still have a `ReviewStack` created and queued for provisioning purely from PR label state, because the `prevent_with_label` disjunct ignores the enablement flag. Once queued, `ReviewStackProvisioningQueue#work` triggers `stack.provisioner.up`, which is the entry point into task/command execution for provisioning the attacker's branch — matching the Critical impact category of "an unauthorized deploy/provisioning of attacker-controlled branch content" for a repository whose owner explicitly opted out of this behavior. This is repeatable by any PR author against any misconfigured repository (same class of repos affected by the twin `OpenedHandler#provision?` bug) and is not scoped to a single tenant — it applies to every repository sharing this specific configuration combination.

### Likelihood Explanation
Requires the target repository to be configured with `review_stacks_enabled: false` and `provisioning_behavior: "prevent_with_label"` — a plausible, valid, non-contradictory configuration state (e.g., an operator disabling auto-provisioning after previously having configured a label-based behavior, or simply an oversight since the two settings are independent enum/boolean fields with no mutual-exclusivity validation in `Repository`). The attacker needs no privileges beyond opening/reopening a PR with no labels, which is achievable by any GitHub user able to interact with the repository's PRs (e.g., a fork PR author). Cost is a single close+reopen action; fully repeatable.

### Recommendation
Parenthesize `unarchive?` (and the identical `provision?` in `OpenedHandler`, and any other handler with this pattern such as `LabeledHandler`/`UnlabeledHandler` if they share it) so `repository.review_stacks_enabled` gates all three disjuncts:
```ruby
def unarchive?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Also add a `Repository` validation or `Stack`-provision entry check that hard-stops provisioning if `review_stacks_enabled` is false as defense in depth.

### Proof of Concept
Under `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb` (existing patterns in that file already use `configure_provisioning_behavior` and `payload_parsed(:pull_request_reopened)`):
```ruby
test "does NOT create/unarchive a stack when review_stacks_enabled is false, even with prevent_with_label and no labels" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::ReviewStack.count } do
    ReopenedHandler.new(payload).process
  end
end
```
Before the fix, this assertion fails: `ReopenedHandler#unarchive?` returns `true` via the third disjunct despite `review_stacks_enabled == false`, `ReviewStackAdapter#unarchive!` calls `create!`, and `Shipit::ReviewStack.count` increases with the stack enqueued via `ReviewStackProvisioningQueue.add`.
