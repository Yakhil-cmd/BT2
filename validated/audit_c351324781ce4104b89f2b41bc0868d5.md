## Title
Operator precedence bug in `ReopenedHandler#unarchive?` bypasses `review_stacks_enabled` gate, allowing unauthorized re-provisioning of disabled review stacks - (File: `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`)

### Summary
`LabeledHandler#respond_to_label_change?` correctly gates `archive?`/`unarchive?` behind `repository.review_stacks_enabled` using a chain of `&&`, so it is not vulnerable. However, `ReopenedHandler#unarchive?` has a Ruby operator-precedence bug: `&&` binds tighter than `||`, so `repository.review_stacks_enabled` only gates the `allow_all` branch of the expression and not the `allow_with_label`/`prevent_with_label` branches, letting an attacker re-trigger `stack.unarchive!` on a repository where review stacks have been disabled.

### Finding Description
The broken binding: the intended invariant is `repository.review_stacks_enabled == true` for every path that can call `ReviewStackAdapter#unarchive!`. In `ReopenedHandler`, that invariant is violated for two of the three provisioning-behavior branches.

`app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb` lines 70-75: [1](#0-0) 

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` has higher precedence than `||` in Ruby, this parses as:

`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is only ANDed into the first disjunct. If the repository's `provisioning_behavior` is `allow_with_label` (or `prevent_with_label`), the second (or third) disjunct can be `true` independent of `review_stacks_enabled`, so `unarchive?` returns `true` even when `review_stacks_enabled` is `false`.

`process` then unconditionally calls `stack.unarchive!` through `ReviewStackAdapter#unarchive!`: [2](#0-1) 

`ReviewStackAdapter#unarchive!` itself performs no `review_stacks_enabled` check — it trusts the caller — and re-enqueues the stack for provisioning: [3](#0-2) 

Exploit flow:
1. Operator initially has review stacks enabled with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) and a `ReviewStack` already exists for an attacker's open PR.
2. Attacker closes their own PR (or it gets closed), archiving the stack via the closed-PR flow.
3. Operator later disables review stacks for the repository (`repository.review_stacks_enabled = false`), intending to stop further provisioning, but the `ReviewStack` row remains.
4. Attacker reopens their own PR (a `pull_request` "reopened" webhook, fully within their control as PR owner) with the provisioning label present (for `allow_with_label`) or absent (for `prevent_with_label`).
5. `ReopenedHandler#unarchive?` evaluates true due to the precedence bug, `stack.unarchive!` runs, and `Shipit::ReviewStackProvisioningQueue.add(stack)` re-enqueues the stack, triggering a fresh deploy of the attacker-controlled branch — despite the operator's explicit intent to disable review-stack provisioning.

Existing guards do not catch this: `respond_to_pull_request_reopened?` only checks `action == "reopened" && unarchive?` — it relies entirely on the buggy `unarchive?` — and `verify_signature`/webhook auth is orthogonal (the webhook itself is legitimately signed since it originates from the attacker's own repository's real GitHub events).

By contrast, `LabeledHandler#respond_to_label_change?` chains all conditions with `&&`, so `repository.review_stacks_enabled` correctly gates it: [4](#0-3) 
`LabelCapturingHandler` never calls `archive!`/`unarchive!` at all, so it is not part of this bypass. [5](#0-4) 

### Impact Explanation
An attacker who owns a PR on a repository with `provisioning_behavior: allow_with_label` or `prevent_with_label` can force re-provisioning/re-deploy of their branch's review stack after the operator has explicitly disabled review stacks (`review_stacks_enabled = false`) for that repository. This is an unauthorized deploy triggered against the operator's configured intent, matching the Critical category "an unauthorized deploy... triggered". The blast radius is scoped to the attacker's own repository/stack (no cross-tenant mutation observed), but it is repeatable indefinitely by closing/reopening the PR as long as the stale `ReviewStack` row exists.

### Likelihood Explanation
Requires: (a) `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (operator configuration, common non-default setting), (b) a pre-existing archived `ReviewStack` for the PR, and (c) the operator subsequently setting `review_stacks_enabled = false` without deleting existing stacks. Given these preconditions, the attacker's cost is trivial — toggle a label and close/reopen their own PR, both ordinary unprivileged GitHub actions — and the exploit is fully repeatable.

### Recommendation
Add explicit parentheses in `ReopenedHandler#unarchive?` so `review_stacks_enabled` gates the entire expression, e.g.:
```ruby
def unarchive?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`, add a test:
1. Create and archive a stack (`create_archived_stack`).
2. Configure `repository.provisioning_behavior = :allow_with_label`, `provisioning_label_name = "pull-requests-label"`, then set `repository.review_stacks_enabled = false; repository.save!`.
3. Build `payload = payload_parsed(:pull_request_reopened)` and add the provisioning label to `payload["pull_request"]["labels"]`.
4. Call `ReopenedHandler.new(payload).process`.
5. Assert both sides of the binding: expected `repository.review_stacks_enabled == false` should imply `stack.reload.archived? == true` (no unarchive). Current buggy behavior: `stack.reload.archived? == false` and the stack is pending provisioning (`assert_pending_provision(stack)`), proving `review_stacks_enabled` was bypassed.
