### Title
Api::CCMenuController#stack bypasses stack-scoped ApiClient authorization, allowing cross-stack read - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` re-implements its own `stack` lookup method that fetches the target `Stack` directly from the request parameter (`Stack.from_param!(params[:stack_id])`) instead of using the scoped `stacks` helper that every other API controller relies on. As a result, an `ApiClient` token that is bound to a single `Stack` (via `ApiClient#stack_id`) and only granted `read:stack` for that stack can be used to read CCMenu build/deploy status for *any* stack in the installation, not just the one the token was authorised for.

### Finding Description
The `Shipit::Api::BaseController` establishes the authorization pattern used across the API: a request is checked for the coarse-grained permission (`read:stack`, `write:stack`, etc.) via `require_permission`, and then the actual set of stacks the client is allowed to touch is restricted by the `stacks` helper: [1](#0-0) 

Every other controller that needs a single stack (e.g. `Shipit::Api::StacksController`) resolves it through this scoped collection: [2](#0-1) 

This is precisely the binding: **the set of stacks a token authorises == the set of stacks its requests can touch**, enforced by `stacks.from_param!`. Tests confirm this scoping is a real security property, e.g. `here_come_the_walrus` is a token bound to a single stack and "will only see that one stack": [3](#0-2) [4](#0-3) 

However, `Shipit::Api::CCMenuController` only requires the coarse `read:stack` permission and overrides `stack` to bypass the scoping entirely, looking the stack up unconditionally from `Stack`: [5](#0-4) 

`ApiClient#check_permissions!` only checks that the permission string (e.g. `read:stack`) is present in the client's `permissions` array — it never compares the requested stack to `ApiClient#stack_id`: [6](#0-5) 

Because `CCMenuController#stack` does not go through `current_api_client.stack_id?` filtering, the binding "stack a token authorises" (its `stack_id` scope) diverges from "stack it touches" (whatever `params[:stack_id]` the caller supplies), matching the class of bug in the external report where the verified/authorised entity (the `receiver`) differs from the entity actually acted upon (`msg.sender`).

### Impact Explanation
Any holder of a valid API token — including a deliberately narrow-scoped, low-trust token created for a single stack/CI integration and granted only `read:stack` — can query `GET /api/stacks/:stack_id/ccmenu.xml` (or the token-query-string variant, since `authenticate_api_client` here also accepts `params[:token]`) for an arbitrary `stack_id` and obtain that stack's build activity, last build status/label/time, and web URL, none of which it was authorised to see. This is an authorization scope escalation: unauthorized read of stack state/deploy output for stacks outside the token's granted scope, which falls under the "unauthenticated/unauthorized read of stack state ... or deploy output" High-impact category — the credential is valid but the boundary it is supposed to be confined to (a single stack) is not enforced for this endpoint.

### Likelihood Explanation
High likelihood if any stack-scoped `ApiClient` exists in a deployment (a supported, documented feature — see `stack: shipit` in `api_clients.yml` fixtures and the dedicated test asserting "an api client scoped to a stack will only see that one stack"). No additional privilege is needed: the caller just needs a token with `read:stack` (or a token created for one repo) and swaps `stack_id` in the URL/param to a different stack's identifier — a straightforward parameter-tampering attack requiring only the credential it already legitimately possesses for its own stack.

### Recommendation
Make `Shipit::Api::CCMenuController#stack` honor the same scoping as the rest of the API by resolving through the `stacks` helper instead of `Stack.from_param!` directly:

```diff
 def stack
-  @stack ||= Stack.from_param!(params[:stack_id])
+  @stack ||= stacks.from_param!(params[:stack_id])
 end
```

This ensures `current_api_client.stack_id?` scoping (already implemented in `BaseController#stacks`) applies uniformly, closing the gap between the stack a token is authorised for and the stack the endpoint actually serves.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to `stack_id: <stack A>` with only the `read:stack` permission (analogous to the `here_come_the_walrus` fixture).
2. Authenticate to the API with that client's token.
3. Issue `GET /api/stacks/<stack B id or param>/ccmenu.xml?token=<token>` (or via Basic Auth), where stack B is a different, unrelated stack the client was never granted access to.
4. Observe the CCMenu XML for stack B is returned successfully (per `CCMenuController#show` → `stack.deploys_and_rollbacks.last`), even though `Api::StacksController#index` for the same client would only list stack A — demonstrating the authorization/action mismatch.

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
```
