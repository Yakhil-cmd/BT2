### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the independent `repository.full_name` field, allowing cross-organization repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook against using the `repository.owner.login` (or `organization.login`) field of the *same* JSON body it is about to verify. Once the signature check passes, every `Webhooks::Handlers::Handler` subclass resolves the actual `Repository`/`Stack` to mutate using a completely different field of that body: `repository.full_name`. Because these two fields are never checked against each other, a payload can be crafted so that the signature validates for one organization while the mutation is performed against a repository belonging to a different, unrelated organization tracked by the same Shipit instance.

### Finding Description
`verify_signature` picks the GitHub App config to check against solely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

The signature check itself, for an organization that has no `webhook_secret` configured (an explicitly *optional* setting per the setup docs), unconditionally passes: [3](#0-2) [4](#0-3) 

Every webhook handler, however, resolves the repository/stack it operates on from an entirely separate field of the same payload: [5](#0-4) 

This pattern repeats across handlers such as `PushHandler` (syncs stacks/commits) and the pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`, `AssignedHandler`), all of which call `Repository.from_github_repo_name(params.repository.full_name)`: [6](#0-5) [7](#0-6) 

The equality that this breaks is: **organization that authenticated the delivery (`repository.owner.login`, used to pick the verifying secret) ≠ repository that is written (`repository.full_name`, used by the handler)**. Nothing in the controller or in `Handler#stacks`/`#repository_name` enforces that the owner of `full_name` matches the org whose secret validated the signature.

Before the attack: only genuine GitHub deliveries for organization X (signed with X's real webhook secret) can affect stacks belonging to repositories under organization X.

After the attacker's crafted request: a delivery whose signature validates for organization A (either because the attacker knows/controls A's `webhook_secret`, since they administer A's own installed GitHub App, or because A has no `webhook_secret` configured at all, in which case verification is skipped entirely) can carry a `repository.full_name` pointing at organization B's tracked repository. The handler then performs real mutations — triggering `GithubSyncJob`, creating/archiving review stacks, updating pull request labels/state, setting commit statuses — against organization B's `Repository`/`Stack` records, which the attacker has no legitimate access to.

### Impact Explanation
This is a cross-repository/cross-organization write: an actor who only controls (or who exploits an org configured without a webhook secret) organization A's webhook channel can inject events that mutate Shipit's tracked state for organization B's repositories — creating/archiving review stacks, forcing commit-status/PR-state changes, and driving `sync_github` against arbitrary commit SHAs for a repository/org they do not administer. This matches the "cross-repository writes" Critical-impact category.

### Likelihood Explanation
Likelihood is high in any multi-tenant Shipit deployment (a supported, documented configuration — see the two-organization fixture `test/dummy/config/secrets_double_github_app.yml` and the "optional" webhook secret note in `docs/setup.md`). If any configured organization lacks a `webhook_secret`, exploitation requires no credentials at all against that org's channel; otherwise it only requires control of one organization's own legitimate webhook secret to affect any other organization tracked by the same Shipit instance.

### Recommendation
Bind the signature-verification target to the same field the handlers use for repository resolution: derive the org used for `Shipit.github(organization:)` from `repository.full_name`'s owner segment (or validate that `repository.owner.login` equals the owner portion of `repository.full_name`) before dispatching to handlers. Additionally, treat organizations with no configured `webhook_secret` as unverifiable rather than auto-passing signature verification.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (webhook secret known to/controlled by the attacker, or unset) and `OrgB` (a real tracked stack, e.g. `OrgB/victim-repo`), as in `test/dummy/config/secrets_double_github_app.yml`.
2. Send `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
signed with `X-Hub-Signature: sha1=<hmac using OrgA's webhook_secret>` (or omitted/incorrect if `OrgA` has no secret configured).
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies (or auto-passes) the signature.
4. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `GithubSyncJob`/mutations against `OrgB`'s stack, per `app/models/shipit/webhooks/handlers/handler.rb` lines 32-38 and `push_handler.rb` lines 12-17, despite the request never being authenticated for `OrgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
