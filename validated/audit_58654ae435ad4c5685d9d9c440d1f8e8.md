### Title
Webhook signature authenticates the wrong GitHub organization/secret while handlers act on payload-supplied repository and commit-sha fields — forged CI status can mark commits deployable - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to HMAC-verify the request against by reading `repository.owner.login` (or `organization.login`) out of the **same untrusted JSON body** it is about to validate, then trusts the entire payload once that org's secret matches. [1](#0-0) [2](#0-1) 

Downstream handlers never re-check that this authenticated organization actually owns the resource they act on. `Webhooks::Handlers::Handler#stacks` resolves the target purely from `repository.full_name`, a distinct field inside the same signed body, with no linkage back to the authenticated org. [3](#0-2) 

Worse, `StatusHandler` doesn't even use the repository field: it resolves target `Commit` rows globally by `sha` alone, across every stack/repo/org configured in the entire Shipit instance. [4](#0-3) 

### Finding Description
Shipit supports hosting multiple GitHub organizations behind one instance, each with its own `webhook_secret` (`docs/setup.md` "Using Multiple Github Applications"). [5](#0-4) 

`Shipit.github(organization:)` picks the config/secret keyed by the org name and `GitHubApp#verify_webhook_signature` performs a straightforward HMAC compare of the raw body against that org's secret. [6](#0-5) [7](#0-6) 

The binding that should hold is: *organization whose secret validated the signature* == *organization/repository the event is permitted to act upon*. Here, both sides of that equation are read from the identical attacker-controlled JSON body, so an attacker who legitimately controls a GitHub App/webhook for **their own** onboarded organization (Org A) can freely choose `repository.owner.login = "OrgA"` (so the signature check passes with the secret they know) while setting `repository.full_name` to an arbitrary victim repository, or, for `status` events, simply target any `sha` in the database regardless of repository:

- Before the "fix" the report analogizes to: DODO validated only that a swap succeeded, never that the swap's output token equalled the token actually withdrawn.
- Here: Shipit validates only that *some* configured org's secret produced a valid signature, never that the org used for verification equals the repository/commit the handler subsequently mutates.

The most concretely reachable handler is `StatusHandler`, which takes attacker-supplied `state`, `context`, `description`, `target_url` for `params.sha` and calls `commit.create_status_from_github!(params)` on every `Commit` row in the database matching that sha — with **zero repository scoping**. [8](#0-7) 

That status feeds directly into `Commit#deployable?`, which becomes true once the aggregate `Status::Group` reflects `success?` (and no blocking status), and can also trigger `schedule_continuous_delivery`, enqueuing `ContinuousDeliveryJob` for the stack if continuous deployment is enabled. [9](#0-8) [10](#0-9) [11](#0-10) 

So a webhook whose signature is only proven valid for Org A's registered secret can inject a fabricated "success" CI status for a commit belonging to a stack owned by Org B (or any org in the instance), directly satisfying the deploy-safety gate (`success? && !blocked?`) and enabling an unauthorized/auto-triggered deploy on a repository the attacker never proved ownership of.

### Impact Explanation
This breaks the required equality: *organization that authenticated (via `webhook_secret` match keyed off `repository.owner.login`) ≠ repository/commit that is actually written to (looked up via `repository.full_name` or bare `sha`)*. The consequence is that an entity with only legitimate control of one onboarded GitHub organization's webhook secret can forge CI status data (and, via `PushHandler`/`CheckSuiteHandler`, sync/refresh triggers) affecting stacks belonging to a different organization/repository hosted on the same Shipit instance, satisfying the "unauthorized deploy" impact bar because it can flip `Commit#deployable?` to true and feed `schedule_continuous_delivery`.

### Likelihood Explanation
Requires the attacker to already have legitimate ownership/admin of at least one GitHub organization/app that is configured in this Shipit instance's multi-org `secrets.github` map (i.e., they know that org's real `webhook_secret`), which they use to forge a payload naming a different, victim repository's `full_name`/commit `sha`. No Shipit session, API client token, or webhook_secret of the *victim* org is needed — only knowledge of a webhook secret belonging to any onboarded org, satisfying the "unprivileged with respect to the target repo" bar. This is a plausible configuration for shared/hosted Shipit instances serving multiple organizations, as documented in `docs/setup.md`.

### Recommendation
In `WebhooksController#verify_signature` / the handler base class, after signature verification succeeds, enforce that the organization whose secret validated the signature actually owns `repository.full_name` (and reject `status`/`check_suite` events whose resolved `Commit`/`Stack` records belong to a `Repository` outside that organization). `StatusHandler` in particular must scope its `Commit.where(sha:)` lookup by the authenticated organization's repositories, not globally by sha.

### Proof of Concept
Not independently executable without the ability to run the Rails test suite/terminal (unavailable in this read-only analysis), but conceptually:
1. Onboard/attacker-control Org A in a multi-org Shipit deployment, knowing Org A's `webhook_secret`.
2. Craft a JSON body for the `status` (or `push`) event with `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/victim-repo"` (or, for `status`, simply an arbitrary `sha` belonging to a commit in Org B's stack), `state: "success"`.
3. Compute `X-Hub-Signature` with Org A's real `webhook_secret` per `GitHubApp#verify_webhook_signature`, matching the controller's `verify_signature` logic. [6](#0-5) 
4. POST to `/github/webhooks` (routed via `config/routes.rb`) with `X-Github-Event: status`; the controller accepts it because Org A's secret validates, then `StatusHandler.call(params)` writes a forged success status onto Org B's commit. [4](#0-3)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
