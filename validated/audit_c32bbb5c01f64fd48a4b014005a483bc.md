### Title
Unsigned STX-locking / PoX-reward hijack via forged `PreStxOp`/`StackStxOp` pair — ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`PreStxOp::parse_from_tx` binds the future `StackStxOp.sender` to whatever Stacks address appears in output index 0 of the PreStx Bitcoin transaction, with no requirement that this address's key ever signs either the PreStx or the StackStx transaction. `StackStxOp::get_sender_txid` only checks that the spent PreStx output index is `1`, never that output 0 (the claimed sender) and output 1 (the UTXO actually spent) are economically tied to the same owner. This lets an attacker who fully controls both transactions' Bitcoin inputs name an arbitrary victim as `sender`, causing the node to invoke pox's `stack-stx` on the victim's behalf and redirect the resulting PoX reward stream to the attacker.

### Finding Description
The broken equality is: **AUTHORITY** — `StackStxOp.sender` (the Stacks account whose STX gets locked and whose PoX reward stream is redirected) must equal the Stacks address that itself authorized the stacking action (i.e., whose Bitcoin key signed the chain of ops), not merely an address chosen as `output[0]` in an unrelated `PreStxOp`.

Code path:
1. `PreStxOp::parse_from_tx` (`stackslib/src/chainstate/burn/operations/stack_stx.rs:74-144`) reads `output[0]` from the PreStx tx's Bitcoin recipients and stores it as `PreStxOp.output` with zero validation that it corresponds to the tx's own inputs or to `output[1]`. [1](#0-0) 
2. `StackStxOp::get_sender_txid` (`stack_stx.rs:232-247`) only verifies that the StackStx tx's first input spends `vout == 1` of the referenced PreStx tx — it never checks who controls `vout == 1`, nor does it compare that ownership to `PreStxOp.output` (`vout == 0`). [2](#0-1) 
3. `Burnchain::classify_transaction` wires these together: it looks up the `PreStxOp` by txid, extracts `sender = pre_stack_stx.output`, and passes it straight into `StackStxOp::from_tx` as the `sender` field with no further authorization check. [3](#0-2) 
4. `StacksChainState::process_stacking_ops` then directly executes the boot `stack-stx` contract call **as** that `sender` — `tx.run_contract_call(&sender.clone().into(), None, &boot_code_id(active_pox_contract, mainnet), "stack-stx", &args, ...)` — with no Stacks-level signature from `sender` ever checked. [4](#0-3) 
5. Inside pox's `stack-stx`, the only balance check is `(>= (stx-get-balance tx-sender) amount-ustx)`, and the only cryptographic check (`consume-signer-key-authorization`) validates ownership of the *reward-address signer key* — which the attacker supplies themselves — not ownership of the account being locked. [5](#0-4) 

Exploit flow: the attacker funds and signs a `PreStxOp` Bitcoin transaction from their own UTXOs, but sets output[0] to the victim's Stacks address and output[1] to an attacker-controlled UTXO. They then craft a `StackStxOp` transaction whose only input spends that output[1] (satisfying `vout==1`), and whose payload sets `reward_addr` and `signer_key`/`signer_sig` to values the attacker controls. Because `sender` is derived purely from `PreStxOp.output[0]`, the node locks the victim's STX balance and streams the resulting PoX rewards to the attacker's own reward address — without the victim ever signing anything.

Existing guards do not stop this: `check-pox-lock-period`, `can-stack-stx`, and `consume-signer-key-authorization` all operate on the `sender`/`pox-addr`/`signer-key` values as given, and none of them re-derive `sender` from a Bitcoin-signature check — that binding is done entirely, and insufficiently, in the burnchain-op parsing layer described above.

### Impact Explanation
The victim's STX is locked (temporarily frozen for `num_cycles` reward cycles) without their consent, and — more importantly — the PoX reward yield that would normally accrue to the victim's locked STX is redirected to an attacker-chosen `reward_addr`, i.e. theft of PoX rewards from a victim's balance that the victim never authorized to be stacked. This matches the Critical category ("theft ... of locked STX or sBTC rewards") since reward entitlement is completely decoupled from the actual owner of the locked value, and also independently qualifies as High ("an unsigned stacking action" / "temporary freezing of staked funds"). The attack is repeatable against any Stacks address with sufficient spendable STX balance, requiring only Bitcoin fees paid by the attacker.

### Likelihood Explanation
Preconditions are minimal: the attacker needs any small amount of BTC to fund the two-transaction chain (`PreStxOp` + `StackStxOp`), knowledge of the victim's Stacks address (public), and the victim must have an unlocked STX balance ≥ the amount claimed (`stacked_ustx`) at the time the ops are mined. No privileged role, no compromised keys, and no cooperation from the victim are required — the entire attack is executable by an ordinary unprivileged actor using only their own Bitcoin UTXOs, exactly matching the attacker capability of "craft burnchain stacking ops from their own Bitcoin inputs" explicitly permitted in this audit's threat model. It is repeatable every reward cycle, against different or the same victim.

### Recommendation
Require that `PreStxOp`'s claimed `output` (vout 0) be cryptographically tied to the party who actually authorizes the downstream `StackStxOp`/`TransferStxOp`/`DelegateStxOp` — e.g., require that vout 1 (the UTXO to be spent by the follow-up op) be sent to the same address/script as vout 0, or otherwise verify that the Bitcoin input(s) of the follow-up operation are signed by keys corresponding to the `sender` Stacks address, before binding `StackStxOp.sender` to `PreStxOp.output`. At minimum, document and consider deprecating burnchain-op-based stacking given it allows unsigned locking of arbitrary Stacks accounts' balances.

### Proof of Concept
Rust integration test extending `stackslib/src/burnchains/tests/db.rs` patterns:
1. Construct a `PreStxOp` Bitcoin tx funded entirely by attacker-controlled UTXOs, with `outputs[0].address = victim_addr` and `outputs[1].address = attacker_addr` (attacker-controlled key).
2. Construct a `StackStxOp` Bitcoin tx whose sole input is `(pre_stx_txid, 1)` (spending the attacker's own UTXO from step 1) and payload encoding `stacked_ustx`, `num_cycles`, `signer_key = attacker_signer_key`.
3. Run `Burnchain::classify_transaction` over both, then feed the resulting `StackStxOp` into `StacksChainState::process_stacking_ops` against a chainstate where `victim_addr` holds ≥ `stacked_ustx` unlocked STX and never signed any Stacks transaction.
4. Assert (equality check before/after): before, `victim_addr`'s STX is fully unlocked and not stacked; after processing, `stx-account victim_addr` shows `locked = stacked_ustx` and PoX reward-set entries point to `attacker_reward_addr` — demonstrating that `sender == victim_addr` even though `victim_addr`'s key never signed the `PreStxOp` or `StackStxOp` Bitcoin transactions. A correct implementation should instead reject the `StackStxOp` (or attribute the lock/reward to the actual UTXO owner) unless `victim_addr`'s key participated in signing the operation chain.

            Some((ref txid, vout)) => {
                if *vout != 1 {

                    Err(op_error::InvalidInput)

                    Ok(txid)
                }
            }
            None => {
                warn!("Invalid tx: StackStxOp must have at least one input");
