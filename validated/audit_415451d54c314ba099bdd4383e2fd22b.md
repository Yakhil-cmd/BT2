### Title
Webhook signature verified against `repository.owner.login`, but handlers act on `repository.full_name` — enabling cross-repository writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook's HMAC signature against using `repository_owner`, a field extracted from the untrusted payload itself. Downstream event handlers, however, resolve the target `Stack`/`Repository` to act on using a *different* field of the same payload (`repository.full_name`, i.e. `owner/repo`). Because Shipit is multi-tenant (it can be configured with several GitHub organizations, each with its own `webhook_secret`, as seen in `config/secrets.development.shopify.yml`), nothing in the controller enforces that `repository.full_name`'s owner segment actually matches the `repository_owner` value used to pick the verifying secret.

### Finding Description
`verify_signature` computes the organization to authenticate against like this: [1](#0-0) 
and: [2](#0-1) 

The whole raw JSON body is HMAC-signed with the secret configured for that specific `repository_owner`/organization — but that secret is one the organization's own GitHub App admin legitimately possesses (they configured it when wiring up the GitHub App/webhook for their own org). Once the signature passes, `create` dispatches the parsed body verbatim to every registered handler for the event: [3](#0-2) 

The bug-class analog to the Solidity report is: the report used one input path (`getUSDPrice` via `priceFeed`) to *compute* a value while the actual economically-relevant quantity should have used a different, correctly-scaled source (`bptOracle`) — a mismatch between what's verified/trusted and what's actually operated on. Here, the same JSON body contains two independent identity fields — `repository.owner.login` (used for **authentication**, i.e. selecting the HMAC secret) and `repository.full_name` (used by handlers such as the push/status handlers to look up and **write to** a `Stack`) — and the controller never asserts that `full_name` is prefixed by the same `owner.login` that was authenticated. GitHub's real webhook deliveries always keep these consistent, but this controller trusts the payload's internal consistency instead of deriving `full_name` from the authenticated owner.

The binding that should hold, expressed as an equality, is:
`organization authenticated by verify_signature (repository_owner) == organization prefix of the repository actually written to by the handler (repository.full_name)`

Before the attacker's crafted payload, in the intended GitHub flow this equality always holds because GitHub itself sets both fields from the same repository object. After an attacker-controlled payload, the equality can be broken: an org administrator who legitimately owns organization `A` (and thus knows/controls `A`'s `webhook_secret`, since they configure it themselves when registering the GitHub App / webhook for their own account) can produce a raw JSON payload where `repository.owner.login = "A"` (so `verify_signature` selects and validates against `A`'s secret, which they can correctly sign) but `repository.full_name = "victim-org/victim-repo"`. This is possible because signing only requires knowledge of the secret used for the chosen `repository_owner`, and the attacker is free to set every other JSON field in the same signed body to point at an unrelated repository — GitHub does not need to be involved at all, the request is a raw POST to `/webhooks` with a manually computed `X-Hub-Signature`.

### Impact Explanation
Handlers keyed off `repository.full_name`/commit SHAs (push, status, check_suite) will resolve and mutate the `Stack`/`Commit` records belonging to `victim-org/victim-repo`, e.g. enqueuing `GithubSyncJob`, creating `Commit::Status` rows, or updating check-run state for a stack the attacker has no access to and never authenticated for — this is a cross-repository write achieved purely by controlling a webhook secret for an unrelated, attacker-owned organization/repo that also happens to be registered in the same multi-tenant Shipit instance. This matches the Critical "cross-repository writes" impact category.

### Likelihood Explanation
Requires the attacker to be a legitimate, unprivileged owner/admin of *some* GitHub organization/App that is configured in this Shipit instance (a realistic scenario for any Shipit deployment onboarding multiple orgs, as the sample multi-org secrets file demonstrates). No access to the victim repository, no Shipit session, and no `ApiClient` token are needed — only the ability to send a raw signed POST to the public `/webhooks` endpoint. This is a moderate-likelihood issue restricted to multi-organization Shipit deployments.

### Recommendation
In `verify_signature`, after determining `repository_owner` and validating the signature, also assert that `repository.full_name` (when present) is prefixed by `repository_owner` (case-insensitively) before dispatching to handlers; reject with `422` otherwise. Alternatively, derive the target repository strictly from the already-authenticated `repository_owner`/`organization.login` rather than independently trusting `full_name` deeper in the handler chain.

### Proof of Concept
Conceptual request (assuming attacker administers org `attacker-org` and knows its `webhook_secret`):
```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1 of raw body computed with attacker-org's webhook_secret>

{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "after": "<arbitrary sha>",
  ...
}
```
`verify_signature` looks up `Shipit.github(organization: "attacker-org")` and validates the signature successfully because the attacker legitimately controls that org's secret. `PushHandler` (dispatched via `Shipit::Webhooks.for_event('push')`) then resolves the `Stack` using `repository.full_name = "victim-org/victim-repo"` and enqueues a `GithubSyncJob`/creates commits against the victim's stack, all without the attacker ever having access to `victim-org`.
