### Title
Unscoped `read:stack` token generated by CCMenu URL feature grants cross-stack read access to any stack's build/deploy status - (File: `app/controllers/shipit/ccmenu_url_controller.rb`)

### Summary
Shipit's CCMenu integration generates a bearer token intended to authorize unattended, unauthenticated read access to *one* stack's build status. In practice the generated `ApiClient` is never bound to that stack, so the token authorizes read access to **every** stack in the installation. This breaks the "stack a token authorises versus a stack it touches" binding: the UI/URL implies scope = single stack, but the actual credential's scope = all stacks.

### Finding Description
`CCMenuUrlController#fetch` mints (or reuses) an `ApiClient` for the current user with `permissions: %w[read:stack]` but does **not** attach a `stack` to it: [1](#0-0) [2](#0-1) 

Because `ApiClient.belongs_to :stack, optional: true` and this client is created with no `stack:` attribute, its `stack_id` is `nil`: [3](#0-2) 

The permission model only checks the *operation:scope* pair (`read:stack`), never a specific stack instance: [4](#0-3) 

The stack-scoping that would normally restrict a client (`stacks` in `Api::BaseController`, which filters by `current_api_client.stack_id`) only applies when `stack_id?` is true; for the CCMenu client it's false, so it falls back to `Stack.all`: [5](#0-4) 

`CCMenuController` (the endpoint actually consuming the token) doesn't even use that scoped `stack` helper — it overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, and authenticates purely via the query-string `token` param, with no session or per-stack binding: [6](#0-5) 

The token is embedded directly in a URL returned to the browser (`ccmenu_url`), a URL that is by design meant to be handed to third-party CI-status tools (CCTray/CCMenu clients), which increases the chance of leakage through logs, proxies, referrer headers, or being pasted into dashboards/status pages/chat — none of which are protected by Shipit session auth.

### Impact Explanation
Any leaked CCMenu token — generated in the context of, and presented to the user as belonging to, one specific stack — can be replayed unauthenticated against `/api/:owner/:repo/:environment/ccmenu.xml` for **any other stack** in the Shipit instance to read its build/deploy status (name, last build status/label, lock state, etc.). This is an unauthenticated read of stack state across repository/stack boundaries, matching the High-impact criterion "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
No privileged Shipit session or GitHub credentials are needed to exploit the token once obtained — only the token string, which is designed to be shared externally in a URL (the entire point of the CCMenu feature is external, unauthenticated polling). The bug requires no user interaction beyond the normal, encouraged workflow of generating and sharing a CCMenu URL, making exploitation straightforward for anyone who intercepts or is given one such URL.

### Recommendation
When `CCMenuUrlController#client` creates the `ApiClient`, bind it to the specific stack (`stack: stack`) instead of leaving it global, and enforce that `Api::CCMenuController#stack`/`authenticate_api_client` reject requests where `params[:stack_id]` does not match `current_api_client.stack_id` (mirroring the scoping already implemented in `Api::BaseController#stacks`). Consider minting a distinct, stack-scoped `ApiClient` per stack rather than reusing a single per-user "CCMenu Client" across all stacks.

### Proof of Concept
1. As a legitimate Shipit user with access to Stack A (`org/repoA/production`), open Stack A's settings and generate the CCMenu URL via `CCMenuUrlController#fetch` → receive `https://shipit.example.com/api/org/repoA/production/ccmenu.xml?token=T`.
2. Share/paste that URL into an external CI dashboard tool (the intended use case) — token `T` is now outside Shipit's session-authenticated boundary.
3. Anyone who obtains `T` (via logs, network capture, dashboard config, etc.) requests `https://shipit.example.com/api/otherorg/otherrepo/production/ccmenu.xml?token=T`.
4. Because the `ApiClient` behind `T` has `stack_id = nil` and `CCMenuController` performs no per-stack ownership check, the request succeeds and returns build/deploy status for `otherorg/otherrepo/production`, a stack the token was never intended to authorize.

```ruby
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
```
