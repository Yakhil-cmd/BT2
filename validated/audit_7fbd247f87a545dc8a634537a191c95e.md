Found the key mechanism: `validateAttestorListUpdate` in `validation.js` confirms that once an asset has `spender_attested: true`, the asset **definer** (a restricted, non-owner role — it cannot steal funds or directly move any user's coins, mirroring the "governor" restriction in the Aloe report) retains **permanent, unilateral, unbounded** power to rewrite the attestor list via an `asset_attestors` message, subject only to the constraint that the new list is non-empty and sorted. [1](#0-0) 

This is validated identically for both plain units and AAs (`aa_validation.js` case `'asset_attestors'`), and applied to storage by `writer.js`: [2](#0-1) [3](#0-2) 

The enforcement point that actually blocks spending is in `validatePayment`/`validatePaymentInputsAndOutputs`, which requires that all authors of a payment (and, for issuance, the issuer) be present in `objAsset.arrAttestedAddresses`, derived from the *latest* attestor list posted for the asset: [4](#0-3) [5](#0-4) 

Because `checkAttestorList` only requires the array to be non-empty, sorted, and made of valid addresses — it does **not** require that any currently-attested holder remain attested, nor that the new attestor(s) ever attest anyone again: [6](#0-5) 

the definer can replace the attestor list with an attestor address that never issues any new attestations (e.g. an address they control but simply never use, or a burned/inaccessible address). Once that happens, every current and future holder of the asset permanently fails the `arrAttestedAddresses.length === 0` / "issuer is not attested" checks, and **no unit spending that asset can ever validate again** — for any holder, including holders who currently possess valid balances and were never at fault. There is no way for holders to route around the definer, because the check is unconditional whenever `spender_attested` is true, and this flag itself is immutable once set at asset definition: [7](#0-6) 

### Title
Asset definer can unilaterally and permanently freeze all holders' funds by rewriting the attestor list of a `spender_attested` asset via `asset_attestors` - (File: `validation.js`)

### Summary
For any asset created with `spender_attested: true`, the asset definer address is granted permanent, unbounded authority to replace the trusted attestor list at will via an `asset_attestors` message, with no requirement that the resulting list actually re-attest existing holders. Because every payment involving that asset (including AA-triggered payments) must have all authors present in the currently-attested set, the definer can trivially and permanently lock every holder's balance by pointing the attestor list at an address that will never attest anyone.

### Finding Description
`validateAttestorListUpdate` only checks that the message is single-authored, the author is the asset's `definer_address`, and the new attestor array passes `checkAttestorList` (non-empty, sorted, valid addresses). It performs no check that the new attestor set is capable of, or under any obligation to, attest existing/future spenders [8](#0-7) .

`validatePayment` enforces `spender_attested` unconditionally for both normal transfers and issuance: if `objAsset.arrAttestedAddresses.length === 0`, the payment is rejected outright ("none of the authors is attested"), and even non-empty attestation lists must specifically include the payer/issuer [4](#0-3) . `storage.readAsset` always resolves to the *single latest* attestor-list unit for the asset (by `level`/`rowid`, i.e. whichever was posted most recently), discarding all previously attested addresses [5](#0-4) .

Because `checkAttestorList` places no obligation on future attestor behavior, and asset definer permission to post `asset_attestors` is unlimited in frequency and content (aside from field/format checks), the definer can, at any time and without users' consent, replace the attestor list with an address that will simply never issue attestations again (e.g. control it and never use it, or reference an address whose keys are lost/unused). From that point forward, `arrAttestedAddresses` will be permanently empty for all holders, and the asset becomes permanently non-transferable — including for holders who deposited/received the asset in good faith before the malicious update, and including internal accounting inside AAs that hold or distribute this asset.

### Impact Explanation
This produces a permanent, protocol-level freeze of user funds by a role that (like the "restricted" governor in the referenced report) is not supposed to be able to prevent users from withdrawing/spending their own balances — the asset issuer/definer role does not have signing authority over user outputs and cannot steal funds directly, yet it can unilaterally render all outstanding units of the asset permanently unspendable for every holder, with no on-chain remedy (no override, no timeout, no way for holders to re-attest themselves). Any AA that issues a `spender_attested` asset (a documented, supported pattern) inherits this exact risk against its own users/depositors. This satisfies the "AA fund loss or freezing" / permanent inability to spend one's own confirmed outputs criterion.

### Likelihood Explanation
The action requires only a single `asset_attestors` message signed by the address that originally defined the asset — no majority vote, no special permissions beyond being the definer, and no additional cost or complexity. Any asset creator (human-authored or AA-authored) who sets `spender_attested: true` is trusted with this power for the lifetime of the asset; a malicious or compromised definer (or an AA definer whose code takes an attacker-controlled parameter into the attestor list) can trigger it in a single unit.

### Recommendation
Consider one or more of: (1) requiring that an `asset_attestors` update be co-signed/acknowledged by at least one currently attested holder or via a timelocked/governance-style delay so holders can exit beforehand; (2) allowing holders who were attested under a previous attestor-list unit to keep spending rights for balances they already held at the time of a later, hostile list change (grandfathering); or (3) exposing a protocol-level warning/inspection tool so wallets can detect and refuse to accept `spender_attested` assets whose definer retains unilateral, un-timelocked control before allowing users to hold them.

### Proof of Concept
1. An AA or user defines asset `A` with `issued_by_definer_only:false or true`, `spender_attested:true`, and an initial `attestors` list containing address `X` (controlled by the definer) [7](#0-6) .
2. `X` attests several holders (e.g. via normal `attestation` messages), who then receive/hold balances of asset `A` and pass the `arrAttestedAddresses` check in `validatePayment` [4](#0-3) .
3. The definer posts a single `asset_attestors` message for asset `A` naming only a new attestor address `Y`, which the definer controls but will never use to issue attestations [1](#0-0) .
4. `storage.readAsset` now resolves the asset's attestor list to the unit containing `Y` only, and since `Y` never attests anyone, `arrAttestedAddresses` is permanently empty for all addresses [5](#0-4) .
5. Every subsequent attempt by any holder to spend/transfer asset `A` fails validation with "none of the authors is attested", permanently freezing their balances with no recourse [4](#0-3) .

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
