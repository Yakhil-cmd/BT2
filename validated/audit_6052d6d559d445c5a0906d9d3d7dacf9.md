### Title
Terminal escape-sequence guard in `readFileRun` only detects 7-bit ESC (0x1B), allowing C1 8-bit control-code injection to bypass `ContainsEscapeSequence` - (File: pkg/cmd/repo/read-file/read_file.go)

### Summary
`readFileRun` disables output sanitization (`opts.IO.SetContentSanitization(false)`) and relies solely on `iostreams.ContainsEscapeSequence` to block terminal escape injection before writing attacker-controlled `file.Content` to `opts.IO.ContentOut`. That function only scans for the single byte `0x1B` (7-bit ESC) and does not detect equivalent 8-bit C1 control codes (0x80-0x9F, e.g. `0x9B` = CSI, `0x9D` = OSC), which many terminal emulators still interpret as escape-sequence introducers even without a preceding ESC byte.

### Finding Description
In `pkg/cmd/repo/read-file/read_file.go`, `readFileRun` fetches `file.Content` from the GitHub Contents API (fully attacker-controlled if the victim reads a file from an attacker's public repo/fork), then: [1](#0-0) 
It disables the IOStreams content sanitizer and gates the raw write on `iostreams.ContainsEscapeSequence`. That function is implemented as: [2](#0-1) 
It performs a single `bytes.IndexByte(b, 0x1B)` check — i.e., it detects only the 7-bit ASCII ESC introducer used in `ESC [ ... ` (CSI), `ESC ] ... ` (OSC), etc. It does not account for the equivalent single-byte C1 control codes defined by ECMA-48/ISO-6429 (0x80-0x9F), such as `0x9B` (CSI) or `0x9D` (OSC), which many terminal emulators (e.g. xterm in certain modes, and various legacy/embedded terminals) still recognize and act on as escape-sequence introducers without requiring a preceding `0x1B`. A file whose content is composed entirely of such C1 bytes (with no `0x1B` anywhere) would pass `ContainsEscapeSequence` cleanly, reach `opts.IO.ContentOut.Write(file.Content)` unmodified (sanitization explicitly disabled), and be able to manipulate the victim's terminal — e.g. via C1 OSC sequences forging prompts/output or setting terminal title/clipboard on terminals that decode 8-bit C1 codes.

Note: the "internal buffer cap" part of the question does not apply here — unlike `CopyGuardedContent` (which streams via a bounded `contentSniffLen` sniff window before falling back to `io.ReadAll`), `readFileRun` calls `ContainsEscapeSequence` directly on the fully-buffered `file.Content` already held in memory, so there's no truncation/streaming bypass in this path. The gap is specifically the 7-bit-only ESC detection.

### Impact Explanation
This maps to terminal escape-sequence injection / trusted-output forgery (spoofing terminal content, prompts, or triggering terminal-specific side effects such as title-bar/clipboard manipulation via OSC), reachable purely by a victim running `gh repo read-file <path>` against an attacker-controlled public repo, fork, or PR branch, without any additional flags. It does not achieve code execution or credential exfiltration by itself, but is a real content-based terminal spoofing/injection vector.

### Likelihood Explanation
Feasibility depends on the victim's terminal emulator accepting 8-bit C1 control codes without UTF-8 mode forcing multi-byte encoding of those code points (raw byte values 0x80-0x9F are only interpretable as C1 controls in non-UTF-8/Latin-1 style terminal modes, or where the terminal explicitly supports 8-bit control sequences). Many modern terminal emulators default to UTF-8 and would instead render 0x80-0x9F as part of invalid/replacement multi-byte sequences rather than as control codes, which reduces exploitability in the common default configuration. This meaningfully limits real-world likelihood versus the classic 7-bit ESC path (`\x1b[`), which works universally regardless of encoding mode. The precondition otherwise is trivial: read a file from an attacker-controlled repo without `--allow-escape-sequences`.

### Recommendation
Broaden `ContainsEscapeSequence` (or add a complementary check used specifically by `read-file`) to also flag C1 control bytes in the 0x80-0x9F range, or more precisely detect valid UTF-8-encoded C1 controls (`\xC2\x80`-`\xC2\x9F`) in addition to the raw single-byte form, matching whatever encoding mode the target terminal is expected to run in. Consider reusing/aligning with the sanitizer logic in `pkg/iostreams/untrusted.go` (already used elsewhere for output sanitization) rather than maintaining a second, narrower, ESC-only check in `content.go`.

func TestContainsEscapeSequence_MissesC1Controls(t *testing.T) {
    // 0x9B is the C1 control code for CSI, equivalent to ESC 0x1B + '['.
    // Terminals that interpret 8-bit C1 controls will treat this as an
    // escape-sequence introducer even though no 0x1B byte is present.
    c1CSI := []byte("danger\x9b31mtext")

    if iostreams.ContainsEscapeSequence(c1CSI) {
        t.Fatal("expected false positive: check only scans for 0x1B, C1 controls bypass it")
    }
    // Demonstrates that readFileRun's guard at
    // pkg/cmd/repo/read-file/read_file.go:198 would let this content through
    // to opts.IO.ContentOut.Write with sanitization disabled.
}
