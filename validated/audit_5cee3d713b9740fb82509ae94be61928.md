### Title
Unchecked `witness` parameter in `submit_unsigned` causes assertion-failure panic on attacker-controlled unsigned extrinsic - ([File: substrate/frame/election-provider-multi-phase/src/lib.rs])

### Summary
`pallet-election-provider-multi-phase::submit_unsigned` is a `ensure_none` (unsigned) dispatchable, meaning it requires no signature, no fee, and no privileged role — anyone can construct and gossip it. The dispatchable's own `witness: SolutionOrSnapshotSize` argument is cross-checked against on-chain `SnapshotMetadata` using `assert!`, not `ensure!`, deliberately intending to panic rather than gracefully reject: [1](#0-0) 

The pre-inclusion validation path, `unsigned_pre_dispatch_checks`, which is documented as covering "the basics checks that MUST happen during the validation and pre-dispatch of an unsigned transaction," only validates phase, round, desired-target count and score improvement — it never compares `witness` to `SnapshotMetadata`: [2](#0-1) 

Because the witness/`SnapshotMetadata` comparison exists only inside the dispatchable body as an `assert!`, and not in the shared pre-dispatch/validation routine, this is structurally analogous to the CVE-2024-3652 pattern: an attacker-supplied field (here, `witness`) that is never checked at the "acceptance" stage (IKEv1 proposal parsing / here, `ValidateUnsigned`/`pre_dispatch`) is only checked deep inside execution via an assertion, causing a hard panic/crash instead of a controlled error.

### Finding Description
- Entry point: `submit_unsigned(origin, raw_solution, witness)` with `ensure_none(origin)` — a completely permissionless, feeless, unsigned call. [3](#0-2) 
- The only shared validation function invoked before dispatch, `unsigned_pre_dispatch_checks`, does not touch `witness` at all; it checks `CurrentPhase`, `Round`, `DesiredTargets` cardinality, and `QueuedSolution` score improvement only. [4](#0-3) 
- Inside the dispatchable itself, after the shared checks pass, the code reads `SnapshotMetadata` and asserts equality against the caller-supplied `witness.voters`/`witness.targets` using hard `assert!` macros with an explicit comment: "NOTE: we are asserting, not `ensure`ing -- we want to panic here." [5](#0-4) 
- `frame-executive`'s own contract states that from the point an extrinsic starts executing, "Under no circumstances may this function panic from here onwards," underscoring that a reachable panic inside dispatch is treated as a serious defect at the framework level. [6](#0-5) 

The `witness` field exists purely so that a submitter can (and is expected to) self-declare the weight-relevant `voters`/`targets` counts (used to compute `WeightInfo::submit_unsigned(witness.voters, witness.targets, ...)` for pre-dispatch weight/fee accounting), while the actual snapshot size lives in `SnapshotMetadata`. There is no code path shown that validates the two match before the value is used to charge weight and before the extrinsic reaches the panic-triggering `assert!`.

### Impact Explanation
If an unsigned transaction with a mismatched `witness` reaches the point of dispatch (i.e., it is not rejected earlier for phase/round/score reasons — which are independent of `witness`), executing it panics the runtime. A panic during `apply_extrinsic`/block execution is a process-level crash for any node (including honest, non-malicious validators or full nodes) that attempts to execute a block containing that extrinsic, which maps to a deterministic denial-of-service / node-crash class matching the reported CVE's severity band (crash upon processing attacker-influenceable, unauthenticated input).

### Likelihood Explanation
The call is unsigned, feeless and requires no special role (`ensure_none`), so submission cost to an attacker is minimal — matching the "no privileged role" requirement in the report. Reachability, however, hinges on whether the transaction-pool/block-authoring validation path (`ValidateUnsigned::validate_unsigned` / `pre_dispatch` in `lib.rs`, which was not fully retrieved in this session due to tool-call limits) performs any additional witness-vs-snapshot check beyond `unsigned_pre_dispatch_checks`. Based on the code actually inspected, no such check exists outside the dispatchable body, but I was **not able to view the full `ValidateUnsigned` implementation in `lib.rs`** before running out of tool iterations, so I cannot fully confirm whether an additional guard exists there that would prevent a mismatched-witness transaction from ever being pooled/included. This is an important open verification gap.

### Recommendation
Move the `witness.voters == SnapshotMetadata.voters` / `witness.targets == SnapshotMetadata.targets` comparison into `unsigned_pre_dispatch_checks` (or an equivalent function invoked by both `validate_unsigned` and `pre_dispatch`), returning a `DispatchResult`/`TransactionValidityError` via `ensure!` instead of relying on a dispatch-time `assert!`. This preserves the intended validator-punishment semantics (transaction is rejected, so it cannot be included at all) while removing the code path where an unauthenticated, well-formed-looking unsigned extrinsic can reach a hard panic during real block execution.

	pub fn unsigned_pre_dispatch_checks(
		raw_solution: &RawSolution<SolutionOf<T::MinerConfig>>,
	) -> DispatchResult {
		// ensure solution is timely. Don't panic yet. This is a cheap check.
		ensure!(
			CurrentPhase::<T>::get().is_unsigned_open(),
			Error::<T>::PreDispatchEarlySubmission
		);

		// ensure round is current
		ensure!(Round::<T>::get() == raw_solution.round, Error::<T>::OcwCallWrongEra);

		// ensure correct number of winners.
		ensure!(
			DesiredTargets::<T>::get().unwrap_or_default() ==
				raw_solution.solution.unique_targets().len() as u32,
			Error::<T>::PreDispatchWrongWinnerCount,
		);

		// ensure score is being improved. Panic henceforth.
		ensure!(
			QueuedSolution::<T>::get()
				.map_or(true, |q: ReadySolution<_, _, _>| raw_solution.score > q.score),
			Error::<T>::PreDispatchWeakSubmission,
		);

		Ok(())
	}
