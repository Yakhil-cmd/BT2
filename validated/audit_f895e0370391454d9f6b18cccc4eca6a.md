### Title
Cross-tenant webhook forgery via decoupled `repository.owner.login` (signature) and `repository.full_name` (stack lookup) - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/push_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC-verifying `GithubApp` using `params.dig('repository', 'owner', 'login')`, while `Webhooks::Handlers::Handler#stacks` (used by `PushHandler`) resolves the target `Repository`/`Stack` rows using `payload.dig('repository', 'full_name')`. Because these are two independent fields of the same attacker-controlled JSON body, an attacker who owns `org-attacker` (and thus knows its `webhook_secret`) can produce a validly-signed webhook whose `repository.owner.login` is `org-attacker` but whose `repository.full_name` is `org-victim/app`, causing Shipit to sync and eventually deploy `org-victim`'s stack.

### Finding Description
The broken binding, stated explicitly: the code implicitly assumes `Shipit.github(organization: payload.repository.owner.login) == Shipit.github(organization: Repository.from_github_repo_name(payload.repository.full_name).owner)`, but no code enforces this equality.

- Signature verification path: `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) and uses it to pick the `GithubApp` instance whose `webhook_secret` is used for HMAC verification: [1](#0-0) [2](#0-1) 
- `GithubApp#verify_webhook_signature` just checks the HMAC-SHA1 of the raw body against that org's configured secret: [3](#0-2) 
- Target resolution path: `PushHandler#process` calls `stacks.not_archived.where(branch:)`, where `stacks` is defined in the base `Handler` class as `Repository.from_github_repo_name(repository_name)&.stacks`, and `repository_name` is `payload.dig('repository', 'full_name')` — a completely separate JSON field from the one used for signature selection: [4](#0-3) [5](#0-4) 
- `Repository.from_github_repo_name` naively splits `"owner/name"` from `full_name` and looks up the real `Repository` row by that owner/name, independent of who verified the signature: [6](#0-5) 
- `branch` is computed as `params.ref.gsub('refs/heads/', '')`, so `ref: "refs/heads/master"` matches any victim stack tracking `master`: [7](#0-6) 
- Once matched, `stack.sync_github` is called unconditionally, enqueuing `GithubSyncJob`, which fetches commits and eventually can trigger `Stack#trigger_continuous_delivery` / deploy for the victim's real repository, using the **victim's own configured `github_app`** (`Stack#github_app` = `Shipit.github(organization: repository.owner)`), completely bypassing any relationship to the org that supplied the valid signature: [8](#0-7) [9](#0-8) 

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: push`, `X-Hub-Signature: sha1=<HMAC of raw body using org-attacker's webhook_secret>`, and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha, purely used as expected_head_sha hint>",
  "repository": {
    "full_name": "org-victim/app",
    "owner": { "login": "org-attacker" }
  }
}
```
The signature check passes because `verify_signature` looks up `Shipit.github(organization: 'org-attacker')` (the attacker's own configured app) and verifies against that secret, which the attacker legitimately knows. The stack-matching logic then ignores `repository.owner.login` entirely and instead parses `org-victim/app` from `full_name`, hitting the real `Repository` row for `org-victim`.

None of the existing guards close this gap:
- `drop_unhandled_event` only checks the event type is registered, not repository consistency.
- `ExplicitParameters` schema on `PushHandler` only requires `ref` and `after` — it does not require or validate `repository.owner.login` matches anything.
- `verify_signature`/`GithubOrganizationUnknown` only fail if `org-attacker` itself is unknown to Shipit; it does not fail merely because `full_name`'s owner differs from `repository.owner.login`.
- There is no `Stack`/`Repository` model validation or controller-level equality check between the verifying org and the matched stack's repository owner anywhere in `WebhooksController`, `Handler`, or `PushHandler`.

### Impact Explanation
This is a payload from one repository (attacker-owned) mutating another repository's stack state (`org-victim/app`), matching the Critical category explicitly listed in scope. Each forged request enqueues `GithubSyncJob` for the victim stack, which fetches new commits from GitHub (using the victim's own GitHub credentials) and can advance `next_commit_to_deploy`/trigger `trigger_continuous_delivery`, leading to an unauthorized deploy trigger of the victim's default/tracked branch. The attack is repeatable against any stack whose repository owner/name is guessable or discoverable (e.g., public GitHub repos, or Shipit's own repository listing UI), and is not limited to a single victim — any org configured in Shipit with a stack tracking a known branch is reachable as long as the attacker owns some org with a configured `webhook_secret` in the same Shipit instance.

### Likelihood Explanation
Preconditions: the attacker needs their own GitHub org/app registered in the same Shipit installation with a `webhook_secret` configured (a normal, low-privilege setup for any legitimate tenant onboarding), and knowledge of the victim's `owner/name` (public information, or discoverable via Shipit's own `/repositories` listing). No Shipit session, API token, or victim secret is required. Cost is a single crafted HTTP POST with a signature computed from the attacker's own secret — trivial and fully repeatable.

### Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler`), enforce that the organization used to verify the signature matches the owner of the repository referenced by `full_name` before dispatching to handlers — e.g., after resolving `Repository.from_github_repo_name(params.dig('repository','full_name'))`, assert its `owner` equals `repository_owner` (case-insensitively), and reject (422) on mismatch, rather than only checking `owner.login` presence/known-org status.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
