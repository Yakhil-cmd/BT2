### Title
Race condition in private payment chain validation allows concurrent double-crediting of a hidden output - (File: `private_payment.js`, `network.js`)

### Summary
`network.js`'s `handleOnlinePrivatePayment()` explicitly disables its unit-in-work de-duplication guard for private payments (`assocUnitsInWork[unit]` set/checked lines are commented out), and the downstream `validateAndSavePrivatePaymentChain()` in `private_payment.js` performs a non-atomic "check-then-act" (SELECT for duplicate, then INSERT) across a **fresh** per-call DB connection/transaction with **no mutex serialization** by unit/output. This is structurally the same bug class as CVE-2024-49768 (Waitress): a security-relevant guard against overlapping/concurrent processing of the same logical request is disabled, letting a second copy of an in-flight "request" be processed and committed before the first one's state is finalized.

This is the *only* place in the codebase where the standard `assocUnitsInWork` in-flight-request guard (used pervasively elsewhere, e.g. `handleJoint`) is deliberately disabled, meaning nothing prevents two concurrent private-payment messages that reveal the same hidden output (same `unit`, `message_index`, `output_index`) from being processed at the same time.

The downstream function `validateAndSavePrivatePaymentChain` in `private_payment.js` opens a brand-new DB connection/transaction per call and performs a classic TOCTOU sequence: it `SELECT`s the existing (possibly still-hidden) output row to check for a duplicate reveal, and only *after* that check decides whether to call the asset module to validate-and-save the reveal: [2](#0-1) 

Because each concurrent call uses its own connection/transaction and there is no mutex on the unit/output key, two racing reveals of the *same* hidden output (e.g., sent once directly by the counterparty and once relayed via a hub, or sent twice deliberately) can both pass the duplicate-check `SELECT` before either transaction commits its `INSERT`/`UPDATE` of the output's address/blinding. Both branches then proceed into `assetModule.validateAndSavePrivatePaymentChain` (`divisible_asset.js`/`indivisible_asset.js`) to validate and write conflicting reveal data for the same physical output.

Contrast this with every other "validate and save" path in the codebase (`composer.js:728-800`, `divisible_asset.js:314-413`, `indivisible_asset.js:825-979`, `network.js:1149-1306`), all of which serialize via `mutex.lock('handleJoint')` before validating/saving a unit. The private-payment reveal path is the outlier that has no equivalent serialization, and the guard that used to exist (`assocUnitsInWork`) was intentionally commented out.

### Impact Explanation
An attacker who is a legitimate (or malicious) private-payment counterparty can send two racing copies of the same private-payment chain reveal (directly and/or via the hub relay path) for the same hidden output. Because the duplicate-detection query and the subsequent write are not atomic and not mutex-protected, both copies can be accepted and separately trigger asset-module save logic that finalizes address/blinding data for the same output/message_index. Depending on how the two reveals differ (e.g. different `output.address`/`blinding` claims), this can corrupt the private chain state for that output, produce two nodes/wallets disagreeing about who legitimately owns the private output, or let the sender attempt to reveal conflicting ownership data that different recipients each treat as valid — a fund-loss/disagreement-on-validity scenario for private, indivisible/divisible asset payments.

### Likelihood Explanation
Reachability requires only sending duplicate/near-simultaneous `private_payment` messages (or one direct + one via-hub relay, which the protocol already supports and forwards — see `forwardPrivateChainsToOtherMembersOfSharedAddresses`/`OutputAddresses` in `wallet.js`), something well within reach of any device that is a private-payment counterparty. No special privilege is needed, and the commented-out guard shows this concurrency-safety mechanism was consciously removed rather than never implemented, increasing confidence this is a genuine gap rather than a false read of intent.

### Recommendation
Re-introduce an in-flight guard (or a `mutex.lock` keyed by `unit + message_index + output_index` or similar) around `validateAndSavePrivatePaymentChain` calls in `network.js:handleOnlinePrivatePayment` and in `private_payment.js`, so that concurrent reveals of the same hidden output are serialized rather than racing across independent DB transactions. At minimum, make the duplicate-check-then-write sequence atomic (e.g., `SELECT ... FOR UPDATE` combined with a mutex, or a unique constraint plus catching write conflicts) instead of relying on an un-synchronized `SELECT` followed by an `INSERT`/`UPDATE` in a separate transaction.

### Proof of Concept
1. Compose a private payment chain that reveals a previously-hidden output (unit `U`, `message_index=M`, `output_index=O`).
2. As the sender/counterparty, send this same `private_payment` message twice in rapid succession to the victim node — once directly and once through a code path that also invokes hub relaying (`handlePrivatePaymentChains`/`forwardPrivateChainsToOtherMembersOfOutputAddresses`), or simply issue two near-simultaneous WebSocket `private_payment` justsayings before the first's transaction commits.
3. Because `handleOnlinePrivatePayment`'s `assocUnitsInWork` guard is disabled (`network.js:2413-2422`) and `validateAndSavePrivatePaymentChain` (`private_payment.js:45-106`) opens independent transactions per call with a non-atomic check-then-write, both calls can pass the "duplicate" `SELECT` check concurrently and each proceed to the asset module's save logic for the same output, resulting in two different reveal writes racing to finalize the same private output's state.
