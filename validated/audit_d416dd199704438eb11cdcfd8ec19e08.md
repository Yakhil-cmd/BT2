### Title
Webhook full_name/owner divergence lets an org's own valid signature enqueue GithubSyncJob against another org's stack - ([File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects a `GitHubApp` and checks the HMAC using only `payload['repository']['owner']['login']` (or `payload['organization']['login']`), while `Handler#stacks`/`#repository_name` resolves the target `Repository` using the independent field `payload['repository']['full_name']`. On a multi-tenant Shipit install these two values are never cross-checked, so a party who legitimately owns one configured GitHub org/webhook_secret can sign a payload whose `full_name` points at a different org's repository.

### Finding Description
The broken binding: `repository_owner (payload.dig('repository','owner','login'))` should equal `owner_of(payload.dig('repository','full_name'))`, but no code enforces this equality.

- `WebhooksController#verify_signature` picks `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(signature, raw_post)` [1](#0-0) , using `repository_owner` derived solely from `owner.login`/`organization.login` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` HMACs the *entire raw body* against that org's `webhook_secret` [3](#0-2) . If the signature matches, the whole payload—including `repository.full_name`—is accepted as trustworthy for that request, but the signature only proves "this org's secret signed this body," not "this org owns the repo referenced by `full_name`."
- Once past `verify_signature`, `PushHandler#process` calls `stacks`, which calls `Repository.from_github_repo_name(repository_name)` [4](#0-3) , and `repository_name` reads `payload.dig('repository','full_name')` directly, never `repository_owner` [5](#0-4) . `Repository.from_github_repo_name` splits `full_name` on `/` and looks up by `owner`/`name` with no relation to which org's secret validated the request [6](#0-5) .
- `PushHandler#process` then iterates matching, non-archived stacks and calls `stack.sync_github(expected_head_sha: params.after)` [7](#0-6) , which (per `test/controllers/webhooks_controller_test.rb`) enqueues `GithubSyncJob` for that stack's id [8](#0-7) .

Attacker request: attacker legitimately administers `attacker-org`, a tenant configured in Shipit with its own `webhook_secret` they know (this is standard multi-tenant configuration, e.g. `secrets_double_github_app.yml` showing multiple orgs each with independent `webhook_secret`) [9](#0-8) . They POST `/webhooks` with `X-Github-Event: push`, a valid `X-Hub-Signature` computed with `attacker-org`'s own secret over a body where `repository.owner.login = "attacker-org"` (so `verify_signature` selects and validates against the correct/known secret) but `repository.full_name = "victim-org/victim-repo"`.

Why existing guards fail: `verify_signature` only authenticates "did the holder of `attacker-org`'s secret sign this body," not "does this body only reference `attacker-org`'s repositories." No model validation, `ExplicitParameters` schema (`PushHandler` only requires `ref`/`after` [10](#0-9) ), or `drop_unhandled_event` step touches this cross-check. `repository_owner` and `repository_name` are two independently attacker-supplied JSON fields with no enforced relationship anywhere in the pipeline.

### Impact Explanation
A tenant that legitimately signs webhooks for their own org can forge a payload that causes Shipit to enqueue `GithubSyncJob` (and by the same handler pattern, other webhook side effects keyed off `full_name`, e.g. PR-related handlers using `from_github_repo_name`) against an entirely different org/repository's stack. This is a payload for one repository mutating another's stack/commit state — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). This is repeatable at will against any repository whose owner/name the attacker can guess or knows (repository names are generally public), and it is not confined to a single victim — any tenant onboarded to the same multi-tenant Shipit instance is at risk from any other tenant.

### Likelihood Explanation
Requires: (1) Shipit deployed in multi-tenant mode with multiple GitHub orgs configured under `secrets.github`, each with its own `webhook_secret` (a supported and demonstrated configuration pattern in this repo's fixtures); (2) attacker legitimately controls one such tenant/org and therefore knows that org's `webhook_secret` (they configured/received it when onboarding). No GitHub, Shipit, or victim secrets are needed. Cost is a single crafted HTTP POST with a valid HMAC over attacker-controlled bytes. This is a design-level omission (missing cross-check), not a probabilistic timing bug, so it is deterministic and repeatable.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`/`#stacks`), enforce that the org used to select/verify the webhook signature matches the owner encoded in `repository.full_name` — e.g., reject the request (422) if `repository_owner.casecmp(payload.dig('repository','full_name')&.split('/')&.first) != 0`. Alternatively, resolve `Repository`/`Stack` scoping in `Handler` using `repository_owner` (the field that was actually cryptographically verified) instead of the unverified `full_name`, or verify that `Repository.from_github_repo_name(repository_name).owner == repository_owner` before processing.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "push signed by org A but full_name pointing at org B's repo enqueues job for org B's stack" do
  victim_stack = shipit_stacks(:shipit) # repository owner/name e.g. "shopify/shipit-engine"

  body = JSON.parse(payload(:push_master))
  body["repository"]["owner"]["login"] = "attacker-org"     # signed org
  body["repository"]["full_name"] = victim_stack.repository.full_name # unrelated victim repo

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", attacker_org_webhook_secret, body.to_json)

  request.headers['X-Github-Event'] = 'push'
  request.headers['X-Hub-Signature'] = signature

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: body["after"]]) do
    post :create, body: body.to_json, as: :json
  end
  # BEFORE fix: job is enqueued for victim_stack despite signature only proving attacker-org's secret.
  # AFTER fix: request should be rejected (422) because repository_owner ("attacker-org") != owner of full_name (victim org).
end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
