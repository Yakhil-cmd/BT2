### Title
Attestor-list update on a `spender_attested` asset permanently freezes coins already held by previously-attested owners - (File: `validation.js`, `storage.js`)

### Summary
For assets defined with `spender_attested: true`, spend-authorization is re-evaluated against the *current* (latest) attestor list every time a payment is validated, instead of the attestor list that was valid when the coins were received. When the asset definer publishes a new `asset_attestors` unit that drops or replaces a previously-trusted attestor, every address whose only attestation came from the removed attestor instantly loses the ability to spend the coins it already legitimately holds — with no path to recover them.

### Finding Description
`validateAttestorListUpdate()` lets the asset definer freely replace the attestor list at any time, with no restriction protecting outstanding balances: [1](#0-0) 

When a spend is validated, `storage.readAsset()` resolves `spender_attested` assets by looking up only the single *latest* `asset_attestors` unit for the asset (`ORDER BY level DESC LIMIT 1`), discarding all older attestor lists: [2](#0-1) 

`filterAttestedAddresses()`/`loadAssetWithListOfAttestedAuthors()` then check whether the spending address is attested **by an attestor in that current list** — attestations issued by an attestor that has since been removed no longer count: [3](#0-2) 

Finally, `validatePaymentInputsAndOutputs()` enforces this check on every input owner at spend time, for both public and private (`fixed_denominations`) payments: [4](#0-3) [5](#0-4) 

This is exactly the pattern described in the reference report: an unprivileged holder legitimately acquired an asset while the eligibility list (whitelist/attestor list) was valid, but a later, one-sided admin action (`whitelistAsset()` in the report, `asset_attestors` update here) invalidates the *exit* check — the check that gates already-existing balances rather than just new issuance/mint. In the reference report, the redeem-path check `whitelistedAssets[asset]` should only gate new PERP openings, not closing of already-open positions; here, the attestor check should only gate *new* attestations of coin ownership, not the spending of coins that were already validly held by a once-attested address.

### Impact Explanation
Any address that received coins of a `spender_attested` asset while attested by attestor A becomes permanently unable to move those coins the moment the asset definer swaps out attestor A for attestor B (e.g., legitimate rotation, compromise recovery, or business-policy change) — unless the holder can also obtain a fresh attestation from an attestor in the new list, which they may have no relationship with and no ability to compel. The funds are frozen at the protocol level with no self-service recovery path: this is a concrete, permanent freezing of assets belonging to a party who has no privilege in and no control over the attestor list, mirroring the "Medium" impact classification of the original report (frozen collateral/positions due to an administrative whitelist change).

### Likelihood Explanation
The asset definer is the only party who can trigger this (via `asset_attestors`), which is a normal, expected, permitted operation for any `spender_attested` asset (attestor rotation, revoking a compromised attestor, changing KYC providers, etc.). Given that attestor lists are explicitly designed to be updatable ("must subsequently publish and update the list of trusted attestors" per the `assets` schema comment), such updates are a realistic, foreseeable administrative action rather than a rare edge case, making the likelihood at least Medium, matching the original report's own likelihood assessment for its analogous whitelist-toggle scenario.

### Recommendation
Do not require attestation strictly against the *current* attestor list when validating spends of already-owned outputs. Instead, either:
- Grandfather ownership: check that the address was attested by *some* attestor list that was valid (defined by the definer) at or before the time the output was created/received, or
- Only apply `spender_attested` restrictions to newly issued outputs / new transfers where the recipient is being validated for the first time, and allow spending of already-received balances regardless of subsequent attestor-list changes (analogous to the report's recommendation to remove the whitelist check specifically from the exit/redeem path while keeping it for new issuance).

### Proof of Concept
1. Definer creates asset `X` with `spender_attested: true` and initial attestor `A1`.
2. `A1` attests address `U` via an `attestation` message referencing `X`'s trust chain.
3. `U` receives a payment of asset `X` (validated successfully because `U` is attested per `filterAttestedAddresses`, `storage.js:1960-1974`).
4. Definer posts a new `asset_attestors` message for asset `X` listing only `A2` (removing `A1`) — allowed unconditionally by `validateAttestorListUpdate`, `validation.js:2829-2848`.
5. `U` attempts to spend the previously received coins. `storage.readAsset()` now resolves the attestor list to `[A2]` only (`storage.js:1917-1946`), and since `U` was never attested by `A2`, `filterAttestedAddresses` returns no match; `validatePaymentInputsAndOutputs` rejects the spend with `"owner address is not attested"` (`validation.js:2506-2507` / `2432-2433`).
6. `U`'s balance of asset `X` is now permanently unspendable unless `A2` (an attestor `U` may have no relationship with) chooses to attest `U`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

// filter only those addresses that are attested (doesn't work for light clients)
function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}

function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
}
