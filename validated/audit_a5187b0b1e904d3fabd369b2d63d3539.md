### Title
Webhook signature verification binds to `repository.owner.login`, while event handlers act on `repository.full_name` — allows cross-organization webhook forgery in multi-app deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) using the payload's `repository.owner.login` field, while the actual event handlers (e.g. `PushHandler`) resolve the target `Repository`/`Stack` using the *different* `repository.full_name` field from the same payload. Because these two fields are never cross-checked, an attacker who can produce a validly-signed payload for *any one* organization configured in a multi-app Shipit deployment can set `repository.full_name` to point at a stack belonging to a completely different organization, and the forged event will be processed against that victim stack.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 

The organization used to pick the verifying `GitHubApp` (and its `webhook_secret`) comes from `repository_owner`: [2](#0-1) 

Shipit explicitly supports multiple, independently-configured GitHub Apps/organizations, each with its own `webhook_secret` (which can even be left `nil`, disabling verification entirely for that org): [3](#0-2) [4](#0-3) 

After the signature check passes, `create` dispatches the full raw payload to handlers keyed only by event type: [5](#0-4) 

Handlers, however, resolve the target repository/stack using a *different* JSON field, `repository.full_name`, not `repository.owner.login`: [6](#0-5) [7](#0-6) 

Because `repository.owner.login` (used to select the verifying secret) and `repository.full_name` (used to select the acted-upon repository/stack) are independent, attacker-controlled fields inside the same JSON body, nothing in the controller enforces that they refer to the same repository/organization. The binding that should hold — "the organization whose secret validated this webhook == the organization that owns the repository being acted upon" — is never checked.

### Impact Explanation
In any Shipit deployment configured with **multiple GitHub Apps for multiple organizations** (the documented "Using Multiple Github Applications" setup), an attacker who controls (or is a legitimate installer of) one configured organization's GitHub App — or who targets an organization whose `webhook_secret` was left unset (`nil`, which is a documented, supported configuration that makes `verify_webhook_signature` always return `true`) — can craft a webhook body that:
- Sets `repository.owner.login` (or `organization.login`) to the organization whose secret they control/know or which is unset, so `verify_signature` passes.
- Sets `repository.full_name` to `victim-org/victim-repo`, a repository belonging to a *different*, victim organization tracked by the same Shipit instance.

This forged payload is then processed by handlers that operate on `repository.full_name`, e.g. `PushHandler`, which calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack of the matched (victim) branch: [7](#0-6) 

This lets an attacker who is not authorized on the victim organization/repository trigger sync/build activity, and in a `continuous_deployment`-enabled stack, kick off unauthorized deploy pipelines for a repository they have no legitimate access to — an unauthorized deploy-adjacent action performed purely by exploiting the mismatch between the field checked for authenticity and the field used to select the acted-upon resource. This matches the High/Critical class of "unauthorized deploy" impact via a broken authentication binding.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (explicitly documented and supported), and (2) the attacker controlling, or being able to send correctly-signed payloads for, at least one of the configured organizations (either because that org's `webhook_secret` is unset, or because the attacker is a legitimate low-trust member/installer of one org but wants to reach another org's stacks on the same Shipit instance). This is a realistic multi-tenant configuration mistake/scenario rather than a purely theoretical one, since the docs explicitly show `webhook_secret:` as optional (commented `# nil`) per-organization.

### Recommendation
After determining `repository_owner` and verifying the signature, re-validate that the organization segment of `repository.full_name` (and/or `organization.login`) matches the `repository_owner`/organization used to select the signing app before dispatching to handlers. Reject (422) any payload where these fields disagree.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgA` (tracked stacks, real secret) and `OrgB` (attacker-controlled or `webhook_secret: nil`), as shown in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker crafts a `push` webhook body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/victim-repo"
  }
}
```
3. Attacker signs the raw body with `OrgB`'s webhook secret (or sends no valid HMAC at all if `OrgB.webhook_secret` is `nil`, since `verify_webhook_signature` returns `true` unconditionally in that case).
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgB")` and passes verification.
5. `Shipit::Webhooks::Handlers::PushHandler` is invoked with the full payload, resolves `Repository.from_github_repo_name("OrgA/victim-repo")`, and enqueues `sync_github` for `OrgA`'s stacks — despite the signature only proving authenticity for `OrgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
