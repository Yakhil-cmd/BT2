### Title
API-token holder can impersonate any Shipit `User` via the unauthenticated `X-Shipit-User` header, breaking the token-vs-identity binding for deploys, rollbacks, aborts and lock attribution - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The API request-signature/identity check binds *only* the `ApiClient` token to the request; the acting `User` identity used for authorship and audit trail (deploys, rollbacks, task aborts, stack locks) is taken directly from a client-supplied HTTP header that is never verified against the authenticated principal.

### Finding Description
`Shipit::Api::BaseController#authenticate_api_client` verifies the caller's `ApiClient` via a signed bearer token (`ApiClient.authenticate`), establishing *which token* is calling. However, `current_user`—the identity attributed to the action—is derived independently and unauthenticated: [1](#0-0) 

`identify_user` simply looks up any `User` row by the login string supplied in the `X-Shipit-User` request header, with no cryptographic binding to the `ApiClient`, its `creator`, or any session. Any valid `ApiClient` token (e.g., a stack-scoped CI token created for `deploy:stack` only) can set this header to the login of an arbitrary Shipit user—including admins/team leads—to have privileged actions attributed to them.

This is exactly the "credential-authorizes-X but action-executes-as-Y" binding break called out in the task: the token authenticates the `ApiClient`, but the `User` object bound to the resulting session-equivalent (`current_user`) is an unverified claim from the payload/header, not the entity the signature covers.

Impact flows into privileged, attributable operations:
- `LocksController#create`/`#update` calls `stack.lock(params.reason, current_user)`, permanently recording the forged user as the one who locked the stack: [2](#0-1) 
- `DeploysController#create` calls `stack.trigger_deploy(commit, current_user, ...)`, attributing (and, depending on deploy authorization/approval logic, potentially authorizing) the deploy as the impersonated user: [3](#0-2) 
- `RollbacksController#create` uses `current_user` both to abort an active task (`aborted_by: current_user`) and to trigger a rollback: [4](#0-3) 

The project's own tests confirm the header is trusted as an authorship claim with no additional check: [5](#0-4) 

### Impact Explanation
This crosses the "GitHub identity versus the `User` bound to the session" boundary named in scope: an `ApiClient` token (which represents a scoped, non-human integration credential) can forge the acting human `User` for every mutating API action that records/relies on `current_user`. Where deploy or lock authorization logic elsewhere in the app depends on team membership or "who is deploying" (e.g., approvals, notifications, `Shipit.github_teams` gated behavior tied to user identity), this allows escalation into that authorization context using nothing but a lower-privileged API token — satisfying the "escalation into `Shipit.github_teams` authorization" High-impact category, and it also causes falsified audit trails for unauthorized deploys/rollbacks/locks attributed to users who never issued them.

### Likelihood Explanation
Trivial to exploit: any holder of any valid `ApiClient` token (not necessarily privileged) can add one arbitrary HTTP header (`X-Shipit-User: <victim-login>`) to any authenticated API call. No knowledge of secrets beyond the caller's own token is required, and the behavior is demonstrably intentional/undocumented-as-risk (it is exercised by the test suite as a normal feature, "claimed user as author").

### Recommendation
Do not allow the identity attributed to an action to be a free-form client-supplied claim. Either:
- Bind `X-Shipit-User` trust to only the `UnlimitedApiClient` / internal-trusted-caller path (never to externally issued `ApiClient` tokens), or
- Restrict which permission scopes/tokens are permitted to set this header (e.g., require an explicit `impersonate:user` permission validated against `check_permissions!`), or
- Cryptographically bind the acting user id into the `ApiClient` token/record itself (e.g., only allow `current_user` to be the token's own `creator`) instead of trusting a header at request time.

### Proof of Concept
1. Create/obtain a `Shipit::ApiClient` token scoped only to `deploy:stack` for stack `S` (no elevated permissions needed).
2. Send `POST /stacks/:s/deploys` with `Authorization: Basic <token>` and header `X-Shipit-User: admin-login`.
3. Observe (as in `test/controllers/api/deploys_controller_test.rb:49-54`) that `Deploy.last.user == User.find_by(login: 'admin-login')`, i.e., the deploy (and any downstream logic keyed on the deploying user) is attributed to `admin-login` despite the request never authenticating as that user.
4. The same technique applies to `LocksController#create/#update` (`stack.lock(reason, current_user)`) and `RollbacksController#create` (`aborted_by: current_user`, `trigger_rollback(current_user, ...)`), forging attribution/authorization context for those privileged operations as well.

```ruby
      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
```
