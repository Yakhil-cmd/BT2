This confirms the vulnerability. The `WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to validate against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). But the event handlers that act on the payload (e.g. `PushHandler`, and the PR handlers) resolve the target `Repository`/`Stack` using an entirely different field: `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name`. Since the raw JSON body is attacker-controlled up to the point where a valid signature is produced, and Shipit supports multiple independent GitHub Apps/organizations each with their own `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications" section), these two fields are never cross-checked against each other or against the organization actually owning the targeted repository.

### Title
Webhook signature verified against attacker-chosen organization while handlers act on an unbound `repository.full_name` — cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments (`docs/setup.md` "Using Multiple Github Applications"), each configured GitHub organization has its own `GitHubApp` instance and `webhook_secret`. `WebhooksController#verify_signature` picks which app/secret to validate the HMAC against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')` [1](#0-0)  and `Shipit.github(organization: repository_owner)` [2](#0-1) . The actual event handlers, however, resolve the target repository/stack using a *different, independent* payload field: `payload.dig('repository', 'full_name')` in the base `Handler#repository_name` [3](#0-2) , and equivalently in `PullRequest::*Handler#repository` methods that call `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [4](#0-3) . `Repository.from_github_repo_name` looks up purely by `owner`/`name` parsed from that string with no relation back to whichever organization's secret validated the request [5](#0-4) .

### Finding Description
The equality that should hold is: `organization whose webhook_secret authenticated the signature == organization owning the repository the handler mutates`. Nothing in the request pipeline enforces this. `verify_signature` reads `repository.owner.login` (or `organization.login`) purely to select the `webhook_secret` used for HMAC verification [2](#0-1) . The signature itself covers the raw POST body, but it is validated per-organization, not tied to the specific `full_name` acted upon later. An attacker who is a legitimate, unprivileged member/collaborator of "OrgA" (and therefore able to trigger real GitHub webhooks — pushes, PR events — from a repository they control in OrgA) can capture (or otherwise produce) a validly-HMAC-signed webhook body for OrgA, then submit a crafted JSON body directly to Shipit's `/webhooks` endpoint where `repository.owner.login` is `"OrgA"` (so `verify_signature` uses OrgA's `webhook_secret`, matching the attacker's known signature) while `repository.full_name` is set to `"OrgB/some-other-repo"` — a stack belonging to a completely different organization the attacker has no access to. Because `verify_signature` and the handlers key off two different fields of the same untrusted JSON, and no code cross-checks that the `full_name` repository actually belongs to the organization identified by `repository_owner`, the forged event is processed against OrgB's stack.

For `PushHandler`, this results in `stack.sync_github(expected_head_sha: params.after)` being invoked against an arbitrary OrgB stack/branch with an attacker-chosen `after` SHA [6](#0-5) , which can trigger unwanted resyncs/deploys of arbitrary commits into a stack the attacker doesn't own. For PR handlers such as `OpenedHandler`/`LabeledHandler`/`ClosedHandler`, this allows an attacker to provision, archive, or unarchive review stacks belonging to OrgB by forging `full_name` while authenticating under OrgA's key [7](#0-6) .

### Impact Explanation
This breaks the binding between "organization that authenticated the webhook" and "repository the handler writes to," letting an attacker who legitimately controls webhook delivery for one onboarded organization forge deploy/rollback/provisioning-affecting events (unauthorized `sync_github`, review-stack archive/unarchive/provision) against stacks belonging to a different organization onboarded to the same Shipit instance — a cross-organization write achieved without ever needing that organization's `webhook_secret`.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (explicitly documented and supported, `docs/setup.md` "Using Multiple Github Applications") and requires the attacker to be able to produce a validly-signed payload for at least one onboarded organization (e.g., by being a contributor able to trigger real webhook deliveries from a repo in that org, or if that org's `webhook_secret` is unset/blank, in which case `verify_webhook_signature` returns `true` unconditionally) [8](#0-7) . The `webhook_secret` field is documented as optional throughout the setup docs and example config [9](#0-8) , making the "no-secret" variant plausible in real deployments.

### Recommendation
After verifying the HMAC, cross-check that the resolved `Repository`/`Stack` for `payload.dig('repository', 'full_name')` actually belongs to the same organization (`repository_owner`) that was used to select the verifying `GitHubApp`/`webhook_secret`, and reject the event (422) if they diverge. Alternatively, look up the target stack's configured organization first and always verify against that organization's secret rather than trusting an organization value taken from the same untrusted payload used to pick the repository.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`).
2. As a contributor to a repo in `OrgA`, obtain a validly HMAC-signed webhook body for a `push` event (or note that `OrgA`'s `webhook_secret` is blank, since `verify_webhook_signature` returns `true` when no secret is set).
3. Craft a JSON body where `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/target-repo"`, and send it to `POST /webhooks` with `X-Github-Event: push` and a signature valid for OrgA's secret (or no secret needed if blank).
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and passes [2](#0-1) ; `PushHandler` then resolves the stack via `Repository.from_github_repo_name("OrgB/target-repo")` and calls `stack.sync_github` on OrgB's stack [6](#0-5) , achieving an unauthorized cross-organization resync/deploy trigger.
