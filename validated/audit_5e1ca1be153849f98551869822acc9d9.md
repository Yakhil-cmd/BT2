### Title
Cross-organization webhook forgery via mismatched signature-selection field and repository-targeting field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to verify a webhook by reading `repository.owner.login` (falling back to `organization.login`) out of the **unverified** request body, then verifies the HMAC using that org's secret. Once verification succeeds, `Shipit::Webhooks::Handlers::Handler#stacks` resolves the target `Repository`/`Stack` using a **different** field from the same body — `repository.full_name` — via `Repository.from_github_repo_name`. In a multi-org Shipit deployment (`docs/setup.md` "Using Multiple Github Applications", `config/secrets.development.shopify.yml`), each organization has its own `webhook_secret`. Nothing ties "the org whose secret validated this HMAC" to "the org whose repository the payload claims to target," so anyone who knows one org's webhook secret can forge a payload naming a completely different org's repository/stack.

### Finding Description [1](#0-0)  verifies the raw body signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is taken straight from the JSON body: [2](#0-1) 

`Shipit.github` resolves per-organization secrets in multi-app mode: [3](#0-2) 

`verify_webhook_signature` only proves the raw body was HMAC-signed with *that org's* secret: [4](#0-3) 

After verification passes, `create` dispatches to handlers with the same raw parsed body: [5](#0-4) 

But every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers, etc.) resolves which `Stack`/`Repository` to act on via `Handler#stacks`, which reads a **different key**, `repository.full_name`: [6](#0-5) [7](#0-6) 

Nothing constrains `repository.full_name`'s owner to equal `repository.owner.login`/`organization.login` — the field the signature check used to select the verifying secret. Since the whole raw body (including both fields) is what gets HMAC'd, an attacker who legitimately knows **any one** configured organization's `webhook_secret` (e.g., they administer that org's GitHub App settings page, a normal, unprivileged-relative-to-other-tenants capability in a multi-org Shipit install) can freely craft the JSON body — setting `repository.owner.login`/`organization.login` to their own org (so `verify_signature` selects their own known secret and passes), while setting `repository.full_name` to `otherOrg/target-repo`, which is a completely different organization's repository configured as a Stack in the same Shipit instance.

This breaks exactly the binding called out: *"an organization that authenticated versus the repository that is written."* The signature only authenticates "sender knows OrgB's webhook_secret"; the code acts on "repository under OrgA," with no check that OrgA's secret was the one used.

### Impact Explanation
With a forged, HMAC-valid-for-OrgB payload naming an OrgA repo:
- `push` events drive `PushHandler#process` → `stack.sync_github(expected_head_sha: ...)` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), forcing a GitHub sync/deploy-spec recache cycle for a stack the attacker has no legitimate relationship to.
- `status` events drive `StatusHandler#process` → `commit.create_status_from_github!(params)` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), letting the attacker inject arbitrary CI status text/state for commits on the victim's stack, which Shipit uses to gate deploys/merges.
- `check_suite` events drive `CheckSuiteHandler#process` → `schedule_refresh_check_runs!` for the victim stack's commits (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`), able to trigger refresh cycles cross-tenant.

Because `stack.github_app`/`Repository#github_app` resolve credentials from the real `repository.owner` DB column (not attacker input) when performing follow-on GitHub API calls, the attacker cannot exfiltrate OrgA's token directly, but they can force out-of-band syncs, spoof status data used to gate deploy/merge decisions, and disturb CI-refresh state for a repository/org they have no access to — an unauthorized-deploy-adjacent, cross-organization write into another tenant's stack state. This lands in the High/Critical impact bucket ("unauthorized deploy" / cross-repository writes) depending on how far `create_status_from_github!` and continuous-deployment gating trust these injected statuses.

### Likelihood Explanation
Requires that the Shipit instance is configured with multiple GitHub organizations sharing one webhooks endpoint (an explicitly documented, supported configuration in `docs/setup.md`), and that the attacker controls (or is an admin of) at least one of those organizations' GitHub Apps — a realistic scenario for shared/hosted Shipit deployments serving several tenant orgs. No Shipit session, API token, or GitHub App private key for the *target* org is needed; only knowledge of one's *own* org's webhook secret, which by design every onboarded org possesses.

### Recommendation
After computing `repository_owner` for secret selection, re-verify that the same value equals the owner encoded in `repository.full_name` (or, better, resolve the target `Repository`/`Stack` and require its stored `owner` to match the organization whose secret validated the signature) before dispatching to handlers. Reject the webhook if the two disagree.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-app schema).
2. Attacker administers `OrgB`'s GitHub App and thus knows `OrgB`'s `webhook_secret`.
3. Attacker crafts a `push` payload body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(OrgB_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` reads `repository.owner.login == "OrgB"`, fetches `Shipit.github(organization: "OrgB")`, verifies the HMAC successfully (attacker knows this secret) — request passes.
6. `PushHandler#process` calls `Handler#stacks`, which resolves `Repository.from_github_repo_name("OrgA/victim-repo")` and finds `OrgA`'s real stack, triggering `stack.sync_github` on a repository/org the attacker does not control.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
