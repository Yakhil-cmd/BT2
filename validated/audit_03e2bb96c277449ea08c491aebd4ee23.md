### Title
Webhook signature validated against `repository.owner.login`, but events are dispatched to a Stack looked up by the unverified `repository.full_name` — allows cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate the incoming payload against using `repository_owner`, computed from the same untrusted JSON body (`params.dig('repository', 'owner', 'login')`). Once the signature check passes, `Handlers::Handler#stacks` resolves the actual `Stack`/`Repository` to act on using a *different* field from the same payload: `payload.dig('repository', 'full_name')`. Because Shipit supports multiple independently-configured GitHub organizations sharing one instance (each with its own `webhook_secret`), an attacker who legitimately controls the webhook secret for **one** configured organization can forge a payload whose `repository.owner.login` matches their own org (so the signature validates against a secret they know) while `repository.full_name` points at a completely different organization's repository/stack. This is exactly the "organization that authenticated versus the repository that is written" trust binding described in the prompt's exploitable class list — mirroring the Timeswap bug where the value used for one step's calculation (`pool.long0Balance`) diverged from the value that should have gated it (`pool.long1Balance`).

### Finding Description
- `verify_signature` in [1](#0-0)  picks the GitHub App/secret via `Shipit.github(organization: repository_owner)`, where: [2](#0-1) 
- Shipit explicitly supports multiple GitHub organizations, each with its own independent `webhook_secret`, sharing a single Shipit deployment, as documented and fixtured: [3](#0-2)  and [4](#0-3) .
- The signature check itself only proves the raw body was HMAC-signed with *some* org's secret, chosen by the attacker-controlled `repository.owner.login`: [5](#0-4) .
- After the signature passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full payload to handlers: [6](#0-5) .
- Every handler resolves which `Stack`(s) to mutate using `Repository.from_github_repo_name(repository_name)` where `repository_name` comes from a *different* JSON key, `repository.full_name`, not the one used for signature selection: [7](#0-6) .
- Nothing cross-checks that `repository.owner.login` (used to select/authenticate the secret) equals the owner embedded in `repository.full_name` (used to select which org/repo's Stack is affected).

### Impact Explanation
An attacker who has legitimately installed the Shipit GitHub App on their own organization (and thus knows/possesses that org's `webhook_secret`, a normal, unprivileged setup step available to any org admin who wants to use Shipit for their own repos) can sign an arbitrary payload with their own org's secret while spoofing `repository.full_name` to point at a Stack belonging to an entirely different, victim organization configured on the same Shipit instance. Handlers such as the status handler write attacker-controlled commit status/state directly into the database keyed off the spoofed repository/commit, as shown by the existing status-handling behavior: [8](#0-7) . Since Shipit gates deploys/merges on commit CI status, this allows an attacker without any access to the victim organization to inject a fabricated "success" status for a victim commit, bypassing CI checks that would otherwise block an unauthorized deploy or merge for that stack — a cross-organization write and an unauthorized-deploy enabler, matching the Critical/High impact classes in scope (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Any actor who can install the Shipit GitHub App on an org they control (an unprivileged, self-service action, not requiring any credential belonging to Shipit operators or the victim org) automatically obtains a valid `webhook_secret` for that org. Crafting a payload with mismatched `owner.login` vs `full_name` requires no special access beyond that — only knowledge of the victim repository's name and a target commit SHA, both public information for public repos. This is a realistic, low-effort path once the multi-org configuration (explicitly documented and supported) is in use.

### Recommendation
In `WebhooksController#verify_signature` / `Handlers::Handler`, derive the organization used to select the webhook secret and the repository owner used to select the Stack from the **same, single trusted value**, and explicitly assert that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatching to any handler. Reject the webhook (422) if they diverge.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `AttackerOrg` and `VictimOrg`, each with independent `webhook_secret`s (supported configuration per `docs/setup.md`).
2. Attacker installs/administers the Shipit GitHub App on `AttackerOrg` and thus knows `AttackerOrg`'s `webhook_secret`.
3. Attacker crafts a `status` (or `push`) webhook JSON body:
   ```json
   {
     "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/victim-repo" },
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "target_url": "https://example.com",
     "description": "forced green"
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(AttackerOrg_webhook_secret, raw_body)` and POSTs to `/github/webhooks`.
5. `verify_signature` resolves `repository_owner` = `"AttackerOrg"`, looks up `AttackerOrg`'s secret, and the HMAC matches — request is accepted.
6. `Handlers::Handler#stacks` resolves the target using `repository.full_name` = `"VictimOrg/victim-repo"`, and the status handler creates a fabricated "success" status against `VictimOrg`'s stack/commit, which the attacker never had a credential for.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
