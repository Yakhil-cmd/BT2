### Title
Webhook signature-verification target selection is not bound to the payload's `repository`/`organization` object it authorizes, allowing forged unsigned events to be processed as belonging to any tracked repo or org - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects **which GitHub App/organization secret** to verify a webhook with by reading `repository_owner` out of the *unverified* JSON body, then calls `github_app.verify_webhook_signature`. But `Shipit::GithubApp#verify_webhook_signature` returns `true` unconditionally when that selected app has no `webhook_secret` configured. The event handler that actually acts on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name` / `#stacks`, used by `PushHandler`, `MembershipHandler`, `PullRequest::*Handler`, etc.) reads a *different* field — `repository.full_name` (or `organization.login` for membership events) — to decide which `Stack`/`Team`/`Repository` to mutate. Nothing binds the two lookups together: the "authenticator" (`repository_owner`, used to pick the verifying secret) and the "target being written" (`repository.full_name` / `organization.login`, used by the handler) are independent fields inside the same unauthenticated JSON body.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
head(422) unless verified
```
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`GithubApp#verify_webhook_signature` is:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

Shipit natively supports multiple GitHub organizations/apps configured side by side, each with its own optional `webhook_secret` (`webhook_secret` is documented as optional, "if you've set" one) — see the sample multi-org config [4](#0-3)  and setup docs [5](#0-4) .

Once `verify_signature` passes (either because the org resolved from `repository_owner` has no `webhook_secret` configured, or degenerates to `true`), the raw `params` hash — fully attacker-controlled JSON, since HMAC verification never inspected `repository.full_name`/`organization.login` at all, only `repository.owner.login`/`organization.login` used for app selection — is dispatched unchanged to the handler:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
end
``` [6](#0-5) 

Handlers resolve the object to mutate from a *different* field than the one used to select the verifying secret:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) 

For membership events, `MembershipHandler#process` creates/loads a `Team` scoped by `params.organization.login` and adds an arbitrary `member.login` to it:
```ruby

  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added'
    team.add_member(member)
  ...
end

def find_or_create_team!

    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [8](#0-7) 

Team membership drives the app-wide authorization gate:
```ruby

end
``` [9](#0-8) 
which is enforced in `force_github_authentication`:
```ruby
elsif Shipit.authentication_disabled? || current_user.logged_in?

    ... forbidden ...
  end
``` [10](#0-9) 

**Equality broken:** `organization/repository whose secret authenticated the request` (`repository_owner` → `Shipit.github(organization: repository_owner)`) is treated as if it equals `organization/repository the handler actually writes to` (`params.organization.login` / `params.dig('repository','full_name')`). These are independent, attacker-supplied JSON fields in the same unauthenticated body, so the equality does not hold.

### Impact Explanation
If a Shipit deployment tracks more than one GitHub organization (a documented, supported configuration) and any one of them has no `webhook_secret` configured (also a documented, optional setting) — or more generally, once *any* configured org's `verify_webhook_signature` is satisfied — an unprivileged remote attacker can `POST` a crafted body to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) set to the unsecured/known org, to satisfy `verify_signature`,
- `organization.login` (membership event) or `repository.full_name` set to a **different, victim** org/stack that Shipit also tracks and that is protected with `Shipit.github_teams`.

This lets the attacker forge a `membership` event that adds an arbitrary GitHub login (including their own) to a `Team` whose `github_id` and `organization` correspond to one of `Shipit.github_teams`, escalating any authenticated GitHub identity into the app's privileged team-based authorization gate — satisfying the High severity bar "escalation into `Shipit.github_teams` authorization." It can also forge `push`/`pull_request`/`status`/`check_suite` events against arbitrary tracked stacks, triggering unwanted sync/status/archival side effects on repositories the attacker does not control.

### Likelihood Explanation
Exploitability requires: (1) the Shipit instance to track ≥2 GitHub orgs/apps (a first-class, documented feature, not a misconfiguration of "not mounting the engine as documented"), and (2) at least one of them to have no `webhook_secret` set (explicitly optional per the setup docs). Both conditions are within normal, documented operation, not a departure from the documented deployment model, so this is reachable without any credential, session, or token — only network access to `/webhooks`.

### Recommendation
Bind signature verification to the same object the handler will act on: verify against the organization/owner derived from `repository.full_name` (or `organization.login` for org-scoped events), not a loosely-coupled `repository.owner.login`/`organization.login` lookup that differs from the field the handler subsequently trusts. Additionally, do not silently treat a missing `webhook_secret` as verification success; require an explicit, auditable opt-in (e.g., `Shipit.disable_webhooks_authentication`) rather than defaulting `verify_webhook_signature` to `true`.

### Proof of Concept
1. Configure Shipit with two organizations, `secured-org` (has `webhook_secret`) and `victim-org` (also has `webhook_secret`), plus `Shipit.github_teams` referencing a team in `victim-org`.
2. Configure (or find) a third tenant org `unsecured-org` without `webhook_secret` set (per the documented optional field).
3. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": <victim team's github_id>, "name": "Cooks", "slug": "cooks", "url": "https://example.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "unsecured-org" } }
}
```
Since `repository_owner` resolves to `unsecured-org`, `Shipit.github(organization: 'unsecured-org').verify_webhook_signature` returns `true` regardless of the (missing/incorrect) `X-Hub-Signature` header, per `return true unless webhook_secret` [11](#0-10) . `MembershipHandler` then adds `attacker-github-login` to the `victim-org` team tied to `Shipit.github_teams`, granting authorization to log in and use the app [12](#0-11) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
