### Title
Cross-organization GitHub App client/token confusion via thread-local caching in `GitHubApp#api` - (File: lib/shipit/github_app.rb)

### Summary
`Shipit.github(organization:)` memoizes one `GitHubApp` instance per organization [1](#0-0) , and each instance has its own installation token via `fetch_new_token`, keyed correctly per-organization in `Rails.cache` [2](#0-1) . However, the Octokit client used to actually call the GitHub API is cached in a single global, unscoped `Thread.current[:github_client]` slot inside `GitHubApp#api`, shared across every `GitHubApp` instance that happens to run on that thread: [3](#0-2) .

### Finding Description
This mirrors the CVE-2026-8927 bug class: authentication state established for one "destination" (a proxy in curl, here an organization/GitHub App) survives a switch to another destination on the same reusable handle (a curl easy-handle in curl, here an application thread in Puma/Sidekiq).

The binding that should hold is: `organization that authenticated the app instance == organization whose GitHub App the returned Octokit client actually represents`. Concretely, `new_client` configures `api_endpoint`/`web_endpoint` from `enterprise?`/`domain`, which are instance attributes set once in `initialize` per-organization config [4](#0-3) [5](#0-4) .

When Shipit is configured with the multi-organization schema (documented, in-scope, standard configuration) [6](#0-5) :

1. Thread T handles an operation for `orgA` (e.g. webhook/job for `orgA`'s repository) and calls `Shipit.github(organization: 'orgA').api`. This creates and caches an Octokit client in `Thread.current[:github_client]`, configured with `orgA`'s `api_endpoint`/`web_endpoint`/middleware, and `access_token = orgA's installation token`.
2. The same thread T is reused (standard Rails/Sidekiq thread-pool behavior) to handle a subsequent operation for `orgB`, e.g. `Shipit.github(organization: 'orgB').api` (a distinct `GitHubApp` instance).
3. Inside `#api`, `Thread.current[:github_client] ||= ...` short-circuits because the slot is already populated with `orgA`'s client — no new client is built for `orgB`.
4. The code updates only `client.access_token = token` (now `orgB`'s token, since `self` is the `orgB` instance) [7](#0-6) , but the underlying `Octokit::Client` object — its `api_endpoint`, `web_endpoint`, and Faraday middleware stack — remains `orgA`'s.

Before the attacker's request sequence: each org's client/token pair is internally consistent (`orgX` token → `orgX` endpoint). After the sequence: `orgB`'s freshly-minted installation access token is attached to a client still pointed at `orgA`'s `api_endpoint`/`web_endpoint`. If `orgA` is configured with a custom Enterprise `domain` (attacker-influenced or a lower-trust tenant in a shared Shipit deployment), `orgB`'s live GitHub App installation token — a credential scoped to `orgB`'s repositories — is transmitted to `orgA`'s host on every subsequent API call from that thread, until the thread happens to serve `orgB` first again.

Root cause: `Thread.current[:github_client]` is a single unscoped slot shared by all `GitHubApp` instances, while `Shipit.github` legitimately creates one `GitHubApp` object per organization [8](#0-7) ; nothing keys the thread-local cache by organization or by the requesting `GitHubApp` instance's identity/domain, so the cached client (and its endpoint configuration) survives across organization boundaries.

### Impact Explanation
This crosses the "a stack a token authorises versus a stack it touches" / cross-organization credential boundary: `orgB`'s live installation access token (equivalent in sensitivity to `GITHUB_TOKEN`) is sent to `orgA`'s endpoint (SSRF-with-credentials to another configured, potentially lower-trust or attacker-influenced Enterprise `domain`), and API calls made in `orgB`'s name execute against `orgA`'s host, enabling exfiltration of `orgB`'s installation token by whoever controls `orgA`'s GitHub Enterprise endpoint. In a shared multi-tenant Shipit deployment this is a real credential-exfiltration / cross-organization-write vector, matching the Critical bar (exfiltration of a GitHub credential functionally equivalent to `GITHUB_TOKEN`).

### Likelihood Explanation
Requires the documented multi-organization `github:` configuration (which is a normal, supported deployment mode, not a misconfiguration) and normal thread reuse under Puma/Sidekiq, which is the default runtime behavior — no attacker privilege, session, or API token is needed to trigger it; it happens purely from ordinary interleaved traffic/jobs for two configured organizations landing on the same worker thread.

### Recommendation
Scope the cached client by organization/instance identity instead of a single global thread-local slot — e.g. key `Thread.current[:github_clients]` by `@organization` (or by `object_id` of the `GitHubApp` instance), and always rebuild (or re-verify `api_endpoint`/`web_endpoint`) rather than only refreshing `access_token`, mirroring how `fetch_new_token`'s cache key already includes the organization.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `orgA` with `domain: attacker-enterprise.example.com`, `orgB` with the default `github.com` domain, per the documented multi-org format [6](#0-5) .
2. On a given worker thread, trigger any code path that calls `Shipit.github(organization: 'orgA').api` first (e.g. a webhook or job touching an `orgA` repo, routed via `repository_owner` in `WebhooksController#verify_signature` / job handlers) [9](#0-8) .
3. On the same thread, trigger a code path for `orgB` (e.g. `Shipit.github(organization: 'orgB').api.create_status(...)`).
4. Observe (via a request log on `attacker-enterprise.example.com`, since `new_client`'s `api_endpoint`/`web_endpoint` came from `orgA`) that the HTTP request intended for `github.com` on behalf of `orgB` is instead sent to `attacker-enterprise.example.com`, carrying `orgB`'s fresh installation access token in the `Authorization` header.

    def fetch_new_token
      cache_key = @organization.nil? ? '' : "#{@organization.downcase}:"
      # Rails can add 5 minutes to the cache entry expiration time when any TTL is provided,
      # so our TTL setting can be lower, and TTL + expires_in should be lower than the GitHub token expiration.
      Rails.cache.fetch(
        "github:integration:#{cache_key}access-token",
        expires_in: GITHUB_TOKEN_RAILS_CACHE_LIFETIME,
        race_condition_ttl: 4.minutes
      ) do
        response = new_client(bearer_token: authentication_payload).create_app_installation_access_token(
          installation_id
        )
        token = Token.from_github(response)
        raise AuthenticationFailed if token.blank?

        Rails.logger.info("Created GitHub access token ending #{token.to_s[-5..]}, expires at #{token.expires_at}"\
          " and will be refreshed at #{token&.refresh_at}")
        token
      end
    end

If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
