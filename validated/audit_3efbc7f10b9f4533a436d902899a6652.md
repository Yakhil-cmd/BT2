### Title
`AddressRegistrar::register` retains excess attached deposit instead of refunding it to the caller - (File: runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs)

### Summary
The `register` method of the `AddressRegistrar` contract (part of the ETH-implicit "Wallet Contract" system shipped in this nearcore repo) is a `#[payable]` method that requires the caller to attach at least `required_deposit` yoctoNEAR to cover storage costs. When the caller attaches more than `required_deposit` and registration succeeds (the `Entry::Vacant` branch), the contract keeps the entire `given_deposit` instead of refunding the excess above `required_deposit`. This mirrors the RubiconRouter "excess ether not returned" bug class: the contract silently keeps user overpayment.

### Finding Description
In `register()`, the contract computes `required_deposit` from the storage bytes needed and compares it to `given_deposit = env::attached_deposit()`, panicking only if `given_deposit < required_deposit` [2](#0-1) . If the deposit is sufficient and the address slot is vacant, the entry is inserted and the function returns `Some(address)` without ever transferring back `given_deposit - required_deposit` [3](#0-2) . By contrast, in the `Entry::Occupied` (collision) branch, the code explicitly refunds the *entire* `given_deposit` back to `predecessor_account_id` via a `Transfer` action, showing that the developers were aware refunds were needed but only implemented it for the failure path, not the "overpaid success" path [4](#0-3) . This is a NEAR-native analog to the RubiconRouter `msg.value > required` issue: NEAR's protocol-level `attached_deposit` mechanic fully credits the deposit to the receiving account before contract execution starts (per the Economics API docs) [5](#0-4) , so it is up to the contract itself to refund unused deposit, which `register()` fails to do in the success path.

### Impact Explanation
Any unprivileged account calling `register` with a deposit larger than the exact required storage cost permanently loses the excess to the `AddressRegistrar` contract, with no path to reclaim it. Given that the recommended pattern from tests (`test_register_without_deposit`) attaches a fixed, hard-coded `deposit_amount` rather than the precise on-chain-computed `required_deposit`, callers integrating with this contract (including the `WalletContract`'s relayer flow) are likely to overpay in practice, resulting in unauthorized loss of user funds to the contract's own balance. This is a real, unauthorized balance change caused directly by protocol-adjacent contract logic reachable from an ordinary function-call transaction.

### Likelihood Explanation
High likelihood: the vulnerable code path is reachable by any account submitting a plain `FunctionCall` transaction to `register`, requires no privileged role, and the only precondition is attaching more NEAR than the exact byte-cost of storing the account id (an easy, common mistake given callers must estimate `account_id.len()` in advance, e.g. via the `test_register_without_deposit` test which itself attaches a deposit larger than strictly necessary).

### Recommendation
In the `Entry::Vacant` success branch of `register`, after computing `required_deposit`, calculate `excess = given_deposit - required_deposit` and issue a `Transfer` promise back to `env::predecessor_account_id()` for `excess` (mirroring the refund logic already present in the `Entry::Occupied` branch), or alternatively require `given_deposit == required_deposit` and reject calls that overpay.

### Proof of Concept
1. Call `AddressRegistrar::register({"account_id": "birchmd.near"})` attaching a deposit deliberately larger than `storage_byte_cost * (20 + len("birchmd.near"))`, e.g. as done with `deposit_amount = NearToken::from_yoctonear(320000000000000000000)` in the existing test [6](#0-5) .
2. Observe the registration succeeds and returns the computed address.
3. Observe the registrar contract's balance increased by the *full* `deposit_amount`, not just `required_deposit`, as asserted by the test itself: `post_tx_account_balance.as_yoctonear() - pre_tx_account_balance.as_yoctonear() >= deposit_amount.as_yoctonear()` [7](#0-6) .
4. No refund transaction is ever generated for the excess, unlike the collision-refund path [8](#0-7) .
