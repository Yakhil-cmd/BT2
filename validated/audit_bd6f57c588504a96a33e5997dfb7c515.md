### Title
Webhook signature is verified against the organization named in the payload while the write target is a repository field never covered by that check - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which per-organization `webhook_secret` to validate the HMAC signature against using `repository_owner`, taken from `payload.dig('repository','owner','login')` or falling back to `payload.dig('organization','login')` [3](#0-2) . Every event handler, however, resolves the stack to act on using a completely different field: `payload.dig('repository', 'full_name')` [4](#0-3) . Because `repository.owner.login` and `repository.full_name` are independent JSON fields inside the same signed payload, an attacker who legitimately owns/administers one organization (and therefore knows that organization's `webhook_secret`, which is entirely normal for any GitHub App owner) can sign a payload whose `repository.owner.login`/`organization.login` says their own org, but whose `repository.full_name` names a repository belonging to a different, victim organization tracked by the same Shipit instance.

### Finding Description
This is the direct binding this engine is supposed to enforce: **the organization whose secret authenticated the request == the organization whose repository is written to**. The code breaks that equality:

- Signature check: `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)` where `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')` [5](#0-4) .
- Handler dispatch/target resolution: `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [4](#0-3) .
- `PushHandler#process` uses that same `stacks` scope (derived from `full_name`) to call `stack.sync_github(expected_head_sha: params.after)` [6](#0-5) , and the pull-request handlers similarly resolve `repository` from `params.repository.full_name` to archive/unarchive/create review stacks [7](#0-6) .

Multi-tenant support is real, not hypothetical: `Shipit.github_app_config(organization)` indexes into `secrets.github` by organization name, and `Shipit.github_organizations` enumerates all configured orgs [2](#0-1) . Each organization's GitHub App has its own `webhook_secret` [8](#0-7) , verified with `verify_webhook_signature` [9](#0-8) . So in a Shipit instance tracking multiple organizations' repositories, org A's own legitimately-configured GitHub App will deliver correctly-signed webhooks whose `repository.owner.login` is `"A"`. Nothing stops an attacker who controls org A's webhook delivery (e.g., by triggering any webhook-eligible event in their own org's repo, or simply by being the org A GitHub App owner and crafting the HTTP request directly with a valid HMAC using A's known secret) from setting `repository.full_name` to `"victim-org/some-repo"` in that same payload before signing/sending it, since the signature covers the raw body but the verification step never cross-checks that the `repository.owner.login` used for secret selection matches the `repository.full_name` used for target resolution.

### Impact Explanation
This lets an attacker who only has authenticated webhook standing for their own (unprivileged, unrelated) organization forge push/pull_request events that are treated as validly signed for a **different** organization's repository. Concretely: `push_handler.rb` will call `stack.sync_github(expected_head_sha: params.after)` for the victim's stack based on attacker-controlled `after` (SHA) and `ref` fields [10](#0-9) , and PR handlers can archive/unarchive/create review stacks belonging to the victim org's repository [7](#0-6) . This is a cross-organization write into another tenant's stack state driven by a signature that was never actually bound to that tenant, satisfying the "cross-repository writes" high/critical impact bar.

### Likelihood Explanation
Requires the Shipit instance to be configured for more than one GitHub organization (a documented, supported configuration per `github_organizations`/`github_app_config`) and requires the attacker to control (or own) at least one of those organizations' webhook secret — which is the normal, expected level of access any org owner has over their own App installation. No repository write access, GitHub App private key, or Shipit session/API token is needed to exploit the target organization; only knowledge of one's own organization's `webhook_secret`, which by design an org's admins are meant to have.

### Recommendation
After selecting the GitHub App / secret via `repository_owner`, `verify_signature` must also assert that the resolved app's organization matches the organization implied by `repository.full_name` (i.e., `full_name.split('/').first == repository_owner`, case-insensitively) before dispatching to handlers. Reject the webhook (422) on mismatch. Alternatively, always look up the app/secret from a single authoritative field (e.g., derive owner strictly from `full_name`) so there is exactly one field driving both authentication and authorization.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `github.orgA.webhook_secret` / `github.orgB.webhook_secret`, and a stack tracking `orgB/victim-repo`.
2. As the (legitimate) owner/admin of `orgA`, know `orgA`'s `webhook_secret`.
3. Craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
   }
   ```
4. Sign the raw body with `orgA`'s `webhook_secret` using HMAC-SHA1 as done in `Hook::DeliverySigner`/`verify_webhook_signature` [9](#0-8) , and send it to `/webhooks` with header `X-Hub-Signature`.
5. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s app, and the signature validates successfully [3](#0-2) .
6. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` [4](#0-3)  and calls `stack.sync_github(expected_head_sha: <attacker sha>)` on the victim org's stack [6](#0-5)  — a write to `orgB`'s stack authenticated only by `orgA`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
