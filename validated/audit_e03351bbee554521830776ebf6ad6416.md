## Analysis

Confirmed: `validateAndSaveUnit` runs full validation on the AA-composed unit at `aa_composer.js:1408`, and this includes `validatePaymentInputsAndOutputs` in `validation.js`, which enforces that every output address of a `spender_attested` asset must be attested by the asset's designated attestor(s) (`validation.js:2630-2641`, using `storage.filterAttestedAddresses`). If validation fails, `bounce(err)` is invoked, which discards the entire response (including any refund), but the AA's earlier balance update from the trigger (already a stable, accepted unit) is not reversed — the asset remains stuck in the AA's balance forever.

### Title
Non-Attested Recipient Permanently Freezes `spender_attested` Asset Funds in an AA - ([File: aa_composer.js])

### Summary
An asset can be defined with `spender_attested: true`, requiring that *every* payment output address (not just the spender) be attested by a fixed list of attestor addresses (`storage.js:1898-1993`, `validation.js:2630-2641`). If an Autonomous Agent (AA) holds a balance of such an asset (received legitimately from an already-attested sender) and its oscript later tries to pay this asset back to `trigger.address` or any other address that is not attested by the asset's attestors, the composed response unit fails validation with `"some output addresses are not attested"`. This is functionally identical to the reported ERC20-blacklist scenario: an untrusted/blacklisted-like status of the destination address makes the transfer/sweep impossible, permanently trapping the funds.

### Finding Description
`aa_composer.js` builds AA response payments via `sendUnit()`. When preparing an asset payment message, it only checks that the **AA itself** (the spender) is attested via `storage.loadAssetWithListOfAttestedAuthors(conn, asset, mci, [address], true, ...)` at `aa_composer.js:1323`. It performs no check that the **recipient** address (e.g., `trigger.address`, or any address computed by oscript) is attested.

The actual enforcement only happens later, when the fully composed unit is passed to `validateAndSaveUnit` (`aa_composer.js:1408`), which runs through `validation.js`'s `validatePaymentInputsAndOutputs`. There, for `spender_attested` assets, **all** output addresses are checked against the attestor list: [1](#0-0) 

If the recipient is not attested, this returns `"some output addresses are not attested"`, and `aa_composer.js` calls `bounce(err)`: [2](#0-1) 

Crucially, the balance increment from the original trigger payment into the AA was already committed as part of processing a separately-valid, already-stable unit (the trigger unit itself was validated and accepted on the DAG before the AA ever executes). The AA's oscript-driven refund/payout attempt is what fails — not the receipt. Since `bounce()` only ever refunds `base`/bytes (and other assets under the bounce-fee mechanism) up to the amount the trigger sent, and even that refund path constructs a `payment` message subject to the exact same `spender_attested` output-address check, there is no path by which the AA can ever release this asset back out if the intended recipient is not (or is no longer) attested.

This mirrors the reported vulnerability class exactly: an address-level restriction on one asset (blacklist there / non-attestation here) blocks a required outgoing transfer, permanently locking value inside a contract-like construct (an ERC20 vault there / an AA balance here).

### Impact Explanation
Any AA that accepts or is designed to relay a `spender_attested` asset (a legitimate, protocol-supported asset feature) can have its logic permanently deadlocked with respect to that asset whenever the counterparty address it needs to pay is not attested — whether because the attestor revoked/never granted attestation, or because the recipient address changed its definition after being attested (attestation is invalidated by subsequent `address_definition_changes`, per `storage.js:1959-1974`). This causes:
- Permanent freezing of AA-held funds (the asset balance becomes unspendable to that recipient forever, since the AA cannot bounce/refund it either).
- In multi-step AA flows (chained triggers/DeFi-like AAs), this can strand user deposits inside the AA with no way to retrieve them, denying users the funds they are owed and effectively causing a fund loss for that user while the AA continues operating for others.

Given `spender_attested` is a first-class asset feature exposed to any oscript/AA author, and attestation status is entirely outside the AA's control (managed by third-party attestors and by the recipient's own address-definition changes), this is a realistic operational hazard rather than a contrived edge case.

### Likelihood Explanation
`spender_attested` is a documented, first-class primitive (`asset_attestors`, `attestors` in asset definition) intended for compliance-style assets. AA authors composing generic payout/refund logic (a common pattern, e.g., `trigger.address` refunds seen throughout `aa_composer.js`/test samples) have no built-in signal that the destination isn't attested until the unit fails to validate and the whole response bounces. Any attestor revoking attestation of a user address after that user has interacted with an AA holding such an asset — or the user changing their address definition — triggers this condition with no attacker action required, making it moderately likely to occur in real-world use of `spender_attested` assets combined with AAs.

### Recommendation
- Before composing/finalizing any `payment` message for a `spender_attested` asset in `aa_composer.js`'s `sendUnit`, check attestation status of **all** intended output addresses (not just the AA's own spender address) using `storage.filterAttestedAddresses`, and surface a clear, actionable bounce reason distinguishing this case from generic validation failure.
- Consider providing oscript-level introspection (e.ss., an `is_attested()`-style helper or exposing `arrAttestedAddresses`) so AA authors can branch logic (e.g., hold funds in a claimable state, or route to a fallback/burn address) instead of unconditionally attempting a payment that will always fail for non-attested recipients.
- Document prominently that `spender_attested` assets should not be used as generic payment/refund vehicles in AAs without an explicit attestation-gated release mechanism, since the AA has no unilateral way to force attestation of a destination it doesn't control.

### Proof of Concept
1. Attestor `X` defines an asset `A` with `spender_attested: true` and publishes an initial attestor list containing `X` (`asset_attestors` message, validated per `validation.js:2033-2042`, `validateAttestorListUpdate` at `validation.js:2829-2848`).
2. User `U`, who is attested by `X`, sends a unit paying asset `A` to AA address `AA1`. This is valid because `U` is in `arrAttestedAddresses` and `AA1` (the output) is also attested by `X` at the time (validation.js:2630-2641 passes for this trigger unit).
3. `AA1`'s oscript, upon receiving `A`, is coded to pay it back to `trigger.address` (`U`) later based on some state condition (a common "hold-then-release" or "escrow" pattern).
4. Before that release trigger fires, `X` revokes `U`'s attestation (or `U` changes its address definition, which per `storage.js:1959-1974` invalidates prior attestations for outputs computed after the definition change).
5. When `AA1` attempts the payout, `aa_composer.js`'s `sendUnit` composes the payment (only checking that `AA1` itself is attested, `aa_composer.js:1323`), builds the unit, and calls `validateAndSaveUnit` (`aa_composer.js:1408`).
6. `validation.js`'s `validatePaymentInputsAndOutputs` rejects the unit with `"some output addresses are not attested"` (`validation.js:2637-2638`), and `aa_composer.js` calls `bounce(err)` (`aa_composer.js:1409-1410`).
7. Because bounce logic itself is subject to the same attestation requirement for asset `A`, no refund of `A` is possible either. `A`'s balance inside `AA1` remains permanently locked, with `U` unable to ever recover it through this AA.
