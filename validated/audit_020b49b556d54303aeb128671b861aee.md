### Title
Membership webhook allows cross-tenant Team hijack via `github_id` lookup with no organization re-verification - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `params.team.id` (the GitHub team's global numeric ID) and only assigns `organization`/`slug`/`name` inside the `find_or_create_by!` block, which Rails skips when a record already exists. Combined with `WebhooksController#repository_owner` falling back to `params.dig('organization','login')` (since `MembershipHandler`'s `params` schema never `requires :repository`), an attacker who controls any Shipit-registered organization's webhook secret can send a minimal, repository-less membership payload naming a *different* organization's pre-existing privileged `Team` by its `github_id`, and get added as a member of that team without ever proving control of the mutated org.

### Finding Description
The binding the attacker breaks is:

`verified_org = Shipit.github(organization: repository_owner).organization` (the org whose webhook secret validated the request)
should equal
`mutated_team.organization` (the `Team#organization` of the row actually written to).

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-38`) computes `repository_owner` via `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`), which is `params.dig('repository','owner','login') || params.dig('organization','login')`. `MembershipHandler`'s `params do ... end` schema (`app/models/shipit/webhooks/handlers/membership_handler.rb:7-21`) never `requires :repository`, so a payload with only `organization` and no `repository` key validates fine and is signed/verified purely against `organization.login`.
- `MembershipHandler#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`) does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
```
`find_or_create_by!` first performs `find_by(github_id: ...)`; the block (which sets `organization`) only executes on the create path. If a `Team` row with that `github_id` already exists (e.g., a legitimately-onboarded team belonging to organization "shopify"), the find branch returns that existing row untouched — `organization` is never re-checked or re-assigned against `params.organization.login`.
- `process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) then calls `team.add_member(member)` (or removes), directly mutating that pre-existing team's membership list, and `member` comes from `User.find_or_create_by_login!(params.member.login)` — fully attacker-controlled (the attacker names their own GitHub login).

Attacker's request: an unprivileged owner of some Shipit-recognized organization ("attacker-org", with its own legitimate webhook secret) POSTs to `/webhooks` with header `X-Github-Event: membership` and JSON body:
```json
{
  "action": "added",
  "team": {"id": <github_id of victim's pre-existing Team row>, "name": "x", "slug": "x", "url": "http://x"},
  "organization": {"login": "attacker-org"},
  "member": {"login": "attacker-github-login"}
}
```
No `repository` key is needed. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and validates the signature against attacker-org's own genuine webhook secret — this passes cleanly since the attacker legitimately controls that org's webhook. `find_or_create_team!` then finds the victim `Team` (organization: e.g. "shopify") by `github_id` and adds the attacker as a member.

None of the existing guards catch this: `verify_signature` only proves the *requesting* org is who it claims — it says nothing about which `Team` row the handler subsequently mutates; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not that `team.organization` matches the verified organization; there is no `require_permission!` or model validation in `Team`/`Membership` that re-derives or checks `organization` on the find branch.

### Impact Explanation
The attacker becomes a member of a `Team` row belonging to a different, victim organization. If that `Team` is one referenced in `Shipit.github_teams` (config-driven authorized teams, computed via `Team.find_or_create_by_handle` in `lib/shipit.rb:256-258`), then `User#authorized?` (`app/models/shipit/user.rb:80-82`, `@authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?`) will now return `true` for the attacker's Shipit user, bypassing `force_github_authentication`'s team-membership gate (`app/controllers/concerns/shipit/authentication.rb:26-30`) and granting the attacker full dashboard access to deploy, rollback, or manage stacks belonging to the victim organization. This is a cross-tenant authorization escalation into `Shipit.github_teams`, repeatable against any organization whose privileged `Team`'s numeric `github_id` the attacker can learn (GitHub team IDs for visible/public teams are discoverable via the GitHub API without special permission).

### Likelihood Explanation
Preconditions: (1) Shipit must be configured to serve multiple organizations, each with its own registered webhook secret, and the attacker must own/administer one such organization (own webhook secret only — no victim secrets needed); (2) the victim's privileged `Team` row must already exist in Shipit's DB (created previously via a real membership webhook or via `Shipit.github_teams` bootstrap) with a `github_id` the attacker can enumerate. Given these, the attack is a single unauthenticated-relative-to-victim HTTP POST, fully repeatable, and costs nothing beyond knowing the target team's numeric GitHub team ID.

### Recommendation
In `find_or_create_team!`, verify/reconcile `organization` on every path, not just create: after `find_or_create_by!`, assert `team.organization.casecmp?(params.organization.login)` (or scope the lookup by both `github_id` and `organization`) and raise/reject the webhook if they diverge, so a `github_id` collision across organizations can never mutate a team belonging to a different, already-verified organization.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":membership cannot mutate a Team belonging to a different organization, even without a repository key" do
  victim_team = shipit_teams(:shopify_developers) # organization == "shopify"

  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: 'x', slug: 'x', url: 'http://x' },
    organization: { login: 'attacker-org' },
    member: { login: 'mallory' }
  } # NOTE: no 'repository' key at all

  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    stub(verify_webhook_signature: true, organization: 'attacker-org')
  )

  @request.headers['X-Github-Event'] = 'membership'

  assert_no_difference -> { Team.count } do
    post :create, body: payload.to_json, as: :json
  end
  assert_response :ok

  victim_team.reload
  # Binding check: verified org != mutated Team#organization
  refute_equal 'attacker-org', victim_team.organization
  # But the exploit still wrote a Membership into the victim's privileged team:
  assert victim_team.members.exists?(login: 'mallory')
end
```
This demonstrates the divergence: the signature verifies against `attacker-org`, yet the row actually mutated (`victim_team`) has `organization == "shopify"` — proving `verified_org != mutated_team.organization` while the request still succeeds and writes cross-tenant. # frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
