### Title
Webhook signature is verified against an organization derived from an unsigned field, while the handler acts on a different unsigned field — allowing cross-organization signature bypass in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret is used to validate the HMAC signature by reading `repository.owner.login` (or `organization.login`) straight out of the *unauthenticated* JSON body. The handler that actually performs the action, however, resolves the target repository/stack from a completely different field of that same unauthenticated body: `repository.full_name` (in `Handler#repository_name`). These two fields are never cross-checked against each other, so the "organization whose secret authenticated the request" and "repository that is written to" are not bound together.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 

`repository_owner` is read directly from the parsed JSON body before any signature check occurs: [2](#0-1) 

This value picks the `GitHubApp` instance (and thus the `webhook_secret` used to verify HMAC) via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

Critically, `verify_webhook_signature` unconditionally returns `true` when the selected organization's `webhook_secret` is blank: [4](#0-3) 

Meanwhile, the actual resource that handlers operate on (e.g. `PushHandler`, `StatusHandler`) is resolved from a *different* field of the same unauthenticated payload — `repository.full_name` — with no relation back to `repository_owner`: [5](#0-4) 

In a multi-organization Shipit deployment (`secrets.github` keyed by multiple orgs, each with its own `webhook_secret`, per `github_app_config`) an attacker who knows that *any one* configured organization has no `webhook_secret` set can:
1. Set `repository.owner.login` (or `organization.login`) in the forged payload to that unprotected organization → `verify_signature` resolves to a `GitHubApp` with `webhook_secret` blank → `verify_webhook_signature` trivially returns `true`, regardless of the `X-Hub-Signature` header content.
2. Set `repository.full_name` in the same payload to a *different*, protected organization's repository that has a real `Stack` registered.

The request passes `verify_signature` entirely, and the event handler (e.g. `StatusHandler`) then acts on the targeted repository as if it were a legitimately GitHub-signed webhook for that repo, even though that repo's organization has a properly configured secret which was never checked.

This breaks the equality the review criteria calls out explicitly: *organization that authenticated* (`repository_owner` → `Shipit.github(organization:)`) must equal *repository that is written* (`repository.full_name` → `Handler#repository_name` → `stacks`), and here it does not.

### Impact Explanation
`StatusHandler` builds a `Status` directly from unauthenticated payload fields (`sha`, `state`, `description`, `target_url`, `context`, `created_at`) for an existing commit on the targeted stack, as shown by the controller test: [6](#0-5) 

Commit statuses gate whether a commit is `deployable?` in Shipit's safety checks. By forging a `success` status for a commit that has not actually passed CI, an attacker who can exploit this cross-organization bypass can make an otherwise-blocked commit appear deployable, enabling an **unauthorized deploy** of an attacker-influenced commit on a stack belonging to an organization that *does* have webhook signing properly configured. This satisfies the Critical bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability depends entirely on the operator's configuration: this is only reachable in a **multi-organization** Shipit setup (`secrets.github` with a per-organization schema) where at least one configured organization has no `webhook_secret` set. Since `webhook_secret` is explicitly documented as *optional* in `docs/setup.md`, and it's plausible for an operator to leave it blank on a low-priority/test organization while properly securing a high-value one, this is a realistic misconfiguration rather than a purely theoretical one. No credentials, session, or GitHub App private key are required — only knowledge (or discovery, e.g. by testing several org names with an empty/garbage signature) of which configured organization has no secret.

### Recommendation
Bind the "signing organization" to the resource that will actually be acted upon:
- Verify the webhook signature using the `webhook_secret` associated with the organization/repository extracted from the *same* field used by `Handler#repository_name` (`repository.full_name`), not a separately-derived `repository.owner.login` / `organization.login`.
- Alternatively, after selecting the signing organization, assert that `repository.full_name`'s owner matches `repository_owner` before dispatching to handlers, and reject the request otherwise.
- Consider treating a blank/missing `webhook_secret` for one organization as inapplicable to verifying requests naming a different organization's repository, rather than a global signature bypass.

### Proof of Concept
Given a `secrets.github` config with two organizations, `unsecured-org` (no `webhook_secret`) and `secured-org` (with `webhook_secret: s3cr3t`, and a registered `Stack` for `secured-org/protected-repo`):

```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything-or-empty

{
  "sha": "<sha of a real commit on protected-repo>",
  "state": "success",
  "description": "forged CI pass",
  "target_url": "https://attacker.example.com",
  "context": "ci/forged",
  "created_at": "2026-09-02T00:00:00Z",
  "repository": { "full_name": "secured-org/protected-repo", "owner": { "login": "unsecured-org" } }
}
```

`verify_signature` resolves `repository_owner` to `unsecured-org` (from `repository.owner.login`), fetches its `GitHubApp` (no `webhook_secret`), and `verify_webhook_signature` returns `true` unconditionally — the request is accepted without any valid GitHub signature. `StatusHandler` then looks up stacks via `repository.full_name` = `secured-org/protected-repo`, and creates a forged `success` status on that stack's commit, potentially making it appear deployable.

*Note: full exploitation to an actual unauthorized deploy also depends on downstream deploy-trigger logic (safety checks / auto-deploy conditions) which was not further traced in this pass; the signature-bypass root cause itself is confirmed with exact file/line support above.*

```ruby
      config = secrets.github
    else
      config = github_app_config(organization)
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
