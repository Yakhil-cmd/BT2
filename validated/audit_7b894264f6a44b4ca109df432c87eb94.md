Confirmed: `ApiClient` supports being scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0)  — the `here_come_the_walrus` fixture demonstrates exactly this scoping pattern (`stack: shipit`, `permissions: [read:stack]`) [2](#0-1) . `BaseController#stack` correctly enforces this scope by resolving stacks through `stacks.from_param!`, where `stacks` is filtered to `Stack.where(id: current_api_client.stack_id)` whenever `stack_id?` is set [3](#0-2) . `Api::CCMenuController`, however, overrides `stack` and resolves it via `Stack.from_param!(params[:stack_id])` directly against the whole `Stack` table, completely bypassing the `current_api_client.stack_id` restriction [4](#0-3) .

### Title
Stack-scoped API tokens can read the CI status of any stack via the CCMenu API - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#stack` does not honor the API client's stack scoping (`ApiClient#stack_id`), unlike the shared `BaseController#stack`/`#stacks` helper used by every other API endpoint. A token created by a user and deliberately scoped to a single stack (e.g. to embed in a CI dashboard widget, as `CCMenuUrlController` itself does) can be replayed against any other stack's CCMenu endpoint and will return that other stack's deploy/build status.

### Finding Description
`BaseController` defines the authoritative scoping mechanism for stack access:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [3](#0-2) 

Every other API controller inherits this and is therefore correctly constrained: e.g. `Api::DeploysController` and `Api::TasksController` use the inherited `stack` method [5](#0-4) [6](#0-5) .

`Api::CCMenuController` overrides `stack` to bypass the scope check entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

`require_permission :read, :stack` only checks that the token has the `read:stack` *permission string*; it never validates that the specific stack requested is the one the token was authorized for [7](#0-6) , [8](#0-7) . This is the exact class of bug described in the report: a value/scope that is supposed to be constrained to a bounded range (here, "this token's authorized stack") is not actually clamped when consumed, letting the request "carry over" into other stacks — analogous to `BYTE_C4096` not wrapping and letting `inV` bleed into an adjacent memory byte.

Because `ApiClient#stack_id` is a legitimate, documented mechanism (the `stack` association, exercised by the `here_come_the_walrus` fixture [2](#0-1) , and by `CCMenuUrlController`, which itself mints such single-purpose CC-Menu tokens [9](#0-8) ), any organization deploying Shipit and handing out stack-scoped tokens (e.g. for embedding a CI status badge in a public/semi-trusted context, per the CCMenu use case) is exposed: the recipient of that narrowly-scoped token can enumerate `stack_id` values and read the build/deploy status of every stack in the Shipit instance, not just the one it was scoped to.

### Impact Explanation
This is an unauthorized read of another stack's task/deploy status through a token that was deliberately restricted to a single stack — matching the in-scope "High" impact category of "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state, task streams or deploy output" via an authorization/scope bypass, since the attacker (holder of a legitimately-issued, narrowly-scoped token) gains read access to stacks outside their granted authorization boundary. It exposes deploy state, lock status, and last build result (`lastBuildStatus`, `lastBuildLabel`, activity) for arbitrary stacks (confirmed by `CCMenuControllerTest` field list) [10](#0-9) .

### Likelihood Explanation
High — no privileged setup beyond possessing any valid `read:stack`-scoped token (even one intentionally issued for a single stack) is required; the attacker only needs to swap the `stack_id` request parameter.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, scope-respecting `stack`/`stacks` helper from `BaseController` instead of calling `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. As an admin, issue an `ApiClient` scoped to `stack_id: <stack A>` with `permissions: ['read:stack']` (as done by `here_come_the_walrus` fixture / `CCMenuUrlController`).
2. Using that client's Basic-Auth token, call `GET /api/stacks/<stack B>/ccmenu.xml` where `<stack B>` is a different stack.
3. Observe HTTP 200 with stack B's CC-Menu XML (name, lastBuildStatus, etc.) returned, despite the token being scoped only to stack A — confirmed by the absence of any scope-narrowing test for `CCMenuController` in `test/controllers/api/ccmenu_controller_test.rb`, in contrast to the scope-narrowing test present for `Api::StacksController#index` ("an api client scoped to a stack will only see that one stack") [11](#0-10) .

module Shipit
  module Api
    class TasksController < BaseController
      require_permission :read, :stack
      require_permission :deploy, :stack, only: %i[trigger abort]

      def index
        render_resources(stack.tasks)
      end

      def show
        render_resource(task)
      end

      params do
        accepts :env, Hash, default: {}
      end
      def trigger
        render_resource(stack.trigger_task(params[:task_name], current_user, env: params.env), status: :accepted)
      rescue Shipit::Task::ConcurrentTaskRunning
        render(status: :conflict, json: {
                 message: 'A task is already running.'
               })
      end

      def abort
        if task.active?
          task.abort!(aborted_by: current_user)
          head(:accepted)
        else
          render(status: :method_not_allowed, json: {
                   message: "This task is not currently running."
                 })
        end
      end

      private

      def task
        stack.tasks.find(params[:id])
      end
