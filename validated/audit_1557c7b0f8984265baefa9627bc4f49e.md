### Title
Webhook signature verified against `repository.owner.login` while stack resolution trusts unrelated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC signature against using one payload field, then hands the *entire same JSON body* to handlers that resolve the target `Stack` using a *different, independently-attacker-controlled* payload field. The two fields are never cross-checked, so a successfully-verified signature for organization A does not guarantee that the payload's target repository actually belongs to organization A.

Signature verification and org selection: [1](#0-0) [2](#0-1) 

`repository_owner` (used purely to pick the HMAC secret via `Shipit.github(organization: repository_owner)`) is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Once the signature check for *that* organization's secret passes, `create` dispatches the raw, fully attacker-controlled JSON body to the registered handlers: [3](#0-2) 

Every handler (base class and all subclasses) determines the *actual* stack/repository to act on using `payload.dig('repository', 'full_name')`, a completely separate field that is not bound to `repository.owner.login` in any way and is never validated against it: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

This is structurally the same class of bug as the reported `consume_events` issue: the code special-cases identity (here, "which org's secret validated this HMAC") but the downstream effect (which repository/stack is mutated) is driven by an entirely different, unverified identity field from the same untrusted payload — exactly the "organization that authenticated versus the repository that is written" binding called out in scope. The equality that should hold but doesn't is:
`organization_whose_secret_signed(payload) == owner(repository.full_name acted upon by the handler)`

Shipit supports multiple independently-configured GitHub Apps/organizations, each with its own `webhook_secret` (confirmed by the multi-org secrets fixture), so this is a real multi-tenant configuration this engine explicitly supports: [8](#0-7) 

### Impact Explanation
Any external actor who legitimately controls one GitHub organization/repository onboarded to a shared Shipit instance (and therefore can obtain a validly-signed webhook payload using their own org's `webhook_secret`, e.g. by triggering any GitHub event on their own repo and capturing/replaying the raw body+signature, or simply computing the HMAC themselves since they know their own secret) can forge a webhook body where `repository.owner.login`/`organization.login` = their own org (so signature check passes) but `repository.full_name` = a victim org's repository. Because handlers key off `repository.full_name` alone, this lets the attacker:
- Trigger `PushHandler` → `stack.sync_github(expected_head_sha: ...)` on a victim stack/branch, which can drive continuous-delivery deploy logic for a repository the attacker does not own — an unauthorized deploy.
- Forge `StatusHandler` commit statuses (e.g., fake CI success) for a victim commit, potentially satisfying CI gating for continuous deployment.
- Manipulate review-stack lifecycle (`opened`, `labeled`, `reopened` handlers) — archive/unarchive/create review stacks belonging to other tenants.

This crosses the "cross-repository writes / unauthorized deploy" Critical-impact bar defined in scope, without requiring any Shipit session, API token, or the victim's `webhook_secret`.

### Likelihood Explanation
Requires only that the attacker legitimately administers one GitHub organization already connected to the same shared Shipit deployment (a realistic scenario for any multi-tenant Shipit install serving several orgs/teams), and the ability to send arbitrary HTTP POSTs to the public `/webhooks` endpoint with a body they can self-sign. No social engineering, GitHub App private key, or Shipit credentials are needed — this is exactly the kind of "payload field acted on but never covered by the verified signature/identity" pattern called out as in-scope.

### Recommendation
After verifying the signature for `repository_owner`, cross-validate that `repository.full_name`'s owner matches the same `repository_owner`/`organization.login` value used to select the webhook secret before dispatching to handlers, rejecting (422) any mismatch. Alternatively, derive the target repository strictly from the same field used for authentication, or bind each `Repository`/`Stack` record to the specific GitHub App/organization installation that is authorized to emit webhooks for it, and enforce that binding in `WebhooksController#create`.

### Proof of Concept
1. Attacker owns `attacker-org/some-repo`, which is a legitimate, small Shipit-tracked stack, and thus knows (or can derive, since HMAC-SHA1 with the org's `webhook_secret` is deterministic and the attacker can trigger arbitrary real events on their own repo to capture/verify their own secret's signature behavior) `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker_org_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and successfully verifies the signature against `attacker-org`'s secret [9](#0-8) .
5. `create` dispatches the body to `PushHandler`, which resolves the stack via `repository.full_name = "victim-org/victim-repo"` [4](#0-3) [10](#0-9) , invoking `stack.sync_github` on a repository the attacker never controlled.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
