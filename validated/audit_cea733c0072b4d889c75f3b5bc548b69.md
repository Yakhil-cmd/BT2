### Title
Field-Boundary Injection in `prosaic_contract.js` Contract Hash Due to Unsanitized Concatenation Without a Delimiter - (File: prosaic_contract.js)

### Summary
`prosaic_contract.js` computes the integrity hash of a prosaic (peer-to-peer) contract by concatenating `title`, `text`, and `creation_date` directly, with no delimiter and no validation that the fields don't contain characters that could shift the perceived boundary between them. This mirrors the root cause of the Hono advisory: an attribute/field boundary is not protected by rejecting unsafe characters, so content from one logical field can bleed into an adjacent one while the resulting serialized/hashed representation stays identical for different underlying inputs. [1](#0-0) 

### Finding Description
`getHash()` and `getHashV1()` both build the hash input as a raw string concatenation `contract.title + contract.text + contract.creation_date`: [2](#0-1) 

Because there is no separator between `title` and `text`, and neither field is validated to disallow ambiguous boundary content, two different `(title, text)` pairs can produce an identical concatenated string and therefore an identical hash — e.g. `title="AB", text="C"` and `title="A", text="BC"` both yield `"ABC"`. This is exactly the bug class described in the Hono advisory (CWE-1113/CWE-113): a security-relevant value is built by concatenating attacker-influenced fields without neutralizing characters that determine field boundaries, allowing the meaning of one field to be reinterpreted as belonging to an adjacent field.

This hash is trusted as an integrity check across multiple paths reachable by an unprivileged paired device (the contract counterparty):
- In `wallet.js`, on receiving a `prosaic_contract_offer` or `prosaic_contract_shared` device message, the hash sent by the peer is verified against the locally recomputed `getHash()`/`getHashV1()` of `title`, `text`, `creation_date` supplied by that same peer. [3](#0-2) [4](#0-3) 
- The same hash is later embedded on-chain in a `data` message payload field `contract_text_hash`, and `handleReceivedSigningUnit()` matches it against `contract.hash` to bind an on-chain unit to a specific offline contract text. [5](#0-4) 

Notably, the project already recognized and fixed this exact bug class for the sibling `arbiter_contract.js` module, which introduced a `DELIMITER`-joined source string for contracts created after a cut-off date (`NEW_HASH_DATE`), specifically to prevent field-boundary ambiguity between `title`, `text`, `payer_name`, `payee_name`, etc.: [6](#0-5) 

`prosaic_contract.js` was never updated with the equivalent fix — both its current (`getHash`) and legacy (`getHashV1`) hashing functions remain vulnerable to the same field-boundary confusion that was patched elsewhere in the codebase.

### Impact Explanation
A malicious contract counterparty (an unprivileged paired device — the peer originating or accepting a prosaic contract) can craft `title`/`text` pairs that collide under `getHash()`/`getHashV1()` while conveying different semantic content. Since the hash is the sole cryptographic binding between:
1. what a device actually displays/stores as the agreed contract text, and
2. the `contract_text_hash` embedded in the signed on-chain unit,

an attacker can present one `(title, text)` split to their counterparty's device for display/acceptance while a differently-split, differently-worded `(title, text)` pair validates against the very same stored `hash`/on-chain `contract_text_hash`. This breaks the non-repudiation guarantee the hash is meant to provide for the signed contract, enabling a party to later dispute or claim a different contract content than what was actually agreed and signed, while still passing all hash-equality checks in `wallet.js` and `prosaic_contract.js`.

### Likelihood Explanation
Exploitation only requires an unprivileged peer able to send a `prosaic_contract_offer`/`prosaic_contract_shared` device message — a standard, unauthenticated-beyond-pairing capability already reachable in this codebase's paired-device contract flow. No special network position, node compromise, or elevated privilege is needed; the attacker fully controls `title` and `text` values, so constructing a colliding pair is trivial (simply move one or more leading characters of `text` into `title`).

### Recommendation
Apply the same fix already used in `arbiter_contract.js`: join `title`, `text`, and `creation_date` (and any other concatenated fields) with an explicit, reserved delimiter before hashing, and/or use `object_hash.getSourceString`/`getJsonSourceString`-style structured hashing (which already rejects delimiter/null bytes inside individual string fields) instead of raw string concatenation, for both `getHash()` and `getHashV1()` in `prosaic_contract.js`.

### Proof of Concept
1. Device A sends a `prosaic_contract_offer` with `title="AB"`, `text="C"`, `creation_date="2026-01-01 00:00:00"`.
   `hash = getHash({title:"AB", text:"C", creation_date:"2026-01-01 00:00:00"})` = SHA256(`"ABC2026-01-01 00:00:00"`).
2. Device A (or a colluding party) later produces an alternate contract record with `title="A"`, `text="BC"`, same `creation_date`.
   `getHash({title:"A", text:"BC", creation_date:"2026-01-01 00:00:00"})` = SHA256(`"ABC2026-01-01 00:00:00"`) — identical hash.
3. Both variants pass the `body.hash !== prosaic_contract.getHash(body)` check in `wallet.js` (lines 465, 488) and the `payload.contract_text_hash !== contract.hash` check in `prosaic_contract.js` (line 173), even though the semantic split between `title` and `text` differs, allowing a party to later argue the on-chain-bound contract text was the other, differently-split variant.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
