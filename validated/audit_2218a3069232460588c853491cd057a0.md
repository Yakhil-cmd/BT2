### Title
API-scoped ApiClient can read any stack's build status via `Api::CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary

### Finding Description
`Shipit::ApiClient` supports being scoped to a single stack via its `stack_id` column, and `Api::BaseController` enforces that scoping through the `stacks`/`stack` helper methods: [1](#0-0) 

Every other API controller relies on this scoped `stack` method (e.g. `Api::StacksController` uses `stacks.from_param!(params[:id])`): [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` to bypass the scoped relation entirely and query the unscoped `Stack` model directly: [3](#0-2) 

Combined with `require_permission :read, :stack`, which only checks that the token's permission list contains the string `read:stack` — never which stack it is scoped to — [4](#0-3)  an `ApiClient` created with `stack_id` set to stack A (e.g. the `here_come_the_walrus` fixture, scoped to the `shipit` stack with only `read:stack` permission) can authenticate and then pass an arbitrary `stack_id` param to `Api::CCMenuController#show` to read the CI/build status of any other stack B, because the controller's own `stack` lookup ignores `current_api_client.stack_id`.

This breaks the same class of trust binding as the raffle bug: the token *authorizes* access to stack A, but the code path it actually *touches* is any stack chosen by the caller — an equality the base controller enforces (`stack ∈ stacks_client_is_scoped_to`) that this one controller silently drops.

### Impact Explanation
This is an authorization-scope escape: a client explicitly restricted to one stack (a common pattern for giving a third-party CI badge/monitoring integration limited access) gains unauthenticated-for-that-stack read access to the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, etc., rendered by `shipit/ccmenu/project`) of every other stack in the Shipit instance. This matches the in-scope High-severity category of "escalation into ... unauthenticated read of stack state ... " since the token was never authorized to read that other stack's state.

### Likelihood Explanation
Any holder of a stack-scoped `read:stack` ApiClient token (which is a normal, low-privilege credential meant to be limited to one stack, e.g. distributed to embed a CI badge) can trivially exploit this by changing the `stack_id` request parameter — no special conditions or races are required. This does not require a full Shipit session, elevated GitHub permissions, or any privileged account beyond the low-privilege API token itself.

### Recommendation
Change `Api::CCMenuController#stack` to use the scoped `stacks` relation from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that stack-scoped API clients cannot read the status of stacks outside their `stack_id` scope.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id` of stack A with only the `read:stack` permission (mirrors the `here_come_the_walrus` fixture) [5](#0-4) .
2. Authenticate as this client via HTTP Basic Auth against `Api::CCMenuController#show`.
3. Send `GET /api/{other_stack_owner}/{other_stack_name}/{other_stack_env}/ccmenu.xml` for stack B, which the client is *not* scoped to.
4. Because `stack` in `Api::CCMenuController` calls `Stack.from_param!(params[:stack_id])` unscoped (rather than `stacks.from_param!`), the request succeeds and returns stack B's build/lock status, even though `current_api_client.stack_id` is set to stack A.
