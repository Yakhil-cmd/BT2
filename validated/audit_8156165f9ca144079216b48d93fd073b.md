### Title
Stale shared per-block index cache lets bad-debt socialization be bypassed for positions valued before the write-down - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`market.clar`/`v0-4-market.clar` caches each vault's liquidity/borrow index in a map keyed only by `{ timestamp: stacks-block-time, aid: uint }` [1](#0-0) [2](#0-1) . Because `stacks-block-time` is identical for every transaction inside a block, this cache is not scoped to a single caller or transaction — it is a resource shared by every principal who touches that asset in the same block, primed by whichever transaction happens to call `accrue-and-cache` first, and silently consumed ("cache HIT") by every subsequent, unrelated transaction that block without re-checking the vault's live state [1](#0-0) .

### Finding Description
`accrue-and-cache` only calls into the vault (`vault-accrue`) on a cache miss; on a hit it returns the value another transaction wrote earlier in the same block, with no validation that the vault's real index has since moved [1](#0-0) .

The protocol's own code shows this staleness is a known, real risk: when bad debt is socialized, the developers explicitly overwrite the shared cache entry immediately afterward because the write-down "decreases" the vault's `lindex`: [3](#0-2) 

This manual refresh is only wired into the `socialize-debt-asset` fold used inside `liquidate`. Any other transaction in the same block that reads the shared index via `get-cached-indexes`/`accrue-and-cache` for the same asset — e.g. another user's `collateral-add`, which primes/consumes the cache to run its "future capacity must not decrease" LTV check for zToken collateral [4](#0-3) , or a separate `liquidate` call on a different borrower that also relies on `get-cached-indexes` for the same `aid` for its debt/collateral math [5](#0-4)  — gets whatever value happened to be cached by whichever transaction executed first that block, not the value that reflects the socialization event that intervened.

This is the CVE-2019-5736 bug class in contract form: a shared, time-windowed resource (there: the host's `/proc/self/exe` fd; here: the market's `index-cache`) is checked/primed at one point and consumed later by a different, unprivileged principal without re-validating that the underlying resource changed in between — the check and the use diverge across two different actors.

### Impact Explanation
Victim: any borrower whose zToken collateral or debt in asset `aid` is valued in the same block as an intervening `socialize-debt-asset` write-down for that same `aid`, and any liquidator computing seizure amounts off `get-cached-indexes` for that block. If a transaction consumes a pre-write-down (stale, higher) `lindex`/index cached earlier in the block instead of the post-write-down value, zToken collateral is overvalued relative to the vault's true backing, letting an under-collateralized `collateral-add`/borrow pass a health check that should have failed, or letting a liquidator under-seize/over-seize relative to the asset's true, just-updated price. This is theft/insolvency risk shared between unrelated protocol participants (borrower vs. protocol solvency, or liquidator vs. borrower), not a self-inflicted loss by the caller, and lands on temporary/permanent freezing or theft of funds depending on which side of the stale value is exploited.

### Likelihood Explanation
Likelihood is moderate and depends on real intra-block ordering: an attacker (or an opportunistic MEV-adjacent actor, excluding pure block-producer/miner reordering which is out of scope) needs a bad-debt socialization event on asset `aid` to land in the same block as their own `collateral-add`/`liquidate` call on that asset, in an order where their transaction reads the cache before the socialization refresh occurs, or vice versa depending on which side benefits them. I was not able to fully verify, within the available search budget, whether other vault-mutating paths (`vault-deposit`, `vault-redeem`, `borrow`, `repay` in the vault contracts) can also move the index/lindex mid-block without a corresponding cache refresh in market.clar — the explicit refresh I found is only in `socialize-debt-asset`, which is the strongest confirmed instance of the pattern; there may be additional unrefreshed paths that would raise likelihood further.

### Recommendation
Either drop the cross-transaction sharing (scope the cache key to the current transaction only, e.g. by including `tx-sender`/a per-call nonce, so no state is shared between unrelated callers), or make every vault state-mutating path that can change `index`/`lindex` responsible for refreshing `index-cache` for its `aid` before returning control, the same way `socialize-debt-asset` already does, and re-validate the cached value against a live vault read at the point health checks or liquidation math consume it.

### Proof of Concept
1. Block N contains, in order: (a) Liquidator L calls `liquidate` on borrower A's fully-collateralized-in-asset-X position, which drives A to zero collateral and triggers `socialize-debt-asset` for asset X, decreasing X's `lindex` and refreshing `index-cache` at `{timestamp: T, aid: X}` to the new lower value [6](#0-5) ; (b) prior to (a) in the same block, attacker B already called `collateral-add` for a zX zToken, which primed `index-cache` at `{timestamp: T, aid: X}` with the pre-write-down (higher) `lindex` and used it to pass the "future capacity must not decrease" check [7](#0-6) .
2. Because B's transaction executed before the socialization refresh, B's health check used the stale, overvalued price and admitted collateral that would not have passed the check against the corrected `lindex`.
3. B now holds a position whose zToken collateral is overvalued relative to the vault's true backing for the rest of the protocol's lifetime of that position, a value only correctable by the next natural accrual, not by A's or L's transaction.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```

```text
(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
```
