### Title
`StatusHandler` ignores webhook `repository` binding, allowing cross-tenant status forgery via valid signature from an unrelated org - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to verify a webhook using only `params.dig('repository','owner','login')`, proving nothing more than "the sender knows *some* configured org's secret." `StatusHandler#process`, unlike `PushHandler` and `CheckSuiteHandler`, never re-checks that binding: it resolves the target `Commit` purely from `Commit.where(sha: params.sha)`, globally, with no reference to `payload['repository']` at all.

### Finding Description
The claimed binding is: `organization_used_to_verify_signature == organization_owning_the_Commit/Stack_that_gets_mutated`.

- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and fetches `github_app = Shipit.github(organization: repository_owner)`, then verifies the HMAC signature against that org's `webhook_secret` [1](#0-0) . This only proves the request was signed by whoever owns the org named in the `repository.owner.login` field of the same payload — it says nothing about which `Stack`/`Commit` should be affected.
- `Handler` base class provides a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository','full_name')` [2](#0-1) . Both `PushHandler` (`stacks.not_archived.where(branch:)`) [3](#0-2)  and `CheckSuiteHandler` (`stacks.where(branch: ...)`) [4](#0-3)  use this helper, so the repository named in the payload constrains which stacks can be mutated.
- `StatusHandler#process` does **not** call `stacks` or reference `payload['repository']` at all — it just does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . The `sha` is a global, content-derived string with no ownership scoping in the query.

Exploit flow: the attacker owns/controls a repository under an org ("attacker-org") that has any legitimate Shipit GitHub App/webhook configuration (a real `webhook_secret`) — a normal, unprivileged precondition in a multi-tenant Shipit deployment. The attacker crafts a `status` event payload with `repository.owner.login = "attacker-org"` (so `verify_signature` succeeds using attacker-org's own secret) but `sha` set to a commit hash that already exists in the victim-org's tracked `Stack`'s `commits` table (e.g., because the exact same commit content — and therefore the same SHA — exists in a fork, mirror, or shared history under both orgs, which is normal Git behavior since SHAs are content hashes, not owner-scoped identifiers, and are typically public). Because `StatusHandler` never checks that the sha actually belongs to a commit under attacker-org's repository, `Commit.where(sha: params.sha)` matches the victim's row and `commit.create_status_from_github!(params)` writes an attacker-controlled `Status` (state, context, description, target_url) onto the victim's commit/stack.

Existing guards fail here specifically because they operate on different axes: `verify_signature` only authenticates "some org's secret," not "this org's commit"; `ExplicitParameters` schema in `StatusHandler` only validates types/presence of `sha`/`state`/etc, not ownership [6](#0-5) ; and the `stacks`/`repository_name` scoping mechanism that protects `PushHandler`/`CheckSuiteHandler` is simply not invoked by `StatusHandler`.

### Impact Explanation
An attacker who controls any Shipit-onboarded org can write a forged CI `Status` (arbitrary `state`, `context`, `description`, `target_url`) onto a commit belonging to a completely different, unrelated org's `Stack`, as long as they can guess/know a SHA that is shared between their own repo and the victim's tracked repo (SHAs of public commits are not secret). Since `Status` state feeds into `Commit#state`/`deployable?` and can influence continuous-deployment decisions [7](#0-6) , this can be used to mark an otherwise-failing/pending commit as `success`, potentially triggering an unauthorized deploy under continuous delivery, or to disrupt (spoof failure of) an unrelated org's pipeline. This is repeatable against any victim stack for which the attacker can find a matching SHA, and it crosses tenant boundaries using only the attacker's own legitimate credentials — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: (1) the attacker controls/owns at least one org/repo already configured in Shipit with a real `webhook_secret` (plausible in any multi-tenant Shipit install serving multiple teams/orgs); (2) the attacker knows or can produce a SHA that also exists in the victim's tracked `Stack` (achievable via forking/mirroring a public repo, since Git SHAs are content-derived and identical across forks/mirrors that haven't rewritten history). No Shipit or GitHub secrets belonging to the victim are required, and no privileged Shipit role is needed — only the attacker's own webhook secret, which they legitimately possess. The request is a single unauthenticated-to-Shipit-session HTTP POST to `/webhooks` with a correctly-computed HMAC over attacker-controlled bytes, so it is fully scriptable and repeatable.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository asserted (and cryptographically bound) in the payload, mirroring `PushHandler`/`CheckSuiteHandler`'s use of the `stacks` helper, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures the commit whose status is mutated actually belongs to a `Stack` under the `repository.full_name` that was cryptographically verified via `verify_signature`, closing the gap between "who signed this" and "what gets written."

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb` patterns):
```ruby
test ":status webhook signed by attacker org writes a Status onto a victim-org commit with a colliding sha" do
  # Arrange: victim commit lives under a stack whose repository owner is "shopify" (fixture default)
  victim_commit = shipit_commits(:first)

  # Configure a second, attacker-controlled org with its own real webhook_secret
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GithubApp.new('attacker-org', webhook_secret: 'attacker-secret')
  )

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => victim_commit.sha, # sha collision: same content exists under attacker's repo/fork
    'state' => 'success',
    'repository' => { 'owner' => { 'login' => 'attacker-org' }, 'full_name' => 'attacker-org/forked-repo' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', 'attacker-secret', body)}"
  request.headers['X-Hub-Signature'] = signature

  # Assert equality claimed by verify_signature does NOT hold after the write:
  # verified organization == 'attacker-org', but the mutated commit's stack.repository.owner == 'shopify'
  assert_difference -> { victim_commit.statuses.count }, 1 do
    post :create, body:, as: :json
  end
  assert_response :ok

  status = victim_commit.statuses.last
  assert_equal 'success', status.state
  assert_not_equal 'attacker-org', victim_commit.stack.repository.owner
end
```
This demonstrates that a payload verified against `attacker-org`'s secret mutates a commit under a different org's stack, confirming the broken binding.
