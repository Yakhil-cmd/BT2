### No vulnerability found for this question.

**Reasoning:** In `checkoutRun`, `pr.HeadRefName` is validated against a leading `-` before `cmdQueue` is built [1](#0-0) , and this check happens prior to both `cmdsForExistingRemote` and `cmdsForMissingRemote` being called, so `localBranch` (when derived from `pr.HeadRefName`) and `remoteBranch` (`remote.Name + "/" + pr.HeadRefName`) cannot start with `-` from the `HeadRefName` component [2](#0-1) .

The remaining two candidate inputs are not attacker-controlled under this threat model:
- `remote.Name` comes from the victim's local git remotes configuration (`opts.Remotes()` / `cliContext.Remote`), not from PR/API data supplied by a remote attacker [3](#0-2) . An attacker publishing a PR/repo has no path to set the victim's local remote name.
- `opts.BranchName` is populated only from the `--branch`/`-b` CLI flag, which the victim types themselves [4](#0-3) . There is no code path in this repo that forwards untrusted remote data (PR title, ref name, etc.) into `opts.BranchName`; the "wrapper that forwards untrusted input" scenario is speculative and outside the scope of this codebase.

Since `remoteBranch` and `localBranch` as used in `checkout -b <localBranch> --track <remoteBranch>` (`cmdsForExistingRemote`, line 238) can only start with `-` via components not reachable by a remote, unprivileged attacker, this does not constitute an exploitable git flag injection under the stated threat model.
