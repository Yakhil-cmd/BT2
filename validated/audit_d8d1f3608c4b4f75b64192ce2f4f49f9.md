## Analog Vulnerability Found

### Title
Asset definer can permanently freeze previously-attested holders' funds by rotating the `asset_attestors` list, with no recovery mechanism - (File: `validation.js`, `storage.js`)

### Summary
The Sherlock report describes `AvailBridge` locking user funds with no withdrawal path once the contract is `paused`, because spendability is gated by a privileged switch that has no unlock/rescue logic. In `ocore`, an analogous "spendability gate with no escape hatch" exists for assets defined with `spender_attested: true`. The asset definer can publish an `asset_attestors` message at any time to replace the list of trusted attestors [1](#0-0) . Validation of every future payment (both issuance and transfer) checks that all owner addresses are in the **current/latest** attestor-derived attestation set, not the set that was valid when the coins were received [2](#0-1) . If the definer removes/rotates attestors, addresses that legitimately hold coins issued while properly attested become permanently unable to spend those coins — there is no bridge-style "withdraw locked funds" mechanism, no grandfathering, and no way for the holder or anyone else to unfreeze the balance.

### Finding Description
When an asset is created with `spender_attested: true`, the definer must maintain a list of attestors whose attestations legitimize spenders [3](#0-2) . `storage.readAsset` loads only the *latest* stable attestor list for the asset before validating any payment [4](#0-3) .

For every payment of such an asset, `loadAssetWithListOfAttestedAuthors` filters the input/output addresses against `arrAttestedAddresses`, which is computed by joining the `attestations` table against the asset's **current** `arrAttestorAddresses` [5](#0-4) . The core check in payment input/output validation then requires every input owner and every output address to be in this attested set: `objAsset.arrAttestedAddresses.indexOf(owner_address) === -1` bounces/rejects the transaction [6](#0-5) , and outputs are checked the same way when building/finalizing the payment message [7](#0-6) .

Because attestation validity is re-evaluated against the *current* attestor list rather than the attestor list at the time the address was actually attested, a definer can:
1. Define an asset with `spender_attested: true` and an initial attestor list.
2. Let honest users receive/hold coins after being attested by a listed attestor.
3. Publish a new `asset_attestors` unit that drops that attestor (or replaces the whole list) [8](#0-7) .
4. From that point on, `arrAttestedAddresses` no longer contains those holders, and any attempt by them to spend their existing (already-owned) coins is rejected with "owner address is not attested" [9](#0-8) .

There is no code path anywhere in asset validation, AA logic, or wallet code that allows a holder whose attestor was removed to recover or withdraw the now-frozen balance — the funds are permanently locked in the same way the reported bridge funds would be locked while paused, except here there is no "unpause" that could ever restore access for that specific holder unless the definer voluntarily re-adds the exact attestor (a privileged, non-guaranteed action).

### Impact Explanation
This is a concrete, unauthorized freezing of already-issued/transferred asset funds reachable by a single privileged-but-still-"asset issuer" party (the definer) acting unilaterally against ordinary unprivileged holders, with no code-level remedy. Holders lose access to funds they legitimately acquired, satisfying the "AA fund loss or freezing" / "asset issuance and transfer conditions" impact class. Because `asset_attestors` updates are single-authored ordinary units (not requiring cooperation of the frozen holders), the definer can trigger this unilaterally at will, at any time, against any subset of holders by choosing which attestors to drop.

### Likelihood Explanation
Any asset created with `spender_attested: true` is exposed; this is a documented, first-class asset flag intentionally supported for KYC/attestation use cases, so such assets are expected to exist in production. The definer needs no special permission beyond being the asset's own definer (checked via `objUnit.authors[0].address !== objAsset.definer_address` in `validateAttestorListUpdate` [10](#0-9) ), a role they already legitimately hold. No cooperation from the frozen holder or the network is required, and the freezing is triggered by ordinary protocol messages, not by any bug requiring rare conditions.

### Recommendation
Evaluate attestation validity against the attestor list that was in effect (or the specific attestor whose attestation the holder relied on) at the time the holder's attestation unit was accepted/stable, rather than always re-checking against the current list at spend time. Alternatively/additionally, provide holders whose previously-attested outputs become "orphaned" by an attestor-list update a path to redeem/convert those coins (e.g., allow spending back to the definer or a "cash-out" transfer condition) so that legitimately acquired funds can never become permanently unspendable purely due to a later, unilateral definer action.

### Proof of Concept
1. Definer issues asset `A` with `spender_attested: true`, `attestors: [X]`.
2. Attestor `X` attests address `H` (holder). Definer issues coins of asset `A` to `H`; `loadAssetWithListOfAttestedAuthors` passes because `H` is in `arrAttestedAddresses` derived from attestor `X` [11](#0-10) .
3. Definer publishes `asset_attestors` message for asset `A` with a new list `[Y]` (dropping `X`) [8](#0-7) ; this passes validation since only definer authorization and a valid sorted address list are required [12](#0-11) .
4. `H` now attempts to spend previously received coins of asset `A`. `storage.readAsset` loads the new latest attestor list `[Y]` [13](#0-12) , and `filterAttestedAddresses` finds no attestation from `Y` for `H`, so `arrAttestedAddresses` excludes `H`.
5. Payment validation rejects `H`'s spend: `"owner address is not attested"` [9](#0-8) . `H`'s coins are now permanently locked with no available recovery action in the codebase.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
