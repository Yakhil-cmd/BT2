### Title
`handleNewSharedAddress` accepts attacker-supplied `device_address` for cosigner routing without verifying the message sender controls that address, allowing hijacking/freezing of shared (multisig) address signature routing - (File: wallet_defined_by_addresses.js)

### Summary
The reported bug class is a missing-caller-validation issue: a function that both processes a transfer and performs a sensitive action (contract deployment) trusts unauthenticated input instead of verifying the caller is the token contract, letting an attacker interfere with legitimate deployment via a deterministic collision. The analogous pattern in `ocore` is `wallet_defined_by_addresses.js:handleNewSharedAddress`, invoked from any paired correspondent device via the `"new_shared_address"` message [1](#0-0) , which persists a `signers` map (`shared_address -> signing_path -> device_address`) into `shared_address_signing_paths` without verifying that the claimed `device_address` for each signing path is actually controlled by the authenticated sender of the message.

### Finding Description
`handleNewSharedAddress` validates that `body.address` is the chash of `body.definition`, and that each `signers[path].address` matches the address found at that path in the definition via `extractAddressPathsFromDefinition` [2](#0-1) . However, it never checks that the `device_address` value attached to each entry in `signers` corresponds to the device that actually authenticated as the sender of the message (`from_address`, verified upstream in `device.js`'s hub message handling). The definition and its member addresses are public once a shared address is first used on-chain, so an attacker who is merely a paired correspondent of the victim (not necessarily a legitimate cosigner) can reconstruct a valid `{address, definition}` pair for any existing shared multisig address and submit a forged `new_shared_address` message with the same structurally-valid `signers.address` values but an arbitrary attacker-controlled `device_address` for one or more signing paths.

`determineIfIncludesMeAndRewriteDeviceAddress` only rewrites/validates device addresses for paths where the *local* device is itself a member; it does not authenticate the third-party `device_address` entries [3](#0-2) . The row is then persisted via `INSERT IGNORE`, keyed by `(shared_address, signing_path)` [4](#0-3) . Because the insert uses `IGNORE`, the first message to arrive for a given `(shared_address, signing_path)` "wins" — exactly the same "first writer" pattern that made `ClonesUpgradeable.cloneDeterministic`-based deployment DoS-able in the external report, except here it silently corrupts routing data instead of reverting.

### Impact Explanation
Once the malicious row is stored, the victim's wallet believes the co-signer at that path lives on the attacker's device. When the wallet later needs a cosignature to spend from the shared multisig address, it will route the signing request to the attacker's device instead of the legitimate cosigner's device (see `readFullSigningPaths`/signing routing logic in `wallet.js`, which resolves signer device addresses from `shared_address_signing_paths`). This lets an unprivileged paired correspondent (not a member of the address) permanently deny/hijack the signature-collection process for that shared address, effectively freezing funds held at that multisig address — a concrete "AA/wallet fund freezing" outcome analogous to the reported deployment DoS.

### Likelihood Explanation
Exploitability requires only that the attacker: (1) be a paired correspondent of the victim (a normal, easy state to reach — pairing is by design open to any device with a valid pairing secret or already-paired relationship), and (2) know the public definition of a target shared address (available once it appears on-chain, or observable from prior `new_shared_address`/`create_new_shared_address` traffic). No signature over the `device_address` field is required, making the forged message trivial to construct once definition data is known. Because `INSERT IGNORE` means only the first submission counts, the attacker's message wins if it is sent before or in place of the corresponding legitimate row is ever recorded (e.g., on wallet recovery/resync, or for signing-paths of members not previously seen by the victim).

### Recommendation
When processing `new_shared_address` (and `handleNewSharedAddress` in general), the `device_address` for a `signing_path` should not be trusted unless independently authenticated (e.g., only trust `device_address` values matching the authenticated `from_address` of the message when the message is about that signer's own path, and use `UPDATE ... WHERE` semantics or explicit conflict resolution rather than blind `INSERT IGNORE` so that legitimate updates can correct a previously-poisoned mapping instead of being silently dropped). At minimum, this mirrors the report's own fix pattern of adding an explicit check binding the trusted identity (`msg.sender`/`from_address`) to the operation being performed, rather than relying purely on structural validation of attacker-supplied fields.

### Proof of Concept
1. Attacker `A` pairs as a correspondent device with victim `V` (normal pairing flow).
2. `V` is a member of an existing shared (multisig) address `S` with public definition `D` (observable on-chain once `S` is used, or leaked via earlier `new_shared_address` traffic between `V` and other cosigners).
3. `A` computes `extractAddressPathsFromDefinition(D)` to get the legitimate `signing_path -> member_address` mapping, then crafts a `new_shared_address` message: `{address: S, definition: D, signers: {...same member addresses, but device_address for cosigner path X rewritten to A's own device...}}`.
4. `A` sends this message to `V` via the normal device-message channel (`device.sendMessageToDevice`), which is delivered to `wallet.js`'s `"new_shared_address"` handler [1](#0-0) .
5. `handleNewSharedAddress` passes all structural checks (address/definition/address-per-path match) and calls `addNewSharedAddress`, which `INSERT IGNORE`s the poisoned `(S, X, member_address, A_device_address)` row if no row for `(S, X)` exists yet [4](#0-3) .
6. When `V` later needs a cosignature from path `X` to spend from `S`, the wallet routes the signing request to `A`'s device instead of the legitimate cosigner, blocking/freezing spending from `S`.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

		var addr = objectHash.getChash160(body.definition);

		return callbacks.ifError("invalid definition: " + e);
