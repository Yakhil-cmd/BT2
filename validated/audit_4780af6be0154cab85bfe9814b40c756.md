### Title
Stack-scoped ApiClient tokens can read the CCMenu status of any stack, bypassing the token's stack scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the base `stack` accessor with a version that skips the `ApiClient#stack_id` scoping enforced everywhere else in the API, letting a token that was only authorized for one stack read the build/deploy state of any stack in the installation.

### Finding Description
`Api::BaseController` establishes the binding "the stack a token authorises == the stack it can touch": `stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `stack` resolves the requested `stack_id` param only within that restricted set: [1](#0-0) 

`Api::CCMenuController`, however, redefines `stack` to bypass that scoped relation entirely and resolve the `stack_id` param against `Stack.from_param!`, i.e. the full, unscoped `Stack` table: [2](#0-1) 

The controller still declares `require_permission :read, :stack`, but `ApiClient#check_permissions!` only checks that the string `"read:stack"` is present in the token's `permissions` array — it never validates that the token's `stack_id` matches the stack being accessed: [3](#0-2) 

So the equality that should hold — `current_api_client.stack_id == stack.id` (or `stack_id` nil, meaning "any stack") — is enforced in `BaseController#stack` but silently dropped in `CCMenuController#stack`. Any token carrying `read:stack`, even one created specifically scoped to a single stack (as in the `here_come_the_walrus` fixture), can therefore fetch the CCMenu XML for a stack it was never granted access to, simply by supplying a different `stack_id` in the URL.

### Impact Explanation
This is an authorization-boundary break for a scoped credential: a token intentionally limited to one stack gains unauthenticated (from the token-scope's perspective) read access to every other stack's build/deploy status in the installation (stack name, last build status/label/time). This matches the "unauthorized read of stack state" impact class defined in scope, since it escalates a stack-scoped token into an installation-wide read capability without any additional credential.

### Likelihood Explanation
Exploitation only requires possession of any valid, stack-scoped `ApiClient` token with the generic `read:stack` permission (a routine, low-privilege credential type intentionally created to be narrowly scoped, e.g. via `CCMenuUrlController`, which itself creates such stack-scoped clients: [4](#0-3) ). No signature forgery, secret knowledge, or elevated privilege is needed — just changing the `stack_id` path segment of an otherwise legitimate, already-granted CCMenu URL. This is trivial and highly likely to be exploited if such tokens are handed to lower-trust integrations (e.g., embedded in CI dashboards).

### Recommendation
Make `CCMenuController#stack` respect the same scoping as `BaseController#stack`, e.g. remove the override and rely on `stacks.from_param!(params[:stack_id])`, or explicitly re-check `current_api_client.stack_id` before resolving from the unscoped `Stack` relation.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to `stack_a` only (`stack_id` set, `permissions: ['read:stack']`), e.g. mirroring fixture `here_come_the_walrus`: [5](#0-4) 
2. Authenticate as that client and call `GET /api/<stack_b_owner>/<stack_b_repo>/<stack_b_env>/ccmenu`, i.e. a stack the token was never scoped to.
3. Observe the request succeeds (HTTP 200) and returns `stack_b`'s CCMenu XML (name, last build status), because `CCMenuController#stack` resolves via `Stack.from_param!` instead of the scoped `stacks.from_param!` used by every other API endpoint under `BaseController`.
