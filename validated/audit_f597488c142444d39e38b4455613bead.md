### Title
Emergency op_list vote counting bypasses the normal end-of-MCI witness validation path, allowing an unauthorized witness-list change - (File: main_chain.js)

### Summary
`main_chain.js` implements two parallel mechanisms for updating `system_vars.op_list` (the witness/order-provider list): the normal path, which runs `countVotes()` once per stabilized MCI after a `system_vote_count` message is included and stabilized in the DAG, and an "emergency" path, `applyEmergencyOpListChange()`, which can re-invoke `countVotes(conn, mci, 'op_list', 1, timestamp)` using only *unstable* votes when the network appears stuck. These two paths compute the OP list from different, inconsistent input sets (stable-and-counted votes vs. speculative unstable votes), analogous to the Neptune Mutual `Protocol`/`AccessControl` bug where a role could be granted through two inconsistent mechanisms with different guarantees.

### Finding Description
The primary vote-counting mechanism is triggered deterministically once per MCI, after stabilization, when a `system_vote_count` message for `op_list` is present in the newly stable unit: [1](#0-0) 

`countVotes()` in the normal (non-emergency) case only reads confirmed `op_votes` (derived from stable `system_vote` messages) and stable balances, giving deterministic, DAG-order-independent output: [2](#0-1) 

The emergency path, however, is invoked from a completely different trigger — the `system_vote_count` inline-payload validation only checks that the subject string is one of the known subjects and that only one such message exists per unit; it performs no additional check tying the "emergency" flag to any consensus-verified condition beyond MCI age: [3](#0-2) 

When a `system_vote_count` message is stabilized and `writer.js` finds `objValidationState.bHasSystemVoteCount` with subject `op_list`, it schedules a call to `applyEmergencyOpListChange`: [4](#0-3) 

`applyEmergencyOpListChange` checks only that enough wall-clock time (`EMERGENCY_OP_LIST_CHANGE_TIMEOUT`) has passed since the last stable MC unit, then calls `countVotes` with `is_emergency=1`: [5](#0-4) 

Inside `countVotes`, when `is_emergency` is set, the vote set is rebuilt from `getUnstableVotes()`, i.e. votes from units that are **not yet stable** and only filtered by a minimum age (`EMERGENCY_COUNT_MIN_VOTE_AGE`) and `sequence === 'good'` (a mutable, node-local judgment before finality): [6](#0-5) [7](#0-6) 

This unstable-vote branch is merged into a temporary votes table and used to elect the new OP list with the same selection query as the normal path: [8](#0-7) 

Critically, `sequence === 'good'` for an *unstable* unit is only the node's current, non-final opinion — it can flip to `final-bad` after a reorg/fork resolution. Two honest nodes that are simultaneously "stuck" (unable to advance stability) can each have different sets of unstable units marked `sequence='good'` at the moment they independently decide to run the emergency path (their local `bCatchingUp`/DAG state need not be identical), and can therefore compute two different OP lists, both persisted permanently via `REPLACE INTO system_vars` and broadcast to light clients: [9](#0-8) [10](#0-9) 

This is the same class of bug as the external report: a security-sensitive state transition (granting witness authority) has two mechanisms — the deterministic, finality-gated `countVotes` invoked by stable `system_vote_count`, and the emergency path that reuses the same function but feeds it non-final data under a much weaker precondition (only a timeout, not agreement/finality). The two mechanisms are not kept consistent with each other, so a node can accept an OP-list change that other honest nodes never accept, or accept a different OP-list change than another honest node accepted.

### Impact Explanation
The OP list (`op_list`) directly determines the witnesses used for main-chain stability and unit validity (`checkWitnessesKnownAndGood`, `main_chain.js` main-chain determination, `network.js` witness replacement). If nodes disagree on the emergency-derived OP list because they used different sets of not-yet-final "good" unstable votes, they will subsequently disagree on which units are on the best/main chain and which units are stable — a direct node disagreement on validity/stability, and potentially a chain split (network unable to reach consensus on new units), which matches the required "Accept" criteria (node disagreement on validity or stability / network unable to confirm new units). Because the OP list also gates unit stabilization and hence transaction finality, an attacker who can produce a burst of high-balance "good"-but-unstable `system_vote` units timed around the emergency-eligibility window could steer different subsets of nodes into different OP lists.

### Likelihood Explanation
Triggering the emergency path requires the network to be "stuck" for longer than `EMERGENCY_OP_LIST_CHANGE_TIMEOUT`, which is an unusual but reachable condition (e.g., if the sitting OPs go offline or censor witnessing, which is exactly the scenario this mechanism exists to remedy). Any ordinary unit poster can post `system_vote` and `system_vote_count` messages — no privileged key is required — so an attacker (or even honest, differently-synced nodes) can race to be the first "good" unstable voter set seen by each node before the emergency window opens, producing divergent local vote tallies. This is a realistic, single-poster-reachable trigger, though it depends on the network actually reaching the stuck/timeout state, which somewhat limits day-to-day likelihood but is precisely the condition the code was written to handle, so it is a live and intended-to-be-exercised code path, not a theoretical dead corner.

### Recommendation
Ensure the emergency and normal vote-counting mechanisms cannot diverge in outcome across honest nodes:
- Require unstable votes used in the emergency count to be from units that are provably included and ordered identically by every node reaching the timeout (e.g., only count votes from units for which finality of "goodness" — not just current local `sequence`, but graph-inclusion-consistent status — is guaranteed), or
- Gate the emergency recount behind a mechanism that itself requires the same degree of agreement as normal stabilization (e.g., require the *same* stable ordering used for last_ball selection), or
- Remove the separate emergency code path entirely and instead make normal `countVotes` resilient to a stuck main chain by adjusting the emergency trigger condition itself to be part of consensus (e.g., an on-chain, witness-signed acknowledgment) rather than a purely local wall-clock timeout combined with local `sequence='good'` opinions.

### Proof of Concept
Conceptual scenario (cannot be fully simulated without a live multi-node testnet, but derivable from the code paths cited):
1. The 12 OPs go silent long enough that no new unit is stabilized past MCI `M` for longer than `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (`main_chain.js:1938-1946`).
2. During the stuck period, several ordinary addresses (regular unit posters, no privileged key needed) post `system_vote`/`system_vote_count` (`subject: 'op_list'`) units. Because the DAG is not advancing to stability, these units remain "unstable" but are marked `sequence='good'` by each node based on that node's local view of conflicts (`writer.js`, `main_chain.js` sequence determination).
3. Two honest nodes, N1 and N2, whose local unstable-unit sets differ slightly (e.g., due to network partition/propagation delay) each independently pass the `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` check (`main_chain.js:1938-1946`) and call `countVotes(conn, mci, 'op_list', 1, ts)`.
4. `getUnstableVotes()` (`main_chain.js:1915-1933`) returns different vote sets on N1 vs N2 because it iterates `storage.assocUnstableMessages`/`assocUnstableUnits`, which reflect each node's own DAG state, not a globally agreed set.
5. `countVotes` computes and `REPLACE`s different `op_list` values in `system_vars` on N1 and N2 (`main_chain.js:1860-1876`, `1909-1912`), and each node subsequently uses its own new witness set for main-chain determination, causing a durable disagreement on unit validity/stability between N1 and N2.

Note: full exploitation requires controlling network timing/propagation to induce divergent unstable-vote sets across nodes during the stuck window; this was reasoned from static code paths and constants (`EMERGENCY_OP_LIST_CHANGE_TIMEOUT`, `EMERGENCY_COUNT_MIN_VOTE_AGE` — exact values not retrieved due to search-index truncation of `constants.js`) rather than empirically reproduced.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}

	cb();
}
