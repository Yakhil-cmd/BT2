### Title
`handleKLAYTransfer` Bypasses `isLockedKLAY` Emergency-Stop; `handleERC20Transfer` / `handleERC721Transfer` Bypass `onlyRegisteredToken` and `onlyUnlockedToken` — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge enforces token-registration and lock guards on every **outbound** (request) path but omits those same guards on every **inbound** (handle) path. A single bridge operator — the default threshold is 1 — can therefore:

1. Drain KLAY from the bridge even after the owner has called `lockKLAY()`.
2. Mint or transfer any ERC-20 token (registered or not, locked or not) by calling `handleERC20Transfer` with an arbitrary `_tokenAddress`.
3. Mint or transfer any ERC-721 token (registered or not, locked or not) by calling `handleERC721Transfer` with an arbitrary `_tokenAddress`.

---

### Finding Description

**Outbound path — guards present:**

`_requestKLAYTransfer` carries the `unlockedKLAY` modifier: [1](#0-0) 

`_requestERC20Transfer` carries both `onlyRegisteredToken` and `onlyUnlockedToken`: [2](#0-1) 

`_requestERC721Transfer` carries both `onlyRegisteredToken` and `onlyUnlockedToken`: [3](#0-2) 

**Inbound path — guards absent:**

`handleKLAYTransfer` only has `onlyOperators` and `nonReentrant`; `unlockedKLAY` is missing: [4](#0-3) 

`handleERC20Transfer` only has `onlyOperators`; `onlyRegisteredToken` and `onlyUnlockedToken` are missing: [5](#0-4) 

`handleERC721Transfer` only has `onlyOperators`; `onlyRegisteredToken` and `onlyUnlockedToken` are missing: [6](#0-5) 

**Default threshold is 1**, so a single operator suffices to reach the threshold and execute any of these calls unilaterally: [7](#0-6) 

The `lockKLAY` / `lockToken` / `unlockToken` owner-only controls exist precisely to provide an emergency stop: [8](#0-7) [9](#0-8) 

None of those controls have any effect on the handle path.

---

### Impact Explanation

| Handle function | Missing guard | Worst-case asset impact |
|---|---|---|
| `handleKLAYTransfer` | `unlockedKLAY` | Operator drains all KLAY held by the bridge after owner locks it |
| `handleERC20Transfer` (`modeMintBurn=true`) | `onlyRegisteredToken`, `onlyUnlockedToken` | Operator mints unbounded supply of any ERC-20 where the bridge holds minter role |
| `handleERC20Transfer` (`modeMintBurn=false`) | same | Operator transfers any ERC-20 balance held by the bridge to an arbitrary address |
| `handleERC721Transfer` | same | Operator mints or transfers any ERC-721 token |

The KLAY drain path is the most direct: after `lockKLAY()` is called, `handleKLAYTransfer` still executes `_to.call.value(_value)("")` with no guard: [10](#0-9) 

The ERC-20 mint path is the most severe: in `modeMintBurn` mode, `handleERC20Transfer` calls `ERC20Mintable(_tokenAddress).mint(_to, _value)` on any address the operator supplies, with no registration check: [11](#0-10) 

---

### Likelihood Explanation

- The default `operatorThresholds[ValueTransfer]` is **1**, so no collusion is required.
- Operators are registered by the bridge owner and are expected to be trusted relayers, but a compromised or malicious operator key is a realistic threat for a live bridge.
- The lock mechanism exists specifically to let the owner override operator activity during an incident; the missing guard defeats that design intent entirely.
- The Go-side relay (`handleRequestValueTransferEvent`) calls these handle functions automatically on every observed cross-chain event, meaning the attack surface is reachable from normal bridge operation: [12](#0-11) 

---

### Recommendation

Add the missing guards to each handle function:

```solidity
// BridgeTransferKLAY.sol
function handleKLAYTransfer(...) public onlyOperators unlockedKLAY nonReentrant { ... }

// BridgeTransferERC20.sol
function handleERC20Transfer(...) public onlyOperators onlyRegisteredToken(_tokenAddress) onlyUnlockedToken(_tokenAddress) { ... }

// BridgeTransferERC721.sol
function handleERC721Transfer(...) public onlyOperators onlyRegisteredToken(_tokenAddress) onlyUnlockedToken(_tokenAddress) { ... }
```

This mirrors the symmetry already present on the request side and ensures that `lockKLAY`, `lockToken`, and `deregisterToken` have the intended effect on both directions of the bridge.

---

### Proof of Concept

**KLAY drain after lock:**

1. Bridge owner calls `lockKLAY()` → `isLockedKLAY = true`.
2. Any subsequent call to `_requestKLAYTransfer` reverts with `"locked"`.
3. Operator calls `handleKLAYTransfer(txHash, from, attacker, bridgeBalance, nonce, blockNum, "")`.
4. No `unlockedKLAY` check fires; `_to.call.value(bridgeBalance)("")` succeeds; all KLAY is transferred to `attacker`.

**ERC-20 unbounded mint (modeMintBurn):**

1. Bridge owner calls `lockToken(tokenAddr)` → `lockedTokens[tokenAddr] = true`.
2. Any subsequent call to `requestERC20Transfer` reverts with `"locked token"`.
3. Operator calls `handleERC20Transfer(txHash, from, attacker, tokenAddr, 1e27, nonce, blockNum, "")`.
4. No `onlyRegisteredToken` or `onlyUnlockedToken` check fires; `ERC20Mintable(tokenAddr).mint(attacker, 1e27)` executes; attacker receives 1 × 10²⁷ tokens.
