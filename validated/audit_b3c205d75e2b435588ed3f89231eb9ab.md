### Title
Missing input/output vault distinctness check in `Swap` accounts allows same-vault reuse, corrupting curve invariant math and enabling vault drainage - (File: `programs/cp-swap/src/instructions/swap_base_input.rs`)

### Summary
The `Swap` account validation in `swap_base_input.rs` and `swap_base_output.rs` verifies `input_vault` and `output_vault` independently — each is only checked to be *one of* the pool's two vaults, with an inclusive-OR constraint. Nothing enforces that `input_vault` and `output_vault` resolve to *different* vaults. This is structurally analogous to the Angular `HttpTransferCache` bug: two semantically distinct roles ("input" and "output") can be satisfied by identical underlying key material (the same vault account), causing the program to reuse one resource's state for two conflicting purposes within the same request.

### Finding Description
In the `Swap` accounts struct:
```rust
#[account(
    mut,
    constraint = input_vault.key() == pool_state.load()?.token_0_vault || input_vault.key() == pool_state.load()?.token_1_vault
)]
pub input_vault: Box<InterfaceAccount<'info, TokenAccount>>,

#[account(
    mut,
    constraint = output_vault.key() == pool_state.load()?.token_0_vault || output_vault.key() == pool_state.load()?.token_1_vault
)]
pub output_vault: Box<InterfaceAccount<'info, TokenAccount>>,
``` [1](#0-0) 

Both constraints independently accept `token_0_vault` OR `token_1_vault`; there is no check that `input_vault.key() != output_vault.key()`. An attacker submitting the transaction fully controls which account is placed in each of the two vault slots, subject only to this OR-based check, so `input_vault == output_vault` is a valid combination that passes account validation.

`get_swap_params` (in `programs/cp-swap/src/states/pool.rs`) is fed `ctx.accounts.input_vault.amount` and `ctx.accounts.output_vault.amount` as the two reserve amounts used to determine trade direction and to seed the constant-product calculation: [2](#0-1) 

If the same vault account is supplied for both slots, `total_input_token_amount` and `total_output_token_amount` collapse to the *same* balance (the ambiguous "key" — the vault account — no longer disambiguates the two logically distinct reserves the curve math assumes). The subsequent invariant check:
```rust
require_gte!(constant_after, constant_before);
``` [3](#0-2) 
is computed against this confused pair of equal reserves rather than the pool's actual two distinct token reserves, so it no longer guarantees the real on-chain economic invariant across `token_0_vault` and `token_1_vault`.

Finally, the actual token movements are dispatched against the (identical) vault account:
```rust
transfer_from_user_to_pool_vault(..., ctx.accounts.input_vault.to_account_info(), ...)?;
transfer_from_pool_vault_to_user(..., ctx.accounts.output_vault.to_account_info(), ...)?;
``` [4](#0-3) 
so the program deposits into and withdraws from the *same* vault in one instruction, using amounts derived from curve math that was never designed to reason about a single reserve serving both roles simultaneously. The `output_token_mint`/`input_token_mint` are each constrained only by `address = input_vault.mint` / `address = output_vault.mint` respectively [5](#0-4) , so when `input_vault == output_vault`, both mints collapse to the same token, and none of the existing constraints prevent the transaction from proceeding.

### Impact Explanation
This lets an unprivileged swapper submit a single `swap_base_input`/`swap_base_output` transaction where the "input" and "output" vault are the same physical account. Because the invariant check and swap-amount math are derived from ambiguous, identical reserve readings rather than the pool's true two-sided balances, the resulting transfer amounts computed by the curve calculator no longer correspond to a valid constant-product trade against the real `token_0_vault`/`token_1_vault` pair. This breaks the fee/accounting invariant the AMM relies on and can permit withdrawing more value from the single reused vault than the invariant is meant to allow, causing insolvency of that vault relative to LP claims — i.e., theft/freezing risk analogous to the cache-key-ambiguity class in the reference advisory, where a security-relevant identity check silently accepted colliding key material for two distinct roles.

### Likelihood Explanation
High reachability: any signer can call `swap_base_input`/`swap_base_output` directly with attacker-chosen `input_vault`/`output_vault` accounts; the only gate is the OR constraint shown above, which both vault parameters can simultaneously satisfy by pointing to the same PDA. No elevated privileges, special build features, or off-chain components are required — this is purely an Anchor account-constraint gap in the instruction reachable by any unprivileged swapper in one transaction.

### Recommendation
Add an explicit constraint that `input_vault.key() != output_vault.key()` in the `Swap` accounts struct (in both `swap_base_input.rs` and `swap_base_output.rs`), and/or derive `input_vault`/`output_vault` unambiguously from `input_token_mint`/`output_token_mint` (each vault tied to exactly one mint side) rather than allowing either side to satisfy either vault independently.

### Proof of Concept
1. Attacker calls `swap_base_input` (or `swap_base_output`) with:
   - `pool_state` = a real pool,
   - `input_vault` = pool's `token_0_vault`,
   - `output_vault` = the *same* `token_0_vault` account (also passes the OR constraint since it equals `token_0_vault`),
   - `input_token_mint`/`output_token_mint` set to the corresponding (identical) mint per the `address = input_vault.mint` / `address = output_vault.mint` constraints,
   - `input_token_account`/`output_token_account` = attacker's own token accounts for that mint.
2. `get_swap_params` reads `input_vault.amount` and `output_vault.amount` from the same account, producing `total_input_token_amount == total_output_token_amount`, and the curve calculation computes an output amount based on this false symmetric-reserve assumption rather than the true `token_0_vault`/`token_1_vault` split.
3. The instruction executes `transfer_from_user_to_pool_vault` (deposit into `token_0_vault`) followed by `transfer_from_pool_vault_to_user` (withdrawal from the same `token_0_vault`), with the withdrawal amount derived from the corrupted invariant check rather than the real two-sided pool state, allowing the attacker to extract more value than a legitimate swap against the true reserves would permit.
