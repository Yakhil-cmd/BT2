### Title
`Api::CCMenuController#stack` bypasses `current_api_client.stack_id` scoping, enabling cross-stack CCMenu status read - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides the base class's `#stack` helper to call `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!(params[:stack_id])` used by `Api::BaseController`. This lets any holder of a stack-scoped `ApiClient` token (e.g. one issued to a legitimate CCMenu user for stack A) read the CCMenu XML deploy/rollback status of any other stack B by supplying B's `stack_id` in the URL while keeping A's token.

### Finding Description
The broken binding is: `stack` in `CCMenuController#show` should equal `current_api_client.stack_id`-authorized stack, i.e. `stacks.from_param!(params[:stack_id]) == Stack.where(id: current_api_client.stack_id).from_param!(params[:stack_id])`. Instead, `CCMenuController#stack` is defined as: [1](#0-0) 

which resolves `Stack.from_param!(params[:stack_id])` against the entire `Stack` table, with no reference to `current_api_client.stack_id` at all. Compare to `Api::BaseController`'s intended scoping: [2](#0-1) 

`ApiClient.authenticate` only verifies the signed token maps to an existing `ApiClient` row; it performs no scope check itself: [3](#0-2) 

The only permission gate on this controller is `require_permission :read, :stack`, which calls `check_permissions!`: [4](#0-3) 

This only checks whether the string `"read:stack"` is present in the client's `permissions` array — it never compares `stack_id` to the requested resource. So a client created via `CCMenuUrlController#fetch` for stack A, with `permissions: ['read:stack']` and `stack_id = A`, passes both `authenticate_api_client` and `require_permission!` when the URL's `params[:stack_id]` is actually stack B. `CCMenuController#stack` then happily resolves stack B via the unscoped `Stack.from_param!`, and `#show` renders B's latest deploy/rollback data.

Attacker request: `GET /api/stacks/<B_id_or_slug>/ccmenu.xml?token=<A's CCMenu token>`. Existing guards (`verify_signature`, permission subset validation, etc.) are irrelevant here since this is a same-engine authorization scoping bug, not a signature/webhook issue.

### Impact Explanation
An attacker who obtains (or is issued, as a normal legitimate user) a CCMenu token for a stack they have access to can use that same token to read the current deploy/rollback status (commit SHA context via `deploys_and_rollbacks`, running/ended state) of any other stack in the installation, including stacks belonging to unrelated repositories/teams. This is a cross-tenant unauthorized read of stack state, repeatable for every stack ID by iterating `stack_id` values, and requires no interaction from the victim stack's owners. This matches the "High - escalation ... unauthenticated read of stack state" category, since the token was never authorized for the target stack.

### Likelihood Explanation
Preconditions are trivial to meet: the attacker only needs to be a legitimate user (or holder) of any single valid CCMenu token for any stack (obtained normally via `CCMenuUrlController#fetch`, which any user with stack access can trigger), and knowledge/guessability of another stack's `stack_id`/slug. No secrets, GitHub credentials, or elevated roles are required. This is fully repeatable and low-cost — a single crafted URL per target stack.

### Recommendation
Change `Api::CCMenuController#stack` to use the scoped `stacks` collection from `Api::BaseController` instead of querying `Stack` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, removing the override entirely if no additional behavior is needed, or otherwise the override must scope by `current_api_client.stack_id` before rendering.

### Proof of Concept
Minitest (`ActionDispatch::IntegrationTest`), no live GitHub required:
1. Create `stack_a` and `stack_b` (`Stack.create!(...)`).
2. Create an `ApiClient` with `stack: stack_a`, `permissions: ['read:stack']`, and generate `token = api_client.authentication_token`.
3. `get api_stack_ccmenu_url(stack_id: stack_b.to_param, token: token)`.
4. Assert response is `200` (or `success`) and the rendered XML body contains stack B's deploy/rollback data (e.g. matches `stack_b.deploys_and_rollbacks.last.id` or similar identifying content), proving the token scoped to stack A leaked stack B's state.
5. As a control, assert that `stacks.from_param!(params[:stack_id])` (base controller behavior) would have raised `Stack::NotFound`/404 for the same token+stack_b combination, demonstrating the divergence introduced by the override.
