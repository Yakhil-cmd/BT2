Based on my research, the strongest local admission-boundary analog to the external report's "registration without full validation" pattern is in Aptos's **multisig transaction prologue**, where the check binding an *approved* payload to the *executed* payload is conditionally skipped.

### Title
Multisig transaction execution can bypass payload-match verification when `abort_if_multisig_payload_mismatch` is not enabled - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`validate_multisig_transaction()`, invoked by the VM prologue for every multisig-sourced transaction, is supposed to guarantee that the payload actually being executed is the same payload that the multisig owners voted to approve. For transactions created via `create_transaction` (full payload stored on-chain rather than only a hash), this binding check is gated behind the feature flag `abort_if_multisig_payload_mismatch_enabled`, mirroring the external report's pattern of a validation step existing in one code path but missing/optional in a sibling path.

### Finding Description
`validate_multisig_transaction` performs quorum/timelock checks (which validate *that enough owners approved something* at the pending sequence number) and then attempts to bind the provided execution payload to what was approved: [1](#0-0) 

Specifically:
- If the transaction was created with only a payload *hash* on-chain (`transaction.payload_hash.is_some()`), the check `sha3_256(payload) == *payload_hash` is unconditional and always enforced.
- If the transaction was created with the *full payload* stored on-chain (`transaction.payload.is_some()`), the corresponding equality check `payload == *stored_payload` is only performed **when** `features::abort_if_multisig_payload_mismatch_enabled()` is true, in addition to requiring the supplied `payload` argument be non-empty.

This means the invariant "the multisig account can only execute what the required quorum of owners actually approved" depends entirely on whether this specific feature flag has been activated on the network. If it has not been (or is rolled out only on some networks), an executing owner — who already possesses enough approvals for *some* pending transaction at the correct sequence number — can submit a `SignedTransaction` whose actual entry-function payload differs from the one the other owners voted on, and the prologue will not detect the mismatch for full-payload-stored multisig transactions.

This is structurally identical to the external bug's core defect: a binding/consistency check that exists in one code path (`payload_hash` comparison, always on) is missing or optional in the parallel code path (`payload` comparison, feature-gated), letting a state transition proceed under an approval set that does not actually correspond to what executes.

### Impact Explanation
If exploited while the feature flag is disabled, this allows a transaction to execute under the wrong "approval set" — i.e., the multisig account performs an action that the required number of owners never actually approved, since their votes were cast against a different payload. This is a direct violation of the "Authenticator/multisig approval validation accepting the wrong signing material or wrong approval set" admission invariant called out as in-scope. Depending on what payload substitution is used, this could let an owner (or an owner colluding with a limited quorum) execute arbitrary entry functions as the multisig account — e.g., withdrawing funds or rotating keys via a completely different call than what was approved.

### Likelihood Explanation
Exploitability is entirely conditioned on the on-chain state of the `abort_if_multisig_payload_mismatch_enabled` feature flag. I was not able to confirm from the available code index whether this flag is currently enabled by default/already activated on Aptos mainnet (feature flags in this codebase are typically rolled out and later made unconditional, and the surrounding code comments — e.g. "Once the feature is fully enabled, this function will be consolidated" — suggest this is a migration-era gate). If the flag is already permanently enabled on all live networks, this finding has no practical impact today; if it is still disabled anywhere multisig `create_transaction` (non-hash) accounts are used, the gap is live. I could not verify this default within the remaining investigation budget, so this should be confirmed before treating it as an active, exploitable issue.

### Recommendation
Make the full-payload equality check (`payload == *stored_payload`) unconditional, exactly as the hash-based check already is, removing the `features::abort_if_multisig_payload_mismatch_enabled()` gate (and the `!payload.is_empty()` allowance) so that any multisig transaction with a stored on-chain payload always verifies that the payload being executed matches what was approved, regardless of feature-flag rollout state.

### Proof of Concept
1. Create a multisig account with owners A, B, C and `num_signatures_required = 2`.
2. Owner A calls `create_transaction(owner_A, multisig_account, payload_X)` (full payload stored on-chain, not a hash), which auto-approves from A.
3. Owner B calls `approve_transaction(owner_B, multisig_account, sequence_number)`, reaching quorum (2 approvals) for `payload_X`.
4. On a network where `abort_if_multisig_payload_mismatch_enabled` is disabled, owner A submits a `SignedTransaction` whose actual raw-transaction payload is `payload_Y` (a different entry function/module/args) targeting the same multisig account and sequence number.
5. `validate_multisig_transaction` checks quorum (satisfied, 2 approvals) and timelock (satisfied), but since `transaction.payload_hash` is `None` and the feature flag is off, the `payload == *stored_payload` check for `payload_Y` vs. `payload_X` never runs.
6. The VM proceeds to execute `payload_Y` as the multisig account — an action never actually approved by B — via `successful_transaction_execution_cleanup` closing out the same sequence number: [2](#0-1) [3](#0-2)

/// Run the prologue for a multisig transaction. This needs to verify that:
/// 1. The multisig tx exists
/// 2. It has received enough approvals to meet the signature threshold of the multisig account
/// 3. If only the payload hash was stored on chain, the provided payload in execution should
/// match that hash.
pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };

    session
        .execute_function_bypass_visibility(
            &MULTISIG_ACCOUNT_MODULE,
            VALIDATE_MULTISIG_TRANSACTION,
            vec![],
            serialize_values(&vec![
                MoveValue::Signer(txn_data.sender),
                MoveValue::Address(multisig_address),
                MoveValue::vector_u8(provided_payload),
            ]),
            &mut UnmeteredGasMeter,
            traversal_context,
            module_storage,
        )
        .map(|_return_vals| ())
        .map_err(expect_no_verification_errors)
        .or_else(|err| convert_prologue_error(err, log_context))
}
