## Title
`Barrier`'s `DenyReserveTransferToRelayChain` is not applied recursively, allowing a local XCM program (via `pallet_xcm::execute`) to hide a forbidden reserve-transfer-to-Relay inside `SetAppendix`/`SetErrorHandler` - (File: `system-parachains/coretime/coretime-kusama/src/xcm_config.rs`)

### Summary
The Coretime-Kusama `Barrier` wraps `DenyReserveTransferToRelayChain` in `DenyThenTry` without the `DenyRecursively` adapter, so the deny check only inspects the top-level instruction sequence of an incoming/local XCM program. An unprivileged signed account can call the `pallet_xcm::execute` extrinsic (enabled here for `Everything`/any signed origin) with a program whose outer instructions pass `AllowTopLevelPaidExecutionFrom`, while a `DepositReserveAsset`/`InitiateReserveWithdraw`/`TransferReserveAsset` targeting the Relay chain is hidden inside a `SetAppendix`/`SetErrorHandler` sub-program that the top-level deny scan never inspects.

### Finding Description
The `Barrier` type is defined as: [1](#0-0) 

Unlike `bridge-hub-polkadot` and `bulletin-polkadot` in the same repository, which wrap the same denial rule as `DenyRecursively<DenyReserveTransferToRelayChain>` specifically to also inspect nested XCM programs: [2](#0-1) [3](#0-2) 

Coretime-Kusama, along with several other chains in this repo (Asset Hub, People, Collectives, Encointer, Bridge Hub Kusama), still uses the bare (non-recursive) `DenyReserveTransferToRelayChain`. `DenyReserveTransferToRelayChain::should_execute` only pattern-matches the top-level `Instruction` slice for `InitiateReserveWithdraw`/`DepositReserveAsset`/`TransferReserveAsset` with `dest`/`reserve == Parent`; it does not descend into the nested `Xcm<Call>` payloads carried by `SetAppendix(xcm)` or `SetErrorHandler(xcm)`.

The attacker-controlled entry path exists because Coretime-Kusama's `pallet_xcm::Config` allows any signed account to locally execute an arbitrary XCM program: [4](#0-3) 

Exploit flow:
1. Attacker (any signed account, no privilege needed) submits `pallet_xcm::execute` with an XCM program such as: `WithdrawAsset(own DOT)`, `BuyExecution`, `SetAppendix([DepositReserveAsset { dest: Parent, .. }])`.
2. `Barrier::should_execute` runs `DenyThenTry`: the deny scan sees only `WithdrawAsset`, `BuyExecution`, `SetAppendix` at the top level — none of these match the deny patterns, so `DenyReserveTransferToRelayChain` returns `Continue`. The fallback `AllowTopLevelPaidExecutionFrom<Everything>` then admits the program because it begins with `WithdrawAsset`+`BuyExecution`.
3. The executor runs the main program, then executes the stored appendix. The appendix's `DepositReserveAsset { dest: Parent, .. }` is executed without ever being re-checked by `Barrier::should_execute`, since only the top-level `prepare()` call invokes the barrier.
4. `DepositReserveAsset` withdraws from local holding (the attacker's own coretime-kusama balance) and sends a remote XCM (`ReserveAssetDeposited` + `DepositAsset`) to the Relay chain, instructing it to credit the beneficiary with native DOT — even though the Relay chain is the *original issuer* of DOT, not a reserve destination for it, and the corresponding sovereign-account backing on the Relay side is left untouched.

### Impact Explanation
This creates unbacked DOT: the attacker's local (derivative) DOT balance on Coretime-Kusama is spent/withdrawn locally, but the "reserve" message sent to the Relay chain results in the Relay chain minting/crediting the same value again via `ReserveAssetDeposited`/`DepositAsset`, with no corresponding debit to the Coretime-Kusama sovereign account held on the Relay. This is precisely the reserve-accounting inflation/imbalance that `DenyReserveTransferToRelayChain` exists to prevent, and it is bypassed here because the check is not recursive.

### Likelihood Explanation
Feasible and repeatable by any signed, funded account: `ExecuteXcmOrigin`/`XcmExecuteFilter` on Coretime-Kusama permit any signed origin to submit arbitrary local XCM programs, and constructing a `SetAppendix`-wrapped `DepositReserveAsset` is a standard, well-understood XCM crafting technique (which is exactly why `DenyRecursively` was introduced upstream and already adopted for `bridge-hub-polkadot`/`bulletin-polkadot` in this same repository, but not for Coretime-Kusama).

### Recommendation
Wrap the deny rule with the recursive adapter, matching the pattern already used elsewhere in this repository:
```rust
pub type Barrier = TrailingSetTopicAsId<
    DenyThenTry<
        DenyRecursively<DenyReserveTransferToRelayChain>,
        ( ... )
    >,
>;
```
Apply the same fix consistently to every chain in the repo that still uses the bare `DenyReserveTransferToRelayChain` (Asset Hub Kusama/Polkadot, People Kusama/Polkadot, Collectives, Encointer, Bridge Hub Kusama), not just Coretime.

### Proof of Concept
xcm-emulator/integration test plan for `coretime-kusama`:
1. Fund a test signed account with DOT on Coretime-Kusama.
2. Build XCM: `Xcm(vec![WithdrawAsset(dot.clone()), BuyExecution{..}, SetAppendix(Xcm(vec![DepositReserveAsset{ assets: All.into(), dest: Parent.into(), xcm: Xcm(vec![DepositAsset{..}]) }]))])`.
3. Submit via `PolkadotXcm::execute(signed_origin, versioned_xcm, weight_limit)`.
4. Assert the extrinsic does NOT complete with the reserve-transfer executed — expected (secure) behavior: `Outcome::Incomplete`/`Error::Barrier` similar to the existing top-level denial test in `integration-tests/emulated/tests/assets/asset-hub-polkadot/src/tests/reserve_transfer.rs` (`reserve_transfer_dot_from_relay_to_asset_hub_fails`), reusing that pattern's assertions.
5. Currently (bug present), the appendix's `DepositReserveAsset` executes and a `ReserveAssetDeposited`/`DepositAsset` message is delivered to and processed by the Relay chain, crediting the beneficiary — assert Relay chain beneficiary balance increases and Coretime-Kusama sovereign account on Relay is unchanged, demonstrating unbacked issuance.
