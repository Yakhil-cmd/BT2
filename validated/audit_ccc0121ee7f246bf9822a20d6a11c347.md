### Title
Malicious/compromised mint with an active freeze authority can freeze a pool vault token account and permanently block swap, deposit, withdraw and creator-fee collection for the entire pool - (File: programs/cp-swap/src/utils/token.rs, programs/cp-swap/src/instructions/{initialize.rs, withdraw.rs, deposit.rs, swap_base_input.rs, swap_base_output.rs, collect_creator_fee.rs, collect_creator_fee_permissionless.rs})

### Summary
`initialize` and `initialize_with_permission` permit anyone to permissionlessly create a pool for an arbitrary pair of mints, gated only by `is_supported_mint`. That check accepts any legacy `Token`-owned mint outright and only screens Token-2022 mints for a small extension allowlist; it never rejects mints that retain a `freeze_authority`. [2](#0-1) [1](#0-0)  Once the pool's vault ATA for that mint is created (owned by the pool `authority` PDA, but still freezable by the mint's freeze authority regardless of account owner), the malicious mint's freeze authority can call SPL Token's `FreezeAccount` at any later time to freeze the vault.

### Finding Description
Every liquidity-affecting instruction (`deposit`, `withdraw`, `swap_base_input`, `swap_base_output`, `collect_creator_fee`, `collect_creator_fee_permissionless`) performs `transfer_checked` CPIs against **both** `token_0_vault` and `token_1_vault` inside a single atomic instruction, e.g. in `withdraw` both `transfer_from_pool_vault_to_user` calls must succeed for the instruction to succeed. [3](#0-2)  The shared transfer helper simply issues `token_2022::transfer_checked` with no fallback or per-side handling. [4](#0-3)  If the mint's freeze authority freezes the corresponding vault token account, the SPL/Token-2022 program will reject any transfer instruction on that frozen account, so every one of these CPIs reverts. This is directly analogous to the report's pattern: a single malicious/attacker-controlled token asset can force a revert in a step that is a hard, no-alternative-path dependency for critical fund-releasing operations, and because both legs of the AMM pool are bundled atomically, the honest, unrelated token in the pool becomes unreachable too — freezing all LPs' funds, not just the malicious token holder's.

Unlike the original report's `PublicVault` bug (where liquidation of a single lien could be worked around eventually, and only blocked epoch bookkeeping), here the freeze is unilaterally reversible only by the mint's freeze authority (an off-chain, adversarial actor by definition) and directly blocks the withdrawal path — there is no alternative recovery instruction in this program.

### Impact Explanation
This results in a permanent freeze of all liquidity (both token sides) supplied to the pool, for every LP, since `withdraw` (the only exit path) requires both vault transfers to succeed atomically. [3](#0-2)  `swap_base_input`/`swap_base_output` and creator-fee collection are similarly blocked. This meets the "permanent freezing of user or LP funds" bar for a valid, high-severity finding, contingent on the fact that the mint's freeze authority is not vetted at pool-creation time.

### Likelihood Explanation
Likelihood is Medium: it requires that (a) a pool is created with a mint whose freeze authority is retained (easy — `is_supported_mint` does not check this, and pool creation via `initialize` is fully permissionless/unprivileged), and (b) that authority later freezes the vault account. Since freezing is an action taken by the token issuer (who is not a "swapper/LP" acting through the AMM program itself, but is a normal, foreseeable actor for any listed token), this is a realistic supply-chain/rug scenario common on Solana AMMs, and is the reason most production AMMs explicitly reject mints with a non-null `freeze_authority` at pool-creation time.

### Recommendation
In `is_supported_mint` (`programs/cp-swap/src/utils/token.rs`), in addition to screening Token-2022 extensions, explicitly reject any mint (legacy `Token` or `Token-2022`) whose `freeze_authority` is `Some(_)`, unless it is on the permissioned `SupportMintAssociated` allowlist. This closes the permissionless-pool-creation path for freezable mints, matching the report's underlying recommendation to vet third-party token behavior before it can be leveraged as an on-chain liquidity dependency, or alternatively to isolate each vault's transfer so a freeze on one side does not block operations for the healthy side.

### Proof of Concept
1. Attacker mints `M` via legacy `spl_token::create_mint` with `freeze_authority = Some(attacker)`.
2. Attacker calls `initialize` to create a CP pool for `(M, USDC)`; `is_supported_mint` passes `M` unconditionally because `*mint_info.owner == Token::id()` short-circuits to `Ok(true)`. [5](#0-4) 
3. Innocent LPs deposit `M`/USDC liquidity via `deposit`.
4. Attacker invokes SPL Token's `FreezeAccount` on `token_0_vault` (the `M` vault), using their retained freeze authority.
5. Any subsequent `withdraw`, `swap_base_input`, `swap_base_output`, `collect_creator_fee`, or `collect_creator_fee_permissionless` call now fails during the `transfer_checked` CPI touching the frozen vault, permanently locking both the `M` and USDC liquidity for all LPs in that pool.

pub fn is_supported_mint(
    mint_account: &InterfaceAccount<Mint>,
    mint_associated_is_initialized: bool,
) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;
    let extensions = mint.get_extension_types()?;
    for e in extensions {
        if e != ExtensionType::TransferFeeConfig
            && e != ExtensionType::MetadataPointer
            && e != ExtensionType::TokenMetadata
            && e != ExtensionType::InterestBearingConfig
            && e != ExtensionType::ScaledUiAmount
        {
            return Ok(false);
        }
    }
    Ok(true)
}
