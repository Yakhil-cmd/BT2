### Title
Webhook signature verified against the payload's `repository.owner.login` while handlers act on the unrelated `repository.full_name` field, allowing cross-organization webhook forgery in multi-GitHub-App deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App config (and thus the HMAC `webhook_secret`) used to validate `X-Hub-Signature` based on `repository.owner.login` (or `organization.login`) taken from the *same untrusted JSON payload* it is about to validate. All the event handlers, however, determine **which repository/stack/commit to mutate** using a different, unrelated field of that payload: `repository.full_name`. Because these two fields are never cross-checked against each other, in a multi-organization Shipit deployment an attacker who legitimately owns a GitHub App installation on one configured organization can forge a webhook whose signature is valid for *their own* org but whose `repository.full_name` points at a stack belonging to a *different* configured organization.

### Finding Description
`verify_signature` computes the org used for signature validation purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the GitHub App/webhook secret registered for that organization name (Shipit explicitly supports multiple GitHub Apps/organizations, each with its own `webhook_secret`): [3](#0-2) 

Once the signature is accepted, the actual event handlers resolve the target repository from a **different, independent field**: `repository.full_name`, with no comparison to the `repository.owner.login`/`organization.login` value that was used to pick the verifying secret: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

The `StatusHandler` is the worst case: it doesn't even scope by repository at all — it matches **any** `Commit` row globally by `sha`: [6](#0-5) 

The binding that should hold is://
`organization that authenticated the request (repository_owner used to pick webhook_secret)` == `repository that is written to (repository.full_name used by the handler)`

Before the attack: only webhooks whose signature is valid for organization X can affect repositories under X.
After the attack: an attacker who owns/administers a GitHub App on organization "AttackerOrg" (a legitimately configured org in the same Shipit instance) can sign a payload with `repository.owner.login = "AttackerOrg"` (passes `verify_webhook_signature` using AttackerOrg's own secret, which the attacker knows) while setting `repository.full_name = "VictimOrg/victim-repo"`. The handler then acts on VictimOrg's stack.

### Impact Explanation
This breaks a repository authorization boundary equivalent to "cross-repository writes" / "unauthorized deploy" in the impact matrix:
- Forging a `status` event lets the attacker inject a fabricated `success` CI status for an arbitrary existing commit `sha` in a victim's repository, potentially satisfying `ci.require` gating (README documents that `ci.require` statuses block deploys) and enabling an unauthorized deploy to proceed that should have been blocked by real CI.
- Forging a `push` event can trigger `stack.sync_github` for a victim stack the attacker does not own.
- Forging a `check_suite` event can trigger `RefreshCheckRunsJob` and PR handlers can mutate `PullRequest`/review-stack state for repositories the attacker has no legitimate relationship to (`pull_request/*_handler.rb` resolve repository purely from `repository.full_name`).

This exactly matches the required "organization that authenticated versus the repository that is written" binding break called out in scope.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured with multiple GitHub Apps for multiple organizations (the documented "Using Multiple Github Applications" feature) and the attacker to control (or be a malicious insider of) at least one of those configured organizations — no privileged Shipit account, `ApiClient` token, or `webhook_secret` of the *victim* org is needed, only the attacker's own webhook secret, which they legitimately possess by having their own app installed. This is a realistic configuration for any Shipit instance shared across a company hosting repos for multiple GitHub orgs. Single-organization deployments (the common case) are not affected because there is only one webhook secret to check against, though the same secret would still validate arbitrary `full_name` values for a repository that isn't tracked/known but that's not a security boundary in the single-org case.

### Recommendation
In `WebhooksController#verify_signature` and/or in `Webhooks::Handlers::Handler`, after determining `repository_owner` used to select the verifying `webhook_secret`, assert that it matches the owner encoded in `repository.full_name` (i.e. `full_name.split('/').first == repository_owner`) before dispatching to handlers, rejecting the webhook (422) on mismatch. Additionally, `StatusHandler` should scope `Commit` lookups by repository/stack rather than matching on `sha` globally.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`) with two GitHub Apps/orgs, e.g. `OrgOne` and `OrgTwo`, each with its own `webhook_secret`, as shown in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker legitimately administers the GitHub App for `OrgTwo` and thus knows `OrgTwo`'s `webhook_secret`.
3. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<victim commit sha in OrgOne/some-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using `OrgTwo`'s webhook secret and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "OrgTwo")` (from `repository.owner.login`), validates successfully against the attacker's own secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, updating CI status on the victim's commit in `OrgOne/some-repo` despite the request only being authenticated for `OrgTwo`. [8](#0-7) [9](#0-8)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))

      ].join(' '))
    end
