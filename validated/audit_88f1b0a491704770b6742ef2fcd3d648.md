Found it: the `MembershipHandler` breaks exactly the binding named in scope — "an organization that authenticated versus the repository/organization that is written."

### Title
Membership webhook trusts attacker-controlled `team.id` to bind an arbitrary GitHub organization/team into `Shipit.github_teams` authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a webhook delivery only against the organization named in `repository.owner.login` / `organization.login`, i.e. it proves "this payload was really sent by GitHub for organization X." [1](#0-0)  However `MembershipHandler#find_or_create_team!` binds the `Team` record — used by `User#authorized?` to gate access into `Shipit.github_teams` — using `find_or_create_by!(github_id: params.team.id)`, and only writes `team.organization = params.organization.login` **on first creation**. Once a `Team` row with a given `github_id` exists, any subsequent `membership` webhook (from *any* authenticated organization, since the signature check only proves the org field matches, not that the numeric `team.id` genuinely belongs to that org for GitHub Enterprise multi-org configs) that references the same `team.id` will reuse the existing team and just add/remove members, without ever re-validating that `team.id` still belongs to the org that authenticated the delivery. [2](#0-1) 

### Finding Description
`User#authorized?` — the check used to gate access to the whole app when `Shipit.github_teams` is configured — is purely: is this user a member of one of the `Shipit.github_teams`. [3](#0-2) 

`Shipit.github_teams` is derived from `oauth.teams` handles configured by the operator (e.g. `"my-org/admins"`), each resolved through `Team.find_or_create_by_handle`, which itself just fetches by `organization`+`slug` or looks it up live via the GitHub API for that org. [4](#0-3) 

The `MembershipHandler` is the only path that mutates `Membership` records (who belongs to which `Team`) from an inbound webhook, and it is keyed by `params.team.id` (an attacker-supplied, GitHub-numeric team id in the JSON body) — the `organization` field is recorded **only** at team creation time and is never re-checked against the authenticating organization on update: [5](#0-4) 

In a single-GitHub-App deployment this is not by itself exploitable (there is only one org's webhook secret configured, so all "membership" deliveries necessarily come from that one org and it owns all its team IDs). But in the documented multi-org configuration (`config/secrets.*.yml` supports keying `github:` by multiple orgs, each with its own `webhook_secret`) [6](#0-5)  the webhook-signature check treats each organization as an independent, mutually-untrusted principal — `Shipit.github(organization: repository_owner)` picks the specific org's secret to validate against. [7](#0-6)  If a lower-privileged organization "OrgB" is validly authenticated (its own webhook secret matches), it can fabricate a `membership` payload whose `organization.login` is `OrgB` but whose `team.id` collides with a `Shipit.github_teams`-authorizing team that was actually created under a different, higher-trust organization "OrgA" (team IDs across GitHub orgs are just sequential integers on github.com, and are guessable/discoverable via GitHub's public API). Because `find_or_create_by!(github_id: params.team.id)` finds the pre-existing `OrgA` team row and `organization` is never re-validated on the update branch, `OrgB`'s webhook can add an arbitrary `member.login` to that `OrgA`-controlled, authorization-relevant team, granting that user `authorized?` access — i.e. escalation into `Shipit.github_teams` authorization from a different, less-trusted authenticated organization. This is precisely the class of impact explicitly called out as valid ("High - escalation into `Shipit.github_teams` authorization").

### Impact Explanation
A team record that is used to gate `Shipit.github_teams` authorization (deciding who may log in/act as an authorized user in Shipit) can have its membership mutated by a webhook delivery that is only cryptographically bound to a *different* GitHub organization than the one that actually owns the team. This is a direct escalation into `Shipit.github_teams` authorization, matching the "organization that authenticated versus the repository/organization that is written" binding called out in the analog rules.

### Likelihood Explanation
This requires: (1) the operator running Shipit in the multi-organization GitHub App configuration with at least one lower-trust org connected, and (2) the attacker (an admin of that lower-trust org, or anyone able to trigger a `membership` webhook delivery from it) knowing/guessing a `team.id` (a small sequential integer, enumerable via GitHub's REST API for any team the attacker can see) that belongs to the higher-trust org and is used in `Shipit.github_teams`. Both preconditions are realistic for the documented multi-org feature, but the vulnerability is inert in the (more common) single-org configuration, so likelihood is moderate.

### Recommendation
In `MembershipHandler#find_or_create_team!`, always validate — on both create and lookup — that `team.organization == params.organization.login` (case-insensitively) before applying membership changes, and reject/log the event otherwise (mirroring how `WebhooksController#verify_signature` already treats each org as an independent trust boundary). Consider also scoping the `Team.find_or_create_by!` lookup by `[github_id, organization]` rather than `github_id` alone.

### Proof of Concept
1. Deploy Shipit with the multi-org GitHub App config, `OrgA` (trusted, referenced in `Shipit.github_teams`) and `OrgB` (lower-trust) both configured with their own `webhook_secret`.
2. `OrgA` has a team, e.g. `github_id: 1000`, that is part of `Shipit.github_teams`, already synced into Shipit as `Team(organization: "OrgA", github_id: 1000)`.
3. An attacker who administers `OrgB` looks up (or brute-forces, since GitHub team IDs are small sequential integers) a `team.id` of `1000`, and sends a `membership` webhook to Shipit, correctly signed with `OrgB`'s `webhook_secret`, with body:
```json
{
  "action": "added",
  "team": { "id": 1000, "name": "Whatever", "slug": "whatever", "url": "https://api.github.com/teams/1000" },
  "organization": { "login": "OrgB" },
  "member": { "login": "attacker-controlled-user" }
}
```
4. `verify_signature` succeeds because the signature is validated against `OrgB`'s own secret. `MembershipHandler#find_or_create_team!` finds the existing `Team` row by `github_id: 1000` (created under `OrgA`) and does not re-check `organization`, then adds `attacker-controlled-user` as a member. [2](#0-1) 
5. `attacker-controlled-user` now passes `User#authorized?` for `Shipit.github_teams`, having been added to an `OrgA` authorization team via a webhook only ever authenticated as `OrgB`. [3](#0-2) 

**Note:** I was unable to fully verify in-code whether GitHub team numeric IDs are practically enumerable/predictable cross-org from the outside (this is a property of GitHub's platform, not of this codebase), so the exploitability of step 3 rests on that external assumption; this should be validated independently before treating this as fully confirmed rather than a strong analog.

    class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
    end
