### Title
Unfiltered PR label injection into process environment reaching `Command#unbundled_env`/`PTY.spawn` - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) directly into the process environment hash with no allow-list, and this hash flows unfiltered through `TaskCommands#env`/`DeployCommands#env` into `Command#unbundled_env`, which is passed straight to `PTY.spawn`. Unlike deploy-triggered custom variables (`deploy.env`, `task.env`), which are always sanitized via `EnvironmentVariables#permit`/`VariableDefinition`, labels never pass through that whitelist, so an attacker-controlled label like `rubyopt` becomes `RUBYOPT=true` in the environment of the actual command executed on the deploy host.

### Finding Description
The broken binding: the question assumes `keys(Command#unbundled_env) == keys(deploy_spec.machine_env) ∪ keys(VariableDefinition list permitted by EnvironmentVariables#permit)`. Tracing the code shows this equality does not hold, because there is a third, unconstrained source of keys: PR labels.

- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does:
```ruby
def env
  return super unless pull_request.present?
  super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })
end
```
Any label name is uppercased and injected as a key with value `"true"` — no filtering, no denylist of sensitive names (`RUBYOPT`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, `RUBYLIB`, `GIT_SSH_COMMAND`, `BASH_ENV`, etc.). This is confirmed by the existing test `test/models/shipit/review_stack_test.rb:59-65` and `test/lib/shipit/task_commands_test.rb`/`deploy_commands_test.rb`, which show arbitrary label names (`WIP`, `BUG`) reach `env` verbatim.

- `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) merges `@stack.env` (which is `ReviewStack#env` for review stacks) directly:
```ruby
def env
  super
    .merge(@stack.env)
    .merge('SHIPIT_USER' => ..., ...)
    .merge(deploy_spec.machine_env)
    .merge(@task.env)
end
```
Nowhere in this chain is `EnvironmentVariables.with(env).permit(...)` invoked. `filter_deploy_envs`/`filter_rollback_envs` (`app/models/shipit/deploy_spec.rb:174-180`) exist and are used, but only against the *user-supplied* `deploy.env`/`task.env` attribute at trigger time (e.g., `Api::TasksController`/`Api::DeploysController` restricting the `env:` param to `TaskDefinition#variables`) — they are never applied to `@stack.env`/labels.

- `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) merges `@env.stringify_keys` last, so attacker-controlled keys win over `BASE_ENV`:
```ruby
def unbundled_env
  BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)
end
```
- `Command#start` (`lib/shipit/command.rb:85-101`) calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, executing the deploy step (e.g. `bundle exec cap ...`) with the attacker-controlled `RUBYOPT` set.

Attacker action: open/own a PR against a repository with Review Stacks enabled, add the label `rubyopt` to that PR (per the stated attacker capabilities). When `capture_labels`/the labeled webhook syncs `pull_request.labels`, any subsequent deploy/task run on that `ReviewStack` executes its deploy-spec commands (e.g. `bundle install`, `bundle exec cap ... deploy`) with `RUBYOPT=true` — or, with a more targeted label value abuse, other Ruby-interpreted startup flags — injected into the environment of the spawned process.

Why existing guards fail: `EnvironmentVariables#permit`/`NotPermitted` guards only the `deploy.env`/`task.env` params path (verified in `test/controllers/api/deploys_controller_test.rb` and `tasks_controller_test.rb`), not the labels-to-env path. `deploy_spec.machine_env`/`VariableDefinition` allow-lists are irrelevant here since labels bypass them entirely by construction.

### Impact Explanation
Any environment variable name can be injected into the exact process environment used by `PTY.spawn` for deploy/task command execution on the Shipit deploy host, for any repository that has Review Stacks enabled. `RUBYOPT` allows injecting arbitrary Ruby interpreter flags (e.g., `-e`, `-r` to require an attacker-supplied library) into any `ruby`/`bundle`-based deploy step, which is command/code execution on the deploy host — Critical severity (RCE via `Command`/`PTY.spawn`). This is repeatable on every deploy/task run for the review stack and against every repository that enables review stacks, since the flaw is generic to `ReviewStack#env`.

### Likelihood Explanation
Preconditions: the target repository must have Review Stacks enabled and use deploy steps invoking `ruby`/`bundle`/similar (very common, e.g. Capistrano/Bundler-based deploy specs as referenced in `deploy_spec/bundler_discovery.rb`). The attacker only needs to add a label to their own PR — no Shipit credentials, no GitHub team membership, and no elevated repository permission is assumed to be required per the stated threat model. Cost is minimal (a single label on a self-owned PR) and the exploit is repeatable on every review-stack deploy/task execution.

### Recommendation
Do not merge raw PR label names into the process environment unfiltered. Either: (1) remove/restrict the label-to-env feature to a fixed, explicit allow-list of variable names configured per-repository (mirroring `VariableDefinition`), (2) reject/strip label names matching known-sensitive interpreter/loader variables (`RUBYOPT`, `RUBYLIB`, `LD_PRELOAD`, `DYLD_*`, `BUNDLE_*`, `GIT_SSH*`, `BASH_ENV`, `PATH`, `IFS`, etc.), or (3) route `ReviewStack#env`'s label-derived hash through `EnvironmentVariables.with(...).permit(deploy_spec.deploy_variables)` (or an equivalent dedicated whitelist) before merging into `TaskCommands#env`/`DeployCommands#env`.

### Proof of Concept
In `test/lib/shipit/task_commands_test.rb`, add:
```ruby
test "#env does not allow labels to set sensitive interpreter env vars" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["rubyopt"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env

  refute env.key?("RUBYOPT"), "label-derived env leaked RUBYOPT into command environment"
end
```
Second assertion tying to the claimed binding, in `test/models/deploy_spec_test.rb` style:
```ruby
test "labels are rejected by the deploy variables whitelist" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["rubyopt"]
  task_env = Shipit::TaskCommands.new(shipit_tasks(:shipit_restart).tap { |t| t.stack = stack }).env

  assert_raises(Shipit::EnvironmentVariables::NotPermitted) do
    Shipit::EnvironmentVariables.with(task_env).permit(stack.deploy_spec.deploy_variables)
  end
end
```
