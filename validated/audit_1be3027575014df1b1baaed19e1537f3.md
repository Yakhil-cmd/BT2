### Title
BPF Upgradeable Loader `InitializeBuffer` can be frontrun because it does not require the authority account to sign - ([File: programs/bpf_loader/src/lib.rs])

### Summary
The `InitializeBuffer` instruction handler in `process_loader_upgradeable_instruction` sets the buffer authority from an instruction account that is never checked for a signature. Any transaction sender can call `InitializeBuffer` on an already-created (but not-yet-initialized) buffer account and name themselves as the authority, exactly analogous to the reported OpenQ bug where an unprotected initializer let an attacker frontrun the legitimate owner-setting transaction.

### Finding Description
`InitializeBuffer` only requires that the target buffer account currently be in `UpgradeableLoaderState::Uninitialized`; it does not require any signature from the account that becomes the buffer authority: [1](#0-0) 

Compare this with every other authority-mutating instruction on the same account type (`Write`, `SetAuthority`, `SetAuthorityChecked`, `DeployWithMaxDataLen`), which all explicitly check `is_instruction_account_signer` for the authority account before allowing state changes: [2](#0-1) [3](#0-2) 

`InitializeBuffer` is the sole exception — the "authority" pubkey passed at index 1 is only read via `get_key_of_instruction_account`, never signature-checked: [4](#0-3) 

Once the account exists on-chain (created by a preceding `system_instruction::create_account` targeting the buffer keypair, with owner set to `bpf_loader_upgradeable`) but before the legitimate deployer's `InitializeBuffer` instruction executes, the account state is `Uninitialized` and is a valid target for anyone to call `InitializeBuffer` on with an arbitrary authority pubkey they control. The `AccountAlreadyInitialized` guard then blocks the legitimate deployer's own `InitializeBuffer` call from succeeding afterward, leaving the attacker as the sole buffer authority.

As buffer authority, the attacker can subsequently call `Close`, which requires the (attacker-controlled) authority to sign, and redirects all lamports held by the buffer account (funded by the victim to make it rent-exempt) to a recipient of the attacker's choosing: [5](#0-4) 

This is the same bug class as the OpenQ report: an initializer function that assigns a privileged role (owner/authority) is not access-controlled and is executed in a transaction separate from account creation, enabling frontrunning to seize control.

### Impact Explanation
If the account creation (`CreateAccount`) and `InitializeBuffer` calls are submitted as two separate transactions — which the on-chain program itself does not prevent, even though the standard client helper `bpf_loader_upgradeable::create_buffer` bundles both instructions atomically in one transaction — an attacker observing the pending `CreateAccount` transaction can race a competing `InitializeBuffer` transaction naming themselves authority. This results in unsigned/unauthorized seizure of a privileged role and subsequent unsigned fund movement: the attacker can later `Close` the buffer and drain the rent-exempt lamports the victim deposited into it to an account of their choosing.

### Likelihood Explanation
Exploitability depends entirely on client behavior: if a deployer always uses the standard, atomic `create_buffer` helper (single transaction containing both `CreateAccount` and `InitializeBuffer`), there is no window to exploit, since instructions within one transaction cannot be interleaved by another transaction. The vulnerability only manifests if a caller manually splits account creation and initialization across two transactions. This narrows the practical likelihood compared to a universally-reachable bug, but the on-chain instruction itself provides no protection against this misuse, unlike its sibling instructions which all enforce signer checks.

### Recommendation
Require the authority account passed to `InitializeBuffer` to be a signer (consistent with `Write`, `SetAuthority`, and `SetAuthorityChecked`), so that only someone possessing the intended authority's private key can be named as buffer authority during initialization, closing the frontrunning window regardless of how the client constructs the transactions.

### Proof of Concept
1. Victim submits transaction A: `system_instruction::create_account(payer, buffer_pubkey, lamports, size, bpf_loader_upgradeable::id())`, signed by `payer` and `buffer_keypair`.
2. Victim intends to submit transaction B: `bpf_loader_upgradeable::InitializeBuffer` naming `victim_authority` as the buffer authority, but has not yet sent it (or it is still in flight).
3. Attacker observes transaction A land (buffer account now exists, owned by `bpf_loader_upgradeable`, state `Uninitialized`).
4. Attacker submits their own `InitializeBuffer` instruction referencing `buffer_pubkey` (account 0) and `attacker_pubkey` (account 1, no signature required) before victim's transaction B lands.
5. Per `process_loader_upgradeable_instruction`'s `InitializeBuffer` handling [1](#0-0) , the buffer state becomes `Buffer { authority_address: Some(attacker_pubkey) }`.
6. Victim's transaction B now fails with `AccountAlreadyInitialized`.
7. Attacker signs and submits a `Close` instruction with `attacker_pubkey` as authority, draining the buffer's lamports (funded by the victim's `CreateAccount` call) to an attacker-controlled account, per `common_close_account` invoked from the `Close` handler [5](#0-4) .
