### Title
`StatusHandler#process` looks up commits by SHA globally, without checking the webhook's repository against the commit's stack — cross-repository status injection triggers unauthorized deploys - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves commits with `Commit.where(sha: params.sha)`, which is **not scoped to the repository that sent the webhook**, unlike the `stacks`/`repository_name` helpers the base `Handler` class provides for exactly this purpose. If the same SHA also exists as a `Commit` row belonging to a different stack (a realistic scenario for forked/shared upstream commits), an attacker-controlled webhook for their own repo can write a `success` `Status` onto the victim's commit and drive that victim stack's continuous-delivery pipeline into deploying.

### Finding Description
The broken binding is: `repository_name(payload) == commit.stack.repository.full_name` (i.e., the repo that authenticated/emitted the webhook must equal the repo owning the commit the status is attached to). This equality is enforced by other handlers via `Handler#stacks` / `Handler#repository_name` [1](#0-0)  but `StatusHandler#process` never calls it — it queries `Commit` purely by `sha`: [2](#0-1) 

`Commit` rows are per-stack (`belongs_to :stack`) [3](#0-2) , so the same SHA landing in two stacks' history produces two distinct `Commit` records sharing a `sha`. `Commit.where(sha: params.sha).each` will iterate over *all* of them regardless of which repository's webhook produced the payload.

Upstream, `verify_signature` in `WebhooksController` only checks that the request is validly signed for the organization named in `payload['repository']['owner']['login']` [4](#0-3) ; it proves the webhook genuinely came from the attacker's own org (`attacker`), not that the org is authorized for the target commit/stack. It never inspects which stack's commit the status will be attached to.

Once a `Commit` matching the attacker-chosen SHA is found under the victim's `Stack B`, `create_status_from_github!` writes a `Status` scoped by that commit's own `stack_id` [5](#0-4) , then the `after_commit` hook fires `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` for `commit.stack` (Stack B) if the commit is `deployable?` and the stack has continuous deployment enabled [6](#0-5) [7](#0-6) . That job calls `Stack#trigger_continuous_delivery`, which picks `next_commit_to_deploy` from Stack B's own commit list and calls `trigger_deploy(commit, Shipit.user, ...)` — an actual deploy of Stack B run as the system actor `Shipit.user`, with no re-check that the triggering webhook's repository matches Stack B's repository [8](#0-7) .

**Exploit flow:** Attacker owns `attacker/decoy`, which is itself a repo/stack configured in the same Shipit instance (so the GitHub App/org "attacker" is already known to `Shipit.github(organization:)`, satisfying `verify_signature`). Attacker crafts an empty commit whose SHA X also exists as a real `Commit` row in victim `Stack B` (from a prior legitimate sync of shared upstream history). Attacker's own CI fires a `status` webhook for SHA X with `state: success` and `repository.full_name = attacker/decoy`. The signature check passes (it's genuinely signed for `attacker`'s org). `StatusHandler#process` finds *both* the decoy's commit and Stack B's commit by SHA and creates a `success` Status on Stack B's commit, potentially unblocking/triggering `Stack#trigger_continuous_delivery` and an unauthorized deploy of Stack B.

**Why existing guards fail:** `verify_signature` validates *who sent* the webhook, not *which repository's data it may touch*; `ExplicitParameters` in `StatusHandler` validates only shape (`sha`, `state`, etc.), not repository ownership; and the handler simply never applies the `repository_name`/`stacks` scoping that would have prevented cross-repository matching.

### Impact Explanation
This is a **payload for one repository mutating another's stack/commit and triggering an unauthorized deploy** — matching the Critical severity category explicitly listed in scope. The attacker fully controls timing and payload of their own webhook and can repeat this against any stack that happens to share a commit SHA with a repo they control (a realistic condition for shared upstream/open-source history, cherry-picks, or squash-merges reproducing identical trees). The deploy executes as `Shipit.user`, bypassing any check that the acting party is an authorized deployer of Stack B.

### Likelihood Explanation
Preconditions: (1) attacker's own repo/org must already be integrated with the same Shipit instance (self-service, not privileged) so `verify_signature` succeeds; (2) a SHA collision must exist between attacker's repo history and the victim stack's `commits` table — realistic for forks/shared upstream commits, especially empty/no-op commits which are trivial for an attacker to reproduce byte-for-byte (since SHA depends on tree, parent, author/committer, timestamps — an attacker with knowledge of the victim's ingested commit metadata could construct an identical commit, or simply wait for a naturally shared commit such as a vendored dependency bump). Once the precondition holds, the attack is trivially repeatable at will via the attacker's own CI.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the webhook's own repository, e.g. restrict to commits whose `stack` is in `stacks` (as derived from `repository_name(payload)`), consistent with the pattern in `Handler#stacks`:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This enforces `repository_name(payload) == commit.stack.repository.full_name` before any status/CD side effects occur.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, but described conceptually since `test/**` is out of scope for delivered code but required for validation per the rules):
1. Create `stack_a` (decoy) owned by `attacker/decoy` and `stack_b` (victim) owned by `victim/app`, with `stack_b.continuous_deployment? == true`.
2. Create two `Commit` rows with the identical `sha = "deadbeef..."`, one under `stack_a`, one under `stack_b`; ensure `stack_b`'s commit is the newest undeployed commit.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call('sha' => 'deadbeef...', 'state' => 'success', 'repository' => { 'full_name' => 'attacker/decoy', 'owner' => { 'login' => 'attacker' } })`.
4. Assert: `stack_b.statuses.count` increased (status leaked into victim stack) — i.e., `commit.stack.repository.full_name` ("victim/app") never equaled `repository_name(payload)` ("attacker/decoy") yet the write succeeded.
5. Perform the enqueued `ContinuousDeliveryJob` and assert `Deploy.where(stack: stack_b).count` increased, proving an unauthorized deploy of Stack B was triggered from a webhook that only ever authenticated `attacker/decoy`.
