### Title
Webhook signature verification binds only to the signing organization, not to the repository a `status` (or `push`) event actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization config to check the HMAC signature against using a field read out of the *same, attacker-controlled* JSON body (`repository.owner.login`, falling back to `organization.login`), then hands the *entire* parsed body to event handlers such as `StatusHandler`, which act on data (`sha`) with no re-check that it belongs to the organization whose secret produced the signature. This breaks the intended binding "organization that authenticated the webhook" == "repository/commit that gets written," the same class of bug as the reported `_vestingInterest()` flaw where a value that is supposed to gate/limit an effect (elapsed vesting time / HMAC-verified org) doesn't actually constrain the value that is ultimately used (`totalAssets()` / the target commit-status row).

### Finding Description
`verify_signature` selects which organization's webhook secret to validate against purely from the incoming payload: [1](#0-0) [2](#0-1) [3](#0-2) 

`Shipit.github(organization: repository_owner)` looks up a per-organization app/secret from `secrets.github` and verifies the `X-Hub-Signature` HMAC over the raw body using only that organization's `webhook_secret`: [4](#0-3) [5](#0-4) 

A valid signature therefore proves only "this exact byte string was HMAC-signed with organization X's secret." It says nothing about which *other* fields inside that same JSON body (e.g. `sha`, `repository.full_name`) the sender chose to put there — those are entirely attacker-controlled as long as the attacker knows one organization's `webhook_secret` in a multi-tenant Shipit deployment.

`StatusHandler`, which is invoked once the signature check passes, uses the attacker-supplied `sha` with **no repository/organization scoping at all**: [6](#0-5) 

`Commit.where(sha: params.sha)` matches across every stack/repository in the whole Shipit instance. Nothing ties `sha` back to `repository_owner` (the field that was actually verified) or even to the `repository.full_name` field in the same payload. `PushHandler` has the analogous gap one level up: it resolves stacks via `payload.dig('repository', 'full_name')`, a field never covered by the signature-selection logic, and then calls `stack.sync_github(expected_head_sha: params.after)`: [7](#0-6) [8](#0-7) 

So the equality that should hold — `organization authenticated by HMAC == organization/repository whose commit/stack state is mutated` — is never enforced. It only accidentally holds for legitimate GitHub-originated traffic, exactly like the vesting bug only "accidentally" avoided MEV when nobody called `totalAssets()` right after an update; the code path itself performs no binding check.

### Impact Explanation
Any party who has legitimate, unprivileged access to one organization's configured `webhook_secret` in a multi-tenant Shipit install (e.g., they are simply an org admin who set up their own GitHub App/webhook, with zero access to the victim's repository, no Shipit session, no `ApiClient` token) can forge a `status` webhook: compute the HMAC with their own secret, but set `repository.owner.login`/`organization.login` to their own org (so `verify_signature` passes) while setting `sha` to a commit SHA belonging to a victim repository/stack hosted on the same Shipit instance. `StatusHandler#process` will then create a fabricated `Status` (`state`, `context`, `target_url`, `description`) on that victim commit via `commit.create_status_from_github!`, with no cross-check against the real GitHub API state for that repository. Since Shipit's deploy checklist/checks rely on commit statuses to determine whether a commit is safe to ship, this lets the attacker inject a fabricated passing (or failing) status on a commit they don't control, directly threatening the "unauthorized deploy" impact category.

### Likelihood Explanation
High for anyone onboarded as a tenant organization in a shared/multi-org Shipit deployment (a documented supported configuration, see `Shipit.github_app_config`/`TOP_LEVEL_GH_KEYS`): they need only their own valid webhook secret and a public commit SHA from the victim repo (trivially obtainable from GitHub) — no privileged Shipit credential, GitHub App key, or repository write access to the victim is required.

### Recommendation
Bind the verified organization to the data the handler acts on: after HMAC verification, re-derive `repository_owner`/`repository.full_name` from the verified payload and pass it explicitly into handlers, and have handlers (especially `StatusHandler`) scope their lookups by the verified repository/organization instead of a global `Commit.where(sha:)`/repository-name string taken from the unauthenticated-relative-to-that-field payload. Concretely, `StatusHandler` and `PushHandler` should filter through `Repository.from_github_repo_name(repository_name)` and additionally assert that `repository_name`'s owner matches the `repository_owner` that was used to select the verifying `GitHubApp`.

### Proof of Concept
1. Attacker controls organization `attacker-org`, configured in Shipit's multi-org `secrets.github` with its own `webhook_secret = S`.
2. Victim organization `victim-org` owns repo `victim-org/victim-repo`, tracked as a Shipit stack, with commit `abcdef123...` pending CI.
3. Attacker builds a JSON body:
```json
{
  "sha": "abcdef123...",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
4. Attacker signs the raw body with `S` and sends `POST /webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<HMAC(S, body)>`.
5. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and verifies successfully because it uses the attacker's own valid secret [9](#0-8) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the victim's commit `abcdef123...`, creating a fabricated `success` status on it [6](#0-5) , even though the signature never authenticated anything about `victim-org` or that commit.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
