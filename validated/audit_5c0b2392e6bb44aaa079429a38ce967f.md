### Title
`TaskCommands#env` lets an attacker-controlled `shipit.yml` (`machine.environment`) override `GIT_ASKPASS`/`GITHUB_TOKEN`, letting a PR exfiltrate the GitHub token - (File: `lib/shipit/task_commands.rb`, `app/models/shipit/deploy_spec.rb`)

### Summary
`TaskCommands#env` merges `deploy_spec.machine_env` — sourced from the repository's own `shipit.yml`, checked out at the commit being deployed — after the base environment that sets `GITHUB_TOKEN` and `GIT_ASKPASS`. Because later keys win in `Hash#merge`, a `shipit.yml` that sets `machine.environment.GIT_ASKPASS` (or `GITHUB_TOKEN`) silently overrides Shipit's own credential-handling variables in the environment ultimately passed to `PTY.spawn`.

### Finding Description
The broken binding: `Command#unbundled_env`'s `GIT_ASKPASS`/`GITHUB_TOKEN` keys should always be the values set by `Commands#base_env` (`Shipit.github.token`, `lib/snippets/git-askpass`) == the values actually present in the process spawned by `PTY.spawn`. This does not hold.

- `Commands#base_env` sets `GITHUB_TOKEN` and, if `Shipit.use_git_askpass?`, `GIT_ASKPASS` to the trusted internal script path: [1](#0-0) 
- `TaskCommands#env` calls `super` (which returns `base_env`) and then merges, in order, `@stack.env`, a hash of task metadata, and finally `deploy_spec.machine_env`, then `@task.env`: [2](#0-1) 
- `deploy_spec.machine_env` reads directly from `config('machine', 'environment')`, i.e., the `machine.environment` key of the repository's `shipit.yml`: [3](#0-2) 
- `TaskCommands#deploy_spec` builds a `DeploySpec::FileSystem` from `@task.working_directory`, which is the checkout of the commit the task is executing against (attacker's PR head for a review stack task): [4](#0-3) 
- `Command#unbundled_env` merges `@env` (the merged hash from `TaskCommands#env`) on top of `BASE_ENV`, and `Command#start` passes this directly to `PTY.spawn`: [5](#0-4) 
- The credential-retrieval script itself reads `GITHUB_TOKEN` from the environment when invoked as the git askpass helper: [6](#0-5) 

Root cause: there is no allowlist/denylist filtering `machine.environment` keys before merging into the task's spawned-process environment; the merge order places attacker-controlled config after the trusted base env, so any key collision favors the attacker. Nothing in `EnvironmentVariables` (used only for `${VAR}` interpolation in command strings, not for filtering `machine_env` keys) or in `DeploySpec` prevents this. I found no `RESERVED`/blocklist mechanism guarding `machine.environment` key names anywhere in the codebase.

Exploit flow (contingent on the stated precondition — a repo where `provision?` precedence causes review stacks to auto-provision despite `review_stacks_enabled: false`): an attacker opens a PR from their fork whose `shipit.yml` contains:
```yml
machine:
  environment:
    GIT_ASKPASS: /path/attacker/exfil-askpass.sh
```
or overrides `GITHUB_TOKEN` directly. When Shipit auto-creates/provisions the review stack and runs any task (`install_dependencies`, `deploy`, `perform`) against the checked-out PR commit, `TaskCommands#env` computes the environment, the attacker's `GIT_ASKPASS` value wins the merge, and `Command#start` spawns the process (e.g., `git fetch`/`git clone` operations in `StackCommands`/`TaskCommands`, which also use `env` built the same way) with that value. Git then executes the attacker's script as the askpass helper, and since `GITHUB_TOKEN` is present in the same process environment (unless also overridden to be blank, in which case the attacker's script can instead read the real value before it's overwritten, or simply exfiltrate whatever `GITHUB_TOKEN`/`GIT_ASKPASS` combination is present at invocation time), the attacker's script can exfiltrate the app's GitHub token.

### Impact Explanation
An attacker-authored script executes on the Shipit deploy host with access to `GITHUB_TOKEN`, the organization-scoped GitHub token used for all git operations against the repository (and potentially reused for the organization via `Shipit.github(organization:)`). This is a Critical impact per the taxonomy: "exfiltration of `GITHUB_TOKEN`". Blast radius: the leaked token is the app's GitHub App / organization token, not scoped to just the attacker's fork, so it can potentially be used to interact with other repos in the same GitHub organization/installation, or its capabilities depending on how `Shipit.github` scopes the token. This is a single-tenant compromise root that escalates into full RCE and credential theft on the deploy host — it should be treated as Critical.

### Likelihood Explanation
This finding depends entirely on the precondition already identified in the linked `provision?` precedence question: a repository must be misconfigured (`review_stacks_enabled: false` combined with `allow_with_label`/`prevent_with_label`) such that an unauthorized PR can still cause a review stack to be auto-provisioned and tasks to run against attacker-controlled content. Given that precondition, the cost to the attacker is trivial: open a PR with a crafted `shipit.yml`, no privileged access needed. Without that precondition, an attacker cannot get their own `shipit.yml` executed as the task's `deploy_spec` unless they already have write access to the target branch (a legitimate use case, not an attack). I was not able to independently re-verify the `provision?` precedence bug in this session (it is the subject of a separate question), so this finding's real-world reachability is conditional on that bug being valid.

### Recommendation
- In `DeploySpec#machine_env` (or in `TaskCommands#env`), filter out reserved/security-sensitive keys (`GIT_ASKPASS`, `GITHUB_TOKEN`, `GITHUB_DOMAIN`, and any other credential-related env vars) from user-supplied `machine.environment` before merging.
- Alternatively/additionally, reorder the merge in `TaskCommands#env` so that the trusted `base_env` (from `Commands#base_env`) is applied last, or explicitly re-assert `GIT_ASKPASS`/`GITHUB_TOKEN` after merging `deploy_spec.machine_env`.
- Ensure `deploy_spec.machine_env` for review-stack tasks is validated against a strict allowlist of variable names that excludes anything matching known credential/env-injection vectors.

### Proof of Concept
Add to `test/lib/shipit/task_commands_test.rb`:
```ruby
test "#env never lets deploy_spec.machine_env override GIT_ASKPASS or GITHUB_TOKEN" do
  stack = shipit_stacks(:review_stack)
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  commands = Shipit::TaskCommands.new(task)
  commands.stubs(:deploy_spec).returns(
    stub(
      machine_env: {
        'GIT_ASKPASS' => '/tmp/attacker-askpass.sh',
        'GITHUB_TOKEN' => 'attacker-value',
        'directory' => nil
      },
      env: {}
    )
  )

  Shipit.stubs(:use_git_askpass?).returns(true)
  trusted_askpass = Shipit::Engine.root.join('lib', 'snippets', 'git-askpass').realpath.to_s
  Shipit.github(organization: stack.repository.owner).stubs(:token).returns('real-github-token')

  env = commands.env

  assert_equal trusted_askpass, env['GIT_ASKPASS'], "attacker-controlled shipit.yml overrode GIT_ASKPASS"
  assert_equal 'real-github-token', env['GITHUB_TOKEN'], "attacker-controlled shipit.yml overrode GITHUB_TOKEN"
end
```
Given the current implementation of `TaskCommands#env` ( [2](#0-1) ), this test fails: `env['GIT_ASKPASS']` equals `/tmp/attacker-askpass.sh` and `env['GITHUB_TOKEN']` equals `attacker-value`, demonstrating the override.
