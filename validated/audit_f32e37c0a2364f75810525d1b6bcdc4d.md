### Title
`review_stacks_enabled` toggle is bypassed for `allow_with_label`/`prevent_with_label` behaviors due to operator precedence in `provision?` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `repository.review_stacks_enabled` with the three provisioning-behavior branches using `&&`/`||` without parentheses, so `review_stacks_enabled` only gates the `allow_all` branch and never gates the `allow_with_label`/`prevent_with_label` branches. As a result, an attacker who opens an unlabeled PR against a repository configured with `provisioning_behavior: :prevent_with_label` gets a review stack created and queued for provisioning even when the operator has explicitly left (or set) `review_stacks_enabled: false`.

### Finding Description
Binding claimed by the operator's intent vs. actual code:
`repository.review_stacks_enabled == false` should imply `provision? == false` for every branch, but in code `provision?` is:

```ruby
repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? ||
  (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
  (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
``` [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. `review_stacks_enabled` is only ANDed into the first disjunct. The second and third disjuncts are evaluated completely independently of `review_stacks_enabled`.

`pull_request_has_provisioning_label?` is `pull_request_label_names.include?(repository.provisioning_label_name)` [2](#0-1) 
For an unlabeled PR, `pull_request_label_names` is `[]`, so `[].include?(x)` is `false` for any `x` — nil or a configured string. So for `provisioning_behavior_prevent_with_label?` repositories, the third disjunct evaluates to `true` for every unlabeled PR, unconditionally of `review_stacks_enabled`.

Attacker path: open a pull request (`action: "opened"`) against a repository configured (by the operator, intentionally or by leaving defaults) with `provisioning_behavior: prevent_with_label` while `review_stacks_enabled` is `false`. `OpenedHandler#process` calls `respond_to_pull_request_opened?` → `provision?`, which returns `true`, so `ReviewStackAdapter#find_or_create!` creates/updates a `Shipit::Stack` and enqueues it for provisioning via `Shipit::Repository`/`Shipit::ReviewStackProvisioningQueue`. [3](#0-2) 

The identical pattern exists in `ReopenedHandler#unarchive?`, which will unarchive a stack on the same misconfiguration. [4](#0-3) 

None of the standard webhook guards mitigate this: `respond_to_pull_request_opened?` only checks `params.action == "opened"` and delegates to the flawed `provision?`; there is no repository-level validation enforcing `review_stacks_enabled` consistency across behaviors; the `Repository` model has no validation tying `provisioning_behavior`/`provisioning_label_name` to `review_stacks_enabled`. [5](#0-4) 
This is purely an application-logic (boolean-precedence) defect, not something signature verification or `ExplicitParameters` schema checks would catch.

### Impact Explanation
On any repository the operator has configured with `provisioning_behavior: :prevent_with_label` — including the unconfigured/default state where `provisioning_label_name` is `nil` — any unprivileged GitHub user able to open a PR against that repository can force `Shipit::Stack` creation and queue it for provisioning, even though the operator disabled dynamic review stacks (`review_stacks_enabled: false`). What actually happens after queuing (whether a `ProvisioningHandler#up` executes real infrastructure/`Command` calls) depends on the host application's registered `ProvisioningHandler`; the shipped default handler (`Shipit::ProvisioningHandler::Base`) is a no-op. This is repeatable against every repository sharing this misconfiguration and is confined to the PR's own repository (no cross-tenant stack mutation observed).

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior` set to `prevent_with_label` (or `allow_with_label`, for the labeled case) while `review_stacks_enabled` is `false` — this is a plausible, easy-to-reach misconfiguration (it's the literal default/unconfigured state described in the question) since the docs describe `review_stacks_enabled` as the master "Dynamically provision stacks for Pull Requests?" toggle that operators expect to gate all behaviors. [6](#0-5) 
The attacker only needs the ability to open a PR against a public/forkable repository tracked by Shipit — no Shipit credentials required.

### Recommendation
Add explicit parentheses in `provision?` (and the identical logic in `ReopenedHandler#unarchive?`, and check `LabeledHandler`/`UnlabeledHandler` for the same operator-precedence issue) so that `review_stacks_enabled` gates all three behavior branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
1. Configure repository: `review_stacks_enabled: false`, `provisioning_behavior: :prevent_with_label`, `provisioning_label_name: nil`.
2. Build `payload_parsed(:pull_request_opened)` with `payload["pull_request"]["labels"] = []` (unlabeled PR).
3. Assert binding before: intended `repository.review_stacks_enabled == false` should imply no stack creation.
4. Call `OpenedHandler.new(payload).process`.
5. Assert `Shipit::Stack.count` increased by 1 (i.e., `assert_difference -> { Shipit::Stack.count } do ... end`), demonstrating the actual state diverges from the intended binding — a stack is created/queued despite `review_stacks_enabled: false`.

# Enabling Review Stacks

Review stacks can be enabled via the shipit-engine Repository UI.

1. Visit the shipit-engine Repository UI - `https://host-application/repositories`
1. Click on the project's repository
1. Check "Dynamically provision stacks for Pull Requests?"
1. Select the "Provisioning Behavior" appropriate for your project - most likely "Allow All"
1. Click "Save"

# Configuring Review Stack behavior

shipit-engine support three distinct behaviors for determining which Pull Requests should be considered for Review Stack creation.

1. "Allow All" - shipit-engine will create a Review Stack for every new Pull Requests.
1. "Allow With Label" - when creating or updating a Pull Request, the user must add a label matching the `Shipit::Repository`'s "provisioning_label" attribute in order for shipit-engine to dynamically create/manage a Review Stack - an opt-in strategy.
1. "Prevent With Label" - when creating or updating a Pull Request, the user must add a label matching the `Shipit::Repository`'s "provisoining_label" attribute in order to **prevent** shipit-engine from dynamically creating/managing a Review Stack - an opt-out strategy.
```
