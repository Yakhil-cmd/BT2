## Confirmed vulnerability found

This is a genuine finding, not the ternary-flip pattern from the M-6 report directly, but the same class of bug: **a value that is checked/authenticated for one purpose is silently decoupled from the value that is actually acted upon** — exactly the "organization that authenticated versus the repository that is written" binding called out in scope.

### Title
Webhook signature is verified against the `repository.owner.login` while all processing keys off `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to HMAC-verify against using `repository_owner`, i.e. `params.dig('repository', 'owner', 'login')`. Once the signature is accepted, `create` dispatches the *entire raw JSON payload* to the event handlers, which never re-check `repository.owner.login` — they instead resolve the target `Stack`/`Commit` using `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb` `repository_name`) or, for the `status` event, an unscoped `Commit.where(sha: params.sha)` lookup with no repository check at all (`app/models/shipit/webhooks/handlers/status_handler.rb`). ### Finding Description
Shipit supports hosting multiple independent GitHub Apps/organizations, each with its own `webhook_secret`, configured under `secrets.github.<organization>` (see `lib/shipit.rb` `github_app_config`, and `docs/setup.md` "Using Multiple Github Applications"). The controller picks which secret to verify a webhook against solely by reading `repository.owner.login` from the untrusted payload: [5](#0-4) 

The equality that should hold — but does not — is:

`organization whose secret validated this signature == organization that actually owns the repository/stack being mutated by the handlers`

Because `repository.owner.login` and `repository.full_name` are both attacker-controlled fields inside the same signed JSON body, and HMAC-SHA1 over the raw body only proves "whoever holds *the secret for the org named in `repository.owner.login`*" produced this payload — it says nothing about consistency between that org name and `full_name`. An operator/collaborator of Organization A (who legitimately knows Org A's `webhook_secret` value, e.g. because they can view/rotate it in their own GitHub App settings) can sign a payload where `repository.owner.login = "orgA"` (so `verify_signature` picks Org A's app and the HMAC checks out) while `repository.full_name = "orgB/some-repo"` — a completely different, unrelated organization also hosted by the same Shipit instance.

Handlers then operate purely on `full_name`/`sha`, with no re-validation against the org that supplied the verified secret:
- `PushHandler` resolves `stacks` via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')`, then calls `stack.sync_github` — cross-org triggering of syncs on someone else's stack.
- `StatusHandler` is the most severe: it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }` with **no repository scoping whatsoever**. Any attacker who can produce a validly-signed webhook for *any* configured organization can inject a fabricated CI `status` (state/description/target_url/context) onto an arbitrary commit `sha` that happens to exist in Shipit's database for a completely different, unrelated stack/repository. [6](#0-5) 

### Impact Explanation
Forged/cross-org CI statuses feed directly into merge-queue and CI-gating logic (`StatusChecker`, `MergeRequest#any_status_checks_failed?`/`all_status_checks_passed?` in `app/models/shipit/merge_request.rb`), and into deploy required-status checks (`DeploySpec#required_statuses`). An attacker who legitimately controls one organization's webhook secret on a shared Shipit instance can spoof a "success" status against a commit belonging to a different organization's repository, potentially satisfying CI requirements and enabling an unauthorized merge or deploy of that other repository/stack — a cross-repository, cross-trust-boundary write that the rules explicitly call in-scope ("cross-repository writes... an unauthorized deploy, rollback or merge"). [7](#0-6) 

### Likelihood Explanation
This requires the deployment to host **multiple organizations** on one Shipit instance (a documented, supported configuration) and for the attacker to be a legitimate holder of one organization's `webhook_secret` (e.g., an admin of their own GitHub App installation feeding into the shared Shipit instance) — not a Shipit session, `ApiClient` token, or GitHub App private key belonging to the victim org. Given the multi-tenant feature is explicitly documented and no additional authorization boundary exists between "which secret validated this request" and "which repository/commit it operates on," this is a realistic misconfiguration-adjacent trust break rather than a purely theoretical one.

### Recommendation
After verifying the signature, `create` should re-derive and enforce that every `repository.full_name` (or `sha`'s owning repository) referenced in the payload actually belongs to the same organization (`repository.owner.login` / the resolved `Repository#owner`) that supplied the validated `webhook_secret`. At minimum, `StatusHandler` should scope its `Commit` lookup by the commit's repository/stack and confirmed organization, not by a bare, unscoped `sha` match across the whole instance.

### Proof of Concept
1. Shipit is configured with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-org setup).
2. Attacker is a legitimate GitHub App admin for `orgA` and thus knows `orgA`'s `webhook_secret`.
3. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "<sha of a commit that exists under orgB's stack>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/whatever" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "orgA")` (from `repository.owner.login`), verifies successfully against `orgA`'s secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — which matches the commit under `orgB`'s stack regardless of the `orgA` value used for verification — and creates a forged `success` status on it, independent of `orgB`'s real CI/GitHub state.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

module Shipit
  module Webhooks

          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String

          accepts :branches, Array do

          end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
