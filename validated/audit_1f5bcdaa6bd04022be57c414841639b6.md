### Title
Cross-organization team membership hijack via github_id-only matching in `MembershipHandler#find_or_create_team!` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` looks up an existing `Team` solely by the attacker-controlled numeric `team.id` from the webhook JSON body, never checking that the payload's `organization.login` matches the `Team#organization` already stored on that row. Combined with the fact that `WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret` used to verify the payload) using the same attacker-controlled `organization.login`/`repository.owner.login` value, a webhook that is legitimately signed for organization A can silently mutate a `Team` record that actually belongs to organization B, adding an arbitrary GitHub login as a member of that team.

### Finding Description
The broken binding: `organization_that_signed_the_request == organization_that_owns_the_mutated_team_row` is assumed by the design but never enforced.

- `WebhooksController#verify_signature` picks the GitHub App/secret to verify against using `repository_owner`, which is read straight from the untrusted JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`): [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is unset: [3](#0-2) 

- `MembershipHandler#process` then calls `find_or_create_team!`, which matches purely by `github_id`, ignoring `organization` entirely on the lookup, and only sets `organization`/other attributes in the `create!` block (i.e., not when an existing row matches): [4](#0-3) 

- `Team#add_member` then unconditionally appends the (attacker-supplied) `User` to the matched `Team`'s memberships: [5](#0-4) 

Exploit flow: Shipit supports multi-organization configuration (`secrets.github` keyed by org name, each with its own `webhook_secret`), as documented and tested: [6](#0-5) [7](#0-6) 

If any configured organization (call it `evil-org`) has `webhook_secret` unset — a supported, non-default but real configuration state shown in the example configs — then any unauthenticated internet request claiming `organization.login: "evil-org"` passes `verify_webhook_signature` trivially (`true unless webhook_secret`). The attacker sets the JSON body's `team.id` to the numeric GitHub `github_id` of a `Team` row already present in the `teams` table (synced from a *different*, legitimately privileged organization, e.g. one listed via `github.oauth.teams` and thus present in `Shipit.github_teams`): [8](#0-7) 

`find_or_create_by!(github_id: params.team.id)` matches that existing row regardless of the `evil-org` claim, `User.find_or_create_by_login!('attacker')` creates/fetches the attacker's `User`, and `team.add_member(member)` inserts a `Membership` binding the attacker to the privileged team. `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) then returns `true` for the attacker: [9](#0-8) 

No existing guard (`drop_unhandled_event`, the `ExplicitParameters` schema, `verify_signature`) checks that the signing organization matches the target `Team#organization`; the `ExplicitParameters` schema only validates types/presence, not cross-field consistency: [10](#0-9) 

### Impact Explanation
An attacker who controls (or can forge signatures for) any Shipit-recognized GitHub organization — including one whose `webhook_secret` was left unset — can add themselves (or anyone) to a `Team` belonging to a different, more privileged organization by supplying that team's known numeric `github_id`. If that `Team` is one of the `Shipit.github_teams` used for access control, this is a direct authentication/authorization bypass into the Shipit application itself (`User#authorized?` flips to `true`). This is repeatable for any organization boundary Shipit manages and matches the "escalation into `Shipit.github_teams` authorization" / authentication-bypass impact category.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where at least one configured org has no `webhook_secret` set (a documented, supported configuration state), or where the attacker otherwise controls a recognized org's signing material. The attacker also needs to know/guess the target team's numeric GitHub `github_id`, which is not secret (visible via GitHub API/UI for team members, and low-cardinality/enumerable). No Shipit session, API token, or secret is required beyond the ability to send an HTTP POST to `/webhooks`.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (`Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify in `WebhooksController#verify_signature`/`MembershipHandler` that the signing organization matches the organization referenced in the payload before performing any mutation, rejecting mismatches.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, hypothetical addition):
```ruby
test ":membership from org A cannot hijack a team belonging to org B" do
  privileged_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: X
  assert_equal 'shopify', privileged_team.organization

  @request.headers['X-Github-Event'] = 'membership'
  Shipit.stubs(:github).with(organization: 'evil-org').returns(
    stub(verify_webhook_signature: true) # simulates unset webhook_secret for evil-org
  )

  payload = {
    action: 'added',
    team: { id: privileged_team.github_id, name: 'x', slug: 'x', url: 'http://example.com' },
    organization: { login: 'evil-org' },
    member: { login: 'attacker' }
  }.to_json

  assert_no_difference -> { Membership.where(team_id: privileged_team.id).count } do
    post :create, body: payload, as: :json
  end
end
```
Before the fix, `assert_no_difference` fails because a `Membership` is created binding `attacker` to `privileged_team`, and `User.find_by(login: 'attacker').authorized?` becomes `true` even though `evil-org != privileged_team.organization ('shopify')`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
