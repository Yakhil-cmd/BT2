### Title
Unauthenticated Membership-webhook forgery grants `Shipit.github_teams` authorization when `webhook_secret` is left unset (documented as optional) - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` treats a missing/blank `webhook_secret` as automatic verification success. Because the setup docs explicitly describe `webhook_secret` as **optional**, an operator following the documented setup can end up with a GitHub App configuration whose webhook signature check is a no-op. Any unauthenticated caller can then POST a forged `membership` event that is processed exactly as if GitHub had sent it, allowing an attacker to add an arbitrary GitHub login (including their own) to any `Shipit::Team`, and if that team is part of `Shipit.github_teams`, this grants the attacker full authorization to use the Shipit application — without ever being a real member of that GitHub team or organization.

### Finding Description
`verify_webhook_signature` short-circuits to `true` when no secret is configured for the resolved organization: [1](#0-0) 

The controller resolves *which* organization's (and therefore which secret's) config to use directly from the unauthenticated request body, before any signature has been checked: [2](#0-1) [3](#0-2) 

The setup guide documents the webhook secret as optional: [4](#0-3) 

If any configured GitHub App/organization is left without a `webhook_secret` (a documented, supported configuration), `verify_signature` passes for **any** payload claiming that organization as `repository.owner.login`/`organization.login`, with no signature required at all.

Once past `verify_signature`, the `membership` event is routed to `MembershipHandler`, which trusts the payload's `team` and `member` fields outright: [5](#0-4) 

It finds-or-creates a `Team` by the attacker-supplied `team.id` (`github_id`) and adds a `User` found/created purely from the attacker-supplied `member.login`, with no call back to GitHub to confirm the membership actually exists: [6](#0-5) 

Application-wide authorization is gated purely on whether the current user is a member (in Shipit's own DB) of one of `Shipit.github_teams`: [7](#0-6) 

This is confirmed by the test asserting that only members of `Shipit.github_teams` can access the app, and forbidding everyone else: [8](#0-7) 

**Binding broken:** the organization that "authenticated" the webhook request (via `verify_webhook_signature`, which is vacuously true when no secret is set) ≠ the GitHub identity/team membership that is actually written into Shipit's authorization model (`Team#add_member`, consumed by `User#authorized?`). The `team`/`member` fields inside the payload are never independently verified against GitHub — they are trusted purely because `verify_signature` passed, and `verify_signature` can pass with zero cryptographic proof whenever `webhook_secret` is blank for the resolved organization.

### Impact Explanation
This directly matches the specified High-severity category: "escalation into `Shipit.github_teams` authorization." An attacker with no credentials, no GitHub App private key, no `webhook_secret`, and no Shipit account can:
1. Discover/guess a `team.id` (GitHub team IDs are often enumerable/public) corresponding to a `Shipit::Team` referenced in `Shipit.github_teams`.
2. POST a forged `membership` webhook (`action: added`) naming their own GitHub login as `member.login` and that team as `team`.
3. Gain a `Shipit::User`/`Membership` record making them a member of that team, satisfying `User#authorized?` and unlocking every gated controller action (deploys, rollbacks, repository management, etc.) once they subsequently authenticate via the (real) GitHub OAuth login flow with their own account.

This is an authentication/authorization bypass into the application's core trust boundary, not merely a resource-exhaustion issue.

### Likelihood Explanation
Likelihood depends entirely on deployment configuration: it requires that at least one configured GitHub App/organization has no `webhook_secret` set. Because the setup documentation explicitly calls this field "(optional)", this is a realistic, documented-as-valid configuration rather than a misuse of the engine, so it does not fall under "host application not mounting the engine as documented." Organizations that skip the optional secret (e.g., for simplicity, or for a secondary/lesser-used GitHub App entry in a multi-org `secrets.yml`) are directly exposed.

### Recommendation
- Make `webhook_secret` mandatory (fail closed) rather than optional; refuse to boot/serve webhooks for an organization with no configured secret instead of returning `true` from `verify_webhook_signature`.
- For `membership` events (and any other webhook that mutates authorization-relevant state), cross-check the claimed membership against the GitHub API (as `refresh_members!` already does for `Team`) rather than trusting the webhook body verbatim.
- Consider re-verifying `Shipit.github_teams` membership via a live GitHub API call at the point authorization is checked (`User#authorized?`), not solely from locally cached `Membership` rows populated by webhooks.

### Proof of Concept
1. Deploy Shipit with a `secrets.yml` GitHub App entry for organization `victim-org` that omits `webhook_secret` (a documented-optional field), while `Shipit.github_teams` includes a team belonging to `victim-org`.
2. As an unauthenticated attacker, send:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": <github_id of the Shipit::Team in Shipit.github_teams>, "name": "Developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "victim-org" } }
}
```
3. Because `victim-org` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`), and `MembershipHandler#process` creates a `Membership` linking `attacker-github-login` to the privileged `Team`.
4. Attacker logs into Shipit via the normal GitHub OAuth flow as `attacker-github-login`; `User#authorized?` now returns `true` because of the forged `Membership`, granting full access to the application despite never being a real member of the GitHub team/organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
