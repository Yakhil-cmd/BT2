## Finding [1](#0-0)  resolves *which organization's secret* to verify the HMAC signature against using `repository_owner`, i.e. `params.dig('repository', 'owner', 'login')` (or `organization.login` as a fallback), as shown at [2](#0-1) . But the code path that actually acts on data — `Handler#stacks`/`Handler#repository_name` — resolves the *target repository to write to* from an entirely different, independently-controlled field: `payload.dig('repository', 'full_name')` [3](#0-2) . These two fields are never checked for consistency, so `organization_authenticated == repository_written` is not enforced.

Critically, `verify_webhook_signature` short-circuits to `true` whenever the resolved organization has no `webhook_secret` configured: `return true unless webhook_secret` [4](#0-3) . `webhook_secret` is an optional, documented per-organization config value [5](#0-4) .

Combining these two facts: on a multi-organization Shipit deployment where at least one onboarded organization has no `webhook_secret` set, an unauthenticated attacker can POST a crafted JSON body to the (CSRF-exempt, unauthenticated) `WebhooksController#create` endpoint with `repository.owner.login` (or `organization.login`) set to the unsecured organization, while setting `repository.full_name` to `secured-org/victim-repo`. `verify_signature` will look up the unsecured organization's `webhook_secret`, find it blank, and accept the request unconditionally — regardless of the `X-Hub-Signature` header — while the handler proceeds to act on the victim repository resolved from `full_name`, e.g. syncing a stack via `PushHandler#process` [6](#0-5) , creating commit statuses via `StatusHandler#process` [7](#0-6) , or manipulating team membership via `MembershipHandler#process` [8](#0-7) .

The membership path is the most severe: it can add an arbitrary attacker-supplied GitHub login to any `Team` record via `team.add_member(member)`, and `User#authorized?` grants dashboard access based on membership in `Shipit.github_teams` [9](#0-8) , so this forged membership event could escalate an attacker-controlled GitHub identity into `Shipit.github_teams` authorization — one of the explicitly in-scope High-impact outcomes.

## Caveat

I could not find, within the indexed context, the exact call site/config loader that builds the map of per-organization `GithubApp` instances (`Shipit.github(organization:)`), so I cannot confirm from code alone how commonly a real deployment would have one organization configured without a `webhook_secret` while onboarding another organization's repos with one. This is a real deployment-configuration precondition, not a code defect that's independently exploitable on a single-organization instance where the org's own `webhook_secret` is set. If you want a definitive confirmation of multi-org config loading and whether `webhook_secret` is per-organization or global across the instance, that would require the full contents of `lib/shipit.rb`, which the index did not surface completely — a Devin session with full repository access could verify this precisely.

### Title
Cross-field trust binding break in webhook signature verification allows organization/repository confusion - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the webhook secret to check based on `repository.owner.login`/`organization.login`, while every `Webhooks::Handlers::Handler` subclass acts on the repository identified by the separate `repository.full_name` field. These fields are never cross-validated.

### Finding Description
An unauthenticated caller controls the entire raw JSON payload. Signature verification is scoped to one field (`repository_owner`) [2](#0-1) , while `Handler#repository_name` — used to find the `Repository`/`Stack`/`Commit` to mutate — reads a different field (`repository.full_name`) [10](#0-9) . Because `verify_webhook_signature` returns `true` unconditionally when the resolved organization has no configured secret [4](#0-3) , an attacker can pick an unsecured organization for the "authenticated" field while targeting a secured organization's repository via `full_name`.

### Impact Explanation
Depending on the event type dispatched, this allows forged pushes (triggering `stack.sync_github`), forged commit statuses, or forged team membership changes on a repository/stack the attacker was never authorized against — including a path to `Shipit.github_teams` authorization escalation via `MembershipHandler`.

### Likelihood Explanation
Requires: (a) a multi-organization Shipit deployment, and (b) at least one onboarded organization configured without a `webhook_secret`. This is a plausible, code-supported configuration (the secret is optional in the config schema), but its prevalence cannot be confirmed from the indexed context alone.

### Recommendation
Verify the signature using the same organization/repository derived from `payload.dig('repository', 'full_name')` that the handlers actually act on, not a separately-trusted `owner`/`organization` field. Additionally, consider rejecting webhook events for organizations with no configured `webhook_secret` rather than treating them as implicitly trusted.

### Proof of Concept
1. Onboard org `unsecured-org` (no `webhook_secret`) and org `secured-org` (has `webhook_secret`) with a stack for `secured-org/victim-repo`.
2. POST to `/webhooks` with header `X-Github-Event: push`, any/garbage `X-Hub-Signature`, and body:
```json
{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "secured-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "unsecured-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. `PushHandler` resolves `secured-org/victim-repo` via `full_name` and triggers `stack.sync_github` for that repo/stack — despite the request never being signed by `secured-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
