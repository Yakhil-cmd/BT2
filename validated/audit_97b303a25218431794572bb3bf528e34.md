### Title
Webhook Authentication Uses `repository.owner.login` While Handlers Act on `repository.full_name` from the Same Untrusted Payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret to validate a webhook against using `repository_owner`, computed from the untrusted JSON body's `repository.owner.login` (or `organization.login`) field. [1](#0-0) [2](#0-1)  The downstream event handlers, however, resolve the `Stack`/`Repository` to mutate using the same payload's `repository.full_name` field, which is a separate JSON key not covered by the organization lookup. [3](#0-2)  Because nothing in the engine enforces that `repository.owner.login` and the owner portion of `repository.full_name` refer to the same organization, a sender who legitimately possesses the webhook secret for one organization configured in `Shipit.github` can craft a signed payload whose `owner.login` matches their own org (passing signature verification) while `full_name` points at a different organization/repository's stack.

### Finding Description
`verify_signature` fetches the `GithubApp` config keyed by `repository_owner` and calls `verify_webhook_signature` against the raw POST body using that organization's `webhook_secret`. [1](#0-0)  `repository_owner` is derived purely from the JSON payload itself (`params.dig('repository', 'owner', 'login')` or the fallback `organization.login`), i.e. from a field inside the very message being authenticated. [2](#0-1)  If verification succeeds, `create` parses the same raw body and dispatches it unmodified to every registered handler for the event. [4](#0-3) 

Handlers such as `LabelCapturingHandler` declare and consume `repository.full_name` (e.g. `"victim-org/protected-repo"`) to identify the target stack, not `repository.owner.login`. [3](#0-2)  The equality the system implicitly relies on — "the organization whose secret authenticated this request" == "the organization/repository the handler will write to" — is never checked. An attacker who legitimately controls (or has been granted) the webhook secret for Organization A (a normal, unprivileged tenant in a multi-org Shipit deployment) can send a payload where `repository.owner.login = "org-a"` (satisfying `verify_signature`) but `repository.full_name = "org-b/some-repo"`, causing handlers to act on Organization B's stack using Organization A's trust.

### Impact Explanation
This breaks the binding between "the organization that authenticated the webhook" and "the repository whose Stack is written to," which is one of the deployment-trust bindings explicitly in scope. Depending on which handler processes the event, this can result in unauthorized mutation of another organization's `Stack`/`PullRequest` records, injection of fabricated commit statuses, or captured labels/merge-state changes on a repository the sender's org secret was never meant to authorize — i.e., a cross-repository/cross-organization write triggered without possessing that organization's own webhook secret.

### Likelihood Explanation
Exploitability requires only sending a crafted HTTP POST to `/webhooks` with a valid signature computed using a webhook secret the attacker already possesses (e.g., their own organization's GitHub App webhook secret in a shared/multi-tenant Shipit instance), which is not privileged Shipit credentials, an `ApiClient` token, or repository write access — it is exactly the kind of external, unprivileged boundary crossing in scope. No further authentication or session is required past that point since `WebhooksController` is unauthenticated by design (`ActionController::Base`) and relies solely on the signature check. [5](#0-4) 

### Recommendation
Bind the resolved organization/owner from the verified signature to the repository the handler is permitted to act on: after `verify_signature` succeeds, re-derive `repository.owner.login` from the payload and require it to match the owner segment of `repository.full_name` before dispatching to handlers, rejecting the webhook (422) on mismatch.

### Proof of Concept
1. Obtain the webhook secret configured for Organization A in `Shipit.github` (as a normal tenant admin of Org A, not a Shipit user).
2. Craft a `pull_request` (or other handled event) JSON payload with:
   - `repository.owner.login = "org-a"`
   - `repository.full_name = "org-b/protected-repo"`
   - `sender.login`, `pull_request.*` fields set to satisfy the handler's required params.
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(org_a_secret, raw_body)`.
4. POST to `/webhooks` with `X-Github-Event: pull_request`.
5. `verify_signature` resolves `Shipit.github(organization: "org-a")` and validates successfully against Org A's secret. [1](#0-0) 
6. The handler processes the same payload and mutates state tied to `org-b/protected-repo`, using Org A's authentication to affect Org B's stack. [6](#0-5) 

Note: due to tool-access limits in this session, the exact line-level logic that maps `repository.full_name` to a specific `Stack`/`Repository` record inside the handler base class could not be fully traced beyond the `params` schema shown above; the params declaration confirms `full_name` is the field consumed independently of the organization used for signature verification.
