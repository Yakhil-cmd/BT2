### Title
Deregistered Bridge Operator's Pending Votes Persist, Allowing Post-Revocation Execution of Value Transfers — (`contracts/service_chain/bridge/BridgeOperator.sol`)

### Summary

`deregisterOperator` removes an operator from the `operators` mapping but does not clear that operator's pending votes stored in the `votes[voteType][nonce]` mapping. A deregistered operator's prior vote can still be combined with a remaining active operator's vote to reach the threshold and execute a bridge value transfer (KAIA, ERC20, or ERC721), defeating the owner's intent to revoke the operator's authority.

### Finding Description

`BridgeOperator.sol` maintains two separate state locations for operator authority:

1. `operators[address]` — the live authorization flag checked by `onlyOperators`
2. `votes[voteType][nonce].voted[address]` and `votes[voteType][nonce].voteCounts[voteKey]` — the accumulated vote state used by `_voteCommon` to determine if the threshold is reached

`deregisterOperator` only clears location (1):

```solidity
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);
    delete operators[_operator];          // only this is cleared
    // votes[...][...].voted[_operator] and voteCounts are NOT cleared
    ...
}
```

`_voteCommon` counts votes by reading `voteCounts[voteKey]` directly, without checking whether each voter is still a registered operator:

```solidity
function _voteCommon(VoteType _voteType, uint64 _nonce, bytes32 _voteKey) private returns(bool) {
    VotesData storage vote = votes[uint8(_voteType)][_nonce];
    ...
    vote.voteCounts[_voteKey]++;
    if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
        return true;
    }
    return false;
}
```

Because `voteCounts` is never decremented on deregistration, the deregistered operator's vote weight remains in the tally permanently.

The code itself acknowledges this in a comment on `deregisterOperator`:

> *"Note that outstanding votes by the deregistered operator are not revoked. This enables a subtle counterintuitive scenario."*

The comment treats this as a known operational hazard rather than a design decision, and the recommended mitigation ("The Owner shall recognize this issue") is insufficient for a production bridge holding real assets.

### Impact Explanation

When the owner deregisters a compromised or malicious operator (e.g., operator A), A's vote on any pending nonce N remains counted. If a second active operator B subsequently calls `handleKLAYTransfer`, `handleERC20Transfer`, or `handleERC721Transfer` for nonce N, `_voteCommon` sees `voteCounts[voteKey] >= threshold` and returns `true`, causing `_voteValueTransfer` to set `closedValueTransferVotes[N] = true` and the handle function to transfer assets to the attacker-controlled `_to` address.

The corrupted value is `closedValueTransferVotes[N]` being set to `true` and the subsequent asset transfer executing, despite the owner having revoked operator A's authority. The affected assets are native KAIA, ERC20 tokens, and ERC721 tokens held or minted by the bridge contract.

### Likelihood Explanation

The trigger requires:
- Operator A votes on nonce N (normal operation, no special action needed)
- Owner deregisters A (e.g., due to key compromise)
- One remaining active operator B votes on nonce N

This is a realistic sequence during an incident response. The owner deregisters A precisely to stop A's influence, but A's vote persists. Operator B may vote legitimately without knowing A's vote was from a compromised key. The threshold for exploitation equals the number of remaining active operators needed to reach `operatorThresholds[ValueTransfer] - 1` after A's deregistered vote is counted.

### Recommendation

In `deregisterOperator`, iterate over all pending nonces and decrement `voteCounts` for the deregistered operator's recorded `voted[_operator]` entries, or alternatively clear the entire `votes` entry for any nonce where the deregistered operator has voted. A simpler mitigation is to modify `_voteCommon` to skip (and decrement) votes from addresses no longer in `operators`:

```solidity
function _voteCommon(VoteType _voteType, uint64 _nonce, bytes32 _voteKey) private returns(bool) {
    VotesData storage vote = votes[uint8(_voteType)][_nonce];
    bytes32 oldVoteKeyOfVoter = vote.voted[msg.sender];
    if (oldVoteKeyOfVoter == bytes32(0)) {
        vote.voters.push(msg.sender);
    } else {
        vote.voteCounts[oldVoteKeyOfVoter]--;
    }
    vote.voted[msg.sender] = _voteKey;
    if (vote.voteCounts[_voteKey] == 0) {
        vote.voteKeys.push(_voteKey);
    }
    vote.voteCounts[_voteKey]++;
    if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
        return true;
    }
    return false;
}
```

Additionally, `deregisterOperator` should sweep and decrement any outstanding votes by the removed operator across all open nonces, or the contract should recount only votes from currently-registered operators at threshold-check time.

### Proof of Concept

Setup: Bridge deployed with operators A and B, `operatorThresholds[ValueTransfer] = 2`.

1. Operator A calls `handleKLAYTransfer(txHash, from, maliciousAddr, value, nonce=5, blkNum, data)`. `_voteCommon` records `votes[0][5].voted[A] = voteKey` and `votes[0][5].voteCounts[voteKey] = 1`. Threshold not reached; returns `false`.
2. Owner discovers A is compromised and calls `deregisterOperator(A)`. `operators[A]` is deleted. `votes[0][5].voteCounts[voteKey]` remains `1`.
3. Operator B calls `handleKLAYTransfer(txHash, from, maliciousAddr, value, nonce=5, blkNum, data)` with identical parameters. `_voteCommon` increments `votes[0][5].voteCounts[voteKey]` to `2 >= threshold`. Returns `true`.
4. `_voteValueTransfer` sets `closedValueTransferVotes[5] = true`. `handleKLAYTransfer` transfers `value` KAIA to `maliciousAddr`.

The owner's deregistration of A did not prevent A's vote from contributing to the execution. The bridge asset transfer completes using a deregistered operator's vote. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
