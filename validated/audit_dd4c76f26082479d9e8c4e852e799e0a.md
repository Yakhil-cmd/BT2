## Title
AA `data_feed`/`in_data_feed` lookups can read not-yet-stable ("unconfirmed") oracle values that may later flip to `final-bad`, causing execution results that depend on non-final state — (File: `data_feeds.js`, `formula/evaluation.js`)

### Summary
The reported bug class is that Chainlink VRF's low `minimumRequestConfirmations` lets a "winner" be decided from data that is not yet final, so a chain reorg can later invalidate the outcome after value has already been paid out. The analogous root cause in ocore is that AA formula evaluation of `data_feed[[...]]`/`in_data_feed[[...]]` is allowed to consult **unstable** (not-yet-finalized) data-feed messages from other units whose final sequence (`good` vs `final-bad`) is not yet settled, and then acts on that value as if it were final.

### Finding Description
When an AA formula evaluates `data_feed` or `in_data_feed`, the evaluator passes `bAA` (a boolean, always true inside AA formulas) as the `unstable_opts` argument to `dataFeeds.readDataFeedValue`/`dataFeeds.dataFeedExists`: [1](#0-0) 

Inside `readDataFeedValue`, when `unstable_opts` is truthy, the function scans `storage.assocUnstableMessages` — i.e., messages belonging to units that are **not yet stable** — and accepts any candidate whose current in-memory `sequence` is `'good'`: [2](#0-1) 

`sequence='good'` for an unstable unit is only a *provisional* status. The real, final `sequence` (`good` or `final-bad`) for a unit is only settled when its MCI stabilizes, via `findStableConflictingUnits`/`markMcIndexStable`, which resolves conflicts among competing (e.g., double-spending) units at stabilization time: [3](#0-2) 

Because the "unstable" scan in `readDataFeedValue` does not wait for this final resolution, an AA can read and act on a data-feed value posted by a unit that is currently provisionally `good` but is later marked `final-bad` once its MCI actually stabilizes (e.g., because it conflicts with a competing double-spend unit that ultimately wins). This is structurally identical to the reported issue: a decision (in the VRF case, "who wins"; here, "what does the oracle feed value equal") is made from state that has not reached the finality threshold and can still change.

The consequence is more severe than the original report because it is not merely a UX problem: `assocUnstableMessages` is populated based on which units a given node happens to have already received and validated locally. Two honest full nodes can therefore have different sets of "currently known unstable messages" at the moment they each execute the very same (already-stabilized-trigger) AA response, producing different `data_feed` results, different AA responses/fund transfers, and permanent state divergence between nodes — i.e., node disagreement on validity/state for the same trigger.

### Impact Explanation
- An AA can commit to a data-feed-driven decision (e.g., release funds, mark an outcome, pay a "winner") based on an oracle unit that has not been finally sequenced.
- If the referenced unit later resolves to `final-bad` at stabilization, the value used no longer exists in the canonical, final state, yet the AA already irrevocably acted on it (payment sent to an address, state variables updated).
- Because different nodes can have different local views of `assocUnstableMessages` at the time of evaluation, this can cause different nodes to compute different results for the same (final) AA trigger, i.e., consensus divergence on AA responses/fund movements.

### Likelihood Explanation
This code path is reached on every ordinary posted AA trigger that uses `data_feed`/`in_data_feed` — no attacker capability beyond normal unit/AA posting privileges is required. Any AA developer using `data_feed[[...]]` relying on another AA's freshly-posted oracle value is exposed. The condition for divergence (a candidate unit being provisionally `good` but ultimately becoming `final-bad`, combined with differing node knowledge of unstable units at execution time) is a natural, achievable network condition rather than a contrived edge case, mirroring exactly how L2 reorgs "often" flip outcomes decided too early.

### Recommendation
Restrict `data_feed`/`in_data_feed` evaluation inside AA formulas to only consider messages from units whose sequence is already **final** (i.e., stable, or otherwise guaranteed not to be reverted, such as being included in the trigger's own causal/parent history with fixed stability guarantees). If "fast" unstable lookups are still desired for latency reasons, require that any unstable candidate unit be provably part of the deterministic causal past of the trigger unit (so all nodes are guaranteed to have already validated it before executing the trigger), rather than an arbitrary scan of whatever happens to be in the node's local `assocUnstableMessages` at evaluation time.

### Proof of Concept
1. AA `X` posts a data feed value `V1` in unit `U1`. `U1` is unstable but currently `sequence='good'`.
2. AA `Y`'s trigger stabilizes (mci m) and its formula does `data_feed[[oracles=X, feed_name="f"]]`, which via `readDataFeedValue(..., bAA=true, ...)` finds `U1` in `storage.assocUnstableMessages`, sees `sequence==='good'`, and returns `V1` — even though `U1`'s MCI has not yet stabilized (`main_chain.markMcIndexStable`/`findStableConflictingUnits` has not run for it).
3. AA `Y` executes its response (e.g., sends funds) based on `V1`.
4. Later, `U1` conflicts with a competing unit and is marked `final-bad` at stabilization (per `markMcIndexStable`/`findStableConflictingUnits`), so `V1` never actually becomes part of the canonical stable state.
5. AA `Y`'s already-executed, now-final response (fund transfer) was based on a value that turned out not to exist in final history — analogous to the VRF winner being paid before the reorg invalidates the randomness that selected them. [4](#0-3) [5](#0-4)
