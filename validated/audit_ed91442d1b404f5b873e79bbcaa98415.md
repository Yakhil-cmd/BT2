### Title
`StatusHandler#process` scopes commit-status writes by `sha` only, with no repository filter, unlike `PullRequest::*Handler` classes which scope through `stacks`/`repository` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` queries `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, with no repository/stack scoping at all. Every other handler inheriting `Handler` (e.g. `PullRequest::OpenedHandler`, `LabelCapturingHandler`, `UnlabeledHandler`, `CheckSuiteHandler`) resolves work through `Repository.from_github_repo_name(repository_name).stacks` (the `Handler#stacks` helper) or an equivalent `Repository.from_github_repo_name(params.repository.full_name)` lookup, confining writes to the repository named in the payload.

### Finding Description
The binding that should hold is: `handler_target_repository == payload.dig('repository', 'full_name')`'s repository, for every write performed by a `Handler` subclass.

`Handler#stacks` enforces this: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`, where `repository_name` is `payload.dig('repository', 'full_name')` [1](#0-0) . `CheckSuiteHandler#process` uses this `stacks` scope before touching any commit [2](#0-1) , and the `PullRequest::*` handlers (e.g. `UnlabeledHandler`, `LabelCapturingHandler`) resolve a `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and only ever mutate `stack`/`review_stack` objects scoped to that repository [3](#0-2) [4](#0-3) .

`StatusHandler`, however, does not even declare `repository` in its `params` schema, and its `process` method never touches `repository_name`, `stacks`, or `Handler#stacks` at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . `Commit#sha` is not globally unique in the schema — the only uniqueness constraint is a composite index on `(stack_id, sha)` [6](#0-5) , meaning the same sha can legitimately exist as separate `Commit` rows on different stacks (e.g. mirrored/forked repositories with identical commit content, tags shared between environments, etc.). Because `create_status_from_github!` fans out over every matching row across the whole `Commit` table regardless of which stack/repository it belongs to, a status/deploy signal for one repository's commit sha can update commit state for another, unrelated repository's stack.

The write is not gated by `verify_signature`, since that check only verifies the webhook came from the correct GitHub organization (via `Shipit.github(organization: repository_owner)`), not that the payload's repository matches the commit being mutated [7](#0-6) . Once the signature check passes for *any* repository within the configured organization, `StatusHandler.call(params)` runs unscoped by repository.

Mutation consequences are non-trivial: `create_status_from_github!` → `add_status` re-evaluates `status`/`deployable?` transitions and can call `stack.schedule_continuous_delivery`, enqueuing a `ContinuousDeliveryJob` for the *other* stack when the new status state satisfies the CD condition [8](#0-7) [9](#0-8) .

### Impact Explanation
This is a repository-scope violation matching the "Critical" category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." Any status webhook (state, description, target_url, context) delivered for a repository within an org whose webhook secret is registered with Shipit can update the commit-status/state of a `Commit` row belonging to a *different* tracked repository/stack, provided the sha value coincides. Because coinciding shas can arise from legitimate cross-repo scenarios (mirrors, forks with identical history, shared vendored commits) without any secret compromise, this is a structural repository-isolation break unique to `StatusHandler`, distinct from — and not mitigated by — `verify_signature`.

### Likelihood Explanation
Preconditions: the attacker needs a GitHub repository within an organization that already has a valid Shipit webhook secret configured (so `verify_signature` passes), and a commit whose sha coincides with a commit sha tracked by another stack. This is plausible when repositories inside the same GitHub org share history (mirrors/forks/re-imports), a documented and not-uncommon setup, but it is not a trivial "any internet user, any target" attack — it requires org-level webhook access and a genuine sha collision, which limits but does not eliminate exploitability compared to a general auth bypass.

### Recommendation
Scope `StatusHandler#process` by repository the same way other handlers do: resolve `stacks`/`Handler#stacks` from `payload.dig('repository','full_name')` and restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalently join through `stack: { repository: ... }`), instead of an unscoped `Commit.where(sha:)`.

### Proof of Concept
Minitest plan (model-level, no live GitHub, under `test/`):
1. Create two `Repository`/`Stack` fixtures, `repo_a` and `repo_b`, each with a `Commit` sharing the identical `sha` value (simulating a legitimate cross-repo sha collision).
2. Build a status webhook payload for `repo_b` (`payload['repository']['full_name'] = repo_b.full_name`, `payload['sha'] = shared_sha`).
3. Call `Shipit::Webhooks::Handlers::StatusHandler.new(payload).process`.
4. Assert that `repo_a`'s `Commit` (belonging to the unrelated stack) received a new `Status` row / state change — `assert_difference -> { repo_a_commit.statuses.count }, 1`.
5. As a contrast, repeat with `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler` (or `UnlabeledHandler`) using a payload with `repository.full_name` pointing at `repo_b`, and use Mocha (`Shipit::Repository.expects(:from_github_repo_name).with(repo_b.full_name)`) to show the PR handler only ever resolves/mutates `repo_b`'s stack, never touching `repo_a`.
6. Additionally spy on `Handler#stacks` (private method) via Mocha to assert it is never invoked inside `StatusHandler#process`, confirming the absence of the repository-scoping call that every other handler performs.

      already_deployed = deployed?

      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
