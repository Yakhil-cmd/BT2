### Title
Unrecovered `throw Error()` in oscript Runtime Evaluator Reachable via Divergence from Static Formula Validator - ([File: formula/evaluation.js])

### Summary
`formula/evaluation.js`'s `evaluate()` function — the runtime interpreter used every time an AA trigger, `init`, `state`, or `getters` formula is executed — contains numerous raw, unrecovered `throw Error(...)` statements for "should never happen" fallback branches inside its operator `switch`. These are distinct from the `setFatalError()` mechanism used everywhere else in the same function to gracefully turn a bad formula into a "bounce" response. The static pre-check for these same formulas is implemented in a **separate file**, `formula/validation.js`, which independently re-implements the grammar's operator cases (e.g. `'comparison'`, `'substring'`, `'replace'`, `to_upper`/`to_lower`/`length`, `starts_with`/`ends_with`/`contains`/`has_only`/`index_of`) to decide whether a formula is admissible when an AA is defined.

Because validation and execution are two independently maintained code paths for the same language grammar, any value/operator combination that `formula/validation.js` fails to reject — but that `formula/evaluation.js`'s switch does not handle through `setFatalError` — falls through to a bare `throw Error(...)`. This mirrors precisely the External Report's bug class #1/#2 ("precompiled contracts lack input checks … result in a runtime panic") and #4 (divergence between two independent representations of the same logical state), applied to ocore's own bytecode-equivalent, the oscript formula engine.

### Finding Description
- `formula/evaluation.js:428-546` (`case 'comparison'`), `:1984-2054` (`length`/`to_upper`/`to_lower`/`starts_with`/`ends_with`/`contains`/`has_only`/`index_of`), and `:2056-2112` (`substring`) all end with either `throw Error("unknown comparison: " + operator)`, `throw Error("unknown op: " + op)`, or `throw Error("unknown type of start/length in substring: " + start)`. None of these are wrapped in `setFatalError`, and none is guarded by a `try/catch` anywhere up the call chain (`handleTrigger` → `evaluateAA`/`executeStateUpdateFormula` in `aa_composer.js`, ultimately invoked from `main_chain.js`'s `handleAATriggers`/`markMcIndexStable` during MC stabilization, a mandatory step for every full node). [1](#0-0) [2](#0-1) [3](#0-2) 
- These branches exist precisely because the language's static admissibility is checked by a **separately maintained** file, `formula/validation.js`, which re-implements the same operator set independently rather than sharing a single source of truth with `evaluation.js`. [4](#0-3) 
- Uncaught exceptions thrown while a node processes a confirmed unit's AA trigger are not contained: `network.js` installs a top-level `uncaughtException` handler that explicitly re-throws to crash the process, by design, to "avoid ending up in an inconsistent state." [5](#0-4) 
- AA-trigger processing is not optional for full nodes — it runs deterministically as part of `markMcIndexStable`/`handleAATriggers` whenever a unit paying an AA becomes MC-stable, meaning every full node in the network executes the same formula and hits the same crash. [6](#0-5) [7](#0-6) 

### Impact Explanation
If `formula/validation.js` admits (at AA-definition time) any formula construct that `formula/evaluation.js` does not translate into a graceful `setFatalError`/bounce at execution time, then triggering that AA with an ordinary payment (something any unprivileged account can do) will cause a bare JS exception to propagate out of `evaluate()`, up through `handleTrigger`, into the deterministic AA-processing pipeline invoked during MC stabilization on every full node. Given `network.js`'s explicit re-throw-to-crash policy on uncaught exceptions, this results in **every full node crashing** while trying to stabilize the same MC index — i.e., the network becomes unable to confirm new units until node operators patch and redeploy, a network-wide denial-of-service triggerable at zero cost beyond posting one unit and defining/triggering one AA.

### Likelihood Explanation
The likelihood is Medium: exploitation strictly depends on finding one concrete divergence between the two independently-maintained switch statements in `formula/validation.js` and `formula/evaluation.js` (e.g., an argument type or edge case that validation accepts but evaluation cannot handle and only guards with a raw `throw`). I was not able to fully diff every operator case within the current investigation to confirm a specific reachable divergence; this requires a dedicated line-by-line comparison of both files for each of `comparison`, `substring`, `replace`, `to_upper/to_lower/length`, and `starts_with/ends_with/contains/has_only/index_of`, as well as any other paired case blocks. The structural root cause — two hand-synchronized re-implementations of the same oscript grammar, with the runtime side using un-recovered `throw` as its fallback instead of routing every unexpected state through `setFatalError` — is confirmed and is inherently fragile to future edits.

### Recommendation
1. Eliminate all bare `throw Error(...)` statements inside `evaluate()`'s reachable operator cases in `formula/evaluation.js`; route every "should never happen" fallback through `setFatalError()` so any inconsistency degrades to a bounced AA response instead of an uncaught exception.
2. Wrap the entire `handleTrigger`/`evaluateAA` execution path in `aa_composer.js` with a top-level `try/catch` that converts any unexpected exception into a bounce, rather than allowing it to propagate to `network.js`'s process-crashing `uncaughtException` handler.
3. Refactor `formula/validation.js` and `formula/evaluation.js` to share a single canonical definition of each operator's argument/type constraints (e.g., a shared schema or generated switch) instead of two independently hand-maintained switch statements, removing the structural risk of divergence entirely.

### Proof of Concept
A definitive PoC requires identifying one operator/argument combination accepted by `formula/validation.js` but which drives `formula/evaluation.js` into one of the un-recovered `throw` branches (for example, a `substring`/`comparison`/`starts_with`-family expression whose argument type validation.js does not check as strictly as evaluation.js's runtime coercion logic). Conceptually the attack is:
1. Attacker authors and posts an AA definition containing an oscript formula in `messages`, `init`, or `getters` using the divergent construct that passes `aa_validation.js`'s `validateAADefinition` (which internally calls `formula/validation.js`).
2. Attacker (or anyone) sends a single trigger payment to the AA.
3. When the triggering unit becomes MC-stable, every full node calls `handleAATriggers`/`handleTrigger` → `evaluate()`, which throws uncaught, and each node's `network.js` `uncaughtException` handler crashes the process — halting confirmation of new units network-wide.

Confirming the exact divergent construct requires further code-level comparison between `formula/validation.js` and `formula/evaluation.js`, which I could not complete within the available tool budget; this should be verified with a full side-by-side diff of both files' `switch` statements before treating the PoC as concrete.
