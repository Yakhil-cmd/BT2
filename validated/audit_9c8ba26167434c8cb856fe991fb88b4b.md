### Title
Cross-repository `Status` write via unscoped `Commit.where(sha:)` lookup enables unauthorized continuous deployment on a victim stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by SHA alone, with no scoping to the repository that the webhook was authenticated for, so a correctly-signed `status` webhook from an attacker-owned repository can create a `success` `Status` against a `Commit` belonging to any other stack that happens to share that SHA. If the victim stack has `continuous_deployment: true` and that commit is its undeployed HEAD, `Commit#deployable?` flips to true and a real deploy is triggered on the victim's infrastructure.

### Finding Description
The broken binding, stated as an explicit equality that the code should enforce but does not:

`repository_owner`/`repository.full_name` used to authenticate the webhook (the attacker's own org/repo) == `stack`/`commit.stack` whose `Commit` row is written by that webhook.

Trace:
- `WebhooksController#verify_signature` verifies the payload using `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight out of the untrusted payload (`params.dig('repository', 'owner', 'login')`). [1](#0-0)  This only proves the request is a genuine GitHub webhook for *that org* (e.g., the attacker's own fork/org, on which the attacker — as repo owner — can legitimately install/configure the GitHub webhook/app). It says nothing about which stack's commits may be touched.
- The base `Handler` class does define a repository-scoped accessor, `stacks`, built from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name`. [2](#0-1)  Handlers such as the pull-request handlers use this scoping.
- `StatusHandler#process` does not use `stacks` at all. It runs a global, unscoped lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [3](#0-2)  Any `Commit` row anywhere in the database with a matching `sha` — regardless of which repository/stack it belongs to — receives the status.
- `Commit#create_status_from_github!` creates a `Status` scoped to `commit.stack` from the SHA match, not from the webhook's repository. [4](#0-3) 
- `Status` has `after_commit :schedule_continuous_delivery, ... on: :create`, which calls `commit.schedule_continuous_delivery`. [5](#0-4)  This eventually reaches `Stack#trigger_continuous_delivery` / `Stack#next_commit_to_deploy`, which selects commits based on `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`), and can trigger `Stack#trigger_deploy` for the victim stack.

The precondition for exploitation is that the same 40-hex git SHA exists as a `Commit` record in both a stack the attacker controls (or can address via a webhook they legitimately trigger) and the victim's stack. This is not a cryptographic SHA-1 collision requirement — it happens naturally whenever two Shipit-tracked repositories share git history for the same commit (e.g., a fork of the victim's public repo that has not diverged from a shared base commit, or a commit landed via subtree/cherry-pick into both repositories). An attacker who owns a fork of the victim's repository can call GitHub's Status API against their own fork for a SHA equal to the victim's undeployed HEAD (forks retain identical SHAs for shared history), and GitHub will deliver a legitimately signed `status` webhook to Shipit for the attacker's own repo/org. None of `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema on `StatusHandler` check that the `sha` belongs to the authenticated repository — the schema only validates `sha`/`state` are present strings. [6](#0-5) 

### Impact Explanation
A payload authenticated for one repository (attacker-owned) mutates state (`Status`, and transitively `Commit#deployable?`) belonging to another party's stack, and can cause an unauthorized deploy/continuous-delivery trigger on the victim's deploy host — this matches the explicitly listed Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy". The attacker does not authenticate against, have push access to, or hold any secret for the victim's repository/stack; only ownership of any repository sharing a commit SHA with the victim (e.g. a fork) is required. This is repeatable against any victim stack for any shared commit and is not limited to a single tenant, since `Commit.where(sha:)` is global across the entire Shipit instance.

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment: true` and an undeployed HEAD commit in `pending`/`failure` state (both plausible default/common configurations). The attacker needs: (1) a repository they control that is wired into Shipit's webhook delivery (trivial if it's their own fork/repo with the GitHub App/webhook installed, which requires no Shipit privilege, only repo-owner-level GitHub permissions on their own repository), and (2) a commit SHA shared with the victim's undeployed HEAD, which is common for forks that have not diverged, or shared-history/cherry-pick/subtree commits. No Shipit session, API token, or GitHub secret is needed. The attack is cheap (a single GitHub Status API call or webhook POST) and repeatable.

### Recommendation
Scope `StatusHandler#process` (and `Commit#create_status_from_github!`) to the webhook's own repository: restrict the `Commit.where(sha: params.sha)` lookup to commits belonging to `stacks` (the `Repository.from_github_repo_name(repository_name)`-derived stacks), mirroring how other handlers (e.g. pull-request handlers) scope by repository. Reject or ignore statuses for SHAs that do not belong to a commit under the authenticated repository's stacks.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Set up two stacks: `@victim_stack` (`continuous_deployment: true`) with an undeployed `@victim_commit` (state `pending`, sha `S`), and `@attacker_stack`/`@attacker_repo` under a different `repository.full_name`/`owner.login`, with a `Commit` also having sha `S` (simulating shared history).
2. Stub `GithubHook`/`GitHubApp#verify_webhook_signature` to return true only for the attacker's organization (simulating a legitimately signed webhook for the attacker's own repo), not for the victim's organization.
3. POST to `/webhooks` with `X-Github-Event: status`, a payload whose `repository.full_name`/`repository.owner.login` reference the **attacker's** repo, and `sha: S`, `state: 'success'`.
4. Assert:
   - `assert_difference('@victim_commit.statuses.count', 1)` around the POST — a `Status` was created on the victim's commit despite the payload naming only the attacker's repository.
   - `assert @victim_commit.reload.deployable?` — `Commit#deployable?` flips to true for the victim's commit.
   - `assert_difference('Deploy.where(stack: @victim_stack).count', 1)` (after performing enqueued `ContinuousDeliveryJob`) — an unauthorized deploy is triggered on the victim's stack, proving the binding "authenticated repository == mutated stack" is violated.
