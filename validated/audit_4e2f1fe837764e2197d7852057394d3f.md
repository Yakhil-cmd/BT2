### Title
Cross-organization webhook confusion: signature verified against one GitHub org while the acted-upon repository/stack belongs to another - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify against using the attacker-controlled, *not-yet-verified* payload field `repository.owner.login` (falling back to `organization.login`), while the code that actually acts on the request (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolves the target `Repository`/`Stack` from an entirely separate field: `repository.full_name`. Nothing enforces that the owner used to pick the verifying secret is the same owner encoded in `full_name`. In a multi-org Shipit deployment (explicitly supported, see `config/secrets.development.shopify.yml` / `docs/setup.md` "multiple Github applications" section), an attacker who legitimately administers one onboarded organization (and therefore knows that organization's own `webhook_secret`) can forge a signed webhook whose `repository.owner.login` is their own org (so the signature check passes) but whose `repository.full_name` names a stack belonging to a different, victim organization on the same Shipit instance. This breaks the binding: *organization that authenticated == repository that is written*.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` runs `verify_signature` as a `before_action`: [1](#0-0) 

`repository_owner` is read straight out of the unauthenticated JSON body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a per-organization `GitHubApp` instance configured with that organization's own `webhook_secret` (see `lib/shipit/github_app.rb` initializer and `verify_webhook_signature`): [3](#0-2) [4](#0-3) 

Once the signature (computed over the *whole* raw body using the secret selected by `repository.owner.login`) checks out, `WebhooksController#create` dispatches the same raw body to event handlers: [5](#0-4) 

Every handler resolves the actual target repository/stack from a *different* JSON field, `repository.full_name`, via `Shipit::Webhooks::Handlers::Handler#repository_name` / `#stacks`: [6](#0-5) 

For example, `PushHandler` uses this to look up stacks and immediately triggers a real GitHub sync against whatever commit SHA the attacker supplies: [7](#0-6) 

Because `repository.owner.login` (used only to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon `Repository`/`Stack`) are two independent JSON fields with no cross-field consistency check, an attacker who knows the `webhook_secret` for *their own* onboarded organization can sign a payload where `repository.owner.login` = their org (verification passes) but `repository.full_name` = `"victim-org/victim-repo"`. The controller has no code path that rejects a mismatch between the two.

### Impact Explanation
This crosses the exact boundary called out in scope: *"an organization that authenticated versus the repository that is written."* A tenant that is only supposed to control webhooks for their own org can forge pushes, pull-request events, or status/check-suite events against a completely different org's `Stack` on the same shared Shipit instance. Concretely, `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for the victim's stack — an unauthorized, attacker-directed action taken against a repository the attacker has no GitHub-side permission on. Depending on which handler is exercised, this can drive `GithubSyncJob`, `Commit`/`Status` creation, `CheckRun` refresh jobs, membership/team mutations, or PR-driven review-stack provisioning (`archive!`/`unarchive!`), all scoped to the victim organization's data. This is an unauthorized cross-tenant write inside the same Shipit deployment, satisfying the Critical "cross-repository writes" / "unauthorized deploy" bar without requiring any Shipit session, API token, or the victim's GitHub credentials.

### Likelihood Explanation
The prerequisite is that Shipit is configured for multiple GitHub organizations sharing one instance — a configuration the engine documents and ships fixtures/examples for (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md`). Any party who is a legitimate admin of one of the onboarded orgs (and thus knows that org's own `webhook_secret`, which they themselves provision when installing their GitHub App) can exploit this without any additional access. No brute-forcing of a secret, no MITM, and no compromise of Shipit internals is required — only crafting two independent JSON fields inconsistently, which the controller never cross-checks.

### Recommendation
After a valid signature is confirmed for the organization identified by `repository_owner`, validate that `repository.full_name`'s owner segment matches that same `repository_owner` (or, more robustly, derive `repository_owner` from `repository.full_name` itself rather than from a separate `owner.login`/`organization.login` field) before dispatching to handlers. Reject the webhook (422) on any mismatch.

### Proof of Concept
1. Shipit is configured with two orgs, `attacker-org` (webhook_secret `S_A`, known to the attacker, who administers that org's GitHub App) and `victim-org` (some stack `victim-org/victim-repo` exists in Shipit, tracking branch `master`).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_A, body)` and sets `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`), verifies successfully against `S_A`.
5. `create` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha: '<attacker-chosen-sha>')` on the victim's stack — a write the attacker never had GitHub permission to trigger.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
