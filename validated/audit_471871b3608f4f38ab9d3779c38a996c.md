### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but the repository actually mutated is taken from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App / webhook secret to validate a signature against using `repository_owner`, a value read straight out of the still‑unverified JSON body. Once the signature check passes, every `Shipit::Webhooks::Handlers::Handler` subclass resolves the repository to mutate using a **different** field of that same payload, `repository.full_name`. Because Shipit is multi‑tenant (one `GitHub App`/webhook secret per organization via `Shipit.github(organization:)`), these two fields are never cross-checked against each other, so the "organization whose secret authenticated the request" and "the repository that gets written to" are two independent trust anchors bound only by attacker-controlled JSON.

### Finding Description
`verify_signature` computes the signing organization directly from the request body before any authenticity check has occurred: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (or `organization.login`) and is used solely to select the `GitHubApp` instance (and thus the `webhook_secret`) that `verify_webhook_signature` checks the HMAC against: [3](#0-2) [4](#0-3) 

Once the HMAC matches *that organization's* secret, `create` dispatches the raw payload to every registered handler for the event: [5](#0-4) 

Every handler (`PushHandler`, the `PullRequest::*` handlers, `StatusHandler`, etc.) subclasses `Shipit::Webhooks::Handlers::Handler`, which independently resolves the target repository/stack from a **different** payload field, `repository.full_name`, via `Repository.from_github_repo_name`: [6](#0-5) 

`PushHandler#process`, for example, uses that repository's stacks and triggers `stack.sync_github(expected_head_sha: params.after)` on the matched branch: [7](#0-6) 

`repository.owner.login` (used for signature-key selection) and `repository.full_name` (used for stack resolution) are two separate JSON fields that GitHub's real webhooks always keep consistent, but the signature itself is computed over the entire raw body with **one specific** secret — it does not assert any relationship between these two fields; it only proves "this exact byte-for-byte payload was signed by whoever holds organization X's secret." Nothing in `verify_signature` or in `Handler#repository_name` cross-validates that the `full_name`'s owner matches `repository.owner.login`.

This is the same class of bug as the reported Lido issue: the code authenticates/validates one quantity (there, `_maxAmount`; here, the signing organization derived from `repository.owner.login`) but then acts on a different, unchecked quantity taken from the same call/payload (there, the true withdrawn `amount`; here, `repository.full_name`), silently trusting they agree.

### Impact Explanation
Any organization onboarded to a shared Shipit instance controls its own webhook secret (an org admin configures the GitHub App/webhook secret for their own org, which is a normal, unprivileged-relative-to-other-tenants action). Such a tenant admin can craft an arbitrary JSON body — sign it with their own known secret, but set `repository.owner.login`/`organization.login` to their own org (so `verify_signature` picks their own secret and the HMAC matches) while setting `repository.full_name` to a victim repository belonging to a completely different organization hosted on the same Shipit instance. The forged event is then dispatched to handlers that only look at `full_name`, letting the attacker trigger `GithubSyncJob`/`sync_github`, forge commit `Status`, or manipulate pull-request/merge-related state (`PullRequest::*Handler`) on a repository/stack they have no legitimate access to. This crosses the "cross-repository writes" impact bucket explicitly listed as Critical.

### Likelihood Explanation
Exploitation requires the attacker to control the webhook secret of at least one organization already configured on the shared Shipit instance — a normal, low-privilege tenant capability in any multi-org Shipit deployment, not a "privileged account" of the target org and not requiring any Shipit session/API token. Because the two fields (`owner.login` vs `full_name`) are never cross-checked anywhere in the verification or dispatch path, the forged cross-tenant event succeeds deterministically once the signature is valid for the attacker's own tenant.

### Recommendation
After `verify_webhook_signature` succeeds, re-derive the organization from the same field the handlers use to resolve the target repository (`repository.full_name`'s owner segment) and assert it matches the organization whose secret validated the signature (or, simpler, always resolve `repository_owner` from `full_name`'s owner component rather than the separate `owner.login`/`organization.login` fields). Reject the webhook if the two disagree.

### Proof of Concept
1. Onboard/attacker-control organization `evil-org` on the shared Shipit instance and note its configured `webhook_secret`.
2. Craft a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "evil-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(evil-org secret, body)>`.
4. POST to `Shipit::WebhooksController#create` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: 'evil-org')` (from `repository.owner.login`), and the HMAC matches that org's secret, so verification passes: [1](#0-0) 
6. `PushHandler#process` runs `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github` on the victim's stack: [6](#0-5) [7](#0-6) 
7. The victim's stack state is mutated using a signature that only ever proved authorization from `evil-org`, not `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
