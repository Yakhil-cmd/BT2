### Title
Unsanitized swap routes execute attacker-controlled contracts under the caller’s authorization, enabling wallet-token theft - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller treats the caller-supplied `swap` payload as opaque executable routing data and forwards it to the configured router without binding it to trusted venue contracts. `swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` all reach this boundary. [1](#0-0) 

Because the strategy entrypoint requires the caller’s authorization, a malicious route-selected contract can perform additional operations that require that same caller’s authorization while nested inside the signed invocation. In particular, it can call `token.transfer(caller, attacker, amount)` for an unrelated wallet token. [2](#0-1) 

### Finding Description
`process_swap_collateral` authenticates `caller`, verifies ownership or delegation, withdraws collateral to the controller, and passes `swap` into `withdraw_and_swap_from_supply`. [3](#0-2)  That helper forwards the exact payload to `swap_tokens_or_passthrough` without inspecting which contracts the route may invoke. [4](#0-3) 

`swap_tokens` validates only that the route is non-empty, authorizes the controller’s exact input-token transfer to the router, invokes `execute_strategy(controller, amount_in, swap)`, and then measures token deltas. [5](#0-4)  These checks bound movement of the strategy input and output tokens, but they do not prevent route-selected code from invoking a different token contract and requesting the caller’s authority.

The test model demonstrates the resulting authorization behavior: a route names a rogue pool, the router invokes it, and that pool calls `wallet_token.transfer(victim, attacker, amount)`. [6](#0-5)  The malicious route is supplied through `swap_collateral`. [7](#0-6)  When the generated authorization tree contains the rogue transfer, the host accepts it and the victim’s wallet balance moves to the attacker. [8](#0-7) 

### Impact Explanation
An attacker can steal any token held by a user who signs a poisoned strategy authorization tree, including tokens unrelated to the lending market being swapped. [9](#0-8)  The malicious transfer succeeds independently of the measured swap-output and router-overspend checks because those checks observe only `token_in` and `token_out`. [10](#0-9) 

This is theft of user funds, but it requires the victim to authorize a transaction whose generated authorization tree includes the rogue transfer, so the impact is bounded by the victim’s signed auth scope rather than allowing an attacker to drain arbitrary users directly. [11](#0-10) 

### Likelihood Explanation
All six router-mediated strategy paths expose caller-controlled `swap` bytes, including `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`. [12](#0-11)  A malicious quote or frontend can supply a route containing attacker-controlled code, while the wallet’s simulation can represent the extra token transfer merely as an additional authorization subtree that the user must manually detect and reject.

The exploit does not require protocol privileges, compromised keys, or control of governance. It does require user interaction and signature approval of the poisoned authorization tree, making it less likely than a purely permissionless direct call but still a practical phishing or malicious-route attack.

### Recommendation
Do not allow route bytes to name arbitrary executable pool contracts. Enforce a governance-controlled venue/pool registry before dispatch, or constrain route execution to fixed, trusted adapters and immutable pool addresses. [13](#0-12) 

At minimum, the controller should reject routes whose decoded hop targets are not approved contracts and should require the router to prove that no route-selected code can consume the original caller’s authorization for unrelated token transfers. Client-side signing software should additionally reject any strategy authorization tree containing children other than the expected controller token pull. [14](#0-13) 

### Proof of Concept
1. Alice supplies USDC and owns a debt-free lending account; she also holds a separate unrelated wallet token. [15](#0-14) 
2. The attacker deploys a contract whose route callback calls `wallet_token.transfer(Alice, attacker, balance)`. [16](#0-15) 
3. The attacker constructs `swap` bytes that route through that contract while still returning a valid output amount. [17](#0-16) 
4. Alice invokes `swap_collateral(Alice, account_id, USDC, amount, ETH, malicious_swap)`. [18](#0-17) 
5. The controller withdraws Alice’s collateral to itself and invokes the configured router with the malicious payload. [19](#0-18) 
6. The rogue contract executes inside the route and requests Alice’s authorization on the unrelated wallet token. If Alice signs the generated authorization tree containing that child invocation, the transfer succeeds and her full wallet balance moves to the attacker. [8](#0-7)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
