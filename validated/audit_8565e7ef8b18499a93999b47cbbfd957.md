### Title
Unbounded `http.Serve` on `--http-bind` endpoint allows slowloris-style file-descriptor/goroutine exhaustion - (File: main.go)

### Summary
The diagnostic HTTP server started when `--http-bind` is set is launched via a bare `http.Serve(ln, mux)` call with no `ReadTimeout`, `WriteTimeout`, `IdleTimeout`, or `ReadHeaderTimeout` configured. Because Go's `net/http` package applies no such timeouts by default when `http.Serve` (rather than a configured `http.Server`) is used, an attacker who can reach the bound port can open many slow/idle connections and hold them open indefinitely, consuming a goroutine and a file descriptor per connection for as long as they choose.

### Finding Description
When `*flHTTPBind != ""`, `main()` binds a listener and starts the liveness (and optionally metrics/pprof) server: [1](#0-0) 

The critical detail is the call `http.Serve(ln, mux)` at line 891. This uses the package-level `http.Serve` helper, which internally constructs a zero-value `&http.Server{}` and calls `Serve` on it. A zero-value `http.Server` has no `ReadTimeout`, `ReadHeaderTimeout`, `WriteTimeout`, or `IdleTimeout` set, so `net/http` will never forcibly close a connection for being slow to send its request or slow to read its response — it relies entirely on the client to close the socket or on OS-level TCP timeouts (which are typically very long or unbounded for idle-but-established connections).

Because the liveness endpoint (`/`) is registered unconditionally whenever `--http-bind` is configured — a standard, documented flag frequently set in Kubernetes sidecar deployments for readiness/liveness probes — any unauthenticated party who can reach the pod's `--http-bind` port (e.g., another pod in the same node/network namespace, or anyone with network access to the Service/Pod) can open many TCP connections, send request bytes slowly (or not at all after the initial SYN/handshake), and never complete or close them. Each such connection ties up one server goroutine (spawned per-accepted connection inside `net/http`) and one open file descriptor for the process's lifetime, since there is no timeout to reclaim it.

This is unrelated to `touch()`, `addUser()`, or `sleepForever()` in a functional sense — those functions do not interact with the HTTP listener — but as the process's file descriptor table and goroutine count are shared process-wide resources, exhausting them via the HTTP listener can starve other subsystems (git process spawning, log file writes via `touch`-created diagnostic files, etc.), causing sync updates to stall or the process to hit `ulimit -n` and fail to fork/exec `git` or open required files.

Existing mitigations do not address this: there is no `net.Listener` deadline wrapper, no `http.Server{ReadTimeout: ...}` configuration, and no per-IP/connection concurrency cap on the listener.

### Impact Explanation
An unauthenticated network peer able to reach the `--http-bind` port can exhaust the git-sync sidecar process's file descriptors and/or goroutines, degrading or halting all sidecar functionality including git fetch/checkout operations and the liveness endpoint itself. In a Kubernetes context this maps to "sidecar denial of service: updates stop" — a real, scoped, in-cluster-reachable resource-exhaustion bug, matching the Kubernetes bug-bounty DoS impact class described in the question.

### Likelihood Explanation
- Requires only the documented, commonly-used `--http-bind` flag to be set (a supported, common Kubernetes sidecar configuration for liveness probes) — no non-default/unusual flags are needed beyond enabling the HTTP endpoint itself.
- No authentication or authorization guards the endpoint.
- The exploit requires only ordinary TCP connections with slow or absent request completion (classic "slowloris"), which is trivially scriptable and highly repeatable; no special network position beyond routable access to the pod's port is needed.
- Feasibility is high and well-understood as a generic Go `net/http` anti-pattern (using `http.Serve`/`http.ListenAndServe` instead of a properly configured `http.Server`).

### Recommendation
Replace the bare `http.Serve(ln, mux)` call with an explicit `http.Server` that sets conservative timeouts, e.g.:
```go
srv := &http.Server{
    Handler:           mux,
    ReadHeaderTimeout: 5 * time.Second,
    ReadTimeout:       10 * time.Second,
    WriteTimeout:      10 * time.Second,
    IdleTimeout:       30 * time.Second,
}
go func() {
    err := srv.Serve(ln)
    log.Error(err, "HTTP server terminated")
    os.Exit(1)
}()
```
Additionally consider limiting maximum concurrent connections (e.g. via a `netutil.LimitListener` wrapper) to bound worst-case goroutine/fd usage.

### Proof of Concept
Integration-style repro (Go test or shell):
1. Start git-sync with `--http-bind=127.0.0.1:PORT` and a valid repo/root.
2. From an attacker script, open N (e.g., 2000) raw TCP connections to `127.0.0.1:PORT`, send only a partial HTTP request line (e.g., `GET / HTTP/1.1\r\n`) without completing headers, and never close the socket.
3. Observe via `/proc/<pid>/fd` (or `lsof -p <pid>`) that open file descriptor count grows linearly with the number of held-open connections and never decreases.
4. Confirm via `curl --max-time 2 http://127.0.0.1:PORT/` from a legitimate health-checker that requests begin to fail/time out once the process approaches `ulimit -n`, and that subsequent git fetch cycles (observable via sync counters/logs) stop advancing — demonstrating "updates stop."
