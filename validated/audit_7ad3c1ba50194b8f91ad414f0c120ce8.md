### Title
Nil Pointer Dereference in `parseAndValidatePrivateProfile` via Attestation Unit Missing `profile` Field - (File: private_profile.js)

### Summary
`parseAndValidatePrivateProfile()` in `private_profile.js` dereferences `payload.profile.profile_hash` without ever checking that `payload.profile` exists. The `payload` here is the `attestation`-app message payload taken directly from a DAG unit that only needs to pass the generic unit validator (`validation.js`), where the `profile` field of an attestation payload is optional. Any unprivileged unit poster can broadcast a normal, fully valid `attestation` unit that omits `profile` entirely; when a peer wallet later receives/handles a `private_profile` message (an untrusted, attacker-controlled payload sent over the wallet chat/contact channel) that references this unit's `payload_hash`, the code crashes with a TypeError ("Cannot read properties of undefined").

### Finding Description
`parseAndValidatePrivateProfile(objPrivateProfile, onDone)` reads a unit from storage and looks up the `attestation` message matching `objPrivateProfile.payload_hash`: [1](#0-0) 

After recomputing a `hidden_profile` hash from attacker-supplied `src_profile` data, it directly compares against `payload.profile.profile_hash`: [2](#0-1) 

There is no check that `payload.profile` is a non-empty object before accessing `.profile_hash`. The outer input validation of `objPrivateProfile` only checks `unit`, `payload_hash`, and `src_profile` shape — it never inspects the referenced unit's actual attestation payload: [3](#0-2) 

Per general unit validation, the `attestation` app message payload requires only a valid `address`; the `profile` sub-object is optional (an attestor can post an attestation with just an address and no profile fields). That means any unprivileged unit poster can construct a fully-valid, on-chain `attestation` message with no `profile` field at all. When any peer subsequently receives an out-of-band `private_profile` message (untrusted wallet/contact message data, handled through `getPrivateProfileFromJsonBase64` → `parseAndValidatePrivateProfile`) pointing its `payload_hash` at that attestation message, `handleJoint()` will execute `payload.profile.profile_hash` on `undefined`, throwing an uncaught TypeError that crashes the node process — the same root cause pattern as the free5GC UDM bug (unvalidated nil access on attacker-influenced nested field reachable via network-received data).

### Impact Explanation
The crash occurs in a `storage.readJoint`/`eventBus` callback with no surrounding try/catch, so the exception is unhandled and terminates the Node.js process (denial of service against the wallet/node processing the private-profile message). This matches the "network unable to confirm new units" / node-crash class of impact acceptable per the validation rules, since a crashed full node stops relaying and confirming units until manually restarted.

### Likelihood Explanation
High. Both preconditions are trivially reachable by an unprivileged actor:
1. Post any valid `attestation` unit with no `profile` field (fully compliant with unit validation rules).
2. Send a `private_profile` payload (or induce a wallet counterparty to process one) whose `payload_hash` matches that message.

No special privileges, keys, or race conditions are required — only crafting two ordinary, protocol-valid inputs.

### Recommendation
In `private_profile.js`, validate `payload.profile` before dereferencing it:
```js
if (!payload.profile || typeof payload.profile !== 'object' || calculated_profile_hash !== payload.profile.profile_hash)
    return onDone("wrong profile hash");
```
Additionally, wrap the `handleJoint` body (or at minimum this comparison) in a try/catch, and reject payloads whose referenced attestation message does not actually contain a `profile` field before attempting hash comparison.

### Proof of Concept
1. Attacker A posts a valid `attestation` unit `U` with `payload = { address: "<addrA>" }` (no `profile` field) — this passes standard unit validation since `profile` is optional in attestation payloads.
2. Attacker A crafts and sends (via wallet chat/contact "private profile" message) a base64 JSON blob decoding to:
```json
{ "unit": "<hash of U>", "payload_hash": "<payload_hash of the attestation message in U>", "src_profile": { "some_field": ["value", "blinding"] } }
```
3. Victim wallet/node calls `getPrivateProfileFromJsonBase64` then `parseAndValidatePrivateProfile`, which locates `U`, finds the attestation `payload` (no `profile` key), computes `hidden_profile` hash, and executes `payload.profile.profile_hash` — throwing `TypeError: Cannot read properties of undefined (reading 'profile_hash')`, crashing the process. [2](#0-1)
