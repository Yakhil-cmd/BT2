### Title
Webhook signature verified against wrong organization allows cross-organization/repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the `webhook_secret` used for HMAC verification) using `repository_owner`, which is derived from `params.dig('repository','owner','login')` **or, if that path is absent, falls back to** `params.dig('organization','login')`. However, the code path that actually decides *which repository/stacks get acted upon* — `Shipit::Webhooks::Handlers::Handler#repository_name` — always reads `payload.dig('repository', 'full_name')`, a completely different field that is never re-checked against the field used to select the signing secret. This breaks the equality: *organization whose secret authenticated the request == organization owning the repository being written to*.

### Finding Description [1](#0-0) 

`verify_signature` picks the `GitHubApp` config (and its `webhook_secret`) via: [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Meanwhile the actual write-path used by every handler resolves the target repository from a *different, unguarded* field: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

In a legitimate GitHub-generated payload these two fields (`repository.owner.login` and `repository.full_name`) are always consistent because GitHub itself populates them from the actual repo being pushed to. But `verify_signature` only checks the raw byte signature against whichever org's secret is *selected by the payload itself*, with a fallback to `organization.login` when `repository.owner.login` is missing. Because Shipit supports hosting multiple GitHub organizations behind one instance (see the "Using Multiple Github Applications" config, each with its own independent `webhook_secret`) [4](#0-3) , an operator/attacker who is a legitimate owner of *one* configured, lower-trust organization (and therefore knows/controls that org's own `webhook_secret`, since GitHub App webhook secrets are generated by the org's own app owner during setup) can build an arbitrary hand-crafted JSON body — not something delivered by GitHub — and sign it with their own org's secret.

The forged payload can:
1. Omit `repository.owner.login` (or nest it however needed) while setting the top-level `organization.login` to their own org — so `verify_signature` resolves and validates against their own known secret.
2. Set `repository.full_name` to point at an arbitrary *other* configured organization's repository (e.g. `"PrivilegedOrg/victim-repo"`).

Since `verify_signature`'s org-selection field and `Handler#repository_name`'s target field are decoupled, the signature check passes even though the payload will be dispatched against a repository belonging to a different, unrelated organization whose secret the attacker never had.

### Impact Explanation
Depending on the event type dispatched, this crosses an organizational trust boundary and can be used to:
- `push` event via `PushHandler` — force `stack.sync_github(expected_head_sha: ...)` on any stack in the victim's org/repo [5](#0-4) , which can trigger a `GithubSyncJob` and influence continuous deployment pipelines for a repository the attacker does not control.
- `status` event via `StatusHandler` — inject arbitrary commit statuses for any commit sha, which the merge queue and deploy gating logic rely on to allow merges/deploys [6](#0-5) .
- `check_suite` event — force check-run refresh scheduling for arbitrary stacks/commits [7](#0-6) .

Forcing/spoofing commit statuses is particularly severe: Shipit's merge queue and blocking-status checks (per the README/CHANGELOG) gate merges and deploys on statuses reported through this exact webhook path. An attacker who can forge a "success" status for an arbitrary commit belonging to a repository they do not own could push that repo's merge queue/deploy pipeline into merging or deploying code it should not, i.e., an unauthorized deploy/merge condition — squarely matching the "unauthorized deploy, rollback or merge" impact bar.

### Likelihood Explanation
This requires the operator to run Shipit in the documented multi-organization mode with more than one GitHub App/organization configured (an explicitly supported and documented deployment topology) [8](#0-7) , and requires the attacker to be the legitimate holder of one such org's own `webhook_secret` (something they normally know because they configure their own org's GitHub App). No repository write access, Shipit session, or `ApiClient` token to the *victim* org is needed — only knowledge of a secret for any one of the organizations sharing the same Shipit instance. This is a realistic scenario in shared/multi-tenant Shipit deployments and does not require social engineering, TLS interception, or a privileged Shipit account.

### Recommendation
Do not let two independent fields determine (a) which secret verifies the signature and (b) which repository is acted upon. Concretely:
- After signature verification succeeds, re-derive the organization strictly from `repository.full_name`'s owner segment (or `repository.owner.login`) and require it to exactly equal the organization whose secret validated the signature; reject (422) on any mismatch.
- Do not fall back to top-level `organization.login` for events that also carry a `repository` object; the fallback should only be used for organization-only events (e.g., `membership`) that have no `repository` key at all, and even then the resulting organization must be the one actually used to resolve any stacks/teams in the handler.
- Consider binding the webhook signature check to a specific, expected organization prior to parsing any repository-derived routing fields, by matching the request path/host to a known org from configuration rather than trusting attacker-suppliable payload fields for that decision.

### Proof of Concept
1. Configure Shipit with two organizations, each with a distinct `webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications"): `OrgTwo` (attacker-controlled) and `OrgOne` (victim, hosts stack for `OrgOne/victim-repo`).
2. Attacker (who administers `OrgTwo`'s GitHub App and therefore knows `OrgTwo`'s `webhook_secret`) crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha in OrgOne/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "organization": { "login": "OrgTwo" },
  "repository": { "full_name": "OrgOne/victim-repo" }
}
```
Note there is no `repository.owner.login` key, so `repository_owner` falls back to `organization.login` = `"OrgTwo"`.
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgTwo_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: 'OrgTwo')` and validates the signature successfully against the attacker's own known secret.
5. `Shipit::Webhooks.for_event('status')` invokes `StatusHandler`, which looks up `Commit.where(sha: ...)` for the victim's commit (found via `repository.full_name = "OrgOne/victim-repo"`) and calls `create_status_from_github!`, injecting an attacker-controlled status for a commit in an organization the attacker never authenticated against.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
