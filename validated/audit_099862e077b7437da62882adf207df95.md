## Analysis

I found a strong analog to the "lifetime signature with no expiration" bug class in ocore's attestation-gated asset mechanism, implemented in `storage.filterAttestedAddresses` and consumed by `validatePaymentInputsAndOutputs` and by the `'attested'` definition operator.

### Title
Permanent, non-revocable attestation grants allow spending attested-only assets forever, even after the attestor wants to revoke authorization - (File: `storage.js`)

### Summary
Assets with `spender_attested=1` (KYC/whitelist-gated tokens) and address definitions using the `['attested', [address, [attestors]]]` operator both rely on `filterAttestedAddresses()` to decide whether an address is "attested" by one of the specified attestor addresses. This check only verifies that *some* immutable attestation unit from that attestor ever became stable for the address; it never checks the attestation's freshness, content, or an expiration, and there is no revocation message type. Once an attestor authorizes an address (analogous to NftPort's SIGNER_ROLE co-signing a license), that authorization is permanent and unrevokable except by rotating the attestor's private key — mirroring exactly the root cause described in the referenced report (lack of expiration on a "signedOnly"-style authorization).

### Finding Description
`filterAttestedAddresses` in `storage.js` performs: [1](#0-0) 
It selects any stable `attestations` row where `attestor_address IN(?)` and `address IN(?)`, filtering out only attestations that predate the address's *latest* definition change. There is no timestamp, expiry, or "latest attestation supersedes/revokes prior" semantics — a single historical attestation unit permanently satisfies the check for the lifetime of the address (or until the address changes its own definition, which is under the *user's* control, not the attestor's).

This function gates two independent enforcement points reachable by an unprivileged unit poster:

1. **Attested-asset payments** — `validatePaymentInputsAndOutputs` requires every output address of a `spender_attested` asset to appear in `filterAttestedAddresses`' result set before a transfer is accepted: [2](#0-1) 

2. **Address-definition `'attested'` spending condition** — `validateAuthentifiers`'s `evaluate()` uses the exact same lookup to unlock a `sig`-style spending branch: [3](#0-2) 

In both cases the asset definer or attestor has no in-protocol mechanism to invalidate a specific previously-issued attestation. Compare this to `data_feeds.js`, which supports time/MCI-scoped freshness checks (`min_mci`, oracle history), or to device-pairing secrets, which explicitly carry `expiry_date` and are consumed/deleted on use — the attestation mechanism has neither.

### Impact Explanation
For any `spender_attested` asset (used for regulated/KYC-gated tokens) or any address definition employing `['attested', ...]`, once the attestor (e.g., a compliance/KYC service) attests an address, that address permanently retains spending/output eligibility for the asset — even if the underlying real-world authorization (KYC status, license, compliance approval) is later revoked by the attestor. The attestor's only recourse is to stop posting *new* attestations for other addresses, but cannot un-attest an address that was already attested; the sole workaround (rotating the attestor address used in the asset's whitelist / definition) breaks the whitelist for **all** previously and legitimately attested addresses at once, not just the one that should be revoked — this is the same "revoke by changing the signer key, collaterally invalidating everyone" flaw called out in the referenced Factory.sol finding. This can let a de-authorized address continue trading/holding a regulated asset indefinitely, causing loss of custodian control and potential regulatory-compliance failure for the asset issuer, without requiring any bug in signature cryptography itself.

### Likelihood Explanation
Any user (attested address holder) can trigger this by simply continuing to transact with a `spender_attested` asset or an `['attested',...]` gated address after the attestor intends to revoke them — no special privileges or malicious peers/hubs are needed; it only requires a single already-attested unit poster acting normally with a payment or address-definition spending path. Given that attested assets are an explicit, documented ocore feature intended precisely for revocable compliance gating (`spender_attested`, `asset_attestors`), the likelihood of this scenario occurring in a live compliance-oriented asset deployment is high.

### Recommendation
Add expiration/revocation semantics to the attestation model:
- Extend the `attestation` payload (and `attestations`/`attested_fields` tables) to support either a `validity`/`expires_at` field checked against `last_ball_mci`/timestamp in `filterAttestedAddresses`, or
- Introduce an explicit "revoke attestation" message type that `filterAttestedAddresses` treats as taking precedence over ("superseding") any earlier attestation from the same attestor for the same address, mirroring how `address_definition_changes` already supersede older attestations in the current query.
- Alternatively, make `filterAttestedAddresses` only honor the *most recent* attestation per (attestor, address) pair rather than "any" attestation, and allow that latest attestation's `profile` to encode a boolean/void state representing revocation.

### Proof of Concept
1. Asset issuer creates asset `A` with `spender_attested=true` and `attestors=[X]` via the `asset`/`asset_attestors` messages (see schema `assets.spender_attested`, `asset_attestors`).
2. Attestor `X` posts an `attestation` message for address `U` (`payload.address = U`), which is written into the `attestations` table by `writer.js`: [4](#0-3) 
3. `U` can now freely receive/spend outputs of asset `A`, validated via `filterAttestedAddresses` returning `U` in the attested set.
4. Attestor `X` decides `U` should no longer be authorized (e.g., failed compliance re-check) but has **no message type** to remove the `attestations` row for `U`/`X`, nor any way to make `filterAttestedAddresses` stop returning `U`.
5. `U` continues to post payments moving asset `A` in/out; `validatePaymentInputsAndOutputs` keeps accepting them because the original (still-stable, permanent) attestation unit satisfies the query in `storage.js` lines 1961-1967 indefinitely.
6. The only mitigation is for `X` to rotate to a new attestor address and reissue attestations for all *still-valid* addresses — an operationally destructive workaround exactly analogous to the Factory.sol `SIGNER_ROLE` rotation workaround described in the original report.
