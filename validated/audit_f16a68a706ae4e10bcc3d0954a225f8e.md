### Title
Cross-Repository Status Injection via Unscoped Commit Lookup in Webhook Status Handler - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App belonging to a *single organization*, derived from the payload's `repository.owner.login` (or `organization.login`), and picks the matching `webhook_secret` to HMAC-verify the raw body. [1](#0-0)  This proves only that the request was sent by *that* organization's GitHub App installation — it says nothing about which `Stack`/`Commit` records in this (potentially multi-tenant) Shipit instance the payload is allowed to mutate. `StatusHandler`, unlike every other handler, never re-derives that scope: it looks up commits globally by `sha` alone and writes the attacker-supplied status onto them.

### Finding Description
Every other webhook handler resolves the target `Stack`/`Repository` via `Handler#stacks`, which filters `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` — e.g. `PushHandler#process` and `CheckSuiteHandler#process` both scope through `stacks`. [2](#0-1) [3](#0-2) [4](#0-3) 

`StatusHandler`, however, only requires `sha` and `state` and never touches `repository`/`stacks` at all: [5](#0-4) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

This is the binding break the analog class targets: the **organization that authenticated** the webhook (verified via the org-specific `webhook_secret` in `GitHubApp#verify_webhook_signature`) [6](#0-5)  is not the same set as **the repository/stack whose data is written** (`Commit.where(sha:)` is unscoped across the entire installation). In a multi-organization deployment (Shipit explicitly supports configuring multiple GitHub orgs, each with its own `webhook_secret`, via `Shipit.github_app_config`) [7](#0-6) , an org that is a legitimate, non-privileged tenant of the Shipit instance can send a correctly-signed `status` event using its own webhook secret, but reference a `sha` belonging to a commit tracked under a *different* organization's stack — most trivially achieved by forking a public target repository (forks share identical SHA-1 commit IDs for all commits prior to the fork point) and reporting a status for one of those shared commits.

Because `Commit` records are not required to be globally unique per organization/repo boundary in this query, the forged status is written onto the *victim* organization's commit, indistinguishable from a genuine GitHub CI status update.

### Impact Explanation
Commit statuses directly gate Shipit's automated deploy/merge logic: `MergeRequest#all_status_checks_passed?` / `any_status_checks_failed?` build a `StatusChecker` from `head.statuses_and_check_runs` [8](#0-7) , and `ProcessMergeRequestsJob` automatically calls `merge_request.merge!` once `all_status_checks_passed?` is true [9](#0-8) . By injecting a fabricated "success" status for a required CI context onto a victim organization's commit, an attacker who only controls their own onboarded (but unrelated) organization can cause CI requirements to be satisfied for a repository they do not own, leading to an **unauthorized automatic merge or deploy** in a stack belonging to another tenant — this is a cross-repository/cross-tenant write and unauthorized-merge scenario, which the rules explicitly classify as Critical impact.

### Likelihood Explanation
Exploitation requires only: (1) the target Shipit instance to host more than one organization/repository (a normal, documented configuration via `secrets.github` multi-org schema), and (2) the attacker to control any onboarded organization's GitHub App webhook secret for their own (legitimate) stack — no privileged access, no stolen tokens, no TLS interception. Producing a `sha` collision with a target repo is trivial via a public fork (identical ancestor commit hashes) rather than requiring a SHA-1 collision attack. This makes the likelihood realistic for any multi-tenant Shipit deployment.

### Recommendation
Scope `StatusHandler#process` (and any future handler) the same way `PushHandler`/`CheckSuiteHandler` do: require and validate `payload.dig('repository','full_name')`, and restrict the `Commit` lookup to commits belonging to stacks of that specific, webhook-verified repository (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or an equivalent join), rejecting/ignoring statuses for shas that don't belong to the authenticated repository's stacks.

### Proof of Concept
1. Shipit instance configured with two orgs in `secrets.github`: `victim-org` (tracks `victim-org/app`) and `attacker-org` (tracks `attacker-org/app-fork`, a fork of `victim-org/app`), each with its own `webhook_secret`.
2. Attacker forks `victim-org/app` to `attacker-org/app-fork`; commit `abcd123...` (pre-fork) exists identically in both repositories/Shipit stacks.
3. Attacker (via their own legitimate GitHub App installation for `attacker-org`) sends a `status` webhook, correctly signed with `attacker-org`'s `webhook_secret`:
```json
{
  "sha": "abcd123...",
  "state": "success",
  "context": "ci/required-check",
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/app-fork"}
}
```
4. `WebhooksController#verify_signature` validates the signature against `attacker-org`'s secret and passes. [10](#0-9) 
5. `StatusHandler#process` runs `Commit.where(sha: 'abcd123...')`, which also matches the `Commit` row belonging to `victim-org/app`'s stack, and writes the forged "success" status onto it. [11](#0-10) 
6. If `ci/required-check` was the only missing/failing required status on a pending merge request or deploy for `victim-org/app`, `ProcessMergeRequestsJob`/deploy automation proceeds, effecting an unauthorized merge/deploy driven entirely by an attacker who never had access to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
