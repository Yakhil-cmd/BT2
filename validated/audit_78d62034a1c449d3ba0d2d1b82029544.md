### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no scoping to the repository that sent the webhook, unlike every sibling handler. Because the `commits` table's uniqueness constraint is `(sha, stack_id)` — not `sha` alone — the schema explicitly anticipates that the same SHA can exist under multiple stacks/organizations (e.g. forks, shared history, template repos), and a validly-signed webhook from one organization can create a `Status` and mutate the CI state of a completely unrelated organization's stack.

### Finding Description
The claimed binding is: `verified_organization(webhook) == commit.stack.repository.owner` for every `Commit` record that `StatusHandler#process` mutates. Tracing the code shows this binding is never enforced.

`WebhooksController#verify_signature` validates the signature against `Shipit.github(organization: repository_owner)`, where `repository_owner` is taken from the payload's `repository`/`organization` field [1](#0-0) . This only proves the request genuinely came from GitHub for *that* organization — it says nothing about which stacks the handler is allowed to touch.

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This query is global across the entire `commits` table — it is not filtered by `repository_name`/`stacks` at all. Contrast this with the base `Handler#stacks` helper, `Repository.from_github_repo_name(repository_name)&.stacks`, which every other handler uses to scope work to the repository named in the payload [3](#0-2) . `CheckSuiteHandler#process`, for example, correctly scopes via `stacks.where(branch: ...)` before touching any commit [4](#0-3) , and `PushHandler#process` does the same [5](#0-4) . `StatusHandler` is the outlier that omits this scoping.

The DB schema confirms multiple stacks can legitimately hold identical SHAs: the unique index is `add_index :commits, %i(sha stack_id), unique: true` [6](#0-5)  — SHA alone is not unique. This happens naturally with forks, mirrored repos, or shared template history, all of which reproduce byte-identical commit objects (and therefore identical SHA-1 hashes) across unrelated repositories/organizations.

`commit.create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, where `stack_id` is the *matched commit's own* `stack_id`, not anything derived from the requesting repository [7](#0-6) . The new `Status` row's `after_create :enable_ci_on_stack` then calls `commit.stack.enable_ci!` on that unrelated stack [8](#0-7) , and `after_commit :schedule_continuous_delivery` runs continuous-delivery evaluation for that same foreign stack/commit.

Root cause: missing repository-to-stack authorization scoping in `StatusHandler#process`, letting a validly-signed webhook for organization A mutate persisted `Status` records (and derived CI-enabled cache state, and potentially trigger continuous delivery) for a completely different, unrelated stack B whenever B happens to contain a commit with the same SHA.

One correction to the question's framing: `Stack#enable_ci!` does **not** write a persisted column — it writes a Rails cache entry (`Rails.cache.write(ci_enabled_cache_key, true)`) [9](#0-8) , and that flag only suppresses a UI "Heads Up!" banner [10](#0-9) . That specific side effect is cosmetic, not a persisted-config mutation. However, the same unscoped query also creates a genuine, persisted `Status` row on the victim stack and can drive `schedule_continuous_delivery`, which (per `test/models/commits_test.rb`'s CD tests) can actually enqueue a `Deploy` if the victim stack has `continuous_deployment: true` and the fabricated status transitions the shared commit to `success`. That is the real, higher-severity consequence of the same missing-scoping bug.

### Impact Explanation
An attacker who controls (or can push commits/webhooks for) any organization/repository already onboarded to Shipit can send a genuine GitHub `status` webhook (signed by GitHub itself using that org's real, legitimate secret — no secret knowledge needed by the attacker) referencing a commit SHA that also exists in a different, unrelated organization's tracked stack (via fork, template, or shared history). This creates a `Status` record on the victim stack that the victim's repository never sent, flips the victim's cached CI-enabled state, and — if the victim stack has continuous deployment enabled — can enqueue an unauthorized `Deploy` for that stack. This is a cross-repository mutation of another tenant's stack/commit state triggered by a payload the victim never authorized, matching the Critical category ("a payload for one repository mutating another's stack, commit, task"), with a path toward an unauthorized deploy.

### Likelihood Explanation
Preconditions: the attacker needs control of at least one repository/organization already integrated with Shipit (so GitHub will sign the webhook with a valid secret), and needs a commit whose SHA collides with a commit tracked under a different stack. This is realistic for forks of a Shipit-tracked public repo, mirrored repos, or repos generated from a common template/scaffold, all of which reproduce identical commit objects and therefore identical SHA-1 hashes without any brute-force collision needed. No Shipit secrets, sessions, or privileged roles are required — only ordinary GitHub push access to an onboarded repo. The exploit is repeatable per matching commit and requires no interaction beyond a normal `git push`/webhook delivery.

### Recommendation
Scope `StatusHandler#process` to the repository that sent the webhook, mirroring `CheckSuiteHandler`/`PushHandler`: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` first, then restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), so a `Status` can only be created for commits belonging to stacks owned by the verified repository.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
test "status webhook for org A cannot create a Status on org B's stack sharing the same sha" do
  attacker_stack = shipit_stacks(:shipit)          # org A, onboarded
  victim_stack   = shipit_stacks(:cyclimse)        # org B, unrelated

  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_stack.commits.create!(sha: shared_sha, ...) # forked/shared history

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "repository" => { "full_name" => attacker_stack.github_repo_name },
    "branches" => [{ "name" => attacker_stack.branch }]
  }

  before = victim_stack.reload.ci_enabled?
  refute before

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_equal victim_commit.stack_id, victim_stack.id
  assert victim_stack.reload.statuses.where(sha: shared_sha).exists? rescue nil
  assert victim_stack.reload.ci_enabled?  # was false, now true, without victim's org ever sending anything
end
```
Assertion on both sides of the binding: `victim_stack.repository.owner` (unaffected org) vs. the organization actually verified by `verify_signature` for `attacker_stack.repository.owner` — these differ, yet `victim_stack.ci_enabled?` still flips to `true` and a `Status` row is written under `victim_stack.id`, proving the divergence.
