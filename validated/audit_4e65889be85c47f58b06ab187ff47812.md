### Title
`subbridge` and `mainbridge` Namespaces Registered as `Public: true` Expose Unauthenticated Bridge Fee Redirection and Operator Unlock Over HTTP RPC — (`node/sc/subbridge.go`, `node/sc/mainbridge.go`, `node/sc/api_bridge.go`)

---

### Summary

The `subbridge` and `mainbridge` RPC namespaces are registered with `Public: true`. When a service-chain node enables its HTTP RPC endpoint (even with no module whitelist), the entire `SubBridgeAPI` and `MainBridgeAPI` surface — including `SetFeeReceiver`, `SetKLAYFee`, `SetERC20Fee`, `UnlockParentOperator`, `UnlockChildOperator`, `DeregisterBridge`, and `DeregisterToken` — is reachable by any unauthenticated HTTP client that can reach the port. This is the direct Kaia analog of the external report's "open ports" finding: sensitive privileged services are exposed without authentication at the API-registration layer.

---

### Finding Description

**Registration with `Public: true`:**

`SubBridge.APIs()` registers the entire `SubBridgeAPI` as public:

```go
// node/sc/subbridge.go
func (sb *SubBridge) APIs() []rpc.API {
    return []rpc.API{
        {
            Namespace: "subbridge",
            Version:   "1.0",
            Service:   sb.APIBackend,   // SubBridgeAPI — all methods
            Public:    true,            // ← exposed over HTTP
        },
        ...
    }
}
```

`MainBridge.APIs()` does the same for `mainbridge`.

**HTTP exposure logic:**

`StartHTTPEndpoint` in `networks/rpc/endpoints.go` exposes every `Public: true` API when no module whitelist is configured:

```go
if !api.IPCOnly && (whitelist[api.Namespace] || (len(whitelist) == 0 && api.Public)) {
    handler.RegisterName(api.Namespace, api.Service)
}
```

When `--rpcapi` is not set, `len(whitelist) == 0`, so every `Public: true` namespace — including `subbridge` — is registered on the HTTP server.

**Sensitive methods exposed without authentication:**

| Method | On-chain effect |
|---|---|
| `SetFeeReceiver(bridgeAddr, receiver)` | Sends tx to bridge contract changing fee recipient |
| `SetKLAYFee(bridgeAddr, fee)` | Sends tx to bridge contract changing KLAY transfer fee |
| `SetERC20Fee(bridgeAddr, tokenAddr, fee)` | Sends tx to bridge contract changing ERC20 transfer fee |
| `UnlockParentOperator(passphrase, duration)` | Unlocks the parent-chain bridge operator account |
| `UnlockChildOperator(passphrase, duration)` | Unlocks the child-chain bridge operator account |
| `DeregisterBridge(cBridge, pBridge)` | Removes bridge pair from manager, stops value transfer |
| `DeregisterToken(...)` | Sends tx to bridge contract deregistering a token pair |
| `RegisterOperator(bridge, operator)` | Adds a new operator to the bridge contract |

`SetFeeReceiver`, `SetKLAYFee`, `SetERC20Fee` call into `bridgeManager` which submits signed on-chain transactions using the bridge operator account. These succeed whenever the operator account is unlocked — which it must be for automated bridge operation to function.

---

### Impact Explanation

An attacker who can reach the HTTP RPC port of a service-chain node running with `--rpc` (and no `--rpcapi` whitelist, or with `subbridge` explicitly listed) can:

1. **Redirect all bridge fees** — call `subbridge_setFeeReceiver(bridgeAddr, attackerAddr)`. This submits an on-chain transaction that changes the fee recipient in the bridge contract. All subsequent cross-chain transfer fees (KLAY and ERC20) are paid to the attacker's address. This is an unauthorized fee charge affecting bridged assets.

2. **Manipulate bridge fees** — call `subbridge_setKLAYFee` / `subbridge_setERC20Fee` to set fees to zero (griefing the operator) or to an extreme value (blocking user transfers).

3. **Unlock bridge operator accounts** — call `subbridge_unlockParentOperator` / `subbridge_unlockChildOperator` with a guessed or empty passphrase. A successful unlock gives the attacker the ability to trigger any subsequent operator-signed transaction.

4. **Disrupt bridge operations** — call `subbridge_deregisterBridge` or `subbridge_deregisterToken` to halt value transfer for a bridge pair or token, causing pending cross-chain transfers to stall.

The corrupted value is the `feeReceiver` storage slot in the deployed bridge contract, written by an unauthorized caller. The lost asset is the stream of bridge fees redirected to the attacker.

---

### Likelihood Explanation

- Service-chain operators routinely enable HTTP RPC for monitoring and management. The default config has `http-rpc.enable: false`, but operators enabling it without an explicit `--rpcapi` whitelist expose the full public surface.
- The bridge operator account must be unlocked for automated value transfer to work, so `SetFeeReceiver` succeeds without any additional step once the attacker reaches the port.
- No authentication, no CORS enforcement for non-browser clients, and no IP allowlist is enforced at the code level.
- The attack requires only network access to the RPC port and knowledge of the bridge contract address (which is logged and discoverable).

---

### Recommendation

1. Change `Public: false` (or add `IPCOnly: true`) for all write-capable `subbridge` and `mainbridge` API entries in `node/sc/subbridge.go` and `node/sc/mainbridge.go`. Read-only informational methods can remain public if needed.
2. Split `SubBridgeAPI` into a read-only public struct and a write-capable private/IPC-only struct, mirroring the pattern used for `debug` (`IPCOnly: s.config.DisableUnsafeDebug`).
3. Document that `--rpcapi subbridge` must never be set on internet-facing nodes.

---

### Proof of Concept

Precondition: service-chain node running with `--rpc --rpcaddr 0.0.0.0 --rpcport 8551` (no `--rpcapi` restriction), bridge operator account unlocked for automated operation.

```bash
# 1. Discover the bridge address (publicly logged at startup or via subbridge_getBridgeInformation)
BRIDGE="0xABCD..."

# 2. Redirect all bridge fees to attacker address — no authentication required
curl -s http://<node-ip>:8551 -X POST \
  -H 'Content-Type: application/json' \
  --data '{
    "jsonrpc":"2.0","id":1,
    "method":"subbridge_setFeeReceiver",
    "params":["'"$BRIDGE"'","0xAttackerAddress"]
  }'
# Returns: {"jsonrpc":"2.0","id":1,"result":"0x<txHash>"}
# On-chain: bridge contract feeReceiver slot updated to attacker address.
# All subsequent cross-chain transfer fees are paid to the attacker.

# 3. Optionally attempt operator unlock (if passphrase is weak/empty)
curl -s http://<node-ip>:8551 -X POST \
  -H 'Content-Type: application/json' \
  --data '{"jsonrpc":"2.0","id":2,"method":"subbridge_unlockParentOperator","params":["","null"]}'
