### Title
CCMenu API endpoint leaks any stack's deploy status because it bypasses the `current_api_client.stack_id` scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the `stack` accessor to call `Stack.from_param!(params[:stack_id])` directly instead of using `BaseController#stacks.from_param!`, which is the only place that scopes lookups to `current_api_client.stack_id`. `require_permission :read, :stack` only checks that the client's permission list contains `"read:stack"` via `ApiClient#check_permissions!`, it never checks which stack the client is bound to. As a result, an API client that is scoped to one stack can fetch the CCMenu XML (`shipit/ccmenu/project.xml.builder`) for any other stack in the installation.

### Finding Description
The binding that should hold is: `stack.id == current_api_client.stack_id` (when `current_api_client.stack_id?` is true), enforced by `BaseController#stacks`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`CCMenuController` shadows this with its own private `stack` method that skips the `stacks` scope entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`require_permission :read, :stack` only invokes `current_api_client.check_permissions!(:read, :stack)`, which is a simple membership check against `ApiClient#permissions`, with no reference to `stack_id` at all:
```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [3](#0-2) 

So after `stack.id == current_api_client.stack_id` is checked against the actual code: for a stack-scoped `ApiClient` (`stack_id` set), the left side is whatever `params[:stack_id]` resolves to via the unscoped `Stack.from_param!`, and the right side is never consulted in `CCMenuController`. The equality is not enforced; any `params[:stack_id]` value resolves regardless of the client's bound stack.

Exploit flow: an operator creates an `ApiClient` scoped to Stack A (`stack_id = A.id`, permission `read:stack`) and hands its token to a limited caller. That caller sends `GET /api/stacks/:owner/:repo/:env/cc.xml?token=<A-scoped-token>` (or via HTTP Basic auth) with `stack_id` matching Stack B's param instead. `authenticate_api_client` in `CCMenuController` authenticates the token fine, `require_permission :read, :stack` passes because the client does have `read:stack` in its permission list, and `stack` resolves to Stack B via the unscoped `Stack.from_param!`. The view then renders Stack B's `deploys_and_rollbacks.last` info (SHA, status, timestamps) into the XML response.

Existing guards do not stop this: `verify_signature`/webhook checks are irrelevant here (this is the CCMenu read path, not the webhook path); `ExplicitParameters` isn't used on this action; `require_permission!` only checks the permission string, not stack identity; and the one guard that would have prevented it — `stacks` scoping in `BaseController` — is explicitly bypassed by the overridden `stack` method in `CCMenuController`.

### Impact Explanation
Any caller holding a token for an `ApiClient` scoped to one stack (even the least-privileged, single-stack client) can read the latest deploy SHA, status (success/failure/locked), and timestamps for every other stack in the Shipit installation, by iterating `stack_id` params. This is a cross-tenant unauthenticated (relative to the target stack) read of deploy state, matching the High severity category "unauthenticated read of stack state, task streams or deploy output." It is fully repeatable against arbitrary stacks since `Stack.from_param!` is unscoped and the request can simply vary `params[:stack_id]`.

### Likelihood Explanation
Preconditions: the attacker must possess a valid `ApiClient` token with `read:stack` permission scoped to any single stack — this is the normal, lowest-privilege configuration an operator would issue to a third party (e.g., a CI dashboard integration meant to see only its own stack's status). No GitHub secrets, webhook secrets, or elevated Shipit roles are needed; the attacker only needs one legitimately issued but narrowly-scoped API token. Given that CCMenu endpoints are typically embedded in third-party CI dashboard tools, distributing a narrowly-scoped token to an external consumer is a realistic operational pattern, making exploitation low-cost and highly repeatable.

### Recommendation
Remove the overriding `stack` method in `Api::CCMenuController` (and the routes/controller for CCMenu in general) and use the inherited `BaseController#stacks.from_param!(params[:stack_id])` so the lookup is scoped by `current_api_client.stack_id` exactly like `Api::StacksController` does.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a client scoped to one stack cannot read another stack's cc.xml" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "other", name: "repo"), branch: 'main', environment: 'production')
  Task.create!(stack: stack_b, status: 'success') rescue nil # ensure a deploy exists if needed

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped',
    stack: stack_a,
    permissions: ['read:stack']
  )
  request.headers['Authorization'] = ActionController::HttpAuthentication::Basic.encode_credentials(scoped_client.authentication_token, '')

  get :show, params: { stack_id: stack_b.to_param }

  # Binding under test: stack.id == current_api_client.stack_id
  assert_not_equal stack_a.id, stack_b.id
  refute_equal scoped_client.stack_id, stack_b.id
  assert_response :forbidden, "expected the request to be rejected because stack_b is outside the client's stack_id scope, but it was: #{response.status}"
end
```
Running this against current code: the response is `200 OK` with Stack B's deploy XML rendered, proving the scope bypass (the assertion `assert_response :forbidden` fails).
