### Title
Governance execution inside `flash_position` invalidates cached collateral risk parameters while the controller continues using them - (File: `contracts/controller/src/context.rs`)

### Summary
A ready governance operation can be executed from the `flash_position` receiver callback after the controller has cached the collateral’s `SpokeAssetConfig` but before deposits and final solvency checks run. Because `Context::cached_spoke_asset` retains the pre-operation config, the post-callback flow can accept collateral under an LTV that governance has just reduced—or after the asset has been removed from the spoke—and persist debt that would be invalid under current storage. [1](#0-0) [2](#0-1) 

### Finding Description
`process_flash_position` validates caller-selected collateral before invoking the receiver; `require_can_supply` reaches `Context::require_spoke_asset`, which loads and caches the asset’s spoke configuration. [3](#0-2) [4](#0-3) 

The controller then mints debt, forwards it to the receiver, and invokes `execute_flash_position` inside `with_flash_guard`. [5](#0-4) [6](#0-5) 

The flash guard only rejects controller entrypoints that call `require_authorized_caller`; it does not invalidate the invocation-local `Context`, and governance execution is not routed through that user-auth gate. [7](#0-6) [8](#0-7) 

`Governance::execute` is callable with `executor = None` for any ready, non-expired scheduled operation and directly invokes the scheduled target. [9](#0-8) [10](#0-9) 

A scheduled `EditAssetInSpoke` or `RemoveAssetFromSpoke` operation resolves to the controller’s `edit_asset_in_spoke` or `remove_asset_from_spoke` function, allowing the callback to change or delete the same collateral configuration already cached by `Context`. [11](#0-10) 

After the callback, `collect_collateral_deposits` and `process_deposit` run, and `process_deposit` calls `cache.require_spoke_asset`; because the old config remains cached, this succeeds even if current storage now sets the collateral LTV to zero or removes the asset. [12](#0-11) [13](#0-12) 

`strategy_finalize` then performs the post-operation solvency and persistence path using the same stale `Context`. [14](#0-13) 

### Impact Explanation
This is the lending analog of the reported lifetime bug: governance frees or replaces the authoritative collateral configuration during the callback, while the controller continues operating on a stale, no-longer-valid object.

If a ready operation lowers a collateral’s LTV to zero, an attacker can open a flash-funded position in the same transaction that borrows against the obsolete positive LTV and commits the account. If the operation removes the asset, the controller can still book that asset as collateral because `cached_spoke_asset` returns the pre-removal entry. Either case can leave debt backed by collateral that current protocol parameters assign no borrowing power, creating immediate bad debt when the collateral is impaired or illiquid. [15](#0-14) [16](#0-15) 

### Likelihood Explanation
The attack requires a governance operation to already be ready, but execution is explicitly permissionless when `executor` is `None`. An unprivileged attacker can deploy the flash receiver, call `flash_position`, and execute the ready operation inside `execute_flash_position` before supplying the callback proceeds back to the controller. [9](#0-8) [2](#0-1) 

### Recommendation
Invalidate or refresh `Context` risk/configuration entries after every external callback, before deposits and final risk checks. At minimum, reload every touched `HubAssetKey` from storage after `invoke_receiver`, or add a controller configuration nonce incremented by all admin mutators and reject strategy completion if the nonce changes while cached config is in use. Governance mutation calls into the controller can also check the flash-guard flag, though nonce validation is safer because it prevents stale-cache use rather than merely blocking one call path. [15](#0-14) [8](#0-7) 

### Proof of Concept
1. Assume governance has scheduled a ready `AdminOperation::EditAssetInSpoke` that changes collateral `C` from `ltv = 0.8` to `ltv = 0`, or a ready `RemoveAssetFromSpoke` for `(spoke_id, C)`. The resolved operation targets the controller through `edit_asset_in_spoke` or `remove_asset_from_spoke`. [11](#0-10) 
2. Attacker deploys receiver `R` implementing `execute_flash_position`. In that callback, `R` calls `Governance::execute(executor=None, target=controller, function="edit_asset_in_spoke", args=<scheduled args>, predecessor, salt)` or the equivalent `remove_asset_from_spoke` operation. [9](#0-8) 
3. Attacker calls `Controller::flash_position(caller=attacker, account_id=0, spoke_id=S, mode=Multiply, debt=D, amount=A, receiver=R, data=<route>, collaterals=[(C, minimum)], refund_assets=[])`. [17](#0-16) 
4. `validate_collaterals` caches the old `C` configuration before the callback; the controller then mints and forwards `A` units of `D` to `R`. [18](#0-17) 
5. Inside `execute_flash_position`, `R` executes the ready governance operation and then swaps/trades the received `D` into `C` and transfers `C` to the controller. [19](#0-18) 
6. `collect_collateral_deposits` measures the receipt, and `process_deposit` accepts `C` using `Context`’s stale pre-operation `SpokeAssetConfig`. [20](#0-19) [21](#0-20) 
7. `strategy_finalize` evaluates and persists the account with the same stale configuration, so the transaction commits debt that would fail if the post-operation config were reloaded. [16](#0-15)

        &mut self,
        spoke_id: u32,

        self.spoke_assets.set(hub_asset.clone(), loaded.clone());

fn mint_and_forward(
    env: &Env,
    account: &mut Account,
    debt: &HubAssetKey,
    amount: i128,
    receiver: &Address,
    cache: &mut Context,
) -> i128 {
    let controller = env.current_contract_address();
    let before = token::Client::new(env, &debt.asset).balance(&controller);

    let reported = borrow_into_controller(
        env,
        account,
        debt,
        amount,
        false,
        PositionAction::FlashPos,
        cache,
    );

    let measured = balance_delta_since(env, &debt.asset, &controller, before);
    assert_with_error!(env, measured == reported, GenericError::InternalError);
    assert_with_error!(env, measured > 0, GenericError::AmountMustBePositive);

        env,
        &debt.asset,
        &controller,
        receiver,
        measured,
        GenericError::AmountMustBePositive,
    );

    forwarded

    before: &Map<Address, i128>,

    set_flash_loan_ongoing(env, true);

    if !prev {
        set_flash_loan_ongoing(env, false);
