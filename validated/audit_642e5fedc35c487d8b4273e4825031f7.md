### Title
Cross-repository CI status forgery via `StatusHandler` — verified organization is never bound to the repository/commit being written - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` applies GitHub `status` webhook events to **any** `Commit` row in the entire database whose `sha` matches the payload, without ever checking that the payload's `repository` belongs to the stack that owns that commit. This breaks the same trust binding described in the external report: a resource (`RoyaltyVault`) was only checked to exist for the minter, not for whoever the funds are actually routed to at payout time. Here, the webhook signature is verified against the *organization derived from the payload* (`repository_owner`), but the status is *written* against whichever stack(s) happen to own a commit with that raw SHA — the "organization that authenticated" is never bound to "the repository that is written."

### Finding Description
The webhook signature check in `app/controllers/shipit/webhooks_controller.rb` selects the GitHub App/organization whose secret to verify against straight from the untrusted payload: [1](#0-0) [2](#0-1) 

This only proves the request came from *some* GitHub organization/app configured on the Shipit instance (identified by `repository.owner.login`). It says nothing about which specific repository or stack the event is allowed to affect.

For the `push` and `check_suite` events, the base `Handler` class scopes all work to the repository named in the payload via `repository_name`/`stacks`: [3](#0-2) [4](#0-3) [5](#0-4) 

`StatusHandler`, however, never uses `stacks`/`repository_name` at all — it looks up commits **globally by SHA** and writes a status to every match: [6](#0-5) 

That status write is not inert: `Commit#create_status_from_github!` → `add_status` schedules merges and deployable-status hooks whenever the simple state changes to `success`/`pending`: [7](#0-6) 

And `Stack#schedule_merges` / `Commit#schedule_continuous_delivery` can advance the merge queue or continuous deployment for the owning stack once a commit is marked `success`: [8](#0-7) [9](#0-8) 

Because git SHAs are content-addressed and repository-independent, an attacker who legitimately controls (or forks/creates) *any* GitHub organization/repository configured to send webhooks to this Shipit instance can produce a commit whose SHA matches a commit that already exists in a completely unrelated victim stack (e.g., by forking the victim's public repository — a fork shares identical SHAs for unmodified history — or by otherwise engineering an identical commit object). The attacker then fires (or has GitHub naturally fire) a genuinely signed `status` webhook for their own org/repo with that shared SHA and `state: success`. `verify_signature` validates the signature against the attacker's own organization successfully (`GithubApp#verify_webhook_signature`, `lib/shipit/github_app.rb:76-83`) — the request is legitimately signed — but `StatusHandler#process` then writes a `success` status onto the victim's identical-SHA commit in the victim's stack, with no verification that the payload's `repository` field corresponds to that stack.

### Impact Explanation
A forged `success`/passing CI status on a victim's commit can:
- Satisfy `ci.require` / merge-queue required-status checks (`Shipit::DeploySpec#required_statuses`, `merge_request_required_statuses`), enabling `MergeRequest`/`ProcessMergeRequestsJob` to merge a pull request in the victim stack that would otherwise be blocked on CI.
- Trigger `stack.schedule_merges` and, if `continuous_deployment` is enabled, `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob`, resulting in an **unauthorized deploy** of a commit whose real CI never passed.

This matches the required "High/Critical" impact bar: an unauthorized deploy or merge in a repository the attacker does not control, achieved purely by exploiting a missing repository-scoping check — no `ApiClient` token, session, or leaked secret is required beyond the attacker's own legitimately-configured GitHub org.

### Likelihood Explanation
Exploitability depends on being able to produce a SHA collision with a target commit, which is trivial when the victim repository is public (fork it — the shared history has identical SHAs) or when the attacker can otherwise construct an identical git commit object (same tree, parents, author/committer, and timestamps) targeting a specific known commit. In a multi-tenant Shipit deployment (multiple GitHub orgs configured under `Shipit.github`, as shown in the multi-org secrets fixtures), any onboarded-but-otherwise-unprivileged organization can reach this path just by pushing/tagging a commit-status event on a SHA they choose in their own repo.

### Recommendation
Scope `StatusHandler#process` to the stack(s) belonging to the repository identified in the payload, mirroring `PushHandler`/`CheckSuiteHandler`'s use of `stacks`/`repository_name`, e.g. restrict the `Commit.where(sha: params.sha)` lookup to `stacks.flat_map(&:commits)` (or join through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) instead of matching by bare SHA across the entire installation.

### Proof of Concept
1. Attacker's org `Evil` is configured in Shipit's multi-tenant `Shipit.github` config (legitimate onboarding, e.g. `test/dummy/config/secrets_double_github_app.yml`-style setup) and has a real `webhook_secret`.
2. Attacker forks victim's public repository `Victim/app` into `Evil/app-fork`, inheriting identical commit SHAs for existing history, including commit `abc123...` that is pending CI in `Victim/app`'s Shipit stack.
3. Attacker uses GitHub's real Statuses API (write access to their own fork) to post a `success` status for SHA `abc123...` on `Evil/app-fork`.
4. GitHub sends a genuinely-signed `status` webhook to Shipit's `/webhooks` endpoint with `repository.full_name = "Evil/app-fork"`, `sha = "abc123..."`, `state = "success"`.
5. `WebhooksController#verify_signature` validates the signature against `Evil`'s webhook secret and passes.
6. `StatusHandler#process` executes `Commit.where(sha: "abc123...")`, which matches the commit in `Victim/app`'s stack too, and calls `create_status_from_github!`, marking it `success` and triggering `schedule_merges` / continuous delivery for `Victim/app`.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
