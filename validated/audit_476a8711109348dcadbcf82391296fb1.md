### Title
Webhook signature verified against one GitHub organization, but events are applied without confirming the target commit/repository belongs to that organization - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
Shipit's multi-tenant GitHub App configuration lets each GitHub organization have its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to verify the inbound signature against solely from the payload's own `repository.owner.login` (or `organization.login`) field [2](#0-1) . Nothing downstream re-confirms that the record actually mutated by the event handler belongs to that same organization. `Webhooks::Handlers::StatusHandler` looks up the commit to update purely `by sha`, with no repository/organization scoping at all [3](#0-2) , and the generic `Handler#stacks` helper resolves the target repository from a separate `repository.full_name` field that is never cross-checked against the `repository.owner.login` used for signature verification [4](#0-3) .

### Finding Description
The equality that should hold is: **organization whose secret authenticated the request == organization that owns the repository/commit being written**. Shipit breaks this binding:

1. `WebhooksController#repository_owner` extracts the authenticating organization from attacker-controlled JSON fields (`repository.owner.login` or `organization.login`) [5](#0-4) .
2. `verify_signature` fetches `Shipit.github(organization: repository_owner)` and checks the HMAC using that organization's own configured `webhook_secret` [6](#0-5) , ` [7](#0-6) `.
3. Once the signature check passes, `Shipit::Webhooks.for_event(event)` dispatches the full, attacker-supplied JSON body to handlers [8](#0-7) .
4. `StatusHandler#process` updates *any* `Commit` whose `sha` matches the payload, with zero scoping to the organization/repository that was actually authenticated [3](#0-2) .
5. Other handlers (push, pull_request, check_suite) use `Handler#repository_name`/`#stacks`, which reads `payload.dig('repository','full_name')` — a field completely independent from the `repository.owner.login` used in step 1 — to resolve the target `Stack` [4](#0-3) .

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name`/`sha` (used to pick the object mutated) are independent, attacker-controlled JSON fields, any tenant organization configured in Shipit — i.e., any org with its own legitimate `webhook_secret` in `Shipit.github_organizations` — can forge events that are cryptographically valid for its own secret but that mutate state belonging to a *different* organization's stacks or commits.

### Impact Explanation
An organization onboarded to a multi-tenant Shipit instance can use its own valid webhook secret to forge a `status` event referencing a commit `sha` that actually belongs to a different organization's stack, injecting a fabricated commit status (e.g. `state: success`) for that foreign commit. Because Shipit stacks use commit CI status to gate `continuous_deployment` (evidenced by the dedicated `deployable_status`/`commit_status` hook events in `Hook::EVENTS` [9](#0-8) ), this can move a foreign stack's commit into a "deployable" state and trigger an unauthorized deploy — without ever possessing that other organization's webhook secret, API client token, or session. This matches the Critical impact category of "an unauthorized deploy."

### Likelihood Explanation
Requires only that the attacker controls (or has compromised) one legitimate, low-privilege webhook secret for any single organization already configured in the Shipit instance — no session, API token, or elevated GitHub permissions on the victim organization are needed. Because `StatusHandler` performs no organization/repository scoping whatsoever, exploitation is a single crafted HTTP POST once any one organization's secret is known.

### Recommendation
- Require handlers to verify that the resource being mutated (`Commit#stack`, `Repository`) actually belongs to the same organization that was used to select/verify the webhook secret (`repository_owner` from `WebhooksController`), rejecting/dropping events where they diverge.
- In `StatusHandler`, scope the `Commit` lookup by the stack's repository/organization derived from the verified payload, not solely by `sha`.
- In `Handler#stacks`, cross-check `repository.full_name`'s owner against the organization used for signature verification before resolving stacks.

### Proof of Concept
1. Configure/compromise a valid webhook secret for organization `attacker-org`, already a Shipit tenant (`Shipit.github_organizations` includes it, with its own `webhook_secret`).
2. Identify the `sha` of a commit belonging to `target-org`'s stack, which has `continuous_deployment` enabled and gates deploys on a passing `ci/tests` status.
3. POST to `/webhooks` with `X-Github-Event: status` and an `X-Hub-Signature` computed with `attacker-org`'s secret over the body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}},
  "sha": "<target-org commit sha>",
  "state": "success",
  "context": "ci/tests"
}
```
4. `verify_signature` resolves `repository_owner` = `attacker-org`, verifies successfully with `attacker-org`'s secret [6](#0-5) .
5. `StatusHandler#process` finds the commit purely by `sha` (belonging to `target-org`) and writes the forged "success" status to it [3](#0-2) , potentially unblocking an unauthorized deploy of `target-org`'s stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"

    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
