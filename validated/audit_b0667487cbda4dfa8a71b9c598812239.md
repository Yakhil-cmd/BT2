### Title
Webhook signature verification is keyed on `repository.owner.login` while handlers act on unrelated payload fields (`repository.full_name`, `organization.login`, `team.id`) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to check the HMAC against using a field taken from the *unverified* JSON body (`repository.owner.login`, falling back to `organization.login`). Once that check passes, the individual `Shipit::Webhooks::Handlers` act on **other, independent** fields of the same payload (`repository.full_name`, `organization.login`, `team.id`) that were never tied to the key used for verification. In a Shipit instance configured with multiple GitHub organizations (as shown in `config/secrets.development.shopify.yml`), an attacker who legitimately controls one onboarded organization's GitHub App/webhook secret can sign a payload with their own secret while pointing the "acted upon" fields at a different organization's team or repository.

### Finding Description
`verify_signature` picks the verification key like this: [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
```
where [2](#0-1) 

`repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')` - both fully attacker-controlled, unauthenticated fields of the raw JSON body that is being verified.

For the `membership` event, `Shipit::Webhooks::Handlers::MembershipHandler` does the real work using **different** fields of the same payload: [3](#0-2) 

`find_or_create_team!` looks the `Team` up **by `params.team.id` (a GitHub team id)**, not by organization, and only sets `organization` when the record doesn't already exist. If the targeted `Team` already exists in Shipit's DB (which is the normal case for any team referenced in `Shipit.github_teams`, since those are pre-created via `Team.find_or_create_by_handle`), the `organization` field of the payload is irrelevant to which record gets modified.

`Shipit.github_teams` is exactly the set of teams used to gate application access: [4](#0-3) [5](#0-4) 

Because the payload's `repository.owner.login` (used only for signature routing) and `organization.login`/`team.id` (used only for the actual DB mutation) are never cross-checked, an attacker who is an admin of any one GitHub organization onboarded into this shared Shipit instance - and therefore knows that organization's `webhook_secret` - can:

1. Craft a `membership` webhook payload with `repository: { owner: { login: "attacker-org" } }` (an extra field GitHub itself never sends for `membership` events, but nothing strips it), `action: "added"`, `team: { id: <victim_team_github_id>, ... }`, `member: { login: "<attacker_github_login>" }`.
2. Sign it with `attacker-org`'s known `webhook_secret`.
3. POST it to the shared `/github/webhooks` endpoint with `X-Github-Event: membership`.
4. `verify_signature` resolves `repository_owner` to `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the signature checks out.
5. `MembershipHandler#process` then finds the pre-existing privileged `Team` record by `github_id == params.team.id` (a team that belongs to a *completely different* organization, e.g. the one referenced in `Shipit.github_teams`), creates/finds a `User` for the attacker's own login, and calls `team.add_member(member)`.
6. The attacker's Shipit `User` is now a member of the privileged `Team`, and `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) returns `true` - granting access to the whole Shipit UI/dashboard as if they were a legitimate member of the restricted organization.

The same class of decoupling exists for repository-scoped events: `Handler#stacks` resolves the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')`, a field distinct from `repository.owner.login` used for signature routing: [6](#0-5) 

So a `push` event signed with `attacker-org`'s secret but carrying `repository.full_name = "victim-org/victim-repo"` will pass verification and then invoke `stack.sync_github(expected_head_sha: params.after)` on the victim's real, unrelated stack: [7](#0-6) 

### Impact Explanation
The concrete, reachable path is the `membership` handler: it lets an attacker who legitimately controls one onboarded org's webhook secret add an arbitrary GitHub login (their own) to a `Team` record used by `Shipit.github_teams` for the entire application's access-control gate (`app/controllers/concerns/shipit/authentication.rb`). This is exactly the "escalation into `Shipit.github_teams` authorization" High-impact category: it is an authentication-bypass primitive that lets an outside org admin grant themselves access to a Shipit deployment they have no legitimate right to use, without ever needing a Shipit session, API token, or GitHub org membership in the target organization.

The `push`/pull_request analogs additionally let the same attacker force syncing of arbitrary commit SHAs into another organization's tracked stack (potentially interacting with continuous-deployment logic in `app/models/shipit/stack.rb`) and archive/unarchive review stacks belonging to a repository they do not own, compounding the impact toward unauthorized state changes on repositories outside the attacker's control.

### Likelihood Explanation
Exploitation requires the attacker to be an administrator of at least one GitHub organization that is legitimately onboarded into the same shared/multi-tenant Shipit instance (a supported configuration, as shown by `config/secrets.development.shopify.yml` listing multiple orgs each with their own `webhook_secret`). Such an attacker only needs to know their own org's webhook secret (which they control) and the numeric GitHub `team.id` of the target privileged team - no interception of the victim's credentials, no `ApiClient` token, and no prior access to the victim organization is required. This is realistic for any multi-tenant Shipit deployment shared across independently-administered GitHub organizations.

### Recommendation
Bind webhook signature verification to the exact same field that handlers subsequently act on, per event type, rather than deriving the routing key from a different/optional sub-object. Concretely:
- For `membership` events, verify the signature using the organization whose GitHub App installation actually delivered it (e.g. compare against `X-GitHub-Hook-Installation-Target-ID`/`installation.id` if available, or require that `organization.login` used for verification is the *same* value later used to look up/create the `Team`, and reject if a spurious `repository` object is present).
- For repository events, verify against `repository.full_name`'s owner (derived consistently, e.g. by splitting `full_name`) rather than a separate `repository.owner.login` field, and reject payloads where the two are inconsistent.
- More generally, treat any field read before signature verification as untrusted routing metadata only, and re-validate after verification that all fields used by the handler are consistent with the organization/repository whose secret validated the signature.

### Proof of Concept
Not runnable without two configured GitHub organizations in `secrets.yml` and knowledge of the target `Team`'s GitHub `team.id`, but the exploit sequence is:

```

# Victim Shipit instance also has "victim-org" onboarded, and
# Shipit.github_teams references a Team whose github_id = 999 (victim-org/admins).

payload = {
  "action": "added",
  "team": { "id": 999, "name": "Admins", "slug": "admins", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker_github_login" },
  "repository": { "owner": { "login": "attacker-org" } }   # <-- spoofs signature routing only
}

signature = "sha1=" + HMAC_SHA1(attacker_org_webhook_secret, payload.to_json)

POST /github/webhooks
X-Github-Event: membership
X-Hub-Signature: <signature>
Body: payload.to_json

# verify_signature uses repository.owner.login == "attacker-org" -> passes.
# MembershipHandler finds Team by github_id=999 (belongs to victim-org),
# creates/finds User("attacker_github_login"), and adds them as a member.
# Attacker now satisfies User#authorized? via Shipit.github_teams.

      github_app = Shipit.github(organization: repository_owner)

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
