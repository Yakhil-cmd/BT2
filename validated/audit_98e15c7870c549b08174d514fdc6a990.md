### Title
Unbounded in-memory scan of unstable units on every `in data feed` check allows CPU-exhaustion DoS via crafted AA/oscript data-feed conditions - ([File: data_feeds.js])

### Summary
`dataFeedExists()` in `data_feeds.js` performs a full, unindexed scan of *all* currently unstable units/messages in memory (`storage.assocUnstableMessages`) every time an `in data feed` condition is evaluated with `bAA=true`. This is directly analogous to CVE-2018-14648: a search operation whose cost is proportional to the total size of a growable, attacker-influenced dataset rather than to the specificity of the query, with no index/early-termination bound on the number of times it can be invoked per validated unit. [1](#0-0) 

### Finding Description
`dataFeedExists(arrAddresses, feed_name, relation, value, min_mci, max_mci, bAA, handleResult)` is called from both `definition.js` (address-definition `in data feed` authentifier evaluation) and `formula/evaluation.js` (`in_data_feed()`/`data_feed()` AA oscript functions) whenever `bAA` is true (i.e. during AA trigger/response processing): [2](#0-1) [3](#0-2) 

When `bAA` is true, before falling back to the indexed key-value store lookup, the function iterates over **every unit currently in `storage.assocUnstableMessages`** (i.e. the entire unstable/unconfirmed portion of the DAG known to the node) and, for each one, iterates over **all of that unit's messages**, doing string/number comparisons against the target `feed_name`/`value`: [4](#0-3) 

This loop has no early cutoff besides `if (bFound) break;` *after* a match is found — if no match exists (the common/attacker-chosen case), it always walks the complete unstable-unit set. There is no per-feed index, no cap on the number of unstable units scanned, and no cost accounting for this operation in the AA complexity/`count_ops` model — `formula/validation.js`'s `data_feed`/`in_data_feed` cases only add a small constant complexity for the call itself, not anything proportional to the actual runtime cost of the in-memory scan.

An attacker can:
1. Post many low-cost units so that `storage.assocUnstableMessages` is large (this is a normal, permissionless operation — anyone can post units that stay unstable for a while).
2. As an AA trigger sender, send a trigger to an AA whose formula/definition contains multiple `in data feed`/`data_feed()` calls that intentionally miss (so the "no match" full-scan path is always taken). The number of such calls per AA execution is only bounded by `MAX_COMPLEXITY`/`MAX_OPS` (a fixed op-count budget), not by the true CPU cost of each op, since each call is charged a flat complexity cost regardless of the size of `assocUnstableMessages` at evaluation time.
3. Every full node that processes/validates this trigger and every witness/hub must perform the same expensive scan, multiplied by the number of `in data feed` calls in the formula — producing CPU consumption disproportionate to the cost the attacker paid, on every validating node simultaneously.

This mirrors the CVE-2018-14648 bug class exactly: a search routine invoked by an unauthenticated/low-privilege actor (crafted LDAP search vs. crafted AA data-feed condition) whose complexity scales with a large, server-side dataset rather than being bounded/indexed, causing excessive CPU and a denial-of-service against validating nodes.

### Impact Explanation
Because AA trigger validation is mandatory for every full node/witness to determine AA response and unit validity, a computation-heavy trigger unit can be broadcast cheaply and force every node in the network to spend disproportionate CPU processing it. If enough such triggers are sent in a burst (which is easy since sending a trigger unit is cheap and the formula's static complexity budget doesn't reflect the real in-memory-scan cost), nodes can fall behind on validating new units — leading to network-wide inability to confirm new units in a timely manner, which is one of the explicitly accepted impact categories (a network unable to confirm new units).

### Likelihood Explanation
Likelihood is high in periods of network congestion (when `assocUnstableMessages` is naturally large) and moderate otherwise, since an attacker can inflate the unstable set themselves by posting many low-value units before sending the exploiting trigger. No special privileges, no cosigning, no hub/peer compromise, and no light-client/network trust assumptions are needed — only the ability to post units and send an AA trigger, both of which are core permissionless operations of ocore.

### Recommendation
- Replace the linear scan over `storage.assocUnstableMessages` with an indexed lookup structure keyed by `(address, feed_name)` (or similar) that is maintained incrementally as units become unstable/stable, so `dataFeedExists`/`readDataFeedValue`'s in-memory path costs O(matches) rather than O(all unstable units × messages).
- Charge AA formula complexity for `in data feed`/`data_feed()` proportionally to the actual expected cost of the in-memory scan (e.g., based on current size of `assocUnstableMessages`), or cap the number of unstable units/messages inspected per call, returning a deterministic "not found" (or an error) once the cap is hit.
- Consider making the "not found" (full-scan, no match) case at least as cheap as the "found" case by maintaining a name-indexed cache instead of iterating the raw associative object of all unstable units.

### Proof of Concept
1. Attacker posts a stream of units to inflate `storage.assocUnstableMessages` (e.g. many payments with data-feed-unrelated payloads) so many units remain in the unstable window.
2. Attacker deploys/uses an AA whose formula body contains repeated `data_feed[oracles=X, feed_name="nonexistent_feed_1"]`, `..._2`, ... calls (up to the `MAX_COMPLEXITY`/`MAX_OPS` budget) that are guaranteed to miss (feed names chosen so no matching `data_feed` message exists).
3. Attacker sends one (or a burst of) low-value trigger unit(s) to this AA.
4. Every validating node must execute `dataFeedExists`/`readDataFeedValue` with `bAA=true` for each call, each one performing a full O(#unstable units × #messages) scan — multiplying attacker-cheap input into disproportionate CPU work across the network, consistent with the excessive-CPU-consumption DoS class described in CVE-2018-14648.

*Note: I was unable to fully confirm the exact numeric values of `constants.MAX_COMPLEXITY`/`MAX_OPS` (the grep for constants.js returned matches but the file content itself was not retrieved before the tool budget ran out), so I cannot state the precise upper bound on the number of `in data feed` calls per AA execution — only that it is a fixed op-count/complexity budget unrelated to the real cost of the in-memory scan.*

					return;

					return;

				if (typeof value === 'string' && typeof feed_value === 'string') { // only one string looks like a number
					if (relationSatisfied(feed_value, value))
