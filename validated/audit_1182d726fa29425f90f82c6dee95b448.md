### Title
`socialize-debt` writes down bad debt using a stale, un-accrued interest index while sibling debt functions always accrue first - (File: `mainnet/contracts/vault/v0-vault-stx.clar`)

### Summary
Every state-mutating debt function in the vault contracts (`system-borrow`, `system-repay`) begins by calling `(try! (accrue))` to roll the interest index forward to the present block before using it. `socialize-debt`, which the market's liquidation flow calls to write off bad debt against the supplier pool, is the one exception: it reads `(var-get index)` directly without first calling `accrue`, and uses that stale index to compute `debt-reduction` and the proportional `lindex` write-down that all suppliers absorb.

### Finding Description
In `v0-vault-stx.clar` (and identically in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`), the borrow/repay entry points explicitly re-accrue interest before computing amounts: [1](#0-0) 

`system-repay` does the same: [2](#0-1) 

`socialize-debt`, however, never calls `accrue`. It uses the raw `(var-get index)` from before the current block's interest has been rolled in to compute how much scaled debt/principal to remove and how much the liquidity index (`lindex`) - the value every zToken supplier's redemption price is derived from - must be written down: [3](#0-2) 

Market.clar's index/interest state is also cached per-block: the first caller to touch a vault in a given block populates `index-cache-`/`index-cache` with the freshly accrued `{index, lindex}`, and every subsequent caller in the same block/timestamp simply reads that cache instead of re-accruing: [4](#0-3) 

This is structurally the same bug class as the StakeWise `EthGenesisVault.updateState()` finding: a shared accounting variable (`totalAssetsDelta`/`legacyPrincipal` there, `index`/`total-assets` here) that should reflect debt/interest *at the moment of the write-down* is instead computed from a value that can be stale relative to what other participants in the same block already saw or will see, because the write happens outside the normal accrual gate that every other debt-mutating path uses.

Concretely: if a borrower repays or borrows against the same vault earlier in the block (going through `accrue`, which advances `index`/`lindex` and mints treasury shares off the accrued interest), and the market's liquidation logic then calls `vault-socialize-debt` for a defaulted position in a *later* transaction of the same block without an intervening `accrue` call, `debt-reduction` is computed off whichever `index` value happens to be sitting in the var at that point rather than the index that matches the actual outstanding scaled debt on the defaulted position. Because `principal-reduction`/`debt-reduction` and the proportional `lindex` markdown are derived from that possibly-stale `index`, the write-off can under- or over-state the bad debt relative to the position's true accrued balance, and the discrepancy is baked permanently into `lindex` (and thus into every zToken's exchange rate) since there is no reconciliation step afterward.

### Impact Explanation
`lindex` directly prices every zToken redemption. A write-down computed from a stale `index` either:
- Under-writes the bad debt, leaving residual phantom debt priced into `total-debt()`/`total-assets()` that legitimate suppliers who redeem before the shortfall is otherwise discovered/repriced effectively "gain" relative to suppliers who redeem after, or
- Over-writes the bad debt, socializing more loss onto all current suppliers than the defaulted position actually owed.

Either direction is a mispricing of unclaimed yield/principal across the shared supplier pool caused by a code-level accrual-ordering gap rather than deliberate protocol economics, landing in the **temporary freezing of funds / theft of unclaimed yield** impact category depending on which suppliers redeem before vs. after the mis-write is effectively corrected by the next `accrue`.

### Likelihood Explanation
Likelihood is bounded by whether `market.clar`'s liquidation path guarantees an `accrue`/`accrue-and-cache` call on the vault immediately before invoking `vault-socialize-debt` in every code path. I was not able to fully verify this ordering in `mainnet/contracts/market/v0-4-market.clar` within the available search results - the tool budget was exhausted before I could pull and confirm the exact liquidation function body around the `socialize-debt` call site. Given `check-caller-auth` restricts direct calls to `socialize-debt` to the market contract, exploitation requires either (a) the market's liquidation flow calling it without a fresh accrual, or (b) a sequence of transactions within the same `stacks-block-time` where one transaction's `accrue`-driven state change is not reflected before `socialize-debt` executes.

### Recommendation
Have `socialize-debt` call `(try! (accrue))` (or reuse `market.clar`'s `accrue-and-cache` result) at its start, exactly like `system-borrow` and `system-repay` do, so the `index`/`lindex` used for the write-down always reflects interest accrued up to the current `stacks-block-time` before any bad-debt socialization is computed.

### Proof of Concept
Conceptual sequence (STX vault):
1. Block N: a borrower calls `system-borrow`/`system-repay` on `vault-stx`, which calls `accrue`, advancing `var-get index` from `idx0` to `idx1` and minting treasury shares for the interest already accrued.
2. Later in block N (or in a follow-up call where the market's liquidation path does not itself force a fresh `accrue` on this vault), a liquidation triggers `vault-socialize-debt` for a defaulted borrower whose position's true outstanding debt should be evaluated at `idx1`.
3. `socialize-debt` reads `(var-get index)` - if any code path allows this to run without accrual (or bypasses the cache primed in step 1's transaction, per `market.clar`'s `index-cache-`), the `debt-reduction`/`principal-reduction`/`new-lindex` computed at lines 946-968 of `v0-vault-stx.clar` no longer match the position's actual `idx1`-priced debt, producing a `lindex` that is inconsistent with the true bad-debt amount and permanently skewing the zToken exchange rate for all current suppliers relative to what it should be.

Note: because I could not confirm within the remaining budget whether `market.clar`'s liquidation function unconditionally calls `accrue-and-cache` immediately before every `vault-socialize-debt` invocation, this should be treated as a code-pattern finding (missing defensive accrual in `socialize-debt` itself, unlike every other debt-mutating vault function) requiring confirmation of the market-side call ordering before being escalated with full confidence.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
