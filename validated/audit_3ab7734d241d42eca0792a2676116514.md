### Title
Unauthenticated access to `/events` pubsub stream exposes live task/deploy broadcasts - ([File: config/routes.rb])

### Summary
The engine mounts `Pubsubstub::StreamAction.new` at `/events` as a raw Rack endpoint, completely outside the Rails controller filter chain that enforces `force_github_authentication`. A code comment in `github_authentication_controller.rb` states that `/events` "leverage[s] `UserRequiredMiddleware`" to gate access, but no such middleware is ever registered in `lib/shipit/engine.rb` or anywhere else in this repo, so the endpoint is unauthenticated by default.

### Finding Description
The broken binding is: the codebase assumes `mounted_at("/events") => protected_by(UserRequiredMiddleware)`, but in reality `mounted_at("/events") => protected_by(nil)`.

- `config/routes.rb` line 9: `mount Pubsubstub::StreamAction.new, at: "/events", as: :events`. This is a plain Rack app mount, not a controller action, so Rails controller `before_action`s (like `force_github_authentication` defined in `app/controllers/concerns/shipit/authentication.rb`) never run against it — that filter is only wired into `ShipitController` subclasses via `include Shipit::Authentication`.
- `app/controllers/shipit/github_authentication_controller.rb` (lines 15-18) explicitly documents the intended protection: "We need to set this so that the /events and /sidekiq endpoint which leverage `UserRequiredMiddleware` will recognize the user is authenticated." Searching the entire repo for `UserRequiredMiddleware` turns up exactly one match — this comment. The middleware is never defined or inserted via `app.middleware.use` in `lib/shipit/engine.rb` (which only registers `OmniAuth::Builder` and, conditionally, `Shipit::SameSiteCookieMiddleware`).
- Because no middleware or controller filter guards this mount, any unauthenticated attacker can send `GET /events?channels=stack.<id>` (or `task.<id>`, per whatever channel naming the app uses for `Pubsubstub.publish`) and receive the live SSE/long-poll stream for that channel, for any stack ID, without a session, API token, or GitHub credentials.
- None of the existing guards apply here: `force_github_authentication` is never invoked (wrong layer — controller vs. Rack mount); there is no `verify_signature`/webhook check (irrelevant, this isn't the webhook path); no `ExplicitParameters` schema restricts `channels`; no scope filtering restricts which channel names a subscriber may request.

### Impact Explanation
An unauthenticated party can subscribe to `stack.<id>` (or other) channels and receive live task status/deploy progress broadcasts for arbitrary stacks/repositories hosted on the Shipit instance — this is an unauthenticated read of stack state and task/deploy streams, matching the **High** severity category explicitly listed in the rules ("unauthenticated read of stack state, task streams or deploy output"). It is repeatable against every stack ID and requires no interaction with GitHub at all; the attacker only needs network access to the Shipit host.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only to know or guess a stack ID (stack IDs/full names are often discoverable, e.g., via the `stacks` index if it's also under-protected, or simply guessable/enumerable) and send a single unauthenticated HTTP GET. No Shipit secrets, GitHub credentials, or session are required, matching the "unprivileged internet attacker" threat model exactly. This is highly feasible and trivially repeatable.

### Recommendation
Register an actual authentication middleware (the missing `UserRequiredMiddleware` referenced in the comment) in `lib/shipit/engine.rb`, inserted before the `/events` mount, that checks `session[:user_id]`/`session[:authenticated]` and rejects unauthenticated requests with 401/403 before they reach `Pubsubstub::StreamAction`. Alternatively, replace the raw mount with a controller action that includes `Shipit::Authentication` and performs `force_github_authentication`, and further validate that the authenticated user is authorized to view the specific stack referenced by the `channels` parameter before allowing a subscription.

### Proof of Concept
Add to `test/` (e.g., `test/integration/events_stream_test.rb`):
```ruby
require 'test_helper'

module Shipit
  class EventsStreamTest < ActionDispatch::IntegrationTest
    test "unauthenticated request to /events is rejected" do
      stack = shipit_stacks(:shipit)

      # No session set, no login performed
      get "/events", params: { channels: "stack.#{stack.id}" }

      # Binding under test: mounted_at("/events") should equal protected_by(some_auth_check)
      # Currently this assertion fails because the mount has no auth guard.
      assert_response :unauthorized # or :forbidden / :redirect to github_authentication_path
    end
  end
end
```
Running this against the current code demonstrates the request succeeds (200/streaming) instead of being rejected, proving the mount is unauthenticated. A full end-to-end proof would additionally assert that a `Pubsubstub.publish(channel: "stack.#{stack.id}", ...)` fired from another test thread/process is received on this unauthenticated connection.
