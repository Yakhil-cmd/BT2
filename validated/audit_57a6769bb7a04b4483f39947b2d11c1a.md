## Title
Webhook signature verification is keyed to the wrong organization, letting an attacker forge cross-repository CI status/push events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook against using `repository_owner`, a value read directly out of the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`). If that organization's `Shipit.github(organization: ...)` config has no `webhook_secret` configured — an explicitly documented, optional setting (`docs/setup.md` line 30: "Webhook secret (optional)") — `verify_webhook_signature` short-circuits to `true` for *any* payload. The event is then dispatched to handlers that resolve the actually-affected data from a *different* field of the same attacker-controlled body (e.g. `repository.full_name` for push, or nothing at all — a bare `sha` — for status events). The organization whose identity is "authenticated" (or rather, exempted from authentication) and the repository/commit actually acted upon are two different bindings that are never cross-checked. ### Finding Description
`verify_signature` computes `repository_owner` from the request body itself, then fetches that organization's `GithubApp`/`GithubAppOAuth` config and calls `verify_webhook_signature`: [4](#0-3) 

`verify_webhook_signature` in `lib/shipit/github_app.rb` explicitly returns `true` when no `webhook_secret` is configured for that organization:
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [3](#0-2) 

This is a realistic configuration: the setup docs mark `webhook_secret` as optional, and the test fixture for a multi-organization deployment even shows two orgs both configured with a blank secret (`webhook_secret: # nil`): [5](#0-4) 

Once verification is bypassed via that no-secret organization, `WebhooksController#create` dispatches the raw JSON to handlers with no further authentication: [6](#0-5) 

The handlers resolve the entity to act on from a field that is completely independent of `repository_owner`:
- `Handler#stacks` resolves by `repository.full_name`, not `repository.owner.login`: [7](#0-6) 
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for whichever stack matches that attacker-chosen `full_name`: [8](#0-7) 
- `StatusHandler#process` is worse: it doesn't even reference the repository/organization at all — it looks up commits **globally by SHA** across the entire Shipit installation and attaches an arbitrary status to them: [9](#0-8) 

So the equality the deployment implicitly relies on — "organization whose credential authenticated the request" == "repository/commit that the event body causes an action on" — does not hold. The signature (or its explicit absence) is bound only to `repository.owner.login`/`organization.login`; the actual mutation is bound to `repository.full_name` (push, membership, pull_request handlers) or to nothing but a bare commit `sha` (status handler), both attacker-controlled and never reconciled with the authenticated organization.

### Impact Explanation
An external, unauthenticated attacker who knows (a) the login of any GitHub organization configured on the target Shipit instance without a `webhook_secret`, and (b) the SHA of a commit on a target stack (visible on public GitHub) or the `full_name` of a target repository, can POST an unsigned `status` or `push` webhook to `/webhooks`:
- `status` event: forge a `success` status with `context` matching the target stack's `ci.require`/`ci.blocking` context for a real commit SHA, bypassing CI gating and enabling an unauthorized deploy of that commit — a Critical impact (unauthorized deploy).
- `push`/`membership`/`pull_request` events: force `GithubSyncJob` execution, archive/unarchive review stacks, or manipulate team membership on a repository/stack that has nothing to do with the "authenticating" organization.

This crosses the "unauthorized deploy" / cross-repository-write boundary defined as Critical impact, without requiring any Shipit session, API token, or GitHub credential.

### Likelihood Explanation
Requires only that the deployment configures at least one GitHub organization without `webhook_secret` (explicitly supported/documented) in a multi-organization Shipit instance — a plausible and demonstrated (via the repo's own multi-org fixture) configuration. No privileged access, tokens, or social engineering are needed; only knowledge of a public commit SHA or repository name.

### Recommendation
Bind the authentication decision to the same identity used for the mutation: verify the webhook signature using the secret associated with the organization that owns the resource the handler will actually act on (`repository.full_name`'s owner, or the Stack's configured GitHub App), not a value the payload itself supplies independently. Additionally, `StatusHandler` should scope its `Commit` lookup by the repository/organization derived from the verified request, not by a bare, globally-unique SHA. Do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank for events that mutate cross-tenant state; either require a secret for all configured organizations or scope handlers strictly to the repository whose credentials were verified.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `victim-org` (has real stacks, may or may not have a webhook secret) and `attacker-org` (no `webhook_secret`, as allowed by docs).
2. Find a public commit SHA on a `victim-org` repository stack that is currently blocked from deploy by `ci.require: ["ci/circleci"]`.
3. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/circleci",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
No `X-Hub-Signature` header is required because `attacker-org` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally.
4. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` (global, unscoped) and calls `commit.create_status_from_github!(params)`, marking the victim commit's CI as passing, unblocking a deploy the attacker never had access to trigger legitimately.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
