### Title
Cross-repository status webhook poisoning via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: app/models/shipit/commit.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits purely by SHA, with no filter on the webhook's originating repository, then calls `create_status_from_github!` on every matching row across all stacks. Because the `commits` table is only indexed on `(stack_id, sha)` and not globally unique, an attacker who owns any repository tracked by Shipit can push (or already share, via fork ancestry) a commit whose SHA collides with a commit that also exists in a victim stack, then legitimately set a GitHub status on their own repo/commit to have Shipit record a fabricated "success" `Status` against the victim's commit row, flipping `commit.deployable?` to `true`.

### Finding Description
Binding claimed to hold: `Status.create!` for a given `commit` must satisfy `payload.dig('repository','full_name') == commit.stack.repository.full_name`. Actual code never enforces this.

`StatusHandler#process` is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Unlike other handlers, `StatusHandler` does not use the base class's `stacks`/`repository_name` scoping helper at all: [2](#0-1) 

`Commit.where(sha: params.sha)` matches **every** commit row in the entire Shipit installation with that SHA, regardless of which stack/repository it belongs to. The only DB constraint is a composite, non-unique index on `(stack_id, sha)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), which does not prevent two different stacks (i.e., two different GitHub repositories) from each having a `Commit` row with an identical SHA — this naturally happens whenever one repository is a fork of another, since all commits shared before the fork point (and any cherry-picked/identical commits after) have identical, content-addressed SHAs.

When a matching `Commit` is found, `create_status_from_github!` creates a `Status` scoped to `commit.stack` (the commit's own stack), as seen in `add_status`'s use of `stack:` (`self.stack`), not the webhook payload's repository: [3](#0-2) 

`Commit#deployable?` then trusts the aggregate status for the commit with no regard to which repository actually produced it: [4](#0-3) 

Exploit flow:
1. Attacker forks (or otherwise obtains) a repository that is tracked by Shipit and shares commit ancestry/SHA with the victim stack's repository — a routine and unavoidable GitHub property for forks.
2. Attacker's own repository has a legitimately configured Shipit webhook (its own valid `webhook_secret`), so GitHub signs and delivers a real `status` event when the attacker sets a commit status on their own repo/commit (which they can do with ordinary GitHub API access to their own repository — no Shipit secret needed).
3. `WebhooksController` validates the signature against the attacker's own hook and passes signature/`drop_unhandled_event` checks (the request genuinely originates from GitHub for the attacker's repo) — these guards check *authenticity of the sender*, not *which commit/repo the payload's SHA is allowed to affect*.
4. `StatusHandler#process` runs `Commit.where(sha: <shared sha>)`, finds the victim's `Commit` row too, and calls `create_status_from_github!`, writing a `success` `Status` scoped to the victim's stack.
5. The victim commit's `deployable?` now returns `true` without any status ever having been produced by the victim's own CI/repository.
6. An operator (legitimately authorized via `require_permission :deploy, :stack`) then calls `POST /stacks/:id/deploys` with `require_ci: true`. The guard `param_error!(:require_ci, "Commit is not deployable") if params.require_ci && !commit.deployable?` in `DeploysController#create` passes because `commit.deployable?` is now (falsely) true, and `stack.trigger_deploy` proceeds. [5](#0-4) 

None of the listed guards catch this: `verify_signature` only confirms the sender owns *a* valid hook for *some* repo, not that the SHA belongs to that repo; `drop_unhandled_event`/`ExplicitParameters` only validate payload shape; there is no `Repository`/`Stack` scoping check anywhere in `StatusHandler`.

### Impact Explanation
An attacker who controls any GitHub repository tracked by Shipit (including their own fork) can cause a fabricated CI "success" status to be written against a commit belonging to a different stack/repository they do not control, bypassing the `require_ci` safety check on deploys. This directly enables an operator (even acting in good faith, unaware of the poisoning) to ship code that never passed the victim repository's real CI — an unauthorized deploy of unvetted code, matching the "unauthorized deploy" Critical impact category. This is repeatable against any pair of stacks that share commit history (all forks, by construction) and is not limited to a single tenant.

### Likelihood Explanation
Preconditions: the attacker needs a repository that (a) is tracked as a Shipit stack (or can become one, e.g., via review-stacks/PR-based stacks common in Shipit deployments) and (b) shares at least one commit SHA with the victim stack's repository — trivially true for any fork relationship or cherry-picked identical commit. The attacker needs no Shipit secrets, sessions, or API tokens — only ordinary GitHub write access to their own repository to trigger a real, correctly-signed `status` webhook. This is low-cost and fully repeatable.

### Recommendation
Scope `StatusHandler#process` (and `Commit` lookups it performs) to the webhook's originating repository, mirroring the pattern used by other handlers via `stacks`/`repository_name`. Concretely, restrict the query to `stacks` scoped by `repository_name` (`Repository.from_github_repo_name(payload.dig('repository','full_name'))`) instead of a bare `Commit.where(sha: params.sha)` across all stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent, ensuring a status can only ever be attached to a commit belonging to the repository that actually sent the webhook.

### Proof of Concept
Minitest plan (webhook controller / integration test, no live GitHub):
```ruby
test "status webhook from repo B cannot mark repo A's commit as deployable" do
  stack_a = shipit_stacks(:shipit)              # victim stack/repo
  stack_b = shipit_stacks(:cyclimse)            # attacker-controlled stack/repo
  shared_sha = "a" * 40

  commit_a = stack_a.commits.create!(sha: shared_sha, message: "shared ancestor")
  commit_b = stack_b.commits.create!(sha: shared_sha, message: "shared ancestor")

  refute commit_a.reload.deployable?

  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => shared_sha, 'state' => 'success', 'context' => 'ci/attacker',
    'repository' => { 'full_name' => stack_b.repository.full_name, 'owner' => { 'login' => stack_b.repository.owner } },
    'branches' => [{ 'name' => stack_b.branch }]
  }.to_json
  post :create, body: body, as: :json

  # broken binding: status repository (stack_b) != commit_a's stack repository (stack_a)
  assert_not_equal stack_a.repository.full_name, stack_b.repository.full_name
  assert commit_a.reload.deployable?   # demonstrates the collision

  post :create, params: { stack_id: stack_a.to_param, sha: shared_sha, require_ci: true }
  assert_response :accepted   # should be :unprocessable_entity
end
```
