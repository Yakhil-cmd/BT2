## Title
Missing return after tar/hash-parsing error causes unvalidated private-payment chain to be processed with corrupted control flow - (File: network.js)

### Summary
`handleSavedPrivatePayments()` in `network.js` mirrors the Incus bug class exactly: a fallible parsing step is wrapped in `try/catch`, the `catch` block performs cleanup, but execution does **not** stop there — the function falls through and uses the (now-invalid) result plus re-invokes the chain-processing pipeline on the same untrusted data, exactly like `UploadAllFiles` continuing to dereference `hdr` after a non-EOF error.

### Finding Description
In the loop that re-processes queued private payments received from peers/devices: [1](#0-0) 

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
```

The `catch` block has no `return` statement, so after `deleteHandledPrivateChain(..., cb)` runs (which itself invokes `cb`, the `async.each` iteratee callback), execution **continues** past the catch and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` a second time on the same attacker-controlled `arrPrivateElements`. That call's own callbacks (`ifOk`/`ifError`/`ifWaitingForChain`) each invoke `cb` again — so the `async.each` iteratee `cb` is invoked twice for the same row.

`arrPrivateElements` originates from `unhandled_private_payments.json`, which is populated directly from a remote peer's or paired device's `private_payment`/`private_payments` justsaying with only shallow structural checks (`ValidationUtils.isNonemptyArray`, presence of `unit`/`payload`), see `handleOnlinePrivatePayment`: [2](#0-1) 
and `handlePrivatePaymentChains` in `wallet.js`: [3](#0-2) 

An attacker (any network peer, or a paired device/private-payment counterparty) can send a `payload` that is not a plain-hashable object (e.g., a value that makes `getSourceString`/`getJsonSourceString` throw, such as a value containing `undefined`, a function, or a structure the hashing serializer rejects) to force the `catch` branch, while the outer array still passes the shallow non-empty checks in `handleOnlinePrivatePayment`/`handlePrivatePaymentChains`.

### Impact Explanation
Double-invocation of the `async.each` iteratee callback corrupts the control flow of `handleSavedPrivatePayments`, which manages a mutex-guarded (`saved_private`) queue of private-payment chains and drives `assocNewUnits`/`eventBus.emit("new_my_transactions", ...)`. Calling the completion callback of an in-flight `async` iteration twice for the same item is a well-known pattern that can cause the final callback to fire prematurely (unlocking the `saved_private` mutex while other rows are still being processed) or double-processing/double-emitting events for the same private chain — this can result in a private payment being accepted or reported as accepted/validated more than once, or the mutex unlocking early and allowing overlapping runs of `handleSavedPrivatePayments`, undermining the serialization guarantee the mutex is meant to provide for private-payment bookkeeping (`unhandled_private_payments` table state, `deleteHandledPrivateChain`). This directly affects private-payment processing integrity, the analogous concern to the "unable to confirm/spend consistently" impact class for a wallet acting on private asset chains.

### Likelihood Explanation
Any peer or paired device that can deliver a `private_payment` (online) or a queued `private_payments` message can trigger this: it only needs a `payload` value that survives the loose validation in `handleOnlinePrivatePayment`/`handlePrivatePaymentChains` but throws inside `objectHash.getSourceString`/`getJsonSourceString` when `getBase64Hash` is called on it later during `handleSavedPrivatePayments`. Because the outer checks never deeply validate `payload`'s exact shape (only checks specific known sub-fields like `asset`, `inputs`, `outputs` being non-empty — extra/malformed nested values are not rejected), a crafted payload reaching the hashing step here is plausible without any special privilege.

### Recommendation
Add `return` immediately after handling the error in the `catch` block so the function does not fall through to compute `key` and call `validateAndSavePrivatePaymentChain` a second time:

```js
try {
    var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
}
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```

### Proof of Concept
1. As a peer or paired device, send a `private_payment`/`private_payments` message where `arrPrivateElements[0].payload` passes the shallow field checks in `handleOnlinePrivatePayment` (`unit`, `message_index`, `denomination`/`output_index` fields as required) but contains a nested value that causes `getSourceString`/`getJsonSourceString` (used by `objectHash.getBase64Hash`) to throw when invoked with `bJsonBased=true` (e.g. a value type not handled by the serializer).
2. Because `conf.bLight` clients queue the payment via `savePrivatePayment()` without deep validation, the row lands in `unhandled_private_payments`.
3. When `handleSavedPrivatePayments()` runs and reaches this row, `getBase64Hash` throws, `deleteHandledPrivateChain(..., cb)` calls `cb()`, then control falls through and `privatePayment.validateAndSavePrivatePaymentChain(...)` is invoked, whose callback also calls `cb()` — `cb` fires twice for the same `async.each` item, corrupting the iteration/mutex lifecycle of `handleSavedPrivatePayments`.

Note: I could not execute this against a live node to confirm the exact downstream `async`/mutex failure mode (e.g., whether `async.each`'s underlying implementation degrades gracefully or asserts); this should be verified with a runtime reproduction, as the index does not include the specific `async` library version's behavior for double-callback invocation used here.

function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
		return callbacks.ifError("malformed private chain");
