## Title
Unauthenticated device-message decryption failure crashes the whole node process (permanent DoS) - ([File: device.js])

### Summary
`decryptPackage()` in `device.js` throws an uncaught exception from inside a `setTimeout` callback whenever an incoming device message's ephemeral DH public key doesn't match any of the recipient's known keys. `network.js` installs a global `uncaughtException` handler that deliberately re-throws to crash the process, so this reachable, no-privilege condition brings down the entire node.

### Finding Description
When a device message arrives (via `hub/message` justsaying while connected to a hub, or via `hub/deliver` when the node is its own hub), the open/unencrypted envelope fields are checked, and the signature over the envelope is verified with `ecdsaSig.verify(...)` using the *sender-supplied* `objDeviceMessage.pubkey` [1](#0-0) . Because the pubkey is attacker-chosen and the signature is self-consistent (attacker signs with their own generated keypair), any unauthenticated party who can reach the hub protocol or the target device can produce a message that passes this check.

After the envelope checks pass, `decryptPackage(objDeviceMessage.encrypted_package)` is invoked [2](#0-1) . Inside `decryptPackage`, if `objEncryptedPackage.dh.recipient_ephemeral_pubkey` does not match the device's temp key, previous temp key, or permanent key, the function falls into the "unknown key" branch: [3](#0-2) 

This branch schedules `throw Error(...)` inside a `setTimeout`, which executes as an uncaught exception on the event loop (outside the calling function's try/catch), rather than being caught by the `try { var json = decryptPackage(...) } catch(e) {...}` wrapper in the caller [4](#0-3) .

`network.js` registers a process-level handler for exactly this situation: [5](#0-4) 

The handler explicitly re-throws (`throw err;`) with the comment "crash the process to avoid ending up in an inconsistent state," terminating the entire node.

### Impact Explanation
Any unprivileged peer able to send a device message to a hub-connected node (or to a node acting as its own hub via `hub/deliver`, see `network.js:3508-3542`) can trivially construct an `encrypted_package.dh.recipient_ephemeral_pubkey` that doesn't match any of the target's known keys — this requires no prior pairing or trust relationship, since the only preconditions are a well-formed envelope, a valid self-signature, and `to === target_device_address`. This causes the target node's process to crash. If repeated, it produces a sustained denial of service against a full node, light wallet backend, or hub, preventing it from confirming/relaying units, i.e., "a network unable to confirm new units" for that node.

### Likelihood Explanation
High likelihood: no authentication, pairing, or special privilege is needed — an attacker only needs the target device address (routinely shared for payments/pairing) and network reachability to the hub/node. The exploit is deterministic and repeatable.

### Recommendation
Wrap the "unknown key" branch so it reports the error through the normal error-handling path instead of throwing asynchronously in a `setTimeout`. Return an error/null synchronously (as the other failure branches of `decryptPackage` already do, e.g., `return console.log(...)` for malformed params or `catch(e)` for decrypt failures at `device.js:458-462`), and let the caller's existing `catch`/`respondWithError` handle it. Avoid `throw` inside `setTimeout` entirely for attacker-reachable code paths; reserve the `eventBus.emit('nonfatal_error', ...)` (already present but commented out at `device.js:434`) for logging instead of crashing the process.

### Proof of Concept
1. Attacker generates an ECDSA keypair and derives `pubkey`/`from_address`.
2. Attacker crafts `objDeviceMessage = { to: <target_device_address>, pubkey: <attacker_pubkey>, encrypted_package: { dh: { sender_ephemeral_pubkey: <random valid b64>, recipient_ephemeral_pubkey: <random b64, not matching any of target's keys> }, iv, authtag, encrypted_message } }`.
3. Attacker computes `signature = ecdsaSig.sign(objectHash.getDeviceMessageHashToSign(objDeviceMessage), attacker_priv)` and sets `message_hash = objectHash.getBase64Hash(objDeviceMessage)`.
4. Attacker sends this as `hub/message` justsaying to the target (if hub-connected) or `hub/deliver` request (if target is its own hub).
5. Envelope validation and signature verification succeed (device.js:154-168 / network.js:3511-3527); `decryptPackage` is called, hits the "unknown key" branch, schedules `throw Error(...)` via `setTimeout`, and the process crashes via the `uncaughtException` handler in `network.js:4530-4543`.

Note: full confirmation of the exact `message_from_hub`/`handle_message_from_hub` wiring in `wallet.js` could not be completed within the available tool calls, but the crash path itself is fully supported by the cited code in `device.js` and the process-level re-throw in `network.js`.
