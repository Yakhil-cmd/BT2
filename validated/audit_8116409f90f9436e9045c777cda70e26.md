## Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

## Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table with no repository/stack scoping, then writes a `Status` row via `Commit#create_status_from_github!`. Because SHAs are content-addressed and can collide across unrelated repositories/forks that happen to be tracked by different Shipit stacks, a webhook that is validly signed for repository A can create/update status rows attached to a commit belonging to stack B, altering `blocked?`/`deployable?` for a victim stack the attacker never authenticated against.

## Finding Description
The broken binding is: **the repository that HMAC-signs the webhook == the repository whose commit/stack records get mutated**. In this codebase that equality does not hold.

Path:
- `Shipit::WebhooksController#create` parses `payload` and dispatches to registered handlers for the `status` event [1](#0-0) .
- `verify_signature` computes the expected HMAC using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from `params.dig('repository', 'owner', 'login')` in the *attacker's own payload* [2](#0-1) . This only proves the payload was signed by *some* organization's configured `webhook_secret` — the org the attacker names in their own payload, which can be an org/repo the attacker legitimately owns and has configured in Shipit.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it never checks `commit.stack.repository` against the webhook's `repository` payload [3](#0-2) .
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, and `Status.replicate_from_github!` persists `state`/`context` tied to `stack_id` derived purely from whichever `Commit` row matched the bare SHA [4](#0-3) [5](#0-4) .
- `Status::Common#blocking?` treats any status whose `context` is in `commit.blocking_statuses` (delegated from stack config) and whose state is not `success` as blocking [6](#0-5) .
- `Commit#blocked?` scans `stack.commits.reachable...any?(&:blocking?)` to decide if the stack is blocked, and `#deployable?` depends on it [7](#0-6) .

Exploit flow: if the victim stack has a `Commit` row whose `sha` collides with a SHA the attacker controls in a repository/org they own (e.g., an empty commit, a rebased/cherry-picked commit shared via a common base branch, or any git object that legitimately exists in both an attacker-controlled fork and the victim's tracked repo history — git SHAs are content addressed and identical content produces identical SHAs across unrelated repos), the attacker can send a signed `status` webhook (`context: github-actions`, `state: failure`) from their own repo. Because `StatusHandler` doesn't scope by repository, this creates a `Status` row against the victim's `Commit`, potentially setting `blocking?` true and flipping `blocked?`/`deployable?` for the victim stack.

Why guards don't help: `verify_signature` validates only that *a* configured org's secret produced the HMAC — it validates authenticity of the sender's own org, not that the sender's org matches the target commit's stack. `drop_unhandled_event` and `ExplicitParameters` (`params.sha`, `params.state`, `params.context`) only validate shape, not repository binding. There is no `Repository` format check applied at the handler level for cross-tenant isolation.

## Impact Explanation
A payload from repository A can flip `blocked?`/`deployable?` for stack B that A never authenticated for — this is "a payload for one repository mutating another's stack/commit," which matches the Critical bucket in the rules. Blast radius depends on SHA collision feasibility across the specific commits tracked by two stacks; it's not a universal free-form primitive (attacker cannot choose the victim's SHA, only exploit an existing shared/colliding SHA), but wherever it applies it is repeatable per shared SHA and requires no privileges beyond owning some Shipit-configured repository.

## Likelihood Explanation
Requires: (1) the attacker controls/owns a repository configured in Shipit (so they can get a validly-signed `status` webhook accepted at all — this is already a routine, low-privilege state for a public/multi-tenant Shipit install), (2) a `Commit` row in the victim stack whose `sha` matches a SHA reachable/creatable in the attacker's own repo (achievable for shared base commits, cherry-picks, identical empty/tree-identical commits, or monorepo/fork scenarios), and (3) the victim stack has `blocking_statuses` configured for the given `context`. Given those preconditions the exploit is a single unauthenticated (from Shipit's perspective, just webhook-signed) POST request, fully repeatable.

## Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogously `CheckRunHandler` if it shares the pattern) by repository: resolve the target stack(s) via `params.dig('repository', 'full_name')` (or equivalent) and restrict `Commit.where(sha: params.sha)` to commits whose `stack.repository_full_name` (or `github_repo_name`) matches the webhook's own repository, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repo.id })` (or the engine's actual repository/stack association) before calling `create_status_from_github!`.

## Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, minitest)
test "status webhook from repository A must not mutate commit/stack belonging to repository B" do
  stack_a = shipit_stacks(:example) # repo A
  stack_b = create_stack_with_blocking_statuses(blocking_statuses: ['github-actions']) # repo B, victim

  shared_sha = "a" * 40
  commit_a = stack_a.commits.create!(sha: shared_sha, ...)
  commit_b = stack_b.commits.create!(sha: shared_sha, ...) # SHA collision across stacks

  before = commit_b.reload.blocked?
  assert_equal false, before # baseline: repo B not blocked

  payload = {
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'github-actions',
    'repository' => { 'full_name' => stack_a.github_repo_name, 'owner' => { 'login' => stack_a.repository_owner } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload) # signature verified for repo A only

  after = commit_b.reload.blocked?
  assert_equal before, after, "status webhook signed for repo A must not change blocked? state of unrelated stack B"
end
```
Assert: `commit_b.blocked?` (and `stack_b.deployable?`) before == after despite the webhook only being validly signed for repository A's organization; if it differs, the cross-tenant mutation is confirmed.
