### Title
Membership webhook signature is verified against the wrong organization's secret, allowing cross-organization team-membership forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook against using the `repository.owner.login` field (falling back to `organization.login`), but `MembershipHandler#process` acts on the separate, attacker-controlled `organization.login` field to decide which `Team` gets created/updated and which user is added to it. The field that is cryptographically bound to the request (the one used to choose the verification secret) is not the same field that is trusted for the privileged write (team scoping), breaking the equality that should hold: `secret_used_for_verification.organization == team.organization_being_mutated`.

### Finding Description
`WebhooksController#verify_signature` derives the "owner" it uses to look up the correct per-organization webhook secret like this: [1](#0-0) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

and then verifies the signature using that owner: [2](#0-1) 

Note the priority: if a `repository` key is present in the JSON body, its `owner.login` is used for secret selection, and the top-level `organization.login` is **ignored** for that purpose. This is confirmed by the engine's own test fixture, which sends membership payloads with *both* keys populated: [3](#0-2) 

```ruby
def membership_params
  { action: 'added', team: team_params, organization: { login: 'shopify' }, member: { login: 'walrus' } }.merge(repository_params)
end
def repository_params
  { repository: { owner: { login: 'shopify' } } }
end
```

However, once the signature check passes, the actual privileged mutation is driven entirely by the `organization.login` and `team` sub-object, not by `repository.owner.login`: [4](#0-3) 

```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)

  case params.action
  when 'added'
    team.add_member(member)
  ...
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```

Because Shipit can be configured to serve multiple organizations, each with its own `webhook_secret` (as documented in `config/secrets.development.example.yml`), any org onboarded onto a shared Shipit instance possesses a valid webhook secret it can sign requests with. An attacker who controls org `A` (and thus knows/owns `A`'s `webhook_secret`) can send a `membership` webhook where:
- `repository.owner.login = "A"` (so `verify_signature` selects and validates against A's own secret — which the attacker can compute correctly), and
- `organization.login = "victim-org"` and `team.id = <github_id of a Team already tracked for victim-org, e.g. one listed in Shipit.github_teams>`, and
- `member.login = <attacker's own GitHub login>`.

Signature verification succeeds (it's validated against `A`, which the attacker legitimately controls), yet `MembershipHandler` uses the `victim-org`/`team.id` fields — never covered by any authenticity check binding them to `A` — to add the attacker as a member of the target `Team` record via `Team.find_or_create_by!(github_id: params.team.id)` and `team.add_member(member)`.

### Impact Explanation
`User#authorized?` grants application access based solely on team membership: [5](#0-4) 

```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
```

If any team configured in `Shipit.github_teams` belongs to another organization hosted on the same Shipit instance, an attacker who merely controls a second, unrelated organization onboarded to that instance can forge a `membership` webhook to add their own GitHub-authenticated user to that privileged `Team` record, escalating from "member of org A" to "authorized Shipit user via victim-org's team" — this is exactly the "escalation into `Shipit.github_teams` authorization" High-severity impact category, achieved purely by exploiting the mismatch between the field used for signature-secret selection and the field trusted for the privileged write.

### Likelihood Explanation
Exploitation requires only: (1) that the attacker be an admin/owner of some GitHub organization already configured with its own entry (and `webhook_secret`) in Shipit's multi-org `github:` configuration — a normal, unprivileged-with-respect-to-Shipit scenario in any shared/multi-tenant Shipit deployment — and (2) knowledge of the numeric `github_id` of the target `Team` record (discoverable via GitHub's public team APIs/URLs or via Shipit's own UI/API which exposes team info). No access to Shipit sessions, `ApiClient` tokens, the GitHub App private key, or the victim organization's webhook secret is needed.

### Recommendation
Bind the organization used for signature verification to the exact organization the payload's privileged action targets:
- For `membership` events, verify the signature using `organization.login`, not `repository.owner.login`, since that is the field the handler actually trusts.
- More generally, `verify_signature` should select the secret/org consistently with whichever field each specific event handler treats as authoritative, or reject payloads where `repository.owner.login` and `organization.login` are both present but disagree.
- Additionally, `MembershipHandler` should confirm the mutated `Team#organization` matches the organization whose secret validated the request before applying membership changes.

### Proof of Concept
1. Attacker controls GitHub org `evil-org`, which is configured on the shared Shipit instance with its own `webhook_secret` (`S_evil`), independent from `victim-org`.
2. Attacker looks up (via GitHub's public API) the `github_id` of `victim-org`'s privileged team that is listed in `Shipit.github_teams` (e.g., `victim-org/admins`, `github_id = 999`).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Admins", "slug": "admins", "url": "https://github.com/..." },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-handle" },
  "repository": { "owner": { "login": "evil-org" } }
}
```
4. `WebhooksController#repository_owner` resolves to `"evil-org"`; `verify_signature` calls `Shipit.github(organization: "evil-org").verify_webhook_signature(...)`, which the attacker satisfies using `S_evil` (which they legitimately possess).
5. `MembershipHandler#find_or_create_team!` looks up/updates the `Team` with `github_id: 999` (the real `victim-org/admins` team, already tracked because it's in `Shipit.github_teams`), sets `team.organization = "victim-org"`, and `team.add_member(User.find_or_create_by_login!("attacker-handle"))`.
6. `attacker-handle`, after completing normal GitHub OAuth login to Shipit, now passes `User#authorized?` because they belong to a team in `Shipit.github_teams` — despite never having any real relationship to `victim-org`.
