### Title
Accrual integer overflow can permanently freeze an oversized market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
Interest accrual multiplies stored RAY-scaled supply and debt balances by their RAY indexes before applying the borrow-index ceiling. When either product exceeds `i128::MAX`, `accrue_step` reverts with `MathOverflow`. Because every market mutation syncs interest before performing the operation, repayment, withdrawal, liquidation, and explicit `update_indexes` all become unavailable for the affected market.

### Finding Description
`update_indexes` is permissionless for any authenticated caller: `Controller::update_indexes` calls `markets::update_indexes`, which only requires `caller.require_auth()` and forwards the selected `HubAssetKey` list to the pool. [1](#0-0) [2](#0-1) 

The pool loads each requested market and calls `global_sync`, which invokes `accrue_step` for elapsed-time chunks. [3](#0-2)  `accrue_step` first computes `borrowed * borrow_index` and `supplied * supply_index` through `scaled_to_original`. [4](#0-3)  `scaled_to_original` delegates to `Ray::mul`, which uses half-up `x * y / RAY` arithmetic and panics with `MathOverflow` when the quotient cannot fit in `i128`. [5](#0-4) [6](#0-5) 

The index ceiling is applied only after these total-value calculations. `update_borrow_index` caps the next index at `MAX_BORROW_INDEX_RAY`, but does not cap or avoid overflow of `borrowed * old_index`, `borrowed * new_index`, or `supplied * supply_index`. [7](#0-6) [8](#0-7) 

The same accrual runs before ordinary market mutations through `synced_market` and `load_leg`. [9](#0-8)  Therefore, once either stored balance/index product crosses the `i128` result domain, the revert is persistent rather than a one-time failed accrual.

### Impact Explanation
This can permanently freeze all funds represented by the affected market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot execute liquidation paths that sync the market, and the permissionless `update_indexes` recovery path itself reverts. Since pool state stores scaled totals rather than their expanded values, the panic recurs on every subsequent accrual attempt.

For example, an 18-decimal asset deposit of one billion whole tokens produces `1e36` RAY-scaled shares. The approximate `i128::MAX` value domain is `1.70e38`, so the expanded market value overflows when its index exceeds roughly `170` RAY. At near-full utilization, debt-side accrual reaches a similar threshold before `MAX_BORROW_INDEX_RAY` can stop further growth.

### Likelihood Explanation
An unprivileged attacker needs sufficient capital to create or participate in a very large market and to open enough collateral-backed debt to keep utilization high while indexes compound. No privileged role, leaked key, oracle manipulation, or contract upgrade is required: `supply`, `borrow`, and `update_indexes` are reachable through normal controller entrypoints, subject to the configured caps and risk gates. The practical barrier is capital requirements and whether a deployed market permits balances large enough to approach the `i128` RAY-value ceiling.

### Recommendation
Bound or split the total-value calculations before multiplying shares by indexes. In particular:

- Compare `scaled` against `i128::MAX / index` before calling `scaled_to_original`.
- When the bound is crossed, cap the market’s index and/or expanded value deterministically instead of panicking.
- Add an emergency-but-safe accrual path that clamps accrued value at the numeric ceiling while preserving repayment and withdrawal.
- Enforce effective caps below the index-dependent value ceiling, or reject further accrual in a recoverable state before the product overflows.
- Add regression coverage showing that `update_indexes`, `repay`, `withdraw`, and liquidation remain callable at the largest admitted cap and highest configured borrow rate.

### Proof of Concept
1. On an active hub, supply a very large amount `S` of an 18-decimal asset, such that its scaled supply is approximately `S * 10^9`.
2. Supply sufficient collateral in another market and borrow enough of the first asset to maintain near-full utilization under the market’s configured rate model.
3. Allow ledger time to pass so repeated `update_indexes(caller, vec![hub_asset])` calls compound the borrow and supply indexes.
4. Once `borrowed * borrow_index` or `supplied * supply_index` exceeds `i128::MAX`, the next `update_indexes` reverts inside `scaled_to_original`.
5. Subsequent `withdraw`, `repay`, and liquidation attempts follow `synced_market`/`load_leg`, hit the same `global_sync -> accrue_step -> scaled_to_original` path, and also revert with `MathOverflow`, leaving the market funds frozen.

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

) -> (Ray, Ray) {

/// Loads a market cache and accrues interest through the current ledger time.
pub(crate) fn synced_market(env: &Env, hub_asset: &HubAssetKey) -> Cache {
    let mut cache = Cache::load(env, hub_asset);
    interest::global_sync(env, &mut cache);
    cache
}

/// Renews instance TTL, then loads and accrues the market.
pub(crate) fn renewed_market(env: &Env, hub_asset: &HubAssetKey) -> Cache {
    renew_instance(env);
    synced_market(env, hub_asset)
}

/// Validates `action.amount ≥ 0`, syncs the market, and returns (cache, scaled position).
pub(crate) fn load_leg(env: &Env, action: &PoolAction) -> (Cache, Ray) {
    require_nonneg_amount(env, action.amount);
    let cache = synced_market(env, &action.hub_asset);
    (cache, Ray::from(action.position.scaled_amount))
