### Title
`ProxyType::NonTransfer::is_superset` falsely claims superset of `ProxyType::Auction`, letting a `NonTransfer` delegate grant itself an `Auction` sub-proxy that can call `Registrar::swap`, which `NonTransfer` explicitly denies - ([File: polkadot/runtime/westend/src/lib.rs])

### Summary
`pallet-proxy`'s `add_proxy`/`remove_proxy` guard only checks `is_superset`, not `filter`, when a delegate tries to grant a new sub-proxy type [1](#0-0) . In the relay-chain runtimes (`westend`, `rococo`, and `substrate/frame/staking-async/runtimes/rc`), `ProxyType::NonTransfer::is_superset` returns `true` for *any* other `ProxyType` except `Any` [2](#0-1) , even though `NonTransfer`'s own `filter` explicitly *excludes* `Registrar::swap` [3](#0-2) , while `ProxyType::Auction::filter` matches the whole `Registrar{..}` call family (which includes `swap`) [4](#0-3) . This is the same bug class that was already found and fixed for `ProxyType::NonTransfer` vs `ProxyType::Governance` on Asset Hub (issue #12724) [5](#0-4) , but the analogous "deny-list is not an actual superset of everything else" flaw persists for `Auction` on the relay-chain runtimes.

### Finding Description
The real user entry point is a signed `pallet-proxy` extrinsic: any account can be delegated a `NonTransfer` proxy (a "restricted" role, analogous to Ghost's non-Admin "contributor" role) by its owner. `pallet_proxy::do_proxy` installs a call filter closure that is consulted before dispatch: for `add_proxy`/`remove_proxy` calls it uses `def.proxy_type.is_superset(proxy_type)` rather than `def.proxy_type.filter(...)` to decide whether the delegate may grant a new proxy type to some (attacker-chosen) account [6](#0-5) .

For `westend`/`rococo`/staking-async-rc, `is_superset` is implemented generically as:
```
(x, y) if x == y => true,
(ProxyType::Any, _) => true,
(_, ProxyType::Any) => false,
(ProxyType::NonTransfer, _) => true,
_ => false,
``` [2](#0-1) [7](#0-6) [8](#0-7) 

This blanket rule assumes `NonTransfer`'s call set is a strict superset of every other `ProxyType`'s call set. But `NonTransfer`'s `filter` explicitly carves out `Registrar::swap` ("Specifically omitting Registrar `swap`") while still allowing `register`/`deregister`/`reserve` [3](#0-2) . Meanwhile `ProxyType::Auction`'s filter matches the entire `RuntimeCall::Registrar{..}` pattern, which includes `swap` [4](#0-3) . Because `is_superset(NonTransfer, Auction) == true`, `do_proxy` allows a `NonTransfer` delegate to call `Proxy::add_proxy { delegate: <attacker_account>, proxy_type: Auction, .. }` on behalf of the real owner (this call itself is allowed since `RuntimeCall::Proxy(..)` is inside `NonTransfer`'s own allow-list [9](#0-8) ). The attacker-controlled delegate can then dispatch `Proxy::proxy(..., Registrar::swap { .. })` as an `Auction` proxy of the real account - a capability the owner's `NonTransfer` grant was specifically designed to withhold.

### Impact Explanation
This is a check-bypass / privilege-escalation-within-delegated-scope bug: a lesser-privileged (`NonTransfer`) proxy relationship is used to mint a different proxy type (`Auction`) whose granted call set exceeds what `NonTransfer` itself permits, defeating the explicit intent encoded in the `NonTransfer` filter ("omitting Registrar `swap`"). This directly mirrors the CVE's bug class: a lower-privilege actor obtaining access to functionality gated to a higher/other privilege tier due to a missing/incorrect authorization check in a permission-comparison routine (`is_superset` acting like Ghost's flawed "limits service" check). I was not able to fully inspect `paras_registrar::Pallet::swap`'s dispatch body (only its imports) within the available tool budget, so I cannot confirm with certainty what `swap`'s prerequisites are (e.g., whether it also requires matching consent from the counterparty para's manager) or the precise blast radius (para-identity swap, potential deposit/slot implications). This uncertainty limits confidence in rating final severity as anything beyond the structural authorization-bypass itself.

### Likelihood Explanation
Likelihood is moderate-to-high for the structural bypass: it requires no privileged role, governance action, or stolen keys — only a legitimately-granted `NonTransfer` proxy (a common, low-trust delegation pattern) and a normal `add_proxy`/`proxy` extrinsic sequence, both fee-paying but otherwise unrestricted. The gating logic (`is_superset`) is pure code and deterministic; there is no race condition or timing dependency. The main uncertainty is downstream impact of reaching `Registrar::swap`, not reachability of the call itself.

### Recommendation
Fix `ProxyType::is_superset` for `NonTransfer` on `westend`, `rococo`, and `staking-async-rc` runtimes to stop assuming `NonTransfer` structurally dominates every other proxy type; either enumerate exact subset relationships (as `asset-hub-westend` now appears to do post-#12724, e.g. explicit `Collator`/`Staking`/`NominationPools`/`StakingOperator` subset lists in its `is_superset` [10](#0-9) ), or derive `is_superset` programmatically from `filter` (e.g., verifying `self.filter` is implied for all `RuntimeCall` variants admitted by `other.filter`) instead of hand-maintained boolean tables that can drift from the `filter` denylist. Add a regression test analogous to `non_transfer_proxy_is_not_a_superset_of_governance` for the `Auction`/`Registrar::swap` case on `westend`/`rococo`.

### Proof of Concept
No dynamic execution was performed; this is a static code-path analysis. Evidence assembled:
- `do_proxy` uses `is_superset` (not `filter`) to gate `add_proxy`/`remove_proxy`: [1](#0-0) 
- `NonTransfer` filter allows `RuntimeCall::Proxy(..)` and explicitly omits `Registrar::swap`: [11](#0-10) 
- `Auction` filter admits the full `Registrar{..}` family (including `swap`): [4](#0-3) 
- `is_superset` blanket rule `(NonTransfer, _) => true`: [2](#0-1) 
- Pre-existing, already-patched analog for `Governance` on Asset Hub confirms this exact class of bug was previously exploitable and is treated as security-relevant by the project: [5](#0-4) 

I could not confirm `paras_registrar::Pallet::swap`'s exact authorization/consent requirements within the remaining tool budget (only its module header/imports were retrieved, not the dispatchable body), so a concrete end-to-end integration-test PoC exercising `Proxy::add_proxy(NonTransfer) -> Proxy::proxy(Auction) -> Registrar::swap` was not executed and its final on-chain impact (para-identity/slot consequences) is unverified. This should be validated with a `frame-support` mock/integration test before filing, and the `swap` prerequisites reviewed to determine whether reachability alone (bypassing the `NonTransfer` denylist) already constitutes a reportable authorization violation independent of `swap`'s own internal checks.

/// Regression test for <https://github.com/paritytech/polkadot-sdk/issues/12724>.
///
/// `NonTransfer` used to claim `Governance` as a subset while denying the `Treasury`,
/// `ConvictionVoting`, `Referenda` and `Whitelist` calls that `Governance` admits, which let a
/// `NonTransfer` proxy add a `Governance` proxy and widen its own permissions.
#[test]
fn non_transfer_proxy_is_not_a_superset_of_governance() {
	use asset_hub_westend_runtime::ProxyType;
	use frame_support::traits::InstanceFilter;

	// `NonTransfer` denies every governance call family that `Governance` admits, except `Utility`.
	for call in [
		RuntimeCall::Treasury(pallet_treasury::Call::void_spend { index: 0 }),
		RuntimeCall::ConvictionVoting(pallet_conviction_voting::Call::remove_vote {
			class: None,
			index: 0,
		}),
		RuntimeCall::Referenda(pallet_referenda::Call::refund_decision_deposit { index: 0 }),
		RuntimeCall::Whitelist(pallet_whitelist::Call::remove_whitelisted_call {
			call_hash: Default::default(),
		}),
	] {
		assert!(ProxyType::Governance.filter(&call), "Governance must admit {call:?}");
		assert!(!ProxyType::NonTransfer.filter(&call), "NonTransfer must deny {call:?}");
	}

	// So it must not declare itself a superset of it. This is what stops a `NonTransfer` proxy
	// from granting itself a `Governance` proxy: `pallet_proxy` gates `add_proxy`/`remove_proxy`
	// on `is_superset` before it ever consults `filter`, which by itself does not deny `Proxy`
	// calls.
	assert!(!ProxyType::NonTransfer.is_superset(&ProxyType::Governance));
```
