### Title
Review-stack PR label `github_token` overrides the real `GITHUB_TOKEN` in git command env - ([File: lib/shipit/task_commands.rb], [File: lib/shipit/stack_commands.rb], [File: app/models/shipit/review_stack.rb])

### Summary
`Shipit::ReviewStack#env` injects every pull request label as an uppercased env key with value `"true"`, and this hash is merged into the command env *after* the real `GITHUB_TOKEN` has already been set by `Shipit::Commands#base_env`, with nothing downstream restoring it. A PR label literally named `github_token` therefore clobbers the real token for that stack's git operations.

### Finding Description
The claimed-safe binding is: `Command#unbundled_env['GITHUB_TOKEN'] == Shipit.github(organization: @stack.repository.owner).token`, always, regardless of PR labels.

Tracing the merge order breaks this binding for review stacks:

- `Shipit::Commands#base_env` sets the real token: `'GITHUB_TOKEN' => github.token` [1](#0-0) 
- `Shipit::StackCommands#env` does `super.merge(@stack.env)` — i.e. the real-token base env is merged with, and can be overridden by, `@stack.env` [2](#0-1) 
- `Shipit::TaskCommands#env` does the same: `super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)`, and none of the keys merged after `@stack.env` (`SHIPIT_USER`, `EMAIL`, `BUNDLE_PATH`, `SHIPIT_LINK`, `TASK_ID`, `IGNORED_SAFETIES`, `GIT_COMMITTER_NAME/EMAIL`) touch `GITHUB_TOKEN` [3](#0-2) 
- `Shipit::ReviewStack#env` overrides `Stack#env` and appends every PR label, uppercased, as `"true"`: `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` [4](#0-3) 
- Labels are captured directly from the GitHub webhook payload with no allow-list/reserved-word filtering: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [5](#0-4)  and `Shipit::PullRequest#github_pull_request=` does the same unfiltered assignment: `self.labels = github_pull_request.labels.map(&:name)` [6](#0-5) 
- `Command#unbundled_env` gives priority to the caller-supplied `@env` over `BASE_ENV`, so whatever ends up in the merged hash reaches `PTY.spawn`: `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [7](#0-6) 

Exploit flow: a PR against a repository with an active `Shipit::ReviewStack` gets labeled `github_token` (or `Github_Token`, any case — `.upcase` normalizes it). The label-capturing webhook handler stores this label on the `PullRequest` record. The next time `StackCommands#fetch`, `#fetch_commit`, or any `TaskCommands`/`DeployCommands` `env` is computed for that review stack, `@stack.env` contains `'GITHUB_TOKEN' => 'true'`, which overwrites the real token set in `base_env`, and nothing downstream restores it.

Existing guards (`verify_signature`, `ExplicitParameters` schema, `EnvironmentVariables#permit`) do not address this because the vulnerable code path is not the webhook signature check itself — it's the unrestricted mapping of arbitrary label text into the process environment key namespace of git commands, with no reserved-word exclusion (`GITHUB_TOKEN`, `GITHUB_DOMAIN`, `GIT_ASKPASS`, etc. are all equally overridable this way).

### Impact Explanation
For the affected review stack, `git fetch`/`git clone`/`git push` and all deploy/rollback/restart task commands run with `GITHUB_TOKEN=true` instead of the real OAuth/App token. This breaks authentication for that stack's git operations (denial of the deploy pipeline for that PR/stack) rather than leaking the real token to the attacker (the attacker cannot read the resulting env value, only clobber it). This matches the "auth failure" direction described in the question rather than credential exfiltration — since the attacker only controls the override value ("true"), not the read side, they cannot exfiltrate the real secret through this path. Blast radius is scoped to the single review stack whose PR carries the label; it does not cross tenants/stacks because `@stack.env` is stack-scoped.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled, and the attacker must be able to get the label `github_token` attached to their PR. Per the question's stated attacker capability ("label their own PR"), this is treated as reachable; in real GitHub, labeling generally requires triage/write access to the base repo, which would normally exclude a pure external contributor — this is a caveat on real-world exploitability that could not be independently verified against GitHub's permission model from this codebase alone. Given the label, the attacker cost is trivial and repeatable (relabel/unlabel to toggle), but the primary consequence is a self-inflicted denial of their own stack's deploy authentication, not a cross-tenant compromise.

### Recommendation
In `Shipit::ReviewStack#env`, filter out labels that collide with reserved environment variable names (at minimum `GITHUB_TOKEN`, `GITHUB_DOMAIN`, `GIT_ASKPASS`, and any other keys set by `Shipit::Commands#base_env`), or re-merge the authoritative `GITHUB_TOKEN`/`GITHUB_DOMAIN` values last (after all stack/task-derived env) in `TaskCommands#env` and `StackCommands#env` so label-derived keys can never take precedence over credentials.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (or a new test/unit file)
test "#env cannot be overridden by a PR label named github_token" do
  stack = shipit_stacks(:review_stack)
  Shipit.stubs(:github).with(organization: stack.repository.owner).returns(stub(token: 'aS3cr3Tt0kEn', domain: 'github.com'))
  stack.pull_request.labels = ["github_token"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env

  assert_equal 'aS3cr3Tt0kEn', env['GITHUB_TOKEN']   # currently fails: env['GITHUB_TOKEN'] == 'true'
end
```
This demonstrates that `Shipit::TaskCommands.new(task).env['GITHUB_TOKEN']` deviates from `Shipit.github(organization: stack.repository.owner).token` when the PR carries the `github_token` label, confirming the equality binding is broken for review stacks. [8](#0-7) [9](#0-8)
