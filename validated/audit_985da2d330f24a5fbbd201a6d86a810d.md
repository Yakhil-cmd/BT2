## Title
Webhook signature verification is scoped to a claimed organization but handlers act on an unrelated `repository.full_name` from the same payload, allowing cross-organization forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
Shipit supports multi-tenant GitHub App configuration, where each organization has its own `webhook_secret` (see `test/dummy/config/secrets_double_github_app.yml` defining `OrgOne`/`OrgTwo`, each with independent `webhook_secret`). `Shipit.github(organization:)` looks up the app/secret for whichever organization is named in the request [1](#0-0) . The `WebhooksController` picks that organization from a payload field (`repository.owner.login`/`organization.login`), uses it solely to select which HMAC secret to verify against, then hands the *entire same payload* to event handlers, which independently pick the target repository from a different payload field (`repository.full_name`) with no cross-check that the two agree.

### Finding Description
`WebhooksController#verify_signature` derives the organization to authenticate against purely from attacker-controlled payload content: [2](#0-1) [3](#0-2) 

It then dispatches the raw parsed body, unmodified, to the registered handler for the event: [4](#0-3) 

Handlers determine which `Repository`/`Stack` to mutate from a *different* field of the very same JSON body, `repository.full_name`, e.g.: [5](#0-4) [6](#0-5) [7](#0-6) 

Nowhere is it verified that the owner encoded in `repository.owner.login`/`organization.login` (the field used to pick the signing secret) matches the owner portion of `repository.full_name` (the field the handler actually acts on). Because `Shipit.github(organization:)` supports arbitrarily many independently-configured GitHub Apps/organizations sharing one Shipit instance [8](#0-7) , an administrator who legitimately knows their own organization's `webhook_secret` (as documented, they configure and keep it "on the side" when creating their GitHub App) can craft an arbitrary raw JSON body, set `repository.owner.login`/`organization.login` to their own org (so verification succeeds with a secret they know), but set `repository.full_name` to a completely different, victim organization's repository that also happens to be hosted on the same Shipit instance. The signature check passes — the body is correctly HMAC'd with the attacker's own known secret — yet the handler operates on the victim's `Repository`/`Stack`.

This is the direct analog of the report's root cause: a value used at authorization/verification time (`repository.owner.login`, feeding into `verify_webhook_signature`) is not the same value later trusted to select the mutated resource (`repository.full_name`), even though both are nominally covered by "the signature." The binding that should hold — "organization that authenticated == organization owning the repository being written" — is never enforced.

### Impact Explanation
This breaks cross-tenant isolation: cross-repository writes on a multi-org Shipit deployment. Depending on handler, this can trigger `stack.sync_github` on a victim stack (`PushHandler`), archive/unarchive a victim's review stack or pull request (`PullRequest::ClosedHandler`, `LabeledHandler`, etc.), or otherwise mutate state belonging to an organization the attacker has no legitimate access to — all without ever needing the victim's own `webhook_secret`, GitHub credentials, or Shipit session. Per the scoring rubric this qualifies as Critical (cross-repository writes / unauthorized deploy path).

### Likelihood Explanation
Requires only: (a) a multi-organization Shipit deployment (a documented, supported configuration), and (b) the attacker being a legitimate administrator/operator of *any one* of the configured organizations (i.e., someone who knows that org's own `webhook_secret`, which is routinely handed to org admins per the setup docs). No compromise of the victim org, no repository write access to the victim, and no Shipit session are required — only a POST to the public `/webhooks` endpoint with a forged body signed by the attacker's own known secret.

### Recommendation
After successfully verifying the HMAC signature for the organization derived from the payload, additionally verify that the owner of `repository.full_name` (and/or `organization.login`) used by the handlers is the same organization whose secret validated the signature, rejecting the webhook otherwise. Alternatively, resolve the target `Repository` first, derive its configured owning organization from Shipit's own repository/stack records (not from attacker-supplied payload text), and verify the signature against that organization's secret exclusively.

### Proof of Concept
1. Deploy Shipit with two orgs configured, `OrgA` (attacker-administered, webhook_secret known to attacker) and `OrgB` (victim, has a `Repository`/`Stack` configured in the same Shipit instance).
2. Attacker crafts a `push` payload: `{"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}, "ref": "refs/heads/master", "after": "<attacker-chosen sha>", ...}`.
3. Attacker computes `X-Hub-Signature` using OrgA's known `webhook_secret` over the raw JSON body, and sets `X-Github-Event: push`.
4. POST to `/webhooks`. `verify_signature` resolves `repository_owner` → `"OrgA"`, fetches OrgA's `GitHubApp`, and the signature validates successfully (attacker signed with the correct, known secret) — see `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`.
5. `PushHandler#process` reads `repository.full_name` = `"OrgB/victim-repo"`, resolves OrgB's `Stack`, and calls `stack.sync_github(expected_head_sha: params.after)` — see `app/models/shipit/webhooks/handlers/push_handler.rb:12-17` and `app/models/shipit/webhooks/handlers/handler.rb:32-38` — mutating a victim organization's stack the attacker never had access to.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
