### Title
Block-hash grinding by the update-block proposer biases the pre-Randao proposer list, enabling unauthorized KAIA reward distribution — (File: `kaiax/valset/impl/getter_proposers.go`)

---

### Summary

In the pre-Randao code path (`WeightedRandom` / `UniformRandom` proposer policy before `IsRandao`), the proposer list that governs who proposes — and therefore who earns block rewards — for the next `ProposerUpdateInterval` blocks is seeded exclusively from `updateHeader.Hash()`. The proposer of that update block controls the block's transaction set and therefore controls the hash. By privately simulating different transaction inclusions/orderings before broadcasting, the proposer can grind the hash until the resulting shuffled list places their own address in the most favorable positions, gaining more block rewards than their staking weight entitles them to. No external service, majority collusion, or cryptographic break is required.

---

### Finding Description

`calcBaseProposers()` fetches the update block's header and passes its hash directly to the PRNG seed derivation:

```go
// kaiax/valset/impl/getter_proposers.go:40-62
updateHeader := v.Chain.GetHeaderByNumber(updateNum)
...
if v.Chain.Config().Rules(...).IsKore {
    list = generateProposerListUniform(qualified, updateHeader.Hash())   // line 56
} else {
    list = generateProposerListWeighted(qualified, si, useGini, updateHeader.Hash())  // line 62
}
```

Both helpers reduce the hash to a 60-bit integer seed via `HashToSeedLegacy`:

```go
// kaiax/valset/address_set.go:218-221
func HashToSeedLegacy(hash common.Hash) int64 {
    n8 := binary.BigEndian.Uint64(hash[:8])
    return int64(n8 >> 4)   // first 15 hex nibbles
}
```

This seed is fed into a linear-congruential PRNG (`math/rand`) that shuffles the weighted proposer list. The resulting order determines which validator proposes each of the next `ProposerUpdateInterval` blocks and therefore which reward address receives the per-block KAIA minting reward plus deferred transaction fees.

The proposer of `updateNum` can, before broadcasting their block:

1. Enumerate candidate transaction sets (include/exclude pending txs, vary ordering, inject a self-transfer with a swept nonce).
2. For each candidate, compute `keccak256(RLP(header))` locally and derive the 60-bit seed.
3. Run `generateProposerListUniform` / `generateProposerListWeighted` to see how many of the next `ProposerUpdateInterval` slots they would occupy.
4. Broadcast only the candidate that maximises their slot count.

This is structurally identical to the NFTX commit-reveal bug: the random outcome (proposer list) and the "payment" (block finalization) occur in the same atomic unit, and the actor can silently discard unfavorable outcomes before committing.

The same-block-hash seed is also used for committee selection in `selectRandomCommittee` (line 112 of `getter_context.go`), seeded from `c.prevHeader.Hash()`, giving the proposer of block N−1 influence over which validators sit on the committee for block N.

The Randao hardfork (`IsRandao`) replaces both seeds with `prevMixHash` — a BLS signature over the block number that is deterministic given the proposer's fixed secret key and therefore cannot be ground. The vulnerable code path remains live for any chain that has not yet activated the Randao hardfork and for all historical block replay.

---

### Impact Explanation

The corrupted value is the `[]common.Address` proposer list stored in `proposerListCache` for `updateNum`. Each extra slot the attacker occupies translates directly to one additional block reward: the full minting amount (`reward.mintingamount`, currently 9.6 KAIA/block on mainnet) plus deferred transaction fees, credited to the attacker's `Rewardbase` address via `FinalizeState`. Over a `ProposerUpdateInterval` of 3 600 blocks the attacker can shift tens of thousands of KAIA from other validators to themselves without any on-chain evidence of manipulation.

---

### Likelihood Explanation

The attack requires only that the adversary is the scheduled proposer of an update block — a normal, recurring event for any council member. The grinding search space is the set of pending transactions in the mempool plus any self-transactions the attacker can inject; with even a handful of pending transactions the attacker can explore thousands of combinations within the block time. No special tooling beyond a local node is needed. The attack is silent: the winning block is indistinguishable from an honest block.

---

### Recommendation

The Randao hardfork already provides the correct fix: replace `updateHeader.Hash()` with a BLS-derived `MixHash` that the proposer cannot choose. For chains that have not yet activated the Randao hardfork, the interim mitigation is to use a commit-reveal scheme: commit to the seed one interval in advance (e.g., use the hash of block `updateNum - ProposerUpdateInterval`) so that the proposer of `updateNum` cannot influence the seed for the list that governs their own interval.

---

### Proof of Concept

```
Setup:
  - ProposerUpdateInterval = 3600
  - Validator V is the scheduled proposer of block U = 3600 (the update block)
  - V has staking weight entitling it to ~34 slots out of 100

Attack:
  1. V builds candidate block B1 with transaction set T1.
     Compute seed1 = HashToSeedLegacy(B1.Hash())
     Run generateProposerListUniform(qualified, B1.Hash())
     → V appears in 34 of the next 3600 slots (expected)

  2. V builds candidate block B2 by adding a self-transfer tx.
     Compute seed2 = HashToSeedLegacy(B2.Hash())
     Run generateProposerListUniform(qualified, B2.Hash())
     → V appears in 51 of the next 3600 slots (favorable)

  3. V broadcasts B2.

Result:
  - V proposes 51 blocks instead of 34 in the next interval.
  - V receives 17 extra block rewards ≈ 17 × 9.6 KAIA = 163.2 KAIA
    (plus deferred fees) transferred from other validators' reward addresses.
  - The corrupted state is proposerListCache[3600] = [...V appears 51 times...]
    which is read by every subsequent call to selectWeightedRandomProposer()
    for blocks 3601–7200.
```

func selectRandomCommittee(qualified *valset.AddressSet, committeeSize uint64, prevBlockHash common.Hash, currProposer, nextDistinctProposer common.Address) []common.Address {
	qualified = qualified.Copy()
	qualified.Remove(currProposer)
	qualified.Remove(nextDistinctProposer)

	seed := valset.HashToSeedLegacy(prevBlockHash)
	shuffled := qualified.ShuffledListLegacy(seed)
	committee := []common.Address{currProposer, nextDistinctProposer}
	committee = append(committee, shuffled[:committeeSize-2]...)
	return committee
}
