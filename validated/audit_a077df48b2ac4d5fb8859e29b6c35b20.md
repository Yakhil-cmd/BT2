### Title
Attacker-selected, secretless GitHub organization lets forged webhook payloads act on repositories/stacks belonging to other organizations - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary

### Finding Description
`WebhooksController#verify_signature` derives the GitHub App/organization used for HMAC verification from a field inside the *unauthenticated* request body itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository','owner','login')` or falls back to `params.dig('organization','login')` — both attacker-controlled JSON fields in the raw POST body that has not yet been authenticated. `Shipit.github(organization: repository_owner)` then returns the `GitHubApp` config for *that org name*, and `verify_webhook_signature` is checked against *that org's* configured `webhook_secret`: [3](#0-2) 

Critically, when an organization entry has no `webhook_secret` configured (a valid, documented configuration shown in `config/secrets.development.example.yml` and `test/dummy/config/secrets_double_github_app.yml`, where `webhook_secret: # nil` is set), `verify_webhook_signature` unconditionally returns `true`.

Meanwhile, the actual repository/stack that webhook handlers *act on* is resolved from a **different** field of the same payload — `repository.full_name` — not the `repository.owner.login`/`organization.login` field that gated authentication: [4](#0-3) 

This breaks the intended binding: `organization that authenticated the webhook == organization owning the repository being written`. Because the field used to select the verification secret (`repository_owner`) and the field used to select the repository/stack that is mutated (`repository.full_name`) are independent, attacker-controlled values in the same forged JSON body, an attacker can pick any organization configured in `Shipit.github` that has a blank `webhook_secret` (satisfying `repository_owner`/`organization.login`) while pointing `repository.full_name` at a completely different, legitimately-tracked repository/stack belonging to another (properly secured) organization. Signature verification passes trivially (secret is nil), yet the handler dispatched by `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` operates on the victim repository's stacks.

### Impact Explanation
With a forged, unauthenticated webhook an attacker can:
- Send a `push` payload to trigger `GithubSyncJob` and CI/deploy-related pipeline behavior for stacks owned by another organization's tracked repositories.
- Send `status`/`check_suite` payloads to inject fake commit statuses / trigger `RefreshCheckRunsJob`, corrupting the deployability gating used before an unauthorized ship.
- Send `pull_request` payloads (`opened`/`reopened`) to auto-provision or unarchive review stacks for a repository outside the attacker's control.
- Send `membership` payloads to create/delete `Team`/`Membership`/`User` records, which is used to gate `Shipit.github_teams` authorization checks (e.g., `RepositoriesControllerTest` shows access is granted based on `Shipit.github_teams` membership) — this is an escalation into `Shipit.github_teams` authorization.

This satisfies the "unauthorized deploy" and "escalation into `Shipit.github_teams` authorization" High/Critical impact categories, because the only prerequisite is that *any one* configured GitHub organization in the multi-tenant `Shipit.github` config has a blank `webhook_secret` — a state the engine itself explicitly supports and documents as valid (`webhook_secret: # nil`).

### Likelihood Explanation
Likelihood depends on deployment configuration: it requires at least one organization entry in the multi-org `github:` config without a `webhook_secret`, while other tracked repositories belong to different, secured organizations. This is a supported, documented configuration (not a misuse of undocumented behavior) rather than a hypothetical one, and the webhook endpoint is unauthenticated/public by design (`skip_before_action :verify_authenticity_token`), so no credential, session, or repository write access is required to attempt the forgery — only knowledge of a Shipit instance's URL and organization list, both of which are visible/guessable.

### Recommendation
Bind the identity used to select the signature-verification secret to the same identity used to resolve which repository/stack is mutated: verify the signature using the config entry that corresponds to `repository.full_name`'s owner (or the sole configured org if in single-tenant mode), and reject webhooks where `repository.owner.login`/`organization.login` disagrees with `repository.full_name`'s owner segment. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in multi-organization configurations, or require `webhook_secret` to be mandatory whenever more than one organization is configured.

### Proof of Concept
1. Deploy Shipit with a multi-org config: `OrgSecure` (tracked repo `OrgSecure/prod-app`, `webhook_secret: <strong-secret>`) and `OrgOpen` (`webhook_secret:` left blank), per the pattern in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgOpen" }, "full_name": "OrgSecure/prod-app" },
  "after": "<attacker-chosen sha>",
  "ref": "refs/heads/master"
}
```
No `X-Hub-Signature` needs to be valid because `repository_owner` resolves to `OrgOpen`, whose `webhook_secret` is blank, so `verify_webhook_signature` in `lib/shipit/github_app.rb:76-77` returns `true` unconditionally.
3. `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) dispatches to the push handler, which resolves the target stack via `payload.dig('repository','full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) — i.e., `OrgSecure/prod-app` — and enqueues `GithubSyncJob` for that stack, despite the request never having been authenticated by `OrgSecure`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
