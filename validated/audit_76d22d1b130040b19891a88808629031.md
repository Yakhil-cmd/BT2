## Analysis: ERC20Transactor trusts boolean return value instead of measuring actual balance changes

The reported Solidity bug ("vault write function return values could not reflect real output") has a direct structural analog in this codebase's `ERC20Transactor`, which trusts an ERC20 contract's boolean `transfer()` return value as proof that the exact requested `amount` moved, without measuring the real balance delta via `balanceOf`. [1](#0-0) 

### Title
ERC20Transactor credits/debits XCM `AssetsInHolding` based on ERC20 `transfer()` boolean return instead of verified balance delta - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call a user-deployed ERC20 contract's `transfer()` via `pallet_revive::Pallet::<T>::bare_call`, and treat a decoded `true` return value as conclusive proof that exactly `amount` tokens moved. Neither function verifies the real balance change with `balanceOf`.

### Finding Description
`withdraw_asset_with_surplus` calls `transfer(checking_address, amount)` on the ERC20 contract identified by `asset_id` (an `H160` derived directly from an XCM `AccountKey20` asset id, per the transactor's own documentation: "asset ids of the form `{parents: 0, interior: X1(AccountKey20 {key, network})}` will be matched... and the corresponding `transfer` function will be called in the smart contract whose address is `key`" — i.e. *any* contract deployed via `pallet-revive` can be referenced this way, with no allowlist/registration in `ERC20Matcher`). On `is_success == true` it unconditionally constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` using the requested `amount`, not a measured delta: [2](#0-1) 

Symmetrically, `deposit_asset_with_surplus` calls `transfer(beneficiary, amount)` from the checking account and, on `Ok(true)`, simply drops the `what` holding (representing `amount`) as consumed, again without confirming the beneficiary's real balance increased by `amount`: [3](#0-2) 

A user can permissionlessly deploy an arbitrary ERC20-like contract through `pallet-revive` (no privileged role required) whose `transfer()` function returns `true` while moving less than `amount` (fee-on-transfer / deflationary / lying tokens — the exact analog of the cited vault bug returning misleading values). Because `Matcher::matches_fungibles` here (per the PR description shipping this feature, `pr_7762.prdoc`) accepts any `AccountKey20` as a valid ERC20 asset id, the attacker controls both the contract logic and the XCM message identifying that contract as the transacted asset — satisfying the "no privileged prerequisite" and "attacker-controlled input" requirements.

Notably, the codebase demonstrates awareness of exactly this failure mode elsewhere: `pallet_revive::impl_fungibles::{burn_from, mint_into}` also call `transfer()` and check the boolean, but then re-derive the real value via `<Self as fungibles::Inspect<_>>::balance(asset_id, who)` (i.e., `balanceOf`) rather than trusting the input `amount`: [4](#0-3) [5](#0-4) 

`ERC20Transactor::withdraw_asset_with_surplus` / `deposit_asset_with_surplus` do not apply this same `balanceOf`-verification mitigation, which is the exact recommendation from the cited report.

### Impact Explanation
If the checking account's `TransactAsset::withdraw_asset_with_surplus` credits `AssetsInHolding` with more than what actually moved into the checking account (because the ERC20 contract's `transfer()` lied), the XCM executor would treat the holding register as backed by real tokens when it is not. Subsequent `deposit_asset_with_surplus` on a normal/honest destination contract would then attempt to move the (over-stated) `amount` out of the checking account, which could fail or drain more from the checking account than the withdrawing account actually contributed — an accounting mismatch that can either freeze other users' legitimate balances in the checking account or allow one user's malicious-token withdrawal to be "recognized" by the XCM system as full value while only partial value was actually escrowed.

### Likelihood Explanation
Deploying an arbitrary `pallet-revive` contract is a normal, unprivileged user action, and the `ERC20Transactor`'s matcher (per its own PR documentation) accepts any `AccountKey20`-addressed contract as a valid XCM asset without registration/allowlisting. Constructing a `transfer()` function that returns `true` while transferring less than requested (e.g., taking a fee, or being a no-op honeypot token) is straightforward Solidity. The remaining uncertainty is whether the runtime's XCM configuration reaches this transactor with attacker-supplied token contracts in a way that produces measurable on-chain loss (e.g., across the full local-XCM execute → withdraw → deposit path), which I could not fully trace end-to-end (e.g., confirming exact `pallet_xcm::execute`/`Transact` reachability and the precise checking-account fund flow) within the available tool budget.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure `balanceOf(checking_address)` (or beneficiary) before and after the `bare_call`, and use the observed delta — not the requested `amount` — to construct/consume `AssetsInHolding`, mirroring the pattern already used in `substrate/frame/revive/src/impl_fungibles.rs::burn_from`/`mint_into`.

### Proof of Concept
No local reproduction was executed (out of scope for this ask-only investigation; only static code review tools were available). The finding is based on direct code inspection of `erc20_transactor.rs`, cross-referenced against the mitigated pattern in `impl_fungibles.rs` and the transactor's own documented permissionless matching behavior (`pr_7762.prdoc`). A concrete PoC would require: (1) a Rust integration test deploying a custom "lying" ERC20 fixture contract under `pallet-revive` whose `transfer()` returns `true` but transfers a reduced amount; (2) triggering `ERC20Transactor::withdraw_asset_with_surplus`/`deposit_asset_with_surplus` via a local XCM program (e.g. through `pallet_xcm::execute`) referencing that contract's address as the asset id; (3) asserting the resulting `AssetsInHolding` amount versus the real `balanceOf` delta on the checking account. This was not executed here; verifying full end-to-end reachability and exact bounty-program eligibility (Parity's live program scope for `assets-common`/asset-hub) requires further hands-on testing in a Devin session with repository access.

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}
