## Title
`TaskCommands#env` merges attacker-controlled `deploy_spec.machine_env` after `TASK_ID`/`GIT_COMMITTER_*`/`SHIPIT_USER`, allowing shipit.yml on a PR's own head ref to overwrite Shipit-computed identity keys - ([File: lib/shipit/task_commands.rb])

### Summary
`TaskCommands#env` builds the environment for `Command`/`PTY.spawn` by merging hashes in a fixed order, and `deploy_spec.machine_env` (sourced from the untrusted `shipit.yml` on the task's own working directory / commit) is merged after the hardcoded `SHIPIT_USER`, `TASK_ID`, `GIT_COMMITTER_NAME`, and `GIT_COMMITTER_EMAIL` keys, then `@task.env` is merged last on top of everything.

### Finding Description
The claimed binding is: `Command#env['TASK_ID'] == @task.id.to_s` and `Command#env['GIT_COMMITTER_EMAIL'] == (@task.user&.email || Shipit.committer_email)`, regardless of `deploy_spec.machine_env` content.

Tracing `lib/shipit/task_commands.rb`:
```ruby
def env
  super
    .merge(@stack.env)
    .merge(
      'SHIPIT_USER' => ...,
      'TASK_ID' => @task.id.to_s,
      'GIT_COMMITTER_NAME' => @task.user&.name || Shipit.committer_name,
      'GIT_COMMITTER_EMAIL' => @task.user&.email || Shipit.committer_email,
      ...
    )
    .merge(deploy_spec.machine_env)   # <-- attacker-controlled shipit.yml machine.environment
    .merge(@task.env)
end
```
`deploy_spec.machine_env` returns `config('machine', 'environment') || {}` [1](#0-0)  with no key allow-list or reserved-key filtering — unlike `filter_deploy_envs`/`filter_rollback_envs`, which explicitly run user-provided deploy/rollback variables through `EnvironmentVariables.with(env).permit(...)` [2](#0-1) . No equivalent `permit`/filtering call is applied to `machine_env` before it is merged in `TaskCommands#env` [3](#0-2) .

Since `Hash#merge` lets the right-hand operand win, `deploy_spec.machine_env` — read from `DeploySpec::FileSystem.new(@task.working_directory, @stack)`, i.e., the checked-out ref for the task, which for a ReviewStack-triggered `install_dependencies`/`perform` run is the PR author's own branch content — silently overwrites `TASK_ID`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `SHIPIT_USER`, `EMAIL`, `SHIPIT_LINK`, `BUNDLE_PATH`, and `IGNORED_SAFETIES`. This confirms the binding is **broken**: an attacker who controls `shipit.yml`'s `machine.environment` on their own branch can set `TASK_ID`, `GIT_COMMITTER_NAME`, or `GIT_COMMITTER_EMAIL` to arbitrary values, and those attacker values (not the Shipit-computed ones) reach the final `Command#env` passed to `unbundled_env`/`PTY.spawn` [4](#0-3) .

None of the listed guards (`verify_signature`, `ExplicitParameters`, `require_permission!`, model validators, `EnvironmentVariables#permit`) intervene here because `machine_env` is never passed through `EnvironmentVariables#permit` at all — that filtering only exists for `deploy`/`rollback` "variables" sections, not for `machine.environment`.

### Impact Explanation
Overwriting `GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` only affects the *content* of these environment variables as consumed by whatever git/deploy steps the task runs in its own working directory/container for the task the attacker themselves triggered (their own ReviewStack). It does not let the attacker read another repository's secrets, does not bypass authentication, and does not let them run commands they could not already run — they already fully control the arbitrary shell commands executed via `dependencies_steps!`/`steps` in their own `shipit.yml` on their own branch (that's the documented, intended trust model for ReviewStacks: the PR author's shipit.yml drives their own review-stack build). The forged `GIT_COMMITTER_EMAIL`/`TASK_ID`/`SHIPIT_LINK` values only corrupt metadata within the attacker's own task/stack execution, not another tenant's stack, commit, or task, and no credential (`GITHUB_TOKEN`, `github_access_token`, `api_clients_secret`) is exposed by this specific merge-order issue.

### Likelihood Explanation
Trivial to trigger (just set `machine.environment.TASK_ID` etc. in `shipit.yml` on a PR branch) but the blast radius is confined to the attacker's own already-fully-controlled task execution environment (they already choose the shell commands run in that environment). This does not meet the Critical/High impact bar defined in scope (RCE reaching a resource the attacker didn't already control, cross-tenant mutation, auth bypass, credential exfiltration, or authorization escalation) — it's a self-inflicted metadata corruption within the attacker's own sandboxed task, which the threat model already treats as attacker-controlled.
