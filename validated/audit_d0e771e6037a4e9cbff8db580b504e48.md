### Title
Hardcoded `elapsedTimeWhenZero` floor lets a unit poster evade TPS-fee-based anti-spam throttling - ([File: storage.js])

### Summary
`storage.js` computes the "transactions per second" (TPS) rate used to determine the mandatory `tps_fee` that every unit must pay after the v4 upgrade. Whenever the time delta between a unit and its referenced `last_ball` is exactly `0`, the code falls back to a hardcoded constant `elapsedTimeWhenZero` instead of treating the burst as an (near-)infinite rate. This is structurally the same bug class as GHSA-mcpw-cp35-p3h8: a hardcoded fallback value neutralizes a rate/aging-based throttling mechanism, letting a party who controls the relevant timing value bypass the intended penalty.

### Finding Description
`elapsedTimeWhenZero` is defined as a constant `1` regardless of network mode: [1](#0-0) 

It is used as the divisor floor in the three TPS computations that drive the anti-spam `tps_fee` mechanism:
- `getFinalTps` (post-hoc fee charged to a stabilized unit): [2](#0-1) 
- `getLocalTps` (fee required at submission time, called from `validateTpsFee`): [3](#0-2) 
- `getCurrentTps` (network-wide current-load fee floor): [4](#0-3) 

In each case, `elapsed = (timestamp_a - timestamp_b) || elapsedTimeWhenZero`, then `tps = count / elapsed`. A unit's own `timestamp` field is author-controlled and only bounded from above (`timestamp` must not be more than `max_seconds_into_the_future_to_accept` seconds in the future); there is no lower bound enforced against `last_ball`'s timestamp: [5](#0-4) 

An unprivileged unit poster can therefore choose `objUnit.timestamp` to exactly equal the timestamp of the `last_ball_unit` they reference. This forces `elapsed` to `0`, which JavaScript's `||` treats as falsy, so it is replaced by the fixed constant `1` instead of representing the true (near-zero) elapsed time. The result is that `tps = count / 1 = count`, an artificially deflated rate, instead of the very large (or undefined/"infinite") rate that should be computed for a burst of units submitted with no real elapsed time. This deflated TPS feeds directly into `getFinalTpsFee`/`getLocalTpsFee`/`getCurrentTpsFee`, which are enforced in `validateTpsFee`: [6](#0-5) 

Because the floor is a fixed `1` rather than a value proportional to real congestion, a poster can repeatedly craft units whose timestamp equals their referenced `last_ball`'s timestamp to keep the computed local/current TPS — and thus the mandatory `tps_fee` — pinned near its minimum, no matter how many units they actually push through in that window.

### Impact Explanation
The TPS-fee mechanism exists specifically to make unit throughput financially self-limiting (higher real-world submission rate ⇒ higher required `tps_fee`, exponential per `getFinalTpsFee`/`getCurrentTpsFee`). By reliably forcing `elapsed=0 → elapsedTimeWhenZero=1` for every unit whose timestamp is set equal to `last_ball`'s timestamp, an attacker defeats this throttle and can flood the DAG with many low-fee units, degrading the network's ability to process/confirm legitimate units in a timely manner — matching the "network unable to confirm new units" impact category. It also causes `tps_fees_balances` (used in `updateTpsFees`) to be updated with an artificially low `actual_tps_fee`, meaning fee accounting deviates from the value the true submission rate would require.

### Likelihood Explanation
Any unprivileged unit poster fully controls their own unit's `timestamp` field and can freely choose it to equal the `last_ball_unit`'s timestamp (only an upper future bound is enforced, no lower bound); this requires no special privileges, race conditions, or cooperation from other nodes, so the condition is trivially reproducible on every unit submission.

### Recommendation
Do not use a fixed constant as a floor for zero elapsed time in `getFinalTps`/`getLocalTps`/`getCurrentTps` in `storage.js`. Instead, when the computed elapsed time is `0`, treat the rate as effectively unbounded (i.e., require the maximum fee tier, or use a strictly-decreasing sub-second/precision-based elapsed value) so that bursts of units referencing the same `last_ball` timestamp cannot be used to bypass the TPS-fee throttle.

### Proof of Concept
1. Compose a unit whose `last_ball_unit` is the current stable tip, and set `objUnit.timestamp` equal to that tip's `timestamp` (allowed since validation only checks the timestamp is not too far in the future — `validation.js` lines 280-287).
2. Submit multiple such units in quick succession, each referencing the same or an updated `last_ball` with a matching timestamp.
3. Observe that `storage.getLocalTps`/`getCurrentTps` compute `elapsed = elapsedTimeWhenZero (=1)` for each, keeping `tps_fee` at its floor value in `validateTpsFee` (`validation.js` lines 1070-1097) regardless of the actual submission rate, allowing sustained low-fee flooding of the network.
