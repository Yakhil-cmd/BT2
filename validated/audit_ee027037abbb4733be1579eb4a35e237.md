### Title
Rollback tasks auto-triggered on deploy abort/revert inherit the aborted deploy's environment unfiltered by the rollback variable whitelist - (File: app/models/shipit/deploy.rb)

### Summary
`Shipit::Api::RollbacksController#create` correctly restricts the environment variables a rollback may run with by calling `stack.filter_rollback_envs(params.env)` before triggering a rollback [1](#0-0) . However, the two code paths that *automatically* trigger a rollback — `Deploy#trigger_revert_if_required` (called after a deploy transitions `to: :aborted`) and `Deploy#trigger_revert` — bypass this whitelist entirely and carry forward the aborted deploy's own `env` attribute (which was only filtered against the deploy's variable whitelist, `deploy_variables`) directly into the new `Rollback` record [2](#0-1) [3](#0-2) . `Deploy#build_rollback`, used by `trigger_rollback`, likewise stores `env: env.to_h` with no call to `filter_rollback_envs` at all [4](#0-3) . The unfiltered env is later merged unconditionally into the spawned process's environment by `TaskCommands#env` (`.merge(@task.env)`) [5](#0-4) .

### Finding Description
This is the same bug class as the report's "missing state check before repeating a privileged action": here, instead of a missing "already withdrawn" flag, there's a missing re-validation of the applicable allowlist when an entitlement (an environment variable value) crosses from one execution context (a deploy, governed by `deploy_variables`) into another (a rollback, governed by the narrower `rollback_variables`).

`DeploySpec#rollback_variables` is explicitly designed to be configurable independently from `deploy_variables` in `shipit.yml`:
```
def rollback_variables
  if config('rollback', 'variables').nil?
    deploy_variables
  else
    Array.wrap(config('rollback', 'variables')).map(&VariableDefinition.method(:new))
  end
end
``` [6](#0-5) 

This lets a stack owner intentionally forbid certain dangerous variables (e.g., ones that skip safety checks, alter migration behavior, or change destructive script behavior) from being settable during a rollback, while still permitting them for a normal deploy. The equality this is supposed to enforce is:

`env keys spawned in a rollback task == env keys permitted by stack.rollback_variables`

The `Api::RollbacksController#create` path enforces this equality via `filter_rollback_envs`. But `Deploy#trigger_revert_if_required` (invoked automatically via the `aborted` state-machine transition) and `Deploy#trigger_revert` instead spawn the rollback with:

`env keys spawned in a rollback task == env keys permitted by stack.deploy_variables` (the aborted deploy's own, already-deploy-filtered env)

Because `deploy_variables` and `rollback_variables` can differ, any deploy-permitted actor who can set env vars on a deploy (via `Api::DeploysController#create`, filtered by `filter_deploy_envs` [7](#0-6) ) can get a value into a variable that is deliberately excluded from `rollback_variables`, then cause (or wait for) that deploy to abort. The automatic revert/rollback that follows will run with that variable set in the spawned rollback process, even though the rollback API itself would have rejected it outright with a `NotPermitted` error [8](#0-7) .

### Impact Explanation
This breaks the deployment-trust binding between "environment key permitted" (for the target execution context) and "environment key spawned" (in the actual subprocess), letting an actor who is not permitted to run a rollback with a given variable achieve exactly that outcome by routing it through a deploy-then-abort flow. Depending on what the excluded rollback variable controls (e.g., disabling a safety check, or a variable interpolated into a shell command via `Command#interpolate_environment_variables`), this can result in an unauthorized/unsafe rollback execution, matching the report's core theme of a privileged action being repeatable/executable outside its intended guard rail.

### Likelihood Explanation
Requires only standard `deploy` permission on the stack (the same permission already required to trigger a rollback through the proper API) plus a `shipit.yml` configuration where `rollback.variables` is a strict subset of `deploy.variables` — a configuration explicitly supported and documented for safety separation. No repository write access, no additional privilege, and no session/token compromise is needed beyond what is already required to trigger deploys.

### Recommendation
Route `Deploy#build_rollback`, `Deploy#trigger_revert`, and `Deploy#trigger_revert_if_required` through `stack.filter_rollback_envs` (the same call used by `Api::RollbacksController#create`) before assigning `env` on the new `Rollback`, rather than reusing the deploy's already-deploy-filtered env verbatim.

### Proof of Concept
1. Configure `shipit.yml` with `deploy.variables` including `DANGEROUS_VAR` but `rollback.variables` excluding it.
2. As a user with `deploy` permission, trigger a deploy via `POST /api/stacks/:id/deploys` with `env: { DANGEROUS_VAR: "1" }` — accepted because `filter_deploy_envs` permits it [7](#0-6) .
3. Cause the deploy to abort (or configure `rollback_once_aborted`), triggering `Deploy#trigger_revert_if_required` → `trigger_rollback`/`trigger_revert` with `env:` taken directly from the deploy [2](#0-1) .
4. The resulting `Rollback` task runs with `DANGEROUS_VAR=1` in its spawned process environment via `TaskCommands#env` [5](#0-4) , even though calling `POST /api/stacks/:id/rollbacks` with the same `env` would have been rejected with `Variables DANGEROUS_VAR have not been whitelisted`.

      rollback = Rollback.create!(
        user_id:,

      stack.emit_lock_hooks
      rollback
    end

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
