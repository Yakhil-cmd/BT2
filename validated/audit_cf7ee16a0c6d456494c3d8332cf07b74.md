### Title
Decrypted device-message plaintext (including private-payment spend secrets) is written unredacted to the process log - (File: device.js)

### Summary
`decryptPackage()` in `device.js` logs the full plaintext of every decrypted device message with `console.log("decrypted: "+decrypted_message)` [1](#0-0)  before the message is even parsed or type-checked. This function is invoked on every inbound `hub/message` received from a paired correspondent device (or relayed via a hub) with no way for the sending peer to opt out of logging on the receiver's side [2](#0-1) . This mirrors GHSA-vcmm-ppqx-95ch / CVE-2016-1000221, where Logstash wrote sensitive HTTP `Authorization` data to log files that were never meant to hold secrets — here, ocore writes the entire decrypted body of every wallet-to-wallet protocol message (private-payment payloads with blinding factors, `sign` requests containing unsigned units and `private_payloads`, pairing data, textcoin mnemonics carried in private asset transfers, etc.) into the node's stdout/log stream.

### Finding Description
Every device message received over the wire is handled in `handleJustsaying()`'s `'hub/message'` case, which calls `decryptPackage(objDeviceMessage.encrypted_package)` immediately after basic structural/signature checks on the *outer* envelope [3](#0-2) . Inside `decryptPackage`, once AES-128-GCM decryption succeeds, the raw plaintext string is dumped to the console before `JSON.parse` is even attempted: [4](#0-3) 

This plaintext `json` object is the actual application-level payload exchanged between paired wallets, and per `handleMessageFromHub()` in `wallet.js` it can legitimately contain:
- `sign` requests, which embed `unsigned_unit` and `private_payloads` — the latter containing `outputs[].blinding` and `outputs[].amount`, i.e. the exact secret blinding factors that let one output owner prove control of a private-asset output [5](#0-4) .
- `private_payments`/`private_payment_chains`, which carry the full chain of private-asset transfer payloads (`payload.inputs`, `payload.outputs`, blinding, spend proofs) [6](#0-5) .
- Textcoin private-asset transfers, where a `mnemonic` (the spending credential for an address holding real funds) is embedded in a stored/forwarded private payload [7](#0-6) [8](#0-7) .

Because `console.log` output is typically captured to a persistent, world/operator-readable log file (the exact bug class in the CVE), any process, log aggregator, crash reporter, or party with read access to the node's logs gains access to spend-enabling secrets (blinding factors, mnemonics, unsigned unit contents used for multi-sig cosigning) that were supposed to remain confidential between the two paired devices. Unlike the outer envelope (pubkey, signature, hub-relayed ciphertext), which the hub is already assumed to see, this plaintext is specifically the part of the protocol designed to be hidden from the hub and any third party — logging it defeats that design guarantee.

Reachability: a device message is delivered whenever any paired correspondent (or, in a hub scenario, anyone who can get a message routed to the victim's hub inbox for a device address the victim has ever paired with) sends a `hub/message`/`hub/deliver` addressed to the victim; `handleJustsaying` accepts it, verifies only the outer envelope, and unconditionally decrypts+logs the body [9](#0-8) , satisfying the "paired device" reachable-actor requirement.

### Impact Explanation
If the console/log output is exposed (log aggregation, crash dumps, shared hosting, misconfigured permissions, support-ticket log pastes — the same class of exposure the CVE addresses), an attacker who obtains it can extract:
- Blinding factors/amounts for private-asset outputs sent to the victim, potentially enabling forged claims or de-anonymization/double-spend attempts on private-asset transfers that rely on these values remaining secret between counterparties.
- Textcoin mnemonics embedded in private payment transfers, which are literal private keys and allow immediate, unauthorized spending of any funds sitting on that mnemonic-derived address.
- Full `unsigned_unit`/`sign` request contents for multisig flows, which could aid an attacker in reconstructing or manipulating a pending multi-party transaction they were not meant to see.

This is a confidentiality failure with a direct path to fund theft (via leaked mnemonics/blinding secrets), which maps to "unauthorized spending" / "AA or wallet fund loss" impact categories.

### Likelihood Explanation
Any correspondent device the victim has ever paired with (a normal, low-privilege relationship established via a pairing code) can trigger delivery of a message that gets decrypted and logged; no special hub privilege or network position is required. The logging occurs unconditionally on the receiving node for every processed message, so exploitation only requires the attacker to obtain read access to the victim node's logs at some point — a realistic scenario for hosted/cloud-run wallets, shared servers, or nodes using third-party log shipping (directly analogous to how the Logstash CVE was exploited).

### Recommendation
Remove or heavily redact the `console.log("decrypted: "+decrypted_message)` statement in `decryptPackage()` [10](#0-9) . At minimum, do not log full message bodies; if debug logging is required, strip/mask fields known to carry secrets (`private_payloads`, `blinding`, `mnemonic`, `unsigned_unit.authors[].authentifiers`) before logging, and gate any remaining diagnostic output behind an explicit debug flag that defaults to off in production.

### Proof of Concept
1. Pair two ocore wallets, A (victim) and B (attacker-controlled device).
2. From B, send a `private_payments`/`sign` message to A containing a private-asset payload with `outputs[].blinding` set, or a textcoin transfer whose payload embeds a `mnemonic`.
3. On A's node, observe stdout/log output produced by `device.js`'s `decryptPackage`: the full plaintext JSON, including the blinding factor / mnemonic, is printed via `console.log("decrypted: "+decrypted_message)` [1](#0-0) .
4. Anyone with read access to A's log file (log aggregator, hosting provider, misconfigured permissions) can now extract the blinding factor or mnemonic and, in the mnemonic case, immediately spend any funds on that derived address — with no interaction from A required.

function expandMnemonic(mnemonic) {
	var addrInfo = {};
	mnemonic = mnemonic.toLowerCase().split('-').join(' ');
	if ((mnemonic.split(' ').length % 3 !== 0) || !Mnemonic.isValid(mnemonic)) {
		throw new Error("invalid mnemonic: "+mnemonic);
	}
	mnemonic = new Mnemonic(mnemonic);
	addrInfo.xPrivKey = mnemonic.toHDPrivateKey().derive("m/44'/0'/0'/0/0");
	addrInfo.pubkey = addrInfo.xPrivKey.publicKey.toBuffer().toString("base64");
	addrInfo.definition = ["sig", {"pubkey": addrInfo.pubkey}];
	addrInfo.address = objectHash.getChash160(addrInfo.definition);
	return addrInfo;
}
