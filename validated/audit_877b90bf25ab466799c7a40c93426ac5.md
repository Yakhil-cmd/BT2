### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook delivery against the GitHub organization derived from the payload's `repository.owner.login`, but `StatusHandler#process` then writes the resulting GitHub status to **any** `Commit` row matching the payload's `sha`, with no filter tying that commit back to the repository/organization whose signature was actually verified. This is the same class of bug as the Trader Joe report: a value is trusted and acted upon (`params.sha` → commit lookup and mutation) without being bound to the field that was actually authenticated/verified (`repository.owner.login`, which only selects the webhook secret used for the HMAC check).

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the webhook secret) using `repository_owner`, computed from the payload itself: [1](#0-0) [2](#0-1) 

Once the signature is verified for *that organization's* webhook secret, `Shipit::Webhooks.for_event(event)` dispatches the parsed payload to `StatusHandler#process`: [3](#0-2) 

`StatusHandler` looks up commits purely by `sha`, with **no repository or stack scoping**, unlike `PushHandler`/`Handler`, which resolve `stacks` via `Repository.from_github_repo_name(repository_name)`: [4](#0-3) 

Because `Commit.where(sha: params.sha)` is global across all repositories/stacks tracked by this Shipit instance, a validly-signed `status` webhook from organization A's repository can write/update a `Status` on a `Commit` belonging to an entirely different repository/stack (organization B), as long as a commit with that SHA exists there too (e.g., shared history from a fork, a common cherry-picked commit, or a common empty/initial commit). The binding that breaks is: *the organization whose webhook signature was verified* ≠ *the repository/stack whose commit status is actually mutated*.

### Impact Explanation
`Commit#create_status_from_github!` persists a `Status` that feeds into `CommitChecksStatus`/deploy gating logic used to decide whether a commit is safe to merge or ship. If an attacker administers a repository under an organization that is a legitimate, independent tenant of this same multi-tenant Shipit installation (a normal, unprivileged position relative to *other* tenants' stacks), they can cause GitHub to deliver a validly-signed `status` webhook (by pushing a commit and setting a status via the GitHub API on their own repo) whose `sha` collides with a commit tracked by a different, unrelated stack. This lets them inject a forged `success`/`failure` status onto another organization's commit, which can flip CI-gating used before merges/deploys — a cross-tenant write and a path toward an unauthorized deploy on a stack the attacker has no authorization over.

### Likelihood Explanation
Exploitability is bounded by the need for a SHA collision between the attacker's repository and the victim's repository — infeasible for arbitrary content but realistic for shared history: forked repositories, repositories seeded from the same template/boilerplate, or squash/cherry-picked commits common across an organization's projects. In any single- or multi-tenant Shipit deployment where distinct GitHub orgs/repos are managed, this is reachable by any GitHub user with push/status-setting rights on their own tracked repository — no Shipit session, API token, or webhook secret needed, since the signature is real (produced by GitHub itself for the attacker's own repo).

### Recommendation
Scope the `StatusHandler` (and any other handler that looks up records purely by `sha`) to the repository identified in the payload, mirroring `Handler#repository_name`/`Handler#stacks`, e.g. filter `Commit` through `stacks` (or the resolved `Repository`) before applying `where(sha:)`, so a status update can never cross repository/stack boundaries regardless of SHA collisions.

### Proof of Concept
1. Attacker's GitHub organization "Attacker-Org" has the Shipit GitHub App installed and is a legitimate, unprivileged tenant of the shared Shipit instance.
2. Attacker pushes a commit to their own repo whose SHA is known to also exist in Victim-Org's tracked repository (e.g., via a fork or shared template commit), then sets a commit status (`success`) on it via the GitHub API.
3. GitHub computes a valid `X-Hub-Signature` using Attacker-Org's webhook secret and POSTs to `/github/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = "Attacker-Org" and verifies the signature successfully: [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which also matches the colliding commit under Victim-Org's stack, and calls `create_status_from_github!`, forging a CI status for that stack: [3](#0-2)
