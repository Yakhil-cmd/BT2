### Title
Webhook signature verification binds only the JSON body via HMAC, not the specific `organization` field used to select the secret vs. the `repository.full_name` field used to select the write target - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization config (and therefore the `webhook_secret` to check the HMAC against) using `repository_owner`, a value read straight out of the **unverified** request body. The event handler that performs the actual write (e.g. `PushHandler`) instead resolves its target `Stack`/`Repository` from a *different* field of that same unverified body: `repository.full_name`. Because the HMAC only proves "this body was signed by whichever org's secret produced a match," and `verify_webhook_signature` trivially returns `true` when the resolved org has no `webhook_secret` configured, nothing binds "the organization whose secret validated the request" to "the repository the handler actually mutates."

### Finding Description
`verify_signature` derives the signing organization from the payload before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`repository_owner` is read from the attacker-controlled JSON body, not from any authenticated source. `verify_webhook_signature` itself only proves the raw body matches the secret for *that chosen* organization, and explicitly bypasses verification entirely when no secret is configured: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Meanwhile, the handler that performs the actual write resolves its target repository/stack from an entirely different, independently-controlled field of the same JSON body: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process` then triggers a real state-changing action (`stack.sync_github(expected_head_sha: params.after)`) against the stack derived from `repository.full_name`: [5](#0-4) 

The equality that the signature is supposed to enforce is:
`organization whose secret validated the HMAC` == `organization that owns the repository being written to`.

Because `repository.owner.login` (used for verification) and `repository.full_name` (used for the write) are two independent, attacker-supplied fields inside the same unsigned-until-verified JSON body, and because any organization configured in Shipit with a blank `webhook_secret` causes `verify_webhook_signature` to return `true` unconditionally (as shown by the default templates, e.g. `config/secrets.development.shopify.yml` shipping `webhook_secret: # nil`), an attacker can craft a payload where:
- `repository.owner.login` = an org configured in this Shipit instance with no webhook secret (verification trivially passes, or, for orgs with a secret, is checked only against that org's own secret, which says nothing about which repo is actually acted upon), and
- `repository.full_name` = an arbitrary *other* org/repo tracked by this Shipit instance.

The push handler then syncs/dispatches against a stack belonging to a repository the "authenticating" organization never controls.

### Impact Explanation
This breaks the deployment-trust binding "an organization that authenticated versus the repository that is written": webhook events for one organization's endpoint can be forged to act on stacks belonging to a completely different tracked repository, without possessing that repository's real webhook secret. Depending on which handler is invoked (`push`, `check_suite`, `status`, `pull_request/*`, `membership`), this can trigger unauthorized syncs, merge-request state changes, or (via `ContinuousDeliveryJob`/`sync_github`) unauthorized deploy triggers against a repository the attacker does not control — matching the "unauthorized deploy" / "cross-repository writes" class of impact.

### Likelihood Explanation
Exploitability requires a multi-tenant Shipit deployment (multiple GitHub orgs/apps configured, as shown by `config/secrets.development.shopify.yml`) where at least one configured organization has no `webhook_secret` set (the documented/default state), or where an attacker otherwise has any valid webhook secret for at least one organization. No privileged Shipit account, `ApiClient` token, or repository write access is required — only knowledge of the target `repository.full_name` string, which is normally public. This is a design gap in `verify_signature`/`repository_owner` rather than a one-off implementation bug, making it consistently reachable whenever such a configuration exists.

### Recommendation
Bind the signature verification and the write target to the same trusted value:
- After verifying the HMAC succeeded with a real (non-blank) secret, re-derive/confirm that `repository.full_name`'s owner matches the organization whose secret validated the signature, rejecting the event otherwise.
- Do not allow `verify_webhook_signature` to return `true` for organizations with a blank `webhook_secret` when the payload's `repository.full_name` refers to a repository under a different, secret-protected organization.
- Consider requiring `webhook_secret` to be present for every configured organization in production, and fail closed if it's missing.

### Proof of Concept
1. Configure Shipit with two organizations: `org-a` (no `webhook_secret`, i.e. blank) and `org-b` (has a tracked `Stack` for `org-b/target-repo`, with its own strong `webhook_secret`).
2. As an unauthenticated external attacker, POST to `/webhooks` with header `X-Github-Event: push` and a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/target-repo"
  }
}
```
No `X-Hub-Signature` header value needs to correctly authenticate against `org-b`'s secret.
3. `verify_signature` calls `Shipit.github(organization: "org-a")`, whose `verify_webhook_signature` returns `true` immediately because `org-a`'s `webhook_secret` is blank (`return true unless webhook_secret`).
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/target-repo")`, finds the real `org-b` stack, and calls `stack.sync_github(expected_head_sha: ...)` — a write triggered without ever supplying a valid signature for `org-b`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
