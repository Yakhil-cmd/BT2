### Title
Cross-repository CI status forgery via unscoped SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `WebhooksController` verifies the GitHub webhook signature using the organization/app config selected from the payload's `repository.owner.login` (or `organization.login`) field [1](#0-0) , but `StatusHandler#process`, which runs after that check, looks up commits to update **purely by SHA, with no scoping to the repository/organization that the signature actually authenticated**: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . This breaks the binding: `organization authenticated by verified webhook signature == repository/stack whose Commit status is written`.

### Finding Description
`WebhooksController#verify_signature` selects the `GithubApp`/secret to validate against based on `repository_owner`, itself taken straight from the untrusted JSON payload (`params.dig('repository','owner','login') || params.dig('organization','login')`) [3](#0-2) . This design implicitly assumes that once the signature is verified for organization X, the rest of the payload (including any repository/commit identifiers used by the handler) also pertains to organization X's own resources.

`StatusHandler`, however, never checks `payload['repository']['full_name']` against the `Commit`'s owning `Stack`/`Repository`. It queries `Commit.where(sha: params.sha)` across the **entire database**, independent of repository or organization [2](#0-1) . Because Git commit SHAs are content-addressed (hash of tree + parents + metadata), any actor who can reconstruct byte-identical commit content (trivial for public repositories/forks, or for private repos whose history the attacker can otherwise learn) can produce an identical SHA in a different repository they control. If that attacker's repository is configured in Shipit under an org/App whose webhook secret they know (e.g., their own low-security org, or one with a blank `webhook_secret`, which `GithubApp#verify_webhook_signature` explicitly treats as "always verified" — `return true unless webhook_secret` [4](#0-3) ), they can send a legitimately-signed `status` webhook event referencing that SHA with `state: "success"`. `StatusHandler` will then create a `Status` on **every** `Commit` row across the whole Shipit instance sharing that SHA, regardless of which `Stack`/`Repository`/organization the attacker was actually authenticated for.

`Commit#deployable?` relies on this same-instance status: `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [5](#0-4) , where `success?` is delegated to the commit's `status`, which is derived from `statuses`/`release_statuses` written by `StatusHandler`. Forging a success status on a commit belonging to another organization's `Stack` can make that commit `deployable?`, allowing an unrelated org's low-trust webhook to influence whether a completely different, protected `Stack` is eligible for deploy.

The `CheckSuiteHandler` avoids this exact issue because it scopes lookups through `stacks` (which is itself derived from `payload.dig('repository','full_name')`) before matching by SHA [6](#0-5) , confirming that repository-scoping is the intended and available pattern that `StatusHandler` fails to apply.

### Impact Explanation
This is High impact: it is an unauthenticated (from the target org's perspective) write of CI/status state into another organization's `Stack`/`Commit` records, which is explicitly called out impact category — "escalation into authorization" / "unauthorized deploy" adjacent, since `success?`/`deployable?` gates automatic and manual deploys. An attacker controlling any org/repo configured in the same Shipit instance (a normal, intended, unprivileged tenant of a multi-org Shipit install) can forge a CI-success status for a commit belonging to a different organization's stack, undermining the CI gating for deploys/merge queue eligibility on that other stack, without ever holding credentials, an `ApiClient` token, or repository write access to the target organization.

### Likelihood Explanation
Likelihood is realistic in the documented multi-organization deployment mode (`config/secrets.yml` supports multiple `github:` orgs, each with its own webhook), which is a supported, documented configuration [7](#0-6) . An attacker only needs: (1) their own org/repo registered as a Shipit stack (fully within their control), and (2) a commit whose SHA collides with a target commit — achievable by cloning a public commit's tree/parent/metadata into their own repo, since Git SHAs are reproducible from public commit contents. No exploitation of GitHub itself is required; the collision is a content match, not a hash break.

### Recommendation
`StatusHandler#process` (and any other handler matching purely by SHA) must scope the `Commit` lookup to the repository named in the verified payload, mirroring the pattern used by `Handler#stacks` / `CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
This ensures the equality `organization authenticated by verified signature == repository/stack whose Commit is mutated` holds.

### Proof of Concept
1. Configure Shipit for two organizations, `org-a` (target, e.g. production stack) and `org-b` (attacker-controlled), per the documented multi-org `secrets.yml` format.
2. Attacker creates a commit in a repo under `org-b` with identical tree/parent/author/committer/timestamp/message as a real commit `C` already tracked in `org-a`'s stack, producing the same SHA.
3. Attacker's GitHub App (org-b) sends a legitimately-signed `status` webhook: `{"sha": "<C's sha>", "state": "success", "repository": {"owner": {"login": "org-b"}, ...}}`.
4. `WebhooksController#verify_signature` validates the signature using `org-b`'s webhook secret — succeeds, since it is a genuine event from org-b's own repo [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds `C` (belonging to `org-a`'s stack), and creates a `success` status on it [2](#0-1) .
6. `C.deployable?` on `org-a`'s stack now returns `true` if it wasn't blocked by other required statuses, enabling an unauthorized deploy trigger for `org-a`.

```markdown
## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
  - Repository permissions:
    - Checks: Read & write
    - Commit statuses: Read-only
    - Contents: Read & write (to allow merging)
    - Deployments: Read & write
    - Issues: Read & write (to allow closing related issues on merge)
    - Metadata: Read-only
    - Pull requests: Read & write
```
