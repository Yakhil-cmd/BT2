### Title
Global, unscoped `BUNDLE_PATH` allows one review-stack task to poison the shared bundler gem cache consumed unfiltered by every other stack's `bundle install` — (File: `lib/shipit/task_commands.rb`, `app/models/shipit/deploy_spec.rb`, `app/models/shipit/deploy_spec/bundler_discovery.rb`, `lib/shipit/command.rb`)

### Summary
`TaskCommands#env` merges the attacker-controlled `deploy_spec.machine_env` (sourced unfiltered from the checked-out PR branch's `shipit.yml`) directly into the command environment that reaches `PTY.spawn`, with no allowlist analogous to `EnvironmentVariables.permit`. The `BUNDLE_PATH` default resolved by `DeploySpec.bundle_path` is a single host-wide constant (`Rails.root.join('data', 'bundler')`), not scoped per stack or repository, so a malicious `bundle install` payload triggered by one repository's review-stack task can plant files in that same directory that get loaded by an unrelated repository's future `bundle install`/`bundle exec` invocation.

### Finding Description
The broken binding: for any two stacks `A` and `B` on the same Shipit host, `TaskCommands.new(taskA).env['BUNDLE_PATH'] == TaskCommands.new(taskB).env['BUNDLE_PATH'] == Rails.root.join('data', 'bundler').to_s` — an isolation boundary that should not exist (each stack's dependency install path should be exclusive to that stack) but does, because `DeploySpec.bundle_path` [1](#0-0)  hard-codes one global path shared by every task on the host, used both as the fallback in `discover_machine_env` [2](#0-1)  and in the generated `bundle config set --local path` step [3](#0-2) .

In `TaskCommands#env`, the merge order is: stack env → hard-coded safe defaults (including a `BUNDLE_PATH` default) → `deploy_spec.machine_env` → `@task.env`, so anything the checked-out repository's `shipit.yml` `machine.environment` key sets (which is read straight from `config('machine', 'environment')` with **no `EnvironmentVariables.permit` allowlist**, unlike `deploy`/`rollback`/task `variables`) overrides the safe default and reaches the spawned process unchanged: [4](#0-3) . This merged hash flows into `Command#unbundled_env`, which stringifies and injects `@env` with zero key filtering before calling `PTY.spawn`: [5](#0-4) [6](#0-5) .

Exploit flow: an unprivileged user opens a PR against a repository configured with `provisioning_behavior: prevent_with_label` (default provisioning path, no label needed). Their PR branch contains a `Gemfile` (making `bundler?` true) and a vendored gem with a malicious `extconf.rb`/native extension or Rakefile hook. `discover_dependencies_steps` auto-generates a `bundle install` step for the review-stack's `TaskCommands#install_dependencies` [7](#0-6) . Because `bundle_path` resolves to the same global `Rails.root.join('data', 'bundler')` for every stack, the malicious `extconf.rb`/Rakefile code, once executed during "their own" review-stack's dependency install, writes/overwrites files inside that shared cache (e.g. hijacking a commonly-depended-upon gem version present in many stacks' `Gemfile.lock`). Any later, unrelated stack (a different repository/tenant) that runs `bundle install` or `bundle exec` and resolves to that same poisoned gem executes the attacker's payload under that other stack's task context — with access to that stack's checkout, secrets, and `GITHUB_TOKEN`.

Existing guards do not stop this: `filter_deploy_envs`/`filter_rollback_envs`/`TaskDefinition#filter_envs` only gate the *deploy/rollback/task* `variables`, not `machine.environment` [8](#0-7) ; `EnvironmentVariables#permit` is simply never invoked for `machine_env` [9](#0-8) ; `Command#unbundled_env` has no key denylist/allowlist at all.

### Impact Explanation
A payload authored for one repository's review stack can mutate/poison a resource (the shared bundler cache) consumed by another repository's stack, satisfying the Critical class "a payload for one repository mutating another's stack." Execution occurs on the Shipit deploy host via `Command`/`PTY.spawn`, potentially exfiltrating another stack's `GITHUB_TOKEN`/deploy secrets or triggering unauthorized actions from that stack's context. This is repeatable against any repository on the same host whose stacks happen to share overlapping gem dependencies with the attacker's crafted `Gemfile.lock`, and the blast radius spans all tenants sharing the Shipit instance's `data/bundler` directory.

### Likelihood Explanation
Preconditions are minimal: `review_stacks_enabled` and `provisioning_behavior: prevent_with_label` (a documented, common configuration) on the target repository, no maintainer approval or label required to trigger provisioning, and a `Gemfile` in the attacker's own PR branch. The attacker needs some knowledge of a gem name/version likely shared with other stacks on the host to maximize blast radius, but even opportunistic poisoning of frequently-used gems (`rake`, `bundler` itself, common gems) is plausible on a shared multi-tenant Shipit deployment. Cost is a single PR open by an unprivileged GitHub user.

### Recommendation
Scope `DeploySpec.bundle_path` (and `BUNDLE_PATH` default in `TaskCommands#env`) per stack/task, e.g. `Rails.root.join('data', 'bundler', stack.id.to_s)`, so no two stacks share a gem install path. Additionally, run `deploy_spec.machine_env` through the same `EnvironmentVariables.permit` allowlist mechanism used for deploy/rollback/task variables (or explicitly deny overriding reserved keys like `BUNDLE_PATH`, `GEM_HOME`, `GEM_PATH`, `RUBYOPT`, `PATH` from `machine.environment`), and merge these safe defaults *after* `machine_env`/`@task.env` rather than before, so untrusted config cannot clobber security-relevant environment values.

### Proof of Concept
```ruby
# test/unit/task_commands_bundle_path_test.rb
require 'test_helper'

module Shipit
  class TaskCommandsBundlePathTest < ActiveSupport::TestCase
    test "machine.environment BUNDLE_PATH from an untrusted checkout is not scoped per-stack and reaches spawned env" do
      stack_a = shipit_stacks(:shipit)
      stack_b = shipit_stacks(:shipit_canaries) # a different repository/stack

      # both stacks resolve to the SAME global bundle path by default
      assert_equal DeploySpec.bundle_path.to_s, DeploySpec.bundle_path.to_s

      task_a = shipit_deploys(:shipit_pending) # belongs to stack_a
      commands_a = TaskCommands.new(task_a)
      commands_a.stubs(:deploy_spec).returns(
        DeploySpec.new('machine' => { 'environment' => { 'BUNDLE_PATH' => DeploySpec.bundle_path.to_s } })
      )

      # attacker-controlled shipit.yml machine.environment is NOT filtered by any
      # EnvironmentVariables.permit allowlist, unlike deploy/rollback/task variables
      env_a = commands_a.env
      assert_equal DeploySpec.bundle_path.to_s, env_a['BUNDLE_PATH']

      # this identical, unscoped path is also what stack_b's task would use
      task_b = shipit_deploys(:shipit_canaries_pending)
      commands_b = TaskCommands.new(task_b)
      commands_b.stubs(:deploy_spec).returns(DeploySpec.new({}))
      env_b = commands_b.env

      # BROKEN INVARIANT: two different repositories/stacks share the exact same
      # BUNDLE_PATH, meaning gem artifacts written by stack_a's `bundle install`
      # are visible to stack_b's `bundle install`/`bundle exec`
      assert_equal env_a['BUNDLE_PATH'], env_b['BUNDLE_PATH']

      # confirm the merged env (with attacker's BUNDLE_PATH) is exactly what
      # reaches Command#unbundled_env / PTY.spawn
      command = commands_a.install_dependencies.first
      assert_equal DeploySpec.bundle_path.to_s, command.unbundled_env['BUNDLE_PATH']
    end
  end
end
```
This demonstrates: (1) `machine.environment` from the checked-out (attacker-controlled) `shipit.yml` is merged unfiltered into `TaskCommands#env`, and (2) the resulting `BUNDLE_PATH` is identical across unrelated stacks, proving the shared/global bundler cache is the cross-tenant poisoning vector reaching `Command#unbundled_env` → `PTY.spawn`.
