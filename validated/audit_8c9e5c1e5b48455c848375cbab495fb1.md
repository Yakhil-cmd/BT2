### Title
Webhook signature is bound to `repository.owner.login`, not to `repository.full_name` used to select the target Stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` derives which GitHub App/organization secret to use for HMAC verification from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), both attacker-controlled fields inside the same unsigned-at-parse-time JSON body. [1](#0-0) [2](#0-1) 

Once the signature check passes, the event is dispatched to handlers such as `PushHandler`, which resolve the *actual* repository/stack to act on from a **different** field of the same payload: `payload.dig('repository', 'full_name')`, via `Repository.from_github_repo_name`. [3](#0-2) [4](#0-3) [5](#0-4) 

### Finding Description
This breaks the binding: `organization authenticated (repository.owner.login used to pick the webhook_secret) == repository/stack acted upon (repository.full_name used to load the Repository/Stack)`.

Any actor who legitimately controls a GitHub organization/App installation already onboarded to the Shipit instance (i.e., knows *their own* valid `webhook_secret` — a normal, unprivileged-relative-to-any-other-tenant condition, not requiring any Shipit credential) can:
1. Set `repository.owner.login` (or `organization.login`) to their **own** org login so `Shipit.github(organization: repository_owner)` resolves to their own `GithubApp`/secret, letting `verify_webhook_signature` pass with a signature they can legitimately compute.
2. Set `repository.full_name` to an arbitrary **other** organization's `owner/repo` that has a Stack configured in the same Shipit instance.

Because `verify_signature` only checks the payload against the secret selected by `repository_owner`, and never checks that `repository.full_name`'s owner matches `repository_owner`, the two fields are never cross-validated. The event handler then acts on the Stack resolved from the forged `full_name`, e.g. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for a victim's Stack chosen entirely by the attacker. [6](#0-5) 

This is the direct analog of the HackerOne report's root cause: the field that is *authorized/verified* (organization for the webhook secret) is not the same field that is *acted upon* (the target repository/stack), letting a legitimately-scoped actor manipulate unverified fields to affect a different tenant's resource — exactly the "payload field acted on but never covered by the verified signature" pattern called out in the rules.

### Impact Explanation
Concretely reachable impact is limited to forcing a `GithubSyncJob`/`sync_github` re-sync of an arbitrary victim Stack (via `PushHandler`), and similar cross-tenant triggering for other webhook-driven handlers (`status`, `check_suite`, `membership`, `pull_request/*`) that also resolve their target via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` rather than the organization used for signature verification. This can influence commit-status ingestion, PR label/state–driven ReviewStack provisioning, and merge-status hooks for a stack the attacker does not own or have any GitHub permission on — an authorization boundary crossing between the tenant whose secret verified the request and the tenant whose Stack is mutated. It does not, by itself, directly yield RCE, credential exfiltration, or a git push/merge without further chaining through review-stack provisioning or CI status manipulation, so I can't confirm it reaches the "Critical: unauthorized deploy/rollback/merge" bar without further tracing of every handler (`check_suite_handler.rb`, `status_handler.rb`, `membership_handler.rb`, `pull_request/*`), which I was not able to fully read before the iteration budget ran out.

### Likelihood Explanation
Any organization with its own GitHub App installation/webhook secret configured against this Shipit instance can attempt this — no privileged Shipit account, `ApiClient` token, or victim's secret is required, only knowledge of one's own legitimately-provisioned webhook secret and the ability to craft an arbitrary HTTP POST to `/github/webhooks` (the mounted `WebhooksController#create` route). This is a low-effort, low-privilege attack once multi-tenant/multi-org Shipit deployments are in play.

### Recommendation
Cross-validate that the organization resolved for signature verification matches the owner encoded in `repository.full_name` (and `organization.login` if present) before dispatching to handlers, e.g., derive the `Repository`/`Stack` for the event from the *same* verified owner rather than trusting `repository.full_name` independently, or reject events where `repository.owner.login` and the owner segment of `repository.full_name` disagree.

### Proof of Concept
1. Attacker legitimately owns/administers GitHub org `attacker-org`, with its own GitHub App installation and `webhook_secret` configured on this Shipit instance (`Shipit.github(organization: 'attacker-org')`).
2. Attacker crafts a `push` webhook payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "deadbeef",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature` using their own known `webhook_secret` for `attacker-org` — `verify_signature` looks up `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and passes. [1](#0-0) 
4. `PushHandler#process` resolves the target stacks via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, unrelated to the verified `attacker-org`, and calls `stack.sync_github(...)` on the victim's Stack. [3](#0-2) [6](#0-5)
