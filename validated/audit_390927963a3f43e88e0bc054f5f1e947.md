### Title
Race condition in pruned-content recovery causes the same withheld unit to be replayed twice, corrupting `assocUnitsInWork` bookkeeping - ([File: network.js])

### Summary
`tryRecoverPrunedContentOfFinalBadUnit` in `network.js` replays a withheld joint from RocksDB (`wj\n`+unit) as soon as content for *any one* of its missing/pruned parent units arrives. When a withheld joint is waiting on more than one pruned unit, it is indexed under `assocUnitsWaitingForPrunedContent[missing_unit]` for *each* missing unit it depends on, but the per-unit list is deleted and processed independently for each missing unit as its content arrives, without any lock coordinating the two code paths that read/delete the same `wj\n`+unit key. This mirrors the CVE-2010-0302 bug class: a shared, reference-counted resource (`assocUnitsWaitingForPrunedContent`, and by extension `assocUnitsInWork`) is manipulated from multiple independent completion paths without proper synchronization, allowing the same object to be processed more than once concurrently.

### Finding Description
`validation.js` sets `bRequestPrunedContent` when a posted/received unit spends an output whose original unit was pruned as final-bad. `network.js` then stores the full joint body in RocksDB and registers it against *every* missing unit it needs recovered: [1](#0-0) 

When content for one of those missing units arrives from a peer, `tryRecoverPrunedContentOfFinalBadUnit` fires: [2](#0-1) 

The function reads the key `'wj\n'+o.unit`, deletes it, and calls `handleOnlineJoint` — all asynchronously (`kvstore.get` callback). If the same withheld unit is registered under two different missing units (e.g. it spends two different pruned final-bad outputs, or the same missing unit resolves through two concurrent peer responses), two independent invocations of `tryRecoverPrunedContentOfFinalBadUnit` can each call `kvstore.get(key)` before either has called `kvstore.del(key)`, because the get/del pair is not atomic and there is no mutex around this whole withheld-joint bookkeeping (unlike the `handleJoint`/`mutex.lock(['handleJoint'])` path used for normal validation). Both call sites will then observe a non-null `strSavedJoint` and both will invoke `handleOnlineJoint(...)` for the same `objJoint` concurrently.

`handleOnlineJoint` -> `handleJoint` is guarded by the `assocUnitsInWork[unit]` check: [3](#0-2) 
but this check-then-set is not atomic either — both replay invocations can enter `handleOnlineJoint` and call `handleJoint` before the first has had a chance to set `assocUnitsInWork[unit] = true` (both are queued via `process.nextTick`/async database callbacks, and the check happens synchronously inside `handleJoint`, but if both replay calls reach `handleJoint` in the same tick before either mutates `assocUnitsInWork`, the second call could still see `undefined` because JS synchronous execution actually would prevent this specific race for a *single-threaded* interleaving — however, the deeper issue is the double-consumption of the `wj\n` record and its associated `assocUnitsWaitingForPrunedContent` entries across two different missing-unit keys, which is a genuine race independent of the `assocUnitsInWork` guard).

Because the guard only protects the synchronous entry into `handleJoint`, and validation itself is asynchronous (`mutex.lock(['handleJoint'], ...)` then `validation.validate`), a second replay that arrives after `assocUnitsInWork[unit]` has already been cleared (e.g., because the first replay's validation failed transiently and cleared the entry via `ifTransientError`/`ifNeedParentUnits` paths shown at lines 1203-1257) can re-trigger a fresh, overlapping validation/save cycle for the exact same recovered final-bad unit, using state (`arrDoubleSpendInputs`, cached pruned-joint reference counts in `archiving.assocCachedPrunedJoints`) that the first cycle is still mutating.

### Impact Explanation
Concurrent replays of the same withheld joint that spends a pruned final-bad output can race through validation and `writer.saveJoint` twice for outputs that reference the now-recovered pruned content. Because the recovery path exists specifically to reconcile spends of pruned final-bad outputs that "raced the pruning locally" (per the code comment in `archiving.js`), a second concurrent execution risks writing duplicate/partial database state for the same recovered unit, corrupting the in-memory `assocUnitsInWork`/`assocUnitsWaitingForPrunedContent` bookkeeping, and potentially causing the node to diverge from other nodes on whether the recovered final-bad unit's dependents are valid or stable — a node-disagreement-on-validity class impact.

### Likelihood Explanation
Reachable by an unprivileged unit poster: a unit spending outputs of two different, still-pruned final-bad units (or racing peer responses for the same missing unit) is a scenario a poster/attacker can deliberately construct, since final-bad units and their pruning schedule are observable on-chain. Triggering the exact interleaving of two peer responses arriving in overlapping ticks is timing-dependent but plausible under normal network conditions with multiple peers, especially since `findNextPeer`/`requestJoints` can solicit the same missing content from multiple peers.

### Recommendation
Serialize access to `assocUnitsWaitingForPrunedContent` and the associated `wj\n` keys behind a mutex keyed by the withheld unit (not just the missing unit), and make the "read + delete" of the `wj\n` record atomic (e.g., use `mutex.lock(['wj:'+o.unit], ...)` around the `kvstore.get`/`kvstore.del`/`handleOnlineJoint` sequence in `tryRecoverPrunedContentOfFinalBadUnit`) so that a withheld joint waiting on multiple missing units can only be replayed exactly once, regardless of which missing unit's content resolves first or how many peers respond concurrently.

### Proof of Concept
1. Construct final-bad units `A` and `B` that both get pruned locally (stripped content) after enough time.
2. Post a unit `U` that spends one output from `A` and one output from `B`.
3. `validation.js` reports `unresolved_dependency` with `bRequestPrunedContent=true` for both `A` and `B`; `network.js` stores `U`'s body once under `wj\n`+U and registers `U` under both `assocUnitsWaitingForPrunedContent[A]` and `assocUnitsWaitingForPrunedContent[B]`.
4. Arrange (e.g. via two different peers) for the full content of `A` and `B` to arrive back-to-back in the same tick/close succession.
5. Both `tryRecoverPrunedContentOfFinalBadUnit(A)` and `tryRecoverPrunedContentOfFinalBadUnit(B)` execute their `kvstore.get('wj\n'+U)` before either has completed `kvstore.del`, both obtain the stored joint, and both call `handleOnlineJoint` for `U`, producing overlapping validation/save cycles for the same unit.

*(Note: I could not fully trace every downstream interleaving in `writer.saveJoint`/`validation.js` to confirm a concrete double-write within the scope of available context; this is flagged as the weakest link in the proof chain and would benefit from a live/dynamic trace to confirm the exact database-level consequence.)*

function tryRecoverPrunedContentOfFinalBadUnit(ws, objJoint){
	const unit = objJoint.unit.unit;
	const arrWaitingJoints = assocUnitsWaitingForPrunedContent[unit];
	if (!arrWaitingJoints)
		return false;
	if (!validation.allHashesAreValid(objJoint)){
		console.log('recovered content for pruned unit ' + unit + ' from ' + ws.peer + ' failed hash check');
		return false;
	}
	archiving.cachePrunedJoint(objJoint);
	breadcrumbs.add('recovered pruned content of final-bad unit ' + unit + ' from ' + ws.peer);
	delete assocUnitsWaitingForPrunedContent[unit];
	// replay the waiting joints in the background, don't make the peer who sent us the recovered content wait for this
	async.eachSeries(arrWaitingJoints, function(o, cb){
		const key = 'wj\n' + o.unit;
		kvstore.get(key, strSavedJoint => {
			kvstore.del(key);
			if (!strSavedJoint) // already replayed via another missing unit it was also waiting on, or expired
				return cb();
			const { objJoint: objWaitingJoint, peer } = JSON.parse(strSavedJoint);
			handleOnlineJoint(peer ? getPeerWebSocket(peer) : null, objWaitingJoint, cb);
		});
	});
	return true;
}
