### Title
Webhook organization used for HMAC-secret selection is never bound to the `repository.full_name` the event handlers act on, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` picks *which* GitHub App/webhook secret to validate a webhook against using `repository_owner`, a field taken from the same untrusted JSON body it is about to verify. Every event handler, however, resolves the actual `Repository`/`Stack` to mutate using a *different* field of that same body: `repository.full_name`. Nothing ties these two fields together, so a valid HMAC computed with organization A's secret can be replayed with a payload whose `repository.full_name` points at organization B's repository.

### Finding Description
`verify_signature` selects the app/secret like this: [1](#0-0) 
`repository_owner` is derived straight from the unverified body: [2](#0-1) 

The actual signature check is a plain HMAC over the raw body, scoped to whichever organization's secret was selected above: [3](#0-2) 

Once verification passes, `create` dispatches the *entire, attacker-controlled* body to handlers: [4](#0-3) 

Handlers never re-check that the target repository belongs to the organization whose secret validated the signature. The base `Handler` class resolves the repository/stacks purely from `repository.full_name`: [5](#0-4) 

`PushHandler` (and similarly the pull-request handlers, all of which call `Repository.from_github_repo_name(params.repository.full_name)`) then acts on whatever stacks that lookup returns: [6](#0-5) [7](#0-6) 

The equality that should be enforced but is not:
`organization_whose_secret_signed_the_request == owner(repository.full_name_acted_upon)`

Because `repository.owner.login` (used to pick the secret) and `repository.full_name` (used to pick the target) are two independent, attacker-supplied JSON fields inside the same body, an attacker who legitimately controls one Shipit-tracked organization/webhook (and therefore knows that organization's `webhook_secret`, configured per-organization via `Shipit.github(organization:)`, see `lib/shipit/github_app.rb` lines 44-57) can sign a payload with their own organization's secret while setting `repository.full_name` to a completely different, victim organization's repository.

### Impact Explanation
This breaks the binding between "the organization that authenticated the webhook" and "the repository/stack that is actually written to." An attacker who only administers their own onboarded Shipit organization can forge push (and other) events that are dispatched against stacks belonging to an unrelated organization they have no access to, e.g. causing `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` to run against a victim stack. If the targeted stack has `continuous_deployment` enabled, a forged push/sync can drive an unauthorized deploy pipeline for a repository the attacker never had write access to — this is a cross-repository/cross-organization boundary crossing that maps to the "cross-repository writes / unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires only that the attacker is a legitimate administrator of *some* organization already onboarded to the same Shipit instance (a realistic scenario for any multi-tenant/self-hosted deployment tracking multiple GitHub organizations) — no privileged Shipit account, session, or `ApiClient` token is needed, since `/webhooks` is a public, unauthenticated endpoint gated only by the HMAC. Crafting the JSON with a mismatched `repository.owner.login` vs `repository.full_name` is trivial.

### Recommendation
After `verify_signature` succeeds, re-derive the organization from `repository.full_name` (or `organization.login` for org-level events) and reject the request (422) unless it matches the organization whose secret validated the signature. Alternatively, verify the signature using the secret associated with the repository actually referenced by `repository.full_name`, not the one implied by `repository.owner.login`/`organization.login` taken at face value before verification.

### Proof of Concept
1. Attacker is the admin of `attacker-org`, which is registered in this Shipit instance with its own GitHub App webhook secret `S_A` (`Shipit.github(organization: "attacker-org")`).
2. Attacker builds a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(S_A, body)>` using the secret they legitimately know for `attacker-org`.
4. `POST /webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and the HMAC check passes because it was signed with `attacker-org`'s real secret.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stacks — an action the attacker was never authorized to trigger.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
