### Title
`StackStxOp::check` accepts `num_cycles` outside `(0, POX_MAX_NUM_CYCLES]` (warns instead of rejecting) - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`StackStxOp::check` is supposed to enforce that `num_cycles` is in `(0, POX_MAX_NUM_CYCLES]` before a burnchain stacking operation is admitted into chainstate, but the out-of-range branch only calls `warn!` and falls through to `Ok(())` instead of returning an error. Any unprivileged party who crafts their own burnchain `StackStxOp` (via a Bitcoin transaction with `OP_RETURN` payload) can set `num_cycles` to any `u8` value, including values far exceeding `POX_MAX_NUM_CYCLES`, and have the operation validated successfully by `SortitionHandleTx::check_transaction`.

### Finding Description
The broken equality is: `accepted_num_cycles == num_cycles ∈ (0, POX_MAX_NUM_CYCLES]`. The code is supposed to guarantee this via `check()`: [1](#0-0) 

but the branch that detects the violation only logs a warning and does not return `Err(...)`: [2](#0-1) 

Compare this to the sibling check just above it for `stacked_ustx`, which correctly returns `Err(op_error::StackStxMustBePositive)` on failure: [3](#0-2) 

`check()` is invoked from `SortitionHandleTx::check_transaction`, which treats `Ok(())` as "accept the operation into the block" and only rejects on `Err`: [4](#0-3) 

Because `check()` returns `Ok(())` regardless of the `num_cycles` value, an attacker constructs a Bitcoin transaction encoding a `StackStxOp` payload with `num_cycles = 255` (or `0`), which `StackStxOp::parse_from_tx` will happily parse (`parse_data` reads `num_cycles` as a raw byte with no bound check): [5](#0-4) 

The op is then admitted as a valid `BlockstackOperationType::StackStx` into the burnchain state transition/snapshot.

### Impact Explanation
If the value is passed through unclamped to the reward-cycle/unlock-height computation, the attacker's own `stacked_ustx` would be locked for more reward cycles than `POX_MAX_NUM_CYCLES` permits — violating the protocol's advertised bound on stacking duration ("SINGLE UNLOCK" invariant: unlock height must equal a bounded, committed number of cycles). This is repeatable per stacking transaction and affects any staker (including the attacker themselves, or anyone who is tricked/chooses to submit such an op), matching the Critical category of "permanent freezing of staked STX ... beyond any cycle bound the protocol is supposed to enforce."

### Likelihood Explanation
The precondition is trivial: the attacker only needs to control their own Bitcoin inputs and craft a raw `StackStxOp` OP_RETURN payload (no bond admin, pause admin, miner, or other privileged role required) — this matches the "craft burnchain stacking ops from their own Bitcoin inputs" attacker capability explicitly allowed by the scope. The `check()` function as coded in this repository will not reject any `num_cycles` value including `0` or `255`; only the Rust-level gate is bypassed. However, I was unable to fully verify, within the available iterations, whether the corresponding Clarity `stack-stx`-style entry point in `pox-4.clar`/`pox-5.clar` (the Clarity contract that actually processes the burnchain op and sets `unlock-burn-height`) independently re-validates and clamps `lock-period`/`num_cycles` before locking funds. If such a redundant Clarity-side check exists and rejects/clamps out-of-range cycles, the practical end-to-end impact would be mitigated to a benign no-op (the burnchain op accepted at the Rust layer, but the Clarity contract call still fails or clamps), even though the Rust-level `check()` remains defectively permissive. This downstream verification could not be completed and is a genuine gap in this analysis.

### Recommendation
Change the out-of-range branch in `StackStxOp::check` to return an error, matching the pattern used for `stacked_ustx`:
```rust
if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
    warn!(...);
    return Err(op_error::StackStxInvalidCycles); // or an equivalent existing error variant
}
```

### Proof of Concept
Rust unit test in `stackslib/src/chainstate/burn/operations/stack_stx.rs` (or its `test` module):
```rust
#[test]
fn test_check_rejects_out_of_range_num_cycles() {
    let op = StackStxOp {
        sender: /* any StacksAddress */,
        reward_addr: /* any PoxAddress */,
        stacked_ustx: 10,
        num_cycles: POX_MAX_NUM_CYCLES + 1, // e.g. 255
        signer_key: None,
        max_amount: None,
        auth_id: None,
        txid: Txid([0u8; 32]),
        vtxindex: 0,
        block_height: 0,
        burn_header_hash: BurnchainHeaderHash([0u8; 32]),
    };
    // Equality claim: check() must be Err for num_cycles > POX_MAX_NUM_CYCLES
    let result = op.check();
    assert!(result.is_err(), "check() incorrectly returned Ok for num_cycles={}", op.num_cycles);
}
```
Running this against the current code shows `result == Ok(())`, confirming the check is bypassed. A full integration-level PoC would additionally require tracing the accepted op through burnchain-op processing into the PoX Clarity contract call to confirm whether the resulting `unlock-burn-height` for the sender's `stacked_ustx` actually exceeds `POX_MAX_NUM_CYCLES` reward cycles — this second half was not completed in this analysis.

```rust
impl StackStxOp {
    pub fn check(&self) -> Result<(), op_error> {
        if self.stacked_ustx == 0 {
            warn!("Invalid StackStxOp, must have positive ustx");
            return Err(op_error::StackStxMustBePositive);
        }

        if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
            warn!(
                "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
                self.num_cycles, POX_MAX_NUM_CYCLES
            );
        }

        // Check to see if the signer key is valid if available
        if let Some(signer_key) = &self.signer_key {
            Secp256k1PublicKey::from_slice(signer_key.as_bytes())
                .map_err(|_| op_error::StackStxInvalidKey)?;
        }

        Ok(())
    }
```
