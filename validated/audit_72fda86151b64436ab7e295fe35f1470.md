### Title
Withdraw instruction sends pool funds to an unvalidated destination token account with no owner-authority check - (File: programs/cp-swap/src/instructions/withdraw.rs)

### Summary
The `Withdraw` accounts struct constrains `token_0_account` and `token_1_account` (the accounts that receive the underlying tokens redeemed from a user's LP burn) only by `token::mint`, with no `token::authority` (or `associated_token::authority`) constraint tying them to the `owner` who signs the instruction. This is the exact bug class described in the external report: a destination token account is not enforced to belong to (or be the ATA of) the intended beneficiary, so funds can land in any SPL token account of the matching mint that an attacker supplies.

### Finding Description
In `programs/cp-swap/src/instructions/withdraw.rs`, the destination accounts are declared as: [1](#0-0) 
Only `token::mint` is checked; there is no `token::authority = owner` or `associated_token::authority = owner` constraint. Contrast this with the source-side accounts in `Deposit`, which explicitly pin ownership: [2](#0-1) 
In `withdraw()`, after the owner-authorized LP burn, the program transfers the underlying tokens directly to these unvalidated accounts via `transfer_from_pool_vault_to_user`, whose SPL `transfer_checked` CPI only validates the *source* (vault) authority — it never validates that the *destination* account's owner matches the transaction signer: [3](#0-2) [4](#0-3) 
The same unvalidated-destination pattern also exists for `output_token_account` in the shared `Swap` accounts struct used by `swap_base_input`/`swap_base_output`, where only `#[account(mut)]` is applied with no authority check: [5](#0-4) 

By contrast, the newer `collect_creator_fee` / `collect_creator_fee_permissionless` instructions correctly enforce `associated_token::authority = creator`, showing the intended, safe pattern that `withdraw`/`swap` lack: [6](#0-5) 

### Impact Explanation
A malicious or compromised front-end/relayer that constructs the `withdraw` (or `swap_base_output`/`swap_base_input`) instruction on behalf of a user can substitute `token_0_account`/`token_1_account` (or `output_token_account`) with an attacker-controlled token account of the correct mint. The `owner`/`payer` still signs the transaction (authorizing the LP burn or input debit), but the redeemed/output funds are silently diverted to the attacker instead of the legitimate user, resulting in theft of user/LP funds. Recovery, as noted in the original report, is possible on-chain but non-trivial for non-technical users.

### Likelihood Explanation
Exploitation requires the victim to sign a transaction whose destination account list was manipulated (e.g., via a malicious dApp UI, compromised SDK, or MEV/relayer tampering during instruction construction before signing) — no privileged program authority is needed, and the token accounts pass Anchor's `token::mint` check normally since SPL Token allows anyone to create a `TokenAccount` for any mint with any owner. This mirrors the exact conditions OtterSec flagged as fixable and worth remediating in the original report.

### Recommendation
Add explicit ownership constraints to the destination token accounts, mirroring the fix applied elsewhere in the codebase (`collect_creator_fee`):
```rust
#[account(
    mut,
    token::mint = token_0_vault.mint,
    token::authority = owner,
)]
pub token_0_account: Box<InterfaceAccount<'info, TokenAccount>>,
```
or, to fully match the OtterSec-recommended remediation, require the accounts be the associated token account of `owner`:
```rust
#[account(
    init_if_needed,
    payer = owner,
    associated_token::mint = token_0_vault.mint,
    associated_token::authority = owner,
)]
pub token_0_account: Box<InterfaceAccount<'info, TokenAccount>>,
```
Apply the same fix to `token_1_account` in `withdraw.rs` and to `output_token_account` (and `input_token_account`, for defense in depth) in `swap_base_input.rs`/`swap_base_output.rs`.

### Proof of Concept
1. Attacker (as a malicious front-end/relayer) builds a `withdraw` instruction on behalf of victim `owner`, using the victim's real `owner_lp_token`, `pool_state`, `token_0_vault`, `token_1_vault`, but substitutes `token_0_account`/`token_1_account` with token accounts the attacker created (correct mint, attacker as `token::authority`).
2. Victim signs the transaction (e.g., via a compromised/malicious wallet UI) believing funds return to their own wallet.
3. `withdraw()` burns the victim's LP tokens via `token_burn` (authorized by victim signature) and then calls `transfer_from_pool_vault_to_user` twice, sending the redeemed `token_0_amount`/`token_1_amount` to the attacker-supplied accounts — no Anchor constraint or CPI-level check rejects this because `token::mint` matches and the SPL `transfer_checked` CPI does not validate the destination's owner.
4. Funds are now in the attacker's token accounts instead of the victim's, with the victim's LP position having already been burned irreversibly.

```rust
pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
```
