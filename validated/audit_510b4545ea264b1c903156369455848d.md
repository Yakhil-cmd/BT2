I have enough context now to determine the validity of this finding.

The core binding claimed by the question is: does `LabeledHandler#archive?/#unarchive?` authorization gate ("only the specific `provisioning_label_name` matters") equal the set of labels that reach the deploy environment via `LabelCapturingHandler#capture_labels` → `ReviewStack#env`? Tracing the code confirms these are two intentionally independent concerns, and the label-to-env behavior is a documented, by-design feature, not a bug.

### Analysis

`Shipit::Webhooks::Handlers::PullRequest::LabeledHandler#archive?`/`#unarchive?` only decide whether to archive/unarchive a review stack based on whether `provisioning_label_name` is present, per `pull_request_has_provisioning_label?`. [1](#0-0) 

`LabelCapturingHandler#capture_labels` independently persists **all** labels on the PR (not just the provisioning label) to `pull_request.labels` whenever the stack is present and not archived, regardless of the provisioning decision. [2](#0-1) 

`ReviewStack#env` then converts **every captured label** into an uppercase environment variable set to `"true"`, merged unconditionally into the stack's env — with no whitelist/permit step at this layer. [3](#0-2) 

This flows into `TaskCommands#env` (and `DeployCommands#env`), which merges `@stack.env` directly into the final command environment, and ultimately into `Command#unbundled_env` / `PTY.spawn`. [4](#0-3) [5](#0-4) 

Critically, this "every PR label becomes an env var" behavior is an explicit, tested, and documented feature of Shipit — not an oversight. It is exercised directly by existing first-party tests asserting that arbitrary label names (`wip`, `bug`) become `WIP=true`, `BUG=true` in the deploy/task environment: [6](#0-5) [7](#0-6) [8](#0-7) 

Note also that other user/task-supplied env sources (`deploy.variables`, `rollback.variables`, `@task.env`, `Stack#trigger_task`, `Stack#build_deploy`) ARE explicitly whitelisted via `EnvironmentVariables#permit`/`filter_deploy_envs`/`filter_envs` before being merged. [9](#0-8) [10](#0-9) [11](#0-10) 

But `ReviewStack#env`'s label-derived variables are a distinct, separate mechanism that was never subject to that whitelist — this is the stack's designed behavior specifically to let PR authors flip flags like `WIP`/`SKIP_TESTS` via labels, and it applies equally to `git_askpath`/`path`-named labels as it does to `do-not-deploy`. The question frames this as if `LabeledHandler`'s authorization logic is supposed to gate which labels flow to `capture_labels`/`env`, but no such coupling exists or was ever intended — the provisioning label controls stack archival, while label capturing/env injection is a completely separate, always-on feature for **any repo with review stacks enabled**, independent of `provisioning_behavior`.

Given `GIT_ASKPASS` is already set by `Commands#base_env` when `Shipit.use_git_askpash?` is enabled (pointing at the trusted `git-askpass` snippet), and a label-derived env var only overwrites it with the string `"true"` (not an attacker-controlled path or script), the "collision" described does not actually enable RCE — `"true"` is not executable as a `GIT_ASKPASS` program in any meaningful way that grants command execution beyond what's already permitted by design. [12](#0-11) 

This is a known, accepted design tradeoff (labels → env vars, unfiltered) rather than a security control being bypassed. There is no equality being broken between the provisioning-label check and the env-injection path because no such equality was ever claimed or enforced by the code — they are independent, correctly-scoped features operating on the same underlying `PullRequest#labels` data by design.
