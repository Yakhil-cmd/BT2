### Title
Signer-key authorizations in `stack-stx`/`stack-extend`/`stack-increase`/`stack-aggregation-commit` are not bound to a specific stacker, enabling front-running griefing that denies the intended stacker from using their own authorized signature - (File: `stackslib/src/chainstate/stacks/boot/pox-4.clar`)

### Summary
`pox-4.clar`'s signer-key authorization scheme (SIP-018 signature or on-chain authorization) is a single-use, nonce-guarded (`auth-id`) permission that a signer grants for a `(pox-addr, reward-cycle, topic, period, max-amount, auth-id)` tuple, but the authorization is **not bound to the specific stacker principal** who is meant to use it. Any address watching the mempool can front-run a legitimate stacker's transaction, reuse the exact same signature/authorization with a different `tx-sender` (and a smaller `amount-ustx` they can actually fund), consume the one-time `auth-id`, and thereby permanently deny the intended stacker from executing their already-authorized stacking action for that reward cycle — the same "front-run the counter-order to deny the victim" griefing pattern described in the referenced report.

### Finding Description
`get-signer-key-message-hash` builds the SIP-018 message from `pox-addr`, `reward-cycle`, `topic`, `period`, `auth-id`, and `max-amount` only: [1](#0-0) 

`verify-signer-key-sig` checks the recovered public key against `signer-key` and that the authorization has not been used, again with no reference to which principal is allowed to consume it: [2](#0-1) 

`consume-signer-key-authorization` marks the authorization as used via `used-signer-key-authorizations`, keyed only by `{signer-key, reward-cycle, topic, period, pox-addr, auth-id, max-amount}` — again, no `stacker`/`tx-sender` field: [3](#0-2) 

This authorization is consumed from `stack-stx` (`tx-sender` is whoever calls the function, not necessarily who the signer intended): [4](#0-3) 

and similarly from `stack-increase`, `stack-extend`, and `inner-stack-aggregation-commit`: [5](#0-4) [6](#0-5) [7](#0-6) 

Because the check `(>= max-amount amount)` only requires the *caller-supplied* `amount-ustx` to be ≤ `max-amount` (it does not require equality, and does not check `stacker`), any `tx-sender` who observes a pending signed authorization in the mempool — e.g. destined for stacker Alice's `stack-stx` call for `1000` STX under `max-amount = 1000` — can front-run with their own `stack-stx` call using the *same* `pox-addr`, `signer-sig`/`signer-key`, `period`, `reward-cycle`, `max-amount`, and `auth-id`, but a much smaller `amount-ustx` funded from their own balance (e.g. the stacking minimum). This second call passes `verify-signer-key-sig` (amount ≤ max-amount) and `consume-signer-key-authorization` inserts the same map key, marking the authorization permanently used. Alice's subsequent, originally-intended transaction then fails with `ERR_SIGNER_AUTH_USED`, since the map lookup key does not distinguish stacker identity.

### Impact Explanation
This lets any unprivileged account grief a specific stacker or signer's client by observing the mempool and racing their properly-signed authorization, spending only enough of their own STX to satisfy the stacking minimum. The victim's already-signed, already-authorized stacking action (locking STX for a reward cycle, extending a lock, increasing a lock, or committing an aggregate) is executed by an unintended, unauthorized party instead of the victim — this is "a stacking action the staker/signer never authorised" being consumed on the victim's behalf, and it denies the victim from performing the very action for which they held a valid signature. Since `stack-stx`/`stack-extend` require the reward cycle/lock period to exactly match the signed authorization (`first-reward-cycle` must equal `specified-reward-cycle`, and cannot be "post-dated"), the victim cannot simply retry with the same authorization in a later cycle — they must obtain a brand new signature from the signer, which they may not control (e.g., pooled stacking where the signer is a separate operator). This can cause the victim to miss an entire reward cycle's worth of stacking, i.e., a temporary freezing/loss of expected stacking participation for that stacker, satisfying the High-impact bar ("an unsigned stacking action").

### Likelihood Explanation
The attack is inexpensive: the attacker only needs the stacking minimum in STX and normal mempool visibility, exactly as in the referenced Trader front-running report. No privileged role is required — any account can submit a transaction with a higher fee to be mined first. The main constraint is that the attacker must supply a valid `pox-addr` (their own, since PoX rewards for that reward cycle would go to whatever `pox-addr` is passed) and enough STX to satisfy `can-stack-stx`'s minimum threshold, both of which are trivial. This applies to any of the four public entry points that call `consume-signer-key-authorization` (`stack-stx`, `stack-extend`, `stack-increase`, `stack-aggregation-commit`/`-indexed`).

### Recommendation
Bind the authorization to the intended stacker principal by adding `stacker: tx-sender` (or an explicit `authorized-stacker` field enforced against `tx-sender`) into the signed message (`get-signer-key-message-hash`) and into the `used-signer-key-authorizations`/`signer-key-authorizations` map keys, so a signature/authorization can only be consumed by the specific principal it was issued for. This closes the front-running/griefing vector while preserving the delegate/pool use case if the signer explicitly authorizes a delegate contract-caller.

### Proof of Concept
1. A pooled-stacking signer S signs a SIP-018 authorization for stacker Alice: `(pox-addr P, reward-cycle R, topic "stack-stx", period 1, auth-id 42, max-amount 1000_000000)`.
2. Alice broadcasts `stack-stx(amount-ustx=1000_000000, pox-addr=P, start-burn-ht=..., lock-period=1, signer-sig=Some(sig), signer-key=S, max-amount=1000_000000, auth-id=42)`.
3. Attacker Mallory observes Alice's pending transaction, extracts `(P, sig, S, max-amount, auth-id)`, and submits her own `stack-stx(amount-ustx=<stacking-minimum>, pox-addr=P, start-burn-ht=..., lock-period=1, signer-sig=Some(sig), signer-key=S, max-amount=1000_000000, auth-id=42)` with a higher fee.
4. Mallory's transaction is mined first: `verify-signer-key-sig` succeeds (`amount ≤ max-amount`, signature valid, auth not yet used), `consume-signer-key-authorization` inserts `used-signer-key-authorizations{signer-key: S, reward-cycle: R, topic: "stack-stx", period: 1, pox-addr: P, auth-id: 42, max-amount: 1000_000000} = true`.
5. Alice's original transaction is then processed and fails at `verify-signer-key-sig` / `consume-signer-key-authorization` with `ERR_SIGNER_AUTH_USED`, even though Alice was the intended, authorized user — she must obtain a fresh authorization from S, and may miss the reward cycle `R` entirely (since `first-reward-cycle` cannot be post-dated).                                          (reward-cycle uint)
                                         (topic (string-ascii 14))
                                         (period uint)
                                         (signer-sig-opt (optional (buff 65)))
                                         (signer-key (buff 33))
                                         (amount uint)
                                         (max-amount uint)
                                         (auth-id uint))
  (begin
    ;; Validate that amount is less than or equal to `max-amount`
    (asserts! (>= max-amount amount) (err ERR_SIGNER_AUTH_AMOUNT_TOO_HIGH))
    (asserts! (is-none (map-get? used-signer-key-authorizations { signer-key: signer-key, reward-cycle: reward-cycle, topic: topic, period: period, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount }))
              (err ERR_SIGNER_AUTH_USED))
    (match signer-sig-opt
      ;; `signer-sig` is present, verify the signature
      signer-sig (ok (asserts!
        (is-eq
          (unwrap! (secp256k1-recover?
            (get-signer-key-message-hash pox-addr reward-cycle topic period max-amount auth-id)
            signer-sig) (err ERR_INVALID_SIGNATURE_RECOVER))
          signer-key)
        (err ERR_INVALID_SIGNATURE_PUBKEY)))
      ;; `signer-sig` is not present, verify that an authorization was previously added for this key
      (ok (asserts! (default-to false (map-get? signer-key-authorizations
            { signer-key: signer-key, reward-cycle: reward-cycle, period: period, topic: topic, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount }))
          (err ERR_NOT_ALLOWED)))
    ))
  )

;; This function does two things:
;;
;; - Verify that a signer key is authorized to be used
;; - Updates the `used-signer-key-authorizations` map to prevent reuse
;;
;; This "wrapper" method around `verify-signer-key-sig` allows that function to remain
;; read-only, so that it can be used by clients as a sanity check before submitting a transaction.
(define-private (consume-signer-key-authorization (pox-addr { version: (buff 1), hashbytes: (buff 32) })
                                                  (reward-cycle uint)
                                                  (topic (string-ascii 14))
                                                  (period uint)
                                                  (signer-sig-opt (optional (buff 65)))
                                                  (signer-key (buff 33))
                                                  (amount uint)
                                                  (max-amount uint)
                                                  (auth-id uint))
  (begin
    ;; verify the authorization
    (try! (verify-signer-key-sig pox-addr reward-cycle topic period signer-sig-opt signer-key amount max-amount auth-id))
    ;; update the `used-signer-key-authorizations` map
    (asserts! (map-insert used-signer-key-authorizations
      { signer-key: signer-key, reward-cycle: reward-cycle, topic: topic, period: period, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount } true)
      (err ERR_SIGNER_AUTH_USED))
    (ok true)))
