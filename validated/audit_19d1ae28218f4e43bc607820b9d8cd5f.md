### Title
Default `--stale-worktree-timeout=0` deletes the previously-published worktree with no grace period, breaking the atomic-publish contract for slow readers - (File: main.go)

### Summary
`git-sync`'s core guarantee ("the contract") is that consumers always see a consistent view of the repo through the `--link` symlink, because a checkout is not atomic but the symlink flip is [1](#0-0) . Immediately after flipping the symlink to a new worktree, the same sync-loop iteration runs `cleanup()`, which deletes any worktree older than `--stale-worktree-timeout` [2](#0-1) . That flag defaults to `0`, meaning stale worktrees "will be removed immediately" on the very next sync attempt [3](#0-2) . This is structurally the same bug class as the Teller report: a safety/grace-period parameter that gates a destructive action can be effectively zero, so the destructive action (deleting the previously-published data set) happens essentially immediately with no window for consumers who already resolved the old symlink target to finish reading.

### Finding Description
The publish path is:
1. `SyncRepo` calls `syncHooks.beforePublish`, then `publishSymlink(newWorktree)` to atomically flip `--link` to the new worktree, then touches the *old* current worktree to start its "stale" clock [4](#0-3) .
2. Immediately afterward, in the same top-level loop iteration, `git.cleanup(ctx)` is invoked [2](#0-1) .
3. `cleanup` calls `removeStaleWorktrees`, which deletes any worktree (other than the one the link currently points at) whose mtime is older than `git.staleTimeout` [5](#0-4)  and [6](#0-5) .
4. Because the old worktree was `touch`ed at essentially the same instant the new symlink was published, and the default `staleTimeout` is `0`, `time.Since(fi.ModTime()) > git.staleTimeout` is true on the very next cleanup pass — i.e., on the same sync-loop iteration that just flipped the link.

This means: any consumer process (an application container sharing the volume, per the sidecar model documented in `docs/kubernetes.md`) that resolved `--link` to the old worktree path just before the flip, and is still in the middle of reading files from that path, can have the directory removed out from under it (`os.RemoveAll`) with no grace period at all [7](#0-6) . The "grace period" mechanism (`--stale-worktree-timeout`) exists precisely to prevent this, but is disabled by default, exactly mirroring the Teller bug where `PaymentDefault` gates a destructive action but defaults/can be set to a value that provides effectively no protection window.

### Impact Explanation
This can result in "publishing wrong or partial content" / broken reads for consumers: readers that hold the old symlink target open across the flip can get `ENOENT` on newly-opened files/subpaths, truncated directory listings mid-read, or race failures, because the tool's own atomicity contract for readers depends on retaining the old worktree until readers are done — a guarantee that is not honored under the default configuration. In a Kubernetes sidecar pattern (the primary documented use case), this can manifest as application containers intermittently failing to read config/data during every sync that changes content, i.e., a low-level but real synchronization/availability defect reachable purely through default settings, no attacker interaction required.

### Likelihood Explanation
Reachable by default configuration with zero required attacker capability — this is not a malicious-operator or malicious-node scenario, it's the tool's own default (`--stale-worktree-timeout` defaults to `0`) combined with normal use (any repo update that changes the ref). Consumers with even a small read window (e.g., opening several files sequentially from within the linked directory) can lose access to files mid-read whenever a sync occurs. This directly parallels the accepted Sherlock finding's judgment that the issue is valid but conditioned on an easily-triggerable default/parameter ("requires ... a low default duration" — here, requires only *not overriding* the zero default), which was still accepted as a valid (medium) issue rather than dismissed.

### Recommendation
- Change the default `--stale-worktree-timeout` to a small but non-zero value (e.g., a few seconds) so that the old worktree is not deleted in the same iteration it stops being the published target, giving in-flight readers a grace window, mirroring the report's own recommendation to "enforce sensible minimums" for the equivalent default-duration parameter.
- Alternatively/additionally, defer `removeStaleWorktrees` for at least one full `--period` after a worktree stops being current, regardless of the configured `--stale-worktree-timeout`, so a `0` value cannot cause "delete in the same tick as publish."
- Document explicitly in `--stale-worktree-timeout` help text that a `0` value provides no protection against readers racing a symlink flip (currently it merely says "removed immediately," without calling out the reader-race implication) [3](#0-2) .

### Proof of Concept
Conceptual reproduction based on `test_e2e.sh`'s existing `stale_worktree_timeout` test [8](#0-7)  (which explicitly exercises non-default timeouts):
1. Run `git-sync --repo=<repo> --root=<root> --link=link --period=100ms` with the default `--stale-worktree-timeout` (unset ⇒ `0`).
2. Have a "consumer" process `open()` a file under `$ROOT/link/<some-file>` (following the symlink to the current worktree directory) and hold the file handle / begin a slow read, then `commit` and push a new change to the source repo so a sync occurs.
3. Observe that on the very next sync loop iteration, `cleanup()` → `removeStaleWorktrees()` deletes the old worktree directory (`os.RemoveAll`) essentially concurrently with (or immediately after) the symlink flip, because `time.Since(fi.ModTime()) > 0` is satisfied instantly [5](#0-4) .
4. Any new `open()` calls the consumer makes against paths under the old (now-stale) worktree during/after this window fail with `ENOENT`, demonstrating that the documented "always valid" symlink/worktree contract does not hold when `--stale-worktree-timeout` is left at its default.

Note: I could not fully execute this end-to-end in the current environment (no filesystem/terminal access here to run the actual binary and time the race), so this PoC is derived directly from reading the sync-loop, `cleanup`, and `removeStaleWorktrees` code paths and the project's own e2e test scaffolding for stale-worktree behavior; a background Devin session with terminal access would be needed to empirically confirm the exact race window size.

func (git *repoSync) removeStaleWorktrees() (int, error) {
	currentWorktree, err := git.currentWorktree()
	if err != nil {
		return 0, err
	}

	git.log.V(3).Info("cleaning up stale worktrees", "currentHash", currentWorktree.Hash())

	count := 0
	err = removeDirContentsIf(git.worktreeFor("").Path(), git.log, func(fi os.FileInfo) (bool, error) {
		// delete files that are over the stale time out, and make sure to never delete the current worktree
		if fi.Name() != currentWorktree.Hash() && time.Since(fi.ModTime()) > git.staleTimeout {
			count++
			return true, nil
		}
		return false, nil
	})
	if err != nil {
		return 0, err
	}
	return count, nil
}

// cleanup removes old worktrees and runs git's garbage collection.  The
// specified worktree is preserved.
func (git *repoSync) cleanup(ctx context.Context) error {
	// Save errors until the end.
	var cleanupErrs multiError

	// Clean up previous worktree(s).
	if n, err := git.removeStaleWorktrees(); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	} else if n == 0 {
		// We didn't clean up any worktrees, so the rest of this is moot.
		return nil
	}

function e2e::stale_worktree_timeout() {
    echo "${FUNCNAME[0]} 1" > "$REPO"/file
    git -C "$REPO" commit -qam "${FUNCNAME[0]}"
    local wt1
    wt1=$(git -C "$REPO" rev-list -n1 HEAD)
    GIT_SYNC \
        --period=100ms \
        --repo="file://$REPO" \
        --root="$ROOT" \
        --link="link" \
        --stale-worktree-timeout="5s" \
        &

    # wait for first sync
    wait_for_sync "${MAXWAIT}"
    assert_link_exists "$ROOT/link"
    assert_file_exists "$ROOT/link/file"
    assert_file_eq "$ROOT/link/file" "${FUNCNAME[0]} 1"

    # wait 2 seconds and make another commit

    echo "${FUNCNAME[0]} 2" > "$REPO"/file2
