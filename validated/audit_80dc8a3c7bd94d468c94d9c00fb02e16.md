This confirms the multi-tenant GitHub App configuration model: `Shipit.github(organization:)` looks up `secrets.github[organization]` by name (e.g. `org-a`, `org-b`), each with its own `webhook_secret`, entirely independent from repository ownership records.### Title
Webhook signature verification uses `repository.owner.login` while all `Handler` subclasses target `repository.full_name`, allowing cross-tenant forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a webhook solely against the GitHub App configured for `repository_owner` (`params.dig('repository','owner','login')`), while every `Shipit::Webhooks::Handlers::Handler` subclass (via `Handler#repository_name`/`payload.dig('repository','full_name')`) independently determines which repository/stack to mutate. Because the attacker directly POSTs raw JSON to `/webhooks` (no GitHub relay enforcing internal consistency), these two fields can be set to different organizations in a single request, letting a signature valid for org-a authorize state changes against org-b.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:

`organization_used_for_HMAC_verification (params.dig('repository','owner','login'))` == `organization_owning_the_mutated_target (payload.dig('repository','full_name').split('/').first)`

Trace:
- `WebhooksController#create` parses the raw body once and dispatches it unmodified to every registered handler: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [1](#0-0) .
- `verify_signature` derives the signing organization exclusively from `repository_owner`, i.e. `params.dig('repository','owner','login') || params.dig('organization','login')`, and validates the HMAC using `Shipit.github(organization: repository_owner)` [2](#0-1) [3](#0-2) .
- `Shipit.github(organization:)` resolves a distinct `GitHubApp` (and distinct `webhook_secret`) per named org key in `secrets.github`, confirming multi-tenant isolation is keyed purely on this one field [4](#0-3) .
- Every `Handler` subclass, however, resolves its target repository from a completely different payload path: `Handler#repository_name` returns `payload.dig('repository', 'full_name')`, used to scope `stacks` via `Repository.from_github_repo_name` [5](#0-4) . `PushHandler#process` uses this to look up and mutate stacks belonging to whatever `full_name` says, regardless of the owner used for verification [6](#0-5) . The `pull_request/*` handlers (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `UnlabeledHandler`, `AssignedHandler`, `LabelCapturingHandler`) all independently do `Shipit::Repository.from_github_repo_name(params.repository.full_name)` to find the target repository and its stacks/review-stacks [7](#0-6) [8](#0-7) .
- Nowhere in this chain is `repository.owner.login` (the field used for signature verification) checked for consistency with `repository.full_name` (the field used to select the mutated stack/repository). Since the attacker crafts the entire raw JSON body themselves (this is a direct POST to `/webhooks`, not a GitHub-relayed callback with server-side consistency guarantees), they can freely set `repository.owner.login = "org-a"` and `repository.full_name = "org-b/repo"` in the same JSON object, then sign the body with org-a's own `webhook_secret` (which they legitimately possess, having configured their own GitHub App org-a in Shipit).
- `verify_webhook_signature` only checks `HMAC(org-a_secret, raw_body) == signature`; it has no visibility into `full_name` [9](#0-8) . This passes, `drop_unhandled_event`/`check_if_ping` do not intervene for real events, and `#create` forwards the payload to handlers that act on `org-b/repo`.
- Existing guards do not close this gap: `ExplicitParameters` schemas only validate types/presence of `repository.full_name`, not cross-consistency with `repository.owner.login`; `Repository.from_github_repo_name` only performs a DB lookup by owner/name with no secret binding [10](#0-9) ; there is no `require_permission!`/session check on this unauthenticated controller.

### Impact Explanation
A single crafted, self-signed POST to `/webhooks` lets an attacker who legitimately controls their own tenant (org-a, with a real registered GitHub App and known `webhook_secret`) trigger side effects against any other tenant's repository/stack (org-b) as long as `org-b/repo` exists in Shipit's `Repository` table: enqueuing `GithubSyncJob` against org-b's stacks (push), writing `Status` records on org-b's commits (status), scheduling `RefreshCheckRunsJob` (check_suite), archiving/unarchiving/creating review stacks or updating pull request records for org-b (pull_request/*). This is a payload for one repository mutating another repository/stack's state — a cross-tenant forgery — matching the Critical impact category. It is fully repeatable against any target repository whose `full_name` the attacker knows, and is systemic to the shared `Handler#repository_name` design rather than a single handler bug.

### Likelihood Explanation
Requires: (1) Shipit configured in multi-tenant mode with ≥2 GitHub App orgs under `secrets.github` (per `github_app_config`), (2) attacker controls one of those orgs as a legitimate, unprivileged tenant (their own GitHub org/App, with its own valid `webhook_secret` they can compute an HMAC with), (3) the target org/repo exists as a `Repository` record in Shipit's database. Given those preconditions — plausible in any Shipit deployment shared across multiple orgs/teams — the attack costs a single crafted HTTP POST with a correctly computed `X-Hub-Signature`, no live GitHub interaction needed, and is trivially repeatable.

### Recommendation
Bind the verified organization to the mutated target within the same request: after computing `repository_owner` for signature verification, require that `payload.dig('repository','full_name')&.split('/')&.first` (case-insensitively) equals `repository_owner`; reject (422) on mismatch. Alternatively/additionally, propagate the verified organization into `Handler#initialize` and have `Repository.from_github_repo_name`/handler lookups scope by `(verified_organization, name)` rather than trusting `full_name` alone, so a repository can only be found under the organization whose secret actually signed the request.

### Proof of Concept
Add a minitest to `test/controllers/webhooks_controller_test.rb` parametrized over `push`, `status`, `check_suite`:
```ruby
test ":push forged cross-org payload mutates org-b's stack when signed with org-a's secret" do
  # Precondition: Shipit.github(organization: 'org-a') and Shipit.github(organization: 'org-b')
  # are both configured GitHub Apps with distinct webhook_secret values.
  org_a_secret = 'org-a-secret'
  Shipit.stubs(:github).with(organization: 'org-a').returns(stub(verify_webhook_signature: true))

  target_repo = shipit_repositories(:org_b_repo) # full_name == 'org-b/repo'
  target_stack = target_repo.stacks.first

  body = JSON.parse(payload(:push_master)).tap do |p|
    p['repository']['owner']['login'] = 'org-a'      # binds signature verification
    p['repository']['full_name']      = 'org-b/repo' # binds mutated target
  end.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', org_a_secret, body)}"

  @request.headers['X-Github-Event']  = 'push'
  @request.headers['X-Hub-Signature'] = signature

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: target_stack.id, expected_head_sha: JSON.parse(body)['after']]) do
    post :create, body:, as: :json
  end
  assert_response :ok
end
```
Assert on both sides of the equality: `params.dig('repository','owner','login') == 'org-a'` (used by `verify_signature`) while `params.dig('repository','full_name') == 'org-b/repo'` (used by `PushHandler`/`Handler#repository_name`), and that the job/status/check-run side effect lands against `org-b`'s records despite verification only ever having checked `org-a`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret
