### Title
`StatusHandler#process` resolves `Commit.where(sha:)` globally instead of scoping to the webhook's authenticated repository, allowing cross-stack `ContinuousDeliveryJob` triggering - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` across the **entire** `commits` table, with no scoping to the repository/stack that the inbound `status` webhook was actually authenticated for. Because Git SHAs are content-addressed, an attacker who legitimately controls one Shipit-tracked repository (their own fork/org, with GitHub sending a correctly-signed `status` event) can cause a status to be recorded — and consequently `ContinuousDeliveryJob` enqueued — against any other unrelated stack whose `commits` table happens to contain the same SHA (e.g. an identical vendored/upstream commit copied verbatim into multiple downstream repos).

### Finding Description
The broken binding: number of stacks affected by one authenticated `status` webhook for repository R should be `|{stacks belonging to R}|`; the actual code produces `|{stacks : ∃ commit with commits.sha == params.sha}|`, which can be any N ≥ 0 unrelated to R.

Path:
1. `WebhooksController#create` verifies the HMAC signature using `Shipit.github(organization: repository_owner)` — this authenticates that the payload was sent by GitHub for **that** organization's webhook, nothing more. [1](#0-0) 
2. It dispatches to `Shipit::Webhooks.for_event('status')` → `StatusHandler`. [2](#0-1) 
3. `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with **no scoping by repository/stack** at all. [3](#0-2) 
   - Contrast this with every other handler (`PushHandler`, `PullRequest::*Handler`), which resolve a `repository`/`stacks` scope from `params.repository.full_name` via `Handler#stacks` / `Repository.from_github_repo_name` before touching any records. [4](#0-3) [5](#0-4) 
   - `StatusHandler`'s param schema doesn't even require `repository`, confirming the repo/stack was never intended to gate the sha lookup. [6](#0-5) 
4. For each matched commit (potentially in N unrelated stacks), `create_status_from_github!` creates a `Status`, whose `after_commit :schedule_continuous_delivery` callback calls `commit.schedule_continuous_delivery`. [7](#0-6) [8](#0-7) 
5. `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob` per stack, gated only by `deployable? && stack.continuous_deployment? && stack.deployable?` — none of which check whether the *webhook's authenticated repository* matches the stack. [9](#0-8) [10](#0-9) 

Why guards fail: `verify_signature` only proves the request was sent by GitHub for the organization named in `params.repository.owner.login` — it says nothing about which stacks' commits may be mutated. `drop_unhandled_event` and the `ExplicitParameters` schema don't constrain the `sha` lookup scope. There is no `Stack`/`Repository` scoping applied before the `Commit.where(sha:)` query, unlike every sibling handler.

Exploit flow: the attacker (or anyone with legitimate write/CI access to their own GitHub-tracked repository configured in this Shipit instance) triggers a real, correctly-signed GitHub `status` webhook on their own repo for a commit SHA that is byte-identical (same tree/parents/author/committer/timestamps/message) to a commit that also exists verbatim in N unrelated victim stacks (e.g. a shared vendored dependency-bump commit cherry-picked into multiple downstream repos tracked as different Shipit stacks). One webhook then fans out `ContinuousDeliveryJob` enqueues to all N victim stacks that have `continuous_deployment?` and `deployable?` true, with no relationship to the authenticated repository.

### Impact Explanation
This is an unauthorized-deploy trigger for a repository that never authenticated the request: `ContinuousDeliveryJob` for stack X is enqueued as a side effect of a webhook that was cryptographically authenticated only for repository R (X ≠ R). This is repeatable against arbitrary victim stacks as long as a shared SHA can be produced or found, and scales to N stacks per single request. This matches the "Critical" impact category: a payload for one repository mutating another's commit/stack state and causing an unauthorized deploy trigger across tenants.

### Likelihood Explanation
Preconditions: the attacker needs a Shipit-tracked repository of their own (or any repo whose webhook signature they can satisfy — trivial for their own org) and needs an identical commit SHA to appear in the victim's `commits` table (plausible for vendored/copied commits, submodule bumps, or squash-merges of shared upstream content — the audit's premise). Given those, exploitation costs exactly one legitimate CI status POST (or GitHub Status API call) on the attacker's own commit; no secrets or privileged roles of the victim are required. Likelihood depends on the SHA-collision precondition being met in practice, which is plausible in monorepo/vendoring workflows but not universal.

### Recommendation
Scope `StatusHandler#process` (and `create_status_from_github!`) to the repository indicated in the webhook payload: require `repository.full_name` in the `params` schema and restrict the lookup to `stacks.commits.where(sha: params.sha)` (using the same `Handler#stacks`/`Repository.from_github_repo_name` pattern already used by `PushHandler` and the `PullRequest` handlers), instead of the unscoped `Commit.where(sha:)`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test ":status fans out across unrelated stacks sharing the same commit sha" do
  attacker_stack = shipit_stacks(:shipit) # repo the webhook is authenticated for
  victim_stack   = shipit_stacks(:cyclimse) # unrelated repo/org
  victim_stack.update!(continuous_deployment: true)

  shared_sha = "deadbeef" * 5
  attacker_stack.commits.create!(sha: shared_sha, ...) # deployable, matches attacker_stack
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...) # deployable, matches victim_stack

  request.headers['X-Github-Event'] = 'status'
  body = {
    sha: shared_sha, state: 'success', context: 'ci/travis',
    repository: { full_name: attacker_stack.repo_name, owner: { login: attacker_stack.repository.owner } }
  }.to_json

  assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack]) do
    post :create, body: body, as: :json
  end
end
```
Binding to assert before/after: expected enqueues for `victim_stack` == `0` (only `attacker_stack` should be affected by a webhook authenticated for it); actual enqueues for `victim_stack` == `1`, proving the divergence.
