### Title
Unbound `creator` Account in `initialize_with_permission` Allows Permanent Freezing of Creator-Fee Funds - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` accepts a `creator` account with no `Signer` requirement and no `address =` constraint tying it to the `payer` (the account whose `Permission` PDA is actually validated). This decouples the authorization check (which validates `payer` via the `permission` PDA seeded on `payer.key()`) from the field that is actually granted perpetual, privileged rights on-chain (`pool_state.pool_creator`). This is the same bug class as CVE-2017-15206: a caller can alter the submitted "form data" (here, an unconstrained instruction account) to bind a privileged, persistent relationship to an arbitrary address that was never authenticated for that role.

### Finding Description
Compare the two pool-creation paths:

- In `Initialize` (permissionless path), `creator` is a `Signer<'info>`, so the recorded `pool_state.pool_creator` is guaranteed to be the actual transaction signer: [1](#0-0) 

- In `InitializeWithPermission`, `creator` is declared as an `UncheckedAccount<'info>` with only a `/// CHECK:` comment, no `Signer` bound and no constraint relating it to `payer` or to the `permission` PDA: [2](#0-1) 

The instruction's actual authorization gate is the `permission` account, which is a PDA derived from `payer.key()`: [3](#0-2) 

However, the value ultimately persisted as the privileged `pool_creator` field comes from the unconstrained `creator` account, not from `payer`: [4](#0-3) 

`pool_creator` is a durable, privileged identity: it is the sole address permitted to sign `collect_creator_fee`, and the sole beneficiary address for `collect_creator_fee_permissionless` (which anyone can invoke, but which always routes accumulated fees to whatever address is recorded as `pool_creator`): [5](#0-4) [6](#0-5) 

Because `creator` in `InitializeWithPermission` is never validated to be the `payer`, a signer, or otherwise attested, the party who actually satisfies the permission check (`payer`) can supply *any* attacker-chosen pubkey as `creator` at pool-creation time — including an address with no discoverable private key (e.g., a deliberately off-curve/unreachable pubkey, or a PDA of an unrelated program that can never sign a transaction).

### Impact Explanation
Every swap into this pool accrues `creator_fees_token_0`/`creator_fees_token_1` inside `PoolState`, funded by real swapper trading fees. If `pool_creator` is set to an address with no reachable signing authority:
- `collect_creator_fee` can never succeed, because it requires `creator` to be a `Signer` matching `pool_creator`.
- `collect_creator_fee_permissionless` will still succeed in creating an ATA and depositing the accrued creator fees to that ATA, but because nobody controls the private key for that address, the tokens sitting in that ATA can never be withdrawn.

This results in permanent, irreversible freezing of the creator-fee portion of every swap fee collected by that pool — funds that are contributed by ordinary swappers as part of their trade and can never be recovered by anyone. This satisfies the "permanent freezing of user funds" bar in the validation criteria.

### Likelihood Explanation
The path is reachable from a single, self-contained transaction (`initialize_with_permission`) by any account that already holds (or can obtain) a `Permission` PDA as `payer`; the `creator` field is fully attacker-controlled instruction data with no additional signature or account-derivation requirement. Because `initialize_with_permission` is listed as an in-scope, reachable instruction and the mismatch between the authorization target (`payer`/`permission`) and the recorded privileged identity (`creator`) is a straightforward account-substitution, this is a low-complexity, high-confidence bug once triggered — the only requirement is that the caller controls the `payer`/`permission` role, which is the account meant to be trusted for pool creation, not for arbitrarily assigning third-party or unclaimable fee-beneficiary addresses.

### Recommendation
Add an explicit binding for the `creator` account in `InitializeWithPermission`, matching the pattern used in `Initialize`: either require `creator` to be a `Signer`, or add `#[account(address = payer.key())]` (or equivalent) so the field that is authorization-checked (`payer`/`permission`) is the same field persisted as `pool_state.pool_creator`. Alternatively, if a distinct beneficiary address is a desired product feature, require the designated `creator` to co-sign the transaction to prove key ownership before being recorded as the perpetual fee recipient.

### Proof of Concept
1. Attacker obtains/holds a valid `Permission` PDA for `payer = attacker_payer` (satisfying the `permission` seeds check in `InitializeWithPermission`). [3](#0-2) 
2. Attacker submits `initialize_with_permission` supplying `creator` = an off-curve pubkey (or any address whose private key does not exist/is not attacker-controlled and cannot sign).
3. Because `creator` has no `Signer` or `address` constraint, the instruction succeeds, and `pool_state.initialize(...)` stores this arbitrary pubkey as `pool_creator`. [4](#0-3) 
4. Swaps against the new pool accrue `creator_fees_token_0/1` in `PoolState`.
5. `collect_creator_fee` can never be called (no signer for `pool_creator`); `collect_creator_fee_permissionless` deposits fees into an ATA owned by the unreachable address, permanently locking those funds. [7](#0-6) 

**Note on completeness:** I was unable to inspect `programs/cp-swap/src/instructions/admin/create_permission_pda.rs` before running out of tool iterations, so I cannot confirm whether obtaining a `Permission` PDA itself requires an admin/privileged action or is permissionless. If `Permission` PDA issuance is admin-gated, the "payer" role in this path may already carry elevated trust, which would somewhat narrow (but not eliminate) the applicability of this finding, since the core bug — an unconstrained `creator` account decoupled from the actual authorization target — remains regardless of who can become `payer`.

```rust
pub fn collect_creator_fee_permissionless(
    ctx: Context<CollectCreatorFeePermissionless>,
) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;
```
