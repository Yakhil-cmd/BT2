### Title
Webhook signature authenticates the wrong organization, allowing forged commit statuses to trigger unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate a request against using an **attacker-controlled** field of the very payload being verified (`repository.owner.login`), while the event handlers act on a **different, independently attacker-controlled** field of the same payload (`repository.full_name`). Because nothing binds these two fields together, an operator/attacker who legitimately controls the webhook secret for one organization configured in Shipit can forge a webhook whose signature validates against their own secret, but whose `repository.full_name` points at a completely different (victim) repository/stack. For the `status` event, this lets the attacker inject a fabricated "success" `Status` for an arbitrary commit SHA in the victim stack, which can flip `deployable?` and trigger an unauthorized continuous deployment.

### Finding Description
`verify_signature` computes the organization used to look up the webhook secret purely from the untrusted payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns the `GithubApp`/`GithubOAuth` instance configured for whatever `login` appears in `repository.owner.login` of the incoming JSON. In Shipit's supported multi-organization configuration (`config/secrets.*.yml` shows multiple orgs each with their own `webhook_secret`), each organization has its own independent secret. If a request's HMAC signature validates against organization A's secret, the controller considers the whole payload authentic and dispatches it to handlers unmodified: [3](#0-2) 

However, every `Handler` subclass resolves the *target* repository/stack from a **separate field** of the same payload — `repository.full_name` — with no cross-check against `repository.owner.login`: [4](#0-3) 

Nothing enforces `full_name.split('/').first == repository.owner.login`. An attacker who controls (or knows) the `webhook_secret` for organization "attacker-org" — a value they are entitled to know because they administer that org's GitHub App/webhook in this Shipit instance — can build a payload where:
- `repository.owner.login = "attacker-org"` (used only to pick the secret for signature verification, which they satisfy trivially since it's their own secret)
- `repository.full_name = "victim-org/victim-repo"` (used by the handler to resolve the actual `Repository`/`Stack` acted upon)

This breaks exactly the binding class called out in scope: *"an organization that authenticated versus the repository that is written."*

The concrete high-impact instance of this is the `status` webhook. As shown by the existing test, whatever `state`, `context`, `target_url`, and `description` appear in the payload are written verbatim into a new `Status` record for the resolved commit, without any independent verification against GitHub's API: [5](#0-4) 

A newly created/updated `Status` feeds directly into `Commit#status`, `deployable?`, and — critically — `schedule_continuous_delivery`, which enqueues an actual deploy job once a commit becomes deployable under continuous deployment: [6](#0-5) [7](#0-6) 

### Impact Explanation
Any party holding webhook credentials for one org served by a shared/multi-tenant Shipit deployment can forge a "success" status for a commit belonging to an entirely different organization's stack. Combined with `continuous_deployment?`, this can cause Shipit to autonomously deploy a commit that never actually passed CI — an unauthorized deploy driven purely by cross-organization webhook spoofing, satisfying the Critical impact bar ("an unauthorized deploy").

### Likelihood Explanation
Exploitation only requires: (1) the target Shipit instance is configured with more than one organization/webhook secret (a documented, supported configuration per `config/secrets.development.shopify.yml`), and (2) the attacker legitimately possesses the webhook secret for at least one of those organizations. No access to the victim organization, no `ApiClient` token, and no GitHub App private key are required — only crafting one HTTP POST with a correctly-shaped JSON body and a correctly-computed HMAC using the attacker's own secret.

### Recommendation
In `WebhooksController#verify_signature` (or in the base `Handler`), enforce that the organization used to select the webhook secret is the same organization implied by `repository.full_name` (and by `organization.login` for org-level events) before dispatching to any handler. Reject the request if these are inconsistent.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret known to the attacker) and `victim-org` (hosts the stack to be attacked), per `config/secrets.development.shopify.yml`'s multi-org format.
2. Build a `status` webhook JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://example.com",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Compute `X-Hub-Signature` as `sha1=` + HMAC-SHA1 of the raw body using `attacker-org`'s `webhook_secret`.
4. POST to `/github/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, verifies successfully using the attacker's own secret.
6. `Handler#stacks` resolves the target via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, and `StatusHandler` (per the behavior exercised in `test/controllers/webhooks_controller_test.rb:42-59`) creates a `success` `Status` on the victim's commit.
7. If `victim-org/victim-repo`'s stack has continuous deployment enabled and this status satisfies the required checks, `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob`, deploying the commit.
