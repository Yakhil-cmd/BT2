### Title
Webhook signature is verified against the organization owner but the handlers act on an attacker-controlled `repository.full_name` field, allowing cross-organization stack writes - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
The external report's root cause is a decimals/scale mismatch between the value that is validated (NAV rate, in liquidation-token decimals) and the value that is actually used/returned (share amount, expected in share-token decimals) — i.e., the thing that's checked and the thing that's acted upon are not the same unit. The same class of bug (verify one field, act on another, unsynchronized field within the same trusted payload) is reachable in Shipit's webhook ingestion pipeline: the field used to select the HMAC secret for signature verification is not the same field used to resolve which repository/stacks are subsequently written to.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App (and therefore the `webhook_secret` used for HMAC verification) using: [1](#0-0) [2](#0-1) 
i.e. `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`.

Meanwhile, every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, pull-request handlers, etc.) resolves the target `Repository`/`Stack` to operate on via a *different* JSON field, `repository.full_name`, through the shared base class: [3](#0-2) 

Both `repository.owner.login` and `repository.full_name` are attacker-supplied JSON keys inside the same POST body. The code never asserts that `repository.full_name`'s owner segment equals `repository.owner.login`. In the intended flow (a genuine GitHub-generated webhook) these two fields always agree because GitHub populates the whole `repository` object consistently. But the code accepts *any* raw POST body along with a matching `X-Hub-Signature`, and the HMAC only proves that "whoever computed this signature knows the `webhook_secret` for the organization identified by `repository.owner.login`" — it says nothing about which repository the payload's `full_name` names.

This breaks the binding: `organization that authenticated == repository that is written`. Before the fix, in the intended design these two must always be the same tenant. An attacker who legitimately knows the `webhook_secret` for their own installed GitHub App/organization (org A — a normal, unprivileged tenant in a multi-org Shipit deployment, as documented in `docs/setup.md`'s "Using Multiple Github Applications" section) can craft a payload where `repository.owner.login` is `"orgA"` (so `verify_signature` looks up and validates against orgA's secret) but `repository.full_name` is `"orgB/some-repo"` (so the handler resolves and writes to org B's `Stack`s), computing a completely valid HMAC-SHA1 signature with the secret they legitimately possess.

### Impact Explanation
This allows a user who only controls one tenant/organization's GitHub App webhook secret to forge webhook events that make Shipit act on a *different* organization's stacks — e.g., trigger `GithubSyncJob`/`stack.sync_github(expected_head_sha: ...)` via `PushHandler` for an arbitrary victim repository/stack, or manipulate commit statuses via `StatusHandler`, or otherwise inject organization/membership data cross-tenant via `MembershipHandler`. Depending on how `sync_github`/status updates feed into deploy eligibility (e.g., CI status gating, merge-queue processing), this can influence which commit is considered deployable/mergeable on a stack the attacker does not own, which is an unauthorized-deploy-adjacent authorization escalation across the organization boundary that the webhook signature is supposed to enforce.

### Likelihood Explanation
Exploitability requires only knowledge of a legitimately-configured `webhook_secret` for *some* organization onboarded to the shared Shipit instance — this is available to any tenant admin in a multi-org Shipit deployment (a normal, unprivileged-relative-to-other-tenants position), not a Shipit operator/privileged account and not a compromise of another tenant's secret. No repository write access, GitHub App private key, or Shipit session/API token is needed. The request is a plain unauthenticated POST to `/webhooks` with a crafted JSON body and computed HMAC.

### Recommendation
In `WebhooksController#verify_signature` (and/or `Shipit::Webhooks::Handlers::Handler#repository_name`), enforce that the organization/owner used to select the verifying `webhook_secret` is the same value used by the handler to resolve the acted-upon repository — e.g., derive both from a single canonical field (`repository.full_name`'s owner segment), or explicitly assert `repository.owner.login == repository.full_name.split('/').first` before dispatching to handlers, rejecting mismatches with 422.

### Proof of Concept
1. Attacker is an admin of `orgA`, a legitimate GitHub App organization configured in Shipit's `config/secrets.yml`, and therefore knows `orgA`'s `webhook_secret`.
2. Attacker crafts a push-event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` and successfully verifies the signature against orgA's secret [4](#0-3) .
5. `PushHandler#process` (via `Handler#stacks`/`#repository_name`) resolves `Repository.from_github_repo_name("orgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on org B's stack [5](#0-4) [3](#0-2) , despite the attacker never having proven any credential tied to org B.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
