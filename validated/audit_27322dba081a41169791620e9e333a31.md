### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while the `status` handler trusts the payload's commit SHA across the entire instance, letting any org with the GitHub App installed forge deploy-blocking/allowing statuses for commits belonging to a different repository's stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the webhook secret) used to validate the HMAC signature based on a field taken directly from the untrusted payload body — `repository.owner.login` or, if absent, `organization.login` — via `repository_owner`. [1](#0-0) [2](#0-1)  The engine explicitly supports "Multiple GitHub Applications", one per organization, each with its own `webhook_secret` known to that organization's own admins. [3](#0-2)  After the HMAC check passes, the dispatched handler for the `status` event resolves the target purely by commit SHA, with **no repository/organization scoping at all**: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [4](#0-3) 

### Finding Description
This mirrors the H-9 bug class: one field (`repository.owner.login`, which selects the signing/verification context — analogous to the oracle price feed selection) is used to authorize the request, while a *different* field consumed downstream (`sha`, used by `StatusHandler` to pick which `Commit` record — and, transitively, which repository's stack — gets acted upon) is never bound to that same authorization context.

The binding that should hold is:
`organization whose secret validated the signature == organization owning the repository/commit actually written`

This binding is broken because:
1. An attacker who administers Organization A can install the Shipit GitHub App on Org A (a legitimate, unprivileged action for their own org) and thus legitimately knows Org A's `webhook_secret`.
2. They craft an arbitrary JSON body: `{"repository": {"owner": {"login": "orgA"}}, "sha": "<victim-commit-sha-from-org-B-stack>", "state": "success", ...}`.
3. `verify_signature` computes `repository_owner = "orgA"`, fetches `Shipit.github(organization: "orgA")`, and validates the HMAC using Org A's own secret — which succeeds, since the attacker legitimately knows it. [1](#0-0) 
4. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which looks up `Commit.where(sha: params.sha)` — a global, unscoped table lookup across *all* stacks/repositories in the instance — and calls `create_status_from_github!` to persist attacker-controlled `state`, `description`, `target_url`, and `context`. [5](#0-4) 
5. `Commit#create_status_from_github!` → `add_status` recomputes `Commit#status`, which feeds `deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) and triggers `stack.schedule_merges` when the injected status is `success`/`pending`. [6](#0-5) [7](#0-6)  This is the same mechanism `RefreshCheckRunsJob`/`ContinuousDeliveryJob` and `merge_status` rely on to gate deploys/merges.

Compare before/after the attacker's forged request:
- Before: only a status webhook whose HMAC is signed with the secret of the organization that actually owns the target repository (verified against the real repo's App config) can update that repository's commit statuses.
- After: any organization on which the Shipit GitHub App is installed (a fully unprivileged action relative to the target repo) can forge a `status` webhook whose signature validates under its *own* secret while writing a status onto a commit belonging to a completely different, unrelated stack — because `StatusHandler` never checks that `params.repository` (or any repo/org field) matches the commit's actual `stack.repository`.

### Impact Explanation
This crosses the "escalation into `Shipit.github_teams` authorization"/"unauthorized deploy" bar: forging a `success` (or matching required-context) status on a victim stack's blocking commit can flip `Commit#deployable?` to true and trigger `stack.schedule_merges`/continuous deployment, effectively causing Shipit to merge or deploy a commit whose CI has not actually passed on the real repository — an unauthorized deploy/merge decision driven entirely by a party with no privileges on the victim repository, only the ability to install the GitHub App on some other org (a normal, expected admin action for their own org, not the victim's).

### Likelihood Explanation
Requires only that the attacker administers/controls a GitHub organization that has the Shipit GitHub App installed (a standard, low-privilege scenario supported and documented for multi-org deployments), plus knowledge of a target commit SHA on the victim stack (SHAs are not secret — they're visible in PRs, CI, GitHub UI). No access to the victim's `webhook_secret`, `ApiClient` tokens, or `github_access_token` is needed.

### Recommendation
Bind the verified signing context to the data actually acted upon: after `verify_signature` succeeds for organization X, `StatusHandler` (and any other handler that doesn't already scope by `payload.dig('repository','full_name')`) must additionally verify that the resolved `Commit`'s `stack.repository.owner` matches the organization/app that produced a valid signature for this request, rejecting cross-organization status/commit writes. At minimum, `StatusHandler` should scope its `Commit` lookup through `stacks` (as `PushHandler` and pull-request handlers already do via `Repository.from_github_repo_name`) rather than a bare, instance-wide `Commit.where(sha:)`.

### Proof of Concept
1. Attacker administers GitHub org `orgA`, installs the Shipit GitHub App there, and is given `webhook_secret_A` (visible in their own app settings, per `docs/setup.md`).
2. Attacker learns the commit SHA `victim_sha` of a commit in `orgB/private-repo`'s Shipit stack (e.g. from a public PR or exposed status page).
3. Attacker builds payload:
```json
{"repository": {"owner": {"login": "orgA"}}, "sha": "victim_sha", "state": "success", "context": "ci/required-check"}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, payload)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner => "orgA"`, calls `Shipit.github(organization: "orgA")`, and `verify_webhook_signature` succeeds since the attacker's own secret matches. [1](#0-0) 
6. `StatusHandler#process` finds the `Commit` with `sha == victim_sha` in `orgB`'s stack (unrelated to `orgA`) and writes the forged `success` status. [4](#0-3) 
7. If this was the last blocking status, `Commit#deployable?` flips true and `schedule_merges`/continuous delivery may act on it. [6](#0-5)

module Shipit

          accepts :context, String

          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|

          end
        end
