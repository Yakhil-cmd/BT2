### Title
API client scoped to one stack can read any stack's build status via CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
### Finding Description
`Shipit::Api::BaseController` enforces per-`ApiClient` stack scoping through a `stacks` collection method that restricts visible stacks to the client's assigned `stack_id` when one is set: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and the default `stack` accessor resolves records through that scoped collection (`stacks.from_param!(params[:stack_id])`). [1](#0-0) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely, resolving the stack directly from the global `Stack` model regardless of which stack the authenticated `ApiClient` is bound to: [2](#0-1) 

The controller's authorization check, `require_permission :read, :stack`, only verifies that the token carries the `read:stack` permission string via `ApiClient#check_permissions!`, which is a pure permission-name membership check with no awareness of which stack is being requested: [3](#0-2) 

This breaks the intended binding: **stack a token authorizes == stack it touches**. An `ApiClient` created with `stack_id` set (i.e., scoped to a single stack, as seen in the `here_come_the_walrus` fixture) is supposed to only ever operate on that one stack, matching the pattern enforced everywhere else (e.g. `Api::HooksController#stack_id`, `Api::StacksController#stacks`). [4](#0-3) 

Because `CCMenuController#stack` calls `Stack.from_param!` (unscoped) instead of `stacks.from_param!` (scoped), a client scoped to Stack A can request `/api/stacks/:owner/:repo/:env/ccmenu?token=<A's token>` for Stack B and receive Stack B's data.

### Impact Explanation
The endpoint exposes unauthenticated-read-worthy state: latest deploy id, start/end time, running status, and build status/label for the target stack (rendered from the `shipit/ccmenu/project` template using `latest_deploy` and `stack`). This is an authenticated read across a repository/stack boundary the token was never granted — a High-severity issue per the rubric ("unauthenticated read of stack state ... via an authorization scope escalation"), since a client explicitly scoped to one stack can read the deploy/build status of any other stack in the installation, including private/internal repositories the client's owner may have no access to.

### Likelihood Explanation
Any holder of a legitimately-issued, single-stack-scoped `ApiClient` token (e.g. one created for a CI dashboard or a single team's stack) can immediately exploit this by simply supplying a different `stack_id` in the URL — no privilege escalation, no additional secrets, and no interaction with other users required. The `CCMenuController` allows token-in-query-string auth (`params[:token]`) which makes probing other stack identifiers trivial once the URL scheme (`owner/name/environment`) is known or guessed.

### Recommendation
Remove the custom `stack` override in `Shipit::Api::CCMenuController` (or make it delegate to the scoped `stacks` collection from `BaseController`) so it resolves via `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`, ensuring stack-scoped `ApiClient`s cannot resolve stacks outside their authorized scope.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to Stack A only, e.g. fixture `here_come_the_walrus` with `stack: shipit`, permission `read:stack`. [4](#0-3) 
2. Compute this token's `authentication_token`.
3. Send `GET /api/stacks/<other_owner>/<other_repo>/<other_env>/ccmenu?token=<token>` for a stack this client is not scoped to.
4. `CCMenuController#authenticate_api_client` authenticates the token via `ApiClient.authenticate(params[:token])`; `require_permission :read, :stack` passes because the client does hold `read:stack` permission (just for a different stack); `stack` resolves via unscoped `Stack.from_param!`, returning the other stack's record; `show` renders that stack's `latest_deploy` and status — leaking cross-stack deploy state to a token never authorized for that stack. [5](#0-4)
