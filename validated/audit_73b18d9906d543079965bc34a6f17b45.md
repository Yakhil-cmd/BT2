### Title
Asset attestor-list update instantly revokes spending rights of previously‑attested holders, freezing their already‑issued asset funds - (File: `validation.js`, `storage.js`)

### Summary
For a `spender_attested` asset, the definer can publish an `asset_attestors` message at any time to change the list of attestor addresses that authorize spending. Payment validation checks the sender against only the *current, latest* attestor list rather than the list that was in effect (or their attestation status) when the funds were issued/received. Consequently, a definer who updates/removes attestors — even for entirely legitimate reasons such as rotating attestor keys or deprecating a stale attestor — instantly and irrecoverably freezes the balances of any address that is no longer covered by the new list, exactly analogous to the reported issue where removing a reward token stranded users' already‑accrued rewards.

### Finding Description
`validateAttestorListUpdate` allows the asset definer to publish a new attestor list for a `spender_attested` asset with no restriction other than being single‑authored and validly formatted: [1](#0-0) 

When a payment spending this asset is validated, `validatePayment` requires `objAsset.arrAttestedAddresses` (built from the *latest* attestor list) to contain the issuer/spender address: [2](#0-1) 

The attestor list used for this check is resolved in `storage.js`'s `readAsset`, which explicitly looks up only the single most-recently published attestor-list unit for the asset and uses that as the sole source of truth — it does not track which addresses were attested at the time each holder acquired the asset: [3](#0-2) 

Because the spending check is evaluated against the current attestor list at spend time (not at receipt time), any address holding a balance of the asset that was valid when received becomes permanently unspendable the moment the definer publishes a new `asset_attestors` list that excludes it — with no check of outstanding balances, no grace period, and no compensation mechanism, mirroring the "no check for outstanding funds before removal" flaw described in the reference report for `removeInternalRewardToken`/`removeExternalRewardToken`.

### Impact Explanation
This is a concrete AA/user fund freezing scenario: legitimate holders of a `spender_attested` asset lose the ability to spend (transfer) their existing balance the instant the definer rotates or narrows the attestor list, with no way to recover access short of the definer re-adding them. Since asset issuance/transfer conditions are core protocol logic reachable by any asset issuer (a normal, unprivileged-in-consensus actor who merely defined an asset), and the loss applies to any counterpaty holding that asset, this matches the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: attestor rotation is an expected, routine maintenance operation (e.g., replacing a compromised or retiring attestor address) for any `spender_attested` asset, not an edge case. Every such update silently freezes any holder who fails to fall under the new list, and there is no explicit warning, migration path, or check in the codebase preventing this.

### Recommendation
- Track attestation status per holder at the time of each transfer/issuance (e.g., snapshot attestation into the output/UTXO metadata) rather than re-checking against the live attestor list on every subsequent spend, or
- Require that removed/added attestor-list updates cannot retroactively invalidate addresses that already hold a balance until they have had an opportunity to move funds, or
- At minimum, document/enforce that attestor-list changes only affect future issuance, and provide an explicit mechanism (e.g., a grace-period spend allowance for the previous list) so that existing balances are not instantly frozen.

### Proof of Concept
1. Definer creates asset `X` with `spender_attested: true` and attestor list `[A]`.
2. Attestor `A` attests address `U`; `U` receives/holds a payment of asset `X` (validated fine because `U` is in `arrAttestedAddresses`).
3. Definer publishes `asset_attestors` message changing the attestor list to `[B]` (removing `A`), which is accepted by `validateAttestorListUpdate` (`validation.js:2829-2848`) with no check of outstanding `X` balances.
4. `U` attempts to spend their held `X` tokens. `storage.readAsset`'s `addAttestorsIfNecessary` (`storage.js:1917-1946`) resolves the attestor list to the new list `[B]`; `arrAttestedAddresses` no longer contains `U`.
5. `validatePayment` (`validation.js:2115-2122`) rejects the spend with `"none of the authors is attested"` even though `U`'s balance was legitimately received before the list change — `U`'s funds are now permanently frozen.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
