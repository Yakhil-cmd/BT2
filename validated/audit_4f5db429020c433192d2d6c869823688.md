### Title
Missing `isRunning` Guard on Bridge Handle Functions Allows Asset Transfers When Bridge Is Stopped — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge has an `isRunning` flag (the direct analog of `whenNotPaused`) that the owner can set to `false` to halt the bridge. All three **request** functions enforce this flag, but all three **handle** functions — which actually move assets — do not. When the bridge is stopped, operators can still call `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` to drain or mint assets on the destination side.

---

### Finding Description

`BridgeTransfer.sol` declares the stop flag and its setter: [1](#0-0) 

The three request-side functions correctly enforce it:

- `_requestKLAYTransfer`: [2](#0-1) 
- `_requestERC20Transfer`: [3](#0-2) 
- `_requestERC721Transfer`: [4](#0-3) 

The three handle-side functions that actually disburse assets have **no `isRunning` check**:

- `handleKLAYTransfer` — sends native KLAY to `_to` via `.call.value()`: [5](#0-4) 
- `handleERC20Transfer` — mints or `safeTransfer`s ERC20 tokens to `_to`: [6](#0-5) 
- `handleERC721Transfer` — mints or `transferFrom`s ERC721 tokens to `_to`: [7](#0-6) 

---

### Impact Explanation

When the bridge owner calls `setRunningStatus(false)` — the intended emergency stop — new cross-chain requests are blocked on the source side. However, operators (a separate, lower-privilege role) can still call any of the three handle functions to settle transfers on the destination side. In `modeMintBurn = false` mode this drains the bridge's locked KLAY/ERC20/ERC721 reserves; in `modeMintBurn = true` mode it mints unbounded tokens to arbitrary recipients. The owner's emergency halt is therefore only half-effective: asset outflow continues unimpeded.

The default operator threshold is 1, meaning a single operator suffices to execute a handle call. [8](#0-7) 

---

### Likelihood Explanation

The scenario is realistic: bridge operators are a distinct, semi-trusted role registered by the owner. The owner stops the bridge in response to an incident (e.g., fraudulent requests already submitted on the source chain). Because the handle functions ignore `isRunning`, operators — acting normally or under compromise — continue to settle those fraudulent requests after the halt, defeating the purpose of the stop mechanism.

---

### Recommendation

Add an `isRunning` guard to all three handle functions, mirroring the pattern already used on the request side:

```solidity
// BridgeTransferKLAY.sol
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
    require(isRunning, "stopped bridge");   // ADD THIS
    ...
}

// BridgeTransferERC20.sol
function handleERC20Transfer(...) public onlyOperators {
    require(isRunning, "stopped bridge");   // ADD THIS
    ...
}

// BridgeTransferERC721.sol
function handleERC721Transfer(...) public onlyOperators {
    require(isRunning, "stopped bridge");   // ADD THIS
    ...
}
```

Alternatively, introduce a shared `whenRunning` modifier in `BridgeTransfer` and apply it uniformly to all six public entry points.

---

### Proof of Concept

1. Owner deploys bridge in lock-transfer mode (`modeMintBurn = false`), charges it with 100 KLAY via `chargeWithoutEvent`.
2. A fraudulent `RequestValueTransfer` event is emitted on the source chain (e.g., via an exploit).
3. Owner detects the incident and calls `setRunningStatus(false)`. `isRunning` is now `false`.
4. Operator calls `handleKLAYTransfer(txHash, attacker, attacker, 100 ether, 0, blockNum, "")`.
5. Because `handleKLAYTransfer` has no `isRunning` check, the call succeeds: `_voteValueTransfer` passes (threshold = 1), and `_to.call.value(100 ether)("")` sends all 100 KLAY to the attacker.
6. The bridge is drained despite the owner's emergency stop. [5](#0-4) [9](#0-8)
