## Analysis

This confirms the exploitable path. In multi-org mode (`config/secrets.yml` using top-level org keys, documented in `docs/setup.md:182-209`), each GitHub organization has its own `webhook_secret`. `Shipit.github(organization:)` selects the app/secret purely by the `organization` string passed in [1](#0-0) , and `WebhooksController#verify_signature` derives that `organization` argument straight from the **unverified** JSON body (`repository.owner.login` / `organization.login`) before the signature is checked [2](#0-1) [3](#0-2) . Once `verify_signature` passes, the handlers dispatch entirely on a *separate* payload field, `repository.full_name`, to find the target `Repository`/`Stack` [4](#0-3) , e.g. `PushHandler#process` syncs any stack matching that repo/branch [5](#0-4) , and `StatusHandler#process` writes CI status onto commits matched only by `sha` [6](#0-5) .

Because the field used to select *which secret verifies the signature* (`repository.owner.login`/`organization.login`) is never checked for equality against the field used to select *which repository/stack the handler acts on* (`repository.full_name`), an attacker who legitimately controls one org onboarded to this Shipit instance (and therefore knows/can derive that org's `webhook_secret` HMAC by observing its own real webhook deliveries) can forge a raw HTTP POST directly to `/github_webhooks` with `organization.login` (or `repository.owner.login`) set to their own org (to pass signature verification) while setting `repository.full_name` to a victim repository belonging to a completely different, unrelated org also configured on the same Shipit instance. This breaks the binding: `organization that authenticates the request == repository that gets written`.

### Title
Webhook signature is verified against an organization named in the unsigned payload while handlers act on an independent `repository.full_name` field, allowing cross-organization stack manipulation - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to validate `X-Hub-Signature` against based on `repository.owner.login` (or `organization.login`) taken from the raw, not-yet-verified JSON body. `Handler#stacks`/`#repository_name` then dispatch the actual write (push sync, commit status, membership, PR handling, etc.) based on the unrelated `repository.full_name` field of the same payload. Nothing enforces that these two payload fields refer to the same organization, so a valid signature computed with Org A's secret can be replayed with `repository.full_name` pointed at Org B's repository.

### Finding Description
- `verify_signature` computes `repository_owner` from the attacker-controlled JSON body, fetches `Shipit.github(organization: repository_owner)`, and checks the HMAC against that organization's `webhook_secret` [7](#0-6) .
- In multi-org deployments, each org has an independent `webhook_secret` [8](#0-7) , and `Shipit.github` looks up config purely by that string key [9](#0-8) .
- After the `before_action` passes, `WebhooksController#create` dispatches the parsed body to handlers [10](#0-9) .
- Handlers resolve the target `Stack`/`Repository`/`Commit` using `payload.dig('repository', 'full_name')` [4](#0-3)  — a field completely independent from the one used for signature-org selection.
- Nothing compares `repository.owner.login` to the owner portion of `repository.full_name`, so the two can diverge freely in an attacker-crafted payload.

The bug-class mirrors the reported nonce issue: a value used to satisfy the verification check (`nonce`/`organization`) is not the same value bound to the action actually performed (`vote`/`repository written`), so a check that appears to authenticate the caller does not actually authenticate the specific object being mutated.

### Impact Explanation
An attacker who is a legitimate member/admin of Organization A (with the Shipit GitHub App installed, hence they can trivially learn A's `webhook_secret` by installing a webhook-forwarding proxy or by triggering and inspecting their own org's deliveries) can forge signed-looking webhook requests that make Shipit believe events came from Organization B — a different tenant configured on the very same instance. Depending on the handler this can:
- Trigger `GithubSyncJob`/`sync_github` on Org B's stacks (`push` event) [5](#0-4) .
- Inject arbitrary/forged commit CI statuses for Org B's commits (`status` event), which can flip a commit's `deployable?` state and let it pass required-CI gates for an actual deploy [6](#0-5) .
This constitutes a cross-tenant integrity break enabling unauthorized influence over another organization's deploy pipeline (falls under "cross-repository writes" / unauthorized deploy pre-conditions).

### Likelihood Explanation
Requires: (1) the host application to run Shipit in the documented multi-organization configuration mode (explicitly documented and supported: `docs/setup.md:182-209`), and (2) attacker control of at least one onboarded organization's GitHub App installation (i.e., legitimate access to *some* tenant, not the target tenant). This is a real deployment mode, not a hypothetical misconfiguration, and no repository write access or Shipit session/API token is needed to exploit it — only knowledge of one tenant's webhook secret, which any admin of that tenant's GitHub org can obtain.

### Recommendation
After identifying the organization used for signature verification, re-derive the target repository/stack strictly from that same trusted organization value rather than trusting `repository.full_name` independently. Concretely: extract `repository_owner` once, verify the signature with that org's secret, and pass the trusted organization down into `Handler#stacks`, rejecting (422) any payload where `repository.full_name`'s owner segment does not case-insensitively match the verified `repository_owner`.

### Proof of Concept
1. Configure Shipit in multi-org mode with `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md` multi-org example).
2. As an admin of `OrgA`, install the Shipit GitHub App on `OrgA` and observe/derive `OrgA`'s `webhook_secret` (e.g., from your own delivered webhooks / GitHub App settings you control).
3. Craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac>` using `OrgA`'s `webhook_secret` over the exact raw body.
5. POST to `/github_webhooks` with header `X-Github-Event: push`. `verify_signature` resolves `repository_owner` to `OrgA`, verifies successfully against `OrgA`'s secret [2](#0-1) .
6. `PushHandler` then loads `Repository.from_github_repo_name("OrgB/victim-repo")` via `repository.full_name` and calls `sync_github` on `OrgB`'s stacks [5](#0-4) [4](#0-3)  — despite the request never having been signed by `OrgB`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:

      webhook_secret:
