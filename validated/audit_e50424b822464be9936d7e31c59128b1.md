## Analog Found

### Title
AA trigger senders can be griefed via front-running that drains the AA's spendable outputs before their trigger is processed - (File: aa_composer.js)

### Summary
The reported bug lets an attacker front-run a `flash()` call and shrink the contract's token balance by a trivial amount, so the victim's balance check reverts and the whole legitimate operation fails. The equivalent pattern exists in ocore's Autonomous Agent (AA) payment-composition logic: when an AA has to send funds in response to a trigger, it looks for currently *unspent* outputs owned by the AA address, and if not enough are found the whole response bounces, consuming the trigger sender's bounce fee.

### Finding Description
When an AA composes an outgoing payment, `completePaymentPayload()` computes a `target_amount` and then scans the AA's own unspent UTXOs to cover it: [1](#0-0) [2](#0-1) 

If the sum of currently-unspent outputs owned by the AA (queried with `is_spent=0`, ordered deterministically by `main_chain_index, unit, output_index` / `latest_included_mc_index, level, ...`) is insufficient, the function calls back with `'not enough funds for ' + target_amount + ' bytes'` (or asset), which propagates to `bounce(err)`: [3](#0-2) 

`bounce()` then returns the trigger's coins minus `bounce_fees` to the sender — the fee is permanently lost: [4](#0-3) 

Because the outputs available at the AA's address are a *shared pool* consumed in whatever DAG order the units end up stabilizing in, an attacker can post a cheap trigger to the same AA that causes it to legitimately spend down its own outputs (e.g. a small withdrawal/order/response covered by the AA's own logic) so that it stabilizes/gets processed *before* the victim's larger trigger. When the victim's trigger is then processed, `completePaymentPayload` finds insufficient unspent outputs, and the victim's otherwise valid call bounces — losing the bounce fee — exactly mirroring the `SwapperImpl.flash()` griefing pattern where a 1-wei transfer drains just enough balance to trip the `InsufficientFunds_InContract` check.

The code even acknowledges a closely related griefing vector already (dust spam draining AA storage/fees): [5](#0-4) 
but this only guards against tiny dust outputs sent *to* the AA — it does not address an attacker's ability to time/front-run a trigger that consumes the AA's existing unspent outputs before a victim's trigger executes.

### Impact Explanation
Any unprivileged user can post a trigger unit to a public AA to consume its pool of unspent outputs immediately before a victim's trigger is included/stabilized. The victim's trigger then fails the funds check, bounces, and the victim permanently loses the bounce fee (`bounce_fees.base`, default `constants.MIN_BYTES_BOUNCE_FEE`, or the asset-specific bounce fee) with no compensating action performed. This is a concrete, repeatable AA fund loss / denial-of-service against any AA whose logic can be triggered cheaply and whose outgoing payment size is meaningful relative to its held balance (e.g. exchange/order-matching AAs, payment-channel AAs, market-maker AAs).

### Likelihood Explanation
Any address can trigger an AA at will and cheaply (minimal fee), and the AA's UTXO set and its processing order are both publicly observable from the DAG. An attacker only needs to be aware of a pending large trigger to the AA (which is public before stabilization) and time/incentivize their own cheap trigger to be included/stabilized earlier, similar to conventional front-running by fee/ordering advantage. This requires no special privileges (no operator, node, or peer access) — only the ability to post a unit, matching the "unprivileged AA trigger sender" reachability criterion.

### Recommendation
When `completePaymentPayload` cannot find enough unspent funds for a trigger's payment, consider degrading gracefully instead of unconditionally bouncing the whole response — e.g., allow the AA definition to explicitly handle a "insufficient funds" branch, or cap outgoing amounts to what is actually available (similar to the reported "solution two" of clamping the transferred amount) rather than always reverting the entire state change and charging the bounce fee. At minimum, document this shared-balance griefing risk for AA authors so payment-dependent AA logic can defensively re-check `balance[asset]` immediately before committing to a fixed-size payout.

### Proof of Concept
1. AA `X` holds outputs worth 10,000 bytes and is programmed to pay out a fixed `9,000` bytes in response to trigger case `A`.
2. Victim posts a trigger unit `U_victim` invoking case `A`, expecting it to be processed with the AA's current balance of 10,000 bytes.
3. Attacker observes `U_victim` in the DAG before stabilization and posts `U_attacker`, invoking some other cheap case of the same AA `X` that spends part of its unspent outputs (e.g., a small legitimate withdrawal covered by the AA's own logic) so that fewer than 9,000+fee bytes' worth of unspent outputs remain.
4. If `U_attacker` stabilizes/gets processed by `handleTrigger`/`sendUnit` before `U_victim` (by virtue of DAG ordering — `ORDER BY main_chain_index, unit, output_index` in `readStableOutputs`), the AA's spendable UTXO pool is reduced.
5. When `U_victim` is processed, `completePaymentPayload` cannot assemble 9,000+fee bytes from unspent outputs and calls back `'not enough funds for ... bytes'`, causing `bounce(err)` at [3](#0-2)  to fire, and the victim's trigger.outputs minus `bounce_fees.base` are returned — the victim loses the bounce fee and receives no service.
