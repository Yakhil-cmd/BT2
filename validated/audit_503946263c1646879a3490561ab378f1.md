### Title
Webhook signature validation binds only to `repository.owner.login`, not to the repository/commit actually mutated, allowing any authenticated GitHub org to forge commit statuses for other tracked repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository_owner`, a field taken straight out of the still-unverified JSON body. Nothing ties that verified organization to the actual repository/commit object mutated by the downstream handler. `StatusHandler`, in particular, updates `Commit` rows by matching `sha` globally, with no scoping to the organization that produced a valid signature. This is the same class of bug as the audit report: a field the code trusts to select a security context (`repository_owner` → secret) is decoupled from the field/record that is actually acted upon (arbitrary `sha` across all tracked stacks), so two different "transactions" (webhook deliveries from two different orgs) can collide on the same target state.

### Finding Description
`WebhooksController#verify_signature` computes the signing org from the payload itself, before the payload is trusted: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` — attacker-controlled JSON, not yet authenticated. It is only used to pick which org's `webhook_secret` should validate the HMAC; if an attacker legitimately controls a GitHub App/org that Shipit tracks (e.g. `attacker-org`), they know that org's `webhook_secret` and can produce a valid signature for a payload whose *body* claims to be `attacker-org`, while other payload fields (like `sha`) reference resources belonging to a completely different, victim-owned stack.

Once the signature passes, `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`: [3](#0-2) 

`StatusHandler#process` looks up commits by `sha` alone — `Commit.where(sha: params.sha)` — with no filter on repository, stack, or organization at all. So the record actually written (`commit.create_status_from_github!`) is never checked against the organization that the signature verification authenticated. The binding that should hold —

`organization authenticated by HMAC == organization owning the repository/commit written`

— is broken: the left side is derived from an attacker-supplied `repository.owner.login` string, the right side is any commit anywhere in the Shipit instance sharing that `sha`.

### Impact Explanation
Commit statuses are used by Shipit to gate deployability (`deploy_spec.release_status_context`, `deployable_status` events) and continuous deployment decisions: [4](#0-3) 

An attacker who legitimately controls one Shipit-configured GitHub organization (with its own valid `webhook_secret`) can forge a `status` webhook — validly signed with their own org's secret — that sets a fabricated "success" CI status on a commit `sha` belonging to a different, victim-owned stack/repository. If that victim stack has continuous deployment enabled and gates on the forged status context, this can lead to an unauthorized deploy — matching the Critical impact bucket ("an unauthorized deploy"). At minimum it lets one tenant corrupt another tenant's commit/CI state, an authorization boundary violation across repositories that the signature check was supposed to enforce.

### Likelihood Explanation
Exploitation requires the attacker to control (own the webhook secret of) at least one GitHub organization/repository that this Shipit instance already tracks — a realistic scenario for any multi-tenant or multi-org Shipit deployment (`docs/setup.md` explicitly documents configuring `github:` per-organization for multiple orgs). No `ApiClient` token, session, or GitHub write access to the victim repository is required; only knowledge of one's own org's webhook secret, which any org admin legitimately possesses. `sha` collisions across repositories are also non-trivial to target for equivalence but commit `sha`s are public via GitHub API/commit pages, so an attacker can look up the victim's real commit SHA and craft a payload for it directly, making this practically exploitable rather than theoretical.

### Recommendation
- After verifying the HMAC signature, re-derive and cross-check the actual repository (e.g., `repository.full_name`, or the specific `Repository`/`Stack` resolved by handlers) against the organization whose secret validated the signature, rejecting the webhook if they diverge.
- Scope `StatusHandler` (and any handler that looks up records purely by cross-repo-ambiguous keys like `sha`) to the repository derived from the same verified payload, e.g. `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, intersecting with `stacks`/`commits` for that repository only, instead of a global `Commit.where(sha: ...)`.
- Consider binding webhook secrets 1:1 to `Repository`/`Stack` records rather than solely to organization, closing the gap between "who signed" and "what gets mutated."

### Proof of Concept
1. Shipit tracks two orgs: `attacker-org` (attacker controls the GitHub App and knows its `webhook_secret`) and `victim-org` (unrelated, tracked in the same Shipit instance).
2. Attacker looks up a real commit SHA `S` belonging to a `victim-org/repo` stack (public GitHub data).
3. Attacker POSTs to the webhooks endpoint:
   - `X-Github-Event: status`
   - Body:
     ```json
     {
       "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/some-repo"},
       "sha": "S",
       "state": "success",
       "context": "ci/tests",
       "created_at": "2026-09-01T00:00:00Z"
     }
     ```
   - `X-Hub-Signature`: HMAC-SHA1 of the raw body computed with `attacker-org`'s known `webhook_secret`.
4. `WebhooksController#verify_signature` resolves `repository_owner => "attacker-org"`, fetches `attacker-org`'s `webhook_secret`, and the signature matches → request passes (per [1](#0-0) ).
5. `StatusHandler#process` executes `Commit.where(sha: "S")` (per [3](#0-2) ), which matches the victim's commit and writes a fabricated "success" status onto it, even though the signature only ever authenticated `attacker-org`.
