### Title
Webhook signature verification binds only the payload organization, not the `repository.full_name` acted on by event handlers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate against using `repository.owner.login` (falling back to `organization.login`), but the handlers that actually mutate state (`StatusHandler`, `PushHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`, etc.) act on `repository.full_name`, a completely separate, unverified field of the same JSON body. The HMAC signature covers the raw body, so it stops tampering by third parties who don't know a secret, but it does **not** bind the "organization whose secret validated this request" to the "repository the handler will operate on" — these are two different fields extracted independently from attacker-suppliable JSON.

### Finding Description
`verify_signature` computes the organization used to fetch the correct `webhook_secret` like this: [1](#0-0) [2](#0-1) 

Once the signature check passes, `create` simply parses the body and dispatches to the registered handler(s) for the event type, handing them the raw, still-unvalidated JSON: [3](#0-2) 

Handlers derive the target repository from a *different* JSON key, `repository.full_name`, e.g.: [4](#0-3) 
which is resolved with `Repository.from_github_repo_name`, splitting `owner/name` straight out of the payload: [5](#0-4) 

Nothing ties `repository.full_name`'s owner segment back to `repository.owner.login`/`organization.login`, the field that was actually used to select the webhook secret in `verify_signature`. The equality that should hold but doesn't is:

`organization authenticated (repository.owner.login / organization.login) == owner of repository.full_name (acted upon by handlers)`

The most severe instance of this is `StatusHandler`, which doesn't even use `repository_name`/owner scoping at all — it looks up commits **globally by SHA**, with no repository/stack scoping whatsoever: [6](#0-5) 

Setting a commit status ultimately drives `Commit#create_status_from_github!` → `add_status`, which can trigger `stack.schedule_merges` and continuous delivery for any stack that happens to contain a commit with a matching SHA: [7](#0-6) [8](#0-7) [9](#0-8) 

Given a Shipit instance configured with multiple GitHub organizations (a supported, documented setup, see `Shipit.github(organization:)` dispatch and `test/dummy/config/secrets_double_github_app.yml`), a party who legitimately administers **one** configured organization's GitHub App (and thus knows that org's own `webhook_secret`) can send a signed webhook whose `repository.owner.login`/`organization.login` matches their own org (so `verify_signature` succeeds against their own known secret) while other payload fields (`repository.full_name` for most handlers, or nothing at all for `StatusHandler`) reference a target belonging to a *different* configured organization on the same Shipit instance.

### Impact Explanation
This crosses the "unauthorized deploy/rollback" and "escalation into `Shipit.github_teams` authorization" boundaries defined in scope:
- Via `StatusHandler`, an attacker who controls a signed webhook for their own organization can forge a `success` CI status for an arbitrary commit SHA belonging to a completely different stack/organization hosted on the same Shipit instance, provided they can guess or observe the target SHA (commit SHAs are often public/known). This can flip `deployable?` to true and trigger `schedule_continuous_delivery`, causing an **unauthorized deploy** of a stack the attacker has no legitimate access to.
- Via `PushHandler`/`CheckSuiteHandler`/`PullRequest::*Handler`, an attacker can inject fabricated push/check/PR-close events for a target repository under a different organization's namespace by crafting `repository.full_name` independently from the org field validated by the signature, driving merge-queue and review-stack state transitions for repositories they don't control.

This matches the required "unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitability requires the attacker to control (or know the webhook secret of) at least one organization configured on a shared, multi-organization Shipit instance — a realistic scenario for hosted/shared Shipit deployments serving several GitHub orgs, as explicitly supported by the multi-org `github:` config format documented and tested in this engine (`test/dummy/config/secrets_double_github_app.yml`, `test/unit/shipit_test.rb`). No repository write access, no `ApiClient` token, and no GitHub App private key for the *target* organization are needed — only a valid signature for the attacker's own configured organization, which they legitimately possess. This is a real cross-tenant boundary violation on any Shipit install with more than one org configured, which is a first-class, documented feature of this engine, not a misconfiguration.

### Recommendation
Bind the webhook signature to the entity actually acted upon: after selecting the GitHub App by `repository_owner`, re-validate that the owner used for signature selection matches the owner embedded in every payload-derived repository reference each handler consumes (`repository.full_name`, and any handler-specific repository/organization fields). For `StatusHandler` specifically, scope the `Commit` lookup by the verified organization/repository (e.g., join through `Stack`/`Repository` and filter by `github_repo_name`) rather than a bare, cross-tenant `Commit.where(sha:)`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker-administered, webhook secret known to attacker) and `OrgB` (victim), as supported by the multi-org config format.
2. Attacker crafts a `status` webhook body: `{"sha": "<victim-commit-sha>", "state": "success", "repository": {"owner": {"login": "OrgA"}}}` and signs it with `OrgA`'s known `webhook_secret`.
3. `WebhooksController#verify_signature` resolves `repository_owner` = `OrgA`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC verifies successfully.
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, which matches the victim's commit under `OrgB` regardless of the verified `OrgA` signature, and calls `create_status_from_github!`, potentially triggering `schedule_merges`/continuous delivery for `OrgB`'s stack.
