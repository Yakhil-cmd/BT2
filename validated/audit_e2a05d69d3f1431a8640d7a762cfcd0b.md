Based on my research, I found a genuine analog to this refcount-leak bug class in ocore's private/indivisible-asset double-spend handling path.

### Title
Unreleased `private_write` mutex on error/exception in `checkForDoublespends()` doublespend-acceptance path leads to permanent validation deadlock - (File: validation.js)

### Summary
The Linux CVE describes a refcount that is incremented on entry to a function but, on several error-handling exit paths, is never decremented, leaking the resource. The analogous ocore pattern is in `checkForDoublespends()` in [1](#0-0) , where the global `private_write` mutex is acquired via `mutex.lock(["private_write"], ...)` when a private/indivisible-asset input's conflicting spend is accepted, but the corresponding `unlock()` call is reachable through only a single, error-unguarded success branch.

### Finding Description
In `validatePaymentInputsAndOutputs()`, when validating a private, fixed-denomination asset transfer whose input double-spends a prior output, the code takes the "accept doublespend" branch and, for private assets, does: [2](#0-1) 
`mutex.lock(["private_write"], function(unlock){ ... conn.query(sql, doubleSpendVars, function(){ ... unlock(); cb3(); }); })`

`mutex.js`'s `exec()` sets `bLocked = true` when the lock is acquired and the key array is only ever removed from `arrLockedKeyArrays` inside the `unlock()` callback passed to the locked routine: [3](#0-2) 

The `conn.query(sql, doubleSpendVars, function(){...})` callback used inside the lock has no error argument and no error handling — it assumes the query always completes successfully and calls `unlock()`. If this query callback is never invoked, or an exception is thrown before reaching `unlock()` (for example a thrown error further up the same `async.eachSeries` chain in `checkForDoublespends`, at [4](#0-3) , or driver-level failure on the raw SQL update), the `private_write` key stays in `arrLockedKeyArrays` forever. This exactly parallels the kernel bug: a resource ("private_write" lock instead of an smmu refcount) is acquired on entry and only released on the "happy path," while abnormal/error paths silently forget to release it.

### Impact Explanation
Once `private_write` is left locked, every subsequent private-asset double-spend acceptance anywhere in the node — including in `validatePaymentInputsAndOutputs` for indivisible/private assets — queues on `mutex.lock(["private_write"], ...)` via `handleQueue()`/`arrQueuedJobs` and never executes, because `isAnyOfKeysLocked()` will always report the key as held: [5](#0-4) 
This permanently stalls processing of any unit containing a private/indivisible-asset double-spend acceptance, i.e. the node becomes unable to reach a validation decision (accept or reject) on such units, which matches the accepted "network unable to confirm new units" impact class.

### Likelihood Explanation
An unprivileged unit poster who owns a private/indivisible asset with `fixed_denominations` can craft a unit whose input double-spends an existing output of that asset; this routes into the vulnerable `acceptDoublespends` callback in `checkForDoublespends()`. Triggering the exact code path that skips `unlock()` requires either a downstream exception (e.g. the `throw Error(...)` calls in the same function at lines 1673/1688/1692, which fire on unexpected but attacker-influenceable conflicting-record states) or any failure of the raw `conn.query` update. Because the vulnerable branch is only exercised for private assets and depends on hitting one of the exception paths, likelihood is lower than a trivially reachable bug, consistent with the Medium severity of the analog CVE.

### Recommendation
Wrap the `conn.query` inside the `private_write`-locked callback with proper error handling, and ensure `unlock()` is called in a `finally`-equivalent path for every exit of `checkForDoublespends()` (including all `throw Error(...)` branches reachable while the lock might be held), so the mutex is always released regardless of success or failure — mirroring the kernel fix's "jump to out label on all error paths" pattern.

### Proof of Concept
1. As an unprivileged asset issuer, define a private, `fixed_denominations` indivisible asset and issue coins to two addresses/units such that a later unit can present a double-spend input against an existing spent output of that asset.
2. Submit (post) a unit that exercises `validatePaymentInputsAndOutputs` for this asset with a conflicting/double-spend input which is accepted via `checkForDoublespends`'s `acceptDoublespends` branch at [2](#0-1) .
3. Arrange (or rely on) one of the `throw Error(...)` conditions in `checkForDoublespends` at [6](#0-5)  to fire concurrently with the `private_write`-guarded update, or cause the raw `conn.query` update to fail — the `unlock()` call is skipped and `private_write` remains locked in `arrLockedKeyArrays` (per `mutex.js` `exec()`), permanently blocking any future private double-spend acceptance processing.

function checkForDoublespends(conn, type, sql, arrSqlArgs, objUnit, objValidationState, onAcceptedDoublespends, cb){
	conn.query(
		sql, 
		arrSqlArgs,
		function(rows){
			if (rows.length === 0)
				return cb();
			var arrAuthorAddresses = objUnit.authors.map(function(author) { return author.address; } );
			async.eachSeries(
				rows,
				function(objConflictingRecord, cb2){
					if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
						throw Error("conflicting "+type+" spent from another address?");
					if (conf.bLight) // we can't use graph in light wallet, the private payment can be resent and revalidated when stable
						return cb2(objUnit.unit+": conflicting "+type);
					graph.determineIfIncludedOrEqual(conn, objConflictingRecord.unit, objUnit.parent_units, function(bIncluded){
						if (bIncluded){
							var error = objUnit.unit+": conflicting "+type+" in inner unit "+objConflictingRecord.unit;

							// too young (serial or nonserial)
							if (objConflictingRecord.main_chain_index > objValidationState.last_ball_mci || objConflictingRecord.main_chain_index === null)
								return cb2(error);

							// in good sequence (final state); final-bad is excluded by the query and treated as non-existent
							if (objConflictingRecord.sequence === 'good')
								return cb2(error);

							throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit);
						}
						else{ // arrAddressesWithForkedPath is not set when validating private payments
							if (objValidationState.arrAddressesWithForkedPath && objValidationState.arrAddressesWithForkedPath.indexOf(objConflictingRecord.address) === -1)
								throw Error("double spending "+type+" without double spending address?");
							cb2();
						}
					});
				},
				function(err){
					if (err)
						return cb(err);
					onAcceptedDoublespends(cb);
				}
			);
		}
	);
}

function handleQueue(){
	console.log("handleQueue "+arrQueuedJobs.length+" items");
	for (var i=0; i<arrQueuedJobs.length; i++){
		var job = arrQueuedJobs[i];
		if (isAnyOfKeysLocked(job.arrKeys))
			continue;
		arrQueuedJobs.splice(i, 1); // do it before exec as exec can trigger another job added, another lock unlocked, another handleQueue called
		console.log("starting job held by keys", job.arrKeys);
		exec(job.arrKeys, job.proc, job.next_proc);
		i--; // we've just removed one item
	}
	console.log("handleQueue done "+arrQueuedJobs.length+" items");
}

function lock(arrKeys, proc, next_proc){
	if (arguments.length === 1)
		return new Promise(resolve => lock(arrKeys, resolve));
	if (typeof arrKeys === 'string')
		arrKeys = [arrKeys];
	if (isAnyOfKeysLocked(arrKeys)){
		console.log("queuing job held by keys", arrKeys);
		arrQueuedJobs.push({arrKeys: arrKeys, proc: proc, next_proc: next_proc, ts:Date.now()});
	}
	else
		exec(arrKeys, proc, next_proc);
}
