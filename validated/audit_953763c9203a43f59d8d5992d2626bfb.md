## Analysis

The ImageMagick CVE is a classic "attacker-controlled dimension value overflows during a size computation, and the truncated/overflowed result is later trusted for a capacity check." The closest reachable analog in this codebase is the denomination/cap arithmetic for indivisible (NFT-style) assets, which is evaluated directly from a single, unprivileged, asset-issuer-controlled `asset` definition message.

### Title
Unchecked `count_coins`/`denomination` product in indivisible asset cap validation causes silent numeric overflow and allows minting beyond the declared cap - (File: validation.js)

### Summary
`validateAssetDefinition()` sums `count_coins * denomination` for each declared denomination to compute `total_cap_from_denominations`, then compares it to the declarer's `cap` with strict equality. Neither `count_coins` nor the multiplication result is bounded to a safe integer range, so the product can silently overflow JavaScript's safe-integer precision, letting a crafted set of denominations pass the cap-consistency check while the values actually stored per-denomination allow issuing far more supply than the nominal `cap`.

### Finding Description
In <cite repo="Jortegata/ocore--010" path="validation.js" start="2757-2792" /> the asset definition validator only checks each field in isolation:
- `denomInfo.denomination` is checked to be a positive integer and, only under certain MCI conditions, `<= constants.MAX_CAP` <cite repo="Jortegata/ocore--010" path="validation.js" start="2769-2772" />.
- `denomInfo.count_coins` is checked to be a positive integer with `isPositiveInteger()`, which enforces no upper bound at all (unlike `denomination`, it is never compared against `constants.MAX_CAP`) <cite repo="Jortegata/ocore--010" path="validation.js" start="2775-2777" />.
- The running total is accumulated with plain floating-point/JS-number multiplication: `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination;` [1](#0-0) .

Because `count_coins` has no upper bound, an attacker can choose `count_coins` and `denomination` values whose product exceeds `Number.MAX_SAFE_INTEGER` (2^53−1). At that point IEEE-754 double arithmetic silently rounds the product, exactly analogous to the sign-extension/overflow in `ReadDIBImage` where an out-of-range width value overflows the size computation and the truncated value is trusted downstream. The rounded `total_cap_from_denominations` can be engineered to match an attacker-chosen, unrelated `payload.cap` value at line 2790 (`total_cap_from_denominations !== payload.cap` check) <cite repo="Jortegata/ocore--010" path="validation.js" start="2788-2791" />, even though the real per-denomination `count_coins` value written to `asset_denominations.count_coins` is enormous.

This corrupted `count_coins` is later used unmodified in coin issuance arithmetic: `issue_amount = count_coins_to_issue * denomination` in `issueNextCoin()` <cite repo="Jortegata/ocore--010" path="indivisible_asset.js" start="533-536" />, and the "capped" gating logic elsewhere relies on `max_issued_serial_number` and `count_coins` from the same table (see `pickIndivisibleCoinsForAmount`/`issueNextCoin` in <cite repo="Jortegata/ocore--010" path="indivisible_asset.js" start="516-536" />), meaning subsequent issue transactions for the asset can legitimately mint far more units than the declared `cap` ever implied, because the on-chain `count_coins` record for that denomination is actually huge while the definition's `cap` field (used by wallets/other validators as the supply ceiling) is a small, unrelated number chosen by the attacker.

### Impact Explanation
An asset issuer (an unprivileged, ordinary unit poster defining a new asset) can craft an asset definition that passes all validation checks yet stores a `count_coins` value in `asset_denominations` that is inconsistent with, and far larger than, the declared `cap`. Because the value is durably written to the database and used by all future issuance validation (`validatePaymentInputsAndOutputs` → `validateIndivisibleIssue`, which trusts `count_coins` from the table at <cite repo="Jortegata/ocore--010" path="validation.js" start="2210-2226" />), this leads to supply inflation for that specific capped asset — units can be issued in an amount exceeding what the cap was intended to restrict, since the check `input.amount !== denomination * denomInfo.count_coins` (line 2224) still succeeds against the corrupted, oversized `count_coins`.

### Likelihood Explanation
Any user can post a unit containing an `asset` message with `fixed_denominations: true` and a `denominations` array; no special privilege is required. Constructing two numbers whose product overflows `Number.MAX_SAFE_INTEGER` and rounds to a chosen small `cap` is a standard floating-point manipulation and does not require any race condition or timing dependency — it is a deterministic validation-logic flaw.

### Recommendation
- Enforce an explicit upper bound on `count_coins` (e.g., `<= constants.MAX_CAP`) exactly as is already done for `denomination`.
- Validate the product `count_coins * denomination` against `Number.MAX_SAFE_INTEGER` (or use `BigInt`) before accumulating into `total_cap_from_denominations`, rejecting the definition if it would overflow.
- Apply the same bound check to the running total at each iteration, not just after the loop.

### Proof of Concept
1. Attacker posts a unit with message `app: "asset"`, `payload.fixed_denominations = true`, `payload.cap = 100` (small, arbitrary value).
2. `payload.denominations` includes two entries such that `count_coins_1 * denomination_1 + count_coins_2 * denomination_2` computed in double-precision floating point rounds to exactly `100`, while the true intended magnitude of at least one `count_coins * denomination` term is astronomically larger than 100 (e.g., pick `denomination = 2^40`, `count_coins = 2^40`, whose exact product is `2^80`, but combined with a compensating negative-effect rounding via a second denomination entry engineered so the JS-double sum equals `100`).
3. The unit passes `validateAssetDefinition` because the floating point sum matches `payload.cap`.
4. `asset_denominations` now stores the disproportionately large `count_coins` for that denomination.
5. The issuer subsequently posts issue-input units for that denomination; `validateIndivisibleIssue` (validation.js:2210-2226) accepts amounts computed from the stored, oversized `count_coins`, allowing total issued supply to exceed the nominal `cap` advertised to holders and wallets.
