### Title
Permissionless `DepositDelegatorRewards` can be front-run to indefinitely block an authorized withdrawer from closing a vote account - (File: programs/vote/src/vote_state/mod.rs)

### Summary
Anyone can call the permissionless `VoteInstruction::DepositDelegatorRewards` instruction to top up a vote account's `pending_delegator_rewards` field with a dust amount of lamports. `vote_state::withdraw()` refuses to fully close (zero out) a vote account while `pending_delegator_rewards > 0`. Because a delegator/attacker can trigger this deposit right before the vote account's authorized withdrawer submits a close/full-withdraw transaction, this mirrors the referenced DYAD finding: an unprivileged party can front-run a privileged "remove/close" action by adding a small amount of value that the removal check treats as blocking.

### Finding Description
`deposit_delegator_rewards` requires only that the *source* account (any wallet, not the vote account's authorized withdrawer) sign the transfer; it does not require any vote-account authority: [1](#0-0) [2](#0-1) 

It transfers lamports into the vote account and unconditionally increments `pending_delegator_rewards` via `add_pending_delegator_rewards`: [3](#0-2) 

Meanwhile, `vote_state::withdraw()` (invoked by the `Withdraw` instruction, which does require the `authorized_withdrawer` to sign) enforces that a full withdrawal (`remaining_balance == 0`) is rejected with `InstructionError::InsufficientFunds` whenever `pending_delegator_rewards > 0`, and a partial withdrawal cannot dip into the amount reserved by `pending_delegator_rewards`: [4](#0-3) 

`pending_delegator_rewards` is only reduced through the automatic partitioned epoch-rewards distribution (`calculate_block_reward`), which is proportional to the vote account's currently *active delegated stake*: [5](#0-4) 

If the vote account has little or no active delegated stake at the time of distribution (`total_active_stake == 0` or very small relative to the dust `pending_delegator_rewards`), the reward-distribution path returns `0` and the reserved balance is not drained. There is no owner-only instruction that lets the authorized withdrawer clear `pending_delegator_rewards` directly — it can only be reduced by the reward-distribution mechanism.

### Impact Explanation
An attacker who observes (or anticipates) a validator operator's transaction to fully withdraw/close their vote account (e.g., `WithdrawFromVoteAccount` computed as `SpendAmount::RentExempt`/`SpendAmount::All`, used by `process_close_vote_account` in `cli/src/vote.rs`) can front-run it with a `DepositDelegatorRewards` call depositing as little as 1 lamport. This sets `pending_delegator_rewards = 1`, causing the legitimate close transaction to fail with `InstructionError::InsufficientFunds`. If the vote account has no (or negligible) active delegated stake, epoch-boundary reward distribution never drains this reserved amount, so the account can be kept permanently un-closable at near-zero cost to the attacker — a denial-of-service on account closure analogous to the DYAD `VaultHasAssets` front-running bug, where an unprivileged deposit blocks an owner-privileged removal path.

### Likelihood Explanation
The attack requires only a wallet with a few lamports and no special role or privilege — matching the "unprivileged user" analog criteria. The instruction and precondition are both reachable directly through normal vote-program instruction processing (`programs/vote/src/vote_processor.rs`), not through any excluded path (no validator/operator role required, no snapshot manipulation, no RPC amplification). The only gating factor is that `SIMD-0123`-related features (`commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing`) must be active, and the vote account must be on `VoteStateV4` with little/no active stake — a realistic scenario for a validator winding down and trying to close its vote account.

### Recommendation
Provide the authorized withdrawer a way to reclaim/zero `pending_delegator_rewards` directly during a full close (e.g., transfer the reserved amount out along with the rest, or allow the withdraw instruction to also flush `pending_delegator_rewards` to the destination when closing under the authorized withdrawer's signature), instead of relying solely on the epoch-rewards distribution mechanism. Alternatively, restrict `DepositDelegatorRewards` so it cannot be invoked by arbitrary unprivileged accounts against a target vote account without some accounting that ties the deposit to actual reward legitimacy, or make `withdraw()`'s full-close path net out `pending_delegator_rewards` against the account being paid to the authorized withdrawer rather than mandating a strict `== 0` check that can never be satisfied for low-stake vote accounts.

### Proof of Concept
1. Create a `VoteStateV4` vote account with the authorized withdrawer `W`, currently with little/no delegated stake, on a cluster with `commission_rate_in_basis_points`, `custom_commission_collector`, and `block_revenue_sharing` features active.
2. Attacker `A` (unrelated wallet) submits `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` naming the target vote account and `A` as the signing source account — this succeeds per `deposit_delegator_rewards`, setting `pending_delegator_rewards = 1` (see test coverage at [6](#0-5) ).
3. `W` submits a `Withdraw` instruction for the full vote-account balance (a close). `withdraw()` computes `remaining_balance == 0` and, seeing `pending_delegator_rewards == 1 > 0`, returns `InstructionError::InsufficientFunds` ( [7](#0-6) ), blocking the close.
4. Because the vote account has negligible active stake, subsequent epoch reward distribution via `calculate_block_reward` computes `total_active_stake == 0` and returns `0`, so `pending_delegator_rewards` is never drained ( [8](#0-7) ), leaving the vote account permanently un-closable unless `W` can somehow attract stake proportional enough to eventually work off the dust reserve.

```rust
/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
```
