## Analysis: Improper size limits on device-level private payment chains → DoS

Mapping the reported bug class ("fails to validate incoming request size... causing service disruption") to ocore, the closest reachable analog is the private-payment-chain message handler reachable by any paired correspondent device, which lacks a bound on the number of chain elements/chains per message, unlike the tight per-unit limits (`MAX_MESSAGES_PER_UNIT`, `MAX_INPUTS_PER_PAYMENT_MESSAGE`, `MAX_OUTPUTS_PER_PAYMENT_MESSAGE`) enforced on normal units.

### Title
Unbounded private-payment-chain size enables DoS via paired-device message handler - (File: wallet.js)

### Summary
`handlePrivatePaymentChains()` in `wallet.js` and `handleOnlinePrivatePayment()` in `network.js` process attacker-supplied `private_payments` device messages (`body.chains`) with only structural field checks and no cap on the number of chains or chain elements per chain. The only global guard is a generic depth/node budget (`isTooDeeplyNestedOrHasTooManyNodes(json, 20, 100000)`) applied once at the top of `handleMessageFromHub`, which is far more permissive than the analogous unit-level anti-spam limits.

### Finding Description
`handleMessageFromHub` gates all hub-relayed device messages with a single generic size/nesting check: [1](#0-0) . This budget (depth 20 / 100,000 nodes) is far larger than the corresponding unit-level default (depth 100 / **10,000** nodes) used in `validation.js`, and unlike unit validation, it is a single flat check regardless of how expensive per-element processing will be.

`handlePrivatePaymentChains` only validates the *shape* of each chain element (non-empty objects/strings/arrays), never the *count* of chains or chain length: [2](#0-1) . It then iterates every chain sequentially with `async.eachSeries`, invoking `network.handleOnlinePrivatePayment` for each one: [3](#0-2) .

`handleOnlinePrivatePayment` performs a DB lookup (`joint_storage.checkIfNewUnit`) and, for units never seen before, unconditionally serializes and inserts the *entire* untrusted chain into `unhandled_private_payments` and issues an outbound network request for the referenced unit: [4](#0-3) . There is no cap on `arrPrivateElements.length`, on the number of `outputs`/`inputs` inside each private element's `payload`, or on the total number of `chains` in the message — only the generic 100,000-node ceiling checked once at message entry.

Contrast this with normal unit validation, where messages, inputs, and outputs are explicitly bounded: [5](#0-4)  and enforced in `validatePaymentInputsAndOutputs`: [6](#0-5) . No equivalent `MAX_CHAINS_PER_MESSAGE` or `MAX_ELEMENTS_PER_CHAIN` constant exists for private payment chains.

### Impact Explanation
A paired correspondent device (an unprivileged private-payment counterparty, explicitly reachable per scope) can send a single `private_payments` justsaying/message containing many fabricated chains/elements (fake but well-formed base64 hash strings, fake asset ids), sized up to the generic 100,000-node budget. This triggers, per chain: a DB read (`checkIfNewUnit`), a DB write of the full serialized JSON blob into `unhandled_private_payments`, and an outbound `requestNewMissingJoints` network call to fetch the (nonexistent) referenced units. Because processing is done with `async.eachSeries` (not bounded/batched) and each element causes disk I/O plus network requests, an attacker can force disproportionate CPU, disk, and network resource consumption on the victim node/hub relative to the cost of crafting the message, degrading the victim's ability to process legitimate wallet/hub traffic — a service disruption consistent with the reported bug class.

### Likelihood Explanation
Medium-High: any two devices that have paired (a normal, low-privilege wallet operation, not requiring special trust) can exchange `private_payments` messages, and hubs relay these `hub/deliver`/`hub/message` messages on behalf of arbitrary registered devices. No signature or economic cost gates the chain contents themselves (only structural JSON shape), so the barrier to triggering repeated expensive processing is low.

### Recommendation
Introduce explicit limits analogous to unit-level anti-spam constants: cap the number of chains per `private_payments` message, the number of elements per chain, and the number of inputs/outputs per chain-element payload, rejecting oversized messages before any DB/network work is performed. Consider tightening the generic device-message node/depth budget in `handleMessageFromHub` to be proportional to the most expensive message type it gates, rather than using one large shared ceiling.

### Proof of Concept
1. Pair a malicious device with a victim wallet/hub client (`handlePairingMessage`, low-privilege operation).
2. Send a `private_payments` justsaying message whose `body.chains` contains as many chains/elements as fit under the 100,000-node/depth-20 budget (e.g., thousands of single-element chains, each with a fake but well-formed 44-char base64 `unit`, a fake `payload.asset`, and minimal `inputs`/`outputs` objects satisfying `isNonemptyObject`).
3. Observe that `handlePrivatePaymentChains` accepts the structural checks, and for each chain `handleOnlinePrivatePayment`'s `ifNew` branch inserts a JSON blob into `unhandled_private_payments` and issues a `requestNewMissingJoints` network call — multiplying DB writes and outbound requests far beyond what unit-level `MAX_MESSAGES_PER_UNIT`/`MAX_INPUTS`/`MAX_OUTPUTS` limits would allow for an equivalent-sized legitimate unit.
