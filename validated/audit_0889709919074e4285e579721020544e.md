### Title
`in_data_feed`/`dataFeedExists` accepts data feeds from not-yet-final ("temp-bad"/soon-to-be "final-bad") units, letting an unconfirmed poster's fake feed drive AA logic - ([File: data_feeds.js])

### Summary
The Crema Finance loss stemmed from a contract trusting a fake, unverified account's price data instead of only trusting data whose validity/finality had actually been confirmed. In `ocore`, the analogous trust boundary is between confirmed ("`sequence: 'good'`") and not-yet-finalized ("`temp-bad`"/"`final-bad`") units when an AA formula reads oracle data feeds from unstable units. `dataFeedExists()` (used by `in_data_feed[...]` in AA oscript and by the `in data feed` address-definition condition) omits the `sequence !== 'good'` filter that its sibling function `readDataFeedValue()` explicitly applies.

### Finding Description
`readDataFeedValue()` in [1](#0-0)  iterates `storage.assocUnstableMessages` and explicitly skips any unit whose `sequence !== 'good'` before treating its `data_feed` message as a valid candidate.

`dataFeedExists()`, which backs the `in_data_feed[...]` oscript operator and the `['in data feed', ...]` address-definition/authentifier condition, performs the equivalent unstable-unit scan but never checks `objUnit.sequence` at all: [2](#0-1) . It only checks `bAA`, MCI range, and author-address intersection before scanning the unit's messages for a matching `data_feed` payload.

Callers reach this bAA branch directly from AA execution: `in_data_feed` in `formula/evaluation.js` calls `dataFeeds.dataFeedExists(arrAddresses, feed_name, relation, value, min_mci, mci, bAA, cb)` after evaluating the oracle/feed parameters supplied by the AA's own oscript [3](#0-2) , and the address-definition `'in data feed'` authentifier case in `definition.js` calls the same function [4](#0-3) .

Units posted by an oracle address can be temporarily `temp-bad` (e.g. because the poster address has a conflicting/double-spending unit pending resolution) before later becoming permanently `final-bad`, as tracked in `main_chain.js`'s stabilization logic (`handleNonserialUnits`/`propagateFinalBad`) [5](#0-4) , and in `validation.js`'s `checkSerialAddressUse`, where a conflicting unit is marked `temp-bad` or `final-bad` depending on whether it conflicts with an already-stable competitor [6](#0-5) . A unit that will ultimately be voided (`final-bad`) is nevertheless present in `storage.assocUnstableMessages` while its finality is undetermined, and `dataFeedExists` will happily count its `data_feed` payload as "found" for any AA calling `in_data_feed[...]` in that window — exactly the "trusting unverified/soon-to-be-invalid data" pattern behind the Crema exploit (a fake/spoofed account whose validity was never actually checked before being used to compute fees).

### Impact Explanation
Any AA that uses `in_data_feed[[oracles=..., feed_name=..., feed_value=...]]` as a boolean gate (e.g., to release funds, confirm a condition, settle a bet/prediction, unlock an escrow, or validate a cross-chain claim) can be manipulated by an attacker who controls (or colludes with) an oracle-listed address: post a `data_feed` unit that conflicts with another pending unit from the same address so it is `temp-bad` (destined to become `final-bad`), yet still gets read as a "true" match by `in_data_feed` during the window it sits in `storage.assocUnstableMessages`. This can cause an AA to release funds, mark conditions as satisfied, or otherwise change state based on data that the network itself has already determined (or will determine) to be invalid — leading to unauthorized fund release/loss for AA-held balances, analogous to the fee theft enabled by trusting a fake price account in Crema Finance.

### Likelihood Explanation
Exploitability requires the attacker to control (or be) an address that is accepted as an oracle by the target AA's `in_data_feed` check, and to be able to create a genuinely conflicting (double-spending) unit from that address so the feed-posting unit becomes `temp-bad`/`final-bad` while still visible in the in-memory unstable cache. This is a realistic, unprivileged-poster scenario for many self-referential or loosely-trusted oracle patterns (e.g., `oracles = trigger.address` style constructs commonly seen in AA templates), and requires no cooperation from witnesses, hubs, or other privileged network roles — only crafting and posting units, which matches the allowed attacker capability set.

### Recommendation
Add the same `sequence !== 'good'` (and any other finality-consistency) filter used in `readDataFeedValue()` to the unstable-unit scan in `dataFeedExists()`, so that `in_data_feed[...]` and the `'in data feed'` authentifier condition never treat `temp-bad`/`final-bad` units' `data_feed` messages as valid matches.

### Proof of Concept
Conceptual PoC (cannot be executed here, but derivable from the cited code paths):
1. Deploy an AA whose logic gates a payment on `in_data_feed[[oracles="ORACLE_ADDR", feed_name='price', feed_value>=X]]`.
2. From `ORACLE_ADDR`, post unit `U1` carrying `data_feed: {price: X}`.
3. From the same `ORACLE_ADDR`, concurrently post a second, conflicting unit `U2` that double-spends against `U1` (or vice versa) so that one of them is assigned `sequence: 'temp-bad'` per `validation.js`'s `checkSerialAddressUse` [6](#0-5) .
4. While `U1`/`U2` remain unstable, trigger the AA. `dataFeedExists()` scans `storage.assocUnstableMessages` without checking `sequence`, so the `temp-bad` unit's `data_feed` payload is still counted, satisfying `in_data_feed[...]` and causing the AA to release funds/act on data that will later be voided once `U1`/`U2` stabilize as `final-bad`.
