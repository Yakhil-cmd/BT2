### Title
Unprivileged dust `supply` mints permanent account/NFT storage that the protocol must renew forever - ([File: contracts/controller/src/account.rs])

### Summary
The kernel bug class is a resource leak: every call to `__feat_register_sp()` allocates state that is never freed, so repetition exhausts a shared resource (kernel memory → DoS). The analog in XOXNO Lending is account creation via `supply`: an unprivileged caller passing `account_id = 0` mints a brand-new position NFT and a full set of controller account entries on each call, with no minimum deposit, no per-user account cap, and no way to delete accounts that still hold dust. Each 1-stroop deposit permanently enlarges the state the protocol's keeper must renew.

### Finding Description
`controller.supply(caller, account_id = 0, spoke_id, payments)` routes through `create_account_with` in `contracts/controller/src/account.rs:44-74`, which calls `nft_mint_call` and writes `AccountMeta`, `SupplyPositions`, `BorrowPositions` (and the NFT's `Owner`, `Balance`, plus four OpenZeppelin enumeration entries) for every call. There is no dust floor on the deposit amount — the repo's own PoC test `poc_single_actor_spams_unbounded_dust_accounts` in `contracts/controller/tests`/`tests/test-harness/tests/controller/supply.rs:313-343` creates 64 distinct accounts with 64 × 1-unit deposits, and asserts each `id > last_id` persists.

Unlike the kernel leak, the entries are not free for the attacker — the attacker pays creation rent and forfeits the dust — but the leak's *cost asymmetry* maps cleanly: per the keeper coverage table in `services/keeper/README.md:135-154`, account state (`AccountMeta`/`SupplyPositions`/`BorrowPositions`/`Delegates`) and NFT `Owner` entries are renewed forever by the protocol-funded keeper scanning the position-NFT counter. `cleanup_account_if_empty` / `remove_account_entry` (`contracts/controller/src/storage/account.rs:250-256`) only fires on full exit, and a dust position can never be fully exited economically — the attacker simply abandons the accounts. Token ids are never reused (`position-nft/README.md:152-154`), so the monotonic counter and all live entries accumulate permanently.

### Impact Explanation
Every iteration adds ~10 persistent ledger entries that the keeper renews in perpetuity at protocol expense (`keeper_entry_ttl_ledgers_min`/`keeper_entries` groups, `services/keeper/README.md`). Renewal cost grows linearly and unboundedly in attacker iterations while the attacker's one-time cost is a few stroops of rent plus a 1-unit deposit per account. Once the aggregate renewal set exceeds what the keeper can fund or fit in a transaction's footprint/TTL job, `AccountMeta`/`Owner` entries begin to archive; while restores are possible via simulation, mass archival of `Owner(token_id)` entries makes the affected accounts (and the `owner_of` checks every verb performs, including liquidation admission) effectively stalled — a temporary freezing of funds and degraded protocol operation, matching the CVE's availability-loss class.

### Likelihood Explanation
Medium. The path is fully unprivileged (`supply` with `account_id = 0`), requires no roles, no price manipulation, and works on any listed non-frozen spoke. It is griefing rather than theft: the attacker burns rent and dust deposits, and the damage is deferred (manifests as keeper cost and eventual archival rather than an immediate failure), which tempers severity but does not remove it. Soroban resource fees bound the per-tx spam rate but not the cumulative permanent state.

### Recommendation
- Enforce a minimum first-deposit (dust floor) when `account_id == 0` so opening an account costs meaningful value, mirroring the pool's `*RoundsToZeroShares` dust defenses.
- Alternatively/additionally, allow permissionless cleanup of accounts whose total claim is below a dust threshold (extend the bad-debt/dust cleanup path to zero-value supply accounts), so abandoned spam can be reaped and its entries deleted instead of renewed forever.
- Consider capping the number of live accounts per owner or charging a refundable account deposit.

### Proof of Concept
Existing in-repo PoC: `poc_single_actor_spams_unbounded_dust_accounts` at `tests/test-harness/tests/controller/supply.rs:313-343`. It mints `N = 64` base units of USDC to one attacker, calls `ctrl.supply(&attacker, &0u64, &1u32, [(hub_asset, 1)])` in a loop, and asserts each call returns a fresh, monotonically increasing `account_id` whose account persists in storage — 64 permanent account/NFT entry sets created with a 64-unit total deposit.
