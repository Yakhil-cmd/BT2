## Title
Percentage-split rounding in headers commission distribution allows minting extra bytes - (File: `headers_commission.js`)

### Summary
`calcHeadersCommissions()` splits the fixed `headers_commission` of a winning "payer" unit among the `earned_headers_commission_recipients` declared by the child unit's author, using an independent `Math.round()` (or SQL `ROUND()`) per recipient. Because each recipient's share is rounded separately instead of being computed so the parts sum exactly to the whole, an attacker who authors a unit with several recipient addresses can choose percentages that make the sum of the rounded shares exceed the original `headers_commission`. This mints extra spendable bytes credited to `headers_commission_outputs`, which is directly analogous to the TELCOIN `claim()` bug where repeated dust-sized calls exploited rounding to extract more than the fair share.

### Finding Description
When a child unit wins the headers commission of a parent ("payer") unit, the reward is split among recipients declared in `earned_headers_commission_recipients`: [1](#0-0) 

For each recipient the code computes `Math.round(full_amount * share / 100.0)` independently: [2](#0-1) 

The equivalent MySQL path does the same per-row `ROUND()`: [3](#0-2) 

The only validation performed on `earned_headers_commission_recipients` is that the *declared* percentage shares sum to exactly 100 — there is no check that the *rounded byte amounts* sum to the original `full_amount`: [4](#0-3) 

Because rounding is applied to each recipient's slice independently, an attacker can pick a set of percentages (e.g. three recipients at 33/33/34, or other combinations) such that `Σ round(full_amount * share_i / 100)` is strictly greater than `full_amount`. The resulting inflated per-address contributions are summed without any invariant check and inserted into `headers_commission_outputs`, which become spendable commission-input outputs later validated by `validatePaymentInputsAndOutputs` via `mc_outputs.calcEarnings`: [5](#0-4) [6](#0-5) 

This is the same bug class as the TELCOIN report: a legitimate, permitted user action (claiming a share) repeatedly exploits independent rounding to extract more total value than was actually deposited/earned, rather than the deposit/earning amount being tracked and capped.

### Impact Explanation
Each exploited unit can inflate the payer unit's `headers_commission` payout by a small amount (bounded by the number of recipients minus 1, at most a few bytes per occurrence due to rounding to nearest integer). However, an attacker fully controls both ends: they can author unlimited units with multiple self-owned recipient addresses and repeatedly become the "winning child" of many parent units (by controlling the SHA1-based tie-break via `getWinnerInfo`, or simply being sole author), harvesting the rounding surplus across many main-chain indices over time. This results in bytes being credited to `headers_commission_outputs` that were never actually paid by anyone, i.e., unbacked currency, then made spendable as a commission input in a normal payment message — supply inflation of the base asset.

### Likelihood Explanation
The attack requires only posting normal, well-formed units with a crafted `earned_headers_commission_recipients` list (multiple attacker-controlled addresses with rounding-favorable percentages) — something any single unposted unit author can do without special privileges, and repeating it costs only the ordinary fee of publishing units, similar to how the TELCOIN PoC repeatedly called `claim()` with small amounts.

### Recommendation
Do not round each recipient's share independently. Instead, compute recipient amounts so they are guaranteed to sum exactly to `full_amount`: e.g., use largest-remainder allocation (round down each part, then distribute the residual bytes to the recipients with largest fractional remainders, or to the first/last recipient), and add an invariant assertion (`throw` / reject the computed distribution) if `Σ amounts !== full_amount` before inserting into `headers_commission_contributions`.

### Proof of Concept
1. Author a unit `U` (single author is enough since multi-recipient split is optional even for one author) with `earned_headers_commission_recipients` = 3 addresses controlled by the attacker with shares `[33, 33, 34]` (sums to 100, passes `validateHeadersCommissionRecipients`).
2. Get `U` selected as the "winner" child for a payer unit whose `headers_commission` is, e.g., 5 bytes (attacker can influence this by controlling unit sizes/parents, or simply wait for a favorable case since headers commissions occur very frequently in the network).
3. `calcHeadersCommissions()` computes: `round(5*33/100)=2`, `round(5*33/100)=2`, `round(5*34/100)=2` → total `6` bytes credited across the 3 addresses versus the `5` bytes actually available. The extra 1 byte is created out of thin air and becomes spendable via `headers_commission` inputs.
4. Repeating this across many parent units and many self-authored child units accumulates unbacked bytes over time.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
