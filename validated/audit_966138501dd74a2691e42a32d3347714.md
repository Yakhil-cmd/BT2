### Title
Precision-loss integer overflow in AA balance accounting bypasses the overflow guard before `pemCurvesFixMci` - (File: aa_composer.js)

### Summary
The gdk-pixbuf CVE is a classic "attacker-controlled numeric field is combined into an arithmetic/pointer computation without a real bounds check, and a fixed-size numeric type silently misbehaves (wraps/loses precision), producing an out-of-bounds/incorrect result that is trusted downstream." The closest reachable analog in ocore is the AA balance bookkeeping in `handleTrigger`'s `updateInitialAABalances`, where balances are summed as raw JS doubles and only gated against overflow after a specific MCI upgrade, meaning an attacker who can post units/triggers to inflate balances before that gate (or via any path that skips the check) can cause AA balances to lose precision and diverge from real on-chain funds.

### Finding Description
In `aa_composer.js`, `MAX_BALANCE` is defined with an explicit acknowledgment of precision loss: [1](#0-0) 

`updateInitialAABalances` accumulates the trigger's output amounts directly into `trigger_opts.assocBalances[address][asset]` (a JS `Number`, i.e., an IEEE‑754 double) without any type-safe/overflow-safe arithmetic: [2](#0-1) 

The overflow flag `bOverflow` is computed, but the resulting error ("balance overflow") is only returned to the caller if `mci >= constants.pemCurvesFixMci`: [3](#0-2) [4](#0-3) 

The same pattern with the same MCI-gated check repeats in the DB-backed branch that updates balances for existing assets: [5](#0-4) 

This is directly analogous to the CVE's root cause pattern: a numeric quantity taken from attacker-influenced input (payment/trigger output amounts, each individually bounded by `constants.MAX_CAP` per the validation in `validation.js`) is summed into a fixed-precision numeric register (`Number`/double) across many messages/triggers without a real-time bound, and the resulting "safety check" (the `MAX_BALANCE` comparison) is either bypassed by version gating or itself operates on an already-imprecise value once totals exceed `Number.MAX_SAFE_INTEGER` — mirrored by the `checkBalances()` sanity job that explicitly has to special-case and *ignore* balance discrepancies once numbers exceed `Number.MAX_SAFE_INTEGER`: [6](#0-5) 

That check-balances job runs periodically and simply logs/tolerates divergence beyond `MAX_SAFE_INTEGER` rather than treating it as fatal, i.e. the network's own self-consistency mechanism is designed to give up precisely where precision loss (the JS analog of integer overflow) occurs.

### Impact Explanation
If an attacker (any unit poster who can trigger an AA repeatedly, e.g. via a bounce-fee-only trigger with a large `output` amount, or a chain of AA-to-AA secondary triggers) can drive an AA's accumulated balance for some asset close to or past `Number.MAX_SAFE_INTEGER` (2^53), further additions/subtractions on that balance become imprecise. Because `objValidationState.assocBalances` values feed directly into: (a) the overflow gate itself, (b) `readBalance` in `formula/evaluation.js` which AA oscript logic uses to decide how much to pay out (`balance[...]`), and (c) `sendDummyUnit`'s "send all" amount computation (`output.amount = trigger_opts.assocBalances[address][asset]`), a precision-degraded balance can cause an AA to pay out more (or less) than it actually holds — i.e. AA fund loss, or a false "not enough balance" bounce that freezes legitimate withdrawals. This satisfies the "AA fund loss or freezing" criterion. The severity is bounded by the fact that reaching `MAX_BALANCE`/`MAX_SAFE_INTEGER` scale requires enormous cumulative amounts (a practical constraint), and the overflow guard is present for units validated at/after `pemCurvesFixMci`, which narrows the exploitable window mainly to historical/pre-upgrade MCIs or to any code path that still lacks the guard.

### Likelihood Explanation
Reaching this requires either (1) operating before `constants.pemCurvesFixMci` (a historical condition, not attacker-controllable going forward) or (2) finding a currently-live path into `updateInitialAABalances`/`updateFinalAABalances` where the overflow check is skipped or where enough legitimate value transfers accumulate to approach `2^53`. I was not able to fully confirm from the indexed code whether any currently-reachable trigger path bypasses the `mci >= constants.pemCurvesFixMci` gate at present (i.e., whether `pemCurvesFixMci` has already passed on mainnet, making the guard permanently active). This is a real design smell (precision-based arithmetic on a value meant to represent exact token counts, with an admittedly imprecise safety net) but its exploitability in the *current* network state could not be fully verified with the tools available; a full network trace of `pemCurvesFixMci` activation status and reachable trigger amount limits would be needed to confirm current-day likelihood.

### Recommendation
Use exact integer arithmetic (e.g., `BigInt` or a decimal library) for all AA balance accounting in `aa_composer.js`, remove the MCI-based gating of the overflow check so it always applies, and fail-closed (reject the trigger / bounce) whenever a balance calculation cannot be represented exactly as a JS safe integer, rather than only when it exceeds `MAX_BALANCE`. Additionally, `checkBalances()` should treat any divergence beyond `Number.MAX_SAFE_INTEGER` as a hard error requiring migration to exact arithmetic rather than silently ignoring it.

### Proof of Concept
Conceptual (not executed): repeatedly send payments to an AA address (or chain secondary AA-to-AA triggers) whose per-message `output.amount` is at or near `constants.MAX_CAP`, accumulating over enough triggers/messages that `trigger_opts.assocBalances[address][asset]` in `aa_composer.js:482` approaches `Number.MAX_SAFE_INTEGER`. Once precision is lost, craft a further trigger whose oscript logic reads `balance[address][asset]` (via `formula/evaluation.js` `readBalance`, lines 1510–1528) or uses "send all" semantics (`aa_composer.js:969-972`) to compute a payout; due to floating-point rounding the computed payout can diverge from the AA's true holdings, causing either an over-payment (fund loss) or an erroneous "not enough balance" bounce (fund freezing). Full confirmation of exploitability at current mainnet MCI values was not completed within the scope of this review.
