### Title
Private-asset payments to AA addresses are permanently unspendable because AAs cannot receive private payment chains or send private assets - ([File: aa_composer.js])

### Summary
`FunnelVaultUpgradeable` on HyperEVM locks funds because it can send `HYPE` to a Layer-1→Layer-2 bridge address on HyperCore, but has no logic to notify/credit the correct HyperCore account, so the transferred funds become permanently unusable. The analogous bug class in ocore is: an unprivileged unit poster can send a **private asset** payment (indivisible or divisible, `is_private: true`) whose output address is an **AA address**. The unit validates and is included on the DAG like any other payment, but the AA can never actually use, recognize, or spend those funds, because (a) AAs have no device address to receive the off-DAG private-payment chain required to prove/spend a private output, and (b) `aa_composer.js` explicitly refuses to let an AA construct outgoing private-asset payments. The funds are credited to the AA's DAG address but are permanently locked, exactly mirroring the "sent to the right address, but the receiving side lacks the mechanism to use them" bug class in the report.

### Finding Description
Private assets in Obyte are only usable because the sender additionally transmits an out-of-band "private payment chain" (containing blinding factors / hidden amounts) to the recipient's *device address*, via `walletGeneral.sendPrivatePayments` / `handlePrivatePaymentChains` in `wallet.js` and `network.js`. Only after the recipient's node calls `privatePayment.validateAndSavePrivatePaymentChain` (`private_payment.js:23`) does the local `outputs` row for that private output get its `address`/`blinding` revealed and become locally known/spendable.

AA addresses are DAG addresses generated by hashing an AA definition; they are not device addresses and have no associated wallet/device that can receive private chat messages. Nothing in `validatePayment` (`validation.js:2060-2124`) nor `validatePaymentInputsAndOutputs` prevents naming an AA address as the output of a private payment message — the only privacy-consistency check is `if (!!objAsset.is_private !== !!objValidationState.bPrivate) return callback("asset privacy mismatch")` [1](#0-0) , which does not check whether the recipient is an AA.

Once such a private payment is posted:
1. The output is inserted (hidden) into the `outputs` table for the AA's address, but since it is private, it is explicitly excluded from `aa_balances` calculation: `WHERE address=? AND is_spent=0 AND sequence='good' AND ... AND (is_private=0 OR is_private IS NULL)` [2](#0-1) . The AA's tracked balance never reflects the funds.
2. `getTrigger()`, which builds the AA trigger from a unit's payment messages, reads `message.payload.outputs` directly from the unit [3](#0-2) . For a private payment message, `payload_location` is `"none"` and there is no inline `payload`, so this payment is invisible to trigger detection — the AA is never triggered by it, and even if a chain later reached the AA host node, there is no mechanism to route it there since the AA has no device address.
3. Even disregarding the trigger problem, `aa_composer.js`'s outgoing-payment logic for AA responses explicitly forbids the AA from spending a private asset: `if (objAsset.is_private) // it'll fail validation anyway due to lack of spend_proofs return cb("sending private asset from AA");` [4](#0-3) . This confirms AAs structurally cannot produce the `spend_proofs`/private chain required to move private-asset funds onward.

The net effect: funds sent as a private asset to any AA address are validly recorded on the DAG (validation accepts the unit), but are permanently unusable — the AA cannot detect them as balance, cannot be triggered by them, and even if it somehow tried to move them, it is explicitly blocked from spending private assets. There is no path (short of a protocol upgrade) for this value to ever be recovered, matching the "funds are locked until the contract/protocol is upgraded to add the missing logic" root cause from the external report.

### Impact Explanation
Any unprivileged holder of a private, transferable asset (or new private-asset issuer) can accidentally or maliciously send/lock arbitrary amounts of a private asset by naming any AA address as the output. This constitutes a fund-freezing defect: the value is permanently unusable by both the sender (it's spent) and the AA (it can never see or move it). This matches the "Medium impact/funds locked, requiring an upgrade" severity class of the source report, adapted for the ocore AA execution/asset-transfer model, since it is a systemic gap in the protocol's handling of private payments directed at AAs rather than a user configuration mistake that can be corrected by the recipient.

### Likelihood Explanation
Likelihood is high in the sense that any user of the private-asset feature (a normal, unprivileged wallet operation available to any private-payment counterparty) can trigger this simply by choosing an AA's address as the payment recipient of a private asset — no special privileges, no cooperation from the AA author, and no malicious peer/hub/node collusion is required. It is plausible this would occur through simple user error (mistaking an AA address for a receiving wallet address) as much as through deliberate action.

### Recommendation
- In `validatePayment`/`validatePaymentInputsAndOutputs` (`validation.js`), reject private-asset payment messages whose output address is a known AA address (mirroring the existing `checkAddressIsNotAA`/AA-detection logic already used elsewhere, e.g. `aa_composer.js:252-259` and `validation.js:1018`), since AAs structurally cannot use private-asset value.
- Alternatively/additionally, extend `aa_addresses.checkAAOutputs` (`aa_addresses.js:120`) — used by the wallet composer to pre-flight-check AA outputs — to also flag/reject private-asset outputs sent to AA addresses before the payment is even composed.

### Proof of Concept
1. Issue or acquire units of a private, transferable asset (`is_private: true`, `is_transferrable: true`) via `divisible_asset.js`/`indivisible_asset.js` composition.
2. Compose and send a private-asset payment (e.g., using `wallet.sendMultiPayment` with `asset` referencing the private asset) with `to_address` set to any existing AA's address instead of a normal wallet address.
3. The unit validates and stabilizes normally (no AA-address check exists for private payments).
4. Observe that `aa_balances` for that AA address never reflects the transferred amount (per the `is_private=0 OR is_private IS NULL` filter in `storage.js`), and the AA is never triggered by this payment.
5. Confirm the funds cannot be recovered: the AA composer explicitly refuses to emit outgoing private-asset payments (`aa_composer.js:1329-1330`), and the AA has no device address to receive/reconstruct the private payment chain needed to prove ownership and spend the output — the value is permanently stranded on the AA's address.
