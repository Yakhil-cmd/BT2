### Title
Uncaught `throw` in `readAsset()`'s attestor-list lookup can crash node validation when re-reading a `spender_attested` asset - (File: `storage.js`)

### Summary
`storage.readAsset()` is the single choke point used by both unit validation (`validatePayment`, `validateAttestorListUpdate`) and AA execution (`aa_composer.js` `sendUnit`/`sendDummyUnit` via `loadAssetWithListOfAttestedAuthors`) whenever a message references an asset that has `spender_attested = true`. Inside `addAttestorsIfNecessary()` it queries for the most recent stable, good-sequence `asset_attestors` row for that asset and, if none is returned, does `throw Error("no latest attestor list")` / `throw Error("no attestors?")` instead of passing an error through the callback chain like every other check in this function.

This mirrors the reported bug class: a single piece of persistent state (here, an asset that was declared `spender_attested`) that must "always succeed" for a shared, security-critical code path (payment validation, AA fund transfers) to complete. If that state ever fails to produce a matching row - because of an edge case in how `is_stable`/`sequence='good'` interacts with the attestor-list unit at the exact `last_ball_mci` boundary, or because attestor rows for an old/pruned unit are no longer resolvable while the `assets` row itself still exists - the function throws synchronously inside an asynchronous DB callback instead of returning a controlled validation error. [1](#0-0) 

### Finding Description
`readAsset()` first fetches the asset row and checks `objAsset.sequence !== "good"` to reject non-serial asset definitions gracefully via the callback. But when the asset is `spender_attested`, it calls `addAttestorsIfNecessary()`, which runs two sequential queries to find "the latest list of attestors" as of `last_ball_mci`: [2](#0-1) 

Both queries `throw Error(...)` on zero rows rather than calling `handleAsset(err)`. This function is invoked as part of a `conn.query` callback deep inside asynchronous control flow (from `validatePayment`, `validateAttestorListUpdate`, `composeDivisibleAssetPaymentJoint`/`composeIndivisibleAssetPaymentJoint`, and AA's `loadAssetWithListOfAttestedAuthors` in `aa_composer.js`), so a `throw` here is not caught by any of the surrounding `try/catch` in the calling code - it propagates as an uncaught exception, which in a Node.js process typically terminates the process (or, in bundled/mobile builds, corrupts in-flight validation state).

This is structurally identical to the reported `sweepTo` pattern: a loop/lookup over a piece of stored, asset-keyed data that is assumed to always be well-formed; when that assumption fails for even one asset, the routine aborts hard instead of degrading gracefully, and every future unit or AA response that touches that same asset hits the same `throw` again — a persistent DoS rather than a one-off failure.

Reachable triggers, all from unprivileged actors:
- Any asset issuer can create a `spender_attested` asset (`validateAssetDefinition`, `checkAttestorList`) [3](#0-2) .
- Any subsequent payment (from any user) or AA-issued payment referencing that asset invokes `loadAssetWithListOfAttestedAuthors` → `readAsset` → `addAttestorsIfNecessary` [4](#0-3) [5](#0-4) .
- AA execution takes the exact same path when an AA sends or bounces a payment of that asset: [6](#0-5) .

### Impact Explanation
If the "no latest attestor list" / "no attestors?" branch is ever hit for an asset that is otherwise considered valid (`sequence === 'good'`), the process throws instead of returning a validation error. Because this code path is shared by both unit validation and AA response construction, a single problematic `spender_attested` asset can:
- crash the validating node process when it tries to validate any unit referencing that asset, or
- crash AA execution when any trigger causes an AA to send/bounce that asset,

repeatedly, for every future occurrence, which is a persistent denial of service on validation/AA execution rather than a single failed transaction. This matches the "network unable to confirm new units" / "node disagreement on validity" impact bar, since nodes that hit the throw stop making progress on units touching that asset while others (with different DB state/timing) might not.

### Likelihood Explanation
This requires a precise edge condition around `is_stable`/`main_chain_index<=last_ball_mci`/`sequence='good'` for the attestor-list row versus the asset row to diverge (e.g., the attestor list row becomes momentarily unavailable relative to the query's stability cutoff, or gets pruned/archived independently of the `assets` row) while the asset itself is still reported as `sequence === 'good'`. I was not able to fully verify from the available index whether `asset_attestors` rows can ever be deleted/archived independently of the parent `assets` row (the archiving/pruning code exists in `archiving.js`, but I could not inspect its full logic within the available iterations to confirm or rule out this divergence). This introduces genuine uncertainty about how easily this exact `throw` is triggered in practice; it is best understood as a code-quality/defense-in-depth gap (unhandled exception on a lookup miss in a security-critical, attacker-reachable code path) rather than a confirmed, trivially-reproducible exploit.

### Recommendation
- Replace both `throw Error(...)` statements in `addAttestorsIfNecessary()` (storage.js, `readAsset`) with calls to `handleAsset(err)`/the callback error path, consistent with every other failure branch in `readAsset`.
- Audit archiving/pruning logic to guarantee `asset_attestors` rows for the *initial* (asset-defining) unit are never purged while the `assets` row for that unit is retained, or alternatively make `readAsset` tolerant of a missing attestor-list row (treat as "no attestors currently valid" rather than throwing).
- Add regression tests that simulate a `spender_attested` asset whose attestor-list row is momentarily unstable/missing at exactly `last_ball_mci`, verifying `readAsset` returns a controlled error instead of throwing.

### Proof of Concept
Not independently reproducible from the indexed code alone: the throw is only reached when the two nested SQL queries in `addAttestorsIfNecessary` return zero rows for an asset whose own `sequence === 'good'`. Confirming an exact, deterministic sequence of units/mci values that produces this divergence (or confirming archiving can decouple `asset_attestors` from `assets`) requires running the actual database/archiving code, which was not available within this analysis. This should be validated with a live Devin session that can execute `ocore`'s test suite and step through `archiving.js`/`readAsset` with a constructed asset + attestor-list unit sequence.
