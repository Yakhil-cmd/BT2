### Title
AA payouts can be permanently blocked (frozen funds) when balance after payout falls below the mandatory storage-size reserve - ([File: aa_composer.js])

### Summary
`aa_composer.js` enforces a hard, non-adjustable rule that an AA's byte balance can never drop below its `storage_size` (the bytes cost of its persisted state vars). This check is applied *after* the AA's response unit (including its intended payment output) has been computed, exactly the same "edge case not considered" pattern as the reported bug: a legitimate withdrawal/payout attempt that leaves the AA below a required minimum will be rejected every time it is retried, with no way to complete the operation unless external actors deposit more bytes into the AA first.

### Finding Description
When an AA responds to a trigger, `sendUnit()` builds the response unit, updates balances via `updateFinalAABalances()`, and only afterwards calls `updateStorageSize()`: [1](#0-0) 

`updateStorageSize()` computes the AA's new persisted-state size and compares it to the projected `byte_balance`: [2](#0-1) 

If `byte_balance < new_storage_size` (and `new_storage_size` exceeds `FULL_TRANSFER_INPUT_SIZE`), the whole trigger is rejected with `"byte balance ... would drop below new storage size ..."`, regardless of how legitimate or intentional the payout was. This is the same class of bug as the report: a downstream, unrelated minimum-amount/reserve check (`poolSettings.minDepositAmount` in Huma vs. `storage_size` reserve in ocore) is evaluated *after* the primary operation (fee reinvestment vs. AA payout) has already committed to an amount, and there is no fallback path that adjusts the amount to satisfy the check.

A partial mitigation exists for the specific case of a "send-all" base-asset output: `completePaymentPayload()` proactively adds a change output equal to `storage_size` to preserve the reserve: [3](#0-2) 

However, this mitigation only fires for `send_all_output` on the base asset. It does **not** apply to explicit/fixed-amount payment outputs computed by AA formulas (e.g., `{amount: "{some_computed_value}"}`), nor does it prevent state-var growth (e.g., incrementing counters, appending records, storing new data) from independently pushing `new_storage_size` above the AA's `byte_balance`. Any AA whose normal operation both (a) pays out most of its balance and (b) writes/extends state (as is extremely common — e.g., updating a withdrawal counter, ledger, or balance mapping) can end up in a state where every future attempt to execute that code path bounces indefinitely, because:
- The payout amount is fixed by the AA's own formula logic (analogous to `depositCoverFor()` always attempting an amount below `poolSettings.minDepositAmount`).
- There is no way for the AA (or the calling user) to reduce the state footprint or otherwise satisfy `byte_balance >= new_storage_size` without an unrelated top-up of bytes.

### Impact Explanation
This directly matches the "AA fund loss or freezing" acceptance criterion. Funds legitimately owed to a user (or the AA operator) become permanently stuck inside the AA: any trigger that both pays out funds and updates state that grows storage will keep bouncing with `"byte balance ... would drop below new storage size ..."`, exactly as the Huma bug made `_investFeesInFirstLossCover()` permanently revert once `getAvailableCap()` dropped below `minDepositAmount`. Users have no self-service way to resolve this from within the AA's own contract logic; they would have to convince a third party to send extra bytes to the AA address to satisfy the reserve, which is not something a normal DeFi user flow provides for.

### Likelihood Explanation
Many AAs implement bookkeeping (counters, balance maps, order books, escrow state) alongside payouts. Any AA design that pays out close to its full balance while also updating even a small state variable is at risk. The larger an AA's persisted state (`storage_size`), the more likely a full/near-full withdrawal will trip this check, since `storage_size` scales with the AA's usage history and cannot decrease unless state vars are deleted (freeing storage), which the AA logic may not do as part of a withdrawal flow.

### Recommendation
- When composing the payout, account for the *net* projected `storage_size` change *before* finalizing output amounts, similarly to how the existing `send_all_output` case reserves `storage_size` bytes — extend this reservation logic to fixed-amount base-asset outputs as well.
- Alternatively, allow an AA response to shrink its own state (freeing storage bytes) atomically with the payout so `new_storage_size` can be reduced to match the reduced `byte_balance`, rather than only failing the whole trigger.
- At minimum, document this reserve requirement clearly for AA authors and provide a getter/formula function so authors can dynamically clamp their payout amount to `byte_balance - storage_size` instead of relying on a fixed formula that can breach the reserve.

### Proof of Concept
1. Deploy an AA whose response, for a given trigger, both (a) pays out `balance[base] - X` bytes to the trigger address, and (b) writes/extends a state var (e.g., `var['count'] += 1`) whose cost pushes `storage_size` above `FULL_TRANSFER_INPUT_SIZE`.
2. Fund the AA so its balance is only slightly above `storage_size` (established via prior interactions).
3. Send a trigger requesting the payout. `sendUnit()` computes the payment, `updateFinalAABalances()` reduces `byte_balance` by the payout amount, then `updateStorageSize()` is invoked at [4](#0-3) .
4. Because `byte_balance < new_storage_size`, `updateStorageSize()` returns the error at [5](#0-4) , causing `revert(err)` and the entire response (including the payout) to bounce.
5. Because the AA's payout formula and state-write logic are fixed by its immutable definition, every subsequent identical trigger will bounce the same way, permanently locking the funds unless a third party manually funds the AA with extra bytes.

Note: I was unable to fully inspect the exact rollback/`revert()` implementation (the tool call to view it did not complete before the session ended), so I cannot cite the precise mechanics of how the bounce is finalized on-chain (e.g., whether bounce fees are still charged to the trigger's sender). This should be verified directly in `aa_composer.js` around the `revert` and `bounce` functions before finalizing severity/exploit details.
