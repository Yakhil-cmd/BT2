### Title
Unvalidated swap routes can add unauthorized wallet-token transfers to a victim’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The controller accepts opaque caller-supplied swap bytes and forwards them to the configured router without decoding the route, constraining its venues, or binding execution to a fixed authorization manifest. A malicious route can therefore invoke attacker-controlled contract code that requests an additional token transfer from the victim, causing simulation to place that transfer beneath the victim’s `swap_collateral` authorization entry. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` accepts a caller-controlled `swap: Bytes`, authenticates the caller, verifies account ownership or delegation, withdraws collateral into the controller, and passes the opaque route to the swap helper. [3](#0-2) 

`swap_tokens` validates only that the route is non-empty and that `amount_in` is positive; it then authorizes exactly one controller-to-router input transfer and calls `router.execute_strategy(controller, amount_in, swap)`. [4](#0-3) 

The helper’s authorization protects only the controller’s input-token transfer: it creates a leaf invocation for `token_in.transfer(controller, router, amount_in)` and does not describe or constrain downstream venue calls. [5](#0-4) 

Because `StrategySwap` is opaque `Bytes`, none of the controller-side checks identify the contracts reached by the route or reject a venue that calls `token.transfer(victim, attacker, amount)`. [6](#0-5) [7](#0-6) 

The harness demonstrates the concrete authorization behavior: a route-selected contract calling `wallet_token.transfer(alice, attacker, balance)` is recorded as a child of Alice’s `swap_collateral` authorization, and the transfer executes when that poisoned tree is signed. [2](#0-1) [8](#0-7) 

The same opaque route parameter reaches `swap_tokens` from `swap_debt`, `repay_debt_with_collateral`, and `multiply`, so the issue is not confined to the collateral-swap entrypoint. [9](#0-8) [10](#0-9) [11](#0-10) 

### Impact Explanation
A crafted route can steal unrelated wallet tokens from the account owner or delegate who signs the poisoned authorization tree, without requiring a prior allowance for those tokens. [12](#0-11) [8](#0-7) 

The normal swap can still return fair output and pass the controller’s measured-output and final-risk checks, so the protocol-visible strategy result does not reveal that an unrelated wallet transfer was also authorized. [13](#0-12) [14](#0-13) 

### Likelihood Explanation
Exploitation requires the victim to sign the authorization tree containing the rogue nested transfer, typically after a malicious route or interface presents the operation as an ordinary collateral, debt, repay-with-collateral, or multiply swap. [15](#0-14) [16](#0-15) 

The attacker does not need a privileged role, leaked key, compromised router, or control of the victim’s lending account; the attacker only needs to induce the victim to submit a route whose venue performs the extra transfer. [17](#0-16) [18](#0-17) 

### Recommendation
Constrain routes to an on-chain allowlist of known venue contracts or otherwise decode and verify every externally callable address before invoking the router. [4](#0-3) 

Until routes are constrained, wallets and SDKs must simulate the transaction, reject any authorization tree containing children beyond the expected input transfer, and display every nested contract call and token movement before signing. [5](#0-4) [19](#0-18) 

### Proof of Concept
1. Give Alice an account with listed USDC collateral and an unrelated wallet-token balance. [20](#0-19) 
2. Deploy a route-selected venue configured to call `unrelated_token.transfer(alice, attacker, balance)`. [21](#0-20) 
3. Simulate `swap_collateral(alice, account_id, USDC, amount, ETH, malicious_route)`; the strategy can still receive the expected ETH output. [22](#0-21) [2](#0-1) 
4. Simulation records the unrelated wallet-token transfer as a child of Alice’s `swap_collateral` authorization. [19](#0-18) 
5. If Alice signs that tree, the venue’s transfer executes, leaving Alice’s unrelated token balance at zero and crediting the attacker. [8](#0-7)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
