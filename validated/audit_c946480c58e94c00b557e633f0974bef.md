### Title
Webhook signature check authenticates the wrong organization to the repository being written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a request against using `repository_owner`, a value read straight out of the *attacker‑controlled* JSON body (`repository.owner.login`, falling back to `organization.login`). The actual write target — the `Repository`/`Stack`/`Commit` acted on by the event handlers — is selected from a *different* field in the same body (`repository.full_name`, or `sha` for status events), which is never checked against the value used for signature verification.

### Finding Description
```ruby

def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`verify_webhook_signature` performs a straightforward HMAC compare against the secret configured for whichever organization name is present in the payload:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [2](#0-1) 

In a multi‑organization Shipit deployment (documented and supported configuration, see `config/secrets.development.shopify.yml` / `docs/setup.md`), each organization has its own GitHub App and its own `webhook_secret`: [3](#0-2)

Since the entire raw body is attacker-controlled when posting directly to `/webhooks`, an attacker who legitimately controls an installation for **Org A** (and therefore knows Org A's `webhook_secret`, obtainable from their own App settings) can construct an arbitrary JSON payload where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` picks Org A's secret and the HMAC check passes), and
- `repository.full_name` = `"OrgB/victim-repo"` or `sha` = a commit sha belonging to a stack under a completely different, unrelated organization tracked by the same Shipit instance.

The binding that should hold is:
`organization authenticated by verify_signature == organization owning the repository/commit written by the handler`

This binding is broken: nothing ties `repository.owner.login` (verified) to `repository.full_name`/`sha` (acted on). An attacker holding valid credentials only for Org A can therefore make Shipit believe a status/push event legitimately originated for Org B's repositories and stacks.

### Impact Explanation
The `StatusHandler` path is the most severe: it creates a `CommitStatus` on any `Commit` matching the attacker-chosen `sha`, regardless of which organization actually owns that commit/stack, as long as the attacker's own org's secret validates the outer signature check. If that status satisfies a stack's required CI contexts and `continuous_deployment` is enabled, `ContinuousDeliveryJob`/`trigger_continuous_delivery` can then deploy the corresponding commit for an org the attacker has no legitimate access to:
```ruby
def perform(stack)
  return unless stack.continuous_deployment?
  return if stack.continuous_delivery_schedule && !stack.continuous_delivery_schedule.can_deploy?
  return if stack.occupied?
  stack.trigger_continuous_delivery
end
``` [7](#0-6) 

This meets the "unauthorized deploy" bar: an attacker with credentials scoped to their own organization's App installation can forge a fake CI-green signal and trigger an unauthorized deploy on a stack belonging to a different organization served by the same Shipit instance. The `PushHandler` path additionally lets the attacker force an arbitrary `sync_github`/`expected_head_sha` on a foreign stack.

### Likelihood Explanation
Requires only: (1) the target Shipit instance to be configured for multiple GitHub organizations (an explicitly supported and documented configuration), and (2) the attacker to control/administer at least one App installation on that instance (their own org), which grants them their own `webhook_secret` value — no access to the victim org's credentials, GitHub session, or `ApiClient` token is needed. Given the documented multi-org setup and the absence of any binding between `repository.owner.login` and `repository.full_name`/`sha`, this is straightforwardly reachable by an unprivileged-for-the-victim-org attacker.

### Recommendation
After verifying the HMAC signature against the secret selected by `repository.owner.login` (or `organization.login`), additionally require that the owner of `repository.full_name` (or the resolved `Commit`'s stack/repository owner) matches that same authenticated organization before any handler mutates state. Reject events where these two identities diverge.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with distinct GitHub Apps/`webhook_secret`s (per `docs/setup.md`'s multi-org config).
2. Attacker administers `OrgA`'s GitHub App and can read `OrgA`'s `webhook_secret` from the App settings page.
3. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "<victim-org-B-commit-sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/some-repo"}
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POSTs directly to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, validates the HMAC successfully (it was computed with the real `OrgA` secret), and the request proceeds.
6. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — matching the real commit under `OrgB` — and creates a passing `CommitStatus` for it, satisfying `OrgB`'s required CI context despite the attacker never having any credentials for `OrgB`.
7. If `OrgB`'s stack has `continuous_deployment` enabled, the next `ContinuousDeliveryJob` run deploys that commit.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
