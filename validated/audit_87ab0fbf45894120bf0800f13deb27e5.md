### Title
Attacker-controlled `.gitmodules` submodule fetch failure causes persistent sync denial - (File: main.go)

### Summary
The external report's root cause is a pattern where an untrusted, attacker-settable destination is called unconditionally inside a critical state-transition path, and a failure of that call aborts the entire operation, blocking legitimate users from making progress (turning the contract into a "honeypot"). The closest reachable analog in `git-sync` is the unconditional `git submodule update --init` call made from committed, attacker-influenced repo content (`.gitmodules`), which runs *before* the atomic symlink publish step. If an attacker who can push a commit to the synced repository (a realistic "untrusted repo content" actor per the CI/GitOps threat model `git-sync` is built for) adds/points a submodule at an unreachable, slow, or credential-gated URL, the unconditional submodule fetch will fail on every sync attempt, and the new (and all subsequent) hashes will never be published — a persistent sync denial.

### Finding Description
`configureWorktree` unconditionally runs a `git submodule update` whenever submodules are not explicitly disabled, on every worktree it builds, regardless of whether the fetch of a specific submodule can succeed: [1](#0-0) 

This call happens as part of `SyncRepo`'s per-cycle sequence — fetch, reset, create worktree, `configureWorktree` (which runs the submodule update), and only *after* that succeeds does the code proceed to `beforePublish`/`publishSymlink`: [2](#0-1) 

If `configureWorktree` returns an error (e.g. because the submodule URL embedded by an attacker-authored `.gitmodules` in a pushed commit is unreachable, requires unknown credentials, or intentionally times out), `SyncRepo` returns an error before ever calling `git.publishSymlink`. The symlink contract is `git-sync`'s core atomicity/consistency guarantee: [3](#0-2) 

Back in the main loop, that error is treated the same as any transient network failure — it increments `failCount`, logs, and retries on the next period; if `--max-failures` is exceeded, the whole process exits: [4](#0-3) 

Unlike a transient network blip, this failure is deterministic and repo-content-controlled: as long as the bad `.gitmodules` reference exists at the target ref, every sync attempt will fail identically, so `--max-failures`/backoff never resolves the problem, and the good hash is never published.

### Impact Explanation
This matches the "persistent sync denial" impact accepted by the rules. An attacker who can commit to the tracked branch/ref (a common scenario for `git-sync` used against forks, PR branches, or any repo where write access is broader than the operator's trust boundary) can permanently stall publication of new content by embedding a submodule pointing at an address they don't control the availability of (or one requiring credentials `git-sync` was never given, see `--credential`/`--askpass-url`/`--ssh-key-file` docs). This denies the intended consumers (sidecar containers relying on the `--link` symlink) any further updates, and can additionally crash the `git-sync` process/pod if `--max-failures` is reached, causing a Kubernetes CrashLoopBackOff — the practical honeypot-style consequence of "buy but never see new state published."

### Likelihood Explanation
Likelihood depends on the operator's threat model for who can push to the synced ref, and on `--submodules` not being set to `off`. `git-sync` explicitly documents credential plumbing specifically to support submodules from multiple hosts (`--credential`, tested e2e for cross-host submodules), which shows submodule support with external URLs is an expected, commonly-used configuration: [5](#0-4) [6](#0-5) 
This makes the analog realistic wherever the synced repository accepts contributions from parties less trusted than the `git-sync` operator (e.g., PR-preview pipelines), without requiring any leaked keys, malicious operator, or malicious git server — only an attacker-authored commit reaching the tracked ref.

### Recommendation
- Treat submodule update failures distinctly from other fetch errors: do not let a submodule failure block re-checking/publishing the top-level repo content when `--submodules` submodule fetch fails, or provide a `--submodules-timeout`/`--submodules-required=false` style opt-out so a broken submodule does not block the primary sync.
- Consider validating/sandboxing submodule URLs (e.g., via `protocol.allow`/an explicit allow-list of hosts, similar to how `--credential` already scopes trust per URL) before invoking `git submodule update --init`, so untrusted commits cannot force outbound network calls to arbitrary or unreachable destinations as a side effect of syncing.
- Ensure `failCount`/`--max-failures` handling distinguishes "will never succeed without operator intervention" (bad submodule config baked into the commit) from transient connectivity errors, and surface this condition prominently (e.g., a distinct metric/log level) rather than silently retrying forever.

### Proof of Concept
1. Operator runs `git-sync --repo=<tracked-repo> --root=/root --link=link` with default `--submodules` (not `off`) against a repository where an untrusted party (e.g., a PR author whose branch gets merged/tracked) has write access.
2. Attacker pushes a commit to the tracked ref that adds a `.gitmodules` entry pointing to an unreachable host or one that requires unknown auth, e.g.:
   `git submodule add http://10.255.255.1/nonexistent.git evil-sub`
3. On the next sync cycle, `git.fetch`/`rev-parse` succeed (top-level repo content is fine), but `configureWorktree` fails at the `git submodule update --init` step: `main.go:1744`.
4. `SyncRepo` returns an error before reaching `publishSymlink`: `main.go:1933-1963`.
5. The main loop logs the error and retries every `--period`, but since the bad submodule reference is committed and immutable, every retry fails identically: `main.go:1056-1063`. The `--link` symlink is never updated to the new (or any subsequent) commit, and if `--max-failures` is set, `git-sync` eventually calls `os.Exit(1)`, crashing the sidecar.

```markdown
### Why the symlink?

git checkouts are not "atomic" operations.  If you look at the repository while
a checkout is happening, you might see data that is neither exactly the old
revision nor the new.  git-sync "publishes" updates via the symlink to present
an atomic interface to consumers.  When the remote repo has changed, git-sync
will fetch the data _without_ checking it out, then create a new worktree, then
change the symlink to point to that new worktree.

git-sync does not currently have a no-symlink mode.
```
