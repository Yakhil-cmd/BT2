### Title
Signature verification keyed on `repository.owner.login`/`organization.login`, while webhook handlers act on `repository.full_name` - organization authenticated ≠ repository written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). But the actual handlers dispatched by `Webhooks.for_event` (e.g. `PushHandler`, `CheckSuiteHandler`) resolve the target `Stack`/`Repository` using a completely different payload field: `Handler#repository_name`, which reads `payload.dig('repository','full_name')`. This is the same class of bug as the external report: a value is trusted for one purpose (authorization/authentication) while a different, unauthenticated value is used to determine what gets acted on.

### Finding Description
In a multi-organization Shipit deployment (see `test/dummy/config/secrets_double_github_app.yml`, which configures independent `webhook_secret` values per organization), the webhook signature is verified per-organization: [1](#0-0) [2](#0-1) [3](#0-2) 

The signature is checked against `Shipit.github(organization: repository_owner)`'s `webhook_secret`, where `repository_owner` is taken from `repository.owner.login` (or `organization.login`).

However, the actual event handlers never look at `repository.owner.login` again — they resolve which `Stack`/`Repository` to mutate purely from `repository.full_name`: [4](#0-3) [5](#0-4) 

Since `repository.owner.login` and `repository.full_name` are two independent, attacker-controlled JSON fields in the same signed payload, an attacker who is an administrator of their own GitHub organization (`OrgA`, which has the Shipit GitHub App installed and thus a webhook secret they legitimately possess) can POST directly to the publicly reachable `/webhooks` endpoint (this is not limited to deliveries relayed by GitHub) with a payload where:
- `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) — so `verify_signature` picks OrgA's webhook secret, which the attacker can correctly sign.
- `repository.full_name = "OrgB/victim-repo"` — so `Handler#repository_name` / `Repository.from_github_repo_name` resolves to a repository belonging to a completely different, victim organization `OrgB` also hosted on the same shared Shipit instance.

The equality that should hold is:
`organization whose secret authenticated the signature == organization owning the repository the handler mutates`

but the code enforces no such equality — the two are looked up from unrelated fields.

### Impact Explanation
Using `PushHandler`, this lets the attacker enqueue `GithubSyncJob`/`stack.sync_github(expected_head_sha:)` for a victim's `Stack` with an attacker-chosen SHA [6](#0-5) , forcing a resync against an arbitrary commit not actually pushed by the victim org, which can affect what Shipit considers deployable/deployed for that stack — an unauthorized, cross-organization influence on deploy state. `CheckSuiteHandler` and `StatusHandler` similarly let the attacker forge check-run refreshes / commit statuses tied to another organization's commits [7](#0-6) [8](#0-7) , potentially manipulating whether a victim stack's commit is considered "green" and deployable, feeding into an unauthorized deploy decision. This crosses a repository/organization write boundary the attacker was never authorized for, matching the "cross-repository writes / unauthorized deploy" high-impact criteria.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple organizations with distinct webhook secrets (a documented, supported configuration — see `test/dummy/config/secrets_double_github_app.yml`), and requires the attacker to control (or be an admin of) at least one of those organizations so they legitimately know that organization's webhook secret. No GitHub relay is required since `/webhooks` is a public unauthenticated HTTP endpoint that only checks the HMAC signature, not the source. This is a moderate-likelihood scenario specific to shared/multi-tenant Shipit deployments.

### Recommendation
After selecting the GitHub App/secret via `repository_owner` for signature verification, re-derive and cross-check that the same organization owns the repository referenced by `repository.full_name` (or any other repository/organization identifier subsequently used by handlers) before dispatching to handlers — i.e., enforce `repository.full_name.split('/').first == repository_owner` (case-insensitively) in `WebhooksController#verify_signature`, or have `Handler#repository_name` reuse the already-authenticated `repository_owner` rather than trusting `full_name` independently.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`), both organizations having stacks tracked by the same Shipit instance.
2. As an admin of `OrgA`, obtain `OrgA`'s webhook secret from its own GitHub App settings.
3. Craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>`.
5. POST the body with headers `X-Github-Event: push` and the computed signature directly to `<shipit-host>/webhooks`.
6. `verify_signature` resolves `repository_owner = "OrgA"`, validates successfully against `OrgA`'s secret; `PushHandler` then resolves the target via `repository.full_name = "OrgB/victim-repo"`, enqueuing `GithubSyncJob` against `OrgB`'s stack with the attacker-supplied `after` SHA — despite the attacker never having been authenticated for `OrgB`.
