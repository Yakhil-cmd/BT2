### Title
Webhook signature verification is silently bypassed when an org has no `webhook_secret`, allowing forged `membership` events to escalate into `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` contains the same class of "special-case early return" bug as the `pow()` finding: it returns `true` (accepted) whenever the configured `webhook_secret` is blank, instead of only special-casing the *hashing* step. This makes the binding "GitHub HMAC-signed the payload" == "payload is trusted and acted upon" collapse to always-true for any organization configured without a webhook secret, letting an unauthenticated attacker forge a `membership` webhook that grants themselves membership in a team listed in `Shipit.github_teams`, bypassing the application's core authorization gate.

### Finding Description
`WebhooksController#verify_signature` derives which GitHub App/org config to use for verification purely from the untrusted JSON payload (`repository_owner`, taken from `params.dig('repository','owner','login')` or `params.dig('organization','login')`), then calls: [1](#0-0) 

into: [2](#0-1) 

Line 77, `return true unless webhook_secret`, is the exact analog of the reported bug: an edge-case check (`self.is_zero()` in the report / `webhook_secret.blank?` here) short-circuits before the "real" verification logic and returns an unconditionally accepted value instead of computing the actual answer. A `webhook_secret` of `nil` is an explicitly supported/shown configuration: [3](#0-2) 

When this early return fires, `verified` in the controller is `true` regardless of the actual `X-Hub-Signature` header content, so any payload is accepted and dispatched to handlers, including `Shipit::Webhooks::Handlers::MembershipHandler`: [4](#0-3) 

Test coverage confirms the membership handler creates/attaches `Team`, `User`, and `Membership` records directly from webhook payload fields with no further authorization check: [5](#0-4) 

Those `Membership` rows are exactly what gates the application's primary authorization control: [6](#0-5) [7](#0-6) 

**Binding broken (equality that should hold but doesn't):**
`organization cryptographically authenticated via webhook_secret` == `membership/team data trusted and written to the datastore`.
When `webhook_secret` is unset for an org, the left side is never actually evaluated (it's vacuously `true`), yet the right side proceeds anyway.

### Impact Explanation
This directly matches the "escalation into `Shipit.github_teams` authorization" High-impact category. An attacker who can complete a legitimate GitHub OAuth login to Shipit (obtaining an ordinary unauthorized `User` row, since `current_user.authorized?` initially denies them) can separately POST an unauthenticated, unsigned `membership` webhook claiming `member.login = <their own login>` and a `team` matching one of `Shipit.github_teams`. Because the target org has no `webhook_secret` configured, `verify_webhook_signature` accepts it unconditionally, `MembershipHandler` creates the `Membership`, and `User#authorized?` subsequently returns `true` for that account — granting full access to Shipit (deploys, rollbacks, API client management, etc.) without ever actually being a member of the required GitHub team.

### Likelihood Explanation
Requires only that at least one configured GitHub organization/app in `Shipit.github_apps` has no `webhook_secret` set — a configuration explicitly shown as acceptable in `config/secrets.development.shopify.yml` — combined with the attacker being able to complete an ordinary OAuth login (any GitHub account, since login itself isn't gated by `github_teams`, only post-login access is, per `app/controllers/concerns/shipit/authentication.rb:20-34`). No token, webhook secret knowledge, or privileged access is required to send the forged webhook itself.

### Recommendation
- In `lib/shipit/github_app.rb#verify_webhook_signature`, do not treat a blank `webhook_secret` as automatic verification success; instead fail closed (reject the webhook) or require `webhook_secret` to be present as a hard configuration requirement for any org whose webhooks are processed.
- Do not let `WebhooksController` select the verifying org/secret based on unauthenticated payload content (`repository_owner`) before any cryptographic check has occurred.
- Add authorization checks in `MembershipHandler` beyond "the webhook was accepted" (e.g., cross-check via the GitHub API rather than trusting the payload verbatim) before mutating `Membership` records that feed `User#authorized?`.

### Proof of Concept
1. Operator configures two orgs in `secrets.yml`: `authorized-org` (real, has `webhook_secret`) and `other-org` (present in config, but `webhook_secret: nil`, e.g. as shown in `config/secrets.development.shopify.yml`).
2. Attacker signs into Shipit via normal GitHub OAuth, creating `User#id=99`, login `attacker`. `attacker.authorized?` is `false` (not in any `Shipit.github_teams`).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: membership`, no valid `X-Hub-Signature`, and body:
   `{"action":"added","organization":{"login":"other-org"},"team":{"id":..., "name":"<team in Shipit.github_teams>","slug":"...","url":"..."},"member":{"login":"attacker"}}`
4. `verify_signature` resolves `Shipit.github(organization: "other-org")`, calls `verify_webhook_signature`, which hits `return true unless webhook_secret` (blank) → `verified = true` → request proceeds (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-77`).
5. `MembershipHandler` runs, creating a `Membership` linking `attacker` to the privileged team (behavior confirmed by `test/controllers/webhooks_controller_test.rb:129-165`).
6. Attacker reloads Shipit; `User#authorized?` (`app/models/shipit/user.rb:80-82`) now returns `true`, and `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:20-34`) grants full application access.

Note: I was unable to inspect the full body of `app/models/shipit/webhooks/handlers/membership_handler.rb` before the tool budget ran out; the impact conclusion relies on the behavior documented by its test suite (`test/controllers/webhooks_controller_test.rb`), which does show `Team`/`User`/`Membership` records being created directly from webhook payload fields.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
```
