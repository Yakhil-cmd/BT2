### Title
Gasless TPS cap is enforced with eventual, per-validator consistency, allowing aggregate admission far above `gasless_max_tps` - (File: crates/sui-core/src/gasless_rate_limiter.rs)

### Summary
`GaslessRateLimiter::try_acquire` combines a per-validator local burst counter with a shared, consensus-fed global counter that is only updated after a commit lands. Because each validator makes its local admission decision independently and the shared counter lags real consensus finality, an attacker who spreads gasless transaction submissions across many validators can get each validator to independently admit up to `gasless_max_tps` before any of them observe the others' admissions via `consensus_counter`, allowing the aggregate admitted (and eventually committed) gasless transaction volume to exceed the configured cap by a factor tied to validator count/consensus latency, not by the single `max_tps` value the protocol intends to enforce network-wide.

### Finding Description
`try_acquire` gates admission with two checks: [1](#0-0) 

The consensus-side gate only reflects transactions that have already been **committed** and fed back via `record_commit`, which is driven by `commit_timestamp_ms`: [2](#0-1) 

Meanwhile, the local gate is a per-validator, `Instant`-based fixed window that resets independently on each validator process, with no coordination with the shared counter's window boundaries: [3](#0-2) 

Because `local` is a per-instance `Arc<Mutex<FixedWindowCounter>>` created fresh at validator startup, each validator's local window phase is a function of that validator's own uptime, and is never synchronized to the other validators' or to the consensus-fed window. The consensus check (`consensus_counter.current_count() >= max_tps`) is checked *before* the local counter is incremented, but it only reflects transactions that already made it through consensus and were reported via `record_commit` — i.e., it lags by at least one round of consensus latency behind transactions currently in flight. During that lag window, every validator's local counter independently permits up to `max_tps` gasless admissions, since none of them yet see each other's in-flight admissions in the shared counter. An attacker submitting gasless transactions concurrently to many/all validators can therefore get up to `N × max_tps` transactions admitted into proposals before the shared `consensus_counter` catches up and starts rejecting further ones (and once it does, `record_commit` resets/accumulates only for the window matching `commit_timestamp_ms`, so misaligned local/global windows further reduce the effectiveness of the global backstop at window boundaries).

### Impact Explanation
This directly defeats the intended purpose of `gasless_max_tps`: capping fee-sponsored ("gasless") transaction throughput to bound sponsor liability. If the sponsor mechanism funds gas for admitted gasless transactions, uncapped admission across the validator set drains sponsor funds/allowance at a multiple of the configured rate, which falls under the "harmful smart-contract behavior" / uncapped free-transaction throughput impact class.

### Likelihood Explanation
The attacker model required is an ordinary, unauthenticated transaction submitter distributing gasless transaction submissions across the validator set — no malicious validator, admin, or governance action is needed. This is a normal, publicly-reachable interaction pattern (submitting the same class of sponsored transaction to multiple validator endpoints), making the likelihood high wherever `gasless_max_tps` is configured to a nonzero, restrictive value.

### Recommendation
Enforce the gasless cap consistently: align the local burst window to the same wall-clock second boundary used by the consensus counter (e.g., derive `window_start`/`window_second` from real time rather than `Instant`, and reduce or remove independent per-validator local allowance), or better, only admit gasless transactions based on the shared/consensus-derived counter with a conservative per-validator share (`max_tps / num_validators`) rather than allowing each validator to independently grant the full `max_tps` burst.

### Proof of Concept
The unit tests already demonstrate that a single limiter's local layer allows `max_tps` admissions irrespective of the consensus counter’s value once the consensus counter is below the threshold (`test_local_counter_prevents_burst`, `test_consensus_allows_under_capacity`): [4](#0-3) 
Extending this to multiple `GaslessRateLimiter` instances (one per simulated validator) sharing a single `ConsensusGaslessCounter`, and calling `try_acquire` on each concurrently before any `record_commit` call reflects the others' admissions, shows the aggregate successful admissions across instances reaching `N × max_tps` instead of being capped at `max_tps`.

Note: I was not able to trace the exact production call sites that invoke `try_acquire` on transaction handling and `record_commit` on consensus commit (in `authority_server.rs`/`consensus_handler.rs`) within the available tool budget, so I cannot fully confirm the real-world consensus round-trip latency or whether any additional synchronization exists outside this file. The finding is based on the rate-limiter module's own logic and documented design, which is internally consistent with the described exploit path.

impl FixedWindowCounter {
    fn try_acquire(&mut self, max_tps: u64) -> bool {
        if self.window_start.elapsed().as_secs() >= 1 {
            self.count = 0;
            self.window_start = Instant::now();
        }
        if self.count < max_tps {

            true
        } else {

        }
