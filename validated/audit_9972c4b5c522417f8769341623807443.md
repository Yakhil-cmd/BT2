### Title
Assets with dynamic `spender_attested`/`transfer_condition` can be revoked by the issuer at any time, permanently freezing collateral held by an AA - (File: `validation.js`, `storage.js`)

### Summary
An Obyte asset can be defined with `spender_attested: true` (a list of attestors that must vouch for an address before it can receive the asset) and/or a `transfer_condition`. Both are evaluated **dynamically, at the time each payment is validated**, using the *current* (last-stable-ball) attestor list / condition state, not a snapshot taken when the asset was created or first accepted as collateral. The asset issuer can change the attestor list at any time via an `asset_attestors` message, or the `transfer_condition` can reference state (oracle feeds, `attested`, etc.) that the issuer or a third party controls. This is functionally identical to a pausable ERC-721 (CryptoKitty/CryptoFighter) whose `transferFrom` can be blocked by the contract owner at will — except here the "pause" is scoped to specific addresses/conditions instead of the whole contract.

### Finding Description
When any payment message carrying a custom asset is validated, `validatePayment` loads the asset and its currently attested addresses via `storage.loadAssetWithListOfAttestedAuthors` / `storage.readAsset`, and then `validatePaymentInputsAndOutputs` checks, for every output address, whether it is attested and whether the `issue_condition`/`transfer_condition` is satisfied: [1](#0-0) 

The attestor list itself is not fixed at asset creation — it is a mutable side table (`asset_attestors`) that only the asset's definer address can update, and each update is evaluated by pulling the *latest* stable list: [2](#0-1) [3](#0-2) 

`storage.filterAttestedAddresses` re-checks attestation against the current attestor set and current `attestations` table for every payment: [4](#0-3) 

Because this check is re-evaluated on every single payment (not cached from when the collateral was deposited), the asset issuer (or the party the issuer delegated as attestor) can simply stop attesting a specific address, or publish a new `asset_attestors` unit removing it from the trusted list, at any point after the asset has already been accepted as collateral by an AA-based lending/vault contract. The same applies to a `transfer_condition` built on external state (data feed, `attested`, etc.) that can flip to `false` after the asset is already locked in the AA.

When an AA (e.g., a lending contract) later tries to send this asset back to the borrower (on repayment) or to a liquidator (on default), the composed response unit goes through the normal validation pipeline inside `sendUnit`, and if the transfer/attestation condition is not currently satisfied, `validateAndSaveUnit` fails and the whole response bounces: [5](#0-4) [6](#0-5) 

`bounce()` only refunds the **trigger's bytes/asset outputs already inside the trigger** using `bounce_fees`; it does not un-freeze or return the asset that is already sitting in the AA's balance from a previous deposit. If the destination address (the original depositor/borrower, or any liquidator) can never satisfy the attestation/condition again, the AA can never successfully send that asset out — the collateral is stuck in the AA forever, and the borrower can never fully "repay" (get collateral back) nor can a liquidator realize the collateral.

### Impact Explanation
Any Obyte AA-based protocol (lending/vault/escrow AA) that accepts a third‑party custom asset as collateral is exposed to this bug class: the asset issuer, by design or maliciously, can attest/de‑attest addresses or otherwise flip the `transfer_condition` at will, at any moment after the AA already holds the collateral. This blocks:
- the borrower from getting collateral back on repayment,
- a liquidator from receiving seized collateral on default,

permanently freezing user funds inside the AA — this is the same "pausable NFT blocks repay/liquidate" pattern from the original report, mapped onto Obyte's asset condition machinery (`spender_attested`/attestor list and `issue_condition`/`transfer_condition`). This is a fund‑freezing bug for any AA relying on such assets, matching the accepted "AA fund loss or freezing" impact category.

### Likelihood Explanation
Likelihood is Medium: it requires the AA in question to accept an asset with `spender_attested: true` or a `transfer_condition` as collateral/consideration, and requires the asset issuer (or whoever the condition depends on) to change the condition after collateral has been locked. Both `spender_attested` assets and custom `transfer_condition` assets are first‑class, fully supported asset types in ocore, so any AA developer who does not explicitly restrict accepted assets to unconditional ones (`spender_attested=false`, no `issue_condition`/`transfer_condition`) is exposed. The action needed from the issuer (publishing an `asset_attestors` unit, or letting a data-feed-based condition flip) is cheap and requires no special privilege beyond being the asset's own definer, which is exactly analogous to an NFT contract owner calling `pause()`.

### Recommendation
- AA-based protocols should validate at the time collateral is accepted (and periodically re-validate) that the asset has `spender_attested: false` and no `issue_condition`/`transfer_condition`, or otherwise ensure the collateral asset's spend conditions cannot be revoked after deposit.
- Consider adding an oscript/AA-level primitive to query whether an asset is "unconditionally transferrable" so AAs can reject risky collateral assets at accept-time.
- Document this asset design behavior prominently for AA authors so they are aware that `spender_attested`/`transfer_condition` are dynamic and re-checked on every payment, not fixed at asset-issuance time.

### Proof of Concept
1. Asset issuer defines asset `A` with `spender_attested: true`, `attestors: [X]`, `issued_by_definer_only: true`.
2. Attestor `X` attests address `U` (the future borrower). `U` deposits asset `A` into lending AA `L` as collateral and borrows bytes.
3. Before `U` repays, attestor `X` (controlled by, or colluding with, the asset issuer) publishes a new `asset_attestors` message for asset `A` that no longer includes `U`'s attestation as valid (or the issuer simply never re-attests `U`, and the earlier attestation unit is superseded by `storage.readAsset`'s "latest attestor list" logic, `storage.js:1917-1946`).
4. `U` repays the loan; AA `L` tries to send asset `A` back to `U` via `sendUnit`. `validatePaymentInputsAndOutputs` (`validation.js:2630-2659`) rejects the output because `U` is no longer attested.
5. `validateAndSaveUnit` fails, `bounce()` fires (`aa_composer.js:909-945`), refunding only trigger bytes — the collateral asset `A` remains stuck in AA `L`'s balance indefinitely, since `U` can never again satisfy the attestation check that the issuer/attestor controls.

			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
