### Title
ERC20Transactor withdraw/deposit path assumes full requested amount was moved, breaking XCM `AssetsInHolding` accounting for fee-on-transfer ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` interact with arbitrary user-deployed `pallet-revive` contracts matched via `assets_common::ERC20Matcher` (any `AccountKey20` location on Asset Hub Westend). Both functions call the token's `transfer()` and, on a `true` boolean return, unconditionally treat the *requested* `amount` as the *actual* amount moved — exactly the "fee on transfer" pattern from the referenced report, where a token that skims a fee on `transfer()` still returns `true` while delivering less than `amount`.

### Finding Description
`withdraw_asset_with_surplus` ( [1](#0-0) ) calls `IERC20::transferCall{ to: checking_address, value: amount }` from the user account to the reserve/checking account. It never reads `balanceOf(checking_account)` before/after; it only checks that the ABI-decoded return value is `true`: [2](#0-1) 
On success it manufactures `Erc20Credit(amount)` — the *requested* amount, not the amount actually received by `TransfersCheckingAccount` — and injects it into the XCM executor's `AssetsInHolding`: [3](#0-2) 

Symmetrically, `deposit_asset_with_surplus` ( [4](#0-3) ) transfers `amount` from the checking account to the beneficiary and, again, only checks the boolean return value, not actual amount received by the beneficiary: [5](#0-4) 

This is precisely the report's violated invariant: "the protocol should use stored token balances instead of transfer for calculating amounts." Here the "protocol" is the XCM executor's `AssetsInHolding` ledger and the ERC20 "checking account" that backs cross-consensus transfers of the ERC20 asset. Every other native FRAME transfer path in this codebase (e.g. `pallet_assets::do_transfer`, `fungible`/`fungibles::Mutate::transfer`, `FungibleAdapter`/`FungiblesAdapter`) uses the *actual* returned/credited amount from the ledger mutation and callers check it (see e.g. `substrate/frame/asset-conversion/ops/src/lib.rs:221-231` requiring `T::Assets::transfer(...)? == expected`). The `ERC20Transactor` is the sole asset transactor in the `AssetTransactors` tuple that instead trusts an external, arbitrary, user-controlled contract's boolean return value and hard-codes the nominal requested amount as the credited/debited amount.

`ERC20Transactor` is wired into Asset Hub Westend's production `AssetTransactors` tuple and is reachable via any `PolkadotXcm::execute`/XCM program a signed account can submit, matching any `AccountKey20`-addressed contract deployed via `pallet-revive` (`ERC20Matcher`, no allow-list observed in `xcm_config.rs`): [6](#0-5) 
Anyone can permissionlessly deploy a fee-on-transfer ERC20 contract via `pallet_revive::instantiate`, then submit a signed `PolkadotXcm::execute` withdrawing/depositing that asset — no privileged role required.

### Impact Explanation
When a fee-on-transfer ERC20 is withdrawn, `TransfersCheckingAccount` receives `amount - fee` real tokens, but the XCM executor's holding register — and any XCM message built from it (e.g. crediting a remote chain via reserve-transfer semantics, or the local `deposit_asset` path) — is backed by the full nominal `amount`. This creates a persistent shortfall between the checking account's real ERC20 balance and the cumulative amount the protocol believes it is holding/has promised elsewhere. Repeated use drains the real backing faster than the nominal accounting reflects, eventually causing genuine depositors/beneficiaries to be unable to redeem their full credited amount (deposit calls will revert/underpay once the checking account's true balance is depleted) — an integrity break in the escrow/backing invariant, not merely a UX inconvenience. This is consistent with Medium severity in the referenced report's class (protocol requests/credits incorrect amounts for fee-on-transfer tokens), scoped to a specific, non-privileged asset-transactor code path added specifically to support arbitrary ERC20s.

### Likelihood Explanation
Likelihood is Medium: the attacker/user needs only to (1) deploy a fee-on-transfer ERC20 contract via `pallet-revive` (no permission required) and (2) submit an XCM program (`PolkadotXcm::execute` or a reserve-transfer) referencing that contract as the transacted asset. The matcher (`assets_common::ERC20Matcher`) appears to accept any `AccountKey20` contract address rather than a curated allow-list, and the transactor is live in the `AssetTransactors` tuple used by `XcmConfig` on Asset Hub Westend. This does require the ERC20 asset itself to be attacker-created/attacker-chosen (since native, first-party FRAME assets cannot behave this way), so it primarily affects the ERC20-token subsystem rather than protocol-native/system assets like DOT/WND.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `balanceOf` of the recipient (checking account / beneficiary) before and after the `bare_call` to `transfer`, and use the observed balance delta — not the requested `amount` — to construct `Erc20Credit`/determine success amount for `AssetsInHolding`. Alternatively/additionally, restrict `ERC20Matcher` to an explicitly governance-approved allow-list of ERC20 contracts known not to charge transfer fees, and add integration tests exercising a deliberately fee-on-transfer mock ERC20 to assert the executor's holding amount matches the real balance delta.

### Proof of Concept
Not executed against a live network; based on static code inspection only. A minimal reproduction (to be run as a `pallet-revive`/XCM integration test similar to existing `asset-hub-westend/tests/tests.rs::smart_contract_not_erc20_will_error`/`smart_contract_does_not_return_bool_fails`) would:
1. Deploy a mock ERC20 contract whose `transfer(to, value)` moves `value - fee` to `to` but still returns `true` (fee retained/burned in the contract).
2. Fund `sender` with tokens and WND for fees; submit `PolkadotXcm::execute` with `withdraw_asset(AccountKey20{contract}, amount)` followed by `deposit_asset(AllCounted(1), beneficiary)`.
3. Assert: `checking_account`'s real ERC20 balance after withdraw is `amount - fee` (via `balanceOf`), while the executor credited/attempted to move the full `amount` in `AssetsInHolding`/on deposit — demonstrating the accounting mismatch. Failed guards: neither `withdraw_asset_with_surplus` nor `deposit_asset_with_surplus` calls `balanceOf` to verify the actual amount transferred; only the boolean return value is checked. This PoC was not executed in this session — no test run or network execution was performed; the analysis is based solely on reading the cited source.

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

	fn deposit_asset_with_surplus(
		what: AssetsInHolding,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<Weight, (AssetsInHolding, XcmError)> {
		tracing::trace!(
			target: "xcm::transactor::erc20::deposit",
			?what, ?who,
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());
		let (asset_contract_id, amount) = match maybe {
			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};
		let who = match AccountIdConverter::convert_location(who) {
			Some(inner) => inner,
			None => return Err((what, MatchError::AccountIdConversionFailed.into())),
		};
		// We need to map the 32 byte beneficiary account to a 20 byte account.
		let eth_address = T::AddressMapper::to_address(&who);
		let address = Address::from(Into::<[u8; 20]>::into(eth_address));
		// To deposit, we actually transfer from the checking account to the beneficiary.
		// We do this using the solidity ERC20 interface.
		let data = IERC20::transferCall { to: address, value: EU256::from(amount) }.abi_encode();
		let weight_limit = WeightLimit::get();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(TransfersCheckingAccount::get()),
				asset_contract_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::deposit", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::deposit", ?return_value, "Return value");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::deposit", "Contract reverted");
				Err((what, XcmError::FailedToTransactAsset("ERC20 contract reverted")))
			} else {
				match IERC20::transferCall::abi_decode_returns_validate(&return_value.data) {
					Ok(true) => {
						tracing::trace!(target: "xcm::transactor::erc20::deposit", "ERC20 contract was successful");
						Ok(surplus)
					},
					Ok(false) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", "contract transfer failed");
						Err((
							what,
							XcmError::FailedToTransactAsset("ERC20 contract transfer failed"),
						))
					},
					Err(error) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", ?error, "ERC20 contract result couldn't decode");
						Err((
							what,
							XcmError::FailedToTransactAsset(
								"ERC20 contract result couldn't decode",
							),
						))
					},
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::deposit", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err((what, XcmError::FailedToTransactAsset("ERC20 contract execution errored")))
		}
	}

/// Transactor for ERC20 tokens.
pub type ERC20Transactor = assets_common::ERC20Transactor<
	// We need this for accessing pallet-revive.
	Runtime,
	// The matcher for smart contracts.
	assets_common::ERC20Matcher,
	// How to convert from a location to an account id.
	LocationToAccountId,
	// The maximum gas that can be used by a standard ERC20 transfer.
	ERC20TransferGasLimit,
	// The maximum storage deposit that can be used by a standard ERC20 transfer.
	ERC20TransferStorageDepositLimit,
	// We're generic over this so we can't escape specifying it.
	AccountId,
	// Checking account for ERC20 transfers.
	ERC20TransfersCheckingAccount,
>;

/// Means for transacting assets on this chain.
pub type AssetTransactors = (
	FungibleTransactor,
	FungiblesTransactor,
	ForeignFungiblesTransactor,

);
