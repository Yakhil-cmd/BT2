### Title
Cross-Organization Webhook Confusion Allows Forged Commit Statuses And Sync Triggers On Any Stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/secret to authenticate a webhook against using `repository.owner.login` (or `organization.login`) pulled from the still-unverified request body, but the event handlers that actually mutate state (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, via `Handler#repository_name`) key off a *different* field of that same unverified body: `repository.full_name`. Nothing forces these two fields to refer to the same organization/repository.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret with: [1](#0-0) [2](#0-1) 

`repository_owner` comes from `params.dig('repository', 'owner', 'login')`, computed before the signature has been checked. Signature verification itself is HMAC over the raw body using the secret configured for *that* organization: [3](#0-2) 

Critically, `return true unless webhook_secret` — if the organization resolved from `repository.owner.login` has no `webhook_secret` configured (documented as optional per `docs/setup.md`), verification is a no-op and *any* attacker-supplied body is accepted: [4](#0-3) [5](#0-4) 

Once accepted, the raw JSON is handed unmodified to handlers: [6](#0-5) 

But `Handler#stacks` resolves the target `Repository`/`Stack` using a **different** field, `repository.full_name`, not `repository.owner.login`: [7](#0-6) 

`PushHandler`, `CheckSuiteHandler` and `StatusHandler` all rely on this `stacks`/`repository_name` binding, or (for status events) `Commit.where(sha: params.sha)` with no repository/organization scoping at all: [8](#0-7) [9](#0-8) [10](#0-9) 

This is structurally the same class of bug as the Behodler report: the code authenticates/authorizes based on one piece of state (`pendingFlashDecision[target][sender]` keyed identity in Behodler; here, the organization identified via `repository.owner.login`/`organization.login` and its secret), then acts on a different, unchecked field of the same request (`amount`/`asset` overwritten in Behodler; here, `repository.full_name` and bare `sha`, unbound to the verified organization) — breaking the equality `organization authenticated == repository/commit written`.

### Impact Explanation
Any organization configured on this Shipit instance whose `webhook_secret` is blank (the documented default/optional state) becomes a skeleton key for the entire installation: an attacker who can reach `/webhooks` (an unauthenticated public endpoint, per `config/routes.rb`) can post a crafted `push`, `check_suite`, or `status` event where `repository.owner.login` names the secret-less org (making `verify_signature` pass unconditionally) while `repository.full_name` (or, for `status`, a bare `sha`) targets a completely unrelated victim stack/commit belonging to a different, properly-secured organization. This allows:
- Forcing `GithubSyncJob`/re-sync on arbitrary stacks (`PushHandler`/`CheckSuiteHandler`).
- Injecting fabricated commit statuses (`state: "success"`) for any commit sha present in the datastore via `StatusHandler`, which can satisfy `ci.require` gating and enable an **unauthorized deploy** on a stack the attacker has no legitimate access to.

This crosses the "organization authenticated vs. repository that is written" boundary called out in the rules and lands in the Critical bucket ("unauthorized deploy") when combined with the CI-status-gated deploy path.

### Likelihood Explanation
Requires only that at least one configured GitHub organization on the Shipit instance has no `webhook_secret` set — explicitly supported/documented as optional (`docs/setup.md`, `config/secrets.development.example.yml`). No GitHub credentials, session, or `ApiClient` token are needed; `/webhooks` is a public unauthenticated POST endpoint. The only precondition (a secret-less org existing in a multi-org config) is operator-configuration-dependent, which lowers likelihood somewhat versus a universal bypass, but is a legitimately supported and undocumented-as-risky configuration.

### Recommendation
- Require `webhook_secret` for every configured organization; refuse to boot (or refuse all webhooks for that org) if it's blank rather than silently trusting unsigned payloads.
- After signature verification succeeds, re-derive and cross-check that `repository.owner.login`/`organization.login` (the field used to select the verifying secret) matches the owner implied by `repository.full_name` used by the handler, rejecting mismatches.
- In `StatusHandler`, scope the `Commit` lookup by the repository resolved from the verified organization, not just by `sha` globally.

### Proof of Concept
1. Configure Shipit with two orgs: `secure-org` (has `webhook_secret`) and `open-org` (no `webhook_secret`, per supported optional config).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "open-org" }, "full_name": "open-org/decoy" },
  "sha": "<sha of a commit belonging to secure-org's stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
No valid `X-Hub-Signature` is needed since `open-org` has no secret, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`).
3. `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event('status')`, invoking `StatusHandler`, which runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — with no scoping to `open-org`, this writes a fabricated "success" status onto `secure-org`'s commit.
4. If that status satisfies `ci.require` for `secure-org`'s stack, a deploy can now be triggered on `secure-org`'s stack that would otherwise have been blocked by real CI.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
