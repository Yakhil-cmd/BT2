Based on my research, I found a concrete accounting-mismatch issue in the block-revenue-sharing reward path that is analogous to the Illuminate bug class (a pool value used to compute a per-account share is never actually debited from its source, so bookkeeping and reality diverge).

### Title
Block-revenue delegator rewards (`block_reward`) are credited to stake accounts without any corresponding debit from the vote account's `pending_delegator_rewards`/lamports, causing capitalization to diverge from actual lamports minted - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
The SIMD-0123/block-revenue-sharing reward path computes a delegator's `block_reward` as a proportional share of the vote account's `pending_delegator_rewards` field [1](#0-0) , then during partitioned distribution adds that `block_reward` directly to the stake account's lamports [2](#0-1) . However, the distribution pipeline (`store_stake_accounts_in_partition` / `build_updated_stake_reward`) only loads, mutates, and stores **stake accounts**, never the originating **vote account** [3](#0-2) , and `pending_delegator_rewards` is only ever incremented (via `DepositDelegatorRewards`/`add_pending_delegator_rewards`) [4](#0-3)  — I could not find any code path that decrements it or debits the vote account's lamports when a `block_reward` is actually paid out to a stake account.

### Finding Description
This mirrors the Illuminate report's core defect: a value is computed as "this account's share of a pool," but the pool itself is never reduced/settled when that share is paid out, so the recorded state (pool balance) and the real economic state (lamports actually available/owed) diverge over time. Concretely:

- `calculate_block_reward` treats `vote_state.pending_delegator_rewards()` as the total pot to be shared among delegators for the rewarded epoch [5](#0-4) .
- `build_updated_stake_reward` mints that `block_reward` straight into the stake account via `checked_add_lamports` [2](#0-1) .
- `distribute_epoch_rewards_in_partition` only adjusts `capitalization` for `stake_reward_lamports_minted` (inflation) and subtracts `block_reward_lamports_burned` (failure case); it never adds `block_reward_lamports_distributed` to capitalization, implying the lamports are assumed to already exist (in the vote account) and simply move [6](#0-5) .
- Yet `store_stake_accounts_in_partition` calls `self.store_accounts` only with `updated_stake_rewards`, i.e., stake accounts — the vote account is never re-stored with a reduced lamport balance or a reduced `pending_delegator_rewards` field [7](#0-6) .

If this debit genuinely does not happen anywhere in the pipeline, every partitioned distribution of `block_reward` mints lamports into stake accounts without removing the equivalent amount from the vote account or from `pending_delegator_rewards`, and without capitalization being credited to match. This breaks the fundamental invariant that total lamports equal `capitalization`, and it also means `pending_delegator_rewards` remains inflated indefinitely, so the *next* epoch's `calculate_block_reward` would use the same undiminished pool as numerator, effectively allowing the same deposited revenue to be distributed to delegators repeatedly (misattributed/duplicated rewards), directly matching the "concrete theft or minting of lamports" and "misattributed or duplicated rewards" acceptance criteria.

### Impact Explanation
If confirmed, this is a capitalization/lamport-conservation violation in a core reward-distribution path (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs`), reached automatically once per epoch whenever `block_revenue_sharing` is active and a vote account has non-zero `pending_delegator_rewards`. It would cause silent, deterministic minting of lamports into stake accounts (or repeated payout of the same pending reward pool across epochs) with no attacker action required beyond having deposited into `pending_delegator_rewards` via the normal `DepositDelegatorRewards` instruction, satisfying the "unprivileged-user analog in reward distribution paths" requirement.

### Likelihood Explanation
This triggers on every partitioned-reward distribution block for any vote account with `block_revenue_sharing` active and `pending_delegator_rewards > 0` — no adversarial input is needed beyond a normal delegator/validator using `DepositDelegatorRewards`, so the likelihood of the code path executing is high. However, I want to flag significant uncertainty: due to the size/scope limits of the code index available to me, I was not able to fully trace every function in the reward-commission/`update_reward_commissions`/vote-account-store pipeline, so it's possible the vote account's lamports or `pending_delegator_rewards` are decremented in a code path I did not locate (e.g., inside `distribute_reward_commissions` or a related helper not surfaced by my searches). I could not find such a decrement despite targeted searches for `pending_delegator_rewards -`/`checked_sub`/reset-to-zero patterns.

### Recommendation
Because I could not conclusively rule out that the debit occurs elsewhere in the codebase, this should be verified directly against the full source (not just the indexed excerpts) before treating it as confirmed. If verification in a full checkout confirms no debit exists: (1) subtract the total `block_reward` paid out in each partition from the corresponding vote account's `pending_delegator_rewards` field and lamport balance in `build_updated_stake_reward`/`store_stake_accounts_in_partition`, storing the updated vote accounts alongside the stake accounts, and (2) add an invariant/assertion (mirroring the existing `assert!` in `distribute_reward_commissions` that total payouts do not exceed `point_value.rewards`) ensuring cumulative `block_reward` payouts across all partitions never exceed the vote account's `pending_delegator_rewards` snapshotted at calculation time.

### Proof of Concept
Not independently reproduced in a live environment; this is a static-analysis finding based on tracing the reward-calculation and reward-distribution code paths cited above. A concrete PoC would require building/running the validator with `block_revenue_sharing` active, calling `DepositDelegatorRewards` on a vote account, allowing an epoch's block-reward distribution to complete, and then asserting: (a) the vote account's lamport balance is unchanged/not reduced by the distributed `block_reward` total, and (b) `pending_delegator_rewards` is unchanged after distribution — which, if true, would prove that the same pool is reusable in the next epoch's calculation, and/or that lamports were created without a capitalization increase. I recommend a Devin session with full source and test-execution access to confirm or refute this before treating it as a settled finding.
