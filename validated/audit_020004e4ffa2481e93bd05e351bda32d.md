This confirms the multi-organization GitHub App configuration model in `lib/shipit.rb`, where `Shipit.github(organization:)` selects a distinct `webhook_secret` per organization key in `secrets.github` (`app/controllers/shipit/webhooks_controller.rb:25`, `lib/shipit.rb:170-200`). ### Title
Webhook signature verification is scoped to `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` field, allowing cross-organization stack takeover - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports multi-organization GitHub App configuration, where each organization key under `secrets.github` has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to use for HMAC verification based solely on `repository.owner.login` (or `organization.login`) taken from the untrusted JSON payload [2](#0-1) . Once verification passes, the actual event handlers (e.g. `PushHandler`, pull-request handlers) resolve the target `Repository`/`Stack` using a completely different payload field, `repository.full_name` [3](#0-2) [4](#0-3) .

### Finding Description
The equality that should hold is: `organization whose secret authenticated the request == organization owning the repository the handler writes to`. Because both `repository.owner.login` (used to pick the verification secret) and `repository.full_name` (used to pick the acted-upon `Stack`) are attacker-controlled fields inside the same JSON body, an attacker who legitimately controls one organization/repository with a Shipit GitHub App installation (their own `webhook_secret`) can craft a payload where:
- `repository.owner.login` = attacker's own org (so `Shipit.github(organization: repository_owner)` resolves to the attacker's own webhook secret, and the HMAC computed with that secret over the full raw body validates successfully), while
- `repository.full_name` = `victim-org/victim-repo` (an arbitrary repository already known to the Shipit instance).

`verify_signature` never checks that the resolved organization matches `repository.full_name`'s owner; it only fails closed if the organization key is entirely unknown to `secrets.github` [5](#0-4) . Handlers such as `PushHandler` then look up stacks purely via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` [3](#0-2)  and trigger `stack.sync_github(expected_head_sha: params.after)` [6](#0-5) , with no cross-check against the organization that authenticated the request.

### Impact Explanation
This breaks the binding "organization that authenticated versus the repository that is written." An attacker with a self-controlled, legitimately Shipit-configured GitHub organization can forge webhook events (push, pull_request opened/labeled/unlabeled/edited, etc.) that are validly signed under their own secret but target any other repository/stack tracked by the same Shipit instance. Depending on which handler is abused, this can force `GithubSyncJob` runs against a victim stack's branch/HEAD (`app/models/shipit/webhooks/handlers/push_handler.rb`), or manipulate review-stack provisioning/archival for a victim's pull requests (`opened_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `edited_handler.rb`), effectively achieving unauthorized cross-repository interference in deploy state without ever compromising the victim's own webhook secret.

### Likelihood Explanation
Exploitability only requires the attacker to be a legitimate Shipit user/org owner able to configure or trigger a webhook for their own repository (a normal, unprivileged capability in any multi-tenant Shipit deployment using the multi-organization GitHub App schema), then send a crafted HTTP POST to `/github/webhooks` with a payload whose `repository.owner.login` and `repository.full_name` refer to different repositories. No GitHub App private key, no victim's webhook secret, and no Shipit session are required.

### Recommendation
After signature verification, re-derive the organization from `repository.full_name` (or `organization.login` for org-level events) and require it to match the organization whose secret validated the signature; reject the request otherwise. Alternatively, embed/track the expected organization on the `Repository` record and assert equality before any handler processes the payload.

### Proof of Concept
1. Attacker owns `attacker-org/attacker-repo` with a Shipit GitHub App installed, giving them their own `webhook_secret` entry under `secrets.github[:attacker-org]`.
2. Attacker computes `sha1=HMAC(attacker_webhook_secret, body)` over a crafted push payload where:
   - `repository.owner.login` = `"attacker-org"`
   - `repository.full_name` = `"victim-org/victim-repo"` (a real Shipit-tracked stack)
   - `ref` = `"refs/heads/main"`, `after` = attacker-chosen SHA
3. POST this to `WebhooksController#create` with header `X-Hub-Signature: sha1=<computed>` and `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, retrieves the attacker's own secret, and successfully verifies the signature against the full raw body (since the attacker knows their own secret) [7](#0-6) .
5. `PushHandler#process` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `stack.sync_github(expected_head_sha: params.after)` against the victim's stack [6](#0-5) , even though the request was never signed by victim-org's secret.
