### Title
Shared-Address Approval Accepts Unverified Attacker-Supplied Address, Bypassing Cosigner Quorum Requirement - ([File: wallet_defined_by_addresses.js])

### Summary
`wallet_defined_by_addresses.js`'s `approvePendingSharedAddress()` — invoked from the `"approve_new_shared_address"` device-message handler in `wallet.js` — records the `address` value supplied by a remote (paired) device as the definitive address for that device's branch of a shared (multi-cosigner) address, without ever re-deriving or verifying that this address is the one actually mandated by the device's portion of the address-definition template. This mirrors the reported bug class: an internal/trusted value (here, the branch address that should only be accepted after real quorum/derivation) is taken verbatim from attacker-controlled message content and used to finalize an authorization structure.

### Finding Description
The device-message handler for subject `"approve_new_shared_address"` only performs superficial format checks before delegating to `approvePendingSharedAddress`: [1](#0-0) 

`approvePendingSharedAddress` then stores the caller-supplied `address` and `device_addresses_by_relative_signing_paths` directly, and once every expected signing-path row has an `address`, it substitutes these values into the address-definition template and hashes the result to derive the final `shared_address`: [2](#0-1) 

No step re-derives the claimed `address` from cryptographic material (pubkeys/definition) that the definition template expects for that device's relative signing path; the only validation performed upstream is that the string is a syntactically valid Obyte address: [3](#0-2) 

Because the final combined definition (`Definition.replaceInTemplate`) is built by literally splicing in whatever address string a cosigner device reports, and this combined definition — not the sub-definitions of each participant — is what future spends must satisfy, a malicious/compromised paired device that is supposed to be *one branch* of an intended multi-key sub-condition (e.g., its own address should itself be a further "and"/"r of set" over multiple keys/devices for extra security) can instead report an address it fully and solely controls. All other legitimate cosigners will accept this claim, finalize `shared_address`, and treat the combined structure as authoritative for future spending.

### Impact Explanation
The vulnerability lets a single paired device that is expected to represent one node of a stronger m-of-n sub-condition instead substitute an address entirely under its own control, without cooperation from the other intended co-controllers of that branch. Payments later made to the resulting `shared_address` can then be spent using authorization weaker than what all honest participants believe was configured (unauthorized spending / loss of expected quorum protection). This satisfies the "concrete unauthorized spending" impact bar since a device that is supposed to require assistance to spend from a given branch can unilaterally do so.

### Likelihood Explanation
The `"approve_new_shared_address"` message handler is reachable directly from any device that has been paired as a correspondent (`bIndirectCorrespondent`/correspondent check happens earlier in `device.js`, but a paired attacker device with a legitimate pairing relationship qualifies as an in-scope "paired device" actor per the rules). An attacker does not need the (marked "unused" in this codebase) UI helper `sendApprovalOfNewSharedAddress` — they can craft and send the raw device message themselves once paired and invited to co-create a shared address. The likelihood depends on the shared-address workflow (multi-level nested cosigning) still being exercised in deployments; the sender-side UI helpers being annotated "unused" in this snapshot suggests this feature may see reduced usage, which is noted as an area of uncertainty, but the receiving handler itself remains fully wired and unguarded against this class of input.

### Recommendation
When processing `"approve_new_shared_address"`, the receiving device should not trust the reported `address` as-is. Instead, it should recompute the expected address for that device's node of the template using the actual sub-definition/pubkeys agreed upon for that relative signing path (i.e., perform the same address-derivation check that `addNewAddress` performs for wallet addresses — reject if the reported address does not match what is independently derivable/verifiable from the definition template and previously exchanged public keys). Only accept the approval if the derived address matches, closing the gap that lets an untrusted control value (the branch address) be smuggled in and bypass the intended cosigning quorum.

### Proof of Concept
1. Attacker device A is invited (via `createNewSharedAddressByTemplate`) to be one signing branch of a shared address, where its relative signing path in the template is itself supposed to resolve to a 2-of-2 sub-multisig requiring cooperation with a second device B.
2. Instead of deriving the real sub-multisig address together with device B, attacker device A immediately sends a device message:
   ```
   {
     subject: "approve_new_shared_address",
     body: {
       address_definition_template_chash: "<chash>",
       address: "<address A alone controls, e.g. simple sig address>",
       device_addresses_by_relative_signing_paths: { "r": "<A's device address>" }
     }
   }
   ```
3. `wallet.js` performs only format checks [3](#0-2)  and calls `approvePendingSharedAddress`, which stores this address as A's fully-approved branch [4](#0-3) .
4. Once all other legitimate signing paths are filled in normally, the shared address is finalized using A's single-key address for that branch [5](#0-4) , letting A spend from that branch alone, defeating the intended 2-of-2 requirement other participants believed was enforced.
