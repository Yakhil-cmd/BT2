### Title
Attacker-Controlled `.git` Path in Synced Commit Corrupts Worktree Linkage, Causing Persistent Sync Denial - ([File: main.go])

### Summary
The external report describes a case where `init_ONft` accepts an unvalidated `token_mint` property (freeze authority) that is never checked, so a later, unavoidable operation (transferring into `token_escrow`) permanently fails and bricks the program. The analogous weakness in `git-sync` is that `configureWorktree` writes a plaintext `.git` gitlink file into the worktree directory and then immediately runs `git reset --hard <hash>` in that same directory, checking out whatever the attacker-pushed commit contains — including, if the remote repo tracks a path literally named `.git` at its root, overwriting the very gitlink file that ties the worktree to its administrative git directory. There is no validation that rejects a commit containing such a path before it is checked out.

### Finding Description
`configureWorktree` first creates the worktree's link to its real git metadata: [1](#0-0) 

It then performs a hard checkout of the untrusted, attacker/upstream-controlled commit in that very directory: [2](#0-1) 

and, in the default configuration, immediately invokes `git submodule update --init --recursive` in the same directory: [3](#0-2) 

No check exists anywhere in `configureWorktree`, `createWorktree`, or the sparse-checkout handling to reject or special-case a tracked path named `.git` before checkout — analogous to the missing `freeze_authority` check in `init_ONft`. Because `git reset --hard` will overwrite any working-tree file that the target commit tracks, a repository whose HEAD (or any ref/branch/tag git-sync is told to sync) contains a regular file at the top level named `.git` will have that file checked out over the top of the `gitdir: ...` pointer file that `configureWorktree` just wrote. This corrupts the association between the worktree directory and its real git object store for every subsequent git invocation against that worktree path (e.g., the `submodule update` call immediately following, or the periodic `sanityCheckWorktree`/`fsck` calls).

`sanityCheckWorktree` is designed to detect and recover from a corrupted worktree by removing it and re-creating it on the next cycle: [4](#0-3) 

However, this recovery path only triggers when `currentHash == remoteHash` (i.e., no new upstream change) — see the branching logic in `SyncRepo`: [5](#0-4) 

When the malicious commit itself is the *new* remote hash being synced (the normal update path, `changed == true`), `createWorktree`/`configureWorktree` run fresh every cycle and re-corrupt the `.git` gitlink file on every attempt, because the poisoned content is baked into the commit being synced. With the default `--submodules=recursive`, the `submodule update --init --recursive` call fails immediately after the corrupting checkout (since git commands in that directory can no longer resolve `.git`), so `SyncRepo` returns an error before `publishSymlink` is ever called: [6](#0-5) 

This repeats every `--period` cycle: `createWorktree` → `configureWorktree` (checkout corrupts `.git`) → submodule step fails → error surfaces to the outer loop, worktree is torn down and rebuilt from scratch next cycle, and the cycle repeats indefinitely. Consumers reading via the published symlink remain permanently pinned to the last good commit and never converge to the (legitimately reachable, attacker-authored) new revision, while git-sync burns CPU/network resources in an endless failure loop unless `--max-failures` is a small non-negative value, in which case the process exits (also a denial of the update contract).

### Impact Explanation
This matches the report's required impact class of "persistent sync denial." An attacker who controls a branch/tag/commit that git-sync is configured to follow (e.g., a compromised or malicious upstream contributor, or any writer to the tracked ref) can craft a single commit containing a tracked file named `.git` to permanently prevent git-sync from ever completing an update to that commit or any descendant of it, without any privileged access to the git-sync host itself. Because the failure recurs identically every sync attempt, this is not a transient blip but a durable, repeatable denial of the git-sync "publication contract" (`README.md`'s description of atomic updates via the worktree+symlink pattern) for the affected ref, directly analogous to the frozen-escrow DoS in the original report.

### Likelihood Explanation
The precondition is that an untrusted party can get a commit merged/pushed to the ref that git-sync follows — the same threat model implied by the prompt ("attacker-pushed commit, ref, or an HTTP request to git-sync") and consistent with git-sync's stated design of syncing "as the remote repository changes." No special git-sync flags are required beyond the defaults (`--submodules=recursive`, which is the default value). No credentials, node compromise, or mocked environment is needed — only the ability to commit a file named `.git` to the synced repository, which is standard, unprivileged repository-content control.

### Recommendation
1. Before or during checkout, validate that the target commit's tree does not contain a top-level entry literally named `.git` (or more generally, reject/rename any tracked path that would collide with git-sync's own worktree administrative files) and fail the sync cleanly with a clear error rather than silently corrupting the gitlink file.
2. Consider writing the worktree's `.git` gitlink file with a mechanism that cannot be overwritten by `git checkout`/`reset --hard` of tracked content (e.g., verify/restore the gitlink file's integrity immediately after every checkout step, before running `submodule update`, and abort/retry safely if it has been tampered with).
3. Extend `sanityCheckWorktree`-style validation to run immediately after `configureWorktree`'s checkout step (not just when hashes match) so a corrupted worktree is detected and handled explicitly (e.g., surfaced as a distinct, actionable error) rather than looping silently.
4. Add an e2e regression test analogous to `e2e::worktree_cleanup`/`e2e::sync_recover_wrong_worktree_hash` that commits a tracked `.git` file and asserts git-sync either rejects the sync with a clear error or successfully isolates/quarantines the offending path instead of entering a failure loop.

### Proof of Concept
```bash
# Attacker (or any writer with push access to the tracked ref) does:
git init /tmp/attacker-repo
cd /tmp/attacker-repo
echo "hello" > file
git add file
git commit -m "init"

# Malicious commit: track a regular file literally named .git
echo "poison" > .git-payload
mv .git-payload .git      # NOTE: must add as a tracked blob named ".git"
git add -f .git
git commit -m "poison the worktree gitlink"

# Victim runs git-sync against this repo
git-sync --repo=file:///tmp/attacker-repo --root=/tmp/gs-root --link=link --period=2s
```
Expected/observed behavior based on code review: `createWorktree` creates `/tmp/gs-root/.worktrees/<hash>`; `configureWorktree` writes the `gitdir: ...` pointer at `.git` in that worktree directory, then `git reset --hard <hash> --` checks out the attacker's tracked `.git` file over the pointer, and the subsequent `git submodule update --init --recursive` call (or any later git invocation against that worktree) fails because the directory is no longer recognized as a valid git worktree. `SyncRepo` returns an error every cycle for this commit; the symlink never advances to the poisoned commit's hash, and the failure recurs on every `--period` tick until `--max-failures` is exhausted (default retries forever unless set) — confirming persistent sync denial for the affected ref, with no privileged access or leaked credentials required by the attacker.

Note: I was unable to execute this PoC directly (no filesystem/terminal access in this mode) — the trace above is derived from static analysis of `main.go`'s `configureWorktree`/`SyncRepo`/`sanityCheckWorktree` control flow. A Devin session with terminal access would be needed to empirically confirm the exact failure message and loop behavior across `--submodules=off` vs `--submodules=recursive`.

// sanityCheckWorktree tries to make sure that the dir is a valid git
// repository.  Note that this does not guarantee that the worktree has all the
// files checked out - git could have died halfway through and the repo will
// still pass this check.
func (git *repoSync) sanityCheckWorktree(ctx context.Context, worktree worktree) bool {
	git.log.V(3).Info("sanity-checking worktree", "repo", git.root, "worktree", worktree)

	// If it is empty, we are done.
	if empty, err := dirIsEmpty(worktree.Path()); err != nil {
		git.log.Error(err, "can't list worktree directory", "path", worktree.Path())
		return false
	} else if empty {
		git.log.V(0).Info("worktree is empty", "path", worktree.Path())
		return false
	}

	// Make sure it is synced to the right commmit.
	stdout, _, err := git.Run(ctx, worktree.Path(), "rev-parse", "HEAD")
	if err != nil {
		git.log.Error(err, "can't get worktree HEAD", "path", worktree.Path())
		return false
	}
	if stdout != worktree.Hash() {
		git.log.V(0).Info("worktree HEAD does not match worktree", "path", worktree.Path(), "head", stdout)
		return false
	}

	// Consistency-check the worktree.  Don't use --verbose because it can be
	// REALLY verbose.
	if _, _, err := git.Run(ctx, worktree.Path(), "fsck", "--no-progress", "--connectivity-only"); err != nil {
		git.log.Error(err, "worktree fsck failed", "path", worktree.Path())
		return false
	}

	return true
}
