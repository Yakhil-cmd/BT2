### Title
Symlink-following in `load_rules()`/`load_rule_file()` breaks `.claude/` workspace confinement, enabling out-of-repo file disclosure via hook `systemMessage` - ([File: plugins/hookify/core/config_loader.py])

### Summary
`load_rules()` uses `glob.glob('.claude/hookify.*.local.md')` and then calls `open(file_path)` in `load_rule_file()` without ever checking whether `file_path` (after symlink resolution) actually resides inside the repository's `.claude/` directory. A repository can ship a symlink at `.claude/hookify.<name>.local.md` pointing to any file readable by the victim's user; when Claude Code invokes any hookify hook, the symlink target is opened and parsed, and if its content happens to look like YAML frontmatter, the resulting `message` field is surfaced to the user via the hook's `systemMessage` output.

### Finding Description
`load_rules()` builds the glob pattern with `os.path.join('.claude', 'hookify.*.local.md')` and calls `glob.glob(pattern)` [1](#0-0) . The returned paths are passed straight to `load_rule_file()`, which does `open(file_path, 'r')` with no `os.path.realpath()`/containment check against the `.claude` directory [2](#0-1) . Neither `glob.glob` nor `open()` refuse to traverse symlinks, so if the attacker's repository contains a symlink such as `.claude/hookify.leak.local.md -> /home/victim/.some-secret.yaml`, the glob match still succeeds (the filename itself matches the pattern) and `open()` transparently follows the symlink to read the external target.

The file content is fed to `extract_frontmatter()`, and if it starts with `---` and contains at least two `---` delimiters, the text between the second `---` and EOF becomes `Rule.message` [3](#0-2) . This `Rule` is then evaluated by `RuleEngine.evaluate_rules()` in the PreToolUse/PostToolUse/Stop/UserPromptSubmit hooks, and the loaded rules (including their `message`) flow into the JSON `result` that is printed to stdout as the hook's `systemMessage` [4](#0-3) .

No existing check enforces that the resolved (post-symlink) path stays under `.claude/`; the only validation performed is on YAML shape (`if not frontmatter: return None`), not on file location. This is a genuine confinement bypass in the `.claude/` rule loader.

Note: the "crafted filename with path-traversal segments" variant of the question is not viable — POSIX filenames cannot literally contain `/`, and glob's `*` wildcard does not match `/` by default, so a filename like `hookify.../../../etc/passwd.local.md` cannot exist as a single path component and would not match the pattern nor escape `.claude/` by naming alone. The exploitable primitive is specifically the symlink case.

### Impact Explanation
An attacker who gets a victim to open/run Claude Code hooks against a cloned repository containing a malicious symlink under `.claude/` can cause the hookify hook to open and read a file entirely outside the intended `.claude/` rules directory (workspace confinement bypass — the target impact class explicitly named in the question). Full content disclosure into `systemMessage` is constrained to cases where the targeted file's content happens to parse as YAML frontmatter (starts with `---`, has a second `---` delimiter); when it doesn't, the load silently fails with only an error message printed to stderr (not to `systemMessage`), so message-content leakage is narrower than "any file," but the out-of-directory read (an unauthorized file access via a git-tracked repository artifact) itself constitutes the workspace-escape/trust-boundary violation.

### Likelihood Explanation
- Precondition: attacker needs the victim to clone/check out a repository containing a committed symlink under `.claude/` (git supports storing symlinks) and to run any hookify-instrumented hook (PreToolUse/PostToolUse/Stop/UserPromptSubmit), which is standard, automatic behavior once the plugin is installed and active for the repo.
- No special privileges or social engineering beyond "victim opens the attacker's repository" are required — this matches the ordinary "repository content is attacker-controlled" trust model in scope.
- Reliable/repeatable: symlink resolution by `open()` is deterministic; the glob match and file read will happen on every hook invocation as long as the symlink and target exist.

### Recommendation
In `load_rules()`/`load_rule_file()`, before opening each matched path:
1. Reject entries where `os.path.islink(file_path)` is true, or
2. Resolve with `os.path.realpath(file_path)` and verify the resolved path's `os.path.commonpath([...])` is still under the absolute, realpath'd `.claude` directory of the current working repo; skip and log a warning otherwise.
Apply the same check consistently to any other file-glob-based loader in the plugin.

### Proof of Concept
Integration test (pytest) for `plugins/hookify/core/config_loader.py`:
```python
import os, tempfile, textwrap
from hookify.core.config_loader import load_rules

def test_symlink_outside_claude_is_not_followed(tmp_path, monkeypatch):
    # Simulate victim's sensitive file OUTSIDE the repo
    secret_dir = tmp_path / "outside"
    secret_dir.mkdir()
    secret_file = secret_dir / "secret.local.md"
    secret_file.write_text(textwrap.dedent("""\
        ---
        name: leaked
        enabled: true
        event: all
        ---
        TOP-SECRET-CONTENT-1234
    """))

    # Repo root with .claude dir containing a symlink pointing outside
    repo = tmp_path / "repo"
    claude_dir = repo / ".claude"
    claude_dir.mkdir(parents=True)
    link_path = claude_dir / "hookify.evil.local.md"
    os.symlink(secret_file, link_path)

    monkeypatch.chdir(repo)
    rules = load_rules()

    # Expected (secure) behavior: symlink should NOT be followed,
    # so no rule with the secret content should be loaded.
    assert not any("TOP-SECRET-CONTENT-1234" in r.message for r in rules), \
        "load_rules() followed a symlink outside .claude/, disclosing external file content"
```
Expected current (vulnerable) result: the assertion fails because `rules` contains a `Rule` whose `message` is `"TOP-SECRET-CONTENT-1234"`, proving the loader read a file outside `.claude/` via a checked-in symlink.
