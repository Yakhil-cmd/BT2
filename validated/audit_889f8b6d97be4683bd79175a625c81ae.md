### Title
Webhook signature verification binds to attacker-controlled `repository.owner.login`, not to the `repository.full_name` used by `LabeledHandler`, allowing cross-tenant stack archive/unarchive - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC against using `params.dig('repository', 'owner', 'login')`, a field taken directly from the attacker-supplied JSON body. `LabeledHandler#repository` independently resolves the target `Shipit::Repository` from `params.repository.full_name`, a *different* field in the same attacker-supplied body. Because nothing ties these two fields together, an attacker who owns org A (and thus legitimately knows org A's webhook secret) can sign a payload where `repository.owner.login = "org-A"` (satisfies signature check) but `repository.full_name = "org-B/protected-repo"` (drives the handler), causing `LabeledHandler#handle` to call `stack.archive!`/`stack.unarchive!` on org B's review stack.

### Finding Description
The claimed binding is: `organization_whose_secret_verified_signature == organization_owning_stack_that_is_mutated`. Tracing the code shows this is **false**:

- `WebhooksController#verify_signature` computes `repository_owner` via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it only to pick which `Shipit::GitHubApp` (and thus which `webhook_secret`) to check the HMAC against: [1](#0-0) [2](#0-1) 
- The raw JSON body (`request.raw_post`) is entirely attacker-controlled and self-consistent-signed: the attacker computes `HMAC-SHA1(org_A_secret, raw_post)` themselves, so any JSON content is valid as long as it's signed with a secret the attacker legitimately possesses (org A's own webhook secret, since they are org A's owner/admin).
- `Shipit::Webhooks::Handlers::PullRequest::LabeledHandler#repository` resolves the actual target repository purely from `params.repository.full_name`, a sibling field in the same body, with no cross-check against `repository.owner.login` or the organization used in `verify_signature`: [3](#0-2) 
- `#handle` then unconditionally calls `stack.archive!` or `stack.unarchive!` on whatever stack that repository resolves to, based on attacker-supplied `pull_request.labels`: [4](#0-3) [5](#0-4) 

**Exploit request**: attacker (org A owner) POSTs to `/webhooks` with header `X-Github-Event: pull_request`, `X-Hub-Signature: sha1=<HMAC using org A secret>`, and a JSON body where:
```json
{
  "action": "labeled",
  "pull_request": { "state": "open", "labels": [{"name": "<org-B-provisioning-label-or-absence>"}], ... },
  "repository": { "full_name": "org-B/protected-repo", "owner": { "login": "org-A" } },
  ...
}
```
`verify_signature` looks up `Shipit.github(organization: "org-A")`, verifies successfully with the attacker's own secret, and proceeds. `LabeledHandler` then resolves `Shipit::Repository.from_github_repo_name("org-B/protected-repo")` — org B's real repository — and, depending on label presence versus org B's configured `provisioning_behavior_allow_with_label?`/`prevent_with_label?`, calls `archive!` or `unarchive!` on org B's review stack.

Existing guards do not stop this: `drop_unhandled_event` and `ExplicitParameters` schema only validate shape, not cross-field consistency; `verify_signature` never re-derives or checks the organization from `repository.full_name`; there is no validation anywhere that `repository.owner.login` matches the owner segment of `repository.full_name`.

### Impact Explanation
An attacker who controls any GitHub organization with a Shipit App installation (i.e., is legitimately an owner/admin of *some* org integrated with this Shipit instance) can forge webhook payloads that mutate the archived/unarchived lifecycle state of **any other organization's** review stacks reachable through the same Shipit instance, without ever possessing that other organization's secret. Unarchiving a stack re-enables it as an active deploy target, which is a state-changing, cross-tenant write triggered purely by a signature belonging to an unrelated party — matching the Critical category "a payload for one repository mutating another's stack." The attack is repeatable against any repository/stack in the multi-tenant Shipit deployment, for every future `labeled`/`unlabeled` webhook the attacker chooses to send.

### Likelihood Explanation
Preconditions: the Shipit instance must be configured for multiple GitHub organizations (`Shipit.github(organization: ...)` multi-app config, as documented in `docs/setup.md`), and the target org B repository must have `review_stacks_enabled` plus `provisioning_behavior_allow_with_label?`/`prevent_with_label?` configured — a supported, documented feature. The attacker only needs to be a legitimate owner/admin of any one participating org (org A) with knowledge of org A's own webhook secret — no privileged access to org B or to Shipit itself is required. Crafting and sending the forged HTTP request is trivial and fully repeatable.

### Recommendation
`WebhooksController#verify_signature` (or the handlers) must ensure the organization used to select/verify the webhook secret is the *same* organization that owns the resource being mutated. Concretely: derive the authorized organization strictly from `repository.full_name`'s owner segment (not a separate `repository.owner.login` field), and/or have each handler (e.g., `LabeledHandler`) re-validate that the resolved `Shipit::Repository`'s organization matches the organization whose secret verified the request before calling `archive!`/`unarchive!`.

### Proof of Concept
Minitest plan (in `test/controllers/webhooks_controller_test.rb` style, illustrative — not to be placed under out-of-scope `test/**` for delivery, but demonstrating the reproduction):
```ruby
test "labeled webhook signed by org A mutates org B's stack" do
  org_b_repo = shipit_repositories(:shipit) # owned by "org-B", review_stacks_enabled, provisioning_behavior_allow_with_label
  stack = org_b_repo.review_stacks.create!(...)
  assert_not stack.archived?

  payload = {
    "action" => "labeled",
    "number" => 1,
    "pull_request" => {
      "id" => 1, "number" => 1, "url" => "...", "title" => "t", "state" => "open",
      "additions" => 1, "deletions" => 1,
      "head" => { "sha" => "a" * 40, "ref" => "branch" },
      "user" => { "login" => "attacker" },
      "assignees" => [],
      "labels" => [{ "name" => org_b_repo.provisioning_label_name }]
    },
    "repository" => { "full_name" => "org-B/protected-repo", "owner" => { "login" => "org-A" } },
    "sender" => { "login" => "attacker" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", org_a_webhook_secret, payload)
  @request.headers["X-Github-Event"] = "pull_request"
  @request.headers["X-Hub-Signature"] = signature

  # left side of binding: org whose secret verified
  assert Shipit.github(organization: "org-A").verify_webhook_signature(signature, payload)
  # right side: org owning the mutated stack
  assert_equal "org-B", org_b_repo.owner

  post :create, body: payload, as: :json
  assert_response :ok

  stack.reload
  assert stack.unarchive_called? # or check archived? flipped, proving org-B's stack changed via org-A's signature
end
```
This asserts both sides of the binding explicitly diverge (`org-A` verified vs. `org-B` mutated) and that the mutation occurs.
