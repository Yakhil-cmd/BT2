### Title
Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits to attach a GitHub `status` webhook to by SHA alone, across the entire `commits` table, instead of scoping the lookup to the repository that the webhook is claimed to originate from. Any genuinely GitHub-signed `status` webhook whose `sha` happens to match a commit that already exists in *any* Shipit-tracked stack will write a `Status` record onto that unrelated commit, regardless of which repository the webhook was actually sent for.

### Finding Description
The broken binding is: `webhook.repository.full_name == commit.stack.repository.full_name` is assumed but never checked; only `webhook.sha == commit.sha` is enforced.

Every other handler scopes its work to the repository named in the payload, e.g. `Handler#stacks` resolves `Repository.from_github_repo_name(repository_name)&.stacks` [1](#0-0) , and `PushHandler`/others iterate over that scoped `stacks` relation. `StatusHandler`, however, does:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit.where(sha: ...)` is a global, unscoped ActiveRecord query — it is not filtered by `stack_id`/repository at all, unlike `Repository.from_github_repo_name` used elsewhere in the same file/module. `sha` has no application-level uniqueness constraint tying it to a single repository/stack; multiple stacks legitimately track independent `Commit` rows that can share the identical 40-character sha, since git commit hashes are content-addressed and identical across forks or shared history [3](#0-2) .

The only gate in front of `StatusHandler` is `WebhooksController#verify_signature`, which validates the HMAC signature against the webhook secret configured for `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the attacker-influenced payload's `repository.owner.login` (or `organization.login`) field [4](#0-3) . This check verifies that the request was authentically signed by the GitHub App installation for *some organization Shipit knows about* — it does **not** verify that the sha in the payload actually belongs to the repository named in that same payload. Once the org-level signature check passes (which it trivially does for any genuine GitHub webhook fired by a repository living under an org Shipit has an app installed on, since one GitHub App/webhook secret covers every repo in that org — and additionally, `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that org [5](#0-4) ), `StatusHandler` blindly matches by sha across all stacks.

Exploit flow: attacker creates/owns any repository R1 whose GitHub App installation is covered by an organization that some Shipit instance already trusts (e.g. a personal scratch repo or an in-org fork under an org that has the Shipit GitHub App installed, or any org with an unset `webhook_secret`). Attacker forks/mirrors the victim's public repository so R1 contains a commit with the exact same sha as a commit already tracked in the victim's Shipit stack (guaranteed identical by git's content addressing). Attacker then triggers a real `status` event for that commit (any CI system posting to GitHub, or a self-hosted GitHub status API call the attacker is authorized to make on their own repo). GitHub delivers a genuinely-signed webhook to Shipit's `/webhooks` endpoint naming R1 as the repository. `verify_signature` passes (real GitHub signature, valid org). `StatusHandler#process` then finds the victim's `Commit` row purely by matching sha and calls `commit.create_status_from_github!(params)` on it — writing an attacker-controlled `state`/`description`/`target_url`/`context` status onto the victim's commit in a completely different stack the attacker never had permission on.

### Impact Explanation
This is a cross-repository write: a payload that authenticated for repository R1 mutates the status/state of a `Commit` belonging to an unrelated, victim-owned `Stack`/`Repository` (R2) that the attacker has no access to. Depending on the victim stack's configured `required_statuses`/CI gating, this can flip a commit from blocked to `deployable?` (`Commit#deployable?` depends on `success?` derived from statuses) [6](#0-5) , potentially unblocking or misrepresenting the readiness of a deploy that a human or automated policy would otherwise gate on CI status — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy". The write is repeatable against any stack in the instance whose tracked commits share a sha with a repository the attacker can trigger genuine webhooks from, and is not limited to a single victim — it is limited only by SHA collisions, which are trivially engineered by forking/mirroring any publicly forkable target repository.

### Likelihood Explanation
Preconditions: (1) the attacker's repository must be covered by a GitHub App/webhook-secret configuration that Shipit already trusts for *some* organization — this is satisfied either when the attacker's repo lives in the same GitHub org as the victim's tracked repo (one GitHub App installation signs all repos in that org) or when that org's `webhook_secret` is left unset (verification is unconditionally bypassed in that case); (2) the attacker must produce a commit with an identical sha to a commit already ingested into some Shipit stack — trivially satisfied by forking/mirroring the victim's public repository, since git hashes are content-addressed and identical on the fork. No guessing of secrets, no privileged Shipit role, and no GitHub credential theft is required once these two conditions hold. The "any internet-wide attacker against any public repo" framing in the question overstates it slightly — a fully external, unrelated attacker still needs their triggering webhook to pass the org-level signature check, so the practical blast radius is bounded to organizations Shipit has configured (multi-repo/monorepo orgs, or misconfigured orgs without a webhook secret), not literally every GitHub org in existence. Within that boundary, however, the attack is cheap, repeatable, and requires no privileged access beyond owning/pushing to any repo in that boundary.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository named in the payload, mirroring `Handler#stacks`, e.g. resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks&.flat_map(&:commits)&.select { |c| c.sha == params.sha }` (or a scoped `Commit.joins(:stack).where(stacks: { repository_id: repo.id }, sha: params.sha)`) instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "does not attach a status cross-repository based on sha alone" do
  attacker_repo = shipit_repositories(:attacker) # full_name: "attacker/r1"
  victim_repo   = shipit_repositories(:shipit)   # full_name: "victim/r2"
  shared_sha    = "a" * 40

  attacker_stack = attacker_repo.stacks.create!(environment: 'production', branch: 'master')
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "attacker commit")

  victim_stack = victim_repo.stacks.first
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "victim commit")

  payload = {
    'sha' => shared_sha, 'state' => 'success', 'context' => 'ci/attacker',
    'repository' => { 'full_name' => attacker_repo.github_repo_name, 'owner' => { 'login' => attacker_repo.owner } }
  }

  assert_no_difference -> { attacker_commit.statuses.count } do
    assert_difference -> { victim_commit.reload.statuses.count }, 0 do
      Shipit::Webhooks::Handlers::StatusHandler.call(payload)
    end
  end
end
```
Assert both sides of the binding: before the fix, `victim_commit.statuses.count` changes (proving the equality `webhook.repository == commit.stack.repository` is violated); after applying the repository-scoped fix, only `attacker_commit.statuses.count` changes and `victim_commit.statuses.count` remains `0`.

    def self.by_sha(sha)
      raise AmbiguousRevision, "Short SHA1 #{sha} is ambiguous (too short)" if sha.to_s.size < 6

      commits = where('sha like ?', "#{sha}%").take(2)
      raise AmbiguousRevision, "Short SHA1 #{sha} is ambiguous (matches multiple commits)" if commits.size > 1

    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
