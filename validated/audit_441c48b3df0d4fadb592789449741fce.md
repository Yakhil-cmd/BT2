### Title
CCMenu API endpoint bypasses stack-scoped `ApiClient` authorization, allowing a token restricted to one stack to read the build state of any other stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The binding that should hold is: **stack a token authorizes == stack the request touches**. `Api::CCMenuController` breaks this equality by resolving the target stack directly from `Stack.from_param!(params[:stack_id])` instead of from the caller's authorized `stacks` scope, so a stack-restricted `ApiClient` can read CI/build status for stacks it was never granted access to.

### Finding Description
`Api::BaseController` implements the scoping contract that every other API controller relies on: [1](#0-0) 

`stacks` restricts the visible set to `current_api_client.stack_id` when the client is scoped to a specific stack, and `stack` resolves `params[:id]` (or `params[:stack_id]` in other controllers) only within that authorized scope, via `stacks.from_param!(...)`.

`Api::CCMenuController`, however, overrides `stack` to bypass this scope entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` — the unscoped model class — instead of the inherited `stacks.from_param!`. The `require_permission :read, :stack` check only verifies that the `read:stack` string is present in the client's `permissions` array: [3](#0-2) 

It never checks whether the requested stack matches `current_api_client.stack_id`. Consequently the permission check and the stack-scoping check are decoupled: any `ApiClient` with `read:stack` permission — including one created with `stack: <specific-stack>` intended to restrict it to a single project — can pass an arbitrary `stack_id` to `Api::CCMenuController#show` and receive that other stack's CI status, last build result, and metadata.

This is the same class of bug as the original report: a check ("does this token's scope include this stack?") that is enforced in one code path (`BaseController#stack`/`#stacks`, used by `StacksController`, `TasksController`, etc.) is silently skipped in a sibling path (`CCMenuController#stack`) that performs an equivalent state-reading operation.

### Impact Explanation
This matches the in-scope High-severity category "unauthenticated/unauthorized read of stack state": an `ApiClient` token that was deliberately scoped to a single stack (a common integration pattern, exemplified by the `here_come_the_walrus` fixture with `stack: shipit`) can be used to enumerate and read the deploy/build status of every other stack in the installation, defeating the tenant-isolation guarantee that stack-scoped tokens are supposed to provide.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` credential with `read:stack` permission (a routine, low-privilege token) can trigger this by simply changing the `stack_id` query parameter on the `ccmenu` endpoint — no additional privilege or interaction is required.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the authorized scope, consistent with the rest of the API controllers:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the direct `Stack.from_param!` call, so the `current_api_client.stack_id` restriction from `BaseController#stacks` is always enforced.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_a` with `permissions: ['read:stack']` (e.g., same shape as fixture `here_come_the_walrus`).
2. Authenticate as that client and call `GET /stacks_url... ccmenu` equivalent: `GET /api_clients...` route resolving to `Api::CCMenuController#show` with `params[:stack_id] = stack_b.to_param`, where `stack_b` is a different, unrelated stack.
3. Observe the response returns `stack_b`'s CI/build XML (`lastBuildStatus`, etc.) even though the client's token is scoped only to `stack_a`, as confirmed by `Api::CCMenuController#stack` calling `Stack.from_param!` unscoped: [4](#0-3)
