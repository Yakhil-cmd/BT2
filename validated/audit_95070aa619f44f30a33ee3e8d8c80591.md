### Title
Cross-organization commit-status forgery due to unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App/organization derived from the payload's `repository.owner.login` (or `organization.login`) field, selecting that organization's `webhook_secret` to validate the HMAC signature. [1](#0-0) [2](#0-1)  However, once the signature check passes, the `status` event handler never re-checks that the acted-upon record actually belongs to that same, authenticated organization/repository: `Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits globally by SHA alone, across every stack/repository configured in the Shipit instance. [3](#0-2)  This mirrors the reported bug class: a value ("scaler"/repository-scope) is enforced at one layer (constructor/signature check) but silently dropped at the point where the value is actually used (`update()`/`process`), breaking the intended invariant between the trusted context and the acted-upon data.

### Finding Description
Every other multi-tenant-aware handler in this engine scopes its DB writes through `Repository.from_github_repo_name(params.repository.full_name)`, which ties the mutation back to the specific repository named in the (verified) payload — e.g. `PushHandler` (via `Handler#stacks`), `CheckSuiteHandler`, and all `PullRequest::*Handler`s. [4](#0-3) [5](#0-4) [6](#0-5) 

`StatusHandler`, however, only requires `sha`/`state`/`description`/`target_url`/`context` and never touches `repository.full_name` at all: [7](#0-6) 
`process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — an unscoped, instance-wide lookup by raw SHA. Because git commit SHAs are content-addressed, any two repositories sharing history (e.g. a public upstream repo and any fork of it, hosted under a different GitHub organization) will contain `Commit` records in Shipit with identical `sha` values but belonging to different `stack`/`repository`/organization records.

The binding that is broken is:
`organization authenticated by verify_signature (via repository_owner/webhook_secret)` ≠ `repository/stack whose Commit row is mutated by StatusHandler#process`

Before the attacker's request: a `status` event for org A's fork is HMAC-signed with org A's webhook secret; `verify_signature` correctly authenticates "org A". After: `StatusHandler#process` writes a forged `Status` onto **every** `Commit` row across the whole Shipit install matching that SHA — including the corresponding commit belonging to org B's tracked stack — even though org B's webhook secret was never used and org B was never authenticated.

### Impact Explanation
`create_status_from_github!` feeds `Commit#status` (via `Status::Group.compact`) which directly drives `Commit#deployable?` (`success? && !blocked?`) and `Commit#schedule_continuous_delivery`, which auto-triggers `ContinuousDeliveryJob` when a commit becomes deployable. [8](#0-7) [9](#0-8)  An attacker who controls a fork/mirror repository in an org they administer (installing the GitHub App there with their own legitimate webhook secret) can send genuine, correctly-signed `status` webhooks for shared-history commit SHAs and thereby mark a target organization's tracked commit as `success`, satisfying required-status gating and potentially causing an unauthorized/auto-triggered deploy or merge of that commit in the victim stack — without ever possessing the victim org's `webhook_secret`, `ApiClient` token, or repository write access. This crosses the "unauthorized deploy/rollback" and "cross-repository writes" bar defined as Critical impact.

### Likelihood Explanation
Requires the attacker to control (own/administer) any GitHub organization/repo that has the Shipit GitHub App installed and shares commit history with a stack tracked under a different, victim organization in the same Shipit instance (e.g. via a public fork) — this is a realistic, low-effort setup for open-source projects deployed through a shared multi-tenant Shipit instance, and needs no compromise of secrets or victim-side access.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries by SHA alone) through the repository named in the verified payload, consistent with `Handler#stacks` / `Handler#repository_name`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or by requiring and validating `repository.full_name` and restricting the `Commit` lookup to `Repository.from_github_repo_name(params.repository.full_name)`'s stacks, mirroring `PushHandler`/`CheckSuiteHandler`.

### Proof of Concept
1. Attacker forks (or otherwise obtains a repo sharing commit history with) a repository tracked by the victim org "OrgB" in the same Shipit instance, hosting it under their own org "OrgA".
2. Attacker installs the Shipit GitHub App on their own "OrgA" fork, obtaining a legitimate `webhook_secret` for OrgA (configured in Shipit's `github.OrgA` section, as supported by multi-org config in `test/dummy/config/secrets_double_github_app.yml`).
3. Attacker triggers a real `status` webhook event on their OrgA fork for a commit SHA `C` that is shared with OrgB's tracked repository (same SHA, since content-addressed), setting `state: "success"`.
4. GitHub signs the payload with OrgA's webhook secret; `WebhooksController#verify_signature` resolves `repository_owner` to "OrgA" and passes signature verification correctly for OrgA.
5. `StatusHandler#process` executes `Commit.where(sha: "C")`, which matches **both** the attacker's OrgA `Commit` row and the victim's OrgB `Commit` row for the same SHA, and calls `create_status_from_github!` on all of them — forging a "success" status on OrgB's commit despite OrgB never being authenticated.
