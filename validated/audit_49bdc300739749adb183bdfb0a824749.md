### Title
Webhook signature verification keyed on attacker-controlled `repository.owner.login` allows cross-repository event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate against using a field taken directly from the *unverified* request body (`repository.owner.login` or `organization.login`), not from any value already authenticated by TLS, routing, or prior verification. The `create` action then dispatches the same raw payload to handlers that resolve the actual target `Repository`/`Stack` using a *different* field of that same unverified payload (`repository.full_name`). Because these two fields are never checked for consistency, and because `webhook_secret` is documented and implemented as *optional per organization*, an attacker who knows (or controls) one configured organization with no `webhook_secret` can forge a signature-exempt webhook whose `repository.full_name` names a completely different, secured stack.

### Finding Description
`verify_signature` resolves the app config purely from payload content: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the resolved organization's `webhook_secret` is blank: [3](#0-2) 

Shipit explicitly supports multiple GitHub App configurations keyed by organization name, each with its own optional `webhook_secret`, resolved by `Shipit.github(organization:)` / `github_app_config`: [4](#0-3) 

The docs and example config confirm `webhook_secret` is optional and can be `nil` per organization, including in a documented multi-org setup: [5](#0-4) 

After `verify_signature` passes (trivially, because the org resolved from `repository.owner.login` has no secret), `create` dispatches the *entire* raw payload — unmodified — to event handlers: [6](#0-5) 

Handlers resolve the actual `Repository`/`Stack` to act on using `repository.full_name` from that same payload, with no cross-check against the organization used for signature verification: [7](#0-6) [8](#0-7) [9](#0-8) 

**Binding broken:** *the organization that authenticated (the signature-verification org, taken from `repository.owner.login`/`organization.login`) ≠ the repository that is written (resolved from `repository.full_name` inside the same forged, unauthenticated field)*. Before the attacker's request: only payloads whose owning org has a configured `webhook_secret` matching a valid HMAC can trigger handlers for that org's repos. After: an attacker can craft a body where the "owner" field points at any org lacking a secret (trivially bypassing HMAC check) while the "full_name" field points at an entirely different, secured repository, causing Shipit to act on it as if authenticated.

### Impact Explanation
This allows an unauthenticated network attacker to forge GitHub events (`push`, `status`, `pull_request`, `check_suite`, `membership`, etc.) for any repository/stack tracked by Shipit, as long as at least one org configured in `secrets.yml`'s multi-org `github:` block lacks a `webhook_secret`. Concretely this can:
- Trigger `stack.sync_github` on a `push` handler for a victim stack, causing Shipit to fetch/sync arbitrary refs it believes came from GitHub — a cross-repository write into stack state.
- Forge `status` events to mark arbitrary commits as passing/failing CI, influencing the merge queue / deploy gating for a repo the attacker doesn't own.
- Forge `pull_request` events (`opened`/`labeled`/`closed`) to create, archive, or unarchive review stacks for a victim repository.
- Add/remove team memberships via forged `membership` events, since that handler is also driven by unauthenticated payload data.

This matches the "cross-repository writes" / "unauthorized deploy/rollback" high-impact category, achievable purely from crafting one HTTP POST — no session, API token, or webhook secret for the victim org required.

### Likelihood Explanation
Requires only that Shipit's operator configured the documented multi-org github schema with at least one organization lacking a `webhook_secret` (explicitly called "optional" in `docs/setup.md`), which is a supported and documented configuration, not a misconfiguration outside the engine's control. Given that, exploitation requires no credentials — just an HTTP POST to `/webhooks` with a crafted JSON body and appropriate `X-Github-Event` header.

### Recommendation
- Verify the webhook signature using the `webhook_secret` associated with the organization actually referenced by the payload's `repository.full_name` (or reject payloads where `repository.owner.login`/`organization.login` doesn't match the owner segment of `repository.full_name`).
- Consider disallowing organizations with a blank `webhook_secret` from being resolvable for any repository not exclusively owned by that org, or require `webhook_secret` to be mandatory in multi-org configurations.
- Add validation that the verified organization is the actual owner of the repository/stack being mutated before handlers execute.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `attacker-org` (no `webhook_secret`) and `victim-org` (with `webhook_secret`, tracking `victim-org/victim-repo` as a Shipit stack).
2. POST to `/webhooks` with header `X-Github-Event: push` and no/garbage `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the (missing/invalid) signature header.
4. `create` dispatches the payload to `PushHandler`, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim stack — despite the request never being validated by `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
