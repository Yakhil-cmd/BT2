### Title
Cross-organization membership webhook lets one org's owner delete a `Membership` from another org's `Team` via `github_id` collision - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` locates the `Team` solely by `params.team.id` (GitHub's numeric team `github_id`) via `Team.find_or_create_by!(github_id: params.team.id)`, without ever checking that the record's `organization` column matches the `params.organization.login` that the webhook's signature was actually verified against. In a multi-organization Shipit deployment, an attacker who owns one configured GitHub organization can craft a signed `membership` webhook for their own org that names an existing, unrelated, privileged team's `github_id` and a victim's `login`, causing Shipit to mutate that privileged team's `Membership` records.

### Finding Description
The binding that must hold is: **the organization whose webhook secret validated this request (`Shipit.github(organization: repository_owner)` in `verify_signature`) == the organization that actually owns the `Team` row being mutated (`Team#organization`)**.

`app/controllers/shipit/webhooks_controller.rb`'s `verify_signature` derives `repository_owner` from the payload itself: [1](#0-0) 
and for `membership` events (no `repository` key), `repository_owner` falls back to `params.dig('organization', 'login')`: [2](#0-1) 
i.e. the signature is checked against **whatever organization the attacker names in the payload**, using that organization's own webhook secret. If the attacker legitimately owns/administers that GitHub organization and it is configured in Shipit's multi-tenant `github:` credentials (`Shipit.github_app_config`/`github_organizations`), they can produce a validly-signed payload for their own org.

`MembershipHandler#process` then resolves the team purely by the global `github_id`, ignoring which organization was authenticated: [3](#0-2) 
`Team.find_or_create_by!(github_id: params.team.id)` will find an **already-existing** `Team` row (e.g. `shopify_developers`, `github_id: 1`, `organization: shopify`) regardless of the `organization.login` in the current, attacker-controlled payload — the `organization` assignment inside the block only runs on creation, not when the team is found. Because `Team.find_or_create_by_handle`/webhook flow never re-validates `team.organization == params.organization.login`, the handler proceeds to run `team.members.delete(member)` against the real privileged team.

Exploit flow:
1. Attacker controls/administers "evil-org", a second GitHub organization configured in Shipit (`secrets.github[:evil-org]`), giving them its legitimate webhook secret path (they can register the org-level `membership` webhook and get GitHub to sign it, or replicate the signing since they own the org's hook configuration).
2. Attacker triggers (or directly POSTs) a `membership` event with `organization.login: "evil-org"`, `team: { id: 1, ... }` (the real `shopify_developers.github_id`), `member.login: "walrus"` (a real privileged operator), `action: "removed"`.
3. `verify_signature` validates the signature against `evil-org`'s secret — passes, because it's genuinely signed by/for evil-org.
4. `MembershipHandler#find_or_create_team!` looks up `Team` by `github_id: 1`, finds the real `shopify_developers` row.
5. `team.members.delete(member)` deletes `walrus`'s `Membership` in `shopify_developers`, and if `Shipit.github_teams` includes that team, `walrus.authorized?` flips to `false`.

None of the existing guards catch this: `verify_signature` only proves the payload matches *some* org's secret, not the target team's org; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence, not organizational ownership; `find_or_create_team!` has no cross-check against `team.organization`.

### Impact Explanation
This directly manipulates `Shipit.github_teams` authorization state (`User#authorized?` depends on `Membership` rows for teams in `Shipit.github_teams`) — an escalation/de-escalation into the authorization system controlled by an attacker who owns an unrelated organization. Repeated calls against arbitrary known `github_id`s let the attacker deauthorize any operator from any privileged team (denial of legitimate access) or, using `action: 'added'`, `team.add_member(member)` to add an arbitrary GitHub user (including themselves, if their login is known/creatable) into a privileged team, granting themselves `authorized?` status without ever being a real member of that team's real GitHub organization. This is a genuine cross-tenant authorization bypass affecting every organization/team sharing this single Shipit instance (multi-org config), matching the "escalation into `Shipit.github_teams` authorization" High/Critical-adjacent impact category.

### Likelihood Explanation
This requires Shipit to be configured with **multiple GitHub organizations** (`secrets.github` keyed by org) so that an attacker's own, unrelated org is a legitimately configured tenant with its own valid webhook secret — that is the documented multi-org support (`Shipit.github_app_config`, `github_organizations`). The attacker only needs to control the org-level `membership` webhook of their own org (something org admins normally can do) and needs to know the target team's numeric GitHub `github_id` (discoverable via the GitHub API/UI for teams they can view, or by observing prior legitimate webhook payload team IDs) and the victim's login (public). No Shipit session, API token, or GitHub App private key of the *victim* org is needed. This is fully repeatable per request and does not depend on any race condition.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that any existing `Team` found by `github_id` has `organization == params.organization.login` before performing any add/remove, and raise/reject (or update trustable identity only under the matched org) rather than silently reusing a `github_id`-keyed record across organizations. Additionally/alternatively, scope the `Team.find_or_create_by!` lookup by `(github_id, organization)` composite instead of `github_id` alone, and have `WebhooksController#verify_signature` reject payloads whose `organization.login`/`repository.owner.login` does not match the record being targeted downstream.

### Proof of Concept
minitest plan (to be placed under `test/controllers/webhooks_controller_test.rb`, not executed here per scope but demonstrating the exact assertions):

```ruby
test ":membership webhook from an unrelated organization can delete membership in another org's privileged team" do
  # Arrange: a privileged team owned by 'shopify' with an existing member 'walrus'
  privileged_team = shipit_teams(:shopify_developers) # github_id: 1, organization: 'shopify'
  victim = shipit_users(:walrus)
  assert privileged_team.members.include?(victim)

  # Attacker's own, unrelated, but legitimately configured organization
  attacker_org = 'evil-org'
  Shipit.stubs(:github).with(organization: attacker_org).returns(stub(verify_webhook_signature: true))

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'removed',
    team: { id: privileged_team.github_id, name: privileged_team.name, slug: privileged_team.slug, url: privileged_team.api_url },
    organization: { login: attacker_org },
    member: { login: victim.login }
  }.to_json

  assert_difference -> { Membership.count }, -1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  # Binding check: the org that authenticated the request ('evil-org') != privileged_team.organization ('shopify')
  refute_equal attacker_org, privileged_team.reload.organization
  refute privileged_team.members.include?(victim)
  refute victim.reload.authorized?
end
```

This asserts that a webhook signed for `evil-org` (`organization.login: 'evil-org'`) is able to delete a `Membership` row belonging to `shopify_developers` (`organization: 'shopify'`), proving the equality "authenticating org == mutated team's org" is violated.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
