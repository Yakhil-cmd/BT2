### Title
`ProxyType::NonTransfer` on Westend relay chain falsely declares itself a superset of `ProxyType::SudoBalances`, letting a limited proxy delegate escalate to sudo-gated balance transfers - ([File: polkadot/runtime/westend/src/lib.rs])

### Summary
The Kibana CVE root cause is that a declared, unvalidated privilege claim (an integration package's cluster-privilege declaration) was trusted and used to mint credentials without checking it against the actual granted permissions. The Polkadot SDK analog is `pallet_proxy`'s privilege lattice: `InstanceFilter::is_superset` is the "declared" privilege relationship that `pallet_proxy::do_proxy` trusts, without cross-checking it against `InstanceFilter::filter` (the "actual" permission), when authorizing `add_proxy`/`remove_proxy` through a proxied call.

This exact bug class was already found and fixed once in this codebase for Asset Hub Westend (`ProxyType::NonTransfer` falsely claiming superset of `ProxyType::Governance`, PR/prdoc `pr_12769.prdoc`, with regression tests `non_transfer_proxy_is_not_a_superset_of_governance` and the lattice-wide test `proxy_type_superset_relation_matches_call_filters` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs`). However, that audit and its regression coverage is scoped to the Asset Hub Westend runtime's `ProxyType`. The **Westend relay chain** runtime (`polkadot/runtime/westend/src/lib.rs`) has its own, separate `ProxyType`/`InstanceFilter` implementation that was not covered by that fix or its tests, and it contains the same class of lattice violation between `NonTransfer` and `SudoBalances`.

### Finding Description
In `polkadot/runtime/westend/src/lib.rs:950-1031`, `ProxyType::is_superset` is defined as: [1](#0-0) 

```rust
fn is_superset(&self, o: &Self) -> bool {
    match (self, o) {
        (x, y) if x == y => true,
        (ProxyType::Any, _) => true,
        (_, ProxyType::Any) => false,
        (ProxyType::NonTransfer, _) => true,
        _ => false,
    }
}
```

This is a catch-all: `NonTransfer` declares itself a superset of **every** other `ProxyType` variant, including `ProxyType::SudoBalances`.

But `NonTransfer`'s `filter` implementation: [2](#0-1) 

enumerates an explicit allow-list of `RuntimeCall` variants (`System`, `Babe`, `Timestamp`, `Indices` claim/free/freeze, `Session`, `Grandpa`, `Utility`, `Identity`, `Vesting` vest/vest_other, `Scheduler`, `Proxy`, `Multisig`, `Registrar` register/deregister/reserve, `Crowdloan`, `Slots`, `Auctions`) and does **not** include `RuntimeCall::Sudo(..)` at all.

Meanwhile `ProxyType::SudoBalances`'s filter: [3](#0-2) 

```rust
ProxyType::SudoBalances => match c {
    RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: ref x }) => {
        matches!(x.as_ref(), &RuntimeCall::Balances(..))
    },
    RuntimeCall::Utility(..) => true,
    _ => false,
},
```

admits `RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Balances(..) })` — a call `NonTransfer` explicitly denies.

The `pallet_proxy::do_proxy` dispatch logic in `substrate/frame/proxy/src/lib.rs:994-1027` gates `add_proxy`/`remove_proxy` **only** on `is_superset`, not on the target type's `filter`: [4](#0-3) 

```rust
Some(Call::add_proxy { ref proxy_type, .. }) |
Some(Call::remove_proxy { ref proxy_type, .. })
    if !def.proxy_type.is_superset(proxy_type) =>
{
    false
},
```

So a `NonTransfer` proxy is permitted to call `Proxy::add_proxy(delegate, ProxyType::SudoBalances, delay)` on behalf of the real account, because `NonTransfer.is_superset(SudoBalances) == true`, even though `NonTransfer`'s own filter would reject a `Sudo` call outright. This mirrors precisely the already-patched `NonTransfer`/`Governance` bug on Asset Hub Westend (`prdoc/pr_12769.prdoc`), just on a different runtime (`polkadot/runtime/westend`) and a different call family (`Sudo` instead of `Treasury`/`ConvictionVoting`/`Referenda`/`Whitelist`).

### Impact Explanation
If a legitimate account (e.g., the holder of `pallet_sudo::Key`, or any other account) grants a third party a `NonTransfer` proxy — reasonably expecting that this restricts the delegate from moving balances or acting outside a limited set of governance/administrative calls — the delegate can instead:
1. Call `Proxy::add_proxy(new_delegate, ProxyType::SudoBalances, 0)` through the `NonTransfer` proxy (accepted, since `is_superset` says so).
2. Have `new_delegate` invoke `Proxy::proxy(real, Some(SudoBalances), Sudo::sudo{ call: Balances::transfer_allow_death{...} })`, which `SudoBalances`'s own filter admits.

Whether this results in an actual privileged balance transfer depends on whether `pallet_sudo::Key` for the `real` account equals the sudo key (i.e., whether `real` actually is the sudo-key holder) — `pallet_sudo::sudo` internally checks `ensure!(sender == Key::<T>::get())`. Regardless of that downstream check, the underlying flaw is the same class as the fixed CVE-analog bug: the declared privilege lattice (`is_superset`) is inconsistent with the actual permission surface (`filter`), which is an incorrect-authorization / privilege-escalation primitive inside `pallet_proxy`'s trust model, independent of whether the current westend sudo key happens to be set.

### Likelihood Explanation
Medium-to-Low. It requires: (a) an account (any account, not necessarily privileged) to grant a `NonTransfer` proxy to an untrusted delegate — a supported and commonly recommended usage pattern precisely because `NonTransfer` is documented/expected to withhold fund-moving power; and (b) that the `SudoBalances` escalation path only yields real value if `real` is (or later becomes) associated with the sudo key, or in a config where `Sudo` pallet key is set to a non-`None` account. I was not able to verify in this pass whether Westend's current genesis/config sets `pallet_sudo::Key` to `Some(_)` or `None` — if `None`, the underlying `sudo` call would fail its own origin check (`Key::get()` compare) and this analog’s user-facing impact would be nullified even though the lattice inconsistency itself remains a genuine authorization defect in `ProxyType`.

### Recommendation
Apply the same fix pattern used in `prdoc/pr_12769.prdoc` for Asset Hub Westend to the Westend relay-chain `ProxyType`: replace the blanket `(ProxyType::NonTransfer, _) => true` arm in `polkadot/runtime/westend/src/lib.rs`'s `is_superset` with an explicit, audited list of subset relationships that only includes proxy types whose entire `filter` allow-list is a strict subset of `NonTransfer`'s. Add a lattice-consistency regression test analogous to `proxy_type_superset_relation_matches_call_filters` (from `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:2493-2516`) for the relay-chain `ProxyType` as well, so this class of bug cannot reappear on any runtime's proxy configuration.

### Proof of Concept
Not executed. This report is a source-level analog derived from cross-referencing the already-fixed `NonTransfer`/`Governance` lattice violation (with its accepted fix `prdoc/pr_12769.prdoc` and regression tests in `asset-hub-westend/tests/tests.rs`) against the still-present, structurally identical `NonTransfer`/`SudoBalances` relationship in `polkadot/runtime/westend/src/lib.rs`. I did not have tool access to execute a live FRAME integration test (e.g., extending `substrate/frame/proxy/src/tests.rs`-style scaffolding against the actual Westend runtime) to confirm end-to-end dispatch behavior, nor did I confirm the current on-chain/genesis value of `pallet_sudo::Key` for Westend, which determines whether the escalation is exploitable in the currently deployed configuration versus merely a latent authorization-model defect. A background engineering session with full build/test tooling would be required to write and run the confirming integration test and to check the live Westend sudo-key configuration before treating this as bounty-eligible with certainty.
