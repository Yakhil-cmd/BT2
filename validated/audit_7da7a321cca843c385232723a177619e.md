### Title
NULL/undefined dereference in private-payment handler crashes node - ([File: network.js])

### Summary
`handleOnlinePrivatePayment()` in `network.js` dereferences `arrPrivateElements[0].payload.denomination` before verifying that `payload` exists on the first private-payment element, mirroring the Wireshark MRDISC bug pattern of dereferencing a field without validating it first.

### Finding Description
`handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks)` is the entry point for processing an incoming private-payment chain (the `private_payment` justsaying message, sent by any private-payment counterparty/paired device). It validates only that `arrPrivateElements` is a non-empty array: [1](#0-0) 

```
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");

	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
```

There is no check that `arrPrivateElements[0]` is a non-empty object, nor that it contains a `payload` field, before `arrPrivateElements[0].payload.denomination` is accessed. If a peer or paired device sends a `private_payment` message whose first chain element lacks a `payload` property (e.g. `{}` or `{unit:"..."}`), `arrPrivateElements[0].payload` is `undefined`, and accessing `.denomination` on it throws an uncaught `TypeError`.

This is structurally the same bug class as ALPINE-CVE-2017-17997: a field (`payload`) is dereferenced without first validating its presence, leading to a crash. Contrast this with the sibling function `validateAndSavePrivatePaymentChain()` in `private_payment.js`, which correctly checks `headElement.payload` before use: [2](#0-1) 

but that check only runs *after* `handleOnlinePrivatePayment` has already dereferenced the unchecked field.

### Impact Explanation
If the resulting `TypeError` is not caught somewhere up the call stack (e.g., inside the WebSocket message dispatcher's try/catch, if any), it becomes an uncaught exception in the process handling network/hub messages, crashing the node process. Because `private_payment` messages can be sent directly by a wallet's private-payment counterparty or via a hub relaying a paired device's message, this is reachable without any special privilege — matching the allowed "private-payment counterparty" attack surface. A crashed node cannot continue confirming units, which the validation rules explicitly recognize as impactful ("a network unable to confirm new units").

### Likelihood Explanation
Likelihood is high for any node that has the corresponding wallet/hub functionality active, since sending a malformed `private_payment` justsaying requires no authentication beyond being a paired device or hub peer, and the malformed message (missing `payload`) is trivial to construct.

### Recommendation
Add explicit validation before dereferencing:
```js
if (!ValidationUtils.isNonemptyObject(arrPrivateElements[0]) || !ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload))
    return callbacks.ifError("bad private_payment head element");
```
placed immediately after the `isNonemptyArray` check in `handleOnlinePrivatePayment`, before `unit`, `message_index`, and `output_index` are read from `arrPrivateElements[0]`.

### Proof of Concept
A malicious/paired device or hub sends a `private_payment` justsaying message with content:
```json
[
  { "unit": "somevalidlookingunit", "message_index": 0 }
]
```
i.e. an array whose sole element has no `payload` property. `handleOnlinePrivatePayment` executes `arrPrivateElements[0].payload.denomination`, throwing `TypeError: Cannot read properties of undefined (reading 'denomination')`, crashing the receiving node's process if uncaught.

**Note on verification limits:** Tool-call budget was exhausted before I could trace the exact justsaying dispatcher code path (`case 'private_payment':`) that invokes `handleOnlinePrivatePayment`, or confirm whether a top-level try/catch wraps all justsaying handlers (which would downgrade this from a crash to a logged error). This should be confirmed with a Devin session that can inspect the full `network.js` justsaying dispatch table and any surrounding exception handling before treating this as fully proven.
