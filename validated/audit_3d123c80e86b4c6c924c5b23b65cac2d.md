This confirms the vulnerability: `WebhooksController#verify_signature` selects which organization's webhook secret to use for HMAC verification based on `repository_owner` (`params.dig('repository', 'owner', 'login')`), but `Handler#stacks` (used by `PushHandler` and other event handlers) looks up the target `Stack` using an entirely different field: `repository_name` (`payload.dig('repository', 'full_name')`). [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

Because these are two separate JSON fields inside the same signed payload (`repository.owner.login` vs `repository.full_name`), an attacker who legitimately controls a GitHub organization/repo that has the Shipit GitHub App installed (and thus legitimately knows *that org's* `webhook_secret`, obtained without any Shipit credential — just by installing a public GitHub App on their own repo) can craft a raw POST body where `repository.owner.login` is set to their own org (so the HMAC verifies successfully against their own known secret) while `repository.full_name` is set to a victim organization/repository that Shipit also tracks. `verify_signature` only checks that the payload's HMAC matches the secret belonging to the *owner* field — it never asserts that the owner field is consistent with the full_name field, and the downstream handler never re-checks the owner at all.

This breaks the trust equality that should hold: `organization whose secret authenticated the payload == organization of the repository that gets written to`. After the signature check passes, `PushHandler` (and other push/status/check handlers) will act on whatever `Stack`s match `repository.full_name`, regardless of which org's secret validated the message. This lets an attacker who is a member of any org with the Shipit App installed forge push/status/check events for a victim repository that they do not control, e.g. triggering `stack.sync_github(expected_head_sha: ...)` against a fabricated `after` SHA, or manipulating commit statuses / check runs for the victim's stack, without holding a Shipit session, API token, or write access to the victim's repository.

### Title
Webhook signature verification uses `repository.owner.login` while handlers act on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature using `repository.owner.login` from the untrusted JSON body, but every webhook `Handler` (e.g. `PushHandler`) resolves the target `Stack` using the separate `repository.full_name` field from the same body. The two fields are never cross-checked, so a valid signature for organization A does not guarantee the acted-upon repository actually belongs to organization A.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-30, 59-62) does:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` comes from `params.dig('repository', 'owner', 'login')`.

Once verified, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs, and each `Handler` subclass (`app/models/shipit/webhooks/handlers/handler.rb`, lines 32-38) resolves stacks via:
```
Repository.from_github_repo_name(repository_name)&.stacks
```
where `repository_name = payload.dig('repository', 'full_name')`.

Both `repository.owner.login` and `repository.full_name` are attacker-controlled JSON fields inside the same raw POST body. The HMAC signature covers the entire raw body byte-for-byte, so the *signature itself* is not forgeable without the correct secret — but Shipit supports per-organization secrets (`Shipit.github(organization: ...)`), and the org used to pick the secret is not the same org whose repositories are ultimately mutated. Any actor who legitimately controls an organization where the Shipit GitHub App is installed (which they can do for their own GitHub org without needing any Shipit-side credential) knows that org's `webhook_secret` and can therefore produce a validly-signed payload whose `repository.owner.login` is their own org (passing `verify_webhook_signature`) while `repository.full_name` names an unrelated, victim-owned repository/stack tracked by the same Shipit instance.

### Impact Explanation
This crosses the "organization authenticated vs. repository written" trust boundary explicitly called out as in-scope. An attacker can forge `push`, `status`, `check_run`/`check_suite`, or other webhook events that Shipit acts on for a repository/stack they do not own or have write access to, causing Shipit to run `GithubSyncJob`, update commit statuses, or affect merge/CI signals for a victim stack — a cross-repository write triggered without holding any Shipit session, API token, GitHub App private key, or push access to the victim repo. This matches the report's "Critical" bucket (cross-repository writes / unauthorized action caused by a mutable base-trust binding — the org used to validate is not necessarily the org whose data is subsequently manipulated).

### Likelihood Explanation
Exploitability requires: (1) Shipit configured with per-organization GitHub Apps/secrets (`config/secrets.yml` multi-org schema, as documented), and (2) the attacker being able to install/operate the shared GitHub App on an org they control (a normal, low-privilege action for any GitHub user/org admin, not requiring any Shipit credential) and get its webhook delivered to Shipit's `/webhooks` endpoint with a crafted `repository.full_name`. This is plausible for any Shipit deployment serving multiple GitHub organizations, which is an explicitly supported/documented configuration.

### Recommendation
After computing `repository_owner` for secret selection, verify it is actually consistent with the owner segment of `repository.full_name` (and/or with the resolved `Repository`/`Stack`'s known owner) before dispatching to handlers. Reject the webhook if the two disagree, rather than only checking whether *some* org's secret validates the raw body.

### Proof of Concept
1. Deploy Shipit configured for multiple organizations, e.g. `attacker-org` and `victim-org`, each with the shared/public Shipit GitHub App installed and its own `webhook_secret` (per `config/secrets.yml` multi-org example in `docs/setup.md`).
2. Attacker, as an admin of `attacker-org` (a GitHub org they legitimately control), knows `attacker-org`'s `webhook_secret` because it's configured by the Shipit operator per-org but the attacker can just install the app and observe deliveries/signatures from their own repo pushes, or in shared-app setups can simply configure the secret themselves.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over this exact raw body, and POSTs it to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against the attacker's own secret.
6. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — a cross-organization action triggered purely with the attacker's own org credentials.
