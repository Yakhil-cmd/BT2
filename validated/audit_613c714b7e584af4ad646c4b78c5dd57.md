### Title
Stack-Scoped API Token Can Read Any Stack's Build/Deploy State via CCMenu Endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The `Api::CCMenuController#stack` method resolves the target stack directly from `params[:stack_id]` using an unscoped `Stack.from_param!`, instead of using the tenant-scoped `stacks` collection that every other API controller relies on. This breaks the binding "stack a token authorises versus a stack it touches": an `ApiClient` token created and scoped to one stack can be replayed with a different `stack_id` to read another stack's CI/deploy status.

### Finding Description
`Shipit::Api::BaseController` establishes the authorization invariant that an `ApiClient` scoped to a stack (`api_client.stack_id?`) may only see that stack, by scoping the `stacks` relation and building `stack` from it: [1](#0-0) 

`Api::StacksController` correctly reuses this scoped lookup: [2](#0-1) 

However, `Api::CCMenuController` overrides `stack` and bypasses the scoped collection entirely, fetching directly from the global `Stack` table using the raw `params[:stack_id]`: [3](#0-2) 

The controller also overrides `authenticate_api_client` to accept a bearer token via the `token` query-string parameter (by design, since CI tools poll this XML endpoint without custom headers): [4](#0-3) 
and only requires the coarse `read:stack` permission bit, not a stack-scope check: [5](#0-4) 

`CCMenuUrlController` is the normal way these tokens are minted: it creates (or reuses) an `ApiClient` bound to a specific stack with only `read:stack` permission, and embeds the token in a shareable URL: [6](#0-5) 
`ApiClient#check_permissions!` only checks that `"read:stack"` is present in the permissions array — it never compares the client's bound `stack_id` against the stack being accessed: [7](#0-6) 

Putting this together:
- Before the attack: `ApiClient#stack_id` = Stack A (the stack the token was minted for and displayed to the user in the CCMenu URL).
- After the attack: the attacker takes that same token (e.g., shared or embedded in a CI dashboard config for Stack A) and calls `GET /api/stacks/:stack_id/ccmenu.xml?token=<token>` with `:stack_id` set to Stack B. `require_permission :read, :stack` passes because the token has `read:stack`. `stack` resolves Stack B directly via `Stack.from_param!`, with no comparison to the token's bound `stack_id`. The response renders Stack B's build/deploy state.

This is exactly the "max return value / missing bound check" bug class from the external report, translated to an authorization scope: the code never checks that `stack.id == current_api_client.stack_id` before acting, the same way the Vesting contract never checked the computed vested amount against `totalAmount`.

### Impact Explanation
Any holder of a stack-scoped CCMenu token (which is a low-privilege, `read:stack`-only credential meant to be embedded in third-party CI dashboards / status widgets and is designed to be shared relatively freely) can escalate its scope to read the deploy/CI status (`lastBuildStatus`, `lastBuildLabel`, lock state, etc., as rendered in `app/views/shipit/ccmenu/project`) of **any** stack in the Shipit installation, including private/internal stacks the token was never authorized for. This is an authorization-scope escalation resulting in unauthorized read of stack state, matching the in-scope High-impact category of "escalation into authorization ... unauthorized read of stack state."

### Likelihood Explanation
Likelihood is high for any attacker who already possesses one legitimate, low-privilege CCMenu token (these are routinely embedded in CI status pages/build monitors and are not treated as highly sensitive since they are stack-scoped and read-only). No additional credentials, GitHub access, or privileged account is required — only substituting the `stack_id` route parameter.

### Recommendation
In `Api::CCMenuController#stack`, resolve the stack through the scoped `stacks` collection (as `BaseController#stack` and `StacksController#stack` do) instead of calling `Stack.from_param!` on the unscoped `Stack` relation, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so a stack-bound `ApiClient` cannot resolve stacks outside its `stack_id`.

### Proof of Concept
1. As a normal user, visit a stack's settings page and trigger `CCMenuUrlController#fetch` for Stack A; this creates/reuses an `ApiClient` with `permissions: ['read:stack']` and `stack_id: A`, returning a URL like `/api/stacks/A/ccmenu.xml?token=<T>`. [8](#0-7) 
2. An attacker with access to token `<T>` (e.g., read from the embedded CI dashboard config) requests `/api/stacks/B/ccmenu.xml?token=<T>` for an unrelated Stack B they should not be able to see.
3. `authenticate_api_client` authenticates the token successfully (it's a valid, non-expired token): [4](#0-3) 
4. `require_permission :read, :stack` passes because the token has `read:stack` permission, with no comparison to `stack_id`.
5. `stack` resolves Stack B via unscoped `Stack.from_param!(params[:stack_id])` and `#show` renders Stack B's build status XML — data the token was never scoped to access. [9](#0-8)
