## Analysis

The Magnetar bug class is: a party-acting-on-behalf-of-a-user (helper/proxy) trusts a caller-supplied "who is authorized" parameter instead of verifying it against the actual authenticated sender, letting an unrelated party leverage another user's standing authorization.

The closest analogous, reachable pattern in this ocore codebase is in the `"sign"` message handler in `wallet.js`, which is reachable from any paired device (a message-handling surface explicitly allowed as an attack entry point). In the `ifLocal` branch of the signing-request flow, the code that would verify that the sending device is actually a registered cosigner of the target address has been intentionally removed/commented out, while the parallel `ifRemote` branch retains an equivalent check (`other_device_addresses.includes(from_address)`). ### Title
Missing cosigner authorization check in `"sign"` message handler lets any paired device spoof a multisig signing request for a local address - (File: wallet.js)

### Summary
The `handleMessageFromHub` function's `"sign"` case (analogous to Magnetar's actions that should be gated by `_checkSender`) allows any paired/correspondent device to send an unsolicited signing request for one of the wallet's own multi-signature addresses. For the `ifRemote` branch, `findAddress`'s callback explicitly checks that the requesting device (`from_address`) is one of the address's listed cosigners before proceeding. The `ifLocal` branch, which handles the same "sign" request when the local device itself holds the signing key, has this equivalent check commented out, with the code comment stating the check was removed to permit multilateral signing.

### Finding Description
In `wallet.js`, the `case "sign":` block validates the shape of `body.address`, `body.signing_path`, and `body.unsigned_unit`, and confirms `body.address` is among the unsigned unit's authors, but it never confirms that the requesting device (`from_address`) is actually entitled to request a signature over that address/signing_path. It defers this decision to `findAddress`, whose `ifRemote` callback does check `other_device_addresses.includes(from_address)` (i.e., it verifies the requester is a known cosigner) before forwarding, but the `ifLocal` callback skips the analogous check:

```
ifLocal: function(objAddress){
    // the commented check would make multilateral signing impossible

    //    if (sender_rows.length !== 1)
    //        return callbacks.ifError("sender is not cosigner of this address");
        callbacks.ifOk();
        ...
        eventBus.emit("signing_request", objAddress, body.address, objUnit, assocPrivatePayloads, from_address, body.signing_path);
``` [3](#0-2) 

Because the requesting device isn't verified against the address's cosigner list, any paired device — not necessarily a member of the shared/multisig address — can craft an `unsigned_unit` with attacker-chosen payment outputs referencing the victim's own address, submit it via `"sign"`, and have the local wallet emit a `"signing_request"` event carrying that unit for user confirmation, misrepresenting the request as coming from a legitimate correspondent/cosigner.

### Impact Explanation
An attacker abusing this path cannot directly move funds (final signing requires user approval), but the missing sender-authorization check breaks the intended security invariant that only registered cosigners of a shared address can initiate signing flows for it — exactly the invariant `_checkSender` enforces in the Magnetar report. This enables spoofed signing requests to reach the victim's confirmation UI purporting to be legitimate multisig cooperation, which can be used to socially engineer approval of an attacker-controlled transaction (e.g., draining a shared/multisig address the victim co-manages), and to flood/confuse the signing workflow of shared addresses.

### Likelihood Explanation
Any device that is merely paired (a correspondent) with the victim's wallet — not a cosigner of the target address — can trigger this path with a single crafted `"sign"` message; no privileged network position or additional compromise is required, matching the "reachable by a paired device" surface explicitly permitted for this analysis.

### Recommendation
Restore (and generalize) the cosigner-membership check in the `ifLocal` branch of the `"sign"` handler, mirroring the `ifRemote` branch's `other_device_addresses.includes(from_address)` check, so that only devices actually listed as cosigners (or otherwise authorized parties, e.g. for legitimate multilateral "dumb contract" signing) can trigger a local signing_request for a given address/signing_path.

### Proof of Concept
1. Device X pairs with the victim's wallet as an ordinary correspondent (not a cosigner of the victim's shared address `S`).
2. Device X sends a `"sign"` message: `{address: S, signing_path: "r.0", unsigned_unit: {authors: [{address: S}], messages: [{app:'payment', payload:{outputs:[{address: attacker_address, amount: victim_balance}]}}]}}`.
3. In `handleMessageFromHub`, the `"sign"` case validates shape/author-membership only, then calls `findAddress(S, "r.0", ...)`.
4. Since `S` is locally hosted, `ifLocal` fires without checking that `from_address` (Device X) is a cosigner of `S`, and the handler proceeds to validate/emit `"signing_request"` for the attacker-crafted unit to the victim's wallet UI, presenting it as a valid cooperative signing request.
