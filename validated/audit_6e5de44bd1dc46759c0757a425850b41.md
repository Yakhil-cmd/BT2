### Title
`Repository#provision?` operator-precedence bug lets stale `provisioning_behavior` bypass `review_stacks_enabled=false` — ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` (and the identically-written `ReopenedHandler#unarchive?`) combine `review_stacks_enabled` with the three `provisioning_behavior_*` predicates using Ruby's default operator precedence, where `&&` binds tighter than `||`. This means `review_stacks_enabled` is only ANDed into the `allow_all` disjunct; the `allow_with_label` and `prevent_with_label` disjuncts are evaluated completely independently of `review_stacks_enabled`.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == false` must imply `provision? == false` for every disjunct (i.e., disabling review stacks must fully disable PR-triggered provisioning).

The actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to Ruby precedence (`&&` before `||`), this parses as:

```
(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)
```

`review_stacks_enabled` is scoped only to the first parenthesized clause. The second and third clauses have no dependency on `review_stacks_enabled` whatsoever, so if `provisioning_behavior` was left at `allow_with_label` (or `prevent_with_label`) from before the operator disabled review stacks, `provision?` still evaluates true for `allow_with_label` + labeled PR, or `prevent_with_label` + unlabeled PR — regardless of `review_stacks_enabled`.

Exploit flow: attacker (unprivileged, owns a fork/PR against the target repo) opens a PR and adds the label matching `repository.provisioning_label_name` (attacker controls PR labels on their own PR in many GitHub workflows, or simply targets a repo whose `prevent_with_label` behavior triggers by default on any *unlabeled* PR — no label action needed at all). This reaches `Shipit::Webhooks::Handlers::Handler#process` via `OpenedHandler#process` → `respond_to_pull_request_opened?` → `provision?` returning `true` despite `review_stacks_enabled == false`, which then calls `ReviewStackAdapter#find_or_create!` → `create!`, which persists a new `Shipit::ReviewStack` and enqueues it via `ReviewStackProvisioningQueue.add(stack)` for `stack.provision` to run in `ReviewStackProvisioningQueue#work`. This creates a real, unauthorized stack record and pushes it into the provisioning pipeline (which ultimately drives task/command execution against the deploy host), for a repository whose operator explicitly believed review-stack automation was off. [2](#0-1) [3](#0-2) 

None of the standard guards intervene here: `verify_signature`/webhook auth only validates that the webhook came from GitHub for *some* repo (an attacker who owns the source repo can freely emit these events for PRs against their own fork/repo pointed at a Shipit-tracked upstream, or any repo whose webhook is registered), `drop_unhandled_event` doesn't apply since `pull_request.opened` is handled, and the `ExplicitParameters` schema only validates payload shape, not authorization logic. The bug is purely a logical/authorization-boundary defect inside `provision?` itself — no other check re-validates `review_stacks_enabled` downstream before `create!`/`provision` runs.

The same defective pattern is duplicated verbatim in `ReopenedHandler#unarchive?`: [4](#0-3) 

### Impact Explanation
For any repository where an operator previously used `allow_with_label`/`prevent_with_label` and later disabled `review_stacks_enabled` without resetting `provisioning_behavior` to `allow_all` (the enum default state is otherwise unconstrained — no validation forces `provisioning_behavior` back to a "disabled-safe" value), an unprivileged PR author can still cause a `Shipit::ReviewStack` to be created and queued for provisioning, feeding into the deploy/task execution pipeline that this codebase treats as trusted, privileged automation. This is repeatable per PR/per repository matching the stale-config precondition and matches the Critical impact category (unauthorized stack/task creation for provisioning that should have been fully disabled, potentially leading to command execution via the provisioning pipeline).

### Likelihood Explanation
Requires a specific but plausible operator misconfiguration: `review_stacks_enabled: false` with a stale `provisioning_behavior` of `allow_with_label` or `prevent_with_label` (not reset to `allow_all`/default) — this is a realistic operational sequence (feature was enabled, then disabled without full cleanup) rather than a contrived edge case. No attacker secrets are required; opening a PR and optionally applying a label are actions available to any external contributor to a public repo webhook-linked to Shipit. Repeatable at will against any repository in this misconfigured state.

### Recommendation
Explicitly parenthesize `review_stacks_enabled` across the entire disjunction so it gates all three behaviors, e.g.:

```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Apply the identical fix to `ReopenedHandler#unarchive?`, and audit `LabeledHandler`/`UnlabeledHandler` for the same pattern.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
1. Create a `Repository` fixture with `review_stacks_enabled: false` and `provisioning_behavior: :allow_with_label`.
2. Build an `opened` pull_request webhook payload for that repo with a label matching `repository.provisioning_label_name`.
3. Invoke `OpenedHandler.new(...).process` (or dispatch via the webhooks controller entrypoint).
4. Assert `repository.review_stacks_enabled == false` (left side of the binding) and, independently, assert `repository.review_stacks.count == 0` and no `ReviewStack` record was created / no job was enqueued to `ReviewStackProvisioningQueue` (right side, expected under the binding).
5. Actual current behavior: `repository.review_stacks.count == 1` — demonstrating the binding `review_stacks_enabled == false ⇒ provision? == false` is violated.
