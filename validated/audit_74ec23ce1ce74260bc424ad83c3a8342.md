Confirmed: `sign_in_github` creates a session for any GitHub user who completes OAuth, with no `authorized?`/team-membership check at login time. Team membership is only enforced later, in `force_github_authentication`, which is explicitly skipped for `MergeStatusController#show`/`#check`.

### Title
Any authenticated-but-unauthorized GitHub user can read merge status of arbitrary stacks via `MergeStatusController#show` - (File: `app/controllers/shipit/merge_status_controller.rb`)

### Summary
`MergeStatusController#show` and `#check` are exempted from `force_github_authentication` via `skip_authentication only: %i[check show]`, so the only gate applied in `show` is `current_user.logged_in?`, not `current_user.authorized?`. Any user who completes GitHub OAuth (which itself performs no team check) obtains a Shipit session and can then pass an arbitrary `stack_id` to read that stack's `merge_status`, regardless of `Shipit.github_teams` membership for that repository.

### Finding Description
The binding the question implies should hold is: `reachable_stack_state(stack_id) == authorized_for(current_user, stack.repository)`, i.e., a stack's merge status HTML should only be rendered when `current_user.authorized?` (team-membership) is true for that stack's repository team.

Tracing the code:
- `app/controllers/concerns/shipit/authentication.rb` `force_github_authentication` is the only place `current_user.authorized?` is checked [1](#0-0) .
- `MergeStatusController` skips exactly this before_action for `check` and `show`: `skip_authentication only: %i[check show]` [2](#0-1) .
- `show` only re-checks `current_user.logged_in?`, not `authorized?`, before rendering `stack_status` for the resolved `stack` [3](#0-2) .
- `stack` is resolved directly from `params[:stack_id]` via `Stack.from_param!` with no ownership/team check [4](#0-3) .
- `User#logged_in?` is unconditionally `true` for any persisted `User` row, independent of team membership; `authorized?` (the actual gate) is a separate method that is never invoked in this controller [5](#0-4) .
- Session creation via GitHub OAuth (`GithubAuthenticationController#callback` → `sign_in_github`) creates/finds a `User` and sets `session[:user_id]` with no `authorized?`/team check at all [6](#0-5) .

So: any GitHub account holder can complete OAuth login on the instance (this alone requires no team membership and is standard, unauthenticated-to-Shipit access), obtaining `session[:user_id]`. That satisfies `current_user.logged_in?` but not `current_user.authorized?`. They can then request `GET /merge_status?stack_id=<any_stack>` and receive the rendered `merge_status` partial (`success.html.erb`, `failure.html.erb`, `backlogged.html.erb`, etc.) for any stack on the instance, including stacks belonging to repositories/teams they have no membership in. The equality claimed by the binding does not hold after tracing: `logged_in?` is checked, but `authorized?` (team-membership) is not, so the two diverge for any logged-in-but-unauthorized user.

Existing guards that fail to prevent this: `force_github_authentication`'s `authorized?` check is bypassed by `skip_authentication`; there is no per-stack or per-repository team check inside `MergeStatusController#show`/`stack`/`stack_status`.

### Impact Explanation
An authenticated-but-team-unauthorized user can enumerate `stack_id` values (or repository/branch/PR referrer URLs) to read the CI/merge/lock status of any stack across any repository/tenant hosted on the instance. This is a High-impact unauthenticated (with respect to per-repository authorization) read of stack state, matching the listed "unauthenticated read of stack state" category, since the only requirement is a valid GitHub account able to complete OAuth against this Shipit instance, not membership in the relevant `Shipit.github_teams`. It is fully repeatable against arbitrary stacks/repositories, since `stack_id` is attacker-controlled and unvalidated against the caller's team memberships.

### Likelihood Explanation
Preconditions: the Shipit instance must allow GitHub OAuth login from arbitrary GitHub accounts (this is the default OAuth flow; `Shipit.github_teams` restricts app *usage* post-login, not who can complete OAuth and receive a session). No secrets, tokens, or privileged roles are required — only a working GitHub account and the ability to complete the standard OAuth handshake this app itself exposes at `/github/auth/github`. Cost is low and the exploit is trivially repeatable by iterating `stack_id`.

Caveat/uncertainty: this requires the attacker to first obtain a Shipit session via OAuth, which is a step beyond a purely anonymous, session-less request; whether this satisfies the strict "no Shipit session" framing in the prompt depends on whether completing this engine's own public OAuth endpoint counts as a privileged precondition — it does not require any Shipit-issued secret, API token, or team membership, only a GitHub account, so it is consistent with the "unprivileged attacker" definition given (any internet user able to send HTTP requests / any GitHub user).

### Recommendation
In `MergeStatusController#show` (and `#check`), replace or augment the `current_user.logged_in?` check with `current_user.authorized?` (or an explicit per-stack authorization check, e.g., verifying the user's team membership against the stack's repository), so that only users authorized for that specific stack's repository/team can view its merge status. Do not fully skip `force_github_authentication` for these actions, or restore the `authorized?` check without the `redirect_to`/forbidden-page side effects that were being avoided.

### Proof of Concept
```ruby
test "GET show returns merge status to a logged-in user with no team membership for the stack's repository" do
  # Arrange: user with no Shipit team membership
  outsider = Shipit::User.create!(login: 'outsider', name: 'Outsider', github_id: 999_999)
  session[:user_id] = outsider.id

  stack = shipit_stacks(:shipit) # belongs to a repository/team the outsider is not a member of
  assert_not outsider.authorized? # binding: authorized? should gate access, and it is false

  get :show, params: { stack_id: stack.to_param }

  # Broken binding: response should be 403/redirect per authorized? == false,
  # but current code only checks logged_in?, so it renders merge status HTML instead.
  assert_response :ok
  assert_includes response.body, stack_status_partial_marker # e.g. 'js-details-container'
end
```
This demonstrates that `current_user.authorized?` (false) and the actual response (200 OK with stack status HTML) diverge, confirming the broken binding.

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end

    def logout
      reset_session
      redirect_to(root_path)
    end

    private

    def sign_in_github(auth)
      user = User.find_or_create_from_github(auth.extra.raw_info)
      user.update(github_access_token: auth.credentials.token)
      user.id
    end
