### Title
`EnvironmentVariables#interpolate` falls back to the Shipit host process's own `ENV`, leaking host secrets into PR-controlled task output - ([File: lib/shipit/environment_variables.rb])

### Summary
`EnvironmentVariables#interpolate` substitutes `$VAR` tokens in command arguments using `@env.fetch(variable) { ENV[variable] }`, so any variable name not present in the deploy/task-scoped `@env` hash silently falls back to reading the Shipit Rails process's own OS environment. Since review-stack and deploy commands are built from a repository's `shipit.yml`, which for review stacks is read from the untrusted PR branch, a PR author can reference an arbitrary variable name (e.g. `$SECRET_KEY_BASE`) in a step and have its value from the Shipit host's process environment echoed into task output that they can read.

### Finding Description
The broken binding: the set of variable names substitutable by `interpolate` should equal the variable names present in `@env` (the task/deploy-scoped environment built from `Stack#env`, `Shipit::Deploy` env, and whitelisted `shipit.yml` env vars). Instead, it equals `keys(@env) ∪ keys(ENV)` because of the fallback block on [1](#0-0) .

Call path: `Command#interpolate_environment_variables` ( [2](#0-1) ) is invoked unconditionally from `Command#start` before every `PTY.spawn` ( [3](#0-2) ), regardless of whether the whitelist method `EnvironmentVariables#permit` ( [4](#0-3) ) was ever applied to the argument strings themselves — `permit` only sanitizes the *env hash* used elsewhere, it does not gate `interpolate`, and `interpolate` never consults it. `StackCommands#env` builds `@env` from `Commands` base env merged with `@stack.env` (`ENVIRONMENT`, `LAST_DEPLOYED_SHA`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `BRANCH`) as seen in [5](#0-4)  and [6](#0-5)  — none of these overlap with typical host secrets like `SECRET_KEY_BASE`, `DATABASE_URL`, `GITHUB_APP_PRIVATE_KEY`, etc., so referencing any such name in a `shipit.yml` step's command string (e.g. `echo $SECRET_KEY_BASE`) causes `@env.fetch` to miss and fall through to `ENV[variable]`, exposing the live Shipit process's environment variable value, `Shellwords.escape`d, directly into the spawned command's argv, whose stdout is streamed back as task output.

Existing guards do not prevent this: `verify_signature`/webhook checks are irrelevant (this is not a webhook path), `EnvironmentVariables#permit` is a separate, optional method not called by `interpolate`, and there is no whitelist check at interpolation time as the question states.

### Impact Explanation
Any secret present in the Shipit Rails host's OS-level `ENV` (commonly populated via dotenv/12-factor deployment, e.g. `SECRET_KEY_BASE`, database credentials, `GITHUB_APP_ID`/private key material if stored as an env var, or any other 12-factor secret) can be exfiltrated into a task's terminal output, which is visible to the PR author who triggers the review-stack/task run. This matches the Critical criteria ("exfiltration of ... deploy-time secrets ... credential leaving the host"). The blast radius is bounded to secrets reachable in the Shipit process's own `ENV` (not other tenants' stack-scoped secrets), but it is repeatable on every task/command run and requires only editing `shipit.yml` in a PR branch that triggers a review stack.

### Likelihood Explanation
Exploitability requires: (1) the Shipit installation enables review stacks (or any deploy/task path) where `shipit.yml` commands are read from a branch an unprivileged actor controls, and (2) the Shipit host process's OS environment contains sensitive values (very common in Rails/12-factor deployments using dotenv or platform env injection). No Shipit credentials or elevated GitHub permissions are needed — only the ability to open a PR/push a branch with a crafted `shipit.yml` review/deploy step. This is low-cost and fully repeatable.

### Recommendation
Remove the `ENV[variable]` fallback in `EnvironmentVariables#interpolate` entirely, or replace it with a strict whitelist so only variables explicitly present in the task/deploy-scoped `@env` (already passed to `Command.new(..., env: ...)`) are substitutable; unresolved variables should raise or be left as literal text rather than reaching into the host process environment.

### Proof of Concept
```ruby
# test/unit/environment_variables_test.rb (or command_test.rb)
class EnvironmentVariablesLeakTest < ActiveSupport::TestCase
  test "interpolate does not fall back to process ENV for variables absent from @env" do
    ENV['SHIPIT_SECRET_TEST'] = 'super-secret-value'
    task_env = {'ENVIRONMENT' => 'production'} # attacker-visible task env, no SHIPIT_SECRET_TEST key

    result = Shipit::EnvironmentVariables.with(task_env).interpolate('echo $SHIPIT_SECRET_TEST')

    # Binding under test: substitutable_vars(interpolate) == keys(task_env)
    # Before fix: result contains 'super-secret-value' (binding violated, ENV leaked)
    # After fix: result should NOT contain the secret value; '$SHIPIT_SECRET_TEST' should
    # remain literal or raise, proving interpolate is scoped strictly to task_env's keys.
    refute_includes result, 'super-secret-value'
  ensure
    ENV.delete('SHIPIT_SECRET_TEST')
  end
end
```

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
