### Title
Global oracle `last-update` timestamp map lets any caller invalidate another user's already-prepared, otherwise-valid price feed, causing a DOS on borrow/withdraw/repay/liquidate - (File: `market/market.clar`, `market/v0-4-market.clar`)

### Summary
`price-resolve` enforces a monotonicity check against a **globally shared** `last-update` map keyed only by `{type, ident}` (the asset feed identity), not per-caller. Any unprivileged user who submits a market operation bundled with a newer signed Pyth/DIA price update advances this shared timestamp for everyone. A different, unrelated user whose transaction carries an independently valid, signed, non-stale price update — but with an earlier `publish-time` than what was just committed — will have their transaction revert with `ERR-ORACLE-INVARIANT`, even though their own price data satisfies the staleness window in isolation.

### Finding Description

It computes `oracle-timestamp-fresh(timestamp, last-update-time, max-staleness)`, defined as: [2](#0-1) 

which requires both `delta <= max-staleness` **and** `ts >= prev`. `prev` comes from the shared map: [3](#0-2) 

This map is not scoped per user or per transaction — it is a single global timestamp watermark per `{type, ident}` asset feed, updated unconditionally whenever any caller's included price update has a newer `publish-time`: [4](#0-3) 

Users submit their own optional bundle of signed price feed updates with each call (`price-feeds (optional (list 3 (buff 8192)))`), which are written via `write-feeds`/`write-feed` before price resolution occurs: [5](#0-4) 

The same shared-watermark pattern exists in the mainnet contract: [6](#0-5) [7](#0-6) 

Because the watermark is shared and monotonic, this creates an ordering dependency between two independent, unprivileged callers within the same block: whichever transaction executes first and includes the newest signed price for a given feed permanently (for that block) raises the bar for everyone else. Attacker: any address, at zero special privilege, that repeatedly submits cheap market calls (e.g., small self-repays or borrows) bundled with the freshest available signed Pyth update for a target asset. Victim: any other user (a borrower calling `withdraw-collateral`/`borrow`/`repay`, or a liquidator calling `liquidate`) whose own price bundle — obtained slightly earlier off-chain but still within `max-staleness` — is executed after the attacker's transaction in the same block. The victim's `price-resolve` call fails `ts >= prev` and reverts the entire operation with `ERR-ORACLE-INVARIANT`, even though nothing is wrong with the victim's own submitted data.

### Impact Explanation
This is a temporary-freezing-of-funds DOS: a targeted victim's withdraw, borrow, repay, or liquidation call can be repeatedly reverted by an attacker who has no special permissions and pays only for cheap transactions that "bump" the shared timestamp ahead of the victim's prepared feed. This is particularly damaging when targeting a liquidator trying to liquidate a specific position (protecting an unhealthy account from being liquidated) or a user trying to withdraw collateral/repay debt during a volatile period — the attacker can grief that specific operation block after block by continually refreshing the global watermark just ahead of the victim.

### Likelihood Explanation
Likelihood is moderate-to-high in blocks with multiple pending price-feed-carrying transactions for the same asset: the attacker only needs to observe the mempool (or simply always relay the newest Pyth update available) and land their transaction first. No special access, oracle compromise, or DAO action is required — this stems purely from the shared, caller-writable, monotonic `last-update` map design in this contract.

### Recommendation
Do not enforce global cross-caller monotonicity on the price timestamp watermark based on submitted feeds from arbitrary callers. Either: (1) validate freshness solely based on `stacks-block-time - ts <= max-staleness` without requiring `ts >= prev` against a globally-shared, caller-writable watermark, or (2) if monotonicity must be preserved to prevent price rollback attacks, decouple it from the caller-supplied bundle path used for legitimate operations, e.g. only update `last-update` via a dedicated, rate-limited or permissioned price-push path, and let `price-resolve` accept any Pyth-verified, non-stale price regardless of whether a "fresher" one was already seen in the same block.

### Proof of Concept
1. Attacker monitors for an upcoming Pyth price publish for asset `X` and observes Victim has prepared (fetched off-chain) a signed price update `P1` with `publish-time = t1`, still within `max-staleness` of the current block.
2. Attacker fetches (or already has) a newer signed update `P2` with `publish-time = t2 > t1` for the same feed, and calls any cheap market function (e.g., `repay` or `borrow` with a trivial amount) bundling `P2` in `price-feeds`.
3. Attacker's transaction lands first in the block: `write-feed` verifies and stores `P2`; `price-resolve` executes `oracle-timestamp-fresh(t2, prev, max-staleness)` → true (since `prev <= t2`), and sets `last-update[{type,ident}] = t2`.
4. Victim's transaction (containing `P1`, `publish-time = t1 < t2`) is then processed: `oracle-timestamp-fresh(t1, t2, max-staleness)` fails the `ts >= prev` check → `price-resolve` returns `ERR-ORACLE-INVARIANT` → Victim's `withdraw-collateral`/`borrow`/`repay`/`liquidate` call reverts.
5. Attacker repeats this in subsequent blocks whenever Victim tries again, sustaining the DOS against that specific user/operation at negligible cost.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
