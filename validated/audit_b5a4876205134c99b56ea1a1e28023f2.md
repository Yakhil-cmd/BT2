### Title
Unbounded per-account iteration in `DeleteAccount`/`DeleteKey` gas-key cleanup can consume unbounded gas/compute in a single receipt - ([File: runtime/runtime/src/access_keys.rs](), [File: core/store/src/utils/mod.rs]())

### Summary
`delete_gas_key` in `runtime/runtime/src/access_keys.rs` and `remove_account` in `core/store/src/utils/mod.rs` both contain loops whose iteration count is proportional to the number of gas-key nonces / access keys / contract-data entries an attacker-controlled account has accumulated, with no hard cap enforced at the point these functions are invoked from `DeleteKey`/`DeleteAccount` action execution.

### Finding Description
`delete_gas_key` loops `for i in 0..gas_key_info.num_nonces { remove_gas_key_nonce(...) }` to remove every nonce slot associated with a gas key when that key is deleted [1](#0-0) . Similarly, `remove_account` iterates over the full set of trie entries under the access-key prefix and under the contract-data prefix for the account being deleted, converting each into an individual per-key removal operation [2](#0-1) [3](#0-2) . `compute_gas_key_balance_sum` likewise iterates the full access-key prefix for an account to sum gas-key balances [4](#0-3) .

These loops are directly analogous to the reported `Pool.totalAssets()`/`Pool.onGoingLoans()` bug class: an unbounded loop whose length is attacker-influenced (number of access keys / gas keys / gas-key nonces / contract-data entries a single account can accumulate) is executed synchronously inside receipt/action processing, which is reachable from an ordinary account submitting `AddKey`, `DeleteKey`, or `DeleteAccount` actions.

Unlike the reported Solidity bug, NEAR's runtime does apply compute/gas accounting per removed item (`storage_removes_compute` in `delete_gas_key`, and general storage-usage/compute charges elsewhere), so the primary risk is not "free" execution but that a single receipt/action could take much longer wall-clock/IO time than its declared gas would suggest, if the number of keys/nonces an account can hold is not otherwise capped. I was not able to conclusively verify, within the available index, whether there is a hard protocol-level limit on the total number of access keys, gas keys, or gas-key nonces a single account may hold (e.g., via `max_number_of_access_keys` or storage-staking limits) that would bound these loops before they are invoked from `action_delete_key`/`action_delete_account`. If no such limit exists or if it is set very high relative to per-item storage cost, the loop length could still grow large enough to cause a chunk-level slow-down for a bounded gas cost.

### Impact Explanation
If the number of gas-key nonces/access keys/contract-data entries per account is unbounded (or bounded only by storage-staking economics rather than an explicit small limit), an attacker can grow one account's key/nonce count over time and then trigger `DeleteKey` or `DeleteAccount`, forcing the runtime to perform a large number of trie removals and compute-cost calculations within a single receipt's synchronous execution. This does not directly cause underpriced execution (compute is charged per removal), but it could translate into disproportionate wall-clock/IO cost per unit of declared compute, a chunk-processing slowdown, or, in the worst case if the per-item compute charge under/over-estimates actual trie removal cost, a resource-exhaustion / chunk-application-slowdown vector affecting all validators applying that chunk.

### Likelihood Explanation
Likelihood is moderate-to-low: the attacker must first pay storage-staking costs to accumulate many keys/nonces on one account (each `AddKey`/`TransferToGasKey`/nonce slot has an associated storage cost), so the attack is not free, and reaching the report's described "DoS via unbounded loop" would require either an absence of a per-account cap on access keys/gas-key nonces or a very high cap combined with mispriced per-item compute cost. I could not fully confirm the existence/value of such a cap from the indexed files, which limits confidence in likelihood.

### Recommendation
1. Verify and, if necessary, introduce an explicit protocol-enforced maximum on the number of access keys / gas-key nonces / contract-data entries that a single account can accumulate, independent of storage-staking cost, to bound the work done by `remove_account`, `delete_gas_key`, and `compute_gas_key_balance_sum` in the worst case.
2. Ensure the compute/gas cost charged per removed access key / gas-key nonce / contract-data entry in `delete_gas_key` and `remove_account` accurately reflects the true trie-removal cost (including deep trie proof costs), so that compute limits (rather than an unbounded loop) are the effective bound on execution time.
3. Consider making `DeleteAccount`/`DeleteKey` cleanup incremental (spread across multiple receipts, akin to how delayed receipts are processed) if very large accounts are possible, rather than a single synchronous loop.

### Proof of Concept
Conceptual scenario (not confirmed against a hard per-account key/nonce cap, which I could not verify in the indexed code):
1. Attacker account repeatedly submits `AddKey` actions creating gas keys with the maximum allowed `num_nonces`, and/or repeatedly writes contract-data entries, paying the associated storage-staking deposit each time.
2. Once a large number of access keys / gas-key nonces / contract-data entries exist on the account, attacker submits a single `DeleteKey` (for a gas key with many nonces, hitting `delete_gas_key`'s loop at `runtime/runtime/src/access_keys.rs:115-117`) or `DeleteAccount` action (hitting `remove_account`'s loops at `core/store/src/utils/mod.rs:497-530` and `538-555`).
3. The single receipt executing this action performs O(n) trie removals and compute-cost computations, where n is attacker-controlled and only bounded by whatever storage-staking economics or protocol limits exist — which this report could not fully confirm.

pub fn compute_gas_key_balance_sum(
    state_update: &TrieUpdate,
    account_id: &AccountId,
) -> Result<Balance, StorageError> {
    let mut total = Balance::ZERO;
    let lock = state_update.trie().lock_for_iter();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if nonce_index.is_some() {
            continue;
        }
        if let Some(balance) = get_access_key_by_handle(state_update, account_id, &key_handle)?
            .as_ref()
            .and_then(|access_key| access_key.gas_key_info())
            .map(|gas_key_info| gas_key_info.balance)
        {
            total = total.checked_add(balance).ok_or_else(|| {
                StorageError::StorageInconsistentState("gas key balance overflow".to_string())
            })?;
        }
    }
    Ok(total)
}
