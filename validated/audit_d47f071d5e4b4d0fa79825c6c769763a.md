### Title
Attacker-supplied swap route injects arbitrary contract calls into the victim's signed auth tree, draining wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The CVE-2022-45639 class — untrusted input reaching a command-execution sink — maps onto XOXNO Lending's strategy swaps: the `swap`/`swap_xdr` bytes a caller passes to `swap_collateral`, `swap_debt`, `repay_debt_with_collateral` and `multiply` are forwarded verbatim to the swap aggregator, which calls whatever pool addresses the payload names with no allowlist. A rogue "pool" in that route can invoke `token.transfer(victim, attacker, amount)` while the victim's `require_auth` context is live; Soroban's recording mode folds that transfer into the victim's simulated authorization tree, and the host executes it once the victim signs that tree. The test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates end-to-end theft of an unrelated wallet token.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` passes the caller-supplied `StrategySwap` (`swap: Bytes` on `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply`, `contracts/controller/src/lib.rs:283-303`, `258-278`, `311-333`, `225-253`) straight to `router.execute_strategy(&controller, &amount_in, swap)` at line 37. The controller constrains only its own grant: one `authorize_transfer_as_current` for `amount_in` (line 34), balance-delta overspend/output checks (lines 42-54). Nothing restricts which contract addresses the route invokes.

The router calls payload-named pool addresses directly, keeping no allowlist (`docs/explanation/threat-model.md:154-165`). Soroban non-root authorization means any `require_auth`-protected call a route contract makes below the caller's entry — e.g. `token.transfer(victim, attacker, x)` — is recorded as a child of the victim's authorization during `simulateTransaction` and executes in enforcement mode once signed. The harness proves this: `UnlistedPoolRouter.execute_strategy` invokes the payload-named `hop_pool`, and `RogueHopPool.swap` performs `token::Client::transfer(&victim, &to, &amount)` (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:39-72`). `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` (lines 195-227) shows the recorded auth tree contains exactly the theft transfer as a child of `swap_collateral`, Alice's `wallet_token` balance goes to zero and the attacker's to `WALLET_BALANCE`; `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` (lines 229-269) confirms the signed poisoned tree executes the theft.

### Impact Explanation
Theft of user funds: any token in the victim's wallet — including assets never listed by the protocol — can be transferred to the attacker. The loss is unbounded by `amount_in`, the payload `min_out`, or the controller's post-swap solvency gate, because the stolen transfer never touches routed funds. It applies to every strategy entrypoint that takes route bytes (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`) and to direct router users.

### Likelihood Explanation
The victim must sign a transaction whose simulated auth tree contains the rogue transfer. That tree is produced automatically by `simulateTransaction`; standard wallet/signing flows submit the simulated auth verbatim and do not render sub-invocation children for user review. An attacker who can serve or inject a route (malicious quote source, compromised route API, phishing UI) gets the theft signed as a side effect of an otherwise fair-priced swap — the route pays fair output, so all on-chain checks pass. This requires victim interaction (signing a swap), so it is not fully unilateral, but no privileged role, key compromise, or contract flaw beyond the missing venue allowlist is needed. Severity: High.

### Recommendation
- Constrain route execution to an on-chain venue/pool allowlist (or a registry hash of approved pool WASM/addresses) so a payload cannot name arbitrary contracts.
- Alternatively or additionally, enforce in `swap_tokens` that the router's execution cannot grow the caller's authorization tree — e.g. have the controller invoke the router with invoker-contract auth only for the exact input transfer and document that any payload causing additional `require_auth` children must revert.
- At the client layer, decode `routeXdr` and reject any simulated auth tree with children other than the single input `token_in.transfer` (the threat model already prescribes this; enforce it in the reference SDK path).

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:
1. Alice supplies 10,000 USDC and holds `WALLET_BALANCE` of an unlisted token.
2. Attacker deploys `RogueHopPool` initialized with `(victim=Alice, token=wallet_token, to=attacker, amount=WALLET_BALANCE)` and crafts a `RoutedSwap` whose `hop_pool` is that contract.
3. Alice calls `swap_collateral(alice, account_id, USDC, 50e9, ETH, route)`. The router pulls the input, `env.invoke_contract(&route.hop_pool, "swap", …)` executes `token.transfer(alice → attacker, WALLET_BALANCE)`, then pays fair ETH output.
4. Recording mode produces an auth tree for Alice whose only child is the theft transfer (asserted at lines 214-222); signing it executes the theft (lines 265-268). Alice's wallet token balance becomes 0, the attacker's becomes `WALLET_BALANCE`, and the swap itself still settles normally.
