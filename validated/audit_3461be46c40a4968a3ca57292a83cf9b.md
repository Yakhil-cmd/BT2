## Confirmed Analog Vulnerability

### Title
Webhook signature is verified against the `organization` field of the payload while the `repository.full_name` field used to select the Stack to mutate is never bound to that organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This maps to the reported bug class ("a value the code trusts/acts on is not actually covered by the check that is supposed to gate it") onto Shipit's webhook trust boundary: the organization used to pick the HMAC secret for signature verification is not cryptographically or logically bound to the `repository.full_name` that the handlers subsequently use to look up and mutate a `Stack`.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/secret to verify against using `repository_owner`, which is read straight out of the untrusted JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves per-organization configuration (used in the documented "multiple GitHub Applications" setup), each with its own independent `webhook_secret`: [3](#0-2) [4](#0-3) 

Once the signature check passes (using the secret belonging to whichever organization `repository.owner.login`/`organization.login` claims to be), the actual event handlers never re-check that binding. They instead take `repository.full_name` from the same untrusted body and use it directly to find the `Repository`/`Stack` record to act on: [5](#0-4) [6](#0-5) [7](#0-6) 

The binding that should hold is:
`organization authenticated by verify_signature == owner(repository.full_name) acted on by Handler#stacks`

Nothing in the code enforces `repository.owner.login == owner(repository.full_name)`. `repository_owner` (used only to pick the secret) and `repository.full_name` (used to select the target `Stack`) are two independently attacker-controlled JSON fields inside the same raw body; the HMAC only proves that *some* secret-holder produced *that whole body*, not that the secret-holder's organization matches the repository being written.

### Impact Explanation
In an installation using the documented multi-organization schema (`config/secrets.yml` with distinct `webhook_secret` per organization — the exact case shown in `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`), an actor who legitimately controls (or has compromised) one onboarded organization's GitHub App/webhook secret can sign an arbitrary payload with `organization.login`/`repository.owner.login` set to their own org (so `verify_signature` passes), but with `repository.full_name` set to a *different* onboarded organization/repository's stack. Because `PushHandler`, `StatusHandler`, etc. only trust `repository.full_name` to resolve the `Stack`, this lets that actor:
- Trigger `sync_github`/deploy-eligibility state changes (`PushHandler`) on a stack belonging to a repository/org they were never granted webhook trust for, and
- Forge commit statuses (`StatusHandler#process` calls `Commit#create_status_from_github!` keyed only on `sha`, with no repository/organization scoping at all) that can flip CI/status gates used by the merge queue and deploy-eligibility checks (`StatusChecker`, `MergeRequest#reject_unless_mergeable!`) for any stack across the whole installation.

This is a cross-repository write driven by a webhook credential that was never actually verified against the repository it operates on, matching the "cross-repository writes" / unauthorized deploy-gate manipulation impact bar.

### Likelihood Explanation
Requires the attacker to already hold a valid webhook secret for at least one organization onboarded to the Shipit instance (a credential explicitly excluded as an assumption for most other findings, but here it's the exact credential being abused *outside its intended scope*). Given any installation running the "Using Multiple Github Applications" configuration with several organizations behind one Shipit instance — the pattern the codebase explicitly supports and ships test fixtures for — this is directly reachable with a crafted HTTP POST to `/github/webhooks` (no GitHub redelivery UI needed, since the attacker can compute the HMAC themselves). Likelihood is High for multi-org deployments and not applicable to single-org deployments (where `repository_owner` is moot and effectively the same secret governs everything).

### Recommendation
After `verify_signature` succeeds, re-derive the authenticated organization and assert it equals the owner segment of `repository.full_name` (and of `organization.login`) before any handler runs; alternatively, scope every `Repository.from_github_repo_name` / `Commit.where(sha:)` lookup used by webhook handlers to require `owner == verified_organization`, rejecting (422) any payload where they diverge.

### Proof of Concept
1. Operator configures Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. Attacker legitimately controls `OrgA`'s GitHub App webhook secret (e.g., as an admin of `OrgA`'s installed app).
3. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha already known to Shipit>",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` and POSTs to `/github/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: 'OrgA')` (from `repository.owner.login`), verifies successfully.
6. `PushHandler#process` resolves `Repository.from_github_repo_name('OrgB/victim-repo')` and calls `stack.sync_github(expected_head_sha: ...)` on `OrgB`'s stack, even though the signature only proves trust from `OrgA`.

Note: the exact `checked webhook_secret model resolution path` (`Shipit.github`) and handler dispatch (`Shipit::Webhooks.for_event`) were directly read from the engine source; the multi-tenant deployment scenario itself (two orgs sharing one Shipit instance) is a documented, supported configuration (`docs/setup.md`) rather than something observed at runtime, so real-world exploitability depends on that configuration being in use.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
