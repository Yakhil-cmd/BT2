### Title
No mechanism to cancel or reclaim funds for stuck Snowbridge V2 outbound Polkadot→Ethereum messages - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`pallet-snowbridge-outbound-queue-v2` accepts an upfront fee for every Polkadot→Ethereum message and stores it in a `PendingOrders` map keyed by nonce. The only path that ever removes an entry from `PendingOrders` and pays out the escrowed fee is `submit_delivery_receipt`/`process_delivery_receipt`, which requires a valid, proven Ethereum event log for that specific nonce. There is no extrinsic, governance call, or timeout mechanism that lets the original sender (or anyone) cancel a pending order and reclaim the fee if the corresponding Ethereum-side event is never produced/relayed. This is the same class of bug as the Kakarot finding: a user-paid cross-chain message fee can become permanently unrecoverable because the protocol only offers a "complete" path, never a "cancel" path.

### Finding Description
A normal, permissionless user flow (as exercised in the emulated tests) is:
1. User calls `pallet_xcm::execute` with `WithdrawAsset` / `PayFees` / `InitiateTransfer { destination: ethereum(), remote_fees: ... }`, as shown in `cumulus/parachains/integration-tests/.../snowbridge_v2_outbound.rs` (`send_weth_from_asset_hub_to_ethereum`, lines 44-123).
2. This is routed through `EthereumBlobExporter`/`SnowbridgeExporterV2` to `OutboundQueue::validate`/`deliver` (`bridges/snowbridge/pallets/outbound-queue-v2/src/send_message_impl.rs`), which enqueues the message via `MessageQueue`.
3. When the `MessageQueue` processes the message, `Pallet::do_process_message` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:379-466`) assigns a `nonce`, stores the message, and creates a `PendingOrder { nonce, fee, block_number }` in `PendingOrders` [1](#0-0) . The `fee` value already represents value that has left the user's control on the Polkadot side (via the XCM `remote_fees` withdrawal on AssetHub/BridgeHub).
4. The **only** call that consumes a `PendingOrders` entry is `submit_delivery_receipt` → `process_delivery_receipt`, which requires `T::Verifier::verify` to accept a real Ethereum event-log proof for that nonce before the order is removed and the fee paid out (always to a relayer/reward account, never back to the original sender) [2](#0-1) .
5. There is no `cancel_order`, no timeout-based expiry, and no governance-triggered refund path anywhere in the pallet's `Call` enum (only `submit_delivery_receipt` exists, at `pallet::call_index(1)`) [3](#0-2) .

If the Ethereum side never processes the message and emits the expected event (e.g., the Ethereum Gateway contract is paused, upgraded incompatibly, runs out of relayer interest because the reward is too low, or the BEEFY/light-client `Verifier` becomes permanently unable to produce a valid proof for that block range), the `PendingOrder` for that nonce remains in storage forever, and the escrowed fee is never returned to the user and never paid to anyone. The repository's own test suite already documents this exact class of stuck-state behavior: `poc_m1` and `submit_delivery_receipt_succeeds_after_unhalt` in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs:437-496` show that `submit_delivery_receipt` fails and the order is left untouched while `VerifierHalted` is true [4](#0-3) ; unlike the halted-verifier case (which is reversible by governance unhalting), there is no equivalent mechanism at all for the broader case where the Ethereum-side event simply never materializes or is never relayed, independent of halted status.

The `AddTip` implementation (`add_tip`, lines 506-518) only allows *increasing* the fee on an existing pending order to incentivize a relayer — it provides no way to decrease, cancel, or reclaim the escrowed value [5](#0-4) .

### Impact Explanation
This is an availability/fund-recovery gap rather than a direct theft: user-paid remote/relayer fees (and potentially the entire cross-chain transfer's fee budget) for a Polkadot→Ethereum message can be permanently locked in the `PendingOrders` map with no code path to ever recover them if delivery/execution on Ethereum never completes or is never proven. Given real-world scenarios (Ethereum Gateway contract paused by Snowbridge governance for extended maintenance, chronically low relayer interest for underpriced messages, or long-tail light-client verification failures), this can realistically occur without any malicious actor, and there is no automatic or manual remediation for affected users. This is analogous in severity/impact to the original Kakarot Medium finding — a legitimate design gap resulting in unrecoverable escrowed fees, not a full protocol break.

### Likelihood Explanation
Likelihood is moderate: it requires a persistent failure/non-delivery of the corresponding Ethereum-side transaction or light-client proof (halting is one of several possible triggers), which is plausible given real operational conditions of a live bridge (contract pauses, low relayer profitability, light-client sync issues) but is not attacker-triggerable at will from an ordinary EOA without cooperation of external factors on the Ethereum side. No privileged role or malicious relayer/validator action is required for the loss to manifest — it is a missing recovery path, not an exploit requiring an active adversary.

### Recommendation
Introduce a bounded cancellation/refund mechanism for `PendingOrders` entries, e.g.:
- Add a `cancel_stale_order(nonce)` extrinsic (permissionless or restricted to the original sender/claimer) that can be called once `block_number + T::CancellationDelay::get() < current_block_number` and no delivery receipt has been submitted, refunding the escrowed fee back to the original sender (or to a claimer address recorded in the order).
- Alternatively, allow governance (`OperatingMode`-style) to trigger a batch refund of pending orders older than a threshold when the bridge is halted for an extended period.
- Record enough information in `PendingOrder` (e.g., original payer/refund account) to support this, since currently only `nonce`, `fee`, and `block_number` are stored [6](#0-5) .

### Proof of Concept
Program/severity rationale: This targets the live Snowbridge V2 outbound-queue pallet (`snowbridge-pallet-outbound-queue-v2`), which is deployed/deployable on Bridge Hub runtimes (e.g. `bridge-hub-westend`) as shown by its wiring in `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-westend/src/bridge_to_ethereum_config.rs` and exercised end-to-end in `cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_outbound.rs`.

Failed guard demonstrated in-repo: `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs::poc_m1` (lines 437-463) shows `submit_delivery_receipt` rejected with `Error::Verification(VerificationError::Halted)` while the `PendingOrder` (fee = 1_000_000) remains in storage, unrecoverable through any other call in the pallet:
```rust
set_verifier_halted(true);
assert_noop!(
    OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
    Error::<Test>::Verification(VerificationError::Halted)
);
let order_after = PendingOrders::<Test>::get(nonce).expect("order still present");
assert_eq!(order_after.fee, fee);
```
This confirms the `PendingOrder` cannot be settled through any path except a successful `submit_delivery_receipt`, and no cancellation/refund extrinsic exists in the pallet's `#[pallet::call]` block (only `submit_delivery_receipt` is defined) to unwind the order and return funds when that path is permanently blocked. The companion test `submit_delivery_receipt_succeeds_after_unhalt` shows the halted case is only recoverable because governance can restore the verifier — no such recovery exists for the broader case of an Ethereum-side event that simply never occurs (Gateway paused/reverted/no relayer interest) while the verifier itself remains healthy. Deployment evidence and reachability from a normal signed user (`pallet_xcm::execute` with `InitiateTransfer` to `ethereum()`) are documented above and in the cited integration tests; execution of the cited existing test harness (`poc_m1`) is part of the repository's existing `#[test]` suite and was not independently re-executed in this analysis.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
