### Title
`multiply`/`swap_debt` charge the live `flashloan_fee` with no caller-supplied fee bound — a queued `UpdateParams` execution landing before the user's transaction raises the strategy origination fee the user signed for - (File: contracts/controller/src/strategies/multiply.rs)

### Summary
The strategy debt-mint path reads `flashloan_fee` from market params at execution time (`contracts/pool/src/ops/strategy.rs:94-100`), and neither `process_multiply` (`contracts/controller/src/strategies/multiply.rs:33`) nor `borrow_into_controller` (`contracts/controller/src/positions/debt.rs:260`) accepts an expected/max fee. `MultiplyParams` (`multiply.rs:19-29`) carries no `believedFee`/`max_fee` field. Governance `update_params` operations become executable by any address once ready, so a fee increase (up to `MAX_FLASHLOAN_FEE_BPS = 500`) can be included between the user's signing simulation and inclusion — the same collision class as `KnightingRound.buy` vs `setTokenOutPrice`. The strongest shape is `PositionMode::Multiply` with the same underlying asset in two hubs: `collateral != debt` as `HubAssetKey` satisfies `validate_multiply_request` (`multiply.rs:136-150`) while `swap_tokens_or_passthrough` lets the route pass through unchanged (`multiply.rs:90-97`), so the router's `min_out` slippage check cannot bound the fee either.

### Finding Description
`borrow_into_controller` calls `pool_create_strategy_call(..., charge_fee = true)` and returns the measured receipt net of the fee (`debt.rs:280-294`). The pool computes `fee = half_up(amount * flashloan_fee / BPS)` from live params (`ops/strategy.rs:90-100`), credits it to protocol revenue, and transfers `amount - fee`. Debt is minted on the gross `amount` (`ops/strategy.rs:70`), so the user's obligation is unchanged while the swapped/supplied collateral shrinks by the fee delta. No argument on the `multiply` or `swap_debt` entrypoint lets the caller pin the fee they simulated. The same gap exists on the cash `flash_loan` path (`ops/flash.rs:107-121`), where repayment is `amount + fee` read live, though that path is safer in practice since the receiver's own callback can price the repayment.

### Impact Explanation
A user who simulates `multiply` at `flashloan_fee = 0` (or 9 bps) and whose transaction lands after a ready `UpdateParams` raising the fee to 500 bps ends a successful, risk-passing transaction with ~5% less collateral for the same gross debt — the delta is booked as protocol revenue (`interest::add_protocol_revenue`, `ops/strategy.rs:72-73`). `strategy_finalize` only enforces the final health factor, so a position that remains solvent succeeds despite the worse economics. This is a direct, involuntary transfer of up to `MAX_FLASHLOAN_FEE_BPS` of the borrowed principal's value from the user to suppliers, matching the "user buys at a price they were not aware of" impact class.

### Likelihood Explanation
Requires a governance `UpdateParams` operation changing `flashloan_fee` to be ready and executed in the same ledger window as the victim's `multiply`/`swap_debt`. Governance delays make pure accidents uncommon, but the executor of a ready operation is permissionless, and there is no on-chain ordering protection — the cost is borne entirely by whichever strategy transactions race the execution. Bounded at 5% of principal keeps it at Medium, not High.

### Recommendation
Add a caller-supplied bound to the strategy entrypoints, e.g. `max_fee_bps: u32` (or `min_amount_received: i128`) in `MultiplyParams` and the `swap_debt` parameters, and assert `cache.params().flashloan_fee <= max_fee_bps` (or `amount_received >= min_amount_received`) after `borrow_into_controller`. For the passthrough multiply leg this is the only protection available; for routed legs, document that a tight router `min_out` already covers the fee indirectly.

### Proof of Concept
1. Market (hub A, XLM) has `flashloan_fee = 0`; market (hub B, XLM) accepts supply.
2. Governance queues `UpdateParams` setting (hub A, XLM) `flashloan_fee = 500`; the delay elapses.
3. Alice simulates and signs `controller.multiply(caller=alice, account_id, spoke_id, collateral=(hubB,XLM), debt_to_flash_loan=1_000 XLM, debt=(hubA,XLM), mode=Multiply, swap=passthrough, initial_payment=None, convert_swap=None)`. `validate_multiply_request` passes because the `HubAssetKey`s differ (`multiply.rs:138`).
4. An unprivileged caller executes the ready governance operation; Alice's tx lands next.
5. `compute_fee` now returns 50 XLM (`ops/strategy.rs:98`); the pool mints debt on the full 1,000 XLM but transfers only 950; `swap_tokens_or_passthrough` supplies 950 XLM of collateral.
6. Alice's account holds 1,000 XLM debt against 950 XLM collateral from this leg (plus her other collateral keeps HF ≥ 1 so `strategy_finalize` passes). She lost 50 XLM-equivalent of expected position value to protocol revenue with no parameter to have prevented it.

Uncertainty note: I confirmed `MultiplyParams` has no fee bound and that `compute_fee` reads live params, but I did not fully verify the `swap_debt` parameter struct or the exact governance `execute` signature — both follow the same `borrow_into_controller`/`create_strategy` path, so the class applies identically.
