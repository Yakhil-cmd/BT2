### Title
Cross-repository event forgery via mismatched `repository.owner.login` vs `repository.full_name` in webhook signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify a payload against using `repository_owner`, which reads `repository.owner.login` (or falls back to `organization.login`) from the JSON body. However, all event handlers derive the target repository/stack from a different field in the same payload — `repository.full_name` — via `Handler#repository_name`. Because these two fields are never cross-checked against each other, an org that legitimately owns a valid webhook secret in a multi-tenant Shipit deployment can sign a payload whose `owner.login` matches their own org (satisfying signature verification) while `full_name` points at a repository/stack belonging to a completely different, victim organization.

### Finding Description
Shipit supports configuring multiple GitHub Apps, one per organization, each with its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which app/secret to validate the HMAC signature against solely based on `repository_owner`: [2](#0-1) 

`repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — a value fully controlled by the sender of the webhook body. Once the signature check passes, `WebhooksController#create` dispatches the entire raw payload to the registered handlers for the event type [3](#0-2) .

Every handler, however, resolves the actual repository/stack to act on using a different key in the same payload — `repository.full_name` — via the shared base class: [4](#0-3) 

Because `verify_signature` never checks that `repository.owner.login` is consistent with `repository.full_name`'s owner, the field that authorizes the signed request (`owner.login`) is not the field that is actually acted upon (`full_name`). This is the equality that is broken: `organization authenticated by signature == organization written by handlers` does not hold. An org administrator who legitimately owns a GitHub App/webhook secret configured in Shipit's multi-org setup (per `docs/setup.md`'s "Using Multiple Github Applications" section) can:
1. Compute a valid HMAC-SHA1 signature over an arbitrary JSON body using their own known `webhook_secret`.
2. Set `repository.owner.login` (or `organization.login`) to their own org login so `verify_signature` looks up and validates against their own app's secret.
3. Set `repository.full_name` to `"<victim-org>/<victim-repo>"`, an unrelated repository/stack that the attacker does not own or control.

The signature check passes (correct secret for the attacker's own org), and the handler layer processes the event as if it legitimately originated from the victim repository, because it only reads `full_name`.

### Impact Explanation
Depending on the event type dispatched (`push`, `status`, `check_suite`, `pull_request`, etc.), this allows an attacker who administers only their own organization's GitHub App integration to inject forged GitHub events for a victim organization's stacks — e.g., forging `push` events that trigger `GithubSyncJob` for the victim stack, or forging `status`/`check_suite` events that alter deployability/merge state for repositories the attacker has no access to. This is a cross-repository write/state-manipulation primitive: an entity authenticated for org A is able to cause writes against org B's stack records, which matches the "cross-repository writes" / "unauthorized deploy" impact class, since manipulated CI/check/status state can feed into merge-queue and deploy decisions for stacks the attacker does not control.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration), and requires the attacker to control (or administer) at least one such org with its own valid webhook secret — a plausible position for a "participating but distrusted" tenant organization in a multi-org Shipit deployment. No repository write access, API token, or session is needed; only knowledge of one's own org's configured webhook secret, which the rules explicitly permit as an unprivileged-attacker capability (crossing the organization-authenticated vs. repository-written binding).

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), validate that the organization used to select/verify the webhook secret is consistent with the owner embedded in `repository.full_name` before dispatching to handlers — e.g., reject the event if `repository.full_name.split('/').first != repository_owner` (case-insensitively). Alternatively, always derive the repository owner used for both signature selection and downstream repository resolution from the same, single field.

### Proof of Concept
Assume Shipit is configured with two orgs, `attacker-org` (attacker administers its GitHub App, secret `S_A`) and `victim-org` (stack `victim-org/victim-repo` exists in Shipit, secret `S_V` unknown to attacker).

1. Attacker builds payload:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "after": "<some-sha-on-victim-repo>"
}
```
2. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(S_A, raw_body)>` using their own known secret `S_A`.
3. Sends `POST /webhooks` with `X-Github-Event: push` and the above signature.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully against `S_A` [5](#0-4) .
5. `create` dispatches the parsed body to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` [6](#0-5) , causing Shipit to act on the victim's stack based on an attacker-forged event, despite the signature only proving authenticity for `attacker-org`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
