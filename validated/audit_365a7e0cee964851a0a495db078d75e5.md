### Title
Membership webhook `find_or_create_team!` looks up teams by `github_id` only, letting a validly-signed webhook from any organization add members to another organization's `Team` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#process` resolves the target `Team` solely via `Team.find_or_create_by!(github_id: params.team.id)`, with no check that the organization verified by `verify_webhook_signature` matches the `organization` column stored on the found `Team`. An attacker who controls a legitimately-installed org (`attacker-org`) can send a validly-signed `membership` webhook naming an arbitrary existing victim team's numeric `github_id`, causing `team.add_member(member)` to add an attacker-chosen `User` to that victim team.

### Finding Description
The broken binding is: `verified_organization (repository_owner used to select the webhook_secret in WebhookController#verify_signature) == team.organization (stored on the Team record ultimately mutated by team.add_member)`.

- `WebhooksController#verify_signature` derives `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and looks up the `GitHubApp` for that organization to validate `X-Hub-Signature` against that org's own `webhook_secret` [2](#0-1) . For a `membership` payload there is no `repository` key, so `repository_owner` resolves to `params.organization.login`, i.e., the attacker's own org, `attacker-org`, which the attacker legitimately controls and for which the signature check passes.
- `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [3](#0-2) . The lookup key is `github_id` alone — it is not scoped by `organization`. If a `Team` row with that `github_id` already exists (e.g., a real victim team previously created via a legitimate webhook from `victim-org`), the block is never run and the existing record — with its real `organization: 'victim-org'` — is returned unchanged.
- `process` immediately does `team.add_member(member)` for `action == 'added'`, where `member = User.find_or_create_by_login!(params.member.login)` is an attacker-supplied string [4](#0-3) , and `Team#add_member` simply appends the member to `members` [5](#0-4) . At no point is `team.organization` compared to the organization that was actually verified for this request.

Attacker request: `POST /webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with the webhook secret configured for `attacker-org` (which the attacker controls, having installed the app there), and body:
```json
{"action":"added","team":{"id":<victim_team_github_id>,"name":"x","slug":"x","url":"https://x"},"organization":{"login":"attacker-org"},"member":{"login":"attacker-controlled-user"}}
```
`<victim_team_github_id>` is the numeric GitHub team ID of a team already tracked by Shipit for `victim-org` (obtainable from the GitHub org/teams API or the org's public team page, or simply known from prior interaction). This request passes signature verification (it's genuinely signed for `attacker-org`), then finds the pre-existing victim `Team` row purely by `github_id` and appends the attacker's chosen user to it.

None of the existing guards prevent this: `verify_signature` only proves the request came from a party who controls `attacker-org`'s secret, it says nothing about which `Team` row may be mutated; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not organizational scoping; there is no model validation tying `Team#organization` immutably to the requesting organization on subsequent lookups.

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization (High/Critical category per the rubric): if `victim-org`'s team is one of the teams referenced by `Shipit.github_teams` for granting deploy/merge/oauth permissions, the attacker's chosen `User` becomes a member of that team via `Membership`, gaining whatever authorization is derived from team membership — without ever authenticating as, or being invited by, `victim-org`. The attack is repeatable against any tracked `Team` whose numeric `github_id` the attacker can learn, is not limited to `attacker-org`'s own resources, and crosses tenant boundaries entirely within this engine's webhook-handling code.

### Likelihood Explanation
Preconditions are modest: the attacker needs an org where the Shipit GitHub App/webhook is legitimately installed (so they know/control that org's webhook secret) and the target victim `Team`'s numeric `github_id`, which is not a secret — GitHub team IDs are visible via the public/authenticated Teams API and appear in GitHub UI links; an attacker with any visibility into the victim org (e.g. former member, public org) can obtain it. No Shipit session, API token, or GitHub App private key of the victim's is required. The request is a single crafted, signed HTTP POST and is fully repeatable.

### Recommendation
Scope the `Team` lookup by the verified organization, not `github_id` alone, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally verify in `MembershipHandler#process` that the found team's `organization` matches the organization actually verified by `verify_webhook_signature` (`repository_owner`) before performing `add_member`/`members.delete`, rejecting/logging mismatches instead of silently operating on a cross-organization team.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership webhook signed for attacker-org cannot add members to a victim-org team sharing the same github_id" do
  victim_team = Shipit::Team.create!(github_id: 555, organization: 'victim-org', name: 'Victim', slug: 'victim', api_url: 'https://x')

  request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: 555, name: 'x', slug: 'x', url: 'https://x' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker-controlled-user' }
  }.to_json

  Shipit.github(organization: 'attacker-org').expects(:verify_webhook_signature).returns(true)

  assert_no_difference -> { victim_team.reload.members.count } do
    post :create, body: payload, as: :json
  end
end
```
Expected (buggy) behavior today: `victim_team.reload.members` gains `attacker-controlled-user` because `find_or_create_team!` finds `victim_team` by `github_id: 555` regardless of the verified `attacker-org` organization, demonstrating `verified_organization ('attacker-org') != team.organization ('victim-org')` while the mutation still proceeds.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      )

      ].join(' '))
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
