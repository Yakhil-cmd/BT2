### Title
Unbounded synchronous AA-trigger cascade processed under the global write lock can stall unit confirmation - ([File: writer.js])

### Summary
The Linux CVE fixes a soft lockup caused by processing an unbounded number of completion-queue events synchronously inside interrupt context, with no per-call cap and no yielding, so a heavy event burst can pin a CPU core indefinitely. The ocore analog is `saveJoint()` in `writer.js`, which stabilizes MCIs and executes Autonomous Agent (AA) triggers synchronously while holding the process-wide `["write"]` mutex, in a loop that can keep re-entering without ever releasing the lock back to the event loop for other unit processing.

### Finding Description
`saveJoint()` takes the global write lock before doing any work: `const unlock = objValidationState.bUnderWriteLock ? () => { } : await mutex.lock(["write"]);` [1](#0-0) . After a unit is committed and an MCI becomes stable, the function synchronously runs `aa_composer.handleAATriggers()` for the newly stabilized MCI and then enters a `while (true)` loop that repeatedly calls `main_chain.advanceMcStability()` and, for every additional MCI it stabilizes, calls `aa_composer.handleAATriggers()` again — all still under the same write lock, without releasing it back to other callers: [2](#0-1) .

`handleAATriggers()` itself loads *every* pending AA trigger row for that MCI and processes them one at a time with `async.eachSeries`, invoking `handlePrimaryAATrigger()` for each, which in turn runs the full AA formula-evaluation/response pipeline (`handleTrigger`) including unbounded secondary-trigger cascades: [3](#0-2) , [4](#0-3) .

Because an unprivileged unit poster can pay any number of outputs to AA addresses in a single unit or in many units within one MCI, and can compose or trigger AAs that recursively call other AAs (bounded per-trigger only by `MAX_RESPONSES_PER_PRIMARY_TRIGGER`, not bounded across the whole batch of primary triggers in a stabilized MCI), the number of primary/secondary trigger evaluations processed inside this single `saveJoint()` call — while the global write mutex is held — is effectively attacker-influenced and unbounded per MCI. This mirrors the kernel bug class exactly: work whose volume is controlled by an external, low-privilege actor is executed synchronously, without an upper bound and without yielding control, inside a section that blocks all other critical work (here, the ability of the node to accept and confirm other units, since nothing else can take the write lock until this synchronous chain completes).

### Impact Explanation
While the write lock is held, no other unit can be validated/written, effectively pausing confirmation of new units on that node. If the AA-trigger workload for a single stabilizing MCI (crafted by chaining/fan-out of triggers, each potentially spawning multiple secondary AA calls) takes long enough to process synchronously, the node's event loop is blocked for an extended period, degrading its ability to confirm new units — the exact impact class called out as acceptable in the validation criteria ("a network unable to confirm new units"). On witness/hub nodes this can meaningfully slow down consensus progress for all peers depending on that node.

### Likelihood Explanation
Triggering a large batch of AA calls is reachable by any ordinary unit poster: outputs to AA addresses, or AAs that recursively call other AAs, are standard, permissionless operations (`app: 'payment'`, `app: 'definition'`, trigger addresses). No special privileges, hub/peer compromise, or protocol violation are required — only paying to enough distinct AA addresses/response chains to be processed in the same stabilized MCI. The magnitude needed to cause a noticeable stall depends on network fee costs and existing per-response caps (`MAX_RESPONSES_PER_PRIMARY_TRIGGER`), which somewhat limits — but does not eliminate — the achievable batch size within one MCI, since that cap is per-primary-trigger, not per-MCI aggregate.

### Recommendation
- Impose a hard cap on the total amount of AA-processing work (number of primary triggers, cumulative responses, or wall-clock budget) executed synchronously per `handleAATriggers()` invocation, deferring the remainder to subsequent ticks/MCIs.
- Release and re-acquire the `["write"]` mutex between chunks of AA-trigger processing (or between stabilized MCIs in the `while (true)` loop in `writer.js`) so other pending unit validations/writes can interleave.
- Add telemetry/alerting on AA-trigger batch size and processing duration per MCI to detect abusive fan-out patterns early.

### Proof of Concept
1. Deploy several AA definitions that call each other in a fan-out/cascade pattern (A → B, C, D, ...; each of those → further AAs), respecting `MAX_RESPONSES_PER_PRIMARY_TRIGGER` per individual trigger chain.
2. From an ordinary wallet, post many units in the same MCI window that each send a small payment to a distinct top-level AA address, maximizing the number of independent primary triggers that will be inserted into `aa_triggers` for the same stabilizing MCI (see the trigger-collection query in `main_chain.js` `handleAATriggers`) [5](#0-4) .
3. Observe, on the node processing the stabilizing MCI, that `saveJoint()`'s synchronous `handleAATriggers()`/`while(true)` block [6](#0-5)  takes proportionally longer as the batch grows, and that other queued unit validations are delayed until the entire batch (and all secondary cascades) finishes, since the write lock is not released in between.

function handleAATriggers(onDone) {
	if (!onDone)
		return new Promise(resolve => handleAATriggers(resolve));
	mutex.lock(['aa_triggers'], function (unlock) {
		db.query(
			"SELECT aa_triggers.mci, aa_triggers.unit, address, definition \n\
			FROM aa_triggers \n\
			CROSS JOIN units USING(unit) \n\
			CROSS JOIN aa_addresses USING(address) \n\
			ORDER BY aa_triggers.mci, level, aa_triggers.unit, address",
			function (rows) {
				var arrPostedUnits = [];
				async.eachSeries(
					rows,
					function (row, cb) {
						console.log('handleAATriggers', row.unit, row.mci, row.address);
						var arrDefinition = JSON.parse(row.definition);
						handlePrimaryAATrigger(row.mci, row.unit, row.address, arrDefinition, arrPostedUnits, cb);
					},
					function () {
						arrPostedUnits.forEach(function (objUnit) {
							eventBus.emit('new_aa_unit', objUnit);
						});
						unlock();
						onDone();
					}
				);
			}
		);
	});
}

			"SELECT DISTINCT address, definition, units.unit, units.level \n\
			FROM units \n\
			CROSS JOIN outputs USING(unit) \n\

			LEFT JOIN assets ON asset=assets.unit \n\
			CROSS JOIN units AS aa_definition_units ON aa_addresses.unit=aa_definition_units.unit \n\
