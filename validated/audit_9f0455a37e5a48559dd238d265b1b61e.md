### Title
Unchecked user input in ad-hoc contract hash construction allows hash collisions between distinct contract terms - ([File: prosaic_contract.js], [File: arbiter_contract.js])

### Summary
`prosaic_contract.js` and `arbiter_contract.js` compute a contract's identifying `hash` by directly concatenating attacker-controlled free-text fields (`title`, `text`) with other contract fields using no delimiter (or a weak delimiter only for post-2026-11-01 contracts), instead of using the codebase's own safe serialization helper (`getSourceString`/`getJsonSourceString` in `string_utils.js`) that explicitly type-tags and rejects ambiguous separators. This mirrors the Swift CVE-2013-2161 bug class: unchecked/unescaped user input is embedded into a structured value that downstream code trusts as a unique, tamper-evident representation of the original content.

### Finding Description
`prosaic_contract.js` builds the contract hash like this: [1](#0-0) 

Both `getHash` and `getHashV1` simply concatenate `contract.title`, `contract.text`, and `contract.creation_date` with **no separator at all**. Because `title` and `text` are both free-form strings supplied by the contract offeror (an unprivileged device-paired counterparty), two different `(title, text)` pairs can produce the identical concatenated string (and therefore the identical SHA-256 hash) simply by shifting characters across the title/text boundary — e.g. `title="AB", text="CD"` and `title="A", text="BCD"` both concatenate to `"ABCD"`.

`arbiter_contract.js` has the same defect, and — critically — the "safe" delimiter-based branch is not yet active: [2](#0-1) 

`exports.NEW_HASH_DATE = '2026-11-01'` [3](#0-2)  — since the system date is currently before this cutoff, every contract created today falls into the vulnerable `contract.creation_date > exports.NEW_HASH_DATE ? ... : [...].join("")` **else** branch, which joins `title`, `text`, `payer_name`, `payee_name`, `amount`, `asset` with an empty string, again allowing boundary-shift collisions across all these attacker/peer-controlled string fields.

This is in stark contrast to the project's own generic hashing utility, `getSourceString`, which was specifically designed to prevent exactly this class of bug by type-tagging every value and rejecting embedded join characters: [4](#0-3) 

The contract hash is not cosmetic — it is used as the primary key (`hash`) for `prosaic_contracts` / `wallet_arbiter_contracts` records, is embedded in `contract_text_hash` inside a `data` message posted on-chain to prove mutual agreement, and — for arbiter contracts — is embedded directly into the oscript address definition as part of the data-feed subject name that gates fund release: [5](#0-4) 
and is used again when parsing the arbiter's dispute resolution: [6](#0-5) 

The integrity check that is supposed to bind the on-chain unit to the exact contract text relies solely on hash equality: [7](#0-6) [8](#0-7) 

Because the hash function is collision-prone by construction (not merely by brute-force preimage search, but by trivial, deterministic boundary-shifting of attacker-supplied strings), an attacker who is a party to the contract (or the arbiter, who also supplies/controls contract fields shown to the client) can construct two distinct `(title, text[, party_name, amount])` combinations that hash identically. This breaks the assumption — relied on throughout both modules — that `hash` uniquely and unambiguously identifies one specific set of contract terms.

### Impact Explanation
The contract hash is used as the shared secret binding: (a) the human-readable agreement text shown to both counterparties, (b) the on-chain `contract_text_hash` proof that both parties signed the same terms, and (c) for arbiter contracts, the exact name of the data-feed subject (`"CONTRACT_" + contract.hash`) that the shared multi-sig address's oscript definition checks to release funds to the dispute winner. Because the hash can collide across different contract terms, an unprivileged contract counterparty/arbiter can present one version of contract text in the UI/negotiation phase while the actual underlying attributes (e.g., party names, amounts as encoded in the hash source string) legitimately differ from what the victim believes was agreed, yet the wallet's collision-based hash check will report a match and treat the record as verified. Since the arbiter's fund-release condition is keyed by this same hash, contract-identity confusion of this kind directly touches the "AA fund loss/freezing" and "node disagreement on validity" categories called out in scope — the shared address's spend authorization ultimately depends on this collision-prone identifier.

### Likelihood Explanation
No cryptographic effort is required — the collision is a simple string-boundary shift over attacker-supplied `title`/`text` (and, for arbiter contracts prior to `NEW_HASH_DATE`, also `payer_name`/`payee_name`/`amount`/`asset`), fully controlled by one contract counterparty during contract creation/negotiation over the device-pairing channel — a reachable, unprivileged path (`createAndSend` → `getHash`/`getHashSrc`, sent as `prosaic_contract_offer`/`arbiter_contract_offer` device messages). This requires no network position, no leaked keys, and no privileged access — only participation as a contract counterparty, which is explicitly in scope.

### Recommendation
Replace the ad-hoc `title + text + creation_date` / `[...].join("")` / `[...].join(DELIMITER)` concatenations in `prosaic_contract.js` (`getHash`, `getHashV1`) and `arbiter_contract.js` (`getHashSrc`) with the project's existing type-safe serialization helper, `object_hash.getBase64Hash`/`string_utils.getSourceString` (or `getJsonSourceString`), which already type-tags each field and rejects embedded join characters, eliminating boundary-shift ambiguity. Additionally, retire or immediately activate the safe `DELIMITER`-based branch in `arbiter_contract.js` regardless of `creation_date`, since the vulnerable empty-string-join branch is presently the active code path for all newly created contracts.

### Proof of Concept
1. Attacker (contract offeror) calls `prosaic_contract.createAndSend` with `title = "AB"`, `text = "CD"+creation_date_string_prefix"`, producing `hash1 = SHA256("AB" + "CD" + creation_date)`.
2. Attacker constructs an alternate record with `title = "A"`, `text = "BCD"+creation_date_string_prefix`, i.e. the same concatenation `"A"+"BCD"+creation_date === "AB"+"CD"+creation_date`, yielding `hash2 === hash1` via `prosaic_contract.getHash` (`prosaic_contract.js:98-100`).
3. Both records validate identically against `payload.contract_text_hash !== contract.hash` in `handleReceivedSigningUnit` (`prosaic_contract.js:173`), letting the attacker substitute contract text/terms post hoc while the victim's client still treats the hash as proof of agreement to the originally shown text.
4. For arbiter contracts, the identical technique applies to `getHashSrc`'s active (pre-`NEW_HASH_DATE`) branch (`arbiter_contract.js:201`), and the resulting colliding `contract.hash` is embedded as the data-feed subject name gating fund release in the shared address definition (`arbiter_contract.js:475,479`), so the collision reaches the fund-release condition, not just a display artifact.

function parseWinnerFromUnit(contract, objUnit) {
	if (objUnit.authors[0].address !== contract.arbiter_address) {
		return;
	}
	var key = "CONTRACT_" + contract.hash;
	var winner;
	objUnit.messages.forEach(function(message){
		if (message.app !== "data_feed" || !message.payload || !message.payload[key]) {
			return;
		}
		winner = message.payload[key];
	});
	if (!winner || (winner !== contract.my_address && winner !== contract.peer_address)) {
		return;
	}
	return winner;
}
