### Title
Webhook signature verification selects the signing secret from an untrusted, unverified payload field, decoupling the authenticated GitHub organization from the repository actually acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-tenant Shipit deployment (multiple `GitHubApp`s configured, one per GitHub organization, as documented in `docs/setup.md` "Using Multiple Github Applications"), `WebhooksController#verify_signature` picks *which* organization's `webhook_secret` to validate the HMAC signature against by reading a field straight out of the same untrusted, attacker-controlled JSON body it is trying to authenticate. This breaks the intended binding: `organization whose secret authenticated the request == organization/repository that the request is allowed to act upon`.

### Finding Description
`WebhooksController#verify_signature` derives `repository_owner` directly from the parsed webhook body before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

It then uses that attacker-supplied `repository_owner` to select which `GitHubApp`/`webhook_secret` to validate the signature against, via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

The signature check itself only proves the request body was signed with *some* org's configured secret — it says nothing about whether that org matches the repository the payload actually targets. The dispatched handler, however, resolves the target `Repository`/`Stack` from a *different* field of the same attacker-controlled body: `payload.dig('repository', 'full_name')`: [4](#0-3) 

Since Shipit explicitly supports one `GitHubApp`/`webhook_secret` per organization (multi-tenant install), an attacker who legitimately administers **their own** GitHub App/org in that same Shipit instance (Org B) knows Org B's `webhook_secret`. They can craft an entire JSON payload where `repository.owner.login` (used only to pick the verifying secret) says "OrgB", while `repository.full_name` (used by the handler to resolve the actual `Stack`) says "OrgA/some-repo". Because they control the whole raw body, they can sign it correctly with Org B's secret; `verify_signature` passes, since it only checks the signature against Org B's secret and Org B's own field.

`PushHandler#process` then resolves stacks purely from `repository.full_name` and unconditionally calls `stack.sync_github`: [5](#0-4) [6](#0-5) 

`GithubSyncJob` fetches commits and can append new ones, and appending commits can, if the target stack has `continuous_deployment` enabled, feed into a real deploy pipeline (`Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → `Stack#trigger_deploy`): [7](#0-6) [8](#0-7) 

This is the exact class of bug described in the Chainlink report: a downstream decision (which trust boundary/price band applies) is made from a value the verification step never actually authenticates end-to-end, and the value used for the security decision (`repository_owner`, used to choose the secret) diverges from the value used for the operational decision (`repository.full_name`, used to choose the target). The equality `organization that authenticated == repository being written to` does not hold.

### Impact Explanation
This breaks the org isolation that the multi-GitHub-App feature is meant to provide. A user who legitimately controls one organization onboarded to a shared Shipit instance can forge webhook events (push, status, check_suite, membership, etc., since `repository_owner`/`Handler#stacks` are used the same way across handlers) that are accepted as authentic for a *different* organization's repository, and trigger `GithubSyncJob`/`ContinuousDeliveryJob` against that other organization's stacks — potentially causing an unauthorized deploy on a stack they have no legitimate access to. This falls into the "High" bucket (escalation across an authorization boundary triggering deploy behavior for a repository the attacker was never authorized on) and can reach "Critical" if it results in an unauthorized deploy being executed on a target org's infrastructure.

### Likelihood Explanation
This requires: (1) the target Shipit instance running the multi-org `github:` config with more than one `GitHubApp`, and (2) the attacker legitimately controlling at least one onboarded organization/app (i.e., knowing its `webhook_secret`). This is a realistic scenario for shared/multi-tenant Shipit deployments, as explicitly documented as a supported configuration. No token, session, or GitHub write access to the victim org is needed — only knowledge of one's own org's webhook secret, which any onboarded org administrator possesses.

### Recommendation
After (or as part of) signature verification, ensure the organization whose secret validated the signature matches the owner of every repository the payload claims to act on (e.g., re-derive `repository_owner` from `payload.dig('repository','full_name')` rather than trusting the pre-verification convenience field, and reject/downscope handling if they disagree). Alternatively, scope handler-side repository/stack lookups (`Handler#stacks`) to only the organization that was actually authenticated for that request, and reject webhooks whose `repository.owner.login`/`full_name` owner does not match the authenticating organization.

### Proof of Concept
Preconditions: Shipit instance configured with the multi-org github schema, i.e. `secrets.github` has (at least) `OrgA` and `OrgB` each with their own `app_id`/`webhook_secret` (see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`). Attacker legitimately administers `OrgB` and knows `OrgB`'s `webhook_secret`. `OrgA/victim-repo` has a Shipit `Stack` with `continuous_deployment: true`.

1. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "<some-real-sha-on-orgA-victim-repo>",
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgB_webhook_secret, body)>` themselves, since they legitimately know `OrgB`'s secret.
3. POST to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#repository_owner` reads `"OrgB"` from `repository.owner.login`; `verify_signature` calls `Shipit.github(organization: "OrgB")` and validates successfully against the attacker-known secret.
5. `PushHandler#process` is invoked with the same parsed body; `Handler#repository_name` reads `"OrgA/victim-repo"` from `full_name`, resolves the real `OrgA` `Stack`, and calls `stack.sync_github(expected_head_sha: after)`, enqueuing `GithubSyncJob` for `OrgA`'s stack — an action the attacker was never authorized to trigger for `OrgA`.

Note: I was not able to execute this against a running instance (no filesystem/terminal access here); the trace above is based on static analysis of `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit.rb#github`, `app/models/shipit/webhooks/handlers/handler.rb`, and `app/models/shipit/webhooks/handlers/push_handler.rb`, and should be confirmed by a Devin session that can run the test suite (e.g., extending `test/controllers/webhooks_controller_test.rb` with a two-org fixture to demonstrate the cross-org enqueue).

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
