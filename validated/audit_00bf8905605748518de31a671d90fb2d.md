### Title
CCMenuController#show ignores ApiClient stack scoping, allowing a single-stack token to read build status for any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's `stack` accessor with a version that resolves the stack directly from `Stack.from_param!(params[:stack_id])`, bypassing the `ApiClient#stack_id` scoping enforced everywhere else in the API. An `ApiClient` token that is scoped to a single stack (e.g. `stack_id` set, used to grant a third-party CI dashboard `read:stack` on one repository) can therefore be replayed against `/api/stacks/*stack_id/ccmenu` for any other stack in the installation, exposing that stack's deploy/build status, lock state, and last build label.

### Finding Description
`Shipit::Api::BaseController` defines the correct scoping helper: [1](#0-0) 

`stacks` restricts the visible `Stack` set to `current_api_client.stack_id` when the client is stack-scoped, and `stack` resolves the requested record through that scoped relation. Every other API controller (`Api::StacksController`, `Api::TasksController`, etc.) inherits this `stack` method and is therefore bound by the equality: `token.stack_id == requested_stack.id` (or the token is unscoped).

`Api::CCMenuController` breaks this binding by redefining `stack` to query the `Stack` model directly, without any reference to `current_api_client`: [2](#0-1) 

The only authorization check performed on this action is the coarse-grained permission check: [3](#0-2) 

which only verifies that the token's `permissions` array includes `read:stack` (see `ApiClient#check_permissions!`): [4](#0-3) 

This check never inspects `stack_id`. The `require_permission :read, :stack` before-action and the `stack` accessor together should implement the binding "the stack a token authorizes == the stack it touches," but for this one controller that binding is dropped, so any valid token with `read:stack` (scoped or not) can query the CCMenu endpoint for an arbitrary `stack_id` route parameter.

Test fixture `here_come_the_walrus` demonstrates the intended per-stack scoping mechanism (`stack: shipit`, `permissions: [read:stack]`), and `test/controllers/api/stacks_controller_test.rb` confirms it is respected by other endpoints ("an api client scoped to a stack will only see that one stack"). No equivalent test exists for `CCMenuController`, and the code confirms none of that scoping logic is applied there.

### Impact Explanation
This matches the High severity criterion "unauthenticated read of stack state, task streams or deploy output" in effect for the CCMenu integration: a token that was only ever meant to authorize read access to one specific stack (a common integration pattern — CCMenu URLs are handed out to CI dashboard tools scoped per-project) can be used to read deploy/build status of every stack managed by the Shipit instance, including internal/private repositories the token holder was never granted access to. This discloses stack names, lock reasons (which can contain sensitive operational text), last build outcome, and build label/timestamps for repositories outside the token's intended scope.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (the exact intended use case per `CCMenuUrlController`/`api_clients_controller`) and exposes any such token to a less-trusted party (e.g., embedding it in a CI status badge or third-party dashboard). No privileged access is required beyond possessing one legitimately-scoped, low-permission (`read:stack` only) token; the attacker simply changes the `stack_id` path segment.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation instead of directly through `Stack`, mirroring `Api::BaseController#stack`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Remove the private override entirely (relying on the inherited `stack`) unless there's a reason to keep a separate definition; if kept, it must go through `current_api_client.stack_id` scoping like every other API controller.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to Stack A only (`stack_id: A.id`, `permissions: ['read:stack']`) — e.g. the flow used by `CCMenuUrlController#fetch`, or an admin-issued token per the `here_come_the_walrus` fixture pattern.
2. Using this token's `authentication_token`, issue:
   `GET /api/stacks/<stack_owner_B>/<repo_B>/<env_B>/ccmenu?token=<token>`
   for Stack B, a completely unrelated stack the token was never scoped to.
3. The request passes `require_permission :read, :stack` (the token does have `read:stack`), and `CCMenuController#stack` resolves Stack B via `Stack.from_param!` with no ownership check, returning Stack B's build status/lock state in the XML response — confirmed by reading `app/controllers/shipit/api/ccmenu_controller.rb:27-31` against `app/controllers/shipit/api/base_controller.rb:74-80`, and the absence of any cross-stack-scoping test in `test/controllers/api/ccmenu_controller_test.rb`.
