### Title
Multisig transaction execution can silently bypass the on-chain approved payload when `abort_if_multisig_payload_mismatch` is disabled - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`multisig_account::validate_multisig_transaction`, which is invoked by the VM prologue (`run_multisig_prologue` in `aptos-move/aptos-vm/src/transaction_validation.rs`) as the admission check for multisig transactions, only cross-checks the *submitted* execution payload against the *approved* on-chain payload when the payload was stored as a hash. When the full payload was stored on-chain (the common case when `store_hash_only` is not used), the match between the submitted payload and the approved payload is enforced **only if** the `abort_if_multisig_payload_mismatch` feature flag is enabled.

### Finding Description
The prologue-time validation function is: [1](#0-0) 

Two distinct branches exist:
1. `payload_hash.is_some()` (hash-only storage) → the SHA3-256 of the submitted payload is **unconditionally** compared to the stored hash.
2. `transaction.payload.is_some()` (full payload storage) → the submitted payload is compared to the stored payload **only if** `features::abort_if_multisig_payload_mismatch_enabled()` is true and the submitted payload is non-empty.

The payload that is actually executed by the VM is not the payload approved and stored on-chain; it is the `provided_payload` derived from the transaction's own `executable_ref()` (i.e., whatever the submitter puts directly in the `SignedTransaction`), as constructed in `run_multisig_prologue`: [2](#0-1) 

Because the quorum check (`can_execute`/`can_be_executed` and `num_approvals >= num_signatures_required`) only verifies that *some* transaction at the pending sequence number received enough votes — it does not itself bind the vote count to the specific bytes being executed — the only binding between "what owners approved" and "what actually executes" is the payload-equality assertion. When the feature flag guarding that assertion is disabled (its default state must be verified on the specific chain deployment; it is a relatively new, feature-gated hardening added after `create_transaction`/`create_transaction_with_hash` existed), that binding disappears for the full-payload-storage path.

An owner who has enough approvals to execute a multisig transaction that was created with `create_transaction` (full payload, not hash-only) can therefore submit an entirely different entry function/argument set as the actual `SignedTransaction` payload at execution time. Admission (mempool + VM prologue) will accept it as a valid, quorum-approved multisig execution, and it will commit using the multisig account's signer authority — even though the other owners never approved those bytes.

This matches the admission-boundary bug class in the seed report: the "approval set" (owners who voted) is correctly checked, but it is bound to the *wrong payload* — analogous to the ERC-20 report's binding of the wrong `Sender` to a downstream privileged action. Here, the wrong *payload* is bound to a correctly-verified approval set, letting a `MultisigTransaction` execute with unauthorized content under the multisig account's authority.

### Impact Explanation
If exploitable (i.e., if `abort_if_multisig_payload_mismatch` is not enabled on a given network/at a given point in time), a single owner (or the minimum quorum) of a multisig account can execute arbitrary entry functions using the multisig account's authority/signer, diverging from what the full set of owners actually approved when they voted on the stored, human-readable payload. This is a critical unauthorized-execution-under-the-wrong-approval-set impact, directly matching "Authenticator, WebAuthn, multisig, or approval validation accepting the wrong signing material or wrong approval set" and "Pre-validation mismatch that causes a transaction which should fail admission to execute and commit."

### Likelihood Explanation
Likelihood depends entirely on the on-chain/runtime state of the `abort_if_multisig_payload_mismatch` feature flag. I was not able to determine its default/enabled status from static feature-flag definitions within the remaining investigation budget (the grep results pointed to `aptos-move/framework/move-stdlff/sources/configs/features.move` and `types/src/on_chain_config/aptos_features.rs`, but I did not get to inspect the exact declared default before running out of iterations). If it defaults to disabled on any network, likelihood is high, since it requires no special privilege beyond being one of the multisig owners with quorum — a role explicitly in scope ("unprivileged" from the perspective of the *other* owners who did not approve the executed content). If it is unconditionally enabled/cannot be disabled, this is a documented, already-hardened path and would not qualify.

### Recommendation
- Verify whether `abort_if_multisig_payload_mismatch` is enabled by default on mainnet/testnet, and if not, make the full-payload equality check in `validate_multisig_transaction` unconditional (remove the feature gate), mirroring the unconditional hash-comparison branch.
- Alternatively, deprecate the "full payload stored, no mismatch enforcement" mode entirely and always require either a hash match or an exact payload match, closing the gap between "what owners approved" and "what executes."

### Proof of Concept
This requires confirming the feature flag's default state, which I could not verify in the time available. Conceptually:
1. Owner A creates a multisig account with `num_signatures_required = 2` and owners {A, B, C}.
2. Owner A calls `create_transaction(multisig_account, payload_transfer_1_APT_to_X)` (full payload stored on-chain).
3. Owner B reviews the stored payload (transfer 1 APT to X) and calls `approve_transaction`, bringing approvals to 2 (A's implicit vote + B's).
4. Owner A (or any owner with execution rights) submits the actual `SignedTransaction` with `TransactionPayload::Multisig` whose inner executable is a *different* entry function (e.g., transfer all APT to attacker address Y) instead of the approved payload.
5. If `abort_if_multisig_payload_mismatch_enabled()` is false, `validate_multisig_transaction` skips the full-payload comparison, quorum check passes (2/2), and the VM executes the attacker-chosen payload with the multisig account's signer — draining funds to Y despite B only ever approving a transfer to X.

Because I could not confirm the feature flag's live default value before the session ended, I cannot assert this as a definitively exploitable finding without that additional verification step (recommended as a follow-up: inspect `aptos-move/framework/move-stdlib/sources/configs/features.move` for `abort_if_multisig_payload_mismatch`'s bit position and check its enablement status in genesis/mainnet feature configs, and confirm via `aptos-move/aptos-release-builder/src/components/feature_flags.rs`).

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );

        // If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
    }

pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };
