### Title
API-scoped tokens can read CI status of any stack via `Api::CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the stack-resolution helper inherited from `Api::BaseController` and drops the scoping that binds an `ApiClient` to a single `Stack`. An `ApiClient` created with `stack_id` set (a token scoped to exactly one stack) can still read the CI/build status of *any* stack by supplying a different `stack_id` param, because the controller resolves the stack directly from `Stack.from_param!` instead of through the scoped `stacks` collection.

### Finding Description
`Api::BaseController` defines the trust binding between an `ApiClient` and the stacks it is allowed to touch: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped to a stack (`stack_id?` true), and `stack` (singular) resolves `params[:stack_id]` only from within that scoped collection via `stacks.from_param!(...)`. This is the equality the app relies on: **"stack a token authorizes" == "stack a token touches."**

`Api::CCMenuController`, however, redefines `stack` to bypass that scoping entirely: [2](#0-1) 

`stack` here is `Stack.from_param!(params[:stack_id])`, resolved against **all** stacks, not `current_api_client`'s scoped subset. The only check performed is `require_permission :read, :stack`, which is implemented by `ApiClient#check_permissions!`: [3](#0-2) 

This only checks that the token has the `read:stack` permission string in its permission list; it never checks the token's `stack_id` against the requested stack. So a token created with `stack: some_stack` (a common pattern used to scope third-party CI-badge tokens, e.g. `CCMenuUrlController` at [4](#0-3)  which creates exactly such a scoped, `read:stack`-only client) is authorized for one stack, but the CCMenu endpoint will happily execute the request against **any** `stack_id` supplied in the URL, since the lookup path ignores the `stack_id` binding on the `ApiClient` record.

This mirrors the reported bug class precisely: `getPoolIdByMarketToken` validated one identifier (via `isPoolGmToken`) in one code path (`gmTokenSwap`) but not in the vulnerable path (`calculateSwapImpactFee`), causing the function to act on an unvalidated/uncontrolled identifier as if it had been checked. Here, the "stack a token authorizes" (`ApiClient#stack_id`) is enforced in `Api::BaseController#stack`/`#stacks`, but the alternate lookup path in `Api::CCMenuController#stack` skips that enforcement and acts on the caller-supplied `params[:stack_id]` unchecked.

### Impact Explanation
This is an authorization-scope escape: an attacker holding *any* valid, stack-scoped, `read:stack` API token (e.g., a leaked CCMenu badge token meant for one stack, generated by `CCMenuUrlController`) can read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`) for every stack in the Shipit instance, not just the one the token was scoped to. This qualifies under "High - escalation into authorization scope / unauthorized read of stack state" since it breaks the token-to-stack authorization binding that the rest of the API enforces.

### Likelihood Explanation
Likelihood is meaningful but bounded: it requires possession of a legitimately-issued, stack-scoped `read:stack` API token (such as a CCMenu badge URL token, which is embedded in a URL and thus more likely to leak/be shared than a full API credential). No privileged account or GitHub credentials are needed beyond that single low-privilege token — the attacker only needs to change the `stack_id` query parameter.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the same scoped `stacks` collection used by `Api::BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot query stacks outside its `stack_id` binding.

### Proof of Concept
1. Using `CCMenuUrlController#fetch` (or the admin UI), generate a CCMenu token scoped to `Stack A` (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` with `stack: A`), matching [4](#0-3) .
2. Call `GET /api/stacks/:stack_id_of_B/ccmenu.xml?token=<A's token>` where `B` is a different stack the token was never scoped to.
3. Observe the endpoint at [5](#0-4)  renders `B`'s CI status successfully (HTTP 200), because `stack` resolves `params[:stack_id]` against all stacks rather than the token's authorized scope, unlike the enforcement path in [1](#0-0) .
