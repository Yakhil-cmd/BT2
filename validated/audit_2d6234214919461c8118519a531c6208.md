### Title
Replacing an asset's attestor list permanently freezes existing coin holders whose attestor is no longer trusted - (File: `storage.js`, `validation.js`)

### Summary
For a `spender_attested` asset, ocore enforces that every spender (and every payment output address, for public assets; every input owner, for private assets) must be attested by one of the asset's *current* attestors. The definer can publish a new `asset_attestors` unit at any time to fully replace the trusted attestor list. Because only the single latest list is consulted, coins already held by an address that was validly attested when received become permanently unspendable the moment the definer swaps out the attestor that vouched for it — with no way for the holder to restore compliance, mirroring the GMX report's "un-whitelisting freezes existing funds" bug class.

### Finding Description
`readAsset()` resolves the attestor set for a `spender_attested` asset by finding only the most recent `asset_attestors` unit and using that as `objAsset.arrAttestorAddresses`, discarding any previous lists: [1](#0-0) 

`validateAttestorListUpdate()` allows the asset definer to publish this replacement list unilaterally and with no constraints preventing removal of currently-relied-upon attestors: [2](#0-1) 

When a payment is later validated, `validatePayment()`/`validatePaymentInputsAndOutputs()` require every author (and issuer) to be attested by the *current* list: [3](#0-2) 

and, for divisible/public transfers, every output address must be attested via `filterAttestedAddresses`, while for private/indivisible transfers the input owner address must be attested: [4](#0-3) [5](#0-4) 

`filterAttestedAddresses` only counts attestations issued by addresses that are members of `objAsset.arrAttestorAddresses` — i.e., the *current* attestor set, not the set that was valid when the holder received/was issued the coins: [6](#0-5) 

Consequently: Alice is attested by Attestor A at time T0. The asset definer issues coins to Alice, and Alice legitimately receives/holds `spender_attested` coins under attestor A. Later the definer publishes a new `asset_attestors` unit listing only Attestor B (dropping A), e.g. because A's key was compromised or the definer simply changes policy. From that point on, any transfer where Alice is an author/output owner fails validation with `"none of the authors is attested"` / `"owner address is not attested"` / `"some output addresses are not attested"`, even though Alice's holdings and attestation were fully valid when acquired. Alice cannot re-attest herself under the new attestor (attestation is controlled by third-party attestors, not by Alice), so her coins become permanently stuck with no code path to recover them (no grace period, no fallback to the previously valid attestor, no way to reference an older attestor-list unit).

This is directly reachable by an asset issuer (an explicitly allowed actor per scope) using only standard `asset` + `asset_attestors` messages — no special privilege beyond being the asset's own definer, which is analogous to a token owner un-whitelisting a token in the GMX report.

### Impact Explanation
Any holder of a `spender_attested` asset can have their funds permanently frozen by an ordinary (and otherwise legitimate) asset-management action — updating the attestor list — performed by the asset definer. This is not a bug requiring malice from the freezer necessarily; a routine attestor rotation performed for security reasons will inadvertently strand any coins associated with a dropped attestor. There is no cancellation/timeout/refund mechanism, unlike order/deposit cancellation flows in other systems: once validation permanently fails, the coins are inert. This qualifies as an AA/asset fund-freezing condition with concrete unauthorized loss of usability of funds for the affected holder(s).

### Likelihood Explanation
`spender_attested` is a first-class, documented asset feature (used in tests such as `test/aa.test.js` and `test/samples/create_an_asset.oscript`) and attestor-list rotation is an expected operational action (e.g., attestor key compromise, provider replacement, policy change) rather than an edge case. Any asset issuer — including an AA that defines `spender_attested` assets and later emits `asset_attestors` — can trigger this by design; no attacker-controlled exploit primitives beyond normal message construction are needed. [7](#0-6) 

### Recommendation
When validating spends of `spender_attested` assets, consider accepting attestations against the attestor list that was current at the time the specific coin/output was created (or at issuance), rather than only the single latest list; alternatively, allow a grace/migration mechanism (e.g., retain prior attestor lists as valid for outputs created before the list change, or require the new list to be a superset of, or explicitly succeed, attestations already relied upon) so that legitimately-held coins do not become unspendable purely due to a later, unrelated attestor-list update.

### Proof of Concept
1. Definer publishes an `asset` message with `spender_attested: true` and `attestors: [A]`.
2. Definer issues (or Alice otherwise legitimately acquires) coins of this asset while attested by A (`attestations` table has an entry from A for Alice, satisfying `filterAttestedAddresses`).
3. Definer later publishes `asset_attestors` with `attestors: [B]` (dropping A) — permitted unconditionally by `validateAttestorListUpdate` (`validation.js:2829-2848`) since it only checks that the sender is the definer and the list is well-formed.
4. `readAsset` now resolves `arrAttestorAddresses = [B]` for all future validations (`storage.js:1921-1946`).
5. Alice attempts to spend/transfer her existing coins. `validatePayment`/`validatePaymentInputsAndOutputs` checks her address against `[B]` only; since she is only attested by A (not in the list anymore), validation fails with `"none of the authors is attested"` (public) or `"owner address is not attested"` (private/indivisible) — her coins are now permanently stuck, as there is no path back to being recognized as attested under the removed attestor A.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
