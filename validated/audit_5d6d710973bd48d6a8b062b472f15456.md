### Title
Webhook signature check keys off attacker-controlled `repository.owner.login`, letting a webhook forged for one (secret-less) GitHub org write to stacks/teams that belong to a completely different, unrelated organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate the request against using a value pulled straight out of the *unverified* JSON body, before any signature has been confirmed. `GitHubApp#verify_webhook_signature` also unconditionally returns `true` when that selected app has no `webhook_secret` configured. Together, this breaks the intended binding "organization that authenticated == repository that gets written," because the org used to authenticate (`repository.owner.login`) and the repository actually mutated (`repository.full_name`, used by every handler) are independent, attacker-supplied fields in the same body.

### Finding Description
`verify_signature` resolves the authenticating org like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read via `params.dig('repository', 'owner', 'login')` from the raw, not-yet-verified request body. This value is used only to pick a `GitHubApp` instance via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

`GitHubApp#verify_webhook_signature` then does: [4](#0-3) 

`return true unless webhook_secret` means that for any organization configured in `secrets.yml` without a `webhook_secret` (an explicitly supported/documented configuration - see `config/secrets.development.shopify.yml` and `docs/setup.md`, both showing `webhook_secret:` left blank), signature verification is a no-op that accepts any request, regardless of the `X-Hub-Signature` header content.

Every webhook handler, however, resolves the actual object to mutate from a *different* field of the same unverified body: `repository.full_name` (not `repository.owner.login`): [5](#0-4) [6](#0-5) 

Because `repository_owner` (used to select the trivially-bypassable app config) and `repository.full_name`/`organization.login` (used to select the target `Stack`/`Team`) are two independent JSON fields that are never cross-validated, an attacker only needs `repository.owner.login` to name any org that happens to have no `webhook_secret` configured on this Shipit instance (a state the documentation itself shows as a normal/default configuration), while setting every other field - `repository.full_name`, `ref`, `after`, `organization.login`, `team`, `member` - to target a *different*, fully-configured, unrelated organization's stacks and teams.

This directly matches the analog to the reported bug class: just as `withdrawFee == 0` silently skips the intended transfer-amount check in the external report, `webhook_secret` being unset/blank silently skips the intended signature check here, and the field that determines "who is trusted" is not the same field that determines "what gets changed."

Concretely exploitable handlers that trust `repository.full_name`/`organization.login` without any relation to the authenticated org:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for any stack matching the forged `repository.full_name`/`ref` [7](#0-6) 
- `MembershipHandler` creates/updates `Team` records and adds/removes arbitrary `User` records as members based on `params.team`/`params.organization`/`params.member`, all attacker-controlled: [8](#0-7)  — this directly touches `Shipit.github_teams` authorization state.
- `StatusHandler`/other handlers write commit statuses that can satisfy CI-gating for continuous deployment on unrelated stacks.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Concrete impact:
- **Cross-repository writes** — an unprivileged attacker can trigger `GithubSyncJob`/`sync_github` on stacks belonging to organizations they have no access to, and manipulate commit/CI state used to gate deploys.
- **Escalation into `Shipit.github_teams` authorization** — via `MembershipHandler`, an attacker can add an arbitrary `User` (e.g., themselves) to a `Team` record that maps to a `Shipit.github_teams` entry used for OAuth authorization, potentially granting themselves privileged access to the Shipit UI/API.
- These meet the High/Critical severity bar (authorization escalation, cross-repository writes) defined in the rules.

### Likelihood Explanation
Likelihood depends on the deployment having at least one configured GitHub organization with a blank/absent `webhook_secret` in a multi-org `secrets.yml` — a configuration explicitly presented as valid/normal in the shipped documentation (`docs/setup.md`) and sample secrets files (`config/secrets.development.shopify.yml`), not a hardening violation the host app must avoid. Any unprivileged network attacker who can reach the `/github/webhooks` endpoint (no session, no API token needed — it's a public GitHub webhook receiver) can exploit this without any credentials, satisfying the "unprivileged attacker" requirement.

### Recommendation
- Do not let `verify_webhook_signature` return `true` merely because `webhook_secret` is unset; either require a `webhook_secret` to be configured for every organization, or reject the webhook (422) when no secret exists for that org rather than silently accepting it.
- Bind the field used to select the verifying `GitHubApp` to the same field(s) later used by handlers to resolve the target repository/organization (e.g., derive both from `repository.full_name`'s owner, and verify that `repository.owner.login`/`organization.login` are consistent), so that one JSON key can't authenticate under one org while another JSON key nominates the write target.

### Proof of Concept
1. Configure Shipit with two GitHub orgs in `secrets.yml`: `orgA` (no `webhook_secret` set, as shown supported in `docs/setup.md`) and `orgB` (has stacks and a `webhook_secret`, `orgB` unknown to attacker).
2. As an unauthenticated attacker, POST to the webhooks endpoint:
   - `X-Github-Event: push`
   - `X-Hub-Signature: sha1=anything` (irrelevant, ignored)
   - Body: `{"repository": {"owner": {"login": "orgA"}, "full_name": "orgB/target-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen-sha>"}`
3. `repository_owner` resolves to `"orgA"`; `Shipit.github(organization: "orgA")` returns a `GitHubApp` with `webhook_secret` nil, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`).
4. `PushHandler#process` uses `repository.full_name` = `"orgB/target-repo"` to locate real `orgB` stacks (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: params.after)`, mutating state for a stack the attacker never authenticated against.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after

        def process
