Based on my research, the strongest analog to this "timelock bypass via an alternate privileged path" issue is the **emergency OP-list (witness) change mechanism** in `main_chain.js`, which is guarded by a fixed time delay (`EMERGENCY_OP_LIST_CHANGE_TIMEOUT`) that can be evaluated using a value fully controlled by the unit's author (`objUnit.timestamp`), rather than by trusted, DAG-derived time.

### Title
Emergency OP-list change timelock can be bypassed using an attacker-controlled unit timestamp - (File: main_chain.js)

### Summary
The `system_vote_count` app for `op_list` is meant to trigger an emergency re-count of order-provider (witness) votes only after normal main-chain stability has been "stuck" for at least `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (3 days) past the last stable unit. The check that enforces this delay compares the *unit's self-declared timestamp* to the last stable unit's timestamp, instead of a value that cannot be freely chosen by the unit's author.

### Finding Description
When a unit contains a `system_vote_count` message for `op_list`, `writer.js` schedules `main_chain.applyEmergencyOpListChange(conn, objUnit.timestamp, cb)` [1](#0-0) . `objUnit.timestamp` is the timestamp field placed in the unit by whoever composed it — an unprivileged unit poster.

`applyEmergencyOpListChange` uses this attacker-supplied value directly as the "current time" reference for deciding whether the mandatory delay has elapsed: [2](#0-1) 

The delay constant is defined as three days: [3](#0-2) 

If `emergency_count_command_timestamp` (== `objUnit.timestamp`) is at least `timestamp_of_last_stable_unit + EMERGENCY_OP_LIST_CHANGE_TIMEOUT`, the "too early" guard is skipped and `countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp)` executes immediately, performing an emergency, is_emergency=1 recount of the OP list using only the votes and balances known at that moment [4](#0-3) . The emergency counting path also folds in unstable (not-yet-stable) votes filtered only by a much shorter `EMERGENCY_COUNT_MIN_VOTE_AGE` of one hour [5](#0-4) , and the resulting OP list is written to `system_vars` and immediately broadcast to change witnesses via `system_vars_updated`/`onSystemVarUpdated` [6](#0-5) [7](#0-6) .

This mirrors the reported bug class: a mechanism explicitly designed with a time-delay safeguard (analogous to `RoleControl`'s two-step, time-delayed role grant) can be short-circuited because the code that enforces the delay trusts a value that the calling party controls (the unit's own `timestamp` field) instead of an independently-verified clock or MCI-based counter.

### Impact Explanation
If a unit's `timestamp` field is not strictly bound to real wall-clock time by unit validation (I was not able to fully confirm the exact bound enforced on `objUnit.timestamp` within the iteration budget — see Likelihood), an attacker who can get even a single `system_vote_count` unit accepted with an inflated timestamp could force the network to perform an "emergency" recount of order providers far earlier than the intended 3-day stall requirement. Because the emergency algorithm only requires the network to have been stuck (not truly 3 days stuck), and it also pulls in unstable votes only one hour old, this could let a coalition with insufficient stable support to win a normal vote instead force through an OP list change prematurely — an OP-list change is consensus-critical since witnesses (order providers) determine main-chain stability for the entire network. A premature or manipulated OP list swap can cause nodes with differing views of "stuck" state to disagree on the active order-provider set, directly causing **node disagreement on validity/stability** of subsequent units, which is the harshest listed acceptable impact category.

### Likelihood Explanation
Likelihood depends entirely on how strictly `objUnit.timestamp` is validated elsewhere in `validation.js`. I located references to `timestamp` validation in that file but did not have remaining tool budget to confirm whether there is a tight "must not be too far in the future" bound comparable to or shorter than the 3-day emergency window. If such a bound exists and is smaller than 3 days, the practical exploitability of "skip the whole 3‑day wait in one unit" is reduced (though a bound that still allows e.g. hours or a day of drift would still meaningfully shrink the intended delay). This uncertainty should be resolved by inspecting the timestamp-validation logic in `validateAuthor`/`validateHeaders` paths of `validation.js` before this is treated as fully proven; the analog is structurally sound (the delay-enforcement code literally trusts a value supplied by the message author) but full exploitability confirmation requires that additional check.

### Recommendation
- Do not use the attacker-supplied `objUnit.timestamp` as the sole basis for the 3-day emergency delay check in `applyEmergencyOpListChange`. Use a value that cannot be chosen by the message author, e.g., the actual DAG-derived stable-unit progression (elapsed MCIs) or the timestamp of the *unit doing the counting* only after independently confirming it is close to real time via existing consensus-safe timestamp bounds.
- If a max-future-timestamp bound already exists elsewhere in validation, tighten it specifically for units carrying `system_vote_count`/`op_list`, or clamp `emergency_count_command_timestamp` to `min(objUnit.timestamp, server_time)` before comparing against the timeout.
- Consider gating emergency OP-list changes on an additional MCI-based "stuck" measure (e.g., N consecutive MCIs without new stable units) rather than purely wall-clock time supplied inside the triggering unit.

### Proof of Concept
1. Attacker crafts and posts a unit containing a single `system_vote_count` message with payload `'op_list'`, setting the unit's `timestamp` field to `last_stable_unit_timestamp + EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (or later), while the true main-chain stall duration is far shorter than 3 days (or the chain is not stalled at all).
2. If unit-timestamp validation does not reject this drift, `writer.js` calls `main_chain.applyEmergencyOpListChange(conn, objUnit.timestamp, cb)` upon saving the unit [1](#0-0) .
3. The "too early" guard in `applyEmergencyOpListChange` is bypassed because `emergency_count_command_timestamp >= timestamp + EMERGENCY_OP_LIST_CHANGE_TIMEOUT` [2](#0-1) .
4. `countVotes(..., is_emergency=1, ...)` executes immediately, counting only currently-known stable votes plus unstable votes older than 1 hour [4](#0-3) [5](#0-4) , and the OP list is force-updated and propagated to the network [8](#0-7) , well before the intended 3-day safeguard would have elapsed.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}

async function applyEmergencyOpListChange(conn, emergency_count_command_timestamp, cb) {
	// last stable unit
	const [{ timestamp, main_chain_index }] = await conn.query("SELECT timestamp, main_chain_index FROM units WHERE is_stable=1 AND is_on_main_chain=1 ORDER BY main_chain_index DESC LIMIT 1");
	if (emergency_count_command_timestamp < timestamp + constants.EMERGENCY_OP_LIST_CHANGE_TIMEOUT) {
		console.log(`too early to apply emergency OP list change yet`);
		return cb();
	}
	console.log(`applying emergency vote count after being stuck at mci ${main_chain_index}`);
	await countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp);
	cb();
}
