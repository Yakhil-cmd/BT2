### Title
Cross-tenant commit-status forgery via unscoped `StatusHandler` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an incoming webhook against the secret belonging to the organization named in the payload's `repository.owner.login`/`organization.login` field [1](#0-0) , but that authentication only proves "this payload was signed by *some organization X* configured on this Shipit instance." It never binds the event to the specific repository the handler is about to mutate. Most handlers re-derive and enforce that binding themselves by scoping their writes through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` from `payload.dig('repository', 'full_name')` [2](#0-1) . `PushHandler` and `CheckSuiteHandler` both go through this `stacks` scope before touching any data [3](#0-2) [4](#0-3) .

`StatusHandler` does not. It looks up commits purely by `sha` across the entire Shipit installation, with no repository/organization scoping at all: [5](#0-4) 

### Finding Description
This engine supports multi-tenant configuration where multiple distinct GitHub organizations, each with its own `webhook_secret`, are hooked to a single Shipit instance [6](#0-5) . `verify_signature` picks the verifying secret dynamically based on the org named inside the untrusted request body itself [7](#0-6) , so a signature check only proves "org X's key signed this exact body" — it says nothing about which *repository/stack* the effects of the event should be confined to. Every handler is expected to independently re-derive that scope from the payload's `repository.full_name` via `Handler#stacks`/`repository_name` [2](#0-1) , which is exactly what `PushHandler`/`CheckSuiteHandler` do.

`StatusHandler`, however, only requires `sha` and `state` from the payload and never calls `stacks`/`repository_name` at all: it runs `Commit.where(sha: params.sha)` against the global `commits` table and calls `commit.create_status_from_github!(params)` on every match [8](#0-7) . Because `Commit#sha` is not namespaced per-organization in this query (it's a raw global lookup), any organization onboarded to the instance — signing with its own legitimately-configured `webhook_secret` — can send a `status` event whose `sha` matches a commit that actually belongs to a *different* organization's stack (e.g., a shared base commit from a fork, a cherry-pick, or simply a colliding/duplicated SHA imported by both repos), and that commit will receive a forged status write it has no authority over.

This is the same class of bug as the Conflux report: a field that participates in *routing/authorization decisions downstream* (which repository's data gets mutated) is not covered by the same trust boundary that authenticated the request (which organization signed it). The binding that should hold is:
`organization authenticated by verify_signature == repository whose commit/stack is written`
For `StatusHandler` this equality is never checked — only `push` and `check_suite` handlers enforce it via `stacks`.

### Impact Explanation
`Status` records feed into commit "mergeable"/CI-green-check logic used for merge queue and deploy-safety gating elsewhere in the engine (`Status::Group`, `MergeRequest`, deploy readiness checks) — a status is not a display-only artifact, it participates in automated merge/deploy decisions for the affected commit. An org with a legitimately configured, unprivileged webhook integration to this Shipit instance could inject/forge a passing status on a commit belonging to a completely different tenant's repository, undermining that tenant's CI gating and potentially enabling an unauthorized merge or deploy to proceed on a commit that never actually passed CI. This satisfies the "cross-repository writes" / "unauthorized deploy or merge" impact class.

### Likelihood Explanation
Requires the attacker to control (or have compromised) a distinct organization's own already-configured webhook secret for this Shipit instance — a lower bar than attacking the victim organization directly, since no access to the victim org's GitHub App, private key, or session is needed. The main practical constraint is producing a `sha` that also exists as a `Commit` row for the victim's stack (trivial for forked repositories or shared upstream history, which is common in this deployment model). This is a genuine, reachable code-path issue distinguishing this handler from its siblings, not a theoretical one.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: restrict the `Commit` lookup to commits belonging to `stacks` (i.e., `Repository.from_github_repo_name(repository_name)`), for example:
```ruby
stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each { |c| c.create_status_from_github!(params) }
```
or equivalently join through `Stack`/`Repository` so a status payload can only ever mutate commits that belong to the repository named (and org-authenticated) in that same payload.

### Proof of Concept
1. Configure two organizations on one Shipit instance, `orgA` (victim, owns stack for `orgA/app`) and `orgB` (attacker-controlled, legitimately registered with its own `webhook_secret` for `orgB/app`), as supported by the multi-org config format [6](#0-5) .
2. Ensure a commit with SHA `S` exists in `orgA`'s tracked stack (common in forks/shared history, or simply already present from a prior sync).
3. As the operator of `orgB`, craft a `status` webhook payload: `{"sha": "S", "state": "success", "repository": {"owner": {"login": "orgB"}, "full_name": "orgB/app"}, ...}` and sign it with `orgB`'s own valid `webhook_secret`.
4. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` succeeds because it only checks the signature against `orgB`'s secret [9](#0-8) .
5. `StatusHandler#process` runs `Commit.where(sha: 'S')` globally and finds `orgA`'s commit, writing a forged status onto it despite the payload never claiming to be from `orgA` [5](#0-4) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
