### Title
Webhook signature verification is keyed by `repository.owner.login`, but event handlers act on `repository.full_name` — allowing cross-organization forgery of CI status / push / check-suite events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the inbound webhook signature against using `repository_owner`, a value taken directly from the *unauthenticated* JSON body (`repository.owner.login`, falling back to `organization.login`). Once the signature check passes, event handlers such as `PushHandler`, `StatusHandler`, and `CheckSuiteHandler` locate the `Stack`/`Commit` to act on using a *different* field from the same body: `repository.full_name` (via `Handler#repository_name`). Because these two fields are never cross-checked, an attacker who knows (or controls) the `webhook_secret` for any one configured GitHub organization in a multi-org Shipit deployment can forge a payload whose `repository.owner.login` matches that organization (so the HMAC check passes) while `repository.full_name` points to a completely different, victim organization's repository/stack.

### Finding Description
The signature verification binding is:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The verified/authenticated organization is entirely a function of the untrusted request body — `repository.owner.login`. Shipit supports configuring multiple independent GitHub Apps, one per organization, each with its own `webhook_secret`: [2](#0-1) 

After the signature check passes, the actual object of the mutation (which `Stack`/`Repository`/`Commit` gets updated) is resolved from a *different* field of the same attacker-controlled body:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler#process` uses `stacks` to trigger a GitHub sync for any not-archived stack matching the branch: [4](#0-3) 

`CheckSuiteHandler#process` uses `stacks` (again keyed by `repository.full_name`) to schedule a check-run refresh for a specific commit sha, unscoped by any organization ownership check: [5](#0-4) 

`StatusHandler#process` is worse: it looks up commits **globally by sha**, with no repository/stack scoping check at all, and writes a CI status directly from the payload: [6](#0-5) 

This produces exactly the equality-breaking binding described in the rules: the **organization that authenticated** (`repository.owner.login` / `organization.login`, used to pick the `webhook_secret`) ≠ the **repository/commit that is written** (`repository.full_name` / global commit `sha`, used by the handler to mutate state). Both fields live in the same signed byte-string, but nothing in `verify_signature` or in `Handler#repository_name` re-derives or cross-checks that `repository.full_name`'s owner segment equals `repository_owner`. An attacker who can produce a validly-signed payload for *any* one organization configured in Shipit (e.g. because they administer that org's GitHub App, or that org's `webhook_secret` has otherwise been exposed/rotated to them, or GitHub itself delivers a legitimate event for their own org) can freely substitute `repository.full_name` (and `sha`) to target a victim org's stack/commit, since the HMAC only proves "someone holding organization A's webhook secret sent this exact byte string" — not "this event genuinely originates from organization A's own repository."

### Impact Explanation
- `StatusHandler` lets the attacker set arbitrary CI status (`state`, `context`, `target_url`, `description`) on **any commit in the system** merely by knowing its sha, with zero repository-ownership check. Since Shipit gates deploys/merges on commit statuses (`ignore_ci`, merge queue's CI checks, deployable status), forging a "success" status for a victim stack's commit can influence whether that commit is considered deployable/mergeable — an unauthorized-deploy/merge-adjacent impact.
- `PushHandler`/`CheckSuiteHandler` let the attacker trigger GitHub syncs and check-run refreshes against arbitrary stacks belonging to organizations the attacker has no legitimate relationship with, using credentials scoped to a different organization.
- This crosses the credential/authentication boundary this scan is meant to catch: the entity that is cryptographically authenticated (organization A) is not the entity whose data is mutated (organization B's repository/stack/commit).

### Likelihood Explanation
This requires the deployment to be configured with multiple GitHub organizations (a documented, supported configuration) and requires the attacker to possess a valid `webhook_secret` for at least one of the configured organizations — which is not "no credential" in the strictest sense, but note this credential is scoped to organization A only; the vulnerability is that it is being used to authorize writes to organization B's data, which is exactly the unauthorized cross-repository/cross-organization write class called out in the rules. Any party legitimately entrusted with one org's webhook secret (e.g., an org admin, or a GitHub App owner in a shared multi-tenant Shipit install) can pivot to affect unrelated organizations' stacks.

### Recommendation
- In `Handler#repository_name` / `stacks`, cross-validate that `payload.dig('repository', 'full_name')`'s owner segment matches `payload.dig('repository', 'owner', 'login')` (the value actually used for signature verification), rejecting the event otherwise.
- In `StatusHandler`, scope the `Commit.where(sha: params.sha)` lookup to stacks belonging to the verified organization/repository rather than searching commits globally by sha.
- Consider deriving the authenticating organization directly from the verified GitHub App/installation context rather than from attacker-controlled JSON fields.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md` multi-org example), and a Shipit stack tracking `org-b/victim-repo`.
2. As a party holding `org-a`'s `webhook_secret` (e.g., an `org-a` GitHub App admin), craft a `status` webhook body:
   ```json
   {
     "sha": "<victim commit sha in org-b/victim-repo>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "full_name": "org-b/victim-repo", "owner": { "login": "org-a" } }
   }
   ```
3. Sign the raw body with `org-a`'s `webhook_secret` and send it to `/webhooks` with `X-Github-Event: status` and the resulting `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s GitHub App, and successfully verifies the signature (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` then updates the status of the commit belonging to `org-b/victim-repo` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), despite the request being authenticated only for `org-a`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
