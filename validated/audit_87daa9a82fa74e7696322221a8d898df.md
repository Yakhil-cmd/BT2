### Title
Front-running theft/griefing of capped, non-definer-restricted asset issuance - (File: `validation.js`, function `validatePaymentInputsAndOutputs`)

### Summary
For a capped asset (`objAsset.cap` set) whose definition allows `issued_by_definer_only: false`, the "issue" input is constrained only to `serial_number === 1` and `amount === objAsset.cap`, with uniqueness enforced by a double-spend check keyed on `type='issue' AND asset AND denomination AND serial_number` (and, only when `issued_by_definer_only` is false, additionally keyed by `address`). This mirrors the PaprController griefing pattern: a shared, single-use resource (the one-time cap-issuance slot) that any unprivileged unit poster can consume ahead of the intended issuer, causing the legitimate issuer's transaction to fail or lose the race, while the attacker claims the entire capped supply for themselves.

### Finding Description
`validatePaymentInputsAndOutputs` validates `issue` inputs at [1](#0-0) . For a capped asset the checks require `serial_number === 1` and, if not `fixed_denominations`, `input.amount === objAsset.cap`. Because `issued_by_definer_only` can independently be `false` for a capped asset (the address-restriction check and the cap/serial_number check are separate, orthogonal conditions), the double-spend key for the issue is built as: [2](#0-1) 
When `issued_by_definer_only` is `false`, the `address` field is also included in the double-spend key, meaning *any* address can independently post its own `serial_number=1` issue input for the full `cap` amount, without colliding with the double-spend key used by other addresses (because the key includes `address` only in the non-definer-restricted case) — but this also means the intended definer is not the only one who can mint the entire capped supply in one shot. `inputs.js`'s coin-selection helper independently checks "is asset already issued" via [3](#0-2) 
which only queries `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` — not filtered by address — so once any single issuer (attacker or legitimate) posts the capped issue, the wallet helper used by the legitimate issuer will believe the asset "already issued" and refuse to construct a competing issuance, causing their transaction attempt to fail/bounce out before even being posted, or to fail double-spend validation if it does get posted.

An unprivileged attacker who monitors the DAG for a newly-announced capped asset with `issued_by_definer_only: false` can race to post the `serial_number=1`/`amount=cap` issue input for their own address before the definer's intended issuance unit is added, taking the entire fixed-cap token supply while the definer's later attempt is rejected as a duplicate/impossible issuance (definer already sees the asset "issued" per the `inputs.js` check, or their issuance unit conflicts and gets marked non-serial/`final-bad` in the doublespend resolution).

### Impact Explanation
This is a supply-inflation/misappropriation analog to the reported griefing bug: instead of merely reverting a transaction, the attacker can outright steal the entire capped, fixed-supply token allocation intended for the asset definer for a negligible cost (one transaction fee), and simultaneously deny the legitimate definer any ability to issue that asset's capped supply at all (their transaction is blocked/DoS'd by the "already issued" check and by double-spend conflict resolution). This satisfies both "AA fund loss/freezing" and "unauthorized... supply" criteria — the attacker acquires tokens that were never meant for them, and the legitimate party's transaction is permanently prevented from succeeding for that asset, exactly analogous to Alice's `reduceDebt` being griefed by Bob in the source report.

### Likelihood Explanation
Exploitability requires only that an asset be defined with `cap` set and `issued_by_definer_only: false` (a supported, valid configuration per `validateAssetDefinition`), and that the attacker observe the asset-definition unit before the definer's issuance unit reaches the DAG/becomes stable — a realistic front-running window since asset definition and issuance are typically separate units/transactions. This makes the attack cheap and directly reachable by any unprivileged unit poster, matching the "grieving/front-run" bug class from the source report.

### Recommendation
For capped assets, either (a) always force `issued_by_definer_only: true` at the `validateAssetDefinition` stage (reject capped + non-definer-restricted combinations), or (b) bind the one-time capped-issue double-spend key to the asset's `definer_address` regardless of `issued_by_definer_only`, so that only the definer's issuance for that specific capped slot can ever be valid, closing the race window for third parties.

### Proof of Concept
1. Definer publishes an asset-definition unit with `{ cap: 1000000, issued_by_definer_only: false, fixed_denominations: false, ... }` (a combination not rejected by `validateAssetDefinition`).
2. Attacker observes this unit and, before the definer's planned issuance unit is included, posts their own unit containing a payment message for this asset with input `{ type: "issue", amount: 1000000, serial_number: 1, address: <attacker_address> }` (validated per [4](#0-3) ).
3. Once this unit is accepted/stable, the definer's own issuance attempt (via `inputs.js`, which checks `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` at [3](#0-2) ) is blocked as "already issued," and even a manually crafted competing issuance from the definer will conflict on the `serial_number=1` double-spend key, being resolved in favor of whichever unit is earlier/better-positioned in the DAG.
4. Result: the attacker obtains the entire capped supply for a trivial fee; the legitimate definer is permanently unable to issue that asset.
