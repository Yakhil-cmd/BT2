## Analysis: Missing chain-id binding in `SignerCapabilityOfferProofChallengeV2`

The external report's root cause is a signed authorization message that omits a field that later differentiates *which* context the signature is valid for (`implementation`), allowing the same signature to be replayed against an unintended target. Looking for a Move-native analog with the same "commit-to-context omission" shape led to `aptos_framework::account`'s off-chain-signed proof-challenge structs, which are exactly built for this purpose (binding a signature to sequence number, originator, and — in some variants — `chain_id`).

Comparing the two capability-delegation flows in the same module shows an inconsistency:

- `offer_rotation_capability` builds `RotationCapabilityOfferProofChallengeV2`, which explicitly includes `chain_id: chain_id::get()` [1](#0-0) , and the struct definition itself documents that `chain_id` was added specifically "to prevent replaying the challenge message" [2](#0-1) .
- `offer_signer_capability`, its sibling function delegating a different (but equally powerful) capability, builds `SignerCapabilityOfferProofChallengeV2` with only `sequence_number`, `source_address`, and `recipient_address` — no `chain_id` field [3](#0-2) .

### Why this matters
`verify_signed_message`/the signature check reconstructs the challenge using the account's *current on-chain sequence number* at verification time (via `get_sequence_number(source_address)`), not a value bound to a specific network. Aptos account addresses are derived purely from the public key/auth key and are identical across independently-running networks (mainnet, testnet, devnet, or any two networks sharing genesis state) unless the account has already transacted and its sequence number has diverged. For any account whose sequence number is still `0` (or otherwise coincides) on two networks, a `SignerCapabilityOfferProofChallengeV2` signature produced for use on one network is also a valid signature for the identical `(source_address, recipient_address, sequence_number)` tuple on the other network, since no `chain_id` (or any other domain separator) prevents cross-network replay. An attacker who has observed or obtained this signature (e.g. from a public chain explorer, mempool, or a dApp flow that only meant to submit it on testnet) can then submit `offer_signer_capability` with the same signature on mainnet (or vice versa), silently granting the recipient a signer capability the account owner never authorized in that context.

By contrast, the deprecated pre-V2 challenge structs were even weaker (no domain binding at all) [4](#0-3) , and the "V2" naming convention together with the rotation-capability sibling's explicit `chain_id` fix strongly implies `chain_id` binding was intended to be applied uniformly but was missed for `SignerCapabilityOfferProofChallengeV2`.

### Caveat / what remains unverified
I was not able to view the full struct definition of `SignerCapabilityOfferProofChallengeV2` in this final pass (only its literal construction site, which conclusively shows the three fields populated and no fourth `chain_id` argument). I also could not fully confirm whether any higher-level guard (e.g., requiring the recipient account to already exist, combined with typical sequence-number divergence in practice) meaningfully mitigates real-world exploitability — this reduces confidence from "certain, broadly exploitable" to "plausible for freshly-created / low-activity accounts replayed across networks that share address derivation." Given the ask-only nature of this task and the residual uncertainty about the full struct layout and practical account-state overlap needed, I present this as the strongest local candidate but recommend a Devin session review the full struct definition and any additional invariants before treating it as fully confirmed.

### Title
Missing `chain_id` domain separator in `SignerCapabilityOfferProofChallengeV2` allows cross-network replay of signer-capability delegation - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
`offer_signer_capability` signs/verifies a `SignerCapabilityOfferProofChallengeV2` that binds only to `sequence_number`, `source_address`, and `recipient_address`, unlike its sibling `RotationCapabilityOfferProofChallengeV2` which was explicitly upgraded to include `chain_id` to stop replay. This omission means the identical delegation signature can be valid on more than one network for accounts whose sequence number coincides across networks (most commonly freshly created accounts at sequence number 0), letting a previously-observed signature be replayed to grant signer capability in a context the signer never intended.

### Finding Description
`offer_signer_capability` constructs and verifies:
```
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
``` [5](#0-4) 

No `chain_id` (or any other network-identifying value) is part of the signed message. `get_sequence_number` reads the *current* chain state at verification time, so the check only validates that the signed sequence number matches whatever the on-chain sequence number is on the network where the transaction is submitted — it does not prove the signer intended that specific network. This is in direct contrast to `RotationCapabilityOfferProofChallengeV2`, which the same file documents as having added `chain_id` specifically to close this class of replay [2](#0-1) .

### Impact Explanation
Signer capability is a powerful primitive — it lets the recipient impersonate `source_address` (via `create_authorized_signer`) [6](#0-5) . If a delegation signature intended for one network is replayed on another network where the same `(address, sequence_number)` state exists, an unintended party can obtain a signer capability over the account on that other network, enabling unauthorized transaction execution/state transition under the account's identity — this fits the "unauthorized transaction execution under the wrong signer set" admission-boundary impact class.

### Likelihood Explanation
Exploitability is conditioned on sequence-number coincidence across networks, which is common for freshly bootstrapped accounts (sequence number 0) or accounts deliberately kept in sync (e.g., test/staging replicas of mainnet accounts, or accounts freshly funded on a new devnet/testnet epoch). This is a realistic but non-universal precondition, so likelihood is moderate rather than certain — flagged in the caveat above as needing further confirmation of the full struct layout and additional runtime invariants.

### Recommendation
Add `chain_id: chain_id::get()` to `SignerCapabilityOfferProofChallengeV2` (mirroring `RotationCapabilityOfferProofChallengeV2`), bump to a new versioned struct if backward compatibility for existing off-chain signing flows must be preserved, and update `offer_signer_capability` to populate/verify the new field.

### Proof of Concept
1. Create account `A` (address derived from keypair `sk`) on Network 1, do not submit any transaction from `A` (sequence number remains 0).
2. Create/derive the same address `A` on Network 2 (same keypair, independent genesis/state), also with sequence number 0.
3. Off-chain, sign `SignerCapabilityOfferProofChallengeV2 { sequence_number: 0, source_address: A, recipient_address: R }` with `sk`, intending this for Network 1 only, and submit `offer_signer_capability` on Network 1.
4. An observer captures this signature (public transaction data) and submits an identical `offer_signer_capability(A, sig, scheme, pk, R)` transaction on Network 2, where `A`'s sequence number is still 0 — verification succeeds because no `chain_id` distinguishes the two networks, silently granting `R` a signer-capability offer from `A` on Network 2 that the account owner never authorized there.

    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }
