### Title
Swap routes can inject unauthorized wallet transfers beneath `swap_collateral` authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller accepts an opaque `swap` byte payload in `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`, then forwards it to the configured router without constraining which pool or token contracts the route invokes. [1](#0-0) [2](#0-1)  A route-selected contract can invoke `token.transfer(victim, attacker, amount)`, which simulation records as a child authorization beneath the victim’s controller call and executes if that signed authorization tree is submitted. [3](#0-2) 

### Finding Description
`swap_collateral` exposes a caller-controlled `Bytes` route and requires only that the current and destination market keys differ before authorizing the owner or delegate. [4](#0-3) [5](#0-4)  The strategy withdraws collateral into controller custody and passes the measured amount together with the opaque route to `swap_tokens_or_passthrough`. [6](#0-5)  `StrategySwap` is defined as raw `Bytes`, so the controller performs no route-address validation before handing the payload to the router. [7](#0-6) 

`swap_tokens` authorizes only the exact controller-to-router input transfer, but it does not and cannot restrict arbitrary third-party contracts reached by the decoded route. [2](#0-1) [8](#0-7)  A route hop that calls `transfer(victim, attacker, amount)` therefore appears as a child of the victim’s top-level controller authorization rather than as part of the controller’s bounded router grant. [9](#0-8) [10](#0-9) 

The in-repository harness demonstrates both sides of the boundary: an honest authorization tree causes the rogue transfer to fail and rolls the swap back, while the poisoned tree produced for the same route authorizes the transfer. [11](#0-10) [12](#0-11) 

### Impact Explanation
A malicious route can steal arbitrary token balances from the swap caller’s wallet, including assets unrelated to the lending position and not listed by the protocol. [13](#0-12) [14](#0-13)  This loss is not limited to the routed collateral because the nested token call uses the caller’s signature rather than the controller’s exact router authorization. [15](#0-14) 

### Likelihood Explanation
An unprivileged attacker can supply the crafted route for any strategy entrypoint that accepts `swap` bytes, but exploitation requires the account owner or delegate to sign the authorization tree containing the malicious child token transfer. [16](#0-15) [17](#0-16)  A wallet or client that signs simulation output without rejecting unexpected child invocations makes the attack practical; an honest tree with no such child rejects the route. [18](#0-17)  This is a user-wallet authorization-boundary bypass rather than a direct protocol insolvency path.

### Recommendation
Restrict executable swap routes to governance-approved pool and token addresses before invoking them, preferably by decoding and enforcing an allowlist at the router boundary rather than treating route addresses as trusted payload data. [19](#0-18) [20](#0-19)  Add regression tests for every controller strategy accepting `swap` bytes that pair a benign signed authorization tree with a route attempting an unexpected caller token transfer. [21](#0-20)  Clients should additionally decode route bytes and reject any simulated authorization tree containing children other than the expected strategy token pull. [22](#0-21) 

### Proof of Concept
The harness constructs a router double that decodes caller-supplied route data, pulls the expected input token, invokes the route-selected pool, and returns a fair output. [23](#0-22)  The attacker-controlled pool then calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` for an unrelated token held by Alice. [24](#0-23) 

Simulation records that transfer as a sub-invocation under Alice’s `swap_collateral` authorization, and the completed swap leaves Alice with zero wallet tokens and the attacker with the full balance. [25](#0-24)  In enforcing mode, the same rogue route is rejected when Alice signs only the honest root authorization, but succeeds and performs the theft when she signs the poisoned tree containing the child transfer. [26](#0-25)

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    s.try_swap_with_signed_tree(&benign, &[])

        .diagnostics()

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
