### Title
Signature verification is keyed off an attacker-controlled `organization`/`owner.login` field that is decoupled from the `repository.full_name` field actually used to select the stack to mutate - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* `GitHubApp` (and thus which `webhook_secret`) to validate the inbound signature against based on `repository_owner`, which is read straight out of the untrusted JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). The event handlers that subsequently act on the payload (e.g. `PushHandler`, `StatusHandler`) instead resolve the target `Repository`/`Stack` using a *different* field of the same body: `payload.dig('repository', 'full_name')`. These two fields are never required to be consistent with each other, so the "organization that authenticated" and "repository that is written" are not the same binding. [1](#0-0) [2](#0-1) 

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [3](#0-2) 

`repository_owner` is derived from the attacker-controlled payload:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

`GitHubApp#verify_webhook_signature` explicitly no-ops when the resolved organization's config has no `webhook_secret` set:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [5](#0-4) 

`webhook_secret` is explicitly documented and shipped as optional/nilable in multi-org configuration (`config/secrets.development.example.yml`, `docs/setup.md`), so a real deployment can legitimately have one organization entry configured without a secret while other organizations in the same Shipit instance do have one.

Once `verify_signature` passes (either because the resolved org has no secret, or trivially because it's a different check entirely from what data is acted upon), `WebhooksController#create` dispatches the *same raw JSON body* to the handler, which derives the actual mutation target independently:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

Because `repository_owner` (used to select the signature/secret) and `repository.full_name` (used to select the stack to mutate) are independent fields of the attacker-controlled JSON, an attacker can set `repository.owner.login` to any organization configured in Shipit with no `webhook_secret` (bypassing signature verification entirely for that request) while setting `repository.full_name` to point at a completely unrelated stack/repository belonging to a different, properly-secured organization served by the same Shipit instance. `PushHandler` will then call `stack.sync_github(expected_head_sha: params.after)` [7](#0-6)  or `StatusHandler` will create commit statuses [8](#0-7)  against that unrelated victim stack, entirely unauthenticated with respect to that stack's real organization/secret.

This is the analog of the Vader `Pools.sync()` finding: the "checks" (signature verification tied to organization A) are enforced on one entity, while the actual state mutation is performed against a different entity (repository/stack under organization B) that never had its own binding verified — an equality of `authenticated_organization == mutated_repository_owner` that the code never enforces.

### Impact Explanation
This allows an unauthenticated network attacker (no GitHub credentials, no Shipit session, no API token) who merely knows that *some* organization configured in the target Shipit deployment has no `webhook_secret` set (a documented, supported configuration state) to forge webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) against *any other* repository/stack tracked by that same Shipit instance — including ones belonging to organizations that do have properly configured secrets. Depending on handler, this can trigger unauthorized `GithubSyncJob` runs, fabricate commit statuses/check runs that gate deploy approval, or manipulate review-stack lifecycle (archive/unarchive) for a repository the attacker has no access to. Faked commit statuses feeding into deploy-approval logic can lead to an unauthorized deploy decision.

### Likelihood Explanation
Requires a specific but realistic and documented misconfiguration: at least one organization entry in `Shipit.github` config without `webhook_secret` while other organizations in the same instance are actively used for real deploys. Given the docs explicitly present `webhook_secret` as "(optional)" and ship example configs with it `nil`, this is a plausible real-world deployment state, especially for a first onboarded/dev org alongside later production orgs. No special privileges, tokens, or GitHub App access are required by the attacker.

### Recommendation
Bind the signature-verification identity to the same identity used to select the mutation target: require that the organization/app resolved for signature verification match the organization owning `repository.full_name` (or resolve the app strictly from the repository being acted upon, not from a separately-supplied `owner.login`/`organization.login` field). Additionally, consider making `webhook_secret` mandatory (reject requests / refuse to boot) rather than silently returning `true` when absent, since a missing secret currently disables signature verification for that organization's namespace entirely.

### Proof of Concept
1. Shipit is configured with two organizations: `org-nosecret` (no `webhook_secret` configured) and `org-secured/target-repo` (a tracked stack with a real `webhook_secret`).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "org-nosecret" },
    "full_name": "org-secured/target-repo"
  }
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "org-nosecret")`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank [9](#0-8) , regardless of the (absent/garbage) `X-Hub-Signature` header.
4. `create` dispatches the payload to `PushHandler`, which resolves the repository via `payload.dig('repository', 'full_name')` = `"org-secured/target-repo"` [2](#0-1)  and calls `stack.sync_github(expected_head_sha: ...)` on the real, secured stack [7](#0-6) , even though the request was never validated against `org-secured`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
