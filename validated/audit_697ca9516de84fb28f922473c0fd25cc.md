The claimed exploit does not hold up structurally, and even if it did, this code path is outside the transaction-admission boundary defined by the review scope.

1. **No mismatch is possible.** `struct_to_type_layout` calls `TypeTagConverter::struct_name_idx_to_struct_tag(idx, ty_args)` using the exact same `idx` and `ty_args` parameters that were passed into `struct_to_type_layout` itself — which in turn come directly from the `Type::Struct { idx, .. }` / `Type::StructInstantiation { idx, ty_args, .. }` variant that triggered the layout construction in `type_to_type_layout_impl`. There is no code path where a different/"substituted" `idx`/`ty_args` pair could be fed into `struct_name_idx_to_struct_tag` than the one identifying the struct currently being laid out — `idx` is used consistently to load the struct definition via `struct_definition_loader.load_struct_definition(idx)` and to compute the same `struct_tag` at line 597. [2](#0-1) [3](#0-2) 

2. **`idx_to_struct_tag` is deterministic and injective per struct identity.** The `TypeTagCache`/`TypeTagConverter` documentation explicitly states struct names map 1:1 to `StructNameIndex`, and identical `(idx, ty_args)` always yield identical, deterministic tags — this is designed for concurrency/speculative execution safety, not attacker-controlled substitution. [4](#0-3) 

3. **Not part of the admission path.** `type_to_annotated_type_layout_with_delayed_fields`, the only entry point that uses `ANNOTATED=true` (and thus reaches `struct_name_idx_to_struct_tag`), is explicitly documented as being "used only for string formatting natives" — not for authenticator/signer binding, mempool, or vm-validator checks. /// Cache for struct tags, that can be used safely for concurrent and speculative execution.
///
/// # Speculative execution safety
///
/// A struct name corresponds to a unique [StructNameIndex]. So all non-generic structs with same
/// names have the same struct tags. If structs are generic, the number of type parameters cannot
/// be changed by the upgrade, so the tags stay the same for different "upgraded" struct versions.
/// The type parameters themselves (vector of [Type]s in this cache used as keys) are also not
/// changing.
///
/// Note: even if we allow to add more type parameters (e.g., for enums), it still does not affect
/// safety because different number of type parameters will correspond to a different entries in
/// cache. For example, suppose we have 3 threads, where threads 1 and 2 cache different versions
/// of an enum (see below).
/// ```
/// // Tag cached by thread 1.
/// enum Foo<A> { V1(A), }
/// ```
/// ```
/// // Tag cached by thread 2, where the version of Foo is upgraded with a new variant and new
/// // type parameter (artificial example).
/// enum Foo<A, B> { V1(A), V2(B), }
/// ```
/// If thread 3 reads the tag of this enum, the read result is always **deterministic** for the
/// fixed type parameters used by thread 3.
