### Title
Cross-organization webhook forgery: signature verified against attacker's own org while target repository/stack is resolved from an unauthenticated `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-tenant configurations (multiple GitHub Apps, one per organization, as documented in `docs/setup.md` "Using Multiple Github Applications"), `WebhooksController#verify_signature` selects *which* organization's HMAC secret to verify the payload against using `repository_owner`, but every event handler resolves the actual `Stack`/`Repository` to act on using a completely different, independently-controlled field: `repository.full_name`. Nothing binds these two fields together, so a party who legitimately controls one onboarded organization (and therefore knows their own app's `webhook_secret`) can forge a signed payload whose signature checks out under their own organization, while `repository.full_name` names a stack belonging to a different, victim organization.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the payload and uses it purely to pick the `GitHubApp`/secret to validate the signature against: [1](#0-0) 

`repository_owner` itself comes straight from the unauthenticated JSON body: [2](#0-1) 

Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full raw payload to the corresponding handler: [3](#0-2) 

Every handler (`PushHandler`, `PullRequest::*Handler`, etc.) resolves the target `Repository`/`Stack` from a *different* payload key, `repository.full_name`, not from `repository.owner.login`: [4](#0-3) 

For example `PushHandler` uses `stacks` (built from `repository_name` = `repository.full_name`) to find and sync stacks: [5](#0-4) 

Shipit explicitly supports one `GitHubApp`/`webhook_secret` per organization for multi-org installs: [6](#0-5) [7](#0-6) 

This is the same class of bug as the referenced report: a value is used to authenticate/authorize an action (here, "which organization signed this"), while a *different*, unauthenticated value drives what is actually acted upon (here, "which repository/stack gets the event"). In the bribe report, the reward-per-epoch mapping key diverges from the epoch actually collectible; here, the signing-organization key diverges from the acted-upon repository key. Both are "verified field A vs. acted-upon field B" mismatches.

### Impact Explanation
In a Shipit deployment configured with multiple, independently trusted GitHub organizations (each with its own `app_id`/`webhook_secret`, a supported and documented configuration), an attacker who administers one onboarded-but-lower-trust organization can forge a webhook whose `X-Hub-Signature` is valid (signed with their own known `webhook_secret`) but whose `repository.full_name` names a repository/stack belonging to a *different* onboarded organization. This crosses the organization boundary the webhook signature is meant to enforce, allowing an attacker to trigger `push`-driven `stack.sync_github` (and any other webhook-triggered handlers such as PR label/close/open handlers acting on review stacks) against a victim organization's stack that they do not own or control. Depending on stack configuration (continuous delivery enabled), this can result in an unauthorized deploy trigger against another organization's stack — matching the "cross-repository writes / unauthorized deploy" Critical impact bucket. I was not able to fully trace `Stack#sync_github`/`GithubSyncJob` internals to confirm whether continuous deployment auto-triggers directly from this path (the file `app/jobs/shipit/github_sync_job.rb` could not be read in this pass), so the precise blast radius (mere resync vs. deploy trigger) is not fully confirmed and should be validated further.

### Likelihood Explanation
This requires the deployment to be configured with the multi-organization GitHub App scheme (each org with its own secret) and requires the attacker to control (or have compromised) one of the onboarded organizations' GitHub App webhook secret — a scenario explicitly supported and documented by the project, but not the default single-org configuration. This is a real, unprivileged-from-the-victim's-perspective attacker (they hold no credentials for the victim org, no Shipit session, and no victim-repo write access), satisfying the "unprivileged attacker breaking a deployment-trust binding" requirement. Likelihood is Medium: it only manifests in multi-tenant setups, but is trivial to exploit once that precondition holds (a single crafted HTTP POST).

### Recommendation
Bind signature verification to the same repository/stack identity used for dispatch: after selecting the `GitHubApp` by `repository_owner` and verifying the signature, additionally verify that `repository.full_name`'s owner segment matches the verified `repository_owner`/organization before handlers are allowed to resolve stacks from it. Reject the webhook (422) if `repository.full_name.split('/').first` does not case-insensitively match `repository_owner`.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with a distinct GitHub App and `webhook_secret` (per `docs/setup.md`), and each has stacks tracking its own repositories.
2. Attacker controls `OrgB`'s GitHub App (e.g., they created/registered it) and therefore knows `OrgB`'s `webhook_secret`.
3. Attacker crafts a `push` webhook payload:
```json
{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<forged-or-real-sha>"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(OrgB_webhook_secret, payload)>` and POSTs to the shared `/github/webhooks` endpoint.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgB"`, looks up `Shipit.github(organization: "OrgB")`, and the signature validates successfully because the attacker's own `OrgB` secret was used [1](#0-0) .
6. `PushHandler` then resolves stacks via `Repository.from_github_repo_name("OrgA/victim-repo")` [4](#0-3)  and triggers `stack.sync_github(expected_head_sha: params.after)` for `OrgA`'s stack [5](#0-4)  — an action the attacker (an `OrgB` principal) has no authorization to invoke on an `OrgA` stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
