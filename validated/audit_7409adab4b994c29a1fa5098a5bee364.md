### Title
`ReopenedHandler#unarchive?` operator-precedence bug bypasses `review_stacks_enabled` re-check, letting a stale attacker branch re-provision after disablement - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
The specific claim that `Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter#unarchive!` itself never re-checks `review_stacks_enabled` is true, but this is by design: the check lives in the calling handlers' predicate methods, which gate the call to `stack.unarchive!`. However, `ReopenedHandler#unarchive?` contains a genuine Ruby operator-precedence bug that defeats this gate for two of the three `provisioning_behavior` values, allowing `review_stacks_enabled` to be bypassed on the `reopened` webhook path.

### Finding Description
The claimed binding is: `review_stacks_enabled(repository) == true` must hold at every provisioning trigger, including re-provisioning via `unarchive!`. That check is not embedded in `ReviewStackAdapter#unarchive!` itself [1](#0-0) , but it is intended to be enforced by the caller before `stack.unarchive!` is invoked, exactly as `LabeledHandler#respond_to_label_change?` and `UnlabeledHandler#respond_to_label_change?` do correctly with parenthesized boolean logic: `params.action == "labeled" && pull_request_state == "open" && repository.review_stacks_enabled && (archive? || unarchive?)` [2](#0-1) .

`ReopenedHandler`, however, computes its gate as:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [3](#0-2) 

In Ruby, `&&` binds tighter than `||`, so this evaluates as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. When the repository's `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, the outcome depends solely on the label condition — `review_stacks_enabled` is never consulted. This lets an attacker retrigger unarchive/provisioning via a forged/legitimate `reopened` PR webhook even after an operator sets `review_stacks_enabled = false`, provided the repository's `provisioning_behavior` remains `allow_with_label` (attacker adds their own label, per the threat model's stated capability) or `prevent_with_label` (attacker simply avoids/removes the label, the default state).

The rest of the path is unguarded once `unarchive?` wrongly returns true: `ReviewStackAdapter#unarchive!` re-enqueues provisioning and calls `stack.unarchive!` purely based on `stack.blank?`/`stack.archived?` [4](#0-3) , and the `ReviewStack` state machine transition `deprovisioned -> provisioning` triggers `stack.provisioner.up` [5](#0-4) . `ReviewStackProvisioningQueue#provision` only checks `stack.provisioner.provision?`, whose base implementation is a no-op returning `true` with no re-check of `review_stacks_enabled` [6](#0-5) [7](#0-6) . Provisioning/deployment proceeds against `stack.branch`, which was fixed at creation time to the attacker's `pull_request.head.ref` [8](#0-7) , so re-provisioning re-runs the deploy/`shipit.yml` pipeline for that same attacker-controlled branch.

Existing guards do not stop this: `OpenedHandler#provision?` has the identical precedence flaw at creation time [9](#0-8) , and `LabeledHandler`/`UnlabeledHandler` are correctly written, but `ReopenedHandler` is not, so the `reopened` webhook is the exploitable trigger.

### Impact Explanation
An attacker who can open, label, and reopen a pull request on a repository with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` can force re-provisioning/redeployment of a review stack keyed to their own attacker-controlled `branch`, even after the operator has disabled `review_stacks_enabled` specifically to shut this off — defeating the intended kill switch. This maps to Critical impact per the rubric (an unauthorized deploy is executed / RCE surface re-opened via `PTY.spawn`/`Command` execution driven by the deploy spec of an attacker branch), repeatable for any repository whose `provisioning_behavior` is not `allow_all` (i.e., the two "safer" modes intended to restrict provisioning are precisely the ones broken).

### Likelihood Explanation
Preconditions: repository must use `provisioning_behavior_allow_with_label` or `provisioning_behavior_prevent_with_label` (not `allow_all`), which per the docs is the more restrictive/opt-in configuration many operators would pick specifically to limit exposure — ironically the exact configurations broken here. The attacker needs only the capabilities explicitly granted in the threat model (open a PR from a fork, name a branch, apply/omit a label on their own PR, and cause a `reopened` webhook, e.g. by closing/reopening their own PR). No secrets, sessions, or maintainer privileges are required, making this a low-cost, repeatable attack once a stack has been archived once.

### Recommendation
Fix the operator precedence in `ReopenedHandler#unarchive?` (and audit `OpenedHandler#provision?` for the same defect) by parenthesizing so `review_stacks_enabled` gates the entire expression, e.g.:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Additionally, consider re-validating `review_stacks_enabled` at the `ReviewStackProvisioningQueue`/`ProvisioningHandler::Base#provision?` layer as a defense-in-depth measure so any future handler bug cannot bypass the kill switch.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb
test "does not unarchive/provision when review_stacks_enabled is false, even with prevent_with_label and no label" do
  stack = create_archived_stack # branch = attacker's head.ref, provision_status: deprovisioned
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :prevent_with_label,
    provisioning_label_name: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] = [] # no label -> prevent_with_label triggers unarchive? = true regardless of review_stacks_enabled

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  # Binding under test: review_stacks_enabled(repository) == false  =>  stack.archived?(after) == true
  assert stack.reload.archived?, "Expected stack to remain archived because review_stacks_enabled is false"
end
```
Given the current code, this assertion fails: `stack.reload.archived?` is `false` and the stack is re-enqueued for provisioning, demonstrating the bypass.
