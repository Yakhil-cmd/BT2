## Finding

The webhook signature-verification binding in this engine ties an incoming webhook to a single verified GitHub organization, but `Shipit::Webhooks::Handlers::StatusHandler` writes commit statuses to *any* stack in the entire installation that happens to have a matching commit SHA, with no check that the matched stack's repository belongs to the organization that was actually authenticated. This is the same class of bug as the reported Dash issue: two related bindings ("the org whose secret was verified" and "the repository actually written to") that should be locked/verified together are checked independently, and the enforcement order/scope lets one substitute for the other.

### Root cause

`app/controllers/shipit/webhooks_controller.rb` selects the `GithubApp`/secret to verify with using only the payload's `repository.owner.login` (or `organization.login`), then verifies the raw body HMAC against that org's secret: [1](#0-0) [2](#0-1) 

This proves only "the request was signed by the webhook secret configured for organization X" — nothing more.

Most handlers correctly re-derive the target stacks by scoping through the payload's `repository.full_name` via `Repository.from_github_repo_name`: [3](#0-2) 

But `StatusHandler` does not use this scoped `stacks` helper at all. It performs a completely global lookup by commit SHA, with no repository/organization scoping whatsoever: [4](#0-3) 

The result is written directly from attacker-controlled payload fields (`state`, `description`, `target_url`, `context`) into a real `Status` record for whatever stack/commit happens to match, via `Commit#create_status_from_github!`: [5](#0-4) [6](#0-5) 

### The broken binding

`organization authenticated by verify_signature` ⟺ `repository/stack actually written by StatusHandler` — this equality is assumed but never enforced. `verify_signature` only proves the request was signed by *some* configured organization's webhook secret (the one named in `repository.owner.login`); `StatusHandler` then blindly matches `Commit.where(sha: params.sha)` across **all stacks in the Shipit instance**, regardless of which organization was verified.

### Exploitability

Any org/repo the attacker legitimately controls (and therefore knows the webhook secret for, since they run their own GitHub App installation as configured in `Shipit.github`) can be used to forge a `status` event: the attacker signs the payload correctly for their *own* org, but sets `sha` to a commit SHA that exists in a *different*, unrelated stack tracked by the same Shipit instance (e.g., a shared/forked/mirrored public commit, or simply guessing/observing SHAs of another tracked public repo). Because `StatusHandler` never checks that the matched commit's stack belongs to the verified organization, Shipit will create an attacker-controlled `Status` (`state`, `context`, `description`, `target_url`) on a victim stack's commit.

Since commit deployability and continuous delivery scheduling are driven by these statuses (`Status#after_create` schedules continuous delivery; `Commit#deployable?` factors in status state and blocking/required statuses), an attacker can forge a fake "success" status for a required CI check they do not control, potentially causing Shipit to treat an unreviewed/unvetted commit as deployable and trigger continuous delivery — an unauthorized deploy of that commit. [7](#0-6) [8](#0-7) 

### Recommendation

`StatusHandler#process` (and any other handler bypassing the `stacks` helper) must scope its `Commit` lookup to the repository indicated by the payload and cross-check that this repository belongs to the same organization/App installation that `verify_signature` authenticated, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of a global `Commit.where(sha: params.sha)`.

### Note on scope of this analysis

This is provided as an ask-only analysis per the current mode; a background Devin session would be needed to implement and test the fix (restricting `StatusHandler` to repository-scoped commit lookups and auditing other handlers for the same unscoped-lookup pattern).
