### Title
Unauthenticated webhook forgery escalates into `Shipit.github_teams` authorization via `MembershipHandler` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` is meant to bind every processed webhook event to the GitHub organization it claims to come from, so that only genuine GitHub-signed events can mutate Shipit state. However `GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured — a state the setup docs explicitly present as optional. Combined with `MembershipHandler`, which grants team membership (and therefore `Shipit.github_teams` authorization) purely from unauthenticated webhook JSON, an attacker who can reach `/webhooks` can add an arbitrary GitHub login to any team ID they choose, without ever needing the app's webhook secret, private key, or an `ApiClient` token — mirroring the report's root cause of privileged state being written from unverified/unchecked input.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from the untrusted JSON body (`repository.owner.login` or `organization.login`) and asks that organization's `GitHubApp` to confirm the signature: [1](#0-0) [2](#0-1) 

The actual cryptographic check is: [3](#0-2) 

`return true unless webhook_secret` means that if the (documented as optional) `webhook_secret` is not configured for an organization, **every** webhook event for that organization is treated as verified, regardless of signature header content. The setup guide explicitly lists the webhook secret as optional: [4](#0-3) 

`MembershipHandler#process` then trusts the webhook body directly to mutate authorization-relevant state — team membership — without any independent confirmation from the GitHub API that the membership actually changed: [5](#0-4) 

`User.find_or_create_by_login!` does call the GitHub API to fetch/validate that the `login` exists, but nothing ties that user's *actual* membership in the organization/team to the `added` event — the event's truthiness is exactly what `verify_signature` was supposed to guarantee: [6](#0-5) 

Team membership is exactly what gates elevated trust in Shipit: `User#authorized?` checks membership against `Shipit.github_teams`: [7](#0-6) 

**The broken binding, stated as an equality:**
`organization whose GitHub App cryptographically signed the webhook == organization/team the handler is allowed to grant privileged membership for`.

Before the attack: this equality holds only when GitHub itself, holding the shared `webhook_secret`, produces the event.
After the attack (secret unset): the left side of the equality is vacuously always true (`verify_webhook_signature` short-circuits to `true`), so the right side — which team a user is added to, and therefore whether they pass `authorized?` — is entirely attacker-controlled via a self-crafted, unsigned HTTP POST.

### Impact Explanation
This is a "High" impact per the rubric's "escalation into `Shipit.github_teams` authorization" bucket. Any unauthenticated party can forge a `membership` webhook event that adds an arbitrary (existing) GitHub login to a `Team` record whose `github_id` matches one of `Shipit.github_teams`. Once granted, that user is treated by Shipit as `authorized?`, which is the primary access gate used throughout the UI/session-authenticated surface of the engine.

### Likelihood Explanation
Medium-to-High: it requires the deployer to have left `webhook_secret` unset, which the project's own setup documentation frames as optional. No GitHub App credentials, `ApiClient` tokens, or session cookies are needed — only knowledge of the numeric GitHub team ID configured in `Shipit.github_teams` (discoverable via the GitHub UI/API for any team the attacker can view) and a POST to the public `/webhooks` endpoint.

### Recommendation
- Require `webhook_secret` to be configured (fail closed) rather than silently trusting unsigned payloads in `GitHubApp#verify_webhook_signature`.
- For `MembershipHandler` (and any handler that mutates authorization-relevant state), re-verify the claimed membership change against the GitHub API (e.g., `Shipit.github.api.organization_membership` / `team_membership`) instead of trusting the webhook body verbatim.

### Proof of Concept
1. Deploy Shipit with `github.webhook_secret` left blank (the documented default/optional state).
2. Determine the numeric GitHub `team.id` corresponding to one of the teams listed in `Shipit.github_teams` (e.g., from the GitHub team's URL/API, which is visible to any member of the org).
3. Send, without any signature header:
```
POST /webhooks
X-Github-Event: membership

{
  "action": "added",
  "team": {"id": <target_team_github_id>, "name": "T", "slug": "t", "url": "https://api.github.com/teams/1"},
  "organization": {"login": "<any-org-name>"},
  "member": {"login": "<attacker-github-login>"}
}
```
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "<any-org-name>").verify_webhook_signature(...)`, which returns `true` because no `webhook_secret` is configured [8](#0-7) .
5. `MembershipHandler#process` runs, creating/finding the `Team` by the attacker-chosen `github_id` and adding the attacker's user to it [9](#0-8) .
6. The attacker's `User#authorized?` now returns `true` [7](#0-6) , granting unauthorized access to `Shipit.github_teams`-gated functionality after they log in via GitHub OAuth.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
