### Title
Stack-scoped API token can read the CCMenu status of any stack, bypassing its `stack_id` restriction - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController#stack` correctly scopes the accessible `Stack` to `current_api_client.stack_id` when the authenticated `ApiClient` is restricted to a single stack: `stacks` returns `Stack.where(id: current_api_client.stack_id)` and `stack` resolves from that scoped relation. [1](#0-0)  `Shipit::Api::CCMenuController`, however, overrides `stack` to resolve directly from `Stack.from_param!(params[:stack_id])`, completely ignoring `current_api_client.stack_id`. [2](#0-1) 

### Finding Description
`CCMenuUrlController#fetch` mints a scoped `ApiClient` (`permissions: ['read:stack']`, `stack: <specific stack>`) and hands the caller a token intended to authorize CCMenu reads for that one stack only. [3](#0-2) 

`CCMenuController` enforces authorization via `require_permission :read, :stack`, which only checks that `"read:stack"` is present in the client's `permissions` list — it never checks whether the specific stack being requested matches the client's `stack_id`. [4](#0-3) [5](#0-4) 

The actual per-request object is resolved by the controller's own `stack` method:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
This bypasses the `stacks` scoping helper (`Stack.where(id: current_api_client.stack_id)`) used everywhere else in the API namespace, and instead loads *any* stack identified by the request's `stack_id` path parameter — a value fully controlled by the caller. [6](#0-5) 

This is the exact class of bug described in the analog report: a credential (`FEE_ADDRESS`) is supposed to bind an action to a specific, pre-approved value, but the code path that performs the action never actually consults that binding. Here, the binding is "the stack a token authorizes" (`ApiClient#stack_id`) versus "the stack the endpoint touches" (`params[:stack_id]`), and `CCMenuController#stack` breaks the equality between them.

### Impact Explanation
Before the request: `ApiClient#stack_id` == the one stack the CCMenu URL was created for; `check_permissions!` guarantees only the `read:stack` scope is required and says nothing about which stack.
After the request: the controller renders `deploys_and_rollbacks`, `merge_status`, and stack name/URL for **any** stack in the installation, chosen entirely by `params[:stack_id]`, regardless of `current_api_client.stack_id`.

Any holder of a stack-scoped `CCMenu Client` token (which is exposed in a plain, non-expiring URL — see `CCMenuUrlController#fetch`, `uri.query = { 'token' => client.authentication_token }`) can enumerate other stacks and read their build/deploy status and history by supplying a different `stack_id` in the URL. This is an unauthorized read of stack state and deploy output across stacks the token was never meant to access — matching the "High: unauthenticated/unauthorized read of stack state, task streams or deploy output" impact category, since the token's declared scope (`stack_id`) is not enforced.

### Likelihood Explanation
Likelihood is high for anyone who already possesses (or can guess/observe) a CCMenu token for one stack: the CCMenu URL/token is routinely shared with CI dashboard tools (CCTray clients) and is not scoped to be secret-but-single-use. No elevated permission is needed beyond having any single-stack `read:stack` token — swapping `stack_id` in the request path is enough to pivot to other stacks.

### Recommendation
Change `CCMenuController#stack` to resolve through the shared, correctly scoped helper instead of loading the stack unconditionally:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
where `stacks` is `BaseController#stacks`, which respects `current_api_client.stack_id`. Apply the same fix to `CCMenuUrlController#stack` if it is ever exposed to non-owner-authenticated flows, and add a regression test asserting that a stack-scoped token cannot fetch another stack's CCMenu XML.

### Proof of Concept
1. As a logged-in user, call `GET /stacks/org/repo-a/staging/ccmenu` (via `CCMenuUrlController#fetch`) to obtain a CCMenu URL/token scoped to stack `repo-a/staging`, e.g. `.../api/stacks/1/ccmenu.xml?token=<T>`.
2. Using the same token `T`, request a different stack's CCMenu feed by changing the path segment: `GET /api/stacks/2/ccmenu.xml?token=<T>` (stack `2` is some other stack not owned by, or intended for, this token).
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (ignoring `current_api_client.stack_id`), and `require_permission :read, :stack` only checks that `"read:stack"` is in the token's permission list, the request succeeds and returns stack `2`'s build status, deploy history, and web URL — data the token was never authorized to access.
