### Title
`ReopenedHandler#unarchive?` operator precedence bug bypasses `review_stacks_enabled` gate, re-enqueuing provisioning for a disabled repository - (File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb)

### Summary
`unarchive?` combines `review_stacks_enabled` with `provisioning_behavior_allow_all?` using `&&`, then `||`s in the `allow_with_label?` and `prevent_with_label?` branches, so Ruby's operator precedence only gates the `allow_all` path with `review_stacks_enabled`. On a repository with `review_stacks_enabled: false` and `provisioning_behavior: :allow_with_label`, an attacker who labels their own reopened PR with the provisioning label satisfies `unarchive?` regardless of `review_stacks_enabled`, causing `stack.unarchive!` and `ReviewStackProvisioningQueue.add(stack)` to run for a stack whose review-stack feature is disabled.

### Finding Description
The broken binding as an explicit equality: the intended invariant is `unarchive_permitted == (repository.review_stacks_enabled == true) AND (one of the behavior branches matches)`. The actual code in [1](#0-0)  is:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. The last two disjuncts never check `review_stacks_enabled` at all. This is the identical bug pattern present in the sibling `OpenedHandler#provision?` at [2](#0-1) , confirming this is a systemic precedence mistake, not a one-off typo.

Exploit flow:
1. Attacker owns a repository already onboarded to Shipit with a `ReviewStack` in the archived state (created earlier while review stacks were enabled, or via any prior provisioning flow).
2. Repository is (re)configured with `review_stacks_enabled: false` and `provisioning_behavior: :allow_with_label` (an operator/maintainer setting, but the *bug* is that this configuration should fully disable review-stack lifecycle actions and does not).
3. Attacker reopens their PR and attaches the configured provisioning label (`repository.provisioning_label_name`), then the GitHub `pull_request` `reopened` webhook fires.
4. `ReopenedHandler#process` calls `respond_to_pull_request_reopened?` → `unarchive?`, which evaluates true via the `allow_with_label? && has_label?` branch, bypassing the `review_stacks_enabled` gate at [3](#0-2) .
5. `stack.unarchive!` is invoked, which per `ReviewStackAdapter#unarchive!` calls `Shipit::ReviewStackProvisioningQueue.add(stack)` then `stack.unarchive!` inside a transaction, as seen at [4](#0-3) .
6. This re-queues the stack for provisioning (`ReviewStackProvisioningQueue.add` → `stack.enqueue_for_provisioning`, later picked up by `ReviewStackProvisioningQueue#work` → `stack.provision`), effectively re-triggering the provisioning/command-execution pipeline for a stack whose feature flag says review stacks are disabled for that repository.

Existing guards do not stop this: `verify_signature`/webhook signature checks only authenticate that GitHub sent the payload for that repository, they do not enforce the `review_stacks_enabled` business rule, and `drop_unhandled_event`, `ExplicitParameters` schema validation, and repository/stack model validations are unrelated to this authorization-logic bug — none of them re-check `review_stacks_enabled` before `unarchive!`.

### Impact Explanation
An attacker who owns a repository (i.e., can push branches, open/label/reopen PRs, and trigger GitHub webhooks against their own repo) can force Shipit to unarchive a `ReviewStack` and re-enqueue it for provisioning even though the operator explicitly disabled review stacks for that repository (`review_stacks_enabled: false`). Provisioning ultimately drives the stack's command/task execution pipeline (`stack.provision` in `ReviewStackProvisioningQueue#provision`), so this results in Shipit performing infrastructure actions (running provisioning tasks) that the operator's configuration intended to prevent. The blast radius is scoped to the attacker's own repository/stack (since `repository` and `stack` are looked up strictly from the webhook's own `params.repository.full_name` and scoped `review_stacks`), so this is not a cross-tenant bug, but it is a genuine authorization/config bypass — the repository owner disabled review stacks and the attacker (a PR author, potentially an outside contributor without repo-admin rights over the Shipit configuration) can still force provisioning to occur. This matches "unauthorized deploy/task execution" (Critical) in scope, scoped to that single repository/stack rather than cross-tenant.

### Likelihood Explanation
Preconditions: an already-archived `ReviewStack` must exist for the PR's environment; the repository must be configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (or, symmetrically, `prevent_with_label`, since neither of those branches checks the enabled flag). The attacker only needs the ability to add/remove labels on their own PR and to reopen it — both of which are attacker-controlled with no privileged Shipit credentials required, and GitHub delivers the `reopened` webhook automatically. This is fully repeatable: an attacker can archive and re-open a PR with the label attached as many times as desired, each time re-enqueuing provisioning.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every branch:
```ruby
def unarchive?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the identical fix to `OpenedHandler#provision?` at [2](#0-1) , since it has the same precedence defect.

### Proof of Concept
minitest plan (to be placed under `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`, out of scope to author here but described):
1. Create a `Shipit::Repository` with `review_stacks_enabled: true`, `provisioning_behavior: :allow_with_label`.
2. Create and provision a `Shipit::ReviewStack` for a PR, then archive it (`stack.archive!`), asserting `stack.reload.archived? == true`.
3. Flip the repository to `review_stacks_enabled: false` (leaving `provisioning_behavior: :allow_with_label`).
4. Build a `reopened` webhook payload for the same PR number/environment with the provisioning label present in `pull_request.labels`.
5. Call `Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process`.
6. Assert the broken binding directly: before, `repository.review_stacks_enabled == false` and `stack.archived? == true`; after, assert `stack.reload.archived? == false` (unarchive occurred despite `review_stacks_enabled == false`), and assert `Shipit::ReviewStack.with_provision_status(:deprovisioned).where(awaiting_provision: true)` includes the stack (i.e., `ReviewStackProvisioningQueue.add` was invoked) — demonstrating that `review_stacks_enabled == false` did not prevent `unarchive?` from returning `true`.
