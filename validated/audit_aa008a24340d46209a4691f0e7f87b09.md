### Title
`StatusHandler#process` mutates commits/stacks of any repository sharing a commit SHA, with no scoping to the webhook's verified repository/organization - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, without ever consulting `payload.dig('repository', 'full_name')` or the base `Handler#stacks`/`repository_name` helpers that every other handler (`PushHandler`, `CheckSuiteHandler`, the `PullRequest` handlers) uses to scope to the repository named in the payload. Signature verification only proves the request was signed with the secret of whichever organization is named in the attacker-supplied JSON body (`repository_owner`), and never constrains which repository's commits get mutated.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:
`organization_that_signed_the_body (derived from payload['repository']['owner']['login'] in WebhooksController#verify_signature)` == `organization/repository whose Commit/Stack rows get mutated (derived from Commit.where(sha:).first.stack.repository inside StatusHandler#process)`.

Trace:
- `WebhooksController#verify_signature` reads `repository_owner` straight from the attacker-controlled JSON body (`params.dig('repository', 'owner', 'login')`) and verifies the raw body's HMAC against `Shipit.github(organization: repository_owner).verify_webhook_signature`. [1](#0-0) [2](#0-1) 
- Once signature verification passes for *some* organization the attacker legitimately controls (or a repository under it), `WebhooksController#create` dispatches to `StatusHandler.call(params)` with the entire attacker-authored JSON body. [3](#0-2) 
- `StatusHandler`'s param schema does not even `require` a `repository` key, and `process` performs a global, unscoped lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [4](#0-3) 
- By contrast, the base `Handler` class provides `stacks`/`repository_name` helpers that scope to `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, and `PushHandler`/`CheckSuiteHandler` use them before touching any `Commit`. [5](#0-4) [6](#0-5) [7](#0-6) 
`StatusHandler` is the outlier that skips this scoping entirely.
- `create_status_from_github!` creates a `Status`, which on `after_create`/`after_commit` triggers `enable_ci_on_stack` (`commit.stack.enable_ci!`) and `schedule_continuous_delivery` on whichever stack the matched commit happens to belong to. [8](#0-7) [9](#0-8) 

Exploit flow: the attacker needs any organization/repository whose webhook_secret they can trigger a legitimate delivery from (an org they administer, or any repo under an org that shares that org-level `webhook_secret`, per Shipit's `github: <org>: webhook_secret:` config keyed only by organization, not by repo). They then send (or replay-with-modification) a `status` event whose JSON body sets `sha` to a commit SHA that also exists on a *different, unrelated* Shipit-tracked repository (achievable when the same git commit object — identical tree/parents/author/committer timestamps — is mirrored, force-pushed, or cherry-picked byte-for-byte into both repositories, which is a normal occurrence for forks/mirrors of shared history). Since `verify_signature` never checks that the `sha` or any implied repository actually belongs to the signing organization, and `StatusHandler#process` never filters `Commit.where(sha:)` by repository/stack/organization, the forged status lands on the unrelated repository's commit and fires `enable_ci_on_stack`/`schedule_continuous_delivery` for a stack the attacker never named and does not own.

None of the existing guards catch this: `verify_signature` validates only the HMAC of the raw body against the (attacker-named) organization's secret, not repository identity of the commit being mutated; the `ExplicitParameters` schema for `StatusHandler` doesn't even require a `repository` field; `drop_unhandled_event`/`check_if_ping` are irrelevant; there is no `force_github_authentication`, `User#authorized?`, or model validation in the `Commit`/`Status` path that re-derives or checks repository ownership.

### Impact Explanation
A webhook payload legitimately signed for one repository/organization (B) causes `Status` rows to be written against Commit/Stack records owned by a completely different, unrelated repository (A), and triggers `Stack#enable_ci!` and `commit.schedule_continuous_delivery` for A's stack — this is a payload-for-one-repository-mutates-another's-stack/commit scenario, matching the **Critical** severity bucket. It is repeatable against any repository tracked by the Shipit instance whose commit history happens to share a SHA with a commit reachable by the attacker's signing organization, and the blast radius spans all tenants/organizations configured in the same Shipit deployment, since the query has no organization filter at all.

### Likelihood Explanation
Preconditions: the attacker must control (or be able to trigger deliveries for) at least one organization/repository already configured with a `webhook_secret` in Shipit, which is a normal, low-cost precondition for anyone who owns/administers a repo under a GitHub App install that Shipit trusts. The harder precondition is the SHA collision: true SHA1 collisions are infeasible, but identical git commit objects (same tree, parents, author/committer identity+timestamps, message) landing in two different Shipit-tracked repositories is realistic in mirror/fork/subtree workflows, making this a plausible, demonstrable, non-cryptographic collision path rather than a purely theoretical one. Given the collision, exploitation is a single crafted HTTP POST, fully repeatable.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: require `repository.full_name` in the params schema, resolve the target repository via `Repository.from_github_repo_name(params.repository.full_name)`, and restrict the `Commit.where(sha:)` lookup to `stacks.flat_map(&:commits)` (or an equivalent `commit.stack.repository == repository` check) before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style):
1. Create two stack fixtures, `stack_a` (repository A) and `stack_b` (repository B), each with a commit sharing the identical `sha` value (simulating a mirrored/cherry-picked commit).
2. Stub `Shipit.github(organization: 'org-b').verify_webhook_signature` to return `true` (attacker legitimately owns B's secret).
3. POST a `status` event body with `repository.full_name = "org-b/repo-b"`, `repository.owner.login = "org-b"`, and `sha` equal to the shared SHA — i.e., a payload that never names repository A.
4. Assert on the broken binding directly:
   - Before: `commit_a.statuses.count == 0` and `stack_a.updated_at` unchanged.
   - After POST: `assert_difference('commit_a.statuses.count', 1)`, and `assert_equal repository_owner_signed, "org-b"` while `assert_equal commit_a.stack.repository.owner, "org-a"` — proving the signing org (B) != the mutated org (A) yet the mutation still occurred.
   - Assert `Stack#enable_ci!`/`schedule_continuous_delivery` (e.g. via `assert_enqueued_with` for the CD job or mocking `Commit#schedule_continuous_delivery`) fired for `stack_a` despite the payload only naming `repo-b`.
