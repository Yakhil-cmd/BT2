### Title
Webhook signature verified against `repository.owner.login` but handlers act on the unrelated `repository.full_name` field, allowing cross-organization stack sync — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub organization's `webhook_secret` using `repository.owner.login` from the JSON body and verifies the HMAC signature over the raw payload with that secret [1](#0-0) . Once verification passes, event handlers act on `repository.full_name` — an entirely different field in the same attacker-influenced JSON body — to resolve which `Repository`/`Stack` records to mutate [2](#0-1) . Because Shipit supports multi-tenant GitHub configuration with per-organization `webhook_secret`s [3](#0-2) , an attacker who legitimately knows one organization's webhook secret can forge a signed payload whose `repository.owner.login` matches that organization (so the signature check passes) while `repository.full_name` points at a stack belonging to a completely different, unrelated organization/repository.

### Finding Description
The binding that should hold is: `organization whose secret authenticated the request == organization/repository the handler is permitted to act on`. This binding is broken because two different fields of the same JSON body are used for these two purposes, and only one field is functionally tied to the signature's *authorization scope selection* — not to which repository is mutated.

1. `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` (or `organization.login`), fetches that organization's `GitHubApp` config via `Shipit.github(organization: repository_owner)`, and verifies `X-Hub-Signature` against `request.raw_post` using that org's `webhook_secret` [4](#0-3) .
2. On success, `create` dispatches the full attacker-controlled `params` to `Shipit::Webhooks.for_event(event)` handlers [5](#0-4) .
3. `Handler#stacks` (base class used by `PushHandler`, `StatusHandler`, pull-request handlers, etc.) resolves the target repository via `payload.dig('repository', 'full_name')`, independent of `repository.owner.login` [2](#0-1) .
4. `PushHandler#process` uses those resolved stacks to trigger `stack.sync_github(expected_head_sha: params.after)` [6](#0-5) , which enqueues `GithubSyncJob` to fetch commits from GitHub (using the app's own credentials for that stack) and append them to the stack, potentially feeding continuous deployment [7](#0-6) .

Nothing in the request pipeline checks that `repository.full_name`'s owner matches `repository.owner.login`, i.e. the value that determined the trusted signing key. A real GitHub-originated webhook would always have these fields consistent, but this endpoint accepts arbitrary JSON directly, so an attacker fully controls both fields independently as long as they can produce a valid HMAC for whichever org they name in `repository.owner.login`.

### Impact Explanation
An attacker who knows (or controls) the `webhook_secret` for any one organization/tenant configured in a multi-tenant Shipit deployment can forge webhook events for stacks belonging to a *different* organization/repository that they have no access to. Concretely, they can:
- Set `repository.owner.login` = an org whose secret they know, computing a valid signature.
- Set `repository.full_name` = `victim-org/victim-repo`.
- Trigger `PushHandler`, causing `GithubSyncJob` to run against the victim's stack, syncing new commits and feeding into automatic/continuous deployment pipelines for a stack the attacker never had write or deploy permission on.

This is a cross-repository/cross-tenant control bypass: an unprivileged party (with respect to the victim stack) can cause the Shipit engine to act on, and potentially unlock deploy triggers for, a repository outside their authorization scope — matching the "cross-repository writes / unauthorized deploy" impact category.

### Likelihood Explanation
Exploitability depends on the attacker possessing a valid webhook secret for at least one configured GitHub organization in this Shipit instance (multi-tenant `secrets.github` configuration). This is plausible in shared/multi-tenant deployments where multiple organizations register their own webhook secrets with the same Shipit instance, since a member of Org A with webhook-management rights on any Org A repo can read that org's `webhook_secret` and reuse it to forge events naming an unrelated `repository.full_name`. In single-tenant deployments where only one organization is configured, this issue collapses (there is no "other" organization's stacks to target), which limits but does not eliminate the exposure in this codebase.

### Recommendation
Enforce that the field used to select the verification key is the same field used to resolve the target repository:
- In `Handler#repository_name`/`#stacks`, cross-check `payload.dig('repository','owner','login')` (or `organization.login`) against the owner portion of `payload.dig('repository','full_name')`, and reject/ignore the event if they diverge.
- Alternatively, pass the already-verified `repository_owner` from the controller into the handler dispatch and have handlers only resolve stacks scoped to that verified owner, rather than re-deriving the owner independently from `repository.full_name`.

### Proof of Concept
1. Configure Shipit for two organizations in `secrets.github`, e.g. `org-a` (secret known to attacker) and `victim-org` (unrelated).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<sha attacker wants synced>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "org-a" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(org-a webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s `GitHubApp`, and verifies successfully because the attacker used `org-a`'s real secret [8](#0-7) .
5. `PushHandler` resolves `stacks` via `repository.full_name = "victim-org/victim-repo"` [2](#0-1) , and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack, which the attacker has no legitimate relationship to [6](#0-5) .

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
