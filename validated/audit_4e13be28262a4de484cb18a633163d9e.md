### Title
Cross-repository status injection via unscoped `sha` lookup enqueues `ProcessMergeRequestsJob`/`ContinuousDeliveryJob` for a victim stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by `sha` alone, with no filtering by the repository named in the verified webhook payload, then calls `commit.create_status_from_github!` on every match. Because commit SHAs are content-addressed and identical across forks/clones of the same history, an attacker who owns any repository already onboarded to the Shipit instance can send a real, validly-signed "status" webhook for their own repo that names a SHA also present in an unrelated victim stack's `commits` table, causing a `Status` to be written against the victim commit and triggering the victim stack's `schedule_continuous_delivery` → `ProcessMergeRequestsJob`/`ContinuousDeliveryJob` path.

### Finding Description
The broken binding: the question claims `stack_passed_to_ProcessMergeRequestsJob == Repository(payload['repository']['full_name']).stacks`. In `StatusHandler#process`: [1](#0-0) 

the code does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it never calls the base class's `stacks` helper (which *does* scope to `Repository.from_github_repo_name(repository_name)`), unlike `PushHandler`, which correctly scopes: [2](#0-1) [3](#0-2) 

`Commit.create_status_from_github!` builds the `Status` using the commit's own `stack_id`, not anything derived from the payload: [4](#0-3) 

The `commits` table is only indexed on `(stack_id, sha)` — SHA is not unique across stacks/repositories: [5](#0-4) 

`Status#after_commit :schedule_continuous_delivery` calls `commit.schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob.perform_later(stack)` for the *commit's own stack* if `deployable? && continuous_deployment? && deployable?`: [6](#0-5) [7](#0-6) 

and (per the existing test suite) a status transition to `pending`/`success` also enqueues `ProcessMergeRequestsJob.perform_later(commit.stack)`: [8](#0-7) 

Since git commit SHAs are deterministic hashes of tree/parents/author/committer/message/timestamps, forking a public victim repository preserves identical SHAs for the shared history. An attacker who owns (or forks into) a repository that is already legitimately onboarded to the same Shipit instance (so `Shipit.github(organization: repository_owner)` in `WebhooksController#verify_signature` resolves and signs correctly for the attacker's own org) can:
1. Fork the victim's public repository (or otherwise obtain a commit with an identical SHA to one already synced into `victim_stack.commits`).
2. Trigger (or directly send, via the GitHub API on their own repo) a `status` event on that SHA from their own repository. GitHub signs and delivers this webhook with the attacker's own org's secret — `verify_signature` passes because it is a genuinely GitHub-signed payload for `repository_owner = attacker's org`.
3. `StatusHandler#process` ignores `repository_owner`/`repository_name` entirely and matches `Commit.where(sha: ...)` against the whole table, hitting the victim's commit row and writing a `Status` scoped to `victim_stack`.
4. This fires `schedule_continuous_delivery`, enqueuing `ContinuousDeliveryJob.perform_later(victim_stack)` and, on `pending`/`success` transitions, `ProcessMergeRequestsJob.perform_later(victim_stack)`.

None of the existing guards catch this: `verify_signature` only validates that the payload came from *some* legitimate GitHub org (the attacker's own), not that the named repository matches the commits actually mutated; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema for `StatusHandler` only validates `sha`/`state`/etc. types, not repository scope; and `Handler#stacks`/`repository_name` exist precisely for this scoping but are simply not used by `StatusHandler`.

### Impact Explanation
An attacker with no relationship to the victim organization can cause `ProcessMergeRequestsJob` (and `ContinuousDeliveryJob`) to run against `victim_stack`, purely by controlling a webhook-signed event on their own onboarded repository whose commit SHA happens to collide with a commit already present in the victim's stack (trivially achievable by forking a public victim repo). This is a genuine cross-repository write: a `Status` record is created for `victim_stack`/`victim_commit` that the victim's repository never authenticated or authorized, and downstream background jobs process merges/deploys for that stack. This matches "Critical: a payload for one repository mutating another's stack, commit... or an unauthorized deploy, rollback or merge" since the enqueued `ProcessMergeRequestsJob`, if the victim stack has queued merge requests (`merge_requests.to_be_merged` non-empty), can proceed to merge without the victim ever authorizing that webhook event. It is repeatable against any stack whose commits share a SHA with a repository the attacker can get onboarded and legitimately signed webhooks for (most straightforwardly, forks of victim's own public repo, if the victim repo itself, or a fork of it, is separately onboarded as another stack — e.g. staging/canary forks, or any multi-stack setup sharing history).

### Likelihood Explanation
Preconditions: attacker must control (own) a GitHub repository that is already onboarded as a Shipit stack in the same instance (so a real, signed webhook can be delivered for it), and a target victim stack must contain a commit whose SHA matches one reachable by the attacker (trivial via forking a public repo, or if attacker's repo and victim's repo share history). No secrets are needed — the attacker relies entirely on GitHub's own webhook signing for their own legitimately configured repository. Cost is low: fork the repo, trigger a status update via GitHub Actions/API on their own fork using their own `GITHUB_TOKEN`, wait for GitHub to deliver the webhook. It is fully repeatable against any stack sharing history/SHAs with an attacker-controlled onboarded repository.

### Recommendation
Scope `StatusHandler#process` to the repository named in the verified payload, mirroring `PushHandler`: iterate over `stacks.find_each { |stack| stack.commits.find_by(sha: params.sha)&.create_status_from_github!(params) }` (or restrict the `Commit.where(sha:)` query to `.where(stack_id: stacks.ids)`), so a status originating from repository X can never mutate commits/stacks belonging to a different repository.

```ruby
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test "status webhook for attacker's repo must not enqueue jobs for a victim stack sharing the same commit sha" do
          victim_stack = shipit_stacks(:shipit)
          attacker_repo = Repository.create!(owner: 'attacker', name: 'decoy')
          Stack.create!(repository: attacker_repo, environment: 'production')

          shared_sha = 'deadbeef' * 5
          victim_commit = victim_stack.commits.create!(
            sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus),
            authored_at: Time.now, committed_at: Time.now, message: 'shared history commit'
          )

          payload = {
            'repository' => { 'full_name' => 'attacker/decoy', 'owner' => { 'login' => 'attacker' } },
            'sha' => shared_sha,
            'state' => 'success'
          }

          assert_no_enqueued_jobs(only: [ProcessMergeRequestsJob, ContinuousDeliveryJob]) do
            StatusHandler.call(payload)
          end
          # BEFORE FIX: this assertion instead PASSES, proving the broken binding:
          # assert_enqueued_with(job: ProcessMergeRequestsJob, args: [victim_stack]) { StatusHandler.call(payload) }
        end
      end
    end
  end
end
```
Equality checked: LHS = stack passed to `ProcessMergeRequestsJob.perform_later` (== `victim_commit.stack` == `victim_stack`); RHS = `Repository.from_github_repo_name(payload['repository']['full_name']).stacks` (== stacks of `attacker/decoy`). Before the fix these diverge (LHS = `victim_stack`, RHS = attacker's stack); the PoC demonstrates the divergence by showing the job is enqueued for `victim_stack` despite the payload naming `attacker/decoy`.
