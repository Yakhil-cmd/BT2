### Title
Cross-repository status forgery bypasses `Commit#deployable?` binding to `stack.repository` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Webhooks::Handlers::StatusHandler#process` looks up commits by SHA only (`Commit.where(sha: params.sha)`), without checking that the webhook's `repository.full_name` matches `stack.repository`. `Commit#deployable?` and `Stack#deploy_failed?` never re-validate the origin of the status, so a `success` status forged from an attacker-controlled repository sharing the same commit SHA (e.g. a public fork) can flip a tracked stack's commit into `deployable?` state, independent of whether the commit previously failed a real deploy attempt.

### Finding Description
The claimed binding is: `deployable? == true` should hold only when every status contributing to it originated from a webhook whose `repository.full_name == stack.repository` (verified via signature scoped to the correct org/repo). Tracing the code:

- `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [1](#0-0) , where `success?` delegates to `status`, itself built from `statuses_and_check_runs` [2](#0-1) [3](#0-2) .
- `Commit#deploy_failed?` is entirely separate: `stack.deploys.unsuccessful.where(until_commit_id: id).any?` [4](#0-3) . For a commit with no prior `Task`/`Deploy` rows this is always `false` and contributes nothing to blocking deployment — it only reflects prior failed deploy attempts, not status authenticity.
- The webhook entry point `WebhooksController#verify_signature` only verifies the HMAC signature using the GitHub App keyed by `repository_owner` (the org in the payload) [5](#0-4) . It authenticates "this event genuinely came from GitHub for this org's app installation," not "this event's repository is the one tracked by any particular Stack."
- `Webhooks::Handlers::StatusHandler#process` then resolves target commits purely by SHA, with no repository/stack filter at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [6](#0-5) .

Because git commit SHAs are content-addressed, an attacker who forks a public tracked repository shares identical SHAs for any commit they don't modify. The attacker (an unprivileged GitHub user, owner of their own fork/repo) can install/trigger a status webhook from their own repository (a fully legitimate, correctly-signed GitHub event for their own org) carrying a `success` state for a SHA that also exists as a `Shipit::Commit` row belonging to a victim stack. `StatusHandler` applies that status to every `Commit` row matching that SHA — including the victim's — regardless of `repository.full_name`.

`should_delay_continuous_delivery?`/`deploy_failed?` do not close this gap: they only look backward at completed `Deploy` rows for that specific commit. For any commit that has never been deployed (no prior `Task` rows — the common case for a brand-new commit that just landed), `deploy_failed?` is `false` regardless of the forged status, so it cannot "catch" the forgery; the forged `success` status is the sole determinant of `deployable?`.

### Impact Explanation
An attacker can make an undeployed commit in a victim's tracked stack appear `deployable?` (and, via `create_status_from_github!` → `add_status` → `schedule_merges`/`Hook.emit(:deployable_status, ...)`, trigger continuous-delivery scheduling and merge-queue processing) without ever authenticating against the victim's repository or webhook secret. This is a cross-repository write: a payload signed for repository A mutates `Shipit::Status`/`Commit` state belonging to stack/repository B, satisfying the "payload for one repository mutating another's stack/commit" Critical criterion. If the affected stack has `continuous_deployment` enabled, this can trigger an unauthorized deploy of a commit whose real CI/status was never verified for that repository.

### Likelihood Explanation
Preconditions: the victim repository must be public (so the attacker can fork it and obtain identical SHAs for shared commits), and the attacker needs a GitHub repo of their own capable of emitting a `status` webhook event (trivial — any repo with a CI integration, or the attacker's own script hitting GitHub's Statuses API on their fork triggers GitHub's own outbound status webhook to Shipit if the app/webhook is installed org-wide, or the attacker can get an app installed on their own account if the Shipit GitHub App is publicly installable). No Shipit secrets, sessions, or API tokens are required — only a legitimately GitHub-signed event for an org the attacker controls. The remaining requirement (SHA collision) is met "for free" whenever the attacker forks and does not need to fabricate a colliding hash — it's inherent to git history sharing.

### Recommendation
In `StatusHandler#process` (and equivalently `CheckSuiteHandler`), filter `Commit` lookups by the stack's repository: join through `stack: :repository` and require `repository.full_name == params.repository.full_name` (or equivalent verified full_name from the webhook payload) before calling `create_status_from_github!`. Do not rely on SHA alone to scope cross-tenant state mutation.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (illustrative)
test "status webhook from unrelated repository must not affect a stack's commit deployability" do
  victim_stack = shipit_stacks(:shipit) # repository "shopify/shipit-engine"
  commit = victim_stack.commits.create!(sha: "a" * 40, message: "shared commit", ...)
  refute_predicate commit, :deploy_failed?  # no prior Task rows -> false
  refute_predicate commit, :deployable?     # no status yet

  # Attacker owns "attacker/fork-of-victim" which shares the same SHA.
  # Binding under test: deployable? == true only if the status came from a webhook naming stack.repository ("shopify/shipit-engine").
  forged_status = OpenStruct.new(sha: commit.sha, state: "success", context: "ci/forged",
                                  branches: [{ name: "master" }])
  # Simulate StatusHandler#process behavior directly (sha-only lookup, no repo check):
  Shipit::Commit.where(sha: forged_status.sha).each { |c| c.create_status_from_github!(forged_status) }

  commit.reload
  assert_predicate commit, :deployable?     # forged cross-repo status flipped this to true
  refute_predicate commit, :deploy_failed?  # unchanged, still false -- proves deploy_failed? cannot catch this
  refute victim_stack.should_delay_continuous_delivery?(commit) if victim_stack.respond_to?(:should_delay_continuous_delivery?)
end
```
This demonstrates the equality `deployable? == true` holding even though the contributing status did not originate from a webhook naming `stack.repository`, and that `deploy_failed?` (and any continuous-delivery delay check keyed off it) provides no protection for commits with no prior deploy history.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
