### Title
Webhook authentication is keyed on `repository.owner.login`/`organization.login` while the actual write target is resolved from the independent `repository.full_name` field, enabling cross-repository/cross-organization event forgery in multi-org installs - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository_owner`, computed from the payload's `repository.owner.login` (falling back to `organization.login`). Once the signature check passes, the handler pipeline resolves the *actual* repository/stack to write to using a completely different payload field, `repository.full_name` (`Handler#repository_name`). Because both fields live in the same attacker-supplied JSON body and are never cross-checked against each other, the identity that "authenticates" the request (the owner login used to pick the secret) is not bound to the identity whose data actually gets mutated (the full_name used to look up the `Stack`).

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

`GitHubApp#verify_webhook_signature` is the only cryptographic gate, and it is a documented per-organization value (`docs/setup.md` "Using Multiple Github Applications"), and it also **auto-passes when no secret is configured for that organization**:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

After the signature gate, `Shipit::Webhooks.for_event(event)` dispatches the parsed JSON to handlers such as `PushHandler`, `StatusHandler`, `PullRequest::*Handler`, all inheriting `Handler#stacks`/`repository_name`, which resolve the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` — an entirely different field of the same attacker-controlled body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

The binding that should hold is: **organization that authenticated the request == organization/repository whose stacks are written**. Because `repository_owner` (auth) and `repository.full_name` (write target) are independent, unvalidated fields inside the same POST body, an attacker who can produce (or does not need) a valid signature for organization A can set `repository.full_name` to `orgB/some-tracked-repo` and have the payload processed against organization B's stacks. In the documented multi-app configuration (`config/secrets.yml` keyed by organization, each with its own optional `webhook_secret`), if *any* configured organization has no `webhook_secret` set (explicitly described as "optional" in the setup guide), `verify_webhook_signature` unconditionally returns `true` for requests whose `repository.owner.login`/`organization.login` matches that organization — regardless of what `repository.full_name` says. This lets an unauthenticated caller forge `push`, `status`, `check_suite`, or `pull_request` events for **any** repository/stack tracked by the Shipit instance, not just the unprotected organization's own repositories.

### Impact Explanation
This breaks the equality "organization that authenticated == repository that is written," producing cross-repository writes: forged `push` events queue `GithubSyncJob` for unrelated stacks, forged `status` events create arbitrary commit statuses (`StatusHandler`) that can satisfy deploy-blocking status requirements on commits in a different repository, and forged `pull_request`/`check_suite` events mutate PR/label/merge-queue state for stacks the attacker's "authenticated" organization has no relationship to. This matches the Critical criterion "cross-repository writes," since state belonging to one repository/organization can be altered by a request that was only proven to originate from a different, unrelated organization's configuration slot.

### Likelihood Explanation
Exploitability is fully conditioned on operator configuration: the installation must use the documented multi-organization `github:` mapping in `config/secrets.yml`, and at least one configured organization entry must omit `webhook_secret` (explicitly presented as optional in setup documentation). If every configured organization has a `webhook_secret` set, the attacker still needs to know that secret to forge a valid signature, which is out of scope per this engine's own trust model. Thus the exposure is real but entirely dependent on the deploying organization's own secrets configuration choices — analogous to the original report's dependence on the guardian's diligence — and is not exploitable against a "fully secured" configuration where every configured GitHub App has a webhook secret.

### Recommendation
Bind the authenticated identity to the identity acted upon: after `verify_webhook_signature` succeeds, re-derive `repository_owner` from the same field the handlers use (`repository.full_name`'s owner segment) and reject the request if it disagrees with the field used to pick the verifying secret. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in a multi-organization configuration — treat a missing secret as a hard configuration error for that organization slot rather than an authentication bypass.

### Proof of Concept
1. Operator configures Shipit with two organizations in `config/secrets.yml`: `orgA` (no `webhook_secret` set) and `orgB` (proper `webhook_secret`, with tracked stacks for `orgB/critical-repo`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/critical-repo" }
}
```
3. `verify_signature` computes `repository_owner = "orgA"`, fetches `orgA`'s `GitHubApp`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — no valid signature is required at all.
4. `StatusHandler` resolves `repository_name = "orgB/critical-repo"` and creates/updates a commit status on `orgB`'s tracked stack, even though the request was never authenticated against `orgB`'s configuration.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
