### Title
Private-asset payments sent to an Autonomous Agent are silently unrecoverable — never trigger the AA, never credited to its balance, and can never be spent by it - ([File: main_chain.js, storage.js, aa_composer.js])

### Summary
The Sherlock finding shows a class of bug where value that actually reaches a contract/AA's control can never be recognized or later used because the accounting logic that decides "how much can I use/receive" is built on a filter that structurally excludes the actual incoming value. In ocore, an analogous structural exclusion exists for private-asset payments sent to an AA address: the code that detects AA triggers, the code that seeds an AA's `aa_balances`, and the periodic consistency check `checkBalances()` all explicitly filter out `is_private=1` outputs. A private-asset payment sent to an AA address is therefore accepted into the DAG as a valid, spent-nothing output sitting at the AA's address, but it never becomes a trigger, is never added to `aa_balances`, and can never be referenced by `balance[asset]` or spent by the AA's own formulas — permanently locking the funds at that address.

### Finding Description
1. In `main_chain.js`, `handleAATriggers()` selects candidate AA triggers from stable, good-sequence outputs, but explicitly filters `AND (outputs.asset IS NULL OR is_private=0)`: [1](#0-0) 
This means any output paying a *private* asset to an AA's address is never inserted into `aa_triggers`, so `handleTrigger()`/`handlePrimaryAATrigger()` is never invoked for it — the AA never runs, never bounces it, and never gets a chance to refund it.

2. `insertAADefinitions()` in `storage.js`, which seeds `aa_balances` for a newly-activated AA from pre-existing unspent outputs at its address, uses the same exclusion: `AND (is_private=0 OR is_private IS NULL)`: [2](#0-1) 
So even outputs that predate the AA's activation are never counted if they are private-asset outputs.

3. The invariant-checking job `checkBalances()`, which cross-validates `aa_balances` against actual unspent `outputs`, also restricts its comparison to `(is_private=0 OR is_private IS NULL)`: [3](#0-2) 
This confirms private outputs are categorically outside the AA balance-accounting universe by design/consistency, not merely as an incidental omission in one code path.

4. On the AA output side, the composer explicitly refuses to let an AA even attempt to *send* a private asset, with the comment acknowledging the underlying reason (lack of spend proofs): [4](#0-3) 
This shows the developers were aware AAs cannot participate in private-asset spend-proof chains, but the receiving side has no analogous protection: nothing stops a private-asset payment from being *sent to* an AA address, and once sent, that value is invisible to every mechanism (`balance[asset]` formula reads, `handleTrigger`, and future `aa_balances` reconciliation) that the AA or the network use to decide what can be spent.

5. `checkAAOutputs()` (used by `wallet.js`'s `sendMultiPayment`), which is the only guard invoked when a wallet posts a payment to an AA, only checks `bounce_fees` sufficiency — it has no logic at all examining whether the asset being sent is private: [5](#0-4) 
So nothing in the client-side guard rails prevents a caller (this could be an ordinary wallet user, a private-payment counterparty forwarding a private-asset chain, or code composing a payment on someone's behalf) from directing a private-asset payment straight into an AA's address.

Once such a private-asset output lands at an AA address:
- It is never treated as a trigger (`main_chain.js` filter), so the AA cannot execute any bounce/refund logic against it.
- It is never added to `aa_balances` (neither by `updateInitialAABalances`'s DB path, nor by `insertAADefinitions`), so `balance[asset]` in AA formulas will never reflect it.
- `checkBalances()` won't flag any discrepancy because it also excludes private assets from its comparison, so the stuck funds produce no operational alarm.

There is no code path anywhere in the surveyed files that returns, bounces, or otherwise makes this value spendable again — this is a structural (not merely intermittent) freeze, exactly analogous to the Unitas Protocol issue where the accounting variable (`portfolio`) could never reflect the yield actually held by the contract, permanently blocking use of real funds that had truly arrived.

### Impact Explanation
Any private-asset payment (including via a private payment chain sent by a counterparty, which is explicitly a reachable actor per the exercise rules) directed to an AA address results in permanent, protocol-level freezing of that value — it is neither returned to the sender (no bounce is triggered), nor credited to the AA's spendable balance, nor detectable by the network's own balance-consistency check. This is a concrete "AA fund loss/freezing" outcome. It can be triggered unintentionally by any user who is unaware that AAs can't process private assets, or deliberately by a griefer against an AA operator/users who expect that funds sent to the AA's address will be processed or refunded (e.g., a malicious counterparty in a private-payment chain choosing an AA address as recipient to permanently destroy value, or simply as an unrecoverable-loss vector affecting any user who mistakenly pays a private asset to an AA).

### Likelihood Explanation
Likelihood is high for accidental occurrence: any wallet user or automated tool that composes a private-asset payment (which is a normal, supported wallet feature) with an AA address as the recipient will trigger this — there is no client-side (`checkAAOutputs`) or protocol-side warning/rejection preventing it. It also requires no special privileges: a normal unit poster or private-payment counterparty can create this condition with an ordinary transaction.

### Recommendation
Add validation rejecting (at broadcast/composition time via `aa_addresses.checkAAOutputs`, and ideally at consensus validation time in `validation.js`/`main_chain.js`) any attempt to send a private (`is_private=1`) asset payment to a known AA address, since AAs structurally cannot process or account for such funds. Alternatively, extend `handleAATriggers()`, `insertAADefinitions()`, and `aa_balances` bookkeeping to properly recognize and either process or refund private-asset outputs sent to AA addresses, and update `checkBalances()` accordingly so any residual private-asset value at AA addresses is visible for reconciliation/refund logic.

### Proof of Concept
1. Deploy any AA (its definition is irrelevant since the trigger will never fire).
2. From a normal wallet, issue or hold a private (non-`fixed_denominations` or fixed-denomination) asset (`is_private: true`) — this is standard private-asset functionality already present in ocore (`indivisible_asset.js`, `divisible_asset.js`, `private_payment.js`).
3. Send a payment of that private asset to the AA's address using the normal wallet payment flow (`wallet.js: sendMultiPayment`); `checkAAOutputs` only checks bounce fee sufficiency for `base`/public balances and does not block this.
4. Observe: the unit stabilizes normally (private outputs are validated the same as any private payment; nothing in `validatePayment`/`validatePaymentInputsAndOutputs` forbids the recipient being an AA).
5. Observe in `main_chain.js: handleAATriggers()` that this output's `unit`/`address` pair is excluded from the `aa_triggers` INSERT because of `AND (outputs.asset IS NULL OR is_private=0)` — the AA is never invoked for this payment.
6. Query `aa_balances` for the AA address/asset: no row exists / no credit was applied, matching `storage.js: insertAADefinitions`'s and `aa_composer.js: checkBalances()`'s identical `is_private` exclusion — confirming the funds are permanently outside any AA-recognized balance and can never be referenced by `balance[asset]` or spent in a future AA response.

function checkAAOutputs(arrPayments, handleResult) {
	var assocAmounts = {};
	arrPayments.forEach(function (payment) {
		var asset = payment.asset || 'base';
		payment.outputs.forEach(function (output) {
			if (!assocAmounts[output.address])
				assocAmounts[output.address] = {};
			if (!assocAmounts[output.address][asset])
				assocAmounts[output.address][asset] = 0;
			assocAmounts[output.address][asset] += output.amount;
		});
	});
	var arrAddresses = Object.keys(assocAmounts);
	readAADefinitions(arrAddresses, function (err, rows) {
		if (err)
			return handleResult(err);
		if (rows.length === 0)
			return handleResult();
		var arrMissingBounceFees = [];
		rows.forEach(function (row) {
			var arrDefinition = JSON.parse(row.definition);
			var bounce_fees = arrDefinition[1].bounce_fees;
			if (!bounce_fees)
				bounce_fees = { base: constants.MIN_BYTES_BOUNCE_FEE };
			if (!bounce_fees.base)
				bounce_fees.base = constants.MIN_BYTES_BOUNCE_FEE;
			for (var asset in bounce_fees) {
				var amount = assocAmounts[row.address][asset] || 0;
				if (amount < bounce_fees[asset])
					arrMissingBounceFees.push({ address: row.address, asset: asset, missing_amount: bounce_fees[asset] - amount, recommended_amount: bounce_fees[asset] });
			}
		});
		if (arrMissingBounceFees.length === 0)
			return handleResult();
		handleResult(new MissingBounceFeesErrorMessage({ error: "The amounts are less than bounce fees", missing_bounce_fees: arrMissingBounceFees }));
	});
}
