### Title
Webhook signature is verified against the org named in `repository.owner.login`/`organization.login` while the target Stack/Repository is selected from the unrelated `repository.full_name` field, allowing cross-tenant event forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App / `webhook_secret` to validate a webhook against using `repository_owner`, derived from `repository.owner.login` (or `organization.login`) in the untrusted, still-unverified JSON body. Once the HMAC check passes, the actual write target for every event handler is computed independently from a *different* field, `repository.full_name`, via `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing enforces that the organisation segment of `full_name` matches the `owner.login`/`organization.login` used to select the signing secret, so a signature that is valid for tenant A's app can be replayed with a forged `repository.full_name` pointing at tenant B's repository.

### Finding Description
Signature selection and verification: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the request body's `repository.owner.login` (falling back to `organization.login`), and is used only to look up which of the (potentially many, per multi-tenant `config/secrets.yml`) configured GitHub Apps' `webhook_secret` should validate `X-Hub-Signature` against the raw body: [3](#0-2) 

Once `verify_signature` passes, `Shipit::WebhooksController#create` dispatches the parsed body to the registered handler(s) unmodified: [4](#0-3) 

All handlers derive the Stack/Repository they operate on from `repository.full_name`, a completely separate key from the one used for signature selection: [5](#0-4) 

For example `PushHandler` uses `stacks` (i.e., `Repository.from_github_repo_name(repository_name)`) to sync commits, and `PullRequest::OpenedHandler` resolves its target `repository` the same way and feeds attacker-controlled PR fields (head sha/ref, labels, assignees) straight into `ReviewStackAdapter.find_or_create!`: [6](#0-5) [7](#0-6) 

Shipit explicitly supports multiple independently configured GitHub organisations/Apps, each with its own `webhook_secret`, in a single instance: [8](#0-7) [9](#0-8) 

**Equality that should hold but doesn't:** `organization that authenticated the webhook signature == organization owning the repository the handlers write to`. Because `repository_owner` (used to pick/verify the secret) and `repository.full_name`'s owner segment (used to pick the Stack that is mutated) are two independent, attacker-supplied fields that are never cross-checked, this equality can be broken by construction.

### Impact Explanation
An actor who legitimately administers one tenant's GitHub App configuration in a shared/multi-tenant Shipit deployment (i.e., knows their own org's `webhook_secret`, which is a normal, unprivileged part of onboarding a repository — not an admin of Shipit itself, and not privileged access to another org) can sign a payload with their own valid secret while setting `repository.owner.login`/`organization.login` to their own org (to pass `verify_signature`) but `repository.full_name` to a victim tenant's repository. Handlers then act on the victim's `Stack`/`Repository` using attacker-chosen payload contents (forged PR metadata driving review-stack creation, forged commit-status payloads recorded against real commits via `StatusHandler`, forged push events driving `GithubSyncJob`, etc.). This is a cross-tenant write achieved purely by exploiting the mismatch between the authentication binding and the data-selection binding — i.e., a cross-repository write / unauthorized-action class issue as called out in the impact criteria.

### Likelihood Explanation
Exploitation only requires being a legitimate, low-privilege tenant of a shared Shipit instance (one who knows their own org's `webhook_secret`, which many organisations distribute to CI/infra teams) and the ability to send an arbitrary HTTP POST with a correctly computed HMAC — no access to the victim org, no Shipit session, and no GitHub write access to the victim repository is required. The bug is a straightforward code-review finding (two independently-sourced fields never compared), not dependent on race conditions or unusual configuration beyond the documented and supported multi-org setup.

### Recommendation
After computing the signing organisation and parsing the payload, verify that the organisation portion of `repository.full_name` (and/or `organization.login`) equals the `repository_owner` value used to select the `webhook_secret`, rejecting the request with `422` if they differ. Alternatively, resolve the target `Stack`/`Repository` via the same trusted identifier that was used to select and verify the signature, rather than trusting the payload's `repository.full_name` independently.

### Proof of Concept
1. Shipit is configured (per `config/secrets.yml`) with two GitHub orgs: `attacker-org` (webhook_secret known to the attacker) and `victim-org` (owns `victim-org/victim-repo`, a `Stack` in this Shipit instance).
2. Attacker crafts a `push` (or `pull_request`) webhook JSON body where `repository.owner.login` = `"attacker-org"` but `repository.full_name` = `"victim-org/victim-repo"`.
3. Attacker computes `X-Hub-Signature` as `sha1=HMAC(attacker-org's webhook_secret, raw_body)` and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully because the signature does match that org's secret — see: [1](#0-0) 
5. `create` dispatches to `Shipit::Webhooks.for_event('push')`, whose `PushHandler#process` resolves `stacks` via `repository_name` = `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, and triggers `stack.sync_github(...)` on the victim's Stack: [6](#0-5) 
6. No code path compares `"attacker-org"` (the authenticated identity) against `"victim-org"` (the acted-upon identity), so the forged event is processed as if it legitimately originated from GitHub for `victim-org/victim-repo`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
