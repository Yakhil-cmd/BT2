### Title
Cross-stack authorization bypass in CCMenu API — stack-scoped `ApiClient` tokens can read the CI status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` scopes which stacks an `ApiClient` may act on via the `stacks`/`stack` helper methods, which restrict the resolvable `Stack` set to `current_api_client.stack_id` when the client is stack-scoped. `Shipit::Api::CCMenuController` overrides `stack` and resolves it directly from the unscoped `Stack` model, bypassing that scoping entirely. `require_permission :read, :stack` only checks that the token carries the `read:stack` permission string — it never checks that the specific stack being requested is the one the token is authorized for.

### Finding Description
In `app/controllers/shipit/api/base_controller.rb`, the intended trust binding is: `current_api_client.stack_id` (the stack a token is scoped to) == the `Stack` record any endpoint using `stack`/`stacks` actually touches: [1](#0-0) 

`stacks` filters to `Stack.where(id: current_api_client.stack_id)` only when `current_api_client.stack_id?` is true, and `stack` calls `stacks.from_param!(...)`, so any endpoint built on top of this properly enforces the scope.

`Shipit::Api::CCMenuController`, however, defines its own `stack`, which calls `Stack.from_param!(params[:stack_id])` directly — never going through `stacks`, i.e., never applying the `current_api_client.stack_id` filter: [2](#0-1) 

The controller's only authorization gate is `require_permission :read, :stack`: [3](#0-2) 

`check_permissions!` only validates the permission string is present on the token; it performs no per-resource/stack check: [4](#0-3) 

The equality that should hold — `current_api_client.stack_id == params[:stack_id]` (when the token is scoped) — is broken specifically in `CCMenuController#stack`. `CCMenuController` also allows the token to be supplied as a query-string `token` parameter, widening reachability (e.g. via logs, browser history, referrer leakage), but the core break is the missing scope filter: [5](#0-4) 

This directly mirrors the report's bug class: a value the authorization layer is supposed to gate on (`payout.ratio`/here, the token's `stack_id` scope) is silently bypassed in one specific code path, letting an operation proceed against data/state it was never authorized to touch (minting for the wrong generation / here, reading the wrong stack).

### Impact Explanation
A stack-scoped `ApiClient` token (an `ApiClient` created with `stack_id` set — the mechanism used to restrict integrations/CI tools to a single stack) can call `GET /api/1/cc/:stack_id/cc.xml` for any other stack's `to_param`, and it will succeed as long as the token has the generic `read:stack` permission. This discloses that stack's deploy/CI state — name, activity, last build status/label/time, and web URL to the deploy — for stacks the token was never meant to see. This is unauthenticated-relative-to-token read of stack/deploy state across the intended isolation boundary between tenants/teams sharing one Shipit instance, matching the "High — unauthenticated read of stack state, task streams or deploy output" impact category via escalation beyond the token's authorized scope.

### Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped API token (a normal, unprivileged, restricted credential intentionally limited to one stack) can trigger this with a single unauthenticated-scope GET request, no special conditions needed. The scoped-token model exists specifically to be handed to lower-trust consumers (e.g., third-party CI dashboards), so this is a realistic, low-effort exploitation path once a scoped token exists — a normal, supported deployment configuration.

### Recommendation
Change `CCMenuController#stack` to reuse the base controller's scoped resolution (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so the `current_api_client.stack_id` restriction is enforced identically to every other API endpoint.

### Proof of Concept
1. Admin creates two stacks, Stack A and Stack B.
2. Admin issues a stack-scoped `ApiClient` token restricted to Stack A (`stack_id = A.id`, `permissions: ['read:stack']`).
3. The token holder requests `GET /api/1/cc/<Stack-B-to_param>/cc.xml?token=<token>` (or via HTTP Basic auth).
4. `authenticate_api_client` succeeds (valid token) and `require_permission :read, :stack` passes (`read:stack` present).
5. `stack` resolves via `Stack.from_param!(params[:stack_id])`, unscoped, returning Stack B — not restricted to Stack A.
6. The response renders Stack B's CI/deploy status via `shipit/ccmenu/project`, disclosing data the token was never authorized to access: [6](#0-5)
