### Title
Unstable-unit cache wiped and asynchronously rebuilt in `storage.resetMemory()` without waiting for concurrent validation readers - ([File: storage.js])

### Summary
`storage.resetMemory()` (invoked from `writer.saveJoint()` on a write failure) synchronously empties `assocUnstableUnits` / `assocBestChildren` and then asynchronously repopulates them from the DB. The `"write"` mutex held by `saveJoint()` only serializes writers against each other; it does **not** serialize against concurrent unit validations, which lock only on the author addresses of the unit being validated. This is directly analogous to the kernel bug: `xfrm_policy_fini()` freed the RCU-protected `policy_bydst` tables without `synchronize_rcu()`, so concurrent RCU readers could dereference freed/half-updated tables. Here, concurrent `validate()` calls (readers of the shared in-memory unit-props cache) can run during the clear→repopulate gap and observe an empty/partial cache for units that the database still reports as unstable.

### Finding Description
`writer.saveJoint()` acquires the `"write"` mutex at entry: [1](#0-0) 
On a write error it calls `storage.resetMemory(conn)`: [2](#0-1) 

`resetMemory()` synchronously deletes every key of `assocUnstableUnits`/`assocBestChildren` and then kicks off an asynchronous DB re-population before returning: [3](#0-2) 

Meanwhile, unit validation (`validation.js`) never contends for the `"write"` mutex; it locks only on the set of author addresses of the unit being validated: [4](#0-3) 

`readUnitProps()`, called throughout validation (parents, authors, AA triggers, etc.), trusts `assocUnstableUnits` as the source of truth for any unit not already in `assocStableUnits`, and **throws** if the DB says a unit is unstable but the in-memory cache disagrees: [5](#0-4) [6](#0-5) 

Because `resetUnstableUnits()`/`resetStableUnits()` clear the caches synchronously but repopulate them only after an `await`ed DB query completes, any `validate()` call for an unrelated unit that happens to interleave in that window (a different author, so it never contends on `"write"`) can call `readUnitProps()` on a genuinely-unstable unit while `assocUnstableUnits` is momentarily empty or only partially rebuilt, hitting `throw Error("no unstable props of "+unit)`. This is the direct analog of dereferencing memory that was freed but not yet safely republished: the reader observes a transiently torn/empty version of a structure that other code assumes is always internally consistent under a lock it does not hold.

### Impact Explanation
An uncaught exception thrown mid-validation from `readUnitProps()` propagates out of the async validation pipeline and, given Node's default unhandled-rejection/exception behavior in this codebase (many such `throw Error(...)` calls are used deliberately as fatal invariant violations), crashes or aborts the hub/full node process handling validation. Because this can be triggered by any posted unit that causes a write failure (e.g., a doublespend/rollback path exercising `resetMemory`) racing with ordinary concurrent unit posting from unrelated authors, an unprivileged unit poster can cause validity-engine crashes/inconsistent state on a node, disrupting the node's ability to validate and confirm new units — i.e., "network unable to confirm new units" / node disagreement on validity, matching the required impact classes for a High-severity analog.

### Likelihood Explanation
Triggering a `saveJoint` failure path (which invokes `resetMemory`) requires forcing a DB write error/rollback, which is less directly attacker-controlled than a pure validation bug, and the race window is a single Node.js event-loop tick during an `await`ed DB query — narrow but real, and reproducible under load (multiple units from different authors posted concurrently while one triggers a rollback). This keeps likelihood at "requires specific timing/conditions" rather than trivially reproducible on every run, consistent with a Medium-High likelihood.

### Recommendation
Ensure `resetMemory()`/`resetUnstableUnits()`/`resetStableUnits()` execute under the same lock domain that all readers of `assocUnstableUnits`/`assocStableUnits` respect (e.g., take a global cache-mutex around both the clear and the full repopulation, or perform an atomic swap of a freshly-built object into `assocUnstableUnits` only after the DB read completes, rather than deleting keys up front). Alternatively, make `readUnitProps()` tolerate a cache miss during rebuild by re-querying instead of throwing a fatal invariant violation.

### Proof of Concept
1. Node A is running normally with several unstable units cached in `assocUnstableUnits`.
2. Attacker posts unit `U1` in a way that causes `writer.saveJoint()`'s commit to fail (forcing the `err` branch), triggering `await storage.resetMemory(conn)`, which synchronously wipes `assocUnstableUnits`.
3. Concurrently (same tick/very next tick), a second unrelated unit `U2` from a different author is posted and enters `validation.js`'s `validate()`; since it locks only on `U2`'s author addresses (not `"write"`), it proceeds into `readUnitProps()` for a parent unit `P` that the DB reports as unstable.
4. Because `assocUnstableUnits` was just cleared and not yet repopulated, `readUnitProps()` hits `if (!assocUnstableUnits[unit]) throw Error("no unstable props of "+unit)`, crashing/aborting validation on the node. [6](#0-5)
