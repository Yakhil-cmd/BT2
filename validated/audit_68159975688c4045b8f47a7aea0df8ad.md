### Title
Cross-organization webhook forgery via mismatched signing-organization and target-repository fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GithubApp`/`webhook_secret` to validate the HMAC signature against using the `repository.owner.login` (or `organization.login`) field of the JSON body, while the actual write target — the `Stack`/`Repository` acted upon by every webhook handler — is resolved from a *different* field, `repository.full_name`, in `Handler#repository_name`. Nothing binds these two fields together, so a webhook that is validly signed for one configured GitHub organization can carry a `repository.full_name` pointing at a repository owned by a different configured organization.

### Finding Description
`Shipit::WebhooksController#verify_signature` computes the signing organization purely from the payload: [1](#0-0) [2](#0-1) 

It looks up `Shipit.github(organization: repository_owner)` and verifies the HMAC using that organization's `webhook_secret`. In a multi-tenant Shipit deployment (as documented in `config/secrets.development.shopify.yml` and `docs/setup.md`), each GitHub organization has its own GitHub App and its own `webhook_secret`.

However, once the signature check passes, every `Handler` resolves the *target* repository using a completely separate field of the same payload: [3](#0-2) 

`repository_name` reads `payload.dig('repository', 'full_name')`, which is then split into `owner/name` and looked up via `Repository.from_github_repo_name`: [4](#0-3) 

For genuine GitHub-generated payloads, `repository.owner.login` and the owner segment of `repository.full_name` are always consistent. But the controller trusts the raw, attacker-suppliable JSON body (`JSON.parse(request.raw_post)`) and never asserts that these two fields agree: [5](#0-4) 

This is exactly the storage/state-overwrite bug class in the report generalized to an authorization binding: the field that is authenticated (`repository.owner.login`, used to pick the signing secret) is not the same field that is acted on (`repository.full_name`, used to pick the repository/stack that gets mutated). An actor who legitimately possesses the `webhook_secret` for their own configured organization ("Org A") — which they obtain by administering their own GitHub App settings, not by compromising Shipit itself — can sign an arbitrary JSON body with Org A's secret while setting `repository.owner.login` to `"orgA"` and `repository.full_name` to `"orgB/some-repo"`, where Org B is a different organization/tenant configured on the same Shipit instance. The signature check succeeds (it only validates against Org A's secret), but the handler dispatched by `event` (e.g. `PushHandler`, `StatusHandler`) then mutates state belonging to Org B's repository.

Concretely, `PushHandler#process` calls `stack.sync_github(expected_head_sha:)` for every non-archived stack matching the branch of the forged `ref`, on stacks resolved from the *forged* `repository.full_name`: [6](#0-5) 

`StatusHandler` similarly creates a `Status` record on a commit belonging to the target stack based on `repository.full_name`, which can affect deployability gating that later permits a deploy to proceed.

### Impact Explanation
This breaks the equality `organization authenticated by the signature == organization whose repository is written`, letting an operator of Org A's GitHub App (an unprivileged party with respect to Org B and with respect to the Shipit application itself) forge webhook events against Org B's stacks. Depending on the dispatched handler this enables cross-repository writes (spoofed push syncs, forged commit statuses affecting deploy-gating `deployable_status`, or team/member manipulation via `membership_handler`), which can influence whether a deploy is allowed to proceed on a stack the attacker does not own. This aligns with the in-scope "cross-repository writes" / "unauthorized deploy" impact category.

### Likelihood Explanation
Medium: it requires the attacker to control at least one organization/GitHub App legitimately configured on the same multi-tenant Shipit instance (a normal, unprivileged-relative-to-Shipit scenario in the documented multi-org configuration), and to send a crafted raw HTTP POST to `/webhooks` with a self-inconsistent JSON body. No Shipit session, API token, or GitHub App private key theft is required — only the `webhook_secret` the attacker already legitimately possesses for their own org.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler#repository_name`), enforce that the organization/owner used to select the signing secret matches the owner embedded in `repository.full_name` before dispatching to handlers; reject the webhook (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own GitHub App/`webhook_secret` (per `config/secrets.development.shopify.yml`).
2. As the administrator of `orgA`'s GitHub App (who has legitimate access to `orgA`'s `webhook_secret` but no privileges over `orgB`), craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" }
}
```
3. Sign the raw body with `orgA`'s `webhook_secret` using `sha1=HMAC-SHA1(secret, body)` and send it as `X-Hub-Signature` with `X-Github-Event: push` to `POST /webhooks`.
4. `verify_signature` calls `Shipit.github(organization: 'orgA')` and validates successfully against `orgA`'s secret.
5. `PushHandler` (dispatched via `Shipit::Webhooks.for_event('push')`) resolves stacks via `Repository.from_github_repo_name('orgb/target-repo')` and calls `sync_github` on `orgB`'s stack, even though the attacker never held `orgB`'s webhook secret.
