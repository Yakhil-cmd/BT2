### Title
Uncaught Type Error in `deserializeMerkleProof` Crashes Node During "in merkle" Authentifier Evaluation - (File: definition.js, merkle.js)

### Summary
The CVE describes a crash caused by `huffcode` in FAAC dereferencing invalid memory when decoding an untrusted, malformed input table entry ("book 8" case), with no bounds/type validation before use. The analogous pattern in `ocore` exists in the `'in merkle'` address-definition operator: a unit author supplies an authentifier value (`assocAuthentifiers[path]`) that is passed directly into `merkle.deserializeMerkleProof()` without any type or format validation and without a surrounding `try/catch`, unlike the equivalent oscript function `is_valid_merkle_proof`, which explicitly type-checks and length-limits its input before deserializing.

### Finding Description
In `definition.js`, the `'in merkle'` case of `validateAuthentifiers`/`evaluate` takes the raw authentifier supplied for a signing path directly from the unit and calls the merkle deserializer on it: [1](#0-0) 

`merkle.deserializeMerkleProof` assumes its argument is a string and immediately calls `.split("-")` on it with no type check: [2](#0-1) 

If `assocAuthentifiers[path]` is not a string (e.g., a number, boolean, array, object, or `null` placed at that signing-path key in the unit's `authentifiers` object), `serialized_proof.split` does not exist and a `TypeError` is thrown. Unlike `verifyMerkleProof`, which wraps its logic in `try/catch` and returns `false` on error, `deserializeMerkleProof` in `definition.js`'s `'in merkle'` branch is called **outside** any `try/catch`, so the exception is not contained there. Contrast this with the oscript builtin `is_valid_merkle_proof`, which explicitly validates that the proof is a string, limits its length, and only enters `deserializeMerkleProof` after these checks (and even then leaves `deserializeMerkleProof` outside the following `try` block, though the string-type guarantee prevents a throw there): [3](#0-2) 

No equivalent type check exists for the `'in merkle'` path in `definition.js`, so a malformed non-string authentifier value reaches the unguarded `.split()` call and throws.

This exception propagates up through the `async.eachSeries` callback chain used by `validateAuthentifiers`/`validateDefinition`, through `validateAuthors` in `validation.js`, all the way out of `validate()`. Because this occurs inside a callback invoked asynchronously (not inside the `try{...}catch(e){...}` block that wraps only the synchronous unit-hash calculation in `validate()`), it becomes an uncaught exception at the process level. `network.js` installs a global handler that deliberately **re-throws** to terminate the process on any uncaught exception: [4](#0-3) 

### Impact Explanation
An attacker can craft and broadcast a unit whose address definition includes an `'in merkle'` clause, and sign/post it with an authentifier value at the corresponding path that is not a string (e.g. a JSON number, boolean, or nested object/array — all of which are valid JSON but invalid for this operator). When any full node (or hub) validates this unit, the `'in merkle'` evaluation path throws an uncaught `TypeError`, which per `network.js`'s `uncaughtException` handler causes the node process to crash. This is a network-wide denial-of-service: any node processing the malicious unit — not just a targeted victim — halts, potentially preventing confirmation of new units if propagated broadly, directly mirroring the "denial of service" impact of the original CVE (crash triggered by malformed/untrusted input reaching an unvalidated decode routine).

### Likelihood Explanation
The `'in merkle'` operator and address-definition mechanism are core, unprivileged features usable by any address owner defining a smart-contract-style address, requiring only that they construct and post a signed unit with a non-string value at the authentifier path corresponding to the `'in merkle'` condition. No special privileges, hub/peer position, or network position are required — it is directly reachable by "an unprivileged unit poster" as scoped. The likelihood is high provided the crafted authentifier value passes the earlier structural checks in `validation.js`/`validateAuthors` that gate entry into `validateAuthentifiers`/`evaluate`; I was not able to fully trace, within the remaining tool budget, whether an upstream check elsewhere strictly forces every value in `authentifiers` to be a string before `assocAuthentifiers` is built and passed to `evaluate`. This should be verified directly against the code (or with a proof-of-concept unit) before treating this as fully confirmed, since if such a check exists, this specific analog would be blocked earlier in the pipeline.

### Recommendation
- In the `'in merkle'` case of `definition.js`, validate that `assocAuthentifiers[path]` is a non-empty string (and enforce a maximum length, mirroring the 1024-byte cap used in `is_valid_merkle_proof`) before calling `merkle.deserializeMerkleProof`.
- Wrap the call to `merkle.deserializeMerkleProof` (and the subsequent `merkle.verifyMerkleProof`) in a `try/catch` within `definition.js`, treating any parse/verify failure as `cb2(false)` rather than allowing an exception to propagate.
- As defense in depth, harden `merkle.deserializeMerkleProof` itself to check `typeof serialized_proof === 'string'` and return/throw a normal validation error instead of a raw `TypeError` on `.split`.

### Proof of Concept
1. Construct an address whose definition includes `['in merkle', [[oracleAddress], 'feed_name', 'expected_value']]` as (part of) a signing condition.
2. Build a unit spent from/authored by that address where the `authentifiers` object at the corresponding signing path (e.g. `"r.0"`) is set to a non-string JSON value, e.g. `authentifiers: { "r.0": 12345 }` (or `true`, or a nested object) instead of a serialized-proof string.
3. Submit/broadcast the unit to a full node for validation.
4. During `validateAuthentifiers` → `evaluate` → case `'in merkle'`, `merkle.deserializeMerkleProof(12345)` executes `(12345).split("-")`, throwing `TypeError: serialized_proof.split is not a function`.
5. The exception is uncaught within the async validation chain and surfaces at process level, triggering `network.js`'s `process.on('uncaughtException', ...)` handler, which re-throws and crashes the node process — reproducing the DoS effect analogous to CVE-2018-19886.
