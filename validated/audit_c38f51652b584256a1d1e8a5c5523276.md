This confirms the vulnerability. The `Handler` base class provides a `stacks` helper scoped to the webhook's own `repository.full_name` [1](#0-0) , and `PushHandler` correctly uses it to scope job enqueuing to only stacks belonging to the authenticated repository [2](#0-1) . `StatusHandler`, however, bypasses this scoping entirely and looks up commits globally by sha across the whole `commits` table [3](#0-2) .

### Title
Cross-tenant `Status` forgery via unscoped sha lookup enqueues `ContinuousDeliveryJob` for a foreign stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, with no constraint tying the match to the repository that authenticated the webhook. Any correctly-signed status webhook (signed by the attacker's own organization's webhook secret) that names a sha which also exists in another organization's `commits` table creates a `Status` on that foreign commit, which can trigger `Commit#schedule_continuous_delivery` and enqueue `ContinuousDeliveryJob` for a stack the attacker never authenticated for.

### Finding Description
The broken binding: the code implicitly assumes `Commit.where(sha: params.sha).stack.repository == webhook.repository`, but no code enforces `commit.stack.repository.full_name == payload.dig('repository', 'full_name')`.

Call path: `WebhooksController#create` parses the JSON body and calls `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) . `verify_signature` only checks that the HMAC signature matches the webhook secret of `repository_owner = params.dig('repository','owner','login')` [5](#0-4)  — this proves the payload was sent by *some organization the attacker controls*, not that the `sha` inside it belongs to that organization's repository. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with zero repository/stack scoping [3](#0-2) , unlike `PushHandler`, which correctly scopes via the `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) [1](#0-0) [2](#0-1) .

`create_status_from_github!` calls `add_status`, which (per `Commit#after_commit` in the fired `Status` model) invokes `schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)` for `commit.stack` — the *victim's* stack — if `deployable? && stack.continuous_deployment? && stack.deployable?` [6](#0-5) .

Exploit: the attacker registers/owns a GitHub organization+repo connected to the target Shipit instance (or otherwise controls a valid webhook secret for some organization on the instance), learns the sha of a victim's commit (public shas are easy to observe; the same sha can also appear across a fork/mirror or duplicate-tracked repository), and POSTs a `status` event webhook to `/webhooks` naming their own repository (`repository.full_name`) — so `verify_signature` passes using their own org's secret — but with `sha` equal to the victim's commit's sha. `StatusHandler` matches that sha against the global `commits` table irrespective of which repository it belongs to, creating a `Status` row on the victim's `Commit`, which can trigger continuous-delivery enqueue for the victim's stack.

None of the existing guards prevent this: `verify_signature` validates only that *a* registered org's secret produced the signature, not that the sha belongs to that org's repo; `ExplicitParameters` schema on `StatusHandler` only validates types/presence of `sha`, `state`, etc., not repository binding [7](#0-6) ; `drop_unhandled_event` and `check_if_ping` are irrelevant; there is no `Stack`-scoping filter analogous to `PushHandler`'s `stacks.not_archived.where(branch:)`.

### Impact Explanation
A payload authenticated for repository A can write a `Status` record for and enqueue a background job (`ContinuousDeliveryJob`) against a stack belonging to repository B, which never authenticated the request — this is "a payload for one repository mutating another's stack, commit ... task" as defined in Critical impact. The blast radius is any Shipit installation where distinct organizations/stacks can end up with overlapping commit shas (fork/mirror/duplicate-tracked repositories, or repos migrated between orgs), and is repeatable per webhook request with no rate limiting beyond normal HTTP throughput.

### Likelihood Explanation
Preconditions: the attacker needs (a) a webhook secret/registered organization on the Shipit instance for signing (this can be their own, legitimately-onboarded organization/repository — not a privileged secret), and (b) a target commit sha that also exists as a `Commit` row belonging to a different stack (realistic for forked/mirrored/renamed repositories, monorepo splits, or repositories re-registered under different orgs, all common operationally). Cost is a single crafted HTTP POST to `/webhooks` with a valid signature for the attacker's own repo. No GitHub or Shipit session/API token is required. This is fully repeatable and scriptable.

### Recommendation
Scope `StatusHandler#process` to only the stacks belonging to the authenticating repository, mirroring `PushHandler`'s use of the `stacks` helper, e.g.: `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) } }`, instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
minitest plan (in `test/controllers/webhooks_controller_test.rb` style, not included per scope but described):
1. Create two stacks/repositories: `victim_stack` (repository `victim/repo`, `continuous_deployment? == true`, unlocked) and `attacker_stack` (repository `attacker/repo`).
2. Create a `Commit` on `victim_stack` with `sha = "deadbeef..."`.
3. Stub `Shipit.github(organization: 'attacker').verify_webhook_signature` to return `true` (simulating attacker's own valid secret).
4. POST to `/webhooks` with `X-Github-Event: status`, body `{"sha" => "deadbeef...", "state" => "success", "repository" => {"full_name" => "attacker/repo", "owner" => {"login" => "attacker"}}}`.
5. Assert `assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack])` fires, proving the equality `commit.stack.repository.full_name == payload["repository"]["full_name"]` does NOT hold yet the job was enqueued for `victim_stack` anyway.
6. After the fix, assert the same request results in `assert_no_enqueued_jobs` because `StatusHandler` scopes lookups to `stacks` derived from `attacker/repo`, which does not include `victim_stack`'s commit.
