### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by bare SHA (`Commit.where(sha: params.sha)`), with no scoping to the repository that authenticated the webhook. Because commit SHAs are only unique per stack (indexed as `stack_id, sha`, not globally unique), an attacker who controls a repository whose GitHub App/webhook is legitimately registered with Shipit can send a real, correctly-signed `status` webhook for a commit SHA that also exists in a victim stack, causing the status to be written onto the victim's commit as well.

### Finding Description
The broken binding is: **a `status` event signed for repository A must only write `Status` rows for commits belonging to stacks associated with repository A** — i.e. `status.commit.stack.repository == repository_that_authenticated(payload)`. This invariant is violated.

Trace:
1. `Shipit::WebhooksController#create` parses the raw payload and dispatches by event name to registered handlers, after `verify_signature` confirms the payload's HMAC matches the webhook secret for `repository_owner` (`payload.dig('repository','owner','login')`). [1](#0-0) 
This only proves the payload was sent by GitHub for *some* repository owned by that org/app — it says nothing about which Shipit `Commit`/`Stack` records may be touched.
2. `Handler` base class exposes a `stacks` helper that properly scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, but `StatusHandler` does not use it. [2](#0-1) 
3. `StatusHandler#process` instead does a bare, unscoped query:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
This iterates over *every* `Commit` row in the database with that SHA, regardless of which `stack`/`repository` it belongs to.
4. `Commit#create_status_from_github!` then creates a `Status` for that commit under its own `stack_id`, triggers `enable_ci_on_stack`, and `schedule_continuous_delivery`, which can flip CI state and trigger merges/deploys. [4](#0-3) [5](#0-4) 
5. `Commit` SHAs are indexed as `(stack_id, sha)`, not uniquely per SHA: [6](#0-5) 
so the same SHA legitimately can (and does, e.g. via forks, cherry-picks, or shared history/rebasing) exist across multiple stacks belonging to different repositories.

Exploit flow: attacker owns/controls a repository (e.g. a fork) whose GitHub App installation is registered with Shipit (satisfying `verify_signature` for their own org). They arrange for one of their commits to share a SHA with a commit tracked by a victim stack (trivial via a fork with unmodified shared history, or by replaying an identical commit object). They then trigger (or fabricate, since they own the repo firing real webhooks) a `status` event with `context: ci/circleci`, `state: success` (or `failure`) for that SHA. GitHub delivers this webhook correctly signed for the attacker's own org. `StatusHandler` writes the `Status` onto every `Commit` row sharing that SHA — including the victim's — flipping the victim commit's CI state and triggering `schedule_continuous_delivery`/merge scheduling, potentially causing an unauthorized deploy or unblocking a gated merge.

None of the existing guards prevent this: `verify_signature` only checks payload authenticity for the *attacker's own* organization, not repository scoping of the DB writes; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not repository identity; there is no `require_permission!`/`stacks`-scoped lookup in `StatusHandler`.

### Impact Explanation
An attacker who controls any repository with a Shipit-registered webhook can write arbitrary `Status` rows (state/context/description/target_url) onto commits in unrelated victim stacks whenever a SHA collision exists, without any privilege on the victim's repository/stack/team. This can flip a commit from blocked to CI-green, unblocking `deployable?`/`blocked?` checks and triggering `schedule_continuous_delivery` and `ProcessMergeRequestsJob`, i.e. a payload from one repository mutating another's stack/commit state and potentially causing an unauthorized deploy or merge. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Requires: (1) attacker owns/controls a repository with a legitimate Shipit GitHub App/webhook installation (any GitHub user who can create a repo/fork and have Shipit track it, or any repo already onboarded to Shipit that the attacker can push status events for), and (2) a SHA collision between attacker's repo and the victim's tracked commit — realistic via forks that share unmodified upstream history, or reused commit objects across repos (git commit SHAs are content-addressed and portable). No Shipit secrets, sessions, or team membership are needed. The attack is repeatable against any stack/commit whose SHA the attacker can reproduce or collide with.

### Recommendation
Scope `StatusHandler#process` to commits belonging to the repository that authenticated the webhook, mirroring `Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a status webhook can only affect commits in stacks belonging to the repository that sent/authenticated it.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or similar, illustrative — actual file under `test/` to be added by implementers):
```ruby
test "status for context ci/circleci does not affect commits in an unrelated stack sharing the same sha" do
  attacker_repo_payload = { 'repository' => { 'full_name' => 'attacker/repo' }, 'sha' => 'deadbeef' * 5, 'state' => 'success', 'context' => 'ci/circleci' }

  victim_stack = shipit_stacks(:shipit) # tracked by repository 'shopify/shipit-engine'
  victim_commit = victim_stack.commits.create!(sha: attacker_repo_payload['sha'], ...)

  # Binding under test: a status authenticated for 'attacker/repo' must not create/alter Status for victim_commit
  before_state = victim_commit.reload.state

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_repo_payload)

  assert_equal before_state, victim_commit.reload.state
  assert_equal 0, victim_commit.statuses.where(context: 'ci/circleci').count
end
```
Given the current implementation (`Commit.where(sha: params.sha)` with no repository scoping), this assertion fails — the victim's commit receives the attacker-authenticated status, demonstrating the cross-repository state manipulation.
