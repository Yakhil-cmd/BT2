### Title
Webhook signature is verified against a GitHub App config selected from an unauthenticated payload field, letting an attacker route a forged event to a different organization's repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which configured GitHub App (and therefore which `webhook_secret`) to validate a webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the unauthenticated JSON body, before the HMAC signature has been checked. If a Shipit deployment configures multiple GitHub organizations (a documented and supported feature) and any one of them has no `webhook_secret` set, `verify_webhook_signature` unconditionally returns `true` for that organization. An attacker can therefore craft a payload that *claims* to originate from the secret-less organization for signature-selection purposes, while embedding a different, protected organization's repository (`repository.full_name`) for the purposes of the actual handler logic (sync, status, membership, etc.). This breaks the binding: organization authenticated (used to pick the verification secret) == repository that is written (used by the event handlers).

### Finding Description
- `verify_signature` derives the org used to select the verifying `GitHubApp` purely from body content: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

- `Shipit.github(organization: repository_owner)` resolves to the `GitHubApp` instance configured for that organization key; verification is then delegated to `verify_webhook_signature`, which trivially passes when the resolved app has no `webhook_secret` configured: [3](#0-2) 

- Multi-organization configuration is a first-class, documented capability, where each organization has its own independent `app_id`/`webhook_secret`/`oauth` block (some legitimately left blank, e.g. during setup or for enterprise-only orgs): [4](#0-3) [5](#0-4) 

- Nothing ties the org used for signature selection back to the repository/stack that the event handlers ultimately act on. The event body's `repository.full_name` (a separate field from `repository.owner.login`) is what downstream handlers use to resolve the target `Stack`/`Repository` and enqueue jobs (e.g. `GithubSyncJob`), as exercised in the controller tests: [6](#0-5) 

Because the JSON body is entirely attacker-controlled prior to signature verification, an attacker can set `repository.owner.login` to an organization known to have `webhook_secret: nil` (satisfying `verify_webhook_signature`'s early `true` return) while setting `repository.full_name` to `victim-org/victim-repo`, a repository that belongs to a different, secret-protected organization. The forged event will pass `verify_signature` and be dispatched to the real handler for `victim-org/victim-repo`, even though the request was never signed by `victim-org`'s actual webhook secret.

### Impact Explanation
This is a cross-repository/cross-organization write: an attacker without any of `victim-org`'s secrets can trigger the `push`/`status`/`check_suite`/`membership` handlers against `victim-org`'s stacks (e.g., enqueue a `GithubSyncJob` for an arbitrary commit SHA, forge commit statuses that gate deploy safety checks, or manipulate team/membership records used for `Shipit.github_teams` authorization). Depending on the targeted handler this can escalate into authorization bypass (falsified CI/check status enabling an "unauthorized deploy") or manipulation of the `Shipit.github_teams` membership records that back `User#authorized?`, both of which are explicitly listed High/Critical impacts.

### Likelihood Explanation
Exploitability requires only that the deployment configures more than one GitHub organization and that at least one of them is left without a `webhook_secret` (shown as a normal/blank default in this engine's own example and fixture configs). No privileged credentials, GitHub App keys, or prior repository access are needed — only knowledge of that organization's login name, which is typically public. This is a realistic misconfiguration given the engine ships examples with blank `webhook_secret` for setup/testing.

### Recommendation
Do not select the verification key from unauthenticated payload content. Either: (a) require and enforce a non-blank `webhook_secret` for every configured organization at boot, refusing to start otherwise; (b) after signature verification succeeds for the app resolved by `repository_owner`, additionally assert that the organization owning the target `repository.full_name`/`Stack` actually matches the organization whose secret validated the request, rejecting the webhook otherwise; or (c) bind webhooks to per-organization endpoints/paths so the secret and the acted-upon organization can never diverge.

### Proof of Concept
1. Configure Shipit with two GitHub orgs: `OpenOrg` (no `webhook_secret`) and `SecretOrg` (has `webhook_secret`), each with a stack, e.g. `SecretOrg/victim-repo` tracked by Shipit. [4](#0-3) 
2. POST to `/github_hooks` (or the mounted webhooks endpoint) with header `X-Github-Event: push` and NO valid `X-Hub-Signature` (or any bogus value), and body:
```json
{
  "repository": { "owner": { "login": "OpenOrg" }, "full_name": "SecretOrg/victim-repo" },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```
3. `repository_owner` resolves to `"OpenOrg"`; `Shipit.github(organization: "OpenOrg")` returns the app config with `webhook_secret: nil`; `verify_webhook_signature` returns `true` unconditionally. [7](#0-6) 
4. The request passes `verify_signature` and is dispatched to `Shipit::Webhooks.for_event('push')`, whose handler resolves the target stack from `repository.full_name = "SecretOrg/victim-repo"` and enqueues a `GithubSyncJob` for it — exactly as demonstrated for legitimate payloads in the existing test. [6](#0-5) 
5. The attacker has thus injected a webhook event against `SecretOrg`'s repository without ever possessing `SecretOrg`'s `webhook_secret`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
