## Title
Private textcoin payload files written with insecure default permissions, exposing spending mnemonic to other local users - (File: wallet.js)

### Summary
When a wallet sends a private asset ("textcoin") to a recipient not paired as a device correspondent, `sendMultiPayment` serializes the recipient's spending mnemonic and the private-element chain into a zip file and writes it to disk via `storePrivateAssetPayload`. The file is created with `fs.writeFile(fullPath, zipFile, cb)`, which uses Node's default file mode (`0o666`, moderated only by the process umask), so on typical multi-user configurations the resulting file is world-readable. This mirrors the CVE-2019-0804 bug class: a sensitive credential is persisted to a resource/shared location with insecure, non-restrictive file permissions, allowing any local, unprivileged user or process on the same device/host to read it.

### Finding Description
`storePrivateAssetPayload` builds a JSON object containing the plaintext `mnemonic` (the private spending key of the textcoin address) plus the private-payment chains, zips it, and writes it with plain `fs.writeFile`: [1](#0-0) 

This function is reached from `sendMultiPayment`'s private-asset commit path whenever a private asset is sent to a recipient without an existing paired device (i.e., to `assocAddresses`/textcoin flow), via the `getPrivateAssetPayloadSavePath` callback chain: [2](#0-1) 

No explicit file mode is passed to `fs.writeFile`, so Node.js applies its default mode `0o666` modified by the OS umask (commonly resulting in world-readable `0644` permissions on typical Linux/macOS defaults). The mnemonic embedded in this file is equivalent to a bearer private key: anyone who reads the plaintext file content can derive the same address/keypair via `expandMnemonic`/HD derivation and claim the funds, exactly as the legitimate recipient would via `handlePrivatePaymentFile`/`receiveTextCoin`.

### Impact Explanation
Any other local, unprivileged account or unprivileged app on the same machine/device (or on shared/removable storage, since the write path is caller-supplied via `getPrivateAssetPayloadSavePath`) can read the world-readable payload file and extract the spending mnemonic before the intended recipient imports it. This directly enables unauthorized spending of the private-asset outputs referenced by the payload — the same bug class as the CVE: sensitive material persisted to disk with insecure, default file permissions leading to information disclosure and subsequent asset theft.

### Likelihood Explanation
The behavior is deterministic and triggered on the normal path of sending a private asset/textcoin to a non-paired recipient — no attacker interaction or race condition is required beyond having local read access to the file before the legitimate recipient claims it (a window that can be arbitrarily long if delivery/import is delayed). Any process or account with local filesystem access at any point before the legitimate claim can silently exfiltrate the mnemonic.

### Recommendation
Explicitly set a restrictive mode (e.g., `0o600`) when writing the private-asset payload file, e.g. `fs.writeFile(fullPath, zipFile, { mode: 0o600 }, cb)`, and additionally consider encrypting the mnemonic/chain payload at rest rather than relying solely on filesystem permissions.

### Proof of Concept
1. Alice sends a private asset to Bob via `sendMultiPayment` with a textcoin-style output (no existing paired device), triggering `storePrivateAssetPayload(fullPath, ...)`.
2. The resulting file at `fullPath` is created via `fs.writeFile` with default mode `0o666`/umask, i.e. world-readable on standard multi-user configurations. [3](#0-2) 
3. Any other local user/process reads `fullPath`, unzips `private_textcoin`, and extracts `data.mnemonic`.
4. The attacker calls `expandMnemonic(data.mnemonic)` (same helper used internally) to derive the address/keypair and claims the asset for themselves before Bob does, resulting in theft of the private-asset funds.
