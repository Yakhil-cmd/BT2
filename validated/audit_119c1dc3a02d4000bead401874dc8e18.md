### Title
Cross-repository CI status forgery via missing repository/commit binding check - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely `by sha` and writes GitHub status updates to every matching `Commit` row, without ever comparing the webhook payload's `repository.full_name` to the `full_name` of the repository owning the `Stack` that the commit belongs to. Because GitHub commit SHAs are content-addressed and public, an attacker who legitimately controls repository A can construct a byte-identical root commit and have Shipit apply forged status data to a completely different repository B's commit and stack.

### Finding Description
The broken binding is the equality that is required but never checked:
`params.repository.full_name` (the org/repo that GitHub verified and signed the webhook for) == `commit.stack.repository.full_name` (the owner of the `Stack` the matched `Commit` actually belongs to).

Code path:
- `WebhooksController#verify_signature` at [1](#0-0)  only validates that the payload was signed by the GitHub App registered for `repository_owner` (i.e. it authenticates "attacker/A" as the legitimate sender of this webhook) — it never links the `sha` inside the payload to that same repository.
- `StatusHandler#process` then does: [2](#0-1) 
This iterates `Commit.where(sha: params.sha)` across the entire database and calls `commit.create_status_from_github!(params)` for every match, regardless of which repository/stack the commit belongs to.
- `Commit#create_status_from_github!` then persists the status against the commit's own `stack_id`: [3](#0-2) 
and `add_status` can trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` on state transitions: [4](#0-3) 

Exploit flow: the attacker observes a public commit's raw sha in victim repo B (e.g. from B's commit history), reconstructs a git commit object with byte-identical tree/parents/author/committer/message/timestamps in their own repo A (feasible for a root/orphan commit whose content is fully known), pushes it, and then sends (or has GitHub send, since they own A) a `status` webhook for that sha with the desired `state`/`context`. `verify_signature` validates correctly because it's genuinely signed for org A. `StatusHandler#process` then finds and mutates the commit row in B's stack because it matches purely on `sha`, ignoring `params.repository.full_name`.

None of the existing guards catch this: `verify_signature` authenticates the sender org, not the sha-to-repo binding; `drop_unhandled_event` only checks event type; the `ExplicitParameters` schema only validates payload shape, not repository ownership; there is no `require_permission!`/`stacks` scope check inside `StatusHandler`.

### Impact Explanation
A successful forged status write lets an attacker flip CI status (`success`/`error`/`failure`, `pending`) on an arbitrary target commit belonging to a repository/stack they do not control, as long as they can reproduce that commit's exact byte content in a repo they own and trigger a webhook. Since `Commit#deployable?`, `blocked?`, and continuous-delivery scheduling (`schedule_continuous_delivery`, `ContinuousDeliveryJob`) depend on status state, this can push an unrelated victim stack toward an unauthorized deploy/merge, or conversely block a legitimate deploy by forging a failing status — satisfying "a payload for one repository mutating another's stack/commit" and "unauthorized deploy" criteria. The attack is repeatable against any commit sha the attacker can reconstruct, across any Shipit-managed repository.

### Likelihood Explanation
The attacker needs no Shipit credentials — just their own GitHub repository (which they can create for free) and the ability to reconstruct a specific commit's exact object bytes, which is realistic for root/orphan commits or short-lived branches whose full commit metadata (tree, author, committer, timestamps, message) is publicly visible. No collision is required, only faithful reproduction of already-public content. This is inexpensive and repeatable per target sha.

### Recommendation
In `StatusHandler#process` (and analogously in `CheckSuiteHandler`/other sha-keyed handlers), filter matched commits by joining through `commit.stack.repository` and only apply the status when `stack.repository.full_name == params.repository.full_name` (case-insensitively), dropping/ignoring any commit whose owning stack's repository doesn't match the authenticated sender repository from the webhook payload.

### Proof of Concept
minitest plan:
1. Create `stack_b` for repository `"victim/B"`, and `commit = shipit_commits(:...)` with `sha: S` belonging to `stack_b`.
2. Build `params = Shipit::Webhooks::Handlers::StatusHandler.new` payload equivalent to what `verify_signature` would accept for org `"attacker/A"`: `OpenStruct.new(sha: S, state: 'success', repository: OpenStruct.new(full_name: 'attacker/A'))`.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(params)` directly (bypassing controller, matching how `WebhooksController#create` dispatches after signature verification).
4. Assert `commit.reload.status.state == 'success'` (mutation happened) while asserting `commit.stack.repository.full_name == 'victim/B' != 'attacker/A' == params.repository.full_name` — proving the write occurred despite the repository mismatch. [2](#0-1)  is the exact code exercised by this PoC.
