### Title
Malicious swap route can add a victim-signed wallet transfer beneath a controller strategy authorization - (File: contracts/controller/src/strategies/swap.rs) [1](#0-0) 

### Summary
Medium severity. Controller strategy entrypoints accept caller-supplied route bytes and forward them to the configured router, whose route can invoke attacker-controlled pool code below the caller’s authorization. [2](#0-1) [3](#0-2)  That code can request an unrelated token transfer from the victim, causing transaction simulation to include it as a child authorization; if the victim signs the displayed tree, the transfer executes even though the strategy itself succeeds normally. [4](#0-3) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` accepts an opaque `swap: Bytes` argument after caller and account-owner authorization. [5](#0-4) [6](#0-5)  The strategy withdraws the selected collateral and sends those bytes into `swap_tokens`, which authorizes only the controller’s exact input transfer but invokes `router.execute_strategy(controller, amount_in, swap)`. [7](#0-6) [1](#0-0)  The router calls pool addresses named by the route payload and does not restrict them to an allowlist, so attacker-deployed code can run during the signed strategy. [8](#0-7)  When that code calls `token.transfer(victim, attacker, amount)`, recording-mode simulation places the transfer under the victim’s `swap_collateral` authorization entry. [9](#0-8)  Enforcing auth rejects the movement under an honest root-only authorization, but accepts it if the victim signs the poisoned simulated tree. [10](#0-9) 

The same route reaches the protocol through `multiply`, `swap_debt`, `swap_collateral`, or `repay_debt_with_collateral`; `swap_collateral` is the clearest path because it needs only an owned collateralized account and caller-controlled `swap` bytes. [11](#0-10) [12](#0-11) 

### Impact Explanation
An attacker can steal arbitrary approved tokens held in the victim’s wallet while the requested collateral swap remains economically valid. [13](#0-12) [14](#0-13)  The controller’s input-spend limit, positive-output check, collateral redeposit, and final risk check do not bound transfers that target the caller’s unrelated wallet balance. [15](#0-14) [16](#0-15) 

### Likelihood Explanation
The attacker must convince a victim to submit a poisoned route and sign the resulting authorization tree, so this is not an unauthenticated direct drain. [17](#0-16)  However, route bytes and nested authorization trees are opaque compared with the visible token pair and amounts, and a malicious venue can make the swap itself return a fair result while adding the theft invocation. [18](#0-17) [14](#0-13) 

### Recommendation
Restrict executable venue and pool addresses to a governance-managed allowlist or otherwise bind route programs to known contract IDs before invocation. [19](#0-18)  Until route execution is constrained, clients must decode `swap`/`routeXdr`, verify every pool and token address, simulate the final transaction, and reject any caller authorization tree containing an unexpected child invocation. [20](#0-19) 

### Proof of Concept
1. Give Alice a debt-free account with 10,000 USDC collateral and 77,770 units of an unrelated wallet token. [21](#0-20) 
2. Deploy a route hop whose `swap` function calls `wallet_token.transfer(alice, attacker, amount)`. [22](#0-21) 
3. Build route bytes naming that contract as `hop_pool`, with USDC input, ETH output, and a fair minimum output. [23](#0-22) 
4. Call `swap_collateral(alice, account_id, USDC, 50_000_000_000, ETH, poisoned_route)`. [24](#0-23) 
5. Simulation records `wallet_token.transfer(alice, attacker, 77_770_000_000)` as a child of Alice’s `swap_collateral` authorization, and execution under that signed tree empties Alice’s wallet token while crediting the fair ETH collateral output. [25](#0-24) [26](#0-25)

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```

```rust
    pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {

        let router = env.current_contract_address();

        token::Client::new(&env, &route.token_out).transfer(&router, &sender, &route.min_out);
        route.min_out
    }
```

```rust
#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
```
