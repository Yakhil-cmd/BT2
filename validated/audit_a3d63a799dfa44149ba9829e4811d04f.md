## Title
Contract-acceptance signature commits only to `title` string, not to the binding terms of the arbiter contract - ([File: wallet.js])

### Summary
`ResourceLockValidator.validateUserOp()` in the external report is exploitable because its signature check only binds to a narrow, derived value (`ResourceLock`) instead of the full transaction data, letting an attacker substitute unrelated malicious data that hashes/verifies to the same narrow value. The same root cause — a signature that is checked against only a small sub-field of a larger, security-critical agreement — exists in ocore's paired-device arbiter-contract acceptance flow in `wallet.js`.

### Finding Description
When a peer device sends an `arbiter_contract_response` message accepting a contract, the handler validates the accompanying signed message like this: [1](#0-0) 

```js
signed_message.validateSignedMessage(db, objSignedMessage, objContract.peer_address, function(err) {
    if (err || objSignedMessage.authors[0].address !== objContract.peer_address || objSignedMessage.signed_message != objContract.title)
        return callbacks.ifError("wrong contract signature");
    processResponse(objSignedMessage);
});
```

`signed_message.validateSignedMessage()` correctly verifies that the *signed_message string* was signed by the claimed address [2](#0-1) , but the binding check performed by the caller only compares `objSignedMessage.signed_message` to `objContract.title` — a single, low-entropy free-text field of the contract. None of the other terms that actually define the financial exposure (`amount`, `asset`, `arbiter_address`, `my_address`/`peer_address`, `me_is_payer`, `ttl`, `text`) are covered by the signature check.

This mirrors the `ResourceLockValidator` bug: the signature validated in `validateUserOp()` only committed to `ResourceLock` and not to the full `userOp`/`callData`, so an attacker could substitute a different `callData` producing the same `ResourceLock` and pass validation. Here, an attacker (the peer device) or a malicious pairing counterparty can obtain *any* string signed by the victim as `signed_message` for a wholly unrelated purpose (ocore explicitly supports general-purpose message signing, as used and tested for arbitrary signed packages via `is_valid_signed_package`/`signed_message` machinery [3](#0-2) ), and if that string happens to equal (or can be engineered to equal) a pending contract's `title`, the response is accepted as a cryptographically valid "acceptance" of that contract — even though the signer never saw or agreed to the amount, asset, or counterparties encoded in it.

Contrast this with the correctly-scoped hash checks used elsewhere in the same file for the *offer* and *dispute-request* flows, which hash the entire relevant object (`arbiter_contract.getHash(body)`, `getContactsHash()`) rather than a single field: [4](#0-3) [5](#0-4) 

The acceptance-signature check at line 933 breaks this pattern by binding only to `title`.

### Impact Explanation
Because the shared address and eventual on-chain payment are derived from the stored `wallet_arbiter_contracts` row (`amount`, `asset`, `arbiter_address`, `me_is_payer`, addresses) via `deriveSharedAddress()` [6](#0-5) , once a response is accepted as "wrong contract signature"-free, the offering party's wallet proceeds to treat the contract as validly agreed and moves to fund the shared address / signing flow. A victim can be induced to sign an arbitrary short string (via any legitimate ocore signed-message use, e.g., chat, another dApp, or a low-value contract with a matching title) and have that signature replayed by an attacker as "cryptographic proof" of acceptance of a *different*, attacker-crafted high-value contract that merely shares the same `title`. This can result in funds being locked into a shared address / arbiter-mediated payment the counterparty never actually authorized under those specific terms, i.e., loss of funds analogous to unauthorized draining described in the source report.

### Likelihood Explanation
Exploitation requires the attacker to control (or collude with) the peer device address recorded as `objContract.peer_device_address`/`peer_address` for a pending contract offer, and to obtain a signature over a string matching the contract's `title` (titles are free-text and can be arbitrarily set by the offeror, including something the attacker can trivially get pre-signed, e.g. by using the same title as a chat message-signing request, an existing signed package, or another lower-stakes contract). This is a realistic scenario for the class of actor explicitly in scope (paired-device / contract counterparty), matching the "concrete unauthorized spending ... AA fund loss" bar, though it depends on social/protocol engineering to get the matching title signed, which slightly limits automatic exploitation compared to the original report's fully self-contained on-chain front-run.

### Recommendation
Bind the acceptance signature to the full set of binding contract terms, not just `title`. Compute and sign/verify a hash over the entire canonical contract object (as already done via `arbiter_contract.getHash()` for offers) instead of comparing only `signed_message` to `objContract.title`, e.g.:

```js
if (err || objSignedMessage.authors[0].address !== objContract.peer_address || objSignedMessage.signed_message != arbiter_contract.getHash(objContract))
    return callbacks.ifError("wrong contract signature");
```

or otherwise include amount, asset, arbiter_address, and party addresses in the signed payload so a valid signature can only correspond to one specific, fully-specified contract.

### Proof of Concept
1. Attacker controls or colludes with the device paired as `peer_device_address` for a target's wallet.
2. Attacker crafts a high-value arbiter contract offer (`arbiter_contract_offer`) whose `title` field is set to some short text `T` that the victim can plausibly be induced to sign in an unrelated context (e.g., a chat "sign message" request, or another low-value contract also titled `T`).
3. Attacker (or a colluding third party) obtains a `signed_message` where `signed_message.signed_message === T`, signed by `objContract.peer_address`, through any legitimate ocore signing flow unrelated to the malicious contract.
4. Attacker replays that signed_message inside an `arbiter_contract_response` with `status: "accepted"` for the malicious contract.
5. `wallet.js`'s handler at line 933 only checks `objSignedMessage.signed_message != objContract.title`, which passes, and `objSignedMessage.authors[0].address === objContract.peer_address`, which also passes — despite the victim never having agreed to the actual `amount`/`asset`/`arbiter_address` in the malicious contract.
6. `processResponse()` marks the contract "accepted", and the offering wallet proceeds with `createSharedAddressAndPostUnit` and fund transfer based on the attacker-controlled terms [7](#0-6) .

function createSharedAddressAndPostUnit(hash, walletInstance, cb) {
	deriveSharedAddress(hash, true, function(err, arrDefinition, assocSignersByPath) {
		if (err)
			return cb(err);
		require("./wallet_defined_by_addresses.js").createNewSharedAddress(arrDefinition, assocSignersByPath, {
			ifError: function(err){
				cb(err);
			},
			ifOk: function(shared_address){
				setField(hash, "shared_address", shared_address, async function(contract) {
					const err = await fillArbstoreAddresses(contract);
					if (err)
						return cb(err);
					// share this contract to my cosigners for them to show proper ask dialog
					shareContractToCosigners(contract.hash);
					shareUpdateToPeer(contract.hash, "shared_address");

					const contacts_hash = getContactsHash(contract);

					// post a unit with contract text hash and send it for signing to correspondent
					var value = {"contract_text_hash": contract.hash, "arbiter": contract.arbiter_address, contacts_hash};
					var objContractMessage = {
						app: "data",
						payload_location: "inline",
						payload_hash: objectHash.getBase64Hash(value, true),
						payload: value
					};

					walletInstance.sendMultiPayment({
						spend_unconfirmed: walletInstance.spendUnconfirmed ? 'all' : 'own',
						asset: "base",
						to_address: shared_address,
						amount: exports.CHARGE_AMOUNT,
						arrSigningDeviceAddresses: contract.cosigners.length ? contract.cosigners.concat([contract.peer_device_address, device.getMyDeviceAddress()]) : [],
						signing_addresses: [shared_address],
						messages: [objContractMessage]
					}, function(err, unit) { // can take long if multisig
						if (err)
							return cb(err);

						// set contract's unit field
						setField(contract.hash, "unit", unit, function(contract) {
							shareUpdateToPeer(contract.hash, "unit");
							setField(contract.hash, "status", "signed", function(contract) {
								cb(null, contract);
							});
						});
					});
				});
			}
		});
	});
}
