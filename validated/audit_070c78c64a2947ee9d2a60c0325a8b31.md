### Title
Stack-scoped `ApiClient` tokens can read CCMenu status of any stack, bypassing token scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to resolve directly from `params[:stack_id]` instead of using the stack-scoped lookup provided by `BaseController`, breaking the binding "the stack a token authorizes = the stack it touches." This lets any `ApiClient` token restricted to a single stack read the CCMenu build/deploy status of every other stack in the installation.

### Finding Description
`Shipit::Api::BaseController` implements stack authorization by intersecting the requested stack with the set of stacks the authenticated `ApiClient` is allowed to see: [1](#0-0) 
`stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is scoped (`stack_id?` true), and only then does `stack` do `stacks.from_param!(params[:stack_id])`, enforcing that the requested stack must be within the client's allowed scope.

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 
It resolves `Stack.from_param!(params[:stack_id])` directly against the whole `Stack` table, without ever consulting `current_api_client.stack_id`. The controller's only authorization gate is: [3](#0-2) 
`require_permission :read, :stack`, which only checks that the client's `permissions` array contains `read:stack` via `ApiClient#check_permissions!`: [4](#0-3) 
This check is scope-agnostic — it never inspects `current_api_client.stack_id`. So a token that was created with `stack: shipit` (i.e., intended to only ever see the `shipit` stack, as in the `here_come_the_walrus` fixture) still satisfies `require_permission :read, :stack`, and `CCMenuController#stack` will happily fetch and render any other stack the caller names in `params[:stack_id]`. [5](#0-4) 

This is a token-scope confusion equivalent to the reported bug class: the authorization check (`read:stack` permission) is verified, but the entity actually acted upon (the specific `stack_id`) is never bound to what the token was issued for.

### Impact Explanation
An attacker holding (or a legitimate holder of) a stack-restricted `ApiClient` token can enumerate/read the deploy status, last deploy id, and build state of any stack hosted by the Shipit instance, not just the one it was scoped to — an unauthenticated-for-that-resource read of stack state/deploy output, matching the "unauthenticated read of stack state, task streams or deploy output" High-impact category. This defeats the purpose of per-stack scoped tokens (e.g., handed to CI dashboards or third parties for a single project) as an isolation boundary between stacks/repositories.

### Likelihood Explanation
High: exploitation only requires possessing any valid `ApiClient` token with `read:stack` permission (even one deliberately scoped to a single stack) and issuing a GET request with a different `stack_id`/`token` query param — no additional privilege or session is needed, and the code path is on by default in `config/routes.rb`'s CCMenu endpoint.

### Recommendation
Make `CCMenuController#stack` reuse the scoped `stacks` collection from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so that stack-restricted tokens cannot resolve stacks outside their `stack_id` scope.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to stack A, e.g. fixture `here_come_the_walrus` (`stack: shipit`, `permissions: [read:stack]`). [5](#0-4) 
2. Using that client's `authentication_token`, call `GET /api/1/stacks/:stack_id/ccmenu.xml?token=<token>` where `:stack_id` refers to a *different* stack (e.g., `soc` or any repo/environment not owned by this token).
3. Observe the request succeeds (200 OK) and returns the CCMenu XML (build status, last deploy) for the unrelated stack, because `CCMenuController#stack` at [6](#0-5)  looks the stack up globally instead of through the client's scoped `stacks` relation.
