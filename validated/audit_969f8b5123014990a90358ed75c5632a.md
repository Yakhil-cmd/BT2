### Title
Webhook signature is verified against the payload's `repository.owner.login`, but every event handler dispatches on the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login` as a fallback). Once the signature check passes, the actual event handlers (`Handler#repository_name`, used by `PushHandler`, `PullRequest::OpenedHandler`, etc.) resolve the target `Repository`/`Stack` using a completely different payload field: `repository.full_name`. Nothing ties these two fields together, so the "organization that authenticated" and the "repository that is acted on" are two independent, uncorrelated fields inside the same signed body.

### Finding Description
`verify_signature` picks the app/secret purely from the owner login: [1](#0-0) [2](#0-1) 

This only proves the request was HMAC-signed with *some* organization's configured `webhook_secret` (chosen by `repository.owner.login`), it does not constrain any other field of the JSON body, including `repository.full_name`.

Every downstream handler, however, looks up the target repository/stack from `repository.full_name`, not from `repository.owner.login`: [3](#0-2) [4](#0-3) [5](#0-4) 

For the `status` event specifically, the handler doesn't even use `repository_name`/stack scoping at all - it matches purely by commit SHA across the whole database and writes a `Status` record with attacker-controlled `state`/`context`/`description`: [6](#0-5) 

Creating a `Status` triggers CI-gating side effects (enabling CI on the stack, scheduling continuous delivery, and feeding into `StatusChecker`/`required_statuses` used for both deploy readiness and the merge queue): [7](#0-6) [8](#0-7) 

**Binding broken:** `repository.owner.login` (the value whose webhook secret authenticated the signed payload) ≠ `repository.full_name` / `sha` (the value the handler actually acts on). This is exactly the "organization that authenticated versus the repository that is written" binding class from the report analog: like the LINK fee being computed from one position size but charged/paid from a different, unverified size, here the *authorization decision* (which org's secret validated the request) is made on one payload field while the *effectful action* (which repository/commit is mutated) is taken on a sibling field that is never cross-checked against it.

### Impact Explanation
In a multi-tenant Shipit deployment (multiple GitHub organizations/webhook secrets configured via `Shipit.github(organization: ...)`), an actor who legitimately controls the webhook configuration for **their own** organization/repo (and thus knows that organization's `webhook_secret`) can craft and directly POST a payload to the shared `/github/webhooks` endpoint where `repository.owner.login` is set to their own org (so the signature check passes) while `repository.full_name` (used by `PushHandler`, PR handlers) or `sha` (used by `StatusHandler`, matched with no repository scoping at all) refer to a stack/commit belonging to a **different** organization/stack on the same instance. This lets them:
- force premature/forced GitHub syncs on stacks they don't own, and
- inject arbitrary CI `Status` records (e.g. forged `success`) on commits belonging to unrelated stacks, since `StatusHandler` never checks `repository_name` and only matches on `sha`, which can bypass `ci.require`/`merge.require` gating and unblock deploys or PR merges (`StatusChecker`, `ProcessMergeRequestsJob`).

This maps to the "unauthorized deploy/merge" and "escalation across trust boundary" impact tiers, since the write (Status/CI state, sync triggers) crosses from one organization's authenticated context into another organization's stack. Full severity depends on the deployment actually hosting multiple orgs with independently-known webhook secrets - single-tenant deployments are not affected because the org boundary is trivial.

### Likelihood Explanation
Requires the attacker to be a legitimate webhook administrator/known-secret holder for at least one organization/repo hosted on the same Shipit instance (i.e., not a fully anonymous internet attacker, but also not someone with a Shipit `ApiClient` token, GitHub App private key, or `github_access_token` - only their own already-authorized webhook secret). This is a realistic scenario in shared/multi-tenant Shipit setups. Likelihood is Medium: it needs multi-org hosting and knowledge of a valid webhook secret, but no additional exploitation complexity once positioned.

### Recommendation
Cross-validate the field used for authorization against the field used for effect: after passing signature verification with the organization derived from `repository.owner.login`, re-derive/require the target repository from the same authenticated organization, and reject events where `repository.full_name`'s owner segment (or `Repository#owner`) does not match the `repository_owner` used to select the webhook secret. For `StatusHandler`, do not operate globally on `Commit.where(sha:)` — scope the update to commits belonging to the authenticated repository only.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (multi-tenant setup via `Shipit.github(organization:)`).
2. As an admin of `org-a`'s GitHub webhook configuration, obtain `org-a`'s `webhook_secret` (legitimate access to your own org's settings).
3. Build a `status` event payload:
```json
{
  "sha": "<sha of a commit belonging to org-b's stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/some-repo" }
}
```
4. Compute `X-Hub-Signature` using `org-a`'s `webhook_secret` over the raw JSON body, and POST it to the webhooks endpoint with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"org-a"`, validates successfully against `org-a`'s secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `org-b` commit irrespective of `repository.full_name` — and creates a forged `success` Status for it, potentially satisfying `required_statuses` and unblocking `org-b`'s deploy/merge pipeline, as shown by `Commit#create_status_from_github!` / `Status.replicate_from_github!`.
