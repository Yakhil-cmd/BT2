## Finding

**Binding claimed by the question:** `count_and_identity(Memberships added to Team T from webhook-verifying org O) == count_and_identity(real members of T reported by GitHub for org O)`.

Tracing the code, this binding is already broken by a single request, and is trivially compounded per the multi-account scenario asked about, because **the organization that GitHub uses to verify the webhook signature is never checked against the organization that owns the target `Team`.**

- `WebhooksController#verify_signature` selects the per-tenant HMAC secret using `repository_owner`, which for a `membership` event (no `repository` key in the real GitHub payload) resolves to the top-level `organization.login` supplied in the request body itself: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that tenant's configured `webhook_secret` is blank: `return true unless webhook_secret`. [3](#0-2) 
- `MembershipHandler#process` then resolves the `Team` purely by the numeric `github_id` carried in the payload (`params.team.id`), and calls `team.add_member(member)` for `action == 'added'`. The `organization.login` field in the payload is only ever used inside the `find_or_create_by!` block, which only runs when the `Team` record is *newly created*; if the team already exists (e.g. a real, previously-synced protected team), that block never executes, so `team.organization` is left untouched — and critically, `process` never compares `params.organization.login` (or the org that actually verified the signature) against `team.organization` before calling `add_member`. [4](#0-3) 
- `Team#add_member` has no authorization check of its own: `members.append(member) unless members.include?(member)`. [5](#0-4) 
- `Membership` only guards `uniqueness: { scope: :team_id }` on `user_id`, which prevents duplicate rows for the *same* user but places no limit on how many *distinct* fabricated users a single verified request-sender can enroll.
- Each fabricated member becomes authorized via `User#authorized?`: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?`. [6](#0-5) 

### Exploit flow
1. Attacker controls (or is granted access to) a low-trust GitHub organization `weak-org` that is configured in Shipit's multi-tenant `github:` secrets with a blank/absent `webhook_secret` (the stated precondition).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: membership` and a JSON body that has **no `repository` key**, `organization.login = "weak-org"`, `team = { id: <protected_team_github_id>, name, slug, url }` (the numeric GitHub team ID of a real, protected team owned by a different, trusted organization), `action = "added"`, and `member.login = "fabricated-login-1"`.
3. `verify_signature` resolves `repository_owner` to `"weak-org"`, fetches `Shipit.github(organization: "weak-org")`, and passes because that tenant's `webhook_secret` is blank.
4. `MembershipHandler#process` looks up the existing protected `Team` by `github_id`, ignoring that the payload's `organization.login` doesn't match `team.organization`, creates/finds a `User` for `"fabricated-login-1"`, and calls `team.add_member`.
5. Attacker repeats step 2 with `member.login = "fabricated-login-2"`, `...-3"`, etc., all against the same protected `team.id`. The `(user_id, team_id)` uniqueness constraint does not block this because each row has a distinct `user_id`.
6. Every fabricated user is now a real `Membership` row on the protected `Team`, and each such `User#authorized?` returns `true`, granting them full Shipit access gated by `Shipit.github_teams`.

None of the existing guards intervene: `drop_unhandled_event` only checks the event type is registered; `ExplicitParameters` only validates the shape of the JSON, not organizational ownership; there is no `require_permission!`/`stacks` scope check in this webhook path; and `verify_signature` authenticates only "a message came from *some* configured org whose secret matches," not "this org is authorized to mutate this particular team."

### Impact Explanation
Any tenant configured in Shipit with a weak/blank `webhook_secret` — which the stated precondition establishes as attacker-controlled — can silently and repeatedly enroll an unbounded number of fabricated GitHub logins into any protected `Shipit.github_teams` `Team`, as long as the team's numeric `github_id` is known. This is a full escalation into Shipit's authorization boundary (`User#authorized?`), matching the **High** severity category ("escalation into `Shipit.github_teams` authorization"). It's repeatable indefinitely and not confined to a single victim team; any team whose `github_id` the attacker can guess or observe is affected.

### Likelihood Explanation
The precondition (a weakly-secured/blank-secret tenant already configured in Shipit) is external to this specific finding and assumed given by the prompt. Given that, the attacker's cost is minimal: crafting a plain HTTP POST with a guessed/known team `github_id`, no cryptographic material needed beyond what the weak tenant already permits. The attack is fully repeatable and scriptable for N distinct logins.

### Recommendation
In `MembershipHandler#process` (and `find_or_create_team!`), verify that the webhook's authenticated organization (the tenant whose `webhook_secret` verified the request) matches `team.organization` before calling `team.add_member`/`team.members.delete`. Reject or drop membership events whose `organization.login` does not match the existing `Team#organization` for the resolved `github_id`, rather than silently trusting the payload-supplied team ID.

### Proof of Concept
Minitest plan (in `test/controllers/webhooks_controller_test.rb` style, illustrative — not to be placed under excluded paths but showing the intended assertions):
```ruby
test "membership events from a weak-secret org cannot mass-enroll into an unrelated protected team" do
  protected_team = shipit_teams(:shopify_developers) # owned by "shopify"
  Shipit.stubs(:github_teams).returns([protected_team])

  # Simulate weak-secret attacker org signature bypass
  weak_org_app = Shipit.github(organization: 'weak-org')
  weak_org_app.stubs(:verify_webhook_signature).returns(true)

  @request.headers['X-Github-Event'] = 'membership'

  logins = %w[fabricated1 fabricated2 fabricated3]
  logins.each do |login|
    Shipit.github.api.stubs(:user).with(login).returns(stub(id: rand(10_000), login:, name: login, email: "#{login}@example.com", avatar_url: '', url: ''))
    post :create, body: {
      action: 'added',
      team: { id: protected_team.github_id, name: protected_team.name, slug: protected_team.slug, url: protected_team.api_url },
      organization: { login: 'weak-org' },
      member: { login: }
    }.to_json, as: :json
  end

  logins.each do |login|
    user = User.find_by(login:)
    # Binding under test: this fabricated user, added via "weak-org"'s signature,
    # should NOT equal a real member of shopify_developers reported by GitHub.
    assert_equal true, protected_team.members.include?(user), "expected escalation to succeed under current code"
    assert_predicate user, :authorized?
  end
end
```
This demonstrates that all `N` fabricated logins gain `Membership` rows on the protected team and pass `authorized? == true`, confirming the broken binding.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
