### Title
CCMenu API token stack-scope bypass allows reading any stack's build/deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` authenticates an `ApiClient` token but resolves the target `stack` without honoring the token's `stack_id` scope, unlike every other API controller. This breaks the binding "stack a token authorises == stack a token touches": a token minted to authorize `read:stack` for one specific stack can be replayed against `/api/stacks/*stack_id/ccmenu` to read the build/deploy status of **any** stack in the Shipit instance.

### Finding Description
`Shipit::Api::BaseController` is the normal authorization boundary for the API. It exposes: [1](#0-0) 

`stacks` restricts the resolvable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is scoped to a stack (`stack_id` present), and only falls back to `Stack.all` for unscoped/global clients. `stack` then calls `stacks.from_param!(...)`, so a stack-scoped token can never resolve a stack outside its `stack_id`. This scoping is a documented, tested feature — `ApiClient` has a `belongs_to :stack, optional: true` column precisely for this purpose: [2](#0-1) 

and the fixture `here_come_the_walrus` demonstrates a token scoped to a single stack with `read:stack` permission: [3](#0-2) 

`CCMenuController`, however, overrides `stack` to resolve directly from the URL parameter, completely bypassing the `stacks` scoping method: [4](#0-3) 

`require_permission :read, :stack` only checks that the token's `permissions` array contains `read:stack` — via `ApiClient#check_permissions!` — it never checks whether the token's `stack_id` matches the stack actually being served: [5](#0-4) [6](#0-5) 

So the equality that should hold — `token.authorized_stack == stack_served_by_action` — is broken specifically in this controller: the token only needs the coarse `read:stack` permission bit; the fine-grained `stack_id` binding checked everywhere else (`app/controllers/shipit/api/base_controller.rb#stacks`) is skipped.

### Impact Explanation
This is an authorization-scope escape that allows unauthorized cross-stack read of deploy/build state — the exact "unauthenticated/unauthorized read of stack state ... or deploy output" category called out as High severity. An attacker holding (or having been issued) any single-stack-scoped `read:stack` token — for example a legitimate but narrowly-scoped CI/monitoring integration token — can enumerate `stack_id` path segments and pull the CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock status, etc., rendered via `shipit/ccmenu/project`) for every stack in the Shipit deployment, including stacks belonging to repositories/teams the token holder was never granted access to.

### Likelihood Explanation
Any actor who legitimately possesses one narrowly-scoped `ApiClient` token (which Shipit explicitly supports issuing, e.g. via `ApiClient.stack_id`) can trivially exploit this by changing the `stack_id` segment of the URL — no additional privilege, secret, or session is required beyond the one token they already legitimately hold for a different, single stack.

### Recommendation
Have `CCMenuController#stack` resolve through the scoped `stacks` collection (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction enforced elsewhere in the API is also enforced here.

### Proof of Concept
1. Issue/obtain an `ApiClient` token scoped to `stack_id = shipit_stacks(:shipit).id` with permission `read:stack` (e.g. as created for `here_come_the_walrus` fixture, or via the normal UI flow that scopes a client to one stack).
2. Call `GET /api/stacks/<other_org>/<other_repo>/<other_env>/ccmenu?token=<that token>` for a *different* stack than the one the token is scoped to.
3. Observe `200 OK` with the other stack's CCMenu XML (`lastBuildStatus`, `activity`, `webUrl`, etc.) returned — despite the token being authorized only for the original stack. Compare with `GET /api/stacks?...` using the same token, which correctly returns only the single authorized stack per `test/controllers/api/stacks_controller_test.rb` ("an api client scoped to a stack will only see that one stack"): [7](#0-6)
