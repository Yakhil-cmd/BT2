### Title
Webhook signature is verified against the organization in `repository.owner.login`, but the stack/repository actually mutated is looked up from the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `params.dig('repository','owner','login')` (falling back to `organization.login`). [1](#0-0)  Once the signature check passes, `WebhooksController#create` dispatches the *entire* raw payload to the matching `Shipit::Webhooks::Handlers::Handler`, whose base class resolves the target `Repository`/`Stack` via a completely different field, `payload.dig('repository','full_name')`, with no cross-check against the organization that was actually used to verify the signature. [2](#0-1) [3](#0-2) 

### Finding Description
This is the same trust-binding class of bug as the GovernorAlpha report: a verification step authenticates one field of the payload (`repository.owner.login`, used to pick the org's `webhook_secret`), while a different, unrelated field of the same payload (`repository.full_name`) is what actually determines which resource gets mutated. Because HMAC verification of GitHub webhooks covers the raw bytes of the payload, an attacker who legitimately controls a GitHub organization/repository that is also onboarded to this same multi-tenant Shipit instance (and therefore genuinely knows *their own* `webhook_secret`, per the per-organization config shown in `secrets.development.shopify.yml`) can craft a payload where:

- `repository.owner.login` = their own organization (`orgA`) → this makes `verify_signature` select `orgA`'s `webhook_secret` and the signature check succeeds because it is a *bona fide* signature they can compute. [4](#0-3) 
- `repository.full_name` = `orgB/victim-repo` (any other onboarded organization/repository), which is what `Handler#repository_name`/`Handler#stacks` actually use to resolve the `Repository`/`Stack` that gets acted upon. [3](#0-2) 

Nothing in `verify_signature`, `create`, or `Handler` enforces that `repository.full_name` belongs to the organization whose secret validated the request. The existing test suite even demonstrates that the code path deliberately tolerates a `repository.full_name` that has nothing to do with any previously known organization/stack ("create github repository which is not yet present in the datastore"). [5](#0-4) 

This affects every handler that resolves its target via `Handler#stacks`/`Handler#repository_name`/`Repository.from_github_repo_name(params.repository.full_name)`, including `PushHandler` (queues `GithubSyncJob`, which fetches commits and mutates `Stack`/`Commit` records for `orgB`'s stack), `CheckSuiteHandler` (schedules check-run refreshes on `orgB` commits), and the `PullRequest` handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`), which create/archive/unarchive review stacks and mutate pull-request records scoped to `orgB`'s repository. [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation
This breaks the "an organization that authenticated versus the repository that is written" binding explicitly called out in the rules, and lands in the Critical bucket ("cross-repository writes"). An org whose webhook signature validated the request can forge sync/pull-request/review-stack events for a repository belonging to a *different* onboarded organization, causing Shipit to fetch and persist commits, archive/unarchive review stacks, or mark stacks inaccessible for a repository the attacker does not administer on GitHub - all without ever knowing that repository's real webhook secret.

### Likelihood Explanation
Any customer/organization legitimately onboarded to a shared, multi-tenant Shipit deployment (as the `secrets.*.yml` files show is a supported configuration with multiple `github:` orgs) can exploit this by simply crafting a webhook payload with mismatched `repository.owner.login` and `repository.full_name` values and signing it with their own, valid `webhook_secret`. No interception, no stolen credentials, and no access to the victim organization's secret are required - only the ability to send an HTTP request with a validly-computed `X-Hub-Signature` for the attacker's own org.

### Recommendation
After `verify_signature` succeeds, verify that the resolved `Repository`/`Stack` (via `repository.full_name`) actually belongs to the same GitHub organization/owner that supplied the valid signature (`repository.owner.login`/`organization.login`), and reject the webhook otherwise. Equivalently, look up the `Repository` first and derive the verifying organization from the repository's *own* stored owner rather than from attacker-supplied JSON fields that can diverge from `full_name`.

### Proof of Concept
1. Assume `orgA` and `orgB` are both configured under `Shipit.github` with distinct `webhook_secret`s (as in `secrets.development.shopify.yml`), and both have stacks/repositories tracked by this Shipit instance.
2. Attacker (an admin of `orgA`, with no privileges on `orgB`) builds a `push` event payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "orgA" },
       "full_name": "orgB/victim-repo"
     }
   }
   ```
3. Attacker signs the raw JSON with `orgA`'s known `webhook_secret` and sends it with header `X-Hub-Signature: sha1=<hmac>` and `X-Github-Event: push` to `POST /webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` and successfully verifies the signature against `orgA`'s secret. [4](#0-3) 
5. `create` dispatches to `PushHandler`, whose `Handler#stacks` resolves `Repository.from_github_repo_name("orgB/victim-repo")` and enqueues `GithubSyncJob` for `orgB`'s stack, causing Shipit to fetch and append commits for a repository the attacker does not own on GitHub. [9](#0-8) [3](#0-2)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
