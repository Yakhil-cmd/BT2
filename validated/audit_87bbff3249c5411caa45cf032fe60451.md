### Title
Unbounded, attacker-keyed `handledChainsCache` in private-payment chain handling enables memory-exhaustion DoS - ([File: wallet.js])

### Summary
`wallet.js` maintains a module-level `handledChainsCache` object that de-duplicates processed private-payment chain messages. Entries are keyed by a hash of the attacker-supplied `body.chains` payload and are only evicted by a time-based sweep (older than 1 hour), with no cap on the number of distinct keys the cache may hold. A private-payment counterparty (any device that can send a `private_payments` message to a wallet) can flood this structure with an unbounded number of uniquely-hashed, cheaply-shaped chain payloads, growing the cache without limit for up to an hour between sweeps, mirroring the reported SiYuan pattern of storing per-request state keyed by attacker-controlled input "without enforcing capacity limits or eviction policies."

### Finding Description
`handlePrivatePaymentChains(ws, body, from_address, callbacks)` computes
```
var cache_key = objectHash.getBase64Hash(arrChains);
``` [1](#0-0) 
directly from the attacker-controlled `body.chains` array, then, once processing of the chain finishes, stores it forever (until the next hourly sweep) via:
```
handledChainsCache[cache_key] = Date.now();
``` [2](#0-1) 

The only structural validation performed before this point is a shallow shape check (`isNonemptyArray`, `isNonemptyObject`, `isNonemptyString` on `unit`, `payload.asset`, `payload.inputs`, `payload.outputs`) [3](#0-2) , not full cryptographic/DAG validation. Because the cache key is derived from the entire chains blob, an attacker can trivially mint a new, unique key on every message (e.g., by varying an unused field, a bogus `unit` string, or output amounts), causing a fresh, permanent (for up to an hour) entry to be added to `handledChainsCache` for every message sent.

The only cleanup mechanism is:
```
var handledChainsCache = {};
setInterval(() => {
	for (let cache_key in handledChainsCache)
		if (handledChainsCache[cache_key] < Date.now() - 3600 * 1000)
			delete handledChainsCache[cache_key];
}, 3600 * 1000); // clear cache every hour
``` [4](#0-3) 
There is no maximum-size check comparable to the `MAX_ITEMS_IN_CACHE` bound used elsewhere in the codebase for other in-memory caches (e.g. `storage.js`'s `shrinkCache`) [5](#0-4) , so `handledChainsCache` can grow without bound between sweeps, and a sustained flood keeps it perpetually large because new entries are added faster than the hourly sweep removes old ones.

### Impact Explanation
An unbounded, time-only-evicted in-process cache keyed by attacker-controlled content lets any private-payment counterparty exhaust the wallet process's memory by repeatedly sending `private_payments` messages with unique payloads, degrading or crashing the node/wallet process (denial of service on availability) — the same impact class as the referenced CVE (VA:H in the CVSS vector, no confidentiality/integrity impact).

### Likelihood Explanation
The entry point is reachable by any device/counterparty capable of sending a `private_payments` message and passing only a shallow shape check (no signature or DAG validation is required before the cache write path is reached), so an unauthenticated-in-effect network actor (any correspondent device or private-payment counterparty) can trigger unlimited unique cache insertions with low per-request cost.

### Recommendation
Bound `handledChainsCache` by a maximum entry count (evicting oldest entries, e.g. LRU) in addition to the time-based sweep, similar to the `MAX_ITEMS_IN_CACHE` pattern already used in `storage.js`, and/or rate-limit `private_payments` processing per `from_address` before computing and storing the cache key.

### Proof of Concept
1. Establish a device pairing/correspondent relationship sufficient to send messages to the target wallet (as any private-payment counterparty would).
2. Repeatedly send `private_payments` messages with `body.chains` payloads that pass only the shallow shape validation (`isNonemptyArray`/`isNonemptyObject`/`isNonemptyString` checks) [3](#0-2)  but differ in some field (e.g., random `unit` strings, or varying output amounts) so each hashes to a unique `cache_key`.
3. Each accepted message adds a new permanent-for-up-to-1-hour entry to `handledChainsCache` [2](#0-1) ; sending faster than the interval clears entries causes unbounded growth, exhausting memory over time.
