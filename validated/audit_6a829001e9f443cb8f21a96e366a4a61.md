### Title
Delimiter Injection in Arbiter Contract Hash Computation Allows Term-Substitution Collision - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js` builds the contract's identifying hash by concatenating attacker-influenced fields (`title`, `text`, party names, `asset`) with a fixed, non-escaped delimiter string, exactly the bug class described in the NATS advisory (unescaped control/separator characters from untrusted input mixed into a delimited protocol/serialization stream, enabling field-boundary confusion). Because none of the joined fields are checked for the delimiter sequence or length-prefixed, a peer can craft contract text/party-name fields that themselves contain the delimiter, shifting field boundaries so that two semantically different contracts (different amount, asset, or party) hash to the same value.

### Finding Description
`getHashSrc()` builds the pre-image for `getHash()` by joining fields with `exports.DELIMITER = "[|#|]"`: [1](#0-0) 

None of `contract.title`, `contract.text`, `contract.my_party_name`/`peer_party_name`, or `contract.asset` are validated to reject the delimiter substring `[|#|]`, unlike `string_utils.getSourceString()` used elsewhere in the codebase for consensus-critical unit hashing, which explicitly throws if any string component contains its join character: [2](#0-1) 

This shows the codebase is aware that unescaped delimiter joining is unsafe for hash computation of untrusted, attacker-supplied string content elsewhere — the protection was not applied to `arbiter_contract.getHashSrc()`. `title`, `text`, and party names are free-form strings supplied by the contract offeror over the device-message channel (`createAndSend`, `store`), i.e., attacker-controlled input from an unprivileged counterparty: [3](#0-2) [4](#0-3) 

The resulting `hash` is treated as the authoritative identifier of contract terms throughout the module: it keys the `wallet_arbiter_contracts` table, is embedded in the shared-address definition as `"CONTRACT_" + contract.hash` / `"CONTRACT_DONE_" + contract.hash` (binding fund-release conditions to the specific contract), and is put on-chain in the `contract_text_hash` field of the signing data message that both parties verify before treating a payment address as valid: [5](#0-4) [6](#0-5) [7](#0-6) 

Because the hash is computed purely from concatenation without a length-prefix or reversible encoding, a malicious counterparty (or arbiter-flow participant) who controls `title`/`text`/party-name fields can construct a version of the contract whose fields, when joined, produce a byte-identical string to a different, legitimate contract with different `amount`/`asset`/`payer_name`/`payee_name` values — yielding the same `hash`.

### Impact Explanation
The contract `hash` is the value that both peers and the arbiter rely on to agree they are contracting on the same terms (amount, asset, arbiter, parties). A collision lets an attacker present differing underlying terms to different observers (e.g., local wallet record vs. what is disclosed to the arbiter in `openDispute`/`appeal`, which independently serializes `title`/`text`/`amount` fields) while both hash to the same identifier used to authorize fund release conditions in `deriveSharedAddress`. This can be leveraged to create ambiguity/disagreement between the payer, payee, and arbiter about what was actually agreed, potentially enabling fund misdirection or dispute-resolution manipulation tied to a shared address whose release conditions reference the colliding hash.

### Likelihood Explanation
Exploitation requires only the ability to author free-text `title`/`text`/party-name fields when creating or countersigning an arbiter contract — something any wallet peer participating in this feature can do unprivileged. No cryptographic collision search is needed; the delimiter-injection technique is a straightforward crafted-input attack, not a hash-preimage attack.

### Recommendation
Reject or escape occurrences of `exports.DELIMITER` (and any other join character) in all string fields fed into `getHashSrc()` before joining, or switch to a length-prefixed / properly escaped serialization (e.g., reuse `string_utils.getSourceString`/`getJsonSourceString`, which already enforce this invariant elsewhere in the codebase) so that field boundaries cannot be forged via crafted content. Apply the same review to `prosaic_contract.js`'s `getHash`/`getHashV1`, which naively concatenate `title + text + creation_date` with no separator at all, similarly vulnerable to boundary-shifting collisions.

### Proof of Concept
1. Attacker (peer) crafts `title = "A"`, and sets `text` to contain the delimiter followed by forged values for the remaining fields, e.g.:
   `text = "X" + "[|#|]" + "2026-01-01 00:00:00" + "[|#|]" + payer_addr + "[|#|]" + "" + "[|#|]" + arbiter_addr + "[|#|]" + payee_addr + "[|#|]" + "" + "[|#|]" + "1" + "[|#|]" + "null"`
2. This is combined with legitimate remaining fields such that the final joined string via `getHashSrc()` equals the string produced for a second, legitimate-looking contract with a different real `amount`/`asset`/party set.
3. `getHash()` on both objects returns the identical SHA-256/base64 hash, even though the two contracts (as stored/displayed by each counterparty) differ in payer/payee names or asset — the value both sides and the arbiter rely on for consistency (`"CONTRACT_" + hash`, `contract_text_hash`) is now shared between two differing agreements.

Note: I was unable to trace a runtime handler in `wallet.js` that re-verifies the received `hash` against a freshly recomputed `getHash(objContract)` on `store()`/offer receipt (searches show these calls exist in `wallet.js` but the handler bodies were not fully retrievable within the indexed context); if such verification exists and strictly recomputes the hash from the same unescaped `getHashSrc`, the collision described above still passes verification, since both colliding strings hash identically.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
