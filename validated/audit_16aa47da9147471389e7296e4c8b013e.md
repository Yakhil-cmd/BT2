### Title
CCMenu API token scope bypass — a stack an ApiClient is bound to vs. a stack it is used to read - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` binds an `ApiClient` to a single stack when `stack_id` is present on the token (`stacks` returns `Stack.where(id: current_api_client.stack_id)` instead of `Stack.all`), and every controller that relies on `BaseController#stack`/`#stacks` inherits this restriction. `Shipit::Api::CCMenuController`, however, overrides `#stack` to bypass that scoping entirely, so a token that is supposed to authorize only one stack can be replayed against any other stack's CCMenu status endpoint.

### Finding Description
`Shipit::Api::BaseController#stacks` and `#stack` enforce the equality "stack the ApiClient's `stack_id` authorizes == stack being acted on": [1](#0-0) 

This is the mechanism that makes a scoped `ApiClient` (one created with `stack: <some stack>`, as in the `here_come_the_walrus` fixture) safe to hand out: even if the caller supplies an arbitrary `stack_id` in the request, `stacks.from_param!` raises unless the requested stack matches the one baked into the token. [2](#0-1) 

`Shipit::Api::CCMenuController` overrides `#stack` and drops that scoping check, resolving the stack straight from the request parameter regardless of `current_api_client.stack_id`: [3](#0-2) 

It also swaps the authentication path from HTTP Basic auth to a bare query-string `token` parameter, but that alone is a design choice, not the root cause. The root cause is that `#stack` here is `Stack.from_param!(params[:stack_id])` — an unscoped, engine-wide lookup — instead of the scoped `stacks.from_param!(params[:stack_id])` used everywhere else (e.g. `OutputsController`, `TasksController`, `HooksController`). [4](#0-3) 

So the binding "stack a token authorizes == stack a token touches" holds for every other `Api::BaseController` subclass, but is broken specifically in `CCMenuController`: `require_permission :read, :stack` only checks the permission list (`read:stack`), never that the target stack matches `current_api_client.stack_id`. [5](#0-4) [6](#0-5) 

### Impact Explanation
An `ApiClient` token that was deliberately scoped to a single stack (e.g. distributed as a CCMenu URL for a specific team's stack, via `CCMenuUrlController#fetch`, which mints a `token` for use against this very endpoint) can be reused by whoever holds it to read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, activity, etc.) of any other stack in the Shipit instance, including stacks the token holder was never granted access to. This is an unauthorized read of stack/deploy state across the scoping boundary the token was supposed to enforce — matching "High: unauthenticated/unauthorized read of stack state ... task streams or deploy output" from the impact criteria, since the attacker only needs a `read:stack`-scoped token for stack A to read stack B.

### Likelihood Explanation
Any holder of a valid, stack-scoped `read:stack` API token (which is routinely distributed for CCMenu integrations, i.e., not a highly privileged credential) can trivially exploit this by changing the `stack_id` route/query parameter of the CCMenu request. No signature, secret, or additional privilege is required beyond possessing one legitimate scoped token, and the override is a one-line divergence from the pattern used by every sibling controller, making it easy to miss in review.

### Recommendation
Remove `CCMenuController`'s custom `#stack` override (or make it delegate to the scoped `stacks` collection from `BaseController`) so the lookup becomes `stacks.from_param!(params[:stack_id])`, consistently enforcing `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` the same way `OutputsController`, `TasksController`, and `HooksController` do.

### Proof of Concept
1. Admin creates an `ApiClient` scoped to Stack A only (`stack: A`, `permissions: [read:stack]`), and shares its `authentication_token` as a CCMenu URL for Stack A (via `CCMenuUrlController#fetch`). [7](#0-6) 
2. Anyone in possession of that token issues: `GET /api/stacks/<Stack B owner/name/env>/ccmenu.xml?token=<Stack A's token>`.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (it is a valid, permission-holding client). [8](#0-7) 
4. `#stack` resolves Stack B directly via `Stack.from_param!(params[:stack_id])`, ignoring that `current_api_client.stack_id` is Stack A, and returns Stack B's build status — a stack the token was never authorized for. [9](#0-8)
