### Title
Permanent, network-wide Denial of Service of AA trigger processing via unhandled validation-error paths in `validateAndSaveUnit` - ([File: aa_composer.js])

### Summary
The `aa_triggers` queue in ocore is processed strictly in order (`ORDER BY mci, level, unit, address`) by `handleAATriggers()`, and a queued row is only removed after the trigger has been *fully and successfully* processed. If processing of any single AA response unit reaches one of several validation branches that are wired to `throw Error(...)` instead of gracefully bouncing, the exception becomes an uncaught process-level exception, which ocore's global handler deliberately turns into a full node crash. Because the offending row is never deleted, the crash repeats forever on every restart, permanently blocking not just one AA's queue but the entire node-wide `aa_triggers` queue for every AA — a direct structural analog of the reported "sequential-queue DoS from a single unbroadcastable/unprocessable item," but reachable purely by a single properly-formatted unit posted by an unprivileged user, and with a network-wide (not per-chain) blast radius.

### Finding Description
`handleAATriggers()` reads all pending triggers and processes them one at a time with `async.eachSeries`, in a strict deterministic order: [1](#0-0) 

Each row's removal from the queue happens only *after* `handleTrigger()` finishes and invokes its `onDone` callback — i.e., the `DELETE FROM aa_triggers` statement is inside the success path: [2](#0-1) 

Inside `handleTrigger`, once an AA-generated response unit is built, it is validated and saved through `validateAndSaveUnit`. Nearly every callback branch here is safe (`ifUnitError` calls back with an error which is bounced gracefully), but several other branches deliberately `throw Error(...)`: [3](#0-2) 

These thrown errors correspond to real, reachable branches inside `validation.js`, e.g. joint-level and transient-error checks on commission/size fields, `max_aa_responses`, oversize_fee, payload-hash mismatches, etc.: [4](#0-3) [5](#0-4) 

Any edge case where the AA-generated unit's deterministic construction in `aa_composer.js` (size/fee/oversize_fee computation, parent selection via `pickParents`, `max_aa_responses` propagation, etc.) diverges even slightly from what `validation.js` independently recomputes will land in one of these `ifJointError`/`ifTransientError`/`ifNeedParentUnits`/`ifNeedHashTree`/`ifOkUnsigned` branches and throw synchronously, deep inside a chain of nested async callbacks with no surrounding try/catch.

That uncaught exception propagates to the top level, where ocore's global handler intentionally crashes the whole process rather than continuing in a possibly-inconsistent state: [6](#0-5) 

Because the trigger row was never deleted (the crash occurred before the `DELETE FROM aa_triggers` step), the very next time the node starts it calls `handleAATriggers()` again specifically to pick up unfinished work: [7](#0-6) 

This recreates the exact same deterministic inputs (same stable unit, same AA definition, same DB state) and crashes again — an infinite crash loop that can only be fixed by out-of-band manual intervention (patching the code or hand-editing the `aa_triggers`/state), exactly as described in the source report's "non-recoverable, requires manual intervention" impact.

Because `aa_triggers` is a single global FIFO ordered by `mci, level, unit, address` (not per-AA), this stuck row blocks *all* subsequent AA triggers for *every* AA address in the network, not just the attacker's target — a strictly larger blast radius than the original single-external-chain DoS.

### Impact Explanation
Any unprivileged user who can post a unit that triggers an AA (i.e., any wallet holder) can construct a trigger whose resulting AA-generated response unit falls into one of the `throw Error` branches of `validateAndSaveUnit`. Since AA trigger execution is fully deterministic across all full nodes (same stable DAG state, same AA bytecode, same trigger payload), every full node in the network reaches the same crash simultaneously when the triggering unit's MCI stabilizes. Restart-and-retry does not fix it, because the queue row persists and is retried in the exact same manner. This halts stabilization-driven AA processing network-wide, preventing the network from confirming any new AA activity — matching the "network unable to confirm new units" / node-disagreement-on-liveness class of impact.

### Likelihood Explanation
No special privileges are needed — only the ability to author a normal unit that triggers an AA (identical prerequisite to the referenced report's cross-chain message). The specific edge case that would trigger one of the unsafe `throw` branches requires precise crafting (an aa_composer-side size/fee computation that legitimately diverges from validation.js's independent recomputation, or a `max_aa_responses`/payload edge condition), so exploitation requires careful engineering of an AA and trigger data, but the code paths themselves are reachable from unprivileged, attacker-controlled trigger data and AA definitions, and the fragile "throw on supposedly-impossible validation branch" pattern is used pervasively throughout `aa_composer.js` (34 occurrences), multiplying the number of potential triggering edge cases.

### Recommendation
- Wrap `validateAndSaveUnit`'s validation callbacks (and more generally the whole `handleTrigger`/`handlePrimaryAATrigger` call chain) so that any of `ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, `ifOkUnsigned` results in a graceful `bounce()` (recording the error in the response) instead of an uncaught `throw`, mirroring how `ifUnitError` is already handled.
- Ensure a failing/throwing trigger cannot block the shared `aa_triggers` queue indefinitely: e.g., delete or quarantine (into a separate "poisoned" table for manual review) a trigger row that repeatedly fails deterministic processing, rather than leaving it at the head of the FIFO forever.
- Avoid crashing the entire process on AA-processing exceptions; isolate a single misbehaving AA trigger's failure from the rest of the node's operation.

### Proof of Concept
1. Author or find an Autonomous Agent whose `messages` template, combined with attacker-controlled `trigger.data`, causes `aa_composer.js`'s independently-computed `headers_commission`/`payload_commission`/`oversize_fee` (or `max_aa_responses`, parent-selection, or payload-hash logic) for the AA-generated response unit to diverge from the value independently recomputed inside `validation.js` (aa_composer.js:1382-1403; validation.js:257-268, 744, 768-776).
2. Post a unit as an unprivileged user that sends the required minimum bounce-fee payment plus the crafted `data` to this AA address, triggering the divergence.
3. Once the triggering unit's MCI stabilizes, `handleAATriggers()` (aa_composer.js:59-89) processes the row, and `validateAndSaveUnit` (aa_composer.js:1800-1838) hits one of the `throw Error(...)` branches instead of the `ifUnitError` bounce path.
4. The uncaught exception reaches `process.on('uncaughtException', ...)` (network.js:4530-4543), which re-throws and crashes the node.
5. On restart, `startRelay()` calls `aa_composer.handleAATriggers()` again (network.js:4452) to finish "anything left from the previous run"; the same un-deleted row is retried, reproducing the exact same crash — a permanent DoS of AA-trigger processing for the whole node (and, since the computation is deterministic, for every full node in the network) until manually patched.
