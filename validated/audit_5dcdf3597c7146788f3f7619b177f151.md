This confirms the vulnerability path: `WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify against based solely on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), per `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`. But every event handler resolves the actual repository/stack to act on using a completely different, independently-controlled field: `payload.dig('repository', 'full_name')` in the base `Handler` class, and `params.repository.full_name` in the PR handlers, per `app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-16`, and e.g. `app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb:49-53`.### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` while every event handler acts on the independently-controlled `repository.full_name` field, allowing a forged webhook signed with one organization's secret to write to another organization's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate the HMAC signature against based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Once the signature passes, the raw, attacker-controlled JSON body is dispatched to event handlers that resolve the target repository/stack using a *different* nested field, `repository.full_name`, which is never cross-checked against the field used for authentication. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Shipit supports multi-organization GitHub App configuration, where each organization has its own `webhook_secret` (documented in `docs/setup.md`, "Using Multiple Github Applications"). The `verify_signature` before_action picks the `GitHubApp` instance — and thus the secret used for HMAC verification — purely from `repository.owner.login` (or `organization.login`) in the JSON payload:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

The signature only proves that the request body was HMAC-signed with the secret belonging to the organization named at `repository.owner.login`. It says nothing about which repository the handler will actually operate on. Once verification passes, `create` hands the entire parsed body to the matching handler(s):

```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [5](#0-4) 

Every handler, however, resolves the repository/stack to mutate from a separate field, `repository.full_name`, not from `repository.owner.login`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler#process` uses `stacks` (i.e., `full_name`) to find stacks and calls `stack.sync_github`: [6](#0-5) . PR handlers (`ClosedHandler`, `OpenedHandler`, `LabeledHandler`, `ReopenedHandler`, `AssignedHandler`) independently derive their target repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, e.g.: [7](#0-6) , [8](#0-7) .

`repository.owner.login` and `repository.full_name` are ordinarily two views of the same GitHub object and are consistent in genuine GitHub-emitted payloads. But since the attacker fully controls the raw JSON body sent to the webhook endpoint (only the byte string is HMAC-signed, not its semantic structure), nothing enforces that `full_name`'s owner segment matches `owner.login`. An attacker who legitimately controls (or has compromised) one org's webhook secret — e.g., because they administer a GitHub App installation for their own org `org-A` that is registered in this same Shipit instance's multi-org `github:` config — can construct a payload where `repository.owner.login = "org-A"` (so the correct secret is selected and the HMAC passes) but `repository.full_name = "org-B/some-repo"` (an entirely different, unrelated organization's tracked repository).

### Impact Explanation
This breaks the equality the engine is supposed to enforce: `organization authenticated by signature == organization whose repository is written`. With a forged/self-signed webhook, an attacker with only org-A's webhook secret can:
- Trigger `PushHandler` to invoke `stack.sync_github` on stacks belonging to `org-B/some-repo`, forcing an unauthorized GitHub sync against a repository the attacker does not control. [6](#0-5) 
- Trigger `ClosedHandler#process` to call `review_stack.archive!` on `org-B`'s review stacks. [9](#0-8) 
- Trigger `OpenedHandler` to provision new review stacks against `org-B`'s repository. [10](#0-9) 
- Trigger `LabeledHandler` to archive/unarchive stacks for `org-B`. [11](#0-10) 

These are unauthorized writes/deploys/rollback-adjacent actions (stack archive/unarchive, provisioning, forced sync triggering deploy pipelines) against a repository/organization the requester was never authenticated for, satisfying the "cross-repository writes / unauthorized deploy or rollback" bar.

### Likelihood Explanation
Likelihood is bounded by the precondition that the attacker must know a valid `webhook_secret` for *some* organization configured in this Shipit instance (its own, in a legitimate multi-org tenancy, or a leaked one) — this is not a privileged Shipit session, `ApiClient` token, or GitHub App private key, so it is in-scope as an "unprivileged attacker" relative to other tenants/repositories of the same instance. Given that precondition, exploitation is a single unauthenticated HTTP POST with a hand-crafted, self-signed body; no interaction with GitHub itself is required since the endpoint accepts any raw body that hashes correctly under the selected secret.

### Recommendation
After selecting the `GitHubApp` and verifying the signature, re-derive the same organization identity from `repository.full_name` (or `organization.login` used consistently) and reject the request (422) if it does not match `repository_owner`. Concretely, in `app/controllers/shipit/webhooks_controller.rb`, add a check such as:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) and return unless verified

  full_name_owner = params.dig('repository', 'full_name')&.split('/')&.first
  head(422) and return if full_name_owner && full_name_owner.casecmp(repository_owner).nonzero?
  ...
end
```
Additionally, `head(422)` calls in this method should `return` immediately rather than relying on Rails' implicit halting, to avoid any risk of continued processing.

### Proof of Concept
1. Configure (or compromise) Shipit's multi-org config with two orgs, `org-a` (secret `SECRET_A`, known to attacker) and `org-b` (secret unknown to attacker), per `docs/setup.md`'s "Using Multiple Github Applications" section, both tracked by the same Shipit instance with existing stacks/review-stacks.
2. Craft a `push` (or `pull_request` `opened`/`closed`/`labeled`) JSON payload where:
   - `repository.owner.login = "org-a"`
   - `repository.full_name = "org-b/target-repo"` (a repo actually tracked under `org-b` in Shipit)
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, raw_body)>` and POST it to `/webhooks` with `X-Github-Event: push` (or `pull_request`).
4. `verify_signature` looks up `Shipit.github(organization: "org-a")`, verifies successfully against `SECRET_A`, and the request is dispatched. [1](#0-0) 
5. The handler resolves the target using `repository.full_name = "org-b/target-repo"` and performs the corresponding write (e.g., `stack.sync_github`, `review_stack.archive!`) against `org-b`'s stack, even though the attacker never possessed `org-b`'s secret. [3](#0-2) [6](#0-5)
