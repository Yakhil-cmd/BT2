This confirms the mechanism: `validateAndSaveUnit` runs full unit validation on the AA's composed response unit, and if it fails (e.g. `validatePaymentInputsAndOutputs` rejecting the payment because an output address is not on the asset's attestor list, per `validation.js:2632-2641`), the composer calls `bounce(err)` [1](#0-0)  instead of the asset payment ever completing.

### Title
AA-issued spender_attested assets can be permanently frozen if the AA blindly pays them back to `trigger.address` and that address is/becomes unattested - (File: aa_composer.js, validation.js)

### Summary
Any Autonomous Agent (AA) that defines a custom asset with `spender_attested: true` and later automatically pays that asset out to `trigger.address` (the unit author who triggered it) is exposed to the same bug class as the reported `doRefund()`/USDC-blacklist issue: a hardcoded, unprivileged-controlled recipient address can be excluded from a gatekeeping list (the asset's attestor list, analogous to a blacklist), causing the AA's outgoing payment to permanently fail and the funds to remain stuck in the AA forever.

### Finding Description
When an AA defines an asset with `spender_attested: true`, every payment of that asset (including AA-originated ones) must have all output addresses on the current attestor list, enforced in `validatePaymentInputsAndOutputs`: [2](#0-1) 

This check is symmetric with the check performed when composing wallet payments client-side [3](#0-2) , and mirrors the identical check performed at the input (owner) side during payment validation [4](#0-3) , showing the "spender must be attested" restriction is fundamental to this asset type, not an oversight.

Attestor lists are not append-only or immutable for a given address; the current attestor list is computed from `asset_attestors` records read via `storage.filterAttestedAddresses`/`loadAssetWithListOfAttestedAuthors`, which any attestor (or the AA itself, since the AA is the asset definer) can update over time by publishing a new `asset_attestors` message [5](#0-4) . If the attestor(s) stop attesting a specific address — the exact analog of a token issuer adding an address to a blacklist — that address permanently loses eligibility to receive the asset.

When an AA composes its response unit and that unit fails full validation (as it will if the recipient became unattested), `sendUnit()` falls back to `bounce(err)` rather than completing the payment [6](#0-5) . `bounce()` only ever returns unused *base* bytes to `trigger.address`, up to `bounce_fees`; it never attempts to re-route or refund the asset itself [7](#0-6) . Since the AA logic is fixed (immutable oscript) and will keep trying to pay the same `trigger.address` on every subsequent trigger from that same user, the asset balance corresponding to that user's entitlement is permanently stuck inside the AA with no code path to redirect it to a different, still-attested address.

This is the direct analog of the reported issue: `doRefund()` sends to a fixed address (`bank.EXECUTOR()`) that can be excluded from an external gatekeeping list (USDC blacklist) with no fallback, permanently freezing funds. In ocore, an AA that defines a `spender_attested` asset and pays it back to `trigger.address` has a fixed recipient that can be excluded from the asset's attestor list, with the same permanent-freeze outcome enforced deterministically by consensus validation rules rather than an external service.

### Impact Explanation
Any AA-managed balance of a `spender_attested` asset owed to a specific address becomes permanently unrecoverable once that address is dropped from (or never added to) the attestor list, since the AA has no branch to send the asset elsewhere and the response unit will always fail `validatePaymentInputsAndOutputs`. This is a fund-freezing condition inside a smart-contract-like AA, matching the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Requires: (1) an AA design that issues/holds a `spender_attested` asset and pays it out based on `trigger.address` without checking attestation status first, and (2) the attestor(s) — who may be the AA definer or a separate governance/compliance party — revoking or never granting attestation for a given user address. Both conditions are realistic for compliance-oriented assets (KYC/AML-gated tokens are a primary use case for `spender_attested`), making this a plausible medium-likelihood scenario analogous to the original stablecoin-blacklist report.

### Recommendation
- AAs that issue `spender_attested` assets should verify attestation status of `trigger.address` before scheduling an asset payment to it (e.g., via a getter that reads `asset_attestors`), and provide an alternative code path (e.g., let the user specify a different, currently-attested destination address, or maintain an internal claimable balance under the AA's control that can be withdrawn later once attestation is restored) rather than relying on an unconditional payment to `trigger.address`.
- At the protocol level, consider allowing partial response success (skip the failing asset-only message while still completing state updates/bounce for the rest) so a single non-attested payment doesn't force a full bounce, or add documentation/warnings in the AA authoring guidance about this asset-freeze risk when combining `spender_attested` assets with automatic payouts to `trigger.address`.

### Proof of Concept
1. An AA's `init`/definition defines an asset `A` with `spender_attested: true` and `attestors: [X]` (attestor `X` may be the AA's own address or a separate trusted party) [8](#0-7) .
2. The AA logic, upon receiving triggers, issues/pays asset `A` to `trigger.address` in a `payment` message such as `{app:'payment', payload:{asset:"{var['A']}", outputs:[{address:"{trigger.address}", amount: ...}]}}`.
3. User `U` triggers the AA once while attested by `X`; the AA successfully sends `A` to `U`, and later the AA schedules a further amount of `A` owed to `U` (e.g., accrued rewards tracked in state vars, to be paid on a subsequent trigger).
4. Attestor `X` revokes/does not renew attestation for `U` (publishes an `asset_attestors` update without `U`, or simply never attested `U` to begin with for a new accrual).
5. `U` triggers the AA again to claim the owed `A`. The AA composes a response `payment` message sending `A` to `trigger.address` (`U`). `sendUnit()` completes the payload and calls `validateAndSaveUnit`, which invokes `validatePaymentInputsAndOutputs` → the `spender_attested` branch → `storage.filterAttestedAddresses` finds `U` is not attested → returns `"some output addresses are not attested"` [9](#0-8) .
6. `sendUnit` receives this error and calls `bounce(err)` [1](#0-0) , which only returns base-currency bounce fees, never the asset `A` [10](#0-9) .
7. Because the AA definition is immutable and always targets `trigger.address`, every subsequent attempt by `U` to claim the owed `A` fails identically — the asset balance is permanently frozen inside the AA, unrecoverable by `U` or anyone else.
