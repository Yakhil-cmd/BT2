### Title
Architecture-Conditional G2 Subgroup Check in Precompile 0x08 Causes Consensus Divergence Between amd64/arm64 and Other-Architecture Validators — (`crypto/bn256/gnark/g2.go`, `crypto/bn256/cloudflare/bn256.go`)

### Summary
The bn256 pairing precompile (address `0x08`) dispatches to two different implementations depending on build architecture. The gnark implementation (amd64/arm64) rejects G2 points not in the prime-order subgroup at deserialization time, while the cloudflare implementation (all other architectures) only checks curve membership. A crafted transaction supplying a G2 point on the twist curve but outside the prime-order subgroup causes the precompile to revert on gnark nodes and succeed (returning `false`) on cloudflare nodes, producing different EVM outputs and different state roots — a permanent chain split.

### Finding Description

The architecture dispatch is defined by build tags: [1](#0-0) [2](#0-1) 

**gnark G2.Unmarshal** performs both checks: [3](#0-2) 

**cloudflare G2.Unmarshal** performs only the curve check, with no subgroup check: [4](#0-3) 

`newTwistPoint` in the precompile layer calls `Unmarshal` with no additional guard: [5](#0-4) 

`runBn256Pairing` propagates any error from `newTwistPoint` directly: [6](#0-5) 

**Execution divergence for a subgroup-violating G2 point:**

| Architecture | `G2.Unmarshal` result | `runBn256Pairing` result | EVM effect |
|---|---|---|---|
| amd64 / arm64 (gnark) | error: "point is not in correct subgroup" | `nil, err` | call reverts |
| other (cloudflare) | success (no subgroup check) | `false32Byte, nil` | call succeeds, returns 0 |

The two nodes compute different EVM outputs for the same transaction, yielding different state roots.

### Impact Explanation
Any smart contract that calls precompile `0x08` and branches on its return value (e.g., a ZK-proof verifier) will execute different code paths on different validator architectures. The resulting state root divergence constitutes a permanent chain split between amd64/arm64 validators and any validator running on a non-amd64/non-arm64 architecture. This falls squarely within "consensus divergence on honest nodes."

### Likelihood Explanation
The attack requires only a public transaction with a crafted 192-byte input — no privileged access. The precondition is that at least one validator runs on a non-amd64/non-arm64 architecture (e.g., 32-bit ARM, MIPS, RISC-V). While most production validators use amd64/arm64, the code makes no architectural homogeneity guarantee, and the divergence is latent and exploitable whenever the condition is met.

### Recommendation
Add an explicit G2 prime-order subgroup check in the cloudflare `G2.Unmarshal`, mirroring the gnark implementation. Alternatively, add a post-`Unmarshal` subgroup check in `newTwistPoint` in `blockchain/vm/contracts.go` that is architecture-independent, so the validation gate is enforced regardless of which backend is compiled in.

### Proof of Concept
1. Construct a point `Q` on the BN254 twist curve (`y² = x³ + 3/(9+u)` over `GF(p²)`) with order dividing `p²-1` but not dividing the prime subgroup order `r`. Such points are well-known in the literature (cofactor-multiple of a generator).
2. Encode `Q` as 128 bytes in EVM format (big-endian `x.1 || x.0 || y.1 || y.0`).
3. Prepend any valid G1 point (64 bytes) to form a 192-byte pairing input.
4. Submit a transaction calling precompile `0x08` with this input.
5. Observe: on amd64/arm64 nodes the call reverts; on cloudflare-architecture nodes the call returns `0x00...00` (false). State roots diverge.
