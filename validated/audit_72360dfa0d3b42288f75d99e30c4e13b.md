### Title
Stack-scoped ApiClient token can read CCMenu status for any stack, bypassing token scope - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to load the target stack directly from `Stack.from_param!(params[:stack_id])` instead of going through the scoped `stacks` helper defined in `BaseController`. This breaks the binding between the stack an `ApiClient` token is authorized for (`ApiClient#stack_id`) and the stack the controller action actually operates on, letting a token scoped to one stack read CCMenu build/deploy status for any other stack.

### Finding Description
`Shipit::Api::BaseController` defines the scoping mechanism that all other API controllers rely on to bound a stack-scoped `ApiClient` to its assigned stack: [1](#0-0) 

`current_api_client.stack_id?` gates whether `Stack.all` or only the single authorized stack is visible, and `stack` (used by `LocksController`, `DeploysController`, etc.) is built on top of this scoped relation: [2](#0-1) 

`CCMenuController`, however, redefines both `authenticate_api_client` (to also accept the token via a query-string param, reasonable for CCMenu clients) and `stack`, and the redefined `stack` calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, never consulting `current_api_client.stack_id`: [3](#0-2) 

The `require_permission :read, :stack` check only verifies the string permission `read:stack` is present in `ApiClient#permissions` — it never checks which specific stack the permission applies to: [4](#0-3) 

So, for any `ApiClient` that has `stack_id` set to stack A and `permissions` including `read:stack`, calling `GET /api/stacks/:B/ccmenu.xml?token=<A's token>` (or with the header) succeeds and returns stack B's build/deploy data, because the controller never applies `current_api_client.stack_id` when resolving `stack`.

The correct binding, enforced everywhere else in the API surface, is: `ApiClient.stack_id == stack the request touches`, unless `stack_id` is nil (unscoped/global client). `CCMenuController` breaks this equality by resolving `stack` independent of `current_api_client` entirely.

### Impact Explanation
This lets a caller holding a stack-scoped, low-privilege `read:stack` API token (e.g., a CCMenu integration token intended only for one project) enumerate/read the build status, last build label/time, activity state, and lock status of **any** stack in the Shipit instance, not just the one it was issued for. This is an authorization-scope escalation / unauthenticated (relative to the token's actual grant) read of stack state, matching the "High" impact bucket: "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Exploitation only requires possession of any valid stack-scoped API token with `read:stack` permission (the exact class of token the `ccmenu_url` feature is designed to hand out per-stack) and knowledge/guessing of another stack's `stack_id` param (owner/repo/env or numeric id) — no additional privilege, GitHub identity, or session is required. This is a straightforward, deterministic bypass of an existing, otherwise well-enforced access control (the same-named `stack` scoping helper used by every other API controller).

### Recommendation
Remove the private `stack` override in `CCMenuController` (or reimplement it to reuse `BaseController#stacks`/`#stack`), so stack resolution is always scoped through `current_api_client.stack_id` just like the rest of the API surface. If a distinct lookup mechanism is required for CCMenu URLs, explicitly re-validate that the resolved stack's id matches `current_api_client.stack_id` when the client is stack-scoped.

### Proof of Concept
1. Create a stack-scoped API client for Stack A with `permissions: ['read:stack']` and `stack_id: A.id` (as done by `CCMenuUrlController#client`, or via the admin `ApiClientsController` if `stack_id` support is added there).
2. As an attacker in possession of that token, issue:
   `GET /api/stacks/:owner/:repo/:env-of-stack-B/ccmenu.xml?token=<stack-A-token>`
3. Observe HTTP 200 with stack B's CCMenu payload (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`), even though the token's `stack_id` refers to stack A only, confirmed by the resolver at: [5](#0-4) 
which is never intersected with `current_api_client.stack_id` from: [6](#0-5)
