## Title
Cross-organization commit-status forgery bypasses CI gating and enables unauthorized deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The external report's root cause — a value the code *trusts for computation* is not the same value that was *cryptographically verified* — has a direct analog in Shipit's webhook pipeline. `WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC against based on an **unverified** payload field (`repository.owner.login`), while the actual event handler (`StatusHandler`) subsequently acts on a **completely different, unscoped** payload field (`sha`) that is never checked against the authenticated organization. This breaks the equality "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config used to validate `X-Hub-Signature` purely from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read from the unauthenticated JSON body (`params.dig('repository', 'owner', 'login')`) and used to look up that organization's own `webhook_secret` via `Shipit.github(organization: repository_owner)`. Because Shipit supports multiple independently-configured GitHub organizations (each with its own `webhook_secret`), this only proves the request was signed by *some* organization Shipit trusts — not that the payload's other fields legitimately belong to that organization's repositories.

The `status` event handler then processes the request without ever re-validating that the target commit belongs to the organization whose secret was used to authenticate: [3](#0-2) 

`Commit.where(sha: params.sha)` performs an **instance-wide** lookup with no repository/organization scoping at all, and `create_status_from_github!` writes a CI status record for every matching commit found, regardless of which repository it belongs to. This is unlike `PushHandler`/`PullRequest` handlers, which at least scope through `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` — but even those never verify that `full_name`'s owner matches the `owner.login` used to select the signing secret in the controller (see `Handler#repository_name` / `#stacks`): [4](#0-3) 

So the binding actually enforced is: *"payload signed by organization X's secret"* → *"act on any commit sha reachable in the entire Shipit database"* (for `status`), or *"act on `repository.full_name` from the same unverified payload, independent of X"* (for push/pull_request). Neither matches the intended invariant that the authenticated organization X must equal the repository being mutated.

### Impact Explanation
Shipit's deploy gating relies on commit CI statuses (`required_statuses` in `shipit.yml`) to decide whether a commit is `deployable?`, and `continuous_deployment`-enabled stacks automatically deploy commits once they become deployable. An attacker who legitimately administers **their own** GitHub organization/App entry in Shipit's `config/secrets.yml` (a normal, unprivileged-to-Shipit action — they only need to be an admin of an org that some Shipit operator chose to onboard, and thus know that org's `webhook_secret`) can:

1. Sign an arbitrary JSON payload with their own organization's `webhook_secret`.
2. Set `sha` to any commit SHA belonging to a *different, victim* organization/repository tracked by the same Shipit instance.
3. Have Shipit write a forged "success" `CommitStatus` for a `required_statuses` context onto that victim commit.

This can mark an unreviewed/unvetted commit as CI-passing, unlocking an unauthorized deploy (automatically via continuous deployment, or by removing the CI blocker for a manual deploy) on a stack the attacker has no legitimate access to — this maps to the "unauthorized deploy" Critical-impact category in scope.

### Likelihood Explanation
Medium. It requires the attacker to control at least one GitHub organization already configured in Shipit's multi-org `github:` secrets section (a supported, documented configuration per `docs/setup.md`), which is a realistic scenario for any Shipit instance shared across several teams/orgs. No Shipit account, API token, or `webhook_secret` belonging to the *victim* org is needed — only the attacker's own credentials, plus a target commit SHA (public, non-secret information visible in the victim's git history/PRs).

### Recommendation
When verifying and processing a webhook, bind the entire trust chain to a single authenticated repository/organization: derive the signing key from the same repository reference that the handler will act on, and have every handler (especially `StatusHandler`) scope its target lookup (`Commit`, `Stack`, `Repository`) to the organization/repository that was cryptographically verified in `WebhooksController#verify_signature`, rejecting the event if the two disagree.

### Proof of Concept
1. Attacker owns/administers `attacker-org`, which is configured in Shipit's `config/secrets.yml` with a known `webhook_secret`.
2. Attacker crafts a `status` event payload targeting a commit SHA from `victim-org/victim-repo` (a stack tracked by the same Shipit instance):
```json
{
  "sha": "<victim_commit_sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s own `webhook_secret` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `attacker-org`'s app, and the signature check passes because it was legitimately signed by that org's own secret. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, unscoped by repository, finds the victim commit, and writes a forged "success" status for `ci/required-check`. [5](#0-4) 
6. If `ci/required-check` is part of `victim-org/victim-repo`'s `required_statuses`, the victim commit is now marked deployable in Shipit despite never having passed real CI, potentially triggering an automatic deploy on a continuous-deployment-enabled stack or unblocking a manual deploy that should have been CI-gated.

```ruby
module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
```
