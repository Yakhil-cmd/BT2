Session Fixation on GitHub OAuth Login Skips Session-ID Rotation - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
The DODO GSP bug lets an attacker manipulate a state boundary (a pool balance that should never legitimately reach zero) that isn't defended by the pricing algorithm's invariants, then reuse that broken state to drain the pool. The engine analog is a broken invariant around the *session-identity* boundary: `Shipit::GithubAuthenticationController#callback` binds a freshly-authenticated GitHub identity to `session[:user_id]` without first rotating the session ID, so a pre-existing (attacker-known) session cookie is silently promoted to an authenticated one — the "GitHub identity vs. `User` bound to the session" binding is violated exactly like the reserve-vs-price binding in the report.

### Finding Description
Session-based auth is implemented in `Shipit::Authentication#find_current_user`, which trusts whatever `session[:user_id]` is set to: [1](#0-0) 

The only place `session[:user_id]` is assigned is in the OAuth callback: [2](#0-1) 

`callback` calls `sign_in_github(auth)` and stores the resulting id directly into the *current* session — the same session object that existed before the user authenticated. It never calls `reset_session` (or otherwise rotates the Rails session id) before writing `session[:user_id]`. Compare this with `logout`, which explicitly calls `reset_session`, and with `force_github_authentication`, which calls `reset_session` only in the unrelated "stale token" branch: [3](#0-2) 

Because the session store is the standard Rails `:cookie_store` (see the dummy app's `session_store.rb`), the session identifier itself is the encrypted cookie; regardless of store type, Rails' own guidance is that a session's privilege level must be rotated on login to prevent fixation. Here, the binding "unauthenticated session that existed before login" vs. "authenticated `User` fixed into the session after login" is never re-established — the pre-login session is reused verbatim.

### Impact Explanation
An attacker who can get a victim's browser to hold a session cookie value known/controlled by the attacker (e.g., by setting a cookie for the Shipit host before authentication — feasible whenever the attacker can write cookies for the same domain, such as via a sibling subdomain, a prior unauthenticated visit relayed back to the victim, or any mechanism that plants a session id before the OAuth dance completes) can wait for the victim to complete the GitHub OAuth login. Because the id is never rotated, the attacker's held session id becomes authenticated as the victim's `User`, and the attacker can then use that same session cookie to act as the victim inside Shipit — creating `ApiClient` tokens, viewing/approving deploys, or performing any action gated by `current_user`, including `Shipit.github_teams`-authorized functionality. This directly maps to the rules' explicit High-impact category: "session fixation / forced OAuth completion."

### Likelihood Explanation
No credentials, `ApiClient` token, webhook secret, or GitHub App private key are needed — only the ability to fix a session cookie value on the shared domain before the victim finishes the standard GitHub OAuth login, which is the textbook session-fixation precondition. The vulnerable code path is unconditional: every successful `callback` reuses the existing session unless the "fresh login" branch happens to fire (an unrelated, narrower condition tied to legacy token formats), so the missing rotation is present in the default/documented deployment.

### Recommendation
Call `reset_session` (or `request.session.exclude?`-safe equivalent, e.g. `session.merge!` after `reset_session`) at the very start of `GithubAuthenticationController#callback`, before or immediately after computing `sign_in_github(auth)`, so a new session id is issued at the point of privilege escalation, exactly as is already done in `logout`. Preserve `omniauth.origin`/`return_url` across the reset since `reset_session` clears all session keys.

### Proof of Concept
1. Attacker visits `https://shipit.example.com/` (unauthenticated) and captures/sets the resulting `_session` cookie value `S` for the shared domain (e.g., via a subdomain cookie-tossing primitive, or by directing the victim to open a link that sets `S` in the victim's browser for the Shipit domain).
2. Victim's browser, still holding cookie `S`, is induced to visit `/github/auth/github` and completes the real GitHub OAuth login.
3. `GithubAuthenticationController#callback` executes with the *existing* session tied to cookie `S`; it sets `session[:user_id] = victim.id` and `session[:authenticated] = true` without rotating the session id.
4. Attacker replays cookie `S` against the Shipit host; `Authentication#find_current_user` resolves `session[:user_id]` to the victim's `User`, granting the attacker an authenticated session as the victim — able to create `ApiClient` tokens, trigger deploys/rollbacks, or perform any action gated on `current_user.authorized?`.
