### Title
Cross-tenant `pull_request` edited webhook forgery via decoupled `repository.owner.login` (signature org) and `repository.full_name` (handler target) - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's GitHub App/webhook secret to verify against using `params.dig('repository', 'owner', 'login')`, while `EditedHandler` independently resolves the *target* repository/stack to mutate using `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`. Because these are two independent, attacker-controlled fields in the same raw JSON body, and because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected organization has no `webhook_secret` configured, an attacker can pick an org with no secret for the "owner" field while pointing `full_name` at an arbitrary victim repository, causing `EditedHandler` to update that victim's `PullRequest` record.

### Finding Description
The broken binding: the question's invariant states that the organization whose `webhook_secret` verified the request must equal the organization owning the repository/stack the handler mutates — i.e. `repository_owner (used in verify_signature)` == `owner segment of repository.full_name (used in EditedHandler#repository)`. This equality is never enforced anywhere in the code.

Trace:
- `Shipit::WebhooksController#verify_signature` computes `repository_owner` purely from `params.dig('repository', 'owner', 'login')` [1](#0-0)  and uses it only to pick which `Shipit.github(organization: ...)` app/secret to check against [2](#0-1) .
- `GitHubApp#verify_webhook_signature` short-circuits to `true` with no signature check at all when that selected organization has no configured `webhook_secret`: `return true unless webhook_secret` [3](#0-2) . When a secret *is* configured, the malformed-header path (`signature.split("=", 2)` producing `algorithm` = full string, `signature` = nil) is actually blocked by `return false unless algorithm == 'sha1'` before `SecureCompare.secure_compare` is ever reached with attacker-shaped nil input — so the literal "nil into secure_compare" bypass described in the question does not work against orgs that have a secret.
- However, the real defect is that `repository_owner` (signature-verification org) is never checked against the repository the handler actually acts on. `Shipit::Webhooks::Handlers::PullRequest::EditedHandler#repository` independently re-derives the target repository from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name` [4](#0-3) , and `#pull_request` finds and mutates any `Shipit::PullRequest` joined to that repository via `stacks: { repositories: { id: repository.id } }` [5](#0-4) , then calls `pull_request.update(github_pull_request: params.pull_request)` [6](#0-5) .

Exploit flow: attacker crafts a JSON body with `repository.owner.login = "org-with-no-secret"` (any org registered in Shipit's config that has no `webhook_secret`, which the attacker can discover/target if such an org exists) but `repository.full_name = "victim-org/victim-repo"` — an org/repo the attacker does not control. `verify_signature` looks up "org-with-no-secret", finds no secret, and passes the request unconditionally regardless of the `X-Hub-Signature` header content. `drop_unhandled_event` passes because `pull_request` has a registered handler. `EditedHandler` then resolves and updates the `PullRequest` belonging to `victim-org/victim-repo`, entirely driven by attacker-supplied `params.pull_request` content.

Existing guards do not prevent this: `ExplicitParameters` schema only validates types/presence of fields, not cross-field consistency between `repository.owner.login` and `repository.full_name` [7](#0-6) ; there is no code anywhere binding the two.

### Impact Explanation
An unprivileged internet user can, with no Shipit credentials, forge a `pull_request` "edited" webhook that mutates a `PullRequest` record belonging to a repository/stack/org unrelated to the one used for signature verification, as long as any org configured in the Shipit instance lacks a `webhook_secret`. This is a cross-tenant state-mutation bug matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable against any repository tracked by Shipit and does not require possessing the victim org's `webhook_secret`.

### Likelihood Explanation
Exploitability is conditioned on at least one organization configured in `Shipit.github_apps`/secrets having no `webhook_secret` set (a real-world common misconfiguration for smoke-test/dev orgs, or intentionally omitted for low-risk orgs) — the code path `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature` exists specifically to allow unauthenticated webhooks for such orgs, but nothing scopes that trust to only that org's own repositories. Attacker cost is a single crafted HTTP POST with no secrets, fully repeatable.

### Recommendation
In `EditedHandler` (and other handlers resolving repository/stack from payload), verify that the resolved repository's owner matches the `repository_owner` that was used to select the webhook-verification organization, or better, pass the verified organization context explicitly into the handler and reject any mismatch. Additionally, consider requiring a configured `webhook_secret` for all organizations (removing the `return true unless webhook_secret` bypass), or scoping the "no secret" bypass so it can only ever affect that same organization's own repositories.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, `ActionDispatch::IntegrationTest`):
1. Configure two orgs in test secrets: `no-secret-org` (no `webhook_secret`) and `victim-org` (has a `webhook_secret`).
2. Create `victim-org/victim-repo` `Shipit::Repository`, a `Stack`, and a `PullRequest` record with `number: 2` and known `github_pull_request` content, owned by `victim-org`.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, `X-Hub-Signature` set to garbage (e.g., `"garbage"` with no `=`), and JSON body: `{"action":"edited","number":2,"pull_request":{...attacker payload...},"repository":{"owner":{"login":"no-secret-org"},"full_name":"victim-org/victim-repo"},"sender":{"login":"attacker"}}`.
4. Assert response is `:ok` (verification passed via the no-secret org).
5. Reload the `victim-org` `PullRequest` and assert `github_pull_request` equals the attacker-supplied `params.pull_request`, proving cross-tenant mutation: `assert_equal(attacker_payload, pull_request.reload.github_pull_request)` — i.e., `repository_owner` used for verification (`"no-secret-org"`) != owner of the repository actually mutated (`"victim-org"`).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
