### Title
CCMenuController#stack bypasses `current_api_client.stack_id` scope, exposing foreign stack deploy data via unauthenticated-equivalent token replay - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuController` overrides the base `stack` accessor to resolve `Stack.from_param!(params[:stack_id])` directly against all stacks, instead of using the scoped `stacks.from_param!` helper from `BaseController` that restricts lookups to `current_api_client.stack_id`. Combined with `require_permission :read, :stack`, which only checks the client's permission bitset and never compares `current_api_client.stack_id` to `params[:stack_id]`, a CCMenu token scoped to one low-privilege stack can be replayed against arbitrary `stack_id` values to read another stack's latest deploy/rollback data.

### Finding Description
The binding that should hold is: `stack.id == current_api_client.stack_id` (when the client is scoped) for every resource returned by `CCMenuController#show`. In `BaseController`, this is enforced by: [1](#0-0) 
which restricts `stacks` to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and resolves `stack` from that restricted relation.

`CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely: [2](#0-1) 

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)`, which validates that `"read:stack"` is present in the client's permission list — it performs no comparison against `params[:stack_id]` or `current_api_client.stack_id`. Because `CCMenuController#stack` calls `Stack.from_param!` (unscoped) rather than `stacks.from_param!` (scoped), any authenticated CCMenu token — including one created for a single, low-privilege stack via `CCMenuUrlController#fetch` (`ApiClient.create_with(permissions: %w[read:stack])`) — satisfies `require_permission` for every other stack in the system, and `show` proceeds to call `stack.deploys_and_rollbacks.last` on the attacker-chosen foreign stack, rendering its `deploy.id`, status, and timestamps in the CCMenu XML response.

Attacker flow:
1. Obtain a CCMenu URL/token for a stack they own (e.g., via `CCMenuUrlController#fetch`), which creates an `ApiClient` scoped to that one stack with `read:stack` permission.
2. Replay `GET /api/stacks/*stack_id/ccmenu?token=<their_token>`, substituting `stack_id` with other tenants' stack identifiers.
3. `authenticate_api_client` succeeds (token is valid), `require_permission!(:read, :stack)` passes (permission bit present, no stack-id check), `stack` resolves the foreign stack unscoped, and the XML in `shipit/ccmenu/project` discloses the foreign stack's latest deploy/rollback id, status, and timestamps.

This is the same root cause identified for the CCMenuController's `stack` resolution as in the related Q1 finding (unscoped `Stack.from_param!` overriding the scoped base implementation), now specifically manifesting as cross-tenant deploy-state disclosure through `NoDeploy`/`deploys_and_rollbacks.last`.

### Impact Explanation
An attacker holding only a token scoped to their own low-privilege stack can enumerate and read the latest deploy/rollback identifier, build status, and timestamps for any other stack in the Shipit instance, purely by varying the `stack_id` path segment — an unauthenticated-equivalent read of deploy state across tenants. This matches the High severity category "unauthenticated read of stack state, task streams or deploy output." The attack is fully repeatable against arbitrary stacks with a single valid token and imposes no additional cost per target.

### Likelihood Explanation
Preconditions are minimal: the attacker needs any valid CCMenu token, obtainable legitimately for their own stack (e.g., via the "Get CCMenu URL" feature which is available to any user with access to at least one stack). No GitHub secrets, webhook secrets, or elevated Shipit roles are required. The exploit is a trivial parameter substitution in an HTTP GET request, fully scriptable for enumeration across all `stack_id`s.

### Recommendation
Change `CCMenuController#stack` to use the scoped lookup, matching `BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
where `stacks` respects `current_api_client.stack_id` as defined in `BaseController#stacks`. Remove the controller-local override entirely if no CCMenu-specific behavior is needed, so it inherits the scoped implementation.

### Proof of Concept
Minitest under `test/controllers/api/ccmenu_controller_test.rb`:
```ruby
test "a token scoped to stack A cannot see stack B's deploy data via ccmenu" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: "main")
  deploy_b = stack_b.deploys.create!(until_commit: stack_b.commits.create!(sha: "a" * 40), since_commit: stack_b.commits.create!(sha: "b" * 40))

  scoped_client = ApiClient.create!(stack_id: stack_a.id, permissions: %w[read:stack])

  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

  assert_response :ok
  project = Hash.from_xml(response.body)['Projects']['Project']
  # Binding under test: rendered project must belong to the client's authorized stack (stack_a), never stack_b
  assert_not_equal stack_b.to_param, project['name']
  refute_includes response.body, deploy_b.id.to_s
end
```
This test currently fails against the unscoped `Stack.from_param!` implementation, confirming the cross-tenant read.
