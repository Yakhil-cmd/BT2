### Title
Cross-stack CI status disclosure via stack-scoped API token in CCMenuController - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` re-defines the `stack` lookup method to resolve the stack directly from `params[:stack_id]` instead of using the stack-scoped lookup defined in `Api::BaseController`. This breaks the binding between "the stack an `ApiClient` token is authorized for" and "the stack whose data is actually returned," allowing a token scoped to one stack to read CI/deploy status of any other stack.

### Finding Description
`Api::BaseController` implements stack-scoping for tokens created with a specific `stack_id`: [1](#0-0) 

`stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `stack` builds on top of that restricted scope via `stacks.from_param!(...)`. Every other API controller (`StacksController`, `DeploysController`, `LocksController`, `CommitsController`, etc.) relies on this inherited `stack` method, so a stack-scoped token can only ever resolve to its own stack.

`Api::CCMenuController`, however, overrides `stack` to bypass the scoped lookup entirely: [2](#0-1) 

The permission check performed before `show` is only: [3](#0-2) 

`check_permissions!` only verifies that the string `"read:stack"` is present in the token's `permissions` array — it never re-validates that the requested stack matches `current_api_client.stack`. Since `CCMenuController#stack` no longer goes through the stack-id-scoped `stacks` relation, `require_permission :read, :stack` combined with the overridden `stack` method allows any authenticated token that merely holds `read:stack` permission — including one that was created scoped to stack A — to fetch build/CI data for stack B by simply passing a different `stack_id` in the URL.

This is directly analogous to the HoneyLocker bug: the migration was authorized based on codehash equivalence but the actually-executed contract used unchecked, attacker-supplied `unlocked`/`referral`/`HONEY_QUEEN` values. Here, the token is authorized ("permission check passes") based only on the `read:stack` string, while the actual stack object acted upon is an unchecked, caller-supplied `stack_id` that is never bound back to the token's own `stack_id`.

### Impact Explanation
This yields unauthenticated (in the sense of unauthorized-scope) read access to another stack's state: repository name, environment, branch, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, and lock status — information that should only be visible to holders of a token scoped (or unscoped) to that specific stack. This matches the "High" impact criterion of "unauthenticated read of stack state, task streams or deploy output" via escalation past the token's intended stack scope.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped API tokens (a normal, documented `ApiClient` feature: `belongs_to :stack, optional: true`, `stack_id?` check) to distinct, less-trusted consumers (e.g. one per team/stack), since simply changing the `stack_id` path segment in a CCMenu request is enough — no additional secrets or privileges are required beyond possessing any valid `read:stack` token, no matter which stack it was minted for.

### Recommendation
Remove the `stack` override in `Api::CCMenuController`, or make it delegate to the inherited, scope-aware `stacks`/`stack` implementation from `Api::BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) so that stack-scoped tokens cannot resolve stacks outside their `stack_id`. Alternatively, harden `ApiClient#check_permissions!`/`require_permission!` to also assert `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` for every controller action, closing this class of bug engine-wide rather than per-controller.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to Stack A only, with `permissions: ['read:stack']` (`stack_id` set to Stack A's id).
2. Using the resulting `authentication_token`, issue a request to `GET /api/:stack_b_id/ccmenu.xml?token=<token>` where `stack_b_id` refers to Stack B (a different stack the token was never scoped to).
3. Observe that `Api::CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])`, ignoring `current_api_client.stack_id`, and the controller renders Stack B's CI/build status (`lastBuildStatus`, `lastBuildLabel`, etc.), even though the token is only supposed to authorize reads of Stack A.
