### Title
Operator-precedence bug in `unarchive?` lets a repository with `review_stacks_enabled: false` still provision a review stack - (File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb)

### Summary
`ReopenedHandler#unarchive?` combines `review_stacks_enabled` with the three `provisioning_behavior_*?` checks using `&&`/`||` in a way that Ruby parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`, so `review_stacks_enabled` only gates the first disjunct. A repository with `review_stacks_enabled == false` but `provisioning_behavior == 'allow_with_label'` (or `prevent_with_label`) will still unarchive/provision a review stack when a labeled PR is reopened.

### Finding Description
The intended binding is that `repository.review_stacks_enabled == false` must always suppress provisioning, i.e. `unarchive? == false` whenever `review_stacks_enabled == false`, regardless of `provisioning_behavior`. The actual code is: [1](#0-0) 
Because `&&` binds tighter than `||`, this evaluates as `(review_stacks_enabled && provisioning_behavior_allow_all?) || (provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) || (provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)`. The second and third disjuncts never reference `review_stacks_enabled`.

There is no model-level constraint tying `provisioning_behavior` to `review_stacks_enabled`; `Repository` only validates `name`/`owner` format and uniqueness, and defines the `provisioning_behavior` enum independently: [2](#0-1) 
So an operator can (or the field can already) hold `review_stacks_enabled: false` with `provisioning_behavior: allow_with_label` at the same time — nothing in this engine prevents that combination.

Exploit flow: an attacker opens a PR carrying the label named by `repository.provisioning_label_name` against a tracked repository configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label`. Note that `OpenedHandler#provision?` has the identical bug: [3](#0-2) 
so the initial `opened` webhook already creates the `ReviewStack` via `ReviewStackAdapter#find_or_create!`/`create!`, queuing it in `Shipit::ReviewStackProvisioningQueue`: [4](#0-3) 
If the PR is then closed (archiving the stack) and reopened, `ReopenedHandler#process` calls `stack.unarchive!` -> `ReviewStackAdapter#unarchive!`, which re-adds the stack to the provisioning queue and unarchives it: [5](#0-4) 
None of the standard guards (`verify_signature`, `ExplicitParameters` schema, model validations) address this because they only check payload shape/authenticity, not this boolean-logic defect; the webhook payload itself is legitimately signed for the attacker's own repository/PR, and the flaw is purely in the handler's decision logic.

### Impact Explanation
An unauthorized `Shipit::ReviewStack` is created/unarchived and queued for provisioning on a repository whose operator explicitly disabled review stacks (`review_stacks_enabled: false`), using a `branch` pointing at the attacker's fork ref. This is a record written (and provisioning triggered) for a repository configuration that did not authorize it — matching the "unauthorized deploy" / stack-mutation-without-authorization class of Critical impact. The issue is repeatable by any user who can open/label/close/reopen PRs against the affected repository, for every such repository with this specific `review_stacks_enabled: false` + non-`allow_all` `provisioning_behavior` configuration.

### Likelihood Explanation
Requires a specific, plausible repository misconfiguration: `review_stacks_enabled: false` combined with `provisioning_behavior: allow_with_label` (or `prevent_with_label`), which the engine does not prevent or validate against. The attacker needs only PR-open/label/close/reopen actions on their own fork PR — no privileged access, secrets, or maintainer role required, and the same bug is present and exploitable via `OpenedHandler` alone for initial creation. Fully repeatable.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all disjuncts, e.g.:
```ruby
def unarchive?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Apply the identical fix to `OpenedHandler#provision?`, `LabeledHandler`, and `UnlabeledHandler`, which share the same broken expression.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`:
1. Create a `Shipit::Repository` fixture/record with `review_stacks_enabled: false`, `provisioning_behavior: 'allow_with_label'`, `provisioning_label_name: 'deploy-preview'`.
2. Create an archived `Shipit::ReviewStack` for that repository with `environment: "pr#{number}"`.
3. Build a `reopened` payload for that repo/PR including a label named `'deploy-preview'`.
4. Assert the broken binding directly: `assert_equal false, repository.review_stacks_enabled` and `refute repository.review_stacks_enabled && true` while `handler.send(:unarchive?)` returns `true` — showing divergence.
5. `assert_difference -> { Shipit::ReviewStackProvisioningQueue.count }, 1 do ReopenedHandler.new(payload).process end` and assert the stack becomes unarchived — demonstrating provisioning occurred despite `review_stacks_enabled == false`.
