### Title
Address definitions that delegate spending authority via `['address', X]` re-evaluate the referenced address's *current* (mutable) definition, creating an unbounded, revocation-less trust analogous to unlimited allowance - (File: definition.js)

### Summary
The reported bug is that `TrueFiStrategy.sol` grants `type(uint256).max` allowance to external, upgradeable proxy contracts, so if the proxy's controlling key is ever compromised the strategy's entire balance can be drained without any further consent from the strategy contract. The analogous risk-class in `ocore` is not a token allowance, but Obyte's spending-condition primitive `['address', 'BASE32']`, which lets one address's definition delegate a branch of its authorization logic to whatever definition another address currently has - evaluated fresh, every single time, against that other address's *latest* definition rather than a snapshot fixed at delegation time.

### Finding Description
When an address (or an asset condition) includes `['address', X]` in its definition, validation does not hard-code or pin the definition of `X` at the moment the delegating definition was created. Instead, at authentifier-evaluation time it looks up `X`'s definition as of `last_ball_mci` and recursively evaluates it: [1](#0-0) 

The code comments explicitly acknowledge this is a live, always-current binding, not a fixed snapshot - it is re-validated "every time" specifically because the referenced address may have since been redefined: [2](#0-1) 

Address `X`'s owner is free to change `X`'s definition at any time via an `address_definition_change` message, and that new definition becomes authoritative going forward for every other address/asset condition that still references `X` via `['address', X]`: [3](#0-2) [4](#0-3) 

This is structurally the same trust pattern as an unlimited ERC20 allowance to a contract behind an upgradeable proxy: the delegating party (`TrueFiStrategy` / the address referencing `X`) grants unbounded, standing authority to an external, mutable target (`tfUSDC`/`tfFarm` implementation / address `X`'s definition), and that authority is never re-confirmed or capped - it simply tracks whatever the external party currently controls. If the private key controlling `X` is ever compromised, or `X`'s owner is coerced/tricked into redefining `X` (e.g. to `['sig', {attacker_pubkey}]` or `["or", [...]]` with an attacker branch), every address that references `X` via `['address', X]` (directly, or nested through `'r of set'`/`'and'`/`'or'`) is silently and immediately affected - with no notification, no re-approval, and no amount limit, exactly mirroring the "if the proxy admin key is compromised, the hacker can drain the strategy" scenario in the report.

The same unlimited, revocation-less delegation pattern also applies to `'cosigned by'` (definition.js) and `'attested'`/`in data feed`/`asset_attestors` conditions, all of which grant standing, unbounded trust to externally-controlled, mutable state (a cosigner address, an attestor list, or an oracle feed) rather than a value or set fixed at definition time.

### Impact Explanation
If the referenced address `X` is compromised (private key theft, social engineering into signing a definition-change, or the owner acting maliciously later), any address whose spending condition contains `['address', X]` can be spent from as soon as `X`'s new definition satisfies the referencing address's logic - without the referencing address's own key ever being involved (e.g., in an `or` combinator) or with reduced security (in an `and`/`r of set` combinator where `X` is one of several required signers, effectively lowering that branch's assurance to whatever `X` currently is). This is unauthorized spending of funds controlled by the referencing address/AA, matching the "Accept only concrete unauthorized spending... or AA fund loss" bar. Because Obyte addresses/AAs frequently reference shared-address definitions, DAO-style multisig setups, or oracle addresses through this mechanism, the blast radius is any construction that builds long-lived trust relationships on `['address', X]`, `'cosigned by'`, or attestor lists without ever hard-pinning the trusted definition.

### Likelihood Explanation
Medium. It requires either (a) compromise of the private key of the referenced address `X`, or (b) `X`'s legitimate owner being convinced/coerced to change `X`'s definition - both realistic key-compromise scenarios analogous to the "proxy admin key compromised" premise in the original report, and not requiring any bug in ocore's core validation logic itself; the risk is inherent to the primitive's semantics (an "unbounded, live-binding trust" instead of a "capped, snapshot-based trust"), just like the TrueFi finding is inherent to the unbounded `approve()` pattern rather than a bug in the ERC20 standard.

### Recommendation
For `['address', X]` (and analogously `'cosigned by'`, asset `attestors` lists) used in security-critical spending conditions, prefer pinning to the specific `definition_chash` known at the time of composing the definition (e.g. via `['definition template']` with the address's current keys baked in, or requiring `['has definition change', [X, expected_chash]]`/`['seen definition change', [X, expected_chash]]` guards) rather than open-ended `['address', X]`, so that a future redefinition of `X` cannot silently expand or transfer spending authority. Where full ocore semantics require the live-binding behavior (as documented in `definition.js`), document and audit any address/AA that references external addresses this way for the standing, unbounded trust it grants, treating it with the same scrutiny as an unlimited ERC20 allowance.

### Proof of Concept
1. Address `A` is defined as `["or", [["sig", {pubkey: pubA}], ["address", "X"]]]`.
2. `X` is currently defined and controlled by a trusted party; `A`'s owner is comfortable delegating spending authority to `X` as a recovery/co-management mechanism.
3. Attacker later compromises the private key of `X` (independent of `A`).
4. Attacker signs a unit spending from `A`, authenticated purely via the `["address", "X"]` branch, which `definition.js`'s `evaluate`/`validateAuthentifiers` resolves by reading `X`'s definition as of `last_ball_mci` [5](#0-4)  and validating the attacker's signature against it.
5. `A`'s funds are spent without ever using `pubA`, purely because `A`'s definition granted unbounded, standing trust to whatever `X` currently is - the ocore analog of draining `TrueFiStrategy` via a compromised, unlimited-allowance-holding proxy.
