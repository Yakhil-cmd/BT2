## Title
Webhook Signature Verified Against Attacker-Chosen Organization While Payload Content Is Applied To Any Tenant's Repository/Commit - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to validate an inbound HMAC signature against by reading an **unverified** field out of the very payload it is about to verify (`repository.owner.login` or `organization.login`). Once verification passes, the downstream `Webhooks::Handlers` resolve *which* stack/repository/commit to mutate using a **different** unverified field of the same payload (`repository.full_name`, or in `StatusHandler`, a bare `sha` with no repository scoping at all). Nothing enforces that the organization whose secret validated the signature is the same organization that owns the repository/commit being acted upon.

### Finding Description
In a multi-organization Shipit deployment (explicitly supported and documented, see `config/secrets.development.example.yml:18-38` and `docs/setup.md`), each onboarded GitHub organization has its own GitHub App and its own `webhook_secret`: [1](#0-0) 

`verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it to select `Shipit.github(organization: repository_owner)`, then checks the signature with that org's secret: [2](#0-1) 

`GitHubApp#verify_webhook_signature` only proves that *some* org's configured secret matches, not that this secret belongs to the org that actually owns the resource the payload describes: [3](#0-2) 

Once the request passes, `create` hands the raw, unauthenticated-as-to-ownership `params` straight to the registered handler: [4](#0-3) 

The base `Handler` resolves the target `Stack` purely by `repository.full_name`, a field completely independent of the `repository_owner` value used to pick the verifying secret: [5](#0-4) 

Worse, `StatusHandler` (which creates GitHub commit statuses used to gate deploys) does not scope by repository/organization at all — it matches purely by `sha`, globally, across the entire Shipit installation: [6](#0-5) 

**Binding broken (equality that should hold but doesn't):**
`organization whose webhook_secret authenticated the request` == `organization/repository whose Stack/Commit is mutated by the payload`.

Before the PR/hypothetical fix: the two are decoupled — the controller authenticates "does *a configured org's* secret match this body", while the handler blindly trusts unrelated fields (`full_name`, `sha`) in that same attacker-authored body to decide what to change.

### Impact Explanation
Any tenant onboarded onto a shared multi-org Shipit instance (an unprivileged actor relative to *other* tenants — they only legitimately possess their own org's `webhook_secret`) can sign an arbitrary payload with their own secret while setting `repository.owner.login`/`organization.login` to their own org (so verification succeeds) but pointing `repository.full_name` or `sha` at a different organization's stack/commit. Via `StatusHandler`, this allows forging a passing CI `status` (`state: success`) on another organization's commit — directly falsifying the signal that `ci.require` gates continuous/manual deploys on, contributing to an unauthorized deploy of another tenant's stack. Via `PushHandler`, it can trigger `sync_github` on another org's stack using attacker-chosen `after` SHA. This is a cross-tenant authorization boundary break using only a credential the attacker legitimately holds for their own org, matching the "organization authenticated vs. repository that is written" binding class.

### Likelihood Explanation
Requires the Shipit operator to run a multi-organization configuration (explicitly documented as a supported mode) and requires the attacker to control at least one onboarded organization's own GitHub App/webhook secret — which is a normal, low-privilege position for any customer of a shared Shipit instance, not a Shipit-internal credential. No repository write access, no `ApiClient` token, no session, and no privileged Shipit account is needed.

### Recommendation
After verifying the HMAC signature, re-derive the organization from the verified payload and enforce that every downstream lookup (`Repository.from_github_repo_name`, `Commit.where(sha:)`, etc.) is scoped to a `Stack`/`Repository` belonging to that same organization. Reject events where `repository.full_name`'s owner segment does not match the `repository_owner`/`organization.login` used to select the verifying secret. `StatusHandler` in particular should scope `Commit` lookups by repository/organization, not by bare `sha` alone.

### Proof of Concept
1. Operator runs Shipit with two configured orgs, `orgA` and `orgB`, each with its own `github.webhook_secret` (per `config/secrets.development.example.yml` multi-org schema).
2. Attacker is an admin of `orgB`'s onboarded GitHub App and legitimately knows `webhook_secret_B`.
3. Attacker crafts and POSTs directly to `/webhooks`:
   - Header `X-Github-Event: status`
   - Header `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_B, raw_body)>`
   - Body: `{"sha": "<commit sha belonging to orgA's stack>", "state": "success", "repository": {"owner": {"login": "orgB"}, "full_name": "orgB/whatever"}}`
4. `verify_signature` resolves `repository_owner == "orgB"`, verifies against `webhook_secret_B` — passes.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, marking `orgA`'s commit as `success` regardless of which org's secret signed the request, satisfying any `ci.require` gate configured on `orgA`'s stack.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
