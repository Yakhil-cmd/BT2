### Title
Webhook signature verification keys off `repository.owner.login` while stack lookup keys off `repository.full_name`, allowing cross-organization stack targeting - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GithubApp`/secret used to authenticate a webhook by digging `repository.owner.login` (or `organization.login`) out of the unauthenticated request body, while `Shipit::Webhooks::Handlers::Handler#stacks` (used by `PushHandler` and other handlers) independently digs `repository.full_name` from the very same body to decide which `Repository`/`Stack` records to act on. These two fields are never checked for consistency with each other.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 
the organization used to look up the `Shipit.github(organization:)` app config (and therefore the `webhook_secret` used in `verify_webhook_signature`) is taken from `repository_owner`: [2](#0-1) 

Meanwhile, the actual entity acted upon by the event handlers is resolved from a *different* JSON key, `repository.full_name`: [3](#0-2) 
and `PushHandler#process` uses that same `stacks` scope to trigger `stack.sync_github(expected_head_sha: params.after)`: [4](#0-3) 

`verify_webhook_signature` itself trivially passes when the selected organization's config has no `webhook_secret` configured: [5](#0-4) 
and the setup documentation explicitly marks `webhook_secret` as optional per GitHub App entry: [6](#0-5) 
This is also reflected in the fixture/test configuration where one organization entry has no secret at all: [7](#0-6) 

**Binding that is broken:** the organization the request *authenticates against* (`repository.owner.login`, used to pick the verifying secret) ≠ the repository that is *written to* (`repository.full_name`, used to find and mutate the `Stack`). Because the HMAC only proves the request came from GitHub for *some* configured org/app (or is unauthenticated entirely when that org's secret is blank), and no code cross-checks that `full_name`'s owner segment matches `owner.login`, a request that is "verified" for org A can carry a `full_name` pointing at a completely different org B's repository/stack.

### Impact Explanation
For any Shipit instance configured with multiple GitHub App entries (a documented, supported configuration — see `docs/setup.md` and the `OrgOne`/`OrgTwo` fixture), if even one configured organization has no `webhook_secret` set (explicitly allowed as "(optional)" by the docs), an attacker can send a completely unsigned request to `/webhooks` with:
- `X-Github-Event: push`
- `repository.owner.login` = the org lacking a secret (bypasses `verify_signature` since `webhook_secret` is blank)
- `repository.full_name` = `"<victim-org>/<victim-repo>"` — any other stack hosted on the same Shipit instance
- `ref` / `after` = attacker-chosen branch/sha

This request passes `verify_signature` and is routed to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name(repository_name)` (using `full_name`, the victim's repo) and calls `stack.sync_github(expected_head_sha: ...)`, enqueuing a `GithubSyncJob` for the *victim's* stack. This is a cross-organization interaction where the attacker never proved control of, or a GitHub-issued signature for, the victim repository, yet triggers state changes (GitHub sync, cache invalidation, `mark_as_inaccessible!`/`mark_as_accessible!` toggling, and potentially races with legitimate deploy automation) tied to a completely unrelated org/repo's stacks. Depending on downstream automation (e.g., merge queues or deploy-on-push configured in `shipit.yml`), this can influence sync/deploy state for a stack the attacker has no access to.

### Likelihood Explanation
This requires: (1) the Shipit instance to be configured with more than one GitHub App/organization entry, and (2) at least one of those configured organizations to have `webhook_secret` left blank — a state the documentation explicitly presents as an acceptable, optional configuration rather than a misconfiguration. Under a single-organization deployment (the more common setup) this is not exploitable, since there is only one `owner.login`/secret pair and it necessarily matches the only stacks hosted. This narrows likelihood to specific documented-but-permissive multi-tenant configurations.

### Recommendation
Bind the authenticated identity to the acted-upon entity: derive the repository owner used to select the webhook secret from the same field (or verify equality against) `repository.full_name`'s owner segment before dispatching to handlers, and reject requests where they diverge. Additionally, treat a blank/missing `webhook_secret` as a hard configuration error (or require it) for any organization entry rather than silently returning `verified = true`, closing the “skip verification entirely” bypass in `GithubApp#verify_webhook_signature`.

### Proof of Concept
Given a Shipit instance with two configured GitHub Apps (`OrgOne` with a secret, `OrgTwo` with `webhook_secret: nil`) and a stack registered for `OrgOne/victim-repo`:

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json
(no X-Hub-Signature needed / any value works)

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/victim-repo"
  }
}
```

`verify_signature` looks up `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [8](#0-7) . The request then reaches `PushHandler`, which resolves stacks for `"OrgOne/victim-repo"` [3](#0-2)  and enqueues `stack.sync_github(expected_head_sha: "deadbeef...")` for that victim stack, despite the request never being cryptographically tied to `OrgOne`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
