### Title
Webhook signature verification uses an attacker-controlled organization field that is decoupled from the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) pulled straight out of the untrusted request body, while every event handler resolves the *actual* repository/stack it mutates from a **different** field in the same body: `repository.full_name`. Because these two fields are never checked for consistency, and because `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the selected organization has no `webhook_secret` configured, an attacker can pick an unprotected (or unknown-to-them-secret) organization name for `repository.owner.login` while setting `repository.full_name` to a real, protected repository owned by a different, secured organization. This breaks the same class of "authorization scope A but execution scope B" binding that the Shipit Router analog describes: the organization whose secret authenticates the request ≠ the repository whose state the handler writes.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`repository_owner` is fully attacker-controlled JSON body content, and it selects which organization's `GitHubApp` (and therefore which `webhook_secret`) is used to verify the signature: [4](#0-3) 

`GitHubApp#verify_webhook_signature` trivially passes verification when the selected organization has no configured secret: [5](#0-4) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Meanwhile, the actual repository that every handler operates on is derived from a *different* JSON field, `repository.full_name`, via `Handler#repository_name` / `Repository.from_github_repo_name`: [6](#0-5) [7](#0-6) 

For example `PushHandler` looks up stacks solely from `repository_name` (i.e. `repository.full_name`) and pushes a `sync_github` job for that stack, never re-checking `repository.owner.login`: [8](#0-7) 

Webhook secrets are documented as **optional per organization** (`docs/setup.md` shows `webhook_secret:` commented as `# nil` for multiple orgs), so a multi-org Shipit deployment where at least one configured organization omits `webhook_secret` is a realistic, in-scope configuration: [9](#0-8) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated by verify_signature (repository.owner.login)` ≠ `repository actually written by the handler (repository.full_name)`.

### Impact Explanation
An unauthenticated network attacker who knows (a) the name of any organization onboarded to the Shipit instance that has no `webhook_secret` configured (or whose secret they can otherwise satisfy), and (b) the `owner/name` of a *different*, secured/protected repository tracked by Shipit, can forge arbitrary GitHub webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) against that protected repository. Depending on handler, this can:
- Trigger `GithubSyncJob` / `stack.sync_github` for an arbitrary tracked stack via forged `push` events, influencing deploy state (`PushHandler`).
- Forge commit `status` transitions, `check_suite` results, or PR `opened`/`closed`/`labeled` events that drive review-stack provisioning, archiving, or deploy gating logic — i.e., unauthorized manipulation of stack/deploy state without ever presenting a valid signature for the targeted repository's organization.
- Fabricate `membership` events that add/remove `Membership`/`Team` records (authorization-adjacent state).

This maps to the "unauthorized deploy/rollback" and "escalation into authorization state" impact classes called out in scope, since it lets an attacker who controls no valid webhook secret still drive state transitions gated by webhook authenticity for a repository protected by a *different* organization's secret.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment, (2) at least one onboarded organization with no `webhook_secret` set (explicitly supported/documented as optional), and (3) knowledge of a target repository's `owner/name` under a different, secured organization (public information for public repos). No credentials, tokens, or GitHub App keys are needed — only knowledge of public repository/organization names and the ability to POST to the public `/webhooks` endpoint. This is a plausible configuration and requires no privileged access, matching the unprivileged-attacker requirement.

### Recommendation
Do not use attacker-supplied payload fields to select the verification secret independently from the field used to resolve the acted-upon repository. Either:
1. Verify the webhook signature using the app-level/default GitHub App secret only (not one chosen dynamically from `repository.owner.login`/`organization.login`), or
2. After selecting the organization for verification, cross-check that `repository.full_name`'s owner matches the verified `repository_owner`/`organization.login` before dispatching to handlers, rejecting mismatches with `422`.
3. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is unset in a multi-org configuration — require an explicit secret per organization when GitHub App verification is multi-tenant, or refuse ambiguous/absent-secret organizations.

### Proof of Concept
Preconditions: Shipit configured with orgs `unsecured-org` (no `webhook_secret`) and `secured-org` (has `webhook_secret`), both with repositories tracked as Shipit stacks (e.g., `secured-org/critical-repo`).

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json
(no valid X-Hub-Signature needed)

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "secured-org/critical-repo",
    "owner": { "login": "unsecured-org" }
  }
}
```

Trace:
1. `WebhooksController#repository_owner` returns `"unsecured-org"` from `params.dig('repository','owner','login')`. [3](#0-2) 
2. `Shipit.github(organization: "unsecured-org")` resolves that org's `GitHubApp`, whose `webhook_secret` is nil. [4](#0-3) 
3. `verify_webhook_signature` returns `true` unconditionally (`return true unless webhook_secret`). [5](#0-4) 
4. `WebhooksController#create` dispatches the payload to `PushHandler`, which resolves the target stack via `repository.full_name` = `"secured-org/critical-repo"`, entirely bypassing `secured-org`'s webhook secret. [10](#0-9) [6](#0-5)

Full verification would require exercising `WebhooksController` in a test/dev environment with two configured organizations, one lacking `webhook_secret`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
