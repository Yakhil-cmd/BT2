### Title
Pull request label names (uppercased) become unfiltered environment variables for `ReviewStack` command execution, permitting `IFS`/`PATH` injection - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges pull-request label names (uppercased, taken verbatim from the GitHub webhook) into the process environment with no key allowlist, and this merged hash flows unfiltered into `Command#start` → `PTY.spawn`. An unprivileged fork-PR author who can only add a label to their own PR can therefore inject arbitrary environment variable *names* — including `IFS` or `PATH` — into every shell command Shipit runs for that review stack's deploys, dependency installs, and tasks.

### Finding Description
The broken binding: the invariant should be `keys(stack.env) ⊆ SHIPIT_KNOWN_ENV_KEYS` for any review stack, i.e. no fork-controllable string should ever become an *environment variable key*. In reality: `keys(stack.env) ⊇ {label.upcase for label in pull_request.labels}` with `label` fully attacker chosen.

Code path:
1. `LabelCapturingHandler#capture_labels` persists label names straight from the webhook payload with no allowlist or character restriction: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`). The `params` schema only requires `labels[].name` to be a `String` — any value, including `"ifs"` or `"IFS"`, is accepted.
2. `ReviewStack#env` turns every stored label into an environment hash entry with no key filtering: [1](#0-0) 
This is exactly what `test/models/shipit/review_stack_test.rb:59-65` demonstrates for benign labels ("wip"/"bug" → `WIP`/`BUG`); nothing stops a label literally named `ifs`.
3. `TaskCommands#env` / `DeployCommands#env` merge `@stack.env` into the full command environment with no filtering of keys: [2](#0-1) 
4. `Command#initialize` only stringifies *values*, never restricts *keys*: [3](#0-2) 
5. `Command#unbundled_env` layers the attacker-controlled hash on top of the process's base env, and `start` passes it straight to `PTY.spawn`: [4](#0-3) 

Why the `deploy.variables` allowlist doesn't help: `deploy_variables` / `filter_deploy_envs` (`app/models/shipit/deploy_spec.rb:120-126,174-176`) and `EnvironmentVariables#permit` (`lib/shipit/environment_variables.rb:13-18`) are only applied to the *user-submitted deploy form* env override (see `Deploy` delegating `filter_deploy_envs` to `stack`, used from the deploys controller), not to the environment that `TaskCommands#env`/`DeployCommands#env` build for `Command.new`. The label-derived keys never pass through this allowlist, so `IFS`, `PATH`, `BUNDLE_GEMFILE`, etc. are all injectable via a label name.

Attacker request: open a fork PR against a repo configured with `provisioning_behavior: allow_all` and `review_stacks_enabled: true`, then add a label literally named `ifs` (or `IFS`, `path`, etc.) to that PR. On the next `pull_request` webhook (`opened`/`labeled`/`reopened`), `LabelCapturingHandler` persists the label, and the next deploy/dependency/task command executed for that review stack inherits `IFS=true` (or any attacker value if GitHub allowed arbitrary label text, which it does) in its environment before invoking a shell command line, altering shell word-splitting behavior for any unquoted variable expansion in the step's command string.

### Impact Explanation
Critical — this reaches `Command#start`/`PTY.spawn` (the RCE class explicitly in scope). The attacker controls an environment variable key/value pair injected into every shell invocation for their own review stack's deploy, dependency, rollback, and task commands. Combined with any unquoted shell-variable expansion in the configured `shipit.yml` step strings (e.g. `cap $ENVIRONMENT deploy`), a manipulated `IFS` can cause argument re-splitting, and other injectable keys (e.g. `PATH`, `BUNDLE_GEMFILE`, `RUBYOPT`) directly enable arbitrary code execution on the deploy host. This is scoped to the attacker's own review stack/repository (assuming per-repo config), but it is repeatable on any repo the attacker can open a PR against with `allow_all` (or `allow_with_label`/label present) provisioning behavior.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with `provisioning_behavior: allow_all` (as specified in the question) so an unprivileged fork PR gets a provisioned review stack automatically. Attacker cost is trivial: opening a PR and adding a label are both actions available to any GitHub user who can open a pull request against the repo (or on their own fork if review stacks fire on fork PRs), no Shipit credentials needed. It's fully repeatable and requires no race conditions.

### Recommendation
In `ReviewStack#env`, prefix or namespace label-derived keys (e.g. `"LABEL_#{label.upcase}"`) and/or apply a strict allowlist regex to label-derived keys, explicitly excluding reserved/dangerous names (`IFS`, `PATH`, `BUNDLE_*`, `LD_*`, `RUBYOPT`, etc.). Additionally, `Command#unbundled_env`/`Command#initialize` should reject or strip environment keys from stack-controlled sources that collide with a hardcoded denylist of shell/interpreter-influencing variables before merging into the process environment passed to `PTY.spawn`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (extend)
test "#env does not allow a pull request label to inject IFS" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["ifs"]

  env = stack.env

  assert_nil env["IFS"], "expected IFS to not be settable via a PR label"
end
```
Expected (current, vulnerable) result: `env["IFS"]` equals `"true"`, proving the fork-controlled label reaches the merged environment with no allowlist, matching the equality violation `keys(stack.env) ⊇ {"IFS"}` derived purely from `pull_request.labels`. A second test can build a `DeployCommands`/`TaskCommands` instance and assert `command.env["IFS"] == "true"` to show the same value reaching `Command#env` right before `PTY.spawn`.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
