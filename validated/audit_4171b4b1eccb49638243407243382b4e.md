### Title
API-scoped ApiClient's stack restriction is bypassed by the CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces a binding between an `ApiClient` token and the set of stacks it is authorised to touch: when a token is scoped to a single stack (`ApiClient#stack_id` present), every controller that inherits from `BaseController` is expected to resolve `stack`/`stacks` through that scope. `Shipit::Api::CCMenuController`, however, overrides `stack` to load the record directly from the URL parameter, ignoring the scoping entirely. This is structurally the same class of bug as the reported `setFlowLimit` issue: a state/authorization invariant that is supposed to be enforced everywhere is silently skipped in one code path, breaking the equality "stack(s) the token authorises == stack(s) the endpoint touches."

### Finding Description
`Shipit::Api::BaseController` defines the intended scoping: [1](#0-0) 

Any endpoint built on top of `stacks`/`stack` restricts a stack-scoped `ApiClient` (`current_api_client.stack_id?`) to `Stack.where(id: current_api_client.stack_id)`. This is confirmed by the general Stacks API, which is explicitly tested to enforce the restriction: `here_come_the_walrus` is fixtured as an `ApiClient` scoped to the `shipit` stack, and `#index` for that client only returns that one stack, per the test "an api client scoped to a stack will only see that one stack" in `test/controllers/api/stacks_controller_test.rb`.

`CCMenuController`, however, defines its own `stack` method that bypasses this scope entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly instead of going through `stacks.from_param!(...)`, so `current_api_client.stack_id` is never consulted when resolving which stack's data to render. The permission check that does run, `require_permission :read, :stack`, only validates the coarse-grained `read:stack` permission name via `ApiClient#check_permissions!`: [3](#0-2) 

It does not check `stack_id` at all — that check only lives inside `BaseController#stacks`/`#stack`, which `CCMenuController` overrides and never calls.

Equality broken: `current_api_client.stack_id` (the stack the token authorises) ≠ `params[:stack_id]` resolved by `CCMenuController#stack` (the stack the endpoint actually touches). Any token holding `read:stack`, even one deliberately scoped to a single stack, can pass an arbitrary `stack_id` to the CCMenu endpoint and receive build/deploy state for any other stack in the installation.

### Impact Explanation
This is an authorization bypass: a caller who legitimately holds a narrowly-scoped `ApiClient` token (e.g., the `CCMenu Client` token generated by `Shipit::CCMenuUrlController`, or any admin-issued token scoped to one stack) can use that token to read the name, activity, last build status/label/time, and web URL of *any* stack managed by the Shipit instance — not just the one it was issued for. This matches the "escalation into authorization... unauthenticated read of stack state" category, since the caller reads state for stacks outside the boundary the token was explicitly restricted to.

### Likelihood Explanation
Likelihood is moderate-to-high wherever operators rely on `ApiClient#stack_id` scoping as an isolation boundary between stacks/teams (e.g., issuing a per-project CCMenu URL/token to external CI dashboards, as `CCMenuUrlController` is designed to do). Exploitation requires only possession of any valid `read:stack` token and knowledge/guessing of another stack's `to_param` — no additional privilege, signature, or secret is needed.

### Recommendation
Have `Shipit::Api::CCMenuController#stack` resolve through the inherited `stacks` scope (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that a stack-scoped token cannot escape its authorised stack via this endpoint.

### Proof of Concept
1. Admin creates a stack-scoped token, e.g. fixture `here_come_the_walrus`, scoped to stack `shipit` with permission `read:stack` only. [4](#0-3) 
2. Attacker in possession of this token calls `GET /api/1/stacks/:other_stack_id/ccmenu.xml?token=<token>`, where `:other_stack_id` refers to a *different* stack than `shipit`.
3. `CCMenuController#authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])`. [5](#0-4) 
4. `require_permission :read, :stack` passes because the client has `read:stack` in its `permissions` list, regardless of which stack is requested.
5. `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` directly (no scope check), returning the *other* stack's record even though `current_api_client.stack_id` points to `shipit`.
6. `#show` renders that other stack's build/deploy status XML, leaking data outside the token's authorised scope.
