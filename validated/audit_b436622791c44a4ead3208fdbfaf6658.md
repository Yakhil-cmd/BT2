### Title
Session fixation on GitHub OAuth callback binds the attacker's pre-authentication session to the victim's authenticated identity - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`Shipit::GithubAuthenticationController#callback` writes `session[:user_id]` and `session[:authenticated]` directly into the existing Rack session without ever regenerating the session identifier, unlike `#logout` which explicitly calls `reset_session`. [1](#0-0) 

### Finding Description
This is the same class of bug as the Multipool `fee0`/`fee1` miscalculation: a value that is supposed to be re-derived/re-bound at a trust boundary is instead carried over from a pre-boundary state, silently breaking an equality the protocol relies on.

In Multipool, `fee0`/`fee1` should equal "fees actually collected in this action", but instead retain a component (`tokensOwed0Before`) from *before* the position was updated, letting an attacker pre-load `tokensOwed*Before` to make the post-action delta collapse to near zero.

In Shipit, the equality that must hold is: **`session_id` bound to a `User` == a session ID that was (re)issued at authentication time**. `#callback` never calls `reset_session`/`session.regenerate_id` before writing the authenticated `user_id`/`authenticated` flags into the session hash: [2](#0-1) 

Because Rails does not automatically rotate the session cookie's underlying ID when values are merely assigned into `session[]`, an already-existing (unauthenticated) session established before the OAuth handshake remains valid and simply gets "promoted" to authenticated status in place. This is the exact "pre-collect state leaking into the post-collect authorization decision" pattern from the analog report: the session state that existed *before* GitHub identity verification is exactly the same object that becomes trusted *after* verification, when it should have been discarded/renewed.

Compare with `#logout`, which correctly resets the session: [3](#0-2) 

This asymmetry (regenerate on logout, but not on login) is the concrete root cause.

### Impact Explanation
This directly matches the rules' High-impact category "session fixation / forced OAuth completion." If an attacker can get a victim's browser to use a session ID that the attacker already knows (e.g., by planting a cookie via a shared/parent domain, a response-splitting/cookie-tossing vector, or any mechanism that sets the Shipit session cookie in the victim's browser prior to login), then once the victim completes the legitimate GitHub OAuth flow, `session[:user_id]` for the victim is written into that same, attacker-known session ID. The attacker, replaying that session ID, becomes fully authenticated as the victim inside Shipit — gaining `Shipit.github_teams`-authorized access, ability to trigger deploys/rollbacks, view task output/streams, and act with the victim's `current_user` identity throughout the app (including creating `ApiClient`s attributed to the victim, per `ApiClientsController#create`). [4](#0-3) 

### Likelihood Explanation
Exploitation depends on the attacker being able to fix a session ID in the victim's browser before the victim authenticates — a standard prerequisite for session-fixation attacks (e.g., cookie scope issues, subdomain trust, or any cookie-setting primitive), not on possessing any Shipit session, API token, webhook secret, or GitHub credentials. No repository write access or privileged account is required. This satisfies the rule that valid analogs must not depend on already having a Shipit session/token; the flaw itself is what would let an attacker obtain one belonging to someone else.

### Recommendation
Call `reset_session` (and re-set `omniauth.origin`-derived `return_url` before resetting, since `reset_session` clears `session`) immediately before establishing the new authenticated session in `GithubAuthenticationController#callback`, mirroring the pattern already used in `#logout`:
```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?

  reset_session
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true

  redirect_to(return_url)
end
```
Rails' `reset_session` regenerates the underlying session ID, ensuring any pre-authentication session (potentially attacker-known) cannot be silently promoted to an authenticated one.

### Proof of Concept
1. Attacker obtains a valid (unauthenticated) Shipit session cookie and, via any cookie-fixation vector affecting the Shipit host/domain, causes the victim's browser to use that same session cookie.
2. Victim visits Shipit, is redirected to `/github/auth/github`, and completes the GitHub OAuth flow.
3. `GithubAuthenticationController#callback` fires: `sign_in_github(auth)` resolves the victim's GitHub identity and `session[:user_id]` / `session[:authenticated]` are written into the *same, unrotated* session ID that the attacker previously fixed. [2](#0-1) 
4. Attacker replays the fixed session cookie and is now treated as the authenticated victim by `Authentication#current_user`/`force_github_authentication`, gaining the victim's `Shipit.github_teams` authorization and ability to perform deploys, rollbacks, and other privileged actions. [5](#0-4) 

I could not find any middleware or Rack session-store configuration in the in-scope `app/**`/`lib/shipit/**`/`config/routes.rb` set that performs session-ID rotation on login independent of the controller, so the absence of `reset_session` in `callback` appears to be the sole safeguard missing at this boundary. Whether the deployed Rack session store additionally mitigates fixation (e.g., via `Rack::Session::Cookie` config or an outer host-app middleware) is outside the indexed engine code and could not be confirmed from this repository alone.
