### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` lookup in StatusHandler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha` across the entire database, with no scoping to the repository/organization whose `webhook_secret` verified the inbound request. Any org/app legitimately registered on the Shipit instance can therefore forge a CI status for a commit belonging to a completely different org's stack, as long as the attacker knows that commit's SHA (which is ordinary, non-secret git metadata).

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: `organization_that_verified_signature(webhook_secret) == organization_owning(Commit.where(sha: params.sha).stack)`.

`WebhooksController#verify_signature` selects the GitHub App purely from the payload's `repository.owner.login` field and validates the HMAC against that org's `webhook_secret`: [1](#0-0) [2](#0-1) 

Once verified, the full parsed body is dispatched unmodified to every registered handler for the event, with no re-binding of repository identity: [3](#0-2) 

`StatusHandler#process` then resolves the target purely by `sha`, without any filter on `repository`, `stack_id`, or organization: [4](#0-3) 

This calls `Commit#create_status_from_github!`, which appends a status and can trigger merge scheduling and deployability changes on the victim's stack: [5](#0-4) [6](#0-5) 

**Exploit flow**: Attacker legitimately owns/controls a repository under org B (app B, secret known only to GitHub/app B — signature verification for org B's own webhook succeeds normally since GitHub signs the payload with org B's secret when app B is installed on attacker's repo). Attacker triggers (or fabricates via their own CI integration, since they control the repo) a `status` event on their own repo naming `sha` equal to a real, existing commit SHA under org A's stack — a value that is not secret (visible on GitHub's public commit history, PR pages, or Shipit's own commit views for that stack). GitHub (or the attacker directly, since nothing besides HMAC-over-body is checked and the attacker fully controls the body content up to needing a valid signature from their own app) delivers/POSTs this to `/webhooks`. `verify_signature` succeeds because it only checks org B's secret against org B's payload — it never checks that the `sha` inside the payload belongs to a repository under org B. `StatusHandler#process` then finds and mutates org A's `Commit` row.

Existing guards do not catch this: `verify_signature` binds signature validity to the *organization named in the payload's repository field*, not to the *stack/commit* being mutated; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema in `StatusHandler.params` only validates types of `sha`/`state`/etc., not ownership; there is no `Repository`/`stack_id` check anywhere in the `status` handling path.

### Impact Explanation
A verified webhook payload for one repository/organization can create an arbitrary CI status (`success`, `failure`, `error`, `pending`) attached to a `Commit` belonging to a different organization's stack. Since `add_status` calls `stack.schedule_merges` on success/pending transitions and can flip `Commit#deployable?`, this can influence automatic merge-request processing and deploy gating for the victim stack — a payload for one repository mutating another's commit/stack state. This matches the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). Blast radius spans across tenants of the same multi-tenant Shipit install, and the exploit is repeatable against any known SHA in the installation.

### Likelihood Explanation
Preconditions: multi-tenant Shipit instance with ≥2 GitHub Apps/orgs configured (each with distinct `webhook_secret`), attacker legitimately controls a repository under one of those orgs (or can trigger a `status` event from it), and knows the target SHA of a commit tracked under a different org's stack (ordinary, frequently public git metadata, or discoverable via Shipit's own UI/API for public stacks). Attacker cost is low: no secrets, tokens, or privileged roles are required — only the ability to cause a `status` webhook to fire from their own already-registered repo/app, which is normal GitHub Apps behavior for repo owners/CI integrators. This is repeatable against any SHA the attacker can learn.

### Recommendation
Bind the webhook-verified organization/repository to the object being mutated. In `StatusHandler#process`, scope the `Commit` lookup to commits whose `stack.repository` (or equivalent org/repo identifier) matches `params.dig('repository', 'full_name')`/`repository.owner.login` from the verified payload, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, repository: { full_name: params.repository.full_name })`, rejecting/ignoring matches outside that repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status event verified for org B does not mutate a commit belonging to org A's stack" do
  org_a_stack = shipit_stacks(:shipit) # repository owned by org A ("shopify")
  org_a_commit = shipit_commits(:first)
  colliding_sha = org_a_commit.sha

  # Simulate org B's app registration with a distinct webhook_secret
  org_b_repo_payload = { "sha" => colliding_sha, "state" => "success", "context" => "ci/attacker",
                          "repository" => { "full_name" => "org-b/attacker-repo", "owner" => { "login" => "org-b" } } }

  assert_no_difference -> { org_a_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new.call(org_b_repo_payload)
  end
end
```
This asserts that a verified body naming org A's commit SHA, but carrying org B's `repository` identity, must NOT create a status on org A's `Commit` — currently it does, because `StatusHandler#process` at [4](#0-3)  ignores the `repository` field entirely.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
