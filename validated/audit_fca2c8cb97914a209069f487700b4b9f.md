### Title
Webhook HMAC verification is keyed off `repository.owner.login`/`organization.login` while handlers act on the unchecked `repository.full_name`/`sha` fields, allowing cross-organization status/push forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC against using `repository_owner`, which is read straight out of the attacker-suppliable JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), then compares `X-Hub-Signature` against `Shipit.github(organization: repository_owner).verify_webhook_signature`. [1](#0-0) [2](#0-1) 

This only proves the request body was signed with the secret belonging to whichever organization name the attacker put in that one field. It does **not** bind that verified organization to the repository the payload actually mutates. The generic `Handler` base class resolves the target `Stack`s from a completely separate, unvalidated field, `repository.full_name`: [3](#0-2) 

`StatusHandler` is worse: it doesn't even consult `repository` at all — it matches purely on commit `sha` across the whole database: [4](#0-3) 

This is structurally the same class of bug as the Poseidon2 report: the constraint (`verify_signature`) only checks one narrow condition (signature valid for *some* org name embedded in the payload) but the actual state-changing action (`stacks`/`Commit.where(sha:)`) is driven by a different, unconstrained value from the same untrusted payload. The equality that should hold — `organization authenticated by the HMAC == organization owning the repository/commit being written` — is never enforced.

### Impact Explanation
Any tenant/organization that is legitimately configured in this Shipit instance (i.e., knows its own valid `webhook_secret`, which any admin of that GitHub org setup can see/rotate in GitHub's webhook settings) can forge an HTTP POST directly to the public `/webhooks` endpoint with:
- `repository.owner.login` (or `organization.login`) = their own org → signature check passes using their own real secret.
- `sha` (for a `status` event) or `repository.full_name` (for a `push`/other event) = a value belonging to a completely different organization/stack hosted on the same Shipit instance.

For the `status` event this lets an attacker inject a fabricated green CI status for an arbitrary commit SHA belonging to a victim stack via `Commit#create_status_from_github!`, which can satisfy `ci.require` gating and enable an unauthorized deploy of that commit on a repository the attacker does not control — this reaches the "Critical - unauthorized deploy" bar. For `push` it can force `Stack#sync_github` to run against a victim stack outside the attacker's organization boundary.

### Likelihood Explanation
Requires the attacker to control (or be a legitimate but hostile tenant of) at least one organization/webhook_secret configured in the shared Shipit deployment — no privileged Shipit session, `ApiClient` token, or GitHub App private key is needed, only knowledge of one org's own webhook secret and network access to the public webhook endpoint. In any multi-tenant Shipit deployment (multiple GitHub organizations sharing one Shipit instance) this is directly and repeatedly exploitable.

### Recommendation
After signature verification, enforce that `repository.owner.login`/`organization.login` used to select the verifying secret matches the `owner` derived from `repository.full_name` (and, for `status_handler`, that the matched `Commit`'s stack repository owner equals the verified organization) before any handler acts on the payload — analogous to adding the missing `assert_zero` constraint in the Poseidon2 fix, binding the two fields together instead of trusting them independently.

### Proof of Concept
1. Attacker administers `org-attacker` in GitHub, which is configured in this Shipit instance with `webhook_secret = S`.
2. Attacker crafts JSON: `{"repository": {"owner": {"login": "org-attacker"}, "full_name":"org-attacker/foo"}, "sha": "<victim-stack-commit-sha>", "state": "success", "context": "ci/required-check"}`.
3. Attacker computes `sha1=HMAC-SHA1(S, raw_body)` and sends `POST /webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=...`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "org-attacker")`, verifies successfully against `S`. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, writing a forged successful status onto the victim organization's commit, without ever checking that the commit belongs to `org-attacker`. [4](#0-3)
