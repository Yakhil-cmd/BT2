### Title
Caller-supplied route bytes execute arbitrary payload-named contract code inside the caller's signed transaction, letting a rogue "pool" drain the signer's wallet — ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The Dataease advisory (CWE-94: a crafted, user-supplied plugin blob is executed as code) maps onto XOXNO Lending's swap strategy surface: the `swap: StrategySwap` bytes accepted by `multiply`, `swap_collateral`, `swap_debt`, and `repay_debt_with_collateral` name the pool and token contracts the router invokes. Neither the controller nor the router allowlists those addresses, so an attacker-crafted route puts arbitrary contract code on the call stack beneath the victim's authorization. That code can issue `token.transfer(victim, attacker, x)` for any token the victim holds; an honest simulation records it as a child of the victim's `require_auth` entry, and it executes if the victim signs the tree.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` forwards the caller's opaque `swap` bytes to `router.execute_strategy(controller, amount_in, swap)` after authorizing exactly one input transfer. The controller checks only that the router didn't overspend (`RouterOverspend`) and that output was positive (`NoSwapOutput`); it never inspects which contracts the route names. The threat model confirms the router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" and that "the loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" (`docs/explanation/threat-model.md:154-165`).

The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates the full chain: `RogueHopPool::swap` (lines 62-71) calls `token.transfer(victim_wallet → attacker, WALLET_BALANCE)` when invoked as a route hop; `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` (lines 195-227) shows recording-mode simulation attaching that theft as a child of Alice's `swap_collateral` auth entry, and after signing, Alice's unrelated wallet token balance is `0` while the attacker holds `WALLET_BALANCE` — even though the swap itself paid a fair `min_out` and the position passed all risk gates. `source_account_credentials_bind_the_rogue_transfer_to_the_tree_without_an_entry_signature` (lines 322-368) confirms the transfer is refused only if the tree lacks the child — i.e., the sole defense is the signer detecting the extra child.

### Impact Explanation
Theft of user funds. A victim who signs a maliciously crafted `routeXdr` (e.g., received from a phishing quote or compromised route source) for `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply` loses every token in their wallet that the rogue hop chooses to pull — far beyond the routed `amount_in`. The loss is unbounded by `amounts[min_out]`, `RouterOverspend`, or the final health-factor check, all of which pass.

### Likelihood Explanation
Reachable by any unprivileged attacker who can get a crafted route in front of a victim to sign; the only victim action is signing a transaction that simulation honestly renders (the stolen transfer appears as a child auth entry). The protocol's own docs acknowledge the exposure and place the entire mitigation burden on the client decoding its auth tree, which standard wallets do not surface intelligibly.

### Recommendation
Enforce an allowlist of venue pool contracts on-chain (or restrict hop pool addresses to governance-registered venues) in the route execution path, so payload bytes cannot name arbitrary contracts. Alternatively, reject routes whose hop pools are not registered protocol assets/venues, and surface child auth entries in signing UX as an interim mitigation.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: a `RogueHopPool` contract named by the route's hop pool field executes `token.transfer(alice, attacker, WALLET_BALANCE)` during `swap_collateral`; the test asserts `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, and the stolen transfer recorded as a child of Alice's signed `swap_collateral` invocation.
