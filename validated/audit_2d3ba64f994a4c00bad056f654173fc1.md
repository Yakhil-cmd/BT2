### Title
`burn_at_relay` irreversibly destroys local balance before relay-side burn is confirmed, causing cross-chain accounting mismatch on `send_xcm`/check-out failure - ([File: system-parachains/coretime/coretime-kusama/src/coretime.rs])

### Summary
`burn_at_relay` calls `AssetTransactor::withdraw_asset` (which immediately reduces the local `Balances::total_issuance` / removes funds from `CoretimeBurnAccount`) *before* it has any confirmation that the corresponding `ReceiveTeleportedAsset`/`BurnAsset` message will actually be executed on the relay chain. If `AssetTransactor::can_check_out` or `PolkadotXcm::send_xcm` subsequently return `Err`, the function returns early via `?` with no compensating re-deposit of the withdrawn value, leaving the funds permanently removed from local accounting with no matching relay-side burn.

### Finding Description
The relevant sequence is: [1](#0-0) 

1. `AssetTransactor::withdraw_asset(&asset, &stash_location, None)?` — this actually removes `value` from `stash`'s balance and reduces the chain's local `Balances::total_issuance` (standard `FungibleAdapter` semantics; the `FungibleTransactor` on this chain uses `()` as the checking type, so there is no reversible "checked" bookkeeping for this asset) [2](#0-1) .
2. `AssetTransactor::can_check_out(&dest, &asset, &dummy_xcm_context)?` — the code itself flags this with a `TODO` referencing `https://github.com/polkadot-fellows/runtimes/issues/404`, i.e. the maintainers are already aware this check is incomplete/insufficient.
3. `PolkadotXcm::send_xcm(...)?` — sends `UnpaidExecution` + `ReceiveTeleportedAsset` + `BurnAsset` to the relay. If the outbound message cannot be enqueued (e.g., XCMP/UMP outbound queue full, message-size/weight limits exceeded), `send_xcm` returns `Err` and the function returns immediately.
4. Only on the success path does `AssetTransactor::check_out(...)` run, and only then is the operation considered complete.

There is no code path that re-deposits the withdrawn `value` back into `stash` (or anywhere) when steps 2 or 3 fail. Since step 1 already performed a real, non-reversible reduction of local issuance/balance, any failure afterward leaves the Coretime chain's local ledger permanently short by `value`, while the relay chain never executes the `BurnAsset` instruction that was supposed to be the "real" destruction event. The two chains' combined asset accounting becomes inconsistent: value disappears from the parachain's books without any matching event on the relay chain.

This function is only reachable through the automatic `on_new_timeslice` hook, which is deterministic based on `pallet_broker::Timeslice` and a fixed `BURN_PERIOD` (`RELAY_DAYS / TIMESLICE_PERIOD`), so the exact timeslice at which `burn_at_relay` will fire is publicly predictable in advance [3](#0-2) . `CoretimeBurnAccount` is funded automatically by `BurnCoretimeRevenue::on_nonzero_unbalanced` from ordinary broker/on-demand sale revenue, requiring no special privilege from an attacker [4](#0-3) . No origin, filter, or barrier logic exists here that would prevent this sequence — the code path is purely internal (not extrinsic-gated), and there is no compensating rollback for the local withdrawal.

### Impact Explanation
If the relay-bound XCM fails to send (for any reason, including queue congestion at the moment `on_new_timeslice` executes), the withdrawn `value` is permanently removed from the Coretime chain's local balance/issuance accounting with no corresponding burn recorded on the relay chain. This produces a persistent, unrecoverable state inconsistency between the parachain's and relay chain's asset ledgers — value is destroyed from the parachain's perspective without any provable, auditable burn event actually occurring on the relay side.

### Likelihood Explanation
The funding precondition (broker sale revenue accumulating in `CoretimeBurnAccount`) happens naturally and needs no attacker action. The timing of `on_new_timeslice`'s burn attempt is fully predictable from public constants (`BURN_PERIOD`), removing timing uncertainty for an attacker who wants to align queue congestion with the burn attempt. The harder part is reliably forcing `PolkadotXcm::send_xcm` to return `Err` specifically at that block via outbound HRMP/UMP saturation — this depends on the current bounded capacity of the outbound message queue implementation and is not unconditionally guaranteed, but it is not an "impossible" external-chain assumption either, since outbound UMP/XCMP queues do have finite capacity that can be pressured with valid, cheap XCM traffic. The underlying bug (no rollback on withdraw-then-fail) is unconditionally present regardless of how `send_xcm`/`can_check_out` come to fail, and is explicitly acknowledged as an open gap by the maintainers via the `TODO` referencing issue #404.

### Recommendation
Do not perform the irreversible local `withdraw_asset` until success of the full relay round-trip is reasonably assured, or make the operation atomic/reversible: e.g., hold the withdrawn `Credit`/`AssetsInHolding` and only resolve/burn it after `send_xcm` succeeds, and on any `Err` path re-deposit the withdrawn value back into `CoretimeBurnAccount` (or otherwise defensively handle the failure so no value is lost) before returning the error from `burn_at_relay`.

### Proof of Concept
An xcm-emulator / integration test plan:
1. Fund `CoretimeBurnAccount` with a known `value` via the normal broker revenue flow, and record `Balances::total_issuance()` on Coretime before the burn attempt.
2. Force `PolkadotXcm::send_xcm` (or the underlying `XcmpQueue`/UMP router) to return `Err` by saturating the outbound queue capacity with attacker-submitted low-fee XCM messages in immediately preceding blocks, or by mocking the router to return `Err` for this specific call.
3. Trigger `on_new_timeslice` at the exact `BURN_PERIOD`-aligned timeslice.
4. Assert: `Balances::total_issuance()` on Coretime decreased by `value` (local burn happened) AND `Balances::total_issuance()` on the relay chain did not decrease correspondingly / no `BurnAsset` execution/event is observed on the relay, confirming a permanent, unaccounted-for asset accounting mismatch across chains.

fn burn_at_relay(stash: &AccountId, value: Balance) -> Result<(), XcmError> {
	let dest = Location::parent();
	let stash_location =
		Junction::AccountId32 { network: None, id: stash.clone().into() }.into_location();
	let asset = Asset { id: AssetId(Location::parent()), fun: Fungible(value) };
	let dummy_xcm_context = XcmContext { origin: None, message_id: [0; 32], topic: None };

	let withdrawn = AssetTransactor::withdraw_asset(&asset, &stash_location, None)?;

	// TODO https://github.com/polkadot-fellows/runtimes/issues/404
	AssetTransactor::can_check_out(&dest, &asset, &dummy_xcm_context)?;

	let parent_assets = withdrawn.reanchored_assets(&dest, &Here);

	PolkadotXcm::send_xcm(
		Here,
		Location::parent(),
		Xcm(vec![
			Instruction::UnpaidExecution {
				weight_limit: WeightLimit::Unlimited,
				check_origin: None,
			},
			ReceiveTeleportedAsset(parent_assets.clone()),
			BurnAsset(parent_assets),
		]),
	)?;

	AssetTransactor::check_out(&dest, &asset, &dummy_xcm_context);

	Ok(())
}

	fn on_new_timeslice(t: pallet_broker::Timeslice) {
		// Burn roughly once per day. TIMESLICE_PERIOD tested to be != 0.
		const BURN_PERIOD: pallet_broker::Timeslice =
			RELAY_DAYS.saturating_div(coretime::TIMESLICE_PERIOD);
		// If checked_rem returns `None`, `TIMESLICE_PERIOD` is misconfigured for some reason. We
		// have bigger issues with the chain, but we still want to burn.
		if t.checked_rem(BURN_PERIOD).is_some_and(|r| r != 0) {
			return;
		}

		let stash = CoretimeBurnAccount::get();
		let value =
			Balances::reducible_balance(&stash, Preservation::Expendable, Fortitude::Polite);

		if value > 0 {
			log::debug!(target: "runtime::coretime", "Going to burn {value} stashed tokens at RC");
			match burn_at_relay(&stash, value) {
				Ok(()) => {
					log::debug!(target: "runtime::coretime", "Succesfully burnt {value} tokens");
				},
				Err(err) => {
					log::error!(target: "runtime::coretime", "burn_at_relay failed: {err:?}");
				},
			}
		}
	}
