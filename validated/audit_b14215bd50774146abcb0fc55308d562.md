### Title
Cross-tenant Commit/Status mutation via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by SHA alone across the entire `commits` table and calls `create_status_from_github!` on every match, without ever checking that the matched `Commit#stack` belongs to the repository that sent the webhook. Since SHAs are not unique per repository (e.g. shared vendored commits, or the universal empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`), an attacker who owns any repository connected to Shipit can send one legitimately-signed status webhook and write `Status` rows into every other tenant stack that happens to have a `Commit` row with the same SHA.

### Finding Description
The broken binding: `mutated_stacks_count == 1` (only the stack for `params.repository.full_name`) is claimed by the code's intent, but the actual code produces `mutated_stacks_count == N` where `N` is the number of distinct stacks owning a `Commit` row with that SHA.

Code path:
- `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This query is completely unscoped by repository/stack. Notably, the base `Handler` class already provides a repository-scoped helper, `stacks`, built from `Repository.from_github_repo_name(repository_name)&.stacks`: [2](#0-1) 

`StatusHandler` does not use this `stacks` scope at all — it queries the global `Commit` table directly by `sha`, so any `Commit` row owned by any other tenant's `Stack` that happens to share the SHA gets mutated. `create_status_from_github!` then creates a `Status` row and can flip the commit's CI state (`add_status`), potentially triggering `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` on a stack the attacker does not own: [3](#0-2) [4](#0-3) 

Existing guards do not prevent this: webhook signature verification only proves the payload was signed by GitHub for the sender's *own* repository — it says nothing about which `Commit` rows in Shipit's database share the reported SHA. `ExplicitParameters` validates the shape of the payload (`sha`, `state`, etc.) but not any repository/stack ownership relationship to the SHA. There is no `stack_id` or `repository` filter applied to the `Commit.where(sha:)` lookup.

Attacker flow:
1. Attacker controls/owns Repo A, connected to Shipit as some stack.
2. Attacker identifies a SHA that also exists as a `Commit` row in stacks belonging to other tenants (shared vendored dependency commit, or the empty-tree SHA which naturally appears across many initial/empty commits).
3. Attacker pushes/commits that SHA into Repo A (trivial for the empty-tree SHA, or by vendoring the same dependency commit) and sends (or triggers via a real GitHub status event) a `status` webhook for Repo A with that SHA.
4. Shipit verifies the signature for Repo A (valid, since attacker owns Repo A and GitHub really sent it, or replicates a legitimately-signed shape), then `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matching Commit rows across all stacks with that SHA, and writes a `Status` to each.

### Impact Explanation
A single valid webhook from a repository the attacker controls causes `Status` writes (and associated CI-state side effects such as `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`) on `Commit` rows belonging to stacks/repositories the attacker does not own and never authenticated for. This is a cross-tenant write: one repository's payload mutates another repository's stack/commit state, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any SHA collision the attacker can arrange or find (trivially, the empty-tree SHA), and scales to every tenant stack sharing that SHA in one request.

### Likelihood Explanation
Preconditions are modest: the attacker needs any repository connected to Shipit under their control (a normal, unprivileged capability for anyone who can add a repo/webhook or push to a repo already tracked), and needs a SHA collision with a `Commit` row in another tenant stack. The empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904` is a naturally occurring, universal collision (any empty commit/initial commit with no tree changes shares it), making this trivially exploitable with no advanced git engineering. No secrets, tokens, or privileged roles are required beyond owning/controlling one Shipit-tracked repository able to emit or receive a status webhook.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the stacks owned by the webhook's originating repository, using the base `Handler#stacks` helper (or an equivalent join through `Repository.from_github_repo_name(repository_name)`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a status can only be attached to commits belonging to stacks tied to the reporting repository.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create three `Stack` fixtures backed by three distinct `Repository` full names (`org/repo-a`, `org/repo-b`, `org/repo-c`).
2. Create three `Commit` fixtures, one per stack, all sharing `sha: '4b825dc642cb6eb9a060e54bf8d69288fbee4904'`.
3. Build a `status` webhook payload naming only `org/repo-a` as `repository.full_name`, with the shared SHA and `state: 'success'`.
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (or POST through the webhooks controller with a valid signature for `repo-a`).
5. Assert: before, `Status.count` for stacks B and C is 0; after, assert `Status.where(commit: commit_b).count == 1` and `Status.where(commit: commit_c).count == 1`, proving the equality `mutated_stacks_count == 1` is violated (actual value is 3).
