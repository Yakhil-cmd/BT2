### Title
Race condition in concurrent private-payment chain validation allows duplicate-output crash / node DoS - (File: `private_payment.js`)

### Summary
`network.js`'s `handleSavedPrivatePayments()` intentionally processes multiple queued private-payment chains **in parallel** via `async.each` [1](#0-0) , each calling `privatePayment.validateAndSavePrivatePaymentChain()` on its own DB connection/transaction with no mutex protecting the "check-then-insert" sequence for a given output. This mirrors the CVE-2017-18224 bug class: a missing semaphore/lock around a shared resource lets two concurrent operations race on the same data (there, ocfs2's extent tree; here, the `outputs` row for a given `unit/message_index/(output_index)`), corrupting internal invariants and triggering an unhandled crash.

### Finding Description
`validateAndSavePrivatePaymentChain()` in `private_payment.js` performs a classic check-then-act pattern without any application-level lock: it `SELECT`s existing rows in `outputs` for `(unit, asset, message_index[, output_index])` to detect duplicates, and only afterward calls into `indivisible_asset.js`/`divisible_asset.js` to insert/update the same rows [2](#0-1) . This function is invoked by `network.js`'s `handleSavedPrivatePayments`, which explicitly runs multiple pending chains **in parallel** ("handle different chains in parallel") [3](#0-2)  and also by `handleOnlinePrivatePayment` for freshly-arrived private payments [4](#0-3) .

Unlike the main unit-validation/write path, which serializes access via `mutex.lock(arrAuthorAddresses, ...)` in `validation.js` [5](#0-4)  and `mutex.lock(["write"], ...)` in `writer.js` [6](#0-5) , private-payment chain processing takes **no** such lock keyed on the unit/output being written. Each parallel invocation opens its own DB connection and its own `BEGIN`/`COMMIT` transaction [7](#0-6) . If two chains referencing the same `(unit, message_index, output_index)` are queued and processed concurrently (e.g., the same private payment delivered twice, once directly and once via the hub — a scenario the code's own comment in `network.js` acknowledges as expected: "we may receive the same unit and message index but different output indexes if recipient and cosigner are on the same device... we also receive the same (unit, message_index, output_index) twice" [8](#0-7) ), both concurrent transactions can pass the duplicate-check `SELECT` before either has committed its `INSERT`/`UPDATE`, because the check and the write are not atomic with respect to each other across connections and no in-process mutex serializes them.

The consequence is either:
1. A crash via `throw Error("more than one output " + ...)` at line 75 if a third read observes both now-committed rows [9](#0-8)  — this throw happens inside a `db.query` callback with no surrounding try/catch, so it becomes an uncaught exception in Node.js, crashing the wallet/hub process (denial of service), directly analogous to the kernel `BUG()` triggered by the ocfs2 race.
2. Duplicate insertion of private outputs/inputs for the same `(unit, message_index)` when the race window is hit before any row exists yet, since the `INSERT ... IGNORE`/`UPDATE ... WHERE is_spent=0` in `indivisible_asset.js`/`divisible_asset.js` are not gated by a lock that spans the initial duplicate check performed in `private_payment.js`.

### Impact Explanation
An uncaught exception thrown from within an asynchronous DB callback in Node.js is fatal by default (no domain/try-catch wraps this code path), crashing the process that is validating incoming private payments — a wallet, hub, or any node handling private-asset chains. This is a concrete denial-of-service against the specific process reachable simply by a private-payment counterparty (or a device/hub relaying the same private chain via two paths), matching the "private payment chains" reachable surface explicitly in scope. It does not require any special privilege beyond normal private-payment participation.

### Likelihood Explanation
The race is a narrow timing window (two DB round-trips across two connections/transactions must interleave in a specific order), so it is not trivially or deterministically triggerable, similar to the underlying kernel race requiring specific timing between direct I/O and extent-tree writers. Under MySQL-backed hubs, real concurrency across connections is normal, and the code's own comments confirm that duplicate delivery of the same private chain (via hub + direct peer, or cosigner + recipient on the same device) is an expected occurrence, increasing the practical likelihood of hitting the race compared to a purely synthetic scenario.

### Recommendation
Serialize concurrent private-payment-chain validation for the same target row by acquiring a `mutex.lock` keyed on `(unit, message_index[, output_index])` (or on the asset) before performing the duplicate-check `SELECT` in `private_payment.js`, and holding it until the transaction commits/rolls back — analogous to the `mutex.lock(["private_write"])` pattern already used elsewhere in `validation.js` [10](#0-9) . Additionally, replace the `throw Error("more than one output ...")` with a graceful `callbacks.ifError(...)` so a genuine data anomaly cannot crash the process.

### Proof of Concept
1. Attacker (or two race-uncoordinated legitimate senders) delivers the same private payment chain head `{unit, message_index, output_index}` to a hub/wallet twice in rapid succession — once directly and once relayed via the hub, as explicitly anticipated by the comment in `handleOnlinePrivatePayment` [8](#0-7) .
2. `handleSavedPrivatePayments` picks up both queued rows and processes them in parallel via `async.each` [11](#0-10) .
3. Both parallel calls to `validateAndSavePrivatePaymentChain` execute their duplicate-check `SELECT` before either's `INSERT`/`UPDATE` transaction commits [12](#0-11) .
4. Both proceed to insert/update the same output row; a subsequent (or racing third) validation attempt for the same key observes two rows and hits `throw Error("more than one output ...")` [9](#0-8) , crashing the process since the throw is unhandled inside the async DB callback.
