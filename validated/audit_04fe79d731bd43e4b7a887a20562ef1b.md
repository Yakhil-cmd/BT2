### Title
Unbounded `extraData` in Bridge Request Functions Permanently Locks Cross-Chain Assets When Destination Chain Has Lower Block Gas Limit — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge accepts an unbounded `extraData` bytes field in every cross-chain value-transfer request (`requestKLAYTransfer`, `requestERC20Transfer`, `requestERC721Transfer`). When the source chain has a higher block gas limit than the destination chain, an attacker (or even an innocent user) can submit a request whose `extraData` is large enough to succeed on the source chain but causes the corresponding `handleXXXTransfer` transaction to exceed the destination chain's block gas limit. Because the handle transaction reverts, the nonce is never marked handled, `lowerHandleNonce` is permanently stuck, and the VT Recovery loop retries the same failing transaction indefinitely — permanently locking the user's bridged KAIA/ERC20/ERC721 assets with no on-chain escape path.

---

### Finding Description

**Root cause — no size bound on `extraData`:**

`_requestKLAYTransfer` in `BridgeTransferKLAY.sol` accepts `bytes calldata _extraData` with no length check and emits it verbatim in the `RequestValueTransfer` event. [1](#0-0) 

The same pattern exists in `BridgeTransferERC20.sol` and `BridgeTransferERC721.sol`. [2](#0-1) 

**Handle path — `extraData` is re-emitted in the event, consuming gas proportional to its size:**

`handleKLAYTransfer` includes `_extraData` in the `HandleValueTransfer` event emission. Each byte of event data costs 8 gas (EVM LOG opcode). With the default operator gas limit of 10 M gas, roughly 1.25 MB of non-zero `extraData` exhausts the budget before the KLAY transfer even executes. [3](#0-2) 

**Nonce accounting — a reverted handle leaves `lowerHandleNonce` permanently stuck:**

`_updateHandleNonce` advances `lowerHandleNonce` only when `handleNoncesToBlockNums[i] > 0` for every consecutive nonce starting from `lowerHandleNonce`. Because the handle transaction reverts (all state changes rolled back), `handleNoncesToBlockNums[N]` is never written, and the loop stops at N forever. [4](#0-3) 

**VT Recovery — retries the same failing nonce indefinitely:**

`retrievePendingEvents` uses `recoveryBlockNumber` (which is also stuck because it is only updated inside the same loop) as the scan start, and `recoverPendingEvents` re-queues the same event. There is no skip-nonce or force-advance mechanism in the bridge contract. [5](#0-4) 

**Operator gas limit — configurable but cannot exceed the destination chain's block gas limit:**

The default operator gas limit is 10 M gas (matching the default block gas limit shown in the config template). If the destination chain's block gas limit is lower (e.g., a custom service chain configured with 5 M), no operator-side increase can make the transaction fit. [6](#0-5) [7](#0-6) 

---

### Impact Explanation

- **Bridged assets permanently locked.** The user's KAIA/ERC20/ERC721 tokens are held by the source-chain bridge contract after `requestXXXTransfer` succeeds. Because the handle transaction on the destination chain always reverts, the tokens can never be released or refunded. There is no `cancelRequest` or `refund` function in the bridge contract.
- **`lowerHandleNonce` permanently frozen.** `recoveryBlockNumber` is also frozen, causing the VT Recovery goroutine to scan the same block range on every interval, wasting resources and never making progress.
- **No privileged escape path on-chain.** The bridge owner can pause the bridge (`setRunningStatus(false)`) but cannot skip a nonce or force-advance `lowerHandleNonce`. A contract upgrade or manual operator intervention at the Go layer is required.

---

### Likelihood Explanation

- Any user who calls `requestKLAYTransfer` / `requestERC20Transfer` / `requestERC721Transfer` can supply arbitrary `extraData`. No special privilege is required.
- The Kaia main chain and service chains can have different block gas limits. The default template sets both to 10 M, but service-chain operators routinely lower this for cost or throughput reasons.
- A malicious actor can deliberately craft the attack; an innocent user with a legitimate large `extraData` payload (e.g., an application embedding metadata) can trigger it accidentally.
- The VT Recovery mechanism (`VTRecovery: false` by default) may not even be enabled, meaning the stuck nonce is never retried and the asset loss is immediate and silent. [8](#0-7) 

---

### Recommendation

1. **Enforce a maximum `extraData` length** in every `requestXXXTransfer` function, sized to fit comfortably within the minimum expected block gas limit of any supported destination chain (e.g., `require(_extraData.length <= MAX_EXTRA_DATA_SIZE, "extraData too large")`).
2. **Document the gas budget** consumed by `handleXXXTransfer` as a function of `extraData` length, and expose a per-bridge configurable `maxExtraDataSize` that operators must set before enabling a bridge pair.
3. **Add a nonce-skip / force-advance function** (owner-only) to `BridgeTransfer.sol` so that a permanently stuck nonce can be administratively bypassed without a contract upgrade, preventing indefinite asset lockup.
4. **Enable VT Recovery by default** and add a circuit-breaker that stops retrying a nonce after N consecutive failures, alerting operators instead of looping silently.

---

### Proof of Concept

**Setup:** Two chains — chain A (block gas limit 30 M, e.g., Kaia mainnet) and chain B (block gas limit 5 M, e.g., a custom service chain). Both chains have a deployed bridge pair. The operator gas limit on chain B is set to 5 M (the maximum possible).

**Step 1 — Attacker submits a request with large `extraData` on chain A:**
```solidity
// ~600 KB of non-zero bytes → calldata cost alone ≈ 9.6 M gas on chain B
bytes memory largeData = new bytes(600_000);
for (uint i = 0; i < largeData.length; i++) largeData[i] = 0xFF;

bridge_A.requestKLAYTransfer{value: 1 ether}(
    attacker_address_on_B,
    0.9 ether,
    largeData          // no size check — accepted
);
// Emits RequestValueTransfer with requestNonce = N
// Gas used on chain A: ~2 M (well within 30 M limit)
```

**Step 2 — VT Recovery (or relayer) calls `handleKLAYTransfer` on chain B:**
```solidity
bridge_B.handleKLAYTransfer{gas: 5_000_000}(
    requestTxHash,
    attacker_address_on_A,
    attacker_address_on_B,
    0.9 ether,
    N,                 // requestedNonce
    blockNumber,
    largeData          // 600 KB re-passed as calldata
);
// Gas consumed: >5 M (calldata + memory + event emission)
// Result: OUT OF GAS → entire transaction reverts
// handleNoncesToBlockNums[N] is never written
// lowerHandleNonce stays at N forever
```

**Step 3 — Verify asset lockup:**
```go
lowerHandleNonce, _ := bridge_B.LowerHandleNonce(nil)
// lowerHandleNonce == N  (stuck)

// User's 0.9 KAIA is held by bridge_A with no recovery path
// VT Recovery retries every VTRecoveryInterval seconds, always fails
```

**Observed invariant violation:** `lowerHandleNonce` on chain B is permanently frozen at N. The user's 0.9 KAIA locked in `bridge_A` is irrecoverable without an off-chain operator intervention or contract upgrade. This matches the "unauthorized lock of bridged assets" impact class.     // _updateHandleNonce increases lower and upper handle nonce after the _requestedNonce is handled.
    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];

        lowerHandleNonce = i;

func retrievePendingEventsFrom(hint *valueTransferHint, from, to *BridgeInfo) ([]IRequestValueTransferEvent, error) {
	if from.bridge == nil {
		return nil, errors.New("from bridge is nil")
	}
	if to.bridge == nil {
		return nil, errors.New("to bridge is nil")
	}
	if hint.requestNonce == hint.handleNonce {
		return nil, nil
	}
	if !checkRecoveryCondition(hint) {
		return nil, nil
	}

	var pendingEvents []IRequestValueTransferEvent

	curBlkNum, err := from.GetCurrentBlockNumber()
	if err != nil {
		return nil, err
	}

	startBlkNum := hint.blockNumber
	endBlkNum := startBlkNum + filterLogsStride

pendingTxLoop:
	for startBlkNum <= curBlkNum {
		if endBlkNum > curBlkNum {
			endBlkNum = curBlkNum
		}
		opts := &bind.FilterOpts{Start: startBlkNum, End: &endBlkNum}
		reqVTevIt, err := from.bridge.FilterRequestValueTransfer(opts, nil, nil, nil)
		if err != nil {
			return nil, err
		}
		reqVTencodedDataIt, err := from.bridge.FilterRequestValueTransferEncoded(opts, nil, nil, nil)
		if err != nil {
			return nil, err
		}

		// TODO: The same logic with two types are verbose and can be neat with Go1.18 which supports generic.
		// For the FilterRequestValueTransfer type
		for reqVTevIt.Next() {
			logger.Trace("pending nonce in the RequestValueTransfer event", "requestNonce", reqVTevIt.Event.RequestNonce)
			if reqVTevIt.Event.RequestNonce >= hint.handleNonce {
				// Check if the event is already handled in target bridge contract
				if isHandledEvent(to, RequestValueTransferEvent{reqVTevIt.Event}) {
					continue
				}
				logger.Trace("filtered pending nonce", "requestNonce", reqVTevIt.Event.RequestNonce, "handledNonce", hint.handleNonce)
				pendingEvents = append(pendingEvents, RequestValueTransferEvent{reqVTevIt.Event})
				if len(pendingEvents) >= maxPendingTxs {
					reqVTevIt.Close()
					break pendingTxLoop
				}
			}
		}
		// For the FilterRequestValueTransferEncoded type
		for reqVTencodedDataIt.Next() {
			logger.Trace("pending nonce in the RequestValueTransferEncoded event", "requestNonce", reqVTencodedDataIt.Event.RequestNonce)
			if reqVTencodedDataIt.Event.RequestNonce >= hint.handleNonce {
				// Check if the event is already handled in target bridge contract
				if isHandledEvent(to, RequestValueTransferEncodedEvent{reqVTencodedDataIt.Event}) {
					continue
				}
				logger.Trace("filtered pending nonce", "requestNonce", reqVTencodedDataIt.Event.RequestNonce, "handledNonce", hint.handleNonce)
				pendingEvents = append(pendingEvents, RequestValueTransferEncodedEvent{reqVTencodedDataIt.Event})
				if len(pendingEvents) >= maxPendingTxs {
					reqVTencodedDataIt.Close()
					break pendingTxLoop
				}
			}
		}
		startBlkNum = endBlkNum + 1
		endBlkNum = startBlkNum + filterLogsStride
		reqVTevIt.Close()
		reqVTencodedDataIt.Close()
	}

	if len(pendingEvents) > 0 {
		logger.Info("retrieved pending events", "bridge", from.address.String(),
			"len(pendingEvents)", len(pendingEvents), "1st nonce", pendingEvents[0].Nonce())
	}
	return pendingEvents, nil
}

func (vtr *valueTransferRecovery) recoverPendingEvents() error {
	defer func() {
		vtr.childEvents = []IRequestValueTransferEvent{}
		vtr.parentEvents = []IRequestValueTransferEvent{}
	}()

	if len(vtr.childEvents) > 0 {
		logger.Warn("VT Recovery : Child -> Parent Chain", "cBridge", vtr.cBridgeInfo.address.String(), "events", len(vtr.childEvents))
	}

	vtRequestEventMeter.Mark(int64(len(vtr.childEvents)))
	vtRecoveredRequestEventMeter.Mark(int64(len(vtr.childEvents)))

	events := make([]IRequestValueTransferEvent, len(vtr.childEvents))
	for i, event := range vtr.childEvents {
		events[i] = event
	}
	vtr.pBridgeInfo.AddRequestValueTransferEvents(events)

	if len(vtr.parentEvents) > 0 {
		logger.Warn("VT Recovery : Parent -> Child Chain", "pBridge", vtr.pBridgeInfo.address.String(), "events", len(vtr.parentEvents))
	}

	vtHandleEventMeter.Mark(int64(len(vtr.parentEvents)))
	events = make([]IRequestValueTransferEvent, len(vtr.parentEvents))
	for i, event := range vtr.parentEvents {
		events[i] = event
	}
	vtr.cBridgeInfo.AddRequestValueTransferEvents(events)

	return nil
}
