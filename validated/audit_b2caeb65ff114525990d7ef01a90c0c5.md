Confirmed: the fixture `here_come_the_walrus` is an `ApiClient` scoped to the `shipit` stack via `stack: shipit`, and elsewhere (`Api::BaseController#stacks`) this scoping is enforced by filtering `Stack.where(id: current_api_client.stack_id)` before resolving `params[:stack_id]`. `Api::CCMenuController` bypasses that enforcement entirely.

### Title
Stack-scoped API token can read build/CI status of any stack via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides both `authenticate_api_client` and `stack` in a way that breaks the binding between the `Stack` a stack-scoped `ApiClient` token is authorized for and the `Stack` whose data the endpoint actually returns.

### Finding Description
Every other API controller resolves the target stack through `Api::BaseController#stacks`, which restricts the queryable set to the client's own stack when the client is stack-scoped: [1](#0-0) 
This is the binding: `ApiClient#stack_id` (if present) == the only `Stack` reachable through `#stack`/`#stacks` for that token.

`Api::CCMenuController`, however, defines its own `stack` method that queries `Stack.from_param!(params[:stack_id])` directly on the global `Stack` relation, never going through the scoped `stacks` helper: [2](#0-1) 

The controller still enforces the permission bit via `require_permission :read, :stack`, which only checks that `"read:stack"` is present in `current_api_client.permissions` — it never checks the requested stack against `current_api_client.stack_id`: [3](#0-2) 

Concretely, the `here_come_the_walrus` fixture is an `ApiClient` scoped to the `shipit` stack (`stack: shipit`, `permissions: ['read:stack']`): [4](#0-3) 

Because `CCMenuController#stack` ignores `current_api_client.stack_id`, presenting that same token with a different `stack_id` in the URL succeeds and returns that other stack's build data, whereas the same token used against `Api::StacksController#show` (which goes through `stacks.from_param!`) would be limited to the `shipit` stack only. This is the exact class of bug described in the report: a credential is checked ("is this token generally allowed to `read:stack`?") but the specific object it's allowed to act on is never re-verified before the privileged action (rendering another stack's deploy/build status) is performed.

### Impact Explanation
This crosses the "unauthenticated/unauthorized read of stack state, task streams or deploy output" High-severity category: any holder of a single-stack-scoped `read:stack` token (e.g. a token deliberately handed to a low-trust CI dashboard integration for one stack, as done by `CCMenuUrlController`) can enumerate and read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock status, etc.) of every stack in the Shipit instance, not just the one it was issued for.

### Likelihood Explanation
High. The endpoint accepts the token via a simple `token` query-string parameter (as shown in the test `"can authenticate with query string token"`), requires no special conditions, and the only thing an attacker needs is any valid stack-scoped token (which by design in `CCMenuUrlController` is generated and embedded directly in URLs that get shared/broadcast, e.g. in CI dashboards) plus knowledge/guessing of another stack's `to_param`.

### Recommendation
Change `Api::CCMenuController#stack` to resolve the stack through the scoped `stacks` collection (i.e. `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the binding between the token's `stack_id` and the stack actually rendered is enforced identically to every other API endpoint.

### Proof of Concept
1. Obtain (or be issued) a `read:stack`-only `ApiClient` token scoped to `stack_id = A` (e.g. via the `/ccmenu/*stack_id` URL flow in `CCMenuUrlController`, which mints exactly such a token).
2. Call `GET /api/ccmenu/*stack_id_B?token=<token>` where `stack_id_B` is any other stack in the instance.
3. Observe `Api::CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])` (bypassing the client's `stack_id` scope) and `require_permission :read, :stack` only checks the permission string, so the response renders stack B's build/deploy status even though the token was only ever authorized for stack A. module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
