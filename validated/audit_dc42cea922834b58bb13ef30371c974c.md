### Title
Webhook Signature Verification Uses an Attacker-Chosen Organization Key While the Handler Acts on a Different, Attacker-Chosen Repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify the request against based on a field taken directly from the *unverified* request body, while the handlers that subsequently act on the request select the target repository/stack from a *different* field in that same unverified body. An attacker who knows (or controls) any organization key configured on the Shipit instance that has no `webhook_secret` set can trivially satisfy signature verification for that organization while pointing the payload's `repository.full_name` at a completely different (victim) repository/stack, causing Shipit to perform unauthenticated, cross-repository state changes (forced syncs, spoofed commit statuses, spoofed check-suite/PR events, etc.) as if they came from a verified GitHub webhook.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App used for HMAC verification like this: [1](#0-0) 

The organization used to pick the app config comes straight from the JSON body, not from any authenticated context: [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config via `github_app_config`, and each organization can independently have (or lack) a `webhook_secret`: [3](#0-2) 

Crucially, `GitHubApp#verify_webhook_signature` unconditionally accepts the request when that organization's `webhook_secret` is blank: [4](#0-3) 

Meanwhile, the event handlers resolve the *actual* repository/stack to act on from a **separate** field of the same untrusted payload, `repository.full_name`, completely independent of the field used to pick the verifying organization: [5](#0-4) 

For example, `PushHandler` uses this repository/stack resolution to trigger a forced sync to an attacker-chosen `after` SHA: [6](#0-5) 

This breaks the trust binding: **organization authenticated for signature purposes == organization/repository actually written to**. `repository.owner.login` (or `organization.login`) is used to select the *authenticating* secret, but `repository.full_name` is used to select the *target* of the write — and both are attacker-controlled fields in the same unsigned-at-verification-time body. In a multi-organization Shipit deployment (a documented, supported configuration via `secrets.github` keyed by org, see `TOP_LEVEL_GH_KEYS`/`github_organizations` in `lib/shipit.rb`), an attacker only needs one organization entry with no `webhook_secret` configured (e.g., a demo/test/staging org) to forge events that write to any other tracked repository's stack.

### Impact Explanation
This allows an unauthenticated attacker to submit forged GitHub webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) that pass signature verification (by claiming to be from an organization with no configured secret) but that actually target a different, victim repository/stack through `repository.full_name`. Consequences include:
- Forcing `GithubSyncJob` to sync a victim stack to an attacker-chosen commit SHA (`stack.sync_github(expected_head_sha: ...)`), which can influence what gets considered deployable/deployed.
- Writing spoofed `CommitStatus` records against arbitrary commits of a victim repository (via the `status` handler), corrupting deploy-gating logic.
- Triggering other cross-tenant side effects (team/membership handlers, check-suite refresh, PR-derived review stacks) without ever holding a valid signing secret for the targeted organization.

This is a cross-repository/cross-tenant write achieved purely by exploiting a mismatch between the authenticated identity and the entity acted upon — matching the "unauthorized deploy/write via broken authentication binding" impact class.

### Likelihood Explanation
Likelihood is High in any multi-organization Shipit deployment where at least one configured organization lacks a `webhook_secret` (a state the code explicitly tolerates and treats as "always verified", per `github_app.rb#L77`). No credentials, GitHub App keys, or prior repository access are required — only knowledge of one such lightly-configured organization key and the target victim's `repository.full_name`, both of which are frequently discoverable (org names/public repo names are not secret).

### Recommendation
Do not derive the verifying organization from the unverified request body field that differs from the field used to resolve the target repository. Instead:
- Bind webhook endpoints to a specific organization/repository via the URL/route or a pre-registered mapping, not via payload contents, or
- Require that `repository.owner.login`/`organization.login` used for secret selection be cross-checked against `repository.full_name` used for the actual write, rejecting mismatches, and
- Do not silently treat a missing `webhook_secret` as "verified"; instead require every configured organization to have a secret, or reject events from an organization with no secret when other organizations require one.

### Proof of Concept
1. Configure Shipit with multi-org GitHub App secrets, e.g.:
```yaml
github:
  attacker-org:
    app_id: 1
    installation_id: 1
    webhook_secret: null   # no secret configured
  victim-org:
    app_id: 2
    installation_id: 2
    webhook_secret: "s3cr3t"
```
2. Send an unsigned/garbage-signed POST to the webhooks endpoint:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, resolves `webhook_secret == nil`, and `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb#L76-77`), regardless of the bogus `X-Hub-Signature`.
4. `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb#L12-17`) resolves the stack via `repository.full_name = "victim-org/victim-repo"` (`handler.rb#L32-38`) and enqueues `GithubSyncJob` with the attacker-chosen `after` SHA against the victim's stack — despite the request never being authenticated for `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
