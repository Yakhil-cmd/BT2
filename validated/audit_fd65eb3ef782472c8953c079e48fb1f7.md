### Title
Unhandled `TypeError` from malformed authentifier crashes validating node in the `in merkle` address-definition operator - (File: definition.js, merkle.js)

### Summary
The `in merkle` opcode in the address-definition evaluator (`definition.js`) passes an attacker-controlled authentifier value directly into `merkle.deserializeMerkleProof()` without checking that it is a string and without any surrounding `try/catch`. `deserializeMerkleProof()` unconditionally calls `.split("-")` on its argument. Supplying a non-string, truthy authentifier value (array/object/number) causes an uncaught `TypeError` that propagates out of the synchronous `evaluate()` call chain used during unit validation. Because ocore's networking layer installs a global `uncaughtException` handler that deliberately re-throws to crash the process (`network.js`), any node validating such a unit crashes. This mirrors the CVE-2018-14367 bug class: attacker-supplied, insufficiently validated data reaches a parsing routine that dereferences/operates on it without a NULL/type check, crashing the component that processes it.

### Finding Description
`validateDefinition`'s internal `evaluate()` function handles the `in merkle` definition operator: [1](#0-0) 

Note that the only guard on the authentifier is a truthiness check (`if (!assocAuthentifiers[path]) return cb2(false);`), not a type check. The value is taken straight from `assocAuthentifiers[path]`, which originates from `objUnit.authors[i].authentifiers`, an attacker-controlled structure whose only high-level constraint enforced elsewhere is that it is a non-empty object — its individual values are not required to be strings before opcodes like `in merkle` consume them.

That value is passed unchecked into: [2](#0-1) 

`serialized_proof.split("-")` throws `TypeError: serialized_proof.split is not a function` if `serialized_proof` is anything other than a string (e.g., an array, object, or number) — none of which are filtered out before this call, and there is no `try/catch` around it in `definition.js`, unlike the equivalent AA-formula opcode `is_valid_merkle_proof` in `evaluation.js`, which explicitly validates string type/length and wraps `merkle.verifyMerkleProof` in `try/catch`: [3](#0-2) 

The `in merkle` code path lacks this defensive handling entirely.

Because `validate()` in `validation.js` invokes address-definition/authentifier evaluation synchronously deep inside an `async.series` callback chain with no blanket `try/catch`, an uncaught `TypeError` thrown here bubbles up to the process level. `network.js` registers a global handler that intentionally crashes the process on any uncaught exception, treating it as an unrecoverable, inconsistent state: [4](#0-3) 

### Impact Explanation
Any node (full node, witness, or hub) that receives and validates a unit signed by an address whose definition contains an `in merkle` condition, where the corresponding authentifier is a non-string truthy value, will throw an uncaught exception and crash per the `uncaughtException` handler's explicit `throw err`. Because the trigger is a single posted unit reachable by any unprivileged unit poster (the attacker only needs to control an address definition that uses `in merkle`, which they can create themselves and self-sign), this can be used to repeatedly crash nodes that receive and validate the malicious unit — a network-wide denial of service preventing confirmation of new units, matching the "network unable to confirm new units" impact bucket.

### Likelihood Explanation
High reachability: `in merkle` is a standard address-definition operator available to any user; the attacker fully controls the shape of `authentifiers` for the address they created, so producing a non-string value at the relevant path is trivial. No special privileges, hub/peer trust, or race conditions are required — only a single broadcast unit.

### Recommendation
In `definition.js`'s `in merkle` case, validate that `assocAuthentifiers[path]` is a non-empty string before calling `merkle.deserializeMerkleProof`, and wrap the deserialize/verify calls in a `try/catch` that resolves to `cb2(false)` (treating malformed proofs as invalid rather than throwing), mirroring the defensive checks already present in `formula/evaluation.js`'s `is_valid_merkle_proof` handling. Additionally, review the global `uncaughtException` handler policy so a single malformed but adversarial unit cannot unconditionally crash the process.

### Proof of Concept
1. Create/own an address whose definition includes an `in merkle` term, e.g. `['in merkle', [['ADDRESS_BASE32'], 'feed_name', 'expected_value']]`, at some authentifier path `path`.
2. Construct a unit signed by this address where `authors[i].authentifiers[path]` is set to a non-string truthy value, e.g. `[1,2,3]` or `{}` (both pass the `if (!assocAuthentifiers[path])` truthiness check but are not strings).
3. Broadcast the unit to the network / post it to a hub.
4. When any node calls `validateAuthentifiers` → `evaluate()` → the `in merkle` case → `merkle.deserializeMerkleProof(assocAuthentifiers[path])`, the array/object has no `.split` method, `serialized_proof.split("-")` throws `TypeError`, this propagates uncaught, and the process crashes via the `uncaughtException` handler in `network.js`. [5](#0-4) [2](#0-1) 

**Note on completeness:** I was not able to fully trace every intermediate call layer between `validateAuthentifiers`/`evaluate()` and the top-level `validate()` function to rule out any intermediate `try/catch` that might swallow the exception before it becomes a true process-level uncaught exception (index/search limits prevented reading `validateAuthentifiers`'s full wrapper and every caller in `validation.js` in this session). The presence and design intent of the global `uncaughtException` handler (`throw err; // crash the process to avoid ending up in an inconsistent state`) strongly suggests such synchronous throws are not expected to be caught anywhere in this call path, but this should be confirmed by tracing `validateAuthentifiers` end-to-end before treating this as fully proven.
