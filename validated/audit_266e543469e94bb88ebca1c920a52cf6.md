### Title
Unbounded private-payment chain buffering enables memory/DB exhaustion via `handlePrivatePaymentChains` - ([File: wallet.js])

### Summary
The CVE describes a pre-authentication resource-exhaustion bug: a length/array-size field is never validated, letting an attacker keep an arbitrarily large amount of attacker-controlled data buffered in server memory because validation is deferred until a terminating condition that the attacker never triggers. The closest reachable analog in ocore is `handlePrivatePaymentChains()` in [1](#0-0) , reached from any paired device or private-payment counterparty (via `hub/message`/`private_payments` subject), which accepts `body.chains` and validates only field *presence* (`isNonemptyString`, `isNonemptyObject`, `isNonemptyArray`) with no bound on the number of chains, the number of elements per chain, or the length of any string field (`unit`, `asset`, `blinding`, `address`, `output_hash`, etc.) before the data is persisted.

### Finding Description
`handlePrivatePaymentChains(ws, body, from_address, callbacks)` performs only a shape check on the incoming chains: [1](#0-0) 
There is no limit on `arrChains.length`, no limit on `c.length` (chain depth), and no length caps on the base64/string fields inside each element. Immediately after this shape check, the function computes a hash over the whole structure and, for light clients, calls `network.requestUnfinishedPastUnitsOfPrivateChains(arrChains)` and then iterates every chain via `network.handleOnlinePrivatePayment`.

In `handleOnlinePrivatePayment()` (network.js), when the client is light and a chain has more than one element, the full unvalidated element array is persisted verbatim into the `unhandled_private_payments` table before any deeper field validation or size check occurs: [2](#0-1) 
This is the "buffer now, validate/complete later" pattern that maps directly to the CVE root cause: data is accepted and stored based only on superficial well-formedness, and the actual bound-enforcing validation (`indivisible_asset.js`/`divisible_asset.js` `validatePrivatePayment`, which does check field types/lengths like `isStringOfLength(payload.asset, HASH_LENGTH)`) only runs later, inside `parsePrivatePaymentChain` — and only once the full past-unit chain is available (`ifWaitingForChain`). Until that resolution happens, or forever if the referenced past units never arrive, the oversized/garbage JSON blobs remain buffered in the `unhandled_private_payments` table and in the `handledChainsCache`/`assocValidatedByKey` in-memory structures, with no message body size cap analogous to `MAX_UNIT_LENGTH` enforced anywhere in this path (that cap lives in unit validation, `validation.js:267`, which is never reached for buffered/queued light-client private payments).

Because the entry point is reached through the standard device-messaging / hub relaying flow available to any paired device or private-payment counterparty (no special privilege beyond being a correspondent), an attacker can:
1. Send `private_payments` messages with `body.chains` containing many chains, each with many elements, each carrying maximal-size strings in `asset`/`unit`/`blinding`/`address`/`output_hash` fields (bounded only by whatever outer device-message size limit exists, if any).
2. Reference `unit` values that don't exist / are never resolvable, so the chain never reaches `ifOk`/`ifError` and stays queued (`unhandled_private_payments`, uncapped table growth) or cached indefinitely in `handledChainsCache`.

### Impact Explanation
Repeated submission of large, unvalidated, unresolvable private-payment chains grows the `unhandled_private_payments` table and associated in-memory bookkeeping (`assocValidatedByKey`, `handledChainsCache`) without bound, exhausting disk/memory on the victim wallet/hub node — a denial of service that prevents the node from confirming/processing legitimate private payments, analogous to the CVE's server-memory exhaustion via unvalidated, never-finalized buffered data.

### Likelihood Explanation
Medium-High: this path is reachable by any device paired with the victim (a correspondent) or any hub relaying `private_payments` messages, with no special privileges. The shape check in `wallet.js` is trivial to satisfy while still allowing arbitrarily large or malformed content in the individual string fields and arbitrarily many chains/elements per message.

### Recommendation
Add explicit bounds in `handlePrivatePaymentChains()` (and/or `handleOnlinePrivatePayment()`) before any persistence: cap `arrChains.length`, cap each chain's element count, and validate/limit the length of every string field (`unit`, `asset`, `blinding`, `address`, `output_hash`) to their expected fixed sizes (e.g., `HASH_LENGTH`) immediately, mirroring the checks already present in `indivisible_asset.js`'s `validatePrivatePayment`, so malformed/oversized data is rejected before it is written to `unhandled_private_payments` or cached in memory. Also add a TTL/cap on `unhandled_private_payments` rows and `handledChainsCache` size to bound worst-case growth.

### Proof of Concept
A paired device (or malicious hub forwarding on a correspondent's behalf) sends a `hub/message`/`private_payments` payload:
```
{
  "chains": [
    [ { "unit": "<64-char base64, but arbitrary garbage>", "payload": {
          "asset": "<attacker-chosen long/garbage base64 string>",
          "inputs": [{"junk":"A".repeat(1e6)}],
          "outputs": [{"junk":"A".repeat(1e6)}]
        } } ],
    ... repeated thousands of times with unresolvable "unit" references ...
  ]
}
```
Because `wallet.js:959-972` only checks non-emptiness/type, not length or resolvability, each chain passes the shape check, gets hashed, and (for light clients) is stored via `network.js:2393-2401` into `unhandled_private_payments` without ever being resolved, since the referenced `unit` doesn't exist. Repeating this floods the table/memory.

```javascript
function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
		return callbacks.ifError("malformed private chain");
```
