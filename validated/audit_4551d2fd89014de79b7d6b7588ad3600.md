### Title
Webhook signature verification authenticates by `repository.owner.login`/`organization.login` while event handlers act on unrelated fields (`repository.full_name`, `sha`) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` used to validate `X-Hub-Signature` based solely on `repository.owner.login` (falling back to `organization.login`), [1](#0-0) [2](#0-1)  but the handlers that actually mutate Shipit state key off completely different, independently-attacker-controlled fields of the same JSON body: `PushHandler`/`Handler#stacks` resolve the target `Repository`/`Stack` from `repository.full_name` [3](#0-2) , and `StatusHandler` matches purely on commit `sha` with **no repository check at all** [4](#0-3) . Because `verify_webhook_signature` short-circuits to `true` when an organization's `webhook_secret` is blank/unset [5](#0-4) , an attacker who can reach the public `/events` (or equivalent) webhook endpoint with a payload claiming to be from any configured-but-secretless organization can supply arbitrary `repository.full_name` or `sha` values that target a completely different, secured organization's stack/commit.

### Finding Description
The binding that should hold is: *the organization whose webhook_secret authenticates the request* == *the repository/commit the payload is permitted to affect*. This binding is broken:

1. `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` or `params.dig('organization','login')` and asks `Shipit.github(organization: repository_owner)` for a `GitHubApp` to validate the HMAC signature [1](#0-0) .
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is not configured: `return true unless webhook_secret` [5](#0-4) . Shipit explicitly supports multi-org configuration where each org has its own (optional) `webhook_secret` [6](#0-5) , and the example secrets template ships `webhook_secret: # nil` [7](#0-6) , so an unauthenticated org entry is a realistic operator configuration.
3. Once past `verify_signature`, `WebhooksController#create` dispatches the *entire, attacker-supplied* JSON body to handlers [8](#0-7) , and those handlers never re-derive or cross-check the organization used for step 1:
   - `Handler#stacks`/`#repository_name` reads `payload.dig('repository', 'full_name')` — a field entirely independent from the `repository.owner.login` used to select the signing org — to locate the `Repository` and its `Stack`s [3](#0-2) . `PushHandler` uses this to enqueue `GithubSyncJob` with an attacker-controlled `expected_head_sha` against any stack under that `full_name` [9](#0-8) .
   - `StatusHandler` is even more permissive: it looks up `Commit.where(sha: params.sha)` globally, with no repository/organization filter whatsoever, and creates a commit status from fully attacker-controlled `state`/`description`/`target_url`/`context` [10](#0-9) . `Status#enable_ci_on_stack` and `Commit#create_status_from_github!` feed directly into deploy-gating logic (CI-status/deployable checks) [11](#0-10) .

So the equality that should hold — `org(signature) == org(repository acted upon)` — is never checked; `org(signature)` is derived from one payload field while every handler acts on a disjoint payload field.

### Impact Explanation
If any organization configured in `Shipit.github` (a normal, documented multi-tenant deployment pattern [12](#0-11) ) has no `webhook_secret` set, an unprivileged network attacker can send a forged webhook that:
- claims `repository.owner.login`/`organization.login` = the secretless org (so `verify_webhook_signature` trivially returns `true`), while
- setting `repository.full_name` or `sha` to target a stack/commit that belongs to a *different, properly secured* organization.

This lets the attacker inject fabricated commit-status webhooks (`state: "success"`) for arbitrary commit SHAs tracked by Shipit — a `Status` record feeds directly into `deployable?`/CI-gating decisions used before triggering a deploy — enabling an unauthorized deploy path, and can also force spurious `GithubSyncJob` triggers against arbitrary tracked stacks. This matches the "unauthorized deploy" Critical-impact criterion.

### Likelihood Explanation
Likelihood depends on operator configuration: it requires at least one organization entry in `Shipit.github` with a blank/absent `webhook_secret` while other organizations/stacks are considered trusted. This is not a hypothetical edge case — the maintained example secrets templates ship `webhook_secret: # nil` by default [7](#0-6) , and the code path explicitly treats a missing secret as "signature always valid" rather than "org not onboarded" [5](#0-4) . No GitHub credentials, Shipit session, or `ApiClient` token are required — only network access to the public webhooks endpoint.

### Recommendation
- After signature verification succeeds, re-derive the acting repository/organization strictly from the same verified `repository.owner.login`/`organization.login` used to select the `GitHubApp`, and reject/ignore any handler action whose target repository (`repository.full_name`) or resolved commit's stack does not belong to that same organization.
- In `StatusHandler`, scope the `Commit.where(sha: ...)` lookup by the verified organization/repository instead of matching globally by `sha`.
- Reconsider `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret` default — an org without a configured secret should fail closed (reject the webhook) rather than implicitly authenticate every payload.

### Proof of Concept
Preconditions: Shipit configured with two GitHub orgs, e.g. `trusted-org` (has `webhook_secret` set) with a tracked stack for `trusted-org/prod-repo`, and `no-secret-org` (no `webhook_secret` configured, as in the shipped template) [7](#0-6) .

1. Attacker POSTs to `/webhooks` (the `WebhooksController#create` route) with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or any junk value):
```json
{
  "sha": "<sha of a commit tracked under trusted-org/prod-repo>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "organization": { "login": "no-secret-org" }
}
```
2. `verify_signature` resolves `repository_owner` = `"no-secret-org"` via the `organization` fallback [2](#0-1) , calls `Shipit.github(organization: "no-secret-org").verify_webhook_signature(...)`, which returns `true` immediately because that org has no `webhook_secret` [5](#0-4) .
3. `create` dispatches the payload to `StatusHandler.call(params)`, which runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no organization/repository filter [4](#0-3) , creating a forged `success` status on the targeted commit belonging to `trusted-org/prod-repo` — an organization whose signature secret the attacker never possessed or satisfied.

This demonstrates the break of the "organization that authenticated" vs "repository/commit that is written" binding, using only unauthenticated network access to the webhook endpoint.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

module Shipit
  class Status < Record
    include Common
    include DeferredTouch

    STATES = %w[pending success failure error].freeze
    enum :state, STATES.zip(STATES).to_h

    belongs_to :stack, required: true
    belongs_to :commit, required: true

    deferred_touch commit: :updated_at

    validates :state, inclusion: { in: STATES, allow_blank: true }, presence: true

    after_create :enable_ci_on_stack
    after_commit :schedule_continuous_delivery, :broadcast_update, on: :create

    delegate :broadcast_update, to: :commit

    class << self
      def replicate_from_github!(stack_id, github_status)
        find_or_create_by!(
          stack_id:,
          state: github_status.state,
          description: github_status.description,
          target_url: github_status.target_url,
          context: github_status.context,
          created_at: github_status.created_at
        )
      end
    end

    private

    def enable_ci_on_stack
      commit.stack.enable_ci!
    end

    def schedule_continuous_delivery
      commit.schedule_continuous_delivery
    end
  end
end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
