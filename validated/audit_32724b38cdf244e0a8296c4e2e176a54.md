### Title
Unvalidated swap-route bytes let injected venues execute arbitrary token calls under the caller's authorization - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The livestatus injection class (attacker-controlled input interpreted as commands without neutralization) maps onto XOXNO Lending's swap strategies: the controller forwards caller-supplied `StrategySwap` bytes verbatim to the router, which dispatches them as contract invocations to whatever pool/token addresses the payload names. Neither the controller nor the router validates or allowlists those addresses, so a crafted route is an injected command stream executed inside the victim's `require_auth` tree.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` accepts a `StrategySwap` blob, grants the router one exact input-transfer authorization (`authorize_transfer_as_current`, line 34), and invokes `router.execute_strategy(&controller, &amount_in, swap)` (line 37) without inspecting the payload. It only measures `token_in`/`token_out` balance deltas afterwards. The documented behavior in `docs/explanation/threat-model.md:154-165` confirms the router "calls the pool and token addresses its payload names and keeps no allowlist of them," so a route can put arbitrary third-party code on the call stack *below the caller's authorization entry*. That code can call `token.transfer(victim, attacker, victim_balance)` and it records as a child of the victim's signed auth tree — proven by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:195-227`, where a malicious `swap_collateral` route drains Alice's entire wallet balance of an unrelated token to the attacker while the swap itself still passes output checks. The same exposure applies to `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, and any receiver-driven swap inside `flash_position`, plus direct `execute_strategy` calls.

### Impact Explanation
Theft of user funds beyond the routed amount: the attacker receives tokens straight from the victim's wallet (the test drains `WALLET_BALANCE` to `s.attacker` at line 224-225). The controller's measured-output and risk gates do not bound the loss because the stolen transfer never touches the controller's balances.

### Likelihood Explanation
Any unprivileged account can submit these entrypoints. Exploitation requires the victim to sign a route they did not decode — the realistic path is a malicious/compromised quote service or an attacker-supplied route fed to a contract or wallet that signs the simulated auth tree without validating child invocations. Recording-mode simulation surfaces the malicious child exactly as a legitimate transfer, so a non-decoding signer authorizes it.

### Recommendation
Validate the route before executing: decode `StrategySwap` in the controller (or router) and reject payloads whose token/pool addresses are not the declared `token_in`/`token_out` or a governance-allowlisted venue set; alternatively require routers to enforce a venue registry. At minimum, wallets/SDKs must decode `routeXdr` and refuse any auth tree containing children beyond the single expected input transfer.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:166-227`: a `swap_collateral` route through a rogue "pool" contract records `token.transfer(alice, attacker, WALLET_BALANCE)` as a child of Alice's signed `swap_collateral` auth entry and executes it; Alice's unrelated-token wallet goes to 0 while the swap's measured output still succeeds.
