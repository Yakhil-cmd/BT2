### Title
Direct token transfers to `LiquidityPool` are permanently locked - (File: contracts/pool/src/cache/cash.rs)

### Summary
Tokens sent directly to the pool contract increase its SAC balance but not its tracked `cash`, while every withdrawal, borrow, revenue claim, and refund is limited to the accounting cash book. Because all pool mutators are restricted to the controller and no sweep or donation-crediting path exists, an unsolicited transfer remains permanently stranded. [1](#0-0) [2](#0-1) 

### Finding Description
The pool treats `cash` as an accounting ledger rather than deriving available funds from `token::Client::balance`; `credit_cash` is the only path that increases the book, while `debit_cash` enforces `self.cash >= amount`. [3](#0-2)  A direct token transfer to `env.current_contract_address()` invokes no pool entrypoint and therefore cannot call `credit_cash`, but the received asset becomes part of the pool's physical custody. [4](#0-3) 

Normal withdrawals burn supply shares, check `cache.cash`, and debit only the accounted net transfer, so they can never intentionally consume an unbooked surplus. [5](#0-4)  Protocol revenue claims likewise cap the payout to claimable revenue and then debit that amount from `cash`; they do not compare the result against the pool's real token balance or claim an excess. [6](#0-5)  `recapitalize` credits at most the computed backing shortfall and returns the remainder to the payer, so it also cannot convert a pre-existing donation into cash. [7](#0-6) 

Every state-mutating ABI method is protected by `#[only_owner]`, and the deployed owner is normally the controller; the token sender has no permissionless pool entrypoint that can rescue or book the surplus. [8](#0-7) [9](#0-8) [10](#0-9) 

### Impact Explanation
An unprivileged user who transfers any listed asset—including native XLM through its Stellar Asset Contract—to the pool address permanently loses those tokens. [4](#0-3)  After all tracked cash has legitimately been paid out, the pool can still hold the donated balance because no accounting state references it and no callable function transfers it. [5](#0-4) [1](#0-0) 

This is permanent freezing of funds rather than a temporary liquidity shortfall: token-level custody increases, but the only reserve used by exits does not. [3](#0-2) 

### Likelihood Explanation
The trigger is a single direct `token.transfer(sender, pool, amount)` to a known contract address, and any unprivileged token holder can perform it without pool authorization. [4](#0-3)  Such transfers are ordinarily accidental rather than economically useful to the sender, so occurrence likelihood is lower than an exploitative attack, but the loss is deterministic once the transfer succeeds. [1](#0-0) [11](#0-10) 

### Recommendation
Add an owner-governed surplus-recovery path that computes the aggregate surplus as `token.balance(pool) - sum(cash across all markets sharing that asset)` and transfers only that surplus to a governance-controlled recipient. [4](#0-3) [1](#0-0)  The calculation must aggregate every `(hub_id, asset_id)` market sharing the same physical pool balance, rather than subtracting only one market's `cash`. [12](#0-11) 

### Proof of Concept
1. Create a market and let its tracked `cash` equal its token balance. [12](#0-11) 
2. An unprivileged sender calls the listed token's `transfer(sender, pool, D)` directly; the pool receives `D` but no pool code runs and `cash` remains unchanged. [4](#0-3) 
3. Exit paths still enforce `cash >= amount` and debit only the accounted amount, so after all `cash` is withdrawn the physical balance is still `D`. [13](#0-12) [5](#0-4) 
4. The sender cannot call `withdraw`, `claim_revenue`, `recapitalize`, or any other mutation because those ABI methods are `#[only_owner]`, leaving `D` unrecoverable. [9](#0-8) [10](#0-9) [14](#0-13)

    /// Panics if cash reserves are below `amount`.
    pub(crate) fn require_reserves(&self, amount: i128) {
        assert_with_error!(
            self.env,
            self.cash >= amount,
            CollateralError::InsufficientLiquidity
        );
    }

    /// Increases accounting cash by `amount`. Rejects negative amounts and overflow.
    pub(crate) fn credit_cash(&mut self, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        self.cash = self
            .cash
            .checked_add(amount)
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));
    }

    /// Decreases accounting cash by `amount`. Rejects negative amounts or
    /// insufficient reserves.
    pub(crate) fn debit_cash(&mut self, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        self.require_reserves(amount);
        self.cash = self
            .cash
            .checked_sub(amount)
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));
    }

/// Enforces reserve, utilization, and solvency guards, then debits cash for
/// the net transfer. Liquidations and footprint-only closes skip utilization.
fn gate_and_debit(env: &Env, cache: &mut Cache, net_transfer: i128, skip_utilization_check: bool) {
    cache.require_reserves(net_transfer);

    if !skip_utilization_check {
        guards::require_utilization_below_max(env, cache);
    }
    guards::require_supply_for_debt(env, cache);
    cache.debit_cash(net_transfer);
}

pub(crate) fn accounting(env: &Env, hub_asset: HubAssetKey) -> RevenueOutcome {
    let mut cache = ops::renewed_market(env, &hub_asset);

    let net_transfer = cache.burn_claimable_revenue();

    guards::require_utilization_below_max(env, &cache);
    guards::require_supply_for_debt(env, &cache);
    cache.debit_cash(net_transfer);

    cache.commit();
    RevenueOutcome {
        cache,
        mutation: PoolAmountMutation {
            actual_amount: net_transfer,
        },
    }
