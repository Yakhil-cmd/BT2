### Title
Legacy `pattern`-only rules silently fail to block Bash commands when `event` is omitted - ([File: plugins/hookify/core/config_loader.py])

### Finding Description
`Rule.from_dict` infers the condition's `field` from the rule's `event` value using `event = frontmatter.get('event', 'all')` and then `if event == 'bash': field = 'command' ... else: field = 'content'` [1](#0-0) . If a rule author writes a legacy `pattern`-only rule intended to guard Bash commands but omits the `event: bash` key, `event` defaults to `'all'`, so the inferred `field` becomes `'content'` instead of `'command'`.

The rule is still loaded and evaluated against Bash invocations because `load_rules` only skips rules when `rule.event != 'all' and rule.event != event`, and a rule with `event == 'all'` passes that filter for every hook event, including `bash` [2](#0-1) .

During evaluation, `RuleEngine._check_condition` calls `_extract_field('content', 'Bash', tool_input, ...)` [3](#0-2) . In `_extract_field`, `'content'` is not a key of Bash's `tool_input` (which only has `command`), the Stop/UserPromptSubmit special cases don't apply, and the `tool_name == 'Bash'` branch only special-cases `field == 'command'` — there is no fallback for `field == 'content'` under `Bash` [4](#0-3) . The function therefore returns `None`, causing `_check_condition` to immediately return `False` [5](#0-4) , so `_rule_matches` returns `False` and the rule silently never fires — regardless of whether the Bash command actually matches the pattern text.

### Impact Explanation
A guard rule authored (e.g., in a project's `.claude/hookify.*.local.md`) to block dangerous Bash commands (`rm -rf`, exfiltration commands, etc.) using the legacy `pattern:` shorthand without an explicit `event: bash` key becomes a silent no-op: `action: block` never triggers, and Claude Code (or an unprivileged actor able to get the agent to run a Bash command, e.g. via prompt injection from repo content) can execute the exact command the rule was meant to stop, with no warning or block emitted. This is a deny-by-default / hook-enforcement bypass matching an approval/guard-bypass impact class.

### Likelihood Explanation
This requires no special privilege beyond authoring/using a legacy-style hookify rule (a common, documented-looking shorthand) without the `event` key — an easy and plausible authoring mistake since the top-level filter in `load_rules` makes such rules appear "active" for all events, giving a false sense that the guard applies. Once such a misconfigured rule exists, any Bash command matching the intended pattern will bypass the guard deterministically and repeatably, with no error surfaced to the user.

### Recommendation
Make legacy-pattern field inference depend on the actual tool/hook context at evaluation time rather than a possibly-defaulted `event` field, or emit a loud warning/error when `pattern` is combined with `event: all` (or missing `event`) recommending explicit conditions. Alternatively, have `_extract_field` fall back to checking `tool_input.get('command')` when `tool_name == 'Bash'` and `field == 'content'`, or reject/normalize `pattern`-only rules at load time by requiring `event` to be explicit when using the legacy `pattern` shorthand.

### Proof of Concept
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

# Legacy rule intended to block "rm -rf" via Bash, event omitted
frontmatter = {
    "name": "block-rm-rf",
    "enabled": True,
    "pattern": r"rm\s+-rf",
    "action": "block",
    # NOTE: no 'event' key -> defaults to 'all' -> field inferred as 'content'
}
rule = Rule.from_dict(frontmatter, "Dangerous rm -rf blocked!")
assert rule.conditions[0].field == 'content'  # bug: should be 'command' for Bash intent

engine = RuleEngine()
input_data = {
    "tool_name": "Bash",
    "tool_input": {"command": "rm -rf /important/data"},
    "hook_event_name": "PreToolUse",
}
result = engine.evaluate_rules([rule], input_data)
assert result == {}  # BUG: dangerous command is NOT blocked despite matching intended pattern
```
Expected (correct) behavior: the rule should block the command (`result` containing `permissionDecision: deny`). Actual behavior confirms the bypass: `result == {}`.
