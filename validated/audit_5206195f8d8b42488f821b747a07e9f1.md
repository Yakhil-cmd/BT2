### Title
CCMenu token authorized for one stack is honored for any stack requested in the URL, breaking the token-stack authorization binding - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The CI radiator ("CCMenu") feature mints a `read:stack` `ApiClient` token for a user and embeds it in a URL scoped to one specific stack, but the controller that serves that URL never checks that the token is actually bound to the requested stack. As a result, the token can be replayed against the `stack_id` of any stack in the Shipit instance to read that stack's deploy state.

### Finding Description
`CCMenuUrlController#client` mints (or reuses) an `ApiClient` per user without ever setting `stack:` on it: [1](#0-0) 
This client is embedded as a `token` query param in a URL that is scoped by `stack_id` in its path, e.g. `/ccmenu/*stack_id`, intended for one particular stack's public/CI radiator display: [2](#0-1) 

`Api::CCMenuController` authenticates using only the `token` param, bypassing the normal basic-auth flow, and then resolves the target stack directly from `params[:stack_id]` via the unscoped `Stack.from_param!`, instead of the scoped `stacks.from_param!` helper used everywhere else in `Api::BaseController`: [3](#0-2) 

Compare with the scoped lookup in the base controller, which restricts stacks to `current_api_client.stack_id` when the client has one set: [4](#0-3) 

Because the `ApiClient` created by `CCMenuUrlController#client` never has `stack_id` populated, `current_api_client.stack_id?` is false, so even the scoped helper degenerates to `Stack.all`; and `Api::CCMenuController#stack` doesn't even use that helper — it calls `Stack.from_param!(params[:stack_id])` unconditionally. The binding that should hold is: `token.authorized_stack == stack_requested_in_url`. Instead, any valid CCMenu token issued to a user for stack A can be used with a different `stack_id` in the path to read stack B's status, for every stack the instance manages, regardless of which stack the token/URL was generated for.

### Impact Explanation
This is an unauthenticated read of stack/deploy state across stack boundaries: a token intentionally scoped (by design/URL) to expose one project's CI radiator status is usable to read the deploy status, latest deploy timestamp, and running/success state of every stack hosted on the Shipit instance — including stacks the token holder was never granted `stacks` visibility for via the UI. CCMenu URLs are commonly embedded in public dashboards/radiators, so leaking this token effectively leaks cross-stack deploy state for the whole instance, matching the "unauthenticated read of stack state ... or deploy output" High-impact category.

### Likelihood Explanation
Likelihood is high: no privileged access is required beyond having any single legitimate CCMenu token (which by design is meant to be embeddable in unauthenticated, non-secret CI dashboard URLs). The attacker only needs to change the `stack_id` segment of the URL path to a different, arbitrary stack identifier; no signature or per-stack claim is checked.

### Recommendation
Bind the `ApiClient` created for CCMenu to the specific stack (`ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(...)`), and make `Api::CCMenuController#stack` use the scoped `stacks.from_param!(params[:stack_id])` (inherited from `Api::BaseController`) instead of the unscoped `Stack.from_param!`, so the token's authorized stack must equal the stack being requested.

### Proof of Concept
1. As user Alice, visit stack A's settings page, which calls `CCMenuUrlController#fetch` and returns a URL like `/ccmenu/ownerA/repoA/production?token=<TOKEN>` (token minted with `permissions: [read:stack]`, no `stack_id`). [5](#0-4) 
2. Take `TOKEN` and request `/api/stacks/ownerB/repoB/production/ccmenu?token=<TOKEN>` for an unrelated stack B that Alice was never granted access to via the UI.
3. `authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])`: [6](#0-5) 
4. `stack` resolves `params[:stack_id]` unconditionally against `Stack.from_param!`, returning stack B despite the token never having been associated with stack B: [7](#0-6) 
5. `show` renders stack B's CCMenu XML (deploy status/timestamp), confirming cross-stack disclosure using a token minted for stack A. [8](#0-7)

  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end
