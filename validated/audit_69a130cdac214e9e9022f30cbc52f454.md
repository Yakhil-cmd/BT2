## Title
Unauthenticated commit-message trailer lets any GitHub committer bind arbitrary GitHub-registered users as the "author" of a `Shipit::Commit` - (File: `app/models/shipit/user.rb`)

### Summary
`Shipit::User.find_or_create_author_from_github_commit` parses the raw git commit message for a `Merge-Requested-By: <login>` trailer and, if found, blindly calls `find_or_create_by_login!(match_info[1])` to set that user as the commit's author, without checking that the login actually authored, committed, or has any relationship to the commit. Because this trailer is attacker-controlled free text inside `commit.commit.message`, any GitHub user who can get a commit fetched by Shipit (via a normal push, or via a pull request whose head commit gets fetched through `MergeRequest#github_pull_request=` / `find_or_create_commit_from_github_by_sha!`) can write `Merge-Requested-By: <victim-login>` in their own commit message and have Shipit attribute that commit's authorship to the victim's existing `Shipit::User` row.

### Finding Description
The intended binding is: `Commit#author == the GitHub account that actually authored the commit` (i.e., `commit.commit.author`/`commit.author`). Instead, the code path is: [1](#0-0) 

`Commit.from_github` calls this for every commit fetched from GitHub, with no distinction between commits Shipit itself created (its own `merge_pull_request` call with a message built from `MergeRequest#merge_message`) and commits pushed by ordinary contributors: [2](#0-1) 

The `MERGE_REQUEST_FIELD` trailer (`"Merge-Requested-By"`) is only ever *written* by Shipit in `MergeRequest#merge_message`, for commit messages of merges Shipit itself performs: [3](#0-2) 

However, `find_or_create_author_from_github_commit` has no way to verify that a given commit message's `Merge-Requested-By` trailer was produced by Shipit's own merge action rather than typed by an arbitrary committer. Any commit whose message contains that exact line will be matched by the regex regardless of provenance, and `find_or_create_by_login!` will look up or auto-vivify a `Shipit::User` for that login and bind it as `author`.

Commits reach `Commit.from_github` through multiple paths that operate on attacker-influenced repositories/branches:
- Ordinary pushes synced via `GithubSyncJob#append_commit` → `stack.commits.create_from_github!` [4](#0-3) 
- Pull request head/base commits fetched in `MergeRequest#github_pull_request=` via `find_or_create_commit_from_github_by_sha!`, which calls `stack.commits.create_from_github!(github_commit, attributes)` [5](#0-4) [6](#0-5) 

For the PR path, the attacker fully controls the commit message on their own fork branch before opening the PR; when Shipit later fetches that head commit (via webhook-triggered `refresh!`), `Commit.from_github` will run the vulnerable parsing on attacker-controlled text and can bind an arbitrary existing `login` (e.g., a victim maintainer or the user recorded in `Shipit.github_teams`) as that commit's `author`.

None of the listed guards prevent this: `verify_signature`/webhook signature checks only authenticate that the payload came from GitHub, not that the commit *content* is trustworthy; `force_github_authentication`/`User#authorized?`/`require_permission!` gate Shipit UI/API actions, not commit ingestion; there is no model validation on `Commit#message` content relevant to this trailer; and `identify_merge_request` in `commit.rb` only overrides `author` from the trusted `merge_request.merge_requested_by` association (set via the authenticated `request_merge!` flow) — it does not protect against `find_or_create_author_from_github_commit` being invoked first with forged data, and for a plain (non-merge) commit `identify_merge_request` doesn't fire at all since `message_parser.pull_request?` is false, leaving the forged `author` binding untouched: [7](#0-6) 

### Impact Explanation
The practical effect is limited to **who is recorded as the `author` (or `committer`) of a `Shipit::Commit` row**. I was not able to fully verify within this investigation whether `Commit#author`/`committer` is consumed anywhere in an authorization decision (e.g., gating a deploy, a merge, or team membership) — grepping `app/models/shipit/stack.rb` showed 16 `author` matches but I did not get to inspect them before running out of iterations, and `MergeRequest#merge!`/`request_merge!` use the separate `merge_requested_by` association (populated only through the authenticated merge-request flow), not `Commit#author`. Based on what was traced, the concrete, demonstrable impact is: a false attribution record in the `commits` table (and any UI/API surface — e.g. `repositories_contributed_to`, `stacks_contributed_to`, commit listings — that display `commit.author`) that can make an attacker's own commit look like it was authored by a chosen existing user. Whether this rises to "Critical/High" per the given rubric (forged deploy/merge provenance or authorization escalation) depends on downstream consumers of `Commit#author` that were not fully confirmed in this pass.

### Likelihood Explanation
Preconditions are low-cost for the attacker: they need only a GitHub account, a fork of the target repository, and the ability to open a pull request or push a branch with a chosen commit message — capabilities explicitly granted to "unprivileged attackers" per the rules. No Shipit secrets, session, or team membership is required. The victim login only needs to be resolvable via `Shipit.github.api.user(login)` (any public GitHub user) for `find_or_create_by_login!` to succeed. This is repeatable against any stack/repository the attacker can open a PR against or push a commit into (subject to normal GitHub push/PR permissions).

### Recommendation
Restrict `find_or_create_author_from_github_commit`'s `Merge-Requested-By` trailer handling to commits that Shipit itself is certain to have generated — e.g., only trust the trailer when the commit SHA matches a merge commit Shipit created via `MergeRequest#merge!` (compare against `merge_request.head`/stored merge SHA, or record the expected merge commit SHA at merge time and match on that), rather than regex-matching arbitrary fetched commit message text. Do not derive authorship from free-text commit message content for commits whose provenance cannot be cryptographically or structurally verified against Shipit's own merge action.

### Proof of Concept
Minitest plan (`test/models/users_test.rb`-style, no live GitHub):
```ruby
test "find_or_create_author_from_github_commit does not attribute authorship from a forged commit message trailer" do
  victim = shipit_users(:walrus) # existing fixture login, e.g. "walrus"
  attacker_login = "attacker"

  github_commit = stub(
    author: stub(id: 999_999, login: attacker_login, presence: stub(id: 999_999, login: attacker_login)),
    commit: stub(
      message: "Some innocuous change\n\nMerge-Requested-By: #{victim.login}\n",
      author: stub(id: 999_999, login: attacker_login)
    )
  )

  resolved_author = Shipit::User.find_or_create_author_from_github_commit(github_commit)

  # Broken binding under test: resolved_author == victim, even though victim never
  # authored/committed/pushed this commit.
  assert_not_equal victim.id, resolved_author.id,
    "author should be derived from the actual GitHub committer, not a message trailer"
  assert_equal attacker_login, resolved_author.login
end
```
This test would currently fail (asserting `assert_not_equal` fails) because `find_or_create_author_from_github_commit` matches the forged trailer and returns `find_or_create_by_login!(victim.login)`.

    def self.find_or_create_author_from_github_commit(github_commit)
      if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
        begin
          return find_or_create_by_login!(match_info[1])
        rescue Octokit::NotFound
          # Corner case where the merge-requested-by user cannot be found (renamed/deleted).
          # In this case we carry on and search for the commit author
        end
      end
      find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
    end

    def find_or_create_commit_from_github_by_sha!(sha, attributes)
      if commit = stack.commits.by_sha(sha)
        commit
      else

      end

      retry
    end
