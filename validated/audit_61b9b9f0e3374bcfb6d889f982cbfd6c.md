### Title
Unfunded `recapitalize` drains pool custody without debiting the cash book, permanently breaking withdrawals - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The audit-issue class is *accounted state updated on only one path diverges from the real on-chain state, so a guard that trusts the accounted state permanently rejects legitimate transactions*. In HatsSignerGate, `enabledModuleCount` is only bumped by `enableNewModule`, so a module enabled by another module makes `checkAfterExecution` revert forever. In XOXNO Lending, the pool keeps a `cash` book (scaled accounting of tokens held in custody) that is debited only on book-aware exits, while `recapitalize` performs a raw token transfer out of the pool without debiting the book. The book then overstates custody, the pool's own liquidity guards keep approving exits, and every withdrawal fails inside the SAC transfer — an unprivileged caller can put the market into this state with a single `recapitalize` call.

### Finding Description
The pool contract tracks `cash` in its market state as the accounting view of tokens custodied for suppliers. Withdrawals are admitted by book-based guards (`InsufficientLiquidity` / `PoolInsolvent` checks) that read `cash`, not the actual token balance, and then pay out with a Stellar Asset Contract `transfer` from the pool address. `recapitalize` (permissionless per the controller surface) executes a refund leg that calls `token.transfer(pool -> recipient, amount)` without requiring a matching input transfer and, critically, without decrementing `cash`. The regression test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` in `contracts/pool/tests/flows.rs:3408-3482` demonstrates the exact sequence: a supplier deposits 10 tokens (book `cash == token.balance(pool)`), `recapitalize(hub_asset, payer, custody)` drains the entire token balance to 0, and `cash` still reads `>= deposit`. A subsequent `withdraw` clears both pool guards and then reverts with the SAC `BalanceError = 10` — i.e., the contract admits exits it cannot pay.

### Impact Explanation
Temporary-to-permanent freezing of supplier funds. Once the book overstates custody, every withdraw whose payout exceeds the real token balance passes the pool's solvency checks and then aborts inside the token transfer, rolling back. Suppliers cannot exit, liquidations that pay out in the drained asset cannot settle, and downstream flows relying on pool custody (flash loans measured by exact balance) are broken. Unless someone voluntarily re-funds the pool out-of-band, the shortfall is unrecoverable because the accounting never recorded the deficit — the protocol's own solvency bookkeeping believes it is whole. An unprivileged attacker can trigger this at zero cost, and it also happens accidentally through ordinary `recapitalize` usage.

### Likelihood Explanation
`recapitalize` is a permissionless entrypoint taking `(hub_asset, to, amount)`; any address can call it with `amount` up to the pool's full token balance. No privileged role, oracle condition, or timing window is required — the divergence is created in a single call and persists until external reimbursement. The bug is structural: the refund leg spends custody the book does not track, so it fires on every invocation that isn't pre-funded.

### Recommendation
Make `recapitalize` custody-consistent with the cash book before transferring out: either (a) require the payer to transfer `amount` into the pool in the same transaction (measured by balance delta, as the flash/strategy paths already do), or (b) debit `cash` (and proportionally `supplied`/reserves) by the refunded amount so the book never claims tokens that left custody. Add a post-transfer assertion `token.balance(pool) >= cash` or fold the payout into the same `require_reserves`-checked path used by `withdraw`, so an underfunded refund reverts instead of corrupting the book.

### Proof of Concept
1. Supplier calls `supply` for 10_000_000_000 units of the asset; pool state `cash == token.balance(pool) == 10e9`.
2. Attacker (any address) calls `Controller/Pool::recapitalize(hub_asset, attacker, 10e9)`. The pool transfers the full balance to `attacker`; `token.balance(pool) == 0` while `state.cash` still reads `>= 10e9`.
3. Supplier calls `withdraw(receiver, scaled_amount, i128::MAX)`. The liquidity/solvency guards read `cash`, approve the exit, and the SAC `transfer` reverts with `BalanceError (10)`; the withdrawal — and every subsequent withdrawal above the real balance — permanently fails. This is exactly the flow encoded in `contracts/pool/tests/flows.rs:3408-3482`.
