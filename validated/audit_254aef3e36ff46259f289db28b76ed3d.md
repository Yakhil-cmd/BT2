### Title
Cross-repository status forgery leads to unauthorized merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, without checking that the webhook's authenticated `repository.full_name` matches the `stack.github_repo_name` that owns that commit. Since a `status` webhook's signature is verified only against the sending organization/repo's own secret via `Shipit.github(organization: repository_owner).verify_webhook_signature` in `app/controllers/shipit/webhooks_controller.rb`, an attacker who controls their own repository (e.g., a fork sharing a commit SHA with the victim's PR head) can post a genuine, correctly-signed `status` event for that shared SHA and have it applied to the victim stack's commit.

### Finding Description
The broken binding is: `payload['repository']['full_name']` (the repo that produced/authenticated the webhook) MUST equal `stack.github_repo_name` for every `Commit`/`Stack` mutated as a result of that webhook. `StatusHandler#process` never enforces this: [1](#0-0) 

versus the base class's repository-scoped helper it deliberately ignores: [2](#0-1) 

Compare with `PushHandler#process` and `CheckSuiteHandler#process`, which both correctly scope through `stacks` (derived from `Repository.from_github_repo_name(repository_name)`): [3](#0-2) [4](#0-3) 

Signature verification in `WebhooksController#verify_signature` only proves the payload came from GitHub for the organization named in the payload's own `repository.owner.login` — it says nothing about which specific commits that organization is allowed to influence in Shipit: [5](#0-4) 

Because git commit SHAs are content-addressed and identical commits are routinely shared across forks (an attacker's fork of the victim repository legitimately contains the same commit object/SHA as the victim's open PR head), the attacker can trigger a real `status` event from their own repository for that shared SHA. GitHub signs this event with the attacker's own org secret, so `verify_webhook_signature` passes legitimately. `StatusHandler#process` then does `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every matching `Commit` row across the entire installation, regardless of which stack/repository owns it: [6](#0-5) 

which calls `Status.replicate_from_github!`, creating a `success` `Status` on the victim's commit: [7](#0-6) 

If that commit is the `head` of a pending `MergeRequest` in the victim's merge queue with a previously missing/failing check, `MergeRequest#all_status_checks_passed?` now evaluates `StatusChecker.new(head, head.statuses_and_check_runs, ...).success?` as true: [8](#0-7) 

`ProcessMergeRequestsJob#perform` then calls `merge_request.merge!`, which invokes `stack.github_api.merge_pull_request(stack.github_repo_name, ...)` — merging the victim's PR using Shipit's own GitHub credentials for the victim's repo: [9](#0-8) [10](#0-9) 

No other guard intervenes: `ExplicitParameters` only validates payload shape, not repository identity; `drop_unhandled_event`/`check_if_ping` are irrelevant; `force_github_authentication`, `User#authorized?`, `require_permission!`, and `Shipit.github_teams` apply only to the web UI/API, not to unauthenticated GitHub webhooks; and `Handler#stacks` — the one mechanism that would enforce the repo binding — is simply never called by `StatusHandler`.

### Impact Explanation
An unprivileged GitHub user who owns (or forks) a repository sharing a commit with a victim's Shipit-tracked PR can forge a passing CI status on the victim's commit and cause Shipit to autonomously execute `merge_pull_request` against the victim's repository, using Shipit's own GitHub App credentials — an unauthorized merge triggered by a payload authenticated for a different repository. This is repeatable against any stack/repository in the Shipit installation whose merge queue contains a pending PR sharing a commit SHA with a repo the attacker controls (most straightforwardly, any fork of the target). This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Preconditions are modest and realistic: the attacker needs any GitHub repository capable of emitting a real, GitHub-signed `status` webhook to the Shipit host (their own fork or repo, connected to the same GitHub App/organization integration Shipit trusts), and a target stack must have a `MergeRequest` pending in the queue whose `head` commit is currently missing/failing a required status. Sharing an identical commit SHA across a fork and the upstream victim repo is the normal, expected behavior of git/GitHub forks (no hash collision needed), making this trivially achievable by forking the victim repo before or during a pending PR. No secrets, sessions, or elevated GitHub permissions are required.

### Recommendation
In `StatusHandler#process` (and any other handler bypassing `stacks`), scope the `Commit` lookup to only commits belonging to stacks whose `github_repo_name` matches the webhook's own `payload['repository']['full_name']`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the pattern already used by `PushHandler` and `CheckSuiteHandler`.

### Proof of Concept
Minitest plan (model/job level, no live GitHub):
1. Set up `stack` (victim), `commit = stack.commits.create!(sha: 'sameshasameshasameshasameshasameshasha1')`, and `merge_request` with `head: commit`, `merge_status: 'pending'`, and no passing status yet (assert `merge_request.all_status_checks_passed?` is `false`).
2. Build a `status` webhook payload whose `repository.full_name` is `"attacker/other-repo"` (a repo unrelated to `stack.github_repo_name`) but whose `sha` equals `commit.sha`, with `state: 'success'`.
3. Stub `GithubHook#verify_signature` (or `Shipit.github(organization: 'attacker').verify_webhook_signature`) to return `true`, simulating a legitimately signed webhook from the attacker's own org.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level concerns already covered by the signature stub).
5. Assert `commit.statuses.reload.last.state == 'success'` even though `payload['repository']['full_name'] != stack.github_repo_name` — this is the broken equality.
6. Assert `merge_request.reload.all_status_checks_passed?` is now `true`.
7. Stub `stack.github_api.expects(:merge_pull_request).with(stack.github_repo_name, merge_request.number, anything, has_entries(sha: commit.sha)).once.returns(true)`.
8. Run `ProcessMergeRequestsJob.new.perform(stack)` and assert the `merge_pull_request` expectation was satisfied, proving an unauthorized merge occurred from a cross-repository, foreign status.
