### Title
Cross-organization webhook forgery lets any onboarded org's webhook secret alter another org's stack state - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify the incoming payload against using a field taken from *inside* the same untrusted, attacker-suppliable JSON payload (`repository.owner.login`, falling back to `organization.login`). The individual event handlers (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`) then act on a *different* field of that same payload (`repository.full_name`, or for `StatusHandler`, no repository scoping at all — just a global `sha` lookup) to decide which `Stack`/`Commit` to mutate. Nothing binds "the organization whose secret validated this signature" to "the repository/stack that is actually written to."

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/org context purely from payload content: [1](#0-0) [2](#0-1) 

The HMAC signature (`verify_webhook_signature`) is computed over the entire raw JSON body using whichever org's `webhook_secret` corresponds to `repository_owner`: [3](#0-2) 

Crucially, this only proves the request was signed by *some* org onboarded to this Shipit instance — it does not constrain what other fields inside that same signed body say. `Handler#stacks`/`#repository_name` resolves the target `Stack` from `repository.full_name`, a field entirely independent from `repository.owner.login`: [4](#0-3) 

`PushHandler` and `CheckSuiteHandler` use this `repository_name`-derived `stacks` scope to trigger `sync_github`/`schedule_refresh_check_runs!`: [5](#0-4) [6](#0-5) 

`StatusHandler` is worse: it doesn't even consult `repository_name`/`stacks` — it looks up commits **globally by `sha`** and writes a status onto them, with no repository check whatsoever: [7](#0-6) 

Shipit is explicitly designed to be multi-tenant, with independent orgs each configured with their own `webhook_secret` sharing a single `/webhooks` endpoint: [8](#0-7) 

Because the signature only certifies "signed by *an* onboarded org's secret" and the payload's `repository.full_name` / `sha` used for targeting is unconstrained, an attacker who legitimately administers **any one** onboarded org (Org A) can craft and sign a payload — e.g. a `push` or `check_suite` event — whose `repository.owner.login`/`organization.login` is `"OrgA"` (so it verifies with Org A's own secret) but whose `repository.full_name` names a **different** org/repo (`"OrgB/victim-repo"`), or for `status` events, whose `sha` matches a commit that also exists in a victim's repository (trivially achievable by forking a public repo — git commit SHAs are content-addressed and identical across forks).

This breaks the binding: **organization authenticated (via `repository_owner`) ≠ repository/stack actually written (via `repository.full_name` / global `sha` lookup)**.

### Impact Explanation
This is a cross-repository/cross-organization write via a shared, unprivileged-relative-to-the-victim channel:
- `PushHandler`/`CheckSuiteHandler`: attacker (admin of an unrelated, legitimately onboarded Org A) can force `GithubSyncJob`/`RefreshCheckRunsJob` on a victim org's stack they don't administer, by simply naming the victim's `repository.full_name` in a payload signed with their own org's secret.
- `StatusHandler`: attacker can inject arbitrary CI status (`state`, `context`, `description`, `target_url`) onto a victim's commit object via `Commit#create_status_from_github!`, with **zero** repository-ownership check — this directly manipulates a stack's deploy gating (`required_statuses`/`blocking_statuses` in `DeploySpec`), enabling an unauthorized deploy by faking a passing/green status on a commit the attacker doesn't control.

This satisfies the "cross-repository writes" / "unauthorized deploy" impact criteria.

### Likelihood Explanation
Requires only that the attacker legitimately administers (or has installed the app on) any single org configured on the shared Shipit instance — a low, unprivileged-relative-to-victim bar for any multi-tenant deployment (which is a documented, supported configuration). No access to the victim's secrets, GitHub tokens, or Shipit sessions is needed.

### Recommendation
Bind the verified organization to the payload's repository owner/organization before dispatching to handlers: after `verify_signature` succeeds, re-derive and enforce that `repository.full_name`'s owner segment (and, for `StatusHandler`, the repository the `sha` belongs to) matches `repository_owner`/the org whose secret validated the signature. Reject events where these disagree.

### Proof of Concept
1. Attacker administers `OrgA`, which is legitimately onboarded to the shared Shipit instance with its own `webhook_secret`.
2. Attacker crafts a `push`/`check_suite` JSON body with `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) but `repository.full_name = "OrgB/victim-repo"`, and computes `X-Hub-Signature` using `OrgA`'s `webhook_secret`.
3. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `"OrgA"`, verifies successfully against `OrgA`'s secret ( [1](#0-0) ).
4. `PushHandler#stacks` resolves stacks via `repository.full_name = "OrgB/victim-repo"` ( [4](#0-3) ) and triggers `sync_github` on OrgB's stack that Attacker does not administer.
5. Alternately, for a `status` event, attacker forks a public victim repo (identical commit SHAs), signs a `status` payload with `OrgA`'s secret containing the shared `sha` and `state: "success"`, and `StatusHandler` writes that status onto the victim's `Commit` row globally ( [7](#0-6) ), potentially satisfying `required_statuses` and enabling an unauthorized deploy of the victim's stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
