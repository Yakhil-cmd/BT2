I now have strong evidence for a concrete analog. Found it: `validatePaymentInputsAndOutputs` in `validation.js` (lines 2630-2642) requires that **all** output addresses of a `spender_attested` asset payment be attested, or the entire payment (and thus the entire unit) is rejected as invalid.### Title
DoS: A single unattested/blacklisted recipient in an AA's payout blocks the entire response and permanently freezes the AA (`validatePaymentInputsAndOutputs()` in `validation.js`)

### Summary
`validatePaymentInputsAndOutputs()` validates a whole `payment` message against `spender_attested`-asset rules by checking that *every* output address in the message is attested, and rejects the *entire* payment (and hence the whole unit) if even one output fails the check. When this payment message is generated by an Autonomous Agent (AA) that batches multiple recipients' payouts into a single output array — the normal, expected pattern for oscript AAs (pools, escrows, lotteries, etc.) — one unattestable/blacklisted-style recipient causes the whole unit to be rejected and the AA response to `bounce()`, exactly as in the C4 finding where one bad ERC20 recipient blocked `withdrawExcessRewards()` for everyone.

### Finding Description
In `validation.js`, `validatePaymentInputsAndOutputs()` collects `arrOutputAddresses` for a payment message and, for assets with `spender_attested: true`, performs a single group check: [1](#0-0) 

```js
async.series([
    function(cb){
        if (!objAsset.spender_attested)
            return cb();
        storage.filterAttestedAddresses(
            conn, objAsset, objValidationState.last_ball_mci, arrOutputAddresses, 
            function(arrAttestedOutputAddresses){
                if (arrAttestedOutputAddresses.length !== arrOutputAddresses.length)
                    return cb("some output addresses are not attested");
                cb();
            }
        );
    },
    ...
], callback);
```

This is an all-or-nothing check: if `arrAttestedOutputAddresses.length !== arrOutputAddresses.length`, the *whole* payment message — and therefore the whole unit — is rejected with `"some output addresses are not attested"`, regardless of how many of the other outputs were perfectly valid.

On the AA side, `aa_composer.js`'s `sendUnit()` builds exactly this kind of multi-recipient output array from oscript template logic (pools/withdrawal patterns like the `a_bank_without_percent.oscript` / `order_book_exchange.oscript` samples, generalized to multi-recipient payouts), and if `validateAndSaveUnit()` fails for any reason including this attestation check, the AA calls `bounce()`: [2](#0-1)

`bounce()` discards the entire state update (`objStateUpdate = null`) and refunds only the *current trigger's* sender — it does not, and cannot, fix the underlying condition that caused the failure: [3](#0-2) 

If the AA's persistent state (e.g., a payout queue, list of pool participants, unclaimed balances) still contains the poisoned/unattested address the next time the AA tries to run the payout logic, the exact same payment message will be reconstructed with the same bad output, and `validatePaymentInputsAndOutputs()` will reject it again — every single time. Because oscript AA execution is atomic (a failed unit means no state changes at all, per `executeStateUpdateFormula`/`bounce` above), there is no way for the AA to "skip" the bad recipient and continue serving everyone else: the whole distribution logic is blocked as long as that one address remains in the required output set and unattested.

This directly parallels the reported Solidity bug class: `withdrawExcessRewards()` iterated `transfer()` to every user and reverted entirely if one failed (e.g., blacklisted address), permanently locking funds for all users and the owner. Here, `spender_attested`'s all-or-nothing output check plays the same role as the failing ERC20 `transfer()`, and the AA's atomic-unit semantics play the role of the Solidity `require(success, ...)` that reverts the whole batch.

### Impact Explanation
Any AA that pays out a `spender_attested` asset to multiple addresses in a single payment message (a natural pattern for pools, dividends, lotteries, DEX/order-matching payouts, or any "distribute to N recipients" logic) is vulnerable to a permanent denial of service: a single participant who becomes de-attested (attestor revokes/changes attestation, or never gets attested in the first place while already being a mandatory output recipient) can cause every future payout attempt by that AA to fail identically, freezing the funds and state of *all* other legitimate participants, not just the affected one. Since AA execution is atomic and irreversible per unit, there is no owner/admin escape hatch analogous to code the affected app could add, unless the AA's own oscript logic is specifically designed to isolate and skip poisoned recipients (most naive implementations, matching the common oscript samples, are not).

### Likelihood Explanation
Likelihood is moderate to high in any deployed AA that (a) uses a `spender_attested` asset, and (b) batches multiple output addresses into one payment message driven by persistent state (e.g., an array/list of participant addresses). An attester revoking attestation for one participant, or a participant address simply never becoming attested while already recorded in the AA's payout state, is a normal, low-cost, and even accidental occurrence — no privileged access or exploit is required, only for the AA's payout logic to include a currently-unattested address among several outputs.

### Recommendation
- In AA payout logic that must serve multiple recipients of a `spender_attested` asset, avoid combining multiple recipients' outputs into a single payment message; instead process/pay recipients individually (one message/output per recipient per trigger or secondary trigger) so a single failure does not block the batch.
- Alternatively, have the oscript logic pre-check attestation status (e.g., via a getter/state query) for each recipient before including them in an output array, and skip or defer unattested recipients rather than failing the whole unit.
- Consider whether `validatePaymentInputsAndOutputs()` could return more granular errors identifying which specific address(es) failed attestation, to make it easier for AA authors to build defensive logic, though the core fix belongs in AA design guidance/patterns rather than solely in core validation.

### Proof of Concept
1. Author an AA (oscript) that issues/manages a `spender_attested` asset, and implements a "distribute to all pool participants" trigger case that builds one `payment` message with outputs to every address recorded in a state array (e.g., `var['participants']`), similar in spirit to the multi-output patterns seen in `test/samples/order_book_exchange.oscript` / `a_bank_without_percent.oscript`, but paying out to several addresses at once instead of only `trigger.address`.
2. Have all attestors revoke/withdraw attestation for one participant address that remains in `var['participants']` (or never attest it while it's already recorded there).
3. Trigger the distribution: `aa_composer.js`'s `sendUnit()` composes the payment with all participant outputs, `validateAndSaveUnit()` invokes `validatePaymentInputsAndOutputs()`, which calls `storage.filterAttestedAddresses()` over `arrOutputAddresses` and returns `"some output addresses are not attested"` because one address is missing from `arrAttestedOutputAddresses` (`validation.js` lines 2634-2638).
4. Observe the AA `bounce()`s the entire unit (`aa_composer.js` lines 1405-1410), state remains unchanged, and every subsequent attempt to run the same distribution logic bounces identically — permanently freezing payouts for all other, fully-eligible participants.
