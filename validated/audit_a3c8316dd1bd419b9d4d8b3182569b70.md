### Title
Unauthenticated forged webhook mutates victim organization's stack when victim's `webhook_secret` is unset - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's `GitHubApp` (and thus which `webhook_secret`) to verify against using the unauthenticated `repository_owner` read straight from the POST body. `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that organization's `webhook_secret` is blank, so any attacker can claim `repository.owner.login = "victim-org"` and have their forged, unsigned payload accepted as if it came from GitHub, causing `Shipit::Webhooks` push handlers to enqueue `GithubSyncJob` against victim-org's stack.

### Finding Description
The broken binding: the request should only be able to mutate a stack owned by organization `O` if `O`'s `webhook_secret` cryptographically verified the request body — i.e. `verifying_secret_owner(body) == stack.repository.owner`. In this code path, when `O.webhook_secret` is blank, **no** secret verifies anything, yet the request is still accepted as valid for `O`.

Code path:
1. `repository_owner` reads `params.dig('repository', 'owner', 'login')` directly out of the attacker-controlled JSON body, with no authentication of the source [1](#0-0) .
2. `verify_signature` uses that attacker-supplied value to select the `GitHubApp` to check against via `Shipit.github(organization: repository_owner)`, then calls `github_app.verify_webhook_signature(...)` [2](#0-1) .
3. `GitHubApp#verify_webhook_signature` returns `true` unconditionally (`return true unless webhook_secret`) when the organization's configured `webhook_secret` is blank [3](#0-2) .
4. With `verified == true`, `create` parses the same attacker body and dispatches it to `Shipit::Webhooks.for_event(event)` handlers, which enqueue `GithubSyncJob` for the stack matching `repository.full_name` [4](#0-3) .

Attacker request: `POST /webhooks` with header `X-Github-Event: push`, no `X-Hub-Signature`, body `{"repository":{"owner":{"login":"victim-org"},"full_name":"victim-org/victim-repo"},"ref":"refs/heads/master","after":"<sha>"}`. If `victim-org`'s `GithubHook`/`GitHubApp` config in `secrets.github` has no `webhook_secret` set, `verify_webhook_signature` returns `true` and the sync job is enqueued for victim-org's stack, no signature or credential required.

Existing guards that fail to catch this: `drop_unhandled_event` only filters by event type, not authenticity [5](#0-4) ; `Shipit.github` only raises `GithubOrganizationUnknown` if the organization name itself is not configured, it does not require the organization to have a secret [6](#0-5) ; there is no fallback rejecting organizations with blank `webhook_secret`.

### Impact Explanation
An unprivileged internet attacker who knows (or guesses) that `victim-org` exists in the Shipit installation and has no `webhook_secret` configured can forge push/status/check_suite/membership events for that organization's repositories, causing `GithubSyncJob` (commit ingestion), `RefreshCheckRunsJob`, status creation, or team/membership record writes to run against victim-org's stack with attacker-chosen data (e.g. `after` SHA, statuses) — this is a payload for one repository/organization mutating another's data with no authentication, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). This is repeatable against any organization sharing the deployment that lacks a configured `webhook_secret`, and the blast radius scales with the number of misconfigured organizations sharing the same Shipit host.

### Likelihood Explanation
Exploitability strictly requires the precondition that at least one configured GitHub organization in `secrets.github` has no `webhook_secret` set — this is an intentional fallback in `GitHubApp#verify_webhook_signature` (`return true unless webhook_secret`), which is likely meant to support "no-op" verification for orgs that genuinely don't set up a secret, but as written it does not distinguish "trusted, no secret configured intentionally" from "attacker abusing the absence of a secret." Given webhook secrets are optional per the setup docs (`webhook_secret` is documented but not enforced), operators plausibly have some organizations without one configured, especially with multi-tenant (`Shipit::GithubHook`) setups. The attack cost is a single unauthenticated HTTP POST, fully repeatable, with no rate limiting or session state needed.

### Recommendation
Reject webhook requests outright when the resolved organization has no `webhook_secret` configured, instead of treating a blank secret as automatically valid — i.e., change `GitHubApp#verify_webhook_signature` to `return false unless webhook_secret` (or fail closed and log a configuration error), and/or enforce that every organization in `Shipit.github_organizations` must have a non-blank `webhook_secret` at boot/config-validation time.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (or a new minitest under `test/`):
```ruby
test ":push with no signature and blank webhook_secret still enqueues GithubSyncJob (vulnerable)" do
  # arrange: stub Shipit.github(organization: 'shopify') to return a GitHubApp with no webhook_secret
  github_app = Shipit::GitHubApp.new('shopify', {}) # no webhook_secret key
  Shipit.stubs(:github).with(organization: 'shopify').returns(github_app)

  request.headers['X-Github-Event'] = 'push'
  # no X-Hub-Signature header set at all
  parsed_body = JSON.parse(payload(:push_master))
  expected_head_sha = parsed_body["after"]

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: @stack.id, expected_head_sha:]) do
    post :create, body: parsed_body.to_json, as: :json
  end
  assert_response :ok
end
```
Assertion on both sides of the binding: before the fix, `verify_webhook_signature(nil, body) == true` for the org with blank `webhook_secret` (attacker side) even though no secret ever verified the payload (trusted side is absent) — job is enqueued. After applying the recommended fix (`return false unless webhook_secret`), the same POST should assert `assert_response :unprocessable_entity` and `assert_no_enqueued_jobs`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
