### Title
Webhook signature verification org can diverge from dispatch-target repository org, enabling cross-tenant forged webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`repository_owner` in `app/controllers/shipit/webhooks_controller.rb#repository_owner` derives the organization used to select the GitHub App/secret for signature verification, but it falls back to the top-level `organization.login` field whenever `repository.owner.login` is absent — even if `repository` itself (and `repository.full_name`) is present. Since handlers (`app/models/shipit/webhooks/handlers/handler.rb#repository_name`) dispatch strictly on `payload.dig('repository','full_name')`, an attacker can pick a different, secret-less organization for verification while naming any victim repository for dispatch.

### Finding Description
The broken binding: `repository_owner` (used to select the verifying `GitHubApp` in `verify_signature`, `app/controllers/shipit/webhooks_controller.rb#L25`) is claimed to always equal the owning org of `repository.full_name` (used by `Handler#repository_name`/`stacks`, `app/models/shipit/webhooks/handlers/handler.rb#L36-37`) that ultimately identifies which `Repository`/`Stack` the event mutates. These are in fact independently attacker-controlled:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
(`app/controllers/shipit/webhooks_controller.rb#L59-62`)

If the attacker's JSON body includes `repository: { full_name: 'OrgVictim/repo' }` (no nested `owner` key) plus a top-level `organization: { login: 'UnsecuredOrg' }`, `repository_owner` resolves to `'UnsecuredOrg'` even though `repository` is present. `verify_signature` then calls `Shipit.github(organization: 'UnsecuredOrg').verify_webhook_signature(...)`. `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb#L76-83`) short-circuits `return true unless webhook_secret` — i.e., if `UnsecuredOrg` is configured in `Shipit.github_organizations` but has no `webhook_secret` set, any signature (even a missing/garbage one) passes.

After `verify_signature` passes, `create` parses the raw body and dispatches to handlers using the **same** payload, which look up the target repo/stack via `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb#L36-37`), i.e. `'OrgVictim/repo'` — a completely different, properly-secured organization. No code re-validates that the verifying org matches the dispatch-target repository's org.

Existing guards do not close this gap: `check_if_ping`/`drop_unhandled_event` only gate on event type; `GithubOrganizationUnknown` handling only fires if `UnsecuredOrg` isn't configured at all (it is configured, just secret-less); handlers' `ExplicitParameters` schemas validate shape, not provenance; there is no comparison anywhere between `repository_owner` and `repository.full_name`'s owning org.

### Impact Explanation
An attacker who controls (or names) an organization slug that happens to be configured in the Shipit deployment without a `webhook_secret` can forge arbitrary webhook events (`push`, `status`, `check_suite`, `pull_request`, etc.) targeting **any other** organization's repository/stack by simply naming that repository in `repository.full_name` while supplying the secret-less org's login as `organization.login` and omitting `repository.owner.login`. This can trigger unauthorized `GithubSyncJob` enqueues, deploy/rollback-relevant state changes, or commit/task/team record writes for a repository that never authenticated the request — a cross-tenant, unauthenticated write, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Exploitability is entirely conditioned on the existence of at least one organization entry in `Shipit.github_organizations` that is configured (so `GithubOrganizationUnknown` is not raised) but has no `webhook_secret` set — a real-world Shipit misconfiguration scenario explicitly assumed by the question. Given that precondition, the attack is a single unauthenticated HTTP POST to `/webhooks` with a crafted JSON body and no valid signature required; it is trivially repeatable against any repository/organization known to be registered in Shipit, since the attacker fully controls both `organization.login` (verification target) and `repository.full_name` (mutation target) independently.

### Recommendation
Do not allow `repository_owner` to silently diverge from the repository actually being dispatched to. Concretely: require `repository.owner.login` (not a global `organization.login` fallback) when a `repository` object is present in the payload; if `repository` is present but `repository.owner.login` is missing, reject the webhook (422) rather than falling back. Additionally, verify that the organization used to select the signing secret matches the ownership of `repository.full_name` before dispatching to handlers.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "cross-tenant forged webhook when repository.owner is omitted" do
  # Precondition: 'unsecuredorg' is configured with no webhook_secret
  Shipit.stubs(:github_organizations).returns(
    'unsecuredorg' => {}, # no webhook_secret
    'orgvictim' => { webhook_secret: 'realsecret' }
  )

  victim_stack = shipit_stacks(:shipit) # belongs to OrgVictim/repo
  request.headers['X-Github-Event'] = 'push'
  # No X-Hub-Signature header at all, or a bogus one
  body = {
    repository: { full_name: 'OrgVictim/repo' }, # no nested owner.login
    organization: { login: 'unsecuredorg' },
    ref: 'refs/heads/master',
    after: 'deadbeef'
  }.to_json

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: 'deadbeef']) do
    post :create, body: body, as: :json
  end
  assert_response :ok
end
```
Both sides of the binding — `repository_owner` (`'unsecuredorg'`) and the owning org of `repository.full_name` (`'orgvictim'`) — diverge, and the test demonstrates `sync_github`/`GithubSyncJob` for `OrgVictim`'s stack executes despite zero valid authentication for that org.
