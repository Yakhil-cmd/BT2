### Title
Re-pairing with a stale/permanent pairing secret silently resets `is_blackhole` and restores trust for an already-blacklisted correspondent device - (File: device.js)

### Summary
`handlePairingMessage()` in `device.js` unconditionally clears the `is_blackhole` flag on `correspondent_devices` for the device address that sent the pairing message, as long as the presented `pairing_secret` is any still-valid (non-expired) secret, including the account's single reusable **permanent** pairing secret (`pairing_secret='*'`/`is_permanent=1`). This happens even when the sending device is already a *known* correspondent that the user has explicitly blackholed.

### Finding Description
When a "pairing" device message is received, `handlePairingMessage` only checks that the presented `pairing_secret` exists and is not expired: [1](#0-0) 

It then always (re)inserts/updates the correspondent row and, critically, forces `is_blackhole=0` regardless of the correspondent's prior blackholed state: [2](#0-1) 

The `is_blackhole` flag is the user's explicit trust-revocation mechanism: when a peer sends `removed_paired_device` and the local operator has configured `bIgnoreUnpairRequests`, the wallet does not delete the correspondent but instead sets `is_blackhole=1` to stop treating it as a live correspondent while retaining history: [3](#0-2) 

Later, outbound messaging respects this flag and refuses to send to a blackholed device: [4](#0-3) 

However, `handlePairingMessage` never checks `is_blackhole` before clearing it. A correspondent device that still possesses (a) the permanent pairing secret (`getOrGeneratePermanentPairingInfo`, used e.g. for arbiter contracts) or (b) any not-yet-expired one-time pairing secret it obtained before being blackholed, can simply resend the "pairing" justsaying to the hub. This causes the local node to silently reset `is_blackhole` to `0`, re-establishing full correspondent trust — including the "paired" event that many UI/bot flows use to grant application-level trust — without any fresh user confirmation: [5](#0-4) 

This matches the reported bug class: reconnection (here, re-pairing) of an already-known peer node mutates approval/trust state in a way that can restore broader authority than the operator intended, because the state-mutation path treats "presents a valid pairing secret" as sufficient proof of trust, ignoring the existing local decision to blackhole that device.

### Impact Explanation
Once `is_blackhole` is cleared, the previously-revoked device becomes eligible again to receive/send all correspondent-gated messages: chat, `signature` requests for shared/multisig addresses, `new_shared_address` offers, `arbiter_contract_offer`, private payment chains, etc. An operator who blackholed a peer specifically to stop receiving further requests from a device they no longer trust (e.g. a suspected-compromised cosigner device in a multi-device shared address, or a scam counterparty in a private payment/arbiter flow) can have that decision silently undone by the peer itself, re-opening a channel that can be used to solicit new signatures/approvals from the user (leading to unauthorized spending from shared addresses) or resume social-engineering flows in private payments/arbiter contracts. This is a node-disagreement-on-trust/authority issue with direct fund-loss potential in multisig/arbiter cosigning workflows, consistent with a Medium-severity approval-scope-confusion bug.

### Likelihood Explanation
Exploitation requires only that the attacker-controlled device already possesses a still-valid pairing secret for the victim (trivial for the permanent secret, which is reused indefinitely per `getOrGeneratePermanentPairingInfo`, or for a one-time secret obtained prior to being blackholed and not yet expired — one-time secrets last up to 1 month by default). No additional privilege beyond "was previously paired" is required, and the reconnection/re-pair message is processed automatically with no user prompt, making this readily reachable by any peer the user has ever paired with.

### Recommendation
In `handlePairingMessage`, before clearing `is_blackhole`/re-confirming an existing correspondent, check the current `is_blackhole` state of the row for `from_address`. If the device is currently blackholed, either reject the re-pairing attempt outright or require explicit user re-approval (e.g. emit a distinct event such as `unblackhole_request` for the UI to confirm) instead of silently resetting the flag as part of the automatic pairing flow.

### Proof of Concept
1. Device B pairs with Device A normally; `correspondent_devices` row for B has `is_blackhole=0`.
2. Operator of A configures `bIgnoreUnpairRequests`; B sends `removed_paired_device`, causing A to set `is_blackhole=1` for B via the path at [6](#0-5) , effectively silencing B without deleting the correspondent record.
3. B still knows a valid pairing secret for A's device (e.g. the permanent one obtained earlier via an arbiter-contract flow, or a one-time secret from a prior pairing that has not yet expired).
4. B sends another `pairing` message to A through the hub with that secret.
5. `handlePairingMessage` matches the still-valid secret, and executes `UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?` for B, restoring B's correspondent trust without any user interaction — B can now resume sending signature/shared-address/arbiter-contract requests to A. [7](#0-6)

function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
				[from_address, device_pubkey, json.device_hub, safe_device_name],
				function(){
					db.query( // don't update name if already confirmed
						"UPDATE correspondent_devices SET is_confirmed=1, name=? WHERE device_address=? AND is_confirmed=0", 
						[safe_device_name, from_address],
						function(){
							db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
								eventBus.emit("paired", from_address, body.pairing_secret);
								if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
									db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
									eventBus.emit('paired_by_secret-'+body.pairing_secret, from_address);
								}
								if (body.reverse_pairing_secret)
									sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null);
								callbacks.ifOk();
							});
						}
					);
				}
			);
		}
	);
}
