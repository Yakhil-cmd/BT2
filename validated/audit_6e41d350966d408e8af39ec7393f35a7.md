### Title
Sensitive private-payment data (blinding factors, amounts, spend proofs, addresses) written to process logs via `console.log` - ([File: indivisible_asset.js])

### Summary
The CVE class here is information disclosure through logging: sensitive connection metadata was written into a persistent log file readable by lower-privileged processes. In ocore, private-asset payment code paths repeatedly `console.log` the full plaintext of "private" (hidden) payment payloads — including `blinding` factors, `amount`, `address`, and `spend_proof` inputs that are specifically designed to stay confidential between payer/payee/cosigners and never appear in the public DAG.

### Finding Description
`indivisible_asset.js` logs the entire private element chain and computed spend proof, including `address`, `amount`, `denomination`, and `blinding`: [1](#0-0) 
and again when saving: [2](#0-1) [3](#0-2) 

`divisible_asset.js` logs the picked private-asset input proofs (which include blinding/hidden output data) when composing a private payment: [4](#0-3) 
and logs the saved unit together with the array of decrypted private elements (`arrPrivateElements`) which contains addresses/blinding of the payer and payee: [5](#0-4) 

`private_payment.js` logs the full private chain of an asset transfer being validated/saved, including plaintext outputs with `address`/`blinding`/`amount`: [6](#0-5) 

`wallet.js` logs the full chain content being forwarded to co-signers/cosigners, and the exact amounts/addresses of a received private payment: [7](#0-6) [8](#0-7) 

By design, blinding factors and hidden-output plaintext for `is_private` assets are meant to be shared only between the sender and the specific recipient/cosigners over an encrypted device-to-device channel (`wallet.js` `handlePrivatePaymentChains`, `forwardPrivateChainsToOtherMembersOfOutputAddresses`), never surfaced elsewhere. Any single unprivileged user who triggers a private-asset transfer (as a payer, payee, or cosigner sharing an address) causes these functions to run and to write the fully de-anonymized payload — the same data the wallet is engineered to keep confidential from anyone but the specific counterparties — to the process's standard log stream via `console.log`.

### Impact Explanation
If the ocore-based node/wallet operator (as is standard Node.js practice) redirects stdout/stderr to a persistent log file (or a logging/monitoring pipeline), any process, backup, log-aggregation service, or other party with read access to that log — but without permission to see private-payment details — obtains the plaintext `blinding` factors, `amount`, and `address` values of private-asset transfers, and the `spend_proof` inputs. This defeats the entire purpose of "private assets" (`is_private`/blinded outputs) in ocore, allowing a party with only log access (not a wallet participant) to trace and de-anonymize private transactions between other users — an information-disclosure defect of the confidentiality guarantee the private-payment subsystem is supposed to provide. This mirrors the Brave/tor.log CVE class: an unprivileged local reader of the log obtains information that was supposed to remain confidential to the connection's/transaction's intended participants.

### Likelihood Explanation
Any user who is a party to (or asked to relay/cosign) a private-asset payment naturally triggers these code paths — this requires no special privilege, and is a routine wallet operation (`sendMultiPayment` for a private asset, `handlePrivatePaymentChains`, `validateAndSavePrivatePaymentChain`). The disclosure is a side effect of ordinary usage, so likelihood of the sensitive data landing in logs is high whenever verbose console logging is enabled/piped to a file, which is common in production Node.js deployments.

### Recommendation
Remove or gate behind an explicit debug-only flag (default off, and never enabled in production) all `console.log` statements that print private-asset payloads, blinding factors, spend proofs, and hidden output amounts/addresses in `indivisible_asset.js`, `divisible_asset.js`, `private_payment.js`, and `wallet.js`. Redact or hash sensitive fields (`blinding`, `address`, `amount`, `spend_proof`) before logging, and ensure only a purpose-built, permission-scoped logger is used for confidential transaction data.

### Proof of Concept
1. Attacker has read access to the node's process log file/output stream (a common deployment artifact, not requiring node compromise).
2. Any user (payer or payee) sends or receives a private-asset payment via `sendMultiPayment`/`handlePrivatePaymentChains`.
3. During validation/saving, `indivisible_asset.js` line 125-133 and 243/272, `divisible_asset.js` line 256/400, and `private_payment.js` line 243 emit the full private payload (address, amount, blinding, spend proof) to console output.
4. The attacker reads the persisted/aggregated log and extracts the private transaction's real sender/receiver addresses and amounts, breaking the confidentiality guarantee of "private" assets without being a participant in the transaction.

Note: I could not confirm within the indexed code whether this specific ocore deployment redirects stdout to a persistent log file by default (no `winston`/`bunyan`/`appendFile`-based logger was found, and `profiler.js` only writes profiling summaries to files under specific flags) — this is a limitation of the available index. If the operator's deployment (server wrapper, systemd service, PM2, Docker logging driver, etc.) captures stdout to disk, as is standard practice, the disclosure above applies directly.
