## Analysis

This is analogous to the reported "add-only safe list" bug in ocore's attestation mechanism, which is the trust primitive used to gate spending of `spender_attested` assets (a restricted/permissioned asset feature) and to satisfy the `'attested'` address-definition condition.

### Title
Attestations are permanently add-only and cannot be revoked by the attestor, permanently exempting an address from an asset's attestation-gated spending restriction - (File: `storage.js`)

### Summary
An `attestation` message lets any address act as an attestor and mark another address as "attested" for arbitrary profile fields. This record is used in two security-critical checks: (1) the `'attested'` operator in address definitions (`definition.js`), and (2) the mandatory attestation check for `spender_attested` assets in payment validation (`validation.js`). In both paths, once an attestor posts an attestation for an address, that address is treated as trusted/attested forever — there is no message type or code path that lets the attestor revoke, unset, or invalidate a previously issued attestation.

### Finding Description
The `'attestation'` message app is written unconditionally into the `attestations` table with no expiry or revocation field: [1](#0-0) 

The only lookup function used to decide whether an address is currently "attested" is `filterAttestedAddresses`, which simply checks for the *existence* of any matching row, gated only by whether the attested address changed its key/definition afterward — not by any attestor-issued revocation: [2](#0-1) 

This existence-only check is used to gate spending of `spender_attested` assets — an issuer-defined asset type intended to allow spending only by KYC'd/attested addresses: [3](#0-2) [4](#0-3) 

It is also used by the `'attested'` operator in general address definitions, which any wallet/AA can use as an authentication/authorization predicate: [5](#0-4) 

Note this is distinct from the separate, fully mutable `asset_attestors` list (which controls *who is allowed to be an attestor* for an asset and can be freely replaced by the asset definer via `validateAttestorListUpdate`): [6](#0-5) 
That mechanism lets the definer change which attestor addresses are trusted, but it does nothing to undo attestations that a (possibly still-trusted) attestor already issued to a specific spender address. The `attestation` payload itself has no "revoke"/"unset" semantics anywhere in validation (`aa_validation.js`) or in the DB writer, so once issued, an attestation for `address` by `attestor_address` is permanent — exactly the "can only be added, but not removed" pattern in the external report, applied to the `attested`/`spender_attested` trust gate instead of a `safeAddress` list.

### Impact Explanation
If an attestor (e.g., a KYC/compliance provider designated by an asset issuer) attests an address and later needs to revoke that trust — because the address's owner is later found to be sanctioned, compromised, or fraudulent — there is no way to do so. The address remains permanently able to:
- Spend/hold the `spender_attested` asset via `validatePayment`/`validatePaymentInputsAndOutputs`, bypassing the intended compliance control indefinitely.
- Satisfy any `'attested'` condition in an address definition, permanently unlocking funds/authority gated by that condition even after the attestor no longer trusts the address.

This is a real, permanent, unauthorized-access/asset-control weakness reachable by any attestor address posting a normal, valid unit — no privileged node or peer role required — matching the Medium-severity class of the reference finding (a one-way, non-revocable trust list controlling a spending/authorization gate).

### Likelihood Explanation
Any address can act as an attestor for an asset it's authorized to attest for (or for a generic `'attested'` definition condition, any address listed as `arrAttestors`). Posting an `attestation` unit is a normal, unprivileged operation available to any protocol participant. The permanence of the resulting record is a deterministic, always-triggered consequence of `filterAttestedAddresses`'s existence check — no race condition or edge case is needed.

### Recommendation
Introduce a revocation mechanism for attestations analogous to `isSafeAddress(address, bool)`:
- Add an explicit `revoke` (or `unset`) flag to the `attestation` message payload, or a dedicated `attestation_revocation` app, validated in `validation.js`'s `validateInlinePayload` alongside the existing `attestation` case.
- In `filterAttestedAddresses` (`storage.js`), take the *latest* attestation (or revocation) from a given attestor for a given address rather than treating any past attestation as permanently valid, mirroring how `asset_attestors` already takes only the latest attestor-list unit.
- Apply the same latest-wins logic to the `'attested'` operator evaluation path in `definition.js`.

### Proof of Concept
1. Asset issuer defines asset `X` with `spender_attested: true` and `attestors: [A]`.
2. Attestor `A` posts an `attestation` message attesting address `V` (e.g., `profile: {kyc: "passed"}`).
3. `V` can now spend/receive asset `X` per `validatePayment` (`validation.js:2115-2122`).
4. `A` later determines `V` is compromised/sanctioned and wants to revoke `V`'s attested status. There is no message type or API to do this — `V` remains attested forever because `filterAttestedAddresses` (`storage.js:1959-1974`) only checks existence of the original attestation row.
5. `V` continues to freely transact in asset `X`, defeating the compliance control the issuer/attestor intended to enforce.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
