### Title
Webhook signature scoping is bound to `repository.owner.login`, but the handler dispatch is bound to `repository.full_name` — allows cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate a payload against using `params.dig('repository', 'owner', 'login')`, but every `Shipit::Webhooks::Handlers::Handler` subclass resolves the target `Repository`/`Stack` to act on using a *different* field: `payload.dig('repository', 'full_name')`. Because these two fields are never checked to be consistent, an attacker who legitimately controls the webhook secret for one GitHub organization onboarded to a multi-tenant Shipit instance can forge a signed webhook whose `repository.owner.login` matches their own org (so it passes signature verification) while `repository.full_name` names a stack belonging to a completely different organization also hosted on the same Shipit instance.

### Finding Description
The equality that should hold is: **the organization whose secret authenticated the request == the organization that owns the repository being mutated**. Shipit breaks this equality by verifying against one field and acting on another.

`verify_signature`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

Every handler (`PushHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`, etc.) inherits `Handler#stacks`/`#repository_name`, which resolves the acted-upon repository from an entirely different JSON path:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

and `Repository.from_github_repo_name` splits that string on `/` to find the target repo/stack:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [3](#0-2) 

Because Shipit's own docs and `secrets.*.yml` show it is designed to host **multiple GitHub organizations from a single instance**, each with its own `webhook_secret`, `app_id`, and `installation_id`:
```yaml
github:
  somegithuborg:
    webhook_secret: ...
  someothergithuborg:
    webhook_secret: ...
``` [4](#0-3) 

an org administrator who is fully entitled to configure/send webhooks for `somegithuborg` (and therefore knows or can view that org's `webhook_secret` in its GitHub App settings) has no legitimate GitHub-side ability to send events for `someothergithuborg`'s repositories — GitHub itself will only ever deliver events with `repository.full_name` matching `repository.owner.login`. However, Shipit's `WebhooksController` never checks that constraint on the received payload: it computes the signing organization from `repository.owner.login` and separately hands the *entire, attacker-authored* raw JSON body to handlers, which pick the actual target purely from `repository.full_name`. Nothing stops these two values from diverging in a forged payload signed correctly for `somegithuborg`.

### Impact Explanation
This breaks the deployment-trust binding "an organization that authenticated versus the repository that is written," explicitly called out as in-scope. Concretely, the `push` event handler:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

allows an attacker who only controls one org's webhook secret to force `GithubSyncJob` (and via it `Commit` creation, `Stack#cached_deploy_spec` refresh, and potentially auto-deploy on continuously-delivered stacks) to run against a **stack belonging to a different organization** they have no authorization over on this Shipit instance — a cross-organization/cross-repository write triggered without the owning organization's consent. The `check_suite` and `pull_request` handlers are affected the same way since they inherit the same `Handler#stacks` resolution.

### Likelihood Explanation
Exploitation requires only:
1. Administrative access to a GitHub organization/App already configured as one of the (potentially several) organizations on the target Shipit deployment's `Shipit.github` config — a routine, low-privilege position relative to Shipit itself (the attacker has zero Shipit credentials, session, or repository write access on the victim org).
2. The ability to POST an HTTP request with an HMAC-SHA1 signature computed from that org's own `webhook_secret` — trivial since the attacker controls that secret for their own org's GitHub App.

No GitHub App private key, `ApiClient` token, or Shipit session is needed, and the request goes directly to the public `/webhooks` endpoint (`WebhooksController` is a plain `ActionController::Base`, not gated by any Shipit authentication). Likelihood is High for any multi-tenant Shipit installation.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), enforce that the field used to select the signing organization is the *same* field used to resolve the target repository, e.g. derive both from `repository.full_name` (or validate `repository.owner.login == repository.full_name.split('/').first`) before dispatching to handlers, and reject the payload with `422` on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` (attacker-controlled GitHub App, webhook secret known to attacker) and `orgB` (victim org, unrelated stack tracked by the same Shipit instance).
2. Attacker crafts a JSON push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<any sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>` using the secret they legitimately hold for `orgA`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'orgA')` and successfully verifies the signature against `orgA`'s secret.
5. `Shipit::Webhooks::Handlers::PushHandler.call(params)` resolves `stacks` via `Repository.from_github_repo_name('orgB/victim-repo')`, finds `orgB`'s stack, and enqueues `GithubSyncJob` for it — despite the request never being authorized by `orgB`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

    rescue Shipit::GithubOrganizationUnknown => e

        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
