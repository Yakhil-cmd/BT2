### Title
Stack-scoped ApiClient can create arbitrary new stacks it is not authorised for - ([File: app/controllers/shipit/api/stacks_controller.rb])

### Summary
An `ApiClient` token that is scoped to a single stack (`ApiClient#stack_id`) is only prevented from *seeing* or *modifying existing* stacks other than its own. The `#create` action of `Shipit::Api::StacksController` never consults that scoping, so a client that is only supposed to operate against Stack A can create a brand-new `Stack` for any other repository, effectively acting outside the boundary its token authorises.

### Finding Description
`ApiClient` can be restricted to a single stack via `belongs_to :stack, optional: true` and the `stack_id` column [1](#0-0) . Permission checks are purely string based (`"#{operation}:#{scope}"`) and never reference `stack_id` at all [2](#0-1) .

The actual binding of "which stacks this token may touch" is enforced ad hoc in `Shipit::Api::BaseController`:
```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [3](#0-2) 

`StacksController#show`, `#update`, `#destroy`, `#refresh` and `#index` all route through this `stacks`/`stack` helper, so a client scoped to Stack A cannot read or mutate Stack B [4](#0-3) .

However, `#create` bypasses this helper entirely:
```
def create
  stack = Stack.new(create_params)
  stack.repository = repository
  stack.save
  render_resource(stack)
end
``` [5](#0-4) 

It only checks `require_permission :write, :stack` (a scope-less string permission) [6](#0-5)  and builds/looks up an arbitrary `Repository` from attacker-supplied `repo_owner`/`repo_name` params [7](#0-6) . There is no check that the created stack corresponds to `current_api_client.stack_id`.

This breaks the equality that the report's bug-class targets: **the stack a token is authorised for (`current_api_client.stack_id`) ≠ the stack the request actually creates/touches**. Before the request: the token's write scope is meant to be limited to `Stack.where(id: current_api_client.stack_id)`, mirroring `#show`/`#update`/`#destroy`. After the request: a brand-new `Stack` row exists for an entirely different repository/branch/environment that the token was never bound to, with `write:stack` permission having been "spent" outside its intended scope — analogous to how `totalWeight`/`weights` in the Solidity report kept counting a voter's stale (unauthorized-for-current-state) power because the code path that updates the value never re-validated the binding.

### Impact Explanation
A stack-scoped API token (intended, per the `stack_id` restriction, to manage a single deployment pipeline) can provision additional `Stack` resources for other repositories/branches it was never granted access to. Because `Stack#create` (via `stack.repository = repository`) can target any GitHub `repo_owner`/`repo_name`, and stacks drive deploy execution (`config/deploy/$ENVIRONMENT`, `shipit.yml` steps, environment variables, etc.), this is an escalation of a narrowly-scoped write credential into the ability to write/attach state for other repositories through the engine — i.e. a cross-repository write performed with credentials that were only supposed to authorize one repository/stack.

### Likelihood Explanation
Requires possession of a valid `ApiClient` token that has `write:stack` permission and a non-null `stack_id` (i.e., an already-issued, deliberately-restricted API credential) — this is within the "unprivileged attacker" boundary defined by the scan rules (a token, not a full admin session or GitHub App key), since scoping the token to one stack is precisely how an operator limits blast radius of a leaked/shared credential. The only steps needed are a single authenticated POST to `/api/stacks` with `repo_owner`/`repo_name` params, no additional privilege needed beyond what the token already carries.

### Recommendation
In `Shipit::Api::StacksController#create`, when `current_api_client.stack_id?` is true, reject the request (403) unless the resolved repository/stack matches the token's authorised `stack_id`, or otherwise disallow `create` entirely for stack-scoped clients. The check should mirror the `stacks` scoping helper used by `show`/`update`/`destroy` so `create` cannot be used to escape the `stack_id` binding.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id = A` (Stack A, e.g. `myorg/repo-a`) with permission `write:stack`.
2. Authenticate as that client and issue:
```
POST /api/stacks
Authorization: Basic <token for stack-A-scoped client>
repo_owner=otherorg
repo_name=repo-b
environment=production
branch=main
```
3. Observe `StacksController#create` executes without any `stack_id` check [5](#0-4) , creating a new `Stack` for `otherorg/repo-b` even though the token is only supposed to be authorised for Stack A — contrast with attempting `GET /api/stacks/<stack-B-id>`, which correctly 404s via `stacks.from_param!` [3](#0-2) .
