### Title
Forged webhook bypasses signature check for one org, but drives sync actions on a completely different tracked repository - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's config (and thus which webhook secret) to verify the request signature against based on the `repository.owner.login` (or `organization.login`) field of the *untrusted* payload, but the actual event handlers (e.g. `PushHandler`) resolve the target `Stack`/`Repository` from the *separate* `repository.full_name` field of that same payload. Because `GitHubApp#verify_webhook_signature` short-circuits to `true` when the selected organization has no `webhook_secret` configured, an attacker only needs one Shipit-tracked organization to be running without a webhook secret to authenticate a forged request as "verified," while pointing the actual `repository.full_name` at any other organization/repository whose stacks Shipit tracks.

### Finding Description
`verify_signature` computes the org to authenticate against purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` treats a blank `webhook_secret` as an automatic pass, which is a documented, supported "optional" configuration per the setup guide: [3](#0-2) [4](#0-3) 

Shipit is designed to track multiple GitHub organizations simultaneously (each with its own `Shipit.github(organization:)` config/secret), per the changelog entry "Support multiple GitHub organisations": [5](#0-4) 

Once the request passes `verify_signature`, `Webhooks.for_event` dispatches to handlers such as `PushHandler`, which resolves the target stacks purely from `repository.full_name` — a field that is never checked against `repository.owner.login`/`organization.login`, the field used earlier to select the signing secret: [6](#0-5) [7](#0-6) [8](#0-7) 

This breaks the trust binding: `organization authenticated (repository.owner.login used to pick the webhook secret) == repository written (repository.full_name used to locate/act on the Stack)`. If org A (tracked by the same Shipit instance) has no `webhook_secret` configured, an unprivileged external attacker can `POST /webhooks` with `repository.owner.login = "orgA"` (or `organization.login = "orgA"`) to pass signature verification for free, while setting `repository.full_name = "orgB/some-tracked-repo"` and an arbitrary `after` SHA. The push handler then locates and acts on `orgB`'s stack, calling `stack.sync_github(expected_head_sha:)`, which enqueues `GithubSyncJob`: [9](#0-8) 

### Impact Explanation
An unprivileged, unauthenticated attacker (no Shipit session, no `webhook_secret`, no GitHub App key) can force out-of-band synchronization on a stack belonging to any other tracked organization, as long as one org lacks a webhook secret. `GithubSyncJob` pulls new commits from GitHub and, if the target stack has continuous deployment enabled, this can drive an unwanted/unscheduled ship of already-merged commits at a time of the attacker's choosing — i.e. an unauthorized deploy trigger crossing an organization boundary that the signature check was supposed to enforce. This matches the report's High/Critical impact bucket ("an unauthorized deploy").

### Likelihood Explanation
Likelihood depends entirely on whether any organization configured on the shared Shipit instance has an unset `webhook_secret` — an explicitly documented "optional" setting in `docs/setup.md`, so it is plausible in real deployments (e.g. a low-traffic internal/test org added without a secret). Given that condition, exploitation requires only a single unauthenticated HTTP POST with a crafted JSON body; no credentials, tokens, or GitHub access are needed.

### Recommendation
After selecting the organization used to verify the signature, revalidate that `repository.full_name`'s owner matches the same `repository_owner`/`organization.login` used for signature verification (or, more robustly, always require a `webhook_secret` to be configured for every registered organization and reject requests when it's absent instead of treating it as an implicit pass).

### Proof of Concept
1. Configure Shipit to track two organizations: `orgA` (no `webhook_secret`) and `orgB` (has stacks and a webhook secret), per `docs/setup.md` multi-org support.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-existing-sha-on-orgB-repo>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/tracked-repo" }
}
```
No `X-Hub-Signature` needed to match anything, since `orgA` has no secret, `verify_webhook_signature` returns `true` — see `lib/shipit/github_app.rb:76-77`.
3. `WebhooksController#create` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("orgB/tracked-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, enqueuing `GithubSyncJob` for `orgB`'s stack — `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`, `app/jobs/shipit/github_sync_job.rb:18-49` — despite the attacker having no relationship whatsoever to `orgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
