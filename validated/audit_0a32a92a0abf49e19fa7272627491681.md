### Title
`StatusHandler#process` creates cross-stack `Status` records from an unscoped `Commit.where(sha:)` lookup, letting a forged status on an attacker-owned repo trigger `Stack#trigger_continuous_delivery` on a victim's stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) with a bare `Commit.where(sha: params.sha)`, with no scoping to the repository named in the webhook payload, unlike every other handler (e.g. `PushHandler`) which restricts to `stacks` derived from `Repository.from_github_repo_name(repository_name)`. Because git commit SHAs are content-addressed, an attacker who forks/owns a repository sharing history with a victim's tracked repository can send a legitimately-signed `status` webhook for their own repo and have the resulting `Status` attached to the *victim's* identical-SHA `Commit`, which cascades into `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → an unauthorized deploy on the victim stack.

### Finding Description
The claimed binding is: `Status.stack_id == Repository.from_github_repo_name(payload['repository']['full_name']).stacks (webhook's verified repository)`. Tracing the code shows this binding is **not enforced** for the `status` event.

- `WebhooksController#verify_signature` only checks that the payload was signed by the GitHub App/secret belonging to `repository_owner` (`params.dig('repository','owner','login')`), i.e., it authenticates *who sent it*, not *which commits it may touch*. [1](#0-0) 
- `Webhooks::Handlers::Handler` defines a repository-scoped helper `stacks`, used correctly by e.g. `PushHandler#process` (`stacks.not_archived.where(branch:).find_each ...`). [2](#0-1) [3](#0-2) 
- `StatusHandler#process`, however, bypasses this scoping entirely:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 
This queries the global `commits` table for *any* row with a matching `sha`, across every stack/repository/tenant in the installation, ignoring `payload['repository']['full_name']` entirely.
- `Status#after_commit :schedule_continuous_delivery` unconditionally calls `commit.schedule_continuous_delivery` for every created `Status`, regardless of which repo the webhook came from. [5](#0-4) 
- `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob.perform_later(stack)` for the commit's own `stack` (the victim's stack) once `deployable?`, `stack.continuous_deployment?`, and `stack.deployable?` hold. [6](#0-5) 
- `Stack#trigger_continuous_delivery` then calls `trigger_deploy(next_commit_to_deploy, Shipit.user, ...)`, creating and enqueuing a real `Deploy`. [7](#0-6) 

**Exploit flow:** The attacker owns/forks a public repository that shares commit history (hence identical SHA-1 objects) with a victim's Shipit-tracked repository - a common situation for forks or mirrored repos. The attacker's own repo is registered on GitHub with a legitimate webhook secret they control (via their own GitHub App installation/org), so `verify_signature` passes for a payload whose `repository.full_name` is the attacker's own repo. The attacker POSTs `X-Github-Event: status` with `sha` equal to a SHA present in both their fork and the victim's stack, `state: 'success'`. `StatusHandler#process` finds the victim's `Commit` row (same SHA, different `stack_id`) via the unscoped `Commit.where(sha:)`, and creates a `Status` on it, which triggers continuous delivery on the victim's stack.

None of the existing guards catch this: `verify_signature` authenticates the sender's own org, not the resource being mutated; `ExplicitParameters` only validates payload shape (`sha`, `state`, etc.), not repository ownership of the referenced commit; there is no `stacks`/`Repository.from_github_repo_name` check in `StatusHandler` as there is in sibling handlers.

### Impact Explanation
A payload authenticated for the attacker's own repository is used to write a `Status` record on, and trigger a real `Deploy` for, a completely different repository/stack that never authenticated any part of this request. This matches "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy" - Critical severity. The blast radius spans every stack in the multi-tenant Shipit install whose `continuous_deployment` is enabled and whose commit history intersects (by SHA) with any repository the attacker controls; each matching SHA is independently exploitable and repeatable.

### Likelihood Explanation
Preconditions: (1) victim stack has `continuous_deployment: true` and is otherwise deployable (`next_commit_to_deploy` resolves and passes `deployable?`); (2) the attacker's own repo has a valid Shipit webhook signing secret configured for it (trivial for a repo they own, per the accepted premise of this question chain); (3) a SHA collision exists between the attacker's repo and the victim's tracked commit history - readily achievable via forking a public repository, since git SHAs are identical across clones/forks until history diverges. Cost to the attacker is a single crafted, self-signed HTTP POST to `/webhooks`; the attack is trivially repeatable against any repository sharing history with one the attacker controls.

### Recommendation
Scope `StatusHandler#process` (and `Status.replicate_from_github!`) to the repository named in the verified payload, mirroring `PushHandler`/`CheckSuiteHandler`: resolve commits only within `stacks` (i.e. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` or iterate `stacks.each { |stack| stack.commits.find_by(sha: params.sha)&.create_status_from_github!(params) }`), so a status can never be attached to a commit belonging to a stack outside the webhook's verified repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook for attacker's repo must not create a Status for a victim stack sharing the same commit sha" do
  victim_stack = shipit_stacks(:shipit)          # victim, continuous_deployment: true
  victim_stack.update!(continuous_deployment: true)
  shared_sha = "deadbeef" * 5

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim work", ...)

  attacker_payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/attacker-repo', 'owner' => { 'login' => 'attacker' } }
  }

  # binding under test, BEFORE:
  assert_equal 0, victim_commit.statuses.count

  assert_no_difference -> { Deploy.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  end

  # binding under test, AFTER: victim commit/stack must remain untouched
  assert_equal 0, victim_commit.reload.statuses.count
end
```
This test should currently fail (i.e., demonstrate the vulnerability): with the current `Commit.where(sha: params.sha)` implementation, `victim_commit.statuses.count` becomes `1` and, once `ContinuousDeliveryJob.new.perform(victim_stack)` runs, `Deploy.count` increments for `victim_stack` - despite the webhook only being signed and scoped for `attacker/attacker-repo`.
