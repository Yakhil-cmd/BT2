### Title
Zip-bomb / decompression size mismatch in textcoin private-payment file handling causes wallet DoS - (File: wallet.js)

### Summary
`wallet.js`'s `handlePrivatePaymentFile` unzips a `private_textcoin` entry from an attacker-suppliable zip file (e.g. a maliciously crafted textcoin claim file sent by a private-payment counterparty) and only guards against oversized payloads by inspecting the *declared* `uncompressedSize` metadata field before calling `entry.async("string")`, rather than enforcing a hard limit on the number of bytes actually produced during inflate. This mirrors the Pillow PNG-bomb bug class (CVE-2014-9601): trusting a compressed container's self-reported size metadata instead of bounding the real decompression output, allowing a small compressed blob to expand to an unbounded amount of data and exhaust memory/CPU of the victim wallet process.

### Finding Description
`handlePrivatePaymentFile` is reachable whenever a user (light or full wallet) opens/imports a textcoin private-payment file — content that can be produced and handed to the victim by any private-payment counterparty (e.g., a sender of a textcoin claim link/file): [1](#0-0) 

The only size check performed is:
```
if (entry._data && entry._data.uncompressedSize > 100 * 1024 * 1024)
    return cb("private_textcoin entry is too large");
```
This reads an internal, underscore-prefixed JSZip field (`entry._data.uncompressedSize`) that reflects the *declared* size taken from the zip's local/central file header — a value fully controlled by whoever crafted the zip. It is not a property that is verified against, or that bounds, the actual number of bytes the DEFLATE stream will produce when decompressed. Nothing in this code path caps the real output size of `entry.async("string")` while it runs; the check only rejects entries whose header *claims* to be too large, not entries whose header lies (understates the size) while the underlying compressed stream actually inflates to a very large payload. Classic zip-bomb technique: a tiny compressed payload (this can be produced with ordinary DEFLATE at ratios well over 1000:1) can be crafted so its declared header size is small (or even absent, since the check is skipped entirely when `entry._data` is falsy) while it decompresses into a huge in-memory string, which is then also `JSON.parse`d.

This is directly analogous to the reported Pillow PNG bomb: an externally supplied compressed chunk whose *decompressed* size is not properly bounded before/while decompression occurs, letting an attacker force massive memory allocation with a tiny input.

### Impact Explanation
A crafted textcoin/private-payment zip file, sent by any counterparty to a victim wallet, can cause the wallet process to allocate an unbounded amount of memory (and CPU for both inflate and the subsequent `JSON.parse` on the resulting giant string) inside `handlePrivatePaymentFile`, crashing or hanging the victim's wallet. Because this path is exercised before any authenticity/asset validation of the payload's contents, an attacker does not need any special privilege beyond being able to hand the victim a file (a normal private-payment/textcoin counterparty interaction) to trigger denial of service.

### Likelihood Explanation
Likelihood is high for any user who accepts textcoin/private-payment files from unknown or semi-trusted counterparties, since generating a DEFLATE-based zip bomb is trivial and the current guard can be bypassed by simply not populating (or under-declaring) the `uncompressedSize` header field trusted by the check.

### Recommendation
Do not rely on zip-header-declared sizes to bound decompression. Enforce a true streaming size cap while inflating (e.g., accumulate output length during decompression and abort as soon as a hard ceiling, such as 100MB, is exceeded, regardless of what the header claims), and apply the same real-time cap to the string passed into `JSON.parse`. Prefer a decompression library/mode that supports an explicit maximum-output-size option enforced during inflate, not just post-hoc metadata inspection.

### Proof of Concept
1. Build a small deflate-compressed file named `private_textcoin` whose compressed size is a few KB but whose true decompressed content is several GB of repeated bytes (standard zip-bomb construction, e.g. repeated zero bytes compress at >1000:1 with DEFLATE).
2. Package it into a zip such that the local file header's uncompressed-size field is omitted, zero, or understated (many zip tools/tests can produce zips where JSZip's `entry._data` is not populated with an accurate size, or `entry._data` itself is falsy), so the `entry._data && entry._data.uncompressedSize > 100*1024*1024` check does not trigger.
3. Send this file to the victim as a textcoin/private-payment claim, or have them open it via `handlePrivatePaymentFile`.
4. `entry.async("string")` decompresses the full multi-GB payload into memory, followed by `JSON.parse(data)`, exhausting memory and crashing/freezing the wallet process.
