### Title
Cross-repository status confusion via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` forces deploy/block on unrelated stacks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with a bare `Commit.where(sha: params.sha)` lookup that is not scoped to the repository that authenticated the webhook, and `Commit#create_status_from_github!` then writes the status to whatever stack that commit row belongs to. Because git SHAs are content-addressed and identical across forks that share history, an attacker who owns any repository sharing a commit with a victim's stack can send a validly-signed `status` webhook from their own repo and flip `review/approved`/`success` on the victim's commit, which — combined with a bot-login-configured (`Shipit.user`) stack that auto-deploys — can force an unauthorized ship or block.

### Finding Description
The invariant that should hold is: `status.repository.full_name == commit.stack.repository.full_name` for every `Status` row written by a webhook. That binding is never checked.

Path:
1. `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses the raw JSON and dispatches to handlers for the `status` event.
2. `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only checks that the payload is signed by the GitHub App/organization derived from `payload.dig('repository','owner','login')` — i.e., it proves the request came from *some* legitimately configured GitHub org/repo, not that it came from *the victim's* repo. An attacker who owns any repository under an org configured in `Shipit.github_apps`/webhook secrets (including their own account/org) can produce a validly-signed status webhook for **their own** repository.
3. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
Unlike other handlers, `StatusHandler` does not use the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`, app/models/shipit/webhooks/handlers/handler.rb:32-38) to scope the query to the repository named in the payload. It queries `Commit` globally by `sha` only.
4. `Commit#create_status_from_github!` (app/models/shipit/commit.rb:165-169) calls `statuses.replicate_from_github!(stack_id, github_status)` on **whatever stack that commit row belongs to**, then `add_status` (app/models/shipit/commit.rb:366-386) recomputes `status`, emits `Hook.emit(:deployable_status, ...)`, and calls `stack.schedule_merges` when the new status is `success`.
5. Because SHAs are derived from commit content, two different `Repository` records (e.g., an upstream repo and any fork, or two repos that happen to share a merge commit/cherry-pick) can have `Commit` rows with the identical `sha`. Nothing in `StatusHandler` verifies `payload.dig('repository','full_name')` matches `commit.stack.repository.full_name`.
6. If the victim stack has `bot_login` configured (`Shipit.user`), its `ContinuousDeliveryJob`/merge-queue logic (triggered via `stack.schedule_merges` and `schedule_continuous_delivery`, app/models/shipit/commit.rb:281-287) runs deploys under that bot identity automatically once the commit becomes `deployable?` (app/models/shipit/commit.rb:227-229), so a forged `success` status for the required `review/approved` context can make the commit `deployable?` and trigger an unattended deploy, or conversely inject a `failure`/blocking status to halt a legitimate victim deploy.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `StatusHandler`) only validate signature and payload shape — none of them re-derive `repository_name` and constrain the `Commit` lookup to `Repository.from_github_repo_name(repository_name)`. The `Handler#stacks`/`repository_name` helper exists precisely for this purpose but `StatusHandler` doesn't use it, unlike other handlers that scope by `stacks`.

### Impact Explanation
An attacker who controls a repository that shares even one commit SHA with a victim's Shipit-managed stack can write arbitrary GitHub-style commit statuses (any `context`, `state`, `description`, `target_url`) onto the victim's `Commit` record for that SHA. This can flip a `review/approved` required-status context to `success`, satisfying `Commit#deployable?` and, on a stack with `Shipit.user`/bot-login auto-deploy configured, trigger an unauthorized deploy of attacker-influenced or unreviewed code, or conversely inject failing/blocking statuses to block or roll back a legitimate deploy. This is a cross-tenant write (a payload authenticated for repo A mutating stack/commit state that belongs to repo B) and directly maps to the "unauthorized deploy, rollback" Critical impact category. It is repeatable against any stack sharing SHAs with an attacker-controlled repository (forks, mirrors, shared history, or even coincidental cherry-pick collisions across unrelated projects), and the attacker does not need any Shipit session, API token, or repository maintainer role — only a repository whose webhook can be validly signed for the org/app on the Shipit installation.

### Likelihood Explanation
Preconditions: victim stack must require the `review/approved` (or similar) status context and have `bot_login`/`Shipit.user` configured for auto-deploy; the attacker must control (or push to) a repository whose commit history overlaps with the victim's repository at the SHA level (trivial for forks, common in monorepo mirrors, or with cherry-picked/rebased commits) and that repository must be reachable by a Shipit-recognized GitHub App/org so `verify_signature` passes. Cost is low: create a fork, push/tag a shared commit, and send one `status` webhook (or trigger it via the GitHub API on the attacker's own repo, which GitHub will deliver signed). This is repeatable at will since `StatusHandler` performs no idempotency/ownership check per request.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the repository that authenticated the webhook, mirroring the pattern already used by `Handler#stacks`:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
where `stacks` resolves via `Repository.from_github_repo_name(repository_name)` (payload's `repository.full_name`), ensuring a status webhook can only ever mutate commits belonging to stacks of the repository that signed it.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, hypothetical — no live GitHub):
1. Create `repository_a` ("victim/repo") and `repository_b` ("attacker/repo").
2. Create `stack_a` for `repository_a` with `bot_login` set (simulate `Shipit.user`) and configure `required_status_contexts`/`review/approved` as required.
3. Create `stack_b` for `repository_b` (attacker-controlled).
4. Insert `Commit` rows with the **same** `sha` (e.g., `"deadbeef" * 5`) for both `stack_a` and `stack_b` (simulating shared history).
5. Assert baseline: `commit_a.deployable?` is `false` (no `review/approved` success yet) — LHS `status.repository == commit_a.stack.repository` should be `"attacker/repo" != "victim/repo"`.
6. Call `Shipit::Webhooks::Handlers::StatusHandler.call('sha' => shared_sha, 'state' => 'success', 'context' => 'review/approved', 'repository' => { 'full_name' => 'attacker/repo', 'owner' => { 'login' => 'attacker' } })`.
7. Reload `commit_a`; assert `commit_a.statuses.where(context: 'review/approved').exists?` is now `true` and `commit_a.deployable?` becomes `true` (or `stack_a.schedule_merges` was invoked), proving the status webhook authenticated for `repository_b` mutated `repository_a`'s commit/stack state — violating the invariant that a `review/approved` status should affect only the repository that authenticated it.       already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
