## Analysis

The confirmed root-cause binding: `Repository.from_github_repo_name` matches solely on `owner/name` extracted from the JSON payload's `repository.full_name` [1](#0-0) , while `WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to authenticate the request against based on a *different* field: `repository_owner`, itself derived from `repository.owner.login` (falling back to `organization.login`) [2](#0-1) [3](#0-2) .

Both `repository.full_name` and `repository.owner.login` (or `organization.login`) are attacker-controlled fields inside the raw JSON body that is only integrity-protected as a whole by the HMAC signature — nothing forces `repository.full_name`'s owner segment to equal `repository.owner.login`/`organization.login`. Shipit explicitly supports one `GitHubApp`/`webhook_secret` per GitHub organization [4](#0-3) , documented for multi-tenant setups [5](#0-4) .

An attacker who legitimately controls one onboarded GitHub organization (and therefore legitimately knows that org's `webhook_secret`, which they themselves configured when creating their GitHub App) can send a signed payload to the shared `/webhooks` endpoint where `repository.owner.login`/`organization.login` = their own org (so `verify_signature` picks their own `GitHubApp` and the HMAC checks out), but `repository.full_name` = `"victim-org/victim-repo"`. `PushHandler`/`StatusHandler`/etc. only look up the target via `payload.dig('repository', 'full_name')` [6](#0-5) , so the handler resolves and mutates the victim's `Stack` (queuing `GithubSyncJob` for a push, writing `Commit` statuses, etc.) even though the signature never proved anything about the victim organization at all.

### Title
Webhook signature verification authenticates a different field than the repository the handlers act on, enabling cross-organization stack manipulation - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` used to validate `X-Hub-Signature` using `repository.owner.login` (or `organization.login`), but the event handlers that subsequently act on the payload (`PushHandler`, `StatusHandler`, `PullRequest::*Handler`) resolve the target `Repository`/`Stack` using the unrelated `repository.full_name` field. Since both fields live in the same attacker-supplied JSON body and are never cross-checked against each other, a valid signature from one legitimately-onboarded GitHub organization can be replayed with a forged `repository.full_name` pointing at a stack belonging to a different organization.

### Finding Description
Shipit supports hosting multiple onboarded GitHub organizations, each with its own `GitHubApp` config and `webhook_secret` [4](#0-3) . Every organization's webhooks are delivered to the single shared `/webhooks` endpoint, and the only authentication the endpoint performs is signature verification, keyed by whichever organization the request body itself claims to be from:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [7](#0-6) 

After the before_action passes, `create` dispatches the *entire raw payload* to the registered handlers for the event type [8](#0-7) . Every handler resolves the target repository using a *different* field of the same body:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

`Repository.from_github_repo_name` splits this `full_name` on `/` and looks up by `owner`/`name` alone, with no relation back to which `GitHubApp`/organization actually authenticated the request:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [1](#0-0) 

Nothing in the controller or handler pipeline asserts `repository.owner.login == repository.full_name.split('/').first`. This breaks the equality the design implicitly relies on: `organization that authenticated == repository that is written`. An attacker who is the legitimate admin of GitHub Organization A (and thus legitimately knows Org A's `webhook_secret`, since it is configured by whoever creates that org's GitHub App) can compute a valid HMAC over an arbitrary body where `repository.owner.login`/`organization.login` = `"OrgA"` (so `Shipit.github(organization: "OrgA")`'s secret is used and validates) while `repository.full_name` = `"OrgB/victim-repo"` (a repository/stack belonging to an unrelated onboarded organization B). The request passes `verify_signature` and is then processed as a legitimate event for OrgB's stack.

### Impact Explanation
This is a cross-repository/cross-organization write from an attacker who only controls webhook material for one onboarded organization:
- Via the `push` event, `PushHandler` will call `stack.sync_github(expected_head_sha:)` on any of victim's non-archived stacks matching the forged branch, triggering `GithubSyncJob`, which fetches commits from GitHub for the victim repo and can affect deploy/rollback state and continuous deployment eligibility [9](#0-8) .
- Via the `status` event, `StatusHandler` will attach forged CI statuses to any victim `Commit` matching an attacker-chosen `sha`, which can flip merge-queue/deploy-eligibility gating that depends on CI status [10](#0-9) .
- The `pull_request` handlers similarly resolve their target `Repository` via `params.repository.full_name` and can archive/unarchive review stacks belonging to a different organization's repository [11](#0-10) .

This matches the in-scope Critical category "cross-repository writes / an unauthorized deploy, rollback or merge," since it allows one tenant organization to forge state-changing events (sync, CI status, PR archival) against another tenant's stack.

### Likelihood Explanation
Moderate-to-high in any multi-tenant Shipit deployment (explicitly documented and tested as a supported configuration, see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`). Any attacker onboarded as an admin of one organization's GitHub App knows that org's `webhook_secret` (they configure it when creating the App) and can freely POST arbitrary JSON bodies to the shared, unauthenticated `/webhooks` endpoint — no GitHub-side delivery is required, since Shipit accepts any HTTP request bearing a matching HMAC, and both `repository.owner.login`/`organization.login` and `repository.full_name` are plain body fields the attacker fully controls.

### Recommendation
After `verify_signature` resolves `repository_owner` and validates the signature, re-derive the acting repository/organization strictly from that same verified `repository_owner` (or verify that `payload.dig('repository','full_name').split('/').first == repository_owner`) before dispatching to handlers, rejecting the event otherwise. Handlers should not independently re-parse `repository.full_name` without this cross-check, closing the gap between "who authenticated" and "what gets written," mirroring the pattern noted in the analog report where an unchecked field silently diverged from the one actually enforced.

### Proof of Concept
1. Attacker legitimately administers GitHub App "OrgA" onboarded in Shipit's `secrets.yml`, and thus knows `OrgA`'s `webhook_secret`.
2. Attacker crafts a JSON push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` and sends `POST /webhooks` with header `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "OrgA"`, loads `Shipit.github(organization: "OrgA")`, and the HMAC validates successfully.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which calls `Repository.from_github_repo_name("OrgB/victim-repo")` and triggers `stack.sync_github` for OrgB's stack — despite the request never being authenticated for OrgB.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

        end

        private

        end
      end
    end
  end
