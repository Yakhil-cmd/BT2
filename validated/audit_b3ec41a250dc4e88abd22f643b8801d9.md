### Title
Stale per-block index cache lets bad-debt write-downs be ignored, overvaluing zToken collateral for other users in the same block - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`v0-4-market.clar` caches each vault's `{index, lindex}` once per block in `index-cache` via `accrue-and-cache`, and every subsequent zToken price resolution in that block reads the cached value instead of the vault's live state. When a liquidation in that same block triggers `socialize-debt` on a vault (writing the vault's `lindex` down to reflect bad debt), the market's cache is never invalidated, so any other user's transaction later in the same block that resolves a zToken price for that vault will use the stale, higher `lindex` — exactly the class of bug described in the report (a decrease in the underlying accounted quantity is silently not propagated into a dependent accounting layer).

### Finding Description
`accrue-and-cache` populates `index-cache` keyed only by `{ timestamp: stacks-block-time, aid }` and returns the cached entry on any subsequent call within the same block: [1](#0-0) 

`resolve-ztoken`, used for all zToken/collateral price resolution, reads this cache directly rather than the vault's live `lindex`: [2](#0-1) 

During `liquidate`, the market first calls `accrue-user-debts`/`accrue-user-collateral` (which populate `index-cache` for the involved asset ids with the *pre-liquidation* index/lindex), and only later — within the same call, after collateral/debt updates — invokes bad-debt socialization when the borrower has no collateral left: [3](#0-2) 

Bad-debt socialization calls into the vault's `socialize-debt`, which writes the vault's `lindex` **down** to reflect the loss: [4](#0-3) 

This vault-level write-down happens entirely inside the vault contract's own state (`var-set lindex new-lindex`) and has no path back into the market's `index-cache` map. Since `index-cache` for that `{timestamp, aid}` was already primed (by the liquidator's own `accrue-user-*` calls, or by any earlier transaction in the block) with the pre-writedown `lindex`, it remains stale — reflecting a *decrease* that never gets propagated — for the remainder of the block. Exactly like the ValidatorManager example (an oracle-reported decrease that a dependent accounting layer ignores because only the increasing path is wired up), here the market's cached collateral pricing input is a one-shot snapshot that is never corrected downward even though the vault's true state changed later in the same block.

### Impact Explanation
Any other borrower (an unrelated, unprivileged principal — the "victim" here is actually the protocol/other suppliers, and the "attacker" is whoever exploits the stale cache) who holds the same zToken as collateral and performs `collateral-add`, `borrow`, or is evaluated for liquidation health later in the same block will have that zToken priced using the higher, stale `lindex` instead of the correct, lower post-bad-debt value. This lets that user:
- Borrow more than their true collateral value supports, or
- Avoid being flagged as liquidatable when they should be (their true LTV is worse than computed),

directly causing under-collateralized debt to be created/preserved in the same block a bad debt event occurred — a temporary but consequential freezing/impairment of protocol funds (unclaimed yield/solvency of suppliers), landing in the in-scope "temporary freezing of funds" / insolvency risk category, since positions opened or preserved on the mispriced snapshot persist into future blocks even after the cache invalidates.

### Likelihood Explanation
Requires: (1) a liquidation in a block that fully wipes a borrower's collateral and triggers `socialize-debt` on a vault whose zToken is used as collateral elsewhere, and (2) another transaction from a different user touching that same zToken later in the same block. Both are plausible under normal operation — liquidations and borrow/collateral operations from many users can land in the same block, especially under network congestion or bot-driven liquidation/borrow activity, and no special privilege is needed to trigger either side.

### Recommendation
Invalidate or refresh the market's `index-cache` entry for an asset whenever a vault write-down (e.g., `socialize-debt`) occurs, or have `vault-socialize-debt` return updated indexes that the market immediately re-caches (`map-set index-cache ...`) rather than relying on stale, pre-liquidation values for the remainder of the block. Alternatively, resolve zToken prices via a live vault read (bypassing the cache) whenever bad-debt socialization has occurred earlier in the same block.

### Proof of Concept
1. User A deposits USDC into `vault-usdc`, receiving zUSDC; User B uses zUSDC as collateral in the market (different position).
2. Early in block N, some transaction calls `accrue-user-collateral`/`accrue-user-debts` for `aid = USDC`, populating `index-cache { timestamp: N, aid: USDC } = { index, lindex: L0 }`.
3. Later in block N, a borrower C with USDC debt and no other collateral gets liquidated; `no-collateral-left` is true, triggering `socialize-debt-asset` → `vault-usdc socialize-debt`, which sets the vault's `lindex` to `L1 < L0`. [5](#0-4) 
4. Still within block N, User B calls `collateral-add`/`borrow`; `resolve-ztoken` for `aid = USDC` reads `get-cached-indexes` and gets the stale `L0` instead of the true `L1`. [2](#0-1) 
5. B's zUSDC collateral is valued using `L0` (too high), letting B borrow more than the true, post-bad-debt collateral value supports — a position that remains under-collateralized once the cache resets in block N+1.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))

    (print {
      action: "socialize-debt",
      caller: contract-caller,
      data: {
        scaled-amount: scaled-amount,
        debt-reduction: debt-reduction,
        principal-reduction: principal-reduction,
        old-lindex: current-lindex,
        new-lindex: new-lindex,
        old-total-assets: old-total-assets,
        principal-scaled: (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0),
        total-borrowed: (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0),
        index: idx
      }
    })

    (ok true)))
