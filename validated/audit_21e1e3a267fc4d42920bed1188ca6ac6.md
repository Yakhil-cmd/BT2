### Title
Unauthenticated null pointer dereference crashes full node during payment message validation - ([File: validation.js])

### Summary
`validatePayment()` in `validation.js` dereferences `payload.inputs[0].type` before verifying that the first element of `payload.inputs` is actually an object. Any unprivileged unit poster (or AA acting on attacker-controlled trigger data) can craft a unit whose asset-payment message has `inputs: [null]` (or any array containing a non-object first element), causing a synchronous `TypeError: Cannot read properties of null (reading 'type')` inside an asynchronous callback with no surrounding try/catch, analogous to the fluidsynth null pointer dereference (CVE-2025-56225) triggered by malformed/invalid input data.

### Finding Description
`validatePayment` checks only that `payload.inputs` is a non-empty array via `isNonemptyArray(payload.inputs)`: [1](#0-0) 

For asset payments, after loading the asset it immediately evaluates: [2](#0-1) 

before any per-input shape validation occurs. The actual per-element check (`isNonemptyObject(input)`) only happens later, inside `validatePaymentInputsAndOutputs`'s `async.forEachOfSeries` loop over `payload.inputs`: [3](#0-2) 

But that check happens *after* line 2099 has already executed. If `payload.inputs[0]` is `null` (which passes `isNonemptyArray` since the array itself is non-empty and has one element), `payload.inputs[0].type` throws a `TypeError`. This code executes inside the callback passed to `storage.loadAssetWithListOfAttestedAuthors`, i.e., inside an asynchronous I/O callback: [4](#0-3) 

There is no `try/catch` wrapping this callback, and the overall `validate()` function's `async.series` machinery in the caller does not guard synchronous throws raised inside nested async callbacks like this one: [5](#0-4) 

A thrown exception inside an async callback executed via `process.nextTick`/I/O callback in Node.js is not caught by surrounding `try/catch` at the call site and becomes an unhandled exception. Unless the process has a global `uncaughtException` handler that safely no-ops (and the code that continued execution afterward remains consistent), this crashes the node process.

### Impact Explanation
This is directly reachable by any unprivileged unit poster: any wallet, hub client, or AA response can include a payment message referencing a non-base asset with `payload.inputs = [null]`. When a full node validates this unit (as required for every network participant to reach consensus), it hits the unguarded dereference and can crash the validating node process. Because unit validation is performed by every node that receives and validates the joint (through normal DAG unit posting flow), a single malicious unit can be used to repeatedly crash validating nodes, causing denial of service and a network unable to confirm new units — matching the accepted impact criteria (network unable to confirm new units) and mirroring the fluidsynth CVE's null-pointer/availability characteristics (CVSS C:N/I:N/A:H).

### Likelihood Explanation
Likelihood is high: crafting `payload.inputs: [null]` for an existing (or self-issued) asset requires no special privileges — only knowledge of a valid asset unit hash and standard unit-posting capability that is available to any ordinary user/wallet. No hub, node operator, or peer collusion is required; a single posted unit suffices to trigger the code path in every node that validates it.

### Recommendation
Move (or duplicate) the `isNonemptyObject(input)` shape check on `payload.inputs[0]` (and generally validate array element types) before any property access such as `payload.inputs[0].type`/`payload.inputs[0].address` in `validatePayment`, i.e., validate all `payload.inputs` elements are non-empty objects immediately after the `isNonemptyArray(payload.inputs)` check at line 2064, before entering the `storage.loadAssetWithListOfAttestedAuthors` callback. Additionally, wrap the callback body in try/catch and route any exception to `callback(err)` instead of letting it propagate as an uncaught exception, consistent with error handling patterns used elsewhere in `validation.js` (e.g., `catch(e){ return callbacks.ifJointError(...) }`).

### Proof of Concept
1. Construct a unit with a payment message for an existing non-base asset:
```json
{
  "app": "payment",
  "payload_location": "inline",
  "payload": {
    "asset": "<valid 44-char base64 asset unit hash>",
    "inputs": [null],
    "outputs": [ { "address": "<valid address>", "amount": 1 } ]
  }
}
```
2. Ensure `payload_hash` matches the computed hash so the unit passes the early payload-hash check in `validate()`.
3. Post/broadcast this unit to a node (e.g., via `hub/joint` / device / peer post channels reachable by an ordinary user).
4. During validation, `validatePayment` loads the asset successfully, reaches line 2099 `payload.inputs[0].type`, and throws `TypeError: Cannot read properties of null (reading 'type')` inside the `storage.loadAssetWithListOfAttestedAuthors` callback, which is uncaught, crashing the node process.
