Confirmed: the `CCMenuController` overrides the `stack` and `authenticate_api_client` methods to bypass the stack-scoping logic that every other API controller inherits from `BaseController`.### Title
CCMenu API endpoint bypasses per-stack `ApiClient` scoping, allowing a token authorized for one stack to read the deploy state of any other stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides both `authenticate_api_client` and `stack` to skip the stack-scoping enforcement that `Shipit::Api::BaseController` applies to every other API endpoint, letting any `read:stack`-permitted `ApiClient` token read the CCMenu XML build status for a stack it was never granted.

### Finding Description
`Shipit::Api::BaseController` restricts the set of stacks an `ApiClient` may act on based on whether the client record has a `stack_id`: [1](#0-0) 

This `stacks`/`stack` pair is what every other API controller (e.g. `StacksController#stack` at `stacks.from_param!(params[:id])`, `HooksController`) relies on to enforce that a token scoped to one stack cannot touch another stack's resources.

`CCMenuController`, however, replaces both the authentication and stack-resolution logic: [2](#0-1) 

`authenticate_api_client` authenticates the token directly via `ApiClient.authenticate(params[:token])` (bypassing `BasicAuth`/`stacks` scoping setup), and `stack` resolves the target stack with the unscoped `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!(params[:stack_id])` used elsewhere. `ApiClient#check_permissions!` only checks whether the string `"read:stack"` is present in the client's `permissions` array — it never compares the client's `stack_id` against the requested stack: [3](#0-2) 

The binding broken is: **the stack a token authorizes (`ApiClient#stack_id`) ≠ the stack the CCMenu endpoint actually touches (`params[:stack_id]` resolved unscoped)**.

Any legitimate `read:stack` token — including one explicitly scoped to a single stack, such as the fixture `here_come_the_walrus` (`stack: shipit`) — can be replayed against `GET /api/stacks/*stack_id/ccmenu` for a *different* `stack_id` and will successfully render that other stack's latest deploy/build status: [4](#0-3) 

Notably this endpoint is also the one exposed to unauthenticated browsers via the "CCMenu URL" feature, whose token is auto-created with only `read:stack` permission and no explicit `stack` binding enforced at the CCMenu controller layer: [5](#0-4) 

### Impact Explanation
This is an unauthenticated-read-across-scope issue: a holder of any valid `read:stack` API token (even one deliberately scoped to a single stack in the `ApiClient` record) can retrieve deploy status, build label, and last build time for *any* stack in the Shipit instance by simply changing the `stack_id` route segment, without ever being granted access to that stack. This matches the defined High-severity category: "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Any actor who already possesses a stack-scoped `read:stack` token (a low-privilege, narrowly-scoped credential, e.g. one issued by the CCMenu "generate URL" feature for a single stack) can exploit this by simply substituting a different `stack_id` in the request path — no additional access or social engineering is required.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped `stacks` collection (`stacks.from_param!(params[:stack_id])`) inherited from `BaseController`, and remove the custom `authenticate_api_client` override (or have it still populate `@current_api_client` through the same scoping-aware path) so the CCMenu endpoint enforces the same per-token stack binding as every other API resource.

### Proof of Concept
1. Create/obtain an `ApiClient` token scoped to stack A (`stack_id` = A, `permissions` includes `read:stack`), e.g. via the CCMenu "generate URL" feature for stack A.
2. Send `GET /api/stacks/<owner>/<repo-of-stack-B>/<env-of-stack-B>/ccmenu?token=<stack-A-token>`.
3. Observe the response renders stack B's `deploys_and_rollbacks.last` build status in the CCMenu XML, even though the token was authorized only for stack A — confirmed by the code path in [6](#0-5) , which never checks `current_api_client.stack_id` against the resolved `stack`.
