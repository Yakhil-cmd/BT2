## Title
Multisig transaction execution can be run with an owner-supplied payload that diverges from the approved on-chain payload when `abort_if_multisig_payload_mismatch` is not enabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction` is the VM prologue function that gates execution of an approved `MultisigTransaction`. It enforces quorum/timelock, but the check that the *payload actually being executed* matches the *payload that owners approved* is unconditional only for the hash-based creation path. For the full-payload-stored path, the match is gated behind the feature flag `abort_if_multisig_payload_mismatch_enabled`. [1](#0-0) 

### Finding Description
`validate_multisig_transaction(owner, multisig_account, payload)` is invoked by the VM prologue with `payload` taken from the actual `SignedTransaction` being submitted by the executing owner, not from chain-stored state. It performs quorum, rejection, and timelock checks, then attempts to bind the submitted `payload` to the stored transaction record:

- If the stored record only has a `payload_hash` (created via the hash-only creation path), the hash of the submitted `payload` is checked unconditionally against the stored hash [2](#0-1) .
- If the stored record has a full `payload` (created via the plain `create_transaction` path), the equality check between submitted and stored payload is only performed `if (features::abort_if_multisig_payload_mismatch_enabled() && transaction.payload.is_some() && !payload.is_empty())` [3](#0-2) .

When the `abort_if_multisig_payload_mismatch` feature is not enabled, an owner who is allowed to execute a multisig transaction (because it already reached quorum for some specific approved payload) can submit a *different* payload in the actual `SignedTransaction` envelope. Prologue admission succeeds because quorum/timelock checks pass and the payload-equality check is skipped, so the VM proceeds to execute the owner-supplied payload under the multisig account's authority instead of the one the other owners actually approved.

### Impact Explanation
This breaks the core invariant of the multisig admission boundary: "the approval set that was collected for payload A must gate execution of payload A, not an arbitrary payload B chosen unilaterally by the executing signer." A single executing owner (who normally has no unilateral authority) can redirect quorum-approved authority to execute an entirely different entry function/arguments than what other owners signed off on, effectively achieving unauthorized state transition under the multisig account's signer, comparable to the admission-boundary "wrong approval set" pivot called out in scope.

### Likelihood Explanation
Exploitability depends entirely on the on-chain state of the `abort_if_multisig_payload_mismatch` feature flag: I was not able to confirm from the available code index whether this flag is enabled by default on mainnet/testnet or still pending rollout (it appears in `aptos-release-builder/src/components/feature_flags.rs` and `features.move` as a flag, consistent with a staged feature-flag rollout, but I could not verify its current activation state or the git history explaining why the check was made conditional). If the flag is currently disabled, exploitation only requires being one of the owners on a multisig account that created a transaction via the full-payload path (`create_transaction`, not `create_transaction_with_hash`) and reaching quorum — a low bar for any owner with signature rights.

### Recommendation
Make the payload/stored-payload equality check unconditional (remove the feature-flag gate) whenever `transaction.payload.is_some()`, mirroring the unconditional hash check for the hash-only path, so admission can never proceed with a payload that differs from what was approved. If the flag exists purely for staged rollout, ensure it is enabled before any multisig accounts using the full-payload creation path are in production use, and audit for any window where transactions could exploit the gap.

### Proof of Concept
1. Multisig account `M` with owners `{A, B, C}`, `num_signatures_required = 2`.
2. Owner `A` calls `create_transaction(A, M, payload_X)` — stores full `payload_X` on-chain (not just its hash).
3. Owner `B` calls `approve_transaction`, reaching quorum (2 approvals) for `payload_X`.
4. Owner `A` (or any owner with execute rights) submits a `SignedTransaction` whose actual multisig payload is `payload_Y` (an arbitrary different entry function call) targeting the same `multisig_account`/`sequence_number`.
5. In the VM prologue, `validate_multisig_transaction` runs: quorum passes (approvals were counted for the transaction record, not the payload bytes), and because `abort_if_multisig_payload_mismatch_enabled()` is false, the `payload_X == payload_Y` check at lines 1375-1384 is skipped.
6. The VM proceeds to execute `payload_Y` with the multisig account's signer — a transaction the quorum never approved.

I could not independently confirm the current activation state of `abort_if_multisig_payload_mismatch_enabled` in this snapshot, so I cannot state with certainty whether this is exploitable today versus already mitigated by governance activation of the flag; this is the one open uncertainty in this finding.

        // If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
