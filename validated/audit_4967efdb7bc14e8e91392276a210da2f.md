### Title
Cross-stack authorization bypass in CCMenu API endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the tenant-scoped `stack` resolver from `BaseController` with an unscoped lookup, letting a stack-scoped `ApiClient` token read build/deploy state for stacks outside its authorized scope.

### Finding Description
`Shipit::Api::BaseController` enforces per-token stack scoping through two cooperating private methods: [1](#0-0) 
`#stacks` restricts the visible collection to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` has a bound `stack_id`, and `#stack` resolves the requested record from that restricted collection via `stacks.from_param!(params[:stack_id])`. Every other API controller (e.g. `DeploysController`, `HooksController`) relies on this inherited `#stack`, so its `stack_id` scoping is respected.

`CCMenuController` instead defines its own `#stack`: [2](#0-1) 
which calls `Stack.from_param!(params[:stack_id])` directly on the model class, never going through the scoped `stacks` relation. The only access check performed is the class-level `require_permission :read, :stack` declaration, which is implemented by `ApiClient#check_permissions!`: [3](#0-2) 
This only verifies that `"read:stack"` is present in the token's `permissions` array — it has no notion of which specific stack the token is bound to. As a result, the binding "stack a token authorizes" (`current_api_client.stack_id`) is decoupled from "stack the request actually touches" (`params[:stack_id]` resolved via unscoped `Stack.from_param!`) specifically in this controller.

The `here_come_the_walrus` fixture demonstrates the intended scoping semantics — a token bound to a single stack: [4](#0-3) 
and existing tests confirm this scoping is enforced for `StacksController#index`: [5](#0-4) 
but no equivalent test exists (nor is the scoping enforced) for `CCMenuController#show`.

### Impact Explanation
An `ApiClient` token that was deliberately provisioned with access limited to one stack (a common configuration for giving a build-status widget, badge, or third-party CI-dashboard integration read-only visibility into a single project) can instead be used to read `deploys_and_rollbacks.last` state — build status, last build label/time, and web URL — for every other stack managed by the Shipit instance, including stacks belonging to different repositories/teams. This is an authorization-boundary break: the credential's authorized scope (one stack) diverges from the resource it can actually touch (any stack), disclosing deploy/task state across tenants without requiring any additional privilege.

### Likelihood Explanation
Exploitation requires only a valid, currently-scoped `ApiClient` token (or its `authentication_token`, which can also be passed as a `token` query/param per `CCMenuController#authenticate_api_client`) with the default `read:stack` permission — no elevated privilege, GitHub credentials, or additional access is needed. Any holder of a single-stack scoped token can enumerate other stacks' `stack_id`/param values (stack slugs are low-entropy and often guessable/enumerable, e.g. `owner-repo-environment`) and query them directly.

### Recommendation
Remove the `#stack` override in `CCMenuController`, or reimplement it using the inherited scoped `stacks` relation (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so that stack-scoped tokens are restricted consistently with every other API endpoint.

### Proof of Concept
1. Create two stacks, `stack_a` (owned by team A) and `stack_b` (owned by team B).
2. Create an `ApiClient` with `permissions: ['read:stack']` and `stack_id: stack_a.id` (analogous to the `here_come_the_walrus` fixture).
3. Authenticate as that client and request `GET /stacks/:stack_a_param/ccmenu.xml` — succeeds as expected.
4. Using the same token, request `GET /stacks/:stack_b_param/ccmenu.xml`.
5. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unscoped, the request resolves `stack_b` (bypassing the `current_api_client.stack_id` restriction enforced everywhere else) and returns `stack_b`'s deploy/build status, even though the token was never authorized for `stack_b`.
