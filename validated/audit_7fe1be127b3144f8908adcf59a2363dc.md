### Title
Missing `return` after private-payment hash failure causes duplicate processing / double-callback in `handleSavedPrivatePayments` - ([File: network.js])

### Summary
`handleSavedPrivatePayments()` in `network.js` iterates over queued rows from `unhandled_private_payments` and, for each one, calls an inner `validateAndSave` function [1](#0-0) . Inside `validateAndSave`, when `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws, the `catch` block sends an error result and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — but execution is **not** stopped there; there is no `return` statement, so the function falls through and unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` with the same `cb` a second time [2](#0-1) . This is analogous to CVE-2020-12770's root cause: a cleanup/removal path is taken on a failure branch, but the caller keeps going as if nothing happened, leaving the tracked resource (`cb`, and the underlying `async.each` iteration state) in an inconsistent double-handled condition — the same class of bug as `sg_write` failing to stop after deciding to abandon a request.

### Finding Description
`handleSavedPrivatePayments` is periodically invoked (and after new private payments arrive) to process rows stored by `handleOnlinePrivatePayment`, which is reachable from any peer or hub sending a `private_payment`/`private_payment_chains` message and stored via `unhandled_private_payments` [3](#0-2) [4](#0-3) .

When processing a saved row, `validateAndSave` computes a hash of the head private element's payload to build a de-duplication `key`: [1](#0-0) 
If `objectHash.getBase64Hash` throws (e.g., because the JSON-decoded payload stored earlier contains a value type that the hashing routine cannot serialize, such as `undefined`/functions smuggled through JSON round-tripping edge cases, or excessively deep/malformed structures the sender controls end-to-end since the payload originates from an attacker-supplied `private_payment` message), the `catch` branch calls `deleteHandledPrivateChain(..., cb)` to remove the row and invoke the `async.each` callback once. Because there is no `return`, control proceeds to build `key` (with `json_payload_hash` now `undefined`) and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...ifOk/ifError/ifWaitingForChain call cb again...})`, each of which independently call `deleteHandledPrivateChain(..., cb)` or `cb()` again [5](#0-4) .

This results in `cb` from `async.each` being invoked twice for the same iteration item. In the `async` library, calling the same iteratee callback twice from one iteration can cause the overall `async.each` completion callback to fire prematurely/incorrectly and can also cause `unlock()` (from `mutex.lock(["saved_private"], ...)` wrapping the whole function) to be invoked twice, which trips the `mutex.js` invariant `if (!bLocked) throw Error("double unlock?")` [6](#0-5) , crashing the node process on an uncaught exception. Because this queue is drained repeatedly (`handleSavedPrivatePayments` re-runs on new private payments and via periodic light-client re-request logic), an attacker who can get one malformed payload into `unhandled_private_payments` can reliably trigger this path.

### Impact Explanation
An uncaught `Error("double unlock?")` thrown from the mutex module crashes the Node.js process (unhandled exception), which halts the local node entirely — it can no longer validate or confirm new units, satisfying the "network unable to confirm new units" impact bar for the affected node. Even absent a full crash, the duplicate/short-circuited callback path corrupts the `async.each` bookkeeping for the private-payment queue, potentially causing other queued private payment chains in the same batch to be skipped or double-processed, which is a functional correctness issue with financial payment data (private asset transfers).

### Likelihood Explanation
The trigger requires an attacker (any peer, or a hub relaying `private_payment_chains`) to supply a private-element `payload` whose `objectHash.getBase64Hash` call throws. Since the payload for private assets is attacker-controlled JSON stored verbatim in `unhandled_private_payments.json` and later `JSON.parse`d back into `arrPrivateElements`, edge cases (e.g., objects that produce non-deterministic key ordering, extremely large numeric precision, or malformed hidden-output structures) reaching the hashing utility unaltered are plausible, though I could not fully verify the exact conditions under which `object_hash.js`'s hash function throws (index limits did not surface its full body for review). The likelihood is therefore assessed as moderate — the code path (missing `return`) is a certain logic defect; whether the hash call can be made to throw for realistic attacker-supplied JSON needs confirmation against `object_hash.js`.

### Recommendation
Add a `return;` immediately after the `deleteHandledPrivateChain(...)` call inside the `catch` block in `validateAndSave` (network.js, around line 2477), so the function does not fall through to compute `key` and call `validateAndSavePrivatePaymentChain` a second time for the same row/callback. Additionally, consider guarding `cb` with a call-once wrapper throughout `handleSavedPrivatePayments` to make the code robust against any other latent double-invocation paths.

### Proof of Concept
1. As a peer (or hub), send a `private_payment_chains` / `private_payment` message whose head element's `payload` is crafted so that `objectHash.getBase64Hash(payload, true)` throws when later re-parsed from the stored JSON (exact payload shape needs confirmation against `object_hash.js`'s hashing implementation, which was not fully available for review due to index limits).
2. The payload is stored in `unhandled_private_payments` via `savePrivatePayment` [3](#0-2) .
3. When `handleSavedPrivatePayments` next processes this row, `validateAndSave` hits the `catch` branch, calls `deleteHandledPrivateChain(..., cb)`, then — due to the missing `return` — falls through and calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, which invokes `cb` (or `deleteHandledPrivateChain`) a second time [7](#0-6) .
4. The double callback into `async.each` combined with the surrounding `mutex.lock(["saved_private"], ...)` unlock logic [8](#0-7)  can trigger the `"double unlock?"` throw in `mutex.js` [6](#0-5) , crashing the node.

**Note on confidence:** I was unable to retrieve the full body of `object_hash.js`'s `getBase64Hash`/hashing implementation within the indexed context to conclusively demonstrate a concrete attacker-controlled payload that throws. The missing-`return` control-flow defect itself is confirmed directly from the code shown above; the exploitability precondition (an attacker being able to make the hash call throw) is plausible but not fully proven from available context. A full Devin session with complete repository access would be needed to construct and verify a concrete PoC payload.
