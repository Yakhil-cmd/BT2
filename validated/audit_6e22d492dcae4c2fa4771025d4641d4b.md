### Title
Bridge KLAY/ERC20 Transfer Permanently Locks Bridged Assets When `_to` Cannot Receive Tokens — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

In `handleKLAYTransfer` and `handleERC20Transfer`, the actual asset transfer to `_to` is the **last** operation in the function. If that transfer reverts — because `_to` is a contract without a payable fallback (KLAY case) or because `_to` is blacklisted by the ERC20 token (e.g., USDC) — the entire transaction reverts, rolling back all prior state updates including nonce advancement. The affected nonce is permanently unprocessable, the bridged assets are permanently locked in the bridge contract, and no built-in recovery mechanism exists.

---

### Finding Description

In `handleKLAYTransfer`:

```solidity
_setHandledRequestTxHash(_requestTxHash);          // line 81
handleNoncesToBlockNums[_requestedNonce] = ...;    // line 83
_updateHandleNonce(_requestedNonce);               // line 84

emit HandleValueTransfer(...);                     // line 86

(bool ok, ) = _to.call.value(_value)("");          // line 98
require(ok, "handleKLAYTransfer: transfer failed"); // line 99
``` [1](#0-0) 

All state mutations — `_setHandledRequestTxHash`, `handleNoncesToBlockNums[_requestedNonce]`, and `_updateHandleNonce` — execute before the KLAY `.call`. If `_to` is a contract whose fallback reverts (no `payable` fallback, or an explicit `revert()`), the `require(ok, ...)` causes the entire transaction to revert, undoing every state change. The nonce is never recorded in `handleNoncesToBlockNums`, so `lowerHandleNonce` never advances past it.

The same pattern exists in `handleERC20Transfer`:

```solidity
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
emit HandleValueTransfer(...);

if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), ...);
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);   // reverts if _to is blacklisted
}
``` [2](#0-1) 

`safeTransfer` (from OpenZeppelin's `SafeERC20`) propagates any revert from the token contract. For tokens with transfer blacklists (USDC, USDT, etc.), if `_to` is blacklisted after the `RequestValueTransfer` event was emitted on the source chain, every operator attempt to call `handleERC20Transfer` for that nonce will revert.

The nonce tracking state in `BridgeTransfer` is:

```solidity
uint64 public lowerHandleNonce;
uint64 public recoveryBlockNumber = 1;
mapping(uint64 => uint64) public handleNoncesToBlockNums;
``` [3](#0-2) 

`_updateHandleNonce` advances `lowerHandleNonce` only when consecutive nonces starting from `lowerHandleNonce` have non-zero entries in `handleNoncesToBlockNums`:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
``` [4](#0-3) 

Because the revert prevents `handleNoncesToBlockNums[N]` from ever being set, `lowerHandleNonce` is permanently stuck at `N`, and `recoveryBlockNumber` never advances past the block preceding nonce `N`.

There is no `skipNonce`, `cancelTransfer`, or admin escape hatch in the bridge contract. The bridge owner can call `setRunningStatus(false)` or `lockToken`, but neither can skip a stuck nonce or recover the locked assets.

---

### Impact Explanation

- **Permanent asset loss**: The KLAY or ERC20 tokens allocated to the stuck nonce are locked in the bridge contract with no withdrawal path.
- **Recovery system degradation**: `recoveryBlockNumber` is permanently frozen at the block before the stuck nonce. The `ValueTransferRecovery` subsystem (`node/sc/vt_recovery.go`) uses `recoveryBlockNumber` as its scan start point; it will perpetually re-scan the same block range and re-attempt the same failing transfer.
- **No admin remedy**: The bridge contract exposes no function to skip, cancel, or reassign a stuck nonce. Remediation would require a contract upgrade.

---

### Likelihood Explanation

- **KLAY path**: Any user can specify a contract address as `_to` in `requestKLAYTransfer`. Contracts without a `payable` fallback are common (e.g., ERC20 token contracts, multisigs that don't accept KLAY). A malicious user can deliberately deploy a contract whose fallback always reverts and use it as `_to` to grief the bridge at the cost of the bridged KLAY.
- **ERC20 path**: Tokens with transfer blacklists (USDC, USDT, and others) are explicitly supported by the bridge. A user's address can be blacklisted by the token issuer between the time the `RequestValueTransfer` event is emitted and the time operators call `handleERC20Transfer`. This is an externally-triggered, unprivileged condition.

---

### Recommendation

Separate the nonce-advancement state update from the asset delivery, mirroring the Axis Finance fix:

1. Mark the nonce as handled and advance `lowerHandleNonce` unconditionally.
2. If the transfer to `_to` fails, record the unclaimed amount in a pull-payment mapping (e.g., `mapping(address => uint256) public claimable`).
3. Expose a `claim()` function so the recipient can withdraw their assets independently.

Alternatively, add an owner-only `skipNonce(uint64 nonce)` function that marks a nonce as handled without executing the transfer, allowing the bridge to advance past a permanently stuck nonce (with the understanding that the corresponding assets are forfeited or handled off-chain).

---

### Proof of Concept

**KLAY scenario (griefing attack):**

1. Attacker deploys `Rejector` — a contract whose fallback always reverts.
2. Attacker calls `requestKLAYTransfer(Rejector, 1 ether, "")` on the source bridge, sending `1 ether`.
3. Bridge operators observe `RequestValueTransfer(KLAY, attacker, Rejector, 0, 1 ether, nonce=N, ...)` and call `handleKLAYTransfer(txHash, attacker, Rejector, 1 ether, N, blockNum, "")` on the destination bridge.
4. `(bool ok,) = Rejector.call{value: 1 ether}("")` returns `ok = false`; `require(ok, ...)` reverts the entire transaction.
5. `handleNoncesToBlockNums[N]` is never set; `lowerHandleNonce` stays at `N`.
6. Every subsequent operator retry for nonce `N` reverts identically.
7. The 1 ether in the destination bridge is permanently locked; `recoveryBlockNumber` is frozen.

**ERC20 blacklist scenario:**

1. Alice bridges 1000 USDC from the service chain to the main chain, specifying her main-chain address as `_to`. `RequestValueTransfer` is emitted with `nonce=N`.
2. Before operators call `handleERC20Transfer`, USDC issuer blacklists Alice's main-chain address.
3. Operators call `handleERC20Transfer(..., Alice, USDC, 1000, N, ...)`.
4. `IERC20(USDC).safeTransfer(Alice, 1000)` reverts (blacklisted recipient).
5. All state changes revert; nonce `N` is permanently unprocessable.
6. 1000 USDC is locked in the destination bridge with no recovery path. [5](#0-4) [6](#0-5) [7](#0-6)

    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
