### Title
Unbounded, unmetered allocation in `TrieViewer::view_access_keys` for accounts with many access keys - ([File: runtime/runtime/src/state_viewer/mod.rs])

### Summary
`view_access_keys` collects the entire iteration over an account's access-key trie prefix into a `Vec` in one shot with no pagination, item cap, or byte cap, unlike `view_state`, which enforces `paginated`/`limit`/`after_key` and (for unpaginated calls) an account-level `state_size_limit` gate. An account holder who funds enough storage staking to add a very large number of access keys can make calls to `view_access_keys` for that account allocate and serialize a response proportional to the number of keys, with no ceiling analogous to `view_state`'s explicit paging caps.

### Finding Description
`view_access_keys` (runtime/runtime/src/state_viewer/mod.rs:150-192) iterates `state_update.iter(&prefix)` over all trie entries under the account's access-key prefix and eagerly `.collect::<Result<Vec<_>, _>>()`s them at line 190, with no `limit`, `after_key`, or size-based early exit. `view_gas_key_nonces` similarly iterates `0..gas_key_info.num_nonces` and collects all of them (lines 194-222) without limit. By contrast, `view_state` (line 224 onward) takes explicit `limit: Option<NonZeroU32>` and `after_key: Option<&[u8]>` parameters and gates unpaginated requests against `self.state_size_limit` (lines 233-262), enforcing per-request bounds analogous to `MAX_VIEW_STATE_PAGE_ITEMS`/`MAX_VIEW_STATE_PAGE_BYTES` used by RPC-level pagination.

An unprivileged account holder can add many `AddKey` actions (and gas keys) to their own account, each requiring storage staking cost proportional to key count/size, and then query the account via the public `view_access_keys` RPC path. Because no per-call cap exists in this function, the number of keys that must be fetched from the trie, decoded, and materialized into the response is bounded only by how much storage-stake the attacker is willing to lock, not by any RPC-side or runtime-side safety limit specific to this call.

### Impact Explanation
This maps to a resource-exhaustion / liveness impact class (unbounded memory allocation and response size proportional to attacker-controlled state) rather than a funds-loss or consensus-safety issue, since `view_access_keys` is a view-only RPC call executed against historical/current trie state and does not affect consensus state or balances. The worst-case impact is increased memory/CPU usage and larger response payload for the node serving the RPC call for that specific account, potentially degrading service for concurrent RPC callers on that node — a node-level DoS/liveness concern, not a chain-halting or fund-loss bug.

### Likelihood Explanation
Exploitability requires the attacker to actually pay for storage staking for every additional access key/gas key added to their account — this is not free, and near protocol charges storage cost proportional to the number of access keys stored per account. This makes the attack costly and self-limiting (the attacker must lock funds proportional to state grown), and the resulting per-call cost is bounded by realistic economic limits an attacker is willing to pay, not literally unbounded. Whether the current storage-staking cost model makes accumulating "enough" keys to cause meaningful resource exhaustion economically infeasible could not be fully confirmed from the available context — the exact per-key storage cost constants and any protocol-level cap on the number of access keys per account were not located in the reviewed files, so the actual scale of an achievable attack (and whether it produces meaningfully more load than existing legitimate large-key accounts) remains unverified.

### Recommendation
Add explicit pagination/limits to `view_access_keys` (and `view_gas_key_nonces`) mirroring `view_state`'s `limit`/`after_key`/size-gate pattern, and enforce a hard cap on the number of keys/nonces returned per RPC call (with the RPC layer requiring callers to page through results), consistent with `MAX_VIEW_STATE_PAGE_ITEMS`/`MAX_VIEW_STATE_PAGE_BYTES`.

### Proof of Concept
Integration test: create an account, submit `AddKey` transactions to add the maximum number of access keys (and gas keys) affordable by the account's staked balance under current storage-staking costs, then invoke `TrieViewer::view_access_keys` for that account and measure allocation/response size growth as key count increases, asserting no cap is applied — in contrast to a parallel test on `view_state` with the same amount of stored data demonstrating that `limit`/`state_size_limit` bounds the response regardless of key count.     pub fn view_access_keys(
        &self,
        state_update: &TrieUpdate,
        account_id: &AccountId,
    ) -> Result<Vec<(PublicKeyHandle, AccessKey)>, errors::ViewAccessKeyError> {
        let prefix = trie_key_parsers::get_raw_prefix_for_access_keys(account_id);
        let access_keys =
            state_update
                .iter(&prefix)?
                .map(|key| {
                    let key = key?;
                    let key_handle = parse_key_handle_from_access_key_key(&key, account_id)
                        .map_err(|_| errors::ViewAccessKeyError::InternalError {
                            error_message: "Unexpected invalid access key from iterator"
                                .to_string(),
                        })?;
                    if let Some(_index) =
                        parse_nonce_index_from_gas_key_key(&key, account_id, &key_handle).map_err(
                            |_| errors::ViewAccessKeyError::InternalError {
                                error_message: "could not parse nonce index".to_string(),
                            },
                        )?
                    {
                        // This is a gas key nonce, skip it.
                        return Ok(None);
                    }
                    let access_key = near_store::get_access_key_by_handle(
                        state_update,
                        account_id,
                        &key_handle,
                    )?
                    .ok_or_else(|| {
                        near_primitives::errors::StorageError::StorageInconsistentState(format!(
                            "iterator yielded an access-key trie key with no value: {key_handle}"
                        ))
                    })?;

                    Ok(Some((key_handle, access_key)))
                })
                .filter_map_ok(|x| x)
                .collect::<Result<Vec<_>, errors::ViewAccessKeyError>>();
        access_keys
    }

    pub fn view_gas_key_nonces(
        &self,
        state_update: &TrieUpdate,
        account_id: &AccountId,
        public_key: &PublicKey,
    ) -> Result<Vec<Nonce>, errors::ViewGasKeyNoncesError> {
        let access_key =
            get_access_key(state_update, account_id, public_key)?.ok_or_else(|| {
                errors::ViewGasKeyNoncesError::GasKeyDoesNotExist { public_key: public_key.clone() }
            })?;
        // If the access key is not a gas key, treat as not found.
        let Some(gas_key_info) = access_key.gas_key_info() else {
            return Err(errors::ViewGasKeyNoncesError::GasKeyDoesNotExist {
                public_key: public_key.clone(),
            });
        };
        (0..gas_key_info.num_nonces)
            .map(|index| {
                get_gas_key_nonce(state_update, account_id, public_key, index)?.ok_or_else(|| {
                errors::ViewGasKeyNoncesError::InternalError {
                    error_message: format!(
                        "gas key nonce at index {} does not exist for account {} and public key {}",
                        index, account_id, public_key
                    ),
                }
            })
            })
            .collect()
    }
