### Title
Unicode bidirectional-override characters in PR/issue comment bodies are not stripped before terminal rendering, enabling Trojan-Source style command spoofing in `gh pr view --comments` output - ([File: pkg/markdown/markdown.go])

### Summary
`markdown.Render` (`pkg/markdown/markdown.go`) is a thin passthrough to `ghMarkdown.Render` with no sanitization of Unicode bidirectional control characters (U+202A–U+202E, U+2066–U+2069). `pkg/cmd/pr/shared/comments.go`'s `formatComment` feeds attacker-controlled `comment.Content()` directly into `markdown.Render` and prints the result to the terminal, so a PR/issue comment containing bidi override characters inside a fenced code block is rendered unmodified, allowing the *displayed* order of a shell command to differ from its *actual* byte order.

### Finding Description
`markdown.Render` at [1](#0-0)  simply forwards the raw text string to `go-gh`'s glamour-based renderer with no character filtering. `formatComment` in `pkg/cmd/pr/shared/comments.go` calls this directly on `comment.Content()` — attacker-controlled text from a PR/issue comment or review — and writes the resulting string straight to the output builder that is ultimately printed to the user's terminal: [2](#0-1) .

The codebase has an extensive, well-designed sanitization layer for terminal-injection risks — the `Untrusted` wrapper and `asciisanitizer`-based `ContentOut`/`SetContentSanitization` mechanism strip ASCII C0/C1 control bytes and escape sequences before untrusted content reaches the terminal, e.g. [3](#0-2)  and [4](#0-3) . However, this sanitization is scoped to ANSI/C0/C1 control characters, not to Unicode "format" characters such as bidi overrides (U+202A RLO/LRO, U+202D/E, U+2066–U+2069 isolates), which are ordinary printable Unicode code points outside the C0/C1 ranges. A repository-wide search found no handling of bidi/RTL/LTR override characters anywhere in the codebase. Additionally, `formatComment` writes `md` via plain `fmt.Fprint(&b, md)` into a `strings.Builder`, not through the `ContentOut`/asciisanitizer path at all — the comment body only goes through whatever glamour/goldmark does internally, and neither performs bidi stripping.

Because a terminal emulator that implements the Unicode Bidirectional Algorithm (several modern terminal emulators do, at least partially, for RTL/mixed-script support) will reorder glyphs according to embedded bidi control characters, an attacker can craft a PR comment with a fenced code block such that the rendered/displayed command text looks benign (e.g. `sudo apt update`) while the actual underlying bytes — which is what gets copied to the clipboard and pasted into a shell — contain a different, malicious command (e.g. by using RLO/PDF characters to reverse a hidden suffix into what looks like a comment or hides a `; rm -rf ~` after visual reordering). This is fed to the victim purely by them running `gh pr view --comments` (or `gh issue view --comments`) on an attacker-authored PR/issue, which is default, ordinary behavior.

### Impact Explanation
This maps to a "Trojan Source"-class impact: the code path can cause a locally-run gh command to display command text that visually differs from its byte-exact content within a fenced code block, and if the victim trusts the displayed text and copies/pastes it into a shell, this results in command execution the victim did not intend — a variant of client-side code/command execution via output spoofing. It matches GitHub bounty impact classes around "unexpected code execution as a result of interacting with attacker-supplied content" through a legitimate, unprivileged interaction path (viewing a PR/issue).

### Likelihood Explanation
Preconditions: an unprivileged GitHub user can post a PR/issue comment on any public repo, and any victim who runs `gh pr view --comments` / `gh issue view --comments` (or lets an agent view PRs, as many CI/agentic workflows do) against that content is affected — no admin rights, tokens, or MITM required. The remaining variable is whether the victim's terminal emulator renders Unicode bidi controls (not universal, but present in several actively used terminals with Unicode/RTL support), making this an environment-dependent but realistic and repeatable attack once such a terminal is in use.

### Recommendation
Strip or visibly neutralize Unicode bidirectional format control characters (U+202A–U+202E, U+2066–U+2069, and related Cf category characters) from untrusted markdown content before or during rendering — ideally as part of the same sanitization pass performed by `asciisanitizer`/`Untrusted`, or by adding an explicit bidi-stripping step inside `markdown.Render` (`pkg/markdown/markdown.go`) so all callers (PR/issue comments, gist view, discussion view, PR body, etc.) are protected uniformly, rather than only stripping ANSI escapes.

### Proof of Concept
```go
package markdown

import (
	"strings"
	"testing"
)

func TestRender_StripsBidiOverrideCharacters(t *testing.T) {
	// U+202E RIGHT-TO-LEFT OVERRIDE hidden inside a fenced shell code block.
	const rlo = "\u202E"
	const pdf = "\u202C" // POP DIRECTIONAL FORMATTING
	input := "```sh\nsudo apt update" + rlo + " ;lru- fr odus" + pdf + "\n```"

	out, err := Render(input)
	if err != nil {
		t.Fatalf("Render error: %v", err)
	}

	if strings.ContainsAny(out, "\u202A\u202B\u202C\u202D\u202E\u2066\u2067\u2068\u2069") {
		t.Fatalf("rendered output still contains Unicode bidi control characters, allowing display/byte mismatch:\n%q", out)
	}
}
```
Expected (current, vulnerable) behavior: the test fails because `Render` passes the RLO/PDF characters through unchanged, meaning the rendered code block bytes still contain the override sequence — a terminal that honors bidi will show reordered/misleading text while the copied bytes contain the reversed malicious suffix. A fix should make this test pass by stripping or escaping the bidi control characters.
