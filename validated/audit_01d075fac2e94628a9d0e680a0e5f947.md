### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` — (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits to update purely by `sha`, with no scoping to the repository that actually sent the webhook, unlike every other webhook handler in the codebase which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before touching any records. A correctly-signed webhook from a repository the attacker owns (or has push access to) can therefore attach a forged CI status to a commit belonging to an unrelated Victim stack, as long as the two repositories happen to share a commit SHA (trivially achievable via forking, since Git SHAs are content-addressed and preserved across forks/cherry-picks of unmodified commits).

### Finding Description
The broken binding: the code implicitly assumes
`Commit.where(sha: params.sha) == the set of commits belonging to the repository identified in payload['repository']['full_name']`.
In reality:
`Commit.where(sha: params.sha) == the set of ALL commits across ALL stacks/repositories in the Shipit instance that happen to have that sha`,
with no filter on `stack.repository`.

Code path:
- `app/controllers/shipit/webhooks_controller.rb#verify_signature` only checks that `X-Hub-Signature` is valid for `Shipit.github(organization: repository_owner)` — i.e., that the webhook was legitimately sent for *some* organization/repository Shipit trusts. It does not verify that the `sha` inside the payload actually belongs to that repository. [1](#0-0) 
- `app/models/shipit/webhooks/handlers/status_handler.rb#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
with no repository scoping at all — it doesn't even declare `requires :repository` in its `params` block. [2](#0-1) 
- Contrast with every other handler (`PushHandler`, `PullRequest::OpenedHandler`, `ClosedHandler`, etc.), which resolves `stacks`/`repository` from `payload.dig('repository', 'full_name')` before acting. [3](#0-2) [4](#0-3) 
- `Commit#create_status_from_github!` calls `add_status`, which creates a `Status` row, and if the commit's state transitions to `pending`/`success` it calls `stack.schedule_merges`, enqueuing `ProcessMergeRequestsJob` for the **Victim's** stack. [5](#0-4) 
- `ProcessMergeRequestsJob#perform` re-fetches real GitHub statuses via `merge_request.refresh!` (which appends, not replaces) and then checks `merge_request.all_status_checks_passed?`, which is computed from `head.statuses_and_check_runs` sorted by `created_at desc` per context. Because the attacker controls `context`, `state`, and `created_at` in the forged webhook payload, they can insert a status row that matches Victim's required check context with a newer `created_at` than the genuine (pending/failing) status, causing `all_status_checks_passed?` to return true and `merge_request.merge!` to execute a real merge via `stack.github_api.merge_pull_request`. [6](#0-5) [7](#0-6) 
- Independently of the merge job, `Commit#pending?/success?/error?/failure?/state` (delegated to `status`, `app/models/shipit/commit.rb:219`) and `Stack#merge_status` will reflect the forged state immediately, which is what the unauthenticated `MergeStatusController#check`/`show` endpoints expose (`skip_authentication only: %i[check show]`). [8](#0-7) 

Existing guards do not stop this: `verify_signature` authenticates the sending organization, not the sha-to-repository binding; `ExplicitParameters` schema for `StatusHandler` requires only `sha`/`state` and never validates repository ownership of that sha; there is no `require_permission!`/`stacks` scope check inside `StatusHandler#process`.

### Impact Explanation
An attacker who owns or can push to any GitHub repository whose organization/app installation is configured in this Shipit instance can inject a forged `Status` record onto a commit belonging to a completely unrelated Victim stack/repository, provided the SHA collides (easily arranged via a fork of a public Victim repo before divergence, or cherry-picking an unmodified commit). This is a "payload for one repository mutating another's stack/commit" — matching the Critical category. Consequences observed in the code:
1. Victim's `Commit#state`/`Stack#merge_status` publicly reflect a fabricated state via the unauthenticated `MergeStatusController#check`/`show` endpoints, which CI-gating automation may trust (High: unauthenticated read of forged stack state).
2. More severely, because a matching status transition triggers `stack.schedule_merges` → `ProcessMergeRequestsJob`, and the forged status can be crafted (context/created_at) to satisfy `all_status_checks_passed?`, this can lead to an actual unauthorized `merge_request.merge!` against the Victim's real GitHub repository (Critical: unauthorized merge).
Repeatable against any repository/stack pair sharing a colliding SHA; blast radius spans the whole multi-tenant Shipit instance since the lookup has zero repository scoping.

### Likelihood Explanation
Preconditions: attacker needs a repository (fork or owned repo) whose organization is configured in Shipit's GitHub App/webhook-secret settings (so `verify_signature` succeeds), and a SHA collision with the target commit — trivially satisfiable for public repos via forking prior to divergence, or for internal monorepos via cherry-picks. No Shipit session, API token, or `webhook_secret` for the Victim's org is required; only a legitimately signed webhook for the attacker's own (differently-scoped) repo/org. This makes the attack feasible for any user with fork/push access to a Shipit-connected organization, and fully repeatable/automatable per target commit.

### Recommendation
Scope `StatusHandler#process` (and any other sha-based handler) to the repository identified in the webhook payload, mirroring the pattern used by `Handler#stacks`/other handlers: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name(params.repository.full_name)`, and restrict the `Commit` lookup to `Commit.where(sha: params.sha, stack_id: repository.stacks.select(:id))` (or equivalent join) before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status webhook for repo A must not update a commit belonging to repo B's stack" do
          victim_stack = shipit_stacks(:shipit) # e.g. Shopify/shipit-engine
          victim_commit = shipit_commits(:first)
          victim_commit.update!(sha: "deadbeefcafedeadbeefcafedeadbeefcafe123")

          attacker_repo_payload = {
            "sha" => victim_commit.sha, # colliding sha from attacker's own repo
            "state" => "success",
            "context" => "ci/circle", # matches a required context on victim stack
            "created_at" => Time.now.utc.iso8601,
            "repository" => { "full_name" => "attacker/unrelated-repo" }
          }

          # Binding under test:
          # expected: victim_commit.statuses.count unchanged (webhook scoped to attacker/unrelated-repo)
          # actual:   victim_commit.statuses.count increases (StatusHandler ignores repository scoping)
          assert_no_difference -> { victim_commit.statuses.count } do
            Shipit::Webhooks::Handlers::StatusHandler.call(attacker_repo_payload)
          end
        end
      end
    end
  end
end
```
Full end-to-end proof would additionally: (1) POST to `WebhooksController#create` with a signature valid for `attacker/unrelated-repo`'s configured org, asserting `commit.statuses.count` changes for the Victim's commit; and (2) GET `/merge_status/*stack_id/check` for the Victim's stack asserting the response flips to `200 "ok"` as a result, demonstrating the unauthenticated read reflects the forged cross-repo state.

      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?

        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
