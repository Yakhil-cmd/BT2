### Title
Signature-verification identity (`repository.owner.login`) is never bound to the handler's write target (`repository.full_name`), allowing a no-secret org to authorize forged PR-closed webhooks that archive arbitrary review stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the `webhook_secret`) to verify a webhook against using `params.dig('repository','owner','login')`, while `Shipit::Webhooks::Handlers::PullRequest::ClosedHandler` locates the `Repository`/`ReviewStack` to mutate using the independent `params.dig('repository','full_name')` field of the same JSON body. Because `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever no `webhook_secret` is configured for the org named in `repository.owner.login`, an attacker who can get any org onto the "no secret" path can set `repository.full_name` to any other org/repo string and have the handler archive that unrelated stack.

### Finding Description
The broken binding: the question asserts an invariant that should hold — "the organization whose `webhook_secret` verified the request equals the organization that owns the repository/stack the handler writes." In code these are two different reads of the same attacker-supplied JSON body:

- Verification identity: `repository_owner` in [1](#0-0) , fed into `Shipit.github(organization: repository_owner)` and then `verify_webhook_signature` in [2](#0-1) .
- Mutation target: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` inside the handler, and `params.repository["full_name"]` / `params.number` used by `ReviewStackAdapter` to find and archive the stack: [3](#0-2)  and [4](#0-3) .

Root cause: `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for the resolved org: [5](#0-4) . There is no code anywhere that checks `repository.owner.login == repository.full_name.split('/').first`, so nothing prevents the JSON body from naming one org for signature bypass and a completely different `full_name` for the actual write.

Exploit flow: the attacker crafts a `pull_request` `closed` payload where `repository.owner.login` is set to an org that the Shipit deployment has configured with no `webhook_secret` (a legitimate but common multi-tenant misconfiguration — e.g. a sandbox/dummy org entry in `secrets.github`), while `repository.full_name` (and `number`) target a genuine, security-conscious org's repository/PR. `verify_signature` calls `Shipit.github(organization: 'no-secret-org').verify_webhook_signature(...)`, which returns `true` regardless of the `X-Hub-Signature` value/algorithm supplied (the check for `sha1` in `verify_webhook_signature` at line 80 is irrelevant here because the whole HMAC path is skipped by the `return true unless webhook_secret` guard). The request proceeds to `ClosedHandler#process`, which resolves the repository from the attacker-chosen `full_name` and calls `review_stack.archive!`, deprovisioning and archiving a `ReviewStack` belonging to the victim org — with none of the victim org's secrets ever having been checked.

Existing guards do not catch this: `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema in `ClosedHandler.params` only validates shapes/types, not cross-field ownership consistency; `GithubOrganizationUnknown`/422 handling only fires if the org name in `repository.owner.login` isn't configured at all, not if it is configured with an empty secret.

### Impact Explanation
An attacker can archive (and trigger deprovisioning of) a `ReviewStack` for a repository they do not control, as long as the Shipit installation has at least one configured GitHub org/app entry without a `webhook_secret`. Because the "signing" org and "target" org are decoupled fields in one JSON body, the same technique generalizes to any other `pull_request`-family handler that reads `repository.full_name` (`opened_handler.rb`, `labeled_handler.rb`, `reopened_handler.rb`, `unlabeled_handler.rb`, `assigned_handler.rb`, `edited_handler.rb`), and to `push`/`status` handlers that similarly key off `repository` fields — this is a cross-tenant "payload for one repository mutates another's stack" class Critical finding.

### Likelihood Explanation
This requires the Shipit deployment to have at least one org configured in `secrets.github` with a blank/absent `webhook_secret` — a real-world possibility for multi-org Shipit setups (test/sandbox/legacy entries, or an org added but not yet given a secret), but not guaranteed for every deployment. It is not attacker-controlled configuration; it depends on operator misconfiguration. Given that precondition, the attack is trivial and free: a single unauthenticated HTTP POST with a crafted JSON body, no valid GitHub secrets or session required, fully repeatable against any stack whose `full_name`/PR `number` the attacker knows.

### Recommendation
Cross-validate the identity used for signature verification against the identity used for the write: derive the verifying org strictly from the repository actually being mutated (e.g., resolve `Shipit::Repository` first, then verify the signature using that repository's known/configured `GitHubApp`, or reject if `repository.owner.login` does not match the owner segment of `repository.full_name`). Additionally, treat "no `webhook_secret` configured" as invalid/reject rather than "trivially verified" in `GitHubApp#verify_webhook_signature`, and require `X-Hub-Signature-256` instead of the legacy sha1-only check.

### Proof of Concept
Minitest plan (integration/controller test, no live GitHub):
1. Seed two orgs in test secrets/config: `"no-secret-org"` with `webhook_secret: nil`, and `"victim-org"` with a real secret (or use an existing fixture org as "victim").
2. Create a `Shipit::ReviewStack` fixture owned by `victim-org/victim-repo`, PR number `42`, not archived.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, body:
   ```json
   {
     "action": "closed",
     "number": 42,
     "pull_request": { "id":1, "number":42, "url":"u", "title":"t", "state":"closed",
       "additions":1, "deletions":1,
       "head": {"sha":"abc","ref":"branch"},
       "user": {"login":"attacker"},
       "assignees": [], "labels": [] },
     "repository": { "owner": { "login": "no-secret-org" }, "full_name": "victim-org/victim-repo" },
     "sender": { "login": "attacker" }
   }
   ```
   with header `X-Hub-Signature: sha1=deadbeef` (any bogus value).
4. Assert `response` is `:ok` (not `422`), proving `verify_signature` passed via the `no-secret-org` no-secret bypass — i.e. assert `Shipit.github(organization: 'no-secret-org').verify_webhook_signature(anything, anything) == true` while `Shipit.github(organization: 'victim-org').verify_webhook_signature(anything, anything)` was never invoked/would have returned `false`.
5. Assert the equality that should have held but didn't: `verifying_org = "no-secret-org"` vs `mutated_repository.owner_login = "victim-org"` — they differ.
6. Assert the victim `ReviewStack` fixture is now `archived?` (or `archive!` / `deprovision` was called), demonstrating the cross-tenant write.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
