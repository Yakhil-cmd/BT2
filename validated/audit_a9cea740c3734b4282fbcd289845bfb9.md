### Title
Cross-organization webhook signature confusion allows an onboarded GitHub org to trigger syncs/deploys on another org's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login`/`organization.login`, but the handlers that subsequently act on the payload resolve the target `Stack`/`Repository` from a *different* JSON field, `repository.full_name`. In a multi-org Shipit deployment (explicitly supported, see `docs/setup.md`), any onboarded organization that knows its own `webhook_secret` can sign a payload as itself while forging `repository.full_name` to point at a stack belonging to a completely different organization on the same instance.

### Finding Description
`verify_signature` derives the authenticating organization purely from attacker-suppliable JSON, then looks up the corresponding `GitHubApp`/secret and verifies the raw body against it: [1](#0-0) [2](#0-1) 

Once verification succeeds, `create` dispatches the *same* raw parsed payload to the registered handlers with no further binding to the organization that was used to authenticate it: [3](#0-2) 

Every repository-scoped handler (push, status, check_suite, pull_request) resolves the `Stack` to write to via `Handler#repository_name`, which reads `repository.full_name` — a field that is never checked for consistency with the `repository.owner.login`/`organization.login` field used to pick the verification secret: [4](#0-3) 

`PushHandler` then uses attacker-controlled `after` (target SHA) to force a sync/deploy pipeline on whatever stacks match the resolved (forged) repository and branch: [5](#0-4) 

The engine explicitly documents and supports hosting multiple, independently-configured GitHub organizations (each with its own `webhook_secret`) on a single Shipit instance: [6](#0-5) 

Because each org's administrator necessarily knows its own `webhook_secret` (they configure it when wiring up their org's GitHub webhook to point at the shared Shipit instance), an org can sign an arbitrary JSON body with its own secret while placing a foreign org/repo's `full_name` in the body. The equality that should hold — `organization used to select verification key == organization whose repository is written` — is never enforced; only `repository.owner.login`/`organization.login` is checked against the *signing* key, while write-side code trusts `repository.full_name` independently.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out as in-scope. A tenant/org that is legitimately onboarded to a shared Shipit instance — but has no privileges over another tenant's repository — can force `GithubSyncJob`/`sync_github` (via `PushHandler`) or fabricate commit `Status` records / check-suite refreshes (via `StatusHandler`/`CheckSuiteHandler`) against a stack owned by a different organization, supplying an attacker-chosen `after`/`sha`. Depending on stack configuration (e.g., `continuous_deployment: true`), this can force Shipit to sync to and potentially deploy an attacker-nominated commit SHA on a repository the attacker does not control, i.e., an unauthorized deploy/cross-repository write — a Critical-tier impact per the rules.

### Likelihood Explanation
Exploitation requires the attacker to control (administer) at least one GitHub organization already onboarded to the same shared Shipit instance and thus to know that org's `webhook_secret` — a normal, unprivileged (relative to Shipit itself and to the victim org) position explicitly enabled by the documented multi-org feature. No Shipit session, `ApiClient` token, `api_clients_secret`, or GitHub App private key is needed; the attacker only needs to be able to send a raw signed HTTP POST to Shipit's public webhook endpoint (which does not require going through GitHub — GitHub itself is not involved in validating field consistency).

### Recommendation
Bind the resolved target repository/stack to the same organization used for signature verification: after `verify_signature` succeeds, re-derive `repository_owner` from the (now-trusted) payload and require that `repository.full_name`'s owner segment matches `repository_owner`/`organization.login` before dispatching to handlers, rejecting mismatches with `422`. Alternatively, pass the verified organization into `Handler.call` and have `Handler#repository_name`/`stacks` validate that the resolved `Repository#owner` equals the verified organization.

### Proof of Concept
1. Onboard/attacker-controlled org `OrgTwo` is configured in Shipit per `docs/setup.md` with its own `webhook_secret` (`SECRET_TWO`), which its administrator necessarily knows.
2. Attacker crafts a JSON body targeting `OrgOne`'s stack while claiming to be `OrgTwo`:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-commit-sha-existing-in-OrgOne-repo>",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/secret-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_TWO, raw_body)>` and POSTs directly to Shipit's webhook endpoint with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'OrgTwo')` and succeeds, since the body was legitimately signed with `SECRET_TWO`.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('OrgOne/secret-repo')` (unrelated to `OrgTwo`) and calls `stack.sync_github(expected_head_sha: '<attacker-chosen-commit-sha>')` for `OrgOne`'s stack, causing Shipit to act on `OrgOne`'s repository/stack on behalf of `OrgTwo`'s forged request.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
