### Title
Unvalidated P2P Staking Info Delivery Allows Malicious Peer to Corrupt Validator Set and Reward Addresses During Fast Sync — (File: `datasync/downloader/queue.go`)

---

### Summary

During fast sync, `queue.DeliverStakingInfos` accepts `P2PStakingInfo` from any connected peer with a completely no-op validation function (marked `TODO`). Every other data type delivered during sync — bodies, receipts — is validated against a cryptographic commitment in the block header. Staking info is not. A malicious peer can respond to a `StakingInfoRequestMsg` with fabricated `CouncilRewardAddrs`, `CouncilStakingAmounts`, `KEFAddr`, and `KIFAddr`, which are then persisted to the node's database and used for proposer selection and reward distribution, causing the node to diverge from the canonical chain.

---

### Finding Description

`queue.DeliverStakingInfos` in `datasync/downloader/queue.go` contains a validate closure that unconditionally returns `nil`:

```go
// datasync/downloader/queue.go:956-958
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
```

Compare this to the sibling functions in the same file:

- `DeliverBodies` validates `types.DeriveTransactionsRoot(...) == header.TxHash`
- `DeliverReceipts` validates `types.DeriveReceiptsRoot(...) == header.ReceiptHash`

No equivalent commitment for staking info exists in the block header, so the TODO has never been resolved.

**Full attack path:**

1. A malicious peer connects to a syncing node (any peer can connect to a public Kaia node).
2. During fast sync, the node sends `StakingInfoRequestMsg` to peers.
3. `handleStakingInfoMsg` in `node/cn/handler.go` decodes the response and calls `pm.downloader.DeliverStakingInfos(p.GetID(), stakingInfos)` — no content check is performed here either.
4. `Downloader.DeliverStakingInfos` in `datasync/downloader/downloader.go` forwards to `d.queue.DeliverStakingInfos(pack.peerId, pack.stakingInfos)`.
5. The no-op validate function accepts any content.
6. `commitFastSyncData` persists the fabricated staking info directly to the database:

```go
// datasync/downloader/downloader.go:1881-1884
if result.StakingInfo != nil {
    d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
}
```

The `P2PStakingInfo` struct carries all fields that govern validator selection and reward routing:

```go
// kaiax/staking/p2p_staking_info.go:31-47
type P2PStakingInfo struct {
    BlockNum              uint64
    CouncilNodeAddrs      []common.Address  // validator node IDs
    CouncilStakingAddrs   []common.Address  // staking contract addresses
    CouncilRewardAddrs    []common.Address  // reward recipient addresses
    KEFAddr               common.Address    // KEF treasury address
    KIFAddr               common.Address    // KIF treasury address
    CouncilStakingAmounts []uint64          // weights for proposer selection
    ...
}
```

All of these fields are fully attacker-controlled.

The `SyncStakingInfo` recovery path (triggered via the `admin_syncStakingInfo` RPC) has the same missing validation at line 677, but that path requires admin access and is out of scope.

---

### Impact Explanation

The corrupted staking info is used for two critical functions:

1. **Weighted-random proposer selection**: `CouncilStakingAmounts` determines each validator's probability of being selected as block proposer. Fabricated amounts cause the node to compute a different proposer sequence than the rest of the network, producing consensus divergence on the affected node.

2. **Block reward distribution**: `CouncilRewardAddrs`, `KEFAddr`, and `KIFAddr` determine where block rewards and treasury allocations are sent. A node with corrupted reward addresses will compute incorrect reward distributions, causing it to reject valid blocks from honest validators (whose reward distributions match the true staking info) or produce invalid blocks if it is itself a validator.

The result is **persistent corruption of the staking info database** and **consensus divergence** on the affected node — an honest node that synced via fast sync will be unable to follow the canonical chain.

---

### Likelihood Explanation

- **No privilege required**: Any peer can connect to a public Kaia node. The `handleStakingInfoMsg` handler only checks that the engine is Istanbul with `WeightedRandom` policy — it does not authenticate the peer's data.
- **Fast sync is the default mode** for new nodes joining the network, making every newly syncing node a potential target.
- **The attack is trivially simple**: the malicious peer only needs to respond to `StakingInfoRequestMsg` with a crafted `P2PStakingInfo` payload. No cryptographic material is required.
- **The TODO comment confirms the gap is known** and intentionally deferred, meaning no guard was added in the interim.

---

### Recommendation

Add content validation in `queue.DeliverStakingInfos` analogous to the receipt and body validators. Since no staking info hash exists in the block header today, two options are available:

1. **Re-derive and compare**: Re-execute the staking info derivation from the block state for the delivered block number and compare it against the peer-supplied data. Reject mismatches.
2. **Add a staking info commitment to the block header**: Introduce a `StakingInfoHash` field (similar to `ReceiptHash`) computed at block production time, allowing the same hash-based validation pattern used for receipts and bodies.

Until one of these is implemented, nodes performing fast sync should only request staking info from trusted peers.

---

### Proof of Concept

A malicious peer that:

1. Connects to a syncing Kaia node running fast sync.
2. Waits for a `StakingInfoRequestMsg` (protocol version ≥ `kaia65`).
3. Responds with a crafted `StakingInfoMsg` containing a `P2PStakingInfo` where:
   - `CouncilRewardAddrs` are replaced with attacker-controlled addresses.
   - `CouncilStakingAmounts` are set to arbitrary values (e.g., giving one attacker node 100% weight).
   - `KEFAddr`/`KIFAddr` are replaced with attacker-controlled addresses.
4. The syncing node's `handleStakingInfoMsg` → `DeliverStakingInfos` → `queue.DeliverStakingInfos` accepts the data without validation.
5. `commitFastSyncData` calls `PutStakingInfoToDB` with the fabricated data.
6. The node now uses the corrupted staking info for all pre-Kaia-hardfork block processing: proposer selection diverges from the canonical chain, and reward distribution is computed against attacker-controlled addresses.

func (q *queue) DeliverReceipts(id string, receiptList [][]*types.Receipt) (int, error) {

// handleStakingInfoMsg handles staking information response message.
func handleStakingInfoMsg(pm *ProtocolManager, p Peer, msg p2p.Msg) error {
	if pm.chainconfig.Istanbul == nil || pm.chainconfig.Istanbul.ProposerPolicy != uint64(istanbul.WeightedRandom) {
		return errResp(ErrUnsupportedEnginePolicy, "the engine is not istanbul or the policy is not weighted random")
	}

	// A batch of stakingInfos arrived to one of our previous requests
	var stakingInfos []*staking.P2PStakingInfo
	if err := msg.Decode(&stakingInfos); err != nil {
		return errResp(ErrDecode, "msg %v: %v", msg, err)
	}
	// Deliver all to the downloader
	if err := pm.downloader.DeliverStakingInfos(p.GetID(), stakingInfos); err != nil {
		logger.Debug("Failed to deliver staking information", "err", err)
	}
	return nil
```

func (d *Downloader) commitFastSyncData(results []*fetchResult, stateSync *stateSync) error {
	// Check for any early termination requests
	if len(results) == 0 {
		return nil
	}
	select {
	case <-d.quitCh:
		return errCancelContentProcessing
	case <-stateSync.done:
		if err := stateSync.Wait(); err != nil {
			return err
		}
	default:
	}
	// Retrieve the a batch of results to import
	first, last := results[0].Header, results[len(results)-1].Header
	logger.Debug("Inserting fast-sync blocks", "items", len(results),
		"firstnum", first.Number, "firsthash", first.Hash(),
		"lastnumn", last.Number, "lasthash", last.Hash(),
	)
	blocks := make([]*types.Block, len(results))
	receipts := make([]types.Receipts, len(results))
	for i, result := range results {
		blocks[i] = types.NewBlockWithHeader(result.Header).WithBody(result.Transactions)
		receipts[i] = result.Receipts
		if result.StakingInfo != nil {
			d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
			logger.Info("Imported new staking information", "number", result.StakingInfo.BlockNum)
		}
	}
	if index, err := d.blockchain.InsertReceiptChain(blocks, receipts); err != nil {
		logger.Debug("Downloaded item processing failed", "number", results[index].Header.Number, "hash", results[index].Header.Hash(), "err", err)
		return fmt.Errorf("%w: %v", errInvalidChain, err)
	}
	return nil
```
