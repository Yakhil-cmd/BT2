## Finding

### Title
Attacker-controlled oracle address in `data_feed[[oracles=...]]` formula lets AA trigger senders supply their own "trusted" price/data source instead of a hardcoded one, enabling fabricated data-feed conditions that drive AA fund transfers/issuance - (File: formula/evaluation.js, formula/validation.js)

### Summary
The Malda incident stemmed from `Migrator.sol` letting the caller pass the Mendi Comptroller address dynamically instead of it being hardcoded, so an attacker supplied a malicious Comptroller and satisfied the contract's trust checks with fabricated data, minting an unauthorized position. The oscript/AA formula language in ocore has the same structural weakness for the `oracles` parameter of `data_feed[[...]]`/`in_data_feed[[...]]`: the address(es) treated as the "trusted oracle" are taken from whatever value the formula evaluates to at run time, including values sourced from `trigger.data` (fully attacker-controlled input), with no requirement that this value be a literal/hardcoded address baked into the AA definition.

### Finding Description
In `formula/validation.js`, `validateDataFeed`/`validateDataFeedExists` only validate the `oracles` field's address-format when it is a *literal string*; when it is a formula/expression the validator explicitly skips the check via the `if (typeof value !== 'string') continue;` branch: [1](#0-0) [2](#0-1) 

At execution time, `getDataFeed` in `formula/evaluation.js` reads `params.oracles.value` after it has been evaluated from the arbitrary formula and only checks that the resulting string looks like valid address(es) — it never enforces that the value originates from a constant/hardcoded literal in the AA definition: [3](#0-2) 

This is confirmed by the codebase's own test showing the oracle address is explicitly allowed to be sourced from unit input/trigger data: [4](#0-3) 

By contrast, when an "oracle" is referenced from an **address definition** (`in data feed` in `definition.js`), the oracle addresses must be literal, hardcoded values baked into the address definition at address-creation time — they cannot be attacker-supplied at spend time: [5](#0-4) 

This asymmetry means AAs (autonomous agents), which execute automatically and move funds based on formula results, can be written (intentionally or via a subtle bug) so that the "oracle" whose data feed is trusted for a payout/issuance decision is chosen from `trigger.data`. Since anyone can be the trigger sender for an AA, an attacker can supply their own address as `oracles`, then author a `data_feed` message from that same address with values crafted to satisfy the AA's condition (e.g., `data_feed[[oracles=trigger.data.oracle, feed_name="price", feed_value>threshold]]`), causing the AA to release funds, mint an asset, or otherwise take an action gated on a data source that is not actually trusted — exactly the "dynamic trusted-authority address instead of hardcoded" pattern from the Malda report.

### Impact Explanation
Any AA whose payout, minting, or state-transition logic relies on a `data_feed`/`in_data_feed` formula where the `oracles` parameter is derived (even partially) from trigger data or other attacker-influenced input is exposed to unauthorized fund release, incorrect asset issuance, or logic bypass, because the "oracle" is not cryptographically or structurally bound to be the AA author's intended source. This matches the "AA fund loss" and "unauthorized spending/issuance" impact categories.

### Likelihood Explanation
Exploitation requires an AA author to (intentionally or mistakenly) let the `oracles` field of `data_feed`/`in_data_feed` be influenced by trigger/user-supplied data rather than a hardcoded address — a realistic pattern for AAs designed to support "bring your own oracle" configurability, similar to how `Migrator.sol` accepted a caller-supplied Comptroller for flexibility. Any unprivileged trigger sender can then act as both the caller and the fabricated oracle to satisfy the condition, requiring no special privilege — only that they post a `data_feed` message from an address they control before/along with the triggering unit.

### Recommendation
- Add a validation rule (in `formula/validation.js`'s `validateDataFeed`/`validateDataFeedExists`) that rejects non-literal (formula-derived) `oracles` values, or at minimum flags/warns when `oracles` depends on `trigger.data`/`params` rather than being a compile-time constant of the AA definition.
- Document and, where feasible, enforce that oracle addresses used for AA financial decisions must be hardcoded in the AA's own definition (mirroring the restriction already present for `in data feed` inside address definitions in `definition.js`), rather than allowing the trust anchor to be supplied dynamically by the calling party.

### Proof of Concept
1. Deploy an AA whose bounce/payment logic includes: `if: "{data_feed[[oracles=trigger.data.oracle, feed_name='price', feed_value>=100]]}"` guarding an unlock/issuance message.
2. As attacker, choose a fresh address `A` you control and set `trigger.data.oracle = A`.
3. Before/with the triggering unit, post a `data_feed` message authored by `A` with `price=100` (or any qualifying value).
4. The AA's formula evaluates `data_feed[[oracles=A, ...]]` to true because `getDataFeed` (formula/evaluation.js:600-618) merely checks address well-formedness of the run-time-supplied `A`, not that `A` is the AA-author's intended oracle, triggering the AA's fund-releasing/minting branch.
