### Title
`GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatic verification, allowing unsigned webhooks to be accepted - ([File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` delegates trust decisions entirely to `GitHubApp#verify_webhook_signature`, which short-circuits to `true` whenever no `webhook_secret` is configured for the resolved organization, before ever inspecting the `X-Hub-Signature` header or payload. Any organization configured without a `webhook_secret` therefore accepts arbitrary unsigned webhook requests, letting an unauthenticated attacker trigger real handler mutations (e.g. `CheckSuiteHandler` scheduling `RefreshCheckRunsJob` against a real stack/commit).

### Finding Description
The binding that should hold is: `verified == (signature cryptographically matches HMAC-SHA1(webhook_secret, raw_body))` for every organization Shipit is configured to serve webhooks for. Instead, in `lib/shipit/github_app.rb`:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [1](#0-0) 

if `webhook_secret` is `nil`/blank for the organization (`@webhook_secret = @config[:webhook_secret].presence` [2](#0-1) ), the method returns `true` unconditionally, regardless of whether `signature` is `nil`, malformed, or simply absent.

`WebhooksController#verify_signature` calls this method with the raw request signature and body and only rejects when it returns `false`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
``` [3](#0-2) 

An attacker who knows (or discovers) that a given organization's Shipit configuration has no `webhook_secret` set can `POST /webhooks` with a `check_suite` payload naming that organization's own repository, a real `head_branch`, and a real `head_sha`, and omit `X-Hub-Signature` entirely. `verify_signature` passes (`verified = true`), `create` proceeds, and `CheckSuiteHandler#process` runs `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...).each(&:schedule_refresh_check_runs!) }` [4](#0-3) , mutating real commit/check-run state without any authentication.

No other guard closes this gap: `drop_unhandled_event` only checks whether a handler exists for the event type [5](#0-4) ; `ExplicitParameters` schema validation only validates payload shape, not authenticity; there is no requirement elsewhere in the controller or `GitHubApp` that a `webhook_secret` must be present before a request is trusted.

### Impact Explanation
For any organization whose Shipit configuration omits `webhook_secret`, an unauthenticated, unprivileged internet attacker can submit arbitrary webhook payloads (any event type with a registered handler: `check_suite`, `push`, `status`, `membership`, etc.) that are accepted as if legitimately signed by GitHub. This drives real writes: scheduling check-run refresh jobs, creating commit statuses, enqueuing `GithubSyncJob`, and mutating team memberships — all without possessing GitHub's signing secret. This is a full authentication bypass on the webhook ingress endpoint, matching the "authentication bypass (forged webhook ... accepted)" Critical category. The blast radius is scoped to organizations lacking a configured `webhook_secret` (misconfiguration-dependent), but is fully repeatable and requires no privileges whatsoever.

### Likelihood Explanation
The only precondition is that the target organization's `GitHubApp` config has no `webhook_secret` set — a configuration state the code explicitly supports and does not warn against or reject (`@webhook_secret = @config[:webhook_secret].presence`). No other secret, session, or token is needed by the attacker; a single unauthenticated HTTP POST with a correctly shaped JSON body and correct `X-Github-Event` header is sufficient and infinitely repeatable.

### Recommendation
`verify_webhook_signature` should never treat an absent `webhook_secret` as automatic success. Options: (1) require `webhook_secret` to be present for any organization config and fail closed (raise/reject) if missing, rather than returning `true`; or (2) explicitly reject the request (return `false`/422) when `webhook_secret` is blank, forcing operators to configure a secret before accepting any webhooks for that organization.

### Proof of Concept
```ruby
# test/lib/shipit/github_app_test.rb
test "verify_webhook_signature rejects unsigned requests when no webhook_secret is configured" do
  github_app = Shipit::GitHubApp.new('org-with-no-secret', { app_id: 1, installation_id: 1 }) # no :webhook_secret key
  assert_equal false, github_app.verify_webhook_signature(nil, 'any body'),
    "verify_webhook_signature must not permissively return true when no secret exists to check against"
end

# test/controllers/webhooks_controller_test.rb
test "check_suite webhook without signature is rejected for org with no webhook_secret" do
  Shipit.stubs(:github).with(organization: 'org-with-no-secret')
    .returns(Shipit::GitHubApp.new('org-with-no-secret', { app_id: 1, installation_id: 1 }))

  request.headers['X-Github-Event'] = 'check_suite'
  body = JSON.parse(payload(:check_suite_master))
  body['repository']['owner']['login'] = 'org-with-no-secret'

  assert_no_enqueued_jobs do
    post :create, body: body.to_json, as: :json
  end
  assert_response :unprocessable_entity
end
```
Both assertions currently fail against the existing implementation (`verify_webhook_signature(nil, 'any body')` returns `true`, and the controller enqueues `RefreshCheckRunsJob` / returns `:ok`), confirming the vulnerability.

      return true unless webhook_secret

    end
