### Title
`Api::CCMenuController#stack` bypasses `current_api_client.stack_id` scoping, allowing cross-stack read with a stack-scoped token - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::BaseController#stacks` restricts every API controller to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` is scoped to a stack, and `Api::BaseController#stack` calls `stacks.from_param!(params[:stack_id])` to enforce that restriction. `Api::CCMenuController` overrides `#stack` with `Stack.from_param!(params[:stack_id])`, calling the class method directly on `Stack` and skipping the `stacks` scope entirely, so a token created for one stack can fetch the CC Menu XML of any other stack by substituting `stack_id` in the URL.

### Finding Description
The intended binding is: for every `Api::*Controller`, `stack ∈ Stack.where(id: current_api_client.stack_id)` when `current_api_client.stack_id?` is true. [1](#0-0) 

`Api::CCMenuController` redefines `stack` as: [2](#0-1) 

This calls `Stack.from_param!` directly (a class method on `Stack`, unrestricted), instead of going through the inherited `stacks` scope, so the equality `stack ∈ Stack.where(id: current_api_client.stack_id)` no longer holds for this controller — `stack ∈ Stack.all` regardless of the token's `stack_id`.

`ApiClient` supports a `stack_id` scope via `belongs_to :stack, optional: true`, and its permission check (`check_permissions!`) only validates the operation/scope permission string (e.g. `read:stack`), never the specific stack instance: [3](#0-2) 

So for any `ApiClient` that does have a `stack_id` set (e.g., one created scoped to a specific stack through the stack's settings, which is a supported model attribute), any other `Api::*Controller` (deploys, tasks, commits, etc.) enforces the stack restriction through `stacks.from_param!`, but `CCMenuController#show` — which calls `stack.deploys_and_rollbacks.last` — does not, because its private `stack` method bypasses `stacks` entirely. [4](#0-3) 

Attacker flow: attacker (or any Shipit user acting as attacker) obtains/holds a `token` for an `ApiClient` whose `stack_id` is set to stack A (any stack-scoped token with `read:stack` permission). They send `GET /api/stacks/B/cc_menu.xml?token=<token>` where B is an arbitrary stack ID/slug. `authenticate_api_client` in `CCMenuController` only verifies the token is a valid `ApiClient` — it does not check `stack_id` match: [5](#0-4) 
`require_permission :read, :stack` then passes because the token has `read:stack` in its permissions list, unconditional on which stack. `stack` resolves to stack B via unrestricted `Stack.from_param!`, and `show` renders B's latest deploy/rollback status. [6](#0-5) 

None of the existing guards catch this: `verify_signature`/webhook checks are irrelevant (this is an API GET, not a webhook); `ExplicitParameters` is irrelevant; the `stacks` scope exists but is simply not used by this controller's overridden `stack` method.

Note: the specific token minted by `CCMenuUrlController#fetch` (via `find_or_create_by!(creator:, name: 'CCMenu Client')` with no `stack:` attribute set) is itself unscoped (`stack_id: nil`), so for *that* particular client it already has access to `Stack.all` even under the correctly-scoped base implementation. The vulnerability is therefore most concretely demonstrable using any stack-scoped `ApiClient` (`stack_id` set to A) with `read:stack` permission, whose token — intended by the `stacks` scoping convention to only read stack A's data — can read arbitrary stack B's deploy/rollback status through this one controller.

### Impact Explanation
An attacker holding any stack-scoped API token with `read:stack` permission can read another tenant/repository's latest deploy or rollback state (commit SHA-ish info via the CC Menu XML, deploy status, running/ended state) for any stack in the Shipit instance, not just the one the token was issued for. This is an unauthenticated-cross-tenant read of build/deploy state, matching the "High: unauthenticated read of stack state" impact category. It is fully repeatable against any stack ID and does not require privileges beyond possessing any valid stack-scoped `read:stack` token.

### Likelihood Explanation
The attacker needs a valid `ApiClient` token scoped to some stack (any stack, even one they legitimately control) with `read:stack` permission — a normal, low-privilege API client that a repository maintainer would routinely be issued for their own stack's CI integration (e.g., CC Menu widget, monitoring tooling). No GitHub or Shipit secrets, no session, and no elevated role are required beyond holding this one token, and no live GitHub interaction is needed. This is high likelihood: any stack owner with API access to their own repo can pivot to reading any other stack's deploy status by changing a URL query parameter.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and rely on the inherited `Api::BaseController#stack`/`#stacks` methods (i.e., delete the `Stack.from_param!` override so it falls back to `stacks.from_param!(params[:stack_id])`), ensuring the `current_api_client.stack_id` scoping is enforced identically to every other API controller.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "#show does not leak another stack's status to a stack-scoped token" do
  stack_a = shipit_stacks(:shipit)
  stack_b = create_stack!(repository: create_repository!(name: 'other-repo'))

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'Scoped Client',
    stack: stack_a,
    permissions: %w[read:stack]
  )

  # Binding under test: stack ∈ Stack.where(id: current_api_client.stack_id)
  assert_equal [stack_a.id], Stack.where(id: scoped_client.stack_id).pluck(:id)

  get api_stack_ccmenu_url(stack_id: stack_b.to_param, token: scoped_client.authentication_token)

  # Expect this to be forbidden/not-found since stack_b is outside scoped_client's stack scope
  assert_response :not_found # or :forbidden, per fixed BaseController#stack behavior
end
```
Before the fix, this request returns `200 OK` with stack B's CC Menu XML, demonstrating cross-tenant read; after routing `CCMenuController#stack` through the inherited `stacks` scope, it returns `404`/`403`.
