### Title
Cross-organization confused deputy in webhook processing lets any configured org's identity forge writes against another org's repositories/teams - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the incoming HMAC signature against based on an **attacker-supplied, pre-verification** field (`repository.owner.login`, falling back to `organization.login`), while every `Handler` (`PushHandler`, `StatusHandler`, `MembershipHandler`, etc.) subsequently acts on a **different, independently-controlled** field (`repository.full_name` via `Handler#repository_name`, or `params.organization.login`/`params.team` for `MembershipHandler`) to decide which `Stack`, `Repository`, or `Team` gets written to. Nothing ties "the org whose secret authenticated this request" to "the repository/org/team the handler actually mutates."

### Finding Description
`verify_signature` picks the org config purely from payload content: [1](#0-0) [2](#0-1) 

The HMAC check itself is bypassed entirely when that org's `webhook_secret` is blank/unconfigured — a documented, supported configuration: [3](#0-2) 

Once "verified" (or trivially passed because the resolved org has no secret), the raw JSON body is dispatched to handlers, which derive the actual target **independently** from a different payload field: [4](#0-3) 

`PushHandler` uses this to locate arbitrary `Stack`s and trigger a sync to an attacker-chosen `expected_head_sha`: [5](#0-4) 

`MembershipHandler` uses the **`organization.login`** field (independent of the `repository_owner` used for verification) to create/find a `Team` and add/remove arbitrary `User` records from it: [6](#0-5) 

`Team`s are what gate `Shipit.github_teams` authorization (OAuth-team-restricted logins): [7](#0-6) [8](#0-7) 

Multi-org setups are explicitly supported and documented, each with its own independent (optionally-blank) `webhook_secret`: [9](#0-8) 

**Equality that should hold but doesn't:** `organization whose webhook_secret authenticated the request == organization/repository the handler writes to`. In reality, verification is keyed off `repository.owner.login`/`organization.login`, while `Handler#repository_name` and `MembershipHandler#find_or_create_team!` independently trust `repository.full_name` and the `organization`/`team` sub-objects to pick the mutated record. An attacker who can get one configured org accepted (trivial if that org's `webhook_secret` is left blank, which the shipped example configs show as a normal option — `webhook_secret: # nil`) can then set the "acted upon" fields to point at any other org/repo/team known to Shipit, since the two lookups are never cross-checked against each other.

This is the direct analog of the reported bug class: the report's root cause is "the step that authorizes an action (collateral seizure) is decoupled from the step that should have been re-checked before acting (debt already repaid)." Here, the step that authorizes the request (signature verification against org A's secret) is decoupled from the step that determines what gets mutated (org/repo/team parsed from a separate field), so the "authorized" binding and the "acted upon" binding can diverge.

### Impact Explanation
- If any configured GitHub org/app in the Shipit instance has no `webhook_secret` set (a supported, documented configuration state, not a violation of the mounting contract), an external, unauthenticated attacker can POST arbitrary webhook JSON to the public `/webhooks` endpoint and have it processed for **any other stack/repo/team** in the same Shipit instance, because signature verification is a no-op for that org and the handlers never confirm the acted-upon repository/org matches the verified one.
- Via `MembershipHandler`, this allows adding an arbitrary GitHub login as a member of any `Team` tracked by Shipit — directly escalating into `Shipit.github_teams`-gated authorization (High impact category).
- Via `PushHandler`/`StatusHandler`, this allows forcing `GithubSyncJob` to treat an attacker-chosen SHA as the expected head or forging commit `Status` records for arbitrary stacks, which can influence deployability checks used to gate deploys.

### Likelihood Explanation
Requires at least one org in a multi-org Shipit deployment to have a blank `webhook_secret` — a state the shipped example/dummy configs explicitly show as the default/common case (`webhook_secret: # nil` appears in `config/secrets.development.example.yml`, `test/dummy/config/secrets.yml`, `test/dummy/config/secrets_double_github_app.yml`, and `config/secrets.development.shopify.yml`). No credentials, tokens, or sessions are required — the webhook endpoint is public and unauthenticated by design (only the HMAC gate protects it).

### Recommendation
- After resolving and verifying the payload against an org's secret, re-derive the acted-upon repository/organization/team from the same trusted org context, and reject the webhook if the `repository.full_name` owner, `organization.login`, or `team.organization` does not match the org whose secret verified the signature.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for orgs participating in a multi-org configuration; require an explicit opt-in (or refuse unsigned webhooks entirely) when more than one org is configured.
- Bind `Handler#repository_name`/`MembershipHandler#find_or_create_team!` lookups to the verified organization context rather than trusting independent payload fields.

### Proof of Concept
1. Deploy Shipit with two orgs configured: `OrgA` (no `webhook_secret`) and `OrgB` (real secret, has a `Stack`/`Team` you want to attack), per the documented multi-org schema (`docs/setup.md` lines 182-209).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": {"id": 1, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/..."},
  "organization": {"login": "OrgB"},
  "member": {"login": "attacker-controlled-login"},
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/some-repo"}
}
```
3. `repository_owner` resolves to `OrgA` (`app/controllers/shipit/webhooks_controller.rb:59-62`), whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`) — no valid signature needed.
4. `MembershipHandler#process` then uses `params.organization.login` ("OrgB") and `params.team` to find/create the real `Team` for `OrgB` and adds `attacker-controlled-login` as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`), granting that GitHub identity whatever `Shipit.github_teams` authorization is scoped to that team.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
