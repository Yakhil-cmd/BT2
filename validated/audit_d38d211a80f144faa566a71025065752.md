### Title
Webhook signature is verified against the payload's `repository.owner.login` while the acted-upon repository is taken from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the `X-Hub-Signature` HMAC against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). But the handler that actually executes side effects, `Handler#repository_name` (used by `PushHandler`), reads a completely different field, `payload.dig('repository', 'full_name')`, to look up the `Repository`/`Stack` to act on. These two fields are never checked for consistency, exactly mirroring the reported bug class: two representations of the same conceptual entity (here, "which org/repo owns this webhook") are used inconsistently — one for the trust decision (signature verification), the other for the state-mutating action.

### Finding Description [1](#0-0) 

`verify_signature` picks the GitHub App/webhook secret using:
```ruby
github_app = Shipit.github(organization: repository_owner)
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Meanwhile `Shipit::Webhooks::Handlers::Handler#repository_name`, used by every handler (e.g. `PushHandler`) to resolve which `Repository`/`Stack` records to mutate, reads a different JSON path:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler#process` uses that repository/stack lookup to trigger `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the matching branch: [4](#0-3) 

`Shipit.github(organization:)` looks up per-organization GitHub App configuration (each org can have its own `webhook_secret`), and unknown organizations raise `Shipit::GithubOrganizationUnknown`, confirming this is a multi-tenant, per-org secret model.

The equality that should hold but is broken:
`org whose webhook_secret authenticates the request (repository.owner.login)` == `repository whose Stacks are synced (repository.full_name)`

An attacker who legitimately controls a GitHub organization/App that is configured in this Shipit instance (i.e., knows that org's own valid `webhook_secret`, which is intentionally shared with them as the org's own App admin — not privileged with respect to *other* tracked repositories) can send an authentic, correctly-signed payload where `repository.owner.login` is their own org, but `repository.full_name` is set to `some-other-org/some-other-repo` that is genuinely tracked by Shipit. The signature check passes (validated against the attacker's own org's secret), yet the mutating action (`PushHandler` → `Repository.from_github_repo_name` → `stack.sync_github`) is performed against the unrelated tracked repository, because the "which repo do we act on" decision reads a different, unauthenticated field.

### Impact Explanation
This breaks the deployment-trust binding "an organization that authenticated versus the repository that is written," as explicitly called out in the analog rules. It allows a user who administers one onboarded GitHub organization/App (an otherwise unprivileged party with respect to any other repository) to force `GithubSyncJob`/`sync_github` calls (fetching and writing new commit/CI state) against a Stack belonging to a completely different, unrelated repository — a cross-repository write triggered without ever presenting a signature verifiable against that target repository's own organization secret. This corresponds to "cross-repository writes" in the accepted impact list.

### Likelihood Explanation
Exploitation requires only that the attacker control one legitimately-configured GitHub App/organization in the Shipit instance (a normal, intended, low-privilege use case for any tenant of a shared Shipit deployment) and be able to send an arbitrary HTTP POST with a correctly computed HMAC signature for their own secret. No repository write access, session, or API token to the *target* repository is needed — only crafting the JSON body's `repository.full_name` field independently of `repository.owner.login`, both of which are attacker-supplied JSON keys with no cross-field validation.

### Recommendation
Derive both the signature-verification organization and the acted-upon repository from the same authenticated field. Either verify the signature against the same value used to resolve the target repository (`repository.full_name`'s owner segment) or, after signature verification, assert that `repository.owner.login` matches the owner parsed from `repository.full_name` before dispatching to handlers, rejecting the webhook otherwise.

### Proof of Concept
1. Assume Shipit is configured multi-tenant with `github.organizations` entries for `attacker-org` (with a known `webhook_secret_A`) and `victim-org` (tracking `victim-org/victim-repo` as a Stack).
2. Attacker computes `sha1=HMAC(webhook_secret_A, body)` for a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. POST to `/webhooks` with header `X-Github-Event: push` and the computed `X-Hub-Signature`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and validates successfully against `webhook_secret_A`. [5](#0-4) 
5. `PushHandler#process` resolves `repository_name` as `victim-org/victim-repo` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's tracked Stack, even though the request was never authenticated for `victim-org`. [3](#0-2) [4](#0-3)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
