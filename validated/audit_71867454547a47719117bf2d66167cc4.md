### Title
`stake-update` can set an earlier `unlock-burn-height` than the staker's existing lock, allowing early/unauthorized unlock of PoX-5 STX - (File: `pox-locking/src/pox_5.rs`)

### Summary
`pox_lock_update_v5` (invoked by `handle_stake_lockup_update_pox_v5` for the `stake-update` contract-call in `pox-5.clar`) reschedules a staker's STX lock to whatever `unlock_burn_height` the contract call returns, calling `snapshot.update_unlock_v5(unlock_burn_height)` with no check that the new height is later than the account's currently stored `unlock_height`. This is the same equality violation as the reported bug: an entity that is supposed to only ever move a lock/end time forward instead overwrites it unconditionally, so a value computed to be earlier than the existing commitment silently shortens (or breaks) the lock.

### Finding Description
Compare the two node-side helpers that both reschedule a pox-5 lock's `unlock_height`:

- `pox_rollover_v5` (used for `stake`/`register-for-bond` roll-overs) explicitly enforces monotonicity: [1](#0-0) 
```
if unlock_burn_height <= bal.unlock_height() {
    return Err(LockingError::PoxInvalidUnlockHeight);
}
```

- `pox_lock_update_v5` (used for `stake-update`, i.e. lock-extension / lock-increase) has **no equivalent check** — it just calls `snapshot.update_unlock_v5(unlock_burn_height)` and proceeds: [2](#0-1) 

`update_unlock_v5` itself, at the balance-structure level, only guards against the height being in the past relative to `burn_block_height`, not against being earlier than the account's own existing `unlock_height`: [3](#0-2) 

`handle_stake_lockup_update_pox_v5` passes whatever `unlock-burn-height` the `stake-update` Clarity function returns straight into `pox_lock_update_v5` and then emits a lock event with that height: [4](#0-3) 

This mirrors the report's root cause exactly: WithdrawProxy set `s.finalAuctionEnd = new_end` unconditionally, trusting that new auctions always end later than old ones; here the node trusts that `pox-5.clar`'s `stake-update` always computes a `new-unlock-ht` that is `>=` the staker's current `unlock-height`. If any path through `stake-update` in `pox-5.clar` can, given some combination of `num-cycles`/timing/rollover inputs, compute a `new-unlock-ht` earlier than the stacker's stored `unlock-height` (e.g., due to a boundary/rounding condition analogous to a "reduced auction time" parameter change), the STX lock is rescheduled to an earlier height than what was previously committed, breaking the invariant that a staker's committed lock period is only ever honored or extended, never silently shortened by an un-validated write.

### Impact Explanation
Freezing/unlocking of staked STX is a Critical/High severity target per rules ("permanent freezing of staked STX" / "value unlocked early"). If `stake-update`'s computed height can (via a bug or edge case in the cycle-count computation) regress below the currently recorded `unlock_height`, the discrepancy at minimum causes lock-state to no longer reflect the amount of time actually committed by the staker/signer, which can let STX unlock earlier than the reward-cycle commitment implies — an "unlock value early" class finding, or conversely could desynchronize lock bookkeeping such that funds become unreachable by the normal unlock path. Because this is enforced asymmetrically (present in `pox_rollover_v5`, absent in `pox_lock_update_v5`), it indicates the invariant was known to matter but wasn't applied uniformly.

### Likelihood Explanation
This requires the `stake-update` Clarity function (`pox-5.clar`) to actually be able to produce a `new-unlock-ht` less than the stacker's existing `unlock-height` for some legal call sequence. I was not able to fully load and inspect the `stake-update` function body in `pox-5.clar` (the file is large, was truncated on read, and I could not locate `define-public (stake-update ...)` within the fetched portion) to confirm whether its own internal Clarity-level assertions already guarantee monotonicity before calling into `pox_lock_update_v5`. This is a real gap: the vulnerability is proven at the Rust/node trust boundary (missing defense-in-depth check), but whether it is *reachable* depends on contract-level guarantees I could not fully verify in this session.

### Recommendation
Add the same monotonicity guard used in `pox_rollover_v5` to `pox_lock_update_v5`:
```rust
let bal = snapshot.canonical_balance_repr()?;
if unlock_burn_height < bal.unlock_height() {
    return Err(LockingError::PoxInvalidUnlockHeight);
}
```
placed before (or in place of) the unconditional `snapshot.update_unlock_v5(unlock_burn_height)` call, so that the node itself enforces the invariant rather than solely trusting `pox-5.clar` to compute a non-decreasing height.

### Proof of Concept
Not independently reproduced end-to-end in this session — I could not confirm a concrete Clarity-level call sequence into `stake-update` in `pox-5.clar` that yields `new-unlock-ht < current unlock-height`, due to being unable to fully read that function's body before the session ended. The concrete code-level asymmetry (missing check in `pox_lock_update_v5` vs. present check in `pox_rollover_v5`) is directly cited above and is the basis for this finding; further work should trace `stake-update`'s cycle-count/height computation in `stackslib/src/chainstate/stacks/boot/pox-5.clar` to determine reachability.

pub fn pox_lock_update_v5(
    db: &mut ClarityDatabase,
    principal: &PrincipalData,
    unlock_burn_height: u64,
    new_total_locked: u128,
) -> Result<STXBalance, LockingError> {
    if unlock_burn_height == 0 {
        return Err(LockingError::PoxInvalidUnlockHeight);
    }
    if new_total_locked == 0 {
        return Err(LockingError::PoxInvalidLockAmount);
    }

    let mut snapshot = db.get_stx_balance_snapshot(principal)?;

    if !snapshot.has_locked_tokens()? {
        return Err(LockingError::PoxExtendNotLocked);
    }

    snapshot.update_unlock_v5(unlock_burn_height)?;
