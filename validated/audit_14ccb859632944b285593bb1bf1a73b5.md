### Title
Webhook signature verification selects the GitHub App/secret by the payload's `repository.owner.login` field while event handlers act on the payload's `repository.full_name` field, allowing a signature valid for one organization to authorize writes against a different organization's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (`Shipit.github(organization:)` supports per-org `app_id`/`webhook_secret`, as documented by `secrets_double_github_app.yml`), `WebhooksController#verify_signature` picks which organization's `webhook_secret` to verify the HMAC against using an **unverified** field read straight out of the raw JSON body, while the actual event-processing code that determines which `Stack`/`Repository` gets written to reads a **different** unverified field. This is the same bug class as the reported analog: a check (HMAC/organization binding) is satisfied using one identifier, while the privileged action is carried out using another identifier from the same untrusted payload, and the two are never cross-validated.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to look up the verification secret like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

`repository_owner` is taken directly from the unauthenticated JSON body, before any signature check has happened: [2](#0-1) 

`Shipit.github(organization:)` resolves per-organization config (each with its own `webhook_secret`) from `github_app_config`: [3](#0-2) 

Once the signature is accepted, the actual event handler (e.g. `PushHandler`, `StatusHandler`, etc.) resolves the target `Stack` using a *different* field of the same payload — `repository.full_name` — via the shared `Handler#repository_name`/`Handler#stacks` helpers: [4](#0-3) 

and, for example, `PushHandler#process` uses that repository scope to call `stack.sync_github`: [5](#0-4) 

Nothing enforces that `repository.owner.login` (used to select the verifying secret) matches `repository.full_name`'s owner (used to select the stack that gets synced/updated). Since both come from the same unauthenticated raw body, an attacker who owns/controls a GitHub App installation for *any* organization configured in Shipit's `secrets.github` map (i.e., knows that organization's `webhook_secret`, which is issued to them by GitHub for their own org, not a Shipit secret) can forge a payload where:
- `repository.owner.login` = attacker's own organization (so `Shipit.github(organization: "attacker-org")` picks the secret the attacker legitimately possesses and the HMAC check passes), and
- `repository.full_name` = `"victim-org/victim-repo"` (so `Handler#stacks` resolves the *victim*'s `Stack` and processes the event — e.g. enqueuing `GithubSyncJob`, updating commit `Status`, or triggering `RefreshCheckRunsJob` — against the victim's repository).

This breaks exactly the "organization that authenticated versus the repository that is written" binding called out as in-scope: the signature is verified against organization A's key, but the write happens against organization B's stack.

### Impact Explanation
This allows cross-organization/cross-repository writes: pushing forged `push`, `status`, or `check_suite` events into a victim stack's history/state without possessing the victim organization's webhook secret, GitHub App credentials, or repository access. Depending on the handler this can create fabricated commit statuses, trigger `sync_github` (which can pull/queue syncs for arbitrary target stacks), or affect merge-queue/check-run refresh logic — state manipulation of a stack the attacker does not own, achieved purely by holding a valid secret for an unrelated, attacker-controlled organization. This matches the "cross-repository writes" impact category.

### Likelihood Explanation
Requires the Shipit deployment to be configured with the multi-organization GitHub App schema (`Shipit.github_organizations` / per-org `secrets.github[org]`), which the engine explicitly supports and documents (`secrets_double_github_app.yml`). Any attacker who has been granted a GitHub App installation for one of the configured organizations (a normal, low-privilege scenario for org admins of any one of the multiple tenants) can exploit this without needing any Shipit-specific credential. No `ApiClient` token, `github_access_token`, or private key theft is needed — only knowledge of one org's own `webhook_secret`, which that org's admins legitimately hold.

### Recommendation
After `verify_webhook_signature` succeeds, re-derive the acting organization from the same trusted field the handlers use for repository resolution (`repository.full_name`'s owner segment) and require it to match the organization whose secret validated the signature; reject the webhook (422) on mismatch. Alternatively, verify the signature using the `full_name`-derived owner in the first place, rather than `repository.owner.login`/`organization.login`, so the same authenticated identity that unlocks verification is the one used to select the target repository/stack.

### Proof of Concept
1. Configure Shipit with the multi-org schema, e.g. `OrgAttacker` and `OrgVictim`, each with distinct `webhook_secret`s (per `test/dummy/config/secrets_double_github_app.yml` schema).
2. Attacker legitimately controls a GitHub App installed on `OrgAttacker` and therefore knows `OrgAttacker`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "deadbeef",
     "repository": {
       "owner": { "login": "OrgAttacker" },
       "full_name": "OrgVictim/victim-repo"
     }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgAttacker_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` computes `repository_owner = "OrgAttacker"`, calls `Shipit.github(organization: "OrgAttacker")`, and the HMAC check passes because the attacker used the correct secret for that org.
6. `PushHandler#process` runs and resolves `stacks` via `Repository.from_github_repo_name("OrgVictim/victim-repo")`, matching and calling `stack.sync_github` on the victim's actual stack — despite the attacker never possessing `OrgVictim`'s webhook secret or any credential related to the victim organization.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
