### Title
Webhook signature verification authenticates the organization owning the `repository.owner.login` field, but every handler dispatches writes based on the independent `repository.full_name` field, allowing a legitimate GitHub-App-owning attacker to forge events for a victim's stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret to validate a webhook against using `repository.owner.login` (or `organization.login`), while every downstream `Shipit::Webhooks::Handlers::Handler` subclass resolves the `Repository`/`Stack` to write to using the unrelated `repository.full_name` field. Because Shipit-engine explicitly supports multiple organizations, each with its own independently-configured `webhook_secret`, an attacker who legitimately administers one such organization's GitHub App can self-sign a webhook payload whose `owner.login` matches their own org (so it passes signature verification) but whose `repository.full_name` names a stack belonging to a different, victim organization on the same Shipit instance.

### Finding Description
Signature verification: [1](#0-0) [2](#0-1) 

This picks the `Shipit.github(organization: repository_owner)` app (and its distinct `webhook_secret`) purely from `repository.owner.login`.

Multi-organization deployments with per-org secrets are a documented/supported configuration: [3](#0-2) [4](#0-3) 

Once the signature is accepted, `params` (the full, attacker-controlled raw JSON) is dispatched unchanged to handlers: [5](#0-4) 

Every handler resolves the target repository/stack from a *different* JSON key, `repository.full_name`, not `repository.owner.login`: [6](#0-5) 

For example, `PushHandler` uses that same `stacks` helper to look up all matching stacks and trigger a sync: [7](#0-6) 

and the `PullRequest::OpenedHandler` independently resolves the repository from `params.repository.full_name` to create review stacks: [8](#0-7) 

Because the field used to select the HMAC secret (`repository.owner.login`) is never cross-checked against the field used to select the write target (`repository.full_name`), a payload is only ever authenticated for "some organization I administer," not for "the organization that owns the repository being acted on." This is exactly the "organization authenticated vs. repository written" binding break: the two fields are logically supposed to describe the same repository, but nothing enforces that equality, and each is consumed by a different, unrelated code path.

### Impact Explanation
An attacker who is a legitimate administrator of *any* GitHub organization/App configured on the shared Shipit instance (i.e., someone who knows their own org's `webhook_secret`, a routine, unprivileged capability for an org owner installing the Shipit GitHub App) can:
1. Craft a JSON body with `repository.owner.login` (or `organization.login`) = their own org, and `repository.full_name` = `victim-org/victim-repo`.
2. Sign the raw body with their own org's `webhook_secret` and `X-Hub-Signature` header.
3. POST directly to the engine's `/webhooks` endpoint (no GitHub source-IP restriction is present in `WebhooksController`).
4. Signature verification succeeds (`Shipit.github(organization: 'their-org')` accepts it), and the handler layer then acts on `victim-org/victim-repo`'s stacks — e.g. forcing arbitrary `push`/`status`/`pull_request`/`membership` events onto the victim's stacks, injecting attacker-chosen commit CI statuses, unarchiving/archiving review stacks, or adding arbitrary GitHub users/teams to the victim's `Team`/`User` records.

This crosses a repository/organization trust boundary using no credential belonging to the victim, satisfying the "cross-repository writes" / "unauthorized deploy" bar (forged CI status changes can flip `Commit#deployable?`, unblocking an otherwise-gated deploy pipeline for a repository the attacker does not own).

### Likelihood Explanation
Requires only that the shared Shipit instance is configured for more than one organization (a supported, documented setup) and that the attacker administers one of them — no access to the victim's GitHub App private key, `api_clients_secret`, or any Shipit `ApiClient` token is needed. This is a low-effort, direct request forgery once the attacker's own org's webhook secret is known to them (which it is, by design, since they configure it).

### Recommendation
In `WebhooksController#verify_signature`, after successfully verifying the signature, additionally assert that `params.dig('repository','owner','login')` (or `organization.login`) matches the owner encoded in `params.dig('repository','full_name')` before dispatching to handlers, rejecting (422) any mismatch. Alternatively, have handlers resolve stacks using the same organization identity that was used for signature verification rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Configure `secrets.yml` with two organizations, `attacker-org` (webhook_secret known to the attacker, who administers it) and `victim-org` (owns `victim-org/victim-repo`, a real Shipit stack).
2. Build a payload: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen sha>"}` (or a `status`-event payload with attacker-chosen `sha`/`state`/`description`).
3. Compute `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s `webhook_secret`.
4. `POST /webhooks` with `X-Github-Event: push` (or `status`) and the above headers/body.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, verifies successfully.
6. `PushHandler`/`StatusHandler` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and acts on the victim's stack (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-16`), despite the attacker never having proven control of `victim-org`.
