### Title
Webhook signature verification silently no-ops when `webhook_secret` is unset, allowing forged `membership` events to escalate into `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Summary
This maps to the same bug class as the audit finding: a security check is supposed to bind two things together (there, "current override" vs. "original campaign"; here, "the organization that is cryptographically proven to have sent a webhook" vs. "the organization whose `Team`/`Membership` records the webhook payload is allowed to mutate"), but a code path silently skips the check that is supposed to enforce that binding, letting an unprivileged actor act as if the binding held.

### Finding Description
`WebhooksController#verify_signature` selects a per-organization `GitHubApp` and asks it to verify the `X-Hub-Signature` header against the raw payload before any handler runs: [1](#0-0) 

The actual verification is implemented in `GitHubApp#verify_webhook_signature`: [2](#0-1) 

Note line 77: `return true unless webhook_secret`. `webhook_secret` is populated from the per-organization config key `webhook_secret`, which is explicitly optional (`@webhook_secret = @config[:webhook_secret].presence`): [3](#0-2) 

Shipit ships example/multi-org configuration where `webhook_secret` is intentionally left blank for an organization (`webhook_secret: # nil`): [4](#0-3) 

So for any organization configured without `webhook_secret`, `verify_webhook_signature` unconditionally returns `true` — the equality "payload is authenticated as coming from organization X" vs. "payload is treated as coming from organization X" is never actually checked; the second is trusted without the first.

Once `verify_signature` passes (unconditionally, in this configuration), `WebhooksController#create` dispatches the raw, attacker-controlled JSON body straight to the registered handler for the event type: [5](#0-4) 

`membership` events are dispatched to `Handlers::MembershipHandler`, which is registered as a default handler: [6](#0-5) 

The controller test suite confirms this handler mutates `Team` and `Membership` records directly based on unauthenticated payload content — creating a new team on the fly and adding/removing members purely from the JSON body: [7](#0-6) 

`Team#add_member` simply appends the resolved user to the team with no additional authorization check: [8](#0-7) 

Team membership is exactly what gates application access. `Shipit.github_teams` is derived from the OAuth app's configured `oauth_teams`: [9](#0-8) 

and `User#authorized?` checks membership in exactly those teams: [10](#0-9) 

This is enforced on every request via `Shipit::Authentication#force_github_authentication`: [11](#0-10) 

### Impact Explanation
For any organization whose Shipit GitHub App config omits `webhook_secret` (a supported configuration, not a misuse), an unauthenticated, unprivileged internet client can `POST` to the webhooks endpoint with `X-Github-Event: membership` and an arbitrary/garbage `X-Hub-Signature` (or none at all — the check trivially passes). The forged payload can specify a `team` object matching one of `Shipit.github_teams`' handles and a `member.login` equal to the attacker's own (real) GitHub username. `MembershipHandler` will create/update the `Team` and add the attacker as a `Membership`, with no verification that the request actually originated from GitHub. The attacker then completes an ordinary, unprivileged GitHub OAuth login to Shipit; `User#authorized?` now returns `true` because of the forged `Membership`, granting full authenticated access to the Shipit application — deploys, rollbacks, task triggers, etc. This is a direct escalation into `Shipit.github_teams` authorization, one of the explicitly in-scope High-severity impacts.

### Likelihood Explanation
Likelihood depends on operator configuration: it is only exploitable when at least one configured GitHub organization has no `webhook_secret` set. This is not a corner case invented for this analysis — Shipit's own multi-org test fixtures and documentation model configurations where `webhook_secret` is blank/commented out, and nothing in the code path forces it to be mandatory. Any deployment following that pattern (e.g., during initial setup before a secret is generated, or for a secondary/legacy org config) is immediately exposed, with no credentials, tokens, or repository access required by the attacker — only knowledge of a team handle used in `oauth_teams`, which is typically not secret.

### Recommendation
Make webhook authentication fail closed instead of fail open:
- In `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb`), reject the request (return `false`) when `webhook_secret` is blank, instead of returning `true`.
- Alternatively/additionally, require `webhook_secret` to be present at boot for every configured organization (validate configuration eagerly), so a misconfigured or intentionally-blank secret cannot silently disable authentication.
- Consider not deriving authorization-relevant `Team`/`Membership` state solely from webhook payload content; cross-check membership changes against a live GitHub API call before trusting them for authorization purposes.

### Proof of Concept
1. Operator configures two GitHub organizations in `secrets.yml`, where `OrgTwo` has no `webhook_secret` (mirrors the shipped test fixture): [4](#0-3) 
2. `Shipit.github_teams` includes a team belonging to `OrgTwo`, e.g. `oauth_teams: ["OrgTwo/admins"]`.
3. Attacker sends:
   ```
   POST /github/webhooks
   X-Github-Event: membership
   X-Hub-Signature: sha1=deadbeef   (any value, or omitted)

   {
     "action": "added",
     "organization": { "login": "OrgTwo" },
     "repository": { "owner": { "login": "OrgTwo" } },
     "team": { "id": 1, "name": "admins", "slug": "admins", "url": "https://api.github.com/..." },
     "member": { "login": "attacker-real-github-login" }
   }
   ```
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgTwo").verify_webhook_signature(...)`, which returns `true` unconditionally because `webhook_secret` is blank for `OrgTwo` (`lib/shipit/github_app.rb:76-77`).
5. `Handlers::MembershipHandler` (dispatched per `app/models/shipit/webhooks.rb:20`) creates/updates the `Team` and adds `attacker-real-github-login` as a member (behavior verified by `test/controllers/webhooks_controller_test.rb:129-165`).
6. Attacker performs a normal GitHub OAuth login to Shipit (`GithubAuthenticationController#callback`). `User#authorized?` now returns `true` because of the forged membership, and `force_github_authentication` grants full access.

Note: the exact internal matching logic of `Handlers::MembershipHandler` (e.g., how it looks up/creates the `Team` record from payload fields) could not be fully retrieved from the index due to size limits; the impact chain above is inferred from the handler's observable behavior in `test/controllers/webhooks_controller_test.rb` and the authorization code paths cited above. A full Devin session with repository access would be needed to confirm the exact matching semantics of `Handlers::MembershipHandler` and to build a fully runnable exploit script.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
