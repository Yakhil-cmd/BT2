### Title
Stack-scoped `ApiClient` tokens can read CCMenu build status for any stack, not just the one they are bound to - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` resolver used everywhere else in the API to enforce per-client stack scoping, and instead resolves the target stack directly from the request parameter without checking it against the authenticated `ApiClient`'s `stack_id`. This breaks the binding "stack a token authorises == stack a token touches": a client token scoped to stack A can be replayed against any other stack's `/ccmenu` endpoint to read its build status.

### Finding Description
`ApiClient` records can be scoped to a single stack via `stack_id`. The intended enforcement of this scope lives in `Shipit::Api::BaseController`: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` resolves `params[:stack_id]` through that restricted relation. Every other controller that needs "the current stack" (e.g. `CommitsController`) relies on this inherited `stack` method, so a stack-scoped token cannot touch a stack it wasn't issued for.

`CCMenuController`, however, defines its own `stack` method that bypasses `stacks` entirely and resolves the model directly: [2](#0-1) 

Permission checking here (`require_permission :read, :stack`) only validates that the client's `permissions` array contains `read:stack` via `ApiClient#check_permissions!`: [3](#0-2) 

`check_permissions!` never inspects `stack_id`, so the only place that binding was supposed to be enforced was the `stack`/`stacks` lookup in `BaseController` - which `CCMenuController` deliberately reimplements without that check. The `LEFT` side of the equality (`current_api_client.stack_id`, i.e. what the token authorizes) is therefore never compared against the `RIGHT` side actually acted upon (`params[:stack_id]`, i.e. what the request touches).

This is exploitable with completely ordinary, low-privilege tokens: e.g. the CCMenu-URL flow itself hands out `read:stack`-permissioned tokens to any logged-in user via `CCMenuUrlController`: [4](#0-3) 

and any stack-scoped `ApiClient` created through the "Humans" UI (`ApiClientsController`, scoped to one stack by an operator) is affected identically, since `check_permissions!` and `CCMenuController#stack` are the same code path regardless of how the token was minted.

### Impact Explanation
An attacker who obtains any valid API token carrying `read:stack` (a CCMenu URL leaked/shared for one project, or a deliberately stack-scoped `ApiClient` meant to be restricted to a single, possibly less sensitive stack) can enumerate `stack_id` path segments and read the CCMenu XML - build status, last build label/SHA, activity, web URL - for every stack managed by the Shipit instance, including stacks the token holder has no authorization for. This is an authorization-scope escalation matching the in-scope impact "unauthenticated read of stack state ... deploy output" achieved through a token whose authorized scope is bypassed.

### Likelihood Explanation
No special privilege is required beyond possessing any valid `read:stack` token (these are routinely distributed as CCMenu URLs to unauthenticated CI dashboard tools). The bypass requires only changing the `stack_id` segment of the URL; both `Stack.from_param!` and the route matcher accept arbitrary well-formed `owner/repo/environment` identifiers, so discovery of valid targets is trivial via the stack listing UI or predictable naming.

### Recommendation
Remove the `CCMenuController#stack` override and rely on the inherited, scope-aware `stacks`/`stack` methods from `BaseController` (i.e. `@stack ||= stacks.from_param!(params[:stack_id])`), so that stack-scoped tokens are restricted exactly like every other API endpoint.

### Proof of Concept
1. As an authenticated Shipit user, request a CCMenu URL for `stack A` via `GET /ccmenu/*stackA` (`CCMenuUrlController#fetch`); this returns a `token` for a `read:stack`-permissioned `ApiClient`.
2. Alternatively, have an operator create/observe a stack-scoped `ApiClient` (`stack_id = A`) through the `api_clients` UI.
3. Call `GET /api/stacks/*stackB/ccmenu?token=<token>` where `stackB != stackA`.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!`, the request succeeds and returns `stackB`'s CCMenu XML (build status, last build SHA/label, web URL), even though the token is only supposed to authorize `stackA`. [5](#0-4)

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
