### Title
Webhook signature verification is keyed to `repository.owner.login`/`organization.login` while push/check_suite/status handlers act on the unrelated `repository.full_name` field, letting a weakly-secured organization forge events for any other organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` chooses which GitHub App configuration (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, a value taken from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Every downstream event handler that actually mutates state, however, resolves the target repository/stack from a completely different, unrelated field: `payload.dig('repository', 'full_name')` in `Handler#repository_name`, used by `PushHandler` and `CheckSuiteHandler`. `StatusHandler` does not scope by repository at all. Because the field that is cryptographically authenticated (`owner.login`) is not the field that is acted upon (`full_name`), an attacker who can produce a validly-signed payload for one configured GitHub organization can point the "acted upon" repository at a stack that belongs to an entirely different, more strongly secured organization.

### Finding Description
`verify_signature` computes the verifying GitHub App from the request payload itself: [1](#0-0) 

`repository_owner` is derived purely from attacker-controlled JSON: [2](#0-1) 

Shipit supports multiple GitHub organizations, each with its own (optionally absent) `webhook_secret`: [3](#0-2) 

`verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for the resolved organization: [4](#0-3) 

Once the signature is accepted, the handlers ignore `repository.owner.login` entirely and instead resolve the stacks to act on from `repository.full_name`: [5](#0-4) 

`PushHandler` uses this `stacks` helper to trigger a GitHub sync with an attacker-supplied `expected_head_sha`: [6](#0-5) 

`CheckSuiteHandler` similarly uses `stacks` (i.e. `full_name`) to schedule check-run refreshes on commits of a stack resolved independently of the verified owner: [7](#0-6) 

`StatusHandler` is the most severe: it does not use `stacks`/`repository_name` at all, and instead creates a commit status for every `Commit` row across the entire installation matching a given `sha`, with fields taken verbatim from the payload: [8](#0-7) 

The bug-class binding being broken is: `verified_organization (repository.owner.login) == repository_acted_upon (repository.full_name)`. This equality does not hold — the engine authenticates one field and writes based on another, unrelated field, exactly matching the "organization that authenticated versus the repository that is written" analog.

### Impact Explanation
In a multi-organization Shipit deployment (explicitly supported per `config/secrets.development.example.yml`), if any configured organization has no `webhook_secret` set (or the attacker otherwise knows/controls a valid signature for a weakly-secured org), the attacker can send a webhook whose `repository.owner.login`/`organization.login` matches the weak org (so `verify_signature` passes trivially) but whose `repository.full_name` names a stack that actually belongs to a different, properly-secured organization tracked by the same Shipit instance. This lets the attacker:
- Forge `status` events that inject arbitrary `state`/`context`/`description` commit statuses for any commit SHA tracked anywhere in the Shipit instance, with zero repository scoping, potentially satisfying required-status gating used to unlock deploys/merges for a stack in a different, correctly-secured organization.
- Forge `push`/`check_suite` events that cause the engine to sync commits or refresh check runs for stacks in an unrelated organization, using an `expected_head_sha` chosen by the attacker.

This crosses an authentication boundary between organizations without any repository write access, GitHub App key, or Shipit session — satisfying the Critical impact category of an unauthorized deploy/rollback/merge being enabled through forged, cross-organization commit statuses, and at minimum the High category of unauthenticated manipulation of stack/commit state.

### Likelihood Explanation
Exploitability depends on the Shipit installation being configured with multiple GitHub organizations where at least one has no `webhook_secret` (or one whose secret the attacker can obtain, e.g. from a less-trusted/less-monitored org's own GitHub App settings). This is a realistic operational configuration explicitly documented and templated in this repo (`config/secrets.development.example.yml`), so the precondition is engine-supported rather than purely hypothetical misconfiguration. Once that precondition holds, exploitation requires only crafting a JSON payload and a correctly computed HMAC for the weak organization — no privileged Shipit credentials are needed.

### Recommendation
Bind the signature verification to the same repository identity used by the handlers: derive the organization/app used for `verify_webhook_signature` from `repository.full_name`'s owner (or, more robustly, verify the payload's `repository.full_name` matches an owner that's actually associated with the app/organization that produced a valid signature) rather than trusting `repository.owner.login`/`organization.login` independently of what handlers act upon. Additionally, `StatusHandler` should scope `Commit` lookups to the repository identified by the verified webhook rather than matching by `sha` across the entire installation.

### Proof of Concept
1. Configure Shipit (per the documented multi-org schema) with two organizations: `weak-org` (no `webhook_secret`) and `strong-org` (has a `webhook_secret`), both with stacks tracked in the same Shipit instance.
2. Attacker sends a `status` webhook to `/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature` needed, and body:
   ```json
   {
     "sha": "<commit sha belonging to a strong-org stack>",
     "state": "success",
     "context": "required-check",
     "repository": { "owner": { "login": "weak-org" } }
   }
   ```
3. `verify_signature` resolves `Shipit.github(organization: "weak-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `strong-org` commit regardless of the org named in the payload — and calls `commit.create_status_from_github!(params)`, injecting a forged "success" status onto a commit that belongs to `strong-org`, without ever presenting a valid signature for `strong-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
