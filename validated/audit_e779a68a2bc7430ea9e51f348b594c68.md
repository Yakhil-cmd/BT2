### Title
Unguarded cache dereference in `forgetUnit` causes an unhandled-exception crash when a unit is "un-cached" twice - ([File: storage.js])

### Summary
`storage.forgetUnit()` unconditionally dereferences `assocUnstableUnits[unit].parent_units` before deleting the cache entry, without checking whether the unit is still present in `assocUnstableUnits`. Multiple independent code paths (AA-response rollback, uncovered-joint purge, and archiving of joint+descendants) can end up calling `forgetUnit()` on the same unit, and any repeated or out-of-order invocation results in a `TypeError: Cannot read properties of undefined` thrown synchronously, crashing the node process. This mirrors the CVE-2024-30807 bug class: an object/record is torn down (freed from the cache) and then a second consumer performs a "destructor"-style operation that assumes the record still exists, causing a use-after-free-equivalent crash (DoS) instead of a clean no-op.

### Finding Description
`forgetUnit(unit)` is defined as: [1](#0-0) 

Note that on line 2212 it does `assocUnstableUnits[unit].parent_units.forEach(...)` with **no guard** for `assocUnstableUnits[unit]` being `undefined`. If `forgetUnit` is invoked a second time for the same unit (after the first call already executed `delete assocUnstableUnits[unit]` on line 2226), this line throws immediately.

This function is treated as an idempotent "free the unit from memory" primitive and is called from at least three independent subsystems that do not coordinate with each other on which units have already been forgotten:

1. AA-response rollback (single-poster/AA-trigger reachable): [2](#0-1) 
called from the `revert()` error path of `handleTrigger`: [3](#0-2) 

2. Uncovered/non-serial joint purge (background maintenance triggered by unit posting/propagation): [4](#0-3) 

3. Archiving of a joint and its descendants: [5](#0-4) 

None of these call sites check "has this unit already been forgotten by someone else" before calling `forgetUnit`; the only safety property relied upon is that each caller runs under the `"write"` mutex and touches disjoint sets of units. Because the same in-memory unit record (`assocUnstableUnits[unit]`) can be the target of more than one of these cleanup flows for units that are rolled back, superseded, or reprocessed (e.g., an AA response unit that is rolled back via `revertResponsesInCaches` and later becomes subject to `purgeUncoveredNonserialJoints`/`archiveJointAndDescendants` handling for the same or a related unit chain), a second `forgetUnit()` call on an already-forgotten unit throws synchronously and uncaught, which is fatal for a Node.js process (default behavior is process termination on an uncaught exception thrown outside of a Promise). This is the same failure shape as the CVE: a cleanup routine touches memory belonging to a record that a previous cleanup routine has already released.

### Impact Explanation
An uncaught exception thrown from `forgetUnit` in the middle of a locked "write" critical section crashes the full node process. Since this cache is central to unit/AA/DAG-parent bookkeeping used by every node that validates AA triggers or handles joint archiving/purging, a reliably triggerable double-`forgetUnit()` condition is a network-wide denial of service: affected nodes stop confirming new units until manually restarted, satisfying the "network unable to confirm new units" bar.

### Likelihood Explanation
The precondition — invoking `forgetUnit` twice on the same unit id from independent subsystems (AA rollback vs. purge/archiving of uncovered joints) — requires a specific ordering of validation/rollback and maintenance-purge events that is plausible under crafted AA triggers/units causing rollback combined with the periodic un-covered/nonserial joint purge (`purgeUncoveredNonserialJointsUnderLock`) and `archiveJointAndDescendants`/`archiveJointAndDescendantsIfExists` paths (invoked from `network.js`) racing on the same in-memory cache entries. Reaching this exact ordering reliably from a remote/single-poster/AA-trigger perspective without local instrumentation is not proven with certainty in this review — the exact call graph that guarantees two invocations for one unit under real conditions was not fully traced within the available context, so this should be treated as a plausible-but-unconfirmed reachable crash rather than a demonstrated exploit chain.

### Recommendation
Make `forgetUnit` defensively idempotent: return immediately (no-op) if `assocUnstableUnits[unit]` is already `undefined`, instead of unconditionally dereferencing `.parent_units`. Additionally, audit and serialize the three call sites (`revertResponsesInCaches`, `purgeUncoveredNonserialJoints`, `archiveJointAndDescendants`) so a unit cannot be targeted for cache removal from more than one of these flows concurrently, and wrap calls to `forgetUnit` in `try/catch` at call sites that run under the write mutex so a stale/duplicate cleanup cannot crash the whole process.

### Proof of Concept
Not independently verified with a runnable repro in this review (would require constructing a rollback scenario in `aa_composer.js` that races with `joint_storage.purgeUncoveredNonserialJoints` or `storage.archiveJointAndDescendants` for the same unit, which was not fully traceable from the available code context). Conceptually:
1. Cause an AA trigger to produce a response unit which then gets rolled back via `revert()` → `revertResponsesInCaches()` → `storage.forgetUnit(unit)` (deletes `assocUnstableUnits[unit]`).
2. Concurrently or subsequently, drive the same unit id into `purgeUncoveredNonserialJoints` or `archiveJointAndDescendants`, both of which call `storage.forgetUnit(unit)` again.
3. The second call executes `assocUnstableUnits[unit].parent_units.forEach(...)` on `undefined`, throwing a `TypeError` that is uncaught, crashing the node process.
