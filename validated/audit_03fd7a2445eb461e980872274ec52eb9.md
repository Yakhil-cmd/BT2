### Title
Cross-tenant `Shipit::Team` hijack via unscoped `github_id` lookup in `MembershipHandler#find_or_create_team!` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
The `membership` webhook handler resolves the target `Shipit::Team` solely by `github_id`, without verifying that the `organization.login` in the (correctly signature-verified) payload matches the `organization` column already stored on that `Team` row. An attacker who owns their own GitHub organization (and therefore its real `webhook_secret`) can sign a `membership` event naming a `team.id` that belongs to a *different* org's pre-existing `Shipit::Team`, causing their own GitHub identity to be added as a member of that unrelated team.

### Finding Description
The claimed binding is: `team.organization == params.dig('organization','login')` for any `Team` row mutated by a `membership` webhook whose signature was verified against that same `organization.login`.

Trace:
1. `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes `repository_owner` via `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and verifies the signature against `Shipit.github(organization: repository_owner)` [2](#0-1) . For a `membership` event there is no `repository` key, so `repository_owner` is the attacker's own `organization.login`, and the signature check legitimately passes using the attacker's own real `webhook_secret`. This part of the binding is correctly enforced — the attacker cannot forge a different org's secret.
2. `Shipit::Webhooks::Handlers::MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }` [3](#0-2) . The block that sets `team.organization` only executes when a **new** record is created. If a `Team` row with that `github_id` already exists (e.g., created earlier via the `teams.rake` task or a prior legitimate webhook for a different org), `find_or_create_by!` simply returns the existing record — the organization on that record is never compared against `params.organization.login`.
3. `process` then calls `team.add_member(member)` where `member` is `User.find_or_create_by_login!(params.member.login)` [4](#0-3) , `member.login` being fully attacker-controlled (their own GitHub login). `Team#add_member` appends the member to `members` (backed by `Membership`) with no organization check [5](#0-4) , and `Membership` validation only enforces `user_id` uniqueness scoped to `team_id`, not any organization/repository binding [6](#0-5) .

Root cause: signature verification is correctly scoped to the org named in the payload, but the *record selection* (`find_or_create_by!(github_id: ...)`) is not re-scoped to that same org when the row pre-exists. The equality `team.organization == params.organization.login` therefore does not hold after the mutation for pre-existing teams belonging to another organization — it is silently bypassed.

Exploit flow: Attacker registers/owns GitHub org `evil-corp` and configures it in the Shipit instance the normal way (so `Shipit.github(organization: 'evil-corp')` has a real, attacker-known `webhook_secret`, since the attacker created it). They discover (via public GitHub team pages/API, which expose numeric team IDs) the `github_id` of a `Shipit::Team` row that already exists for a victim org, e.g. `victim-corp/deployers` (github_id `999`). They POST to `/webhooks` with header `X-Github-Event: membership`, a body `{"action":"added","team":{"id":999,...},"organization":{"login":"evil-corp"},"member":{"login":"attacker-handle"}}`, signed with `evil-corp`'s real secret. `verify_signature` passes (org `evil-corp` matches). `find_or_create_team!` finds the existing `victim-corp` `Team` row by `github_id: 999` and ignores that `organization.login` said `evil-corp`. `attacker-handle` is added as a `Membership` of `victim-corp`'s team.

None of the existing guards catch this: `verify_signature` only checks the HMAC against the org named in the payload (correctly, but that's a different org than the team's real owner); `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not cross-field org/team ownership; there is no `require_permission!`/`authorized?` check in the webhook path at all, since webhooks are meant to be trusted once signature-verified — but the signature only attests to *which org sent it*, not *which team the payload may mutate*.

### Impact Explanation
An unprivileged attacker who controls any GitHub organization onboarded into the Shipit instance can add their own GitHub identity as a `Membership` of an arbitrary pre-existing `Shipit::Team` belonging to a completely different, victim organization, as long as they know/guess that team's numeric GitHub `id` (discoverable via public GitHub APIs). If that `Team`'s `handle` (`organization/slug`) is listed in `Shipit.github_teams` for privileged actions (e.g., stack access, deploy permission gating, admin UI), this escalates the attacker into that authorization group for the victim's repositories/stacks — a cross-tenant authorization escalation (High severity, "escalation into `Shipit.github_teams` authorization"). The attack is repeatable against any `Team` row whose `github_id` the attacker can enumerate, and works from any org the attacker legitimately controls in the Shipit installation.

### Likelihood Explanation
Preconditions: (1) the Shipit instance must host/integrate more than one GitHub organization (multi-tenant deployment), (2) the victim org's `Shipit::Team` row must already exist in the database (created via a prior legitimate `membership` webhook or the `teams.rake` task), and (3) the attacker must control at least one onboarded GitHub org (which is a normal, low-cost precondition for any GitHub org owner using a shared Shipit instance — no privileged Shipit credentials are needed). GitHub team IDs are visible via the public GitHub API/UI for teams belonging to orgs with public team visibility, or leak via other webhook payloads, making them feasible to obtain. The attack requires only a single crafted HTTP POST with a valid HMAC signed using the attacker's own legitimately-issued secret — fully repeatable and cheap.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` and `organization` (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally reject/raise if a `Team` with that `github_id` already exists under a *different* `organization` than the one named in the verified payload, rather than silently mutating it.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual, no live GitHub)
test "membership webhook cannot add member to a team belonging to a different organization" do
  victim_team = Team.create!(organization: 'victim-corp', slug: 'deployers', name: 'Deployers', github_id: 999, api_url: 'https://api.github.com/...')

  payload = {
    action: 'added',
    team: { id: 999, name: 'Deployers', slug: 'deployers', url: 'https://example.com' },
    organization: { login: 'evil-corp' }, # attacker's own org, signs with evil-corp's real secret
    member: { login: 'attacker-handle' }
  }

  @request.headers['X-Github-Event'] = 'membership'
  # signature computed/stubbed using evil-corp's real webhook_secret, verifying against organization: 'evil-corp'

  post :create, body: payload.to_json, as: :json
  assert_response :ok

  victim_team.reload
  # Assert the binding: team.organization ('victim-corp') must equal the verified payload's organization.login ('evil-corp')
  # for this mutation to be legitimate. It does not.
  refute_equal 'evil-corp', victim_team.organization
  # Yet the attacker was added anyway, proving the broken binding:
  assert victim_team.members.exists?(login: 'attacker-handle'), "attacker should NOT be a member of victim-corp's team, but is"
end
```
