### Title

Malicious route pool can inject arbitrary token transfers into a user's signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary

High. Controller strategies accept caller-supplied route bytes and invoke arbitrary route-selected pool contracts without constraining the caller's authorization tree to the expected router input pull. [1](#0-0) [2](#0-1)  A malicious pool can satisfy the measured swap accounting while also calling `token.transfer(victim, attacker, amount)` on an unrelated wallet token; simulation records that transfer as a child of the user's strategy authorization, and enforcement succeeds if the simulated tree is signed. [3](#0-2) [4](#0-3) 

### Finding Description

`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` route attacker-controlled `swap` bytes through `swap_tokens` or `swap_tokens_or_passthrough`. [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

The controller authorizes only the intended `token_in.transfer(controller, router, amount_in)` invocation and then forwards the caller-controlled route to the configured aggregator. [9](#0-8)  Afterward, it validates only that controller input did not increase or exceed `amount_in`, and that the controller received positive `token_out`; it does not inspect or constrain authorization behavior inside the route. [10](#0-9) 

The route program identifies the pool by an index into a caller-supplied address registry, and `execute_op` passes that address to the venue dispatcher. [11](#0-10) [12](#0-11)  The dispatcher selects the declared venue and calls the corresponding adapter without checking the pool address against an allowlist. [13](#0-12)  For example, the Aquarius adapter invokes `swap` directly on the supplied pool address. [14](#0-13) 

Balance accounting cannot distinguish a legitimate venue from a trojanized one: the dispatcher requires only a positive output delta and an exact input spend. [15](#0-14)  A malicious pool can therefore pull the authorized input, return enough prefunded output to pass `min_out` and the controller risk checks, and additionally invoke `token.transfer(caller, attacker, amount)` on any token held by the caller. [15](#0-14) [16](#0-15) 

The security boundary failure is the authorization tree, not the measured swap result. [17](#0-16)  The harness records the rogue transfer beneath the user's `swap_collateral` authorization and drains the unrelated wallet token once the poisoned tree is signed. [18](#0-17) [4](#0-3) 

### Impact Explanation

A user who signs the simulated authorization tree loses arbitrary wallet assets unrelated to the lending collateral or route input. [18](#0-17)  The routed amount, output minimum, measured output check, and final account-risk checks do not bound this loss because the malicious transfer is authorized directly by the victim and can target a token the protocol never listed. [10](#0-9) [19](#0-18)  This constitutes theft of user funds.

### Likelihood Explanation

An unprivileged attacker can deploy the trojanized pool, encode it in the route address registry, prefund it with output tokens, and distribute the malicious `swap` bytes as a plausible strategy route. [2](#0-1) [20](#0-19)  Execution still requires the victim to sign the extra child authorization produced by simulation, so the practical precondition is that a wallet or user accepts the opaque authorization tree without rejecting unexpected token transfers. [21](#0-20)  The documented client-side expectation is not enforced on-chain, leaving users of route-producing integrations exposed when that expectation is not implemented correctly. [22](#0-21) 

### Recommendation

Enforce a venue/pool allowlist or registry for every route-selected pool instead of accepting arbitrary pool addresses in `StrategyPayload.assets`. [12](#0-11)  Alternatively, execute each hop through an intermediate authorization boundary that prevents route-selected code from inheriting the account caller's authorization, while preserving the router's own invoker-contract authority for pool pulls. [23](#0-22)  At minimum, simulation and signing integrations should reject any authorization tree containing children beyond the one expected input transfer, and this should be treated as a protocol-enforcement gap rather than only a client warning. [22](#0-21) 

### Proof of Concept

1. Alice owns an unrelated token `WALLET_TOKEN` and calls `swap_collateral(caller=alice, account_id, current=USDC, amount=5_000_000_000, new=ETH, swap=malicious_route)`. [1](#0-0) [19](#0-18) 

2. `malicious_route` encodes one Aquarius hop whose `idx_a` selects attacker contract `TROJAN_POOL`, `idx_b` selects USDC, and `idx_c` selects ETH, with a positive `min_out`. [11](#0-10) [24](#0-23) 

3. The router pulls USDC from the controller, dispatch selects Aquarius, and `invoke_pool_swap` invokes `TROJAN_POOL.swap`. [25](#0-24) [13](#0-12) [14](#0-13) 

4. `TROJAN_POOL` implements the expected surface, pulls the router-authorized USDC, transfers enough prefunded ETH back to the router, and additionally calls `WALLET_TOKEN.transfer(alice, attacker, WALLET_BALANCE)`. [15](#0-14) [16](#0-15) 

5. Simulation attaches the wallet-token transfer as a child of Alice's `swap_collateral` authorization; signing that tree makes the malicious transfer enforceable. [26](#0-25) 

6. The strategy still succeeds because the router's input spend is exact, measured ETH output is positive, and Alice's account passes final risk checks; Alice's `WALLET_TOKEN` balance is reduced to zero and the attacker's balance increases by `WALLET_BALANCE`. [15](#0-14) [27](#0-26)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
