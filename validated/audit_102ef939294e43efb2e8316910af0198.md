### Title
Unsanitized terminal output of skill-derived strings in `renderDiagnosticsPlain` allows ANSI/OSC escape sequence injection - (File: pkg/cmd/skills/publish/publish.go)

### Summary
`renderDiagnosticsPlain` writes `d.severity`, `d.skill`, and `d.message` directly to `opts.IO.Out` via `fmt.Fprintf` with no escaping or control-character stripping. Since `d.skill`/`d.message` are populated from data derived while validating a skill's frontmatter/content during `gh skills publish`, any C0/C1 control bytes or ANSI/OSC sequences embedded in that content are passed through verbatim to the terminal.

### Finding Description
The function is: [1](#0-0) 

It iterates diagnostics and prints `%s\t%s\t%s\n` with `d.severity`, `d.skill`, `d.message` unsanitized. Unlike `renderDiagnosticsTTY`, which wraps text with `cs.Bold`/`cs.Red`/etc. (color-scheme helpers that at least route through the same styling layer but still do not strip raw control bytes from the underlying string), the plain renderer performs no filtering at all. Neither function calls any ANSI-stripping or control-character-sanitization routine before writing to `opts.IO.Out`.

`d.message` and `d.skill` are built while validating a skill directory (frontmatter parsing, metadata key detection, e.g. `findGitHubMetadataKeys`/`stripGitHubMetadata` at lines 1130-1167) and while inspecting a repo's git remotes (`detectMissingRepoDiagnostic`, lines 1021-1054), which embeds remote URLs directly into diagnostic messages via `fmt.Sprintf` at line 1052. If a victim runs `gh skills publish` against a repository/skill whose frontmatter fields, metadata values, or git remote URL were crafted by an attacker (e.g., a cloned fork, a collaborator-supplied skill file, or a repo with an attacker-controlled remote configured), those attacker strings flow unsanitized into terminal output.

I was not able to fully trace every call site that constructs `publishDiagnostic{...}` with skill-derived text (26 matches in the file were not individually reviewed due to tool budget), so I cannot confirm with certainty that a specific field is populated purely from remote/attacker-supplied frontmatter versus only from filenames/paths under the victim's own control. This introduces some uncertainty regarding the exact reachable attacker-controlled field.

### Impact Explanation
If confirmed exploitable, an attacker could embed OSC 52 (clipboard write) or terminal title/DCS sequences inside a skill's frontmatter field or a git remote URL string that ends up in a diagnostic message. When the victim runs `gh skills publish` in a non-TTY context (which selects `renderDiagnosticsPlain`), the escape sequence would be written to the terminal/stream unmodified, potentially leading to clipboard hijacking, terminal spoofing, or (with capable terminal emulators) prompt injection — matching a "High: Terminal output/prompt spoofing" class of impact, contingent on the victim's terminal emulator honoring the injected sequence.

### Likelihood Explanation
Requires: (1) the victim to run `gh skills publish` with stdout piped/redirected or otherwise non-TTY (to hit the plain renderer) or a TTY that doesn't get the color-scheme escaping either, and (2) the victim to be validating/publishing a skill directory or repository containing attacker-influenced content (fork, cloned PR, or a repo with an attacker-set git remote). This is a plausible but not fully-confirmed path since I could not verify each `publishDiagnostic` construction site's exact data provenance within the available investigation budget.

### Recommendation
Sanitize all diagnostic `skill` and `message` fields (and any other externally-derived string) before writing to `opts.IO.Out`/`opts.IO.ErrOut` in both `renderDiagnosticsPlain` and `renderDiagnosticsTTY` — strip C0/C1 control characters and ANSI/OSC/DCS escape sequences (e.g., via a shared sanitization helper) prior to formatting, regardless of TTY status.

### Proof of Concept
Golden test plan:
1. Construct a `publishDiagnostic{severity: "error", skill: "skill\x1b]52;c;<base64>\x07", message: "desc\x1b]0;pwned\x07"}`.
2. Call `renderDiagnosticsPlain` with a buffer-backed `IO.Out`.
3. Assert the rendered output buffer does not contain the raw `\x1b` (0x1B) byte or any `\x9b`/C1 escape byte — expected assertion should currently fail against the existing implementation, demonstrating passthrough.

Note: exact confirmation of the attacker-reachable field construction for `d.skill`/`d.message` from remote/registry frontmatter data was not fully traced in this session; a full session with file access would be needed to pin the precise call site and craft a complete end-to-end PoC using a git-stub/httpmock scenario.

func renderDiagnosticsPlain(opts *PublishOptions, diagnostics []publishDiagnostic, errors, warnings int) {
	for _, d := range diagnostics {
		if d.severity == "info" {
			continue
		}
		fmt.Fprintf(opts.IO.Out, "%s\t%s\t%s\n", d.severity, d.skill, d.message)
	}
	if errors == 0 && warnings == 0 {
		fmt.Fprintf(opts.IO.Out, "ok\n")
	}
}
