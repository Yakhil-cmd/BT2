### Title
Arbiter Contract Fee Split Can Be Front‑Run by a Malicious ArbStore Operator via Live, Unlocked `cut` Value - (File: arbiter_contract.js)

### Summary
Arbiter‑mediated contracts in `arbiter_contract.js` bind two counterparties to a payment split (payer amount / payee amount / arbstore fee) that is computed at shared‑address‑derivation time using a `cut` value fetched live from the arbiter's ArbStore HTTP endpoint. This `cut` is never included in the cryptographic commitment (`getHash`/`getHashSrc`) that both parties sign to accept the contract, so the ArbStore operator can change its advertised fee between the moment the contract terms are agreed and the moment the immutable shared address is actually derived and funded, silently changing how much of the payment goes to the arbstore versus the counterparty — exactly the "operator can front‑run committed request terms" bug class described in the external report (deliveryRate/paymentType fetched from a mutable, operator‑controlled source instead of being locked in by the requester).

### Finding Description
When two parties negotiate an arbiter contract, the terms that are hashed and mutually signed are computed by `getHashSrc()`: [1](#0-0) 

Note that this hash covers `title`, `text`, `creation_date`, `payer_address`, `payer_name`, `arbiter_address`, `payee_address`, `payee_name`, `amount`, and `asset` — but **not** the ArbStore's fee cut or the ArbStore's payout address.

The actual payment split, however, is computed later in `deriveSharedAddress()`, which fetches the ArbStore's current fee live from the network: [2](#0-1) 

`arbstoreInfo.cut` (and `arbstoreInfo.address`) come from `arbiters.getArbstoreInfo()`, which performs a live HTTP request to a URL provided by the hub and returns whatever `cut`/`address` the ArbStore server currently reports, cached only in an in‑memory map keyed by `arbiter_address` (not by contract hash, not committed anywhere): [3](#0-2) 

Because `deriveSharedAddress()` is invoked twice, independently, by each side — once by the offeror in `createSharedAddressAndPostUnit()` to actually generate and fund the multisig/shared address, and once by the acceptor in `handleReceivedSharedAddress()` to verify it — an ArbStore operator can change the reported `cut` (or `address`) between the time the contract offer/terms were shown to and accepted by the users and the time the shared address is derived and paid into: [4](#0-3) 

The resulting shared address is a hash of an oscript definition (`["has", {..., amount: ...}]` clauses) that hard‑codes the payer/payee/arbstore split amounts based on whatever `cut` was fetched at that moment. Since `cut` was never part of the signed contract hash, neither counterparty has any cryptographic guarantee that the split embedded in the funded shared address matches what was actually disclosed/agreed when the deal was struck. This mirrors the reported MechMarketplace bug precisely: the party posting the on-chain artifact (`priorityMechServiceId` / here, `arbiter_address`) only commits to a *reference* to a third‑party‑controlled configuration, while the actual economic terms (`deliveryRate`/`paymentType` / here, `cut`/`arbstore_address`) are fetched from that third party at execution time and can be changed by that third party to the requester's disadvantage.

### Impact Explanation
A malicious or compromised ArbStore server can unilaterally alter the fee cut it reports between contract negotiation and shared‑address funding, causing the payer's funds to be split differently than what was displayed and accepted (e.g., a higher percentage routed to the ArbStore's address, or funds routed to a different `arbstoreInfo.address` entirely). Because the split is baked into an on‑chain immutable multisig address definition rather than the mutually-hashed contract terms, this results in concrete unauthorized diversion of funds during the payment phase of the contract with no additional cryptographic check to catch the discrepancy on the payer side beyond a simple address mismatch (which is itself only checked on the *acceptor* side in `handleReceivedSharedAddress`, not re-verified by the payer against the originally agreed cut).

### Likelihood Explanation
Exploitation only requires control of (or MITM access to) the ArbStore HTTP endpoint associated with the chosen `arbiter_address`; no control over the counterparty's device, private keys, or the DAG/network is needed. The window between contract agreement and shared-address creation/funding (`createSharedAddressAndPostUnit`) is entirely attacker-influenced timing since the ArbStore server can serve different `cut` values on each request. This is reachable by any unprivileged party that operates or compromises an ArbStore that users choose as an arbiter for a contract — a normal private-payment counterparty scenario.

### Recommendation
Include the ArbStore `cut` (and `address`) in the cryptographically committed contract terms (`getHashSrc`/`getHash`) that both parties sign, so any subsequent change to the ArbStore's reported fee causes a verifiable hash/address mismatch. `deriveSharedAddress()` should use the `cut`/`arbstore_address` value that was locked in at contract-agreement time (stored in `wallet_arbiter_contracts`) rather than re-fetching potentially different live values, and the payer should independently verify the `cut` used to build the shared address matches the value it agreed to before funding it.

### Proof of Concept
1. Alice and Bob agree to an arbiter contract via `createAndSend`/`respond`, referencing `arbiter_address` A, at a time when A's ArbStore advertises `cut = 0.01` (1%). This `cut` is shown in the UI but is not part of `getHashSrc`/`getHash`.
2. The malicious operator of A's ArbStore server changes the reported `cut` to `0.20` (20%) for subsequent `/api/get_info` requests.
3. Alice (offeror/payer) calls `createSharedAddressAndPostUnit`, which calls `deriveSharedAddress` → `arbiters.getArbstoreInfo(A)`, fetching the new `cut = 0.20` live, and derives/funds a shared address whose immutable oscript definition sends 20% of the payment to the ArbStore's address instead of the originally agreed 1%.
4. Bob's `handleReceivedSharedAddress` independently re-derives the address using the (now also changed) live `cut` and it matches Alice's, so the mismatch check passes — both parties unknowingly accept a shared address that pays the ArbStore 20% instead of the 1% that was actually negotiated, since the `cut` was never bound to the signed `contract.hash`.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}

function createSharedAddressAndPostUnit(hash, walletInstance, cb) {
	deriveSharedAddress(hash, true, function(err, arrDefinition, assocSignersByPath) {
		if (err)
			return cb(err);
		require("./wallet_defined_by_addresses.js").createNewSharedAddress(arrDefinition, assocSignersByPath, {
			ifError: function(err){
				cb(err);
			},
			ifOk: function(shared_address){
				setField(hash, "shared_address", shared_address, async function(contract) {
					const err = await fillArbstoreAddresses(contract);
					if (err)
						return cb(err);
					// share this contract to my cosigners for them to show proper ask dialog
					shareContractToCosigners(contract.hash);
					shareUpdateToPeer(contract.hash, "shared_address");

					const contacts_hash = getContactsHash(contract);

					// post a unit with contract text hash and send it for signing to correspondent
					var value = {"contract_text_hash": contract.hash, "arbiter": contract.arbiter_address, contacts_hash};
					var objContractMessage = {

						asset: "base",

function getArbstoreInfo(arbiter_address, cb) {
	if (!cb)
		return new Promise(function(resolve, reject){
			getArbstoreInfo(arbiter_address, function(err, info){
				if (err) return reject(err);
				resolve(info);
			});
		});
	if (arbStoreInfos[arbiter_address]) return cb(null, arbStoreInfos[arbiter_address]);
	device.requestFromHub("hub/get_arbstore_url", arbiter_address, function(err, url){
		if (err) {
			return cb(err);
		}
		if (!validationUtils.isNonemptyString(url))
			return cb("invalid url received from hub");
		requestInfoFromArbStore(url+'/api/get_info', function(err, info){
			if (err)
				return cb(err);
			if (!validationUtils.isNonemptyObject(info))
				return cb("invalid info received from arbstore");
			const cut = parseFloat(info.cut);
			if (!info.address || !validationUtils.isValidAddress(info.address) || isNaN(cut) || cut < 0 || cut >= 1) {
				return cb("malformed info received from ArbStore");
			}
			info.url = url;
			arbStoreInfos[arbiter_address] = info;
			cb(null, info);
		});
	});
}
