### Title
Webhook signature verification is bound to `repository.owner.login`, not to the repository actually acted upon (`repository.full_name`) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit verifies an incoming GitHub webhook's HMAC signature using the GitHub App configured for the organization taken from `repository.owner.login` (or `organization.login`), but every webhook handler subsequently selects the `Stack`/`Repository` to act on using a completely different, independently-controlled field of the same JSON body: `repository.full_name`. Nothing ties these two fields together, so a payload can pass signature verification as belonging to organization A while acting on a repository/stack that belongs to organization B.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/secret to validate against solely from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), and `Shipit.github(organization: repository_owner)` is used to fetch the `GithubApp`/`webhook_secret` used for `verify_webhook_signature`. This means the signature is only proven to originate from *some* GitHub App installation owning organization `repository.owner.login` — it proves nothing about `repository.full_name`.

Every handler, however, resolves the actual target repository from the unrelated `full_name` field: [3](#0-2) 

and acts on the resulting `stacks`/`Repository` (e.g. `PushHandler#process` syncs commits for whatever stacks match `full_name`, `PullRequest::ClosedHandler#process` archives whatever review stack matches `full_name`): [4](#0-3) [5](#0-4) 

Because `repository.owner.login` and `repository.full_name` are two independent JSON fields in the same unsigned-structure payload, there is no code path enforcing `repository.full_name` starts with `repository.owner.login`. This breaks the intended binding: **the organization whose secret authenticated the request must equal the organization that owns the repository being written to**. Concretely, if Shipit is configured for multiple GitHub organizations (as documented in `docs/setup.md`, `github: { orgA: {...}, orgB: {...} }`), an actor who legitimately controls org A's GitHub App/webhook (i.e., can produce a validly-signed payload for org A) can set `repository.owner.login = "orgA"` (so `verify_signature` succeeds using orgA's real secret) while setting `repository.full_name = "orgB/victim-repo"` (so the handler acts on org B's stack).

This is the direct analog of the reported `VotingMachine.verifyNonce` bug: the check validates one attacker-controlled field (`_relayerNonce` / `repository.owner.login`) while a different, unchecked field (the actual vote effect / `repository.full_name`) determines what state gets mutated, letting a value that passes verification be reused/redirected to affect a target it was never authorized for.

### Impact Explanation
Any webhook event handler that resolves its target via `repository.full_name` is reachable cross-organization once an attacker holds a legitimately signed webhook for any one organization configured in the same Shipit instance:
- `PullRequest::ClosedHandler`/`OpenedHandler`/`ReopenedHandler`/`(Un)labeledHandler` create, archive, or unarchive review stacks belonging to a different organization's repository — a cross-repository write.
- `PushHandler` enqueues `GithubSyncJob` for another organization's stack, forcing Shipit to re-sync/re-cache another tenant's deploy spec and commit history outside of that tenant's own webhook trust boundary.

This is a cross-organization authorization bypass leading to cross-repository writes on stacks the attacker's organization has no legitimate relationship with, satisfying the "cross-repository writes" / unauthorized action impact bar for a multi-organization Shipit deployment.

### Likelihood Explanation
Exploitability requires the attacker to control (or have leaked) the webhook secret/App credentials for *any one* organization configured on the shared Shipit instance — a realistic scenario for the documented multi-organization configuration (`docs/setup.md` "Using Multiple Github Applications"), where different, mutually untrusted teams/orgs share one Shipit deployment. No Shipit session, API token, or GitHub write access to the victim org is needed — only the ability to send a correctly-HMAC-signed payload for one's own org with a forged `repository.full_name`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler#repository_name`), enforce that the organization used to select/validate the webhook signature matches the organization prefix of `repository.full_name` (and of `organization.login` when present). Concretely, after computing `repository_owner`, require:
```ruby
repository_full_name = params.dig('repository', 'full_name')
head(422) if repository_full_name && !repository_full_name.start_with?("#{repository_owner}/")
```
so that a payload's claimed signing organization is cryptographically and logically bound to the repository it is permitted to mutate.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own GitHub App/`webhook_secret` (per `docs/setup.md` multi-app setup), and a stack tracking `orgB/victim-repo`.
2. As the holder of `orgA`'s GitHub App webhook secret, craft a `pull_request` "closed" event payload:
```json
{
  "action": "closed",
  "number": 1,
  "pull_request": { "...": "..." },
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "sender": { "login": "attacker" }
}
```
3. Sign the raw body with `orgA`'s real `webhook_secret` and send it as `X-Hub-Signature` to `POST /webhooks` with `X-Github-Event: pull_request`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `"orgA"`, fetches `orgA`'s `GithubApp`, and successfully verifies the signature against `orgA`'s secret [1](#0-0) .
5. `PullRequest::ClosedHandler#repository` resolves `Shipit::Repository.from_github_repo_name("orgB/victim-repo")` from the `full_name` field [6](#0-5)  and calls `review_stack.archive!`, mutating org B's stack despite the request having been authenticated only against org A's credentials.
