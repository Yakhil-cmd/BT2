### Title
Signature verification org (`repository.owner.login`) decoupled from repository resolution org (`repository.full_name`) lets attackers archive victim `ReviewStack`s via `ClosedHandler` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify a webhook against using `repository_owner` (`params.dig('repository','owner','login')`), while `ClosedHandler#repository` resolves the actually-mutated `Repository`/`ReviewStack` using `params.repository.full_name` split into `owner/name` — two independent, attacker-controlled fields that are never checked for equality. If the attacker names an org whose Shipit-configured `webhook_secret` is blank in `repository.owner.login`, `GitHubApp#verify_webhook_signature` trivially returns `true`, letting a forged `pull_request` `closed` event for an unrelated victim repository (named via `full_name`) reach `ClosedHandler`, which archives that victim's existing `ReviewStack`.

### Finding Description
The broken binding as an equality that should hold but doesn't:
`repository_owner` (used to pick `Shipit.github(organization: repository_owner)` for signature verification) `== ` the owner embedded in `params.repository.full_name` (used by `Repository.from_github_repo_name` to resolve the repository the handler mutates).

Code path:
- `Shipit::WebhooksController#verify_signature` picks the app config via `repository_owner`, defined at [1](#0-0)  and used at [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected org's `webhook_secret` is not configured: [3](#0-2) .
- `ClosedHandler#repository` resolves the target `Repository` purely from `params.repository.full_name`, independent of `repository.owner.login`: [4](#0-3) .
- `ClosedHandler#process` then calls `review_stack.archive!` which, if a `ReviewStack` already exists for that PR's environment (`pr#{number}`) scoped to the resolved repository, deprovisions and archives it: [5](#0-4) .

Root cause: the signature-verification org selection and the repository-mutation org resolution are two unrelated fields in the same JSON body, and no code path cross-checks that `repository.owner.login == repository.full_name.split('/').first`.

Note on the "provisioning precedence" amplification claimed in the question: it does not apply to `ClosedHandler`. `ClosedHandler`/`ReviewStackAdapter#archive!` never calls `create!`/`find_or_create!`; it only acts if `stack` (an existing, already-provisioned `ReviewStack`) is present, per [6](#0-5) . `review_stacks_enabled` is checked only by `OpenedHandler`/`LabeledHandler`-style creation paths, not by `ClosedHandler`, and it is not referenced anywhere in `closed_handler.rb` or `review_stack_adapter.rb`. So the amplification mechanism described ("provision? precedence bug still provisions" despite `review_stacks_enabled` false) is not present for this handler — `ClosedHandler` can only archive a `ReviewStack` that already exists, it cannot create one.

Existing guards checked and found insufficient/inapplicable:
- `verify_signature` — insufficient, because it verifies against the wrong org's secret (`repository_owner`, attacker-chosen) rather than the org that actually owns the mutated repo (`full_name`).
- `drop_unhandled_event` — irrelevant, `pull_request`/`closed` is a handled event.
- `ExplicitParameters` schema on `ClosedHandler` — only validates shape/presence, not owner consistency: [7](#0-6) .
- `review_stacks_enabled` — not checked by this handler at all, so it neither blocks nor is bypassed by this path.

### Impact Explanation
An unprivileged internet requester who knows (a) an org configured in Shipit with no `webhook_secret` and (b) the `owner/name` of a victim repository that Shipit tracks with an existing (non-archived) `ReviewStack`/PR number can forge a `pull_request` `closed` payload where `repository.owner.login` is the no-secret org and `repository.full_name` is the victim repo. This bypasses signature verification for the victim org entirely and causes `ClosedHandler` to deprovision and archive the victim's real `ReviewStack` — "a payload for one repository mutating another's stack," matching the Critical impact category. The attack is repeatable against any tracked repo/PR number as long as a no-secret org can be found, and is not limited to a single tenant.

### Likelihood Explanation
Preconditions: (1) Shipit must be configured with at least one organization entry lacking a `webhook_secret` (or the attacker must otherwise get `verify_webhook_signature` to return true, e.g. an org with no config match raising `GithubOrganizationUnknown` would instead 422 — so the attacker specifically needs a *known, configured-but-secret-less* org); (2) a victim repository/`ReviewStack` must exist and be tracked. Attacker cost is a single unauthenticated HTTP POST with a crafted JSON body and `X-Github-Event: pull_request` header — no secrets, tokens, or sessions required. Feasibility depends entirely on Shipit's multi-org configuration having at least one org without a webhook secret, which is a plausible but not universal deployment configuration.

### Recommendation
In `Shipit::WebhooksController#verify_signature`, verify the webhook using the org derived consistently with whatever field the handler will use to resolve the repository (i.e., derive both from `repository.full_name`, or require `repository.owner.login` to match `repository.full_name.split('/').first` before proceeding). Additionally, require that a `webhook_secret` be mandatorily configured for every organization Shipit tracks (fail closed instead of `return true unless webhook_secret`), so no org can be used as a signature-bypass vector.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/closed_handler_owner_split_test.rb
test "cross-org owner/full_name split bypasses signature check and archives victim stack" do
  stack = create_stack # tracked under shipit_repositories(:shipit), e.g. "shopify/shipit-engine"

  payload = payload_parsed(:pull_request_closed)
  # attacker names a no-secret org for signature verification...
  payload["repository"]["owner"]["login"] = "no-secret-org"
  # ...but points full_name at the victim repo the handler actually resolves
  payload["repository"]["full_name"] = "shopify/shipit-engine"

  # Assert both sides of the equality diverge:
  assert_not_equal payload["repository"]["owner"]["login"],
                    payload["repository"]["full_name"].split("/").first

  Shipit::Webhooks::Handlers::PullRequest::ClosedHandler.new(payload).process

  assert stack.reload.archived?, "victim stack archived despite signature verified against unrelated org"
end
```
This demonstrates the equality `repository_owner == full_name.split('/').first` is false yet `ClosedHandler` still mutates the victim stack, confirming the cross-org confused-deputy path. It also confirms the "provisioning precedence" amplification claim in the question does not hold for `ClosedHandler`, since no `create!`/provisioning call is reachable from `archive!` — the impact stems solely from the owner/full_name split, not from a review-stacks-disabled provisioning bug.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
