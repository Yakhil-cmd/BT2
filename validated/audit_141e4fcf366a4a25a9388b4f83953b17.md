### Title
Signature-selection field (`repository.owner.login`) is not bound to the field the webhook payload acts on (`repository.full_name`), allowing an org whose secret is known to forge writes against a stack belonging to a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multi-tenant GitHub App configuration, where each organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which organization's secret to HMAC-verify the raw request body against based on `repository_owner`, itself read straight out of the *unverified* JSON body [2](#0-1) [3](#0-2) . Once the HMAC passes, the event handlers (e.g. `PushHandler`) determine which `Repository`/`Stack` to act on using a *different* field of the same JSON body: `repository.full_name` [4](#0-3) . Nothing enforces that `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon repository) refer to the same organization/repository. This is the same equality-mismatch bug class as the `UniswapV3Swapper` report: a value used to derive/select the "key" (pool fee / webhook secret) is not the same value that determines what is actually acted upon (token pair being swapped / repository being written to).

### Finding Description
- `Shipit.github(organization:)` looks up a per-organization `GitHubApp` (and its distinct `webhook_secret`) from `secrets.github` [5](#0-4) .
- `WebhooksController#verify_signature` computes `repository_owner` from the raw, unauthenticated request body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) and uses it to fetch that organization's `GitHubApp` to verify `X-Hub-Signature` [2](#0-1) :
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
```
- `verify_webhook_signature` is a plain HMAC-SHA1 over the raw bytes using that organization's secret [6](#0-5) . The HMAC covers the *bytes*, but it does not cryptographically bind "the org whose secret validated this request" to "the repository that will be written to" — those are two independently-read JSON keys within the same signed blob.
- After `verify_signature` succeeds, `Webhooks.for_event(event)` dispatches the *same* parsed body to handlers such as `PushHandler`, which resolves the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')` [4](#0-3)  and then calls `stack.sync_github(expected_head_sha: params.after)` [7](#0-6) .
- An attacker who legitimately controls (and has installed the Shipit GitHub App with a known `webhook_secret` for) organization **A** can craft a POST body where `repository.owner.login = "A"` (so `verify_signature` selects org A's secret, which the attacker knows, and produces a valid HMAC) while `repository.full_name = "B/victim-repo"` (a repository belonging to organization **B**, tracked by a different, unrelated Shipit stack). The signature check passes using org A's secret, but the `PushHandler` acts on org B's stack.

### Impact Explanation
This breaks the binding "the organization that authenticated the webhook == the repository that is written by the webhook," which is exactly the class of unprivileged-attacker analog in scope (authenticated org vs. written repository). Concretely, an attacker controlling org A can forge a `push` event for org B's tracked repository with an attacker-chosen `after` SHA, causing `GithubSyncJob` to run against org B's stack [8](#0-7) . While `GithubSyncJob` re-fetches commits from GitHub (using org B's real GitHub credentials, via `stack.github_commits`) rather than trusting attacker-supplied commit content directly, it still drives cross-organization state changes (syncing, unlocking reverted-commit locks, marking accessibility, and — depending on `continuous_deployment` configuration on stack B — can trigger unauthorized deploys/rollbacks off a forged `expected_head_sha`) using credentials/authorization scoped to org A's webhook secret but targeting org B's resources. This crosses a repository/authentication boundary and can result in an unauthorized deploy for a stack the attacker has no legitimate relationship to, matching the "unauthorized deploy" High-severity impact category.

### Likelihood Explanation
Likelihood is Medium: it requires (a) a multi-organization Shipit deployment (documented and supported via `github_app_config`/`github_organizations`) [9](#0-8) , and (b) the attacker legitimately controlling at least one configured organization (i.e. knowing its `webhook_secret`) while targeting a different organization's stack hosted on the same Shipit instance. This is a realistic scenario for any Shipit instance shared across multiple GitHub orgs/teams (a common multi-tenant setup), where a low-privilege org owner could pivot into other orgs' stacks.

### Recommendation
Bind the signature-verification identity to the identity actually acted upon: after selecting `github_app` and verifying the HMAC, re-derive the acting organization from a trusted, already-verified value (or explicitly re-check that `repository.full_name`'s owner matches `repository_owner`/the verified organization) before dispatching to handlers, rather than trusting the same untrusted JSON twice for two different purposes. Alternatively, resolve the `Repository`/`Stack` for a webhook only from repositories explicitly registered as belonging to the verified organization, rejecting events whose target repository's owner differs from the organization whose secret matched.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `A` and `B`, each with its own GitHub App / `webhook_secret` (per `lib/shipit.rb:170-200`), where `B` owns a stack tracked by Shipit.
2. Attacker (owner of org `A`, and thus knows `A`'s `webhook_secret`) crafts a `push` webhook JSON body: `{"ref": "refs/heads/<branch>", "after": "<attacker-chosen-sha>", "repository": {"owner": {"login": "A"}, "full_name": "B/victim-repo"}, ...}`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(A_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "A")`, verifies the HMAC successfully (attacker knows the secret) [2](#0-1) .
5. `PushHandler#process` resolves `repository_name` = `"B/victim-repo"` [4](#0-3)  and enqueues `GithubSyncJob` for org B's stack with the attacker-supplied `expected_head_sha` [7](#0-6) , even though the request was never authenticated by org B's webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
