### Title
CCMenu API token is not scoped to the intended stack, allowing unauthenticated cross-stack read of deploy state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The CCMenu integration hands out an `ApiClient` token that is supposed to authorize read-only access to a *single* stack's build/deploy status, embedded in a shareable URL (e.g. for CI dashboards). In practice, the token is created without any stack binding and the `CCMenuController` looks up the target stack from an unscoped `params[:stack_id]`, so the token silently authorizes reading the deploy state of *every* stack in the installation, not just the one intended.

### Finding Description
When a user requests a CCMenu URL for a stack, `CCMenuUrlController#client` creates (or reuses) an `ApiClient`: [1](#0-0) 

This uses `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — keyed only on the creator and a fixed name, with `permissions: %w[read:stack]` but **no `stack:` attribute**. The result is a single global "CCMenu Client" per user, shared across every stack they ever request a CCMenu URL for, whose `stack_id` column is always `nil`.

That token is then embedded in a URL scoped (in appearance) to one stack: [2](#0-1) 

On the consuming side, `Shipit::Api::BaseController` defines the *correct* scoping pattern — `stacks` restricts to `current_api_client.stack_id` when present: [3](#0-2) 

But `CCMenuController` overrides `stack` and bypasses this scoping entirely, resolving directly from the unscoped `params[:stack_id]`: [4](#0-3) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string — it never verifies the token is scoped to the specific `stack` being requested: [5](#0-4) 

Because the token has no `stack_id` at all (per the creation bug) and `stack` is resolved from `Stack.from_param!(params[:stack_id])` unconditionally, any holder of one CCMenu URL/token can substitute a different `stack_id` in the query string and receive that other stack's deploy/build state — an unprivileged, unauthenticated (no Shipit session, no login) third party who only ever received one CCMenu URL. This breaks the binding "a stack a token authorises versus a stack it touches": the token is presented/authorized for stack A, but the code lets it touch any stack.

### Impact Explanation
This grants **unauthenticated read of stack state / deploy output** for every stack in the Shipit instance to anyone possessing a single leaked CCMenu URL (these URLs are explicitly designed to be embedded in low-trust contexts like CI status dashboards, per `CCMenuUrlController`/`CcmenuController` tests showing `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl` fields returned). This matches the High-severity bucket "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
High. Any legitimate, unprivileged Shipit user can generate a CCMenu URL for a project they're allowed to view (a normal, expected workflow for CI dashboard integration), and that single leaked/shared URL grants an outside observer read access to *all* stacks' status, not just the one it was generated for. No credential theft, session hijack, or privileged access is required beyond possessing one such URL.

### Recommendation
- When creating the CCMenu `ApiClient`, bind it to the specific stack: `ApiClient.create_with(permissions: %w[read:stack], stack: stack).find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')` (uniquely per stack, not per user).
- In `CCMenuController`, use the scoped `stacks` helper from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!(params[:stack_id])`, so tokens with a `stack_id` cannot be used against other stacks.

### Proof of Concept
1. As a normal Shipit user with access to `stack-a`, visit `/stack-a/ccmenu_url` to obtain `ccmenu_url` containing `token=<T>`.
2. Share/embed this URL for `stack-a` monitoring, per its intended purpose.
3. An external party (no Shipit login) takes `<T>` and requests:
   `GET /api/<stack-b-owner>/<stack-b-name>/<env>/ccmenu.xml?token=<T>`
4. Because the `ApiClient` behind `<T>` has `stack_id = nil` and `CCMenuController#stack` ignores any token scoping, the request succeeds and returns `stack-b`'s deploy/build status — a stack the token was never intended to expose.

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end
