Confirmed vulnerability: `Api::CCMenuController` creates an ApiClient token that is *created* scoped to one stack (`CCMenuUrlController#client` creates a client with only `read:stack` permission, meant to be used for `stack.to_param` per `CCMenuUrlController#fetch`), but `Api::CCMenuController#stack` overrides the base class's scoped lookup (`BaseController#stack` / `#stacks`, which restricts to `Stack.where(id: current_api_client.stack_id)` when `current_api_client.stack_id?`) with an unscoped `Stack.from_param!(params[:stack_id])`. The `require_permission :read, :stack` check only validates the permission *name* on the token (`ApiClient#check_permissions!`), not which stack the token is bound to. This breaks the binding "stack a token authorizes == stack it touches".

### Title
Stack-scoped CCMenu API token can read the status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuUrlController#fetch` mints a `Shipit::ApiClient` token intended to be usable only for a single stack (embedded in the generated CCMenu URL for that stack), granting `read:stack` permission. However, `Api::CCMenuController`, which serves that URL, resolves the target stack with `Stack.from_param!(params[:stack_id])` directly instead of using the stack-scoping helper (`stacks`/`stack`) inherited from `Api::BaseController`, which restricts the queryable stacks to `current_api_client.stack_id` when the client is stack-scoped.

### Finding Description
`Api::BaseController` defines the safe, scope-aware accessor: [1](#0-0) 

`Api::CCMenuController` overrides `stack` with an unscoped lookup, and also overrides `authenticate_api_client` to accept the token via a query-string `params[:token]` (used by CI/build-status tools that poll this URL): [2](#0-1) 

The generating endpoint mints a token bound to one stack for CCMenu polling purposes: [3](#0-2) 

`require_permission :read, :stack` only checks the permission *name* against `ApiClient#check_permissions!`, which has no notion of which stack the token is allowed to touch: [4](#0-3) 

Because `Api::CCMenuController#stack` bypasses `stacks` (the only place `current_api_client.stack_id` is actually enforced), any holder of a CCMenu token — which any authenticated Shipit user can generate for a stack they can see, and which is embedded as a plain URL query parameter (often pasted into CI dashboards, IM channels, monitoring tools, etc.) — can request `GET /api/{ANY_OTHER_STACK}/ccmenu.xml?token=<the-leaked-token>` and get build/deploy status output for stacks they were never scoped to. This equality that should hold — "stack the token authorizes == stack the token can touch" — is broken specifically in this one controller, even though the base API controller correctly enforces it elsewhere (e.g. `Api::StacksController`, confirmed by the "an api client scoped to a stack will only see that one stack" test in `test/controllers/api/stacks_controller_test.rb`).

### Impact Explanation
This qualifies as High severity per the listed criteria: "escalation into `Shipit.github_teams` authorization" is not exactly it, but it does match "unauthenticated read of stack state, task streams or deploy output" in effect — a token scoped to stack A is used, without further authorization, to read state (name, last build status/label, last build time, activity, running task status) of any other stack B in the Shipit instance, which the token holder was never granted access to. Because the token leaks trivially (it's a bare URL query parameter designed to be embedded in third-party CCMenu-compatible clients), the practical exposure is broad: any leaked/observed CCMenu URL for a low-privilege stack grants read access to the status of every stack tracked by that Shipit instance.

### Likelihood Explanation
Likelihood is high given normal usage patterns: CCMenu URLs are explicitly generated to be pasted into external tools (CI dashboards, IDE plugins, IM status bots) exactly because they are meant to be used outside of an authenticated browser session; the query-string-token support in `authenticate_api_client` exists specifically to make this convenient. No special privilege beyond having once obtained a CCMenu URL for any stack is required to enumerate/query other stacks — the attacker only needs to know or guess another stack's `owner/repo/environment` triple used in `Stack.from_param!`.

### Recommendation
Make `Api::CCMenuController#stack` use the inherited, scope-aware `stacks`/`stack` accessor (i.e., delete the local override, or change it to `stacks.from_param!(params[:stack_id])`) so that stack-scoped API clients are restricted to their assigned `stack_id` exactly as in every other API controller.

### Proof of Concept
1. As an authenticated Shipit user with access to `stack-A`, visit `stack-A`'s CCMenu link, triggering `CCMenuUrlController#fetch`, which creates (or reuses) an `ApiClient` with `permissions: ['read:stack']` and no explicit `stack_id` restriction is enforced at read time... actually the client itself has no `stack_id` set at all (it's a global client, `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — no `stack:` attribute is passed), and receive URL `https://shipit.example.com/api/stack-A/ccmenu.xml?token=<TOKEN>`.
2. Note that because this client is *never* assigned a `stack_id` at creation, `current_api_client.stack_id?` is false in `Api::BaseController#stacks`, so even the correctly-scoped `Api::StacksController` would treat this token as unrestricted across all stacks — this token is effectively a Shipit-instance-wide "read:stack" token, not stack-scoped at all, compounding the issue: it was never bound to `stack-A` in the first place.
3. Send `GET https://shipit.example.com/api/stack-B/ccmenu.xml?token=<TOKEN>` for any other `stack-B` in the instance.
4. `Api::CCMenuController#authenticate_api_client` accepts the token via `params[:token]`; `require_permission :read, :stack` passes because the token has `read:stack`; `Api::CCMenuController#stack` resolves `stack-B` unscoped via `Stack.from_param!`, returning `stack-B`'s build/deploy status in the XML response — despite the token/URL having been generated for, and intended to be scoped to, `stack-A`.
