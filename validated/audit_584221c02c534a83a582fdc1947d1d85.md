### Title
Cross-repository/cross-stack commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound `status` webhook against the GitHub App/organization derived from the payload's `repository.owner.login` (or `organization.login`), but the handler that then *acts* on the payload, `StatusHandler#process`, never re-checks that binding. It looks up commits globally by SHA across the entire Shipit installation and writes a CI status onto every matching `Commit` row, regardless of which stack/repository/organization it belongs to. This breaks the trust equality: `organization whose signature was verified == repository/stack that gets written`.

### Finding Description
The webhook signature check selects the GitHub App config to verify against using only the repository/organization fields of the payload: [1](#0-0) [2](#0-1) 

This confirms only that *some* configured organization's webhook secret matches the raw request body — it does not, by itself, constrain which `Stack`/`Commit` records the handler is allowed to mutate. That constraint is supposed to be enforced by the handler.

The base `Handler` class does define a `stacks` helper scoped to the repository named in the payload (`Repository.from_github_repo_name(repository_name)&.stacks`) and `PushHandler` correctly uses it: [3](#0-2) [4](#0-3) 

However `StatusHandler#process` does **not** use this repository-scoped helper at all. It resolves the target purely by commit SHA across the whole database: [5](#0-4) 

`Commit.where(sha: params.sha)` matches any `Commit` record in any `Stack`/`Repository` that happens to share that SHA. Git SHAs are shared across forks, mirrors, and repositories with common ancestor history (a routine, non-adversarial occurrence for Shipit installs that track multiple stacks/environments of the same or related codebases, or forks). An attacker who legitimately controls one organization/repository already onboarded into the same Shipit instance (with its own valid `webhook_secret`) can therefore send a fully-signed `status` event for that org, but cite a `sha` that also exists as a commit in a different, unrelated stack (e.g. a shared ancestor commit, a cherry-picked/rebased commit, or a mirrored repository). `StatusHandler#create_status_from_github!` will then attach an attacker-chosen CI state (`success`, description, context, `target_url`) to the commit object living in the victim stack, even though the signature that authorized the request was never scoped to that victim repository/organization.

### Impact Explanation
Commit statuses drive `Commit#deployable?` and the `ci.require` gate that Shipit uses to decide whether a commit is safe to deploy. By forging a `success` status on a commit belonging to a stack the attacker does not control, the attacker can make an otherwise-failing or unchecked commit appear CI-green, defeating the `ci.require` safety check and enabling an unauthorized deploy of that commit in the victim stack. This is a cross-repository write (writing to `Commit`/`Status` records outside the authenticated repository/organization scope) and can translate into an unauthorized deploy — both are listed as Critical-severity impacts.

### Likelihood Explanation
Exploitation requires the attacker to control (or have push/App access to) at least one organization/repository already configured in the target Shipit instance — a realistic scenario in shared or multi-tenant Shipit deployments (e.g., an organization with several teams/orgs onboarded, or fork-based workflows). No compromise of another org's `webhook_secret`, no `ApiClient` token, and no session are required; the attacker uses their own valid, legitimately signed webhook. The only additional requirement is a shared commit SHA between their repository and the victim stack's repository, which is common in fork/mirror/rebase workflows and can also be deliberately engineered by an attacker who forks or imports history from the victim repository into their own controlled repository before onboarding it.

### Recommendation
Scope `StatusHandler#process` (and any other handler that performs writes) to the repository identified in the payload, exactly as `PushHandler` does via `Handler#stacks`/`repository_name`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
This ensures a webhook can only ever mutate commits belonging to the same repository whose organization/App secret produced a valid signature.

### Proof of Concept
1. Attacker owns/administers GitHub organization `attacker-org`, which is legitimately onboarded to the target Shipit instance with a real `webhook_secret`.
2. Attacker forks (or otherwise obtains shared history with) `victim-org/victim-repo`, which is also tracked as a Shipit stack, so that some commit `C` with SHA `deadbeef...` exists identically in both the attacker's repository and the victim's repository/stack.
3. Attacker sends a `status` webhook to Shipit for `attacker-org/attacker-repo`, correctly signed with `attacker-org`'s `webhook_secret`, with body:
   ```json
   {
     "sha": "deadbeef...",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "full_name": "attacker-org/attacker-repo", "owner": { "login": "attacker-org" } }
   }
   ```
4. `WebhooksController#verify_signature` verifies successfully against `attacker-org`'s secret.
5. `StatusHandler#process` executes `Commit.where(sha: "deadbeef...")`, which also matches commit `C` inside `victim-org/victim-repo`'s stack, and calls `create_status_from_github!`, marking that commit `success` for `ci/required-check` in the victim's stack — even though the request was never authorized for `victim-org`.
6. If `victim-org`'s stack has `ci.require: ["ci/required-check"]`, the forged status now makes commit `C` `deployable?`, allowing an unauthorized deploy of that commit in the victim stack.
