### Title
Webhook signature is verified against the claimed `repository.owner.login`, but handlers act on the unrelated `repository.full_name` / a global commit `sha` — allowing cross-organization forgery of deploy-gating events - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to check the HMAC signature against using `repository_owner`, a field read straight out of the unauthenticated JSON body [1](#0-0) . Signature verification only proves the body was signed with the secret belonging to *that claimed owner* — it says nothing about which repository/stack the event handlers then act on, because handlers independently pull `repository.full_name` (or, in the case of commit statuses, only a bare `sha` with no repository scoping at all) out of the very same attacker-supplied body [2](#0-1) [3](#0-2) .

### Finding Description
This is the same class of bug as the external report: a value that is authenticated/verified (the *organization* whose secret produced a valid signature) is not the same value that is subsequently trusted to determine *what gets written* (the *repository*/commit acted upon). In the C4 report, `callDebt` is a stale snapshot of a value (`creditMultiplier`) that later diverges from the live value used to compute `principal`, letting one loan's bad debt force others into loss. Here, the "snapshot" that is checked (`repository_owner`) is decoupled from the value later used to select the mutated resource (`repository.full_name` / `sha`).

Concretely:
- `Shipit.github(organization: repository_owner)` picks a `GitHubApp`/secret keyed on `params.dig('repository','owner','login') || params.dig('organization','login')` [4](#0-3) .
- In the documented multi-org deployment mode, each organization has its own independent `webhook_secret` [5](#0-4) .
- Once the signature check passes for organization A (because the raw body was HMAC-signed with A's own secret — something anyone administering org A's GitHub App legitimately possesses), the raw JSON body is handed unmodified to every registered handler: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) .
- `Handler#stacks` resolves the target `Stack` purely from `payload.dig('repository','full_name')`, with no check that this repository belongs to the organization whose secret validated the request [2](#0-1) . `PushHandler` uses this to trigger `stack.sync_github(expected_head_sha: params.after)` on any matching stack, regardless of the actual repository owner [7](#0-6) .
- Worse, `StatusHandler` doesn't even look at `repository` at all — it applies the forged commit status to `Commit.where(sha: params.sha)` across the *entire* Shipit instance, i.e. any stack/repository whose commit happens to have that sha [3](#0-2) .

So the equality that should hold — "organization whose secret validated the signature" == "organization/repository being mutated" — is never enforced. An unprivileged-relative-to-victim attacker who legitimately administers (or has extracted the webhook secret for) *their own* onboarded organization/GitHub App in a multi-org Shipit deployment can forge a validly-signed webhook whose `repository.owner.login`/`organization.login` matches their own org (so it passes `verify_signature`), while its `repository.full_name` and `sha` fields target a completely different, victim organization's stack.

### Impact Explanation
This crosses a repository/organization trust boundary that the signature check is supposed to enforce: cross-repository writes and unauthorized deploy triggers. A forged `push` event drives `GithubSyncJob`/deploy pipelines for a stack the attacker's org secret was never meant to authorize (`PushHandler#process`). A forged `status` event can mark an arbitrary commit (belonging to any repository tracked by the instance) as successful, which is exactly the kind of check gating `deployable_status` used to permit deploys — potentially unblocking an unauthorized deploy on a victim's stack. This matches the "Critical: cross-repository writes / unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires only that the attacker legitimately control (or have compromised) the webhook secret for *some* organization/GitHub App already configured in the same multi-tenant Shipit instance — a realistic scenario for any shared/self-service Shipit deployment onboarding multiple orgs, as explicitly documented in `docs/setup.md`. No access to the victim organization, its repo, or its webhook secret is needed; only the ability to POST a crafted, self-signed JSON body to `/webhooks`.

### Recommendation
After verifying the signature for the claimed `repository_owner`, re-derive/validate that `repository.full_name`'s owner segment (and any `sha`/commit lookups) actually belongs to that same, authenticated organization before dispatching to handlers — i.e., bind handler-visible identifiers to the verified organization instead of trusting them independently from the same unauthenticated JSON body. For `StatusHandler`, scope the `Commit` lookup by the verified repository, not solely by `sha`.

### Proof of Concept
1. Configure Shipit in multi-org mode with organizations `orgA` (attacker-controlled GitHub App, secret known to attacker) and `orgB` (victim, stack tracked in Shipit).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "orgB/victim-repo", "owner": { "login": "orgA" } }
}
```
3. Attacker computes `X-Hub-Signature` using `orgA`'s own webhook secret over this exact raw body and sends it with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"orgA"` from `params.dig('repository','owner','login')`, fetches `orgA`'s `GitHubApp`, and the signature validates successfully [4](#0-3) .
5. `PushHandler#stacks` resolves the target via `payload.dig('repository','full_name')` = `"orgB/victim-repo"`, and triggers `sync_github` against org B's stack [2](#0-1) [7](#0-6)  — despite the signature having only proven possession of `orgA`'s secret, never `orgB`'s.
