### Title
CCMenuController#stack bypasses ApiClient stack-scoping, allowing cross-stack disclosure - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The specific claim in the prompt — that the `token`-param / Basic-Auth dual authentication fallback in `CCMenuController#authenticate_api_client` lets an attacker escalate past the `read:stack` permission check — does not hold, because `ApiClient#check_permissions!` is invoked identically regardless of which path authenticated the client and correctly raises `InsufficientPermission` for a `write:hook`-only client. However, tracing the same code path reveals a real, related bug: `CCMenuController#stack` overrides the base controller's stack lookup and drops the `stack_id` scoping that restricts a stack-scoped `ApiClient` to its own stack.

### Finding Description
Binding claimed broken: `current_api_client.permissions.include?("read:stack")` == permission required by `require_permission :read, :stack`. Tracing `authenticate_api_client` (ccmenu_controller.rb:33-36) into `BaseController#authenticate_api_client` (base_controller.rb:48-61) and then into `ApiClient#check_permissions!` (api_client.rb:38-45) shows the permission set check is performed the same way no matter which authentication path (query `token` vs Basic-Auth) supplied the client, so a `write:hook`-only client is correctly rejected with `InsufficientPermission`. That part of the claim is false — the equality holds and the guard works.

The actual divergence is elsewhere in the same call chain: `BaseController#stack` (base_controller.rb:78-80) resolves the target record through `stacks` (base_controller.rb:74-76), which restricts lookup to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated client is scoped to a specific stack. `CCMenuController#stack` (ccmenu_controller.rb:29-31) overrides this and instead does `Stack.from_param!(params[:stack_id])` directly against all stacks, with no reference to `current_api_client.stack_id`. So a client created with `stack_id = 5` and `read:stack` permission (for legitimate use on stack 5's CC-menu badge) can request `GET /api/stacks/999/cc_menu.xml` with its own credentials (via either the `token` param or Basic-Auth) and receive stack 999's deploy status, bypassing the per-client stack restriction entirely.

### Impact Explanation
This exposes deploy/rollback status (`stack.deploys_and_rollbacks.last`, running state, timestamps) for any stack in the installation to any holder of a `read:stack`-permitted `ApiClient`, even one intentionally scoped to a single stack by an operator. This is an authorization bypass of the per-client stack restriction — unauthorized read of another tenant's/repository's stack state — matching the High severity category for "unauthenticated/unauthorized read of stack state."

### Likelihood Explanation
Requires possession of any valid `ApiClient` token with `read:stack` permission (regardless of its assigned `stack_id`). Per this audit's threat model the attacker holds no such token, so this is not directly reachable by the fully unprivileged attacker defined in scope; it is a genuine bug reachable only by a legitimate, low-privilege API client attempting to escalate beyond its intended single-stack scope.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped `stacks`/`stack` lookup from `BaseController` (i.e., remove the override, or implement it as `stacks.from_param!(params[:stack_id])`) so stack-restricted `ApiClient`s cannot query stacks outside their assigned `stack_id`.

### Proof of Concept
In `test/controllers/shipit/api/ccmenu_controller_test.rb` (not modifying, just describing expected test): create `client_a = shipit_api_clients(:scoped, stack_id: stacks(:shipit).id, permissions: ['read:stack'])`; issue `get :show, params: { stack_id: stacks(:cyclimse).id, token: client_a.authentication_token }`; assert response is `403`/`404` rather than `200`, i.e. assert `client_a.stack_id != stacks(:cyclimse).id` and that the controller must not render `cyclimse`'s deploy state to a client scoped to `shipit`.
