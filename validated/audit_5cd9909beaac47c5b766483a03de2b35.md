### Title
Unauthenticated live SSE task/stack stream via unauthenticated `mount Pubsubstub::StreamAction.new, at: '/events'` - ([File: config/routes.rb])

### Summary
The engine mounts `Pubsubstub::StreamAction` directly as a Rack endpoint at `/events` in `config/routes.rb`, bypassing the Rails controller stack entirely. All authentication in this engine is enforced exclusively via the `before_action :force_github_authentication` callback in the `Shipit::Authentication` concern, which only runs for requests dispatched through `Shipit::ShipitController` (and its subclasses); a directly mounted Rack app receives no controller callbacks at all.

### Finding Description
The claimed binding is: `authorized?(current_user) == true` must hold before any stack/task broadcast data is exposed to a requester, for every code path that returns that data. Trace:

- `config/routes.rb` line 9: `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` — this is a raw Rack app mounted directly in the engine's route set, not a Rails controller action. [1](#0-0) 
- The engine's only authentication mechanism is `Shipit::Authentication`, a concern providing `before_action :force_github_authentication`, which checks `current_user.logged_in?` and `current_user.authorized?`, redirecting or rendering `403` otherwise. [2](#0-1) 
- This concern is `include`d only in `Shipit::ShipitController` (and separately in `Shipit::Api::BaseController`), meaning it is wired in via Rails' `before_action` filter chain, which only executes for requests routed to an `ActionController` action. [3](#0-2) 
- `Pubsubstub::StreamAction` is a plain Rack endpoint (`.new` instance mounted via `mount`), so it never passes through `ApplicationController`/`ShipitController`/`force_github_authentication` — there is no before_action hook possible on a raw Rack app.
- The engine's `lib/shipit/engine.rb` initializer only inserts `SameSiteCookieMiddleware` and OmniAuth middleware globally; neither authenticates or authorizes requests to `/events`. [4](#0-3) 
- Legitimate views subscribe to channels like `"stack.#{@stack.id}"` and `"repository.#{@repository.id}"` after the surrounding page already passed `force_github_authentication`, e.g. in `stacks/show.html.erb` and `repositories/show.html.erb`. But nothing stops an attacker from independently requesting `GET /events?channels[]=stack.<id>` directly, since `events_path` is a public, guessable, sequential-ID route with no per-channel authorization check inside `Pubsubstub::StreamAction` itself. [5](#0-4) [6](#0-5) 
- Broadcasts to these channels carry live stack/task/commit state updates (`Pubsubstub.publish` calls in `app/models/shipit/stack.rb`, `deploy.rb`, `commit.rb`, `status.rb`), which is exactly the "task/stack broadcast data" the binding is supposed to gate.

Root cause: authorization in this engine is implemented purely as a controller-level `before_action`, with no engine-level Rack middleware or `Pubsubstub::StreamAction` wrapper enforcing `current_user.authorized?` before serving the SSE channel. Mounting a bare Rack app inside the engine's own routes.rb sidesteps that filter entirely.

### Impact Explanation
An unauthenticated attacker who guesses or enumerates a `stack.<id>` (sequential integer, easily brute-forced) can open `GET /events?channels[]=stack.<id>` and receive the live Server-Sent-Events stream of that stack's updates — deploy/task lifecycle events, commit status changes, and other broadcast content — with zero Shipit session, GitHub team membership, or API token. This is repeatable against arbitrary stack or repository IDs across all tenants hosted on the same Shipit instance, matching the "High – unauthenticated read of stack state, task streams" category. It does not by itself grant write/deploy capability or leak GitHub secrets, so it is bounded at High rather than Critical.

### Likelihood Explanation
Preconditions: default engine mounting as documented (`mount Shipit::Engine, at: '/'` per `template.rb`), no additional host-side middleware wrapping `/events` (which the question explicitly asks to exclude). Attacker cost is minimal — a single unauthenticated HTTP GET with a guessed integer ID, no secrets, no privileged role, fully repeatable and scriptable against every stack ID.

### Recommendation
Wrap the `/events` mount with the same authentication/authorization guard used by the rest of the engine (e.g., route through a thin controller action that runs `force_github_authentication`/`current_user.authorized?` and validates the requester has access to the specific `stack.<id>`/`repository.<id>` channel(s) requested before proxying to `Pubsubstub::StreamAction`, or insert dedicated Rack middleware in front of the `/events` mount in `lib/shipit/engine.rb` that enforces the session/authorization check per requested channel).

### Proof of Concept
```ruby
# test/integration/unauthenticated_events_stream_test.rb
require 'test_helper'

module Shipit
  class UnauthenticatedEventsStreamTest < ActionDispatch::IntegrationTest
    setup do
      @stack = shipit_stacks(:shipit)
    end

    test "GET /events with no session reaches Pubsubstub without going through force_github_authentication" do
      # No session cookie set, no current_user, no api_clients_secret used.
      get "/events", params: { channels: ["stack.#{@stack.id}"] },
          headers: { "Accept" => "text/event-stream" }

      # Binding under test: authorized?(current_user) == true required
      # to reach broadcast data. Here current_user would be AnonymousUser,
      # whose #authorized? is false, yet the request is NOT redirected/403'd
      # by force_github_authentication because /events never runs it.
      assert_not_equal 302, response.status, "expected no redirect to github_authentication_path"
      assert_not_equal 403, response.status, "expected no forbidden from force_github_authentication"
      # Pubsubstub::StreamAction itself responds 200 and keeps the connection
      # open for SSE, proving the request reached the stream handler
      # unauthenticated.
      assert_equal 200, response.status
    end
  end
end
```
This demonstrates that the engine's own route/controller stack (`Shipit::Authentication#force_github_authentication`) never executes for `/events`, and the request is served directly by the mounted `Pubsubstub::StreamAction`.

      def skip_authentication(*args)
        skip_before_action(:force_github_authentication, *args)
      end
    end

    private

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
