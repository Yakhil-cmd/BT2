Analog found — mapping the SAML `<Conditions>` validation gap (accepting an assertion structure while never enforcing its temporal-window/audience fields) to ocore's `is_valid_signed_package()` mechanism.

### Title
`is_valid_signed_package()` accepts a `timestamp` field in signed packages but never validates it, enabling indefinite replay of stale AA authorizations - ([File: signed_message.js])

### Summary
`signed_message.js`'s `validateSignedMessage()` explicitly whitelists `timestamp` as a permitted field of a signed package (`"signed_message", "authors", "last_ball_unit", "timestamp", "version"`), giving oscript authors the impression that the platform enforces a temporal validity window on the package, analogous to a SAML assertion's `<Conditions>` element (`NotBefore`/`NotOnOrAfter`). In reality this field is never read or compared against `Date.now()`, `last_ball_timestamp`, or any expiry logic anywhere in the function. [1](#0-0) 

### Finding Description
The only "freshness" check performed by the signature-verification path is in `formula/evaluation.js`'s `is_valid_signed_package` handler, which resolves `last_ball_unit` and rejects the package only if that unit's MCI is unknown or is *later* than the current evaluation MCI: [2](#0-1) 

This is a one-sided ("not from the future") bound only — equivalent to SAML's `NotBefore` check on the *authoring context*, not to an upper bound (`NotOnOrAfter`) on how long the package itself can be presented and reused. `validateSignedMessage()` itself performs no comparison at all involving the accepted `timestamp` field: [3](#0-2) 

Because the signature only binds `signed_message`, `authors`, `last_ball_unit`, `timestamp`, and `version` together (via `getSignedPackageHashToSign`), and the framework never checks the `timestamp` value against wall-clock time or any window, a valid signed package remains cryptographically and semantically "valid" (`is_valid_signed_package` returns `true`) forever, as long as its `last_ball_unit`'s MCI is `<= mci` at evaluation time — which is trivially true for any past unit. An oscript/AA author who follows the field's apparent purpose (treating `signed_message.timestamp` as a self-enforced expiry, similar to how SAML consumers trust `Conditions`) gets no protection from the platform: the field is decorative unless the AA independently tracks a nonce/counter in state (as the shipped `payment_channels.oscript` and `order_book_exchange.oscript` samples do manually via `period` / `executed_<id>` state variables) precisely because the platform provides none. [4](#0-3) [5](#0-4) 

### Impact Explanation
Any AA that relies on `is_valid_signed_package()` to authorize a fund-moving action gated by a claimed expiry/one-time semantics embedded in the signed package's `timestamp` field (rather than implementing its own explicit anti-replay state, which is not mandatory and not obviously required by the API) can have old, stale signed authorizations (price quotes, vouchers, channel-close instructions, order confirmations) replayed by any party who can post an AA trigger unit — an unprivileged capability. This can result in AA fund loss/draining or double-execution of an action the off-chain co-signer believed was time-limited, since the platform silently accepts the stale package as valid.

### Likelihood Explanation
Any unprivileged unit poster can construct an AA trigger unit whose `data` field embeds a previously captured, still-correctly-signed package and invoke the target AA at any later MCI; `last_ball_unit`'s MCI will always be `<= mci` for a past package, so the only two checks in the pipeline (definition/signature match, and "not from the future") both pass trivially. No special privileges, hub/node compromise, or timing race is required — only that the target AA's oscript logic trusts the built-in `timestamp` field as if it were enforced, rather than adding its own nonce/state check.

### Recommendation
- Either strip `timestamp` from the whitelisted/allowed fields of a signed package in `signed_message.js` (line 132) so authors cannot mistakenly rely on unenforced platform semantics, or
- Add explicit temporal-window validation in `validateSignedMessage()`/`is_valid_signed_package` (e.g., comparing `timestamp` against `objValidationState.last_ball_timestamp` and a configurable max-age), mirroring `NotBefore`/`NotOnOrAfter` semantics, and
- Update documentation/oscript samples to state unambiguously that anti-replay/expiry for signed packages must be implemented by the AA itself via persistent state (nonce, period counter, or explicit id/lookup) — as already done in `payment_channels.oscript` and `order_book_exchange.oscript` — since the framework provides no such guarantee despite accepting the `timestamp` field.

### Proof of Concept
1. Party A signs a package containing `signed_message: {action: "release_funds", amount: 1000, timestamp: <T0>}`, `last_ball_unit`, `authors`, intending it to authorize a one-time transfer valid only "around" `T0`, and sends it off-chain to Party B (e.g., in a payment-channel or voucher scheme) trusting the built-in `timestamp` field as the expiry.
2. The target AA's oscript checks only `is_valid_signed_package(trigger.data.pkg, address_A)` (without independently tracking a nonce/period in `var[]`), then executes the fund-moving message.
3. Party B (or anyone who obtained the package) posts the exact same signed package inside a new AA trigger unit at MCI `T1 >> T0`, arbitrarily far in the future.
4. `is_valid_signed_package` resolves `last_ball_unit`'s MCI, finds it `<= mci` (always true for a past unit), calls `validateSignedMessage`, which never inspects `timestamp`, and the signature verification succeeds exactly as it did at `T0`. The AA re-executes the fund transfer, believing the authorization is still "fresh," even though `timestamp` (`T0`) is long expired.
