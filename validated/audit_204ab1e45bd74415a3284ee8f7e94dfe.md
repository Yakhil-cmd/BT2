### No vulnerability found for this question.

**Reasoning:** `deposit` (mainnet/contracts/vault/v0-vault-stx.clar:763) calls `accrue` (which is the only thing that may update `index`/`last-update`), pulls underlying from `contract-caller` via `receive-underlying`, and mints `zft` shares to the caller-chosen `recipient` via `ft-mint?` [1](#0-0) . It never writes `principal-scaled`, `total-borrowed`, or any per-borrower record — only `assets` and the `zft` supply/balances are mutated [2](#0-1) . `total-debt` is a pure read of `(calc-cumulative-debt (var-get principal-scaled) (var-get index))` [3](#0-2) , and `deposit` only *reads* it indirectly (through `convert-to-shares-preview` → `total-assets-preview` → `debt-preview`) to price shares — it never writes borrower debt state [4](#0-3) .

Because `deposit`'s `recipient` argument only directs newly minted *shares* (an asset/credit) to an arbitrary principal, an "unsolicited on-behalf-of" call can at most give a stranger shares they didn't ask for — it cannot debit them, alter their debt ledger, or socialize a borrower's loss onto them. There is no mechanism by which caller A's `deposit` call writes any shared debt-ledger variable (`principal-scaled`, `index`, `total-borrowed`) that a distinct victim B's transaction later reads to B's detriment. The required two-party loss pattern (A writes shared state, B is harmed reading it) does not exist on this path, so the claim fails the invariant check.
