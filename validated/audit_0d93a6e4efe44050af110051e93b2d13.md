### Title
`Bridge.transferOwnership()` Does Not Deregister the Old Owner as an Operator, Allowing the Former Owner to Drain Bridge Funds — (`contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`BridgeOperator`'s constructor registers `msg.sender` as both the Ownable `owner` and as an `operator`. When `transferOwnership()` is called, only the `_owner` slot is updated (via the inherited OpenZeppelin `Ownable`). The old owner's entry in `operators[oldOwner]` and `operatorList` is never cleared. With the default threshold of 1, the former owner can immediately call `handleKLAYTransfer()`, `handleERC20Transfer()`, or `handleERC721Transfer()` to drain bridged assets to an arbitrary address.

---

### Finding Description

`BridgeOperator.sol` maintains two independent authority roles:

1. **Owner** — stored in `_owner` (OpenZeppelin `Ownable`), controls administrative functions (`registerOperator`, `deregisterOperator`, `setOperatorThreshold`, `setRunningStatus`, etc.).
2. **Operators** — stored in `operators` mapping and `operatorList` array, control value-transfer execution (`handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer`) and configuration voting (`setKLAYFee`, `setERC20Fee`).

The constructor seeds both roles with the same address:

```solidity
// BridgeOperator.sol lines 54-61
constructor() internal {
    for (uint8 i = 0; i < uint8(VoteType.Max); i++) {
        operatorThresholds[uint8(i)] = 1;
    }
    operators[msg.sender] = true;
    operatorList.push(msg.sender);
}
```

`transferOwnership()` is inherited verbatim from OpenZeppelin `Ownable`:

```solidity
// Ownable.sol lines 70-74
function _transferOwnership(address newOwner) internal {
    require(newOwner != address(0), "Ownable: new owner is the zero address");
    emit OwnershipTransferred(_owner, newOwner);
    _owner = newOwner;
}
```

It only writes `_owner`. The `operators` mapping and `operatorList` array are untouched. After the call, the old owner is no longer the `owner` but remains a registered operator.

The `handleKLAYTransfer` function is gated only by `onlyOperators`:

```solidity
// BridgeTransferKLAY.sol lines 62-100
function handleKLAYTransfer(
    bytes32 _requestTxHash,
    address _from,
    address payable _to,
    uint256 _value,
    uint64 _requestedNonce,
    uint64 _requestedBlockNumber,
    bytes memory _extraData
)
    public
    onlyOperators
    nonReentrant
{
    ...
    (bool ok, ) = _to.call.value(_value)("");
    require(ok, "handleKLAYTransfer: transfer failed");
}
```

The default `operatorThresholds[ValueTransfer] = 1`, so a single operator vote immediately executes the transfer.

---

### Impact Explanation

The former owner retains the ability to call `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` with arbitrary `_to` and `_value` parameters. With threshold = 1 (the default), a single call by the former owner is sufficient to execute the transfer and drain KLAY or ERC20/ERC721 tokens held by the bridge contract. This constitutes an **unauthorized transfer of bridged assets** (KLAY, ERC20, ERC721) to an attacker-controlled address.

---

### Likelihood Explanation

- `transferOwnership` is a standard, expected administrative operation. A new owner taking over a bridge would naturally call it.
- The old owner is automatically an operator from deployment — no extra setup is needed.
- The default threshold is 1, so no collusion or additional votes are required.
- The new owner cannot prevent the attack: `deregisterOperator` is `onlyOwner`, so the new owner can call it, but the old owner can front-run any deregistration by immediately calling `handleKLAYTransfer` in the same block.

---

### Recommendation

Override `transferOwnership` in `BridgeOperator` to atomically deregister the old owner from the operator list before updating `_owner`:

```solidity
function transferOwnership(address newOwner) public onlyOwner {
    address oldOwner = owner();
    // Deregister old owner from operators if still registered
    if (operators[oldOwner]) {
        delete operators[oldOwner];
        for (uint i = 0; i < operatorList.length; i++) {
            if (operatorList[i] == oldOwner) {
                operatorList[i] = operatorList[operatorList.length - 1];
                operatorList.length--;
                break;
            }
        }
        emit OperatorDeregistered(oldOwner);
    }
    super.transferOwnership(newOwner);
}
```

Alternatively, add a combined `transferOwnershipAndOperator(address newOwner)` that atomically deregisters the old operator and registers the new owner as an operator.

---

### Proof of Concept

```
1. Alice deploys Bridge(false).
   State: owner = Alice, operators[Alice] = true, threshold = 1

2. Alice calls transferOwnership(Bob).
   State: owner = Bob, operators[Alice] = true  ← Alice still an operator

3. Bob (new owner) intends to deregisterOperator(Alice), but Alice front-runs:

4. Alice calls handleKLAYTransfer(
       requestTxHash = <any>,
       _from = Alice,
       _to = Alice,          // attacker-controlled address
       _value = <bridge balance>,
       _requestedNonce = 0,
       _requestedBlockNumber = <current>,
       _extraData = ""
   )
   → onlyOperators passes (Alice is still in operators mapping)
   → _voteValueTransfer passes (threshold = 1, Alice's single vote suffices)
   → Bridge sends entire KLAY balance to Alice
```

**Root cause:** [1](#0-0)  registers `msg.sender` as operator at construction, while [2](#0-1)  only updates `_owner` on transfer, leaving `operators[oldOwner]` intact.

**Exploitable function:** [3](#0-2)  — `handleKLAYTransfer` is gated only by `onlyOperators` and sends KLAY to an arbitrary `_to`.

**Operator gate:** [4](#0-3)  — `onlyOperators` checks `operators[msg.sender]`, which remains `true` for the old owner after `transferOwnership`.
