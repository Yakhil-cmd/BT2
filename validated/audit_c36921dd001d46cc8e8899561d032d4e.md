### Title
Unfiltered fork-controllable environment variables (PR labels & `shipit.yml` `machine.environment`) reach `PTY.spawn`, allowing environment-variable injection into the deploy process - ([File: lib/shipit/task_commands.rb], [File: app/models/shipit/review_stack.rb], [File: lib/shipit/command.rb])

### Summary
`ReviewStack#env` merges every PR label name (uppercased) directly into the stack's environment hash with no allowlist, and `TaskCommands#env` merges `deploy_spec.machine_env` (read from the PR branch's `shipit.yml`) with no allowlist either — unlike deploy/rollback/task variables, which are always passed through `EnvironmentVariables#permit`. Both paths flow unfiltered into `Command#env`, then into `Command#unbundled_env`, which is passed straight to `PTY.spawn`. Under `provisioning_behavior = allow_with_label`, an attacker who can label their own PR (per this audit's threat model) or control the PR branch's `shipit.yml` can inject arbitrary keys — including `SHELL` — into the spawned deploy/task process's environment.

### Finding Description
The invariant that should hold is: `env reaching PTY.spawn ⊆ allowlisted keys defined by VariableDefinition/EnvironmentVariables.permit`. This holds for `Stack#trigger_task` (`definition.filter_envs(env)` → `EnvironmentVariables.with(env).permit(variables)`) [1](#0-0)  and for `Stack#build_deploy` (`filter_deploy_envs(env.to_h)`) [2](#0-1) , both of which raise `EnvironmentVariables::NotPermitted` for unlisted keys [3](#0-2) .

The invariant is broken for two other contributors to the same final environment hash:

1. `ReviewStack#env` merges every PR label name, uppercased, as a `"true"`-valued env var, with no allowlist at all: [4](#0-3) 

2. `TaskCommands#env` merges `deploy_spec.machine_env` (sourced from `shipit.yml`'s `machine.environment` key on the checked-out branch) directly, with no call to `EnvironmentVariables.permit`: [5](#0-4) [6](#0-5) 

Both merged hashes end up in `Command#env`, then in `Command#unbundled_env`, which builds the final env passed to `PTY.spawn` with no filtering of dangerous keys such as `SHELL`, `RUBYOPT`, `BUNDLE_GEMFILE`, `LD_PRELOAD`, etc.: [7](#0-6) [8](#0-7) 

Reachability: under `provisioning_behavior_allow_with_label`, `OpenedHandler#provision?` and `LabeledHandler#archive?/unarchive?` gate stack provisioning strictly on presence/absence of the configured label on the PR — no maintainer approval or additional check is performed beyond the label match: [9](#0-8) [10](#0-9) 

Per this audit's attacker model, the attacker can label their own PR and/or control the shipit.yml on the PR's branch, so both `pull_request.labels` and `deploy_spec.machine_env` are attacker-influenced inputs that reach the spawned process's environment unfiltered, in violation of the intended `EnvironmentVariables#permit` allowlist boundary that is enforced everywhere else in the codebase (deploy env, rollback env, task env).

Existing guards do not close this gap: `EnvironmentVariables#permit` is never invoked on `ReviewStack#env`'s label-derived hash nor on `DeploySpec#machine_env`, and `Command#unbundled_env` performs no denylist/allowlist of dangerous variable names before merging `@env`.

### Impact Explanation
An attacker can inject arbitrary named environment variables into the child process for every review-stack deploy/task on the affected review stack. Confirmed unfiltered injection vectors are (a) PR label names, and (b) `shipit.yml` `machine.environment` values on the PR branch. This directly matches the Critical “command running that should not” category to the extent that the injected variable influences downstream tool behavior (e.g. `RUBYOPT`, `BUNDLE_GEMFILE`, `GEM_PATH`, `LD_PRELOAD`, or values consumed by scripts/tools invoked inside the deploy steps that honor such variables) — this is a genuine unauthorized-write into the deploy process's execution environment for the affected repository's review stack.

One caveat that could not be fully verified from static inspection alone: whether the specific mechanism claimed in the question — `SHELL` changing which shell binary interprets a step passed to `PTY.spawn` — actually materializes, because Ruby's `Process.spawn`/`PTY.spawn` single-string-command invocation path uses a hardcoded `/bin/sh -c` (not the `$SHELL` env var) when shell interpretation is triggered, and may bypass the shell entirely for metacharacter-free command lines. Regardless of that specific detail, the broader vulnerability — arbitrary, unwhitelisted environment variables reaching the spawned deploy/task process — is confirmed and is a real security boundary violation, since other equivalent code paths (deploy/rollback/task env) are deliberately allowlisted and these two are not.

Blast radius is scoped to the review stack(s) belonging to the repository whose PR triggered provisioning; it is repeatable against every such review stack/task run.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled = true` and `provisioning_behavior = allow_with_label` (or `allow_all`, which removes even the label gate). The attacker must be able to add the configured provisioning label to their PR, and/or control the `shipit.yml` on the PR's branch. Per this audit's stated attacker capabilities, both are assumed available at zero cost to the attacker (self-service on their own PR), making this a low-cost, repeatable action for every PR/task run on the review stack.

### Recommendation
Apply the same `EnvironmentVariables.with(...).permit(...)` allowlist used for deploy/rollback/task env to (1) the PR-label-derived hash built in `ReviewStack#env`, and (2) `DeploySpec#machine_env` before merging it into `TaskCommands#env`. Additionally, harden `Command#unbundled_env` to explicitly strip/deny a fixed denylist of security-sensitive variable names (`SHELL`, `RUBYOPT`, `BUNDLE_GEMFILE`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `GEM_PATH`, `GEM_HOME`, etc.) regardless of source, so that no single source of untrusted input can affect process-level execution behavior.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_env_test.rb
require 'test_helper'

module Shipit
  class ReviewStackEnvInjectionTest < ActiveSupport::TestCase
    test "PR labels inject unfiltered env vars into TaskCommands#env" do
      stack = shipit_stacks(:review_stack)
      stack.pull_request.labels = ["SHELL"] # attacker-controlled label
      task = shipit_tasks(:shipit_restart)
      task.stack = stack

      env = Shipit::TaskCommands.new(task).env

      # Binding under test: no fork-controllable key should reach env.
      assert_equal "true", env["SHELL"], "SHELL should not be attacker-settable via PR label"
    end

    test "machine_env from shipit.yml is not allowlisted before reaching Command#env" do
      deploy_spec = stub(
        dependencies_steps!: [],
        deploy_steps!: [],
        machine_env: { "SHELL" => "/tmp/attacker_shell" },
        directory: nil,
        clear_working_directory?: true
      )
      task = shipit_tasks(:shipit_restart)
      commands = TaskCommands.new(task)
      commands.stubs(:deploy_spec).returns(deploy_spec)

      command = commands.perform.first || Command.new('true', env: commands.env, chdir: '.')

      assert_equal "/tmp/attacker_shell", command.unbundled_env["SHELL"],
        "Command#unbundled_env should not carry an attacker-supplied SHELL value to PTY.spawn"
    end
  end
end
```
Both assertions currently pass (i.e., the malicious value is present), demonstrating the broken binding: attacker-controlled `SHELL` (or any other key) reaches `Command#unbundled_env`, which is passed directly to `PTY.spawn`.
