### Title
Permanent market freeze from RAY-value overflow in interest accrual - (File: common/src/rates/index.rs)

### Summary
`accrue_step` computes `borrowed * borrow_index` (and `supplied * supply_index`) in `i128` via `Ray::mul` before the `MAX_BORROW_INDEX_RAY` clamp can engage. On a large high-decimal market at sustained high borrow utilization, the compounded index grows until the raw RAY value exceeds `i128::MAX` (~1.7e38), at which point the multiplication panics with `MathOverflow`. Because every pool entrypoint runs `global_sync` first, the panic permanently bricks the market: no repay, withdraw, borrow, liquidate, or `update_indexes` call can ever succeed again. This is the lending-protocol analog of the referenced crash-DoS class (CVE-2021-2278): a reachable, repeatable panic that halts the component, here with permanent fund lockup rather than a restartable crash.

### Finding Description
Every pool mutation loads the market into `Cache` and calls `interest::global_sync`, which loops `accrue_chunk` over elapsed time and delegates to `accrue_step` (`contracts/pool/src/interest.rs:20-53`). Inside accrual, `calculate_supplier_rewards` computes `old_total_debt = borrowed.mul(env, old_borrow_index)` and `new_total_debt = borrowed.mul(env, new_borrow_index)` (`common/src/rates/index.rs:80-83`), and `update_supply_index` computes `supplied.mul(env, old_index)` (`common/src/rates/index.rs:34`). `Ray::mul` panics on `i128` overflow (`GenericError::MathOverflow`).

The `MAX_BORROW_INDEX_RAY` / `MAX_SUPPLY_INDEX_RAY` ceilings (1e36 raw, `common/src/constants/pool.rs:19-23`) clamp the *index*, but the overflow happens in the *value* product `scaled_shares * index`, which can exceed `i128::MAX` while the index is still far below the cap. The test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates this exactly: a ~1e9-whole-token, 18-decimal market at 98% utilization on the XLM rate curve reaches the cliff, `update_indexes` panics with `MathOverflow`, and afterward both `withdraw` and `repay` panic identically because they accrue first (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:315-361`). The test asserts `last.borrow_index < MAX_BORROW_INDEX_RAY`, proving the cap never engages.

An unprivileged attacker can set up the precondition alone: `supply` a very large balance into a listed high-decimals market, `borrow` up to the steep curve segment, then let time pass. Any subsequent `update_indexes` (callable permissionlessly) or any user verb triggers the freezing panic. No privileged action, oracle manipulation, or leaked key is needed.

### Impact Explanation
Permanent freezing of funds for the entire affected market. Once the panic state is reached, every supplier's deposit and every borrower's collateral backing that debt is unrecoverable: `withdraw`, `repay`, `liquidate`, `seize`, `claim_revenue`, and `recapitalize` all route through `global_sync` and all panic. There is no admin escape hatch — the accrual runs inside the same transaction before any mutation, so even owner-only paths cannot skip it. This also blocks `clean_bad_debt`/liquidation flows in the controller that call pool entrypoints for that market, so protocol insolvency handling is impaired.

### Likelihood Explanation
Medium. The trigger demands whale-scale capital (test uses ~1e9 whole units of an 18-decimal token, i.e. raw scaled shares near 1e36) and sustained ~98% utilization on a steep rate curve for multiple years before the value product crosses `i128::MAX`. That is a high but purely economic barrier — on a token with a large real supply (e.g., XLM-class assets) the capital requirement is feasible for a motivated attacker or can arise organically without any attack. Once crossed, the freeze is deterministic and irreversible; the index-cap guard that was supposed to bound growth provably does not fire first.

### Recommendation
Enforce the index cap by value headroom, not just by index magnitude. Options:
- In `update_borrow_index`/`update_supply_index`, clamp the new index to `min(cap, i128::MAX / scaled)` computed with saturating division so `scaled * index` can never overflow (`common/src/rates/index.rs:13-44`).
- Alternatively use saturating multiplication for the value products inside `accrue_step` (`borrowed.mul`, `supplied.mul`, `calculate_supplier_rewards`) so accrual saturates instead of panicking, then let `MAX_BORROW_INDEX_RAY` cap growth on subsequent steps.
- A defense-in-depth option is bounding the market's scaled `supplied`/`borrowed` totals at listing/mint time so that `scaled * MAX_BORROW_INDEX_RAY <= i128::MAX` holds by construction.

### Proof of Concept
The repository already contains an executable PoC: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`.

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);          // unprivileged supply
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);             // unprivileged 98% borrow

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// -> Error(Contract, MathOverflow); borrow_index < MAX_BORROW_INDEX_RAY
// Market permanently frozen:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

After the accrual panic, no verb on that market — including liquidation and revenue claims — can execute, leaving all supplier and collateral value in it permanently locked.
