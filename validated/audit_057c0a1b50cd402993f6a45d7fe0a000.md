### Title
Webhook signature verification keys off `repository.owner.login`, but handlers act on the independent, attacker-controlled `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) taken directly from the attacker-supplied JSON body. `Webhooks::Handlers::Handler#repository_name`, used by every handler (`PushHandler`, `PullRequest::ClosedHandler`, etc.) to look up the `Stack`/`Repository` to act on, reads a *different*, independently-controlled field: `repository.full_name`. Nothing enforces that these two fields refer to the same repository/organization. Since the entire request body is authored by the attacker before signing, an attacker who knows (owns) the webhook secret for any one org configured in a multi-org Shipit deployment can forge a payload where `repository.owner.login` matches "their" org (so the signature check passes) while `repository.full_name` names a totally different, victim org's repository that the attacker does not control.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes: [1](#0-0) 
using `repository_owner`, defined as: [2](#0-1) 

The secret used for the HMAC check is looked up via `Shipit.github(organization: repository_owner)`, i.e. it is entirely determined by a value the attacker put in the JSON body they are about to sign.

Every webhook handler, however, resolves the target repository/stack from a *separate* JSON field, unrelated to the one used for signature-secret selection: [3](#0-2) 

`Repository.from_github_repo_name` then does a straight DB lookup by owner/name parsed out of that string: [4](#0-3) 

Because HMAC-SHA1 verification only proves "this exact byte sequence was signed with secret S"; it does not, and cannot, prove any semantic relationship between two fields that both live inside that byte sequence. In genuine GitHub webhooks, `repository.owner.login` and `repository.full_name`'s owner segment always agree because GitHub itself constructs the payload. Shipit has no equivalent server-side check that these two attacker-adjacent fields are consistent — it trusts the payload's own internal claims about which org "owns" it for secret selection, then separately trusts a different internal claim about which repository to mutate.

Concretely, in a Shipit instance configured for multiple organizations (as documented in `config/secrets.development.example.yml:18-38` and `docs/setup.md:20-104`), each org has its own `webhook_secret`. An attacker who is an admin of (or has otherwise obtained the webhook secret for) OrgA's GitHub App installation can craft a POST to `/webhooks` with:
- `repository.owner.login = "orgA"` (or `organization.login = "orgA"`) → signature verified against OrgA's secret, which the attacker legitimately knows.
- `repository.full_name = "orgB/victim-repo"` → used by every handler to locate the actual `Stack`/`Repository` acted upon.

This breaks the binding: **organization authenticated (via signature) == repository written (via handler)**.

### Impact Explanation
Downstream handlers act on whatever `Stack` belongs to the victim repository named in `repository.full_name`:
- `PushHandler#process` enqueues `GithubSyncJob` for every non-archived stack on the branch, using an attacker-chosen `expected_head_sha` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), forcing the victim stack to sync against a commit of the attacker's choosing. [5](#0-4) 
- `StatusHandler#process` creates a commit status on any commit matching an attacker-supplied `sha`, which can influence CI-gated deploy decisions for the victim stack. [6](#0-5) 
- `PullRequest::ClosedHandler#process` archives review stacks for the victim repository based on a forged "closed" PR event. [7](#0-6) 

This lets an attacker who controls only their own org's webhook secret manipulate state (commit statuses, sync triggers, review-stack lifecycle) belonging to a repository/organization they have no access to. This does not by itself grant `GITHUB_TOKEN`/`github_access_token` exfiltration or direct RCE, but it does cross the organization/repository trust boundary the signature mechanism is supposed to enforce, and can be leveraged to influence deploy-gating signals (fake commit statuses, forced re-syncs) on a victim's stack — i.e., cross-repository writes performed by the engine acting on GitHub state it does not own.

### Likelihood Explanation
Exploitability requires the attacker to know a valid `webhook_secret` for *some* org configured in the same Shipit instance — realistic in any shared/multi-tenant Shipit deployment where different teams/orgs each manage their own GitHub App installation but share one Shipit host, since installing a GitHub App and setting its webhook secret is something each org's own admins legitimately do. No repository write access, API token, or session to the victim's Shipit account/org is needed — only the webhook secret of an unrelated org already trusted by the instance.

### Recommendation
After signature verification succeeds, re-derive the organization/owner strictly from the field(s) actually used by the handlers (`repository.full_name` / `organization.login`) and require it to match the org whose secret validated the signature; reject the webhook if they diverge. Alternatively, verify the signature using the secret resolved from `repository.full_name`'s owner segment (the same field handlers use) rather than a separately-read `repository.owner.login`/`organization.login`, so a single field controls both signature-secret selection and target-repository resolution.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` and `orgB`, each with a distinct `webhook_secret` (per `docs/setup.md`'s multi-org example).
2. As an attacker who administers `orgA`'s GitHub App (and thus knows `orgA`'s `webhook_secret`), craft a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. In `WebhooksController#verify_signature`, `repository_owner` resolves to `"orgA"`, so `Shipit.github(organization: "orgA")` is used and the signature validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
5. `PushHandler#process` calls `Handler#repository_name`, which returns `"orgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), and `Repository.from_github_repo_name` resolves the real `orgB/victim-repo` `Stack`, enqueuing `GithubSyncJob` for it with the attacker-supplied `expected_head_sha` — despite the attacker never having proven any relationship to `orgB`.
