## Title
Webhook signature verification keys off `repository.owner.login` while handlers act on the unrelated, unscoped `repository.full_name` / global commit `sha` — organization authenticated ≠ repository/commit written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using `repository.owner.login` (or `organization.login`) taken from the *unauthenticated* request body itself. Once that check passes, `Webhooks::Handlers::Handler#stacks`/`#repository_name` and `StatusHandler#process` act on a *different* attacker-controlled field (`repository.full_name`, or a bare `sha` with no repository scoping at all). Nothing enforces that the organization used to pick the verification secret matches the repository/commit actually mutated. This mirrors the reported bug class: a state-affecting operation is driven by a value that was never bound to the value that was actually checked/verified.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`lib/shipit/github_app.rb#verify_webhook_signature` unconditionally accepts the request when the target org has no `webhook_secret` configured — a state the setup docs explicitly describe as *optional*:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) [3](#0-2) 

The org used for *authentication* (`repository.owner.login`) is never bound to the repository the handlers then act on, which is instead read from `repository.full_name`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Worse, `StatusHandler` doesn't even scope by repository at all — it looks up commits by bare `sha` across the *entire* installation and writes attacker-supplied CI status fields directly:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

**Binding broken:** organization authenticated by `verify_signature` (`repository.owner.login`, an org with no `webhook_secret`) ≠ repository/commit actually written by the handler (`repository.full_name` for Push/CheckSuite handlers, or an unscoped global `sha` for `StatusHandler`).

### Impact Explanation
If any GitHub App entry in `config/secrets.yml` is configured without a `webhook_secret` (explicitly supported/"optional" per `docs/setup.md`), an unauthenticated attacker can:
1. Send a POST to `/webhooks` with `X-Github-Event: status`, `repository.owner.login` set to that unsecured org (or `organization.login` for organization-scoped events) — passing `verify_signature` trivially since no secret is enforced.
2. Set `sha`, `state`, `context`, `description`, `target_url` to any values that reference a commit belonging to a completely different, secured organization/stack.
3. `StatusHandler` creates the forged `Status` for that commit — with no repository check at all — because `Commit.where(sha:)` is global.

This can be used to forge a passing status for a `ci.require` context (see README `ci.require`) on a commit awaiting deploy in an unrelated, properly-secured stack, satisfying Shipit's CI gating and enabling an **unauthorized deploy**. It can also spoof `push`/`check_suite` events to resync/trigger jobs for stacks belonging to organizations the attacker was never authenticated against. This satisfies the required "unauthorized deploy" / cross-repository-write impact bar.

### Likelihood Explanation
Requires only that one configured GitHub App entry omit `webhook_secret` — an officially documented, supported configuration (multi-org setups per `docs/setup.md` are explicitly designed to let each org have its own optional secret). No credentials, no `ApiClient` token, no repository write access, and no session are required — only a single unauthenticated HTTP POST to the public `/webhooks` endpoint. The mismatch between the field used for signature-org selection and the field used for repository/commit resolution is unconditional or, in `StatusHandler`'s case, entirely absent.

### Recommendation
- Verify webhook signatures using the org config tied to the *actual* repository being mutated (derive both from the same trusted field, e.g. `repository.full_name`'s owner segment, not a separately-sourced `owner.login`), and never allow one org's (potentially secret-less) verification to authorize writes to a repository/commit outside that org.
- Reject (or explicitly warn/require signature) webhook processing when `webhook_secret` is blank rather than silently returning `true`, or at minimum ensure any org lacking a secret cannot affect repositories outside its own namespace.
- Scope `StatusHandler#process` (and any other handler using a bare identifier) to commits belonging to stacks under the same repository/organization validated by `verify_signature`, instead of a global `Commit.where(sha:)` lookup.

### Proof of Concept
Given `config/secrets.yml`:
```yaml
production:
  github:
    unsecured-org:
      app_id: 1
      installation_id: 1
      webhook_secret: # blank/omitted, per docs as "optional"
    victim-org:
      app_id: 2
      installation_id: 2
      webhook_secret: some-real-secret
```
Attacker sends (no valid signature needed, since `unsecured-org` has no secret):
```
POST /webhooks
X-Github-Event: status

{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "unsecured-org/whatever" },
  "sha": "<sha of a commit currently pending in victim-org/production stack>",
  "state": "success",
  "context": "<ci.require context configured on victim-org's stack>",
  "description": "forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```
`verify_signature` resolves `Shipit.github(organization: 'unsecured-org')`, whose `verify_webhook_signature` returns `true` unconditionally. `StatusHandler#process` then runs `Commit.where(sha: <victim sha>)` — matching the commit in `victim-org`'s stack regardless of the org used for authentication — and calls `commit.create_status_from_github!(params)`, writing a forged "success" status that can satisfy `ci.require` and clear the way for an unauthorized deploy of that commit.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
