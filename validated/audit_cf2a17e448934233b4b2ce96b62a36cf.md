## Finding

### Title
Type-unsafe `!=` comparison in the in-memory AA data-feed fast path allows incorrect `in_data_feed` results before stabilization - (File: `data_feeds.js`)

### Summary
`dataFeeds.dataFeedExists()` has two code paths that are supposed to be equivalent: a slow, authoritative path that queries the persisted key-value store (`dataFeedByAddressExists`), and a fast, in-memory "shortcut" path that scans still-unstable AA-authored `data_feed` messages (`storage.assocUnstableMessages`) before falling back to the persisted lookup. Just like the axios `shouldBypassProxy()` bug, where a bypass decision was made using naive string matching instead of resolving true equivalence between `localhost`/`127.0.0.1`/`::1`, this fast path makes a type-equivalence decision using an incomplete check, causing it to disagree with the authoritative persisted logic it is meant to shortcut.

### Finding Description
In the `!=` branch of the fast in-memory path: [1](#0-0) [2](#0-1) 

The comment explicitly states the intended semantics: `!=` comparisons should only be considered "found" when the query value and the feed value are of the *same comparable type*, because otherwise incomparable values (e.g. `'abc' != 123`) would be wrongly reported as unequal. However, `valueIsNumber()` only inspects the *query* `value`, never `feed_value`. So if the query value looks numeric (e.g. `5`) but the actual `feed_value` stored by the oracle/AA is a non-numeric string (e.g. `"hello"`), the code does `value.toString() !== feed_value.toString()` → `"5" !== "hello"` → `true`, and immediately sets `bFound = true`.

This directly contradicts the authoritative persisted-store implementation, `dataFeedByAddressExists`, which handles `!=` by recursing into `>` and `<` only, and which strictly separates keyspaces by an explicit type prefix (`'n\n'` for numeric, `'s\n'` for string) bounded by `type+'\r'`/`type+'\n'`: [3](#0-2) 

Under this authoritative logic, a numeric-typed query never matches a string-typed feed value, so for the same data (query value `5`, feed value `"hello"`) the persisted path correctly returns "not found" (incomparable ⇒ no match), while the fast path returns "found" (`true`). When `bFound` is `true`, `dataFeedExists()` short-circuits and returns `true` immediately without ever consulting the persisted store: [4](#0-3) 

This fast path is reached only for `data_feed` messages authored by AA response units (`objUnit.bAA`) that are still unstable: [5](#0-4) 

Once the AA's data-feed-posting unit stabilizes, its entry is removed from `storage.assocUnstableMessages` and any subsequent evaluation of the same query would exclusively use the authoritative persisted path: [6](#0-5) 

`in_data_feed` is directly reachable from oscript/AA formulas and from static address-definition conditions: [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker who authors/controls an AA can have that AA post a non-numeric string value via a `data_feed` app response. While that response unit is included in the DAG but not yet MC-stable, any other AA (including one the attacker controls, or a victim AA that queries the attacker's AA as an oracle) that evaluates `in_data_feed[[oracles=<attacker AA>, feed_name=..., feed_value != <number>]]` will get an incorrect `true` result that the protocol's own persisted-store semantics would treat as `false` (incomparable ⇒ not found). Since `in_data_feed`/`in data feed` conditions gate branching logic and fund-release/authentication decisions in AAs and address definitions, this discrepancy lets an attacker force a branch to execute (e.g., release funds, satisfy an authentication condition, or unlock a payout) that should not have been satisfied — a concrete AA fund-loss / logic-bypass vector, consistent in class with the reported bug (an equivalence/identity check that fails to fully resolve type/representation, producing a security-relevant bypass).

### Likelihood Explanation
Exploitation requires the attacker to control (or deploy) an AA acting as the referenced oracle and to time a query against it while its data-feed-posting response unit is still unstable but already included — both are things any user can arrange by design (AAs are permissionless and unstable windows are a normal, frequent occurrence in the DAG). No special network position, hub compromise, or privileged access is needed; a single crafted trigger/AA pair posted by an ordinary unit author is sufficient.

### Recommendation
In the `!=` branch of the fast path, check the type-comparability of both `value` and `feed_value` (mirroring the `>`/`<`/`>=`/`<=` branches' `f_value`/`f_feed_value` null-check logic) before deciding `bFound`, so that mismatched/incomparable types never produce a positive match. Alternatively, remove the special-cased `!=` fast path entirely and implement it, like the persisted path does, purely in terms of the already-correct `>` and `<` handling.

### Proof of Concept
1. Deploy AA `ORACLE_AA` whose response posts `{"data_feed": {"x": "notanumber"}}` when triggered.
2. Deploy AA `VICTIM_AA` whose formula contains `in_data_feed[[oracles=ORACLE_AA_ADDRESS, feed_name='x', feed_value != 5]]` gating a payout.
3. Send a trigger to `ORACLE_AA`, then, before its response unit stabilizes (same DAG wave / while still in `storage.assocUnstableMessages`), send a trigger to `VICTIM_AA` that causes the `in_data_feed` condition to be evaluated.
4. `dataFeedExists` fast path (`data_feeds.js:56-66`) evaluates `valueIsNumber()` on `5` → `true`, then `"5" !== "notanumber"` → `true`, returning `bFound=true`/condition satisfied and triggering the payout branch.
5. Re-run the identical query after `ORACLE_AA`'s response has stabilized (forcing the persisted-store path only): `dataFeedByAddressExists` never finds a numeric-typed match for `feed_value != 5` because `"notanumber"` is stored under the string type prefix, outside the numeric-type key range — the authoritative answer is `false`, proving the two paths diverge on identical underlying data.
