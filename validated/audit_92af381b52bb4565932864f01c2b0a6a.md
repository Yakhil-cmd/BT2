### Title
Same Bitcoin L1 lockup output can be credited to multiple bonds because outpoint de-duplication is call-scoped, not global - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`validate-l1-lockup`/`verify-l1-lockups` in `pox-5.clar` prove that a Bitcoin UTXO exists, is properly time-locked to the staker, and hasn't already appeared *within the same call's list of lockup outputs* — but nothing prevents the exact same on-chain outpoint from being submitted again in a later, separate `register-for-bond` (or similar) call for a different `bond-index`, crediting the same locked sats to two bonds simultaneously.

### Finding Description
`verify-l1-lockups` seeds the fold accumulator with a freshly empty `seen-outpoints: (list)` on every invocation: [1](#0-0) 

`validate-l1-lockup` only checks the outpoint against this call-local `seen-outpoints` list, rejecting duplicates *within the same fold*, but never consults or updates any persisted map keyed by `{txid, output-index}`: [2](#0-1) [3](#0-2) 

No `map-set` anywhere in the surrounding code persists spent/credited outpoints (searches for `spent-outpoints`, `used-lockup`, `credited-outpoints`, `lockup-outpoints` return no hits in `pox-5.clar`). This means the same real Bitcoin lockup transaction output — locked once for a real amount of sats — can be presented as proof for `bond-index A` and later again for `bond-index B` (or for a `stake` call and a bond call), because each call only guards against duplicates it sees in its own list.

### Impact Explanation
This breaks the equality "sats credited by L1 proof == sats actually locked on Bitcoin." Since `verify-l1-lockups`'s returned `sum` feeds directly into `get-total-shares-staked-for-cycle`/`add-staker-to-bond-cycles` (weighting sBTC-denominated stake, signing weight, and reward-per-token accrual), a single BTC lockup could be double-counted across two bonds, inflating that staker's/signer's effective stake and pro-rata claim on `calculate-rewards`'s sBTC reward pool beyond what is actually collateralized. This matches the "double-counting a commitment or reward" Critical-impact category, since it lets a user inflate share weight without locking additional BTC, siphoning rewards away from honest stakers.

### Likelihood Explanation
This requires only unprivileged registration calls with attacker-controlled lockup proof data (`tx`, `header`, `leaf-hashes`, etc., for a real, previously-mined BTC output the staker controls) submitted twice through the normal `register-for-bond`/staking entry points — no admin, miner, or other user's key is needed. The bar is low if the register/stake flow can indeed be invoked more than once referencing the same outpoint, which the code as written does not prevent.

### Recommendation
Persist a global map (e.g., `credited-l1-outpoints: {txid, output-index} -> bool`) that is checked and set atomically the first time an outpoint's sats are credited to any bond/stake, and reject subsequent credit attempts referencing the same outpoint across separate contract calls, not just within a single fold invocation.

### Proof of Concept
1. Staker locks sats S in a single Bitcoin transaction/output `O` to a valid timelock script for their bond.
2. Staker calls the bond/stake registration function once, submitting `O` as a lockup proof for `bond-index=A`; `validate-l1-lockup` succeeds (empty `seen-outpoints` on this call), sats S credited to bond A's stake.
3. Staker calls the registration function again for a different `bond-index=B` (or a different staking path), submitting the same outpoint `O` again. Because `seen-outpoints` is reinitialized to `(list)` for this new call, the duplicate check in `validate-l1-lockup` passes, crediting sats S to bond B as well.
4. The staker now holds `2S` worth of credited stake/reward-weight backed by only `S` sats actually locked on Bitcoin.

Note: I was not able to fully trace every caller of `verify-l1-lockups` (e.g., confirm whether `register-for-bond` itself enforces a one-time-use rule elsewhere not surfaced by search) due to tool-call limits; a full-repo Devin session would be needed to exhaustively confirm no other guard exists before treating this as fully proven in production code.
