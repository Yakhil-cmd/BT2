### Title
Operator precedence bug in `provision?` lets `provisioning_behavior_allow_with_label?`/`prevent_with_label?` bypass a disabled `review_stacks_enabled`, and no downstream check exists before `ReviewStackProvisioningQueue.add` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `review_stacks_enabled` with `provisioning_behavior_allow_all?` using `&&`/`||` without parentheses, so Ruby operator precedence only gates the `allow_all` branch on `review_stacks_enabled`; the `allow_with_label` and `prevent_with_label` branches are unconditionally evaluated regardless of `review_stacks_enabled`. Once `provision?` returns true through either mislabeled branch, `ReviewStackAdapter#find_or_create!` → `create!` unconditionally calls `Shipit::ReviewStackProvisioningQueue.add(stack)` with no second read of `review_stacks_enabled` anywhere between stack creation and the enqueue call.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == true` should be the single gate controlling whether **any** provisioning behavior can enqueue a stack. The actual code is: [1](#0-0) 
Due to `&&` binding tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. If an operator sets `review_stacks_enabled = false` while `provisioning_behavior` is `allow_with_label` or `prevent_with_label` (a state reachable via the repository settings UI, since `review_stacks_enabled` and `provisioning_behavior` are independent columns with no coupled validation in `Shipit::Repository`), `provision?` still returns true whenever the label condition matches.

No code between `scope.create!(stack_attributes)` and `Shipit::ReviewStackProvisioningQueue.add(stack)` re-reads `repository.review_stacks_enabled`; the queue add is unconditional once execution reaches `create!`.

An attacker who can open a pull request on their own repository (already tracked by Shipit with this contradictory configuration) and apply/omit a label per the configured behavior can force stack creation and provisioning enqueue despite the operator's intent to disable review stacks.

### Impact Explanation
The immediate effect is creation of a `Shipit::ReviewStack` record and an unconditional call to `Shipit::ReviewStackProvisioningQueue.add(stack)` (`stack.enqueue_for_provisioning`) for the attacker's own repository/PR, bypassing the operator's `review_stacks_enabled = false` kill switch. This is confined to the same repository/tenant that already has PR-based review-stack tooling configured (`provisioning_behavior` set to a label-based mode); it does not cross tenant boundaries, does not expose credentials, and does not itself constitute RCE — the actual provisioning execution (`ReviewStackProvisioningQueue#work` → `stack.provisioner.provision?` → `stack.provision`) depends on a host-supplied `ProvisioningHandler` subclass, which is outside this engine's code (`Shipit::ProvisioningHandler::Base#provision?`/`#up` are no-ops by default).

### Likelihood Explanation
Requires a specific, unusual operator misconfiguration: `review_stacks_enabled = false` combined with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` — a state that is logically contradictory (operator disabled review stacks but still configured label-based provisioning rules) and not the primary supported configuration path. It is not attacker-controlled; the attacker can only trigger the latent bug once an operator has already created this configuration.

### Recommendation
Fix operator precedence explicitly:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
