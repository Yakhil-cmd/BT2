### Title
Stale `is_free` cache after reverting a branching AA-response tree can desynchronize DAG-tip tracking - (File: aa_composer.js)

### Summary
The CVE describes a class of bug where a data structure is split/mutated but an auxiliary index that tracks membership over that structure is not fully updated for all affected nodes, leaving stale entries that later cause corrupted state. In `ocore`, `aa_composer.js`'s `revertResponsesInCaches()` performs an analogous incomplete update: when an AA-trigger execution (which can fan out into a *tree* of secondary-AA response units, each choosing its own DAG parents) fails and must be rolled back, only the immediate parents of the *first* response unit are used to recompute the `is_free` cache, even though every unit in the whole response tree is forgotten.

### Finding Description
`revert()` in `handleTrigger` calls `revertResponsesInCaches(arrResponses)` to undo in-memory cache mutations after a `ROLLBACK TO SAVEPOINT` (the SQL rollback does not touch the JS-side caches in `storage.js`): [1](#0-0) 

`revertResponsesInCaches` collects **all** response units into `arrResponseUnits`, forgets every one of them via `storage.forgetUnit`, but computes the `parent_units` used to repair the `is_free` flag **only from the first response unit** (`objFirstUnit.parent_units`): [2](#0-1) 

`storage.forgetUnit` correctly removes each forgotten unit from `assocBestChildren[parent]` for *all* of that unit's own real parents (not just the first unit's), because it reads `assocUnstableUnits[unit].parent_units` per-unit before deleting: [3](#0-2) 

However, `fixIsFreeAfterForgettingUnit` — which decides whether a parent should be flipped back to `is_free=1` because it no longer has any children in `assocUnstableUnits` — is only invoked with the parent set of the *root* response unit: [4](#0-3) 

A single AA trigger can spawn a *branching* tree of responses: `handleSecondaryTriggers` iterates over multiple secondary AAs triggered by one unit's outputs, and each secondary trigger independently calls `pickParents()`/`handleParents()`, which can select a **different external parent unit** (or even two external parents via `[row.unit, objMcUnit.unit].sort()`) for each downstream response unit in the tree: [5](#0-4) [6](#0-5) 

Consequently, when the whole tree is reverted, external parents of the *non-root* response units (secondary-AA responses further down the branching tree) are never passed to `fixIsFreeAfterForgettingUnit`. If such an external parent had no other unstable children besides the forgotten secondary response, its `is_free` flag is left stuck at `0` in `assocUnstableUnits`, even though the unit genuinely has no children anymore after the revert (mirroring the CVE's "region split without index update" pattern — the response tree was "split apart" during forgetting, but the auxiliary `is_free` index was only patched for one branch).

### Impact Explanation
`is_free` in `assocUnstableUnits` is consumed by DAG-composition and stability logic across `main_chain.js`, `parent_composer.js`, `graph.js`, and `joint_storage.js` (e.g., selecting free tip units, archiving orphaned bad units, and the `getFreeUnits()`/`checkNotRebuildingStableMainChainAndGoDown` sanity checks). A unit incorrectly stuck at `is_free=0` will never be treated as an eligible free tip for local composition or correctly purged/archived, causing this node's in-memory DAG-tip state to permanently diverge from the true DAG topology after specific AA-trigger failure sequences that produce branching response trees. Because this divergence is silent (no thrown error in the normal path) and persists for the life of the process, it can accumulate over many bounced/reverted branching AA triggers, degrading a node's ability to correctly track free units and potentially contributing to inconsistent local views of DAG state relative to peers that did not process the same trigger locally (light/full node divergence in AA execution paths). This falls into the "node disagreement" / AA-freezing category described in the validation rules, though I could not fully trace a concrete double-spend or fund-loss path within available time — the primary confirmed defect is a memory-cache correctness bug in the `is_free` bookkeeping, not a directly demonstrated fund-loss exploit.

### Likelihood Explanation
Any unprivileged AA trigger sender can construct a scenario that (a) causes a primary AA to call multiple secondary AAs that each pick independent DAG parents, and (b) causes the overall response chain to fail later (e.g., `updateStorageSize` failing, or a downstream secondary bounce), forcing `revert()`/`revertResponsesInCaches()` to run. This requires no special privileges — only crafting an AA (or using an already-deployed one) whose execution branches and later fails, which is a normal, attacker-reachable code path through `handleAATriggers`.

### Recommendation
In `revertResponsesInCaches` (aa_composer.js), collect the `parent_units` of **every** unit in `arrResponseUnits` (before forgetting any of them) rather than only the first unit's parents, and pass the union of all these parent sets to `storage.fixIsFreeAfterForgettingUnit`, so that any external parent that loses its last unstable child during the revert of a branching response tree is correctly re-marked `is_free=1`.

### Proof of Concept
Conceptual reproduction (not verified end-to-end due to tool/time constraints):
1. Deploy a primary AA that, on trigger, sends outputs to two different secondary AAs in the same response unit (fan-out), where `handleSecondaryTriggers` invokes `pickParents()` for each secondary trigger independently, causing each secondary response unit to select a different external best-parent unit (e.g., different `latest_included_mc_index` states across two secondary triggers processed at slightly different times/log states).
2. Make the second secondary AA's response deterministically fail after the response unit has already been `validateAndSaveUnit`-ed (e.g., trigger a `storage_size` overflow or make it bounce with an error condition after some in-memory unit already added to `assocUnstableUnits`).
3. This causes `revert()` → `revertResponsesInCaches(arrResponses)` to run over the whole multi-branch `arrResponses` array.
4. Inspect `storage.assocUnstableUnits[<second_secondary_parent>].is_free` after the revert completes — expect it to remain `0` even though that parent unit has no children left in `assocUnstableUnits`, whereas a correctly-implemened fix (using all response units' parents) would set it to `1`. function revertResponsesInCaches(arrResponses) {
	// remove the rolled back units from caches and correct is_free of their parents if necessary
	console.log('will revert responses ' + JSON.stringify(arrResponses, null, '\t'));
	var arrResponseUnits = [];
	arrResponses.forEach(function (objAAResponse) {
		if (objAAResponse.response_unit)
			arrResponseUnits.push(objAAResponse.response_unit);
	});
	console.log('will revert response units ' + arrResponseUnits.join(', '));
	if (arrResponseUnits.length > 0) {
		var first_unit = arrResponseUnits[0];
		var objFirstUnit = storage.assocUnstableUnits[first_unit];
		var parent_units = objFirstUnit.parent_units;
		arrResponseUnits.forEach(storage.forgetUnit);
		storage.fixIsFreeAfterForgettingUnit(parent_units);
	}
}

// parent_units are parent units of the forgotten unit
function fixIsFreeAfterForgettingUnit(parent_units) {
	parent_units.forEach(function(parent_unit){
		if (!assocUnstableUnits[parent_unit]) // the parent is already stable
			return;
		var bHasChildren = false;
		for (var unit in assocUnstableUnits){
			var o = assocUnstableUnits[unit];
			if (o.parent_units.indexOf(parent_unit) >= 0)
				bHasChildren = true;
		}
		if (!bHasChildren)
			assocUnstableUnits[parent_unit].is_free = 1;
	});
}
