### Title
AA addresses that earn headers commission or witnessing income can never spend it, permanently trapping bytes - (File: validation.js, headers_commission.js, aa_composer.js)

### Summary
An Autonomous Agent (AA) address, like any other address referenced as `unit_authors` of a unit, can be selected as the "winning child" for headers commission distribution, or (in principle) be listed as a unit witness earning witnessing income. These earnings are credited into `headers_commission_outputs` / `witnessing_outputs`, separate ledgers from the `outputs` table that backs `aa_balances`. Because AA logic can only ever spend from `aa_balances`/`outputs`, and the protocol explicitly bans `headers_commission`/`witnessing` input types in AA-authored units, any bytes credited this way to an AA address become permanently unspendable — mirroring the "excess balance trapped forever because the strategy contract can't reach it" bug class from the reference report.

### Finding Description
When a main-chain index stabilizes, `calcHeadersCommissions` distributes header commissions to the `unit_authors.address` of the winning child unit for each parent unit [2](#0-1) , with no special-casing to exclude AA addresses. AA response units are posted with `authors: [{ address: address }]` where `address` is the AA's own address [1](#0-0) , so an AA response unit is a fully valid, "good"-sequence unit that can legitimately win headers commission for MC-index blocks it happens to be a "best child" of. The commission is then written into `headers_commission_outputs`, indexed by `(main_chain_index, address)` [6](#0-5) .

Separately, `aa_balances` — the only balance ledger the oscript `balance[]`/`var[]` operators and the AA payment composer read from — is populated strictly from the `outputs` table (i.e., normal payment/issue outputs), and explicitly does not include `headers_commission_outputs`/`witnessing_outputs` [3](#0-2) . `readAABalances`, used elsewhere to expose an AA's balance, likewise only reads `aa_balances` [7](#0-6) .

Critically, `validatePaymentInputsAndOutputs` explicitly rejects `headers_commission`/`witnessing` input types whenever the validation state is for an AA (`objValidationState.bAA`) [4](#0-3) . Since the AA composer (`aa_composer.js`) only ever builds `payment` messages that spend from `outputs`, via `completePaymentPayload`/`iterateUnspentOutputs`, and never constructs `headers_commission`/`witnessing`-type inputs [8](#0-7) , there is no code path by which an AA can ever spend bytes sitting in `headers_commission_outputs` or `witnessing_outputs` credited to its own address. Once credited, those bytes are permanently stuck — the AA has no `oscript` primitive and the protocol has no validation path to move them into `aa_balances` or out to any other address.

This is directly analogous to the reported bug class: extra value accrues to a "vault"-like contract/address outside of the tracked accounting balance (`poolAmount`/`aa_balances`), and the contract's only withdrawal mechanism (`withdraw()`/AA payment composer) is hard-limited to the tracked balance, leaving the excess permanently locked.

### Impact Explanation
Any bytes earned by an AA address via headers commission or witnessing income become permanently and irrecoverably locked, since:
1. `aa_balances` (the AA's only spendable accounting ledger) never reflects these amounts.
2. AAs are categorically barred by `validation.js` from constructing units with `headers_commission`/`witnessing` input types.
3. No oscript primitive or protocol mechanism exists to sweep `headers_commission_outputs`/`witnessing_outputs` into `aa_balances`.

This constitutes a direct, permanent loss of funds for the AA and its users (since these bytes were paid by real network participants as commissions intended for the winning author, here an AA), fitting a Medium severity "funds trapped forever" classification.

### Likelihood Explanation
The main precondition is that an AA response unit becomes the "winning child" for some parent unit under the headers-commission-distribution algorithm, which is a normal, permissionless, probabilistic outcome of posting to the DAG — AAs post response units continuously and have no way to opt out of being selected as a best-parent's best-child. No malicious actor or special privilege is required; it can happen purely as a side effect of normal AA activity as the network grows. (Witnessing income additionally requires the AA address to be part of the active order-provider/witness list, which is less directly reachable but conceptually suffers the identical bug once triggered.)

### Recommendation
Either:
- Exclude AA addresses from headers-commission/witnessing distribution eligibility in `calcHeadersCommissions`/`paid_witnessing.js` (redirect earnings elsewhere, e.g., burn or the AA's `aa_balances` directly), or
- Extend `aa_balances`/`readAABalances`/`updateInitialAABalances` to also account for `headers_commission_outputs`/`witnessing_outputs` credited to AA addresses, and allow the AA composer to construct `headers_commission`/`witnessing` inputs (removing the `bAA` restriction in `validation.js` for this specific, controlled case) so that AAs can actually redeem these earnings through oscript-driven payments.

### Proof of Concept
1. Deploy an AA and let it respond to a trigger, producing a response unit authored by the AA address (`aa_composer.js` builds `authors: [{ address: address }]`).
2. Arrange (or simply wait, given normal network conditions) for this AA response unit to become the "winning child" of some parent unit under the headers-commission best-child selection algorithm in `headers_commission.js`.
3. Observe `headers_commission_outputs` gains a row for `(main_chain_index, aa_address, amount)`.
4. Observe that `aa_balances` for this AA address is unaffected — `balance[base]` in oscript does not increase.
5. Attempt to have the AA (via any oscript logic) spend or withdraw this amount: there is no `headers_commission` input type available to the AA composer, and even if a hand-crafted unit tried to add one, `validation.js` rejects it with `"headers_commission in AA"` because `objValidationState.bAA` is true for any unit authored by an AA address.
6. Confirm the bytes remain permanently inaccessible — no future oscript execution, `withdraw`-like message, or protocol mechanism can move them into a spendable form for the AA.
