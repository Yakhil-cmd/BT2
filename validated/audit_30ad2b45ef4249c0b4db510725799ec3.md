### Title
Cross-stack CCMenu status leak via unscoped `stack` lookup in `Shipit::Api::CCMenuController#stack` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides both `authenticate_api_client` and `stack`, bypassing the stack-scoping that `Shipit::Api::BaseController` normally enforces for every other API endpoint. As a result, a `token` that a `SimpleMessageVerifier` proves belongs to an `ApiClient` scoped to stack A can be replayed against any other stack B's CCMenu endpoint and will return stack B's build/deploy status.

### Finding Description
The broken binding: `current_api_client.stack_id == stack.id` must hold for a scoped `ApiClient` to read a stack's data. Elsewhere, `BaseController#stack` enforces this: `stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `#stack` resolves `params[:stack_id]` against that relation [1](#0-0) .

`CCMenuController` re-implements both methods and drops the scoping entirely:
```
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [2](#0-1) 

`authenticate_api_client` only verifies the token's signature via `ApiClient.authenticate`, which does `find_by(id: message_verifier.verify(token).to_i)` — it never checks `stack_id` [3](#0-2) . `require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)`, which checks the `permissions` array membership, not stack identity [4](#0-3) . Since `stack` is resolved via the module-level `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!`, any stack id can be supplied regardless of the authenticated client's `stack_id`.

Stack-scoped `ApiClient`s are a real, supported configuration in this codebase (e.g. fixture `here_come_the_walrus` has `stack: shipit` and only `read:stack` permission, used to prove per-stack scoping in `Api::StacksController`) [5](#0-4) , and are exercised by tests asserting `Api::StacksController#index`/`#show` correctly restrict a stack-scoped client to its own stack [6](#0-5) . `CCMenuController` is the one endpoint that does not apply this restriction.

Attacker request: knowing (or having been given, e.g. via the "Fetch URL" CCMenu button on stack A's settings page) a token for a stack-A-scoped `ApiClient` with `read:stack` permission, the attacker sends `GET /api/stacks/B/ccmenu.xml?token=<A's token>` for arbitrary stack B. `authenticate_api_client` accepts the token (it belongs to a real, valid `ApiClient`), `require_permission :read, :stack` passes (the client does have `read:stack`), and `stack` resolves directly to B via `Stack.from_param!`, returning B's `deploys_and_rollbacks.last` status in the XML response.

No existing guard intercepts this: `verify_signature`/webhook checks are irrelevant here; `ExplicitParameters` is not used on this controller; `force_github_authentication` does not apply to `Api::BaseController`-derived controllers (this is the API auth path, not the browser session path); the `stacks` scope exists in `BaseController` but is explicitly not used by `CCMenuController#stack`.

### Impact Explanation
The attacker obtains unauthorized read access to another stack's CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock status) — this is "unauthenticated read of stack state ... deploy output" for a stack the attacker's token was never authorized for, matching the High severity category (unauthorized read of stack state/deploy output). The attack is fully repeatable against any stack id known to the attacker and only requires possession of any valid, permission-bearing token (even one deliberately scoped to a different, unrelated stack). Blast radius spans all stacks hosted by the Shipit instance, since `Stack.from_param!` is unscoped.

### Likelihood Explanation
Preconditions: the attacker needs a valid `ApiClient` token with `read:stack` permission for any stack (e.g. obtained legitimately for stack A via the CCMenu "Fetch URL" feature, or leaked/shared in a CI dashboard config), and knowledge of stack B's slug/id (`owner/repo/branch`), which is often discoverable/public. No GitHub or Shipit secrets are needed, and no privileged role is required — only possession of one valid CCMenu-style token. This is a low-cost, deterministic, repeatable exploit (single unauthenticated GET request per target stack).

### Recommendation
In `Shipit::Api::CCMenuController`, remove the local `stack` override and use the inherited scoped `stack`/`stacks` from `BaseController` (i.e., resolve `params[:stack_id]` via `stacks.from_param!` instead of `Stack.from_param!`), so that a stack-scoped `ApiClient`'s `stack_id` is enforced identically to every other API controller.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token scoped to stack A cannot read stack B's ccmenu status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.create!(owner: 'foo', name: 'barbar'), branch: 'main')

  client_a = ApiClient.create!(
    creator: shipit_users(:walrus), name: 'Scoped To A',
    stack: stack_a, permissions: ['read:stack']
  )

  assert_not_equal client_a.stack_id, stack_b.id # binding under test

  get :show, params: { stack_id: stack_b.to_param, token: client_a.authentication_token }

  assert_response :ok # VULNERABLE: should be :forbidden / :not_found
  project = Hash.from_xml(response.body)['Projects']['Project']
  assert_equal stack_b.to_param, project['name'] # leaked stack B data via a stack-A token
end
```
