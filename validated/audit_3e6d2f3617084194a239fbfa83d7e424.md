### Title
Cross-tenant webhook forgery: signature verified against ORG_A's secret while `repository.full_name` names ORG_B, letting `UnlabeledHandler#archive?` archive ORG_B's `ReviewStack` — ([File: app/models/shipit/webhooks/handlers/pull_request/unlabeled_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret to verify the raw payload against using `repository_owner`, which is read straight out of the untrusted request body (`params.dig('repository','owner','login')`) rather than any value fixed at routing/config time. `UnlabeledHandler` (and its sibling PR handlers) then independently resolves the target `Repository`/`ReviewStack` using a *different* field of the same untrusted body, `params.repository.full_name`. Nothing checks that these two fields refer to the same organization, so a payload correctly signed with ORG_A's webhook secret can carry a `repository.full_name` pointing at ORG_B, and the handler will act on ORG_B's stack.

### Finding Description
Binding claimed: **org whose secret verified the payload (derived from `repository.owner.login`) == org owning the acted-upon repository (derived from `repository.full_name`)**.

- `verify_signature` picks the HMAC secret via `Shipit.github(organization: repository_owner)`, and `repository_owner` is `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')` [1](#0-0) . `Shipit.github_app_config` looks the secret up per-organization from `secrets.github` [2](#0-1) , and `verify_webhook_signature` HMACs the raw body against that org-specific secret [3](#0-2) .
- After signature verification passes, `UnlabeledHandler#repository` resolves the acted-upon `Repository` from `params.repository.full_name` — a completely separate field of the same JSON body, with no relation enforced to `repository.owner.login` used above [4](#0-3) .
- `archive?` then evaluates purely against that repository's `provisioning_behavior_allow_with_label?` / label state and, if true, `stack.archive!` runs against the resolved `ReviewStack` [5](#0-4) .

Exploit flow: an attacker who legitimately controls ORG_A's Shipit-configured GitHub App (i.e., knows or can produce ORG_A's `webhook_secret` — the premise stated in the question as "signing as ORG_A") crafts a JSON body where `repository.owner.login = "org_a"` (so `verify_signature` selects and successfully validates against ORG_A's secret) but `repository.full_name = "org_b/victim-repo"` and `number = <victim PR number>`. `drop_unhandled_event`, `check_if_ping`, and the `ExplicitParameters` schema only check field *types/presence*, not cross-field organizational consistency, so none of them block this. `force_github_authentication`, `User#authorized?`, `require_permission!`, and the `stacks` scope are session/API-token controls that don't apply to the unauthenticated `/webhooks` endpoint at all. The signature check therefore only proves "this body was produced by someone who knows ORG_A's secret," not "the `repository` object inside this body belongs to ORG_A" — and the handler trusts the latter unconditionally.

### Impact Explanation
A single forged, but validly-HMAC-signed (using the attacker's own org's secret), `pull_request`/`unlabeled` webhook causes `Shipit::Repository.from_github_repo_name('org_b/victim-repo')` to resolve ORG_B's real `Repository`, and `stack.archive!` runs against ORG_B's live `ReviewStack`, tearing down a running review environment the attacker has no relationship to. This matches "a payload for one repository mutating another's stack" (Critical). The same broken binding affects every other PR handler that follows this pattern (`ClosedHandler`, `OpenedHandler`, `ReopenedHandler`, `LabelCapturingHandler`, etc.), so the attacker can repeat the technique to archive/unarchive/create stacks or overwrite PR label state for arbitrary victim repositories/stacks as long as they know some organization's webhook secret and that organization is configured in the same Shipit instance.

### Likelihood Explanation
Requires: (1) the attacker's own organization (ORG_A) is registered in this Shipit instance's `secrets.github` multi-org config with the attacker knowing/controlling its `webhook_secret` (plausible if Shipit supports self-service or many-tenant onboarding where org admins configure their own secret) — this is exactly the capability the question stipulates ("signing as ORG_A"); (2) the victim repository (ORG_B) exists in Shipit with `provisioning_behavior: allow_with_label` and review stacks enabled; (3) attacker knows or guesses the victim's open PR number (often public/enumerable). No GitHub session, API token, or team membership is needed — the attacker only needs HTTP access to `POST /webhooks` and knowledge of ORG_A's own secret. Cost is a single crafted HTTP request; fully repeatable against any repository name/PR number.

### Recommendation
After signature verification, re-derive/enforce that the `repository.owner.login` (or `organization.login`) used to select the verifying secret matches the organization segment of `repository.full_name` in the same payload before dispatching to handlers — reject the request (e.g. `head(422)`) on mismatch. Alternatively, resolve the target `Repository` by `(owner.login, full_name)` pair and refuse to act if they diverge, rather than trusting `full_name` alone in each handler.

### Proof of Concept
Minitest plan (webhooks controller / integration test):
```ruby
test "unlabeled webhook signed with org_a's secret cannot archive org_b's stack" do
  # Setup: two orgs in Shipit config with distinct webhook_secret values: org_a, org_b
  victim_repo = shipit_repositories(:org_b_repo) # provisioning_behavior: 'allow_with_label', owner org_b
  victim_stack = create_active_review_stack(repository: victim_repo, pull_request_number: 42)

  body = {
    action: 'unlabeled',
    number: 42,
    pull_request: { id: 1, number: 42, state: 'open', head: { sha: 'abc', ref: 'branch' },
                     user: { login: 'attacker' }, assignees: [], labels: [] }, # no provisioning label
    repository: { full_name: 'org_b/victim-repo', owner: { login: 'org_a' } }, # mismatch!
    sender: { login: 'attacker' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', ORG_A_WEBHOOK_SECRET, body)}"

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = signature

  post :create, body: body, as: :json
  assert_response :ok

  # Binding check: org that verified (org_a) != org owning stack (org_b)
  assert_not_equal 'org_a', victim_repo.owner # org_b
  assert victim_stack.reload.archived?, "org_b's stack was archived by a payload signed only with org_a's secret"
end
```
Expected (buggy) result: `victim_stack.archived?` becomes `true` even though the signature only proves knowledge of `org_a`'s secret, confirming the cross-tenant binding failure.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
