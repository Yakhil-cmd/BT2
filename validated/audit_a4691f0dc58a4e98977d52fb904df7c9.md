Based on the investigation, I found a valid analog in the AA (Autonomous Agent) subsystem: private assets sent to an AA address become permanently, irrecoverably lost — and unlike the Hubble insurance-fund case, there is no possible governance/upgrade path to recover them later, since AAs are immutable smart-contract-like addresses with no owner key.

### Title
Private assets sent to an Autonomous Agent are permanently and unrecoverably lost - (File: `aa_composer.js`)

### Summary
Any unprivileged user (a "private-payment counterparty") who sends a private (`is_private: true`) asset payment to an AA address causes those funds to disappear irrecoverably. The private payment's output is never recorded in the on-chain `outputs` table for a `payload_location: "none"` message (only `spend_proofs` are recorded on-chain), so no full node — including the AA's own processing logic — ever learns that the AA "received" anything, and the AA can never spend the coin. Even if the balance were somehow known, ocore explicitly forbids AAs from sending private assets in their responses.

### Finding Description
For private assets, the payment message uses `payload_location: "none"` and only a `spend_proofs` array is included inline; the actual `outputs` (address, amount, blinding) are transmitted off-chain only to the immediate chain of private-payment participants [1](#0-0) . Since an AA is not a device/wallet capable of participating in private-chain forwarding, it never receives (and no witness/full node stores) the actual output row corresponding to this payment.

Consistent with this, `aa_composer.js`'s trigger-construction logic (`getTrigger`) derives `trigger.outputs` purely from `message.payload.outputs`, which is only populated for inline (public) payment messages [2](#0-1) . A private payment carries no visible payload, so it cannot even trigger or credit the AA.

The AA balance bookkeeping in `storage.js` explicitly excludes private outputs when computing `aa_balances` (`AND (is_private=0 OR is_private IS NULL)`), confirming that private-asset receipts are never credited to an AA's spendable balance [3](#0-2) .

Finally, even in the hypothetical case where an AA did hold a private-asset balance, `aa_composer.js` explicitly refuses to let the AA send it out: `if (objAsset.is_private) return cb("sending private asset from AA");` [4](#0-3) . This is a hard, permanent restriction, not a temporary limitation — there is no sweep/withdraw mechanism, and AA definitions are immutable (unlike Hubble's upgradeable `InsuranceFund` contract that the judge in the referenced report relied on to downgrade severity).

### Impact Explanation
Any user attempting to pay a private/custom asset to an AA loses those funds permanently and unrecoverably. Unlike the referenced Hubble finding — where the contract is upgradeable and governance can eventually sweep the tokens out — ocore AAs have no owner, no upgrade path, and no way for anyone (not even the AA's author or witnesses) to retrieve or reissue the trapped value. This constitutes a permanent fund loss for the sender with no corresponding credit anywhere in the system, satisfying the "AA fund loss or freezing" impact criteria at Medium-to-High severity.

### Likelihood Explanation
This is trivially reachable by any single unprivileged private-payment counterparty simply by composing a private-asset payment (`divisible_asset.js` / `indivisible_asset.js`) with `to_address` set to any known AA address. No special privileges, race conditions, or malicious peers/nodes are required — it is a direct consequence of normal wallet/composer behavior interacting with AA semantics.

### Recommendation
- Reject (at validation time) any private-asset payment output whose destination address is a registered AA address, returning a clear validation error to the sender before funds are irrecoverably spent.
- Alternatively, extend AA definitions to support a defined recovery/sweep mechanism for such stranded balances, analogous to the mitigation recommended in the referenced report, though full prevention via validation is preferable given AAs have no owner to perform a sweep.

### Proof of Concept
1. Deploy any AA with a valid definition.
2. From a wallet, compose a private-asset (`is_private: true`) divisible or indivisible asset payment via `composer.js`/`divisible_asset.js` with `to_address` set to the AA's address.
3. Broadcast the unit; it validates and stabilizes normally (spend proofs check out).
4. Observe: the AA is never triggered by this payment (no `payload.outputs` visible to `getTrigger`), `aa_balances` for the AA never reflects the asset (per the `is_private=0 OR is_private IS NULL` filter in `storage.js`), and even in a hypothetical direct credit, `aa_composer.js` would reject any attempt by the AA to send that asset back out ("sending private asset from AA").
5. The asset is permanently and unrecoverably lost, with no governance or upgrade path to reclaim it.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
