### Title
Missing cross-path serialization when un-uniquing double-spent inputs allows a stable-output double-spend - ([File: validation.js])

### Summary
`checkInputDoubleSpend()` in `validation.js` marks the `is_unique` flag of a conflicting, not-yet-stable competing input as `NULL` whenever a new unit is accepted that double-spends the same source output. For assets flagged `is_private`, this "un-uniquing" write is wrapped in `mutex.lock(["private_write"], ...)` before the `UPDATE inputs SET is_unique=NULL ...` query is executed immediately [1](#0-0) . For every other case (public/base assets, and non-private divisible/indivisible assets) the same kind of update is instead queued into `objValidationState.arrAdditionalQueries` and executed later during unit save, with no dedicated lock at all [2](#0-1) .

### Finding Description
The `inputs.is_unique` column is the mechanism that enforces "no double spend" at the DB level (see the `UNIQUE KEY bySrcOutput(src_unit, ..., is_unique)` constraint) [3](#0-2) . Whenever a newly-validated unit is found to conflict with an existing not-yet-stable input, ocore must atomically "uninstall" the uniqueness of the losing (older) input so that the constraint doesn't block insertion of the winning one, then let sequence resolution at stabilization time (`markMcIndexStable`) decide which one is `good`/`final-bad` [4](#0-3) .

This installation/removal of uniqueness is guarded by two entirely different, non-overlapping synchronization domains:
- The top-level `validate()` function serializes all validation and its side effects per set of author addresses via `mutex.lock(arrAuthorAddresses, ...)` [5](#0-4) .
- The private-asset branch of `checkInputDoubleSpend()` additionally serializes only against itself using a completely separate, global key `"private_write"` [6](#0-5) . A repository-wide search shows this is the *only* place `"private_write"` is used as a lock key, i.e. no other code path (in particular the ordinary per-author-address validation path) ever waits on it.

Because the `"private_write"` lock and the `arrAuthorAddresses` lock are disjoint lock domains that both read-then-write the same `inputs` rows (same `unit`, `address`, `asset`), a private-asset double-spend resolution and a concurrent public/base-asset (or another private-asset) validation touching the same conflicting input can interleave: one path can read the pre-image of `is_unique` while the other is mid-update, or both can decide independently that they are the sole "winner," each un-uniquing the same competitor and each internally believing it is now the exclusive successor. This mirrors the XSA-428/CVE-2022-42334 pattern precisely: installation and removal of an access-control-relevant record (there, pinned cache regions; here, the uniqueness record backing double-spend prevention) is not serialized across all code paths that can install/remove it, only within one of them.

### Impact Explanation
If two conflicting spends of the same not-yet-stable output are processed through these two different lock domains at the same time, the `is_unique` un-marking and the subsequent `arrDoubleSpendInputs`/sequence bookkeping in `objValidationState` can diverge between the interleaved executions, letting both units be accepted with `sequence='good'` locally, or letting nodes disagree on which unit is final-bad. Since sequence and stability determine which spend of a shared output is ultimately confirmed, this can lead to node disagreement on validity/stability and, in the worst case, both conflicting spends being propagated as serial, which is a double-spend of value pending stabilization.

### Likelihood Explanation
Reachable by an ordinary (non-privileged) unit poster: any private-asset holder or private-payment counterparty who submits a private payment chain in parallel with a conflicting public spend from the same address exercises exactly this code path, since `is_private` assets are attacker/user controlled and validation of private payments (`divisible_asset.js` / `indivisible_asset.js` `validateAndSave...PrivatePayment[Chain]`) reaches `checkInputDoubleSpend` with `objAsset.is_private` true [7](#0-6) . No hub/peer/network privilege is required — a wallet user racing two conflicting transactions (one private, one not, or two units validated via different entry points) is sufficient to trigger the race window.

### Recommendation
Serialize all installation/removal of `is_unique` for a given `(asset, denomination, serial_number/src_unit, address)` tuple through a single, consistent lock domain that is always held for the full duration from read to write — e.g. always route the update through the same `arrAuthorAddresses`-based lock (or fold `"private_write"` handling into that same lock acquisition) rather than using an independent `"private_write"` key that other double-spend-resolution paths never wait on.

### Proof of Concept
1. Address `A` owns an unspent, not-yet-stable output of a private asset `X` with `spender_attested`/`is_private=true`.
2. Compose and submit unit `U1`, a private payment from `A` spending that output, driving execution into `checkInputDoubleSpend` → the `mutex.lock(["private_write"], ...)` branch in `validation.js` [6](#0-5) .
3. Concurrently (same real-time window, before `U1`'s lock releases), submit unit `U2` from address `A` spending a competing public output whose conflict-check path only takes `mutex.lock(arrAuthorAddresses, ...)` at the top of `validate()` [5](#0-4) ; because `"private_write"` and the address-array lock never intersect, `U2`'s validation can proceed to also un-unique the same conflicting record concurrently with `U1`.
4. Observe both `U1` and `U2` complete validation with `sequence='good'` and get written by `writer.saveJoint`, producing two accepted spends of the same conflicting output rather than one being marked `temp-bad`/`final-bad` as intended.
