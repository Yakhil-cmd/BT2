## Title
Signature Malleability in `verifyMessageWithSecp256k1PemPubKey` Enables Replay of AA `is_valid_sig` Authorizations - (File: `signature.js`)

## Summary
The reported bug class (ECDSA signature malleability defeating "signature has been used" replay protection) has a concrete analog in `ocore`'s oscript/AA signature-verification path. The `is_valid_sig()` oscript function, reachable by any AA trigger sender, delegates to `signature.verifyMessageWithSecp256k1PemPubKey()`, which explicitly re-encodes and *normalizes* the supplied signature bytes before verifying them. This means multiple distinct byte-strings (the value an AA author would naturally use as the "already used" key to prevent replay) can all verify successfully for the same message/key pair, exactly mirroring the OpenZeppelin `ECDSA.recover`/EIP-2098 malleability class described in the external report.

## Finding Description
`is_valid_sig` is implemented in `formula/evaluation.js` and is directly reachable from AA trigger data (an unprivileged trigger sender fully controls `message`, `pem_key`, and `sig`): [1](#0-0) 

It calls `signature.verifyMessageWithPemPubKey`, which for secp256k1 PEM keys post-fix dispatches to `verifyMessageWithSecp256k1PemPubKey`: [2](#0-1) 

That function is where the malleability is introduced. It accepts the signature in either hex or base64 encoding, decodes it, and — critically — imports (`ecdsa.signatureImport`) and then **normalizes** it (`ecdsa.signatureNormalize`) before calling `ecdsaVerify`: [3](#0-2) 

This is functionally the same defect class as the OpenZeppelin advisory: the verification function accepts more than one canonical byte-representation of "the same" valid signature (e.g., a non-lower-S signature, or an alternate valid DER encoding that decodes to the same `(r, s)`), and still returns `true`. In `formula/evaluation.js`, the raw string `evaluated_signature` (as passed in the trigger, un-normalized) is what would naturally be checked/stored by an AA author to prevent replay of a one-time authorization — the same `_salt`-style anti-replay pattern flagged in the original report. Because `evaluated_signature` is never canonicalized before it reaches the AA's own storage/comparison logic, and because `verifyMessageWithSecp256k1PemPubKey` will happily validate several distinct raw encodings of the same underlying signature, an attacker can resubmit a *previously seen, already-consumed* signature in an alternate but still-valid byte form and have `is_valid_sig` return `true` a second time.

By contrast, ocore's native unit-signing path (`signature.js` `verify`, used in `definition.js` `validateAuthentifiers` for the `sig` definition op) uses the fixed 64-byte compact `ecdsaVerify` directly without any import/normalize step, so it does not exhibit this specific malleability: [4](#0-3) [5](#0-4) 
That confirms the malleable code path is isolated to the PEM/secp256k1 signature verification used by oscript's `is_valid_sig`.

## Impact Explanation
AAs are documented/expected to use `is_valid_sig` as an off-chain/cross-chain authorization primitive (e.g., allowing a user to authorize a payout, claim, or order execution by presenting a signature over some message, with the AA recording the signature to block reuse) — this is analogous to the `whitelistMint`/`claimPreSale`/`FCFSMint` `_salt`-based anti-replay pattern in the original report, and matches usage seen in AA sample contracts such as `test/samples/order_book_exchange.oscript` and `test/samples/payment_channels.oscript` that exercise `is_valid_sig`-style replay/nonce checks. If an AA stores the literal signature string as its replay-prevention key, an attacker who has previously used (or observed) a valid signature can re-submit a malleable variant of it and have `is_valid_sig` re-validate it as "new," causing the AA to execute its authorized logic more than once. Depending on the AA's design this can produce unauthorized double payouts/double-spends of AA-held funds, duplicate claims, or state corruption — a concrete AA fund-loss scenario.

## Likelihood Explanation
Exploitability requires only a single AA trigger unit crafted by an unprivileged sender; no special network position, hub/node compromise, or leaked keys are needed — the attacker only needs to know one previously-valid signature (which by design is often disclosed once it's used, exactly as flagged in the original report re: "if a malicious actor sees the signature ... they could resubmit it"). The likelihood is directly tied to how many AA authors rely on `is_valid_sig`'s output string as a replay-prevention key, which the codebase's own PEM/secp256k1 signature samples and design (an authorization function specifically intended for salt/nonce-based one-time proofs) show is an anticipated usage pattern.

## Recommendation
Canonicalize the signature before it is used as a comparison/storage key, and reject non-canonical encodings during verification rather than silently normalizing them:
- In `verifyMessageWithSecp256k1PemPubKey` (`signature.js`), reject signatures whose raw bytes are not already in canonical low-S / minimal-DER form instead of calling `ecdsa.signatureNormalize`, or
- If normalization must be kept for compatibility, have `formula/evaluation.js`'s `is_valid_sig` return/expose the *normalized* canonical signature (or a canonical hash of it) rather than the raw attacker-supplied string, so AA-side "used signature" bookkeeping cannot be bypassed by re-encoding.

## Proof of Concept
1. An AA is written to authorize a one-time claim via `is_valid_sig(message, pem_key, signature)` and stores the exact `signature` string in AA state (`var['used_' || signature]`) to prevent replay — mirroring the anti-replay pattern from the external report.
2. A legitimate user submits a trigger with a valid `signature` S1 over `message`; the AA validates it via `is_valid_sig`, marks `used_S1 = 1`, and pays out.
3. An attacker takes the same underlying `(r, s)` pair and re-encodes it as an alternate valid byte-string S2 (e.g., a non-lower-S variant, or a different valid DER encoding), which decodes/normalizes to the same signature inside `verifyMessageWithSecp256k1PemPubKey` (`signature.js:50-70`).
4. The attacker submits a new trigger with `signature = S2`. `is_valid_sig` re-validates successfully (since `ecdsaVerify` is called on the normalized signature), but the AA's `used_S2` state key was never set, so its replay check passes and the payout logic executes again. [3](#0-2) [1](#0-0)

function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();

	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}

function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;

		var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
		var sigBytes = Buffer.from(signature, encoding);
		var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
		var compactSig = Buffer.from(ecdsa.signatureNormalize(rawCompact));

		var msgBuf = Buffer.isBuffer(message) ? message : Buffer.from(message);
		var hash = crypto.createHash('sha256').update(msgBuf).digest();
		return ecdsa.ecdsaVerify(compactSig, hash, pubkey);
	} catch(e) {
		console.log('secp256k1 pem verify exception: ' + e);
		return false;
	}
}
