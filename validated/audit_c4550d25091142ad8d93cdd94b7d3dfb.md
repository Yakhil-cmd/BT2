Based on my investigation, I found a genuine analog in `WebhooksController`.

### Title
Webhook signature verified against attacker-controlled organization key that differs from the repository whose data is written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App / organization config (and thus which `webhook_secret`) to use for HMAC verification based on a value taken directly from the unauthenticated request body, before the signature over that body has been checked. In a multi-organization deployment (`Shipit.github_organizations` / `github_app_config`), this creates a binding mismatch: the "organization authenticated" (the config picked to verify) is not cryptographically tied to the "organization/repository actually written" by the handlers that subsequently run on the same payload.

### Finding Description
`verify_signature` computes `repository_owner` straight from the raw JSON body — `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  — and uses it to fetch the app config: `Shipit.github(organization: repository_owner)` [2](#0-1) . This app instance's `webhook_secret` is then used to HMAC-verify `request.raw_post` [3](#0-2) .

`Shipit.github` resolves configuration through `github_app_config`, which downcases the organization key looked up in `secrets.github` [4](#0-3) . Because any attacker can submit a payload with an arbitrary `repository.owner.login`/`organization.login` value, they fully control which organization's secret is used to verify the signature they also fully control (they can simply craft a valid signature using an org whose secret they know, e.g. by owning a repo under a low-trust org that is nonetheless configured in the same Shipit instance).

Once `verify_signature` passes (i.e., `verified` is truthy for *some* organization's secret), the `create` action re-parses the *same* raw body and dispatches it unconditionally to `Shipit::Webhooks.for_event(event)` handlers [5](#0-4) . Those handlers derive the actually-affected repository independently, via `payload.dig('repository', 'full_name')` in `Handler#repository_name` [6](#0-5) , or `params.organization.login` in `MembershipHandler#find_or_create_team!` [7](#0-6) . Nothing enforces that the "owner" field used to select the verifying secret is the same value the handler later trusts for writes — the controller only checks that *a* secret it looked up validates the body, not that the org whose secret validated it is the org whose resources are mutated.

Concretely, the equality that must hold for this trust boundary to be safe is:
`organization_used_to_select_secret(repository_owner from payload) == organization_whose_secret_actually_signed_this_request (GitHub's real signer for the named repository)`

but the controller never independently proves the right-hand side — it merely trusts whatever `repository_owner` string the attacker put in the JSON body to pick the verification key, then also trusts that same untrusted body for the write. If an attacker controls (or compromises) the `webhook_secret` for **any one** organization onboarded to a multi-tenant Shipit instance (e.g. because they were themselves granted a low-privilege org for their own repos, and can see/reuses that secret from their own GitHub App webhook deliveries), they can forge a payload claiming `repository.full_name` = `SomeOtherHighTrustOrg/critical-repo`, sign it with their own org's known secret, and set the login fields to make `repository_owner` resolve to their own org for verification while `repository.full_name`/`organization.login` (used by the handler) points at the victim repository — because the controller's org selection and the handler's org/repo trust extraction read from *different independent fields of the same unauthenticated JSON*, they are not forced to agree, and GitHub itself never validated this cross-org combination.

This directly instantiates the report's underlying bug class ("a value the code trusts but which is not itself bound by verification") applied here as: the organization authenticated (secret-lookup key) vs. the repository/organization actually written (handler's own field read from the same untrusted body).

### Impact Explanation
A successful forgery lets an attacker trigger `GithubSyncJob` (push), create/delete `Membership`/`Team` records, or post commit `Status`/`check_suite` state for a repository/organization they do not own, as long as they can obtain or guess the `webhook_secret` of *any* organization configured on the same multi-tenant Shipit instance. This crosses the "cross-repository writes" / "escalation into `Shipit.github_teams` authorization" impact bar (e.g., `membership` events can add a user to a `Team` that gates deploy authorization via `User#authorized?` and `Shipit.github_teams`) [8](#0-7) .

### Likelihood Explanation
Exploitability requires the deployment to be configured with multiple organizations (the `secrets.github` multi-org schema, per `github_app_config`) and requires the attacker to know or obtain one org's `webhook_secret` — which is plausible for a self-service or federated Shipit setup where different orgs' admins each hold their own app secret but share the Shipit instance. This is a real but conditionally-scoped likelihood, not a trivial unauthenticated-everywhere bypass.

### Recommendation
After selecting the organization used to look up the verification secret, re-derive and cross-check that the same organization/repository identity is what the handler will act on before dispatching — i.e., verify that `repository.owner.login`/`organization.login` used for secret selection is authoritative and cannot diverge from the identity used by `Handler#repository_name`/`MembershipHandler`. Prefer verifying with a single, deployment-wide default secret unless multi-tenancy is explicitly required, and if multi-tenant, ensure repository/org resolution used for signature verification is the exact same resolved `Repository`/`Stack` record consumed by the handler, not a re-parsed raw field.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `LowTrustOrg` (attacker knows its `webhook_secret`) and `HighTrustOrg` (victim).
2. Attacker crafts a JSON payload for event `push` with `repository.full_name = "HighTrustOrg/critical-repo"` but `repository.owner.login = "LowTrustOrg"`.
3. Attacker signs `request.raw_post` with `LowTrustOrg`'s known `webhook_secret` using the same HMAC scheme as `Hook::DeliverySigner`/`verify_webhook_signature` and sets `X-Hub-Signature` accordingly.
4. `verify_signature` calls `Shipit.github(organization: "LowTrustOrg")` (from `repository_owner`), verifies successfully against the attacker-known secret [9](#0-8) .
5. `create` dispatches the same payload to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("HighTrustOrg/critical-repo")` [10](#0-9)  and enqueues `GithubSyncJob` for the victim's stack, despite the request never being signed by `HighTrustOrg`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
