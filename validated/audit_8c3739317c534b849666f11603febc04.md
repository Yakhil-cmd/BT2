### Title
Cross-organization webhook forgery via `repository_owner`/`repository.full_name` mismatch in signature verification - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization Shipit deployments (one `webhook_secret` per GitHub organization), the field used to select **which** organization's secret verifies a webhook's HMAC signature (`repository.owner.login`) is a different, independently attacker-controlled field from the one used to decide **which repository/stack** the webhook payload acts on (`repository.full_name`). Because the whole raw body is still "validly signed" as long as the attacker knows *any one* onboarded organization's `webhook_secret`, that attacker can forge events that update or drive actions on stacks belonging to any *other* organization configured on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to check the signature against using a payload field, not a value tied to the actual repository being acted on: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization configuration (`webhook_secret`, etc.) from `secrets.github`, a schema explicitly documented and supported for "configuring multiple Github applications for different Github organizations": [3](#0-2) [4](#0-3) 

Once the signature passes, event handlers resolve the actual `Repository`/`Stack` from a *separate* JSON field, `repository.full_name`, with no cross-check that this repo belongs to the same organization whose secret validated the signature: [5](#0-4) [6](#0-5) 

Since the HMAC only proves "the sender knows organization A's `webhook_secret`", and both `repository.owner.login` and `repository.full_name` are ordinary attacker-controlled JSON fields inside the same signed body, an attacker who legitimately administers (or has otherwise obtained the webhook secret for) organization A's GitHub App can craft a payload where:
- `repository.owner.login = "org-a"` (so `verify_signature` selects and validates against org A's secret, which the attacker knows), while
- `repository.full_name = "org-b/victim-repo"` (a repository actually owned by a different, unrelated organization B also configured on the same Shipit instance).

This breaks the trust binding **organization that authenticated == repository that is written**, matching the analog class from the report: a field (the acting-repository) is consumed by downstream logic yet is never bound to the identity that the signature actually verified.

Concretely reachable, in-scope handlers that act purely on `repository.full_name` (no other authorization check) include:
- `PushHandler#process`, which enqueues `stack.sync_github(expected_head_sha:)` for stacks resolved from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`: [7](#0-6) 
- `StatusHandler#process`, which writes a `Status` record for any `Commit` matching `params.sha` — commit statuses are used by Shipit to gate whether a commit is deployable: [8](#0-7) 
- `PullRequest::ClosedHandler#process`, which resolves `Repository.from_github_repo_name(params.repository.full_name)` and calls `review_stack.archive!`: [9](#0-8) 

### Impact Explanation
This lets an attacker who controls one organization's webhook secret manipulate the deploy-relevant state (commit statuses / deployable status, git sync, review-stack lifecycle) of stacks belonging to a completely different organization hosted on the same Shipit instance, without any GitHub write access to that victim repository. Since Shipit's `Status`/`deployable_status` pipeline determines whether a commit can be deployed, and `sync_github` pulls and records commits with attacker-chosen SHAs for another org's repo, this can enable an unauthorized deploy path or corrupt another organization's stack state — a cross-repository/cross-organization write performed under a security boundary (`webhook_secret` per organization) that the code fails to enforce consistently between the field it authenticates and the field it acts on.

### Likelihood Explanation
Requires the attacker to know one onboarded organization's `webhook_secret` (obtainable if they administer that org's GitHub App, or if that one org's secret otherwise leaks) — this is exactly the credential this engine treats as the security boundary between organizations in its documented multi-org configuration. No GitHub write access to the victim repository, no Shipit session, and no `ApiClient` token are needed, only crafting a raw HTTP POST with a valid HMAC computed from the known secret and a payload whose `repository.owner.login`/`organization.login` differs from `repository.full_name`'s owner.

### Recommendation
In `WebhooksController`, after verifying the signature, re-derive the acting repository/organization strictly from the same field used to select the verifying secret (or vice-versa), and reject the webhook (422) if `repository.full_name`'s owner does not case-insensitively match `repository_owner`/`organization.login`. Apply the same consistency check inside `Handler#repository_name` / `Repository.from_github_repo_name` so that no handler can be reached with a `full_name` belonging to an organization other than the one whose secret validated the request.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `config/secrets.development.example.yml` multi-org schema), both with existing stacks.
2. As an administrator/holder of `org-a`'s GitHub App webhook secret, craft a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac_sha1(org-a_webhook_secret, raw_body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner == "org-a"`, verifies successfully against `org-a`'s secret.
5. `PushHandler#process` resolves the stack via `Repository.from_github_repo_name("org-b/victim-repo")` — a repository belonging to organization `org-b` — and enqueues `stack.sync_github(expected_head_sha: "deadbeef")`, an action that should only be triggerable by GitHub webhooks authenticated with `org-b`'s own secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
