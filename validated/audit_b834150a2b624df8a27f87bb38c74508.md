### Title
Cross-organization commit-status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub webhook only against the organization/App derived from the payload's own `repository.owner.login` (or `organization.login`), then hands the *entire raw JSON* to whichever handler is registered for the event. `StatusHandler`, unlike every other handler in the same module, never re-derives or checks the repository the status belongs to — it looks up affected commits with a completely unscoped `Commit.where(sha: params.sha)`, which spans every stack/repository/organization in the Shipit installation. The organization whose signature was verified is therefore never the same entity bound to the records that get written.

### Finding Description
`Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) picks the GitHub App/secret to validate the HMAC against using: [1](#0-0) 
and derives that organization purely from attacker-supplied payload fields: [2](#0-1) 

This authenticates *that the sender genuinely controls org X*, nothing more — the signature covers the raw payload bytes, but it does not restrict *which repository's data* the payload is allowed to mutate. `Shipit::Webhooks::Handlers::Handler` (the base class most handlers use) correctly re-derives the target repository from the same payload and scopes all writes to that repository's stacks: [3](#0-2) 
`PushHandler` and `CheckSuiteHandler` both use this `stacks` scope, so a signed webhook from org X can only ever touch stacks belonging to org X's repository: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, does not inherit the repository scoping and instead queries the `Commit` table globally by SHA alone: [6](#0-5) 

`Commit#sha` is unique only per `(sha, stack_id)` pair, not globally: [7](#0-6) 

Because git commit SHA-1 identifiers are computed from commit content (tree, parents, author/committer, message) and are independent of which GitHub organization/repository hosts them, identical commits pushed to two different repositories (a fork, a mirror, a repo migrated between orgs, etc.) will have identical SHAs. Any organization legitimately connected to this Shipit instance can therefore forge a `status` webhook — correctly signed with *its own* legitimate webhook secret — carrying an arbitrary `sha` value that happens to also exist as a commit in a completely different stack owned by a different organization. `StatusHandler` will apply the forged CI status to every matching commit across the whole installation.

**Binding broken:** `organization that authenticated == repository that is written` is violated — the authenticated party is org X (whoever's secret validated the HMAC), but the write target is any `Commit` row in the database whose SHA matches, regardless of stack/repository/organization ownership.

### Impact Explanation
Commit statuses recorded this way feed directly into deploy/merge gating logic:
- `Commit#deployable?`/CI state, checked before automated deploys.
- `MergeRequest#all_status_checks_passed?` / `any_status_checks_missing?`, which use `StatusChecker` to gate the merge queue's `merge!` call and `ProcessMergeRequestsJob`'s automatic merges.
- `schedule_continuous_delivery` is triggered `after_commit` and continuous-delivery jobs can fire deploys once required statuses are satisfied.

An attacker who only has legitimate GitHub App access to their own (unrelated) organization can forge a passing CI status for a commit shared with (or coincidentally colliding with, though practically achieved via forks/mirrors) a victim stack in a different organization, potentially unblocking an automatic merge or deploy that the victim organization never actually approved via its own CI. This falls under "unauthorized deploy, rollback or merge" / cross-repository writes.

### Likelihood Explanation
The only barrier is possessing a legitimate GitHub App/organization already onboarded onto the same Shipit instance (a routine, low-privilege situation for any org using the shared installation, e.g. a customer's own low-trust fork/mirror repo) and being able to reference a commit SHA that also exists in the target stack — trivially achievable by forking the target repository (fork commits keep identical SHAs) and posting a real `status` event through GitHub for that fork. No Shipit session, API token, or webhook secret of the *victim* org is ever needed; the attacker's own org's real, valid webhook signature is sufficient because `StatusHandler` never checks it belongs to the correct repository.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: resolve commits through `stacks.joins(...).where(sha: ...)` (i.e., restrict to commits belonging to stacks under the repository derived from the payload), instead of the bare, cross-tenant `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Attacker legitimately owns/administers GitHub organization `evil-org`, which has a Shipit App installation with its own valid `webhook_secret` (this is a normal, low-privilege situation, not a Shipit account/API token).
2. Attacker forks victim's public repository `victim-org/app` into `evil-org/app`. The fork shares identical commit objects/SHAs with the upstream repo (e.g. `abcd1234...`), which is also tracked by a Shipit stack `victim-org/app/production`.
3. Attacker uses the GitHub REST API to create a commit status on `evil-org/app` for SHA `abcd1234...` with `state: success`, `context: <required CI context>`.
4. GitHub sends a `status` webhook to Shipit, correctly HMAC-signed with `evil-org`'s legitimate webhook secret. `repository.owner.login == "evil-org"`, so `verify_signature` succeeds using `Shipit.github(organization: "evil-org")`.
5. `StatusHandler#process` executes `Commit.where(sha: "abcd1234...")`, which matches the commit belonging to `victim-org/app/production`'s stack (unrelated to `evil-org`), and records the forged `success` status on it via `commit.create_status_from_github!(params)`.
6. If that context was required by `victim-org/app/production`'s merge queue or continuous-delivery gating, the forged status can help satisfy `all_status_checks_passed?`/`deployable?`, contributing to an unauthorized merge or deploy on a stack the attacker has no legitimate access to.
