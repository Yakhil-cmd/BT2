### Title
Cross-organization webhook forgery via mismatched authentication/authorization fields lets an unprivileged attacker impersonate any tracked GitHub repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a request against using `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body, while every `Webhooks::Handlers::Handler` subsequently resolves the actual `Repository`/`Stack` to act on using a **different** field of the very same unverified body: `repository.full_name`. Nothing binds these two fields together before the signature check runs, so the organization whose credentials authenticate the request and the repository that is actually written to can be made to diverge.

### Finding Description
The webhook signature check is: [1](#0-0) 

`repository_owner` is read straight out of the JSON body before any cryptographic check: [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially returns `true` whenever the resolved organization's configuration has no `webhook_secret` set: [3](#0-2) 

Meanwhile, every handler that actually performs writes derives the target repository from a **different** key of the same attacker-supplied body: [4](#0-3) 

and dispatch happens unconditionally after `verify_signature` passes: [5](#0-4) 

Because Shipit explicitly supports multiple GitHub Apps keyed by organization name, with each org independently configuring (or omitting) its own `webhook_secret`: [6](#0-5) [7](#0-6) 

an attacker only needs to know (or guess) that **any one** configured organization in the instance has a blank `webhook_secret` (a state the engine's own example configs treat as normal/default: `webhook_secret: # nil`) to forge signatures for events targeting a completely different, unrelated, properly-secured repository owned by a different organization: [8](#0-7) 

The bug is a binding violation of the exact class called out in the rules: *"an organization that authenticated versus the repository that is written."* The verification path authenticates as org `A` (whose secret is blank), while the write path (via `PushHandler`, `StatusHandler`, `MembershipHandler`, etc.) acts on repository `B/repo`, which is a different org/repository entirely, e.g.: [9](#0-8) [10](#0-9) 

`StatusHandler` writes forged commit statuses directly into `Commit#create_status_from_github!`, which factor into deployability/CI-gating logic (`Shipit::Status::Group`, `Commit#deployable?` machinery referenced in `app/models/shipit/commit.rb`), and `PushHandler` triggers `Stack#sync_github`, which for stacks with `continuous_deployment: true` can lead to an automatic, unauthorized deploy of attacker-influenced state.

### Impact Explanation
This crosses a credential/authentication boundary without any Shipit session, API token, or knowledge of the target organization's real secret: the attacker only needs a *different, unrelated* org in the same instance to have no webhook secret configured. The result is forged GitHub events accepted as authentic for a **victim repository/stack**, enabling: injection of fake commit statuses that satisfy `ci.require` checks and unlock otherwise CI-blocked commits for deploy (unauthorized deploy), forced `sync_github` calls that can trigger continuous deployment, and fabricated team membership changes via `MembershipHandler` that can alter `Shipit.github_teams` authorization decisions. This matches the Critical ("unauthorized deploy") and High ("escalation into `Shipit.github_teams` authorization") impact bands.

### Likelihood Explanation
Requires only: (1) the target Shipit instance be configured with more than one GitHub App/organization (a documented, supported configuration), and (2) at least one configured organization having an unset `webhook_secret` (a state the shipped example configs present as the default/acceptable value). No credentials, tokens, or session are needed — the webhook endpoint is unauthenticated by design. The main variable is discovering which org (if any) lacks a secret, which is plausible in real deployments where teams onboard additional organizations incrementally.

### Recommendation
Bind authentication and authorization to the same field: derive the repository/organization used for both signature verification and event dispatch from a single, consistent source (e.g., always `repository.full_name`, and refuse to select a GitHub App by an org name that doesn't match the owner segment of `full_name`). Additionally, treat a missing/blank `webhook_secret` for a configured organization as a hard failure (reject the webhook) rather than an implicit "verification passed" (`return true unless webhook_secret` in `lib/shipit/github_app.rb`), since it currently converts absence of configuration into an authentication bypass.

### Proof of Concept
1. Instance is configured with GitHub Apps for `OrgA` (no `webhook_secret` set) and `OrgB` (repository `OrgB/victim-repo` tracked by Shipit, `webhook_secret` properly configured and secret).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
with any/no `X-Hub-Signature` value.
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`; because `OrgA.webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of the header value — see `lib/shipit/github_app.rb` lines 76-83.
4. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves the target via `payload.dig('repository','full_name')` = `"OrgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb` lines 32-38), and calls `stack.sync_github` on the real `OrgB/victim-repo` stack — a write the attacker never had credentials for.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
