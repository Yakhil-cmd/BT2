### Title
`recalculate_stake_rewards` reads live, mutable `stakes_cache` state instead of the frozen epoch-boundary snapshot, causing recalculated stake rewards to diverge from the originally cached amounts - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`recalculate_stake_rewards` reconstructs pending partitioned stake rewards from the *live* `stakes_cache` whenever a bank is initialized after a snapshot restore while epoch rewards are still active, rather than from a frozen snapshot of stake state taken at the original epoch-boundary calculation. Because a stake account's raw `delegation.stake` magnitude can be mutated by its owner (e.g. via `Split`/`Merge`/re-delegate) in blocks between the calculation slot and the later distribution/recalculation slot, an unprivileged user can cause the recalculated reward for their own not-yet-distributed stake entry to differ from the amount originally computed in `begin_partitioned_rewards` and baked into the `EpochRewards` sysvar's fixed `total_rewards`.

### Finding Description
The reward lifecycle is:
1. At the epoch boundary, `calculate_rewards_for_partitioning` / `calculate_stake_rewards_and_commissions` compute `stake_rewards` and `total_stake_rewards_lamports` from the stakes at that moment, which are cached into `Bank::epoch_reward_status` and used to fix the `EpochRewards` sysvar's `total_rewards` in `begin_partitioned_rewards`. [1](#0-0) 

2. If a node instead comes up via `initialize_after_snapshot_restore` while that epoch's rewards are still active, `recalculate_partitioned_rewards_if_active` calls `recalculate_stake_rewards`, which explicitly reads `self.stakes_cache.stakes()` — the *live* stakes cache at recalculation time — rather than any frozen snapshot corresponding to the original calculation slot. [2](#0-1) [3](#0-2) 

3. `calculate_stake_rewards_and_commissions` → `redeem_delegation_rewards` extracts `let stake = *stake_account.stake();` from that live account and feeds it (unchanged) into `redeem_rewards`/`calculate_stake_points_and_credits`, whose Tower-points formula multiplies `earned_credits` by `delegation_effective_stake(&stake.delegation, rewarded_epoch, stake_history, ...)` — a function of the account's *current* `delegation.stake` field, not a value frozen at the original calculation slot. [4](#0-3) [5](#0-4) 

4. While already-distributed accounts are naturally idempotent (their `credits_observed` was advanced during distribution, so recalculation yields zero — as asserted in `test_recalculate_partitioned_rewards`), *not-yet-distributed* accounts have no such protection: their reward is recomputed purely from whatever `delegation.stake`/`credits_observed` values happen to be live at recalculation time. [6](#0-5) 

5. The code base is aware of exactly this class of issue for the Alpenglow block-reward denominator (comment explaining `stake > total_active_stake` can occur "during recalculation" and is clamped, and `RewardEpochDelegatedStakes` is snapshotted specifically to avoid it for AG points), but no equivalent frozen-magnitude protection exists for the raw `delegation.stake` field consumed by the Tower points/redeem-rewards path used in `redeem_delegation_rewards`. [7](#0-6) [8](#0-7) 

An unprivileged staker who owns their own stake account can issue a normal `Split`/`Merge`/redelegate instruction against it in a block that lands strictly between the epoch-boundary calculation slot and the block at which some validator recalculates (via snapshot restore) before that account's partition is distributed. This mutates the raw `delegation.stake` magnitude used by the recalculation path, so `recalculate_stake_rewards`' output for that stake entry differs from the value cached at `begin_partitioned_rewards` time, which fixed the sysvar's `total_rewards`/capitalization accounting.

### Impact Explanation
Because `distribute_epoch_rewards_in_partition`/`store_stake_accounts_in_partition` pay out exactly the `inflation.stake_reward` value present in whichever `PartitionedStakeRewards` set is active in `epoch_reward_status` at distribution time, a validator that recalculates mid-epoch (via legitimate, unmodified snapshot restore) will mint a different lamport amount for the affected account than a validator that never restarted and is still using the originally cached set. This falls into the "misattributed/duplicated rewards" and "cross-node state divergence" (bank hash divergence between honest nodes) categories, since both nodes execute the identical distribution block/slot but arrive at different resulting stake-account states and total lamports minted versus what was recorded as `total_rewards` in the `EpochRewards` sysvar at `begin_partitioned_rewards` time.

### Likelihood Explanation
Exploitation requires: (1) the attacker's own stake account still has an undistributed reward pending in a later partition (any staker at all satisfies this for most of the ~`REWARD_CALCULATION_NUM_BLOCKS`/`num_partitions` window), (2) the attacker issues a normal, self-authorized `Split`/`Merge`/redelegate instruction on their own account after the epoch-boundary calculation block but before their partition is distributed, and (3) at least one validator in the network restarts from a (legitimate, non-malicious) snapshot taken in that same window before finishing distribution — a routine operational event (crash recovery, planned restart, new/rejoining validator), not something requiring privileged access. Given restarts occur regularly across a large validator set and the distribution window can span many blocks, this is plausible without needing an adversary-controlled snapshot or validator identity.

### Recommendation
`recalculate_stake_rewards` should not rely on the live `stakes_cache` for the raw stake magnitude/`credits_observed` inputs to reward computation. Instead, persist (or reconstruct deterministically from data already committed at the calculation slot, e.g. via the `EpochRewards` sysvar plus a serialized snapshot of the stake state used in `begin_partitioned_rewards`) the exact per-account inputs used at the original calculation time, and use those frozen values during recalculation instead of whatever the stake accounts look like at restart time. At minimum, add a `RewardEpochDelegatedStakes`-style frozen snapshot for the raw stake magnitude analogous to the fix already applied to the Alpenglow block-reward denominator.
