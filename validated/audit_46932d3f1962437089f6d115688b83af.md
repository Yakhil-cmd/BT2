### Title
Cross-tenant `Status` write via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by SHA alone, with no restriction to the stack(s) belonging to the repository named in the webhook payload. Since `Commit#create_status_from_github!` forwards the *matched* commit's own `stack_id` into `Status.replicate_from_github!`, any repository owner who can get a commit with an identical SHA into their own onboarded repo (e.g. via a fork sharing history with the victim repo) can emit a legitimately-signed `status` webhook from their own org and have Shipit write a `Status` row against the victim's stack.

### Finding Description
Claimed binding: for a `status` webhook whose signature is verified against `repository_owner` (the attacker's own org), the produced `Status#stack_id` should equal only stacks belonging to that same repository. The traced binding is instead: `Status#stack_id == commit.stack_id` for *every* `Commit` row in the entire table whose `sha` matches `params.sha`, irrespective of which repository/org signed the webhook.

Path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only proves the payload was signed by `Shipit.github(organization: repository_owner)` — i.e., that *some* org the attacker controls sent this webhook. It performs no join against the `repository` field to constrain which `Commit`/`Stack` rows may be touched.
- `StatusHandler#process` [1](#0-0)  executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no scope tying the query to the webhook's `repository`/`organization` — any commit anywhere in the datastore with a matching SHA is updated.
- `Commit#create_status_from_github!` [2](#0-1)  calls `statuses.replicate_from_github!(stack_id, github_status)` using the matched commit's own `stack_id` — correct *per commit*, but the commit set itself was never scoped to the authenticated repository.
- `Status.replicate_from_github!` [3](#0-2)  persists `stack_id:` verbatim as given.

Root cause: SHA is content-addressed and not unique per repository — two different repositories (e.g. a fork and its upstream, or two forks of the same public repo) commonly share identical commit SHAs. `StatusHandler` never restricts the SQL query by repository, so the "repository scope" that `verify_signature` establishes is discarded before the write.

Attacker flow: attacker owns/administers a GitHub repo `attacker/repo` that is a fork of (or shares an ancestor commit with) a victim's Shipit-tracked repository `victim/repo`. Because forks share git object history, a commit `abc123...` exists identically in both repos. Attacker calls GitHub's Statuses API (`POST /repos/attacker/repo/statuses/abc123...`) — an action fully within their own repo permissions — producing a `status` webhook signed with the correct secret for `attacker`'s org. `verify_signature` passes because it only checks the signature belongs to `repository_owner = attacker`. `StatusHandler#process` then matches **all** `Commit` rows with `sha = abc123...`, including the one owned by the victim's stack, and writes a `Status` (attacker-controlled `state`, `description`, `context`, `target_url`) against the victim stack.

### Impact Explanation
An attacker who does not own or administer the victim's stack can inject a fabricated CI status (e.g., `state: success`) onto a commit in the victim's stack, using data none of which is validated against the victim's actual CI. Since Shipit gates deploy eligibility and "deployable" checks on commit statuses (`deployable_status` hooks, required statuses), this can trick the victim's Shipit instance into treating an unvetted/failing commit as deployable — a payload from one repository mutating another repository's `Status`/commit state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The write is repeatable against any repository that shares commit history (any fork network) with the attacker's own repo, and is not limited to a single victim.

### Likelihood Explanation
Preconditions: attacker must own/administer a GitHub repository that is onboarded to their own Shipit-monitored org/webhook AND shares at least one commit SHA with the victim's tracked repository (trivially true for forks of public repos, or repos sharing a common base/vendor commit). No Shipit secrets, sessions, or privileged roles are required — only the attacker's own repo's GitHub webhook, which they legitimately control. Cost is low (one GitHub API call to set a status); it is fully repeatable for every shared SHA.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to stacks belonging to the repository/organization identified in the webhook payload (e.g., join through `Stack`/`Repository` matching `params`'s `repository.full_name`) instead of matching `sha` globally across all tenants.

### Proof of Concept
Minitest plan (model/controller test, no live GitHub):
1. Create two stacks/repositories, `stack_victim` (repo `victim/repo`) and `stack_attacker` (repo `attacker/repo`), each with a `Commit` sharing the identical `sha` (`shared_sha`), belonging to different stacks (simulating shared fork history).
2. Stub `Shipit.github(organization: 'attacker').verify_webhook_signature` to return `true` (attacker's own legitimate signature), for the `attacker` org only.
3. POST to `/webhooks` with `X-Github-Event: status`, payload `{ sha: shared_sha, state: 'success', repository: { full_name: 'attacker/repo', owner: { login: 'attacker' } } }`.
4. Assert: `Status.where(stack_id: stack_victim.id, commit_id: commit_victim.id).exists?` is `true` even though the webhook's signing org (`attacker`) never owns `stack_victim`.
   - Equality before: expected `Status#stack_id == stack_attacker.id` (only stacks under `attacker/repo` should be touched).
   - Equality after: observed `Status#stack_id == stack_victim.id`, proving the divergence.
