This confirms the vulnerability: signature verification is scoped per GitHub *organization* (`Shipit.github(organization: repository_owner)`), not per-repository, and `StatusHandler#process` queries `Commit.where(sha: params.sha)` with no repository/stack filter at all.

### Title
`StatusHandler#process` writes commit statuses by bare SHA with no repository scoping, letting a webhook authenticated for one repository flip CI state on any stack sharing that SHA - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits solely via `Commit.where(sha: params.sha)`, without checking that the SHA belongs to the repository that authenticated the webhook. Since `WebhooksController#verify_signature` authenticates the sender only against a per-organization `webhook_secret` (`Shipit.github(organization: repository_owner)`), any repository within that same organization/installation can produce a validly signed `status` event that mutates a `Commit` belonging to a completely different repository/stack, as long as the two commits share a SHA (trivial via shared git history/forks/cherry-picks of identical content).

### Finding Description
The broken binding is: `commit.stack.repository.full_name == payload.repository.full_name`, which the code never enforces. `StatusHandler#process` does: [1](#0-0) 
It loops over every `Commit` row with a matching `sha`, calling `commit.create_status_from_github!(params)` for each, regardless of which `stack`/`repository` that commit belongs to.

Authentication only asserts that the payload came from GitHub for the claimed organization, not the claimed repository: [2](#0-1) 
`repository_owner` is read directly out of the attacker-influenced payload: [3](#0-2) 
and the HMAC secret used for verification is per-organization (`@webhook_secret = @config[:webhook_secret]`), not per-repository: [4](#0-3) [5](#0-4) 

So a GitHub organization can contain many repositories all sharing one webhook secret; GitHub itself will faithfully sign `status` events for *any* repo in that org/installation, with attacker-controlled `context` and `state` fields, and `sha` values under the attacker's control (attacker can create a commit in their own repo whose content, tree, parents, author/committer and timestamps are identical to a target commit, producing an identical SHA1 - trivial in shared-history/fork scenarios). Once such a webhook is delivered and passes `verify_signature` (which only checks org-level HMAC, not repo identity), `StatusHandler#process` finds and mutates *every* `Commit` row across *every* stack that has that SHA, including a victim's production stack, via `Status::Collection#replicate_from_github!` → `commit.create_status_from_github!`.

Existing guards do not catch this: `drop_unhandled_event` only filters unknown event types; `ExplicitParameters` (`params do ... end` block) only validates payload shape, not repository ownership; there is no repository/stack scoping anywhere in `StatusHandler`. `Commit#deployable?` and `Commit#blocked?` (`app/models/shipit/commit.rb` lines 227-237) key directly off `status`/`blocking?`/`success?`, so once the attacker flips the status to `success` for the required `ci/integration` context, a production stack's deployability/merge/rollback state changes immediately (`stack.schedule_merges` is triggered inside `Commit#add_status`, `app/models/shipit/commit.rb` lines 366-386).

### Impact Explanation
An attacker who controls (or has push access + webhook delivery from) any repository sharing the same GitHub organization/App installation as a victim's Shipit-managed production stack can, by crafting a commit whose SHA collides with a commit already present in the victim stack, inject a forged `success` status for the required context (e.g. `ci/integration`). This directly toggles `Commit#deployable?`/`blocked?` for the victim's production stack, enabling unauthorized deploy/merge/rollback of attacker-influenced state - a cross-repository/cross-tenant write, matching the Critical category "a payload for one repository mutating another's stack, commit... or an unauthorized deploy, rollback or merge." The blast radius spans every repository/stack sharing an organization-level webhook secret, which in multi-repo Shipit deployments can be broad.

### Likelihood Explanation
Preconditions: attacker needs (a) a repository under the same GitHub organization/App installation as the victim stack (so the org-scoped webhook secret validates their event), and (b) a commit SHA collision with a target commit in the victim's stack, which is realistic when repos share history (forks, subtree merges, cherry-picks preserving author/committer/timestamps) — no cryptographic SHA1 collision needed. This requires organizational co-tenancy rather than true internet-wide unauthenticated access, but no Shipit session, API token, or GitHub App secret is needed, and the attack is fully repeatable per SHA/context.

### Recommendation
Scope `StatusHandler#process` (and the equivalent check-run/other SHA-keyed handlers) to only update commits belonging to stacks whose `Repository#full_name` matches `params.dig('repository','full_name')` (or `payload.repository.full_name`) from the verified webhook payload, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { full_name: params.repository.full_name })`. Additionally, verify signatures against the specific repository/App installation associated with the payload where the App model supports per-repository installations, rather than a single org-wide secret shared across all repos.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Create `repo_a` (attacker-controlled, same org `shopify`) and `stack_victim` under `repo_b`/production environment, both under organization `shopify` (same `webhook_secret`).
2. Create `commit_victim` on `stack_victim` with `sha = "deadbeef..."`, required status context `ci/integration`, currently `pending`/not deployable. Assert `commit_victim.deployable? == false`.
3. Create `commit_attacker` on a stack tied to `repo_a` with the same `sha = "deadbeef..."` (simulating SHA collision/shared history).
4. POST `/webhooks` with `X-Github-Event: status`, a validly-signed-for-`shopify` payload: `{ sha: "deadbeef...", context: "ci/integration", state: "success", repository: { owner: { login: "shopify" }, full_name: "shopify/repo_a" } }`.
5. Assert both `commit_attacker.reload.status.state == "success"` AND `commit_victim.reload.status.state == "success"` even though the payload's `repository.full_name` was `shopify/repo_a`, not `shopify/repo_b` — proving `StatusHandler` mutated a commit belonging to a repository that did not authenticate the request. Assert `commit_victim.deployable? == true` post-webhook, demonstrating the forced ship/block state flip on the production stack.
