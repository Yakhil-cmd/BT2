Based on my research, I identified a plausible analog to the CVE-2021-44926 null-pointer-dereference/crash bug class, but I was **not able to fully confirm** every step of the exploit chain before running out of tool budget. I'll present what I found and be explicit about the residual uncertainty.

### Title
Uncaught exception on `null`-valued AA trigger data field crashes every full node — (File: `formula/evaluation.js`)

### Summary
`selectSubobject()` in `formula/evaluation.js`, used whenever an oscript formula in an AA definition selects nested fields from attacker-controlled `trigger.data`, `params`, or `state` (e.g. `trigger.data.a.b`), ends with a bare `throw Error("unknown type of subobject: " + value)` for any resolved value that is not boolean/number/Decimal/string/non-null-object [1](#0-0) . Unlike almost every other type-mismatch branch in this file, which fails gracefully via `setFatalError(...)` [2](#0-1) , this branch performs a raw synchronous `throw`.

### Finding Description
An unprivileged AA trigger sender fully controls the JSON payload of the message sent to an Autonomous Agent (e.g. a `data` message or `payment` message with `.data`), which becomes `trigger.data` inside the AA's oscript formulas [3](#0-2) . If the AA definition contains a selector expression such as `trigger.data.someField` and the posted JSON contains an explicit `null` for that key, `selectSubobject` traverses into it via `hasOwnProperty(value, evaluated_key)` / `value = value[evaluated_key]` [4](#0-3)  and can leave `value === null` at the end of the traversal, which is not handled by any of the typed branches and falls into `throw Error(...)`.

This `throw` occurs deep inside `async.eachSeries` completion callbacks invoked transitively from `aa_composer.js`'s `handleTrigger` / `replace` / `evaluateAA`, none of which wrap `formulaParser.evaluate(...)` calls in a `try/catch` — they only check `if (res === null) return cb(err.formattedError || ...)` for formula-reported errors [5](#0-4) [6](#0-5) . A raw synchronous `throw` in this context is not converted to a formula error and instead escapes as a Node.js uncaught exception.

`network.js` installs a process-wide handler that deliberately crashes the node on any uncaught exception: `process.on('uncaughtException', ... ); throw err; // crash the process to avoid ending up in an inconsistent state` [7](#0-6) . Because AA trigger processing (`handlePrimaryAATrigger`) runs identically and deterministically on every full node once the triggering unit becomes stable [8](#0-7) , a single crafted trigger unit would crash every full node in the network at the same MCI, matching the CVE's "null pointer dereference causing a crash" bug class but with network-wide DoS impact instead of a single-process crash.

### Impact Explanation
If exploitable, this would crash every full node processing the same AA-triggering unit, i.e. the network becomes unable to confirm new units past that MCI — the accepted "network unable to confirm new units" impact category.

### Likelihood Explanation
**Uncertain / not fully confirmed.** I could not verify within the available tool budget whether an actual JS `null` (as opposed to `false`, which many other code paths substitute for missing/empty values, e.g. `trigger.data` returns `false` when empty [3](#0-2)  and `local_var` returns `false` for `undefined` [9](#0-8) ) can actually survive traversal through `selectSubobject` from attacker-supplied JSON without being caught earlier. I also could not confirm the null-safety of `ValidationUtils.hasOwnProperty` (defined in `validation_utils.js`, not fully inspected) when called with `value === null` mid-traversal, which could throw a different (but still uncaught) `TypeError` even earlier in the same function.

### Recommendation
Have a Devin agent:
1. Confirm whether a crafted AA trigger with a `null`-valued nested field in `trigger.data`/`params` can reach the `throw Error("unknown type of subobject...")` line or the `hasOwnProperty(value, evaluated_key)` call in `formula/evaluation.js` with `value === null`, using the existing AA composer test harness (`test/aa_composer.test.js` has patterns like `dryRunPrimaryAATrigger` already used for similar "invalid selector" tests around line 1714).
2. If confirmed, replace the raw `throw Error(...)` in `selectSubobject` with the graceful `setFatalError(...)` pattern used elsewhere in the file, and add an explicit `value === null` guard before the `hasOwnProperty` call.
3. Audit other raw `throw Error(...)` statements inside `formula/evaluation.js` and `aa_composer.js`'s `replace`/`handleTrigger` closures for the same uncaught-exception-crashes-the-node pattern, since `network.js` treats any of them as fatal.

### Proof of Concept
Not verified — would require constructing an AA definition with a selector formula (e.g. `$x = trigger.data.a.b;`) and sending a trigger whose `data` payload is `{"a": null}`, then observing whether `dryRunPrimaryAATrigger`/`handlePrimaryAATrigger` throws uncaught rather than bouncing gracefully. This step needs to be executed in a Devin session with the test suite to confirm before treating this as a validated finding.
