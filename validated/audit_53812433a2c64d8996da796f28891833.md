### Title
Status webhook handler applies commit statuses across repositories, letting one authenticated GitHub organization write CI state into another stack's commits and trigger an unauthorized deploy - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook against the GitHub organization/repository derived from the payload (`repository.owner.login`, falling back to `organization.login`), and selects the matching per-organization `webhook_secret` to validate the HMAC signature. Once verified, the event is dispatched to a handler. Unlike `PushHandler`, which correctly scopes its writes to the `Repository` matching `payload.dig('repository', 'full_name')`, `StatusHandler#process` looks up target `Commit` rows solely by SHA, with no repository/stack scoping at all. This breaks the trust binding between "the organization whose webhook secret authenticated this request" and "the repository/stack whose commit state gets written."

### Finding Description
The webhook signature check is repository/organization-scoped: [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The intent is: "only accept this event if it is HMAC-signed with the secret configured for the organization that owns the referenced repository." The base `Handler` class exposes a `stacks` helper that correctly performs this same repository scoping: [2](#0-1) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler` uses this helper, so its writes are properly confined to stacks belonging to the repository named in the (signature-verified) payload: [3](#0-2) 

`StatusHandler`, however, ignores this scoping entirely and updates any `Commit` record matching the SHA, regardless of which repository/stack it belongs to: [4](#0-3) 

```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Because `Commit.sha` is looked up globally with no `stack_id`/repository filter, any organization that Shipit trusts (i.e., any org with a configured `webhook_secret` and installed GitHub App) can send a validly-signed `status` event referencing a commit SHA that also happens to exist in a *different, unrelated* stack's commit history (e.g., via a fork sharing git history, a cherry-picked/replayed commit with identical tree/parent/author metadata, or any other means of producing an identical SHA), and that status will be applied to the victim stack's commit — even though the signing organization has no relationship to the victim's repository. This is exactly the pattern of "organization authenticated ≠ repository written": the HMAC binds trust to `repository_owner`/`organization.login` from the payload, but `StatusHandler` never re-checks that binding before mutating state.

### Impact Explanation
`Commit` statuses directly influence deploy automation. `Stack#deployable?`/`allows_merges?` and continuous-delivery triggers rely on the recorded status state (`required_statuses`, `blocking_statuses`, merge-queue status). Forging a `success` (or otherwise favorable) status through a trusted-but-unrelated organization's signature can:
- Make an otherwise-failing/unreviewed commit appear CI-green in a victim stack, satisfying `deployable?`/`required_statuses` checks.
- Trigger `ContinuousDeliveryJob`/`trigger_continuous_delivery` to deploy that commit automatically if continuous deployment is enabled, or unblock the merge queue (`allows_merges?`) to merge/deploy a PR that never passed the real required checks.

This lines up with the accepted High-impact class "escalation... unauthorized deploy, rollback or merge," since it lets an actor who is authenticated only for organization A push state that results in an unauthorized deploy for organization/stack B.

### Likelihood Explanation
Exploitation requires: (1) Shipit is configured with more than one trusted GitHub organization/app installation (a common multi-tenant deployment pattern for this engine), and (2) the attacker can get a commit with the desired SHA to exist under an organization they control while a stack elsewhere tracks a commit with the same SHA (achievable via forks that preserve full git history/SHAs, or by replaying a commit with identical metadata). Given Shipit's design explicitly supports multiple orgs (`Shipit.github(organization:)`, `test/dummy/config/secrets_double_github_app.yml`), and GitHub commit statuses can be freely set by any collaborator/integration on their own repository via the GitHub API, this is a realistic, no-special-privilege path once cross-org trust exists. Likelihood is assessed as reasonable but conditioned on the multi-organization configuration, so it is not certain but concretely reachable through the engine's own code (not requiring any credential the rules exclude).

### Recommendation
Scope `StatusHandler#process` (and any other handler that writes to `Commit`/`Stack` records) to the repository indicated in the verified payload, mirroring `Handler#stacks`/`repository_name`, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` so a status can only be applied to commits belonging to the repository that was actually authenticated by the webhook signature.

### Proof of Concept
1. Shipit is configured with two trusted GitHub organizations/apps, `OrgA` (attacker has write/admin access to a repo there) and `OrgB` (hosts the victim stack with continuous deployment or a merge queue enabled), each with its own `webhook_secret` per `Shipit.github(organization:)`.
2. Victim stack in `OrgB` has a tracked commit `SHA_X` (e.g., the HEAD of its deploy branch) awaiting a passing CI status.
3. Attacker creates/obtains a commit with the identical `SHA_X` under a repository in `OrgA` (e.g., by forking the `OrgB` repo into `OrgA`, which preserves all original SHAs) and, as owner of that repo, calls the GitHub Statuses API to set `state: success` on `SHA_X`.
4. GitHub sends a `status` webhook to Shipit signed with `OrgA`'s `webhook_secret`; `WebhooksController#verify_signature` validates it successfully because `repository_owner` resolves to `OrgA`.
5. `StatusHandler#process` executes `Commit.where(sha: 'SHA_X')`, which matches the `OrgB` victim stack's commit row (no repository filter), and calls `create_status_from_github!`, marking it `success` for the victim stack.
6. If `OrgB`'s stack has continuous deployment enabled or relies on this status for `deployable?`/merge-queue checks, this forged status can trigger an unauthorized deploy or unblock an unauthorized merge — despite the request only ever being authenticated for `OrgA`.
