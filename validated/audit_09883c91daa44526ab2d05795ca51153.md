### Title
Potential Stake/Reward Lock and State Inconsistency Due to Blocked Validator Exit - ([File: kaiax/valset/impl/transition_context.go])

### Summary
The Kaia blockchain's permissionless validator lifecycle introduces a `ValExiting` state for nodes that violate staking requirements or performance thresholds. However, a transition to `ValExiting` can be blocked if the system's "exit slots" are full or if the number of active validators would drop below the minimum required for BFT consensus. When this happens, a validator that *should* be exiting remains in the `ValActive` state. This creates a state inconsistency where a node failing system invariants continues to participate in consensus and earn rewards, potentially locking rewards in a "zombie" state if the validator's underlying staking contract has already initiated a withdrawal or if the node is otherwise unmaintained.

### Finding Description
In the `kaiax/valset` module, the `applyViolationTransition` function is responsible for demoting validators that fall below the `MinStake` or exceed the `PfsThreshold` (proposal failure score). These nodes are intended to transition from `ValActive` to `ValExiting` [1](#0-0) .

However, this transition is guarded by `canDemoteActive`, which checks two conditions:
1. `hasSlot(valset.ValExiting)`: Whether there is an available slot in the `ValExiting` state (capped by `MaxSlotAvailable`) [2](#0-1) .
2. `newValidators.CountByState(valset.ValActive) > ctx.MinActiveCount`: Whether removing this validator would drop the active set below the safety floor required for Istanbul BFT consensus [3](#0-2) .

If either check fails, the transition is skipped, and the validator remains `ValActive` [4](#0-3) . While this preserves consensus liveness, it creates a native analog to the external report's bug: a validator that has functionally "failed" or is in the process of being removed is kept in an active state. Because reward eligibility is strictly tied to the `ValActive` state [5](#0-4) , these "zombie" validators continue to be selected as proposers and receive staking rewards [6](#0-5) .

### Impact Explanation
The impact matches the "Unauthorized reward distribution" and "Invalid state transition" categories:
1. **Asset Impact**: Rewards (KAIA) continue to be minted and distributed to validators that have violated system invariants (e.g., dropped below `MinStake`). If these nodes are unmaintained or their operators have already triggered contract-level withdrawals, these funds may become effectively locked or misallocated.
2. **State Inconsistency**: There is a discrepancy between the validator's performance/stake (which dictates they should exit) and their protocol state (`ValActive`). This allows a malicious or failing node to remain in the consensus council indefinitely if they can ensure the exit slots remain full.

### Likelihood Explanation
The likelihood is medium. The `MaxSlotAvailable` and `MinActiveCount` are derived from the total number of validators using `SlotMath` [7](#0-6) . In a network with a small number of validators (e.g., 4 to 7), the `totalBudget` for exits is very low (1 or 2), making it easy for the exit queue to fill up and block necessary demotions.

### Recommendation
Implement a "Pending Removed" or "Graceful Exit" sub-state that allows a validator to be marked as "failed" even if the active set cannot yet be reduced. For reward distribution, modify `IsRewardEligible` to exclude nodes that have pending violations, even if they must remain in the consensus set for liveness reasons.

### Proof of Concept
The vulnerability is demonstrated in the existing test suite, which confirms that nodes failing `MinStake` requirements are kept as `ValActive` when slots are full:

```go
// From kaiax/valset/impl/transition_context_test.go
t.Run("minStake violation: skip when slot full", func(t *testing.T) {
    m := NodeMap{
        addr1: {State: ValActive, StakingAmount: belowMinStake},
        addr2: {State: ValActive, StakingAmount: belowMinStake},
        addr3: {State: ValActive, StakingAmount: aboveMinStake},
        addr4: {State: ValActive, StakingAmount: aboveMinStake},
    }
    // maxSlot=1 means only one node can transition to ValExiting
    ctx := violationCtx(t, ctxOpts{MaxSlotAvailable: 1, MinActiveCount: 3})
    out := ctx.applyViolationTransition(m)
    assert.Equal(t, 1, int(out.CountByState(ValExiting)))
    assert.Equal(t, 3, int(out.CountByState(ValActive))) // One node belowMinStake STAYS ValActive
})
``` [8](#0-7) 

In this scenario, the node that remains `ValActive` despite being `belowMinStake` will continue to receive rewards because `ValActive.IsRewardEligible()` returns `true` [9](#0-8) .
