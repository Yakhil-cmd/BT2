### Title
Webhook signature verification authenticates the payload's `owner.login` while every handler acts on the independently-attacker-controlled `repository.full_name` / `organization.login`, enabling cross-organization forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which per-organization webhook secret to validate the HMAC against using `repository.owner.login` (falling back to `organization.login`) taken from the raw, attacker-supplied JSON body. Every webhook handler, however, resolves the target `Repository`/`Team`/`Stack` using a *different* field of that same body (`repository.full_name`, or `organization.login` for membership events) without checking it is consistent with the field that was actually verified. Because Shipit explicitly supports multiple organizations each with its own webhook secret (`Shipit.github_app_config`, `Shipit.github_organizations`), a party who legitimately knows the webhook secret for *one* onboarded organization can forge a signed payload whose `repository.owner.login` matches their own org (so the signature check passes) while `repository.full_name` names a repository belonging to a *different* onboarded organization, causing writes against that other org's stacks.

### Finding Description
`verify_signature` picks the app config strictly from the owner field: [1](#0-0) 

`repository_owner` is read straight out of the untrusted JSON body (`params.dig('repository','owner','login')` / `params.dig('organization','login')`), and `Shipit.github(organization: repository_owner)` looks up that organization's independently configured `webhook_secret`: [2](#0-1) 

Once the HMAC computed with that organization's secret matches, the entire raw body — including `repository.full_name`, which is unrelated to `repository.owner.login` as far as the code is concerned — is handed to the handlers. Handlers resolve the acted-upon repository purely from `full_name`: [3](#0-2) [4](#0-3) 

Nothing ties `full_name`'s owner segment back to the `repository.owner.login`/`organization.login` value that was actually verified. Because Shipit is explicitly designed to host several organizations, each with its own app/webhook config (`github_app_config`, `github_organizations`), knowledge of org A's `webhook_secret` is a normal, low-privilege capability for anyone with admin access to org A's GitHub App/webhook settings — it grants no rights over org B by design. This breaks the equality "organization that authenticated == repository that is written": the signature authenticates org A, but the write lands on org B's `Repository`/`Stack`/`PullRequest`/`Team` records.

Concretely reachable, unauthenticated (from org B's point of view) actions once a payload signed with org A's secret but claiming `repository.full_name = "orgB/repo"` is accepted:
- Create/unarchive a `ReviewStack` and attach forged `PullRequest` data (title, state, additions/deletions, labels, assignees, head commit) for org B's repository via `OpenedHandler`/`LabeledHandler`/`UnlabeledHandler`/`ReviewStackAdapter`: [5](#0-4) 
- Archive an existing review stack belonging to org B via `ClosedHandler`: [6](#0-5) 
- Overwrite an existing `PullRequest`'s recorded state/labels/head via `EditedHandler`/`AssignedHandler`: [7](#0-6) 

### Impact Explanation
This is a cross-repository/cross-organization write: an entity whose only privilege is knowing org A's webhook secret can create, mutate, and archive stack/pull-request state belonging to org B, which it has no authorization over. This matches the explicitly in-scope Critical impact class "cross-repository writes."

### Likelihood Explanation
Requires only that the attacker legitimately holds a webhook secret for any one organization already onboarded to the Shipit instance — an ordinary, low-privilege capability in a multi-org deployment, and not equivalent to a Shipit session, `ApiClient` token, or `api_clients_secret`. The rest of the exploit is a straightforward crafted HTTP POST with a correctly computed HMAC.

### Recommendation
After verifying the signature, ensure every field actually acted upon by handlers is bound to the authenticated organization: e.g., re-derive/validate that `repository.full_name`'s owner segment equals the `repository_owner`/`organization.login` value used to select the webhook secret, and reject the request otherwise.

### Proof of Concept
1. Attacker has admin access to org `attacker-org`, which is configured in `Shipit.secrets.github` with webhook secret `S`.
2. Attacker crafts a `pull_request` `opened` webhook body:
```json
{
  "action": "opened",
  "number": 999,
  "pull_request": { "...": "...", "head": { "sha": "...", "ref": "evil" }, "user": {"login": "attacker"} },
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sender": { "login": "attacker" }
}
```
3. Attacker computes `X-Hub-Signature` using secret `S` (known to them for `attacker-org`) over this exact body.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose secret matches → signature verified.
5. `OpenedHandler` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and creates/mutates a `ReviewStack` under `victim-org/victim-repo`, a repository the attacker has no authorization over.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
