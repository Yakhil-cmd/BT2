### Title
Residual receiver-to-pool token allowance is never cleared after a flash loan, letting any caller re-pull `principal + fee` from the receiver without its authorization - (File: contracts/pool/src/ops/flash.rs)

### Summary
The pool collects flash-loan repayment via `transfer_from`, spending only `principal + fee` of whatever allowance the receiver granted. The excess allowance is left standing indefinitely. Because `flash_loan` is permissionless and the repayment pull requires no fresh authorization from the receiver, an unprivileged caller can initiate flash loans naming that receiver and repeatedly drain `fee`-sized amounts from it until the residual allowance is exhausted. This mirrors the report's bug class — an acquired resource (a refcounted node / a granted allowance) that is not released when the operation completes.

### Finding Description
`apply` pays the principal to `receiver`, invokes its `execute_flash_loan` callback, then calls `collect_repayment`, which only requires `asset.allowance(receiver, pool) >= terms.total_repayment` and pulls exactly `total_repayment` via `transfer_from`. There is no `approve(0)` or equivalent cleanup afterward; any allowance the receiver granted beyond `total_repayment` remains valid against the pool forever. Contrast with the swap-aggregator's Comet venue, which explicitly clears its approval after each hop (`clear_comet_approval`), showing the codebase treats standing approvals as a leak hazard — the pool's own allowance consumption has no symmetric release. Attack path (all unprivileged): `controller.flash_loan(caller=attacker, hub_asset, amount, receiver=victim, data)` → `process_flash_loan` → `pool_flash_loan_call` → `pool::apply` → `collect_repayment`. The pool first transfers `amount` to the victim, calls the victim's `execute_flash_loan`, then pulls `amount + fee` from the victim's standing allowance. The victim nets a loss of exactly `fee` per invocation, with the attacker paying nothing (principal round-trips). [3](#0-2) [4](#0-3) 

### Impact Explanation
Theft of user funds. Any flash-receiver contract that holds a residual token allowance to the pool — a natural pattern for receivers that approve once or over-approve — can be forced to pay the flash fee on loans it never requested, on any flashloanable market, repeatedly, until the allowance is consumed. The pool's own accounting stays solvent (`require_balance` enforces `balance_after_repayment`), so the loss is borne entirely by the receiver. Severity is bounded per call by the fee, keeping it Medium rather than High.

### Likelihood Explanation
Requires a receiver contract with residual `allowance(receiver, pool) > 0` after prior flash loans (approving more than the exact repayment, or approving for a loan that reverted after approval, leaves this state) and the victim's `execute_flash_loan` not reverting on unsolicited calls. Both conditions are plausible for reusable receiver contracts; the attacker needs no privilege, no capital, and no victim signature. Each repetition needs the residual allowance to cover the next `amount + fee`, so choosing smaller `amount` values keeps the attack alive longer.

### Recommendation
After `transfer_from` in `collect_repayment`, zero the remaining allowance the same way the Comet venue does (`approve(receiver → pool, 0)` is not possible since the spender is the pool — instead have the receiver-facing protocol use exact-amount approvals, or have the pool track/revoke residual approval via a second `transfer_from`-independent mechanism). The cleaner fix: make the receiver `transfer` the repayment directly to the pool inside `execute_flash_loan` and drop the allowance/`transfer_from` pattern entirely, so no standing approval can ever leak.

### Proof of Concept
1. Victim receiver contract `V` executes a legitimate flash loan of `A` USDC and inside `execute_flash_loan` calls `approve(V → pool, A + fee + extra)` (a safety margin, or approves a max amount).
2. The loan completes; `collect_repayment` pulls `A + fee`, leaving `extra` allowance standing on `(V, pool)`.
3. Attacker calls `controller.flash_loan(attacker, {hub, USDC}, A', V, data)` with `A' + fee' <= extra`.
4. Pool transfers `A'` to `V`, invokes `V.execute_flash_loan` (no-op returns), checks `allowance(V, pool) >= A' + fee'` — passes — and pulls `A' + fee'` from `V`'s residual allowance.
5. `V` is down `fee'`; `extra` shrinks by `A' + fee'`. Repeat with a smaller `A'` until `extra` no longer covers `amount + fee`. No authorization from `V` is ever requested — allowance spends carry no `require_auth`.

```rust
/// Pulls principal + fee via `transfer_from` after verifying allowance.
fn collect_repayment(
    env: &Env,
    asset: &token::Client,
    pool: &Address,
    receiver: &Address,
    terms: &FlashTerms,
) {
    assert_with_error!(
        env,
        asset.allowance(receiver, pool) >= terms.total_repayment,
        FlashLoanError::InvalidFlashloanRepay
    );
    asset.transfer_from(pool, receiver, pool, &terms.total_repayment);
    require_balance(env, asset, pool, terms.balance_after_repayment);
}
```
