### Title
Bridge Operator Can Front-Run `requestERC20Transfer` to Drain User's Entire `_feeLimit` — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `BridgeFee.sol`, `BridgeOperator.sol`)

---

### Summary

A bridge operator with the default threshold of 1 can front-run a user's `requestERC20Transfer` (or `requestKLAYTransfer`) call by atomically raising `feeOfERC20[token]` (or `feeOfKLAY`) to exactly the user's `_feeLimit` before the transfer lands. Because the fee is read from storage at execution time and the user has no way to commit a maximum-acceptable fee inside the transfer call, the operator drains the user's entire `_feeLimit` of bridged ERC20 tokens (or KAIA) to the `feeReceiver` with no recourse.

---

### Finding Description

`BridgeTransferERC20.requestERC20Transfer` first pulls `_value + _feeLimit` from the caller via `safeTransferFrom`, then delegates to `_requestERC20Transfer`, which calls `_payERC20FeeAndRefundChange`. That helper reads `feeOfERC20[_token]` from storage at the moment of execution and transfers up to `_feeLimit` worth of tokens to `feeReceiver`, refunding the remainder to the user. [1](#0-0) [2](#0-1) 

The fee is mutable: `setERC20Fee` (and `setKLAYFee`) are callable by any registered operator and take effect immediately once the operator threshold is reached. [3](#0-2) [4](#0-3) 

The operator threshold defaults to **1** for all vote types, set unconditionally in the `BridgeOperator` constructor: [5](#0-4) 

The configuration vote gate (`_voteConfiguration`) only enforces a sequential `configurationNonce`; it does not impose any time delay or cooldown: [6](#0-5) 

`configurationNonce` is a public state variable, so any observer can read the current value and craft a valid `setERC20Fee` call immediately.

---

### Impact Explanation

**Corrupted value:** The user's `_feeLimit` worth of bridged ERC20 tokens (or KAIA in the KLAY path) is transferred to `feeReceiver` instead of being refunded. The user receives zero refund despite having approved and transferred `_value + _feeLimit`.

**Invariant broken:** The bridge fee mechanism is supposed to charge only the pre-announced `feeOfERC20[token]` that the user observed before constructing the transaction. The operator can silently replace that value between the user's approval and the transfer execution, causing an unauthorized token drain from the user to the operator-controlled `feeReceiver`.

This falls squarely within the allowed impact: *unauthorized fee charge affecting bridged assets*.

---

### Likelihood Explanation

- Default operator threshold is 1; no multi-sig coordination is required.
- `configurationNonce` is public; the attacker reads it in the same block as the mempool observation.
- The attack requires only two transactions (one `setERC20Fee`, one already pending from the victim) and higher gas priority — a standard front-running setup on any EVM-compatible chain.
- Service-chain bridges are operated by a small set of known operators, making a malicious-insider scenario realistic.

---

### Recommendation

1. **Add a `maxFee` parameter to `requestERC20Transfer` and `requestKLAYTransfer`.** Revert if `feeOfERC20[token] > maxFee` at execution time, mirroring the ERC20 `approve`/`transferFrom` slippage-protection pattern.
2. **Enforce a time-lock on fee changes.** Record the block number when a fee change is voted in and only apply it after N blocks, giving users a window to observe and react.
3. **Alternatively, snapshot the fee at the time of `approve`/`requestERC20Transfer` and commit it into the request event**, so the operator relay cannot substitute a higher value.

---

```text
    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
```

```text
    function _voteConfiguration(uint64 _requestNonce)
        internal
        returns(bool)
    {
        require(configurationNonce == _requestNonce, "nonce mismatch");
```
