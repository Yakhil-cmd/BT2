## Title
Webhook organization used for signature verification is not bound to the repository the payload actually mutates, enabling cross-organization stack forgery in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment (each GitHub organization has its own GitHub App / `webhook_secret`, as documented in `config/secrets.development.example.yml`), the webhook signature is verified against the secret belonging to whichever organization is named in `repository.owner.login` (or `organization.login`), but the handlers that actually mutate data key off a *different*, independently attacker-controlled field: `repository.full_name`. These two fields are never cross-checked, so a valid signature for organization A does not guarantee the payload's effects are scoped to organization A's repositories.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to verify the `X-Hub-Signature` against, based on the organization name extracted from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (multi-tenant schema) and instantiates a `GitHubApp` scoped to that org's `webhook_secret`: [3](#0-2) 

Once the signature check passes, the raw payload is dispatched unmodified to registered handlers: [4](#0-3) 

Every handler resolves the repository/stack to act on from a *different* field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

For example `PushHandler` uses `stacks` (derived from `full_name`) to trigger `sync_github`: [7](#0-6) 

Both `repository.owner.login` and `repository.full_name` are attacker-controlled JSON fields inside the same signed request body — nothing forces `repository.full_name`'s owner segment to equal `repository.owner.login`. The equality the code implicitly assumes but never enforces is:
`organization_that_authenticated(payload.repository.owner.login) == organization_of_repository_written(payload.repository.full_name)`

An operator of (or anyone who otherwise learns) organization A's `webhook_secret` in a multi-org install can sign a payload with `repository.owner.login = "orgA"` (so `verify_signature` succeeds using orgA's secret) while setting `repository.full_name = "orgB/some-repo"`. The handler then acts on org B's stack, which the attacker has no legitimate relationship to, because `Repository.from_github_repo_name` and `Repository.from_param!` split `full_name` independently of the field used for authentication.

### Impact Explanation
This breaks the multi-tenant isolation the per-organization `webhook_secret` schema is meant to provide. It allows an attacker who possesses only one organization's webhook secret to forge webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) that are dispatched against stacks/repositories belonging to an entirely unrelated organization configured in the same Shipit instance — i.e., a cross-organization/cross-repository write, matching the Critical-impact category ("cross-repository writes"/"unauthorized deploy"). Concretely, a forged `push` event can trigger `Stack#sync_github`, and other forged handler events can mutate commit statuses, memberships, or pull-request-driven merge/review-stack state for a repository the attacker does not control.

### Likelihood Explanation
This only matters for deployments using the documented multi-organization `secrets.yml` schema (`github: <org>: ... webhook_secret: ...` per org), which is a first-class, documented configuration option, not a misconfiguration. Any party capable of registering/knowing one tenant org's webhook secret (e.g., a org admin who installed their own GitHub App pointing at the shared Shipit instance) can exploit this without any Shipit session, API token, or GitHub write access to the victim organization/repository — satisfying the "unprivileged attacker" bar relative to the victim org.

### Recommendation
After selecting the GitHub App/secret via `repository_owner` and verifying the signature, `WebhooksController` (or `Handler#repository_name`) should also validate that the owner segment of `repository.full_name` matches the authenticated `repository_owner`/`organization.login`, rejecting the webhook (e.g., `head(422)`) on mismatch. Alternatively, resolve the target repository/stack using the authenticated organization value rather than trusting `full_name` wholesale.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`, `orgA` and `orgB`, each with its own GitHub App and `webhook_secret`.
2. As someone who knows/controls `orgA`'s `webhook_secret` (e.g., an admin who created orgA's GitHub App), craft a JSON payload:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. Compute `X-Hub-Signature: sha1=<hmac(orgA_webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` and the signature validates successfully.
5. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on orgB's stack — a write triggered on an organization the attacker never authenticated for.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
