### Title
Cross-org confused deputy in `WebhooksController#verify_signature` allows a valid webhook from one GitHub org to mutate/archive another org's stack via `ClosedHandler#process` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify against using `params.dig('repository', 'owner', 'login')`, while `ClosedHandler` (and the shared `Handler#repository_name` / `ReviewStackAdapter`) resolve the target `Repository`/`Stack` using the independent field `params.dig('repository', 'full_name')`. Because these are two unrelated leaves of the same attacker-controlled JSON body, an entity holding a valid webhook secret for one configured Shipit organization can sign a payload whose `repository.owner.login` matches their own org (passing signature verification) while `repository.full_name` points at a different, victim organization's repo, causing `Repository.from_github_repo_name` to resolve and mutate the victim's stack/review-stack.

### Finding Description
Binding claimed and traced: `organization_verifying_signature == organization_owning_mutated_stack`.

- `verify_signature` in [1](#0-0)  computes `github_app = Shipit.github(organization: repository_owner)` and verifies the raw HMAC against that org's secret, where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) .
- `Shipit.github(organization:)` in [3](#0-2)  looks up a per-organization webhook secret from `secrets.github[organization]`, confirming this is a first-class multi-tenant configuration where each org has its own `webhook_secret` (see `github_app_config`, `github_organizations`) [4](#0-3) .
- Once verification passes, `WebhooksController#create` dispatches the raw parsed `params` hash to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) .
- `ClosedHandler#process` resolves the target repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5)  and then calls `review_stack.archive!` [7](#0-6) , which via `ReviewStackAdapter#archive!` deprovisions and archives the resolved stack, and the base `Handler` class independently derives targets the same way via `payload.dig('repository', 'full_name')` [8](#0-7) .

Root cause: `repository.owner.login` (used for signature/secret selection) and `repository.full_name` (used for target resolution) are never cross-validated against each other. GitHub's real webhook payloads always keep them consistent, but nothing in this engine enforces that invariant on the raw JSON body an attacker sends. An attacker who legitimately administers a repo/org onboarded as one tenant of a multi-org Shipit deployment (and therefore knows that tenant's `webhook_secret`, as they configured it when integrating the webhook) can freely author `repository.full_name` to name any other repository, including one owned by a completely different, victim organization. The HMAC signs the exact raw body the attacker crafted, so the signature check in `verify_webhook_signature` (`app/models/shipit/github_app.rb` around lines 76-83) passes using the attacker's own known secret, while the mutation lands on the victim's `full_name`-addressed repository/stack.

None of the listed guards prevent this: `drop_unhandled_event` only checks event type presence; the `ExplicitParameters` schema in `ClosedHandler` only validates types/presence of fields, not cross-field consistency between `repository.owner.login` and `repository.full_name`; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` in the webhook path since webhooks are inherently server-to-server and authenticated only by HMAC.

### Impact Explanation
A correctly-signed webhook from organization A can archive, deprovision, and mutate PR/stack bookkeeping (`Stack#archive!`, `remove_from_provisioning_queue`, `deprovision`) belonging to organization B's stack, entirely because the signature-selection field and the target-resolution field are independent leaves of the same attacker-supplied JSON. This matches the listed Critical category "a payload for one repository mutating another's stack," and is repeatable against any repository/stack tracked by the Shipit instance as long as the attacker can guess or enumerate `owner/name` full names (stack pages/URLs are often not secret). The same class of divergence applies to every other `pull_request` handler using `params.repository.full_name` independently of the signature check's `repository.owner.login` (e.g. `OpenedHandler`, `ReopenedHandler`, `EditedHandler`, `AssignedHandler`, `label_capturing_handler`), broadening blast radius beyond just `ClosedHandler`.

### Likelihood Explanation
Requires the Shipit instance to be configured in the multi-organization mode (`secrets.github` keyed by multiple orgs, each with its own `webhook_secret`) — a supported, documented configuration per `lib/shipit.rb#github_app_config` and `docs/setup.md`. The attacker only needs to be a legitimate tenant/admin of one configured org (knows their own org's `webhook_secret`) and to know or guess a victim repository's `owner/name`. No Shipit session, API token, or GitHub org membership in the victim org is needed — only the ability to POST a hand-crafted JSON body with a correct HMAC computed from their own known secret. This is a single unauthenticated HTTP POST to `/webhooks`, fully repeatable and low-cost.

### Recommendation
In `WebhooksController#verify_signature` (or in `ClosedHandler`/`Handler` base class), enforce that the organization derived from `repository.full_name` matches `repository.owner.login` (or better, always derive the org used for signature verification and repository resolution from the same single field), and reject the webhook if they diverge. Additionally, after resolving the target `Repository` in each handler, verify its `owner` matches the organization whose secret validated the request signature before performing any mutation.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, using a multi-org secrets fixture like `test/dummy/config/secrets_double_github_app.yml`):

```ruby
test "cross-org signature does not authorize mutation of another org's stack" do
  # Setup: two tenants configured, "attacker-org" and "victim-org", each with distinct webhook_secret
  # (via secrets_double_github_app.yml style config).
  victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "repo")
  victim_stack = create_review_stack_for(victim_repo) # existing, un-archived

  attacker_secret = Shipit.github(organization: "attacker-org").send(:webhook_secret)

  payload = {
    action: "closed",
    number: victim_stack.pull_request.number,
    pull_request: { ..., head: { sha: "x", ref: "pr-branch" }, user: { login: "attacker" }, assignees: [], labels: [] },
    repository: { full_name: "victim-org/repo", owner: { login: "attacker-org" } }, # divergent fields
    sender: { login: "attacker" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", attacker_secret, payload)

  # LEFT side of binding: org whose secret verified signature
  assert Shipit.github(organization: "attacker-org").verify_webhook_signature(signature, payload)

  request.headers["X-Github-Event"] = "pull_request"
  request.headers["X-Hub-Signature"] = signature

  assert_difference -> { victim_stack.reload.archived? ? 1 : 0 }, 1 do
    post :create, body: payload, as: :json
  end

  # RIGHT side of binding: org owning the mutated stack
  assert_equal "victim-org", victim_repo.owner
  # Both sides diverge: "attacker-org" != "victim-org", yet mutation succeeded.
  assert_response :ok
  assert victim_stack.reload.archived?, "victim-org's stack was archived by an attacker-org-signed webhook"
end
```

This demonstrates the divergence: signature verification is bound to `attacker-org`'s secret while the actual database mutation (`Stack#archive!`) lands on `victim-org`'s stack, proving the cross-tenant authorization bypass.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
```
