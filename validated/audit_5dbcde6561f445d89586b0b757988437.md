### Title
Unbounded iteration over global `storage.assocUnstableMessages` in AA `data_feed`/`data_feed_exists` formula evaluation can DoS unit processing - (File: `data_feeds.js`)

### Summary
The oscript functions `data_feed` and `data_feed_exists`, which any AA trigger sender can invoke by posting a trigger unit to an Autonomous Agent, call into `dataFeeds.readDataFeedValue()` / `dataFeeds.dataFeedExists()` with the `bAA` flag set [1](#0-0) [2](#0-1) . When this flag is truthy, both functions execute an unbounded `for (var unit in storage.assocUnstableMessages)` loop that walks the entire in-memory map of every currently-unstable unit in the DAG, regardless of how many oracle addresses were requested [3](#0-2) [4](#0-3) . This is the same "unbounded for loop reachable by an ordinary caller" bug class as the reported `BatchRequests.sendWithdrawalRequests` finding, except here the loop bound is the size of a global, network-wide data structure rather than an owner-curated array.

### Finding Description
`storage.assocUnstableMessages` accumulates one entry per unstable unit carrying payloads (data feeds, definitions, votes, AA responses, etc.) until the unit is stabilized, at which point it is deleted in `main_chain.js`'s `saveUnstablePayloads()` [5](#0-4) . Until stabilization occurs, this map can grow arbitrarily large as more units are posted to the DAG (each new unstable unit adds one entry, and a network under load, or one with a malicious burst of unit postings/spam AA triggers, may keep many units unstable simultaneously).

Any AA author can write an AA whose formula calls `data_feed(...)` (with `ifseveral`/oracle lookups routed through the `bAA` branch) or `data_feed_exists(...)`. Both are executed synchronously for every trigger sent to that AA, during `handleTrigger` in `aa_composer.js`, which is invoked as part of ordinary consensus-critical unit stabilization/response processing. Every such formula call performs a full linear scan of `storage.assocUnstableMessages`, `.forEach`-ing over every message of every unstable unit, with no cap tied to the number of oracle addresses supplied by the caller (unlike `readDataFeedByAddress`, which uses a bounded KV range query per requested address).

### Impact Explanation
Because the loop bound is controlled by global network state (total count of currently-unstable units) rather than by input the AA author supplies, an attacker who floods the network with many unstable units (or simply relies on normal periods of high unstable-unit backlog) can make every `data_feed`/`data_feed_exists` call performed by any AA — triggered by any unprivileged AA trigger sender — cost time proportional to the size of that backlog. Since this code runs synchronously inside AA trigger handling, which occurs as part of processing/stabilizing units, repeatedly invoking such an AA (which any user can do just by sending trigger payments) can materially slow down or stall the node's unit processing pipeline, matching the "network unable to confirm new units" impact class from the reported analog.

### Likelihood Explanation
Likelihood is moderate: the attacker does not need any special privilege — only the ability to post units (to grow `assocUnstableMessages`) and to send AA triggers to any AA that uses `data_feed`/`data_feed_exists` (a common, documented oscript feature for oracle-based AAs). The severity scales with how large the unstable-unit backlog can get, which is influenced by normal network conditions as well as by an attacker's own unit-posting activity.

### Recommendation
Bound the `bAA`/unstable-lookup path in `dataFeedExists` and `readDataFeedValue` so it does not scan the entire `storage.assocUnstableMessages` map: e.g., maintain a secondary index of unstable data-feed messages keyed by author address (similar to how stable feeds are indexed by address in the KV store), so lookups scale with the number of oracle addresses requested rather than with the total number of unstable units in the system. Alternatively, impose an explicit cap on `storage.assocUnstableMessages` size or on the number of iterations per formula evaluation call, consistent with existing `MAX_COMPLEXITY`/`MAX_OPS` budgets in `aa_validation.js`/`definition.js`.

### Proof of Concept
1. An attacker posts a large volume of units/AA triggers so that many units remain unstable simultaneously (growing `storage.assocUnstableMessages`).
2. The attacker (or anyone) sends a trigger to an existing AA whose formula includes a call like `data_feed[oracles="ORACLE_ADDR", feed_name="x", ifseveral="last"]` or `data_feed_exists[...]`, executed through `formula/evaluation.js`'s `data_feed` case with `bAA` true [6](#0-5) .
3. `dataFeeds.readDataFeedValue()` enters the `bIncludeUnstableAAs` branch and iterates the full `storage.assocUnstableMessages` map [7](#0-6) , with cost proportional to the current (attacker-inflated) size of that map rather than to the number of oracle addresses in the trigger.
4. Repeating triggers to this AA while the backlog remains large causes disproportionate CPU time to be spent per trigger, slowing down node unit processing.
