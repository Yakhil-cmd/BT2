## Title
AAs reading `data_feed[[...]]` act on unstable oracle data whose sequence can later flip to `final-bad`, causing irreversible AA fund loss — (File: `data_feeds.js`, `formula/evaluation.js`)

### Summary
The Chainlink report flags that `latestRoundData()` is consumed without validating that the round/price is final and non-stale. The equivalent trust boundary in ocore is the `data_feed[[...]]` oscript function that AA definitions use to read oracle-posted values. When invoked from inside an AA, this function is allowed to read **unstable** (not-yet-final) oracle data by default and has no mechanism for the AA author to require finality, so an AA can commit irreversible actions (payments, state changes) based on data that is later invalidated.

### Finding Description
`data_feed[[...]]` in `formula/evaluation.js` calls `dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ifseveral, ...)`, passing `bAA` (true whenever the formula executes inside an AA) as the `unstable_opts` argument. [1](#0-0) 

Inside `readDataFeedValue`, `bIncludeUnstableAAs = !!unstable_opts` is therefore always true for AA evaluations, causing the function to scan `storage.assocUnstableMessages` — units that are not yet stable/final — for `data_feed` messages from the requested oracle addresses, and to use them as the returned value: [2](#0-1) 

The only filter applied is `objUnit.sequence !== 'good'`, which excludes units already known to be temp-bad/final-bad at read time: [3](#0-2) 

However, `sequence` for an unstable unit is not final. It is assigned during validation in `validateAuthor` and can later be **flipped** when the unit's main-chain-index stabilizes and `findStableConflictingUnits` discovers a genuine serial conflict: [4](#0-3) [5](#0-4) 

`markMcIndexStable`'s `handleNonserialUnits` explicitly re-evaluates and can set a previously-"good" unstable unit's final sequence to `final-bad` at stabilization time, and `propagateFinalBad` cascades this to dependents: [6](#0-5) 

Because an AA's response (payments, state variable updates) is composed and broadcast at trigger time — before the underlying oracle unit is stable — the AA can execute and irreversibly transfer funds or mutate state based on an oracle data-feed value that is later determined not to be a legitimate/serial unit (i.e., the "round" is effectively voided after the fact). There is no parameter exposed to `data_feed[[...]]` that lets the AA author require the queried oracle unit to be stable/final before using its value; unstable inclusion is hard-coded whenever `bAA` is true.

This mirrors the reported bug class precisely: the code consumes external oracle input (`data_feed` payload) without validating that it corresponds to a finalized/non-reversible "round," analogous to skipping `answeredInRound >= roundId` / staleness checks on Chainlink data.

### Impact Explanation
An AA that reads a data feed value from an oracle-posted but not-yet-stable unit can act on that value (e.g., trigger a payout, mint/burn shares, or record a price used for later calculations) before the network has finished determining whether that unit is a legitimate part of the DAG. If the unit is later ruled non-serial and voided (`sequence` → `final-bad`), the AA's already-executed, irreversible response was based on data that the network subsequently disowns — this can lead to AA fund loss/misallocation (e.g., paying out at an incorrect price) with no way to roll back the AA's already-sent messages.

### Likelihood Explanation
Triggering requires an oracle whose posted data-feed unit ends up in a serial conflict that resolves to `final-bad` after being read as "good" by a pending AA trigger — most plausible if the oracle address itself becomes involved in address-definition/serial conflicts (e.g., a compromised or misbehaving oracle key posts conflicting units), or during chain reorganizations at MC-index stabilization boundaries. It is a narrower attack surface than a fully open network condition, but it is a real, reachable code path baked into every AA that uses `data_feed[[...]]`, since unstable-oracle inclusion is unconditional for AAs and not opt-out.

### Recommendation
- Require finality/stability of the oracle-authored unit before its data-feed value is used by an AA, or expose an explicit opt-in flag (e.g., `unstable=true`) so unstable reads are a deliberate AA-author choice rather than the unconditional default.
- If unstable reads must remain the default for latency reasons, additionally validate at stabilization time that any AA response already sent based on an unstable data-feed value that later becomes `final-bad` is flagged/logged so integrators can detect and mitigate divergence, and document the residual risk prominently for AA authors performing financial actions based on `data_feed[[...]]`.

### Proof of Concept
1. Oracle `O` posts unit `U1` (unstable) containing `data_feed: { PRICE: 100 }`.
2. An AA trigger arrives referencing `data_feed[[oracles=O, feed_name=PRICE]]` while `U1` is still unstable; `readDataFeedValue` includes `U1` because `objUnit.sequence === 'good'` at that moment (per `data_feeds.js:217-224`).
3. The AA composes and sends a payment based on `PRICE=100` immediately (AA responses do not wait for trigger stabilization).
4. Before `U1` stabilizes, oracle `O`'s address is involved in a serial conflict (e.g., two units built on diverging parents by the same address), and at `markMcIndexStable` time `findStableConflictingUnits` determines `U1` is the losing competitor, flipping its `sequence` to `final-bad` (`main_chain.js:1326-1351`).
5. The AA's payment, already sent based on the now-invalidated `PRICE=100` data feed, cannot be reversed, resulting in fund loss/mispriced payout inconsistent with the data feed value ultimately recognized by the network.
