### Title
CCMenu API token issued for one stack grants read access to every stack's deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The `ApiClient` model supports scoping a token to a single stack via `stack_id`, and `Api::BaseController` enforces that scope whenever a stack is resolved through the `stacks`/`stack` helpers. `Api::CCMenuController`, however, overrides `stack` to resolve the stack directly from the request parameter instead of going through the scoped `stacks` collection, so a CCMenu token minted for one stack can be replayed with a different `stack_id` to read any other stack's deploy status.

### Finding Description
`ApiClient` records may optionally `belongs_to :stack` and `Api::BaseController#stacks` uses that association to restrict which stacks a scoped token may touch: [1](#0-0) 

`CCMenuUrlController#client` mints an `ApiClient` with the `read:stack` permission but **without** setting `stack:`, so the token it embeds in the generated CCMenu URL is not bound to the stack the user requested it for: [2](#0-1) 

`Api::CCMenuController` then overrides `stack` (instead of using the scoped `stacks` helper from `BaseController`) and resolves it straight from `params[:stack_id]`, with authorization limited to the coarse-grained `require_permission :read, :stack` check that only verifies the `read:stack` permission string is present on the token, not which stack it is tied to: [3](#0-2) 

The binding that is broken is: *the stack a token authorises* (intended: the single stack for which the CCMenu URL was generated) *≠ the stack the request actually touches* (any stack, chosen by the caller's `stack_id` parameter). This is the same class of bug as the Omni report's `withdraw()`/`deposit()` pause mismatch: one component's state (the token's intended scope) is decoupled from the component that actually acts (the controller resolving an arbitrary stack), letting an unprivileged holder of one legitimate CCMenu token cross the intended boundary.

### Impact Explanation
Any user who obtains a legitimate CCMenu URL for a stack they're permitted to see (these URLs are routinely embedded in dashboards, CI widgets, or shared informally since they are meant to expose low-sensitivity build-status XML) can strip the `token` query parameter and reattach it to `api_stack_ccmenu_url` for **any other stack id** in the Shipit instance. The response includes deploy/rollback state (`stack.deploys_and_rollbacks.last`) for stacks the token holder was never granted visibility into, i.e., unauthenticated-style read of stack deploy state across the whole instance using a token that was only ever meant to authorize one stack.

### Likelihood Explanation
High likelihood: no special privilege is required beyond having been granted a CCMenu URL for any single stack (a routine, low-friction action any authenticated Shipit user can request for stacks they can view), and exploitation is a trivial parameter substitution with no additional credential needed. This directly matches the pattern flagged in the report: a value ("the stack the token is scoped to" ~ "ACTION_WITHDRAW state") is bypassed because a different code path (the CCMenu controller's own `stack` resolution, analogous to a mispaused bridging leg) doesn't enforce the same binding as the rest of the API stack (`Api::BaseController#stacks`).

### Recommendation
- Set `stack:` on the `ApiClient` created in `CCMenuUrlController#client` so the token is actually scoped to the requested stack.
- Remove the `stack` override in `Api::CCMenuController` and use the inherited, scope-respecting `stacks`/`stack` resolution from `Api::BaseController` (or explicitly check `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id`) before rendering.

### Proof of Concept
1. As User A (who has access to Stack #1), visit `GET /1-environment/ccmenu` → `CCMenuUrlController#fetch` returns a URL like `.../api/1/ccmenu?token=<TOKEN>`, where `<TOKEN>` is an `ApiClient` with `permissions: [read:stack]` and no `stack_id`.
2. Take `<TOKEN>` and request `GET /api/2/ccmenu?token=<TOKEN>` (Stack #2 that User A has no access to).
3. `Api::CCMenuController#authenticate_api_client` authenticates the token, `require_permission :read, :stack` passes (token has `read:stack`), and `stack` resolves `Stack.from_param!(2)` directly — the XML response discloses Stack #2's latest deploy/rollback status despite the token having been minted only for Stack #1.

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
```
