### Title
Concurrent, unlocked validation of private-payment chains allows a private-asset output to be double-spent - ([File: private_payment.js])

### Summary
`private_payment.js:validateAndSavePrivatePaymentChain` (lines 23-119) performs a "check-then-write" sequence (read asset info, `BEGIN`, SELECT for a pre-existing/duplicate output row, then INSERT the new inputs/outputs) inside its own dedicated DB transaction, with **no mutex serializing this operation per output/asset/address**. `network.js:network.js:2443-2521 handleSavedPrivatePayments` explicitly drives multiple pending private chains through this exact function using `async.each` ("handle different chains in parallel"), i.e. concurrently, on separate DB connections/transactions. [1](#0-0) [2](#0-1) 

### Finding Description
This mirrors the CVE-2019-17341 bug class: a resource-ownership/validity check ("is this output already claimed / not yet spent?") is performed, and a privileged write (crediting the payment, marking the source coin consumed) is committed later, but the window between check and write is not protected against a concurrent, colluding "second write" that changes the state the check relied on.

In `ocore`, `validateAndSavePrivatePaymentChain` (`private_payment.js:23`) reads the asset, opens a fresh `conn`, does `BEGIN`, then runs a duplicate-detection `SELECT` against `outputs` (`private_payment.js:70-107`) before calling `divisibleAsset.validateAndSavePrivatePaymentChain` / `indivisibleAsset.validateAndSavePrivatePaymentChain`, which insert the spend (`INSERT INTO inputs...`, `UPDATE outputs SET is_spent=1...`, `divisible_asset.js:57-70`). [3](#0-2) 

The underlying double-spend detection used for these inputs, `checkForDoublespends` / `checkInputDoubleSpend` in `validation.js`, only takes a lock (`mutex.lock(["private_write"])`) in the branch where an *existing conflicting row is already found* (i.e. it is only used to un-mark a previous claimant, `validation.js:2283-2295`). When **no conflicting row exists yet** — which is exactly the state during the race window, before either concurrent transaction has committed — `checkForDoublespends` returns immediately with no lock at all (`validation.js:1661-1667`, "if (rows.length === 0) return cb();"). [4](#0-3) [5](#0-4) 

Because each invocation of `validateAndSavePrivatePaymentChain` runs in its own `BEGIN...COMMIT` transaction and no application-level mutex (e.g. `mutex.lock(['private_write'])`, `mutex.lock(['handleJoint'])`, or a per-source-output lock) wraps the entire check-then-insert sequence for the *initial* claim, two private-payment chains that both spend the *same* underlying private output (attacker crafts two variant chains referencing the same `src_unit/src_message_index/src_output_index`, differing only in destination/blinding) can be delivered to the same wallet at the same time (e.g. queued in `unhandled_private_payments` and replayed by `handleSavedPrivatePayments`, or delivered simultaneously by direct peer and via hub). Each is processed on its own connection, each SELECT sees no conflicting `inputs` row yet, both commit independently, and both end up recorded as valid/serial spends of the same private coin. [2](#0-1) 

### Impact Explanation
This is a double-spend of a private-asset output reachable purely by a private-payment counterparty (no malicious node/hub/peer/network assumption is required — a normal correspondent or textcoin sender can trigger it). A successful race lets an attacker have the same private coin accepted twice by the victim's own node (recorded with `is_unique=1`/serial for both spends), inflating the recipient's or a colluding recipient's private-asset balance beyond what the issuer/payer actually transferred — a concrete case of unauthorized spending / asset-supply inconsistency for private assets, matching the "double-spend of a stable output" acceptance criterion.

### Likelihood Explanation
Exploitability depends on winning a narrow timing race between two independent DB transactions, which is inherently non-deterministic, but the codebase explicitly creates the parallel-processing condition (`async.each` "handle different chains in parallel" in `handleSavedPrivatePayments`) and the vulnerable window (`checkForDoublespends` with `rows.length === 0` requires no lock) is not rare — it's the normal, common path for any first-time spend, making the attack surface real for a patient/adversarial peer that can influence delivery/retry timing of two conflicting private chains (e.g. by controlling network latency to trigger simultaneous delivery+resend).

### Recommendation
Serialize the entire "duplicate-check → validate → insert-spend" sequence per (asset, src_unit, src_message_index, src_output_index) — or globally under the existing `mutex.lock(['private_write'])` — for private payment processing, not just the "accept a doublespend / un-unique a previous claim" branch. In particular, wrap `private_payment.js:validateAndSavePrivatePaymentChain`'s BEGIN…duplicate-check…COMMIT sequence, and the parallel dispatch in `wallet.js:handleSavedPrivatePayments`, so that concurrent chains touching the same source output are processed strictly one at a time (e.g. `async.eachSeries` instead of `async.each`, plus a mutex keyed by the spent output).

### Proof of Concept
1. Attacker (or two colluding correspondents) creates two private payment chains `chainA` and `chainB` that both consume the same private output `(src_unit, src_message_index, src_output_index)` of a fixed-denomination or divisible private asset, sending the coin to two different addresses/units.
2. Both chains are delivered to the victim wallet nearly simultaneously — e.g. one via direct P2P `handleOnlinePrivatePayment` and the other queued in `unhandled_private_payments`, then triggered by `handleSavedPrivatePayments`'s `async.each`, which starts multiple `privatePayment.validateAndSavePrivatePaymentChain` calls concurrently on separate DB connections.
3. Each call's `BEGIN` transaction runs the duplicate/conflict `SELECT` in `private_payment.js` and `checkForDoublespends` in `validation.js` before either transaction has committed its `INSERT INTO inputs`; both see zero conflicting rows and proceed.
4. Both transactions `COMMIT` independently, each recording the same source coin as spent to a different destination with `is_unique=1`, resulting in the victim's wallet (and ledger view) accepting two valid spends of one private coin.
